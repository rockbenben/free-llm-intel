# 重建“信任链”：Kimi Vendor Verifier [![GitHub](https://img.shields.io/badge/GitHub-181717?style=flat&logo=github&logoColor=white)](https://github.com/MoonshotAI/Kimi-Vendor-Verifier)

在发布 Kimi K2.6 模型的同时，我们开源了 Kimi Vendor Verifier（KVV）项目，帮助开源模型的用户验证自己推理实现的准确性。

这不是事后补上的想法，而是因为我们在实践中吃够了苦头才明白：开源一个模型只是打赢了一半的仗，另一半是确保它在别处也能正确运行。

## 为什么要做 KVV

**从个别事件到系统性问题**

自 K2 Thinking 发布以来，社区关于 benchmark 分数异常的反馈一直不断。我们排查后确认，其中相当一部分源于解码参数用错。为了立刻缓解这个问题，我们在 API 层建起第一道防线：在 Thinking 模式下强制 Temperature=1.0、TopP=0.95，并强制校验 thinking 内容是否被正确回传。

然而，更隐蔽的异常很快又敲响了警钟。在 [LiveBenchmark](https://www.reddit.com/r/LocalLLaMA/comments/1osglws/kimi_k2_thinking_scores_lower_than_gemini_25/?rdt=41412) 上的一次评测中，我们看到第三方 API 与官方 API 之间存在鲜明反差。在对多家基础设施提供商做了大量测试之后，我们发现这种差异相当普遍。

这暴露了开源模型生态里更深层的问题：权重越开放、部署渠道越多元，质量就越难以掌控。

如果用户无法区分“模型能力缺陷”和“工程实现偏差”，对开源生态的信任必然崩塌。

## 我们的方案

**六个关键 benchmark**（专门挑选出来暴露特定基础设施故障）：

- [预校验](https://github.com/MoonshotAI/Kimi-Vendor-Verifier?tab=readme-ov-file#3-pre-flight-check)：验证 API 参数约束（temperature、top_p 等）是否被正确执行。所有测试通过后才会进入 benchmark 评测。
- [OCRBench](https://github.com/MoonshotAI/Kimi-Vendor-Verifier?tab=readme-ov-file#ocrbench-quick-validation)：面向多模态流水线的 5 分钟冒烟测试。
- [MMMU Pro](https://github.com/MoonshotAI/Kimi-Vendor-Verifier?tab=readme-ov-file#mmmu-pro-vision)：用多样化的视觉输入检验 Vision 输入预处理。
- [AIME2025](https://github.com/MoonshotAI/Kimi-Vendor-Verifier?tab=readme-ov-file#aime-2025)：长输出压力测试，能抓出短 benchmark 掩盖的 KV cache bug 和量化退化。
- [K2VV ToolCall](https://github.com/MoonshotAI/K2-Vendor-Verifier)：衡量触发一致性（F1）与 JSON Schema 准确率。工具错误在 agent 中会层层放大，我们要尽早发现。
- SWE-Bench：完整的 agentic 编码测试。（因依赖沙箱，未开源）

**上游修复**：我们深入参与 vLLM/SGLang/KTransformers 社区，从根因上修复问题，而不只是检测症状。

**发布前验证**：与其等部署之后收到抱怨，我们提前开放测试模型。基础设施提供商可以在用户遇到问题之前先验证自己的技术栈。

**持续 benchmark**：我们会维护一份公开的各厂商结果排行榜。这种透明度会促使厂商把准确性放在优先位置。

## 测试成本估算

我们在两台 NVIDIA H20 8-GPU 服务器上完成了完整评测流程的验证，串行执行约需 15 小时。为提升评测效率，脚本针对长时间运行的推理场景做了优化，包括流式推理、自动重试和 checkpoint 续跑机制。
