## 为什么我们构建 KVV

**从孤立事件到系统性问题**

自 K2 Thinking 发布以来，我们经常收到社区关于基准分数异常的反馈。我们的调查证实，这些案例很大一部分源于解码参数的滥用。为了立即缓解这种情况，我们在 API 级别构建了第一道防线：在思考模式下强制Temperature=1.0 和 TopP=0.95，并强制验证思考内容是否正确传回。

然而，更微妙的异常现象很快引发了我们的警报。在[LiveBenchmark](https://www.reddit.com/r/LocalLLaMA/comments/1osglws/kimi_k2_thinking_scores_lower_than_gemini_25/?rdt=41412)的具体评测中，我们观察到第三方API与官方API之间形成了鲜明的对比。经过对各个基础设施提供商的广泛测试，我们发现这种差异很普遍。

这暴露了开源模型生态中更深层次的问题：权重越开放，部署渠道越多样化，质量就越不可控。

如果用户无法区分“模型能力缺陷”和“工程实现偏差”，对开源生态的信任将不可避免地崩溃。

## 我们的解决方案

**六个关键基准**（选择用于暴露特定的基础设施故障）：

- [预验证](https://github.com/MoonshotAI/Kimi-Vendor-Verifier?tab=readme-ov-file#3-pre-flight-check)：验证 API 参数约束（温度、top_p 等）是否正确执行。在进行基准评估之前，所有测试都必须通过。
- [OCRBench](https://github.com/MoonshotAI/Kimi-Vendor-Verifier?tab=readme-ov-file#ocrbench-quick-validation)：多模式管道的 5 分钟烟雾测试。
- [MMMU Pro](https://github.com/MoonshotAI/Kimi-Vendor-Verifier?tab=readme-ov-file#mmmu-pro-vision)：通过测试不同的视觉输入来验证视觉输入预处理。
- [AIME2025](https://github.com/MoonshotAI/Kimi-Vendor-Verifier?tab=readme-ov-file#aime-2025)：长输出压力测试。捕获短基准测试隐藏的 KV 缓存错误和量化退化。
- [K2VV ToolCall](https://github.com/MoonshotAI/K2-Vendor-Verifier)：测量触发器一致性 (F1) 和 JSON 架构准确性。工具错误在代理中复合；我们很早就抓住了他们。
- SWE-Bench：完整的代理编码测试。 （由于依赖沙箱，未开源）

**上游修复**：我们嵌入 vLLM/SGLang/KTransformers 社区来修复根本原因，而不仅仅是检测症状。

**发布前验证**：我们提供对测试模型的早期访问，而不是等待部署后投诉。这使得基础设施提供商可以在用户遇到问题之前验证其堆栈。

**持续基准测试**：我们将维护供应商结果的公共排行榜。这种透明度鼓励供应商优先考虑准确性。

## 测试成本估算

我们在两台 NVIDIA H20 8-GPU 服务器上完成了完整的评估工作流程验证，顺序执行大约需要 15 小时。为了提高评估效率，脚本针对长时间运行的推理场景进行了优化，包括流式推理、自动重试和检查点恢复机制。
