# 使用 Amazon EC2 Spot 在 AWS 上优化 AssemblyAI 语音到文本推理的成本

语音到文本的推理是计算密集型的。每个音频文件都会触发在 NVIDIA GPU 上运行的深度学习模型（声学模型、语言模型和后处理阶段）的管道，以满足延迟要求。从规模上看，这意味着数千个 GPU 实例连续运行。

[AssemblyAI](https://www.assembleai.com/) 需要一种方法来经济高效地大规模运行 GPU 密集型推理工作负载，同时又不牺牲客户所依赖的可用性和延迟保证。完全在按需实例上运行成本高昂。 Spot 实例可以显着节省成本，而 Amazon Elastic Compute Cloud (Amazon EC2) 可以在其他地方需要容量时通过 2 分钟警告来回收它们。 AssemblyAI 需要一种架构，能够优雅地吸收 Spot 中断，同时维持服务级别协议 (SLA) 承诺。此外，医疗保健、金融和法律等受监管行业的客户必须将音频数据保存在特定的地理边界内。他们在欧洲 AWS 区域实施严格的数据驻留配置。

AssemblyAI 在 [AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-n24l7xlhzr4o6) 上提供，提供用于转录、说话人检测、情绪分析、章节检测和个人身份信息 (PII) 编辑的 API。他们的模型可以转录和分析技术、媒体、医疗保健和金融服务等行业的大量工作负载的语音。

在这篇文章中，我们将向您展示 AssemblyAI 如何为其语音转文本平台大规模运行成本优化的人工智能推理。该架构使用 Amazon Elastic Container Service (Amazon ECS)、Amazon Elastic Compute Cloud (Amazon EC2) Spot 实例和 Amazon Simple Queue Service (Amazon SQS)。这些服务结合了灵活的 NVIDIA GPU、ECS 容量提供程序和基于队列的重试机制。结果是显着节省成本，同时维持欧洲 AWS 区域的 SLA 承诺。

## 解决方案概述

AssemblyAI 的推理平台在 Amazon ECS 上运行，并通过 ECS 容量提供商管理计算容量。该队列在多个 NVIDIA GPU 实例系列中混合使用 Amazon EC2 Spot 实例和按需实例，在数千个实例的规模上为每个 GPU 运行一个推理模型。该架构建立在四大支柱之上，它们共同提供成本优化且具有弹性的推理：

- Amazon ECS 容量提供商混合现货和按需。
- 跨 EC2 实例类型（例如 g4dn.xlarge、g4dn.2xlarge、g5.xlarge、g5.4xlarge 和 g6.2xlarge）的多系列 GPU Spot 多样化。
- 基于队列的重试架构，使用 Amazon SQS 进行中断恢复。
- 在美国西部（俄勒冈州）us-west-2 和欧洲（伦敦）eu-west-2 进行区域部署，以实现数据驻留合规性。

Amazon ECS 集群在跨多个可用区的 Virtual Private Cloud (VPC) 内运行。该集群托管 GPU 支持的 ECS 任务（显示为 ECS 任务、GPU Spot 1 和 ECS 任务 GPU Spot 2），这些任务轮询队列并处理推理作业。每个任务都会从 Amazon Simple Storage Service (Amazon S3) 检索音频文件，并将完成的转录写入结果存储，AssemblyAI 将其配置为将输出交付给最终客户。

当 Spot 实例收到中断通知时，Amazon EventBridge 会调用 Spot 中断处理程序（AWS Lambda 函数）。处理程序将正在进行的作业返回到主作业 SQS 队列，以便另一个正常运行的 ECS 任务可以拾取它。客户将其系统配置为将耗尽重试尝试的作业路由到死信 SQS 队列进行调查。 Amazon CloudWatch Metrics 监控队列的运行状况和 Spot 中断事件，提供整个系统的可观察性。

## Amazon ECS 容量提供商和 Spot 多元化

为了在不影响可靠性的情况下优化推理成本，AssemblyAI 在每个 ECS 集群内的单个容量提供程序策略中配置多个容量提供程序。按需容量提供程序充当始终在线的基准，而现货容量提供程序则跨越不同的 GPU 实例系列和可用区来满足需求高峰。每个容量提供商都与一个 Amazon EC2 Auto Scaling 组关联。 Amazon ECS 托管扩展可根据容量提供程序权重和待处理的推理任务自动扩展 GPU 实例。当任务队列增长时，Spot 容量提供程序会从多元化池中请求更多实例。当需求下降时，实例会优雅地缩小。

最有效的 Spot 最佳实践之一是灵活地适应各种实例类型，以增加获得所需聚合计算容量的机会。 AssemblyAI 的基础设施不依赖于单个 GPU 实例系列，而是跨越三个 Amazon EC2 GPU 实例系列：

- **g4dn 实例** – 由 NVIDIA T4 GPU 提供支持，为标准语音识别模型提供经济高效的基准。
- **g5 实例** – 配备 NVIDIA A10G GPU，为要求更高的模型架构提供更高的吞吐量。
- **g6 实例** – 采用 NVIDIA L4 GPU，为大型模型（包括基于大型语言模型的推理）提供更高的性价比。

通过跨实例系列和规模分散需求，AssemblyAI 从更大的可用 Spot 容量池中获取资源。使用[价格-容量优化分配策略](https://docs.aws.amazon.com/autoscaling/ec2/userguide/allocation-strategies.html)，Amazon EC2 以最低的价格从 Spot 容量池中配置具有最高可用容量的实例，从而降低了中断的可能性。

## 基于队列的重试以实现中断恢复

在 Spot 中断期间保持服务质量是一项核心设计要求。 AssemblyAI 使用 Amazon SQS 将作业提交与执行分离。当转录请求到达时，它会被放入 Amazon SQS 队列中。在 GPU 实例上运行的 Amazon ECS 任务轮询队列、拉取作业并执行推理管道。个别作业通常需要 15 秒到几分钟，具体取决于音频长度。

当 Spot 实例收到 2 分钟中断通知时，重试流程如下：

- 可以在 2 分钟窗口内完成的正在进行的作业正常完成。需要更多时间的作业将返回到 Amazon SQS 队列，其他工作人员可以立即使用它们。
- 另一个运行状况良好的 GPU 实例可能会在不同的实例类型或不同的可用区中获取消息，并完成推理。

为了缩短恢复时间，AssemblyAI 在大约 2 分钟内创建了包含模型工件和容器映像的自定义 Amazon 系统映像 (AMI)。对于最终客户而言，Spot 中断的影响是处理时间略有增加，但转录会成功完成并按预期交付。

## 数据驻留的区域部署

在多个 AWS 区域中运行使得 AssemblyAI 能够为受监管行业的客户提供支持，包括医疗保健、金融服务和法律服务，在这些行业中，音频数据绝不能离开特定的地理边界。每个 AWS 区域都运行完全独立的推理架构副本：自己的 Amazon SQS 队列、Amazon ECS 集群、容量提供程序和 GPU 队列。这些欧洲区域提供多个 GPU 实例系列（g4dn、g5、g6），并且具有具有竞争力的现货价格。这种实例多样性支持可靠的基于 Spot 的推理服务，同时满足严格的数据驻留要求。

## 结果

通过在生产环境中运行带有 GPU 的 Amazon EC2 Spot 实例，与按需定价相比，AssemblyAI 在推理计算方面实现了 70% 的成本节省。随着该平台的计算需求同比增长近 4 倍，基于 Spot 的架构保持了单位经济效益的可持续发展。在如此规模的运营中，AssemblyAI 了解到，实例系列和规模的多样化是最大限度降低 Spot 中断率的最有效手段。 g4dn、g5 和 g6 系列可接入独立的容量池，因此当一个系列遇到容量压力时，其他系列仍然可用。从第一天开始就通过基于队列的重试和快速预热来设计容错，将 Spot 中断转变为例行事件，同时维护 SLA 承诺。

＃＃ 结论

运行具有相似特征的批量或近实时 AI 工作负载（GPU 计算上的短期、独立可重试作业）的团队可以应用此模式。首先使实例系列多样化并构建基于队列的容错能力，以在不影响可用性的情况下利用经济高效的 Spot 基础设施。
