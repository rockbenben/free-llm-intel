# 在 Amazon SageMaker HyperPod 上微调 GPT-OSS-20B 以实现多语言推理

GPT-OSS-20B 是一个用英语思考的开放权重推理模型。要求它用法语、德语、西班牙语或意大利语推理时，它会表示接受这条指令，但随后仍然用英语生成思维链。在包含 50 个样本的多语言推理测试中，基础模型只有 22% 的情况下用正确的目标语言推理。这 22% 几乎全部来自英语样本（英语 100%，法语 0%，德语 10%，西班牙语 0%，意大利语 0%）。

对于要为非英语用户部署推理模型的团队来说，这个差距很重要。用法语提问的用户期望模型用法语推理和作答，而不是在思考中途切换成英语。弥合这个差距是一个微调问题。它引出了一个每个团队在开始定制开放权重模型后都会面对的问题：监督微调（SFT）、使用组相对策略优化（GRPO）的强化学习，还是两者都用？

在本文中，我们介绍如何在 [Amazon SageMaker HyperPod](https://aws.amazon.com/sagemaker/hyperpod/) 上微调 GPT-OSS-20B 以实现多语言推理。我们展示了何时单独使用 SFT 就已足够，以及 GRPO 在哪些地方叠加了可衡量的价值。为了更广泛地理解 GRPO 何时有帮助，我们还在两个能力差距不同的任务上运行了一项受控的 Qwen2.5-7B 实验。简短的回答是：SFT 承担了大部分工作，GRPO 在有提升空间时做细化，而让技术与能力差距相匹配才是决定结果的关键。

## 解决方案概述

本节介绍多语言推理任务与数据集、SFT 和 GRPO 如何互补，以及我们在 Amazon SageMaker HyperPod 上运行的训练栈。

### 任务与数据集

数据集是 `HuggingFaceH4/Multilingual-Thinking` —— 一个思维链推理数据集，除英语外还翻译成了法语、西班牙语、德语和意大利语，大约包含 949 个训练样本和 50 个验证样本。模型会收到一条 `reasoning language:` 系统提示指令，必须用该目标语言同时进行推理和给出答案，从而覆盖其强烈的英语先验。评估包含 50 个测试用例：5 种语言（EN/FR/DE/ES/IT）各 10 道数学/逻辑题。

有两个指标很重要：

- **推理语言正确** – 思维链是否使用了所请求的语言？
- **答案语言正确** – 最终答案是否使用了所请求的语言？

### SFT 与 GRPO 如何配合

理解这两种技术最清晰的方式是：SFT 教会模型一种它原本不具备的行为。GRPO 优化的是模型已经偶尔能产生的行为。GRPO 的工作方式是为每个提示采样一组回答，并把策略推向高于平均水平的那部分。如果期望的行为在基础分布中的概率为零，GRPO 就几乎没有可强化的对象。这一个观点几乎解释了本文中的每一个结果。

### 训练栈

我们在由 Amazon Elastic Kubernetes Service（Amazon EKS）编排的 Amazon SageMaker HyperPod 上运行。对于 GPT-OSS-20B 上最初的 SFT 和 GRPO 运行，我们使用了 PyTorch TRL 库。对于 Qwen 对照实验，我们改用 veRL 作为训练器，用 Ray 和 KubeRay 做分布式编排，用 vLLM 做快速的 rollout 生成。检查点和数据集存放在 Amazon FSx for Lustre 上，节点间的网络结构使用 Elastic Fabric Adapter（EFA）。所有微调都使用了低秩适配（LoRA），它参数高效，非常适合 SFT 和 GRPO。

下图端到端地展示了训练数据路径。用户提交的任务落在 Amazon SageMaker HyperPod 集群的 Amazon EKS 控制平面上。Amazon EKS 调度一个 Ray head pod 以及若干运行 veRL 训练器和 vLLM rollout worker 的 worker pod。两组 pod 都挂载 Amazon FSx for Lustre，以获取基础模型、训练数据和检查点。节点间的集合通信使用 EFA。Rollout 从 vLLM 流回 veRL 训练器，训练器再把检查点写回 Amazon FSx for Lustre。

![Amazon SageMaker HyperPod 上的端到端微调架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/08/ML-21403-1.png)

图 1：在 Amazon SageMaker HyperPod 上使用 veRL、Ray、KubeRay、vLLM 和 Amazon FSx for Lustre 进行 SFT 和 GRPO 微调的端到端训练数据路径，用于 Qwen 对照实验

下面更详细地描述每一跳。提交者从 Amazon SageMaker Studio 或 AWS Command Line Interface（AWS CLI）启动运行。Amazon SageMaker HyperPod 上的 Amazon EKS 控制平面把 pod 放置到 GPU 节点上，并启动一个 Ray head 以及供 veRL 训练器和 vLLM rollout worker 使用的 worker pod。Amazon FSx for Lustre 为基础模型、训练数据和检查点提供共享的高吞吐存储。训练完成后，训练器把 LoRA 适配器写回 Amazon FSx for Lustre，用于下游评估或服务。

## 先决条件

要跟着操作，你需要：

- 一个由 Amazon EKS 编排的 Amazon SageMaker HyperPod 集群。GPT-OSS 的 SFT 使用了 4× ml.g6e.12xlarge（16× L40S 48GB）。Qwen 对照使用了 2× g6e.48xlarge（16× L40S）。
- 一个挂载到集群上的 Amazon FSx for Lustre 文件系统，在 `/fsx` 处有一个名为 `fsx-claim` 的 `PersistentVolumeClaim`。
- 支持 EFA 的实例，以及可用的 NVIDIA Collective Communications Library（NCCL）和 `aws-ofi-nccl` 栈，用于多节点 SFT。
- 一个容器镜像仓库，例如 Amazon Elastic Container Registry（Amazon ECR），用来存放从参考仓库构建的训练镜像。
- 一个 HuggingFace 访问 token，用于 `openai/gpt-oss-20b` 和 `HuggingFaceH4/Multilingual-Thinking` 数据集。
- 工作站上可用的 AWS Command Line Interface（AWS CLI）、`kubectl`、`docker` 和 `envsubst`。

## 搭建训练环境

下文引用的所有命令、清单和脚本都位于 [awsome-distributed-ai](https://github.com/aws-samples/awsome-distributed-ai) GitHub 仓库的 `3.test_cases/pytorch/trl/gpt-oss-lora-grpo/` 下。克隆仓库并切换到该测试用例目录：

```
git clone https://github.com/awslabs/awsome-distributed-ai
cd awsome-distributed-ai/3.test_cases/pytorch/trl/gpt-oss-lora-grpo
```

复制环境模板，然后编辑 `env_vars` 以设置你的 ECR 仓库、镜像名、标签和 HuggingFace token：

```
cp env_vars.example env_vars
source env_vars
```

构建训练镜像并推送到你的仓库。该镜像打包了 PyTorch、TRL、HuggingFace Transformers、PEFT 以及训练和推理脚本：

```
cd artifacts && ./build_push.sh && cd ..
```

把 `kubectl` 指向你的集群，并应用 FSx storage manager pod。storage manager 为你提供一个进入共享文件系统的 shell，用于检查点转换和 eval 日志检查：

```
aws eks update-kubeconfig --name <YOUR_CLUSTER_NAME> --region us-east-2
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < kubernetes/fsx-storage-manager.yaml | kubectl apply -f -
```

## 使用 SFT 和 LoRA 微调 GPT-OSS-20B

我们先测量基础模型，然后配置 SFT 运行并检查结果。

### 基础模型的差距

基础 GPT-OSS-20B 在 50 个用例的评测中得分是 **推理语言正确率 22%**（11/50）。按语言分：英语 100%，法语 0%，德语 10%，西班牙语 0%，意大利语 0%。无论指令是什么，模型都默认用英语推理。

### SFT 配置

SFT 设置使用 LoRA r=8、α=16，在 4× ml.g6e.12xlarge（16× L40S 48GB）上训练 1,000 步，采用 Fully Sharded Data Parallel（FSDP）full-shard、bf16 精度和梯度检查点。该作业作为弹性 `HyperPodPyTorchJob` 运行，由 Kueue 管理，通过 `hyperpodrun` 启动。

应用 SFT 清单：

```
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < hyperpod-eks/train-lora-hyperpod-elastic-g6e.yaml | kubectl apply -f -
```

观察训练进度：

```
kubectl get pods -l app=gpt-oss-lora-elastic
kubectl logs -f -l app=gpt-oss-lora-elastic
```

每一步都会打印 loss 和梯度范数。一次健康的运行看起来像这样：

```
{'loss': 1.035, 'grad_norm': 0.163, 'learning_rate': 0.0002, 'mean_token_accuracy': 0.716, 'epoch': 3.25}
{'loss': 1.003, 'grad_norm': 0.171, 'lr': 0.0002, 'acc': 0.722, 'epoch': 3.32}
{'loss': 0.976, 'grad_norm': 0.159, 'lr': 0.0002, 'acc': 0.726, 'epoch': 3.57}
```

训练完成后，把 FSDP 检查点转换为 Parameter-Efficient Fine-Tuning（PEFT）格式，也就是 TRL 的 GRPO 训练器和推理脚本所期望的格式：

```
kubectl exec -it fsx-storage-manager -- python /app/convert_fsdp_checkpoint.py \
  --checkpoint /fsx/checkpoints/checkpoint-1000 \
  --output    /fsx/checkpoints/converted-peft/lora-checkpoint-1000-peft
```

### SFT 结果与分阶段的学习曲线

经过 SFT 之后，模型在全部五种语言上 **100% 的时间**（50/50）都用正确的语言推理。SFT 分两个阶段学会了这一点：

- 大约在第 200 步，模型学会了用目标语言*推理*（推理语言指标达到 100%）。
- 大约在第 1000 步，模型进一步学会了用目标语言给出*答案*。

最终 SFT 评测（第 1000 步）：

- 推理语言正确：**100%**（50/50）。
- 答案语言正确：**62%**（31/50）。
- 两者都正确：**62%**（31/50）。
- 各语言答案准确率：FR 60%，DE 60%，ES 30%，IT 60%，EN 100%。

**要点：** 在这里 SFT 不是可选项。基础模型完全无法遵循推理语言指令，而 SFT 把推理语言从 22% 提升到了 100%。剩下的差距是答案语言，为 62%。这是更难的后一半，因为最终答案很短，而英语先验在那里最强。

## 用 GRPO 细化答案语言

答案语言是 GRPO 显而易见的目标。SFT 已经能 100% 产出正确的推理，而模型*有时*能用正确的语言给出答案，所以存在可以强化的信号。

### 在 SFT 检查点之上运行 GRPO

我们使用 TRL 的 `GRPOTrainer` 运行 GRPO，从 SFT 检查点开始。设置是：加载 SFT LoRA，调用 `merge_and_unload`，再添加一个新的 LoRA（r=8，α=16，约 0.068% 可训练参数，20B 中的 13.6M）。训练使用每个提示 K=8 次生成、`device_map=auto`、学习率 1e-6 和 10 个 epoch。奖励函数对答案语言（±5.0）、推理语言（±1.5）和简洁性（+0.5 或 −1.0）打分，合计范围为 −7.5 到 +7.0。

从转换后的 SFT 检查点启动 GRPO：

```
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < kubernetes/train-grpo-singlenode.yaml | kubectl apply -f -
kubectl logs -f grpo-single
```

GRPO 会把检查点写到 `/fsx/checkpoints/grpo-singlenode/`。针对你的留出评测挑选最佳检查点（本次运行中答案语言指标在早期就达到峰值），并把它转换为 PEFT 格式用于推理和评测。

结果（基于 SFT 检查点）：

- 推理语言正确：**100%**（保持住了：GRPO 没有破坏 SFT 教的内容）。
- 答案语言正确：**62% 到 70%**（+8 个百分点，35/50）。
- 两者都正确：**70%**。
- 各语言答案：FR 70%，DE 80%，ES 60%，IT 40%，EN 100%。

GRPO 在答案语言指标上带来了真实的 +8 个百分点提升，同时把推理保持在 100%。收益出现在本来就有提升空间的地方。答案语言正是 SFT 尚未完全收敛的那种“有时正确”的行为，GRPO 强化了它。

### 并排比较 base、SFT 和 GRPO 的推理结果

为了看到定性差异，部署三个推理 pod，它们共享同一个基础模型，但加载不同的适配器：

```
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < kubernetes/inference-g6e-base.yaml    | kubectl apply -f -
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < kubernetes/inference-g6e-trained.yaml | kubectl apply -f -
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < kubernetes/inference-g6e-grpo.yaml    | kubectl apply -f -
```

把同一个法语推理提示依次送给每个变体：

```
kubectl exec -it inference-base    -- python /app/inference_g6e.py \
  --reasoning_language French

kubectl exec -it inference-trained -- python /app/inference_g6e.py \
  --checkpoint /fsx/checkpoints/converted-peft/lora-checkpoint-1000-peft \
  --reasoning_language French

kubectl exec -it inference-grpo    -- python /app/inference_grpo_new.py \
  --use_grpo \
  --grpo_checkpoint /fsx/checkpoints/converted-peft/checkpoint-1470-peft \
  --reasoning_language French
```

base pod 无视指令用英语推理。SFT pod 用法语推理，但经常用英语作答。GRPO pod 用法语推理并用法语作答。要复现前面那些数字所依据的完整 50 用例评测，运行评测清单，并从 FSx storage manager 读取结果文件：

```
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < kubernetes/eval-grpo.yaml | kubectl apply -f -
kubectl logs -f eval-grpo
kubectl exec fsx-storage-manager -- \
  cat /fsx/experiments/grpo_eval_checkpoint1470_*.txt
```

为了更广泛地理解 GRPO 何时带来额外价值，我们在 Qwen2.5-7B 上针对两个能力差距不同的任务做了一项受控实验。

## 用 Qwen2.5-7B 对照验证这一模式

为了在另一个模型和不同任务上检验“让技术与能力差距相匹配”这一论点，我们在 Qwen2.5-7B-Instruct 上做了受控实验。第一个任务是同一个多语言推理任务（存在提升空间）。第二个任务是 GSM8K，模型在该任务上已经达到峰值准确率。这是一项内部实验，公开仓库尚未发布。

**基础设施：** 2× g6e.48xlarge（16× L40S）、EFA 100Gbps、FSx Lustre、Ray 2.44 + KubeRay 1.4.2、veRL v0.6.1、vLLM 0.8.4。

**实验组：** A = 基础，B = 仅 SFT，C = SFT+GRPO。

### 多语言推理（50 个用例）

| **指标** | **A 基础** | **B SFT** | **C SFT+GRPO** | **Δ GRPO** |
| --- | --- | --- | --- | --- |
| 结构化格式 | 0% | 92% | 98% | +6 |
| 推理语言 | 0% | 96% | 98% | +2 |
| 答案语言 | 0% | 38% | 44% | +6 |
| 两者都正确 | 0% | 38% | 44% | +6 |

### GSM8K：一个没有提升空间的任务

在 GSM8K 上，基础 Qwen2.5-7B 已经得到 **90.5%**（181/200）。GRPO 在第 30 步同样得到 90.5%。当大多数采样组全部正确时，组相对优势会坍缩为零，因此没有学习信号。这是论点的另一半：**GRPO 需要提升空间（pass@k >> pass@1）才有东西可优化。** 没有提升空间就没有收益。

## 最佳实践

- **从 SFT 开始。** GRPO 无法教一个基础概率为零的行为。它只能强化模型已经偶尔产生的回答。SFT 把推理语言从 22% 提升到 100%，而本工作中每一次 GRPO 的收益都建立在那份 SFT 检查点之上。
- **SFT 和 GRPO 都使用 LoRA。** LoRA r=8/α=16 参数高效（0.068% 可训练），在 Qwen 对照中它在整个 GRPO 过程中保持数值稳定（梯度范数 0.23，每块 GPU 约 11.7 GB）。当你希望 SFT 和 GRPO 共享同一种适配器形状时，这是一个强有力的默认选择。
- **让技术与差距相匹配。** 对于缺失的行为用 SFT。对于细化一个已有的、偶尔正确的行为用 GRPO。GRPO 在这里的现实上限是 +6 到 +8 个百分点。
- **在花掉 GPU 小时之前检查奖励提升空间。** 如果大多数组全部正确（GSM8K 基础为 90.5%），组相对优势会坍缩为零，GRPO 得不到梯度。在开始 GRPO 运行前，确认存在提升空间（pass@k >> pass@1）。

## 清理资源

为避免持续计费，先删除工作负载资源，再删除底层基础设施：

- 删除训练和推理的 pod 与 job：  `kubectl delete hyperpodpytorchjob lora-hyperpod-elastic --ignore-not-found kubectl delete pod grpo-single inference-base inference-trained inference-grpo \ eval-grpo fsx-storage-manager --ignore-not-found`
- 缩容或删除 Amazon SageMaker HyperPod 集群或其节点组。
- 导出你想保留的检查点后，删除 Amazon FSx for Lustre 文件系统。
- 删除用于训练数据或检查点归档的任何 Amazon Simple Storage Service（Amazon S3）桶或对象。

## 结论

我们展示了如何在 Amazon SageMaker HyperPod 上为多语言推理微调 GPT-OSS-20B，以及如何在 SFT 和 GRPO 之间做选择。SFT 完成了大部分工作：推理语言从 22% 提升到 100%。GRPO 在存在提升空间的地方，在其之上带来了真实但适度的细化（答案从 62% 提升到 70%）。一个并行的 Qwen2.5-7B 对照证实了这一模式。在有改进空间的多语言推理上，GRPO 增加了 +6%；而在模型已经达到峰值准确率（90.5%）的 GSM8K 上，它没有带来任何收益。

**决策框架：**

- 模型完全做不到的行为：使用 **SFT**。
- 模型偶尔能做到、且有提升空间的行为：使用 **SFT 再 GRPO**，再多争取几分。
- 模型已经达到峰值准确率，或目标的基础概率为零：**GRPO 帮不上忙**。
