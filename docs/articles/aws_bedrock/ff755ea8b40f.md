# 在 Amazon SageMaker HyperPod 上微调 GPT-OSS-20B 以进行多语言推理

GPT-OSS-20B是一个用英语思考的开放权重推理模型。要求它用法语、德语、西班牙语或意大利语进行推理，它会接受指令，然后用英语产生自己的思维链。在包含 50 个示例的多语言推理测试中，基本模型仅在 22% 的时间内以正确的目标语言进行推理。这 22% 几乎全部是英语示例（英语 100%、法语 0%、德语 10%、西班牙语 0%、意大利语 0%）。

对于为非英语用户部署推理模型的团队来说，这种差距很重要。用法语提问的用户希望模型用法语进行推理和回答，而不是在思考过程中切换到英语。缩小这一差距是一个微调问题。这提出了每个团队在开始定制开放权重模型后都会面临的一个问题：监督微调（SFT）、使用组相对策略优化（GRPO）的强化学习，还是两者兼而有之？

在这篇文章中，我们将介绍如何在 [Amazon SageMaker HyperPod](https://aws.amazon.com/sagemaker/hyperpod/) 上微调 GPT-OSS-20B 以进行多语言推理。我们展示了何时单独 SFT 就足够了，以及何时 GRPO 增加了可衡量的价值。为了更广泛地了解 GRPO 何时发挥作用，我们还针对具有不同能力差距的两项任务进行了受控 Qwen2.5-7B 实验。简而言之：SFT 完成大部分工作，GRPO 在有改进空间时进行改进，而将技术与能力差距相匹配才是决定结果的因素。

## 解决方案概述

本节介绍多语言推理任务和数据集、SFT 和 GRPO 如何相互补充，以及我们在 Amazon SageMaker HyperPod 上运行的训练堆栈。

### 任务和数据集

该数据集是“HuggingFaceH4/Multilingual-Thinking”——一个被翻译成法语、西班牙语、德语和意大利语以及英语的思维链推理数据集，大约有 949 个训练示例和 50 个验证示例。该模型接收“推理语言：”系统提示指令，并且必须用该目标语言进行推理和回答，从而超越其强大的英语先验。评估包含 50 个测试用例：跨 5 种语言（EN/FR/DE/ES/IT）的 10 个数学/逻辑问题。

有两个指标很重要：

- **推理语言正确** – 所请求语言的思想链是否正确？
- **答案语言正确** – 最终答案是所要求的语言吗？

### SFT 和 GRPO 如何结合在一起

思考这两种技术的最清晰方法是：SFT 教授模型没有的行为。 GRPO 优化了模型有时已经可以产生的行为。 GRPO 的工作原理是根据提示对一组响应进行采样，并将策略推向高于平均水平的方向。如果所需行为在基本分布中的概率为零，则 GRPO 几乎没有什么可强化的。这个想法几乎解释了本文中的所有结果。

### 训练堆栈

我们使用 Amazon Elastic Kubernetes Service (Amazon EKS) 编排在 Amazon SageMaker HyperPod 上运行。对于在 GPT-OSS-20B 上运行的初始 SFT 和 GRPO，我们使用了 PyTorch TRL 库。对于 Qwen 控制实验，我们改用 veRL 作为训练器，使用 Ray 和 KubeRay 进行分布式编排，使用 vLLM 进行快速部署生成。检查点和数据集位于 Amazon FSx for Lustre 上，节点间结构使用 Elastic Fabric Adapter (EFA)。所有微调均使用低秩适应 (LoRA)，该技术参数高效且非常适合 SFT 和 GRPO。

下图显示了端到端的训练数据路径。用户提交的内容到达 Amazon SageMaker HyperPod 集群的 Amazon EKS 控制平面。 Amazon EKS 安排 Ray head pod 以及运行 veRL trainer 和 vLLM rolloutworker 的工作器 pod。两组 Pod 都安装 Amazon FSx for Lustre 作为基本模型、训练数据和检查点。节点间集体使用 EFA。部署从 vLLM 流回 veRL 训练器，训练器将检查点写回 Amazon FSx for Lustre。

## 先决条件

要继续操作，您需要：

- 采用 Amazon EKS 编排的 Amazon SageMaker HyperPod 集群。 GPT-OSS SFT 使用 4× ml.g6e.12xlarge (16× L40S 48GB)。 Qwen控制使用2×g6e.48xlarge（16×L40S）。
- Amazon FSx for Lustre 文件系统安装在集群上，并在“/fsx”处使用名为“fsx-claim”的“PersistentVolumeClaim”。
- 支持 EFA 的实例以及有效的 NVIDIA Collective Communications Library (NCCL) 和用于多节点 SFT 的“aws-ofi-nccl”堆栈。
- 容器注册表，例如 Amazon Elastic Container Registry (Amazon ECR)，用于保存从参考存储库构建的训练映像。
- “openai/gpt-oss-20b”和“HuggingFaceH4/Multilingual-Thinking”数据集的 HuggingFace 访问令牌。
- 您的工作站上可以使用 AWS 命令​​行界面 (AWS CLI)、“kubectl”、“docker”和“envsubst”。

## 使用 SFT 和 LoRA 微调 GPT-OSS-20B

我们首先测量基本模型，然后配置 SFT 运行并检查结果。

### 基础模型差距

基于 50 个案例评估的 GPT-OSS-20B 得分 **22% 推理语言正确** (11/50)。每种语言：英语 100%、法语 0%、德语 10%、西班牙语 0%、意大利语 0%。无论指令如何，模型都默认采用英语推理。

### SFT配置

SFT 设置使用 LoRA r=8、α=16，在 4× ml.g6e.12xlarge (16× L40S 48GB) 上训练 1,000 步，采用完全分片数据并行 (FSDP) 全分片、bf16 精度和梯度检查点。该作业作为由 Kueue 管理的弹性“HyperPodPyTorchJob”运行，通过“hyperpodrun”启动。

应用 SFT 清单：
```
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < hyperpod-eks/train-lora-hyperpod-elastic-g6e.yaml | kubectl apply -f -
```
观察训练进度：
```
kubectl get pods -l app=gpt-oss-lora-elastic
kubectl logs -f -l app=gpt-oss-lora-elastic
```
损失和梯度范数打印每一步。健康的跑步应该是这样的：
```
{'loss': 1.035, 'grad_norm': 0.163, 'learning_rate': 0.0002, 'mean_token_accuracy': 0.716, 'epoch': 3.25}
{'loss': 1.003, 'grad_norm': 0.171, 'lr': 0.0002, 'acc': 0.722, 'epoch': 3.32}
{'loss': 0.976, 'grad_norm': 0.159, 'lr': 0.0002, 'acc': 0.726, 'epoch': 3.57}
```
训练完成后，将 FSDP 检查点转换为 TRL 的 GRPO 训练器和推理脚本期望的参数高效微调 (PEFT) 格式：
```
kubectl exec -it fsx-storage-manager -- python /app/convert_fsdp_checkpoint.py \
  --checkpoint /fsx/checkpoints/checkpoint-1000 \
  --output    /fsx/checkpoints/converted-peft/lora-checkpoint-1000-peft
```
### SFT 结果和分阶段学习曲线

SFT 后，模型在所有五种语言中**100%** (50/50) 使用正确的语言进行推理。 SFT 通过两个阶段了解到这一点：

- 在第 200 步左右，模型学会了用目标语言“推理”（推理语言指标达到 100%）。
- 在第 1000 步左右，模型还学会了用目标语言给出“答案”。

最终 SFT 评估（步骤 1000）：

- 推理语言正确：**100%** (50/50)。
- 答案语言正确：**62%** (31/50)。
- 均正确：**62%** (31/50)。
- 每种语言的答案准确性：FR 60%、DE 60%、ES 30%、IT 60%、EN 100%。

**要点：** SFT 在这里不是可选的。基础模型根本无法遵循推理语言指令，而 SFT 将推理语言从 22% 提高到 100%。剩下的差距是答案语言，为 62%。这是较难的一半，因为最终答案很短，而且英语先验是最强的。

## 使用 GRPO 优化答案语言

答案语言是 GRPO 的明显目标。 SFT 已经在 100% 的情况下产生了正确的推理，并且该模型“有时”以正确的语言产生了答案，因此存在需要强化的信号。

### 在 SFT 检查点之上运行 GRPO

我们从 SFT 检查点开始使用 TRL 的“GRPOTrainer”运行 GRPO。设置：加载 SFT LoRA，调用 `merge_and_unload`，然后添加一个新的 LoRA（r=8，α=16，约 0.068% 可训练参数，13.6M of 20B）。训练使用每个提示 K=8 代、“device_map=auto”、学习率 1e-6 和 10 个时期。奖励函数对答案语言（±5.0）、推理语言（±1.5）和简洁性（+0.5或-1.0）进行评分，综合范围为-7.5至+7.0。

从转换后的 SFT 检查点启动 GRPO：
```
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < kubernetes/train-grpo-singlenode.yaml | kubectl apply -f -
kubectl logs -f grpo-single
```
GRPO 将检查点写入“/fsx/checkpoints/grpo-singlenode/”。针对您保留的评估（答案语言指标在此运行早期达到峰值）选择最佳检查点，并将其转换为 PEFT 格式以进行推理和评估。

结果（来自 SFT 检查点）：

- 推理语言正确：**100%**（认为：GRPO 没有违反 SFT 的教学内容）。
- 答案语言正确：**62% 到 70%**（+8 分，35/50）。
- 均正确：**70%**。
- 每种语言的答案：FR 70%、DE 80%、ES 60%、IT 40%、EN 100%。

GRPO 在答案语言指标上实际提高了 8 分，同时将推理保持在 100%。收益来自于有收益空间的地方。答案语言是 SFT 尚未完全收敛的有时正确的行为，GRPO 强化了它。

### 并排比较基础、SFT 和 GRPO 推理

要查看质量差异，请部署三个共享相同基础模型但加载不同适配器的推理 Pod：
```
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < kubernetes/inference-g6e-base.yaml    | kubectl apply -f -
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < kubernetes/inference-g6e-trained.yaml | kubectl apply -f -
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < kubernetes/inference-g6e-grpo.yaml    | kubectl apply -f -
```
通过每个变体运行相同的法语推理提示：
```
kubectl exec -it inference-base    -- python /app/inference_g6e.py \
  --reasoning_language French

kubectl exec -it inference-trained -- python /app/inference_g6e.py \
  --checkpoint /fsx/checkpoints/converted-peft/lora-checkpoint-1000-peft \
  --reasoning_language French

kubectl exec -it inference-grpo    -- python /app/inference_grpo_new.py \
  --use_grpo \
  --grpo_checkpoint /fsx/checkpoints/converted-peft/checkpoint-1470-peft \
  --reasoning_language French
```
尽管有说明，但基础 Pod 还是用英语进行推理。 SFT pod 用法语推理，但通常用英语回答。 GRPO pod 用法语进行推理和回答。要重现之前生成数字的完整 50 案例评估，请运行评估清单并从 FSx 存储管理器读取结果文件：
```
envsubst '$REGISTRY $IMAGE $TAG $HF_TOKEN' \
  < kubernetes/eval-grpo.yaml | kubectl apply -f -
kubectl logs -f eval-grpo
kubectl exec fsx-storage-manager -- \
  cat /fsx/experiments/grpo_eval_checkpoint1470_*.txt
```
为了更广泛地了解 GRPO 何时增加价值，我们在 Qwen2.5-7B 上针对两个具有不同能力差距的任务进行了对照实验。

## 使用 Qwen2.5-7B 控件测试模式

为了在不同模型和不同任务上测试“能力差距匹配技术”论文，我们在 Qwen2.5-7B-Instruct 上进行了对照实验。第一个任务是相同的多语言推理任务（存在空间）。第二个任务是 GSM8K，模型已经达到峰值精度。这是一个内部实验，公共存储库尚未发布。

**基础设施：** 2× g6e.48xlarge (16× L40S)、EFA 100Gbps、FSx Lustre、Ray 2.44 + KubeRay 1.4.2、veRL v0.6.1、vLLM 0.8.4。

**臂：** A = 底座，B = 仅 SFT，C = SFT+GRPO。

### 多语言推理（50例）

| **公制** | **一个基地** | **B SFT** | **C SFT+GRPO** | **ΔGRPO** |
| --- | --- | --- | --- | --- |
|结构化格式| 0% | 92% | 98% | +6 |
|推理语言| 0% | 96% | 98% | +2 |
|回答语言 | 0% | 38% | 44% | +6 |
|两者都正确 | 0% | 38% | 44% | +6 |

### GSM8K，一项没有空间的任务

在 GSM8K 上，基础 Qwen2.5-7B 的得分已经达到 **90.5%** (181/200)。第 30 步的 GRPO 得分也为 90.5%。当大多数样本组都是正确的时，组相对优势就会降至零，因此不存在学习信号。这是论文的另一半：**GRPO 需要余量 (pass@k >> pass@1) 才能优化任何内容。** 没有余量意味着没有增益。

## 最佳实践

- **从 SFT 开始。** GRPO 无法教授零基概率的行为。它只能强化模型有时已经产生的反应。 SFT 将推理语言从 22% 提高到了 100%，这项工作中的每一次 GRPO 胜利都是建立在 SFT 检查点的基础上的。
- **将 LoRA 用于 SFT 和 GRPO。** LoRA r=8/α=16 具有参数效率（可训练 0.068%），并且在 Qwen 控制上，它通过 GRPO 保持数值稳定（梯度范数 0.23，每个 GPU 约 11.7 GB）。当您希望 SFT 和 GRPO 共享相同的适配器形状时，这是一个很强的默认设置。
- **将技术与差距相匹配。** 使用 SFT 来查找缺失的行为。使用 GRPO 来改进现有的、有时是正确的行为。 GRPO 的实际上限是 +6 到 +8 分。
- **在花费 GPU 时间之前检查奖励空间。** 如果大多数组都是正确的（GSM8K 90.5% 基础），则组相对优势将降至零，并且 GRPO 不会获得梯度。在开始 GRPO 运行之前验证是否有余量 (pass@k >> pass@1)。

## 清理资源

为了避免持续产生费用，请删除工作负载资源，然后删除底层基础设施：

- 删除训练和推理 Pod 和作业：`kubectl delete hyperpodpytorchjob lora-hyperpod-elastic --ignore-not-found kubectl delete pod grpo-single inference-base inference-trained inference-grpo \ eval-grpo fsx-storage-manager --ignore-not-found`
- 缩小或删除 Amazon SageMaker HyperPod 集群或其节点组。
- 导出要保留的任何检查点后，删除 Amazon FSx for Lustre 文件系统。
- 删除用于训练数据或检查点存档的任何 Amazon Simple Storage Service (Amazon S3) 存储桶或对象。

## 结论

我们展示了如何在 Amazon SageMaker HyperPod 上微调 GPT-OSS-20B 以进行多语言推理，以及如何在 SFT 和 GRPO 之间做出选择。 SFT 完成了大部分工作：推理语言从 22% 上升到 100%。 GRPO 在存在净空的地方添加了真正的、适度的改进（回答为 62% 到 70%）。平行的 Qwen2.5-7B 对照证实了该模式。 GRPO 在多语言推理方面增加了 6%，这方面还有改进的空间。它在 GSM8K 上没有增加任何增益，该模型已经达到峰值准确度（90.5%）。

**决策框架：**

- 模型根本无法执行的行为：使用 **SFT**。
- 有时会出现这种情况，但有余量：使用 **SFT 然后使用 GRPO** 以获得更多分数。
- 模型已经达到最高准确度，或者目标的基本概率为零：**GRPO 不会有帮助**。
