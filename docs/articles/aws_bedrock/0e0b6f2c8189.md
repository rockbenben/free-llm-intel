# 借助 Amazon Bedrock 的生成式 AI 原型改变生命科学与基因组分析流程

生物制药公司将一种新药送到患者手中需要 [10 年以上](https://ncats.nih.gov/research/research-activities/ntu)，[成本超过 20 亿美元](https://www.scientificamerican.com/article/cost-to-develop-new-pharmaceutical-drug-now-exceeds-2-5b/)，且[失败率超过 90%](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC9293739/)。生物制药公司为将新药带给患者而必须遵循的 Market to Molecule（M2M，从市场到分子）价值流流程，资源密集、周期漫长且风险极高。十分之九的生物制药公司是 AWS 客户，帮助他们精简和转型 M2M 流程，可以更快地将药物送到患者手中、降低风险，并为客户带来价值。

制药公司正在采用[一种药物发现的新方法：在人类基因组中寻找变异，并将其与疾病关联起来](https://www.nature.com/articles/d42473-023-00140-6#:~:text=Some%20pharmaceutical%20companies%20are%20using%20a%20more%20human-focused,head%20of%20genetics%20at%20biomedical%20investment%20company%2C%20Deerfield.)。这种遗传验证方法通过聚焦疾病的根本原因和基因变异，可以提高 M2M 价值流流程的成功率。

如下面的 M2M 价值流图所示，Research 流程（以及 Basic Research 子流程）对于将基因变异与疾病关联起来的下游流程至关重要，并且有助于确定目标分子。这可能是加快新药交付并降低成本的关键一步。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/16/ML-16693-arch-diag-Image-001-1.png)

为了转型 M2M 价值流流程，我们的客户一直致力于利用其超过 200 万个已测序外显子组（表达为蛋白质的基因）的大型数据集，将基因与疾病关联起来。为此，客户的临床科学家不得不开发方法，通过在线[基因组浏览器](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC3525149/#:~:text=Genome%20browsers%20have%20been%20created%20to%20allow%20the,as%20a%20central%20starting%20point%20for%20genomic%20research.)在这个庞大的数据集中导航，这是一种以数据为中心的机械式体验，并不能完全满足用户需求。从搜索查询获取结果开始，典型的导航层级、筛选、等待和重复搜索等交互可能既耗时又乏味。将 UI 从传统的人工浏览器简化为对话式 AI 助手，可以提升临床研究流程中的用户体验。

[生成式 AI](https://aws.amazon.com/generative-ai/)是引领这一变革的演进过程中很有前景的下一步。随着生成式 AI 开始在医疗和生命科学领域产生重大影响，这个用例已准备好进行生成式 AI 实验。AWS 与客户合作构建了一种自定义方法，通过提出一个问题或一系列问题，让科学家在探索基因组时拥有更大的灵活性和敏捷性。我们的客户希望借助全新的生成式 AI 基因助手，为研究人员节省无数小时的工作。通过提出一个问题或一系列问题，科学家在探索基因组时拥有更大的灵活性和敏捷性。用文字而非筛选器、设置和按钮来识别变异及其与疾病的潜在关联，可以更高效地完成。借助更加精简的研究流程，我们可以帮助提高带来新突破的可能性。

本文探讨如何部署一个使用生成式 AI 模型和 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 的 text-to-SQL 管道，向基因组数据库提出自然语言问题。我们演示如何用 [AWS Amplify](https://aws.amazon.com/amplify/) 实现 AI 助手 Web 界面，并解释为生成 SQL 查询所采用的 prompt 工程策略。最后，我们给出在你自己的 AWS 账户中部署该服务的说明。Amazon Bedrock 是一项全托管服务，通过单一 API 提供对领先 AI 公司的大语言模型（LLM）和其他基础模型（FM）的访问，使你无需太多精力即可立即使用，为开发者节省宝贵时间。我们使用 [AWS HealthOmics](https://aws.amazon.com/healthomics/) 变体存储来保存带有组学数据的 Variant Call Format（VCF）文件。VCF 文件通常是生物信息学流程的输出。VCF 编码[单核苷酸多态性](https://www.genome.gov/genetics-glossary/Single-Nucleotide-Polymorphisms)（SNP）和其他结构遗传变异。该格式在[1000 Genomes 项目网站](http://www.1000genomes.org/wiki/Analysis/Variant%20Call%20Format/VCF%20%28Variant%20Call%20Format%29%20version%204.0/encoding-structural-variants)上有进一步描述。我们使用 [AWS HealthOmics – End to End workshop](https://catalog.workshops.aws/amazon-omics-end-to-end/en-US/001-getting-started) 来部署变体存储和注释存储。

虽然本文聚焦于面向组学数据库的 text-to-SQL 方法，但这里讨论的生成式 AI 方法可以应用于各种复杂的关系数据库 schema。

## 面向基因组数据的 Text-to-SQL

Text-to-SQL 是自然语言处理（NLP）中的一项任务，用于自动将自然语言文本转换为 SQL 查询。这涉及将书面文本转换为结构化格式，并用它生成可在数据库上运行的准确 SQL 查询。这项任务难度很大，因为人类语言灵活、含糊且依赖上下文，而 SQL 是结构化的，二者差异巨大。

在 LLM 出现用于 text-to-SQL 之前，用户查询必须经过预处理以匹配特定模板，然后再用这些模板重新表述查询。这种方法特定于用例，需要数据准备和人工工作。如今，有了 LLM，text-to-SQL 任务发生了重大转变。LLM 在从自然语言查询生成有效 SQL 查询方面不断展现出关键的性能提升。凭借在海量数据集上训练的预训练模型，LLM 能够识别语言中词与词之间的关系，并准确预测接下来要使用的词。

不过，尽管 LLM 在许多 text-to-SQL 问题上表现卓越，但它们也存在导致幻觉的局限。本文描述了用于克服这些局限的主要方法。

要在 text-to-SQL 服务中实现高准确率，有两种关键策略：

- **Prompt 工程** – prompt 经过结构化设计，用于标注不同组件，例如指向列和 schema，然后指示模型创建哪种类型的 SQL。这些标注充当指令，引导模型正确格式化 SQL 输出。例如，prompt 可以包含显示特定表列的标注，并引导模型生成 SQL 查询。通过显式指定 SQL 查询所需的结构和格式，这种方法可以对模型输出进行更多控制。
- **Fine-tuning** – 你可以从一个在大型通用文本语料上预训练的模型开始，然后使用带标注的示例进行基于指令的 fine-tuning，以提升模型在 text-to-SQL 任务上的性能。该过程通过在最终任务上直接训练模型，使其适应目标任务，但这需要大量 text-SQL 示例。

本文聚焦于用于 SQL 生成的 prompt 工程策略。AWS 客户首先采用 prompt 工程策略，因为它能高效返回高质量结果，且需要的基础设施和流程不那么复杂。有关何时采用每种方法的更多细节和最佳实践，请参阅[在 AWS 上构建生成式 AI 应用的最佳实践](https://aws.amazon.com/blogs/machine-learning/best-practices-to-build-generative-ai-applications-on-aws/)。

我们尝试使用 chain-of-thought 和 tree-of-thought 方法的 prompt 工程来提升推理和 SQL 生成能力。chain-of-thought prompt 技术引导 LLM 将问题分解为一系列中间步骤或推理步骤，在得出确定答案或输出之前明确表达其思考过程。

通过 prompt，我们促使 LLM 生成一系列关于自身推理的陈述，使 LLM 能够清晰表达其推理过程，从而产生准确且易于理解的输出。tree-of-thought 方法为推理过程引入了一种结构化的分支方式。我们不再使用线性链，而是提示 LLM 生成树状结构，其中每个节点代表整体问题解决过程中的一个子任务、子问题或中间步骤。

## 解决方案概述

以下架构图描述了我们为实现该原型所使用的解决方案和 AWS 服务。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/16/ML-16693-arch-diag-Image-002-1.png)

该工作流包含以下步骤：

- 科学家向一个通过 Amplify 连接并集成了 [AWS AppSync](https://aws.amazon.com/appsync/?nc2=type_a) GraphQL API 的聊天 Web 应用提交自然语言问题或请求。
- 请求被提交到 [Amazon API Gateway](https://aws.amazon.com/api-gateway/?nc2=type_a)，后者将请求转交给包含 text-to-SQL 实现的 [AWS Lambda](https://aws.amazon.com/pm/lambda/) 函数。我们建议实现第二个辅助 Lambda 函数，用于获取变体数据、基因名称或 ClinVar 列出的疾病，以简化用户体验并促进 SQL 生成过程。
- text-to-SQL Lambda 函数接收自然语言请求，将输入问题与 prompt 模板合并，然后提交给 Amazon Bedrock 生成 SQL。  我们的实现还增加了一个步骤，将传入的历史记录简化为单个请求。我们向 Amazon Bedrock 提交请求，将该用户会话中的历史输入转换为一个简化的自然语言请求。此步骤是可选的。
- 借助生成的 SQL，Lambda 函数将查询提交到 [Amazon Athena](https://aws.amazon.com/athena/?nc2=type_a)，从 [Amazon Simple Storage Service](https://aws.amazon.com/s3/?nc2=type_a)（Amazon S3）存储桶中检索基因组数据。  如果成功，Lambda 函数会通过 AWS AppSync 请求更新存储在 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/?nc2=type_a) 中的用户会话。该更改将自动出现在订阅了会话表变更的 UI 上。如果发生错误，代码会尝试重新生成 SQL 查询，将返回的错误作为输入并要求修正错误。然后 Lambda 函数针对 Athena 重新运行重新生成的 SQL 并返回结果。

## 面向 Text-to-SQL 的生成式 AI 方法

我们测试了以下 prompt 工程策略：

- LLM SQL agent
- 使用检索增强生成（RAG）的 LLM 来检测目标表和列
- 使用目标表和列的完整描述进行 prompt 工程
- 使用 chain-of-thought 和 tree-of-thought 方法进行 prompt 工程
- 使用动态 few-shot 方法进行 prompt 工程

我们使用 SQL agent 没有取得好结果。我们尝试了 [LangChain SQL agent。](https://python.langchain.com/docs/tutorials/sql_qa/) agent 难以利用数据集中的上下文信息生成准确且语法正确的 SQL。组学数据的一大挑战在于某些列是结构体或映射的数组。在构建该项目时，这些 agent 无法识别这些细微差别，因而无法生成相关的 SQL。

我们尝试了一种 RAG 方法，根据用户问题检索相关的表和列。然后通过 prompt 指示 LLM 仅使用这些表和列生成 SQL 查询。这项实验背后的动机是，RAG 方法能够很好地处理成百上千的列或表。然而，这种方法也没有返回理想的结果。该 RAG 方法返回了太多不相关的变量，无法用于每次 SQL 生成。

接下来的三种方法取得了成功，我们将它们组合使用，以在合成正确的 SQL 生成中获得最高准确率。

我们测试的第一个 prompt 思路是，针对用户问题提供要在 SQL 生成中使用的主要表和列的完整描述。在下面的示例中，我们展示了用于描述 1000 Genome `variants` 表的 prompt 快照。包含数据库表和列描述的 prompt，目标是教会 LLM 如何使用 schema 生成查询。我们将其视为在教一位将要对该数据库编写查询的新开发者，提供 SQL 查询示例来提取正确的数据集、如何过滤数据，以及只使用最相关的列。

```
<table>
       <table_name>
       variants
       </table_name>
       <table_description>
       This table contains information about genetic variants.
       </table_description>
       <column>
              <column_name>contigname</column_name>
              <column_description>
This column specifies the name of the contig (a contiguous sequence of DNA) or chromosome where the variant is located. It is typicauy prefixed with "chr". If the user asks for variants at the chromossome 22, use `chr22` to access variants in this table.
              </column_description>
              <example_use>
                      setect *
                      from variants
                      wnere contigname = 'chr22'
                      and start between 45509414 and 45509418;
              </example_use>
       </column>
       <column>
              <column_name>start</column_name>
              <column_description>
                      The start position of the variant on the chromosome. This should
                      be used to compose the primary key of the variant, along with the
                      following tables: `contigname`, `end`, `referenceallele`, `alternatealleles`.
              </column_description>
              <example_use>
                      SELECT * FROM variants WHERE start > 100000 and end < 200000;
              </example_use>
       </column>
</table>
```

团队还致力于创建一个使用 chain-of-thought 概念及其演进 tree-of-thought 的 prompt，以提升推理和 SQL 生成能力。

chain-of-thought prompt 技术鼓励 LLM 将问题分解为一系列中间步骤，在得出确定答案或输出之前明确表达其思考过程。这种方法的灵感来自人类通常将问题拆解为更小的、可管理部分的方式。

通过使用 prompt，我们促使 LLM 生成一条 chain-of-thought，让 LLM 清晰表达其推理过程，并产生更准确、更易理解的输出。这项技术有可能提升需要多步推理的任务的性能，例如从开放式自然语言问题生成 SQL。在我们测试的 FM 上，这种方法表现出色。

作为实验的下一步，我们使用了 tree-of-thought 技术，取得了比 chain-of-thought 方法更好的结果。tree-of-thought 方法为推理过程引入了一种更结构化、分支化的方式。我们不再使用线性链，而是提示 LLM 生成树状结构，其中每个节点代表整体问题解决过程中的一个子任务、子问题或中间步骤。以下示例展示了我们如何在 prompt 模板中使用这两种方法：

```
Imagine three different experts are answering this question. All experts will write down 1 step 
of their thinking, then share it with the group. Then all experts will go on to the next step, etc. 
If any expert realises they're wrong at any point then they leave. Each of the three experts should 
explain their thinking along with the generated SQL statement. Your final step is to review the 
generated SQL code for syntax errors. Pay close attention to any use of the UNNEST function - it 
MUST be immediately followed by 'AS t(unpacked)' rather than 'AS t' . If you find a syntax error 
with the generated SQL, produce a corrected version within <SQL_FIXED> tags. Only produce 
the <SQL_FIXED> code if you find a syntax problem in the <SQL_QUERY> tags.
```

最后，我们测试了 few-shot 和动态 few-shot 方法。few-shot 方法是 LLM prompt 工程中使用的一种提示技术。它涉及向 LLM 提供少量示例或演示，连同输入 prompt 一起，以引导模型的生成或输出。在 few-shot 设置中，prompt 包含以下内容：

- 一条指令或任务描述
- 针对特定输入的少量期望输出示例或演示
- LLM 将为其生成输出的新输入

通过让 LLM 接触这些示例，模型能够更好地识别模式，并推断输入与期望输出之间的底层规则或映射。

动态 few-shot 方法扩展了 few-shot 提示技术。它引入了根据特定输入或上下文动态生成或选择 prompt 中所用示例或演示的概念。在这种方法中，prompt 生成过程不再提供固定的示例集，而是包括：

- 分析输入或上下文
- 为示例和输入创建嵌入，并通过应用语义搜索检索或生成针对特定输入定制的相关示例或演示
- 使用所选示例和输入构建 prompt
