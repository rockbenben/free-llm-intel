# 用于生产 AI 代理的四层上下文工程：Deep Insight 如何将它们应用到工作代码中

当生产型人工智能代理处理数据分析和报告生成等任务时，上下文管理可能成为主要瓶颈。 20 万代币的窗口听起来很慷慨，但现实世界的任务在几分钟内就耗尽了其中的大部分。数据分析和报告生成会使代理在执行过程中失败、失去准确性或增加成本。已发布的指南正文已经解决了这个问题，但个别技术更容易阅读而不是应用。将它们结合在一起应用会产生显着的差异：在本文介绍的参考实现中，单个写入和执行工具将每个脚本添加到上下文的标记减少了约 95%，并且按需加载技能将系统提示缩小了约 97%。

本系列将这些指南整理成您可以直接应用的实践。 Anthropic 的工程帖子以及 Strands Agents SDK 中内置的功能，集中在上下文工程的四层上：在架构级别隔离上下文，通过提示对其进行控制，将其外部化到文件系统，并使用独立代理和防护措施对其进行验证。在这篇文章（第 2 部分）中，您将了解每一层的工作原理以及它在工作代码中的样子。我们在 *Deep Insight* 中应用了这些技术，这是一个基于 Strands Agents SDK 和 Amazon Bedrock AgentCore 构建的开源多代理数据分析解决方案，它作为全文的参考实现。

## 什么是情境工程？

上下文工程是在大型语言模型 (LLM) 的有限上下文窗口中优化信息的学科，以便智能体发挥最佳性能。 Amazon Bedrock 上提供的 Anthropic Claude Sonnet 4.5 提供了 200K 上下文窗口，但复杂的生产任务很快就超过了它。例如，一个看似简单的请求“*分析销售数据并创建 DOCX 报告*”会经历几个阶段：数据加载和探索（5 分钟）、基于类别的销售分析（3 分钟）、生成五个图表进行时间序列分析（10 分钟）、统计验证（3 分钟）和最终报告生成（5 分钟）。他们在 15 分钟内总共消耗了超过 15 万个代币。

在单个上下文中处理此类任务会导致问题：窗口在任务中溢出、过时的上下文会降低性能，并且错误需要重新运行整个管道。随着上下文的增长，对重要信息的关注度下降，并且效率低下会增加按代币定价的成本。

>“随着上下文窗口中标记数量的增加，模型从上下文中准确回忆信息的能力会下降（Context rot）。”
> — Anthropic，“AI 代理的有效上下文工程”(2025.09)

情境工程正是解决了这些问题，而且它不仅仅是技术的集合。它涵盖架构设计、提示编写、工具实现和验证，是一个分层学科，每一层都弥补了前一层的缺失。这篇文章详细介绍了可用于有效管理上下文的四层方法。

## 如何处理超出上下文窗口的任务

Anthropic 发布了几种处理长期任务的技术。 Deep Insight 将这些技术分为四层，每一层都解决其他层的局限性。下表列出了四个层。

| **层** | **练习** | **核心原则** | **限制** |
| ---| ---| ---| ---|
|第一层：架构 |通过多代理架构隔离上下文 |每个代理在独立的上下文中运行 |当仅靠隔离还不够时 |
|第 2 层：提示 |输出控制和行为规则|通过提示限制上下文摄入 |当仅提示还不够时 |
|第三层：工具|基于文件的上下文外部化|将文件中的大量内容保留在上下文之外 |当问题仍然出现时 |
|第 4 层：验证代理和保障措施 |独立验证和保障|捕获错误并防止上下文溢出 |最后的防线|

接下来的部分按顺序介绍每一层，说明该层规定的内容、为什么仅靠前面的层是不够的，以及如何在 Deep Insight 中实施该实践。

## 1.通过多代理架构隔离上下文

为每个专用代理提供自己的上下文窗口，并仅将压缩结果传递给协调器。 Deep Insight 通过协调员、规划员、计划审核员、主管和工具代理（编码员、验证员、报告员、跟踪员、审计员）的层次结构来实现此目的。

使用单个代理，从用户请求到数据探索、分析、图表生成、验证和报告的所有信息都会在一个上下文中累积，并且很容易超出窗口。为每个代理提供自己的上下文，甚至使用最多的编码器也能将令牌总数保持在 25K 以下。每个代理仅收到其需要的内容，并通过完成通知和简短摘要向其他代理发出信号。

隔离的关键是尽量减少共享信息。 Deep Insight 使用 Python 字典“shared_state”，它只存储四件事：

- `messages`：前一个客服人员的最终消息（不是完整的对话历史记录）。
- `线索`：从每个代理收集的压缩摘要。
- `full_plan`：由 Planner 生成并由 Tracker 更新的清单。
- `历史记录`：代理名称和消息的简短日志。

线索使用固定的 CLUES_FORMAT：而不是每个代理的完整对话（数万个令牌），只传递压缩的核心结果。
```
# coder_agent_tool.py -- context passing format
CLUES_FORMAT = "Here is clues from {}:\n\n<clues>\n{}\n</clues>\n\n"
RESPONSE_FORMAT = "Response from {}:\n\n<response>\n{}\n</response>\n\n*Please execute the next step.*"

# After Coder completes: add only compressed result to clues
clues += CLUES_FORMAT.format("coder", response["text"])
```
这种模式是 Anthropic 的“[我们如何构建多智能体研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)”文章中推荐的模式，该模式描述了一种协调者-工作者模式，其中首席智能体委托给专门的子智能体，每个智能体仅在自己的上下文中工作。您不需要自己构建它：Strands Agents SDK 中的agents-as-tools 模式在框架级别提供了这种隔离。

## 2. 通过提示控制上下文流入

仅第 1 层隔离是不够的：即使具有独立的上下文，生成长响应的代理也会夸大 Supervisor 的上下文。第 2 层通过提示限制每个代理的输出。

对于 Deep Insight，我们使用提示来限制每个代理返回给 Supervisor 的信息量。正如 Deep Insight 的提示所示，三个规则完成了大部分工作。

> “从最强的模型和简单的提示开始。然后根据实际观察到的故障案例逐步添加具体说明。”
> — Anthropic，“AI 代理的有效上下文工程”(2025.09)

### 实现细节 2-1：显式的每个代理输出代币预算

每个代理的提示指定最大响应令牌计数，防止长响应污染主管的上下文。

| **代理** | **输出代币预算** | **原因** |
| ---| ---| ---|
|编码员 | 1,000–1,500 个代币 |分析代码保存到文件中，因此代理仅返回状态摘要、已完成的任务和见解 |
|验证者 | 800 个代币 |验证结果保存到“引用.json”。代理仅返回摘要 |
|记者| 1,000 个代币 |代理将报告生成为 DOCX 文件，并仅返回结果摘要 |

Anthropic 的“[为代理编写有效的工具](https://www.anthropic.com/engineering/writing-tools-for-agents)”文章建议为工具提供简洁或详细的响应选项，以提高上下文效率。在每个代理的系统提示中应用相同的想法上一层。在 Deep Insight 中，所有代理共享一种标准化格式：
```
## Status
[SUCCESS | PARTIAL_SUCCESS | ERROR]
## Completed Tasks
- [Task 1 from FULL_PLAN -- use exact wording so Tracker can match]
- [Task 2 -- be specific, not generic]
## Key Insights
- [Key finding 1 with numbers and ratios]
- [Key finding 2 with business implications]
## Generated Files
- ./artifacts/chart.png -- brief description
- ./artifacts/calculation_metadata.json -- N calculations
```
### 实现细节 2-2：自包含代码哲学

Coder 代理的提示明确指出“变量在脚本之间不会保留”。每个脚本必须包含所有必要的导入并直接加载数据。提示提供了错误和正确的示例：
```
# WRONG -- Attempting to use a variable from Turn 1 in Turn 2
# Turn 1:
df = pd.read_csv('data.csv')
total = df['Amount'].sum()

# Turn 2:
print(f"Total: {total}")  # NameError: name 'total' is not defined

# CORRECT -- Every script is self-contained
import pandas as pd
df = pd.read_csv('./artifacts/cache/df_main.csv')  # Load from cache
total = df['Amount'].sum()
print(f"Total: {total}")
```
该规则与上下文工程相关的原因是，引用先前脚本中的变量需要代理“记住”先前的对话，这意味着过去的代码必须保留在上下文中。自包含原则意味着过去的代码可以安全地从上下文中删除。

### 实施细节2-3：主管部分完成规则

主管的提示包括规则“在当前座席部分中的所有清单项目都标记为“[x]”之前，不要移动到下一个座席。”我们在提示中表达了这条规则，因为决定编码器的工作是否完成需要主管使用来自跟踪器更新的信息来解释计划。这种判断很难单独用代码来表达。

## 3.“只有上下文中的指针，文件中的实际数据”

第 1 层隔离代理之间的上下文，第 2 层限制代理内的输出。但是，当 Coder 代理生成 100 行 Python 代码时，该代码本身就会进入上下文。即使有“简短回应”的提示指令，有些代码也写不简短。第 3 层使用工具设计将大量内容移出上下文，移至文件系统中。四种技术带来了大部分好处，如以下实施细节所示。

### 实现细节 3-1：使用写入和执行工具将代码移出上下文

编码器读取分析计划，编写 Python，并执行它以生成可视化。但是，当代码变长时，传统方法（单独的文件写入和执行工具）会直接向每个脚本的上下文添加 100 行，累计超过 1,000 行。

解决方法是将这两个步骤折叠到一个工具中，这样代码就永远不会作为消息进入上下文。 Deep Insight 的 Coder 代理为此使用一个“write_and_execute_tool”。

这是 write_and_execute_tool 的一部分。写入并执行该文件后，仅返回一个摘要：“写入105行，执行成功，完成五类分析。”代码保留在文件中，大约三行摘要保留在上下文中。根据此示例，这可以节省大约 95% 的令牌。
```
# write_and_execute_tool.py
def _handle_write_and_execute_tool(file_path, content, timeout=300):
    """Write a Python script and immediately execute it."""
    # Step 1: Write file
    with open(file_path, 'w', encoding='utf-8') as f:
        f.write(content)
    # Step 2: Execute immediately
    result = subprocess.run(
        f"python {file_path}",
        shell=True,
        capture_output=True,
        timeout=timeout
    )
    # Return only summary
    return f"Written {len(content.split(chr(10)))} lines to {file_path}\n" \
        f"Execution successful\n" \
        f"Output: {result.stdout[:500]}"  # Only first 500 chars
```
> “服务器端过滤：在数据到达上下文之前在执行层过滤数据，令牌减少 98.7%（150K 至 2K）。”
> — Anthropic，“使用 MCP 执行代码”(2025.11)

### 实现细节 3-2：在 Coder 代理中将通用逻辑重用为模块

通用模块可以在分析中重复使用。不必每次都重新生成它们，而是将常用函数定义为模块一次并导入它们，这样可以防止令牌浪费和上下文重复。

如果没有这个，在每次分析中定义像 to_python_type() 或 track_calculation() 这样的函数会在 10 次分析中产生 200-300 行重复代码。 Deep Insight 在第一个任务之前生成一个名为“coder_analysis_utils.py”的模块。它包括用于转换 numpy 类型、跟踪计算元数据以及保存为 JSON 的函数。后续分析将导入它，用两个导入行替换 20-30 个重新生成的行，这样可以节省标记并提高一致性和调试能力。
```
# coder_analysis_utils.py -- common module generated before first task
import numpy as np
import json
from datetime import datetime

_calculations = []

def to_python_type(value):
    """Convert numpy/pandas types to Python native types"""
    if isinstance(value, (np.integer, np.int64)): return int(value)
    elif isinstance(value, (np.floating, np.float64)): return float(value)
    elif isinstance(value, np.ndarray): return value.tolist()
    return value

def track_calculation(calc_id, value, description, formula,
                      source_file, source_columns, importance):
    """Track calculation metadata -- Validator independently verifies later"""
    _calculations.append({
        "id": calc_id, "value": to_python_type(value),
        "description": description, "formula": formula,
        "source_file": source_file, "source_columns": source_columns,
        "importance": importance
    })

def save_calculation_metadata(path="./artifacts/calculation_metadata.json"):
    """Save all tracked calculations to JSON"""
    with open(path, 'w', encoding='utf-8') as f:
        json.dump({"generated_at": datetime.now().isoformat(),
                   "calculations": _calculations}, f, ensure_ascii=False, indent=2)
```
### 实施细节3-3：通过结构化笔记保存和共享分析结果

我们使用结构化笔记来共享详细的分析结果，而无需将它们传递给每个代理的上下文。 Deep Insight 将这些结果存储在名为“all_results.txt”的文件中，然后代理根据需要读取该文件。

例如，Coder 代理在每个分析任务之后将结果附加到“all_results.txt”：
```
with open('./artifacts/all_results.txt', 'a', encoding='utf-8') as f:
    f.write(f"""
## Category Sales Analysis (completed at: 14:32)
- Top revenue category: Fruit (417,166,008 KRW, 45% of total)
- Top 3 categories: Fruit, Vegetables, Meat (78% of total)
- Generated file: ./artifacts/category_sales_chart.png
""")
```
编码员在每次分析后将详细结果记录在该文件中，报告员在编写最终报告时读取它。其他代理以相同的方式通过 all_results.txt 进行协作。

无需做笔记，编码员就会在每项任务完成后将详细结果传递给主管，并在其上下文中累积。通过记笔记，只会传递大约 30 个令牌的消息，例如“类别销售分析完成，找到 3 个关键见解，详细结果保存到 all_results.txt”，报告者会在需要时读取该文件。

该模式泛化到单个文件之外。文件系统本身可以充当代理间通信总线，就像 Deep Insight 中那样：

| **文件名** | **制片人** | **消费者** | **角色** |
| ---| ---| ---| ---|
|所有结果.txt |编码员 |记者|分析结果累积日志|
| `calculation_metadata.json` |编码员 |验证者 |数值计算记录：来源、公式和值（用于验证）|
| `引用.json` |验证者 |记者|已验证的引文数据（在报告中作为 [1]、[2] 插入）|
| `audit_findings.json` |审计师|记者|最终报告中发现的引文缺陷（促使有针对性的记者重试）|
| `coder_analysis_utils.py` |编码员 |所有脚本 |共享实用函数（一次编写，重复导入）|
|完整计划（共享状态）|计划/追踪器 |主管|清单状态（更新 [x]）|

>“‘及时’方法，在运行时将数据动态加载到上下文中，而不是预先预处理所有相关数据，可以保持上下文的新鲜度、相关性，并适应任务不断变化的状态。”
> — Anthropic，“AI 代理的有效上下文工程”(2025.09)

### 实现细节 3-4：仅加载技能所需的知识

这种方法不是将所有专业知识放入系统提示中，而是仅在需要时才加载。包括每个技能指南（数据结构检查、README 生成、技能创建、系统提示编写、工具创建）都会添加超过 20K 的令牌，在每次调用时将不必要的信息加载到 Coder 代理中，并强制重新部署以添加技能。

Deep Insight 的技能系统在启动时仅加载约 500 个令牌的技能目录，技能列表仅包含名称和简短描述。当用户请求“创建自述文件”时，代理决定“我需要自述生成器技能”并调用“skill_tool(skill_name =“readme-generator”)`。 SkillLoader 读取 readme-generator/SKILL.md 并返回约 3K 令牌的详细指南。
```
# 1. Skill Discovery (at initialization)
from src.utils.skills.skill_utils import initialize_skills
available_skills, skill_prompt = initialize_skills(
    skill_dirs=["./skills"],
    verbose=True
)

# 2. Add to System Prompt (~500-token catalog)
system_prompt = base_prompt + skill_prompt

# 3. Runtime -- Agent loads skill when needed
# Agent decides: "This is README generation, I need the readme-generator skill"
# -> skill_tool(skill_name="readme-generator")
# -> Returns full SKILL.md content (~3K tokens)
```
每个技能都定义为一个“SKILL.md”文件，由 YAML frontmatter 和详细的 markdown 指南组成。它包括名称、描述、许可证和允许的工具等元数据，以及概述、何时使用此技能、详细说明和最佳实践。要添加新技能，请在 Skills/ 下创建一个新目录并写入 SKILL.md 文件，它会自动发现。

启动时，代理会加载大约 500 个令牌的技能目录，而不是在完整指南上浪费超过 20,000 个令牌（大约减少 97%）。当需要时，它可以额外加载数千代币的详细技能说明。

## 4. 使用验证代理和保障措施验证质量

即使使用第 1-3 层，仍然存在一个风险：孤立的代理无法看到彼此的工作，因此如果编码器计算错误，报告器会将该错误带入报告中。第四层是最后的防线。

>“提供测试工具，以便代理可以自我验证功能并修复仅从代码中不明显的错误。让模型使用描述性提交消息将其进度提交到 git，并在进度文件中写入进度摘要。”
> — Anthropic，“长时间运行智能体的有效安全带”(2025.11)

### 实施细节 4-1：跟踪器、验证器和审核器代理：进度跟踪和质量保证

Tracker 实时更新计划的清单。当Coder完成数据加载时，Supervisor调用Tracker，Tracker根据“数据加载完成（1000行，5列）”等信息将计划项从“[]”更新为“[x]”。这有助于用户和系统准确地了解进度。

验证器独立地重新执行编码器的计算以验证准确性。它读取“calculation_metadata.json”，根据源数据重新执行每个计算，并进行比较：0.01 遍内匹配，不匹配被标记。经过验证的计算结果会转到“itations.json”供记者引用。报告者完成后，审核员会根据“itations.json”和“calculation_metadata.json”检查最终的 DOCX，而不对其进行修改。它在“audit_findings.json”中记录引用缺陷，并可以向报告者请求最多两次有针对性的重试。

### 实现细节 4-2：验证计算的优先级

验证每个计算的效率很低，因此请按重要性确定验证范围。 Deep Insight 的 OptimizedValidator 应用以下阈值：

- 超过 50 个计算：积极过滤，验证所有高值加上仅 10 个中等值。
- 超过20种计算：中等过滤，验证所有高加15中。
- 20 次或更少的计算：验证大多数、所有高加所有中加 5 个低。

它还应用类型安全比较：为了避免 numpy 与 Python 类型问题，所有值都转换为 `float()` 并检查 0.01 以下的绝对差异：
```
# validator.md -- type-safe numerical comparison
try:
    match = abs(float(expected) - float(actual)) < 0.01
except:
    match = str(expected) == str(actual)
```
### 实现细节 4-3：SummarizingConversationManager：最后的安全网

在特殊情况下，上下文仍然可能溢出，因此请在其他层下保留安全网。为此，Deep Insight 使用 Strands Agents SDK 中的 [SummarizingConversationManager](https://strandsagents.com/docs/user-guide/concepts/agents/conversation-management/#summarizingconversationmanager)。
```
# strands_sdk_utils.py -- safety net configuration at agent creation
agent = Agent(
    model=llm,
    system_prompt=system_prompts,
    tools=tools,
    conversation_manager=SummarizingConversationManager(
        summary_ratio=0.5,  # summarize oldest 50% on overflow
        preserve_recent_messages=10,  # always preserve 10 most recent messages
        summarization_system_prompt=apply_prompt_template("summarization", {})
    )
)
```
在溢出时，LLM 将最旧的 50% 消息汇总为一条消息，同时始终保留 10 条最新消息以保留当前任务的上下文。摘要提示 (summarization.md) 需要逐字保留“线索”、“计划”和“跟踪状态”。

### 实现细节 4-4：选择性提示缓存以实现成本优化

上下文工程涵盖成本优化，而不仅仅是代币节省。根据使用相同提示调用每个代理的频率，为每个代理启用提示缓存。 Deep Insight 的每个代理设置：

| **代理** | **提示缓存** | **工具缓存** | **原因** |
| ---| ---| ---| ---|
|主管|是的 |是的 |重复调用频率高，系统提示及工具定义庞大|
|编码员 |是的 |是的 |按顺序运行多个分析脚本，每次都有相同的提示 |
|记者|是的 |是的 |逐节增量生成报告，提示重用频率高 |
|审计师|是的 |是的 |使用相同的提示和工具多次检查 DOCX 和 JSON 文件，并在每次 Reporter 重试后重新运行 |
|协调员|没有 |没有 |一次性调用，没有缓存优势 |
|规划师|没有 |没有 |每个请求调用一次，并且仅当用户请求计划修订时再次调用 |
|验证者 |没有 |没有 |每次调用不同的数据，缓存命中率低|
|追踪器 |没有 |没有 |轻量级任务，无需工具，无需缓存 |

启用缓存的代理将缓存点插入系统提示和工具定义中，从而将重复调用的输入令牌成本降低高达 90%。这是 Strands Agents SDK 本身支持的功能。计划审核者不会出现在表中，因为它是一个人机交互步骤，用于收集用户批准或反馈，而不是调用模型。

## 结论

这篇文章详细介绍了四层工程方法，您可以使用它来有效管理超出上下文窗口的复杂任务的上下文。

- 第 1 层（架构级隔离）：每个代理通过多代理架构在独立的上下文中工作，仅传递压缩摘要。
- 第 2 层（基于提示的控制）：输出代币预算、标准化响应格式和独立的代码哲学主动限制上下文流入。
- 第 3 层（文件系统使用）：write_and_execute_tool 将代码保留在上下文之外，文件系统充当代理间通信总线，并且仅在需要时才延迟加载知识。
- 第 4 层（验证和保障）：验证者的独立计算重新验证、审核员对最终报告的只读引文审核、Tracker 的进度跟踪、SummarizingConversationManager 的溢出预防以及选择性提示缓存管理质量和成本。

每一层都形成一个防御系统，可以弥补前一层的缺失。当架构隔离不足时，提示限制输出。当提示不足时，工具会将内容保留在外部。当问题仍然出现时，验证就会发现它们。

这些层中的每一层都记录在 Anthropic 的工程帖子中，[“AI 代理的有效上下文工程”](https://www.anthropic.com/engineering/ effective-context-engineering-for-ai-agents)、[“使用 MCP 执行代码”](https://www.anthropic.com/engineering/code-execution-with-mcp) 和 [“我们如何构建多代理研究”系统”](https://www.anthropic.com/engineering/multi-agent-research-system)。他们推荐的大部分内容已经在 Strands Agents SDK 中提供，而不是您构建的东西：SummarizingConversationManager、提示缓存和代理即工具模式。

在构建生产代理时，仅LLM的上下文窗口是远远不够的。应用这些上下文工程技术来有效管理上下文并扩展代理以适应生产工作负载。
