# 超越 KV 缓存：使用本机 PyTorch 在 AWS Trainium2 上训练和服务 i14 的拉普拉斯 3B 线性注意力模型

大多数大型语言模型 (LLM) 使用带有 softmax 注意力的 Transformer 架构。在推理过程中，它们的键值 (KV) 缓存随着对话或文档上下文而增长。这会减少并发性，增加服务成本，并迫使代理应用程序丢弃有用的历史记录。

[i14](https://i14.ai) 将 Laplace 3B 设计为线性注意力替代方案。其循环状态保持在每个序列 29.5 MB，与上下文长度无关。 i14 与 AWS 合作，使用[通过 TorchNeuron Native 提供的原生 PyTorch 支持](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/frameworks/torch/index.html) 将此自定义架构引入 [AWS Trainium2](https://aws.amazon.com/ai/machine-learning/trainium/)。这保留了门控线性注意力 (GLA) 设计和 Muon 优化器。

在一个 trn2.48xlarge 实例上，Laplace 3B 的训练速度约为每秒 120,000 个令牌。该模型每秒在 1,280 个并发序列中提供 11,544 个输出令牌。这篇文章解释了模型设计、i14 对 Trainium2 所做的更改以及训练和推理结果。

## 关于 i14

i14 是一家人工智能研究和技术公司，致力于开发模型架构、组件和运行时。其工作借鉴了人工智能、计算认知科学以及对生物系统如何随时间学习的研究。 i14 将这些想法应用到可以保留远程上下文而不允许服务状态随着每个令牌而增长的模型中。

## 为什么是线性注意力模型？

Transformer softmax 注意力比较上下文中的标记。在训练期间，该计算量随序列长度呈二次方增长。在推理过程中，KV 缓存会随着模型处理更多令牌而增长。

线性注意力围绕针对每个标记更新的循环状态重新组织计算。 Laplace 3B 使用 GLA 将先验上下文压缩为固定大小的矩阵状态。这会将训练注意力从 O(*T*2) 更改为 O(*T*) 并将推理状态固定为每个序列 29.5 MB。

| **考虑** | **Transformer Softmax 注意力** | **拉普拉斯 3B 与 GLA** |
| --- | --- | --- |
|培训关注|通过 O(*T*2) 缩放构建成对标记分数 |以 O(*T*) 缩放更新分块循环状态 |
|推理记忆 | KV 缓存随上下文增长 |循环状态的大小保持固定 |
|更长的上下文 |每个序列都会消耗更多的加速器内存 |上下文长度不会增加循环状态分配 |
|实施 |使用广泛优化的注意力内核 |需要特定于体系结构的内核和编译器调整 |

线性注意力压缩历史而不是保留每个键和值。因此，您必须评估工作负载的检索质量。固定状态有利于长时间运行的代理、大文档分析以及需要持久内存和可预测服务需求的应用程序。

## i14 如何为 AWS Trainium2 调整 Laplace 3B

Laplace 3B 的原始实现使用 GPU 优化的 Triton 内核。 AWS 生成式 AI 创新中心 (GenAIIC) 团队首先使用 Trainium2 的标准 PyTorch 运算符重写了 GLA 内核。在比较这两种方法后，团队选择了 [TorchNeuron Native，AWS Trainium 的本机 PyTorch 后端](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/frameworks/torch/index.html) 的 Beta 版本，因为它的性能更好。

实施需要三项改变：

- **使用原生 PyTorch 作为 GLA 注意力内核。** 该团队用标准 PyTorch 运算符替换了 GPU 特定的 fused_chunk_simple_gla Triton 内核，使用 16 个 128 个令牌的块来匹配 NeuronCore 片上缓冲区的 128 个分区。
- **重新设计 Muon 的通信方式。** MuonFSDP2 中的两个 all_to_all 集合将每列流量减少了 24 倍，并将吞吐量提高了 1.63 倍。
- **编译顺序向后传递。** 该团队静态展开 GLA 循环的 16 个块步骤，以适应编译器的图形大小和片上内存限制。

工程挑战部分详细描述了每项更改。

## 为什么选择 AWS Trainium 加速器？

[AWS Trainium](https://aws.amazon.com/ai/machine-learning/trainium/) 是一系列 AWS 机器学习 (ML) 加速器，专为模型训练和推理而设计。 trn2.48xlarge 实例结合了 16 个 Trainium2 芯片、64 个逻辑 NeuronCore、高带宽内存和 NeuronLink-v3 连接。这些资源支持本文中描述的分布式训练和推理配置。

Trainium2 的三个特性决定了其实现：软件管理的片上存储器（挑战 1）、快速芯片间互连（挑战 2）和静态编译器（挑战 3）。编译器将 GLA 递归跟踪为固定图。

**软件管理的片上内存。** 每个 NeuronCore 都有一个 28 MiB 状态缓冲区 (SBUF)（包含 128 个分区）和一个 2 MiB 部分和缓冲区 (PSUM)。 PSUM 连接到 128×128 收缩张量引擎，以及单独的矢量和标量单元。 SBUF 不是缓存：编译器会提前安排每个“HBM 到 SBUF”传输，因此数据就位，不会被逐出或丢失（图 1）。

## i14 和 Laplace 3B 架构

Laplace 3B 是 24 层 i14 解码器，其中每一层都用 Simple GLA 替换 softmax 注意力。图 2 遵循一层从顶部的输入 **x***t* 到底部的输出 **x***t* + 1。本节介绍每个模块：归一化和卷积、QKVG 投影、GLA 混合器和前馈通道混合器。

**归一化和卷积。** 每个 token 的残差流向量 **x***t* ∈ ℝ*D* (*D* = 3, 072) 通过 LayerNorm 和宽度为 *k* = 4 的深度因果 Conv1d（带有 SiLU）。这在混合器之前为每个位置提供了 4 克摘要。然后，GLA 混合器通过其衰退状态对整个历史进行基于内容的检索。

**QKVG 投影。** 后卷积输出经过一个融合矩阵 **W***q**k**v**g* ∈ ℝ9, 216 × 3, 072，其中 9, 216 = *H* × (2*d**k* + 2*d**v*)。它分为四个每个令牌流：查询 **q***t*、键 **k***t*、值 **v***t* 和门 **g***t* (*H* = 16、*d**k* = 96、*d**v* = 192)。浇口在混合器之后使用。

## 工程挑战

这三个变化中的每一个都提出了自己的工程挑战。

### 挑战 1：在 Trainium 上使用原生 PyTorch for GLA

在 GPU 上，GLA 作为来自 flash-linear-attention 库的融合 Triton 内核 fused_chunk_simple_gla 运行。 GenAIIC 团队使用通过 [TorchNeuron Native](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/frameworks/torch/index.html) 运行的标准 PyTorch 运算符重新表达它，作为固定大小块上的显式循环。块计数在编译时固定并设置向后展开深度。该团队使用 fla_num_chunks = 16，因此每个块包含 *C* = 128 个代币。

在每个块 *c* 中，块内输出被屏蔽线性注意力，并且运行状态 **S** 添加早期上下文：

### 挑战 2：FSDP2 下的分布式 Muon 正交化

Muon 在更新之前对每个梯度进行正交。对于 96 个二维权重矩阵（27.18 亿个参数）中的每一个，它运行五次 Newton-Schulz 迭代（算法 1）。

![牛顿-舒尔茨算法](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/19/07-newton-schulz-algorithm.png)

牛顿-舒尔茨算法

**分布式问题。** Gram 矩阵 **A** = **X****X**⊤ 将权重的每一行与其他每一行相关联。在完全分片数据并行 (FSDP2) 下，64 个列中的每个列仅保存 1/64 的行。因此，分片局部 **X****X**⊤ 仅产生一个对角块并丢弃每个跨分片项（图 5）。

![FSDP2下的Newton-Schulz通信模式](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/14/ML-21817-9.png)

图 5：FSDP2 下的 Newton–Schulz：分片本地 Gram 块，以及收集/广播与 all_to_all 的比较。

**简单的方法：收集并广播。** 每个等级都会收集完整的梯度（5.44 GB），一个等级运行牛顿-舒尔茨，并广播结果。每步移动 10.87 GB，而其他 63 个等级则等待。

**生产方法：all_to_all 转置。** 在 MuonFSDP2 中，一个 all_to_all 为每个等级提供一些完整矩阵，所有 64 个等级并行运行 Newton-Schulz，第二个 all_to_all 返回结果。每排名流量下降至 0.45 GB，减少了 24 倍。吞吐量从每秒 73,378 个代币增加到 119,934 个代币，增加了 1.63 倍，并且损失曲线完全相同（图 6）。

![每个训练步骤的通信量](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/14/ML-21817-10.png)

图 6：每步通信量：使用 all_gather 时为 10.87 GB，而使用 all_to_all 时为 0.45 GB。

**通信成本。** Newton-Schulz 仅占训练步骤中 FLOP 的 2% 左右（1.95 × 1014 或 9.53 × 1015），因此通信是瓶颈。在 NeuronLink-v3 上，速度为 1.28 TB/s，0.45 GB 交换在大约 4.4 秒的步骤中只需要不到 0.4 毫秒。

### 挑战 3：向后传递展开顺序循环

后向传递区分所有 16 个连续状态更新。在 GPU 上，autograd 在运行时构建此图。在 Trainium2 上，编译器必须提前看到整个展开的 16 步图，这会产生三个约束。

图深度随着块计数而增长：在 32 个块 (*C* = 64) 时，图溢出了调度程序。每个块的内存随着块大小的增加而增长：在 8 个块 (*C* = 256) 时，中间体溢出到 HBM 中。每个形状在跟踪时都是固定的，因此每个循环中间都需要自己的静态分配。

十六个块 (*C* = 128) 满足所有三个要求：展开适合调度程序，中间体保留在芯片上，并且切片与 128 个 SBUF 分区对齐。

## Trainium2 上的推理优化

通过未经修改的 vLLM 引擎，GenAIIC 团队在一个 trn2.48xlarge 实例上以 1,280 个并发序列每秒提供 11,544 个输出令牌。

**恒定的服务状态。** 每个序列 29.5 MB 的循环状态大约比具有 8,192 个令牌的类似 KV 缓存小 82 倍。将提示从 2,048 个代币增加到 8,192 个代币，每个输出代币的成本仅增加了 0.5%。

**未修改的 vLLM。** 包装器替换每个解码器层的一个属性（令牌混合器），以读取和写入 vLLM 池中的循环状态。由于该模型声明自身是无注意力的，因此 vLLM 为每个序列分配一个固定页面。输出与令牌的 i14 参考令牌匹配（BF16 中 3/3 提示上的 48/48 步）。

**固定批量基准隐藏了什么。** 在真实流量下，每个新的解码批量宽度都是一个单独编译的形状，其首次使用时间约为 11 秒。这些步骤仅占总数的 1.1%，但却消耗了 47.5% 的解码时间。填充到固定宽度消除了这种成本，并获得了位精确的结果。编译后的解码在交错到达情况下将每个副本的吞吐量提高了 3.52 倍，而在固定批次情况下提高了 1.46 倍。由于 BF16 重新关联使编译输出与 eager 略有不同，因此当精确的再现性很重要时，请使用 eager 解码。

## 要点

该项目在训练和推理方面都提供了经验教训：

- **Native PyTorch 可以支持 Trainium2 上的自定义架构。** i14 保留了 GLA 架构并使用 TorchNeuron Native 进行最终实现。
- **通信设计对于自定义优化器很重要。** Muon all_to_all 设计将每排名流量减少了 24 倍，并将训练吞吐量增加了 1.63 倍。
- **固定状态保持推理内存可预测。** 无论上下文长度如何，每个序列都使用 29.5 MB。
- **编译前的配置文件。** 操作员调度（而不是算术或 HBM 带宽）占据了大部分解码时间。
- **基准现实到达模式。** 固定批次隐藏了编译新形状以更改批次宽度的成本。

## 结论

Laplace 3B 表明 AWS Trainium2 可以支持标准转换器之外的模型架构。 i14 通过 TorchNeuron Native 和 AWS Neuron SDK 使用原生 PyTorch 来训练和服务其基于 GLA 的模型，同时保留固定的循环状态。

对于代理系统，这改变了基本的服务约束。更长的历史不需要更大的每个序列状态，这可以帮助团队保留更多上下文，同时保持内存使用可预测。

如果不断增长的上下文会增加服务成本、降低并发性或限制代理内存，请尝试 [i14](https://i14.ai) 或联系您的 AWS 客户团队在 AWS Trainium2 上评估 Laplace 3B。
