# 超越 KV cache：用原生 PyTorch 在 AWS Trainium2 上训练并提供 i14 的 Laplace 3B 线性注意力模型

大多数大语言模型（LLM）使用带 softmax attention 的 transformer 架构。推理期间，它们的键值（KV）cache 会随对话或文档上下文增长。这会降低并发度、推高服务成本，并迫使 agentic 应用丢弃有用的历史。

[i14](https://i14.ai) 把 Laplace 3B 设计成一种线性注意力替代方案。它的递推状态每条序列固定为 29.5 MB，与上下文长度无关。i14 与 AWS 合作，用 [TorchNeuron Native 提供的原生 PyTorch 支持](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/frameworks/torch/index.html)把这套自定义架构带到 [AWS Trainium2](https://aws.amazon.com/ai/machine-learning/trainium/) 上。这保住了它的门控线性注意力（GLA）设计与 Muon 优化器。

在一台 trn2.48xlarge 实例上，Laplace 3B 的训练速度约为每秒 120,000 token。模型在 1,280 条并发序列上达到每秒 11,544 个输出 token。本文介绍模型设计、i14 为 Trainium2 所做的改动，以及训练和推理结果。

## 关于 i14

i14 是一家 AI 研究与技术公司，开发模型架构、组件和运行时。它的工作取材于 AI、计算认知科学，以及关于生物系统如何随时间学习的研究。i14 把这些想法应用到一类模型上：既能保留长程上下文，又不让服务状态随每个 token 增长。

## 为什么用线性注意力模型？

Transformer 的 softmax attention 会在上下文范围内比较 token。训练时，这部分计算随序列长度呈二次增长。推理时，KV cache 随模型处理更多 token 而增长。

线性注意力围绕一个随每个 token 更新的递推状态重新组织计算。Laplace 3B 用 GLA 把先前的上下文压缩成一个固定大小的矩阵状态。这把训练时的注意力从 O(*T*2) 变为 O(*T*)，并让推理状态固定在每条序列 29.5 MB。

| **考量** | **Transformer softmax attention** | **采用 GLA 的 Laplace 3B** |
| --- | --- | --- |
| 训练注意力 | 构建成对的 token 分数，O(*T*2) 级增长 | 更新分块的递推状态，O(*T*) 级增长 |
| 推理内存 | KV cache 随上下文增长 | 递推状态大小保持不变 |
| 更长的上下文 | 每条序列占用更多加速器内存 | 上下文长度不会增加递推状态的分配 |
| 实现 | 使用高度优化过的注意力 kernel | 需要架构专用的 kernel 与编译器调优 |

线性注意力压缩历史，而不是保留每一个 key 和 value。因此你必须针对自己的工作负载评估检索质量。固定状态可以惠及长时间运行的 agent、大文档分析，以及需要持久记忆且服务需求可预测的应用。

## i14 如何为 AWS Trainium2 适配 Laplace 3B

Laplace 3B 的原始实现使用针对 GPU 优化的 Triton kernel。AWS 生成式 AI 创新中心（GenAIIC）团队先用标准 PyTorch 算子为 Trainium2 重写了 GLA kernel。在比较两种方案之后，团队选择了 beta 版的 [TorchNeuron Native——AWS Trainium 的原生 PyTorch 后端](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/frameworks/torch/index.html)，因为它的性能更好。

实现过程中需要三项改动：

- **为 GLA 注意力 kernel 使用原生 PyTorch。** 团队用标准 PyTorch 算子替换了 GPU 专用的 fused_chunk_simple_gla Triton kernel，采用 16 个 128 token 的分块，以对上 NeuronCore 片上缓冲区的 128 个分区。
- **重新设计 Muon 的通信方式。** MuonFSDP2 中的两次 all_to_all 集合通信把每 rank 流量削减了 24 倍，把吞吐量提高了 1.63 倍。
- **编译顺序化的反向传播。** 团队把 GLA 递推的 16 个分块步骤静态展开，以适配编译器的图大小和片上内存限制。

工程挑战一节会详细说明每一项改动。

## 为什么选 AWS Trainium 加速器？

[AWS Trainium](https://aws.amazon.com/ai/machine-learning/trainium/) 是一族为模型训练和推理设计的 AWS 机器学习（ML）加速器。一台 trn2.48xlarge 实例组合了 16 颗 Trainium2 芯片、64 个逻辑 NeuronCore、高带宽内存和 NeuronLink-v3 互连。这些资源支撑了本文所述的分布式训练与推理配置。

Trainium2 的三个特性塑造了这次实现：软件管理的片上内存（挑战 1）、高速的芯片间互连（挑战 2）和一个静态编译器（挑战 3）。编译器把 GLA 递推追踪成一张固定的图。

**软件管理的片上内存。** 每个 NeuronCore 有一个 28 MiB 的状态缓冲区（SBUF），含 128 个分区，以及一个 2 MiB 的部分和缓冲区（PSUM）。PSUM 与一个 128×128 的脉动 Tensor Engine 相连，旁边还有独立的向量单元和标量单元。SBUF 不是 cache：编译器会提前调度每一次 `HBM-to-SBUF` 传输，因此数据就位，没有淘汰也没有缺失（图 1）。

## i14 与 Laplace 3B 架构

Laplace 3B 是 24 层的 i14 decoder，每一层都用 Simple GLA 取代 softmax attention。图 2 追踪一层：从顶部的输入 **x***t* 到底部的输出 **x***t* + 1。本节逐一解释各模块：归一化与卷积、QKVG 投影、GLA mixer，以及前馈通道混合器。

**归一化与卷积。** 每个 token 的残差流向量 **x***t* ∈ ℝ*D*（*D* = 3, 072）先经过一次 LayerNorm，再经过宽度为 *k* = 4、带 SiLU 的深度可分离因果 Conv1d。这让每个位置在进入 mixer 之前都有一个 4-gram 摘要。GLA mixer 随后通过其带衰减的状态，对整个历史做基于内容的检索。

**QKVG 投影。** 卷积后的输出经过一个融合矩阵 **W***q**k**v**g* ∈ ℝ9, 216 × 3, 072，其中 9, 216 = *H* × (2*d**k* + 2*d**v*)。它拆成四路逐 token 流：query **q***t*、key **k***t*、value **v***t* 和门控 **g***t*（*H* = 16，*d**k* = 96，*d**v* = 192）。门控在 mixer 之后使用。

![Laplace decoder 层架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/14/ML-21817-2.png)

图 2：Laplace decoder 层架构。绿色 = 固定（无参数），灰色 = 学习得到，黄色 = 递推状态，蓝色 = 投影。

## 工程挑战

三项改动各带来一个工程挑战。

### 挑战 1：在 Trainium 上用原生 PyTorch 实现 GLA

在 GPU 上，GLA 以 flash-linear-attention 库中融合的 Triton kernel fused_chunk_simple_gla 运行。GenAIIC 团队用标准 PyTorch 算子重新表达它，通过 [TorchNeuron Native](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/frameworks/torch/index.html) 执行，写成对固定大小分块的显式循环。分块数在编译期固定，并决定反向展开的深度。团队使用 fla_num_chunks = 16，因此每个分块容纳 *C* = 128 个 token。

在每个分块 *c* 内部，块内输出是带掩码的线性注意力，而运行中的状态 **S** 叠加更早的上下文：

### 挑战 2：FSDP2 下的分布式 Muon 正交化

Muon 在更新之前对每个梯度做正交化。对 96 个二维权重矩阵（27.18 亿参数）中的每一个，它都跑五次 Newton–Schulz 迭代（算法 1）。

![Newton-Schulz 算法](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/19/07-newton-schulz-algorithm.png)

Newton-Schulz 算法

**分布式带来的问题。** Gram 矩阵 **A** = **X****X**⊤ 会把权重的每一行与其余每一行关联起来。在完全分片数据并行（FSDP2）下，64 个 rank 各自只持有 1/64 的行。因此分片本地的 **X****X**⊤ 只能得到一个对角块，丢弃了所有跨分片项（图 5）。

![FSDP2 下 Newton-Schulz 的通信模式](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/14/ML-21817-9.png)

图 5：FSDP2 下的 Newton–Schulz：分片本地的 Gram 块，以及 gather/broadcast 与 all_to_all 的对比。

**朴素做法：gather 加 broadcast。** 每个 rank 都收集完整梯度（5.44 GB），由其中一个 rank 运行 Newton–Schulz，再广播结果。每步要搬运 10.87 GB，而其余 63 个 rank 在等待。

**生产做法：all_to_all 转置。** 在 MuonFSDP2 中，一次 all_to_all 让每个 rank 拿到几个完整的矩阵，全部 64 个 rank 并行运行 Newton–Schulz，然后第二次 all_to_all 把结果送回。每 rank 流量降到 0.45 GB，少了 24 倍。吞吐量从每秒 73,378 token 升到 119,934 token，提高 1.63 倍，且 loss 曲线逐位一致（图 6）。

![每个训练步的通信量](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/14/ML-21817-10.png)

图 6：每步通信量：all_gather 为 10.87 GB，all_to_all 为 0.45 GB。

**通信成本。** Newton–Schulz 在一次训练步骤的 FLOPs 中只占约 2%（9.53 × 1015 中的 1.95 × 1014），所以通信才是瓶颈。在 1.28 TB/s 的 NeuronLink-v3 上，0.45 GB 的交换在约 4.4 秒的一步里只占不到 0.4 ms。

### 挑战 3：为顺序递推展开反向传播

反向传播要对全部 16 次顺序状态更新求导。在 GPU 上，autograd 在运行时构建这张图。在 Trainium2 上，编译器必须提前看到整张展开后的 16 步图，这带来三个约束。

图深度随分块数增长：到 32 个分块（*C* = 64）时，图会让调度器溢出。每分块内存随分块大小增长：到 8 个分块（*C* = 256）时，中间结果会溢到 HBM。所有形状在追踪时固定，因此每个循环中间结果都需要自己的静态分配。

16 个分块（*C* = 128）同时满足三者：展开后的图能放进调度器，中间结果留在片上，瓦片与 128 个 SBUF 分区对齐。

## Trainium2 上的推理优化

通过一个未经修改的 vLLM 引擎，GenAIIC 团队在一台 trn2.48xlarge 实例上以 1,280 条并发序列达到每秒 11,544 个输出 token。

**恒定的服务状态。** 每条序列 29.5 MB 的递推状态，比 8,192 token 时同等的 KV cache 小约 82 倍。把提示词从 2,048 token 增加到 8,192 token，每个输出 token 的成本只增加 0.5%。

**未经修改的 vLLM。** 一个 wrapper 替换每个 decoder 层的单个属性——token mixer，从 vLLM 的池中读写递推状态。由于模型声明自己不含 attention，vLLM 为每条序列分配一个固定页。输出与 i14 参考实现逐 token 一致（BF16 下 3/3 条提示词、48/48 步）。

**定位瓶颈。** 把 decode 时间对 decoder 层数 *L* 做线性拟合，得到：

![Decode 时间线性拟合公式](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/19/08-decode-time-linear-fit.png)

在

*L* = 24

时，即每步 168.1 ms，其中 96.9% 花在 decoder 层内部。大投影耗时 13.27 ms，接近 12 ms 的 HBM 流式下限。大部分时间花在 eager PyTorch 下逐个派发的小算子上。

**扩展到整台实例。** 不使用张量并行时，吞吐量靠副本扩展，每个逻辑 NeuronCore 一个引擎、20 条序列。eager 吞吐量从单副本的每秒 133 个输出 token 增长到 64 副本的 6,772，此时宿主机 CPU 使用率达到 82%。编译 decode 步骤消除了逐算子派发，把吞吐量提高 1.7 倍，达到 11,544（图 8）。

**固定批次基准掩盖了什么。** 在真实流量下，每个新的 decode 批次宽度都是一份单独编译的形状，其首次使用约耗时 11 秒。这类步骤只占总量的 1.1%，却消耗了 47.5% 的 decode 时间。填充到固定宽度以逐位精确的结果消除了这项成本。编译后的 decode 在交错到达下把每副本吞吐量提高 3.52 倍，而在固定批次上只有 1.46 倍。由于 BF16 的重结合会让编译输出与 eager 略有差异，当需要精确可复现时请使用 eager decode。

## 关键要点

这个项目在训练和推理两侧都产出了经验：

- **原生 PyTorch 可以在 Trainium2 上支撑自定义架构。** i14 保住了 GLA 架构，并用 TorchNeuron Native 完成最终实现。
- **通信设计对自定义优化器很关键。** Muon 的 all_to_all 设计把每 rank 流量减少 24 倍，把训练吞吐量提高 1.63 倍。
- **固定状态让推理内存可预测。** 无论上下文多长，每条序列都只用 29.5 MB。
- **先做剖析，再编译。** 占用大部分 decode 时间的是算子派发，而不是算术或 HBM 带宽。
- **用真实的到达模式做基准。** 固定批次掩盖了为变化的批次宽度编译新形状的成本。

## 结论

Laplace 3B 表明 AWS Trainium2 可以支撑标准 transformer 之外的模型架构。i14 通过 TorchNeuron Native 和 AWS Neuron SDK 使用原生 PyTorch，训练并服务了它基于 GLA 的模型，同时保住了固定的递推状态。

对 agentic 系统而言，这改变了一个基础的服务约束。更长的历史不再需要更大的每序列状态，这有助于团队在保持内存用量可预测的同时留住更多上下文。

如果增长的上下文正在推高服务成本、降低并发度或限制 agent 的记忆，可以试试 [i14](https://i14.ai)，或联系你的 AWS 客户团队，在 AWS Trainium2 上评估 Laplace 3B。
