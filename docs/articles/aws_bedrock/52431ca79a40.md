# 用 llama.cpp 在 Amazon SageMaker AI 上部署决策模型

需要路由请求、选择智能体动作或判定策略结果的应用，往往要的是一组固定选项上的得分，而不是自由生成的文本。用 [llama.cpp](https://github.com/ggml-org/llama.cpp)把这些决策模型部署到 [Amazon SageMaker AI](https://docs.aws.amazon.com/sagemaker/latest/dg/realtime-endpoints.html)，就有一条托管路径，可以在 CPU 或 GPU 基础设施上服务量化后的模型。

本文延续一个系列，主题是面向生成式 AI 推理的专用 AWS Deep Learning Container（DLC）。之前的文章写过 [WhisperX](https://aws.amazon.com/blogs/machine-learning/speaker-labeled-transcription-with-whisperx-on-sagemaker-ai/)、[vLLM-Omni —— 第 1 部分](https://aws.amazon.com/blogs/machine-learning/build-real-time-voice-applications-with-vllm-omni-on-sagemaker-ai-part-1/)和 [vLLM-Omni —— 第 2 部分](https://aws.amazon.com/blogs/machine-learning/generate-images-and-video-with-vllm-omni-on-sagemaker-ai-part-2/)。

在本文里，你先用 [AWS DLC for llama.cpp](https://aws.github.io/deep-learning-containers/llama-cpp/)，通过 SageMaker AI 的 `InvokeEndpoint` 提供 OpenAI 兼容的 chat completions。随后用 [SemIf](https://github.com/TheoLeeCJ/SemIf-OpenJev)（原名 OpenJev）扩展同一个运行时，它会在声明好的选项上直接返回概率，不需要解码出答案 token。配套的[代码示例](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/03-features/semif-decision-model)给出了 CPU 和 GPU 两种部署选项。

## 方案概览

图 1 展示从同一个打包模型出发的两条部署路径。文本生成路径使用 AWS DLC for llama.cpp，通过 OpenAI 兼容 API 返回生成的响应。结构化决策路径则构建一个子镜像，用 SemIf 适配器替换默认服务器，返回各个已声明选项的概率。

图 1：按你的负载对 API 和延迟的要求，选择在 CPU 或 GPU 上运行 AWS DLC for llama.cpp 或 SemIf 子镜像

标准路径下，把模型打包成 `model.tar.gz` 放到 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/)里，然后直接引用已发布的 DLC 镜像。容器会找到 `/opt/ml/model` 下的第一个 `.gguf` 文件，把 `POST /invocations` 映射到 `llama-server` 的 `/v1/chat/completions`，并把 `SM_LLAMA_CPP_*` 环境变量转成 llama.cpp 的启动参数。

`llama-server` 的 HTTP API 并不暴露 SemIf 要用的末位 logits 和状态操作。因此结构化决策路径改用 [AWS CodeBuild](https://aws.amazon.com/codebuild/)构建一个子镜像，并存进 [Amazon Elastic Container Registry（Amazon ECR）](https://aws.amazon.com/ecr/)。子镜像保留 DLC 编译好的 CPU 或 CUDA 库，同时把入口点换成一个兼容 SageMaker 的适配器。

## 理解输入与输出 schema

AWS DLC for llama.cpp 接受 OpenAI Chat Completions schema。请求里发一个带 `role` 和 `content` 的 `messages` 数组，再加上 `max_tokens`、`stream` 这类生成控制参数：

```
{
  "messages": [
    {
      "role": "user",
      "content": "A customer cannot receive a password reset email. Reply with the best support queue."
    }
  ],
  "max_tokens": 64,
  "stream": false
}
```

响应使用 OpenAI 兼容的 `choices` 数组，生成的文本从 `choices[0].message.content` 读取。

SemIf 用的是一套受约束的决策 schema，而不是 chat messages。请求里包含调用方定义的 ID、非结构化的状态、一个问题，以及一个有序的允许选项列表：

```
{
  "decision": {
    "id": "support-route",
    "state": "The customer cannot receive a password reset email.",
    "question": "Which queue should handle this request?",
    "options": [
      {"id": "account_access", "description": "Account access support."},
      {"id": "billing", "description": "Billing support."}
    ]
  }
}
```

响应按同样的顺序返回 `option_ids`、`probabilities` 和原始的 `option_logits`，另外附上提示、耗时以及固定了模型版本的元数据。有了稳定的选项 ID，你的应用就能施加阈值、回退和策略校验，而不必去解析生成出来的那段文字。

SemIf 属于更宽泛的一类决策模型：从非结构化状态出发，为应用自定义的结果打分。其他实现还包括 [Jev](https://docs.typesafe.ai/introduction)，即 TypeSafe 的决策模型与 `/v1/systemone` API；[Kev](https://github.com/jaredpalmer/kev)，一个以兼容 TypeSafe API 为设计目标的模型服务器；以及 [Strands Decider 2B](https://github.com/strands-labs/strands-decider)，一个为智能体工作流量身构建、输出经过校准的模型。

## 选对决策工作流

当你的应用在请求时才确定允许的选项，并且需要模型去理解非结构化上下文时，适合用这个模式。例子包括把工单路由到某个队列、从已知取值集合里抽取一个值、给事件定优先级、校验策略结果，或者挑选智能体的动作。鉴权和确定性的业务规则要留在模型外面；把模型概率当作运营上的置信度之前，先验证它们。

需要通过 `InvokeEndpoint` 拿到 OpenAI 兼容的 chat completions 时，就用标准的 SageMaker AI 文本生成路径。SageMaker AI 镜像把 `POST /invocations` 映射到 `llama-server` 的 `/v1/chat/completions` 端点。只有当应用需要这套接口给不了的行为时才去构建子镜像，比如 SemIf 那种直接访问 logits 和状态的用法。

去掉答案 token 的生成本身并不省掉模型推理。SemIf 读取末位 logits 之前，模型仍然要处理完整的状态、问题和选项描述。提示要写得聚焦；投产之前，用你应用里已经标注好的决策来评估所选模型。

## 按你的延迟与质量目标调优

下面的基准测试针对的是 SemIf 扩展，不是文本生成端点。模型规模、量化方式、提示长度、运行时以及 CPU 线程数，都会影响每一次决策。为了量化这些取舍，我们把同一批 231 个公开的 [JevBench](https://github.com/fstandhartinger/jevbench)任务，串行发送给一个 CPU 端点和一个 GPU 端点。

| **配置** | **AWS DLC for llama.cpp** | **有效响应** | **准确率** | **客户端 p50** | **客户端 p95** |
| --- | --- | --- | --- | --- | --- |
| Qwen3.5-4B `Q4_K_M`、`ml.c6i.8xlarge`、32 线程 | [llama-cpp:server-sagemaker-cpu-v1](https://aws.github.io/deep-learning-containers/llama-cpp/) | 231/231 | 179/231（77.5%） | 1.715 秒 | 19.291 秒 |
| Qwen3.5-4B `Q4_K_M`、`ml.g6e.xlarge`、GPU 全量 offload | [llama-cpp:server-sagemaker-cuda-v1](https://aws.github.io/deep-learning-containers/llama-cpp/) | 231/231 | 180/231（77.9%） | 0.352 秒 | 0.599 秒 |

与 CPU 配置相比，GPU 端点在 p50 上快 4.9 倍，在 p95 上快 32.2 倍。示例用上了 SageMaker AI 的实例池功能，按优先级列出兼容的 GPU 实例类型，首选类型不可用时 SageMaker 可以改选其他类型。这个池的顺序是 `g6e`、`g6`、`g5`、`g4dn`。SageMaker 选中了 `ml.g6e.xlarge`，启动日志确认 llama.cpp 把全部 34 层模型都 offload 到了 NVIDIA L40S 上。CPU 镜像和 GPU 镜像用的是不同的 llama.cpp 构建，在 6 道较难的题目上给出了不同的预测。准确率只差一个答案，应当看作运行时的波动，而不是 GPU offload 能提升模型质量的证据。

更小的模型能把中位延迟降下来，但 2B 和 0.8B 候选的准确率只有 66.7% 和 58.4%。因此示例仍把 4B 的 `Q4_K_M` 模型作为质量优先的默认选择。这些测量包含网络延迟，不构成服务承诺。

要用你自己的决策集，对完整的模型与基础设施配置做基准测试。后台、离线、吞吐量不大这类对延迟不敏感、能容忍秒级响应时间的负载用 CPU；交互式决策、长提示，或对尾部延迟要求苛刻的负载用 GPU。状态和选项描述要简练，共享同一状态的决策合并进一个请求，并发靠扩端点实例来扛。共享状态的打分能复用公共的提示前缀，而适配器宁可返回可重试的 HTTP `503` 响应，也不让它那个有状态的 llama.cpp 上下文外面堆出无界的队列。

## 前置条件

你需要：

- 一个 AWS 账户，以及部署所在 AWS 区域里的一个 S3 bucket。
- Python 3.10 或更高版本、Git，以及 AWS Command Line Interface（AWS CLI）。
- 一个用途专用的 CodeBuild 服务角色，供可选的 SemIf 扩展使用。
- 一个供 SageMaker AI 扮演的 [AWS Identity and Access Management（IAM）](https://aws.amazon.com/iam/)角色。
- 针对 SageMaker AI、Amazon ECR、Amazon S3、CodeBuild、IAM pass-role 操作，以及 [Amazon CloudWatch Logs](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/WhatIsCloudWatchLogs.html)的权限。
- x86 CPU 或 NVIDIA GPU 这类兼容实例的 SageMaker 实时端点配额。

文本生成示例使用 CPU DLC 和一个固定的 CPU 实例。SemIf 扩展仍以 CPU 为默认，服务那些对延迟不敏感的负载，同时提供一个可选的 CUDA 镜像，支持有序的实例池。创建端点前请先看 [SageMaker AI 定价](https://aws.amazon.com/sagemaker/ai/pricing/)。

## 部署决策模型并用 SemIf 扩展

按下面的步骤部署标准的文本生成端点，然后构建可选的 SemIf 扩展，在 CPU 或 GPU 上做结构化决策。

- **克隆代码示例并安装它的依赖。**  `git clone https://github.com/aws-samples/sagemaker-genai-hosting-examples.git cd sagemaker-genai-hosting-examples/03-features/semif-decision-model python3 -m venv .venv . .venv/bin/activate python3 -m pip install -r deploy/requirements.txt`
- **按你的账户设置部署取值。**  `export AWS_REGION="<your-region>" export ARTIFACT_BUCKET=amzn-s3-demo-semif-artifacts export CODEBUILD_ROLE_ARN=arn:aws:iam::111122223333:role/semif-codebuild-role export SAGEMAKER_ROLE_ARN=arn:aws:iam::111122223333:role/semif-sagemaker-role export STANDARD_ENDPOINT_NAME=llamacpp-gguf export SEMIF_ENDPOINT_NAME=semif-decision-workflows`
- **用 CodeBuild 打包指定版本的 GGUF 模型和 tokenizer。**  `python deploy/prepare_model_build.py \ --region "$AWS_REGION" \ --bucket "$ARTIFACT_BUCKET" \ --codebuild-role-arn "$CODEBUILD_ROLE_ARN" \ --model-s3-uri "s3://$ARTIFACT_BUCKET/semif-llamacpp/model.tar.gz"`  等返回的 build ID 进入 `SUCCEEDED` 状态。构建会把源版本和校验和记录到 `model-manifest.json` 里，一旦 GGUF 的校验和与验证过的值不一致就停止。
- **用 AWS DLC for llama.cpp 部署 GGUF 模型。** 从 [AWS DLC for llama.cpp 文档](https://aws.github.io/deep-learning-containers/llama-cpp/)里取出一个按摘要固定的 `server-sagemaker-cpu-v1` 镜像，然后创建 SageMaker AI 模型、端点配置和端点：  `export STANDARD_IMAGE_URI="<published-llama-cpp-cpu-image>@sha256:<digest>" python deploy/deploy_standard_endpoint.py \ --region "$AWS_REGION" \ --image-uri "$STANDARD_IMAGE_URI" \ --model-data-url "s3://$ARTIFACT_BUCKET/semif-llamacpp/model.tar.gz" \ --role-arn "$SAGEMAKER_ROLE_ARN" \ --instance-type ml.c6i.2xlarge \ --name "$STANDARD_ENDPOINT_NAME"`  请选择 `server-sagemaker-cpu-v1` 或 `server-sagemaker-cuda-v1` 镜像，而不是对应的 EC2 镜像。SageMaker AI 镜像实现了 `/ping` 和 `/invocations` 的容器契约，并把调用负载映射到 chat completions。本演练通过 Amazon S3 里的 SageMaker AI 模型工件来提供 GGUF 模型。另一种做法是配置 `SM_LLAMA_CPP_HF_REPO` 和 `SM_LLAMA_CPP_HF_FILE`，在端点有网络出口时从 Hugging Face 下载 GGUF 文件。这条路径不需要 Dockerfile，也不需要 ECR 仓库。等端点进入 `InService`，再发一个 OpenAI 兼容的聊天请求：  `python deploy/invoke_standard_endpoint.py \ --region "$AWS_REGION" \ --endpoint-name "$STANDARD_ENDPOINT_NAME"`
- **构建可选的 SemIf 子镜像，并取到它不可变的摘要。** CPU 用：  `python deploy/prepare_build.py \ --region "$AWS_REGION" \ --bucket "$ARTIFACT_BUCKET" \ --codebuild-role-arn "$CODEBUILD_ROLE_ARN"`  GPU 则改为构建 CUDA 子镜像：  `python deploy/prepare_build.py \ --region "$AWS_REGION" \ --bucket "$ARTIFACT_BUCKET" \ --codebuild-role-arn "$CODEBUILD_ROLE_ARN" \ --dockerfile Dockerfile.gpu \ --image-tag "gpu-$(date +%Y%m%d%H%M%S)"`  构建成功后，拼出不可变的镜像 URI：  `ECR_REPOSITORY_URI=$(aws ecr describe-repositories \ --region "$AWS_REGION" \ --repository-names semif-llamacpp-dlc \ --query 'repositories[0].repositoryUri' \ --output text) IMAGE_DIGEST=$(aws ecr describe-images \ --region "$AWS_REGION" \ --repository-name semif-llamacpp-dlc \ --query 'sort_by(imageDetails,&imagePushedAt)[-1].imageDigest' \ --output text) export IMAGE_URI="${ECR_REPOSITORY_URI}@${IMAGE_DIGEST}"`  部署脚本会拒绝可变的镜像 tag。
- **部署 SemIf 端点。** CPU 配置用的是固定实例类型：  `python deploy/deploy_endpoint.py \ --region "$AWS_REGION" \ --image-uri "$IMAGE_URI" \ --model-data-url "s3://$ARTIFACT_BUCKET/semif-llamacpp/model.tar.gz" \ --role-arn "$SAGEMAKER_ROLE_ARN" \ --instance-type ml.c6i.8xlarge \ --threads 32 \ --name "$SEMIF_ENDPOINT_NAME"`  等返回的端点名进入 `InService`。这条路径会设 `n_gpu_layers=0`。适配器围绕一个有状态的 llama.cpp 上下文把打分串行化，所以要先测量自己的负载，再用端点实例横向扩容，不要假定一个容器内部能并行打分。GPU 镜像需要提供有序的实例池，并要求 offload 整个模型：  `python deploy/deploy_endpoint.py \ --region "$AWS_REGION" \ --image-uri "$IMAGE_URI" \ --model-data-url "s3://$ARTIFACT_BUCKET/semif-llamacpp/model.tar.gz" \ --role-arn "$SAGEMAKER_ROLE_ARN" \ --instance-pool ml.g6e.xlarge \ --instance-pool ml.g6.2xlarge \ --instance-pool ml.g5.2xlarge \ --instance-pool ml.g4dn.2xlarge \ --gpu-layers=-1 \ --provision-timeout 1200 \ --name "$SEMIF_ENDPOINT_NAME"`  实例池是按顺序回退的放置选择，不是推理层的负载均衡，SageMaker 只为该变体选出一种可用的类型。SageMaker AI 逐个尝试池中类型期间，端点创建可能耗时更久。要去启动日志里确认选中的 GPU，以及所有模型层都已 offload 的那条确认信息。
- **用示例决策调用 SemIf 端点。** 请求为每个允许的选项声明了稳定的 ID：  `{ "decision": { "id": "support-route", "state": "Customer asks to reset a forgotten password and says the reset email never arrived.", "question": "Which queue should handle this request?", "options": [ {"id": "account_access", "description": "Account access and authentication support."}, {"id": "billing", "description": "Billing and payment support."}, {"id": "sales", "description": "Sales and product evaluation."} ] } }`     `python deploy/invoke_endpoint.py \ --region "$AWS_REGION" \ --endpoint-name "$SEMIF_ENDPOINT_NAME"`  响应保持了选项顺序，并给出条件概率、原始 logits、token 与提示元数据，以及所固定模型的标识：  `{ "result": { "id": "support-route", "option_ids": ["account_access", "billing", "sales"], "probabilities": [0.99996, 0.00003, 0.00001], "option_logits": [28.47, 17.92, 17.04], "prompt_sha256": "016267542103ab91422c425d2234ec7e1b9aef77f9d3e481b96db2de7cca470a", "readout": "quantized last-position logits restricted to declared answer slots; no generated tokens" } }`  阈值和回退要放在应用层。不要把模型的决策当作鉴权的替代。

## 清理

删除 SageMaker AI 端点、端点配置和模型：

```
python deploy/cleanup_endpoint.py \
  --region "$AWS_REGION" \
  --name "$STANDARD_ENDPOINT_NAME"

python deploy/cleanup_endpoint.py \
  --region "$AWS_REGION" \
  --name "$SEMIF_ENDPOINT_NAME"
```

脚本只删除显式点名的那些 SageMaker AI 资源。不再需要时，请删除 CodeBuild 项目、ECR 仓库、Amazon S3 中的模型与源对象、日志，以及那些专用 IAM 角色。

## 结论

AWS DLC for llama.cpp 提供了一个托管底座，让你在 SageMaker AI 的 CPU 和 GPU 实例上服务决策模型。它可以从 SageMaker AI 的模型工件或配置好的 Hugging Face 仓库加载 GGUF 模型，然后通过 `InvokeEndpoint` 提供 OpenAI 兼容的 chat completions，不需要自定义容器。当应用需要直接访问 logits 和模型状态操作时，可以用 SemIf 适配器扩展这个 DLC。对延迟不敏感的负载选 CPU；当提示 prefill 和尾部延迟会影响应用体验时选 GPU。

请查看[代码示例](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/03-features/semif-decision-model)、[AWS DLC for llama.cpp 文档](https://aws.github.io/deep-learning-containers/llama-cpp/)和 [SageMaker AI 自定义推理容器契约](https://docs.aws.amazon.com/sagemaker/latest/dg/your-algorithms-inference-code.html)，据此把部署改造成适合你自己负载的形态。
