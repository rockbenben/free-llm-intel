# 用 Amazon Bedrock AgentCore 的数据集管理，构建随 agent 一同成长的测试套件

*AgentCore 中的[数据集（Datasets）](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/datasets-manage.html)目前处于公开预览阶段。*

把快速变化的线上信号与稳定的离线基线结合起来，agent 评估才能发挥最大威力。要弄清你的 agent 是否随时间真正在进步，你需要在不断变化的真实流量之外，再有一套固定的基准。

在 Amazon Bedrock AgentCore 中把评估基线所需的测试用例作为数据集来管理，等于把带版本的测试夹具（test fixture）这套纪律带进了 agent 评估。你可以编写包含输入、期望输出、断言与工具调用序列的场景，再把它们发布为不可变的编号版本，这样同一个版本在一次运行之内不会悄悄变动。你可以在可修改的草稿上自由迭代，直到准备锁定一个检查点。而当生产中出问题时，那次故障会变成一个永久的测试用例，此后每一次变更都要拿它来评估。

在本文中，我们用一个金融市场情报 agent 走完整套工作流。我们从生产 trace 中捕获故障，构建带版本的数据集，运行一次评估，修复 agent，再用同一组锁定输入确认改进。

## 数据集为何重要

agent 天生就是非确定性的。同样的输入在不同运行中可能产生不同的输出，这让单次评估结果几乎毫无意义。你无法判断分数的变化是因为 agent 变了，还是因为模型采样不同。要确认某项变更是否真的有用，唯一办法是在稳定的输入上做一致的度量。

但仅有稳定的输入还不够。大语言模型（LLM）评判器能告诉你一个回答听起来是否有帮助，却无法告诉你股价是否准确、经纪人的工作流是否按正确顺序执行，或者个人可识别信息（PII）是否在会话之间泄露。这些检查需要标准答案（ground truth）：期望的响应、必需的工具调用序列，以及无论回答如何措辞都必须成立的断言。正是 ground truth 把主观打分变成可验证的度量。没有它，你衡量的只是正确性的表象，而不是正确性本身。

带版本的数据集让两者兼得。它把输入固定住，使分数在不同运行之间可比；它又携带 ground truth，使这些分数具有意义。在 agent 评估真正发生的两个场所，这一点最为重要。

![示意图：开发者迭代的内循环与 CI/CD 评估的外循环，二者都汇入一个共享的带版本数据集](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/28/ML-21133-1.png)

**内循环**是开发者的工作台。你调用 agent、看分数、调整某个工具描述，然后再调用一次。这个循环以分钟计。问题不在于这个阶段要不要跑评估，而在于测试用例往往只是手边现成的东西：上周某人写的几个问题，或者你碰巧保存下来的一个会话。当分数提升时，你希望相信修复奏效了。但如果底下没有稳定的输入，你无从判断是 agent 变好了，还是问题变简单了。

**外循环**是 CI/CD pipeline。在一次变更发布之前，需要有东西来说明它没有弄坏任何东西。多数团队都有这道门禁。他们常常缺少的，是门禁底下那组稳定的、带版本的输入，以及明确的断言。这意味着门禁只是在测试某人上次指向的东西，没有 ground truth 可供核对。一条因为换了问题而通过的 pipeline，并没有抓住回归，它是漏掉了回归。

带版本的数据集填补了这道缺口。开发者在内循环中把故障整理进草稿。在外循环中，该草稿的某个已发布版本成为门禁。它不可变、ground truth 完整，测试的场景与上一个 sprint 以及再上一个 sprint 完全一致。告诉开发者修复生效的那个分数，也正是 pipeline 用来决定是否发布的同一个分数。

## 两类测试场景

Amazon Bedrock AgentCore 中的数据集支持两种 schema 类型，分别以不同方式服务这两个循环。

**预定义场景**面向过去。你已经定义了用户会发给 agent 的确切查询，也知道正确是什么样：期望的响应、工具调用序列，以及必须成立的断言。你把它们写下来，评估器检查 agent 是否满足这些要求。一旦某个故障被固化为预定义场景，它就会留在此后每一次评估运行中。它们属于外循环门禁，因为通过与否的标准是明确的、可重复的，并且不取决于对话如何展开。

**用户模拟场景**面向未来。你不去编写对话轮次，而是描述一个 persona：这个 actor 是谁、想达成什么、如何沟通。一个由 LLM 驱动的 actor 与你的 agent 进行真实的多轮对话，直到目标达成或达到轮次上限。你不编写 actor 说什么，覆盖面从交互中自然涌现。更多信息请参阅 AgentCore 用户指南中的[用户模拟](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/user-simulation.html)。

这与标准评估工具包中的任何东西都不同。预定义场景测试你的 agent 是否能正确处理某个特定输入。模拟场景测试你的 agent 能否满足某一类用户，而不论该用户走的是哪条路径。

本文全程使用一个 [Market Trends Agent](https://github.com/awslabs/agentcore-samples/tree/main/02-use-cases/market-trends-agent) 作为贯穿示例。该 agent 为金融机构的投资经纪人服务。经纪人给 agent 发消息，比如“我是 Morgan Stanley 的 Sarah Chen，关注科技与清洁能源——NVDA 今天怎么样？”agent 识别出这位经纪人，把其偏好存入 AgentCore Memory，检索 NVIDIA 当前股价，并在 Bloomberg 与 Reuters 上搜索相关新闻。随后它给出一份个性化简报，把数据与 Sarah 声明的投资关注点联系起来。第二天 Sarah 再来时，agent 记得她的档案，并据此调整回答。

对于预定义场景，你可能已经有用户与 agent 交互的生产 trace，可以整理进评估数据集。针对 Market Trends Agent 的一个例子如下：

```
PreDefinedScenario{
    "scenario_id": "broker_profile_onboarding",
    "turns": [
        {
            "input": (
                "Hi, I'm Sarah Chen from Morgan Stanley. "
                "I focus on tech and clean energy. "
                "Risk tolerance: moderate-high. "
                "Client base: institutional and high-net-worth."
            )
        }
    ],
    "expected_trajectory": {"toolNames": ["identify_broker", "update_broker_financial_interests"]},
    "assertions": [
        "Agent identifies the broker by name and firm.",
        "Agent stores the broker's sector preferences and risk tolerance.",
        "Agent acknowledges receipt of the profile and offers to help.",
    ],
    "metadata": {"category": "onboarding", "priority": "high"},
}
```

一位模拟的资深科技分析师，可能先就 NVIDIA Corporation Common Stock（[NVDA](https://www.nasdaq.com/market-activity/stocks/nvda)）提出一个宽泛的问题。当回答显得单薄时她会追问，要求与 Advanced Micro Devices, Inc. Common Stock（[AMD](https://www.nasdaq.com/market-activity/stocks/amd)）做对比，只有当手里有了能在客户电话会上引用的内容时才表示结束。没有人编写这些轮次。这个 actor 从档案中把它们生成出来。你可以这样定义这个场景：

```
SimulatedScenario(
    scenario_id="sim-tech-analyst-nvda-amd-deep-dive",
    scenario_description=(
        "A senior technology research analyst probes for a deep, citable NVDA vs AMD briefing ahead of a client call."
    ),
    actor_profile=ActorProfile(
        traits={
            "expertise": "senior",
            "focus": "semiconductors",
            "style": "skeptical and data-driven",
        },
        context=(
            "Senior sell-side technology analyst preparing talking points for a high-value client call. "
            "Expects multi-layered analysis, not surface-level summaries, and will push back when answers feel generic or thin."
        ),
        goal=(
            "Pressure-test the agent's semiconductor domain depth by asking about NVIDIA, then insisting on richer detail, "
            "requesting a structured comparison with AMD, and only concluding when she has citable points for a client conversation."
        ),
    ),
    input=(
        "I'm prepping for a client call and need a quick but solid briefing on NVIDIA. "
        "Start with NVDA's recent performance and positioning in semiconductors."
    ),
    max_turns=8,
    assertions=[
        "Agent provides an initial NVDA summary with recent performance and positioning",
        "Agent responds with deeper fundamentals, product/roadmap, or moat detail for NVDA",
        "Agent produces a structured NVDA vs AMD comparison (e.g., valuation, growth, segments)",
        "Agent includes specific, citable data points or metrics suitable for a client call"
    ],
)
```

在你还不确定有哪些故障模式尚未被发现时，用户模拟在内循环中尤其有用。浮现出来的故障会成为下一个数据集版本中预定义场景的候选，并直接汇入外循环门禁。

![示意图：用户模拟基于 actor 档案生成多轮对话，其中的故障被提升进预定义数据集](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/28/ML-21133-2.png)

关于模拟在底层如何工作，有几点值得了解。actor 运行在你于 `SimulationConfig` 中指定的 Bedrock 模型上。每一轮，actor 接收 agent 的响应并产出三样东西：它对目标是否达成的内部推理、下一条要发送的消息，以及一个停止信号。当 actor 发出完成信号、达到 `max_turns`、或 actor 不再产出下一条消息时，对话结束。由于对话路径是动态的，模拟场景不支持 `expected_trajectory` 或逐轮的 `expected_response`。请改用断言来表达 ground truth，并描述你期望的结果，而不论对话是如何走到那一步的。

对于 Market Trends Agent，一个预定义场景覆盖了已经坑过某位经纪人的价格漂移缺陷。一个模拟场景覆盖一位环境、社会与治理（ESG）专家，此人尚未暴露出故障，但代表了 agent 必须妥善服务的真实用户类型。

## AgentCore 中的数据集如何工作

在 AgentCore 中，[数据集](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/datasets-manage.html)是内建的一等资源，具备 ARN、IAM 授权与标签。无需预置 Amazon Simple Storage Service（Amazon S3）存储桶，也无需配置外部服务。

- **草稿与发布。** 每个数据集都有一个可修改的草稿，你可以在其中自由增删场景。当你想有一个稳定检查点时，就发布它。草稿会变成一个不可变的编号版本。把一次评估运行固定到 Version 3，它就会使用 Version 3 中确切的那些场景，无论此后你往草稿里加了什么。
- **写入时即做 schema 校验。** 创建数据集时你声明一个 schema 类型，每个场景在被接受前都要对照该 schema 校验。格式错误的样本在摄入时就被拒绝，而不是在 30 分钟的评估跑到一半时才作为错误浮现。
- **一个数据集，多个 runner。** 用 `DatasetManagementServiceProvider` 加载数据集，再把它传给按需 runner（用于快速的逐场景反馈）或批量 runner（用于跨多个会话的汇总打分）。无论你是在工位上迭代，还是在为部署设门禁，同样的场景、断言与数据集 ID 都适用。

## 这个 agent：Market Trends Assistant

我们使用部署在 AgentCore Runtime 上的 LangGraph 应用 [Market Trends Agent](https://github.com/awslabs/agentcore-samples/tree/main/02-use-cases/market-trends-agent) 作为贯穿示例。完整源码位于 AgentCore samples 仓库的 `02-use-cases/market-trends-agent` 目录下。该 agent 具备以下工具，用于服务金融经纪人的查询：

| **工具** | **作用** |
| --- | --- |
| `get_stock_data` | 某个 ticker 的当前价格、当日涨跌与成交量。 |
| `search_news` | 多来源金融新闻搜索（Bloomberg、Reuters、CNBC、WSJ、FT）。 |
| `identify_broker` | 从消息中提取经纪人身份，用于检索记忆。 |
| `get_broker_financial_profile` | 读取已存储的偏好、风险承受能力与行业关注点。 |
| `update_broker_financial_interests` | 把新的偏好写入长期记忆。 |

有三种故障模式出现得足够频繁，值得为它们设立永久测试用例：

- **价格陈旧** — agent 报出的数字与实时值偏离超过 2%，通常是因为它复用了缓存的工具响应，而不是发起一次新的调用。
- **跳过身份检查** — agent 没有先调用 `identify_broker` 就直接跳到 `get_broker_financial_profile`，这可能取到错误经纪人的偏好，并给出为他人投资组合定制的回答。
- **PII 泄漏** — 某位经纪人档案中的个人可识别信息泄露到另一个会话的响应中，通常是因为记忆层没有尊重会话边界。

这些故障每一个都细微到能通过人工抽查，却又严重到会侵蚀那些每天依赖该 agent 的经纪人的信任。

![Market Trends Agent 架构示意图，展示运行在 AgentCore Runtime 上的 LangGraph 应用、AgentCore Memory，以及用于服务经纪人查询的五个工具](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/28/ML-21133-3.png)

## 实现

这套动手演练大约需要 30 分钟。

### 先决条件

你需要准备以下内容：

- 一个具备 AgentCore Runtime、Memory、Evaluations 与 Amazon CloudWatch 权限的 AWS 账户。
- 已配置 AWS 命令行界面（AWS CLI）。
- 已启用 CloudWatch Transaction Search（账户一次性开通）。
- 已克隆 samples 仓库并部署 Market Trends Agent（`uv run python deploy.py`）。

完整示例位于 [AgentCore samples 仓库](https://github.com/aws-samples/amazon-bedrock-agentcore-samples) 的 `02-use-cases/market-trends-agent` 目录中。

### 操作演练

- **部署 Market Trends Agent。** 运行 `uv run python deploy.py` 预置 AgentCore Runtime、Memory、IAM 角色与 ECR 容器。agent ARN 会写入 `.agent_arn`。
- **创建并版本化评估数据集。** 运行 `uv run python optimization/manage_dataset.py --no-cleanup` 创建两个数据集，并分别为它们发布一个不可变版本。**预定义数据集**包含五个脚本化测试用例，覆盖 agent 的核心故障模式：经纪人引导、股票数据检索、多轮画像后跟新闻、回访经纪人的记忆召回，以及 PII 安全检查。PII 用例在用户消息中使用了一个虚构的 SSN，它绝不应出现在响应中。**模拟数据集**包含三个 actor 档案场景。第一个是资深科技经纪人，需要在客户电话会前拿到一份动量简报。第二个是审查组合对齐情况的 ESG 专家。第三个是寻找收益机会、偏好分红的投资者。每个 actor 都驱动自己的对话，没有脚本化轮次。脚本还演示了日常的整理工作流：新增示例、更新既有示例，并在发布前删除陈旧用例。
- **针对带版本数据集运行评估。** 运行 `uv run python optimization/user_simulated_dataset.py` 加载模拟场景，逐一调用 agent，并等待 span 落到 CloudWatch。脚本随后提交一次批量评估，包含 Correctness、Helpfulness 与 GoalSuccessRate。逐场景分数与解释会打印到控制台。
- **迭代：修复 agent 并重新评估。** 根据评估解释更新工具描述或系统 prompt。用 `add_examples_and_wait()` 把新暴露的边界用例加入草稿，用 `create_dataset_version_and_wait()` 发布新版本，然后重跑。因为两次运行之间的场景与断言完全相同，前后对比就隔离出了你这次变更的效果。此时价格漂移场景上 Correctness 的提升才真正有意义：两次测试用的是同一份输入。或者，你也可以直接使用 AgentCore 给出的建议来完成这一轮 agent 改进——它以评估器作为信号，就改进 agent 的系统 prompt 与工具描述给出建议，Market Trends Agent 示例中的 [optimize_agent.py](https://github.com/awslabs/agentcore-samples/blob/main/02-use-cases/market-trends-agent/optimization/optimize_agent.py) 演示了这一做法。
- **查看结果。** 分数会显示在 AgentCore Observability 控制台以及一个专用的 CloudWatch 日志组中。explanation 字段告诉你某个场景为何通过或失败：“在 `get_broker_financial_profile` 之前从未调用过 `identify_broker`”或者“agent 的响应包含与 PII 安全断言匹配的 SSN 模式”。

完成这些步骤后，数据集会作为托管资源持久保存在你的 AWS 账户中。后续的评估作业可以引用同一个数据集 ID 与版本，无论它们是从开发者机器、CI/CD pipeline 还是定时回归检查触发的。

## 在工作流中复用该数据集

| **模式** | **用例** | **行为** |
| --- | --- | --- |
| 按需 runner | 开发、CI/CD 门禁 | SDK 调用 agent、收集 span、立即打分，返回逐场景详情。 |
| 批量 runner | 基线、大规模对比 | 服务异步完成打分，把汇总结果写入 CloudWatch。 |

当你需要开发阶段的即时逐场景反馈、且数据集较小并能自行管理并发时，使用按需 runner。当你需要在大数据集上衡量整体质量，或在规模上对比两个 agent 版本时，使用批量 runner。

对于部署门禁，把评估固定到一个已发布版本，并在任一评估器低于你的阈值时让构建失败。由于该版本不可变，门禁在每次 PR 上测试的都是同样的场景，无论此后草稿里又加了什么。

同一个带版本数据集也会输入到 AgentCore Optimization。当你使用 Recommendations API 生成改进后的系统 prompt 或工具描述时，驱动这些决策的评估分数都以你的数据集为依据。当你设置 A/B 测试来用真实流量验证这些改进时也是如此。稳定的输入让优化循环值得信赖，而不是随着测试集变动而产生的副产物。

## 值得尽早采用的实践

**让测试套件扎根于真实事故。** 最能抓到问题的场景，源自真实的生产故障。某位经纪人收到了陈旧价格、某个档案在会话之间串了、或者 PII 出现在了不该出现的地方。这些针对的是你的 agent 已经在真实用户面前暴露过的弱点。而凭空设想的问题，针对的只是想象中的弱点。

**用预定义场景求深度，用模拟场景求广度。** 预定义场景守护你已经发现的 bug，模拟场景暴露你还没发现的 bug。健康的数据集两者兼备。对 Market Trends Agent 而言，预定义场景覆盖已经坑过用户的价格漂移与工作流顺序 bug，模拟场景则演练各色经纪人 persona，把 agent 推向没人预料到的方向。

**每次变更前先发布一个版本。** 版本不可变，保留也不花什么成本。几个月后当你排查分数回归时，你会希望确切知道每个检查点上生效的是哪些场景。

**一个数据集，多个版本。** 不要每个 sprint 都新建一个数据集。价值在于连续性。同一个数据集 ID 会累积你的 agent 遇到过的每一个故障，而未来每一次评估都继承这段历史。发布新版本意味着在已学到的一切之上继续构建。新建数据集则意味着从零开始。

## 清理

为避免产生后续费用，请用 `DatasetClient.delete_dataset()` 删除数据集及其版本。要移除 Market Trends Agent，请按仓库 README 中的清理章节操作。

## 结论

测试套件只有在保持不动时才有用。当两次运行之间输入发生变化，你的分数衡量的是测试集的漂移，而不是 agent 的改进。

在 AgentCore 中管理数据集，让你把带版本、经 schema 校验的测试用例作为托管资源来使用。生产故障变成永久的回归场景，模拟 persona 生成你无法手写脚本的覆盖面，而不可变版本让你能在不同 agent 发布之间诚实地对比。

上个季度某位经纪人发现的那个价格 bug，如今就是一个测试用例。系统 prompt 的每一次改动、工具描述的每一次更新、以及每一次模型替换，都要拿它来评估。这套测试套件累积关于你的 agent 如何失败的机构知识，并让未来每一个版本都对这段历史负责。

要开始使用，请参阅 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/) 与 [Market Trends Agent 示例](https://github.com/aws-samples/amazon-bedrock-agentcore-samples/tree/main/02-use-cases/market-trends-agent)。
