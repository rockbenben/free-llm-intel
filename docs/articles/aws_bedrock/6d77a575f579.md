# agent 评估手册：Amazon Bedrock AgentCore Evaluations 上的内置、DeepEval 和 AutoEval

把 agent 部署到生产环境后，最难回答的问题之一是：它到底有没有在正常工作？衡量标准不是它能不能跑起来，而是它能否在规模化的情况下完成业务需要的事。很多团队会说，这一点他们其实看不见。他们抽查输出、盯着延迟、能拿到时就收集用户反馈。可这些都回答不了：agent 是否完成了用户的任务、在长会话里有没有跑题、有没有泄露个人身份信息（PII），或者悄悄跳过了本该执行的一半步骤。

![冰山图：把团队关注的表面信号，与水线之下决定成败的隐藏 agent 行为作对比](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/10/ML-21893-1.png)

图 1：团队通常盯着表面信号，但业务结果由水线之下的 agent 行为决定

agent 评估就是为解决这个问题的。难点在于：某一项指标得分高，可能掩盖另一项上的失败。一个支持 agent 可以解决每一张工单，却仍在回复里泄露个人信息。这种情况下，尽管完成率很高，agent 其实是失败的。要把评估做对，就得在合适的粒度上，衡量对每个 agent 真正重要的行为。

本文展示如何在 Amazon Bedrock AgentCore 上做到这一点。我们把 AgentCore 内置评估器，与直接来自 AgentCore Evaluations 的 DeepEval、AutoEval 评估器结合使用。

## 从业务结果出发，而不是从指标名称出发

最常见的错误是从指标清单入手，挑几个名字听起来顺眼的。“Helpfulness 听着不错，就用它。”结果跑起来、也产出了数字，却几乎给不出有用的洞察。这个指标贴合的是它的名字，而不是成功对这个 agent 意味着什么。

换个做法，从三步开始。

- **用业务语言定义成功。** 对客户支持 agent 来说，可能是首次接触即解决；对研究 agent 来说，可能是给出完整、来源充分、且完全基于检索文档的答案；对内容审核助手来说，则是该标记的都标记、且只标记该标记的。
- **把结果拆成可观察的行为。** 一个实现首次接触即解决的客户支持 agent，通常会完成用户明确提出的目标、在问题需要澄清时跨轮次保持连贯、把回复控制在合规边界内，并正确调用后端工具，比如创建工单或查询订单。
- **把每个行为映射到合适层级的评估器。** trace 级指标覆盖逐轮或逐次工具调用的行为；session 级指标覆盖只有通看整段对话才有意义的结果。

![从业务成功到可观察行为再到评估器的三步流程，以客户支持映射示例说明](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/10/ML-21893-2.png)

图 2：把业务结果转化为可观察行为，再转化为 trace 或 session 级的具体评估器

这个三步流程，正是让评估变得有用的心智模型。本文余下部分讲 AgentCore 提供了哪些能力来落地它。

## 评估器目录

AgentCore 拥有来自三个来源的庞大评估器目录：

- **内置评估器**由 AWS 编写并做过质量测试。你按 ID 引用它们（`Builtin.GoalSuccessRate`、`Builtin.Helpfulness` 等另外 13 个），其余都由服务处理。它们经过可靠性基准测试、覆盖常见维度，是最直接的起点。
- **第三方托管评估器**来自 [DeepEval](https://deepeval.com/) 和 [AutoEval](https://www.braintrust.dev/docs/evaluate/autoevals) 这两个成熟的开源评估库。以托管模式使用时，AgentCore 托管代码、挑选 judge 模型，并在自有算力上运行推理，和内置评估器完全一样。如果你的团队在开发里已经用了其中之一，就能在生产中跑同样的指标，不必另建评估服务。
- **自定义评估器**以某个内置或第三方评估器为基础，可以换成自己的模型，并修改 prompt 或评分标准。

![按评分逻辑、judge 模型和 AWS 质量测试，对比 AgentCore 内置、第三方托管和自定义派生评估器三层的表格](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/10/ML-21893-3.png)

图 3：三层评估器以 AWS 质量保证为代价，换取对运行推理的模型和账户越来越强的控制

创建之后，自定义派生评估器的用法与其他评估器完全一致。

## 评估器全景

AgentCore 自带庞大的评估器目录，所以你很少需要从一张白纸开始。在动手写自定义 judge 之前，先看看是否已经有一个在衡量你关心的行为。下图展示了完整全景。

![按来源划分的 AgentCore 评估器目录：内置 AWS 评估器与轨迹检查、DeepEval、AutoEval，以及自定义 LLM-as-a-judge](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/10/ML-21893-4.png)

图 4：AgentCore 上跨内置、DeepEval、AutoEval 和自定义来源的完整评估器全景

**内置 AWS 评估器**分为五组：

- **响应质量**衡量答案是否准确、有依据、组织良好：`Correctness`、`Faithfulness`、`Helpfulness`、`ResponseRelevance`、`Conciseness`、`Coherence`、`InstructionFollowing`、`Refusal`。
- **任务与目标完成**有 `GoalSuccessRate`，它通看整个 session，判断用户的目标是否达成。
- **工具使用**有 `ToolSelectionAccuracy` 和 `ToolParameterAccuracy`，检查 agent 是否选对了工具、传入了正确的参数。
- **Skills** 有 `SkillSelectionAccuracy` 和 `SkillInstructionFollowing`，面向加载 skills 的 agents：是否调用了正确的 skill，是否遵循了其步骤？
- **安全**有 `Harmfulness` 和 `Stereotyping`。

除此之外，还有三项基于 ground truth 的轨迹检查：`TrajectoryExactOrderMatch`、`TrajectoryInOrderMatch` 和 `TrajectoryAnyOrderMatch`。它们把 agent 实际的工具路径与你预期的路径对比。当“怎么走到结果”和“产出了什么”同样重要时，就用它们。

**DeepEval** 提供四组托管的开源指标：

- 任务与目标完成：`TaskCompletion`、`GoalAccuracy`、`ConversationCompleteness`。
- 对话质量：`TurnRelevancy`、`KnowledgeRetention`、`Summarization`。
- 工具使用：`ToolUse`。
- 安全：`Bias`、`Toxicity`、`PIILeakage`。

这些指标对多轮 agents 尤其有用。`ConversationCompleteness` 能抓出那种只回最新一条消息、却悄悄丢掉早先请求的 agent；`KnowledgeRetention` 能抓出忘了用户三轮前说过什么的 agent。

**AutoEval** 提供更专门的信号：

- `Security` 标记恶意输出，比如试图注入指令或泄露系统 prompt。
- `Possible` 抓出过度谨慎、把有效任务误判为无法完成的 agents。
- `Humor` 对面向消费者的 agents 有意义，因为个性本身就是产品的一部分。

**自定义评估器**。当目录里没有合适的评估器时，可以自己写一个自定义 LLM-as-a-judge。

每个评估器的确切定义、评分刻度和输入要求，都在 [AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/prompt-templates-builtin.html)的 prompt 模板库里，包括它使用的 judge prompt、运行在 trace 还是 session 级，以及是否需要参考答案或预期轨迹。你可以调用 `ListEvaluators` API，在一次响应里拿到完整目录和自己账号下的自定义评估器。

### 多维度评估器

到目前为止，每个评估器对每条 trace 或每个 session 只返回一个分数。衡量单一行为时这没问题，但结果映射的第 2 步很少能给每个评估器只配一种行为。一条支持回复既要解决问题、又要遵守退款和数据政策、还得保持专业。让一个 judge 同时权衡三者，只会返回一个数字，你根本看不出是哪条标准在起作用。

多维度评估器是一种自定义 LLM-as-a-judge，用一组维度取代单一刻度。每个维度都有自己的名称、指令，以及数值或分类刻度。judge 只读一次 trace，就在同一次调用里给所有维度打分。AgentCore 对每个维度各返回一个结果。

![多维度评估器示意图：一次 judge 调用只读一遍 trace，为每个评分维度各返回一个结果](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/10/ML-21893-5.png)

图 5：多维度评估器用单次 judge 调用为多个维度打分，每个维度各返回一个结果，没有综合分

当成功标准可能各自独立失败时，就用多维度评估器，比如答案准确却不合规，或者问题解决了但语气很冲。它还要求每条标准都能依据同一份证据来评判，这样一次 judge 调用就能取代好几个几乎一样、反复读同一条 trace 的评估器。把标准分开打分后，你可以逐条设卡。一个改善了语气却让政策合规倒退的发布就该被拦下，而单一混合分数会把这一点掩盖掉。

如果某个现成的内置或第三方指标已经覆盖了某条标准，比如 `Builtin.Correctness` 或 `ThirdParty.DeepEval.PIILeakage`，就把标准留在单独的评估器里。当不同标准需要不同级别或不同 judge 模型时，也要分开——因为一个评估器里的所有维度共用同一个级别和模型。有些标准需要 ground truth（如 `{expected_response}` 或 `{assertions}`）时同样如此。把不依赖参考答案的标准单独放在自己的评估器里，它才能继续跑在实时流量上。

## 按 agent 类型给出的示例组合

下面每个组合都从两三个最贴合业务结果的评估器起步。当你发现第一组漏掉了某种失败模式时，再补上其余的。标有“需要 ground truth”的评估器只能在批量评估中运行，因为实时流量没有参考答案或预期路径。

|  | **客户支持** | **多步骤研究** | **领域内容（医疗、法律、金融）** |
| --- | --- | --- | --- |
| 业务结果 | 一次会话内解决问题，且无后续风险 | 通过既定工作流给出完整、来源充分的答案 | 领域内正确、无偏见、安全的答案 |
| 主要风险 | 请求被丢弃、不安全或不合规的回复 | 工具路径不对却答对了，或长会话中丢失上下文 | 一个错误答案。错误答案比没有答案更糟。 |
| 起步用 | `Builtin.GoalSuccessRate`（锚点）`ThirdParty.DeepEval.ConversationCompleteness` `ThirdParty.DeepEval.PIILeakage` | `Builtin.TrajectoryAnyOrderMatch`（需要 ground truth）`ThirdParty.DeepEval.GoalAccuracy` `ThirdParty.DeepEval.KnowledgeRetention` | `Builtin.Correctness`（需要 ground truth）`ThirdParty.DeepEval.PIILeakage` `ThirdParty.AutoEval.Security` |
| 按需添加 | `ThirdParty.DeepEval.Toxicity` `ThirdParty.AutoEval.Security`（敏感账户数据）`Builtin.Helpfulness` | `Builtin.SkillInstructionFollowing` `ThirdParty.AutoEval.Possible` | `ThirdParty.DeepEval.Bias` `Builtin.Helpfulness` |
| 派生评估器 | 可选 | 若推理必须留在自己的账户内，用于轨迹和 skill 指标 | 几乎总是需要，让每次 judge 调用都处于自己的数据治理之下 |

## 运行评估：三种模式

AgentCore 支持三种评估模式。

按需评估是最快的反馈闭环。开发或调试时，把 session 直接传给 `client.evaluate()`。系统里所有评估器（包括第三方）都能在这里用。

```
import boto3

client = boto3.client('bedrock-agentcore')

response = client.evaluate(
    evaluatorId="ThirdParty.DeepEval.TaskCompletion",
    evaluationInput={"sessionSpans": session_span_logs}
)

for result in response["evaluationResults"]:
    print(f"Value: {result.get('value')}")
    print(f"Explanation: {result.get('explanation', '')}")
```

在线评估挂到实时的 agent runtime 上，按设定的比例对真实流量采样。这是你的生产健康信号。内置与第三方评估器可以在同一份在线评估配置里自由混用。

批量评估针对一组固定的 session 运行既定的评估器组合：也就是发布前做回归测试的黄金数据集。用它来确认 prompt 改动或模型升级没有让你关心的任何一个维度掉质量。

三种模式用的是同一套评估器 ID。从开发期的按需测试切到生产期的在线评估，只是改配置，不用重写代码。

## 综合运用

越来越难的反倒是选哪些评估器。挑出最能说明你是否达成业务结果的两三种行为，先量它们；等发现当前组合漏掉了某类失败，再补一个评估器。

想看完整目录，调用 `ListEvaluators` API：它会在一次响应里返回内置、DeepEval、AutoEval 评估器，以及你账号下的所有自定义评估器。在挑任何一个之前，先回答两个问题：“对这个 agent 来说，成功长什么样？”以及“trace 里的哪种行为能说明它确实发生了？”
