# 代理评估手册：Amazon Bedrock AgentCore 评估上的内置、DeepEval 和 AutoEval

当您将代理部署到生产环境时，最困难的问题之一是它是否真正有效？酒吧不在于它是否运行。关键在于它是否能够大规模满足业务需求。许多团队会告诉你他们并不能真正看到这一点。他们抽查输出，观察延迟，并在可以获得时收集用户反馈。这些都无法告诉您代理是否完成了用户的任务、在长时间的会话中停留在主题上、泄露了个人身份信息 (PII)，或者悄悄地跳过了应该遵循的一半步骤。

![冰山图，将团队观察到的表面信号与决定水线以下成功的隐藏代理行为进行对比](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/10/ML-21893-1.png)

图 1：团队通常关注表面信号，但业务成果由水线以下的代理行为决定

代理评估解决了这个问题。这项工作之所以具有挑战性，是因为一项指标的高分可能会掩盖另一项指标的失败。支持代理可以解决每张票证，并且仍然在其回复中公开个人信息。在这种情况下，尽管代理的完成率很高，但它还是失败了。为了获得正确的评估，请以正确的详细程度衡量对每个代理而言重要的行为。

本文展示了如何在 Amazon Bedrock AgentCore 上执行此操作。我们将 AgentCore 内置评估器与直接来自 AgentCore 评估的 DeepEval 和 AutoEval 评估器一起使用。

## 从业务成果开始，而不是指标名称

最常见的错误是从指标列表开始，然后选择听起来正确的名称。 “乐于助人听起来不错，所以我们就利用它。”结果运行并产生数字，但它几乎没有提供有用的见解。该指标符合其标签，而不是成功对代理意味着什么。

相反，从三个步骤开始。

- **用业务术语定义成功。** 对于客户支持代理来说，这可能是首次联系解决方案。对于研究代理来说，它可能会产生一个完整的、来源良好的答案，完全基于检索到的文档。对于内容审核助理来说，这意味着标记所有应该标记的内容，并且仅标记应该标记的内容。
- **将结果分解为可观察的行为。** 实现首次联系解决方案的客户支持代理通常会完成用户既定的目标，在问题需要澄清时保持一致，将响应保持在合规范围内，并正确调用后端工具，例如工单创建或订单查找。
- **将每个行为映射到正确级别的评估器。** 跟踪级别指标涵盖每轮或每工具调用的行为。会话级指标涵盖的结果只有在您查看整个对话时才有意义。

![从业务成功到可观察行为再到评估者的三步流程，以客户支持映射示例进行说明](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/10/ML-21893-2.png)

图 2：将业务成果转化为可观察的行为，然后转化为跟踪或会话级别的特定评估器

这个三步过程是使评估变得有用的心智模型。这篇文章的其余部分是关于 AgentCore 为您提供执行它的内容。

## 评估器目录

AgentCore 拥有来自三个来源的广泛评估者目录：

- **内置评估器**由 AWS 编写和质量测试。您可以通过 ID（“Builtin.GoalSuccessRate”、“Builtin.Helpativity”等 13 个）来引用它们，该服务会处理其他所有事情。它们以可靠性为基准并涵盖常见尺寸，因此它们是直接的起点。
- **第三方托管评估器**来自 [DeepEval](https://deepeval.com/) 和 [AutoEval](https://www.braintrust.dev/docs/evaluate/autoevals)，这是两个已建立的开源评估库。当您在托管模式下使用它们时，AgentCore 托管代码，选择判断模型，并根据自己的能力运行推理，就像内置评估器一样。如果您的团队已在开发中使用这些库之一，则您可以在生产中运行相同的指标，而无需单独的评估服务。
- **自定义评估器** 以内置或第三方评估器为基础，因此您可以交换自己的模型并修改提示或评分标准。

![通过评分逻辑、判断模型和 AWS 质量比较 AgentCore 内置、第三方托管和自定义派生评估器层的表格测试](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/10/ML-21893-3.png)

图 3：三个评估器层以 AWS 质量保证为代价来增强对运行推理的模型和账户的控制

创建后，自定义派生评估器的使用方式与其他评估器完全相同。

## 评估者情况

AgentCore 附带了广泛的评估器目录，因此您很少从空白页开始。在编写自定义判断之前，请检查是否已经测量了您关心的行为。下图展示了整个景观。

![AgentCore 评估器的来源目录：内置 AWS 评估器和轨迹检查、DeepEval、AutoEval 和自定义LLM作为法官](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/10/ML-21893-4.png)

图 4：AgentCore 上跨内置、DeepEval、AutoEval 和自定义源的完整评估器环境

**内置 AWS 评估器**分为五组：

- **响应质量**涵盖答案是否准确、有根据和格式良好：“正确性”、“忠实性”、“有帮助性”、“响应相关性”、“简洁性”、“连贯性”、“遵循指令”和“拒绝”。
- **任务和目标完成**有“GoalSuccessRate”，它查看整个会话并询问用户的目标是否达到。
- **工具使用**具有“ToolSelectionAccuracy”和“ToolParameterAccuracy”，它们检查代理是否选择了正确的工具并向其传递了正确的参数。
- **技能**具有“SkillSelectionAccuracy”和“SkillInstructionFollowing”，对于加载技能的代理：是否调用了正确的技能，是否遵循了其步骤？
- **安全**有“有害性”和“刻板印象”。

接下来是三个真实轨迹检查：“TrajectoryExactOrderMatch”、“TrajectoryInOrderMatch”和“TrajectoryAnyOrderMatch”。他们将代理的实际刀具路径与您预期的路径进行比较。当代理如何到达那里与它产生的结果一样重要时，就去接触它们。

**DeepEval** 提供四组托管开源指标：

- 任务和目标完成情况：“TaskCompletion”、“GoalAccuracy”和“ConversationCompleteness”。
- 对话质量：“回合相关性”、“知识保留”和“摘要”。
- 工具使用：`ToolUse`。
- 安全性：“偏差”、“毒性”和“PIILeakage”。

这些指标对于多轮代理特别有用。 “ConversationCompleteness”捕获代理回复最新消息但悄悄丢弃较早的请求。 “KnowledgeRetention”捕获了一个忘记用户三回合前说过的话的代理。

**AutoEval** 提供更专业的信号：

-“安全”标记恶意输出，例如尝试注入指令或显示系统提示。
- “可能”捕获过度谨慎的代理，错误地声明有效任务不可能。
- “幽默”对于面向消费者的代理商来说很重要，因为个性是产品的一部分。

**自定义评估器**。当目录中没有适合的评估者时，您可以编写自定义的LLM作为法官。

每个评估者的确切定义、评分标准和输入要求均位于 [AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/prompt-templates-builtin.html) 中的提示模板库中。这包括它使用的判断提示、运行的跟踪或会话级别，以及是否需要参考答案或预期轨迹。您可以调用“ListEvaluators” API 在一个响应中获取完整目录和您自己的自定义评估器。

### 多维度评估器

到目前为止，每个评估者都会为每个跟踪或会话返回一个分数。当你衡量一种行为时，这是有效的。但结果映射的第 2 步很少为每个评估者提供一种行为。支持回复必须解决问题、遵循退款和数据政策并保持专业。一位法官权衡所有三者后，会返回一个数字，而你无法判断是哪个标准驱动了它。

多维度评估器是一种定制的LLM作为法官，具有一系列维度而不是一个尺度。每个维度都有自己的名称、说明以及数字或分类尺度。法官读取一次轨迹并在同一次呼叫中对每个维度进行评分。 AgentCore 对每个维度返回一个结果。

![多维度评估器图：一个判断调用读取一次跟踪，并为每个评分维度返回一个单独的结果](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/10/ML-21893-5.png)

图 5：多维度评估器根据单个判断调用对多个维度进行评分，并为每个维度返回一个结果，没有综合分数

当您的成功标准可能单独失败时，请使用多维度评估器，例如答案准确但不合规，或已解决但粗鲁。它还需要每个标准都可以根据相同的证据进行判断，以便一个判断呼叫可以取代几个几乎相同的评估者重新读取相同的痕迹。当您单独对标准进行评分时，您可以对每一项进行门控。改进语气但降低政策合规性的版本会失败，而单一的混合分数会掩盖这一点。

当已建立的内置或第三方指标已经涵盖标准时，将标准保留在单独的评估器中，例如“Builtin.Correctness”或“ThirdParty.DeepEval.PIILeakage”。当需要不同的级别或判断模型时，也要将它们分开，因为一个评估器中的维度共享单个级别和模型。当某些标准需要基本事实（例如“{expected_response}”或“{assertions}”）时，请执行相同的操作。在自己的评估器中保留无参考标准意味着它仍然可以在实时流量上运行。

## 运行评估：三种模式

AgentCore支持三种评估模式。

按需评估是最快的反馈循环。在开发或调试期间将会话直接传递给“client.evaluate()”。系统中的每个评估员（包括第三方）都在这里工作。
```
import boto3

client = boto3.client('bedrock-agentcore')

response = client.evaluate(
    evaluatorId="ThirdParty.DeepEval.TaskCompletion",
    evaluationInput={"sessionSpans": session_span_logs}
)

for result in response["evaluationResults"]:
    print(f"Value: {result.get('value')}")
    print(f"Explanation: {result.get('explanation', '')}")
```
在线评估附加到您的实时代理运行时，并以配置的速率对实际流量进行采样。这是您的生产健康信号。内置和第三方评估器可以在单个在线评估配置中自由混合。

批量评估针对一组固定的会话运行定义的评估器堆栈：发布前用于回归测试的黄金数据集。用它来确认即时更改或模型升级是否在您关心的每个维度上保持了质量。

所有三种模式都使用相同的评估者 ID。从按需开发测试切换到生产在线评估是配置更改，而不是代码重写。

## 把它放在一起

越来越困难的部分是选择评估者。选择最能表明您是否达到业务成果的两到三种行为，并首先衡量这些行为。当您发现当前设置遗漏的故障时，添加评估员。

要查看完整目录，请调用“ListEvaluators” API。它会在一次响应中返回内置、DeepEval 和 AutoEval 评估器以及您帐户中的任何自定义评估器。在您选择其中任何一个之前，请回答两个问题：“该代理的成功是什么样的？”以及“跟踪中的哪些行为表明它发生了？”
