# 智能文档处理的自动化 schema 生成

在使用智能文档处理（intelligent document processing，IDP）技术从文档中提取信息之前，你需要为每种文档类别准备一个 schema，定义要提取哪些内容。但当你有数千份文档、且不知道存在哪些类别时，该如何创建 schema？大规模做这件事需要大量人工投入，使下游 IDP 项目难以证明值得投入。

在这篇博文中，我们将展示我们的多文档发现功能如何解决这一问题。它充当自动化预处理步骤：分析未知文档、按类型聚类，并生成可直接用于 [IDP Accelerator](https://aws.amazon.com/blogs/machine-learning/accelerate-intelligent-document-processing-with-generative-ai-on-aws/) 的 schema。你将了解这项新能力如何使用视觉嵌入进行自动聚类，以及如何使用 agent 生成 schema。我们还将带你逐步在自己的文档集合上运行该方案。

## IDP Accelerator

[IDP Accelerator](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws) 是一个可扩展、serverless 的开源方案，用于自动化文档处理和信息提取。要针对你的特定文档类型定制该方案，你需要一个[配置文件](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/blob/main/docs/configuration.md)，在其中指定类别和字段。有关最小配置示例，请参阅 IDP Accelerator 的 [GitHub 仓库](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/blob/main/docs/configuration.md#minimal-configuration-example)。

如果不了解自己的文档类型，创建这个 schema 会很困难。IDP Accelerator 包含一个 [Discovery Module](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/blob/main/docs/discovery.md)，可以从单个示例文档出发引导生成类别配置。但你必须已经知道自己的文档类别，并能为每个类别找到一份有代表性的示例文档。本文介绍的多文档发现功能消除了这一前提条件，加快你将 IDP Accelerator 应用于未标注文档集合的进程。

发现任务首先使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上提供的嵌入模型，将 [Amazon S3](https://aws.amazon.com/s3/) 中的每份文档转换为向量嵌入，然后将相似文档分组为簇。一个用 [Strands Agents](https://strandsagents.com/) 和 Amazon Bedrock LLM 构建的 agent 会分析每个簇，识别文档类型并生成 schema。最后，一个反思步骤会一并审查所有 schema，在你的最终审核之前发现重叠和不一致之处。

## 技术细节

我们将逐步讲解流程中的每一步，重点说明关键决策和实现细节。

### 嵌入生成

该工作流为每份文档生成一个嵌入，将视觉特征转换为数值表示。对于多页文档，只使用第一页。目前，该工作流使用视觉嵌入而非基于 OCR 的文本，因为视觉嵌入能够捕捉区分文档类型的布局、格式和结构线索，即使文本内容相似也是如此。该方案通过 Amazon Bedrock 使用 [Cohere Embed v4](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-embed-v4.html) 作为发现任务的默认嵌入模型。嵌入步骤会自动处理常见的痛点和障碍，例如图像压缩、重试逻辑和速率限制。

### 文档聚类

多文档发现功能使用 [silhouette score](https://en.wikipedia.org/wiki/Silhouette_(clustering))（轮廓系数）来判定你的集合中有多少种文档类型。在此场景下，轮廓系数衡量各簇之间的分离程度以及每个簇内文档的紧密程度。通过 k-means 聚类，agent 默认测试 2 到 20 的 k 值，并选择轮廓系数最高的分组。这里 k 代表集合中不同文档类型的数量。为形成有意义的簇，每个簇必须至少包含两份文档。必要时，k 的上限会降到 20 以下以满足这一约束。

### 嵌入与聚类的基准测试

为验证嵌入与聚类方法，我们使用 Cohere Embed v4，在 IDP Accelerator CloudFormation 栈部署的测试集 bucket 中可用的 [OCR 基准数据集](https://huggingface.co/datasets/getomni-ai/ocr-benchmark)子集上进行了实验。要找到你的 bucket 名称，请进入 CloudFormation 控制台，选择你的 IDP Accelerator 栈，打开 Outputs 标签页，查找键 `S3TestSetBucketName`。

该数据集由单页文档类型组成。部署的子集包含 9 种文档类型的 293 份文档：银行支票、商业租赁协议、信用卡账单、送货单、设备检查、词汇表、请愿表、房地产和排班表。

为评估 k-means 聚类能否使用 Cohere 嵌入模型正确识别这些分组，我们测试了将轮廓系数作为选择最优 k 值的指标。我们运行了流水线的头两个阶段（嵌入和聚类），并分析了 k 值在 2 到 20 之间的轮廓系数。下图展示了这些 k 值对应的轮廓系数分布。最高轮廓系数出现在 k=9 处，与数据集中文档类型的真实数量一致。

![折线图：展示轮廓系数与簇数量（k = 2–20）的关系，在 k = 9 处达到峰值约 0.43，并以红色竖直虚线标出。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/01/ml-20447-3.png)

TSNE 图（t-distributed Stochastic Neighbor Embedding 图，一种可视化技术，可在保留数据点之间关系的同时将高维数据降维到二维空间）展示了这些嵌入在二维空间中的可视化结果，图例中显示了簇分类。

![t-SNE 散点图：展示文档嵌入形成 9 种彼此分明、分离良好的文档类型簇，验证了嵌入质量对文档分类的有效性。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/01/ml-20447-4.png)

该聚类达到了完美的 Adjusted Rand Index（ARI）和 Normalized Mutual Information（NMI），均为 1.0。ARI 衡量聚类与真实分组的吻合程度，NMI 则量化预测簇与实际簇之间共享的信息量。每个簇都以 100% 的纯度一对一映射到真实的文档类别。这些结果表明，高质量的多模态嵌入能够实现完全无监督的文档分类。这些嵌入在没有标注训练数据的情况下，也能准确区分银行支票、房地产表格和信用卡账单等多种文档类型。

**注意：**在此基准数据集上的表现并不能保证在你的特定文档数据上获得类似结果，因为数据集的特征会直接影响结果质量。

### Agentic schema 生成

识别出各簇之后，流水线进入 agentic 阶段。对每个簇，都会调用一个 [Strands Agent](https://strandsagents.com/latest/) 来确定文档类型并生成 schema。我们选择 Strands Agents 是因为它的模型驱动方法。这使模型能够灵活地自主推理每个 schema。在生成 schema 之前，agent 需要有策略地查看簇内不同位置的文档，以捕捉完整的变化范围。例如，它会检查靠近中心的一份文档、边缘的一份文档，以及处于中间距离的一份文档。这里采用确定性的固定采样方式并不可行，因为聚类质量在很大程度上取决于你的具体文档。为此，agent 配备了两个专门工具：

- Cluster Analysis Tool – 检索按与簇质心距离排序的文档 ID，使 agent 能够跨簇内变化范围进行有策略的采样。
- Document Viewer Tool – 获取并压缩文档图像以供视觉检查，自动处理模型上下文窗口的大小限制。

agent 的 system prompt 编码了关于 JSON Schema 约定和 [IDP Accelerator 配置](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/tree/main/config_library)要求的领域专业知识。它指示 agent：

- 有策略地对文档采样，如果确信覆盖范围足够则提前停止。
- 生成带有恰当元数据、类型定义和描述的 JSON Schema。
- 包含 IDP Accelerator 专属注解，例如 `x-aws-idp-document-type` 和 `x-aws-idp-evaluation-method`。`x-aws-idp-evaluation-method`is 由基于 [Stickler](https://github.com/awslabs/stickler) 的评估扩展使用。
- 为地址、明细项和税务信息等常见结构创建可复用的 `$defs`。
- 根据字段类型应用恰当的评估方法：字符串用 `EXACT`，数字用 `NUMERIC_EXACT`，复杂或嵌套对象用 `LLM`。

这些工具、prompt 和模型使 agent 具备推理自身采样策略的能力。这些 agent 并行运行，因此你无需等待每个簇完成后才开始下一个簇*.*

### Schema 分析

在各 agent 独立生成 schema 之后，schema 分析步骤会从整体上评估输出之间的差异。它判断所发现的文档分组是彼此分离还是相互重叠，以及生成的 schema 是否完整、一致。它会查找跨文档类型的冗余或重复。基于这些发现，它给出具体建议，例如合并簇或细化字段定义。它会生成一份摘要报告，其中包含对你的类别的可读概览。这份质量报告可在 IDP Accelerator 的 Discovery Job 详情中查看。

## 在你的文档上运行任务

要在自己的文档上运行多文档发现工作流，请在 IDP Accelerator Console 中按照以下步骤操作。

**步骤 1：创建新配置**

首先在 IDP Accelerator Console 中创建一个全新的配置：

- 导航到 **Configuration** 部分，选择 **View/Edit Configuration。**
- 选择 **Document Schema** > **Wipe All**，创建一个新的空配置。
- 选择 **Save as Version**，提供一个描述性的 **Version Name**，然后选择 **Save as Version。**

![AWS IDP Document Processing Configuration 控制台截图，显示 Document Schema 标签页中有一个“Save as New Version”模态对话框，其中输入了版本名“multi-doc-discovery-config”。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/01/ml-20447-5.png)

**步骤 2：运行多文档发现**

配置就绪后，启动发现过程：

- 导航到 **Discovery** 部分，选择 **Multiple Documents option。**
- 选择你刚刚创建的配置版本。
- 配置文档来源：  选择 **S3 Path** 或 Zip Upload。选择源 bucket。指定文档所在的 S3 前缀。

**注意： **要使用 Source Bucket 选项，你的文档必须添加到 IDP Accelerator 现有的某个 bucket（Discovery Bucket、Test Bucket 或 Input Bucket）中。

- 选择 **Start Discovery** 以触发状态机。

## 获得最佳效果的最佳实践

在大规模运行多文档发现任务之前，有几项最佳实践值得牢记。由于该工作流目前只处理每个 PDF 的第一页，请确保输入文件是单一文档文件。目前尚不支持多文档合包。获得初步结果后，请全面审阅质量报告摘要，以便在最终确定 schema 之前发现簇重叠或文档分布不均等问题。

## 后续步骤

接下来怎么做取决于工作流在文档中发现了什么：

- 如果 schema 看起来干净且质量报告显示重叠较少：你可以在文档上大规模运行 IDP。这些 schema 会自动添加到 IDP Accelerator 配置的 classes 字段中。
- 如果质量报告标记出重叠的簇，请审阅建议并用其优化生成的 schema。这可能包括将相似 schema 合并为一个类别，或调整字段定义以减少重叠。
- 如果各簇的 schema 质量不一致：检查文档集合中文档类型的分布是否严重不均。在更均衡的子集上运行发现任务，有助于 agent 生成更可靠的簇和 schema。

## 结语

在这篇博文中，我们展示了多文档发现功能如何解决这样一个难题：处理文档前需要 schema，而构建 schema 又需要先处理文档。该方案结合了视觉嵌入、自动聚类，以及使用多模态 LLM 的 agentic schema 生成。它将不透明的未知文档集合转换为结构化、可供审核的文档类别和 schema。你已经看到工作流如何处理嵌入生成、簇调优，以及并行的分类与 schema 生成。你还看到了反思步骤如何为 agent 生成的输出提供透明分析，以供人工审核。
