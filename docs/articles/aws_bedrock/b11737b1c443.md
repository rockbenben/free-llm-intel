# AgentOps：借助 Amazon Bedrock AgentCore 让 agentic AI 规模化可运营

构建 [agentic AI](https://aws.amazon.com/what-is/agentic-ai/) 方案时，你会面对独特的运维挑战。Agent 会做出不可预测的决策，成本会意外失控，调试非确定性的失败看起来无从下手。Agentic AI 应用并不只是执行预定好的工作流，它们会推理、会适应，并做出自主决策，因此 DevOps 实践也需要相应调整。这正是 AgentOps 的用武之地——它是用于在生产中部署、管理并持续改进 AI agent 的运维纪律。

我们博客系列的[第一部分](https://aws.amazon.com/blogs/machine-learning/operationalize-generative-ai-workloads-and-scale-to-hundreds-of-use-cases-with-amazon-bedrock-part-1-genaiops/)介绍了如何让生成式 AI 工作负载变得可运营。在本文中，我们展示如何通过用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 实施 AgentOps，来加速 agentic AI 工作负载走向生产的路径、检查 agent 与工具的质量，并在组织中推动 agentic AI 的采用。我们围绕四大支柱讨论来自真实落地实践的最佳实践：治理与安全、构建与运维、评估，以及可观测性。我们还会展示 AWS 服务、人员与流程如何汇聚成一套你可以按自身组织调整的参考架构。

请注意，本文聚焦于运维而非 agent 设计。实现示例使用 Amazon Bedrock AgentCore 与配套的 AWS 服务，但所讨论的原则具有广泛适用性。这套参考架构只是一个起点：如何调整它取决于你组织自身的需求。

### AgentOps：四大支柱

本文涵盖 AgentOps 各支柱的最佳实践与真实世界经验：

- **治理与安全：**使用多账户策略、确定性控制、推理控制与 human-in-the-loop，以验证 agent 在授权边界内运行，且每个操作都可追溯。
- **构建与运维：**把每个 agent、工具与记忆配置都视为带自身 CI/CD pipeline 的、可版本化的可部署制品。
- **评估：**在工具、对话轮次、会话结果与系统四个层级上，于开发与生产环境中进行评估。
- **可观测性与监控：**在四个遥测层上做埋点，以便追踪每一次 agent 决策、监控质量下滑，并跟踪每次交互的成本。

[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 提供的组件可以单独使用，也可以组合使用，来实现这些支柱。它是 AWS 的 Agentic AI 平台，用于安全地大规模构建、部署与运营高效的 agent。AgentCore 可与任何开源框架和任何大语言模型（LLM）配合使用，你无需管理基础设施，就能从本地开发过渡到生产。

### AWS 上的 AgentOps 生命周期

与其他软件解决方案一样，agent 也遵循从想法到生产的开发生命周期，而这一进程从未真正结束。agent 在每个阶段都需要持续的运维关注与改进。下面我们梳理了 agentic AI 如何影响 DevOps pipeline 的各个阶段：规划（Plan）、开发（Develop）、构建（Build）、测试（Test）、部署与发布（Deploy & Release）、维护与监控（Maintain and Monitor）。

| **DevOps 阶段** | **AgentOps 关注点** |
| --- | --- |
| **Plan** | 评估 AI 适用性、风险与伦理。取得法务/合规批准，确立性能指标，准备数据。定义人工监督点、工具权限、agent 信任模型、跨 agent 认证与初始 agent 设计 |
| **Develop** | 实验与模型选择、评估、检索增强生成（RAG）/prompt、分块策略、guardrails。编排、记忆、状态、工具注册表/发现、Model Context Protocol（MCP）工具、Agent-to-Agent（A2A）、agent 身份、agent 评估、认证模式 |
| **Build** | 单元/集成/安全/agent 测试，部署到预生产。工作流测试、工具链校验。基于角色的访问控制（RBAC）校验 |
| **Test & release** | 运行质量、性能、端到端与安全测试。在发布说明中补充 AI 相关考量。执行路径评估端到端目标、循环次数上限、human-in-the-loop（HITL）测试、未授权的 agent 操作。 |
| **Deploy** | 把解决方案部署到生产。部署 MCP 服务器与工具。并发、最小权限、agent 端点的网络配置。配置回滚策略、金丝雀部署或流量管理 |
| **Maintain and monitor** | 跟踪质量、guardrails、延迟、吞吐、负责任 AI、错误，跟踪用量与成本。用户反馈。traces/spans 监控、漂移、告警、操作审计轨迹、异常检测、agent 端到端调用的 guardrails |

无论你处在生命周期的哪个位置，这些支柱都适用。从负责任 AI 的角度看，你需要在全程做系统化的风险管理。《[The Agentic AI Security Scoping Matrix: A framework for securing autonomous AI systems](https://aws.amazon.com/blogs/security/the-agentic-ai-security-scoping-matrix-a-framework-for-securing-autonomous-ai-systems/)》可以帮助识别与管理风险。

### 解决方案概览

下面的参考架构展示了各支柱、生命周期、人员、流程与 AWS 服务如何连接在一起。我们逐步来看。

**规划与设置**

- **产品负责人**在集中式目录中登记该用例。法务与合规团队评估风险并提供指导。
- 用例获批后，**产品负责人与领域专家**及技术团队一起确定范围、成功指标，以及用于评估的事实基准测试 prompt。
- **平台工程师**用 IaC 部署环境，访问控制与安全团队商定，并打标签以支持治理与成本跟踪。

**开发**

- **开发者与数据科学家**创建带种子代码的 agent、应用与工具仓库并开始构建。他们可以使用共享 AgentCore Gateway 背后已批准的工具，以及 AWS Registry 背后的 agent。新的工具或 MCP 服务器请求需经产品负责人、平台团队与法务批准。
- **数据工程师**为开发与测试创建数据集与评估集。
- **开发者**运行手动与自动化评估，包括工具选择准确率、多步推理验证、对话连贯性与记忆持久性。领域专家评审结果并给出反馈。
- 实验在开发期间于本地跟踪，随后同步到共享账户，以便集中跟踪与跨团队对比。
- **开发者**合并到 main，触发部署 pipeline。

**构建与部署 pipeline**

- CI/CD pipeline 创建发布分支，把资源部署到预生产（包括通过 ECR 把 agent 部署到 AgentCore Runtime），并触发评估 pipeline。对于 RAG 实现，摄取 pipeline 部署到数据治理账户。
- 在预生产中运行集成、性能、UAT、回归与生成式 AI 评估测试，包括认证流程、用户上下文传播，以及工具访问的授权校验。
- **QA 工程师**与**领域专家**对照既定指标进行验证，并批准提升到生产。

**生产部署与运维**

- 解决方案部署到生产。生产遥测、用户反馈与性能指标回流到规划环节，用于持续改进。
- Agent 注册到 Agent Discovery API，使其可被发现，以便复用与 agent 间协作。
- **最终用户**与应用程序交互并提供反馈。AgentCore Observability 看板跟踪决策轨迹、工具调用模式、延迟、错误、记忆使用量与每次交互的成本。

### 支柱 1：治理与安全

在 agentic 系统中，单个用户请求可能跨越层级链条，也可能触发多个 agent 代表用户协作行动的 swarm（群体）。用户与 agent 之间的每一次交互都需要被严格控制。当 Agent A 调用 Agent B 时，究竟哪个 agent 被授权执行哪些操作可能存在歧义。如果触发 agent 的用户权限有限，agent 必须继承这些限制。调用链越深，这种歧义只会越叠加。你需要在以下方面实施严格治理：谁能访问这些 agent、agent 能访问哪些数据、工具与 API、谁能授予这些权限，以及问题出现时如何处置。

下图展示了 agent 处理一次请求时，每一步需要做出的安全决策。用户的输入流经环境进入 agent，agent 再使用工具与记忆生成输出。应用要验证用户身份、用户是否被允许调用该 agent，以及 agent 能否以特定参数访问所请求的上下文、记忆与工具。它还会校验输入是否安全，以及 agent 是否被授权返回这些具体的输出。

![流程图展示 AI agent 系统中的安全与授权检查点，从用户输入经环境、agent、记忆、工具到输出的全过程。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/19/ml-19465-image-1.png)

要建立一套分层安全方案，让 agent 在明确定义的边界内运行同时保持可审计性，你应该考虑以下几个维度。

**多账户架构**

AgentOps 是 GenAIOps 的延伸，正如 MLOps 是 DevOps 的延伸。如果你读过[第 1 部分：GenAIOps](https://aws.amazon.com/blogs/machine-learning/operationalize-generative-ai-workloads-and-scale-to-hundreds-of-use-cases-with-amazon-bedrock-part-1-genaiops/)，那么同样的设计原则也适用于 AgentOps。你应该采用[多账户策略](https://docs.aws.amazon.com/whitepapers/latest/organizing-your-aws-environment/organizing-your-aws-environment.html)实现组织级隔离，并用[服务控制策略](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html)（SCP）在各账户之间设置安全护栏。

下面的参考图展示了多账户 AWS 架构：

- 一个共享服务账户，存放 [Amazon Elastic Container Registry（ECR）](https://aws.amazon.com/ecr/) 容器镜像、pipeline 制品、AWS Secrets Manager，以及集中式监控与认证服务。
- 数据账户，把生产者账户与数据治理账户分开，支持隔离与对知识库的安全访问，并符合合规要求。
- 应用账户，即按业务线或应用团队划分的 a. 专用开发（dev）、b. 预生产（pre-prod）与 c. 生产（prod）账户，并打标签以支持治理与成本跟踪。

账户与资源使用基础设施即代码（IaC）进行部署与管理。

![AWS 架构图展示一个业务线账户，其中包含 Amazon ECS、带多个 agent runtime 的 Bedrock AgentCore、MCP 服务器、GenAI Gateway 与应用数据存储。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/19/ml-19465-image-2.png)

**受控的模型访问**

使用 Amazon Bedrock 时，你可以通过 SCP 与 [IAM 基于身份的策略](https://docs.aws.amazon.com/bedrock/latest/userguide/security_iam_id-based-policy-examples.html#security_iam_id-based-policy-examples-deny-inference)控制应用能访问哪些模型。你的 agent 可以直接使用这些模型，也可以通过 [LiteLLM](https://www.litellm.ai/) 之类的生成式 AI 网关使用。借助网关，你可以集中访问控制、简化跨多个模型供应商的治理实现，同时提供统一的 API 接口，用于按用户或 agent 限流、token 预算、成本跟踪与预算执行、基于安全策略的模型路由，以及面向合规的集中审计轨迹。AWS 已发布关于如何部署生成式 AI 网关的指南。为简单起见，我们起初把网关放在共享服务中，但后来发现难以把成本归属到各个 agent，于是把它移到了应用账户。

**身份与访问控制**

你可以使用 [AWS Identity and Access Management（IAM）](https://aws.amazon.com/iam/)做细粒度访问控制。此外，借助 AgentCore Identity，你可以跨 agent 管理认证与授权，其细粒度访问控制与跨 agent 认证协议会在请求穿过系统时维持安全边界。更多信息请参考 [Amazon Bedrock AgentCore Identity: Securing agentic AI at scale](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-bedrock-agentcore-identity-securing-agentic-ai-at-scale/)。[AWS CloudTrail](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-user-guide.html) 可用于全面的审计日志记录与取证分析。

**数据治理**

数据流经多个触点：用户输入（文本、附件）、agent 指令、输出、被访问的数据源以及记忆操作，每一处都带来潜在的安全风险。配置 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/)，对照你的安全策略评估用户 prompt 与模型响应，并防范无意披露 PII 之类的威胁。有关实施 guardrails 并将其与生成式 AI 网关集成的详细设置说明，请参阅 [Safeguard generative AI applications with Amazon Bedrock Guardrails.](https://aws.amazon.com/blogs/machine-learning/safeguard-generative-ai-applications-with-amazon-bedrock-guardrails/)

除上述内容之外，请对评估数据集（含数百条示例）实施版本控制，并系统性跟踪 RAG 知识库中文档与生成嵌入的变化，以支撑评估与审计要求。

**记忆**

在 agentic 应用中，数据代表底层的事实、文档与结构化信息，agent 通过 RAG 之类的检索机制查询它们（知识库、数据库、API），并由传统访问控制来治理。而记忆则是 agent 的工作上下文（它记住的对话内容、用户偏好与交互模式）。记忆是动态的、对话式的，随每次交互而演化。

借助 [AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html)，你可以获得短期记忆与长期记忆，并配有内置与自定义的记忆抽取策略。你还可以覆盖抽取逻辑，或针对特殊需求实现自管理策略。命名空间（namespace）在创建时作为长期记忆策略配置的一部分被定义，用于按 actor、会话或策略组织记忆。它们提供的结构有助于个性化以及跨用户的共享学习。AgentCore Memory 在 actor 层级把数据限定到各个聚合体上。当 agent 需要学习跨用户的模式时，记忆可以在更上层的应用级进行聚合。在多账户部署模式中，每个账户（dev、pre-prod、prod）都有各自的 AgentCore Memory 资源，由团队随应用一起部署与管理。这种部署模式有助于安全隔离、独立扩缩容、对齐数据驻留要求，以及按应用分摊成本。

应用可以访问多个记忆资源。下图说明了这种做法：欺诈与理赔这两个应用，分别从各自专属的资源中获取风险信号与保单详情，并从共享记忆资源中获取用户详情。你可以[用 IAM 策略控制它们能访问哪些记忆资源与信息](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-organization.html)。

![AWS 架构图展示欺诈与理赔 agent 如何在 AgentCore Memory 资源中使用各自独立与共享的长期记忆存储，并通过 IAM 做访问控制。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/19/ml-19465-image-3.png)

**工具治理**

Agent 代表用户调用工具，但并非每个用户都应该以任意参数触发任意工具。你可以使用 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 治理工具，把 API、Lambda 函数与服务转换为兼容 MCP 的工具，通过单一、安全的端点访问。它与 AgentCore Identity 配合，同时管理入站认证（验证 agent 身份）与出站认证（通过 OAuth、token 刷新、凭据存储来连接工具），从而让 agent 不直接处理凭据。你定义 agent 可以访问哪些 runtime、工具与后端，并由 IAM/资源策略与工作负载身份来强制执行。Identity 划定边界，回答“你是谁”与“你可以访问哪些基础设施”。

AgentCore 中的 Policy 会拦截经 Gateway 路由的工具请求，在允许访问工具之前，先以 [Cedar](https://www.cedarpolicy.com/en)（AWS 开源的策略语言）表达的确定性策略来评估请求。它回答的是“你现在被允许做这件事吗”（例如，你能开一笔超过一百万的理赔吗？）。你可以在所有 agent 交互上获得可审计的强制执行，降低通过操纵 agent 绕过策略的风险。

治理边界就位之后，你还需要一致的机制，来跨环境构建、版本化并部署 agent、工具与记忆配置。

### 支柱 2：构建与运维

agent 依赖的基础设施、资源、工具与模型都可能独立变化。你需要运维纪律，避免其他团队更新自己负责的工具时影响你的 agent，或避免记忆配置错误无意中泄露用户上下文。把每个组件都当作带独立仓库的、可版本化的可部署制品：

- **基础设施仓库：**账户设置、agent 注册表、资源（向量存储、agent 与工具注册表等），以及可复用组件的种子代码。
- **Agent 仓库：**agentic 解决方案代码，包含工具、guardrails、策略、prompt 与评估框架的共享模块（取决于你的业务规模与需求，共享模块也可以放在单独的仓库中）。
- **工具仓库：**工具代码，工具带有自己的 CI/CD，通常部署在 MCP 服务器之后。
- **应用仓库：**使用该 agent 的业务应用；多个应用可以共享同一个 agent。

有了这种分离，你就能拥有独立的版本化、测试与部署，同时保持清晰的归属与变更跟踪。下图说明了这种做法：

**面向 agentic 应用的环境与 CI/CD pipeline**

在 dev 账户中工作的开发者克隆带种子代码的仓库。在开发应用与 agent 的过程中，他们会修改：1. agent 代码（包括共享模块）与用于为 agent 预置 AgentCore 资源的 IaC 模板；2. 向量存储，使用 [Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/)、用于嵌入的 [Amazon S3 Vectors](https://aws.amazon.com/s3/features/vectors/) 或 [搭配 pgvector 的 Amazon Aurora](https://aws.amazon.com/about-aws/whats-new/2023/07/amazon-aurora-postgresql-pgvector-vector-storage-similarity-search/) 等服务；3. 数据摄取 pipeline；4. 连接该 agent 的应用代码；5. 自动化评估 pipeline 的变更。合并这些变更会触发 CI/CD pipeline。该 pipeline 把 IaC 模板部署到 pre-prod 账户，并把应用与 agent 代码打包成容器镜像，推送到共享服务账户或 pipeline 账户中的 [Amazon Elastic Container Registry（ECR）](https://aws.amazon.com/ecr/)。

在 pre-prod 中，自动化测试覆盖七个维度：集成、性能、UAT、回归、安全、agentic AI 与负责任 AI。Agentic AI 评估包括认证流程、用户上下文传播、工具访问的授权校验，以及 agent 特有的质量指标。Agentic AI 评估是最复杂的一类，横跨多个维度。例如，要验证用户身份与权限在多 agent 链条中正确传播，可能需要搭建自定义测试装置，模拟请求流过多个 agent，以验证身份与权限在每一步都正确传播。

**Agent 生命周期**

你在 agent 仓库中创建 agent。你把 agent 实现容器化，把容器镜像存放在 ECR 中，再部署到 AgentCore Runtime，并连接到 AgentCore Identity、AgentCore Memory 资源，以及账户级与共享的 AgentCore Gateway。当你准备合并变更时，CI/CD pipeline 会把 agent 打包成容器镜像、推送到 ECR，并部署到 pre-prod 中的 AgentCore Runtime。

该 pipeline 还会把 agent 的元数据以结构化记录的形式注册或更新到 [AgentCore 中的 AWS Agent Registry](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry.html)。借助 AWS Agent Registry，你有了一个集中的位置，可以在整个组织中发现问题、共享与复用 agent、MCP 服务器、工具与 agent skill。它支持从 MCP 与 A2A 端点自动摄取元数据，并通过审批工作流（draft → pending → approved）跟踪记录，审批通过后才在全组织范围内可被发现。你可以直接调用 agent，也可以通过 A2A 调用，或作为 MCP 服务器背后的目标来调用。在 pre-prod 中，它会在提升到生产之前运行自动化测试。基础设施仓库中的 IaC 模板定义了 Runtime、Memory 资源与 IAM 角色，确保各环境基础设施一致。

每个 AgentCore Runtime 都会[自动维护不可变的版本](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agent-runtime-versioning.html)。你可以创建指向特定版本的端点别名（例如 DEV、PREPROD、PROD），从而在部署工作流中实现独立提升、即时回滚与版本管理。

为每个 agent 打上负责人、成本中心与用例 ID 标签，并使用 AWS CloudTrail 记录审计轨迹。

**工具生命周期**

Agent 可以直接调用工具（针对内置能力），也可以经由同账户内的 AgentCore Gateway 端点调用，或经由共享服务账户中的共享 AgentCore Gateway 端点调用——该端点指向组织范围内已批准的工具。每个通过 AgentCore Gateway 暴露的工具都有自己的生命周期与 CI/CD pipeline，以部署到 pre-prod。

要把工具注册到 AgentCore Gateway，需在工具仓库中定义一个 manifest，指明该工具所属的 Gateway（共享或应用专属）、认证方式、请求的前缀与合规元数据。合并时，CI/CD pipeline 从环境相关配置注入端点、校验 manifest 与工具前缀，并把该工具注册为目标。为此，它会调用 [CreateGatewayTarget](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_CreateGatewayTarget.html) 与 [SynchronizeGatewayTargets](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_SynchronizeGatewayTargets.html)，使用基础设施仓库中的模板。这样一来，你就能实现一致的工具命名，并用 IAM 策略限制对 Gateway 的直接访问——只有 Gateway 本身可以访问。应用团队控制注册什么，平台团队控制在哪里注册、如何注册。

**记忆**

像对待其他可部署制品一样对待记忆配置：纳入版本控制、经过测试，并通过 CI/CD pipeline 提升。对记忆资源、TTL 配置、抽取策略与命名空间结构实施版本控制，并通过 CI/CD pipeline 部署，从而在各环境间获得一致行为，无需手动配置，也不会出现漂移。在提升到生产之前，用自动化测试验证记忆持久性、LTM 抽取质量、命名空间隔离与跨会话检索。

想了解这些构建与运维模式在企业规模下如何运作，请看 [Allianz 如何用 Amazon Bedrock AgentCore 设计企业级 AIOps。](https://www.youtube.com/watch?v=GYNeA7NZE3w)

可靠的 pipeline 把 agent 送进生产。结构化、多层次的评估则捕捉任何问题。

### 支柱 3：评估

agent 的失败方式往往并不显眼。一次错误的工具选择、一处被漏掉的上下文，或一次幻觉响应，都可能难以察觉。跨多个层级（工具、对话轮次、会话结果与系统）的结构化评估，有助于阻止这些失败进入生产。评估生命周期的步骤如下：

- 构建 agent，
- 找到、创建、更新数据集，通常通过捕获 agent 执行过程中的 trace，或使用领域专家提供的输入
- 选择要跟踪的评估器与指标
- 选择用于评判 agent 输出的模型
- 构建/配置为这些评估提供服务的基础设施
- 记录结果、保存到 Amazon S3、综合提炼洞见并做出调整
- 在生产中监控，设置 Amazon CloudWatch 告警以捕捉漂移，并进行人工复核

如果你读过[第 1 部分：GenAIOps](https://aws.amazon.com/blogs/machine-learning/operationalize-generative-ai-workloads-and-scale-to-hundreds-of-use-cases-with-amazon-bedrock-part-1-genaiops/)，你的评估基础依然适用，但 agentic 应用带来了额外要求：你仍然需要评估 LLM，但现在还要评估一条在整段对话中不断叠加的决策链、工具调用链与记忆检索链。

在 agentic 工作流中，评估在每个 agent 上分四个不同层级进行：

#### 1. 工具层级（span 级）

首先评估工具本身。对于 API 这类**确定性工具**，可以包含验证预期行为的单元测试，以及延迟、超时等性能指标。对于 RAG 这类**由 LLM 支撑的工具**，使用 human-in-the-loop 或 LLM-as-a-Judge 评估模型性能指标，示例指标包括正确性、有用性、相关性、有害性与风格/语气。对于**从知识库检索的数据**，评估检索质量、分块相关性与新鲜度。查看如何构建[坚实的数据基础](https://d1.awsstatic.com/psc-digital/2024/gc-600/10-tips-genai/10-tips-for-building-a-data-foundation-for-genai.pdf)才能取得成功。**对于多模态工具**（音频到音频、图像生成、视频创作），评估模态特有的质量指标（图像保真度、音频清晰度、视频连贯性）、跨模态一致性（生成内容是否与文本指令一致？）、安全与内容策略遵从度，以及生成延迟。

其次评估 agent 对工具的使用。验证 agent 是否正确地推理与规划、是否为任务选择了合适的工具、是否从用户查询中准确抽取了相关参数。关键指标包括工具选择准确率、参数抽取准确率，以及工具响应延迟与错误率。

#### 2. 对话轮次层级（trace 级）

在这一层级，你要评估单轮对话（一对输入-输出），以识别具体有问题的响应与质量问题。一些示例指标包括：正确性（信息在事实上是否准确）、有用性（这条具体响应有多大用处？）、忠实性（响应是否基于所提供的上下文？）、响应相关性（是否针对了用户的查询？）、简洁性、连贯性、指令遵循、拒答、有害性、刻板印象。多 agent 系统中还有更多可评估的指标，示例包括：agent 编排准确率（编排器能否把请求正确路由到合适的 agent，并协调它们之间的交接？）、agent 之间的信息交换质量、agent 在共享任务上的协作。

#### 3. 会话结果层级

这一层级考察 agent 是否在整段对话中达成了用户的目标。单个响应正确并不保证整体结果成功。关键指标包括任务完成率、目标准确率、对话效率与记忆一致性。

#### 4. 系统级指标

在这一层级，你评估生产就绪度与运维性能方面的因素。一些示例指标包括端到端延迟、首 token 时间、吞吐、工具调用错误率、循环检测，以及每个已完成任务的成本。你也可能有反映自身用例或业务需求的自定义成功指标，例如领域特定要求、对监管规则的合规性，或对品牌规范的遵循。

### 按需评估与在线评估

除了这四个层级，agentic 评估还以两种模式运行，服务于不同需求：

**按需评估（on-demand evaluation）**针对特定的 span、trace 或会话运行，用于开发期，并作为每次发布前的质量门禁。你提供参考输入，与会话 span 一起作为金标准，用来比对结果。定向测试包括逐轮调试、组件校验与 CI/CD 集成。部署前测试包括稳定性验证、轮次级指标与组件监控。这种即时反馈驱动一个迭代循环，用来精炼模型、prompt、工具与逻辑。

**在线评估（online evaluation）**以可配置的采样率持续监控生产环境的实时流量，从低采样量到全流量覆盖。它在生产会话、A/B 测试以及全量发布期间，对对话质量、轮次级指标与组件监控进行采样。持续产出的结果会输入 Amazon CloudWatch 看板，用于持续监控。

在本地开发与开发账户中，你运行按需评估以实现快速迭代。在预生产中，按需评估变成一道 pipeline 门禁：评估不通过，构建就不会提升到生产。在生产中，在线评估接手，持续采样实时流量，并在质量下滑时告警。你应当在用户之前发现质量问题。当评估检测到质量下滑时，结果会直接进入你的人工复核队列，或通过 CI/CD pipeline 触发自动回滚。

| --- | --- | --- | --- |
| Development | 按需，手动与自动 | 工具、trace、span 与会话。ground truth 评估。 | 必须先通过才能进入预生产 |

在 AWS 中，借助 [Amazon Bedrock Evaluations](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html)，你可以获得 LLM-as-a-judge 能力，并可以使用一支人工团队来评估 Amazon Bedrock 模型与知识库的性能与效果。借助 [AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html)，你可以为 agent 做在线与按需评估；[Strands Evaluation](https://strandsagents.com/latest/documentation/docs/user-guide/evals-sdk/quickstart/) 提供评估工具的框架，而 [Amazon Augmented AI](https://docs.aws.amazon.com/augmented-ai/)（A2I）把人工复核引入循环。更多关于如何评估 agent 的信息，请参阅 [Generative AI Atlas: Evaluating Agentic Framework Use Cases](https://awslabs.github.io/generative-ai-atlas/topics/2_0_technical_foundations_and_patterns/2_6_model_evaluation_and_selection_criteria/2_6_4_domain_specific_evaluations/2_6_4_5_evaluating_agentic_workflow/2_6_4_5_evaluating_agentic_workflow.html)。

对于性能指标，你可以用 [Amazon CloudWatch](https://docs.aws.amazon.com/cloudwatch/) 提取日志与指标，并使用 [pytest](https://docs.pytest.org/en/stable/) 与 [JUnit](https://docs.junit.org/) 等开发者工具对 API 运行单元测试。

评估告诉你 agent 在发布那一刻是否可用；可观测性告诉你它是否持续可用，以及为什么失效。

### 支柱 4：可观测性与监控

可观测性是 AgentOps 循环闭合的地方。它产生的遥测回流到治理决策、为下一轮评估提供输入，并影响你在下一次迭代中如何构建与部署。对于生产中的 agent，你需要在四个不同层级上具备可见性：

- **Agent 与框架遥测**，用于审计你的 agent 决定并做了什么：推理步骤、模型调用、工具调用，以及由 Strands SDK 这类 agent 框架生成的响应。
- **服务遥测**，用于理解 agent 所依赖的 AgentCore 服务内部发生了什么，例如记忆读写、网关认证与路由操作、身份与策略评估，以及内置工具调用。这些操作发生在框架之外，对框架级埋点不可见。
- **基础设施遥测**，用于监控承载 agent 与工具的环境，例如 runtime 容器指标与 Lambda 执行数据。
- **应用遥测**，用于捕获业务所需的指标——这些指标分布在多个 agent 与应用的运行之中

以下是你应当采集的数据类型：

**执行追踪：**每一步、每次工具调用与每次 LLM 交互

- **结构化日志：**跨 agent 与 runtime 关联日志
- **指标与告警：**延迟、输入与输出 token 用量、首 token 时间（TTFT）与错误率、工具调用次数与模型调用次数。在用户受影响之前就设置告警。
- **记忆：**agent 记住了什么、为什么记住；在配置错误无意中泄露用户上下文之前就发现它。
- **负责任 AI：**毒性、偏见及类似指标、幻觉率与 PII 泄露。
- **成本跟踪：**每个会话、每个 agent 与每个任务的 token 花费；判断你的 agent 在大规模下是否经济可持续
- **以人为本的指标：**满意度、信任与再参与度；其他所有指标都在告诉你 agent 表现如何，而这一项告诉你它是否有意义。

请确认你的支持团队、利益相关方与领域专家能访问相关看板，以便基于这些指标采取行动，例如通过 [IAM 基于身份的策略](https://docs.aws.amazon.com/bedrock/latest/userguide/security_iam_id-based-policy-examples.html)。

可观测性与监控分为三层：埋点层（[OpenTelemetry SDK](https://opentelemetry.io/docs/languages/php/sdk/)，可直接内嵌，也可通过框架原生支持）、采集与处理层（[AWS Distro for OpenTelemetry Collector 即 ADOT](https://github.com/aws-observability/aws-otel-collector)），以及分析后端（例如 Amazon CloudWatch）。像 Strands SDK 这样的 agent 框架内置了 OpenTelemetry（OTEL）埋点。对于基于 Python 的 agent，你可以用 opentelemetry-instrument 命令引导自动埋点。遥测通过 [OpenTelemetry Protocol](https://opentelemetry.io/docs/specs/otel/protocol/)（OTLP）导出到 ADOT collector，由它负责采样、过滤、批处理与路由。开发时你可以直接导出到后端，但在生产环境中我们建议使用 Collector 作为中间层。

当你的架构跨多个运行在不同框架上的 agent 时，OpenTelemetry 的 W3C Trace Context 传播会把一个共享的 trace ID 传递到每个 agent 与服务，让你在一个视图中看到完整的执行路径。对于共享同一逻辑会话但分散在不同 trace 中的请求，你可以使用 OpenTelemetry Baggage 跨服务边界传播会话 ID。至于后端，我们见过两种做法：使用 AgentCore Observability 及其由 Amazon CloudWatch 驱动的看板，或通过 OpenTelemetry 使用第三方工具。

**做法 1：在 Amazon CloudWatch 中使用 AgentCore Observability**

借助 Amazon CloudWatch，你可以得到两个面向 agentic 工作负载的看板。

[CloudWatch 模型调用看板](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/model-invocations.html) 覆盖 Bedrock 模型指标，包括延迟、token 计数、限流与错误计数，并提供按时间模式、工具使用与知识库查询的额外筛选。

[Bedrock AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html) 看板为你提供 agent 工作流的综合视图（trace、成本、延迟、token 与自定义元数据），并配有 IAM 访问控制、PII 脱敏与用于排障的 trace 摘要。它由 CloudWatch Transaction Search 驱动，后者把 span 转换为语义约定格式，并作为结构化日志存储在 aws/spans 日志组中，使每个 span 都可搜索、可分析。CloudWatch Application Signals 把生成式 AI 应用遥测与底层基础设施指标关联起来，实现统一的端到端排障。

AgentCore Runtime 会自动配置所需的日志组、IAM 权限与 OTEL 环境变量，应用只需把 OpenTelemetry SDK 添加为依赖。AgentCore 还会为其托管资源（包括 Memory、Gateway、内置工具、Identity 与 Policy）向 CloudWatch 发送服务指标。例如，你可以实时看到记忆操作的运行情况，包括调用次数、延迟、系统错误、用户错误、限流，以及事件与记忆的记录数。在多账户部署中，你在监控账户中构建并管理集中式看板，重建各个账户中原生具备的视图。

#### **做法 2：通过 OpenTelemetry（OTEL）使用第三方可观测性**

由于 AgentCore Runtime 通过标准 OpenTelemetry 协议导出遥测，它可以与专精 agent 遥测的第三方可观测性方案集成，例如 [LangFuse](https://langfuse.com/)。这类工具有两种用法：

**自管理第三方部署：**把可观测性工具部署在共享的 AWS 账户或 VPC 中，通过安全的 TLS 端点暴露。其他账户中运行在 AgentCore Runtime 上的 agent，使用 OTLP over HTTPS 直接导出 OTEL trace 与指标。通过 Transit Gateway 连接各账户，并用凭据轮换、API key 与网络访问策略保障流量安全。数据治理、保留与隐私控制仍由你直接管理。

**第三方 SaaS：**agent 把 OTEL 数据发送到托管云端点（例如 LangFuse Cloud、Arize Cloud）。授权使用供应商的 API key，流量依工具而定，或走公共互联网，或走 VPC 端点。这带来快速上手与运维扩展能力，但遥测数据会离开你的 AWS 环境。

来自可观测性的遥测回流到 agent 设计、运维改进决策与评估优化中，从而闭合 AgentOps 循环。

## 结论

构建生产级 agentic AI 很难。agent 会做出自主决策、调用外部工具，并以难以预料、更难调试的方式协作。在本文中，我们分享了在四大支柱上于生产实践中被验证有效的做法：治理与安全、构建与运维、评估，以及可观测性。

我们鼓励你开始在项目中应用这些做法，并分享你的经验。从实施支柱 1（治理与安全）的多账户隔离开始，然后推进 agent 的 CI/CD，加入评估门禁，最后是可观测性。开始使用请参阅 [AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/)。
