# 用 AWS DevOps Agent 和 AgentCore Evaluations 监控生产环境中的 agent 生命周期

生产环境中的多 agent 系统出现问题时，传统监控往往看不见。例如，agent 无法调用其基础模型（FM）并返回空响应。原因可能是 agent 执行角色上缺少某项 AWS Identity and Access Management（IAM）权限，而这并不会抛出 500 错误。一个 prompt 范围界定不当的 supervisor agent 不会抬高错误率，而是开始把 20% 的请求路由到不该去的专家 agent，同时基础设施指标依然一片绿。

基础设施监控与 agent 有效性监控需要不同的方法。[Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 指标能说明系统是否执行正确，却说明不了 agent 是否帮用户达成了目标。一个 agent 可以成功调用 Amazon Bedrock、无错调用每一个工具并返回响应，同时完全误解用户的需求。基础设施问题往往表现为 agent 行为退化，而不是明确的错误。当权限被撤销或服务限流时，agent 可能经历的是静默的问题。例如，预订 agent 不再完成预订，但日志显示工具执行成功，因为问题发生在三层调用链深处，并未抛出异常。

在多 agent 系统中，这些问题会叠加放大：单个用户请求触发一个 supervisor agent，由它把任务路由给多个专家 agent，每个专家都有自己的工具和模型调用。通常没有固定的执行图可供埋点，失败可能发生在多个交接点，而它们在系统中的传播方式也不总是可预测的。

我们构建了一个生产级的机票预订系统，包含四个专家 agent，并把 [Amazon Bedrock AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 用于持续的 agent 质量评估、[AWS DevOps Agent](https://aws.amazon.com/devops/) 用于自主的基础设施事件调查。*Amazon Bedrock AgentCore* 是一个可以用任意框架或模型大规模构建、连接和优化 agent 的平台。*AgentCore Evaluations* 填补了质量监控的空白，持续对线上交互打分，以捕捉工具选择错误、任务失败，以及基础设施指标完全看不到的质量退化。*AWS DevOps Agent* 则解决第二个问题：自主跨服务边界追踪失败，关联 IAM 策略、调用日志和编排 trace，无需人工排查。这两层一起回答了 agent 是否工作正常，以及基础设施是否支撑得住。

## 关键技术

该系统使用了多项 AWS 服务：

- [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/) 提供对来自 Anthropic、Meta、Mistral、Amazon 等领先 AI 公司的基础模型的 API 访问。在我们构建于 AgentCore runtime 之上的机票预订系统中，Amazon Bedrock 负责语言理解。各 AWS 区域的模型可用性，请参阅 [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)中的「各 AWS 区域支持的模型」。
- [AgentCore runtime](https://aws.amazon.com/bedrock/agentcore/) 负责 agent 编排并管理交互生命周期，通过 OpenTelemetry 埋点内置了可观测性。
- 借助 [Fullstack AgentCore Solution Template（FAST）](https://github.com/awslabs/fullstack-solution-template-for-agentcore)，团队可以快速部署一个安全的 React 前端，并连接到 AgentCore 后端。
- [AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 是集成在 AgentCore runtime 中的质量评估框架。它使用 [LLM-as-a-Judge](https://arxiv.org/abs/2306.05685) 方法持续对 agent 交互打分，提供有用性、正确性、目标完成度等质量维度的指标。
- [AWS DevOps Agent](https://aws.amazon.com/devops-guru/) 是一个自主调查工具，相当于你基础设施的 on-call 工程师。事件发生时，它会自动分析 Amazon CloudWatch 日志、跨服务边界追踪失败，并给出根本原因分析与修复建议。
- [Strands Agents](https://strandsagents.com/) 是一个开源 SDK，用模型驱动的方式构建 AI agent，支持 Swarm、Graph 和 Agents-as-Tools 等多 agent 协作模式。
- [OpenTelemetry](https://opentelemetry.io/) 是一个开源可观测性框架，为采集 trace、指标和日志提供标准化的埋点。AgentCore runtime 使用 OpenTelemetry 把监控数据发送到 Amazon CloudWatch，让整个系统保持一致的可观测性。
- [Swarm 模式](https://strandsagents.com/docs/user-guide/concepts/multi-agent/swarm/) 是一种多 agent 编排方式：supervisor agent 根据当前任务把工作动态路由给专家 agent。与固定工作流不同，Swarm 支持随运行时决策而变化的适应性执行路径，这使它在复杂任务上很强大，但也难以监控。

## 双层监控：质量与基础设施

这套监控架构回答两个问题：agent 工作得好吗？基础设施健康吗？

**Amazon Bedrock AgentCore Evaluations：持续的质量监控**

AgentCore Evaluations 从有用性、正确性和目标完成度三方面为线上 agent 交互打分。系统按可配置的比例对生产请求采样，并在后台进行评估。每个分数都附带推理，依据对话上下文、所用工具和任务要求解释该分数为何如此。

当质量指标下滑时，它会对近期低分会话做模式分析，找出共同的失效模式。如果 agent 对某类请求总是选错工具，或以无用的形式提供正确信息，模式分析会把这一点揭示出来。随后它会生成具体建议：具体的 prompt 修改、工具选择的调整，或编排逻辑的改进。

**AWS DevOps Agent：自主的基础设施调查**

AWS DevOps Agent 通过指标、日志和错误模式监控系统健康。一旦出问题，agent 会自行展开调查。它会拉取相关的 Amazon CloudWatch 日志，构建受影响资源的拓扑图，跨服务（IAM、Amazon Bedrock、你的 agent runtime）关联错误，追踪失败路径，并给出具体的修复建议。除了发送带有 Amazon CloudWatch 链接的告警之外，它还会把调查做完：把空白响应关联到缺失的 IAM 权限，或把超时激增关联到某个特定区域的 Amazon Bedrock 限流。

**两层如何协同**

AgentCore Evaluations 用量化的质量指标取代直觉，让团队能够衡量变更带来的实际影响。AWS DevOps Agent 把过去需要人工「作战室」的大量调查工作自动化——在基础设施事件发生的那一刻自主调查。两者共同构成生产级多 agent 系统所需的持续反馈闭环：监控、分析、改进、部署。

## 机票预订系统：为什么难以监控

为了端到端演示这套架构，我们构建了一个机票预订系统，用于处理复杂、动态的查询：多城市预订、常旅客权益应用，以及公司差旅政策合规，而且全部要在单个对话轮次内完成。这个用例恰好需要那种让生产监控变难的多 agent 协同：并行操作、多个数据源、顺序依赖，以及错误会带来真实后果的严格正确性要求。

考虑这样一个请求：*「帮我订 3 月 15 日西雅图到波士顿，再订 3 月 18 日波士顿到迈阿密。第二段用我的同行人证书，并确保两个航班都符合我公司的差旅政策。我是金卡会员，把符合条件的升舱都用上。」*

要在单个对话轮次内处理它，就得同时搜索两条独立航线，并在航班搜索进行的同时从另一个数据源获取常旅客状态和证书。随后这些预订还必须按正确顺序串起来，因为在航班选定、舱位等级已知之前，同行人证书无法使用。把证书用在不符合条件的航班上会让用户沮丧；订下违反公司政策的航班则是在浪费钱。

我们用四个专家 agent、以 **Swarm 模式**构建了它（图 1）。Supervisor Agent 接收请求并作为入口，使用 think 工具规划子任务，把工作路由给其他 agent，而这些 agent 之间也可以互相交接任务。Flight Agent 搜索航线并处理多城市中转。User Agent 获取常旅客状态、证书和档案数据。Reservation Agent 创建、修改和取消预订，并在提交变更之前做校验。

在 Swarm 中，agent 共享工作记忆，并动态地互相交接工作。每个专家根据自己发现的情况决定下一步该由谁行动，而不是遵循预先确定的执行计划。supervisor 只是入口。请求一旦开始执行，控制权就交给最适合下一步的那个同伴，而不是回到中央路由器。如果航班搜索找不到直飞航线，Flight Agent 会自己执行中转搜索，一旦拿到可订的选项就交接给 Reservation Agent。如果用户的证书不适用，User Agent 会做调整并把任务传下去。这样无需预定义执行图就能处理不可预测的请求结构，但也意味着没有固定的调用图可供埋点。

失败可能发生在任何交接点；而且由于执行路径会随运行时决策变化，失败路径每次也都不同。质量失败和基础设施失败从外部看可能几乎一模一样，但需要的应对完全不同。从外部看，质量失败和基础设施失败看起来是一样的。AgentCore Evaluations 捕捉的是第一类：一切都在执行，但 agent 仍然没能帮到用户。AWS DevOps Agent 捕捉的是第二类：基础设施静默地坏掉，表现为行为退化。

## 双层监控架构

下图展示了这些组件如何连接。

![包含 React 前端、AgentCore runtime、Amazon CloudWatch 和 AWS DevOps Agent 的完整系统架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/31/ML-20434-2-1.jpg)

图 2：完整系统架构，展示 React 前端、AgentCore runtime、Amazon CloudWatch 和 AWS DevOps Agent

我们构建了一个托管在 [AWS Amplify](https://aws.amazon.com/amplify/) 上的 React 前端，它通过 Amazon Bedrock AgentCore Identity（Amazon Bedrock AgentCore 的一项能力）连接到 Amazon Bedrock AgentCore runtime，由四 agent 的 swarm 在那里处理用户请求。AWS Amplify 承载对话界面，[Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/) 负责会话存储，Amazon Bedrock AgentCore Identity 管理前端与 runtime 之间的身份验证。

监控数据只有一个源头：承载四 agent swarm 的 Amazon Bedrock AgentCore runtime。Amazon Bedrock AgentCore Observability（Amazon Bedrock AgentCore 的一项能力）直接对 runtime 埋点，以 OpenTelemetry 格式采集 trace 和指标并转发到 Amazon CloudWatch。Amazon Bedrock AgentCore Evaluations 则从同样的 runtime trace 中取材，为线上交互打分，评估结果同样流入 Amazon CloudWatch。这意味着运营指标、分布式 trace 和质量分数都汇聚到同一个地方。

第二个监控层连接的是同一个后端。事件发生时，团队成员通过签名 webhook 把它提交给 AWS DevOps Agent。agent 会拉取 Amazon CloudWatch 日志和指标，自主调查，并返回发现与修复步骤，无需任何人在不同工具之间来回切换。

### 第一层：Amazon Bedrock AgentCore Evaluations，agent 工作得好吗？

生产环境 agent 中那些静默的质量问题，会影响团队效率、用户信任和业务结果。AgentCore Evaluations 通过持续按结构化质量维度为线上交互打分，在这些失败刚出现的那一刻就将其捕捉到。

*视频 1：为会话、trace 和 span 提取评估指标；在仪表板上查看指标以了解 agent 表现；通过浏览会话 trace 与 span 执行按需评估；运行 AI 引擎以识别低分会话中的模式；上传 prompt 以获得 AI 生成的改进建议*

Amazon Bedrock AgentCore 提供 16 个内置评估器，按它们衡量什么、何时运行来组织。其中 13 个是 LLM-as-a-Judge 评估器，可为交互打分并给出详细解释，让团队能够核对判断、准确理解某次交互为何得到某个评分；另有三个确定性的 trajectory 匹配器。

| **Evaluator** | **Definition** | **Evaluation Level** |
| --- | --- | --- |
| Goal Success Rate | 通过端到端分析整段对话，评估 AI 助手是否在一个会话内成功完成了用户目标。 | 会话 |
| Coherence | 评估回答的逻辑一致性与衔接性，检查自我矛盾、逻辑空白和推理的合理性，但不评判事实准确性。 | Trace |
| Conciseness | 衡量助手沟通的效率，评估回答是否以最少的文字提供必要信息，且没有多余的铺陈。 | Trace |
| Correctness | 评估回答对给定任务的事实准确性，关注内容与解决方案是否准确，而不论风格或呈现形式。 | Trace |
| Faithfulness | 评估回答是否与对话历史保持一致，识别当前回答与同一对话中先前交互之间的冲突。 | Trace |
| Harmfulness | 检测回答中可能有害的内容，包括侮辱、仇恨言论、暴力、不当性内容和刻板印象。 | Trace |
| Helpfulness | 评估回答在多大程度上帮助用户推进其目标，完全从用户视角判断该回答是否让他们更接近目标。 | Trace |
| Instruction Following | 评估回答是否遵守用户输入中给出的明确指令，关注对具体指令的遵循情况，而不论回答的整体质量。 | Trace |
| Refusal | 检测助手拒绝处理或满足用户请求的情况，既识别直接拒绝，也识别对所求任务的间接回避。 | Trace |
| Response Relevance | 评估回答对特定问题或请求的切合程度，衡量回答相对于给定输入的聚焦度与相关性。 | Trace |
| Stereotyping | 检测回答中的偏见与刻板内容，识别针对特定人群的偏见性假设或泛化。 | Trace |
| Tool Parameter Accuracy | 评估助手在发起工具调用时是否正确使用上下文信息，验证工具参数是否准确取自对话上下文。 | Tool |
| Tool Selection Accuracy | 评估助手是否为给定情境选择了合适的工具，判断所选动作在对话的特定时点是否合理且最优。 | Tool |
| Trajectory Any Order Match | 验证预期工具是否出现，不限制顺序。 | 会话 |
| Trajectory Exact Order Match | 验证实际工具与预期工具完全按顺序匹配，且没有多余项。 | 会话 |
| Trajectory In Order Match | 验证预期工具是否按顺序出现在实际 trajectory 中，中间允许出现其他工具。 | 会话 |

#### 在线评估：持续的生产监控

在线评估通过持续采样可配置比例的 trace（0.01–100%）并异步地用你选定的评估器打分，来监控线上 agent 交互。这种异步、事件驱动的设计意味着评估与生产流量并行运行，不会增加面向用户的响应延迟。

Amazon Bedrock AgentCore 通过 OpenTelemetry 实时把评估指标发送到 Amazon CloudWatch。如果你已经在为可观测性采集 trace，在线评估会在你现有的运营指标旁边补充质量分数，无需改动代码或重新部署。你可以设置 Amazon CloudWatch 告警，在质量指标跌破你设定的阈值时立即触发，从而在静默的质量失败波及大量用户之前将其捕获。

在我们的机票预订系统的在线评估中，我们选用了三个内置的 Amazon Bedrock AgentCore 评估器，它们能全面覆盖 agent 质量：**Helpfulness、Correctness 和 Goal Success Rate**。选择这些指标，是因为它们代表了最终用户最在意的 agent 性能的三个基本维度。三项指标共同构成一张均衡的记分卡，既捕捉单次回答的质量，也捕捉整体交互的有效性。这让团队能获得可执行的洞察，看清 agent 在哪些方面表现出色、在哪些方面需要改进。

| **Metric** | **Why it matters** | **Example scenarios** |
| --- | --- | --- |
| **Helpfulness** | 捕捉正确性之外的用户满意度。识别技术上准确但没用的回答。帮助针对用户体验而非仅仅准确率做优化。检测 agent 提供过多或过少信息的情况。 | ✅ 高有用性：agent 给出清晰、可执行且带上下文的答案。❌ 低有用性：agent 对一个简单问题给出正确但过于技术化的回答。 |
| **Correctness** | 促成可靠性与可信度。捕捉幻觉和事实错误。对需要准确性的领域（金融、医疗健康、法律）至关重要。建立用户对 agent 的信心。 | ✅ 高正确性：agent 提供准确的数据和有效的推理。❌ 低正确性：agent 编造事实或给出错误计算。 |
| **Goal Success Rate** | 衡量实际交付的业务价值。捕捉多轮对话的有效性。识别 agent 卡住或未能完成任务的情况。与用户意图和业务目标对齐。 | ✅ 高目标成功率：用户想订机票，agent 完成了预订。❌ 低目标成功率：用户想订机票，agent 只提供了航班选项。 |

**设置在线评估配置的工作流：**

在线评估在生产环境中于后台不间断运行，按你配置的比例自动采样会话，并把结果写入 Amazon CloudWatch Logs，且不影响生产延迟。

**为什么不多用一些指标？**

- **避免指标过载**：指标太多会让人难以判断什么才重要。
- **降低评估成本**：每增加一个评估器，每次调用都会增加延迟和成本。
- **聚焦可执行的洞察**：这三项已覆盖用户最在意的维度。
- **支持快速迭代**：团队可以快速理解这些指标并采取行动。
- **额外的评估器**（Faithfulness、Instruction Following、Tool Use Quality）可用，但默认未启用。团队可以根据自身需要添加。

评估仪表板把原始的 Amazon CloudWatch 日志和 OpenTelemetry trace 转化为可执行的视图，呈现你的 agent 实际表现如何（图 3）。你不必再翻遍多个日志组里成千上万条 JSON 日志，去拼凑某个会话中到底发生了什么；仪表板以可视化界面呈现会话时间线、span 层级和评估分数。你可以按日期范围过滤会话，下钻到单条 trace，准确看到 agent 在哪里耗时或遇到错误。你还可以用内置或自定义评估器对特定会话执行按需评估。

#### 负责任 AI 防护措施

像 Correctness 和 Faithfulness 这样的评估器是在事后捕捉幻觉或不准确的输出，但由于在线评估是异步地对一部分会话运行，一个有问题的回答仍可能在被打分之前就送到用户手上。对于生产级 agent 系统，[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 提供了一个互补的内联层，在每次回答返回之前对其进行处理。关键能力包括：内容过滤以阻止有害或不当内容；拒绝主题检测，帮助阻止 agent 回应超出范围的查询（例如在航空场景中提供医疗或法律建议）；上下文接地检查，把缺乏检索源材料支撑的回答标记出来；以及敏感信息脱敏，遮蔽可能出现在工具输出中的 PII，例如信用卡号或护照信息。

对机票预订 agent 这样的系统来说，这些控制针对的是异步评估无法覆盖的实时风险：模型编造听起来合理、但并非任何工具返回的机票价格；agent 就自己无权决定的退款政策做出法律层面的承诺；或者某位客户档案中的 PII 泄漏到另一个会话。AgentCore Evaluations 是在一部分会话上*事后*打分，而 Guardrails 对每次回答*同步*生效，提供仅靠采样评估无法实现的实时安全网。两者共同构成完整的质量与安全态势：Guardrails 帮助从一开始就阻止有害输出到达用户，而 Evaluations 则识别那些随时间累积、更隐蔽的质量退化。

#### 按需评估：开发与 CI/CD 集成

在线评估提供的是持续监控，而按需评估帮助你调查特定的会话：一条用户投诉、一个边界情况，或一次被监控标记出来的会话。生产指标按采样率运行（通常是 10%），因此并非每个会话都会被打分。按需评估填补了这个空白，让你可以在任何时候用选定的评估器对特定会话做评估。除了三项默认指标（Helpfulness、Correctness、Goal Success Rate）之外，Amazon Bedrock AgentCore 还提供完整的内置评估器目录，可按需运行，如表 1 所示。

你还可以用自己定制的评分细则和指令，创建针对自身领域的自定义评估器。仪表板通过 evaluators API 呈现这些评估器，因此你可以浏览有哪些可用项，并针对单个会话运行组合评估，或跨多个会话批量运行（图 4）。这让按需评估成为根本原因分析的首选工具：当生产指标下滑时，你挑出有问题的会话，运行有针对性的评估器，准确理解到底哪里出了问题。

#### AI 分析引擎：从分数到改进

获取评估指标之后，构建一个分析层：它检测低表现会话中的模式，运行统计分析以区分系统性问题与孤立事件，并生成具体的 prompt 改进。这一层应当应用：

- **无监督模式检测**，在各评估维度上揭示反复出现的失效模式。
- **统计分析**（频次、相关性），判断哪些失效模式是系统性的、哪些是孤立的。
- **基于 LLM 的推理**，生成以生产证据为依据的具体 prompt 优化建议。

AI 引擎会识别常见的失效模式：工具选择不当、上下文缺失，或某些特定标准得分偏低。把它配置为返回结构化发现，包含频次计数、受影响的会话 ID，以及来自 trace 的具体证据。例如，你的引擎可能发现：23% 的低分会话涉及 agent 在用户询问航班变更时选错工具，而这一模式在多轮对话中出现得最频繁（图 5）。

**prompt 改进层**：在模式分析的基础上，实现一个 prompt 改进功能，为你的原始 prompt 生成修订版本。该功能应直接针对已识别的模式，并清晰说明改了什么、为什么这样改，以及预期影响（图 6）。这就闭合了评估闭环：指标暴露问题，分析定位根本原因，prompt 改进提供可执行的修复，它们在下一轮持续集成与持续交付（CI/CD）运行中得到验证，并在下一个生产周期中被持续监控。

### 第二层：AWS DevOps Agent，系统健康吗？

AgentCore Evaluations 监控的是 agent 质量，而权限、工具错误这类基础设施问题需要另一种方法。AWS DevOps Agent 充当自主的 on-call 工程师，自动调查基础设施问题。出现异常时，它会分析系统日志、基础设施指标和错误模式，然后给出具体的修复步骤。

下面的演示视频（视频 2）展示了如何通过签名 webhook 为 Travel Agent 触发 AWS DevOps Agent：

*视频 2：AWS DevOps Agent 如何执行一次调查——查阅相关的 Amazon CloudWatch 日志和 AWS 服务缺口，以定位根本原因并提供修复步骤*

如视频所示，事件通过签名 webhook 提交之后，AWS DevOps Agent 首先从 Amazon CloudWatch 中找出相关日志，然后分析这些日志以检查常见错误，例如 IAM 权限问题、工具失败或其他隐藏错误，最后应用基于大语言模型（LLM）的推理来确定根本原因，并给出有针对性的建议，帮助防止问题将来再次发生。

没有 AWS DevOps Agent 的话，你看到的会是：这个机票 swarm agent 突然不再响应机票预订请求，返回一条通用错误信息或完全空白的输出，而不是帮助用户。

此时，你会：

- 检查应用日志中的错误模式。
- 回顾最近的部署，寻找可能的原因。
- 手工检查 IAM 策略与权限。
- 跨多个服务关联 Amazon CloudWatch 指标。
- 追踪贯穿多个 agent 交互的执行流。

这一过程可能要花 30–60 分钟——而且前提是对系统架构有深入了解。

我们把事件通过连接到 AWS DevOps Agent Space 的签名 webhook 直接提交到我们的 AWS DevOps Agent Space 之后，一次调查随即启动，产出了受影响 AWS 资源的拓扑图，以及对 AgentCore runtime 的 Amazon CloudWatch 日志的全面分析。

![AWS DevOps Agent UI 展示已定位的根本原因与追踪到的失败路径](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/31/ML-20434-13.jpg)

图 8：AWS DevOps Agent UI 展示已定位的根本原因——缺少 bedrock:InvokeModel 权限，以及从用户请求经 AgentCore runtime 到 Amazon Bedrock API 拒绝的完整失败路径

它识别出执行角色上缺少 `bedrock:InvokeModel` 权限。每次 agent 调用都会调用 Amazon Bedrock 来运行其语言模型，而每次调用都在 IAM 层被拒绝。Supervisor Agent 无法调用其模型来处理初始请求，因此返回了空白输出（而不是 403 错误或异常），因为根本没有可用的模型响应，无从合成更有信息量的内容。

关键在于，AWS DevOps Agent 不只是指出了 IAM 错误，还从用户请求出发追踪了完整的失败路径：

**用户请求 → AgentCore runtime → Amazon Bedrock API 调用 → 访问被拒绝 → Agent 失败**

最后，这次调查在 prevention 标签页中给出了具体的修复步骤。

![AWS DevOps Agent UI 展示 prevention 标签页中的修复步骤](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/31/ML-20434-14-1.jpg)

图 9：AWS DevOps Agent UI 展示 prevention 标签页，其中包含具体、可执行的修复步骤和高置信度评级

总体而言，建议的做法是为该执行角色添加所需的 Amazon Bedrock 权限，并把权限限定到正在使用的那个特定基础模型资源。这为用户今后的开发提供了值得考虑的要点，有助于在这一范式下预防失败。

AWS DevOps Agent 通过自动化整个多 agent 系统的失败诊断，提升了开发者效率。例如，它能把 agent 的空白输出映射到 IAM 层缺失的 Amazon Bedrock 权限。AWS DevOps Agent 会在 Amazon Bedrock AgentCore runtime、Amazon Bedrock、AWS IAM 执行角色和 Amazon CloudWatch Logs 之间协调，自动与某次失败建立关联。它在整个多 agent 调用流上做模式匹配的能力，能捕捉到原本会被忽略的错误。

除了 IAM 权限问题，AWS DevOps Agent 还设计用于处理多 agent 系统中常见的各类复杂失效模式。示例如下：

- **负载下的模型限流**：当子 agent 扩容并触达 Amazon Bedrock 的每分钟 token 上限时，个别子 agent 开始间歇性失败。AWS DevOps Agent 会把限流指标与 agent 调用时间线关联起来，识别是哪个模型、哪个区域以及哪次流量激增导致了问题。
- **被重试逻辑掩盖的工具调用失败**：如果某个子 agent 的工具集成开始返回错误，而 Supervisor Agent 静默改道，AWS DevOps Agent 会从日志中找出下游工具错误，并把它们与用户体验下降联系起来。
- **记忆与上下文问题**：如果 agent 在会话中途失去对记忆资源的访问，回答会变得不连贯，而不是直接失败。AWS DevOps Agent 会检测回答质量模式中的异常，并把它们与配置变更关联起来。
- **跨 agent 通信中断**：当 agent 之间的交接因网络问题或身份验证问题而失败时，AWS DevOps Agent 会追踪完整的交接链，准确指出通信在哪里断掉。

**注意：** 采用这套架构之前，请留意以下几点：

- **LLM-as-judge 的可靠性**：AgentCore Evaluations 使用基于 LLM 的打分，缺少绝对的正确性基准。把分数当作信号，而不是绝对度量。与领域专家一起校准评估器，让自动判断与你所在领域的真人预期对齐。
- **服务成熟度**：AWS DevOps Agent 仍在持续演进。目前 webhook 凭据的生成需要通过控制台完成，但 Agent Space 的创建和管理可以用 [AWS CDK](https://docs.aws.amazon.com/devopsagent/latest/userguide/getting-startedwith-aws-devops-agent-getting-started-with-aws-devops-agent-using-aws-cdk.html) 和 [AWS SDK](https://docs.aws.amazon.com/AWSJavaScriptSDK/v3/latest/client/devops-agent/) 实现自动化。
- **延迟权衡**：在线评估会带来额外处理开销。降低采样率可以减少这部分开销，但可能漏掉边界情况。请根据你的流量规模以及需要覆盖交互空间的全面程度来调整采样率。
- **安全性**：需要谨慎配置 IAM 策略。AWS DevOps Agent 需要对日志和指标有较宽的读取权限，请合理划定权限范围，同时确保它能访问追踪跨服务失败所需的一切。
- **负责任 AI 控制**：对于生产部署，请用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 补充评估能力，对每次回答内联执行内容过滤、拒绝主题、接地检查和 PII 脱敏。Evaluations 捕捉随时间出现的质量漂移，Guardrails 则实时帮助阻止有害输出。

## 结论

把 agent 部署到生产只是开始。这套双层监控方法——质量与基础设施——为团队提供了持续改进所需的反馈闭环。AgentCore Evaluations 监控质量，AWS DevOps Agent 调查基础设施。两者共同把生产数据转化为具体的改进。

我们的机票预订系统用 Strands agent 按 Swarm 模式构建、部署在 AgentCore 上，它证明了这套双层监控方法切实可行、可扩展且有效。其结果是更快的故障解决、更高的政策合规性，以及一个以真实生产行为为依据的迭代改进循环。

无论你是在构建第一个多 agent 系统，还是在扩展已有部署，同样的原则都适用：持续衡量质量，自主调查失败，并让生产数据驱动你的下一轮迭代。
