# 用 anti-unification 给形式化策略做语义 diff

审代码时，你从一份 diff 起步。你不会把两个 3,000 行的文件放一起用眼睛比、然后指望看出每一处改动。形式化策略可能更难比较，因为文本 diff 常常把「不影响含义的句法变化」也高亮出来。把两个 conjunct 调个序、把等式两边换个位置、或换一个等价的谓词，文件里很大一片可能就看着变了。而行为上一次真正的改变——比如要求写的是 *and*、却用了个 `Or`——反倒可能淹没在这片噪声里。

语义 diff 展示两份策略有什么共同点、又在哪里不一致。本文用的[开源引擎](https://github.com/yaspar-org/semi-persistent)借 [anti-unification](https://en.wikipedia.org/wiki/Anti-unification) 算出这份 diff，它为两个表达式找出一个最具体的公共模式。Plotkin 的 [1970 年论文](https://homepages.inf.ed.ac.uk/gdp/publications/MI5_note_ind_gen.pdf)给了经典表述。引擎作用在一个 e-graph 上，后者记录已知相等的表达式。我们提供为这些相等关系背书的一堆代数律和领域规则，例如「把 external destination 与一个非 internal 的 destination 视作相等」。结果把共享部分只列一次，并把每处有分歧的部分的两个版本都留着供评审。若不再有差异，那么在这些律与规则之下两份策略等价。当规则或搜索并不完备时，一处残留的差异也可能对应着引擎尚未找到的某个等价关系。

**一个用例是 autoformalization。** autoformalization 把自然语言翻成形式化语言。假设你想把需求转成 [SMT-LIB](https://smt-lib.org/)——Z3、cvc5 这类 satisfiability modulo theories（SMT）solver 的标准输入语言，或转成 [Cedar](https://www.cedarpolicy.com/)、[Dogwood](https://github.com/dogwood-policy/dogwood) 来控制你软件系统里的授权。一个 large language model（LLM）从散文生成形式化制品，模型负责写这个制品，完全不参与 diff 的计算。把模型跑两遍，它可能给出两份不同的形式化，而没有 ground truth 能指出哪份对。语义 diff 展示它们哪里一致、哪里不同。变换模型、prompt 或 sampling temperature 再多生成几个候选，相互比较就能看出哪些部分保持不变、哪些会变。先评审那些会变的部分。

需求也可以变成 [OpenShell sandbox policies](https://docs.nvidia.com/openshell/latest/how-it-works/policies/schema) 或 [Common Expression Language（CEL）](https://cel.dev/overview/cel-overview) 表达式。OpenShell 用 YAML 描述一个 agent 的文件系统与网络访问。CEL 嵌在应用里求值表达式，包括策略条件。这些语言与格式在表达力上各不相同，但翻进其中任何一种，都可能在某个条件、作用域或事件上出现分歧。下表给出几类示意性的分歧：

| **语言或格式** | **策略关注点** | **示意分歧** |
| --- | --- | --- |
| [Cedar](https://www.cedarpolicy.com/) | 谁能在何种条件下对某资源执行某动作。 | 一份译文要求 ownership *且* approval，另一份接受两者之一。 |
| [Dogwood](https://github.com/dogwood-policy/dogwood) | 涉及当前请求与近期事件历史的授权。 | 一份译文检查此前一次成功的 response，另一份检查一个 request event。 |
| [OpenShell policies](https://docs.nvidia.com/openshell/latest/how-it-works/policies/schema) | 一个 agent 的文件系统与网络访问，含针对特定 binary 的规则。 | 一份译文允许 repository 范围的 `GET`，另一份允许 organization 范围的 `POST`。 |
| [CEL](https://cel.dev/overview/cel-overview) | 在宿主应用提供的输入上求值的条件。 | 一份译文要求两个允许的 port 都处于 production，另一份只要求其中一个。 |

在每个可跑的例子里，我们都比较同一策略语境下、同一需求的若干份译文。我们把相关句法编码成 terms，并声明比较中所用的相等关系。引擎读的是这些编码，并不从这四种格式里导入原生策略。

这个思路是 [semantic entropy](https://doi.org/10.1038/s41586-024-07421-0) 在形式化方法里的对应物，后者由 Farquhar 等人在 *Nature*（2024）描述。那种做法采样若干条自然语言回答、把彼此蕴含的聚成簇，再报出一个数字。对形式化输出，anti-unification 保留了更多信息：它找出共享结构与每一处分歧，而不只返回一个分数。

**反例有助于解释一处分歧的后果。** 一个 SMT solver 能找到一个具体赋值，满足其中一个公式却违反另一个。评审者随后可以沿着这个赋值穿过两个公式，弄清相互冲突的决策。anti-unifier 给的是另一种视角：它把共享结构和有差异的片段组织好，不发 SMT 查询；一个 solver 或 policy validator 可以帮忙裁决那些片段。我们假定你能读 S-expression 语法（如 SMT-LIB 里的），也知道授权策略是什么。e-graphs 与 anti-unification 会在出现处随文解释。

> 当若干份译文在需求的某一部分上一致时，diff 把那部分只列一次；它们不一致的地方，则把各个备选保留可见供评审。

## 语义 diff 如何表示分歧

假设某条策略生成流水线针对这个需求交给你两条候选规则：*敏感数据发往 external destination 时必须加密*。

| **规则 A** | **规则 B** |
| --- | --- |
| *sensitive*(*data*) **∧** *external*(*dst*) **→** *encrypted* | **¬***internal*(*dst*) **∧** *sensitive*(*data*) **→** *audited* |

这两条是不是同一条规则，并不显然。条件换了序，*external* 被间接地写成 *not internal*，结论也对不上。引擎为这两个 terms 算出一个最具体的 anti-unifier。在它的输入语言里，两条规则都是 S-expressions。

完整程序先声明词汇表：

```
(sort Formula)
(sort Data)
(sort Dest)
(function Lit (bool) Formula)
(function And (Formula) Formula :assoc-comm-idem :identity (Lit true))
(function Implies (Formula Formula) Formula)
(function Not (Formula) Formula)
```

随后为每个谓词（`sensitive`、`external`、`internal`）和常量（`data`、`dst`、`encrypted`、`audited`）各加一行 `function`。这里 `And` 被声明为 associative、commutative 和 idempotent，下一节会解释：

```
(let ruleA (Implies (And (sensitive (data)) (external (dst)))
                    (encrypted)))
(let ruleB (Implies (And (Not (internal (dst))) (sensitive (data)))
                    (audited)))

(antiunify ruleA ruleB :algorithm exact)
```

引擎以一个 term 作答：

```
(anti-unify :size 11 :cr 0.5000 :completion exact
  (Implies
    (And (sensitive data) (Variants (external dst) (Not (internal dst))))
    (Variants encrypted audited)))
```

换序没有出现在结果里，因为 `And` 被声明为 associative、commutative 和 idempotent。剩下两个 `Variants` 节点，各自标出一处输入不一致的位置，而其中只有一处是含义上的差异。`(external dst)` 与 `(Not (internal dst))` 之间的差别只是词汇上的：两者表达同一个领域事实。引擎没法单从句法推出这一点。把那个领域事实写成一条 `rewrite`，跑到 saturation（直到没有规则再加进新的相等关系），再 diff 一次：

```
(rewrite (external d) (Not (internal d)))
(run 2)
(antiunify ruleA ruleB :algorithm exact)
```

saturation 之后，引擎作答：

```
(anti-unify :size 8 :cr 0.1429 :completion exact
  (Implies (And (sensitive data) (external dst)) (Variants encrypted audited)))
```

只剩一个 `Variants` 节点：需求要的是加密，规则 B 却做了审计。教科书式讲法会在那个位置放一个新变量，引擎则写成 `(Variants encrypted audited)`：一个同时持有*两种读法*的节点。把每个 `Variants` 节点的第一个孩子挑出来，你就在「所声明的代数与 rewrites 取模」的意义下重建出规则 A；挑第二个孩子就得到规则 B。anti-unifier 是两个 term 的无损合并：共享结构只出现一次，每一处真正的分歧都是一个局部化、可评审的节点。

有三个字段描述结果：`:size`、`:cr` 和 `:completion`。`:size` 数字段数具体的节点（`Variants` 标记本身不计，但它的两个孩子都计，因此结构没法藏进一个节点里）。

`:cr` 字段给出压缩比 `(s - a) / b`，其中 `s` 是结果大小，`a` 和 `b` 分别是较小与较大的输入大小。对每个输入，我们用当前 e-graph 里已知最小的等价形式。分数为 0 表示在所声明的相等关系下完全一致。

上一条 rewrite 之后，两个输入各有七个节点、结果有八个，于是 `(8 - 7) / 7`，约 0.1429。若把两份完整策略塞进单独一个 `Variants` 节点，会用掉十四个节点，得到 `(14 - 7) / 7 = 1`。这就是「毫无共享」的参照值。

分数 1 是参照值，不是上界。搜索可能用到比已知最小输入更大的等价形式，因此一个大于两者合计大小的结果会算出高于 1 的分数。例如两个最小输入形式各有十个节点、结果有二十三个，比值就是 `(23 - 10) / 10 = 1.3`。

`:completion` 字段在搜索空间被穷尽时报 `exact`，在默认的 anytime 搜索（一种 Monte Carlo 搜索，实现一节会讲）于穷尽搜索空间之前撞到 playout 上限时报 `budget`。

低的 `:cr` 意味着在所声明的相等关系下，输入共享更多结构。它并不证明正确性：两个候选可能犯同一个错。entropy 分数把变异压成一个数字，而完整的语义 diff 还指出候选在哪里不一致，并把两个备选都保留在 `Variants` 节点里。

语义 diff 只忽略那些被所声明相等关系覆盖的差异。一个纯粹的*句法* anti-unifier 在这个例子里连换序也会报出来。下面三节展示如何声明代数、补上领域恒等式。

> anti-unifier 把共享结构存一次，用 `Variants` 节点标出每处分歧。把每个节点挑定一侧，就在所声明相等关系取模下重建出对应的输入。

## 5 分钟跑一次语义 diff

从源码构建这个引擎只需要一个钉住版本的 Rust toolchain。它的形式化验证标注（实现一节会讲）在普通 `rustc` 下会被编译掉。下面这些命令钉住了可跑例子所用的那个 revision：

```
git clone https://github.com/yaspar-org/semi-persistent.git
cd semi-persistent
git fetch origin 5a7969ae4ea88117a64faac4f42af5c358e213e2
git checkout --detach FETCH_HEAD
cargo build --release
./target/release/semi-persistent doc/book/examples/12-first-au.egg
```

它打印出单个 `(anti-unify ...)` term。

命令行解释器读入一个 S-expression 文件（按惯例用 `.egg`）。你声明 sorts 和 operators，用 `let` 定义两个 term，可选地加 rewrite rules 并把它们跑到 saturation，然后发出 `antiunify`。有两种机制告诉引擎「哪些句法变化不影响含义」：给 operator 赋结合律、交换律、幂等律这类代数性质的 annotations，以及为其余一切写显式 rewrite rules。下面是可跑例子里所用 signature 的代数部分：

```
(function Lit (bool) Formula)
(function And (Formula) Formula :assoc-comm-idem :identity (Lit true))
(function Or  (Formula) Formula :assoc-comm-idem :identity (Lit false))
(function Eq  (Account Account) Formula :comm)
```

`And` 和 `Or` 是 variadic、associative、commutative 和 idempotent 的，各有一个 Boolean 中性元素；`Eq` 是 commutative。于是 conjunct 的每一次换序、重新分组和重复，都算作*同一个 term*。别的什么都没假定：只有写明的律成立，任何进一步的恒等式都必须写成显式 rewrites。`:identity` 元素让 diff 能把「一个输入有、另一个没有」的 conjunct 对上：缺掉的那个 conjunct 与 `(Lit true)` 配对，而不是让整条 `And` 表达式对不齐。两个案例研究都依赖这种 identity alignment。

> `:assoc-comm-idem` 让换序、重新分组和重复的 operand 等价；`:identity` 让 diff 把缺掉的 operand 与该 operator 的中性元素对上。

## 带两个策略 bug 的可跑例子

这个贯穿全文的例子随 repository 一起提供：[egraph/examples/au_policy_divergence.egg](https://github.com/yaspar-org/semi-persistent/blob/main/egraph/examples/au_policy_divergence.egg)。考虑一句策略：

> 只有当源 bucket 启用了 versioning、且目标 bucket 位于获批 Region 时，才允许跨 Region 复制请求。若对象被标记为 confidential，目标与源账户必须相同，且必须启用使用 customer managed key 的 server-side encryption。不超过 multipart threshold 的对象直接复制，更大的对象需要 multipart copy。

两个人、或同一模型两次独立运行，给出了它的形式化（文件里的 `formulaA` 和 `formulaB`）：

| **编码 A**   `(**Implies** (permit) (**And** (versioningOn (src)) (approvedRegion (regionOf (dst))) (**Implies** (taggedConfidential (obj)) (**And** (**Eq** (accountOf (dst)) (accountOf (src))) (sseCmk))) (**Ite** (**Lte** (sizeOf (obj)) (multipartThreshold)) (directCopy) (multipartCopy))))` | **编码 B**   `(**Implies** (permit) (**And** (**Ite** (**Lt** (sizeOf (obj)) (multipartThreshold)) (directCopy) (multipartCopy)) (**Implies** (taggedConfidential (obj)) (**Or** (**Eq** (accountOf (src)) (accountOf (dst))) (sseCmk))) (**Or** (usEast1 (regionOf (dst))) (euWest1 (regionOf (dst)))) (versioningOn (src))))` |
| --- | --- |

文本上有五处不同。三处是呈现上的：conjunct 换了序、`Eq` 两边调换、`approvedRegion` 被显式展开成两个 AWS Regions（`us-east-1` 和 `eu-west-1`）。两处涉及不同的 operator：confidential 子句里一个 `And` 变成了 `Or`，大小阈值处 `Lte` 变成了 `Lt`。两份编码的 unified diff 把 28 行里的 18 行标成改动（图 1 的 textual-diff 面板），却完全没指出这五处差异里哪几处改变了含义。两份编码的 exact anti-unifier 如下：

```
(anti-unify :size 42 :cr 0.5862 :completion exact
  (Implies
    permit
    (And
      (Implies
        (taggedConfidential obj)
        (And
          (Or (Eq (accountOf dst) (accountOf src)) (Variants (Lit false) sseCmk))
          (Variants sseCmk (Lit true))))
      (Ite
        (Variants
          (Lte (sizeOf obj) multipartThreshold)
          (Lt (sizeOf obj) multipartThreshold))
        directCopy
        multipartCopy)
      (versioningOn src)
      (Variants
        (approvedRegion (regionOf dst))
        (Or (usEast1 (regionOf dst))
            (euWest1 (regionOf dst)))))))
```

**五处差异里有两处消失了。** conjunct 换序被吸收，因为 `And` 被声明为 associative、commutative 和 idempotent（ACI）。`Eq` 两边调换，因为 `:comm` 把它们 canonize 了，两种读法里打印出来的顺序一样。两者都不改含义，因此都不报。

**confidential 子句在要求写 *and* 的地方用了 `Or`。** 编码 A 要求「同账户检查」与「使用 customer managed key 的 server-side encryption」*两者都*成立，编码 B 接受*两者之一*。引擎借各自的中性元素，把 A 的合取与 B 的析取对齐，于是这处分歧表现为相邻的两个 `Variants` 节点。在每个节点挑第一个孩子就重建出 A：`Or` 塌成那条普通的等式，`sseCmk` 仍是必需的 conjunct。每个节点挑第二个孩子就重建出 B：必需的 `sseCmk` 弱化成 `(Lit true)`，只作为 `Or` 里的一个备选留存。两个 `Variants` 节点合起来说明：编码 B 单凭 server-side encryption 就放行，因而允许 confidential 对象的跨账户复制。

你也许本以为 `sseCmk` 该被共享、而非重复。然而一阶 anti-unifier 没法概括 connective 本身，因此 `And` 对 `Or` 迫使它拆成两种对齐。identity alignment 仍让那个五节点的等式共享了一次。exact solver 的穷尽搜索找不到更小的形式，打印出的结果比「把两个子句整个塞进一个 `Variants`」还小一个节点。

**补上领域 `rewrite`，再 diff 一次。** Region 的那个 `Variants` 节点不是 bug，它反映的是缺失的领域知识：在这次部署里，获批 Regions *正是*那两个。把它写成一条 `rewrite`、saturate、再 diff：

```
(rewrite (approvedRegion r) (Or (usEast1 r) (euWest1 r)))
(run 3)
(antiunify formulaA formulaB :algorithm exact)
```

Region 差异挪进共享骨架，`:cr` 从 0.5862 降到 0.4000。完整结果就是图 1 的 semantic-diff 面板。恰好还剩两处分歧：被削弱的 confidential 子句，以及阈值。B 的 `Lt` 是严格的，因此正好等于 `multipartThreshold` 的对象在 A 下被直接复制、在 B 下走 multipart 路径。这处分歧被圈在 `Ite` 条件里，两条分支都落在共享骨架上。残留的两处差异都是授权评审者必须裁决的真实 bug，其余差异由代数和一条领域 rewrite 解释掉了。同一个文件也跑 anytime 搜索 `(antiunify formulaA formulaB :algorithm uct :playouts 3000)`，返回同样那个 size-35 的 term。整个程序在一台 Apple M3 Pro 笔记本上远低于 100 ms 就跑完（binary 热起来后 50–60 ms）。这覆盖了解析、声明、saturation、五次 anti-unification 查询及其回归检查，以及进程启动。我们用 Rust 1.97.1 的 release build、借助 shell 的 `time` 命令、在五次热运行上测了 `./target/release/semi-persistent egraph/examples/au_policy_divergence.egg` 的墙钟时间。Get started 一节给出同一条命令。

| **文本 diff：28 行里 18 行被标记**   ` (Implies (permit) (And - (versioningOn (src)) - (approvedRegion (regionOf (dst))) + (Ite + (Lt (sizeOf (obj)) (multipartThreshold)) + (directCopy) + (multipartCopy)) (Implies (taggedConfidential (obj)) - (And - (Eq (accountOf (dst)) (accountOf (src))) + (Or + (Eq (accountOf (src)) (accountOf (dst))) (sseCmk))) - (Ite - (Lte (sizeOf (obj)) (multipartThreshold)) - (directCopy) - (multipartCopy)))) + (Or + (usEast1 (regionOf (dst))) + (euWest1 (regionOf (dst)))) + (versioningOn (src)))) ` | **语义 diff：两处分歧，已局部化**   `(anti-unify :size 35 :cr 0.4000 :completion exact (Implies permit (And (Implies (taggedConfidential obj) (And (Or (Eq (accountOf dst) (accountOf src)) **(Variants (Lit false) sseCmk)**) **(Variants sseCmk (Lit true))**)) (Ite **(Variants** **(Lte (sizeOf obj) multipartThreshold)** **(Lt (sizeOf obj) multipartThreshold))** directCopy multipartCopy) (versioningOn src) (approvedRegion (regionOf dst)))))` |
| --- | --- |

*图 1：同一对编码分别在 diff 与 anti-unification 下的样子。左边，文本 diff 把 28 行里的 18 行标成改动（删除、新增）。右边，一条领域 rewrite 把共享结构挪进灰色骨架，高亮的 `Variants` 把残留差异圈在被削弱的 confidential 子句和严格的阈值上。semantic-diff 面板为适配版面折了一处长行*

> 应用所声明的代数和一条领域 rewrite 之后，五处文本差异缩减为两处语义分歧：被削弱的 confidential 子句，以及严格的大小阈值。

## 给 Cedar 与 Dogwood 策略做语义 diff

在授权策略里，丢掉一个 guard 会放宽被允许的范围，可能让策略 *fail open*。Cedar 是 Amazon Verified Permissions 背后的开源授权策略语言。[Dogwood](https://aws.amazon.com/blogs/opensource/introducing-dogwood-runtime-verification-for-ai-agents/) 给 Cedar 授权策略扩上时序条件，用于 AI agents 的 runtime verification。它的时序子语言用记录下来的事件历史来给动作设 guard。引擎并不求值 Dogwood 策略，它是在「所声明代数取模」下 diff 它们的抽象句法。validation（schema checking）和 replay（拿一份策略对记录下来的事件历史求值）仍归 Dogwood 管。引擎的 [user guide](https://yaspar-org.github.io/semi-persistent/) 有一章可跑例子，针对一条需求 diff 两份独立产出的 Dogwood 候选：

> 该 agent 可以 POST 到 /deploy，但前提是过去 15 分钟内已有一次健康检查返回过 200。

候选 A 保留了两道 request guard（method 和 path），却从一个 request event 里读 status code——这种 event kind 并没有这个字段。候选 B 用了正确的 response event，却*丢掉了 `/deploy` path guard*。于是任何一次匹配的健康检查之后，B 也允许向 `/admin/purge-all` 发 `POST`。两份候选另有六处呈现上的差异，全都被所声明的代数或一套三条规则的 comparison theory 吸收了：

| **呈现上的差异** | **由谁吸收** |
| --- | --- |
| Cedar condition 顺序 | `eAnd :assoc-comm-idem` |
| 时序合取顺序 | `tAnd :assoc-comm-idem` |
| predicate 字段顺序 | `args :assoc-comm-idem` |
| `method == "POST"` 对 `"POST" == method` | `eEq :comm` |
| `15m` 对 `900s` | unit rewrite + constant fold |
| `count >= 1` 对 `1 <= count` | `(birewrite (tLte a b) (tGte b a))` |

这套 comparison theory 由三条看得见的 rewrites 组成，不是一次藏在暗处的 normalization pass：

```
(rewrite (mins x) (secsTimes x 60))
(rewrite (secsTimes x y) (secs (IBig::* x y)))
(birewrite (tLte a b) (tGte b a))
(run 4)
```

两份候选的 anti-unifier（repository 里的 [doc/book/examples/20-dogwood-simple.egg](https://github.com/yaspar-org/semi-persistent/blob/main/doc/book/examples/20-dogwood-simple.egg)）大小为 61、`:cr` 0.1864，在一条其余部分共享的策略骨架上恰好有两处分歧：

```
(anti-unify :size 61 :cr 0.1864 :completion exact
  (rule
    permit
    (head anyPrincipal (actionEq aHttpRequest) anyResource)
    (eAnd
      (eEq (eCtx (fld fInput (fld fMethod fnil))) (eStr vPOST))
      (temporal
        ...
                  (pred
                    aHttpRequest
                    (Variants request response)
                    ...
      (Variants
        (eEq (eCtx (fld fInput (fld fPath fnil))) (eStr vDeploy))
        eTrue))))
```

**对每处分歧用手头最简单的检查。** 两处二元分歧给出四个候选补全。Dogwood validation 无需人工评审就裁决了第一处：它拒掉两种 request 补全（「predicate … mentions field `output.status_code`, which is not declared on that event」）。第二处分歧是一次 identity alignment：候选 A 的 path guard 与 `eTrue` 配对，说明候选 B 漏掉了这道 guard。需求把它裁决掉（保留 guard），而覆盖两个决策点的 replay 展示出后果：一次健康检查之后，候选 B 放行那次越界的 `POST`，修好的策略则拒绝它。把 B 的 event kind 与 A 的 guard 合起来，得到一份两份候选都没写出的策略。若只在两份候选之间选，就会留下两个 bug 中的一个。

**交换律有个附带条件，而引擎不检查它。** Cedar 的 `&&` 会 short-circuit，因此只有当两个 operand 都不会抛错时，交换它才成立。所以这套比较要靠 validation 排除顺序相关的错误，例如「只有挡在 `has` guard 之后才安全的属性访问」。引擎并不复核这个条件。

**canonical printer 能消掉呈现差异，但找不回丢掉的 guard。** 一台 canonizing printer 加文本 diff，能更便宜地吸收表六处差异里的大部分、甚至可说是全部。但没有任何 normalizer 能在一个其余部分都匹配好的 term 里，把「两个 conjunct 的条件」与「三个 conjunct 的条件」对上。按 identity 元素取模来匹配，则把丢掉的那个 conjunct 与 `eTrue` 配对，从而对齐它们。在 `permit` 条件里，那个丢掉的 conjunct 暴露了让策略 fail open 的放宽。

> 对 Dogwood 候选，代数加三条 rewrites 消掉六处呈现差异。残留分歧暴露出一次 schema error 和一道丢掉的 guard。把各自正确的选择合起来，得到一份两份候选都没给出的策略。

## 比较策略译文：OpenShell 与 CEL

下面两个例子改编自 OpenShell 和 CEL 两篇文章里的谓词。对每个例子，我们为同一条需求构造候选译文。这些是示意性编码，不是采下来的真实 LLM 样本。

**OpenShell：method 与 path 作用域。** 这个 [OpenShell 例子](https://nvidia.github.io/OpenShell-Research/dev-notes/posts/2026-09-10-learning-formal-methods-agent-policy-prover/) 把网络权限建模成作用在 binary、host、port、layer、method 和 path 上的谓词。我们改编文章里那个精简的 SMT-LIB 模型，它的 path 条件是一个前缀测试。用这套词汇表达这条需求：

> 允许 /usr/bin/gh 向 api.github.com 的 443 port 发出、method 为 GET 且 path 以 /repos/NVIDIA/OpenShell/issues/ 开头的、经过检查的 REST 请求。拒绝所有其它请求。

候选 A 要求 `GET` 和该 repository 的 issues 前缀，候选 B 用 `POST` 和更宽的 `/repos/NVIDIA/` 前缀，其余检查出现顺序也不同。编码里 `gh`、`github` 和 `https` 分别指前面给出的 binary、host 和 port，`issuePrefix` 与 `orgPrefix` 标识那两个前缀。exact solver 返回：

```
(anti-unify :size 21 :cr 0.1053 :completion exact
  (And
    (EqText binary gh)
    (EqText host github)
    (EqText layer rest)
    (EqText method (Variants GET POST))
    (EqNumber port https)
    (Prefix (Variants issuePrefix orgPrefix) path)))
```

binary、host、port 和 layer 检查是共享的，它们的顺序消失，因为 `And` 被声明为 associative、commutative 和 idempotent。两个 `Variants` 节点指出相互冲突的读法：被允许的操作和 path 作用域。这里需求把两个选择都定下来了；若需求本身含糊，同样的节点会给它的负责人两个具体备选去裁决。

**CEL：一个共享条件的作用域。** 这个 [CEL 例子](https://opensource.googleblog.com/2026/08/securing-the-agentic-era-introducing-formal-verification-for-cel.html) 暴露出一次重构中丢掉的 production 检查。我们把那些表达式复用为这条需求的候选译文：

> 当且仅当请求处于 production、且 port 为 80 或 443 时允许它。

```
// Candidate A
(is_prod && port == 80) || (is_prod && port == 443)

// Candidate B
is_prod && port == 80 || port == 443
```

CEL 的 `&&` 比 `||` 结合得更紧，因此候选 B 只对 port 80 施加 production 检查。我们用提供的 Boolean 与 integer 输入编码这些表达式，用 `isProd`、`port80` 和 `port443` 指代相应输入与字面量：

```
(anti-unify :size 13 :cr 0.3636 :completion exact
  (Or
    (And (Eq port port443) (Variants isProd (Lit true)))
    (And isProd (Eq port port80))))
```

port-80 分支是共享的。在 port-443 分支里，`(Variants isProd (Lit true))` 显出那道缺失的 production 条件。在 `is_prod = false`、`port = 443` 时，A 拒绝请求而 B 放行。这份 diff 把评审直接引到句子里的一个点上：「in production」是否同时作用于两个备选。

这个例子假定 `is_prod` 以 Boolean 提供、`port` 以 integer 提供。在这些假定下，两个表达式都不抛错。编码没有建模 CEL 的 error 或 unknown 值，引擎也不检查这些输入假定。

CEL-Java 的验证框架能用 Z3 检查等价性与策略不变量。这类检查可以在裁决分歧时提供证据。anti-unifier 本身并不判定哪份译文符合需求，而两份候选共有的错误仍会共有。

## 实现与性能

算法跑在 e-graph 上——一种把某个 term 连同「已知与它相等的一切」一起存下来的数据结构。e-graphs（equivalence graphs）源自定理证明器里的 congruence-closure 过程，并因 equality saturation 在编译器优化中普及开来，见 Willsey 等人的 [“egg: Fast and Extensible Equality Saturation”](https://doi.org/10.1145/3434304)（POPL 2021）。本引擎的 e-graph 给 associative 与 commutative operator 加了原生 canonization。

e-graph 上的 anti-unification 也被 [babble](https://doi.org/10.1145/3571207)（Cao 等人，POPL 2023）用于 abstraction learning 与程序压缩。更早的实现规模超不过小例子，我们那个基于 saturation 的原型也卡在那里。原生 AC canonization、对 distinct children 做的 AC-aware matching，以及直接搜索，让亚秒级查询变得可行；semi-persistence 压低了重复查询的成本。

**原生 AC canonization。** Associativity、commutativity 和 idempotence 在这个引擎里不是 rewrite rules，而是数据结构的性质。associative-commutative（AC）operator 在插入时就把孩子存成 canonical sorted multisets（ACI operator 存成 canonical sorted sets）。于是一个 e-node 就代表某个 term 的全部重结合与排列；对 idempotent operator，重复孩子还被当作一个。「在所声明律取模下的相等」*就是*结构相等。改写式那条路会在真正干活之前，先用指数级的等价副本把 e-graph 淹掉。

**对 distinct children 做 AC-aware matching。** 对 multiset 节点做模式匹配用的是 maximum-partition semantics：它在一个节点的*互异*孩子上分支，而不是枚举 multiplicity splits，于是大量重复的参数不会引发组合爆炸。

**直接搜索而非 rewriting。** anti-unification 本身同样没被编码成 rewrite rules。一个 exact dynamic programming solver（`:algorithm exact`）最优地解出 joint-decomposition 问题。这里的「最优」是相对于它 size-first 的目标、当前 e-graph 和配好的 cycle policy 而言。一个 anytime Monte Carlo graph search（`:algorithm uct`，默认项）在任意 playout budget 下都返回它当前最好的答案。在那个可跑例子的配对上，3,000 次 playouts 就复现了 exact 最优。两者都先优化结果大小，再在同样大小的答案里偏好那些在共享骨架里保留更多结构的。

**Semi-persistence。** e-graph 支持 `(push)` 和 `(pop)` 快照，以 sparse diffs 而非深拷贝记录。因此恢复一个状态的代价与「改了多少」成正比（快照本身），外加修复派生索引的成本。这种按比例的恢复代价，让引擎能在同一张共享图上比较许多候选；回溯搜索也能恢复较早状态而无需复制整张图。

**一个经过验证的核心及其范围。** e-graph 底层的容器层在 Verus（一个面向 Rust 的 verifier）里得到验证。被验证的性质是「restore 重现匹配那次 `(push)` 时的状态」（1,703 条已验证条件，0 个错误）。anti-unification crate 证明了它的 objective-order 与 lower-bound 引理，但完整 solver 还没有端到端的 refinement proof。引擎能为它推出的每条等价关系记一条 justification（`--proofs`）。如 repository 所说，这些记录还不是经独立重放校验的证书。所有这些主张，连同证据层级*与撤回说明*，都在 repository 的 claims inventory（[doc/claims.md](https://github.com/yaspar-org/semi-persistent/blob/main/doc/claims.md)）里。

> 原生 canonization 避免把等价的 AC terms 具象化；distinct-child matching 控住 multiplicity；直接 solver 不把 anti-unification 编码成 rewrites；semi-persistence 压低重复查询的成本。

## 在流水线里用语义 diff

**同一方法能从两个候选扩展到更大的样本。** 为需求生成 *N* 个候选形式化，把它们装进同一张共享 e-graph，在你的领域规则下 saturate，再用两两相等检查把它们聚簇。在 user guide 那个更大的 Dogwood 研究里，五个样本塌成三簇：仅在呈现上不同的候选，在构建期间就进了同一个 equivalence classes。对簇代表两两做 anti-unify，然后在架于引擎输出之上的一层里，按 `Variants` 节点在共享骨架中的位置把反复出现的归组。在那项研究里，三次两两 diff 缩减成恰好*两项*评审事项。对每一项用手头最简单的检查：schema validation、replay、示例 I/O 对，或人工评审。

有了 `(push)` 和 `(pop)` 快照，你不必重建图就能试一个提议的裁决。临时把某个 `Variants` 节点的一支断言为领域事实，再跑一次 diff，然后回滚。架在引擎之上的工具可以针对硬约束与软约束，选出并修好一份完整候选，例如在 variant 空间上用一个 [MaxSMT solver](https://z3prover.github.io/papers/programmingz3.html)。MaxSMT（maximum satisfiability modulo theories）求一个满足所有硬约束、同时尽可能多满足软约束或最大化其总权重的解。*Programming Z3* 第 8 节描述了这种优化形式。这项能力不在当前引擎里。图 2 概括这条流水线。

![流水线图：把候选形式化聚簇，定位反复出现的分歧，把每处分歧路由到 validation、replay、示例或人工评审检查](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/19/ML-21875-1.png)

图 2：一条把候选形式化聚簇、定位反复出现的分歧、并把每处分歧路由到合适检查的流水线。簇大小与评审项数取自 user guide 里更大的 Dogwood 研究

**在 continuous integration（CI）里用一份语义 diff 预算。** 命令 `(checkau A B :max_size N :algorithm exact)` 成功时什么都不打印，并在 anti-unifier 超出预算时让程序失败。user guide 里每个打印出来的结果都用这种方式钉住，因此 guide 与引擎不会各走各的。同一条命令也能当回归闸：为一份参考形式化和一份重新生成的形式化设一个最大结果大小，anti-unifier 超出就让流水线失败。binary 遵循标准 shell 约定：结果去 `stdout`，诊断（`ok --- N nodes`）去 `stderr`，任一检查失败进程就以非零退出。

这份 diff 也能引导一次后续 prompt、或给需求负责人提一个问题。样本间两两 `:cr` 的均值给每条需求一个分歧分数。一个 `Variants` 节点里已经装着做某次具体澄清所需的备选，比如「你的意思是严格小于阈值，还是至多等于？」

> 有多个候选时，把等价输出聚簇、比较簇代表，再用 validation、replay、示例或人工评审裁决反复出现的分歧。

## 开始使用

按本文所用的 revision 构建引擎，再跑那些策略例子。下面这些命令选中含 OpenShell 与 CEL 例子、来自 [pull request 103](https://github.com/yaspar-org/semi-persistent/pull/103) 的那个 revision：

```
git clone https://github.com/yaspar-org/semi-persistent.git
cd semi-persistent
git fetch origin 5a7969ae4ea88117a64faac4f42af5c358e213e2
git checkout --detach FETCH_HEAD
cargo build --release        # toolchain auto-pinned; Verus not required

# The worked example from this post:
./target/release/semi-persistent egraph/examples/au_policy_divergence.egg

# The Dogwood policy-diff example:
./target/release/semi-persistent doc/book/examples/20-dogwood-simple.egg

# The constructed OpenShell and CEL translation examples:
./target/release/semi-persistent egraph/examples/au_openshell_policy.egg
./target/release/semi-persistent egraph/examples/au_cel_policy.egg

# Your own formulas: declare a signature, two terms, and antiunify:
./target/release/semi-persistent MY_PROGRAM.egg
```

引擎在 [GitHub](https://github.com/yaspar-org/semi-persistent) 上以 Apache-2.0 开源。[user guide](https://yaspar-org.github.io/semi-persistent/) 从基础 term 一路走到策略案例研究，测试套件直接跑 repository 里指南中的每一个程序。附录 B 记载 `antiunify` 与 `checkau` 命令。只要你的制品语言有 abstract syntax tree（AST）和一套 equational theory，你就能 diff 它：声明代数、把领域恒等式写成 rewrites、再求最具体的 anti-unifier。如果你的策略是 Cedar，无论手写还是为 [Amazon Verified Permissions](https://aws.amazon.com/verified-permissions/) 生成，同一套配方一样适用。OpenShell 与 CEL 例子展示如何编码其它策略构造，并比较对一条需求的候选读法。
