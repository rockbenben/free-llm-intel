# 使用 Amazon Bedrock 与 Converse API 构建自定义 text-to-SQL agent

开发健壮的 text-to-SQL 能力是[自然语言处理](https://aws.amazon.com/what-is/nlp/)（NLP）与数据库管理领域的一项关键挑战。在这一领域，NLP 与数据库管理的复杂性会进一步上升，尤其是在处理复杂查询和数据库结构时。本文介绍一个直接但功能强大的方案，并附带代码：它借助自定义 agent 实现，同时使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 和 [Converse API](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html) 来完成 text-to-SQL。

把自然语言查询转换为 SQL 语句的能力对企业和组织而言具有变革意义，因为用户如今能以更直观、更易上手的方式与数据库交互。然而，数据库 schema 的复杂性、表之间的关系以及自然语言的细微差别，常常会导致 SQL 查询不准确或不完整。这不仅会损害数据的完整性，也会影响整体用户体验。借助一个直接而强大的架构，agent 可以理解你的查询、制定执行计划、生成 SQL 语句、在出现 SQL 错误时自我纠正，并从执行过程中学习，从而在未来做得更好。随着时间推移，agent 能够形成一套连贯的认识：哪些该做、哪些不该做，才能高效地回答用户的查询。

## 解决方案概览

该解决方案由一个 [AWS Lambda](https://aws.amazon.com/lambda/) 函数构成，其中包含 agent 的逻辑：它与 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 通信以保留长期记忆，通过 Converse API 调用 [Amazon Bedrock 中的 Anthropic Claude Sonnet](https://aws.amazon.com/bedrock/claude/)，使用 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 获取数据库连接信息与凭证，并连接 [Amazon Relational Database Service](https://aws.amazon.com/rds/)（Amazon RDS）中一个名为 HR Database 的示例 Postgres 数据库。该 Lambda 函数连接到一个虚拟私有云（VPC），并通过 [AWS PrivateLink](https://aws.amazon.com/privatelink/) VPC endpoint 与 DynamoDB、Amazon Bedrock 和 Secrets Manager 通信，这样 Lambda 既能与 RDS 数据库通信，又能让流量通过 AWS 网络保持私有。

在 demo 中，你可以通过 Lambda 函数与该 agent 交互。你可以向它提供自然语言查询，例如“每个区域每个部门各有多少员工？”或“每个区域的员工性别构成如何”。下面是该解决方案的架构。

### 使用 Converse API 构建自定义 agent

Converse API 由 Amazon Bedrock 提供，用于构建对话式应用。它支持诸如工具使用（tool use）等强大功能。[工具使用](https://docs.aws.amazon.com/bedrock/latest/userguide/tool-use.html) 指[大语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）能够从一组工具（例如对数据库执行 SQL 查询）中进行选择，并根据对话上下文决定使用哪个工具。使用 Converse API 还意味着你可以在 User 和 Assistant 角色之间维护一系列消息，从而与 Anthropic 的 Claude 3.5 Sonnet 这类 LLM 进行对话。本文中创建了一个名为 ConverseSQLAgent 的自定义 agent，专门面向长时间运行的 agent 执行，并遵循执行计划。

### Agent 循环：agent 规划、自我纠正与长期学习

该 agent 包含若干关键特性：规划与计划延续、执行与工具使用、SQLAlchemy 与自我纠正，以及基于记忆的反思与长期学习。

#### 规划与计划延续

agent 采取的第一步是为完成 text-to-SQL 任务创建执行计划。它首先思考用户究竟在问什么，并制定如何满足用户请求的计划。这一行为由 system prompt 控制，system prompt 定义了 agent 应当如何表现。agent 思考完该做什么之后，会输出计划。

长时间运行的 agent 执行面临的一个挑战是：随着它不断执行步骤、上下文越来越长，agent 有时会忘记自己本该执行的计划。应对这一问题的主要方法之一，是把初始计划“延续（carry over）”下来，将其重新注入 system prompt 的某个区块。system prompt 是每次 converse API 调用的一部分，它能提升 agent 遵循计划的能力。由于 agent 在推进执行过程中可能会修改计划，system prompt 中的计划会随着新计划的出现而更新。下图展示了计划延续的工作方式。

[![流程图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/02/ML-16627-image-2-1.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/02/ML-16627-image-2-1.png)

#### 执行与工具使用

计划制定完成后，agent 会一步一步执行计划。它可能决定调用一个或多个它可访问的工具。借助 Converse API，你可以传入 toolConfig，其中包含它可访问的每个工具的 toolSpec。toolSpec 定义了工具是什么、工具的描述以及工具所需的参数。当 LLM 决定使用某个工具时，它会在响应中输出一个 tool use block。应用（在本例中是 Lambda 代码）需要识别该 tool use block，执行相应的工具，把工具结果的响应追加到消息列表中，然后再次调用 Converse API。如下图所示（a）处，你可以通过添加 toolConfig 和 toolSpecs 来为 LLM 增加可选工具。（b）部分展示了在 ConverseSQLAgent 的实现中，tool group 包含一组工具，每个工具包含 toolSpec 和可调用函数。tool group 被添加到 agent 中，agent 又把它加入 Converse API 调用。tool group instructions 是关于如何使用该 tool group 的额外说明，会被注入到 system prompt 中。虽然你可以为每个单独的工具添加描述，但拥有 tool group 级别的统一说明能让该 group 的使用更有效。

[![Converse API 处理工具](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/02/ML-16627-image-3-1.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/02/ML-16627-image-3-1.png)

#### SQLAlchemy 与自我纠正

如上一张图所示，SQL 工具组（这些工具属于所提供的 demo 代码）使用 [SQLAlchemy](https://www.sqlalchemy.org/) 实现，它是一个 Python SQL 工具包，你可以用它对接不同的数据库，而无需担心特定数据库的 SQL 语法差异。你可以连接 Postgres、MySQL 等数据库，而不必每次都改代码。

本文中有一个 InvokeSQLQuery 工具，允许 agent 执行任意 SQL 语句。尽管几乎所有数据库相关任务（例如查询 schema 和表）都可以通过 InvokeSQLQuery 完成，但对特定任务来说，更好的做法是提供 SQLAlchemy 实现，例如 GetDatabaseSchemas，它获取数据库中的每个 schema，能大幅减少 agent 生成正确查询所需的时间。可以把它理解为给 agent 一条获取所需信息的捷径。agent 通过 InvokeSQLQuery 工具查询数据库时可能出错。InvokeSQLQuery 工具会把遇到的错误返回给 agent，agent 则可以执行自我纠正来修正查询。该流程如下图所示。

[![agent 流程](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/02/ML-16627-image-4.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/02/ML-16627-image-4.png)

#### 基于记忆的反思与长期学习

尽管自我纠正是 agent 的一项重要能力，但 agent 还必须能够从错误中学习，以避免将来重犯同样的错误。否则，agent 会不断犯同样的错，大幅降低效果与效率。该 agent 维护一个分层的记忆结构，如下图所示。agent 自行决定如何组织它的记忆。下面是一个它可能采用的组织方式示例。

[![记忆管理](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/02/ML-16627-image-5-1.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/02/ML-16627-image-5-1.png)

agent 可以对自己的执行过程进行反思，学习最佳实践与错误规避方法，并将其保存到长期记忆中。长期记忆借助 Amazon DynamoDB 以分层记忆结构实现。agent 维护一个主记忆（main memory），其中包含指向其他记忆的指针。每条记忆在 DynamoDB 表中表示为一条记录。当 agent 在执行中学习并遇到错误时，它可以更新主记忆，并通过在主记忆中维护一份记忆索引来创建新的记忆。之后它就能调用这些记忆来避免错误，甚至通过缓存事实来提升查询效率。

## 先决条件

开始之前，请确认你已具备以下先决条件：

- 一个 [AWS 账户](https://docs.aws.amazon.com/signin/latest/userguide/what-is-sign-in.html)，其中具有一个有权部署 CloudFormation 模板的 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）用户
- 已安装并[完成配置](https://docs.aws.amazon.com/cli/latest/userguide/cli-chap-configure.html)的 [AWS Command Line Interface](https://aws.amazon.com/cli/)（AWS CLI）
- Python 3.11 或更高版本
- 对 Anthropic Claude 3.5 Sonnet 的 Amazon Bedrock 模型访问权限
