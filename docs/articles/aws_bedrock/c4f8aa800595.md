## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 在 AgentCore 和 OpenClaw 上构建上下文感知 AI 助手

现成的人工智能助手可以很好地回答个人问题，但它们在另一个方面存在缺陷：连续性。今天向无国籍助理询问您的花园，它不知道您三周前提到过您的快速排水的高架床，您只使用有机肥料，或者您的矮牵牛正在热浪中挣扎。每次对话都从零开始，重新解释上下文的负担落在用户身上。

问题不在于答案的质量，而在于助手不记得你了。本文展示了如何使用 [OpenClaw](https://openclaw.ai/) 构建一个积累上下文的个人助理，OpenClaw 是一个开源代理系统，在 AgentCore 运行时（Amazon Bedrock AgentCore 的一项功能）上运行。 AgentCore 内存是 Amazon Bedrock AgentCore 的一项功能，可将一次性聊天转化为持久的知识。您还将了解如何使用结构化元数据标记这些记忆，以检索与当前问题相关的记录。

我们运行的示例是 Sprout，一个园艺助手，但其架构与领域无关。交换角色和技能表现，同一个管道可以为支持机器人、健身教练或内部服务台提供服务。整个系统位于单个 AWS CloudFormation 模板中，使用一个命令进行部署，并在基于消耗的模型上运行，每月花费几美元用于轻度个人使用。在此过程中，我们分享了您可以应用于在此堆栈上构建的助手的设计指南。

## 解决方案概述

AgentCore 是一个使用任何框架或模型大规模构建、连接和优化代理的平台。下图显示了从入站 Telegram Webhook 通过 AgentCore 运行时的端到端请求流及其支持的 AWS 服务。

图 1：Telegram Webhook 和 Amazon EventBridge 计划均调用相同的 AgentCore 运行时代理，该代理协调 OpenClaw 网关、AgentCore 内存和 Amazon Bedrock

两个入口点汇聚到一个代理上。 Telegram 消息通过 Amazon API Gateway 和 Webhook AWS Lambda 函数到达，而计划作业（例如早上浇水提醒）则通过 Amazon EventBridge Scheduler 和 cronjob Lambda 函数到达。两者都调用 AgentCore 运行时上的“InvokeAgentRuntime” API，其中精简“server.py”进程协调 OpenClaw 网关、AgentCore 内存和 Amazon Bedrock Converse API。 Amazon Simple Storage Service (Amazon S3) 提供工作区存储，AWS Key Management Service (AWS KMS) 处理加密，AWS Secrets Manager 保存机器人令牌，Amazon CloudWatch 捕获日志和指标。

## 先决条件

要使用 Launch Stack 按钮或 script/`deploy.sh` 部署您自己的版本（在“扩展您自己的”部分中进行了描述），您将需要：

- Amazon Bedrock AgentCore 访问，包括 AgentCore 运行时和 AgentCore 内存。
- 为您计划路由到的模型授予模型访问权限：用于文本的 Claude Haiku 4.5 和用于视觉的 Claude Sonnet 4.5（或您帐户中可用的等效项）。
- Docker 具有“linux/arm64”构建支持，以及配置的 AWS 命令​​行界面 (AWS CLI)。仅当您计划构建并推送自己的映像时才需要这样做。
- Telegram 机器人令牌（来自 BotFather），用作助理的前门。
- 基本熟悉代理编排概念和 CloudFormation。

## 架构：AgentCore 运行时上的无服务器代理

每个组件都位于单个 CloudFormation 模板中，无需构建工具即可启动。以下各节将介绍承重决策。

### AgentCore 运行时：仅为活动计算付费

代理位于 AgentCore 运行时的容器中，该容器使用基于消耗的定价。您需要为代理主动消耗的计算量付费，而不是为挂钟正常运行时间付费，并且您无需为等待 I/O（例如模型响应）的时间付费。对于短时间使用的个人助理，这是大约 1-2 美元/月的基准与大约 35 美元/月的始终在线 Amazon Elastic Compute Cloud (Amazon EC2) 实例之间的差异。这些数字是截至 2026 年 7 月的轻度个人使用的估计值。有关当前费率，请参阅 [AgentCore 定价](https://aws.amazon.com/bedrock/agentcore/pricing/)。

运行时强制执行最小容器契约：侦听端口 8080，并公开“GET /ping”以获取运行状况，并公开“POST /incalls”作为代理入口点。我们的容器是“linux/arm64”，由官方 OpenClaw 镜像加上 Python 层构建而成。

### OpenClaw作为代理基板

OpenClaw 提供代理循环、工具使用和技能系统。它运行一个包装器（`server.py`），使其适应 [AgentCore HTTP 协议合约](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-http-protocol-contract.html)：

- 在容器启动时，“server.py”将“openclaw gateway run”作为子进程启动并对其进行运行状况检查。
- `GET /ping` 快速恢复正常，因此 AgentCore 就绪探测通过。
- `POST /incalls` 完成真正的工作：解析有效负载，检索内存，组装上下文，将轮流转发到网关，并保存结果。一个标注：AgentCore 可以解冻其子进程已退出的冻结容器。因此，调用路径并不假设网关处于活动状态，它会调用“ensure_openclaw_ready()”帮助程序，在转发回合之前重新检查运行状况（并在需要时重新启动网关）。

此包装器模式可推广到其他用例。任何作为本地进程运行的代理框架都可以以相同的方式适应 AgentCore 运行时，而无需修改框架本身。

### 两个模型，按任务路由

文本聊天和图像理解具有不同的成本和质量权衡，因此助手将它们路由到 [Bedrock](https://aws.amazon.com/bedrock/) 上的不同 Claude 模型：

- **Claude Haiku 4.5 for text：** 快速且便宜，适合日常使用的大量对话。
- **用于视觉的 Claude Sonnet 4.5：** 更强的多模态推理，适用于从照片诊断植物这一不太常见但更困难的任务。

文本通过 OpenClaw 网关流动，带来技能和会话状态。图像直接从“server.py”调用 Bedrock 的大语言模型 (LLM)，将图像字节作为多模式内容块传递。我们特意在网关周围路由图像：容器内 OpenClaw 构建在到达 Bedrock 之前删除了“image_url”内容部分，因此直接从“server.py”调用 Converse API 可确保模型看到实际像素。两条路径共享相同的系统提示（角色加内存），因此体验保持一致。

模型 ID 是环境变量（“MODEL_ID”、“VISION_MODEL_ID”），因此您可以在每次部署时交换模型，而无需重建映像。

### 技能作为可重用的能力单元

功能在“community-skills.json”清单中声明为技能。部署时脚本将它们具体化到容器中，并在构建映像之前将它们注册到 OpenClaw 配置中。在发表这篇文章时，Sprout 附带了天气、提醒和植物笔记技能。交换清单，同一个管道服务于不同的域。这就是使整个事情成为可重用模式而不仅仅是一个机器人的原因。

### Telegram 作为无服务器前门

Telegram 是个人助理的实用渠道，因为它基于 Webhook，并且它使一切都保持无服务器状态。它不需要客户端开发，适用于用户已经拥有的每台设备，并通过简单的机器人 API 支持文本、图像和丰富的格式。 BotFather 颁发机器人令牌，该令牌存储在 Secrets Manager 中。该部署注册了一个将 Telegram 指向 API 网关端点的 Webhook。当用户发送消息时，Telegram 将其传递到 webhook Lambda 函数以验证有效负载并调用“InvokeAgentRuntime”。回复通过电报机器人 API 返回。

需要注意的一个格式化课程：Telegram 的旧版 Markdown 模型对于未转义的字符是无情的，并且模型响应中的单个下划线可能会导致整个消息无法发送。将回复呈现为 HTML 是可靠的，因此助手会在发送之前将模型输出转换为 Telegram 安全的 HTML。

## 记忆：将一次性聊天变成持久的知识

到目前为止所描述的架构是一个功能强大、廉价的无服务器代理，但它本身仍然会在对话之间忘记您。记忆改变了这一点。想象一下，几周前提到你进行有机园艺，今天助理推荐了一种处理方法，并补充说，它选择了有机选项，因为你不使用合成肥料。无状态模型无法做到这一点。

### 心智模型：短期事件，长期提取

AgentCore 内存有两层。 **短期记忆**通过“CreateEvent”将每个对话轮次存储为一个事件，并以“actorId”（Telegram 聊天 ID）和“sessionId”为键。这是原始记录。 **长期记忆是通过托管提取策略异步生成的，形成持久的结构化记录。我们配置了三种策略：

- `USER_PREFERENCE`：园丁所说的明确选择（“我只使用有机肥料”）。
-“语义”：推断事实（“在耐候钢高架床上种植墨西哥矮牵牛”）。
- `SUMMARIZATION`：情景会议摘要（“讨论热浪期间下部叶子变黄”）。

### 命名空间：每个园丁一个花园

Sprout 文件记录到每个用户的命名空间中，因此不会有两个聊天混合在一起：

- `sprout/{chat_id}/long_term`：偏好和语义事实。
- `sprout/{chat_id}/episodic/{session_id}`：会话摘要。

聊天 ID 是唯一的变量段，这使得隔离易于推理和测试：每个独特的园丁都映射到一个命名空间，并且不会有两个园丁发生冲突。

### 检索、组装和注入管道

每次，代理都会检索相关的长期记录，对它们进行排名，并将它们注入系统提示中。以下是 `server.py` 中每条消息所发生的情况：

- **Retrieve.** 针对 `sprout/{chat_id}/long_term` 调用 `RetrieveMemoryRecords`，使用用户的消息作为搜索查询，上限为 50 个结果，预算为 3 秒。如果检索超时或出现错误，我们会优雅地降级并在没有记忆的情况下回答，而不是失败。
```
try:
    records = memory_client.retrieve_memory_records(
        memoryId=MEMORY_ID,
        namespace=f'sprout/{chat_id}/long_term',
        searchCriteria={
            'searchQuery': user_message,
            'topK': 50,
            'metadataFilters': []
        },
    )  # 3s timeout
except Exception:
    records = []  # fall back to answering without memory
```
*片段 1：检索当前回合的长期记录（代表性。请参阅存储库以获取完整源代码）。*

组装功能添加了额外的自定义逻辑。我们希望显式偏好排在推断事实之前，每个类中的顺序是稳定的，并且结果在注入之前受到限制：
```
def assemble(records, cap=50):
    explicit = [r for r in records if r.type == 'USER_PREFERENCE']
    inferred = [r for r in records if r.type != 'USER_PREFERENCE']
    # explicit beats inferred; stable order within each class
    ordered = explicit + inferred
    return ordered[:cap]
```
*片段 2：组装步骤将显式偏好排在推断事实之前。*

### 元数据：对命名空间内的内存进行分组

命名空间回答记录在谁的内存中，而元数据回答记录的内容。在 `sprout/{chat_id}/long_term` 中，对“我的矮牵牛正在枯萎”的语义搜索将返回含义相近的所有内容。对于园丁来说，这意味着从三月份开始的肥料偏好和无花果树修剪记录与实际重要的记录一起排列。结构化元数据可以帮助我们在到达提示之前缩小记忆范围。

这里的每一个决定都由一条规则决定。如果将元数据键声明为索引键，则它只能在服务器端进行过滤。您可以在[使用 Amazon Bedrock AgentCore 内存中的元数据进行结构化内存过滤](https://aws.amazon.com/blogs/machine-learning/structed-memory-filtering-with-metadata-in-agentcore-memory/) 中了解更多信息。在这种情况下，sprout 使用三个索引键：
```
IndexedKeys:  # on the AWS::BedrockAgentCore::Memory resource
  - Key: type  # seperate the kinds of records
    Type: STRING
  - Key: section  # which bed or area it describes
    Type: STRING
  - Key: plants  # what is growing there
    Type: STRINGLIST
```
每个条目都会命名一个键，该键必须与可过滤的索引键匹配，并将“extractionType”设置为“STRICTLY_CONSISTENT”（从事件传递）或“LLM_INFERRED”（从对话中提取）。对于推断的键，提取配置可以将值限制为固定列表。 Sprout 正是这样做的，因此两个写入路径都会创建相同的词汇表，并且过滤器意味着相同的事情，无论哪个部分创建了记录。

### 保持转弯并关闭循环

模型响应后，“server.py”会调用“CreateEvent”，同时由用户轮流和助理轮流轮流调用。这个新事件为提取策略提供了支持，从而丰富了下一次的长期存储。
```
memory.create_event(
    memoryId=MEMORY_ID,
    actorId=chat_id,
    sessionId=session_id,
    payload=[
        {'role': 'user', 'content': user_message},
        {'role': 'assistant', 'content': reply},
    ],
)  # feeds USER_PREFERENCE / SEMANTIC / SUMMARIZATION extraction; errors are logged, never fatal
```
*片段 3：持续转动，以便提取策略可以异步丰富长期记忆。*

提取是异步的，因此本次会议中提到的事实通常可以在以后的会议中检索。针对延迟进行设计：短期会话事件涵盖当前对话，长期记录涵盖之前的所有内容。

### 整合：个性化浇水计划

这是整个管道端到端工作的地方。通过几次对话，您可以用简单的语言对整个花园进行分类，一次一株植物。每次提及都会成为一个事件。提取策略将有关植物、其位置及其阳光照射的信息提取到“sprout/{chat_id}/long_term”中。今天早上，用户问了一个问题：“你还记得我花园里的其他植物吗？”检索将记录拉回，对它们进行排序，然后将它们放入系统提示符中。助手会回答用户的位置、阳光照射、床铺结构、土壤行为和植物库存，这些信息本身都没有出现。

图 2：Sprout 通过回忆储存的植物库存和生长条件回答了有关花园的问题

使用 Amazon EventBridge→Cron 路径上的调度程序技能，Sprout 还可以将该计划转变为主动提醒（“跳过草药，昨天的土壤仍然潮湿”），并在下雨或热浪来临时根据天气技能进行调整。

记忆和视觉也相互结合。当用户发送枯萎植物的照片时，图像会转到 Claude Sonnet 4.5，而系统提示仍然包含内存层所知道的所有内容。助手将照片与用户保存的库存中已有的墨西哥矮牵牛进行匹配，并根据上下文诊断枯萎压力，而不是分析匿名植物照片。

图 3：视觉和记忆协同工作。照片进入视觉模型，同时系统提示携带用户存储的花园环境

视觉模型并非绝对正确。在早期没有库存背景的交流中，同一种植物被自信地鉴定为牵牛花，一种具有类似喇叭形紫色花朵的物种。将视觉模型与用户自己存储的库存作为基础，将看似合理的猜测转变为正确的个性化诊断，这很好地说明了为什么记忆提高了准确性，而不仅仅是语气。

### 通过即时缓存保持较低的推理成本

在每个回合中注入内存会使系统提示变大，并且天真的实现会在每个请求上为这些令牌付费。 Amazon Bedrock 上的提示缓存解决了这个问题。助手构造其提示，以便稳定的前缀、角色和组装的内存块首先出现，易失性用户消息最后出现。 Bedrock 跨请求缓存已处理的前缀，因此会话中的重复轮流会跳过未更改部分的重新计算。对于受支持的模型，即时缓存可将成本降低高达 90%，将延迟降低高达 85%。

排序规则比任何单个设置都更重要：将稳定内容放在前面，将易失性内容放在最后，并保持内存块的内部排序确定性（前面的组装函数有助于实现），以便前缀在请求之间实际匹配。

## 基于 AgentCore 和 OpenClaw 的设计指南

Sprout 是一名助手，但其背后的决定具有普遍性。如果您要在此堆栈上构建自己的助手，则我们将在任何领域采用以下指南。

- **包装，不要分叉。** 使用瘦 HTTP 包装器使您的代理框架适应 AgentCore 容器合约，而不是修改框架。该合约很小，端口 8080，带有“/ping”和“/incalls”，并且包装器使您能够保持框架的升级路径。
- **在存储任何内容之前设计命名空间。** 内存命名空间是您的隔离边界。将用户 ID 设为唯一的可变段，并从您已经信任的渠道原生 ID 中选择它，例如聊天 ID。多租户设计最终会收到审核和删除请求。干净的命名空间方案使这两者变得微不足道。
- **将内存视为增强功能，而不是依赖项。** 应允许每个内存操作正常失败。检索失败应该产生无记忆的答案，而不阻塞回复。用户更容易原谅忘记的转变，而不是失败的转变。
- **按任务路由模型。** 对大容量文本使用快速、经济高效的模型，并为需要的转弯保留更强大的多模式模型。将模型 ID 保留在环境变量中，以便路由更改是配置，而不是代码。
- **缓存的顺序提示。** 首先稳定的角色和内存，最后是不稳定的用户输入，始终确定性排序。这一结构性习惯是大部分推理节省的来源。
- **规划提取延迟。** 长期记忆是异步提取的，因此不要承诺在同一会话中回忆新事实。让短期会话事件涵盖当前对话，长期记录涵盖之前的对话。
- **从第一天开始就制定预算。** 基于消耗的代理是便宜的，直到重试循环或健谈的用户否则。达到每月上限 80% 和 100% 的 AWS 预算警报不需要任何成本，并且可以尽早发现意外情况。
- **保持技能小而单一。** 技能应该做用户在句子中命名的一件事，例如检查天气或设置提醒。小技能可以独立测试、独立交换，并且易于模型正确选择。万能技能迫使模型猜测你指的是它的哪些行为。

## 种植你自己的

同一个花园，有两种种植方法：

- **单步启动堆栈：** CloudFormation 模板指向公共 Amazon Elastic Container Registry (Amazon ECR) 映像，因此它只部署 Telegram 机器人令牌。
- 构建您自己的：scripts/`deploy.sh` 脚本验证模板、构建您自己的 ARM64 映像并将其推送到您的私有 Amazon ECR 存储库、部署堆栈并注册 Telegram Webhook，以实现完全可定制的构建。

截至 2026 年 7 月，轻度个人使用费用约为每月 5-9 美元（大约 2 美元基础设施、1-3 美元俳句文本、2 美元十四行诗视觉），内置 AWS 预算会在您设置的上限的 80% 和 100% 时发出警报。

完整的源代码可在 [sample-agentcore-memory-openclaw GitHub 存储库](https://github.com/aws-samples/sample-agentcore-memory-openclaw) 中获取。

## 清理

完成实验后，将所有东西都拆掉，以避免持续产生费用。由于整个系统是一个 CloudFormation 堆栈，因此清理主要是一次删除：

- 删除 CloudFormation 堆栈。这将删除 AgentCore 运行时代理、API Gateway、Lambda 函数、Amazon EventBridge 计划以及关联的 AWS Identity and Access Management (IAM) 角色。
- 删除 AgentCore 内存存储（及其命名空间），以便不保留任何用户记录。
- 删除您推送到私有 ECR 存储库的所有图像，以及存储库本身（如果不再需要）。
- 如果您在堆栈外部创建了 AWS 预算警报，请删除 AWS 预算警报。
- 撤销 Telegram 的 webhook（或通过 BotFather 删除机器人），并在不再需要时撤销 Bedrock 模型访问权限。

## 结论

该解决方案的可重用核心是 Amazon Bedrock AgentCore 上的无服务器代理，具有技能系统和托管内存。 AgentCore 内存消除了构建自定义向量存储和提取管道的需要，同时让您完全控制代理记住和忘记的内容，基于消耗的计算加上提示缓存使真正个性化的助手每月只需几美元，OpenClaw 技能清单使整个模式可以跨域移植。个性化也更加复杂：用户交互越多，助手就越有用。

为了更进一步，从浇水提醒等单一领域开始，逐步扩大记忆范围，探索情景记忆，以便代理可以参考过去的特定对话（“上次我们讨论无花果树，你决定推迟施肥”），或者分叉[存储库](https://github.com/aws-samples/sample-agentcore-memory-openclaw)，交换你自己的角色和技能，并发展你需要的任何助手。
