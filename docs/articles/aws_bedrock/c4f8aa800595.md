## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 用 AgentCore 与 OpenClaw 构建上下文感知的 AI 助手

现成的 AI 助手能把单个问题答得很好，却在另一个维度上力有不逮：连续性。你今天问一个无状态的助手关于自己花园的事，它完全不知道你在三周前提到过那几张排水很快的抬高种植床，不知道你也只用有机肥，更不知道你的矮牵牛前阵子在热浪里过得有多挣扎。每一次对话都从零开始，重新交代上下文的负担全落在用户身上。

问题不在于回答的质量，而在于助手根本不记得你。本文展示如何用 [OpenClaw](https://openclaw.ai/)（一个开源的智能体式系统）构建一个持续积累上下文的个人助手，它运行在 AgentCore runtime 之上——AgentCore runtime 是 Amazon Bedrock AgentCore 的一项能力。AgentCore memory 同样是 Amazon Bedrock AgentCore 的一项能力，它把一次性的对话变成可长期留存的知识。你还会看到如何给这些记忆打上结构化元数据标签，从而检索出与当前问题真正相关的记录。

我们的贯穿示例是 Sprout，一个园艺助手，但这套架构与具体领域无关。换掉角色设定和技能清单，同一条流水线就能服务客服机器人、健身教练或内部帮助台。整个系统都装在一个 AWS CloudFormation 模板里，一条命令即可部署，按用量计费，轻度个人使用每月只需几美元。过程中我们也会分享一些设计准则，你可以直接用到自己在这套技术栈上构建的助手里。

## 方案概览

AgentCore 是一个平台，让你用任意框架或模型大规模地构建、连接和优化智能体。下图展示了端到端的请求流转：从 Telegram 的入站 webhook 进入 AgentCore runtime，以及支撑它的各项 AWS 服务。

图 1：Telegram webhook 与 Amazon EventBridge 定时计划调用的是同一个 AgentCore runtime 上的智能体，由它协调 OpenClaw gateway、AgentCore memory 和 Amazon Bedrock

两个入口汇聚到同一个智能体。Telegram 消息经 Amazon API Gateway 和一个 webhook AWS Lambda 函数进来；清晨浇水提醒这类定时任务则经 Amazon EventBridge Scheduler 和一个 cronjob Lambda 函数进来。两者都调用 AgentCore runtime 上的 `InvokeAgentRuntime` API，runtime 里一个轻量的 `server.py` 进程负责协调 OpenClaw gateway、AgentCore memory 和 Amazon Bedrock Converse API。Amazon Simple Storage Service (Amazon S3) 提供工作区存储，AWS Key Management Service (AWS KMS) 负责加密，AWS Secrets Manager 保管 bot token，Amazon CloudWatch 采集日志与指标。

## 前提条件

若要用 Launch Stack 按钮或 scripts/`deploy.sh`（见「自己种一个」一节）部署属于你自己的版本，你需要：

- Amazon Bedrock AgentCore 的访问权限，包括 AgentCore runtime 和 AgentCore memory。
- 已为你打算路由到的模型开通模型访问权限：文本用 Claude Haiku 4.5，视觉用 Claude Sonnet 4.5（或你账户中可用的等价模型）。
- 支持 `linux/arm64` 构建的 Docker，以及配置好的 AWS Command Line Interface (AWS CLI)。仅当你打算自行构建并推送镜像时才需要。
- 一个 Telegram bot token（向 BotFather 申请），作为助手的对外入口。
- 对智能体编排概念和 CloudFormation 有基本了解。

## 架构：跑在 AgentCore runtime 上的无服务器智能体

所有组件都放在一个 CloudFormation 模板里，启动不需要任何构建工具链。下面几节逐一说明其中几个承重的决策。

### AgentCore runtime：只为活跃算力付费

智能体跑在 AgentCore runtime 的一个容器里，而 AgentCore runtime 采用按用量计费。计费依据是你的智能体实际消耗的算力，不是墙上时钟意义上的在线时长，等待 I/O（比如等模型返回）的那段时间也不收钱。对一个短时间突发使用的个人助手来说，这就决定了每月约 $1–2 的基线成本，与一台常年在线、每月约 $35 的 Amazon Elastic Compute Cloud (Amazon EC2) 实例之间的差距。这些数字是截至 2026 年 7 月对轻度个人使用的估算。当前费率请参见 [AgentCore 定价](https://aws.amazon.com/bedrock/agentcore/pricing/)。

runtime 强制一个极简的容器契约：监听 8080 端口，暴露 `GET /ping` 做健康检查，并以 `POST /invocations` 作为智能体入口。我们的容器是 `linux/arm64`，采用多阶段构建，在官方 OpenClaw 镜像之上再加一层 Python。

### OpenClaw 作为智能体的底座

OpenClaw 提供智能体循环、工具调用和技能系统。它由一个包装层（`server.py`）适配到 [AgentCore HTTP 协议契约](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-http-protocol-contract.html)：

- 容器启动时，`server.py` 以子进程方式拉起 `openclaw gateway run`，并对其进行健康检查。
- `GET /ping` 很快返回健康状态，让 AgentCore 的就绪探针得以通过。
- `POST /invocations` 干的是真正的活：解析请求负载、检索记忆、拼装上下文、把这一轮对话转发给 gateway，再把结果持久化。有一点要特别提醒：AgentCore 可以解冻一个子进程已经退出的冻结容器。所以调用路径并不假设 gateway 还活着，它会先调用 `ensure_openclaw_ready()` 辅助函数重新做一次健康检查（必要时重启 gateway），然后才转发这一轮对话。

这种包装层模式可以推广到其他场景。任何能以本地进程运行的智能体框架，都能用同样的方式适配到 AgentCore runtime，无需改动框架本身。

### 两个模型，按任务分流

文本对话和图像理解在成本与质量上的权衡不同，因此助手把它们分流到 [Bedrock](https://aws.amazon.com/bedrock/) 上不同的 Claude 模型：

- **文本用 Claude Haiku 4.5：** 日常使用中占绝大多数的对话轮次量大，用它又快又便宜。
- **视觉用 Claude Sonnet 4.5：** 从照片诊断植物不那么频繁但更难，需要更强的多模态推理。

文本轮次经过 OpenClaw gateway，由它带上技能和会话状态。图像轮次则由 `server.py` 直接调用 Bedrock 上的大语言模型 (LLM)，把图像字节作为多模态内容块传进去。我们刻意让图像绕开 gateway：容器内的 OpenClaw 构建会在 `image_url` 内容部分到达 Bedrock 之前把它丢弃，所以从 `server.py` 直接调用 Converse API 才能确保模型看到真正的像素。两条路径共用同一套系统提示（角色设定加记忆），体验因此保持一致。

模型 ID 是环境变量（`MODEL_ID`、`VISION_MODEL_ID`），所以可以按部署切换模型，不必重新构建镜像。

### 技能：可复用的能力单元

各项能力以技能的形式声明在 `community-skills.json` 清单里。部署阶段的脚本会在镜像构建之前把它们实体化到容器内，并注册进 OpenClaw 配置。本文发布时，Sprout 自带天气、提醒和植物笔记三个技能。换掉清单，同一条流水线就能服务另一个领域。这正是整套东西成为一种可复用模式、而不只是某一个 bot 的原因。

### Telegram 作为无服务器的门面入口

对个人助手来说 Telegram 是个务实的渠道，因为它基于 webhook，整套东西都能保持无服务器。不需要开发客户端，在用户已有的任何设备上都能用，还通过一套直白的 bot API 支持文本、图像和富格式。BotFather 签发一个 bot token，存放在 Secrets Manager 里。部署时注册一个 webhook，把 Telegram 指向 API Gateway 端点。用户发出消息后，Telegram 把它投递给 webhook Lambda 函数，由该函数校验负载并调用 `InvokeAgentRuntime`。回复再经 Telegram bot API 送回。

有一条排版的教训值得记下：Telegram 旧版 markdown 模型对未转义字符毫不宽容，模型回复里多出一个下划线，整条消息就可能发不出去。把回复渲染成 HTML 更可靠，因此助手在发送前会把模型输出转换成对 Telegram 安全的 HTML。

## 记忆：把一次性对话变成持久知识

到目前为止描述的架构是一个能干、便宜、无服务器的智能体，但单靠它，两次对话之间依然会把你忘掉。记忆改变的正是这一点。设想你几周前顺口提过自己做有机园艺，今天助手推荐了一种处理方案，并主动补充说选有机的那一项是因为你不用合成肥料。无状态的模型做不到这个。

### 心智模型：短期事件，长期抽取

AgentCore memory 分两层。**短期记忆**通过 `CreateEvent` 把每一个对话轮次存成一个事件，以 `actorId`（也就是 Telegram chat ID）和 `sessionId` 作为键，这就是原始逐字记录。**长期记忆由托管的抽取策略异步生成**，产出可长期留存的结构化记录。我们配置了三种策略：

- `USER_PREFERENCE`：园丁明确说出的选择（「我只用有机肥」）。
- `SEMANTIC`：推断出的事实（「在耐候钢抬高种植床里种墨西哥矮牵牛」）。
- `SUMMARIZATION`：情景式会话摘要（「讨论过热浪期间下部叶片发黄」）。

### 命名空间：一位园丁一座花园

Sprout 把记录归档到按用户划分的命名空间里，因此任意两个聊天都不会混在一起：

- `sprout/{chat_id}/long_term`：偏好与语义事实。
- `sprout/{chat_id}/episodic/{session_id}`：会话摘要。

chat ID 是唯一可变的片段，这让隔离既容易推理也容易测试：每一位园丁恰好对应一个命名空间，两位园丁之间不会相撞。

### 检索、拼装与注入流水线

每一轮，智能体都会检索相关的长期记录、对其排序，然后注入系统提示。`server.py` 里每一条消息都会发生下面这些：

- **检索。** 针对 `sprout/{chat_id}/long_term` 调用 `RetrieveMemoryRecords`，用用户消息作为检索查询，结果上限 50 条，时间预算 3 秒。检索超时或报错时我们优雅降级，不带记忆照样回答，而不是失败。

```
try:
    records = memory_client.retrieve_memory_records(
        memoryId=MEMORY_ID,
        namespace=f'sprout/{chat_id}/long_term',
        searchCriteria={
            'searchQuery': user_message,
            'topK': 50,
            'metadataFilters': []
        },
    )  # 3s timeout
except Exception:
    records = []  # fall back to answering without memory
```

*片段 1：为当前轮次检索长期记录（示意代码，完整源码见仓库）。*

拼装函数在这之上加了一层自定义逻辑。我们要求显式偏好排在推断事实之前，同一类内部的顺序保持稳定，并且在注入前对结果数量设上限：

```
def assemble(records, cap=50):
    explicit = [r for r in records if r.type == 'USER_PREFERENCE']
    inferred = [r for r in records if r.type != 'USER_PREFERENCE']
    # explicit beats inferred; stable order within each class
    ordered = explicit + inferred
    return ordered[:cap]
```

*片段 2：拼装步骤把显式偏好排在推断事实之前。*

### 元数据：在命名空间内部再分组

命名空间回答的是「这条记录是谁的记忆」，元数据回答的则是「它是关于什么的」。在 `sprout/{chat_id}/long_term` 里，用「我的矮牵牛蔫了」做语义检索，会把所有语义上相近的结果都返回来。对一位园丁来说，这意味着三月的一条肥料偏好、一条无花果修剪笔记，会和真正相关的记录排在一起。结构化元数据能帮我们在记忆进入提示之前先把范围收窄。

这里有一条规则决定了所有取舍：元数据的键必须先声明为索引键，服务端才能按它过滤。更多细节见 [在 Amazon Bedrock AgentCore Memory 中用元数据做结构化记忆过滤](https://aws.amazon.com/blogs/machine-learning/structured-memory-filtering-with-metadata-in-agentcore-memory/)。本项目中，Sprout 用了三个索引键：

```
IndexedKeys:  # on the AWS::BedrockAgentCore::Memory resource
  - Key: type  # seperate the kinds of records
    Type: STRING
  - Key: section  # which bed or area it describes
    Type: STRING
  - Key: plants  # what is growing there
    Type: STRINGLIST
```

每个条目都指定一个键——要和某个索引键对应上才可被过滤——并把 `extractionType` 设为 `STRICTLY_CONSISTENT`（从事件原样透传）或 `LLM_INFERRED`（从对话中抽取）。对于推断类的键，抽取配置可以把取值限定在一个固定列表内。Sprout 正是这么做的，于是两条写入路径产出同一套词表，同一个过滤器不管记录由哪一侧创建，含义都相同。

### 持久化本轮对话，闭合循环

模型回复之后，`server.py` 调用 `CreateEvent`，同时写入用户轮次和助手轮次。这个新事件喂给抽取策略，为下一次把长期存储充实起来。

```
memory.create_event(
    memoryId=MEMORY_ID,
    actorId=chat_id,
    sessionId=session_id,
    payload=[
        {'role': 'user', 'content': user_message},
        {'role': 'assistant', 'content': reply},
    ],
)  # feeds USER_PREFERENCE / SEMANTIC / SUMMARIZATION extraction; errors are logged, never fatal
```

*片段 3：持久化本轮对话，让抽取策略能够异步地充实长期记忆。*

抽取是异步的，所以本次会话里提到的事实，通常要等到之后某次会话才检索得到。设计上要容忍这个延迟：短期会话事件覆盖当前这次对话，长期记录覆盖此前的一切。

### 串起来：一份个性化的浇水计划

这就是完整流水线端到端跑通的地方。几次对话下来，你用平实的语言，一株一株地把整座花园登记在册。每一次提及都成为一个事件。抽取策略把植物的信息、它的位置、它的日照情况抽进 `sprout/{chat_id}/long_term`。今天早上用户问了一句：「你还记得我花园里的其他植物吗？」检索把记录捞回来，拼装把它们排好序，随后一同进入系统提示。助手答出了用户的位置、日照、种植床构造、土壤特性和植物清单，而这些内容没有一个出现在消息本身里。

图 2：Sprout 通过回忆已存储的植物清单和生长条件，回答关于花园的问题

借助 Amazon EventBridge → Cron 这条路径上的 scheduler 技能，Sprout 还能把这份计划变成主动提醒（「香草先别浇，昨天的土还湿着」），并在降雨或热浪来临前结合天气技能对其做出调整。

记忆和视觉还会彼此放大。用户发来一张蔫掉的植物照片时，图像交给 Claude Sonnet 4.5，而系统提示里仍然带着记忆层知道的全部信息。助手把照片对应用户已存清单里的那株墨西哥矮牵牛，在有上下文的情况下诊断萎蔫胁迫，而不是冷冰冰地分析一张来路不明的植物照片。

图 3：视觉与记忆协同工作。照片交给视觉模型，系统提示则带着用户已存储的花园上下文

视觉模型并非不会出错。在早前一轮没有清单上下文的交流中，同一株植物被自信地认定成牵牛花——一个开着相似喇叭状紫花的物种。把用户自己存下的清单作为视觉模型的接地依据，正是让「听着合理的猜测」变成「正确的、个性化的诊断」的关键，也很好地说明了记忆提升的是准确率，而不只是语气。

### 用提示缓存把推理成本压下来

每一轮都注入记忆会让系统提示变大，朴素的实现会为每次请求都付出这些 token 的成本。Amazon Bedrock 的提示缓存正是解决这个问题的。助手组织提示的方式是：稳定的前缀——角色设定和拼装好的记忆块——放在最前面，易变的用户消息放在最后。Bedrock 会跨请求缓存已处理的前缀，于是同一次会话里的重复轮次可以跳过对未变化部分的重新计算。对支持的模型，提示缓存最多能把成本降低 90%、延迟降低 85%。

排序这条规则比任何单个配置都重要：稳定内容在前、易变内容在后，记忆块内部的顺序必须是确定的（前面那个拼装函数正是为此准备的），这样前缀在请求之间才真能匹配上。

## 在 AgentCore 与 OpenClaw 上做设计时要遵循的准则

Sprout 只是一个助手，但它背后的决策是可以推广的。如果你要在这套技术栈上构建自己的助手，下面这些准则是我们会带到任何领域去的部分。

- **包装，而不是分叉。** 用一个轻量的 HTTP 包装层把你的智能体框架适配到 AgentCore 容器契约，而不是去改框架。契约很小：8080 端口加上 `/ping` 和 `/invocations`；用包装层，你就还走在框架自己的升级路径上。
- **先设计命名空间，再存任何东西。** 记忆命名空间就是你的隔离边界。让用户 ID 成为唯一的可变片段，并且从一个你已经信任的、渠道原生的 ID 里取，比如 chat ID。多租户设计迟早都要面对审计和删除请求，一套干净的命名空间方案会让这两件事都变得很轻松。
- **把记忆当增强，绝不当依赖。** 每个记忆操作都应允许优雅失败。检索失败时应当产出一个不带记忆的回答，而不是阻塞回复。用户能原谅一次「忘了」的轮次，却很难原谅一次失败的轮次。
- **按任务路由模型。** 高频文本用快而省钱的模型，把更强的多模态模型留给真正需要的轮次。模型 ID 放在环境变量里，路由变更就是配置改动，不是代码改动。
- **为缓存安排提示的顺序。** 稳定的角色设定和记忆在前，易变的用户输入在后，全程顺序确定。推理开销的节省，大头就来自这一条结构性习惯。
- **为抽取延迟留出预期。** 长期记忆是异步抽取的，所以不要承诺新事实能在同一会话里被回忆起来。让短期会话事件覆盖当前对话，长期记录覆盖此前的对话。
- **从第一天起就设预算。** 按用量计费的智能体本来很便宜，直到某个重试循环或一个话多的用户把它变贵。在月度上限的 80% 和 100% 各设一条 AWS Budgets 告警不花钱，却能早早发现意外。
- **技能要小而单一。** 一个技能应该只做一件用户一句话就能说清的事，比如查天气、设提醒。小技能可以独立测试、独立替换，模型也更容易选对。什么都做的技能会迫使模型去猜你要的到底是它哪一种行为。

## 自己种一个

两种种法，同一座花园：

- **一步到位的 Launch Stack：** CloudFormation 模板指向一个公开的 Amazon Elastic Container Registry (Amazon ECR) 镜像，所以部署时除了一个 Telegram bot token 什么都不用提供。
- 自己构建：scripts/`deploy.sh` 脚本会校验模板、构建你自己的 ARM64 镜像并推送到你的私有 Amazon ECR 仓库、部署 stack，并注册 Telegram webhook，得到一个完全可定制的构建。

截至 2026 年 7 月，轻度个人使用大约每月 $5–9（其中基础设施约 $2，Haiku 文本 $1–3，Sonnet 视觉约 $2），并且内置一个 AWS Budget，在你自设上限的 80% 和 100% 处发出告警。

完整源码见 [sample-agentcore-memory-openclaw GitHub 仓库](https://github.com/aws-samples/sample-agentcore-memory-openclaw)。

## 清理

实验结束后把所有东西拆掉，以免持续产生费用。因为整套系统就是一个 CloudFormation stack，清理基本就是一条删除操作：

- 删除 CloudFormation stack。这会一并移除 AgentCore runtime 智能体、API Gateway、各 Lambda 函数、Amazon EventBridge 定时计划，以及相关的 AWS Identity and Access Management (IAM) 角色。
- 删除 AgentCore memory 存储（连同其命名空间），以免留存任何用户记录。
- 删除你推送到私有 ECR 仓库的所有镜像，如果不再需要，把仓库本身也删掉。
- 如果你在 stack 之外创建了 AWS Budget 告警，把它移除。
- 撤销 Telegram 的 webhook（或通过 BotFather 删除这个 bot），并在不再需要时撤销 Bedrock 的模型访问权限。

## 结论

这套方案可复用的内核，是一个跑在 Amazon Bedrock AgentCore 上的无服务器智能体，配上技能系统和托管记忆。AgentCore memory 免去了自建向量存储和抽取流水线的需要，同时让你对智能体记住什么、忘掉什么保有完全控制；按用量计费的算力加上提示缓存，把一个真正个性化的助手压在每月几美元；OpenClaw 的技能清单则让整套模式可以跨领域迁移。个性化还会复利累积：用户交互越多，助手就越好用。

想继续往前走，可以先从一个单一领域入手，比如浇水提醒，再逐步扩大记忆范围；可以试试情景记忆，让智能体能引用具体的过往对话（「上次我们讨论无花果时，你决定先不施肥」）；也可以 fork 那个[仓库](https://github.com/aws-samples/sample-agentcore-memory-openclaw)，换上你自己的角色设定和技能，种出你需要的任何助手。
