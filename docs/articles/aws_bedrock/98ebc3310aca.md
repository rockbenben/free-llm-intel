# 在 Amazon Bedrock 托管知识库上使用 Agentic Retrieve 构建内存感知 AI 代理

基于知识的应用程序的用户希望它能够记住它们，而不仅仅是很好地搜索。他们提出仅在上一回合的背景下才有意义的后续问题。他们希望有关政策或程序的答案能够反映他们上个月向应用程序透露的有关自己的信息。他们仍然希望每个答案都以他们被允许阅读的文件为基础，并附有引用。无论应用程序是客户支持助理、SaaS 产品内的文档聊天，还是公司政策的内部助理，期望都是相同的。

满足这种期望是很困难的，因为能够锐化搜索的上下文存在于知识库之外。用户的位置、角色或产品等级经常在几周前的一次不相关的对话中被提及。要使用它，应用程序必须存储每个对话，从中提取持久的事实，确定哪些事实对当前问题重要，并将它们注入到请求中。当许多用户共享应用程序时，每个步骤都必须针对每个用户进行隔离，每个文档也是如此。

[Amazon Bedrock 托管知识库](https://aws.amazon.com/bedrock/knowledge-bases/) 和 [Amazon Bedrock AgentCore 内存，Amazon Bedrock AgentCore 的一项功能](https://aws.amazon.com/bedrock/agentcore/)，现在接管以下步骤：存储每个对话，从中提取事实，并将相关事实引入搜索。您可以通过将“memoryConfiguration”添加到“AgenticRetrieveStream”请求来打开此功能，这使得 AgentCore 内存与您的知识库一起成为检索源。在同一次通话中，服务恢复对话，规划者自行决定何时有关用户的事实会有所帮助。它从长期记忆中检索该事实，并使用它来组成发送到知识库的子查询。生成答案后，服务会将转弯保存回内存中。同一请求携带“userContext”，因此知识库仅返回用户访问控制列表（ACL）允许的文档。该集成是选择性加入且向后兼容的。您的应用程序仅保留真正属于您的内容：验证用户身份并传递他们的身份。

这篇文章展示了如何为共享一个知识库和一个内存资源的许多用户构建这样一个助手。每个用户只能看到他们可以阅读的文档，并且每个用户的内存都是私有的。运行的示例是 AnyCompany（一家虚构公司）的内部员工助理。员工使用 Amazon Cognito 登录并提出有关 HR 政策、IT 指南、工程操作手册和销售计划的问题。我们展示了如何从 Cognito ID 令牌读取用户的身份，如何将其传递给文档 ACL 和内存的“AgenticRetrieveStream”，如何为许多用户设计内存命名空间，以及如何读取跟踪以查看规划器何时使用内存。最后，我们让 AWS Identity and Access Management (IAM) 强制执行每用户内存隔离，即使应用程序代码出现错误也是如此。如果您从[使用 Amazon Bedrock 托管知识库在企业数据上构建多租户代理聊天应用程序](https://aws.amazon.com/blogs/machine-learning/build-multi-tenant-agentic-chat-applications-on-enterprise-data-with-amazon-bedrock-management-knowledge-base/) 部署应用程序，则本文将替换其“自行保留对话历史记录”步骤。

## 解决方案概述

AnyCompany 将其文档保存在 Amazon Simple Storage Service (Amazon S3) 中。一个托管知识库通过支持 ACL 的 Amazon S3 数据源同步它们。同一存储桶中的全局 ACL 文件规定了哪些员工可以阅读每个文件夹：每个人都阅读 HR 和 IT，只有工程师阅读工程操作手册，只有销售人员阅读佣金计划。每个员工共享一个 AgentCore 内存资源。 Amazon Cognito 对员工进行身份验证，其 ID 令牌提供两个声明：“sub”（用户 ID）标识用户的内存，经过验证的“电子邮件”向知识库的 ACL 过滤器标识用户。三名测试用户登录：两名工程师 Maya 和 Liam，以及一名销售人员 Sofia。本文中的跟踪摘录取自 [GitHub 存储库](https://github.com/aws-samples/sample-management-knowledge-base-patterns/tree/main/agentcore-memory-multiuser) 中示例应用程序的运行。

![内存感知员工助理的架构：应用程序、AgenticRetrieveStream、托管知识库和 AgentCore 内存](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/13/ML-21969-1.png)

图 1：内存感知员工助理的架构。应用程序对用户进行身份验证并构造请求（步骤 1-4）。 Amazon Bedrock 托管知识库恢复会话、检索信息、返回答案，并将交换保存到 AgentCore 内存（步骤 5-8）。短期事件和长期记录属于相同的内存资源。

- 员工使用 Cognito 登录并收到 ID 令牌，即由用户池签名的 JSON Web 令牌 (JWT)。
- 应用程序的 API 验证令牌 - 生产中的 Amazon API Gateway JWT 授权方，示例中的小型 FastAPI 服务。未经身份验证的请求不会到达处理程序。
- 处理程序从已验证的令牌中读取两个声明：“sub”成为内存“actorId”和命名空间，“email”成为“userContext.userId”。客户端主体仅包含“{question, sessionId? }`。然后，处理程序会使用会话标签“userId=<sub>”为该用户承担应用程序的 IAM 角色。
- 处理程序使用知识库作为检索器、“userContext”和绑定到该用户的“memoryConfiguration”来调用“AgenticRetrieveStream”。
- 托管知识库从 AgentCore 内存中的短期记忆 (STM) 中恢复由“sessionBinding”标识的参与者和会话的对话历史记录。
- 托管知识库通过基于“userContext”的 ACL 过滤从知识库中检索。它还可以通过推测检索或规划者选择的记忆搜索来检索用户配置的长期记忆。
- 托管知识库将引用的答案和跟踪事件流式传输回处理程序。处理程序使用相关 ID 记录跟踪，并将答案和跟踪信息转发到 UI。
- 使用“persistenceMode: DEFAULT”，服务将问题和生成的答案保存到会话中。然后AgentCore内存根据配置的策略异步提取长期记录。

*图 2：一个“AgenticRetrieveStream”轮与“userContext”和“memoryConfiguration”。第一个和最后一个箭头之间的所有内容都是服务的工作。*

托管知识库拥有摄取、ACL 过滤、索引、排名、规划、检索和生成。通过“memoryConfiguration”，它还拥有会话恢复、内存搜索和持久性。 AgentCore 内存拥有存储、保留、加密和提取功能。您的应用程序拥有身份验证、UI 并从令牌中读取用户身份。没有对话表：当 UI 列出或重新打开对话时，它会读取相同的内存资源。

### 身份如何映射到请求

每个值均由应用程序从经过验证的 ID 令牌派生。没有一个来自请求正文。

| **请求字段** | **源自** | **它的范围** | **执行者** |
| --- | --- | --- | --- |
| `userContext.userId` | ID 令牌“email”（已验证，在池中不可变）|哪些文件可以检索 |知识库ACL过滤|
| `memoryConfiguration.sessionBinding.actorId` | ID 令牌 `sub` |谁的短期记忆被恢复并写入，以及长期命名空间中的`{actorId}` | AgentCore 内存键控，加上 IAM 条件 |
| `memoryConfiguration.sessionBinding.sessionId` |由应用程序为新对话生成。与“ListSessions”一起列出 |那个演员的对话 |在“actorId”下键入 |
| `memoryConfiguration.retrievalConfigs[0].namespacePath` | `/anycompany/<sub>` |规划者可以搜索哪些长期记录 | IAM 条件 |

两种不同的主张有两种不同的作用。知识库通过电子邮件识别用户，因为这是连接的数据源在其 ACL 中记录的内容。内存需要一个永远不会改变并且永远不会被重用的“actorId”。 Cognito ‘sub’ 两者兼而有之。电子邮件地址可以更改，或者在某人离开后重新分配给新员工，然后该人将继承旧的记忆。您可以使用您自己的用户存储中的另一个稳定用户 ID 作为“actorId”。重要的是它永远不会转移到另一个人身上。

## 先决条件

- 本演练使用美国西部（俄勒冈）区域 (us-west-2) 中的托管知识库和 AgentCore 内存资源。如[代理检索文档](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html)中所述，此集成使用的内存资源必须与知识库位于同一 AWS 账户中，并且处于“ACTIVE”状态。
- Python 3.10 或更高版本和 Boto3 1.43.72 或更高版本。
- 创建 S3 存储桶、Cognito 用户池、IAM 角色、知识库和内存资源的权限。该示例的“infra/setup.py”以幂等方式创建所有这些资源。

## 解决方案演练

以下步骤创建知识库及其数据源、设置内存资源和 Amazon Cognito、构建请求并读取跟踪以确认结果。

### 步骤 1：使用启用 ACL 的数据源创建知识库

托管知识库不需要向量存储：

按照[为托管 Amazon Bedrock 知识库创建服务角色](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-management-permissions.html) 为您的设置配置服务角色，并在 `roleArn` 中传递其 ARN。有关模型访问要求，另请查看[托管和自定义模型的先决条件](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-management-prereqs.html)。
```
kb = agent.create_knowledge_base(
    name="anycompany-assistant-docs",
    description="AnyCompany internal documents: HR policies, IT guides, engineering runbooks, sales plans.",
    roleArn=kb_service_role_arn,
    knowledgeBaseConfiguration={
        "type": "MANAGED",
        "managedKnowledgeBaseConfiguration": {"embeddingModelType": "MANAGED"},
    },
)["knowledgeBase"]
```
文档位于 `docs/<folder>/` 下的存储桶中。 Amazon S3 没有自己的爬网权限系统，因此您可以在同一存储桶中的全局 ACL 文件中提供 ACL。每个条目都会将 S3 前缀映射到可能读取它的电子邮件：
```
[
  {"keyPrefix": "s3://BUCKET/docs/hr/",
   "aclEntries": [{"Name": "maya@example.com",  "Type": "USER", "Access": "ALLOW"},
                  {"Name": "liam@example.com",  "Type": "USER", "Access": "ALLOW"},
                  {"Name": "sofia@example.com", "Type": "USER", "Access": "ALLOW"}]},
  {"keyPrefix": "s3://BUCKET/docs/engineering/",
   "aclEntries": [{"Name": "maya@example.com",  "Type": "USER", "Access": "ALLOW"},
                  {"Name": "liam@example.com",  "Type": "USER", "Access": "ALLOW"}]},
  {"keyPrefix": "s3://BUCKET/docs/sales/",
   "aclEntries": [{"Name": "sofia@example.com", "Type": "USER", "Access": "ALLOW"}]}
]
```
该示例的文件还为每个人提供了“docs/it/”。然后创建数据源。对于托管知识库，每个连接器都具有类型“MANAGED_KNOWLEDGE_BASE_CONNECTOR”，并且“connectorParameters.type”选择源：
```
ds = agent.create_data_source(
    knowledgeBaseId=kb["knowledgeBaseId"],
    name="s3-docs-acl",
    dataSourceConfiguration={
        "type": "MANAGED_KNOWLEDGE_BASE_CONNECTOR",
        "managedKnowledgeBaseConnectorConfiguration": {
            "connectorParameters": {
                "type": "S3",
                "version": "1",
                "connectionConfiguration": {"bucketName": BUCKET, "bucketOwnerAccountId": ACCOUNT_ID},
                "filterConfiguration": {"inclusionPrefixes": ["docs/"]},
                "aclEnabled": True,
                "aclConfiguration": {"globalAccessControlListS3Uri": f"s3://{BUCKET}/acl/global-acl.json"},
            }
        },
    },
)["dataSource"]
```
创建数据源后，无法更改“aclEnabled”。 `CreateDataSource` 是异步的，因此请等待状态 `AVAILABLE`。然后调用“StartIngestionJob”并等待“COMPLETE”。同步读取文档和 ACL 文件，并使用其 ACL 为每个文档建立索引。在示例中，对所有 11 个文档进行了扫描和索引，失败次数为 0。没有 ACL 条目涵盖的文档不会被提取，并且电子邮件与任何条目不匹配的用户不会收到来自此数据源的结果。

相同的模型适用于从源系统爬取权​​限的连接器，例如 Microsoft SharePoint、Google Drive 和 Atlassian Confluence。在那里，权限来自源，组从源解析，知识库还根据源实时检查每个结果。您的应用程序代码不会更改：它仍然在“userContext”中传递用户的电子邮件。有关完整列表，请参阅[访问控制列表感知启用](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-management-acl.html)。

### 步骤 2：创建内存资源并设计命名空间

一种内存资源服务于每个用户。每用户分离来自命名空间模板中的“{actorId}”，AgentCore 内存在提取时从每个事件中解析该模板。两个选择很重要。

[策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/built-in-strategies.html)。这两种策略提取出不同的东西。摘要策略总结了每个对话，因此它捕获了用户顺便提及的事实，例如“我在法兰克福办公室使用 Mac”。这些事实是后来关于 PTO 等问题的个性化回答的依据。用户偏好策略将陈述的偏好提取到结构化记录中（“偏好没有表格的简短要点答案”、“始终首先部署到 eu-central-1”），并且不会将偶然提及的偏好视为偏好。摘要为您提供“我们讨论的内容”。偏好会告诉你“这个人希望如何得到回答”。两者都用。

布局。 `retrievalConfigs` 接受一个条目，因此单个 `namespacePath` 必须到达规划器应该为用户看到的所有内容。将 `{actorId}` 直接放在根目录下： `namespacePath: "/anycompany/<sub>"` 然后覆盖个人资料和每个对话摘要。诸如“/anycompany/profile/{actorId}”和“/anycompany/summaries/{actorId}”之类的布局只会让一个条目到达其中之一。
```
memory = control.create_memory(
    name="anycompany_assistant_memory",
    eventExpiryDuration=30,          # days; raw conversation events expire after this
    # encryptionKeyArn=CMK_ARN,      # optional customer managed key
    memoryStrategies=[
        {"userPreferenceMemoryStrategy": {
            "name": "EmployeeProfile",
            "namespaces": ["/anycompany/{actorId}/profile"],
        }},
        {"summaryMemoryStrategy": {
            "name": "ConversationSummaries",
            "namespaces": ["/anycompany/{actorId}/summaries/{sessionId}"],
        }},
    ],
)["memory"]
```
等待内存达到“ACTIVE”。创建内存不需要用户或“actorId”，因此步骤 2 和步骤 3 的顺序并不重要。没有为每个用户配置任何内容：新的 Cognito 用户在第一次提出问题时就成为新参与者。

### 步骤 3：设置 Cognito 并授予应用程序权限

创建一个用户池和一个没有客户端密钥的应用程序客户端。电子邮件决定用户可以阅读哪些文档，因此使其成为必需、经过验证且用户不可更改的文档：
```
pool_id = idp.create_user_pool(
    PoolName="anycompany-assistant-employees",
    AutoVerifiedAttributes=["email"],
    Schema=[{"Name": "email", "Required": True, "Mutable": False, "AttributeDataType": "String"}],
    AdminCreateUserConfig={"AllowAdminCreateUserOnly": True},
)["UserPool"]["Id"]
```
创建池后，“Mutable”将无法更改。通过可变电子邮件，登录用户可以将其电子邮件更改为同事的地址。如果您的用户从 Okta 或 Microsoft Entra ID 联合，请将 IdP 的电子邮件映射到此属性，以便它与数据源 ACL 中的电子邮件匹配。

该示例启用“USER_PASSWORD_AUTH”，以便本地 UI 和测试可以直接登录。生产应用程序通常使用 Cognito 托管登录或 AWS Amplify。

为应用程序设置 IAM 角色。后端假设每个用户一次，并使用会话标签“userId=<sub>”，并且每个内存语句都以该标签为条件。这是示例运行时使用的完整策略：
```
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "AgenticRetrieve", "Effect": "Allow",
      "Action": "bedrock:AgenticRetrieveStream", "Resource": "*" },
    { "Sid": "KnowledgeBaseRetrieval", "Effect": "Allow",
      "Action": ["bedrock:Retrieve", "bedrock:GetDocumentContent"],
      "Resource": "arn:aws:bedrock:us-west-2:111122223333:knowledge-base/KB_ID" },
    { "Sid": "PlannerAndGeneration", "Effect": "Allow",
      "Action": "bedrock:InvokeModelWithResponseStream", "Resource": "*" },
    { "Sid": "MemoryDescribe", "Effect": "Allow",
      "Action": "bedrock-agentcore:GetMemory",
      "Resource": "arn:aws:bedrock-agentcore:us-west-2:111122223333:memory/MEMORY_ID" },
    { "Sid": "MemorySessionsScopedToCaller", "Effect": "Allow",
      "Action": ["bedrock-agentcore:ListEvents", "bedrock-agentcore:CreateEvent",
                 "bedrock-agentcore:ListSessions"],
      "Resource": "arn:aws:bedrock-agentcore:us-west-2:111122223333:memory/MEMORY_ID",
      "Condition": {"StringEquals": {"bedrock-agentcore:actorId": "${aws:PrincipalTag/userId}"}} },
    { "Sid": "MemoryRecordsScopedToCaller", "Effect": "Allow",
      "Action": ["bedrock-agentcore:RetrieveMemoryRecords", "bedrock-agentcore:ListMemoryRecords"],
      "Resource": "arn:aws:bedrock-agentcore:us-west-2:111122223333:memory/MEMORY_ID",
      "Condition": {"StringLike": {"bedrock-agentcore:namespacePath": "/anycompany/${aws:PrincipalTag/userId}/*"}} }
  ]
}
```
当“persistenceMode”为“DEFAULT”时，“ListEvents”需要与“sessionBinding”配合使用，“RetrieveMemoryRecords”需要与“retrievalConfigs”配合使用，并且需要“CreateEvent”。 `ListSessions` 和 `ListMemoryRecords` 用于应用程序自己的读取（对话列表和“内存了解你的信息”视图），而不是用于 `AgenticRetrieveStream`。该角色的信任策略允许来自后端自己的身份（生产中的 AWS Lambda 执行角色或 Amazon Elastic Container Service (Amazon ECS) 任务角色）的 `sts:AssumeRole`、`sts:TagSession` 和 `sts:SetSourceIdentity`。如果内存使用客户管理的密钥，请在该密钥上添加“kms:Decrypt”。

### 步骤 4：从令牌中读取用户，然后构建请求

验证 ID 令牌并阅读两个声明。只有 ID 令牌带有“email”。访问令牌不会：
```
@dataclasses.dataclass(frozen=True)
class Principal:
    sub: str     # -> memory actorId and namespace
    email: str   # -> userContext.userId (document ACLs)

    def namespace_path(self, root: str) -> str:
        return f"{root}/{self.sub}"       # resolved literal, e.g. /anycompany/a8e1b390-...


def verify(id_token: str) -> Principal:
    key = jwks.get_signing_key_from_jwt(id_token)   # public keys from {issuer}/.well-known/jwks.json
    claims = jwt.decode(id_token, key.key, algorithms=["RS256"], issuer=ISSUER, audience=CLIENT_ID)
    if claims.get("token_use") != "id" or claims.get("email_verified") is not True:
        raise PermissionError("a verified ID token is required")
    return Principal(sub=claims["sub"], email=claims["email"].lower())
```
`jwt.decode` 检查签名、发行者（您的用户池）、到期日和受众（您的应用程序客户端）。有关声明的详细信息，请参阅[了解身份 (ID) 令牌](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-the-id-token.html)。使用 API Gateway，JWT 授权者会执行相同的检查并将声明传递给您的处理程序。

接下来，获取用户的 AWS 凭证。后端承担该用户的应用程序角色并缓存会话直到其过期前不久：
```
creds = sts.assume_role(
    RoleArn=APP_ROLE_ARN,
    RoleSessionName=f"user-{principal.sub}",
    SourceIdentity=principal.sub,
    Tags=[{"Key": "userId", "Value": principal.sub}],
)["Credentials"]
```
该用户的每次调用（包括代理检索代表调用者进行的内存调用）现在都以 `assumed-role/anycompany-assistant-app-role/user-<sub>` 的形式运行，并带有步骤 3 中策略检查的标签。

确定“sessionId”。对于新的对话，应用程序会生成一个对话，例如““conv-”+ uuid4().hex”，并将其返回给客户端。要继续对话，客户端将其发回。要向用户显示他们的对话，请使用用户的“actorId”调用“ListSessions”：
```
def list_conversations(principal):
    try:
        resp = memory.list_sessions(memoryId=MEMORY_ID, actorId=principal.sub, maxResults=50)
    except memory.exceptions.ResourceNotFoundException:
        return []   # the user has not asked anything yet, so there is no actor
    return [{"sessionId": s["sessionId"], "createdAt": s["createdAt"].isoformat()} for s in resp["sessionSummaries"]]
```
您不需要自己的表来将用户映射到会话。从客户端接受“sessionId”是安全的，因为短期记忆由“(memoryId, actorId, sessionId)”作为键控，而“actorId”来自令牌。如果 Liam 发送 Maya 的“sessionId”，它会在 Liam 自己的空间内命名一个会话，该空间是空的。代理检索本身不会验证您提供的“actorId”、“sessionId”或命名空间是否属于发出请求的用户，因此它们绝不能来自客户端。仅当您需要内存无法保存的数据（例如对话标题）时，才保留自己的会话表。

然后构建请求：
```
def build_request(principal, question, session_id):
    return {
        # With sessionBinding, messages carries ONLY the current question.
        "messages": [{"role": "user", "content": {"text": question}}],
        "retrievers": [{"configuration": {"knowledgeBase": {"knowledgeBaseId": KB_ID}},
                        "description": KB_DESCRIPTION}],
        # Document ACLs: only documents this email may read are retrieved.
        "userContext": {"userId": principal.email},
        "agenticRetrieveConfiguration": {
            "foundationModelType": "MANAGED",
            "rerankingModelType": "MANAGED",
            "maxAgentIteration": 3,
        },
        "generateResponse": True,
        "memoryConfiguration": {
            "memoryId": MEMORY_ID,
            "sessionBinding": {"actorId": principal.sub, "sessionId": session_id},
            "persistenceMode": "DEFAULT",
            "retrievalConfigs": [{"namespacePath": principal.namespace_path("/anycompany")}],
        },
    }
```
如果没有“userContext”，启用 ACL 的数据源根本不会返回任何结果。将请求与其替换的无状态处理程序进行比较：
```
history = history_table.query(KeyConditionExpression=Key("sessionId").eq(session_id))
messages = [*replay(history), {"role": "user", "content": {"text": question}}]
response = runtime.agentic_retrieve_stream(messages=messages, retrievers=..., agenticRetrieveConfiguration=...)
history_table.put_item(Item={"sessionId": session_id, "q": question, "a": consume(response)})
```
调用前的查询和调用后的写入都消失了，“messages”只有一个元素。 “sessionBinding”附带三个规则，每个规则都通过特定的“ValidationException”强制执行。首先，“messages”仅包含当前问题，因此您可以为每个请求选择一个历史源。其次，“persistenceMode: DEFAULT”（默认）将问题和生成的答案作为一个事件写入，因此需要“generateResponse: true”。第三，单独使用“memoryId”是无效的。 `persistenceMode: NONE` 恢复历史记录并且不写入任何内容，以供审核或重播视图。

### 步骤 5：更新客户端合约和渲染历史记录

客户端发送`{问题，sessionId？ }`。在新对话中，应用程序生成一个“sessionId”并将其作为第一个流帧返回。客户端在稍后的回合中回显它并忽略它以重新开始。

因为内存资源是你的，所以应用程序直接读取它来渲染对话：
```
def conversation_history(principal, session_id):
    resp = memory.list_events(memoryId=MEMORY_ID, actorId=principal.sub, sessionId=session_id,
                              includePayloads=True, maxResults=100)
    return [{"role": p["conversational"]["role"].lower(), "text": p["conversational"]["content"]["text"]}
            for ev in sorted(resp["events"], key=lambda e: e["eventTimestamp"])
            for p in ev["payload"] if "conversational" in p]
```
每个持续的回合都是一个具有两个有效负载的事件：用户的问题和最终答案。因此，历史记录会呈现为干净的记录，并可供其他 AgentCore 内存客户端使用。

### 步骤 6：从跟踪中验证

跟踪每轮都会告诉您知识库和内存做了什么：

| **跟踪事件** | **当它出现时** | **看什么** |
| --- | --- | --- |
| `SessionHistoryLoad` |每当设置“sessionBinding”时第一个事件 | `_memory_event_count` 和 `_memory_message_count`，在新会话中均为 0 |
| `推测检索` |规划前|在新会话中，“retrievalMetadata”还列出了“BedrockAgentCoreMemory”。内存项携带“_memory_*”元数据，但不包含文本。知识库项目带有 `_source_uri` |
| `计划` |每次迭代 | `actions[].memoryRetrieve` 表示规划器选择搜索内存，并使用它组成的查询 |
|具有“retrievalType: BedrockAgentCoreMemory”的“Retrieval” |按计划的记忆动作| `_内存_记录_计数`。计数为 0 是正常结果 |
|具有“状态：失败”的内存事件 |内存不可用或访问被拒绝 | `失败[].消息`。尽力记忆：请求继续，从知识库中生成答案 |

## 安全和多用户隔离

**在本演练中，应用程序进行身份验证。知识库过滤器。** ACL 感知检索是过滤，而不是授权。仅从带有“email_verified: true”的已验证 ID 令牌中获取电子邮件，使其在池中不可变，并处理电子邮件重用：如果将地址重新分配给其他人，则该人将获得旧所有者的文档访问权限。知识库无法关闭：没有 ACL 或 ACL 错误的文档意味着更少的结果，而不是额外的结果。如果结果丢失，请检查电子邮件是否与 ACL 条目匹配。

**身份也来自内存的令牌**（第 4 步）：“actorId”和命名空间来自经过验证的“sub”，而不是来自客户端。

**IAM 条件键，作为深度防御。** AgentCore 内存在“ListEvents”、“CreateEvent”和“ListSessions”上公开“bedrock-agentcore:actorId”，在“RetrieveMemoryRecords”和“ListMemoryRecords”上公开“bedrock-agentcore:namespacePath”。代理检索在请求期间进行的内存调用是根据调用身份进行授权的。这就是为什么调用者的策略必须授予这些操作，以及为什么步骤 3 中的条件适用于它们。在假定 Maya 会话的情况下，绑定到 Maya 的“actorId”的请求将正常进行。绑定 Liam 的“actorId”的请求是该策略要防范的错误，并且在每次内存操作时都会被拒绝：
```
SessionHistoryLoad/FAILED      failures: ["AccessDeniedException"]
SpeculativeRetrieval/SUCCEEDED failures: ["AccessDeniedException"]   # memory leg denied, KB leg answered
```
Liam 的记忆中没有写入任何内容：他的会话计数仍为 0。答案仍然是从知识库生成的。由于每个用户都有自己的角色会话，AWS 还会查看每个调用针对哪个用户：调用者是“assumed-role/anycompany-assistant-app-role/user-<sub>”，其中“SourceIdentity=<sub>”，会话持有者无法更改。

还有两点。内存是客户拥有的资源，您帐户中的其他系统也可以写入该资源。将其内容视为输入，并通过“policyConfiguration”将 Amazon Bedrock 护栏附加到请求。并规划数据生命周期。原始事件按照“eventExpiryDuration”过期，但提取的记录不会。因此，用户删除工作流程涵盖参与者会话的“DeleteEvent”和参与者命名空间下的“DeleteMemoryRecord”。

## 可观察性和故障行为

每回合使用相关 ID 记录完整跟踪。规划器的子查询与其最终结果一样值得审核。 “AWS/Bedrock/KnowledgeBases”报告“Operation=AgenticRetrieveStream”的“调用”、“ClientErrors”和“TotalIterationCount”。 “AWS/Bedrock-AgentCore”报告每个内存操作的“调用”、“延迟”、“错误”和“用户错误”，以及每个提取策略的“InputTokenUsage”/“OutputTokenUsage”。启用 Amazon CloudWatch Transaction Search 后，AgentCore 可观察性（Amazon Bedrock AgentCore 的一项功能）可显示回合端到端的跨度。

内存操作在设计上是尽力而为的。如果内存调用失败或被拒绝，请求不会失败。跟踪携带带有失败消息的“FAILED”内存事件，并且轮流在没有该内存的情况下继续。答案是从知识库生成的。确定您的 UI 是否显示降级状态。

## 注意事项

- 在对话期间使用稳定的“sessionId”。 API 接受每个请求一个新的 ID，但新的 ID 会默默地破坏连续性并每轮生成一个摘要记录。
- 使用 `namespacePath` 来访问用户的所有长期记录。 `retrievalConfigs` 接受一个条目，最多包含五个 `metadataFilters`。 “namespace”按前缀匹配，“namespacePath”按层次结构匹配，因此“namespacePath”适合根目录下的每个用户 ID。提供完全解析的命名空间，因为“/anycompany/{actorId}”等模板被拒绝。
- 预计仅恢复“USER”和“ASSISTANT”对话事件。其他系统编写的具有“TOOL”或“OTHER”角色的事件将被跳过。
- 当您的应用程序需要准确控制每个请求携带的历史记录时，继续发送“消息”而不是“sessionBinding”。例如，您现有的历史记录存储可能是对话记录系统，或者您可以在发送历史记录之前对其进行编辑或编辑。通过“sessionBinding”，该服务可以为您恢复并保留对话。您不能将两者合并为一个请求。
- 一个请求最多可以携带5个知识库。对于多个检索器，规划器会根据知识库“描述”路由每个子查询，因此请仔细编写。
- 规划延迟和成本。会话恢复会增加大约 200 毫秒。在我们的运行中，使用托管模型，一个知识库、ACL 和内存完成一整轮需要 4-10 秒。计划迭代驱动的是时间，而不是内存。这些是观察到的数字，而不是服务承诺。代理检索按每次调用加上基础检索进行定价，调用期间进行的内存操作按 AgentCore 内存使用量计费。有关详细信息，请参阅 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/) 和 [Amazon Bedrock AgentCore 定价](https://aws.amazon.com/bedrock/agentcore/pricing/)。

## 结论

Amazon Bedrock 托管知识库已经为您提供了检索堆栈作为服务。该堆栈涵盖了“AgenticRetrieveStream”中的摄取、文档 ACL、索引、排名和规划循环，将难题转化为引用的答案。通过“memoryConfiguration”，同一个调用现在可以承载对话和用户的历史记录。对于多用户应用程序，删除了对话存储、历史重播和提取管道。剩下的就是一份简短的职责清单。对用户进行身份验证并从 ID 令牌读取两个声明：将经过验证的电子邮件作为“userContext”传递，以便知识库过滤文档，并使用“sub”作为具有“{actorId}”根命名空间的一个内存资源的“actorId”。在每用户角色会话上使用 IAM 条件键作为通过代理路径的第二道防线。
