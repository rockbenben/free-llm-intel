# 使用 Agentic Retrieve 在 Amazon Bedrock Managed Knowledge Base 上构建具备记忆感知能力的 AI agents

知识库驱动的应用，其用户期待它记住自己，而不只是检索得好。他们提出的追问，只有放在前一轮对话的语境里才说得通。他们期望关于某项政策或流程的回答，能反映上个月自己告诉过应用的关于自己的信息。同时，他们仍然期望每个回答都基于自己有权阅读的文档，并带有引用。无论应用是客户支持助手、SaaS 产品内的文档问答，还是面向公司政策的内部助手，期待都是一样的。

满足这种期待很难，因为能让检索更精准的上下文存在于知识库之外。用户的位置、角色或产品层级，往往是在几周前一段不相关的对话里提到的。要用上它，应用必须存储每一次对话、从中抽取持久事实、判断哪些事实对当前问题重要，并把它们注入请求。当许多用户共用同一个应用时，上述每一步还必须按用户隔离，每一份文档也一样。

[Amazon Bedrock Managed Knowledge Base](https://aws.amazon.com/bedrock/knowledge-bases/) 与 [Amazon Bedrock AgentCore memory（Amazon Bedrock AgentCore 的一项能力）](https://aws.amazon.com/bedrock/agentcore/) 现在接管了这些步骤：存储每一次对话、从中抽取事实，并把相关事实带入检索。你只需在 `AgenticRetrieveStream` 请求中添加 `memoryConfiguration` 就能开启它，这会让 AgentCore memory 成为与知识库并列的检索源。在同一次调用中，服务会恢复对话，planner 则自行决定何时某条关于用户的事实会有帮助。它从长期记忆里取回该事实，并用它来组织发往知识库的子查询。生成答案之后，服务把这一轮保存回记忆。同一个请求还携带 `userContext`，因此知识库只会返回用户的访问控制列表（ACL）允许的文档。该集成是选择性启用（opt-in）的，并向后兼容。你的应用只保留真正属于自己的部分：认证用户，并传递用户是谁。

本文展示如何为共用同一个知识库和同一个 memory 资源的众多用户构建这样的助手。每个用户只能看到自己有权阅读的文档，每个用户的记忆保持私有。贯穿全文的示例是为虚构公司 AnyCompany 构建的内部员工助手。员工通过 Amazon Cognito 登录，就 HR 政策、IT 指南、工程运维手册和销售计划提问。我们会展示如何从 Cognito ID token 读取用户身份、如何把它传给 `AgenticRetrieveStream` 以用于文档 ACL 和记忆、如何为众多用户设计 memory 命名空间，以及如何读取 trace 观察 planner 何时用到了记忆。最后，我们会让 AWS Identity and Access Management（IAM）即使在应用代码出错时也强制实施按用户的记忆隔离。如果你已经按 [使用 Amazon Bedrock Managed Knowledge Base 在企业数据上构建多租户 agentic 聊天应用](https://aws.amazon.com/blogs/machine-learning/build-multi-tenant-agentic-chat-applications-on-enterprise-data-with-amazon-bedrock-managed-knowledge-base/) 部署了应用，本文会替换其中“自己持久化对话历史”那一步。

## 方案概览

AnyCompany 把文档存放在 Amazon Simple Storage Service（Amazon S3）中。一个 managed knowledge base 通过启用 ACL 的 Amazon S3 数据源同步这些文档。同一存储桶中的一个全局 ACL 文件规定哪些员工可以读取哪个文件夹：所有人都能读 HR 和 IT，只有工程师能读工程运维手册，只有销售人员能读佣金计划。所有员工共用一个 AgentCore memory 资源。Amazon Cognito 负责认证员工，其 ID token 提供两个 claim：`sub`（用户 ID）标识该用户的记忆，经过验证的 `email` 则向知识库的 ACL 过滤器标识该用户。三个测试用户登录：两位工程师 Maya 和 Liam，一位销售人员 Sofia。本文中的 trace 摘录取自 [GitHub 仓库](https://github.com/aws-samples/sample-managed-knowledge-base-patterns/tree/main/agentcore-memory-multiuser) 中示例应用的一次运行。

![记忆感知员工助手的架构：应用、AgenticRetrieveStream、Managed Knowledge Base 与 AgentCore memory](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/13/ML-21969-1.png)

图 1：记忆感知员工助手的架构。应用认证用户并构造请求（步骤 1–4）。Amazon Bedrock Managed Knowledge Base 恢复会话、检索信息、返回答案，并把这次交互保存到 AgentCore memory（步骤 5–8）。短期事件与长期记录属于同一个 memory 资源。

- 员工通过 Cognito 登录，获得 ID token，即由用户池签名的 JSON Web Token（JWT）。
- 应用的 API 校验该 token——生产环境中是 Amazon API Gateway JWT authorizer，示例中是一个小的 FastAPI 服务。未认证的请求不会到达 handler。
- handler 从已验证的 token 中读取两个 claim：`sub` 成为记忆的 `actorId` 和命名空间，`email` 成为 `userContext.userId`。客户端请求体只携带 `{ question, sessionId? }`。随后 handler 以会话标签 `userId=<sub>` 代入该用户对应的应用 IAM 角色。
- handler 调用 `AgenticRetrieveStream`，以知识库作为 retriever，并携带 `userContext` 以及绑定到该用户的 `memoryConfiguration`。
- Managed Knowledge Base 从 AgentCore memory 的短期记忆（STM）中恢复由 `sessionBinding` 标识的 actor 与会话的对话历史。
- Managed Knowledge Base 基于 `userContext` 做 ACL 过滤，从知识库中检索。它还可以通过推测式检索，或 planner 选择的记忆搜索，取回用户已配置的长期记忆。
- Managed Knowledge Base 把带引用的答案和 trace 事件流式返回给 handler。handler 用关联 ID 记录 trace，并把答案和 trace 信息转发给 UI。
- 使用 `persistenceMode: DEFAULT` 时，服务把问题和生成的答案保存到该会话。随后 AgentCore memory 按配置的策略异步抽取长期记录。

Managed Knowledge Base 负责摄取、ACL 过滤、索引、排序、规划、检索和生成。有了 `memoryConfiguration`，它还负责会话恢复、记忆搜索与持久化。AgentCore memory 负责存储、保留、加密与抽取。你的应用负责认证、UI 以及从 token 读取用户身份。这里没有对话表：当 UI 列出或重新打开会话时，它读取的是同一个 memory 资源。

### 身份如何映射到请求

每个值都由应用从已验证的 ID token 推导，没有一个来自请求体。

| **请求字段** | **来源** | **作用范围** | **强制方式** |
| --- | --- | --- | --- |
| `userContext.userId` | ID token `email`（已验证，在用户池中不可变） | 可检索哪些文档 | 知识库 ACL 过滤 |
| `memoryConfiguration.sessionBinding.actorId` | ID token `sub` | 恢复并写入谁的短期记忆，以及长期命名空间中的 `{actorId}` | AgentCore memory 的键控，外加 IAM 条件 |
| `memoryConfiguration.sessionBinding.sessionId` | 新对话由应用生成。通过 `ListSessions` 列出 | 该 actor 内的哪个会话 | 在 `actorId` 下键控 |
| `memoryConfiguration.retrievalConfigs[0].namespacePath` | `/anycompany/<sub>` | planner 可以搜索哪些长期记录 | IAM 条件 |

两个不同的 claim 承担两项不同的职责。知识库用 email 标识用户，因为连接的数据源在其 ACL 中记录的就是 email。记忆需要一个永不改变、永不复用的 `actorId`。Cognito 的 `sub` 两者兼具。邮箱地址可能被修改，或在某人离职后分配给新员工，那个人就会继承旧的记忆。你也可以用自己用户存储中的另一个稳定用户 ID 作为 `actorId`。关键是它永远不会转移到别人名下。

## 先决条件

- 本演练使用美国西部（俄勒冈）区域（us-west-2）中的 managed knowledge base 和 AgentCore memory 资源。如[agentic retrieval 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html)所述，与此集成配合使用的 memory 资源必须与知识库位于同一个 AWS 账户，并处于 `ACTIVE` 状态。
- Python 3.10 或更高版本，以及 Boto3 1.43.72 或更高版本。
- 创建 S3 存储桶、Cognito 用户池、IAM 角色、知识库和 memory 资源的权限。示例的 `infra/setup.py` 会幂等地创建所有这些资源。

## 方案演练

以下步骤会创建知识库及其数据源、搭建 memory 资源与 Amazon Cognito、构造请求，并读取 trace 以确认结果。

### 第 1 步：创建知识库并配置启用 ACL 的数据源

managed knowledge base 不需要向量存储：

请按 [为 managed Amazon Bedrock Knowledge Bases 创建服务角色](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-permissions.html) 为你的配置创建服务角色，并在 `roleArn` 中传入其 ARN。关于模型访问要求，也请查阅 [managed 与自定义模型的先决条件](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-prereqs.html)。

```
kb = agent.create_knowledge_base(
    name="anycompany-assistant-docs",
    description="AnyCompany internal documents: HR policies, IT guides, engineering runbooks, sales plans.",
    roleArn=kb_service_role_arn,
    knowledgeBaseConfiguration={
        "type": "MANAGED",
        "managedKnowledgeBaseConfiguration": {"embeddingModelType": "MANAGED"},
    },
)["knowledgeBase"]
```

文档位于存储桶的 `docs/<folder>/` 下。Amazon S3 自身没有可供爬取的权限系统，因此你在同一存储桶的全局 ACL 文件中提供 ACL。每个条目把一个 S3 前缀映射到可以读取它的邮箱：

```
[
  {"keyPrefix": "s3://BUCKET/docs/hr/",
   "aclEntries": [{"Name": "maya@example.com",  "Type": "USER", "Access": "ALLOW"},
                  {"Name": "liam@example.com",  "Type": "USER", "Access": "ALLOW"},
                  {"Name": "sofia@example.com", "Type": "USER", "Access": "ALLOW"}]},
  {"keyPrefix": "s3://BUCKET/docs/engineering/",
   "aclEntries": [{"Name": "maya@example.com",  "Type": "USER", "Access": "ALLOW"},
                  {"Name": "liam@example.com",  "Type": "USER", "Access": "ALLOW"}]},
  {"keyPrefix": "s3://BUCKET/docs/sales/",
   "aclEntries": [{"Name": "sofia@example.com", "Type": "USER", "Access": "ALLOW"}]}
]
```

示例中的文件还让所有人可读 `docs/it/`。接着创建数据源。对于 managed knowledge base，每个 connector 的类型都是 `MANAGED_KNOWLEDGE_BASE_CONNECTOR`，由 `connectorParameters.type` 选择来源：

```
ds = agent.create_data_source(
    knowledgeBaseId=kb["knowledgeBaseId"],
    name="s3-docs-acl",
    dataSourceConfiguration={
        "type": "MANAGED_KNOWLEDGE_BASE_CONNECTOR",
        "managedKnowledgeBaseConnectorConfiguration": {
            "connectorParameters": {
                "type": "S3",
                "version": "1",
                "connectionConfiguration": {"bucketName": BUCKET, "bucketOwnerAccountId": ACCOUNT_ID},
                "filterConfiguration": {"inclusionPrefixes": ["docs/"]},
                "aclEnabled": True,
                "aclConfiguration": {"globalAccessControlListS3Uri": f"s3://{BUCKET}/acl/global-acl.json"},
            }
        },
    },
)["dataSource"]
```

`aclEnabled` 在数据源创建后无法更改。`CreateDataSource` 是异步的，所以要等待状态变为 `AVAILABLE`。然后调用 `StartIngestionJob` 并等待 `COMPLETE`。同步会读取文档和 ACL 文件，并为每份文档连同其 ACL 建立索引。在示例中，全部 11 份文档都被扫描并建立索引，0 次失败。没有被任何 ACL 条目覆盖的文档不会被摄取；邮箱不匹配任何条目的用户，从这个数据源得不到任何结果。

同一模型也适用于从源系统爬取权限的 connectors，例如 Microsoft SharePoint、Google Drive 和 Atlassian Confluence。在那里，权限来自源系统，用户组从源系统解析，知识库还会实时把每个结果与源系统核对。你的应用代码无需改动：它仍然在 `userContext` 中传入用户的 email。完整列表见 [访问控制列表感知的启用](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-acl.html)。

### 第 2 步：创建 memory 资源并设计命名空间

一个 memory 资源服务所有用户。按用户隔离来自命名空间模板中的 `{actorId}`，AgentCore memory 在抽取时从每个事件中解析它。有两个选择很重要。

[策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/built-in-strategies.html)。两种策略抽取的内容不同。摘要策略对每次对话做摘要，因此会捕获用户顺带提到的事实，例如“我在法兰克福办公室用 Mac”。正是这些事实让之后关于（比如）PTO 的回答变得个性化。用户偏好策略把明确表达的偏好抽取成结构化记录（“偏好简短的无表格要点式回答”“总是先部署到 eu-central-1”），而不把顺带提及当作偏好。摘要给你“我们讨论过什么”，偏好给你“这个人希望被怎样回答”。两者都要用。

布局。`retrievalConfigs` 只接受一个条目，因此单个 `namespacePath` 必须覆盖 planner 对某用户应当看到的全部内容。把 `{actorId}` 直接放在根下：`namespacePath: "/anycompany/<sub>"` 于是覆盖 profile 与所有对话摘要。像 `/anycompany/profile/{actorId}` 和 `/anycompany/summaries/{actorId}` 这样的布局，会让一个条目只能触达其中之一。

```
memory = control.create_memory(
    name="anycompany_assistant_memory",
    eventExpiryDuration=30,          # days; raw conversation events expire after this
    # encryptionKeyArn=CMK_ARN,      # optional customer managed key
    memoryStrategies=[
        {"userPreferenceMemoryStrategy": {
            "name": "EmployeeProfile",
            "namespaces": ["/anycompany/{actorId}/profile"],
        }},
        {"summaryMemoryStrategy": {
            "name": "ConversationSummaries",
            "namespaces": ["/anycompany/{actorId}/summaries/{sessionId}"],
        }},
    ],
)["memory"]
```

等待 memory 达到 `ACTIVE`。创建 memory 不需要用户或 `actorId`，所以第 2 步和第 3 步的顺序无关紧要。不会为每个用户预置任何东西：新的 Cognito 用户第一次提问时就成为新的 actor。

### 第 3 步：设置 Cognito 并授予应用权限

创建一个用户池和一个不带客户端密钥的 app client。email 决定用户能读哪些文档，所以要把它设为必填、验证，且不可由用户更改：

```
pool_id = idp.create_user_pool(
    PoolName="anycompany-assistant-employees",
    AutoVerifiedAttributes=["email"],
    Schema=[{"Name": "email", "Required": True, "Mutable": False, "AttributeDataType": "String"}],
    AdminCreateUserConfig={"AllowAdminCreateUserOnly": True},
)["UserPool"]["Id"]
```

`Mutable` 在用户池创建后无法更改。如果 email 可变，已登录用户就可能把自己的 email 改成同事的地址。如果你的用户从 Okta 或 Microsoft Entra ID 联合登录，请把 IdP 的 email 映射到这个属性，使其与数据源 ACL 中的 email 一致。

示例启用了 `USER_PASSWORD_AUTH`，以便本地 UI 和测试可以直接登录。生产应用通常使用 Cognito managed login 或 AWS Amplify。

为应用设置一个 IAM 角色。后端为每个用户代入它一次，会话标签为 `userId=<sub>`，并且每条 memory 语句都以该标签为条件。下面是示例运行所用的完整策略：

```
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "AgenticRetrieve", "Effect": "Allow",
      "Action": "bedrock:AgenticRetrieveStream", "Resource": "*" },
    { "Sid": "KnowledgeBaseRetrieval", "Effect": "Allow",
      "Action": ["bedrock:Retrieve", "bedrock:GetDocumentContent"],
      "Resource": "arn:aws:bedrock:us-west-2:111122223333:knowledge-base/KB_ID" },
    { "Sid": "PlannerAndGeneration", "Effect": "Allow",
      "Action": "bedrock:InvokeModelWithResponseStream", "Resource": "*" },
    { "Sid": "MemoryDescribe", "Effect": "Allow",
      "Action": "bedrock-agentcore:GetMemory",
      "Resource": "arn:aws:bedrock-agentcore:us-west-2:111122223333:memory/MEMORY_ID" },
    { "Sid": "MemorySessionsScopedToCaller", "Effect": "Allow",
      "Action": ["bedrock-agentcore:ListEvents", "bedrock-agentcore:CreateEvent",
                 "bedrock-agentcore:ListSessions"],
      "Resource": "arn:aws:bedrock-agentcore:us-west-2:111122223333:memory/MEMORY_ID",
      "Condition": {"StringEquals": {"bedrock-agentcore:actorId": "${aws:PrincipalTag/userId}"}} },
    { "Sid": "MemoryRecordsScopedToCaller", "Effect": "Allow",
      "Action": ["bedrock-agentcore:RetrieveMemoryRecords", "bedrock-agentcore:ListMemoryRecords"],
      "Resource": "arn:aws:bedrock-agentcore:us-west-2:111122223333:memory/MEMORY_ID",
      "Condition": {"StringLike": {"bedrock-agentcore:namespacePath": "/anycompany/${aws:PrincipalTag/userId}/*"}} }
  ]
}
```

`sessionBinding` 需要 `ListEvents`，`retrievalConfigs` 需要 `RetrieveMemoryRecords`，当 `persistenceMode` 为 `DEFAULT` 时需要 `CreateEvent`。`ListSessions` 和 `ListMemoryRecords` 用于应用自身的读取（会话列表和“记忆知道你什么”视图），而不是用于 `AgenticRetrieveStream`。该角色的信任策略允许后端自身的身份（生产环境中是 AWS Lambda 执行角色或 Amazon Elastic Container Service（Amazon ECS）任务角色）执行 `sts:AssumeRole`、`sts:TagSession` 和 `sts:SetSourceIdentity`。如果 memory 使用客户托管密钥，请为该密钥添加 `kms:Decrypt`。

### 第 4 步：从 token 读取用户，然后构造请求

校验 ID token 并读取这两个 claim。只有 ID token 携带 `email`，access token 没有：

```
@dataclasses.dataclass(frozen=True)
class Principal:
    sub: str     # -> memory actorId and namespace
    email: str   # -> userContext.userId (document ACLs)

    def namespace_path(self, root: str) -> str:
        return f"{root}/{self.sub}"       # resolved literal, e.g. /anycompany/a8e1b390-...


def verify(id_token: str) -> Principal:
    key = jwks.get_signing_key_from_jwt(id_token)   # public keys from {issuer}/.well-known/jwks.json
    claims = jwt.decode(id_token, key.key, algorithms=["RS256"], issuer=ISSUER, audience=CLIENT_ID)
    if claims.get("token_use") != "id" or claims.get("email_verified") is not True:
        raise PermissionError("a verified ID token is required")
    return Principal(sub=claims["sub"], email=claims["email"].lower())
```

`jwt.decode` 会校验签名、签发者（你的用户池）、过期时间和受众（你的 app client）。关于这些 claim 的细节，见 [了解身份（ID）token](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-the-id-token.html)。使用 API Gateway 时，JWT authorizer 做同样的校验，并把 claim 传给 handler。

接下来，获取该用户的 AWS 凭证。后端为该用户代入应用角色，并把会话缓存到临近过期之前：

```
creds = sts.assume_role(
    RoleArn=APP_ROLE_ARN,
    RoleSessionName=f"user-{principal.sub}",
    SourceIdentity=principal.sub,
    Tags=[{"Key": "userId", "Value": principal.sub}],
)["Credentials"]
```

现在，该用户的每次调用——包括 agentic retrieval 替调用方发起的 memory 调用——都以 `assumed-role/anycompany-assistant-app-role/user-<sub>` 身份运行，并携带第 3 步策略所检查的那个标签。

确定 `sessionId`。对于新对话，应用生成一个，例如 `"conv-" + uuid4().hex`，并返回给客户端。要继续对话，客户端把它传回来。要向用户展示其会话列表，用该用户的 `actorId` 调用 `ListSessions`：

```
def list_conversations(principal):
    try:
        resp = memory.list_sessions(memoryId=MEMORY_ID, actorId=principal.sub, maxResults=50)
    except memory.exceptions.ResourceNotFoundException:
        return []   # the user has not asked anything yet, so there is no actor
    return [{"sessionId": s["sessionId"], "createdAt": s["createdAt"].isoformat()} for s in resp["sessionSummaries"]]
```

你不需要自己维护把用户映射到会话的表。接受客户端传来的 `sessionId` 是安全的，因为短期记忆以 `(memoryId, actorId, sessionId)` 为键，而 `actorId` 来自 token。如果 Liam 发来 Maya 的 `sessionId`，它只会在 Liam 自己的空间里指向一个空会话。agentic retrieval 本身并不校验你提供的 `actorId`、`sessionId` 或命名空间是否属于提问的用户，因此它们绝不能来自客户端。只有当你需要 memory 不保存的数据（例如会话标题）时，才需要自己的会话表。

然后构造请求：

```
def build_request(principal, question, session_id):
    return {
        # With sessionBinding, messages carries ONLY the current question.
        "messages": [{"role": "user", "content": {"text": question}}],
        "retrievers": [{"configuration": {"knowledgeBase": {"knowledgeBaseId": KB_ID}},
                        "description": KB_DESCRIPTION}],
        # Document ACLs: only documents this email may read are retrieved.
        "userContext": {"userId": principal.email},
        "agenticRetrieveConfiguration": {
            "foundationModelType": "MANAGED",
            "rerankingModelType": "MANAGED",
            "maxAgentIteration": 3,
        },
        "generateResponse": True,
        "memoryConfiguration": {
            "memoryId": MEMORY_ID,
            "sessionBinding": {"actorId": principal.sub, "sessionId": session_id},
            "persistenceMode": "DEFAULT",
            "retrievalConfigs": [{"namespacePath": principal.namespace_path("/anycompany")}],
        },
    }
```

没有 `userContext` 时，启用 ACL 的数据源完全不返回结果。把这个请求与它取代的无状态 handler 对比一下：

```
history = history_table.query(KeyConditionExpression=Key("sessionId").eq(session_id))
messages = [*replay(history), {"role": "user", "content": {"text": question}}]
response = runtime.agentic_retrieve_stream(messages=messages, retrievers=..., agenticRetrieveConfiguration=...)
history_table.put_item(Item={"sessionId": session_id, "q": question, "a": consume(response)})
```

调用前的查询和调用后的写入都不见了，`messages` 只有一个元素。`sessionBinding` 带来三条规则，每条都由特定的 `ValidationException` 强制执行。第一，`messages` 只携带当前问题，因此每个请求由你选择唯一的历史来源。第二，`persistenceMode: DEFAULT`（默认值）把问题和生成的答案作为一个事件写入，因此它要求 `generateResponse: true`。第三，只有 `memoryId` 是无效的。`persistenceMode: NONE` 会恢复历史但不写入任何内容，适用于审计或回放视图。

### 第 5 步：更新客户端契约并渲染历史

客户端发送 `{ question, sessionId? }`。对于新对话，应用生成一个 `sessionId` 并把它作为第一个流式帧返回。客户端在后续轮次中回传它，要重新开始则省略它。

由于 memory 资源属于你，应用可以直接读取它来渲染对话：

```
def conversation_history(principal, session_id):
    resp = memory.list_events(memoryId=MEMORY_ID, actorId=principal.sub, sessionId=session_id,
                              includePayloads=True, maxResults=100)
    return [{"role": p["conversational"]["role"].lower(), "text": p["conversational"]["content"]["text"]}
            for ev in sorted(resp["events"], key=lambda e: e["eventTimestamp"])
            for p in ev["payload"] if "conversational" in p]
```

每个持久化的轮次恰好是一个事件、带两个 payload：用户的问题和最终答案。因此历史会渲染成干净的 transcript，并且仍可被其他 AgentCore memory 客户端使用。

### 第 6 步：从 trace 验证

trace 会告诉你每一轮知识库和记忆做了什么：

| **Trace 事件** | **何时出现** | **要看什么** |
| --- | --- | --- |
| `SessionHistoryLoad` | 首个事件，只要设置了 `sessionBinding` 就会出现 | `_memory_event_count` 与 `_memory_message_count`，新会话时两者均为 0 |
| `SpeculativeRetrieval` | 规划之前 | 新会话时，`retrievalMetadata` 还会列出 `BedrockAgentCoreMemory`。memory 条目带有 `_memory_*` 元数据且没有文本。知识库条目带有 `_source_uri` |
| `Planning` | 每次迭代 | `actions[].memoryRetrieve` 表示 planner 选择搜索记忆，并带上它组织的查询 |
| `Retrieval`（`retrievalType: BedrockAgentCoreMemory`） | 每个规划出的记忆操作 | `_memory_record_count`。计数为 0 是正常结果 |
| `status: FAILED` 的 memory 事件 | memory 不可用或访问被拒绝 | `failures[].message`。记忆是尽力而为的：请求继续，答案由知识库生成 |

## 安全与多用户隔离

**在本演练中，应用负责认证，知识库负责过滤。** 具备 ACL 感知的检索是过滤，不是授权。只从经过验证、`email_verified: true` 的 ID token 中取 email，在用户池中把它设为不可变，并处理 email 复用：如果某个地址被重新分配给另一个人，那个人就会继承原主人的文档访问权限。知识库失败时是关闭的（fail closed）：没有 ACL 的文档，或 ACL 出错，意味着结果更少，而不是更多。如果结果缺失，请检查 email 是否与 ACL 条目匹配。

**身份同样来自 token**（第 4 步）：`actorId` 和命名空间来自已验证的 `sub`，绝不来自客户端。

**IAM 条件键，作为纵深防御。** AgentCore memory 在 `ListEvents`、`CreateEvent` 和 `ListSessions` 上暴露 `bedrock-agentcore:actorId`，在 `RetrieveMemoryRecords` 和 `ListMemoryRecords` 上暴露 `bedrock-agentcore:namespacePath`。agentic retrieval 在请求期间发起的 memory 调用，会以调用方身份进行授权。这就是为什么调用方的策略必须授予这些动作，以及为什么第 3 步中的条件对它们生效。在代入 Maya 的会话下，绑定 Maya 的 `actorId` 的请求正常进行。而绑定 Liam 的 `actorId` 的请求，正是该策略防范的 bug，它会在每一个记忆操作处被拒绝：

```
SessionHistoryLoad/FAILED      failures: ["AccessDeniedException"]
SpeculativeRetrieval/SUCCEEDED failures: ["AccessDeniedException"]   # memory leg denied, KB leg answered
```

没有任何东西写入 Liam 的记忆：他的会话数保持为 0。答案仍然由知识库生成。由于每个用户都有自己的角色会话，AWS 也能看到每次调用属于哪个用户：调用方是 `assumed-role/anycompany-assistant-app-role/user-<sub>`，并带有 `SourceIdentity=<sub>`，会话持有者无法更改它。

另外两点。memory 是客户所有的资源，你账户中的其他系统也可能写入它。把它的内容当作输入，并通过 `policyConfiguration` 为请求附加 Amazon Bedrock guardrail。还要规划数据生命周期。原始事件按 `eventExpiryDuration` 过期，但抽取出的记录不会。因此，用户删除工作流需要覆盖该 actor 会话的 `DeleteEvent`，以及该 actor 命名空间下的 `DeleteMemoryRecord`。

## 可观测性与失败行为

为每一轮用关联 ID 记录完整 trace。planner 的子查询和它的最终结果一样值得审计。`AWS/Bedrock/KnowledgeBases` 为 `Operation=AgenticRetrieveStream` 报告 `Invocations`、`ClientErrors` 和 `TotalIterationCount`。`AWS/Bedrock-AgentCore` 按 memory 操作报告 `Invocations`、`Latency`、`Errors` 和 `UserErrors`，并按抽取策略报告 `InputTokenUsage`/`OutputTokenUsage`。启用 Amazon CloudWatch Transaction Search 后，AgentCore Observability（Amazon Bedrock AgentCore 的一项能力）可以端到端展示一轮的 span。

记忆操作按设计是尽力而为的。如果 memory 调用失败或被拒绝，请求不会失败。trace 会带上一个 `FAILED` 的 memory 事件及失败消息，这一轮在没有该记忆的情况下继续。答案由知识库生成。请决定你的 UI 是否要暴露这种降级状态。

## 注意事项

- 在一次对话的整个生命周期内使用稳定的 `sessionId`。API 接受每个请求使用新 ID，但新 ID 会悄悄破坏连续性，并且每一轮都会产生一条摘要记录。
- 用 `namespacePath` 触达用户的全部长期记录。`retrievalConfigs` 接受一个条目，最多五个 `metadataFilters`。`namespace` 按前缀匹配，`namespacePath` 按层级匹配，因此 `namespacePath` 适合把每用户 ID 放在根下。提供的命名空间必须完全解析，因为像 `/anycompany/{actorId}` 这样的模板会被拒绝。
- 只有 `USER` 和 `ASSISTANT` 角色的对话事件会被恢复。其他系统写入的 `TOOL` 或 `OTHER` 角色事件会被跳过。
- 当你的应用需要精确控制每个请求携带哪段历史时，继续发送 `messages`，而不是用 `sessionBinding`。例如，你现有的历史存储可能是对话的权威记录，或者你可能在发送前编辑或脱敏历史。使用 `sessionBinding` 时，服务会替你恢复并持久化对话。两者不能在一个请求中混用。
- 一个请求最多可携带五个知识库。存在多个 retriever 时，planner 依据知识库的 `description` 为每个子查询做路由，所以要谨慎撰写它。
- 为延迟和成本做规划。会话恢复大约增加 200 毫秒。在我们的运行中，使用 managed 模型、一个知识库、ACL 和记忆时，完整一轮耗时 4–10 秒。驱动这一时间的是规划迭代，而不是记忆。这些是观测到的数字，不是服务承诺。agentic retrieval 按调用次数加上底层检索计费，调用期间发生的 memory 操作按 AgentCore memory 用量计费。详情见 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/) 和 [Amazon Bedrock AgentCore 定价](https://aws.amazon.com/bedrock/agentcore/pricing/)。

## 清理

在示例中运行 `python infra/teardown.py`，即可删除知识库、S3 存储桶及其对象、memory 资源（含对话历史和长期记录）、Cognito 用户池以及 IAM 角色。

## 结论

Amazon Bedrock Managed Knowledge Base 已经把整套检索栈作为服务提供给你。这套栈覆盖摄取、文档 ACL、索引、排序，以及 `AgenticRetrieveStream` 中那个把难题变成带引用答案的规划循环。借助 `memoryConfiguration`，同一次调用现在还携带对话和用户历史。对于多用户应用，这省掉了对话存储、历史回放和抽取流水线。剩下的是一份很短的责任清单。认证用户并从 ID token 读取两个 claim：把经过验证的 email 作为 `userContext` 传入，让知识库过滤文档；把 `sub` 用作 `actorId`，配一个带有以 `{actorId}` 为根的命名空间的 memory 资源。在按用户的角色会话上使用 IAM 条件键，作为贯穿 agentic 路径的第二道防线。
