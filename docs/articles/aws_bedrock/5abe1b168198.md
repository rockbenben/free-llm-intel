# 在 Amazon Bedrock 上为 OpenAI GPT-5.6 模型引入跨区域推理

*本文由 OpenAI 的 Chris Dickens 共同撰写。*

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 现已在超过 25 个 AWS 区域通过跨区域推理（cross-Region inference）提供 OpenAI GPT-5.6 模型。三个 GPT-5.6 变体支持跨区域推理：Sol、Terra 和 Luna，每个变体都在能力与成本之间做了不同的平衡。

Amazon Bedrock 中的跨区域推理（CRIS）通过推理配置文件（inference profile）实现：推理配置文件定义一个模型，以及 Amazon Bedrock 可以将请求路由到的 AWS 区域。你从源区域调用该配置文件，Amazon Bedrock 使用目标区域中的算力把请求路由到目标区域。CRIS 主要是一种容量机制。它允许请求从更广泛的算力池中取用资源，而不必受限于单个区域的可用容量，从而提升吞吐量，并有助于在负载下保持稳定的性能。地理推理配置文件在单一地理范围内路由请求，因此你可以在扩展的同时让数据处理保留在该地理范围内。对于 GPT-5.6，[本次发布引入了美国地理范围（US 跨区域推理）和全局 CRIS](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-bedrock-cross-region-openai-v2/)。全局推理配置文件会在该模型已部署的所有受支持的 AWS 商业区域之间路由请求，让你可以广泛访问 Amazon Bedrock 的容量。

在本文中，我们概述 Amazon Bedrock 上的 GPT-5.6 模型、这些模型的地理与全局跨区域推理如何工作，以及如何从 Amazon Bedrock 控制台、并在代码中使用 OpenAI Responses API、OpenAI Chat Completions API 和 Amazon Bedrock Converse API 调用它们。

## Amazon Bedrock 上的 GPT-5.6

Amazon Bedrock 上的 GPT-5.6 系列既包含通用变体，也包含专门的网络安全变体。本文介绍支持跨区域推理的三个通用变体：Sol、Terra 和 Luna。三者都接受文本和图像输入并返回文本，拥有 100 万 token 的上下文窗口，并支持推理模式、服务端工具调用和 prompt 缓存。你可以使用 OpenAI Responses API、OpenAI Chat Completions API 和 Amazon Bedrock Converse API 调用它们。流式响应通过 Responses 和 Chat Completions API（`stream=True`）以及 `ConverseStream` 得到支持。

Amazon Bedrock 推理配置文件是逻辑标识符，你传入它来代替原始的模型 ID。

- **地理推理配置文件**（带有诸如 `us.` 之类的地理代码前缀，例如 us.openai.gpt-5.6-terra）将推理处理限定在其预定义地理范围内的区域之中。请求通过你的源区域进入，并且只能路由到该地理范围内的目标区域，因此有数据驻留要求的工作负载可以跨区域扩展，同时仍留在此边界之内。
- **全局推理配置文件**（带有 `global.` 前缀，例如 global.openai.gpt-5.6-terra）可以将请求路由到该模型已部署的任意受支持的商业 AWS 区域。它提供最广泛的容量池，当你的工作负载没有地理处理要求时，它是合适的选择。

无论由哪个后端区域处理请求，计费与配额消耗都记在你的账户上，因此支出与吞吐量仍然只有一份视图。通过全局 CRIS 处理的数据可能会跨越该模型合格区域集合中的多个区域。如果你的工作负载有数据驻留要求、需要把处理限制在特定地理范围内，请使用与该地理范围对应的地理配置文件（例如 us.openai.gpt-5.6-terra），或者直接调用某一个区域，而不要使用全局配置文件。Amazon Bedrock 的[跨区域推理文档](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-support.html)列出了哪些区域参与每个模型的全局配置文件集合与地理配置文件集合。

## 在 Amazon Bedrock 控制台中试用 GPT-5.6

试用 GPT-5.6 最快的方式是使用 Amazon Bedrock 控制台中的文本 playground，它不需要写代码，也不需要配置 SDK。你可以发送 prompt、调整推理参数，并在各个变体之间切换，从而在集成 API 之前先了解每个模型的表现。模型选择器同时列示地理与全局跨区域推理配置文件，因此你可以在编写代码之前先测试任一种跨区域推理选项。在上图中，源区域是美国东部（弗吉尼亚北部）。模型选择器中的 US 条目是地理推理配置文件，Global 条目是全局推理配置文件。

- 在模型可用的区域中打开 [Amazon Bedrock 控制台](https://console.aws.amazon.com/bedrock/)，例如美国东部（弗吉尼亚北部）。
- 在导航窗格中，在 **Test** 下选择 **Playground**。
- 在页面中部选择 **Select model**。
- 搜索 **OpenAI GPT-5.6 Sol**，选择 **US OpenAI GPT-5.6 Sol** 或 **Global OpenAI GPT-5.6 Sol**，然后选择 **Apply**。
- 输入 prompt 并选择 **Run** 生成响应。

## API 入门

GPT-5.6 在 Amazon Bedrock 上原生支持 OpenAI Responses API 格式。如果你的应用已经在调用 OpenAI 模型，你可以把现有的 OpenAI SDK 客户端指向 Amazon Bedrock 的 OpenAI 兼容端点，然后把模型参数替换为推理配置文件 ID（全局或地理）。在身份验证方面，Amazon Bedrock 既接受标准 AWS 凭证，也接受 Amazon Bedrock API key。API key 方式对 OpenAI SDK 来说最为直接，因为 SDK 会把它作为 bearer token 传递。生产环境中，请使用 `aws-bedrock-token-generator` 包以编程方式生成短期 API key，它会基于你现有的 AWS 凭证派生出 bearer token（长期 key 仅建议用于探索）。

```
from aws_bedrock_token_generator import provide_token
from openai import OpenAI
region = "us-east-1"
# Point the OpenAI SDK at Amazon Bedrock's OpenAI-compatible endpoint for your Region. provide_token() generates a short-term Amazon Bedrock API key from your current AWS credentials (valid up to 12 hours), so no static key needs to be stored.
client = OpenAI(
    base_url= f"https://bedrock-runtime.{region}.amazonaws.com/openai/v1",
    api_key=provide_token(region=region),
)

# Use the global inference profile ID for GPT-5.6 Terra.
model_id = "global.openai.gpt-5.6-terra"
response = client.responses.create(
    model=model_id,
    input="Summarize the difference between horizontal and vertical scaling in two sentences.",
     max_output_tokens=512,
)

print(response.output_text)
```

受支持参数的完整列表，请参阅 Amazon Bedrock 用户指南中的 [OpenAI GPT 模型参数](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-gpt.html)页面。同一个客户端也适用于 Chat Completions API，如果你的应用已经在使用这种格式，会很方便。

```
response = client.chat.completions.create(
     # For US Geo CRIS, use "us.openai.gpt-5.6-terra".
     # Other variants: gpt-5.6-sol, gpt-5.6-luna
     model="global.openai.gpt-5.6-terra",
     messages=[
         {
             "role": "user",
             "content": "In one sentence, what is cross-Region inference in Amazon Bedrock?",
         }
     ],
     max_completion_tokens=2000,
     reasoning_effort="low",
 )

print(response.choices[0].message.content)
```

如果你是直接调用 Amazon Bedrock，而不是通过 OpenAI SDK，请使用 Amazon Bedrock Converse API，它带来的请求结构与你在 Bedrock 上调用其他模型时使用的相同：

```
import boto3

client = boto3.client("bedrock-runtime", region_name="us-east-1")

model_id = "global.openai.gpt-5.6-terra"
 response = client.converse(
     modelId=model_id,
     messages=[{"role": "user", "content": [{"text": "List three common uses for a message queue."}]}],
     inferenceConfig={"maxTokens": 512},
 )
 print(response["output"]["message"]["content"][0]["text"])
```

对于流式响应，请使用相同的参数调用 converse_stream，并遍历事件流：

```
stream_response = client.converse_stream(
     modelId=model_id,
     messages=[{"role": "user", "content": [{"text": "List three common uses for a message queue."}]}],
     inferenceConfig={"maxTokens": 512},
 )

for event in stream_response["stream"]:
     if "contentBlockDelta" in event:
         print(event["contentBlockDelta"]["delta"]["text"], end="")
```

### 在 Amazon Bedrock Mantle 与 Runtime 端点之间选择

对于新应用，我们推荐使用 bedrock-runtime 端点。它支持 Amazon Bedrock 原生的 [InvokeModel](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-api.html) 和 [Converse](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html) API、OpenAI 兼容的 [Responses](https://docs.aws.amazon.com/bedrock/latest/userguide/bedrock-mantle.html#bedrock-mantle-responses) 和 [Chat Completions](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-chat-completions.html) API，以及 Anthropic [Messages](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-messages-api.html) API，并且 [Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html)、[intelligent prompt routing](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.html) 和[跨区域推理](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)等 Amazon Bedrock 功能也都在这里提供。Amazon Bedrock 还支持第二个端点 bedrock-mantle，它目前提供额外的能力，例如服务端与预配置工具使用（包括[网络搜索](https://docs.aws.amazon.com/bedrock/latest/userguide/web-search.html)），以及创建 [Projects](https://docs.aws.amazon.com/bedrock/latest/userguide/projects.html) 和 [Workspaces](https://docs.aws.amazon.com/bedrock/latest/userguide/workspaces.html)。要查看每个模型支持哪个端点，请参阅[端点可用性](https://docs.aws.amazon.com/bedrock/latest/userguide/models-endpoint-availability.html)。

## 安全与合规

跨区域推理使用与区域内直接调用相同的 Amazon Bedrock 安全模型。请求使用你的 AWS Identity and Access Management（IAM）凭证进行身份验证，IAM 策略控制某个角色可以调用哪些推理配置文件。Amazon Bedrock 采用在芯片层面强制执行的零操作员访问（zero-operator access，ZOA）安全模型，因此任何 AWS 操作人员都无法访问你的 prompt 或补全结果。每次模型调用都在你的 IAM 策略下运行，可以通过 VPC 端点从你的虚拟私有云（VPC）私有访问，并记录到 AWS CloudTrail。数据边界策略有助于防止数据跨账户和网络边界外泄。

对于包括 GPT-5.6 在内的某些模型，被 Amazon Bedrock 自动滥用检测分类器标记的内容会保留最多 30 天，用于离线滥用检测。要了解这适用于哪些模型以及其工作方式，请参阅 Amazon Bedrock 用户指南中的[滥用检测](https://docs.aws.amazon.com/bedrock/latest/userguide/abuse-detection.html)。要进一步了解 Bedrock 上的数据保留配置，请参阅 [Amazon Bedrock 数据保留文档](https://docs.aws.amazon.com/bedrock/latest/userguide/data-retention.html#data-retention-modes)。每个配置文件路由集合中各区域的权威列表，请参阅 [Amazon Bedrock 跨区域推理支持](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-support.html)页面。

跨区域推理请求会出现在你源区域的 AWS CloudTrail 中，`additionalEventData.inferenceRegion` 字段会记录每个请求由哪个区域处理。如果你启用了模型调用日志，请求和响应负载会被投递到同一账户和区域中的 Amazon Simple Storage Service（Amazon S3）或 Amazon CloudWatch Logs。

### 为跨区域推理设置 IAM 权限

要让某个角色通过推理配置文件调用 GPT-5.6，需要授予它访问该推理配置文件的权限，以及在配置文件可以路由到的每个区域中访问基础模型的权限。你可以使用托管策略 [AmazonBedrockLimitedAccess](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/AmazonBedrockLimitedAccess.html)，也可以自行创建。

对于**地理推理配置文件**，该策略包含三条语句。第一条授予访问源区域中地理推理配置文件和默认 project 的权限。第二条授予访问源区域以及该地理范围内每个目标区域中基础模型的权限，并附带一个条件，把这种访问限制为通过该配置文件发出的请求。第三条授予 OpenAI 兼容 API 所使用的 bearer token 身份验证权限。

```
{ 
  "Version": "2012-10-17", 
  "Statement": [ 
    { 
      "Sid": "GrantGeoCrisProfileAndProjectAccess", 
      "Effect": "Allow", 
      "Action": ["bedrock:InvokeModel"], 
      "Resource": [ 
        "arn:aws:bedrock:<SOURCE REGION>:<ACCOUNT>:inference-profile/us.openai.gpt-5.6-terra", 
        "arn:aws:bedrock:<SOURCE REGION>:<ACCOUNT>:project/default" 
      ] 
    }, 
    { 
      "Sid": "GrantGeoCrisDestinationModelAccess", 
      "Effect": "Allow", 
      "Action": ["bedrock:InvokeModel"], 
      "Resource": [ 
        "arn:aws:bedrock:us-east-1::foundation-model/openai.gpt-5.6-terra", 
        "arn:aws:bedrock:us-east-2::foundation-model/openai.gpt-5.6-terra", 
        "arn:aws:bedrock:us-west-2::foundation-model/openai.gpt-5.6-terra" 
      ], 
      "Condition": { 
        "StringLike": { 
          "bedrock:InferenceProfileArn": "arn:aws:bedrock:<SOURCE REGION>:<ACCOUNT>:inference-profile/us.openai.gpt-5.6-terra" 
        } 
      } 
    }, 
    { 
      "Sid": "AllowBearerTokenAuth", 
      "Effect": "Allow", 
      "Action": ["bedrock:CallWithBearerToken"], 
      "Resource": "*" 
    } 
  ] 
} 
```

**全局推理配置文件**使用包含四部分的策略。第一条授予访问源区域中全局推理配置文件和默认 project 的权限。第二条授予访问源区域中基础模型的权限。第三条通过不区分区域的全局 ARN 授予访问基础模型的权限，正是这一点实现了跨区域路由。第四条授予 OpenAI 兼容 API 所使用的 bearer token 身份验证权限。

```
{ 
 "Version": "2012-10-17", 
 "Statement": [ 
   { 
     "Sid": "GrantGlobalCrisProfileAndProjectAccess", 
     "Effect": "Allow", 
     "Action": ["bedrock:InvokeModel"], 
     "Resource": [ 
       "arn:aws:bedrock:<REQUESTING REGION>:<ACCOUNT>:inference-profile/global.openai.gpt-5.6-terra", 
       "arn:aws:bedrock:<REQUESTING REGION>:<ACCOUNT>:project/default" 
     ], 
     "Condition": { 
       "StringEquals": { "aws:RequestedRegion": "<REQUESTING REGION>" } 
     } 
   }, 
   { 
     "Sid": "GrantGlobalCrisInRegionModelAccess", 
     "Effect": "Allow", 
     "Action": ["bedrock:InvokeModel"], 
     "Resource": ["arn:aws:bedrock:<REQUESTING REGION>::foundation-model/openai.gpt-5.6-terra"], 
     "Condition": { 
       "StringEquals": { 
         "aws:RequestedRegion": "<REQUESTING REGION>", 
         "bedrock:InferenceProfileArn": "arn:aws:bedrock:<REQUESTING REGION>:<ACCOUNT>:inference-profile/global.openai.gpt-5.6-terra" 
       } 
     } 
   }, 
   { 
     "Sid": "GrantGlobalCrisGlobalModelAccess", 
     "Effect": "Allow", 
     "Action": ["bedrock:InvokeModel"], 
     "Resource": ["arn:aws:bedrock:::foundation-model/openai.gpt-5.6-terra"], 
     "Condition": { 
       "StringEquals": { 
         "aws:RequestedRegion": "unspecified", 
         "bedrock:InferenceProfileArn": "arn:aws:bedrock:<REQUESTING REGION>:<ACCOUNT>:inference-profile/global.openai.gpt-5.6-terra" 
       } 
     } 
   }, 
   { 
     "Sid": "AllowBearerTokenAuth", 
     "Effect": "Allow", 
     "Action": ["bedrock:CallWithBearerToken"], 
     "Resource": "*" 
   } 
 ] 
}
```

这些策略授予了对 project/default 资源的 `bedrock:CallWithBearerToken` 和 `bedrock:InvokeModel` 权限，OpenAI Responses 与 Chat Completions API 使用它们以 Amazon Bedrock API key 进行身份验证并运行推理。如果你使用流式 Converse API（ConverseStream），请在推理配置文件与基础模型的语句中加入 `bedrock:InvokeModelWithResponseStream`。

这些语句协同工作，因此移除其中一条就会拒绝该角色对这个配置文件的跨区域访问，这也为你提供了一种干净的方式，针对特定角色关闭其中任一能力。另一种做法是附加一条显式拒绝，指定 `global.` 或 `us.` 推理配置文件作为对象。

### 全局跨区域推理的服务控制策略注意事项

如果你的组织使用限制区域的服务控制策略（SCP），全局 CRIS 请求会把 `aws:RequestedRegion` 设置为 `unspecified`，而不是某个具体的区域名称。地理 CRIS 请求则会针对配置文件中的每个目标区域进行评估。推荐的做法是使用 `bedrock:InferenceProfileArn` 条件豁免跨区域推理，而不是放宽你的区域允许列表。Amazon Bedrock 在为基础模型授权时会设置该条件键，因此你可以允许 CRIS 路由，同时对其他所有服务保持很窄的允许列表。你的源区域仍然必须在允许列表之内。如果你不愿使用该条件，也可以把目标区域和 `unspecified` 加入允许列表，但这会把这些区域开放给所有服务，而不只是 Amazon Bedrock。如需可直接使用的 SCP 和分步指引，请参阅 [Bedrock CRIS 区域控制 SCP 示例](https://github.com/aws-samples/service-control-policy-examples/blob/main/Region-controls/Deny-access-to-AWS-based-on-the-requested-AWS-region-with-Bedrock-CRIS.json)。

以下 SCP 拒绝在你的批准区域之外进行 Amazon Bedrock 推理（示例中为悉尼和弗吉尼亚北部），并豁免 GPT-5.6 使用的 us. 和 global. 推理配置文件。第一条语句对其他所有服务仍强制实施区域允许列表，因此请把你的组织所使用的全局服务加入其 NotAction 列表。

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyOutsideApprovedRegionsExceptBedrockInvoke",
      "Effect": "Deny",
      "NotAction": [
        "iam:*", "sts:*", "organizations:*", "account:*",
        "route53:*", "cloudfront:*", "waf:*", "wafv2:*", "shield:*",
        "support:*", "trustedadvisor:*", "health:*",
        "budgets:*", "ce:*", "cur:*", "tax:*", "billing:*",
        "bedrock:Invoke*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": ["ap-southeast-2", "us-east-1"] }
      }
    },
    {
      "Sid": "DenyBedrockInferenceOutsideApprovedRegionsUnlessCris",
      "Effect": "Deny",
      "Action": [
        "bedrock:Invoke*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": ["ap-southeast-2", "us-east-1"] },
        "ArnNotLike": {
          "bedrock:InferenceProfileArn": [
            "arn:aws:bedrock:*:*:inference-profile/us.*",
            "arn:aws:bedrock:*:*:inference-profile/global.*"
          ]
        }
      }
    }
  ]
}
```

两种配置文件类型都必须在账户和区域层面启用模型访问权限。完整检查清单请参阅[推理配置文件的前提条件](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-prereq.html)。

## 使用 prompt 缓存

三个 GPT-5.6 变体都支持 `bedrock-runtime` 端点上的 prompt 缓存。当你的请求共享一段很长的 prompt 前缀时，例如系统 prompt 或一组 few-shot 示例，Amazon Bedrock 会缓存该前缀。后续请求复用已缓存的前缀，而不是重新处理它。这会降低被缓存部分的输入成本与延迟。

GPT-5.6 在 Amazon Bedrock 上支持两种缓存模式。隐式缓存是默认模式：服务会在最新的 user 或 tool 消息处放置一个缓存断点，适合通过追加消息而增长的对话。如果你的请求共享一段稳定的前缀，而前缀之后的内容每次请求都会变化，你可以改用显式缓存断点标记稳定内容的结尾。在两种模式中，都请传入可选的 `prompt_cache_key` 参数，以便具有相同前缀的请求被路由到同一个缓存。两种模式都适用于地理与全局推理配置文件。每个缓存断点都需要至少 1,024 个 token 的 prompt 前缀。更多信息请参阅[用 prompt 缓存加速模型推理](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)。

prompt 缓存也会影响配额用量。缓存读取 token 不计入你的 TPM 配额，因此复用已缓存前缀的请求会消耗更少配额。下一节将说明配额如何计算。以下示例使用显式 prompt 缓存，所用的客户端与 `model_id` 来自“入门”一节：

```
# support_policy_manual is a long, stable prefix shared across requests.
# The breakpoint marks the end of the stable content; the user question
# after it changes on every request without invalidating the cached prefix.
completion = client.chat.completions.create(
     model=model_id,
     messages=[
         {
             "role": "system",
             "content": [
                 {
                     "type": "text",
                     "text": support_policy_manual,
                     "prompt_cache_breakpoint": {"mode": "explicit"},
                 }
             ],
         },
         {"role": "user", "content": "A customer wants a refund for a damaged laptop. What must I verify first?"},
     ],
     max_completion_tokens=300,
     prompt_cache_key="support-policy-v1",
 )
```

要确认缓存是否生效，请检查每个响应的 usage 对象。

```
details = completion.usage.prompt_tokens_details
print("Cached tokens:", details.cached_tokens)
print("Written tokens:", details.cache_write_tokens)
```

## 配额管理

GPT-5.6 的按需配额以每分钟 token 数（TPM）管理，并附加到你调用的推理配置文件上：同一模型的地理配置文件与全局配置文件携带独立的配额额度，因此在两者之间切换会改变你所取用的容量池。要查看当前额度或申请提升，请在你应用调用 Amazon Bedrock 的区域中，于 [AWS Service Quotas 控制台](https://console.aws.amazon.com/servicequotas/)搜索 GPT-5.6 模型推理配额。

在估算配额提升申请的规模时，请考虑消耗速率（burndown rate）：即输入与输出 token 折算为限流系统所用 token 配额的比率。输入 token 按 1:1 计入你的配额，而输出 token 可能以更高的倍数消耗配额。对于 GPT-5.6 模型，输出 token 的消耗速率为 10 倍，也就是说一个输出 token 会从你的 TPM 配额中消耗 10 个 token，因此输出密集型工作负载消耗配额的速度会明显快于原始 token 数量所显示的程度。每次请求的计算方式为：

```
Input token count + Cache write input tokens + (Output token count x Burndown rate)
```

例如，一个包含 2,000 个输入 token 和 1,000 个输出 token 的请求会从你的配额中消耗 12,000 个 token。缓存读取 token 不参与这一计算，这正是 prompt 缓存（上一节）对配额管理和成本有效的原因。各模型当前的消耗速率，请参阅 [Amazon Bedrock 配额页面](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-token-burndown.html)。有三项做法可以帮助你避免意外：

- **在部署前申请提升。** 如果你预期使用量较高，请在上线之前通过 Service Quotas 控制台申请提升，而不是等到生产环境出现限流再被动应对。
- **监控利用率。** Amazon CloudWatch 会按推理配置文件实时发布配额利用率指标，因此你可以在用量接近阈值时设置告警，并跟踪历史趋势以规划未来的提升。
- **用真实流量做负载测试**（包括峰值模式和生产规模的 prompt），然后再把工作负载投入生产，并针对你实际会用到的配置文件类型进行验证，因为地理配额与全局配额是分开的。

## 监控与日志

由于 GPT-5.6 请求通过 Bedrock Runtime API 运行，通过地理或全局推理配置文件发出的请求会像按需请求一样出现在 [Amazon Bedrock 模型调用日志](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html)中，推理配置文件 ARN 会与请求和响应负载一起记录（受你的日志配置约束）。你可以把调用日志投递到 Amazon S3 或 Amazon CloudWatch Logs。无论使用哪种配置文件类型，调用日志和指标都会记录在你的源区域，因此即使请求在其他地方被处理，你的可观测性也集中在一处。

涵盖调用次数、token 数、延迟、限流和错误的 Amazon CloudWatch 指标按推理配置文件发布。由于地理配置文件与全局配置文件是不同的资源，它们的指标会分别上报。每次请求的延迟会因请求落到哪个目标区域而略有差异，因此如果你的仪表盘目前按区域拆分指标，可以考虑增加一个按推理配置文件 ID 聚合的视图，因为这个 ID 才是你的应用代码与配额消耗所绑定的标识。用量也会在 AWS Cost Explorer 和 AWS Cost and Usage Report 中分项列出，因此你可以像处理其他 Bedrock 工作负载那样，按模型和配置文件归集 GPT-5.6 的支出。

## 结论

GPT-5.6 模型可通过 `bedrock-runtime` 和 `bedrock-mantle` 两个端点在 Amazon Bedrock 上使用。对于新应用，我们推荐使用 `bedrock-runtime` 端点。它支持 Responses、Chat Completions 和 Converse API，并可与本文介绍的各项能力配合使用，包括跨区域推理配置文件、模型调用日志、Amazon CloudWatch 指标以及 AWS Cost Explorer 中的成本分项。当推理处理需要留在一个地理范围内时（在该范围内的各区域之间扩展），你可以使用**地理配置文件**；当你希望在所有受支持的商业 AWS 区域获得最广泛的容量池时，可以使用**全局配置文件**。无论哪种方式，你的应用都只与一个端点、一个配置文件 ID 打交道，日志、配额和计费都留在你的源区域。如果你的应用已经运行在 `bedrock-mantle` 端点上，并且你有 `In-Region Requirement for usage,`，你可以继续为该工作负载使用 `bedrock-mantle`。它得到完全支持，现有工作负载无需任何改动。

要开始使用，请打开 [Amazon Bedrock 控制台](https://console.aws.amazon.com/bedrock/)，通过推理配置文件向 GPT-5.6 Sol、Terra 或 Luna 发送一条测试 prompt，或者通过 Responses API 以编程方式调用这些模型。在评估生产工作负载规模之前，请查看 [Amazon Bedrock 定价页面](https://aws.amazon.com/bedrock/pricing/)了解当前的 GPT-5.6 费率。如果你的应用需要长上下文（100 万 token）处理，请查看 [Amazon Bedrock 模型区域支持](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)页面了解区域可用性。
