# Rescale 如何使用 Strands Agents 和 AI-DLC 构建 AI 分类代理

每个工程团队都知道这个仪式，Rescale 也不例外。每晚测试套件失败。值班工程师会提取日志，对根本原因进行分类，并将其发送给正确的团队，然后在第二天早上重复该过程。从规模上看，跨分布式服务和数十个存储库，这种仪式变成了隐藏在待命轮换中的全职工作。

[Rescale](https://rescale.com/)是专为AI时代打造的数字工程平台。航空航天、汽车、能源、生命科学、半导体和制造领域的研发和工程团队使用 Rescale 平台加速创新，将智能 HPC、高级建模和仿真、代理数字工程和 AI 物理集成在一个平台上。

除了编码之外，Rescale 在整个工程生命周期中使用人工智能，从规划和设计到实施、测试、审查和运营，同时让工程师对结果负责。人工智能可以提出并执行，但人们可以定义范围、验证工作并批准生产变更。然后，工程师可以专注于架构、产品判断以及操作复杂分布式系统所需的上下文。

在这篇文章中，我们将展示 Rescale 如何使用 AWS 上的 [AI 驱动的开发生命周期 (AI-DLC)](https://github.com/awslabs/aidlc-workflows) 框架来构建智能分类代理。他们从问题定义到分阶段部署仅用了五天时间，并在几周内投入生产。这篇文章还介绍了 Rescale 如何在其工程组织中扩展 AI-DLC。

## 挑战

随着 Rescale 平台的发展，维持其运行的运营开销也随之增加。工程师们花费了大量时间来完成一项重复但关键的任务：对自动化端到端测试失败进行分类。套件中运行了数百个测试用例，当出现故障时，每个警报、错误报告和升级都需要进行分类、确定优先级并路由到正确的团队。布线后，工程师需要从多个日志记录和监控系统以及多个源存储库收集证据，然后才能开始调试。将服务部署到生产中需要通过端到端测试，因此调试这些系统故障是对生产进行新更改的关键路径。

在手动工作流程中，工程师从测试报告转向日志、历史模式和源代码，以对故障进行分类并确定可能的所属团队。由于这些集成测试每周都会发布生产版本，因此未解决的故障可能会使多个团队在允许部署继续进行之前进行数小时的协调。

该团队清楚地了解解决方案的样子：可以自动分类和路由问题的智能代理。他们正在寻找一种结构化的方法，将这种理解转变为生产中的工作系统，并具有足够的结构来将该方法扩展到其他用例。

## 为什么 Rescale 选择 AI-DLC

Rescale 的分类代理是一个范围广泛、时间紧迫的问题。该团队需要一种能够以这种速度发展的开发方法，而无需跳过决定系统是否在生产中运行的架构决策。

[AI 驱动的开发生命周期 (AI-DLC)](https://github.com/awslabs/aidlc-workflows) 是一种开源、以 AI 为中心的软件开发方法，围绕两个想法构建：

- 人工智能执行，人类决定：人工智能生成工作计划、编写代码并提出架构，但它会提出决策点并提出澄清问题而不是猜测。人类验证并引导每一步。
- 团队会议取代异步交接：AI-DLC 使用集中小组会议，而不是一个人单独构建并稍后请求审查：Mob 细化（一起定义需求）和 Mob 构建（在 AI 处理实施时一起构建）。决策是实时发生的。

AI-DLC 很适合，因为困难的部分不是编写代码。它确保人工智能理解团队想要构建的东西。在群众会议中，Rescale 工程师一起回答了人工智能的问题，并在人工智能继续之前批准了每个计划，因此没有任何假设。

## 解决方案概述

Rescale 的分类代理可以自动对夜间端到端测试失败进行分类和路由。它作为 Amazon Elastic Kubernetes Service (Amazon EKS) 上的 Rescale 现有 Argo Workflows 持续集成和持续交付 (CI/CD) 管道中的一个步骤运行。当每晚包含数百个测试用例的 Playwright 套件出现故障时，管道会触发分类代理 Pod。

代理执行以下步骤：

- 在 Amazon Bedrock 上调用 Claude Opus 4.8，将每个故障分类为根本原因类别：基础设施问题、代码错误、不稳定测试或环境问题。
- 从知识库中检索相关的历史故障模式以获取更多背景信息。
- 通过模型上下文协议 (MCP) 查询 pod 日志，以获取支持分类的运行时证据。
- 生成结构化的修复报告，其中包含特定的文件引用、函数名称和建议的修复方案，以便工程师在采取任何操作之前进行审查。

## AI-DLC 研讨会体验

此次活动以为期五天的面对面研讨会的形式进行。 AWS 架构师指导构建，而 Rescale 工程师则通过键盘实际操作，实时共同构建。

### 启动阶段（第 1-2 天）：从愿景到经过验证的需求

该团队首先确定需求范围，捕获愿景文档和技术环境文档中的意图，从而在任何构建开始之前为工作奠定基础。这一意图最初是一个单一的声明，“我们希望人工智能驱动的测试分类能够对故障进行分类并建议补救措施”。该团队以群体形式协作，回答了人工智能生成的 20 多个澄清问题。这产生了一个范围化的需求文档，其中明确定义了第一阶段的边界，并推迟了第二阶段的项目。五个用户故事被合并为四个工作单元：

- 历史故障模式的知识库。
- AI分类代理作为核心分类和修复引擎。
- Argo 工作流程集成，用于触发器、基础设施和部署。
- 用于精度测量和回归门控的评估工具。

人类决策决定了关键界限：第一阶段和第二阶段的内容、优先级排序以及自动拉取请求 (PR) 生成等延迟功能。

### 构建阶段（第 2-4 天）：架构到运行代码

团队定义了接口契约和数据模式，完成了功能和非功能设计问题，并签署了架构。构建过程中出现了两个架构枢轴，团队在改变路线之前验证了每个架构枢轴。

首先，该团队计划在 Amazon Bedrock AgentCore 上托管代理，然后将其迁移到 Amazon EKS，其中 Rescale 已经运行其 Argo Workflows CI/CD 管道。将代理保留在现有集群中意味着无需运行新的运行时以及来自 Argo 的直接触发路径。其次，在早期构建中，代理通过 MCP 从第三方日志服务中提取日志证据。该团队将日志检索移至 Amazon CloudWatch，从而简化了依赖链。 MCP 模式保持不变。只是其背后的源头发生了变化。由于 AI-DLC 将需求和设计决策保留在共享文档中，因此团队对其进行了适当更新，并在不丢失上下文的情况下继续构建。

该代理是使用 Strands SDK 构建的，支持并发故障分析，并采用 JSON 和 HTML 格式的结构化输出，并在 Amazon EKS 上容器化。

到第 4 天，完整的管道已在分段运行：Argo 工作流触发器、分类代理 Pod、MCP 日志查询、知识库检索和结构化分类输出。

### 运营阶段（第 5 天）：评估和移交

该团队构建了一个基于 PyTest 的评估框架，具有实时和存根测试模式，建立了初始分类协议基线来衡量代理并从中进行改进。该代理已向 Rescale 的首席技术官和工程副总裁现场演示，通过特定的文件级修复建议正确分类基础设施故障和真实代码错误。

### AI-DLC 如何将严格性扩展到复杂性

并非每个工作单元都得到相同的待遇。该知识库需要最少的设计，并使用 Terraform 在数小时内完成部署。 Triage Agent 非常严格：架构审查、接口契约、12 个设计问题和迭代代码审查。 Argo Integration 专注于基础设施合同和 IAM。评估线束采用轻量级设计，但实施繁重。 AI-DLC 自动将深度与复杂性相匹配。

到第 5 天结束时，代理已进入分阶段状态，通过测量的精度基线和清晰的生产路径来处理真实的测试失败。

### 生产成果

分诊机从车间开始就投入生产运行。它会自动对每晚的端到端测试故障进行分类，用工程师验证的自动首次通过取代手动首次通过分类。对于每个故障，代理都会生成一份结构化的修复报告，其中包含可操作的后续步骤，而不是原始日志。该代理与人类分类的分类一致性已从最初部署时的 44% 上升到如今的 68%。随着团队迭代黄金数据集和提示工程，它不断改进。

自从分类代理投入生产以来，团队发现在分析测试失败时，阻止生产部署的时间减少了 20%。由于这些测试限制了 Rescale 每周的生产发布，因此这种减少直接体现在变更到达生产的速度上。工程师在重复分类上花费的待命轮换时间也更少。

## 研讨会结束后的生活：从一个智能体到人工智能优先的实践

该研讨会交付了一名生产代理，但其更大的影响在于 Rescale 如何处理工程工作。该分类代理是 Rescale 为人工智能时代提供数字工程能力的更广泛推动的一部分。在内部，Rescale 正在将人工智能带来的这些好处应用到其自己的工程组织中。 AI-DLC 为 Rescale 的工程师提供了一种结构化、可重复的方法来将这一方向付诸实践。

### 在整个组织中扩展 AI-DLC

Rescale 正在评估内部 AI-DLC *卓越中心*，这是一个编写最佳实践并帮助其他团队独立采用该方法的小组。

参与的工程师已经在应用他们所学到的知识。一位工程师指出，这个过程“将成为我未来工作流程的一部分”，不仅适用于构建代理，也适用于人工智能可以贡献的任何复杂的开发工作。

### 更广泛的人工智能原生开发

Rescale 目前正在将 AI-DLC 纳入新工程仿真产品的标准软件开发生命周期中。该框架将仿真领域的专业知识、产品要求、平台架构、验证和操作整合到一个结构化设计流程中。团队尽早解决关键问题，在可执行规范中捕获经过审查的决策，并为编码代理提供具有明确验收标准的重点工作。这缩短了从产品概念到验证实施的路径，同时工程师仍然对产品的正确性负责。

同样的方法已经被用于产品支持平台工作和代理系统：

- HPC模拟应用程序目录管理。
- 容器漏洞跟踪和修复，以满足政府合规性要求。
- 基于工作流的云编码代理。

＃＃ 结论

对于分类代理来说，AI-DLC 最有用的输出并不是代码本身。这是从最初的想法到经过审查的系统设计的结构化路径：澄清问题、范围要求和评估标准。

该规范为编码代理提供了一个更狭窄、更明确的问题来解决。团队可以使用代理根据人类已经审查过的决策进行集中构建，而不是要求代理在实现架构时推断架构。结果是更加集中、可审查的输出，更容易集成和改进。对于 Rescale 来说，这是可重复的模式：使用 AI-DLC 构建设计对话，将决策转化为规范，然后使用编码代理加速实施。

## 要点

- **从实际问题开始。** Rescale 的分类代理之所以成功，是因为它解决了工程挑战。问题驱动解决方案，而不是相反。
- **人类监督会加速，而不是减速。** 改进系统的每个架构枢轴都来自对人工智能提案的人类验证。人工智能生成并由人类验证的暴徒格式比单独工作更快。
- **AWS 堆栈提供了代理所需的每一层。** Amazon Bedrock 在 Rescale 已使用的环境中提供了用于分类的基础模型访问权限，因此团队可以构建分类工作流程，而无需承担额外的模型基础设施开销。 Strands SDK 提供了代理框架，Amazon EKS 在 Rescale 的现有管道中托管了容器化代理。
