# 用 AWS Batch 配额管理跨团队借调 SageMaker Training 作业资源

随着 [AWS Batch](https://aws.amazon.com/batch/) 支持 Amazon SageMaker Training 作业，客户多了一种全新的全托管方式来为机器学习（ML）训练工作负载排队、调度和重试，而不必自建基础设施——他们直接用上 AWS Batch 的排队与调度能力即可。当组织把人工智能与机器学习（AI/ML）运营规模化、接入更多团队时，协调对共享图形处理器（GPU）容量的访问，会给管理员带来额外的沟通、协调与配置开销。这些开销包括单独建队列、调整容量上限，以及小心翼翼地编排对的负载在对的时间拿到对的资源。AWS Batch 的一个核心价值主张就是帮客户提高算力利用率；而训练环境越大，用现有容量多做些事的机会也就越大。

从客户如何管理多团队训练环境倒推，我们听到一个一致的需求：给我们一个办法，能按团队或项目定义配额、自动共享闲置容量，并且让最高优先级的负载先跑。正是这个需求推动我们构建了[配额管理](https://docs.aws.amazon.com/batch/latest/userguide/quota-management.html)，AWS Batch 的一项新调度能力。管理员可以用它把算力划分为 quota share（配额份额），按团队、项目或工作负载来组织。每个 quota share 都有一套可配置的资源共享策略，在最大化 GPU 利用率的同时，于最关键的时候守住每个团队自己那份配额。

这篇文章会展示配额管理是怎么工作的，包括如何配置带借出与借入策略的 quota share、如何为高优先级负载设置 share 内抢占，以及如何用 SageMaker Python SDK 上手。

## Quota share 与抢占

管理员可以通过为不同主体（比如单个团队或单个项目）定义 quota share，来分配并共享紧张的 GPU 资源。每个 quota share 都包含计算配额（容量上限）以及针对闲置算力的资源共享策略。这些策略决定闲置算力是要一直预留到有作业到来（`RESERVE`）、借给那些手上还有活的 quota share（`LEND`），还是既在闲置时借出、又在本份额有活时借入（`LEND_AND_BORROW`）。

一个 quota share 以虚拟队列的形式运作，层级嵌套在它关联的 job queue 里面。在为某个 job queue 调度作业、遍历其关联的 quota share 时，AWS Batch 会优先选择那些还没用到容量上限的份额。如果有作业进入一个已经把自己的容量借出去的 quota share，AWS Batch 会执行跨份额抢占，把资源为出借的那个份额收回，管理员因此不必自己去追踪哪些作业占着借来的容量并手动终止它们。如果有作业进入一个已经达到或超过容量上限的 quota share，AWS Batch 会检查是否有可以从别的份额借来的可用容量；如果有，负载就能用上那些本会闲置的算力跑起来。

配置 quota share 时，你可以打开基于优先级的 share 内抢占。跨份额抢占是在作业进入出借方份额时把借出的容量收回来，而 share 内抢占则会抢占那些处于 SCHEDULED、STARTING 或 RUNNING 状态的低优先级作业，让排在队列前面的高优先级作业更早开始运行。

## 配置配额管理资源

要用上新的配额管理能力，需要创建一个包含 `quotaSharePolicy` 的 [Scheduling Policy](https://docs.aws.amazon.com/batch/latest/APIReference/API_CreateSchedulingPolicy.html)、一个用具体实例类型来表达其容量上限的 [Service Environment](https://docs.aws.amazon.com/batch/latest/APIReference/API_CreateServiceEnvironment.html)，以及一个[把两者连接起来的 SageMaker Training 作业队列](https://docs.aws.amazon.com/batch/latest/APIReference/API_CreateJobQueue.html)。在那之后，你就可以把 quota share 关联到某个 job queue。用户指南里有[配置配额管理资源](https://docs.aws.amazon.com/batch/latest/userguide/create-quota-management-resources.html)与[配置 quota share](https://docs.aws.amazon.com/batch/latest/userguide/create-quota-shares.html)的 AWS Command Line Interface（AWS CLI）和控制台示例。与 SageMaker Python SDK v3 里 [aws_batch](https://github.com/aws/sagemaker-python-sdk/tree/master/sagemaker-train/src/sagemaker/train/aws_batch) 模块集成的配额管理端到端示例，放在一个[示例 notebook](https://github.com/aws/sagemaker-python-sdk/blob/master/v3-examples/training-examples/aws_batch/sm-training-queues_quota-management.ipynb) 里。在这个示例中，我们会逐段过一遍概括关键组件的代码片段，并借助 notebook 里的辅助函数创建一个 Scheduling Policy、一个 Service Environment、一个 Job Queue 和三个 Quota Share。

这里配置的三个 quota share 代表三个不同的项目，每一个都设了相同的容量上限：一台 `ml.g5.xlarge` 实例。QS1 这个 quota share 代表后台作业。就这个项目而言，你希望先跑最重要的那个后台作业，并尽可能多地借入富余容量。在这个份额里没有作业是紧急的，抢占也可以接受，因为所有作业都用了 checkpoint。这个 quota share 使用 `LEND_AND_BORROW` 资源共享策略，并且打开了 share 内抢占。于是同一个份额内优先级更高的作业可以抢占那些正在运行的低优先级作业。

```
from sagemaker.train.aws_batch.boto_client import get_batch_boto_client
from utils.aws_batch_resource_management import AwsBatchResourceManager, QuotaShareConfig, create_quota_management_resources

INSTANCE_TYPE = "ml.g5.xlarge"

# Create SchedulingPolicy, ServiceEnvironment, JobQueue, and QuotaShares
resource_manager = AwsBatchResourceManager(get_batch_boto_client())
qs1 = QuotaShareConfig(
    name="QS1",
    capacity_unit=INSTANCE_TYPE,
    max_capacity=1,
    in_share_preemption=True,
    sharing_strategy="LEND_AND_BORROW",
    borrow_limit=200
)
```

QS2 代表中等优先级的负载。选这套配置的团队宁愿等容量腾出来，也不愿忍受额外的抢占——这些抢占来自被借出的容量被收回，或者来自更高优先级作业提交引发的 share 内抢占。它适合较短的作业，或者提交的作业彼此优先级都相近的情形。这个份额仍然能受益于调度作业时会考虑作业优先级。提交的作业会触发 AWS Batch 收回运行它们所需的任何已借出容量。

```
qs2 = QuotaShareConfig(
    name="QS2",
    capacity_unit=INSTANCE_TYPE,
    max_capacity=1,
    in_share_preemption=False,
    sharing_strategy="LEND"
)
```

QS3 代表要尽快开始、尽量少被打断的负载。它被配置为预留容量，既不向别的 quota share 借出，也不从别的份额借入。它不会遭遇跨份额抢占，因为它的负载不会超出容量上限。再加上 share 内抢占也关着，只要容量上限不变，提交到这个份额的负载就不会被 AWS Batch 抢占。

```
qs3 = QuotaShareConfig(
    name="QS3",
    capacity_unit=INSTANCE_TYPE,
    max_capacity=1,
    in_share_preemption=False,
    sharing_strategy="RESERVE"
)
```

这些 quota share 配置是示例 notebook 中 `create_quota_management_resources` 函数的输入；该函数还会用选定的这几个常量名配置与之对应的 Scheduling Policy、Service Environment 和 Job Queue。

```
SCHEDULING_POLICY_NAME = "my-qm-scheduling-policy"
JOB_QUEUE_NAME = "my-sm-training-qm-jq"
SERVICE_ENVIRONMENT_NAME = "my-sm-training-qm-se"

resources = create_quota_management_resources(
    resource_manager=resource_manager,
    scheduling_policy_name=SCHEDULING_POLICY_NAME,
    job_queue_name=JOB_QUEUE_NAME,
    service_environment_name=SERVICE_ENVIRONMENT_NAME,
    capacity_unit=INSTANCE_TYPE,
    max_capacity=3,
    quota_share_configs=[qs1, qs2, qs3]
)
```

## 向 QS1 提交 SageMaker Training 作业

SageMaker Python SDK 里的 [aws_batch](https://github.com/aws/sagemaker-python-sdk/tree/master/sagemaker-train/src/sagemaker/train/aws_batch) 模块已经做了扩展，可以用编程方式把 SageMaker Training 作业提交到启用了配额管理的 AWS Batch job queue。为了演示这些新能力，我们用一个提交到该队列的 Hello World `ModelTrainer`。下面的代码片段会根据所选的 Region 和实例类型确定要使用的 image URI。

```
import logging

logging.basicConfig(
    level=logging.INFO, format="%(asctime)s - %(name)s - %(levelname)s - %(message)s"
)
logging.getLogger("botocore.client").setLevel(level=logging.WARN)
logger = logging.getLogger(__name__)

from sagemaker.core.helper.session_helper import Session
from sagemaker.core import image_uris

session = Session()

image_uri = image_uris.retrieve(
    framework="pytorch",
    region=session.boto_session.region_name,
    version="2.5",
    instance_type=INSTANCE_TYPE,
    image_scope="training",
)
```

我们在一个基础的 hello world 模型训练示例里使用这个 image URI：

```
from sagemaker.train.model_trainer import ModelTrainer
from sagemaker.train.configs import SourceCode, Compute, StoppingCondition

TRAINING_JOB_NAME = "hello-world-simple-job"
MAX_RUN_TIME = 300

source_code = SourceCode(command="echo 'Hello World'")

model_trainer = ModelTrainer(
    training_image=image_uri,
    source_code=source_code,
    base_job_name=TRAINING_JOB_NAME,
    compute=Compute(instance_type=INSTANCE_TYPE, instance_count=INSTANCE_COUNT),
    stopping_condition=StoppingCondition(max_runtime_in_seconds=MAX_RUN_TIME),
)
```

要在 SageMaker Python SDK 里使用这个 job queue，把队列名传给 `aws_batch` 模块中的 `TrainingQueue` 构造函数。

```
from sagemaker.train.aws_batch.training_queue import TrainingQueue, TrainingQueuedJob

# Construct the queue object using the SageMaker Python SDK
queue = TrainingQueue(JOB_QUEUE_NAME)
logger.info(f"Using queue: {queue.queue_name}")
```

接着我们可以向 QS1（我们的后台作业 quota share）提交三个作业。第一个提交的作业优先级最高，随后是中等优先级作业，最后是最低优先级作业。由于 QS1 和 QS2 当前都没有在跑任何东西，应当会有相当于两台实例的作业开始运行，对应最先提交的那两个作业（它们的相对优先级最高）。注意因为这只是一个 hello world 训练作业，它不需要数据；但通常一个 `ModelTrainer` 是需要数据才能完成训练的。

```
from utils.aws_batch_resource_management import JobStatus, await_jobs, list_jobs_by_quota_share

# Submit three jobs to QS1, all with different priorities to guarantee dispatch ordering.
qs1_job_high: TrainingQueuedJob = queue.submit(job_name="qs1_job_high", training_job=model_trainer, quota_share_name=qs1.name, priority=3, inputs=None)
qs1_job_med: TrainingQueuedJob = queue.submit(job_name="qs1_job_med", training_job=model_trainer, quota_share_name=qs1.name, priority=2, inputs=None)
qs1_job_low: TrainingQueuedJob = queue.submit(job_name="qs1_job_low", training_job=model_trainer, quota_share_name=qs1.name, priority=1, inputs=None)

logger.info(f"Submitted jobs: {qs1_job_high.job_name}, {qs1_job_med.job_name}, {qs1_job_low.job_name}")
logger.info(f"Waiting for jobs to transition...")

# qs1_job_high is dispatched first using capacity from QS1, and qs1_job_med is dispatched second borrowing idle capacity from QS2
await_jobs([([qs1_job_high, qs1_job_med], JobStatus.dispatched() | JobStatus.terminal())])
list_jobs_by_quota_share(queue, [qs1.name, qs2.name, qs3.name], JobStatus.active())
```

## 向 QS2 提交作业会触发跨份额抢占以收回借出的容量

拥有 QS2 的那个团队可能突然发现自己有活要干，于是向 QS2 提交一个作业。这么做的结果，是把容量从 QS1 那边抢占回来——QS1 正在借用那份容量（QS3 的容量并没有配置成可借）。这就是一次跨份额抢占。

```
# When a job is submitted to QS2, it will preempt its capacity back from QS1
qs2_job_1: TrainingQueuedJob = queue.submit(job_name="qs2_job_1", training_job=model_trainer, quota_share_name=qs2.name, priority=1, inputs=None)

logger.info(f"Submitted job {qs2_job_1.job_name}")
logger.info(f"Waiting for jobs to transition...")

await_jobs([
    ([qs2_job_1], JobStatus.dispatched() | JobStatus.terminal()),
    ([qs1_job_med], {JobStatus.RUNNABLE}) # Lowest priority QS1 job will be preempted
])
list_jobs_by_quota_share(queue, [qs1.name, qs2.name, qs3.name], JobStatus.active())
```

## 更新 QS1 内的作业优先级会触发 share 内抢占，让最高优先级作业先跑

如果一位研究员发现 QS1 里那个仍处于 RUNNABLE 状态的 `qs1_job_low` 作业因为优先级变化必须现在开始运行，他可以用新的 [UpdateServiceJob](https://docs.aws.amazon.com/batch/latest/APIReference/API_UpdateServiceJob.html) API 提高 QS1 中一个已提交作业的优先级。由于没有可借来的可用容量，这会触发一次 share 内抢占，让当前正在运行的那个作业被抢占，`qs1_job_low` 于是得以开始。

```
# Updating qs1_job_low to be the highest priority job in QS1
qs1_job_low.update(scheduling_priority=4)

logger.info(f"Updated job {qs1_job_low.job_name} to increase its priority")
logger.info(f"Waiting for jobs to transition...")

await_jobs([
    ([qs1_job_low], JobStatus.dispatched() | JobStatus.terminal()),
    ([qs1_job_high], {JobStatus.RUNNABLE}) # High priority job will preempt lower priority jobs within the same quota share
])
list_jobs_by_quota_share(queue, [qs1.name, qs2.name, qs3.name], JobStatus.active())
```
