# 使用 Amazon Bedrock AgentCore 构建面向商业智能的 AI agent

[OPLOG](https://www.oplog.io/) 是一家由 AI 和机器人驱动的技术型履约（fulfillment）公司，每月在 Türkiye、英国和德国为大型品牌和全球交易市场处理数百万件商品。OPLOG 运营着一种与客户无关（customer-agnostic）的履约模式，多个品牌共享仓库基础设施、工人和自主机器人，因此它面临许多 B2B 组织共有的挑战：业务数据分散在多个系统中，导致洞察延迟，以及每天消耗数小时生产时间的人工报表。

为解决这一挑战，OPLOG 使用部署在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上的 AI agent 构建了一套可用于生产的商业智能（BI）系统。该方案自主处理业务交易，在销售管道管理、数据质量管控和潜在客户研究方面提供实时洞察。结果显示出可衡量的业务影响：销售周期缩短 35%、CRM 数据完整度提升 91%、人工研究时间减少 98%。

本文将介绍 OPLOG 如何使用 [Strands Agents SDK](https://strandsagents.com/latest/) 开发三个 AI agent、将它们部署到 Amazon Bedrock AgentCore，并把 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 与 Anthropic 的 Claude Sonnet 以及 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 集成以实现检索（RAG）。我们描述其架构、实现方式和业务成果，展示 AI agent 如何改变 BI 运营。

## OPLOG 的业务与数据挑战

OPLOG 的快速增长带来了传统 BI 系统无法应对的运营复杂性。该公司的数据分散在多个互相隔离的系统中：Hubspot CRM 保存销售管道信息，通信系统存储客户对话，Microsoft Teams 承载沟通上下文，Databricks 数据仓库维护运营指标。每个系统独立运行，形成了阻碍全面 BI 的数据孤岛。

这种碎片化造成了具体的运营痛点。2 从不同系统获取报表、汇总信息并准备更新。这种人工流程意味着洞察总是来得太晚——周报错过了 60% 的机会，因为等到分析完成时，交易要么已经推进、要么已经停滞。由于销售代表被人工录入要求压得喘不过气，录入的信息也不一致，CRM 数据质量因此受损。运营团队在问题发生数小时后才发现问题，被迫做出被动响应，而不是主动干预。

OPLOG 量化了 BI 碎片化带来的可观运营成本，包括洞察延迟导致的机会损失、人工报表占用生产时间的开销、数据质量不一致对决策的影响，以及被动运营造成的低效响应。公司需要一个能够自主跨系统处理数据、提供实时洞察、消除人工报表开销，同时保持数据质量并支持主动决策的方案。

## 解决方案概览

OPLOG 开发了三个 AI agent，每个聚焦一个特定的 BI 领域。这些 agent 彼此独立运行、互不通信；每个 agent 处理来自特定数据源的数据，并提供有针对性的洞察：

- **Deal Analyzer Agent** – 该 agent 按与业务运营相一致的调度定期执行，分析 Hubspot 中近期有活动的交易。它会依据 OPLOG 的销售方法论校验交易、识别缺失字段，并把完成状态报告到 Microsoft Teams。该 agent 通过自动化日报改善销售管道的数据质量与方法论遵循度。
- **Sales Coach Agent** – 该 agent 在交易阶段发生变化时响应 Hubspot webhook 事件，依据 OPLOG 的商业模式（仅 B2C、仅 B2B，或 B2B 与 B2C）校验必填字段，并自动为缺失信息创建任务。该 agent 实时执行数据质量标准，帮助防止交易在数据不完整的情况下推进。
- **Lead Insight Agent** – 当 Hubspot 中新增营销线索时，该 agent 会被触发，分析该线索在六个社交媒体环境（Instagram、LinkedIn、Facebook、YouTube、Twitter、TikTok）中的数字足迹。它应用 OPLOG 的资格判定方法论评估理想客户画像（ICP）匹配度，汇编带匹配判定的完整画像，并把研究报告投递到 Microsoft Teams，从而最大限度减少人工潜在客户研究，同时把销售精力集中到高潜力机会上。

该架构使用 Amazon Bedrock AgentCore 作为 agent 的部署环境。OPLOG 使用 Strands Agents SDK 开发 agent，该 SDK 提供定义 agent 行为、自定义工具和集成点的框架。每个 agent 都使用带 Anthropic 的 Claude Sonnet 的 Amazon Bedrock 进行推理——分析数据、依据业务规则推理并生成洞察。Amazon Bedrock Knowledge Bases 实现 RAG，使 agent 能够从存储在 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）中的销售手册、产品目录和方法论文档中检索相关上下文。

[AWS Lambda](https://aws.amazon.com/lambda/) 函数负责外部系统集成，把 agent 连接到 Hubspot、Microsoft Teams 和外部数据源。[Amazon EventBridge](https://aws.amazon.com/eventbridge/) 为 Deal Analyzer Agent 调度 agent 执行，而 Hubspot webhook 实时触发 Sales Coach 和 Lead Insight Agent。[AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-onboarding.html) 提供全面的监控，通过 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 跟踪 agent 调用、性能指标和成本。OPLOG 只为 agent 执行付费，无需管理任何基础设施。[AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-toolkit.html) 根据工作负载从零自动扩展到数千个会话，部署更新也无需停机。

以下各节详细介绍 OPLOG 如何实现每个 agent 以应对特定的 BI 挑战。Deal Analyzer Agent 提供定时的管道报告，Sales Coach Agent 实时执行数据质量，Lead Insight Agent 自动化潜在客户研究。虽然这些 agent 服务于不同目的，但它们共享同一技术基础：Amazon Bedrock、Amazon Bedrock Knowledge Bases 和 Strands Agents SDK，并全部部署到 Amazon Bedrock AgentCore。

## Deal Analyzer Agent：每日管道质量报告

OPLOG 的销售经理每天都面临一个挑战：逐一查看几十笔交易，找出其中信息缺失的那些。人工审阅要花数小时，而且往往直到交易停滞才发现问题。Deal Analyzer Agent 通过按计划自动运行分析来帮助解决这个问题，把突出显示哪些交易需要关注的完整报告投递到 Microsoft Teams。

下图展示了该 agent 的架构：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/09/ml-20112-1-1024x364.png)

EventBridge 按与业务运营相一致的调度触发 Lambda。Lambda 调用 AgentCore Runtime，后者执行 agent 来分析 Hubspot 中近期有活动的交易。该 agent 依据 OPLOG Way 方法论校验这些交易，并把格式化报告发送到 Microsoft Teams。

OPLOG 使用 Strands Agents SDK 构建该 agent，并配有三个专用工具。`hubspot_properties()` 工具通过 Lambda 从 Hubspot 的 API 获取交易数据和元数据。`deal_enrichment()` 工具执行校验逻辑，依据带商业模式专属规则的 OPLOG Way 方法论分析交易。`send_teams()` 工具把结果格式化为结构化报告，并通过 webhook 投递。参见以下代码：

```
from strands_agents import Agent, tool
class DealAnalyzerAgent(Agent):
    @tool
    def hubspot_properties(self, deal_id: str) -> dict:
        """Retrieve deal data and metadata from Hubspot"""
        pass
    
    @tool
    def deal_enrichment(self, deal_data: dict) -> dict:
        """Analyze deal against OPLOG Way methodology"""
        pass
    
    @tool
    def send_teams(self, report: dict) -> bool:
        """Format and deliver report to Microsoft Teams"""
        pass
```

校验逻辑要处理 OPLOG 与客户无关的履约模式的复杂性。不同的交易需要不同的校验，取决于是仅 B2C、仅 B2B，还是 B2B 与 B2C。对于 B2C 交易，agent 校验 B2C 专属字段加上必填字段。对于 B2B 交易，它校验 B2B 专属字段。对于混合交易，它校验两类字段。条件逻辑贯穿全程——对 B2C 交易，数量校验要求至少一种库存数量类型，而对 B2B 交易则同时要求出库量和库存量。

该 agent 使用带 Anthropic 的 Claude Sonnet 的 Amazon Bedrock 来解释业务规则，并区分有意填零的取值与缺失字段——这是一个需要超出简单空值检查的推理的细微判断。Amazon Bedrock Knowledge Bases 使用业界标准的嵌入模型和向量数据库，把 OPLOG Way 方法论存储在 Amazon S3 中。校验交易时，agent 用自然语言查询知识库，Anthropic 的 Claude 应用检索到的上下文，为每笔交易的阶段和商业模式确定正确的校验规则。

投递到 Microsoft Teams 的报告包含交易完成状态、缺失字段详情、优先级排序和可执行的建议。销售经理一天开始时就能清楚看到哪些交易需要关注。该实现消除了大量每日人工审阅时间，并把阶段准确率提升了 91%。AgentCore Observability 通过 CloudWatch 跟踪处理时间和报告投递成功率。

## Sales Coach Agent：实时校验与任务自动化

Sales Coach Agent 采用与 Deal Analyzer Agent 不同的思路——它不是报告问题，而是实时执行数据质量。当销售代表在阶段之间移动交易时，该 agent 立即校验必填字段，并为缺失的信息创建任务。这有助于防止交易在数据不完整的情况下推进，确保管道保持干净。

下图展示了该 agent 架构：![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/09/ml-20112-2-1024x487.png)该架构使用 Hubspot webhook 在交易阶段发生变化的那一刻触发 Lambda。Lambda 调用 AgentCore Runtime，后者校验交易并在需要时创建任务——全部在 10 秒内完成。这种基于 webhook 的方式意味着销售代表在尝试推进交易时能获得即时反馈。该 agent 使用两个用 Strands Agents SDK 构建的工具。`analyze_deal_properties()` 工具从 Hubspot 获取交易数据，并依据该交易的运营模式和新的阶段校验必填字段。`assign_task()` 工具创建带详细说明的高优先级任务，把它们关联到交易，并分配给交易负责人。

参见以下代码：

```
from strands_agents import Agent, tool
class SalesCoachAgent(Agent):
    @tool
    def analyze_deal_properties(self, deal_id: str) -> dict:
        """Validate required fields based on operating model"""
        pass
    
    @tool
    def assign_task(self, deal_id: str, task_description: str) -> bool:
        """Create and assign validation task to deal owner"""
        pass
```

该校验逻辑与 Deal Analyzer Agent 的商业模式规则一致，但它是对单笔交易实时运行，而非批量处理。该 agent 使用同一个存储 OPLOG Way 方法论的 Amazon Bedrock 知识库，查询它来确定特定阶段与商业模式组合下哪些字段是必填的。Anthropic 的 Claude Sonnet 解释这些规则，并对有意填零的取值和缺失字段做出关键区分。

任务描述具体且可执行。任务不会写成泛泛的“补全缺失字段”，而是明确指出需要完成哪些字段、为什么当前阶段要求这些字段，以及如何完成它们的指引。这种清晰度帮助销售代表快速解决问题，而无需查阅文档或询问经理。

该实现把交易质量提升了 91%，并实现超过 96% 的字段完成率。从阶段变化到任务创建的平均响应时间低于 10 秒，任务创建成功率超过 99.2%，校验准确率超过 97%，这些均通过 CloudWatch 监控。

## Lead Insight Agent：自动化潜在客户研究

OPLOG 的销售代表过去要花大量时间研究每一个新潜在客户——手动搜索 LinkedIn、查看公司网站、审阅社交媒体存在，并试图理解其商业模式。Lead Insight Agent 自动化了整个流程，帮助在新联系人加入 Hubspot 后的 2–5 分钟内给出完整画像。

下图展示了该 agent 的架构：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/09/ml-20112-3-1024x346.png)

该架构使用 Hubspot webhook 在新增联系人时触发 Lambda。Lambda 带着联系人详情调用 AgentCore Runtime，agent 并行搜索六个社交媒体环境：Instagram、LinkedIn、Facebook、YouTube、Twitter 和 TikTok。分析完数字足迹后，它把完整报告投递到 Microsoft Teams。

该 agent 使用 [AgentCore Browser](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-onboarding.html) 进行社交媒体发现。AgentCore Browser 处理网页导航、JavaScript 渲染和内容抽取——免去了自建网页抓取基础设施的需要。agent 提供搜索查询和 URL 模式（例如对 LinkedIn 使用 `site:linkedin.com/in/ [name] [company]`），AgentCore Browser 返回来自各环境的结构化内容。它由 AWS 维护，能处理反机器人防护，并随 agent 调用自动扩缩容。

该 agent 的价值除数据采集能力之外，还在于它的分析。带 Anthropic 的 Claude Sonnet 的 Amazon Bedrock 分析抽取出的内容，以识别相关画像、总结数字足迹并生成个性化的接触建议。agent 应用 OPLOG 的资格判定方法论评估 ICP 匹配度，依据商业模式、行业和数字足迹判断该线索是否符合 OPLOG 的目标客户特征。

这种 ICP 评估改变了销售团队的工作方式。他们不再平等对待所有线索，而是可以优先处理高潜力机会。报告包括六个环境中的社交媒体存在、显示潜在客户分享和讨论什么的内容分析、从其数字足迹推导出的商业模式洞察、带推理的 ICP 匹配判定，以及用于个性化外联的下一步建议。

该实现把潜在客户研究时间减少了 98%，同时提供比人工研究更全面的情报。该 agent 实现超过 92% 的社交媒体发现成功率和超过 88% 的网站可访问率。销售团队反馈，初次外联的互动率更高，因为他们在接触之前就已掌握相关上下文。AgentCore Observability 通过 CloudWatch 跟踪分析时间、覆盖范围和 Teams 投递成功率（超过 99.5%）。

## 业务影响与技术成果

销售表现显著改善。平均交易周期缩短 35%。线索转化率提升 28%。CRM 数据完整度提升了 102%。每日报表时间减少 92%。销售代表生产力提升 40%。

运营效率的提升同样可观。问题检测时间减少 81%。解决响应时间改善 83%。流程合规性提升 52%。决策速度加快 70%。

技术性能指标显示出生产级的可靠性。系统提供接近实时的性能，可用性达 99.9%。系统每天跨各 agent 处理数千个业务事件。成本效益通过随用量扩展的无服务器架构实现，基础设施成本显著低于传统系统。

运营效率的改善带来了可衡量的 ROI，显著超出 AI agent 系统的基础设施成本。

## 结论

OPLOG 的实施表明，部署在 Amazon Bedrock AgentCore 上的 AI agent 能够改变 BI 运营。该系统每天自主处理数千个业务交易，带来 35% 更快的销售周期、92% 的报表时间缩减和 99.9% 的正常运行时间。无服务器架构的成本效益——相比传统基础设施有显著降低——使先进的 AI 驱动 BI 既易获得又可扩展。

> “我们相信 AI 能够彻底改变商业运营。以 Amazon Bedrock AgentCore 为基础，我们不仅是在改善销售周期——我们正在重新定义履约公司如何大规模竞争。”OPLOG 创始人兼 CEO Halit Develioğlu 表示。

该方案的成功源自若干架构决策：使用 Amazon Bedrock AgentCore 进行 agent 部署，消除了基础设施管理的开销；用 Amazon Bedrock Knowledge Bases 实现 RAG，把业务逻辑与 agent 代码分离，无需重新部署即可更新；使用 Anthropic 的 Claude Sonnet 进行推理，提供了复杂业务规则解释所需的推理能力；集成 EventBridge 用于调度和事件驱动触发，使自动化执行与实时执行都能实现。

OPLOG 继续扩展该系统，增加更多 agent、用于处理图像和文档的多模态能力，以及针对特定业务场景优化 agent 行为的自定义微调。公司的路线图还包括若干正在开发中的运营与商业 AI 能力。

有兴趣构建类似 AI agent 方案的组织可以从 Amazon Bedrock AgentCore 入手，查阅开发者指南、用 Strands Agents SDK 为某个具体业务流程试做一个 agent，并部署到 AgentCore 的无服务器运行时。按执行付费的模式意味着团队可以从小规模开始，在验证结果的同时逐步扩展。
