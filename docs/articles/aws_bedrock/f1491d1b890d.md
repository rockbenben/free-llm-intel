# 用按需与批处理 pipeline 动态抽取数据

许多公司拥有大量纸质或电子文档，其中蕴含着尚未被挖掘的商业情报。随着[生成式 AI](https://aws.amazon.com/generative-ai/)的发展，各种大语言模型可以被用来从这些文档中准确抽取相关数据。本文展示一条智能文档处理 pipeline，它在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上同时提供按需推理与批处理推理两种选项，使文档处理在时间和成本上具备灵活性。对时间敏感的请求可以使用按需推理选项，而批处理推理选项在成本上最为优化。本文还会说明如何在文档级别动态指定大语言模型和提示词，让你用同一套 pipeline 处理多种类型的文档。

## 方案概览

如果你和我们的一位客户一样，待处理队列里堆着数亿份扫描版 PDF 格式的土地租赁文件（只含图像、没有可编辑文本的 PDF，例如本例中以 PDF 形式保存的扫描土地租赁件），而且每天仍有新文档不断涌入，那么这就是一个可以用来从这些文档中高效抽取数据的方案。如下图所示，该方案构建了按需与批处理两条推理 pipeline，并提供动态调用它们的机制。借助在 Amazon Bedrock [Prompt Management](https://aws.amazon.com/bedrock/prompt-management/) 中管理的精心设计的提示词，可以从格式与惯例往往各不相同的扫描 PDF 或文本文件中抽取并标准化数据。

![架构图，展示基于 Amazon Bedrock 的按需推理 pipeline 与批处理推理 pipeline](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/02/ML-18264-1.png)

左侧的 pipeline 是按需 pipeline，它逐份从文档中抽取数据，在数秒内返回结果。因此它适合对时间敏感的请求。

右侧的 pipeline 是批处理推理 pipeline，它在单个 Amazon Bedrock [批处理推理](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference-create.html)作业中处理多个文档请求，模型调用会以异步方式处理。在两条 pipeline 中，用户都可以在请求里指定 prompt ID 与版本，相应的提示词文本会从 Amazon Bedrock Prompt Management 中获取。

以下各节将详细描述这两条 pipeline。

## 1. 按需推理 pipeline

按需推理 pipeline 中会创建一个 [AWS SQS](https://aws.amazon.com/sqs/) 先进先出（FIFO）队列。当一条包含文档 ID、LLM 模型 ID、prompt ID/版本和系统 prompt ID/版本的队列消息到达时，它会触发一个 AWS Lambda 函数。该函数从指定的 Amazon S3 存储桶取回 PDF 文档，把 PDF 页面转换为 PNG 图像，从 Amazon Bedrock Prompt Management 取回相关提示词，组装调用 LLM 的消息，并把结果保存到 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 表中。

### 1.1. AWS SQS FIFO 队列

当单份文档到达时，使用 AWS SQS FIFO 队列来触发 Amazon Bedrock 推理。使用 FIFO 队列的主要原因如下：

- 可靠的消息投递 – 确保每条消息都恰好投递一次。
- 先进先出（FIFO）处理 – 维持严格顺序，使处理过程更具可预测性。
- 消息分组 – Message Group ID 属性确保组内消息按顺序处理。每个生产者可以使用唯一的 Message Group ID，为相关消息保持顺序。

#### 队列消息是如何创建的？

队列消息可以在外部用 AWS CLI 或 AWS SDK API 创建。下面是一个 AWS CLI 命令示例：

```
aws sqs send-message --queue-url https://sqs.us-east-1.amazonaws.com/1111111111/ondemand-data-pipeline-queue.fifo --message-group-id "1" --message-body "msg 1" --message-attributes file://message_txt.txt
```

本示例中的 `message_txt.txt` 文件是一个 JSON 文件，包含应用所需的消息属性。详情请见下文“测试 pipeline”一节。

在 Amazon Bedrock 返回抽取到的数据之后，Lambda 函数会删除该队列消息。

### 1.2. Lambda 函数 – 队列消息处理与推理

#### 1.2.1 获取文档、转换为图像，并切分大文件

Lambda 函数使用队列消息中的 `s3_location` 属性下载文档。如果文档是扫描版 PDF，则会被转换为图像，供多模态模型理解。

截至撰写本文时，Claude 4 Sonnet 模型在每次多模态调用中最多只允许 20 张图像。因此，如果一份文档包含超过 20 页图像，就必须按每 20 页切分成块。`doc_id`、`chunk_count` 和 `chunk_id` 会连同抽取结果与模型性能指标一起存入 Amazon DynamoDB 表。

- `doc_id`：文档的标识符
- `chunk_count`：该文档的总块数
- `chunk_id`：文档每一块的标识符

#### 1.2.2. 从 Amazon Bedrock Prompt Management 取回提示词

土地租赁文档的格式各不相同 – 有的用编号列表呈现地块属性，有的用表格，有的甚至用土地图纸。因此，针对每种文档格式使用不同的提示词能提升抽取准确率。

LLM 调用所使用的提示词存放在 Amazon Bedrock Prompt Management 中。每个 prompt 都有唯一 ID 并带版本号。SQS 消息必须指定相关的 prompt ID 与版本，Lambda 执行时便用它们取回提示词正文。

注意：服务限额为每个区域 50 个 prompt、每个 prompt 10 个版本。

#### 1.2.3 为 LLM 调用组装消息并处理响应

Lambda 函数继续执行以下步骤：

- 通过拼接提示词正文与图像来组装发给 LLM 的消息。
- 使用 [Converse API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html) 向 Amazon Bedrock 发送请求。

LLM 会以 JSON 字符串返回抽取到的数据，你可以在 DynamoDB 表中查看结果，如下文“测试 pipeline”一节所示。

#### 1.2.4 保存结果

最后，Lambda 函数通过以下步骤完成流程：

- 解析 JSON，并把地块属性存入 DynamoDB 表。
- 如果文档已成功处理且结果已保存，则从队列中删除该 SQS 消息。

## 2. 批处理推理 pipeline

批处理推理 pipeline 使用标准 AWS SQS 队列，因为它吞吐量高。队列消息的创建方式与按需 pipeline 类似，只是不需要 `message-group-id` 属性。

批处理推理 pipeline 的主要组件包括：

- [Amazon EventBridge Scheduler](https://docs.aws.amazon.com/scheduler/latest/UserGuide/what-is-scheduler.html)。
- Batch Inference AWS Lambda 函数，用于预处理扫描版 PDF、创建 JSONL 文件并提交批处理推理作业。
- Amazon EventBridge 规则。
- 后处理 AWS Lambda 函数。

以下各节详细描述批处理推理 pipeline。

### 2.1. Amazon EventBridge 调度器

Amazon EventBridge Scheduler 按计划启动批处理推理 Lambda 函数。

### 2.2. 批处理推理 Lambda 函数

该函数会先检查队列中是否有足够的消息，然后再继续。截至撰写本文时，Amazon Bedrock 批处理推理作业的最小记录数为 100。

#### 2.2.1 接收队列消息

Lambda 函数遍历队列中的消息，抽取文档 ID、LLM 模型 ID、prompt ID/版本和系统 prompt ID/版本。

#### 2.2.2 无重复地获取文档、转换为图像，并切分大文件

随后 Lambda 函数取回文档，如果文档是扫描版 PDF 就转换为图像，必要时切分大文件 – 与按需 pipeline 中完全一致。由于标准 SQS 队列不保证消息恰好投递一次，该函数还会确保忽略重复消息。

#### 2.2.3 在一个批处理推理作业中允许使用不同的提示词

与按需 pipeline 类似，不同文档格式需要不同的用户提示词，才能更有效地抽取数据。

每份文档要使用的 prompt ID 与版本在 SQS 消息中指定。Lambda 执行期间，函数会从 Amazon Bedrock Prompt Management 取回提示词正文。

#### 2.2.4 为批处理推理作业创建 JSONL 制品

随后 Lambda 函数处理以下任务：

- 在 Batch Inference Data S3 存储桶中创建 `metadata.json`，用于存储消息属性，包括 SQS 消息 ID、`doc_id`、prompt ID/版本、系统 prompt ID/版本以及其他与项目相关的属性。该文件随后由 Post-Processing Lambda 用于填充 DynamoDB 表。
- 处理文档以创建 Amazon Bedrock 批处理推理作业所需的 JSONL 文件。为提升效率，该过程使用 Python 的 multiprocessing 模块并行化。JSONL 文件随后上传到 Batch Inference Data S3 存储桶。
- 在文档准备好并上传到 S3 存储桶之后删除 SQS 消息。这需要为队列设置较大的 Visibility Timeout。

#### 2.2.5 组装消息并提交批处理推理作业

最后，批处理推理 Lambda 函数使用上一步生成的 JSONL 制品创建 Amazon Bedrock 批处理推理作业。注意，每个批处理作业只能使用一个模型处理文档，这意味着同一批处理作业内的 SQS 消息必须指定相同的模型 ID。如果传入消息中指定了不止一个模型 ID，Lambda 函数会使用轮询机制，选出被指定次数最多的模型 ID 来使用。

### 2.3. Amazon Bedrock 批处理推理作业

Amazon Bedrock 收到批处理推理作业后，会把它放入队列。作业开始后，会依次执行以下步骤。

#### 2.3.1 为批处理推理作业取回 JSONL 制品

Amazon Bedrock 取回在创建作业时指定的 JSONL 制品。

#### 2.3.2 存储批处理推理输出

作业完成后，Amazon Bedrock 把输出存储到 Batch Inference Data S3 存储桶，该存储桶同样在创建作业时指定。

#### 2.3.3 通知 Amazon EventBridge

作业完成后，Amazon Bedrock 向 Amazon EventBridge 发送作业状态变更事件，由 EventBridge 规则捕获。

### 2.4. Amazon EventBridge 规则触发推理后的 Lambda 函数

EventBridge 规则触发后处理 Lambda 函数，以完成模型输出的进一步处理。

### 2.5. 后处理 Lambda 函数

#### 2.5.1 取回输出的 JSONL

Lambda 函数从批处理推理数据 S3 存储桶取回推理输出的 JSONL。

#### 2.5.2 保存推理输出

该函数解析 JSONL 文件，并把抽取到的地块属性保存到 DynamoDB 表。

## 清理

要清理资源：

- 登录 AWS 管理控制台
- 跳转到 CloudFormation 服务
- 在 CloudFormation 控制面板中找到并选中要删除的堆栈
- 选择页面顶部的“Delete”按钮
- 在提示时确认删除

CloudFormation 会按正确顺序自动删除作为堆栈一部分创建的资源，并妥善处理依赖关系。

删除 CloudFormation 堆栈不会删除 S3 存储桶和 DynamoDB，因为它们的删除策略被设置为保留，以帮助防止数据丢失。要删除这些资源，请前往 AWS 管理控制台中各服务的页面手动删除。

## 结论

本文介绍的按需与批处理 Amazon Bedrock 推理 pipeline 说明了如何根据时间敏感度和数据量动态处理文档。在决定使用哪条 pipeline 时，你还应考虑成本因素。如我们在测试中所见，使用批处理 pipeline 时 Amazon Bedrock 的成本比按需 pipeline 低 50%。

该方案的另一个关键特性是能够在单个文档级别指定大语言模型（对按需 pipeline 而言）和提示词，使这些 pipeline 能够支持多种类型的智能文档处理。

借助 Python 的 multiprocessing 模块启用并行后，批处理推理 pipeline 的两个 Lambda 函数都能在 15 分钟内处理 1,000 份文档。
