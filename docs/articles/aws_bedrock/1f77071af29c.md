# 构建领域感知的数据预处理 pipeline：一种多 agent 协作方法

企业——尤其是保险行业的企业——在处理来自 PDF、电子表格、图像、视频和音频文件等多种格式的海量非结构化数据时，正面临越来越大的挑战。这些数据可能包括理赔文档包、碰撞事件视频、聊天记录或保单文档。它们都包含贯穿理赔处理生命周期的关键信息。

传统的数据预处理方法虽然可用，但在准确性和一致性上可能存在局限。这可能影响元数据抽取的完整性、工作流速度，以及数据用于 AI 驱动洞察（例如欺诈检测或风险分析）的利用程度。为应对这些挑战，本文介绍一种多 agent 协作 pipeline：一组分别负责分类、转换、元数据抽取和领域特定任务的专用 agent。通过编排这些 agent，你可以自动化摄取并转换范围广泛的多模态非结构化数据——提升准确性并实现端到端洞察。

对于只需处理少量同质文档的团队，单 agent 的配置可能更容易实现，也足以满足基础自动化需求。但如果你的数据横跨多个领域和格式——例如理赔文档包、碰撞录像、聊天记录或音频文件——多 agent 架构则具备明显的优势。专用 agent 可以针对特定的数据类型做 prompt 工程、调试更容易、抽取也更准确。

随着数据量和种类增长，这种模块化设计扩展起来更为从容，你可以接入新的领域感知 agent，或改进单个 prompt 与业务逻辑——而不会打乱整条 pipeline。human-in-the-loop 阶段领域专家给出的反馈，也可以映射回具体 agent，支撑持续改进。

为支撑这种自适应架构，你可以使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/)，这是一项全托管服务，让你可以借助来自领先 AI 公司的基础模型（FM），通过单一 API 轻松构建和扩展生成式 AI 应用；这些公司包括 [AI21 Labs](https://aws.amazon.com/bedrock/ai21/)、[Anthropic](https://aws.amazon.com/bedrock/claude/)、[Cohere](https://aws.amazon.com/bedrock/cohere/)、[DeepSeek](https://aws.amazon.com/bedrock/deepseek)、[Luma](https://aws.amazon.com/bedrock/luma-ai/)、[Meta](https://aws.amazon.com/bedrock/llama/)、[Mistral AI](https://aws.amazon.com/bedrock/mistral/)、[poolside ](https://aws.amazon.com/bedrock/poolside/)（即将推出）、[Stability AI](https://aws.amazon.com/bedrock/stability-ai/) 和 [Amazon](https://aws.amazon.com/ai/generative-ai/nova/)。Amazon Bedrock 有一项强大的能力——[Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/)——它可以创建智能的、领域感知的 agent，这些 agent 能从 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 检索上下文、调用 API，并编排多步骤任务。这些 agent 提供了大规模处理非结构化数据所需的灵活性与适应力，并且能与组织的数据和业务工作流一同演进。

## 方案概览

我们的 pipeline 充当保险非结构化数据的预处理中枢，具备以下功能：

- 基于领域规则对传入的非结构化数据进行分类
- 抽取理赔编号、日期等元数据
- 将文档转换为统一格式（例如 PDF 或转录文本）
- 将音频/视频数据转换为结构化的标记文本格式
- 对不确定或缺失的字段进行人工校验

丰富后的输出及其关联元数据最终会落入一个元数据丰富的非结构化数据湖，为欺诈检测、高级分析和 360 度客户视图奠定基础。

## 多 agent 协作 pipeline

这条 pipeline 由多个专用 agent 组成，每个 agent 负责一项独立职能，例如分类、转换、元数据抽取和领域特定分析。与试图包揽全部任务的单一巨型 agent 不同，这种模块化设计带来了可扩展性、可维护性和复用性。单个 agent 可以独立更新、替换或扩展，以适配新的文档类型或不断变化的业务规则，而不会影响整个系统。这种关注点分离提升了容错能力并支持并行处理，从而带来更快、更可靠的数据转换工作流。

多 agent 协作带来以下指标与效率收益：

- **减少人工校验耗时** – 针对具体 agent 定制的聚焦 prompt 会带来更干净的输出和更简单的核对，从而在验证时间上获得效率。
- **更快的迭代周期与回归隔离** – prompt 或逻辑的改动被限定在单个 agent 范围内，把更新的影响面降到最小，并在调优或增强阶段显著减少回归测试工作量。
- **提升元数据抽取准确性，尤其是在边界情况上** – 专用 agent 减少了 prompt 过载，并允许更深度的领域对齐，从而提升字段级准确性——在处理碰撞视频与理赔文档包这类混合文档类型时尤为明显。
- **借助自动化问题解决 agent 获得可扩展的效率收益** – 随着自动化问题解决 agent 逐步增加，每份文档的处理时间预计会明显改善，减少人工介入点。这些 agent 可以设计为利用 human-in-the-loop 反馈映射和智能数据湖查询，来自动化处理反复出现的修复。

### 非结构化数据中枢 Supervisor Agent

Supervisor Agent 负责编排工作流、委派任务，并调用下游的专用 agent。它的关键职责如下：

- 接收来自用户门户的传入多模态数据和处理指令（多模态理赔文档包、车辆损伤图像、音频转录文本或维修估价单）。
- 将每种非结构化数据类型转发给 Classification Collaborator Agent，以判断是否需要转换步骤，还是可以直接分类。
- 通过为每种数据类型调用合适的 agent 来协调领域专用处理——例如理赔文档包由 Claims Documentation Package Processing Agent 处理，维修估价单则交给 Vehicle Repair Estimate Processing Agent。
- 确保所有传入数据最终连同其元数据一起落库到 S3 数据湖。

### Classification Collaborator Agent

Classification Collaborator Agent 使用领域特定的规则判定每个文件的类型，并确保它要么被转换（如需要），要么直接被分类。这包括以下步骤：

- 识别文件扩展名。如果是 DOCX、PPT 或 XLS，先将文件路由到 Document Conversion Agent。
- 为每份标准化后的文档输出统一的分类结果——指明类别、置信度、抽取到的元数据和后续步骤。

### Document Conversion Agent

Document Conversion Agent 将非 PDF 文件转换为 PDF，并抽取初始元数据（创建日期、文件大小等）。这包括以下步骤：

- 将 DOCX、PPT、XLS 和 XLSX 转换为 PDF。
- 采集嵌入的元数据。
- 将新的 PDF 返回给 Classification Collaborator Agent 做最终分类。

### 专用分类 agent

每个 agent 负责特定的数据模态：

- Document Classification Agent：处理文本密集的格式，例如理赔文档包、标准作业程序文档（SOP）和保单文档；抽取理赔编号、保单编号、投保人详情、承保日期和费用金额作为元数据；识别缺失项（例如缺少投保人信息、缺少日期）
- Transcription Classification Agent：专注于音频或视频转录文本，例如损失首次通知（FNOL）通话或理算员回访；将转录文本归类到业务类别（例如第一方理赔或第三方通话），并抽取相关元数据
- Image Classification Agent：分析车辆损伤照片和碰撞视频，以获取损伤严重程度、车辆识别信息或位置等细节；生成可输入下游损伤分析系统的结构化元数据

此外，我们还定义了下游的专用 agent：

- Claims Document Package Processing Agent
- Vehicle Repair Estimate Processing Agent
- Vehicle Damage Analysis Processing Agent
- Audio Video Transcription Processing Agent
- Insurance Policy Document Processing Agent

在高层次分类判定某文件属于（例如）理赔文档包或维修估价单之后，Supervisor Agent 会调用相应的专用 agent 执行更深度的领域特定转换与抽取。

## 元数据抽取与 human-in-the-loop

元数据对自动化工作流至关重要。如果没有准确的元数据字段——例如理赔编号、保单编号、承保日期、损失日期或索赔人姓名——下游分析就缺乏上下文。方案的这一部分通过以下功能处理数据抽取、错误处理与恢复：

- **自动抽取** – 大型语言模型（LLM）与领域特定规则从非结构化内容中解析关键数据、识别关键元数据字段，并尽早标记异常。
- **数据暂存待审** – pipeline 抽取元数据字段，并将每条记录暂存以供人工审核。该过程会呈现抽取到的字段——并高亮缺失或错误的值供人工审核。
- **Human-in-the-loop** – 领域专家在 human-in-the-loop 阶段介入，校验并纠正元数据，为理赔编号、投保人详情和事件时间线等关键字段提供准确性与上下文。这些介入不仅是某一时点的错误恢复机制，也为 pipeline 的领域特定规则、转换逻辑和分类 prompt 的持续改进奠定基础。

最终，可以在迭代中引入自动化问题解决 agent，承担越来越多的数据修复工作，进一步减少人工审核需求。可以引入若干策略来推动这一进程，以随时间提升韧性与适应力：

- **持久化反馈** – 领域专家所做的更正可以被捕获下来，并映射到它们所解决的 issue 类型。这些结构化映射有助于改进 prompt 模板、更新业务逻辑，并生成有针对性的指令，引导自动化问题解决 agent 的设计，使其在未来的工作流中模拟类似的修复。
- **上下文元数据查询** – 随着非结构化数据湖的元数据日益丰富——保单编号、理赔 ID、车辆信息与佐证文档之间建立起更深的关联——可以引入带有恰当 prompt 的问题解决 agent 来执行智能的动态查询。例如，若某个媒体文件缺少保单编号，但包含理赔编号和车辆信息，问题解决 agent 便可以通过查询相关已索引文档（如理赔文档包或维修估价单）来取回缺失的元数据。

通过组合这些策略，pipeline 的适应性不断增强——持续提升数据质量，并在整个企业范围内实现可扩展、元数据驱动的洞察。

## 元数据丰富的非结构化数据湖

每一种非结构化数据类型完成转换和分类后，标准化后的内容

及其元数据 JSON 文件会存入非结构化数据湖（Amazon S3）。该存储库通过共享的元数据统一不同类型的数据（图像、转录文本、文档），从而实现以下功能：

- 通过对重复索赔人或矛盾细节做交叉比对来检测欺诈
- 通过串联理赔、通话和服务记录构建客户 360 度画像
- 高级分析与实时查询

## 多模态、多 agent 模式

在我们的 [AWS CloudFormation](https://aws.amazon.com/cloudformation) 模板中，每种多模态数据类型都走一条专用流程：

- 数据转换与分类：Supervisor Agent 接收上传内容并转交给 Classification Collaborator Agent。如有需要，Document Conversion Agent 可能介入以标准化文件。Classification Collaborator Agent 的分类步骤会将上传内容归入各类别——FNOL 通话、理赔文档包、碰撞视频等。
- 文档处理：Document Classification Agent 及其他专用 agent 应用领域规则抽取理赔编号、承保日期等元数据。pipeline 会把抽取到的信息以及缺失的信息呈现给领域专家，以便纠正或更新。
- 音频/视频分析：Transcription Classification Agent 处理 FNOL 通话和第三方通话转录文本。Audio Video Transcription Processing Agent 或 Vehicle Damage Analysis Processing Agent 进一步解析碰撞视频或损伤照片，将语音中描述的事件与视觉证据对应起来。
- 标记文本转换：专用处理 agent 根据完全分类并纠正后的元数据生成标记文本。这样，数据被转换为元数据丰富的格式，可供知识库、Retrieval Augmented Generation（RAG）pipeline 或图查询直接使用。

## Human-in-the-loop 与未来改进

human-in-the-loop 组件对于校验和补充缺失元数据、修正数据分类错误至关重要。不过，这条 pipeline 的设计目标是按如下方式持续演进：

- **精炼 LLM prompt** – 领域专家的每一次更正都有助于精炼 LLM prompt，减少未来的手动步骤并提升元数据一致性
- **问题解决 agent** – 随着元数据一致性逐步提升，专用修复器可以在极少用户输入的情况下处理元数据与分类错误
- **交叉引用** – 问题解决 agent 可以交叉引用元数据丰富的 S3 数据湖中的现有数据，自动补全缺失的元数据

这条 pipeline 正朝着全面自动化演进，除最复杂的场景外，尽可能减少人工干预。

每种多模态数据类型都会经过一系列 agent 处理：

- **Supervisor Agent** – 启动处理
- **Classification Collaborator Agent** – 对多模态数据分类
- **专用处理 agent** – 执行领域特定处理

最后，处理后的文件连同其丰富化的元数据一起存入 S3 数据湖。接下来我们进入实际用例。

### 用例 1：理赔文档包

本用例演示处理一个多模态理赔文档包的完整工作流。通过向 pipeline 上传一份 PDF 文档，系统会自动识别文档类型、抽取关键元数据，并将每一页归入具体的组成部分。

- 在 UI 中选择 **Upload File**，然后选择该 pdf 文件。

文件上传可能需要一些时间，取决于文档大小。

- 上传完成后，你可以确认抽取到的元数据值如下：理赔编号：0112233445 保单编号：SF9988776655 损失日期：2025-01-01 索赔人姓名：Jane Doe

Classification Collaborator Agent 识别出该文档为 Claims Document Package。元数据（例如理赔 ID 和事故日期）会被自动抽取并显示以供审核。

- 本用例中不做任何修改——只需选择 **Continue Preprocessing** 继续。

处理阶段可能需要长达 15 分钟才能完成。与其手动检查 S3 存储桶（在 CloudFormation 堆栈输出中标识为 `KnowledgeBaseDataBucket`）以确认已生成 72 个文件——每页一个文件及其对应的元数据 JSON——你可以通过定期选择 **Check Queue Status** 来监控进度。这样可以实时查看处理队列的当前状态。

pipeline 还会进一步将每一页归入具体类型（例如律师函、警方报告、医疗账单、医生报告、健康表格、X 光片）。它同时生成对应的标记文本文件和元数据 JSON 文件。

最后，处理后的文本和元数据 JSON 文件会存入非结构化 S3 数据湖。

## Amazon Bedrock Knowledge Bases 集成

要在数据湖中使用新处理的数据，请完成以下步骤，将数据摄取到 Amazon Bedrock Knowledge Bases，并通过结构化工作流与数据湖交互。该集成支持跨不同文档类型的动态查询，从而从多模态数据中获得更深入的洞察。

- 选择 **Chat with Your Documents** 打开聊天界面。

[![同步 Bedrock Knowledge Base](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/12/ML-18173-SyncChat.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/12/ML-18173-SyncChat.png)

- 选择 **Sync Knowledge Base** 启动作业，将新处理好的文件及可用元数据摄取并索引到 Amazon Bedrock 知识库中。
- 同步完成后（可能需要几分钟），在文本框中输入查询。例如，将 **Policy Number** 设为 SF9988776655，然后尝试提问：“检索所有以多个索赔人名义针对该保单编号提交的理赔详情。”“Jane Doe 的理赔性质是什么，提交了哪些文档？”“投保人 John Smith 是否提交过车辆维修理赔，是否有任何估价单在档？”
- 选择 **Send** 并查看系统回复。

[![与文档对话](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/12/ML-18173-Chats.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/12/ML-18173-Chats.png)

该集成实现了跨文档分析，你可以跨转录文本、图像、理赔文档包、维修估价单和理赔记录等多模态数据类型进行查询，从你的领域感知多 agent pipeline 中揭示客户 360 度洞察。通过综合多个来源的数据，系统可以关联信息、发现隐藏模式，并识别在孤立文档中可能看不出的关系。

这项智能的关键使能因素是预处理期间生成的丰富元数据层。领域专家会主动校验并完善这些元数据，从而在各类文档之间提供准确性与一致性。通过复核关键属性——例如理赔编号、投保人详情和事件时间线——领域专家强化了元数据基础，使其对下游 AI 驱动分析更可靠。

在丰富元数据到位之后，系统现在能更有效地推断文档之间的关系，从而支持以下用例：

- 识别与单一保单关联的多笔理赔
- 检测已提交文档中的不一致
- 追踪理赔从 FNOL 到结案的完整生命周期

通过人工校验持续改进元数据，系统变得更加自适应，为未来的自动化铺路——届时问题解决 agent 可以在数据摄取过程中，以极少的人工干预主动识别并自我纠正缺失和不一致的元数据。

## 结论

通过把非结构化的保险数据转换为元数据丰富的输出，你可以实现以下目标：

- 通过交叉引用多模态数据加速欺诈检测
- 通过统一理赔、通话和服务记录增强客户 360 度洞察
- 通过 AI 辅助的搜索与分析支持实时决策

随着这条多 agent 协作 pipeline 日趋成熟，专用的问题解决 agent 和精炼后的 LLM prompt 可以进一步减少人工参与——释放端到端自动化与更优的决策能力。最终，这种领域感知的方法把原始非结构化数据转化为可执行的商业智能，为你的理赔处理工作流提供面向未来的能力。

要开始使用本方案，可采取以下后续步骤：

- 部署 CloudFormation 堆栈并试用示例数据。
- 根据你团队的反馈改进领域规则或 agent prompt。
- 使用 S3 数据湖中的元数据进行高级分析，例如实时风险评估或欺诈检测。
- 将 Amazon Bedrock 知识库连接到 `KnowledgeBaseDataBucket`，以实现高级问答与 RAG。

在多 agent 架构到位之后，你的保险数据不再是散落各处的负担，而会成为高价值洞察的统一来源。
