# BMW 集团如何在数千名开发者之间治理数百个 agent

当数百个 agent 要同时服务于数千名开发者时，企业治理就绝不能退居为一个事后才补上的环节。

在 BMW 集团的研发部门，超过 12,500 名开发者共同参与约 5 亿行车辆软件代码的开发与维护。这些软件由 BMW Connected Vehicle 后端提供增强——这是一个基于云的系统，内部包含 1,300 多个微服务，为已经在路上行驶的 2,400 万辆车提供数字服务。在受监管的行业里，（软件）质量、稳定性和治理合规所要求达到的门槛异常之高，几乎不容许任何妥协。

尽管如今已有各类研究、框架和指南为构建 agent 提供便利，但要以高效、可扩展的方式把高质量的 agent 工业化并运营起来，仍然是一项重大挑战。

在大型组织里规模化 agentic AI，靠孤立的团队是无法实现的。它需要整个集体共同投入，需要由各个局部团队自己推动起来的实验，也需要在整个企业范围内主动进行知识共享。这就带来一个根本性的治理两难：一方面，开发团队需要快速创新的自由；另一方面，企业又必须守住安全、安防、可组合性和成本效率方面的标准。一旦失去这种平衡，组织就要面对 AI 孤岛四处林立、重复建设代价高昂的局面。考虑到 BMW 集团内有数百个分布在全球各地的团队同时在构建 agent，要把这个挑战处理好绝非易事。

本文详细介绍了我们用来支撑 BMW 研发团队大规模构建、治理和运营 agent 的实践与模式，而且这些做法是在不牺牲速度、质量与合规的前提下实现的。

## 解决方案

我们的出发点很直接：从一开始就构建能够互相协作的 agent。这要求架构能让多样性变得可组合、可治理、可自动化，同时又不要求所有人必须统一到某一个框架、或者某一条工具链上。

这一架构的核心是 agent harness，也就是包裹在大语言模型（LLM）外围的一层运行时。它为自主运行提供执行循环、工具分发、记忆管理，以及用于观测的可观测性钩子。

正如 [AWS Well-Architected Framework](https://aws.amazon.com/architecture/well-architected/) 统一了云基础设施的设计方式，agentic 系统也需要一套对等的模式——也就是可复用的蓝图，从一开始就把治理、可组合性和运营最佳实践一并编码进去。

我们把方案组织为五项彼此咬合的实践，这些实践来自我们自 2023 年以来在企业规模上亲手构建并运营 agentic 系统所积累下来的经验。每项实践都被固化为基础设施即代码（IaC），使采纳过程可重复、可审计、可在各团队之间强制执行，同时又不会拖慢 DevOps 的推进速度。

### 主动治理，而非事后治理

治理必须从一开始就具备结构性，并在整个生命周期中持续维护下去。我们认为，有效的 agentic 治理应当具备下面三个属性：

**框架无关且外部化：** 诸如认证、授权、速率限制和内容过滤这类治理规则，一律在集成层强制执行。这一层包括 Model Context Protocol（MCP）网关、中央 agent 注册表和编排边界，而不是落在各个 agent 各自的代码库内部。这意味着，无论发生框架迁移、模型替换还是团队重组，治理都能够存活下来。

**领域敏感且分级：** 并不是每一个 agent 动作都承担着同样的风险：起草文档、更新客户记录、写入生产数据库，这三者所需要的监督程度截然不同。我们通过为每个步骤设定自主级别的方式，来实现分级信任：

- **Level 0（Human-in-the-loop）：** 每一个动作都需要获得明确的人工批准。这是新 agent 以及高风险操作的起点。
- **Level 1（Human-on-the-loop）：** agent 自主执行，但会把关键决策呈现出来，供人工异步复核。它适合那些输入、输出和回滚手段都已经明确界定的中风险任务。
- **Level 2（护栏内自主）：** agent 在严格定义的策略边界内独立运行，而这些边界以确定性方式强制执行，而不是靠 prompt 指令来约束（见下文）。它只用于那些低风险、已经被充分理解、并且拥有验证记录的操作。

信任级别按步骤分配，而不是按 agent 分配。同一条工作流里可以同时包含三个级别的步骤，团队因此能保守起步，随着信心建立逐步提高自主度——依据的是可度量的评估数据，而不是想当然。

**确定性执行：** 治理以确定性代码的形式，运行在 agent 的推理循环之外。在实践中，这主要发生在 CI/CD 流水线里：权限检查、策略即代码规则和合规校验，会在 agent 到达生产环境之前，为每一次部署把关。由于这些检查与 agent 分开运行，无论是 agent 本身还是它的 prompt，都没有能力去覆盖它们。出口控制（收件人允许列表、出站密钥扫描）则有助于防止这样一种情形：持有保密数据的 agent，借一次原本合法的调用，把数据泄露到外面去。

### 持续插桩、验证与评估

agentic 系统中的可观测性，已经超出了传统应用监控的范畴。真正的问题已经不再是某个服务有没有返回 HTTP 200 状态码，而是 agent 有没有产出忠实、符合策略的输出，以及这一点能否通过可观测的执行轨迹来加以证明。要回答这个问题，就需要一个覆盖常见查询与边缘用例的真值数据集作为依据。这个数据集从第一天起就用于评估，因此我们在衡量质量时，依据的是有代表性、并且受到适当治理的评估数据集，而不是合成 prompt。

这套基础设施没有办法事后加装，必须从一开始就作为初始设计的一部分。持续集成与持续交付（CI/CD）流水线会强制执行这一点：缺少插桩的 agent，会在评估真正运行之前就验证失败。

我们建议从三个维度来做插桩：

- **意图追踪：** 为每一次执行都捕获可观测的 agent 轨迹，其中包括推理步骤、工具调用和 context 检索。OpenTelemetry span 会建立起一条可以查询的血缘，把用户的请求一直追溯到最终的输出。
- **验证与评估即 CI：** 对 agent 的任何改动（改 prompt、加工具、换模型）都会触发流水线。**验证**先跑，用自动化回归测试先覆盖 agent 的各个组件，再覆盖组件之间的交互。由于 harness 的大多数组件都是确定性的，这些测试跑得很快，而且完全可以自动化。**评估**后跑，它对着真值数据集给非确定性的输出打分，并以质量阈值作为门控。这个顺序是刻意安排的：验证充当一道门，只有构建通过，评估才会运行。
- **模型分层与路由遥测：** 当 agent 在多个模型之间路由时，要记录下路由决策及其依据，而不只是记录结果。层级归属由按任务类型的评估结果推导而来，效果不佳的结果则会回流，成为新的评估用例。

### 聚焦起步，为组合而设计

在分布式云系统里，业界靠微服务、服务网格这类架构模式，化解了端到端工作流的复杂度。agentic 系统的演进也需要走一条类似的轨迹：从单体、通用的 agent，走向多个互相协作的专用 agent，而不是一直停留在什么都能干的大一统形态上。

团队应当先定义问题，再去考虑 agent 的功能。在写下任何编排逻辑之前，团队应先产出五份具体的工件：

- **清晰的范围定义：** agent 该做什么、又不该做什么。
- **交互模型：** 用户和其他 agent 将分别如何调用它。
- **无歧义的工具定义：** 每个工具和参数都要精确界定。
- **真值数据集：** 即上文所述的评估参照，并且要在任何实现开始之前就建立好。
- **评估标准：** agent 将被衡量的质量阈值和基准。

这条纪律能够挡住我们观察到的最常见失败模式：当 agent 承担了过多的职责，它的 prompt 就会不断膨胀，结果是准确性下降、延迟上升。

单个 agent 一旦范围清晰，就必须被设计成可组合的积木。为此我们定义了三层组合体系：

- **MCP 工具** 是原子的集成契约。每个工具只封装单一能力（例如一次 API 调用或一次数据库查询），也不会把任何关于工作流的假设写进契约里。这是整个体系中最稳定、最可复用的那一层。
- **skill** 是 MCP 工具的打包式、领域特定组合。例如一个代码审查 skill，就可以把一个静态分析工具、一个风格检查工具和一个基于 LLM 的推理步骤串联在一起。skill 承载着领域逻辑，但依然可以在不同工作流之间移植。
- **flow** 是 skill 的端到端编排，代表着完整的业务流程（例如一整条 PR 审查流水线，或者从需求到部署的一个完整周期）。

每一层都在 CI/CD 流水线中独立验证：组件测试覆盖工具和 skill，交互测试则覆盖它们组合成 flow 的过程。

这些层级通过开放标准相连：工具集成用 MCP 和 Agent Skills，agent 之间的通信用相应协议，而跨这些交互的可观测性则用 OpenTelemetry 来承载。

### 边实践边专业化

在生产环境中，即便是范围清晰的 agent，也会随着实际用法逐渐偏离设计预期而失效：查询模式变了，工具选择逻辑卡住了，性能也会莫名其妙地掉下去。

正确的应对方式，是把复杂的 agent 拆成多个专用的 agent，每一个都拥有更清晰的指令、更简单的工具集和更聚焦的推理。这样做的收益相当具体：

- **独立演进：** 在更新需求工程 agent 的时候，完全不需要去碰编码 agent。
- **独立扩展：** 当范围和接口定义得足够清晰时，单个 agent 就可以独立扩展，无需重新部署，也无需调整整个系统的规模。
- **缩小影响面：** 某一个 agent 的失败或幻觉，不会级联扩散到整条工作流。
- **节省成本：** 范围狭窄的 agent，往往可以跑在更小的模型上，推理和托管成本也随之下降。

复杂度可以从两条轴上削减：

- **agent 内部：** 把能力拆成 skill，因为工具和少样本示例在每次调用时都会消耗 context，同时还会降低准确性、抬高成本。粒度要靠实验来确定：agent 很少选用的 skill 就合并，随输入产生不同行为的 skill 就拆开。
- **agent 之间：** 把 agent 领域之外的工作，通过 A2A 协议交给专用的同伴 agent，而不是不断扩展当前这个 agent。agent 应该成长在能力上，而不是成长在 context 上。

关键在于，每个专用 agent 只访问其职责所需的数据和工具，这种架构因此在设计上就落实了最小权限原则——而在受监管的行业里，这本身就是一项合规要求。

不过，要让这些收益真正落地，agent 之间还必须能够互相发现、互相操作。为了防止出现 *AI 孤岛*，我们维护一份 agent、工具和 skill 的*集中式*注册表。它承担着以下作用：

- **发现机制：** 依据构建期间存入的元数据，对当前可用的 agent、工具和 skill 逐一编目。
- **治理检查点：** 确认某类资产获准用于生产，并维护一条可供追查的审计线索。
- **安全检查点：** 在批准之前施加自动化的安全检查，例如 prompt 注入及类似问题。
- **去重防线：** 识别其他团队已经维护的等效能力，避免重复劳动。这项检查会在注册时自动运行，在批准之前就把重复项标记出来。

### 以代码化求规模化

从管理单个 agent 转向治理一支 agent 机群，要求把 agent 架构代码化。团队使用 Terraform 或 [AWS CloudFormation](https://aws.amazon.com/cloudformation/) 这类基础设施即代码框架来供给和管理 agent 基础设施，严谨程度与对待任何生产系统完全一致：

- **细粒度最小权限角色：** 按 agent 或工具划定范围。
- **CI/CD 流水线：** 跨账户、跨区域的一致且经过验证的部署，并在测试失败或指标恶化时自动中止部署。
- **策略即代码：** 用规则（例如 [AWS Config](https://aws.amazon.com/config/)、Open Policy Agent）扫描已经部署的 agent，检查它们是否符合组织标准。

这三项都作为流水线关卡强制执行，在注册之前完成验证，而不是事后再做审计。

采纳模式刻意做成自下而上、中央策展。各个团队为解决眼前的问题，自行构建 skill 和 MCP 工具；所有团队都可以通过注册表共享自己的资产，从而做出贡献。一个中央团队负责在 CI 流水线中构建自动化治理检查，以维护统一的标准。为了支持开发团队、推动*左移*，中央团队还会把这些构建块以治理即代码模块的形式提供出来。

这种平衡既避免了中央强推架构，也避免了无人管理的实验。结果是，当新的运营问题出现时，团队可以扩展现有的模式，而不必推倒重来、重新设计自己的架构。

## 在 agent 生命周期中落实最佳实践

架构模式和治理标准，只有真正嵌进团队构建与运营 agent 所使用的工作流（部署前和运行时）当中，才会发挥出效果。

### 部署之前

治理在第一行编排逻辑被写下之前，就已经开始了。团队会拿到从注册表中提取出来的参考架构模式与示例。这些预先验证过的蓝图覆盖了常见的 agent 配置、工具集成模式和组合结构，既能加速开发，又把经过验证的默认值一起编码了进去。在任何东西进入生产之前，标准化的 CI/CD 控制会强制执行这些实践。图 2 展示了参考流水线的四个阶段，它们自左向右依次执行。

**阶段 2** 并行执行安全与治理检查。静态分析会扫描代码中的问题，安全测试则在隔离的预发布环境中探测 agent。流水线还会校验出口控制和最小权限。此外还有两项检查：一项确认 agent 声明的自主级别与它实际的权限相符，另一项确认它的配置能够通过策略即代码规则。一个治理 agent 会对照既定标准检查目标 agent，并把发现的问题标记出来供人工复核，从而加速审计，例如：

- **范围蔓延：** 超出了最初定义的目的或者权限范围运行。
- **prompt 臃肿：** 指令当中存在不必要的复杂度。
- **工具误用：** 在预期用例之外去调用工具。
- **性能退化：** 准确性、延迟或者成本效率出现下滑。

如果其中任何一步失败，或者指标出现恶化，部署就会中止，并留下日志供根因分析使用。若全部检查都通过，agent 会被打包，并以容器化工作负载的形式部署出去，产出可复现、前后一致的部署结果。这样一来，既挡住了未受治理的 agent 进入生产，又自动化了合规检查，同时也保持了注册表的准确性。

### 运行时

到了运行时，可观测性要抓住两类漂移。数据漂移表现为用户查询模式的新增或者变化，也可能是上游 API 发生了变更；模型漂移则表现为错误率上升，或者工具选择的准确性下降。当客户对某一次回复提出异议时，同样会触发一次调查。而针对漂移、分布偏移、评估分数下滑或者客户直接反馈的告警，则会启动一次分阶段的响应。这些事件都会被记录下来，并转交人工复核。此外，团队可以持续运行治理 agent，把漂移和运营问题标记出来，交由负责的团队排查。

## 总结

大规模构建和运营 agent 是一门工程学科，而不是一次实验活动。

有效的治理必须从结构上内建、外部化、领域敏感，并以确定性方式强制执行。我们提出了三层组合体系（MCP 工具、skill 和 flow），把它作为可复用、可组合、可互操作 agent 的架构基础，并进一步拆分为专用 agent，以约束复杂度和范围。我们展示了每一次 CI/CD 运行中的验证与评估，如何让质量保证成为日常开发工作当中自然的一部分；也展示了把 agent 基础设施定义为代码，如何让团队把同一套治理规则施加到机群中的每一个 agent 上。最后，我们把这些模式落到了 agent 生命周期的各个环节——从预验证的参考架构、结构化流水线，一直到在运行时持续评估已部署 agent 的治理 agent。

我们的经验显示，这些实践在好几个方面都带来了回报。可复用的模板和共享基础设施降低了开发成本；凭借标准的交互模型和自动化部署，团队把 agent 送上生产的速度也更快了；质量同样得到了改善，因为流水线会在生命周期的每个阶段都强制执行经过验证的模式。

规模化 agentic 治理是整个行业都必须面对的一课。向 AI 与生成式 AI 支持的工作流自动化转型，已经在重塑工程组织的运作方式。最终的胜出者，将是那些不再止步于实验、并且真正建立起大规模治理自主 agent 网络之纪律的组织。有了这些实践，BMW 的工程师就可以专注于解决真正重要的问题：打造终极驾驶机器。

要把这些想法用在你自己的 agent 上，请从 [AWS Well-Architected Framework](https://aws.amazon.com/architecture/well-architected/) 开始——本文正是把它当作可复用 agent 蓝图的范本。如果想进一步了解 BMW 如何在它的 AWS 环境中把治理代码化，请阅读 [How BMW Group uses automation to achieve end-to-end compliance at scale on AWS](https://aws.amazon.com/blogs/mt/how-bmw-group-uses-automation-to-achieve-end-to-end-compliance-at-scale-on-aws/)。

## 展望与后续步骤

本文描述的模式与实践只是地基，而不是终点。我们正在几条战线上积极地扩展它们：

- **改进架构指引：** 为正在构建 agent 的团队发布最佳实践指南，内容涵盖架构上的权衡、组合模式以及反模式。
- **扩充基础设施即代码模板：** 把 agent 蓝图做成可以直接拿来使用的 IaC 模块，并且在默认情况下就内置了安全与治理标准。
- **深化治理合规测试：** 增加一批 CI/CD 测试用例，专门用来验证治理方面的合规性。
- **自动化标准执行：** 在部署前和运行时这两个阶段，扩大自动化检查与托管式合规扫描规则的覆盖范围。
- **扩展 agentic FinOps：** 治理模型与工具调用的规模适配，让规模与真实需求相匹配。
- **agentic 用户指引：** 把上述模式集成进 Archimedes——也就是 BMW 的架构指引 agent——以便提供更贴合上下文的架构建议。
