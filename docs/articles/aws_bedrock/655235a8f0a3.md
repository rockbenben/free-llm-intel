# BMW 集团如何在数千名开发者中治理数百个 agent

当数百个 agent 服务于数千名开发者时，企业治理不能是事后才考虑的事情。

在 BMW 集团的研发部门，超过 12,500 名开发者参与约 5 亿行车辆软件代码的开发。这些软件由 BMW Connected Vehicle 后端增强，这是一个基于云的系统，包含超过 1,300 个微服务，为现场 2,400 万辆汽车提供数字服务。在受监管的行业中，（软件）质量、稳定性和治理合规的标准异常之高。

尽管研究、框架和指南如今已为构建 agent 提供了便利，但以高效、可扩展的方式工业化和运营高质量 agent 仍然是一项重大挑战。

在大型组织中扩展 agentic AI 无法靠孤立的团队实现。它需要集体努力、本地驱动的实验以及跨企业的积极知识共享。这造成了一个根本性的治理两难：开发团队需要快速创新的自由，而企业必须执行安全、安防、可组合性和成本效益方面的标准。若缺乏这种平衡，组织就会面临 AI 孤岛碎片化格局和昂贵重复工作的风险。考虑到 BMW 集团有数百个全球分布的团队在构建 agent，这是一个真实的挑战。

在本文中，我们详细介绍了支持 BMW 研发团队在不牺牲速度、质量或合规性的前提下大规模构建、治理和运营 agent 的实践与模式。

## 解决方案

我们的前提很直接：构建从一开始就能协作的 agent。这需要一种架构，使多样性可组合、可治理、可自动化，而无需依赖单一框架或工具链。

该架构的核心是 agent harness，即包裹在大语言模型（LLM）外围的运行时层。它提供执行循环、工具分发、记忆管理以及用于自主运行的可观测性钩子。

正如 [AWS Well-Architected Framework](https://aws.amazon.com/architecture/well-architected/) 标准化了云基础设施设计，agentic 系统也需要同等的模式——即可复用的蓝图，从一开始就编码治理、可组合性和运营最佳实践。

我们围绕五项相互关联的实践来组织解决方案，这些实践源自 2023 年以来在企业规模上构建和运营 agentic 系统的亲身经验。每项实践都被编纂为基础设施即代码（IaC），使采用过程可重复、可审计、可在各团队间强制执行，同时不妨碍 DevOps 速度。

### 主动治理，而非事后治理

治理必须从一开始就是结构性的，并在整个生命周期中保持。我们主张有效的 agentic 治理具备三个特性：

**框架无关且外部化：** 身份验证、授权、速率限制和内容过滤等治理规则在集成层强制执行。这包括 Model Context Protocol (MCP) 网关、中央 agent 注册表和编排边界，而不是在各个 agent 代码库内部。这意味着治理能够在框架迁移、模型替换和团队重组后依然存活。

**领域敏感且分级：** 并非每个 agent 操作都承担相同的风险：起草文档、更新客户记录和生产数据库写入需要截然不同的监督级别。我们通过每步自主级别来实现分级信任：

- **Level 0（Human-in-the-loop）：** 每个操作都需要明确的人工批准。这是新 agent 和高风险操作的起点。
- **Level 1（Human-on-the-loop）：** agent 自主执行，但将决策呈现出来供异步人工审查。适用于具有明确输入、输出和回滚选项的中风险任务。
- **Level 2（护栏内自主）：** agent 在严格定义的策略边界内独立运行，这些边界以确定性方式强制执行，而非通过提示指令（见下文）。保留给低风险、已充分理解且经过验证的运营。

按步骤而非按 agent 分配信任级别。单个工作流可以包含全部三个级别的步骤，因此团队可以从保守起步，随着信心建立而逐步增加自主性，且基于可衡量的评估数据而非假设。

**确定性执行：** 治理作为确定性代码在 agent 的推理循环之外运行。在实践中，这主要发生在 CI/CD 管道中。权限检查、策略即代码规则和合规验证在那里对每次部署进行把关，在 agent 进入生产之前。由于这些检查与 agent 分开运行，无论是 agent 还是其提示都无法覆盖它们。出口控制（收件人允许列表、出站密钥扫描）有助于防止持有机密数据的 agent 通过原本合法的调用泄露数据。

### 持续插桩、验证和评估

agentic 系统中的可观测性超越了传统的应用监控。真正的问题不再是服务是否返回了 HTTP 200 状态，而是 agent 是否产生了忠实、符合策略的输出，以及如何通过可观测的执行轨迹来证明这一点。回答这个问题需要一个覆盖常见查询和边缘用例的基准数据集。该数据集从第一天起就用于评估，因此质量是针对具有代表性且经过适当治理的评估数据集来衡量的，而非合成提示。

这一基础设施无法事后加装，必须作为初始设计的一部分。持续集成和持续交付（CI/CD）管道强制执行这一点，因此缺乏插桩的 agent 会在评估运行之前就验证失败。

我们建议对三个维度进行插桩：

- **意图追踪：** 捕获每次执行的可观测 agent 轨迹（推理步骤、工具调用和上下文检索）。OpenTelemetry span 创建从用户请求到最终输出的可查询血缘。
- **验证和评估即 CI：** 对 agent 的任何更改（提示编辑、工具添加、模型替换）都会触发管道。**验证**首先运行，包含覆盖 agent 组件及其交互的自动化回归测试。由于大多数 harness 组件是确定性的，这些测试快速且完全可自动化。**评估**其次运行，针对基准数据集对非确定性输出评分，并以质量阈值为门控。这个顺序是刻意的：验证充当门控，因此评估只在通过的构建上运行。
- **模型分层和路由遥测：** 当 agent 在模型之间路由时，捕获路由决策及其理由，而不仅仅是结果。层级分配源自按任务类型的评估结果，而糟糕的结果会回流为新的评估用例。

### 聚焦起步，为组合而设计

对于分布式云系统，业界通过采用微服务或服务网格等架构模式解决了端到端工作流的复杂性。agentic 系统的演进需要遵循类似的轨迹，从单体、通用型 agent 转向多个协作的专用 agent。

团队应在考虑 agent 功能之前先定义问题。在编写任何编排逻辑之前，他们应产出五个具体工件：

- **清晰的范围定义：** agent 应该做什么和不应该做什么。
- **交互模型：** 用户和其他 agent 将如何调用它。
- **无歧义的工具定义：** 每个工具和参数都精确定义。
- **基准数据集：** 上文所述的评估参考，在任何实现开始之前建立。
- **评估标准：** agent 将被衡量的质量阈值和基准。

这种纪律防止了我们观察到的最常见失败模式：承担过多职责的 agent 积累了臃肿的提示，降低了准确性并增加了延迟。

一旦单个 agent 范围明确，它必须被设计为可组合的构建块。因此，我们定义了一个三层组合层次结构：

- **MCP 工具** 是原子集成契约。每个工具封装单一能力（例如，一次 API 调用或一次数据库查询），不编码工作流假设。这是稳定、可复用的层。
- **技能** 是 MCP 工具的捆绑式、领域特定组合。例如，一个代码审查技能可能串联一个静态分析工具、一个风格检查工具和一个基于 LLM 的推理步骤。技能编码领域逻辑，但保持跨工作流的可移植性。
- **流** 是技能的端到端编排，代表完整的业务流程（例如，整个 PR 审查管道或从需求到部署的周期）。

每一层都在 CI/CD 管道中独立验证。组件测试覆盖工具和技能，交互测试覆盖它们组合成流的过程。

这些层级通过开放标准连接：用于工具集成的 MCP 和 Agent Skills、用于 agent 间通信的协议，以及用于跨由此产生的交互进行可观测性的 OpenTelemetry。

### 在实践中学习并专业化

在生产中，即使是范围明确的 agent 也可能因实际使用偏离设计时的预期而崩溃：查询模式发生变化，工具选择逻辑陷入困境，性能不可预测地下降。

正确的应对方式是将复杂 agent 分解为多个专用 agent，每个都有更清晰的指令、更简单的工具集和更聚焦的推理。好处是具体的：

- **独立演进：** 更新需求工程 agent 无需触及编码 agent。
- **独立扩展：** 当范围和接口明确定义时，单个 agent 可以独立扩展，而无需重新部署或调整整个系统的规模。
- **最小化影响范围：** 一个 agent 的失败或幻觉不会级联到整个工作流。
- **成本节省：** 范围狭窄的 agent 通常可以在更小的模型上运行，这降低了推理和托管成本。

复杂性可以从两个轴向上降低：

- **agent 内部：** 将能力分解为技能，因为工具和少样本示例在每次调用时消耗上下文，同时降低准确性并增加成本。通过经验确定粒度：合并 agent 很少选择的技能，拆分根据输入产生不同行为的技能。
- **agent 之间：** 将 agent 领域之外的工作通过 A2A 协议委托给专用对等 agent，而不是扩展当前 agent。agent 应该在能力上增长，而不是在上下文上增长。

关键在于，由于每个专用 agent 只访问其角色所需的数据和工具，这种架构有助于在设计上强制执行最小权限，这是受监管行业的合规要求。

然而，要实现这些好处，需要 agent 能够相互发现和互操作。为防止出现 *AI 孤岛*，我们维护一个 agent、工具和技能的*集中式*注册表。该注册表充当：

- **发现机制：** 根据构建期间存储的元数据编目可用的 agent、工具和技能。
- **治理检查点：** 确认资产类型获准用于生产，并维护审计追踪。
- **安全检查点：** 在批准前应用自动化安全检查，例如提示注入及类似问题。
- **去重保障：** 识别其他团队已维护的等效能力，以避免重复工作。此检查在注册时自动运行，在批准前标记重复项。

### 通过编纂实现规模化

从管理单个 agent 到治理 agent 集群的转变，要求将 agent 架构编纂为代码。使用 Terraform 或 [AWS CloudFormation](https://aws.amazon.com/cloudformation/) 等基础设施即代码框架，团队以与任何生产系统相同的严谨性来配置和管理 agent 基础设施：

- **细粒度最小权限角色：** 按 agent 或工具限定范围。
- **CI/CD 管道：** 跨账户和区域的一致、经过验证的部署，在测试失败或指标恶化时自动停止部署。
- **策略即代码：** 规则（例如，[AWS Config](https://aws.amazon.com/config/)、Open Policy Agent）扫描已部署的 agent，以检查是否符合组织标准。

这三者都作为管道门控强制执行，在注册前验证，而非事后审计。

采用模式刻意采用自下而上加集中策展的方式。各个团队构建技能和 MCP 工具来解决眼前的问题。所有团队都可以通过注册表共享其资产来做出贡献。一个中央团队构建自动化治理检查作为 CI 管道的一部分，以维护标准。为支持开发团队并促进*左移*，中央团队还提供构建块作为治理即代码模块。

这种平衡避免了中央强制架构和不受管理的实验。结果是，当新的运营问题出现时，团队可以扩展现有模式，而不是重新设计其架构。

## 在 agent 生命周期中落实最佳实践

架构模式和治理标准只有在嵌入团队构建和运营 agent 所使用的工作流中（在运行前和运行时）才有效。

### 部署前

治理在编写第一行编排逻辑之前就开始。团队获得从注册表中提取的参考架构模式和示例。这些预验证的蓝图覆盖常见的 agent 配置、工具集成模式和组合结构，加速开发的同时编码经过验证的默认值。在任何东西进入生产之前，标准化的 CI/CD 控制强制执行这些实践。图 2 展示了参考管道的四个阶段，从左到右依次运行。

- **范围蔓延：** 超出最初定义的目的或权限运行。
- **提示臃肿：** 指令中不必要的复杂性。
- **工具误用：** 在预期用例之外调用工具。
- **性能下降：** 准确性、延迟或成本效益下降。

### 运行时

在运行时，可观测性必须捕捉两类漂移。数据漂移表现为新的或变化的用户查询模式，或上游 API 的变化。模型漂移表现为错误率上升或工具选择准确性下降。当客户标记某个响应时，也会触发调查。针对漂移、分布偏移、评估分数下降或直接客户标记的警报会触发分阶段响应。这些事件被记录并转发给人工审查。此外，团队可以持续运行治理 agent 来标记漂移和运营问题，供负责团队调查。

## 总结

大规模构建和运营 agent 是一门工程学科，而非实验活动。

有效的治理必须从一开始就是结构性的、外部化的、领域敏感的，并以确定性方式强制执行。我们引入了三层组合层次结构（MCP 工具、技能和流）作为可复用、可组合和可互操作 agent 的架构基础，分解为专用 agent 以控制复杂性和范围。我们展示了每次 CI/CD 运行中的验证和评估如何使质量保证成为日常开发的一部分，以及将 agent 基础设施定义为代码如何让团队对集群中的每个 agent 应用相同的治理规则。最后，我们在 agent 生命周期中落实了这些模式，从预验证的参考架构和结构化管道到持续评估已部署 agent 的运行时治理 agent。

我们的经验表明这些实践在几个方面带来了回报。可复用的模板和共享基础设施降低了开发成本。由于标准交互模型和自动化部署，团队也更快地将 agent 投入生产。质量也得到了改善，因为管道在生命周期的每个阶段强制执行经过验证的模式。

扩展 agentic 治理是整个行业的当务之急。向 AI 和生成式 AI 支持的工作流自动化的转变已经在重塑工程组织的运作方式。赢家将是那些超越实验并建立纪律以大规模治理自主 agent 网络的人。有了这些实践，BMW 工程师可以专注于解决真正重要的问题：打造终极驾驶机器。

要将这些想法应用到您自己的 agent，请从 [AWS Well-Architected Framework](https://aws.amazon.com/architecture/well-architected/) 开始。本文将其用作可复用 agent 蓝图的模型。要了解 BMW 如何在其 AWS 环境中编纂治理，请阅读 [How BMW Group uses automation to achieve end-to-end compliance at scale on AWS](https://aws.amazon.com/blogs/mt/how-bmw-group-uses-automation-to-achieve-end-to-end-compliance-at-scale-on-aws/)。
