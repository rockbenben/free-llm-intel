# nOps 如何借助 Amazon Bedrock AgentCore 将 FinOps agent 交付速度提升 75%

[nOps](https://nops.io/) 是一个 AI 驱动的云优化解决方案，最近通过转向 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 重新构想了其 Financial Operations (FinOps) 分析能力。Amazon Bedrock AgentCore 是一项服务，可用任何框架或模型大规模构建、连接和优化 agent。这一新基础帮助 nOps 更好地服务那些在 Amazon Web Services (AWS)、Google Cloud Platform (GCP) 和 Microsoft Azure 上管理承诺优化的客户。通过对 Reserved Instances 和 AWS Savings Plans 等承诺进行持续优化，nOps 帮助团队最大化节省、降低风险，并自动化地消除人工 FinOps 的运营负担。如今，nOps 支持的客户所管理的云支出超过 40 亿美元。

在本文中，我们说明 nOps 如何利用 Amazon Bedrock AgentCore、Databricks Lakehouse Metric Views、Databricks Lakebase、Amazon DynamoDB 和 Vercel 转型我们的分析与 agent 体验，从而加快产品交付、提升响应质量并降低运营复杂度。

## 突破以 API 为中心的基础设施限制，扩展 FinOps AI

随着我们扩展产品组合和客户群，基础设施、前端和后端团队需要支持日益复杂的分析工作流，同时保持高可靠性和多租户隔离。现有基础设施模式带来了阻力：

- **响应延迟与不一致：** 来自基于 API 的数据访问的长上下文消息增加了延迟，降低了响应一致性。
- **系统复杂性：** 多个编排和可观测性层增加了系统复杂度。
- **创新 drag：** 工程时间越来越多地被基础设施维护而非产品创新所消耗。

> “我们试图在并非为分析驱动型 agent 设计的基础设施之上构建高级 AI 能力，这使得迭代缓慢、复杂，且容易出现不准确的情况。”

— Jordan Stein

## 当前状态

在转型之前，我们在现有基础设施组件之上推出了我们的 FinOps AI agent Clara，这些组件包括 Kubernetes、Amazon Bedrock 模型调用、LangChain/LangGraph 编排，以及围绕 Web API 的工具包装器。

这实现了快速的初步交付，但也暴露了结构性限制：

- **洞察获取更慢**：API 形态的数据和大的上下文窗口增加了轮次延迟。
- **运营开销**：多个非专用层让迭代和调试更加困难。
- **数据路径不匹配**：agent 的回答受制于 API 响应，而非专用的语义分析层。

为解决这一问题，我们转向以 Amazon Bedrock AgentCore 为运行时/编排中心、以 Databricks Metric Views 为受治理分析语义层、以 Databricks Lakebase 为持久应用状态的专用架构。我们选择 Bedrock AgentCore，是因为它的托管 agent 运行时、内置记忆和编排能力，以及使用任何框架或模型的自由。凭借这种自由，我们基于 Strands 构建，并在不切换服务的情况下演进模型选择，使团队能够专注于领域逻辑而非基础设施。

## 解决方案概览

我们设计的新架构可随需求扩展、产出准确答案，并让开发者更快交付。

下图展示了基于 Amazon Bedrock AgentCore 构建的 nOps Clara 解决方案的端到端架构：

图 1：nOps Clara 解决方案在 Amazon Bedrock AgentCore 上的端到端架构

该解决方案包含：

- **交互层：** 一个由 Vercel 托管的 Next.js Web 应用，客户通过由流式 Server-Sent Events 支撑的对话式界面与 Clara 交互。
- **agent 运行时层：** Amazon Bedrock AgentCore 运行一个基于 Strands 的单一 agent，可直接访问工具用于 canvas 操作、查询执行、数据源发现和工作流编排，从而减轻多 agent 路由开销。
- **数据层：** Databricks Lakehouse Metric Views 提供受治理的语义分析层，Databricks Lakebase（serverless PostgreSQL）存储持久的应用状态，如会话、canvas 和 widget 规格。
- **异步工作流层：** 一条事件驱动的执行路径，使用 Amazon DynamoDB 任务跟踪、Amazon Simple Notification Service (Amazon SNS) 和 Amazon Simple Queue Service (Amazon SQS) 通知，以及 Amazon API Gateway WebSocket 推送，用于实时更新 UI 的长时间运行分析任务。

### Web 应用

在交互层，客户通过 Vercel 托管的 Web 应用使用 Clara。请求流经一个 Next.js Backend for Frontend (BFF)，后者调用 Amazon Bedrock AgentCore。Clara 作为基于 Strands 的 agent 运行时运行，支持流式响应和工具调用。**用户可以手动调用 Clara 通过 Strands 工具调用的相同工作流。** 这是对 Clara 而言重要的一项需求和构建基石，因为它要求 agent 执行的任务遵循与人类在产品需求范围内相同的程序。

### Amazon Bedrock AgentCore 后端

运行时作为 Docker 容器部署在 Amazon Bedrock AgentCore 上，完整基础设施（运行时、记忆、guardrails、队列和工作器函数）定义在单个 AWS Cloud Development Kit (AWS CDK) 堆栈中。Clara 采用单 agent 架构而非多 agent 路由器：一个 Strands Agent 可直接访问以下工具：canvas 操作、查询执行、数据源发现和工作流编排。这避免了 agent 之间交接带来的延迟和错误传播开销，同时保持工具分发的确定性。

流式传输是体验的核心。一个自定义的合并层位于 Strands 异步流与 Server-Sent Event 输出之间，一次性处理三个问题：

- 心跳在长时间工具执行期间保持连接活跃。
- 带词边界感知刷新的文本缓冲区，将模型输出的小增量合并为可读的数据块，以帮助防止用户界面 (UI) 闪烁。
- 一个 widget 轮询工作器将实时 canvas 更新事件交织进同一条流。

Clara 使用 [AgentCore memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html) 及三种策略（语义事实、用户偏好和 canvas 摘要），从而随时间了解每个用户如何使用其数据。偏好影响布局选择、默认聚合和图表类型。事实捕获组织背景，如账户结构和成本分摊惯例。canvas 摘要在不同会话间保留分析思路，使用户可以从中断处继续，而无需重新解释上下文。会话按 canvas 划分（而非短暂的 HTTP 会话），因此对话上下文在浏览器刷新和重连后依然存在。

在租户隔离方面，[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 在 agent 被调用之前对原始用户 prompt 运行一次独立预检，强制执行跨租户数据访问策略和提示攻击检测。随后，一个租户策略层对出站流数据块和 widget 事件进行净化，在内部标识符到达前端之前将其脱敏。

### 数据湖仓

在数据层，Clara 不再依赖通用产品 API 获取分析上下文。相反，它使用精选工具对由 [Databricks Lakehouse Metric Views](https://docs.databricks.com/aws/en/business-semantics/metric-views) 支撑的 Databricks SQL Warehouse 执行 Structured Query Language (SQL)。这为度量和维度提供了受治理的语义层，提升了对话式回答与仪表板输出之间的一致性。

#### 示例

Metric views 与原始 SQL 的对比（True Customer Cost）

用户提问："Show my true AWS Cost for the last 30 days by account."

**原始 SQL Model Context Protocol (MCP) 方法：** 该工具必须每次跨各种 AWS 定价计划和基于承诺的折扣重新计算业务逻辑，然后在按账户分组之前连接并规范化这些值。

```
-- Raw SQL MCP approach
-- User asks: "True Customer Cost for last 30 days by account"
SELECT
    a.account_name,
    SUM(
        -- Base amortized cost
        COALESCE(c.amortized_cost, 0)
        -- Apply EDP discount
        - COALESCE(c.edp_discount_amount, 0)
        -- Apply PPA credits
        - COALESCE(c.ppa_credit_amount, 0)
        -- Add RI effective amortized component
        + COALESCE(c.ri_effective_cost, 0)
        -- Add Savings Plan effective amortized component
        + COALESCE(c.sp_effective_cost, 0)
    ) AS true_customer_cost
FROM raw_cost_and_usage c
JOIN account_dim a
    ON c.account_id = a.account_id
LEFT JOIN pricing_adjustments p
    ON c.account_id = p.account_id
    AND c.usage_day = p.usage_day
WHERE c.usage_day >= date_sub(current_date(), 30)
    AND c.usage_day < current_date()
    AND c.charge_type NOT IN ('Credit', 'Refund')
GROUP BY a.account_name
ORDER BY true_customer_cost DESC;
```

**Metric View MCP 方法：** 该工具查询一个预定义的 measure，利用详细注释和同义词（例如 `true_customer_cost`），并搭配一个维度（`account_name`）和一个时间范围（过去 30 天）。

```
-- Metric View MCP approach
-- Same user ask, but financial logic is pre-modeled in metric view measure
SELECT
    account_name,
    SUM(true_customer_cost) AS true_customer_cost
FROM mv_true_customer_cost
WHERE usage_day >= date_sub(current_date(), 30)
    AND usage_day < current_date()
GROUP BY account_name
ORDER BY true_customer_cost DESC;
```

**结果：** 一个受治理的 True Customer Cost 定义、更简单的 MCP 逻辑，以及跨聊天与仪表板的一致输出。

**Metric View 的 measure 在 large language model (LLM) 看来是什么样子**

**ID：** `true_customer_cost`
**显示名称：** True Customer Cost
**注释：** 在扣除抵扣、退款、承诺以及折扣（如 Enterprise Discount Program (EDP) 和 Private Pricing Agreements (PPA)）之后，客户支出的真实成本。

**同义词：** 用于 LLM 分析的自定义字段。我们借用了同义词来承载 key:value 对，以向前端发送额外的元数据。

### 状态层

在状态层，Databricks Lakebase（serverless PostgreSQL）存储持久的产品对象、会话、canvas、widget 以及查询/图表规格，使聊天中生成的洞察可以被提升为持久、可共享的分析产物。

### 分析工作流

对于长时间运行的分析工作流，我们引入了一条异步执行路径，使用工作流工作器、Amazon DynamoDB 任务跟踪、Amazon SNS 和 Amazon SQS 通知，以及 Amazon API Gateway WebSocket 推送。这样，Clara 可以提供响应迅速的用户交互，同时繁重的处理在后台完成并实时更新 UI。

### 结果

这些组件共同形成一个单一的托管架构，其中：

- Amazon Bedrock AgentCore 运行 agent 运行时和编排。
- Databricks Lakehouse Metric Views 驱动受治理的分析查询。
- Lakebase 存储持久的应用和仪表板状态。
- 异步工作流和 WebSocket 提供可扩展的实时用户体验 (UX)。

## 成效

通过围绕 Amazon Bedrock AgentCore 和湖仓优先的分析模型重构 Clara，我们为 AI 驱动的 FinOps 工作流建立了更具可扩展性的基础。

### 开发速度

- 投产时间缩短 75%，在用单一托管服务替换自管理的 Amazon Elastic Kubernetes Service (Amazon EKS) 技术栈后，从 10–12 个月降至 4 个月。
- 目前有 4–6 个可用于生产的 agent 在共享运行时上提供分析服务。

### 响应质量

- 正确率得分 81.7%（较上一期提升 145%），而 v1 约为 65%。
- 有用性得分 79.4%（较上一期提升 138%）。
- 在采用 Amazon Bedrock AgentCore 配合新的工具调用方法后，工具失败率从 7.49% 降至 0.92%。

### 运营效率

- 人工分析时间减少 75%，对 Customer Success Managers 和 Solutions Architects 而言，从估计的 2 小时降至 30 分钟。
- 通过流式响应和基于推送的工作流完成机制，减少了客户成功、解决方案架构和销售客户团队每日的人工投入。

### 基础设施简化

- 完全移除了 LangGraph/LangChain 编排层，由 AgentCore 运行时和 AgentCore 记忆，以及内置的请求路由和可观测性取而代之。这使工程团队得以专注于产品差异化。

## 结论

我们将 Clara 从一个分层的、以 API 为中心的 AI 助手，转变为一个统一的、agent 原生的分析系统。通过将 Amazon Bedrock AgentCore 与 Databricks Lakehouse Metric Views 和 Lakebase 相结合，我们创建了一种可复用的模式，用于构建企业级 AI 分析体验，在保持大规模准确性的同时不带来沉重的运营开销。
