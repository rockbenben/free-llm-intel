# 使用 Pipecat 和 Amazon Bedrock AgentCore Runtime 部署语音 agent —— 第 1 部分

*本文是 AWS 与 [Pipecat](https://www.pipecat.ai/?model=aws-nova-sonic) 的合作文章。*

部署能够保持自然、类人对话的智能语音 agent，需要把流式能力送到用户所在的地方——跨 Web、移动端和电话渠道，即使在高流量和不稳定的网络条件下也要如此。即便是很小的延迟也可能打断对话流，让用户觉得该 agent 反应迟钝或不可靠。对于客户支持、虚拟助手和外呼活动这类用例，自然的对话流对用户体验至关重要。在本系列博文中，你将了解流式架构如何借助 [Pipecat](https://github.com/pipecat-ai/pipecat) 语音 agent 在 [Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 上应对这些挑战。

在第 1 部分中，你将学习如何使用不同的网络传输方式（包括 WebSockets、WebRTC 和电话集成）在 AgentCore Runtime 上部署 Pipecat 语音 agent，并获得实用的部署指导与代码示例。

## AgentCore Runtime 对语音 agent 的价值

部署实时语音 agent 颇具挑战：你需要低延迟的流式能力、为安全而设的严格隔离，以及按不可预测的对话量动态扩缩容的能力。如果架构设计不当，你可能会遇到音频抖动、扩展性受限、因过度预置而成本虚高，以及复杂度上升等问题。如需深入了解语音 agent 架构（包括级联式（STT → LLM → TTS）与语音到语音两种方案），请参阅我们之前的博文[用 Amazon Nova Sonic 构建实时语音助手，并与级联架构对比](https://aws.amazon.com/blogs/machine-learning/building-real-time-voice-assistants-with-amazon-nova-sonic-compared-to-cascading-architectures/)。

[Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 通过提供安全、无服务器的环境来扩展动态 AI agent，从而应对这些挑战。每个对话会话都在相互隔离的 microVM 中运行以保证安全。它会针对流量峰值自动扩缩容，并能维持最长 8 小时的持续会话，因此非常适合长时间、多轮的语音交互。它只对实际使用的资源计费，有助于把闲置基础设施相关的成本降到最低。

Pipecat 是一个用于构建实时语音 AI pipeline 的 agentic 框架，只需极少配置即可在 AgentCore Runtime 上运行。把你的 Pipecat 语音 pipeline 打包成容器，直接部署到 AgentCore Runtime。该 runtime 支持实时音频的双向流式传输，并内置可观测性，用于追踪 agent 的推理过程与工具调用。

AgentCore Runtime 要求使用 ARM64（Graviton）容器，因此请确保你的 Docker 镜像针对 `linux/arm64` 架构构建。

## AgentCore Runtime 上语音 agent 的流式架构

本文假定你已熟悉常见的语音 agent 架构：具体来说，是在 pipeline 中把语音转文本（STT）与文本转语音（TTS）模型连接起来的[级联式](https://aws.amazon.com/blogs/machine-learning/building-intelligent-ai-voice-agents-with-pipecat-and-amazon-bedrock-part-1/)模型方案，以及像 [Amazon Nova Sonic](https://aws.amazon.com/ai/generative-ai/nova/speech/) 这样的[语音到语音](https://aws.amazon.com/blogs/machine-learning/building-intelligent-ai-voice-agents-with-pipecat-and-amazon-bedrock-part-2/)模型方案。如果你对这些概念还不熟悉，请先阅读我们早期关于这两条基础路线的博文：[级联式](https://aws.amazon.com/blogs/machine-learning/building-intelligent-ai-voice-agents-with-pipecat-and-amazon-bedrock-part-1/)和[语音到语音](https://aws.amazon.com/blogs/machine-learning/building-intelligent-ai-voice-agents-with-pipecat-and-amazon-bedrock-part-2/)，然后再继续。

在构建语音 agent 时，延迟是一项关键考量，它决定了语音对话感觉是否自然、是否可靠。对话需要近乎即时的响应，通常端到端要在一秒以内，才能保持流畅、类人的节奏。

![构建语音 agent：流式架构概览](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/03/15/voice-ai-streaming-architectures-overview.png)

要实现低延迟，你需要考虑多条路径上的双向流式传输，包括：

- **Client to Agent（客户端到 agent）：** 你的语音 agent 会运行在各类设备与应用上，从 Web 浏览器、移动应用到边缘硬件，每种环境的网络状况都各不相同。
- **Agent to Model（agent 到模型）：** 你的语音 agent 依赖双向流式传输来与语音模型交互。大多数语音模型都暴露实时 WebSocket API，你的 agent runtime 或编排框架可以消费这些 API，用于音频输入以及文本或语音输出。模型选择对实现自然的响应性至关重要。请选择像 [Amazon Nova Sonic](https://aws.amazon.com/ai/generative-ai/nova/speech/)（在级联式 pipeline 方案中则是 [Amazon Nova Lite](https://aws.amazon.com/nova/)）这样针对延迟做过优化、并提供快速首 token 时延（TTFT）的模型。
- **Telephony（电话）：** 对于通过呼叫中心或电话系统处理的传统呼入或呼出电话，你的语音 agent 还必须与电话服务提供商集成。这通常通过交接（handoff）和/或 Session Interconnect Protocol（SIP）转移来实现，即把实时音频流从电话系统转移到你的 agent runtime 进行处理。

在本系列的第 1 部分中，我们将聚焦 *Client to Agent* 这一连接，讨论如何把边缘设备到语音 agent 的第一跳网络延迟降到最低，并探讨语音 agent 架构其他组件相关的更多考量。

为说明这些概念，我们将探讨四种网络传输方案，并考量以下方面：

- 用户如何与你的语音 agent 交互（Web/移动应用或电话）
- 在各种变化的网络条件下的性能一致性与韧性
- 实现难易程度

| 方案 | 说明 | 性能一致性 | 实现难易程度 | 适用场景 |
| --- | --- | --- | --- | --- |
| WebSockets | Web 和移动应用通过 WebSockets 直接连接到你的语音 agent。 | 良好 | 简单 | 原型验证和轻量级用例。 |
| WebRTC（TURN 辅助） | Web 和移动应用通过 WebRTC 直接连接到你的语音 agent。 | 优秀 | 中等 | 生产用例，延迟取决于客户端经由 Traversal Using Relays around NAT（TURN）服务器中继后与 runtime 环境的直连。 |
| WebRTC（托管） | Web 和移动应用通过 WebRTC，经由先进、全球分布的基础设施连接到你的语音 agent。 | 优秀（全球分布） | 简单 | 生产用例，延迟优化交由具备全球分布式网络和媒体中继的专业提供商处理。还提供可观测性和多方通话等额外能力。 |
| Telephony | 语音 agent 通过传统电话呼叫访问。 | 优秀 | 中等 | 呼叫中心和电话用例。延迟可能取决于电话服务提供商。 |

### 示例方案：使用 WebSockets 双向流式传输

你可以从 WebSockets 开始，它是最简单的方案：它原生支持大多数客户端和 AgentCore Runtime。在 AgentCore Runtime 上部署 Pipecat 语音 agent，使用持久、双向的 WebSocket 连接在客户端设备与你的 agent 逻辑之间流式传输音频。

![使用 WebSockets 的示例方案](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/03/15/voice-ai-streaming-websockets.png)

该连接遵循一个直白的三步流程：

- **客户端请求 WebSocket 端点：** 客户端首先向中间服务器（/server）发送 POST 请求，以获取安全的 WebSocket 连接端点。
- **中间服务器处理 AWS 认证：** Pipecat 预构建前端上的中间服务器使用 AWS SDK 生成 AWS SigV4 预签名 URL，并把凭证作为查询参数嵌入其中。例如：`X?-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Credential=`
- **客户端建立直连：** 客户端使用通过认证的预签名 URL，直接连接 AgentCore Runtime 上的 agent 并双向流式传输音频，后续通信绕过中间服务器。

你使用 Pipecat 的 [WebSocket transport](https://docs.pipecat.ai/server/services/transport/fastapi-websocket) 在 `/ws` 路径上暴露端点，以满足 AgentCore Runtime 的要求。该架构把凭证管理与 agent 逻辑分离，从而在不让 AWS 凭证直接暴露给浏览器应用的前提下实现安全的客户端访问。

如需了解更多，请试用 AgentCore 上 Pipecat 的[使用 WebSockets transport 的代码示例](https://github.com/pipecat-ai/pipecat-examples/tree/main/deployment/aws-agentcore-websocket)。

### 示例方案：使用 WebRTC 双向流式传输并借助 TURN 辅助

虽然 WebSockets 适用于简单部署，但 WebRTC 可以提供更好的性能。它被设计为使用快速、轻量的网络路径发送音频，从而把延迟降到最低。它通常使用 UDP，以获得低延迟和更顺畅的实时体验，并在网络状况多变时提供更强的韧性。如果 UDP 不可用，WebRTC 会自动回退到 TCP；TCP 更可靠，但可能引入轻微延迟：这对语音来说不太理想，但在连接受限时会很有帮助。这种可靠性来自 Interactive Connectivity Establishment（ICE）服务器，它们通过 NAT 和防火墙协商点对点直连路径，并在无法直连时回退为经由 [Traversal Using Relays around NAT（TURN）](https://en.wikipedia.org/wiki/Traversal_Using_Relays_around_NAT) 服务器的流媒体中继。

Pipecat 支持 [SmallWebRTCTransport](https://docs.pipecat.ai/server/services/transport/small-webrtc)，用于客户端与 AgentCore Runtime 上的 agent 之间直接建立点对点 WebRTC 连接。与需要专用媒体服务器（例如 Selective Forwarding Units 或 SFU）的完整 WebRTC 架构相比，这种轻量级 transport 可以直接运行在 AgentCore Runtime 内，从而免去复杂的媒体服务器管理。

![使用 WebRTC TURN 辅助的示例方案](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/03/15/voice-ai-streaming-webrtc-turn.png)

在这种场景下，连接流程如下：

- **信令（Signaling）：** 客户端向中间服务器发送 Session Description Protocol（SDP）offer，中间服务器再把它转发到 AgentCore Runtime 中的 /invoke/ 端点。agent 的 `@app.entrypoint` 处理程序处理该 offer，并返回包含媒体能力和网络候选的 SDP answer。
- **连接建立：** 为建立直连，客户端与 agent 都使用 Interactive Connectivity Establishment（ICE）协议来发现最优网络路径。AgentCore Runtime 支持经 Traversal Using Relays around NAT（TURN）中继的连接。该协议按以下顺序尝试连通：  **直连：** 使用本地网络地址进行点对点连接。AgentCore Runtime 不支持这条路径，因为 runtime 环境无法分配公网 IP 地址。  **Session Traversal Utilities for NAT（STUN）辅助连接：** 使用 STUN 服务器通过 Network Address Translation（NAT）发现公网 IP/端口，并尝试直连。这条路径需要*同时*有入站和出站 UDP 流量，目前不受支持，因为 AWS NAT Gateway 使用对称 NAT，会使基于 STUN 的直连无法成功。  **经 Traversal Using Relays around NAT（TURN）中继的连接：** 通过 TURN 中继服务器转发媒体。使用托管服务（例如 [Cloudflare](https://developers.cloudflare.com/realtime/turn/) 或 [Twilio](https://www.twilio.com/docs/stun-turn)）、[Amazon Kinesis Video Streams（KVS）](https://aws.amazon.com/kinesis/video-streams/) 或自托管方案（例如 VPC 中的 [coturn](https://github.com/coturn/coturn)）来配置 TURN。在配置了 VPC 的 AgentCore Runtime 上推荐这条路径（详见下文）。
- **经 VPC 连接：** 连通性建立后，流量将经 VPC 从客户端路由到 runtime 环境（详见下一节）。

如需了解更多，请试用 AgentCore 上 Pipecat 的[使用 WebRTC transport 的代码示例](https://github.com/pipecat-ai/pipecat-examples/tree/main/deployment/aws-agentcore-webrtc)。

#### 在 VPC 上为 WebRTC 连通性配置 AgentCore Runtime

[代码示例](https://github.com/pipecat-ai/pipecat-examples/tree/main/deployment/aws-agentcore-webrtc) 演示了一个使用 WebRTC 的简单语音 agent。首先，你需要在两处配置 `ICE_SERVER_URLS` 环境变量：1）Pipecat 预构建前端上的中间服务器（`/server`），以及 2）runtime 环境（`/agent`）。这样它们之间就能双向通信。

接下来，你把 agent 部署到[配置了 VPC 网络的 AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-vpc.html)，以允许通过 UDP 与 TURN 服务器通信。为安全起见，你把 runtime 放置到私有 VPC 子网中，并在公有子网中放置一个 NAT Gateway 来路由互联网访问，如下图所示。

![为 WebRTC 连通性配置 VPC 版 AgentCore Runtime](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/03/15/voice-ai-streaming-webrtc-vpc-architecture.png)

采用这种方式，你可以配置 ICE 服务器以获得完整的 WebRTC 连通性，既支持 STUN，也支持带 TCP 回退的 UDP。例如，你可以按如下方式配置 Cloudflare 托管的 TURN：

```
# Configure agent/.env and server/.env
ICE_SERVER_URLS=stun:stun.cloudflare.com,turn:turn.cloudflare.com:53,turn:turn.cloudflare.com:3478,turn:turn.cloudflare.com:5349
```

#### 使用 Amazon Kinesis Video Streams（KVS）的 AWS 原生 TURN

如果需要完全 AWS 原生、可替代托管 TURN 服务的方案，[Amazon Kinesis Video Streams（KVS）](https://docs.aws.amazon.com/kinesisvideostreams/latest/dg/what-is-amazon-kinesis-video-streams.html) 可以承载 TURN 基础设施，而不引入第三方依赖。它通过 [GetIceServerConfig](https://docs.aws.amazon.com/kinesisvideostreams/latest/dg/API_signaling_GetIceServerConfig.html) API 提供临时的、自动轮换的 TURN 凭证，避免 NAT 穿越引入第三方依赖。流程如下：

- **一次性设置：** 创建一个 KVS 信令通道。该通道仅用于预置 TURN 凭证 —— 你的 agent 仍然使用 Pipecat 的 WebRTC transport 进行信令和媒体传输。
- **在连接时：** 你的 agent 调用 `GetSignalingChannelEndpoint` 获取 HTTPS 端点，然后调用 `GetIceServerConfig` 取回临时 TURN 凭证（URI、用户名、密码）。
- **配置对等连接：** 把返回的凭证作为 ICE 服务器传给 `RTCPeerConnection`。TURN 流量经由 KVS 托管的基础设施流转。

**使用 KVS 托管 TURN 时的注意事项**

| **因素** | **KVS 托管 TURN** | **第三方 TURN** |
| --- | --- | --- |
| AWS 原生 | 是 —— 无外部依赖 | 否 —— 需要外部账户 |
| 凭证管理 | 自动轮换 | 手动或由提供商管理 |
| 设置 | 创建信令通道 + API 调用 | 配置环境变量 |
| 最适合 | AWS 为中心的部署 | 追求简单，或已有提供商关系 |

其他注意事项：

- **成本：** 每个活跃信令通道每月 $0.03。在中低用量下，这可以忽略不计。
- **速率限制：** 每个通道的 `GetIceServerConfig` 限制为每秒 5 次事务（TPS）。对于每月超过 100,000 个会话的高用量部署，请实施通道池化策略，把请求分散到多个通道：`channels_needed = ceil(peak_new_sessions_per_second / 5)`。
- **不支持 PrivateLink：** VPC 仍需要互联网出网（经由 NAT Gateway）才能访问 KVS TURN 端点。
- **凭证有效期：** KVS TURN 凭证是临时的并自动轮换，因此你无需管理凭证轮换。

如需了解更多，请试用[使用 KVS 托管 TURN 的代码示例](https://github.com/pipecat-ai/pipecat-examples/tree/main/deployment/aws-agentcore-webrtc-kvs)。

### 示例方案：使用 AWS Marketplace 上的托管 WebRTC

![通过 Daily 使用托管 WebRTC 的示例方案](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/03/15/voice-ai-streaming-webrtc-daily-managed.png)

虽然直连 WebRTC 能带来控制力，但托管 WebRTC 提供商通常会提供 TURN 服务器和全球分布的 SFU，以实现可靠的连通性和低延迟的媒体路由。它还提供内置分析与可观测性、以及支持超越 1 对 1 agent 对话的多方房间等额外功能。对于大规模生产环境中的语音 agent，可以考虑 AWS Marketplace 上可用的托管提供商，例如 [Daily](https://aws.amazon.com/marketplace/seller-profile?id=d52484b0-a717-4b6d-a7aa-82f1c0c40b35)。Daily 在 AWS 上运行其全球分布的 WebRTC 基础设施，提供多种部署模式：

- **全托管 SaaS：** 你通过公开 API 端点连接到 Daily 托管的基础设施。这非常适合快速部署，以及优先考虑运维简便的环境。在这种场景下，AgentCore Runtime 中的 agent 只需通过公网连接到托管的 WebRTC 基础设施。
- **客户 VPC 部署：** 你把 Daily 的媒体服务器直接部署到自己的 VPC 中，以获得完整的网络控制力并满足严格的数据驻留合规要求。在这种场景下，你按上文所述为 AgentCore Runtime 配置 VPC。
- **带 AWS PrivateLink 的 SaaS：** 你连接到 Daily 托管的基础设施，并[配置 AWS PrivateLink](https://aws.amazon.com/blogs/networking-and-content-delivery/accelerate-ipv6-application-migration-with-aws-privatelink-and-dual-stack-network-load-balancers-udp-support/)，让流量经 VPC 端点直接流向 Daily 的托管基础设施而不经过公网，从而降低延迟，同时保持与 AWS 骨干网络的网络隔离。在这种场景下，你按上文所述为 AgentCore Runtime 配置 VPC。

如需了解更多，请联系你的 AWS 客户团队了解 [AWS Marketplace 上的 Daily](https://aws.amazon.com/marketplace/seller-profile?id=d52484b0-a717-4b6d-a7aa-82f1c0c40b35)，或试用[使用 Daily transport 的代码示例](https://github.com/pipecat-ai/pipecat-examples/tree/main/deployment/aws-agentcore-daily)及其 `DAILY_API_KEY`，以体验全托管 SaaS 方案。

### 示例方案：使用电话服务提供商

![使用电话的示例方案](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/03/15/voice-ai-streaming-telephony.png)

虽然 WebRTC 在 Web 和移动渠道表现出色，但电话交接让传统公共交换电话网（PSTN）集成成为可能，可用于呼叫中心、IVR 替代和外呼活动。要实现实时对话，你的 agent runtime 必须与语音模型、业务逻辑和电话服务提供商保持持久、双向的音频流。这些提供商提供托管的语音服务，通过简单的 API 处理传统电话基础设施的复杂性。根据电话提供商的能力，你可以用 Session Initiation Protocol（SIP）、流式 WebSocket 或 WebRTC 协议与之集成。Pipecat 的 [transports](https://docs.pipecat.ai/server/services/supported-services#transports) 和 [serializers](https://docs.pipecat.ai/server/services/supported-services#serializers) 提供了实现所需的连接器。

如需了解更多，请参阅 [Pipecat 电话指南](https://docs.pipecat.ai/guides/telephony/overview) 和[《构建 AI 驱动的语音应用：电话集成指南》](https://aws.amazon.com/blogs/machine-learning/building-ai-powered-voice-applications-amazon-nova-sonic-telephony-integration-guide/)。

## 结论

AgentCore Runtime 提供安全、无服务器的基础设施，可可靠地扩展语音 agent。本文介绍了低延迟对自然对话有多关键，以及根据你的延迟、可靠性和用量需求选择不同传输模式时的关键考量：WebSockets、TURN 辅助的 WebRTC、托管 WebRTC 和电话集成。在评估传输方案时，可先用最简单的 WebSockets 做快速原型验证，然后为生产部署考虑 VPC 模式下的 AgentCore 与 WebRTC，或托管提供商。如果你的语音 agent 打算处理电话或呼叫中心用例，请在你的实现中考虑与电话提供商已有的集成。

在本系列的第 2 部分中，你将探讨网络传输之外的更多考量：涵盖 agent 与模型通信、工具执行、记忆和检索等方面的流式策略，以实现最优的端到端延迟。
