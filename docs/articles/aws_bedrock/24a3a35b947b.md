# 在 Amazon SageMaker HyperPod Slurm 中推出用于可观测性和用户管理的托管集群扩展

维护一个用于基础模型开发的共享 Slurm 集群，需要让多个分别维护的配置片段与节点上实际运行的内容保持匹配。集群的形态存在于多个配置文件中，其软件存在于自定义脚本中，其网络拓扑存在于必须随节点变化而编辑的文件中，其用户存在于管理员必须维护并重新运行的名册中。随着时间推移，这些片段会偏离实际运行的内容，而且没有任何机制会在偏离发生时告知你。

我们认为集群配置应当像管理其他 AWS 基础设施一样被管理。你通过 API 或控制台声明想要的内容，AWS 在应用之前进行校验，集群持续保持在该状态，并且你可以看到它是否正常工作。在 2026 年期间，Amazon SageMaker HyperPod 将这一方法带到了 Slurm 集群，包括 API 驱动的 Slurm 配置、基于 AMI 的配置、持续预置、自动拓扑管理和深度健康检查。今天，我们推出了集群扩展（cluster extensions），将同样的方法带到运行中节点上的软件和设置，并提供用于可观测性和用户管理的托管扩展。不过，在整个过程中，你仍然保留对集群中每个节点的完全访问权限，包括控制器节点。你可以通过 SSH 登录、直接配置节点，并运行自己的生命周期脚本。API 让你需要维护的东西更少，直接访问让你拥有更多控制权，你可以选择平衡点。

在本文中，我们将介绍 2026 年推出的各项功能，并解释为什么运行中节点上的软件需要不同的机制。然后，我们将通过 API 和控制台展示集群扩展的工作原理，并跟随一个平台团队走过使用这些扩展的一个季度。

## Slurm 集群操作的声明式基础

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/image_43512305-1.jpg)

我们可以将 Slurm 集群的配置划分为六个层。其中五层描述集群本身：其定义、节点设置、容量、网络拓扑和硬件健康。第六层涵盖运行在其节点上的软件，我们将在下一节讨论。下图展示了这六个层。

2026 年早些时候，我们为前五层引入了声明式管理。通过 [API 驱动的 Slurm 配置](https://aws.amazon.com/about-aws/whats-new/2026/02/amazon-sagemaker-hyperpod-slurm/)，管理员在 CreateCluster 和 UpdateCluster 请求中定义节点角色、分区以及 Amazon FSx for Lustre 和 Amazon FSx for OpenZFS 挂载，并连接[外部记账数据库](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-external-accounting-db-slurm.html)。HyperPod 会更新分区设置，同时保留控制器节点上的其他 Slurm 自定义配置。[基于 AMI 的配置](https://aws.amazon.com/about-aws/whats-new/2026/05/amazon-sagemaker-hyperpod-ami-based-node/)用预配置了 Slurm、Docker、Enroot、Pyxis 和主目录的镜像替代例行设置脚本。[自定义 AMI](https://aws.amazon.com/about-aws/whats-new/2026/07/hyperpod-custom-ami-slurm/) 或 OnInitComplete 脚本处理组织特定的软件。[Slurm 的持续预置](https://aws.amazon.com/about-aws/whats-new/2026/03/amazon-sagemaker-hyperpod-continuous-provisioning/)在后台重试容量请求；[基于 AMI 的配置可与之配合使用](https://aws.amazon.com/about-aws/whats-new/2025/06/ami-configuration-continuous-slurm/)，[最低容量要求](https://aws.amazon.com/about-aws/whats-new/2026/05/amazon-sagemaker-hyperpod-mincount/)让团队可以指定 MinInstanceCount，而[集群操作](https://aws.amazon.com/about-aws/whats-new/2026/11/sagemaker-hyperpod-cluster-ops/)会跟踪扩缩容请求。

[自动拓扑管理](https://aws.amazon.com/about-aws/whats-new/2026/04/amazon-sagemaker-hyperpod-automatic-slurm-topology/)在节点扩缩容或被替换时维护网络布局。在 Slurm 25.11 或更高版本上，[分区级拓扑](https://aws.amazon.com/about-aws/whats-new/2026/07/hyperpod-partition-topology-slurm/)支持每个分区的树形或块状拓扑。对于硬件健康，[按需深度健康检查](https://aws.amazon.com/about-aws/whats-new/2026/04/amazon-sagemaker-hyperpod-on-demand-deep-health-check/)会对 GPU 施加压力并测试 NVIDIA Collective Communications Library (NCCL) 连接性，而[结合持续预置的深度健康检查](https://aws.amazon.com/about-aws/whats-new/2026/07/deep-health-check-continuous-slurm/)会在节点预置时运行。处于检查中的节点会留在 Slurm 维护预留中，直到检查完成，从而避免作业落在这些节点上。

## 推出集群扩展

到目前为止描述的五层是 HyperPod 在预置节点时可以推导或一次性应用的配置。第六层，即运行在节点上的软件，行为不同，因为它在集群的整个生命周期中不断变化。随着研究人员加入和离开、某个团队要求在一周内获得更深入的 GPU 指标、某个 exporter 发布修复，这一层都在变化。对于这一层，生命周期脚本一直是主要机制，而当软件不断变化时，它们存在缺点。脚本只在节点被预置时运行，因此每次变更都意味着编辑脚本，然后替换节点或在整个集群中重新运行脚本。错误只有在脚本于节点上运行时才会显现，而且没有任何机制报告已安装的内容，因此节点会随时间推移而逐渐产生差异。

我们希望软件在一个地方声明、在提交时接受检查、在所有节点上保持一致，并且在事后可见。2026 年 11 月，我们推出了集群扩展，这些是由 AWS 管理的软件包，你可以通过 API 或 Amazon SageMaker AI 控制台安装、配置、更新和移除，首批软件扩展是可观测性和用户管理（包括目录集成）。与脚本相比，扩展具有以下优势：

- **预先校验：** 当你通过 API 或控制台提交扩展的设置时，HyperPod 会根据其 schema 进行检查，因此拼写错误的设置会在到达任何节点之前被拒绝。
- **在每个节点上保持一致：** HyperPod 会将扩展应用到每个节点，包括通过扩容或替换添加的节点，并在集群扩缩容和自愈过程中保持节点一致。
- **通过 API 或控制台变更：** 你可以通过 API 调用或从 SageMaker AI 控制台更改设置或升级版本，而不是编辑脚本和替换节点。两种路径使用相同的已校验配置，本文在 API 示例旁边展示了控制台截图。
- **可见：** 每个扩展都会报告其状态和每节点健康状况。

当 HyperPod 提供托管软件能力时，请使用集群扩展。对于组织特定的软件或现有扩展未涵盖的初始化，请使用自定义 AMI 和生命周期脚本。HyperPod 目前支持两种集群托管扩展：

- 可观测性扩展（sagemaker-observability）收集节点、GPU、Elastic Fabric Adapter (EFA)、Slurm 作业和 Slurm 集群指标，并将它们发送到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 或 [Amazon Managed Service for Prometheus](https://aws.amazon.com/prometheus/)。
- 用户管理扩展（sagemaker-user-management）在每个节点上创建具有相同 ID 的用户和组，控制谁可以在每种节点类型上使用 SSH 和 sudo，并将用户注册到 Slurm 记账中。它还可以将集群连接到 Active Directory，例如 [AWS Directory Service for Microsoft Active Directory](https://aws.amazon.com/directoryservice/)。

### 使用集群扩展

你可以从 SageMaker AI 控制台或通过 API 使用集群扩展。在控制台上，集群详情页的 Extensions 选项卡会列出每个扩展及其状态、版本和 ARN，你也可以在这里安装新扩展。每个扩展都会添加自己的控件，例如可观测性的指标存储和“在 Grafana 中打开仪表板”按钮，以及用户管理的用户和组数量与“管理用户”按钮。你还可以通过 API（从 AWS CLI 或 SDK）管理每个扩展，以编写安装脚本、将设置纳入版本控制、在多个集群间重复设置，或从你自己的工具中检查状态和健康。下表列出了六个集群扩展 API，从安装扩展到列出可升级的版本，以及扩展的控制台视图。

当你创建或更新扩展时，HyperPod 会在 API 调用期间根据该版本的 schema 校验你的设置，因此拼写错误的设置会立即被拒绝。然后它会将版本和设置记录为期望状态并应用它们，每个节点只安装其角色所需的内容，例如仅在 GPU 节点上安装 GPU exporter。新节点和替换节点会在启动几分钟后获得相同的状态，每个节点都会报告扩展是否已应用以及是否健康。

更新只发送你希望更改的设置，HyperPod 会将它们合并到已存储的设置中。仅在节点上出现的问题（例如某个端口或用户 ID 已被其他东西占用）会出现在 DescribeClusterExtension 的 Health 字段中，按原因分组，并附有代码、消息和受影响节点数量。HyperPod 会自行重试内部故障；对于其他情况，你修复原因并在不进行任何更改的情况下调用 UpdateClusterExtension，以重试受影响的节点。

扩展的状态在变更 rollout 期间为 Creating 或 Updating，当每个节点都运行所请求的版本和设置且没有任何问题报告时为 Active，当部分节点失败或报告问题时为 Degraded。每个扩展都有自己的 ARN，因此平台团队可以拥有 sagemaker-user-management，而监控团队拥有 sagemaker-observability。每个健康问题都会指明组件、描述对集群的影响、给出下一步操作，并统计受影响的节点数量，这样你无需登录每个节点就能知道该去哪里查看，如下图所示。

### 何时使用集群扩展，何时使用生命周期脚本

一个有用的决策方法是问：软件归谁所有，以及它变化的频率如何。集群上的部分软件是组织特有的，例如安全代理、许可证服务器以及数据管道所期望的存储布局。生命周期脚本和自定义 AMI 是适合它们工具，因为只有你的团队知道它需要什么。其余的是几乎每个集群都需要的软件，例如 GPU 和作业指标，以及具有一致 ID 和访问规则的用户账户。这类软件必须在每个节点上保持一致并且不断变化，因此集群扩展更合适，因为你只需声明一次，HyperPod 会校验它，而且每个扩展都会报告是否健康。

这两种方法可以共存，但每个组件应只有一个所有者。不要同时通过生命周期脚本和扩展管理同一个 exporter、用户或服务，因为相互竞争的配置可能导致安装或运行时冲突。集群扩展可与所有生命周期配置选项配合使用。

如果你已经通过脚本运行这些能力，可以一次一个能力地迁移到扩展，迁移期间脚本和扩展可以并行运行。对于每个能力，迁移需要四个步骤：

- 调用 UpdateClusterSoftware 将集群迁移到 2026 年 11 月或更高版本的 HyperPod AMI。
- 在生命周期脚本中关闭该能力，并将脚本上传到你的 S3 存储桶，以便新节点跳过它。
- 在计划维护窗口内，停止并移除每个节点上由脚本安装的代理。这是唯一需要手动、全集群操作的步骤。
- 调用 CreateClusterExtension，在干净的集群上安装扩展。

如果有任何遗留内容，安装过程会指出冲突，例如已在使用中的端口，DescribeClusterExtension 会在 Health 下显示它。使用用户管理时，你保留相同的用户名和用户 ID。下图展示了四个步骤。

### 开始使用集群扩展所需的条件

你需要一个运行 2026 年 11 月 2 日或更高版本 HyperPod AMI 的 HyperPod Slurm 集群，并[启用持续预置](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-scaling-slurm.html)。扩展会以 root 身份在每个节点上运行软件，因此请将 CreateClusterExtension、UpdateClusterExtension 和 DeleteClusterExtension 视为管理员权限。我们建议不要将它们授予集群的执行角色，因为每个能登录节点的用户都可以使用其凭证。该角色确实需要访问扩展所使用的目标，即用于可观测性的 Amazon CloudWatch 或 aps:RemoteWrite，以及用于用户管理读取的 Active Directory 密钥的 secretsmanager:GetSecretValue。如果这些密钥使用客户管理的 AWS Key Management Service (AWS KMS) 密钥加密，该角色还需要对该密钥具有 kms:Decrypt 权限。用户管理还需要一个共享文件系统（例如 Amazon FSx for Lustre）用于主目录。

有关操作步骤、IAM 策略和配置参考，请参阅 Amazon SageMaker AI 开发人员指南中的 [Amazon SageMaker HyperPod Slurm 集群的集群扩展](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-slurm-extensions.html)。

## 平台团队使用集群扩展管理共享 Slurm 集群的历程

为了了解集群扩展在实践中如何使用，我们以一个平台团队为例，该团队为多个研究组管理一个共享 Slurm 集群。该团队需要可审查的集群定义、GPU 和作业指标、企业目录访问、合作伙伴实验室的本地账户，以及可观测性和用户管理的独立所有权。以下示例展示了该团队如何配置这些能力并应对日常变更和故障。

### 从一个定义创建集群

管理员在单个 CreateCluster 请求中声明整个集群，包括节点角色、分区、FSx 挂载、最低容量、深度健康检查和外部记账数据库。有关完整的示例请求，请参阅[使用 AWS CLI 开始使用 SageMaker HyperPod](https://docs.aws.amazon.com/sagemaker/latest/dg/smcluster-getting-started-slurm-cli.html)。

该请求没有生命周期配置、拓扑文件或 Slurm 配置文件。每个 SlurmConfig 为其实例组指定一个角色，GPU 组加入 train 分区。基于 AMI 的配置设置节点，安全团队的合规代理已包含在自定义 AMI 中。GPU 组请求 8 个节点并要求 6 个，因此作业可以在 6 个节点就绪后立即启动，而 HyperPod 会预置其余节点，并在每个 GPU 节点到达时进行健康检查。HyperPod 会自行选择 P5 节点的树形拓扑，记账会写入团队拥有的 Amazon Relational Database Service (Amazon RDS) 数据库。管理员仍然可以通过 SSH 登录控制器节点，直接检查或调优 Slurm。

### 安装可观测性

领导层希望获得 GPU 和作业指标，因此管理员安装可观测性扩展。在 SageMaker AI 控制台的集群 Extensions 选项卡上，管理员选择可观测性扩展，选择指标类别及其级别和收集间隔，并选择两种指标存储之一：Amazon CloudWatch 或 Amazon Managed Service for Prometheus。以下截图显示了选择一个存储的安装表单。另一个选项在同一字段中可用。

![可观测性扩展的控制台安装表单，可配置指标级别并可选择指标存储](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22428-7.png)

图 7：从控制台安装可观测性扩展，可配置指标级别并可选择指标存储

通过 API 进行的相同安装只需一次 create-cluster-extension 调用。以下示例使用 Amazon CloudWatch 作为指标存储。要将指标发送到 Amazon Managed Service for Prometheus，请在同一配置中设置 Prometheus 目标。

管理员通过一次 create-cluster-extension 调用安装扩展：

```
aws sagemaker create-cluster-extension \
    --cluster-arn arn:aws:sagemaker:us-west-2:{{111122223333}}:cluster/{{abcd1234efgh}} \
    --extension-name sagemaker-observability \
    --configuration-values file://observability-config.json
```

该调用返回扩展的 ARN，管理员在后续调用中使用它：

```
{
    "ExtensionArn": "arn:aws:sagemaker:us-west-2:111122223333:extension/sagemaker-abcd1234efgh/sagemaker-observability/0a1b2c3d4e5f"
}
```

无论以哪种方式安装，每个节点只运行与其角色相关的组件，例如 GPU 节点上的 DCGM 和 EFA exporter，以及控制器上的 Slurm 集群指标。schema 错误会在 rollout 之前被拒绝，而节点特定的冲突会出现在扩展健康中。

安装后，扩展会出现在集群的 Extensions 选项卡上，显示其版本、状态和 ARN。截图显示了一个同时安装了可观测性和用户管理扩展的集群的选项卡，两者均为 Active。

### 开启更深入的 GPU 和 NCCL 指标

后来，一个正在调优多节点训练的研究团队要求更多细节，因此管理员只发送要更改的设置：

```
aws sagemaker update-cluster-extension \
    --cluster-arn {{cluster-arn}} \
    --extension-arn {{observability-extension-arn}} \
    --configuration-values '{"metricsProvider":{"acceleratedComputeMetrics":{"level":"ADVANCED"},"ncclMetrics":{"level":"ENABLED"}}}'
```

HyperPod 会将这些设置合并到已存储的配置中，并应用到每个节点，只重启设置发生更改的组件。调查结束后，将两者设置为 null 可恢复默认值，并且在整个过程中不会替换节点或重新运行脚本。

### 修复指标投递问题

一天早上，扩展显示为 Degraded。一个新的实例组的执行角色缺少 aps:RemoteWrite，describe-cluster-extension 显示了影响：

```
{
    "NodeSummary": { "TotalCount": 19, "ActiveCount": 11 },
    "Health": {
        "Issues": [
            {
                "Code": "ExtensionUnhealthy",
                "Message": "otel-exporter-health: no successful exports in 5m6s",
                "NodeCount": 8
            }
        ]
    }
}
```

管理员添加权限后，节点报告健康，扩展恢复为 Active，无需重新安装任何内容。

### 为人员授予访问权限

用户管理扩展管理每个节点上的 Linux 用户和组，以及谁可以在每种节点类型上登录并使用 sudo。你声明谁应存在以及他们可以做什么，HyperPod 会将其应用到每个节点，包括稍后添加或替换的节点，因此无需为了添加或删除用户而连接节点或运行脚本。用户来自你在配置中列出的本地账户、通过 LDAPS 从 Active Directory 获取，或两者兼有，每个组都会指明其成员可以通过 SSH 登录以及获得免密 sudo 的节点类型（controller、login 或 compute）。

对于平台团队，安全部门希望使用企业身份，并将 sudo 保留给管理员，而一个不在目录中的合作伙伴实验室需要自己的账户。管理员在一个配置中声明两个来源，并带有组规则，说明每个组可以登录和使用 sudo 的节点类型：

```
{
    "sharedFilesystemMount": "/fsx",
    "userSources": {
        "localUsers": {
            "groups": [
                { "name": "cluster-admins", "gid": 3002,
                  "ssh": [ { "nodeTypes": ["controller", "login", "compute"] } ],
                  "sudo": [ { "nodeTypes": ["controller", "login", "compute"] } ] },
                { "name": "partner-lab", "gid": 3101,
                  "ssh": [ { "nodeTypes": ["login", "compute"] } ] }
            ],
            "users": [
                { "username": "admin-1", "uid": 2001, "groups": ["cluster-admins"] },
                { "username": "partner-1", "uid": 2101, "groups": ["partner-lab"] }
            ]
        },
        "ldap": {
            "ldapUri": ["ldaps://{{ad.example.com}}"],
            "ldapSearchBase": "{{dc=example,dc=com}}",
            "ldapDefaultBindDn": "{{CN=ReadOnly,OU=Users,DC=example,DC=com}}",
            "ldapDefaultAuthtokSecretArn": "arn:aws:secretsmanager:us-west-2:{{111122223333}}:secret:{{ad-readonly-AbCdEf}}",
            "ldapTlsCacertSecretArn": "arn:aws:secretsmanager:us-west-2:{{111122223333}}:secret:{{ldaps-ca-GhIjKl}}",
            "domain": "{{example.com}}",
            "useFullyQualifiedNames": "ENABLED",
            "ldapGroups": [
                { "name": "{{ClusterAdmin@example.com}}",
                  "ssh": [ { "nodeTypes": ["controller", "login", "compute"] } ],
                  "sudo": [ { "nodeTypes": ["controller", "login", "compute"] } ] },
                { "name": "{{ml-researchers@example.com}}",
                  "ssh": [ { "nodeTypes": ["login", "compute"] } ] }
            ]
        }
    }
}
```

访问是显式的，因此安装扩展后，只有授予 SSH 访问权限的组以及默认 ubuntu 用户可以登录。目录用户保留其在 Active Directory 中的身份和组成员资格，而合作伙伴实验室的用户获得相同的 ID、主目录和默认 Slurm root 账户。

### 升级扩展以获取新功能而无需更新 AMI

当 AWS 发布扩展的新版本时，管理员列出可安装的版本并就地升级，无需更新 AMI：

```
aws sagemaker list-cluster-extension-versions \
    --extension-name sagemaker-observability

aws sagemaker update-cluster-extension \
    --cluster-arn {{cluster-arn}} \
    --extension-arn {{observability-extension-arn}} \
    --extension-version {{new-version}}
```

HyperPod 会根据新版本的 schema 检查已存储的设置，如果设置对其无效，则拒绝请求且不做任何更改。否则，新版本会 rollout 到每个节点，稍后加入的节点也会获得它。升级只能向前进行，因此管理员会选择维护窗口。随后，可以通过类似之前的更新开启该版本带来的任何新设置或能力。

### 扩展集群并替换故障节点

在季度末运行之前，管理员对 GPU 组启动按需深度健康检查，然后使用 batch-add-cluster-nodes 添加节点。请求在 HyperPod 接受后立即返回，因此管理员将其作为集群操作来跟踪：

```
aws sagemaker list-cluster-operations \
    --cluster-name shared-gpu-cluster \
    --status InProgress
```

随着容量到位，每个节点都会接受健康检查、加入 Slurm、在拓扑中占据其位置，并获得与其他每个节点相同版本和设置的两个扩展。如果 GPU 在运行期间发生故障，替换节点会以相同方式配置并获取扩展。

### 审查谁拥有访问权限

在季度末，安全部门询问谁在控制器上拥有 sudo，管理员通过 API 回答，无需登录节点：

```
aws sagemaker describe-cluster-extension \
    --cluster-arn {{cluster-arn}} \
    --extension-arn {{user-management-extension-arn}} \
    --query ExtensionDetails.ConfigurationValues --output text |
jq '[.userSources.localUsers.groups[]?, .userSources.ldap.ldapGroups[]?]
    | map(select(any(.sudo[]?; .nodeTypes | index("controller")))) | map(.name)'
```

答案是 cluster-admins 和 ClusterAdmin@example.com，目录组的成员资格在目录中审计。由于每个扩展都有自己的 ARN，平台团队的角色只能更新 sagemaker-user-management，监控团队的角色只能更新 sagemaker-observability，而安全部门对两者具有只读访问权限。这些权限都不属于集群的执行角色。当扩展为 Active、ActiveCount 等于 TotalCount 且 Health 为空时，每个节点都运行完全相同的配置。

## 结论

当集群的更多部分被声明、校验、收敛和可观测时，运行起来就更容易。今年的改进将这一点带到了 HyperPod Slurm 集群的定义、节点设置、容量、网络拓扑和硬件健康，而自 2026 年 11 月起可用的集群扩展将这一点带到了节点上的软件，也就是变化最频繁的那一层。生命周期脚本和自定义 AMI 仍然专注于组织特有的内容，控制器节点仍然属于你。

要创建本文所述的集群，请参阅[使用 AWS CLI 开始使用 SageMaker HyperPod](https://docs.aws.amazon.com/sagemaker/latest/dg/smcluster-getting-started-slurm-cli.html)。要开始使用集群扩展，请参阅 [Amazon SageMaker AI 开发人员指南中的集群扩展](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-slurm-extensions.html)。请在评论中或通过你的 AWS 客户团队分享反馈。
