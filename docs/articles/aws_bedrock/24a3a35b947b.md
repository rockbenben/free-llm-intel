# Amazon SageMaker HyperPod Slurm 推出托管集群扩展，改善可观测性与用户管理

维护一个用于基础模型开发的共享 Slurm 集群，意味着要让多个分别维护的配置片段与节点上实际运行的内容保持匹配。集群的形态散落在多个配置文件里，软件写在自定义脚本里，网络拓扑存在必须随节点变化而编辑的文件里，用户则记在管理员必须维护并重新运行的名册里。时间一长，这些片段就会偏离实际运行的状态，而且没有任何机制会在偏离发生时告诉你。

我们认为，集群配置应当像其他 AWS 基础设施一样管理。你通过 API 或控制台声明想要的状态，AWS 在应用前完成校验，集群持续保持在该状态，你还能看到它是否正常。2026 年，Amazon SageMaker HyperPod 把这套做法带到了 Slurm 集群上，包括 API 驱动的 Slurm 配置、基于 AMI 的配置、持续预置、自动拓扑管理和深度健康检查。今天，我们推出集群扩展（cluster extensions），把同样的做法带到运行中节点上的软件和设置，并首批提供用于可观测性和用户管理的托管扩展。不过在整个过程中，你仍然保留对集群每个节点的完全访问权限，包括控制器节点。你可以通过 SSH 登录、直接配置节点，并运行自己的生命周期脚本。API 让你需要维护的东西更少，直接访问让你拥有更多控制权，平衡点由你选择。

本文将介绍我们在 2026 年推出的各项功能，解释为什么运行中节点上的软件需要另一种机制，然后通过 API 和控制台展示集群扩展的工作方式，并跟随一个平台团队走过使用这些扩展的一个季度。

## Slurm 集群操作的声明式基础

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/image_43512305-1.jpg)

可以把 Slurm 集群的配置看作分成六层。其中五层描述集群本身：定义、节点设置、容量、网络拓扑和硬件健康。第六层是运行在节点上的软件，我们将在下一节讨论。下图展示了这六层。

2026 年早些时候，我们为前五层引入了声明式管理。借助 [API 驱动的 Slurm 配置](https://aws.amazon.com/about-aws/whats-new/2026/02/amazon-sagemaker-hyperpod-slurm/)，管理员可以在 CreateCluster 和 UpdateCluster 请求中定义节点角色、分区，以及 Amazon FSx for Lustre 和 Amazon FSx for OpenZFS 挂载，并连接[外部记账数据库](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-external-accounting-db-slurm.html)。HyperPod 更新分区设置时，会保留控制器节点上的其他 Slurm 自定义配置。[基于 AMI 的配置](https://aws.amazon.com/about-aws/whats-new/2026/05/amazon-sagemaker-hyperpod-ami-based-node/)用预装了 Slurm、Docker、Enroot、Pyxis 和主目录的镜像取代例行设置脚本。[自定义 AMI](https://aws.amazon.com/about-aws/whats-new/2026/07/hyperpod-custom-ami-slurm/) 或 OnInitComplete 脚本负责组织特有的软件。[Slurm 的持续预置](https://aws.amazon.com/about-aws/whats-new/2026/03/amazon-sagemaker-hyperpod-continuous-provisioning/)会在后台重试容量请求；[基于 AMI 的配置可以与之配合](https://aws.amazon.com/about-aws/whats-new/2025/06/ami-configuration-continuous-slurm/)，[最低容量要求](https://aws.amazon.com/about-aws/whats-new/2026/05/amazon-sagemaker-hyperpod-mincount/)让团队可以指定 MinInstanceCount，[集群操作](https://aws.amazon.com/about-aws/whats-new/2026/11/sagemaker-hyperpod-cluster-ops/)则跟踪扩缩容请求。

[自动拓扑管理](https://aws.amazon.com/about-aws/whats-new/2026/04/amazon-sagemaker-hyperpod-automatic-slurm-topology/)会在节点扩缩容或被替换时维护网络布局。在 Slurm 25.11 或更高版本上，[分区级拓扑](https://aws.amazon.com/about-aws/whats-new/2026/07/hyperpod-partition-topology-slurm/)支持为每个分区配置树形或块状拓扑。在硬件健康方面，[按需深度健康检查](https://aws.amazon.com/about-aws/whats-new/2026/04/amazon-sagemaker-hyperpod-on-demand-deep-health-check/)会对 GPU 施压并测试 NVIDIA Collective Communications Library (NCCL) 连接性，[结合持续预置的深度健康检查](https://aws.amazon.com/about-aws/whats-new/2026/07/deep-health-check-continuous-slurm/)则会在节点预置时运行。处于检查中的节点会留在 Slurm 维护预留中，直到检查完成，作业因此不会落到这些节点上。

## 推出集群扩展

前面介绍的五层，都是 HyperPod 在预置节点时可以推导或一次性应用的配置。第六层是运行在节点上的软件，它的行为不同，因为它在集群的整个生命周期里不断变化：研究人员有进有出，某个团队要求在一周内拿到更细的 GPU 指标，某个 exporter 发布了修复。对这一层来说，生命周期脚本一直是主要机制，但当软件持续变化时，它就显得力不从心。脚本只在节点预置时运行，所以每次变更都得先改脚本，再替换节点，或者在整个集群里重跑一遍。错误只有在脚本于某个节点上执行时才会暴露，也没有任何东西报告装了什么，于是节点之间的差异会越拉越大。

我们希望软件能在一处声明、在提交时校验、在所有节点上保持一致，并且在事后可见。2026 年 11 月，我们推出集群扩展：这些是由 AWS 管理的软件包，你可以通过 API 或 Amazon SageMaker AI 控制台安装、配置、更新和移除，首批软件扩展是可观测性和用户管理（含目录集成）。与脚本相比，扩展有以下优势：

- **提交前校验：** 无论通过 API 还是控制台提交，HyperPod 都会按扩展的 schema 校验设置，拼错的配置在到达任何节点之前就会被拒绝。
- **每个节点保持一致：** HyperPod 会把扩展应用到每个节点，包括扩容或替换新增的节点，并在集群扩缩容和自愈过程中保持节点一致。
- **通过 API 或控制台变更：** 改一个设置或升一个版本，只需一次 API 调用，或者在 SageMaker AI 控制台操作，不必编辑脚本再替换节点。两条路径使用同一份经过校验的配置，本文会在 API 示例旁附上控制台截图。
- **可见：** 每个扩展都会报告自己的状态和逐节点健康情况。

当 HyperPod 提供某项托管软件能力时，请使用集群扩展。组织特有的软件，或现有扩展尚未覆盖的初始化工作，仍应使用自定义 AMI 和生命周期脚本。HyperPod 目前支持两种集群托管扩展：

- 可观测性扩展（sagemaker-observability）收集节点、GPU、Elastic Fabric Adapter (EFA)、Slurm 作业和 Slurm 集群指标，并发送到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 或 [Amazon Managed Service for Prometheus](https://aws.amazon.com/prometheus/)。
- 用户管理扩展（sagemaker-user-management）在每个节点上创建 ID 一致的用户和组，控制每种节点类型上谁可以使用 SSH 和 sudo，并把用户注册到 Slurm 记账中。它还能把集群接入 Active Directory，例如 [AWS Directory Service for Microsoft Active Directory](https://aws.amazon.com/directoryservice/)。

### 使用集群扩展

你可以从 SageMaker AI 控制台或通过 API 使用集群扩展。在控制台上，集群详情页的 Extensions 选项卡会列出每个扩展及其状态、版本和 ARN，也是安装新扩展的地方。每个扩展都会附带自己的控件，例如可观测性的指标存储和“在 Grafana 中打开仪表板”按钮，用户管理的用户与组数量及“管理用户”按钮。你也可以通过 API（从 AWS CLI 或 SDK）管理所有扩展，用来编写安装脚本、把设置纳入版本控制、在多个集群间复刻同一套配置，或从自己的工具里查询状态和健康。下表列出了六个集群扩展 API，从安装扩展到列出可升级的版本，右侧是扩展的控制台视图。

创建或更新扩展时，HyperPod 会在 API 调用过程中按该版本的 schema 校验设置，拼错的配置会被立即拒绝。随后它把版本和设置记录为期望状态并加以应用，每个节点只安装自己角色所需的内容，例如 GPU exporter 只装在 GPU 节点上。新节点和替换节点启动几分钟后就会获得相同的状态，每个节点都会报告扩展是否已应用、是否健康。

更新只发送你想改的设置，HyperPod 会把它们合并进已存储的设置。只在某个节点上出现的问题，比如某个端口或用户 ID 已被别的进程占用，会出现在 DescribeClusterExtension 的 Health 字段里，按原因分组，并附上代码、消息和受影响节点数。HyperPod 会自行重试内部故障；其他情况则需要你先修掉原因，再以不带任何改动的 UpdateClusterExtension 调用来重试受影响的节点。

扩展在变更 rollout 期间的状态是 Creating 或 Updating；当每个节点都运行所请求的版本和设置、且没有任何问题上报时为 Active；当部分节点失败或上报问题时为 Degraded。每个扩展都有自己的 ARN，因此平台团队可以负责 sagemaker-user-management，监控团队负责 sagemaker-observability。每条健康问题都会指明组件、说明对集群的影响、给出下一步操作，并统计受影响的节点数，这样你不必逐台登录节点就能知道该看哪里，如下图所示。

### 何时使用集群扩展，何时使用生命周期脚本

一个实用的判断方法是问：软件归谁所有，变化有多频繁。集群上有些软件是组织特有的，例如安全 agent、许可证服务器，以及数据管道所要求的存储布局。这类软件适合用生命周期脚本和自定义 AMI，因为只有你的团队知道它需要什么。剩下的则是几乎每个集群都需要的软件，比如 GPU 和作业指标，以及 ID 一致、访问规则明确的用户账户。这类软件必须在每个节点上保持一致，而且不断变化，所以集群扩展更合适：你只需声明一次，HyperPod 负责校验，每个扩展还会报告自己是否健康。

两种方式可以共存，但每个组件只能有一个所有者。不要用生命周期脚本和扩展同时管理同一个 exporter、用户或服务，因为相互竞争的配置可能导致安装或运行时冲突。集群扩展可与所有生命周期配置选项配合使用。

如果你已经用脚本运行这些能力，可以一次迁移一种能力到扩展，迁移期间脚本和扩展可以并行运行。每种能力的迁移分四步：

- 调用 UpdateClusterSoftware，把集群升级到 2026 年 11 月或更高版本的 HyperPod AMI。
- 在生命周期脚本中关闭该能力，并把脚本上传到 S3 存储桶，让新节点跳过它。
- 在计划内的维护窗口中，停止并移除每个节点上由脚本安装的 agent。这是唯一需要手动、全集群执行的步骤。
- 调用 CreateClusterExtension，在干净的集群上安装扩展。

如果有东西残留，安装过程会指出冲突，例如端口已被占用，DescribeClusterExtension 会在 Health 下显示。使用用户管理时，你保留原有的用户名和用户 ID。下图展示了这四个步骤。

### 开始使用集群扩展需要什么

你需要一个运行 2026 年 11 月 2 日或更高版本 HyperPod AMI 的 HyperPod Slurm 集群，并[启用持续预置](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-scaling-slurm.html)。扩展会以 root 身份在每个节点上运行软件，因此请把 CreateClusterExtension、UpdateClusterExtension 和 DeleteClusterExtension 当作管理员权限对待。我们建议不要把它们授予集群的执行角色，因为任何能登录节点的用户都可以使用该角色的凭证。该角色确实需要访问扩展所使用的目标，也就是用于可观测性的 Amazon CloudWatch 或 aps:RemoteWrite，以及用于读取用户管理所需 Active Directory 密钥的 secretsmanager:GetSecretValue。如果这些密钥由客户管理的 AWS Key Management Service (AWS KMS) 密钥加密，该角色还需要对该密钥具有 kms:Decrypt 权限。用户管理还需要一个共享文件系统（例如 Amazon FSx for Lustre）来存放主目录。

有关操作步骤、IAM 策略和配置参考，请参阅 Amazon SageMaker AI 开发人员指南中的 [Amazon SageMaker HyperPod Slurm 集群的集群扩展](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-slurm-extensions.html)。

## 一个平台团队用集群扩展管理共享 Slurm 集群的历程

为了看清集群扩展在实践中的用法，我们以一个平台团队为例：它为多个研究组管理一个共享 Slurm 集群。该团队需要可审查的集群定义、GPU 和作业指标、企业目录访问、为合作实验室准备的本地账户，以及可观测性和用户管理分别归属不同团队。下面的示例展示了这个团队如何配置这些能力，以及如何应对日常变更和故障。

### 用一份定义创建集群

管理员在单个 CreateCluster 请求中声明整个集群，包括节点角色、分区、FSx 挂载、最低容量、深度健康检查和外部记账数据库。完整的示例请求请参阅[使用 AWS CLI 开始使用 SageMaker HyperPod](https://docs.aws.amazon.com/sagemaker/latest/dg/smcluster-getting-started-slurm-cli.html)。

这个请求里没有生命周期配置、拓扑文件或 Slurm 配置文件。每个 SlurmConfig 为其实例组指定角色，GPU 组加入 train 分区。基于 AMI 的配置负责节点设置，安全团队的合规 agent 已经预置在自定义 AMI 中。GPU 组申请 8 个节点、要求至少 6 个，因此只要 6 个就绪作业就能启动，其余节点由 HyperPod 继续预置，并在每个 GPU 节点到位时做健康检查。HyperPod 会自行给 P5 节点选择树形拓扑，记账数据写入团队自己拥有的 Amazon Relational Database Service (Amazon RDS) 数据库。管理员仍然可以 SSH 登录控制器节点，直接检查或调优 Slurm。

### 安装可观测性

领导层想要 GPU 和作业指标，于是管理员安装可观测性扩展。在 SageMaker AI 控制台的集群 Extensions 选项卡上，管理员选择可观测性扩展，挑选指标类别及其级别、采集间隔，并从两种指标存储中选一个：Amazon CloudWatch 或 Amazon Managed Service for Prometheus。下面的截图显示了选中其中一种存储的安装表单，另一个选项在同一字段里可选。

![可观测性扩展的控制台安装表单，可配置指标级别并选择指标存储](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22428-7.png)

图 7：从控制台安装可观测性扩展，可配置指标级别并选择指标存储

同样的安装通过 API 只需一次 create-cluster-extension 调用。下面的示例使用 Amazon CloudWatch 作为指标存储。若要把指标发送到 Amazon Managed Service for Prometheus，只需在同一份配置里设置 Prometheus 目标。

管理员用一次 create-cluster-extension 调用安装扩展：

```
aws sagemaker create-cluster-extension \
    --cluster-arn arn:aws:sagemaker:us-west-2:{{111122223333}}:cluster/{{abcd1234efgh}} \
    --extension-name sagemaker-observability \
    --configuration-values file://observability-config.json
```

该调用返回扩展的 ARN，管理员在后续调用中使用它：

```
{
    "ExtensionArn": "arn:aws:sagemaker:us-west-2:111122223333:extension/sagemaker-abcd1234efgh/sagemaker-observability/0a1b2c3d4e5f"
}
```

无论用哪种方式安装，每个节点只运行与自身角色相关的组件，例如 GPU 节点上的 DCGM 和 EFA exporter，控制器上的 Slurm 集群指标。schema 错误会在 rollout 之前被拒绝，节点特有的冲突则会出现在扩展健康信息里。

安装完成后，扩展会出现在集群的 Extensions 选项卡上，显示版本、状态和 ARN。截图展示了一个同时装好可观测性和用户管理扩展、且两者均为 Active 的集群的选项卡。

![同时安装并处于 Active 状态的可观测性和用户管理扩展的集群 Extensions 选项卡](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22428-8.png)

### 开启更细的 GPU 和 NCCL 指标

后来，一个正在调优多节点训练的研究团队要求看到更多细节，于是管理员只发送要改的设置：

```
aws sagemaker update-cluster-extension \
    --cluster-arn {{cluster-arn}} \
    --extension-arn {{observability-extension-arn}} \
    --configuration-values '{"metricsProvider":{"acceleratedComputeMetrics":{"level":"ADVANCED"},"ncclMetrics":{"level":"ENABLED"}}}'
```

HyperPod 会把这些设置合并进已存储的配置并应用到每个节点，只重启设置发生变化的组件。调查结束后，把两项都设为 null 即可恢复默认值，整个过程不会替换节点，也不会重跑脚本。

### 修复指标投递问题

一天早上，扩展显示为 Degraded。一个新实例组的执行角色缺少 aps:RemoteWrite，describe-cluster-extension 显示了影响：

```
{
    "NodeSummary": { "TotalCount": 19, "ActiveCount": 11 },
    "Health": {
        "Issues": [
            {
                "Code": "ExtensionUnhealthy",
                "Message": "otel-exporter-health: no successful exports in 5m6s",
                "NodeCount": 8
            }
        ]
    }
}
```

管理员补上权限后，节点报告健康，扩展回到 Active，无需重装任何东西。

### 给人授予访问权限

用户管理扩展管理每个节点上的 Linux 用户和组，以及每种节点类型上谁可以登录、谁可以使用 sudo。你声明谁应该存在、能做什么，HyperPod 就会把它应用到每个节点，包括之后新增或替换的节点，因此没人需要为了增删用户去连节点或跑脚本。用户来源可以是你在配置里列出的本地账户、通过 LDAPS 连接的 Active Directory，或两者兼有；每个组都要指明其成员可以在哪些节点类型（controller、login 或 compute）上通过 SSH 登录，以及在哪些节点类型上获得免密 sudo。

对这个平台团队来说，安全部门希望使用企业身份，并把 sudo 留给管理员；而一个不在目录里的合作实验室需要自己的账户。管理员在一份配置里声明两个来源，并用组规则规定每个组可以登录和使用 sudo 的节点类型：

```
{
    "sharedFilesystemMount": "/fsx",
    "userSources": {
        "localUsers": {
            "groups": [
                { "name": "cluster-admins", "gid": 3002,
                  "ssh": [ { "nodeTypes": ["controller", "login", "compute"] } ],
                  "sudo": [ { "nodeTypes": ["controller", "login", "compute"] } ] },
                { "name": "partner-lab", "gid": 3101,
                  "ssh": [ { "nodeTypes": ["login", "compute"] } ] }
            ],
            "users": [
                { "username": "admin-1", "uid": 2001, "groups": ["cluster-admins"] },
                { "username": "partner-1", "uid": 2101, "groups": ["partner-lab"] }
            ]
        },
        "ldap": {
            "ldapUri": ["ldaps://{{ad.example.com}}"],
            "ldapSearchBase": "{{dc=example,dc=com}}",
            "ldapDefaultBindDn": "{{CN=ReadOnly,OU=Users,DC=example,DC=com}}",
            "ldapDefaultAuthtokSecretArn": "arn:aws:secretsmanager:us-west-2:{{111122223333}}:secret:{{ad-readonly-AbCdEf}}",
            "ldapTlsCacertSecretArn": "arn:aws:secretsmanager:us-west-2:{{111122223333}}:secret:{{ldaps-ca-GhIjKl}}",
            "domain": "{{example.com}}",
            "useFullyQualifiedNames": "ENABLED",
            "ldapGroups": [
                { "name": "{{ClusterAdmin@example.com}}",
                  "ssh": [ { "nodeTypes": ["controller", "login", "compute"] } ],
                  "sudo": [ { "nodeTypes": ["controller", "login", "compute"] } ] },
                { "name": "{{ml-researchers@example.com}}",
                  "ssh": [ { "nodeTypes": ["login", "compute"] } ] }
            ]
        }
    }
}
```

访问权限是显式声明的，所以扩展安装完成后，只有被授予 SSH 权限的组以及默认的 ubuntu 用户能够登录。目录用户保留自己在 Active Directory 中的身份和组成员关系，合作实验室的用户则获得相同的 ID、主目录以及默认的 Slurm root 账户。

同一份配置也可以从控制台管理。在用户管理扩展上点“Manage users”会打开集群的 Users 选项卡，管理员可以在那里添加、编辑和移除组与用户，并设置每个组可以登录和使用 sudo 的节点类型，如下图所示。

### 升级扩展，无需更新 AMI 即可获得新功能

当 AWS 发布扩展的新版本时，管理员列出可安装的版本，就地升级，无需更新 AMI：

```
aws sagemaker list-cluster-extension-versions \
    --extension-name sagemaker-observability

aws sagemaker update-cluster-extension \
    --cluster-arn {{cluster-arn}} \
    --extension-arn {{observability-extension-arn}} \
    --extension-version {{new-version}}
```

HyperPod 会按新版本的 schema 检查已存储的设置，如果这些设置对新版本无效，就拒绝请求、不做任何改动。否则，新版本会 rollout 到每个节点，之后加入的节点也会拿到。升级只能向前，所以管理员会挑一个维护窗口。该版本带来的新设置或新能力，随后可以用类似前面的更新操作开启。

### 扩展集群并替换故障节点

在季度末的那次运行之前，管理员先对 GPU 组发起按需深度健康检查，然后用 batch-add-cluster-nodes 添加节点。请求在 HyperPod 接受后立即返回，因此管理员把它当作集群操作来跟踪：

```
aws sagemaker list-cluster-operations \
    --cluster-name shared-gpu-cluster \
    --status InProgress
```

随着容量到位，每个节点都会接受健康检查、加入 Slurm、在拓扑中占据自己的位置，并获得与其他所有节点版本和设置都相同的两个扩展。如果运行期间有 GPU 故障，替换节点会以同样的方式完成配置并接上扩展。

### 审查谁拥有访问权限

季度末，安全部门询问谁在控制器上拥有 sudo，管理员直接通过 API 回答，无需登录节点：

```
aws sagemaker describe-cluster-extension \
    --cluster-arn {{cluster-arn}} \
    --extension-arn {{user-management-extension-arn}} \
    --query ExtensionDetails.ConfigurationValues --output text |
jq '[.userSources.localUsers.groups[]?, .userSources.ldap.ldapGroups[]?]
    | map(select(any(.sudo[]?; .nodeTypes | index("controller")))) | map(.name)'
```

答案是 cluster-admins 和 ClusterAdmin@example.com，目录组的成员关系在目录中审计。由于每个扩展都有自己的 ARN，平台团队的角色只能更新 sagemaker-user-management，监控团队的角色只能更新 sagemaker-observability，安全部门对两者都只有只读权限。这些权限都不应放在集群的执行角色上。当扩展为 Active、ActiveCount 等于 TotalCount、Health 为空时，每个节点运行的正是这套配置。

## 结论

一个集群被声明、校验、收敛和可观测的部分越多，运行起来就越轻松。今年的各项改进把这套做法带到了 HyperPod Slurm 集群的定义、节点设置、容量、网络拓扑和硬件健康，而自 2026 年 11 月起可用的集群扩展把它带到了节点上的软件，也就是变化最频繁的那一层。生命周期脚本和自定义 AMI 继续专注于组织特有的内容，控制器节点也始终属于你。

要创建本文所述的集群，请参阅[使用 AWS CLI 开始使用 SageMaker HyperPod](https://docs.aws.amazon.com/sagemaker/latest/dg/smcluster-getting-started-slurm-cli.html)。要开始使用集群扩展，请参阅 [Amazon SageMaker AI 开发人员指南中的集群扩展](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-slurm-extensions.html)。欢迎在评论区或通过你的 AWS 客户团队分享反馈。
