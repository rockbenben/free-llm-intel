## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# Natera 如何用 Amazon Bedrock AgentCore 为实验室运营设计 agentic AI 系统

在 [Natera](https://www.natera.com/) 这样一家无细胞 DNA（cfDNA）检测领域的领先企业，让实验室仪器持续正常运转至关重要，因为设备停机会打乱样本处理流程。由 Ariel Jirau 带领的 Natera 实验室工程团队与 AWS 合作构建了 SWARM（Systematic Workflow Analytics and Resolutions Manager），一套面向实验室运营的 agentic AI 系统。

本文梳理 Natera 团队如何借助 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 构建面向实验室运营的 agentic AI 系统，大规模沉淀并调用机构知识。文中给出完整架构，从知识库构建到系统自动部署与评估，方便你把同样的模式用到自己的运营工作流里。

SWARM 让首次响应速度提升约 130 倍，支持工单的自动化覆盖率达到 96.2%，工程师在工单一到达就能立刻调取机构知识。

## 挑战：知识连续性

Natera 的实验室运营依赖大量精密仪器，横跨多个设备系列，每种都有自己的故障模式、供应商文档和处置模式。负责维护这套基础设施的服务工程团队，靠的是个人深厚的经验，而不是标准化操作手册。当一位花多年时间专攻某个设备系列诊断的资深技师离职，他带走的机构知识实际上就随之流失了。当时没有任何系统能够大规模地捕获、整理并运用这些专长。

三个 Jira 队列每天涌进 65 张以上工单，平均首次响应时间长达 17.4 小时，仪器停机拖慢了实验室样本处理和患者报告。多招工程师也跟不上。SWARM 必须几分钟内就给出响应，覆盖各类设备给出准确诊断，并靠一套结构化的评估循环持续改进。

## Natera 为何选择 Amazon Bedrock AgentCore

Natera 团队选择在 Amazon Bedrock AgentCore 上构建 SWARM。这是 AWS 提供的一项完全托管、可扩展的服务，专为大规模构建、部署、连接、保护并运营 AI agent 而设计。促成这一决定的是三项核心要求：

- 无需人工介入，自主处理大量支持工单。
- 与 Jira、Confluence 等现有运营工具深度集成。
- 内置安全性与可观测性（加密、AWS Identity and Access Management (IAM) 集成、分布式追踪），不必由团队自行构建和维护定制基础设施。

“我们需要一个托管运行时，让工程精力集中在诊断准确性上，而不是耗在基础设施的杂活上——AgentCore 正好给了这些，还附带内置的身份管理，以及不改写 agent 逻辑就能换模型的灵活性，”Jirau 说。

AgentCore 与多项服务原生集成，包括 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/)（完全托管的 NoSQL 数据库服务）、[Amazon Simple Queue Service (Amazon SQS)](https://aws.amazon.com/sqs/)，以及 [AWS X-Ray](https://docs.aws.amazon.com/xray/latest/devguide/aws-xray.html)（Amazon CloudWatch 的一项能力）。

## SWARM 如何运作：两个 agent，一个技能库

SWARM 用两个互补的运行时，共用同一个技能库。swarm-agent 在工程师打开工单之前就自主生成结构化诊断报告；工程师则用 swarm-hive 实时交互、上传图片，并尝试其他排障路径。

“这套系统并不取代工程师——工单一到，它就让他们能调取全部深层的机构知识，”Jirau 说。

架构由四层串起：

- **事件层** 通过 Amazon EventBridge 和 Amazon SQS 路由 Jira 工单。
- **agent 层** 承载 swarm-agent、swarm-hive 和技能库，并把诊断报告回传给工程师。
- **上下文层** 取用供应商手册、历史工单和运营数据。
- **可观测性与交付层** 采集追踪、日志和指标。

## 安全架构

Natera 团队的第一个架构决定，是让 agent 跑在哪里。团队需要一个托管运行时，替他们处理容器编排、扩缩容和安全，而不必自己维护定制基础设施。他们选了 AgentCore runtime（Amazon Bedrock AgentCore 的一项能力）：它把 swarm-agent 和 swarm-hive 都放在安全、托管的环境中，自带身份管理与监控，省去自建 agent 执行层的工夫。无论你选哪个框架，都可以套用这一模式。

团队选了无密钥部署模型，因为 SWARM 跑在临床环境里，凭证泄露不可接受。OpenID Connect (OIDC) 与 [AWS Security Token Service (AWS STS)](https://docs.aws.amazon.com/STS/latest/APIReference/Welcome.html) 按每次部署生成限定范围的临时凭证，流水线里不留长期密钥。[AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 在组件层面强制最小权限。[Amazon Virtual Private Cloud (Amazon VPC)](https://docs.aws.amazon.com/vpc/latest/userguide/what-is-amazon-vpc.html) 用私有子网和 VPC endpoints 把流量挡在公网之外。[AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 对仅存的那几个凭证按 30 天周期自动轮换。

GitLab CI runner 向账户里配置好的 IAM 身份提供商出示 OIDC token，以此向 AWS 完成认证。AWS STS 把 token 换成限定在部署角色范围内的短期凭证（流水线中不存长期访问密钥）。设置细节见 [IAM OIDC provider 文档](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_create_oidc.html)。

下面的示例展示这一模式：面向 GitLab CI 的 IAM OIDC 信任策略大致是这样的：

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::ACCOUNT_ID:oidc-provider/gitlab.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "gitlab.com:sub": "project_path:YOUR_PROJECT:ref_type:branch:ref:main"
        }
      }
    }
  ]
}
```

这些基础设施层的安全控制与 SWARM 的数据治理策略协同起作用，共同构成在受监管临床环境中运行 AI 系统所需的完整合规态势。

## 合规与数据治理

SWARM 依据一份业务伙伴协议（[BAA](https://aws.amazon.com/compliance/hipaa-compliance/)），运行在符合 HIPAA 条件的 AWS 服务上，这体现了 Natera 作为临床实验室运营方的义务。每次 agent 调用都会记入审计日志（可检索的记录，满足数据访问可追溯性要求）。任何可识别患者身份的信息都不会进入向量索引或语言模型，工单里只有设备与工作流元数据。在 HIPAA 或类似监管框架下构建的团队，应在设计知识库流水线之前先确认 BAA 覆盖范围与数据隔离要求。

## 知识库与文档流水线构建

早期原型用的是通用检索，没有针对具体设备的元数据，结果不稳定，于是 Natera 团队专门针对技术设备文档搭了一条定制的文档处理流水线。[Amazon Titan Text Embeddings](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html) 生成用于语义检索的向量表示，[Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 提供完全托管的 Retrieval Augmented Generation (RAG)，把文档转成 embedding，按 100 条一批存储——这个批量是为了在索引吞吐量和 API 速率限制之间取平衡。对于含表格、图示、结构化程度高的源文档，与其依赖默认分块，不如投入定制解析流水线，每一次诊断都能叠加由此带来的准确率收益。

包括 Amazon Titan Text Embeddings 在内的 Amazon Bedrock 服务，以及 Amazon Bedrock AgentCore，已在多个 AWS 区域提供。最新信息见 [Amazon Bedrock 支持的区域](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html) 和 [Amazon Bedrock AgentCore 支持的区域](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-regions.html)。

Natera 团队用 tiktoken 分词器配合 cl100k_base 编码来度量分块边界。下面的示例展示这一模式，分块配置采用一套标准结构：

```
# Document chunking configuration
chunk_size = 1000  # tokens
chunk_overlap = 150  # tokens
encoding = tiktoken.get_encoding("cl100k_base")
batch_size = 100  # documents per embedding API call
```

批量摄取模式的更多细节，见 [Amazon Bedrock Knowledge Bases 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-how-it-works.html)。

“诊断准确性首先是数据质量问题，”Jirau 说，“把得分最低那个设备系列缺的供应商手册补上，没动模型，准确率就从 71% 提到了 75%。”

这决定了 Natera 团队的改进思路：准确率一旦停滞，先查数据覆盖，再谈模型调优，因为供应商文档的缺口才是漏诊最常见的成因。流水线会重新处理新增或更新的文档并刷新向量索引，且不打断正在进行的运营。

## 技能库架构

Natera 团队面临一个关键架构抉择：把逻辑直接写进 agent 的 prompt，还是另建一个带版本管理的技能库。Natera 选了后者，因为这样 SWARM 才可审计、可改进。

“诊断一旦出错，我们要能指到某一项具体技能，而不是把整个系统翻一遍调试——所以从一开始我们就建了带版本管理的技能库，”Jirau 说。

库里有 33 项技能：24 项针对具体仪器，覆盖 Natera 支持的全部设备系列；另有 9 项跨领域的工作流技能，广泛适用于各类工单。每项技能都有明确定义的接口，可独立测试，并按与整体系统相同的标准评估，被当作生产软件对待，而不是嵌在 prompt 里的逻辑。

技能架构有一条清晰的分工：Python 负责解析 Jira 字段、格式化 HTML 报告这类确定性任务，而大型语言模型（LLM）技能负责语言推理，比如解读症状、匹配供应商文档、生成诊断叙述。对构建多技能 agent 的团队来说，把确定性的 Python 技能和 LLM 驱动的推理技能这样分开，是影响力最大的决策之一。

## agent 运行时部署

Natera 把诊断工作拆成两个独立的运行时，因为自主的后台分析与交互式的工程协作，在延迟和上下文要求上根本不同。swarm-agent 为吞吐量而生：它按设备类型和症状挑技能、查知识库，产出一份结构化 HTML 报告，里面带首要原因假设、排好序的排障步骤和置信度标签。报告几分钟内送达 Amazon Simple Storage Service (Amazon S3)，并挂到 Jira 工单上。swarm-hive 为深度而设计：工程师可以做交互式追问、上传图片、探索别的路径，由 [AgentCore memory（Amazon Bedrock AgentCore 的一项能力）](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html) 跨会话保留每位工程师的对话上下文。

由于 swarm-hive 接受工程师自由格式的输入，prompt 会先经过 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 做内容过滤。

## 事件驱动的 Jira 集成

SWARM 通过 [Amazon EventBridge Scheduler](https://docs.aws.amazon.com/scheduler/latest/UserGuide/what-is-scheduler.html) 和一个轮询式的 [AWS Lambda 函数](https://aws.amazon.com/lambda/) 与 Jira 集成；后者是事件触发运行代码的 serverless 计算服务，这样就不用配 webhook。核验过的工单进入 Amazon SQS 队列，保证可靠投递。DynamoDB 以工单 ID 为分区键、配 time-to-live (TTL) 过期来处理去重，并存下每次运行的元数据（状态、成本、token 用量等）喂给评估循环。这个 `EventBridge-to-SQS` 模式把 agent 运行时与工单系统的可用性解耦开了。

下面的示例展示这一模式。去重表用一张极简的表结构，配 TTL 过期：

```
dynamodb.create_table(
    TableName='swarm-deduplication',
    KeySchema=[
        {'AttributeName': 'ticket_id', 'KeyType': 'HASH'}
    ],
    AttributeDefinitions=[
        {'AttributeName': 'ticket_id', 'AttributeType': 'S'}
    ],
    TimeToLiveSpecification={
        'Enabled': True,
        'AttributeName': 'ttl'
    }
)
```

## 可观测性设计

组件众多、彼此交互的 agentic 系统，没有逐次调用的追踪就很难调试，所以 Natera 团队在第一次生产部署之前就把可观测性做进了 SWARM。如果你在生产环境跑 agent，逐次调用追踪没有商量余地：缺了它，排查一次糟糕的诊断就只能靠猜是哪一项技能出了问题。

在临床实验室环境里，仪器停机直接影响患者报告，能追踪、告警并审计 agent 的每一步动作，并不是“锦上添花”的事，而是监管和运营上的要求。

SWARM 的可观测性技术栈用 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 为每次运行采集可检索日志，清楚记录运行健康状况。AWS X-Ray 从工单接入一路追到诊断报告，记下每次工具调用的耗时与成本；一旦某处变慢或变贵，团队就能定位到具体是哪一项技能，而不必靠猜。[Amazon Simple Notification Service](https://aws.amazon.com/sns/) 用邮件发送故障告警，Slack tracker 则让整个团队实时看到 agent 的活动。

## 持续评估方法

SWARM 用的是持续评估循环，而不是部署时测一次就完事；对文档会变、工作流会演进的系统来说，这一点尤其关键。每处理一张工单，agent 都会给出首要原因假设、排好序的排障步骤和一个自评置信度标签。工程师记录自己发现了什么、修了什么，评估器再把每条响应评为 Accurate、Partial 或 Wrong，并按设备系列细分。团队复核结果，找出 agent 表现不佳之处，落地修复（通常是更新知识库），再重跑评估集确认改进。

SWARM 的自评置信度标签与实际准确率呈方向性关联。标为 High confidence 的工单在 154 个评估案例中达到 74% 准确率，Moderate 和 Low confidence 工单则分别在 78 个和 37 个案例中都是 65%。要注意，Moderate 与 Low 目前准确率相同。Low confidence 的 37 个案例样本太小，得不出有统计意义的结论，Natera 团队预计随着评估数据集扩大，这两档会拉开差距。

High 与其余各档之间的这种区分，给工程师一个有用的信号：读诊断报告时，该对每条诊断给多大分量。

## SWARM 的性能

Natera 团队用 524 张支持工单评估 SWARM，建立性能基线。评估集这 524 张工单里，269 张带有 High、Moderate 或 Low 置信度标签，且有对应的、经工程师验证的处理结果可供比对。其余工单要么标签为 none，要么在分析时还没有经核验的处理结果。

平均首次响应时间从 17.4 小时降到约 8 分钟（快约 130 倍）。这些测量值取自 90 天生产评估期内的 Jira 工单元数据。覆盖率同样重要：96.2% 的工单能拿到自动首次响应，无需工程师启动诊断流程。覆盖率的计算口径是：在工程师审阅之前就收到 SWARM 生成诊断报告的来单占比。

## 在生产环境构建 agentic AI 的经验

SWARM 里的几处架构决策，可以直接搬到构建类似系统的团队身上。

- 把块大小和重叠量当成可调参数。合适的值取决于源文档的结构。
- 从一开始就把可追溯性做进技能库。诊断出错时，你要能指到某一项具体技能，而不是调试整个系统。
- 如果负载同时混有批处理和交互式查询，就把它们拆到不同的运行时里。
