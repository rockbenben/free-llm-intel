## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# Natera 如何使用 Amazon Bedrock AgentCore 为实验室操作设计代理 AI 系统

在无细胞 DNA (cfDNA) 测试领域的领导者 [Natera](https://www.natera.com/)，保持实验室仪器正常运行至关重要，因为设备停机会扰乱样品处理。由 Ariel Jirau 领导的 Natera 实验室工程团队与 AWS 合作构建了 SWARM（系统工作流分析和解决方案管理器），这是一个用于实验室运营的代理 AI 系统。

本文介绍了 Natera 团队如何使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 构建用于实验室操作的代理 AI 系统，该系统可大规模捕获和部署机构知识。它描述了完整的架构，从知识库构建到自动化系统部署和评估，因此您可以将相同的模式应用到您自己的操作工作流程中。

SWARM 的首次响应速度提高了约 130 倍，支持票证的自动化覆盖率达到 96.2%，让工程师在票证到达时立即获取机构知识。

## 挑战：知识连续性

Natera 的实验室运营依赖于涵盖多个设备系列的各种精密仪器，每种仪器都有自己的故障模式、供应商文档和解决模式。负责维护此基础设施的服务工程团队是根据深厚的个人专业知识而不是标准化的剧本来组织的。当一位花费数年时间诊断特定仪器系列的高级技术人员离开时，他们所携带的机构知识实际上就丢失了。不存在能够大规模捕获、组织或部署专业知识的系统。

三个 Jira 队列中每天有超过 65 个请求单，平均首次响应时间为 17.4 小时，仪器停机延迟了实验室样本和患者报告。雇用更多的工程师无法跟上步伐。 SWARM 必须在几分钟内做出响应，为各种设备类型提供准确的诊断，并通过结构化评估循环不断改进。

## 为什么 Natera 选择 Amazon Bedrock AgentCore

Natera 团队选择在 Amazon Bedrock AgentCore 上构建 SWARM，这是 AWS 提供的一项完全托管的可扩展服务，旨在大规模构建、部署、连接、保护和操作 AI 代理。三个核心要求推动了这一决定：

- 无需人工干预即可自主处理大量支持请求。
- 与 Jira 和 Confluence 等现有运营工具深度集成。
- 内置安全性和可观察性（加密、AWS Identity and Access Management (IAM) 集成和分布式跟踪），无需团队构建和维护自定义基础设施。

“我们需要一个托管运行时，让我们将工程工作的重点放在诊断准确性上，而不是基础设施管道上——AgentCore 为我们提供了这一点，以及内置的身份管理和交换模型的灵活性，而无需重写代理逻辑，”Jirau 说。

AgentCore 提供与服务的本机集成，包括 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/)（一种完全托管的 NoSQL 数据库服务）、[Amazon Simple Queue Service (Amazon SQS)](https://aws.amazon.com/sqs/) 和 [AWS X-Ray](https://docs.aws.amazon.com/xray/latest/devguide/aws-xray.html)（Amazon CloudWatch 的一项功能）。

## SWARM 的工作原理：两个智能体，一个技能库

SWARM 使用两个互补的运行时共享一个技能库。在工程师开具故障单之前，swarm-agent 会自动生成结构化诊断报告，而工程师则使用 swarm-hive 进行实时交互、上传图像并探索替代故障排除路径。

“该系统不会取代工程师，而是让他们在收到罚单后立即获得全面的机构知识，”Jirau 说。

四层连接架构：

- **事件层** 通过 Amazon EventBridge 和 Amazon SQS 路由 Jira 票证。
- **代理层**托管 swarm-agent、swarm-hive 和技能库，并将诊断报告返回给工程师。
- **上下文层**利用供应商手册、历史票据和运营数据。
- **可观察性和交付层**捕获跟踪、日志和指标。

## 安全架构

Natera 团队的第一个架构决策是在哪里运行代理。该团队需要一个托管运行时来处理容器编排、扩展和安全性，而不需要他们维护自定义基础设施。他们选择了 AgentCore 运行时（Amazon Bedrock AgentCore 的一项功能），因为它在安全的托管环境中托管 swarm-agent 和 swarm-hive，并具有内置身份管理和监控功能，从而无需构建和操作自定义代理执行层。无论您选择什么框架，都可以采用此模式。

该团队选择了无密钥部署模型，因为 SWARM 在临床环境中运行，凭证暴露是不可接受的。 OpenID Connect (OIDC) 和 [AWS Security Token Service (AWS STS)](https://docs.aws.amazon.com/STS/latest/APIReference/Welcome.html) 生成每个部署范围内的临时凭证，管道中没有长期密钥。 [AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 在组件级别强制执行最低权限。 [Amazon Virtual Private Cloud (Amazon VPC)](https://docs.aws.amazon.com/vpc/latest/userguide/what-is-amazon-vpc.html) 具有私有子网和 VPC 终端节点，可确保流量远离公共互联网。 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 以 30 天的自动周期轮换现有的少量凭证。

GitLab CI 运行程序通过向账户中配置的 IAM 身份提供商提供 OIDC 令牌来向 AWS 进行身份验证。 AWS STS 将令牌交换为部署角色范围内的短期凭证（管道中不存储长期访问密钥）。有关设置详细信息，请参阅 [IAM OIDC 提供商文档](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_create_oidc.html)。

以下示例说明了该模式：GitLab CI 的 IAM OIDC 信任策略遵循以下结构：
```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::ACCOUNT_ID:oidc-provider/gitlab.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "gitlab.com:sub": "project_path:YOUR_PROJECT:ref_type:branch:ref:main"
        }
      }
    }
  ]
}
```
这些基础设施级安全控制与 SWARM 的数据治理策略协同工作。它们共同构成了在受监管的临床环境中运行人工智能系统所需的完整合规态势。

## 合规性和数据治理

SWARM 根据业务伙伴协议 ([BAA](https://aws.amazon.com/compliance/hipaa-compliance/)) 在符合 HIPAA 条件的 AWS 服务上运行，反映了 Natera 作为临床实验室运营商的义务。每个代理调用都会进行审核记录（满足数据访问可追溯性要求的可搜索记录）。没有患者可识别信息触及向量索引或语言模型。票证仅包含设备和工作流程元数据。根据 HIPAA 或类似监管框架构建的团队应在设计知识库管道之前确认 BAA 覆盖范围和数据分离要求。

## 知识库和文档管道建设

早期原型使用通用检索，没有特定于设备的元数据，会产生不一致的结果，因此 Natera 团队构建了一个针对技术设备文档定制的自定义文档处理管道。 [Amazon Titan 文本嵌入](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html) 生成用于语义搜索的矢量表示，而 [Amazon Bedrock 知识库](https://aws.amazon.com/bedrock/knowledge-bases/) 提供完全托管的检索增强生成 (RAG)，将文档转换为以 100 个批次存储的嵌入，大小选择平衡索引吞吐量与 API 速率限制。对于包含表格和图表的高度结构化源文档，投资自定义解析管道而不是依赖默认分块可以提高每次诊断的准确性。

Amazon Bedrock 服务（包括 Amazon Titan Text Embeddings 和 Amazon Bedrock AgentCore）已在多个 AWS 区域推出。有关最新信息，请参阅 [Amazon Bedrock 支持的区域](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html) 和 [Amazon Bedrock AgentCore 支持的区域](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-regions.html)。

Natera 团队使用带有 cl100k_base 编码的 tiktoken 分词器来测量块边界。以下示例说明了该模式，分块配置遵循标准结构：
```
# Document chunking configuration
chunk_size = 1000  # tokens
chunk_overlap = 150  # tokens
encoding = tiktoken.get_encoding("cl100k_base")
batch_size = 100  # documents per embedding API call
```
有关批量摄取模式的更多信息，请参阅 [Amazon Bedrock 知识库文档](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-how-it-works.html)。

“诊断准确性首先是数据质量问题，”吉劳说。 “为得分最低的仪器系列添加缺失的供应商手册，将准确度从 71% 提高到 75%，而无需更改型号。”

这塑造了 Natera 团队的改进方法：当准确性停滞不前时，团队在模型调整之前检查数据覆盖范围，因为供应商文档中的差距是漏诊的最常见原因。该管道重新处理新的或更新的文档并刷新向量索引，而不会中断活动操作。

## 技能库架构

Natera 团队面临一个关键的架构选择：将逻辑直接嵌入到代理提示中，或者构建一个单独的版本化技能库。 Natera 选择库方法是因为它使 SWARM 可审计和可改进。

“当诊断错误时，我们需要指出特定技能，而不是调试整个系统 - 这就是我们从一开始就构建版本化技能库的原因，”Jirau 说。

该库包含 33 项技能：24 项特定于仪器的技能，涵盖 Natera 支持的全系列设备系列，加上 9 项广泛适用于各种票据类型的跨领域工作流程技能。每个技能都有一个定义的界面，可以独立测试，并根据与整个系统相同的标准进行评估，被视为生产软件，而不是嵌入的提示逻辑。

技能架构遵循明确的划分：Python 处理确定性任务，例如解析 Jira 字段或格式化 HTML 报告，而大型语言模型 (LLM) 技能则处理语言推理，例如解释症状、匹配供应商文档和生成诊断叙述。对于构建多技能代理的团队来说，确定性 Python 技能和 LLM 支持的推理技能之间的这种划分是影响最大的决策之一。

## 代理运行时部署

Natera 将诊断工作分为两个不同的运行时，因为自主后台分析和交互式工程协作具有根本不同的延迟和上下文要求。 swarm-agent 是为了提高吞吐量而构建的。它根据设备类型和症状选择技能，查询知识库，并生成包含主要原因假设、排名故障排除步骤和置信度标签的结构化 HTML 报告。该报告将在几分钟内传送到 Amazon Simple Storage Service (Amazon S3) 并链接到 Jira 票证。 Swarm-hive 专为深度而设计：工程师可以利用 [AgentCore 内存，Amazon Bedrock AgentCore 的一项功能](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html) 进行交互式跟进、上传图像并探索替代路径，从而在会话中保留每个工程师的对话上下文。

由于 swarm-hive 接受自由格式的工程师输入，因此提示将通过 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 路由以进行内容过滤。

## 事件驱动的 Jira 集成

SWARM 通过 [Amazon EventBridge Scheduler](https://docs.aws.amazon.com/scheduler/latest/UserGuide/what-is-scheduler.html) 和轮询 [AWS Lambda 函数](https://aws.amazon.com/lambda/) 与 Jira 集成，这是一种无服务器计算服务，运行代码以响应事件，从而避免 Webhook 配置。经过验证的票证会进入 Amazon SQS 队列以进行可靠的交付。 DynamoDB 使用票证 ID 作为分区键（具有基于生存时间 (TTL) 的到期时间）来处理重复数据删除，并存储每次运行的元数据（例如状态、成本和令牌使用情况）以供评估循环使用。这种“EventBridge-to-SQS”模式将代理运行时与票务系统的可用性分离。

以下示例说明了该模式。重复数据删除表使用具有基于 TTL 到期时间的最小架构：
```
dynamodb.create_table(
    TableName='swarm-deduplication',
    KeySchema=[
        {'AttributeName': 'ticket_id', 'KeyType': 'HASH'}
    ],
    AttributeDefinitions=[
        {'AttributeName': 'ticket_id', 'AttributeType': 'S'}
    ],
    TimeToLiveSpecification={
        'Enabled': True,
        'AttributeName': 'ttl'
    }
)
```
## 可观测性设计

具有许多交互组件的代理系统很难在没有每次调用跟踪的情况下进行调试，因此 Natera 团队在第一次生产部署之前将可观察性构建到了 SWARM 中。如果您在生产中运行代理，则每次调用跟踪是不可协商的：没有它，调试错误的诊断意味着猜测哪个技能行为不当。

在临床实验室环境中，仪器停机时间直接影响患者报告，因此跟踪、警报和审核每个代理操作的能力并不是“最好的”。这是监管和运营要求。

SWARM 的可观察性堆栈使用 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 捕获每次运行的可搜索日志，从而提供操作运行状况的清晰记录。 AWS X-Ray 跟踪从票据接收到诊断报告的每次运行，记录每次工具调用的时间和成本，以便团队可以在某些事情缓慢或昂贵时查明负责的特定技能，而不是猜测。 [Amazon Simple Notification Service](https://aws.amazon.com/sns/) 通过电子邮件发送故障警报，而 Slack 跟踪器使整个团队能够实时了解代理活动。

## 持续评估方法

SWARM 使用连续的评估循环，而不是在部署时进行一次测试，这对于处理不断变化的文档或不断发展的工作流程的系统尤其重要。对于处理的每张票证，客服人员都会提供主要原因假设、排定的故障排除步骤以及自评置信度标签。工程师记录他们发现和修复的内容，评估员将每个响应按仪器系列细分为准确、部分或错误。审查结果以确定代理表现不佳的地方，应用修复（通常通过更新知识库），并重新运行评估集以确认改进。

SWARM 的自评置信度标签显示了与实际准确性的方向关系。标记为“高置信度”的工单在 154 个评估案例中达到了 74% 的准确率，而“中等”和“低置信度”工单在 78 个和 37 个案例中分别达到了 65%。请注意，“中等”和“低”目前具有相同的准确率。 37 个案例的低置信度样本量太小，无法得出具有统计意义的结论，Natera 团队预计随着评估数据集的扩大，这两层会出现分歧。

高级别和其余级别之间的分离为工程师提供了有用的信号，告诉他们在阅读诊断报告时应该对每个诊断赋予多少权重。

## SARM 性能

Natera 团队评估了 524 个支持票证中的 SWARM，以建立性能基准。在评估集中的 524 张票证中，有 269 张收到了高、中或低置信度标签，并具有相应的经工程师验证的分辨率可供比较。其余的票证在分析时要么没有标记，要么缺乏经过验证的解决方案。

平均首次响应时间从 17.4 小时缩短至大约 8 分钟（大约快 130 倍）。这些测量结果是在 90 天的生产评估期内从 Jira 票证元数据中收集的。覆盖范围同样重要：96.2% 的故障单会获得自动第一响应，而无需工程师启动诊断过程。覆盖率以在工程师审查之前收到 SWARM 生成的诊断报告的传入工单的百分比来衡量。

## 在生产中构建代理 AI 的经验教训

SWARM 中的一些架构决策可以直接转化为构建类似系统的团队。

- 将块大小和重叠视为可调参数。正确的值取决于源文档的结构。
- 从一开始就将可追溯性构建到您的技能库中。当诊断错误时，您希望指出特定的技能，而不是调试整个系统。
- 如果您的工作负载将批处理与交互式查询混合在一起，请将它们分成不同的运行时。
