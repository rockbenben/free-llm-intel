[Amazon Textract](https://docs.aws.amazon.com/textract/latest/dg/what-is.html) 是一项完全托管的机器学习（ML）服务，能自动从扫描文档中提取文本、手写内容、版式元素和结构化数据。各组织使用 Amazon Textract 来自动化文档处理工作流，例如发票处理、抵押贷款申请受理、保险理赔处理和身份验证，从而消除人工数据录入并加速下游决策。Amazon Textract Custom Queries adapter 扩展了这一能力，让你能针对特定文档类型微调提取，提升在具有独特版式或领域专用术语的表单上的准确率。更多信息参见 [Amazon Textract Custom Queries 文档](https://docs.aws.amazon.com/textract/latest/dg/textract-using-adapters.html)。

虽然本文以 Custom Queries adapter 作为示例和 API 调用，但生命周期管理模式——如方案架构、晋级策略和安全配置——与 adapter 类型无关，同样适用于 Forms 和 Tables adapter。在本文中，你会找到基础设施模板（AWS CloudFormation 和 Terraform）、一份跨账户晋级 adapter 的成文流程、生产安全配置，以及一个用于文档路由的预分类模式。通过把 adapter ID 外置到 AWS Systems Manager Parameter Store，你可以在零停机、无需重新部署应用的情况下更新生产环境的 adapter 引用，于是一个过去需要数小时或数天协调的改动只需几秒。

把文档提取工作负载从概念验证推进到生产，需要对 adapter 生命周期管理采取结构化的方法。Amazon Textract adapter 作为模块化组件扩展了预训练的 Amazon Textract 深度学习模型，针对你的特定文档类型定制其输出。要创建一个 adapter，你上传示例文档、用查询和期望响应对其进行标注，并训练 adapter 以识别你文档的独特版式模式。这会提升针对你特定表单的提取准确率。你无需构建自定义 ML 模型。

然而，一旦越过概念验证阶段，就会出现三个核心挑战：

**Adapter 晋级：** 你如何跨 AWS 账户把训练好的 adapter 从训练环境移到生产环境？该流程目前需要提交 AWS Support 工单，且只有训练好的模型权重会转移。查询定义和训练数据不会转移。没有自动化，这会变成一个拖慢你发布节奏的人工瓶颈。

**文档路由：** Amazon Textract 支持每次 AnalyzeDocument API 调用、每页、每种特性类型只能用一个 adapter。如果你处理多个表单版本（多数企业都会如此），就需要在 Amazon Textract 调用上游设置一个路由机制，为每个文档选择合适的 adapter。

**生产安全：** 受监管行业要求静态和传输加密、网络隔离、最小权限的 AWS Identity and Access Management (IAM)、全面的审计日志以及合规认证。以下安全控制进一步强化你的 Amazon Textract 部署，并确认它对受监管工作负载已具备生产就绪。

**注意：支持的格式与 API 约束**

Amazon Textract 支持 JPEG、PNG、PDF 和 TIFF 文件格式。同步的 AnalyzeDocument API 处理单页文档（或多页文件的第一页），而异步的 StartDocumentAnalysis API 处理最多 3,000 页的多页 PDF 和 TIFF。不支持基于 XFA 的 PDF。完整配额列表参见 Amazon Textract 的[设置配额](https://docs.aws.amazon.com/textract/latest/dg/limits-document.html)。

## 方案概览

你实现一个多阶段处理流水线，把文档分类、adapter 选择和提取三者关注点分离：

图 1：Amazon Textract adapter 生命周期架构，展示文档处理流水线

- **文档摄入。** 文档到达一个使用服务端加密的 Amazon Simple Storage Service (Amazon S3) 桶。本文的示例代码为简便起见使用 S3 托管加密（AES256）。对于生产工作负载，使用 AWS Key Management Service (AWS KMS) 客户托管密钥，以完全控制密钥轮换和访问策略。
- **预分类。** 对每个传入文档（任意受支持格式），一个轻量路由步骤用 DetectDocumentText 提取原始文本，然后通过扫描文本标记（表单标题、版本标识符、字段标签）来识别文档版本。
- **Adapter 选择。** 根据分类结果，从 AWS Systems Manager Parameter Store（Parameter Store）检索正确的 adapter ID。
- **Amazon Textract 处理。** 用选定的 Custom Queries adapter 调用 AnalyzeDocument 或 StartDocumentAnalysis API。
- **结果交付。** 提取出的键值对流向下游处理系统（数据库、工作流引擎或人工审阅队列）。

对于生产部署，通过 AWS PrivateLink 路由 API 调用以实现网络隔离。IAM 强制最小权限访问。AWS CloudTrail 提供 API 审计日志，Amazon CloudWatch 处理运营监控和告警。

该架构将 adapter 管理与应用逻辑解耦。当你训练一个新 adapter 版本或将 adapter 晋级到新环境时，你只需更新 SSM 参数，无需改动应用代码或重新部署。

### 多环境拓扑

本文所述的 adapter 生命周期跨越四个环境，作为生产工作负载的推荐最佳实践。不过，多环境设置并非强制。你可以调整这一模型以匹配你组织现有的账户结构和运营成熟度。

对于较小的团队或早期实现，你可以少至在单个 AWS 账户里用两个环境（训练和生产），通过命名约定、标签和独立的 S3 桶来隔离工作负载。随着你的 adapter 组合增长，你可以扩展到专用账户。以下环境代表逻辑阶段，并非要求独立的 AWS 账户。许多组织把这些阶段映射到其现有的 AWS 账户策略（例如带有工作负载 OU 的 AWS Organizations 结构），而另一些组织通过资源级隔离在单个账户内运行多个阶段：

- **训练：** adapter 创建、训练和标注。
- **验证：** 针对多样化的测试文档集做测试、回归测试。
- **预生产：** 与下游系统做集成测试、性能基准测试。
- **生产：** 带完整安全控制的实际文档处理。

### 晋级策略

在环境间移动 adapter 有两种架构方法：

**方法 1：跨账户复制（标准）。** 你在训练账户（创建和训练 adapter 的账户）中训练 adapter，然后通过一个 AWS Support 工单把它复制到每个下游账户。每个环境维护自己的 adapter ID。对于 adapter 数量少（不到 10 个）且更新不频繁的组织，这种方法更直接。

**方法 2：集中式 hub 账户。** 你在单个专用 hub 账户中训练所有 adapter。各个环境（训练、验证、预生产、生产）通过跨账户 IAM 角色在 hub 账户中调用 Amazon Textract。这消除了反复提交支持工单和复制 adapter。对于管理大量 adapter、更新频繁的组织，这种方法降低了运营开销，尽管它引入了跨账户网络复杂性。

你可以根据需求选择任一方法。正确的选择取决于你组织的 adapter 数量、更新频率和网络约束。

### 基础设施即代码

Amazon Textract 是一项完全托管的服务，没有服务器要配置，也没有集群要设置。你可以通过 AWS Management Console、AWS CLI 或 AWS SDK 创建和管理 adapter。本文侧重 CLI 和基础设施即代码方法，以实现可重复、自动化的部署。支撑性基础设施（IAM 角色、S3 桶、KMS 密钥、SSM 参数、CloudWatch 告警）通过 CloudFormation 或 Terraform 管理。用 AWS CLI 创建 adapter。你可以把 CLI 调用封装在一个由 AWS Lambda 支撑的 CloudFormation 自定义资源里，或把它作为持续集成与持续交付（CI/CD）流水线中的一个步骤运行。

#### 支撑性基础设施（AWS CloudFormation）

这份 [CloudFormation 模板](https://github.com/aws-samples/sample-textract-adapter-lifecycle-management/blob/main/cloudformation/textract-adapter-infrastructure.yaml)为一个 Amazon Textract adapter 工作负载配置核心的支撑性基础设施。

#### 用 AWS CLI 创建 adapter

由于 adapter 无法原生通过 CloudFormation 创建，请使用 AWS CLI。它可以被封装在一个由 Lambda 支撑的 CloudFormation 自定义资源里，或作为你 CI/CD 流水线中的一步执行：

```
# Create a new adapter
aws textract create-adapter \
    --adapter-name "<your-adapter-name>" \
    --feature-types '["QUERIES"]' \
    --auto-update "ENABLED" \
    --tags '{"Environment":"<your-environment>","FormType":"<your-form type>","Version":"<your-version>"}'

# After training completes, store the adapter ID in Parameter Store
aws ssm put-parameter \
    --name "/textract/adapters/<your-adapter-name>/id" \
    --type "String" \
    --value "<adapter-id-from-create-response>" \
    --overwrite
```

*完整实现参见 [create-adapter.sh](https://github.com/aws-samples/sample-textract-adapter-lifecycle-management/blob/main/scripts/create-adapter.sh)，进一步探索[CLI 命令参考](https://docs.aws.amazon.com/cli/latest/reference/textract/create-adapter.html)。*

#### 替代方案：用 terraform_data 配合 Terraform

对于使用 Terraform 的组织，请使用 terraform_data（在 Terraform 1.4 中引入，是已弃用的 null_resource 的后继者）配合 local-exec provisioner。根据 AWS Prescriptive Guidance，把这视为临时方案，并定期检查 Amazon Textract adapter 资源是否已加入原生 Terraform provider 支持。

支撑性基础设施的 Terraform 等价物可在 [Terraform 模块](https://github.com/aws-samples/sample-textract-adapter-lifecycle-management/blob/main/terraform/main.tf)获取。或者，你可以像前面所示用 AWS CLI 创建 adapter。

### 用 CI/CD 做环境晋级

基于官方的复制 adapter 文档，跨 AWS 账户的 adapter 晋级遵循一个三步流程。理解这一流程至关重要，因为它与你晋级其他 AWS 资源的方式大不相同。

一个 adapter 学习的是某类文档的结构和字段版式，它并不学习任何单个文档的内容。一旦在开发环境用有代表性的样本训练好，同一个 adapter 就能在生产环境从该类任何新文档中准确提取数据。

例如，你用 10 份 ABC 表单样本训练一个 adapter，让它学习版式和字段。在生产中，同一个 adapter 处理 18,000 份该类型的各不相同的 ABC 表单。

#### 步骤 1：准备

- 在发起复制请求前收集以下信息：
- 源 adapter ID 和版本号。
- 源 AWS 账户 ID 和区域。
- 目标 AWS 账户 ID（必须在同一区域）。
- adapter 名称和特性类型。

**复制流程如何运作：**

- 源和目标账户必须在同一 AWS 区域。按需为每个区域提交单独的请求。
- 每个 adapter 版本都需要自己的复制请求，让你能控制晋级哪些版本。
- 只有训练好的模型权重会转移。在你的配置存储中（如 Parameter Store 或一个版本受控文件）维护查询定义和训练数据。
- 你必须在外部自行维护每个 adapter 的查询配置记录。

#### 步骤 2：通过 AWS Support 请求复制

开一个 AWS Support 工单请求复制 adapter。包含步骤 1 中的所有细节：区域、源 AWS 账户、adapter ID、adapter 版本、目标 AWS 账户和 adapter ID。

你必须已经用控制台或 API 在目标账户中创建了一个 adapter。你无需在目标账户中训练 adapter 版本，只需元数据（adapter 名称和描述）存在即可。通过 AWS Support 提交请求，并留意你的工单以获取完成通知。

#### 步骤 3：在目标账户中验证

复制完成后，用你的测试文档集跑一遍复制过来的 adapter，验证提取准确率与你的基线一致：

```
aws textract analyze-document \
    --document '{"S3Object":{"Bucket":"<your-destination-bucket>","Name":"<your-test-document>"}}' \
    --feature-types QUERIES \
    --adapters-config '{"Adapters":[{"AdapterId":"<your-adapter-id>","Version":"<your-adapter-version>","Pages":["*"]}]}' \
    --queries-config '{"Queries":[{"Text":"<your-query>","Alias":"<your-alias>","Pages":["*"]}]}'
```

#### 替代方案：集中式 hub 账户

如果你管理大量 adapter 且更新频繁，考虑集中式 hub 账户：

- 在单个专用 hub 账户中训练所有 adapter。
- 各环境（训练、验证、预生产、生产）通过跨账户 IAM 角色在 hub 账户中调用 Amazon Textract。
- 这消除了反复提交支持工单和复制 adapter 的需要。

这种方法用跨账户网络复杂性换取 adapter 管理的运营简洁。当你有一个专门负责 adapter 训练与质量的 ML 平台团队时，它尤其有效。

#### 跨账户 IAM 角色信任策略

在 hub 账户中，创建一个工作负载账户可代入（assume）以调用 Amazon Textract 的角色。以下信任策略允许指定的工作负载账户代入该角色。ExternalId 条件可防止“混淆代理（confused deputy）”攻击。在每个工作负载账户中，处理用的 Lambda 在调用 Amazon Textract API 前用 sts:AssumeRole 代入这个跨账户角色。

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": {
                "AWS": [
                    "arn:aws:iam::<workload-account-id-1>:root",
                    "arn:aws:iam::<workload-account-id-2>:root"
                ]
            },
            "Action": "sts:AssumeRole",
            "Condition": {
                "StringEquals": {
                    "sts:ExternalId": "textract-adapter-access"
                }
            }
        }
    ]
}
```

为这个角色附加一个限定到所需 Amazon Textract 动作的权限策略：

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "TextractDocumentProcessing",
            "Effect": "Allow",
            "Action": [
                "textract:AnalyzeDocument",
                "textract:StartDocumentAnalysis",
                "textract:GetDocumentAnalysis",
                "textract:DetectDocumentText"
            ],
            "Resource": "*"
        }
    ]
}
```

截至目前，这些动作不支持资源级权限（参见[Amazon Textract 的动作、资源和条件键](https://docs.aws.amazon.com/service-authorization/latest/reference/list_textract.html)），因此 Resource 必须设为 “*”。考虑把策略限定到仅必要的动作。

#### 成本影响

采用集中式 hub 方法时，所有 Amazon Textract API 费用都记在 hub 账户。在评估这一方法时考虑以下几点：

- **账单合并：** 所有 Amazon Textract 用量都记到单个账户，这简化了成本跟踪，但需要内部的费用分摊机制（如 AWS 成本分配标签）把成本归属到各个工作负载团队。
- **定价模型：** Amazon Textract 按处理的页计费，带 adapter 的 Custom Queries 比基本文本检测收费更高。把量合并到一个账户并不能解锁批量折扣，因为 Amazon Textract 采用固定的按页定价。
- **数据传输：** 同一区域内的跨账户 S3 访问不产生数据传输费。但如果工作负载账户把文档传入 hub 账户的 S3 桶，要把 S3 PUT/GET 请求成本算进去。
- **与跨账户复制的对比：** 采用复制方法时，每个账户独立为它自己的 Amazon Textract 用量付费，这为每个团队提供了天然的成本隔离，但会重复 adapter 管理工作。

**服务配额考量：** 在采用这一集中式 hub 方法之前，评估你所有工作负载账户的每秒事务数（TPS）总需求。集中 API 调用意味着所有环境竞争单个账户的 [Amazon Textract 配额](https://docs.aws.amazon.com/general/latest/gr/textract.html)。通过 [Service Quotas 控制台](https://console.aws.amazon.com/servicequotas/)主动申请配额提升，并注意“Maximum number of adapters”和“Maximum AdapterVersions created per month”配额是集体适用于 hub 账户的（这些是可调整的默认配额，请在 Service Quotas 控制台查看你所在区域的当前值）。如果你的组合峰值吞吐即使提升后仍超过单个账户所能承受的，考虑采用分布式（跨账户复制）方法以获得故障隔离。

当你有不到 10 种 adapter 类型、可预测的吞吐和一个平台团队时，选择集中式 hub。当你有高突发工作负载、严格的故障隔离要求，或跨团队超过 10 种 adapter 类型时，选择分布式（复制）。

### 预分类与 API 调用模式

本节说明如何把每个文档路由到正确的 adapter，以及如何调用 Amazon Textract 进行同步和异步处理。

#### 文档路由

Amazon Textract 每页每种特性类型应用一个 adapter，且一页只能应用一个 adapter。因为同步的 AnalyzeDocument API 处理单页，它每次调用最多用一个 adapter。有两种方式处理多个表单版本。要路由大量表单版本各异的独立文档，使用下面的预分类模式为每个文档选择一个 adapter。这对同步和异步 API 都适用。要在单个多页文档内应用不同的 adapter，使用异步的 StartDocumentAnalysis API，并用 AdaptersConfig 中的 Pages 参数限定每个 adapter 的作用范围。

#### 基于文本的分类

解决单 adapter 约束的一种方法是轻量级的基于文本的分类步骤：它扫描文档内容以寻找版本特定的标记（表单标题、版本标识符、修订日期或有辨识度的字段标签），并路由到合适的 adapter。路由逻辑把文档文本与可配置的表单标记做匹配，并从 Parameter Store 检索对应的 adapter ID。完整实现参见[这个示例](https://github.com/aws-samples/sample-textract-adapter-lifecycle-management/blob/main/src/classify_and_route.py)。

其他方法包括使用 Amazon Comprehend 做文档分类、维护一张基于文档元数据的查找表，或用文档的 S3 键前缀作为路由信号。正确的选择取决于你的文档多样性和分类准确率要求。

在路由逻辑选定正确的 adapter ID 后，根据文档大小使用同步或异步模式调用 Amazon Textract。

#### 用 adapter 调用 Amazon Textract

根据文档大小和页数选择同步或异步 API。

##### 同步

对于单页文档（最大 10 MB），使用同步的 AnalyzeDocument API：

```
aws textract analyze-document \
    --document '{"S3Object":{"Bucket":"<your-bucket>","Name":"<your-document>"}}' \
    --feature-types QUERIES \
    --adapters-config '{"Adapters":[{"AdapterId":"<your-adapter-id>","Version":"1","Pages":["*"]}]}' \
    --queries-config '{"Queries":[{"Text":"<your-query>","Alias":"<your-alias>","Pages":["*"]}]}'
```

##### 异步

对于多页文档，或超过 10 MB 同步限制的文件，使用异步的 StartDocumentAnalysis API。

这遵循相同的 adapter 和查询配置，但额外增加了用于 S3 结果存储的 OutputConfig，以及可选的、通过 Amazon Simple Notification Service (Amazon SNS) 发送完成通知的 NotificationChannel。完整实现参见 [async_analyze.py](https://github.com/aws-samples/sample-textract-adapter-lifecycle-management/blob/main/src/async_analyze.py)。

### Adapter 版本管理实践

理解何时创建新 adapter、何时为现有 adapter 创建新版本，对于维护一个干净、可管理的 adapter 清单至关重要。使用 Amazon Textract，你可以同时保留一个 adapter 的多个版本以供开发流水线使用，从而可以回滚并运行并行测试。

#### 何时创建新 adapter

- 处理一种**不同的文档类型**或表单家族（例如从保险理赔切换到贷款申请）
- 使用一种**不同的特性类型**（Queries、Forms 或 Tables）
- 开始一个全新的**用例**。
- 在根本不同的方案之间运行 **A/B 测试**。

#### 何时为现有 adapter 创建新版本

- 为同一文档类型添加、移除或改写查询。
- 用额外的示例文档扩充训练数据。
- 修正生产监控中发现的标注错误。
- 改进特定文档变体的边界情况处理。

#### 推荐的版本管理实践

- 训练最低量。每个 adapter 至少 5 个训练文档和 5 个测试文档。
- 最大容量。最多 2,500 页训练页和 1,000 页测试页。
- 样本多样性。确认文档代表了你用例的方方面面。
- 自动更新。在存在回归测试之前，考虑在生产中禁用。
- 活跃版本。维护多个版本（生产 + 回滚 + 预生产）。
- 查询文档。在外部记录查询。Amazon Textract 不会把查询文本作为可离散检索的产物存储。

**重要：** 当你在账户间复制一个 adapter 时，只有训练好的模型权重会转移。查询定义和训练数据不会转移。维护一个单独的配置存储（如 Parameter Store 或一个版本受控配置文件），把每个 adapter 映射到它完整的查询集。

## 安全最佳实践

生产文档处理工作负载常常处理敏感数据，包括可识别个人身份信息（PII）、财务记录受保护的 health 信息（PHI）。Amazon Textract 支持多层安全控制，你应为这些工作负载以“纵深防御”方式实施它们。以下小节详述需要处理的关键安全领域。

### 用 VPC 端点做网络隔离

为 Amazon Textract 部署一个接口型[专有网络 (VPC) 端点](https://docs.aws.amazon.com/textract/latest/dg/vpc-interface-endpoints.html)（AWS PrivateLink），使 API 流量绝不经过公共互联网。有了 VPC 端点，你 VPC 中的实例通过 Amazon 网络上的私有 IP 地址与 Amazon Textract API 通信，消除了对互联网网关、NAT 设备或 VPN 连接的需要。配置 VPC 端点策略以限制哪些 IAM 主体可以通过该端点调用 Amazon Textract 动作，并把安全组应用到端点网络接口以在网络层控制入站流量。实现细节参见 [Amazon Textract 和接口 VPC 端点](https://docs.aws.amazon.com/textract/latest/dg/vpc-interface-endpoints.html)。

### 静态与传输加密

与 Amazon Textract 的所有通信都使用 TLS 1.2+ 的传输加密。对于静态加密，把 S3 输入和输出桶配置为使用客户托管的 AWS KMS 密钥进行服务端加密（SSE-KMS）。这让你完全控制密钥轮换、访问策略和审计轨迹。当使用带 OutputConfig 的异步 API 时，写入你 S3 桶的结果继承桶的默认加密设置。确保 Amazon Textract 使用的 IAM 角色对输入桶的 KMS 密钥具有 kms:Decrypt 权限，对输出桶的 KMS 密钥具有 kms:Encrypt 权限。更多信息参见 [Amazon Textract 中的加密](https://docs.aws.amazon.com/textract/latest/dg/encryption.html)。

### IAM 最小权限访问

应用最小权限的 IAM 策略，把权限限定到最低必要的动作和资源。对于文档处理，限定到具体动作（textract:AnalyzeDocument、textract:StartDocumentAnalysis、textract:GetDocumentAnalysis）和具体的 S3 桶 ARN，而不要使用通配符资源。在你的 S3 桶策略中使用 aws:CalledViaFirst 条件键，把对象访问限制为源自 Amazon Textract 的请求，为防止直接桶访问提供纵深防御。对于跨账户 adapter 场景，使用显式的资源型策略和 external ID 以防止混淆代理攻击。示例策略参见 [Amazon Textract 基于身份的策略示例](https://docs.aws.amazon.com/textract/latest/dg/security_iam_id-based-policy-examples.html)。

### 日志、监控与告警

为所有 Amazon Textract API 调用启用 AWS CloudTrail 日志，以维护谁在何时访问了哪些文档的审计轨迹。配置 Amazon CloudWatch 指标和告警来监控 API 限流（ThrottledCount）、错误率和延迟。对于生产工作负载，设置 CloudWatch Logs 以捕获详细的处理结果，并为异常模式创建告警，例如失败的提取请求突然激增——这可能表明 adapter 配置错误或有未授权的访问尝试。考虑使用 AWS Organizations 把日志聚合到一个集中安全账户，以获得跨账户可见性。

### 数据隐私与 ML 退出

默认情况下，AWS 可能使用 Amazon Textract 处理的内容来改进和开发该服务。对于敏感的文档工作负载（PII、PHI、财务数据），通过在组织、组织单元（OU）或账户级别用 AWS Organizations 附加一个 AI 服务退出策略来选择退出这一使用。当你选择退出时，AWS 不会为你的服务改进而存储或使用你的内容，同时该服务对你的工作负载仍以完全相同的方式运行。此外，同步处理的文档在 API 响应返回后不再留存。对于异步处理，结果在你指定的 S3 桶中、在你的加密控制下存储。设置说明参见 [AI 服务退出策略](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_ai-opt-out.html)。

### 合规认证

Amazon Textract 可用于受 HIPAA、PCI DSS、FedRAMP High、SOC 1/2/3、ISO 27001/27017/27018 和 HITRUST CSF 合规框架约束的工作负载。在 [AWS 范围内服务](https://aws.amazon.com/compliance/services-in-scope/)页面核实当前的认证状态，并确认你的实现遵循责任共担模型——AWS 保障底层基础设施安全，你保障自己的配置、访问控制和数据处理实践。

## 清理

为避免持续产生费用，如果你跟随本文时创建了以下资源，请删除它们：

- 删除 Amazon Textract adapter：  `aws textract delete-adapter --adapter-id <your-adapter-id>`
- 删除 SSM 参数：  `aws ssm delete-parameter --name /textract/adapters/<your-adapter-name>/id`
- 删除 CloudFormation 栈（这会移除 IAM 角色、S3 桶以及所有相关资源）：  `aws s3 rm s3://<your-source-bucket> --recursive aws s3 rm s3://<your-output-bucket> --recursive aws cloudformation delete-stack --stack-name <your-stack-name>`

如果你用 Terraform 部署，请在 `terraform/` 目录运行 `terraform destroy`。

## 结论

在本文中，我们展示了如何通过应对企业在越过概念验证后都会遇到的三个关键挑战，把 Amazon Textract Custom Queries adapter 投产到生产工作负载。

**支撑性基础设施与 adapter 配置。** 用 CloudFormation 或 Terraform 配置 IAM 角色、S3 桶和 KMS 密钥，并用 CLI 命令或 terraform_data 创建 adapter。Parameter Store 把 adapter ID 与应用代码解耦，因此你可以在零停机下更新引用。

**多环境晋级。** 如果你管理大量 adapter，一个集中式 hub 账户通过让各环境从单个账户调用 adapter，彻底消除跨账户复制——这是跨账户复制流程的一个替代方案。

**生产安全加固。** 对于受监管行业，考虑实施 VPC PrivateLink 做网络隔离、带 OutputConfig 的客户托管 AWS KMS 加密以控制数据静态、最小权限 IAM 策略，以及 CloudTrail 做全面审计日志，以支持你的 Amazon Textract 工作负载。

### 关键要点

- Amazon Textract adapter 需要一个路由机制，因为每次 API 调用每页只能应用一个 adapter。
- 账户间的 adapter 复制只转移训练好的模型权重。要单独维护查询配置。
- 使用异步 API 时，始终指定 OutputConfig 以控制结果存储在哪里。
- Parameter Store 把 adapter ID 与应用代码解耦，因此你可以在零停机下更新 adapter 版本。
- 对于生产工作负载，考虑添加 AWS KMS 加密、用于网络隔离的 VPC 端点，以及用于审计日志的 CloudTrail。
- 在 S3 桶策略上使用 aws:CalledViaFirst 条件键做纵深防御。
- 对于敏感文档工作负载，通过 AWS Organizations 策略选择退出 ML 训练。
