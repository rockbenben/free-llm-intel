# 构建对话式数据助手，第 1 部分：使用 Amazon Bedrock Agents 实现 Text-to-SQL

如果你能用一分钟的对话取代数小时的数据分析，会怎样？大语言模型能够改变我们弥合业务问题与可执行数据洞察之间差距的方式。对大多数组织来说，这道差距依然顽固地宽阔：业务团队陷在无休止的循环里——解读指标定义、寻找正确的数据源，再手工编写每一条 SQL 查询。简单的业务问题可能演变成耗时数日的折磨，分析团队被例行请求淹没，而不是专注于战略性举措。

Amazon 的 Worldwide Returns & ReCommerce（WWRR）组织在大规模上遭遇了这一挑战。用户每年要针对我们 PB 级的 [Amazon Redshift](https://aws.amazon.com/redshift/) 数据仓库执行超过 450,000 条 SQL 查询，我们的商业智能与分析团队因此成为关键瓶颈。我们需要一个自助式解决方案，能够应对企业级的复杂性：数千张相互关联的表、专有的业务术语，以及在不同业务域之间各不相同且不断演进的指标定义，还有严格的治理要求。

本系列文章介绍 WWRR 如何开发 Returns & ReCommerce Data Assist（RRDA）——一个由生成式 AI 驱动的对话式界面，它改变了组织各层级获取数据的方式。RRDA 让 4000 多名非技术用户能够识别正确的指标、构建经过校验的 SQL，并生成复杂的可视化——全部通过自然对话完成。结果是：查询解决速度提升 90%（从数小时缩短到数分钟），且完全不依赖商业智能团队。

在第 1 部分中，我们聚焦于使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 构建 Text-to-SQL 解决方案，这是一个用于构建生成式 AI 应用的托管服务。具体而言，我们演示 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 的能力。[第 2 部分](https://aws.amazon.com/blogs/machine-learning/build-a-conversational-data-assistant-part-2-embedding-generative-business-intelligence-with-amazon-q-in-quicksight/) 说明我们如何扩展该解决方案，借助 [AWS Quick Sight](https://aws.amazon.com/quicksight/q/) 提供业务洞察，这是一个能够以自动生成的可视化来回答问题的商业智能助手。

## Text-to-SQL 的基础原理

[Text-to-SQL 系统](https://aws.amazon.com/blogs/machine-learning/generating-value-from-enterprise-data-best-practices-for-text2sql-and-generative-ai)通过多步流程把自然语言问题转换为数据库查询。从根本上说，这类系统必须弥合人类交流与结构化查询语言之间的差距，具体方式是：

- 理解用户意图，并从自然语言中抽取关键实体
- 将这些实体与数据库 schema 的组成部分（表、列、关系）匹配
- 生成语法正确、能够准确表达用户问题的 SQL

企业级实现还会遇到额外的挑战，包括术语歧义、复杂的 schema 关系、领域特定的业务指标，以及实时查询校验。下面我们来看 RRDA 如何落实这些原则。

## RRDA 架构概览

RRDA 通过 [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 建立 WebSocket 连接，把用户连接到 [AWS Lambda](https://aws.amazon.com/lambda/)，实现实时的无服务器处理。下图展示了 RRDA 的整体架构，重点说明用户消息如何在系统中流转，以生成 SQL 查询或指标可视化。

*这张架构概览图展示了系统的两条处理路径：上方路径通过 Amazon Bedrock Agents 处理 SQL 生成，下方路径则通过 AWS Quick Sight 管理可视化请求。*

在架构图中，用户的输入会先被归类为一个 intent，然后路由到最合适的处理路径。该架构包含两条主要的处理路径：

- 对于对话式体验（`INFO`、`QUERY` 和 `UNKNOWN` 这几类 intent），系统会先检查语义缓存中是否已有经过验证的回答，然后再路由到 Amazon Bedrock agent，由它在多个 [action group](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-action-create.html) 之间编排。这些 action group 是定义 agent 可以协助执行的具体操作的组件：在带域过滤的条件下检索指标定义，从 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 获取 SQL 表元数据与 schema，生成 SQL 代码并校验查询语法
- 对于可视化请求（`SHOW_METRIC` intent），系统会检索相关的 [AWS Quick Sight Q topics](https://docs.aws.amazon.com/quicksight/latest/user/quicksight-q-topics.html)，对问题做适当改写，然后使用 AWS Quick Sight 展示可视化。

就本文第 1 部分而言，我们聚焦于那个能够回答指标相关问题并生成经过校验的 SQL 的 Amazon Bedrock agent。[第 2 部分](https://aws.amazon.com/blogs/machine-learning/build-a-conversational-data-assistant-part-2-embedding-generative-business-intelligence-with-amazon-q-in-quicksight/)将介绍使用 AWS Quick Sight 的指标可视化路径。

## Intent 与业务域分类

RRDA 依据用户 intent 和相关业务域对进入的用户消息进行分类。Intent 分类与域分类会在并行线程中同时进行，以尽量降低延迟。该方案把查询划分为四种不同的 intent，并据此把请求路由到我们的 agent 或 AWS Quick Sight：

- **INFO** – 用于关于指标、定义、表 schema 等的信息类问题（例如，“解释一下 resolution index 这个指标”）
- **QUERY** – 用于生成 SQL 查询（例如，“为过去 6 个月的美国 resolution index 写一条查询”）
- **SHOW_METRIC** – 用于请求从 AWS Quick Sight 展示可视化（例如，“给我看过去 6 个月美国的 resolution index”）
- **UNKNOWN** – 用于不符合已知模式的请求

Intent 分类通过 [Amazon Bedrock Converse API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html) 使用一个轻量级基础模型（FM）。系统使用一段专门的 prompt，其中包含每种 intent 类型的大量示例，并分析当前用户消息和最近的对话历史，以确定最合适的类别。系统使用 [structured outputs](https://docs.aws.amazon.com/nova/latest/userguide/prompting-structured-output.html) 把模型的响应约束为四种预定义 intent 之一。

下面这张截图是一个 `QUERY` intent 消息的示例，用户在其中请求针对 resolution index 指标的 SQL 查询：“给我一条 RP resolution index 在 2025 年 5 月、美国商城的查询。”

![RRDA 聊天界面截图，蓝色消息气泡中显示用户查询 “Give me a query for RP Resolution Index for June 2025 and US marketplace”。系统返回一段指标定义 “Resolution Index % = Items resolved within 7 business days / Total returned items”，紧接着是一条使用 SELECT、COUNT 和 CASE 语句从 wwrr_metrics.a_rp_resolution 表计算 resolution index 的格式化 SQL 查询。响应中带有一个绿色的 “Validated SQL Syntax” 徽标，最后是一个标题为 “Get related insights from Amazon Q in QuickSight” 的建议区，其中的可点击链接询问 “What is the Resolution Index for June 2025 in the US marketplace?”。界面底部显示点赞、点踩和刷新图标。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/07/image-1-35.png)

在这个示例中，系统识别出用户消息中的“RP”，并正确地将它映射到 Returns Processing 域，从而只能访问那些专属适用于 Returns Processing 域中 resolution index 指标定义的特定表和指标定义。

业务域分类至关重要，因为企业里同一个指标在不同项目、团队或部门之间的计算方式可能不同。我们的域分类系统使用字符串比较，对一个预定义字典做模式匹配，该字典把各种变体、缩写和别名映射到规范域名称（例如，用户消息中的 `"rp"`、`"returns-processing"` 和 `"return-process"` 子串会映射到 Returns Processing 域；而 `"promos"` 映射到 Promotions 域）。系统会对用户消息分词，并识别整词或短语匹配，而不是部分字符串匹配，以帮助避免误报。这一域上下文会跨对话轮次持续存在，从而实现有针对性的知识检索和域特定处理，提升我们 agent 的回答准确率。

## Amazon Bedrock agent 概览

RRDA 架构的核心是运行在 Amazon Bedrock 上、由 Anthropic 的 Claude 3.5 Haiku 驱动的 Amazon Bedrock agent。这个 agent 充当智能决策者，在下面这些 action group 之间编排并解释结果：

- **RetrieveFromKnowledgeBase** – 使用元数据过滤在 WWRR 指标字典中搜索域特定的指标定义、计算逻辑和数据源
- **FetchTableSchema** – 从 DynamoDB 获取表信息，为 agent 提供最新的表 schema、列定义、类别列的维度，以及该表的示例查询
- **GenerateSQLQuery** – 把复杂的 SQL 生成任务委派给 Anthropic 的 Claude 3.7 Sonnet，同时把检索到的知识库信息、表 schema 和用户需求传递过去

下面的时序图展示了 agent 如何依据 intent 在不同的 action group 之间编排。

*时序图展示了 RRDA 的混合模型架构：Anthropic 的 Claude 3.5 Haiku 编排 agent 动作以实现快速检索与交互，同时把复杂的 SQL 生成任务委派给 Anthropic 的 Claude 3.7 Sonnet。*

该图展示了我们如何采用混合模型架构，在性能与适应性之间取得优化：Anthropic 的 Claude 3.5 Haiku 负责编排 agent，实现快速的信息检索和交互式响应；同时把复杂的 SQL 生成委派给在代码生成任务上表现出色的 Anthropic 的 Claude 3.7 Sonnet。这种均衡的做法既带来了响应灵敏的交互，也保证了高质量的输出。

## 带业务域过滤的指标字典

RRDA 的指标字典是 WWRR 各业务域中 1000 多个指标的权威来源。每个指标都编码为一个 JSON 对象，包含元数据（业务域、类别、名称、定义）和指标用法细节（SQL 表达式、源数据集、过滤条件、粒度）。这种结构把业务术语直接映射到技术实现，从而实现准确的 SQL 转换。

每个指标对象都以带域元数据标签的单个 [chunk](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html) 形式导入我们的指标知识库。当用户问“解释一下 RP resolution index 指标”时，RRDA 会检测出 Returns Processing 是目标域，并调用 `RetrieveFromKnowledgeBase` action group。该 action group 通过[对向量搜索配置施加域过滤](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-knowledge-bases-now-supports-metadata-filtering-to-improve-retrieval-accuracy/)，只检索该特定业务域内的指标。

对于域不明确的查询，该 action group 会识别出可能相关的域，并指示 agent [请用户确认](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-enable-user-input.html)正确的那一个。下面这张截图是一个用户交互示例，其中域无法被分类。

*RRDA 演示域分类与知识库检索。系统识别出多个包含“resolution index”指标的域，请求澄清，然后为选定的 Returns Processing 域给出详细的指标定义。*

系统的回复列出了一批包含“resolution index”指标的候选相关域。检测到某个域之后，后续搜索会用确认过的域过滤进一步收窄。这种有针对性的检索确保 RRDA 只访问与该域相称的指标定义，在提升回答准确率的同时，通过限制搜索空间来降低延迟。

## 表 schema 检索

agent 调用 `FetchTableSchema` action group 以低延迟获取 SQL 表元数据。当 agent 需要理解一张表的结构时，该 action 会从 DynamoDB 表元数据存储中检索列定义、示例查询和使用说明。下面这张截图展示了一次用户询问某张表细节的交互。

*RRDA 为 RP aggregate 数据集提供详细的类别维度值。agent 从表元数据中检索并归类状态分桶，帮助用户理解可用的过滤选项，并给出实用的使用建议。*

agent 回复了具体的类别维度值（例如“In Warehouse, Quality Check Complete”），用户可以据此过滤。这些不同的取值是重要的上下文，能帮助 agent 生成与业务术语和数据库结构相一致的合法 SQL。不过，这些不同取值并不能直接从表 schema 中获得，而是通过下图中的工作流收集的。

我们创建了一个 [AWS Step Functions](https://aws.amazon.com/step-functions/) 工作流，用丰富的元数据（包括表 schema、维度和示例查询）来充实 DynamoDB 表元数据存储。

用于自动化表元数据充实、向 DynamoDB 元数据存储写入 schema 信息、类别维度和用法示例的 AWS Step Functions 工作流。

该工作流编排了元数据刷新流程，每天运行以保持信息最新。工作流会从 [AWS Glue Data Catalog](https://docs.aws.amazon.com/glue/latest/dg/catalog-and-crawler.html) 同步 schema，使用 Amazon Bedrock 的 FM 识别值得抽取的类别维度，通过运行有针对性的 Redshift 查询（例如 `SELECT DISTINCT column_name FROM table_name ORDER BY COUNT(*) DESC LIMIT K;`）填充前 K 个不同取值，并从 Redshift 查询日志中纳入示例用法模式。这条自动化 pipeline 减少了人工元数据维护，同时确保表元数据存储能够反映当前的数据结构、业务术语和用法模式。

## SQL 生成与校验

我们方案的核心在于 RRDA 究竟如何创建并校验 SQL 查询。我们没有采用一步生成 SQL 的做法，而是利用 [Amazon Bedrock Agents 的 return of control 能力](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-returncontrol.html)设计了一套更聪明的方案，它就像我们系统不同部分之间的一场对话。当用户提出诸如“写一条查询，找出上个季度美国电子产品的 resolution index”这样的问题时，整个过程分几步展开：

- 我们的 agent 查询自己的知识库，确定正确的指标以及这些数据存放在哪里。如果有任何不清楚的地方，它会向用户追问，例如“你想查的是美国商城中电子产品的 resolution index，还是北美区域的？”以确认自己准确理解了需求。
- 当 agent 知道该用哪个数据源后，它会获取那张表的详细 schema——列名、数据类型、维度和示例查询——从而了解数据是如何组织的。
- `GenerateSQLQuery` action group 使用 Amazon Bedrock Converse API，以一段专门用于 SQL 生成的 prompt 调用 Anthropic 的 Claude 3.7 Sonnet。响应会返回 SQL 代码并附带解释。
- 我们的系统通过 return of control 拦截 action group 的响应。[它会提取生成的 SQL，并用 EXPLAIN 命令对 Redshift 数据库进行校验，EXPLAIN 只检查语法错误而不会真正执行查询](https://aws.amazon.com/blogs/machine-learning/build-a-robust-text-to-sql-solution-generating-complex-queries-self-correcting-and-querying-diverse-data-sources/)。如果系统发现语法问题，就会自动把该查询连同具体的错误信息发回 Amazon Bedrock 的 FM，让它在继续之前自行修正。
- 在确认查询合法之后，agent 会收到它，并用通俗的语言向用户呈现，同时给出清晰的解释。agent 会说明这条查询做了什么、应用了哪些过滤条件、结果应当如何解读——并且能够按需回答后续问题。

这种做法带来了即时的业务价值：用户拿到的是语法正确、首次执行即可运行的查询，无需具备 SQL 专业技能，也无需了解数据库 schema。通过使用 Redshift 的 EXPLAIN 命令校验查询——而不是执行它们——RRDA 在保持安全边界的同时确保了可靠性。用户通过现有工具、以正确的身份认证来执行经过校验的查询，从而在消除手工开发 SQL 反复试错循环的同时，保留了企业的访问控制。

## 最佳实践

基于我们构建 RRDA 的经验，以下是实现 agentic Text-to-SQL 解决方案的最佳实践：

- **实现域感知的上下文** – 使用业务域分类来检索域特定的指标定义，确保 SQL 生成尊重各业务单元之间指标计算方式的差异。
- **采用混合模型架构** – 用更小、更快的模型负责编排和用户交互，把更强的模型保留给复杂的 SQL 生成任务，以平衡性能与准确性。
- **只校验、不执行** – 使用 Redshift EXPLAIN 这类轻量命令实现实时 SQL 校验，在不执行查询的前提下捕获语法问题。把查询生成与执行分离，可以在保留既有认证边界的同时减少错误。
- **自动化元数据维护** – 构建无需人工介入即可持续刷新元数据（例如 schema 信息和维度）的 pipeline，确保系统引用的是最新信息。
- **为透明度和用户参与度而设计** – 通过公开 agent 的推理过程、中间步骤，并对生成的 SQL 给出清晰的解释来建立信任。为响应时间在 15–60 秒的多步流程实现实时状态指示器和进度更新。透明的处理反馈能在 SQL 生成和知识检索这类复杂操作中维持用户参与度并建立信心。

## 结论

Returns & ReCommerce Data Assist 通过 Amazon Bedrock 把自然语言转换为经过校验的 SQL 查询，从而改变了 WWRR 的数据访问方式。借助我们这种域感知并带实时校验的做法，业务用户无需 SQL 专业技能就能获取准确数据，极大缩短了从问题到洞察的路径。这项 Text-to-SQL 能力只是第一步——[第 2 部分](https://aws.amazon.com/blogs/machine-learning/build-a-conversational-data-assistant-part-2-embedding-generative-business-intelligence-with-amazon-q-in-quicksight/)将探索如何使用 AWS Quick Sight 以自动化可视化扩展该解决方案。
