# 停止猜测 Amazon SageMaker AI 上 TTS 的自动扩缩容目标

流量高峰袭来，你自托管的文本转语音（TTS）端点开始排起请求队列。延迟在最需要收听的人最多的时候，越过你的服务等级目标（SLO）持续攀升。该端点背后的自动扩缩容策略本应防止这种情况，但它赖以扩缩容的目标值只是一个猜测，而这类猜测会静默失败，直到真实流量证明它是错的。

这个数字一旦错了，代价会以两种方式之一付出，而这两种方式都不会触发告警。猜得太保守，集群里运行的 GPU 实例大部分时间都在闲置。这笔成本会落在每一张账单上，却永远不会出现在事故报告里。猜得太激进，集群就背上了一个没人看得见的风险：每个实例承载的并发请求数超出了它在延迟承诺内所能服务的数量。一切看起来都正常，直到真实流量高峰把排队时间推过 SLO。而这恰恰发生在收听人数最多的时候。这就是那处隐藏的缺口。一个在控制台上看起来没问题的策略，可能已经在辜负它本该服务的人。

在本文中，我们将 [Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M)（一个 8200 万参数的 TTS 模型）作为自定义容器部署到 Amazon SageMaker AI 实时端点上。[AWS Cloud Development Kit (AWS CDK)](https://aws.amazon.com/cdk/) 堆栈负责部署。我们用针对在线端点所做的两项测量取代猜测。`Q_max` 是一个实例在不突破 SLO 的前提下所能维持的最高并发数，`T_total` 是一次扩容端到端所需的时间。我们通过算术运算，从这两个数字推导出扩容阈值、缩容阈值以及两个冷却时间。本文中的每个数字都来自本文所引 aws-samples 仓库的一次实际部署与测量运行。

## 为什么默认自动扩缩容指标不适用于 TTS

关于 Amazon SageMaker AI 自动扩缩容目标的大多数公开指南，针对的都是短的同步请求/响应调用，或大语言模型（LLM）推理服务，其自然指标是每秒生成的 token 数。TTS 语音合成两种模式都不符合：单个请求会让连接保持打开数秒，而且没有可供挂接指标的 token 生成循环。Kokoro-82M 是非自回归的，它是 StyleTTS2 的衍生模型，采用 ISTFTNet 解码器，以对抗方式训练，而非通过自回归的下一 token 预测或迭代去噪训练。它通过一次时长对齐的前向计算就产出一整句话音。根本不存在可以插桩统计每 token 指标的生成循环。决定一个 TTS 实例是否过载的因素其实比听起来简单：此刻有多少请求正在该实例上排队和执行。

部署的策略基于 `ConcurrentRequestsPerModel` 扩缩容，这是 Amazon SageMaker AI 自身发布的原生指标，而不是本项目自己的容器代码必须上报的指标。基于 Amazon SageMaker AI 发布的指标扩缩容，消除了一整类故障：自定义指标配置在纸面上看起来正确，但实际上没有任何东西在上报数据。

`ConcurrentRequestsPerModel` 发布的是 10 秒窗口内的 Maximum 统计值，它与压测客户端直接测量的平均在飞请求数不是同一个量。工具链考虑到了这一点。在并发阶梯的每一级，它都在相同负载下同时测量这两个量，并记录两者之间的比值。随后，它用该比值把客户端测得的阈值换算成 Amazon CloudWatch 单位，再写入可部署配置。对于本文中的 Kokoro-82M 运行，测得的比值在每一级都恰好是 1.0，因此客户端测得与 Amazon CloudWatch 上报的阈值直接一致。

## 方案概览

本方案将 Kokoro-82M 以自定义容器部署到 Amazon SageMaker AI 实时端点上，然后用在那个在线端点上所做的两项测量来取代猜测出来的自动扩缩容目标：`Q_max`，即一个实例在 SLO 内可服务的并发上限，以及 `T_total`，即一次真实扩容所需的时间。一个合成请求流经四层：客户端、Amazon SageMaker AI 端点、端点后面 GPU 实例上的自定义容器，以及容器内部的 Kokoro-82M 模型。

![Diagram showing a client connecting to an Amazon SageMaker AI real-time endpoint, which contains a custom GPU container exposing two routes, POST /invocations for response streaming and WS /invocations-bidirectional-stream for bidirectional streaming, both feeding into a KPipeline running Kokoro-82M with lang_code=“a”](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/19/ML-21705-1.png)

图 1：Kokoro-82M 的请求路径，从客户端经 Amazon SageMaker AI 端点和自定义容器到达模型

该容器支持两种传输方式：响应流式传输（`InvokeEndpointWithResponseStream`），在合成的同时把音频流式返回，使播放能在整句话音完成之前就开始；以及双向流式传输（`InvokeEndpointWithBidirectionalStream`），保持一个长连接会话以承载多条消息。

把 Kokoro-82M 跑在自定义容器里、而不是托管推理工具包后面，正是本文后续内容得以成立的前提。由你掌控的容器可以强制执行自己的准入限制，并暴露 Amazon SageMaker AI 已经发布的那个精确并发信号，而不是把借来的指标硬套在一个并非为其设计的工作负载上。部署该端点的 AWS CDK 堆栈只有在模型存在一个真实、经过测量的 `plan` 之后才会挂载自动扩缩容资源，因此猜测出来的配置永远无法悄悄进入生产环境。本文余下的内容就是这次测量。

## 先决条件

要跟随本演练，你需要：

- 一个 AWS 账户，并具备创建 AWS Identity and Access Management (IAM) 角色、Amazon Simple Storage Service (Amazon S3) 存储桶、Amazon Elastic Container Registry (Amazon ECR) 仓库和 Amazon SageMaker AI 资源的权限。注意：示例容器固定了一个存在已知安全公告（`PYSEC-2026-2286`，已在 torch 2.10.0 中修复）的早期 PyTorch 版本。在任何非概念验证用途之前，请审查并升级该固定版本。
- [AWS CDK v2](https://docs.aws.amazon.com/cdk/v2/guide/getting_started.html)，已在你的目标账户和区域中安装并完成引导（bootstrap）。
- Python 3.11 或更高版本、[uv](https://docs.astral.sh/uv/) 以及用于构建容器镜像的 Docker。
- 一个 `ml.g5.xlarge` 服务配额，在运行本文的扩容测量之前，至少比你基线多出一个空闲槽位。
- 本文所引 [GitHub 仓库](https://github.com/aws-samples/sample-kokoro-tts-for-ai-agents)中的部署代码。

## 演练

到本演练结束时，你将拥有一个针对 Kokoro-82M 的、在线的 Amazon SageMaker AI 自动扩缩容策略，它完全来自针对你自己端点所做的两项测量，而不是来自猜测。

### 部署端点堆栈

端点通过三个 AWS CDK 堆栈按顺序部署：`SpeechFoundationStack` 创建 IAM 角色和用于缓存模型权重的 Amazon S3 存储桶，`SpeechModelCacheStack` 一次性把模型的 Hugging Face 权重同步到该存储桶，`SpeechEndpointStack` 构建容器镜像、推送到 Amazon ECR，并创建 Amazon SageMaker AI 模型、端点配置和端点。

![Diagram showing three AWS CDK stacks in sequence, SpeechFoundationStack, SpeechModelCacheStack, and SpeechEndpointStack, feeding into a decision gate labeled scaling_enabled AND a feasible measured plan artifact exists, branching to EndpointAutoscaling plus EndpointObservability on yes, or no scaling resources synthesized on no](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/19/ML-21705-2.png)

图 2：三个 AWS CDK 堆栈，以及决定是否合成自动扩缩容资源的“关卡”

第三个堆栈上的“关卡”阻止默认的、未经测量的扩缩容配置进入生产环境。`scaling_enabled` 是一个静态标志，只要 `max_instances` 配置得大于 `min_instances` 就为 true，它本身完全不能说明背后的数字是否经过测量。该堆栈在合成阶段增加了第二项独立检查：这个模型是否存在一个真实、可行的 `plan` 产物？只有两个条件同时成立，堆栈才会合成扩缩容资源：一个 `EndpointAutoscaling` 构造，用于接好扩缩容策略和告警；以及一个 `EndpointObservability` 构造，用于添加监控所需的仪表盘和告警。一个 `scaling_enabled=True` 但没有测量支撑的模型，其输出与 `scaling_enabled=False` 的模型相同，都是*不合成任何扩缩容资源*。

项目的 CLI 把这三个堆栈封装在一条命令之后，按依赖顺序应用：

```
uv run speech-infra deploy kokoro-82m
```

`SpeechModelCacheStack` 运行一个 AWS CodeBuild 项目，一次性把模型的 Hugging Face 权重同步到缓存的 Amazon S3 存储桶。端点冷启动时就不必从互联网拉取权重。在前述 `scaling_enabled` 检查的把关下，`SpeechEndpointStack` 构建容器镜像、推送到 Amazon ECR，并创建 Amazon SageMaker AI 模型、端点配置和端点。

这套方法论被打包成一条工具链，按固定顺序运行：

### 第 1 步：检查漂移

`drift` 总是第一个运行，在每次运行前都会先跑，先于任何花钱或让端点承受负载的操作。它是一次只读的对账，比较实际部署的内容（可扩缩目标、扩缩容策略、告警状态）与配置文件声称应该部署的内容。来自早前模型的孤立策略，或者一次被停止或取消的 `qmax`、`ttotal` 运行，否则会在测量过程中悄悄改变容量，污染正在测量的数字。

```
uv run tts-bench drift
```

干净的结果会报告没有不匹配，并以 preflight-ok 状态退出，为 `qmax` 扫清道路。一次被停止或取消的 `qmax` 或 `ttotal` 运行，是报告不匹配最常见的原因，因为它可能让自动扩缩容冻结在单个实例上。`uv run tts-bench thaw --endpoint speech-kokoro-82m` 会在你继续之前恢复已部署的策略，因为 `qmax` 和 `ttotal` 都假定部署状态与配置文件完全一致。

### 第 2 步：测量 Q_max，即并发上限

`Q_max` 是这样一个最大并发值——即排队请求数加上在一个实例上执行的请求数——在该并发下，请求仍能在 SLO 内于第 95 百分位达到首个音频字节。它通过闭环负载阶梯测量：精确保持一个固定并发 `N`，然后逐级向上递增 `N`，直到 SLO 被突破。闭环可以避免协调省略（coordinated omission），那是固定到达率测试中的缺陷：服务器变慢时客户端反而少发请求，而不是显现出真实的排队延迟。

```
uv run tts-bench qmax --model kokoro-82m --dry-run
uv run tts-bench qmax --model kokoro-82m
```

`--dry-run` 会在零次 AWS 调用的前提下打印排程和挂钟时间估算，所以你可以先为实际运行约 36 分钟的成本做好预算。实际命令会在运行期间冻结自动扩缩容，并把容量固定为一个实例，退出时自动恢复，因此它产出的数字是名副其实的单实例上限。

`Q_max = 50`，而且这是被夹逼出来的结果：第 60 级确实越过了 SLO，这让 50 成为真正的上限，而不是一个下界。同一次运行还测量了无争用服务时间，即一个请求在完全无排队情况下所花的时间：均值 61.3 ms，p95 为 66.1 ms。这个数字驱动了本文后面描述的第二个独立告警。

### 第 3 步：测量 T_total，即真实扩容时间

`T_total` 是从请求更多容量那一刻起，到该容量开始服务健康流量那一刻止的挂钟时间。它的测量方式是直接强制触发一次扩容，绕过所部署策略自身的检测逻辑，然后为每个可区分的阶段打上时间戳。

```
uv run tts-bench ttotal --model kokoro-82m --qmax <qmax-artifact>
```

`ttotal` 需要把 `qmax` 产物作为输入，因为它的恢复判定读取的是那条阶梯自身测得的各级数据，并且它会拒绝针对在另一种传输方式上测得的阶梯运行。

这次强制扩容可分解为八个已测量阶段：

| **阶段** | **时长** | **占 `T_total` 的比例** |
| --- | --- | --- |
| 请求容量到 desired_set | 30.0 s | 9.4% |
| desired_set 到实例在日志中可见 | 180.8 s | 56.5%（主要耗时） |
| 实例可见到容器启动 | 3.7 s | 1.2% |
| 容器启动到 framework_init | 0.0 s | 0.0% |
| framework_init 到 weights_ready | 6.5 s | 2.0% |
| weights_ready 到 warmup_done | 1.0 s | 0.3% |
| warmup_done 到 in_service | 20.7 s | 6.5% |
| in_service 到流量恢复 | 47.4 s | 14.8% |
| **实测总计（t_total_s）** | **260.2 s** |  |
| + 策略检测滞后，上界估算（未实测） | 60.0 s |  |
| **规划所用的 T_total** | **320.2 s** |  |

主要耗时的阶段是 Amazon Elastic Compute Cloud (Amazon EC2) 实例预配加上容器镜像拉取，耗时 181 秒，占规划总计的 56%。降低 `T_total` 影响最大的途径不是应用代码，而是减小镜像体积或使用热容量池。“实例在日志中可见”之后的所有环节加起来相对较小，合计 79 秒。

在实测 260.2 秒之上增加的 60 秒并未在本次运行中实测。它是根据策略自身的配置（告警评估周期乘以评估周期数，再加上冷却时间）估算出的上界，因为本次运行有意绕过了策略的检测逻辑，以单独隔离纯粹的预配时间。`plan` 按完整的 320.2 秒总计来规划突发余量，因为即使本次测量排除了这段反应时间，它在任何生产环境扩容中都是真实存在的一部分。

### 第 4 步：用 plan 推导出部署策略

`plan` 是唯一一个从不访问 AWS 的命令。它读取 `qmax` 和 `ttotal` 产物，把它们与两个由操作者选定的输入——3,000 ms p95 TTFAB 的 SLO，以及 1.25x 的突发比例（集群能容忍流量在一个扩容周期内增长 25% 而不突破 SLO）——结合起来，然后做如下算术运算。随后它会打印一份报告，为每项发现给出判定：`ok`、`warn`，或者对于真正不可行的方案给出 `stop`。

```
uv run tts-bench plan --qmax <qmax-artifact> --ttotal <ttotal-artifact> --peak-rps 5000
```

`--peak-rps` 标志（此处为每秒 5,000 个请求，同时假定低谷为 10）用于确定集群的实例数量。它不参与下面的阈值算术运算。

```
h  = surge_ratio - 1                    = 1.25 - 1 = 0.25

C_scale_max = (1 - h)     x Q_max       = 0.75 x 50   = 37.50
C_scale_min = (1 - 2h)    x Q_max       = 0.50 x 50   = 25.00

W_max = SLO - S_p95                     = 3.000s - 0.066s = 2.934s
```

`C_scale_max` 是要再增加一个实例时的并发数，它比 `Q_max` 低出突发比例 `h`，这样集群在请求更多容量时仍有排队余量。`C_scale_min` 是移除一个实例的并发数（等于或低于该值），设为 `Q_max` 的 `(1 - 2h)`，这样只有负载降到远低于再次触发扩容的水平之后，才会触发缩容。

最终部署配置，与工具链产出的完全一致：

```
"kokoro-82m": ModelEndpointConfig(
    model_name="kokoro-82m",
    instance_type="ml.g5.xlarge",
    min_instances=1,             # trough 10 rps; 3 is the smallest safe floor for scale-in
    max_instances=9,             # peak 5000 rps
    scaling_target_value=37.500, # C_scale_max, in Amazon CloudWatch units (ratio measured as 1.0)
    scale_in_threshold=25.000,   # C_scale_min, in Amazon CloudWatch units
    ttfab_slo_ms=3000,
    queue_max_depth=50,          # enforced by the container's own admission gate
    scale_out_cooldown_s=30,     # short: one instance added at a time
    scale_in_cooldown_s=960,     # long: see below
)
```

两个冷却时间是有意不对称的。扩容出错代价很低：最坏情况也不过是为一个用不上的实例多付三十秒。缩容的代价并不对称，因为移除后又需要恢复的容量，要用整整一个 `T_total`（320 秒）才能补回来。缩容冷却时间设为大约 `T_total` 的三倍，这样只有在负载真正、持续下降之后，缩容决策才会触发。

容器自身的准入控制另行强制 `queue_max_depth=50`，等于 `Q_max`：超过该深度后，请求会立即被拒绝，返回 `503 queue_saturated` 响应，而不是被留到排队超过它本可满足 SLO 的程度。一个 `FirstChunkLatencyP95` 告警以 65 ms 为阈值（并发 1 时实测的 p95 服务时间），监视已在服务中的实例的服务时间，比包含排队的端到端 SLO 更严格。

Kokoro-82M 运行中有两项发现值得纳入，因为它们是工具正确地揭示了一个已知且可接受的权衡，而不是一个缺陷：

- `surge_survival` **（warn）：**把 `C_scale_max`（37.5）对上 `Q_max`（50）时，扩容一触发的瞬间某个实例的利用率就是 97.4%，而要补上一个实例需要整整一个 `T_total`。突发比例预留了额外的排队槽位，但真正扛过突发靠的是流量，即队列排空的速度，而在 97.4% 的利用率下，剩余的流量余量已经很少了。
- `scale_in_safety` **（warn）：**从 `N` 个实例的集群中移除一个实例，会把每个剩余实例的并发数乘以 `N / (N-1)`。只有当该比值保持在 `C_scale_max / C_scale_min`（此处为 1.5）以下时，缩容才保持稳定，这要求 `N >= 3`。在实例下限为 1 的情况下，从 2 缩到 1 会让幸存的那个实例恰好落在 `Q_max` 上，正好回到会再次触发扩容的上限。较长的冷却时间会抑制这种振荡，但无法消除它。把下限提高到 3 可以在结构上消除它，代价是在低流量时保有闲置容量。

每个 `qmax` 或 `ttotal` 产物的文件名都编码了其测量所依据的配置，实例类型和容器镜像摘要会被压缩成一个 slug（例如 `g5xlarge-8b1b96bc`）。`ttotal` 和 `plan` 都拒绝配对那些指纹不一致的产物。这可以用 `--allow-config-mismatch` 降级为警告，但默认是拒绝。

### 第 5 步：用 validate 确认已部署的策略

`validate` 是这条链上的最后一条命令，也是除 `drift` 之外第二个从不改动任何东西的命令。它把实际部署的扩缩容策略与 `plan` 产物中的值进行比较，在你把该配置视为已生效之前确认两者一致。

```
uv run tts-bench validate --model kokoro-82m --plan <plan-artifact>
```

干净的结果会确认已部署可扩缩目标上的 `scaling_target_value`、`scale_in_threshold` 以及两个冷却时间都与 `plan` 推导的结果一致。任何不匹配都意味着已部署策略与测量得到的计划已经脱节，在依赖该端点的自动扩缩容行为之前应当先解决。

## 测试与验证

本文引用的每个 `qmax`、`ttotal` 和 `plan` 产物都是仓库中已提交的文件，而不是一次性的本地输出。前面的完整示例（包括每一个数字）都可以通过针对两个已提交的测量文件重新运行 `plan` 来独立复现，且零 AWS 调用、零新增支出：

```
$ uv run tts-bench plan --qmax <qmax-artifact> --ttotal <ttotal-artifact> --peak-rps 5000
scaling_target_value : 37.500 (C_scale_max)
scale_in_threshold    : 25.000 (C_scale_min)
surge_survival        : warn
scale_in_safety       : warn
```

## 清理

要删除本次演练中创建的资源，用一条命令按相反顺序拆除这些堆栈：

```
uv run speech-infra destroy kokoro-82m
```

`speech-infra destroy` 会删除 Amazon SageMaker AI 模型、端点配置、端点，以及挂接其上的任何自动扩缩容或 Amazon CloudWatch 资源。它不会清空用于缓存模型权重的 Amazon S3 存储桶，也不会删除存放容器镜像的 Amazon ECR 仓库，因为两者都可能在多个模型之间共享。如果你不再需要它们，请手动清空并删除 Amazon S3 存储桶、移除 Amazon ECR 仓库，因为已存储的模型检查点和容器镜像在删除之前会持续产生少量存储费用。

## 结论

把 Kokoro-82M 作为自定义容器部署到 Amazon SageMaker AI 实时端点上，并用针对在线端点所做的两项测量取代猜测：`Q_max`，一个实例在不突破 SLO 前提下可维持的最高并发；`T_total`，一次真实扩容所需的时间。你通过算术运算从这两个数字推导出扩容阈值、缩容阈值以及两个冷却时间。基于 `ConcurrentRequestsPerModel` 这个由 AWS 发布的原生指标扩缩容，并直接测量其单位换算而不是想当然，正是让该配置与真实并发保持绑定的关键。

结果是一个自动扩缩容策略，其中每个数字都能追溯到针对你自己端点的一次真实测量，而不是从不同工作负载形态沿用来的假设。正是这一区别，把一个可能悄悄多花钱、或悄悄突破 SLO 的配置文件猜测，变成一个你能够用具体并发上限和具体扩容时间来辩护的策略，两者都是测量出来的，而不是断言出来的。

这个四数字模型——选定 SLO 和突发比例，测量 `Q_max` 和 `T_total`，其余全部推导——没有任何部分特定于 TTS。它可以推广到延迟敏感、受并发约束的实时 Amazon SageMaker AI 端点。例如，一个让每个请求在 GPU 前向计算期间保持打开的实时图像嵌入端点，受同一个并发上限约束，而不是受吞吐量指标约束。同样的 `qmax`/`ttotal`/`plan` 工具链可以原样适用。那里真正的瓶颈是同时在飞的并发请求，而不是从另一种工作负载形态借来的吞吐量指标。这里的具体数字 `Q_max=50` 和 `T_total=320s` 只对 `ml.g5.xlarge` 上的 Kokoro-82M 成立。换成其他模型或实例类型，它们会不同。而产出它们的方法论和工具不会变。包含 `drift`、`qmax`、`ttotal`、`plan` 和 `validate` 的五命令工具链，可以原样沿用到你以这种方式部署的下一个模型。

克隆[示例仓库](https://github.com/aws-samples/sample-kokoro-tts-for-ai-agents)，然后针对你自己的端点运行五命令链 `drift`、`qmax`、`ttotal`、`plan` 和 `validate`，产出一个经过测量的策略。参阅 [Amazon SageMaker AI 自动扩缩容文档](https://docs.aws.amazon.com/sagemaker/latest/dg/endpoint-auto-scaling.html)以调整阈值适配你的 SLO，并打开 SageMaker AI 控制台观察该策略对实时流量的反应。如果你需要帮助构建类似的测量驱动部署，请联系你的 AWS 账户团队。
