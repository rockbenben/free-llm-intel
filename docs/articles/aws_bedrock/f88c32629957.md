# agent 间协作：使用 Amazon Nova 2 Lite 和 Amazon Nova Act 构建多 agent 系统

我最初尝试构建旅行规划 agent 时，做的和大多数早期原型一模一样：一个大模型、几个工具，外加一段很长的 system prompt。它一直运作良好，直到现实世界的复杂性出现。航班数据来自干净的 API，酒店却藏在不断变化的 Web UI 后面，而模型不断混淆指令、遗忘上下文，或者编造步骤。就在那时事情变得明显：单 agent 并不是答案，它就是瓶颈。

解决办法是拆分工作，而不是试图修好 prompt。本文详述 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的 agent 间协作在实践中如何运作：用 [Amazon Nova 2 Lite](https://aws.amazon.com/nova/models/) 负责规划，用 [Amazon Nova Act](https://nova.amazon.com/act?tab=playground) 负责浏览器交互，从而把脆弱的单 agent 配置变成可预测的多 agent 系统。

## **方案概览**

该系统由一小群协同工作的 agent 组成，如下图所示。一个 agent 负责规划工作并与用户对话。其他 agent 处理具体任务，例如航班搜索或酒店搜索。它们通过简单的消息通信，因此每个 agent 都能保持专注，任务也便于推理。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/02/ML-20141-image-1.png)

当我看清单 agent 设计究竟在哪里断裂时，模式就很明显了：这个 agent 之所以吃力，不是因为任务难，而是因为这些任务本质上不同。航班搜索是结构化、可预测的。酒店搜索则杂乱、视觉化，充满动态元素。强迫一个模型同时应付这两者，就像让同一位工程师既写后端 API，又实时手动点击网页。而我越是试图用 prompt、更多工具和更多兜底逻辑去补，情况就越糟。当一个单 agent 承担了过多职责，它就会变慢、丢失上下文、做出不一致的选择，最终被自身的重量压垮。问题出在设计上，试图通过 prompt 解决行不通。正确的做法是把工作拆给三个 agent，让每个只承担单一职责。Travel Agent 负责用户意图和规划。Flight Agent 与结构化的航班 API 对话。而 Hotel Agent 使用浏览器自动化浏览真实的酒店网站。不再是一个超载的模型，而是每个 agent 把一件事做好 —— 它们通过一个简单的消息传递层协调，因此从外部看 workflow 依然流畅。每个 agent 都有非常清晰的工作。Travel Agent 是协调者，负责解释请求、把它拆成步骤，并决定哪部分由哪个 agent 执行。Flight Agent 完全专注于数据可预测的结构化 API 调用。而 Hotel Agent 处理杂乱的部分：浏览网页、处理动态布局，并从真实网站中提取酒店详情。以这种方式分离系统，让逻辑保持干净，也防止单个 agent 再次超载。

要让这套配置运转起来，agent 之间需要一种简单的通信方式。Travel Agent 必须向 Flight Agent 发送清晰的请求，等待结果，然后用下一步触发 Hotel Agent。我们不需要任何花哨的东西，只需要一种轻量的消息格式，让 agent 之间可以传递，从而每个 agent 都知道下一步该做什么。当这个通信回路就位后，整个 workflow 终于显得协调有序，而不再是那些布局动态变化、又没有公开 API 的混乱页面。让同一个 agent 同时处理两者，往往会导致工具过载、指令纠缠，以及更高的幻觉风险。

## 实现概览

架构清楚之后，就该真正构建系统了。这时每个 agent 背后的工具终于派上用场。Travel Agent 和 Flight Agent 都使用 Amazon Nova 2 Lite 进行推理和规划，Flight Agent 还会调用结构化的航班 API 获取真实数据。在没有 API 可用时，Hotel Agent 依靠 Amazon Nova Act 自动化浏览器交互。三个 agent 通过直白的 agent 到 agent（A2A）消息传递模式通信：agent 之间交换小的结构化消息来协调工作，这让 workflow 即使在各 agent 运行于不同执行环境时也保持可预测。在多 agent 系统中，协调与专业化同等重要。agent 需要一种结构化、可预测的方式来交换目标、共享状态并触发行为，尤其是在像规划行程这样的任务上协作时。

### Travel agent 实现（Amazon Nova 2 Lite）

Travel Agent 是整个 workflow 的编排者。它接收用户请求，使用 Amazon Nova 2 Lite 解释意图，并决定接下来调用哪个 agent。这里的重推理由 Nova 2 Lite 完成 —— 它把输入拆解为步骤，判断何时触发 Flight Agent 或 Hotel Agent，并跟踪整体计划。由于 Travel Agent 不直接接触外部系统，它唯一的工作就是清晰地思考并用 A2A 路由消息。

下面的代码示例是 Travel Agent 初始化方式的简化版本：

```
    # Initialize A2A client tools
    provider = A2AClientToolProvider(known_agent_urls=[
        "http://localhost:9000",  # Hotel Booking Expert (NovaAct)
        "http://localhost:9001"   # Flight Booking Expert
    ])
    bedrock_model = BedrockModel(
    model_id="global.amazon.nova-2-lite-v1:0",
    region_name="us-east-1",
)
    
    # Create client agent with A2A tools
    client_agent = Agent(
        name="Travel Client",
        model=bedrock_model,
        description="Client agent that coordinates travel planning using specialized      A2A agents",
        tools=provider.tools,
        system_prompt="""You are an autonomous travel planning agent. You MUST take action immediately without asking for confirmation.
```

在实践中，Travel Agent 接收一条自然语言请求，例如“帮我找 7 月 10 日从纽约到东京的航班，以及住到 7 月 15 日的酒店”。随后，Amazon Nova 2 Lite 承担重推理：它识别出需要完成两个独立任务，生成清晰的计划，向 Flight Agent 发送消息，等待结果，然后用下一条指令触发 Hotel Agent。最后，它把两个输出组装成一个连贯的响应。这让编排逻辑保持干净顺畅。Nova 2 Lite 实际上充当 workflow 的大脑，而专职 agent 负责真正的执行。

### Flight agent 实现（Amazon Nova 2 Lite 与 API）

Flight Agent 的工作范围窄得多：把结构化请求转换为真实的航班选项。它使用 Amazon Nova 2 Lite 完成所需的轻量推理，用于校验输入、格式化搜索条件，以及决定在凭证不可用时是调用实时航班 API 还是回退到模拟数据。API 调用完成后，该 agent 通过 A2A 向 Travel Agent 返回干净、可预测的 JSON 响应。

下面的代码示例展示了航班搜索工具的简化版本。完整实现（包括 OAuth、回退逻辑和机场代码处理）见 [Agent to Agent with Amazon Nova](https://github.com/aws-samples/sample-Agent-to-Agent-with-Amazon-Nova) GitHub 仓库：

```
@tool
def search_flights(origin: str, destination: str, departure_date: str, return_date: Optional[str] = None) -> str:
    # Nova 2 Lite handles the reasoning around which path to take
    if amadeus_configured():
        return _search_amadeus_flights(
            origin=origin,
            destination=destination,
            departure_date=departure_date,
            return_date=return_date
        )
    else:
        # Local development fallback
        return _search_flights_web(origin, destination, departure_date, return_date)
{
  "flights": [
    { "flight_number": "DL456", "price": 520, "duration": "14h 30m" },
    { "flight_number": "JL701", "price": 545, "duration": "13h 50m" }
  ],
  "source": "Amadeus API"
}
```

由于该 agent 处理的是干净、结构化的数据，推理负担较轻，Amazon Nova 2 Lite 的工作主要是选择正确的执行路径并对输出做规范化。这让整条 pipeline 保持可预测，也避免把 API 特有的逻辑嵌进 Travel Agent 里。

### Hotel agent 实现（Amazon Nova Act）

酒店和航班完全不同。你没有一个干净的 API 可以调用，而大多数预订网站的加载方式每次访问都会变化。这正是 Amazon Nova Act 的用武之地。Hotel Agent 使用 Nova Act 控制真实浏览器并遵循自然语言指令。agent 不必编写脆弱的抓取代码，只需告诉 Nova Act 它需要什么，Nova Act 负责浏览并返回结构化数据。

下面是该工具的缩短版本：

```
@tool
def search_hotels(location: str, checkin_date: str, nights: int = 2) -> str:
    with NovaAct() as nova:
        result = nova.act(
            f"Search for hotels in {location} from {checkin_date} for {nights} nights. "
            f"Return the top 3 listings with name, price, and rating.",
            schema=HotelSearchResults.model_json_schema()
        )
        return json.dumps(result)
```

使用 Amazon Nova Act 可以让 Hotel Agent 不会因网站每次改版就失效。借助它，你也可以免去自己编写抓取或 DOM 解析逻辑。

### A2A 消息流（agent 之间如何对话）

现在每个 agent 都知道自己负责什么，它们需要一种互相通信的方式。在 Travel Agent 开始派发真正的工作之前，它会先调用其他 agent 的 A2A 端点，确认它们已就绪。它还会加载每个 agent 暴露的工具列表，好让 Nova 2 Lite 知道有哪些能力可用。这些完成后，流程就很直接：Travel Agent 把所需字段发给 Flight Agent；Flight Agent 完成后回发一条消息；随后 Travel Agent 把下一条消息传给 Hotel Agent。每条消息都是一个小的 JSON 对象，包含动作、输入数据以及响应要发送到哪里等内容。

### 端到端示例运行

**下面是一次完整运行的样子。** 用户向 Travel Agent 发送一条请求：

```
Please arrange travel for one person from NYC to Paris on December 6, 2025, including a two night stay in Paris.
```

- Travel Agent -> Flight Agent：  Travel Agent 抽出请求中的航班部分并发送给 Flight Agent。Flight Agent 返回三个从 JFK 到巴黎的直飞低价航班，包括航空公司、时间、价格和时长。
- Travel Agent -> Hotel Agent：  Travel Agent 把请求中的酒店部分发送给 Hotel Agent。Hotel Agent 使用 Nova Act 查询巴黎的酒店，并返回前三名的选项及其名称、价格和简短备注。
- **返回给用户的最终结果**  Travel Agent 把两个答案合并，返回一份清晰的摘要，其中包括：
- 推荐的航班
- 推荐的酒店
- 入住和退房日期
- 价格
- 一个询问是否预订的问题

## 结论

用三个小 agent 构建这个旅行规划器，最终证明比用一个大的 agent 更容易管理。每个 agent 专注于一项工作，而 Amazon Nova 2 Lite 负责推动工作从一个步骤走到下一步所需的思考。Amazon Nova Act 覆盖那些没有 API 的部分（例如酒店搜索），无需编写抓取代码。A2A 消息流让各部分保持连接，同时依然直白。

这套配置并不局限于旅行。混合了不同技能的任务都可以采用同样的思路：让一个 agent 规划工作，让其他 agent 做各自擅长的部分，并在它们之间传递小的消息。这让系统在变更和解释时都显得顺畅自然。

如果你想自己试一试，完整代码和示例见 [Agent to Agent with Amazon Nova](https://github.com/aws-samples/sample-Agent-to-Agent-with-Amazon-Nova) GitHub 仓库。
