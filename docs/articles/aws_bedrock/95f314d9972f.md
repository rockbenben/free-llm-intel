当你在规模上以人类反馈强化学习（RLHF）或 Group Relative Policy Optimization（GRPO）后训练一个混合专家（MoE）模型时，会同时出现三个挑战。第一个要求为 rollout 生成和策略训练协调异构计算。第二个是在数百个加速器上维持高吞吐通信。第三是动态编排每个子系统以保持它们的平衡。在 AWS 上，你可以用 Amazon Elastic Kubernetes Service (Amazon EKS)、Elastic Fabric Adapter (EFA) 和 DeepEP 来应对这些挑战。

混合专家（MoE）已成为把大语言模型（LLM）扩展到数千亿乃至数万亿参数、同时通过稀疏性维持高效推理的标准架构。然而，稀疏性并不消除训练中的基础设施复杂性。作为标准训练流水线的一部分，这些模型必须经历预训练、中途训练、监督微调（SFT）和强化学习（RL）。在这些阶段中，大规模 RL 训练对基础设施提出不寻常的要求，因为它把弹性推理工作与需要高带宽通信、紧密耦合的模型训练相结合。奖励模型、验证器和 checkpoint 更新 adds 进一步的内存、网络和编排压力。这种多工作负载优化反映了一个常见的基础设施挑战：你在共享资源上运行模型训练、推理和评估，而不造成瓶颈或让容量闲置。

与稠密模型相比，后训练 MoE 模型引入了一项新的基础设施挑战：随着较新的 MoE 架构变得越来越稀疏以降低推理成本，训练更受通信而非计算的制约。这份通信开销的一个主要来源是专家并行（EP）。EP 在稠密、结构化的张量并行（TP）、数据并行（DP）和流水线并行（PP）通信模式之外，引入了跨设备的动态 all-to-all token 路由。在紧密耦合的异步 RL 工作负载中，MoE 训练的异构计算和通信需求必须与基于推理的生成相平衡。慢的训练步会拖住推理 worker，而不足的推理吞吐会让训练加速器空闲。这一挑战普遍存在于大规模强化学习工作负载中，包括基于近端策略优化（PPO）的 RLHF 流水线和诸如 GRPO 的较新方法。

PPO 通常在策略优化期间用一个 critic 模型来估计价值，而 GRPO 通过使用基于组的相对奖励避免了对单独 critic 模型的需要。尽管它们的算法和模型要求不同，两者都施加类似的基础设施需求：大规模的 rollout 生成、紧密耦合的策略训练，以及高带宽的节点间通信。

在本文中，我们描述一个为加速 MoE 训练而优化的架构，它结合 Amazon Elastic Kubernetes Service (Amazon EKS) 和 EFA 来编排并加速大规模 RL 训练，以及 DeepEP 如何在 EFA 上优化专家并行通信。

## 大规模 RL 训练的挑战

大规模 RL 训练呈现三个相互关联的挑战：

- 平衡 rollout 生成与策略训练相互竞争的资源需求。
- 同时管理加速器计算、内存和网络带宽。
- 处理随着作业扩展到单个实例之外、从高带宽节点内通信向低带宽节点间链路的转变。

### rollout-训练循环

大规模异步 RL 作业有两个不同、同时需要优化的工作负载：rollout 生成和策略训练。在 rollout 生成期间，系统执行大规模分布式推理，聚焦于最大化总吞吐，而非最小化首 token 时间（TTFT）或 token 间延迟。相比之下，策略训练需要以lockstep推进的、紧密耦合的 worker，很像预训练或 SFT。任何延迟尖峰或掉队 worker 都可能拖住整个作业或触发 NVIDIA Collective Communications Library（NCCL）超时。RL 系统必须平衡这两个工作负载，因为它们速率上的任何错配都可能让硬件空闲或引入训练不稳定。

图 1：异步 RL 循环，其中 rollout worker 通过分布式推理生成经验，而策略训练 worker 消费批次并更新模型权重

### 计算、内存与带宽压力

RL 工作负载有异构的计算和通信需求。因此，任何 RL 系统都必须平衡三个资源约束：加速器计算、内存和网络带宽。策略训练是计算密集型的，必须跟上 rollout 生成的节奏。同时，分布式推理必须管理 KV 缓存容量和 token 生成。在 token 被跨设备路由时 MoE 层加上了稀疏、动态的 all-to-all 通信，因此平衡内存带宽和计算对最大吞吐至关重要。奖励模型在训练期间提供反馈，而数据移动增加更多压力。所有这些子系统必须联合平衡，以帮助防止其中任何一个成为瓶颈。

### 节点内 vs 节点间通信

当 RL 训练作业扩展到单个实例之外时，模型分区和并行组跨多个节点，把通信从高带宽的节点内 NVLink 结构转移到低带宽的节点间链路。MoE 模型加剧了这一转变：与张量并行和流水线并行的结构化模式不同，专家并行通过稀疏、细粒度的 all-to-all 通信流量动态地把 token 跨设备路由，而随着专家并行度增长，它越来越多地变成节点间通信。

图 2：多节点 MoE 训练中的通信域，其中 NVLink 承载高带宽节点内流量，而 EFA 处理专家并行、张量并行和数据并行的节点间 token 路由

P5 和 P6 这类 AWS 加速计算实例使用两个主要通信域：一个实例内的 NVLink 结构（通常通过 NVSwitch 连接），和通过 EFA 的实例间网络。EFA 提供实例之间的高带宽通信流量。在[受支持的配置](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html#efa-instance-types)上，EFA 配合 NVIDIA GPUDirect RDMA 和 OS bypass，跨实例在 GPU 内存缓冲区之间直接传输数据，减少 CPU 和操作系统在通信路径上的参与。优化 RL 工作负载中的带宽利用率需要平衡这两个通信域，通过判断哪些操作能高效地跑在 EFA 上、哪些必须留在 NVLink 结构之内。

## 架构概览

要在 AWS 上扩展 RL 工作负载，我们结合 Amazon EKS、EFA 和 Amazon Simple Storage Service (Amazon S3)，使编排、高性能通信和持久存储能独立扩展。借助 Amazon EKS，你可以管理异构 worker 的生命周期和放置。借助 EFA，你得到面向通信密集型 GPU 工作负载的节点间数据路径。借助 Amazon S3，你可以存储数据集、模型 checkpoint 和完成的训练产物，包括模型权重。下面各节描述如何映射 RL 系统的不同层——涵盖编排、高性能网络和持久存储——以及每一层如何独立扩展。

### EKS 集群拓扑

Amazon EKS 集群含有为 RL 工作流每个阶段优化的独立节点组。GPU 加速实例运行 rollout 生成、奖励模型推理和策略训练，而 CPU 实例执行环境和预处理任务。内存优化实例托管经验缓冲和 checkpoint 缓存，让生产者和消费者交换数据而无需把持久存储直接放在关键路径上。

图 3：EKS 集群拓扑，带用于策略训练和 rollout 生成的 GPU 节点组、用于环境 worker 和预处理的 CPU 节点组，以及用于经验缓冲和 checkpoint 缓存的内存优化实例

### RL 作业拓扑

在 rollout 期间，模型通过与基于 CPU 的环境 pod 交互来生成样本，得到的经验流入一个内存优化缓冲。从那里，策略训练步消费批次、更新模型权重并发布新的 checkpoint，反馈进下一轮 rollout 生成。checkpoint 和完成的训练产物也持久化到 Amazon S3 以做持久存储、恢复和下游使用。策略训练、权重更新和新 checkpoint 生成都可以在 EKS 集群上运行。

图 4：EKS 上的 RL 作业数据流，其中 rollout worker 通过 CPU 环境交互生成经验并写入一个共享内存缓冲，而策略训练 worker 消费批次、发布更新的 checkpoint 并把产物持久化到 Amazon S3

### 网络与执行层

EKS 为调度、伸缩、故障恢复和跨不同 worker 组的协调提供控制平面。在 GPU 实例内部，NVLink 和 NVSwitch 承载高带宽的节点内通信。EFA 支持分布式策略训练和其他紧密耦合 GPU 操作对延迟敏感的节点间通信。经验缓冲和 Amazon S3 构成数据层，把高频样本和 checkpoint 交换与长期产物存储分离。

## 性能与成本优化

本节涵盖两项关键优化：用 DeepEP 减少 EFA 上的专家并行通信开销，以及用 Amazon Elastic Compute Cloud (Amazon EC2) Spot 实例帮助降低 rollout 生成的成本。

### EFA 上的 DeepEP

DeepEP，连同其他拓扑感知的专家并行通信技术，是一种旨在减少通信瓶颈的 MoE 工作负载常见优化。标准的 all-to-all 集合通信对稠密、规则的通信最高效，但当 token 被动态跨专家路由时，MoE 工作负载生成稀疏、细粒度、不均衡的流量。当专家并行跨多个节点时，同步和每消息开销增加，使节点间通信成为一个主导瓶颈。DeepEP 通过用专门的 dispatch 和 combine 内核替换通用的 all-to-all 集合通信来应对这一点。这些内核用 NVLink 做节点内通信，用一个支持 RDMA 的后端做节点间通信。

Amazon 为把 DeepEP 的通信原语迁移到 libfabric 贡献了若干特性。这使传输层在支持 libfabric 的网络结构之间可移植，并优化 EFA 上的 MoE 训练。有了这些改动，DeepEP v2 获得原生 EFA 支持。此外，NCCL 2.31 纳入了最新的、用于稠密集合通信的 EFA 优化。在下一节中，我们描述 EFA 上的 DeepEP 如何通过减少专家 dispatch 和 combine 操作的通信开销来提升 rollout 生成吞吐。

### DeepEP 如何在 EFA 上通信

DeepEP 用两个专门的 GPU 内核替换标准的 NCCL all-to-all 集合通信：一个把 token 从本地 GPU 路由到远程专家的 dispatch 内核，和一个把处理过的 token 收集回来的 combine 内核。对于节点内传输，这些内核通过 NVSwitch 使用 NVLink。对于节点间传输，DeepEP 用 libfabric 通过 EFA 发送数据。在 P5 和 P6 这类受支持实例类型上，EFA 配合 NVIDIA GPUDirect RDMA 跨实例在 GPU 内存缓冲区之间直接传输数据，绕过 CPU 和操作系统。来自 Amazon 的上游贡献把 DeepEP 的通信原语从一个 CUDA 专用的 RDMA 后端迁移到 libfabric。这使传输在 EFA 支持的配置之间可移植，并减少了专家并行所生成的稀疏、细粒度流量模式的每消息开销。

在 48 台 P5en 实例（16 台专用训练，32 台推理）上运行一个[超稀疏 MoE 模型](https://github.com/radixark/miles/blob/main/scripts/run_glm5_744b_a40b.py)时，启用 EFA 上的 DeepEP 使总 RL rollout 吞吐提升 40%。图 5 展示带与不带 DeepEP 的吞吐比较。

图 5：跨 48 台 P5en 实例、带与不带 EFA 上 DeepEP 的 RL rollout 吞吐

### 用于 rollout 生成的 Spot 实例

rollout 生成很适合 Amazon EC2 Spot 实例，因为它由可跨独立 worker 分区的分布式推理任务组成。与紧密耦合 worker 必须一起推进的策略训练不同，一个 rollout worker 被打断不需要整个 RL 作业停止。未完成的任务可以返回队列并在其余 worker 继续生成经验的同时被重新分派。

借助 Amazon EKS，你可以根据 rollout 需求和队列深度来伸缩基于 Spot 的 rollout 节点组，同时为策略训练维持稳定容量。rollout worker 应处理有界的工作单元并频繁发布完成的样本。当 Spot 打断通知到达时，worker 排空活跃的请求并把未完成的任务返回队列。这种分离能帮助降低 rollout 生成成本。策略训练 worker 与 Spot 打断、延迟或 NCCL 超时相隔离。

## 把一切串起来

本节演练配置前面各节所描述的基础设施，从创建集群到启用 DeepEP 通信运行一个 RL 作业。

### 前提条件

在 Amazon EKS 上运行 RL 之前，确认满足以下要求：

- 带有适当 AWS Identity and Access Management (IAM) 权限的 AWS 账户。
- Amazon EKS 1.31 或更新。
- EFA installer 1.49 配 AWS OFI NCCL 插件。
- DeepEP 2.0.0、NCCL 2.31.2、SGLang 0.5.17、PyTorch 2.12.1（CUDA 13.0）。
- 受支持的 GPU 实例，如 p5.48xlarge、p5e.48xlarge 或 p6-b200.48xlarge。
- 熟悉 Kubernetes 和分布式训练概念。

### EKS 集群设置

这一架构可以在 [Amazon EKS](https://docs.aws.amazon.com/eks/latest/userguide/getting-started.html) 上部署，通过把策略训练、rollout 生成和支持服务分离到独立管理的节点组。这保持了紧密耦合训练工作负载与更弹性 rollout worker 之间的隔离，同时让每个组件使用为其执行特性优化的容量模型。

托管节点组简化了配置、更新和实例生命周期管理。策略训练 worker 可以运行在稳定的 GPU 容量上，而 rollout 生成容量可以独立伸缩并在中断容忍允许之处纳入 Spot 实例。基于 CPU 的服务（包括编排和支持组件）可以放在独立的节点组中，以避免与 GPU 工作负载争夺容量。

下面的 eksctl ClusterConfig 为集群定义一个通用 CPU 节点组和一个 GPU 加速器节点组：

```
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: my-eks-cluster
  region: us-west-2
  version: "1.33"

managedNodeGroups:

  # ------------------------------------------------------------
  # General-purpose CPU node group
  # ------------------------------------------------------------
  - name: general-purpose-ng
    minSize: 3
    desiredCapacity: 3
    maxSize: 6
    capacityType: ON_DEMAND
    privateNetworking: true
    launchTemplate:
      id: lt-xxxxxxxxxxxxxxxxx
      version: "1"
    labels:
      workload-type: general-purpose
    tags:
      Name: eks-general-purpose
      NodeGroup: general-purpose-ng
      Workload: general-purpose
    updateConfig:
      maxUnavailable: 1

  # ------------------------------------------------------------
  # GPU / accelerator node group
  # ------------------------------------------------------------
  - name: accelerator-ng
    minSize: 3
    desiredCapacity: 3
    maxSize: 6
    capacityType: ON_DEMAND
    privateNetworking: true
    launchTemplate:
      id: lt-yyyyyyyyyyyyyyyyy
      version: "1"
    labels:
      workload-type: accelerator
      accelerator: nvidia-b300
    taints:
      - key: nvidia.com/gpu
        value: "true"
        effect: NoSchedule
    tags:
      Name: eks-accelerator
      NodeGroup: accelerator-ng
      Workload: accelerator
    updateConfig:
      maxUnavailable: 1
```

列出的 Ampere、Hopper 和 Blackwell 实例类型（p4d.24xlarge、p4de.24xlarge、p5.48xlarge、p5e.48xlarge、p6-b200.48xlarge 和 p6-b300.48xlarge）支持大规模 RL 训练，可用于 rollout 或训练工作负载。

### 设置 EFA 驱动与插件

要在 Amazon EKS 上优化异步 RL，通信节点必须在同一个可用区（AZ），且必须设置 EFA Kubernetes 设备插件。借助 EFA，你得到快速高效的模型更新、高性能的模型训练和低延迟的通信。要应用 EKS EFA 设备插件，你可以用 `kubectl` 把它直接应用到集群。

```
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: aws-efa-k8s-device-plugin
  namespace: kube-system
  labels:
    app: aws-efa-k8s-device-plugin
spec:
  selector:
    matchLabels:
      app: aws-efa-k8s-device-plugin
  updateStrategy:
    type: RollingUpdate
  template:
    metadata:
      labels:
        app: aws-efa-k8s-device-plugin
    spec:
      # Only install on the accelerator node group
      nodeSelector:
        eks.amazonaws.com/nodegroup: accelerator-ng
      priorityClassName: system-node-critical
      hostNetwork: true
      automountServiceAccountToken: false
      tolerations:
        - operator: Exists
      containers:
        - name: aws-efa-k8s-device-plugin
          # Current AWS EFA K8s device plugin
          image: 602401143452.dkr.ecr.us-west-2.amazonaws.com/eks/aws-efa-k8s-device-plugin:v0.5.20
          securityContext:
            privileged: true
            allowPrivilegeEscalation: true
            runAsUser: 0
            runAsNonRoot: false
          resources:
            requests:
              cpu: 10m
              memory: 20Mi
          volumeMounts:
            - name: device-plugin
              mountPath: /var/lib/kubelet/device-plugins
            - name: infiniband
              mountPath: /dev/infiniband
      volumes:
        - name: device-plugin
          hostPath:
            path: /var/lib/kubelet/device-plugins
        - name: infiniband
          hostPath:
            path: /dev/infiniband
```

额外说明和性能测试参见 [EKS EFA 设置说明](https://docs.aws.amazon.com/eks/latest/userguide/node-efa.html)。

### 启动 DeepEP

参考实现组合了支持前面各节所述优化所需的 CUDA、PyTorch、通信和推理组件。下表列出基准环境：

- CUDA：13.0。
- PyTorch：2.12+cu130。
- NCCL：2.31。
- EFA：1.49。
- DeepEP：2.0。
- SGLang：0.5.17。
- Miles：[0.1.0](https://github.com/radixark/miles/releases/tag/v0.1.0)。

保持这些组件对齐至关重要。GPU 内核、集合通信库和底层 EFA 传输各自对端到端性能做出贡献。使用 `763104351884.dkr.ecr.<region>.amazonaws.com/sglang:0.5.17-gpu-py312-cu130-ubuntu24.04-ec2` 镜像（在 [SGLang Deep Learning Containers 目录](https://aws.github.io/deep-learning-containers/reference/available_images/#sglang-ubuntu)中提供）是一个实用的起点。下面的 Dockerfile 可用于设置训练技术栈。

### 启动一个作业

借助 TorchX，你可以向 Amazon EKS 提交 RL 工作负载，同时把应用配置与基础设施配置分离。TorchX 把工作负载需求翻译成 Kubernetes 资源，包括计算请求、存储挂载和运行时配置。这种分离让改动模型和训练配置更容易，而不把它们耦合到集群配置。

下面的命令用 TorchX 向你的 Amazon EKS 集群提交一个 RL 训练作业。参考的 `train_rl.py` 脚本（可在 [Miles 仓库](https://github.com/radixark/miles)获取）编排前述的 rollout-训练循环，把 rollout worker 和策略训练 worker 作为独立的 Kubernetes pod 启动。deepseek_v3_moe 配置指定 MoE 模型架构，包括专家数和并行策略。TorchX 把应用配置与底层 Kubernetes 基础设施分离，因此你可以调整模型参数、worker 数和并行设置而无需修改集群级资源。

一个 RL 作业可以用下面的命令启动：

```
torchx run -s kubernetes -cfg queue=default \
    dist.ddp -j 4x8 \
    --script train_rl.py \
    --model_conf deepseek_v3_moe \
    --num_rollout_workers 32 \
    --checkpoint_dir s3://my-bucket/checkpoints
```

## 清理

为避免持续产生费用，删除你在本次演练期间创建的资源。首先，删除任何正在运行的训练作业及其关联的 pod。接着，移除用于策略训练、rollout 生成和环境 worker 的 EKS 托管节点组。然后，删除 EKS 集群本身。最后，确认任何关联的 Amazon EC2 Spot 容量、用于 EFA 的 Elastic Network Interfaces，以及用于 checkpoint 的 Amazon S3 桶也被按需移除或清空。

```
# Delete training jobs
kubectl delete jobs --all -n rl-training

# Delete node groups
eksctl delete nodegroup --cluster my-eks-cluster --name general-purpose-ng
eksctl delete nodegroup --cluster my-eks-cluster --name accelerator-ng

# Delete the cluster
eksctl delete cluster --name my-eks-cluster
```

关于管理 Amazon EKS 资源的更多信息，参见 Amazon EKS 文档中的[删除一个 Amazon EKS 集群](https://docs.aws.amazon.com/eks/latest/userguide/delete-cluster.html)。

## 结论与关键要点

为 MoE 模型扩展 RLHF 和 GRPO，需要一种能平衡弹性 rollout 生成与紧密耦合策略训练的基础设施。在我们的内部工作负载中，该架构把总 rollout 吞吐提升了 40%（见图 5），同时缩短了端到端策略迭代时间并扩展到约一千个加速器。这一比较在同一 48 台 P5en 实例（16 台专用训练，32 台推理）上、用运行同一超稀疏 MoE 模型的两种配置。基线用一个基于 Slime 的技术栈（CUDA 12.9、PyTorch 2.9.1、NCCL 2.27、SGLang 0.5.9、Slime 0.2.4），没有 EFA 加速的专家并行。改进后的配置用本文描述的 `DeepEP-over-EFA` 技术栈（CUDA 13.0、PyTorch 2.12、NCCL 2.31、EFA 1.49、DeepEP 2.0、SGLang 0.5.17、Miles 0.1.0）。对应的吞吐比较见图 5。

本文展示了如何构建并优化一个可扩展架构，结合 Amazon EKS、EFA 和 Amazon S3，为大规模分布式 RL 工作负载提供一条灵活、经济的路径。

### 关键要点

- **独立伸缩组件：** RL 工作负载的异构性质意味着不同子系统可以独立伸缩。因此可以有选择地应用像 Spot 实例这样的成本优化。
- **平衡资源约束：** RL 系统同时对计算、内存和带宽施加需求。端到端的收益需要跨技术栈的协同设计，把从传输和通信原语到模型设计的优化结合起来。
