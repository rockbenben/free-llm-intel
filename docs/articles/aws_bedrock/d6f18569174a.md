# Harmonic Security 如何利用 Amazon SageMaker、Amazon Bedrock 和 Amazon Nova Pro 上的低延迟微调模型改进其数据泄露检测系统

*本文与 Harmonic Security 的 Bryan Woolgar-O’Neil、Jamie Cockrill 和 Adrian Cunliffe 共同撰写*

组织在支持第三方生成式 AI 工具的同时保护敏感数据，面临着越来越大的挑战。[Harmonic Security](https://www.harmonic.security/) 是一家网络安全公司，它开发了一套 AI 治理与控制层，可在员工使用 AI 时实时识别敏感数据，让安全团队能够在业务加速前进的同时确保 PII、源代码和薪资信息安全。

下面的截图展示了 Harmonic Security 的软件工具，突出了不同的数据泄露检测类型，包括员工 PII、员工财务信息和源代码。

[![带有已启用的 PII 与代码监控检测类型的 Harmonic Security 配置仪表板](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-harmonic-app-screenshot.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-harmonic-app-screenshot.png)

Harmonic Security 的解决方案现已在 [AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-rdb3b4ogktlu2) 上架，使组织能够部署企业级数据泄露防护并与 AWS 无缝集成。该平台提供对 GenAI 使用的 prompt 级可见性、风险发生点的实时指导，以及对高风险 AI 应用的检测——所有这些都由本文所述的优化模型驱动。

他们系统的初始版本是有效的，但检测延迟为 1–2 秒，仍有进一步提升能力、改善整体用户体验的空间。为此，Harmonic Security 与 AWS Generative AI Innovation Center 合作优化其系统，并设定了四个关键目标：

- 将第 95 百分位的检测延迟降低到 500 毫秒以内
- 在各类被监控的数据类型上保持检测准确率
- 继续支持欧盟数据驻留合规要求
- 为生产负载提供可扩展的架构

本文详细介绍了 Harmonic Security 如何使用 [Amazon SageMaker AI](https://aws.amazon.com/sagemaker-ai/)、[Amazon Bedrock](https://aws.amazon.com/bedrock/) 和 [Amazon Nova Pro](https://aws.amazon.com/ai/generative-ai/nova/) 微调 ModernBERT 模型，实现低延迟、准确且可扩展的数据泄露检测。

## 方案概览

Harmonic Security 最初的数据泄露检测系统依赖一个 80 亿（8B）参数的模型，它能有效识别敏感数据，但会带来 1–2 秒的延迟，已接近影响用户体验的阈值。为了在保持准确率的同时实现低于 500 毫秒的延迟，我们基于微调的 [ModernBERT 模型](https://huggingface.co/docs/transformers/en/model_doc/modernbert)开发了两种分类方法。

首先，我们优先采用二元分类模型来检测并购（Mergers & Acquisitions，M&A）内容，这是帮助防止敏感数据泄露的一个关键类别。我们最初专注于二元分类，因为它是最简单的方法，能够无缝集成到他们现有系统中，而该系统会并行调用多个二元分类模型。其次，作为延伸，我们探索了一种多标签分类模型，可在一次推理中检测多种敏感数据类型（例如账单信息、财务预测和雇佣记录），目标是降低并行运行多个二元分类器带来的计算开销，从而获得更高效率。尽管多标签方法在未来可扩展性上展现出潜力，但 Harmonic Security 决定在初始版本中沿用二元分类模型。该方案使用了以下关键服务：

- [Amazon SageMaker AI](https://aws.amazon.com/sagemaker-ai/) – 用于微调和部署模型
- [Amazon Bedrock](https://aws.amazon.com/bedrock/) – 用于访问业界领先的大语言模型（LLM）
- [Amazon Nova Pro](https://aws.amazon.com/ai/generative-ai/nova/) – 一个能力很强的多模态模型，在准确率、速度和成本之间取得平衡

下图展示了面向低延迟推理与可扩展性的方案架构。

[![以 SageMaker 托管 ModernBERT 模型并配备自动扩缩容与监控的端到端 AWS 架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-arch-diagram.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-arch-diagram.png)

该架构由以下组件构成：

- 模型构件存放在 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）中
- 包含推理代码的自定义容器托管在 [Amazon Elastic Container Registry](https://aws.amazon.com/ecr/)（Amazon ECR）中
- SageMaker 端点使用 ml.g5.4xlarge 实例进行 GPU 加速推理
- [Amazon CloudWatch](https://aws.amazon.com/cloudwatch) 监控调用量，并依据每分钟 830 次请求（RPM）的阈值触发自动扩缩容，调整实例数量（1–5）。

该方案支持以下特性：

- 低于 500 毫秒的推理延迟
- 支持在欧盟 AWS 区域部署
- 根据需求在 1–5 个实例之间自动扩缩容
- 在低使用率时段优化成本

## 合成数据生成

针对敏感信息（例如 M&A 文档和财务数据）的高质量训练数据十分稀缺。我们使用 Meta Llama 3.3 70B Instruct 和 Amazon Nova Pro 生成合成数据，在 Harmonic 既有数据集的基础上进行扩展，该数据集包含以下类别的数据示例：M&A、账单信息、财务预测、雇佣记录、销售管线和投资组合。下图给出了合成数据生成过程的高层概览。

[![从主数据集到最终输出的端到端合成数据生成流水线](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-synth-data-pipeline.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-synth-data-pipeline.png)

### 数据生成框架

合成数据生成框架由一系列步骤组成，包括：

- **智能样例选择 **– 对句子嵌入做 K-means 聚类，支持多样化的样例选择
- **自适应 prompt **– Prompt 融入领域知识，并按类别调整 temperature（0.7–0.85）和 top-p 采样
- **近似负例增强 **– 构造与正例相似的负例，以提升精确率
- **校验 **– 采用 LLM-as-a-judge 方法，使用 Amazon Nova Pro 和 Meta Llama 3 校验样例的相关性与质量

### 二元分类

针对 M&A 二元分类任务，我们生成了三种不同类型的样例：

- **正例** – 这些样例包含明确的 M&A 信息，同时保持真实的文档结构和金融领域特有的语言模式。它们包含诸如“merger”“acquisition”“deal terms”和“synergy estimates”等关键指标。
- **负例** – 我们创建了与领域相关的内容，这些内容刻意避开 M&A 特征，同时在语境上仍适合商业通信。
- **近似负例** – 这些样例与正例相似，但刚好落在分类边界之外。例如，讨论战略合作或合资企业、但并不构成实际 M&A 活动的文档。

生成过程在这些样例类型之间保持了谨慎的比例，并特别强调近似负例，以满足精确率要求。

### 多标签分类

针对跨四类敏感信息、更为复杂的多标签分类任务，我们制定了一套精细的生成策略：

- **单标签样例** – 我们生成了只包含恰好一个类别相关信息的样例，以建立清晰的类别特有特征
- **多标签样例** – 我们创建了跨越多个类别、分布受控的样例，覆盖多种组合（2–4 个标签）
- **类别特定要求** – 对每个类别，我们定义了必需元素，以保持显式而非隐含的关联：**财务预测** – 前瞻性的营收和增长数据 **投资组合** – 关于持仓和绩效指标的详情 **账单与支付信息** – 发票和供应商账户 **销售管线** – 商机和预计营收

我们的多标签数据生成优先考虑类别之间符合现实的共现模式，同时保持单个类别及其组合的充分代表性。结果是，合成数据把训练样例分别增加了 10 倍（二元分类）和 15 倍（多标签分类）。它还改善了类别平衡，因为我们确保以更均衡的标签分布来生成数据。

## 模型微调

我们在 SageMaker 上微调 [ModernBERT](https://huggingface.co/docs/transformers/en/model_doc/modernbert) 模型，以实现低延迟和高准确率。与 Meta Llama 3.2 3B、Google Gemma 2 2B 等仅解码器模型相比，ModernBERT 紧凑的规模（149M 和 395M 参数）转化为更低的延迟，同时仍能提供更高的准确率。因此，我们选择 ModernBERT，而不是微调那些替代模型。此外，ModernBERT 是少数支持最长 8,192 个 token 上下文长度的基于 BERT 的模型之一，这是我们项目的一项关键需求。

### 二元分类模型

我们的第一个微调模型使用 ModernBERT-base，专注于 M&A 内容的二元分类。我们有条不紊地推进这项任务：

- **数据准备** – 我们用合成生成的数据充实 M&A 数据集
- **框架选择** – 我们在 SageMaker 上运行 PyTorch 环境，使用 Hugging Face transformers 库和 Trainer API
- **训练过程** – 我们的过程包括：  分层采样，以在训练集和评估集之间保持标签分布  专门的分词处理，序列长度最长 3,000 个 token，以匹配客户生产环境中的配置  二元交叉熵损失优化  基于 F1 分数的早停，以防止过拟合。

结果是一个微调后的模型，它能够以比 8B 参数模型更高的 F1 分数，将 M&A 内容与非敏感信息区分开来。

### 多标签分类模型

对于第二个模型，我们应对了更复杂的多标签分类挑战（在单段文本中同时检测多种敏感数据类型）。我们微调 ModernBERT-large 模型，以便在一次推理中识别账单信息、雇佣记录和财务预测等多种敏感数据类型。这需要：

- **Multi-hot 标签编码** – 我们把各个类别转换为向量格式，以便同时预测。
- **Focal loss 实现** – 我们没有使用标准的交叉熵损失，而是实现了一个自定义的 FocalLossTrainer 类。与静态加权损失函数不同，Focal Loss 在训练过程中自适应地降低简单样例的权重。这帮助模型专注于具有挑战性的样本，显著提升了那些出现频率较低或更难检测的类别的表现。
- **专门配置** – 我们为每个类别概率添加了可配置的类别阈值（例如 0.1 到 0.8），以决定标签分配，因为我们观察到在不同决策边界下性能存在差异。

这一方法使我们的系统能够在一次推理中识别多种敏感数据类型。

### 超参数优化

为了给我们的模型找到最优配置，我们使用 Optuna 优化关键参数。Optuna 是一个开源的超参数优化（HPO）框架，它通过运行大量实验（称为*试验*）来帮助为给定的机器学习（ML）模型找到最佳超参数。它使用一种称为 Tree-structured Parzen Estimator（TPE）的贝叶斯算法，根据过往结果选择有希望的超参数组合。

搜索空间探索了大量关键超参数组合，如下表所列。

| **超参数 ** | **范围** |
| --- | --- |
| 学习率 | 5e-6–5e-5 |
| 权重衰减 | 0.01–0.5 |
| 预热比例 | 0.0–0.2 |
| Dropout 率 | 0.1–0.5 |
| 批大小 | 16, 24, 32 |
| 梯度累积步数 | 1, 4 |
| Focal loss gamma（仅多标签） | 1.0–3.0 |
| 类别阈值（仅多标签） | 0.1–0.8 |

为了优化计算资源，我们实现了剪枝逻辑，提前终止表现不佳的试验，从而可以丢弃次优的配置。如下面的 Optuna HPO 历史图所示，试验 42 在二元分类上拥有最优参数和最高 F1 分数，而试验 32 在多标签分类上最为最优。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-optimisation-history-plot-1.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-optimisation-history-plot-1.png)

此外，我们的分析显示 dropout 和学习率是最重要的超参数，分别占二元分类模型 F1 分数方差的 48% 和 21%。这解释了我们为何在此前的运行中观察到模型迅速过拟合，也凸显了正则化的重要性。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-hyperparameter-importance-1.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-hyperparameter-importance-1.png)

经过优化实验后，我们发现了以下几点：

- 我们能够为每项任务确定最优超参数
- 模型在训练中收敛得更快
- 最终的绩效指标相比我们手工测试的配置显示出可测量的提升

这使我们的模型能够以自动化方式运行超参数调优，从而高效地获得较高的 F1 分数，这对生产部署至关重要。

## 负载测试与自动扩缩容策略

在完成微调并将优化后的模型部署到 SageMaker 实时端点后，我们执行了负载测试，以验证其性能以及在压力下的自动扩缩容能力，从而满足 Harmonic Security 对延迟、吞吐量和弹性的需求。负载测试的目标是：

- 验证在不同负载下的延迟 SLA：平均值低于 500 毫秒，P95 约为 1 秒
- 确定在延迟 SLA 范围内使用 ml.g5.4xlarge 实例时的最大 RPM 吞吐容量
- 为自动扩缩容策略的设计提供依据

方法包括以下内容：

- **流量模拟** – 使用 Locust 模拟具有不同文本长度（50–9,999 个字符）的并发用户流量
- **负载模式** – 我们执行了阶梯式爬坡测试（60–2,000 RPM，每档 60 秒），识别瓶颈并对极限进行压力测试

如下图所示，我们发现延迟在 1 秒以内的最大吞吐量为 1,185 RPM，因此我们决定把自动扩缩容阈值设为该值的 70%，即 830 RPM。

[![ModernBERT M&A 分类器在不同吞吐率下的延迟表现及 SLA 阈值](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-load-testing.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-load-testing.png)

基于负载测试中观察到的性能，我们使用 Application Auto Scaling 为 SageMaker 端点配置了目标跟踪式自动扩缩容策略。下图展示了该策略的工作流。

[![含流量阈值与实例管理的 AWS SageMaker 端点自动扩缩容示意图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-auto-scaling.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/13/ML-18972-auto-scaling.png)

定义的关键参数为：

- **指标** – `SageMakerVariantInvocationsPerInstance`（830 次调用/实例/分钟）
- **最小/最大实例数** – 1–5
- **冷却时间** – 扩容 300 秒，缩容 600 秒

这种目标跟踪策略根据流量调整实例，从而保持性能和成本效益。下表汇总了我们的发现。

| **模型** | **每分钟请求数** |
| --- | --- |
| 8B 模型 | 800 |
| 启用自动扩缩容的 ModernBERT（5 个实例） | 1,185-5925 |
| **额外容量（ModernBERT 对比 8B 模型）** | **48%-640%** |

## 结果

本节展示微调与优化工作对 Harmonic Security 数据泄露检测系统的显著影响，重点是实现大幅的延迟降低。首先详述绝对延迟的改进，以说明达成低于 500 毫秒目标的情况，随后给出性能提升的概览。以下小节提供 M&A 二元分类以及跨多种敏感数据类型的多标签分类的详细结果。

### 二元分类

我们把用于 M&A 二元分类的微调 ModernBERT-base 模型与方案概览中介绍的 8B 基线模型进行了评估对比。最引人注目的成果是延迟的变革性降低，解决了最初 1–2 秒延迟可能干扰用户体验的问题。这一跃升至低于 500 毫秒延迟的情况详见下表，标志着系统响应能力的关键提升。

| 模型 | median_ms | p95_ms | p99_ms | p100_ms |
| --- | --- | --- | --- | --- |
| Modernbert-base-v2 | 46.03 | 81.19 | 102.37 | 183.11 |
| 8B 模型 | 189.15 | 259.99 | 286.63 | 346.36 |
| **差值** | **-75.66%** | **-68.77%** | **-64.28%** | **-47.13%** |

在这一延迟突破的基础上，以下绩效指标反映了准确率和 F1 分数的百分比提升。

| **模型** | **准确率提升** | **F1 提升** |
| --- | --- | --- |
| ModernBERT-base-v2 | **+1.56%** | **+2.26%** |
| 8B 模型 | – | – |

这些结果表明，ModernBERT-base-v2 带来了突破性的延迟降低，并辅以 1.56% 和 2.26% 的适度准确率与 F1 提升，这与 Harmonic Security 在不影响用户体验的前提下增强数据泄露检测的目标相一致。
