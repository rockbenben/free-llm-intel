# Amazon Bedrock AgentCore 运行时快速会话启动的架构模式

如今，代理人员会审查代码、处理索赔并在无人值守的情况下运行数小时。许多人还坐在互动体验后面，等待第一反应。 [Amazon Bedrock AgentCore 运行时](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 为这些代理提供了完全托管的无服务器环境：每个会话都在自己的隔离 microVM 中运行，当没有工作时，平台会扩展到零，并且您只需为会话消耗的资源付费。

[AgentCore 运行时](https://aws.amazon.com/blogs/machine-learning/the-new-agentcore-runtime-elastic-optimized-and-consistly-fast-starts/) 将“platformVersion”设置为“V2”会更改会话的启动方式。它不是为每个会话初始化容器，而是准备一次环境，为其创建快照，然后为每个新会话恢复该快照。会话开始时间更快且更一致。 V2 还会回收您的会话不使用的内存，因此您的账单会跟踪代理使用的内存。

对于大多数代理来说，切换到 V2 就足够了。一些代理需要重组才能获得全部好处，对于聊天和语音体验来说，即使 2 秒也太慢了。这篇文章解释了 V2 如何启动会话、如何测量会话开始时间以及如何让第一个请求不再工作，包括 AgentCore 运行时现在支持的构建挂钩。我们涵盖四种模式，从更改代理代码到在用户需要之前启动会话。

## 您需要哪种模式？

| **您的情况** | **做什么** | **部分** |
| --- | --- | --- |
|大约 2 秒内完成新会话就可以了 |切换到 V2 并在 `app.run()` 之前完成所有初始化 |让工作远离第一个请求 |
|您的代理需要早期的大文件、CLI 或浏览器，并且无法将它们保留在进程中 |添加构建挂钩以在构建快照时加载并启动它们 |使用钩子 |
|您需要亚秒级的时间，用户在发送第一个请求（打开应用程序或聊天窗口）之前就参与进来 |当用户参与时在后台启动会话 |预热用户参与度 |

## V2 如何启动会话

AgentCore 运行时在新的 microVM 中运行每个会话。在 V1 上，AgentCore 从 Amazon Elastic Container Registry (Amazon ECR) 中提取容器映像、启动容器并运行初始化代码，然后才能处理第一个请求。镜像拉动占主导地位，因此冷启动随着镜像大小而增长。

V2 只做一次这样的工作。当您创建或更新运行时时，AgentCore 运行时会在新的 microVM 中启动容器并等待第一个正常的 ping (`GET /ping`)，该 ping 必须在 120 秒内到达。然后，它会清除操作系统的文件缓存，以保持快照较小，冻结 microVM，并将其内存和磁盘存储为快照。

**这是对 V1 的更改：在构建快照时，每次创建或更新现在都需要几分钟**。

在这篇文章中，**init** 意味着您的代理在“/ping”报告健康之前所做的一切。对于 AgentCore Python SDK，这就是“app.run()”之前的所有内容。如果您使用“Node.js”或其他语言运行自己的 HTTP 服务器，则仅在初始化完成后报告运行状况良好。

当新会话到达时，AgentCore 将快照恢复到新的 microVM 中。您的流程将在其被冻结的位置准确恢复，其导入、对象和客户端均就位。图像中的文件是延迟加载的：会话第一次读取每个块时都会获取它。

![调用流程，其中每个新会话将快照恢复到新的 microVM，进程恢复，并且首先获取图像文件阅读](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/13/ML-22099-2.png)

图 2：每个新会话都调用

从这些流程中可以得出三个事实，本文的其余部分也以此为基础：

- **内存完整恢复。** 进程在快照时保存的任何内容，以及 RAM 支持的文件系统（例如“/dev/shm”）中的任何内容，都可以从第一次访问时以内存速度使用。
- **文件读取不会延续。** 文件缓存在冻结之前被清除，因此在 init 期间读取文件不会使其在恢复的会话中速度更快。
- **图像文件在第一次读取时获取。** 块的第一次读取来自快照存储，然后缓存在靠近主机的位置。

下表显示了这对于典型代理所做的工作意味着什么，具体取决于其工作地点：

| **工作** | **在初始化期间完成** | **在处理程序中完成** |
| --- | --- | --- |
|导入库 |会话开始时在内存中 |在每个新会话中读取图像 |
|创建客户端（例如“boto3”）|已完成端点和凭证解析的恢复。套接字在首次使用时重新连接 |在每个新会话中从头开始构建 |
|打开网络连接 |恢复后就失效了。在快照之前关闭它们 |新鲜开封|
|从图像加载静态数据并将其保存在对象中 |会话开始时在内存中 |在每个新会话中读取图像 |
|从图像中读取文件而不保留数据 |没有效果，因为文件缓存被清除了 |在每个新会话中读取图像 |

如果您了解 AWS Lambda SnapStart，您会感觉很熟悉。 Marc Brooker 关于 SnapStart 如何加载快照的帖子和 SnapStart 启动策略帖子是有用的背景。

表中的所有内容均假设您的代理可以在自己的流程中保留其所需的内容。这并不总是可能的。作为单独进程运行并退出的 CLI，或浏览器二进制文件，会在 init 期间读取，然后消失，因此恢复的会话会再次从映像中获取它。对于这些情况，您可以添加构建钩子，如“使用钩子”中所述。图 3 显示了它的运行位置。

## 优化之前先进行测量

代理应用程序中的延迟不是一个数字。请求花费时间在 AgentCore 运行时让会话准备好运行您的代码，然后在您的代码中花费时间：模型调用、工具调用、子代理以及流式传输响应。您可以通过不同的方式解决这些问题，因此首先要找出哪种方式占主导地位。

AgentCore 运行时将两者发布为“AWS/Bedrock-AgentCore”命名空间中的 [Amazon CloudWatch 指标](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-runtime-metrics.html)。 “延迟”是到达第一个字节的时间。 `OverheadLatency` 是属于平台的部分，例如启动 microVM 并在新会话上恢复快照。

| **你想要什么** | **如何获得** |
| --- | --- |
| TTFB（第一个字节的时间）| `延迟` |
|运行时间| `开销延迟` |
|你的代码时间 | `延迟` - `开销延迟` |
|初始化时间 |在启动时在代码中测量（请参阅以下示例）。它不是 V2 上任何请求的一部分 |

Init 不会出现在这些指标中，因为在 V2 上，它在构建快照时运行一次，而不是在每个会话中运行。它增加了创建或更新达到就绪状态所需的时间，而不是请求延迟。要查看需要多长时间，请在“app.run()”之前记录一次。该行出现在运行时的构建日志中：
```
import time
INIT_START = time.time()  # first line of your module
# imports, clients, data loading ...
print(f"init_ms={round((time.time() - INIT_START) * 1000)}")
app.run()
```
如何阅读拆分：

- **新会话上的高“OverheadLatency”：**时间是在会话开始时。使用本文后面的模式在用户需要之前启动会话。
- **您的代码在同一会话中第一个请求的时间比第二个请求的时间要长得多：** 属于 init 的工作正在您的处理程序中运行。在 AgentCore Observability（Amazon Bedrock AgentCore 的一项功能）中围绕工具设置、文件加载和后期导入添加自定义跨度以找到它，然后将其移动到 init 中。

报告百分位（例如 P90 和 P99），或修剪平均值（例如 TM90），它对最快的 90% 请求进行平均并丢弃最慢的尾部。简单的平均值隐藏了缓慢的请求。 “OverheadLatency”涵盖了对正在运行的会话和新会话的请求，因此其分布取决于有多少请求启动新会话。将运行与类似的组合进行比较。

按照您在生产中预期的新会话速率进行测试，而不是在部署后使用少量会话进行测试。

要包括客户端的网络时间，还要在客户端上进行测量。对调用进行计时，让处理程序返回运行的时间，然后减去。两个时间戳都来自同一台机器，因此客户端和 microVM 之间的时钟差异并不重要。如果进行流式传输，非常小的事件可以被保留，直到数百字节的输出建立起来，因此第一个事件的时间可以读取高于会话开始的时间。

## 让工作远离第一个请求

通常的冷启动建议是延迟导入并保持初始化较小。在 V2 上，执行相反的操作：在构建快照时 init 运行一次，并且延迟到处理程序的工作由每个新会话支付。这适用于*静态*工作：导入、客户端和图像中的数据。动态数据无法快照。下一节将介绍它。

**最引人注目的代理**是在请求时从图像中读取大文件的代理：小型本地模型的权重、嵌入、数据集、大型库、用于自动化的浏览器二进制文件或编码代理作为子进程运行的 CLI 工具链。读取许多小文件，就像编译 TypeScript 项目一样，具有相同的效果。导入一些库并调用托管模型的代理主要需要正确地导入和客户端。

### 如何重组你的代理人

**在 init 期间创建对象，而不仅仅是导入。** 创建对象会加载它所依赖的模块并将它们保留在活动内存中。也在 init 期间初始化使用外部库的本地工具，而不是在代理首次调用它们时。

**在初始化期间创建客户端。** 端点解析、凭证解析和客户端模块都会随快照返回。套接字不会，但“boto3”客户端会在第一次调用时干净地重新连接。其他一些网络客户端首先尝试过时的套接字，这会增加数百毫秒的时间，因此请在快照之前关闭其连接。

**将静态数据保留在内存中**，例如提示、技能前言、配置和小索引。将数据保存在对象中，而不仅仅是读取它：
```
INDEX = pathlib.Path("/opt/data/index.bin").read_bytes()  # during init: keep the bytes
```
**保持工具运行，而不是根据请求启动它们。** 在处理程序中启动的子进程在每个新会话中从图像中读取其二进制文件和库。在 init 期间启动的长时间运行的帮助程序（例如语言服务器或完成导入的工作进程）将作为进程内存的一部分返回。通过管道或套接字与它交谈。

**将无法保存在内存中的文件复制到 RAM 支持的磁盘中。** 像“tsc”这样的工具链作为单独的程序运行，读取自己的文件。在初始化期间将它们复制到“/dev/shm”或 ramfs 挂载，以便它们的读取来自内存。

**发送已编译的字节码。** `uv pip install` 默认情况下不会编译，因此后期导入也会从源代码进行编译。设置“UV_COMPILE_BYTECODE=1”或使用“pip install --compile”。

下面的示例在 init 期间构建代理、其模型及其客户端，因此每个会话都会继承它们：
```
import json, pathlib
import boto3
import pandas as pd  # import during init, including rarely used libraries
from strands import Agent
from strands.models import BedrockModel
from bedrock_agentcore.runtime import BedrockAgentCoreApp

MODEL_ID = "us.anthropic.claude-haiku-5-5"

# Init: runs once, before the snapshot. Every new session inherits these objects.
PROMPTS = json.loads(pathlib.Path("prompts.json").read_text())
ddb = boto3.client("dynamodb")
agent = Agent(model=BedrockModel(model_id=MODEL_ID), system_prompt=PROMPTS["system"])

app = BedrockAgentCoreApp()

@app.entrypoint
def invoke(payload):
    return agent(payload["prompt"])

app.run()  # /ping answers only after this line
```
**权衡：**新会话上第一个字节的时间是启动 microVM 和恢复快照的时间，加上处理程序所花费的时间。将工作移入 init 会缩短处理程序，但内存中保存的任何内容都会使快照更大。您还需要为每次会话中保留的内存付费。测量更改之前和之后的端到端会话启动，以便您知道您已经减少了延迟，而不仅仅是将其从处理程序移至恢复。

### 参考卡

| **数据** | **方法** |
| --- | --- |
|第一次请求需要大文件，例如模型、CLI 或浏览器 |在初始化期间将它们保存在内存中，或者使用构建钩子来启动它们 |

|会话创建的文件 |无需改变 |

### 使用钩子

构建钩子构建于 init 之上，但不会取代它。在 init 中尽你所能，并使用 hook 来处理 init 无法覆盖的内容。您在容器中公开 HTTP 端点，AgentCore 运行时在构建运行时时向其发送两次“POST”请求：

- **快照之前。** 在构建 microVM 上，代理报告运行状况之后且冻结之前。您的代理在此处加载并保留在内存中的任何内容都是快照的一部分，因此每个会话都以此开始。
- **测试恢复后。** 在恢复快照以进行检查的单独 microVM 上。这次通话中没有任何内容被快照。使用它来读取您的会话将需要的文件，这决定了恢复的会话首先获取的内容。

“X-Amzn-Bedrock-AgentCore-Runtime-Warmup-Type”标头告诉您的代理正在处理哪个调用：第一个为“内存”，第二个为“磁盘”。这两个调用共享 120 秒，因此无论“内存”调用离开什么时间，“磁盘”调用都会得到。仅在工作完成后返回“2xx”响应。任何其他响应、连接失败或超时都会导致创建或更新失败，并且 AgentCore 运行时不会重试。运行时日志组中的“build-logs-”流显示哪个调用失败以及原因。

挂钩在 V2 运行时可用。创建或更新运行时时使用“hooksConfiguration”配置它们：
```
client = boto3.client("bedrock-agentcore-control")
client.create_agent_runtime(
    agentRuntimeName="my_agent",
    agentRuntimeArtifact={"containerConfiguration": {"containerUri": IMAGE_URI}},
    roleArn=ROLE_ARN,
    networkConfiguration={"networkMode": "PUBLIC"},
    platformVersion="V2",
    hooksConfiguration={
        "build": {
            "warmup": {
                "action": {"httpPost": {"path": "/warmup", "port": 8080}}
            }
        }
    },
)
```
该端口是可选的，默认为代理的服务端口。如果设置，请使用平台未保留的 8000 至 12000 端口。该路径无法与 AgentCore 运行时已在该端口上使用的路由匹配，例如“POST /incalls”或“GET /ping”。 `UpdateAgentRuntime` 替换了整个钩子配置，因此在每个要保留钩子的更新中包含 `hooksConfiguration` 。

在代理中，处理同一端点上的两种调用类型：
```
import asyncio
from fastapi import FastAPI, Request, Response

app = FastAPI()

# Files that each session reads when it starts.
STARTUP_FILES = ["/app/models/tokenizer.json", "/app/config/agent.json"]

def load_shared_state():
    # Load what every session needs into memory, such as heavy imports,
    # model weights, and caches.
    ...

def read_startup_files():
    # Read the files that a session reads when it starts, so that new
    # sessions can use them faster.
    for path in STARTUP_FILES:
        with open(path, "rb") as f:
            while f.read(1024 * 1024):
                pass

@app.get("/ping")
def ping():
    return {"status": "Healthy"}

@app.post("/warmup")
async def warmup(request: Request):
    # Header lookup in Starlette and FastAPI is case-insensitive.
    warmup_type = request.headers.get(
        "X-Amzn-Bedrock-AgentCore-Runtime-Warmup-Type", ""
    ).lower()
    # Run the work in a worker thread so that /ping keeps answering.
    if warmup_type == "memory":
        await asyncio.to_thread(load_shared_state)
    elif warmup_type == "disk":
        await asyncio.to_thread(read_startup_files)
    # Respond only after the work is done.
    return Response(status_code=200)

@app.post("/invocations")
async def invoke(request: Request):
    payload = await request.json()
    # Per-request work runs here on every session.
    return {"response": payload.get("prompt", "")}
```
有关完整配置参考，请参阅[为 AgentCore 运行时配置生命周期挂钩](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-lifecycle-hooks.html)。有关完整的代码示例，请参阅[示例代码](https://github.com/evandrofranco/agentcore-samples/tree/main/01-features/02-host-your-agent/01-runtime/03-advanced/17-strands-decider-hooks)。

## 快照陷阱：什么必须保留在处理程序中

在 init 期间创建的所有内容都将冻结到快照中，直到下次部署为止，并且每个会话都以相同的副本开始。对于大多数物体来说，这就是重点。对于下面的值，这是一个错误，对于随机值，这是一个安全问题。

**在处理程序中加载动态数据，每个会话一次。** 来自 AgentCore Gateway（Amazon Bedrock AgentCore 的一项功能）的工具目录、功能标志和价格列表在部署后会发生变化。将它们加载到处理程序中并在模块级别缓存它们，因此每个会话都会获取它们一次。会话最多可以持续 8 小时，因此请给缓存一个过期时间：
```
_tools, _loaded_at = None, 0.0

def get_tools():
    global _tools, _loaded_at
    if _tools is None or time.time() - _loaded_at > 300:  # wall clock: refresh after 5 minutes
        _tools, _loaded_at = load_gateway_tools(), time.time()
    return _tools
```
从处理程序调用“get_tools()”并将结果传递给您在初始化期间创建的代理。

**在处理程序中创建每个会话的值。**

| **价值** | **在哪里创建它** | **为什么** |
| --- | --- | --- |
|随机值、随机数、秘密、密钥 |在处理程序中，使用 `secrets`、`os.urandom()` 或 `uuid.uuid4()` |在初始化期间创建的库随机状态（Python 的“随机”、NumPy）在每个会话中都是相同的。来自操作系统的值是唯一的 |
|当前和经过的时间 |在处理程序中，使用 `time.time()` |初始化时间戳在快照时间是固定的，并且“time.monotonic()”不计算快照存储所用的时间 |
|定时器、速率限制器、TTL 缓存 |使用挂钟时间，或在第一次请求时重置它们 |任何用单调时钟测量经过时间的东西在恢复过程中几乎看不到间隙|
|您自己获取的凭证和令牌 |过期时刷新它们 |在初始化期间加载的值可能会在会话开始之前过期 |

**了解限制。** 当会话的空闲超时到期（“idleRuntimeSessionTimeout”：默认情况下为 15 分钟，从 60 秒到 8 小时）、达到其最大生命周期（“maxLifetime”：默认情况下最多为 8 小时）或停止会话时，会话就会结束。

## 亚秒级：在用户需要之前启动会话

假设您的新会话需要大约 2 秒才能启动，包括前面几节中介绍的所有计时细目。已经运行的会话将在大约 200 毫秒内给出答案。对于聊天或语音体验，亚秒级的方法是确保会话在用户的第一个请求到达之前已开始。有两种方法可以做到这一点。

### 预热用户参与度

大多数交互式应用程序都会在第一个提示之前收到信号：用户打开应用程序、聊天窗口或支持页面。使用它。生成会话 ID，在后台向代理发送预热请求，并将会话 ID 与对话一起保留。当用户输入第一条消息时，会话就开始运行。
```
# Backend, when the user opens the chat (don't block the UI on it)
session_id = f"chat-{uuid.uuid4().hex}"  # session IDs need at least 33 characters
agentcore.invoke_agent_runtime(agentRuntimeArn=ARN, runtimeSessionId=session_id,
                               payload=json.dumps({"action": "prime"}).encode())
save_conversation(user_id, session_id)  # every later turn reuses this session ID

# Agent handler: answer the warm-up before any model call
@app.entrypoint
def invoke(payload):
    if payload.get("action") == "prime":
        return {"primed": True}
    return agent(payload["prompt"])
```
此模式不需要额外的基础设施，并且只要用户发送第一条消息的时间超过 2 秒，就会完全隐藏会话启动。每个参与但从未发送提示的用户都会花费一个会话时间。较短的空闲超时可以保持较小的值。

## 结论

在 V2 上，AgentCore 运行时将启动会话的大部分工作移至部署时间。您的容器启动一次，每个新会话都会恢复结果：内存全部恢复，并且在第一次读取时获取文件。

为了使会话启动时间保持在 2 秒左右，请在 init 期间执行静态工作，将第一个请求所需的数据保存在内存中，并在处理程序中保存动态值和每个会话值。对于您的进程无法容纳的文件，请添加构建挂钩。为了缩短一秒钟的时间，请在用户需要之前启动会话：当您收到信号时，在用户参与时启动会话。

首先，请在创建或更新运行时时将“platformVersion”设置为 V2，然后查看[针对 AgentCore 运行时 V2 优化代理](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-v2-optimize.html)。有关您的工作负载的问题，请联系您的 AWS 客户团队。
