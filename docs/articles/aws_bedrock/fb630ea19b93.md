# 使用 Strands Agents 构建自适应 agentic 智能框架

构建 AI agent 的组织面临一个共同的挑战：每一个请求，无论是例行的状态检查还是复杂的分析，通常都会被路由到单个大型、昂贵的模型。这种一刀切的做法会推高 API 成本、引入不可预测的延迟，并使离线运行成为不可能。即便是本可在本地解决的例行查询，最终也要经历一次到云端托管的 large language model（LLM）的完整网络往返。

用 Strands Agents 构建的 Adaptive Agentic Intelligence Framework（AAIF）采取了不同的做法。AAIF 不把所有请求都路由到单个大型模型，而是用 small language model（SLM）在本地处理例行任务。更复杂的请求则通过 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 路由到云端托管的模型。这一做法建立在 [NVIDIA 的 Belcak 等人](https://arxiv.org/abs/2506.02153)提出的研究立场之上。他们认为，small language model“对 agentic 系统中的许多调用而言已经足够强大、本质上更合适，而且必然更经济”。该框架基于 Strands Agents 构建，展示了智能模型编排如何帮助降低成本，同时为本地操作维持低延迟。

在本文中，我们逐步介绍 AAIF 的关键组件：通过 Ollama 使用本地 SLM，并通过 Amazon Bedrock 使用云端模型。我们以物联网（IoT）监控场景作为参考实现。

## 解决方案概览

AAIF 将 AI 处理组织为三个层，每一层针对不同的任务类型进行优化，如图 1 所示：

- 智能编排使用一个轻量级 SLM（llama3.2:1b）作为决策层。该编排器对传入的请求进行分类，并将它们路由到合适的处理层，而无需硬编码规则。
- 本地处理使用通过 [Ollama](https://ollama.com/) 运行在本地硬件上的 SLM，处理设备遥测数据获取和图像分析等例行任务。这些任务以低延迟完成，且不依赖云端。
- 云端处理通过 Amazon Bedrock 中的前沿模型处理复杂的模式分析和战略建议。这些请求需要更广泛的上下文和多步推理，而 SLM 无法可靠地提供。

![AAIF three-layer architecture with an SLM orchestrator routing requests to local processing tools or to Amazon Bedrock cloud processing](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/20/ML-19699-1.png)

图 1：AAIF 用于智能编排、本地处理和云端处理的三个处理层

图 1 展示了完整的 AAIF 系统架构。位于中心的是 Strands agent，它连接到 Ollama 运行时，该运行时同时托管 1B 参数的编排器模型和视觉模型。该 agent 暴露了三个工具：用于获取本地传感器数据的 get_device_telemetry、用于通过 llama3.2-vision 进行设备端视觉处理的 analyze_camera_feed，以及通过 boto3 调用 Amazon Bedrock 以完成复杂分析的 get_expert_insights。传入的用户请求流经 SLM 编排器，由它分类每个请求，并根据任务复杂度将其分派到本地工具或云端端点。

![Strands agent connected to an Ollama runtime and three tools, with get_expert_insights calling Amazon Bedrock](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/20/ML-19699-2.jpg)

该框架会适应你的部署约束，而不是要求你围绕它重构基础设施。这一架构可以运行在诸如 8 GB 内存的 Raspberry Pi 之类的边缘设备上，可以运行在所有推理都打到 Amazon Bedrock 的完整云部署中，也可以运行在把本地速度与云端推理相结合的混合配置中。这种灵活性来自把路由逻辑（SLM 编排器）与处理工具分离，你可以根据可用的硬件和网络连接情况，独立地替换或重新配置这些工具。

## 先决条件

在本次演练中，你应具备以下先决条件：

- 一个 [AWS 账户](https://portal.aws.amazon.com/gp/aws/developer/registration/index.html)。
- 在所需 Region 中配置好 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 模型访问权限。
- 已安装 [Python 3.10+](https://www.python.org/downloads/)。
- 已安装 [Ollama](https://ollama.com/)，并拉取以下模型： `ollama pull llama3.2:1b`（编排器）。`ollama pull llama3.2-vision`（视觉分析）。
- 已安装 [Strands Agents](https://strandsagents.com/latest/)：`pip install strands-agents strands-agents-tools`。
- 已配置好合适凭证的 [AWS Command Line Interface（AWS CLI）](https://aws.amazon.com/cli/)。
- 已安装 [Boto3](https://boto3.amazonaws.com/v1/documentation/api/latest/index.html)：`pip install boto3`。

## 实现本地处理工具

Strands Agents 使用 `@tool` 装饰器来定义 agent 可以调用的能力。首先创建用于本地处理的工具。

第一个工具用于获取设备遥测数据。在生产环境中，它会连接到实际的 IoT 传感器。在本次演练中，它使用的是模拟的设备数据：

```
from strands import Agent, tool
import random

DEVICE_TELEMETRY = {
    "sensor-001": {
        "device_type": "Temperature Sensor",
        "location": "Building A - Floor 2",
        "temperature": 72.5,
        "humidity": 45.2,
        "status": "normal"
    },
    "camera-001": {
        "device_type": "Security Camera",
        "location": "Main Entrance",
        "fps": 30,
        "resolution": "1080p",
        "status": "recording"
    },
    "hvac-001": {
        "device_type": "HVAC Controller",
        "location": "Building A - Central",
        "set_temp": 71.0,
        "current_temp": 72.5,
        "mode": "cooling",
        "status": "active"
    }
}

@tool
def get_device_telemetry() -> str:
    """Retrieve current telemetry data from connected IoT devices."""
    device_id = random.choice(list(DEVICE_TELEMETRY.keys()))
    device_data = DEVICE_TELEMETRY[device_id]

    report = f"Device: {device_id} ({device_data['device_type']})\n"
    report += f"Location: {device_data['location']}\n"
    report += f"Status: {device_data['status']}\n"
    for key, value in device_data.items():
        if key not in ['device_type', 'location', 'status']:
            report += f"{key}: {value}\n"
    return report
```

第二个工具使用本地 SLM 执行视觉分析。llama3.2-vision 模型完全运行在本地硬件上，这意味着敏感的摄像头画面不会离开设备：

```
import ollama

@tool
def analyze_camera_feed(image_path: str) -> str:
    """Analyze visual data from cameras using local vision model."""
    stream = ollama.chat(
        model='llama3.2-vision',
        messages=[{
            'role': 'user',
            'content': 'Describe this image in one sentence. '
            'What are the 3 most important things you see?',
            'images': [image_path]
        }],
        stream=True,
    )

    full_response = ""
    for chunk in stream:
        chunk_content = chunk['message']['content']
        print(chunk_content, end='', flush=True)
        full_response += chunk_content

    return f"Object Detection Report:\n{full_response}"
```

## 实现云端处理

对于需要更广泛推理的复杂分析，创建一个调用 Amazon Bedrock 的工具。只有当编排器判定本地模型无法处理该请求时，才会调用这个工具：

```
import boto3

@tool
def get_expert_insights(context_data: str, question: str) -> str:
    """Get advanced analysis and expert recommendations
    for complex questions via Amazon Bedrock."""
    client = boto3.client("bedrock-runtime", region_name="us-east-1")

    conversation = [
        {
            "role": "user",
            "content": [
                {"text": f"Context: {context_data}\n\nQuestion: {question}"}
            ],
        }
    ]

    response = client.converse(
        modelId="<<model_id>", //Refer model id [details](https://docs.aws.amazon.com/bedrock/latest/userguide/foundation-models-reference.html)
        messages=conversation,
        inferenceConfig={
            "maxTokens": 512,
            "temperature": 0.5,
            "topP": 0.9
        }
    )

    response_text = response["output"]["message"]["content"][0]["text"]
    return f"Expert Analysis:\n{response_text}"
```

## 配置具备智能编排能力的 Strands agent

AAIF 的核心是 Strands agent 的配置。该 agent 使用本地 SLM（llama3.2:1b）作为其编排器。Strands Agents 支持多种模型提供方，这里我们使用 Ollama 提供方在本地运行编排器：

```
from strands.models.ollama import OllamaModel

model = OllamaModel(
    model_id="llama3.2:1b",
    host="http://localhost:11434",
    params={
        "max_tokens": 300,
        "temperature": 0.3,
    },
)

system_prompt = """You are a monitoring assistant for operational facilities.
You have access to device telemetry tools, analysis capabilities,
and expert insights to help monitor operations effectively.

When users ask for:
- Device status or telemetry: use get_device_telemetry
- Image or data analysis: use analyze_camera_feed
- Expert advice or complex questions: use get_expert_insights

Always return the complete tool results directly to the user."""

agent = Agent(
    model=model,
    system_prompt=system_prompt,
    tools=[
        get_device_telemetry,
        analyze_camera_feed,
        get_expert_insights,
    ],
)
```

由 SLM 驱动的编排器会分析每个请求，并将其路由到合适的工具，而无需硬编码的关键词匹配。路由是通过模型对请求的理解来完成的：

| **请求** | **路由** | **延迟** |
| --- | --- | --- |
| “检查设备状态” | 本地 SLM | 低（本地推理） |
| “分析这张图像” | 本地视觉 AI | 低（本地推理） |
| “你推荐哪些优化策略？” | 云端（Amazon Bedrock） | 较高（网络往返） |

*表 1：本地推理与云端推理的请求、路由和延迟估计*

## 运行 agent

配置好 agent 之后，你可以直接与它交互：

```
# Local processing - device telemetry
response = agent("What's the current status of our devices?")
print(response)

# Local processing - vision analysis
response = agent("Analyze the camera feed from camera-001")
print(response)

# Cloud processing - complex analysis
response = agent(
    "Based on current telemetry patterns, "
    "what optimization strategies do you recommend?"
)
print(response)
```

agent 会自动对每个请求进行分类，并将其路由到合适的处理层。无需任何显式的路由规则。

## 适应不同的部署场景

AAIF 架构通过更改模型配置来适应不同的基础设施需求：

当你的工作负载完全运行在云端、且没有可用的边缘硬件时，可将 Ollama 模型配置替换为 Amazon Bedrock 来处理所有任务。这样每个请求都会走托管的云端推理，让你无需本地 GPU 资源即可获得自动扩缩容能力。拥有可靠的低延迟连接且不受数据驻留限制的团队最能从这种配置中受益：

```
from strands.models import BedrockModel

model = BedrockModel(
    model_id="<<model_id>", //Refer model id [details](https://docs.aws.amazon.com/bedrock/latest/userguide/foundation-models-reference.html)
    region_name="us-east-1"
)
```

混合配置在保留本地 SLM 编排器的同时，为超出本地模型能力的请求增加云端模型。这就是本次演练中展示的默认 AAIF 配置。它适合这样的环境：大多数请求足够常规，可以在本地解决，但有些请求需要更大模型进行更广泛的推理。成本节省可以来自大约 80% 不会打到付费 API 端点的流量。

对于完全物理隔离（air-gapped）或具有严格数据主权要求的环境，可将云端工具替换为一个更大的本地模型，并在设备上运行所有处理。一个 3B 参数模型运行在内存充足的硬件上，可以处理 1B 编排器原本会升级到云端的中等复杂度任务。代价是在最困难的查询上推理深度有所降低，但好处是数据不会离开本地：

```
model = OllamaModel(
    model_id="llama3.2:3b", # Larger local model for complex tasks
    host="http://localhost:11434",
)
```

## 展望未来：通过 MCP server 实现集中式工具调用

本文中的实现使用的是直接在 agent 代码中定义的本地工具调用。对于有多个 agent 跨服务共享工具的生产部署，可将这些工具暴露为 Model Context Protocol（MCP）server。MCP 提供了用于工具发现和调用的标准化接口，因此你可以集中管理工具，并在不同的 agent 和环境之间复用工具。在图 3 中，我们展示了如何把 AAIF 的工具转换为 MCP server，以实现分布式的集中式工具调用。

如图 3 所示的分布式配置中，Device 1 充当编排中枢，运行带有 SLM 路由器和本地遥测工具的 Strands agent。它通过 MCP 协议连接到 Device 2，后者运行着一个带 llama3.2-vision 的边缘视觉处理服务器。Device 3 充当连接到 Amazon Bedrock 的云端分析网关。从编排器的角度看，所有远程工具都表现为本地函数调用，因为 MCP 传输层会透明地处理序列化和网络通信。

## 清理

为避免产生未来费用，请完成以下清理步骤：

- 禁用 Amazon Bedrock 模型访问权限：打开 Amazon Bedrock 控制台，选择 **Model access**，并撤销对 Amazon Nova Lite 的访问权限。详细步骤请参阅 Amazon Bedrock 用户指南中的 [Manage model access](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html#model-access-modify)。
- 停止 Ollama 服务器并移除模型以释放本地磁盘空间（约 2 GB）： `ollama stop ollama rm llama3.2:1b ollama rm llama3.2-vision`
- 如果你不再需要示例代码，请删除项目目录： `rm -rf aaif-demo`

## 结论

我们展示了如何使用 Adaptive Agentic Intelligence Framework 和 Strands Agents 构建高性价比的 AI agent。通过把例行请求路由到本地 SLM，并把 Amazon Bedrock 上的云端模型保留给复杂分析，AAIF 可以帮助降低 API 成本，同时为例行操作维持低延迟。

在生产环境中运行这一模式之前，请为云端推理路径添加负责任的 AI 控制措施，因为这些请求会携带工具输出、检索到的数据和用户输入。你可以通过 guardrail ID 和版本，把 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 挂到 Strands BedrockModel 上。它随后会应用针对有害类别的内容过滤器、提示注入过滤器和上下文 grounding 检查，阻止缺乏源数据支撑的响应。若要对本地 SLM 层应用同样的策略，可对其输入和输出调用独立的 ApplyGuardrail API。这样一来，无论由哪个模型处理，每个请求都遵循同一套安全标准。

这一架构模式并不限于 IoT 监控。一家医疗健康机构可以在本地运行患者监控，同时把诊断支持路由到云端模型。一家金融服务公司可以在本地处理交易，并把云端容量保留给风险分析。一个制造团队可以在边缘运行质量控制视觉模型，同时把优化请求发送到云端。

要了解有关使用 Strands Agents 构建 agent 的更多信息，请访问 [Strands Agents documentation](https://strandsagents.com/docs/user-guide/quickstart/overview/)。有关可用基础模型的信息，请参阅 [Amazon Bedrock](https://aws.amazon.com/bedrock/)。
