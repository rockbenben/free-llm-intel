# Reflection Beam 发布：面向 AWS 上智能体编码的开放权重模型

[Reflection AI](https://reflection.ai/) 推出了 Beam，一个面向智能体编码，以及维护代码、使用工具、解读结果、完成多步骤工作流这类长程任务的开放权重模型。开放权重的发布让开发者和研究者得以掌控运行时、部署环境和定制流程。

在这篇文章里，我们会说明 Reflection 的愿景，并展示如何把 Beam 部署到 AWS 上。可以先从一个 Amazon SageMaker JumpStart 实时端点开始，那是一条全托管的路径。当你需要以 Kubernetes 原生方式掌控分布式 GPU 基础设施时，用 JumpStart、SGLang 或 vLLM 配合 [Amazon SageMaker HyperPod Inference](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-model-deployment.html)。我们还会说明 Beam 的 5,010 亿 总参数如何影响 checkpoint 存储、权重内存、分片和并行，以及它的 230 亿 激活参数如何影响每个 token 的计算量。

上线时，Beam 在 US East (N. Virginia) 和 US East (Ohio) 的 Amazon SageMaker JumpStart 中可用。

## Reflection 对开放智能的愿景

Reflection 的使命是通过开放的模型权重、公开发表的研究和开源软件，[让智能开放并惠及所有人](https://reflection.ai/about)。它的[完整 AI 栈](https://reflection.ai/solutions)横跨模型、核心软件、生产基础设施和应用。Beam 把这套做法带给构建软件工程系统和智能体系统的开发者。

## 关于 Reflection Beam

Beam 是一个稀疏混合专家（sparse mixture-of-experts）模型，用于解决软件 issue、修改代码、调用工具，并基于中间结果采取行动。它有 5,010 亿 总参数和 230 亿 激活参数，Reflection 报告的有效上下文长度为 100 万 token。

Reflection 通过 Hugging Face 以 Apache 2.0 许可证发布 Beam 的权重。Beam 1.0 提供 BF16、FP8 和 NVFP4 三种 checkpoint 变体。这些格式带来不同的内存占用和硬件兼容性。你可以用 AWS 托管的 JumpStart 容器配置来部署这个模型，也可以在你的 AWS 环境里用 SGLang 或 vLLM 检视并定制它。

## 理解部署架构

选择能满足你掌控需求和扩展需求的服务路径。

- 当你想要 AWS 托管的模型包、端点和调用 API，而不用自己运维 Kubernetes 时，先从 **SageMaker JumpStart 实时端点**开始。
- 当你想在由 Amazon Elastic Kubernetes Service (Amazon EKS) 编排的 HyperPod 集群上使用 AWS 托管的容器和模型配置时，用 **JumpStart on HyperPod Inference**。
- 当你需要掌控服务镜像、运行时参数、量化或分布式执行时，用 **SGLang or vLLM on HyperPod Inference**。
- 按 checkpoint 存储、权重内存、KV cache、上下文长度、批处理、运行时开销，以及所支持的并行方式来为部署定规模。
- 先定义预期的并发和延迟目标，再根据实测的工作负载行为来配置副本数、缓存、路由和自动扩缩容。

JumpStart 实时路径把模型、容器和端点打包在一个托管的部署工作流背后。HyperPod 路径则把集群和服务运行时暴露给你，让你掌控分布式执行、缓存、路由和扩缩容。

## 前提条件

你需要：

- 一个 AWS 账户，并具备你所选 SageMaker 部署路径，以及它所依赖的 AWS Identity and Access Management (IAM)、网络和存储资源的相应权限。
- 通过 SageMaker JumpStart，或 Hugging Face 上的某个 Beam 1.0 checkpoint 仓库访问 Beam 的权限。
- 接受模型条款，以及 AWS Command Line Interface (AWS CLI) 和 Python 3.11 或更高版本。
- 支撑某个受支持的 Beam 配置所需的 GPU 配额和容量。

## 规划并取得 GPU 容量

Beam 的 5,010 亿 总参数需要一个多 GPU 部署。BF16 的权重内存需求最大，所以要规划一个多节点配置，为权重和运行时开销留足聚合 GPU 内存。FP8 请用搭载 NVIDIA H100 GPU 的 `ml.p5.48xlarge`，或搭载 H200 GPU 的 `ml.p5e.48xlarge` 与 `ml.p5en.48xlarge`。NVFP4 请用搭载 NVIDIA B200 GPU 的 `ml.p6-b200.48xlarge`。确认已发布的 checkpoint、运行时和并行布局支持你所选的实例类型。

- 先算出一个副本在权重、KV cache 和运行时开销上需要的内存，再用一次负载测试确认这个估算。
- 选择一个支持所需加速实例的 AWS Region。
- 检查所选实例类型的服务配额和可用容量。有按需容量就用按需容量，或者用 [SageMaker training plan](https://docs.aws.amazon.com/sagemaker/latest/dg/reserve-capacity-with-training-plans.html) 为计划中的工作做短期预留。
- 为镜像传输、权重下载、分片加载和运行时初始化留出时间。

## 路径 1：用 SageMaker JumpStart 实时端点开始

当你想走从模型目录到托管 HTTPS 端点最短的那条路时，先用 JumpStart 实时端点。这个示例通过一条感知变体的命令支持 BF16、FP8 和 NVFP4 三种模型 ID。它的 README 和 Python 文件是受支持的实例类型、请求 schema、部署命令和清理命令的唯一正本。

- 克隆示例仓库。  `git clone https://github.com/aws-samples/sagemaker-genai-hosting-examples.git`
- 进入 SageMaker JumpStart 部署示例目录。  `cd sagemaker-genai-hosting-examples/01-models/ReflectionAI/Beam-1.0-501B-A23B-NVFP4/`
- 创建并激活一个 Python 虚拟环境。  `python3 -m venv .venv source .venv/bin/activate`
- 安装示例依赖。  `python -m pip install -r requirements.txt`
- 为 FP8 运行这套有边界限制的部署、调用和清理生命周期。  `python jumpstart_real_time.py \ --variant fp8 \ --endpoint-name reflection-beam-fp8-smoke`  这条命令会部署 FP8 端点、发送一个简短请求、打印响应，然后清理掉端点。用 `bf16` 或 `nvfp4` 选择另一个 checkpoint 变体；省略 `--variant` 时默认就是 NVFP4。当你需要让某个端点持续运行时，使用 README 里的 Python 函数。

## 路径 2：用 SageMaker HyperPod Inference 部署

当你需要以 Kubernetes 原生方式掌控分布式 GPU 基础设施时，用 HyperPod Inference。你可以用 AWS 托管的 JumpStart 容器配置，也可以用 SGLang 或 vLLM 部署 Beam。[HyperPod Inference 部署示例 README](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/SageMakerHyperpod/reflection-beam) 和它的配置文件是已发布的 manifest、模型与镜像标识符、受支持的运行时版本以及命令的唯一正本。

开始之前，先配好 `kubectl` 对一个由 EKS 编排、装有 HyperPod Inference Operator 和必需 add-on 的 HyperPod 集群的访问。你还需要集群的专有网络（VPC）、子网、安全组，对所选 Beam 与运行时制品的访问权限，以及（如果你启用模型缓存）本地 NVMe 容量。如果所选仓库需要认证，请使用一个隔离的 Hugging Face access token。

开发和实验阶段，从 Hugging Face Hub 部署一个锁定 revision 的 Beam。生产部署和模型缓存则把 checkpoint 复制到 Amazon S3 或 Amazon FSx。[HyperPod 模型与镜像缓存](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-model-deployment-model-caching.html) 可以把权重预先加载到节点本地 NVMe 存储，并预先拉取服务镜像。

[HyperPod Inference Gateway](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-model-deployment-inference-gateway.html) 提供一个 OpenAI 兼容的接口，并在各副本之间路由请求。HyperPod Inference 也支持[托管的分层 KV 缓存与智能路由](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-model-deployment-caching-routing.html)。这些都属于 [2026 年推出的 Amazon SageMaker Inference 能力](https://aws.amazon.com/blogs/machine-learning/amazon-sagemaker-inference-2026-year-to-date-launches-in-review/)。

下一张图展开了模型准备和运行时的请求流程。启用模型缓存后，Inference Operator 会用所选权重和服务镜像预热符合条件的节点。运行时，Inference Gateway 和 Endpoint Picker 可以把每个请求导向一个合适的 JumpStart 托管副本、SGLang 副本或 vLLM 副本。

### 准备部署产物

使用不可变的输入，这样你才能复现部署和性能结果。

- 使用部署示例中记录的 JumpStart 模型发布版本。
- 为自定义运行时选择 BF16、FP8 或 NVFP4 checkpoint。
- 自定义运行时的情况下，把公开的 Beam commit SHA 和镜像 digest 保留在示例的发布配置里。
- 只有当你的集群拉不到上游镜像，或你的组织要求使用经批准的镜像仓库时，才把已发布的镜像复制到私有的 Amazon Elastic Container Registry (Amazon ECR) 仓库。
- 不要把 token、生成的 secret、私有模型 ID、镜像仓库凭证和未发布的结果放进仓库。

### 选择服务路径

除非你的工作负载需要特定的推理运行时或配置，否则从 SageMaker JumpStart 开始。

| **服务路径** | **什么时候用它** | **你自己要管什么** |
| --- | --- | --- |
| SageMaker JumpStart | 你想要 AWS 托管的容器和模型配置，运行时维护更少。 | 选择 Beam 模型版本、受支持的实例类型、端点配置和扩缩策略。 |
| SGLang 或 vLLM | 你需要特定的推理运行时或配置，例如自定义运行时参数、解析器、量化或并行。 | 锁定受支持的运行时镜像、模型 revision、解析器配置和分布式执行设置。 |

### 用 SageMaker JumpStart 部署

SageMaker JumpStart 减少了容器集成方面的工作，而 HyperPod 保留了对集群容量、扩缩和可观测性的掌控。

- 在 SageMaker Studio 里打开 **JumpStart 模型目录**。
- 在 **All public models** 下选择 **Beam**。
- 选择 **SageMaker HyperPod** 作为部署目标。
- 选择集群和 Kubernetes namespace。
- 填入端点名称，然后选择 **Deploy**。
- 在用已发布的 JumpStart 请求 schema 调用端点之前，先确认部署状态。

对于基础设施即代码的流程，请使用 HyperPod 示例里已发布的 JumpStart 配置。在配置部署之前，你可以先查看 [reflection-beam-jumpstart.yaml manifest 模板](https://github.com/aws-samples/sagemaker-genai-hosting-examples/blob/main/SageMakerHyperpod/reflection-beam/reflection-beam-jumpstart.yaml)。

- 克隆示例仓库，并进入 HyperPod Beam 目录。  `git clone https://github.com/aws-samples/sagemaker-genai-hosting-examples.git cd sagemaker-genai-hosting-examples/SageMakerHyperpod/reflection-beam/`
- 按 README 所述创建本地配置文件。  `cp config/deployment.env.example config/deployment.env cp config/release.env.example config/release.env`
- 在改动集群之前先校验 JumpStart 配置。  `python hyperpod_tool.py \ --config config/deployment.env \ --config config/release.env \ validate jumpstart`
- 部署 JumpStart 配置。  `python hyperpod_tool.py \ --config config/deployment.env \ --config config/release.env \ deploy jumpstart \ --timeout-seconds 1800`

这个 helper 会渲染并应用已发布的 `JumpStartModel` 资源，而不把填好取值的发布配置写到磁盘上。

### 用 SGLang 或 vLLM 部署

当你需要直接掌控服务运行时，选 SGLang 或 vLLM。在配置部署之前，先查看 [reflection-beam-sglang.yaml manifest 模板](https://github.com/aws-samples/sagemaker-genai-hosting-examples/blob/main/SageMakerHyperpod/reflection-beam/reflection-beam-sglang.yaml) 或 [reflection-beam-vllm.yaml manifest 模板](https://github.com/aws-samples/sagemaker-genai-hosting-examples/blob/main/SageMakerHyperpod/reflection-beam/reflection-beam-vllm.yaml)。示例 README 仍是已发布取值和命令的唯一正本。

- 克隆示例仓库。  `git clone https://github.com/aws-samples/sagemaker-genai-hosting-examples.git`
- 进入 HyperPod Beam 目录。  `cd sagemaker-genai-hosting-examples/SageMakerHyperpod/reflection-beam/`
- 按 README 所述创建本地配置文件。  `cp config/deployment.env.example config/deployment.env cp config/release.env.example config/release.env`
- 在改动集群之前先校验所选配置。  `python hyperpod_tool.py \ --config config/deployment.env \ --config config/release.env \ validate sglang`
- 部署 Beam，并等待部署进入终态。  `python hyperpod_tool.py \ --config config/deployment.env \ --config config/release.env \ deploy sglang \ --timeout-seconds 1800`  把 `sglang` 换成 `vllm` 即可使用 vLLM。这个 helper 会校验所选设置、应用渲染好的 manifest（不把发布取值写到磁盘）、以固定超时等待，并在部署失败时打印诊断信息。

## 调用 Beam

用已发布的模型请求 schema 调用 JumpStart 端点。对于 SGLang 或 vLLM，使用 HyperPod 示例里包含的那个有边界限制的 smoke 测试。

### 调用已部署的端点

- 安装示例客户端依赖。  `python3 -m venv .venv source .venv/bin/activate python -m pip install -r requirements.txt`
- 用推荐的初始采样设置，跑一次私有的健康检查和一个简短请求。  `python hyperpod_tool.py \ --config config/deployment.env \ smoke sglang \ --prompt "List three checks for a healthy model deployment." \ --temperature 1.0 \ --top-p 0.7`  对于 vLLM 部署，把 `sglang` 换成 `vllm`。这个 helper 会选一个就绪的 worker、打开一个临时的 port-forward、检查端点健康、发送请求，然后关闭 port-forward。

响应大致如下：

```
1. Confirm that the endpoint reports ready.
2. Send a short inference request.
3. Review the service logs for startup errors.
```

对于需要认证的 Inference Gateway，请使用 HyperPod 示例 README 里的 bearer token 流程。不要把凭证放进源代码、manifest 和命令历史。

## 度量与调优性能

- 用重复的、有代表性的编码和工具调用请求，在预期并发下测试每一条服务路径。
- 记录下 Beam 模型版本、镜像 digest、实例类型、精度、上下文长度、并行方式、服务参数、缓存状态和测试重复次数。
- 度量请求成功率、p50 和 p95 首 token 时间、每个输出 token 的时间、端到端延迟，以及聚合的输出 token 每秒数量。
- 根据这些结果来调优批量大小、KV cache 分配、副本数、自动扩缩，以及模型缓存和镜像缓存。
- 改动精度或量化之后，重新检查输出质量。

## 清理

测试结束后删除资源，以避免持续产生费用。

- 对于 SageMaker JumpStart 实时端点，请按 SageMaker JumpStart 部署示例 README 里的清理说明操作。
- 对于在 Amazon SageMaker HyperPod Inference 上的 JumpStart、SGLang 或 vLLM，请按 HyperPod Inference 部署示例 README 里的清理说明操作。
- 删除这次演练专门创建的 HyperPod 集群或 Amazon EKS 集群。
- 删除不再使用的缓存权重、复制过去的制品、负载均衡器、日志组、临时 IAM 角色，以及捕获到的推理数据。

## 结论

Reflection Beam 给开发者提供了一个为智能体编码和多步骤任务设计的开放权重模型。先用 SageMaker JumpStart 实时端点做全托管部署。当你需要 Kubernetes 原生的基础设施掌控、却不想自己管服务容器时，用 JumpStart 配合 SageMaker HyperPod Inference；当你需要自定义运行时，选 SGLang 或 vLLM。

使用 [SageMaker JumpStart 部署示例](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/01-models/ReflectionAI/Beam-1.0-501B-A23B) 或 [HyperPod Inference 部署示例](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/SageMakerHyperpod/reflection-beam)，然后照其中的说明操作。

要了解更多关于 Reflection AI 以及它对开放智能的愿景，请访问 [Reflection AI](https://reflection.ai/about) 并阅读 [Introducing Beam](https://reflection.ai/blog/introducing-beam)。
