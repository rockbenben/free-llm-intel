# 使用 Authorization Code flow 将 MCP server 连接到 Amazon Bedrock AgentCore Gateway

[Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 提供了一个集中式的层，用于管理 AI agents 如何连接整个组织内的工具和 MCP servers。它将身份验证、可观测性和策略执行整合到单一 endpoint 中，无需再逐个配置和保护每个 MCP server 连接。

在本文中，我们将介绍如何配置 AgentCore Gateway，以使用 Authorization Code flow 连接到受 OAuth 保护的 MCP server。

## 将 AgentCore Gateway 用作 MCP server endpoint

随着组织不断扩展其 AI agent 部署，每个团队所依赖的 MCP servers 数量也在迅速增长。开发者正在采用 Amazon Bedrock AgentCore Gateway 作为访问多个 MCP servers 的单一 endpoint。团队不再针对每个 IDE 逐个配置 MCP server，而是统一指向一个 Gateway URL，从而跨 tool 一致地访问其完整的 MCP 工具集。

随着团队超越自定义 MCP servers、转向采用生产级的第三方 MCP servers（例如来自 [AWS](https://docs.aws.amazon.com/aws-mcp/latest/userguide/what-is-mcp-server.html)、[GitHub](https://github.com/github/github-mcp-server)、[Salesforce](https://developer.salesforce.com/blogs/2025/06/introducing-mcp-support-across-salesforce) 和 [Databricks](https://docs.databricks.com/aws/en/generative-ai/mcp/) 的产品），这一模式正在加速普及。这些 MCP servers 中有许多是通过其主 identity provider 以联邦方式受到保护，另一些则由自身的 authorization server 保护。随着每个组织中 MCP servers 数量的增长，在 IDE 层面管理连接、身份验证和路由变得难以为继。AgentCore Gateway 将这种复杂性集中起来，为团队提供单一的 MCP 访问控制平面，同时为开发者带来顺畅无阻的体验。

许多企业级 MCP servers 需要 OAuth 2.0 authorization，即 agent 必须先代表用户完成身份验证，才能调用工具。AgentCore Gateway 现在通过 [Amazon Bedrock AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) 支持 OAuth 2.0 Authorization Code flow。借助这一能力，你的 agents 可以安全地访问受保护的 MCP servers，而无需在应用代码中嵌入凭据，也无需手动管理 token 生命周期。

## 关键术语

- **AgentCore Gateway user** – 使用 MCP clients 消费 Amazon Bedrock AgentCore Gateway 中工具的最终用户。Gateway users 不管理 AgentCore Gateway 本身，而是使用单一的 AgentCore Gateway URL 来访问可用的工具。
- **Admin user** – 管理和维护 Amazon Bedrock AgentCore Gateway 的用户。该用户负责将 MCP servers、工具或 APIs 附加到 AgentCore Gateway，以便 AgentCore gateway users 使用它们。
- **MCP server** – 在本文中，我们假设该 MCP server 受 OAuth 2.0 Authorization Code flow 保护，需要用户交互才能完成身份验证。这不同于 Client Credentials 或 Token Exchange 这类 machine-to-machine 身份验证方式，后者不需要用户介入。本文描述的模式专门适用于需要用户委托 authorization 的 MCP servers。

## Authorization Code flow 的工作原理

为支持 Authorization Code Grant 类型，我们提供了两种创建 target 的方式。

- **MCP Server target 创建期间的隐式同步**

在这种方法中，admin user 在 [CreateGatewayTarget](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_CreateGatewayTarget.html)、[UpdateGatewayTarget](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_UpdateGatewayTarget.html) 或 [SynchronizeGatewayTargets ](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_SynchronizeGatewayTargets.html)operations 期间完成 authorization code flow。这让 AgentCore Gateway 能够预先发现并缓存 MCP server 的工具。

- **在 MCP Server targets 创建时预先提供 schema**

使用这种方法，admin users 在 [CreateGatewayTarget ](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_CreateGatewayTarget.html)or [UpdateGatewayTarget ](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_UpdateGatewayTarget.html)operations 期间直接提供工具 schema，而不是由 AgentCore Gateway 从 MCP server 动态获取。AgentCore Gateway 解析所提供的 schema 并缓存工具定义。这样，admin user 就无需在 target 创建或更新期间完成 authorization code flow。当 create/update 操作无法人工介入时，这是推荐的做法。当你不希望暴露 MCP server target 提供的全部工具时，这种方法也很有用。

**注意**：由于这种方法会预先提供工具 schema，因此不支持 [SynchronizeGatewayTargets](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_SynchronizeGatewayTargets.html) 操作。你可以通过更新 target 配置，在 Method 1 和 Method 2 之间切换 target。

这意味着 AgentCore Gateway users 可以调用 list/tools，而不会被提示向 MCP server 的 authentication server 进行身份验证，因为这会获取缓存的工具。只有当 Gateway user 调用该 MCP server 上的工具时，才会触发 authorization code flow。当多个 MCP servers 附加到同一个 Gateway 上时，这一点尤其有用。用户无需对每个 MCP server 都进行身份验证即可浏览完整的工具目录（缓存工具），只需针对其调用工具的那台特定 server 完成该流程。

### URL Session Binding

[URL session binding](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/oauth2-authorization-url-session-binding.html) 用于验证发起 OAuth authorization 请求的用户与授予同意的用户是同一人。当 AgentCore Identity 生成 authorization URL 时，它还会返回一个 session-URI。用户完成同意后，浏览器会带着 session-URI 重定向回 callback URL。随后应用负责调用 [CompleteResourceTokenAuth](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_CompleteResourceTokenAuth.html) API，同时提供用户身份和 session-URI。在用 authorization code 换取 access token 之前，AgentCore Identity 会验证启动该 flow 的用户与完成该 flow 的用户是同一人。这有助于避免用户意外分享 authorization URL、而由其他人完成同意的情况——否则 access token 会被授予错误的接收方。authorization URL 和 session URI 仅在 10 分钟内有效，进一步缩小了被滥用的时间窗口。Session binding 适用于 admin target 创建（隐式同步）和工具调用期间。

### MCP Server target 创建期间的隐式同步

在本节中，我们将介绍 MCP Server target 创建期间的隐式同步是如何工作的。请确保 AgentCore Gateway 的执行角色具有 `GetWorkloadAccessTokenForUserId` 和 `CompleteResourceTokenAuth` 权限。首先，让我们从理解该 flow 开始。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/02/flash-3089-image-5.png)

- admin user 调用 `CreateGatewayTarget`，提供 MCP server endpoint、AgentCore Identity Credential Provider 和 return URL。这会告诉 AgentCore Gateway 要连接到哪台 MCP server，以及使用哪个 credential provider 来获取 OAuth 2.0 tokens。同样的 flow 也适用于 `UpdateGatewayTarget` 和 `SynchronizeGatewayTargets` 操作。
- AgentCore Gateway 向 AgentCore Identity Credential Provider [请求](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_GetWorkloadAccessTokenForUserId.html)一个 workload access token，传入 AgentCore Gateway 的 workload identity 以及格式为 `{gatewayId}{targetId}{uuid}` 的 user ID。该 workload access token 将 AgentCore Gateway 标识为后续 credential 操作的授权调用方。
- 使用该 workload access token，AgentCore Gateway 向 AgentCore Identity Credential Provider [请求](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_GetResourceOauth2Token.html)一个 OAuth 2.0 access token。这会为 admin user 提供一个 authorization URL 和一个 session-URI。此时，target 处于 **Needs Authorization** 状态。
- admin 在浏览器中打开 authorization URL，登录并向 AgentCore Gateway 授予所请求的权限。
- admin 授予同意后，OAuth 2.0 authorization server 会将 authorization code 发送到 AgentCore Identity Credential Provider 注册的 callback endpoint。
- credential provider 将 admin 的浏览器连同 session URI 重定向到 return URL。admin 应用调用 `CompleteResourceTokenAuth`，提供 user id 和第 2 步返回的 session-URI。credential provider 会验证发起 authorization flow 的用户（第 3 步）与完成同意的用户是否为同一人。如果 authorization URL 被意外分享，这可以防止 token 被劫持。如果该 flow 是从 AWS Console 发起的，这一步会自动处理。如果从其他上下文发起，则需要 admin 自行直接调用 `CompleteResourceTokenAuth` API。
- session binding 验证成功后，credential provider 会用 authorization code 向 OAuth 2.0 authorization server 换取 OAuth 2.0 access token。
- 该 access token 用于列出 MCP server target 上的工具；target 返回的工具定义会缓存在 AgentCore Gateway。

请注意，后续对 target 的更新或同步不会复用该 access token。相反，AgentCore Identity 会从 Authorization Server 获取一个新的 access token。

## 演示

无论使用隐式同步方法还是预先提供 schema，target 成功创建后，AgentCore Gateway users 都可以使用 MCP 协议发现和调用工具。在本节中，我们来看 AgentCore Gateway 的 tools/list 和 tools/call flows。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/02/flash-3089-image-14.png)

- gateway user 携带其入站 authorization token 向 AgentCore Gateway 发送 `tools/list` 请求。由于工具定义在 target 创建时已被缓存，AgentCore Gateway 会立即返回缓存的工具定义。
- gateway user 携带其入站 authorization token 向 AgentCore Gateway 发送 `tools/call` 请求。这会针对特定的 MCP server target 触发 OAuth authorization code flow，因为 AgentCore Gateway 需要一个 access token 来代表该用户调用 MCP server。
- AgentCore Gateway 向 AgentCore Identity [请求](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_GetWorkloadAccessTokenForJWT.html)一个 workload access token，传入 workload identity 以及来自入站 authorization header 的用户 JWT。
- 使用该 workload access token，AgentCore Gateway 向 credential provider [请求](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_GetResourceOauth2Token.html)一个 OAuth 2.0 access token。由于该用户尚不存在有效 token，credential provider 会改为返回一个 authorization URL 和一个 session-URI。
- AgentCore Gateway 将 authorization URL 和 session URI 传回 gateway user。用户在浏览器中打开 authorization URL，登录 OAuth 2.0 authorization server 并授予所请求的权限。AgentCore Gateway 返回的 [URL elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation#url-mode-flow) 响应示例如下：

```
{    
      "jsonrpc": "2.0",                                                     
      "id": 3,    
      "error": {   
          "code": -32042,     
          "message": "This request requires more information.",   
          "data": {
            "elicitations": [{
               "mode": "url",
               "elicitationId": "<ID>",     
			   "url": "<identity_url>/?request_uri=urn%3Aietf%3A...",
               "message": "Please login to this URL for authorization."
              }]      
          }       
      }
  	}
```

- 用户授予同意后，OAuth 2.0 authorization server 会将 authorization code 发送到 AgentCore Identity Credential Provider 注册的 callback endpoint。
- credential provider 将用户的浏览器连同 session URI 重定向到 return URL。用户的应用调用 CompleteResourceTokenAuth，提供用户的 JWT 和 session-URI。credential provider 会验证发起 authorization flow 的用户（第 4 步）与完成同意的用户是否为同一人。
- session binding 验证成功后，credential provider 用 authorization code 向 OAuth 2.0 authorization server 换取 OAuth 2.0 access token。credential provider 会将该 token 缓存在 Token Vault 中，并以 workload identity 和 user identity 为键。
- 当 gateway user 再次发出 tools/call 请求时，AgentCore Gateway 会基于 workload identity 和 user identity 从 AgentCore Identity 获取缓存的 token，并用它来调用 MCP server。

现在让我们看一个端到端 flow 的演示，我们会向 AgentCore Gateway 发送 tools/list 和 tools/call 请求。

在本文中，我们演示了如何使用 Authorization Code flow 将受 OAuth 保护的 MCP server 连接到 Amazon Bedrock AgentCore Gateway。通过 AgentCore Gateway 集中处理身份验证，团队可以使用 Amazon Bedrock AgentCore Identity 安全地管理凭据，同时让开发者从 MCP client 无缝访问受保护的工具。
