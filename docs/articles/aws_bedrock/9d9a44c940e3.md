# 扩展生成式 AI 用例，第 1 部分：使用 AWS Transit Gateway 的多租户 hub 与 spoke 架构

[生成式 AI](https://aws.amazon.com/ai/generative-ai/) 持续重塑企业开展创新和解决问题的方式。客户正在从试验阶段走向在整个组织范围内扩展生成式 AI 用例，越来越多的企业把这些技术全面集成到核心流程中。这一演进跨越业务线（LOB）、团队和软件即服务（SaaS）提供商。尽管许多 AWS 客户通常从单个 AWS 账户起步，用它运行生成式 AI 的概念验证用例，但随着采用规模扩大和向生产环境迁移，新的挑战也随之出现。

这些挑战包括有效管理和扩展实现，以及抽象并复用多租户、隔离、身份验证、授权、安全网络、速率限制和缓存等共性关注点。要有效应对这些挑战，[多账户架构](https://docs.aws.amazon.com/whitepapers/latest/organizing-your-aws-environment/benefits-of-using-multiple-aws-accounts.html) 会很有帮助，对于为多个企业客户提供服务的 SaaS 提供商、拥有多个独立事业部的大型企业，以及有严格合规要求的组织尤其如此。这种多账户方式通过为你的 AWS 环境提供更好的组织性、安全性和可扩展性，帮助维持良好的架构设计。它还使你能够更高效地在不断扩展的生成式 AI 实现中管理这些共性关注点。

在这个由两部分组成的系列中，我们讨论一种用于构建多租户、多账户架构的 hub 与 spoke 架构模式。该模式支持跨用例和团队的共享服务抽象，有助于构建安全、可扩展且可靠的生成式 AI 系统。在第 1 部分中，我们介绍一个集中式的 hub，用于承载生成式 AI 服务抽象，以及面向各租户的 spoke，并使用 [AWS Transit Gateway](https://aws.amazon.com/transit-gateway/) 实现跨账户互操作。hub 账户充当最终用户请求的入口，集中提供身份验证、授权、模型访问和路由决策等共享功能。这种方式免去了在每个 spoke 账户中分别实现这些功能的需要。在适用的情况下，我们使用[虚拟私有云（VPC）端点](https://docs.aws.amazon.com/whitepapers/latest/aws-privatelink/what-are-vpc-endpoints.html) 来访问 AWS 服务。

在第 2 部分中，我们讨论该架构的一种变体，使用 [AWS PrivateLink](https://aws.amazon.com/privatelink/) 把 hub 账户中的集中式端点安全地共享给组织内的团队或外部合作伙伴。

两篇文章的重点都是集中处理身份验证、授权、模型访问和多账户安全网络，以便使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 接入并扩展生成式 AI 用例。我们不讨论 prompt 目录、prompt 缓存、版本管理、模型注册表和成本等其他系统能力。不过，这些都可以作为该架构的扩展。

## 解决方案概览

我们的解决方案实现了 hub 与 spoke 模式，为跨多个账户管理生成式 AI 实现提供安全、可扩展的系统。该架构的核心是一个集中式的 hub 账户，它充当请求的入口，并由包含租户专属资源的 spoke 账户配合。下图展示了该架构。

![Architecture Diagram](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/01/ML-16510-architecture-daigram.png)

*hub 账户* 作为集中式账户，跨租户提供公共服务，并充当最终用户请求的入口。它集中提供身份验证、授权和路由决策等共享功能，免去了为每个租户分别实现这些功能的需要。hub 账户由核心工程团队运营和维护。

hub 基础设施包括公有和私有 VPC、面向互联网的 [Application Load Balancer](https://aws.amazon.com/elasticloadbalancing/application-load-balancer/)（ALB）、用于身份验证的 [Amazon Cognito](https://aws.amazon.com/cognito/)，以及访问 AWS 服务所需的 VPC 端点。

*spoke 账户 *包含租户专属资源，例如 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色权限和 Amazon Bedrock 资源。spoke 账户可以由核心工程团队或租户自己管理，具体取决于组织需求。

每个 spoke 账户维护自己的私有 VPC、用于 Amazon Bedrock 的 VPC 接口端点、特定的 IAM 角色和权限，以及账户级控制。这些组件通过 Transit Gateway 连接，后者提供安全的跨账户网络，并管理 hub 与 spoke VPC 之间的流量。如前面的架构图所示，请求在系统中的流转包括以下步骤：

- 用户（代表租户 1、2 或 N）访问客户端应用。
- hub 账户公有子网中的客户端应用对用户进行身份验证，并获得 ID/JWT token。在我们的示例中，我们使用 Amazon Cognito 用户池作为身份提供方（IdP）。
- 客户端应用使用 JWT token 中的自定义属性来确定 ALB 中对应的路由。ALB 根据上下文路径把请求路由到该租户的 [AWS Lambda](https://aws.amazon.com/lambda) 函数目标组。
- hub 账户私有子网中该租户专属的 Lambda 函数被调用。
- 该函数承担租户账户中的跨账户角色。该函数通过引用 Amazon Bedrock VPCE 的区域 DNS 名称，在 spoke 账户中调用 Amazon Bedrock。模型被调用，结果返回给用户。

该架构确保请求通过一个中心入口流转，同时保持租户隔离。由于在 spoke 账户中调用 Amazon Bedrock，每个请求都会继承该账户的限制、访问控制、成本分摊、服务控制策略（SCP）以及其他账户级控制。

该解决方案的示例代码分为两部分。第一部分展示单个 hub 与 spoke 账户的解决方案。第二部分通过部署另一个 spoke 账户来扩展该解决方案。每个步骤的详细说明见仓库 [README](https://github.com/aws-samples/genai-secure-networking-arch-patterns/blob/main/hub-spoke-transit-gateway/README.md)。在以下各节中，我们概述部署步骤。

## 先决条件

我们假设你熟悉 AWS 网络的基础知识，包括 [Amazon Virtual Private Cloud](https://aws.amazon.com/vpc/)（Amazon VPC）以及路由表和 [VPC 互连选项](https://docs.aws.amazon.com/whitepapers/latest/aws-vpc-connectivity-options/amazon-vpc-to-amazon-vpc-connectivity-options.html) 等 VPC 构建模块。我们还假设你熟悉[多租户架构](https://docs.aws.amazon.com/whitepapers/latest/saas-architecture-fundamentals/saas-architecture-fundamentals.html) 及其核心原则：在保持隔离的同时，从共享基础设施为多个租户提供服务。

要实施该解决方案，你必须具备以下先决条件：

- hub 与 spoke 账户（必需）：  两个 AWS 账户：一个 hub 账户和一个 spoke 账户 在 spoke 账户中拥有对 amazon.titan-text-lite-v1 模型的访问权限
- 额外的 spoke 账户（可选）：  第三个 AWS 账户（用于第二个租户的 spoke 账户） 在第二个 spoke 账户中拥有对 anthropic.claude-3-haiku-20240307-v1:0 模型的访问权限

## 设计考量

该架构的实现涉及若干重要的设计选择，它们会影响解决方案的运行方式、扩展能力和可维护性。在本节中，我们按不同组件探讨这些考量，解释每项选择背后的理由，并在适用时说明可能的替代方案。

### Lambda 函数

在我们的设计中，ALB 目标组是运行在 hub 账户而非 spoke 账户中的 Lambda 函数。这样就能集中管理业务逻辑，并集中进行日志记录和监控。随着架构演进以纳入 prompt 缓存、语义路由或使用大语言模型（LLM）代理（提供对多个模型的统一访问，同时处理速率限制和请求路由的中间件服务，如第 2 部分所述）等共享功能，在 hub 账户中实现这些功能可以保证各租户之间的一致性。我们选择用 Lambda 函数来实现 token 校验和路由逻辑，但你也可以根据组织的偏好，使用 [Amazon Elastic Container Service](https://aws.amazon.com/ecs/)（Amazon ECS）或 [Amazon Elastic Kubernetes Service](https://aws.amazon.com/eks/)（Amazon EKS）等其他计算选项。

我们为每个租户使用一对一的 Lambda 函数映射。尽管目前每个函数中的逻辑相似，但为每个租户配备专属函数可以尽量减少[噪声邻居](https://docs.aws.amazon.com/pt_br/wellarchitected/latest/saas-lens/noisy-neighbor.html)问题，并便于做租户层级相关的特定配置，例如内存和并发数。

### VPC 端点

在本解决方案中，我们在 spoke 账户中使用专用的 Amazon Bedrock 运行时 VPC 端点。为每个 spoke 账户配置专用 VPC 端点，适合由 spoke 账户的运营者管理租户功能（例如允许访问模型、设置知识库和 guardrails）的组织。根据你组织的策略，还可以通过在 hub 账户中使用集中式的 Amazon Bedrock 运行时 VPC（如第 2 部分所示）来实现该架构的另一种变体。集中式 VPC 端点适合由中心工程团队管理租户功能的组织。

在为 Amazon Bedrock VPC 端点选择集中式还是专用方式时，还需要考虑成本、访问控制和端点配额等其他因素。采用集中式方式时，随着租户数量增长，[VPC 端点策略](https://docs.aws.amazon.com/vpc/latest/privatelink/vpc-endpoints-access.html) 可能会触及 20,480 字符的上限。已预置的 VPC 端点和 transit gateway 连接无论是否使用，都会产生按小时计费的费用。如果 VPC 端点预置在各 spoke 账户中，每个租户都会产生额外的按小时费用。

### 客户端应用

出于演示目的，本解决方案中的客户端应用部署在 hub VPC 的公有子网中。该应用可以部署在 hub 或 spoke VPC 之外的账户中，也可以使用 [Amazon CloudFront](https://aws.amazon.com/cloudfront/) 和 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）作为[单页应用](https://docs.aws.amazon.com/prescriptive-guidance/latest/patterns/deploy-a-react-based-single-page-application-to-amazon-s3-and-cloudfront.html) 部署在边缘。

### 租户模式

企业在扩展生成式 AI 时会采用各种租户模式，各有明显的优缺点。我们的解决方案实现了 silo 模式，为每个租户分配专属的 spoke 账户。对于租户较少、隔离要求不那么严格的较小组织，采用 [pooled 模式](https://docs.aws.amazon.com/whitepapers/latest/saas-architecture-fundamentals/full-stack-silo-and-pool.html)（每个 spoke 账户承载多个租户）的替代方案可能更合适，除非它们计划未来大幅扩展或有特定的合规要求。有关多租户设计的更多信息，请参阅 [Let’s Architect! Designing architectures for multi-tenancy](https://aws.amazon.com/blogs/architecture/lets-architect-multi-tenant-saas-architectures/)。面向多租户应用的单元化（cell-based）架构可以提供故障隔离和扩展等好处。更多信息请参阅 [Reducing the Scope of Impact with Cell-Based Architecture](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/reducing-scope-of-impact-with-cell-based-architecture.html)。

### 前端网关

在本解决方案中，我们选择 ALB 作为请求入口。对于我们的生成式 AI 用例，ALB 具有多项优势：

- **长连接** – ALB 支持最长 4,000 秒的连接，这对可能需要超过 30 秒才能完成的 LLM 响应很有利
- **可扩展性** – ALB 能够处理大量并发连接，适合企业级部署
- **与 AWS WAF 集成** – ALB 可与 [AWS WAF](https://aws.amazon.com/waf/) 无缝集成，提供更强的安全性和对常见 Web 攻击的防护

当需要 API 版本管理、用量计划或精细的 API 管理能力，且预期的消息大小和响应时间符合其配额时，[Amazon API Gateway](https://aws.amazon.com/api-gateway/) 是一个替代选项。[AWS AppSync](https://aws.amazon.com/appsync/) 是另一个选项，适合通过 GraphQL 接口对外提供 LLM 的场景。

选择最能服务你客户的网关。ALB 能高效处理高并发、长时间运行的连接。API Gateway 提供全面的 REST API 管理。AWS AppSync 提供实时 GraphQL 能力。请根据应用的响应时间要求、API 需求、规模要求和具体用例来评估每一种方案。

尽管本文为简单起见使用 HTTP 演示连接，但不建议在生产环境中这样使用。生产部署应始终使用 [HTTPS](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/create-https-listener.html) 并配置适当的 SSL/TLS 证书，以保持通信安全。

### IP 寻址

用于部署解决方案资源的 [AWS CloudFormation](https://aws.amazon.com/cloudformation) 模板使用示例 CIDR。在第二个 spoke 账户中部署该架构时，请使用不与现有环境重叠的唯一 IP 地址。Transit Gateway 在第 3 层运行，需要不同的 IP 空间才能在 VPC 之间路由流量。

## 部署 hub 与 spoke 账户

在本节中，我们配置本地 [AWS Command Line Interface](https://aws.amazon.com/cli)（AWS CLI）环境，以在两个 AWS 账户中部署该解决方案。详细说明见仓库 [README](https://github.com/aws-samples/genai-secure-networking-arch-patterns/blob/main/hub-spoke-transit-gateway/README.md)。

- 在 hub 账户中部署一个 CloudFormation 堆栈，在 spoke 账户中部署另一个堆栈。
- 使用 Transit Gateway 连接配置 hub 与 spoke VPC 之间的连通性。
- 创建一个 Amazon Cognito 用户，把自定义用户属性 `tenant_id` 的值设为 tenant1。
- 在 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 表中创建一个条目，把租户 ID 映射到该租户（本例中为 `tenant1`）专属的模型访问和路由信息。

## 结论

随着各组织越来越多地在不同团队和业务线中采用并扩展生成式 AI 用例，对安全、可扩展且可靠的多租户架构的需求也在增长。这个由两部分组成的系列通过提供实施 hub 与 spoke 架构模式的指引来回应这一需求。从一开始就采用这类架构良好的实践，你就能构建可扩展且健壮的解决方案，在整个组织范围内释放生成式 AI 的全部潜力。

在本文中，我们介绍了如何建立一个集中式的 hub 账户，使用 Transit Gateway 承载身份验证、授权和网络等共享服务。我们还演示了如何配置 spoke 账户来承载 Amazon Bedrock 等租户专属资源。不妨试用提供的代码示例，看看该架构如何运作。
