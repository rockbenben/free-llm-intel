# 使用 Amazon Bedrock Managed Knowledge Base 在企业数据上构建多租户 agentic chat 应用

多租户 agentic chat 助手已成为大型客户的高频需求，而文档聊天更是排在首位。用户上传一份合同、一份报告或一本产品手册，然后立刻或在将来对它做研究、提问题。对话界面本身很好做，但支撑它的多租户 agentic 检索系统并不好做。

每个租户的文档都必须与其他租户的文档保持隔离，而这个边界必须从经过验证的身份来强制执行，而不是来自客户端发送的某个值。agentic 检索让问题更复杂：agent 会把一个问题拆成子查询并执行多次检索，这些跳转中的每一次都必须携带租户过滤条件，否则隔离就会失效。你还需要向量与全文检索引擎、能解析并嵌入多种模态的摄取 pipeline，以及一个保持同步的索引。对于一个原本只想交付这项功能的团队来说，需要构建、加固和运维的基础设施相当可观。

借助 [Amazon Bedrock Managed Knowledge Base](https://aws.amazon.com/bedrock/knowledge-bases/)，你可以卸下这部分无差别的工作。该服务负责摄取、存储、嵌入和排序，因此无需预置基础设施，也无需监控容量。除了基础设施之外，它还内建 agentic 检索，使用迭代规划与多跳检索来回答复杂问题，并在每一次跳转上都遵循访问权限。通过自定义连接器进行直接摄取，你的应用可以把文档直接发送到 knowledge base，它在数秒之内即可被检索。

在本文中，我们介绍一个构建在 Amazon Bedrock Knowledge Bases 之上的多租户 agentic 文档聊天应用的架构。该方案有两条数据流：文档摄取与会话式检索。我们会描述这两条数据流，以及异步索引生命周期、按用户的数据隔离，还有在大规模下运维该方案的最佳实践。我们还提供配套的仓库，方便你在自己的账户中部署这些代码。

## 方案概览

该方案解决了引言中列出的挑战。它交付一套多租户文档聊天体验：每个用户都能上传自己的文档，并立刻针对这些文档提出有依据的问题，而团队无需自行构建检索栈，也无需实现把一位用户的内容与另一位用户隔离开的隔离逻辑。

当用户提出问题时，应用会调用 Amazon Bedrock Knowledge Bases 上的 agentic 检索 API。该 API 运行一个 agentic workflow 来决定如何回应问题。对于简单的查找，它只发起一次检索。对于复杂或多部分的问题，它把问题拆解成子查询，并在给出回答之前执行若干次检索（多跳检索）。

在两种情况下，回答都以检索到的段落为依据，并带有引用。这套架构之所以易于运维，是因为 knowledge base 拥有负责检索与生成的那些组件：决定要查什么的规划步骤、向量索引、排序器，以及生成最终回答的模型。你的应用只负责与自身产品相关的部分，例如上传体验、聊天 UI、身份验证、按用户隔离，以及任何自定义业务逻辑。

该方案由以下关键组件构成：

- [Amazon Bedrock Managed Knowledge Base](https://aws.amazon.com/bedrock/knowledge-bases/)：抓取、解析、存储并检索多模态内容。它为文本、向量、元数据以及 CSV 和 Excel 文件这类结构化内容预置并管理检索基础设施，包括托管式解析、嵌入和索引。自定义连接器数据源可直接摄取用户上传的内容。
- [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 与 [AWS Lambda](https://aws.amazon.com/lambda/)：暴露上传、状态和聊天端点，并运行应用逻辑。
- [Amazon Cognito](https://aws.amazon.com/cognito/)：对用户进行身份验证，并提供应用用来隔离每位用户文档的已验证身份。
- [Amazon Simple Queue Service](https://aws.amazon.com/sqs/)（Amazon SQS）：把上传与摄取解耦，吸收上传峰值，并把反复失败的消息路由到死信队列。这让上传端点无论摄取端有多大反压都能保持响应。
- [Amazon DynamoDB](https://aws.amazon.com/dynamodb/)：跟踪每份文档的索引状态，使应用能够告诉用户文档何时可用。
- [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）：暂存超过内联限制的文件，并托管位于 Amazon CloudFront 之后的单页应用。

该 workflow 由以下步骤组成，编号与图中一致：

- 用户通过 Amazon Cognito 登录，并向应用上传一份文档。每个请求都携带用户的 JSON Web Token（JWT），由 Amazon API Gateway 校验。应用在服务端推导用户身份，而不是信任客户端发送的某个值。
- 应用从已校验的 JWT 中取出用户身份，并与文档（或其 S3 引用）一起放进 SQS 消息。它会立刻向用户返回响应，因此在后台执行摄取时浏览器不会被阻塞。6 MB 以内的文件在 API 请求中内联发送。更大的文件先上传到 Amazon S3，SQS 消息携带该 S3 URI，使 Amazon Bedrock 可以直接从 S3 读取文件。
- 一个 worker Lambda 函数从队列中读取消息，并用 `user_id` 元数据属性给文档打标签，其值设为调用方的 Amazon Cognito `sub`。这个值是由已通过身份验证的上传处理器放到消息上的。随后 worker 调用 [IngestKnowledgeBaseDocuments](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent_IngestKnowledgeBaseDocuments.html) API，Amazon Bedrock 会异步地对文档分块、嵌入并建立索引。
- worker 把每份文档的状态记录在 Amazon DynamoDB 中。浏览器轮询一个从 DynamoDB 读取的状态端点并更新 UI。用户无需刷新页面，就能看到每份文档从已接收进入处理中、再变为就绪。
- 要提问时，用户把问题发送给应用。
- 为回答问题，应用调用 [AgenticRetrieveStream](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_AgenticRetrieveStream.html) API，并对 `user_id` 施加显式的 equals 过滤。过滤值由应用在服务端根据已验证的 JWT 构建，而不是取自请求体，因此用户只能检索自己的文档。knowledge base 返回匹配的段落，基础模型生成带引用的回答，应用再以流式方式返回给用户。

## 方案详解

下面几节追踪一个请求在该方案中的流转：我们会更仔细地看摄取路径、索引生命周期、按用户隔离以及检索。

### 用户上传内容的直接摄取

由于用户是在应用运行期间上传文档，应用通过自定义连接器数据源直接摄取这些文档，而不是用 S3 连接器。S3 连接器是为批量摄取而设计的，那些文档靠计划同步来刷新，而这种同步可能覆盖或删除用户刚刚添加的文档。通过 `IngestKnowledgeBaseDocuments` API 直接摄取没有同步，因此文档会一直保留，直到你删除它。你还可以自己分配文档 ID，这让按用户的管理和更新保持简单。knowledge base 会保留每份原始文件的副本，你可以用 [GetDocumentContent](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_GetDocumentContent.html) API 取回。因此，你无需运维一套独立的文档存储，用户也能打开回答背后的原始出处。

应用根据文件大小在两条摄取路径中选择一条。6 MB 内联限制以内的文件作为字节直接在 API 调用中发送，这覆盖了大多数文本文档、合同和报告。更大的文件（文本最多 50 MB）会暂存到 Amazon S3，并通过其 S3 URI 以引用方式摄取。一个大小路由器在服务端应用这条规则，因此这条路径对用户是透明的，两条路径也最终汇入同一个 knowledge base。

有两种 API 行为值得在设计时考虑。第一，由于文档 ID 由你设置，用同一个 ID 重新摄取文档会就地更新它，而不是创建副本——这正是用户替换文件时你想要的行为。应用自己负责用户文件与文档 ID 之间的映射。在参考实现中，同一张用于跟踪索引状态的 DynamoDB 表也存储 (`user_id`, `filename`) → `document_id` 的映射，因此当用户重新上传文件时，应用会查出已有 ID 并复用。(不支持部分更新。一次编辑就是一次完整的重新摄取。)第二，单次 `IngestKnowledgeBaseDocuments` 调用最多接受 10 份文档，因此一个 worker 可以把多个摄取任务打包进一个请求。我们会在最佳实践一节中说明如何使用这一点。

### 文档索引生命周期

`IngestKnowledgeBaseDocuments` API 是异步的。它会立即返回一个 `STARTING` 状态，但在 Amazon Bedrock 完成解析、嵌入并建立索引之前，文档不可被检索。每份文档会经历五个状态，只有在 `INDEXED` 时才完全可查询，如下表所示。

|  | **状态** | **含义** | **可查询** |
| --- | --- | --- | --- |
| 1 | `STARTING` | 请求已被接受。处理尚未开始 | 否 |
| 2 | `PENDING` | 已入队，等待处理槽位 | 否 |
| 3 | `IN_PROGRESS` | 正在解析和嵌入 | 否 |
| 4 | `TEXT_INDEXED` | 文本块已建立索引。多模态处理（针对 PDF）仍在进行 | 是，文本部分 |
| 5 | `INDEXED` | 已完全处理 | 是 |

索引时间取决于文档类型。下表展示了我们在自己的测试中，针对空闲 knowledge base 与小文档（5 MB 以下）观察到的数值。时间会随文档大小、内容复杂度、区域以及 knowledge base 上的负载而变化，它们不构成服务级别承诺。请把这些数字当作设计时数量级上的参考，而不是有保证的延迟。

|  | **文档类型** | **文本可查询时间** | **完全 `INDEXED`** |
| --- | --- | --- | --- |
| 1 | 纯文本 | 2 至 3 秒 | 2 至 3 秒 |
| 2 | PDF | 5 至 30 秒（`TEXT_INDEXED`） | 约 90 秒 |

在负载之下，文档还会在等待处理槽位时停留在 `PENDING`，因此达到 `INDEXED` 的时间会随摄取队列的深度而增长。

应用轮询 `GetKnowledgeBaseDocuments` API，并把每份文档的状态记录在 DynamoDB 中，再在 UI 上以「已接收」「处理中」「就绪」呈现。文档一旦达到 `TEXT_INDEXED` 即可被搜索，因此应在那一刻就标记为就绪，而不是等 `INDEXED`。这两个状态的差异只对 PDF 和其他多模态内容才有意义。在 `TEXT_INDEXED` 时，文本块已可查询，覆盖了大多数检索需求。在 `INDEXED` 时，多模态元素（例如 PDF 中的图片和表格）也可查询。如果你把「已接受」（`STARTING`）当作可搜索，那么对一份仍在建立索引的文档发起的查询将返回空结果。

### 借助元数据过滤实现按用户数据隔离

在多租户应用中，一位用户的文档绝不能出现在另一位用户的结果中。你可以用两种方式之一强制执行这条边界：为每个租户预置一个独立的 knowledge base，或者使用一个共享的 knowledge base 并把每次查询都限定到调用用户。采用共享方式时，你通过元数据过滤器，或通过由服务评估的文档级访问控制列表（ACL），把每次查询限定住。对于有大量最终用户的应用，共享 knowledge base 是正确选择，因为它避免了每账户的 knowledge base 配额、大量小索引的基线成本，以及在注册时创建 knowledge base 的预置延迟。Amazon Bedrock Knowledge Bases 可以在单次调用中查询多个 knowledge base。这项能力是为了把同一个用户的不同知识领域合并起来，而不是用来在租户之间做隔离。当你只有少量大型租户、且有严格隔离要求时，按租户划分 knowledge base 仍然合理。对于用户级别的多租户，共享 knowledge base 扩展性更好，所需配置也更少。

如 workflow 中所示，worker 用 `user_id` 元数据属性给每份文档打标签，应用则对每次查询都按同一属性过滤。过滤值在服务端根据已验证的 JWT 构建。这种服务端推导就是安全边界。knowledge base 也可以从问题的措辞中推断出过滤条件，但那种推断是相关性特性，不是访问控制。隔离必须来自应用根据已认证身份构建的显式过滤器。作为纵深防御，参考实现会在每次请求之前确认过滤器已限定到调用方，并丢弃任何 `user_id` 不匹配的返回块。

未认证的请求返回 HTTP 401 响应，而已认证但无法解析出 `sub` 的请求返回 HTTP 403 响应。对于需要由服务本身来强制执行访问的受监管工作负载，knowledge base 还支持在查询时针对 `userContext` 评估的文档级访问控制列表。这会把强制执行移出你的应用代码。

### 检索与回答生成

检索是两条数据流中更直接的一条。`AgenticRetrieveStream` API 在单次调用中完成一整轮对话。它把问题拆成子查询，对每一个都应用按用户过滤条件执行检索，并在你启用 `generateResponse` 时以流式方式返回有依据、带引用的回答。它干净地映射到聊天界面，让你无需自己编排检索与生成就能获得较低的首 token 时间。Managed Knowledge Base 不支持 `RetrieveAndGenerate` API。当你需要更多控制时，例如为某个租户定制 prompt 或指定某个模型，可以使用 `Retrieve` API 获取段落，再自行调用 `Converse` API，并传入同样的按用户过滤条件。要展示引用背后的原始出处，`GetDocumentContent` API 会返回原始文档以供预览或下载。

## 最佳实践

随着用量增长，以下做法能让这条链路保持可靠。

**用队列把上传与摄取解耦。** 对于低用量工作负载，你可以直接在上传处理器中调用 `IngestKnowledgeBaseDocuments`。对于任何预期会有多个用户并发上传的应用，请在上传端点与摄取之间放置一个 Amazon SQS 队列。上传端点接收文件、把一个摄取作业写入队列并立即返回，因此浏览器不会因摄取而阻塞。一个 worker Lambda 函数从队列读取，并把最多 10 份文档打包进每次 `IngestKnowledgeBaseDocuments` 调用，这是上传集中到达时提升摄取吞吐的主要杠杆。例如，当 500 位用户几乎同时各上传一份文档时，worker 会把 500 个排队作业变成大约 50 次批量 API 调用。反复失败的消息会被路由到死信队列以供排查。这种设计能吸收峰值，让你在一个地方计量摄取调用速率，并使上传端点无论下游是否存在反压都保持响应。关于当前的摄取吞吐限制，请参阅 [Amazon Bedrock 配额文档](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-quotas.html)。

**要为摄取上限做规划，而不是为检索上限做规划。** 摄取与检索的扩展方式不同。`Retrieve` API 支持每秒 25 次查询（QPS）的突发，或每个 knowledge base 持续 10 QPS，远超会话式工作负载，因此它很少成为约束。摄取吞吐（前面已描述）足以应对交互式上传，但对现有仓库做批量迁移会把它打满。在这类场景中，请使用带计划同步的 S3 连接器，它是为大规模语料的一次性载入而设计的，可避免与实时用户上传争抢。

**把并发限制当作可重试的条件。** 当你超过并发限制时，Amazon Bedrock 返回的是 `ValidationException`，而不是 `ThrottlingException`。只对限流做重试的重试分类器会把它当成致命错误，从而丢弃该文档。

**监控那些预示上限的信号。** 跟踪摄取成功率、P50 与 P99 分位下达到 `INDEXED` 的时间，以及检索延迟。达到 `INDEXED` 的时间上升，是摄取 pipeline 接近其吞吐上限的最早指标，远早于请求开始失败。

**自行持久化对话历史。** `AgenticRetrieveStream` API 在 `messages` 参数中接受此前的轮次以支持多轮上下文，但它不会在多次调用之间持久化这些内容。请把对话历史存放在你自己的数据存储中，例如 Amazon DynamoDB，并在每次请求时传入相关轮次。把这件事留在你的应用里，也意味着你可以像对待文档那样，对对话历史强制执行按用户隔离。

## 成本

该方案的成本取决于你的模型配置。使用托管模型时，Managed Knowledge Base 只按存储和检索计费（按调用计，而不是按 token 计），摄取不产生额外费用。如果你选择某个 Amazon Bedrock 模型，则需要为摄取时的嵌入 token，以及使用 agentic 检索时的编排和生成 token 付费。当前费率请参阅 [Amazon Bedrock 定价页面](https://aws.amazon.com/bedrock/pricing/)。

在中等规模下，配套服务（AWS Lambda、Amazon API Gateway、Amazon SQS、Amazon DynamoDB 和 Amazon S3）只占总成本的一小部分。
