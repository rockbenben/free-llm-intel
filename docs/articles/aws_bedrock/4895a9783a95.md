# TCS 如何使用 Amazon Bedrock AgentCore 构建 Agentic Test Orchestrator

*本文与来自 Tata Consultancy Services (TCS) 的 Varun Valsan 共同撰写。*

Tata Consultancy Services (TCS) 为银行、金融服务和保险（BFSI）客户开展大规模测试。在这类工作中，一次发布里最慢的环节很少是编写应用代码。更大的制约是紧随其后的一连串工作：解读需求、设计场景、编写并维护自动化、准备执行环境、排查故障，以及汇总证据供评审。

BFSI 客户需要在保留金融服务应有管控的前提下提高测试吞吐量。目标不是取代质量工程师，而是去掉重复的转换与执行工作，让工程师能把更多时间花在风险分析、探索性测试和发布决策上。这些行业需求给 TCS 带来了四项具体要求。第一，每个测试都必须以项目特定的上下文为依据，而不是通用 prompts。第二，必须同时覆盖 API 测试和基于浏览器的 UI 测试，以贴合 BFSI 应用的构建方式。第三，安全至上，因此每个租户的数据和知识库都必须隔离。最后，必须提供一条从需求摄取到测试证据与报告的可重复路径，让收益能跨团队、跨发布保持住。本文将展示 TCS 如何构建 Agentic Test Orchestrator，把需求转化为可执行、受治理的测试，以及它给 BFSI 测试团队带来了哪些改变。

## 为什么传统自动化和既有系统还不够

TCS 已经为客户使用传统测试自动化，它确实能提升执行速度。但那些耗时的活儿一点没变：团队仍得自己创建场景、把场景转成脚本、维护定位器和依赖、诊断故障。一旦关联的用户故事发生变化，为早先故事生成的脚本很快就会过时。单条生成式 AI prompt 也无法提供多阶段工程工作流所需的控制。

因此，TCS 设计了 Agentic Test Orchestrator，把测试拆解成专门的任务。每个任务都有自己的 agent、工具、校验规则和上下文。一个确定性的 supervisor 负责路由工作，而执行工作流控制重试、错误分类、持久化和报告。

为了运行这些 agents，TCS 选择了 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)——一项可使用任意框架或模型、大规模构建、连接和优化 agents 的服务。有三项能力促成了这个决定。第一，[Amazon Bedrock](https://aws.amazon.com/bedrock/) 提供多种模型可选，每个 agent 都能用上契合其任务的模型，比如场景设计或代码生成，而且模型更新时 TCS 可以随时采用。第二，AgentCore runtime（Amazon Bedrock AgentCore 的一项能力）随需求弹性扩展，多个租户的测试人员可以同时运行生成与执行会话，TCS 无需自行配置或调优 agent 服务器。第三，该 runtime 把每个会话放在各自隔离的 microVM 中运行，为 TCS 的多租户平台提供了 session 级隔离，不必自己再搭这一层。这些能力合在一起，让 TCS 把工程精力集中在测试逻辑而非 agent 基础设施上，从而缩短了平台交付给 BFSI 客户的时间。

## 解决方案概述

下图展示了平台跨五个阶段的端到端流程，底层是每租户的安全层。来自 Jira、业务需求文档（BRDs）和 GitLab 的输入进入租户 Web 应用，该应用运行在 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/) 上，前面挂着 [Amazon CloudFront](https://aws.amazon.com/cloudfront/)，登录通过 [Amazon Cognito](https://aws.amazon.com/cognito/)。TCS 用 Amazon Bedrock AgentCore runtime 托管平台的专用 agents，这些 agents 使用 [Strands Agents SDK](https://strandsagents.com/) 构建，负责生成测试、与测试人员一起打磨测试，并管理测试的执行。[Amazon Elastic Container Service (Amazon ECS)](https://aws.amazon.com/ecs/) 运行生成的测试。[Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 和 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 存储结果，[Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 采集日志。全程由 [AWS WAF](https://aws.amazon.com/waf/)、Amazon Cognito、[AWS Key Management Service (AWS KMS)](https://aws.amazon.com/kms/) 和 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 落实每租户的安全与隔离。

TCS Agentic Test Orchestrator 是一套基于 AWS 构建的多租户软件即服务（SaaS）解决方案。测试人员通过 Jira 故事、业务需求文档（BRDs）、Swagger 规范、上传的文档、GitLab 源文件夹或捕获的 UI 流程来提供需求。平台据此生成测试场景、Gherkin feature 文件，以及可执行的 Java 或 Python 测试。它在 Amazon ECS 上运行这些测试，存储工件与结果，并在每租户的 Web 应用中展示进度和报告。接下来的小节逐一说明平台的每个部分如何满足 TCS 设定的四项要求之一。

## 1. 将控制平面与每个租户应用平面分离

TCS 要求严格隔离每个租户的身份、数据和密钥，因此平台采用计算资源池化、数据与身份各自独立的模式。共享的控制平面提供 Amazon EKS 集群、容器镜像仓库、管理门户、租户注册表、入驻自动化、Amazon CloudFront 分发和 AWS WAF 防护。每个租户应用平面都有专属的 Kubernetes 命名空间、Amazon Cognito 用户池、AWS KMS 密钥、Amazon S3 存储桶、Amazon DynamoDB 表，以及 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)。这种分离为每个 BFSI 租户划出了金融服务业管控所要求的数据与密钥边界。

租户入驻由事件驱动。管理 API 写入一条待处理租户记录，通过 [Amazon EventBridge](https://aws.amazon.com/eventbridge/) 发出事件，并启动一个 [AWS CodeBuild](https://aws.amazon.com/codebuild/) 项目，用 AWS Cloud Development Kit（[AWS CDK](https://aws.amazon.com/cdk/)）部署租户基础设施。这一模式让租户配置可重复执行，同时保留 TCS 所需的租户级身份与数据边界。

## 2. 让每个 agent 都基于项目上下文

TCS 的第一项要求是：生成结果要反映每个项目的领域，而不是套用通用 prompt，所以 grounding 被内建进平台。平台把上传的需求和生成的工件存到 Amazon S3，把会话元数据存到 Amazon DynamoDB。项目文档和同步的源文件通过向量嵌入在 Amazon Bedrock Knowledge Bases 中建立索引。资料送达 agent 之前，检索会按租户、项目和会话上下文过滤，因此一个客户的上下文不会进入另一个客户的测试。

这层上下文支持 BFSI 团队表达需求的各种方式：Jira 故事及关联的故事链、BRDs、Swagger 定义、参考代码、定位器文档、设置模块、测试数据和 GitLab 源文件夹。对于 UI 自动化，一个独立的捕获服务用 Puppeteer 把 URL 和自然语言目标转换成 UI 流程文档和 XPath 定位器文档。

## 3. 用专用 agents 取代单个大 prompt

单条 prompt 无法给受监管工作流所需的控制，因此平台把工作分给多个专用 agents：它们用 Strands Agents SDK 以容器化服务的形式运行在 Amazon Bedrock AgentCore runtime 中。生成 runtime 把请求路由到专用的场景、Gherkin、代码生成和校验工具。其他 runtime 负责对话式打磨、BRD 到故事的转换、跨关联 Jira 故事的增量生成，以及测试执行。每个 agent 负责生命周期中的一个阶段。下面是各专用 agent 的简要说明：

**Generation agent：** 创建结构化场景，转换为 Gherkin，生成 Java 或 Python 自动化代码，并校验生成的代码。

**Chat agent：** 把请求归类为信息查询或更新请求，然后作答或修改当前工件。

**Dynamic task agent：** 检索 BRD 上下文，生成包含需求与验收标准的结构化用户故事。

**Incremental agent：** 沿关联的 Jira 故事链扩展场景、Gherkin 或代码，而不是从头开始。

**Execution agent：** 取回工件、选择执行环境、运行测试、对故障分类、施加受控修复，并保存最终结果。

## 4. 把 API 和 UI 测试路由到正确的执行环境

TCS 需要同时覆盖 API 测试和基于浏览器的 UI 测试，两者对基础设施的要求不同，因此执行 agent 会从生成的代码中识别测试类型，据此路由。API 测试被路由到 [AWS Fargate](https://aws.amazon.com/fargate/) 上的 Amazon ECS。Selenium UI 测试被路由到由 [Amazon Elastic Compute Cloud (Amazon EC2)](https://aws.amazon.com/ec2/) 支撑的 Amazon ECS 集群，执行器可以在其中用虚拟显示器运行 Chrome。

对于 UI 运行，执行器可以用 FFmpeg 捕获虚拟显示器，把 HTTP Live Streaming（HLS）流发布到 Amazon S3，再经 Amazon CloudFront 分发。测试日志送到 Amazon CloudWatch，生成的 Cucumber 报告存放在 Amazon S3 中，并设有有时限的访问。

## 5. 管控执行与修正循环

为了让自动修正对 BFSI 流水线足够安全，执行 agent 把取回、执行、修复、保存这几步定义成一个 [LangGraph](https://www.langchain.com/langgraph) 工作流。LangGraph 显式状态图为 TCS 提供固定的步骤顺序和有界重试循环，而 AgentCore runtime 负责托管、扩展并隔离运行它的 agent。取回节点拿到测试项目和生成的资产、清理文件、识别框架。执行节点启动选定的 ECS 任务、监控状态、取回日志并解析结果。

当故障被判定为代码错误、且重试策略允许时，修复 agent 会收到受限的错误上下文，给出有针对性的修正。安全检查会拒绝空文件、意外出现的新文件，或文件大小变化过大的情况。连接或认证失败这类环境错误不会交给代码修复程序。保存节点把最终代码、状态、尝试次数、日志、解析结果和报告位置持久化下来。

## 6. 安全与运营管控

由于这套解决方案服务的是受监管的 BFSI 租户，它在身份、网络、数据和应用各层都施加了管控。身份层面，独立的 Amazon Cognito 用户池分别服务平台管理员和每个租户，并在后端做 JSON Web Token（JWT）校验和基于角色的授权。数据层面，每个租户拥有自己的 AWS KMS 密钥和加密的 Amazon S3 存储，DynamoDB 访问限定在租户范围内，Jira 与 GitLab 凭证由 AWS Secrets Manager 保管。在 Amazon EKS 的工作负载层面，Kubernetes 命名空间、NetworkPolicy 和 ResourceQuota 把租户隔开，容器以非 root 运行并丢弃 Linux capabilities。在网络边缘，AWS WAF 托管规则和请求速率控制保护平台。流量经 Amazon CloudFront 和 [Application Load Balancer](https://aws.amazon.com/elasticloadbalancing/application-load-balancer/) 以 HTTPS 交付，响应携带严格的安全标头。贯穿所有这些环节，OpenTelemetry traces 采集 agent 活动，Amazon CloudWatch 日志与 Container Insights 提供应用和执行的可观测性。

## 成果

TCS 已在生产环境中为 BFSI 客户运行 Agentic Test Orchestrator。为量化节省的工作量，TCS 在一个约含 100 个测试场景的代表性 BFSI 工作负载上，把该方案与既有流程做了对比。手工流程里，每个场景大约要花工程师两小时来设计、编写脚本和执行，全套约 200 小时。使用 Agentic Test Orchestrator 后，每个场景平均约 14 分钟，同一工作负载降到约 24 小时。这一对比中，工作量减少了 88%。（*这些数字来自 TCS 在约 100 个场景上运行的一次受控内部基准测试。实际结果会因工作负载、应用复杂度和团队而异。*）

对 TCS 来说，工作量这个数字不如它背后的运营模式重要。需求摄取、生成、执行、修正和报告如今汇成一条可追溯的工作流，而不再是一串彼此脱节的交接。质量工程师审核并治理 AI 生成的工件，而不是亲手搭建，于是时间重新回到风险分析、探索性测试和发布决策上——这些正是过去被手工流程挤掉的部分。这才是 TCS 一开始想达到的结果。

## 结论

TCS 想解决的问题不只是测试执行慢，而是从业务需求到可信测试证据之间那条支离破碎、全靠手工的路径。这正是 BFSI 发布中最耗工程时间、却又不增加保障的环节。本文展示了 TCS 如何在 AWS 上构建 Agentic Test Orchestrator，用上下文检索、专用 agents、感知工作负载的执行、隔离的每租户服务和可观测的基础设施来填上这道缺口。

结果是一套可复用的模式：把生成式 AI 用于软件质量工程，又不把测试简化成单条 prompt。Amazon Bedrock AgentCore 托管并扩展 agents，Amazon Bedrock 与 Amazon Bedrock Knowledge Bases 提供 AI 能力和项目上下文，Amazon EKS 承载每租户应用层，Amazon ECS 提供按需适配的执行，AWS 的安全、存储、集成和可观测性服务支撑整个生命周期。对 TCS 的 BFSI 团队而言，回报是更快、更一致的测试流程，让工程师的时间回到风险、质量和发布决策上。
