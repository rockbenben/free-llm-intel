# TCS 如何使用 Amazon Bedrock AgentCore 构建代理测试编排器

*这篇文章是与塔塔咨询服务公司 (TCS) 的 Varun Valsan 共同撰写的。*

塔塔咨询服务 (TCS) 为银行、金融服务和保险 (BFSI) 客户进行大规模测试，其中发布中最慢的部分很少是编写应用程序代码。更大的约束是接下来的工作链：解释需求、设计场景、编写和维护自动化、准备执行环境、调查故障以及收集证据以供审查。

BFSI 客户需要提高测试吞吐量，同时保留金融服务中预期的控制。目标不是取代质量工程师。它是为了消除重复的翻译和执行工作，以便工程师可以将更多时间花在风险分析、探索性测试和发布决策上。这些行业需求对 TCS 提出了四项具体要求。首先，每个测试都必须基于项目特定的上下文，而不是通用的提示。其次，它必须涵盖 API 和基于浏览器的 UI 测试，以匹配 BFSI 应用程序的构建方式。第三，安全性至关重要，因此每个租户的数据和知识存储都必须隔离。最后，它必须提供从需求获取到测试证据和报告的可重复路径，以便跨团队和发布保持收益。在这篇文章中，我们展示了 TCS 如何构建一个代理测试编排器，将需求转化为可执行的、受管理的测试，以及它为其 BFSI 测试团队带来的变化。

## 为什么传统的自动化和系统还不够

TCS 已经为其客户使用传统的测试自动化，并且确实提高了执行速度。但它让缓慢的工作保持不变：团队仍然必须创建场景，将其转换为脚本，维护定位器和依赖项，并诊断故障。当链接的用户故事发生变化时，为早期故事生成的脚本可能很快就会变得过时。单个生成人工智能提示也无法提供多阶段工程工作流程所需的控制。

因此，TCS 设计了 ​​Agentic Test Orchestrator，将测试分解为专门的任务。每个任务都有自己的代理、工具、验证规则和上下文。确定性主管路由工作，而执行工作流控制重试、错误分类、持久性和报告。

为了运行这些代理，TCS 选择了 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)，这是一种使用任何框架或模型大规模构建、连接和优化代理的服务。三个能力推动了这一决定。首先，[Amazon Bedrock](https://aws.amazon.com/bedrock/) 提供模型选择，因此每个代理都使用适合其任务的模型，例如场景设计或代码生成，并且 TCS 可以在更新的模型可用时采用它们。其次，AgentCore 运行时是 Amazon Bedrock AgentCore 的一项功能，可根据需求进行扩展，因此多个租户的测试人员可以同时运行生成和执行会话，而无需配置 TCS 或调整代理服务器。第三，运行时在其自己的隔离 microVM 中运行每个会话，这为其多租户平台提供了 TCS 会话级分离，而无需自行构建该层。这些功能共同使 TCS 将其工程工作重点放在测试逻辑而不是代理基础设施上，从而缩短了将该平台交付给 BFSI 客户的时间。

## 解决方案概述

下图显示了该平台跨五个阶段的端到端流程，下面是每个租户的安全层。来自 Jira、业务需求文档 (BRD) 和 GitLab 的输入进入在 [Amazon CloudFront](https://aws.amazon.com/cloudfront/) 后面的 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/) 上运行的租户 Web 应用程序，并通过 [Amazon Cognito](https://aws.amazon.com/cognito/) 登录。 TCS 使用 Amazon Bedrock AgentCore 运行时来托管平台的专用代理，这些代理是使用 [Strands Agents SDK](https://strandsagents.com/) 构建的。这些代理生成测试，与测试人员一起完善它们，并管理它们的执行。 [Amazon Elastic Container Service (Amazon ECS)](https://aws.amazon.com/ecs/) 运行生成的测试。 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 和 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 存储结果，[Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 捕获日志。在整个过程中，[AWS WAF](https://aws.amazon.com/waf/)、Amazon Cognito、[AWS Key Management Service (AWS KMS)](https://aws.amazon.com/kms/) 和 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 强制执行每个租户的安全和隔离。

TCS Agentic Test Orchestrator 是基于 AWS 构建的多租户软件即服务 (SaaS) 解决方案。测试人员通过 Jira 故事、业务需求文档 (BRD)、Swagger 规范、上传的文档、GitLab 源文件夹或捕获的 UI 流来提供需求。然后，平台根据这些输入生成测试场景、Gherkin 功能文件以及可执行的 Java 或 Python 测试。它在 Amazon ECS 上运行这些测试，存储工件和结果，并在每个租户的 Web 应用程序中显示进度和报告。以下部分描述了平台的每个部分如何满足 TCS 设定的四个要求之一。

## 1. 将控制平面与每个租户应用平面分离

TCS 要求严格隔离每个租户的身份、数据和密钥，因此该平台使用具有孤立数据和身份的池化计算。共享控制平面提供 Amazon EKS 集群、容器注册表、管理门户、租户注册表、加入自动化、Amazon CloudFront 分发和 AWS WAF 保护。每个租户应用程序平面都会收到自己的 Kubernetes 命名空间、Amazon Cognito 用户池、AWS KMS 密钥、Amazon S3 存储桶、Amazon DynamoDB 表和 [Amazon Bedrock 知识库](https://aws.amazon.com/bedrock/knowledge-bases/)。这种分离为每个 BFSI 租户提供了金融服务控制需求的数据和关键边界。

租户入职是事件驱动的。管理 API 写入待处理租户记录，通过 [Amazon EventBridge](https://aws.amazon.com/eventbridge/) 发出事件，并启动 [AWS CodeBuild](https://aws.amazon.com/codebuild/) 项目，该项目使用 AWS 云开发套件 ([AWS CDK](https://aws.amazon.com/cdk/)) 部署租户基础设施。此模式使租户配置可重复，同时保留 TCS 所需的特定于租户的身份和数据边界。

## 2. 让每个代理都融入项目环境

TCS 的第一个要求是生成反映每个项目的领域而不是通用提示，因此平台内置了基础。该平台将上传的需求和生成的工件存储在 Amazon S3 中，并将会话元数据存储在 Amazon DynamoDB 中。项目文档和同步源文件使用矢量嵌入在 Amazon Bedrock 知识库中建立索引。在材料到达代理之前，检索会按租户、项目和会话上下文进行过滤，因此一个客户端的上下文不会影响另一个客户端的测试。

该上下文层支持 BFSI 团队表达需求的多种方式：Jira 故事和链接的故事链、BRD、Swagger 定义、参考代码、定位器文档、设置模块、测试数据和 GitLab 源文件夹。对于 UI 自动化，单独的捕获服务使用 Puppeteer 将 URL 和自然语言目标转换为 UI 流文档和 XPath 定位器文档。

## 3. 使用专门的代理而不是一大堆提示

由于单个提示无法为受监管的工作流程提供所需的控制，因此该平台将工作分配给专用代理，这些代理使用 Strands Agents SDK 在 Amazon Bedrock AgentCore 运行时中作为容器化服务运行。生成运行时将请求路由到专用场景、Gherkin、代码生成和验证工具。其他运行时支持对话细化、BRD 到故事的转换、跨链接的 Jira 故事的增量生成以及测试执行。每个代理都拥有生命周期的一个阶段。以下是每个专业代理的简要概述：

**生成代理：** 创建结构化场景，将其转换为 Gherkin，生成 Java 或 Python 自动化，并验证生成的代码。

**聊天代理：** 将请求分类为信息查询或更新请求，然后回答或修改活动工件。

**动态任务代理：** 检索 BRD 上下文并生成包含需求和验收标准的结构化用户故事。

**增量代理：** 在链接的 Jira 故事链上扩展场景、Gherkin 或代码，而不是从头开始。

**执行代理：**获取工件、选择执行环境、运行测试、对故障进行分类、应用受控修复并保存最终结果。

## 4. 将 API 和 UI 测试路由到正确的执行环境

TCS 需要涵盖 API 和基于浏览器的 UI 测试，这对基础设施提出了不同的要求，因此执行代理从生成的代码中检测测试类型并相应地路由它。 API 测试路由到 [AWS Fargate](https://aws.amazon.com/fargate/) 上的 Amazon ECS。 Selenium UI 测试被路由到由 [Amazon Elastic Compute Cloud (Amazon EC2)](https://aws.amazon.com/ec2/) 支持的 Amazon ECS 集群，其中执行器可以使用虚拟显示器运行 Chrome。

对于 UI 运行，执行器可以使用 FFmpeg 捕获虚拟显示，并将 HTTP Live Streaming (HLS) 流发布到 Amazon S3，以便通过 Amazon CloudFront 进行传输。测试日志发送到 Amazon CloudWatch，生成的 Cucumber 报告存储在 Amazon S3 中，并且具有有时限的访问权限。

## 5.控制执行和修正循环

为了保证 BFSI 管道的自动校正足够安全，执行代理将其获取、执行、修复和保存步骤定义为 [LangGraph](https://www.langchain.com/langgraph) 工作流程。 LangGraph 的显式状态图为 TCS 提供了固定的步骤顺序和有界重试循环，而 AgentCore 运行时则托管、扩展和隔离运行它的代理。获取节点检索测试项目和生成的资产、清理文件并检测框架。执行节点启动选定的 ECS 任务、监控状态、检索日志并解析结果。

当故障被分类为代码错误并且重试策略允许时，修复代理会接收受约束的错误上下文并提出有针对性的纠正。安全检查拒绝空文件、意外的新文件或文件大小的极端变化。连接或身份验证失败等环境错误不会发送到代码修复程序。保存节点保存最终代码、状态、尝试、日志、解析结果和报告位置。

## 6. 安全和操作控制

由于该解决方案为受监管的 BFSI 租户提供服务，因此它在身份、网络、数据和应用程序层应用控制。对于身份，单独的 Amazon Cognito 用户池为平台管理员和每个租户提供服务，并提供后端 JSON Web 令牌 (JWT) 验证和基于角色的授权。对于数据，每个租户都有自己的 AWS KMS 密钥和加密的 Amazon S3 存储，DynamoDB 访问仅限于租户范围，AWS Secrets Manager 保存 Jira 和 GitLab 凭证。在 Amazon EKS 上的工作负载级别，Kubernetes 命名空间、NetworkPolicy 和 ResourceQuota 单独的租户以及容器以非 root 身份运行，并删除了 Linux 功能。在网络边缘，AWS WAF 托管规则和请求率控制可以保护平台。流量通过 Amazon CloudFront 和 [Application Load Balancer](https://aws.amazon.com/elasticloadbalancing/application-load-balancer/) 通过 HTTPS 传输，并且响应携带限制性安全标头。在所有这些中，OpenTelemetry 跟踪捕获代理活动，而 Amazon CloudWatch 日志和 Container Insights 提供应用程序和执行的可观察性。

## 结果

TCS 在生产环境中为其 BFSI 客户端运行 Agentic Test Orchestrator。为了量化节省的工作量，TCS 在大约 100 个测试场景的代表性 BFSI 工作负载上对照其现有流程测量了该解决方案。在手动流程中，每个场景大约需要工程师两个小时的时间来设计、编写脚本和执行，或者全套场景需要大约 200 小时。使用 Agentic Test Orchestrator，每个场景的平均工作量约为 14 分钟，相同的工作负载大约需要 24 小时。相比之下，这意味着工作量减少了 88%。 （*这些数字来自 TCS 在大约 100 个场景中运行的受控内部基准。实际结果因工作负载、应用程序复杂性和团队而异。）*

对于 TCS 来说，工作量的多少比其背后的运营模式更重要。需求摄取、生成、执行、纠正和报告现在形成一个可追踪的工作流程，而不是一系列互不相连的交接链。质量工程师审查和管理人工智能生成的工件，而不是手工构建它们，这将他们的时间投入到风险分析、探索性测试和发布决策上，而手动流程则挤掉了这些时间。这就是 TCS 想要达到的结果。

＃＃ 结论

TCS 想要解决的问题不仅仅是缓慢的测试执行。这是从业务需求到值得信赖的测试证据的支离破碎的手动路径。这是 BFSI 版本的一部分，会消耗工程时间而不会增加保证。在这篇文章中，我们展示了 TCS 如何在 AWS 上构建 Agentic Test Orchestrator，通过结合上下文检索、专用代理、工作负载感知执行、隔离的每租户服务和可观察基础设施来缩小这一差距。

结果是一种可重用的模式，可将生成式人工智能应用于软件质量工程，而无需将测试减少到单个提示。 Amazon Bedrock AgentCore 托管和扩展代理，Amazon Bedrock 和 Amazon Bedrock 知识库提供 AI 功能和项目上下文，Amazon EKS 托管每租户应用程序层，Amazon ECS 提供适合用途的执行，AWS 安全、存储、集成和可观察性服务支持整个生命周期。对于 TCS 的 BFSI 团队来说，回报是更快、更一致的测试流程，让工程师有时间做出风险、质量和发布决策。
