# 让 Amazon Quick 具备企业就绪能力：自动化、可审计的跨账户资源晋级

Amazon Quick 是亚马逊面向工作场景打造的 agentic AI 助手。你可以构建能够对自身数据进行推理、调用 action connector、并把多步骤任务执行到底的 agent。把这些资源（chat agent、action connector、知识库、flow 和 space）从开发 AWS 账户晋级到生产 AWS 账户——就像你对其他应用所做的那样——一直是一件手工、易错且繁琐的工作。本文展示如何用部署在 Amazon Bedrock AgentCore 上的一个幂等、可审计的 Model Context Protocol（MCP）服务器把它自动化。

agentic 解决方案的构建块是它的 **agent、action connector、知识库和 space**：配置了自定义指令的 chat agent、用于 Slack、Jira 及其他集成的 connector、以你自己的文档为根基的知识库，以及把它们绑定在一起的 Space。团队会在一个开发账户中快速搭建并迭代这些资源。

大多数企业会为开发和生产分别使用独立的 AWS 账户，有时中间还夹一个质量保证（QA）账户。当 agent、action connector 和知识库在开发账户中验证完毕后，并没有原生的、一键式的方法把它们晋级到下一个账户。团队只能逐个手工重建每一资源：用相同的指令和 starter prompt 重新创建每个 agent，为每个 agent 重新挂载其 action connector，重新授予资源权限，并为每个知识库重新配置 Amazon Simple Storage Service（Amazon S3）bucket、bucket policy 和数据源。这项工作缓慢、难以审计，且很容易在细微处出错，从而削弱了企业所需的治理叙事。

## 通过 API 管理 Amazon Quick 资源

Amazon Quick 资源是可编程的。Space、agent、action connector、知识库和 flow 都通过 Amazon Quick API（属于 [Amazon Quick Sight API 接口](https://docs.aws.amazon.com/cli/latest/reference/quicksight/)）来管理，该 API 提供完整的资源生命周期——创建、读取、更新、删除和列表。业务用户在 Amazon Quick 中配置的任何东西——一个带指令和 starter prompt 的 agent、一个 connector、一个知识库，或一个 flow——我们都能以编程方式进行检查、重建、更新和治理，权限也不例外。

正是这个可编程接口让受治理的晋级成为可能。我们不再手工重建每一资源，而是通过 API 读取一个资源及其权限，并在另一个账户中原样重新施加它们。本文中的迁移器（migrator）把创建、读取、更新和列表操作组合成一条可重复的工作流，并且从不针对目标发起删除操作，因此每一次运行只会新增或更新。

在本文中，我们将介绍 Quick Resource Migrator——一个托管在 Amazon Bedrock AgentCore 运行时（Amazon Bedrock AgentCore 的一项能力）上的示例 MCP 服务器，它通过一次工具调用即可自动完成 Amazon Quick 资源的跨账户晋级。它是资源驱动的：你选择一种资源类型（agent、connector、知识库、flow 或 space），并按 id、按名称或全部进行选取。它是幂等的（可安全重跑），并通过描述源资源、在目标中重放相同操作来忠实地复制权限。完整源代码可在 [aws-samples 仓库](https://github.com/aws-samples/sample-amazon-quick-suite-knowledge-hub/tree/main/infrastructure/multi-tenant-assets-deployment)中找到。

## 方案概览

迁移器在一次调用中晋级所选的一组资源。它是一个 upsert：目标中尚不存在的资源会被创建，已存在的资源会被就地更新。每一次更新都受到保护——在变更前会向 Amazon S3 写入一个带版本号的备份，因此每项资源都保留一份可查阅、可回滚的完整历史。一个只读的预览会在你提交之前准确报告某次运行将创建或更新什么，而迁移本身运行在 Amazon Bedrock AgentCore 之上，因此可以从 Amazon Quick 或任何兼容 MCP 的客户端来驱动。

### 迁移的内容

- **选取模型：** 选择一种资源类型（agent、connector、知识库、flow 或 space），并按 id、按名称或全部进行选择。选取是资源驱动的。你可以直接迁移一种资源类型，或迁移一个 space 以把它所关联的资源一并带过去。
- **Chat agent：** 连同其自定义指令、身份、语气、starter prompt 和欢迎消息一并重建，并重新挂载其 action connector（重映射到目标账户）。当迁移一个 space 时，它的 agent 会被自动重新关联到该 space。
- **Action connector：** 连同其配置一并重建。Secret 值从不从源读取。Connector 以占位凭证创建，并在目标中重新完成认证。
- **知识库：** 在目标账户中注册该知识库，重建其数据源，并复制其权限。对于以 S3 为支撑的知识库，迁移器还会配置目标 bucket 及其 bucket policy（这是迁移的一项独立产出）。文档本身（S3 对象）不会被复制。
- **Flow：** 依据其定义在目标账户中重建。由于 flow ID 在不同账户间不同，flow 按名称匹配：同名目标 flow 会被更新，否则创建一个新 flow。Flow 权限会被复制。
- **Space：** 在目标账户中重建，并重新关联到其 agent、connector 和知识库（资源 Amazon Resource Name（ARN）重映射到目标）。请先迁移那些被关联的资源，以便目标 ARN 能够解析。Space 权限会被复制。

### 关键设计原则

- **资源驱动选取。** 你每次迁移一种资源类型（agent、connector、知识库、flow 或 space），按 id、按名称或全部选取。Agent 连同其 action connector 重新挂载而被重建。Space 连同其 agent、connector 和知识库被重建并重新关联，ARN 重映射到目标账户。
- **权限保真。** 权限并非硬编码。服务器在每个源资源上调用相应的 `Describe*Permissions` API，并在目标中重放完全相同的操作列表，把 principal 重映射到目标账户中的注册用户。
- **幂等性。** 每项资源都被"创建或更新"。服务器先描述目标，再决定是创建还是更新，因此重跑一次迁移会收敛到相同状态，而不会产生重复项或失败。
- **最小权限与隔离。** 源角色为只读。目标角色仅持有迁移所需的操作。运行时使用 Cognito JSON Web Token（JWT）对调用方进行认证，并可在虚拟私有云（VPC）网络模式下运行。
- **安全、可回滚的更新。** 在迁移器更新任何已存在的目标资源之前，它会把该资源及其依赖的一份带版本号的快照写入一个专用的备份 bucket。如果该备份无法写入，更新就会被中止。每个被创建或被更新的资源也都会被快照化，并且一个 restore 工具可以把任何资源回滚到更早的版本。

## 架构

本方案采用三账户模型。一个中央 runner 账户在 Amazon Bedrock AgentCore 运行时上托管 MCP 服务器。该服务器使用 AWS Security Token Service（AWS STS）在源账户中承担一个只读角色、在目标账户中承担一个读写角色，因此任何地方都不存储长期凭证。

### 组件职责

| **组件** | **职责** |
| --- | --- |
| **AgentCore 运行时（runner 账户）** | 托管 MCP 服务器（`server.py`）。向源账户和目标账户承担角色，并编排迁移。以 VPC 网络模式运行，配有一个 Cognito JWT 授权器。 |
| **Amazon Cognito（runner 账户）** | 用户池、资源服务器，以及一个机器对机器的 app client。签发调用方出示给 AgentCore 的 JWT（client-credentials 授权方式，scope 为 `invoke`）。 |
| **Runner 执行角色** | AgentCore 执行角色：Amazon CloudWatch Logs、遥测，以及向源角色和目标角色的 `sts:AssumeRole`。 |
| **Migrator 角色（源账户）** | 只读的 Quick Sight describe/list 权限，外加知识库读取。 |
| **Migrator 角色（目标账户）** | 读写的 Quick Sight create/update 权限、知识库和 S3 写入，以及用于 principal 解析的 `ListUsers`。 |
| **备份 bucket（runner 账户）** | 一个加密的 S3 bucket，存放目标资源在更新前和迁移后的带版本快照。运行时直接写入其中，Restore 从中读取。可选（未设置时禁用）。 |

### 迁移流程

- 解析资源：根据资源类型和选取器（id、名称或全部），在源账户中解析出具体的资源 ID。
- 描述源：描述每个被选中的资源，以捕获其配置和权限。
- Connector：重建每个 connector。认证配置被净化为创建（写）模型，并使用占位 secret，然后在目标中重新完成认证。复制权限。
- 知识库：创建目标 bucket（`knowledge-base-<env>-<account>`）、bucket policy、数据源和知识库，然后复制知识库权限。S3 对象不会被复制。
- Agent：重建每个 agent 并挂载其 action connector（重映射到目标账户），然后复制 agent 权限。agent 与 space 的关联会在 space 本身被迁移时恢复（见 space 步骤）。
- Flow：依据其定义重建每个 flow，按名称匹配（flow ID 在不同账户间不同）：更新同名目标 flow 或创建一个新 flow，然后复制 flow 权限。
- Space：重建每个 space，并在 ARN 重映射到目标账户后重新关联其 agent、connector 和知识库（请先迁移那些资源），然后复制 space 权限。
- 报告：返回一份 JSON 报告，列出被创建或被更新的资源、bucket、备份、被跳过的权限，以及任何错误。

## MCP 服务器暴露的工具

服务器暴露五个工具，全部在 `server.py` 中定义。

### preview_migration（只读）

`preview_migration` 接收一个源账户 ID、一种资源类型（agent、connector、知识库、flow、space 或 all）、一个选取器（id、名称或全部），以及一个 AWS Region。它会返回一份将要被迁移的 agent、action connector、知识库和 flow 的清单，含名称和类型，而不做任何更改。可把它当作一次 dry run 来确认范围，并在晋级前支持一个变更管理审批环节。当你同时传入一个目标账户 ID 时，响应会额外给出一份源到目标的映射，为每项资源标注 CREATE 或 UPDATE，好让你在运行迁移之前准确看到它会改变什么。

### migrate_resources（完整迁移）

`migrate_resources` 接收源和目标账户 ID、一种资源类型（agent、connector、知识库、flow 或 space）、一个选取器（id、名称或全部）、一个 region、源和目标环境名称（用于知识库 bucket 命名），以及 Quick Sight 服务角色名称。它执行上文所述完整的"创建或更新"迁移，并返回一份结构化报告，列出它创建、更新和授予的一切，以及任何错误。由于它是幂等的，你可以反复运行它——例如在每次发布时运行——它会收敛到相同的目标状态。

### list_backups（只读）

`list_backups` 检索备份目录，并列出每个资产可用的版本。备份就是迁移器写入备份 bucket 的更新前快照——每次更新对应一个带版本的对象，因此你可以查看任何被迁移资源的完整历史。

### get_backup（只读）

`get_backup` 返回给定资产和版本（默认为最新）的完整已存备份，包括被捕获的资源配置及其依赖。

### restore_backup

`restore_backup` 把一份已存的备份版本重新施加到目标资源上，就地更新它；如果它已不存在，则重建它。它会先取一份全新的 restore 前备份，因此这次回滚本身也是可逆的。

## 部署本方案

完整源码和分步部署说明位于 [aws-samples 仓库](https://github.com/aws-samples/sample-amazon-quick-suite-knowledge-hub/tree/main/infrastructure/multi-tenant-assets-deployment)的 README 中。从高层来看，你会部署三个 AWS CloudFormation 栈——跨账户的 AWS Identity and Access Management（IAM）角色、VPC 网络，以及托管 MCP 服务器、由 Cognito 认证的 AgentCore 运行时——然后把该运行时注册为 Amazon Quick 中的一个 action connector。

## 通过 Quick App 使用迁移器

通过把该运行时注册为一个 action connector，你可以用自然语言从 Amazon Quick 驱动迁移器；你也可以构建一个 Quick App——一个叠加在相同 MCP 工具之上的点选式 Web 体验。你无需手工编写这个 UI。仓库附带一份可直接使用的 [app-builder prompt](https://github.com/aws-samples/sample-amazon-quick-suite-knowledge-hub/blob/main/infrastructure/multi-tenant-assets-deployment/docs/quick-app-integration.md)，你把它粘贴进 Amazon Quick 的 app builder，用你自己的占位 connector 和 action ID 替换掉，即可生成这个应用。该应用把工作流变成一条引导式流程：选择源和目标账户以及要晋级的资源，预览将被创建或更新的内容，运行迁移，并查看每一次历史迁移的记录，每条记录都由服务器写入的带版本 S3 快照支撑。下面的界面展示了这种体验。

## 结论

跨账户晋级是企业软件的一项基本要求，而直到此前，它一直是 Amazon Quick 所缺失的一环。Quick Resource Migrator 把一项缓慢、手工、难审计的任务变成一项快速、可重复、受治理的任务：一次工具调用即可在目标账户中重建 agent、connector 和知识库，并忠实地复制权限，全程幂等，因此你可以在每次发布时运行它。

克隆该[示例仓库](https://github.com/aws-samples/sample-amazon-quick-suite-knowledge-hub/tree/main/infrastructure/multi-tenant-assets-deployment)，把它部署到一个 runner 账户，并试着把一个 agent 或知识库从开发晋级到生产。然后根据你的治理与加固要求调整这一模式。
