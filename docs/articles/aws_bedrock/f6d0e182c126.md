# 在 Amazon Bedrock 上使用大语言模型执行多步任务

本文的目标是展示如何用大语言模型（LLM）完成那些需要多步动态推理与执行的任务。这类任务的例子包括回答如下形式的问题：“患有[特定疾病]的患者在不同医院的平均住院时长是多少？”或“[特定药物]的处方趋势在不同地区之间有何差异？”传统上，回答这类查询需要商业智能专家与数据工程师的专业能力，往往导致流程耗时且可能出现瓶颈。

不过，LLM 的进步开辟了令人兴奋的新可能：把复杂任务拆解为一系列步骤，用工具完成每一步，并产出最终解决方案。

在本文语境中，tools 指的是模型可以访问并与之交互的外部能力或 API，用来把自身功能扩展到基于文本的回复之外。这些工具让 LLM 能够执行各类专门任务，例如检索实时信息、运行代码、浏览网页或生成图像。借助工具，LLM 可以提供更准确、具备上下文感知且可付诸行动的产出，从而有效协助那些需要访问其内部知识库之外的数据或功能的复杂查询。

本文展示这类能力的一个示例：一个构建在既有数据集之上的患者病历检索方案，它只依赖 API，而不用 [text-to-SQL](https://langchain-ai.github.io/langgraph/tutorials/sql-agent/)。你可以在 [GitHub](https://github.com/aws-samples/plan-and-execute-analytical-queries) 上找到本文的代码。

## 方案概览

该方案的目标是准确回答需要多步推理与执行的分析型问题。以下是与该 agent 的一次预期交互示例。

> 用户：告诉我疫苗接种次数最少的患者的名和姓，以及其疫苗数量。
>         AI：根据我们分析的结果，我可以回答你的问题：接种疫苗数量最少的患者是 Sharleen176 Kulas532，其疫苗数量为
>         以下是我们得出这一答案的过程解析：
>         1. 我们首先检索了患者与免疫接种记录。
>         2. 然后我们按 patient_id 对免疫接种记录分组，并统计每位患者的疫苗数量。
>         3. 我们按疫苗数量对该列表做了升序排序。
>         4. 我们将结果限制为前 1 条（即疫苗数量最少的患者）。
>         5. 我们把这一结果与患者信息连接，以获得名和姓。
>         6. 最后，我们只选出相关信息（名、姓以及疫苗数量）。
>         结果显示 Sharleen176 Kulas532 只接种了 1 剂疫苗，这是数据库中患者里的最低值。

本方案使用 [Synthetic Patient Generation 数据集](https://synthetichealth.github.io/synthea/)，其中包含多张与医疗健康行业相关的合成数据表。

你可以按以下步骤把该数据集配置到项目根目录：

```
curl https://synthetichealth.github.io/synthea-sample-data/downloads/synthea_sample_data_csv_apr2020.zip > dataset.zip

unzip dataset.zip

mv csv dataset
```

## 规划

在规划阶段，LLM 会拿到一组预定义的 API 函数签名，以及每个函数功能的简要说明。这些函数签名充当工具，LLM 可以用它们来制定回答用户查询的计划。目标是让 LLM 像人一样，把得出答案所需的步骤推理清楚。

### 为什么规划阶段很重要

规划阶段至关重要，因为它让 LLM 能够构建一套结构化、有逻辑的行动序列，并在下一阶段执行。通过规划，LLM 可以把复杂问题拆解成可处理的步骤，确保以正确顺序调用正确的 API。这种结构化做法有助于减少错误，并提高产出准确结果的可能性。

### 提供函数签名

在这一阶段，LLM 会拿到一组函数签名，它们代表 LLM 可使用的工具。每个函数签名包含函数名、它接受的参数以及它返回值的类型。以下是几个函数签名的示例：

- `def get_patients() -> List[Patient]:`
 从数据集中检索患者列表。
- `def get_immunization() -> List[Immunization]:`
- 从数据集中检索免疫接种记录列表。
- `def filter(list: List[object], keys: List[str], values: List[str]) > List[object]:`
 根据指定的键与值过滤给定列表。
- `def join(a: List, b: List, left_key: str, right_key: str, how: JoinMode) > List:`
 基于匹配的键连接两个列表，使用指定的连接模式（例如 INNER、LEFT、RIGHT）。

这些函数签名是 LLM 生成计划的构件。LLM 必须挑选合适的函数，并按逻辑顺序排列它们，以达成期望的结果。

检索增强生成（RAG）会依据任务缩小 LLM 看到的工具范围，从而简化 prompt，改进工具选择过程。在工具众多的项目里，RAG 确保针对给定查询只暴露最相关的工具，降低复杂度，帮助 LLM 做出更准确的决策。这种聚焦式的呈现通过避免模型被无关选项淹没来提升性能。

## 生成计划

在提供函数签名之后，会提示 LLM 制定一份计划。计划通常由一系列步骤组成，每一步都表示为一个 JSON 对象。每个步骤指明需要执行的函数、需要传入的参数，以及预期的结果（通常称为 evidence）。

例如，如果任务是找出疫苗接种次数最少的患者，LLM 可能生成一份包含以下步骤的计划：

- **检索患者**：使用 `get_patients()` 函数获取患者列表。
- **检索免疫接种记录**：使用 `get_immunization()` 函数获取免疫接种记录列表。
- **按患者分组**：使用 `group_by()` 函数按 `patient_id` 对免疫接种记录分组，统计每位患者的疫苗数量。
- **按数量排序**：使用 `order_by()` 函数，根据疫苗数量对分组后的列表做升序排序。
- **限制结果**：使用 `limit()` 函数选出疫苗数量最少的患者。
- **与患者数据连接**：使用 `join()` 函数把选出的结果与患者信息匹配起来。
- **选择相关字段**：使用 `select()` 函数只提取必要字段，例如患者的名、姓以及疫苗数量。

## 执行

在执行阶段，上一步 LLM 生成的结构化计划会被以程序化方式落实，产出最终的输出。规划阶段产出的 JSON 蓝图会被解析，计划中描述的每个函数调用按顺序依次执行。

流程从数据检索开始，例如使用 `get_patients()` 或 `get_immunization()` 这类预定义 API 函数访问患者病历或免疫接种数据。这些最初的函数调用会产生中间结果，它们被存为 evidence，并在后续步骤中被引用。

计划通常涉及一系列数据变换函数，例如用 `group_by()` 聚合数据、用 `filter()` 精炼结果、用 `order_by()` 对数据排序。每个函数都按 JSON 计划中列出的具体参数执行，通过逐步精炼数据来回答查询。

每个函数执行后，其输出会传递给序列中的下一个函数。这条函数调用链最终汇聚到一个收尾步骤，通常涉及 select() 函数，用来提取最相关的信息，例如患者的姓名与疫苗数量。

执行阶段的错误处理对于保障整个流程的可靠性与稳健性至关重要。在 LLM 的计划被执行的过程中，可能出现各种问题，包括数据集为空、参数无效，或在 `join()`、`filter()` 这类函数调用中出现数据类型不匹配。为应对这些潜在挑战，系统在每一步都内置了错误检查机制，使其能够高效地检测并响应异常。如果某个函数返回了意外结果或遇到问题，系统可能把错误回传给 LLM 本身，让它带着必要的调整重新生成计划。这种做法不仅减少了执行失败，还通过交付准确可靠的结果提升了整体用户体验，即便面对意外挑战也是如此。

## 小结

本文探讨了 LLM 在通过 API 执行复杂分析查询方面的应用，并特别聚焦于 Amazon Bedrock。传统上，业务用户依赖数据专业人员来获取并呈现数据，而如今 LLM 可以提供一种精简的方式，借助预定义的 API 工具直接给出查询答案。为说明这一能力，我们使用 Synthetic Patient Generation 数据集，并给出一个围绕两个主要阶段构建的方案：规划（Plan）与执行（Execution）。

在规划阶段，LLM 获得 API 函数签名，并据此生成一套结构化、有逻辑的步骤序列来回答查询。该计划以 JSON 形式输出，既清晰又便于顺畅执行。在执行阶段，系统通过依次执行每个函数调用来以程序化方式落实该计划。系统集成了稳健的错误处理机制，用于识别潜在问题，并在必要时把错误回传给 LLM 以重新生成计划。

为演示这一过程，我们给出一个用例：系统通过检索、分组与排序数据，找出疫苗接种次数最少的患者，并最终呈现结果。这个示例展示了 LLM 能够超越单纯的文本回复，提供可付诸行动且具备上下文感知的产出，从而显著改进业务决策流程。
