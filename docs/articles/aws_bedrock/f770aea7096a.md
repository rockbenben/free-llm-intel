# 使用 Skyflow 和 Amazon Bedrock AgentCore Gateway 保护代理工具调用

在这篇文章中，我们展示 [Skyflow](https://www.skyflow.com/) 与 Amazon Bedrock [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 如何让敏感数据既不进入 AI agent 调用的工具，也不留在这些工具回灌给模型的上下文里。我们把 Skyflow Detect 作为请求与响应 [拦截器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-interceptors.html) 挂到 Amazon Bedrock AgentCore Gateway 上。数据到达工具之前，Skyflow 拦截器先做去标识化；agent 读取结果之前，再把原始值还原；agent 打开文档之前，则用干净的副本替换原文。你的 agent 和工具本身不需要任何改动。

Skyflow 已在 AWS Marketplace 上架，拦截器也在 GitHub 上开源。

## Agent 通过工具采取行动，工具则在搬运数据

agent 已经从回答问题走向采取行动，而行动是通过工具完成的：Model Context Protocol (MCP) 服务器、SaaS API、文档存储、网页搜索。每一次 agent 工具调用都是一次数据流动。企业的管控大多覆盖模型的输入和输出，却鲜少管住 agent 发给工具的内容，以及这些工具返回的内容。

这种缺口体现在三个方面：

- **敏感数据从工具参数中流出。** 模型是用上下文里的全部内容来写参数的，其中包含工具根本不需要的细节。你让 agent 查一个客户，客户的姓名、账号、邮箱就直接进了发往第三方服务器的查询里。而那台服务器位于你的 AWS 账户和合规边界之外。
- **敏感数据随工具结果回流。** 抓取的网页、CRM 记录、案件备注会落进模型的上下文、记忆、trace 和日志，哪怕这项任务从来用不到它们。
- **文档绕过了文本检查。** Amazon Simple Storage Service (Amazon S3)、Box、Google Drive 这类文档工具返回的是一个签名 URL，而不是文本。只检查字符串的过滤器看到一个链接就放行了，agent 随后打开的是原始文件。

逐个给 agent 打补丁，既无法跨团队、跨框架复用，也碰不到第三方工具。管控必须放在每一次工具调用都会经过的位置，这样授权、内容安全和数据保护才能对每个 agent、每个工具以同样的方式生效。

AgentCore Gateway 就是这个位置。它横在 agent 使用的每个工具前面，不管 agent 跑在什么框架、什么模型上。而且它做的远不止路由流量。借助 AgentCore Gateway 拦截器，你可以在每一次经过它的调用上以 AWS Lambda 函数的形式运行自己的代码。请求拦截器在调用到达工具之前看到它，响应拦截器在结果到达 agent 之前看到它。两者都可以检查 payload、改写 payload，或者直接拦截这次调用。因此，网关是除 Policy 和 Guardrails 之外再加一层数据保护的天然落点。这项管控只需挂一次，就能覆盖网关背后的所有 agent 和所有工具，agent 和工具的代码一行都不用改。

### 示例：一家欧洲大型银行的争议处理 agent

设想一家在欧洲经营零售与对公业务、受严格数据驻留要求约束的大型银行。它的运营团队正在用 agent 调查信用卡争议。

一位分析师让 agent 核查一笔有争议的交易。agent 先在网页上搜索商户，再从 Amazon S3 取出争议案件备注做摘要。没有任何保护时，会发生三件事：

- 模型用上下文里的全部内容拼出搜索查询。搜索服务商收到的是 “Mateo Jackson dispute AnyCompany Electronics London”。客户姓名就这样发给了第三方，而这次搜索本来只需要商户名。
- 抓取到的商户页面把不相关的个人数据带进了模型上下文。
- agent 读到的案件备注是原件，里面有客户的全名、邮箱、电话号码和卡号。

把 Skyflow 拦截器挂到网关上，同样的流程会变成另一番样子：

- 搜索服务商收到的是 “[NAME_AJbrIud] dispute AnyCompany Electronics London”，其中 [NAME_AJbrIud] 是可逆的 Vault 令牌。商户搜索结果照旧，服务商始终不知道客户是谁，而分析师在 agent 的回答里仍然能看到真实姓名。
- 网页内容到达模型时已经完成去标识化。
- agent 拿到的始终只是去标识化副本的链接，而不是案件备注原件。

## 方案概览

Skyflow 拦截器是同一个 AWS Lambda 函数，挂在 AgentCore Gateway 的两个拦截点上：

- `REQUEST`：网关调用工具之前运行。
- `RESPONSE`：工具返回之后、agent 看到结果之前运行。

在每一个拦截点上，它都会调用 Skyflow Detect 找出敏感实体，比如姓名、邮箱地址、电话号码、政府证件号、卡号、出生日期和位置，然后把这些值替换成令牌，或者还原成原始值。原始值保存在 Skyflow Vault 中，授权系统可以据此反解令牌。

Skyflow 的网关配置按工具决定采用三种保护模式中的哪一种：屏蔽工具、屏蔽模型、屏蔽文档。

| **模式** | **做什么** | **谁能看到真实数据** | **如何工作** | **典型用途** |
| --- | --- | --- | --- | --- |
| **屏蔽工具** | 敏感值在出站时从参数中剥离，回程时在结果中还原 | agent 和用户能看到，工具看不到 | 使用可逆的 Vault 令牌，工具回显的值会在 agent 读取之前还原 | 网页搜索、数据增强，以及不需要客户身份就能完成工作的第三方 API |
| **屏蔽模型** | prompt、历史记录、文件和工具结果在模型读取之前完成去标识化，回答在回程时重新标识 | agent 和用户能看到，模型看不到 | 模型调用走网关的推理 endpoint；回程时只还原本次调用所生成的令牌 | 客户对话、抓取的网页内容、跨区域或第三方模型 |
| **屏蔽文档** | 文件的签名 URL 被换成指向去标识化副本的 URL | agent 一侧无人能看到 | Skyflow Detect v2（预览版）取回文件、清洗文件，并把副本存放在获批的 Region；文件从不经过 Lambda，因此 payload 大小限制不会限制文件体积 | Amazon S3、Box、Google Drive 中的案件备注、对账单、合同 |

在生产环境中，有四点很关键：

- **agent 和工具无需改动。** agent 照旧发现网关，并用自己的 AWS Identity and Access Management (AWS IAM) 角色给请求签名。要屏蔽模型时，agent 只需把模型客户端指向网关的推理 endpoint。除此之外，拦截器对它们是不可见的。
- **改配置不用重新部署。** 策略按服务器、按工具设定方向、实体类型和令牌类型（可逆 Vault 令牌或单向令牌）。策略存放在 AWS Systems Manager Parameter Store 中，改动即时生效，无需重新部署。
- **失败即关闭。** 如果去标识化没能完成，这次调用会被扣住，而不是以明文发出去。拦截器只从允许列表中的位置取文件，对无法检查的流量直接阻断，而不是悄悄放行。
- **运维全部基于 AWS。** Skyflow API key 存放在 AWS Secrets Manager 中。每一次决策都记入 Amazon CloudWatch，并配有指标告警，而且拦截器从不记录凭证或原始值。

流程如下：

- agent 通过 AgentCore Gateway 调用工具，并用自己的 IAM 角色签名。
- `REQUEST` 拦截器把工具与策略比对，在需要时用 Skyflow Detect 对参数去标识化。
- 网关调用工具，工具收到的是令牌而不是敏感值。
- `RESPONSE` 拦截器按策略要求对结果做重新标识、去标识化，或者替换文档 URL。
- agent 收到结果。

agent 运行在 [AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 上，这是 Amazon Bedrock AgentCore 的一项能力。在这条流程之外，拦截器从 Parameter Store 读取策略、从 Secrets Manager 读取 Skyflow API key，并把每一次决策记入 Amazon CloudWatch。它在获批的 Region 中调用 Skyflow Detect 和 Skyflow Vault，完成数据的去标识化与重新标识。目标端位于网关之外：一个第三方网页搜索 MCP 服务器、一个 Amazon S3 中的案件备注存储，以及网关通过推理目标访问的 Amazon Bedrock 中的模型。对于模型调用，拦截器会在 Amazon DynamoDB 中保留一条短期记录，记下每次调用生成了哪些令牌，从而只还原这些令牌；该记录不含任何原始值。对于文档，Skyflow Detect 直接通过预签名 URL 取回文件，文件字节从不经过 Lambda。

## 它与 AgentCore 其他部分如何配合

拦截器补上了 AgentCore 与 Amazon Bedrock 已有管控的缺口：

- **Amazon Bedrock AgentCore 中的 Policy** 用 Cedar 和 Dogwood 规定 agent 能做什么。它不止判断某个 principal 能否调用某个工具：它可以根据 agent 轨迹中此前的动作做决策，控制对 agent 和模型的访问，阻止特定参数被发给特定工具，并用 Amazon Bedrock Guardrails 检查流经网关的数据。Skyflow 与 Policy 并行工作。当 Policy 放行一次调用时，Skyflow 会把其中的敏感值换成可逆令牌，于是这次调用既能通过，又不会把真实数据暴露给工具或模型。Policy 决定 agent 可以做什么，Skyflow 则在它做的过程中控制敏感数据怎么处理。
- **Amazon Bedrock Guardrails** 负责模型交互中的内容安全和敏感信息脱敏。Skyflow 在同一个网关上补上由 Vault 支撑的令牌化和文档去标识化。两者合用，就能在每一次模型调用和工具调用上形成分层防护。
- **AgentCore Identity（Amazon Bedrock AgentCore 的一项能力）与 AWS IAM** 保持原样。拦截器没有给 agent 增加任何需要管理的凭证。
- **AgentCore Observability（Amazon Bedrock AgentCore 的一项能力）与 Amazon CloudWatch** 把拦截器的决策与网关 trace 记录在一起。

## 部署方案

Skyflow 拦截器以 MIT 许可证在 GitHub 的 [agentcore-skyflow](https://github.com/SkyflowFoundry/agentcore-skyflow) 仓库中开源。Skyflow 可在 [AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-zysz3tjic76qg) 获取。要把拦截器加到你已经在运行的网关上：

- 在 AWS Marketplace 订阅 Skyflow，创建一个 Vault，并把它的 API key 存进 AWS Secrets Manager。
- 用 AWS Cloud Development Kit (AWS CDK) 从仓库部署拦截器 stack。它会创建 Lambda 函数、策略参数、用于记录模型调用的 DynamoDB 表，以及 Amazon CloudWatch 指标与告警。
- 把拦截器挂到网关的两个拦截点上。仓库中的脚本会完成这一步，并授予网关角色仅调用该函数的权限。如果你用 AWS CloudFormation 或 AWS CDK 管理网关，则改为在其中声明拦截器，这样后续的 stack 更新会保留它。
- 要屏蔽模型，给网关添加一个推理目标，并把 agent 的模型客户端指向网关的推理 endpoint。

仓库里还包含本文的完整参考部署，包括 agent、网关及其目标，你可以用 AgentCore CLI（Amazon Bedrock AgentCore 的一项能力）部署它。

有五种接入方式：

- **已有网关。** 把拦截器挂到你已经在运行的网关上，agent 和工具保持原样。
- **新建 agent。** 从第一天起就把工具放在 AgentCore Gateway 后面。
- **AWS 之外的 MCP 服务器。** 把它们作为网关的 MCP server 目标接进来，让它们的流量经过拦截器。
- **文档存储。** 对于返回签名 URL 的工具，把它的位置加入策略允许列表即可覆盖。
- **模型调用。** 添加推理目标，让 agent 的模型调用走网关。

Skyflow 提供多种 Vault 部署模型和 Region 选择，以满足数据驻留要求。参见 [Skyflow 部署模型](https://docs.skyflow.com/docs/fundamentals/product-overview)。

## 注意事项

- **格式。** 文本和 Office 格式（TXT、JSON、CSV、XML、JSONL、DOCX、XLSX 和 PPTX）保留可逆的 Vault 令牌。PDF 和图片会完整去标识化，但拿到的是单向令牌，因此无法从这些文件还原原始值。
- **可用性。** 字符串的去标识化与重新标识已正式可用。通过签名 URL 进行文档去标识化使用的是处于预览阶段的 Skyflow Detect v2。AgentCore Gateway 的可用性因 AWS Region 而异。部署前请查阅 Amazon Bedrock AgentCore 文档中的[支持的 AWS Region](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-regions.html)。
- **文档大小与延迟。** 文档去标识化在设计上是有边界的。拦截器在提交之前先检查文件大小，超过所设限制的文件会被立即拒绝，而不是等到超时。限制之内的文件能在 AgentCore Gateway 允许的连接窗口内完成。去标识化耗时随文档大小增长，因此请按你的文档规模设定大小上限。Skyflow Detect v2 目前处于预览阶段。扩大上线范围之前，先在试点中针对自己的工作负载和 Region 验证延迟。

## 结论

agent 的可信度，取决于它搬运的数据。借助 AgentCore Gateway 和 Skyflow 拦截器，你可以在每一次工具调用都必经的那一个点上落实隐私管控。它双向生效，覆盖文档和文本，而且不需要改动 agent 代码。

### 从何处入手

- 挑一个会接触客户数据、并且至少调用一个账户外工具的 agent 工作流。
- 列出绝不允许外流的实体类型，以及允许看到它们的工具。
- 从 [GitHub 仓库](https://github.com/SkyflowFoundry/agentcore-skyflow) 部署拦截器，并挂到该工作流的网关上。
- 先做屏蔽工具。然后为文档存储加上屏蔽文档，等 agent 的模型调用改走网关之后，再加屏蔽模型。
- 在扩大上线范围之前，先观察拦截器的 CloudWatch 指标一周。
- 如果还有疑问，参见 [Skyflow SDK 文档](https://docs.skyflow.com/docs/sdks/overview)。
