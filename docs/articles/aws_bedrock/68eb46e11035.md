# 借助 AI agent 实现智能放射科工作流优化

许多医疗机构反映，传统工作列表系统依赖僵化的规则，忽略了关键上下文——放射科医生的专科方向、当前工作量、疲劳程度和病例复杂度。这造成了一个长期难题：放射科医生会挑更容易、价值更高的病例，回避复杂检查，导致诊断延迟和成本上升。一项覆盖 62 家医院、分析 220 万例检查的研究发现，病例分配效率低下会造成 [加急病例 17.7 分钟延误，以及各医院网络合计 $2.1M–$4.2M 的成本](https://theimagingwire.com/2023/05/17/effects-on-healthcare-of-cherry-picking/)。根因很直接：传统放射科工作列表系统依赖僵化、基于规则的引擎，忽略了最重要的上下文——放射科医生的专科方向、当前工作量、疲劳程度和病例复杂度。在本文中，我们将展示如何在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 和 [Strands Agents SDK](https://strandsagents.com/latest/) 上借助 AI agent 构建放射科工作流优化方案。

放射科工作列表系统依赖确定性的、基于规则的引擎，按预定义的逻辑分派检查。静态的专科匹配忽略上下文，例如当前可用的放射科医生是否已连续数小时判读复杂病例，或一次简单的随访扫描是否真的值得亚专科医生关注。负载均衡只响应当前队列深度，而不会基于病例复杂度、预估判读时间或医生疲劳模式来预判需求。最关键的是，当确定性规则产生次优分配时系统并不会学习，同样的低效模式会不断重复，直到有人手工更新底层逻辑。在本文中，你将了解如何：

- 通过构建智能工作列表系统减少诊断延迟
- 部署能够推理你团队的专科方向、工作量和疲劳程度的 AI agent
- 实现上下文感知的病例分配，减少诊断延迟

通过摆脱僵化的确定性规则、转向真正理解我们各亚专科的 Agentic AI，我们正见证一次范式转变：它把放射科工作流从简单的任务管理提升为真正自主的编排。合适的亚专科医生在合适的时间与合适的病例无缝匹配，让放射科医生能够完全专注于诊断质量，而不必在队列中周旋。

## Agentic AI 方法

AI agent 是一个自主的软件组件，能够感知所处环境、围绕目标进行推理并采取行动来达成目标。在你的放射科工作流优化中，一组专用 AI agent 协同编排复杂的临床工作流，从头到尾贯通全流程。每个 agent 负责工作流中的特定任务。agent 跨专科协作并自适应调整，为患者和团队交付最佳结果。Bedrock AgentCore 上的 AI agent 同时评估多个因素，例如放射科医生的专科方向、当前工作量、疲劳模式、病例复杂度、临床紧急程度和可用性，从而做出最优的病例分配。为 agent 提供动力的 AI 模型是可通过 Amazon Bedrock 获得的基础模型（FM）。系统持续从历史模式中学习并适应不断变化的条件，从而削弱驱动“挑病例”行为的激励结构。

当[技师](https://www.asrt.org/main/career-center/careers-in-radiologic-technology)完成一项新检查、该检查进入影像归档与通信系统（PACS）可供判读时，工作流即被触发。经技师确认影像质量的检查排入队列，等待分配给最合适的可用放射科医生。分配过程以异步工作流方式运行，检查与放射科医生的匹配由动态规则触发。系统的目标是在合适的时间把合适的放射科医生分配给合适的检查。检查分配触发器通过调用 **Intelligent worklist orchestration** agent（2）来启动 [AgentCore Runtime session ](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html)，该 agent 是解决方案的大脑。编排 agent 负责协调多个各自并行执行任务的专用 AI agent。对于常规工作流，编排器先与两个 agent 协作——Exam Metadata Synthesizer 和 Patient History Synthesizer——收集相关的上下文信息。基于这些聚合数据，Rad Assignment Agent 应用推理逻辑把检查与最优放射科医生匹配。对于优先病例，分诊系统会识别出需要立即关注的关键发现。当 AI 算法检测到颅内出血等紧急情况时，它们会自动触发检查排序，促使编排器为判读放射科医生标记高优先级指示。这些 agent 托管在 [AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 上，可使用 [AgentCore Runtime starter toolkit](https://github.com/aws/bedrock-agentcore-starter-toolkit)、[AgentCore SDK](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/develop-agents.html#develop-agents-bedroock-agentcore-sdk) 或直接通过 [AWS SDKs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/develop-agents.html#develop-agents-bedrock-agentcore-aws-sdk) 构建。[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 在工作列表流程中的两个位置生效。在入站侧，它会在查询到达 Worklist orchestrator 之前进行拦截，拒绝那些试图从临床数据存储中提取患者个人可识别信息（PII，如姓名、SSN、地址）的 prompt。在出站侧，它会扫描来自 Exam metadata、Clinical data history、Rad mapper、Exam prioritization 和 Dynamic rules 各 agent 的响应，对在从 AgentCore Memory 或 Clinical data API 检索过程中可能浮现的 PII 进行脱敏。这样一来，agent 内部使用完整的检查级数据进行准确优化，但只向用户返回与运营相关的信息（检查类型、模态、紧急程度、排班）。主题限制进一步约束 agent，使其只处理与工作列表优化相关的查询。**Exam metadata synthesizer** agent（3a）从新到达的检查中抽取检查详情，包括模态、检查部位和紧急标记。同时，**Patient history synthesizer** agent（3b）收集相关临床上下文并检索既往检查记录，提供全面的患者背景信息以支撑优先级决策。**Rad Assignment Agent**（4）为每项检查优化放射科医生分配，分析多个因素，包括放射科医生档案、角色、专科方向、偏好的医院归属、实时可用性和动态业务规则。该 agent 通过把每项检查匹配给专科方向与检查类型相符的放射科医生、优先处理 STAT 病例以满足紧急需求，并分配复杂与常规检查的合理组合以防止疲劳，从而智能地平衡工作列表。未来的增强可以让 agent 依据检查来源医院及相应的服务级别协议（SLA）周转时间要求来分派检查。**Rad availability **sub agent（4a）检查实时排班与当前工作负载分布，以平衡病例分配。此外，**Dynamic rules** agent（4b）应用关键业务逻辑，包括服务级别协议要求、新模态与检查类型，以及为符合机构与合同义务所需的升级策略。该 agent 在匹配决策中还会使用技师提供的非结构化备注。[AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html) 通过两套互补的记忆系统为检查处理维护上下文信息：**短期记忆**存储原始交互，以在单次会话内保留上下文。它把完整对话历史记录为按序事件，每条检查元数据和 agent 响应分别保存。这种架构帮助 agent 重建完整的对话历史，即使在服务重启或检查重新排序触发之后也能保持连续性。当被分配的检查未能满足其服务级别协议（SLA）时，触发器会通知编排器发起重新分配。系统从短期记忆上下文中取回检查元数据，并且只调用放射科医生可用性 agent。同样，当被分配的放射科医生拒绝或跳过某项检查时，重新分配流程会基于短期记忆上下文自动触发，以加快分配。**长期记忆**使用语义记忆策略，在多次会话之间提供持久的知识保留。系统抽取并存储检查分配的关键信息，包括 Order MRN（病历号）与被分配的放射科医生、操作类型与影像模态、患者临床病史、分配理由和决策因素。这个持久化知识库维护完整的放射科医生分配历史，帮助系统从既往决策中学习，并基于历史模式、放射科医生专长和工作量均衡来优化未来的检查分配。语义记忆保留事实，而 AgentCore 的**情节记忆**捕获经验层面的知识：尝试过的目标、推理步骤、采取的行动（包括使用的工具以及传入的上下文或参数）、结果，以及对结果的反思。它不是存储每一个原始事件，而是识别 SLA 违约或放射科医生拒绝分配等重要时刻，把它们总结成紧凑记录并加以组织，使系统能够检索到重要的内容而不受噪音干扰。反思通过识别模式、提炼洞察并综合出可执行的指引，把情节经验转化为策略性知识，帮助 agent 学习并随时间做出越来越明智的决策。**Exam prioritization** agent（5）将使用影像模型对检查进行分诊，这些模型根据急性肺栓塞之类需要立即关注以优化临床结果的关键发现，判断是否需要提高某项检查的优先级。这个异步工作流通过 AI 影像模型处理影像，例如用于在 CT 肺血管造影（CTPA）影像中检测肺栓塞的 [Artery-aware network（AANet）](https://github.com/guojiajeremy/AANet)。当模型以高置信度检测到关键发现时，它们会自动触发检查排序，供放射科医生立即审阅。检查分配给放射科医生后，医生可以与智能前端工作流管理应用交互，通过友好的界面使用这套工作流优化功能。放射科医生可以接受、拒绝或跳过该分配并继续判读。系统会自动学习放射科医生的选择，并随时间改进。例如，通过分析反馈回路与上下文判断进行持续自适应学习，这套 agentic 系统能实时优化病例分配，减轻放射科医生的认知负担。基于 SLA 违约、分配被拒等情节记录构建的情节记忆策略反思，有助于分析过往情节，浮现洞察、模式与更高层级的结论。反思不是简单地检索发生了什么，而是帮助系统理解某些事件为何重要，以及它们应如何影响未来行为。当 agent 需要外部数据来完成任务时，它们通过 AgentCore Gateway 的 /mcp 端点调用工具。该网关是整个架构的中央集成枢纽，负责 Model Context Protocol（MCP）路由以及系统通信的入站和出站认证。网关连接到 AgentCore Identity，后者与外部身份提供方集成，以在系统交互与数据交换中实现安全的访问控制。

工具请求被路由到 AgentCore Runtime 内的 MCP Server，它暴露了工作流所必需的多个后端工具。这些集成的工具包括访问 **Clinical data API**，用于从电子健康记录（EHR）系统获取患者记录与病史；以及 Rad calendar，用于通过 MCP server 获取放射科医生排班信息。这些工具将使用现有的企业 Imaging API，通过 OpenAPI 规范直接从 PACS 访问影像检查。

## 实施步骤

实施该解决方案需要以下步骤。完整代码见 [GitHub](https://github.com/aws-samples/sample-agentic-radmapper)** 仓库**。

- 智能工作列表编排 agent 采用 [agent-as-tool](https://aws.amazon.com/blogs/opensource/introducing-strands-agents-1-0-production-ready-multi-agent-orchestration-made-simple/) 模式，可以访问四个 Strands 工具作为 sub-agent。编排 agent 判断哪个专用的“tool-agent”最适合某个子任务，然后像调用函数一样“调用”该 agent。被调用时，sub-agent 接管该子任务，用它自己的大语言模型（LLM）和 prompt 推理问题，并多次调用自己的工具，最后把综合后的结果返回给编排器。该 agent 使用内置的 MCP client，通过 AgentCore Gateway 与正确的工具建立通信。这让 agent 可以借助这些工具自主执行复杂任务，在真实世界中采取行动：按专科方向匹配放射科医生、检索患者病史、抽取检查元数据并核对其班次。该 agent 使用以下系统 prompt：  `MAIN_SYSTEM_PROMPT = "" You are a Radiologist Assignment Orchestrator Agent responsible for identifying and recommending the most appropriate radiologist for a new medical imaging study. You receive a user query along with a JSON object containing associated study and patient data. Role & Responsibilities Your primary responsibilities are: Delegate specific tasks to specialized sub-agents: rad_mapper, image_assessor, clinical_data_collector, metadata_finder, and shift_checker. Collect relevant historical patient data and gather detailed information about the imaging study, particularly rom its metadata Analyze all collected information to identify and return a prioritized list of appropriate radiologists for assignment Manage the end-to-end workflow across all system components Make sure all recommendations align with established clinical best practices Tool selection Always select the most appropriate sub-agent or tool based on the nature of the incoming query and the data available. Behavioral Guidelines You must always: Maintain HIPAA compliance and protect patient data privacy at every step Follow established clinical workflows without deviation Document decision rationale clearly and transparently for every recommendation Coordinate effectively with all sub-agents for seamless information flow Prioritize patient safety above all other considerations in every recommendation Output Format Return the recommended radiologists in priority order, along with a brief rationale for each recommendation based on the study type, metadata, patient history, and radiologist availability/expertise. ""`

- MCP server 使用 [FastMCP](https://pypi.org/project/fastmcp/)，采用无状态 HTTP 传输，暴露用 @mcp.tool() 装饰的工具，提供放射科医生检索、影像检查元数据、患者临床数据和值班可用性。agent 通过 AgentCore Gateway 访问这些 MCP 工具以获取相关数据。Rad calendar MCP 工具从医疗排班系统中查找放射科医生的值班与实时排班，供放射科医生可用性 sub-agent 使用。同样，clinical data MCP 工具可以为患者病史 synthesizer agent 查找患者的历史临床数据。
- 创建了以下 sub-agent。第一个是 Rad assignment agent（***rad_mapper）***，它根据机构、院区、疾病、亚专科、患者历史健康数据、临床记录和其他医疗参数匹配放射科医生，然后按优先级分类，并回答有关放射科医生详情的问题。第二个是 Patient history synthesizer agent（***clinical_data_collector）***，它检索患者病史并识别与放射科医生分配相关的历史信息。第三个是 Exam metadata synthesizer agent（***metadata_finder）***，它从当前影像检查中抽取元数据，为放射科医生分配提供上下文（解剖部位、记录、检查详情）。第四个是 Rad availability agent***（shift_checker）***，它核实放射科医生的可用性，并通过检查其排班、当前工作量和例外情况，从筛选后的列表中选出最合适的可用放射科医生。该列表由 clinical data collector、metadata finder 和 rad_mapper 等 sub-agent 过滤。
- 通过 AgentCore Gateway，agent 获得对 [PACS](https://www.intelerad.com/en/2022/01/24/what-is-pacs/)/Imaging API 的访问权限，用于查询检查元数据。[AWS HealthImaging](https://aws.amazon.com/healthimaging/) 提供云原生医学影像仓库，存储 PB 级 [DICOM](https://www.dicomstandard.org/about) 影像，检索速度达亚秒级。它为 exam metadata synthesizer agent 提供影像检查元数据的访问能力，包括患者病史、模态类型、检查部位和紧急程度。
- 该方案使用 [Amazon SageMaker AI](https://aws.amazon.com/sagemaker/ai/) 对机器学习模型执行实时推理，这些模型可检测急性、时间敏感的病症，如肺栓塞。这些模型分析存储在 AWS HealthImaging 中的医学影像，识别出需要立即重新排序检查的关键发现。推理结果通过 PACS/Imaging API 返回给 exam prioritization agent 等 agent，由它们根据临床紧急程度动态调整工作列表顺序。
- 在该方案中，[AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html) 用于追踪查询流经智能工作列表编排器、并分发到 Exam metadata、Clinical data history、Rad mapper、Rad shift checker 和 Dynamic rules 各 agent 的完整执行路径。每次 agent 调用都被捕获为带独立 span 的 trace，因此当一次检查分配请求耗时超出预期时，就能定位瓶颈究竟在经 MCP Gateway 的 Clinical data API 调用、AgentCore Memory 中较慢的记忆检索，还是 LLM 推理本身。这里展示的 Trajectory 视图把单次工作列表查询的端到端 span 链可视化，使排查诸如 Rad shift checker agent 取不到日历数据、或编排器路由到错误 sub-agent 之类的问题变得简单直接。这些 trace 汇入 Amazon CloudWatch 仪表板，用于跟踪各 agent 的延迟、工具调用成功率、token 消耗和记忆读写模式。这为运维团队提供了调优 agent 性能、并在回归问题影响工作列表吞吐量之前发现它们所需的信号。

## 结论

在本文中，我们展示了把放射科工作列表管理从僵化的、基于规则的系统转向智能化、agent 驱动的编排，如何为你的组织提供一条可行路径：减少运营低效，并保护你的临床医生免于倦怠。我们讨论过的结果表明，你的工作流之所以改善，并不是靠增加更多规则，而是靠部署真正具备推理、上下文判断和持续适应能力的系统。你还可以进一步扩展该方案以提升其价值。通过分析检查量与复杂度模式，你的 agent 可以在工作流瓶颈演变成积压之前就识别出来，从而实现主动的排班调整，例如在数据表明需求即将激增的准确时间与地点提前调配更多放射科医生。当你准备推进时，先从自己的环境中识别影响最大的用例开始。在此基础上，与现有临床系统建立稳健的集成模式，并采用分阶段推进的方式，为你的方案留出学习和持续改进所需的时间与数据。
