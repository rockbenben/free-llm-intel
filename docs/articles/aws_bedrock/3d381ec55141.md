# 在 Amazon Bedrock 上从 Anthropic 的 Claude Sonnet 3.x 迁移到 Claude Sonnet 4.x

*本文与 Anthropic 的 Gareth Jones 合写。*

Anthropic 的 Claude Sonnet 4.5 模型已在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上线，标志着基础模型能力的一次重大进步。相应地，Anthropic 的 Claude Sonnet 3.x 的弃用时间表也已公布。这一演进为生产环境的 AI 应用带来双重紧迫性：既有利用更强性能的机会，也有在弃用之前完成迁移的运营必要性。组织必须把模型迁移视为 AI 推理战略的核心组成部分，因为执行不当可能导致服务中断、性能回退和成本超支。

本文提供一套系统化方法，用于在 Amazon Bedrock 上从 Anthropic 的 [Claude Sonnet 3.x](https://aws.amazon.com/blogs/aws/anthropics-claude-3-5-sonnet-model-now-available-in-amazon-bedrock-the-most-intelligent-claude-model-yet/) 迁移到 [Claude Sonnet 4.5](https://aws.amazon.com/bedrock/anthropic/) 模型。我们剖析关键的模型差异，指出必不可少的迁移考量，并给出经过验证的最佳实践，帮助把这次必要的转换变成能为您的组织带来可衡量价值的战略优势。

## 模型差异概览

了解各模型版本之间的具体变化，是规划一次成功迁移的第一步。从 Anthropic 的 Claude Sonnet 3.5 Sonnet 迁移到 Claude Sonnet 4.5，会带来一些您可以加以利用的能力与行为转变：

- **更大的上下文窗口** – Anthropic 的 Claude Sonnet 4.5 把上下文窗口从 200,000 token 扩展到 [1,000,000 token（beta）](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-anthropic-claude-messages-request-response.html)。这使应用能够在单个 prompt 中处理并在代码库、财务报告或冗长的法律文档之上进行推理，从而简化复杂的工作流。
- **原生推理机制** – Anthropic 的 Claude 3.5 Sonnet 模型依赖思维链（chain-of-thought，CoT）提示技术，而 Claude 4 模型引入了内置的、可通过 API 启用的推理功能，例如 [extended thinking](https://docs.aws.amazon.com/bedrock/latest/userguide/claude-messages-extended-thinking.html) 和 [interleaved thinking](https://aws.amazon.com/blogs/opensource/using-strands-agents-with-claude-4-interleaved-thinking/)。这些功能让模型在作答之前拥有专门的计算时间来推理，从而大幅提升解决复杂问题的表现。
- **进阶的工具使用** – Anthropic 的 Claude Sonnet 4.5 模型显著升级了工具使用能力。它们可以[并行执行多个工具](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#maximizing-parallel-tool-use)，并在工具调用之间使用 extended thinking，相比早期模型顺序式的工具使用，可以实现更复杂、更高效的 agentic 工作流。

如需进一步了解模型差异，请参阅 [Complete Model Comparison Guide](https://claudelog.com/model-comparison/)。

一次成功的迁移取决于若干关键的技术与战略考量，我们将在后续章节中讨论。主动应对这些要点可以降低风险，并加快您走向生产环境的进程。

## 前提条件

开始之前，请先确认 Claude Sonnet 4.5 在您计划使用的 AWS Region 中可用，因为模型支持情况可能因地域而异。受支持 Region 的最新列表，请参阅 [Model support by AWS Region in Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。此外，在运行模型推理时指定一个 inference profile，即可使用[跨区域推理](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)（cross-Region inference，CRIS），这有助于提升吞吐量并最大化资源可用性。另外，Bedrock 近期宣布为 Claude Sonnet 4.x 模型提供全局跨区域推理，通过把模型请求路由到全球范围内受支持的 Region，可进一步提升吞吐量。受支持的跨区域推理 profile 列表，请参阅 [Supported Regions and models for inference profiles](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-support.html)。关于全局跨区域推理的更多细节，请参阅我们近期的[博客文章。](https://aws.amazon.com/blogs/machine-learning/unlock-global-ai-inference-scalability-using-new-global-cross-region-inference-on-amazon-bedrock-with-anthropics-claude-sonnet-4-5/)

## API 变更与代码更新

在 Amazon Bedrock 上迁移时，您可以使用模型专属的 InvokeModel API，也可以使用统一的 Converse API。

如果使用 InvokeModel API，迁移很直接。您只需要更新代码中的 `modelId`，因为 Anthropic 的 Messages API 的请求体结构在各版本之间保持一致：

- 旧模型 ID – `'anthropic.claude-3-5-sonnet-20240620-v1:0'` 或 `'anthropic.claude-3-5-sonnet-20241022-v2:0'`
- 新模型 ID – 对于 Claude Sonnet 4.5 为 `'anthropic.claude-sonnet-4-5-20250929-v1:0'`
- Claude Sonnet 4.5 仅支持指定 `temperature` 或 `top_p` 中的一个，而不能同时指定两者。请更新您现有的推理代码，只选择一个推理参数

如果为该模型使用 [CRIS profile](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-use.html)，请务必在某个源 Region 中指定[正确的 inference profile ID](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-support.html)，例如 us CRIS profile 使用 `'us.anthropic.claude-sonnet-4-5-20250929-v1:0'`，global CRIS 使用 `global.anthropic.claude-sonnet-4-5-20250929-v1:0`。

这次迁移是切换到 Converse API 的绝佳机会。它为 Amazon Bedrock 上的语言模型提供了标准化的请求/响应格式，使今后迁移到不同模型或不同提供商都简单得多。参见以下代码：

```
import boto3
 bedrock_runtime = boto3.client(service_name='bedrock-runtime')

# Simply change the model ID to switch models 
response = bedrock_runtime.converse( 
    modelId='us.anthropic.claude-sonnet-4-5-20250929-v1:0', 
    messages=[{'role': 'user', 'content': [{'text': "Your prompt here"}]}], 
    inferenceConfig={'maxTokens': 1024})

print(response['output']['message']['content'][0]['text'])
```

## Prompt 工程与行为转变

不要假定您已有的 prompt 在新模型上也能完美工作。遵循模型专属的最佳实践才是关键。

请参考 Anthropic 发布的 [Claude 4 prompt 工程最佳实践](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/claude-4-best-practices) 以取得最佳效果。例如，当 prompt 用 [XML 标签](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/use-xml-tags)（比如 `<document>`、`</document>`）清楚地分隔输入的不同部分时，Anthropic 的 Claude 模型表现最好。

Anthropic 的 Claude Sonnet 4.5 被设计为更精确地遵循指令。这是一大优势，但也可能意味着除非明确要求，它的输出不如 Claude 3.5 Sonnet 那样详尽铺陈。您用来定义 AI 人设的 system prompt 可能需要调整。

## 新的推理功能

Anthropic 的 Claude Sonnet 4.5 模型内置的 [extended thinking](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking) 是一项强大的能力。为释放新模型的深度推理能力，开发者可以在 API 调用中传入 `thinking` 关键字参数来启用 extended thinking。但要确保策略性地使用它——extended thinking 会产生额外费用，因为推理 token 按标准模型费率作为输出 token 计费。您需要为完整的思考过程付费（而不只是您看到的摘要），成本会随您设定的思考预算而增长。

我们建议对准确性至关重要的、需要深度多步分析的任务（例如复杂的科学问题或高难度的编程挑战）启用 extended thinking。

对于简单查询或对延迟敏感的应用，我们建议禁用 extended thinking。该功能既增加成本（推理 token 要计费），也增加响应时间。对许多任务来说，精心设计的 CoT prompt 仍是效率最高的选择。

要使用 extended thinking，只需在 Converse API 调用中加入 `additionalModelRequestFields` 参数并配置 `thinking`。您可以通过为 `budget_tokens` 设值来指定模型可用的最大思考 token 数。注意，对于 extended thinking，`maxTokens` 应大于 `budget_tokens`。参见以下代码：

```
import boto3

bedrock_runtime = boto3.client(service_name='bedrock-runtime')

# Add configurations to enable extended thinking
response = bedrock_runtime.converse(
    modelId='us.anthropic.claude-sonnet-4-20250514-v1:0',
    messages=[{'role': 'user', 'content': [{'text': "Your prompt here"}]}],
    inferenceConfig={'maxTokens': 2048},
    additionalModelRequestFields={"thinking":{"type": "enabled",
     "budget_tokens": 1024}}
)

reasoning_text = response['output']['message']['content'][0]['reasoningContent']['reasoningText']['text']
assistant_response = response['output']['message']['content'][1]['text']
```

下表展示了 extended thinking 的一个示例，以及它如何提升回答的准确性。我们用一个示例 prompt 分别询问 Anthropic 的 Claude 3.5 Sonnet v2 和 Claude Sonnet 4.5（已启用 thinking）：

```
Alan, Bob, Colin, Dave and Emily are standing in a circle. Alan is on Bob's immediate left. Bob is on Colin's immediate left. Colin is on Dave's immediate left. Dave is on Emily's immediate left. Who is on Alan's immediate right?
```

该表展示了两款模型的回答。借助 extended thinking，模型能够仔细地推理这个问题并得出正确答案。

| **模型** | **Extended Thinking** | **输出** | **正确答案** |
| --- | --- | --- | --- |
| **Claude 3.5 Sonnet v2** | **N/A** | 让我一步一步来解。首先，让我们理清已知条件：Alan 在 Bob 的紧左边；Bob 在 Colin 的紧左边；Colin 在 Dave 的紧左边；Dave 在 Emily 的紧左边。从任意一个人开始，我们把他们排成顺序：如果 Dave 在 Emily 的紧左边，那么 Emily 就在 Dave 的紧右边；如果 Colin 在 Dave 的紧左边，那么 Dave 就在 Colin 的紧右边；如果 Bob 在 Colin 的紧左边，那么 Colin 就在 Bob 的紧右边；如果 Alan 在 Bob 的紧左边，那么 Bob 就在 Alan 的紧右边。所以顺时针的顺序是：Alan → Bob → Colin → Dave → Emily。由于他们围成一圈，Emily 必须与 Alan 相邻才能闭合这个圈。因此，Emily 在 Alan 的紧右边。答案是 Emily。 | **否** |
| **Claude Sonnet 4.5 ** | *让我一步一步地推演一下。* *有 5 个人站成一圈：Alan、Bob、Colin、Dave 和 Emily。* *让我梳理一下已知信息：* *Alan 在 Bob 的紧左边* *Bob 在 Colin 的紧左边* *Colin 在 Dave 的紧左边* *Dave 在 Emily 的紧左边* *既然他们围成一圈，我需要确定顺序。让我从一个人开始，沿着圈子推。* *如果 Alan 在 Bob 的紧左边，那就意味着顺时针是：Alan，然后是 Bob。* *如果 Bob 在 Colin 的紧左边，那就意味着顺时针是：Bob，然后是 Colin。* *如果 Colin 在 Dave 的紧左边，那就意味着顺时针是：Colin，然后是 Dave。* *如果 Dave 在 Emily 的紧左边，那就意味着顺时针是：Dave，然后是 Emily。* *所以沿圆圈顺时针是：Alan → Bob → Colin → Dave → Emily* *但等一下，既然是圆圈，Emily 必须连回某个人。既然我们有 Alan → Bob → Colin → Dave → Emily，而这是 5 个人的完整一圈，那么 Emily 后面必须是 Alan。* *所以顺时针的完整一圈是：Alan → Bob → Colin → Dave → Emily → Alan* *这意味着 Emily 在 Alan 的紧左边，因此 Alan 的紧右边会是……让我仔细想一想。* *如果顺时针走：Alan → Bob → Colin → Dave → Emily →（回到 Alan）* *那么 Alan 的紧右边（从 Alan 顺时针方向）是 Bob。而 Alan 的紧左边（从 Alan 逆时针方向）是 Emily。* *等等，让我用已知条件再核对一遍：* *Alan 在 Bob 的紧左边 ✓（顺时针方向 Alan 紧接在 Bob 之前）* *Bob 在 Colin 的紧左边 ✓（顺时针方向 Bob 紧接在 Colin 之前）* *Colin 在 Dave 的紧左边 ✓（顺时针方向 Colin 紧接在 Dave 之前）* *Dave 在 Emily 的紧左边 ✓（顺时针方向 Dave 紧接在 Emily 之前）* *我确认在圆形排列中 Bob 就坐在 Alan 的正右手边。* | 让我一步一步来看：已知信息：Alan 在 Bob 的紧左边；Bob 在 Colin 的紧左边；Colin 在 Dave 的紧左边；Dave 在 Emily 的紧左边。让我沿圆圈梳理顺时针顺序：Alan → Bob（因为 Alan 在 Bob 的紧左边）；Bob → Colin（因为 Bob 在 Colin 的紧左边）；Colin → Dave（因为 Colin 在 Dave 的紧左边）；Dave → Emily（因为 Dave 在 Emily 的紧左边）。由于他们站成一圈，Emily 必须连回去才能闭合圆圈：Emily → Alan。所以完整的顺时针顺序是：Alan → Bob → Colin → Dave → Emily → Alan。因此，**Bob 在 Alan 的紧右边**。 | 是 |

启用 extended thinking 后，API 默认会[返回模型完整思考过程的摘要](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#summarized-thinking)，而不是整条推理链。这是一项防止滥用的保护措施，同时仍能提供完整的智能收益。开发者应当注意，这可能导致流式响应出现成块或延迟的模式，并应在应用的用户体验中加以考虑。

Anthropic 的 Claude 4 模型在与工具配合使用 extended thinking 时具备 [interleaved thinking](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking) 能力，使模型可以在工具调用之间进行中间推理，并基于收到的工具结果得出更细致的分析结论。要为工具调用[启用 interleaved thinking](https://aws.amazon.com/blogs/opensource/using-strands-agents-with-claude-4-interleaved-thinking/)，请在 Converse API 请求的 `additionalModelRequestFields` 中加入额外参数 `"anthropic_beta": ["interleaved-thinking-2025-05-14"]`。

关于使用 extended thinking 的更多细节，请参阅 [Extended thinking](https://docs.aws.amazon.com/bedrock/latest/userguide/claude-messages-extended-thinking.html)。

## 稳健的评测不可妥协

您必须验证新模型在您具体任务上的表现与旧模型持平或更好。请构建一套精心挑选的 prompt 与期望输出，使其高度代表您的生产流量。这套自建基准比任何公开报告的基准分数都更有价值。

把这套数据集接入自动化的评测 pipeline。该 pipeline 应成为您持续集成与持续交付（CI/CD）流程的一部分，作为未来模型或 prompt 变更的永久回归测试套件。在工具方面，团队可以使用 [Amazon Bedrock evaluations](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html) 这类内置方案，或 [RAGAS](https://docs.ragas.io/en/stable/howtos/integrations/amazon_bedrock/) 与 [DeepEval](https://dev.to/makawtharani/elevating-llm-evaluation-with-deepeval-with-native-aws-bedrock-support-155h) 这类开源评测框架。

## 管理集成的安全与治理

模型的安全特性会随版本变化。这必须作为集成系统的一部分进行测试。绝不要孤立地测试新模型。只有当您的迁移测试计划使用与生产环境完全相同的护栏配置（例如 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/)）来评测新模型时，它才是有效的。新模型的对话风格可能会以意想不到的方式触发既有护栏，导致被拦截的响应激增。

## 实施安全的部署策略

把 Anthropic 的 Claude Sonnet 4.5 部署到生产环境时，请采用分阶段的发布策略以降低风险。可以考虑影子测试，用镜像流量比较模型表现而不影响用户，然后进行 A/B 测试来衡量对业务 KPI 的影响。在实际发布阶段，可以采用金丝雀发布，逐步让一小部分用户接触新模型；也可以采用蓝绿部署，维持并行环境以便即时回滚。这种结构化的做法既有助于安全地验证新模型的表现，又能保持业务连续性。
