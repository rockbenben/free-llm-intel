# 使用 AWS Agent Registry 中的通用元数据管理和发现记录

随着组织构建更多代理、模型上下文协议 (MCP) 服务器和技能，他们需要一种一致的方式来描述、管理和查找它们。 [AWS Agent Registry](https://aws.amazon.com/blogs/machine-learning/manage-agents-tools-and-skills-at-scale-with-aws-agent-registry/) 提供用于注册、批准和发现这些资源和自定义记录的目录。每条记录都带有名称、描述、协议描述符和批准状态。然而，每个组织都有想要跟踪的属性和事实，其中一些属性和事实是该组织特有的，例如其业务部门、资源所有者、风险分类和开发环境。组织希望每个属性都有一个通用定义，并且希望注册表中的每个代理、MCP 服务器和技能都包含这些事实。到目前为止，组织无法在 AWS Agent Registry 中定义这些事实并将其存储在每条记录中。

AWS AgentRegistry 中现在提供自定义元数据架构。自定义元数据架构是一组组织定义的键值对，记录在 AWS 代理注册表中。管理员定义架构并将其应用到注册表，然后注册表中的所有记录都必须遵守该架构。当发布者创建或提交记录时，他们会为适用架构中指定的字段提供值，AWS Agent Registry 会根据管理员设置的架构验证这些值。审批者在审查记录时可以依赖经过验证的值，消费者和代理可以使用它们来发现和过滤记录。管理员、发布者、安全和治理团队、审批者、消费者和代理都根据一组共享的事实来管理、发现和理解其代理队列中的资源。

在这篇文章中，我们跟随 AnyCompany 组织发布具有自定义架构定义的 MCP 服务器，丰富该记录，并使其可供人类或代理发现。我们使用 MCP 服务器作为示例，但相同的步骤适用于其他记录类型。

## 自定义元数据如何工作

通过自定义元数据，组织可以使用标准化词汇来描述其资源。注册表管理员定义[自定义元数据架构](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-custom-metadata-schema.html)：字段名称、类型、允许的值以及每个字段是必填还是可选。注册表在每条记录上强制执行该架构，因此无论哪个团队发布该记录，`environment` 等字段都具有相同的名称和相同的允许值。

该架构具有适用于每种记录类型的通用属性，并且您可以添加仅适用于特定记录类型的专用字段。每个字段都是文本、枚举、URL 或布尔值。

- 创建或更新记录时，注册表会根据管理员设置的架构验证自定义元数据。   如果创建的记录***没有任何自定义元数据，*** AWS Agent Registry 会将其保存为 `NON_COMPLIANT`。团队可以通过这种方式保存正在进行的工作，但在具有所需的字段和值之前，无法提交记录以供审批。  如果记录***包含自定义元数据***且字段未知、缺少必填字段或无效值，则 AWS Agent Registry 会拒绝该记录并返回 `ValidationException`。
- `GetRegistryRecord` 返回记录的自定义元数据值及其合规状态。 （`COMPLIANT` 表示这些值与管理员的架构匹配。这不是批准。批准者做出决定。）
- 发现 API 还允许根据自定义属性过滤记录。

## 自定义元数据使什么成为可能

由于团队可以使用相同的字段和值描述 AWS 代理注册表记录，因此注册表可以支持和扩展治理和合规性。

### 所有权和运营

`environment`（`prod`、`staging` 或 `dev`）、`businessUnit`、`ownerTeam`、`supportContact` 和 `costCenter` 等字段记录资源运行的位置、负责人以及付费者。配置管理数据库 (CMDB) ID 将记录链接到现有库存，支持层字段为依赖该资源的任何人设置期望。

### 安全与合规性

数据分类、支付卡行业 (PCI) 或健康保险流通与责任法案 (HIPAA) 等合规范围、风险等级、扫描状态和扫描报告 URL 将批准转变为对结构化证据的检查。您现有的扫描仪、CMDB 同步作业和分类工具在提交记录之前通过 API 写入这些值。您可以使用这些值构建记录审批流程或自动化，如本文所示。

### 更好的发现

自定义元数据值已编入索引以供搜索。消费者或代理可以将自然语言查询与特定元数据过滤器（例如 `environment=prod AND businessUnit=payments AND securityScanStatus=PASSED`）相结合。仅返回批准的记录，因此与过滤器匹配但尚未批准的记录不会出现在结果中。 *图 1* 显示了从管理员到消费者的每个角色如何通过模式定义、注册、充实、批准和发现来移动记录。

### 先决条件

要按照演练操作，您需要：

- [支持的 AWS 区域](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-regions.html) 中的 AWS 账户。
- Boto3 可用的 AWS 凭证以及 AWS Agent Registry 的 AWS Identity and Access Management (IAM) 权限。
- Python 3.11 或更高版本和 boto3 1.43.113 或更高版本。
- [示例实现](https://github.com/awslabs/agentcore-samples/tree/main/01-features/07-centralize-and-govern-your-ai-infrastructure/03-registry/03-advanced/custom-metadata-in-registry) 位于 GitHub 存储库中。

代码片段已缩短：`cp` 和 `dp` 是 `agent-registry-control` 和 `agent-registry` boto3 客户端。示例存储库具有完整的代码。

### 第 1 步：AWS Agent Registry 管理员为注册表定义自定义元数据架构

AnyCompany 的管理员创建一个具有自定义元数据模式的注册表，每条记录都必须遵循该模式。

- **每条记录必须具有**其 `environment`、`businessUnit` 和 `securityScanStatus` 字段。
- 记录还可以携带发布者或自动化稍后填写的可选字段：`ownerTeam`、`cmdbId`、`dataClassification` 和 `securityScanReportUrl`。
- MCP 服务器还记录其 `networkEgress`，这是可选的。
```
default_schema = {"type": "object", "properties": {
    "environment": {"type": "string", "enum": ["prod", "staging", "dev"]},
    "businessUnit": {"type": "string"},
    "ownerTeam": {"type": "string"},
    "cmdbId": {"type": "string"},
    "dataClassification": {"type": "string", "enum": ["public", "internal", "confidential", "restricted"]},
    "securityScanStatus": {"type": "string", "enum": ["PENDING", "PASSED", "FAILED"]},
    "securityScanReportUrl": {"type": "string", "format": "uri"},
}, "required": ["environment", "businessUnit", "securityScanStatus"]}

mcp_schema = {"type": "object", "properties": {"networkEgress": {
    "type": "string", "enum": ["none", "vpc-only", "allowlisted-internet"]}}}

cp.create_registry(
    name="anycompany-governed-registry",
    approvalConfiguration={"autoApprovalRules": []},
    customMetadataSchemaConfiguration={
        "defaultSchema": json.dumps(default_schema),
        "recordTypeSchemaOverrides": [
            {"recordType": "MCP", "schema": json.dumps(mcp_schema)}]})
```
图 3 显示了此架构以及步骤 3 中完成丰富后将携带的值 `payments-ledger-mcp`。空的 `autoApprovalRules` 列表意味着注册表本身不会批准任何内容。每条提交的记录都会保留在 `Pending approval` 中，直到有人或某事批准为止。您可以决定是通过您构建的自动检查（步骤 4 使用 AWS Lambda 函数）、人工审批者还是两者来完成。

### 步骤2：发布者注册服务器

支付团队的管道使用其自定义元数据注册 `payments-ledger-mcp`。它的第一次尝试使用 `production` 而不是管理员允许的值之一。
```
customMetadata sent by the pipeline:

{
    "environment": "production",
    "businessUnit": "payments",
    "securityScanStatus": "PENDING"
}

ValidationException: Custom metadata validation failed for record type MCP: /environment: does not have a value in the enumeration ["prod", "staging", "dev"]
```
注册表拒绝该记录。管道发送 `prod` 后，记录将创建为合规草稿。这就是模式如何让每个团队使用相同的值。

### 步骤 3：自动化添加额外元数据并提交

接下来，AnyCompany 的自动化添加了自己的系统所知道的内容：安全扫描器的结果、CMDB 的资产 ID 以及批准的数据分类。然后提交记录以供批准。
```
record = cp.get_registry_record(registryId=registry_id, recordId=record_id)
scan = run_security_scan(record)  # Replace this stub with your scanner call.
metadata = {**record["customMetadata"],
    "cmdbId": get_cmdb_id(record),
    "dataClassification": get_classification(record),
    "securityScanStatus": scan["status"],
    "securityScanReportUrl": scan["report_url"]}
cp.update_registry_record(registryId=registry_id, recordId=record_id,
    customMetadata={"optionalValue": metadata})
wait_for_record(cp, registry_id, record_id, "DRAFT")
cp.submit_registry_record_for_approval(
    registryId=registry_id, recordId=record_id)
```
更新[替换整个元数据映射](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-custom-metadata-values.html)，因此自动化会读取当前值，添加自己的值，然后将它们写回到一起。在示例中，扫描程序和 CMDB 调用是您可以用自己的工具替换的存根。注册表将 [待批准事件](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-notifications-approvals.html) 发送到 Amazon EventBridge。在步骤 4 中，您创建的规则将事件传递给您的审批功能。

### 步骤4：批准自动化根据证据决定

当记录转至待批准状态时，AWS Agent Registry 会向 Amazon EventBridge 发送一个事件，并设置 Amazon EventBridge 规则来调用自定义 AWS Lambda 函数。 *图 5* 显示了 `payments-ledger-mcp` 的控制台视图，其中包含批准功能读取以进行检查的自定义元数据值。

![AWS Agent Registry 控制台显示 payment-ledger-mcp 记录上的自定义元数据值](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/16/ML-22167-5.png)

图 5：记录上的自定义元数据是审批功能将检查的证据

该函数读取记录的自定义元数据和合规性状态，以检查记录是否为 `COMPLIANT`、扫描 `PASSED`、是否存在 `cmdbId`，以及数据是公共的还是内部的。 `payments-ledger-mcp` 通过了全部四项，因此该功能获得批准。检查失败的记录将被拒​​绝，并给出失败检查的原因。在您的生产系统中，您可以选择路由需要人工审核的记录（例如具有机密或受限数据的记录）以进行人工审核，而不是被拒绝。

### 步骤 5：消费者使用自定义元数据字段作为过滤器从 AWS Agent Registry 查找记录

寻找账本工具的开发人员会搜索注册表并过滤管理员定义的相同字段。
```
dp = boto3.client("agent-registry")
matches = dp.search_discoverable_registry_records(
    registryIds=[registry_id],
    searchQuery="ledger lookup",
    filters={"$and": [
        {"customMetadata.environment": {"$eq": "prod"}},
        {"customMetadata.businessUnit": {"$eq": "payments"}},
        {"customMetadata.securityScanStatus": {"$eq": "PASSED"}},
    ]},
)
```
搜索返回 `payments-ledger-mcp`，因为它已获得批准并匹配所有三个过滤器。代理可以通过注册表的 MCP 端点 `https://agentregistry.<region>.api.aws/registry/<registryId>/mcp` 运行相同的搜索，该端点提供搜索、列表和获取作为 MCP 工具。在 GitHub 示例中，Strands 代理连接到 AWS Registry MCP 终端节点并使用 Amazon Bedrock 上的模型。其系统提示列出了用于过滤记录的自定义元数据字段。该代理将简单语言请求（例如“用于通过安全扫描进行支付分类账查找的生产 MCP 服务器”）转换为过滤搜索。它以 `payments-ledger-mcp` 回答。

开发人员和代理查询管理员定义的相同字段，并检查批准功能，因此两者都只查找满足您的治理规则的服务器。

## 设计长期使用的架构

将架构视为组织的共享词汇表：

- 首先就词汇达成一致。在创建架构之前，与发布和批准记录的团队确定字段名称和允许的值。 [架构更改是附加的](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-custom-metadata-schema.html)：您可以添加字段、添加允许的值或将可选字段设为必填，但不能重命名、删除或重新输入字段。
- 预计现有记录会落后于将记录添加到注册表后所做的架构更改。现有记录不会被重写。不再与架构匹配的记录将报告为 `NON_COMPLIANT` 并保留其审批状态。该记录保持批准状态，但其下一次更新必须符合新架构。编辑已批准的记录会创建一个草稿，必须再次提交该草稿以供批准，并且在每个必填字段都有值之前，提交会失败。在策展人批准新修订版之前，消费者会一直看到已批准的修订版。
- 将每个字段置于正确的级别。对适用于每种记录类型的问题使用通用属性，对特定于记录的事实使用记录类型字段，例如代理的“自治级别”。
- 选择适合该领域的类型。对需要一致拼写的决策字段使用枚举，对外部标识符使用文本，对存储在源系统访问控制后面的证据使用 URL。
- 仅当发布者可以在注册时分配值时，才将字段设置为必填字段。对于持续集成 (CI) 或自动化在记录发布后提供的值，请允许使用临时值，例如 `PENDING`。在本文中，扫描在注册后运行，因此 `securityScanStatus` 具有三个值：`PENDING`、`PASSED` 和 `FAILED`。出版商编写了 `PENDING`，浓缩自动化取代了它。
- 保留敏感细节。将秘密、内部端点和详细的发现排除在广泛可读的元数据之外。

## 结论

在这篇文章中，我们展示了如何在 AWS Agent Registry 中添加自定义元数据，为每条记录提供一组通用的事实，例如其环境、所属业务部门、数据分类和安全扫描状态。使用一台 MCP 服务器，我们向管理员展示了定义架构、发布者和现有的自动填写值、您在 AWS Lambda 中构建的批准功能（决定批准）以及消费者通过元数据过滤器查找批准的服务器。由于管理员拥有架构，因此每个团队都使用相同的字段和值，这种一致性使得 AWS Agent Registry 中的批准和搜索变得可靠。
