# 用 Amazon Bedrock AgentCore 突破上下文窗口瓶颈

当你分析横跨数百万字符的文档时，就会撞上上下文窗口这道墙，即便是最大的上下文窗口也不够用。模型要么拒绝输入，要么基于不完整的信息给出答案。面对放不下的文档，你该如何推理？

本文中，你将学习如何使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) Code Interpreter 和 [Strands Agents SDK](https://strandsagents.com/) 实现递归语言模型（RLM）。读完本文，你将了解如何：

- 处理长度各异的文档，上下文大小没有上限。
- 把 [Bedrock AgentCore Code Interpreter](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/code-interpreter-tool.html) 用作持久的工作记忆，支撑迭代式文档分析。
- 在沙箱化的 Python 环境中编排对子大语言模型（sub-LLM）的调用，用以分析特定的文档片段。

## 为什么上下文窗口还不够

设想一个典型的财务分析任务：对比同一家公司两个年度报告中的各项指标。每份报告有 300–500 页。再加上分析师报告、SEC 备案文件和补充材料，总量可达数百万字符。

当你把这些文档直接发给模型时，要么输入超出模型的上下文窗口上限、请求失败，要么输入虽然放得下，但模型难以关注到长输入中间部分的信息，这常被称为「中间丢失」（lost in the middle）问题。

这两种失败模式之所以存在，都是因为上下文窗口大小是一道硬性上限，仅靠 prompt 工程无法解决。你需要一种把文档规模与模型的上下文窗口解耦的做法。

## RLM：把上下文当作环境

RLM 由 Zhang 等人在 [arXiv:2512.24601](https://arxiv.org/abs/2512.24601) 中提出，它重新定义了这一问题。RLM 不再把整份文档塞进模型的上下文窗口，而是把输入视为一个外部环境，由模型以编程方式与之交互。

![递归语言模型（RLM）的架构图，展示三个层次：顶部的根 LLM 编写代码并产出最终响应；中间的 REPL 环境（工作记忆）把长 prompt 作为变量存放，并执行代码以检视、分解和累积结果；底部的递归调用层并行发起子任务 LLM 调用。箭头展示了迭代流程：用户查询进入 REPL 环境，根 LLM 编写代码以符号方式交互，Python 变量向上回流，根 LLM 依据当前结果创建子任务，子响应返回工作记忆。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/07/ML-20487-image-1.png)

*图 1. 递归语言模型以迭代循环的方式运行：根 LLM 生成代码来探索文档环境，把语义分析委派给针对选定片段的 sub-LLM，并在改进下一步之前把结果累积到工作记忆之中。*

模型只会收到查询和可用环境的描述。随后它编写代码来迭代地搜索、切片和分析文档。当模型需要理解某个特定章节的语义时，就把这项分析委派给一次 sub-LLM 调用，结果以 Python 变量的形式留在工作记忆中，而不占用上下文窗口空间。

这形成了一种递归结构：根 LLM 通过代码编排分析，在需要语义任务时按需调用 sub-LLM，而整份文档始终不进入模型的上下文窗口。

## 架构

这里我们展示如何使用 Amazon Bedrock AgentCore Code Interpreter 作为执行环境来实现 RLM。Amazon Bedrock AgentCore Code Interpreter 提供一个沙箱化的 Python 运行时，其状态可跨多次执行持久保留。该架构由三个协同工作的组件构成。

一个用 Strands Agents SDK 构建的根 LLM agent 接收用户的查询，并决定要执行什么代码。一个运行在 PUBLIC 网络模式下的 Amazon Bedrock AgentCore Code Interpreter 会话，把整份文档作为 Python 变量加载。注入沙箱的 `llm_query()` 函数直接从 Code Interpreter 内部调用 Amazon Bedrock，因此 sub-LLM 的结果留在 Python 变量中，不会回流到根 LLM 的上下文窗口。

*![架构图，展示基于 Amazon Bedrock AgentCore 的 RLM 实现。流程分为三个编号部分：（1）输入——长上下文文档与用户查询送入 RLM Agent；（2）带执行环境的 RLM——RLM Agent 通过 Execute Python Tool 把代码发送到 Amazon Bedrock AgentCore Code Interpreter，后者已把整份文档加载为 Python 变量，并提供 llm_query() 函数用于 sub-LLM 调用，sub-LLM 的结果留在变量中而不返回根 LLM 上下文；（3）Amazon Bedrock LLM——Code Interpreter 向 Amazon Bedrock 基础模型发起出站调用，用于对文档片段做语义分析。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/07/ML-20487-image-2.png)*

*图 2. 使用 Amazon Bedrock AgentCore Code Interpreter 的 RLM 架构。根 LLM agent 在沙箱环境中迭代地编写并执行 Python 代码，完整的输入数据已预先载入其中。agent 可以在沙箱内部经 Amazon Bedrock 调用 sub-LLM，对特定章节做语义分析。中间结果作为 Python 变量留在沙箱中，使根 LLM 的上下文窗口专注于编排。*

Amazon Bedrock AgentCore Code Interpreter 的 PUBLIC 网络模式为此提供支持：它允许沙箱向 Amazon Bedrock 发起出站 API 调用。会话状态的持久化意味着变量、中间结果和提取到的数据会在多次代码执行之间不断累积，从而为模型提供贯穿整个分析过程的持久工作记忆。

## 实现

请按以下步骤用 Amazon Bedrock AgentCore Code Interpreter 搭建并运行 RLM。

## 前提条件

要跟随本文操作，你需要：

- 一个可访问 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 基础模型（FM）的 [AWS 账户](https://aws.amazon.com/free/)。
- Python 3.10 或更高版本。
- 已配置好相应凭证的 [AWS Command Line Interface (AWS CLI)](https://aws.amazon.com/cli/)。
- 熟悉 Python 以及 AWS SDK（Boto3）的基本用法。
- 一个配置为 PUBLIC 网络模式的 Amazon Bedrock AgentCore Code Interpreter。
- 用于 `bedrock:InvokeModel`、`bedrock-agentcore:StartCodeInterpreterSession`、`bedrock-agentcore:InvokeCodeInterpreter` 和 `bedrock-agentcore:StopCodeInterpreterSession.` 的 IAM 权限。

**1：启动 Code Interpreter 会话并加载文档**

创建一个 Amazon Bedrock AgentCore Code Interpreter 会话，并把文档写入沙箱：

```
import boto3
import json

# Start a Bedrock AgentCore Code Interpreter session
client = boto3.client('bedrock-agentcore', region_name='us-east-1')
response = client.start_code_interpreter_session(
    codeInterpreterIdentifier=code_interpreter_id,
    name="rlm-session",
    sessionTimeoutSeconds=3600
)
session_id = response["sessionId"]

# Write the document to the sandbox
client.invoke_code_interpreter(
    codeInterpreterIdentifier=code_interpreter_id,
    sessionId=session_id,
    name="writeFiles",
    arguments={"content": [{"path": "_context.txt", "text": document}]}
)
```

**2：初始化文档，并在沙箱内定义 llm_query() 辅助函数**

在沙箱内加载文档，并定义 sub-LLM 调用将要使用的 `llm_query()` 函数：

```
# Runs inside the Bedrock AgentCore Code Interpreter sandbox
with open('_context.txt', 'r') as f:
    context = f.read()

def llm_query(prompt: str) -> str:
    """Query a sub-LLM from within the sandbox."""
    response = bedrock_client.invoke_model(
        modelId=sub_model_id,
        body=json.dumps({
            "anthropic_version": "bedrock-2023-05-31",
            "max_tokens": 4096,
            "messages": [{"role": "user", "content": prompt}]
        })
    )
    result = json.loads(response['body'].read())
    return result['content'][0]['text']
```

**3：创建 Strands Agent 并运行你的查询**

创建一个带单个 `execute_python` 工具的 Strands Agent，该工具在会话中运行代码，然后提交你的问题：

```
from strands import Agent

agent = Agent(
    model="us.anthropic.claude-sonnet-4-5-20250929-v1:0",
    system_prompt=rlm_system_prompt,
    tools=[execute_python],
)

answer = agent("What are the key revenue trends across these reports?")
```

agent 会迭代地编写并执行 Python 代码，以探索文档、提取相关章节，并在需要对特定片段做语义分析时调用 `llm_query()`。

## 评估

在我们的评估中，我们把 RLM 与两个基线作比较，即 *Base* 和 *Long Context*。在 Base 方法中，整份文档在一次 API 调用中直接发给具有 200K token 上下文窗口的模型。这是最直接的策略，但当文档超出模型的上下文窗口时就会失败。在 Long Context 方法中，我们使用 Claude 扩展后的 100 万 token 上下文窗口，它能处理更大的输入，但仍存在上限，并且可能遭受「中间丢失」之类的问题。

我们在 [LongBench v2](https://huggingface.co/datasets/zai-org/LongBench-v2) 的 Financial Multi-Document QA 子集上评估了这一方法，该基准用于测试 LLM 在需要跨长上下文推理的任务上的表现。该子集包含 15 道多选题，每道题都需要跨多份财务报告进行分析，上下文长度最高约 200 万字符。

我们报告两项指标：*成功率*，即模型在不超出输入上限、不遇到错误的前提下能够处理的题目百分比；以及*准确率*，即正确答案数占全部提问数的百分比（未回答的题计为错误）。

我们比较了前面描述的三种方法：*Base*、*Long Context* 和 *RLM*。我们在四个 Claude 模型作为根 LLM 的情况下评估 RLM，其中 sub-LLM 配置为同一模型或 Haiku 4.5，以平衡性能与效率。我们选用 Claude Haiku 4.5 作为 sub-LLM，因为它在做局部片段级分析时延迟和成本都显著更低，而根模型仍负责全局推理与编排。

*表 1. LongBench v2 Financial Multi-Document QA（15 道题）。人工专家的准确率来自 LongBench v2 论文。* *Claude Sonnet 4.6 和 Opus 4.6 的 Base 结果被省略，因为这些模型默认具有 100 万 token 的上下文窗口，使 Base 与 Long Context 两种方法等价。*

| **模型** | **方法** | **成功率** | **准确率** |
| --- | --- | --- | --- |
| Claude Haiku 4.5 | Base | 46.7% | 33.3% |
| Claude Haiku 4.5 + Haiku 4.5 | RLM | 100.0% | 66.7% |
| Claude Sonnet 4.5 | Base | 46.7% | 26.7% |
| Claude Sonnet 4.5 | Long Context | 93.3% | 66.7% |
| Claude Sonnet 4.5 + Haiku 4.5 | RLM | 100.0% | 66.7% |
| Claude Sonnet 4.6 | Long Context | 93.3% | 60.0% |
| Claude Sonnet 4.6 + Haiku 4.5 | RLM | 100.0% | 73.3% |
| Claude Opus 4.6 | Long Context | 93.3% | 66.7% |
| Claude Opus 4.6 + Haiku 4.5 | RLM | 100.0% | **80.0%** |
| 人工专家 | – | – | 40% |

结果揭示了三个关键发现：

- **RLM 缓解了上下文长度导致的失败。**Base 和 Long Context 方法因上下文限制而无法处理某些输入。Base 方法的成功率为 46.7%（7/15 题），Long Context 为 93.3%（14/15 题）。相比之下，RLM 通过彻底解耦文档规模与上下文窗口大小，在所有评估配置下都达到 100% 的成功率。随着文档规模增大，这一可靠性优势对实际部署越来越重要。
- **RLM 在多数模型上提升了准确率。**RLM 把 Claude Sonnet 4.6 和 Opus 4.6 的准确率分别从 60.0% 和 66.7%（Long Context）提升到 73.3% 和 80.0%，并把 Claude Haiku 4.5 从 33.3%（Base）提升到 66.7%。提升幅度最大的是 Claude Haiku 4.5，而更强的模型（Sonnet 4.6、Opus 4.6）提升稳定但幅度较小。Claude Sonnet 4.5 相比 Long Context 基线没有提升，两种设置下都是 66.7%。这表明 RLM 的收益取决于根模型把任务拆解为子查询的有效程度，而这一点在此设置下可能限制了 Sonnet 4.5 的提升。
- **在此设置下，sub-LLM 的选择影响有限。**在额外实验中，我们对比了把 Claude Haiku 4.5 用作 sub-LLM 与根模型和 sub-LLM 使用同一模型两种情况，发现各配置之间的准确率没有显著差异。这表明对于该任务，性能主要由根模型能否生成有效的子查询决定，而非执行这些查询的 sub-LLM 的能力。

## 扩展到代码仓库理解：LongBench v2 CodeQA

Financial QA 评估聚焦于长篇文档推理。接下来我们考察在另一个领域的泛化能力：**代码仓库理解**，这需要在大规模代码库中导航、解析函数依赖关系，并跨文件追踪逻辑。这一场景特别适合通过代码执行进行程序化探索。

为验证这一点，我们在 LongBench v2 的 Code Repository Understanding 子集上进行了评估，该子集包含 50 道多选题。每道题都提供整个代码仓库作为上下文（范围从约 100K 字符到超过 16M 字符），并考察实现细节、API 行为或架构决策等需要浏览并理解代码库的问题。

架构与 Financial QA 相同：整个仓库作为单个上下文变量加载到 Code Interpreter 沙箱中。模型编写 Python 代码来搜索相关文件、提取函数定义、追踪调用链，并使用 `llm_query()` 分析特定的代码段。

我们用同样的方法、以四个 Claude 模型评估了全部 50 道题。基于 Financial QA 的发现——sub-LLM 的选择对更强的模型影响有限——我们在所有 RLM 运行中把 sub-LLM 固定为 Claude Haiku 4.5。

*表 2. LongBench v2 Code Repository Understanding（50 道题）。*

| **模型** | **方法** | **成功率** | **准确率** |
| --- | --- | --- | --- |
| Claude Haiku 4.5 | Base | 30.0% | 20.0% |
| Claude Haiku 4.5 + Haiku 4.5 | RLM | 100.0% | 64.0% |
| Claude Sonnet 4.5 | Base | 30.0% | 20.0% |
| Claude Sonnet 4.5 | Long Context | 60.0% | 46.0% |
| Claude Sonnet 4.5 + Haiku 4.5 | RLM | 100.0% | **76.0%** |
| Claude Sonnet 4.6 | Long Context | 60.0% | 42.0% |
| Claude Sonnet 4.6 + Haiku 4.5 | RLM | 100.0% | 66.0% |
| Claude Opus 4.6 | Long Context | 60.0% | 44.0% |
| Claude Opus 4.6 + Haiku 4.5 | RLM | 100.0% | 74.0% |

结果与 Financial QA 的发现一致：RLM 在所有模型上都达到 100% 的成功率，而 Base 和 Long Context 只有 30–60%。在 RLM 下，各模型的准确率大幅提升，每个模型都落在 64% 到 76% 之间——而 Base 和 Long Context 下只有 20–46%。

## 模型如何一步步解决一个问题

为说明 RLM 在实践中如何运作，下面是一个评估题目中具有代表性的执行序列。模型被要求对比两份年度报告中的财务指标，两份报告合计约 150 万字符。

首先，模型在上下文中搜索结构标记，以了解文档布局：

```
matches = re.findall(r'Table of Contents|ANNUAL REPORT', context)
```

接着，它切出特定章节来查找营收表格：

```
revenue_section = context[450000:500000]
print(revenue_section)
```

需要语义分析时，它委派给 sub-LLM：

```
analysis = llm_query(f"Compare these revenue figures: {chunk}")
```

最后，它汇总多个章节的发现，得出最终答案。

## 注意事项

在为你的文档分析工作负载采用 RLM 时，请留意以下实际权衡。

- **延迟。**RLM 用延迟换能力。基于我们对两个 LongBench v2 数据集的评估，单次 RLM 运行从简单问题约 10 秒到上下文很大的复杂问题数分钟不等，大多数能在几分钟内完成。对于批处理或离线分析，这个权衡非常值得。对于实时应用，请考虑该任务是否真的需要处理超出模型上下文窗口的文档。
- **成本。**每次 RLM 运行都涉及多次模型调用，既有根 LLM 的迭代推理，也有沙箱内发出的 sub-LLM 调用。对于成本敏感的工作负载，你可以用更小的模型（如 Haiku 4.5）作为子模型，同时保留更大的模型作为根模型，以在降低成本的同时保持准确率。
- **prompt 工程。**系统 prompt 会影响模型使用工具的效率。若缺乏引导，模型往往会产生不必要的 sub-LLM 调用来验证自己的推理，或通过代码执行打印冗长的中间摘要。清楚地说明何时使用代码执行、何时直接推理，可以减少无效的工具调用并改善端到端延迟。

```
    sessionId=session_id

```

## 结论

递归语言模型为处理超出模型上下文窗口的文档提供了一条实用路径。通过把 Amazon Bedrock AgentCore Code Interpreter 与 Strands Agents SDK 结合，你可以实现 RLM，借助迭代式代码执行和 sub-LLM 调用来对任意长度的输入数据进行推理。

在我们的各项评估中，结果颇为显著：Claude Opus 4.6 搭配 RLM 在 LongBench v2 Financial QA 上达到 80.0% 的准确率（相比之下，具有 100 万 token 上下文窗口的 Long Context 为 66.7%，人类专家为 40%），Claude Sonnet 4.5 搭配 RLM 在 LongBench v2 Code Repository QA 上达到 76.0%（相比之下，具有 200K token 上下文窗口的 Base prompting 为 20.0%，Long Context 为 46.0%）。

需要在长上下文或大型参考库上推理的任务都能从这一模式中受益，无论是财务分析、代码仓库理解、医疗与生命科学研究、法律审阅还是合规审计。如果你在自己的文档分析工作负载上尝试了这一方法，我们很想了解你构建的东西。欢迎在评论区分享你的经验。
