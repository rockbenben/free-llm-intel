# 从新手到冠军：一名学生在 AWS AI League 东盟总决赛中的历程

由 [Amazon Web Services (AWS)](https://aws.amazon.com/) 发起的 [AWS AI League](https://aws.amazon.com/ai/aileague/)，去年把覆盖范围扩展到东南亚国家联盟（ASEAN），迎来来自新加坡、印度尼西亚、马来西亚、泰国、越南和菲律宾的学生参赛者。其目标是通过一场以微调大语言模型（LLM）为核心、游戏化的动手挑战，把各种背景与经验水平的学生带入生成式 AI 这个激动人心的世界。

在本篇博文中，你将直接听到 AWS AI League 冠军 Blix D. Foryasen 的分享，他回顾了整场竞赛中的挑战、突破与关键收获。

## 竞赛背后

AWS AI League 竞赛以一场教程课程开场，由 AWS 团队与 [Gen-C Generative AI Learning Community](https://gen-c.info/) 主讲，介绍了两个强大且易用的服务：[Amazon SageMaker JumpStart](https://aws.amazon.com/sagemaker/ai/jumpstart/) 与 [PartyRock](https://partyrock.aws/)。

- SageMaker JumpStart 让参与者能够在云端环境中运行 LLM 微调流程，并可灵活调整超参数、优化性能。
- 由 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 驱动的 PartyRock，提供了直观的演练场与界面，用于整理微调 Llama 3.2 3B Instruct 模型所用的数据集。Amazon Bedrock 汇集了来自领先 AI 公司的大量高性能基础模型，包括 Anthropic Claude、Meta Llama、Mistral 等；全部可通过单一 API 访问。

以在基于测验的评测中跑赢一个更大的 LLM 参考模型为目标，参与者需围绕生成式 AI 的三个核心领域展开：基础模型、负责任 AI 与 prompt 工程。预赛采用公开排行榜，为该地区表现最好的微调模型排名。每个提交的模型都会通过与一个更大的基线 LLM 对决来测试，评测方式是对生成式 AI 相关问题做自动化、测验式的评估。评估由一位未公开的 LLM 裁判执行，兼顾准确性与全面性。模型每次跑赢基线 LLM，其胜率就会提升。这项挑战在技术属性之外还需要战略规划。参与者必须在 SageMaker JumpStart 上充分利用有限的训练时长，同时谨慎管理受限的排行榜提交次数。该上限最初为 5 小时，后来根据社区反馈扩大到 30 小时。提交次数也会影响决赛入围评定的并列名次判定。

每个国家的最高分调参者晋级 [区域总决赛](https://www.youtube.com/watch?v=U-_t1keLzsA)，该赛事于 2025 年 5 月 29 日在新加坡举行。决赛选手在那里正面对决，各自展示其微调模型对一组新问题的回答。最终成绩由加权评审体系决定：

- 40% 来自 LLM-as-a-judge
- 40% 来自专家
- 20% 来自现场观众。

## 务实的微调思路

在深入技术细节之前，先做一个简短声明：以下各节分享的做法大多是实验性的，来自反复试错。它们未必是微调的最优方法，也不构成权威指南。其他决赛选手因为技术背景不同而采用了不同的做法。最终帮助我成功的，不只是技术上的精确，还有协作、随机应变，以及愿意根据往届经验去推演这场竞赛可能如何发展的探索精神。我希望这份记述能为未来可能面临类似约束的参与者提供一个基线或启发。即便你像我一样从零开始，保持策略性、好奇心与社区驱动也确有价值。我遇到的最大障碍之一是时间，或者说时间的匮乏。由于参赛确认较晚，我在竞赛开始两周后才加入。这让我只剩两周时间来规划、训练和迭代。考虑到时间紧张、SageMaker JumpStart 上的算力时长有限，我知道必须让每一次训练都算数。我没有去做穷举式实验，而是把精力集中在打磨一个强数据集和调整部分超参数上。这一路上，我从学术论文和 LLM 微调的既有做法中汲取灵感，在约束范围内尽可能做调整。

## 打造合成数据的“精彩”

如前所述，竞赛开始时的关键学习环节之一，向参与者介绍了 SageMaker JumpStart 与 PartyRock——这两款工具让微调与合成数据生成既易用又直观。特别是 PartyRock，让我们可以克隆并自定义应用，从而控制合成数据集的生成方式。我们可以调整 prompt 结构、创造性水平（temperature）和 token 采样策略（top-p）等参数。PartyRock 还让我们可以使用多种基础模型。从一开始，我就选择用 Claude 3.5 Sonnet 来生成数据集，力求在竞赛的三个核心子领域上实现广泛而均衡的覆盖。为尽量减少偏差、在各主题之间实现公平代表性，我整理了多个版本的数据集，每个版本从 1,500 到 12,000 个问答对不等，并仔细保持各子领域之间的分布均衡。以下是我重点关注的几个示例主题：

- **Prompt 工程**：零样本提示、思维链（CoT）提示、评估 prompt 的有效性
- **基础模型**：Transformer 架构、预训练与微调的区别
- **负责任 AI**：数据集偏差、代表性公平性，以及 AI 系统中的数据保护

为保持数据质量，我对数据集生成器做了调整，强调事实准确性、独特性与应用知识。每批生成包含 10 个问答对，prompt 专门设计以鼓励深度与清晰度。

**问题 prompt：**

```
You are a quiz master in an AI competition preparing a set of challenging quiz bee questions about [Topic to generate] The purpose of these questions is to determine the better LLM between a fine-tuned LLaMA 3.2 3B Instruct and larger LLMs. Generate [Number of data rows to generate] questions on [Topic to generate], covering: 
	* Basic Questions (1/3) → Direct Q&A without reasoning. Must require a clear explanation, example, or real-world application. Avoid one-word fact-based questions.
	* Hybrid Questions (1/3) → Requires a short analytical breakdown (e.g., comparisons, trade-offs, weaknesses, implications). Prioritize scenario-based or real-world dilemma questions.
	* Chain-of-thought (CoT) Questions (1/3) → Requires multi-step logical deductions. Focus on evaluating existing AI methods, identifying risks, and critiquing trade-offs. Avoid open-ended "Design/Propose/Create" questions. Instead, use "Compare, Evaluate, Critique, Assess, Analyze, What are the trade-offs of…" 

Ensure the questions on [Topic to generate]: 
	* Are specific, non-trivial, and informative.
	* Avoid overly simple questions (e.g., mere definitions or fact-based queries).
	* Encourage applied reasoning (i.e., linking theoretical concepts to real-world AI challenges).
```

**答案 prompt：**

```
You are an AI expert specializing in generative AI, foundation models, agentic AI, prompt engineering, and responsible AI. Your task is to generate well-structured, logically reasoned responses to a list of [Questions], ensuring that all responses follow a chain-of-thought (CoT) approach, regardless of complexity, and formatted in valid JSONL. Here are the answering guidelines: 
	* Every response must be comprehensive, factually accurate, and well-reasoned.
 	* Every response must use a step-by-step logical breakdown, even for seemingly direct questions.
For all questions, use structured reasoning:
	* For basic Questions, use a concise yet structured explanation. Simple Q&As should still follow CoT reasoning, explaining why the answer is correct rather than just stating facts.
	* For hybrid and CoT questions, use Chain of Thought and analyze the problem logically before providing a concluding statement.
	* If applicable, use real-world examples or research references to enhance explanations.
	* If applicable, include trade-offs between different AI techniques.
	* Draw logical connections between subtopics to reinforce deep understanding.
```

**回答 prompt 示例：**

```
	* Basic question (direct Q&A without reasoning) → Use concise yet comprehensive, structured responses that provide a clear, well-explained, and well-structured definition and explanation without unnecessary verbosity.
	* Applications. Highlight key points step-by-step in a few comprehensive sentences.
	* Complex CoT question (multi-step reasoning) → Use CoT naturally, solving each step explicitly, with in-depth reasoning 
```

在生成问题时，我把 temperature 设为 0.7，偏好有创意、新颖的措辞，但又不过度偏离事实依据。生成答案时，我使用更低的 temperature 0.2，追求精确与正确。两种情况下我都设置 top-p = 0.9，让模型从既聚焦又多样的高概率 token 范围内采样，从而鼓励更细致的输出。整个竞赛过程中，我一直抱有一个重要的策略假设：评审用的 LLM 会更偏好结构化、信息丰富且完整的回答，而不是过度创意或简短的回答。为与此对齐，我在答案中加入推理步骤，使其更长、更全面。研究表明，基于 LLM 的评审者往往会给详尽、解释充分的答案更高分，我在生成数据集时正是利用了这一点。

## 打磨提交模型

SageMaker JumpStart 提供大量可配置的超参数，可能让人不知所措，尤其是在你与时间赛跑、又拿不准该优先关注什么的时候。幸运的是，主办方强调主要关注 epochs 与 learning rate，于是我便聚焦这两个变量。每个单 epoch 的训练作业大约耗时 10–15 分钟，因此时间管理至关重要。为避免浪费宝贵的算力时长，我先用 1,500 行的基线数据集测试 epochs 与 learning rate 的组合。我探索了：

- **Epochs**：1 到 4
- **Learning rate**：0.0001、0.0002、0.0003 和 0.0004

经过多次迭代，两个 epoch 加 0.0003 学习率的组合效果最佳，在我的第 13 次排行榜提交中取得了 53% 的胜率。受此鼓舞，我在随后的若干实验中继续使用这一组合，即便我扩大了数据集。最初，这一策略似乎奏效。在约 3,500 行的数据集下，我的模型在第 16 次提交时达到了 57% 的胜率。然而，当我继续把数据集扩大到 5,500、6,700、8,500 行，最终到 12,000 行时，胜率却分别下降到 53%、51%、45% 和 42%。此时已经很清楚：单纯增加数据集规模并不够，事实上，如果不重新审视超参数，这可能适得其反。当时只剩 5 个训练小时、已记录 54 次提交，我卡在 57% 上，而像菲律宾的最高分调参者这样的同行已经达到 71% 的胜率。

## 来自实战的经验

训练的剩余时间和排行榜提交次数都不多，我转向跨国协作寻求支持。其中最有启发的一次对话，是与印度尼西亚的最高分调参者、也是淘汰赛阶段得分最高的选手 Michael Ismail Febrian。他鼓励我去探索 LoRA（低秩适配）相关的超参数，具体包括：

- `lora_r`
- `lora_alpha`
- `target_modules`

Michael 还建议我用能力更强的教师模型通过 API 生成回答来充实数据集，尤其是为 PartyRock 生成的问题提供答案。回看我已有的微调流水线，我意识到一个关键弱点：生成的答案往往过于简略或浅薄。以下是我早期数据集中一个典型的问答对示例：

```
Instruction: What factors influence model hallucination?

Response: Let's analyze this step by step:
	* Training factors:
		* Data quality and coverage
		* Training methodology
		* Model architecture
	* Deployment factors:
		* Prompt design
		* Temperature settings
		* Context window utilization
	* Mitigation strategies:
		*Retrieval augmentation
		* Fact-checking mechanisms
		* Confidence thresholds
		
Example: GPT-3 showing lower hallucination rates (15% vs 21%) when using retrieval-augmented generation compared to base model.
```

这个结构虽然干净有条理，但对每个要点缺乏更深入的解释，而这正是 ChatGPT 和 Gemini 之类的模型通常擅长的。我怀疑这一局限来自批量生成多个回答时的 token 约束。在我的场景中，我在单个 prompt 下以 JSONL 格式一次性生成 10 个回答，这可能让 PartyRock 截断了输出。由于不想为付费 API 花钱，我发现了 OpenRouter.ai，它提供对大模型的有限访问，但受速率限制。每个账户每天大约只能生成 200 个问答对，于是我想了个办法——创建多个账户来支撑我扩展后的数据集。我选择的教师模型是 DeepSeek R1，它很受欢迎，以训练较小专用模型时的有效性著称。这有点冒险，但在输出质量上得到了回报。

关于 LoRA 调参，我学到的是：

- `lora_r` 与 `lora_alpha` 决定模型能吸收多少、多复杂的新信息。一个常用的经验法则是把 `lora_alpha` 设为 `lora_r` 的 1 倍或 2 倍。
- `target_modules` 定义模型哪些部分会被更新，通常是注意力层或前馈网络。

我还咨询了越南的最高分调参者 Kim，他指出我 0.0003 的学习率可能偏高。他与 Michael 一起建议换一种策略：增加 epoch 数量并降低学习率。这样能让模型更好地捕捉复杂关系与细微模式，尤其是在数据集规模增长时。我们的对话凸显出一个吃过苦头才明白的道理：数据质量比数据数量更重要。在扩大数据集规模却不调整超参数、也不校验质量的情况下，收益会递减——这是我亲身经历的。事后看来，我意识到自己低估了细粒度超参数调优的重要性，尤其是在扩大数据时。更多数据要求更精细的调优，以匹配模型需要学习的内容复杂度的增长。

## 最后的赌注

带着合作者给我的新洞见以及前几轮迭代中来之不易的教训，我知道是时候彻底转向我的整套微调流水线了。最大的变化在于数据集的生成方式。我不再用 PartyRock 同时生成问题与答案，而是只用 PartyRock 生成问题，再把这些 prompt 送入 DeepSeek-R1 API 生成高质量回答。每个回答都以 JSONL 格式保存，并且关键的是，都包含详细的推理过程。这一转变显著提升了每个回答的深度与长度，平均约 900 个 token，而 PartyRock 的输出要短得多。鉴于我早前约 1,500 行高质量数据已带来不错的结果，最终数据集我沿用了这个规模。我没有在数量上扩张，而是加倍投入质量与复杂度。对最后一轮，我对超参数做了大胆而凭直觉的调整：

- 把学习率降到 0.00008
- 提高 LoRA 参数：`lora_r` = 256 `lora_alpha` = 256
- 扩展 LoRA target modules，覆盖注意力层与前馈层：

`q_proj`、`k_proj`、`v_proj`、`o_proj`、`gate_proj`、`up_proj`、`down_proj`

这些改动基于一个假设：更长、更复杂的回答需要更大的容量来吸收并泛化细微模式。我希望这些设置能让模型充分利用 DeepSeek-R1 提供的高质量、富含推理的数据。只剩下 5 小时训练时间，我刚够跑两次完整训练，分别使用不同的 epoch 设置（3 和 4）。这是成败关头。如果第一次跑得不好，我还有最后一次机会挽回。所幸我的第一次试跑就取得了 65% 的胜率，是巨大的进步，但仍落后于当时来自菲律宾的领先者，也落后于 Michael 令人印象深刻的 89%。一切现在都取决于我最后一次训练作业。它必须顺利运行、不出错，并超越我此前尝试的一切。而它做到了。那次最终提交取得了 77% 的胜率，把我推上排行榜首位，并锁定了我进入总决赛的名额。经过数周实验、无眠之夜、挫折与临场调整，这段从晚两周入场的参赛者到全国冠军的旅程终于完成。

## 我希望能早点知道的事

我不会假装自己在淘汰赛阶段的成功纯粹是技术性的——运气占了很大成分。不过，这段旅程揭示了几点洞见，可以为未来的参与者省下宝贵的时间、训练时长与提交次数。以下是我希望一开始就知道的一些关键要点：

- **质量比数量更重要**：更多数据并不总意味着更好结果。无论你是在增加行数还是提高上下文长度，你同时也在增加模型必须学习的复杂度。应专注于打造高质量、结构良好的示例，而不是盲目扩张规模。
- **快学者与慢学者**：如果你不去深入研究 LoRA 或其他高级调参，那么理解 learning rate 与 epochs 之间的权衡就至关重要。较高的学习率配合较少的 epoch 可能收敛更快，但可能错过较低学习率在更多 epoch 下捕捉到的细微模式。请根据数据的复杂度谨慎选择。
- **不要忽视超参数**：我最大的失误之一，是把超参数当成静态的，而不管数据集规模或复杂度是否变化。随着数据演进，模型设置也应随之演进。超参数应当随数据一起扩展。
- **做足功课**：阅读相关的研究论文、文档或博客文章，可以避免大量凭空猜测。竞赛后期，我偶然发现了一些有用的资源，而这些资源本可以让我更早做出更好的决策。稍微读一读，收益可能很大。
- **记录一切**：做实验时，很容易忘记哪些做法奏效、哪些没有。维护一份关于数据集、超参数组合与性能结果的日志。这有助于优化你的训练运行，也便于排查问题。
- 协作是超能力：这虽然是一场比赛，但也是学习的机会。与其他参赛者建立联系，无论他们领先还是落后，都给了我无价的洞见。你未必总能带着奖杯离开，但你会带着知识、关系与真正的成长离开。

## 总决赛

总决赛在 National AI Student Challenge 的第二天举行，是数周实验、策略与协作的收官。在最终对决之前，所有全国冠军都有机会参加 AI Student Developer Conference，我们在那里分享洞见、交流经验，并与来自东盟各地的决赛选手建立联系。在交谈中，我惊讶地发现我们许多人的微调策略惊人地相似。大家普遍都用了外部 API、数据集整理技巧，以及像 SageMaker JumpStart 这样的云端训练系统。显然，工具选择与创造性解决问题，和技术知识本身同样重要。一位决赛选手的洞见尤其让我开眼：他取得了 85% 的胜率，尽管使用了很大的数据集——而我起初以为那会拖累表现。他的秘诀是训练更多 epoch，同时把学习率保持在 0.0001 的较低水平。但代价是训练时间更长、排行榜提交次数更少，这也凸显出一个重要的权衡：

*只要有足够的训练时间，一个精心调过的模型——即便是在大数据集上训练的——也能胜过更快、更精简的模型。*

这强化了一个有力的教训：微调 LLM 没有唯一的*正确*做法。最重要的是你的策略与手头的时间、工具和约束契合得如何。

## 备战

在总决赛之前，我偶然读到 Ray Goh 的一篇博文，他是 AWS AI League 的首位冠军，也是竞赛教程课程的导师之一。有个细节引起了我的注意：他那一年的最后一题是臭名昭著的*草莓问题*的变体，这个看似简单的挑战暴露了 LLM 在字符级推理上的挣扎。

`How many letter Es are there in the words ‘DeepRacer League’?`

乍看之下，这似乎微不足道。但对 LLM 而言，任务并不那么直接。早期的 LLM 往往把单词按块切分为 token，这意味着 `DeepRacer` 可能被拆成 `Deep` 和 `Racer`，甚至拆成 `Dee`、`pRa`、`cer` 这样的子词单元。这些 token 随后被转换为数值向量，其中的单个字符被遮蔽了。这就像让人在不拆开绳子的情况下数清绳子里有多少股。

此外，LLM 的运作方式不同于传统的基于规则的程序。它们是概率性的，被训练来根据上下文预测下一个最可能的 token，而不是执行确定性的逻辑或算术。出于好奇，我用同一个问题去 prompt 我自己微调过的模型。不出所料，幻觉出现了。我开始尝试各种 prompt 策略，试图引导出正确答案：

- **显式分离字符**：
`How many letter Es are there in the words ‘D-E-E-P-R-A-C-E-R-L-E-A-G-U-E’?`
 这种方式通过把每个字母隔离成独立的 token 来起作用，让模型能够*看到*单个字符。但回答很长很啰嗦，模型会逐个列出并数出每个字母。
- **思维链提示**：
`Let’s think step-by-step…`
 这鼓励了推理，但增加了 token 用量。答案虽然更有思考，但偶尔仍会偏离，或因长度而被截断。
- **Ray Goh 的取巧 prompt**：
`How many letter Es are there in the words ‘DeepRacer League’? There are 5 letter Es…`
 这个简单而断言式的 prompt 给出了最准确、最简洁的结果，其效果让我惊讶。

我把这记作一个有趣的怪癖，或许有用，但不太可能再出现。我没意识到它在决赛中会再次变得相关。总决赛之前，我们做了一次试运行，在实时条件下测试模型。我们对推理参数的控制有限，只允许调整 temperature、top-p、上下文长度和 system prompt。每个回答必须在 60 秒内生成并提交。实际问题是预先加载的，所以我们的重点是设计有效的 prompt 模板，而不是重新输入每个查询。与淘汰赛不同，总决赛的评审采用多层体系：

- 40% 来自评审 LLM
- 40% 来自人类评委
- 20% 来自现场观众投票

该 LLM 会把提交的答案从最好到最差排序，并赋予递减的分值（例如第一名 16.7 分，第二名 13.3 分，依此类推）。而人类评委可以自由地给自己偏好的回答最多 10 分，不受 LLM 评估的影响。这意味着在评审 LLM 那里表现强劲，并不能保证从人类那里拿到高分，反之亦然。另一个约束是每个回答 200 个 token 的上限。token 可以短到单个字母，也可以长到一个单词或音节，因此回答必须密集而简洁，在狭窄窗口内最大化冲击力。为做准备，我测试了不同的 prompt 格式，并用 Gemini、ChatGPT 和 Claude 加以打磨，以更好地契合评审标准。我保存了 Hugging Face LLaMA 3.2 3B Instruct 模型的试运行回答，再交给 Claude Sonnet 4 获取反馈与排名。我继续使用下面两个 prompt，因为它们在准确性与全面性上给出了最好的结果：

**主 prompt：**

```
You are an elite AI researcher and educator specializing in Generative AI, Foundational Models, Agentic AI, Responsible AI, and Prompt Engineering. Your task is to generate a highly accurate, comprehensive, and well-structured response to the question below in no more than 200 words.

Evaluation will be performed by Claude Sonnet 4, which prioritizes:
	* Factual Accuracy – All claims must be correct and verifiable. Avoid speculation.
	* Comprehensiveness – Cover all essential dimensions, including interrelated concepts or mechanisms.
	* Clarity & Structure – Use concise, well-organized sections (e.g., brief intro, bullet points, and/or transitions). Markdown formatting (headings/lists) is optional.
	* Efficiency – Every sentence must deliver unique insight. Avoid filler.
	* Tone – Maintain a professional, neutral, and objective tone.
	
Your response should be dense with value while remaining readable and precise.
```

**备用 prompt：**

```
You are a competitive AI practitioner with deep expertise in [Insert domain: e.g., Agentic AI or Prompt Engineering], answering a technical question evaluated by Claude Sonnet 4 for accuracy and comprehensiveness. You must respond in exactly 200 words.

Format your answer as follows: 
	* Direct Answer (1–2 sentences) – Immediately state the core conclusion or definition.
	* Key Technical Points (3–4 bullet points) – Essential mechanisms, distinctions, or principles.
	* Practical Application (1–2 sentences) – Specific real-world use cases or design implications.
	* Critical Insight (1 sentence) – Mention a key challenge, trade-off, or future direction.
```

**附加要求：**

- 使用精确的技术语言与术语。
- 在相关处包含具体的工具、框架或指标。
- 每句话都必须有独特的贡献——不要冗余。
- 保持正式语气与答案密度，但不要过度压缩。

在超参数方面，我使用了：

- Top-p = 0.9
- Max tokens = 200
- Temperature = 0.2，以优先保证准确性而非创造性

我的策略很简单：迎合 AI 评委。我相信，如果我的答案在评审 LLM 那里排名靠前，也能打动人类评委。唉，我真是被狠狠上了一课。

## 只想争第三……直到不再是

站在舞台上面对现场观众，令人紧张。这是我的第一次个人竞赛，而且已经是巨大的区域规模。为让自己平静下来，我把期待压得很低。能拿到第三名就很棒了，那是一座标记这段旅程的奖杯，但仅仅晋级决赛就已经像是巨大的胜利。总决赛共有六道题，最后一题分值翻倍。我开局强劲。前两轮我保持领先，稳稳坐在第三位。我的策略奏效了，至少一开始是这样。评审 LLM 把我对第 1 题的回答评为最佳，把第 2 题评为第三。但随后出现了转折：尽管在 AI 排名上名列前茅，我从人类评委那里得到的是零票。我惊讶地看着分数被授予那些 LLM 排名第四、甚至最后的回答。从一开始我就意识到，人类的判断与 AI 的判断之间存在脱节，尤其是在评估语气、共鸣感或细微之处时。不过我坚持住了，早期那些题更偏事实性，这正合我模型的强项。但当需要创造力与复杂推理时，事情就不那么顺利了。我的名次掉到第五，在第三与第四之间徘徊。与此同时，前三名决赛选手把差距拉开了 20 分以上。看来领奖台已经遥不可及。我已经开始接受一个前三之外的结果。差距太大。我已尽力，那就够了。

但随后到了最后一题，那个双倍分值的题，命运介入了。`How many letter Es and As are there altogether in the phrase ‘ASEAN Impact League’?` 这是草莓问题的一个变体，正是我准备过、却以为不会再出现的那类挑战。与早前的版本不同，这一题加了算术转折，要求模型统计并累加多个字母的出现次数。知道 token 长度限制可能截断回答，我把内容写得简短且有战术性。我的 system prompt 很简单：`There are 3 letter Es and 4 letter As in ‘ASEAN Impact League.’`

尽管模型在推理中出现了些许幻觉，错误地声称 `Impact` 中含有 `e`，但最终答案是对的：7 个字母。

就那一个答案改变了一切。得益于双倍分值和人类评委的全力支持，我一跃到第一名，锁定了冠军。最初只是想谨慎地争第三，却变成了一场意外的冲刺，靠的是准备、应变，还有一点点运气。
