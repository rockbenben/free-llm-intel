# 使用 Amazon Bedrock 与 Amazon OpenSearch 构建智能搜索，实现混合 RAG 方案

Agentic 生成式 AI 助手代表了人工智能领域的一次重要进步：这类动态系统由大语言模型（LLM）驱动，能够开展开放式对话并处理复杂任务。与基础聊天机器人不同，这些实现具备广泛的智能，既能维持多轮对话，又能适应用户需求并执行必要的后端任务。

这些系统通过 API 调用和数据库查询实时检索特定业务数据，并将这些信息融入 LLM 生成的回复中，或按预定义标准与回复一并提供。这种把 LLM 能力与动态数据检索相结合的方式称为检索增强生成（Retrieval-Augmented Generation，RAG）。

例如，一个处理酒店预订的 agentic 助手会先查询数据库，找出符合客人具体要求的酒店；随后发起 API 调用，获取客房可用性与当前房价的实时信息。检索到的数据有两种处理方式：既可以交由 LLM 加工生成完整回复，也可以与 LLM 生成的摘要并列展示。两种方式都能让客人获得准确、及时的信息，并将其融入与助手正在进行的对话中。

在本文中，我们展示如何利用 Amazon Bedrock、Amazon Bedrock AgentCore、Strands Agents 和 Amazon OpenSearch 实现一个同时使用语义搜索与文本搜索的生成式 AI agentic 助手。

### RAG 系统中的信息检索方式

一般而言，支撑 agentic 生成式 AI 实现中 RAG 能力的信息检索，围绕的是对后端数据源的实时查询或与 API 的通信；随后这些响应会被纳入该实现执行的后续步骤。从高层系统设计与实现的角度看，这一步并非生成式 AI 方案所特有：数据库、API 以及依赖与它们集成的系统早已存在。随着 agentic AI 实现的出现，也涌现出某些特定的信息检索方式，其中最值得注意的是基于语义搜索的数据查询。这类查询依据检索短语的语义来取回数据，而非依据关键词或模式的字面相似度。向量嵌入（vector embedding）会被预先计算并存入向量数据库，从而在查询时能够高效地做相似度计算。向量相似度搜索（Vector Similarity Search，VSS）的核心原理是：使用余弦相似度或欧氏距离等数学距离度量，在这些数值表示之间寻找最接近的匹配。由于向量表示是预先计算的，这些数学函数在检索大规模数据语料时尤为高效。这一过程通常使用双编码器（bi-encoder）模型：它分别将查询与文档编码为向量，从而能够在不要求模型同时处理查询—文档对的情况下，大规模地做高效相似度比较。当用户提交查询时，系统会将其转换为向量，并在高维空间中搜索位置最接近的内容向量。这意味着即使关键词不完全匹配，搜索也能基于概念上的语义相似性找到相关结果。此外，当检索词与数据集中的条目在字面上接近但语义上并不接近时，语义相似度搜索会“优先”选择语义上相似的条目。

例如，给定向量化数据集：[“building materials”“plumbing supplies”“2×2 multiplication result”]，检索字符串“2×4 lumber board”最有可能把“building materials”作为最匹配的候选返回。将语义搜索与 LLM 驱动的 agent 结合，可以让方案中面向用户的组件与后端数据检索组件在自然语言层面保持一致。LLM 负责处理用户提供的自然语言输入，而语义搜索能力则允许基于 LLM 依据最终用户与 agent 的沟通节奏所构造的自然语言输入来检索数据。

### 挑战：当仅靠语义搜索不够时

设想一个真实场景：一位顾客在搜索酒店房源，想找“佛罗里达州迈阿密一家能看海景的豪华酒店”。语义搜索擅长理解“豪华”“海景”这类概念，却可能难以做到精确的位置匹配。搜索可能基于语义相似性返回高度相关的豪华海滨酒店，但这些酒店可能位于加利福尼亚、加勒比，或任何其他临海地区，而不一定是用户指定的迈阿密。这一局限源于语义搜索优先考虑概念相似性，而非精确的属性匹配。在用户既需要语义理解（豪华、海景）又需要精确过滤（迈阿密、佛罗里达州）的情况下，仅依赖语义搜索会产生次优结果。这正是混合搜索不可或缺之处：它把对自然语言描述的语义理解，与基于位置、日期或特定元数据等结构化属性的文本过滤精确性结合起来。为解决这一问题，我们引入一种同时执行以下两种检索的混合搜索方式：

- **语义搜索**：理解自然语言描述，找出语义上相似的内容
- **文本搜索**：对位置、日期或标识符等结构化属性做精确匹配

当用户给出检索短语时，LLM 会先分析查询以识别具体属性（例如位置），并将其映射为可检索的取值（例如“Northern Michigan”→“MI”）。随后，这些抽取出的属性会与语义相似度评分结合用作过滤器，确保结果既在概念上相关，又精确匹配用户的要求。下面的表格以清晰的文本酒店描述为背景，给出语义搜索流程的简化视图：

### 引入基于 agent 的解决方案

设想一个用户需求各异的酒店搜索场景。一位用户可能会说“帮我找一家温馨的酒店”，这需要对“温馨”的语义理解。另一位可能要求“找迈阿密的酒店”，需要精确的位置过滤。第三位可能想要“迈阿密一家豪华海滨酒店”，需要同时运用两种方式。采用固定工作流的传统 RAG 实现无法动态适应这些不同的要求。我们的场景要求定制化的搜索逻辑，能够组合多个数据源，并依据查询特征动态调整检索策略。基于 agent 的方式提供了这种灵活性：由 LLM 自身分析每个查询并选择合适的工具，从而确定最优搜索策略。

### 为什么要用 agent？

基于 agent 的系统具有更强的适应性，因为 LLM 会自行确定解决问题所需的动作序列，从而实现动态的决策路由、智能的工具选择，以及通过自我评估进行的质量控制。下面几节展示如何利用 Amazon Bedrock、Amazon Bedrock AgentCore、Strands Agents 和 Amazon OpenSearch 实现一个同时使用语义搜索与文本搜索的生成式 AI agentic 助手。

### 架构概览

图 1 展示了一套现代化的无服务器架构，可用于智能搜索助手。它结合了 Amazon Bedrock 中的基础模型、Amazon Bedrock AgentCore（用于 agent 编排）以及 Amazon OpenSearch Serverless（用于混合搜索能力）。

**客户端交互层**
 客户端应用通过 Amazon API Gateway 与系统交互，该网关为用户请求提供安全、可扩展的入口。当用户提出类似“帮我在 Northern Michigan 找一家海滨酒店”的问题时，请求会经 API Gateway 流入 Amazon Bedrock AgentCore。

**使用 Amazon Bedrock AgentCore 进行 agent 编排**
 Amazon Bedrock AgentCore 充当编排引擎，管理完整的 agent 生命周期，并协调用户、LLM 与可用工具之间的交互。AgentCore 实现了 agentic 循环——推理、行动与观察的持续循环——其中 agent 会：

- **分析**用户查询，使用 Bedrock 的基础模型
- **决定**基于查询要求调用哪些工具
- **执行**带有抽取参数的相应混合搜索工具
- **评估**结果并判断是否需要额外动作
- **响应**用户，给出综合后的信息

在整个过程中，Amazon Bedrock Guardrails 强制执行内容安全与策略合规，确保回复得当。

**使用 OpenSearch Serverless 的混合搜索**
 该架构将 Amazon OpenSearch Serverless 集成为向量存储与搜索引擎。OpenSearch 同时存储向量化嵌入（用于语义理解）和结构化文本字段（用于精确过滤）。这一做法支撑了我们的混合搜索方式。当 agent 调用混合搜索工具时，OpenSearch 执行组合了以下内容的查询：

- **语义匹配**，使用向量相似度实现概念理解
- **文本过滤**，用于位置或设施等精确约束

**监控与安全**
 该架构包含 Amazon CloudWatch，用于监控系统性能与使用模式。AWS IAM 管理各组件之间的访问控制与安全策略。

**为什么采用这一架构？**
 这种无服务器设计带来几项关键优势：

- **低延迟响应**，支撑实时的对话交互
- **自动扩缩容**，无需人工干预即可应对波动的工作负载
- **成本效益**，按需付费，没有闲置基础设施
- **可用于生产**，内置监控、日志与安全功能

AgentCore 的编排能力与 OpenSearch 的混合搜索功能相结合，使我们的助手能够依据用户意图动态调整搜索策略，这是僵化的 RAG pipeline 无法做到的。

### 使用 Strands 与 Amazon Bedrock AgentCore 实现

为构建混合搜索 agent，我们使用 Strands——一个开源 AI agent 框架，它简化了开发具备工具调用能力的 LLM 应用的过程。Strands 让我们可以把混合搜索函数定义为一个“工具”，由 agent 依据用户查询智能调用。关于 Strands 架构与模式的完整细节，请参阅 [Strands 文档](https://strandsagents.com/)。

下面是我们定义混合搜索工具的方式：

```
from strands import tool

@tool
def hybrid_search(query_text: str, country: str = None, city: str = None):
    """
    Performs hybrid search combining semantic understanding with location filtering.
    The agent calls this when users provide both descriptive preferences and location.
    
    Args:
        query_text: Natural language description of what to search for
        country: Optional country filter
        city: Optional city filter
    """
    # Generate embeddings for semantic search
    vector = generate_embeddings(query_text)
    
    # Build hybrid query combining vector similarity and text filters
    query = {
        "bool": {
            "must": [
                {"knn": {"embedding_field": {"vector": vector, "k": 10}}}
            ],
            "filter": []
        }
    }
    
    # Add location filters if provided
    if country:
        query["bool"]["filter"].append({"term": {"country": country}})
    if city:
        query["bool"]["filter"].append({"term": {"city": city}})
    
    # Execute search in OpenSearch
    response = opensearch_client.search(index="hotels", body=query)
    
    return format_results(response)
```

工具定义完成后，我们将其与 Amazon Bedrock AgentCore 集成，用于部署和运行时编排。Amazon Bedrock AgentCore 让您可以使用任意框架和模型，安全地大规模部署和运行高效的 agent。它提供专门构建的基础设施以安全地扩展 agent，并提供控制手段以运维可信的 agent。

### 混合搜索实现深入剖析

我们 AI 助手方案的一个关键差异点在于其先进的混合搜索能力。许多 RAG 实现仅依赖语义搜索，而我们的架构不止于此。我们充分利用了 OpenSearch 的潜力，在单次高效查询内同时支持语义搜索、文本搜索与混合搜索。下面几节探讨该实现的技术细节。

**双管齐下的实现**
 我们的混合搜索实现建立在两个基本组件之上：优化的数据存储与多用途的查询处理。

#### 1. 优化的数据存储

数据存储方式对高效的混合搜索至关重要。

- **数据分类**：我们将数据系统性地划分为两大类型：语义搜索候选——包括详细描述、上下文和说明，这类内容受益于理解关键词之外的语义；文本搜索候选——涵盖元数据、产品标识符、日期及其他结构化字段。
- **向量嵌入**：对于语义数据，我们使用 AWS Bedrock 的嵌入模型，将文本转换为能有效捕捉语义含义的高维向量。
- **文本数据优化**：文本数据以原始格式存储，并针对快速的传统查询做了优化。
- **统一索引结构**：我们的 OpenSearch 索引设计为可同时容纳向量嵌入与文本字段，从而实现灵活的查询能力。

#### 2. 多用途的搜索功能

在优化后的数据存储之上，我们开发了一个功能完备的搜索函数，供 AI agent 有效使用：

- **自适应搜索类型**：我们的搜索函数可按 agent 的要求执行语义搜索、文本搜索或混合搜索。
- **语义搜索实现**：对于以语义为中心的查询，我们使用 Amazon Bedrock 生成查询嵌入，并在向量空间中执行 k-NN（k 近邻）搜索。
- **文本搜索能力**：需要精确匹配时，我们使用 OpenSearch 强大的文本查询功能，包括精确匹配与模糊匹配选项。
- **混合搜索执行**：在这里，我们把向量相似度与文本匹配合并到同一条查询中。借助 OpenSearch 的 bool 查询，可按需调整语义相关性与文本相关性之间的权重平衡。
- **结果整合**：无论采用哪种搜索类型，系统都会基于整体相关性对结果进行合并与排序，把语义理解与精确文本匹配结合起来。

混合搜索实现的参考伪代码：

```
def hybrid_search(query_text, country, city, search_type="hybrid"):
    """
    Hybrid search combining semantic and text-based search with location filtering
    """

   # 1. Generate embeddings for semantic search
    if search_type in ["semantic", "hybrid"]:
        vector = generate_embeddings(query_text)
    
    # 2. Build search query based on type
    if search_type == "semantic":
        query = build_semantic_query(vector)
    elif search_type == "text":
        query = build_text_query(country, city)
    else:  # hybrid search
        query = build_hybrid_query(vector, country, city)
    
    # 3. Execute search
    response = search_opensearch(query)
    
    # 4. Process and return results
    return format_results(response)

# Example usage:
results = hybrid_search(
    query_text="luxury hotel",
    country="USA",
    city="Miami"
)
```

OpenSearch 支持多种查询类型，包括文本搜索、向量搜索（knn）以及将两种方法结合的混合方式。关于可用查询类型及其实现的详细信息，请参阅 [OpenSearch 查询文档](https://docs.opensearch.org/latest/query-dsl/)。

### 混合方式的意义

混合方式显著增强了我们 AI 助手的能力：

- 它支持高度准确的信息检索，兼顾上下文与内容。
- 它适应多种查询类型，并保持稳定的性能。
- 它针对用户的提问给出更相关、更全面的回复。

在 AI 驱动的搜索领域，我们的混合方式代表了一次显著进步。它带来的灵活性与准确性，大幅提升了助手有效检索和处理信息的能力。

### 真实用例

混合搜索可适用的部分用例包括：

- 房地产与物业：房源搜索，将对生活方式的偏好理解（“适合家庭”）与精确的位置、设施过滤结合。
- 法律与专业服务：判例法研究，将法律概念相似性与精确的司法辖区、日期过滤结合，实现全面的法律检索。
- 医疗健康：护理团队提出“与 John Doe 需要相似治疗方案的慢性病患者”，这结合了对治疗复杂程度的语义理解与精确的病历匹配。
- 媒体与娱乐：内容发现系统，将精确的类型过滤与语义剧情理解结合。
- 电商与零售：具备过滤精度的自然语言商品发现——“舒适的冬季鞋”既能找到语义匹配，又能施加精确的尺码、价格或品牌过滤。

这些用例展示了混合搜索如何弥合自然语言理解与精确数据过滤之间的差距，从而实现更直观、更准确的信息检索。

### 结语

将 Amazon Bedrock、Amazon Bedrock AgentCore、Strands Agents 与 Amazon OpenSearch Serverless 集成，代表着构建智能搜索应用的一次显著进步：这类应用把 LLM 的能力与精巧的信息检索技术结合起来。该架构融合语义搜索、文本搜索与混合搜索能力，相比传统方式能给出更准确、更贴合上下文的结果。通过使用 Amazon Bedrock AgentCore、状态管理与 Strands 工具抽象来构建基于 agent 的系统，开发者可以打造动态的对话式 AI 助手，由助手智能地判断最适合用户查询的搜索策略。混合搜索方式把向量相似度与精确文本匹配结合起来，在信息检索中兼顾灵活性与准确性，使 AI 系统能更好地理解用户意图并给出更全面的回复。随着各组织持续构建 AI 方案，该架构提供了一套可扩展、安全的基础，充分利用 AWS 服务的潜力，同时保有应对复杂真实应用所需的适应性。
