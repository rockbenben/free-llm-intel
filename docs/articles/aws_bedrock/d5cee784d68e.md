# 从概念到现实：走完 RAG 从概念验证到生产环境的旅程

生成式 AI 已成为一股变革性力量，以其创造、创新与解决复杂问题的潜力吸引着各行各业。然而，从概念验证走向可用于生产的应用，这一旅程既有机遇也有挑战。从概念验证转向生产，关键在于打造可扩展、可靠且有影响力的方案，从而带来业务价值与用户满意度。

这一领域最有前景的进展之一，是 [检索增强生成（RAG）](https://aws.amazon.com/what-is/retrieval-augmented-generation/) 应用的兴起。RAG 是优化基础模型（FM）输出的过程：在生成响应之前，先引用其训练数据源之外的知识库。

下图展示了一个示例架构。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/31/POC-to-Production-RAG-Architecture-1024x651.jpeg)

本文探讨 RAG 应用如何从概念验证或最小可行产品（MVP）阶段走向成熟的生产系统。当 RAG 应用从概念验证转向可投产系统时，优化就变得至关重要，以确保方案可靠、成本可控且性能出色。我们来更深入地探讨这些优化技术，并为后续关于托管、扩展、安全与可观测性考量的讨论作铺垫。

## 优化技术

下图说明了可投产的 RAG 应用需要考虑的取舍。

### ![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/31/TradeoffTriangle-300x250.jpeg)

可投产的 RAG 系统是否成功，以质量、成本和延迟来衡量。机器学习（ML）工程师必须做取舍，并针对其具体用例与业务需求确定最重要的因素。例如，考虑为奢侈时尚品牌生成个性化营销内容的用例。该品牌可能愿意承担使用更强大、更昂贵的 FM 所带来的更高成本，以获得最高质量的分类结果，因为误分类可能导致客户不满并损害品牌声誉。再看另一个用例：为电商网站生成个性化商品描述。只要生成的描述仍然足够准确且有吸引力，零售商可能愿意接受稍长的延迟，以降低基础设施与运营成本。质量、成本与延迟的最佳平衡，在不同应用和行业之间可能差异很大。

我们来看看如何提升 RAG 工作流整体质量的实用指南，包括使用 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 与 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 的其他功能来提升检索器质量与结果生成器质量。Amazon Bedrock Knowledge Bases 提供完全托管的能力，帮助你实现从数据摄取到检索再到 prompt 增强的整个 RAG 工作流，无需自行构建与数据源的自定义集成，也不必管理数据流。

## 评估框架

有效的评估框架对于 RAG 系统从概念验证走向生产过程中的评估与优化至关重要。这类框架通常既包含从整体上评估整个 RAG pipeline 的总体指标，也包含分别针对检索与生成组件的具体诊断指标。这样可以针对系统的每个阶段做改进。通过实施稳健的评估框架，开发者可以持续监控、诊断并增强其 RAG 系统，在应用扩展到生产规模时于质量、成本与延迟三个维度都取得最佳表现。[Amazon Bedrock Evaluations](https://aws.amazon.com/bedrock/evaluations/) 可以帮助你评估 Amazon Bedrock Knowledge Bases 中的检索工作流或端到端 RAG 工作流。下面几节将更详细地讨论 RAG 工作流不同阶段的这些具体指标。

## 检索器质量

为了更好的检索表现，数据在 [向量存储](https://aws.amazon.com/blogs/machine-learning/dive-deep-into-vector-data-stores-using-amazon-bedrock-knowledge-bases/) 中的存放方式影响很大。例如，你的输入文档可能在 PDF 中包含表格。这种情况下，使用 FM 来解析数据会得到更好的结果。你可以使用 Amazon Bedrock Knowledge Bases 支持的 [高级解析选项](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking-parsing.html#kb-advanced-parsing)，借助 FM 从文档中解析非文本信息。许多组织把数据以结构化格式存放在数据仓库与数据湖中。Amazon Bedrock Knowledge Bases 提供了一项功能，可让你的 RAG 工作流连接到 [结构化数据存储](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-build-structured.html)。这一完全托管、开箱即用的 RAG 方案能帮助你原生地查询数据所在位置的结构化数据。

另一个重要考量是源文档被切分成块的方式。如果你的文档能从其内部固有的关系中获益，那么使用 [分层切块](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking-parsing.html#kb-hiearchical-chunking) 可能更明智，它能实现更细粒度、更高效的检索。有些文档则受益于 [语义切块](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking-parsing.html#kb-semantic-chunking)，它保留块内的上下文关系，有助于确保相关信息留在同一逻辑块中。你也可以针对 RAG 应用的独特需求，使用自己定制的 [切块策略](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking-parsing.html#kb-custom-transformation)。

RAG 应用通过在大量文档中搜索来处理用户查询。然而在许多情况下，你可能需要检索具有特定属性或内容的文档。你可以使用 [元数据过滤](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-knowledge-bases-now-supports-metadata-filtering-to-improve-retrieval-accuracy/)，通过指定包含与排除条件来缩小搜索结果范围。Amazon Bedrock Knowledge Bases 现在还支持 [自动生成的查询过滤器](https://aws.amazon.com/about-aws/whats-new/2024/12/amazon-bedrock-knowledge-bases-auto-generated-query-filters-improved-retrieval/)，它扩展了手动元数据过滤的既有能力，让你无需手工构造复杂的过滤表达式就能缩小搜索结果。这通过确保文档与查询相关来提升检索准确度。

## 生成器质量

写好有效的查询，与生成准确度的其他任何考量同等重要。你可以添加 [prompt](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-templates-and-examples.html)，向 FM 提供指令以给出恰当的回答。例如，一家法律科技公司会希望给出指令，把答案限制在输入文档的基础上，而不是基于 FM 已知的通用信息。[查询分解](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)——把输入查询拆成多个查询——同样有助于检索准确度。在这个过程中，语义复杂度较低的子查询可能找到更精准的块。这些块随后可被汇集并一起排序，再传给 FM 生成响应。

[重排序（reranking）](https://aws.amazon.com/about-aws/whats-new/2024/12/amazon-bedrock-rerank-api-accuracy-rag-applications/) 作为检索后步骤，可以显著提升响应质量。该技术使用 LLM 分析查询与检索到的文档之间的语义相关性，并按相关程度重新排序。引入重排序后，你可以确保只有上下文最相关的信息被用于生成，从而得到更准确、更连贯的响应。

调整 [推理参数](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-parameters.html)（例如 temperature 与 top-k/p 采样），有助于进一步细化输出。

你可以使用 Amazon Bedrock Knowledge Bases 来[配置和定制](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)查询与响应生成。也可以借助 Amazon Bedrock 中的[重排序模型](https://docs.aws.amazon.com/bedrock/latest/userguide/rerank.html)提升查询响应的相关性。

## 整体质量

检索器质量的关键指标是[上下文精确度](https://aws.amazon.com/blogs/machine-learning/evaluate-the-reliability-of-retrieval-augmented-generation-applications-using-amazon-bedrock/)、[上下文召回率](https://aws.amazon.com/blogs/machine-learning/evaluate-the-reliability-of-retrieval-augmented-generation-applications-using-amazon-bedrock/) 与[上下文相关性](https://aws.amazon.com/blogs/machine-learning/evaluate-the-reliability-of-retrieval-augmented-generation-applications-using-amazon-bedrock/)。上下文精确度衡量系统对给定上下文中相关信息片段的排序效果，它考虑问题、标准答案与上下文。上下文召回率给出检索到的上下文所覆盖的标准答案论断或关键信息的百分比。上下文相关性衡量检索到的段落或块是否与回答给定查询相关，并排除无关细节。这三项指标合起来，可以让人看出检索器在多大程度上能够呈现最相关、最聚焦的源材料，以支撑高质量的回答。

生成器质量可以通过若干关键指标来评估。[上下文利用率](https://github.com/amazon-science/RAGChecker/blob/main/tutorial/ragchecker_tutorial_en.md#generator-metrics) 考察生成器使用所提供源材料中相关信息的有效程度。[噪声敏感度](https://github.com/amazon-science/RAGChecker/blob/main/tutorial/ragchecker_tutorial_en.md#generator-metrics) 衡量生成器把检索内容中不准确细节纳入进来的倾向。[幻觉](https://github.com/amazon-science/RAGChecker/blob/main/tutorial/ragchecker_tutorial_en.md#generator-metrics) 衡量生成器产出源数据中并不存在的错误论断的程度。[自我知识](https://github.com/amazon-science/RAGChecker/blob/main/tutorial/ragchecker_tutorial_en.md#generator-metrics) 反映所生成的准确陈述中、在检索到的块里找不到的部分所占比例。最后，[忠实度](https://github.com/amazon-science/RAGChecker/blob/main/tutorial/ragchecker_tutorial_en.md#generator-metrics) 评估生成器的输出与源材料所含信息的吻合程度。

要衡量整体生成质量，关键指标包括[精确率](https://github.com/amazon-science/RAGChecker/blob/main/tutorial/ragchecker_tutorial_en.md#overall-metrics)、[召回率](https://github.com/amazon-science/RAGChecker/blob/main/tutorial/ragchecker_tutorial_en.md#overall-metrics) 与[答案相似度](https://aws.amazon.com/blogs/machine-learning/evaluate-the-reliability-of-retrieval-augmented-generation-applications-using-amazon-bedrock/)。精确率表示模型响应中正确论断所占的比例，召回率则表示模型响应所覆盖的标准答案论断所占的比例。答案相似度把生成答案的含义与内容同参考答案或标准答案作比较，评估生成答案与标准答案意旨的接近程度。

基于这些质量指标，用评估框架建立反馈回路，就能持续改进：系统可以从用户交互中学习，并随时间不断优化其表现。通过优化这些质量指标，RAG 系统可以被设计成能为用户交付可靠、成本可控且性能出色的结果。

关于如何在 Amazon Bedrock 中使用 RAG 评估框架计算 RAG 质量指标的演示，请参阅 [New RAG evaluation and LLM-as-a-judge capabilities in Amazon Bedrock](https://aws.amazon.com/blogs/aws/new-rag-evaluation-and-llm-as-a-judge-capabilities-in-amazon-bedrock/)。

## 负责任 AI

落实负责任的 AI 实践，对于维持 RAG 系统合乎伦理且安全的部署至关重要。这包括使用护栏（guardrails）过滤有害内容、拒绝某些话题、遮蔽敏感信息，以及把响应锚定在经验证的来源上以减少幻觉。

你可以使用 [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 来落实负责任的 AI 策略。除了防范毒性内容与有害内容，它还可用于[自动推理检查](https://aws.amazon.com/blogs/aws/prevent-factual-errors-from-llm-hallucinations-with-mathematically-sound-automated-reasoning-checks-preview/)，帮助你防范幻觉。

## 成本与延迟

成本考虑运行系统所需的计算资源与基础设施，延迟则评估最终用户感受到的响应时间。为优化成本与延迟，可实施[缓存策略](https://aws.amazon.com/blogs/database/improve-speed-and-reduce-cost-for-generative-ai-workloads-with-a-persistent-semantic-cache-in-amazon-memorydb/)以减少昂贵的模型推理需求。高效的[查询批处理](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference.html)也能提升整体吞吐并降低资源占用。在性能与资源占用之间取得平衡，找到满足应用需求的理想配置。

使用 Amazon Bedrock Knowledge Bases 这类工具，你就能享受对端到端 RAG 工作流的全托管支持。它支持我们前面讨论的许多[高级 RAG 能力](https://aws.amazon.com/about-aws/whats-new/2024/07/knowledge-bases-amazon-bedrock-advanced-rag-capabilities/)。把这些优化技术落到实处，你就能把由 RAG 驱动的概念验证转变为一个稳健、可投产的系统，为用户交付高质量、成本可控且低延迟的响应。

关于使用 Amazon Bedrock Knowledge Bases 构建 RAG 应用的更多信息，请参阅 [Building scalable, secure, and reliable RAG applications using Amazon Bedrock Knowledge Bases](https://aws.amazon.com/blogs/machine-learning/building-scalable-secure-and-reliable-rag-applications-using-amazon-bedrock-knowledge-bases/)。

## 托管与扩展

在托管你的 Web 应用或服务时，有几种方式可供考虑。关键在于选择能有效承载你的数据库与计算基础设施的方案。这可能包括基于服务器的选项，如 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2/)（Amazon EC2）；托管服务，如 [Amazon Relational Database Service](https://aws.amazon.com/rds/)（Amazon RDS）与 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/)；或无服务器方式，如 [AWS Amplify](https://aws.amazon.com/amplify/) 与 [Amazon Elastic Container Service](https://aws.amazon.com/ecs/)（Amazon ECS）。关于使用 Amazon ECS 构建自动化 AI 助手的实践做法，见 [Develop a fully automated chat-based assistant by using Amazon Bedrock agents and knowledge bases](https://docs.aws.amazon.com/prescriptive-guidance/latest/patterns/develop-a-fully-automated-chat-based-assistant-by-using-amazon-bedrock-agents-and-knowledge-bases.html)。

除了服务器或计算层，你还需要考虑编排工具、测试环境，以及用于简化应用部署的持续集成与交付（CI/CD）pipeline。基于质量指标建立反馈回路并配合 CI/CD pipeline，是打造自愈架构重要的第一步。

随着应用成长，你需要确保基础设施能够扩展以满足不断增长的需求。这可能涉及用 Docker 做容器化或选择无服务器方案、实施负载均衡、设置自动伸缩，以及在本地部署、云端或混合方案之间做选择。它还包括前端应用与后端生成式 AI 工作流各自的独特扩展需求，以及内容分发网络（CDN）的使用、灾难恢复与备份策略。

## 数据隐私、安全与可观测性

维护数据隐私与安全至关重要。这包括在应用的每一层实施安全措施，从加密传输中的数据，到设置稳健的身份验证与授权控制。它还涉及关注计算与存储安全，以及网络安全。遵守相关法规并定期做安全审计必不可少。保障生成式 AI 系统安全是另一个关键方面。默认情况下，Amazon Bedrock Knowledge Bases 使用 AWS 托管的 [AWS Key Management Service](https://aws.amazon.com/kms)（AWS KMS）密钥加密流量。你也可以选择客户托管的 KMS 密钥，以更好地控制加密密钥。关于应用安全的更多信息，请参阅 [Safeguard a generative AI travel agent with prompt engineering and Amazon Bedrock Guardrails](https://aws.amazon.com/blogs/machine-learning/safeguard-a-generative-ai-travel-agent-with-prompt-engineering-and-amazon-bedrock-guardrails/)。

全面的日志、监控与维护对于维持健康的基础设施至关重要。这包括设置结构化日志、集中式日志管理、实时监控，以及系统更新与迁移的策略。

把这些关键领域处理好，你就能构建安全且有弹性的基础设施，支撑不断成长的 Web 应用或服务。敬请关注后续博客文章中关于这些话题的更深入论述。
