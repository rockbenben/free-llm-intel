## 自适应流水线编排

企业知识文档含有大量信息，而查询对其所需信息量差异巨大。一个像“我团队的季度达成率是多少？”的聚焦问题，可能只取自少量小节（检索出的企业知识文档的离散块）。一个像“给我一份完整的区域表现分析”的全面请求则需要在数百节上综合。用户两种情况下都期待相同的响应时间。这种异构性要求一种路由策略，能快速处理常见情形，又不牺牲复杂场景的全面性。

没有单一的处理策略适用于所有查询，因为正确的方法取决于一个查询实际需要多少数据。单次拼接快而便宜，但当聚合的小节超出模型的上下文窗口（典型为 200K token）时会崩溃，迫使截断和质量损失。固定的多遍批处理避免截断，但它为每个查询——包括约 90% 不需要它的查询——为多次 LLM 调用买单。我们的方法基于其总聚合小节量 ∣D∣（其中 D 是检索到的文档小节集合）路由每个查询：数据放得下就单遍，只有必要时才批处理。结果是一个三阶段流水线，对每个查询分类一次，然后沿那条保留质量的最廉价路径处理它。

### 三阶段自适应处理

流水线最多在三阶段内处理每个查询：Mode-Aware Consolidation 打包检索到的小节并选一条路径，Bifurcated Analysis 要么作为单个快速路径调用、要么作为并行正常路径批次执行那条路径，Conditional Consolidation 在需要时合并并行结果。下表总结两条路径如何穿过这些阶段，然后我们逐一详细演练每个阶段。

|  | **快速路径（约 90% 查询）** | **正常路径（约 10% 查询）** |
| --- | --- | --- |
| **触发** | 检索量 ∣D∣ ≤ θ | 检索量 ∣D∣ > θ |
| **阶段 1：Mode-Aware Consolidation** | 所有小节拼进单个块 | 小节按文档边界打包成 N 个批次 |
| **阶段 2：Bifurcated Analysis** | 单个 LLM 调用，直接流式到评估 | N 个并行 LLM 调用，每批一个 |
| **阶段 3：Conditional Consolidation** | 完全跳过 | 合并 N 份分析、解决冲突、流式输出最终答案 |

第一阶段 Mode-Aware Consolidation 在检索到的文档小节上运作。它应用一个贪心首次适配（first-fit）打包策略来填满上下文窗口至 token 上限，同时保留小节优先级顺序和小节边界。对于较小量（∣D∣≤θ，其中 θ 是一个经验校准的字符数阈值），所有小节拼进单个块，这称为“快速路径”。对于大量（∣D∣>θ），小节按文档边界打包成最优批次，这称为“正常路径”。阈值 θ 相对于模型的上下文窗口上限设定，并校准为在快速路径上捕获 70–90% 的查询（实践中约 90% 走这条路径，如结果一节所示）。因为执行模式在第一阶段就已固定，每个下游阶段都能为其特定路径优化，而不必同时处理两者。

第二阶段 Bifurcated Analysis 执行所选路径。快速路径用完整上下文做一次 LLM 调用并把结果直接流式到评估流水线。正常路径把批次分发到 N 个并行 LLM 调用（其中 N 是阶段 1 产生的批次数），它们独立分析各块以取得接近线性的加速。

第三阶段 Conditional Consolidation 只在正常路径上运作，把 N 份独立分析综合成一个统一响应。综合 LLM 接收带原始问题的部分分析，并在流式输出最终答案的同时应用冲突解决启发式。快速路径完全跳过这一阶段，因为最终响应只用一份分析。图 2 展示完整流程，两条路径汇聚到流式响应。

图 2：三阶段流水线的端到端流程，展示快速路径绕过综合

在生产中，这一基于阈值的路由交付了超乎寻常的效率。约 90% 的查询走快速路径（单个 LLM 调用，首 token 时间（TTFT）在几秒内，总延迟通常低于 25 秒）。剩下 10%（复杂的多文档查询）获得完整的并行批处理（约 50–75 秒，而快速路径不到 25 秒），与其复杂度相称。以正常路径查询典型的 N=4 个批次，每查询的混合成本约为 1.4 次 LLM 调用。相比总是用多遍策略，这是每查询 LLM 调用数减少 72%，同时为复杂查询保持完整的质量覆盖。团队应校准自己的阈值以匹配其工作负载的查询量分布，并保持它低于模型的上下文窗口上限。

## 跨账户多模型故障转移

自适应流水线高效地综合信息，但一条快的流水线只有在其背后的模型保持可用时才有用。在峰值评审期，当数千用户同时跑他们的分析时，一次被限流的请求就会侵蚀对工具的信任并把用户赶回手动电子表格分析。标准的缓解措施——带抖动的指数退避——被证明不足。Amazon Bedrock 为每个模型、每个账户分配独立配额。把每个模型-账户对当作其自己的容量空间，能在不配置新基础设施的前提下成倍提升可用吞吐。我们不去等容量腾出，而是去发现那些从一开始就未被争用的容量。本节展示把每个模型-账户对当作其自己的配额空间，如何在不配置新基础设施的前提下成倍提升容量。

那份容量就藏在明处。Amazon Bedrock 配额跨两个轴彼此独立：每个模型有自己的限制，每个 AWS 账户收到自己的配额。一个 3 模型 × 3 账户的配置因此提供九个独立配额空间。在运行时，系统通过先尝试排名最高的模型、并对账户做随机化以帮助防止热点，来探索这个网格。实现是一个定制的 [Strands](https://strandsagents.com/) 模型提供方——标准 [BedrockModel](https://github.com/strands-agents) 的一个即插即用替代品，它在保持与现有智能体代码完全兼容的同时加上透明的容量扩展。图 3 展示网格以及一个请求穿过它的级联路径。

图 3：跨一个 3 模型 × 3 账户配置的故障转移级联，其中每个单元格是一个独立配额空间，请求在耗尽当前层级的账户之后才降级模型质量

### 三机制协调

三个机制协调使这一切运作。第一个是模型排名，它确立一个质量-速度层级。查询先尝试排名最高的模型，只在必要时级联，因此用户自动收到最好的可用模型。第二个是账户级分发，它通过随机负载均衡帮助防止热点。在每次故障转移尝试之前，Python 的 `random.shuffle()` 通过创建一个副本并就地打乱来随机化 AWS 角色 ARN 列表的顺序。于是负载随时间在账户间均匀分发，无需复杂的流量整形算法或集中协调。每个请求获得新的随机化，自然地达到约 1/N 的流量分布，其中 N 是配置的账户数。这最大化了整个账户池的 Amazon Bedrock API 配额利用率。第三个是检测与快速恢复，它完全避免退避。`ThrottlingException`、`ServiceQuotaExceededException` 和 `TooManyRequestsException` 由 `ThrottlingDetector` 捕获，并立即尝试下一个模型-账户组合。[AWS Security Token Service (STS)](https://docs.aws.amazon.com/STS/latest/APIReference/Welcome.html) AssumeRole 在 100–200 毫秒内获得新凭证，相比[带抖动的指数退避](https://docs.aws.amazon.com/general/latest/gr/api-retries.html)的多秒延迟可忽略不计。

在跨越 4,000 多用户、为期六个月的生产部署中，N×M 的配额探索（其中 N 是模型数，M 是账户数）吸收了流量激增，并在峰值期减少了用户可见的限流。改进的程度与配置的模型-账户组合数成正比。用 Locust 框架做的负载测试显示，系统能够在一段持续时间内支持 100 多用户的模型请求并发，而没有任何失败请求。下面这个快照展示了 100 多用户请求通过应用从 Amazon Bedrock 流式响应时的负载测试细节。关键要点是：基础设施不需要扩展。扩展的是配额空间。

## 实时流式评估

故障转移架构现在在配额压力下提供不间断的 token 流。然而，一个可靠送达却含幻觉收入数字的响应只会让问题更糟。没有准确率的可用性是一种负担。我们最初的做法把质量检查实现为一个顺序的后处理步骤。它会生成完整响应、运行评估器，然后交付经验证的输出。虽然这达到了高准确率，但首个内容时间（TTFC）超过一分钟，因为用户要等整个响应生成并评估完才看到输出。这种准确率与响应速度之间的权衡把我们引向一个关键问题：整段响应需要在验证可以开始之前完全生成完吗？本节展示回答这一问题的并行评估架构，它用[生产者-消费者并发模式](https://arxiv.org/pdf/cs/0210001)实现了近乎零的验证开销。

### 段落独立性

验证第 N 段输出不需要等第 N+1 段生成。这种逻辑独立性使并行执行成为可能。它显著减少了首个内容时间（TTFC），即从提交请求到用户看到第一个被交付的、经验证内容所经过的时间。

在一条顺序流水线里，用户要等所有段生成，*然后*所有段评估，才看到任何东西。我们的并行方法在每段产生时就验证它，于是用户只需一段生成并评估完就能看到第一个内容，而不必等整段响应完成。只有最初那一段在用户看到内容之前承受评估延迟。之后每一段都与下一段的生成*并发*评估，于是评估成本被吸收在生成窗口之内。对每个后续段，交付延迟只是二者中较长的那个：评估当前段，或生成下一段。

在实践中，段落生成耗时大约几秒，而确定性检查（weasel words、emoji）在几十毫秒内完成，提供了一个宽的稳定裕度，即使在常见情形下偶尔调用昂贵的、基于 LLM 的评估，也让评估对用户实际上不可见。

### 生产者-消费者架构与性能模型

图 5：协调生产者、有界队列和消费者的生产者-消费者流式架构

该实现协调三个异步组件。生产者任务从 Amazon Bedrock 流式 API 接收 token 并把它们累积成通过可配置启发式（用于 markdown 边界的双换行）检测的段落大小的单位。完整的段被排入一个线程安全的有界缓冲，带相互阻塞和先进先出（FIFO）顺序以保持连贯。一个哨兵值信号完成。消费者任务出队各段、执行顺序验证检查（如数据准确性验证），并把批准的作为多词块流式输出以保持平滑的感知交付。

在实践中，这一稳态行为根据给定段落触发了哪些评估器，分裂成两个不同的区制。

定义 *λ**g**e**n* 为段落生成率，*μ**e**v**a**l* 为评估率。缓冲利用率 $\rho = \frac{\lambda_{gen}}{\mu_{eval}}$ 决定平衡行为。鉴于评估方法的本质（无论是确定性还是基于 LLM），我们会预期一个双峰的 ρ 分布，而非一个单一平均值。

在快速路径上，只需要确定性检查（Weasel Word、Emoji）的段在约 79 毫秒的中位数内完成评估，得到 ρ ≈ 0.095，远低于 1。在这个区制下，缓冲几乎保持空着，因为消费者在等生成，而评估增加零可感知延迟。在慢速路径上，触发基于 LLM 的数值验证的段评估耗时约 2,025 毫秒，得到 ρ 中位数 ≈ 21.5，远高于 1。这里背压（backpressure）自然地对生产者在限速，帮助防止队列无界增长，而消费者在追赶。不丢失任何内容，且在一段通过之后交付恢复。

这一分裂是本文后面讨论的组合评估框架的直接后果。多数散文在毫秒内清过确定性检查，而含数值指标的段落触发更深的、基于 LLM 的验证。

### 流式评估结果

为验证这一架构，我们在一个企业部署环境中跨 1,000 个生产查询（约 10,439 段）测量了性能，用 Amazon Bedrock 上的 Anthropic Claude Sonnet，商业智能查询平均每响应超过 10 段。绝对的时序数值是这个环境特有的，但相对改进和架构模式广泛适用于流式 LLM 部署。

| **评估模式** | **中位 TTFC** | **与我们的方法相比** |
| --- | --- | --- |
| 并行流式 | 13.2 秒 | – |
| 无质量检查（未评估流式） | 11.8 秒 | +1.4 秒开销 |
| 顺序后生成（基线） | 100.2 秒 | 慢 7.6× |

并行架构相比顺序评估取得了 86.8% 的延迟降低。与未评估流式相比那 1.4 秒的差距，只反映流水线达到稳态之前一次性首段评估成本。

## 组合评估框架

流式流水线把段落交付给一个评估器消费者，但单一的大型验证器只应对一种失败模式。企业质量保障要求同时在多个正交维度上覆盖。因此这一系统中的负责任的 AI 是双面的：Amazon Bedrock Guardrails 在生成开始前筛查每个传入查询，而组合评估器在每段到达用户之前筛查它。语言客观性、格式标准与数值准确率各代表一种单一评估器无法覆盖的不同失败模式。本节展示一个通过共享接口协调独立评估器的组合评估框架。一个正式的可扩展性约束让流水线与前述的实时流式架构保持兼容。

### 可扩展性

组合框架为持续扩展而设计。如在实时流式评估一节所确立的，每个评估器都为流水线缓冲利用率 ρ（评估延迟与生成时间之比）做贡献。只要所有评估器的合计 ρ 保持在 1 以下，添加一个新评估器就是有效的，从而保持流式流水线稳定。在实践中，亚毫秒时间运行的廉价确定性评估器可无条件添加。昂贵的、基于 LLM 的评估器必须只触发足够小比例的段落，以保持加权贡献有界。

每个评估器实现一个标准接口。它接受段落内容作为输入，返回一个通过/失败结果，带检测到的问题和建议的纠正。这支持自主运行和流水线无关的集成。团队可以添加领域特定的评估器，如毒性检测、合规政策检查或货币格式验证，而无需改动流水线，前提是 ρ 准入门槛得到满足。

### 三个参考评估器与自动纠正器

我们实例化三个针对商业智能响应中正交失败模式的评估器。

`WeaselWordEvaluator` 通过正则模式匹配强制执行客观语言，因为高管报告需要定量陈述（“16% 增长”）而非主观描述（“强劲增长”）。`EmojiEvaluator` 通过 Unicode 检测过滤对话式 emoji 来维持正式的呈现。`DataAccuracyEvaluator` 应对数值幻觉——商业智能系统中风险最高的失败模式。捏造的指标传播进决策工作流，构成重大的合规暴露，需要两级层次验证来做全面的校验。

这些评估器针对同一段并行执行，因此总评估延迟等于被触发中最慢那个评估器的延迟。来自某评估器的一个关键违规触发段落拒绝。可纠正的问题调用配对纠正器。通用通过则把流式批准给用户。

自动纠正把检测转化为可行动的修复。流水线按次序应用纠正器。

- `WeaselWordCorrector` 在保持语言流畅的同时移除主观形容词。
- `EmojiCorrector` 剥离 Unicode 字符。
- `DataAccuracyCorrector` 用“LLM Reasoning”标签标注捏造，以保持透明。

这个次序很重要。文本修改先运行，然后是字符移除，然后是标注，这为每个变换保持了稳定的输入。

### 组合评估结果

在生产中，组合框架标记的段落远多于一个单独运作的评估器。关键在于，被标记段落中近四分之一同时触发了两个或更多评估器，这意味着单评估器部署会完全漏掉第二个质量维度上的共现失败。这种多维覆盖是组合方法的主要收益。扩展这一框架的团队可以用单一接口实现插入新评估器而无需改动流水线，只要总评估时间保持在段落生成窗口之内。

## 数据准确性验证

在组合评估框架一节引入的三个评估器中，`DataAccuracyEvaluator` 应对风险最高的失败模式。一个语法通顺、客观措辞的响应，仍可能幻觉出高管据以行动的那个确切数字。在实践中，这意味着在实际数字是“$414M”时报告“$441M”，一个足以在任何人发现错误之前驱动错误资源分配决策的差异。这一失败模式需要一个专用的两级验证架构，从精确值匹配级联到语义验证。本节展示该架构，它在检测准确率与计算成本之间取得平衡。该验证的第一阶段执行精确匹配以过滤无接地的输出，而第二阶段通过渐进验证应用上下文验证。它先做字符串相似度分析，然后是基于 LLM 的语义验证。

### 层次化验证

幻觉检测呈现出相互竞争的目标。全面的准确率需要语义理解，而实时部署要求亚秒级验证。大型 LLM 验证达到准确率却付出每段 2–3 秒的 prohibitive 延迟。纯模式匹配提供速度却牺牲上下文理解。例如，它能正确提取“$414M”却检测不出不当的语义放置。两级架构通过渐进计算投入的级联验证解决了这一点。

该设计应对需要不同检测策略的不同错误模式。第一种错误模式是值捏造，发生在 LLM 生成语料库中不存在的指标时。例如，在文档只含“$414M”时报告“$441M”，或在源只覆盖 2024 上半年时引用“2024 第三季度收入”。这些错误在第一阶段通过精确值匹配允许确定性检测。第二种错误模式是上下文错配，发生在 LLM 误用源中存在的指标时，如把收入数字用于成本讨论、把 Q1 增长率应用到 Q3 查询，或跨业务单元混淆指标。这些错误需要在第二阶段做语义验证。层次化方法对每个错误类别施加适当的计算投入：对明显的捏造用廉价的精确匹配，只在必要处用昂贵的语义分析。

这级联在实践中如何工作。第一阶段 Exact Value Matching 用正则模式从源文档和 LLM 响应中提取数值指标，然后检查响应中的每个指标在源集合中是否有精确匹配。没有匹配的指标被分类为 UNVERIFIED，以最小的成本为捏造终止验证。第二阶段 Progressive Contextual Verification 在匹配指标上通过两个子阶段运作。阶段 2a 应用 `SequenceMatcher`，计算 w 字符窗口（w=50）内响应上下文 Cr 与源上下文 Cs 之间的相似度 ρ=ratio(Cr, Cs)。对高相似度，分类作为 MATCH 继续，避免昂贵的 LLM 调用。阶段 2b 对低相似度情况（σ<τ）采用 `ContextualDataAgent`，执行语义验证以检测细微的上下文错配。这种级联设计把计算投入集中在需要的地方。字符串相似度以每指标约 1.7 毫秒处理明显匹配，而 LLM 验证以每次调用约 1,758 毫秒应对歧义。

图 6：两级数据准确性验证级联，从精确匹配升级到基于 LLM 的语义验证

每个阶段的计算成本显著不同。第一阶段用正则和集合操作耗时约 0.3 毫秒。阶段 2a 做字符串比较耗时约 1.7 毫秒。阶段 2b 做 LLM 推理耗时约 1,758 毫秒。因为多数指标通过第一阶段（生产中 87%）且其中只有 30% 需要在阶段 2b 做昂贵的 LLM 验证，每指标的有效成本平均约 812 毫秒。这相比大型 LLM 验证减少了 54%。这减少来自把多数指标路由过廉价的确定性检查，只有一小部分需要 LLM 验证。成本节省的程度会随工作负载而不同。含更高比例数值内容的团队会有更多指标到达阶段 2b，而文本密集型工作负载从早终止中获益更多。

## 架构集成

五项技术形成一个分层的依赖链，其中每一层支持其上的那一层。自适应流水线把可变的文档量综合成 LLM 就绪的上下文，并把 90% 的查询路由过单个快速通道。这份综合后的输出到达多模型跨账户故障转移层，它把硬性 API 配额限制转成透明的路由决定，并提供流式评估器所需的不间断 token 流。没有这份可用性保证，评估流水线就必须同时处理质量失败和生成失败，大大复杂化其设计。流式评估器对这条可靠的 token 流运行生产者-并行化，在稳态下让验证对用户不可见。组合框架和数据准确性级联插入消费者任务，加入三维质量覆盖和数值幻觉检测，而不打乱延迟预算。

在系统层面，在生产部署中，协调的架构交付在约 13 秒内开始流式、保持 99.3% 数值准确率的响应，并在这次六个月部署中观察到的每个请求上持续可用，而没有专用验证基础设施、配额提升或序列化瓶颈。

## 结论：桥接 AI 研究与生产现实

当高管在他们的领导团队面前问数据驱动的问题时，准确率和速度不可妥协。一个错误的指标或一个延迟的响应都会带来即时的职业后果。达到这一标准需要解决远超模型选择和基本系统设计的根本工程挑战：指标幻觉、峰值并发负载下的 API 限流、阻塞实时交付的验证延迟，以及损害可信度的主观措辞。

这一质量保障机制作为一条协调的流水线运作。自适应流水线编排把 90% 的查询路由过单个快速通道，为常见情形保持低延迟，同时为复杂的多文档查询保留全覆盖。跨账户多模型故障转移能通过在多个独立模型-账户空间扩展可用配额，显著降低生成停摆的可能性，在没有用户可见限流的情况下吸收流量激增。实时流式评估在每段产生的那一刻验证它，而非等完整响应，把感知评估延迟削减至多 86.8%。组合评估框架针对每段并行运行多个独立检查，抓住单评估器会漏掉的共现失败。最后，数据准确性验证应用一个两级级联，先用廉价的精确匹配、只在必要时用昂贵的语义验证来抓住数值幻觉，按测试以比大型 LLM 验证平均低 54% 的成本达到约 99% 的数值准确率。

结果是一个约 13 秒内开始流式经验证响应、在这次六个月部署的峰值全球负载下每个观察到的请求都保持可用、并产出足以直接进入高管业务评审之准确输出的系统。对每天使用 NarrateAI 的数千位领导者而言，这些技术正是为什么数值错误从未在评审中浮现、答案在会议进行中而非结束后到达、系统在整个部署窗口跨时区保持可用，以及输出直接进入业务评审而无需重写的原因。

## 后续步骤

要应用这些模式，先通过剖析你的查询量分布来判断自适应路由能否降低你的 LLM 成本（自适应流水线编排）。如果你在峰值负载期间触及限流上限，跨账户故障转移（跨账户多模型故障转移）能在无基础设施改动的情况下带来即时容量收益。对已经在流式 LLM 输出的团队，加上生产者-消费者评估（实时流式评估）是影响最大的质量改进。对于负责任的 AI，采用前面所描述控制对的两侧：对传入查询用 Amazon Bedrock Guardrails，对传出响应用接地检查。只筛查输入会让幻觉内容未被过滤，而只做输出接地会让系统对 prompt 攻击和越界请求敞开大门。

这些模式在 NarrateAI 之外也广泛适用于其他准确率和可靠性不可妥协的生产 LLM 系统。要开始构建，探索以下资源。

- [Amazon Bedrock 用户指南](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html) — 基础模型（FM）访问与配置。
- [Amazon Bedrock 中按 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html) — 按 AWS 区域的模型可用性。
- [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) — 智能体编排。
- [Strands Agents SDK](https://github.com/strands-agents/sdk-python) — 本实现中使用的公开可用框架。
