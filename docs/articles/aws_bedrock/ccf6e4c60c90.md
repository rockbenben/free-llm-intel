# Inscribe 如何借助 Amazon Bedrock 在数秒内阻止文档欺诈

*本文与 Inscribe 的 CTO 兼联合创始人 Conor Burke 共同撰写*

如今每 16 份文档中就有 1 份存在欺诈，而 AI 生成的伪造文档在 2025 年 4 月至 12 月间增长了 5 倍（[Inscribe 的 2026 年文档欺诈状况报告](https://www.inscribe.ai/reports/2026-document-fraud-report)）。对于每天处理数千份申请的金融机构来说，这种规模的欺骗构成了几乎不可能应对的挑战。传统人工审核每份申请需要 30 分钟，无法跟上不断增长的业务量。更关键的是，人工流程难以识别现代欺诈工具所催生的不断演变的作案手法。仅有速度还不够。解决方案还必须捕获复杂的伪造、deepfake 以及协同作案的欺诈团伙——这些从来都不是人工审核员和传统规则系统在设计时要识别的东西。

[Inscribe](https://www.inscribe.ai/) 自 2017 年起为领先的[银行](https://www.inscribe.ai/industries/banks)、[贷款机构](https://www.inscribe.ai/industries/lenders)与金融科技公司构建 AI 驱动的文档欺诈检测。在本文中，你将了解 Inscribe 如何使用 Amazon Bedrock 开发出一套 [agentic AI](https://www.inscribe.ai/why-inscribe) 系统，像资深欺诈分析师那样跨文档推理。借助这套新的 agentic AI 系统，Inscribe 现在能在 90 秒内检测出被篡改、伪造以及由 AI 生成的财务文档。相比传统人工审核，这是 20 倍的提升，同时保持了金融服务监管所要求的准确性与可解释性。

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 是一项全托管服务，通过单一 API 提供来自领先 AI 公司的高性能基础模型（FM）供你选择，包括 AI21 Labs、Anthropic、Cohere、Meta、Stability AI 与 Amazon。它还提供构建生成式 AI 应用所需的一整套能力，涵盖安全性、隐私与负责任 AI。

## 挑战

设想一家中型银行的典型贷款申请。客户提交银行对账单、工资单、税务文件和身份证明。欺诈分析师必须核实每份文档的真实性、交叉比对文档间的信息、检查是否存在篡改迹象（包括日益复杂的 deepfake 与 AI 生成伪造），还要调查申请人的雇主与住址。他们必须在完成这一切的同时保持快速周转，以免客户被竞争对手抢走。

这套人工流程带来三重叠加的挑战：

- **规模：** 随着申请量增长，机构必须按比例增聘分析师，成本随之上升，检测准确率却并未提高。
- **适应性：** 静态的欺诈检测规则会漏掉复杂手法，例如 deepfake、AI 生成的假文档以及有组织的身份盗用团伙。
- **一致性：** 不同分析师对相似案件得出不同结论，带来合规风险与公平性方面的顾虑。

财务上的利害关系十分重大。漏掉一个案件就可能意味着数百万的直接损失、因金融犯罪防控失职而面临的监管风险，以及更难恢复的声誉后果。耗时的人工审核会把客户审批拖上数天，导致较高的放弃率。与此同时，欺诈者不断变换手法，从 AI deepfake 与伪造文档转向合成身份欺诈，因为他们清楚，超负荷的分析师每天处理数百份申请时，可能会漏掉细微的篡改信号。

## 解决方案：为什么 agentic AI 能捕获人工审核漏掉的问题

Inscribe 构建了一套[AI 解决方案](https://www.inscribe.ai/why-inscribe)，与风险团队和核保团队协同工作。它自动完成常规文档分析，同时把复杂案件标记出来交由人工审核，把深厚的领域专长与[分层检测技术](https://www.inscribe.ai/ai-risk-agents)结合起来，发现人工审核团队与其他供应商容易漏掉的问题。

可以把 agentic AI 系统想象成一位从头到尾独立工作的专家分析师。它接受一个目标，把目标拆成步骤，使用多种工具，一路推进到完成。基础 AI 工具可能只回答单个问题，而 agentic 系统会协调专用模型、在需要时调用外部 API，并把一切综合成最终决策。就文档欺诈检测而言，这意味着 Inscribe 的系统不只是标记某个可疑字段。它会提交文档、将其路由到合适的模型、并行执行取证检查、上网核实雇主信息、在整个文档集内交叉比对数据，并在无需人工介入的情况下生成可供审计的欺诈报告，整个过程在数秒内完成。

[基础模型](https://aws.amazon.com/what-is/foundation-models/)擅长理解上下文、跨文档推理以及生成自然语言解释，这些都是欺诈分析必不可少的能力。塑造 Inscribe 架构的关键认识是：没有哪一个模型能同样胜任所有任务。为每一步协调最合适的模型，而不是用一个模型包打天下，能以更低的成本取得更好的结果。

## Amazon Bedrock 如何支撑多模型欺诈检测

Amazon Bedrock 丰富的模型选择意味着 Inscribe 可以为每项任务挑选合适的 FM，而无需管理各自独立的基础设施，从而把模型选择变成一项配置决策，而不是一个集成项目。

Serverless 弹性伸缩可以应对文档处理量的剧烈波动——从夜间低谷到工作时段高峰——而无需 Inscribe 预置专用的服务基础设施。

企业级安全与合规满足金融服务所需的严格数据保护标准：加密覆盖传输中与静态存储的数据，AWS Identity and Access Management（IAM）提供细粒度访问控制。

模型版本管理与治理让 Inscribe 可以在预发环境中测试新发布的模型，再推广到生产，这对保持欺诈检测准确率的一致性至关重要。

## 为任务匹配模型，兼顾速度与成本效率

Inscribe 在 Amazon Bedrock 上评估了多个模型，衡量性能、延迟与成本，为每项欺诈检测任务确定合适的模型。

### Anthropic Claude Haiku 4.5：在不拖慢审核的前提下降低成本 40%

相比使用 Claude Sonnet 处理常规任务，你可以把推理成本降低约 40%，而不牺牲速度。Inscribe 把 Claude Haiku 4.5 用于那些数秒内即可完成的高吞吐操作：文档解析、字段提取、初步分类与预筛检查。升级到 Haiku 4.5 后，常规任务的准确率有所提升，同时实现了上述成本下降。

### Meta Llama 3.1 70B 与 Meta Llama 4：让交易分析保持快速与低成本

在交易信息补全与实体提取方面，Inscribe 使用 Meta Llama 模型。Inscribe 的工程经理 Ivo 解释了这一决定：

> “我们在性能上没有看到太大差别。Llama 在这些任务上的质量达到了我们期望的水平，所以选择 Llama 让我们在不牺牲质量的前提下降低了成本。价格在最终决策中确实起了作用。”

这种务实的做法——当 Llama 的表现与更昂贵的替代方案相当时就选用 Llama——在高吞吐推理任务上带来了显著的成本节省。

### Anthropic Claude Sonnet 4 与 4.5：捕获跨文档的欺诈模式

Claude Sonnet 充当协调层，处理最复杂的任务：跨文档欺诈分析、多步推理工作流、用于核实雇主的 Web 搜索集成，以及生成可供审计的欺诈报告的自然语言。Sonnet 的扩展上下文窗口让它能对整套文档保持全局感知，识别出孤立分析单份文档时无法看见的模式。

## Inscribe 如何在 AWS 上扩展欺诈检测

Inscribe 的欺诈检测系统构建在 AWS 基础设施之上，旨在规模化地提供速度、可靠性与合规性。其 agentic 架构意味着系统会协调专用模型、决定下一步分析什么、在需要时调用外部 API，并在无需人工介入的情况下把一切综合成最终决策。

Inscribe 在 AWS 上的欺诈检测架构

### 文档摄取与存储

当贷款申请文档通过 Inscribe 的 Web 界面或 API 上传后，文档会落到 [Amazon Simple Storage Service](https://aws.amazon.com/pm/serv-s3/)（Amazon S3）——一项业界领先的可扩展对象存储服务。通过 [Amazon CloudFront](https://aws.amazon.com/cloudfront/) 与 [Application Load Balancer](https://aws.amazon.com/elasticloadbalancing/application-load-balancer/) 提供服务的 Web 应用会创建处理作业，并将其排入 [Amazon Simple Queue Service](https://aws.amazon.com/sqs/)（Amazon SQS）队列。文档随即进入处理队列，无需任何人工交接。

### 异步处理

运行在 Amazon Elastic Compute Cloud（Amazon EC2）上的 Celery worker 进程（一种分布式任务队列）从队列中拉取作业。这种基于队列的架构能够无延迟地应对流量尖峰。工作时段会自动扩容更多 worker，夜间则缩减容量以尽量降低成本。无论你是在处理十份申请还是一万份申请，系统都能提供一致的性能。

### 文本提取

[Amazon Textract](https://aws.amazon.com/textract/) 提供基础的光学字符识别（OCR）以及从 PDF 与图像中提取文本的能力。Inscribe 已越来越多地把解析负载直接转移到 Amazon Bedrock 上的 FM，从复杂的财务文档中获得更准确的提取结果。

### 多模型欺诈检测 pipeline

Inscribe 提取文本后，文档会以协调好的顺序流经 Amazon Bedrock 上的多个 FM。Claude Haiku 执行快速的初步解析与分类。Meta Llama 模型处理交易数据并提取实体。Claude Sonnet 进行跨文档分析、协调用于雇主核实与地址验证的 Web 搜索，并生成最终的欺诈评估。每个模型各司其长，把审核时间控制在数秒之内。

### 运行在 Amazon SageMaker AI 上的专有欺诈检测模型

在基础模型分析并行进行的同时，Inscribe 还运行托管在 [Amazon SageMaker AI](https://aws.amazon.com/sagemaker/ai/) 上的专有机器学习（ML）模型。这些模型完全由内部构建，基于 Inscribe 每年处理的数百万份申请训练而成，能检测通用大语言模型（基础模型的一个子集）遗漏的信号：用于识别数字篡改图像的像素级取证分析、将文档与已知欺诈模板库比对的网络模式检测，以及针对被篡改签名或版式的视觉异常检测。

SageMaker AI 提供托管基础设施，用于大规模部署这些专用模型，并内置模型部署、自动扩缩容与性能监控能力。Inscribe 的工程团队因此可以专注于改进欺诈检测算法，而不是管理基础设施；这一点尤其重要，因为金融犯罪手法的演变速度已超过静态规则系统的适应能力。

### 结果存储、缓存与可观测性

Inscribe 把中间推理轨迹与最终欺诈报告都存储在 Amazon Relational Database Service（Amazon RDS）中，为合规团队提供可靠的审计轨迹，同时支持持续的模型改进。[Amazon ElastiCache for Valkey](https://aws.amazon.com/elasticache/what-is-valkey/) 缓存 webhook token 等短生命周期数据、执行限流，并管理 Celery 任务元数据。[Amazon MemoryDB](https://aws.amazon.com/memorydb/) 支撑向量数据库层，交易 embedding 在其中存储，并通过 K-最近邻（KNN）搜索查询——这种技术在数据集中找出最相似的记录——为辅助模型提供支持。

[Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 跟踪模型性能指标，包括推理延迟、错误率、token 用量与每请求成本。这种可观测性对于检测模型漂移至关重要——预测准确率的变化正是需要重新训练或更新模型的信号。
