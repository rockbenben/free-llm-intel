## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 使用 Okta Cross App Access 和 Amazon Bedrock AgentCore 管理 AI 代理访问 – 第 1 部分

更新票证或读取客户记录的人工智能代理在该人可以访问的应用程序内代表一个人。然后，您的身份团队必须回答每个应用程序 OAuth 同意和共享服务帐户保持开放的问题：哪个代理可能在哪个应用程序中为哪个用户执行操作，以及如何停止它。 Okta Cross App Access (XAA) 在您的身份提供商 (IdP) 中回答该问题。您在 Okta 中注册代理，管理员批准其可能访问的应用程序，并且每次代理要求代表用户执行操作时，Okta 都会评估策略。在我们的测试中，管理员删除用户对代理的分配后，Okta 在大约 1 秒内拒绝了代理对该用户的新请求，并且已颁发的令牌在 5 分钟内过期。

[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 是一个使用任何框架或模型大规模构建、连接和优化代理的平台。该解决方案使用其两项功能在 AWS 上执行 Okta 的决策。 Amazon Bedrock AgentCore 运行时是 Amazon Bedrock AgentCore 的一项功能，可验证 Okta 的授权。 Amazon Bedrock AgentCore Identity 是 Amazon Bedrock AgentCore 的一项功能，可使用您的代理代码看不到的凭证将其兑换为短期访问令牌，并将该令牌保留在其令牌库中。在我们的测试中，AgentCore Identity 使端到端耗时约 30 秒的请求增加了约 0.6 秒。

在这篇文章（两篇文章中的第一篇）中，您将在 AgentCore 运行时构建一个任务代理，该代理通过 XAA 和 AgentCore Identity 为登录用户提供服务。您配置所需的 AgentCore Identity 部分，在工具中强制执行每个用户的权限，并查看我们测量的内容：每次检查拒绝的内容、我们确定的做法以及 Okta 的控制生效的速度。 [第 2 部分](https://aws.amazon.com/blogs/machine-learning/govern-ai-agent-access-with-okta-cross-app-access-and-amazon-bedrock-agentcore-part-2/) 然后将相同的治理置于 Amazon Bedrock AgentCore Gateway 后面，这是 Amazon Bedrock AgentCore 的一项功能，具有 Cedar 策略、Amazon Elastic Kubernetes Service (Amazon EKS) 上的第二个代理以及 Amazon CloudWatch 中的审计跟踪。

## 解决方案概述

Okta 是治理平面：它决定哪个代理可以为哪个用户、针对哪个资源执行操作。 AgentCore Identity 是执行平面：它保存代理的凭据，将 Okta 的决策转换为资源接受的令牌，并将两个身份保留在该令牌中。在图 1 中，代理及其调用的两个模型上下文协议 (MCP) 服务器均在 AgentCore 运行时上运行。

![Okta 治理平面和 AgentCore Identity 执行平面，代理和两个 MCP 服务器在 AgentCore 运行时上运行](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/29/ML-21547-1.png)

图 1：解决方案架构，编号与后续步骤相匹配

每个请求携带三个令牌，每个请求都记录不同的决策：ID 令牌表示用户是谁，身份断言 JWT 授权授予 (ID-JAG) 是 Okta 的决策，访问令牌是资源接受的决策。一个请求的流程如下：

- 用户通过代理链接的 Okta 应用程序使用 OpenID Connect 登录 Web 前端（前端的后端 (BFF)）。
- 对于每个请求，BFF 在 Okta 的组织授权服务器上将用户的 ID 令牌交换为 ID-JAG，并作为代理进行身份验证（RFC 8693 令牌交换）。 Okta 检查代理是否处于活动状态、用户是否已分配给它以及管理员是否将其连接到请求范围的目标授权服务器。 ID-JAG 是一次性的，5 分钟后失效。
- BFF 使用 ID-JAG 作为其承载令牌来调用 AgentCore 运行时上的代理。运行时的 JWT 授权方仅接受 Okta 向该代理颁发的 ID-JAG。
- 运行时从 AgentCore Identity 获取工作负载访问令牌，该令牌将代理的工作负载身份绑定到用户，并将其传递给代理代码。此工作负载访问令牌是 AWS 内部绑定令牌：Okta 和资源都看不到它，因此它不是三个令牌之一。
- 代理向 AgentCore Identity 请求访问令牌。 AgentCore Identity 使用 JWT 授权 (RFC 7523) 在资源的 Okta 自定义授权服务器上兑换 ID-JAG，并作为代理进行身份验证。 Okta 返回一个 5 分钟的访问令牌，其中命名了用户和代理并包含用户的组。
- 代理使用该令牌调用 MCP 服务器。任务管理器检查注册代理是否获得了该工具，以及用户的组和范围是否允许该工具。

图 2 将相同的请求显示为一个序列，并包含各方进行的检查。

![显示 ID 令牌、ID-JAG 和访问令牌的三令牌链序列，以及各方进行的检查](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/29/ML-21547-2.png)

## 在 Okta 中注册代理

Okta 需要资源、代理、它们之间的连接以及接受代理授权的策略的授权服务器。在 Okta 管理控制台中执行所有这些步骤：注册代理会创建其链接的应用程序，因此您不需要应用程序集成向导。

- 使用受众“api://task-manager”和自定义范围“xaa:read”和“xaa:write”为资源应用程序创建自定义授权服务器。仅请求资源的自定义范围：Okta 会拒绝包含 OpenID Connect 范围（例如“openid”或“profile”（“invalid_scope”））的 ID-JAG 请求，因此请求至少需要一个自定义范围，并且不需要 OpenID Connect 范围。
- 向其访问令牌添加“groups”声明，过滤到以“xaa-”开头的组。该声明承载了每个用户对工具的权限。
- 在管理控制台中，转至 **目录** > **AI 代理**，选择 **注册 AI 代理**，然后选择 **手动注册**，可选择分配所有者，然后创建链接的 OpenID Connect 应用程序。在 **客户端注册** 上，选择 **客户端密钥**，生成密钥，然后激活代理。代理和应用程序共享一个客户端 ID，并且该应用程序必须让您的用户登录：来自另一个应用程序的 ID 令牌无法进行交换，并显示“客户端应用程序未注册委派给此代理”。
- 在代理的 **资源连接** 选项卡上，将其连接到授权服务器，仅限于其所需的范围，如图 3 所示。
- 将访问策略规则添加到自定义授权服务器，以允许代理的 JWT Bearer 授予，访问令牌的生命周期为 5 分钟。如果没有授权类型，第二次交换将失败并显示“no_matching_policy”，并且生命周期限制了已撤销的委托继续工作的时间。
- 分配可能通过代理进行操作的用户或组。他们通过链接的应用程序登录，因此为其提供一个应用程序登录策略，允许他们使用他们注册的身份验证器。在我们的沙箱组织中，链接的应用程序有自己的策略和测试组的规则。对于真实用户，请应用您组织的策略，包括多重身份验证。

图 3：Okta 中任务代理的资源连接，仅限于 xaa:read 和 xaa:write 范围

Okta 的[跨应用程序访问指南](https://developer.okta.com/docs/guides/xaa-agent-to-app/main/) 涵盖了控制台步骤和 AWS 示例[08-okta-xaa-delegation-chain](https://github.com/awslabs/agentcore-samples/tree/2747451473d1fadbba18f5aee0524e533e3c2b2e/01-features/05-authenticate-and-authorize/08-okta-xaa-delegation-chain)编写授权服务器及其JWT脚本不记名政策。然后，BFF 请求 ID-JAG，并作为代理进行身份验证：

```
Authorization: Basic <the agent's client ID and secret>
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&requested_token_type=urn:ietf:params:oauth:token-type:id-jag
&subject_token=<the user's ID token>
&subject_token_type=urn:ietf:params:oauth:token-type:id_token
&audience=https://YOUR-ORG.okta.com/oauth2/YOUR-CUSTOM-AS-ID

```

## 设置 AgentCore 身份

AgentCore Identity 为该解决方案保留了三件事，并且您的代理代码看不到客户端密钥或调用 Okta 的令牌端点：

| **AgentCore 身份的一部分** | **它包含什么** | **谁创造了它** |
| --- | --- | --- |
|工作负载身份| AWS 上的代理身份，针对每个请求绑定到登录用户 | AgentCore 运行时，针对每个代理运行时 |
| OAuth2 凭据提供程序 |代理的 Okta 客户端 ID 和密码，以及使用授权 |你，每个 Okta 特工一次 |
|代币库 |提供商获得的访问令牌 | AgentCore 身份 |

### 创建凭证提供者

凭证提供者执行第二次交换。将其指向自定义授权服务器，将其验证为 AI 代理，并将代表授权设置为“JWT_AUTHORIZATION_GRANT”，AgentCore Identity 将其作为“jwt-bearer”发送，并以 ID-JAG 作为断言：
```
control = boto3.client("bedrock-agentcore-control")
provider = control.create_oauth2_credential_provider(
    name="okta-xaa-obo",
    credentialProviderVendor="CustomOauth2",
    oauth2ProviderConfigInput={"customOauth2ProviderConfig": {
        "oauthDiscovery": {"discoveryUrl": f"{OKTA_ORG}/oauth2/{CUSTOM_AS_ID}/.well-known/openid-configuration"},
        "clientId": AGENT_CLIENT_ID,          # the AI agent's Okta client ID
        "clientSecret": AGENT_CLIENT_SECRET,  # AgentCore Identity stores it in AWS Secrets Manager
        "clientAuthenticationMethod": "CLIENT_SECRET_BASIC",
        "onBehalfOfTokenExchangeConfig": {"grantType": "JWT_AUTHORIZATION_GRANT"},
    }},
)
provider_arn = provider["credentialProviderArn"]
```
Okta 将两个交换都绑定到 ID-JAG 中指定的客户端，因此每个 Okta 代理都需要自己的提供程序：当我们将一个代理的 ID-JAG 兑换为另一个代理时，Okta 拒绝了“JWT 承载授权中的‘client_id’必须与用于验证客户端的‘client_id’匹配。” AgentCore Identity 将机密保存在服务管理的 AWS Secrets Manager 机密中，您可以使用“update-oauth2-credential-provider”轮换该机密。如果您的团队已在 Secrets Manager 中管理客户端密钥，您可以改为引用该密钥的 ARN。 AgentCore Identity 从中读取客户端密钥，因此您可以轮换密钥而无需更新提供程序（请参阅[在 Amazon Bedrock AgentCore Identity 中引用您自己的 AWS Secrets Manager 密钥](https://aws.amazon.com/blogs/machine-learning/reference-your-own-aws-secrets-manager-secrets-in-amazon-bedrock-agentcore-identity/)）。为了避免共享秘密，请改为使用私钥进行身份验证。请参阅[使用 Amazon Bedrock AgentCore Identity 通过私钥 JWT 进行身份验证](https://aws.amazon.com/blogs/machine-learning/authenticate-with-private-key-jwt-using-amazon-bedrock-agentcore-identity/)。图 4 显示了 AgentCore 控制台中的提供程序。

### 使用 AgentCore 运行时管理的工作负载身份

AgentCore 运行时为每个代理运行时创建并管理工作负载身份。当请求通过运行时的 JWT 授权方时，运行时会获取该工作负载身份以及入站令牌的颁发者和主题的工作负载访问令牌，并将其传递给您的代码。然后，AgentCore Identity 使用其背后的 ID-JAG 作为交换的断言。

AgentCore Python SDK 将工作负载访问令牌保存在“BedrockAgentCoreContext”中，而不是保存在入口点收到的请求标头中。我们的第一个版本在标头中查找它，但什么也没找到，然后在我们检查的所有 21 个请求上使用第二个工作负载身份回退到它自己的“GetWorkloadAccessTokenForJWT”调用。请从上下文中阅读：
```
from bedrock_agentcore.runtime import BedrockAgentCoreContext

identity = boto3.client("bedrock-agentcore")

def okta_access_token() -> str:
    workload_token = BedrockAgentCoreContext.get_workload_access_token()  # minted by the runtime
    return identity.get_resource_oauth2_token(
        workloadIdentityToken=workload_token,
        resourceCredentialProviderName="okta-xaa-obo",
        scopes=["xaa:read", "xaa:write"],  # must equal the ID-JAG's scopes
        oauth2Flow="ON_BEHALF_OF_TOKEN_EXCHANGE",
    )["accessToken"]
```
AgentCore Identity 将访问令牌保留在其令牌库中以供其余请求使用。在 10 个请求中，代理的第一个调用在大约半秒内兑换了 ID-JAG（请参阅验证结果中的延迟表），而第二个调用（对于其他 MCP 服务器）在中位数 58 毫秒内返回了相同的令牌，而无需再次兑换一次性 ID-JAG。同一用户的新 ID-JAG 获得了新令牌，因此每个请求都反映了 Okta 的最新决定。示例 [08-okta-xaa-delegation-chain](https://github.com/awslabs/agentcore-samples/tree/2747451473d1fadbba18f5aee0524e533e3c2b2e/01-features/05-authenticate-and-authorize/08-okta-xaa-delegation-chain) 读取工作负载访问令牌同样的方式（[agent/agent.py]（https://github.com/awslabs/agentcore-samples/blob/2747451473d1fadbba18f5aee0524e533e3c2b2e/01-features/05-authenticate-and-authorize/08-okta-xaa-delegation-chain/agent/agent.py#L86-L101））。

### 将代理的角色范围限定为其工作负载身份和提供者

AgentCore Identity 不会将工作负载身份绑定到同一账户中的凭证提供程序。代理的 IAM 角色确实如此，因此将其范围限定为代理自己的工作负载身份和提供商以及该提供商的秘密：
```
[
  {
    "Sid": "OktaOnBehalfOf",
    "Effect": "Allow",
    "Action": "bedrock-agentcore:GetResourceOauth2Token",
    "Resource": [
      "arn:aws:bedrock-agentcore:us-west-2:123456789012:workload-identity-directory/default",
      "arn:aws:bedrock-agentcore:us-west-2:123456789012:workload-identity-directory/default/workload-identity/RUNTIME-WORKLOAD-IDENTITY",
      "arn:aws:bedrock-agentcore:us-west-2:123456789012:token-vault/default",
      "arn:aws:bedrock-agentcore:us-west-2:123456789012:token-vault/default/oauth2credentialprovider/okta-xaa-obo"
    ]
  },
  {
    "Sid": "ReadProviderSecret",
    "Effect": "Allow",
    "Action": "secretsmanager:GetSecretValue",
    "Resource": "arn:aws:secretsmanager:us-west-2:123456789012:secret:bedrock-agentcore-identity!default/oauth2/okta-xaa-obo-*"
  }
]
```
从“GetAgentRuntime”中的“workloadIdentityDetails”中获取工作负载身份的名称，并从“credentialProviderArn”中获取提供程序的 ARN：该段是“oauth2credentialprovider”，并且使用连字符形式，每个调用都会因“AccessDeniedException”而失败。该角色不需要“GetWorkloadAccessToken”权限，因为运行时获取该令牌，而不是代理。我们的测试仅通过这两个语句就通过了。

## 在 AgentCore 运行时部署代理

将代理运行时的入站授权方配置为仅接受 Okta 向该代理颁发的 ID-JAG。它的发行者是 Okta 的组织授权服务器，其受众是资源的自定义授权服务器。在“agentcore.json”中：
```
"authorizerType": "CUSTOM_JWT",
"authorizerConfiguration": {
  "customJwtAuthorizer": {
    "discoveryUrl": "https://YOUR-ORG.okta.com/.well-known/openid-configuration",
    "allowedAudience": ["https://YOUR-ORG.okta.com/oauth2/YOUR-CUSTOM-AS-ID"],
    "allowedClients": ["YOUR_AGENT_CLIENT_ID"],
    "allowedScopes": ["xaa:read", "xaa:write"]
  }
}
```
“allowedClients”与 ID-JAG 携带的“client_id”声明匹配。如果没有它，运行时会使用 HTTP 200 承认另一个代理的 ID-JAG，并且请求稍后在交换时失败。使用它，运行时会使用 HTTP 401 拒绝该令牌。

除了上一节中的策略之外，执行角色还需要“bedrock:InvokeModel”和“bedrock:InvokeModelWithResponseStream”。它不需要 MCP 服务器的“bedrock-agentcore:InvokeAgentRuntime”权限：每个服务器都在自己的 JWT 授权者后面的 AgentCore 运行时上运行，自定义授权服务器作为颁发者，“api://task-manager”作为受众，因此代理使用 Okta 访问令牌作为承载令牌来调用它，而不是使用 AWS 签名版本 4 (SigV4)。

## 在MCP服务器中强制执行每个用户的权限

资源连接为代理的每个用户设置范围，因此所有三个测试用户都收到“xaa:read xaa:write”，并且每个用户的权限在“groups”声明中传递：Alice 的令牌携带“xaa-readers”，Bob 的“xaa-writers”，而 Carol 则没有。

任务管理器检查两件事：它只接受注册代理获得的令牌，并且仅当组和范围都存在时才允许写入：
```
REGISTERED_AGENTS = {"YOUR_AGENT_CLIENT_ID"}

def _require_agent() -> None:
    claims = _decode_claims()  # the runtime's JWT authorizer already validated the token
    agent = (claims.get("act") or {}).get("sub")
    if agent in REGISTERED_AGENTS and claims.get("cid") == agent:
        return
    raise ToolError("insufficient_privileges: this server accepts only tokens that a registered "
                    "AI agent obtained through Okta Cross App Access")

def _require_write() -> None:
    _require_agent()
    if WRITERS_GROUP in _groups() and "xaa:write" in _scopes():
        return
    raise ToolError(f"insufficient_privileges: this tool requires membership in '{WRITERS_GROUP}'")
```
两项检查弥补了我们发现的差距：允许不带“groups”声明的令牌的写入检查让不属于任何组的 Carol 创建任务，而在“_require_agent”之前，向不带“act”声明的服务应用程序颁发普通令牌交换令牌，为 Bob 创建任务。服务器可以读取声明而无需再次验证令牌，只是因为运行时的 JWT 授权者已经验证了它。前面没有该授权者的服务器必须自行检查签名、颁发者、受众和过期时间，就像 Amazon EKS 上的第 2 部分代理所做的那样。

## 管理运行中的代理

Okta 在创建 ID-JAG 时会评估代理、用户和连接。我们测量了每个管理员操作对下一个请求和颁发的令牌的影响：

| **Okta 中的管理操作** | **新请求** | **代币已发行** |
| --- | --- | --- |
|删除代理的资源连接 |立即拒绝 (`invalid_target`) |工作直至过期，最多 5 分钟 |
|删除用户的分配 |即使用户已经持有 ID 令牌，也会在大约 1 秒内被拒绝 |最多 5 分钟 |
|停用代理 | Okta 运行操作后被拒绝，我们的测试组织排队等待了 86 分钟 |最多 5 分钟 |

对一名特工采取的行动让另一特工继续工作。兑换 ID-JAG 时，Okta 不会重新检查用户：其自定义授权服务器在我们删除用户后 3 秒发出访问令牌，用于删除之前创建的 ID-JAG。 Okta 的系统日志记录以代理为参与者的每个授权，第 2 部分将这些事件流式传输到 CloudWatch。

## 委托链的最佳实践

这些测量得出了六种做法，每一种都是链的属性而不是偏好：

| **练习** | **我们测量了什么** |
| --- | --- |
|为每个请求创建一个新的 ID-JAG | ID-JAG 是一次性的，使用寿命为 300 秒。运行时拒绝还剩 60 秒的时间，因此 225 秒有效，245 秒无效 |
|在“groups”声明中携带每用户权限，并为每个请求请求一个范围集 | Okta 从资源连接设置范围，因此所有三个用户都获得相同的范围，并且第二个交换必须准确请求 ID-JAG 的 |
|运行时固定代理，并在工具中检查`act`和`cid` | “allowedClients”与 ID-JAG 携带的“client_id”声明匹配。 Okta 访问令牌改为携带“cid” |
|直接针对 Okta 重现失败的交换 |通过 AgentCore Identity，范围不匹配和错误的客户端都会显示为“令牌交换失败，HTTP 状态 400” |
|授予代理角色对提供商机密的读取权限 |在角色可以读取之前，`GetResourceOauth2Token` 失败 |
|保持较短的生命周期，并使用资源连接作为终止开关 |删除连接立即生效。停用代理在 Okta 的 beta AI 代理 API 队列中等待了 86 分钟，没有取消 |

## 跨应用程序访问与普通令牌交换的比较

普通 RFC 8693 令牌交换还向下游传送用户身份。我们将其与 XAA 与相同的 Okta 授权服务器和用户进行比较：

| **我们观察到的行为** | **普通代币交换** | **跨应用程序访问** |
| --- | --- | --- |
|代币中的代理身份 |没有“行为”声明 | `act` 命名代理 |
|范围 |拓宽：Alice 自己的代币有 `xaa:read`，交易所返回了 `xaa:read xaa:write` |管理员批准的范围 |
|交换规则仅限于“xaa-writers” | Alice 仍然收到了令牌 |爱丽丝否认|
|用户未分配，之前的令牌已重用 |还是交流|拒绝 |
|管理员看到什么 |具有授权类型的服务应用程序 |代理、其连接以及每个日志事件中的代理 |

这些结果反映了我们的 Okta 配置。 Okta 的指南显示了交换代币的“act”声明，但我们没有收到。普通的代币交换承载了用户的身份，但不承载用户的权限。

## 此模式适用的地方

我们与媒体和娱乐公司合作，这是我们首先遇到问题的地方。工作室或流媒体或游戏组织针对制作跟踪、标题和资产元数据、权利和本地化以及观众或玩家支持运行代理。每个系统都有自己的授权模型和自己的审核员，并且用户的权限因名称、地区或发布窗口而异，因此在代理发货之前必须回答“哪个代理可能在哪个系统中为哪个用户代理”。

链中没有任何内容是特定于该行业的：代理是 IdP 中的身份，目标是 OAuth 2.0 授权服务器，用户的权限取决于声明。金融服务、医疗保健和公共部门团队将不同的资源置于相同的控制之下。

## 清理

为了避免持续产生费用，请删除您创建的资源：

- 删除 AgentCore CLI 为代理和两个 MCP 服务器创建的 AWS CloudFormation 堆栈。
- 使用“aws bedrock-agentcore-control delete-oauth2-credential-provider --name okta-xaa-obo”删除凭证提供程序，以及使用“delete-workload-identity”自行创建的任何工作负载身份。
- 删除您添加到执行角色的 IAM 策略。
- 在 Okta 中，停用并删除 AI 代理及其链接的应用程序，并删除资源连接、授权服务器的策略规则、范围和声明以及测试用户和组。

## 结论

在本文中，您使用 Okta Cross App Access 来决定哪个代理可以为哪个用户执行操作，并使用 AgentCore Identity 来执行每个决策。运行时仅允许代理自己的 ID-JAG，凭证提供程序使用代理未持有的秘密兑换每个 ID-JAG，令牌库在请求中重用结果，MCP 服务器根据“组”声明强制执行每个用户的权限。

这种设计将交换保持在代理角色中，并在每个 MCP 服务器中重复授权检查。请参阅[本系列的第 2 部分](https://aws.amazon.com/blogs/machine-learning/govern-ai-agent-access-with-okta-cross-app-access-and-amazon-bedrock-agentcore-part-2/)，了解其设计为何采用 Cedar 策略将两个 AgentCore 网关置于一个 AgentCore 网关后面，在 Amazon EKS 上添加第二个代理，并将 Okta 系统日志与 CloudWatch 中的 AgentCore 跟踪结合起来。

首先，请探索 [AgentCore 示例](https://github.com/awslabs/agentcore-samples/tree/2747451473d1fadbba18f5aee0524e533e3c2b2e/01-features/05-authenticate-and-authorize) 和 Okta 的 [跨应用程序访问]文档](https://developer.okta.com/docs/concepts/xaa/)。有关 API 详细信息，请参阅 AgentCore 开发人员指南中的[代表令牌交换](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/on-behalf-of-token-exchange.html)。
