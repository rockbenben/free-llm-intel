# 使用 Amazon Bedrock Guardrails 保护生成式 AI 应用

希望借助 AI agent 实现流程自动化，或借助基于聊天的 AI 助手提升员工生产力的企业，需要针对负责任地使用 AI，以及由[大语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）处理敏感数据，落实全面的防护措施与审计控制。许多企业已经构建了自研的[生成式 AI 网关](https://aws.amazon.com/solutions/guidance/multi-provider-generative-ai-gateway-on-aws/)，或采用了现成的解决方案（例如 [LiteLLM](https://github.com/BerriAI/litellm) 或 [Kong AI Gateway](https://konghq.com/products/kong-ai-gateway)），以便让他们的 AI 从业者和开发者能够访问来自不同提供商的 LLM。然而，要在规模化场景下针对来自各类提供商、数量不断增长的 LLM 统一执行并维持一致的 prompt 安全与敏感数据保护策略，却颇具挑战。

本文演示如何通过 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 为自研的多提供商生成式 AI 网关添加集中式防护措施，以此应对这些挑战。Amazon Bedrock Guardrails 提供了一整套安全功能，帮助组织在规模化场景下构建负责任的生成式 AI 应用。你将了解到如何使用 [Amazon Bedrock ApplyGuardrail API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ApplyGuardrail.html)，为来自 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 以及 Microsoft Azure OpenAI 等第三方提供商的 LLM 统一执行 prompt 安全与敏感数据保护策略。该方案还带来集中式日志记录与监控、分析，以及成本分摊机制等额外收益。

## 方案概述

要用集中式防护措施保护生成式 AI 应用，需要满足若干要求。首先，组织需要为生成式 AI 网关及其防护组件搭建健壮且可扩展的基础设施。方案还需要一套全面的日志记录与监控系统来跟踪 AI 交互，并需要具备分析能力以评估使用模式与合规情况。在敏感数据保护方面，组织需要制定清晰的数据治理策略并实施适当的安全控制。此外，他们需要开发或集成一套成本分摊机制，用于跟踪并在不同部门或项目之间分摊 AI 使用成本。了解所在行业特有的监管要求至关重要，可确保防护措施配置得当并符合合规标准。

下图展示了我们建议方案的概念示意图。工作流从已认证用户向生成式 AI 网关发送 HTTPS 请求开始；该网关是运行在 [Amazon Elastic Container Service](https://aws.amazon.com/ecs/)（Amazon ECS）上的集中式应用，充当 LLM 交互的主要接口。在生成式 AI 网关的应用逻辑中，每个传入请求首先被转发到 Amazon Bedrock `ApplyGuardrail` API 进行内容筛查。随后，生成式 AI 网关依据预定义配置对内容进行评估，并做出关键决策：完全阻止请求、屏蔽敏感信息，或允许其原样通过。

这一评估过程是生成式 AI 网关功能的核心组成部分，有助于遵循既定的安全与合规准则。对于通过筛查的请求，生成式 AI 网关逻辑会依据用户的指定确定合适的 LLM 提供商（Amazon Bedrock 或第三方服务）。筛查后的内容随后被转发给选定的 LLM 进行处理。最后，生成式 AI 网关接收 LLM 的响应并返回给用户，完成整个交互周期。响应流程分为两条不同路径：被阻止的请求会让用户收到内容已被阻止的消息；被批准的请求则返回模型的响应，并对用户 prompt 施加必要的内容屏蔽。在我们的实现中，防护措施仅应用于输入（即 prompt），不应用于 LLM 的响应。这一精简的流程为 Amazon Bedrock 与第三方提供商提供了统一的 LLM 访问、安全与合规方式。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/01/08/flow_diagram-1.png)

生成式 AI 网关应用托管在 [AWS Fargate](https://aws.amazon.com/fargate/) 上，并使用 [FastAPI](https://fastapi.tiangolo.com/) 构建。该应用会与其他 [Amazon Web Services](https://aws.amazon.com/)（AWS）服务交互，例如 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）、Amazon Bedrock、[Amazon Kinesis](https://aws.amazon.com/kinesis/) 和 [Amazon Data Firehose](https://aws.amazon.com/firehose/)。该方案包含健壮的数据持久化层，用于捕获交互详情，并通过 [Amazon Kinesis Data Streams](https://aws.amazon.com/kinesis/data-streams/) 和 Amazon Data Firehose 将其存储到 Amazon S3。持久化的数据包括经脱敏处理的请求与响应、交易信息、防护措施元数据，以及被阻止的内容及其相关元数据。这套全面的日志记录实现了完整的可审计性，并使防护机制得以持续改进。

## 方案组件

该方案通过以下工具与技术实现可扩展性：

- [nginx](https://nginx.org/)，通过在每个容器内对请求进行负载均衡，为应用提供最高的性能与稳定性。
- [Gunicorn](https://gunicorn.org/)，一个 Python Web Server Gateway Interface（WSGI）HTTP 服务器，常用于在生产环境中提供 Python Web 应用。它是一款高性能服务器，能够高效处理多个 worker 进程与并发请求。Gunicorn 仅支持同步通信，但具备健壮的进程管理功能。
- [Uvicorn](https://www.uvicorn.org/)，用于提供轻量级、异步的请求处理。尽管 Gunicorn 是同步的，但它支持使用 Uvicorn 这类异步 worker 类型，从而可以建立异步通信。这对等待时间较长的应用是必需的。在从 LLM 获取响应的场景中，你应预期更长的等待时间。
- [FastAPI](https://fastapi.tiangolo.com/)，在生成式 AI 网关应用层处理实际请求。
- [Amazon ECS Fargate 集群](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html)，用于在 AWS 上托管容器化应用；并使用 AWS Auto Scaling 自动扩缩任务或容器。
- [Amazon Elastic Container Registry（Amazon ECR）](https://aws.amazon.com/ecr/)，用于存储生成式 AI 网关应用的 Docker 镜像。
- [Elastic Load Balancing（ELB）](https://aws.amazon.com/elasticloadbalancing/) 和 [Application Load Balancer](https://aws.amazon.com/elasticloadbalancing/application-load-balancer/?nc=sn&amp;loc=2&amp;dn=2)，用于在 ECS 容器之间对请求进行负载均衡。
- [HashiCorp Terraform](https://developer.hashicorp.com/terraform)，用于资源预置。

### 集中式防护措施

生成式 AI 网关通过 Amazon Bedrock Guardrails 实施全面的安全控制，使用 `ApplyGuardrail` API 实现多层防护。这些防护措施提供四项核心安全功能：内容过滤，用于筛查不当或有害内容；拒绝主题（denied topics），帮助阻止特定主题的讨论；词过滤器，用于阻止特定词语或短语；敏感信息检测，帮助保护个人与机密数据。

组织可以使用三档可配置的强度级别来实施这些控制——low、medium 和 high。这样，各业务部门就能让其 AI 安全态势与自身的风险容忍度和合规要求相匹配。例如，营销团队在处理创意内容生成时可能采用低强度防护，而金融或医疗部门在处理敏感客户数据时可能要求高强度防护。除这些基础防护之外，Amazon Bedrock Guardrails 还包含上下文接地（contextual grounding）与自动化推理检查（automated reasoning checks）等高级功能，有助于检测并防止 AI 幻觉（即模型生成虚假或误导性信息的情形）。用户可以根据自身用例扩展生成式 AI 网关的功能，以支持这些高级特性。

### 多提供商集成

生成式 AI 网关对 LLM 提供商与模型均保持无关性，从而可与多个提供商和 LLM 无缝集成。用户可以直接在请求负载中指定首选的 LLM 模型，让网关把请求路由到相应的模型端点。[AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 用于存储生成式 AI 网关的 API 访问 token，以及来自 Azure OpenAI 等第三方 LLM 的访问 token。生成式 AI 网关的 API token 用于对调用方进行身份验证。LLM 访问 token 用于为第三方提供商建立客户端连接。

### 日志记录、监控与告警

实施生成式 AI 网关的一大优势，是以集中方式对 LLM 交互进行日志记录与监控。每一次交互——包括用户请求与 prompt、LLM 响应以及用户上下文——都会被捕获，并以标准化格式存储在统一位置。组织可以利用这种采集策略执行分析、排查问题并提炼洞察。日志记录、监控与告警通过以下 AWS 服务实现：

- [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 捕获容器日志与应用日志。我们可以针对特定的日志消息创建自定义指标，并创建可用于主动告警的 alarm（例如在发生 500 Internal Server Error 时）
- [Amazon Simple Notification Service](https://aws.amazon.com/sns/)（Amazon SNS）用于向分发列表发送通知（例如在发生 500 Internal Server Error 时）
- Kinesis Data Streams 与 Data Firehose 用于把请求、响应数据及元数据以流式方式传输到 Amazon S3（用于合规与分析，或用于成本分摊）。成本分摊是一种把成本归属到所有者层级的机制。例如，运行在 AWS 上的某个应用会为每项服务产生一定成本，而该应用可能服务于某位员工，该员工则为某个业务部门治理的项目工作。成本分摊是一个能把成本归属到单个用户这一最低层级、并可在多个中间层级逐级汇总直至业务部门的过程。
- Amazon S3 用于在交易级别持久化请求与响应（用于合规），同时持久化交易元数据与指标（例如 token 数量），用于分析与成本分摊。
- [AWS Glue](https://aws.amazon.com/glue/) [Crawler API](https://docs.aws.amazon.com/glue/latest/webapi/API_Crawler.html) 和 [Amazon Athena](https://aws.amazon.com/athena/) 用于暴露交易元数据的 SQL 表，供分析与成本分摊使用。

## 前提条件

部署该方案前，你需要满足以下前提条件：

- 一个 AWS 账户
- 一个具备以下权限的 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色：Amazon S3 访问（CreateBucket、PutObject、GetObject、DeleteObject）AWS Secrets Manager 访问 Amazon CloudWatch 日志访问 Amazon Bedrock 服务 Amazon Bedrock 基础模型（FM）访问 Amazon Bedrock Guardrails IAM 权限
- Amazon Bedrock Guardrails 所需的 IAM 权限：

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "VisualEditor0",
            "Effect": "Allow",
            "Action": [
                "bedrock:ApplyGuardrail",
                "bedrock:ListGuardrails",
                "bedrock:GetGuardrail"
            ],
            "Resource": "arn:aws:bedrock:<AWS_REGION>:<AWS_ACCOUNT_ID>:guardrail/*"
        }
    ]
}
```

- Amazon Bedrock 上的无服务器 FM 会自动启用。你无需手动申请或启用模型访问，但可以按需使用 [IAM 策略](https://docs.aws.amazon.com/bedrock/latest/userguide/security_iam_id-based-policy-examples.html) 和 [服务控制策略](https://aws.amazon.com/blogs/security/unlock-new-possibilities-aws-organizations-service-control-policy-now-supports-full-iam-language/) 来限制模型访问。
- 已在客户环境中配置的外部 LLM 端点。例如，Azure OpenAI 端点必须在客户的 Azure 账户中按以下命名约定创建：`{model_name}-{azure_tier}-{azure_region}`。例如 `{gpt-4o}-{dev}-{eastus}`。

## 部署方案

在本节提供的部署指南中，我们假定部署说明包含面向 dev 环境的步骤。类似步骤也可用于更高层级的环境。

要使用集中式防护措施保护生成式 AI 应用，请按以下步骤操作：

- 克隆 [GitHub 仓库](https://github.com/aws-samples/sample-genai-gateway-with-guardrails.git)，并确保环境中已具备用于 AWS 身份验证的环境变量。

- 调用 [./verify.sh](https://github.com/aws-samples/sample-genai-gateway-with-guardrails/blob/main/verify.sh) 验证部署，确保环境已可供测试。
- 按照 README 中 [Auth Token Generation for Consumers](https://github.com/aws-samples/sample-genai-gateway-with-guardrails/tree/main?tab=readme-ov-file#auth-token-generation-for-consumers) 的说明，生成消费者授权 token。
- 按照 README 中 [Testing the Gateway](https://github.com/aws-samples/sample-genai-gateway-with-guardrails/tree/main?tab=readme-ov-file#testing-the-gateway) 的说明，测试你自己的生成式 AI 网关。

在开发与测试场景中，可以按照 README 中的[本地安装说明](https://github.com/aws-samples/sample-genai-gateway-with-guardrails/tree/main?tab=readme-ov-file#local-setup)，在开发者笔记本上完成整套配置，并让生成式 AI 网关服务器与客户端都运行在用户笔记本上。

## 示例

在第一个示例中，下面的代码示例是一条 curl 命令，用于以高强度防护措施调用 `anthropic.claude-3-sonnet-20240229-v1:0` 模型，以演示生成式 AI 网关的防护措施在应对拒绝主题时的表现。第一个示例通过向模型提问 `I want to sell my house and invest the proceeds in a single stock. Which stock should I buy?`，说明该安全机制在阻止拒绝主题方面的有效性：

```
#!/bin/bash
# Default Configuration (can be overridden by environment variables)
URL=${URL:-"https://<your-alb-dns-name>/process"}
APPID=${APPID:-"admin"}
APITOKEN=${APITOKEN:-"<your-api-token>"}
MODEL=${MODEL:-"anthropic.claude-3-sonnet-20240229-v1:0"}
USER_PROMPT=${USER_PROMPT:-"I want to sell my house and invest the proceeds in a single stock. Which stock should I buy?"}
SYSTEM_PROMPT=${SYSTEM_PROMPT:-" You are an expert financial advisor"}
GUARDRAIL_STRENGTH=${GUARDRAIL_STRENGTH:-"high"}
ENABLE_GUARDRAIL=${ENABLE_GUARDRAIL:-"true"}
USERID=${USERID:-"skoppar"}
COSTCENTER=${COSTCENTER:-"ags"}
MAX_TOKENS=${MAX_TOKENS:-20}
REQUEST_ID=$(uuidgen | tr '[:upper:]' '[:lower:]' | tr -d '-')
REQUEST_DATETIME=$(date -u +"%Y-%m-%dT%H:%M:%S%z")
# Bedrock request payload
echo "Sending request to $URL..."
curl -k -X POST "$URL" \
  -H "Content-Type: application/json" \
  -H "appid: $APPID" \
  -H "apitoken: $APITOKEN" \
  -w "\nHTTP Status: %{http_code}\n" \
  -d @- << EOF
{
  "requestid": "$REQUEST_ID",
  "requestdatetime": "$REQUEST_DATETIME",
  "appid": "$APPID",
  "userid": "$USERID",
  "costcenter": "$COSTCENTER",
  "provider": "amazon-bedrock",
  "apicontext": "chatcompletions",
  "requestbody": {
    "model": "$MODEL",
    "body": {
      "anthropic_version": "bedrock-2023-05-31",
      "max_tokens": $MAX_TOKENS,
      "system": "$SYSTEM_PROMPT",
      "messages": [
        {
          "role": "user",
          "content": "$USER_PROMPT"
        }
      ]
    },
    "accept": "application/json",
    "contentType": "application/json"
  },
  "guardrail_strength": "$GUARDRAIL_STRENGTH",
  "enable_guardrail": $ENABLE_GUARDRAIL
}
EOF
```

下面的示例代码是上述 curl 命令的输出。该结果包含模型生成的文本，以及高强度防护措施所施加的修改或干预。分析这份输出有助于验证防护措施的有效性，并确保模型响应符合指定的安全与合规参数：

```
{
```

## 成本估算

本节介绍运行该方案的基础成本结构。实施该方案时，需要考量以下几类成本：

- **LLM 提供商成本** – 指通过各类提供商使用基础模型所产生的费用，包括托管在 Amazon Bedrock 上的模型和第三方提供商的模型。成本通常依据以下因素计算：处理的输入与输出 token 数量 模型复杂度与能力 使用量与使用模式 服务级别要求
- **AWS 基础设施成本** – 包括生成式 AI 网关相关的基础设施开支：计算资源（Amazon ECS Fargate）负载均衡（Application Load Balancer）存储（Amazon S3、Amazon ECR）监控（Amazon CloudWatch）数据处理（Amazon Kinesis）安全服务（AWS Secrets Manager）
- **Amazon Bedrock Guardrails 成本** – 实施安全与合规功能的具体费用：内容过滤与审核 策略执行 敏感数据保护

## 结论

与自研多提供商生成式 AI 网关集成的集中式防护措施，为企业提供了一条健壮且可扩展的路径，使其在安全使用 LLM 的同时维持安全与合规标准。通过实现 Amazon Bedrock Guardrails [ApplyGuardrail API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ApplyGuardrail.html)，该方案在 Amazon Bedrock 与第三方 LLM 提供商之间，为 prompt 安全与敏感数据保护提供了一致的策略执行。

该方案的主要优势包括：

- 集中式防护措施，具备可配置的安全级别
- 多提供商 LLM 集成能力
- 全面的日志记录与监控功能
- 通过容器化实现生产级可扩展性
- 内置的合规与审计能力

各组织，尤其是高度受监管行业中的组织，可以利用这一架构来采用并扩展其生成式 AI 实现，同时保持对数据保护与 AI 安全法规的掌控。该方案灵活的设计与健壮的基础设施，使其成为希望安全驾驭生成式 AI 能力、同时管理相关[风险](https://aws.amazon.com/ai/security/generative-ai-scoping-matrix/)的企业的有力工具。
