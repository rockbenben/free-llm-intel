# 借助 vLLM 中的双向 KV 传输改善多轮代理工作负载的 TTFT

多轮代理工作负载建立在累积的上下文之上：代理先推理，再调用工具，然后把先前的结果纳入后续判断。每新增一轮，客户端都会重新发送对话历史，其中包括系统指令、此前的提示、工具结果和模型响应，于是不断变长的上下文被反复处理。在[预填充-解码（P-D）分离](https://docs.vllm.ai/en/latest/features/disagg_prefill/)中，每个请求被拆分到专门的节点上执行：预填充节点处理提示并构建键值（KV）缓存，随后解码节点取回这些 KV 块并生成响应。

然而，传统的分离式服务只沿一个方向传输 KV 缓存：从预填充节点到解码节点。这种单向流动给多轮工作负载带来两处低效。第一，生成响应之后，解码节点同时持有提示与新生成 token 的 KV 缓存条目。处理下一轮时，预填充节点无法取回这些条目，因此必须为上一轮响应的 token 重新计算 KV 投影。第二，解码节点维护会话状态，而预填充节点不维护，这提高了预填充节点上活跃会话缓存被逐出的概率。一旦发生完全缓存未命中，预填充节点就必须为整段对话历史重新计算 KV 投影，包括系统指令、此前的用户请求、工具结果和模型生成的响应。随着对话增长，这些冗余工作会消耗更多加速器容量，并推高首 token 时延（TTFT）。

在构建对话助手和代理式应用时，更长的交互历史会因反复的预填充计算而增加延迟、消耗加速器容量。本文展示**双向 KV 缓存传输**如何让预填充节点与解码节点跨轮次复用此前计算过的上下文，从而提升加速器利用率，并帮助应用在对话变长时仍保持灵敏的 TTFT。

在我们基于 Amazon Elastic Compute Cloud（Amazon EC2）P5en 实例的 1P1D 部署所进行的多轮基准测试中，双向 KV 传输将 Qwen3-32B 的 TTFT 最多降低 1.6 倍，将 zai-org/GLM-5-FP8 最多降低 3.3 倍（参见性能数据一节）。结果随工作负载和配置而异。这些实例通过 AWS Elastic Fabric Adapter（[AWS EFA](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html)）相连，这是 AWS 内部各服务器之间使用的低延迟远程直接内存访问（RDMA）网络。在[受支持的实例类型](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html#efa-instance-types)上，AWS EFA 支持 GPUDirect RDMA 和 Neuron Direct RDMA，可以在预填充节点与解码节点的 GPU 或 AWS Trainium 设备内存之间直接搬运 KV 块。

我们最初在与 EFA 相连的 [AWS Trainium](https://aws.amazon.com/ai/machine-learning/trainium/) 实例集群上构建并验证了该功能，随后将其作为与加速器无关的能力贡献给 vLLM。本文给出的结果来自带 EFA 的 Amazon EC2 P5en GPU 集群，说明这些收益同样可以带到 GPU 上。本文会讲解双向 KV 传输的架构、路由器元数据流、KV 块保留与重算控制、性能结果，以及如何复现该基准测试。

## 双向 KV 传输

双向 KV 传输是一种机制：解码节点在对话的后续轮次中，把此前计算好的 KV 返回给预填充节点。这样就避免了在预填充节点上重算共享上下文，而是否重算由一个可配置的 KV 重算阈值决定。它同时缓解了前文描述的两种计算冗余情形。要让它生效，KV 必须在其产生的那一轮之后继续存活，并沿相反方向传输，整个过程由具备 KV 缓存感知能力的路由器协调。

### 针对双向传输的 NIXL KV 连接器增强

我们扩展了 NVIDIA Inference Xfer Library（NIXL）的 [KV 连接器](https://docs.vllm.ai/en/latest/features/nixl_connector_usage/)，让预填充节点可以消费远端 KV 块，方式类似于解码节点此前消费预填充节点提供的 KV 块。这不是一处简单的改动，因为两类节点在架构上并不相同：预填充节点会为新提示 token 计算 KV 表示，可以提供完整的提示 KV 块；解码节点则不具备生成完整 KV 表示的能力（或者说效率），只能提供此前已缓存的 KV 块。因此，预填充节点与解码节点仍然各自承担自己的角色和逻辑，用来计算远端与本地 KV 块的元数据。不过，实际的 KV 传输机制（一次 NIXL READ）在 `P->D` 和 `D->P` 两个方向上都是同一套。

下图先用蓝色展示既有流程。路由器把请求发送给预填充节点，预填充节点计算提示 KV 并返回其块元数据，路由器再把请求和元数据转发给解码节点，执行标准的 P→D NIXL READ。红色编号路径示意双向 KV 传输新增的步骤：(1) 解码节点在生成结束后保留符合条件的 KV 块，(2) 在流式响应中返回这些块的元数据，(3) 路由器缓存该元数据，供下一次预填充请求使用。随后预填充节点 (4) 在应用本地缓存匹配之后检查远端可复用的 KV，(5) 当可复用 token 数达到阈值时排入一次异步接收，(6) 在计算剩余后缀之前执行 D→P NIXL READ。

### KV 缓存感知路由器

vLLM 在连接器侧提供了对双向 KV 传输的支持，而要在对话轮次之间协调 KV 复用，还需要一个具备 KV 缓存感知能力的路由器。vLLM 的 GitHub 仓库提供了一个[示例代理](https://github.com/vllm-project/vllm/blob/main/examples/disaggregated/disaggregated_serving/disagg_proxy_multiturn.py)，实现了本文所用的流程，可以按你的环境进行改造。

KV 缓存感知路由器是位于客户端、预填充节点和解码节点之间的一个轻量、有状态的控制面组件。它维护一份内存中的映射，从客户端提供的 `conversation_id` 指向解码节点的 `kv_transfer_params`。路由器只存储块位置元数据，不存储 KV 张量；这些元数据取自响应流，而不是另外向解码节点查询。

下图展示路由器如何在对话轮次之间管理 KV 元数据。在第一轮中，缓存查找未命中，请求走标准的 P→D 流程。随后路由器从响应流中保存解码节点的元数据。在之后的轮次中，路由器用 `conversation_id` 取出该元数据，使预填充节点能够复用解码节点的 KV。生成完成后，它再刷新元数据，供下一轮使用。

![两幅纵向排列的时序图，聚焦 KV 缓存感知路由器。第一轮中，路由器记录缓存未命中，把请求发送给 Prefill，收到 Prefill 元数据，把请求和 Prefill 元数据发送给 Decode，从流中保存 Decode 元数据，然后返回响应。在之后的某一轮中，路由器取出已保存的 Decode 元数据，发送给 Prefill，收到更新后的 Prefill 元数据，把请求和 Prefill 元数据发送给 Decode，刷新 Decode 元数据条目，然后返回响应。紫色箭头表示 Decode 到 Prefill、Prefill 到 Decode 的 KV 读取；KV 张量不经过路由器。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/15/ML-21811-2.png)

### 块保留 TTL

正常情况下，解码实例在生成一结束就释放该请求占用的块。在双向 KV 传输模式下，它会把块保留一段可配置的时长（`decoder_kv_blocks_ttl`，默认 480 秒），并公布这些块的位置与过期时间。这样一来，该对话的 KV（既包括提示前缀，也包括生成的响应）在下一轮仍然可用。如果下一轮在存活时间（TTL）到期之前到达，预填充节点就复用这些 KV；如果到达得更晚，则退回常规的预填充流程。由于该 TTL 是固定的、不会续期，应根据轮次之间的预期间隔来调优，以在 KV 复用与加速器内存占用之间取得平衡。一个自然的下一步改进，是把按心跳续期的租约延伸到解码侧：这样解码实例就能在对话空闲时立刻回收块，而不必等到固定计时器到期。

### KV 重算阈值

KV 复用并不总是比本地重算更快。对于很短的可复用前缀，互连与协调开销可能超过重算这些 token 所需的时间。`kv_recompute_threshold` 设置控制这一取舍，默认值为 64 个 token。当需要计算的 token 数低于阈值时，预填充节点自行重算；当达到或超过阈值时，预填充节点从解码节点拉取 KV。部署方可以根据模型计算耗时、KV 大小和互连性能来调整这个值。

## 性能数据

评估中，我们使用 Qwen3-32B 和 GLM-5-FP8 两个模型，在通过 EFA 相连的 Amazon EC2 P5en 实例上做 1P1D 部署。为了模拟预填充节点已逐出本地缓存、或路由器选中了另一个不含该对话 KV 块的预填充节点这类场景，我们在预填充节点上用 `--no-enable-prefix-caching` 关闭了前缀缓存。

在两个模型上，开启双向 KV 传输都能减少多轮对话中的预填充计算量，而且收益通常随提示变长而增大。关闭该功能时，预填充实例每一轮都要重算整个已增长的上下文，因此 TTFT 急剧上升：Qwen3-32B 从 2k 时的 158 ms 升到 24k 时的 778 ms，GLM-5-FP8 从 2k 时的 500 ms 升到 20k 时的 2,334 ms。开启后，解码实例保留的 KV 被复用而不是被重算，TTFT 曲线平缓得多：在同样的区间内，Qwen3-32B 只从 122 ms 升到 460 ms（最长提示下约降低至原来的 1/1.6），GLM-5-FP8 从 358 ms 升到 702 ms，在长提示下比重算路径低至其 1/3.3。预填充耗时的拆解可以解释其中的原因。

双向传输会额外增加少量 KV 传输时间（Qwen3-32B 约为 30 ms 至 130 ms；GLM-5-FP8 约为 29 ms 至 110 ms），但它省下的预填充计算远超这段传输时间。因此，开启传输后的预填充总耗时（Qwen3-32B：128 ms 至 414 ms；GLM-5-FP8：316 ms 至 541 ms）明显低于仅重算的路径（Qwen3-32B：153 ms 至 744 ms；GLM-5-FP8：500 ms 至 2,331 ms）。更大的 GLM-5-FP8 表现出更大的绝对差距与相对差距，因为其更高的单 token 重算耗时使 KV 复用随模型与上下文规模增长而更划算。

## 如何运行基准测试

要复现我们的 1P1D 基准配置（一个预填充节点加一个解码节点、使用通过 EFA 相连的 Amazon EC2 P5en 实例），请按[复现结果指南](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-10-12-bidirectional-kvxfer-multiturn-agentic-workload.md#appendix-reproducing-our-results)中的分步说明操作。该指南涵盖环境准备、启动 vLLM 的预填充与解码服务器、运行基准测试以及收集结果。该功能也可以在其他受支持的配置上运行，但性能结果会因硬件、模型、工作负载和网络配置而异。

## 结论

本文展示了双向 KV 缓存传输如何在代理的对话历史增长时降低 TTFT。在 P-D 分离式部署中，该功能让预填充节点能够跨轮次复用解码节点保留的 KV 块，从而减少重复计算。可配置的块保留时长与重算阈值决定了何时发生复用。在通过 EFA 相连的 Amazon EC2 P5en 实例构建的 1P1D 部署上，在测试的最长提示长度下，我们观测到 Qwen3-32B 的 TTFT 降低 1.6 倍、zai-org/GLM-5-FP8 降低 3.3 倍。结果取决于工作负载与部署配置。要在你的环境中实施，请使用 vLLM v0.21.0 或更高版本搭配 NixlConnector，在预填充与解码服务器上都启用 `bidirectional_kv_xfer`，使用 KV 缓存感知路由器，并参照 [GitHub 复现指南](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-10-12-bidirectional-kvxfer-multiturn-agentic-workload.md#appendix-reproducing-our-results)。
