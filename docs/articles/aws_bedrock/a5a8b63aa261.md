# Pluggable Agentic AI 框架：Amazon Bedrock AgentCore 上的七层可组合企业代理 AI 参考架构

“我们如何在生产中大规模运行我们的人工智能代理？”这是每个客户最终都会问的问题。它附带了几个问题。我们如何安全、自信地处理数千个并发用户请求？我们如何确保代理在实际流量下保持可靠，而不是默默地失败？我们如何知道代理是否仍符合测试期间通过的质量和安全标准？什么是代理安全最佳实践？这应该是确定性的还是非确定性的？还有更多。概念验证不能回答这些问题，因为它的构建是为了表明代理模型可以完成任务，而不是为了在生产流量、成本压力和安全审查中生存。

工作原型与大规模可靠、安全、节俭和负责任地运行的系统之间存在差距，这是大多数代理人工智能计划停滞不前的地方，而这很少是模型的错。每个构建代理的团队都倾向于从头开始重建相同的脚手架：自己的路由逻辑、自己的护栏、自己的可观察性，所有这些都是事后应用的，而不是从一开始就内置的。团队需要一个共享的、生产就绪的架构，每个代理都可以在该架构上进行构建。

这篇文章介绍了一个七层可组合参考架构，旨在将多智能体人工智能应用程序从原型推向生产规模。

## 可组合架构

可插拔代理人工智能框架是一个多代理应用程序的参考架构，分为**七层**，每层都有不同的职责和稳定的合同。每层中显示的服务和技术反映了参考实现，而不是强制选择。组织可以使用符合其现有基础设施和要求的替代方案。这些层共同提供了在生产规模上构建、保护和操作代理人工智能应用程序的蓝图。

![可插拔代理人工智能框架的七层，从数据和知识到代理操作](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/06/ML-22256-1.png)

图 1：可插拔代理 AI 框架的七层

**数据和知识**是Agentic AI的基础。代理的好坏取决于它可以访问的**数据**。无论代理是在检查医疗保健处方集、跟踪库存还是解释合规规则，都需要相关的最新信息才能正确回答。该层通过明确的合同和协议拥有检索、嵌入和对结构化和非结构化数据的访问：接受查询并返回最相关的信息，作为代理的上下文。 [Amazon Bedrock 知识库](https://aws.amazon.com/bedrock/knowledge-bases/)、[Amazon OpenSearch Serverless 矢量引擎](https://aws.amazon.com/opensearch-service/serverless-vector-database/)、[Amazon S3 矢量](https://aws.amazon.com/s3/features/vectors/) 和 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 是此基础的示例构建块。

**模型和推理**选择应由配置驱动，而不是硬连线到代理或应用程序逻辑中。对于简单任务使用更小、更快的模型，对于需要更细致推理的请求使用更大的模型。使用真实且具有代表性的业务数据对您正在构建的用例进行彻底的模型评估非常重要。模型路由层依靠一致的请求和响应契约，使 AI 代理与模型托管环境和特定于提供商的 API 分离。 [LiteLLM](https://www.litellm.ai/) 等代理提供跨提供商的通用接口，因此您可以根据评估切换模型，而无需重写应用程序逻辑。

**编排**决定了工作的分配方式，选择正确的方法至关重要。对于简单的任务，使用单个代理来处理端到端的工作。对于复杂的跨域工作流程，请使用主管来委派专家代理，每个代理都有特定的功能并绑定到一组特定的工具。避免构建一个包办所有事情的代理。随着工具、指令和上下文的积累，上下文窗口会增大，延迟会增加，并且准确性会受到影响。工具蔓延，可能会将代理推到其预期边界之外，导致意外操作和安全漏洞。职责划分可以使每个代理的上下文保持集中，并使延迟更加可预测。您还可以测试每个代理的行为、对其进行扩展并独立定义其安全模型。实施有限的自主权：专家应该严格在他们被授予的工具范围内执行，仅此而已。

除了分解为具体的专家并设定其边界外，还将专家智能体与主管智能体解耦。允许主管从集中式代理注册表中发现专家，并通过 MCP（模型上下文协议）和 A2A（代理到代理）等标准化协议调用它们。维护一个集中的代理注册表，对每个代理的工具、技能和所有者进行分类。这为您的组织提供了大规模治理所需的可见性，通过可重用性提高了 AI 代理实施的速度，并避免了重复开发的成本。考虑为专家使用 [Strands Agents](https://strandsagents.com/)，为协调器使用 [Amazon Bedrock AgentCore 线束](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness.html)，为协调器使用 [AWS Agent Registry](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry.html) 和 [Amazon Bedrock AgentCore网关](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 用于集中发现和路由。

**安全和护栏**应该是首要考虑的问题，从第一天起就融入到设计中。代理人工智能使组织面临传统安全框架无法解决的新型风险，从即时注入和工具滥用到内存和数据中毒。默认情况下，将所有外部内容视为不可信。通过 [Amazon Bedrock AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) 等服务对每个请求进行身份验证，无论它来自用户、其他代理还是自动化工作流程。然后使用细粒度的访问控制来确定每个工具调用在执行之前是否被允许。授予代理临时的、有范围的凭据，而不是持久的秘密。在数据保护方面，在代理和工具请求和响应中屏蔽敏感数据，例如 PHI（个人健康信息）和 PII（个人身份信息），以便敏感的客户信息不会出现在代理输出中或在内存中徘徊。为了问责，在防篡改的审计跟踪中捕获每一个重要决策，通过人工审批门来路由高影响力的操作，并部署断路器以在异常行为升级之前阻止异常行为。考虑使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 进行用户输入，使用 [Amazon Bedrock AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) 和 [Amazon Bedrock AgentCore 中的策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html) 进行身份验证和访问控制，以及 AWS 安全和治理控制，以实现深度防御安全。

**应用程序**是最终用户体验所在，无论是聊天界面、API 界面还是嵌入式小部件。故意保持这一层较薄。它唯一的职责应该是呈现对话并将请求传递给其下面的编排层。抵制在这里嵌入业务逻辑的冲动。分离越清晰，您就越容易迭代用户体验，而不会破坏后端的稳定性。决策模型可以作为一种快速、廉价的检查位于此边界：在一个调用中，它对请求是否在范围内、是否需要人工或是否紧急进行评分，返回概率而不是自由文本。您的代码通过简单的阈值对这些分数进行操作，直接回答偏离主题的请求并标记升级，因此完整的代理循环仅在增加价值时运行。在构建应用程序层时，请考虑另一个 AI 代理需要什么来与人类一起使用您的 AI 代理并与之交互。相应地构建您的外部接口。

**可观察性**应该从第一天开始就观察每一层，而不是在第一次事件之后。除了日志和指标之外，端到端代理跟踪对于衡量代理是否正确执行其任务也至关重要。除了跟踪之外，还收集每个请求的成本和令牌使用情况、第一个令牌的时间、调用是否安全，以及在上线之前显示延迟、错误率和支出的仪表板。主动监控比被动消防更便宜。考虑将 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 与 OpenTelemetry 以及 [Amazon CloudWatch Omni](https://aws.amazon.com/cloudwatch/omni/) 结合使用来进行跟踪和指标，以获得整个堆栈的全面可见性。

**代理运营**通过持续评估来关闭循环，因此从第一天就开始设置。对每个生产环节的基础性、准确性和安全性进行评分，并设置回归门以在质量下降到达客户之前捕获它们。如果没有这个，您只知道代理在启动时工作。有了它，您可以证明它在每个后续版本之后仍然有效。考虑使用 [Amazon Bedrock AgentCore 评估](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 进行评分，并使用 [Amazon Bedrock AgentCore 优化](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/optimization.html) 进行持续性能调整。

## 零售客户支持代理的参考实现

![零售客户支持代理的功能流程，从购物者请求通过主管路由到订单和退款专家代理](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/06/ML-22256-2.png)

图 2：零售客户支持参考实施的功能流程

为了使该架构栩栩如生，该框架包括一个可立即运行的参考实现，该参考实现基于涵盖订单状态和退款资格的零售客户支持场景。我们选择这个用例是因为它锻炼了堆栈的每一层，同时保持足够的直观性，让团队能够遵循和适应自己的需求。

主管代理收到客户的退款请求，并将其委托给订单代理和退款代理，每个代理都是拥有一组特定工具的专家。订单代理从 Amazon DynamoDB 查找配送和购买详细信息。退款代理从知识库中检索基于等级的政策规则，并使用交付日期、当前日期和客户的忠诚度等级来计算资格。这些调用中的每一个都经过 AgentCore 网关，该网关在使用 AgentCore 中的策略执行工具之前强制执行细粒度的访问控制，并且每个调用都会通过可观察层进行端到端跟踪，因此当计算出错时，跟踪会准确显示是哪一层和哪个决策点导致了错误。

任何构建类似的主管和专家模式的人都可以克隆参考实现并逐层交换到他们自己的领域逻辑中。

## 为什么可插拔性与层本身一样重要

七层架构的价值不仅在于它如何分离职责，还在于每一层的发展速度。 **可插拔性**使这成为可能。从身份检查和访问策略到遥测接口，层边界的稳定契约让您可以更改底层技术，而无需重新设计堆栈的其余部分。本质上，采用架构优先的方法来构建代理人工智能系统，而不是技术驱动的方法。

该框架通过跨层与第三方提供商集成来展示可插拔性，从而将其付诸实践：推理层的模型和托管提供商、编排层的搜索功能、应用程序层的决策 API、安全层的护栏、可观察层的代理跟踪和监控解决方案以及业务价值和成本跟踪。它在每一层都支持行业标准提供商，因此您可以构建满足您特定要求的解决方案。

对于企业来说，灵活性可以保护现有投资。团队可以保留他们已经信任的可观察性、安全性和推理工具，在需要时填补空白，并逐步采用新功能。该架构提供了一致的基础，而不要求每个技术决策都来自同一供应商。

## 结论

工作原型证明了代理的能力。一个设计良好的架构决定了您的企业是否可以依赖它。转向人工智能运营意味着从第一天起就将安全性、治理、可见性、成本控制、可靠性和适应性设计到设计中，而不是在系统构建后添加它们。

可插拔代理人工智能框架将这些问题带入一个具有明确原则的架构中：构建稳定的基础，而不锁定每个技术选择。模型将会改变。工具将会不断发展。业务需求将会发生变化。您的架构应该使这些更改易于管理，而不是将每个更改都变成重建。

将这一原则付诸实践。从 [Workshop Studio 体验](https://catalog.us-east-1.prod.workshops.aws/workshops/a782d075-7943-4251-9d8f-58c428b119a9) 开始，探索[公共示例存储库](https://github.com/aws-samples/sample-pluggable-agentic-ai-framework)，并使用动手实现作为您自己的架构的起点。它不能替代生产安全强化、测试和审查。

构建您今天所需的功能以及您明天所需的**灵活性**。
