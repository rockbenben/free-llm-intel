# 使用 Amazon CloudWatch 指标监控 Amazon Bedrock 批量推理

随着组织扩大生成式 AI 的使用，许多工作负载需要的是高性价比的批量处理，而不是实时响应。[Amazon Bedrock](https://aws.amazon.com/bedrock/) 批量推理（batch inference）正是为此而设，它能以可预期的性能批量处理大型数据集——成本比按需推理低 50%。因此它非常适合历史数据分析、大规模文本摘要和后台处理类工作负载。

本文探讨如何使用 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch) 的指标、告警和仪表盘来监控与管理 Amazon Bedrock 批量推理作业，从而优化性能、成本与运营效率。

## Amazon Bedrock 批量推理的新特性

Amazon Bedrock 的批量推理在持续演进，最近的更新在性能、灵活性和成本透明度方面带来了显著增强：

- **扩展的模型支持** – 批量推理现在支持更多模型家族，包括 Anthropic 的 Claude Sonnet 4 和 OpenAI OSS 模型。最新列表请参阅[批量推理支持的 Region 和模型](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference-supported.html)。
- **性能增强** – 在较新的 Anthropic Claude 和 OpenAI GPT OSS 模型上，批量推理的优化如今带来比以往模型更高的批量吞吐，帮助你更快处理大型工作负载。
- **作业监控能力** – 现在可以直接在 CloudWatch 中跟踪已提交批量作业的进度，无需再费力自建监控方案。该能力提供 AWS 账户级别的作业进度可见性，让管理大规模工作负载变得简单直接。

## 批量推理的用例

AWS 建议在以下用例中使用批量推理：

- 作业**不**对时间敏感，可容忍数分钟到数小时的延迟
- **处理是周期性的**，例如每天或每周对大型数据集（新闻、报告、转录文本）做摘要
- 需要分析**批量或历史数据**，例如呼叫中心转录、邮件或聊天日志的归档
- **知识库需要充实**，包括**大规模**生成 embedding、摘要、标签或翻译
- 内容需要**大规模转换**，例如分类、情感分析，或把非结构化文本转换为结构化输出
- 需要做**实验或评估**，例如测试不同的 prompt 变体或生成合成数据集
- 必须对**历史内容**执行合规与风险检查，用于敏感数据检测或治理

## 启动 Amazon Bedrock 批量推理作业

你可以使用 [AWS Management Console](https://aws.amazon.com/console)、AWS SDK 或 [AWS Command Line Interface](https://aws.amazon.com/cli)（AWS CLI）在 Amazon Bedrock 中启动批量推理作业。详细说明请参阅[创建批量推理作业](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference-create.html)。

要使用控制台，请完成以下步骤：

- 在 Amazon Bedrock 控制台的导航窗格中，选择 **Infer** 下的 **Batch inference**。
- 选择 **Create batch inference job**。
- 在 **Job name** 处输入作业名称。
- 在 **Model** 处选择要使用的模型。
- 在 **Input data** 处输入 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）输入存储桶的位置（JSONL 格式）。
- 在 **Output data** 处输入输出存储桶的 S3 位置。
- 在 **Service access** 处选择你为 Amazon Bedrock 授权的方式。
- 选择 **Create batch inference job**。

## 用 CloudWatch 指标监控批量推理

Amazon Bedrock 现在会自动在 AWS/Bedrock/Batch 命名空间下发布批量推理作业的指标。你可以用以下 CloudWatch 指标在 AWS 账户级别跟踪批量工作负载的进度。对于当前支持的 Amazon Bedrock 模型，这些指标包括待处理的记录数、每分钟处理的输入与输出 token 数；对于 Anthropic Claude 模型，还包括待处理的 token 数。

以下指标可按 `modelId` 监控：

- **NumberOfTokensPendingProcessing **– 显示还有多少 token 在等待处理，帮助你判断积压规模
- **NumberOfRecordsPendingProcessing **– 跟踪队列中还剩多少推理请求，提供作业进度的可见性
- **NumberOfInputTokensProcessedPerMinute **– 衡量输入 token 的消耗速度，反映整体处理吞吐
- **NumberOfOutputTokensProcessedPerMinute **– 衡量生成速度

要使用 CloudWatch 控制台查看这些指标，请完成以下步骤：

- 在 CloudWatch 控制台的导航窗格中选择 **Metrics**。
- 按 AWS/Bedrock/Batch 筛选指标。
- 选择你的 `modelId`，查看该批量作业的详细指标。

![CloudWatch 指标仪表盘](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/06/image2.png)

想进一步了解如何使用 CloudWatch 监控指标，请参阅[使用 CloudWatch Metrics Insights 查询 CloudWatch 指标](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/query_with_cloudwatch-metrics-insights.html)。

## 监控与管理批量推理的最佳实践

监控与管理批量推理作业时，可考虑以下最佳实践：

- **成本监控与优化** – 结合批量作业计划，监控 token 吞吐指标（`NumberOfInputTokensProcessedPerMinute` 和 `NumberOfOutputTokensProcessedPerMinute`），再借助 Amazon Bedrock 定价页面的信息就能估算推理成本。这有助于你了解 token 处理的速度、这对成本意味着什么，以及如何调整作业规模或调度，在满足吞吐需求的同时控制预算。
- **SLA 与性能跟踪** – `NumberOfTokensPendingProcessing` 指标适合用来了解批量积压规模和跟踪整体作业进度，但不应依赖它来预测作业完成时间，因为完成时间会随 Amazon Bedrock 的整体推理流量而变化。要了解批处理速度，我们建议改为监控吞吐指标（`NumberOfInputTokensProcessedPerMinute` 和 `NumberOfOutputTokensProcessedPerMinute`）。如果这些吞吐率明显低于你预期的基线，可以配置自动告警来触发补救动作——例如把部分作业转为按需处理，以符合你期望的时间线。
- **作业完成跟踪** – 当指标 `NumberOfRecordsPendingProcessing` 降为零时，说明所有正在运行的批量推理作业都已完成。你可以用这个信号触发干系人通知或启动下游工作流。

## CloudWatch 指标示例

本节演示如何使用 CloudWatch 指标设置主动告警与自动化。

例如，你可以创建一个 CloudWatch 告警：当 `NumberOfInputTokensProcessedPerMinute` 的 6 小时平均值超过 100 万时，发送一条 [Amazon Simple Notification Service](https://aws.amazon.com/sns)（Amazon SNS）通知。该告警可以促使运维团队复核，或触发下游数据流水线。
