# 基于推送的 KV 传输，为 vLLM 中的分离式推理改善 TTFT 与 TPOT

[vLLM](https://github.com/vllm-project/vllm) 是一个面向大语言模型（LLM）的开源推理与服务平台。LLM 推理包含两个截然不同的阶段：预填充（prefill）负责处理输入提示并构建键值（KV）缓存，解码（decode）则利用该缓存逐个 token 生成输出。这两个阶段在计算、内存和扩展特性上各不相同。[预填充-解码（P-D）分离](https://docs.vllm.ai/en/latest/features/disagg_prefill/)让它们运行在各自独立的引擎实例上，使每个阶段都能独立扩展和优化。这可以在负载下改善资源利用率、吞吐和延迟。但它同时也要求在开始生成 token 之前，把 KV 缓存从预填充实例传输到解码实例，因此高效的 KV 传输对首 token 时延（TTFT）至关重要。

vLLM 执行这类传输的途径之一是 NVIDIA Inference Xfer Library（NIXL）[连接器](https://docs.vllm.ai/en/latest/features/nixl_connector_usage/)，它通过支持远程直接内存访问（RDMA）的互连搬运 KV 块，例如 AWS Elastic Fabric Adapter（[AWS EFA](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html)，即 AWS 内部各服务器之间使用的低延迟 RDMA 网络）。在[受支持的实例类型](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html#efa-instance-types)上，AWS EFA 支持 GPUDirect RDMA 和 Neuron Direct RDMA。因此 NIXL 可以直接在 GPU 或 [AWS Trainium](https://aws.amazon.com/ai/machine-learning/trainium/) 设备内存之间传输 KV 块，无需经主机内存中转。NIXL 连接器的默认模式是**基于拉取（pull-based）**：预填充实例算完提示 KV 缓存后，路由器把源端元数据（包括预填充块 ID）转发给解码实例。解码实例接着分配目标块、准备 NIXL 传输，并发起 NIXL READ 从预填充实例拉取 KV 块。由于这些协调与准备工作是在预填充之后、解码开始之前串行发生的，它们会拉长 TTFT 的关键路径，如下图所示。

![拉取模式时间线：路由器转发、解码侧分配与 NIXL READ 在通往首 token 的路径上串行执行。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/15/ML-21812-1.png)

图 1：拉取模式下的 KV 传输时间线，路由器转发、解码侧分配与 NIXL READ 在通往首 token 的路径上串行执行

本文介绍一种**基于推送（push-based）**的 NIXL 连接器，它把预填充之后的传输协调与准备工作移出关键路径。如果你正在用 vLLM 运行分离式预填充/解码推理，推送模式可以通过降低 TTFT 和 TPOT 来改善应用响应性，在高请求速率下尤其明显。

在我们使用通过 EFA 相连的 Amazon Elastic Compute Cloud（Amazon EC2）P5en 实例所做 1P1D 部署的基准测试中，针对 Qwen3-32B 模型，推送模式相比拉取模式最多带来 3 倍的 TTFT 改善，以及最高 30% 的每输出 token 耗时（TPOT）改善（参见性能数据一节）。结果取决于工作负载和配置。

我们在通过 EFA 相连的 AWS Trainium 实例集群上构建并验证了该功能，随后把它作为与加速器无关的特性贡献给 vLLM。这里的结果来自带 EFA 的 Amazon EC2 P5en（GPU）集群，说明这些收益同样可以带到 GPU 上。本文会讲解推送式架构、传输流程、线程模型、性能结果，以及如何复现该基准测试。

## 基于推送的 KV 传输

本节说明推送式设计：它的架构、传输协议，以及让 KV 传输远离关键路径的线程模型。

### 架构概览

推送式传输之所以能改善 TTFT 和解码吞吐，原因有两个：

- **它通过重叠生产者与消费者的工作，消除了拉取模式的串行化。** 解码实例在生产者仍在计算 KV 时就提前注册自己的目标块。这样一来，传输在生产者块就绪的瞬间就开始，而不必等消费者侧完成一轮 ID 发现往返，从而把这轮往返从通往首 token 的路径上移除。
- **它把传输准备工作从解码实例上移走。** 这些准备工作在预填充侧、在后台线程上完成：它准备好 NIXL 描述符并提交传输，因此解码实例不必在对延迟至关重要的 token 生成阶段消耗这些周期。

最终效果是：解码实例上的 TTFT 更低，输出 token 吞吐更高。

推送连接器协调三个角色：解码实例提前注册目标块，预填充实例为每个请求做匹配并发出传输，一个专门的后台线程把 KV 写入带离引擎的前向计算循环。下图展示这些部件如何配合。

### 实现细节

该协议包含三个逻辑步骤。

**1. 注册（解码侧）。** 当解码实例为一个需要远端预填充的请求分配本地块时，它会准备一份注册信息，描述预填充实例应当把 KV 写到哪里：自身的标识，以及它刚预留的块位置。在同一个引擎步内，worker 以 NIXL 通知的形式把该注册信息发送给预填充实例。由于注册发生在分配块的时候，连接器在预填充实例完成预填充之前就已经知道目标块了。

**2. 会合（预填充侧）。** 来自解码器的注册信息与生产者侧预填充的完成，到达顺序不定，连接器对两种情况都能处理。如果注册先到，生产者会先持有它，直到自己的预填充结束；如果预填充先完成，生产者会先持有该请求的块，直到注册信息到达。无论哪个事件后到，都由它触发传输。连接器按 ID 配对请求，这种匹配能正确处理被重新下发的请求，把被抢占或重试过的请求正确对应起来。

**3. 传输（预填充侧）。** 请求配对成功后，生产者与解码实例建立连接（若尚无连接），并发起一次 NIXL WRITE，把 KV 块直接写入解码器已注册的内存，并逐一寻址每个目标张量并行 rank。生产者与消费者可能使用不同的内部块布局：双方在传输时各自把块位置映射到自己的物理布局，因此两侧的块大小可以不同。每次 WRITE 都会带一个完成通知，数据到达后由 NIXL 投递给解码实例。解码器统计这些通知，每有一个向它写入的生产者 rank 就计一个；只有在全部预期通知都到达之后，它才认为 KV 已接收完毕，此时请求才进入解码阶段。

### 线程模型

推送连接器在每个预填充 worker 上使用一个专门的后台传输线程，从而把模型执行与 KV 传输准备分离开。请求开始时，解码主循环在分配自己的目标 KV 块并向预填充实例注册这些块，与此同时预填充主循环在计算提示 KV 缓存。等目标注册与提示 KV 都就绪后，预填充主循环把 KV 块交给后台线程，随即快速回到模型执行。

后台线程建立或复用 NIXL 连接，把请求的 KV 块 ID 映射为内存描述符，把连续块合并成更大的传输区域，然后向解码实例提交 NIXL WRITE。NIXL 完成传输后，会向解码实例发送完成通知，解码实例随后开始生成 token。把描述符准备与传输提交留在对延迟至关重要的主循环之外，可以避免这类逐请求的工作拖慢模型执行。下图展示单个请求下主循环与后台线程之间的这几次交接。

![线程模型：解码与预填充主循环把 KV 块交给后台线程，由后台线程在前向计算循环之外完成 NIXL 传输](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/15/ML-21812-3.png)

### 拉取与推送的时序对比

下图概括了前面几节所述的拉取与推送传输流程，并突出它们对 TTFT 的影响。两种模式使用相同的 NIXL 与 EFA/RDMA 数据路径，但拉取模式在预填充之后才做元数据转发和解码侧准备，而推送模式把解码侧准备与预填充重叠起来。因此，推送模式把这些操作从预填充之后的关键路径上移除，使解码可以更早开始。

![并排时间线对比拉取与推送 KV 传输，展示推送模式如何让解码侧准备与预填充重叠，从而缩短通往首 token 的路径](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/15/ML-21812-4.png)

图 4：拉取与推送传输流程对比，突出推送模式如何让解码侧准备与预填充重叠

两种模式在路由上也有取舍。拉取模式允许路由器在预填充完成后再选择解码实例，这为感知负载的路由和服务质量管理提供了更大灵活性。推送模式则更早选定解码实例，以便目标准备能与预填充重叠。作为回报，在相当负载下，预填充实例可以更早释放其 KV 块，因为提示 KV 与目标注册一旦都就绪，传输就开始了。

## 性能数据

评估中，我们使用 Qwen3-32B 模型，在通过 EFA 相连的 Amazon EC2 P5en 实例上做 1P1D 部署。为了单独考察 P→D 传输性能，我们在基准测试中用 `--no-enable-prefix-caching` 关闭了前缀缓存。这样配置后，解码节点对每个请求都要从预填充节点取回完整 KV 缓存；否则存在重叠的提示可能复用解码节点的本地缓存、绕过传输，从而得出有误导性的对比结果。

下图对比推送与拉取 KV 传输的 TTFT。我们扫描了 1k–16k 的输入长度，以及每秒 1–8 次查询（QPS）的请求速率。在低负载、短提示下，两种模式的表现几乎一致。随着 QPS 和输入长度增长，拉取模式急剧恶化，在 8 QPS、16k 时达到约 1,744 ms；推送模式则保持在约 540 ms，低得多，约为前者的 1/3。差距之所以拉开，是因为拉取模式在解码 worker 上、在其引擎循环内同步地内联提交 NIXL 描述符，这部分工作会阻塞 token 生成；推送模式则把它移到后台线程，离开了关键路径。

![Qwen3-32B 在带 EFA 的 Amazon EC2 P5en 实例上推送与拉取 KV 传输的四格 TTFT 对比。测试配置：1P1D 拓扑，128 个输出 token，解码节点关闭前缀缓存。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/15/ML-21812-5.png)

图 5：不同输入长度与请求速率下推送与拉取 KV 传输的 TTFT（1P1D 拓扑，128 个输出 token，解码节点关闭前缀缓存）

下图展示相同条件下的 TPOT，其规律与 TTFT 一致。轻负载时，推送与拉取相差不大，约为 5.6–5.8 ms。随着负载和输入长度上升，拉取模式在 4–8 QPS、16k 时升到约 10.4 ms，而推送模式维持在 7 ms 附近。原因在于推送模式把描述符准备与传输提交从解码 worker 上卸下，token 生成不再被挤压，因此即使在高并发和长上下文下，每 token 延迟也保持平稳。

![Qwen3-32B 在带 EFA 的 Amazon EC2 P5en 实例上推送与拉取 KV 传输的四格 TPOT 对比。测试配置：1P1D 拓扑，128 个输出 token，解码节点关闭前缀缓存。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/15/ML-21812-6.png)

## 如何运行基准测试

要复现我们的 1P1D 基准配置（一个预填充节点加一个解码节点、使用通过 EFA 相连的 Amazon EC2 P5en 实例），请参阅[复现我们的结果](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-10-14-nixl-push-connector.md#appendix-reproducing-our-results)指南中的详细说明。该指南涵盖环境准备、启动 vLLM 的预填充与解码服务器、运行基准测试以及收集结果。该功能也可以在其他受支持的配置上运行，但性能结果会因硬件、模型、工作负载和网络配置而异。

## 结论

本文展示了基于推送的 KV 连接器如何把预填充计算与解码侧的块分配、块注册重叠起来，从而把预填充之后的路由器往返和解码侧传输准备从关键路径上移除。这降低了 TTFT 和 TPOT，在高请求速率下尤其明显。在我们针对 Qwen3-32B、使用通过 EFA 相连的 Amazon EC2 P5en 实例所做 1P1D 部署的基准测试中，推送模式相比拉取模式最多带来 3 倍的 TTFT 改善和 30% 的 TPOT 改善。结果随工作负载与配置而异。要使用推送模式，请把预填充与解码服务器都配置为使用 `NixlPushConnector`，而不是 `NixlConnector`。

如果早选解码节点可以接受、并且优先考虑更低的 TTFT，就选择推送式连接器。对于需要[双向 KV 传输](https://vllm.ai/blog/2026-10-12-bidirectional-kvxfer-multiturn-agentic-workload)、或者为了感知负载的路由而把解码实例选择推迟到预填充之后的工作负载，拉取式连接器仍然是更合适的选择。vLLM 同时支持推送式与拉取式 KV 连接器，你可以挑选最适合自己部署的方式。

作为未来的改进，我们正在探索把后台 NIXL 线程模型引入拉取模式连接器，把 NIXL 的准备移出关键路径，让拉取模式的工作负载也能获得同样的优化。我们已经提交了一个[拉取请求](https://github.com/vllm-project/vllm/pull/45211)来探索这一点。
