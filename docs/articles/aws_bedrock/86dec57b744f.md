# 使用 Amazon Bedrock AgentCore 构建 AI 驱动的 AWS 支持助手

管理 AWS 基础设施往往意味着要在多个控制台之间切换、搜索文档并手工创建支持案例。每遇到一次故障，工程师都要打开 AWS Management Console、查看 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)、搜索 AWS 文档、浏览社区帖子，然后提交支持案例。在真正开始解决问题之前，这种上下文切换每次调查累计要花掉 30–45 分钟。

在本文中，你将使用 [Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 构建一个 AWS Support Companion。该 agent 以 [Strands Agents](https://strandsagents.com/) 作为编排框架，并通过 [Model Context Protocol（MCP）](https://modelcontextprotocol.io/) 连接 AWS 服务。读完本文，你会得到一个可用的 agent，它能够分析 CloudWatch 日志、搜索 AWS 文档、查询来自 [AWS re:Post](https://repost.aws/) 的社区知识并创建支持案例，而这一切都在同一个对话式界面中完成。该方案用单个脚本、借助 [AWS CloudFormation](https://aws.amazon.com/cloudformation/) 完成部署，并包含一个基于 [AWS Amplify](https://aws.amazon.com/amplify/) 构建的 Web 前端，用于与 agent 交互。

![AWS Support Companion 解决方案的架构图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/24/ML-19981-1.png)

## 故障调查的瓶颈

AWS 支持与运维团队在每次故障中都会重复同一套动作：

- 打开 AWS Management Console，并导航到受影响的服务。
- 查看 CloudWatch 日志与指标，寻找错误模式。
- 搜索 AWS 文档，查找相关的故障排查指导。
- 浏览 AWS re:Post 上关于类似问题的社区帖子。
- 汇总调查发现，并按合适的严重级别创建支持案例。
- 把证据与上下文附加到案例中。

每个步骤都需要不同的工具与界面。人工调查限制了团队的响应速度，而且在某一个工具中收集到的上下文无法带到下一个工具里。

## 解决方案概览

本方案把这些步骤整合为一个部署在 Amazon Bedrock AgentCore 上的对话式 agent。AgentCore 负责处理运行生产级 AI agent 的运维复杂性（会话隔离、自动扩缩容、安全与可观测性），因此你可以专注于 agent 做什么，而不是它如何运行。

该 agent 连接以下组件：

**Agent runtime ——** 一个使用 Strands Agents 的 Python 应用，打包为 Docker 容器并部署到 AgentCore Runtime。该 agent 会根据你的输入，编排对基础模型（FM，即通过 Amazon Bedrock 调用的 Amazon Nova Pro）与各类工具的调用。你可以换成其他受支持的模型，而无需改动 agent 代码。

**MCP servers ——** 三个 MCP server 让该 agent 能够访问 AWS 文档（`aws-documentation-mcp-server`）、[AWS Support](https://aws.amazon.com/premiumsupport/) API（`aws-support-mcp-server`）以及 AWS 服务 API（`aws-api-mcp-server`）。MCP 为 AI agent 从外部工具接收上下文提供了标准协议。

**AgentCore Gateway ——** 把工具集中为可复用、安全的端点。该 gateway 通过一个由 [AWS Lambda](https://aws.amazon.com/lambda/) 支撑的 target，并借助 [Amazon Cognito](https://aws.amazon.com/cognito/) JSON Web Token（JWT）身份验证，提供对 AWS re:Post 社区知识的访问。

**AgentCore Memory ——** 维护短期对话上下文，使 agent 能够在同一个会话中基于之前的排查步骤继续推进。

**API 与前端层 ——** 带 Cognito 授权与请求校验的 [Amazon API Gateway](https://aws.amazon.com/api-gateway/)、[AWS WAF](https://aws.amazon.com/waf/) 限流，共同位于一个调用 AgentCore Runtime 的 Lambda 函数之前。一个由 AWS Amplify 托管的 React 应用提供用户界面，并通过 Cognito 身份验证完成注册与登录。

**Guardrails ——** 一份 [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 配置会过滤有害内容、帮助阻断 prompt injection 攻击、对 AWS 密钥、信用卡与社会安全号码等个人可识别信息（PII）进行脱敏，并把 agent 限制在 AWS 支持类话题内。

**基础设施 ——** 单个 CloudFormation 模板即部署全部资源，包括 AWS 身份与访问管理（IAM）角色、Cognito 用户池、[AWS Key Management Service（AWS KMS）](https://aws.amazon.com/kms/) 密钥、[AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 中保存的机密，以及 [AWS Systems Manager Parameter Store](https://aws.amazon.com/systems-manager/) 参数。

![展示 agent runtime、MCP servers、AgentCore Gateway、API Gateway 与 Amplify 前端的组件图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/24/ML-19981-2.png)

## 前提条件

开始之前，请确认你已具备以下条件：

- Python 3.11 或更高版本。
- 支持 ARM64 buildx 的 Docker。
- 一个具备 Amazon Bedrock、IAM 与 CloudFormation 权限的 AWS 账户。
- 在你部署所用的 AWS Region 中已获得 Amazon Nova Pro 的 Amazon Bedrock 模型访问权限（也可以改用其他受支持的模型）。
- 已安装并配置好合适凭证的 [AWS Command Line Interface（AWS CLI）](https://aws.amazon.com/cli/)。
- 已安装 [uv](https://docs.astral.sh/uv/) 包管理器。
- AWS Business、Enterprise On-Ramp 或 Enterprise Support 支持计划（Support MCP server 要求具备）。

**重要：** 本方案会创建计费的 AWS 资源。请按本文末尾的「清理」一节操作，以避免持续产生费用。

## 部署解决方案

部署过程使用单个脚本，它会预置全部基础设施、构建容器，并输出你需要的配置值。

### 第 1 步：克隆仓库

先克隆示例代码，然后进入项目目录：

```
git clone https://github.com/aws-samples/sample-support-agent-with-agentcore
cd sample-support-agent-with-agentcore
```

### 第 2 步：配置 AWS 凭证

确认你的 AWS CLI 已配置具备所需权限的凭证：

```
aws sts get-caller-identity
```

### 第 3 步：运行部署

让部署脚本可执行，并带上容器构建标志运行它：

```
chmod +x deploy.sh
./deploy.sh --build-container
```

该脚本负责：用 uv 搭建 Python 环境、部署前安全校验（AWS CloudTrail 检查、模板校验、凭证类型检查）、创建 Amazon Elastic Container Registry（Amazon ECR）仓库、构建 Docker 镜像，以及部署 CloudFormation stack。它会核实目标 Region 中的 CloudTrail 处于启用状态、校验 CloudFormation 模板，并确认你使用的是临时角色凭证而不是长期的 IAM 用户密钥。

当 stack 完成后，脚本会输出前端所需的配置值：Cognito User Pool ID、Cognito Client ID、Cognito Identity Pool ID，以及 Agent Runtime 的 Amazon Resource Name（ARN）。

![终端输出显示 CloudFormation 部署成功并给出配置值](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/24/ML-19981-3.png)

### 第 4 步：部署 Amplify 前端

在部署所用的 Region 中进入 AWS Amplify 控制台，然后按以下步骤操作：

- 选择 **support-agent-frontend** 应用。
- 在主分支中选择 **Deploy updates**。
- 选择 **Drag and drop** 作为方式，然后上传 `frontend/` 目录下的 `support-agent-amplify-frontend.zip` 文件。
- 选择 **Save and deploy**。

### 第 5 步：配置并访问应用

用 CloudFormation 的输出值（User Pool ID、Client ID、Identity Pool ID 与 Runtime ARN）更新前端配置。通过 Sign Up 选项创建用户账户，用一次性验证码验证邮箱，然后登录。

![登录后显示聊天面板的 Support Companion Web 界面](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/24/ML-19981-4.png)

### 第 6 步：与 agent 交互

聊天界面会连接到运行在 AgentCore Runtime 中的 agent。该 agent 可以访问用于文档与支持的 AWS MCP server，并通过 AgentCore Gateway 访问 AWS re:Post。可以试试这类提问：

- “保护 Amazon Simple Storage Service（Amazon S3）存储桶的最佳实践有哪些？”
- “帮我排查 us-east-1 中一个 Lambda 函数超时的问题”
- “为我的 RDS 实例间歇性连接问题创建一个支持案例”

![agent 在聊天界面中回答一个故障排查问题](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/24/ML-19981-5.gif)

## 理解 agent 代码

该 agent 定义在 `agent.py` 中，并使用 `BedrockAgentCoreApp` 框架。本节重点介绍三种实现模式，它们分别应对生产环境 agent 常见的挑战。

**并行初始化 MCP。** 依次加载三个 MCP server 会带来明显的启动延迟。该 agent 使用 `asyncio.gather` 并行初始化全部三个 client，从而缩短冷启动时间。每个 client 都通过 `uvx` 连接自己的 server，并把可用的工具注册到 Strands Agent：

```
# Initialize all clients in parallel
results = await asyncio.gather(
    init_aws_docs(),    # AWS Documentation MCP
    init_aws_support(), # AWS Support MCP
    init_aws_api(),     # AWS API MCP
    return_exceptions=True
)
```

**带优雅超时的记忆。** 该 agent 使用 AgentCore Memory 维护对话上下文。每次请求时，它会以两秒超时获取最近三轮对话。如果上下文获取超时，agent 会不带上下文继续处理，而不是阻塞响应。生成响应后，它会异步保存这次对话。Memory 以 session ID 为作用域，因此每个用户对话都维护各自的上下文。

**Gateway token 刷新。** AgentCore Gateway client 使用存放在 Secrets Manager 中的 Cognito JWT token 进行身份验证。该 agent 在每次 gateway 调用前校验 token 是否过期，并在 token 距过期不足五分钟时自动刷新。没有这一机制，在 token 一小时有效期过后，gateway 调用会间歇性失败。

## 安全考量

本方案部署时默认配置了多层安全措施。身份验证使用 Amazon Cognito，并采用与 NIST SP 800-63B 对齐的密码策略。带限流与托管规则集的 AWS WAF 为 API Gateway 提供防护。每个组件都有各自的最小权限 IAM 角色，agent invoker Lambda 会在把响应返回给用户之前，先从响应中脱敏凭证模式。

Amazon Bedrock Guardrails 会过滤有害内容、阻断 prompt injection（级别设为 HIGH）、对 PII（AWS 密钥、信用卡、SSN）进行脱敏，并把 agent 限制在 AWS 支持类话题内。API Gateway 的访问日志会写入 Amazon CloudWatch 并保留 90 天，AWS CloudTrail 记录 API 调用。完整的安全实现细节——包括加密配置、IAM 角色范围划定与 guardrail 策略——见仓库中的 [SECURITY.md](https://github.com/aws-samples/sample-support-agent-with-agentcore/blob/main/SECURITY.md)。

## 清理

为避免持续产生费用，请按以下顺序删除资源。

**警告：**这些步骤不可逆。请在继续之前备份你需要保留的任何数据。

- 从 AWS Amplify 控制台删除该 Amplify 应用。
- 删除 CloudFormation stack：  `aws cloudformation delete-stack --stack-name bedrock-agentcore-stack --region us-west-2`
- 删除 ECR 仓库（CloudFormation 不会删除非空仓库）：  `aws ecr delete-repository --repository-name support-agent --region us-west-2 --force`
- 删除用于 CloudFormation 模板的 S3 存储桶：  `aws s3 rb s3://cfn-templates-ACCOUNTID-us-west-2 --force`

## 结论

在本文中，你使用 Amazon Bedrock AgentCore 构建了一个 AI 驱动的 AWS Support Companion。该 agent 把基础模型的推理能力与通过 MCP 和 AgentCore Gateway 实时访问 AWS 文档、支持 API 及社区知识的能力结合起来。本方案用单个脚本完成部署，并包含身份验证、限流、加密、guardrail 与审计日志。

该 agent 把多种调查工具整合进一个对话式界面，因此工程师可以从定位问题一路走到创建支持案例，而无需在多个控制台之间切换。

示例仓库还就网络隔离、多账户部署、基于 AgentCore tracing 的可观测性、人工升级阈值，以及面向生产就绪的 secret 轮换提供了额外指导。要开始使用，请访问 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)，并[克隆示例仓库](https://github.com/aws-samples/sample-support-agent-with-agentcore)。

如果你需要完全托管的故障调查服务，请参阅 [AWS DevOps Agent](https://aws.amazon.com/devops-agent/)。本文展示的是：当你需要对工具、模型、guardrail 与 workflow 拥有完全控制时，如何在 AgentCore Runtime 上构建自定义 agent。
