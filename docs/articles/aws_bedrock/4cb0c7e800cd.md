# Circle K 如何使用 Amazon Bedrock 将 DevOps 事件分类速度加快到 15 分钟以内

*本文是与 Circle K 的云 DevOps 工程师 Marek Klatowicz 共同撰写的。*

许多 DevOps 团队都知道事件分类模式：警报发出后，在任何人能够解决问题之前，工程师会花 45-60 分钟弄清楚发生了什么。他们通过一些工具提取日志、检查服务运行状况并关联症状。所有这些都发生在修复开始之前。

在 Circle K，这一挑战随着业务的发展而不断扩大。该公司在 27 个国家经营着 17,200 多家便利和燃料零售店。在店面后面，云原生基础设施支持在 AWS 上运行的销售点系统、忠诚度应用程序和电动汽车 (EV) 充电应用程序。随着公司扩大数字化业务，分类管理费用也随之增加。更多的服务意味着更多的警报，并且每一项都需要相同的手动调查才能开始修复。

为了解决这个问题，Circle K 使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 构建了一个自动分类系统，这是一项完全托管的服务，可通过单个 API 提供基础模型 (FM)。有关 AWS 区域的模型可用性，请参阅 [Amazon Bedrock 中 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。该系统使用代理人工智能架构来自主调查每个事件，并在警报触发后几分钟内向 Slack 提供结构化摘要。值班工程师现在收到的是可操作的上下文，而不是原始警报，因此他们可以立即采取行动，而不必花一个小时来弄清楚发生了什么。

自从部署该系统以来，Circle K 已将平均分类时间缩短至 15 分钟以下，根据团队的内部事件响应指标，缩短了 67%–75%。

在这篇文章中，我们描述了初始 [Amazon Bedrock Flows](https://aws.amazon.com/bedrock/flows/) 实施和迁移到 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 的架构，并分享了从扩展系统中吸取的经验教训。

## 分类开销的挑战

Circle K 的 DevOps 团队使用 Grafana 监控多个 AWS 账户的基础设施。通常一天会发出有关容器重新启动、错误率升高、延迟峰值和部署失败的警报。每个警报都是有用的信号，但随着系统的扩展，团队希望帮助值班工程师在正确的上下文中快速查看哪些信号需要注意。

当警报出现时，分类涉及一系列熟悉的手动步骤：查看 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 中的最新日志、检查 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 中的应用程序级跟踪、检查 [Amazon Elastic Container Service (Amazon ECS)](https://aws.amazon.com/ecs/) 任务状态以及将症状与内部交叉引用GitHub 中的操作手册。这为工程师提供了他们所需的信息，但它也显示了随着更多服务的加入，需要多少重复的上下文收集。

该团队认识到主动投资可以在两个领域有所帮助。首先，将对每个事件重复相同的日志查询、运行状况检查和运行手册查找。其次，分类的深度和速度可能会因待命工程师对受影响服务的熟悉程度而异。随着警报量和服务所有权的增长，每次调查在多个工具之间切换可能会减慢响应速度，并使团队更难一致地应用最佳实践。

因此，Circle K 的 DevOps 团队启动了一项研发 (R&D) 计划，探索人工智能如何支持监控和事件分类。目标是自动收集重复的上下文并提供结构化的、可操作的发现，同时支持工程师在调查期间的操作判断。

## 为什么 Circle K 选择 Amazon Bedrock

该团队在构建之前评估了多种方法，包括自我管理基础设施上的开源代理框架。这种方法意味着拥有模型托管、提示版本控制、工具编排和安全控制。

借助 Amazon Bedrock，该团队避免了这种开销。他们可以通过单个 API 访问基础模型并交换基础模型，而无需重写代码。由于 Circle K 已在 AWS 上运行，因此 Amazon Bedrock 适合现有的 AWS Identity and Access Management (IAM) 策略、Amazon Virtual Private Cloud (Amazon VPC) 配置和日志记录管道。

两项托管功能涵盖编排和检索。 Amazon Bedrock 帮助代理编排，让代理可以使用本机工具调用 AWS API、查询数据库和检索文档，而无需自定义编排代码。 Amazon Bedrock 知识库是完全托管的检索增强生成 (RAG) 功能，可处理内部产品卡的摄取和检索，因此团队无需运行单独的矢量数据库。这让 DevOps 团队专注于提示设计和工具定义。

数据隐私完成了这一切。 Circle K 的事件数据包括运营指标、基础设施详细信息以及可能包含敏感信息的日志。 [Amazon Bedrock 不会与模型提供商共享客户数据或使用其来训练基础模型](https://aws.amazon.com/bedrock/security-privacy-responsible-ai/)。对于将生产日志和内部服务详细信息输入系统的团队来说，这种数据处理方法满足了 Circle K 的安全要求。

## 解决方案概述

本部分介绍团队在 Amazon Bedrock Flows 上构建的初始架构。后面的部分将介绍向 AgentCore 的迁移。

该解决方案使用 Amazon Bedrock Flows 作为编排层，协调一组专用代理，每个代理处理分析的不同部分。当 Grafana 警报将通知发布到 [Amazon Simple Notification Service (Amazon SNS)](https://aws.amazon.com/sns/) 时，管道就会启动，该通知会将其转发到 [Amazon Simple Queue Service (Amazon SQS)](https://aws.amazon.com/sqs/) 队列。 [AWS Lambda](https://aws.amazon.com/lambda/) 函数轮询队列、提取警报负载并调用流。

在 Flow 内部，两个代理被并行调用。 “AWSResourceExplorerAgent”跨由 [AWS Organizations](https://aws.amazon.com/organizations/) 管理的多个工作负载账户查询基础设施。它检查 Amazon ECS 任务状态、Application Load Balancer 目标运行状况以及 CloudWatch 指标和日志。同时，“OpenSearchExplorerAgent”会查询 Amazon OpenSearch Service 以获取应用程序级日志和分布式跟踪。由于 OpenSearch 返回大量日志数据，因此该代理单独运行。隔离它可以使每个代理的上下文窗口保持可管理性。它还具有对知识库的独占访问权，其中包含描述每个服务及其依赖项的产品卡。

两个代理返回结果后，“GitHubExplorerAgent”就会运行。它接收前两个代理的输出并查找受影响服务的 GitHub 存储库。然后，它会搜索他们的应用程序代码、基础设施定义和最近的提交，以查明问题的根源并提出具体的解决方案。在并行代理之后运行它意味着它确切地知道要搜索什么而不是执行广泛的查询。

所有三个输出都会输入“AnalysisPrompt”节点，该节点是不附加任何工具的单个模型调用。它接收 AWS 资源数据、OpenSearch 日志和 GitHub 上下文，然后生成结构化摘要：可能的根本原因、支持证据、受影响的服务和所有者以及建议的修复步骤。提示输出使用一致的格式，待命团队可以在 2 分钟内完成扫描。

Flow 将此摘要返回给调用 Lambda 函数，该函数将其发布到 Slack 通道。从警报到 Slack 消息的整个过程需要 5-15 分钟，具体取决于事件的复杂性。

### 分类示例

Grafana 警报：服务上的 HTTP 5xx 错误率连续 3 分钟超过 5%。

AWSResourceExplorerAgent 检查目标账户中的 ECS 任务运行状况，发现数据库连接池已耗尽，ECS 服务尝试重新启动。 OpenSearchExplorerAgent 返回应用程序日志，显示从服务到其支持 PostgreSQL 数据库的“连接被拒绝”错误。它还从知识库中检索受影响服务的产品卡，该卡记录了其对该数据库的依赖关系。 GitHubExplorerAgent 搜索服务的存储库和基础设施文件并查找 Amazon Relational Database Service (Amazon RDS) 定义。它看到该服务为每个请求打开一个新的数据库连接，而不是重用现有的数据库连接。

AnalysisPrompt 接收所有三个结果。它将时间与警报前 10 分钟开始的预定营销活动相关联。它将这一点与 GitHubExplorerAgent 的发现相结合，推荐具体的代码级修复，而不是临时补丁。

最后的 Slack 消息如下：
```
Summary: XYZ Service 5xx errors caused by connection pool exhaustion
Root cause: Scheduled marketing campaign drove traffic spike; connection pool max (50) insufficient for load
Evidence: OpenSearch logs show "connection refused" at 14:32 UTC; ECS shows 3 task restarts since 14:30
Owner: XYZ team (backend)
Next steps: Add Amazon RDS Proxy to pool connections, or update the service to reuse existing connections instead of opening a new one per request; consider an Auto Scaling rule for future campaigns
```
## 扩展到 Amazon Bedrock AgentCore

Amazon Bedrock Flows 架构连续几个月运行良好，简单事件在 10 分钟内就得到了分类。随着时间的推移，尽管服务集保持不变，但每次调查背后的数据量和背景都在增长。有些事件需要运行时间更长的分析，单个 Flow 节点无法完成。

该团队首先通过更积极地过滤日志、缩短上下文窗口以及将某些服务拆分为单独的流来在现有设计中进行优化。这些步骤有所帮助，但日志量和知识库不断增长。

Amazon Bedrock AgentCore 满足了这一需求。 AgentCore 是一个使用任何框架或模型大规模构建、连接和优化 AI 代理的平台。对于此工作负载，关键功能是 AgentCore 运行时：完整的调查在单个会话中运行，因此每个步骤都可以占用其数据所需的时间。 AgentCore Runtime 支持长达 8 小时的会话，远远超出了当前调查的需要。该团队将其代理逻辑容器化并将其部署在 AgentCore Runtime 上。

分析逻辑保持不变，但运行方式发生了变化。 Flows 版本中的三个专用代理现已合并为在 AgentCore 运行时会话中运行的单个代理。 Lambda 函数启动会话，代理执行与之前相同的步骤。它跨账户查询 AWS 资源、从 Amazon OpenSearch Service 提取日志、搜索 GitHub 并从知识库检索产品卡。代理会在 15 分钟内将其结果返回给 Lambda 函数，这在最大 Lambda 超时范围内。然后，Lambda 函数将结构化摘要发布到 Slack。

Amazon Bedrock AgentCore Gateway 是 Amazon Bedrock AgentCore 的一项功能，可代理代理对其数据源的访问，包括 Amazon OpenSearch Service、Amazon Bedrock 知识库和 GitHub。网关将每个源公开为代理调用的工具，从而集中访问控制并使团队更轻松地添加或更改数据源。

### AgentCore Runtime 如何支持团队不断扩大的规模

除了运行时间较长的会话之外，Amazon Bedrock AgentCore Runtime 还添加了三项支持团队规模不断扩大的功能：会话持久性、基于 OpenTelemetry 的可观察性和框架灵活性。

**会话持久性：** 代理在整个调查过程中保持中间状态。如果第一次通过日志发现了一些东西，代理可以运行第二次更有针对性的通过，而不会丢失它已经构建的上下文。这适合调查复杂的多服务事件的迭代方式。

**可观察性：** AgentCore 使用 OpenTelemetry 标准和通过 CloudWatch 的表面捕获每个会话的跟踪。团队可以看到每个步骤需要多长时间、代理进行哪个知识库查询以及出现瓶颈的位置。这些见解直接反馈到即时调整中。

**框架灵活性：** 借助 AgentCore Runtime，团队可以部署使用各种框架构建的容器化代理。他们可以迭代代理逻辑、添加分类步骤或根据需求变化重构代理的推理，所有这些都在同一个运行时上进行。

AgentCore 架构现在在生产中运行并处理全方位的事件，从简单的单一服务警报到大型多服务调查。

## 结果

Circle K 于 2026 年 4 月部署了 AgentCore 版本的分流系统。根据团队的内部事件响应指标，平均分流时间从 45-60 分钟降至 15 分钟以下，减少了 67-75%。简单的事件会在 5-8 分钟内收到摘要。复杂的多服务事件以前需要一个多小时才能手动分类，现在只需 15 分钟即可完成。

工程师现在从摘要开始，而不是自己收集背景信息。该团队发现事件处理方式发生了三项变化：

**一致的分类。** 每个待命工程师都会收到相同的结构化摘要，其中包含相同的日志摘录、知识库参考和建议的后续步骤，无论他们对受影响的服务了解程度如何。

**更快升级。** 当问题需要其他团队的支持时，摘要会为待命工程师提供相关背景信息，以便及时、知情地升级。

**更快地处理错误警报。** 当分析发现服务正常并且没有相关错误时，工程师可以确认警报并继续。

## 经验教训

构建这个系统需要多次迭代。有四个经验教训适用于使用 Amazon Bedrock 构建类似解决方案的团队。

直接在提示中包含日志内容。早期版本仅传递日志组名称和时间范围，然后代理尝试通过操作组查询 CloudWatch。这增加了延迟，并且经常返回太多数据需要处理。 Circle K 通过使用 Lambda 函数预查询日志并将相关行直接传递给代理，获得了更好的结果。当代理可以读取实际的错误消息时，它的推理速度会更快。

调整用例的检索和生成。检索配置显着影响知识库的结果质量。在测试可用选项后，Circle K 团队发现具有默认配置的 Amazon Bedrock 知识库最适合他们的数据。 Amazon Bedrock 端到端处理嵌入、索引和矢量存储，因此团队需要维护的组件更少。在生成方面，精心设计的系统提示和调整的温度设置在 Slack 中生成了一致的摘要。

根据日志中的发现缩小代码搜索范围。在没有线索的情况下搜索服务的存储库会返回太多无用的结果。团队在 AWS 资源和日志分析之后运行 GitHub 搜索，因此代理已经知道要查找哪个错误、组件或最近的更改。在示例分类中，代理发现服务为每个请求打开一个新的数据库连接。

保持分析逻辑独立于编排层。分析时间随着数据量的增加而增加，因此要计划好调查时间会随着时间的推移而延长。该团队将提示、工具定义和分析步骤与流程结构分开。这使得可以将它们合并到 AgentCore Runtime 上的单个代理中，而无需重写分类逻辑。

## 后续步骤

今天，分类系统找到了可能的根本原因并建议修复，然后由工程师执行修复。接下来，该团队计划与 [AWS DevOps Agent](https://aws.amazon.com/devops-agent/) 集成，以便系统也可以处理简单的修复。示例包括重新启动任务、扩展服务或回滚部署。 Slack 中的每个操作在运行之前都会由工程师批准。

该团队还计划为代理提供更多的工作背景：

- Jira，将每个事件与相关票证相关联并跟踪后续工作。
- Confluence，将内部文档添加到代码中并记录代理已读取的内容。
- 知识库中的操作手册，因此代理可以将症状与已知的故障模式和以前有效的修复相匹配，而不是仅仅依赖产品卡。

## 结论

Circle K 团队通过自动化工程师过去手动进行的上下文收集，将 45-60 分钟的手动事件分类缩短到了 15 分钟以内。该系统从日志、AWS 资源和代码中收集数据，让代理对其进行推理，并向 Slack 提供结构化摘要。

该团队在 Amazon Bedrock Flows 和 Amazon Bedrock 知识库上构建了第一个版本。随着调查规模的扩大，团队转向 Amazon Bedrock AgentCore Runtime 上的单个代理，并通过 AgentCore Gateway 提供对其数据源的访问。

如果您的团队将大部分事件响应时间用于收集上下文而不是解决问题，则可以直接应用此模式。首先，请探索 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 和 [Amazon Bedrock 知识库](https://aws.amazon.com/bedrock/knowledge-bases/)。如需实践指导或与 AWS 专家讨论您的使用案例，请访问 [Amazon Bedrock 入门页面](https://aws.amazon.com/bedrock/getting-started/) 或 [联系 AWS](https://aws.amazon.com/contact-us/)。
