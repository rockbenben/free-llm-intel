合成监控（synthetic monitoring）通过自动化交易模拟真实用户旅程。团队不必等客户遇到问题，而是按计划持续验证关键工作流（登录、购买、表单提交）。用这一方法，当性能退化或 UI 交互失效时你能更快地发现问题。

对面向客户的业务——尤其在电商——合成监控守护那些最重要的交互。组织验证产品搜索正确工作、定价和库存按预期展示、购物车操作成功，以及下单确认无误地完成。持续的测试在客户遇到问题之前就识别出问题。

同样的方法适用于各行业。金融服务组织确保账户访问和交易流程保持可用。旅游和酒店提供商监控预订和预约旅程。软件即服务（SaaS）公司验证注册和订阅升级路径。医疗机构监控那些可用性和交易健康至关重要的预约门户。

本文演练一个用 [Amazon Nova Act](https://aws.amazon.com/nova/act/) 和 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 做的、由智能体驱动的合成监控方法。结合这些服务，你可以从脆弱的 UI 脚本走向有韧性、托管的旅程验证。本文描述智能体驱动合成监控的架构和模式，并附一个含完整实现的[示例仓库](https://github.com/aws-samples/sample-nova-act-synthetic-monitoring)。

## 传统合成监控的挑战

多数组织通过指标、日志、trace 和 API 级检查来监控基础设施健康。然而，高影响故障常发生在用户旅程层，那里后端信号可能不会立即揭示问题。常见例子：一次前端部署弄坏了一个下单按钮、一个第三方登录页意外改变，或一次 UI 回归让关键元素无响应。

Selenium 和 Playwright 这类传统浏览器自动化框架依赖显式的文档对象模型（DOM）定位器和选择器，这造成了脆弱性。即便是微小的 UI 改动也能弄坏测试并要求持续维护。团队投入大量持续精力管理选择器、处理与时间相关的 instability，并随应用演进更新脚本——常常花在维护上的时间比构建新自动化还多。

**传统方法**

```
# Breaks when CSS class changes
driver.find_element(By.CLASS_NAME, "checkout-button").click()
driver.find_element(By.ID, "payment-form").submit()
driver.find_element(By.XPATH, "//button[@data-test='complete-order']").click()
# Requires 10+ lines of explicit selectors per workflow
```

**Nova Act 方法**

```
# Adapts to UI changes in most cases
nova_act.act("Click the checkout button")
nova_act.act("Complete the payment form")
nova_act.act("Confirm the order")
# 3 lines, no selectors to maintain
```

Amazon Nova Act 使用一个多模态大语言模型（LLM），它处理 UI 截图而非 DOM 选择器，使其对 UI 改动显著更有韧性。因为模型是从它在屏幕上所看到的东西推理（而非从 CSS 类或元素 ID），它在样式变化时能适应而无需更新脚本。在早期的企业客户用例中，Amazon Nova Act 在浏览器工作流上[展示了超过 90% 的准确率](https://aws.amazon.com/blogs/machine-learning/amazon-nova-act-sdk-preview-path-to-production-for-browser-automation-agents/)。相对那些任何元素变化就立刻失败的选择器方法，这是一个有意义的改进。团队应在自己的站点上测试，并为适配不奏效的情况设计带重试逻辑的监控。

企业监控平台把浏览器检查定价为高级附加项，从而加剧了维护挑战。这迫使团队在监控广度与预算之间做取舍，而这全都偏离了验证关键客户旅程这一真正目标。

## 方案概览

该方案结合以下 AWS 服务，各自处理一项不同的职责：

- **Amazon Nova Act** 通过自然语言动作加编排逻辑来定义并执行 UI 工作流。它用视觉和语言推理取代了基于选择器的脚本。
- **Amazon Bedrock AgentCore Runtime** 提供带会话隔离和稳定调用端点的无服务器执行。它托管监控智能体，而无需团队管理服务器或容器。
- **AgentCore Browser 工具**（Amazon Bedrock AgentCore 的一项能力）为每次测试运行提供一个安全的、隔离的远程浏览器环境。它消除了运营浏览器集群的开销。
- **Amazon EventBridge Scheduler** 和 **Amazon Simple Notification Service (Amazon SNS)** 分别处理调度和告警，按节奏触发测试并把失败通知投递到订阅的端点。

## 架构

架构遵循这一流程：

- Amazon EventBridge Scheduler 按定义的计划（从每 5 分钟到每小时，取决于工作流的关键程度）触发合成监控运行。
- 每次计划调用通过 Amazon EventBridge Scheduler 的 universal target 能力直接调用 `InvokeAgentRuntime`。
- 智能体在 AgentCore Runtime 内执行，调用 Amazon Nova Act，在一个 AgentCore Browser 会话中用自然语言动作驱动 UI 工作流。
- 如果旅程在任一步失败，智能体通过 Amazon SNS 发布一个通知。
- 失败立即路由到订阅的端点（邮件、聊天集成、事件响应工具）。

## 实现

下面各节演练设置要求、旅程定义、智能体部署和调度基础设施。

### 前提条件

实现前，确认以下内容：

- 一个 AWS 账户，可访问 Amazon Nova Act、Amazon Bedrock AgentCore（Runtime 和 Browser 工具）、Amazon Elastic Container Registry (Amazon ECR)、IAM、Amazon EventBridge Scheduler 和 Amazon SNS。
- Python 3.11 或更高、Docker，以及配置好凭证的 AWS Command Line Interface (AWS CLI) v2。
- 用于生产基础设施路径的 Node.js 18 或更高，以及 AWS Cloud Development Kit (AWS CDK)（也提供了独立的 `deploy.py` 脚本）。
- 如果你希望 `deploy.py` 或 CDK 为告警创建一个 SNS 邮件订阅，则需一个邮件地址。

### 定义一个旅程

实现从定义那些要验证的最重要客户旅程开始。对电商应用，这些通常包括首页加载、产品搜索、产品详情导航、加入购物车验证和下单就绪。

不要只聚焦工作流完成，而要显式地验证结果。监控应当确认搜索结果正确出现、购物车含商品，且没有错误横幅显示。显式的结果验证减少了不完整检查造成的误报，以及过于宽松的断言造成的漏报。

### 智能体定义

该智能体把自然语言动作分组成逻辑的旅程步骤，并在关键检查点使用断言。动作用 `act()` 通过自然语言驱动 UI。断言用 `act_get()` 配一个布尔 schema 来验证结果。当一个旅程失败时，智能体发布旅程类型、目标 URL、时长、已完成步骤和失败步骤。详细的异常信息留在运行时日志里。

代码直接使用 Nova Act SDK。当部署到 AgentCore Runtime 时，执行环境通过 Browser 工具管理浏览器会话生命周期。在测试中，一个典型的六步旅程在 2 到 4 分钟内完成，取决于页面加载时间。当前方法签名和 SDK 版本参见 [Nova Act 用户指南](https://docs.aws.amazon.com/nova-act/latest/userguide/)。示例仓库包含带错误处理和单次尝试步骤执行的完整智能体定义。

### 把智能体部署到 AgentCore Runtime

在 Amazon EventBridge 计划能调用智能体之前，用 Nova Act CLI 把它部署到 AgentCore Runtime。act workflow 命令把智能体代码打包、把容器镜像推送到 Amazon ECR，并配置运行时。部署后，端点的 Amazon Resource Name (ARN) 保持恒定。更新创建新的运行时版本而无需你更新你的 Scheduler target。

```
act workflow create --name synthetic-monitoring-workflow
act workflow deploy --name synthetic-monitoring-workflow --source-dir . --entry-point workflow.py
act workflow show --name synthetic-monitoring-workflow
```

`act workflow show` 命令返回你要作为 Scheduler target 引用的 AgentCore Runtime ARN。示例仓库的 `deploy.py` 脚本把这些命令包上前提条件检查（Docker、AWS 凭证）、创建 SNS 告警主题，并接好 Amazon EventBridge 计划，于是一条 `python deploy.py` 完成端到端部署。（AgentCore 也提供其自己的 agentcore CLI 用于智能体开发。本示例统一使用 Nova Act 的 act workflow 命令。）

### 用 CDK 部署

对于生产级、可重复的部署，示例包含一个作为 `deploy.py` 独立替代方案的 CDK 栈。它配置带最小权限 IAM 的 Amazon EventBridge 计划、SNS 告警主题，以及一个捕获来自 Scheduler 的失败 `InvokeAgentRuntime` 调用的 SQS 死信队列。

该栈还创建两个 Amazon CloudWatch 告警：一个针对死信队列深度（失败的 Scheduler 调用），一个针对缺失的计划运行（使用 `AWS/Scheduler InvocationAttemptCount` 指标，把缺失数据视为越界）。注意这些告警检测基础设施故障，例如到智能体的投递失败或计划未触发。一个功能上失效却仍在 HTTP 层返回的客户旅程，是通过智能体的 SNS 发布浮现的，而非通过这些 CloudWatch 告警。

### 避免告警疲劳

把合成监控聚焦在高价值的客户旅程上，而非穷尽的页面覆盖。过度监控制造噪声，让团队对真实故障变得迟钝。从 3–5 个关键工作流（登录、下单、账户访问）开始，并根据实际的失败模式和业务影响扩展。监控那些直接影响收入或客户信任的旅程，而不是每一条可能的用户路径。

同样，避免对每个页面元素过度断言。验证有意义的结果（搜索结果是否出现、购物车是否含商品），而不是检查页面上每个 DOM 元素。过于细粒度的断言会增加误报而不改进失败检测。

示例智能体代码对每步使用单次尝试执行，以最小化 Browser 会话成本。由于 Nova Act 的自然语言适配在约 90% 的情况下成功，单次尝试方法偶尔会在 Nova Act 找不到一个实际存在的 UI 元素时产生虚假告警。需要更低误报率的团队可以添加步骤级重试（在判定失败前重跑一个失败的步骤一次），代价是更长的会话时长。

## 运维考量

部署后，有两个运维问题需要关注：观测监控系统本身和管理成本。

### 监控监控系统

AgentCore Runtime 把智能体调用指标发布到 Amazon CloudWatch，因此你可以跟踪执行频率和时长。成功时，智能体不发布到 SNS 就完成了。旅程失败通过智能体的 SNS 发布浮现。配置带死信队列的 SNS 主题以检测失败的智能体调用。

### 成本考量

成本来自五个组件：AgentCore Runtime 调用、Browser 工具会话、Nova Act 推理、Amazon EventBridge Scheduler 调用和 SNS 通知。主要成本驱动是 Browser 会话时长和每旅程步骤的 Nova Act 推理调用。

下表为该示例每 5 分钟运行一次的六步电商旅程（每月约 8,640 次调用）提供成本近似：

| **组件** | **每月用量** | **估计成本** |
| --- | --- | --- |
| AgentCore Runtime 调用 | 8,640 个会话，每个约 2–4 分钟 | 见[定价页面](https://aws.amazon.com/bedrock/agentcore/pricing/) |
| Browser 工具会话 | 8,640 个会话，每个约 2–4 分钟 | 见[定价页面](https://aws.amazon.com/bedrock/agentcore/pricing/) |
| Nova Act 操作 | 约 207,360 次动作和断言调用（每旅程 24 次） | 见[定价页面](https://aws.amazon.com/bedrock/pricing/) |
| Amazon EventBridge Scheduler | 8,640 次调用 | 约 $0.009   见[定价页面](https://aws.amazon.com/eventbridge/pricing/) |
| SNS 通知 | 仅失败告警（配置时） | 可忽略   见[定价页面](https://aws.amazon.com/sns/pricing/) |

### 方案收益

采用用 Nova Act 和 AgentCore 的智能体驱动合成监控的组织，可以在关键运营维度上期待可测量的改进：

- **减少的脚本维护**：自然语言动作取代了选择器更新循环。团队不再需要在常规 UI 部署后重建监控。
- **更快的平均检测时间（MTTD）**：持续的 5 分钟节奏验证在部署后几分钟内而非客户报告浮现之后抓住失败。
- **更低的误报率**：通过 Firecracker microVM 的会话隔离帮助防止那种困扰共享浏览器监控设置的状态泄漏诱发的误报。
- **更低成本的更广覆盖**：完全托管的基础设施（无浏览器集群、无服务器维护）让团队能监控更多旅程，而持续成本不按比例增加。

## 安全与合规

合成监控必须产出可靠结果，而不引入误报或掩盖真实故障。AgentCore Runtime 用一个建立在 Firecracker microVM 之上的严格一会话一 microVM 模型，为每次测试执行提供会话隔离。默认情况下，每个会话在完全的内存清理中终止，防止 cookie、浏览器缓存和 LocalStorage 在多次运行间持久。这帮助防止跨测试状态泄漏造成的误报。对于合成监控，临时会话是保持测试独立的推荐模式。AgentCore 确实通过 `SaveBrowserSessionProfile` API 为其他用例提供持久浏览器配置，但合成监控应始终使用临时会话。

对于网络访问，Browser 工具默认在公有网络模式下运行，提供适合验证面向客户网站的合成监控的互联网访问。对于需要出口控制的环境，AgentCore 支持带 Amazon Virtual Private Cloud (Amazon VPC) 配置的 Browser，让团队在监控内部应用时把网络访问限制到特定域名。

团队把合成监控与 AWS Identity and Access Management (IAM) 集成以强制执行最小权限。IAM 角色定义智能体能访问哪些资源，包括 SNS 发布权限和 Browser 工具调用。

当合成测试需要认证时，团队应把凭证存储在 AWS Secrets Manager，它保持敏感信息加密，且访问可通过 AWS CloudTrail 审计。

## 用基础设施即代码做多区域部署

有全球用户的组织可以在多个 AWS 区域部署 Nova Act 合成监控，以从不同地理位置测试用户体验。这帮助验证用户体验并在多个区域识别问题。

用基础设施即代码（IaC）在受支持区域上一致、可重复地部署该方案。关于当前的区域可用性，参见 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 和 [Amazon Nova Act](https://aws.amazon.com/nova/act/) 产品页面。

## 清理

为避免本文创建的资源持续产生费用，在不再需要时移除它们：

- 对于 `deploy.py` 路径，运行 `python deploy.py --cleanup` 以停止计划调用并移除工作流及相关示例资源。
- 对于 CDK 路径，运行 cdk destroy 以移除 CDK 管理的计划、SQS 死信队列、CloudWatch 告警、SNS 主题和 IAM 角色。
- CDK 栈不拥有 AgentCore Runtime。用 `act workflow delete --name synthetic-monitoring-workflow` 删除单独部署的工作流。

## 结论

合成监控传统上需要在脆弱的脚本、以及随应用变化维护它们所需的持续努力之间做权衡。Amazon Nova Act 和 Amazon Bedrock AgentCore 减轻了这份负担。Nova Act 使用对常规 UI 变化更有韧性的自然语言动作，而 AgentCore Runtime 提供了大规模运行工作流的基础设施。
