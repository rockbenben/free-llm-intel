# 为 AgentCore memory 设计生命周期策略

记忆生命周期策略通过系统化地管理 agent 记住什么、忘记什么，帮助运行在 Amazon Bedrock AgentCore 上的长时 agent 保持有效性。你的 agent 会从每一次对话中生成记忆。如果你不主动管理这些记忆，agent 就会不断累积过时的上下文，进而降低回答质量，并为你的部署带来合规风险。

在生产环境使用几个月后，问题就会显现。我们观察到，一个客户支持 agent 引用了一笔四个月前就已解决的账单争议，并把它当作仍在处理中；另一个 agent 反复给出过时的部署建议，因为它的记忆中仍保留着已被取代的 runbook。

本文介绍面向 AI agent 的记忆生命周期管理：即随着时间推移，系统化地对 agent 记忆进行评分、合并与清理的实践。我们会讲解一个可部署的架构，它使用 [AgentCore memory](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-agentcore-memory-building-context-aware-agents/)（Amazon Bedrock AgentCore 的一项能力）、AWS Step Functions 和 Amazon Bedrock，运行一个夜间生命周期工作流。读完之后，你将拥有一个 AWS Cloud Development Kit（AWS CDK）stack，以及一套把 agent 记忆当作托管资源来管理的框架。完整代码可在 [GitHub 仓库](https://github.com/aws-samples/sample-memory-lifecycle-policies-for-bedrock-agentcore) 中获取。

该方案面向在数周或数月内累积大量交互数据的 agent，例如客户支持 agent、销售顾问和 IT 服务台机器人。对于个人助理这类量级更低的 agent，你可能只需先从生存时间（TTL）过期和《通用数据保护条例》（GDPR）合规做起。所有阈值都可配置，以匹配你的 agent 的需求。

## 解决方案概览

该解决方案把一套共享的记忆分类法与三项以夜间工作流形式运行的生命周期策略结合起来。我们先从塑造这些策略的记忆类型讲起。

### 记忆类型

在设计生命周期策略之前，我们需要一套共享的词汇来界定 agent 记住什么。我们把 agent 记忆分为三类，每类的保留要求各不相同。

- **Episodic memory（情节记忆）：** 情节记忆记录发生了什么，是过往对话的档案。它们带时间戳、绑定会话，且体量很大。AgentCore memory 用 Summary 和 Episodic 两种策略存储这类信息。两种策略都把记忆存为单条记录，并绑定到特定的 agent 与用户会话。Episodes 和 Summary 提供短期连续性，但单独来看，它们会随着时间推移而逐渐失去相关性。在设计生命周期策略时，应优先让这类记忆先过期。
- **Semantic memory（语义记忆）：** 语义记忆是从交互中提炼出的事实与偏好，但已与任何单次对话解耦，例如「该用户偏好使用美国东部（弗吉尼亚北部）区域（us-east-1）进行部署」。它们持久、价值高且紧凑。在生命周期策略中，语义记忆的保留时间应长于情节记忆。它们也是合并的首要候选对象——把多条情节观察合并成一条权威事实。
- **Procedural memory（流程记忆）：** 流程记忆编码学到的工作流和工具使用模式，例如「当用户询问成本时，先查询 AWS Cost Explorer API，再做汇总」。它们代表 agent 的运营专长。流程记忆体量更小，但对某些用例来说是最有价值的类型。它们的保留时间最长，清理的门槛也最高。AgentCore memory 把流程知识存为与情节记忆绑定的 reflection。更多内容请参阅 [Episodic memory 深入解析博客](https://aws.amazon.com/blogs/machine-learning/build-agents-to-learn-from-experiences-using-amazon-bedrock-agentcore-episodic-memory/)。随着流程演进，你应该检查这些内容是否仍然有效。

### 生命周期策略

有了这套分类法，我们就可以设计三项互补的生命周期策略。每一项针对的都是记忆无限增长时的不同失效模式。

#### 策略 1：基于 TTL 的过期

第一项策略会自动删除超过配置 TTL 的记忆。我们为情节记忆设置的默认值是 90 天。TTL 并不考虑记忆是否仍然有用，但它为累积量提供了硬性上限，并且对合规至关重要。

在生产环境中，应按记忆类型区分 TTL。把 Summary 记忆配置为 30–60 天后过期，语义记忆为 6–12 个月后过期，并考虑对流程记忆不设 TTL。本文提供一个可配置的 `memoryTtlDays` 参数作为起点。TTL 过期先于评分和合并执行，这有助于避免在本该已经消失的记忆上浪费计算。

AgentCore memory 并不提供内置的自动删除 TTL。不过，它暴露了系统生成的时间戳字段，这些字段在 `ListMemoryRecords` 上支持 `BEFORE` 和 `AFTER` 过滤操作符。我们的 pruner 使用 `x-amz-agentcore-memory-createdAt` 配合 `BEFORE` 过滤，只取回早于所配置 TTL 的记录，然后将其删除。

```
cutoff = (now - timedelta(days=ttl_days)).isoformat()

response = client.list_memory_records(
    memoryId=memory_id,
    namespace=agent_id,
    metadataFilters=[{
        "left": {"metadataKey": "x-amz-agentcore-memory-createdAt"},
        "operator": "BEFORE",
        "right": {"metadataValue": {"dateTimeValue": cutoff}},
    }],
)
```

#### 策略 2：相关性衰减评分

并不是所有记忆都以同样的速度变旧。昨天被访问过的记忆，比几周未被动过的记忆更相关。我们用三项加权公式为每条记忆打分，把创建时间的新近度、最近一次访问的新近度和访问频次结合起来：

```
score = W_RECENCY * exp(-decay_rate * days_since_creation)
        + W_ACCESS * exp(-decay_rate * days_since_last_access)
        + W_FREQUENCY * min(access_count / MAX_ACCESS_BASELINE, 1.0)
```

我们没有直接暴露原始的衰减常数，而是提供一个更直观的参数：`pruneDays`，即一条未被访问的记忆其分数降到相关性阈值以下大约需要经过的天数：

```
import math

def decay_rate_from_prune_days(prune_days: int, threshold: float) -> float:
    """Convert pruneDays to an exponential decay rate.

    decay_rate = -ln(threshold) / prune_days
    """
    if prune_days <= 0:
        raise ValueError(f"prune_days must be a positive integer, got: {prune_days}")
    if threshold <= 0 or threshold >= 1:
        raise ValueError(
            f"threshold must be in the open interval (0, 1), got: {threshold}"
        )
    return -math.log(threshold) / prune_days
```

在默认值下（`pruneDays = 45`、`threshold = 0.3`），由此得到 `decay_rate ≈ 0.02676`。该公式产生的分数介于 0.0–1.0 之间。当记忆的分数低于你配置的阈值时，系统会根据你的策略设置把它们标记为待合并或待清理。

该公式平衡了三种直觉：新近的记忆更重要，最近被用过的记忆更重要，被频繁检索的记忆还带有额外信号。指数衰减意味着分数在最初几周急剧下降，之后趋于平缓。一条虽然陈旧、但最近被频繁访问的记忆，依然可以获得不错的分数。

三个权重都可配置，让运营者可以根据 agent 的工作负载强调不同的信号：

- `W_RECENCY`（默认 **0.4**）：创建新近度的权重。取值越高越偏向较新的记忆。
- `W_ACCESS`（默认 **0.35**）：最近访问新近度的权重。取值越高越偏向最近被检索过的记忆。
- `W_FREQUENCY`（默认 **0.25**）：访问频次的权重。取值越高越偏向经常被检索的记忆。
- `MAX_ACCESS_BASELINE`（默认 **50**）：频次项达到饱和值 1.0 时的访问次数。应把它设置为一条「高频使用」的记忆在你的回看窗口内大致累积的访问次数。

当三个权重之和为 1.0 时，分数会落在 [0.0, 1.0] 区间内。运营者可以调整权重来匹配 agent 的需求。例如，对于频繁访问的记忆价值最高的 agent（比如反复引用同一份故障排查 runbook 的支持机器人），可以提高 `W_FREQUENCY`；对于时效性最重要的 agent（比如实时交易助手），则可以提高 `W_RECENCY`。

合适的 `pruneDays` 取值取决于 agent 的用例。下表为常见的 agent 类型提供了推荐的起点：

| **Agent 类型** | **pruneDays** | **理由** |
| --- | --- | --- |
| 实时支持机器人 | 7 | 工单在数小时或数天内解决，不需要旧上下文 |
| 销售／入职引导 agent | 21 | 交易在数周内关闭，陈旧的线索会污染上下文 |
| 通用助手 | 45 | 面向混合工作负载的均衡保留策略 |
| IT 服务台／运维 agent | 90 | 故障模式按季节重复出现 |
| 法律／合规顾问 | 180 | 判例在数月内保持相关性 |

下面的评分函数来自我们的 Memory Scorer AWS Lambda 函数（`code/lambdas/memory_scorer/handler.py`）：

```
def compute_relevance_score(
    created_at: datetime,
    last_accessed_at: datetime,
    access_count: int,
    decay_rate: float,
    now: datetime,
    w_recency: float = 0.4,
    w_access: float = 0.35,
    w_frequency: float = 0.25,
    max_access_baseline: int = 50,
) -> float:
    """Compute relevance score using the 3-term weighted decay formula.

    score = w_recency * exp(-decay_rate * days_since_creation)
            + w_access * exp(-decay_rate * days_since_last_access)
            + w_frequency * min(access_count / max_access_baseline, 1.0)

    Returns a float in [0.0, 1.0] when weights sum to 1.0.
    Raises ValueError if max_access_baseline is zero or negative.
    """
    if max_access_baseline <= 0:
        raise ValueError(
            f"max_access_baseline must be a positive integer, got: {max_access_baseline}"
        )
    days_since_creation = max((now - created_at).total_seconds() / 86400, 0.0)
    days_since_last_access = max((now - last_accessed_at).total_seconds() / 86400, 0.0)
    recency_term = w_recency * math.exp(-decay_rate * days_since_creation)
    access_term = w_access * math.exp(-decay_rate * days_since_last_access)
    frequency_term = w_frequency * min(access_count / max_access_baseline, 1.0)
    score = recency_term + access_term + frequency_term
    return score
```

#### 基于 AWS CloudTrail 的访问跟踪

AgentCore memory API 的 `MemoryRecordSummary` 中并不包含 `lastAccessedAt` 字段。为了获得真实的访问数据，我们使用 AWS CloudTrail。CDK stack 配置了一条 trail，通过高级事件选择器捕获 `GetMemoryRecord` 数据事件。你的 CloudTrail 配置会把每一次记忆检索连同其 `memoryRecordId` 和时间戳记录下来，然后把日志投递到你的 Amazon Simple Storage Service（Amazon S3）存储桶。每次评分调用开始时，Memory Scorer 会列出过去 25 小时的 CloudTrail 日志文件，解压它们，并把 `GetMemoryRecord` 事件聚合成一份按记录查询最近访问时间戳和访问次数的查找表。为了在多次调用之间保持累计的访问历史，scorer 在 Amazon S3 中持久化一份访问台账。每次运行都把 CloudTrail 的新计数与历史计数合并，使频次项获得真正的全生命周期信号，而不是狭窄的单日快照。

#### 策略 3：基于 LLM 的合并

在清理低分记忆之前，我们先给它们最后一次机会。合并会使用 Amazon Bedrock 把相关记忆合并成一条紧凑的语义记录。五条关于部署偏好的情节记忆会变成一条权威事实。在这一步中，大语言模型（LLM）是在总结自己的记忆。合并 prompt 会指示模型保留关键事实、去除冗余，并输出一个置信度评分：

```
CONSOLIDATION_PROMPT_TEMPLATE = """You are a memory consolidation assistant.
Given the following agent memories, create a single concise summary that
preserves essential facts, user preferences, and actionable knowledge.
Remove redundancy and outdated information.

Memories:
{memory_contents}

Output a JSON object with:
- "summary": the consolidated memory text
- "confidence": a float 0.0-1.0 indicating consolidation quality
- "key_facts": list of preserved key facts"""
```

系统把合并后的记忆写回 AgentCore memory，然后删除原始记录。如果 Amazon Bedrock 调用失败，系统会原样保留原始记录。系统还会记录失败的删除操作，供你人工复查。合并本质上是有损的：LLM 把五条记忆总结成一条时，可能丢掉一些细微差别。模型返回的置信度评分有助于把低质量的合并标记出来交给人工审阅。对于高风险的领域，可以考虑把原始记录归档到冷存储，而不是直接删除。

对于生产部署，请配置 Amazon Bedrock Guardrails 来过滤有害内容，并使用接地检查（grounding checks）验证合并后的记忆仍然忠实于源材料。这些控制是生产环境的必备要求，而不是可选项。

### 架构图

下图展示了夜间生命周期工作流的架构。Amazon EventBridge 触发一个 AWS Step Functions 状态机，由它按顺序编排五个 Lambda 函数。

![夜间记忆生命周期工作流：Amazon EventBridge 触发一个运行五个 Lambda 函数的 Step Functions 状态机](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/26/ML-20851-1.png)

图 1：由 Amazon EventBridge 和 AWS Step Functions 编排的夜间记忆生命周期工作流

**无障碍文本描述：** 一条 Amazon EventBridge 规则每晚触发一个 Step Functions 状态机。该状态机按顺序调用 Lambda 函数：Memory Pruner（TTL 过期）、Memory Scorer（使用 CloudTrail 访问数据进行相关性评分）、Memory Consolidator（通过 Amazon Bedrock 做基于 LLM 的合并）、Metrics Emitter（Amazon CloudWatch 指标）和 Run Output Writer（S3 持久化）。失败会路由到 Amazon Simple Notification Service（Amazon SNS）主题以发出告警。

工作流按以下步骤进行：

- TTL 过期：Memory Pruner 向 AgentCore memory 查询早于所配置 TTL（默认 90 天）的记录并删除。
- 记忆评分：Memory Scorer 从 CloudTrail 日志构建按记录查询的访问查找表，与持久的 S3 台账合并，计算相关性分数，并返回低于阈值的记忆。
- 合并：工作流把低分记忆分批（默认每批 10 条）发送给 Memory Consolidator，后者调用 Amazon Bedrock 把它们合并成紧凑的语义记录，并删除原始记录。
- 发出指标：Metrics Emitter 把工作流指标（已处理、已合并、已清理的记忆数量）发布到 CloudWatch。
- 写入运行输出：Run Output Writer 把工作流结果持久化到 S3 以便审计。如果任一步骤失败，Catch 块会路由到一个失败处理器，把错误详情发布到 Amazon SNS 主题。

## 解决方案详解

我们把整个生命周期编排为一个由 [Amazon EventBridge](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-what-is.html) 触发的夜间 [AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/welcome.html) 工作流。该工作流按顺序运行五个阶段：TTL 过期、评分、合并、指标发出和运行输出写入。

### CDK stack 详解

一个 CDK stack（`code/lib/memory-lifecycle-stack.ts`）定义了全部基础设施。以下是关键部分。

**Lambda 函数定义**：每个 handler 使用 Python 3.12，并遵循最小权限的 IAM 权限。该 stack 把共享代码作为 Lambda Layer 部署，并以环境变量传递可配置参数：

```
// Lambda Layer for the shared Python module (constants, models)
const sharedLayer = new lambda.LayerVersion(this, 'SharedLayer', {
  code: lambda.Code.fromAsset(
    path.join(__dirname, '..', 'lambdas', 'shared'),
    {
      bundling: {
        image: lambda.Runtime.PYTHON_3_12.bundlingImage,
        command: [
          'bash', '-c',
          'mkdir -p /asset-output/python/shared && cp -r . /asset-output/python/shared/',
        ],
      },
    },
  ),
  compatibleRuntimes: [lambda.Runtime.PYTHON_3_12],
  description: 'Shared constants and models for memory lifecycle Lambdas',
});

const memoryScorerFn = new lambda.Function(this, 'MemoryScorerFunction', {
  runtime: lambda.Runtime.PYTHON_3_12,
  handler: 'handler.handler',
  code: lambda.Code.fromAsset(
    path.join(__dirname, '..', 'lambdas', 'memory_scorer')
  ),
  layers: [sharedLayer],
  timeout: cdk.Duration.minutes(5),
  environment: {
    MEMORY_TTL_DAYS: String(memoryTtlDays),
    RELEVANCE_THRESHOLD: String(relevanceThreshold),
    CONSOLIDATION_BATCH_SIZE: String(consolidationBatchSize),
    BEDROCK_MODEL_ID: bedrockModelId,
    PRUNE_DAYS: String(pruneDays),
    TRAIL_BUCKET_NAME: trailBucket.bucketName,
    TRAIL_LOOKBACK_HOURS: '25',
    W_RECENCY: String(wRecency),
    W_ACCESS: String(wAccess),
    W_FREQUENCY: String(wFrequency),
    MAX_ACCESS_BASELINE: String(maxAccessBaseline),
  },
});
```

**AWS Identity and Access Management（IAM）最小权限**：Memory Scorer 只能列出记忆。Consolidator 可以读取、创建、删除记忆并调用 Amazon Bedrock。Pruner 可以列出和删除：

```
// Memory Scorer: list records only (read-only)
memoryScorerFn.addToRolePolicy(new iam.PolicyStatement({
  effect: iam.Effect.ALLOW,
  actions: ['bedrock-agentcore:ListMemoryRecords'],
  resources: [
    `arn:aws:bedrock-agentcore:${this.region}:${this.account}:memory/*`,
  ],
}));

// Memory Consolidator: full memory record CRUD + Bedrock
memoryConsolidatorFn.addToRolePolicy(new iam.PolicyStatement({
  effect: iam.Effect.ALLOW,
  actions: [
    'bedrock-agentcore:GetMemoryRecord',
    'bedrock-agentcore:BatchCreateMemoryRecords',
    'bedrock-agentcore:DeleteMemoryRecord',
  ],
  resources: [
    `arn:aws:bedrock-agentcore:${this.region}:${this.account}:memory/*`,
  ],
}));

memoryConsolidatorFn.addToRolePolicy(new iam.PolicyStatement({
  effect: iam.Effect.ALLOW,
  actions: ['bedrock:InvokeModel'],
  resources: [
    `arn:aws:bedrock:${this.region}::foundation-model/${bedrockModelId}`,
  ],
}));
```

**Step Functions 工作流**：状态机把 TTL 过期、评分、针对低分记忆的 Choice 状态、批量合并（Map 状态）、指标发出和运行输出写入串联起来：

```
// Chain EmitMetrics -> WriteRunOutput once (both branches converge here)
const emitAndWrite = emitMetrics.next(writeRunOutput);

const definition = ttlExpiration
  .next(scoreMemories)
  .next(
    checkLowScoreMemories
      .when(
        sfn.Condition.isPresent('$.scoringResult.below_threshold[0]'),
        batchConsolidate.next(emitAndWrite),
      )
      .otherwise(emitAndWrite),
  );

const stateMachine = new sfn.StateMachine(this, 'MemoryLifecycleStateMachine', {
  definitionBody: sfn.DefinitionBody.fromChainable(definition),
  timeout: cdk.Duration.hours(1),
  tracingEnabled: true,
});
```

**夜间触发**：一条 Amazon EventBridge 规则每天 UTC 2:00 触发该工作流：

```
new events.Rule(this, 'NightlyMemoryLifecycleRule', {
  schedule: events.Schedule.expression('cron(0 2 * * ? *)'),
  targets: [new targets.SfnStateMachine(stateMachine)],
});
```

所有可配置参数（`memoryTtlDays`、`relevanceThreshold`、`consolidationBatchSize`、`pruneDays`、`bedrockModelId` 以及评分权重）都从 CDK context 读取，因此你可以在部署时调整它们，而无需改动代码：

```
npx cdk deploy \
  -c memoryTtlDays=60 \
  -c relevanceThreshold=0.25 \
  -c consolidationBatchSize=15 \
  -c pruneDays=45 \
  -c wRecency=0.4 \
  -c wAccess=0.35 \
  -c wFrequency=0.25 \
  -c maxAccessBaseline=50
```

### 成本考量

主要成本驱动因素是合并阶段对 Amazon Bedrock 的调用。对于一个拥有 1,000 条记忆、其中 20% 分数低于阈值的 agent，每次夜间运行大约会产生 20 次 Bedrock 调用（约 0.01–0.02 美元）。到 100,000 条记忆时，每月可能达到 50–100 美元。可以先设置较高的相关性阈值来限制合并量，并根据你的具体工作负载查看 Amazon Bedrock 定价。

### 测试记忆质量

只有当 agent 在清理和合并之后仍能正确作答时，这些操作才有意义。我们用一个回归测试套件来衡量生命周期操作是否降低了回答质量。

#### 记忆回归测试套件

我们把测试用例定义为「问题＋判定标准」的成对结构（`code/test/test_regression_suite.py`）。每个测试用例指定一个问题、agent 回答应满足的判定标准，以及最低质量分数：

```
DEFAULT_TEST_FIXTURES = [
    {
        "question": "What are the user's preferred programming languages?",
        "expected_criteria": "Response mentions specific languages previously discussed with the user",
        "min_quality_score": 0.7,
    },
    {
        "question": "Summarize the last project we worked on together.",
        "expected_criteria": "Response includes project name, key milestones, and outcome",
        "min_quality_score": 0.6,
    },
]
```

该回归套件遵循「前后对照」的模式：

- **基线**：在生命周期运行*之前*，用每个测试问题查询 agent。使用 AgentCore Evaluations（Amazon Bedrock AgentCore 的一项能力）记录质量分数。
- **运行生命周期**：执行夜间工作流（评分、合并、清理）。
- **生命周期之后**：用相同的问题再次查询 agent，记录新的质量分数。
- **判定**：如果生命周期后的分数达到或超过所配置的最低值，该测试用例即通过。我们还会计算质量变化量（`post_lifecycle_score - baseline_score`）用于报告。

```
def determine_pass_fail(test_case: RegressionTestCase) -> RegressionTestCase:
    if test_case.post_lifecycle_score is None:
        test_case.passed = None
        return test_case
    test_case.passed = test_case.post_lifecycle_score >= test_case.min_quality_score
    return test_case
```

#### 与 AgentCore Evaluations 集成

该回归套件与 Amazon Bedrock AgentCore Evaluations 集成，以编程方式计算质量分数。AgentCore Evaluations 作为 LLM-as-judge 系统工作：你提供 agent 的回答和人工定义的判定标准，服务返回 0.0 到 1.0 之间的归一化质量分数。这使得该套件完全自动化，适合持续集成与持续交付（CI/CD）流水线。

运行该套件会产出一份按测试用例列出的报告，把基线分数和生命周期后的分数并列呈现，方便你一眼看出质量变化：

```
Memory regression suite (2 test cases)
------------------------------------------------------------
[PASS] Preferred programming languages
baseline=0.82 post=0.85 delta=+0.03 min=0.70
[PASS] Summary of last project
baseline=0.74 post=0.71 delta=-0.03 min=0.60
------------------------------------------------------------
Result: 2/2 passed
```

在这次示例运行中，两个测试用例都保持在配置的最低值以上。只有当生命周期后的分数低于其 `min_quality_score` 时，测试用例才会失败，这说明清理或合并做得过头了。

### 隐私与合规

记忆生命周期管理不只是性能问题，它也是一项合规要求。当你的 agent 在记忆中存储个人数据时，你就要承担 GDPR 等法规下的义务。

#### GDPR 被遗忘权

一个专门的 GDPR Deletion Handler（`code/lambdas/gdpr_deletion/handler.py`）用于删除某个特定用户的全部记忆。它会列出该用户在 AgentCore memory 中的所有记忆，并逐条删除：

```
def handler(event: dict, context) -> dict:
    user_id = event["user_id"]
    memory_id = event["memory_id"]
    client = boto3.client("bedrock-agentcore")

    response = client.list_memory_records(
        memoryId=memory_id,
        namespace=user_id,
    )
    memories = response.get("memoryRecordSummaries", [])

    deleted_count = 0
    failed_memory_ids = []
    for memory in memories:
        record_id = memory["memoryRecordId"]
        try:
            client.delete_memory_record(memoryId=memory_id, memoryRecordId=record_id)
            deleted_count += 1
            logger.info(json.dumps({
                "action": "gdpr_delete",
                "user_id": user_id,
                "memory_id": record_id,
                "timestamp": datetime.now(timezone.utc).isoformat(),
            }))
        except Exception as exc:
            failed_memory_ids.append(record_id)

    status = "success" if len(failed_memory_ids) == 0 else "partial_failure"
    return {
        "status": status,
        "user_id": user_id,
        "deleted_count": deleted_count,
        "failed_memory_ids": failed_memory_ids,
    }
```

该 handler 返回一份确认结果，包含已删除的记忆数量和任何失败的 ID。部分失败时，响应中会包含失败记忆的标识符，便于运营者排查并重试。

#### 用 CloudTrail 做审计日志

每一次记忆变更（评分、合并、清理、GDPR 删除）都会在 Amazon CloudWatch Logs 中产出结构化 JSON 日志，包含操作类型、记忆 ID 和 ISO 8601 时间戳。

该 CDK stack 还配置 AWS CloudTrail 记录 AgentCore memory 的 API 调用，为合规举证提供不可篡改的审计轨迹：

```
new cloudtrail.Trail(this, 'MemoryLifecycleTrail', {
  bucket: trailBucket,
  trailName: 'MemoryLifecycleAuditTrail',
  isMultiRegionTrail: false,
  includeGlobalServiceEvents: false,
  enableFileValidation: true,
});
```

该 stack 还会创建一个 Amazon CloudWatch 仪表板，展示已处理、已合并、已清理的记忆数量以及工作流执行状态，提供实时的运营可见性。

## 结论

我们展示了如何用 AWS Step Functions 和 Amazon Bedrock，为 Amazon Bedrock AgentCore 上的 agent 构建记忆生命周期策略。该方案应用了三项互补的策略：用 TTL 过期设定硬性时间上限，用相关性衰减评分实现智能优先级排序，用基于 LLM 的合并保留知识。借助 `pruneDays` 参数，你可以调整衰减的激进程度。我们还介绍了如何通过测试确认清理不会降低质量，以及记忆层面的 GDPR 合规。

完整代码可在 [GitHub 仓库](https://github.com/aws-samples/sample-memory-lifecycle-policies-for-bedrock-agentcore) 中获取。用 `npx cdk deploy -c pruneDays=45` 部署它，就可以开始为你的 agent 运行夜间记忆生命周期管理。
