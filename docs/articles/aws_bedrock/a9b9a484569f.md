# 使用 Amazon EKS 和 SageMaker HyperPod EKS 上的 NVIDIA Nemotron 模型加速 agentic AI

NVIDIA [Nemotron 3.5 Super VL](https://aws.amazon.com/about-aws/whats-new/2026/01/nvidia-nemotron-3.5-super-vl-on-sagemaker-jumpstart/) 加入了已在 AWS 上可用的 NVIDIA Nemotron 3 [Nano](https://aws.amazon.com/blogs/machine-learning/run-nvidia-nemotron-3-nano-as-a-fully-managed-serverless-model-on-amazon-bedrock/)、[Nano Omni](https://aws.amazon.com/blogs/machine-learning/nvidia-nemotron-3-nano-omni-model-now-available-on-amazon-sagemaker-jumpstart/)、[Super](https://aws.amazon.com/blogs/machine-learning/run-nvidia-nemotron-3-super-on-amazon-bedrock/)、[Ultra](https://aws.amazon.com/blogs/machine-learning/nvidia-nemotron-3-ultra-now-available-on-amazon-sagemaker-jumpstart/) 以及 [Nemotron 3.5 Lightning](https://aws.amazon.com/blogs/machine-learning/nvidia-nemotron-3-5-lightning-now-available-in-amazon-sagemaker-jumpstart/) 模型阵营。它是一个 1200 亿参数的混合专家（MoE）模型，每个 token 激活 120 亿参数。它把推理与工具调用同文本、图像、文档和视频理解结合在一起，因此一个模型即可同时服务文本和视觉任务。本文探讨它的架构与用例，然后演示如何在 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/)、[Amazon EKS Auto Mode](https://aws.amazon.com/eks/auto-mode/) 和 [Amazon SageMaker HyperPod EKS](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks.html) 上部署它。

## 关于 Nemotron 3.5 Super VL

NVIDIA Nemotron 3.5 Super VL 是一个从 Nemotron 3 Ultra 蒸馏而来的开放多模态模型。NVIDIA 公开了权重、训练数据集和后训练配方，因此你可以针对特定领域的工作负载定制该模型，并在你自己控制的基础设施上运行它。模型详情：

- 总参数 1200 亿，每 token 激活 120 亿。
- 混合 Mamba-2、[MoE](https://www.nvidia.com/en-us/glossary/mixture-of-experts/) 与注意力层，并配有 RADIO 视觉编码器。
- 上下文长度最高 100 万 token。
- 输入：文本、图像、文档和视频。
- 输出：文本。
- BF16 和 NVFP4 checkpoint。

NVIDIA 报告其在 [Hermes Bench](https://portal.nousresearch.com/bench) 上得 63.44%，在 LangChain agent 评估上得 87.05%，在 CharXiv 图表推理基准上得 80.8%。（[技术报告](https://research.nvidia.com/labs/nemotron/files/NVIDIA-Nemotron-3.5-Super-and-Lightning-Technical-Report.pdf)）

### 模型架构

Nemotron 3.5 Super VL 采用 Mamba-Transformer 混合 MoE 架构，将 Mamba-2、注意力与专家层交错排布。稀疏路由让每个 token 只激活 1200 亿参数中的 120 亿，因此单 token 的计算量相当于一个小得多的模型，而 GPU 显存仍要容纳全部权重。Mamba-2 层在生成期间携带大小恒定的状态，其内存不会像 KV cache 那样随序列长度增长，从而让长上下文的成本可控。一个递归共享的多 token 预测（MTP）头支持原生投机解码。

### 使用场景

Nemotron 3.5 Super VL 支持把推理与视觉理解结合的 agent 工作流：

- **编码：** 测试并验证代码、分析错误、推荐修复方案。
- **Web 研究：** 对搜索工具返回的来源进行交叉比对和核实。
- **文档智能：** 读取表格、图表和页面版式以生成摘要。
- **网络安全：** 识别漏洞并分诊威胁。
- **视频理解：** 搜索、内容、审核与事件分析。

Nemotron 3.5 Super VL 通过 NVIDIA 参考实现、cookbook 和 [NVIDIA Agent Toolkit](https://blogs.nvidia.com/blog/nvidia-agent-toolkit-open-models-tools-skills-secure-runtime-ai-agents/) 与主流开放 agent 框架及编排系统集成。支持框架的完整列表见 [NVIDIA 开发者博客](https://developer.nvidia.com/blog/nvidia-nemotron-3-5-super-vl-powers-specialized-agents-with-multimodal-reasoning/)。

## 在 AWS 上部署

本节概述架构、验证和性能评估的方法。在 [aws-do-eks](https://bit.ly/do-eks) 项目中提供了于 AWS 上部署 Nemotron 3.5 Super VL 和 Nemotron 3 Ultra 的详细[演练](https://github.com/aws-samples/aws-do-eks/tree/main/Container-Root/eks/deployment/inference/agentic-ai/nemotron)，内容包括前置条件、集群创建、模型权重下载、部署、测试、基准测试与清理。同样的模式也可应用于 NVIDIA Nemotron 家族中的其他模型。

### 部署架构

[参考实现](https://bit.ly/aws-do-nemotron)可运行在标准 Amazon EKS、EKS Auto Mode 和 SageMaker HyperPod EKS 上。使用 EKS Auto Mode 时，AWS 会代你管理集群内的扩缩容、GPU 和 EFA 支持。用于模型部署的 Kubernetes manifests 对这几种编排方式都是相同的。每个集群都有一个承载 Kubernetes API 的控制平面，以及一个由 CPU 节点和 GPU 节点组成的数据平面。CPU 节点运行系统和测试 pod，GPU 节点运行模型。Amazon Elastic Container Registry (Amazon ECR) 存放容器镜像，一个共享的 Amazon FSx for Lustre 卷存放模型权重，Elastic Fabric Adapter (EFA) 连接各个 GPU 节点。下图展示的是一个标准 Amazon EKS 集群。

![带控制平面、CPU 与 GPU 数据平面节点、Amazon ECR、Amazon FSx for Lustre 以及 EFA 连接的标准 Amazon EKS 集群](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/28/ML-21105-1.png)

图 1：用于服务 NVIDIA Nemotron 模型的标准 Amazon EKS 集群架构

NVIDIA Dynamo 可以聚合方式在单个节点上服务该模型，也可以分离方式把 prefill 和 decode 放在不同节点上。对于视觉语言模型，图像/视频编码阶段还可以额外以分离方式运行在其专属节点上。

## 验证与性能

该架构已在 p6-b200.48xlarge（8 x NVIDIA B200 GPU）和 p5en.48xlarge（8 x NVIDIA H200 GPU）两种实例上完成验证。你可以用 NVIDIA Collective Communications Library (NCCL) 的 all-reduce 微基准来验证集群及其网络。

![NCCL all-reduce 测试期间显示 GPU 全部利用率与 EFA 适配器流量的仪表盘](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/28/ML-21105-2.png)

图 2：NCCL all-reduce 验证测试期间的 GPU 与 EFA 利用率

在 NCCL 测试运行时看到所有 GPU 都有利用率、所有 EFA 适配器都有流量，即可验证集群正按预期工作。

你可以用 [NVIDIA aiperf](https://github.com/ai-dynamo/aiperf) 工具度量集群上已部署模型的性能。

![aiperf 输出窗格展示已部署模型的首 token 时间、token 间延迟与吞吐量指标](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/28/ML-21105-3.png)

图 3：已部署模型的 aiperf 性能指标

aiperf 左上窗格的输出展示了关键性能指标（KPI），如首 token 时间（TTFT）、token 间延迟（ITL）以及以每秒 token 数（TPS）计的吞吐量。通过在不同并发级别上做这些测量，我们可以研究延迟和吞吐量如何依赖并发请求数。这些信息对于审慎规划容量和模型部署拓扑至关重要。[aws-do-eks container](https://gallery.ecr.aws/hpc-cloud/aws-do-eks) 提供了自动化能力，可以用单条命令可视化 GPU 与 EFA 利用率、运行 aiperf 和并发扫描。

![并发扫描图，对比各并发级别下聚合部署与分离部署的 TTFT 和 ITL](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/28/ML-21105-4.png)

图 4：对比聚合部署与分离部署的并发扫描

上面的并发扫描图显示，Nemotron 3.5 Super VL 的推理在双节点的聚合部署与分离部署之间对比时，TTFT 更低，ITL 大致相同。

这样的图表在制定部署决策时很有用。把延迟预算画成水平线，例如 TTFT 低于 600 ms（约 1 秒）、每 token 的 ITL 低于 100 ms。两条线之下的最右侧点，就是该拓扑的单个副本在服务等级目标（SLO）内可服务的吞吐量，这里是 c32，约每秒 320 token。规划容量时，用你的目标每秒 token 数除以这个单副本吞吐量，得出需要部署的 prefill-decode 配对数。在做出变更（精度、TP/PP 形态、聚合还是分离、新的 Dynamo 或 vLLM 版本）后重跑同一次扫描，就能立即看清权衡。曲线向右下方移动就是胜利。由于 TTFT 和 ITL 是分开绘制的，它还能告诉你该扩哪一侧：ITL 上升说明要增加 decode 容量，TTFT 上升说明要增加 prefill 容量。
