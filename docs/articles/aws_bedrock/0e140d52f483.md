# 使用 Amazon Nova Embeddings 构建智能音频搜索：深入探究语义音频理解

如果你想增强内容理解和搜索能力，音频嵌入提供了一个强大的解决方案。在本文中，你将学习如何使用 [Amazon Nova Multimodal Embeddings](https://aws.amazon.com/ai/generative-ai/nova/) 将音频内容转换为可搜索的智能数据，这些数据能够捕捉音调、情感、音乐特征和环境声音等声学特性。

在这些音频库中查找特定内容带来了真正的技术挑战。传统搜索方法，如人工转录、元数据标记和语音转文本转换，擅长捕捉和搜索口语内容。然而，这些基于文本的方法关注的是语言内容，而不是音调、情感、音乐特征和环境声音等声学属性。音频嵌入弥补了这一空白。它们将音频表示为高维空间中的密集数值向量，同时编码语义和声学属性。这些表示使你能够使用自然语言查询进行语义搜索、匹配听起来相似的音频，并根据声音本身而非仅仅元数据标签自动分类内容。Amazon Nova Multimodal Embeddings 于 2025 年 10 月 28 日发布，是 Amazon Bedrock 中提供的一个多模态嵌入模型 [1]。它是统一的嵌入模型，通过单一模型支持文本、文档、图像、视频和音频，实现准确的跨模态检索。

本文将带你理解音频嵌入、实现 Amazon Nova Multimodal Embeddings，并为音频内容构建一个实用的搜索系统。你将了解嵌入如何将音频表示为向量，探索 Amazon Nova 的技术能力，并查看用于索引和查询音频库的实操代码示例。读完本文后，你将掌握部署生产级音频搜索能力所需的知识。

## 理解音频嵌入：核心概念

### 音频内容的向量表示

可以把音频嵌入想象成声音的坐标系。正如 GPS 坐标能精确定位地球上的位置，嵌入将音频内容映射到高维空间中的特定点。Amazon Nova Multimodal Embeddings 提供四种维度选项：3,072（默认）、1,024、384 或 256 [1]。每个嵌入都是一个 float32 数组。各个维度编码声学和语义特征——节奏、音高、音色、情感基调和语义——所有这些都是在训练过程中通过模型的神经网络架构学习得到的。Amazon Nova 使用 Matryoshka Representation Learning（MRL，套娃表示学习）技术，以分层方式组织嵌入 [1]。可以把 MRL 想象成俄罗斯套娃。一个 3,072 维的嵌入包含全部信息，但你可以只提取前 256 维，仍然能获得准确的结果。只需生成一次嵌入，然后选择在准确性和存储成本之间取得平衡的尺寸。尝试不同维度时无需重新处理音频——这种分层结构允许你截断到所需尺寸。

**如何衡量相似度：** 当你想找到相似的音频时，可以计算两个嵌入 v₁ 和 v₂ 之间的余弦相似度 [1]：

`similarity = (v₁ · v₂) / (||v₁|| × ||v₂||)`

余弦相似度衡量向量之间的夹角，取值范围为 -1 到 1。越接近 1 的值表示语义相似度越高。当你把嵌入存储在向量数据库中时，它使用距离度量（距离 = 1 – 相似度）来执行 k 近邻（k-NN）搜索，为你的查询检索出最相似的前 k 个嵌入。

**真实案例：** 假设你有两个音频片段——“一把小提琴演奏旋律”和“一把大提琴演奏相似的旋律”——它们生成嵌入 v₁ 和 v₂。如果它们的余弦相似度为 0.87，它们就会在向量空间中聚集在一起，表明具有很强的声学和语义相关性。而另一个不同的音频片段，如“带鼓点的摇滚乐”，生成的 v₃ 与 v₁ 的余弦相似度为 0.23，在嵌入空间中相距很远。

### 音频处理架构与模态

**理解端到端工作流：** 在深入技术细节之前，我们先来看看音频嵌入在实践中是如何工作的。主要有两种工作流：

**数据摄取与索引流程：** 在摄取阶段，你批量处理音频库。将音频文件上传到 Amazon S3，然后使用异步 API 生成嵌入。对于较长的音频文件（超过 30 秒），模型会自动将其切分为更小的片段，并附带时间元数据。你将这些嵌入连同文件名、时长和流派等元数据一起存储在向量数据库中。整个音频库只需执行一次这样的处理。

**运行时搜索流程：** 当用户搜索时，你使用同步 API 为其查询生成嵌入——查询可以是“欢快的爵士钢琴”这样的文本，也可以是另一个音频片段。由于查询较短，且用户期望快速得到结果，同步 API 提供低延迟响应。向量数据库执行 k-NN 搜索以找到最相似的音频嵌入，并返回带有相关元数据的结果。整个搜索在毫秒级内完成。

当你提交纯音频输入时，时间卷积网络或基于 Transformer 的架构会分析声学信号中的频谱-时间模式。Amazon Nova 不直接处理原始波形，而是基于梅尔频谱图或学习到的音频特征等音频表示进行操作，从而能够高效处理高采样率音频 [1]。音频是需要时间上下文的序列数据。你的音频片段（最长 30 秒）会经过具有时间感受野的架构，捕捉跨时间的声学模式 [1]。这种方法能够捕捉节奏、韵律、语调以及跨越数秒的远距离声学依赖关系——完整保留音频内容的丰富性。

### API 操作与请求结构

**何时使用同步嵌入生成：** 当实时应用需要嵌入且延迟很重要时，使用 `invoke_model` API 进行运行时搜索 [1]。例如，当用户提交搜索查询时，查询文本很短，你希望提供快速的用户体验——同步 API 非常适合这种情况：

```
import boto3
import json
 
# Create the Bedrock Runtime client.
bedrock_runtime = boto3.client("bedrock-runtime", region_name="us-east-1")
 
# Define the request body for a search query.
request_body = {
    "taskType": "SINGLE_EMBEDDING",  # Use for single items
    "singleEmbeddingParams": {
        "embeddingPurpose": "GENERIC_RETRIEVAL",  # Use GENERIC_RETRIEVAL for queries
        "embeddingDimension": 1024,  # Choose dimension size
        "text": {
            "truncationMode": "END",  # How to handle long inputs
            "value": "jazz piano music"  # Your search query
        }
    }
}
 
# Invoke the Nova Embeddings model.
response = bedrock_runtime.invoke_model(
    body=json.dumps(request_body),
    modelId="amazon.nova-2-multimodal-embeddings-v1:0",
    contentType="application/json"
)
 
# Extract the embedding from response.
response_body = json.loads(response["body"].read())
embedding = response_body["embeddings"][0]["embedding"]  # float32 array
```

**理解请求参数：**

- **taskType**：为单个项目选择 `SINGLE_EMBEDDING`，为分块处理选择 `SEGMENTED_EMBEDDING` [1, 2]
- **embeddingPurpose**：针对你的用例优化嵌入——`GENERIC_INDEX` 用于索引内容，`GENERIC_RETRIEVAL` 用于查询，`DOCUMENT_RETRIEVAL` 用于文档搜索 [1]
- **embeddingDimension**：你选择的输出维度（3072、1024、384、256）[1]
- **truncationMode**：如何处理超出上下文长度的输入——`END` 在末尾截断，START 在开头截断 [1]

**返回内容：** API 返回一个包含嵌入的 JSON 对象：

```
{
  "embeddings": [
    {
      "embedding": [0.123, -0.456, 0.789, ...],  // float32 array
      "embeddingLength": 1024
    }
  ]
}
```

**何时使用异步处理：** Amazon Nova Multimodal Embeddings 支持两种处理大量内容的方式：异步 API 和批处理 API。了解何时使用哪种方式有助于优化工作流。

**异步 API：** 当你需要处理超出同步 API 限制的单个大型音频或视频文件时，使用 `start_async_invoke` API [1]。这非常适合：

- 处理单个大文件（数小时的录音、完整长度的视频）
- 需要分段的超过 30 秒的文件
- 需要在数小时内（而非立即）获得结果时

```
response = bedrock_runtime.start_async_invoke(
    modelId="amazon.nova-2-multimodal-embeddings-v1:0",
    modelInput=model_input,
    outputDataConfig={
        "s3OutputDataConfig": {"s3Uri": "s3://amzn-s3-demo-bucket/output/"}
    }
)
invocation_arn = response["invocationArn"]
# Poll job status
job = bedrock_runtime.get_async_invoke(invocationArn=invocation_arn)
status = job["status"]  # "InProgress" | "Completed" | "Failed"
```

作业完成后，会以 JSONL 格式（每行一个 JSON 对象）将输出写入 Amazon S3。对于 AUDIO_VIDEO_COMBINED 模式，输出位于 `embedding-audio-video.jsonl` 中 [1]。

**批处理 API：** 当你需要在单个作业中处理数千个音频文件时，使用批处理推理 API [3]。

这非常适合：

- 批量处理整个音频库（从数千到数百万个文件）
- 通过批处理定价实现成本优化
- 可以等待 24-48 小时的非时间敏感型索引操作
- 高效处理大量中小型文件

批处理 API 为大规模操作提供更好的成本效率，并自动处理作业管理。你提交一个包含所有输入文件的清单文件，服务会并行处理它们，并将结果写入 S3。

**在异步与批处理之间选择：**

- **单个大文件或需要实时分段？** → 使用异步 API
- **需要批量处理数千个文件？** → 使用批处理 API
- **需要在数小时内获得结果？** → 使用异步 API
- **为了节省成本可以等待 24-48 小时？** → 使用批处理 API

有关批处理推理的更多信息，请参阅 [Amazon Bedrock 批处理推理文档](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference-supported.html)。[3]

### 分段与时间元数据

**为什么需要分段：** 如果音频文件超过 30 秒，就需要对其进行分段 [1]。想象你有一个 2 小时的播客，想找到主持人讨论 AI 的那个特定 30 秒片段——分段使这成为可能。

你可以通过 `segmentationConfig` 参数控制分块：

```
"segmentationConfig": {
    "durationSeconds": 15  # Generate one embedding every 15 seconds
}
This configuration processes a 5-minute audio file (300 seconds) into 20 segments (300 ÷ 15 = 20), generating 20 embeddings [1]. Each segment receives temporal metadata marking its position in your original file.
```

**理解分段输出：** 异步 API 将带有时间元数据的分段嵌入写入 JSONL [1]：

```
{"startTime": 0.0, "endTime": 15.0, "embedding": [...]}
{"startTime": 15.0, "endTime": 30.0, "embedding": [...]}
{"startTime": 30.0, "endTime": 45.0, "embedding": [...]}
```

**如何解析分段输出：**

```
import json
from boto3 import client
s3 = client("s3", region_name="us-east-1")
# Read JSONL file from S3
response = s3.get_object(Bucket="bucket", Key="output/embedding-audio-video.jsonl")
content = response['Body'].read().decode('utf-8')
segments = []
for line in content.strip().split('\n'):
    if line:
        segment = json.loads(line)
        segments.append({
            'start': segment['startTime'],
            'end': segment['endTime'],
            'embedding': segment['embedding'],
            'duration': segment['endTime'] - segment['startTime']
        })
print(f"Processed {len(segments)} segments")
print(f"First segment: {segments[0]['start']:.1f}s - {segments[0]['end']:.1f}s")
print(f"Embedding dimension: {len(segments[0]['embedding'])}")
```

**真实用例——时间搜索：** 你可以将分段嵌入及其时间元数据存储在向量数据库中。当有人搜索“客户投诉账单”时，你会检索到带有时间戳的特定 15 秒片段，从而精确导航到数小时通话录音中的相关时刻。无需收听整段录音。

### 向量存储与索引策略

**回顾架构：** 在第 2.2 节中，我们向你展示了端到端工作流图。现在我们将深入探讨 **Vector Database** 组件——在摄取阶段和运行时搜索阶段，嵌入都存放在这个存储层中。这是将已索引的音频嵌入与快速搜索查询连接起来的关键组件。

**理解存储需求：** 嵌入是 float32 数组，每个维度需要 4 字节。以下是所需空间：

- **3,072 维**：每个嵌入 12,288 字节（12 KB）
- **1,024 维**：每个嵌入 4,096 字节（4 KB）
- **384 维**：每个嵌入 1,536 字节（1.5 KB）
- **256 维**：每个嵌入 1,024 字节（1 KB）

**计算示例：** 对于 100 万个使用 1,024 维嵌入的音频片段，你需要 4 GB 的向量存储空间（不含元数据和索引结构）。

**选择维度尺寸：** 更大的维度提供更详细的表示，但需要更多存储和计算。较小的维度在检索性能和资源效率之间提供了实用的平衡。从 1,024 维开始——它能为大多数应用提供出色的准确性，同时保持成本可控。

**使用 Amazon S3 Vectors：** 你可以使用 Amazon S3 Vectors 存储和查询嵌入 [2]：

```
s3vectors = boto3.client("s3vectors", region_name="us-east-1")
# Create vector index
s3vectors.create_index(
    vectorBucketName="audio-vectors",
    indexName="audio-embeddings",
    dimension=1024,
    dataType="float32",
    distanceMetric="cosine"
)
# Store embedding with metadata
s3vectors.put_vectors(
    vectorBucketName="audio-vectors",
    indexName="audio-embeddings",
    vectors=[{
        "key": "audio:track_12345",
        "data": {"float32": embedding},
        "metadata": {
            "filename": "track_12345.mp3",
            "duration": 180.5,

        }

```

**元数据如何增强搜索：** 元数据属性与嵌入协同工作，提供更丰富的搜索结果。当你从向量数据库检索结果时，元数据可帮助你筛选、排序并向用户展示信息。例如，genre 字段可让你只筛选爵士乐录音，duration 帮助你找到特定长度范围内的曲目，filename 提供实际音频文件的路径以供播放。`upload_date` 可帮助你优先展示近期内容或跟踪数据新鲜度。语义相似度（来自嵌入）与结构化元数据的这种结合，创造了强大的搜索体验。

**查询向量：** k-NN 搜索检索最相似的前 k 个向量 [2]：

    queryVector={"float32": query_embedding},

for result in response["vectors"]:

### **批处理优化与生产模式**

**为什么批处理很重要：** 当你处理多个音频文件时，批处理推理通过减少网络延迟开销来提高吞吐量 [1]。你不必为每个文件单独发起 API 调用，而是可以更高效地处理它们。

**批处理模式示例：**

```
texts = ["jazz music", "rock music", "classical music"]
vectors = []
for text in texts:
    response = bedrock_runtime.invoke_model(
        body=json.dumps({
            "taskType": "SINGLE_EMBEDDING",
            "singleEmbeddingParams": {
                "embeddingDimension": 1024,
                "text": {"truncationMode": "END", "value": text}
            }
        }),
        modelId="amazon.nova-2-multimodal-embeddings-v1:0",
        contentType="application/json"
    )
    embedding = json.loads(response["body"].read())["embeddings"][0]["embedding"]
    vectors.append(embedding)
# Batch write to vector store
s3vectors.put_vectors(
    vectorBucketName="audio-vectors",
    indexName="audio-embeddings",
    vectors=[
        {"key": f"text:{text}", "data": {"float32": emb}}
        for text, emb in zip(texts, vectors)
    ]
)
```

**多语言支持：** 该模型支持 200 多种语言的文本输入 [1]。这支持强大的跨模态搜索场景：你的客户可以用西班牙语搜索以英语索引的音频内容，反之亦然。嵌入能够捕捉跨语言的语义。

## Amazon Nova 音频多模态嵌入深度解析

### 技术规格

**模型架构：** Amazon Nova Multimodal Embeddings 构建在一个基础模型之上，该模型经过训练，能够在统一的嵌入空间中理解不同模态（文本、图像、文档、视频和音频）之间的关系。

**灵活的嵌入维度：** 你可以选择四种输出维度：3,072、1,024、384 和 256。更大的维度提供更详细的表示，但需要更多存储和计算。较小的维度在检索性能和资源效率之间提供了实用的平衡。这种灵活性帮助你针对特定应用和成本要求进行优化。

**媒体处理能力：** 对于视频和音频输入，模型支持最长 30 秒的片段，并自动对更长文件进行分段 [1]。当你处理大型媒体文件时，这种分段能力尤其有用——模型会将它们拆分为易于管理的片段，并为每个片段创建嵌入。输出包含带时间元数据的视频和音频文件嵌入。

**API 灵活性：** 你可以通过同步和异步 API 访问该模型。在延迟重要的查询场景使用同步 API。在可以容忍较长处理时间的数据摄取和索引场景使用异步 API。异步 API 支持对文本、音频和视频文件进行批量分段/分块。分段是指将长文件拆分为更小的块，每块都会创建一个独特的嵌入，从而实现细粒度且更准确的检索。

**输入方式：** 你可以通过指定 S3 URI，或以 base64 编码内联传入要嵌入的内容。这使你在将嵌入集成到工作流时具有灵活性。

**工作流的工作方式：**

- 使用 Amazon Nova Multimodal Embeddings 为视频或音频片段生成嵌入
- 将嵌入存储在向量数据库中
- 当最终用户搜索内容时，使用 Amazon Nova 为其搜索查询生成嵌入
- 你的应用比较搜索查询嵌入与已索引内容嵌入的相似度
- 你的应用根据相似度指标（如余弦相似度）检索与搜索查询最匹配的内容
- 向最终用户展示相应的内容

**支持的输入：** 用于生成嵌入的输入可以是文本、图像、文档图像、视频或音频形式。这些输入既包括你用来创建索引的项目，也包括最终用户的搜索查询。模型输出嵌入，你用它们检索与查询最匹配的资产并展示给最终用户。

**音频格式支持：** Amazon Nova Multimodal Embedding 目前支持 mp3、wav 和 ogg 作为输入格式。这些格式覆盖了从音乐到语音录音的大多数常见音频用例。

### 关键能力

**音频到音频搜索：** 在音频库中查找声学上相似的内容。例如，找到所有具有相似音乐特征或说话风格的录音。

**文本到音频搜索：** 使用自然语言查询检索相关音频片段。搜索“欢快的爵士钢琴”或“表达沮丧情绪的客户”，即可返回匹配的音频片段。

**跨模态检索：** 同时跨图像、音频、视频和文本进行搜索。这种统一方法意味着你可以用一个查询搜索整个内容库，而无需考虑格式。

**时间理解：** 模型能够识别音频中随时间发生的动作和事件。这使你能够搜索长录音中的特定时刻。

### 何时选择 Amazon Nova

Amazon Nova Multimodal Embeddings 专为需要可扩展性能、快速部署和最低运营开销的生产应用而设计。

**为何选择 Amazon Nova：**

- **上市速度**：数小时或数天内部署，而非数月
- **托管服务**：无需维护基础设施或训练模型
- **跨模态能力**：一个模型覆盖所有内容类型，并提供企业级部署支持
- **持续改进**：无需迁移工作即可受益于模型更新

**需要考虑的决策因素：**

- **规模要求**：你需要处理多少音频文件和查询
- **上市时间**：你多快需要一个可用的解决方案
- **专业能力储备**：你是否有工程团队来维护自定义模型
- **集成需求**：你是否需要与 AWS 服务无缝集成

**核心应用领域：** Amazon Nova Multimodal Embeddings 服务于广泛的、针对多模态 RAG、语义搜索和聚类优化的应用：

- **Agentic 检索增强生成（RAG）：** 你可以将 Amazon Nova Multimodal Embeddings 用于基于 RAG 的应用，模型在其中充当检索任务的嵌入模型。输入可以是文档中的文本、图像，或是将文字与信息图、视频和音频交织在一起的文档图像。通过嵌入，你可以从知识库中检索最相关的信息，并提供给 LLM 系统以改进响应。
- **语义搜索：** 你可以从文本、图像、文档图像、视频和音频生成嵌入，为存储在向量索引中的搜索应用提供动力。向量索引是一种专门的嵌入空间，可减少返回结果所需的比较次数。由于模型在嵌入中捕捉了用户查询的细微差别，它支持不依赖关键词匹配的高级搜索查询。你的用户可以搜索概念，而不只是精确的词语。
- **聚类：** 你可以使用 Amazon Nova Multimodal Embeddings 从文本、图像、文档图像、视频和音频生成嵌入。聚类算法可以基于距离或相似度将彼此接近的项目归为一组。例如，如果你从事媒体管理工作，希望按相似主题对媒体资产进行分类，就可以使用嵌入将相似资产聚集在一起，而无需为每个资产提供元数据。模型会自动理解内容相似度。

## 结论

在本文中，我们探讨了 Amazon Nova Multimodal Embeddings 如何超越传统的基于文本的方法，实现语义音频理解。通过将音频表示为同时捕捉声学和语义属性的高维向量，你可以构建能够理解音调、情感和上下文（而不只是口语内容）的搜索系统。我们介绍了构建音频搜索系统的端到端工作流，包括：- 使用同步和异步 API 生成嵌入- 对长音频文件进行分段并附带时间元数据- 将嵌入存储在向量数据库中- 执行 k-NN 搜索以检索相关音频片段。这种方法使你能够将大型音频库转换为可搜索的智能数据集，支持呼叫中心分析、媒体搜索和内容发现等用例。

在我们的实现中，我们选取了一个真实场景：对呼叫中心录音进行嵌入，并使用 Amazon Nova Multimodal Embeddings 模型使这些录音能够按情感和内容进行搜索。我们没有手动给通话打标签，而是使用诸如“找到一段说话人听起来很生气的通话”或“给我看一段关于账单问题的对话”这样的文本查询。它奏效了，能够按需提取出正确的音频片段。换句话说，我们免去了麻烦，将音频档案转变为可按基调和主题搜索的体验。对于想深入研究的读者，可以在最后一节查看我们链接的代码示例和片段。
