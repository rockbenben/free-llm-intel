# 用 OWASP Top 10 缓解措施为生成式 AI 助手加固安全

我们在客户评估生产用例时经常见到的一种[生成式 AI](https://aws.amazon.com/generative-ai/)用例，是由生成式 AI 驱动的助手。然而在它能够部署之前，通常还要进行生产就绪评估，其中涵盖了解安全态势、监控与日志、成本追踪、韧性等方面的关切。在这些生产就绪评估当中，优先级最高的通常是安全。如果存在无法清晰识别的安全风险，就无法着手处理，这会阻碍生成式 AI 应用的生产部署。

本文给出一个生成式 AI 助手应用的示例，演示如何使用 [OWASP Top 10 for Large Language Model Applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/) 评估其安全态势，以及如何针对常见威胁施加缓解措施。

## 生成式 AI 范围界定框架

首先要弄清你的生成式 AI 应用在“全托管”到“完全自建”这一谱系中处于哪个位置。使用 AWS 生成式 AI 范围界定框架，可以了解适用于你应用的安全控制在共享责任模型下的具体划分。例如，Scope 1“消费者应用”（如 PartyRock 或 ChatGPT）通常是对公众开放的应用，其中大部分应用内部安全由提供商负责和控制，你在安全方面的责任落在消费侧。与之相对的是 Scope 4/5 应用：你不仅要自己构建并保护生成式 AI 应用，还要负责微调和训练底层大语言模型（LLM）。Scope 4/5 应用所涉及的安全控制范围更广，从前端一直延伸到 LLM 模型安全。本文将聚焦 Scope 3 的生成式 AI 助手应用，这也是业界较常见的用例之一。

## LLM 的 OWASP Top 10

用 OWASP Top 10 来理解应用面临的威胁与缓解措施，是评估应用安全最常见的方式之一。[OWASP Top 10 for LLMs](https://genai.owasp.org/llm-top-10/) 把一个久经验证的框架应用到生成式 AI 应用上，帮助我们查明、理解并缓解生成式 AI 带来的新型威胁。

## 解决方案概览

我们先从一个典型生成式 AI 助手应用的逻辑架构入手，并在其上叠加 OWASP Top 10 的 LLM 威胁，如下图所示。

![逻辑解决方案图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/17/ml-16964-Logical-diagram.png)

在该架构中，终端用户的请求通常会经过以下组件：

- **认证层** – 该层验证连接到应用的用户确实是其所声称的身份。这通常通过某种身份提供商（IdP）能力实现，例如 Okta、[AWS IAM Identity Center](https://aws.amazon.com/iam/identity-center/) 或 [Amazon Cognito](https://aws.amazon.com/pm/cognito/)。
- **应用控制器** – 该层包含应用的大部分业务逻辑，负责决定如何处理传入的用户请求：生成 LLM prompt，并在 LLM 响应返回给用户之前对其进行处理。
- **LLM 与 LLM agent** – LLM 为助手提供核心的生成式 AI 能力。LLM agent 负责编排完成目标请求可能必需的一系列步骤。这些步骤可能同时涉及 LLM 的使用以及外部数据源和 API。
- **agent 插件控制器** – 该组件负责与外部数据源和 API 的 API 集成。该组件还保存着外部组件的逻辑名称（LLM agent 可能引用）与物理名称之间的映射。
- **RAG 数据存储** – 检索增强生成（RAG）数据存储通过数据连接器，从数据仓库、数据库以及其他软件即服务（SaaS）应用等多种数据源提供最新、精确且受访问控制的知识。

OWASP Top 10 的 LLM 风险映射到应用栈的各个层，凸显了从 UI 到后端系统的各类漏洞。在接下来的几节中，我们讨论每一层的风险，并给出一个在 AWS 上构建生成式 AI 助手应用的设计模式，用以缓解这些风险。

## 认证层（Amazon Cognito）

暴力破解攻击、会话劫持和拒绝服务（DoS）攻击等常见安全威胁都可能发生。为缓解这些风险，应实施多因素认证（MFA）、速率限制、安全的会话管理、会话自动超时以及定期轮换 token 等最佳实践。此外，部署 [AWS WAF](https://aws.amazon.com/waf/) 和分布式拒绝服务（DDoS）缓解等边缘安全措施，有助于拦截常见的 Web 攻击利用，并在攻击期间维持服务可用性。

在上述架构图中，AWS WAF 与 [Amazon API Gateway](https://aws.amazon.com/api-gateway) 集成，用于过滤入站流量，拦截非预期请求，保护应用免受 SQL 注入、跨站脚本（XSS）和 DoS 攻击等威胁。[AWS WAF Bot Control](https://docs.aws.amazon.com/waf/latest/developerguide/waf-bot-control.html) 进一步提升了安全性，提供对 bot 流量的可见性和控制，让管理员能够拦截不想要的 bot 或对其限速。借助 [AWS Firewall Manager](https://aws.amazon.com/firewall-manager/)，该功能可以跨多个账户集中管理，从而以一致且稳健的方式保护应用。

Amazon Cognito 通过提供用户认证与数据同步来补强这些防护。它同时支持用户池和身份池，可跨设备无缝管理用户身份，并能与第三方身份提供商集成。Amazon Cognito 提供[多项安全特性](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pool-settings-advanced-security.html)，包括 MFA、OAuth 2.0、OpenID Connect、安全的会话管理和基于风险的自适应认证，通过评估登录请求是否存在可疑活动，并以 MFA 或阻止登录等额外安全措施作出响应，帮助防范未经授权的访问。Amazon Cognito 还强制执行[防止密码重用](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pool-settings-advanced-security-password-reuse.html)，进一步防范凭证被泄露带来的风险。

[AWS Shield Advanced](https://aws.amazon.com/shield/) 提供针对复杂 DDoS 攻击的增强防护，从而增加了一层额外的防御。Shield Advanced 与 AWS WAF 集成，提供全面的边界防护，通过定制化检测和基于健康状态的评估来增强对攻击的响应能力。它还提供来自 AWS Shield Response Team 的全天候支持，并包含 DDoS 成本保护，使应用保持安全且具成本效益。Shield Advanced 与 AWS WAF 共同构成一个安全框架，在维持可用性的同时保护应用免受各类威胁。

这一全面的安全设置应对了 LLM10:2025 Unbound Consumption 和 LLM02:2025 Sensitive Information Disclosure，确保应用既具韧性又安全。

## 应用控制器层（LLM 编排器 Lambda 函数）

应用控制器层通常容易受到 LLM01:2025 Prompt Injection、LLM05:2025 Improper Output Handling 和 LLM 02:2025 Sensitive Information Disclosure 等风险的影响。外部方可能频繁尝试利用该层，通过构造非预期输入来操纵 LLM，使其可能泄露敏感信息或危及下游系统。

在物理架构图中，应用控制器就是 LLM 编排器 [AWS Lambda](https://aws.amazon.com/lambda) 函数。它通过从 API Gateway 提取事件 payload，并同时执行语法校验和语义校验，来实现严格的输入验证。通过对输入进行清洗、应用关键词允许列表与拒绝列表，以及按预定义格式或模式校验输入，该 Lambda 函数有助于防范 LLM01:2025 Prompt Injection 攻击。此外，通过把 user_id 向下游传递，它使下游应用组件能够缓解敏感信息泄露风险，从而应对与 LLM02:2025 Sensitive Information Disclosure 相关的关切。

[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 通过过滤和拦截敏感内容提供额外一层保护，例如个人可识别信息（PII）以及由 regex 模式定义的其他自定义敏感数据。Guardrails 还可配置为检测并拦截攻击性语言、竞争对手名称或其他不良用语，确保输入和输出都安全。你还可以用 guardrails 防范 LLM01:2025 Prompt Injection 攻击：在有害或具有操纵性的 prompt 到达 LLM 之前就检测并过滤掉它们，从而维护 prompt 的完整性。

安全的另一个关键方面是管理 LLM 输出。由于 LLM 可能生成包含可执行代码（如 JavaScript 或 Markdown）的内容，如果这些内容处理不当，就会存在 XSS 攻击风险。为缓解该风险，应施加输出编码技术，例如 HTML 实体编码或 JavaScript 转义，在内容呈现给用户之前中和任何潜在有害内容。这种方法应对的是 LLM05:2025 Improper Output Handling 风险。

实施 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 的 prompt 管理与版本控制，可以在维持应用整体安全的同时持续改进用户体验。通过谨慎管理 prompt 的变更及其处理方式，你可以在增强功能的同时不引入新的漏洞，并缓解 LLM01:2025 Prompt Injection 攻击。

把 LLM 当作不受信任的用户来对待，并对某些操作施加 human-in-the-loop（人在回路）流程，是降低未经授权或非预期操作发生可能性的策略。

## LLM 与 LLM agent 层（Amazon Bedrock LLM）

LLM 与 LLM agent 层经常处理与 LLM 的交互，面临 LLM10: Unbounded Consumption、LLM05:2025 Improper Output Handling 和 LLM02:2025 Sensitive Information Disclosure 等风险。

DoS 攻击可以用大量资源密集型请求压垮 LLM，在推高成本的同时降低整体服务质量。在与 Amazon Bedrock 托管的 LLM 交互时，设置输入请求最大长度等请求参数，可以把 LLM 资源耗尽的风险降到最低。此外，Amazon Bedrock agent 为完成客户意图所能排队的动作数量与动作总数都有硬性上限，这限定了对 LLM 响应做出反应的系统中动作的数量，避免不必要的循环或可能耗尽 LLM 资源的密集任务。

不当的输出处理会导致远程代码执行、跨站脚本、服务端请求伪造（SSRF）和权限提升等漏洞。LLM 生成的输出在向下游发送之前缺乏充分的校验与管理，可能间接授予对额外功能的访问，从而实际上让这些漏洞得以被利用。为缓解该风险，应把模型当作任何其他用户来对待，并对 LLM 生成的响应施加校验。借助 Amazon Bedrock Guardrails 的各类过滤器（例如带可配置阈值的内容过滤器），这一过程得以简化：在有害内容被其他后端系统进一步下游处理之前将其过滤掉，并防范 prompt 攻击。Guardrails 会自动评估用户输入和模型响应，以检测并帮助阻止落入受限类别的内容。

[Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 执行多步骤任务，并与 AWS 原生服务和第三方服务安全集成，以降低不安全输出处理、过度代理权限和敏感信息泄露的风险。在架构图中，agents 下的 action group Lambda 函数用于对所有输出文本进行编码，使其自动无法被 JavaScript 或 Markdown 执行。此外，action group Lambda 函数会在 agents 执行的每一步解析 LLM 的每个输出，并据此控制输出的处理方式，确保它们在进一步处理之前是安全的。

敏感信息泄露是 LLM 的一项风险，因为恶意的 prompt 工程可能导致 LLM 在响应中意外泄露非预期的细节。这可能造成隐私和保密性方面的违规。为缓解该问题，应通过 Amazon Bedrock Guardrails 中的内容过滤器实施数据清洗实践。

此外，实施基于 user_id 的自定义数据过滤策略以及严格的用户访问策略。Amazon Bedrock Guardrails 有助于过滤被视为敏感的内容，而 Amazon Bedrock Agents 则允许你在预处理和后处理模板中实现自定义逻辑来剥离任何非预期信息，从而进一步降低敏感信息泄露的风险。如果你已为 LLM 启用模型调用日志，或在应用中实现了自定义日志逻辑以在 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch) 中记录 LLM 的输入和输出，那么 CloudWatch Log 数据保护等措施对于掩蔽 CloudWatch 日志中识别出的敏感信息非常重要，可进一步缓解敏感信息泄露的风险。

## agent 插件控制器层（action group Lambda 函数）

agent 插件控制器经常与内部和外部服务集成，并对内部与外部数据源以及第三方 API 施加自定义授权。在这一层，LLM08:2025 Vector & Embedding Weaknesses 和 LLM06:2025 Excessive Agency 的风险是实际存在的。不受信任或未经核实的第三方插件可能以非预期代码的形式引入后门或漏洞。

对 action group Lambda 函数的 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色[应用最小权限访问](https://aws.amazon.com/blogs/security/techniques-for-writing-least-privilege-iam-policies)，该函数负责与面向外部系统的插件集成交互，这有助于缓解 LLM06:2025 Excessive Agency 和 LLM08:2025 Vector & Embedding Weaknesses 的风险。物理架构图中对此有所体现；agent 插件层的 Lambda 函数关联了一个最小权限 IAM 角色，用于安全访问其他内部 AWS 服务并与之对接。

此外，在确定用户身份之后，通过把 `user_id` 传递到 agent 插件层等下游层来施加用户级访问控制，从而限制数据平面。虽然 `user_id` 参数可以在 agent 插件控制器 Lambda 函数中用于自定义授权逻辑，但它的主要用途是为第三方插件实现细粒度的访问控制。应用所有者需要在 action group Lambda 函数内实现自定义授权逻辑，其中的 `user_id` 参数可以与预定义规则组合使用，以对第三方 API 和插件施加适当级别的访问权限。这种方法把确定性的访问控制包裹在非确定性的 LLM 之外，并对哪些用户可以访问和执行特定第三方插件实现了精细的访问控制。

把基于 `user_id` 的数据授权，与 action group Lambda 函数上的最小权限 IAM 角色结合起来，通常可以把 LLM08:2025 Vector & Embedding Weaknesses 和 LLM06:2025 Excessive Agency 的风险降到最低。

## RAG 数据存储层

RAG 数据存储负责从各类一方和第三方数据源中安全地检索最新、精确且受用户访问控制的知识。默认情况下，Amazon Bedrock 使用 AWS 托管密钥加密所有与知识库相关的数据。你也可以选择使用客户托管密钥。在为知识库设置数据摄取作业时，你还可以使用自定义的 [AWS Key Management Service](https://aws.amazon.com/kms)（AWS KMS）密钥加密该作业。

如果你决定为知识库使用 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 中的向量存储，Amazon Bedrock 可以把你选定的 KMS 密钥传递给它用于加密。此外，你还可以用 KMS 密钥加密那些通过查询知识库生成响应的会话。为促进安全通信，[Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 在与第三方向量存储交互时使用 TLS 加密，前提是该服务支持并允许传输中的 TLS 加密。

在用户访问控制方面，Amazon Bedrock Knowledge Bases 使用过滤器来管理权限。你可以利用元数据和过滤特性，在知识库之上构建分段的访问解决方案。在运行时，你的应用必须对用户进行认证和授权，并把该用户信息包含在查询中，以维持准确的访问控制。为让访问控制保持更新，你应定期重新同步数据，以反映权限的任何变化。此外，组可以存储为可过滤的属性，进一步细化访问控制。

这种方法有助于缓解 LLM02:2025 Sensitive Information Disclosure 和 LLM08:2025 Vector & Embedding Weaknesses 的风险，帮助确保只有获得授权的用户才能访问相关数据。

## 总结

本文讨论了如何使用 AWS Generative AI Security Scoping Matrix，从安全共享责任的角度对你的生成式 AI 应用进行分类。我们回顾了一个常见的生成式 AI 助手应用架构，使用 [OWASP Top 10 for LLMs](https://genai.owasp.org/llm-top-10/) 框架评估了其安全态势，并展示了如何借助 AWS 的服务控制与各项服务施加 OWASP Top 10 for LLMs 的威胁缓解措施，以强化你的生成式 AI 助手应用架构。如需进一步了解如何构建生成式 AI 应用，请参阅 [AWS Workshops for Bedrock](https://workshops.aws/card/bedrock)。
