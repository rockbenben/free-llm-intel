# 使用 Amazon SageMaker AI 通过 Amazon Nova 评估容器评估模型

本篇博客文章介绍 [Amazon SageMaker AI](https://aws.amazon.com/sagemaker/ai/) 中新增的 [Amazon Nova 模型评估](https://docs.aws.amazon.com/sagemaker/latest/dg/nova-model-evaluation.html) 功能。本次发布新增了自定义指标支持、基于 LLM 的偏好测试、对数概率捕获、元数据分析，以及面向大规模评估的多节点扩展能力。

新增功能包括：

- **自定义指标**使用自带指标（bring your own metrics，BYOM）函数，为你自己的用例控制评估标准。
- **Nova LLM-as-a-Judge** 通过成对 A/B 比较处理主观评估，报告胜/平/负比例与 Bradley-Terry 分数，并为每次判定给出解释。
- **token 级对数概率**揭示模型置信度，可用于校准与路由决策。
- **元数据透传**保留每行字段，无需额外处理即可按客户细分、领域、难度或优先级进行分析。
- **多节点执行**在保持聚合稳定的同时分散负载，让评估数据集从数千条扩展到数百万条样本。

在 [SageMaker AI](https://aws.amazon.com/sagemaker/ai/resources/) 中，团队可以用 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/) 里的 JSONL 文件定义模型评估，然后把它们作为 [SageMaker 训练作业](https://docs.aws.amazon.com/sagemaker/latest/dg/how-it-works-training.html) 执行，并可控地编排前置与后处理流程，结果以结构化 JSONL 交付，包含逐样本指标、聚合指标和详细元数据。团队随后可以把结果接入 [Amazon Athena](https://aws.amazon.com/athena/) 和 [AWS Glue](https://aws.amazon.com/glue/) 等分析工具，或直接路由到现有的可观测性栈中，且结果保持一致。

本文余下部分先介绍这些新功能，然后以 IT 支持工单分类为例，逐步演示如何搭建评估、运行 judge 实验、捕获并分析对数概率、使用元数据进行分析，以及配置多节点运行。

## 使用 Amazon SageMaker AI 进行模型评估的功能

在挑选要投入生产的模型时，恰当的评估方法要求测试多个模型，包括 SageMaker AI 中的定制版本。要高效地做到这一点，团队需要完全相同的测试条件，把同样的 prompt、指标和评估逻辑传给不同模型。这样才能确保分数差异反映的是模型表现，而不是评估方法。

在 SageMaker AI 中定制的 Amazon Nova 模型现在作为基础模型继承完整的评估基础设施，从而保证比较的公平性。结果以结构化 JSONL 落到 Amazon S3，可直接用 Athena 查询或路由到你的可观测性栈。下面讨论模型评估可用的一些新功能。

### 自带指标（BYOM）

标准指标未必总能满足你的特定要求。自定义指标功能借助 [AWS Lambda](https://aws.amazon.com/lambda/) 函数来处理数据预处理、输出后处理和指标计算。例如，客服机器人需要共情能力与品牌一致性指标；医疗助手可能需要临床准确性度量。有了自定义指标，你就可以测试对自己领域真正重要的东西。

在这一功能中，前置与后置处理函数封装在一个 Lambda 函数里：推理前用它处理数据，以规范化格式或注入上下文；模型响应之后再调用后置处理函数计算你的自定义指标。最后，结果按你选择的最小值、最大值、平均值或求和方式聚合，因此当不同测试样本的重要性各不相同时，灵活性更强。

### 多模态 LLM-as-a-judge 评估

LLM-as-a-judge 使用 Amazon Nova LLM-as-a-Judge 模型做响应比较，为文本以及多模态任务自动化偏好测试。系统采用成对评估：对每个 prompt，它比较基线响应与挑战者响应，并以前向和后向两种顺序各跑一遍，以检测位置偏差。输出包含 Bradley-Terry 概率（一个响应比另一个更受偏好的可能性），并附带 bootstrap 采样得到的置信区间，从而为偏好结果提供统计置信度。

Nova LLM-as-a-Judge 模型专门针对评判类评估任务做了定制。每次判定都包含自然语言理由，解释评判者为什么更偏好某个响应，从而帮助你做有针对性的改进，而不是盲目优化。Nova LLM-as-a-Judge 能评估支持工单分类这类复杂推理任务——在这类任务中，细微的理解比简单的关键词匹配更重要。

平局检测同样有价值，能识别出模型已经达到同等水平的情形。结合标准误差指标，你可以判断性能差异在统计上是否有意义，还是落在噪声范围内；在决定某次模型更新是否值得部署时，这一点很重要。

### 使用对数概率进行模型评估

对数概率显示模型对每个生成 token 的置信度，从而揭示关于模型不确定性与预测质量的洞见。对数概率支持校准研究、按置信度路由以及幻觉检测，作用超出基础准确率。token 级置信度有助于识别不确定的预测，让系统更可靠。

在 SageMaker AI 模型评估中使用 Nova 评估容器时，现在可以在推理过程中捕获 token 级对数概率，以支撑感知不确定性的评估流程。该功能与评估 pipeline 集成，为更高级的诊断能力打下基础。你可以把模型置信度与实际表现关联起来，基于不确定性阈值实现质量门禁，并在潜在问题影响生产系统之前就发现它们。要给评估配置加入对数概率捕获，只需添加 `top_logprobs` 参数：

```
# Add log probability capture to your evaluation configuration
inference:
  max_new_tokens: 2048
  temperature: 0
  top_logprobs: 10  # Captures top 10 log probabilities per token
```

与下一节讨论的元数据透传功能结合使用时，对数概率有助于跨不同数据分段和用例做分层置信度分析。这一组合提供对模型行为的细致洞见，让团队不仅知道模型在哪里失败，还能知道为什么失败、对预测有多自信，从而更好地掌控校准。

### 在使用模型评估时传递元数据信息

准备评估数据集时，自定义数据集现在支持元数据字段。元数据有助于跨不同模型和数据集比较结果。**metadata** 字段接受任意字符串，用于给输入数据和评估结果打标签、做分析。加入 **metadata** 字段后，JSONL 文件中每个数据点的整体 schema 如下：

```
{
  "query": "(Required) String containing the question or instruction that needs an answer",
  "response": "(Required) String containing the expected model output",
  "system": "(Optional) String containing the system prompt that sets the behavior, role, or personality of the AI model before it processes the query",
  "metadata": "(Optional) String containing metadata associated with the entry for tagging purposes."
}
```

### 启用多节点评估

评估容器支持多节点评估以加快处理速度。把 replicas 参数设为大于 1 的值即可启用多节点评估。

### 第 1 步：准备 prompt

对于我们的支持工单分类任务，我们不仅要评估模型是否识别出正确类别，还要评估它是否给出连贯的推理、是否遵守结构化输出格式，从而获得生产系统所需的完整视角。编写 prompt 时，我们将采用 [Nova 提示词最佳实践](https://docs.aws.amazon.com/nova/latest/userguide/prompting-text-understanding.html)。

**系统 prompt 设计：** 从 system prompt 入手，我们用一个聚焦的系统 prompt 确立模型的角色与期望行为：

```
You are an IT support specialist. Analyze the support ticket and classify it accurately based on the issue description and technical details.
```

这个 prompt 设定了明确的期望：模型应扮演领域专家，依据可见证据做判断，并把准确性放在首位。通过把任务框定为专家分析而非随意观察，我们鼓励更深入、更详细的回答。

**Query 结构**：query 模板同时要求分类与理由说明：

```
# Query template requests classification and reasoning
"What category does this support ticket belong to? Provide your reasoning based on the issue description."
```

明确要求给出推理很重要——它迫使模型把决策过程讲清楚，有助于在评估分类准确率的同时评估解释质量。这也对应现实中的要求：模型决策往往需要对利益相关方或监管合规而言是可解释的。

**结构化响应格式**：我们把期望输出定义为包含三个组成部分的 JSON：

```
{
  "class": "network_connectivity",
  "thought": "Based on the error message mentioning network timeout and intermittent connectivity issues, this appears to be a network infrastructure problem",
  "description": "Network connectivity issue requiring infrastructure team escalation"
}
```

这一结构支撑我们将在本文后面讨论的三维评估策略：

- **class** 字段 – 分类准确率指标（precision、recall、F1）
- **thought** 字段 – 推理连贯性评估
- **description** 字段 – 自然语言质量评估

通过把响应定义为可解析的 JSON，我们既能借助自定义 Lambda 函数实现指标自动计算，又能保留人类可读的模型决策解释。这一 prompt 架构把评估从简单的对/错分类，转变为对模型能力的完整评估。生产级 AI 系统需要准确、可解释，并在输出格式上可靠——我们的 prompt 设计明确检验了这三个维度。结构化格式还便于我们在后续步骤中使用元数据驱动的分层分析，届时可以把推理质量与置信度分数以及不同类别下的难度等级关联起来。

### 第 2 步：准备带元数据的评估数据集

这一步我们要为支持工单数据集加上元数据支持，以便跨不同类别与难度等级做分层分析。元数据透传功能会完整保留自定义字段，无需事后 join 即可做细致的性能分析。先来看一个示例数据集。

#### 带元数据的数据集 schema

在支持工单分类评估中，我们使用带结构化元数据的增强 `gen_qa` 格式：

```
{
  "system": "You are a support ticket classification expert. Analyze the ticket content and classify it accurately based on the issue type, urgency, and department that should handle it.",
  "query": "My laptop won't turn on at all. I've tried holding the power button, checking the charger connection, but there's no response. The LED indicators aren't lighting up either.",
  "response": "{\"class\": \"Hardware_Critical\", \"thought\": \"Complete device failure with no power response indicates a critical hardware issue\", \"description\": \"Critical hardware failure requiring urgent IT support\"}",
  "metadata": "{\"category\": \"support_ticket_classification\", \"difficulty\": \"easy\", \"domain\": \"IT_support\", \"priority\": \"critical\"}"
}
```

再深入看看：我们如何为每个评估样本自动生成结构化元数据？这一元数据增强过程会分析内容，对任务类型分类、评估难度等级并识别领域，为后续步骤的分层分析打下基础。通过把这些上下文信息直接嵌入数据集，我们帮助 Nova 评估 pipeline 完整保留这些洞见，从而无需复杂的后处理 join 就能理解模型在不同分段上的表现。

```
import json
from typing import List, Dict

def load_sample_dataset(file_path: str = 'sample_text_eval_dataset.jsonl') -> List[Dict]:
    """Load the sample dataset with metadata"""
    dataset = []
    with open(file_path, 'r') as f:
        for line in f:
            dataset.append(json.loads(line))
    return dataset
```

数据集完成元数据增强后，我们需要按 Nova 评估容器要求的 JSONL 格式导出。

下面的导出函数把我们准备好的、带内嵌元数据的样本整理好，使其可直接进入评估 pipeline，并保持 Amazon SageMaker 处理工作流所需的精确 schema 结构：

```
# Export for SageMaker Evaluation
def export_to_sagemaker_format(dataset: List[Dict], output_path: str = 'gen_qa.jsonl'):
    """Export dataset in format compatible with SageMaker """
    
    with open(output_path, 'w', encoding='utf-8') as f:
        for item in dataset:
            f.write(json.dumps(item, ensure_ascii=False) + '\n')
    
    print(f"Dataset exported: {len(dataset)} examples to {output_path}")

# Usage Example
dataset = load_sample_dataset('sample_text_eval_dataset.jsonl')
export_to_sagemaker_format(dataset)
```

### 第 3 步：准备自定义指标以评估自定义模型

在准备好数据并验证其符合所需 schema 之后，下一个重要步骤是编写评估指标代码，衡量自定义模型的表现。使用 Nova 评估容器和自带指标（BYOM）工作流，通过自定义指标与数据流掌控你的模型评估 pipeline。

#### BYOM 工作流简介

借助 BYOM 功能，你可以用完全可定制的预处理、后处理和指标能力，把模型评估工作流调整成贴合自身需求的样子。BYOM 让你掌控评估过程，帮助你按项目的独特需求微调并提升模型的性能指标。

#### 这个分类问题的关键任务

- 定义任务与指标：在这个用例中，模型评估需要三项任务：  **类别预测准确率**：用于评估模型在给定输入下预测正确类别的准确程度。为此我们使用 accuracy、precision、recall 和 F1 分数等标准指标来量化表现。**schema 遵循度**：其次，我们还要确保模型输出符合指定的 schema。这一步对保持与下游应用的一致性和兼容性很重要。为此我们使用校验技术来确认输出格式与所需 schema 一致。**思考过程连贯性**：再次，我们还要评估模型决策背后的连贯性与推理。这涉及分析模型的思考过程，以帮助验证预测在逻辑上是否成立。注意力机制、可解释性工具和模型解释等技术可以为理解模型的决策过程提供洞见。

用 BYOM 功能评估自定义模型需要构建一个 Lambda 函数。

- 在 Lambda 函数上配置自定义层。在 [GitHub release](https://github.com/aws/nova-custom-eval-sdk/releases) 中找到并下载预构建的 **nova-custom-eval-layer.zip** 文件。
- 使用以下命令上传自定义 Lambda 层：

```
# Upload custom lambda layer for Nova evaluation
aws lambda publish-layer-version \
    --layer-name nova-custom-eval-layer \
    --zip-file fileb://nova-custom-eval-layer.zip \
    --compatible-runtimes python3.12 python3.11 python3.10 python3.9
```

- 把已发布的层以及 `AWSLambdaPowertoolsPythonV3-python312-arm64`（或按 Python 版本与运行时版本兼容性选择的类似 AWS 层）添加到 Lambda 函数，确保所有必要依赖都已安装。
- 开发 Lambda 函数时，导入两个关键依赖：一个用于导入 preprocessor 和 postprocessor 装饰器，另一个用于构建 `lambda_handler`：

```
# Import required dependencies for Nova evaluation
from nova_custom_evaluation_sdk.processors.decorators import preprocess, postprocess
from nova_custom_evaluation_sdk.lambda_handler import build_lambda_handler
```

- 添加 preprocessor 与 postprocessor 逻辑。  **Preprocessor 逻辑：** 实现一些函数，在数据被传给推理服务器之前对其进行处理。这可以包括 prompt 改写或其他数据预处理步骤。pre-processor 期望输入一个事件字典（dict），即一系列键值对：  `event = { "process_type": "preprocess", "data": { "system": < passed in system prompt>, "prompt": < passed in user prompt >, "gold": <expected_answer> } }` 示例：  `@preprocess def preprocessor(event: dict, context) -> dict: data = event.get('data', {}) return { "statusCode": 200, "body": { "system": data.get("system"), "prompt": data.get("prompt", ""), "gold": data.get("gold", "") } }`  **Postprocessor 逻辑：** 实现处理推理结果的函数。这可以涉及解析字段、添加自定义校验或计算特定指标。postprocessor 期望输入一个事件 dict，格式如下：  `event = { "process_type": "postprocess", "data":{ "prompt": < the input prompt >, "inference_output": < the output from inference on custom or base model >, "gold": < the expected output > } }`
- 定义 Lambda handler，分别在推理之前和之后挂上 pre-processor 与 post-processor 逻辑。  `# Build Lambda handler lambda_handler = build_lambda_handler( preprocessor=preprocessor, postprocessor=postprocessor ) `

### 第 4 步：用自定义指标启动评估作业

既然已经构建好自定义处理器并写好了评估指标，你可以选择一个 recipe 并做必要调整，确保前面那套 BYOM 逻辑真正被执行。为此，先从公共仓库中选择 [bring your own data recipes](https://github.com/aws/sagemaker-hyperpod-recipes/blob/main/recipes_collection/recipes/evaluation/nova/nova_micro_p5_48xl_bring_your_own_dataset_eval.yaml)，并确认完成以下代码改动。

- 确认 recipe 中已加入 processor 键且内容正确：  `# Processor configuration in recipe processor: lambda_arn: arn:aws:lambda:<region>:<account_id>:function:<name> preprocessing: enabled: true postprocessing: enabled: true aggregation: average `   **lambda-arn**：负责预处理与后处理的客户 Lambda 函数的 Amazon Resource Name（ARN） **preprocessing**：是否加入自定义预处理操作 **post-processing**：是否加入自定义后处理操作 **aggregation**：可选的内置聚合函数。
 min、max、average 或 sum

### 第 5 步：用元数据与对数概率校准准确率

你也可以把对数概率作为推理配置项，以便进行基于 logit 的评估。为此可以在 recipe 的 inference 下传入 `top_logprobs`：

`top_logprobs` 表示在每个 token 位置返回的最可能 token 数量，每个 token 都附带对应的对数概率。该值必须是 0 到 20 之间的整数。logprobs 包含所考虑的候选输出 token，以及 message 内容中返回的每个输出 token 的对数概率。

```
# Log probability configuration in inference settings
inference:
  max_new_tokens: 2048 
  top_k: -1 
  top_p: 1.0 
  temperature: 0
  top_logprobs: 10  # Number of most likely tokens to return (0-20)
```

作业成功运行并拿到结果后，你可以在 `pred_logprobs` 字段下找到对数概率。该字段包含所考虑的候选输出 token，以及 message 内容中返回的每个输出 token 的对数概率。现在你可以用产生的 logit 为分类任务做校准。每个输出 token 的对数概率对校准很有用，可以据此调整预测，把这些概率当作置信度分数。

### 第 6 步：对低置信度预测做失败分析

用元数据和对数概率校准模型之后，我们现在可以识别并分析低置信度预测中的失败模式。这项分析帮助我们理解模型在何处吃力，并指导有针对性的改进。

#### 加载带对数概率的结果

接下来详细看看我们如何把推理输出与 Amazon Nova 评估 pipeline 提供的详细对数概率数据结合起来。这样就能把预测结果与 token 级不确定性信息合并，从而做感知置信度的失败分析。

通过对数概率生成置信度分数：把 logprobs 转成概率，并取分类响应中第一个 token 的分数。我们只用第一个 token，因为已知分类响应中后续 token 会与类别标签保持一致。这一步为下游质量门禁创造条件：可以把低置信度分数路由到人工复核，也能查看模型的不确定性以验证模型是否在“猜”，防止幻觉传到用户那里，同时还为后续的分层分析铺路。

```
def calculate_confidence_score(pred_logprobs_str, prediction_text="") -> tuple:
    """
    Calculate confidence score from log probabilities for the predicted class.
    
    Args:
        pred_logprobs_str (str): String representation of prediction logprobs (updated field name as of 10/23/25)
        prediction_text (str): The actual prediction text to extract class from
        
    Returns:
        tuple: (confidence, predicted_token, filtered_keys) - 
               confidence: The first token probability of the predicted class
               predicted_token: The predicted class name
               filtered_keys: List of tokens in the class name
    
    Note: Tokens may include SentencePiece prefix characters (▁) as of container update 10/23/25
    """
    if not pred_logprobs_str or pred_logprobs_str == '[]':
        return 0.0, "", []
    
    try:
        # Extract the predicted class from the prediction text
        predicted_class = ""
        if prediction_text:
            try:
                parsed = json.loads(prediction_text)
                predicted_class = str(parsed.get("class", "")).strip()
            except:
                predicted_class = ""
        
        if not predicted_class:
            return 0.0, "", []
        
        logprobs = ast.literal_eval(pred_logprobs_str)
        if not logprobs or len(logprobs) == 0:
            return 0.0, predicted_class, []
        
        # Build dictionary of all tokens and their probabilities
        token_probs = {}
        for token_prob_dict in logprobs[0]:
            if isinstance(token_prob_dict, dict) and token_prob_dict:
                max_key = max(token_prob_dict.items(), key=lambda x: x[1])[0]
                max_logprob = token_prob_dict[max_key]
                token_probs[max_key] = np.exp(max_logprob)
        
        # Find tokens that match the predicted class
        class_tokens = []
        class_probs = []
        
        # Split class name into potential tokens
        class_parts = re.split(r'[_\s]+', predicted_class)
        
        for token, prob in token_probs.items():
            # Strip SentencePiece prefix (▁) and other special characters for matching
            clean_token = re.sub(r'[^a-zA-Z0-9]', '', token)
            if clean_token:
                # Check if this token matches any part of the class name
                for part in class_parts:
                    if part and (clean_token.lower() == part.lower() or 
                                part.lower().startswith(clean_token.lower()) or
                                clean_token.lower().startswith(part.lower())):
                        class_tokens.append(clean_token)
                        class_probs.append(prob)
                        break
        
        # Use first token confidence (OpenAI's classification approach)
        if class_probs:
            confidence = float(class_probs[0])
        else:
            confidence = 0.0
        
        return confidence, predicted_class, class_tokens
    except Exception as e:
        print(f"Error processing log probs: {e}")
        return 0.0, "", []
```

#### 初步分析

接下来我们做分层失败分析，把置信度分数与元数据类别结合起来，找出具体的失败模式。这种多维分析揭示不同任务类型、难度等级和领域下的失败形态。分层失败分析系统地检查低置信度预测，识别具体模式与根因。它先筛出低于置信度阈值的预测，再跨元数据类别做多维分析，精确定位模型最吃力之处。我们还会分析失败预测的内容模式，寻找表达不确定性的措辞，并对错误类型分类（JSON 格式问题、长度问题或内容错误），最后产出洞见，明确告诉团队该修什么。

```
def analyze_low_confidence_failures(results_df: pd.DataFrame, confidence_threshold: float = 0.7, quality_threshold: float = 0.3) -> dict:
    """Perform comprehensive failure analysis"""
    
    # Make a copy to avoid modifying original
    df = results_df.copy()
    
    # Helper to extract prediction text
    def get_prediction_text(row):
        pred = row['predictions']
        
        # Handle string representation of array: "['text']" 
        if isinstance(pred, str):
            try:
                pred_list = ast.literal_eval(pred)
                if isinstance(pred_list, list) and len(pred_list) > 0:
                    return str(pred_list[0]).strip()
            except:
                pass
        
        # Handle actual array
        if isinstance(pred, (list, np.ndarray)) and len(pred) > 0:
            return str(pred[0]).strip()
        
        return str(pred).strip()
    
    # Apply the function with both logprobs and prediction text
    confidence_results = df.apply(
        lambda row: calculate_confidence_score(row['pred_logprobs'], get_prediction_text(row)), 
        axis=1
    )
    df[['confidence', 'predicted_token', 'filtered_keys']] = pd.DataFrame(
        list(confidence_results), 
        index=df.index,
        columns=['confidence', 'predicted_token', 'filtered_keys']
    )
    
    df['quality_score'] = df['metrics'].apply(
        lambda x: ast.literal_eval(x).get('f1', 0) if x else 0
    )
    df['is_correct'] = df['quality_score'] >= quality_threshold
    
    # Analyze low confidence predictions
    low_conf_df = df[df['confidence'] < confidence_threshold]
    
    # Also identify high confidence but low quality (overconfident errors)
    overconfident_df = df[(df['confidence'] >= confidence_threshold) & 
                          (df['quality_score'] < quality_threshold)]
    
    analysis_results = {
        'summary': {
            'total_predictions': len(df),
            'low_confidence_count': len(low_conf_df),
            'low_confidence_rate': len(low_conf_df) / len(df) if len(df) > 0 else 0,
            'overconfident_errors': len(overconfident_df),
            'overconfident_rate': len(overconfident_df) / len(df) if len(df) > 0 else 0,
            'avg_confidence': df['confidence'].mean(),
            'avg_quality': df['quality_score'].mean(),
            'overall_accuracy': df['is_correct'].mean()
        },
        'low_confidence_examples': [],
        'overconfident_examples': []
    }
    
    # Low confidence examples
    if len(low_conf_df) > 0:
        for idx, row in low_conf_df.iterrows():
            try:
                specifics = ast.literal_eval(row['specifics'])
                metadata = json.loads(specifics.get('metadata', '{}'))
                
                analysis_results['low_confidence_examples'].append({
                    'example': row['example'][:100] + '...' if len(row['example']) > 100 else row['example'],
                    'confidence': row['confidence'],
                    'quality_score': row['quality_score'],
                    'category': metadata.get('category', 'unknown'),
                    'difficulty': metadata.get('difficulty', 'unknown'),
                    'domain': metadata.get('domain', 'unknown')
                })
            except:
                pass
    
    # Overconfident errors
    if len(overconfident_df) > 0:
        for idx, row in overconfident_df.iterrows():
            try:
                specifics = ast.literal_eval(row['specifics'])
                metadata = json.loads(specifics.get('metadata', '{}'))
                
                analysis_results['overconfident_examples'].append({
                    'example': row['example'][:100] + '...' if len(row['example']) > 100 else row['example'],
                    'confidence': row['confidence'],
                    'quality_score': row['quality_score'],
                    'category': metadata.get('category', 'unknown'),
                    'difficulty': metadata.get('difficulty', 'unknown'),
                    'domain': metadata.get('domain', 'unknown')
                })
            except:
                pass
    
    return analysis_results
```

### 第 7 步：用多节点预测扩展评估

识别出失败模式后，我们需要把评估扩展到更大的数据集上做测试。Nova 评估容器现在支持多节点评估，只需在 recipe 中配置所需的副本数，就能提升吞吐与速度。

当评估 recipe 中指定的副本数大于 1 时，Nova 评估容器会自动处理多节点扩展。多节点扩展把负载分散到多个节点，同时保持相同的评估质量与元数据透传能力。

```
# Multi-node scaling configuration - just change one line!
run:
  name: support-ticket-eval-multinode
  model_name_or_path: amazon.nova-lite-v1:0:300k
  replicas: 4  # Now scales to 4 nodes automatically

evaluation:
  task: gen_qa
  strategy: gen_qa
  metric: all

inference:
  max_new_tokens: 2048
  temperature: 0
  top_logprobs: 10
```

#### 结果聚合与性能分析

Nova 评估容器会自动处理来自多个副本的结果聚合，但我们可以分析扩展效果，并把基于元数据的分析限定在分布式评估上。

多节点评估通过 `replicas` 参数使用 Nova 评估容器的内置能力，自动分散负载并聚合结果，同时保留所有基于元数据的分层分析能力。容器处理了分布式处理的复杂性，帮助团队通过增加副本数把评估从数千条扩展到数百万条样本。
