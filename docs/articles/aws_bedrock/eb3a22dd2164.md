## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 使用 Amazon Bedrock 和 LiteLLM 构建自助式 LLM 网关

开发人员希望人工智能编码助手只需最少的设置。借助大型语言模型 (LLM) 网关和 LiteLLM，他们可以快速访问 Amazon Bedrock 上提供的基础模型 (FM)，同时您可以获得可见性和使用控制。平台团队需要监控延迟和错误，财务团队需要将推理成本归因于团队和项目，安全团队需要一致的访问控制。 LLM 网关可以通过为支持编码助理的模型提供集中管理的访问点来帮助满足这些需求。

在本文中，我们将展示如何使用 Amazon Bedrock 应用程序推理配置文件以及在 AWS Fargate 上运行的 [LiteLLM](https://github.com/BerriAI/litellm) 构建自助式 LLM 网关，以将 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 抽象为 OpenAI 兼容的 API。通过这种模式，开发人员可以通过具有专用密钥的单个 API 访问基础模型，同时您可以获得每个用户的成本控制和模型性能可观察性。最后，您将充分理解该模式，以便根据说明性代码片段和 AWS 云开发工具包 (AWS CDK) 构造构建您自己的版本。本文使用Claude Sonnet和Claude Haiku模型作为示例。有关 AWS 区域的型号和可用性列表，请参阅 [Amazon Bedrock 中 AWS 区域支持的型号](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

此 LLM 网关模式遵循从开发人员通过 LiteLLM 层到 Amazon Bedrock 和底层 FM 的简单请求流。下图说明了该流程背后的生产拓扑。为简单起见，我们不会介绍添加 Amazon Bedrock Guardrails，例如内容过滤和接地，但您通常会在部署到生产之前包含适当的负责任的 AI 控制。

开发人员的 OpenAI 兼容客户端通过 Amazon Route 53、Amazon CloudFront 和应用程序负载均衡器 (ALB) 到达 LLM 网关。它使用每用户 API 密钥向 Fargate 上的 LiteLLM 进行身份验证。在此背后，该请求利用 Amazon Relational Database Service (Amazon RDS) (PostgreSQL) 来获取虚拟密钥和支出状态。它还与 Amazon ElastiCache for Valkey 交互作为缓存，并与 AWS Secrets Manager 交互以获取密钥。然后，LiteLLM 最终使用限定范围的 AWS Identity and Access Management (IAM) 任务角色调用 Amazon Bedrock 应用程序推理配置文件。 Amazon CloudWatch 捕获每分钟请求数 (RPM) 和每分钟令牌数 (TPM) 指标以及配额警报。

图1：LLM网关架构（生产拓扑）

该架构由以下核心组件组成：

- **AWS Fargate 上的 LiteLLM**：LiteLLM 提供公开 OpenAI 兼容 API 的代理。我们在 AWS Fargate 任务上运行它，并根据 CPU 利用率进行目标跟踪 Auto Scaling。开发人员将他们的工具指向此端点，而不直接与 Amazon Bedrock 交互。
- **自助服务门户**：LiteLLM 包括一个用于管理员和开发人员自助服务的轻量级门户。此 Web 应用程序可以与您的公司单点登录 (SSO) 集成。使用该门户，运营工程师可以设置支出策略，而开发人员可以在这些参数内自行配置 API 密钥。
- **持久和缓存存储**：LiteLLM 使用 Amazon ElastiCache for Valkey 进行非持久响应缓存。它还协调 AWS Fargate 任务之间的速率限制。单独的 Amazon RDS (PostgreSQL) 数据库是持久状态（例如 API 密钥元数据和支出跟踪）的记录数据库。
- **Amazon Bedrock 应用程序推理配置文件**：每个模型（例如 Claude Sonnet 和 Claude Haiku）都有自己的推理配置文件，您可以使用 AWS 云开发套件 (AWS CDK) 对其进行管理。这样，您就可以实现每个模型的配额隔离，并在 LiteLLM 的配置和 Amazon Bedrock 的模型版本控制之间建立一个干净的抽象层。
- **Langfuse**：开源 LLM 可观察性，用于提示级遥测、延迟跟踪和调试。它通过应用程序级洞察力补充了 Amazon CloudWatch 的基础设施级指标。

通过使用 OpenAI 兼容协议，开发人员可以使用单个基本 URL 和 API 密钥配置他们的工具，例如 Claude Code、Continue 和 Cursor。然后，开发人员可以在 Amazon Bedrock 后端之上的级别进行操作，并且可以交换模型、添加回退或迁移模型提供程序，而无需触及开发人员配置。

## 先决条件

您将需要一个 AWS 账户、Amazon Bedrock 模型访问权限和适当的 IAM 权限来部署此项目。您还需要 LiteLLM。 LiteLLM AI Gateway 组件是开源的，适合有一些限制的小型试点。 [LiteLLM 文档](https://docs.litellm.ai/docs/enterprise) AI 网关免费供最多 5 个用户使用，除此之外还需要许可证。 LiteLLM Enterprise 是一个可扩展、注重生产的许可版本，包括开源网关以及单点登录、审核日志、委派管理角色和支持。虽然免费套餐支持虚拟密钥，但本文中描述的自助密钥颁发需要企业版本。

## 端到端配置：从左到右

我们遍历从开发人员的机器到基础模型的每个配置层。

### 第 1 步：开发者 IDE 配置（例如 Claude Code）

开发人员将其编码助手配置为指向 LLM 网关。这是开发人员需要对其工具进行的唯一配置：
```
{
  "apiProvider": "openai-compatible",
  "apiBaseUrl": "https://llm-gateway.internal.example.com/v1",
  "apiKey": "sk-user-abc123",
  "model": "claude-sonnet-4-20250514"
}
```
通过该配置，每个开发人员都可以从自助服务门户获取自己的 API 密钥，并将其放入自己的工具配置中。

### 步骤 2：LiteLLM 网关配置

按照 [LiteLLM 文档](https://docs.litellm.ai/docs/proxy/docker_quick_start) 将 LiteLLM 部署到容器服务。在此示例中，我们使用 AWS Fargate。这将包括门户，您可以在本地测试期间通过“http://localhost:4000/ui”打开该门户。

您可以在 LiteLLM 网关中将模型名称映射并强制执行到具有每个密钥支出限制的 Amazon Bedrock 推理配置文件 ARN：
```
model_list:
  - model_name: claude-sonnet-4-20250514
    litellm_params:
      model: bedrock/arn:aws:bedrock:us-east-1:111122223333:application-inference-profile/sonnet-profile-id
      aws_region_name: us-east-1
      max_retries: 3
      timeout: 900  # 15 min for extended thinking
    # REQUIRED for spend tracking: when `model` is a raw inference-profile ARN,
    # LiteLLM can't find it in its built-in cost map and defaults the cost to $0
    # which means per-key `spend` stays 0 and budgets NEVER enforce. Set the
    # per-token costs explicitly.
    model_info:
      input_cost_per_token: 0.000003        # example cost
      output_cost_per_token: 0.000015    # example cost

  - model_name: claude-haiku-4-5
    litellm_params:
      model: bedrock/arn:aws:bedrock:us-east-1:111122223333:application-inference-profile/haiku-profile-id
      aws_region_name: us-east-1
      timeout: 120
    model_info:
      input_cost_per_token: 0.000001       # example cost
      output_cost_per_token: 0.000005    # example cost

litellm_settings:
  max_budget: 250            # example per key cost
  budget_duration: 7d      # Rolling 7-day window
  max_parallel_requests: 10
  set_verbose: false
  cache: true
  cache_params:
    type: redis    # Valkey is protocol-compatible, so this stays "redis"
    host: elasticache-endpoint
    port: 6379
master_key: os.environ/LITELLM_MASTER_KEY
database_url: os.environ/DATABASE_URL
```
从 AWS Secrets Manager 设置 Fargate 任务：
```
LITELLM_MASTER_KEY=sk-platform-admin-... DATABASE_URL=postgresql://user:password@rds-endpoint:5432/litellm
```
**注意：** 不要在“config.yaml”中对“master_key”或数据库凭据进行硬编码。 LiteLLM 在加载时解析“os.environ/VAR_NAME”引用，因此将“LITELLM_MASTER_KEY”和“DATABASE_URL”设置为 Fargate 任务上的环境变量（源自 AWS Secrets Manager）。以与步骤 5 中相同的方式设置 Langfuse 凭据。

例如，当开发人员调用“claude-sonnet-4-20250514”时，LiteLLM 会将其解析为推理配置文件 ARN。然后，它使用 AWS Fargate 任务的 IAM 角色向 Amazon Bedrock 进行身份验证，并以 OpenAI 格式流式传输响应。

### 步骤 3：Bedrock推理配置文件 (CDK)

借助 [Amazon Bedrock 应用程序推理配置文件](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles.html)，您可以为特定模型创建命名终端节点，从而获得配额隔离和细粒度 IAM 控制。

#### 选择跨区域推理 (CRIS)：地理或全球

Amazon Bedrock CRIS 避免了您自行实施跨区域请求路由的开销。其他好处包括：

- 获得更广泛的区域能力。
- 自动将请求路由到具有可用容量的受支持区域。
- 更广泛的模型选择，因为某些模型只能通过推理配置文件获得。

对于此代理模式，当所选模型支持全局跨区域推理并且组织策略允许跨全球受支持的 AWS 商业区域进行推理处理时，我们建议使用全局跨区域推理。地理跨区域推理使处理保持在定义的地理范围内。例如，美国推理配置文件仅将请求路由到支持的美国区域。与地理跨区域推理相比，全球跨区域推理可以访问更广泛的区域容量，并具有潜在的定价优势。您可以通过当前的 AWS 文档和 AWS 定价页面验证模型可用性、适用的服务配额和特定于模型的定价。

#### CDK 构建
```
import * as cdk from 'aws-cdk-lib';
import * as bedrock from 'aws-cdk-lib/aws-bedrock';
import * as iam from 'aws-cdk-lib/aws-iam';

// Create an Application Inference Profile pointing to the Global CRIS
// system-defined inference profile (note the `global.` prefix in the ARN).
const sonnetProfile = new bedrock.CfnApplicationInferenceProfile(this, 'SonnetProfile', {
  inferenceProfileName: 'claude-sonnet-gateway',
  modelSource: {
    copyFrom: `arn:aws:bedrock:us-east-1:${this.account}:inference-profile/global.anthropic.claude-sonnet-4-20250514-v1:0`,
  },
  description: 'Claude Sonnet for developer coding assistants (Global CRIS)',
});

// Grant LiteLLM's task role access to invoke the profile.
// For Global CRIS, include the inference profile, the regional FM, and the global FM resources.
litellmTaskRole.addToPolicy(new iam.PolicyStatement({
  effect: iam.Effect.ALLOW,
  actions: ['bedrock:InvokeModel', 'bedrock:InvokeModelWithResponseStream'],
  resources: [
    sonnetProfile.attrInferenceProfileArn,
    'arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-sonnet-4-20250514-v1:0',
    'arn:aws:bedrock:*::foundation-model/anthropic.claude-sonnet-4-20250514-v1:0',
  ],
}));
```
**重要提示：** 对于 Global CRIS，“copyFrom” ARN 必须引用前缀为“global.”的**系统定义的推理配置文件，而不是直接引用基础模型 ARN。使用基础模型 ARN 创建单区域配置文件，无需跨区域路由。此外，IAM 策略必须包含调用实际涉及的资源 ARN：应用程序推理配置文件**和**它可能路由到的任何区域中的底层基础模型（区域通配符）。仅将范围限定到 application-inference-profile ARN 将在调用时返回“未授权在资源：arn:aws:bedrock:us-east-1::foundation-model/... 上执行: bedrock:InvokeModel”。这是范围最小权限：它命名正在使用的确切模型，而不是“bedrock:*”或“*”。

### 步骤 4：Bedrock 调用基础模型

推理配置文件透明地处理模型解析和跨区域路由，无需额外配置。当 LiteLLM 调用推理配置文件 ARN 时，Amazon Bedrock 会路由到已配置的 AWS 区域中的可用容量并返回响应。

### 步骤 5：Langfuse 可观测性

LiteLLM 通过记录回调与 Langfuse 集成，提供模型调用的可见性，而无需更改开发人员工具配置。要启用集成，请将以下条目合并到步骤 2 配置中的现有 litellm_settings 块中，并保留现有回调条目：
```
litellm_settings:
  success_callback: ["langfuse"]
  failure_callback: ["langfuse"]  # also log failed requests
```
将 Langfuse 公钥、密钥和部署端点配置为 Fargate 任务上的环境变量。将凭证存储在 AWS Secrets Manager 中：
```
LANGFUSE_PUBLIC_KEY=pk-lf-...
LANGFUSE_SECRET_KEY=sk-lf-...
LANGFUSE_HOST=https://us.cloud.langfuse.com  # or your self-hosted URL
```
端点必须与所选的 Langfuse Cloud 区域或自托管部署匹配。根据数据治理和运营要求选择托管选项。在启用提示和响应日志记录之前，请检查集成捕获的内容并配置适当的编辑、保留和访问控制。

Langfuse 跟踪可以包括提示、响应、模型参数、令牌使用和延迟，具体取决于集成和日志记录配置。此信息有助于调查意外的模型响应并补充 Amazon CloudWatch 中收集的操作指标。

## 实施成本控制

成本控制是成功的人工智能战略的一个重要方面。如果没有成本控制，大量使用扩展思维功能可能会导致意外的高额费用，正如我们在早期试点中观察到的那样。

如果设置了每个模型的“model_info”成本，则在步骤 2 中配置的支出限制（“max_budget: 250”、“budget_duration: 7d”）强制每个 API 密钥滚动 7 天窗口（请参阅步骤 2 注释）。当用户达到其预算时，LiteLLM 会返回 HTTP“429”代码，并附有一条明确的消息，说明其预算已超出。没有无声的降级或意外的账单。开发人员和工程团队可以通过以下任一方式检查当前支出并重置时间：

- **每日支出**：使用“start_date”和“end_date”范围查询 [GET /user/daily/activity](https://docs.litellm.ai/docs/proxy/cost_tracking#daily-spend-breakdown-api) 以获取每日指标：支出、提示令牌、完成令牌和 API 请求，按模型、提供商和 API 密钥进行细分。
- **每用户支出**：查询 [GET /user/info?user_id=…](https://docs.litellm.ai/docs/proxy/cost_tracking#total-spend-per-user) 以获取用户总支出及其每个关联 API 密钥支出的摘要。
- **门户仪表板**：[管理 UI](https://docs.litellm.ai/docs/proxy/ui)（位于 `https://<proxy-host>/ui`）包含一个“使用情况”选项卡，开发人员和管理员可以在其中按模型、用户和标签浏览支出，而无需直接访问 API。

这些相同的端点是您的财务团队在无需构建自定义计量基础设施的情况下获取每个用户归因的方式。命中“/user/daily/activity”或“/global/spend/report”的计划作业足以提供成本仪表板或退款报告。

## 开发者自助服务门户

自助服务门户还处理关键的生命周期流程。开发人员通过您的公司 SSO 进行身份验证，以生成与其身份绑定的密钥，如果密钥暴露或匹配轮换策略，他们可以稍后重新生成该密钥。平台工程师一次性配置预算策略，让各个开发者在自己的约束下自主运营。开发人员直接使用门户的两件事：

- **密钥生成**：在[管理 UI 的虚拟密钥页面](https://docs.litellm.ai/docs/proxy/virtual_keys) (`https://<proxy-host>/ui`)，通过 SSO 进行身份验证的开发人员选择 **生成密钥** 来创建自己的密钥，并与其身份绑定。
- **速率限制可见性**：每个“/chat/completions”响应都包含“x-litellm-key-remaining-requests-{model}”和“x-litellm-key-remaining-tokens-{model}”标头，因此开发人员可以直接在工具的响应中查看该模型的剩余 RPM 和 TPM 空间。这与本文前面基于美元的支出跟踪不同。

## 监控和可观察性

对于 LLM 网关，延迟百分位数等传统指标可能会产生误导，尤其是在扩展思维模型中，单个请求可能需要几分钟的时间。相反，我们专注于 **每分钟请求数 (RPM)** 和 **每分钟令牌数 (TPM)** 作为主要信号。在这里，Amazon CloudWatch 可以通过以下配置帮助您监控这些信号并发出警报。

### 用于配额管理的 Amazon CloudWatch 警报
```
new cloudwatch.Alarm(this, 'BedrockTPMAlarm', {
  metric: new cloudwatch.Metric({
    namespace: 'LiteLLM/Gateway',
    metricName: 'TokensPerMinute',
    statistic: 'Sum',
    period: cdk.Duration.minutes(1),
  }),
  // Alert at ~60% of your account's TPM quota (check Service Quotas for your
  // actual limit, defaults vary by model and account).
  threshold: 600000,
  evaluationPeriods: 3,
  comparisonOperator: cloudwatch.ComparisonOperator.GREATER_THAN_THRESHOLD,
  alarmDescription: 'TPM approaching Bedrock quota - request increase proactively',
});
```
请注意，警报配置会在配额利用率达到 60-70% 时发出警报，而不是等待限制。这提供了在用户遇到降级之前扩展 Amazon Bedrock 配额的准备时间。

**发出指标：** LiteLLM 没有内置回调来将名为“TokensPerMinute”的指标发布到“LiteLLM/Gateway”命名空间，因此警报需要一个源。一个小的自定义记录器回调会在每个请求上调用 CloudWatch `PutMetricData` 来完成这项工作。通过“litellm_settings.success_callback”（这是**附加**）注册它，而不是“callbacks”。 “回调”列表**取代** LiteLLM 的内部记录器列表，其中包括内置的支出跟踪记录器，并将默默地禁用预算执行。

这是该回调的最小版本，使用 LiteLLM 的“CustomLogger”类：
```
import boto3
from litellm.integrations.custom_logger import CustomLogger

cloudwatch = boto3.client("cloudwatch")

class TPMEmitter(CustomLogger):
    async def async_log_success_event(self, kwargs, response_obj, start_time, end_time):
        total_tokens = kwargs.get("standard_logging_object", {}).get("total_tokens", 0)
        cloudwatch.put_metric_data(
            Namespace="LiteLLM/Gateway",
            MetricData=[{
                "MetricName": "TokensPerMinute",
                "Value": total_tokens,
                "Unit": "Count",
            }],
        )

# Register alongside success_callback, not in place of it:
import litellm
litellm.callbacks = [TPMEmitter()]
```
对于提示级调试，我们将 Langfuse 与 CloudWatch 一起运行。当开发人员报告“模型给出了错误的响应”时，您可以使用 Langfuse 检查确切的提示、令牌计数和模型参数。对于合规性敏感的环境，Amazon Bedrock 对 Amazon Simple Storage Service (Amazon S3) 的本机调用日志记录提供了不可变的审计跟踪。

## 大规模的经验教训

我们在一个新的 AWS 账户上端到端部署了此模式，以确认示例代码片段有效。在我们自己的部署中，我们将这个 LLM 网关扩展到数百名开发人员，并吸取了一些教训。

### 操作课程

大规模运行的主要发现：

- **扩展思维改变了有关延迟的一切。** 使用 Claude 扩展思维的请求可能需要几分钟或更长时间，具体取决于思维预算。如果您的负载均衡器有 60 秒的空闲超时，这些请求将默默失败。为了解决这个问题，您可以将负载均衡器空闲超时设置为至少 900 秒，并相应地配置 LiteLLM 的请求超时（本文前面第 2 步配置中的“超时：900”）。
- **当节流时，在启动回退之前先退出并重试同一模型。**我们最初的本能是在节流时从 Sonnet 回退到 Haiku。但这对于编码助理来说并不是最理想的，因为改变模型会破坏开发人员所依赖的一致行为。相反，在代理级别使用指数退避重试相同的模型（步骤 2 中的“max_retries: 3”）。当重试后无法处理请求时，请清楚地显示错误，而不是返回备用模型的完成结果。
- **将自动化工具调用与开发人员流量分开。** 持续集成和持续交付 (CI/CD) 管道以及自动代码审查工具应使用自己的推理配置文件和配额直接调用 Amazon Bedrock。将自动化流量与交互式开发人员流量混合会导致不可预测的延迟，并阻碍有意义的成本归因。
- **如果可行，从第一天开始使用全球 CRIS。** 我们最初使用地理（美国）CRIS，但最终在达到区域配额限制时迁移了我们的推理配置文件。对于我们的用例，我们没有数据驻留限制，因此我们可以使用 Global CRIS。全球 CRIS 将请求发送到各个区域，以利用更广泛的容量池，从而大规模简化管理。

### 部署注意事项

有两种配置错误很常见，并且在支出或连接中断之前很难注意到：

**为了执行预算，必须配置每个模型的成本。** 如果您想跟踪每个用户的成本控制，则每个模型上的“model_info”块不是可选的。当“model”指向 Amazon Bedrock 推理配置文件 ARN 时，LiteLLM 无法在其内置定价表中查找 ARN。相反，它记录每个代币 0 美元，因此“max_budget”和“429”限制强制执行不会默默触发。无论有多少代币流动，支出都保持在 0 美元。通过设置“input_cost_per_token”和“output_cost_per_token”（或“input_cost_per_million_tokens”）来修复此问题。

**数据库与缓存相比：** `database_url` 必须是 PostgreSQL。 LiteLLM 的虚拟密钥（`/key/generate`）、`store_model_in_db` 和支出跟踪均由 Postgres 支持。

一些较小的部署细节完善了我们的清单：

- **全球 CRIS IAM 需要基础模型资源**，而不仅仅是应用程序推理配置文件 ARN。否则，调用将在运行时被拒绝。
- **为 Fargate 任务提供足够的内存。** LiteLLM 的网关映像耗尽内存，并在通过运行状况检查之前在 512 MB 处被终止（退出 137）。大约 2 GB 是安全下限。
- **覆盖容器 `entryPoint`。** 官方镜像的入口点是 `litellm`。如果您在启动时使用 shell 脚本渲染配置，请设置 `entryPoint: ['/bin/sh','-c']` 或您的脚本作为参数传递给 `litellm`。
- **IAM 角色和安全组描述必须为 ASCII。** IAM 和 Amazon EC2 会拒绝长破折号和“->”箭头。
- **确认您的账户和区域中的模型可用性。**模型 ID 和 CRIS 配置文件发生变化。使用“aws bedrock list-inference-profiles”进行验证（例如，我们使用“claude-haiku-4-5”，因为“claude-haiku-3-5”不可用）。

## 清理

这篇文章通过说明性片段而不是单个可部署堆栈来介绍该模式，并且没有单命令拆卸。但该架构依赖于多种在运行时持续计费的资源。其中包括 AWS Fargate 服务、Amazon RDS (PostgreSQL)、Amazon ElastiCache for Valkey 和 Application Load Balancer，以及支持的 Secrets Manager 密钥、CloudWatch 警报和 Amazon Bedrock 应用程序推理配置文件。完成测试后，将其删除以避免持续产生费用。

如果您使用 AWS 上的多提供商生成 AI 网关指南部署了完整的解决方案，请按照该解决方案的清理说明删除其创建的所有内容。对于 AWS CDK，运行 cdk destroy。对于 AWS CloudFormation，删除堆栈。

如果您根据本文中的片段自行构建了模式，请删除每个资源：

- AWS Fargate 服务和集群：删除 Amazon Elastic Container Service (Amazon ECS) 服务以停止并耗尽任务，然后删除集群。
- 应用程序负载均衡器：删除 ALB 及其侦听器和目标组。
- Amazon RDS (PostgreSQL)：删除数据库实例。仅当您需要保留 API 密钥和支出数据时，才先拍摄最终快照。
- Amazon ElastiCache for Valkey：删除复制组或集群。它仅保存缓存数据，因此不需要快照。
- Amazon Bedrock 应用程序推理配置文件：通过删除 AWS CDK 构造或运行“aws bedrock delete-inference-profile”来删除在步骤 3 中创建的配置文件。
- AWS Secrets Manager 密钥：安排删除代理密钥，例如主密钥和数据库凭证。
- Amazon CloudWatch 警报和日志组：删除 TPM 警报和任何 LiteLLM 日志组。

在删除它们所依赖的 Amazon RDS 和 ElastiCache 终端节点之前删除 AWS Fargate 服务和 ALB，这样在拆卸过程中运行任务就不会因删除的后端而出错。

＃＃ 结论

在这篇文章中，我们详细介绍了 LLM 网关的模式，该模式抽象了 Amazon Bedrock 的多模型架构，为您的团队提供可扩展且可观察的自助服务访问。由于 Amazon Bedrock 通过单一界面跨模型进行路由，而无需更改基础设施，因此您的开发人员可以通过熟悉的 API 即时访问基础模型。成本治理、可观察性和单一控制平面将交给您的工程和安全团队，而财务人员则无需构建自定义计量基础设施即可获得每个用户的归属。

首先研究本文中的模式和片段，以了解各个部分如何组合在一起。 AWS CDK 片段涵盖 Amazon Bedrock 应用程序推理配置文件、其 IAM 策略和 CloudWatch 警报。周围的 AWS Fargate 服务、Amazon RDS、Amazon ElastiCache、ALB 和 AWS Secrets Manager 资源遵循标准 AWS CDK 模式，因此未显示。
