## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 用 Amazon Bedrock 和 LiteLLM 构建自助式 LLM 网关

开发者希望 AI 编码助手几乎不用配置就能上手。借助大语言模型（LLM）网关和 LiteLLM，他们能快速用上 Amazon Bedrock 上提供的基础模型（FM），而你则获得用量可见性和管控能力。平台团队需要监控延迟和错误，财务团队需要把推理成本归到各个团队和项目，安全团队需要一致的访问控制。LLM 网关为支撑编码助手的模型提供一个集中管理的访问点，就能满足这些需求。

本文展示如何用 Amazon Bedrock Application Inference Profiles 搭配运行在 AWS Fargate 上的 [LiteLLM](https://github.com/BerriAI/litellm) 构建自助式 LLM 网关，把 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 抽象成一个 OpenAI 兼容的 API。采用这一模式后，开发者通过一个 API、一把专属密钥就能访问基础模型，你则能按用户控制成本、观测模型性能。读完之后，你会充分理解这个模式，可以凭文中的示意代码片段和 AWS Cloud Development Kit（AWS CDK）构造搭出自己的版本。本文以 Claude Sonnet 和 Claude Haiku 模型为例。各 AWS Region 的模型与可用情况，参见 [Amazon Bedrock 各 AWS Region 支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

这个 LLM 网关模式的请求链路很直接：从开发者出发，经过 LiteLLM 层，到 Amazon Bedrock，再到底层 FM。下图画出了这条链路背后的生产拓扑。为简单起见，我们不展开 Amazon Bedrock Guardrails 的接入，比如内容过滤和接地检查；但在正式部署到生产环境前，你通常应当加上相应的负责任 AI 控制措施。

开发者的 OpenAI 兼容客户端经 Amazon Route 53、Amazon CloudFront 和 Application Load Balancer（ALB）抵达 LLM 网关，并用按用户分配的 API key 向 Fargate 上的 LiteLLM 认证。再往后，请求会从 Amazon Relational Database Service（Amazon RDS）（PostgreSQL）读取 virtual key 和支出状态，也会与用作缓存的 Amazon ElastiCache for Valkey 以及存放密钥的 AWS Secrets Manager 交互。最终，LiteLLM 以一个限定范围的 AWS Identity and Access Management（IAM）任务角色调用 Amazon Bedrock Application Inference Profiles。Amazon CloudWatch 采集每分钟请求数（RPM）与每分钟 token 数（TPM）指标，以及配额告警。

图 1：LLM 网关架构（生产拓扑）

该架构由以下核心组件构成：

- **AWS Fargate 上的 LiteLLM**：LiteLLM 提供一个暴露 OpenAI 兼容 API 的代理。我们把它跑在 AWS Fargate 任务上，按 CPU 使用率做目标跟踪 Auto Scaling。开发者把工具指向这个 endpoint，不直接与 Amazon Bedrock 打交道。
- **自助服务门户**：LiteLLM 自带一个轻量门户，供管理员和开发者自助使用。这个 Web 应用可以对接企业的单点登录（SSO）。运营工程师通过门户设定支出策略，开发者则在策略范围内自行申领 API key。
- **持久化与缓存存储**：LiteLLM 用 Amazon ElastiCache for Valkey 做非持久化的响应缓存，同时跨 AWS Fargate 任务协调速率限制。另有一个 Amazon RDS（PostgreSQL）数据库作为记录库，保存 API key 元数据、支出跟踪这类持久状态。
- **Amazon Bedrock Application Inference Profiles**：每个模型（比如 Claude Sonnet 和 Claude Haiku）都有自己的 inference profile，用 AWS Cloud Development Kit（AWS CDK）管理。这样你就能按模型隔离配额，并在 LiteLLM 的配置与 Amazon Bedrock 的模型版本之间留出一层干净的抽象。
- **Langfuse**：开源的 LLM 可观测性工具，提供 prompt 级遥测、延迟跟踪和调试能力。它用应用层的洞察补足 Amazon CloudWatch 的基础设施级指标。

由于走的是 OpenAI 兼容协议，开发者只需一个 base URL 和一把 API key，就能配置好 Claude Code、Continue、Cursor 这类工具。开发者由此工作在 Amazon Bedrock 后端之上的一层，可以更换模型、加回退、迁移模型供应商，都不用动开发者的配置。

## 先决条件

要部署这个项目，你需要一个 AWS 账户、Amazon Bedrock 的模型访问权限，以及相应的 IAM 权限。还需要 LiteLLM。LiteLLM AI Gateway 组件是开源的，适合小规模试点，但有一些限制。[LiteLLM 文档](https://docs.litellm.ai/docs/enterprise)说明，AI Gateway 最多 5 个用户免费，超出就需要许可证。LiteLLM Enterprise 是面向生产、可扩展的许可版本，包含开源网关，外加单点登录、审计日志、委派管理员角色和支持。免费层虽然支持 virtual key，但本文讲的自助签发密钥需要 Enterprise 版本。

## 端到端配置：从左到右

我们从开发者的机器开始，逐层走到基础模型。

### 第 1 步：开发者 IDE 配置（以 Claude Code 为例）

开发者把编码助手指向 LLM 网关。这是开发者对工具唯一要做的配置：

```
{
  "apiProvider": "openai-compatible",
  "apiBaseUrl": "https://llm-gateway.internal.example.com/v1",
  "apiKey": "sk-user-abc123",
  "model": "claude-sonnet-4-20250514"
}
```

配好之后，每个开发者从自助服务门户拿到自己的 API key，填进工具配置里即可。

### 第 2 步：LiteLLM 网关配置

按 [LiteLLM 文档](https://docs.litellm.ai/docs/proxy/docker_quick_start)把 LiteLLM 部署到容器服务。本例用的是 AWS Fargate。部署会带上门户，本地测试时可在 `http://localhost:4000/ui` 打开。

在 LiteLLM 网关里，你要把模型名映射并约束到 Amazon Bedrock inference profile ARN，同时按 key 设置支出上限：

```
model_list:
  - model_name: claude-sonnet-4-20250514
    litellm_params:
      model: bedrock/arn:aws:bedrock:us-east-1:111122223333:application-inference-profile/sonnet-profile-id
      aws_region_name: us-east-1
      max_retries: 3
      timeout: 900  # 15 min for extended thinking
    # REQUIRED for spend tracking: when `model` is a raw inference-profile ARN,
    # LiteLLM can't find it in its built-in cost map and defaults the cost to $0
    # which means per-key `spend` stays 0 and budgets NEVER enforce. Set the
    # per-token costs explicitly.
    model_info:
      input_cost_per_token: 0.000003        # example cost
      output_cost_per_token: 0.000015    # example cost

  - model_name: claude-haiku-4-5
    litellm_params:
      model: bedrock/arn:aws:bedrock:us-east-1:111122223333:application-inference-profile/haiku-profile-id
      aws_region_name: us-east-1
      timeout: 120
    model_info:
      input_cost_per_token: 0.000001       # example cost
      output_cost_per_token: 0.000005    # example cost

litellm_settings:
  max_budget: 250            # example per key cost
  budget_duration: 7d      # Rolling 7-day window
  max_parallel_requests: 10
  set_verbose: false
  cache: true
  cache_params:
    type: redis    # Valkey is protocol-compatible, so this stays "redis"
    host: elasticache-endpoint
    port: 6379
master_key: os.environ/LITELLM_MASTER_KEY
database_url: os.environ/DATABASE_URL
```

在 Fargate 任务上由 AWS Secrets Manager 注入：

```
LITELLM_MASTER_KEY=sk-platform-admin-... DATABASE_URL=postgresql://user:password@rds-endpoint:5432/litellm
```

**注意：** 不要把 `master_key` 或数据库凭据硬编码进 `config.yaml`。LiteLLM 在加载时解析 `os.environ/VAR_NAME` 这类引用，因此要把 `LITELLM_MASTER_KEY` 和 `DATABASE_URL` 设成 Fargate 任务上的环境变量，值取自 AWS Secrets Manager。第 5 步的 Langfuse 凭据也照此设置。

比如开发者调用 `claude-sonnet-4-20250514` 时，LiteLLM 会把它解析成 inference profile ARN，接着用 AWS Fargate 任务的 IAM 角色向 Amazon Bedrock 认证，再以 OpenAI 格式把响应流式返回。

### 第 3 步：Bedrock inference profiles（CDK）

借助 [Amazon Bedrock Application Inference Profiles](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles.html)，你可以为特定模型创建具名 endpoint，从而实现配额隔离和细粒度的 IAM 控制。

#### 选择跨 Region 推理（CRIS）：Geographic 还是 Global

Amazon Bedrock CRIS 省去了自己实现跨 Region 请求路由的开销。其他好处包括：

- 可调用更大的区域容量池。
- 自动把请求路由到有可用容量的受支持 Region。
- 模型选择更广，因为有些模型只能通过 inference profile 使用。

对于这个代理模式，如果所选模型支持、且组织策略允许在全球受支持的 AWS 商业 Region 内做推理处理，我们推荐 Global cross-Region inference。Geographic cross-Region inference 把处理限定在某个地理范围内，例如一个 US inference profile 只把请求路由到受支持的 US Region。相比之下，Global cross-Region inference 能调用更大的区域容量池，还可能带来价格优势。模型可用性、适用的服务配额和具体模型定价，可通过最新的 AWS 文档和 AWS 定价页面核实。

#### CDK 构造

```
import * as cdk from 'aws-cdk-lib';
import * as bedrock from 'aws-cdk-lib/aws-bedrock';
import * as iam from 'aws-cdk-lib/aws-iam';

// Create an Application Inference Profile pointing to the Global CRIS
// system-defined inference profile (note the `global.` prefix in the ARN).
const sonnetProfile = new bedrock.CfnApplicationInferenceProfile(this, 'SonnetProfile', {
  inferenceProfileName: 'claude-sonnet-gateway',
  modelSource: {
    copyFrom: `arn:aws:bedrock:us-east-1:${this.account}:inference-profile/global.anthropic.claude-sonnet-4-20250514-v1:0`,
  },
  description: 'Claude Sonnet for developer coding assistants (Global CRIS)',
});

// Grant LiteLLM's task role access to invoke the profile.
// For Global CRIS, include the inference profile, the regional FM, and the global FM resources.
litellmTaskRole.addToPolicy(new iam.PolicyStatement({
  effect: iam.Effect.ALLOW,
  actions: ['bedrock:InvokeModel', 'bedrock:InvokeModelWithResponseStream'],
  resources: [
    sonnetProfile.attrInferenceProfileArn,
    'arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-sonnet-4-20250514-v1:0',
    'arn:aws:bedrock:*::foundation-model/anthropic.claude-sonnet-4-20250514-v1:0',
  ],
}));
```

**重要：** 对于 Global CRIS，`copyFrom` ARN 必须指向**带 `global.` 前缀的系统定义 inference profile**，不能直接指向 foundation-model ARN。用 foundation-model ARN 会创建出单 Region 的 profile，没有跨 Region 路由。此外，IAM 策略必须覆盖调用真正会触及的资源 ARN：application inference profile **以及**它可能路由到的任何 Region 里的底层 foundation model（用 Region 通配符）。如果只把范围限定到 application-inference-profile ARN，调用时会报 `not authorized to perform: bedrock:InvokeModel on resource: arn:aws:bedrock:us-east-1::foundation-model/...`。这是最小权限的做法：它点名正在使用的具体模型，而不是 `bedrock:*` 或 `*`。

### 第 4 步：Bedrock 调用基础模型

inference profile 会透明地完成模型解析和跨 Region 路由，无需额外配置。LiteLLM 调用 inference profile ARN 时，Amazon Bedrock 会在已配置的各 AWS Region 中路由到可用容量，并返回响应。

### 第 5 步：Langfuse 可观测性

LiteLLM 通过 logging callback 与 Langfuse 集成，无需改动开发者的工具配置就能看到模型调用情况。要启用集成，把下面这些条目合并进第 2 步配置里已有的 litellm_settings 块，保留原有的 callback 条目：

```
litellm_settings:
  success_callback: ["langfuse"]
  failure_callback: ["langfuse"]  # also log failed requests
```

把 Langfuse 的 public key、secret key 和部署 endpoint 配成 Fargate 任务上的环境变量，凭据存进 AWS Secrets Manager：

```
LANGFUSE_PUBLIC_KEY=pk-lf-...
LANGFUSE_SECRET_KEY=sk-lf-...
LANGFUSE_HOST=https://us.cloud.langfuse.com  # or your self-hosted URL
```

endpoint 必须与所选的 Langfuse Cloud 区域或自托管部署一致。托管方式按数据治理和运维要求来定。在开启 prompt 与响应记录之前，先看清集成会采集哪些内容，并配好相应的脱敏、留存和访问控制。

根据集成方式和日志配置的不同，Langfuse trace 里可能包含 prompt、响应、模型参数、token 用量和延迟。这些信息有助于排查意外的模型响应，也补上了 Amazon CloudWatch 收集的运维指标之外的视角。

## 实施成本控制

成本控制是 AI 战略能否落地的关键一环。没有成本控制，频繁使用 extended thinking 功能会产生意外的高额账单，我们在早期试点里就遇到过。

第 2 步配置的支出上限（`max_budget: 250`、`budget_duration: 7d`）会对每个 API key 强制一个滚动的 7 天窗口，前提是按模型设好了 `model_info` 成本（见第 2 步的说明）。用户一旦触顶，LiteLLM 会返回 HTTP `429`，并附上明确消息说明预算已超。不会悄悄降级，也不会冒出意外账单。开发者和工程团队可以通过以下任一方式查看当前支出和重置时间：

- **每日支出**：用 `start_date` 和 `end_date` 区间查询 [GET /user/daily/activity](https://docs.litellm.ai/docs/proxy/cost_tracking#daily-spend-breakdown-api)，拿到按天拆分的指标：支出、prompt token、completion token 和 API 请求，并可按模型、供应商和 API key 细分。
- **按用户支出**：查询 [GET /user/info?user_id=…](https://docs.litellm.ai/docs/proxy/cost_tracking#total-spend-per-user)，汇总某个用户的总支出及其名下各 API key 的支出。
- **门户仪表盘**：[Admin UI](https://docs.litellm.ai/docs/proxy/ui)（位于 `https://<proxy-host>/ui`）里有一个 Usage 标签页，开发者和管理员可以按模型、用户和 tag 浏览支出，不必直接调 API。

同样这几个 endpoint，就是财务团队拿到按用户成本归因的方式，你不必自建计量基础设施。用一个定时任务去打 `/user/daily/activity` 或 `/global/spend/report`，就够喂给成本仪表盘或扣费报表了。

## 开发者自助服务门户

自助服务门户还负责 key 的生命周期。开发者通过企业 SSO 认证，生成一把与自己身份绑定的 key；万一泄露，或为了配合轮换策略，之后可以重新生成。平台工程师一次性配好预算策略，让每位开发者在约束内自主操作。开发者直接用门户做两件事：

- **生成 key**：在 [Admin UI 的 Virtual Keys 页面](https://docs.litellm.ai/docs/proxy/virtual_keys)（`https://<proxy-host>/ui`），通过 SSO 认证的开发者选择 **Generate Key**，就能创建一把绑定自己身份的 key。
- **速率限制可见性**：每个 `/chat/completions` 响应都带 `x-litellm-key-remaining-requests-{model}` 和 `x-litellm-key-remaining-tokens-{model}` 两个 header，开发者在工具的响应里就能直接看到该模型还剩多少 RPM 和 TPM 余量。这与本文前面按美元计的支出跟踪是两回事。

## 监控与可观测性

对 LLM 网关来说，延迟分位数这类传统指标可能误导人，尤其遇上 extended thinking 模型——单个请求就可能跑上好几分钟。我们改用 **每分钟请求数（RPM）** 和 **每分钟 token 数（TPM）** 作为主要信号。下面这套配置里，Amazon CloudWatch 可以帮你监控这些信号并告警。

### 用于配额管理的 Amazon CloudWatch 告警

```
new cloudwatch.Alarm(this, 'BedrockTPMAlarm', {
  metric: new cloudwatch.Metric({
    namespace: 'LiteLLM/Gateway',
    metricName: 'TokensPerMinute',
    statistic: 'Sum',
    period: cdk.Duration.minutes(1),
  }),
  // Alert at ~60% of your account's TPM quota (check Service Quotas for your
  // actual limit, defaults vary by model and account).
  threshold: 600000,
  evaluationPeriods: 3,
  comparisonOperator: cloudwatch.ComparisonOperator.GREATER_THAN_THRESHOLD,
  alarmDescription: 'TPM approaching Bedrock quota - request increase proactively',
});
```

注意，这套告警配置在配额用到 60–70% 时就提醒，而不是等被限流了才响。这样能留出提前量，在用户感知到性能下降之前就把 Amazon Bedrock 配额提上去。

**上报指标：** LiteLLM 没有内置 callback 能把名为 `TokensPerMinute` 的指标发到 `LiteLLM/Gateway` 命名空间，所以告警得有个数据来源。写一个小的 custom-logger callback，在每次请求时调用 CloudWatch `PutMetricData` 就够了。要通过 `litellm_settings.success_callback` 注册它（这是**追加**），别用 `callbacks`。`callbacks` 列表会**替换** LiteLLM 内部的 logger 列表——其中包含内置的支出跟踪 logger——从而悄悄关掉预算强制。

下面是这个 callback 的最小版本，用的是 LiteLLM 的 `CustomLogger` 类：

```
import boto3
from litellm.integrations.custom_logger import CustomLogger

cloudwatch = boto3.client("cloudwatch")

class TPMEmitter(CustomLogger):
    async def async_log_success_event(self, kwargs, response_obj, start_time, end_time):
        total_tokens = kwargs.get("standard_logging_object", {}).get("total_tokens", 0)
        cloudwatch.put_metric_data(
            Namespace="LiteLLM/Gateway",
            MetricData=[{
                "MetricName": "TokensPerMinute",
                "Value": total_tokens,
                "Unit": "Count",
            }],
        )

# Register alongside success_callback, not in place of it:
import litellm
litellm.callbacks = [TPMEmitter()]
```

要做 prompt 级调试，我们把 Langfuse 和 CloudWatch 一起跑。开发者反馈"模型给了一个糟糕的回答"时，你可以用 Langfuse 查到确切的 prompt、token 计数和模型参数。对合规要求高的环境，Amazon Bedrock 原生的调用日志写入 Amazon Simple Storage Service（Amazon S3），能提供不可篡改的审计轨迹。

## 规模化后的经验教训

我们在一个全新的 AWS 账户里端到端部署了这个模式，确认示例代码片段能跑通。在自己的部署中，我们把这个 LLM 网关扩展到几百名开发者，也攒下了一些教训。

### 运维经验

规模化运行下来的主要发现：

- **extended thinking 把延迟这件事彻底改写了。** 用了 Claude extended thinking 的请求可能要跑几分钟甚至更久，取决于 thinking budget。如果负载均衡器的空闲超时是 60 秒，这类请求会无声失败。办法是把负载均衡器的空闲超时调到至少 900 秒，并相应配置 LiteLLM 的请求超时（本文前面第 2 步配置里的 `timeout: 900`）。
- **被限流时，先在同一模型上退避重试，再考虑回退。** 我们最初的本能是一遇限流就从 Sonnet 回退到 Haiku。但这对编码助手并不理想，因为换模型会打破开发者依赖的一致行为。正确做法是在代理层用指数退避重试同一模型（第 2 步的 `max_retries: 3`）。重试之后仍无法处理的请求，要把错误明确抛出来，而不是返回另一个模型的补全结果。
- **把自动化工具的调用和开发者流量分开。** 持续集成与持续交付（CI/CD）流水线和自动代码审查工具应当用各自的 inference profile 和配额直接调 Amazon Bedrock。把自动化流量和开发者交互流量混在一起，会让延迟变得不可预测，也让成本归因失去意义。
- **如果条件允许，第一天就上 Global CRIS。** 我们起初用的是 Geographic（US）CRIS，但撞到区域配额上限后，最终还是迁移了 inference profile。我们的场景没有数据驻留约束，所以能用 Global CRIS。Global CRIS 跨 Region 路由请求，调用更大的容量池，规模化时管理也更简单。

### 部署注意事项

有两个配置错误很常见，而且在支出或连接出问题之前很难察觉：

**要强制预算，就必须配置按模型的成本。** 只要你想做按用户的成本控制，每个模型上的 `model_info` 块就不是可选项。当 `model` 指向 Amazon Bedrock inference-profile ARN 时，LiteLLM 在内置价目表里查不到这个 ARN，于是把每 token 记成 $0，结果 `max_budget` 和 `429` 限流强制都不会触发，无论跑过多少 token，支出始终是 $0。修法是显式设置 `input_cost_per_token` 和 `output_cost_per_token`（或 `input_cost_per_million_tokens`）。

**数据库与缓存之别：** `database_url` 必须是 PostgreSQL。LiteLLM 的 virtual key（`/key/generate`）、`store_model_in_db` 和支出跟踪都由 Postgres 支撑。

还有几条零碎的部署细节，补齐了我们的检查清单：

- **Global CRIS 的 IAM 需要 foundation-model 资源**，不能只给 app-inference-profile ARN。否则调用会在运行时被拒。
- **给 Fargate 任务足够的内存。** LiteLLM 的网关镜像在 512 MB 下会内存耗尽、在通过健康检查前就被杀掉（退出码 137）。大约 2 GB 是安全下限。
- **覆盖容器的 `entryPoint`。** 官方镜像的 entrypoint 是 `litellm`。如果你在启动时用 shell 脚本渲染配置，要设 `entryPoint: ['/bin/sh','-c']`，否则脚本会被当成参数传给 `litellm`。
- **IAM 角色和安全组的描述必须是 ASCII。** 长破折号和 `->` 箭头会被 IAM 和 Amazon EC2 拒收。
- **确认模型在你的账户和 Region 里可用。** 模型 ID 和 CRIS profile 会变。用 `aws bedrock list-inference-profiles` 核实（比如我们用 `claude-haiku-4-5`，是因为 `claude-haiku-3-5` 不可用）。

## 清理

本文是用示意代码片段讲这个模式，并没有一整套可直接部署的 stack，所以没有一条命令就能拆干净的做法。但这套架构依赖好几种只要运行就持续计费的资源：AWS Fargate 服务、Amazon RDS（PostgreSQL）、Amazon ElastiCache for Valkey、Application Load Balancer，外加配套的 Secrets Manager 密钥、CloudWatch 告警和 Amazon Bedrock application inference profile。测试结束后把它们删掉，免得一直产生费用。

如果你是用 Guidance for Multi-Provider Generative AI Gateway on AWS 部署的完整方案，按该方案的清理说明删掉它创建的所有东西。用 AWS CDK 就跑 cdk destroy，用 AWS CloudFormation 就删除 stack。

如果你是按本文片段自己搭的，就逐个删资源：

- AWS Fargate 服务和集群：先删 Amazon Elastic Container Service（Amazon ECS）服务，停掉并排空任务，再删集群。
- Application Load Balancer：连监听器、目标组一起删掉 ALB。
- Amazon RDS（PostgreSQL）：删除数据库实例。只有在需要保留 API key 和支出数据时，才先做一次最终快照。
- Amazon ElastiCache for Valkey：删除复制组或集群。它只存缓存数据，不用做快照。
- Amazon Bedrock application inference profiles：删掉第 3 步创建的 profile，可以移除 AWS CDK 构造，也可以跑 `aws bedrock delete-inference-profile`。
- AWS Secrets Manager 密钥：给代理用的密钥安排删除，比如 master key 和数据库凭据。
- Amazon CloudWatch 告警和日志组：删掉 TPM 告警以及所有 LiteLLM 日志组。

先删 AWS Fargate 服务和 ALB，再删它们依赖的 Amazon RDS 和 ElastiCache endpoint，这样拆除过程中正在跑的任务就不会因为后端已删而报错。

## 结论

本文详细讲了一个 LLM 网关模式：它把 Amazon Bedrock 的多模型架构抽象掉，为团队提供可扩展、可观测的自助访问。由于 Amazon Bedrock 通过单一接口在各模型间路由，无需改动基础设施，开发者用熟悉的 API 就能立刻用上基础模型。成本治理、可观测性和单一控制平面交给工程与安全团队，财务则拿到按用户的归因，不必自建计量基础设施。

先照着本文的模式和片段走一遍，弄清各部分怎么拼起来。AWS CDK 片段覆盖了 Amazon Bedrock application inference profile、它的 IAM 策略和 CloudWatch 告警。外围的 AWS Fargate 服务、Amazon RDS、Amazon ElastiCache、ALB 和 AWS Secrets Manager 资源都按标准 AWS CDK 写法处理，文中没有展开。

等你想要一套完整、可直接部署的实现时，[Guidance for Multi-Provider Generative AI Gateway on AWS](https://aws.amazon.com/solutions/guidance/multi-provider-generative-ai-gateway-on-aws/) 与这个模式高度契合。指南在 AWS Solutions Library 上，配套的还有[博客文章](https://aws.amazon.com/blogs/machine-learning/streamline-ai-operations-with-the-multi-provider-generative-ai-gateway-reference-architecture/)和 [GitHub](https://github.com/aws-solutions-library-samples/guidance-for-multi-provider-generative-ai-gateway-on-aws) 项目。本文逐步讲的是同一套核心模式，但聚焦在面向开发者编码助手的 Amazon Bedrock 上。更大的方案架构还加了多供应商支持、Amazon ECS 或 Amazon Elastic Kubernetes Service（Amazon EKS）、Amazon CloudFront 与 AWS WAF 选项，以及一个 admin UI。

想深入了解这套架构的各个组件，可以再看 [Amazon Bedrock Inference Profiles](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles.html)、[LiteLLM gateway](https://docs.litellm.ai/)、[AWS Fargate](https://aws.amazon.com/fargate/) 和 [Langfuse](https://langfuse.com/) 的补充文档。
