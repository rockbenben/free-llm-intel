# Fanatics Betting and Gaming 如何构建多 agent 客服系统

Fanatics Betting and Gaming（FBG）在 AWS 上构建了一套多 agent 客服系统，用来解决体育博彩独有的难题。客户期望即时、准确的答案，尤其是在每分钟都至关重要的现场赛事期间。客户会问账户问题、存款限额、各州特定法规以及负责任博彩（responsible gaming）资源，而在运营方获得牌照的每个司法辖区，规则都不尽相同。基于决策树构建的传统 chatbot 方案难以应对这种复杂性，往往让客户受挫，并随着人工客服队列变长而推高成本。

[Fanatics Betting and Gaming](https://www.fanaticsinc.com/fanatics-betting-gaming)（FBG）是一个把先进技术与深厚体育专业能力结合起来的体育博彩平台。作为 Fanatics 品牌家族的一员，FBG 在多个美国州运营，服务快速增长的庞大用户群——这些用户需要 7×24 小时支持，尤其是在 NFL 季后赛和超级碗这类高流量赛事期间。

面对支持量的指数级增长，FBG 的工程团队在 AWS 上构建了一套多 agent AI 系统，以更快、更准确、并且仅相当于纯人工支持零头的成本解决客户问题。本文将介绍其架构、涉及的 AWS 服务，以及你在设计自己的多 agent 客服方案时可以参考的模式。

## 挑战

随着 FBG 规模扩大，其原有支持模式每次交互需要更多的人工介入，导致运营成本更高，并随客户基数成比例增长。团队意识到，既存在改善客户体验的机会，也能为下一阶段增长准备好支持基础设施。有几个因素让这个问题格外棘手。

美国每个州对支付方式、存款限额、提现时限和负责任博彩要求都有自己的规定。印第安纳州的客户得到的答案可能与新泽西州的客户不同。在重大体育赛事期间，支持请求可能激增到每两分钟 40 多笔咨询，系统需要即时扩容而不能降低回答质量。

查询的多样性让问题更加复杂。客户会问从交易记录、账户设置到投注规则与自我排除（self-exclusion）选项的各种事情。没有哪个单一模型或知识库能覆盖全部。除此之外，运营方还必须实时识别并响应问题赌博的迹象，这需要对对话上下文有细致入微的理解，而不只是关键词匹配。

FBG 需要一个能自主处理这种复杂性、同时又清楚何时该升级给人工客服的系统。

> “随着规模扩大，我们知道支持体验也必须随之演进。我们希望给客户更快、更准确的答案，同时确保在负责任博彩与合规上绝不妥协。目标不是把系统做得更大，而是让它随着时间变得更好。”

——Ian Botts，Fanatics Betting and Gaming 首席技术官

## 方案概览

FBG 没有依赖单一的巨型 chatbot，而是设计了一套多 agent 系统，由专门化的 agent 处理客户交互的不同方面。由于团队已经在 [Amazon Elastic Kubernetes Service](https://aws.amazon.com/eks/)（Amazon EKS）上积累了深厚的运维经验，他们可以基于现有容器平台独立地部署、扩缩与迭代每个 agent。

FBG 选择 Amazon Bedrock，是因为它能通过单一 API 以模型无关的方式访问多个基础模型，让团队为每项任务匹配最合适的模型，并在出现更好选择时替换模型。由于 Bedrock 运行在他们既有的 AWS 环境中，系统还继承了 FBG 已建立的安全与治理控制，而 Amazon Bedrock Guardrails 则提供了其合规要求所需的负责任 AI 防护措施。

架构采用编排器（orchestrator）模式。一个主编排 agent 接收每条客户消息，与专门化的工具和子 agent 协作，并返回统一回复。这种设计让团队可以新增能力——例如新工具、新知识域、新业务单元——而无需重写核心系统。

> “我们设计这套系统时，让每个 agent 都有清晰的职责，并且可以独立改进。正是这种模块化让我们能快速行动。当我们需要支持新的案件类型或新的业务单元时，只需新增一个工具或 agent，而不用碰系统的其余部分。”

——Luis Fernandez Rocha，Fanatics Betting and Gaming 软件工程高级经理

客户消息从 FBG 移动应用进入，经 Salesforce Einstein 传递到 Amazon EKS 上的 Spring AI 服务，然后经过 Amazon Bedrock Guardrails 与负责任博彩分类器，再到达 Supervisor Agent。Supervisor Agent 调用专门化的工具——包括检索增强生成（RAG）pipeline、账户与交易的 Model Context Protocol（MCP）服务器，以及转人工工具——来生成回复。

## 请求如何在系统中流转

客户通过 FBG 移动应用发送消息，该应用连接 Salesforce Einstein 作为聊天界面层。请求经标准 REST 调用路由到运行在 Amazon EKS 上的 Spring AI 服务。该服务校验客户 token 并调用 AI agent。

随后请求经过 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 传向 AI 层，以帮助检测 prompt 注入。一个由 [Amazon Nova 2 Lite](https://aws.amazon.com/blogs/aws/introducing-amazon-nova-2-lite-a-fast-cost-effective-reasoning-model/) 驱动的负责任博彩分类 agent，会按合规部门批准的分类框架评估每条消息。高严重程度的分类会立即触发转人工，并附带完整对话上下文。

运行在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上、使用 Anthropic Claude 的 Supervisor Agent，会根据客户意图决定调用哪些工具。视查询而定，supervisor 会调用一个或多个专门化工具，其中一些通过 MCP，另一些是该服务本地的：

- RAG（Retrieval Augmented Generation，检索增强生成）工具：为 FAQ 类问题从向量存储中检索相关知识。
- 账户工具（MCP）：查询内部账户服务以获取与客户相关的信息。
- 交易工具（MCP）：检索近期交易记录，包括存款、提现与投注活动。
- 转人工工具：当客户明确要求，或情况需要人工判断时，升级给人工客服。

supervisor 综合各工具的响应，并以自然语言回复客户。

## 深入剖析：关键架构组件

本节我们逐一考察让系统运转的四个组件：Amazon EKS 托管平台、自定义 RAG pipeline、负责任博彩分类器，以及帮助保障对话安全的 guardrails。

### 用 Amazon EKS 托管 agent 与 MCP 服务器

FBG 把整个 AI 栈都跑在 Amazon EKS 上，将 MCP 服务器与 Spring AI 服务作为 Kubernetes 服务托管。MCP 服务器暴露的工具会向账户服务、交易历史服务等外部服务发起 REST 调用。本地工具则直接与 Claude 大语言模型（LLM）一起位于 Spring AI 服务中，包括 RAG 工具与转人工工具。

这种做法为多 agent 系统带来若干优势。MCP 服务器与 Spring AI 服务能够按需独立扩缩。当 FBG 需要支持更多业务域或功能时，新增一个 MCP 服务器不过是一次额外的 Kubernetes 部署。团队还可以只更新单个工具而无需重新部署整个系统。新的 MCP 工具被添加到现有 MCP 服务器上，无需新建 pod 部署。

FBG 使用 [Spring AI](https://spring.io/projects/spring-ai) 作为应用框架，它原生支持 MCP。MCP 服务器定义的工具可被 supervisor agent 动态发现和调用。团队选择 Spring AI，是因为开发者拥有深厚的 Java 专长，能够快速推进。对于使用 Python 的团队，[Strands Agents](https://strandsagents.com/) 是 AWS 提供的开源 SDK，提供类似的 agent 编排与 MCP 支持。

对于考虑类似做法的团队，Amazon EKS 提供了大规模管理多个 agent 服务所需的容器编排能力，MCP 则提供 agent 之间工具通信的标准化协议。偏好托管体验的团队还可以了解 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)——一个可用任意框架或模型大规模构建、连接与优化 agent 的平台。AgentCore 同样支持用 MCP 做工具集成。

### 使用 Amazon Titan embedding 的自定义 RAG

系统中使用最频繁的工具是 RAG pipeline。FBG 选择了自定义实现而非托管式知识库，从而精确控制摄取、分块与检索过程。

这条 pipeline 的工作方式如下。支持文档从上游来源汇集，包括各州特定的支付方式指南、FAQ 文章、负责任博彩资源与账户管理指南。文档采用基于 token 的分块策略切分，即每份文档被分成固定 token 数（模型处理文本的单位）的片段，而不是按句子或段落切分。这让团队能够细粒度地控制块边界。随后使用 [Amazon Titan](https://aws.amazon.com/bedrock/titan/) V2 为各个块生成 embedding，得到的向量表示存入 MongoDB Atlas。

当客户提问时，系统用 LLM 把查询转换为适合向量检索的形式，然后对文档库做相似度搜索。对于与特定司法辖区相关的问题，系统会同时做一次州特定搜索和一次通用搜索，把结果合并后再交给 supervisor agent 生成回复。

当你的知识库有复杂的检索要求时——例如需要在一次回复中同时组合州特定文档与通用文档——这种自定义做法尤其有价值。知识库在不断扩张，随着团队通过对话分析发现缺口，每月会新增数百份文档。

> “自建 RAG pipeline 让我们能完全控制模型看到什么、以及它如何检索信息。每个州的规则都不同，所以我们需要在一次回复中组合州特定文档与通用文档的能力。这种程度的控制对准确性至关重要。”

——Sharoze Amir，Fanatics Betting and Gaming 软件工程师

### 使用 Amazon Nova 做负责任博彩分类

负责任博彩既是监管要求，也是 FBG 的核心价值。团队与合规部门合作构建了一套分类系统。该系统评估客户交互，确认是否满足负责任博彩标准，并在需要时把客户引导到合适的资源。

系统使用 [Amazon Nova](https://aws.amazon.com/ai/generative-ai/nova/) 2 Lite——一个轻量、快速的分类模型。团队是刻意选择更小的模型的。该任务定义明确、有清晰示例、结果集合有限，因此更大更贵的模型只会增加延迟而不会提升准确率。

模型同时接收当前消息与完整对话历史，因此能够识别逐步升级的模式，而不必依赖单条消息的关键词匹配。当系统识别出高严重程度的关注点时，会立即把客户转给人工客服，并附带完整对话上下文。较低严重程度的标记会被记录下来供合规审查，同时允许对话继续进行。

这是一个适用范围很广的模式：对于边界清晰的分类任务，使用满足你准确率要求的最小模型；把更大的模型留给开放式推理。

> “开箱即用的客服 agent 把每段对话都同样处理。我们的不行——一个关于提现的问题，背后可能其实是一个负责任博彩的关键时刻，要识别这一点，需要与我们合规框架深度集成。这就是我们选择在 AWS 上自建的原因：没有哪家供应商会按我们这个行业要求的方式处理这些敏感领域。”

——Trevor Gurgick，Fanatics Betting and Gaming 应用 AI 负责人

### 用 Amazon Bedrock Guardrails 保障安全

FBG 使用 Amazon Bedrock Guardrails 帮助防范 prompt 注入，并帮助把对话保持在适当边界内。团队调整了 guardrail 配置，以在安全与客服交互的现实之间取得平衡——过于严格的过滤器会在客户体验中制造摩擦。

关键洞见在于：按你的实际用例调整 guardrails，而不是默认套用最严格的限制。对客服而言，prompt 注入防护至关重要，但过于激进的内容过滤会产生误报，让客户受挫。

## 多模型架构

FBG 在 Amazon Bedrock 上运行多模型架构，对模型选择采取刻意、自下而上的方式。对于负责任博彩这类分类任务，他们使用 Amazon Nova 2 Lite：它快速、经济，且在有清晰示例的明确定义分类任务上足够好用。对于对话管理等 supervisor 与编排任务，他们使用 Amazon Bedrock 上的 Anthropic Claude Sonnet，由 Claude 处理复杂推理、工具编排与自然对话。对于 RAG pipeline 中的 embedding，他们使用 Amazon Titan V2，它能生成高质量的向量表示。关于各 AWS 区域可用的模型，请参阅 [Amazon Bedrock 中各 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

团队对 supervisor agent 在多个模型区域之间采用轮询（round-robin）策略，确保在高峰赛事期间不会触及吞吐上限。由于所有模型都通过同一个 Amazon Bedrock API 访问，把不同工作负载路由到不同模型无需改动底层基础设施。

## 成果

根据 FBG 的内部指标，部署后的头两个月里，这套多 agent 系统相比 FBG 之前的支持体验带来了可衡量的改善。自助解决率（containment rate）提升了约 56%，意味着现在有更多客户问题无需人工客服介入即可解决。解决率提升了约 53%，客户的问题得到真正解决而不是被推诿。系统已自主解决了数千个案件，带来了可观的成本节省，因为 AI 驱动的交互成本只是人工客服交互的一小部分。客户满意度也在上升。对话质量提升之大，以至于客户常常没意识到自己是在与 AI 交互。

在体育赛事高峰期间，系统能处理高请求量，同时保持一致性能与回答质量。Amazon EKS 的自动扩缩确保 MCP 服务器与 Spring AI 服务在流量激增时自动增加容量，无需人工干预。这意味着无论是一个平静的周二还是超级碗之夜，无论同时有多少人在提问，客户都能得到同样快速、准确的回复。

## 持续改进：评估与迭代

构建 agent 只是开始。FBG 做法真正突出之处，是他们在部署之后持续改进系统上的投入。团队把多 agent 系统当作一个活的产品，而不是一次性交付的项目。他们审阅对话日志、跟踪解决准确率，并利用真实客户交互来优化 prompt、调整工具行为、发现知识库中的缺口。这种持续投入确保系统随时间变得更聪明，而不是随着客户需求演进逐渐退化。

其评估策略的核心是一个 LLM-as-a-Judge 系统，它自动审阅每段已完成的对话，判断 AI 是成功解决了该案件还是未能达标。运营团队每天审阅这些评估，找出 agent 吃力的模式，并提交改进工单来补齐缺口。这就形成了一个反馈闭环，让 agent 随时间可衡量地变得更好。

在工程侧，团队通过实时可观测性指标监控系统健康度，包括幻觉检测、延迟与成本跟踪。在开发新功能或测试改动时，他们会从生产环境取来真实客户对话，针对更新后的架构回放，从而在任何东西触达客户之前暴露边界情况。

其中特别有效的一项纪律是团队的 prompt 工程做法。当性能下滑时，他们不会立刻换用更强（也更贵）的模型，而是先看 system prompt 是否能改进、指令之间是否存在矛盾。这既压低了成本，又推动质量持续改善；只有在 prompt 已针对任务充分优化之后，他们才会升级模型。希望把这一纪律系统化的团队，可以使用 Amazon Bedrock 中的高级 prompt 优化功能——它会依据评估准则反复打磨 prompt，并在多个模型之间比较结果，然后才决定是否迁移。

## 上手：构建你自己的多 agent 客服系统

如果你想构建类似的多 agent 客服系统，这里有一条实用的起步路径。

### 把范围定义得窄一些

FBG 上线时只做了 20 多种案件类型中的 4 种。从窄范围起步能让你快速证明价值、建立评估基础设施，并在扩张之前弄清什么有效。挑选量最大、解决标准最清晰的案件类型。

### 搭好基础设施

把 agent 服务部署在 Amazon EKS 上以获得完全控制，或使用 Amazon Bedrock AgentCore 获得托管体验。用 MCP 作为编排器与工具服务之间的通信方式。

### 构建你的 RAG pipeline

可以从 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 这个完全托管的 RAG 能力起步；如果你需要细粒度控制检索逻辑，也可以用 Amazon Titan embedding 构建自定义 pipeline。无论哪种方式，都要在分块策略上花时间——它对回答质量的影响比模型选择更大。

### 从第一天就落实 guardrails 与合规

使用 Amazon Bedrock Guardrails 帮助防范 prompt 注入。如果你的行业有合规要求（博彩、医疗、金融），请尽早构建分类 agent。一开始就集成，比事后补装容易得多。

### 模型选择从小处着手

为每项任务选用满足你准确率要求的最小模型。把更大的模型留给需要复杂推理的编排 agent。Amazon Bedrock 让替换模型变得简单，方便你持续迭代。

### 尽早投入评估

把评估 pipeline 与 agent 一起建设，而不是之后再补。从第一天起就跟踪自助解决率、解决率与客户满意度。使用 LLM-as-a-Judge 模式大规模自动化对话审阅。

## 结论

Fanatics Betting and Gaming 的多 agent 架构展示了：把 Amazon EKS、Amazon Bedrock、MCP 与专用的 AWS AI 服务结合起来，能够交付随业务扩展、同时保持质量与合规的客户支持。通过让专门化的 agent 分别承担不同任务——编排、知识检索、分类与工具执行——系统应对了州特定法规的复杂性、实时负责任博彩检测以及高流量体育赛事。

本文中的模式适用范围很广：把范围定义得窄，使用职责清晰的专门化 agent，选择满足准确率要求的最小模型，并从一开始就投入评估基础设施。

如果你已准备好构建类似的多 agent 客服系统，先从界定 agent 边界、明确每个 agent 需要哪些工具开始。你可以把 agent 部署在 [Amazon EKS](https://aws.amazon.com/eks/) 上，对扩缩与编排获得完全控制；或使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 提供的托管运行时，由它代为处理基础设施。在 AI 层，[Amazon Bedrock](https://aws.amazon.com/bedrock/) 让你通过单一 API 访问 Anthropic Claude 与 [Amazon Nova](https://aws.amazon.com/nova/) 等模型，[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 则能在不写自定义代码的情况下帮你加上安全检查。要开始上手，请参阅 [Amazon Bedrock 入门指南](https://docs.aws.amazon.com/bedrock/latest/userguide/getting-started.html)；关于支持基于 MCP 的工具编排的开源 Python 框架，请参阅 [Strands Agents 文档](https://strandsagents.com/)。
