# 基于 Amazon Bedrock 的具身 AI 国际象棋

生成式 AI 持续改造着众多行业与活动，其中一个应用就是用复杂精妙的 AI 与大语言模型（LLM）来增强国际象棋这一传统的人类游戏。现在，借助 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 中的 [Custom Model Import](https://aws.amazon.com/bedrock/custom-model-import/) 功能，你可以在针对棋局微调过的基础模型（FM）之间组织引人入胜的对局，把经典策略与生成式 AI 能力结合起来。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/26/Image-001-Chess-1024x683.jpeg)

Amazon Bedrock 以托管方式提供对来自 Anthropic、Meta、Mistral AI、AI21 Labs、Cohere、Stability AI 和 Amazon 的领先 FM 的访问，让开发者能够构建精密的 AI 驱动应用。这些模型在理解复杂棋局模式、战略决策和自适应学习方面展现出卓越能力。借助 Custom Model Import 功能，你现在可以顺畅地部署针对特定棋风或历史对局微调过的定制国际象棋模型，既无需管理基础设施，又能实现无服务器、按需推理。这一能力让你可以就以下这些有趣的对战组合进行实验：

- 基础 FM 对比定制微调模型
- 按不同特级大师棋风训练的定制微调模型

本文演示基于 Amazon Bedrock 的具身 AI 国际象棋，通过生成式 AI 能力为传统国际象棋带来新的维度。我们的装置包括一块能够实时识别走子的智能棋盘，并配以两条执行这些走子的机械臂。每条机械臂由不同的 FM 控制——基础模型或定制模型。这一物理实现让你可以观察并实验不同生成式 AI 模型在真实棋局中如何处理复杂的博弈策略。

## 方案概述

该国际象棋演示使用广泛的 AWS 服务来打造交互性强、引人投入的游戏体验。下图展示了演示中的服务集成与数据流。

![Connected Edge Intelligence Chess with Amazon Bedrock - Architecture](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/26/Image-002-Architecture.png)

在前端，[AWS Amplify](https://aws.amazon.com/amplify/) 托管了一个响应式的 React TypeScript 应用，同时通过 Amplify SDK 借助 [Amazon Cognito](https://aws.amazon.com/cognito/) 提供安全的用户身份验证。该身份验证层通过由 [AWS AppSync](https://aws.amazon.com/appsync/) 管理的 GraphQL API 把用户连接到后端服务，实现实时数据同步与棋局状态管理。

应用的核心后端功能由 Unit resolver 与 Pipeline resolver 组合处理。Unit resolver 负责棋局状态管理、创建和删除等轻量操作，而关键的走子流程则通过 Pipeline resolver 编排。这些 resolver 会把走子排入队列交由 [AWS Step Functions](https://aws.amazon.com/step-functions/) 处理，从而提供可靠且可扩展的对局流程管理。

在为对局提供生成式 AI 支持方面，Amazon Bedrock 的集成使得既能访问 FM，也能访问定制微调模型。使用 [Amazon SageMaker](https://aws.amazon.com/sagemaker/) 微调好的 FM 随后会通过 Custom Model Import 功能导入 Amazon Bedrock，与内置 FM 并列，在对局中按需访问。关于微调以及把微调后的 FM 导入 Amazon Bedrock 的更多细节，请参阅博文[把问答微调模型作为自定义模型导入 Amazon Bedrock](https://aws.amazon.com/blogs/machine-learning/import-a-question-answering-fine-tuned-model-into-amazon-bedrock-as-a-custom-model/)。

棋盘上走子的执行由一个名为 Chess Game Manager 的自定义组件协调，它运行在 [AWS IoT Greengrass](https://aws.amazon.com/greengrass/) 上。该组件弥合了云基础设施与物理硬件之间的差距。

处理一次走子时，Step Functions 工作流会把走子请求发布到 [AWS IoT Core](https://aws.amazon.com/iot-core/) 的某个主题并暂停，等待确认。Chess Game Manager 组件消费该消息，并实施一套三阶段校验机制，确保走子被准确执行。首先，它用能够识别棋子位置的智能棋盘校验预期走子。其次，它向两条机械臂发送请求，由其物理移动棋子。最后，它通过智能棋盘确认走子后棋子处于正确位置。智能棋盘的这一第三阶段校验，正是具身 AI 中“信任但要验证”理念的体现——物件的物理状态可能与仪表盘上显示的不一致。因此，在走子状态被登记之后，Step Functions 工作流才会继续。走子被确认后，该组件会把响应消息发布回 AWS IoT Core 的另一个主题，通知 Step Functions 工作流继续执行。

该演示提供几种对局选项。玩家可以从以下对手列表中选择：

- 可在 Amazon Bedrock 上使用的生成式 AI 模型
- 部署到 Amazon Bedrock 的[定制微调模型](https://aws.amazon.com/bedrock/custom-model-import/)
- 国际象棋引擎
- 人类对手
- 随机走子

构建本项目时采用了基础设施即代码（IaC）的方式。你会使用 [AWS Cloud Deployment Kit](https://aws.amazon.com/cdk/)（AWS CDK）来构建各组件，以便部署到任意 AWS 账户。下载代码库后，你可以按照 [GitHub 仓库](https://github.com/aws-samples/embodied-chess-demo-with-amazon-bedrock) 中的说明部署该项目。

## 使用微调模型下棋

国际象棋 AI 的传统做法侧重于手工编写的规则与搜索算法。这些方法虽然有效，却往往难以刻画人类特级大师那种微妙的决策与长期战略思考。近来，强化学习（RL）通过让 AI agent 在自我对弈与试错中学习，在掌握国际象棋方面展现出潜力。RL 模型能够发现策略并评估棋盘局面，但通常需要大量计算资源与训练时间——要达到特级大师水平的下法，一般需要数周到数月的不间断学习。

微调生成式 AI FM 提供了一种很有吸引力的替代方案：只需使用标准 GPU 实例，在几天内就能学到国际象棋的底层模式与原则，这使其成为开发专用国际象棋 AI 时更节省资源的方式。微调过程显著减少了所需的时间与计算资源，因为模型已经理解基本的模式与结构，可以把注意力集中在学习国际象棋特有的战略与战术上。

## 准备数据集

本节深入介绍为微调一个会下国际象棋的模型而准备高质量数据集的过程，重点是从特级大师对局和世界冠军赛中提炼有价值的洞察。

我们数据集的核心是 Portable Game Notation（PGN），这是一种记录国际象棋对局各个方面的标准格式。PGN 包含 Forsyth–Edwards Notation（FEN），用于记录任意时刻棋盘上棋子的确切位置。这两种格式结合起来，既保存了实际走的棋，也保存了棋手姓名、日期等重要对局信息，为模型提供了全面的学习数据。

数据集准备包括以下关键步骤：

- **数据获取** – 我们首先从 [PGN mentor 项目网站](https://www.pgnmentor.com/) 上公开可用的 PGN 文件中下载一批 PGN 格式的对局。我们使用的是著名国际象棋特级大师 Magnus Carlsen 的对局。你可以用以下命令下载类似的数据集：

```
# Download games zip file to the target directory - You may choose a different set of games – replace filename with the name of the file you want to download
curl -o /data/filename.zip https://www.pgnmentor.com/players/filename.zip

# Unzip the file in the target directory 
unzip filename.zip
```

- **筛选胜局** – 为了训练一个专注于制胜策略的模型，我们筛选对局，只保留该棋手获胜的棋局。这让模型能够从成功的对局中学习。
- **PGN 转 FEN** – PGN 文件中的每一步都代表棋盘状态的一次转换。为有效捕获这些状态，我们把 PGN 记法转换为 FEN 格式。该转换过程会遍历 PGN 中的各步走子，相应地更新棋盘状态，并为每一步生成对应的 FEN。

下面是一个 PGN 文件中的示例对局：

`[Event “Titled Tue DDth MMM Late”]`
`[Site “chess.com INT”]`
`[Date “YYYY.MM.DD”]`
`[Round “10”]`
`[White “Player 1 last name,Player 1 first name”]`
`[Black “Player 2 last name, Player 2 first name “]`
`[Result “0-1”]`
`[WhiteElo “2xxx”]`
`[BlackElo “2xxx”]`
`[ECO “A00”]1.e4 c5 2.d4 cxd4 3.c3 Nc6 4.cxd4 d5 5.exd5 Qxd5 6.Nf3 e5 7.Nc3 Bb4 8.Bd2 Bxc3 9.Bxc3 e4 10.Nd2 Nf6 11.Bc4 Qg5 12.Qb3 O-O 13.O-O-O Bg4 14.h4 Bxd1 15.Rxd1 Qf5 16.g4 Nxg4 17.Rg1 Nxf2 18.d5 Ne5 19.Rg5 Qd7 20.Bxe5 f5 21.d6+ 1-0`

下面是包含 FEN 的示例 JSON 记录，其中记录了下一步走子与下一步行棋方颜色。我们采用了两种方式创建 JSON 记录。对于能较好理解 FEN 格式的模型，我们使用更简洁的记录：

```
{
    "move": "d4",
    "fen": "rnbqkbnr/pp1ppppp/8/2p5/4P3/8/PPPP1PPP/RNBQKBNR w KQkq - 0 2",
    "nxt_color": "WHITE"
}
```

对于对 FEN 格式理解有限的模型，我们使用更详细的记录：

```
{
    "move": "d4",
    "fen": "rnbqkbnr/pp1ppppp/8/2p5/4P3/8/PPPP1PPP/RNBQKBNR w KQkq - 0 2",
    "nxt_color": "WHITE",
    "move_history": "e4, c5"
}
```

这些记录包含以下参数：

- **move** – 给定 FEN 状态下的一个合法下一步走子。
- **fen** – 当前棋盘局面（FEN 表示）。
- **nxt_color** – 下一步轮到哪一方行棋。
- **move_history** – 截至当前棋盘局面为止的对局走子历史。

对于 PGN 文件中的每一局，都会创建多条与上述示例类似的记录，以捕获 FEN、下一步走子和下一步行棋方颜色。

- **走子合法性校验** – 我们校验按上述格式记录下来的每一步的合法性。这一步维护数据完整性，防止模型学到错误或不可能的走法。
- **数据集划分** – 我们把处理后的数据集分为两部分：训练集和评估集。训练集用于训练模型，评估集用于评估模型在未见数据上的表现。这种划分有助于我们了解模型对新棋局局面的泛化能力。

通过执行这些步骤，我们构建出一个全面而精炼的数据集，使我们的国际象棋 AI 能够从胜局中学习、理解合法走子，并把握战略对弈的精微之处。这种数据准备方式为微调出一个能高水平对弈的模型奠定了基础。

## 微调模型

在准备好由胜局与合法走子构成的精炼数据集之后，我们现在使用 [Amazon SageMaker JumpStart](https://aws.amazon.com/sagemaker/jumpstart/) 来微调模型。微调过程需要通过结构化的 prompt 模板给出明确指令。这里同样，我们依据不同的 FM 采用了两种方式。

对于理解 FEN 格式的 FM，我们使用更简洁的 prompt 模板：

```
template = {
    "prompt": (
        "<s>[INST] You are a chess engine. Given a chess position in FEN notation and the color to move, provide the next best valid move in SAN (Standard Algebraic Notation) format to progress towards winning the game of chess. Your response must be a single move wrapped in <move></move> tags.\n\n"
        "Chess Position (FEN): {fen}\n"
        "Color to Move: {nxt_color} [/INST]"
    ),
    "completion": " <move>{move}</move> </s>"
}
```

或者，对于 FEN 知识有限的模型，我们提供类似下面的 prompt 模板：

```
template = {
    "prompt": (
        "<s>[INST]\nYou are a chess engine that provides the next best valid move in SAN format based on:\n- FEN position where:\n  Black pieces: p=pawn, r=rook, n=knight, b=bishop, q=queen, k=king (lowercase)\n  White pieces: P=pawn, R=rook, N=knight, B=bishop, Q=queen, K=king (uppercase)\n  Numbers 1-8 indicate consecutive empty squares\n- Color to move\n- Move history\n\nAnalyze these inputs to recommend a legal move that progresses toward winning. Respond with a single move in <move></move> tags.\n\n"
        "Chess Position (FEN): {fen}\n"
        "Color to Move: {nxt_color}\n"
        "Move History: {move_history}\n"
    ),
    "completion": " <move>{move}</move> </s>"
}
```

随后，训练与评估数据集，以及用上述某个模板创建好的 template.json 文件，会被上传到 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）桶中，从而为将通过 SageMaker JumpStart 提交的微调作业做好准备。

现在数据集已准备好、模型也已选定，我们用以下代码提交 SageMaker 训练作业：

```
estimator = JumpStartEstimator(
    model_id=model_id,
    model_version=model_version,
    environment={"accept_eula": "true"},  
    disable_output_compression=True,
    instance_type="ml.g5.24xlarge"
)
# By default, instruction tuning is set to false. 
estimator.set_hyperparameters(instruction_tuned=True, epoch="3", max_input_length="1024")
estimator.fit({"training": train_test_data_location})
```

我们来拆解上面的代码，看看其中几个重要部分：

- **estimator** – 这是 [SageMaker 对象](https://docs.aws.amazon.com/sagemaker/latest/dg/docker-containers-adapt-your-own-private-registry-estimator.html)，用于接收所有训练参数，同时负责启动并编排训练作业。
- **model_id** – 这是你要微调的 LLM 对应的 SageMaker JumpStart 模型 ID。
- **accept_eula** – 该 EULA 因提供商而异，在从 SageMaker JumpStart 部署或微调模型时必须接受。
- **instance_type** – 这是微调作业运行所用的计算实例。在本例中是 g5.24xlarge。该实例包含 4 块 NVIDIA A10G GPU，共 96 GiB 显存。在决定实例类型时，请选择最能平衡计算需求与预算的那一款，以实现价值最大化。
- **fit** – .fit 方法是真正启动 SageMaker 训练作业的那行代码。所有算法指标与实例使用指标都可以在 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 日志中查看，CloudWatch 与 SageMaker 已直接集成。

SageMaker 训练作业完成后，模型构件会被存储到由用户指定或系统默认指定的 S3 桶中。

我们用来微调其中一个模型的 notebook 可在以下 [GitHub 仓库](https://github.com/aws-samples/amazon-bedrock-samples/blob/main/custom-models/import_models/llama-3.1-jumpstart-chess/llama-3.1-8b-jumpstart-chess-finetuning.ipynb) 中获取。

## 微调的挑战与最佳实践

本节讨论微调中常见的挑战与最佳实践。

### 使用 SageMaker JumpStart 的自动优化

使用 SageMaker 微调 LLM 来做走子预测，既带来独特的机会，也带来挑战。我们使用 SageMaker JumpStart 完成微调，因为它在为国际象棋应用做微调时会针对不同模型规模提供自动优化。SageMaker JumpStart 会根据模型规模自动应用合适的量化技术与资源分配。例如：

- **3B–7B 模型** – 启用 FSDP 与全精度训练
- **13B 模型** – 配置 FSDP，并可选用 8-bit 量化
- **70B 模型** – 自动实施 8-bit 量化，并为稳定性而禁用 FSDP

这意味着，如果你创建 SageMaker JumpStart Estimator 时没有显式指定 int8_quantization 参数，它会根据你所处理的模型规模自动使用这些默认值。之所以做出这样的设计选择，是因为更大的模型（例如 70B）需要大量计算资源，所以默认启用量化以降低训练期间的显存占用。

### 数据准备与格式

数据集的识别与准备可能颇具挑战。我们使用世界冠军赛和特级大师对局中现成可得的 PGN 数据集，来简化国际象棋 LLM 微调的数据准备流程，显著降低了数据集整理的复杂度。

选择能与 LLM 配合产生最佳结果的合适棋谱格式，对微调之后的效果至关重要。我们发现，Standard Algebraic Notation（SAN）在训练收敛与模型表现方面显著优于 Universal Chess Interface（UCI）格式。

### Prompt 一致性

在微调期间使用一致的 prompt 模板，有助于模型更有效地学习预期的输入输出模式，而 [Amazon Bedrock Prompt Management](https://aws.amazon.com/bedrock/prompt-management/) 提供了系统化创建与管理这些模板的可靠工具。我们建议使用模型提供商给出的 prompt 模板建议，以获得更好的效果。

### 模型规模与资源分配

成功的 LLM 训练需要通过多种途径在成本管理上取得良好平衡，其中实例选择是首要方面。你可以先从下面推荐的实例起步，并根据训练所需的质量与可用时间逐步升级。

| **模型规模** | **显存需求** | **推荐实例与量化** |
| --- | --- | --- |
| **3B – 7B** | 24 GB | 使用 QLoRA 4-bit 量化可运行在 g5.2xlarge 上 |
| **8B -13B** | 48 GB | 需要 g5.4xlarge，并配合高效的内存管理 |
| **70B** | 400 GB | 需要 g5.48xlarge 或 p4d.24xlarge，并配备多 GPU |

## 把微调模型导入 Amazon Bedrock

模型微调完成、模型构件已放在指定的 S3 桶之后，就可以使用 Custom Model Import 把它导入 Amazon Bedrock 了。

下面介绍两种导入模型的方式：使用 SDK，或使用 Amazon Bedrock 控制台。

下面的代码片段展示了如何使用 SDK 导入模型：

```
create_model_import_job_resp = br_client.create_model_import_job(
        jobName=rivchess_imp_jb_nm,
        importedModelName=rivchess_model_nm,
        roleArn=role_arn,
        modelDataSource=rivchess_model_src)
```

在代码片段中，提交了一个创建模型导入作业的请求，以把微调后的模型导入 Amazon Bedrock。该作业的参数如下：

- **JobName** – 导入作业的名称，便于通过 SDK 或 Amazon Bedrock 控制台识别它
- **ImportedModelName** – 导入模型的名称，将用于通过 SDK 调用推理，并在 Amazon Bedrock 控制台上标识该模型
- **roleArn** – 具有把模型导入 Amazon Bedrock 所需正确权限的 role
- **modelDataSource** – 训练作业完成后存放模型构件的 S3 桶

要使用 Amazon Bedrock 控制台，请完成以下步骤：

- 在 Amazon Bedrock 控制台的导航窗格中，于 **Foundation models** 下选择 **Imported models**。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/26/Image-003-Bedrok-home-page-1.png)

- 选择 **Import model**。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/26/Image-004-Import-model.png)

- 提供以下信息：  **Model name** 用于输入模型名称。  **Import job name**¸ 用于输入导入作业的名称。  **Model import settings** 选择 **Amazon S3 bucket** 并输入你的桶位置。创建一个 IAM role，或使用已有的 role。

## 设置 AWS IoT Core 资源

## 防止非法走子

在使用 Amazon Bedrock 中的 FM 生成下一步走子时，系统采用一套重试机制，与生成式 AI 模型进行三次不同的尝试，每次提供的上下文都比上一次更多：

- **第一次尝试** – 提示模型基于当前棋盘状态预测最佳下一步。
- **第二次尝试** – 如果第一步走法不合法，会告知模型失败，并提示它重试，同时给出上一次尝试失败原因的上下文。
- **第三次尝试** – 如果仍未成功，会向模型提供此前非法走子的信息以及对过往失败的解释。不过，这次尝试还会附上所有可用合法走法的列表，然后提示模型从该列表中选出下一步合乎逻辑的走法。

如果三次生成式 AI 尝试都失败，系统会自动回退到国际象棋引擎，以保证得到合法走法。

对于 Amazon Bedrock 中自定义导入的微调模型，系统采用一套重试机制，与模型进行五次不同的尝试。如果五次尝试全部失败，系统会自动回退到国际象棋引擎，以保证得到走法。

在国际象棋评估测试中，使用超过 100,000 条训练记录完成微调的模型展现出显著的有效性。这些增强模型在对阵基础版本的比赛中 80% 获胜，其余 20% 以和局收场。

**# 删除单个模型文件**

```
aws s3 rm s3://bucket-name/path/to/model/file
```

**# 删除目录中的多个模型文件**

```
aws s3 rm s3://bucket-name/models/ --recursive
```

**# 使用 include/exclude 模式删除特定模型文件**

```
aws s3 rm s3://bucket-name/ --recursive --exclude "*" --include "model*.tar.gz"
```

这段代码使用了以下参数：

- **–recursive** – 删除多个文件或目录时必需
- **–dryrun** – 测试删除命令而不实际移除文件
