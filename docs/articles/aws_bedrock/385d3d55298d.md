# Novo Nordisk 借助 Amazon Bedrock AgentCore 实现制造流程文档现代化

[Novo Nordisk](https://www.novonordisk.com/)（Novo）是全球领先的制药公司之一，为糖尿病和肥胖症等慢性疾病生产药物，并把药物送到许多国家的患者手中。每一款产品背后，都是一张遵循严格质量要求的制造网络。每一个与质量相关的工艺步骤都必须通过正式文档来描述、控制和验证。让这些文档保持最新、准确，是片剂（Tablet）领域制造技术团队的核心职责；这项职责横跨全球组织内一个庞大而多样的受控文档组合，涵盖标准操作规程、工作指令、表单和培训材料。

管理这个文档组合面临不小的挑战。文档更新频繁，驱动因素包括法规变化、工艺改进、设备改造和审计发现。每一次更新都需要仔细评审、结构化的审批工作流，以及与所有受影响相关方的及时沟通。成千上万份活跃文档分散在多个事业部、部门和产品项目之间，要追踪哪些文档到了修订期、哪些在等待审批、哪些需要立即关注，变得越来越复杂。目前，这种监督有很大一部分仍依赖人工流程和碎片化的追踪方式，比如电子表格或彼此割裂的系统。这些方法耗时、容易出错，而且难以扩展。结果是：过时的文档仍可能在流转，更新被延误，合规可见性出现关键缺口。

除了文档管理，还有一个更深层的知识挑战。宝贵的制造知识分散在许多受控文档、版本、工厂和产品项目之中。要在正确的时间找到正确的答案，往往依赖有经验的员工知道该去哪里查。这种对口耳相传的经验知识的依赖形成了瓶颈，拖慢决策，最终影响救命药物多快能送到患者手中。

为应对这些挑战，片剂领域的制造技术团队着手开发一套由 agentic AI 驱动的智能支持系统，部署在 AWS 上。目标是缩短前置时间、提升文档可见性、让关键的制造知识更容易获取，最终帮助组织更快行动、服务全球更多患者。本文深入介绍这套方案的架构，以及为满足受监管制药环境对准确性和可追溯性的高标准而做出的关键设计决策。该方案帮助主题专家（SME）把过去需要数小时甚至数天的工作在几分钟内完成。

我们还会介绍一个 AI 流程智能助手，它能针对复杂的流程问题给出有依据、带引用的回答。这套方案围绕 GraphRAG 架构构建：把知识图谱与混合检索结合起来，检索出最相关、语境上最准确的信息。基于托管 agent 框架构建的 AI agents 端到端地协调检索和应答过程。*引导模式*会在发起检索前帮助澄清模糊的问题，让回答更精确、更经得起质询。

## 挑战

支持制造的团队会反复回答同一个问题的各种变体：*对这个工厂、这个产品、这台设备，工艺流程要求什么？* 要回答好，需要同时具备四样东西：

- 从庞大语料中找对文档。
- 找对版本和生命周期状态（已批准且生效，而不是草稿或已作废）。
- 找对范围（它确实适用于该工厂、该产品代次和设备）。
- 关系（哪些文档引用了哪些文档，一项变更会影响什么）。

传统关键词搜索返回的是文档而不是答案，对范围、版本或关系没有概念。纯基于向量的检索增强生成（RAG）系统提升了对自然语言问题的召回，但在精确标识符（文档编号、设备代码）、多跳关系问题，以及（对受监管领域最重要的）识别相关内容不可用时仍然吃力。团队需要一个把结构和关系当作一等公民、始终扎根于已批准来源、遇到不清楚时去澄清而不是猜测的系统。

## 方案概览

该助手构建在 GraphRAG 架构之上：[Amazon Neptune](https://aws.amazon.com/neptune/) 中的知识图谱捕获结构和关系，[Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/serverless/) 中的混合检索索引对文档内容提供语义和精确匹配召回。两个存储被有意分开，在查询时桥接，而不是合并成单一引擎。这是生产环境中常见的 GraphRAG 模式。

推理层运行在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上，这是一个可以用任意框架或模型大规模构建、连接和优化 agents 的平台。选择 AgentCore 是因为它提供带内置会话隔离的托管 agent 运行时、原生工具编排，以及集成的 AWS Identity and Access Management（IAM）与可观测性。这消除了不必要的底层基础设施工作，让团队可以专注于领域逻辑。agent 运行时用 [Strands Agents SDK](https://github.com/strands-agents) 构建，由 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的 [Anthropic Claude](https://aws.amazon.com/bedrock/claude/) 模型驱动。文档通过一条摄取流水线处理，该流水线用 [Amazon Bedrock Data Automation](https://aws.amazon.com/bedrock/data-automation/) 做多模态解析，由 [AWS Step Functions](https://aws.amazon.com/step-functions/) 和 [AWS Lambda](https://aws.amazon.com/lambda/) 编排。整套技术栈用 [AWS Cloud Development Kit（AWS CDK）](https://aws.amazon.com/cdk/)以基础设施即代码的方式定义。

从高层看，一个问题流经系统的过程是这样的：

- *查询 agent* 接收问题，在引导模式下判断范围是否清晰到足以给出好答案。
- 如果问题模糊，agent 会在检索前先提出一个简短、有图谱依据的澄清问题（例如适用哪个工厂或哪一代产品）。
- 范围清晰后，混合检索取回候选段落，图谱从这些结果向外扩展以补充结构和关系，再进行一次重排序以提升精确度。
- agent 组织出以已批准源文档为依据、并标注引用的答案，在内容不可用时明确说明。

## 两层分类法：结构加领域细节

图谱围绕两个互补的层组织，正是这一点让助手能够考虑文档位于*哪里*，以及它*讲的是什么*。

**高层分类法：流程树。** 组织的官方流程框架被建模为流程节点的层级结构（大致三层，父到子）。每份受控文档都被挂到适用的最低流程层级上，因此每份已接入的文档都有已知的位置。这让助手在检索任何内容之前就能把问题限定到某个流程领域，并自动对新摄取的文档进行分类。

**低层分类法：领域实体。** SME 定义那些决定制造场景中答案对错的实体：工厂、产品代次、设备、工艺步骤以及类似属性。它们被建模为一等图节点，链接到描述它们的文档，并使用一小组统一的关系类型，而不是一份不断膨胀的边名称列表。

对两层都建模，正是真正的 GraphRAG 系统与*两个并排摆着的数据库*的区别所在。OpenSearch 段落上的文档编号同时也是图谱中的一个节点，因此一条搜索命中就是进入图谱结构的立即入口，不需要模糊重新匹配。这种从 chunk 到图谱的桥接是检索路径中的一个关键设计选择。

## 为什么用固定、精选的分类法（以及为什么这是最佳实践）

早期的 GraphRAG 工作偏好开放式抽取，让语言模型在没有固定 schema 的情况下自行发现实体。这种方法对于在海量文本上做开放式*意义构建*很强大，但它嘈杂、难维护、难以审计。过去几年里，共识已转向本体引导的抽取，即用一个预定义的、领域专用的 schema 来引导模型，这能提升专门语料上的准确性和可靠性。

对受监管的制药制造来说，这不是妥协，而是正确的默认选择。这个领域本来就有一套由专家精选的真实本体，而一个固定 schema、外加新实体的人工审核晋级流程，支撑了团队在受监管制药环境中需要的可审计性。这一设计与领域自早期开放式 schema 方案以来的大体走向一致，同时让设计决策更容易向质量和审计相关方解释。

## 检索：混合搜索、图谱扩展与重排序

两个存储各自覆盖对方的盲区：

- **OpenSearch 提供召回——** 混合检索把稠密向量相似度（Amazon Titan Text Embeddings）与词法 BM25 匹配结合起来，并用 reciprocal rank fusion 融合。向量检索捕获语义，词法匹配则抓住这里真正重要的精确 token：文档编号、设备代码和多语言术语。
- **Neptune 提供结构——** 给定搜索浮现出的实体和文档，图谱回答“什么相连、怎么相连、相隔多远”：相邻文档、引用关系、在层级中的位置，以及一项变更的影响，而这些正是纯向量检索做不到的。

常见模式是*向量找到种子，图谱从种子扩展*，关系优先的问题则反过来。融合之后还有一道*重排序*阶段（通过 Amazon Bedrock Rerank 的 cross-encoder）：它把问题和每个候选段落放在一起读并重新排序，在更便宜的召回阶段之上再加一道精确度处理，然后才送到模型。

## 引导模式：先澄清，再检索

该助手一个独特之处在于它如何处理模糊性。像*“在制粒机上取哪些样品？”*这样的问题，取决于产品代次、工厂、设备和批量大小，可能有多个正确答案。立刻作答可能给出一个自信、错误、超出范围的回答，而在受监管环境中这是最糟糕的结果。

引导模式颠倒了通常的 RAG 顺序：agent 先通过澄清收窄范围，然后再检索，而不是先检索。这遵循了近期关于在检索前澄清模糊问题、以及用知识图谱来*提供*澄清选项（而不是让模型编造选项）的研究。它使用两类范围：

- 一小组、近乎通用的属性（如工厂和产品代次），对流程相关的问题会直接、一致地询问。
- 更深层的一切：哪些设备、哪种批量，以及随时间新增的属性。这些都从查询时的图谱中推导出来。一个范围解析步骤会把用户的说法匹配到真实的图节点，按已知信息过滤；如果还剩多个候选，就提供真正能区分它们的那个属性，且只使用图谱中存在的值。

这让澄清选项扎根于真实数据（旨在帮助降低选项被幻觉出来的风险），而且可扩展：当专家向分类法中加入新的区分属性时，助手会自动把它呈现出来，无需修改 prompt 或代码。

## 受监管环境中的依据与信任

这里的准确性被狭义定义，并且刻意强制执行：

- **显式的索引状态——** 一份文档可以先以元数据、关系和在层级中的位置存在于图谱中，之后其内容才可被搜索。一个确定性的标记追踪文档内容是否已被索引，因此助手能区分“我有这份文档的内容”和“我只有它的元数据”，而不是从空搜索结果去推断可用性。
- **默认使用已批准的来源——** 答案依赖已批准且生效的文档以及最新的适用版本，除非用户明确要求草稿或历史修订。
- **反幻觉规则——** 澄清选项和引用论断被设计为来自实际的工具结果，而不是模型自身的知识。
- **明确说明局限——** 当检索到的材料缺失或模糊时，助手会说明，而不是填补空白，并标记何时需要 SME、质量或监管评审。

一个自动化评测框架会按这些标准检查回答：相关来源选择、有效文档状态、最新适用版本、范围合规性、引用准确性，以及对要求强度（must、should 或 may）的忠实保留，从而在系统演进过程中可以度量行为。

## 面向数百万文档库的智能搜索引擎

这套方案所依托的更大文档库约有 400 万份文档。在这种规模下，问题不是信息短缺，而是几乎不可能靠人工找到恰好正确、在范围内、当前有效的答案。传统企业搜索返回的是按关键词重合度排序的长列表，把难活留给提问的人：判断哪条结果适用、哪个版本有效、文档之间如何关联。

这套方案把文档库变成一个智能的、答案优先的搜索引擎，而正是两层分类法让这在规模上变得可行：

- **图谱是完整地图，索引是可搜索的子集。** 所有已注册领域中每份接入的文档都会连同元数据、关系和在层级中的位置被放入图谱。这意味着助手可以推理一份文档位于何处、如何连接，即便其中数百万份的内容尚未被索引。全文内容已为已接入的领域建立索引，并增量补充，助手会明确说明哪些属于哪种情况。
- **范围在检索前收窄搜索空间。** 由于引导模式会先解析工厂、产品代次、流程领域和设备，一个问题会被过滤到文档库中能够回答它的那一小片。系统检索的是范围内那几份文档，而不是几百万份。这有助于在语料增长时保持答案精确。
- **混合搜索加图谱扩展超越关键词排序**，浮现出相关文档、引用和层级关系，这些是排序列表永远无法揭示的，并返回有依据、带引用的答案（而不是十条蓝色链接），同时在内容不可用时说明。

该设计的目标是随文档库扩展而扩展，而不是随着增长而退化：文档越大、连接越密，图谱和范围限定带来的价值就越高。

## 成果

取决于 SME 在做什么类型的任务（查找答案、更新文档，还是为新情境改编文档），过去需要数小时或数天的工作被缩短到几分钟。除了节省的原始时间，这套方案还改变了一些事：过去根本谈不上可行的做法，现在变得实际可行：

- **纵览集团的流程版图——** 用户可以跨流程分类法的全部三层移动，横跨约 400 万份文档及其众多子流程，借助一个既充当搜索引擎、又充当文档、流程和组织地图向导的单一助手。
- **合并结构化与非结构化数据——** 元数据、流程层级和文档内容被统一到一个可搜索的知识图谱中，因此过去分散在不同系统里的信息可以一起查询。
- **理解实体与文档之间的关系——** 图谱帮助用户询问文档、流程、设备、工厂和产品之间如何连接，包括人工搜索无法回答的多跳问题。
- **端到端追踪并校验引用——** 这套方案可以梳理一份文档完整的引用链，并标记文档指向过时或被取代材料的地方，从而在整份语料上暴露完整性问题，而不是一次只看一份文档。
- **扩展到更多的 AI 与 agentic 能力——** 同样有依据的基础为文档生成、带影响分析的修订，以及其他 agentic 工作流打开大门，这些都可以复用同一套图谱、检索和护栏，而不必从零开始。

同样重要的是，在受监管环境中，助手澄清范围并标记缺失或模糊内容的设计有助于降低自信但超范围回答的风险——而错误的真正代价恰恰在这里。

## 协作交付模式

片剂领域的 Novo 制造技术团队与 AWS 合作构建了这套方案，主题专家以及数据和 AI 工程师全程紧密协作。让助手准确的分类法直接来自集团的领域专家。检索和 agent 架构则与 AWS 一起设计并迭代。

构建原型是让方案走向上线的关键。团队没有抽象地争论能力，而是很早就把一套可运行的系统摆在主题专家面前。他们用真实问题测试它，并利用学到的东西打磨分类法、检索路径和引导模式行为。原型把一个宏大的想法变成了人们可以试用、批评并信任的东西。它还在更大范围推广之前降低了架构决策的风险。

## 结论

通过把精选知识图谱、混合搜索和一个“先澄清再检索”的 agent 结合在 Amazon Bedrock AgentCore 上，片剂领域的 Novo 制造技术团队构建了一个流程智能助手：在速度有用的地方快，在准确性重要的地方有依据。该设计把当前的 GraphRAG 模式应用到受监管制造中：本体引导抽取、双存储桥接的检索路径、有图谱依据的消歧，以及重排序。这把一片广大的文档版图变成了有依据、带引用的答案，并且留有扩展到新领域的空间。

要开始构建你自己的 agentic AI 方案，可以了解 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 的托管 agent 运行时、工具编排和规模化可观测性。本文中的 agent 运行时用 [Strands Agents SDK](https://github.com/strands-agents) 构建，这是一个开源、框架无关的工具包，可以配合你自己的检索栈使用。关于使用 Amazon Neptune 和 Amazon OpenSearch Serverless 的 GraphRAG 参考架构，请访问 [AWS 架构中心](https://aws.amazon.com/architecture/)。
