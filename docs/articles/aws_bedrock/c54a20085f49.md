# 在 Amazon Bedrock 上追踪多租户模型推理的成本

为多个租户提供 AI 应用服务的组织面临一个共同挑战：如何跨不同客户细分追踪、分析并优化模型用量。尽管 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 通过其 Converse API 提供强大的[基础模型（FM）](https://aws.amazon.com/what-is/foundation-models/)，但真正的业务价值在于能够把模型交互与特定租户、用户和用例关联起来。

[使用 Converse API](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference-call.html) 的 requestMetadata 参数为这一挑战提供了解决方案。通过在每次请求中传递租户特定的标识符和上下文信息，您可以将标准的调用日志转化为丰富的分析数据集。这种方法意味着您可以在不修改核心应用逻辑的情况下，以租户级精度衡量模型性能、追踪使用模式并分摊成本。

## 通过应用程序推理配置文件追踪和管理成本

为[生成式 AI](https://aws.amazon.com/generative-ai/) 工作负载管理成本是组织每天都要面对的挑战，在使用不支持成本分摊标签的按需[基础模型](https://aws.amazon.com/what-is/foundation-models/) 时尤其如此。当您手动监控支出并依赖被动式控制时，就会带来超支风险，同时引入运维效率低下的问题。

**应用程序推理配置文件**（application inference profiles）通过允许将自定义标签（例如租户、项目或部门）直接应用到按需模型来解决这一问题，从而实现细粒度成本追踪。结合 [AWS Budgets](https://aws.amazon.com/aws-cost-management/aws-budgets/) 和成本分摊工具，组织可以自动化预算告警、为关键工作负载设定优先级，并在规模化场景下执行支出护栏。这种从人工监督到程序化控制的转变降低了财务风险，同时通过增强对跨团队、应用和租户的 AI 支出的可见性来促进创新。

当涉及数十到数千个应用程序推理配置文件时，要追踪多租户成本，请参阅 AWS Artificial Intelligence 博客文章中的 [Manage multi-tenant Amazon Bedrock costs using application inference profiles](https://aws.amazon.com/blogs/machine-learning/manage-multi-tenant-amazon-bedrock-costs-using-application-inference-profiles/)。

在 Amazon Bedrock 中使用应用程序推理配置文件时，大规模多租户环境中的成本和资源管理会变得更加复杂。当面对数十万到数百万租户以及复杂的标签要求时，您会遇到额外的考量。

这些配置文件的生命周期管理带来了运维挑战。您需要大规模处理配置文件的创建、更新和删除。将这些流程自动化，需要针对配置文件命名冲突等边界情况具备稳健的错误处理、为高可用性进行区域特定的复制，以及能维持各租户安全访问控制的级联 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）策略更新。

另一层复杂性来自成本分摊标签的限制。尽管组织和团队可以为每个应用程序推理配置文件资源添加多个标签，但对于有细粒度追踪需求的组织——例如组合租户标识符（`tenantId`）、部门代码（`department`）和成本中心（`costCenter`）——可能会觉得这一限制过于严格，从而可能损害成本归集的深度。这些考量促使组织采用消费端或客户端追踪方法，而这正是基于元数据的打标签可能更合适的地方。

## 结合请求元数据使用 Converse API

您可以在通过 Amazon Bedrock 调用基础模型时使用 Converse API 包含请求元数据。这些元数据不会影响模型的响应，但您可以将其用于追踪和日志记录（由键值对组成的 JSON 对象元数据）。请求元数据的常见用途包括：

- 添加用于追踪请求的唯一标识符
- 包含时间戳信息
- 为请求打上应用特定的信息标签
- 添加版本号或其他上下文数据

请求元数据通常不会在 API 响应中返回。它主要用于您在客户端的追踪和日志记录。

使用 Converse API 时，您通常会将请求元数据作为 API 调用的一部分。例如，使用 [AWS SDK for Python (Boto3)](https://aws.amazon.com/sdk-for-python/) 时，您可能会这样构造请求：

```
response = bedrock_runtime.converse(
    modelId='your-model-id'
    messages=[...],
    requestMetadata={
        "requestId": 'unique-request-id',
        "timestamp": 'unix-timestamp',
        "tenantId": 'your-tenant-id',
        "departmentId": 'your-department-id'
        ...
    },
    # other parameters
)
```

## 解决方案概览

下图展示了一个跨两个主要环境的综合日志处理与分析架构：客户虚拟私有云（VPC）和 AWS 服务账户。

在客户 VPC 中，流程从 Amazon Bedrock 调用日志开始，这些日志由 [AWS Glue](https://aws.amazon.com/glue/) 管理的抽取、转换和加载（ETL）pipeline 处理。日志经过调度器和转换流程，并由 AWS Glue crawler 进行编目。处理失败的日志会被捕获到单独的存储位置。

在 AWS 服务账户部分，架构展示了报告与分析能力。[AWS Quick Sight Enterprise edition](https://aws.amazon.com/quicksight/) 作为主要的分析与可视化服务，提供基于租户的报告仪表板。

[![架构图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/31/ML-18463-arch-diag.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/31/ML-18463-arch-diag.png)

为了将带有租户元数据的 Amazon Bedrock 调用日志转化为可付诸行动的商业智能（BI），我们设计了一个可扩展的数据 pipeline，用于处理、转换并可视化这些信息。该架构由三个主要组件构成，协同交付租户特定的分析。

流程始于客户的虚拟私有云（VPC），Amazon Bedrock 调用日志在其中捕获与您的 AI 应用的每一次交互。这些日志包含有价值的信息，包括您为识别租户、用户和其他业务上下文而配置的 requestMetadata 参数。

ETL 调度器按固定间隔触发 AWS Glue 作业来处理这些日志。AWS Glue ETL 作业从每条日志条目中抽取租户元数据，将其转换为针对分析优化的结构化格式，并将结果加载到转换后的日志存储桶。为保证数据质量，处理失败的记录会被自动路由到单独的失败日志存储桶以便排查。

数据转换完成后，crawler 调度器会激活 AWS Glue crawler 扫描处理后的日志。crawler 会更新 [AWS Glue Data Catalog](https://docs.aws.amazon.com/glue/latest/dg/catalog-and-crawler.html) 中的最新 schema 和分区信息，使您的租户特定数据立即可被发现和查询。

这种自动化编目为您的 Amazon Bedrock 应用中的租户交互创建了统一视图。数据目录通过弹性网络接口连接到您的分析环境，在保持网络隔离的同时提供安全访问。

您在 AWS Quick Sight 账户中的报告基础设施将租户数据转化为可付诸行动的洞察。AWS Quick Sight Enterprise edition 作为您的可视化服务，通过 Quick Sight 到 [Amazon Athena](https://aws.amazon.com/athena/) 的连接器连接数据目录。

您的报告管理员可以创建基于租户的仪表板，展示按租户细分的使用模式、热门查询和性能指标。成本仪表板提供按租户划分的模型使用财务洞察，帮助您理解多租户 AI 应用的经济性。

## 自定义解决方案

[Converse metadata cost reporting 解决方案](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/cost-reporting/converse-metadata-cost-reporting) 提供多个自定义点，以适应您特定的多租户需求和业务需要。您可以通过编辑 `[cdk/glue/bedrock_logs_transform.py](https://github.com/aws-samples/amazon-bedrock-samples/blob/main/cost-reporting/converse-metadata-cost-reporting/cdk/glue/bedrock_logs_transform.py)` 处的 AWS Glue ETL 脚本来修改 ETL 流程，以抽取额外的元数据字段或根据您的租户结构转换数据。schema 定义可以在相应的 JSON 文件中更新，以容纳自定义租户属性或分层组织数据。

对于定价模型不断演进的组织，可以更新存储在 `[cdk/glue/pricing.csv](https://github.com/aws-samples/amazon-bedrock-samples/blob/main/cost-reporting/converse-metadata-cost-reporting/cdk/glue/pricing.csv)` 中的定价数据，以反映当前的 Amazon Bedrock 成本，包括缓存读取和写入定价。编辑该 .csv 文件并上传到您的转换数据 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 存储桶，然后运行定价 crawler 刷新数据目录。这样可确保您的成本分摊仪表板在定价变化时保持准确。

Quick Sight 仪表板可直接通过控制台界面提供丰富的自定义能力。您可以修改现有的可视化以聚焦特定租户指标、添加部门或区域视图的过滤器，并创建符合业务报告需求的新分析洞察。您可以在仪表板编辑器中保存自定义版本，同时保留原始模板以备日后参考。


## 结论

为 Amazon Bedrock Converse API 实施租户特定的元数据，为 AI 应用分析奠定了强大的基础。这种方法将标准的调用日志转化为驱动业务决策并改善客户体验的战略资产。

该架构通过自动化处理租户元数据带来立即可见的好处。您可以获得跨客户细分的使用模式可见性。您可以准确分摊成本，并根据租户特定需求发现模型优化机会。有关实现细节，请参阅 [converse-metadata-cost-reporting](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/cost-reporting/converse-metadata-cost-reporting) GitHub 仓库。

该解决方案能够带来可衡量的业务成果。产品团队可以依据租户使用数据确定功能优先级。客户成功经理可以利用租户特定的洞察提供个性化指导。财务团队可以基于不同客户细分的实际使用模式制定更准确的定价模型。随着 AI 应用在业务运营中变得日益核心，理解不同租户如何与您的模型交互变得至关重要。今天就在您的 Amazon Bedrock Converse API 调用中实施 requestMetadata 参数，为未来的 AI 战略构建分析基础。先从小处着手，确定用于元数据的关键租户标识符，然后随着数据积累扩展分析能力。此处描述的可扩展架构会随您的需求增长。您可以持续完善对租户行为的理解，并交付日益个性化的 AI 体验。
