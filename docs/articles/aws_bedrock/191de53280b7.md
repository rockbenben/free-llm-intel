# 使用 Amazon Bedrock AgentCore gateway 中的 Policy 与 Lambda 拦截器保护 AI agent

保护 AI agent 的行为是构建 agentic 方案时客户面临的关键挑战。随着企业迅速采用 AI agent 来自动化工作流，它们在管理跨组织的安全工具访问方面面临规模化难题。现代统一的企业 AI 平台有数百个 agent 为全组织用户服务。这些 agent 需要访问数千个 Model Context Protocol (MCP) tool，跨越不同团队、组织和业务部门。这种平台规模带来了根本性的治理问题。传统应用执行固定逻辑。由大型语言模型 (LLM) 驱动的 agent 则在运行时决定调用哪些工具、使用什么参数以及按什么顺序调用。由于这一工作流具有动态性，提前审计调用图变得困难。你必须为 LLM 构建机制，使其按你预期的方式行事。

你可以用 [Amazon Bedrock AgentCore gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 通过两种互补机制来保护 agent 和工具：[Policy in Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html) 用于确定性访问控制，[interceptors for AgentCore gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-interceptors.html) 用于动态校验。Policy in Amazon Bedrock AgentCore 让你能对挂在 Gateway 上的工具定义策略。策略用 Cedar 编写，这是一种声明式策略语言，会针对每个请求，依据 *principal*、*action* 和 *resource* 进行评估，并可对请求上下文附加条件。结果是确定性的允许或拒绝决策，并自动记录到审计日志。Lambda 拦截器让你定义自定义代码，在每次工具调用之前或之后运行，支持动态校验、payload 富化、令牌交换和响应过滤。你可以把两种机制结合起来，为 agentic 方案构建分层安全架构。

本文用一个 lakehouse 数据 agent 演示如何用 Policy 做确定性访问控制、用 Lambda 拦截器做动态校验。然后我们展示如何把 Lambda 拦截器与 Policy 结合，实现基于 geography 的访问控制——它同时需要动态校验和确定性访问控制。

## 方案概览

lakehouse 数据 agent 是一个 AI 助手，让保险公司员工可以查询理赔数据。数据存储在 [Amazon S3 Tables](https://aws.amazon.com/s3/features/tables/)（Apache Iceberg）中，通过 [Amazon Athena](https://aws.amazon.com/athena/) 和 [AWS Lake Formation](https://aws.amazon.com/lake-formation/) 查询。应用中有三种用户角色：投保人（policyholder，只能查看自己的理赔）、理赔员（adjuster，管理分配给自己的理赔）和管理员（administrator，拥有包括审计日志在内的完整数据访问权限）。Streamlit UI 通过 [Amazon Cognito](https://aws.amazon.com/cognito/) 对用户进行认证，并把 JSON Web Token (JWT) 传给 agent。

MCP Server 暴露五个 tool：`query_claims`、`get_claim_details`、`get_claims_summary`、`query_login_audit` 和 `text_to_sql`。角色到 tool 的访问权限、租户 IAM 角色映射以及用户 `geography` 存储在 Amazon DynamoDB 中。AWS Lake Formation 在查询时强制实施行级和列级安全。在这种情况下，即使 agent 构造了一条宽泛的 SQL 查询，结果也会自动限定在调用方 IAM 角色被允许查看的范围内。

### 请求流程

下图展示本方案中的工具调用流程：

![工具调用流程图，展示 lakehouse agent 调用 AgentCore Gateway、Request Interceptor Lambda 转换请求、Policy Engine 根据 Cedar 策略评估、lakehouse MCP Server 执行工具，以及 Response Interceptor Lambda 在返回给用户前过滤响应](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/29/ML-20712-2.png)

当 lakehouse agent 通过 AgentCore Gateway 发起工具调用时，请求会被 Request Interceptor Lambda 函数拦截。Request Interceptor 用租户范围的凭证替换 bearer token 来转换请求，并注入额外上下文。随后 Policy Engine 根据 Cedar 策略评估转换后的请求。转换后的请求被用来通过 lakehouse MCP Server 调用工具。然后响应由 Response Interceptor Lambda 函数处理，它在响应返回给用户之前过滤 tool 列表。

Gateway 在 Cedar 策略之前评估请求拦截器。这一顺序是这些设计模式的基础：你先用拦截器富化请求上下文，再用策略评估富化后的上下文。

## AgentCore Gateway 中的 Policy 执行

Policy in Amazon Bedrock AgentCore 使用 Cedar 策略语言，在 Gateway 上实施确定性、可审计的访问控制。Cedar 策略表示为 `permit` 或 `forbid` 规则，针对 principal、action 和 resource 评估，并带有基于 action 上下文的条件。

当授权规则可以表达为针对身份属性、action 标识符和请求上下文的逻辑条件时，我们就用 Cedar 策略做细粒度访问控制。典型用例包括限制某个角色可以调用哪些工具，以及阻止某些用户组访问敏感操作。Cedar 还能基于拦截器注入的上下文属性执行数据驻留规则，并支持在请求到达下游服务之前，在 gateway 上进行作用域检查或时间窗口强制执行。

### 设计 1：仅使用 Policy

首先，来看一个策略充当 lakehouse agent 安全层的例子。假设业务方决定投保人不应调用 `get_claims_summary`。投保人可以查看自己的单条理赔记录，但汇总摘要只保留给理赔员和管理员。要做到这一点，你可以[把 Policy Engine 挂到 Gateway 上](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-getting-started.html)，并定义两条协同工作的 Cedar 策略：一条基线 `permit` 规则和一条针对性的 `forbid` 规则。

当 Policy Engine 挂到 Gateway 上时，它遵循默认拒绝语义。如果没有策略显式允许某个请求，该请求就会被拒绝。因此，你首先需要一条基线 `permit` 策略，允许 agent 在 Gateway 上调用工具：

```
permit(
    principal,
    action,
    resource == AgentCore::Gateway::"<gateway_arn>"
);
```

仅凭这条策略，所有通过认证的用户都可以调用任何工具。

接下来，添加一条 `forbid` 规则，为投保人划出特定限制。因为在 Cedar 中 `forbid` 规则优先于 `permit` 规则，这一条规则就足以阻止目标工具调用，同时保持其他所有访问不变。

```
forbid(
    principal is AgentCore::OAuthUser,
    action == AgentCore::Action::"lakehouse-mcp-target___get_claims_summary",
    resource == AgentCore::Gateway::"<gateway_arn>"
) when {
    principal.hasTag("cognito:groups") &&
    principal.getTag("cognito:groups") like "*policyholders*"
};
```

这两条策略组合起来后，agent 可以调用任何工具，只有投保人试图访问理赔摘要时例外。

**注意：**最佳实践是先把 policy engine 的策略执行模式设为 `LOG_ONLY`。所有策略决策都会写入 CloudWatch，但不会阻塞任何请求。这样你就能在切换到 `ENFORCE` 模式之前，验证每条策略规则是否按预期工作。

![仅 Policy 的调用流程，展示 AgentCore Gateway 验证 JWT、Cedar Policy Engine 基于 Cognito group claim 评估 forbid 和 permit 规则，以及允许请求到达 lakehouse MCP Server 或拒绝请求](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/29/ML-20712-3.png)

当 lakehouse agent 发来请求时，AgentCore Gateway 首先用内置授权验证 JWT 令牌。然后 Policy Engine 根据一组挂载的 Cedar 策略评估该请求。本例中，Cedar 策略采用 forbid-permit 模式：先禁止 OAuth 用户访问 `get_claims_summary` 工具，然后只在 principal 带有匹配 `policyholders` 的 Cognito group 标签时才允许访问。这种确定性策略评估确保只有属于授权组的用户才能调用特定工具。根据策略评估结果，Gateway 要么允许调用 lakehouse MCP Server 并把原始响应返回给 agent，要么在请求到达工具之前将其拒绝。

### 基于 Policy 执行的优势

Cedar 策略为保护 AI agent 带来三个关键好处：

- 确定性。无论 LLM 行为如何，相同的输入总是产生相同的决策。
- 可审计。一旦为 Gateway 启用 CloudWatch 日志投递，每次允许或拒绝决策都会连同完整上下文记录下来，提供完整的审计轨迹。
- 低延迟。Cedar 评估给请求处理带来的开销极小。

## 用于动态控制的拦截器

拦截器是 AgentCore Gateway 在请求生命周期的两个阶段调用的自定义 Lambda 函数。`REQUEST` 拦截器在请求到达下游工具之前运行，`RESPONSE` 拦截器在响应返回给 agent 之前运行。Gateway 会把一个 JSON 事件放在 `mcp` 键下传给每个拦截器，其中包含原始请求头和请求体。拦截器转换请求内容，并以相同结构返回。拦截器适用于所有 Gateway 目标类型，包括 Lambda 函数、OpenAPI 端点和 MCP server。完整的 payload 契约和详细演练见[这篇文章](https://aws.amazon.com/blogs/machine-learning/apply-fine-grained-access-control-with-bedrock-agentcore-gateway-interceptors/)。

当 agent 代表用户调用工具时，一个关键的安全决策是身份如何沿调用链传播。冒充（impersonation）做法是把原始用户 JWT 原样传给每个下游服务。这更简单，但也会让下游服务获得超出所需的权限。一旦某个服务被攻破，它就能在其他地方重用这个权限过高的令牌（即 [confused deputy problem](https://en.wikipedia.org/wiki/Confused_deputy_problem)）。另一种做法是"act-on-behalf"，每个下游目标获得一个单独的、最小权限的令牌，专门限定用于该服务。用户的身份上下文随调用链传递以供审计。设计 2 实现了这一模式。`REQUEST` 拦截器通过 `sts:AssumeRole` 把用户的 Cognito JWT 换成短期、租户范围的 IAM 凭证，最终到达 MCP Server 的正是这些限定范围的凭证。

### 设计 2：仅使用拦截器 —— act-on-behalf 令牌交换与上下文传播

`REQUEST` 拦截器中发生了三项 Cedar 无法完成的操作：

- JWT 到 IAM 的令牌交换（act-on-behalf）。从 JWT 中读取用户的 Cognito 组，在 DynamoDB 中查找对应的租户 IAM 角色，并调用 `sts:AssumeRole` 获取短期限定范围的凭证。
- 上下文注入。把用户身份和临时 IAM 凭证写入 MCP 请求体的 `params.arguments.context`，使 MCP Server 能用它们构造限定范围的 Athena 客户端。
- 工具授权。在转发请求前检查 DynamoDB 中的 `allowed_tools`，对未授权调用返回结构化的 MCP 错误。

`REQUEST` 拦截器处理函数（简化版）：

```
def lambda_handler(event, context):
    # Parse the MCP gateway request from the interceptor event
    mcp_data = event.get('mcp', {})
    gateway_request = mcp_data.get('gatewayRequest', {})
    body = gateway_request.get('body', {})
    headers = gateway_request.get('headers', {})

    token = extract_bearer_token(headers)
    claims = validate_and_decode_jwt(token)  # Step 1: validate Cognito JWT

    # Step 2: check tool authorization against DynamoDB allowed_tools
    is_authorized, error_msg, tool_name = validate_tool_access(claims, body)
    if not is_authorized:
        return build_mcp_error_response(error_msg, status_code=403)

    # Step 3: act-on-behalf --- exchange JWT group claim for tenant IAM credentials
    claim_name, claim_value = get_claim_for_exchange(claims)
    tenant_credentials = exchange_jwt_to_iam(claim_name, claim_value)  # sts:AssumeRole

    # Step 4: inject user identity and scoped credentials into the MCP request body
    if 'params' in body and 'arguments' in body['params']:
        body['params']['arguments']['context'] = {
            'user_id': user_principal,
            'tenant_credentials': {
                'access_key_id': tenant_credentials['AccessKeyId'],
                'secret_access_key': tenant_credentials['SecretAccessKey'],
                'session_token': tenant_credentials['SessionToken'],
            }
        }

    # Return transformed request in the required interceptor output format
    return {
        'interceptorOutputVersion': '1.0',
        'mcp': {
            'transformedGatewayRequest': {
                'headers': transformed_headers,
                'body': body,
            }
        }
    }
```

MCP Server 收到带有注入上下文的转换后请求。每个 tool 函数接受一个 context 参数，并用它构造限定范围的 Athena 客户端。然后 Lake Formation 在查询时根据租户角色的权限自动应用行级和列级过滤器，无需 SQL WHERE 子句：

```
# server.py --- query_claims tool
def query_claims(claim_status=None, context=None):
    user_id, tenant_creds = get_user_id_with_fallback(context)

    # Athena client uses the tenant's scoped IAM credentials (not the user's JWT)
    # Lake Formation applies row-level and column-level filters automatically
    athena_client = boto3.client(
        'athena',
        aws_access_key_id=tenant_creds['access_key_id'],
        aws_secret_access_key=tenant_creds['secret_access_key'],
        aws_session_token=tenant_creds['session_token']
    )
    ...
```

### 用 Response 拦截器动态过滤工具

Response 拦截器还让你控制工具响应后 agent 能看到什么。最常见的用途是过滤 tool 列表和语义搜索响应，让每个用户只看到自己有权调用的工具。你也可以与 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 等服务集成，用于 personally identifiable information (PII) 遮蔽等场景。这通过对 agent 隐藏未授权工具、防止 PII 等敏感信息泄漏来提升安全性。同时它也提升可靠性：给 LLM 一个更小、范围正确的 tool 列表，减少错误的工具选择决策。

## Policy 与 Lambda 拦截器的选用时机

Policy 与拦截器不可互换。它们在安全架构中承担不同职责。下表总结了关键决策标准。

| **考量因素** | **使用 Policy** | **使用 Lambda 拦截器** |
| --- | --- | --- |
| 规则性质 | 针对已知属性的确定性逻辑条件 | 需要外部数据或运行时计算 |
| 外部查询（DynamoDB、STS、API） | 不支持 | 完全支持 |
| Payload 转换 | 不支持 | 对请求头和请求体有完全读写权限 |
| 响应修改 | 不支持 | `RESPONSE` 拦截器 |
| 延迟影响 | 可忽略（Cedar 评估 <1 毫秒） | Lambda 冷启动 + 执行时间 |
| 可审计性 | 自动按决策记录 CloudWatch 日志 | Lambda 日志（需手动埋点） |
| 紧急阻断 | 通过 API 添加 `forbid` 规则，立即生效 | 需要重新部署 Lambda |
| 规则变更速度 | 高：API 调用，无需重新部署 | 低：改代码 + 重新部署 |
| 评估顺序 | 在 `REQUEST` 拦截器之后 | 在 Cedar Policy 之前 |
| 令牌交换 / 凭证发放 | 不支持 | 完全访问 STS 和 secrets |
| 语义搜索过滤 | 不支持 | `RESPONSE` 拦截器 |

以下情况使用 Policy：

- 你需要一条硬性的、可审计的边界，agent 或 LLM 都无法绕过。
- 授权规则只依赖身份 claim、action 名称、resource ARN 或请求中已有的上下文。
- 你需要一个紧急停止开关。`forbid` 规则通过控制面 API 立即生效。

以下情况使用拦截器：

- 规则需要必须在运行时获取的数据（DynamoDB、secrets、外部授权服务）。
- 你需要在请求 payload 到达工具之前对其进行转换或富化。
- 你需要在工具响应返回给 agent 之前对其进行过滤或净化。
- 授权决策是有状态的——例如令牌交换或按用户限流。
- 你需要在方法级别（`tools/call` 对比 `tools/list`）而非工具级别实施授权。

设计目标是可组合性。凡是本质上动态的部分都用拦截器，凡是能表达为针对富化上下文的逻辑规则的部分都用 Cedar。因为 `REQUEST` 拦截器在 Cedar 之前运行，两种机制形成一条自然的流水线，而不是争抢同一职责。

## 组合使用 Policy 与 Lambda 拦截器

当策略与拦截器协同工作时，每一层各司其职。下图展示结合 Policy 与 Lambda 拦截器的分层安全调用流程：

![分层安全调用流程，结合 Policy 与 Lambda 拦截器。AgentCore Gateway 把请求路由到 Request Interceptor Lambda，后者注入 geography、user_id 和租户凭证。Policy Engine 评估富化后的请求，若允许，Gateway 调用 lakehouse MCP Server。Response Interceptor 在响应返回给 agent 前过滤工具。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/29/ML-20712-5.png)

在这一模式中，当 lakehouse agent 发来请求时，AgentCore Gateway 验证 JWT 令牌，并把原始请求路由到 Gateway Request Interceptor Lambda。该拦截器通过动态注入 `geography`、`user_id` 和租户凭证来富化请求。然后 Policy Engine 基于这一富化上下文执行确定性的 Cedar 策略评估，给出一致的访问决策。如果允许，Gateway 就用带有注入租户凭证的转换后请求调用 lakehouse MCP Server。当 MCP Server 返回原始响应时，Gateway Response Interceptor 会根据用户权限动态过滤 tool 列表并遮蔽敏感信息，然后把转换后的响应返回给 agent。

评估顺序是 `REQUEST` 拦截器先于 Cedar 策略。通过这种组合，你可以用拦截器从任何来源获取任何数据并注入请求参数，再用 Cedar 策略评估已经富化的请求。在下一个设计模式中我们会再次看到这一点。

### 设计 3：Policy + 拦截器 —— 基于 geography 的访问控制

这一模式应对一个合规要求示例。我们要建立一条边界：从欧盟（EU）司法辖区操作的用户不能访问单条理赔记录，只能访问汇总摘要。这是一条数据驻留规则，把动态属性（存储在 DynamoDB 中的用户 `geography`）与确定性策略规则（EU 用户不得调用 `query_claims` 或 `get_claim_details`）结合起来。

Cedar 无法从 DynamoDB 获取 `geography`。Lambda 拦截器无法表达带自动审计日志的声明式 `forbid` 语义。Policy 与 Lambda 拦截器的组合同时解决这两点：用 Lambda 拦截器获取 `geography` 并富化请求；然后 Policy 利用这个富化后的请求，在把请求传给目标之前，根据用户 `geography` 评估单条理赔记录的访问。

#### 第 1 步：拦截器获取 geography 并注入工具参数

```
# interceptor-request/lambda_function.py

# Production: fetch geography from DynamoDB table 'lakehouse_user_geography'
# This demo uses an in-Lambda mapping for simplicity
USER_GEOGRAPHY: Dict[str, str] = {
    'policyholder001@example.com': 'US',
    'policyholder002@example.com': 'EU',
    'adjuster001@example.com': 'US',
    'admin@example.com': 'US',
}

# After existing context injection, inject geography at the TOP LEVEL of arguments.
# Cedar evaluates it as context.input.geography.
# If placed inside context (params.arguments.context.geography),
# Cedar would need context.input.context.geography --- harder to express cleanly.
geography = USER_GEOGRAPHY.get(user_principal, 'UNKNOWN')
if 'params' in transformed_body and 'arguments' in transformed_body['params']:
    transformed_body['params']['arguments']['geography'] = geography

logger.info(f'Injected geography={geography} for user={user_principal}')
```

**关键细节：**Cedar 把工具参数引用为 `context.input.<field>`。Cedar 可以访问任意字段，不论嵌套深度如何，但把 `geography` 放在 `params.arguments` 的顶层能让策略保持简洁。这样它就可以引用为 `context.input.geography`，而不是嵌套时的冗长写法 `context.input.context.geography`。

#### 第 2 步：Cedar 策略评估注入的 geography

```
// EU users cannot access individual claim records (GDPR data-residency requirement).
// The broad permit_all rule still allows EU users to call get_claims_summary.
forbid(
    principal,
    action in [
        AgentCore::Action::"lakehouse-mcp-target___query_claims",
        AgentCore::Action::"lakehouse-mcp-target___get_claim_details"
    ],
    resource == AgentCore::Gateway::"<gateway_arn>"
) when {
    context.input has geography &&
    context.input.geography == "EU"
};

// Restricted geographies are denied all tool access.
forbid(
    principal,
    action in [
        AgentCore::Action::"lakehouse-mcp-target___query_claims",
        AgentCore::Action::"lakehouse-mcp-target___get_claim_details",
        AgentCore::Action::"lakehouse-mcp-target___get_claims_summary",
        AgentCore::Action::"lakehouse-mcp-target___query_login_audit",
        AgentCore::Action::"lakehouse-mcp-target___text_to_sql"
    ],
    resource == AgentCore::Gateway::"<gateway_arn>"
) when {
    context.input has geography &&
    context.input.geography == "RESTRICTED"
};
```

三条 `forbid` 策略由同一个 Cedar Policy Engine 一起评估。只要有任意一条 `forbid` 规则匹配，无论是否有 `permit` 规则匹配，请求都会被拒绝。

#### 组合设计的职责矩阵

| **控制项** | **由谁处理** | **为何由这一层处理** |
| --- | --- | --- |
| 用户认证（JWT） | Gateway JWT Authorizer | 内置能力，无需自定义代码 |
| 工具授权（组 → 工具） | Cedar Policy (`forbid`) | 声明式、可审计、无需重新部署 Lambda |
| act-on-behalf 令牌交换 | Lambda 拦截器 | 需要 `sts:AssumeRole` —— Cedar 无法调用 API |
| 上下文注入（`user_id`、凭证） | Lambda 拦截器 | 需要 DynamoDB 查询和 payload 修改 |
| Geography 查询与注入 | Lambda 拦截器 | 需要 DynamoDB 查询和 payload 修改 |
| 基于 Geography 的访问控制 | Cedar Policy (`forbid`) | 针对注入属性的声明式规则，带审计日志 |
| Tool 列表过滤（用户体验） | `RESPONSE` 拦截器 | 需要修改响应体 |
| 行/列数据安全 | Lake Formation | 在 Gateway 层之下由后端强制执行 |

### 设计 3 的策略评估结果

| **用户** | **Geography** | **工具** | **预期结果** | **决策方** |
| --- | --- | --- | --- | --- |
| policyholder001 | US | `query_claims` | 允许 | 无 forbid 规则匹配 |
| policyholder002 | EU | `query_claims` | 拒绝 | Cedar：EU 对单条理赔的 forbid |
| policyholder002 | EU | `get_claims_summary` | 拒绝 | Cedar：设计 1 的投保人 forbid |
| adjuster001 | US | `get_claims_summary` | 允许 | 无 forbid 规则匹配 |
| adjuster002 | EU | `get_claim_details` | 拒绝 | Cedar：EU 对单条理赔的 forbid |
| any user | RESTRICTED | any tool | 拒绝 | Cedar：RESTRICTED geography forbid |

## 可观测性：贯穿流水线的端到端可追溯性

AgentCore Gateway 与 AgentCore Observability 及 Amazon CloudWatch 集成，在每个执行层提供可追溯性。每一层都会留下独特、可查询的轨迹。Gateway JWT authorizer 记录每个请求的令牌验证结果。`REQUEST` 拦截器 Lambda 函数记录 JWT claim 提取、DynamoDB 查询结果、令牌交换结果和 `geography` 注入。Policy Engine 每次评估都记录完整授权上下文以及由此产生的 ALLOW 或 DENY 决策。`RESPONSE` 拦截器 Lambda 函数记录从 `tools/list` 和语义搜索响应中过滤了哪些工具，提供每个用户的工具可见性记录。

## 结论

本文演示了三种设计模式，用 Policy、Lambda 拦截器以及两者的组合来构建安全的 agent。当授权规则是确定性的、可基于身份和上下文表达时，用 Policy。当规则需要外部数据、payload 转换或令牌交换时，用 Lambda 拦截器。当你需要在运行时获取动态上下文并以声明方式对其实施规则时，把两者结合。在构建 agentic 方案时，你可以用这些模式来保护 agent 行为。
