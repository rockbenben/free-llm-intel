## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 打造人工智能构建者：缩小人工智能知识能力差距的手册

采用人工智能的最大障碍不是意识。这是谈论人工智能和利用人工智能进行构建之间的差距。

主要职责不是编写代码，但日常工作越来越依赖人工智能解决方案的专业人士不需要工程背景来开始构建人工智能能力。他们需要正确的工具、结构化的支持以及失败的许可。以下是我们如何证明这一点，以及如何复制它。

## 问题组织被忽视

您的团队已经在进行人工智能对话，无论他们是在回答客户的问题、评估供应商解决方案，还是在日常职责中识别自动化机会。考虑到代理人工智能工具普遍可用的速度，他们中的大多数人从未使用他们正在讨论的工具构建过任何东西。

这些团队，无论是销售、运营、财务还是产品部门，都观看了演示并完成了认证。但是，当有人问“这实际上是如何工作的？”时，他们无法通过自己构建来得到答案。

成本是真实的：采用速度较慢，生产力提高延迟，错过了识别用例的机会，以及您的团队“了解”和他们可以“实施”之间的脱节越来越大。

我们询问了商业专业人士，即那些每天使用人工智能工具但不编写生产代码的人，是什么阻碍了他们采用人工智能。答案不是“我不想学习”。 90% 的人希望获得构建人工智能代理的实践经验。他们缺少安全建造所需的结缔组织和脚手架。下图说明了业务团队在尝试使用人工智能进行构建时面临的最常见障碍。

图 1：业务团队认为使用人工智能进行构建的主要障碍

在较高层面上，他们可以谈论 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 和 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)，这是一个使用任何框架或模型大规模构建、连接和优化代理的平台（80% 的人已经探索过）。但只有不到五分之一的人接触过 Strands Agents SDK 或使用 [AWS Lambda](https://aws.amazon.com/lambda/) 代理构建。他们选择退出黑客马拉松和举办活动，因为他们不相信自己的技术知识足以与工程师竞争。

为了解决这个问题，我们设计了一个为期六周的结构化计划，将业务专业人员与导师和生产级工具配对，以构建可以超出计划范围的工作人工智能原型。目标：缩小概念知识和实践能力之间的差距。

## 一个团队构建了什么：六周内的证明

四位从未合作过的面向客户的专业人士参加了我们的计划。没有人有工程背景。六周后，他们展示了自己的原型 WealthWise，这是一种多代理人工智能财务咨询工具，并获得了第一名。

他们建造了什么：

- **五名专业人工智能代理**提供智能财务咨询：投资组合分析、风险评估、财务规划、市场洞察和个性化投资建议。
- **双服务器架构**（`Node.js` + Python Flask）与 Amazon Nova 模型。*
- **Strands Agents SDK** 用于多代理编排和对话内存。
- **四个 Amazon DynamoDB 表**用于实时数据持久性。
- **实时市场数据集成**，提供情境感知的财务建议。
- **复杂财务推理的响应时间不到 5 秒**。

该系统具有协调决策的特点：每个代理独立决定调用哪些工具，并将多个工具链接在一起，跨投资组合数据、市场数据库和财务规划模型执行多步骤推理。

他们将自己的成功归功于第一天制定的五项原则：

- **学习胜过获胜** – 选择具有挑战性的方法而不是安全的捷径，让他们能够毫无恐惧地进行实验。
- **定期节奏** – 每日站立会议可以防止孤立并尽早发现问题。
- **从最小可行产品 (MVP) 开始，然后完善** – 在第 2 天进行端到端流程，然后进行迭代。
- **参与办公时间** – 当遇到困难时积极寻求指导。
- **玩得开心** – 在技术输出之前先心理安全。

参与者反思了实践形式如何加速他们的学习：

> “这次黑客马拉松的时机非常完美，事实证明，实践形式对于 AgentCore 的实现非常宝贵——加速了原本漫长的学习曲线。”

> “很棒的团队建设和人工智能学习项目！我自学了很多东西，并且对刚接触人工智能解决方案的客户有更多的同理心。”

## 剧本：我们如何设计该程序

以下部分详细介绍了程序结构、每个阶段以及使其发挥作用的设计决策。

### 程序结构

该计划持续六周多，参与者每周投入大约四个小时。我们特意以这种方式构建：根据我们的计划数据，完成分阶段计划的参与者保留的实践技能比两天强化计划的参与者多三倍。不为主要工作编写代码的专业人员需要迭代周期：在信心变得持久之前，有时间与不熟悉的概念作斗争、恢复和重新构建。

### 第 0 阶段：招募和计划设置

我们通过经理提名、Slack 和电子邮件活动招募参与者，目标受众是每天使用人工智能解决方案但不构建这些解决方案的专业人士：客户经理、解决方案顾问、运营分析师、项目经理和类似角色。管理层的支持是第一位的。我们向团队领导简要介绍了时间投入（每周四小时，持续六周），并将其视为对流畅性和对话质量的投资，而不是分散他们日常交付的注意力。

该计划由四名核心团队成员和导师精心策划，他们在日常工作的同时负责该计划。这是一个关键的可复制性点：这不需要专门的项目团队，但确实需要至少一个具有足够组织信任的人来保护参与者的时间。

### 第一阶段：团队组建和启动

**参与者做什么：** 组成 3-4 人的团队，有意混合不同的经验水平。团队定义与他们在角色中遇到的真实场景相关的问题陈述。

**这会产生什么：** 可以演示的范围项目概念和团队责任结构。

**在继续之前为什么这很重要：**如果没有具体的问题需要解决，支持会议就会变得抽象。定义目标用例的团队首先有目的地吸收技术内容。

### 第 2 阶段：启用

**参与者做什么：** 参加有关代理 AI 概念和 AWS 工具的现场培训课程。这些不是讲座。参与者在构建阶段使用的实际工具中工作，完成反映其项目工作的结构化练习。

**这会产生什么：** 基线技术流畅性和本地工作环境。

**为什么这在继续之前很重要：**直接跳到构建的团队在环境设置和基本概念方面遇到了障碍。此阶段避免了最常见的下车点。

### 第 3 阶段：构思、构建和开发

**参与者做什么：** 在数周内设计和迭代工作原型。每个团队都配有一位技术精湛的导师，他提供安全网、解决基础设施问题并提出架构模式建议，而无需为他们做任何工作。

**这会产生什么：** 可以向利益相关者或客户演示的功能原型。

**在继续之前为什么这很重要：** 延长的时间线允许 2-3 个迭代周期。在第 3 周构建原型的团队有时间不断应用新的学习内容，将其拆除，并在第 5 周更好地重建。迭代才是真正学习发生的地方。

### 第 4 阶段：评审和演示

**参与者的职责：** 提供现场演示，评估内容涵盖五个类别：业务影响、技术卓越、可重用性和可扩展性、创新和演示质量。

**这会产生什么：** 经过同行验证的能力证明和可重用原型库。

**为什么这很重要：** 演示格式反映了参与者在与客户、领导层和跨职能合作伙伴的真实对话中将做什么。评判标准强调“工作”是不够的。它必须具有影响力、可扩展性和清晰的沟通。

### 关键设计决策

对于非工程师的建筑商来说，工具选择是最重要的决定。错误的工具会产生阻碍动力的摩擦。合适的人会抽象基础设施并满足人们当前专业水平的需求。我们选择：

- [Kiro](https://kiro.dev/) 用于自然语言开发的集成开发环境 (IDE)：描述您想要的内容，并构建架构。
- 适用于该区域中可用的 API 可访问基础模型的 Amazon Bedrock：无需机器学习 (ML) 专业知识即可从模型获得工作响应。
- 用于可组合代理模式的 Strands Agents SDK：代理像构建块一样组合。
- [AWS 模型上下文协议 (MCP) 服务器](https://docs.aws.amazon.com/agent-toolkit/latest/userguide/mcp-server.html) 和 AWS Lambda 代理推动团队转向可部署的生产级架构，而不仅仅是本地笔记本。

核心原则从未改变：构建一些可以在短时间内演示的真实内容。

### 管理日常工作中断

我们特意将每周承诺的时间限制为四个小时，并为参与者提供了在这些时间发生的时间上的灵活性。最常见的反馈是，参与者在前两周内将他们所学到的知识直接应用到工作中，使时间投入感觉是累加的，而不是竞争的。

## 影响：从观察者到建设者

当我们的参与者亲身体验人工智能工具时，他们从讨论可能性转向构建工作原型。数字讲述了这个故事：

- 自评“强或专家”对代理人工智能的理解：从 27% 增加到 82%（+55 个百分点）。
- 感觉“准备好或非常准备”来识别 AI 机会：从 41% 增加到 85%（+44 个百分点）。
- 仅具有理论或有限经验的参与者：从 34% 下降到 0%（已删除）。

对此进行投资可以解锁以下内容：

**对于您的团队：** 他们不再是人工智能观察者，而是成为人工智能构建者。他们知道什么是可行的，什么是昂贵的，以及什么是通过直接实验周末构建的。在我们的队列中，52% 的人确定了可以从他们在该计划期间构建的产品中受益的特定客户，87% 的人希望在 30 天内将他们学到的知识应用到客户身上。该程序超额交付了实际用例，因为它要求他们自己创建示例。

**对于您的工程组织：** 当业务伙伴可以建立原型并阐明架构权衡时，工程团队可以花更少的时间来翻译需求，并花更多的时间进行构建。技术构建者可以获得更清晰的信息、更少的不一致请求，以及可以在提交单个冲刺之前对可行性进行压力测试的合作伙伴。考虑一下：82% 的参与者对代理 AI 架构有深入的了解。整个堆栈的工具流畅度大幅提升：Strands Agents SDK 的采用率从 20% 上升到 80%（+60%），AgentCore 从 39% 上升到 85%，提高了工程判断的标准。

**对于您的客户来说：** 他们拥有的合作伙伴通过拥有直接的实践经验，解决了他们所面临的相同架构权衡问题。对话从“让我回复你”转变为现场演练。在该计划之前，44% 的参与者将架构模式的不确定性视为障碍。计划结束后，90% 的人感觉自己已经做好充分准备，或者更好地在真实客户对话中发现人工智能机会。

**对于您的组织：** 您将获得一个可复制的复合模型。我们的试点从一个团队扩展到区域部署，现在又扩展到全球部署，这证明了这种模式：实践的流畅性会自行扩展。该计划获得了 100% 的推荐率，95% 的参与者表示该计划达到或超出了预期。

## 在您的组织中复制这一点的七个教训

这七个经验总结了该计划的成功因素以及在您自己的组织中可以复制的内容。

### 1. 工具选择改变一切

低代码、代理体验消除了“我技术不够”的障碍。这是一个计划设计决定，而不是采购后的想法。如果你的工具需要精通 Python，那么在第一周之前你就已经损失了一半的空间。

### 2. 结构胜过强度

对于非技术受众来说，具有明确里程碑的分阶段计划（6 周）优于为期两天的冲刺。预计第一周会感觉缓慢。之后是复合。

### 3. 指导是事半功倍

将非技术参与者与技术熟练的导师配对可以消除对失败的恐惧并加速学习。导师不是为他们构建的。他们提供了一个安全网。

### 4. 构建一些真实的东西

需要带有代码存储库和参考架构（而不是幻灯片）的工作原型迫使人们深入使用这些工具。你无法通过现场演示来伪装自己。这就是黑客马拉松与培训课程的区别。

### 5. 测量之前和之后

之前和之后的能力评估使影响可见并构建扩展的业务案例。自我报告的信心是有用的，但从“有限”到“广泛”的实践经验的转变才是重要的。

### 6. 使其可复制

详细记录的剧本（参与者指南、评估规则、导师配对框架、环境设置指南）可将一次性活动转变为可扩展的计划。

### 7. 创造心理安全第一

当人们不害怕失败时，他们就会创造出他们从未想过可能实现的东西。获胜团队将“学习胜于获胜”作为他们的首要原则。每个蓬勃发展的团队都在编写代码之前建立了信任。
