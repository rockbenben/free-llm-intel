# 使用 Amazon Bedrock AgentCore Browser Tool 自动化遗留 Web 应用

医疗、制造、零售和金融等行业的企业都难以自动化那些需要类人交互的遗留 Web 应用，而标准的机器人流程自动化（RPA）无法大规模提供这种能力。Amazon Bedrock AgentCore Browser Tool 结合 Strands Agents，通过一项全托管的浏览器服务填补了这一空白，让 AI agents 能够通过安全、隔离的会话来驱动这些遗留界面。由于大多数企业仍在遗留技术上运行关键工作负载，且这些系统大多只暴露由服务端中间件渲染的 HTML，而非现代 API，大量手工数据录入仍然是一大成本中心和数字化转型的障碍。

设想一个各行业企业都熟悉的场景：一家大型保险公司每年在遗留保单管理系统中处理数以万计的操作变更，包括方案修改、理赔调整、保额更新和批单。由于需要专职员工在遗留服务端中间件生成的复杂 Web 界面中操作，仅人工失误一项就给组织带来巨大的年度损失。每一次变更都需要走完多步骤工作流、在多个屏幕中输入数据，并根据业务规则进行校验。这些任务消耗了数千小时。在遗留 Web 应用仍是关键业务运营支柱的地方，这种模式在各行各业不断重演。

Amazon Bedrock AgentCore Browser Tool 通过提供一项全托管的、基于云的浏览器服务来应对这些限制，AI agents 可以通过安全、隔离的浏览器会话与遗留 Web 界面交互。Browser Tool 通过基于 WebSocket 的 Chrome DevTools Protocol（CDP）连接来集成 Playwright，因此 AI agents 可以与遗留 Web 应用交互，而无需关心其底层技术栈。Browser Tool 在云端运行一个托管的 Chromium 实例。目标遗留应用只需能通过 HTTP 或 HTTPS 访问，无论它最初是为哪种浏览器设计的。

结合 [Strands Agents](https://strandsagents.com/) 进行模型驱动的编排，组织可以实现复杂的自动化工作流，从单步骤自动化扩展到多 agent 复杂工作流。该解决方案通过 [Amazon Bedrock AgentCore runtime](https://aws.amazon.com/bedrock/agentcore) 与 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 的 foundation models（FMs）集成，提供会话隔离的安全性、AWS Identity and Access Management（IAM）控制和完整的审计轨迹。这可以帮助企业实现关键工作流的现代化，同时满足监管合规要求并保留人工监督。

在本文中，我们将介绍一个使用 Amazon Bedrock AgentCore Browser Tool 和 Strands Agents 构建的 AI 驱动数字员工的参考实现。我们将讨论其架构、关键设计决策，以及包含 terraform 部署的企业蓝图。完整源代码可在 [GitHub](https://github.com/aws-samples/sample-agentcore-browser-legacy-automation) 上获取。

## 理解业务与技术挑战

企业级 RPA 实施通常面临三项重大技术挑战，传统自动化方法难以应对。它们是遗留 Web 应用集成的复杂性、受监管行业的合规要求，以及阻碍成功生产部署的可扩展性限制。

### 遗留 Web 应用的复杂性

回到保险公司的场景，其保单管理系统与许多行业的遗留应用一样，是在几十年前基于服务端中间件构建的，由该中间件为浏览器生成 HTML、CSS 和 JavaScript。这些系统缺乏现代 REST API，迫使自动化方案只能通过最初为人类用户设计的 Web 界面进行交互。这些应用具有复杂的多步骤工作流、动态表单校验和依赖会话的状态管理，传统 RPA 机器人无法可靠地应对。经过数十年的修改造成的文档缺失带来了额外的复杂性，关键业务逻辑只存在于机构经验中，而非可查阅的系统规格说明里。

身份验证机制进一步加剧了问题。有些遗留应用需要多因素身份验证（MFA），有些使用专有的单点登录（SSO），还有许多依赖过期规则不可预测的会话 token。基于规则的 RPA 机器人在这里举步维艰，这也是生产部署最终会留下大量人工干预长尾的原因。在我们的保险场景中，操作员需要在复杂的 Web 界面中操作以修改方案。他们更新保额、调整受益人、处理批单，每一步都需要多个屏幕和校验步骤，而当 UI 渲染与预期不同时，脆弱的、基于规则的机器人无法可靠应对。

### 合规与审计要求

受监管行业必须实施全面的审计轨迹，记录用户身份、时间戳、数据修改和系统交互，以满足 GDPR、HIPAA 和金融法规的要求。技术实现需要不可篡改的日志系统、加密的数据传输和基于角色的访问控制，而传统 RPA 系统若不进行大量定制开发就无法提供这些能力。金融法规要求防篡改的记录保存六年，且最近 90 天的记录必须可立即访问。这些要求需要复杂的日志架构，而大多数 RPA 系统都缺乏这种架构。

在这个场景中，每一次保单修改都必须可追溯。这意味着要记录是谁发起变更、变更了什么、何时变更，以及是否获得批准。AI 驱动的数字员工必须提供与人工操作员相当甚至更高的可审计性。

### 可扩展性与脆弱性

传统 RPA 方案面临根本性的架构约束，使其无法在企业级规模上取得成功。基于 UI 的自动化会形成对屏幕布局、元素定位和应用时序的脆弱依赖，稍有系统更新就会失效。传统 RPA 基于规则的本质无法处理异常、动态内容或复杂业务流程所需的认知决策。性能限制又加剧了这些问题。传统 RPA 机器人需要专用的虚拟机或物理系统，带来资源开销和扩展限制。在处理多个并发流程时，会话管理变得复杂，而错误恢复机制仅限于预定义场景，无法自适应地解决问题。

对于我们的保险公司而言，该组织每年处理数以万计的方案变更。要扩展传统 RPA 以处理参保期、监管变更和年末处理等高峰容量，同时保持可靠性，被证明是不切实际的。该组织需要一种能够弹性扩展、并在页面以意外状态呈现时智能恢复的方法。

## 解决方案架构

应对这些挑战需要一种自动化方案，能够处理 JavaScript 密集的 Web 界面、在各流程之间隔离会话、通过 API 暴露程序化控制、以不可篡改的方式记录每一次交互、在置信度低时交由人工处理，并能弹性扩展。参考实现通过一小组职责范围明确的组件来满足这些要求。这些组件包括面向操作员的 React 单页应用、解决特定浏览器限制的 TLS 终止 proxy、在 Amazon Bedrock AgentCore runtime 上运行 Strands Agents 的 Python worker，以及由 Amazon Bedrock AgentCore Browser Tool 提供的托管浏览器环境。[Amazon Cognito](https://aws.amazon.com/pm/cognito/) 负责操作员登录，并签发在整个技术栈中流转的 JWT。该架构旨在帮助提高自动化的投资回报，同时保持安全性、合规性和人工监督。

图 1：解决方案架构

图中的编号步骤勾勒出端到端的流程：

- **加载 UI。**用户的浏览器从 [Amazon CloudFront](https://aws.amazon.com/cloudfront/) 加载 React 聊天界面，其背后是一个托管静态 UI 资源的私有 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/pm/serv-s3/) 存储桶。
- **OIDC 登录。**用户通过标准的 OpenID Connect（OIDC）登录流程，经由 Amazon Cognito（配置了 SPA 和 machine-to-machine 应用客户端）进行身份验证。
- **WSS。**浏览器通过一个 AWS Application Load Balancer（ALB）打开 WebSocket 连接，该 ALB 使用 AWS Certificate Manager（ACM）证书终止 TLS。
- **明文 HTTP。**ALB 将 WebSocket 连接转发到在私有子网中作为 [AWS Fargate](https://aws.amazon.com/fargate/) 任务运行的 NGINX 反向 proxy。该 proxy 从查询字符串中提取 JWT，并为下一跳做好准备。
- **WSS Auth Bearer。**NGINX proxy 将连接转发到 Amazon Bedrock AgentCore runtime，并在 Authorization 标头中携带 JWT。AgentCore runtime 通过其 JWT 授权方验证 token，并路由到运行 Strands Agents、VisualBrowserTool 和 human-in-the-loop 处理程序的 browser-agent 容器。
- **InvokeModel。**agent 调用 Amazon Bedrock 上一个具备视觉能力的 foundation model，以分析截图并确定下一步的浏览器操作。
- **CDP / WSS（Playwright）。**agent 通过 Chrome DevTools Protocol 驱动 Amazon Bedrock AgentCore Browser Tool 中一个隔离的 Chrome 实例。该浏览器在客户网络中导航目标遗留 Web 应用。
- **PutObject。**agent 将会话记录和截图存储到 Amazon S3 存储桶，为每张截图生成预签名 URL，并通过现有的 WebSocket 连接将该 URL 流式传回用户的浏览器。
- **预签名 URL Get。**用户的浏览器使用预签名 URL 直接从 S3 获取截图图片，并将其与 agent 的推理轨迹一起渲染在聊天 UI 中。图片字节不经过 WebSocket，只有短期有效的 URL 经过。

支撑性基础设施包括 [Amazon Elastic Container Registry (Amazon ECR)](https://aws.amazon.com/ecr/)（托管 NGINX 网关和 browser-agent 容器镜像）和 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)（审计日志与可观测性）。

## AgentCore Browser Tool

Amazon Bedrock AgentCore Browser Tool 提供一项全托管的、基于云的浏览器服务。AI agents 通过安全、隔离的浏览器会话与遗留 Web 界面交互。每个会话都在一个专用的隔离环境中运行，拥有自己的 CPU、内存和文件系统。会话完成后，该环境会被终止，状态会被清除。

Agents 通过 Playwright 经由基于 WebSocket 的 CDP 连接，以实现对 Web 应用的程序化控制，包括 JavaScript 密集的界面、动态表单和多步骤工作流，而无需关心底层技术栈。

三项能力直接应对前面描述的挑战：

- 浏览器配置文件可跨会话保持身份验证状态。只需认证一次，或由人工操作员通过 live-view 完成初始登录，后续会话即可在已登录状态下继续，从而免去重复的 SSO 和 MFA 流程。
- proxy 配置通过企业 proxy 基础设施路由流量，支持基于域名的路由，并将凭证存放在 AWS Secrets Manager 上，使企业网络内部或 IP 白名单门户后的遗留应用可以被访问。
- 会话录制捕获浏览器交互，包括点击、表单输入和页面导航，并将它们存储在 Amazon S3 中。结合 AWS CloudTrail 日志，这可以满足金融法规的审计轨迹要求。

回到保险示例，Browser Tool 会像人工操作员一样浏览保单管理系统。它使用配置文件持久化的会话状态登录，在多个屏幕中输入修改，并提交变更，所有这些都在一个安全、隔离的会话内完成，并生成完整、可重放的审计记录。

## Amazon Bedrock foundation models 与 Strands Agents 编排

Amazon Bedrock 提供驱动 agent 决策循环的多模态 foundation model。参考实现通过跨区域推理使用 Amazon Bedrock 上一个具备视觉能力的 foundation model，分析浏览器当前状态的截图，并决定下一步采取什么行动。这是使该方案区别于传统 RPA 的核心能力。模型看到页面，对屏幕上的内容进行推理，并确定下一步浏览器操作——可以是点击、填写、滚动，或暂停等待人工确认。

Strands Agents 是将模型的决策转化为具体工具调用的编排框架。模型不是遵循固定脚本，而是通过 ReAct（Reason + Act）循环驱动自身行为。模型捕获截图、在视觉上分析页面、决定调用哪个工具、执行它、观察结果，然后重复。该框架支持多种编排模式，包括用于层级委派的 Agents-as-Tools、用于结构化工作流的 Graphs，以及用于复杂多步骤流程的协作模式。

当操作员给出自然语言指令，例如"打开保单 #12345，将保额更新为 $500,000，并提交审批"时，模型会将其分解为按顺序执行的浏览器操作。每次操作后，模型都会截图，在视觉上解读新的页面状态，并决定下一步。如果意外出现确认对话框，或某个字段的校验结果与预期不同，模型会针对新状态进行推理，而不是直接失败。这缓解了使传统 RPA 难以大规模应用的脆弱性。

应用到我们的保险场景中，一条自然语言指令就能驱动完整的方案修改工作流。模型通过视觉导航到正确的保单，从截图中识别表单字段，在多个屏幕中输入变更，处理意外的校验提示，并提交审批。无需人工编写每一步的脚本，也无需在 UI 演进时维护脆弱的选择器。

## human-in-the-loop 集成

操作员可以实时看到自动化的执行过程。agent 将推理轨迹和截图实时流式传输到聊天界面。当模型判断在继续之前需要人工输入时——例如在提交变更之前确认打开的是正确的保单——它会调用 handoff_to_user 工具，暂停自动化，并向操作员呈现一个问题和当前截图。

在 agent 等待响应期间（默认最长 300 秒），浏览器会话保持存活。操作员可以批准、拒绝、提供额外指令，或让 agent 尝试不同的方法。响应到达后，模型会结合操作员输入恢复 ReAct 循环。它会重新截图以评估当前状态，然后从那里继续。如果操作员在超时窗口内没有响应，模型会决定是重试、尝试替代方法，还是优雅地中止。

在我们的保险工作流中，这意味着数字员工会在关键操作之前暂停，例如提交方案修改、确认受益人变更，或处理超过阈值的批单。这使操作员有机会在变更永久生效之前在屏幕上核实准确性。操作员始终掌握控制权，而无需手动驱动每一步。

## 安全与合规

该架构提供会话隔离、用于访问管理的 IAM 控制，以及每次使用后清除状态的临时会话。参考实现使用 Amazon Cognito 作为身份提供方，并通过替换 OIDC 发现 URL 来支持 Microsoft Entra ID 和 Okta。符合标准的 OIDC 提供方可以在相同的配置界面上工作。

对我们的保险公司而言，这意味着数字员工执行的每一次保单修改都是完全可追溯的，会话录制存储在 Amazon S3 中，操作通过 Amazon CloudWatch 记录。这满足了金融法规的留存要求。

## 关键设计决策

有两项实现选择值得特别指出，因为它们直接影响生产可靠性：

**事件循环隔离。**浏览器 agent 与一个向操作员流式推送更新的 WebSocket 服务一同运行。上游浏览器工具的线程模型会干扰该服务的事件循环，导致连接在约 15 秒后断开。参考实现覆盖了这一点，使浏览器操作在自己的隔离循环上运行，从而在整个会话期间保持操作员连接的稳定。完整实现请参见 visual_browser_tool.py。

**用语义定位器取代 CSS 选择器。**当 UI 元素移动或被重命名时，传统 RPA 机器人就会失效。semantic_action 工具采用了不同的方法。模型描述它所看到的内容（"点击标有 Submit 的按钮"），该工具使用不区分大小写的模糊匹配将其映射到 Playwright 的语义 Locator API。这使自动化能够抵御遗留应用中常见的细微 UI 变化。这正是该方案着手解决的脆弱性问题。完整实现请参见 semantic_action_tool.py。

## 部署与测试

整个解决方案通过一个 Terraform 技术栈即可部署。以下步骤将带你从 git clone 走到一个可用的聊天 URL。

## 前置条件

你必须具备以下条件：

- 一个 AWS 账户，并已为某个具备视觉能力的 foundation model 启用 Amazon Bedrock 模型访问权限。
- 已配置凭证的 AWS Command Line Interface（AWS CLI）v2。
- Docker 24 或更高版本。
- Terraform 1.5 或更高版本。
- Node 20 或更高版本，以及 Yarn。
- Python 3.12。

## 部署

```
git clone <repo-url> && cd <repo>
cp deployment/terraform/stacks/all/terraform.tfvars.sample \
deployment/terraform/stacks/all/terraform.tfvars
# Edit terraform.tfvars - set aws_region, project_name, cognito_domain_prefix

terraform -chdir=deployment/terraform/stacks/all init
terraform -chdir=deployment/terraform/stacks/all apply
```

该技术栈会配置 Cognito 用户池、CloudFront 分发、ECR 仓库、ECS proxy 服务、带 JWT 授权方的 AgentCore runtime，以及 S3 会话存储。Terraform provisioner 会一次性构建并推送两个容器镜像、编译 React UI、同步到 S3，并使 CloudFront 缓存失效。首次 apply 大约需要 20–30 分钟，其中大部分时间用于 CloudFront 传播和容器镜像构建。

## 测试解决方案

部署完成后，Terraform 会输出 CloudFront URL。在浏览器中打开它，使用 Cognito 用户登录，并尝试如下 prompt：

"打开 https://httpbin.org/forms/post, 将客户姓名填写为 John Smith，选择中号披萨，勾选培根配料，然后提交表单。"

你应该会看到推理轨迹流式进入聊天界面，每一步旁边出现截图，并在最终提交前出现一个 human-in-the-loop 提示。更多测试场景、示例 prompt 和 UI 实际运行的截图，请参阅[仓库 README](https://github.com/aws-samples/sample-agentcore-browser-legacy-automation/blob/main/README.md)。

## 清理

为避免持续产生费用，完成后请销毁基础设施：

```
terraform -chdir=deployment/terraform/stacks/all destroy
```

这会移除已配置的资源，包括 Cognito 用户池、CloudFront 分发、ECR 仓库、ECS 服务、AgentCore runtime 和 S3 存储桶。

## 结论与后续步骤

本文描述的 AI 驱动数字员工使这一愿景得以实现。传统 RPA 之所以脆弱，是因为它与精确的 UI 布局紧密耦合；而 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 中具备视觉能力的 foundation models、[Strands Agents](https://strandsagents.com/) 的模型驱动编排，以及 [AgentCore Browser Tool](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html) 的隔离浏览器会话三者结合，产生的自动化能够对页面状态进行推理、从意外分支中恢复，并在置信度低时交由人工处理。它做到这一切的同时，并未牺牲受监管行业所需的审计轨迹。

参考实现还有进一步扩展的空间。如果你的工作流需要跨会话上下文，Amazon Bedrock AgentCore memory 提供托管的短期和长期记忆。如果你需要把现有 REST API 集成为 agent 可与浏览器操作一同调用的工具，Amazon Bedrock AgentCore Gateway 可以处理这一点，而无需编写定制的 Strands 工具。对于需要自定义浏览器行为的门户，可以在创建会话时将 Chrome 扩展加载到 AgentCore Browser Tool 会话中。完整源代码可在 [GitHub](https://github.com/aws-samples/sample-agentcore-browser-legacy-automation) 上获取。
