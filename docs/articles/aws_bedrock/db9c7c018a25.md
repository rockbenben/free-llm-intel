# 为监督微调准备数据 第 1 部分：格式与质量

数据准备决定任何监督微调（SFT）项目的上限。你已经评估过自己的基础模型（FM），而开箱即用的表现无法满足生产要求。也许模型不能可靠地遵循你的输出 schema，或者在你所在领域的分类体系上表现吃力，又或者无法维持应用所要求的语气。问题不在于是否要定制，而在于如何定制。本文假设你已经决定对基础模型进行微调，并且正在评估如何为这项工作准备数据。

训练后定制提供了三个不同的着力点，每个都针对模型当前能力与你所需能力之间的不同差距。*持续预训练（CPT）* 摄入大量非结构化领域文本，以扩展模型的知识库。当模型对你所在领域的术语、概念或数据模式不熟悉时，使用 CPT。*监督微调（SFT）* 在精选的输入-输出对上训练，以重塑模型的行为。SFT 教模型如何回应：遵循指令、遵守 schema、采用特定语气，或产出结构化输出。它并不注入新知识，而是教模型以你需要的方式运用它已经掌握的内容，这一思路有时被称为[表面对齐假设](https://arxiv.org/abs/2312.00752)。*强化微调（RFT）* 通过奖励信号而非显式示范来优化行为。当你能够以编程方式评估输出质量、但难以大规模示范推理路径时，RFT 会派上用场。

这些技术并非互斥。一种生产模式是 CPT、然后 SFT、然后 RFT：先扩展知识，再塑造行为，最后通过反馈优化。在实践中，CPT 用得较少，只有当基础模型缺少任务所需的关键领域词汇或知识时才需要。像 Amazon Nova 这样的基础模型已经在广泛的语料上预训练过，因此通常 SFT 之后再接 RFT 就足够了。

本文是两篇系列文章中的第一篇，介绍 SFT 数据准备的基础：质量检查、格式要求以及训练/评估划分。我们使用 [Amazon Bedrock 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/nova-2-sft-data-prep.html)中的代码片段来说明关键概念，同时让这些指引适用于你选择的任何模型。[第二篇文章](https://aws.amazon.com/blogs/machine-learning/preparing-data-for-supervised-fine-tuning-part-2-advanced-data-strategies/)介绍进阶策略：就绪度评估、数据子集选择与过滤、数据增强以及数据混合。

## 数据质量检查

在投入格式处理或训练基础设施之前，先审计你的原始数据。尽早发现问题，可以在下游节省大量时间和算力成本。

### 准确性与正确性

数据集中的每一条响应都应是你可以放心部署到生产的金标准答案。错误的示例会让模型养成难以戒除的持久坏习惯。这一风险在 SFT 中尤为突出，因为模型学到的更多是该模仿哪些模式，而不是新的事实。错误的示范会被模仿。

由此得出的实际结论是：质量以很大的幅度胜过数量。[LIMA](https://arxiv.org/abs/2305.11206) 表明，1,000 个精心筛选的示例就能与用多几个数量级数据训练出的模型相媲美。[AlpaGasus](https://arxiv.org/abs/2307.08701) 表明，把指令集过滤到最干净的 20%，训练更快且得分高于完整数据集。如果你使用的是人工标注数据，请在示例进入训练集之前实施多轮评审流程。

### 示例的多样性

数据集多样性是 SFT 成功最有力的预测因素之一。关于[监督微调的可扩展性](https://arxiv.org/abs/2502.14854)的研究指出了决定微调泛化效果的两个属性。第一是语义覆盖度，即所涵盖的任务领域与 prompt 表述方式的广度。第二是信息深度，即单个示例的丰富程度。只覆盖生产流量一小部分的数据集，训练出的模型会在该部分表现良好，而在其他所有地方表现糟糕。

先审计数据集的 prompt 多样性。你的示例应涵盖用户表述同一意图的不同方式，因为只用“Summarize this document”训练的模型无法可靠处理“Give me the key takeaways.”。接下来检查领域与主题的广度。如果你的任务跨越多个领域，请确认每个领域按其生产频率成比例地出现。然后看难度范围：在复杂多步问题之外也要包含直白简单的案例，并按真实流量的复杂度分布加权。最后，显式纳入边界情况，例如含义模糊的输入、不完整的信息和超出范围的请求，并为这些情形配上你希望模型给出的响应。

一种实用的做法是按 embedding 相似度对示例聚类，并检查聚类结果中的缺口。稀疏或缺失的聚类表明模型将在这些方面缺乏训练信号。例如，一个客户支持数据集可能聚成密码重置、账单问题和物流更新几类。如果在生产环境中退款是常见请求，却没有聚类覆盖它，那片空白区域就是你的缺口。模型对退款对话几乎不会有信号，因此应在训练前收集或编写退款示例。本系列的第二篇文章介绍如何用数据子集选择方法把这一思路自动化。

### 相似任务内部的一致性

虽然整个数据集的多样性至关重要，但处理同一类情境的示例应在内部保持一致。同一任务类型内部的不一致，会就什么是正确行为发出相互矛盾的信号。例如，如果相似的 prompt 既产生要点式回答又产生段落式回答，模型就无法学到可靠的默认响应结构。如果你需要简洁的两句话答案，就不要在训练数据中放入整段长度的响应。

| **目标行为** | **两个不一致的示例（避免）** | **两个一致的示例（采用）** |
| --- | --- | --- |
| **从固定集合中返回一个小写标签** | Positive 这一条读起来相当负面。 | positive negative |
| **用两句话总结，不要开场白** | 登录失败 重置后 iOS 17 已升级至 Tier 2  好的！这里是一份简短总结：客户反映…… | 客户在 iOS 17 上重置密码后无法登录。工单已升级至 Tier 2。客户的卡在结账时被拒三次。计费部门确认发卡行拦截了该笔交易。 |
| **用一句固定的话拒绝超出范围的请求** | 这个我帮不了。非常抱歉，但这超出了我今天能够协助的范围。不过我很乐意…… | 该请求超出了本助手的范围。该请求超出了本助手的范围。 |

### 去重

重复或近乎重复的示例会让模型在这些模式上过拟合，相对数据集其余部分抬高它们的重要性。在 SFT 中，重复没有预训练时那么关键，但当你合并多位标注者的数据、跨项目合并数据集或使用合成数据生成时，重复就可能渗入。在这些情况下，请在训练前同时应用精确匹配去重和语义去重。

### 毒性内容与安全筛查

扫描数据集中的有害、有偏见或不适宜的内容。即使你的用例很窄，模型也可能从有问题的示例中内化模式，并在意想不到的语境中表现出来。使用自动分类器（例如开源的 [Llama Guard](https://arxiv.org/abs/2312.06674)）标记内容以供人工复核，并为你的领域明确界定什么构成可接受的训练数据。

## 数据格式

质量检查完成后，你就可以为训练组织数据结构了。格式不只是语法问题。你组织示例的方式会塑造模型学到的行为，因为 SFT 教模型对特定形状的输入作出响应，而不只是对其内容。

### 样本中的系统 prompt

如果你计划在推理时使用系统 prompt，请在训练示例中包含系统 prompt。系统 prompt 确立了塑造模型行为的上下文、人格和约束。如果训练数据缺少系统 prompt 而推理时却包含，你就会造成分布不匹配，从而可能降低表现。

### 对话格式（JSONL）

大多数现代 SFT 流水线（包括 Amazon Nova 配方）使用对话式 JSONL 格式，其中每一行都是一个自包含的 JSON 对象，表示一段对话。Amazon Nova 2.0 模型使用 Converse API 格式：

```
{
  "schemaVersion": "bedrock-conversation-2024",
  "system": [{"text": "You are a helpful coding assistant."}],
  "messages": [
    {
      "role": "user",
      "content": [{"text": "Write a Python function to check if a string is a palindrome."}]
    },
    {
      "role": "assistant",
      "content": [
        {"text": "def is_palindrome(s):\n    cleaned = s.lower().replace(' ', '')\n    return cleaned == cleaned[::-1]"}
      ]
    }
  ]
}
```

需要遵循的关键格式规则：

- 每行一个 JSON 对象，不要跨多行做美化缩进。
- 上传前校验每一行都能解析为合法 JSON。
- 在 user 与 assistant 轮次之间保持严格交替。
- 如果你的生产设置使用系统消息，请在数据中包含它们。

### 推理轨迹

对于具备推理能力的模型（例如启用 `reasoning_enabled: true` 的 Amazon Nova 2.0），请在 assistant 轮次中使用 `reasoningContent` 字段包含中间的思考步骤。正是在推理轨迹上训练，才把以 chain-of-thought 之名流行的行为从一种 prompt 技巧转移到模型自身之中。

```
{
  "schemaVersion": "bedrock-conversation-2024",
  "system": [{"text": "You are a financial analyst. Provide data-driven answers with supporting calculations."}],
  "messages": [
    {
      "role": "user",
      "content": [{"text": "Calculate YoY revenue growth. 2024: $4.2M, 2025: $5.1M"}]
    },
    {
      "role": "assistant",
      "content": [
        {
          "reasoningContent": {
            "reasoningText": {
              "text": "The user asks for year-over-year revenue growth. I need to calculate the percentage change: (new - old) / old x 100. That gives (5.1 - 4.2) / 4.2 x 100 = 21.43%."
            }
          }
        },
        {"text": "YoY revenue growth is approximately 21.4 percent: ($5.1M - $4.2M) / $4.2M x 100."}
      ]
    }
  ]
}
```

使用推理轨迹最难的部分不是格式，而是获得真正能教给模型一些东西的轨迹。有用的轨迹忠实于答案，也就是说推理确实通向最终响应。它们与难度成比例：短问题配短轨迹，长问题配长轨迹，[难度感知的轨迹压缩](https://arxiv.org/abs/2502.12012)把这一取舍明确表达了出来。它们是完整的，没有思维跳跃，因为专家撰写的推理过程常常跳过模型尚未学会的中间步骤。而且质量比数量更重要：[s1](https://arxiv.org/abs/2501.19393) 和 [LIMO](https://arxiv.org/abs/2502.03387) 都表明，不到 1,000 个精心筛选的推理示范，就能在有能力的基础模型中激发出强大的推理能力。本系列的第二篇文章介绍如何通过蒸馏与自生成大规模获取这些轨迹。

推理内容请使用纯文本，并让它与问题求解过程直接相关。如果在训练时启用了推理，推理时也应启用，以保持行为一致。请记住，在启用 `reasoning_enabled: true` 的情况下用非推理数据集训练，可能导致模型丧失推理能力，因为它学到的是在不应用推理的情况下生成响应。

### 工具调用与多模态格式

SFT 支持训练模型的工具使用（函数调用）与多模态理解（文档、图像、视频）能力。对于工具调用，`toolUse` 块出现在 assistant 轮次中，`toolResult` 块出现在 user 轮次中，二者各自引用一个唯一的 `toolUseId`：

```
{
  "schemaVersion": "bedrock-conversation-2024",
  "system": [{"text": "You are an expert in composing function calls."}],
  "toolConfig": {
    "tools": [
      {
        "toolSpec": {
          "name": "getItemCost",
          "description": "Retrieve the cost of an item from the catalog",
          "inputSchema": {
            "json": {
              "type": "object",
              "properties": {
                "item_id": {
                  "type": "string",
                  "description": "The ASIN of item to retrieve cost for"
                }
              },
              "required": ["item_id"]
            }
          }
        }
      }
    ]
  },
  "messages": [
    {
      "role": "user",
      "content": [{"text": "How much does item id-456 cost?"}]
    },
    {
      "role": "assistant",
      "content": [
        {
          "toolUse": {
            "toolUseId": "getItemCost_0",
            "name": "getItemCost",
            "input": {"item_id": "id-456"}
          }
        }
      ]
    },
    {
      "role": "user",
      "content": [
        {
          "toolResult": {
            "toolUseId": "getItemCost_0",
            "content": [
              {"text": "{"name": "getItemCost", "results": {"cost": "$29.99"}}"}
            ]
          }
        }
      ]
    },
    {
      "role": "assistant",
      "content": [
        {"text": "Item id-456 costs $29.99."}
      ]
    }
  ]
}
```

工具调用数据的关键约束：

- `toolUse` 只能出现在 assistant 轮次中，`toolResult` 只能出现在 user 轮次中。
- 每个 `toolResult` 必须引用前面某个 assistant 轮次中的有效 `toolUseId`，且在一段对话中只使用一次。
- `toolResult` 的内容只能是文本或 JSON。
- `toolSpec` 中的 `inputSchema` 必须是合法的 JSON Schema 对象。

对于多模态训练，文档和图像内容块会与文本一同出现在 user 轮次中，其来源引用 Amazon Simple Storage Service（Amazon S3）位置：

```
{
  "schemaVersion": "bedrock-conversation-2024",
  "system": [{"text": "You are a document analysis assistant."}],
  "messages": [
    {
      "role": "user",
      "content": [
        {
          "document": {
            "format": "pdf",
            "name": "quarterly_report",
            "source": {"s3Location": {"uri": "s3://<your-bucket-name>/report.pdf"}}
          }
        },
        {"text": "Summarize the key findings from this quarterly report."}
      ]
    },
    {
      "role": "assistant",
      "content": [
        {"text": "The quarterly report highlights three key findings..."}
      ]
    }
  ]
}
```

### 贴近原始模型的 chat 模板

每个基础模型都是用特定 chat 模板进行后训练的，该模板由划分系统 prompt、user 轮次和 assistant 轮次的确切 token 序列构成。你的训练数据应完全匹配这一模板。偏离它，哪怕是细微偏离，都会迫使模型在学习新行为的同时学习新的输入格式，从而把学习预算分摊到两个目标上。最坏情况下，模板不匹配会导致模型在推理时忽略其系统 prompt 或产生格式错误的输出。

模板对齐的实用准则：

- **使用模型提供方的官方格式化工具。** 对于 Amazon Nova，使用 Converse API schema。对于开源模型，使用 Hugging Face Transformers 中 tokenizer 的 `apply_chat_template()` 方法。
- **绝不手写分隔符。** 如果你要从 ShareGPT、Alpaca 等其他格式转换数据，请让它经过目标模型的 chat 模板函数，而不是手动插入角色标记字符串。
- **验证 tokenization 往返。** 格式化之后，对数据样本做 tokenize 再解码回文本，确认角色边界、特殊 token 与内容被完全保留。
- **训练时的结构与推理时保持一致。** 如果你的生产流水线在特定位置注入系统 prompt、工具定义或检索上下文，训练数据中也应在相同位置包含这些元素。

## 训练/评估划分

留出 10–20% 的数据作为评估集。这不是可选项。没有评估集，你无法区分真正的学习与过拟合。评估集应能代表你的生产分布，而不是一个可能低估稀有但重要类别的随机切片。

对于小数据集（少于 1,000 个样本），使用分层划分，使每个任务类别都出现在训练集和评估集中。对于较大的数据集，随机划分通常足够，但之后要核实分布。训练之前，先用未经修改的模型在评估集上建立基线表现。这为你提供了一个具体的目标去超越，也帮助你量化监督微调的价值。

## 结论

数据准备是任何 SFT 工作流中影响最大的活动。本文涵盖的模式——包括系统性的质量检查、符合 schema 的格式，以及有代表性的训练/评估划分——无论你是在为狭窄的分类任务微调，还是为复杂的多轮对话系统微调，都同样适用。提前投入时间，你的训练任务就会收敛更快、泛化更好，并避免因模型行为问题追溯到数据问题而付出高昂的调试代价。
