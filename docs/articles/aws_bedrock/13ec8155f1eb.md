# 从数据过载到可执行洞察：Verizon Connect 如何将 agentic AI 扩展到 10 万用户

*特别感谢 Verizon Connect 团队为该项目付出的艰辛努力：Matteo Simoncini、Luca Bravi、Alberto Rossettini、Martin Villarruel、Ceyhun Unlu、Adriel Zuquini、Andrea Benericetti。*

如今，车队管理者面临一项艰巨挑战：把过载的数据转化为可执行的洞察。当你管理着数千辆车，每辆车每天产生数百个数据点时，靠人工分析来识别关键模式几乎不可能。[Verizon Connect](https://www.verizonconnect.com/) 是一家全球车队管理解决方案提供商，通过其 Reveal 平台为世界各地企业提供服务，它在大规模场景中遇到了完全相同的挑战。

超过 120 万个活跃车辆订阅每天产生 5 亿多个数据点，覆盖 8 万个独特的数据指标，车队管理者被这些数据淹没，不得不在支离破碎的纸质记录和事后补救的电子表格中寻找异常。数据量之大，使得在安全问题、维护需求或运营低效演变成代价高昂的问题之前几乎无法识别它们。Verizon Connect 没有再构建另一个只能捕捉预定义模式的静态仪表盘或基于规则的自动化系统，而是选择 agentic AI，用一个集中式的智能方案取代人工猜测。agentic AI 会动态调查新模式、提出后续问题，并根据发现调整分析，因此非常适合车队运营这种不可预测的场景。

在本文中，我们向你展示 Verizon Connect 如何构建并扩展 agentic AI 方案，把海量车队数据转化为清晰、可执行的洞察，每天服务 10 万用户。我们将带你了解架构决策、实施挑战以及可衡量的成果，为你的数据到洞察转型提供指引。

### 各组件与逻辑流程的概述如下。

- 编排开始——每日触发器通过激活分析层中的异常检测模块来启动工作流。
- 数据摄取——该模块从原始数据存储中拉取结构化信息。计算量最大的工作就发生在这里。
- 定向输出——这个模块并不要求大语言模型（LLM）“大海捞针”，而是识别具体异常并写入专门的异常表。通过把数值分析交给专门的代码，我们避免了 LLM 处理原始表格数据时面临的规模和准确性问题。
- AI agent 激活——异常数据准备就绪后，管理器触发 AI agent。为了提升性能，多个 agent 可以并行运行，各自聚焦不同的客户或数据分片。
- 推理与上下文——AI agent 编排最终分析。它查询异常数据以了解*发生了什么*，再回溯原始数据以探究*为什么*，并用 LLM 把这些输入综合为连贯的叙述。
- 洞察交付——最终推理结果被存储为生成的洞察，再通过 Reveal 应用交付给最终用户。

## 方案的组件

### 异常检测

AI 工程中一个常见误区，是让 LLM 对大规模原始表格数据做数值分析。正如 [AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/strategy-data-considerations-gen-ai/differences.html) 所指出的，LLM 在复杂的表格结构和大规模数值提取方面可能力不从心。为此，我们使用 [AWS Step Functions](https://aws.amazon.com/step-functions/) 和 [AWS Lambda](https://aws.amazon.com/lambda/) 构建了一个 serverless 统计模型（见图 4）。该模型在结构化数据上执行计算密集的异常检测工作。它识别出异常*是什么*，这样 AI agent 就可以专注于异常*为什么*发生以及*如何应对*。

### AI agent

我们选择了 [Strands Agents](https://strandsagents.com/)，这是一个用于构建和执行 AI agent 的开源 SDK，运行在 serverless 的 AWS Lambda 环境中。这种部署模式会根据需求横向扩展。AI agent 通过动态推理循环运作，自主决定必要的调查路径，而不是遵循固定的步骤序列。从下面的描述可以看出，AI agent 是无状态的，生成洞察所需的上下文会在分析时重新获取。

AI agent 使用特定工具来：

- 从 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/)检索预先计算好的异常。
- 从 [Amazon Aurora](https://aws.amazon.com/rds/aurora/)查询原始数据的补充上下文，从 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/)查询历史洞察。
- 把最终洞察写回 Amazon S3。
- 在 Amazon DynamoDB 中跟踪任务请求状态。

### 两阶段 agentic 架构

洞察生成采用两阶段方式，各自以不同方式使用 LLM 的推理能力：

**阶段 1：** 摘要生成（异常聚合与优先级排序）在第一阶段，agent 接收一组跨车队检测到的原始异常。LLM 不会逐条处理每个异常，而是自主决定如何把它们聚合为连贯的洞察候选。它可以按以下方式对异常分组：

- 共同的根本原因（例如多辆车表现出相同的行为模式）
- 时间相关性（事件集中在特定日期）
- 类别相似性（相关的安全或效率指标）

分组逻辑和选择标准完全由 LLM 自行决定。系统不会强行规定异常应如何组合。聚合之后，agent 会根据严重程度、复发情况、全车队影响和可操作性等因素，为每条候选洞察分配一个相关性分数。在这批打分后的候选中，agent 选出相关性最高的四条，进入详细生成阶段。通过这种方式，优先级排序会适配每个用户车队的具体情境，而不是依赖可能错过新模式的静态业务规则。

**阶段 2：** 详细生成（基于 agentic 工具调查）第二阶段是系统的 agentic 特性变得关键的地方。对于每条摘要洞察，都会生成一个独立的 agent 实例，并授予其数据检索工具的访问权限。agent 自主决定调用哪些工具、按什么顺序、调用多少次——不断迭代，直到收集到足够证据，产出有数据支撑的洞察。既然已经解释了 agent 的执行方式，下面来看看为什么 agentic 方法对这个用例至关重要。车队管理涉及无数变量和不可预测的场景，需要动态调查而非预设逻辑，这带来了两个根本性限制：

- 有限的模式覆盖：代码只能检测被明确编写进去的模式。边缘情况、新颖的关联或意料之外的数据分布都会被忽略。
- 僵化的调查流程：脚本会按照预设步骤执行，不管数据在分析中揭示出什么。

相比之下，AI agent 可以发现任何性质的模式，包括开发阶段未曾预料到的边缘情况。如果数据暗示出某种意外的关联（例如急刹车事件与一天中特定时段模式相关，或某辆车在某个特定日期之后行为发生改变），agent 可以实时调整调查策略，追加工具调用来探索这些新出现的假设。这种灵活性在车队管理中尤其宝贵，因为：

- 驾驶员的行为变化不可预测
- 外部因素（天气、交通、路况）会产生不易察觉的关联
- 车队构成和使用模式会随时间演变
- 可能出现历史数据中从未有过的新异常类型

流程编排示例

- 初步发现：agent 识别出一条摘要洞察，报告整个车队的急刹车事件增加了 30%。
- 建立基线：它自主决定拉取过去 30 天的全车队历史平均值，以确认这次激增是真正的异常还是典型的季节性趋势。
- 模式识别：看到激增集中在特定日期后，agent 把重点转向按天细分。它发现这些安全事件中的大多数都发生在同样的两天里。
- 定向深入：根据这些日期，agent 确定车辆 1015、1142 和 1032 造成了近 70% 的事件。
- 对比分析：随后它发起最后一次定向请求，把车辆 1015 的历史表现与当前行为进行比较，看看驾驶员的特征是否发生了根本变化。
- 综合：只有在“把这些点连起来”之后，agent 才结束循环，生成最终的有数据支撑的洞察，突出涉及的具体驾驶员和日期。

### 大语言模型

为了优化性价比，我们先用高端型号 Claude 4.5 Sonnet 验证逻辑和洞察质量。验证之后，我们在生产用例中改用成本更低的 Claude 4.5 Haiku。进一步的性价比优化让我们选择了 [Amazon Nova 2 Lite](https://aws.amazon.com/nova/models/)，一个极快的多模态模型，它提供的洞察质量相当，但输入 token 成本比 Claude 4.5 Haiku 低 70%。这项可观的节省至关重要，因为工作负载主要由输入 token 构成（车联网数据、异常、上下文）。Nova 2 Lite 的高效率使 Verizon Connect 能够以更低的成本向全体用户交付 AI 洞察。质量通过自动化测试套件和黄金标准数据集得以保持，确保完整发布时得到一个久经考验的方案。LLM 大规模托管在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上，这是一项完全托管的服务，具备全面的生成式 AI 能力、安全性、隐私和负责任 AI 特性。

### 每日触发器管理与并发

为了在这 10 万用户开始一天工作时就提供准备好的洞察，我们使用 [Amazon Simple Queue Service（Amazon SQS）](https://aws.amazon.com/sqs/)来管理执行。通过控制 SQS 到 Lambda 触发器的最大并发数，我们可以：

- 平滑 API 需求的高峰
- 保持在 Amazon Bedrock 配额之内：Tokens Per Minute（TPM）和 Requests Per Minute（RPM）
- 在不超量配置资源的前提下提供可靠交付

举例来说，考虑一个为全美客户交付洞察的场景。洞察的目标交付时间是美国东部时间上午 8:00，基于截至前一天太平洋时间午夜生成的数据。考虑到 3 小时时区差，整个端到端流程必须在 5 小时窗口内完成。给异常检测分配 1 小时后，AI agent 和 LLM 还剩下 4 小时窗口来生成洞察。以 1,500 RPM（可调）的速率计算，洞察生成阶段大约需要 1.25 小时，完全在我们的运营要求之内。

## 成果：可执行的智能洞察

Operational Insights 功能于 2025 年 11 月向 [Verizon Connect 用户推出](https://www.verizonconnect.com/solutions/operational-insights/)，并为车队管理者提供了如下清晰的自然语言叙述：

- 安全模式检测：“本周你的车队急刹车事件增加了 100%。有趣的是，这同时伴随着急加速的减少，提示可能是驾驶员疲劳或拥堵加剧。”
- 运营效率：“车辆 #90000 在发动机开启时间中有 50% 处于怠速状态，明显高于你的车队平均水平。这代表着不必要的燃油成本。”
- 车队表现：“每日里程下降了 59%，但超速事件增加了 54%。这表明车辆正在以更高速度行驶更短的距离——考虑路线优化。”

## 结论与展望

在本文中，我们展示了 Verizon Connect 如何在 AWS 上构建可扩展的 Agentic AI 方案，把原始 IoT 车联网数据转化为可供超过 10 万用户使用的可执行车队洞察。该架构结合了 Amazon Bedrock、Strands Agents、AWS Step Functions、Amazon SQS 和多层数据层，以规模化方式交付可靠、高性价比的洞察。

随着 AI 格局演进，我们计划把基于 AWS Lambda 的 agent 部署迁移到 [Amazon Bedrock AgentCore Runtime](https://aws.amazon.com/bedrock/agentcore/)，进一步简化 AWS Lambda 执行，并使用 [Model Context Protocol（MCP）](https://docs.aws.amazon.com/prescriptive-guidance/latest/mcp-strategies/introduction.html)加快工具集成。

要有效实施 agentic AI 方案，先从一个小规模试点开始，验证基本用例并确立成本效益。初步价值得到证明后，通过集成自动化工作流和数据驱动的个性化来扩展系统。最后阶段是过渡到完整的部署，支持整个组织范围内的高级编排和实时处理。现在就开始构建：

- 从基础做起：用 Amazon Bedrock 提供托管 AI 服务，用 AWS Lambda 实现 serverless agent 托管
- 加入编排：用 AWS Step Functions 管理工作流，用 Amazon SQS 实现可扩展队列
- 存储与检索数据：用 Amazon S3 做对象存储，Amazon Aurora 存结构化数据，Amazon DynamoDB 做快速查找
- 探索 agent 框架：[Strands Agents 文档](https://strandsagents.com/docs/user-guide/quickstart/overview/)用于开源 agent 开发
