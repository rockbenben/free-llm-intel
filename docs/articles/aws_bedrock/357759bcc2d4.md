# HPE Zerto 如何借助 Amazon Bedrock 构建 agentic 故障排查系统

*本文由 AWS 与 HPE Zerto 团队共同撰写。*

如果你管理混合云和多云基础设施，你可能已经在借助 AI 系统来评估健康状况、调查问题并更快地处理问题。HPE Zerto 通过构建一个由 Amazon Bedrock 驱动的 agentic 故障排查系统来应对这一挑战。

[HPE Zerto Software](https://www.hpe.com/il/en/zerto-software.html) 帮助你增强网络弹性、灾难恢复和持续数据保护。你可以利用这些能力大幅减少数据丢失和停机时间，同时支持从勒索软件事件、服务中断和其他中断中快速恢复。

本文介绍我们所选的系统架构，以及我们在开发由 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 驱动的 agentic 故障排查系统时遇到的挑战。我们将它部署在本地环境中，对运维信号、环境上下文和产品知识进行受控且安全的访问。

该系统提供自然语言体验，帮助你快速度过从提问到可执行洞察的过程，从而支持更快、更有依据的恢复决策。

## 业务挑战

数据保护与灾难恢复团队所处的环境在规模、复杂性和业务关键性上都在不断增长。他们必须持续监控保护健康状况、验证服务级别协议（SLA）合规性、解读告警、调查故障，并为恢复事件做好准备。这项工作往往横跨多个站点和大量受保护的工作负载。

- 回答运维问题所需的信息往往分散在产品告警、事件和文档中，迫使团队在采取行动前手动收集上下文。
- 运维人员不得不在仪表板、报告和知识来源之间来回切换，以了解正在发生什么以及下一步该做什么，从而浪费时间。
- 经验较少的管理员可能难以解读症状，或难以确定最安全的修复路径。
- 管理者可能无法快速获得关于风险、SLA 敞口或恢复就绪状态的清晰摘要。
- 在服务中断或网络事件期间，这些延迟会变得更加严重，因为不确定性的代价很高，团队需要快速获得清晰、可信的指导。

因此，我们的客户需要一种方式，能够将复杂的韧性数据转化为可执行的答案，同时不增加额外的运维负担，并且能部署在不同的环境中。

## 解决方案概述

从根本上说，我们设计该系统是为了：

- 充当支持助手，帮助你在短时间内解决配置问题并排查故障，而无需创建支持工单。
- 就系统健康问题向你发出告警，并协助缓解。
- 代表你执行任务，以加快部署时间和功能采用。

我们将该系统作为 Zerto 产品中的一个 pod 部署在你的本地环境中，可以直接从你日常运维所使用的同一 UI 访问。你可以用自然语言交互，该系统旨在基于你环境的实时状态进行推理、行动，并以有上下文、可执行的答案作出回应。

我们选择 [Amazon Bedrock](https://aws.amazon.com/bedrock/)，是因为它能够支持安全的企业级部署、模型灵活性和运维控制。

关键考量包括：

- **安全与治理 **– Amazon Bedrock 支持对基础模型的受控访问，帮助我们让 AI 使用符合企业安全、合规和数据保护要求。
- **模型灵活性 **– 该服务使得访问和[评估](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html)多个基础模型成为可能，并可基于质量、延迟和成本选择最合适的一个。
- **运维集成 **– Amazon Bedrock 与用于 [guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html)、可观测性和[知识检索](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html)的 AWS 服务集成，支持更易管理的生产架构。

我们使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 强制执行内容安全，以确保你的 prompt 和系统输出符合公司政策、合规和安全要求。

下图展示了架构的关键组件：

- **UI 层 **– 你通过嵌入现有 Zerto UI 的聊天界面与系统交互。使用 Server-Sent Events（SSE）的实时流式传输会在调查进行时展示进度，提供更好的用户体验。
- **Agentic 层 **– 使用 [Strands Agents framework](https://strandsagents.com/) 构建的 agent 作为 pod 在你的本地环境中运行，并可访问以下内容：**会话历史** – 本地存储的历史聊天对话和上下文。**内部工具** – 本地 Model Context Protocol（MCP）服务器，暴露 ZVM（Zerto Manager）API，agent 可调用这些 API 以结构化方式访问实时环境数据。**外部工具** – 使用 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 智能获取公开文档、相关 runbook 和运维知识，这是一种集中式、全托管的检索增强生成（RAG）能力，内置用于上下文检索的语义搜索。
- **智能层 **– 由三个主要组件构成：**推理 **– 请求被发送到 [Amazon Bedrock](https://aws.amazon.com/bedrock/model-choice/)，由其路由到所选的基础模型。按租户的请求标记通过每个租户所承担的 AWS Identity and Access Management（IAM）角色标签完成。**安全** – 在推理前后应用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/)，以强制执行内容边界，并帮助验证响应始终限定在运维主题范围内。**限制与配额 **– 将 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)、Amazon DynamoDB 和 AWS Lambda 组合使用，以强制执行按租户的配额和限制，并维持一个成本高效的系统。
- **可观测性层 **– 系统发送到 Amazon CloudWatch 的遥测数据提供对 agent 性能、错误率和使用模式的可见性。

## Agentic 流程

该系统由多个 sub-agent 组成，由一个 Orchestrator agent 控制，后者可以根据手头的任务将每个 sub-agent 作为工具使用。反过来，每个 sub-agent 都有自己的一组工具和独立的上下文来处理其子任务。图 3 展示了各 agent 之间的流程与层级关系。

Orchestrator 决定何时委派工作。常规问题会被直接回答，而深入的、日志密集的调查会被路由到专用于相关组件的专门 sub-agent。每个 sub-agent 都用自己全新的上下文运行，拥有专门的 system prompt、自己的工具，并使用更强的模型来处理推理密集的工作。它的最终响应是一份紧凑、精炼的报告，不会让原始日志和调查过程中的临时记录污染或膨胀父级的上下文。

- **Orchestrator agent –** 有两个用途。你可以用它检查保护组状态、查看最近的告警，或询问配置最佳实践。当给定一个当前系统中确实存在的问题时，agent 会在各 sub-agent 之间编排故障排查流程。它会在从响应中剥离密钥或原始日志后，向你转达最终答案。
- **ZVM agent** – 负责排查与 ZVM 相关的问题，例如服务崩溃、网络问题和升级失败。它使用提供领域特定知识和特定日志模式的专用 skill，分析日志并通过 MCP 补充环境数据。这为手头的问题及其可能原因提供了全面的分析。
- **VRA agent** – 负责排查与 VRA（Zerto Replication Engine）相关的问题，例如复制问题和延迟、站点之间以及安装之间的网络问题。它同样具备领域特定的知识 skill，为 agent 提供结构化的日志模式上下文，以便与日志以及通过 MCP 获取的环境数据进行匹配。

## 挑战

构建 HPE Zerto agentic 故障排查系统需要应对若干关键工程决策，包括模型选择、评估方法以及本地部署的约束。

### **模型选择**

作为开发流程的一部分，我们比较并随后组合了多个模型用于推理和推断，权衡了质量、性能与成本之间的关系。

在最初的验证性项目（POC）中，我们首先评估了更大、更强的模型以证明可行性，随后实现了一套 agent 评估机制（在下一节中介绍），并比较了其他模型，其中一些更快、更小、更便宜。最终，如前面所述，选定了一种多模型架构。随着新模型面世，我们会持续对其进行评估。

关于各 AWS 区域支持的模型，请参阅 Amazon Bedrock 中的[各区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

### **Agent 评估**

我们使用 PyTest 和 [Strands Agents Evals SDK](https://strandsagents.com/docs/user-guide/evals-sdk/quickstart/) 来系统化、持续地评估 agent，因为我们一直在升级系统。我们还创建了用于运行完整评估套件的作业，以观察 agent 行为的回归和改进。

我们创建了三类评估：

- **基础查询评估 **– 单轮查询-响应评估，将查询作为测试交给 agent，并对响应进行评估。
- **多轮评估 **– 完整对话评估，将初始查询作为测试交给 agent，agent 作出响应，并由一个用户模拟器大语言模型（LLM）扮演真实用户。该技术使用 [Strands Agents ActorSimulators](https://strandsagents.com/docs/user-guide/evals-sdk/simulators/)。完整对话在最后进行评估。
- **动态测试评估 **– 为了评估尚未覆盖的动态用例，我们使用 [Strands Agents Experiment Generator](https://strandsagents.com/docs/user-guide/evals-sdk/experiment_generator/) 构建了完全动态的测试套件，它根据特定标准创建唯一的测试套件。每个测试有四类[评估器](https://strandsagents.com/docs/user-guide/evals-sdk/evaluators/)：
- **Response evaluator **– 根据特定的预定义标准评估 agent 响应，并使用可解析的结构化输出以提取相关数据。
- **Trajectory evaluator **– 根据特定的预定义标准评估 agent 的工具选择。该评估器同样使用结构化输出。
- **Latency evaluator **– 评估 agent 延迟，并检查其是否在定义的阈值之内。
- **Token evaluator **– 评估 agent 的 token 使用量，并检查其是否保持在边界之内。

> “Strands Agents 消除了构建 AI agent 的复杂工作 —— 没有刻板的工作流定义，没有样板式的工具链代码，只需要一个模型、一个 prompt 和你需要的工具。借助内置的评估和可观测性，我的团队构建、测试和迭代 agent 的速度比我们尝试过的任何框架都快。它覆盖了整个开发生命周期，让我们可以专注于解决真实问题，而不是编写胶水代码。”

— Shahak Gabay，HPE Zerto 高级软件工程师

### 本地部署模式

我们 agentic 故障排查系统在部署上的一项约束是，它必须运行在你自己的环境内部。灾难恢复（DR）基础设施常常是气隙隔离的、对延迟敏感的，或受严格的数据驻留要求约束。我们使用 [Strands Agents SDK](https://strandsagents.com/docs/user-guide/quickstart/overview/) 实现 agent 运行时，它完全在 ZVM 设备内部本地运行。只有模型推理请求和知识库查询会通过 HTTPS 发送到 AWS。

## 经验教训

构建和部署该解决方案的过程中浮现出若干洞见，它们塑造了我们对 agentic 架构的处理方式。这些洞见集中于本地环境约束、agent 分解以及实时用户反馈。

- **本地部署从根本上改变了架构。** 尽量减少传输到客户环境之外的数据、并防止敏感客户信息被发送出去的要求，塑造了每一项架构决策 —— 从我们选择 [Strands Agents SDK](https://strandsagents.com/) 进行本地编排，到为本地数据访问设计 MCP 服务器。
- **MCP 服务器是将 agent 建立在实时运维数据之上的有效模式。** 将现有产品 API 包装在 MCP 服务器中，为 agent 提供了对实时环境数据的结构化、类型化访问，并显著加快了我们的 agent 开发。
- **多 agent 分解提升了复杂任务的可靠性。** 将 workflow 拆分为多个专门的 agent，每个都有明确的职责边界，使每个组件都可以独立测试，整个系统也更易于调试。我们将各 sub-agent 以 hub-and-spoke 拓扑连接。每次委派都经由父级流转，若某个 sub-agent 发现该问题应归别处处理，它会向父级报告，而不是直接调用同级 agent。这种设计为安全规则和最终答案保留了单一控制点，并使流程保持线性、易于在遥测中追踪。它还有助于防止失控的 agent 间递归，避免耗尽 token 预算。结果是：在复杂问题上给出更好的答案，同时不牺牲日常对话的速度与可预测性。
- **流式传输对用户信任很重要。** 通过 SSE 实时展示调查进度显著改善了用户体验。用户可以看到每一步的发生过程，而不是在没有任何可见性的情况下等待。
