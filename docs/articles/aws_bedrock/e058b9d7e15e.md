# 使用 Amazon Bedrock 为车辆数据采集与自动化构建 AI 驱动的策略创建

车辆数据对[原始设备制造商（OEM）](https://en.wikipedia.org/wiki/Original_equipment_manufacturer)推动持续的产品创新和性能改进、支持新的增值服务至关重要。同样，车辆架构日益数字化以及可软件配置功能的采用，让 OEM 能够高效地增加新特性与新能力。在汽车行业向软件定义汽车（SDV）演进的过程中，[Sonatus 的](https://www.sonatus.com/) [Collector AI](https://www.sonatus.com/products/collector/) 和 [Automator AI](https://www.sonatus.com/products/automator/) 产品正好应对这两个方面。

Collector AI 降低了在整车生命周期内使用数据的门槛，其数据采集策略的创建无需改动车辆电子器件，也无需修改嵌入式代码。然而，OEM 工程师及其他车辆数据使用者要面对成千上万的车辆信号，难以挑选出能驱动自身用例与结果的信号。同样，Automator AI 采用直观的 if-then 风格脚本化工作流、以无代码方式自动化车辆功能，这也可能颇具挑战，尤其对那些并不熟悉车上可用事件与信号的 OEM 用户而言——他们要从中挑选信号来构建期望的自动化动作。

为应对这些挑战，Sonatus 与 [AWS Generative AI Innovation Center](https://aws.amazon.com/ai/generative-ai/innovation-center/) 合作，开发了一个自然语言界面，用生成式 AI 生成数据采集与自动化策略。这一创新的目标是把策略生成过程从数天缩短到数分钟，同时让工程师与非专家都能使用。

本文探讨我们如何使用 Sonatus 的 Collector AI 和 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 构建这一系统。我们会讨论背景、挑战以及高层次的方案架构。

## Collector AI 与 Automator AI

Sonatus 开发了一套精细的车辆数据采集与自动化工作流工具，包含两个主要产品：

- **Collector AI** —— 基于可配置的触发事件采集并传输精确的车辆数据
- **Automator AI** —— 基于分析后的数据和触发条件在车内执行自动化动作

当前流程要求工程师手工创建数据采集或自动化策略。视 OEM 用例范围而定，某个车型可能有数百条策略。此外，要为给定意图确定应采集的正确数据，需要层层筛查信息，还要应对组织层面的难题。我们的目标是开发一种更智能、更直观的方式，以实现以下几点：

- 从用户的自然语言输入生成策略
- 把策略创建时间从数天大幅缩短到数分钟
- 对生成过程中的中间步骤提供完整控制
- 把策略创建能力扩展到非工程师，例如车辆产品负责人、产品规划人员，甚至采购人员
- 为既有策略和新建策略实现 human-in-the-loop 审核流程

## 主要挑战

在实现过程中，我们遇到了若干挑战：

- **复杂的事件结构** —— 车型与不同策略实体使用多样的表示和格式，要求策略生成足够灵活
- **标注数据有限** —— 把自然语言输入映射到期望策略的标注数据很有限
- **格式转换** —— 方案必须处理不同客户与车型之间的各种数据格式和 schema
- **质量保证** —— 生成的策略必须准确且一致
- **可解释性** —— 对策略如何生成给出清晰说明，有助于建立信任

## 成功指标

我们定义了以下关键指标来衡量方案的成功：

- **业务指标：** 策略生成时间缩短、每客户策略数量增加、策略创建的用户群扩大
- **技术指标：** 生成策略的准确度、修改后的 prompt 的结果质量
- **运营指标：** 相比人工流程减少的策略生成投入与周转时间、与现有系统的成功集成

### 实体抽取

一条完整生成的车辆策略由多个部分组成，而这些部分可能都包含在用户的一句陈述中。对 collector 策略而言是触发器和目标数据，对 automator 策略而言是触发器、动作以及关联任务。用户的陈述首先按照以下步骤和规则被拆解为各个实体：

- 为每个实体提供 few-shot 示例
- 触发器输出必须自包含，带有恰当的信号值与比较运算符信息：查询示例：“生成一条自动化策略，在车辆行驶时自动锁门” 触发器输出：`<response>vehicle speed above 0, vehicle signal</response>`
- 触发器和动作会使用分类 prompt 进行二次校验
- 对 Automator AI，触发器和动作必须与其对应的任务关联
- 该过程的最终输出是用户自然语言查询的中间结构化 XML 表示：查询示例：“生成一条自动化策略，在车辆行驶时自动锁门” 生成的 XML：

```
<response>
<task> Lock doors when moving </task>
<triggers> vehicle speed above 0, vehicle signal </triggers>
<actions> lock doors, vehicle signal </actions>
</response> 
```

下图展示了我们改进后的方案，它把用户查询转换为 XML 输出。

### 信号转换与参数化

要从中间的结构化 XML 输出得到最终的 JSON 策略结构，必须识别出正确的信号、生成信号参数，并把这些信息组合起来以符合应用期望的 JSON schema。

此阶段选用的输出信号格式是 Vehicle Signal Specification（VSS），这是由 [COVESA.](https://covesa.global/project/vehicle-signal-specification/) 推动制定的行业标准规范。VSS 规定了车辆信号命名约定与策略的标准，使车辆信号相比其物理控制器局域网（CAN）信号对应物更具描述性、更易理解。这不仅使它适用于[生成式 AI](https://aws.amazon.com/ai/generative-ai/) 生成过程，而且在该过程中不可或缺，因为描述性的信号名称及其含义的可用性是必需的。

VSS 信号连同其描述和其他必要元数据被嵌入到向量索引中。对每个需要查找车辆信号的 XML 结构，信号转换过程包含以下步骤：

- 可用的信号数据经过预处理并存入向量数据库。
- 每个 XML 表示——触发器、动作和数据——都被转换为其对应的嵌入。某些情况下，还可以对 XML 短语进行增强，以获得更好的嵌入表示。
- 对上述每个实体：找出 Top-k 相似的向量嵌入（假设 k 为 20）。候选信号会基于名称和描述重新排序。最终的信号通过 LLM 选择 prompt 确定。
- 对触发器而言，在选定正确信号之后，触发值和条件比较运算符也会使用 few-shot 示例生成。
- 这些检索到的和生成的信息被组合进预定义的 trigger、action、data 和 task JSON 对象结构。
- 各个 JSON 对象被组装起来，构建最终的 JSON 策略。
- 保存之前，会先通过策略 schema 校验器。

## 方案要点

本节讨论方案的关键组件和特性。

### 改进任务邻接关系

在 automator 策略中，*task* 是更大流程中的一个离散工作单元。它有特定目的，执行一组定义好的动作——既可在车内，也可在车外。它还可选地定义一组触发条件，当条件被判定为真时，定义的动作开始执行。更大的流程——即 *workflow*——定义任务之间的依赖图以及它们的执行顺序。工作流遵循以下规则：

- 每条 automator 策略都以恰好一个任务开始
- 一个任务可以指向一个或多个后续任务
- 一个任务只能启动另一个任务
- 可以存在多个可能的后续任务，但同一时间只能触发一个
- 每个策略工作流在同一时刻只运行一个任务
- 任务可按线性或分支模式排列
- 如果没有任何条件满足，默认行为是监视下一个可用任务的触发条件

例如：

```
# Linear Task Adjacency
t1 → t2 → t3 → t4 → t1*
# Branching Task Adjacency
t1 → t2, t3, t4
t3 → t5
t5 → t4
```

*循环回到起点。

在部分生成的输出中，我们发现可能存在两个相邻任务，其中一个没有动作，另一个没有触发器。任务合并旨在通过把它们合并为单个任务来解决这一问题。为此，我们在 Amazon Bedrock 上使用 Anthropic 的 Claude 实现了任务合并。我们的成果如下：

- 解决任务合并问题，把多个信息不完整的任务合并为一个任务
- 正确生成指向多个后续任务的任务
- 把 prompt 风格改为基于决策树的规划，使其更灵活

### 用于参数生成的多 agent 方法

在信号转换过程中，一份详尽的信号列表会被送入向量存储；当相应的触发器或动作被生成时，就用它们搜索向量存储，选出相关性最高的信号。然而，这有时会产生不够准确或含糊的结果。

例如，下面的策略要求给车辆降温：

`Action: <response> cool down the car </response>`

对应的信号应当尝试冷却车内座舱，如下面的信号所示：

`Vehicle.Cabin.HVAC.Station.Row1.Driver.Temperature`

它不应当冷却汽车发动机，如下面的错误信号所示：

`Vehicle.Powertrain.CombustionEngine.EngineCoolant.Temperature`

我们通过引入多 agent 方法来缓解这一问题。我们的方法包含两个 agent：

- **ReasoningAgent** —— 基于查询和知识库提出初始信号名称
- **JudgeAgent** —— 评估并改进所提出的信号

两个 agent 迭代交互，直到达到设定的循环次数阈值后，才宣告信号识别成功。

### 减少冗余的 LLM 调用

为降低延迟，我们识别出 pipeline 中可合并为单次 LLM 调用的部分。例如，触发条件值生成和触发条件运算符生成原本是两次独立的 LLM 调用。我们通过引入更快的 Anthropic Claude 3 Haiku 模型并在可能时合并 prompt 来解决这一问题。下面是合并前后的一组 prompt 示例。第一个示例是合并前，触发器设为温度高于 20 摄氏度时：

```
Operator response: <operator> > </operator>
Parameter response: <value> 20 </value>
```

下面是对同一触发器的合并响应：

```
<response>
<operator> > </operator>
<value> 20 </value>
</response>
```

### 上下文驱动的策略生成

此处的目标是消除信号转换中的歧义，类似于用于参数生成的多 agent 方法。为了让策略生成更具上下文感知能力，我们提出了一个客户意图澄清器（customer intent clarifier），它执行以下任务：

- 通过知识库查找检索相关子系统
- 识别预期的目标子系统
- 允许用户核实和覆盖

该方法利用外部和预处理过的信息（例如可用的车辆子系统、知识库和信号）来引导信号选择。用户也可以在出现歧义时尽早澄清或覆盖意图，从而减少无效迭代、更快达成期望结果。例如，在前文提到的“cool the car”生成歧义的例子里，用户会被要求澄清其所指的是哪个子系统——从“Engine”或“Cabin”中选择。

## 结论

把早期反馈回路与多 agent 方法结合起来，使 Sonatus 的策略创建系统转变为更自动化、更高效的方案。借助 Amazon Bedrock，我们构建的系统不仅实现了策略创建自动化，把耗时减少 70%，还通过上下文感知的生成与校验保证了准确度。因此，组织可以在自己复杂的策略创建工作流中，用 Amazon Bedrock 实施这种多 agent 方法，从而获得类似的效率提升。开发者可以利用这些技术构建自然语言界面，在业务关键系统中保持精确性的同时大幅降低技术复杂度。
