# Formula 1® 如何利用生成式 AI 加速其 IT 工程师在比赛日的故障处理

[Formula 1®（F1）](https://www.formula1.com/)赛事是高风险的活动，运营效率至关重要。在这些直播赛事期间，F1 的 IT 工程师必须对其各项服务中的关键问题进行分类处理，例如某个 API 的网络性能下降。这会影响消费该 API 数据的下游服务，包括 F1 TV 等产品，因为这些产品提供每场比赛的直播与点播内容以及实时遥测数据。确定这些问题的根本原因并防止其再次发生需要投入大量精力。受赛程和变更冻结期的限制，分类、测试并解决一个关键问题最多可能需要 3 周，且需要开发、运营、基础设施和网络等多个团队协同排查。

“我们过去常常遇到 Web API 系统反复出现的问题：响应缓慢、输出不一致。团队在数场赛事期间前后花费了大约 15 个完整工程师日，反复审查日志、检查异常并迭代修复，才逐步解决这个问题。”Formula 1 的 IT 运营负责人 Lee Wright 说道。F1 将这一挑战视为创新机会，与 [Amazon Web Services（AWS）](https://aws.amazon.com/)合作，使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 开发了一套 AI 驱动的解决方案来简化问题处理。在本文中，我们展示 F1 如何构建一个专门定制的根因分析（RCA）助手，让运营工程师、软件开发人员和网络工程师等用户能够排查问题、缩小根因范围，并显著减少在直播赛事期间及之后修复重复性问题所需的人工介入。我们还为配套的对话式应用提供了一个通用版本的 GitHub 仓库。

用户可以用自然语言提示词向基于对话的 RCA 助手提问，解决方案会在后台进行排查，识别事件的潜在原因并推荐后续步骤。该助手连接内部和外部系统，能够查询 SQL 数据库、[Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 日志和第三方工具等多种来源，以检查系统的实时健康状态。由于该解决方案不要求具备特定领域知识，甚至让不同专业方向、不同经验水平的工程师都能解决问题。

“借助 RCA 工具，团队可以在 3 天内缩小根因范围并实施解决方案，其中还包括在一个比赛周末内完成部署和测试。该系统不仅在主动处理问题上节省时间，还能把问题转交给正确的团队来解决，让各团队可以专注于其他高优先级任务，例如构建新产品以提升观赛体验。”Wright 补充道。借助生成式 AI，工程师针对某个具体查询可在 5–10 秒内收到回复，初始分类时间从一天以上缩短到 20 分钟以内。端到端的解决时间最多缩短了 86%。

## 实现根因分析解决方案架构

F1 与 AWS Prototyping 团队合作，启动了为期 5 周的原型项目，以验证该方案的可行性。目标是用 AWS 复现并自动化当前针对两个候选系统的人工排查流程。作为起点，团队梳理了真实发生的问题，绘制了一张流程图，列出 1）排查流程，2）涉及的团队与系统，3）所需的实时检查，以及 4）每种场景所需的日志调查。以下是解决方案架构图。

![根因分析解决方案的架构图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/02/06/root-cause-analysis-architecture.png)

为高效处理日志数据，原始日志被集中到一个 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）存储桶中。[Amazon EventBridge](https://aws.amazon.com/eventbridge/) 定时任务每小时检查该存储桶是否有新文件，并触发使用 [AWS Glue](https://aws.amazon.com/glue/) 和 Apache Spark 构建的日志转换 ETL（抽取、转换、加载）流水线。转换后的日志存放在另一个 S3 存储桶中，再由另一个 EventBridge 定时任务把这些转换后的日志送入 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)——一项端到端托管的[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）工作流能力，使对话助手能够高效查询这些日志。[Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 负责与内部系统（如数据库和 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2/)（Amazon EC2）实例）以及外部系统（如 Jira 和 Datadog）交互。Anthropic 的 Claude 3 模型（开发时的最新模型）用于编排并生成高质量回答，确保对话助手提供的信息准确且相关。最后，对话应用托管在 [Amazon Elastic Container Service](https://aws.amazon.com/ecs/)（Amazon ECS）的 [AWS Fargate](https://aws.amazon.com/fargate/) 服务上，具备可扩展性和可靠性，能够在不牺牲性能的情况下应对负载波动。

以下小节进一步说明该解决方案的主要组件：转换日志数据的 ETL 流水线、agentic RAG 实现，以及对话应用。

## 创建 ETL 流水线以转换日志数据

在 AI 项目中，第一步是准备好数据以产出高质量结果。AWS 帮助你持续提升数据质量，让你可以放心大胆地创新。Amazon CloudWatch 让你看清整个系统的性能，并支持设置告警、自动响应变化，获得统一的运营健康视图。

在本方案中，AWS Glue 和 Apache Spark 负责处理来自这些日志及其他数据源的数据转换，以提升聊天机器人的准确性和成本效率。AWS Glue 帮助你在规模化场景中发现、准备和集成数据。在这个项目中，日志数据转换包含简单的三步流程。以下是数据处理流程图。

| ![展示创建 ETL 流水线步骤的示意图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/02/06/creating-ETL-pipeline.png) |
| --- |

- **数据标准化：Schema、类型与格式** – 将数据统一为一致的格式，有助于对话助手更透彻地理解数据，从而提高输出准确性。要让 Amazon Bedrock Knowledge Bases 摄取来自不同来源、不同格式（如结构、schema、列名、时间戳格式）的数据，必须先对数据进行标准化。
- **数据过滤：移除不必要的数据** – 为进一步提升对话助手的性能，减少需要扫描的数据量很重要。一个简单方法是确定哪些数据列不会被对话助手使用。这样在 ETL 阶段、甚至在摄取进知识库之前就能去掉相当多的数据。此外，它还降低了 embeddings 过程的成本，因为用于转换并 tokenize 进向量数据库的数据更少。所有这些都有助于改善对话助手的准确性、性能和成本。例如，对话助手并不需要某些 HTTP 请求的全部标头，但确实需要 host 和 user agent。
- **数据聚合：缩小数据规模** – 用户只需要知道问题发生在哪一分钟，因此按分钟粒度聚合数据有助于缩小数据规模。例如，当每分钟有 60 个 API 响应时间数据点时，数据会被聚合成每分钟一个数据点。这一条聚合后的事件包含请求完成所需最大时长等属性，让对话助手聚焦于判断响应时间是否偏高——这同样减少了分析问题所需的数据量。

## 使用 Amazon Bedrock Agents 和 Amazon Bedrock Knowledge Bases 构建 RCA 助手

RCA 助手的 agentic（基于 agent 的）RAG 解决方案是基于 Amazon Bedrock 构建的。[Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 可简化工作流并自动执行重复性任务。Agents 利用[基础模型](https://aws.amazon.com/what-is/foundation-models/)（FM）的推理能力，将用户请求的任务拆解为多个步骤。它们根据给定的指令制定编排计划，然后通过调用公司 API 以及使用 RAG 访问知识库来执行该计划，最终向终端用户给出回复。

知识库是 RAG 框架的核心，它查询业务数据源并补充相关上下文来回答问题。Amazon Bedrock Agents 还支持与内部和外部系统交互，例如查询数据库状态以检查其健康状况、查询 Datadog 进行应用实时监控，以及创建 Jira 工单供后续分析和调查。选择 Anthropic 的 Claude 3 Sonnet 模型，是因为它能给出信息丰富、全面的回答，并且能够理解多样化的提问。例如，它能正确解读用户输入的日期格式，如“2024-05-10”或“10th May 2024”。

Amazon Bedrock Agents 与 Amazon Bedrock Knowledge Bases 集成，为终端用户提供统一、整合的前端。RCA agent 会考虑可用的工具与知识库，智能且自主地制定执行计划。在从知识库收到文档、从工具 API 收到响应后，agent 会汇总这些信息，交给[大语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）生成最终回复。下图展示了编排流程。

## 系统安全

使用 Amazon Bedrock，你可以完全控制用于为 RCA 等生成式 AI 应用定制 FM 的数据。数据在传输和静态存储时都会加密。基于身份的策略让你可以进一步控制数据，帮助你管理各角色能对哪些资源、在什么条件下执行哪些操作。

为评估 RCA 的系统健康状况，agent 会执行一系列检查，例如 AWS Boto3 API 调用（比如用 [boto3_client.describe_security_groups](https://boto3.amazonaws.com/v1/documentation/api/latest/reference/services/ec2/client/describe_security_groups.html) 判断某个 IP 地址是否被允许访问系统），或数据库 SQL 查询（SQL：[sys.dm_os_schedulers](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-views/sys-dm-os-schedulers-transact-sql?view=sql-server-ver16)，用于查询 CPU、内存或用户锁等数据库系统指标）。

为帮助保护这些系统免受潜在幻觉甚至提示词注入的影响，agent 不允许临时自行创建数据库查询或系统健康检查。取而代之的是，遵循最小权限原则（PoLP）实现了一系列受控的 SQL 查询和 API 检查。这一层还会校验输入和输出的 schema（参见 [Powertools 文档](https://docs.powertools.aws.dev/lambda/python/latest/core/event_handler/bedrock_agents/#required-resources)），确保这一方面也受到控制。要了解更多关于保护应用的信息，请参阅这篇 ArXiv 论文 [From Prompt Injections to SQL Injection Attacks](https://arxiv.org/abs/2308.01990)。以下代码是一个示例。

```
"""
- Health Checks: one explicit function per Health Check, to avoid potential LLM hallucinations or risky syntax errors.
- DB is KMS-encrypted and behind private subnets. Connection uses Least-Privileges and Secrets Manager
- Schema is protected using OpenAPI, via AWS Lambda Powertools BedrockAgentResolver
"""

from typing import List, Annotated
from helpers import run_sql_query, check_ec2_port_access
from aws_lambda_powertools.event_handler.bedrock_agent import BedrockAgentResolver 
from aws_lambda_powertools.event_handler.openapi.params import Query, Body
from aws_lambda_powertools import Metrics, Tracer, Logger
from aws_lambda_powertools.metrics import MetricUnit

# Initialize Agents, Metrics, Loggers and Tracers
app = BedrockAgentResolver()
metrics = Metrics(namespace="rca-stack-api-logs", service="HealthChecks")
tracer = Tracer()
logger = Logger(level='INFO')

@tracer.capture_method
@app.get("/checkDatabaseCPUMemory", description='Checks the CPU and Memory usage, for the Database server.')
def check_db_cpu_memory() -> Annotated[List, Body(description='Returns Database CPU and Memory metrics')]:
    response = run_sql_query('db_cpu_memory')
    metrics.add_metric(name="DBCpuMemory", unit=MetricUnit.Count, value=1)
    logger.info(response)

    return response
```

## 前端应用：对话助手 UI

对话助手 UI 使用 [Streamlit](https://streamlit.io/) 框架开发，该框架基于 Python，提供简单而强大的应用组件。在 Streamlit 应用中，用户可以通过提供或替换 agent ID 和别名 ID，无缝测试 Amazon Bedrock agent 的各个迭代版本。在对话助手中会显示完整的对话历史，选择 **Clear** 即可重置对话。LLM 应用的响应由两部分组成。左侧是基于用户问题的最终中性回复。右侧是 LLM agent 编排计划与执行的轨迹，默认隐藏，以保持响应简洁清晰。用户可以查看和检视这条轨迹，确认 LLM 聊天机器人调用了正确的工具、检索到了正确的文档。

该对话式应用的通用版本可在 [GitHub 仓库](https://github.com/yhou-uk/streamlit-app-for-amazon-bedrock/tree/main)中获取，你可以在那里试用该方案，并为其他用例进行修改。

在以下演示中，场景是用户反映无法连接 F1 数据库。借助对话助手，用户可以检查所用的数据库驱动版本是否被服务器支持。此外，用户还可以通过提供 EC2 实例 ID 和 [AWS 区域](https://docs.aws.amazon.com/glossary/latest/reference/glos-chap.html#region)来验证 EC2 实例的网络连通性。这些检查由 agent 可访问的 API 工具执行。更进一步，用户还可以通过查看系统日志来排查网站访问问题。在演示中，用户提供错误码和日期，对话助手会从 Amazon Bedrock Knowledge Bases 检索相关日志，以回答他们的问题并为后续分析提供信息。

![](https://d2908q01vomqb2.cloudfront.net/artifacts/DBSBlogs/ml-17879/image004.gif)

技术工程师现在可以用自然语言查询，以调查系统错误和问题。它与现有的事件管理工具（如 Jira）集成，便于无缝沟通和创建工单。在大多数情况下，即使同时存在多个问题，对话助手也能快速识别根因并给出修复建议。在必要时，特别棘手的问题会自动升级给 F1 工程团队调查，让工程师能更好地安排任务优先级。

## 结论

在本文中，我们说明了 F1 与 AWS 如何开发了由 Amazon Bedrock 驱动的根因分析（RCA）助手，以减少人工介入，并把比赛期间反复出现的运营问题从数周加速到数分钟解决。RCA 助手让 F1 团队能把更多时间投入到创新和服务改进上，最终为车迷和合作伙伴带来卓越体验。F1 与 AWS 的成功合作展示了生成式 AI 的变革潜力，它让团队能在更短时间内完成更多工作。
