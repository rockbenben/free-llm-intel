# 使用 Amazon Nova 2 Sonic 将文本 agent 迁移为语音助手

将文本 agent 迁移为语音助手正变得越来越重要，因为用户期待更快、更自然的交互。客户不想打字，而是希望实时说话并被理解。金融、医疗、教育、社交媒体和零售等行业正在探索使用 [Amazon Nova 2 Sonic](https://aws.amazon.com/ai/generative-ai/nova/speech/) 的解决方案，以实现规模化、自然的实时语音交互。

在本文中，我们探讨如何使用 Amazon Nova 2 Sonic 将传统文本 agent 迁移为对话式语音助手。我们比较文本与语音 agent 的需求，强调不同用例的设计重点，拆解 agent 架构，并解决常见问题，例如工具和 sub-agent 的复用、system prompt 的适配。本文帮助你顺利走完迁移过程并避免常见陷阱。

你还可以在 Nova 示例仓库中找到一个 [Skill](https://github.com/aws-samples/amazon-nova-samples/tree/main/skills/text-agent-to-strands-voice-agent)，它可与 Kiro 和 Claude Code 等 AI IDE 配合使用，自动将你的文本 agent 转换为语音 agent。

## 文本 agent 与语音 agent 不是同一个问题

虽然从文本 agent 迁移到语音助手看起来像是在保持业务逻辑不变的前提下加一个语音界面，但重要的是要理解以下几方面的差异。

| **方面** | **文本 agent** | **语音 agent** |
| --- | --- | --- |
| 用户输入 | 键入的文本：用户按自己的节奏阅读、滚动、复制粘贴 | 语音音频流：实时，可打断（barge-in），停顿很重要 |
| 响应风格 | 段落、列表、表格、链接：格式丰富，一次性交付所有信息 | 简短的口语短语，一次只说一件事："Want me to continue?" 并带确认循环 |
| 延迟预算 | 中等延迟容忍度：输入指示器掩盖等待时间 | 要求超低延迟：静默会让人觉得出了问题 |
| 轮次转换 | 严格的请求 → 响应：用户输入、按回车、等待 | 流畅、重叠、可打断：voice activity detection (VAD) + turn detection，需要支持 barge-in |
| 传输 | HTTP / REST / Server-Sent Events：无状态的请求-响应 | 双向流式传输：持久连接，双向实时音频 |

为了更好地应对这些挑战，让我们拆解文本 agent 与语音助手之间的关键差异，以及这些差异如何影响设计与实现。

### 响应设计

文本 agent 的构建目标是交付用户可以按自己节奏阅读的段落，可随时回滚、复制内容并按需点击链接。语音 agent 则运行在完全不同的媒介中。响应必须是对话式的、简洁的，并且针对听而非读精心组织。以一个返回账户信息的银行 agent 为例：

**文本 agent 响应：**

```
Here's your account summary:
- Checking (****4521): $3,245.67
- Savings (****8903): $12,450.00
- Credit Card (****2187): -$1,823.45 (payment due: March 15)

You can click on any account for detailed transactions.
```

**语音 agent 响应：**

“You have three accounts. Your checking account ends in 4521 with a balance of three thousand two hundred forty-five dollars. Want me to go through the others or would you like details on this one?”.

语音 agent 将信息拆分成易于理解的小块，并在继续之前请求确认。它使用 *autonomous conversation style***,** 主动引导用户，而不是一次性倒出所有信息。

### 延迟预算

文本用户对中等延迟有容忍度。他们看到输入指示器并等待。语音用户几乎立刻就会察觉延迟。语音对话中的静默让人觉得线路断了。这改变了 agent 的架构方式：

| **因素** | **文本 agent** | **语音 agent** |
| --- | --- | --- |
| 可接受的响应时间 | 中等延迟容忍度：有加载指示器时等待几秒可以接受。 | 低延迟容忍度：对话应在几百毫秒内完成，并尽快输出首个音频；延迟几秒，尤其是在工具调用期间，会让人感觉没有响应。 |
| 工具调用容忍度 | 多次顺序调用可以接受 | 每次调用都会增加明显的静默 |
| 流式传输 | 锦上添花 | 必不可少 |
| 异步工具处理 | 有则更好 | 必须具备 |

Amazon Nova 2 Sonic 支持[异步工具调用](https://docs.aws.amazon.com/nova/latest/nova2-userguide/sonic-async-tools.html)，因此当工具在后台运行时，对话仍能自然继续。它持续接受输入，可以并行运行多个工具，如果用户中途改变请求，也能从容适配，在交付所有结果的同时聚焦于仍然相关的内容。

### 轮次转换与打断

文本对话本质上是基于轮次的。用户输入、按回车、等待响应。语音对话则是流动的。用户会打断（barge-in）、在句子中间停顿，并期望 agent 自然处理重叠的语音。像 Amazon Nova 2 Sonic 这样的原生 speech-to-speech 模型通过内置的 voice activity detection (VAD) 和 turn detection 在内部处理这些情况。Nova 2 Sonic 管理对话上下文，无需在每一轮都发送完整历史。

## 从架构视角看迁移

考虑到这些差异，我们从架构角度拆解迁移过程，将系统分为三个主要组件，并考察每个组件如何演进。文本 agent 的概念设计由三个组件构成：

- 客户端应用（例如 Web、移动端或 IoT 界面）。
- 一个文本 orchestrator，负责管理 system prompt、工具和对话上下文。
- 连接到你系统的工具集成，例如 API、数据库、工作流、Retrieval Augmented Generation (RAG) 管道或 sub-agent。

将这一架构迁移到语音 agent 时，这些组件保持不变，但每个组件都需要不同的改动以支持语音特有的逻辑。

### 客户端应用

agent 客户端通常用 Web 浏览器、移动应用或 IoT 设备所使用的编程语言和系统实现，具体取决于部署场景。语音 agent 客户端需要持久的双向连接（例如 WebSocket 或 WebRTC），并处理音频编码/解码、客户端事件、barge-in 逻辑、噪声控制和转录显示。这比文本客户端复杂得多，后者通常通过无状态的 REST 或单向 HTTPS 流式接口与 agent 通信。

因此，该组件通常需要重构或完全重写。例如，用 [Streamlit](https://streamlit.io/) 前端构建的 PoC 很可能需要使用 [React](https://react.dev/) 这样的 JavaScript 框架重建，以支持双向连接。

关于使用 WebSocket 的 REACT 轻量级语音 agent Web 客户端应用，请参阅[此示例](https://github.com/aws-samples/amazon-nova-samples/tree/main/speech-to-speech/amazon-nova-2-sonic/sample-codes/agentcore/strands/client)。

### orchestrator

agent orchestrator 是构建文本或语音 agent 时的中心枢纽。它管理 system prompt、选择并路由工具或 sub-agent，并维护对话上下文，使交互保持连贯且与 agent 的角色一致。在文本 agent 中，orchestrator 处理客户端与推理模型之间的请求和响应，同时集成工具以触发业务逻辑。语音 orchestrator 遵循相同的原则，但增加了音频流、Voice Activity Detection (VAD)、Automatic Speech Recognition (ASR)、推理和 Text-to-Speech (TTS)。Amazon Nova 2 Sonic 提供双向流式接口，将这些功能组合在一起，因此用户可以从文本 agent 迁移推理 prompt 和工具触发器，更平滑地过渡到语音。

与传统文本 agent 架构的一个关键区别是，Amazon Nova 2 Sonic 可以**在同一个模型接口中同时接受文本和音频输入**。这意味着 Sonic 可以直接替代文本 orchestrator 中通常使用的独立文本推理模型。Sonic 不再串联独立的 ASR → LLM → TTS 组件，而是将语音识别、推理、工具使用和语音合成统一到一个双向模型中。这样一来，团队可以复用现有的 prompt 和工具，同时精简架构、降低延迟，并免去在语音技术栈中管理单独的文本推理模型的需要。

以下代码片段展示了一个用 [Strands Agents](https://strandsagents.com/) 构建的示例文本 agent，它使用 [Amazon Nova 2 Lite](https://docs.aws.amazon.com/ai/responsible-ai/nova-2-lite/overview.html) 作为 large language model (LLM)。其中定义了工具，并给出一个使用 [Strands BidiAgent](https://strandsagents.com/docs/user-guide/concepts/bidirectional-streaming/agent/) 和 Nova 2 Sonic 创建可通过 WebSocket 访问的语音 agent orchestrator 的示例。你会注意到，在 Strands 中文本 agent 和语音 agent 的编码风格高度相似。尽管示例使用 Strands，但同样的方法适用于用 LangChain、LangGraph 或 CrewAI 等其他框架构建的文本 agent，因为文本 orchestrator 所需的关键输入就是 system prompt 和工具定义。

在运行以下各节的示例之前，请安装 Python 及所需依赖（包括 strands-agents 和 Boto3），并确保你的 IAM 配置对所需服务具备必要的权限。

```
from strands import Agent, tool 
from strands.models import BedrockModel 
 
# ---- Mock tools will be used in both text and voice agents ---- 
@tool 
def authenticate_customer(account_id: str, date_of_birth: str) -> str: 
    """Verify customer identity and return an auth token.""" 
    # In real implementation, call your auth service / API 
    if account_id == "123456": 
        return "AUTH_TOKEN_ABC123" 
    return "Authentication failed" 
 
@tool 
def get_account_balance(auth_token: str) -> str: 
    """Return the customer’s current account balance.""" 
    if auth_token == "AUTH_TOKEN_ABC123": 
        return "Your current checking account balance is $5,420." 
    return "Unauthorized request" 
 
@tool 
def get_recent_transactions(auth_token: str) -> str: 
    """Return recent transactions.""" 
    if auth_token == "AUTH_TOKEN_ABC123": 
        return "Recent transactions: $45 groceries, $120 utilities, $18 coffee." 
    return "Unauthorized request" 
```

使用 Strands Agents，你可以用 Nova 2 Lite 创建一个文本 agent orchestrator，如下例所示：

```
# ---- Nova 2 Lite model ---- 
model = BedrockModel(model_id="amazon.nova-2-lite-v1:0") 
 
# ---- Banking assistant text agent ---- 
bank_agent = Agent( 
    model=model, 
    system_prompt="""You are a banking assistant. Answer user questions about account balances, recent transactions accurately. Always validate user identity before providing sensitive information. 
""", 
    tools=[authenticate_customer, get_account_balance, get_recent_transactions], 
) 
```

使用 Strands BidiAgent，你可以用类似的编码风格、借助 Nova 2 Sonic 模型构建一个语音 agent orchestrator，并复用相同的工具：

```
# voice_orchestrator.py — BidiAgent with sub-agents as tools  
from strands.experimental.bidi.agent import BidiAgent  
from strands.experimental.bidi.models.nova_sonic import BidiNovaSonicModel  

# ---- Nova 2 Sonic model ----  
model = BidiNovaSonicModel(  
    region="us-east-1",  
    model_id="amazon.nova-2-sonic-v1:0",  
    provider_config={"audio": {"voice": "tiffany", "input_sample_rate": 16000, "output_sample_rate": 16000}},  
)  

# ---- Banking assistant voice agent ----  
agent = BidiAgent(  
    model=model,   
    system_prompt=""" You are a banking assistant. Speak naturally and answer questions about account balances, recent transactions. Confirm the customer’s identity before sharing sensitive details. Use short, clear responses and acknowledge when retrieving data. 
""",  
    tools=[authenticate_customer, get_account_balance, get_recent_transactions], 
)  
await agent.run(inputs=[ws_input], outputs=[ws_output]) 
```

system prompt 是文本和语音 agent 的基础。它定义 agent 的角色、语气和 guardrails，确保响应在书面和口头交互中都保持一致、可靠，并符合业务目标和用户期望。从文本迁移到语音时，要针对实时音频调整 system prompt。保持简洁和对话化，考虑延迟和多轮上下文，并将复杂的指导拆分为更小的步骤。

**文本 prompt（原始）：**
*“You are a banking assistant. Answer user questions about account balances, recent transactions accurately. Always validate user identity before providing sensitive information.”*

**语音适配后的 prompt：**
*“You are a banking assistant. Speak naturally and answer questions about account balances, recent transactions. Confirm the customer’s identity before sharing sensitive details. Use short, clear responses and acknowledge when retrieving data.”*

注意，在使用 Nova 2 Sonic 的语音 orchestrator 中，你使用 Sonic 内置的推理能力来管理 system prompt、工具选择和会话上下文。你不再需要在 orchestrator 层面提供自己的 LLM 进行推理。

### 业务逻辑层

工具集成是将 agentic 助手连接到业务层的关键环节，使用 Model Context Protocol ([MCP](https://modelcontextprotocol.io/docs/getting-started/intro))、Agent-to-Agent ([A2A](https://github.com/a2aproject/A2A)) 和标准 HTTP 等协议。在基于文本的 agent 中，orchestrator 将文本输入发送给工具（如 REST API、[RAG](https://aws.amazon.com/what-is/retrieval-augmented-generation/) 系统或数据库），并接收文本响应以生成面向用户的回复。

在 Strands Agents 示例中，用于文本 agent 的相同工具无需改动代码即可复用于语音 agent。然而，为语音复用工具和 sub-agent 涉及的远不止实现细节。

如果你已经使用多 agent 架构，你的专门业务逻辑 agent 通常只需稍作更新即可复用于语音。下图展示了一个银行助手，其中语音 orchestrator 调用 sub-agent 来进行身份验证和房贷查询。

[![voice-multi-agents](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/20/ml-20642-image-3.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/20/ml-20642-image-3.png)

尽管这些 sub-agent 不需要完全重写，但确实需要针对语音进行调优：

**更短的响应 –** 文本 sub-agent 可能返回一整段详细内容。语音 sub-agent 应返回 1–2 句话，让 orchestrator 能自然地读出。例如，你将 sub-agent 的 system prompt 改为 “Summarize in 1 to 2 concise sentences”，而不是 “Provide a comprehensive answer.”

**延迟改进 –** 为 sub-agent 选择更小、更快的模型（例如，从 [Nova 2 Lite](https://docs.aws.amazon.com/ai/responsible-ai/nova-2-lite/overview.html) 开始，而非更大的模型）。在语音对话中，每一次额外的推理跳数都会增加明显的静默。对于 Nova 2 Lite，我们建议限制或避免使用 thinking mode，以降低延迟。更多信息请参阅 [Amazon Nova 2 的 Amazon Nova 开发者指南](https://docs.aws.amazon.com/nova/latest/nova2-userguide/extended-thinking.html#how-extended-thinking-works)..

**工具结果的精简 –** 有些 sub-agent 被设计为返回大量原始有效载荷，例如包含超出所需数据的 JSON，让 orchestrator 自行过滤响应。这并不理想，对语音尤其如此。更大的有效载荷会增加延迟、可能降低准确性，并可能暴露敏感数据。精简、有针对性的响应至关重要，尤其是对延迟敏感的语音体验。

**使用填充消息**，在工具处理时间较长时保持对话自然。借助 Amazon Nova 2 Sonic，你可以进行[异步工具调用](https://docs.aws.amazon.com/nova/latest/nova2-userguide/sonic-async-tools.html)并自定义这些过渡消息，确保在 agent 完成任务期间用户保持参与。

这些调整大多涉及 prompt 和配置更改，而非架构修改。sub-agent 的工具、业务逻辑和部署保持不变。虽然 sub-agent 架构提供了清晰性、可复用性和可移植性，并且在将文本 agent 迁移到语音时尤其有用，但每次 sub-agent 调用都会因其自身的推理模型和工具调用而增加延迟。在语音对话中，这可能表现为由 sub-agent 推理导致的明显停顿。

## 结论

将文本 agent 迁移到语音助手并非套一层外壳那么简单。从响应设计到延迟预算再到轮次转换行为，交互模型根本不同。但借助结构良好的多 agent 架构和 Amazon Nova 2 Sonic，业务逻辑层可以保持不变。
