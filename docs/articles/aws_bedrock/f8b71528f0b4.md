对照不断变化的州房东-租客法律核查数万份公寓租约，并证明你确实核查了全部，一直超出了多数合规团队的能力范围。但在 [Amazon Quick](https://aws.amazon.com/quick/) 中把生成式 AI 与合适的后端相配，如今这成为可能。在本文中，我们引入一个叫做“裁定式查询（Adjudicated Query）”的设计模式。业务用户可以在一个聊天界面（Amazon Quick）中用它问合规问题，而实际的通过/失败决定留在一个确定性（非 AI）规则引擎里。我们演练一个实现该模式的 AWS 参考架构，并部署一个你可以端到端运行的可用示例。该模式也适用于其他高风险合规领域（制裁筛查、保险理赔裁定、出口管制），但租约合规作为我们的具体例子。

## 规模下的合规挑战

一个组合运营商在多个州持有 50,000 份租约。每个州发布房东-租客法规（滞纳金上限、通知期、押金上限），这些法规按立法机构的日程而非运营商的日程变化。当一项法规变化时，负责合规的团队必须判定哪些租约现在越界了。

在少量时，一名律师助理阅读租约。答案是可信的，因为有一个人在背后担保。越过某个阈值之后，这就不再可行。工作转向软件，而一个新问题出现：答案如今是屏幕上的一个数字，没有人能独立验证。

从这个现实得出两个属性：

- **可证明的完整性：** 像“我们核查了全部 22,910 份德州租约”这样的声明必须为真且可证明。一条从未被评估的记录必须被报告为未评估，而非被悄然省略。
- **可辩护性：** 一个发现可能在数月后在诉讼、审计或监管检查中被质疑。为它辩护意味着知道哪个版本的哪条规则、被应用到哪个条款文本、用什么方法、在什么日期、由谁。

这两个属性正是把这一问题与企业搜索区分开来的东西。检索增强生成（RAG）应对了可及性缺口，但无法满足其中任何一个属性。相似度搜索没有一个意味着*全部*的阈值。一个排名的样本从不知道自己排除了什么。

Text-to-SQL 缩小了这一差距，却携带一类风险：一个幻觉的谓词会悄然缩小总体，而由此得到的数字即便范围错了也看起来精确。

## 裁定式查询模式如何解决它

裁定式查询模式是一个确定性规则引擎之上的、有界的对话层。模型只做两件事：把一个自然语言问题翻译成对一个固定类型化操作集的调用，并叙述返回的结果。它从不写查询、从不固定总体，也从不执行一个裁定。

在这道边界之后坐着一个规则引擎。规则是版本化的数据，而非代码。引擎知道通用的比较操作符（`gte`、`lte`、`equals`、`exists`），且不含任何点名某个司法辖区或主题的分支。一次法律变更是一次规则手册行编辑，而非一次代码部署。

每次合规扫描都产出一张完整性回执：一个被断言的不变式——compliant + in-breach + ambiguous + unreadable 必须等于 scanned。它由计数计算得出，并在任何东西持久化之前被断言。一个无法说明其总体的运行永远不会结束。不存在某条记录被悄然跳过的路径。

对话界面承载计数、回执和一个带标签的样本。完整的结果集（可能数万行）住在一个读取同一数据存储的仪表盘界面上，可逐记录钻取。这一分离意味着模型永远不会把那份保证摘要掉。

### 为什么不用 RAG 或 text-to-SQL？

| 方法 | 总体 | 完整性 | 可辩护性 |
| --- | --- | --- | --- |
| 语义检索（RAG） | 一个排名的样本 | 结构上不可能 | 部分 |
| 生成的查询（text-to-SQL） | 声称但无法证明 | 悄然缩小的风险 | 若建模 |
| 规则引擎 + BI（无聊天） | 精确且已证明 | 是 | 是 |
| 裁定式查询 | 精确且已证明 | 是 | 是 |

裁定式查询模式把自然语言访问加到规则引擎加商业智能（BI）方法之上，而不牺牲那份保证。当需担责的用户需要对话式访问，而漏掉一条记录是一种负债而非小麻烦时，它是正确的选择。

## 参考架构

下图端到端展示各组件如何拼合。一名合规官在 Amazon Quick 中与两个界面交互：一个用于问问题的聊天智能体，和一个用于浏览完整结果集的 Amazon Quick Sight 仪表盘。聊天智能体先从 Amazon Cognito 取一个 OAuth 令牌。然后它通过一个 Amazon API Gateway HTTP API 发送 Model Context Protocol (MCP) 请求，该 API 在转发到一个 AWS Lambda 函数之前验证令牌。该 Lambda 函数托管 MCP server 和规则引擎，通过 RDS Data API 读写 Amazon Aurora Serverless v2，并只为探索性条款搜索路径调用 Amazon Bedrock。Amazon Quick Sight 仪表盘通过一条专有网络（VPC）连接直接读取同一个 Aurora 存储。因此两个界面从同一个存储读取，这正是让完整性回执成为单一事实来源的原因。

图 1：裁定式查询模式的参考架构

两个界面读取同一个存储。聊天智能体承载完整性回执和一个到仪表盘的链接。仪表盘承载体量，因为 10,800 行无法在一个聊天消息中渲染。Amazon Bedrock 只被探索性操作从 AWS Lambda 调用。没有任何模型参与合规扫描，而 Amazon Aurora Serverless v2 也不调用模型。

### 有界的操作面

该 MCP server 恰好暴露六个工具，每个有不同的语义：

| 工具 | 它做什么 | 结果意味着 |
| --- | --- | --- |
| sweep_compliance | 对照某个指定日期生效的规则做穷尽的总体扫描 | 官方。每份租约都计入一张计算出的回执。写入发现 |
| simulate_rule_change | 一条规则在一个提议值下对照已批准的基线测试 | 探索性。仅有方向性计数。不记录任何东西 |
| explore_clauses | 在一个过滤总体内按语义相似度的 Top K | 解释性。一个排名的样本。无法回答“有多少” |
| get_finding | 一个发现的完整证据链 | 钻取到单个裁定 |
| list_rules | 某日期生效的规则手册，带版本、引用、批准人 | 参考查找 |
| check_connection | 存活检查，不触碰任何数据 | 传输健康 |

这一有界操作面消除了通向生成查询那种悄然缩小风险的路径。因为模型只能从一个总体逻辑由人来编写、审阅和测试的固定操作集中选择，它无法组合出一个错误的总体。

### 关键架构组件

借 Amazon Quick 对话式界面和智能体编排层，你可以问自然语言合规问题，Amazon Quick 聊天智能体把它们翻译成对有界 MCP 操作面的调用。Amazon Quick 用 OAuth 2LO 通过 [Amazon Cognito](https://aws.amazon.com/cognito/) 向 MCP server 认证，并处理工具发现和响应叙述。确定性引擎处理合规逻辑。

[Amazon Aurora Serverless v2](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2.html)（Postgres + pgvector）在一个单一的关系存储中存储规则手册、租约记录、提取状态、裁定和运行。把一切都放进一个数据库，使完整性回执成为一个 SQL 计数——一种以低成本让核心保证可检视的方式。

[AWS Lambda](https://aws.amazon.com/lambda/) 托管 MCP server（基于 Streamable HTTP 的 JSON-RPC 2.0，对响应使用 Server-Sent Events 成帧，这是 Amazon Quick 客户端所要求的）和规则引擎。有界操作被翻译成基于集合的 SQL，规则值作为参数绑定。没有自然语言到达查询层。

[Amazon API Gateway](https://aws.amazon.com/api-gateway/) HTTP API 提供一个由 Amazon Cognito 支撑的 JSON Web Token (JWT) 授权器的前门。不存在未认证的路由。

[Amazon Cognito](https://aws.amazon.com/cognito/) 通过一个双腿（客户端凭证）流程签发 OAuth 令牌。client secret 在注册时从 Amazon Cognito 读取，而不写到磁盘。

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 只为探索性路径提供动力，用 Amazon Titan Text Embeddings V2（`amazon.titan-embed-text-v2:0`）做语义相似度排名，并用通过跨区域推理配置调用的 Anthropic Claude Sonnet 5 做定性的条款评估。官方合规裁定不征询它。Amazon Bedrock 的模型可用性——包括 Amazon Titan Text Embeddings V2 和 Anthropic Claude Sonnet 5——因 AWS 区域而异，因此部署前确认这些模型在你的区域可用。

[Amazon Quick Sight](https://aws.amazon.com/quicksight/) 通过一条 VPC 连接接入 Aurora，并渲染完整的发现表，可按扫描和严重性带过滤，每行上已经带着为辩护一个裁定所需的每一列。

### 不可妥协的设计规则

- 规则是数据。一次法律变更是一条规则手册行。引擎不含辖区特定的分支。
- 没有自然语言到达 SQL。操作符选取固定的 SQL 模板。规则值作为参数绑定。
- 确定性先于 AI。一个数字比较回答扫描。不征询任何模型。
- 精确过滤以保证完整性，向量仅用于排名。相似度从不决定成员资格。
- 回执是计算出来的，而非手写。这一不变式在一次扫描提交之前被断言。
- 不可读的文档被点名，而非丢弃。每份租约恰好落进一个桶。
- 发现是仅追加的。代码库中不存在对发现的 UPDATE 或 DELETE。

## 把摘要模型当作一个不可信的渲染器

有一个设计元素值得单独一节，因为它看起来很陌生：那些用于经受住聊天模型改述的工程防护。

把模型排除在决策路径之外、却又把一个放回交付路径，会在链的末端重新引入风险。在实践中，我们观察到：

- **一个模型剥掉了一个限定前缀。** 一个 ILLUSTRATIVE 引用标签在改述中被移除，而模型把一个编造出来的引用当作法规呈现。
- **一个模型从一个样本外推。** 给定 20 行预览，模型推断出一个数据中并不存在的、覆盖整个总体的范围。

三种技巧应对这一点：

- **把限定措辞作为不可剥离的方括号后缀**，在多个载荷层级重复，而非作为看起来可移除元数据的引导标签。
- **提供使诚实答案成为简单答案的数据。** 对每一条记录计算真实的聚合，并把它们交给模型。一个握有真实数字的模型不必从样本来猜。
- **在多个结构层级重复模式标签**（字段、字符串、摘要），以便至少有一个经受住改述。

原则是：载荷中的一道防护，其强度只等于它经受改述的能力。

## 部署并运行示例

完整的参考实现可在 GitHub 获取。它随附合成数据（没有真实客户租约数据）、确定性的语料生成，以及针对已部署栈的验收测试。

### 前提条件

部署前，确认你有：

- 一个 AWS 账户，在美国东部（弗吉尼亚北部）区域（us-east-1）为 Amazon Titan Text Embeddings V2 和 Anthropic Claude Sonnet 5 启用了 Amazon Bedrock 模型访问。
- 配好凭证的 AWS Command Line Interface (AWS CLI) v2（`aws sts get-caller-identity` 应成功）。
- Python 3.12。
- 用于 AWS Cloud Development Kit (AWS CDK) CLI 的 Node.js 24。mise 是可选的，仅用于配置 Node 24。你可以用你选择的方法安装 Node 24（Node 18 对 CDK 已到生命周期终点）。

### 步骤 1：克隆仓库

克隆示例仓库并设置 Python 环境：

```
git clone https://github.com/aws-samples/sample-quick-adjudicated-query.git
cd sample-quick-adjudicated-query
python3 -m venv .venv && .venv/bin/pip install -q -r requirements.txt
```

### 步骤 2：部署基础设施

引导 CDK（如果尚未做）并部署栈。Aurora 配置通常需要约 11 分钟，尽管时长因账户和区域而异。

```
eval "$(mise env -s zsh)"
export CDK_DEFAULT_ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
npx aws-cdk@2.261.0 bootstrap aws://$CDK_DEFAULT_ACCOUNT/us-east-1
npx aws-cdk@2.261.0 deploy --outputs-file outputs.json
```

CDK 版本被固定到 2.261.0 以匹配 requirements.txt。该栈部署：

- Amazon Cognito（2LO 客户端）。
- 带 JWT 授权器的 Amazon API Gateway。
- AWS Lambda（MCP server + 规则引擎）。
- Amazon Aurora Serverless v2。
- Amazon Quick Sight 网络。

### 步骤 3：填充数据并验证

依次运行迁移、语料生成、摄入和 Amazon Quick Sight 设置脚本：

```
PY=.venv/bin/python
$PY db/migrate.py          # schema, rulebook, views (7 checks)
$PY gen_corpus.py          # deterministic corpus + manifest
$PY ingest.py              # load + embed (timing varies by environment)
$PY setup_dashboard.py     # Quick Sight wiring
$PY acceptance.py          # 28 checks against the live stack
```

语料是确定性的，因此一个重建的栈会复现相同的结果。

### 步骤 4：在 Amazon Quick 中注册 MCP 集成

Amazon Quick 在注册时对工具列表做快照。在你删除并重新创建集成之前，Amazon Quick 不会检测到新的或重命名的工具。仅部署 Lambda 是不够的。

从你的部署输出打印注册输入：

```
python3 - <<'PY'
import json
o = json.load(open('outputs.json'))['QuickPocStack']
for k in ('McpUrl', 'TokenEndpoint', 'ClientId', 'Scope'):
    print('%-14s %s' % (k, o[k]))
PY
```

取回 client secret（每次从 Amazon Cognito 读取，不写到磁盘）。用你输出中 Issuer URL 里的用户池 ID：

```
aws cognito-idp describe-user-pool-client \
    --user-pool-id <UserPoolId> \
    --client-id <ClientId> \
    --query UserPoolClient.ClientSecret --output text
```

然后在 Amazon Quick 中：Connectors > Create for your team > Model Context Protocol。先删除任何现有条目，然后用那些值（OAuth 客户端凭证/2LO）创建一个新条目。把 client secret 直接复制到 Amazon Quick 中，而非复制到一个文件或 shell 变量里。

### 步骤 5：验证集成

按此顺序端到端验证部署：

```
$PY show_payload.py check_connection   # transport alive
$PY acceptance.py                      # 28/28 checks
```

验收套件证明服务器工作。下一节演练 Amazon Quick 聊天体验，以确认 Amazon Quick 选对工具。

## 演练体验

在栈部署并验证之后，你现在可以从 Amazon Quick 聊天运行一次合规扫描并检查结果。

### 问一个合规问题

在 Amazon Quick 聊天中，输入：“Which Texas leases violate the late fee cap? Use rules effective 01/01/2026.”

Amazon Quick 把这识别为一次合规扫描并选择 `sweep_compliance` 工具。该工具对总体中每一份德州租约做穷尽检查，应用在指定日期生效的规则。裁定中不涉及任何模型。

Amazon Quick 叙述结构化的结果。图 2 展示聊天响应：一张表中若干不合规发现的简短样本、以计数渲染的完整性回执、一个合成数据限定，以及一个打开完整仪表盘的链接。

图 2：带完整性回执和发现样本的 Amazon Quick 聊天响应

响应含若干不合规发现的样本，以及作为计数的完整性回执：10,111 个违规、689 个模糊和 20 个不可读。它还含一个合成数据限定和一个进入 Amazon Quick Sight 仪表盘的链接。它刻意不尝试渲染全部 10,111 行。

通过检查那个不变式来验证完整性回执：compliant + in-breach + ambiguous + unreadable 应等于所扫描的总体。在本例中，这些计数之和等于整个德州租约总体，确认每条记录都恰好落进一个桶。

### 在仪表盘上检视完整总体

跟随聊天响应中的仪表盘链接打开 Amazon Quick Sight 仪表盘。图 3 展示发现标签页，其中扫描得到的每一对租约-规则都作为其自己的行出现，带完整的证据链。

图 3：列出扫描得到每一个发现的 Amazon Quick Sight 仪表盘

仪表盘显示扫描得到的每一个发现，每对租约-规则一行。用严重性带过滤器隔离违规中的发现。每一行带租约 ID、触发的那条规则、提取出的值和期望值。按规则排序以把相关违规分组并识别跨组合的模式。

### 钻取到单个发现

选择一行会打开发现详情。图 4 展示单个发现，一侧是逐字的租约条款，另一侧是触发的那条规则，包括其版本、引用和被比较的值。

图 4：展示租约条款与触发规则并列的发现详情

这就是可辩护性在实践中的样子。发现展示提取的值（7% 滞纳金）、要求的值（5% 上限），以及规则引用（TX Prop. Code ch. 92 subch. B, as amended eff. 2026-01-01）。这一切都逐字与租约里的条款文本并列呈现，因此无需重建任何东西。

### 测试额外的路由路径

通过测试其余操作来确认 Amazon Quick 路由到正确的工具：

- “Find Texas clauses that read like liability waivers.”（应调用 `explore_clauses`）。
- “What if the Texas late fee cap dropped to 3%?”（应调用 `simulate_rule_change`）。

## 清理

为避免持续产生费用，完成时销毁栈：

```
npx aws-cdk@2.261.0 destroy
```

Aurora Serverless v2 可以缩放到 0 个 Aurora 容量单元（ACU），并在一段不活动后自动暂停（见 [Amazon Aurora 定价](https://aws.amazon.com/rds/aurora/pricing/)）。本示例作为一个刻意的决定改为设一个小的非零最小容量，因为一个暂停的集群会给一个会话的第一个问题增加恢复延迟。不部署 NAT 网关。

如果你计划之后再回到该栈、却想在多次会话之间最小化成本，在 `infra/stack.py` 中设 `serverless_v2_min_capacity=0` 并重新部署，以启用带自动暂停的缩放到零。预期在集群暂停后的第一个查询有一个短暂的恢复延迟。语料是确定性的，因此一个被完全销毁并重新部署的栈会复现相同的结果。

## 安全考量

因为这一模式为合规工作而打造，安全是设计的一部分而非附加项。示例应用以下实践，你应在适配之前对照自己的要求逐一审视它们。

- **仅认证访问。** 来自 Amazon Quick 的每个请求通过一个由 Amazon Cognito 支撑的 JSON Web Token (JWT) 授权器保护的 Amazon API Gateway HTTP API 到达 MCP server。不存在未认证的路由，而双腿（客户端凭证）OAuth 流程签发短期令牌而非长期密钥。
- **Secret 处理。** Amazon Cognito 的 client secret 在注册时读取，不写到磁盘也不提交到源码控制。只把它存储在 Amazon Quick 连接器配置中，并按你的正常日程轮换它。
- **最小权限的模型访问。** AWS Lambda execution 角色只为示例所用的具体 Amazon Titan Text Embeddings V2 和 Anthropic Claude Sonnet 5 模型 ARN 授予 Amazon Bedrock InvokeModel，而非覆盖所有模型。在你自己的构建中同样地限定 AWS Identity and Access Management (IAM) 权限的范围。
- **数据路径的网络隔离。** Amazon Quick Sight 通过一条 VPC 连接而非一个公共端点接入 Amazon Aurora Serverless v2，而数据库安全组只放行预期的来源。把存储保持在公网之外。
- **查询路径中没有自然语言。** 规则引擎只从一张固定的操作符到模板表、带规则值作为参数绑定来组装 SQL，这消除了一个由模型编写的查询会造成的注入面。这既是一种正确性属性，也是一种安全属性。
- **可审计、仅追加的发现。** 发现是仅追加的，代码库中没有 UPDATE 或 DELETE 路径，因此合规记录不能在事后被悄然篡改。每个裁定带它的证据链以供后续审阅。
- **合成数据边界。** 示例随附合成租约数据，并清楚标注占位规则和引用。在针对真实记录运行之前，完成你组织的数据分类、访问审查，以及对任何规则内容的法务验证。
- **一次扫描的人工归属。** Amazon Quick 通过双腿（客户端凭证）流程机器到机器地向 MCP server 认证，因此令牌标识的是 Amazon Quick 应用，而非在聊天中提问的那个人。引擎记录了决定了什么、规则版本、证据、方法和日期，但它不接收一个终端用户身份来随发现一起存储。对于可辩护性中“由谁”的部分，归属住在 Amazon Quick 审计层，它记录哪个用户运行了哪个聊天动作。一个发现通过把其扫描 ID 和时间戳与该记录相关联来回溯到一个人。如果你需要把归属记录在合规存储本身中，把一个终端用户 ID 从 Amazon Quick 贯穿到工具调用并持久化在扫描行上。那时“谁”就随发现一起传输，而非只活在 Amazon Quick 审计层中。

## 何时使用这一模式

只要以下条件成立，裁定式查询模式就适用：

- 漏掉一条记录是一种负债而非小麻烦。
- 答案可能在数月后被一个不在场的人质疑。
- 支配逻辑由外部所有并自成日程地变化。
- 记录主体是可枚举的（你能列出某个问题覆盖的每一条记录）。

这一描述覆盖了很广的领域。例子包括租约合规、保险理赔裁定、制裁筛查、出口管制、临床试验方案监控、建筑规范检查、财务报告控制测试，以及资质验证。

当看似合理的答案就足够、且用户可以重新发问时，RAG 是更简单的选择。Text-to-SQL 对那些能够验证生成的查询、并容忍偶发错误结果的团队很有效。如果需担责的用户会接受没有对话层的仪表盘，考虑直接用规则引擎加 BI：它以更低的成本交付同样的保证。

## 何时这是错误的选择

这一模式很重：一个规则引擎、一个有界的工具面，以及一张完整性回执。这套机器只在正确的问题上值回其成本，把它照搬到错误的问题上只增加成本而不增加信任。在三种情况下避免这一模式。

- **规则其实不是确定性的。** 当合规是一个干净的比较时——如费用小于等于一个上限，或通知大于等于一个要求的天数——这一模式才奏效。当一个裁定是真正的判断时——如一个条款是否显失公平、或一项披露是否充分——把它强塞进这一模式会把主观性藏进规则编写之中，并让结果在本不精确时看起来精确。对那些裁定保留一个人在环，而不是把它们装扮成确定性的。
- **完整性对那个问题无关紧要。** 如果用户只想要几个代表性的例子，或在探索而非裁定，那么完整性回执就是一项为他们并不需要的保证而付出的开销。对那一类问题，RAG 是更简单、正确的答案。
- **总体本身是模糊的。** 回执证明你覆盖了总体中的每一条记录，而非证明总体是正确的那个。如果“所有德州租约”的定义本身可被质疑，那么那份保证对错误的分母是精确的。在你依赖回执之前，确保总体能被一个精确、可辩护的谓词描绘出来。

## 结论

在本文中，我们引入了裁定式查询模式，并演示了它如何通过 Amazon Quick 对话式界面交付可证明完整、可辩护的合规答案。该模式把一个有界的 MCP 操作面与一个确定性规则引擎配对，因此模型翻译问题并叙述结果，却不触碰产出那份保证的决定。

通过部署示例栈、在 Amazon Quick 聊天中问一个合规问题，并跟随结果穿过 Amazon Quick Sight 仪表盘，你端到端演练了完整模式。完整性回执说明每一条记录，发现带它们的完整证据链，而分离界面的交付让那份保证在改述中保持完好。

要开始上手，克隆[示例仓库](https://github.com/aws-samples/sample-quick-adjudicated-query)、部署栈、在 Amazon Quick 中注册 MCP 集成，并试着问你的第一个合规问题。
