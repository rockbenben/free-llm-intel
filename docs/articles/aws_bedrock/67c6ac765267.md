借助 [Amazon SageMaker HyperPod](https://aws.amazon.com/sagemaker/ai/hyperpod/) 和 [Qumulo](https://qumulo.com/product/aws)，你可以把一个 AWS 区域用于训练计算，而把数据集放在另一个区域。训练大型 AI 模型需要海量 GPU 容量，但你理想的计算资源和训练数据并不总在同一个 AWS 区域。跨区域访问数据会增加网络延迟和传输成本。团队面临一个选择：要么把 PB 级的数据跨区域复制，要么在每次读取上承受跨区域延迟并接受更慢的训练。这一组合能帮助解决这一权衡，让团队在不移动数据、不牺牲吞吐的前提下保持前沿模型的最新。

在本文中，我们提出这一挑战的一个方案，解释架构，并分享一次跨区域训练运行的验证结果。通过把 Amazon SageMaker HyperPod 与 [Cloud Native Qumulo (CNQ)](https://qumulo.com/product/aws) 以及 Qumulo 的 [Cloud Data Fabric (CDF)](https://qumulo.com/product/cloud-data-fabric/) 配对，训练作业可以读取存放在另一个 AWS 区域或本地部署的数据集，而不复制数据、不改代码、不牺牲吞吐。我们通过在两个集群上各自运行同一训练作业来验证这一方法。hub 集群运行在美国东部（俄亥俄）区域（us-east-2），与数据同处一地。spoke 集群运行在美国西部（俄勒冈）区域（us-west-2），经 CDF 以 60 毫秒网络延迟远程读取数据。然后我们比较它们的吞吐。在一段简短的预热后，spoke 集群追平了 hub 的性能。

把 Amazon SageMaker HyperPod 与 CNQ 配对交付两项可测量的成果：

- **单区域训练性能：** CNQ 的云端原生架构允许它独立于其数据存储大小来伸缩性能。这带来满打满算 99% 的 GPU 利用率和 p5.48xlarge 网络饱和，数据操作延迟低于 3 毫秒。
- **远程集群以最优利用率训练：** 一个运行在其数据所在区域之外不同区域的 HyperPod 集群，达到与一个和数据同处一地的集群相同的吞吐（115–117 样本/秒），无需额外的数据编排。吞吐在前 100–150 个批次内收敛，而这一次性的预热在规模下可忽略不计：在 10,000+ 批次下不足挂钟时间的 1%，在超过 100,000 下不足 0.1%。这最终使得在训练初始阶段的 100–150 个批次达到 80–90% 的 GPU 利用率，然后收敛到 98–100% 的 GPU 利用率。

## 方案概览

Amazon SageMaker HyperPod 提供托管的训练基础设施，包括带自动健康检查、节点替换和 checkpoint 恢复的弹性集群。该方案把 SageMaker HyperPod 与 Qumulo 的存储层配对。我们用以下组件验证了该方案：

- **单一事实来源**：用 Cloud Native Qumulo (CNQ) 在一个 AWS 区域存储你的训练数据集。
- **跨区域访问**：每个 HyperPod 集群通过 NFS（Network File System）挂载其本地 CNQ 实例。CNQ spoke 集群通过 [Virtual Private Cloud (VPC)](https://aws.amazon.com/vpc/) 对等连接从 hub 集群取回数据，使整个数据集可用，而计算节点无需跨区域访问。
- **智能数据放置**：Qumulo 的 Cloud Data Fabric (CDF) 通过 [NeuralCache](https://qumulo.com/product/neural-cache/) 使用预测性缓存。它学习你的数据加载器访问模式，并从本地 Non-Volatile Memory Express (NVMe) 服务数据，使跨区域延迟在一段初始预热期之后变得透明。

图 1 展示经验证的架构。在 spoke 区域，机器学习开发者通过一个 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/) 编排器提交作业，它在 HyperPod 集群计算节点上运行它们。那些节点通过 NFS 挂载一个本地 CNQ spoke。第二区域的 CNQ hub 持有训练数据的唯一一份副本，而 CDF 通过 VPC 对等连接把那份数据集投射到 spoke，因此两个区域的计算节点都从同一个本地挂载路径读取。

图 1：SageMaker HyperPod 配 Qumulo 上的跨区域数据

### 关于 Qumulo Cloud Data Fabric

CDF 让 *hub* Cloud Native Qumulo (CNQ) 上的一份数据集对多个 *spoke* CNQ 实例即时可见、可访问。即便在超过 100 毫秒延迟的网络链路上也成立。主要组件是 Qumulo 的 NeuralCache，它用一个 AI 模型预测作业接下来需要的 4 KB 块并在 spoke 上预先缓存它们。结合 CNQ 的弹性性能，在这套经验证的配置中，该数据集对 spoke 集群表现得像本地存储，而没有完整数据复制的成本。

我们在每个集群上各自运行同一训练作业（10.2 亿参数的 LLaMA v3，每个 Amazon SageMaker HyperPod 集群两个 ml.p5.48xlarge 实例，共 16 块 H100 GPU）。下表比较性能：

| **配置** | **训练速度** | **到 999 批次的时间** | **NeuralCache 状态** |
| --- | --- | --- | --- |
| Hub（us-east-2 到 us-east-2） | 116–117 样本/秒 | **18.5 分钟** | N/A（本地） |
| Spoke，热缓存（us-east-2 到 us-west-2） | 115–116 样本/秒 | **18.5 分钟** | 已收敛 |
| Spoke，冷启动（us-east-2 到 us-west-2） | 95–115，然后 116 样本/秒 | 约 19–20 分钟* | 预热中，然后已收敛 |

** 无任何先前运行的最坏情况。批次 0–150 在 NeuralCache 预热期间慢 15–20%，然后在第一个 epoch 内收敛到 hub 级性能。*

## 理解架构

下面各节介绍经验证的架构，其中 Qumulo 与 HyperPod 集群在同一区域配置为 hub，同时也作为 spoke。

### Cloud Data Fabric 与 NeuralCache 如何工作

Cloud Data Fabric (CDF) 在 hub 集群上保持你数据集的单一权威副本，并把它作为统一的可移植操作系统接口（POSIX）命名空间投射到 spoke 集群。当创建一个 spoke 时，CDF 把文件系统元数据复制到它，于是完整命名空间在几秒内即可浏览——在文件数据移动之前。当 spoke 挂载文件系统时，CDF 从最近的合法源为每次读取提供服务：命中时是本地 NVMe 缓存，未命中时是 hub。CDF 还使用先进的拥塞控制，它按测量到的瓶颈带宽和往返传播时间来调节节奏，而非在丢包时退避。这正是让一条长距离链路在基于丢包的算法崩溃之处仍然满载的原因。CDF 在往返时间（RTT）高达 900 毫秒的路径上维持接近线速的吞吐。

NeuralCache 是 CDF 内部的预测性缓存层。它观察训练数据加载器发出的顺序 4 KB 块读取并学习访问模式。然后在作业发出请求之前预测性地放置数据。在前 100–150 个批次内，模型学会预测接下来哪些块会被请求，并从 hub 预取到 spoke 上的本地 NVMe 存储。一旦预热好，94–96% 的读取以低于 5 毫秒的延迟从本地缓存服务。这为应用带来更低延迟的操作。

### Hub 配置

数据和计算共享同一区域。Qumulo 交付 1.0–1.3 GBps 的持续读吞吐（饱和 10 Gbps 网络链路），最大读延迟 2–3 毫秒，让 GPU 在整个训练中保持满载。把数据和计算同处一地很重要，因为每次数据加载器读取只在区域内传输，因此关键路径上没有广域网跳。CNQ 能维持这些数字，是因为其云端原生架构按集群大小（而非数据集大小）来伸缩吞吐。这就是为什么一个 4 节点集群能喂饱 GPU 的网络链路。图 2 展示这一单区域布局，其中 HyperPod 集群、Amazon EKS 编排器，以及存储数据集的 CNQ hub 全在一个区域。

图 2：SageMaker HyperPod 配 Qumulo 上的单区域数据

### Spoke 配置（冷启动）

你的 Amazon SageMaker HyperPod 集群运行在数据来源地之外的不同区域。它挂载本地 Qumulo spoke，由它负责从 hub 取数据。NeuralCache 实时观察你的数据加载器访问模式并开始本地缓存数据。在最初的 100–150 个批次期间，跨区域延迟可见，训练以每秒 95–105 样本运行。然后性能收敛到 hub 等价水平（每秒 115–117 样本）并贯穿余下的运行。图 3 展示这一跨区域布局。HyperPod 集群和一个 CNQ spoke 运行在一个区域，持有数据集的 CNQ hub 运行在第二个区域，由 CDF 通过 VPC 对等连接相连。

图 3：SageMaker HyperPod 配 Qumulo 上的跨区域数据（冷启动，最坏情况）

### Spoke 配置（热缓存）

后续运行受益于一个完全预热的 NeuralCache。在 94–96% 的缓存命中率下，数据从本地 NVMe 以低于 5 毫秒延迟服务，交付即时的 hub 等价性能，GPU 利用率高于 99%。

## 演练

本演练提供一个配置并运行这些相同测试的逐步流程。

### 前提条件

要搭建一个有代表性的环境，你需要以下前提条件：

- 一个启用了 Amazon SageMaker HyperPod 的 AWS 账户。
- 在你的主区域（us-east-2，俄亥俄）部署 Qumulo Cloud Native。
- 用于 ml.p5.48xlarge 实例（每集群两个）的足够配额。
- 在 hub 和 spoke 区域之间配置 VPC 对等连接。
- 熟悉 PyTorch 和分布式训练概念。

### 步骤 1：在你的 hub 区域部署 Qumulo Cloud Native

从 [AWS Marketplace](https://aws.amazon.com/marketplace/) 在 us-east-2 部署 Qumulo Cloud Native。在承载你部署文件的 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 桶中，找到 [AWS CloudFormation](https://aws.amazon.com/cloudformation/) 模板 templates/cnq-standard.`template.yaml` 并复制其对象 URL。从那个 URL 创建栈，然后在你现有的 VPC 中选择 r5.8xlarge 实例和一个 4 节点集群。

### 步骤 2：配置区域之间的 VPC 对等连接

在你的 hub（us-east-2）和 spoke（us-west-2）VPC 之间创建一个 VPC 对等连接。然后在配对区域接受该连接，并更新两个区域的路由表，使每个 VPC 的 CIDR 范围路由到对等连接。这让 spoke 区域的 Qumulo 实例有一条到 hub 区域 Qumulo 实例的路径。现在，spoke 区域（us-west-2）的 Amazon SageMaker HyperPod 实例通过它们的本地 NFS 挂载访问 hub 区域（us-east-2）的数据。这是因为两个 Qumulo 集群通过一条私有、低延迟路径相连。

AWS 区域之间的 VPC 对等流量在传输中加密。在 Qumulo 和 HyperPod 实例上配置安全组，只允许两个 VPC 之间所需的 NFS 端口（TCP 2049）。

**注意：** 用你自己的资源标识符替换占位值（显示在尖括号中）。

```
aws ec2 create-vpc-peering-connection \
    --vpc-id <hub-vpc-id> \
    --peer-vpc-id <spoke-vpc-id> \
    --peer-region us-west-2 \
    --region us-east-2
```

从 spoke 区域接受对等连接。然后更新两个区域的路由表，使每个 VPC 的 CIDR 块经对等连接路由：

```
# Accept the peering connection in the spoke Region (us-west-2)
aws ec2 accept-vpc-peering-connection \
    --vpc-peering-connection-id <peering-connection-id> \
    --region us-west-2

# Add a route in the hub route table (us-east-2) pointing to the spoke CIDR
aws ec2 create-route \
    --route-table-id <hub-route-table-id> \
    --destination-cidr-block <spoke-vpc-cidr> \
    --vpc-peering-connection-id <peering-connection-id> \
    --region us-east-2

# Add the reciprocal route in the spoke route table (us-west-2)
aws ec2 create-route \
    --route-table-id <spoke-route-table-id> \
    --destination-cidr-block <hub-vpc-cidr> \
    --vpc-peering-connection-id <peering-connection-id> \
    --region us-west-2

# Verify the peering connection is active
aws ec2 describe-vpc-peering-connections \
    --vpc-peering-connection-ids <peering-connection-id> \
    --query "VpcPeeringConnections[0].Status.Code" \
    --region us-east-2
# Expected output: "active"
```

### 步骤 3：上传你的训练数据集到 Qumulo

通过 NFS 挂载 Qumulo 并同步你预先 token 化的数据集。我们用了 [C4 数据集](https://huggingface.co/datasets/allenai/c4)，为 LLaMA 做了 token 化（4,840 万个序列打包成 4,096 token 窗口）。Qumulo 呈现一个统一的 POSIX 命名空间，因此 hub 和 spoke 实例使用同一挂载路径。

```
sudo mount -t nfs4 -o rw,hard,nointr,proto=tcp <qumulo-ip>:/ /mnt/qumulo
aws s3 sync s3://<your-bucket-name>/c4-tokenized/ /mnt/qumulo/data/c4/
```

### 步骤 4：创建你的 HyperPod 集群

在两个区域用 ml.p5.48xlarge 实例创建 Amazon SageMaker HyperPod 集群。HyperPod 管理底层基础设施（健康监控、自动节点替换和基于 checkpoint 的恢复），因此你的训练运行无需人工干预就能挺过硬件故障。配置一个在启动时挂载 Qumulo 的生命周期脚本。spoke 集群使用同样的生命周期脚本，并通过 NFS 挂载本地 Qumulo spoke 实例。Qumulo spoke 通过 VPC 对等连接透明地从 hub 取回数据。

```
aws sagemaker create-cluster \
    --cli-input-json file://hub-cluster-config.json \
    --region us-east-2

aws sagemaker create-cluster \
    --cli-input-json file://spoke-cluster-config.json \
    --region us-west-2
```

每个集群由一个 CreateCluster 请求文件定义。下面这个 `hub-cluster-config.json` 创建一个附加到你 Amazon EKS 控制平面的两节点 ml.p5.48xlarge 实例组，开启自动节点恢复，并带一个在启动时挂载 Qumulo 的生命周期脚本：

```
{
    "ClusterName": "hyperpod-hub-us-east-2",
    "InstanceGroups": [
        {
            "InstanceGroupName": "training",
            "InstanceType": "ml.p5.48xlarge",
            "InstanceCount": 2,
            "LifeCycleConfig": {
                "SourceS3Uri": "s3://sagemaker-<your-bucket-name>/lifecycle-scripts/",
                "OnCreate": "on_create.sh"
            },
            "ExecutionRole": "arn:aws:iam::<account-id>:role/<hyperpod-execution-role>",
            "ThreadsPerCore": 1,
            "OnStartDeepHealthChecks": ["InstanceStress", "InstanceConnectivity"]
        }
    ],
    "VpcConfig": {
        "SecurityGroupIds": ["<hub-security-group-id>"],
        "Subnets": ["<hub-private-subnet-id>"]
    },
    "Orchestrator": {
        "Eks": {
            "ClusterArn": "arn:aws:eks:us-east-2:<account-id>:cluster/<hub-eks-cluster-name>"
        }
    },
    "NodeRecovery": "Automatic"
}
```

用相同的结构创建 `spoke-cluster-config.json`，把 ClusterName、Amazon EKS 集群 ARN 中的区域，以及 VpcConfig 值改为 spoke 区域的资源。每个 HyperPod 集群必须位于与其 Amazon EKS 控制平面相同的 VPC 中，且子网必须是私有的。

### 步骤 5：配置容器存储接口（CSI）驱动以挂载 Qumulo

用你偏好的安装方法安装 Qumulo CSI 驱动。本例用 Helm：

```
helm repo add qumulo https://qumulo.github.io/qumulo-csi-driver
helm repo update
helm install qumulo-csi qumulo/qumulo-csi-driver --namespace kube-system
```

在继续挂载前，验证 CSI 驱动 pod 正在运行：

```
kubectl get pods -n kube-system -l app=qumulo-csi

# All pods should report STATUS=Running. If any pod shows Pending or CrashLoopBackOff, run to inspect the events:
kubectl describe pod <pod-name> -n kube-system
```

用如下 YAML 创建一个 Static Persistent Volume：ReadWriteMany 的 accessModes 值让每台训练节点同时挂载同一个卷，这正是让 hub 和 spoke 集群共享一个数据集的关键。server 属性指向每个区域的本地 Qumulo 实例。同一份清单在 hub 和 spoke 集群都能工作，只需把那个值改为本地 Qumulo 地址。

```
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-qumulo-static
spec:
  capacity:
    storage: 50Ti
  accessModes:
    - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  storageClassName: ""
  mountOptions:
    - vers=3
    - proto=tcp
    - nolock
  csi:
    driver: nfs.csi.k8s.io
    # Unique ID for this directory/volume; use a stable path-based handle
    volumeHandle: qumulo-nfs-root
    volumeAttributes:
      server: <qumulo-spoke-address>
      share: "/"
      #storeExportPath: "/csi"
      #storeRealPath: "/data"
    # If your driver requires secrets for node stage/publish, uncomment:
    nodeStageSecretRef:
      name: cluster1-login
      namespace: kube-system
```

最后，创建 Persistent Volume Claim：

```
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-qumulo-static
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 50Ti
  storageClassName: ""
  volumeName: pv-qumulo-static
```

### 步骤 6：在你的 Amazon SageMaker HyperPod 集群上运行训练

用 kubectl 配下面这个 YAML 部署一个 Test Pod：

```
apiVersion: v1
kind: Pod
metadata:
  name: qumulo-test
spec:
  containers:
    - name: app
      image: busybox
      command: ["sleep", "3600"]
      volumeMounts:
        - mountPath: /csi
          name: storage
  volumes:
    - name: storage
      persistentVolumeClaim:
        claimName: pvc-qumulo-static
```

用 PyTorch torchrun 启动分布式训练，把数据集和 checkpoint 路径指向 Qumulo 挂载。hub 和 spoke 运行之间无需改动代码。下面这个 `job.yaml` 把这次运行定义为一个 Kubeflow PyTorchJob，每个 ml.p5.48xlarge 实例一个 worker。它把 Qumulo PersistentVolumeClaim 挂载到 /csi，并把该挂载上的数据集和 checkpoint 路径传给训练脚本：

```
apiVersion: kubeflow.org/v1
kind: PyTorchJob
metadata:
  name: llama-fsdp
spec:
  pytorchReplicaSpecs:
    Worker:
      replicas: 2
      restartPolicy: OnFailure
      template:
        spec:
          containers:
            - name: pytorch
              image: <account-id>.dkr.ecr.us-east-2.amazonaws.com/<training-image>:latest
              resources:
                limits:
                  nvidia.com/gpu: 8
                  vpc.amazonaws.com/efa: 32
              command:
                - torchrun
                - --nproc_per_node=8
                - --nnodes=2
                - /workspace/train_fsdp.py
                - --dataset-path=/csi/data/c4
                - --checkpoint-path=/csi/checkpoints/llama-fsdp
                - --batch-size=24
                - --seq-length=4096
                - --num-workers=64
                - --prefetch-factor=4
              volumeMounts:
                - mountPath: /csi
                  name: storage
          volumes:
            - name: storage
              persistentVolumeClaim:
                claimName: pvc-qumulo-static
```

把清单应用到集群：

```
kubectl apply -f job.yaml
```

配置 64 个数据加载器 worker 配 prefetch_factor=4，保持 256 个批次在途。这在缓存预热期间掩盖延迟，而 Fully Sharded Data Parallel (FSDP) 把梯度同步与 I/O 重叠。

## 性能结果

相关测试的性能结果在下面各节展示，说明每次测试运行的每秒 I/O 操作（IOPS）、吞吐和延迟。所有测试用 PyTorch 2.1 FSDP、每 GPU 批大小 24，以及 4,096 token 序列长度。

### Hub 配置

hub 在整个训练中交付一致的性能：1.0–1.3 GBps 持续读吞吐、2–3 毫秒读延迟，以及 98–100% 的 GPU 利用率。这些数字是 spoke 配置所对照测量的基线，因为 hub 的数据路径上没有广域网。Qumulo 仪表盘（图 4）在整个训练运行上显示稳定的 IOPS 曲线，其中的周期性尖峰对应 checkpoint 写入而非读停顿。该仪表盘在同一窗口上堆叠三个时间序列：IOPS、吞吐和延迟。吞吐在整个运行期间保持略高于 1.0 GBps 的平稳带，而延迟轨迹在其旁边保持平稳。

图 4：Qumulo 仪表盘，显示 hub 训练（us-east-2）的持续 IOPS 和吞吐

### Spoke 配置冷启动（最坏情况）

NeuralCache 从第 0 批开始学习。当它观察数据加载器时，识别出 FSDP 训练产生的顺序访问模式，并在作业请求之前开始预取接下来的块，从而最小化数据操作延迟。缓存命中率稳步攀升。它在预取器可靠地领先于数据加载器之后稳定下来。收敛落在约第 100–150 批而非一个固定点，因为它取决于访问模式多快变得可预测。这两个阶段阐明了这一过渡。

- 阶段 1（批次 0–100）：跨区域延迟以超过 60 毫秒占主导，GPU 利用率降到 80–90%，吞吐以 500–800 MBps 运行。
- 阶段 2（批次 100–150）：缓存命中率稳定，延迟降到 5–10 毫秒，训练速度升到约每秒 115 样本和 98–100% 的 GPU 利用率。

图 5 在 Qumulo 仪表盘上展示同一过渡。IOPS 和吞吐在预热窗口内向上攀升，同时读延迟下降，而三条轨迹在 NeuralCache 收敛后都变平。

图 5：Qumulo 仪表盘，显示 spoke 冷启动（us-west-2 到 us-east-2）的 NeuralCache 收敛

在生产规模下，这一一次性惩罚对于地理分布式训练迅速减弱：

| **训练规模** | **总批次** | **挂钟时间** | **冷启动影响** |
| --- | --- | --- | --- |
| 开发运行 | 10,000 | 约 3 小时 | 0.81% |
| 生产训练* | 100,000 | 约 31 小时 | 0.08% |
| 大规模预训练* | 1,000,000 | 约 13 天 | 0.008% |

## 清理资源

本演练在两个区域配置了在你移除之前会持续产生费用的基础设施。完成时，大致按创建的反向顺序拆掉资源，以便干净地释放依赖。

- 删除 PersistentVolumeClaim 和 PersistentVolume，然后卸载 Qumulo CSI 驱动（helm uninstall qumulo-csi -n kube-system）。
- 删除两个 Amazon SageMaker HyperPod 集群（aws sagemaker delete-cluster），分别在 us-east-2 和 us-west-2。完整流程参见[删除一个 SageMaker HyperPod 集群](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-operate-cli-command-delete-cluster.html)。
- 删除 VPC 对等连接并移除你在两个区域路由表中添加的路由。完整流程参见[删除一个 VPC 对等连接](https://docs.aws.amazon.com/vpc/latest/peering/delete-vpc-peering-connection.html)。
- 删除 Qumulo Cloud Native 部署，方式是移除其 AWS CloudFormation 栈，它也会释放底层实例和存储。在删除栈之前，确认你想保留的任何数据都已从集群复制出去。CNQ 存储卷随栈一起删除且不可恢复。要删除，打开 AWS CloudFormation 控制台，选择你在 us-east-2 为 Qumulo 创建的栈，并选择 **Delete**，如[从 CloudFormation 控制台删除一个栈](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cfn-console-delete-stack.html)所述。或者运行 `aws cloudformation delete-stack --stack-name <qumulo-stack-name> --region us-east-2`。

## 结论

通过把 [CNQ](https://qumulo.com/product/cloud-native-qumulo) 和 [CDF](https://qumulo.com/product/cloud-data-fabric/) 与 [Amazon SageMaker HyperPod](https://aws.amazon.com/sagemaker/ai/hyperpod/) 配对，你可以从一个单一数据集运行地理分布式训练而无需数据复制。我们的验证确认：你数据的一份单一副本、无复制开销，在一段简短预热后就能交付接近本地的延迟和 hub 等价的吞吐。要完全避免冷启动，在训练开始前通过在你的训练作业编排脚本中用 [Ray](https://www.ray.io/)、[Amazon EKS](https://aws.amazon.com/eks/)、[Slurm](https://slurm.schedmd.com/overview.html) 或其他工具，对数据集经 Qumulo API 发出一个预发热请求，提前预热 spoke。

要扩展这一架构，考虑从三个或更多区域访问单一数据集的多 spoke 部署、用 [AWS Direct Connect](https://aws.amazon.com/directconnect/) 处理本地部署数据的混合配置，或用生命周期策略把 checkpoint 归档到 [Amazon S3 Glacier](https://aws.amazon.com/s3/storage-classes/glacier/) 存储类别。

要开始上手，参见 Amazon SageMaker AI 开发者指南中的[用 Amazon EKS 编排 SageMaker HyperPod 集群](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks.html)。关于像本演练中那样配置集群的 AWS CloudFormation 模板、Terraform 模块和生命周期脚本，参见 awsome-distributed-ai GitHub 仓库中的 [SageMaker HyperPod EKS 参考架构](https://github.com/awslabs/awsome-distributed-ai/tree/main/architectures/sagemaker-hyperpod-eks)。

要了解更多关于 Cloud Native Qumulo 的内容，阅读 [Building a Cloud Native File System with Cloud Native Qumulo and Amazon S3](https://aws.amazon.com/blogs/apn/building-a-cloud-native-file-system-with-cloud-native-qumulo-and-amazon-s3/)。
