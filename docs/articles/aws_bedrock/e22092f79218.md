# 使用 Okta Cross App Access 与 Amazon Bedrock AgentCore 治理 AI agent 访问（第 2 部分）

在[第 1 部分](https://aws.amazon.com/blogs/machine-learning/govern-ai-agent-access-with-okta-cross-app-access-and-amazon-bedrock-agentcore-part-1/)中，您在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)（一个无论使用何种框架或模型，都能大规模构建、连接并优化 agent 的平台）上构建了一个任务 agent。该 agent 运行在 Amazon Bedrock AgentCore runtime（Amazon Bedrock AgentCore 的一项功能）上，并通过 Okta Cross App Access (XAA) 代表已登录用户执行操作。Okta 决定了哪个 agent 可以代表哪个用户执行操作，而 Amazon Bedrock AgentCore Identity（Amazon Bedrock AgentCore 的一项功能）则在 agent 内部兑换了 Okta 的授权。这验证了治理机制的可行性，但它运行在一个特意简化的拓扑结构上：一个 agent、两个 Model Context Protocol (MCP) server，且授权检查直接写在每个服务器的代码中。

这种机制可以扩展，但该拓扑结构无法扩展。对于一个 agent 和两个工具而言完全行得通的三件事，在拥有数百个 agent 和数千个工具的企业环境中便会演变成棘手的瓶颈：

| **第 1 部分的做法** | **为何无法扩展** | **第 2 部分的改进做法** |
| --- | --- | --- |
| agent 持有每个 MCP server 的 runtime ARN 并直接调用它 | N 个 agent 对接 M 个服务器构成了复杂的连线矩阵，每增加一个新工具都需要改动需要该工具的所有 agent | agent 统一访问一个 Gateway 端点，由 Gateway 维护目标注册表 |
| agent 的角色持有 token-exchange 权限并读取提供商的密钥 | 每个代表用户执行操作的 agent 都会获得通往其可能访问的每个资源的凭据路径 | 由 Gateway 统一兑换授权，agent 的角色不持有任何 token-exchange 或密钥权限 |
| 每个 MCP server 都在各自代码中包含相同的 `groups` 检查 | 相同的规则复制到数千个服务器中容易发生漂移，且无法在一个集中位置进行审计或修改 | 采用一套默认拒绝的 Cedar 策略，在工具运行前由 Gateway 进行评估 |

在本文中，您将对第 1 部分的方案进行上述架构改造。Amazon Bedrock AgentCore Gateway（Amazon Bedrock AgentCore 的一项功能）成为统一的入口门户，并针对每个目标资源兑换 Okta 的授权。Amazon Bedrock AgentCore 中的策略引擎（Policy in Amazon Bedrock AgentCore）评估 Cedar 策略，将每个工具与 agent 以及 Okta 委托的 scope 绑定。运行在 Amazon Elastic Kubernetes Service (Amazon EKS) 上的第二个 agent 以其独立的 Okta 身份加入进来，以证明该入口门户并不关心 agent 运行在何处。此外，Amazon Bedrock AgentCore Observability（Amazon Bedrock AgentCore 的一项功能）结合 Amazon CloudWatch 为您提供了一个统一读取所有决策（包括 Okta 的决策）的集中视图。我们还将针对无法接受 Okta 授权的应用，将 XAA 与按用户的 OAuth 用户许可进行了对比。

## 相比第 1 部分的变化

Okta 配置、AgentCore Identity 凭据提供商以及第 1 部分的 MCP server 均保持不变。图 1 展示了新增组件后的整体架构。

![Part 1 solution extended with AgentCore Gateway, Policy, and Observability, a second agent on Amazon EKS, and the audit path](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/29/ML-21547-p2-1.png)

图 1：结合了 AgentCore Gateway、Policy 和 Observability、Amazon EKS 上的第二个 agent 以及审计链路的第 1 部分增强方案，编号对应下文中的步骤

- 用户登录，服务于前端的后端（BFF）将 ID token 兑换为签发给任务 agent（agent A）的 Identity Assertion JWT Authorization Grant (ID-JAG)，与第 1 部分相同。
- BFF 使用 ID-JAG 在 AgentCore runtime 上调用 agent A。
- agent A 将该 ID-JAG 作为其 MCP 会话的 bearer token 转发给它的 Gateway。Gateway 的入站 authorizer 仅接受 agent A 的 ID-JAG。
- 在 Gateway 调用目标资源之前，AgentCore 中的 Policy 引擎会针对每次工具列表请求和每次工具调用评估 Cedar 策略。
- 对于 Cedar 允许的调用，Gateway 让 AgentCore Identity 通过第 1 部分的凭据提供商在 Okta 的自定义授权服务器处为各个目标资源兑换 ID-JAG。被 Cedar 拒绝的调用则不会触发 ID-JAG 兑换。
- MCP server 检查用户的组和 scope（与第 1 部分相同），并将每项决策记录为 `authz.check` span。
- 每一个调用跳步都会向 AgentCore Observability 发出 OpenTelemetry span，由 CloudWatch Transaction Search 进行收集；Okta 则通过 Amazon EventBridge 将其 System Log 流式传输到 CloudWatch。

报表 agent（agent B）运行在 Amazon EKS 上，并通过其自身的 Gateway 遵循完全相同的路径。

## 创建接受 ID-JAG 的 Gateway

Gateway 的入站 authorizer 工作方式与第 1 部分中的 runtime authorizer 类似。其 issuer 为 Okta 的组织授权服务器，audience 为自定义授权服务器，并通过 `allowedClients` 将其固定到特定 agent：

```
authorizer = {"customJWTAuthorizer": {
    "discoveryUrl": f"{OKTA_ORG}/.well-known/openid-configuration",  # the ID-JAG's issuer
    "allowedAudience": [f"{OKTA_ORG}/oauth2/{CUSTOM_AS_ID}"],         # the resource's authorization server
    "allowedClients": [AGENT_CLIENT_ID],                               # only this agent's ID-JAGs
    "allowedScopes": ["xaa:read", "xaa:write"],
}}
```

图 2：Gateway 仅接受 Okta 为资源的授权服务器签发给该 agent 的 ID-JAG

每个 MCP server 都成为 Gateway 的一个目标，其出站授权通过第 1 部分的凭据提供商使用 `TOKEN_EXCHANGE`，从而由 Gateway 执行第二次兑换：

```
"credentialProviderConfigurations": [{
    "credentialProviderType": "OAUTH",
    "credentialProvider": {"oauthCredentialProvider": {
        "providerArn": provider_arn,          # the JWT_AUTHORIZATION_GRANT provider from Part 1
        "scopes": ["xaa:read", "xaa:write"],  # must equal the ID-JAG's scopes
        "grantType": "TOKEN_EXCHANGE",
    }},
}]
```

![Gateway target for the task manager configured to redeem the ID-JAG through the Part 1 credential provider](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/29/ML-21547-p2-3.png)

图 3：任务管理器目标配置为通过第 1 部分的凭据提供商兑换 ID-JAG

这里有三个关键细节。首先，与第 1 部分一样，目标资源的 scope 必须与 ID-JAG 的 scope 完全一致。其次，为每个目标资源配置静态工具模式（tool schema，将 `listingMode` 设置为 `DEFAULT` 并内嵌 `mcpToolSchema`），这样当您编写 Cedar 策略时，策略中所引用的工具名称是固定确定的。在我们的测试中，显式指定工具名称的策略无法附加到动态列出工具的目标资源上。第三，Gateway 按目标资源对 `tools/list` 进行分页，因此您的客户端必须跟随分页游标，否则后续目标资源的工具将会丢失。AgentCore Identity 会保留来自 Gateway 兑换的 token，因此单个单次有效的 ID-JAG 即可服务于会话内的所有工具调用。在我们的测试中，它还在其 5 分钟的有效期内成功开启了第二个会话。

由于一个凭据提供商只能以单个 Okta agent 身份进行认证，因此请为每个 agent 分配其专属的 Gateway 和提供商。示例 [08-okta-xaa-delegation-chain](https://github.com/awslabs/agentcore-samples/tree/main/01-features/05-authenticate-and-authorize/08-okta-xaa-delegation-chain) 采取了不同的路线，由 Gateway 拦截器自身执行两次兑换。

## 使用 Cedar 将工具与 agent 绑定

以 `ENFORCE` 模式将 AgentCore 中的 Policy 引擎挂载到 Gateway 上，并编写仅包含 permit 的策略。Cedar 将 JWT claim 暴露为标签。读取不存在标签的策略会报错并被跳过。被跳过的 `permit` 策略不会授予任何权限，因此保持默认拒绝；但被跳过的 `forbid` 策略也不会阻止任何操作。请使用 `hasTag` 来防范每个标签的缺失：

```
permit(
  principal is AgentCore::OAuthUser,
  action in [AgentCore::Action::"taskmanager___create_task",
             AgentCore::Action::"taskmanager___update_task_status"],
  resource == AgentCore::Gateway::"<gateway-arn>"
) when {
  principal.hasTag("client_id") && principal.getTag("client_id") == "<agent-client-id>" &&
  principal.hasTag("scope") &&
  (principal.getTag("scope") == "xaa:write" ||
   principal.getTag("scope") like "xaa:write *" ||
   principal.getTag("scope") like "* xaa:write" ||
   principal.getTag("scope") like "* xaa:write *")
};
```

scope 标签保存了 ID-JAG 中以空格分隔的 `scope` claim，因此这四个条件仅将 `xaa:write` 作为独立完整条目进行匹配。诸如 `xaa:write-admin` 之类的 scope 则不会匹配。以相同方式编写的对应策略使用 `xaa:read` 来允许读取类工具。在挂载策略引擎之前，请确保每条策略都处于 `ACTIVE` 状态：如果策略引擎中的策略创建失败，会导致 Gateway 拒绝每一次调用。Cedar 将工具与 agent 及其受托 scope 进行绑定，而 MCP server 仍像第 1 部分一样，根据 `groups` claim 决定每位用户的权限。

## 将 agent 指向 Gateway

agent A 现在将其入站 ID-JAG 转发给 Gateway，而不再自行调用 AgentCore Identity：

```
id_jag = context.request_headers["Authorization"].removeprefix("Bearer ")  # allowlisted header
tools = make_client(GATEWAY_URL, id_jag)  # the Gateway redeems the ID-JAG for each target
```

从 agent 的执行角色中移除第 1 部分的 AgentCore Identity 策略语句。这是对角色的唯一变动，该角色现在不再持有任何 token-exchange 或密钥访问权限，因为 token 兑换权限已由 Gateway 的角色所持有。在 runtime 的 authorizer 上保留 `allowedClients` 配置。

## 在 Amazon EKS 上运行第二个 agent

我们的第二个 agent（报表 agent）在 Amazon EKS 上运行相同的代码，并拥有自己独立的 Okta 注册信息。其资源连接仅允许 `xaa:read`，并且它拥有自己的 Gateway 和凭据提供商。EKS Pod Identity 为 Pod 分配了一个仅能调用模型并写入自身日志与 trace 的 IAM 角色，没有其他多余权限。AWS Distro for OpenTelemetry (ADOT) SDK 负责导出其 trace。[agents-on-eks 示例](https://github.com/awslabs/agentcore-samples/blob/2747451473d1fadbba18f5aee0524e533e3c2b2e/03-integrations/agents-hosted-outside-runtime/agents-on-eks/deploy.sh#L137-L143) 展示了 Pod Identity 的具体设置方式。

在 AgentCore runtime 之外，Pod 前方没有任何 authorizer 保护，因此该 agent 在调用模型前会自行验证 ID-JAG。它会检查签名、issuer、audience、token 类型 `oauth-id-jag+jwt`、过期时间，以及 `client_id` 是否为自身。如果您在 MCP server 中保留了第 1 部分的 agent 检查，请将 agent B 的 client ID 添加到 `REGISTERED_AGENTS` 中。我们在测试中踩过两处设置坑：一是 EKS Auto Mode 通用节点池仅运行 amd64 架构，因此请构建多架构镜像；二是 AgentCore Python SDK（Amazon Bedrock AgentCore 的一项功能）默认绑定到 `localhost`，除非您设置环境变量 `DOCKER_CONTAINER=true`。

## 使用 AgentCore Observability 追踪每项决策

本节中的 span 均来自 [AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html)（图 1 中位于 agent 与 CloudWatch 之间的组件）。在开启 Transaction Search 和 trace 投递后，Runtime、Gateway、Identity 和 Policy 无需任何代码改动即可为每个跳步发出 OpenTelemetry span。您自己的服务可以通过 AWS Distro for OpenTelemetry (ADOT) 添加自定义 span。CloudWatch Transaction Search 负责收集它们，AgentCore 控制台将其读取为 agent trace，而 Amazon CloudWatch Omni 则将相同的 span 读取为 `traces.default`，这使得通过单次查询即可将它们与 Okta 的事件并置展示。

因此，单次工具调用会产生如下链路的 span，每个 span 都标明了做出决策的管控机制：

| **Span** | **发出方** | **记录的内容** |
| --- | --- | --- |
| `AgentCore.Gateway.InboundAuth` | Gateway | 入站 ID-JAG 是否签发给该 agent |
| `AgentCore.Policy.AuthorizeAction` | Policy | 针对该工具的 Cedar 决策 |
| `AgentCore.Identity.GetWorkloadAccessToken` | Identity | 将 agent 的工作负载身份与用户进行绑定 |
| `AgentCore.Identity.GetResourceOauth2Token` | Identity | 在 Okta 处兑换 ID-JAG 以获取带作用域的 access token |
| `AgentCore.Gateway.InvokeTool` | Gateway | 工具调用及其结果 |
| `authz.check` | MCP server (ADOT) | 用户的组、agent、决策结果以及原因 |

Okta 的 System Log 是 AWS 自身无法发出的唯一记录，因此需要将其导入进来。图 4 展示了这两条路径在 Omni 中汇合的架构。

![Audit path where AgentCore spans and Okta’s System Log both reach CloudWatch and one Omni query joins them](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/29/ML-21547-p2-4.png)

图 4：审计链路，其中 span 与 Okta 的 System Log 均汇入 CloudWatch，并通过单个 Omni 查询进行关联

配置步骤如下：

- 开启 CloudWatch Transaction Search，为每个 Gateway 开启 trace 投递（参见此[示例脚本](https://github.com/awslabs/agentcore-samples/blob/2747451473d1fadbba18f5aee0524e533e3c2b2e/02-use-cases/02-workflow-automation-agents/event-driven-claims-agent/scripts/enable_observability.py#L196-L222)），并向 BFF 和 MCP server 中添加 ADOT。任务管理器将每项决策、用户以及 agent 写入 `authz.check` span。
- 在 Okta 中，为 Amazon EventBridge 添加一个 Log Stream。Okta 会将每个事件投递到您账户中的合作伙伴事件总线，并通过一条规则将其写入 CloudWatch Logs 日志组。在我们的测试中，事件在 Okta 发布后约 1 秒钟便到达。每个 ID-JAG 授权事件都将 agent 标为 actor，将用户标为 target，并包含所授予的 scope 和资源连接。
- 在该账户与 AWS 区域中设置一个 Omni 空间，将 Okta 日志组添加到 CloudWatch Dataset 集成中，并在 `authz.check` span 上保存一个视图 `view.xaa_authz_decisions`。

随后，通过单个查询即可将每个 ID-JAG 授权与它引发的各项决策关联起来：

```
SELECT o.okta_time, o.agent, o.user_email, o.granted, a.decision_time, a.decision, a.reason
FROM (SELECT `@timestamp` AS okta_time, detail['actor']['id'] AS agent_id,
             detail['actor']['displayName'] AS agent,
             array_element(regexp_match(`@message`, '"type"\s*:\s*"User"\s*,\s*"alternateId"\s*:\s*"([^"]+)"'), 1) AS user_email,
             detail['debugContext']['debugData']['grantedScopes'] AS granted
      FROM "logs.default"
      WHERE `@timestamp` BETWEEN NOW() - INTERVAL '1' HOUR AND NOW()
        AND detail['eventType'] = 'app.oauth2.token.grant.id_jag') o
JOIN (SELECT `@timestamp` AS decision_time, user_id, agent_client_id, decision, reason
      FROM "view.xaa_authz_decisions"
      WHERE `@timestamp` BETWEEN NOW() - INTERVAL '1' HOUR AND NOW()) a
  ON a.user_id = o.user_email AND a.agent_client_id = o.agent_id
 AND a.decision_time BETWEEN o.okta_time AND o.okta_time + INTERVAL '5' MINUTE
```

对于 Alice 而言，结果显示 Okta 为她授予了任务 agent `xaa:read xaa:write` 权限，随后 16.7 秒后 MCP server 拒绝了她的 `create_task` 请求，并在此后允许了 `list_tasks`，如图 5 所示。

每个请求也是一条完整的 trace，从 BFF 经由 agent、Gateway 的身份与策略检查，直至 MCP server 的决策，如图 6 所示。Omni 将该 trace 标记为 fault，因为 agent 的 `create_task` 调用返回了拒绝结果。

这里有两个重要的插桩细节。ADOT 会通过 `botocore` 查找 Region 并为其导出签名，因此请在缺少 `botocore` 的服务中补齐它。在添加之前，我们的 MCP server 完全没有导出任何 span。此外，ADOT 的 agent 模式默认关闭了对 `requests` 和 `urllib3` 等 HTTP 客户端库的插桩，因此请在您的 BFF 中配置 `OTEL_PYTHON_DISABLED_INSTRUMENTATIONS`，以一个不包含 BFF 所用 HTTP 客户端（在我们的实现中为 `requests`）的列表来覆盖该默认值，否则其 trace 上下文将无法传递给 agent。

| Carol，agent A，Gateway A | 6 | 被 MCP server 拒绝：无 `groups` claim | 允许 |
| Bob，agent B，Gateway B | 4：Cedar 隐藏了写工具 | 被 Gateway 拒绝：“No policy applies to the request (denied by default)” | 允许 |

通过实际部署的 agent 测试，结果完全吻合：agent A 拒绝了 Alice 和 Carol 并成功为 Bob 创建了任务，而 agent B 则告诉 Bob 它没有用于创建任务的工具。同一位用户通过不同的 agent 获得了不同的权限，且完全由 Okta 进行决策。

以下请求在入口处即被拦截：

| **请求** | **响应** |
| --- | --- |
| Gateway A 收到 Agent B 的 ID-JAG，或 Gateway B 收到 Agent A 的 ID-JAG | HTTP 403，MCP 错误 -32002 `insufficient_scope` |
| 使用 Okta access token 代替 ID-JAG | HTTP 403，报相同错误 |
| 无 token | HTTP 401，“Missing Bearer token” |
| 发送给 EKS 上 agent B 的 Agent A ID-JAG | 在模型调用前耗时 98 毫秒被拒绝：“issued to a different agent” |

Gateway 对 agent 错误和 token 类型错误均返回相同的泛型错误，因此当遇到此类错误时，请对照 token 的 `client_id` 和 `aud` 检查您的配置。

相比工具本身的执行耗时，Gateway 在身份和策略方面的开销微乎其微。以下是来自 Omni 中 Gateway A 在 24 小时内的 span 中位数与 90 分位数：

| **Span** | **p50** | **p90** |
| --- | --- | --- |
| `Gateway.InboundAuth` | 34 ms | 69 ms |
| `Identity.Authorize` | 25 ms | 60 ms |
| `Identity.GetWorkloadAccessToken` | 48 ms | 94 ms |
| `Identity.GetResourceOauth2Token` | 70 ms | 439 ms |
| `Policy.AuthorizeAction`（Cedar，每次调用） | 47 ms | 56 ms |
| `Policy.PartiallyAuthorizeActions`（Cedar，每次工具列表） | 65 ms | 75 ms |
| `Gateway.TargetInvocation`（AgentCore runtime 上的 MCP server） | 5,565 ms | 6,273 ms |

单次工具调用中的身份与策略 span 在中位数上合计约 0.2 秒，而 MCP server 自身的 `authz.check` span 耗时不足 1 毫秒。Gateway B 呈现出相同的规律，其中位数上的 `GetResourceOauth2Token` 耗时为 408 毫秒。

## Cross App Access 还是按用户的独立授权许可

XAA 适用于目标应用的授权服务器接受 ID-JAG 的场景。在这种场景下，由您的 Okta 管理员决定哪个 agent 可以代表哪些用户执行操作，用户无需面对任何授权同意弹窗，且 Okta 在每次请求 token 时都会评估策略。而拥有独立授权服务器的应用（例如 GitHub）则依赖于每个用户自身的 OAuth 授权许可。图 7 对比了我们实测的这两种方式。

![Comparison of Cross App Access and per-user OAuth consent, including the revocation behavior measured](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/29/ML-21547-p2-7.png)

图 7：Cross App Access 与按用户 OAuth 授权许可的对比，附带我们实测的撤销行为

我们在现有技术栈旁边部署了 AWS 示例 [07-consent-portal-auth-code-flow-targets](https://github.com/awslabs/agentcore-samples/tree/2747451473d1fadbba18f5aee0524e533e3c2b2e/01-features/05-authenticate-and-authorize/07-consent-portal-auth-code-flow-targets)，其中 Okta 将用户登录到 AgentCore Identity 授权许可门户，并由独立的 Gateway 对接 GitHub 目标资源。Alice 通过该门户连接了 GitHub 测试账号，而 Bob 则从未连接过。[使用 Amazon Bedrock AgentCore 管理 AI agent 的最终用户 OAuth 授权许可](https://aws.amazon.com/blogs/machine-learning/manage-end-user-oauth-consent-for-ai-agents-with-amazon-bedrock-agentcore/)一文对该路径进行了完整介绍。以下是我们的实测观察结果：

| **操作** | **后续 GitHub 工具调用** |
| --- | --- |
| Alice 在门户中完成授权 | 返回她的 GitHub 身份信息 |
| Bob 从未完成授权 | 返回 MCP 错误 -32042 并附带 AgentCore 授权 URL |
| Alice 在 Okta 中被挂起，重用先前的 token | 仍然正常工作：Gateway 仅检查入站 token 的签名与有效期，而该 token 有效期为 1 小时 |
| Alice 被挂起后重新尝试登录 | 被拒绝 |
| Alice 解除挂起 | 恢复工作，无需重新进行授权许可 |
| 通过授权门户 API 断开 Alice 的授权 | 显示未连接，随后再次返回 -32042 |

这两条路径的撤销机制截然不同。在 XAA 中，Okta 的管控直接阻断下一次 ID-JAG 的签发，已签发 token 在约 5 分钟内失效。而在用户授权许可路径中，Okta 仅控制登录认证：已存储的授权凭据在用户被挂起后依然有效，直到我们主动将其断开。请针对每个目标应用具体评估选择，而不是在企业层面做一刀切的决定。

## 本模式适用的场景

在媒体和娱乐行业中，agent 集群的发展非常迅猛。电影制片厂、流媒体平台或游戏组织通常拥有用于制作跟踪、片名与资产元数据、版权与本地化以及观众或玩家支持等领域的众多 agent，每个 agent 都位于不同的系统前端，各自具有独立的授权模型与审计要求。核心问题并不在于单个 agent 是否可以治理，而在于当规模扩展到第一百个 agent 时，能否以相同的方式治理，以及管理员是否依然能够明确回答哪些 agent 可以代表哪些用户访问哪些系统。

这里的机制并不针对特定行业。agent 是您 IdP 中的一种身份实体，目标资源是 OAuth 2.0 授权服务器，Gateway 则是决定授权的枢纽。金融服务、医疗保健以及公共部门团队同样可以将不同的资源置于同一入口门户之后，并获得相同的审计追踪能力。

## 下一步展望：可观测性与评估

本文使用 AgentCore Observability 仅为了一个目的：证明每一次允许和拒绝都能追溯到具体的管控机制。但它的能力远不止于此，其本身也是一个完整的工程体系。各个 span 已经记录了每项治理决策背后的模型和工具延迟，Transaction Search 能够在拒绝量激增时发出告警，AgentCore 评估功能还可以根据您自己的标准为 agent 的行为打分（既可在线针对实时流量进行评估，也可按需针对选定的一组 span 进行评估）。后续文章将深入探讨这一主题：在受控治理的 agent 上应当度量哪些指标、哪些评估器能够捕获工具调用被拒绝却依然汇报成功的 agent，以及如何在不让 trace 变成最大账单的前提下运行这两项能力。

## 总结

在本文中，您将[第 1 部分](https://aws.amazon.com/blogs/machine-learning/govern-ai-agent-access-with-okta-cross-app-access-and-amazon-bedrock-agentcore-part-1/)的方案从适合少量 agent 和工具的拓扑结构，升级为了能够支撑大规模集群的稳健架构。Gateway 成为统一的入口门户并代为兑换 Okta 的授权，从而使各个 agent 无需持有工具凭据。由 AgentCore 中的 Policy 引擎评估的 Cedar 策略，取代了复制代码到各个服务器中的重复检查。运行在 Amazon EKS 上的第二个 agent 以其独立的 Okta 身份加入体系。此外，AgentCore Observability 结合 CloudWatch Omni 中的 Okta System Log，将每一次允许和拒绝都精准追溯到 agent、用户以及做出决定的管控规则。治理机制本身并未发生改变（这正是本方案的精妙之处），改变的只是围绕它构建的拓扑结构。
