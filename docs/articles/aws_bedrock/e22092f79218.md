# 使用 Okta Cross App Access 和 Amazon Bedrock AgentCore 管理 AI 代理访问 – 第 2 部分

在[第 1 部分](https://aws.amazon.com/blogs/machine-learning/govern-ai-agent-access-with-okta-cross-app-access-and-amazon-bedrock-agentcore-part-1/) 中，您在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上构建了一个任务代理，这是一个使用任何框架或模型大规模构建、连接和优化代理的平台。该代理在 Amazon Bedrock AgentCore 运行时（Amazon Bedrock AgentCore 的一项功能）上运行，并通过 Okta 跨应用程序访问 (XAA) 为登录用户提供服务。 Okta 决定哪个代理可以代表哪个用户，而 Amazon Bedrock AgentCore Identity（Amazon Bedrock AgentCore 的一项功能）在代理内部兑换了 Okta 的授权。这证明了治理机制，并且它在一个特意小的拓扑上运行：一个代理、两个模型上下文协议（MCP）服务器以及写入每个服务器的授权检查。

该机制具有规模性。拓扑结构没有。对于一个代理和两种工具来说可以完成的三件事，在拥有数百个代理和数千个工具的企业中却变成了工作：

| **第 1 部分的作用** | **为什么它停止缩放** | **第 2 部分的作用** |
| --- | --- | --- |
|代理保存每个MCP服务器的运行时ARN并直接调用它 | N 个代理针对 M 个服务器是一个接线矩阵，每个新工具都会触及每个需要它的代理 |代理到达一个网关端点，网关保存目标注册表 |
|代理的角色持有令牌交换权限并读取提供者的秘密 |每个代表用户的代理都会获得一条通往它可能到达的每个资源的凭证路径 |网关兑换授权，代理角色不拥有令牌交换或秘密权限 |
|每个 MCP 服务器在其自己的代码中都带有相同的“groups”检查 |同样的规则，复制到数千台服务器中，会发生漂移，并且无法在一个地方进行审核或更改 |一套默认拒绝 Cedar 策略集，在工具运行之前在网关进行评估 |

在本文中，您将对第 1 部分的解决方案进行更改。 Amazon Bedrock AgentCore Gateway 是 Amazon Bedrock AgentCore 的一项功能，它成为单一前门，并为每个目标兑换 Okta 的赠款。 Amazon Bedrock AgentCore 中的策略评估将每个工具绑定到代理和 Okta 委托范围的 Cedar 策略。 Amazon Elastic Kubernetes Service (Amazon EKS) 上的第二个代理以其自己的 Okta 身份加入，以表明前门并不关心代理在哪里运行。 Amazon Bedrock AgentCore 可观察性（Amazon Bedrock AgentCore 的一项功能）与 Amazon CloudWatch 一起为您提供一个位置来阅读每个决策，包括 Okta 的决策。对于无法接受 Okta 授权的应用程序，我们还将 XAA 与每用户 OAuth 同意进行比较。

## 与第 1 部分相比有何变化

第 1 部分中的 Okta 配置、AgentCore Identity 凭据提供程序和 MCP 服务器保持不变。图 1 显示了添加内容的架构。

![使用 AgentCore Gateway、Policy 和 Observability、Amazon EKS 上的第二个代理以及审核路径扩展的第 1 部分解决方案](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/29/ML-21547-p2-1.png)

图 1：第 1 部分解决方案，包含 AgentCore Gateway、策略和可观察性、Amazon EKS 上的第二个代理以及审核路径，编号与后续步骤相匹配

- 用户登录，前端后端 (BFF) 将 ID 令牌交换为颁发给任务代理（代理 A）的身份断言 JWT 授权授予 (ID-JAG)，如第 1 部分中所示。
- BFF 使用 ID-JAG 在 AgentCore 运行时调用代理 A。
- 代理 A 将 ID-JAG 转发到其网关作为其 MCP 会话的承载令牌。网关的入站授权者仅接受代理 A 的 ID-JAG。
- 在网关调用目标之前，AgentCore 中的策略会评估每个工具列表和每个工具调用的 Cedar 策略。
- 对于 Cedar 允许的调用，网关让 AgentCore Identity 通过第 1 部分凭证提供程序在 Okta 的自定义授权服务器上为每个目标兑换 ID-JAG。 Cedar 否认的跟注并不能兑换 ID-JAG。
- MCP 服务器检查用户的组和范围，如第 1 部分中所示，并将每个决定记录为“authz.check”范围。
- 每个跃点都会发出 OpenTelemetry 跨度到 AgentCore Observability，CloudWatch Transaction Search 会收集该数据，Okta 通过 Amazon EventBridge 将其系统日志流式传输到 CloudWatch。

报告代理（代理 B）在 Amazon EKS 上运行，并通过其自己的网关遵循相同的路径。

## 创建一个接受 ID-JAG 的网关

网关的入站授权方的工作方式类似于第 1 部分中的运行时授权方。其颁发者是 Okta 的组织授权服务器，其受众是自定义授权服务器，并且“allowedClients”将其固定到一个代理：
```
authorizer = {"customJWTAuthorizer": {
    "discoveryUrl": f"{OKTA_ORG}/.well-known/openid-configuration",  # the ID-JAG's issuer
    "allowedAudience": [f"{OKTA_ORG}/oauth2/{CUSTOM_AS_ID}"],         # the resource's authorization server
    "allowedClients": [AGENT_CLIENT_ID],                               # only this agent's ID-JAGs
    "allowedScopes": ["xaa:read", "xaa:write"],
}}
```

![网关入站授权方仅接受 Okta 向资源授权服务器代理颁发的 ID-JAG](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/29/ML-21547-p2-2.png)

图 2：网关仅接受 Okta 向资源授权服务器代理颁发的 ID-JAG

每个 MCP 服务器都成为网关目标，其出站授权通过第 1 部分凭证提供程序使用“TOKEN_EXCHANGE”，因此网关执行第二次交换：
```
"credentialProviderConfigurations": [{
    "credentialProviderType": "OAUTH",
    "credentialProvider": {"oauthCredentialProvider": {
        "providerArn": provider_arn,          # the JWT_AUTHORIZATION_GRANT provider from Part 1
        "scopes": ["xaa:read", "xaa:write"],  # must equal the ID-JAG's scopes
        "grantType": "TOKEN_EXCHANGE",
    }},
}]
```

![配置为通过第 1 部分凭证提供程序兑换 ID-JAG 的任务管理器的网关目标](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/29/ML-21547-p2-3.png)

图 3：任务管理器目标通过第 1 部分凭证提供程序兑换 ID-JAG

这里有三个细节很重要。首先，与第 1 部分一样，目标的范围必须等于 ID-JAG 的范围。其次，为每个目标提供一个静态工具架构（使用内联的“mcpToolSchema”将“listingMode”设置为“DEFAULT”），以便在编写 Cedar 策略引用时工具名称是固定的。在我们的测试中，命名工具的策略也无法附加到动态列出的目标。第三，网关按目标分页“工具/列表”，因此您的客户端必须跟随分页光标，否则后面目标中的工具会消失。 AgentCore Identity 保留网关交换中的令牌，因此一个一次性 ID-JAG 可以为会话中的每个工具调用提供服务。在我们的测试中，它还在 5 分钟的生命周期内打开了第二个会话。

由于凭证提供程序作为一个 Okta 代理进行身份验证，因此请为每个代理提供其自己的网关和提供程序。示例 [08-okta-xaa-delegation-chain](https://github.com/awslabs/agentcore-samples/tree/main/01-features/05-authenticate-and-authorize/08-okta-xaa-delegation-chain) 采用不同的路线，其中网关拦截器自行执行两种交换。

## 使用 Cedar 将工具绑定到代理

将 AgentCore 引擎中的策略以“ENFORCE”模式附加到网关，并编写仅允许的策略。 Cedar 将 JWT 声明公开为标签。读取缺失标签错误并被跳过的策略。跳过的“permit”不会授予任何内容，因此默认拒绝保留，但跳过的“forbid”不会阻止任何内容。使用“hasTag”保护每个标签：
```
permit(
  principal is AgentCore::OAuthUser,
  action in [AgentCore::Action::"taskmanager___create_task",
             AgentCore::Action::"taskmanager___update_task_status"],
  resource == AgentCore::Gateway::"<gateway-arn>"
) when {
  principal.hasTag("client_id") && principal.getTag("client_id") == "<agent-client-id>" &&
  principal.hasTag("scope") &&
  (principal.getTag("scope") == "xaa:write" ||
   principal.getTag("scope") like "xaa:write *" ||
   principal.getTag("scope") like "* xaa:write" ||
   principal.getTag("scope") like "* xaa:write *")
};
```
范围标记保存 ID-JAG 的空格分隔的“范围”声明，因此四个条件仅作为整个条目匹配“xaa：write”。诸如“xaa:write-admin”之类的范围不匹配。以相同方式编写的匹配策略允许使用“xaa:read”的读取工具。在附加引擎之前，请检查每个策略是否处于“活动”状态：策略创建失败的引擎会使网关拒绝每个呼叫。 Cedar 将工具绑定到代理及其委托范围，并且 MCP 服务器仍然根据“组”声明来决定每个用户的权限，如第 1 部分中所示。

## 将代理指向网关

代理 A 现在将其入站 ID-JAG 转发到网关，而不是调用 AgentCore Identity 本身：
```
id_jag = context.request_headers["Authorization"].removeprefix("Bearer ")  # allowlisted header
tools = make_client(GATEWAY_URL, id_jag)  # the Gateway redeems the ID-JAG for each target
```
从代理的执行角色中删除第 1 部分 AgentCore Identity 语句。这是对该角色的唯一更改，该角色现在不拥有令牌交换或秘密权限，因为网关的角色拥有交换令牌的权限。将“allowedClients”保留在运行时的授权者上。

## 在 Amazon EKS 上运行第二个代理

我们的第二个代理（报告代理）在具有自己的 Okta 注册的 Amazon EKS 上运行相同的代码。它的资源连接仅允许“xaa:read”，并且它有自己的网关和凭证提供程序。 EKS Pod Identity 为 Pod 提供了 IAM 角色，该角色可以调用模型并写入自己的日志和跟踪，仅此而已。 AWS Distro for OpenTelemetry (ADOT) SDK 导出其跟踪。 [agents-on-eks 示例](https://github.com/awslabs/agentcore-samples/blob/2747451473d1fadbba18f5aee0524e533e3c2b2e/03-integrations/agents-hosted-outside-runtime/agents-on-eks/deploy.sh#L137-L143) 显示 Pod 身份设置。

在 AgentCore 运行时之外，没有授权者位于 pod 前面，因此代理会在模型调用之前验证 ID-JAG。它检查签名、颁发者、受众、令牌类型“oauth-id-jag+jwt”、过期时间，以及“client_id”是否是它自己的。如果您在 MCP 服务器中保留第 1 部分代理检查，请将代理 B 的客户端 ID 添加到“REGISTERED_AGENTS”。有两个设置让我们绊倒了。 EKS Auto 模式通用节点池仅运行 amd64，因此构建多架构映像。 AgentCore Python SDK（Amazon Bedrock AgentCore 的一项功能）会绑定到“localhost”，除非您设置“DOCKER_CONTAINER=true”。

## 使用 AgentCore Observability 跟踪每个决策

本部分中的跨度是 [AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html)，它是图 1 中位于代理和 CloudWatch 之间的组件。在您打开事务搜索和跟踪传递后，运行时、网关、身份和策略会为每个跃点发出 OpenTelemetry 跨度，而无需更改代码。您自己的服务通过 AWS Distro for OpenTelemetry (ADOT) 添加自己的服务。 CloudWatch Transaction Search 收集它们，AgentCore 控制台将它们作为代理跟踪进行读取，Amazon CloudWatch Omni 读取与“traces.default”相同的跨度，这样一个查询就可以将它们放在 Okta 的事件旁边。

因此，一个工具调用会产生这一连串的跨度，每个跨度都命名做出决定的控件：

| **跨度** | **由**发出| **它记录了什么** |
| --- | --- | --- |
| `AgentCore.Gateway.InboundAuth` |网关|入站 ID-JAG 是否已发给该代理 |
| `AgentCore.Policy.AuthorizeAction` |政策 | Cedar 对此工具的决定 |
| `AgentCore.Identity.GetWorkloadAccessToken` |身份 |将代理的工作负载身份与用户绑定 |
| `AgentCore.Identity.GetResourceOauth2Token` |身份 |在 Okta 兑换 ID-JAG 以获得范围访问令牌 |
| `AgentCore.Gateway.InvokeTool` |网关|工具调用及其结果 |
| `authz.check` | MCP 服务器 (ADOT) |用户群体、代理、决策和原因 |

Okta 的系统日志是 AWS 无法发出的一条记录，因此您将其引入。图 4 显示了 Omni 中的两条路径。

![AgentCore 跨越的审核路径和 Okta 的系统日志均到达 CloudWatch，并且一个 Omni 查询将它们加入](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/29/ML-21547-p2-4.png)

图 4：审核路径，其中 span 和 Okta 的系统日志到达 CloudWatch，并且一个 Omni 查询将它们连接起来

设置方法：

- 打开 CloudWatch Transaction Search，打开每个网关的跟踪传送（请参阅此 [示例脚本](https://github.com/awslabs/agentcore-samples/blob/2747451473d1fadbba18f5aee0524e533e3c2b2e/02-use-cases/02-workflow-automation-agents/event-driven-claims-agent/scripts/enable_observability.py#L196-L222))，并将 ADOT 添加到BFF 和 MCP 服务器。任务管理器将每个决策、用户和代理写入“authz.check”范围。
- 在 Okta 中，添加 Amazon EventBridge 的日志流。 Okta 将每个事件传送到您账户中的合作伙伴事件总线，并通过规则将其写入 CloudWatch Logs 日志组。在我们的测试中，事件在 Okta 发布后大约 1 秒到达。每个 ID-JAG 授予事件将代理命名为参与者，将用户命名为目标，以及授予的范围和资源连接。
- 在账户和 AWS 区域中设置 Omni 空间，将 Okta 日志组添加到 CloudWatch 数据集集成，并在“authz.check”跨度上保存视图“view.xaa_authz_decisions”。

然后，一个查询将每个 ID-JAG 授权与其所导致的决策结合起来：
```
SELECT o.okta_time, o.agent, o.user_email, o.granted, a.decision_time, a.decision, a.reason
FROM (SELECT `@timestamp` AS okta_time, detail['actor']['id'] AS agent_id,
             detail['actor']['displayName'] AS agent,
             array_element(regexp_match(`@message`, '"type"\s*:\s*"User"\s*,\s*"alternateId"\s*:\s*"([^"]+)"'), 1) AS user_email,
             detail['debugContext']['debugData']['grantedScopes'] AS granted
      FROM "logs.default"
      WHERE `@timestamp` BETWEEN NOW() - INTERVAL '1' HOUR AND NOW()
        AND detail['eventType'] = 'app.oauth2.token.grant.id_jag') o
JOIN (SELECT `@timestamp` AS decision_time, user_id, agent_client_id, decision, reason
      FROM "view.xaa_authz_decisions"
      WHERE `@timestamp` BETWEEN NOW() - INTERVAL '1' HOUR AND NOW()) a
  ON a.user_id = o.user_email AND a.agent_client_id = o.agent_id
 AND a.decision_time BETWEEN o.okta_time AND o.okta_time + INTERVAL '5' MINUTE
```
对于 Alice，结果显示 Okta 为她授予任务代理“xaa:read xaa:write”，然后 MCP 服务器在 16.7 秒后拒绝她的“create_task”，并在此之后允许“list_tasks”，如图 5 所示。

有两个仪器细节很重要。 ADOT 找到该区域并通过“botocore”签署其导出，因此将“botocore”添加到缺少它的服务中。在此之前，我们的 MCP 服务器没有导出任何跨度。 ADOT 的代理模式默认会关闭 HTTP 客户端库（例如“requests”和“urllib3”）的检测，因此在 BFF 中设置“OTEL_PYTHON_DISABLED_INSTRUMENTATIONS”，以使用排除 BFF 的 HTTP 客户端（在我们的中为“requests”）的列表来覆盖默认设置，否则其跟踪上下文将无法到达代理。

## 验证结果

我们通过第 1 部分中的用户通过两个网关运行每次检查。每个会话都会列出工具，然后调用“list_tasks”、“create_task”和员工查找：

| **调用者和路径** | **列出的工具** | **`创建任务`** | **阅读** |
| --- | --- | --- | --- |
| Alice，代理 A，网关 A | 6 |被 MCP 服务器拒绝：需要 `xaa-writers` |允许 |
| Bob，代理 A，网关 A | 6 |创建 |允许 |
|卡罗尔，特工 A，网关 A | 6 |被 MCP 服务器拒绝：没有“组”声明 |允许 |

| **请求** | **回应** |
| --- | --- |
|代理 B 在网关 A 的 ID-JAG，或代理 A 在网关 B 的 ID-JAG | HTTP 403，MCP 错误 -32002 `insufficient_scope` |
| Okta 访问令牌而不是 ID-JAG | HTTP 403，同样的错误 |
|没有令牌 | HTTP 401，“缺少承载令牌”|
|特工 A 的 ID-JAG 在 EKS 上发送给特工 B |在模型调用之前的 98 毫秒内被拒绝：“发布给不同的代理” |

对于错误的代理和错误的令牌类型，网关会返回相同的一般错误，因此当您看到令牌时，请根据令牌的“client_id”和“aud”检查您的配置。

与工具本身相比，网关的身份和政策工作很小。 Omni 中网关 A 跨度 24 小时的中位数和第 90 个百分位数：

| **跨度** | **第50页** | **第90页** |
| --- | --- | --- |
| `Gateway.InboundAuth` | 34 毫秒 | 69 毫秒 |
| `身份.授权` | 25 毫秒 | 60 毫秒 |
| `Identity.GetWorkloadAccessToken` | 48 毫秒 | 94 毫秒 |
| `Identity.GetResourceOauth2Token` | 70 毫秒 | 439 毫秒 |
| `Policy.AuthorizeAction`（Cedar，每次调用）| 47 毫秒 | 56 毫秒 |
| `Policy.PartiallyAuthorizeActions`（Cedar，每个工具列表）| 65 毫秒 | 75 毫秒 |
| `Gateway.TargetInspiration`（AgentCore 运行时上的 MCP 服务器）| 5,565 毫秒 | 6,273 毫秒 |

一个工具调用的身份和策略跨度的中位数约为 0.2 秒，而 MCP 服务器自己的“authz.check”跨度花费了不到 1 毫秒。网关 B 显示了相同的模式，“GetResourceOauth2Token”的中位数为 408 毫秒。

## 跨应用程序访问或每用户同意

XAA 适用于目标应用程序的授权服务器接受 ID-JAG 的情况。在那里，您的 Okta 管理员决定哪个代理可以为哪些用户执行操作，用户看不到同意提示，并且 Okta 在每次请求令牌时都会评估策略。拥有自己的授权服务器的应用程序（例如 GitHub）则依赖于每个用户自己的 OAuth 同意。图 7 对我们测量的两者进行了比较。

![跨应用程序访问和每用户 OAuth 同意的比较，包括测量的撤销行为](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/29/ML-21547-p2-7.png)

图 7：跨应用程序访问与每用户 OAuth 同意的比较以及我们测量的撤销行为

我们部署了AWS示例[07-consent-portal-auth-code-flow-targets](https://github.com/awslabs/agentcore-samples/tree/2747451473d1fadbba18f5aee0524e533e3c2b2e/01-features/05-authenticate-and-authorize/07-consent-portal-auth-code-flow-targets)在我们的旁边堆栈，Okta 将用户登录到 AgentCore Identity 同意门户和其自己的网关上的 GitHub 目标。 Alice 通过门户连接了一个 GitHub 测试帐户，而 Bob 从未连接过。 [使用 Amazon Bedrock AgentCore 管理 AI 代理的最终用户 OAuth 同意](https://aws.amazon.com/blogs/machine-learning/manage-end-user-oauth-consent-for-ai-agents-with-amazon-bedrock-agentcore/) 文章完整描述了此通道。这是我们观察到的情况：

| **行动** | **下一次 GitHub 工具调用** |
| --- | --- |
|爱丽丝在门户中同意 |归还了她的 GitHub 身份 |
|鲍勃，他从未同意过| AgentCore 授权 URL 出现 MCP 错误 -32042 |
| Alice 在 Okta 中被暂停，之前的代币被重新使用 |仍然有效：网关检查入站令牌的签名和过期时间，并且该令牌存活了 1 小时 |
| Alice 已暂停，新登录 |拒绝 |
|爱丽丝被解除停职 |未经新人同意就工作 |
| Alice 的授权通过同意门户的 API 断开连接 |未连接，则再次-32042 |

两条车道撤销方式不同。在 XAA 中，Okta 的控制措施会停止下一个 ID-JAG 铸币，并且发行的代币会在大约 5 分钟内过期。在同意通道中，Okta 仅控制登录：存储的授权在暂停后仍有效，并一直保留到我们断开连接为止。根据目标应用程序进行选择，而不是为企业一次选择。

## 此模式适用的地方

在媒体和娱乐领域，车队到达速度很快。工作室或流媒体或游戏组织拥有用于制作跟踪、标题和资产元数据、权利和本地化以及观众或玩家支持的代理，每个代理都位于不同的系统前面，具有自己的授权模型和自己的审计员。问题不在于是否可以治理一名代理人。问题在于第一百个是否以同样的方式进行管理，以及管理员是否仍然可以回答哪些代理针对哪些用户访问哪些系统。

这里没有任何特定于该行业的内容。代理是 IdP 中的身份，目标是 OAuth 2.0 授权服务器，网关是决定授权的地方。金融服务、医疗保健和公共部门的团队将不同的资源放在同一个前门后面，并获得相同的审计跟踪。

## 结论

在本文中，您将[第 1 部分](https://aws.amazon.com/blogs/machine-learning/govern-ai-agent-access-with-okta-cross-app-access-and-amazon-bedrock-agentcore-part-1/) 解决方案从适合少数代理和工具的拓扑移至可支持多种代理和工具的拓扑。 Gateway 成为唯一的前门并兑换了 Okta 的赠款，因此代理不持有任何工具凭证。 AgentCore 中的策略评估的 Cedar 策略取代了复制到每个服务器中的检查。 Amazon EKS 上的第二个代理以其自己的 Okta 身份加入。 AgentCore Observability 以及 CloudWatch Omni 中的 Okta 系统日志可以追踪每个允许和拒绝的代理、用户以及做出决定的控制。治理机制没有改变，这就是重点：只有它周围的拓扑发生了变化。
