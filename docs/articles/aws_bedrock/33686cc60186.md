# Stretto 如何用 Amazon Nova 2 Sonic 构建 AI 语音 agent

*本文与 Stretto 的 Danya Gordin 以及 CI&T 的 Marcelo Wzorek 合作撰写。*

在 [Stretto](https://www.stretto.com/) 构建 AI 语音 agent 之前，在其 Bankruptcy.com 网站上考虑申请破产的消费者需要填写一个只有几个字段的网页表单：债务金额、律师状态和联系信息。这些由表单产生的线索利润微薄。

网页表单线索与完全合格的线索之间存在显著差距。破产律师更看重包含详细财务数据的线索：债务、资产、车辆、房地产、就业经历以及此前的申请记录。网页表单本可以扩展以采集这些细节，但表单越长，中途放弃的访客就越多。电话访谈本可以自然地引出这些信息，因为人们在对话中更愿意分享财务敏感细节，但要组建并培训一支人工受理团队来执行这些访谈，成本高得难以承受。

Stretto 看到了一个机会：用 AI 语音 agent 取代网页表单，由它通过电话执行受理访谈。该 agent 会以对话方式引导来电者完成完整的破产问卷，并实时抽取结构化数据。随后，它会依据律师定义的规则对线索进行分类，以支持律师的决策。

挑战在于找到一款语音 AI 解决方案：它能自然地处理敏感的财务对话，具备低延迟、干净的打断处理能力和情绪感知能力，并且成本能让单位经济性成立。

在本文中，我们将介绍 Stretto 如何与 [AWS Generative AI Innovation Center](https://aws.amazon.com/ai/generative-ai/innovation-center/) 以及 [CI&T](https://ciandt.com/)（AWS 合作伙伴）合作，构建 Tara——一个由 [Amazon Nova 2 Sonic](https://docs.aws.amazon.com/nova/latest/nova2-userguide/using-conversational-speech.html) 驱动的 AI 语音 agent，后者是 Amazon Bedrock 中的一款语音到语音模型。Tara 执行多阶段的破产受理访谈，并依据律师定义的规则对线索进行分类。我们将涵盖架构、从验证到生产部署的分阶段构建过程，以及团队如何针对敏感对话测试语音质量。

## 解决方案概览

Tara 是一款通过电话执行破产受理访谈的 AI 语音 agent。当来电者拨打 Bankruptcy.com 的号码时，Tara 会接听、自我介绍，并引导来电者经历一场结构化的对话。她收集个人信息、财务细节、资产清单和就业经历，同时根据来电者的情绪状态调整语气。通话结束时，Stretto 的系统会应用律师定义的规则，将线索归类为合格、不合格或需要更多信息（交由律师审核）。

该解决方案构建在 Amazon Nova 2 Sonic 之上，这是一款可通过 Amazon Bedrock 使用的基础模型（FM），原生支持语音到语音。它在单个模型中处理语音输入并生成语音输出，而不是把语音转文本、语言模型和文本转语音等独立组件串联起来。这种架构旨在降低延迟并让对话听起来更自然，这两点对于破产受理电话的敏感性都至关重要。构建在 Amazon Bedrock 之上，让团队可以通过一个托管服务同时获得 Amazon Nova 2 Sonic 和 Anthropic 的 Claude，无需运行任何模型基础设施。它还为处理敏感财务数据的工作负载引入了 AWS 的安全与治理控制。对这两个模型的访问由 AWS Identity and Access Management（IAM）治理。发往 Amazon Bedrock 的流量通过虚拟私有云（VPC）端点（AWS PrivateLink）保持在 AWS 网络内。Amazon Bedrock 不会使用 prompt 或模型输出来训练模型（详情请参阅 [Amazon Bedrock 中的数据保护](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html)）。由于这些模型与语音桥接层、数据库以及 Amazon CloudWatch 监控运行在同一个 AWS 环境中，团队可以用一套工具来保护和运维整个解决方案。Amazon Nova 2 Sonic 和 Amazon Bedrock 并非在所有 AWS 区域都可用。有关当前的区域可用性，请参阅 [Amazon Bedrock 支持的区域](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

团队选择 Amazon Nova 2 Sonic 而非此前的语音解决方案，原因有三：

- **成本：** Stretto 报告称，与之前的解决方案相比，每分钟语音成本降低了 95%，该结论基于截至 2026 年 4 月 us-east-1 区域的 [Amazon Bedrock 按需定价](https://aws.amazon.com/bedrock/pricing/)。
- **延迟：** 在 Stretto 的测试中，之前的解决方案首音频延迟超过 500 毫秒，造成尴尬的停顿。Amazon Nova 2 Sonic 专为低延迟设计，以支持自然的对话流。
- **打断处理：** 处于压力情境下的来电者需要插话、纠正自己并提出澄清性问题。之前的解决方案对插话（barge-in）处理不佳，常常打断对话流。Amazon Nova 2 Sonic 设计为在不打断会话的情况下处理干扰。

来电者通过 Twilio 联系到 Tara，Twilio 会向 AWS 打开一个 WebSocket 连接。流量经过 AWS WAF 和 Application Load Balancer，到达运行在 AWS Fargate 上 Amazon Elastic Container Service（Amazon ECS）中的语音桥接层，后者与 Amazon Nova 2 Sonic（通过 Amazon Bedrock 访问）流式传输音频。通话结束后，带死信队列的 Amazon Simple Queue Service（Amazon SQS）会把转写文本交给一个异步处理器。该处理器使用 Amazon Bedrock 上 [Anthropic 的 Claude 3 Haiku](https://aws.amazon.com/bedrock/claude/) 抽取结构化字段，这些字段会持久化到 Amazon Aurora Serverless v2 中。合格的线索按司法辖区路由给律师。配套服务包括 NAT 网关、VPC 端点（AWS PrivateLink）、Amazon Elastic Container Registry（Amazon ECR）、AWS Secrets Manager 和 Amazon CloudWatch。

Stretto 之所以选择 Twilio 作为电话网络，是因为 Tara 的受理流程完全自动化，没有人工坐席接听电话；同时也因为 Stretto 希望与 Amazon Nova 2 Sonic 直接集成，并保留其现有的 AWS 后端。Twilio Media Streams 通过 WebSocket 传递来电者的原始音频，这正是语音桥接层所需的输入，而 CI&T 已经将它和 Amazon Nova 2 Sonic 集成过。对于在人工坐席之间路由呼叫的联系中心工作负载，[Amazon Connect](https://aws.amazon.com/connect/) 也支持 Amazon Nova 2 Sonic。

该架构使用以下 AWS 服务：

- [Amazon Nova 2 Sonic](https://docs.aws.amazon.com/nova/latest/nova2-userguide/using-conversational-speech.html)（通过 Amazon Bedrock）：为 Tara 的语音对话提供支持的语音到语音基础模型。它在一次处理中同时完成语音识别和响应生成，并支持在访谈过程中通过工具调用采集结构化数据。
- 运行在 [AWS Fargate](https://aws.amazon.com/fargate/) 上的 [Amazon Elastic Container Service（Amazon ECS）](https://aws.amazon.com/ecs/)：一种无服务器计算引擎，运行连接电话层与 Amazon Nova 2 Sonic 的语音桥接容器。语音桥接任务跨三个可用区持续运行，以实现高可用性。
- [Amazon Aurora Serverless v2](https://aws.amazon.com/rds/aurora/serverless/)：一个兼容 PostgreSQL 的无服务器关系数据库，以多可用区（Multi-AZ）配置部署。它存储来电者档案、受理回答、资格判定结果和会话元数据。Aurora 的无服务器扩缩容能力与波动的通话量模式相匹配。
- Amazon Bedrock（Anthropic 的 Claude 3 Haiku）：负责从对话转写文本中抽取结构化数据。在 Amazon Nova 2 Sonic 生成转写文本后，Claude 3 Haiku 将带类型的字段（姓名、美元金额、地址、车辆详情）抽取到关系型 schema 中。
- 带死信队列的 [Amazon Simple Queue Service（Amazon SQS）](https://aws.amazon.com/sqs/)：管理通话后事件的异步 webhook 处理，并保留失败消息以供重试。
- [AWS WAF](https://aws.amazon.com/waf/)、VPC 端点和 [Application Load Balancer](https://aws.amazon.com/elasticloadbalancing/application-load-balancer/)：安全与网络层，帮助保护 API 端点、跨可用区路由流量，并为 AWS 服务提供私有连接。

## 构建并验证语音 agent

团队采取了分阶段的方法：先验证语音质量，再构建生产集成，然后在系统经真实来电者验证可用之后再扩大问卷范围。

### 为敏感对话验证语音质量

破产相关的对话往往情绪浓重。来电者常常紧张、犹豫或感到难堪。语音 agent 需要听起来有共情且自然，而不是机械或事务性的。在编写任何集成代码之前，团队专门花了一周时间，针对多种来电者场景测试 Amazon Nova 2 Sonic 的语音质量。

验证内容涵盖：

- 不同来电者情绪状态（平静、紧张、犹豫、沮丧）下的语音质量。
- 首次出声延迟（time-to-first-audio）与之前解决方案 500 毫秒以上基线之间的基准对比。
- 插话与打断处理：来电者能否在一句话中间插话而不破坏对话？
- 情绪语调适配：当来电者听起来痛苦时，agent 是否会调整语速和语调？

这一验证步骤产出了一份对比报告，记录了 Amazon Nova 2 Sonic 与之前的解决方案在各个维度上的表现。该报告成为是否进入集成阶段的 go/no-go 关卡。

### 部署到生产环境并面对真实来电者

语音质量得到验证后，团队用三周时间构建了端到端集成。通话流程如下：

- 来电者拨打 Bankruptcy.com 的号码。Twilio 的电话层接听该呼叫，并向运行在 AWS Fargate 上 Amazon ECS 中的语音桥接层打开一个 WebSocket 连接。
- 语音桥接层在来电者与 Amazon Nova 2 Sonic 之间双向流式传输音频。Tara 进行自我介绍、采集同意，然后开始受理访谈。
- 通话结束后，完整转写文本进入一条由 Amazon Bedrock 上 Anthropic 的 Claude 3 Haiku 驱动的抽取流水线。该流水线从对话中抽取字段并存储到 Amazon Aurora。

由律师设计的完整受理流程可能持续 15–20 分钟，长于单个 Amazon Nova 2 Sonic 流式会话的最长时长（当前数值请参阅 [语音到语音入门](https://docs.aws.amazon.com/nova/latest/nova2-userguide/sonic-getting-started.html)）。团队把该会话时长当作一个设计参数，并实现了[会话延续模式](https://docs.aws.amazon.com/nova/latest/userguide/speech-errors.html)，这种模式可以把对话上下文跨越会话边界传递下去。语音桥接层会跟踪与 Amazon Nova 2 Sonic 的每条双向流已经打开多久。在接近上限前不久，它会用相同的 system prompt 和工具配置打开一条新流，并把此前的对话作为文本历史发送过去。当 Tara 完成当前回复后，桥接层将来电者的音频切换到新流并关闭旧流，因此对话对来电者而言能够平滑延续。

首次部署覆盖了现有的 13 字段受理表单，采集与网页表单相同的数据点，但通过自然对话进行。这为团队提供了一个生产基线，可以在扩大范围之前据此衡量效果。

### 扩展受理范围与线索资格判定

在生产试点运行的同时，团队用四周时间把问卷扩展到律师设计的完整受理流程。这是范围上的显著扩张：

- 超过 18 个受理类别，并带有条件分支——Tara 提出的问题取决于来电者此前的回答。
- **复杂的关系型数据：** 车辆（年份、品牌、型号、融资状态、每辆车月供）、房产、单笔债务明细、多个就业与收入来源，以及此前的破产申请记录。
- **基于规则的线索分类：** Stretto 对每条线索应用律师定义的规则，并由律师做出最终决定。由于语音 agent 采集的是比静态网页表单更丰富、更具条件性的数据，Stretto 在应用这些规则、准确判定线索资格时有了更大的灵活性。
- **线索路由：** 合格的线索被路由给破产领域从业者，而不符合资格标准的来电者则被引导至其他资源。

Amazon Aurora 的 schema 扩展为完整的关系型数据模型，支持一对多关系。单条来电者记录可能包含四辆车、两处房产以及数十条单笔债务明细。

### 衡量结果并持续优化

最后一个阶段侧重于收集生产数据，并根据真实来电者的行为调优系统。团队跟踪的关键绩效指标包括通话量、平均时长、受理完成率、档案完整度、转化率和流失节点。

来自生产数据的洞察推动了多项优化：调整问题顺序以减少早期流失、调整条件分支以便在对话更早阶段采集高价值字段，以及根据律师反馈修改资格判定阈值。下表展示了两项关键的生产指标。

| --- | --- |
| 数据抽取准确率 | **约 96%** |

## 面向质量与合规的测试

部署一个处理敏感财务数据的语音 agent，需要的不仅仅是功能测试。AWS Generative AI Innovation Center（GenAIIC）顾问团队指导开发了一套覆盖四个类别的完整测试框架：

- **正常路径测试：** 与配合的来电者完成覆盖完整问卷的端到端受理访谈。这些通话用于确认超过 18 个类别都能采集到准确的结构化数据，并且资格判定规则产出了正确结果。
- **对抗性测试：** 来电者提供自相矛盾的信息、在对话中途改变回答、拒绝回答某些问题，或试图操纵资格判定结果。agent 需要处理这种模糊性并保持对话连贯。
- **合规测试：** 同意采集、披露告知和数据处理流程。团队验证了 agent 会准确进行披露告知，并在继续之前采集同意，因为破产受理涉及敏感的财务信息。
- **插话场景测试：** 来电者在对话的各个时点打断，包括在披露过程中、问题中途以及 agent 回复过程中。Tara 应当在不丢失上下文、也不要求来电者重复信息的情况下恢复。

## 生产环境中的负责任 AI 控制

团队把负责任 AI 当作一项生产控制，而不只是一个测试步骤。Amazon Nova 2 Sonic 内置了安全防护措施，详情见 [Amazon Nova 2 Sonic 的 AWS AI Service Card](https://docs.aws.amazon.com/ai/responsible-ai/nova-2-sonic/overview.html)。在此基础上，该解决方案把重大决策排除在模型之外：线索分类在通话后依据明确的律师定义规则运行，并由律师做出最终决定。同意与披露告知会在受理开始前完成并记录，对抗性测试套件则检查操纵对话的企图不会改变线索结果。除模型推理之外，该解决方案还使用 Amazon Bedrock 双向流式 API 处理实时音频、在访谈过程中使用工具调用来采集结构化数据，并通过 VPC 端点与 Amazon Bedrock 建立私有连接。

GenAIIC 顾问团队还就面向语音类应用的 prompt engineering 最佳实践提供了指导，包括跨会话延续边界管理对话状态的技术，以及编写能在长访谈中保持 agent 人格一致的系统 prompt 的方法。

## 结果

在生产环境中运行大约三个月后，Stretto 报告了以下结果：

- **单条线索价值：** 拥有完整受理数据的完全合格线索，对破产律师而言比仅采集几个基础字段的网页表单线索有价值得多。
- **线索转化：** Stretto 的早期生产结果显示，与网页表单相比转化率相对提升了 20%，而此时该解决方案尚未在更多地区广泛推广。
- **数据质量与通话时长：** Stretto 报告称，在其测试中 Tara 抽取结构化字段的准确率约为 96%，已完成通话的平均时长约为 8 分钟。
- **语音解决方案成本：** Stretto 报告称，与之前的解决方案相比，每分钟语音成本降低了 95%。

## 结论

Stretto 从网页表单线索走向 AI 辅助受理访谈的历程，说明了当语音 AI 达到敏感用例所需的质量门槛时，哪些事情变得可能。通过把 Amazon Nova 2 Sonic 的语音到语音能力与 AWS 上精心设计的架构结合起来，团队构建了一个语音 agent：它对讨论个人财务困境的来电者而言足够自然，同时在成本上也足够高效，能够在大规模下带来可观的节省。

这种分阶段的做法——先验证语音质量，把最小化的受理流程部署到生产，再根据真实世界的数据扩大范围——在每一步都降低了风险。团队构建在已验证的假设之上，而不是建立在对未来的推测之上。

如果你正在为自己的用例探索 AI 语音 agent，以下是一些可以帮助你入门的资源：

- 了解 [Amazon Nova 2 Sonic](https://docs.aws.amazon.com/nova/latest/nova2-userguide/using-conversational-speech.html) 及其语音到语音能力。
- 通过 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 入门，访问包括 Amazon Nova 2 Sonic 在内的基础模型。
- 了解 [AWS Fargate](https://aws.amazon.com/fargate/)，用于容器的无服务器计算。
- 了解 [AWS Generative AI Innovation Center](https://aws.amazon.com/ai/generative-ai/innovation-center/)，为你的生成式 AI 计划获取顾问支持。

如果你正在为一个敏感、高价值的受理流程权衡是否采用语音 AI，你的 AWS 客户团队和 AWS Generative AI Innovation Center 可以帮助你界定范围并完成构建。
