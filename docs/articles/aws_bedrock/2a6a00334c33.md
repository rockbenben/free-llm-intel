# 优化企业级 AI 助手：Crypto.com 如何借助 LLM 推理与反馈提升效率

*本文与 Crypto.com 的 Jessie Jiao 共同撰写。*[*Crypto.com*](https://crypto.com/)* 是一家加密货币交易所与综合交易服务商，为 90 个国家的 1.4 亿用户提供服务。为提升 Crypto.com 的服务质量，该公司在 AWS 上落地了由 *[*生成式 AI*](https://aws.amazon.com/ai/generative-ai/)*-驱动的助手服务。*

现代 AI 助手——这类人工智能系统被设计为通过自然语言与用户交互、回答问题，甚至执行任务——在生产环境中面临日益复杂的挑战。除了处理基础 FAQ 之外，它们现在还必须执行有意义的动作、遵循公司政策、实施内容过滤、在需要时升级给人工坐席，并管理后续跟进任务。这些要求需要复杂精密的系统，能够在处理多样场景的同时保持一致性与合规性。

为应对这些挑战，模块化的子系统架构显得极有价值。这种架构思路把 AI 系统拆分为相互独立、各有所专的组件，它们既能独立运作，又能作为内聚的整体协同工作。这类设计允许灵活集成不同的处理逻辑，例如在知识库之间做智能路由、动态调整信息源的优先级，以及无缝引入业务规则与政策。每个子系统都可以针对特定任务独立开发与优化，同时保持整个系统的协调一致。

随着 AI 助手系统复杂度上升、多个子系统承担各类负载，prompt engineering 成为一项关键工作。精心设计输入文本的这门技艺引导着语言模型的响应，并促成相互关联的各组件之间行为一致。要写出既能在不同子系统间通用、又能保持一致性与准确性的有效 prompt，既关键又耗时。在企业环境中，这一挑战尤为突出，因为精确与可靠至关重要。

本文探讨我们如何利用用户反馈与系统反馈持续改进和优化指令 prompt。这种反馈驱动的方法让我们得以打造更有效的 prompt，既能适配各子系统，又能在不同用例中保持高性能。

## 反馈与推理：提升 LLM 表现的关键

尽管大语言模型（LLM）已展现出卓越能力，但面对复杂或含糊的输入时仍可能吃力。这正是反馈机制不可或缺之处。通过引入反馈闭环，LLM 可以从错误中学习、改进指令，并适应富有挑战性的场景。

一种强有力的做法是 *critiquing*（批评式评审），即让 LLM 搭配一个提供批评或反馈的外部反馈机制。举例来说，在处理文档时，如果 LLM 生成了错误的摘要，事实核查工具可以识别出不准确之处并给出反馈。模型随后可以修订其输出，从而提升准确性与可靠性。这一迭代过程类似于人类学习，反馈推动持续改进。设想这样一个例子：客户对企业 AI 助手说：「我因紧急采购需要立刻提高信用额度。」助手最初可能只给出审批步骤而未做验证，但评审系统会指出：「该回答绕过了必需的身份验证流程，且未按公司政策评估资格条件。」有了这一反馈，助手就能修订回答，补上恰当的身份认证步骤、资格审查，以及紧急情形下的替代方案——这说明批评式评审既能促成对业务规则的遵循，又能维持有助益的客户服务。

不同于传统机器学习（ML）流程中反馈充当更新模型权重的损失函数，在推理时的 LLM 应用中，这些反馈机制的运作方式有所不同。反馈并不修改底层模型参数，而是提供补充性指令，动态引导模型的行为。这种做法无需承担重新训练的计算开销即可实现行为适配，相当于构建了一个灵活的指令层，在塑造模型输出的同时保留预训练模型的核心能力。这种运行时适应性是一项重要进步，使 LLM 无需改动架构就能更贴合具体需求。

反馈机制的作用不止于简单的错误纠正，它还能让 LLM 对任务要求形成更细致的理解。通过多轮反馈迭代，模型可以学会更有效地解读含糊指令、识别隐含上下文，并据此调整处理策略。在企业场景中，这项能力尤为宝贵，因为复杂的领域特定任务要求对指令做精确解读。通过长期分析反馈模式，LLM 甚至能预判可能的误解并主动调整做法，带来更高效、更准确的结果。在我们的研究中，我们把这一方法[应用于金融服务分类任务](https://github.com/aws-samples/sample-prompt-optimization-with-reasoning-feedback/tree/main)，观察到显著的性能提升——准确率从最初的 60%，经系统性引入反馈后最终达到 100%。每一轮都针对前几轮发现的具体薄弱环节，说明结构化批评如何带来模型的持续改进。

如欲深入了解这些机制，我们建议阅读两篇关键研究论文：[CRITIC: Large Language Models Can Self-Correct with Tool-Interactive Critiquing](https://arxiv.org/abs/2305.11738)，它展示了 LLM 如何借助工具交互式批评实现自我纠正；以及 [Reflexion: Language Agents with Verbal Reinforcement Learning](https://arxiv.org/abs/2303.11366)，它探讨了具备言语强化学习的语言 agent。下图直观呈现了该反馈过程。

推理能力的最新进展让这一反馈过程更为强大。现代 LLM 现在能对自身输出做精细分析，把复杂问题拆解为可处理的组成部分，并系统评估自身表现的各个方面。想了解更多，请参阅 [Anthropic 的 Claude 3.7 Sonnet 混合推理模型现已在 Amazon Bedrock 中可用](https://aws.amazon.com/blogs/aws/anthropics-claude-3-7-sonnet-the-first-hybrid-reasoning-model-is-now-available-in-amazon-bedrock/) 与 [DeepSeek-R1 现已作为全托管无服务器模型在 Amazon Bedrock 中可用](https://aws.amazon.com/blogs/aws/deepseek-r1-now-available-as-a-fully-managed-serverless-model-in-amazon-bedrock/)。这种自我分析能力与外部反馈相结合，构成了持续改进的稳健框架。

设想一个让 LLM 做情感分析的场景。起初，在给一条褒贬混合的评论「产品与宣传一致，但客户服务令人失望」分类时，模型可能错误地标为正面。通过错误分析与验证，一个批评机制（由另一个推理模型驱动）可以给出针对性反馈，说明关于服务质量的负面表述会显著影响整体情感倾向。这类反馈并不修改模型权重，而是作为补充指令丰富原有的 prompt 模板，帮助模型在同一条文本中恰当权衡相互冲突的情感。

经过多轮反馈迭代，LLM 运用推理能力吸收这些外部反馈，并发展出更精细的分类启发式规则。在批评系统持续验证输出并给出建设性指引的情况下，模型学会识别某些模式为何导致误分类，并据此改进做法。遇到新的含糊评论时，它现在可以运用这些习得的洞察，正确解读微妙的情感差别。这说明基于推理的反馈能有效修改指令上下文而无需调整参数，从而通过分析性理解而非机械优化实现持续改进。

下一节我们探讨如何把这些反馈机制与推理能力落地为可操作的流程，以增强工作流。

## LLM 优化工作流

以下是 LLM 优化的高层流程：

- 流程始于对任务要求与成功标准的精确表述。这关键的第一步包含三个要点：定义具体任务目标；编写结构良好、指令清晰的 prompt 模板；汇集带已核验标准答案标注的完整评估数据集。在此阶段，我们会确立可量化的成功指标与验收标准，以便有效衡量改进。我们还会配置 [Amazon Nova Pro](https://aws.amazon.com/ai/generative-ai/nova/) 理解模型，使其既输出任务结果，也为自己的决策给出详细解释，从而让评估过程保持透明。

为便于说明，我们从简单的 prompt 模板起步，把客户咨询归入多个类别，例如 `PASSWORD_RESET`、`ESCALATION` 和 `OUT_OF_SCOPE`。这个初始模板只给出基本的类别定义，没有针对边界情况或分类优先级的详细指引，作为我们改进的基线。你可以参阅测试用例[数据集](https://github.com/aws-samples/sample-prompt-optimization-with-reasoning-feedback/blob/main/src/data/test_cases.json)与[初始模板](https://github.com/aws-samples/sample-prompt-optimization-with-reasoning-feedback/blob/main/src/results/optimization_iteratiion_log.json)。

- 搭建完成后，我们针对标准答案数据做严格测试，以评估模型表现。此类评估同时关注成功与失败的案例，并特别侧重分析误分类。模型为每个决策生成的解释，是了解其推理过程的有价值线索。我们既收集量化表现指标（准确率、精确率、召回率），也收集关于错误模式的定性洞察，从而形成完整的表现基线。

在这一步中，我们把模型预测与标准答案标注做比对，记录量化指标与详细错误案例。例如，当客户紧急报告账户被非授权改动、说「肯定有人访问了我的账户……我需要立刻解决」时，模型可能错误地把它归为 `CARD_DISPUTE`，而正确类别应是 `ESCALATION`。每个预测都会连同其成功状态（`true/false`）、模型的解释以及正确标注一起记录。这种完整分析构建出包含成功分类与失败案例的结构化数据集，为下一步基于推理的优化提供关键输入。

- 优化流程的关键一步，是借助专门的推理框架做系统性错误分析。该框架检视模型针对每个错误案例给出的解释，找出根本原因与模式识别失败之处。除了逐个错误分析之外，我们还会运用模式识别来发现多个案例中的系统性问题。推理模型（在我们的场景中是 [Anthropic 的 Claude 3.7](https://aws.amazon.com/bedrock/claude/)）会纳入历史反馈与学习模式，为改进 prompt 生成具体、可执行的反馈。这一关键步骤产出结构化、详细的 prompt 优化建议。

推理模型通过一个结构化框架分析分类表现：识别错误模式、追查与 prompt 相关的根本原因、考虑此前迭代的历史上下文，并提出有针对性的改进。这种有条理的方法只专注于提升 prompt 的清晰度、结构与精确度，避免做超出 prompt engineering 范围的模型或数据改动。通过系统地消除含糊之处并细化分类标准，我们每一轮都取得了更好的表现。参见以下代码：

```
critique_prompt_template = """
    Analyze classification performance and provide reasoning for prompt improvements:
    Current Template: ${input_current_template}
    Evaluation Results: ${evaluation_results}
    
    Follow these thinking steps:
    1. Error Pattern Analysis:
    2. Root Cause Investigation:
    3. Historical Context Review:
       • Previous suggestions: ${suggestion_history}
    4. Prompt Improvement Ideas:
     
    Output final suggestions between <suggestion> </suggestion> tags
"""
```

详细实现见 [error_analysis_with_reasoning.py](https://github.com/aws-samples/sample-prompt-optimization-with-reasoning-feedback/blob/main/src/prompt_optimization/error_analysis_with_reasoning.py)。

- 利用推理框架给出的结构化反馈，我们对 prompt 模板实施有针对性的修改。这些细化可能包括提升指令清晰度、调整分类参数，或重构 prompt 格式。每项修改都直接针对分析阶段识别出的具体问题，确保改动有据可依且有明确目的。重点始终是改进指令层，而不是改动底层模型架构。

为落实这些结构化改进，我们开发了一套系统化的 prompt 改写机制，封装在 [prompt_rewrite.py](https://github.com/aws-samples/sample-prompt-optimization-with-reasoning-feedback/blob/main/src/prompt_optimization/prompt_rewrite.py) 模块中。该组件通过专门的模板化方式，把分析反馈转换为具体的 prompt 增强。改写流程遵循一条有条理的工作路径：保留占位符等关键构成，纳入分析中识别出的具体改进，并确保改动直接针对反馈中的根本原因。这种系统化改写方式保证了每一轮迭代都建立在既有经验之上，而非做随意改动。

```
rewrite_prompt_template = """
TASK: Improve the prompt template based on critique feedback.
INPUT:
- Current Template: ${input_current_template}
- Critique Analysis: ${critique_feedbacks}
INSTRUCTIONS:
1. Preserve the current template structure and all placeholders
2. Implement specific improvements identified in the critique
3. Focus on addressing root causes of errors
4. Create a complete, ready-to-use improved template
OUTPUT FORMAT:
- Root cause summary
- Improved template incorporating all recommended changes
The improved template should directly address identified issues while remaining concise and effective.
"""
```

- 优化流程在每一轮结束时用评估数据集测试细化后的 prompt。我们通过对关键指标的对比分析来衡量改进幅度，并对新输出做质量评估。这一阶段会开启下一轮迭代：成功的改动被并入基线，新发现的挑战则用于指导下一轮优化。由此形成一个可持续的改进闭环，在逐步提升 prompt 有效性的同时，为成功策略保留详尽记录。

通过这一迭代细化过程，我们把一个基础 prompt 转变成了对 LLM 极为有效的指令集。每一轮迭代都有策略地针对结构化分析框架识别出的具体薄弱环节。关于每轮迭代的分析与改进的完整记录，见 [iteration_log](https://github.com/aws-samples/sample-prompt-optimization-with-reasoning-feedback/blob/main/iteration_log)。

最初只是一个简单 prompt，最终演变成一套完整的指令，其中纳入了细微的任务边界、边界情况的显式优先级规则、分层决策标准，以及针对极端情况的精确处理说明。我们没有修改模型权重或架构，而是用来自批评机制的有针对性反馈增强指令层，在不重新训练的情况下有效引导模型行为。每一轮迭代都建立在前几轮的经验之上，系统地处理批评框架揭示的错误模式。反馈作为补充指令丰富了原有 prompt 模板，使模型随着时间推移发展出愈发精细的处理启发式规则。

## 结果

借助这些迭代方法，我们在生产系统上对该方案做了基准测试。对初始 prompt 与最终 prompt 的对比分析揭示了几个重要规律：

- 通过在重叠类别之间加入显式的优先级规则，解决了边界混淆问题
- 通过纳入明确分类阈值的具体示例，边界情况的处理得到改善
- 通过在输出格式中要求结构化推理，决策透明度得以提升
- 通过加入反例帮助避免在敏感领域过度归类，分类一致性得到增强

经过 10 轮有意识的迭代并引入详细的任务特定指令，我们的任务效果提升了 34 个百分点，成绩相当可观：原本准确率 60% 的基础 prompt 被转化为在困难案例上准确率达 94% 的稳健分类系统。这不仅验证了我们的迭代优化策略，也说明系统性 prompt 细化能在不改动底层模型架构的前提下大幅提升 LLM 模型表现。

## 结论

把反馈机制引入 AI 助手系统，是对话式 AI 能力的一次重要跃升。通过实现稳健的反馈闭环，我们展示了 AI 助手如何从静态的问答系统演进为动态、可自我改进的资源。模块化子系统架构与借助反馈持续优化 prompt 相结合，使 AI 助手能够处理日益复杂的任务，同时保持合规与准确。

正如我们通过实际示例与研究洞察所展示的，反馈驱动的系统不仅产出更好的结果，还能随着时间推移形成更有效、更精简的输入指令。这种效率收益在企业环境中尤为宝贵——那里精确与适应性至关重要，而重新训练模型则代价高昂或不切实际。每一轮迭代都建立在前几轮的教训之上，系统地处理批评框架揭示的错误模式。

展望未来，持续细化反馈机制与 prompt engineering 技巧，对开发下一代 AI 助手系统至关重要。采纳这些方法，组织就能构建出既满足当前需求、又能适应未来挑战的 AI 助手，提供日益精细且可靠的交互。我们诚邀你在自己的应用中试用我们提出的反馈驱动 prompt 优化方法。对于有兴趣实施这些技巧的读者，Amazon Bedrock 为在具体业务语境中探索这些方法提供了理想的环境，并提供了多样化 FM 与灵活的部署选项。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/09/13/gary-1.jpeg)**Gary Lo** 是 AWS 的解决方案架构师，常驻香港。他是一位极具热情的 IT 专业人士，拥有 10 年以上经验，为初创公司与企业客户设计并实施分布式系统、Web 应用与移动平台方面关键且复杂的解决方案。工作之外，他喜欢烹饪，并在自己的社交媒体平台上与数千名关注者分享最新技术趋势与洞察。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2020/09/21/Yanwei-Cui.jpg)**Yanwei Cui** 博士是 AWS 的高级机器学习专家解决方案架构师。他在 IRISA（计算机科学与随机系统研究所）开始机器学习研究，并在计算机视觉、自然语言处理与在线用户行为预测领域拥有多年构建 AI 驱动的工业应用的经验。在 AWS，他分享自己的领域专长，帮助客户释放业务潜力，并借助大规模机器学习推动可执行的成果。工作之外，他喜欢阅读与旅行。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/06/13/dmhong-100.jpeg)**Michelle Hong** 博士是 Amazon Web Services 的原型解决方案架构师，帮助客户使用各类 AWS 组件构建创新应用。她在机器学习、尤其是自然语言处理方面展现了专业能力，用于开发优化业务流程、改善客户体验的数据驱动解决方案。
