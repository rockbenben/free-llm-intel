# Build a semantic layer for agentic AI with EDB Postgres AI and Amazon Bedrock AgentCore

In this post, we show how to build a semantic layer for agentic AI using [EDB Postgres AI](https://www.enterprisedb.com/docs/aidb/latest/).我们在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上运行 [Strands Agents](https://github.com/strands-agents) 代理，该代理查询该层以回答客户 360 (C360) 问题。本系列的早期文章使用 [Stardog 的知识图谱](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/)、[Denodo 的数据虚拟化]构建了相同的 C360 模式平台](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-denodo-and-amazon-bedrock-agentcore/)，[AtScale 的维度模型](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-atscale-and-amazon-bedrock-agentcore/)，以及 [Strategy Mosaic 的链接模型]（https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-strategy-mosaic-and-amazon-bedrock-agentcore/）。

EDB Postgres AI 将语义层作为 [AIDB 扩展](https://www.enterprisedb.com/docs/aidb/latest/overview/) 放入可操作的 Postgres 数据库中。业务含义与标准 Postgres“COMMENT”语句中的数据相邻，连接图来自 Postgres 外键，治理使用 Postgres“GRANT”，并通过 AIDB 附带的[模型上下文协议 (MCP) 端点](https://www.enterprisedb.com/docs/aidb/latest/mcp-endpoint/) 实现行级安全性。

读完这篇文章你将会知道：

- 如何在 Postgres 架构上构建 AIDB 语义知识库 (SemKB)，“COMMENT ON”语句和“aidb.create_semantic_alias”如何充当创作界面，以及外键如何爬入连接路径。
- 如何通过内置 EDB MCP 端点向外部代理公开 AIDB 工具目录，该端点以 [应用程序负载均衡器 (ALB)](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html) 为前端，并在 [AgentCore 上注册为 MCP 目标网关](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-targets-mcp.html)，Amazon Bedrock AgentCore 的一项功能。
- Postgres 角色、列级“GRANT”语句和行级安全性如何为不同的调用者产生不同的结果。提示符、工具目录和代理代码保持不变。
- AIDB 如何将每个 SQL 执行的 [OpenTelemetry 跟踪](https://www.enterpriseb.com/docs/aidb/latest/reference/observability/) 捕获为“aidb_otel”模式中的行，可使用普通 SQL 进行查询。

## 代理需要三层

从实时数据回答业务问题的代理需要三层：计划和编写查询的模型、告诉代理数据代表什么的含义层以及托管代理并控制身份和访问的运行时。本系列中的 [Stardog 帖子](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/) 介绍了此框架。本文中的模型层是 [Amazon Bedrock 上的 Anthropic Claude](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)，与之前的帖子相同（模型可用性因 [AWS 区域](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html) 而异）。运行时层是 [AgentCore 运行时](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)，它是 Amazon Bedrock AgentCore 的一项功能。 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-core-concepts.html) 处理入站授权，而 [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) 是 Amazon Bedrock AgentCore 的一项功能，它保存工具目标的出站凭证，与之前的帖子相同。 EDB Postgres AI 在数据库内部托管代理和工具，并通过其 MCP 端点充当外部代理的连接点。

意义层是这篇文章与其他文章不同的地方。这是一个位于可操作的 Postgres 数据库中的 [SemKB](h​​ttps://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/)。架构和业务定义一起索引。 Postgres `GRANT`、行级安全性和列级授予强制访问，而不是咨询系统提示。接下来的部分介绍了 AIDB 如何构建该层、AgentCore 如何公开它以及两个 Postgres 角色询问同一问题如何获得不同的答案。

## 示例用例：EDB Postgres AI 上的 C360

该数据集是 [Stardog C360 Knowledge Kit](https://github.com/stardog-union/knowledge-kits/tree/main/examples/c360)，加载到专用“c360”模式中的单个 EDB Postgres AI 实例中。该数据模型有四个表和一个派生视图。

| **对象** | **关键栏目** |
| ---| ---|
| `客户` | `cid`、`first_name`、`last_name`、`full_name`、`email`、`ssn`、`phone`、`picture`、`location`（FK 到 `locations.id`）|
| `地点` | `id`、`city`、`state`、`zip` |
| `产品` | `id`、`名称`、`品牌`、`部门`、`价格` |
| `购买` | `id`、`cid`（外文转为 `customers.cid`）、`pid`（外文转为 `products.id`）、`日期`、`数量`、`价格` |
| `big_spender`（视图）| `cid`、`full_name`、`state`、`large_orders`、`largest_order` |

物理模式是一个普通的 Postgres 连接图：“customers”表中的客户住在“location”，放置“purchass”，每次购买都引用一个产品。语义工作依赖于列名称未透露的三个业务理念。

状态不在客户行。它位于“locations”中，通过“customers.location”外键访问，并且对该列的注释告诉 SemKB 在哪里可以找到它。

`purchases.price` 记录订单总额。代理将其读取为单价并乘以“数量”，为顶级客户返回 502,529 美元，而不是 27,991.66 美元。

“大手笔”是企业拥有的一个术语。使用“COMMENT ON VIEW”语句捕获为视图，其定义保留在每个代理、仪表板和查询读取的一个位置。

我们通过代理端到端地提出的问题：

- 按总支出计算，我们的前 10 位客户是谁？每个客户位于哪个州？
- 每个州有多少大手笔的消费者？
- 您能列出 10 位客户以及每个客户所在的州吗？
- 哪 10 种产品销量最多？
- 您能列出五位客户及其社会安全号码吗？ （在治理重播中使用）。

## 参考架构

下图显示了从分析师通过 Amazon Bedrock AgentCore 到 EDB Postgres AI 内部语义层的请求路径。分析师使用 Amazon Cognito 进行身份验证，并使用颁发的 JSON Web 令牌 (JWT) 作为“承载”令牌来调用 AgentCore Gateway。网关路由到 AgentCore 运行时，该运行时与 Claude 一起在 Amazon Bedrock 上进行规划。代理通过网关调用 MCP 工具，网关转发到 EDB Postgres AI 虚拟私有云 (VPC) 中的应用程序负载均衡器，并转发到 AIDB 内的“edb-endpoints”MCP 服务器。 AIDB 提供 SemKB、语义别名和只读 PostgreSQL 表。 AgentCore 跟踪会发送到 Amazon CloudWatch，AIDB 将 OpenTelemetry 跟踪捕获为 Postgres 内“aidb_otel”架构中的行。

![从分析师通过 Amazon Cognito 和 Amazon Bedrock AgentCore 到应用程序负载背后的 EDB Postgres AI 语义层的请求路径平衡器](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/28/ML-22159-1-1.png)

图 1：EDB Postgres AI 和 Amazon Bedrock AgentCore 的参考架构

两个流跨越 AgentCore 和 EDB Postgres AI 之间的边界。

**入站：** 客户端使用 [Amazon Cognito 用户池](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-idp-cognito.html) 颁发的不记名令牌调用 AgentCore Gateway。网关[入站 JWT 授权方](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html) 根据 Cognito 发现 URL 验证令牌。然后，网关根据令牌的声明评估其 [Cedar 策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-authorization-flow.html)，以决定代表该用户的代理可以调用​​哪些工具。然后，它将调用路由到 AgentCore 运行时。该代理调用 Amazon Bedrock 上的 Claude 进行规划和答案撰写。

**出站到语义层：** 代理的工具调用是一个 [MCP](https://modelcontextprotocol.io/) 请求。 AgentCore Gateway 直接支持 [MCP 服务器目标](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-targets-mcp.html)。 AIDB 的“edb-endpoints” HTTP 服务器使用 [具有 HTTP 基本身份验证的流式 HTTP MCP](https://www.enterprisedb.com/docs/aidb/latest/mcp-endpoint/connecting-a-client/)，这让 Gateway 将其视为没有转换层的 MCP 服务器目标。具有 HTTPS 侦听器和 [AWS 证书管理器 (ACM)](https://docs.aws.amazon.com/acm/latest/userguide/acm-overview.html) 证书的 Application Load Balancer 位于 Amazon Elastic Compute Cloud (Amazon EC2) 实例上的“edb-endpoints”前面。 ALB URL 注册为网关目标。 [AgentCore Identity 凭证提供程序](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-outbound-credential-provider.html) 持有 Postgres 角色凭证，并将其作为每个出站请求的基本身份验证注入。代理代码看不到 Postgres 凭证。

**可观察性：** AgentCore 向 [CloudWatch Transaction Search](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-configure.html) 发出工具调用、大型语言模型 (LLM) 调用和令牌使用情况的跟踪。 AIDB 将 [SQL 执行的 OpenTelemetry 跟踪](https://www.enterpriseb.com/docs/aidb/latest/reference/observability/) 捕获为 Postgres 内 `aidb_otel` 模式中的行，在数据库配置为写入它们后可以使用普通 SQL 进行查询（请参阅[在源数据库上启用遥测](https://www.enterpriseb.com/docs/agent-governance/latest/connecting_aidb/)）。

此架构中不需要 AWS Lambda。 AIDB 已经支持 MCP，因此网关可以直接通过 ALB 与它作为 MCP 服务器目标进行对话。本系列中的 Denodo 帖子在其 MCP 服务器前面使用相同的 ALB 模式，并且除了供应商之外，这里的架构没有变化。

## 构建语义层

这些步骤假设 EDB Postgres AI 实例上安装并启用了 [AIDB](https://www.enterpriseb.com/docs/aidb/latest/)，并且 Stardog C360 套件的四个 CSV 已加载到专用的“c360”架构中，其中主键和外键如前所示。由于该层与数据位于同一数据库中，因此无需部署第二个系统，也无需同步目录。语义层是在 SQL 中定义的，位于与写入行的应用程序相同的数据库内。

AIDB [语义知识库](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/) 索引 Postgres 模式，而不是数据。它将每个表、视图和列的定义（旁边带有“COMMENT ON”文本）嵌入到向量存储中，代理可以用自然语言进行搜索。三个创作任务可帮助代理通过含义找到正确的表和列：编写“COMMENT ON”语句、将业务术语定义为带有自己注释的视图，以及将重复出现的问题注册为[语义别名](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/semantic-aliases/)。注释是三个创作任务中最简单的，对于用户和代理来说，它可以最大程度地提高文本到 SQL 的准确性。

### 在代理会查看的位置添加注释
```
COMMENT ON COLUMN c360.purchases.price IS
  'Total amount the customer paid for the entire order, in US dollars. Not the unit price.';
COMMENT ON COLUMN c360.purchases.cid IS
  'Customer who placed the order. Joins to customers.cid.';
COMMENT ON COLUMN c360.customers.location IS
  'Home address of the customer. Joins to locations.id. State is in locations.state.';
COMMENT ON COLUMN c360.customers.ssn IS
  'US Social Security number. Sensitive, column-level grant required.';

CREATE VIEW c360.big_spender AS
  SELECT c.cid, c.full_name, l.state,
         count(*)      AS large_orders,
         max(pu.price) AS largest_order
    FROM c360.purchases pu
    JOIN c360.customers c ON c.cid = pu.cid
    JOIN c360.locations l ON l.id  = c.location
   WHERE pu.price > 250
   GROUP BY c.cid, c.full_name, l.state;

COMMENT ON VIEW c360.big_spender IS
  'Big spenders. A big spender is a customer with at least one order over 250 US dollars. '
  'Use this view for any question about big spenders.';
```
该视图将业务定义保存在一处，因此代理或仪表板无需重新定义“大支出者”。您预先花在评论上的时间会在代理随后运行的每个查询上得到回报。

### 创建语义知识库

在“c360”架构上创建 SemKB。该调用注册名称、嵌入模型、目标模式和自动处理模式。
```
SELECT aidb.create_semantic_kb(
    name            => 'c360_kb',
    model           => 'bge-small-en-v1.5-f16',
    schemas         => ARRAY['c360'],
    auto_processing => 'Live'
);
```
嵌入模型是随 AIDB Amazon 系统映像 (AMI) 附带的本地 llama.cpp 模型 (`llamacpp_embeddings`)。 SemKB 每 KB 使用一个嵌入模型，因此每个条目都位于同一向量空间中。 AIDB AMI 在“public”上附带了一个名为“semkb”的默认 SemKB，因此创建“c360_kb”会在实例上留下两个 SemKB。当存在多个 SemKB 时，每个“aidb.semantic_kb_search”调用都必须显式传递“kb_name”。要将本地模型替换为远程嵌入模型，例如 [Amazon Bedrock 上的 Amazon Titan Text Embeddings](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html)，请使用 [aidb.create_model](https://www.enterprisedb.com/docs/aidb/latest/integrating-models/remote-models/) 注册远程模型。将其名称作为 SemKB 的“model”参数传递。 “auto_processing”参数接受“Disabled”、“Live”或“Background”。 “Live”通过 Postgres 事件触发器对架构更改做出反应。 “后台”从工作人员异步处理它们。 `Disabled` 等待显式的 `aidb.refresh_semantic_kb()`。 SemKB 同时也会抓取[外键转化为关系](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/)。 “purchases.cid”外键成为代理可以通过含义而不是列名称发现的连接路径。

### 将重复出现的问题捕获为语义别名

[语义别名](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/semantic-aliases/) 是一个命名的、参数化的只读“SELECT”，具有自然语言描述，SemKB 与模式元数据一起索引该描述。代理根据含义找到它，使用参数调用它，并返回受管理的答案。
```
SELECT aidb.create_semantic_alias(
    name        => 'big_spenders_by_state',
    description => 'Count big spenders grouped by state, ordered from most to fewest.',
    query_text  => $$SELECT state, count(*) AS big_spenders
                     FROM c360.big_spender
                     GROUP BY state
                     ORDER BY big_spenders DESC, state$$,
    params      => '[]'
);
```
别名是 AIDB 可重用的文本到 SQL 构建块。它们位于 SemKB 索引中的表和视图旁边，并作为工具向代理显示。有关完整的[文本到 SQL 演练](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/text-to-sql/)，请参阅[EDB 文档](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/)。

## 管理访问

该架构中的治理自始至终贯穿 Postgres 原语。 AIDB MCP 端点没有自己的权限系统：“Postgres 授予决定每个代理可以运行的内容”（[MCP 端点参考](https://www.enterprisedb.com/docs/aidb/latest/mcp-endpoint/)）。每个 MCP 请求都通过自己的连接使用 Postgres 用户名和密码进行身份验证，因此每个工具调用中的“current_user”都是代理的角色，与其他连接一样在“pg_stat_activity”中可见。

下图跟踪了身份如何从最终用户通过 AgentCore 流向评估 SQL 的 Postgres 角色，以及如何捕获生成的跟踪以供审核。该链分四个阶段运行：网关的入站信任、来自 AgentCore Identity 的出站凭证、通过 GRANT 和行级安全性在 Postgres 中实施，以及通过 `aidb_otel` 模式中的 OpenTelemetry 跟踪进行审核。

![身份流从最终用户的 Amazon Cognito 令牌通过 AgentCore 网关和身份到运行SQL](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/28/ML-22159-2-1.png)

图 2：从最终用户到评估 SQL 的 Postgres 角色的身份传播链

**网关的入站信任：** 1. 最终用户使用 Amazon Cognito 进行身份验证并接收 JWT 不记名令牌。 2. 客户端使用“Authorization”标头中的令牌调用 AgentCore Gateway。 3. 网关 [JWT 授权者](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html) 根据 Cognito 用户池的发现 URL 验证令牌。 4. 网关根据令牌的声明评估其 [Cedar 策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-authorization-flow.html)，以决定该代理可以调用​​哪个工具。

**AIDB 的出站凭证：** 5. 网关从 [AgentCore Identity 凭证提供程序](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-outbound-credential-provider.html) 解析 MCP 目标的出站凭证。对于 AIDB，这是用作 HTTP 基本身份验证的 Postgres 用户名和密码。 6. 网关将 MCP 可流式 HTTP 请求转发到 ALB，ALB 将其转发到“edb-endpoints”。

**Postgres 中的强制执行：** 7. `edb-endpoints` 使用 Basic auth 标头中的用户名和密码打开 Postgres 连接。 Postgres 根据 `pg_hba.conf` 验证登录角色，工具调用中的 `current_user` 就是该角色。 8. “c360”表上的列级“GRANT”语句和行级安全策略强制执行工具调用返回的行和列。拒绝表现为受限制的表或列上的 Postgres 权限被拒绝错误，MCP 端点会原样转发该错误。

**审核。** 9. AIDB 将 SQL 执行的 OpenTelemetry 跟踪捕获为“aidb_otel”架构中的行，可立即通过 SQL 获取。

### 两个 Postgres 角色，同样的问题，不同的结果

定义两个仅在列级“GRANT”方面不同的代理登录角色：“mcp_agent_full”可查看每一列，“mcp_agent_restricted”可查看除“customers.ssn”之外的每一列。
```
CREATE ROLE mcp_agent_full       LOGIN PASSWORD '...';
CREATE ROLE mcp_agent_restricted LOGIN PASSWORD '...';

GRANT USAGE ON SCHEMA c360 TO mcp_agent_full, mcp_agent_restricted;

-- Both roles need aidb_users to list MCP tools
GRANT aidb_users TO mcp_agent_full, mcp_agent_restricted;

-- Full role sees every column
GRANT SELECT ON ALL TABLES IN SCHEMA c360 TO mcp_agent_full;

-- Restricted role sees every table and view, with customers.ssn withheld
GRANT SELECT ON c360.locations, c360.products, c360.purchases, c360.big_spender
  TO mcp_agent_restricted;
GRANT SELECT (cid, first_name, last_name, email, phone, picture, location, full_name)
  ON c360.customers TO mcp_agent_restricted;
```
两个登录角色都需要本地“edb-endpoints”连接路径的“pg_hba.conf”中的密码身份验证条目，如[配置您的代理角色](https://www.enterprisedb.com/docs/aidb/latest/mcp-endpoint/configuring-agent-roles/)中所述。通过两个角色运行相同的问题会产生不同的结果。在“mcp_agent_restricted”下调用的代理无法投影“ssn”列：在尝试时，Postgres 返回“permission returned for ssn”，并且 MCP 端点会原封不动地转发该错误。然后代理回复说它无法读取 SSN。两个角色之间的提示、工具目录、SemKB 和代理代码是相同的。唯一的区别是 AgentCore Identity 在出站基本身份验证标头上注入的凭据。

行级过滤遵循相同的模式。在目标表上启用行级安全性 (RLS) 并附加每个角色的“USING”策略。 AIDB MCP 端点看到的行与角色在直接“psql”连接中看到的行相同。

**关于 AIDB 用途的说明。** AIDB 还提供了[用途](https://www.enterpriseb.com/docs/aidb/latest/governance/)，这是一种将数据库内代理（使用 `aidb.create_agent` 创建并使用 `aidb.agent_converse` 调用的代理）限制到指定 Postgres 角色的策略抽象。用途适用于数据库内代理路径。如前所述，本文使用的外部 AgentCore 路径直接通过 MCP 端点上的 Postgres 角色进行管理。有关外部 MCP 代理的审计，请参阅 [EDB 代理治理](https://www.enterprisedb.com/docs/agent-governance/latest/)，其中读取相同的“aidb_otel”跨越并可视化代理会话和策略决策。

**负责任的人工智能考虑因素。** 到目前为止显示的治理界面控制着代理在数据库层“可以执行”的内容。在模型端将其与 [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 配对，以塑造代理*允许生成*的内容：敏感主题、拒绝主题列表和 PII 修订的内容过滤器。这两层相辅相成。 Postgres `GRANT` 阻止代理在数据层读取 SSN。护栏有助于防止 PII 模式通过模型响应中的其他路径泄漏。对于回答有关客户数据的业务问题的代理来说，两者都是生产控制。

## 暴露该层并运行代理

启用 AIDB MCP 端点需要两个 Postgres 参数以及重新启动。在 `postgresql.conf` 中设置 `edb.endpoints_mcp_enabled = on`，将 `aidb` 添加到 `shared_preload_libraries`，然后重新启动（[启用端点](https://www.enterprisedb.com/docs/aidb/latest/mcp-endpoint/enabling-the-endpoint/)）。要从 EC2 实例外部访问终端节点，请将“edb.endpoints_mcp_host”设置为非环回地址，例如“0.0.0.0”。使用“edb.endpoints_mcp_port”选择端口（默认为 8765）。为传输层安全 (TLS) 对提供“edb.endpoints_mcp_tls_cert”和“edb.endpoints_mcp_tls_key”，端点需要使用它们来进行非环回绑定（[配置端点](https://www.enterprisedb.com/docs/aidb/latest/mcp-endpoint/configuring-the-endpoint/)）。

具有 HTTPS 侦听器和 ACM 证书的应用程序负载均衡器向 AgentCore 网关公开“edb-endpoints”。 ALB 目标组在端口 8765 上使用 HTTPS 连接到 EC2 实例，并且不验证后端证书链，因此“edb-endpoints”上的自签名证书足以用于开发和测试。对于生产，请使用具有 [AgentCore Gateway VPC 出口](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-vpc-egress.html) 的内部 ALB，以保持网关与 ALB 之间的连接私有。

使用 Cognito 授权者创建 AgentCore 网关，将 ALB URL 注册为 MCP 服务器目标，并将两个 Postgres 凭证存储在 AgentCore Identity 凭证提供程序中（[凭证提供程序参考](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-outbound-credential-provider.html)）。

该代理是一个简短的 Python 脚本。它使用 [Strands Agents](https://github.com/strands-agents/sdk-python) 将指向最新 Claude Sonnet 的 `BedrockModel` 连接到 `MCPClient`。 “MCPClient”通过 [流式 HTTP MCP 传输](https://modelcontextprotocol.io/) 连接到网关 URL，并使用 Cognito 访问令牌作为“Bearer”标头。系统提示指示代理首先调用“semantic_kb_search”以获取模式上下文，传递“kb_name => 'c360_kb'”，然后“execute_sql”运行生成的查询。 [AgentCore 运行时入门工具包与 Strands](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-toolkit.html) 有一个在生产中托管这种形状的代理的有效示例。

我们建议为代理的系统提示打开 [Amazon Bedrock 提示缓存](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)。每次调用时都会重复使用相同的指令和相同的工具列表，这就是提示缓存的用途。

## 跨数据源扩展

对于超出操作数据库容量的分析工作负载，[EDB Postgres 分析加速器 (PGAA)](https://www.enterprisedb.com/docs/pgaa/latest/) 让 Postgres 通过 Iceberg REST 目录读取对象存储中的 Apache Iceberg、Delta Lake 和 Parquet 表。 [EDB Postgres AI 分析概述](https://www.enterprisedb.com/docs/edb-postgres-ai/analytics/) 涵盖了端到端设置。 PGAA 表在 Postgres 中显示为普通表，因此相同的 SemKB 描述继续针对分析副本起作用，并且代理的工具目录不会更改。

为了联合外部关系源，Postgres [外部数据包装器](https://www.postgresql.org/docs/current/ddl-foreign-data.html) 使外部表可访问，就像它是本地表一样。在任何一种情况下，语义层都不会改变，因为业务定义、列注释和语义别名都存在于 Postgres 中。

## 部署

该架构有两种形状。

**在 Amazon EC2 上自行管理。** 使用 AWS Marketplace 中的 EDB Postgres AI Agent Factory AMI。客户拥有 VPC、子网、版本节奏和 EDB Postgres AI 软件升级。 ALB 和 AgentCore Gateway 目标配置与之前的架构相比没有变化。

**EDB 在 Amazon EC2 上托管。** [EDB 托管数据库](https://www.enterprisedb.com/services/driven-database) 是 EDB 专家代表客户处理数据库管理的一项服务。 AgentCore 方面没有变化。

＃＃ 结论

Reliable agentic analytics needs three things working together: a foundation model that can plan and generate queries, a semantic layer that provides a governed business view of the data, and an agent runtime that hosts the agent and manages identity. Amazon Bedrock supplies the model, Amazon Bedrock AgentCore supplies the runtime, and EDB Postgres AI supplies a semantic layer that lives inside the operational Postgres database.业务含义、连接路径和治理来自模式中已存在的 Postgres 原语。 AWS 端与本系列的其余部分相同：AgentCore Gateway、Runtime、Identity、Bedrock 和 CloudWatch。

数据、业务定义和访问规则都位于一个 Postgres 架构中，因此没有单独的目录可以保持同步。审计位于同一个数据库中：“aidb_otel”在每个工具调用的数据旁边保存一个范围。

### 从哪里开始

要将此架构应用于您自己的数据，请完成以下步骤：

- 选择您的代理需要实时查询的一个 Postgres 数据库。越窄越好。
- 为代理数据创建专用模式，并将“GRANT USAGE”范围限定为服务角色。
- 在使用业务语言的列和视图上编写“COMMENT ON”语句。使用“COMMENT ON VIEW”语句将业务术语捕获为视图。
- 使用“aidb.create_semantic_kb”和“auto_processing => 'Live'”（或高写入量下的“Background”）在架构上创建 SemKB。
- 将重复出现的问题注册为语义别名。
- 启用 AIDB MCP 端点，在其前面添加带有 HTTPS 的 ALB 和 ACM 证书，并将 ALB URL 注册为 AgentCore Gateway MCP 服务器目标。
- 通过代理运行三个真实问题，然后在拨款减少的角色下重新运行一个问题，以确认执行表面端到端的工作。
