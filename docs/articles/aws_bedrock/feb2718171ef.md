# 用 EDB Postgres AI 与 Amazon Bedrock AgentCore 为 agentic AI 构建语义层

在本文中，我们演示如何用 [EDB Postgres AI](https://www.enterprisedb.com/docs/aidb/latest/) 为 agentic AI 构建一个语义层。我们在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上运行一个 [Strands Agents](https://github.com/strands-agents) agent，由它查询这一层来回答 customer 360（C360）问题。本系列此前的几篇文章用 [Stardog 的知识图](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/)、[Denodo 的数据虚拟化平台](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-denodo-and-amazon-bedrock-agentcore/)、[AtScale 的维度模型](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-atscale-and-amazon-bedrock-agentcore/) 以及 [Strategy Mosaic 的关联模型](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-strategy-mosaic-and-amazon-bedrock-agentcore/) 搭建过同一个 C360 模式。

EDB Postgres AI 把语义层放进运营 Postgres 数据库的内部，形态是一个 [AIDB 扩展](https://www.enterprisedb.com/docs/aidb/latest/overview/)。业务含义以标准 Postgres `COMMENT` 语句的形式与数据相邻而居，join 图来自 Postgres 外键，治理则通过 AIDB 自带的 [Model Context Protocol（MCP）端点](https://www.enterprisedb.com/docs/aidb/latest/mcp-endpoint/) 用上 Postgres `GRANT` 和行级安全来落实。

读完本文，你将了解：

- 如何在一个 Postgres schema 之上构建 AIDB 的语义知识库（SemKB），`COMMENT ON` 语句与 `aidb.create_semantic_alias` 作为创作界面各自是怎么工作的，以及外键如何被爬取成 join 路径。
- 如何通过内置的 EDB MCP 端点把 AIDB 的工具目录暴露给外部 agent；该端点由一个 [Application Load Balancer（ALB）](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html) 前置，并作为 MCP target 注册到 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-targets-mcp.html)（Amazon Bedrock AgentCore 的一项能力）上。
- Postgres 角色、列级 `GRANT` 语句和行级安全如何让不同的调用者得到不同的结果。prompt、工具目录和 agent 代码都不变。
- AIDB 如何把每一次 SQL 执行的 [OpenTelemetry trace](https://www.enterprisedb.com/docs/aidb/latest/reference/observability/) 记录为 `aidb_otel` schema 中的行，从而可以用普通 SQL 查询。

## agent 需要的三层

一个要从实时数据里回答业务问题的 agent 需要三层：一个负责规划并编写查询的模型，一个告诉 agent 数据代表什么的含义层，以及一个托管 agent 并控制身份与访问的运行时。本系列中的 [Stardog 那篇](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/) 提出了这套划分。本文的模型层是 [Amazon Bedrock 上的 Anthropic Claude](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)，与此前几篇相同（模型可用性因 [AWS Region](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html) 而异）。运行时层是 [AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)，它是 Amazon Bedrock AgentCore 的一项能力。[AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-core-concepts.html) 处理入站授权，而 [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html)（同样是 Amazon Bedrock AgentCore 的一项能力）为各个工具 target 持有出站凭证，这一点也与此前几篇相同。EDB Postgres AI 则把 agents 和工具托管在数据库自身内部，并通过它的 MCP 端点充当外部 agent 的接入点。

含义层是本文与其他几篇分野的地方。这里的含义层是一个住在运营 Postgres 数据库内部的 [SemKB](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/)。schema 与业务定义被一起建了索引。访问由 Postgres `GRANT`、行级安全和列级授权强制执行，而不是一条只是建议性质的系统 prompt。下面几节会讲 AIDB 如何构建这一层、AgentCore 如何把它暴露出去，以及两个 Postgres 角色问同一个问题为何得到不同答案。

## 示例用例：EDB Postgres AI 上的 C360

数据集用的是 [Stardog C360 Knowledge Kit](https://github.com/stardog-union/knowledge-kits/tree/main/examples/c360)，加载进单个 EDB Postgres AI 实例中一个专门的 `c360` schema。数据模型有四张表和一个派生视图。

| **对象** | **关键列** |
| --- | --- |
| `customers` | `cid`、`first_name`、`last_name`、`full_name`、`email`、`ssn`、`phone`、`picture`、`location`（外键指向 `locations.id`） |
| `locations` | `id`、`city`、`state`、`zip` |
| `products` | `id`、`name`、`brand`、`dept`、`price` |
| `purchases` | `id`、`cid`（外键指向 `customers.cid`）、`pid`（外键指向 `products.id`）、`date`、`quantity`、`price` |
| `big_spender`（视图） | `cid`、`full_name`、`state`、`large_orders`、`largest_order` |

物理 schema 就是一张普通的 Postgres join 图：`customers` 表里的一个客户住在一个 `location`，下了一些 `purchases`，而每一笔购买都引用一个产品。语义工作则建立在三个列名体现不出来的业务概念之上。

state 不在客户那一行上。它在 `locations` 里，要经由 `customers.location` 这个外键才能到达，而该列上的一条注释会告诉 SemKB 去哪里找它。

`purchases.price` 记录的是订单总额。一个把它当单价、再乘上 `quantity` 的 agent，会给消费额最高的那位客户返回 $502,529，而不是 $27,991.66。

*big spender* 是业务方自己拥有的一个术语。用一个 `COMMENT ON VIEW` 语句把它沉淀成视图之后，它的定义就留在一个地方，供所有 agent、dashboard 和查询读取。

我们端到端地交给 agent 跑的这几个问题：

- 按总消费额排名，我们的前 10 名客户是谁，他们各自住在哪个州？
- 每个州各有多少 big spender？
- 能否列出 10 位客户以及各自所在的州？
- 哪 10 个产品卖出的件数最多？
- 能否列出五位客户以及他们的社会保障号？（用于治理复跑）。

## 参考架构

下图展示请求路径：从分析师出发，经过 Amazon Bedrock AgentCore，抵达 EDB Postgres AI 内部的语义层。分析师用 Amazon Cognito 认证，然后带着签发的 JSON Web Token（JWT）作为 `Bearer` token 调用 AgentCore Gateway。Gateway 把请求路由到 AgentCore runtime，后者用 Amazon Bedrock 上的 Claude 做规划。agent 通过 Gateway 调用 MCP 工具，Gateway 再把调用转发到 EDB Postgres AI 虚拟私有云（VPC）里的一个 Application Load Balancer，进而到达 AIDB 内部的 `edb-endpoints` MCP server。AIDB 对外提供 SemKB、semantic aliases 以及只读的 PostgreSQL 表。AgentCore 的 traces 汇入 Amazon CloudWatch，AIDB 则把 OpenTelemetry traces 记录为 Postgres 内部 `aidb_otel` schema 中的行。

图 1：EDB Postgres AI 与 Amazon Bedrock AgentCore 的参考架构

有两条流程跨过 AgentCore 与 EDB Postgres AI 之间的那道边界。

**入站：** 客户端带着由 [Amazon Cognito 用户池](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-idp-cognito.html) 签发的 bearer token 调用 AgentCore Gateway。Gateway 的[入站 JWT 授权器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html)对照 Cognito 的 discovery URL 校验这个 token。随后 Gateway 依据 token 的 claims 评估它的 [Cedar policy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-authorization-flow.html)，判定这个代表该用户行事的 agent 能调用哪些工具，再把调用路由到 AgentCore runtime。agent 调用 Amazon Bedrock 上的 Claude 来规划并组织答案。

**出站前往语义层：** agent 的工具调用是一个 [MCP](https://modelcontextprotocol.io/) 请求。AgentCore Gateway 直接支持 [MCP server targets](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-targets-mcp.html)。AIDB 的 `edb-endpoints` HTTP server 说的是[带 HTTP Basic 认证的 streamable HTTP MCP](https://www.enterprisedb.com/docs/aidb/latest/mcp-endpoint/connecting-a-client/)，这让 Gateway 可以把它当作一个 MCP server target 直接使用，中间不需要任何转换层。一个带 HTTPS 监听器和 [AWS Certificate Manager（ACM）](https://docs.aws.amazon.com/acm/latest/userguide/acm-overview.html) 证书的 Application Load Balancer，前置在跑着 `edb-endpoints` 的 Amazon Elastic Compute Cloud（Amazon EC2）实例之前。ALB 的 URL 被注册为 Gateway target。[AgentCore Identity 的凭证提供方](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-outbound-credential-provider.html)持有 Postgres 角色凭证，并在每一个出站请求上把它注入为 Basic auth。agent 代码看不到那份 Postgres 凭证。

**可观测性：** AgentCore 会把工具调用、大语言模型（LLM）调用和 token 用量的 traces 发到 [CloudWatch Transaction Search](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-configure.html)。AIDB 会把 [SQL 执行的 OpenTelemetry traces](https://www.enterprisedb.com/docs/aidb/latest/reference/observability/) 记录为 Postgres 内部 `aidb_otel` schema 中的行，在把数据库配置成写入这些行之后，就能用普通 SQL 查询它们（见[在源数据库上启用遥测](https://www.enterprisedb.com/docs/agent-governance/latest/connecting_aidb/)）。

这套架构不需要 AWS Lambda。AIDB 本身就讲 MCP，所以 Gateway 通过 ALB 直接把它当作 MCP server target 来对话。本系列的 Denodo 那篇在其 MCP server 前面用的是同一套 ALB 模式，除了厂商之外，这里的架构没有变化。

## 构建语义层

这些步骤假定 EDB Postgres AI 实例上已经[安装并启用了 AIDB](https://www.enterprisedb.com/docs/aidb/latest/)，并且 Stardog C360 kit 的那四个 CSV 已经带着前面给出的主键与外键加载进一个专门的 `c360` schema。因为这一层与数据待在同一个数据库里，所以没有第二个系统要部署，也没有目录要同步。语义层是用 SQL 定义的，就在写入这些行的应用程序所在的那个数据库内部。

AIDB 的[语义知识库](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/)索引的是 Postgres schema，不是数据。它把每一张表、每一个视图、每一列的定义（连同并排的 `COMMENT ON` 文本）嵌入到一个向量存储里，agent 可以在其中用自然语言检索。有三项创作工作能帮助 agent 按含义找到正确的表和列：编写 `COMMENT ON` 语句、把业务术语定义成自带注释的视图、把反复出现的问题登记为 [semantic aliases](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/semantic-aliases/)。注释是这三项创作工作里最简单的一项，无论对用户还是 agent，它对 text-to-SQL 准确率的提升都最大。

### 在 agent 会查看的地方加注释

```
COMMENT ON COLUMN c360.purchases.price IS
  'Total amount the customer paid for the entire order, in US dollars. Not the unit price.';
COMMENT ON COLUMN c360.purchases.cid IS
  'Customer who placed the order. Joins to customers.cid.';
COMMENT ON COLUMN c360.customers.location IS
  'Home address of the customer. Joins to locations.id. State is in locations.state.';
COMMENT ON COLUMN c360.customers.ssn IS
  'US Social Security number. Sensitive, column-level grant required.';

CREATE VIEW c360.big_spender AS
  SELECT c.cid, c.full_name, l.state,
         count(*)      AS large_orders,
         max(pu.price) AS largest_order
    FROM c360.purchases pu
    JOIN c360.customers c ON c.cid = pu.cid
    JOIN c360.locations l ON l.id  = c.location
   WHERE pu.price > 250
   GROUP BY c.cid, c.full_name, l.state;

COMMENT ON VIEW c360.big_spender IS
  'Big spenders. A big spender is a customer with at least one order over 250 US dollars. '
  'Use this view for any question about big spenders.';
```

这个视图把业务定义收在一处，于是没有任何 agent 或 dashboard 需要重新定义一遍 *big spender*。你在前期花在注释上的时间，会在 agent 之后运行的每一条查询上得到回报。

### 创建语义知识库

在 `c360` schema 之上创建 SemKB。这个调用会注册名称、嵌入模型、目标 schema 以及自动处理模式。

```
SELECT aidb.create_semantic_kb(
    name            => 'c360_kb',
    model           => 'bge-small-en-v1.5-f16',
    schemas         => ARRAY['c360'],
    auto_processing => 'Live'
);
```

嵌入模型是一个本地的 llama.cpp 模型（`llamacpp_embeddings`），随 AIDB Amazon Machine Image（AMI）一起提供。SemKB 每个 KB 使用一个嵌入模型，所以所有条目都落在同一个向量空间里。AIDB AMI 自带一个建在 `public` 之上、名为 `semkb` 的默认 SemKB，因此创建了 `c360_kb` 之后，实例上就会有两个 SemKB。只要存在不止一个 SemKB，每一次 `aidb.semantic_kb_search` 调用都必须显式传入 `kb_name`。要把这个本地模型换成远程嵌入模型，例如 [Amazon Bedrock 上的 Amazon Titan Text Embeddings](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html)，就用 [aidb.create_model](https://www.enterprisedb.com/docs/aidb/latest/integrating-models/remote-models/) 注册那个远程模型，并把它的名字作为 SemKB 的 `model` 参数传入。`auto_processing` 参数可取 `Disabled`、`Live` 或 `Background`。`Live` 通过 Postgres 事件触发器响应 schema 变更。`Background` 由 worker 异步处理这些变更。`Disabled` 则等待一次显式的 `aidb.refresh_semantic_kb()`。SemKB 同时还会把[外键爬取成关系](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/)。`purchases.cid` 这个外键就成了一条 join 路径，agent 按含义而不是按列名就能发现它。

### 把反复出现的问题登记为 semantic aliases

一个 [semantic alias](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/semantic-aliases/) 是带名字、带参数、只读的 `SELECT`，附上一段自然语言描述，SemKB 会把它与 schema 元数据一起建索引。agent 按含义找到它，带参数调用它，返回一个受治理的答案。

```
SELECT aidb.create_semantic_alias(
    name        => 'big_spenders_by_state',
    description => 'Count big spenders grouped by state, ordered from most to fewest.',
    query_text  => $$SELECT state, count(*) AS big_spenders
                     FROM c360.big_spender
                     GROUP BY state
                     ORDER BY big_spenders DESC, state$$,
    params      => '[]'
);
```

semantic aliases 是 AIDB 可复用的 text-to-SQL 构件。在 SemKB 索引里它们与表和视图并列，在 agent 眼中则呈现为一个工具。完整的 [text-to-SQL 演练](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/text-to-sql/)见 [EDB 文档](https://www.enterprisedb.com/docs/aidb/latest/semantic-knowledge-bases/)。

## 治理访问

这套架构里的治理一路到底都是 Postgres 原语。AIDB MCP 端点本身没有权限体系：「Postgres grants 决定每个 agent 能运行什么」（[MCP endpoint 参考](https://www.enterprisedb.com/docs/aidb/latest/mcp-endpoint/)）。每个 MCP 请求都用一个 Postgres 用户名和密码在自己的连接上认证，所以每次工具调用内部的 `current_user` 就是这个 agent 的角色，和其他连接一样能在 `pg_stat_activity` 里看到。

下图梳理身份如何从终端用户出发、经过 AgentCore，一路流到执行 SQL 的那个 Postgres 角色，以及随之产生的 trace 如何被记录下来供审计。这条链分四个阶段：Gateway 上的入站信任、来自 AgentCore Identity 的出站凭证、Postgres 内通过 GRANT 与行级安全的强制执行，以及通过 `aidb_otel` schema 中 OpenTelemetry traces 完成的审计。

![https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026-10-28/ML-22159-2-1.png](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/28/ML-22159-2-1.png)

图 2：从终端用户到执行 SQL 的 Postgres 角色的身份传播链

**Gateway 上的入站信任：** 1. 终端用户向 Amazon Cognito 认证，拿到一个 JWT bearer token。2. 客户端带着 `Authorization` 头里的这个 token 调用 AgentCore Gateway。3. Gateway 的 [JWT 授权器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html)对照 Cognito 用户池的 discovery URL 校验该 token。4. Gateway 依据 token 的 claims 评估它的 [Cedar policy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-authorization-flow.html)，判定这个 agent 能调用哪个工具。

**前往 AIDB 的出站凭证：** 5. Gateway 从[AgentCore Identity 的凭证提供方](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-outbound-credential-provider.html)解析出这个 MCP target 的出站凭证。就 AIDB 而言，那是一个 Postgres 用户名和密码，用作 HTTP Basic auth。6. Gateway 把 MCP 的 streamable-HTTP 请求转发给 ALB，ALB 再把它转发给 `edb-endpoints`。

**Postgres 内的强制执行：** 7. `edb-endpoints` 用 Basic auth 头里的用户名和密码打开一个 Postgres 连接。Postgres 按 `pg_hba.conf` 认证这个登录角色，工具调用内部的 `current_user` 就是该角色。8. `c360` 表上的列级 `GRANT` 语句与行级安全策略，决定这次工具调用返回哪些行和哪些列。被拒绝时表现为针对受限表或列的 Postgres permission-denied 错误，MCP 端点原封不动地把它转发出去。

**审计。** 9. AIDB 把这条 SQL 执行的 OpenTelemetry traces 记录为 `aidb_otel` schema 中的行，立刻就能通过 SQL 查到。

### 两个 Postgres 角色，同一个问题，不同结果

定义两个 agent 登录角色，它们之间只差一个列级 `GRANT`：`mcp_agent_full` 能看到所有列，`mcp_agent_restricted` 能看到除 `customers.ssn` 之外的所有列。

```
CREATE ROLE mcp_agent_full       LOGIN PASSWORD '...';
CREATE ROLE mcp_agent_restricted LOGIN PASSWORD '...';

GRANT USAGE ON SCHEMA c360 TO mcp_agent_full, mcp_agent_restricted;

-- Both roles need aidb_users to list MCP tools
GRANT aidb_users TO mcp_agent_full, mcp_agent_restricted;

-- Full role sees every column
GRANT SELECT ON ALL TABLES IN SCHEMA c360 TO mcp_agent_full;

-- Restricted role sees every table and view, with customers.ssn withheld
GRANT SELECT ON c360.locations, c360.products, c360.purchases, c360.big_spender
  TO mcp_agent_restricted;
GRANT SELECT (cid, first_name, last_name, email, phone, picture, location, full_name)
  ON c360.customers TO mcp_agent_restricted;
```

两个登录角色都需要在 `pg_hba.conf` 里为本地 `edb-endpoints` 的连接路径配上口令认证条目，这一点在[配置你的 agent 角色](https://www.enterprisedb.com/docs/aidb/latest/mcp-endpoint/configuring-agent-roles/)中有说明。让两个角色跑同一个问题会产生不同结果。以 `mcp_agent_restricted` 身份调用的 agent 无法投影 `ssn` 列：它一尝试，Postgres 就返回 `permission denied for column ssn`，MCP 端点原封不动地转发这个错误。于是 agent 回答自己读不到 SSN。在两个角色之间，prompt、工具目录、SemKB 和 agent 代码完全相同，唯一的区别是 AgentCore Identity 在出站 Basic auth 头上注入的那份凭证。

行级筛选遵循同样的模式。在目标表上启用行级安全（RLS），为各个角色挂上 `USING` 策略即可。AIDB MCP 端点看到的行，与该角色在一条直接的 `psql` 连接中看到的行一致。

**关于 AIDB purposes 的说明。** AIDB 还提供了 [purposes](https://www.enterprisedb.com/docs/aidb/latest/governance/)，这是一种策略抽象，把数据库内的 agents（用 `aidb.create_agent` 创建、用 `aidb.agent_converse` 调用的那些）限定在某个具名的 Postgres 角色内。purposes 适用于数据库内 agent 这条路径。本文所用的外部 AgentCore 路径则如前所述，直接在 MCP 端点处通过 Postgres 角色来治理。对外部 MCP agents 的审计，参见 [EDB Agent Governance](https://www.enterprisedb.com/docs/agent-governance/latest/)，它读取同一批 `aidb_otel` spans，并把 agent 会话与策略判定可视化。

**负责任 AI 的考量。** 到此为止展示的治理面控制的是 agent 在数据库层*能执行什么*。把它与模型侧的 [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 配对使用，来约束 agent *被允许生成什么*：针对敏感话题的内容过滤器、禁用话题清单以及 PII 脱敏。这两层互为补充。Postgres `GRANT` 在数据层挡住 agent 读取 SSN；Guardrails 有助于防止 PII 形态的内容从模型回答的其他路径漏出。对于在客户数据上回答业务问题的 agents，两者都是生产环境的控制手段。

## 暴露这一层并运行 agent

启用 AIDB MCP 端点只需要两个 Postgres 参数加一次重启。在 `postgresql.conf` 里设置 `edb.endpoints_mcp_enabled = on`，把 `aidb` 加进 `shared_preload_libraries`，然后重启（[启用端点](https://www.enterprisedb.com/docs/aidb/latest/mcp-endpoint/enabling-the-endpoint/)）。要从 EC2 实例之外访问这个端点，就把 `edb.endpoints_mcp_host` 设成一个非环回地址，例如 `0.0.0.0`。用 `edb.endpoints_mcp_port` 选一个端口（默认是 8765）。再用 `edb.endpoints_mcp_tls_cert` 和 `edb.endpoints_mcp_tls_key` 提供 Transport Layer Security（TLS）证书与密钥这对配置，端点在非环回绑定时会要求它们（[配置端点](https://www.enterprisedb.com/docs/aidb/latest/mcp-endpoint/configuring-the-endpoint/)）。

一个带 HTTPS 监听器和 ACM 证书的 Application Load Balancer 把 `edb-endpoints` 暴露给 AgentCore Gateway。ALB 的 target group 用 HTTPS 连接 EC2 实例上的 8765 端口，且不校验后端证书链，所以在 `edb-endpoints` 上用一张自签名证书就足以应付开发和测试。在生产环境，请用带 [AgentCore Gateway VPC egress](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-vpc-egress.html) 的内部 ALB，把 Gateway 与 ALB 之间的连通性保持在私有网络里。

创建一个带 Cognito 授权器的 AgentCore Gateway，把 ALB 的 URL 注册为一个 MCP server target，并把两份 Postgres 凭证存放在 AgentCore Identity 的凭证提供方中（[凭证提供方参考](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-outbound-credential-provider.html)）。

这个 agent 是一段简短的 Python 脚本。它用 [Strands Agents](https://github.com/strands-agents/sdk-python) 把一个指向最新 Claude Sonnet 的 `BedrockModel` 接上一个 `MCPClient`。`MCPClient` 通过 [streamable HTTP MCP 传输](https://modelcontextprotocol.io/) 连接 Gateway 的 URL，并把 Cognito 的 access token 作为 `Bearer` 头带上。系统 prompt 指示 agent 先调用 `semantic_kb_search` 取得 schema 上下文，传入 `kb_name => 'c360_kb'`，然后再调用 `execute_sql` 运行生成的查询。[带 Strands 的 AgentCore runtime 起步工具包](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-toolkit.html)里有一个把这种形态的 agent 托管到生产环境的完整示例。

我们建议为这个 agent 的系统 prompt 开启 [Amazon Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)。每一次调用都在复用同一段指令和同一份工具列表，而这正是 prompt caching 的用途。

### 查询 2：每个州各有多少 big spender？

agent 通过 `semantic_kb_search` 找到 `big_spender` 视图，因为它的 `COMMENT ON VIEW` 与这个自然语言问题相匹配。业务定义恰好只存在于一处：

```

----------------------+--------------

 ...
```

如果业务方日后把 big spender 重新定义为累计消费超过 $5,000 的客户，这次改动就是一条 `CREATE OR REPLACE VIEW` 语句。下一次 SemKB 刷新后，所有 agent 看到的就是新定义。

### 查询 3：列出 10 位客户以及各自所在的州

state 在 `locations` 里，不在 `customers` 里。这条 join 路径编码在 `customers.location` 外键和那一列的注释中，两者都由 SemKB 建了索引。agent 给出：

SELECT c.cid, c.full_name, l.state
  FROM c360.customers c
  JOIN c360.locations l ON l.id = c.location
 ORDER BY c.cid

### 治理复跑：列出五位客户以及他们的社会保障号

同一个 prompt 跑两次。在 `mcp_agent_full` 之下，agent 返回五行客户记录，`ssn` 的取值填在其中。在 `mcp_agent_restricted` 之下，agent 的工具调用以 Postgres 错误 `permission denied for column ssn` 失败，agent 于是回一句简短的说明：这个调用者访问不到 SSN。这一失败是列级 `GRANT` 强制出来的，不是 prompt 或模型的作用。AIDB 把这条 SQL 执行的 OpenTelemetry trace 记录在 `aidb_otel` 中，所以审查者之后可以查询那条 trace 行，确认这次治理判定。

## 扩展到更多数据源

对于超出运营数据库承载能力的分析负载，[EDB Postgres Analytics Accelerator（PGAA）](https://www.enterprisedb.com/docs/pgaa/latest/) 让 Postgres 可以通过一个 Iceberg REST catalog 读取对象存储里的 Apache Iceberg、Delta Lake 和 Parquet 表。[EDB Postgres AI 分析总览](https://www.enterprisedb.com/docs/edb-postgres-ai/analytics/) 覆盖了端到端的设置。PGAA 表在 Postgres 中就是普通的表，所以同一份 SemKB 描述对分析副本依然有效，agent 的工具目录也不变。

要联邦到外部关系型数据源，Postgres 的 [foreign data wrappers](https://www.postgresql.org/docs/current/ddl-foreign-data.html) 能让一张外部表像本地表一样可访问。两种情况下语义层都不变，因为业务定义、列注释和 semantic aliases 都住在 Postgres 里。

## 部署

这套架构有两种可用的形态。

**自管理，跑在 Amazon EC2 上。** 使用 AWS Marketplace 上的 EDB Postgres AI Agent Factory AMI。VPC、子网、版本节奏以及 EDB Postgres AI 软件升级都由客户自己负责。ALB 与 AgentCore Gateway target 的配置和前面那套架构相比没有变化。

**由 EDB 管理，跑在 Amazon EC2 上。** [EDB Managed Database](https://www.enterprisedb.com/services/managed-database) 是一项由 EDB 专家代客户处理数据库管理的服务。AgentCore 那一侧不变。

## 结论

可靠的 agentic 分析需要三样东西协同工作：一个能规划并生成查询的基础模型，一个给出受治理的业务数据视图的语义层，以及一个托管 agent 并管理身份的 agent 运行时。Amazon Bedrock 提供模型，Amazon Bedrock AgentCore 提供运行时，EDB Postgres AI 提供一个住在运营 Postgres 数据库内部的语义层。业务含义、join 路径和治理都来自 schema 中本来就有的 Postgres 原语。AWS 这一侧与本系列其余几篇相同：AgentCore Gateway、Runtime、Identity、Bedrock 和 CloudWatch。

数据、业务定义和访问规则都住在同一个 Postgres schema 里，所以没有另一个需要保持同步的独立目录。审计也在同一个数据库里：`aidb_otel` 为每次工具调用保存一个 span，就在它所针对的那些数据旁边。

### 从哪里开始

要把这套架构用到你自己的数据上，请依次走这些步骤：

- 挑一个你的 agents 需要实时查询的 Postgres 数据库。范围越窄越好。
- 为 agent 的数据创建一个专门的 schema，并把 `GRANT USAGE` 限定在一个服务角色上。
- 对使用业务语言的列和视图编写 `COMMENT ON` 语句。用 `COMMENT ON VIEW` 语句把业务术语沉淀成视图。
- 用 `aidb.create_semantic_kb` 在该 schema 之上创建 SemKB，取 `auto_processing => 'Live'`（写入量大时取 `Background`）。
- 把反复出现的问题登记为 semantic aliases。
- 启用 AIDB MCP 端点，用带 HTTPS 监听器和 ACM 证书的 ALB 前置它，并把 ALB 的 URL 注册为 AgentCore Gateway 的 MCP server target。
- 让 agent 跑三个真实问题，然后在一个权限更小的角色下复跑其中一个，确认强制执行面端到端可用。
