# 在 Amazon Bedrock AgentCore 中通过自然语言编写 Dogwood 策略

AI agent 可以自动化复杂工作流，但如果缺乏适当管控地使用，可能会采取不符合组织策略或监管约束的行动。为此，我们构建了 [Policy in Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html)，让团队能够实现适用于 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 中所运行 agent 的管控措施。最近，它扩展了新能力，可以强制执行*跨时间*约束 agent 行为的限制，支持速率限制、前置条件、工具调用的顺序编排以及累积效应等策略。这些策略用 [Dogwood](https://github.com/dogwood-policy/dogwood) 表达——一种开源治理语言——并由内置于 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)（Amazon Bedrock AgentCore 的一项能力）的 Dogwood monitor 实时应用到 agent 行为上。

作为本次新发布的一部分，我们扩展了 [Policy Authoring](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-natural-language.html) 的能力。这是一个由 AI 驱动的工具，可把自然语言编写的策略规格文档转换为语法和语义都正确的 Dogwood 形式化规格。借助这项新功能，你可以生成强制执行时间和轨迹约束的策略，调用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 服务来检测自由文本语义中的不当内容，也可以生成对工具输入参数施加限制的策略——后者在上一版 Policy in AgentCore 中就已经提供。无论你的技术背景如何，都可以把用自然语言编写的策略文档直接导入 Amazon Bedrock AgentCore 中的 policy，以保护你已部署的 agentic 系统。

在本文中，我们通过示例演示这项新能力，并就构建自然语言策略时如何运用最佳实践提供指导。

## 自然语言策略到 Dogwood 的自动转换

Dogwood 策略可以完全手工编写，对于少量管控项来说，这是一个完全合理的起点。当你已经有以散文形式写好的规则，眼前的工作只是转录而非设计时，Policy Authoring 的效果最好。你可以提供一份包含清晰规则集的文档：策略列表、操作规程中的规则章节，或是一段描述允许或受限行为的文字。Authoring 是翻译器而不是摘要器，因此如果文档把规则与理由、背景和评述交织在一起，最好先把它精简为纯粹的规则。

## 示例场景

为了让示例具体一些，我们设想一家零售银行的客户服务 agent。它负责核验来电者、提交争议、针对有争议的费用退款、在客户自己的账户之间转账，还可以请主管批准某笔费用。它的工具通过 AgentCore Gateway 访问，每个工具都接受少量参数并返回结果：

| **工具** | **用途** | **输入** | **输出** |
| --- | --- | --- | --- |
| `verify_identity` | 对来电者进行 step-up 身份验证 | `{ account: String }` | `{ verified: Bool }` |
| `initiate_transfer` | 在客户自己的账户之间转账 | `{ account: String, dest_account: String, amount: Long }` | `{ confirmation: String }` |
| `issue_refund` | 撤销有争议的费用 | `{ account: String, charge_id: String, amount: Long }` | `{ refunded: Bool }` |
| `file_dispute` | 创建争议案件 | `{ account: String, description: String }` | `{ case_id: String }` |
| `request_approval` | 请主管批准一笔费用 | `{ charge_id: String }` | `{ approved: Bool }` |

除策略文档外，Authoring 还会接收一个携带这些信息的 schema：工具名称、它们接受的参数以及返回的值。该 schema 由 agent 的 Model Context Protocol（MCP）工具清单生成，因此产出的策略引用的就是 agent 实际调用的名称。例如，生成策略中的 `context.input.amount` 就是上表中的 `amount` 参数。Authoring 还会获得可用的 Amazon Bedrock Guardrails 检查集，以及策略允许引用的身份声明。

该银行的合规团队以书面文档的形式维护其管控措施，格式与其用于人类员工的格式相同。下面的规则均摘自该文档，每条规则后面都跟着 Policy Authoring 为它生成的 Dogwood 策略。有两条约定可以让输出更易读。Dogwood 采用默认拒绝（default-deny），且 `forbid` 优先于 `permit`，因此授予某项能力的规则会变成带有条件的 `permit`，而限制或封顶某事的规则会变成 `forbid`。条件既可以检查正在决策的调用，也可以检查同一会话中已经发生的事情。下面的示例两者兼有。

## 策略转换示例

以下示例展示 autoformalizer 如何把自然语言策略转换为 Dogwood 公式。

### 对工具参数的约束

*退款只能在营业时间内发放，定义为 UTC 时间上午 9:00 至下午 5:00，且金额不得超过 2,500 美元。*

```
permit ( principal, action == AgentCore::Action::"issue_refund", resource )
when { context.system.now.toTime() >= duration("9h")
    && context.system.now.toTime() <= duration("17h") }
when { context.input.amount <= 2500 };
```

一句话包含两个独立要求，变成了一条带有两个条件的策略，退款要被允许必须同时满足这两个条件。`context.input.amount` 是 agent 发起 `issue_refund` 调用时的 amount 参数，按工具声明的单位进行比较。文档中的“$2,500”和工具的 `amount` 必须在这个单位上保持一致。时间比较读取的是调用被决策那一刻的时钟，两个条件都不依赖于 agent 之前做过的任何事情。有关 `duration` 等基于时间的函数的更多细节，请参阅[基于时间的策略支持](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-time-based.html)。

### 必需的前置步骤

*除非来电者的身份在之前 15 分钟内已针对同一账户完成验证，否则不得发起转账。*

```
permit ( principal, action == AgentCore::Action::"initiate_transfer", resource )
when temporal {
    formerly within 15m AgentCore::Action::"verify_identity"::response{
        input.account:   context.input.account,
        output.verified: true
    }
};
```

这条规则无法仅凭转账请求来判定，因此生成的条件会查看 agent 已经做过的事情。`formerly within 15m` 询问它所描述的事件是否在过去 15 分钟内的某个时刻发生过。这里指的是一次 `verify_identity` 调用的完成（`::response`，即结果，而不是调用被发起），且返回了 `verified: true`。在事件模式中，单独的 `input.account` 指的是那个较早事件中的字段，而 `context.input.account` 指的是正在决策的调用中的字段。把两者设为相等，就精确表达了“同一账户”。对其他账户的验证，或者尝试过但未通过验证的情况，都不满足这条规则。而且由于检查的历史是当前会话的历史，这条规则不需要单独的来电者 ID，这也正是 `verify_identity` 只接受账户参数的原因。

### 累积上限

*如果过去 12 小时内的转账总额将超过 50,000 美元，则阻止该转账。*

```
forbid ( principal, action == AgentCore::Action::"initiate_transfer", resource )
when temporal {
    exists (total: Long). (
        (sum a for (a: Long), (t: Timepoint). where (
            formerly within 12h (
                AgentCore::Action::"initiate_transfer"::request{ input.amount: a } && tp(t)
            )
        )) == total && total > 50000
    )
};
```

这里，历史不是被搜索，而是被累加。该策略取出过去 12 小时内每笔转账的 amount 参数，把它们相加，如果累计总额超过 50,000 美元就拒绝当前调用。该时间窗口内的每一笔转账单独看可能都很小、很平常，但这条条件约束的是它们的总和。还要注意文档留下的开放点：它说的是“已转账”，但没有说明被阻止或失败的尝试是否计入。转换结果对 `::request` 事件求和，也就是 agent 尝试过的每一次转账，对于上限来说这是更安全的解读。不过，在文档中明确写出来就可以免去猜测，这正是后面第一条最佳实践的主题。

### 速率限制

*该 agent 在一小时内针对同一账户尝试退款不得超过三次。*

```
forbid ( principal, action == AgentCore::Action::"issue_refund", resource )
when temporal {
    exists (n: Long). (
        (count for (t: Timepoint). where (
            formerly within 1h (
                AgentCore::Action::"issue_refund"::request{ input.account: context.input.account } && tp(t)
            )
        )) == n && n > 3
    )
};
```

这条策略与上一条结构相同，只是计数事件而不是对某个字段求和。计数范围限定为针对所考虑调用中指定账户的退款，并且包含该调用本身，因此一小时内第四次尝试才会被拒绝。这条规则明确说了“尝试”，所以与上一条不同，没有什么需要推断的：被拒绝或失败的退款仍然计入限额。

### 对自由文本的检查

*拒绝任何描述中包含社会安全号码（Social Security number）的争议提交。*

```
forbid ( principal, action == AgentCore::Action::"file_dispute", resource )
when {
    BedrockGuardrails::SensitiveInformation(["US_SOCIAL_SECURITY_NUMBER"], [context.input.description])
        .maxConfidenceScore().greaterThanOrEqual(decimal("0.2"))
};
```

有些规则针对的是自由文本的语义，而不是结构化值，任何字段比较都无法判定它们。对于这类规则，生成的策略会在规则指定的字段上内联调用 Amazon Bedrock Guardrails 检查，并把报告的置信度与阈值比较。这条规则没有给出阈值，因此转换结果采用该检查的默认值。如果文档确实给出了阈值（例如“高置信度”或某个具体数字），则会沿用该值。

### 结合多种条件的规则

*超过 500 美元的退款需要主管对该笔费用予以批准，且批准记录须在过去 30 分钟内。*

```
forbid ( principal, action == AgentCore::Action::"issue_refund", resource )
when { context.input.amount > 500 }
unless temporal {
    formerly within 30m AgentCore::Action::"request_approval"::response{
        input.charge_id: context.input.charge_id,
        output.approved: true
    }
};
```

这句话包含两个部分，检查方式截然不同：一是对当前调用某个参数的阈值判断，二是对已经发生事情的条件判断。两个子句都放在同一条策略里。这条规则收窄了一项既有许可：它拒绝超过 500 美元的退款，而 `unless` 子句则是例外——当存在匹配的批准记录时解除拒绝。和前面那个前置条件的例子一样，正是基于 `charge_id` 的关联，防止了对一笔费用的批准被拿去授权另一笔费用的退款。

## 最佳实践

无论实现者是人类用户还是自主 agent，清晰、无歧义的策略都会带来更可预测的行为和更少的错误。同时，这也能提升前面介绍的自然语言到 Dogwood 编写方案的效果。接下来，我们回顾一些构建自然语言策略的技巧和最佳实践。

- **说明你指的是尝试还是结果**。“转账之后”是有歧义的。“转账成功之后”则没有。尝试指的是 agent 发起的任何调用，包括被拒绝或失败的调用。只有完成的调用才会携带工具返回的值。速率限制和累积上限通常针对尝试，前置条件和顺序规则则针对结果。
- **写明时间窗口**。“最近”无法转换。“过去 30 分钟内”则可以。时间窗口是从正在决策的调用向前回溯的，因此如果某条规则打算按日历边界重置，而不是随时间滑动，就要明确写出来，因为那需要另一种管控方式。
- **指明规则以什么为键**。“每小时转账不超过三次”没有说明是谁的三次：是这位来电者的三次，还是针对这个账户的三次？两者都可以表达，但它们是不同的策略，而这句话两者都没选。凡是规则涉及计数、求和或关联的地方，都要指明把事件串在一起的字段。
- **给出阈值及其边界**。“超过三次”和“至少三次”相差一个动作，而那往往正是规则想要阻止的那个动作。内容检查的置信度水平也是如此。
- **审阅生成的 Dogwood 策略是否正确**。每条 Dogwood 策略都会连同它所来自的句子一起返回，方便你对照阅读。验证可以确认一条策略格式良好、并且锚定在正确的 schema 上，但它无法确认这条策略是否表达了作者的本意。这个判断仍由文档的所有者来做。

## 了解哪些内容无法强制执行

虽然编写服务可以过滤并标出与 Policy in AgentCore 的强制执行不兼容的策略，你也应当了解一些常见问题。

- **它不是关于某个动作的规则**。“agent 应始终以客户的最佳财务利益行事，并运用良好的专业判断。”这里没有任何针对动作、字段或 principal 的条件。这是一项真实的要求，但它属于 agent 的指令、评估和训练，而不属于授权引擎。
- **它要求的是动作，而不是裁决**。“当争议描述中包含社会安全号码时，在存储备注之前将其隐去。”策略引擎只能允许或拒绝调用，不能修改调用。与之相邻的那条拒绝包含社会安全号码的提交规则是可以表达的，并且出现在前面的示例中。信息隐去是另一种管控，在流水线的不同环节施加。
- **它超出了该语言的表达能力**。“拒绝在周末和美国联邦银行假日进行电汇。”Dogwood 的日期和时间支持涵盖时间点、偏移量和时间差。它没有星期几访问器，也没有假日日历。[Dogwood 语言](https://github.com/dogwood-policy/dogwood/tree/main/dogwood-docs/guide)指南详细列出了可用的构造；当某条规则被策略编写服务搁置时，值得通读该指南，既能确认缺失之处，也能看看是否有相近的表述方式受支持。
- **它超出了强制执行范围**。“客户每天最多可发起十笔转账，按该客户所有并发会话合计计算。”强制执行评估的是单个会话内的轨迹，因此跨会话汇总的上限无法通过换一种表述来挽回。

在这些情况下，有用的输出不是一条策略，而是一个标签，表明它无法转换为 Dogwood——这提示你考虑其他方案：重写该规则、把它移到另一种管控方式，或者接受它仍作为一个人工流程存在。

## 策略编写的工作原理

自动形式化流水线分四步运行。首先是*分解*文档。为读者写的规则往往是复合的：一个编号条款经常包含若干独立义务，一句话有时也承载两个，就像前面那个营业时间的例子。分解把它们拆成原子规则，每条都是关于某个特定工具或一组工具的陈述，可以单独强制执行。然后每条规则被*路由*。一条规则要么能用 Dogwood 及其组成 monitor 表达，要么不能；不能的那些会被搁置而不是转换，通常是因为上一节提到的四个原因。在尝试转换之前先在这里过滤，可以避免一条无法表达的规则变成一条校验通过却执行了错误行为的策略。剩下的规则被*自动形式化*为 Dogwood，并锚定在随文档一起提供的工具 schema 上。最后，每条候选策略都会使用与该开源语言一同发布的 [Dogwood 命令行工具](https://github.com/dogwood-policy/dogwood/tree/main/dogwood-cli)进行*验证*。这是流水线中不涉及判断的部分：对于一条策略能否解析、其中每个名称是否存在于 schema 中，编译器是精确且确定的权威。如果候选策略被拒绝，其诊断信息会被回传，并在考虑这些错误的情况下重新转换该规则，重复有限的轮数。

产出是两个集合：一是通过语法与环境 schema 兼容性验证的策略，连同生成它们的原子自然语言规则；二是被搁置的原子自然语言规则。

## 结论

本文演示了 Policy Authoring 如何把书面策略文档转换为 Dogwood 策略。你已经看到了涵盖工具参数约束、前置条件、累积上限、速率限制以及自由内容检查的转换示例。同时，你也回顾了让自然语言规则易于转换的特性：明确的时间窗口、指明的主体、清晰的阈值，以及在尝试与结果之间做出清楚选择。Dogwood 可以直接编写，喜欢直接使用该语言的团队尽可以继续这么做。Authoring 面向的是规则已经以散文形式存在的常见情况，用于缩短从你已经在维护的文档到一组可审阅、可部署策略之间的路径。

要开始使用，请参阅 [Policy in AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html)了解如何创建策略引擎并从文档编写策略；如果你想自己阅读或扩展生成的策略，请参阅 [Dogwood 语言指南](https://github.com/dogwood-policy/dogwood/tree/main/dogwood-docs/guide)。要进一步了解这些策略在运行时如何被解释和强制执行，请参阅[使用 Amazon Bedrock AgentCore 中的时间策略保护 AI agent](https://aws.amazon.com/blogs/machine-learning/securing-ai-agents-with-temporal-policies-in-amazon-bedrock-agentcore/)和[Dogwood 简介：面向 AI agent 的运行时验证](https://aws.amazon.com/blogs/opensource/introducing-dogwood-runtime-verification-for-ai-agents/)。
