# AWS 上生成式 AI 应用的多 LLM 路由策略

在构建生成式 AI 应用时，组织越来越多地使用多个 large language model（LLM）。尽管单个 LLM 可能非常强大，但它未必能最优地覆盖广泛的使用场景，也未必能满足多样化的性能要求。multi-LLM 方法使组织能够为每项任务有效选择正确的模型、适应不同领域，并针对特定的成本、延迟或质量需求进行优化。这一策略带来更健壮、更通用、更高效的应用，更好地服务于多样化的用户需求和业务目标。

部署 multi-LLM 应用伴随着一项挑战：把每个用户 prompt 路由到适合预期任务的 LLM。路由逻辑必须准确解释 prompt 并将其映射到某个预定义任务，然后将其导向该任务所分配的 LLM。在本文中，我们概述常见的 multi-LLM 应用。随后我们探讨在这些应用中实现有效 multi-LLM 路由的策略，讨论影响此类策略选择与实施的关键因素。最后，我们提供示例实现，你可以将其作为自己 multi-LLM 路由部署的起点。

## 常见 multi-LLM 应用概述

以下是你在应用中可能选择使用 multi-LLM 方法的一些常见场景：

- **多种任务类型 **——许多使用场景需要在同一应用内处理不同的任务类型。例如，营销内容创作应用为了产出高质量、个性化的内容，可能需要执行文本生成、文本摘要、情感分析和信息抽取等任务类型。每种不同的任务类型很可能需要一个独立的 LLM，该 LLM 还可能使用自定义数据进行了微调。
- **多种任务复杂度 **——有些应用被设计为处理单一任务类型，例如文本摘要或问答。然而，它们必须能够在同一任务类型内响应复杂度各异的用户查询。例如，设想一个面向学术研究和文献综述的文本摘要 AI 助手。有些用户查询可能相对直接，只是要求应用总结一篇短文章的核心观点和结论。这类查询可以由简单、成本更低的模型有效处理。相比之下，更复杂的问题可能要求应用对研究结果进行更深入的分析、比较和评估，以总结一篇冗长的学位论文。这类查询更适合由具备更强推理能力的更高级模型来处理。
- **多个任务领域 **——某些应用需要为跨多个专业领域的用户提供服务。一个例子是面向企业业务运营的虚拟助手。这样的虚拟助手应支持财务、法务、人力资源和运营等各种业务职能的用户。为了应对如此广泛的专业领域，虚拟助手需要使用在不同领域专属数据集上微调过的不同 LLM。
- **带租户分层的软件即服务（SaaS）应用 **——SaaS 应用通常被设计为针对不同客户画像（customer profile）提供不同的定价和体验，这些画像被称为[层级](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/tenant-tiers.html)。通过使用针对每个层级定制（tailored）的不同 LLM，SaaS 应用可以提供与其多样化客户群的不同需求和预算相匹配的能力。例如，设想一个为不同规模企业设计的 AI 驱动的法律文档分析系统，它提供两个主要订阅层级：Basic 和 Pro。Basic 层级会使用一个更小、更轻量的 LLM，适合处理直接的任务，例如执行简单的文档搜索或为不太复杂的法律文档生成摘要。而 Pro 层级则需要一个高度定制化的 LLM，该 LLM 已在特定数据和术语上训练过，使其能够协助起草复杂法律文档这类错综复杂的任务。

## multi-LLM 路由策略

在本节中，我们探讨把请求路由到不同 LLM 的两种主要方法：静态路由和动态路由。

### 静态路由

把用户 prompt 导向合适 LLM 的一种有效策略，是在同一界面内实现彼此不同的 [UI 组件](https://ui.docs.amplify.aws/)，或为特定任务定制独立界面。例如，面向电商公司的 AI 驱动生产力工具可以为不同角色提供专用界面，例如内容营销人员和业务分析师。内容营销界面包含两个主要 UI 组件：一个用于创建社交媒体帖子、电子邮件和博客的文本生成模块，以及一个从客户评论中识别最相关关键词和短语以改进内容策略的洞察抽取模块。与此同时，业务分析界面则会聚焦于文本摘要，用于分析各类业务文档。下图展示了这一点。

[![multi-LLM 静态 prompt 路由](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/04/07/ml-17345-multi-llm-static-routing-004.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/04/07/ml-17345-multi-llm-static-routing-004.png)

对于用户体验支持为每项任务设置独立 UI 组件的应用，这种方法效果很好。它还允许灵活、模块化的设计，新的 LLM 可以快速接入某个 UI 组件或从中换出，而不会破坏整体系统。然而，这种方法的静态特性意味着应用可能难以适应不断演进的用户需求。新增一项任务不仅需要选择和集成新模型，还需要开发新的 UI 组件。

### 动态路由

在某些使用场景中，例如虚拟助手和多用途聊天机器人，用户 prompt 通常通过单一 UI 组件进入应用。例如，设想一个处理三类任务的客户服务 AI 助手：技术支持、账单支持和售前支持。这些任务各自都需要自己的定制 LLM 来提供恰当的响应。在这种场景下，你需要实现一个动态路由层，拦截每个入站请求并将其导向下游 LLM，该 LLM 最适合处理该 prompt 中的预期任务。下图展示了这一点。

[![multi-LLM 动态 prompt 路由](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/04/03/ml-17345-multi-llm-dynamic-routing.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/04/03/ml-17345-multi-llm-dynamic-routing.png)

在本节中，我们讨论实现这一动态路由层的常见方法：LLM 辅助路由、语义路由和混合方法。

#### LLM 辅助路由

这种方法在应用的入口点使用一个分类器 LLM 来做出路由决策。LLM 理解复杂模式和上下文细微差别的能力，使这种方法非常适合需要在任务类型、复杂度层级或领域之间做细粒度分类的应用。然而，这种方法存在取舍。尽管它提供了精密的路由能力，但也引入了额外的成本和延迟。此外，随着应用演进，保持分类器 LLM 的相关性可能颇为费力。可能需要进行审慎的模型选择、微调、配置和测试，以在延迟和成本的影响与期望的分类准确率之间取得平衡。

#### 语义路由

这种方法使用[语义搜索](https://en.wikipedia.org/wiki/Semantic_search)作为在 multi-LLM 系统中使用分类器 LLM 进行 prompt 分类和路由的替代方案。语义搜索使用[嵌入](https://aws.amazon.com/what-is/embeddings-in-machine-learning/)把 prompt 表示为数值向量。系统随后通过度量用户 prompt 的嵌入与一组参考 prompt 的嵌入之间的相似度来做出路由决策，每个参考 prompt 代表一个不同的任务类别。用户 prompt 随后被路由到与最接近匹配的参考 prompt 所属任务类别相关联的 LLM。

尽管语义搜索不像分类器 LLM 那样提供显式分类，但它擅长识别宽泛的相似性，并能有效处理 prompt 措辞上的变化。这使它特别适合那些可以基于 prompt 的粗粒度分类（例如任务领域分类）来进行路由的应用。它在任务类别数量众多或经常引入新领域的场景中也表现出色，因为它只需向参考 prompt 集合中添加新的 prompt 就能快速适应更新。

语义路由提供若干优势，例如通过在向量数据库中快速执行相似度搜索而获得的效率，以及可容纳大量任务类别和下游 LLM 的可扩展性。然而，它也存在一些取舍。参考 prompt 集合对所有可能的任务类别具有足够的覆盖度，对准确路由至关重要。此外，由向量数据库和嵌入 LLM 等额外组件带来的系统复杂度上升，可能影响整体性能和可维护性。需要审慎的设计和持续的维护来应对这些挑战，并充分发挥语义路由方法的优势。

#### 混合方法

在某些场景中，结合两种技术的混合方法也可能被证明非常有效。例如，在任务类别或领域数量众多的应用中，你可以使用语义搜索进行初始的宽泛分类或领域匹配，然后使用分类器 LLM 在这些宽泛类别内做更细粒度的分类。这种初始过滤使你能够为最终路由决策使用更简单、更聚焦的分类器 LLM。

例如，设想一个处理各种不同咨询的客户服务 AI 助手。在这种情境下，语义路由可以先按用户 prompt 把请求路由到相应部门——无论是账单、技术支持还是销售。在确定宽泛类别之后，再由该特定部门的专用分类器 LLM 接手。这个专门的 LLM 可以在其领域内的细微差别上训练，随后能够判定任务复杂度或紧迫性等关键因素。基于这种细粒度分析，prompt 随后被路由到最合适的 LLM，或在必要时升级给人工坐席。

这种混合方法将语义搜索的可扩展性与灵活性，与分类器 LLM 的精确性和上下文感知能力结合起来。其结果是健壮、高效且高度准确的路由机制，能够适应现代 multi-LLM 应用的复杂性与多样需求。

## 动态路由的实现

在本节中，我们探讨在 AWS 上实现动态路由的不同方法，既涵盖内置路由功能，也涵盖可作为构建自有方案起点的自定义解决方案。

### 使用 Amazon Bedrock 的智能 prompt 路由

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 是一项完全托管的服务，通过 API 提供来自领先 AI 初创公司和 Amazon 的高性能 LLM 及其他基础模型（FM），因此你可以从广泛的 FM 中选择最适合自己的使用场景的模型。借助 Amazon Bedrock 的无服务器体验，你可以快速上手、用自己的数据私密地定制 FM，并使用 AWS 工具将其集成和部署到你的应用中，而无需管理基础设施。

如果你正在用 Amazon Bedrock 上的 LLM 构建应用，并且需要一个具备直接路由能力的完全托管解决方案，[Amazon Bedrock Intelligent Prompt Routing](https://aws.amazon.com/bedrock/intelligent-prompt-routing/) 提供了一种高效的动态路由实现方式。Amazon Bedrock 的这一功能提供单一无服务器端点，可在同一模型家族内的不同 LLM 之间高效路由请求。它使用先进的 prompt 匹配和模型理解技术，为每个请求预测每个模型的性能。Amazon Bedrock 随后动态地把每个请求路由到它预测最有可能以最低成本给出期望响应的模型。Intelligent Prompt Routing 可以在不牺牲准确率的前提下将成本降低最多 30%。截至本文撰写时，Amazon Bedrock 支持在 [Anthropic’s Claude](https://aws.amazon.com/bedrock/claude/) 和 [Meta’s Llama](https://aws.amazon.com/bedrock/llama/) 模型家族内进行路由。例如，Amazon Bedrock 可以根据 prompt 的复杂度，在 Anthropic’s Claude 3.5 Sonnet 和 Claude 3 Haiku 之间智能地路由请求，如下图所示。同样，Amazon Bedrock 可以在 Meta’s Llama 3.1 70B 和 8B 之间路由请求。

[![Amazon Bedrock Intelligent Prompt Routing](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/04/03/ml-17345-bedrock-intelligent-prompt-routing-003.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/04/03/ml-17345-bedrock-intelligent-prompt-routing-003.png)

这一架构工作流包含以下步骤：

- 用户通过 Web 或移动应用提交一个问题。
- Anthropic’s prompt router 预测每个下游 LLM 的性能，选择它预测能提供响应质量与成本最佳组合的模型。
- Amazon Bedrock 把请求路由到选中的 LLM，并返回响应以及关于该模型的信息。

关于 Amazon Bedrock 上 Intelligent Prompt Routing 的详细实施指南和示例，请参阅[使用 Amazon Bedrock Intelligent Prompt Routing 和 prompt caching 降低成本和延迟](https://aws.amazon.com/blogs/aws/reduce-costs-and-latency-with-amazon-bedrock-intelligent-prompt-routing-and-prompt-caching-preview/)。

### 自定义 prompt 路由

如果你的 LLM 托管在 Amazon Bedrock 之外，例如托管在 [Amazon SageMaker](https://aws.amazon.com/sagemaker/) 或 [Amazon Elastic Kubernetes Service](https://aws.amazon.com/eks/)（Amazon EKS）上，或者你需要对路由进行定制，你就需要开发自定义路由解决方案。

本节提供 LLM 辅助路由和语义路由的示例实现。我们讨论该方案的运作机制、关键设计决策，以及如何将其作为开发自有自定义路由解决方案的基础。有关每种路由解决方案的详细部署说明，请参阅 [GitHub 仓库](https://github.com/aws-samples/sample-multi-llm-dynamic-prompt-routing)。该仓库中提供的代码旨在用于开发环境。在把所提供的任何解决方案迁移到生产之前，我们建议遵循 [AWS Well-Architected Framework](https://aws.amazon.com/architecture/well-architected)。

#### LLM 辅助路由

在这个解决方案中，我们演示一个教育辅导助手，它在历史和数学两个领域帮助学生。为实现路由层，应用使用 Amazon Bedrock 上的 [Amazon Titan Text G1 – Express 模型](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-text-models.html#titantx-express)，按问题主题把它们分类到历史或数学。历史问题被路由到更具成本效益且更快的 LLM，例如 Amazon Bedrock 上的 [Anthropic’s Claude 3 Haiku](https://aws.amazon.com/bedrock/claude/)。数学问题由更强大的 LLM 处理，例如 Amazon Bedrock 上的 [Anthropic’s Claude 3.5 Sonnet](https://aws.amazon.com/bedrock/claude/)，它更适合复杂问题求解、深入解释和多步推理。如果分类器 LLM 不确定某个问题属于历史还是数学类别，它会默认将其分类为数学。

下图展示了该系统的架构。本演示中使用 Amazon Bedrock 上的 Amazon Titan 和 Anthropic 模型是可选的。你可以用部署在 Amazon Bedrock 上或其之外的其他模型来替代它们。

[![LLM 辅助 prompt 路由](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/04/03/ml-17345-llm-assisted-routing-004.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/04/03/ml-17345-llm-assisted-routing-004.png)

这一架构工作流包含以下步骤：

- 用户通过 Web 或移动应用提交一个问题，该应用把查询转发到 [Amazon API Gateway](https://aws.amazon.com/api-gateway)。
- API Gateway 收到请求后，会触发一个 [AWS Lambda](https://aws.amazon.com/lambda/)
- 该 Lambda 函数把问题发送给分类器 LLM，以判定它是历史问题还是数学问题。
- 根据分类器 LLM 的决定，Lambda 函数把问题路由到相应的下游 LLM，由其生成答案并返回给用户。

按照 [GitHub 仓库](https://github.com/aws-samples/sample-multi-llm-dynamic-prompt-routing/tree/main/llm-assisted-router) 中的部署步骤，为 LLM 辅助路由创建必要的基础设施，并运行测试以生成响应。以下输出展示了对问题“What year did World War II end?”的响应。

```

  "answer": "World War II ended in 1945.",
  "question_classification": "history",
  "classifier_LLM": "amazon.titan-text-express-v1",
  "classification_time": 0.5374360084533691,
  "answerer_LLM": "anthropic.claude-3-haiku-20240307-v1:0",
  "answer_generation_time": 0.2473313808441162,
  "total_response_time": 0.7847845554351807
}
```

该问题被正确地分类为历史问题，分类过程耗时约 0.53 秒。随后该问题被路由到 Anthropic’s Claude 3 Haiku 并由其作答，耗时约 0.25 秒。总共大约用了 0.78 秒收到响应。

#### 语义路由

在这个解决方案中，我们聚焦与 LLM 辅助路由相同的教育辅导助手用例。为实现路由层，你首先需要创建一组参考 prompt，代表你打算覆盖的历史和数学主题的完整谱系。这个参考集合构成语义匹配过程的基础，使应用能够把入站查询正确归类。作为示例说明，我们提供了一个样例参考集合，为历史和数学两个主题各包含五个问题。在真实世界的实现中，你可能需要大得多、也多样得多的参考问题集合，才能获得健壮的路由性能。

```
History:
    - What were the main causes of World War I?
    - What region of the United States saw the largest economic growth as a result of the Industrial Revolution?
    - Who was the first man on the moon?
    - What country gifted the United States with the Statue of Liberty?
    - What major event sparked the beginning of the Great Depression in 1929?
Math:
    - Solve the quadratic equation: 2x^2 + 5x - 12 = 0.
    - Find the derivative of f(x) = 3x^4 - 2x^3 + 5x - 7.
    - In a right triangle, if one angle is 30° and the hypotenuse is 10 cm, find the lengths of the other two sides.
    - Determine the area of the region bounded by y = x^2, y = 4, and the y-axis.
    - If log_2(x) + log_2(y) = 5 and xy = 64, find the values of x and y.
```

你可以使用 Amazon Bedrock 上的 [Amazon Titan Text Embeddings V2](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html) 模型把参考集合中的问题转换为嵌入。你可以在 [GitHub 仓库](https://github.com/aws-samples/sample-multi-llm-dynamic-prompt-routing/tree/main/generate-faiss-reference-index) 中找到这一转换的代码。这些嵌入随后被保存为内存中的 [FAISS](https://github.com/facebookresearch/faiss) 向量存储内的参考索引，该向量存储以 Lambda 层的形式部署。

下图展示了该系统的架构。本演示中使用 Amazon Bedrock 上的 Amazon Titan 和 Anthropic 模型是可选的。你可以用部署在 Amazon Bedrock 上或其之外的其他模型来替代它们。

[![语义 prompt 路由](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/04/03/ml-17345-semantic-routing-004.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/04/03/ml-17345-semantic-routing-004.png)

这一架构工作流包含以下步骤：

- 用户通过 Web 或移动应用提交一个问题，该应用把查询转发到 API Gateway。
- API Gateway 收到请求后，会触发一个 Lambda 函数。
- 该 Lambda 函数把问题发送给 Amazon Titan Text Embeddings V2 模型，将其转换为嵌入。随后它在 FAISS 索引上执行相似度搜索，以在参考索引中找到最接近匹配的问题，并返回相应的类别标签。
- 根据检索到的类别，Lambda 函数把问题路由到相应的下游 LLM，由其生成答案并返回给用户。

按照 [GitHub 仓库](https://github.com/aws-samples/sample-multi-llm-dynamic-prompt-routing/tree/main/semantic-router) 中的部署步骤，为语义路由创建必要的基础设施，并运行测试以生成响应。以下输出展示了对问题“What year did World War II end?”的响应。

#### 自定义 prompt 路由的补充考量

所提供的解决方案在 LLM 辅助路由中使用示例 LLM 进行分类，在语义路由中使用示例 LLM 进行文本嵌入。然而，你很可能需要评估多个 LLM，才能选出最适合自己特定使用场景的 LLM。使用这些 LLM 确实会带来额外成本和延迟。因此，把查询动态路由到合适 LLM 所带来的收益能否证明实现自定义 prompt 路由系统所引入的开销是值得的，这一点至关重要。

对某些使用场景，尤其是需要专业知识（specialized domain knowledge）的场景，可以考虑用你自己的专有数据微调 LLM 辅助路由中的分类器 LLM 和语义路由中的[嵌入 LLM](https://aws.amazon.com/blogs/machine-learning/improve-rag-accuracy-with-fine-tuned-embedding-models-on-amazon-sagemaker/)。这可以提升分类的质量和准确率，从而带来更好的路由决策。

此外，语义路由解决方案使用 FAISS 作为内存中的向量数据库进行相似度搜索。然而，你可能需要评估 [AWS 上的其他向量数据库](https://aws.amazon.com/what-is/vector-databases/#seo-faq-pairs)，看哪一个在规模、延迟和成本要求方面更契合你的使用场景。持续从用户那里收集 prompt 并迭代参考 prompt 集合也很重要。这有助于确保它反映用户实际提出的问题类型，从而随着时间推移提高相似度搜索分类的准确率。

#### 自定义 prompt 路由的成本分析

本节以我们的教育辅导助手应用的示例流量场景为例，分析两种自定义 prompt 路由解决方案的实现成本和潜在节省。

我们的计算基于以下假设：

- 应用部署在 US East (N. Virginia) AWS 区域，每天收到 50,000 个历史问题和 50,000 个数学问题。
- 对于 LLM 辅助路由，分类器 LLM 对每个问题处理 150 个输入 token 并生成 1 个输出 token。
- 对于语义路由，嵌入 LLM 对每个问题处理 150 个输入 token。
- 作答 LLM 对每个问题处理 150 个输入 token 并生成 300 个输出 token。
- 在 LLM 辅助路由中，Amazon Titan Text G1 – Express 模型执行问题分类，价格为每 1,000 个输入 token $0.0002，输出成本可忽略不计（每个问题 1 个 token）。
- 在语义路由中，Amazon Titan Text Embeddings V2 模型生成问题嵌入，价格为每 1,000 个输入 token $0.00002。
- Anthropic’s Claude 3 Haiku 处理历史问题，价格为每 1,000 个输入 token $0.00025、每 1,000 个输出 token $0.00125。
- Anthropic’s Claude 3.5 Sonnet 回答数学问题，价格为每 1,000 个输入 token $0.003、每 1,000 个输出 token $0.015。
- Lambda 运行时间为每个数学问题 3 秒、每个历史问题 1 秒。
- Lambda 使用 1024 MB 内存和 512 MB 临时存储，API Gateway 配置为 REST API。

下表汇总了两种路由策略下由 LLM 生成答案的成本。

| **问题类型** | **每月输入 token 总数** | **每月输出 token 总数** | **答案** **每月生成成本** |
| --- | --- | --- | --- |
| 历史 | 225,000,000 | 450,000,000 | $618.75 |
| 数学 | 225,000,000 | 450,000,000 | $7425 |

| **问题类型** | **每月输入 token 总数 ** | **分类器 LLM 成本/月** | **Lambda + API Gateway 成本/月** | **嵌入 LLM 成本/月 ** | **Lambda + API Gateway 成本/月** |

第一张表显示，对历史问题使用 Anthropic’s Claude 3 Haiku 每月花费 $618.75，而对数学问题使用 Anthropic’s Claude 3.5 Sonnet 每月花费 $7,425。这表明，与对所有问题都使用更昂贵的模型相比，把问题路由到合适的 LLM 可以实现显著的成本节省。第二张表显示，这些节省伴随着实现成本：LLM 辅助路由为 $188.9/月，语义路由为 $107.9/月，与答案生成成本方面的潜在节省相比相对较小。

### 选择合适的动态路由实现

关于哪种动态路由实现最适合你的使用场景，这一决定在很大程度上取决于三个关键因素：模型托管要求、成本和运维开销，以及对路由逻辑期望的控制程度。下表按这些维度比较了 Amazon Bedrock Intelligent Prompt Routing 和自定义 prompt 路由。

| **设计标准** | **Amazon Bedrock Intelligent Prompt Routing** | **自定义 prompt 路由** |
| --- | --- | --- |
| 模型托管 | 仅限于同一模型家族内由 Amazon Bedrock 托管的模型 | 灵活：可与托管在 Amazon Bedrock 之外的模型配合使用 |
| 运维管理 | 具备内置优化的完全托管服务 | 需要自定义实现和优化 |
| 路由逻辑控制 | 定制能力有限，针对成本和性能有预定义的优化 | 完全控制路由逻辑和优化标准 |

这些方案并非**’**互斥的。你可以实现混合解决方案：对某些工作负载使用 Amazon Bedrock Intelligent Prompt Routing，同时对另一些工作负载保留自定义 prompt 路由——这些工作负载使用托管在 Amazon Bedrock 之外的 LLM，或者需要更多路由逻辑控制。

## 结语

本文探讨了现代 AI 应用中的 multi-LLM 策略，展示了使用多个 LLM 如何增强组织在各类任务和领域中的能力。我们考察了两种主要路由策略：通过使用专用界面实现的静态路由，以及在应用入口点使用 prompt 分类的动态路由。

对于动态路由，我们涵盖了两种自定义 prompt 路由策略——LLM 辅助路由和语义路由，并讨论了各自的示例实现。这些技术使 LLM 能够拥有定制化的路由逻辑，无论其托管平台为何。我们还讨论了 Amazon Bedrock Intelligent Prompt Routing 作为动态路由的另一种实现，它通过在 Amazon Bedrock 内的不同 LLM 之间路由 prompt 来优化响应质量和成本。

尽管这些动态路由方法提供了强大的能力，但它们需要审慎考量工程上的取舍，包括延迟、成本优化和系统维护复杂度。通过理解这些取舍，并结合模型评估、成本分析和领域微调等实施最佳实践，你就可以设计出针对应用需求优化的 multi-LLM 路由解决方案。
