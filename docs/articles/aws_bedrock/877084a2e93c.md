# 在 Amazon Bedrock 上通过 multi-agent 协作解锁复杂问题求解

基于大语言模型（LLM）的 AI agent 已针对特定任务实现了专业化，并展现出强大的问题解决能力。通过组合多个智能专业 agent 的推理能力，multi-agent 协作已成为应对更复杂、多步工作流的一种强大方法。

multi-agent 系统的概念并不完全新颖——它可以追溯到 1980 年代的分布式人工智能研究。然而，随着 LLM 的近期进展，专业 agent 在推理、决策、理解以及通过语言和其他模态进行生成等方面的能力已大幅扩展。例如，单个景点调研 agent 可以执行网络搜索，并根据用户偏好列出可能的目的地。通过构建一个由专业 agent 组成的网络，我们可以组合多位专家 agent 的优势，解决日益复杂的问题，例如在考虑邻近城市天气预报、交通状况、航班与酒店可用性、餐厅评价、景点评分等诸多因素的情况下，创建并优化一份完整的旅行计划。

AWS 的研究团队在构建和评估 multi-agent 协作（multi-agent collaboration，MAC）框架方面做了大量工作，使客户可以在 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 上编排多个 AI agent。本文探讨 multi-agent 协作（MAC）的概念及其优势，以及我们 MAC 框架的关键组件。我们还会深入介绍评估方法，并呈现研究带来的洞察。更多技术细节请参见我们的[技术报告](https://www.amazon.science/publications/towards-effective-genai-multi-agent-collaboration-design-and-evaluation-for-enterprise-applications)。

## multi-agent 系统的优势

multi-agent 协作相比单 agent 方式有几项关键优势，主要源于**分布式问题求解**和**专业化**。

分布式问题求解指的是把复杂任务拆解为更小的子任务，由专业 agent 来处理。通过拆解任务，每个 agent 都可以聚焦问题的特定方面，从而实现更高效、更有效的问题求解。例如，旅行规划问题可以分解为查看天气预报、查找可用酒店、选择最佳路线等子任务。

分布式这一特点也提升了系统的可扩展性与健壮性。当问题范围扩大时，我们只需增加更多 agent 来扩展系统能力，而不是试图优化一个塞满指令和工具的单体 agent。在健壮性方面，系统对故障可以更有韧性，因为多个 agent 能够补偿、甚至可能纠正单个 agent 产生的错误。

专业化让每个 agent 聚焦问题域中的特定区域。例如，在一个从事软件开发的 agent 网络中，协调 agent 可以管理整体规划，编程 agent 可以生成正确的代码和测试用例，代码评审 agent 可以对生成的代码给出建设性反馈。每个 agent 都可以被设计和定制，以擅长某一特定任务。

对构建 agent 的开发者而言，这意味着设计和实现 agent 系统的工作负载可以被有机地分布出去，从而带来更快的开发周期和更好的质量。在企业内部，开发团队通常拥有分布式的专长，这非常适合开发专家 agent。这样的专家 agent 还可以被整个组织内的其他团队复用。

相比之下，开发一个执行所有子任务的单一 agent，会要求该 agent 在高层次上规划问题求解策略，同时还要跟踪低层次细节。例如在旅行规划场景中，该 agent 需要维护一个关于查看天气预报、搜索酒店房间和景点的高层计划，同时还要推理一组酒店搜索 API 的正确用法。这种单 agent 方式很容易让 LLM 产生混乱，因为当不同类型的信息混在一起时，长上下文推理会变得困难。本文后文会提供评估数据点，用以说明 multi-agent 协作的优势。

## 分层式 multi-agent 协作框架

面向 Amazon Bedrock Agents 的 MAC 框架从分层方式出发，未来会扩展到其他机制。该框架由若干关键组件构成，旨在优化性能与效率。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/02/ml-17975-image001.jpg)

下面说明 multi-agent 团队各组件的含义：

- **Supervisor agent** – 这是一个协调专业 agent 网络的 agent。它负责组织整体工作流、拆解任务，并把子任务分配给专家 agent。在我们的框架中，supervisor agent 可以分配和委派任务，但解决问题的责任不会被转移。

- **专家 agent** – 这些是具备特定专长、被设计用于处理给定问题特定方面的 agent。

- **agent 间通信** – 通信是 multi-agent 协作的关键组件，使 agent 能够交换信息并协调行动。我们使用一套标准化通信协议，让 supervisor agent 能向专家 agent 发送消息并接收来自它们的消息。

- **载荷引用（payload referencing）** – 这一机制让 agent 之间能够高效共享大块内容（例如代码片段或详细的旅行行程），显著降低通信开销。agent 无需反复传输大块数据，而是可以用唯一标识符引用此前共享的载荷。这一特性在软件开发等领域尤其有价值。

- **路由模式（routing mode）** – 对于较简单的任务，该模式允许直接路由到专家 agent，跳过完整编排流程，从而提升对延迟敏感应用的效率。

## **对 multi-agent 协作的评估：一种全面的方法**

评估 multi-agent 系统的有效性与效率面临独特挑战，原因有几点：

- 用户可以跟进并向 supervisor agent 提供额外指令。

- 对许多问题而言，存在多种解决方式。

- 任务的成功往往要求 agent 系统正确执行多个子任务。

基于匹配标准答案动作或状态的常规评估方法，往往难以给出直观的结果与洞察。为解决这一问题，我们开发了一个综合框架，基于对人工标注断言的自动判定来计算成功率。我们把这种方法称为“基于断言的基准测试”（assertion-based benchmarking）。其工作方式如下：

- **场景创建** – 我们跨不同领域创建一组多样化的场景，每个场景都带有具体目标，agent 必须达成这些目标才算成功。

- **断言** – 对每个场景，我们人工标注一组断言，只有这些断言全部成立，任务才被视为成功。这些断言同时覆盖用户可观察的结果和系统级行为。

- **agent 与用户模拟** 我们在沙箱环境中模拟 agent 的行为，要求 agent 解决场景中描述的问题。每当需要用户交互时，我们使用一个独立的基于 LLM 的用户模拟器来提供反馈。

- **自动评估** – 我们使用 LLM，基于对话记录自动判定每条断言是否成立。

- **人工评估** – 我们不用 LLM，而是让人基于模拟轨迹直接判定是否成功。

下面是一个用于基于断言的基准测试的场景及其对应断言示例：

- 目标：  用户需要拉斯维加斯明天（2025 年 1 月 5 日）的预期天气情况。用户需要搜索明天上午（2025 年 1 月 5 日）从丹佛国际机场直飞拉斯维加斯麦卡伦国际机场的航班。

- 断言：  用户被告知拉斯维加斯明天（2025 年 1 月 5 日）的天气预报。用户被告知明天（2025 年 1 月 5 日）从丹佛国际机场到拉斯维加斯麦卡伦国际机场的可用直飞航班选项。

`get_tomorrow_weather_by_city` 被触发，以查找拉斯维加斯明天（2025 年 1 月 5 日）的预期天气情况信息。`search_flights` 被触发，以搜索明天（2025 年 1 月 5 日）从丹佛国际机场直飞麦卡伦国际机场的航班。

为更好地模拟用户，我们还会在场景中纳入额外的上下文信息。只有当所有断言都满足时，一条 multi-agent 协作轨迹才会被判为成功。

### 关键指标

我们的评估框架专注于评估跨多个任务的高层成功率，以提供系统性能的整体视图：

**目标成功率（goal success rate，GSR）** – 这是我们的主要成功度量，表示所有断言都被判为成立的场景所占比例。总体的 GSR 会按每个问题域聚合成一个数字。

### 与单 agent 系统比较

我们还在等价设置下与单 agent 方式进行了同等条件的对比。MAC 方式在全部三个领域上达到了 90% 的成功率。相比之下，单 agent 方式在旅行规划、抵押贷款融资和软件开发数据集上的得分分别是 60%、80% 和 53%，明显低于 multi-agent 方式。分析后我们发现，当面对大量工具时，单个 agent 倾向于幻觉出工具调用，并且未能拒绝一些超出范围的请求。这些结果突显了我们的 multi-agent 系统在处理跨多种领域的复杂、真实任务方面的有效性。

为理解自动判定的可靠性，我们对相同场景开展了人工评估，以考察模型判定与人工判定之间的相关性，发现在端到端 GSR 上高度相关。

## 构建 multi-agent 系统的最佳实践

multi-agent 团队的设计会显著影响跨任务问题求解的质量与效率。在我们学到的众多经验中，我们发现精心设计团队层级和 agent 角色至关重要。

**基于性能目标设计 multi-agent 层级**

 在设计 multi-agent 团队的层级时，重要的是考虑用例中不同目标的优先级，例如成功率、延迟和健壮性。例如，如果用例是一个对延迟敏感的面向客户的应用，那么在层级中纳入过多层的 agent 可能并不理想，因为通过多层三级 agent 路由请求会增加不必要的延迟。同样，为优化延迟，最好避免功能重叠的 agent，那会引入低效并拖慢决策。

**清晰定义 agent 角色**

 每个 agent 都必须有界定明确的专长领域。在 Amazon Bedrock Agents 上，这可以通过配置 multi-agent 协作时的协作者指令（collaborator instructions）来实现。这些指令应以清晰、简洁的方式撰写，以尽量减少歧义。此外，多个 agent 的协作者指令之间不应存在混淆，因为那会导致通信低效和错误。

下面是一条清晰、详细的指令：

```
Trigger this agent for 1) searching for hotels in a given location, 2) checking availability of one or multiple hotels, 3) checking amenities of hotels, 4) asking for price quote of one or multiple hotels, and 5) answering questions of check-in/check-out time and cancellation policy of specific hotels.
```

下面这条指令过于简略，使其含义不清且存在歧义。

```
Trigger this agent for helping with accommodation.
```

第二个不清晰的示例，在涉及多个专家 agent 时会导致混乱并降低协作效率。由于该指令没有明确界定酒店专家 agent 的能力，即使用户查询超出范围，supervisor agent 也可能过度沟通。

## 结语

multi-agent 系统代表了应对复杂现实问题的一种强大范式。通过使用多个专业 agent 的集体能力，我们证明这类系统可以在广泛的领域取得令人印象深刻的结果，并优于单 agent 方式。

multi-agent 协作为开发者提供了一个框架，用以组合众多由 LLM 驱动的 AI agent 的推理能力。随着我们不断推进可能性的边界，可以预期会出现更加创新、更加复杂的应用，例如由 agent 网络协同创建软件或生成财务分析报告。在研究层面，重要的是探索不同的协作模式——包括合作性与竞争性交互——将如何涌现并应用于真实场景。
