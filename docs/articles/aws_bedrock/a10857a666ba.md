并发扫描（concurrency sweep）通过找到那个在把延迟保持在可接受范围内时最大化性价比的实例类型和服务配置，帮你合理配置一个生成式 AI 端点。没有一套系统化的方法，合理配置就意味着部署、手动负载测试、调整、再重复，直到那些数字看起来可接受。在只需要一台时选了五台 `ml.g7e.2xlarge` 实例，你就在空闲 GPU 上烧掉预算。选太少，请求就会排队、延迟激增、用户经历退化的服务。

并发扫描解决了这一问题。一次并发扫描是一种系统化的基准测试方法，它向你的 Amazon SageMaker AI 端点发送受控、递增的并发流量并分析其性能。并发扫描内建在 [Amazon SageMaker AI Inference Recommendations](https://docs.aws.amazon.com/sagemaker/latest/dg/generative-ai-inference-recommendations.html) 中，因此无需构建或维护定制的负载测试基础设施。

在本文中，我们演练部署 [NVIDIA Nemotron-3 Nano 30B](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16) 模型、运行自动化的并发扫描，并利用结果做出数据驱动的容量决策。到最后，你会知道在延迟变得不可接受之前你的端点能处理多少并发请求，以及如何自动化那份发现。

## 什么是并发扫描？

一次并发扫描向你的 SageMaker AI 端点发送受控数量的同时请求，并在每个级别测量两个指标：

- *吞吐*：你的端点每秒产出多少 token。
- *延迟*：每个请求耗时多久。

通过逐步提高并发（例如从 64 到 256，然后到 1,024 个同时请求），你可以描绘出一条揭示端点*饱和点*的曲线。那正是增加更多并发流量不再提升吞吐、反而使延迟退化的那个点。

一次并发扫描为你的生产规划给出三个数据点：

- 理想的平衡：吞吐在可接受延迟下最大化的并发级别。
- 崩溃点：延迟越过你服务级别协议（SLA）阈值之处。
- 合理配置因子：给定每实例容量，你需要多少实例来覆盖峰值流量。

现在来看端到端工作流如何拼合在一起。

## 方案概览

并发扫描工作流有四个步骤：

- **部署**模型到一个 SageMaker AI 端点，使用原生 vLLM 容器。
- **配置**工作负载概况（输入和输出 token 数、流式模式）。
- **运行**并发扫描，使用 [CreateAIBenchmarkJob](https://docs.aws.amazon.com/sagemaker/latest/APIReference/API_CreateAIBenchmarkJob.html) API。
- **分析**结果以识别最优并发并合理配置你的机群。

## 演练

下面四个步骤会把你从一个全新部署带到一个完整的容量概况。每一步都建立在前一步之上，所以我们建议你配着[配套 notebook](https://github.com/aws-samples/sagemaker-genai-hosting-examples/blob/main/03-features/gen-ai-inference-recommendations/inference_optimization_concurrency_sweep.ipynb) 一起操作。

### 前提条件

开始前，确认你有：

- 一个具备 Amazon SageMaker AI 访问权限的 AWS 账户。
- 一个具备 SageMaker AI 和 Amazon Simple Storage Service (Amazon S3) 权限的 AWS Identity and Access Management (IAM) execution 角色。你可以在 notebook 中查看说明。
- `ml.g7e.2xlarge` 端点的服务配额。

### 步骤 1：用原生 vLLM 容器部署模型

我们把 NVIDIA Nemotron-3 Nano 30B——一个只有 3B 活跃参数的混合专家（MoE）模型——部署到一台 `ml.g7e.2xlarge` 实例。这台实例由一块 [NVIDIA Blackwell GPU](https://www.nvidia.com/en-us/products/workstations/professional-desktop-gpus/rtx-pro-6000-family/) 支撑，它为推理工作负载提供出色的性价比。

我们使用用于 SageMaker AI 的 [vLLM Deep Learning Container](https://aws.github.io/deep-learning-containers/reference/available_images/#vllm)，通过 `SM_VLLM_*` 环境变量配置：

```
VLLM_IMAGE = (
    f"763104351884.dkr.ecr.{region}.amazonaws.com/"
    f"vllm:0.19.1-gpu-py312-cu129-ubuntu22.04-sagemaker"
)

environment = {
    "SM_VLLM_MODEL": "nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16",
    "SM_VLLM_ENFORCE_EAGER": "true",  # required for Mamba-Transformer hybrid
    "SM_VLLM_TENSOR_PARALLEL_SIZE": "1",  # single GPU
    "SM_VLLM_GPU_MEMORY_UTILIZATION": "0.85",
    "SM_VLLM_MAX_MODEL_LEN": "10240",
    "SM_VLLM_ENABLE_PREFIX_CACHING": "true",
    "SM_VLLM_TRUST_REMOTE_CODE": "true",
}
```

其中三个设置值得一说。`SM_VLLM_ENFORCE_EAGER` 标志是必需的，因为 Nemotron-3 Nano 使用一种需要 eager 执行模式的 Mamba-Transformer 混合架构。我们把 GPU 显存利用率设为 0.85，以在高并发下为 KV 缓存增长留出余量。开启前缀缓存是为了在系统 prompt 跨请求重复的场景下提升性能，从而复用缓存的键值对。

在创建模型、端点配置和端点之后，我们用一次验证确认部署，然后进入基准测试。

### 步骤 2：配置工作负载概况

在运行任何负载测试之前，基准引擎需要知道要模拟什么类型的流量。我们用 [CreateAIWorkloadConfig](https://docs.aws.amazon.com/sagemaker/latest/APIReference/API_CreateAIWorkloadConfig.html) 定义一个反映真实生成式 AI 推理模式的工作负载概况。下表总结我们用于定义工作负载的各值。你可以配着[配套 notebook](https://github.com/aws-samples/sagemaker-genai-hosting-examples/blob/main/03-features/gen-ai-inference-recommendations/inference_optimization_concurrency_sweep.ipynb) 跟踪代码。

| **参数** | **值** | **描述** |
| --- | --- | --- |
| `tokenizer` | 模型分词器 ID | 用于准确计数 token |
| `streaming` | `True` | 启用流式响应（TTFT 指标所必需） |
| `prompt_input_tokens_mean` | 1,024 | 平均输入 prompt 长度 |
| `output_tokens_mean` | 256 | 平均生成响应长度 |

1,024 输入 token 和 256 输出 token 的选择代表性地反映了检索增强生成（RAG）或摘要类工作负载。如果你的应用用更短的 prompt 和更长的补全（如代码生成），相应调整这些值。启用流式传输是为了捕获首 token 时间（TTFT）指标，这对感知响应速度与原始吞吐同等重要的交互式用户体验很关键。

定义好工作负载概况后，下一步是启动扫描。

### 步骤 3：运行并发扫描

我们现在用 CreateAIBenchmarkJob API 配扫描要用的参数来创建基准作业。在示例 notebook 中演示的场景里，我们有：

```
sweep_params = {
    "concurrency": [64, 256, 1024],  # powers of 4
    "request_count": 1024,  # requests per concurrency level
}
```

基准引擎（[AIPerf](https://docs.nvidia.com/aiperf/welcome-to-ai-perf-documentation)）在单个作业内按序运行每个并发级别，在每个级别发送 `request_count` 下定义的总请求数。按序而非并行运行各级别，意味着每次测量都反映一个干净、隔离的负载。这种方法给你统计上稳定的估计，同时把成本控制在范围内。

当作业完成时，结果作为含逐级别 JSON 格式指标的 tarball 写入 `OutputConfig` 下定义的 Amazon S3 路径。

### 步骤 4：分析结果

作业完成后，我们可以下载并解析输出做分析。在读结果时，四个指标最重要：

- **吞吐（输出 token/秒）：** 它进入平台期还是持续攀升？
- **p99 端到端延迟**：它在哪里越过你的 SLA？
- **p50 到 p99 延迟跨度：** 不断拉大的差距表明负载下在排队。
- **首 token 时间（TTFT）**：对流式用户体验至关重要。

当你在各并发级别上绘制吞吐对延迟时，饱和点在曲线上表现为一个“拐点”：吞吐变平而 p99 延迟急剧上翘。在我们的测试场景中这发生在 256 个并发请求处。拐点以下的并发级别是你安全运行区。在其之上，端点过载而用户在等待。

图 2：各并发级别上的吞吐和 p99 延迟，饱和拐点在 256 个并发请求

此时你对端点在负载下的行为有了完整的了解。对许多团队，这足以做出一个有信心的容量决定。如果你想跨模型版本或实例类型自动化寻找最优运行点，基准引擎提供了一个自动化的替代方案。

## 更进一步：基于 SLA 的自动并发搜索

步骤 3 中的并发扫描要求你选择要测试的并发级别。你可能不知道合适的范围，或你想跨模型版本自动化容量规划。无论哪种情况，在同一个 `CreateAIBenchmarkJob` 调用中用一个搜索配方替换固定的并发列表。`max-concurrency-under-sla` 配方接受一个或多个 SLA 阈值，并搜索满足全部它们的最高并发。

下表描述可用的 SLA 阈值参数：

| **参数** | **含义** | **统计量** | **需要流式吗？** |
| --- | --- | --- | --- |
| `ttft_sla_ms` | 最大首 token 时间（ms） | p95 | 是 |
| `tpot_sla_ms` | 最大每输出 token 时间（ms） | p95 | 是 |
| `e2e_sla_ms` | 最大端到端请求延迟（ms） | p99 | 否 |
| `error_rate_sla` | 最大失败请求比例 | 平均 | 否 |

例如，我们可以用下面的搜索参数找到 p99 端到端延迟保持在 50 秒以下时的最大并发：

```
search_params = {
    "search_recipe": "max-concurrency-under-sla",
    "e2e_sla_ms": 50000,
    "concurrency_min": 16,
    "concurrency_max": 4096,
    "search_max_iterations": 10,
    "search_initial_points": 512,
    "request_count": 1024,
}
```

搜索引擎使用一个优化规划器，它能比线性扫描用更少的迭代收敛到答案。它从一个宽范围开始并逐步收窄，只评估识别边界所需的并发级别。这能同时减少迭代次数和搜索的总成本。

| **迭代** | **并发** | **吞吐（OTPS）** | **通过 SLA？** |
| --- | --- | --- | --- |
| 1 | 16 | 492.5 | ✓ |
| 2 | 32 | 904.2 | ✓ |
| 3 | 64 | 1433.4 | ✓ |
| 4 | 128 | 2066.8 | ✓ |
| 5 | 256 | 2823.4 | ✓ |
| 6 | 512 | 2782.3 | ✗ |
| 7 | 320 | 2781.8 | ✓ |
| 8 | 284 | 2788.6 | ✗ |

在这个例子中，规划器从并发 16 开始并在每次迭代翻倍。在并发 512 处发生第一次 SLA 违规，要么因为 p99 端到端延迟超过阈值，要么因为调用失败。规划器随后把搜索收窄到 256–512 范围，并发现并发 320 在每秒 2,782 个 token 时满足 SLA。搜索最多运行你在 `search_max_iterations` 中定义的迭代次数。

## 组合多个 SLA

单个 SLA 阈值对多数生产工作负载不够，因为有些场景要求一个模型必须同时满足多个 SLA。例如，在交互式用户体验中，你可能需要同时控制端到端延迟和首 token 时间。你仍可以通过在搜索参数下传入多个 SLA 来使用 `max-concurrency-under-sla` 搜索配方：

```
search_params = {
    "search_recipe": "max-concurrency-under-sla",
    "e2e_sla_ms": 50000,  # p99 end-to-end < 50s
    "ttft_sla_ms": 1500,  # p95 time-to-first-token < 1.5s
    "concurrency_min": 16,
    "concurrency_max": 4096,
    "search_max_iterations": 10,
    "request_count": 1024,
}
```

| **迭代** | **并发** | **吞吐（OTPS）** | **通过 SLA？** |
| --- | --- | --- | --- |
| 1 | 16 | 480.2 | ✓ |
| 2 | 32 | 888.6 | ✓ |
| 3 | 64 | 1429.9 | ✓ |
| 4 | 128 | 2061.4 | ✗ |
| 5 | 80 | 1599.3 | ✓ |

在这种情况下，我们观察到当同时对端到端延迟和首 token 时间施加 SLA 时，支持的最大并发级别是 80。

基准测试完成后，我们来清理本次演练期间创建的资源。

## 清理

为避免持续产生费用，测试后[删除你的 SageMaker 端点](https://docs.aws.amazon.com/sagemaker/latest/APIReference/API_DeleteEndpoint.html)、[端点配置](https://docs.aws.amazon.com/sagemaker/latest/APIReference/API_DeleteEndpointConfig.html)和[模型](https://docs.aws.amazon.com/sagemaker/latest/APIReference/API_DeleteModel.html)。无论是否在接收流量，端点都按小时计费。

## 结论

并发扫描用数据取代生成式 AI 端点容量规划过程中的猜测。你不必作为预防而超配，也不必在生产中发现瓶颈，而是可以系统地描绘端点的性能包络。于是你能在单个用户请求到达你的系统之前，就机群规模做出知情的决定。

在本文中，你学到了如何：

- 用 Amazon SageMaker AI 上的原生 vLLM 容器部署一个模型。
- 用 `CreateAIBenchmarkJob` API 运行并发扫描。
- 绘制吞吐对延迟以识别饱和点。
- 用 `max-concurrency-under-sla` 配方为你的 SLA 目标自动发现最优并发。
