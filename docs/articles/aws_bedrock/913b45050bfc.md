# 在 hub-and-spoke 网络中通过集中式检查将 Amazon Bedrock AgentCore Gateway 连接到私有 API

在许多企业中，中央网络团队拥有每一个虚拟私有云（VPC）和子网，VPC 之间的每条流量都必须在两个方向上经过中央防火墙。通过 [Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)——Amazon Bedrock AgentCore 的一项能力——调用内部 REST API 和 Model Context Protocol（MCP）服务器的 agent，必须满足同样的两项要求。Amazon Bedrock AgentCore 是一个用于大规模构建、连接和优化 agent 的平台，支持任意框架或模型。

本文介绍一种同时满足这两项要求的模式。网络团队保留对每个子网的所有权，而 Gateway 与你的私有 API 和 MCP 服务器之间的流量会在两个方向上经过中央防火墙。文中说明应将 Gateway 用于访问私有目标的 Amazon VPC Lattice resource gateway 放在哪里，也说明各部分的归属、六项配置决策，以及用于确认该模式确实可行的检查。

我们在位于美国东部（弗吉尼亚北部）AWS 区域（`us-east-1`）的一间实验环境中构建并测试了该模式，该实验环境包含三个成员账户以及 AWS Organizations 中的一个管理账户。AWS CloudFormation 模板、测试脚本、测试证据和参考资料（地址规划、完整验证检查、故障排查、配额）都在[配套仓库](https://github.com/aws-samples/sample-bedrock-agentcore-gateway-hub-spoke-inspection)中。请将该模式作为指导，并根据你自己的账户架构进行调整。

### 本文使用的术语

- **Resource gateway：** [Amazon VPC Lattice](https://docs.aws.amazon.com/vpc-lattice/latest/ug/what-is-vpc-lattice.html) 进入 VPC 的入口：在你选择的子网中创建的弹性网络接口（ENI）。后端会将其地址视为每个连接的来源。
- **Resource configuration：** 一个 VPC Lattice 对象，用于指定 resource gateway 后面的一个后端（这里是内部负载均衡器或 VPC 端点的 DNS 名称和端口）。你可以通过 AWS Resource Access Manager（AWS RAM）将它共享给其他账户。
- **托管模式和自管模式：** Gateway 目标的两种[私有端点](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/vpc-egress-private-endpoints.html)选项。在托管模式下，AgentCore 为你创建 resource gateway。在自管模式下，由你创建它，并为目标指定 resource configuration。

## 何时使用该模式

当以下条件全部成立时，请使用该模式：

- 网络账户拥有每个 VPC、子网和 AWS Transit Gateway 挂载，并通过 AWS RAM 共享应用子网。
- 检查 VPC 中的中央防火墙必须检查进出每个 VPC 的流量。
- 应用团队只管理自己的资源和安全组。

否则，表 1 中的某个选项可能更合适。

*表 1：何时其他选项更合适。*

| **你的环境** | **使用** |
| --- | --- |
| Gateway 账户可以拥有能访问你的工具的子网 | [托管模式](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/vpc-egress-private-endpoints.html#lattice-vpc-egress-managed-lattice) |
| Gateway 与工具之间的流量不需要集中检查 | [自管模式](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/vpc-egress-private-endpoints.html#lattice-vpc-egress-self-managed-lattice)，如文档所述 |
| 工具可通过公有端点访问 | 标准的 [Gateway target](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) |

我们还考虑了在 AgentCore 拥有的子网中使用托管模式、在每个工具 VPC 或中央端点 VPC 中放置 resource gateway，以及为每个工具配置带有 AWS WAF 的面向互联网的负载均衡器。[备选方案说明](https://github.com/aws-samples/sample-bedrock-agentcore-gateway-hub-spoke-inspection/blob/main/docs/considerations.md#alternatives-we-considered)解释了为什么每种方案在这些约束下都不够用。

## 集中式检查的设计要求

- 网络账户拥有每个子网。Gateway 账户和应用账户只在通过 AWS RAM 共享给它们的子网中进行构建。
- VPC 之间的每条流量都会在两个方向上经过中央防火墙。检查 VPC 中的中央防火墙会检查 Gateway 与你的私有 API 和 MCP 服务器之间的流量。

AgentCore Gateway 通过 VPC Lattice resource gateway 访问私有目标，而两种私有端点模式对它的放置位置不同。托管模式会在 Gateway 账户中创建它，这适合该账户能够拥有其运行所在子网的环境。自管模式如文档所述，会将它放在可直接访问后端的子网中，这适合不要求在 Gateway 与工具之间进行检查的环境。本环境同时需要这两个条件，因此该模式使用自管模式并做一处改动。网络账户拥有 resource gateway，并将其放在经由 AWS Transit Gateway 路由的子网中，因此每个请求和响应都会经过检查 VPC。

## 解决方案概述

在网络账户中为 resource gateway 分配独立的 VPC 和子网。不要共享它们，也不要将后端放入其中。让它们经由中转网关路由，使 VPC 之间的每个请求和响应都经过防火墙。通过 AWS RAM 将每个后端对应的一份 resource configuration 共享给 AgentCore 账户。图 1 展示了账户、VPC 和流量路径。

图 1：网络账户拥有每个 VPC 和 resource gateway。其他账户只拥有它们放入共享子网中的内容。实线在两个方向上穿过防火墙。步骤编号与下文流量路径中的步骤一致

### 流量路径

- agent 位于没有互联网路由的共享子网中，它调用 Gateway URL。Gateway 接口端点上的私有 DNS 会在 agent 的 VPC 内解析该地址。
- 如果挂载了 AWS WAF，它会评估该请求。Gateway 会检查其资源策略和入站 JSON Web Token（JWT），然后选择目标和工具。
- Gateway 为工具账户获取一个出站 OAuth token，并通过 VPC Lattice 将请求发送到网络账户中的 resource gateway。
- resource gateway 子网路由到中转网关，中转网关将流量经由检查 VPC 发送到工具账户的内部 Application Load Balancer（ALB）或 `execute-api` 端点。（经过防火墙。）
- ALB 或 Amazon API Gateway 验证 token，并将请求转发到后端。
- 响应沿相同路径返回。（经过防火墙。）

在 AgentCore 账户中没有中转网关挂载的情况下，Gateway 流量如何进入网络账户的 VPC？当你创建目标时，AgentCore 会将共享的 resource configuration 与其自己的 VPC Lattice service network 关联。随后 VPC Lattice 会将该 service network 的连接投递到你 VPC 中 resource gateway 的网络接口。这一跳由 AWS 运营，从此之后由你的路由和防火墙接管。

该模式不做的事情。在采纳之前，请对照你的要求检查这些限制：

- **不检查负载内容 –** 从 Gateway 到 ALB 的流量是端到端 TLS，并带有 Gateway 会验证的证书。防火墙看到的是流元数据和 TLS Server Name Indication（SNI），而不是负载。请求内容在 Gateway、AWS WAF 和 ALB 日志中。
- **部分链路段跳过防火墙 –** agent 到接口端点这一段，以及 Gateway 到 resource gateway 这一段，都不会经过它。AgentCore 向各个身份提供方发出的 token 请求同样不会经过。
- **工具端没有最终用户身份 –** 使用 client credentials 授权类型时，到达工具的每次调用都携带 Gateway 的客户端身份。要将某次调用追溯到调用方，请使用 Gateway 应用日志中的入站 JWT 声明。

## 先决条件

- 一个 AWS Organizations 组织，并已启用 AWS RAM 中的资源共享。
- AWS Command Line Interface（AWS CLI）2.37.7 或更高版本，或 AWS SDK for Python（Boto3）1.43.106 或更高版本，以支持 `certificateConfigurations` 参数。
- 对于创建 Gateway 目标的角色：`vpc-lattice:GetResourceConfiguration`、`vpc-lattice:CreateServiceNetworkResourceAssociation`、`vpc-lattice:GetServiceNetworkResourceAssociation`、`vpc-lattice:ListServiceNetworkResourceAssociations` 和 `vpc-lattice:AssociateViaAWSService`，以及 bedrock-agentcore 的目标操作。如果你的组织目前没有使用 VPC Lattice，请检查你的服务控制策略（SCP）。
- 一台位于中央检查 VPC 中、挂载到中转网关并启用了 appliance 模式的防火墙。

## 关键设计决策

这些代码片段摘自实验模板，并使用实验的[地址规划](https://github.com/aws-samples/sample-bedrock-agentcore-gateway-hub-spoke-inspection/blob/main/docs/lab-layout.md)。`RGW_NET` 是 resource gateway 子网（10.0.1.0/24–10.0.3.0/24），`TOOL_NET` 是工具 VPC（10.12.0.0/16），`ALB_NET` 是其中的 ALB 子网。

### 决策 1：将 resource gateway 放在网络账户的专用 VPC 中

在网络账户中为 resource gateway 创建一个专用 VPC，其子网不共享，也不包含中央端点或后端。将这些子网路由到中转网关。每个信任区域保留一个 resource gateway。
```
ResourceGateway:
  Type: AWS::VpcLattice::ResourceGateway
  Properties:
    Name: hub-resource-gateway
    VpcIdentifier: !Ref ResourceGatewayVpc
    SubnetIds: [!Ref RgwSubnetA, !Ref RgwSubnetB, !Ref RgwSubnetC]
    SecurityGroupIds: [!Ref RgwSg]          # egress 443 to application ranges only
    IpAddressType: IPV4

RgwRouteToTgw:
  Type: AWS::EC2::Route
  Properties:
    RouteTableId: !Ref RgwRouteTable
    DestinationCidrBlock: 10.0.0.0/8        # internal ranges go to the transit gateway
    TransitGatewayId: !Ref Tgw
```
仅在配合 AgentCore 使用时，resource gateway [在每个子网中消耗一个 IP 地址](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/vpc-egress-private-endpoints.html#lattice-vpc-egress-compare-modes)，因此小型子网就足够了。有两项设置在创建后无法更改，即 `Ipv4AddressesPerEni` 和 `ResourceConfigDnsResolution`，因此请提前选好。请使用 VPC Lattice 和你的 AgentCore 功能所支持的可用区 ID。[实验布局](https://github.com/aws-samples/sample-bedrock-agentcore-gateway-hub-spoke-inspection/blob/main/docs/lab-layout.md#availability-zones)列出了 `us-east-1` 对应的可用区。

### 决策 2：为每个负载均衡器创建一份 resource configuration，并通过 AWS RAM 共享

将 resource configuration 指向内部 ALB 的 DNS 名称，并与 AgentCore 账户共享。不要以 `rcfg-` 开头命名，该前缀由 VPC Lattice 保留。
```
ToolsResourceConfig:
  Type: AWS::VpcLattice::ResourceConfiguration
  Properties:
    Name: tools-account-a
    ResourceConfigurationType: SINGLE
    ResourceGatewayId: !Ref ResourceGateway
    ProtocolType: TCP
    PortRanges: ["443"]
    ResourceConfigurationDefinition:
      DnsResource:
        DomainName: internal-tools-alb-1234567890.us-east-1.elb.amazonaws.com
        IpAddressType: IPV4

ShareToAgentCore:
  Type: AWS::RAM::ResourceShare
  Properties:
    Name: agentcore-resource-configs
    AllowExternalPrincipals: false
    Principals: ["<agentcore-account-id>"]
    ResourceArns: [!GetAtt ToolsResourceConfig.Arn]
```
VPC Lattice 会将连接投递到 resource configuration 的域。AgentCore 会将目标 URL 的主机名（例如 `tools.example.internal`）作为 SNI 发送，并据此校验 ALB 证书。证书的主体备用名称必须与该主机名匹配。该主机名不需要能在 DNS 中解析。

对于私有 API Gateway REST API，请将一份 resource configuration 指向网络账户的 `execute-api` 接口端点。每个 API 的目标使用自己的 URL，并且每个 API 的资源策略必须通过 `aws:SourceVpce` 允许该端点。在我们的测试中，另一个账户中的第二个 API 通过同一份 resource configuration 即可工作，无需任何网络改动。

### 决策 3：只让需要的流量经过防火墙

你的防火墙需要两条有状态放行规则：从 resource gateway 子网到工具 VPC 的 443 端口，以及从 ALB 子网到身份提供方主机名的 443 端口。基于会话的防火墙会放行已允许流的响应。在实验中，我们使用了 AWS Network Firewall，采用严格规则顺序，默认动作为 *Drop established *和 *Alert established*。使用这些默认值，防火墙会丢弃没有任何规则放行的客户端到服务器数据包，并放行响应，除非有规则将其丢弃。[规则顺序说明](https://github.com/aws-samples/sample-bedrock-agentcore-gateway-hub-spoke-inspection/blob/main/docs/considerations.md#aws-network-firewall-rule-order)解释了其语义。

```
# Policy: RuleOrder STRICT_ORDER, StatefulDefaultActions [aws:drop_established, aws:alert_established]
pass tcp $RGW_NET any -> $TOOL_NET 443 (msg:"resource gateway to tool VPC"; flow:to_server; sid:100001; rev:4;)
pass tls $ALB_NET any -> any 443 (msg:"ALB to identity provider JWKS"; tls.sni; content:"cognito-idp.us-east-1.amazonaws.com"; nocase; startswith; endswith; flow:to_server; sid:100010; rev:2;)
```
第一条规则只允许 resource gateway 子网在 443 端口访问工具 VPC。第二条规则允许 ALB 获取其身份提供方的签名密钥（JSON Web Key Set，即 JWKS），但只允许从 ALB 子网发出，并且只允许访问身份提供方的主机名。工具 VPC 需要有一条指向中转网关的默认路由，该获取请求才能到达中央出口。如果你的身份提供方不是 Amazon Cognito，请替换主机名。在我们的测试中，如果没有这条规则，ALB 会返回 HTTP 500，agent 会收到 `MCP invocation failed`。

为了证明响应确实经过防火墙，我们在放行规则之前添加了一条针对响应方向的丢弃规则：

```
drop tcp $TOOL_NET 443 -> $RGW_NET any (msg:"PROOF return path blocked"; flow:to_client; sid:100098; rev:2;)
```
随后工具调用会一直挂起直到超时，防火墙记录到了 sid 100098 的 `to_client` 丢弃。删除该规则后调用恢复正常。请在你自己的防火墙上运行同样的测试。

### 决策 4：在内部 ALB 或私有 API 上验证工具账户的 token

工具账户保留自己的身份提供方（实验中为 Amazon Cognito），并为 Gateway 创建一个应用客户端。在通往后端的每条路径上验证该客户端的 token。

**内部 ALB –** 将监听器的默认动作设置为固定响应，并在每条转发规则上放置一个 [jwt-validation](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/listener-verify-jwt.html) 动作。将 `client_id` 固定为 Gateway 的应用客户端，以便同一用户池中的其他客户端会被拒绝。

```
McpRule:
  Type: AWS::ElasticLoadBalancingV2::ListenerRule
  Properties:
    ListenerArn: !Ref Listener                # default action: fixed-response 404
    Priority: 10
    Conditions: [{Field: path-pattern, PathPatternConfig: {Values: [/mcp]}}]
    Actions:
      - Type: jwt-validation
        Order: 1
        JwtValidationConfig:
          Issuer: !Sub https://cognito-idp.${AWS::Region}.amazonaws.com/${ToolPool}
          JwksEndpoint: !Sub https://cognito-idp.${AWS::Region}.amazonaws.com/${ToolPool}/.well-known/jwks.json
          AdditionalClaims:
            - {Format: space-separated-values, Name: scope, Values: [tools/invoke]}
            - {Format: single-string, Name: client_id, Values: [!Ref GatewayAppClient]}
      - Type: forward
        Order: 2
        TargetGroupArn: !Ref ToolsTargetGroup
```
在我们的测试中，不带 token 的目标、带另一个身份提供方 token 的目标，以及带不同应用客户端 token 的目标，都在后端运行之前被以 HTTP 401 拒绝。agent 只看到 `An internal error occurred`，因此请使用 ALB 访问日志来诊断 token 问题。

**私有 REST API –** API key 不会对调用方进行身份验证，因此请为每个方法添加授权方，例如带必需作用域的 Cognito 用户池授权方（如实验中所做）。同时为 `execute-api` 端点附加端点策略，将其限制为仅能访问由已批准账户拥有的 API。该策略控制端点可以访问哪些 API，而不是谁可以调用它。授权方控制调用方。

```
{"Statement": [{"Effect": "Allow", "Principal": "*", "Action": "execute-api:Invoke",
  "Resource": ["arn:aws:execute-api:us-east-1:<tool-account-id>:*"]}]}
```
ALB 或端点的安全组只允许 resource gateway 子网，因此 resource gateway 是唯一的入站网络路径。如果你的防火墙应用了源 NAT，那么安全组必须改为允许防火墙的地址，此时它会放行防火墙转发的任何内容。防火墙规则和 token 验证便成为控制手段。

### 决策 5：创建引用共享 resource configuration 的 Gateway 目标

创建 Gateway 时使用 JWT 授权方，并可选地使用 AWS WAF Web 访问控制列表（Web ACL），它会检查每个目标的工具调用参数。默认情况下，AWS WAF 只检查 body 的前 16 KB（可调整到 64 KB），因此请决定每条规则如何处理更大的 body。将 `AWSManagedRulesSQLiRuleSet` 添加到通用规则集。请参阅 [AWS WAF 说明](https://github.com/aws-samples/sample-bedrock-agentcore-gateway-hub-spoke-inspection/blob/main/docs/considerations.md#aws-waf-rule-groups-for-tool-calls)。

使用私有端点的 Gateway 目标[无法使用 NO_AUTH](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-vpc-egress.html#gateway-vpc-access-limitations)进行入站授权，除非你配置了 interceptor 函数。

每个目标都需要一个 OAuth 凭证提供方，其中保存工具账户的应用客户端 ID 和密钥，以及身份提供方的 discovery URL：

```
# provider.json holds the client secret, so it stays out of the command line and shell history:
# {"name": "tools-account-a", "credentialProviderVendor": "CustomOauth2",
#  "oauth2ProviderConfigInput": {"customOauth2ProviderConfig": {
#    "clientId": "<tool-app-client-id>", "clientSecret": "<tool-app-client-secret>",
#    "oauthDiscovery": {"discoveryUrl": "https://cognito-idp.<region>.amazonaws.com/<pool-id>/.well-known/openid-configuration"}}}}
chmod 600 provider.json
aws bedrock-agentcore-control create-oauth2-credential-provider --cli-input-json file://provider.json
rm provider.json
```
如果 ALB 使用来自私有证书颁发机构（CA）的证书，还需将 CA 证书以 PEM 字符串形式存储在 AWS Secrets Manager secret 中。Gateway 执行角色（你创建 Gateway 时为其指定的 AWS Identity and Access Management（IAM）角色）需要读取该 secret 和凭证提供方的权限。

```
import boto3

agentcore = boto3.client("bedrock-agentcore-control", region_name="us-east-1")

agentcore.create_gateway_target(
    gatewayIdentifier="<gateway-id>",
    name="classifier",
    targetConfiguration={"mcp": {"mcpServer": {"endpoint": "https://tools.example.internal/mcp"}}},
    credentialProviderConfigurations=[{
        "credentialProviderType": "OAUTH",
        "credentialProvider": {"oauthCredentialProvider": {
            "providerArn": "<oauth-provider-arn>",
            "scopes": ["tools/invoke"],
            "grantType": "CLIENT_CREDENTIALS"}}}],
    # Shared from the network account through AWS RAM
    privateEndpoint={"selfManagedLatticeResource": {
        "resourceConfigurationIdentifier": "<shared-resource-configuration-arn>"}},
    # Trust the private CA that issued the ALB certificate
    certificateConfigurations=[{"secretsManager": {"secretArn": "<ca-secret-arn>"}}],
)
```
OpenAPI 目标使用相同的配置块，只是用 `openApiSchema` 替代 `mcpServer`。要轮换 CA，请更新 secret 并调用 `UpdateGatewayTarget`。已打开的连接最多可以继续使用旧的信任材料 15 分钟。

让 Gateway 成为共享 resource configuration 的唯一使用方。AWS RAM 的 AWS 托管权限还会授予 `ec2:CreateVpcEndpoint`，因此 AgentCore 账户可能通过自己的 resource VPC 端点或 service network 访问后端。客户托管权限无法解决这个问题：AWS RAM 会拒绝其中包含的 `vpc-lattice:AssociateViaAWSService`，而没有它 Gateway 目标会失败。请改为向 AgentCore 账户附加 SCP：

```
{"Version": "2012-10-17", "Statement": [
  {"Sid": "NoOwnEndpointsToSharedResourceConfigurations", "Effect": "Deny",
   "Action": "ec2:CreateVpcEndpoint", "Resource": "arn:aws:vpc-lattice:*:*:resourceconfiguration/*"},
  {"Sid": "ServiceNetworkAssociationsOnlyThroughAwsServices", "Effect": "Deny",
   "Action": "vpc-lattice:CreateServiceNetworkResourceAssociation", "Resource": "*",
   "Condition": {"BoolIfExists": {"aws:ViaAWSService": "false"}}}]}
```
有了这条 SCP，我们尝试创建 resource VPC 端点和其自有的 service network 关联均被拒绝，而新的 Gateway 目标仍能达到 `READY` 状态。SCP 不适用于管理账户，因此不要在那里运行 AgentCore。在网络账户中，请使用匹配 AWS CloudTrail 事件 `CreateServiceNetworkResourceAssociationBySharee` 的 Amazon EventBridge 规则，对意外关联发出告警。

撤销访问时，请先删除 Gateway 目标（或 service network resource association），再从共享中移除 resource configuration。仅从共享中移除它[并不会删除已有的关联](https://docs.aws.amazon.com/vpc-lattice/latest/ug/sharing.html)。

### 决策 6：私有访问 Gateway，并关闭公有端点

在共享的 agent VPC 中创建 Gateway 接口端点并启用私有 DNS，然后附加一个列出已批准 Gateway 的[端点策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/vpc-interface-endpoints.html)。principal 必须是 *，因为 Gateway 使用 bearer token 对调用方进行身份验证。`Resource` 列表才是控制手段。

```
{"Version": "2012-10-17", "Statement": [{"Effect": "Allow", "Principal": "*", "Action": "bedrock-agentcore:InvokeGateway",
  "Resource": ["arn:aws:bedrock-agentcore:us-east-1:<agentcore-account-id>:gateway/<gateway-id>"]}]}
```
在我们的测试中，通过同一端点调用的第二个 Gateway 返回了 JSON-RPC 错误 -32002 `Insufficient permissions`，但它的公有端点仍然可以应答。

接口端点并不会关闭 Gateway 的公有端点。请附加[资源策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/resource-based-policies.html)，仅在 `aws:SourceVpce` 为你的端点时允许 `bedrock-agentcore:InvokeGateway`，否则拒绝（[完整策略](https://github.com/aws-samples/sample-bedrock-agentcore-gateway-hub-spoke-inspection/blob/main/lab-code/gateway-resource-policy.example.json)在仓库中）。在我们的测试中，应用该策略约 30 秒后，来自互联网的调用返回 -32002，而端点调用继续正常工作。AWS 指出策略变更[最多可能需要 15 分钟](https://aws.amazon.com/blogs/machine-learning/secure-ingress-connectivity-to-amazon-bedrock-agentcore-gateway-using-interface-vpc-endpoints/)生效。

没有互联网路由的 agent 仍然需要其入站 JWT。请为它提供一条通往其身份提供方 token 端点的路径，例如指向中转网关的路由，以及一条像决策 3 中 JWKS 规则那样限定范围的防火墙规则。或者，使用私有身份提供方。

## 在你的环境中验证该模式

在依赖该模式之前，请在你网络账户的非生产副本中、使用你自己的防火墙运行这些检查。仓库中包含[全部 14 项检查](https://github.com/aws-samples/sample-bedrock-agentcore-gateway-hub-spoke-inspection/blob/main/docs/validation-checks.md)（包括每项检查的执行方式和我们观察到的结果），以及[每一跳的日志来源](https://github.com/aws-samples/sample-bedrock-agentcore-gateway-hub-spoke-inspection/blob/main/docs/logging.md)。

- **请求来自 resource gateway –** ALB 访问日志显示的源 IP 位于 resource gateway 的地址范围（如果防火墙应用了源 NAT，则为防火墙的地址范围）。
- **请求经过防火墙 –** 防火墙流日志显示从 resource gateway 地址到工具账户 443 端口的 TLS 流。
- **响应经过防火墙 –** 在放置了响应方向的丢弃规则（决策 3）后，调用会失败，防火墙会记录 `to_client` 丢弃。
- **ALB 和私有 API 是 token 边界 –** 不带 token 或带其他客户端 token 的目标会收到 HTTP 401，且后端不会被调用。
- **Gateway 公有端点已关闭 –** 附加资源策略后，互联网调用会得到 -32002，而端点调用成功。

如果某项检查失败，或 agent 收到通用错误，[故障排查指南](https://github.com/aws-samples/sample-bedrock-agentcore-gateway-hub-spoke-inspection/blob/main/docs/troubleshooting.md)会将每种症状映射到能显示原因的日志。

## 注意事项

- **成本：** 每个 VPC Lattice service network resource association 都会产生按小时计费以及数据处理费用。请参阅 [VPC Lattice 定价](https://aws.amazon.com/vpc/lattice/pricing/)。按每个目标一个关联来规划。要查看你的目标创建了多少个关联，可以比较 `GetGatewayTarget` 为每个目标返回的 `resourceAssociationArn`，并优先采用每个 API 或 MCP 服务器一个目标，而不是大量小目标。
- **发往公有端点的流量：** 有三类调用会离开私有路径：ALB 获取 JWKS、agent 的入站 token 请求，以及 AgentCore 向各身份提供方发出的出站 OAuth token 请求。
- **账户布局与配额：** Gateway 工具调用配额既按账户计算，也按网关计算。每个环境使用一个 AgentCore 账户，并在达到限制之前尽早按域或 agent 组拆分网关。VPC Lattice 会关闭空闲连接，因此对于长期存活的 MCP 流请使用 keepalive。仓库中列出了[其他配额](https://github.com/aws-samples/sample-bedrock-agentcore-gateway-hub-spoke-inspection/blob/main/docs/quotas.md)。
- **我们的测试范围：** 我们只使用了 AWS Network Firewall、没有源 NAT，并且仅在 `us-east-1` 中进行。源 NAT、多区域、私有身份提供方和 OpenAPI 限制在[其他注意事项](https://github.com/aws-samples/sample-bedrock-agentcore-gateway-hub-spoke-inspection/blob/main/docs/considerations.md#other-considerations)中介绍。

## 结论

当你的网络团队拥有每个子网、且 VPC 之间的每条流量都必须经过中央防火墙时，请将 VPC Lattice resource gateway 放在网络账户中，并让其子网经由中转网关路由。网络团队只需设置一次入口点，并为每个后端负载均衡器添加一份 resource configuration。应用团队仍然只拥有自己的负载均衡器、安全组、身份提供方和 Gateway 目标，而 AWS WAF 则从每个工具的公有负载均衡器迁移到 Gateway 上。在依赖该模式之前，请在你自己的环境中运行验证检查。
