# 由 AI 驱动的元数据校正与协调

随着数据采集与数据生成的加速，我们生产原始数据的能力与将其标准化的能力之间的差距在持续扩大。若没有自动化，这一差距就会变成关键瓶颈：它拖慢分析、让解读复杂化，并限制共享数据集的全球价值。

元数据协调（把标签、标识符与格式标准化，使来自不同来源的数据集能够协同工作）在很大程度上仍靠人工完成。由 AI 驱动的元数据校正与协调提供了一条前进路径：它把元数据管理从一项耗时的职责，转变为一种随数据量扩展、支持开放科学而非阻碍开放科学的流程。

在本文中，我们演示由 AI 驱动的元数据校正在实践中如何运作，探讨两种实现方式（从人在回路（human-in-the-loop）校验到完全自主的 agent 驱动工作流），并为在你的组织中部署这些方案提供治理层面的考量。

## 元数据校正与协调工作流

为应对这一挑战，我们构建了一套基于 AWS 的集中式元数据校正与协调工作流，旨在支持跨异构元数据源的一致性、互操作性与准确性。该系统使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 完成由大语言模型（LLM）驱动的 schema 对齐与校正建议，使用 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/) 存储 schema 与结果，使用 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 进行任务跟踪，使用 [Amazon Cognito](https://aws.amazon.com/pm/cognito) 做身份认证，并使用 [Amazon Elastic Container Service（Amazon ECS）](https://aws.amazon.com/ecs/) 提供算力。该工作流包含一个协调包，用于对齐元数据 schema、校验数据完整性并生成校正建议。

该元数据校正与协调系统以循环式工作流运行：引导数据通过校验、生成建议，然后把控制权交回用户做最终批准。下图展示了这一高层流程：

### schema 对齐

元数据校正的第一步是比较源数据与目标数据的 schema：核实正确的列是否存在并且恰当对齐。常见问题包括命名约定不一致（同义词、拼写错误、缩写）、列缺失或多余，以及需要拆分或合并列的情况。模糊字符串匹配可以处理基本的命名差异，但更复杂的对齐挑战需要另一种方法。Amazon Bedrock 上可用的 LLM 为这一问题带来了语义理解能力。LLM 驱动的方法不只依赖字符串相似度，还能识别行业特有的同义词、从相邻列推断含义，并判断某个源列是否应拆分为多个目标列，或反过来把多个源列合并为一个目标列。这种语义匹配能够处理基于规则的系统所遗漏的情况。

### 元数据字段校验

元数据字段校验组件检查各个字段值是否符合 schema 要求。系统依据预定义规则评估每个字段，并把失败归为三类。

必填字段校验会找出缺失、为空或仅含空白字符的必填字段。例如，某一行缺少必填的样本标识符时，会在进一步处理之前被标记出来。

枚举值校验会把字段内容与 schema 中定义的受控词表进行比对。如果某字段只接受特定的仪器类型（例如测序系统），那么该列表之外的值会触发校验错误。这有助于防止自由格式文本在标准化字段中引入不一致。

格式模式校验应用正则表达式匹配来核实格式约定。日期字段可能要求 YYYY-MM-DD 格式，而标识符字段可能需要特定的字母数字模式。偏离预期格式的值会被标记出来。

每一次校验失败都会被分类并记录，且附带足够的上下文，供推荐系统生成恰当的校正建议。结构化错误报告会指明每个问题的位置、类型与性质。

### 元数据字段推荐

当元数据字段校验过程中检测到校验错误时，系统会通过对自然语言处理（NLP）与基于 AI 的技术做分层组合来生成建议，这种设计旨在平衡成本效率、性能与可解释性。工作流会优先使用经典 NLP 与基于 embedding 的相似度，然后再调用 LLM，从而在保持推理成本可预测的同时，获得准确、可扩展的建议。

这些技术既可以单独使用，也可以在 bagging 或 boosting 架构中按顺序组合，并依据置信度阈值动态选择。这种自适应分层让较简单的方法高效处理常规校正，而高级模型只负责解决那些需要上下文推理的模糊或新颖情况。

#### 1. 基于 embedding 的语义相似度

向量 embedding 让系统能够从语义上比较元数据值，基于相似度阈值识别接近的匹配。这支持对同义词、缩写或首字母缩略词等常见变体做精确校正。例如，系统可以把 “Human” 映射为 “Homo sapiens”，或把 “NYC” 映射为 “New York City”。

这种方法依赖更小、更高效的 embedding 模型（在 Amazon Bedrock 上可用），其输出可以被缓存，从而在保持准确性的同时，提供比 LLM 驱动推理更具成本效益的替代方案。

我们评估了多种 embedding 模型，包括面向特定领域的生物医学模型和 Amazon Titan，以找出最适合该工作负载的选择。我们最终选择 Amazon Titan，原因是它在通用与生物医学元数据任务上表现强劲、具备商业可用性，并且与 Amazon Bedrock 的模型推理兼容。这使它非常适合那些需要受支持、可扩展的 embedding 方案，又不愿承担自管理领域专用模型运维开销的组织。

#### 2. 上下文推断

上下文推断让系统能够通过识别元数据内部的关联与共享模式来推荐校正。许多数据集表现出内部一致性：相似的行共享结构特征，或不同列之间存在重复取值。通过分析这些局部相似性，模型可以仅利用当前上传内容中的信息来推断缺失或不一致的元数据值，而无需大型外部训练数据集。

在该实现中，上下文推断采用混合方法，结合距离加权 k 近邻、词频-逆文档频率（TF-IDF）特征表示以及共现统计。数据集中的每一行都会被转换成由文本、类别和数值字段构成的复合向量。文本字段被转换为 TF-IDF 表示，类别值通过独热编码或紧凑的学习表示进行编码，数值字段则被缩放到可比较的范围。随后系统使用余弦或欧氏距离度量行之间的相似度，并通过对最相似的样本进行加权投票来预测缺失值，其中距离更近的邻居贡献更大的影响。

进一步的改进通过使用点互信息（PMI）的共现分析实现，它能识别数据集中自然一起出现的取值组合。PMI 衡量的是超出原始频次的统计关联，可捕捉诸如“当 A 列包含 X 时，B 列通常包含 Y”这样的模式。最终建议以可配置的权重融合相似度与共现两种信号。这样产生的建议稳定且可解释，其依据是内部数据结构而非外部训练，因此即使在小规模或专门化的数据集上也能保持效率与可靠性。

#### 3. 模糊匹配

Levenshtein 距离等模糊搜索算法可以检测并修正拼写或格式上的不一致。它们在解决手工录入元数据中的错误（例如拼写错误、空格或标点差异）时尤其有效。模糊匹配通常在校正工作流的早期阶段应用，以便在施加语义或上下文推断层之前先捕获低层级的不一致。

#### 4. 基于 LLM 的解析（兜底层）

当先前的校验方法（包括基于规则的 NLP 与 embedding 相似度模型）无法达到足够的置信度时，通过 Amazon Bedrock 进行的基于 LLM 的解析会作为兜底层介入。这些模型能够跨越复杂的元数据结构进行推理，以解读模糊的或此前未见过的模式。基于 LLM 的推理是按需选择性调用的，也就是说，只有在更简单的算法无法以高置信度解析某个字段时，才会使用计算密集的推理。随后结果会呈现给人工审查，以维护下游数据协调中的准确性与可追溯性。

## 总结

元数据校正与协调工作流结合了三个阶段：通过 LLM 驱动的语义分析做 schema 对齐、使用分层规则方法做字段校验，以及由 embedding、模糊匹配和上下文推断驱动的建议。较简单的方法负责常规校正，而基于 LLM 的解析则作为兜底，处理传统方法无法解决的边缘情况。

## 开始使用

### 第 1 步：克隆仓库并安装依赖

克隆仓库并安装所有 Python 与 TypeScript 依赖：

```
git clone https://github.com/aws-samples/sample-intelligent-metadata-harmonization.git
cd metadata-harmonization

# Create and activate Python virtual environment
make createPythonEnvironment
source .venv/bin/activate

# Install all dependencies (Python packages, TypeScript packages, CDK, frontend)
make install
```

`make install` 命令会使用 `uv` 把 processor、API、agent 和 evaluation 包安装为可编辑的 Python 包，并为基础设施与前端项目运行 `npm install`。

### 第 2 步：配置部署

复制配置模板，并按你的 AWS 账户信息进行编辑：

```
cp config.yaml.example config.yaml
```

编辑 `config.yaml`：

```
appName: "metadata-harmonization-app"
env: "dev"

dev:
  profile: "your-aws-profile"
  deploymentName: "metadata-harmonization-dev"
  accountNumber: "123456789012"     # Your 12-digit AWS account number
  region: "us-east-1"
  deploymentStage: "dev"
  removalPolicy: "destroy"
  logLevel: "INFO"
  targetPlatform: "linux/amd64"
```

校验配置：

```
make validateConfig
```

### 第 3 步：部署基础设施

先引导（bootstrap）AWS CDK（仅首次需要），然后部署：

```
# First-time setup: prepare your AWS account for CDK
make bootstrap

# Deploy all AWS resources
make deploy
```

`make deploy` 会构建 API 容器镜像、将其推送到 Amazon ECR，并部署 AWS CDK 栈。这会创建 Amazon DynamoDB 表、Amazon S3 存储桶、Amazon Cognito 用户池以及 Amazon ECS Fargate 服务。

部署完成后，生成一个包含已部署资源标识符的本地 `.env` 文件：

```
make createLocalDotEnvFile
```

### 第 4 步：创建 Amazon Cognito 用户

部署完成后，在 Amazon Cognito 用户池中创建用户，以便他们登录该应用：

- 打开 [Amazon Cognito 控制台](https://console.aws.amazon.com/cognito/v2/idp/user-pools)。
- 选择由本次部署创建的用户池（例如 `metadata-harmonization-users`）。
- 转到 **Users**，然后选择 **Create user**。
- 输入用户的电子邮件地址和一个临时密码。
- 选择 **Create user**。

用户首次登录时会被提示设置一个永久密码。

### 第 5 步：在本地运行 Web 应用

启动 API 服务器与 Next.js 前端：

```
# Run both API and frontend together (recommended)
make runLocal
```

或分别在两个终端中运行：

```
# Terminal 1: API server
make runApiLocal

# Terminal 2: Frontend
make runUiLocal
```

通过以下地址访问系统：

- Web 界面：`http://localhost:3000`。
- API 文档：`http://localhost:8080/api/docs`。

### 第 6 步：运行元数据 agent

在 API 服务器运行的情况下，打开第二个终端并运行 agent：

```
uv run metadata-agent validate data/synthetic_dataset/simple_test.csv --interactive
```

该 agent 通过 Model Context Protocol（MCP）连接 API、校验数据集、取回失败报告，并自主施加校正。

## 人在回路

人工监督仍是维持元数据质量与信任的核心。该元数据校正与协调系统被设计为协作式工作流，让数据贡献者始终掌控自己提交的内容。界面会提供即时反馈、建议与可执行的校正，使贡献者能够高效地校验并批准元数据，同时保持数据完整性。

### UI 流程与交互

人在回路流程从数据贡献者通过浏览器界面上传自己的元数据文件开始。贡献者可以在启动校验之前在本地检视并修改元数据，从而借助轻量的客户端工具在提交前完成调整。准备就绪后，他们触发元数据处理，把数据集发送到云端进行自动校验与协调。工作流执行时会出现两种结果之一：

- 校验通过：元数据与 schema 完全对齐，并被输出到下游进行整合。
- 校验失败：针对缺失或不一致的字段生成详细的建议。

这些建议会直接显示在界面中，供审查与校正。贡献者可以检视被标记的条目、查看 AI 生成的建议，并接受、编辑或拒绝它们。满意之后，他们重新提交校正后的元数据以进行再次校验。成功提交的内容会被自动确认并传播到下游，从而完成协调循环。

## Agent 驱动的工作流

虽然人在回路系统极大加速了元数据协调，但它仍然需要贡献者主动参与：审查建议、接受校正并重新提交更新。对于涉及数百或数千条记录的数据集，这部分人力投入依然相当可观。为减轻这一负担、让贡献者能专注于研究而不是重复性的元数据校正，该工作流可以通过 agent 驱动的自动化加以扩展。

### 从人工到 agent 中介

在这一模式中，元数据 agent 作为一个自主或半自主系统运行，能够分析、校正并校验元数据记录。它同时使用确定性与非确定性推理系统，从基于规则的逻辑到 Amazon Bedrock 的 LLM 推理，来识别、解决并重新提交校正后的元数据。通过 MCP，该 agent 可以访问一组专用工具，包括远程元数据处理服务、schema 校验器和基于 embedding 的相似度模块。被调用时，agent 可以触发校验、取回失败报告与 AI 生成的建议，并根据上下文线索决定如何施加校正。

### 上下文感知与组织级 agent

对于高价值或领域特定的数据，单个通用 agent 可能缺乏必要的上下文。为提高准确性，可以部署组织专属的 agent，每个 agent 都能访问该群体的私有数据存储、实验日志与研究成果。通过把本体使用情况、实验方法与内部命名约定等全局上下文注入 agent 的推理 prompt，元数据校正会变得更加精确，也更符合本地数据标准。

该架构支持两个层面的适配：

- 局部推理：agent 使用当前数据集与既往提交来推断缺失或模糊的字段。
- 上下文增强：agent 从论文、实验方案与受控词表等更广泛的组织知识中取材，以自动校验并填充元数据字段。

## 治理与合规考量

从概念验证走向生产，需要把治理贯穿整个开发生命周期。有四个方面尤其值得关注。

数据完整性与变更追踪：组织应为元数据变更如何被记录与保留建立清晰的控制框架。科学可复现性依赖于数据来源的维护。正如人在回路工作流所展示的，系统会提供按类型与来源归类的变更摘要，在元数据提交期间支持审查与批准。机构应制定适合其监管环境的保留策略、审计轨迹要求与完整性控制。

架构治理：组织需要确定 AI 建议如何融入其数据工作流，特别是校正是需要先获批准才能应用，还是可以自动应用并在事后审查。这一决定会影响数据完整性、可回退能力以及与机构数据策略的一致性。架构选择应当连同清晰的理由一并记录，并设计为能够适应不断演进的标准与不断增长的数据量。

负责任的 AI 与内容安全：使用 LLM 推理的生产部署应纳入 Amazon Bedrock Guardrails，以界定模型行为的边界，并防范 prompt injection 攻击——当来自外部来源的元数据值被直接传入模型 prompt 时尤其如此。Guardrails 可以配置为过滤有害内容、强制主题边界并施加 grounding 校验。这会让 LLM 生成的校正建议始终锚定在工作流所定义的 schema 与受控词表上。对于 agent 驱动的部署，Guardrails 还可以依据每个 agent 的自主操作边界进行校验，帮助防止在缺乏适当监督的情况下应用非预期的校正。

安全：处理敏感基因组数据的 AI 系统必须满足与传统研究数据系统相同的安全标准。基于角色的访问控制、校验 pipeline 全程的数据保护，以及（对于 agent 驱动的工作流）自主操作的边界，都应当对照组织的风险画像进行评估。

## 清理

为避免持续产生费用，完成后请销毁所有已部署的 AWS 资源：

```
make destroy
```

这会拆除 AWS CDK 栈，包括 Amazon ECS 服务、Amazon DynamoDB 表、Amazon S3 存储桶和 Amazon Cognito 用户池。该命令在执行前会提示确认。

如果你在 `config.yaml` 中把 `removalPolicy` 设为 `"retain"`（生产环境推荐），那么部分资源会在栈删除后继续存在。请通过 AWS Management Console 或 AWS CLI 手动删除保留的 Amazon S3 存储桶与 Amazon DynamoDB 表。

要清理本地构建产物：

```
make clean
```

## 结论

本文介绍的由 AI 驱动的元数据校正与协调系统，解决了生物医学研究中一个长期存在的挑战：时间被花在数据标准化上，而不是科研工作上。两种实现方式——人在回路校验与 agent 驱动的工作流——为处于不同 AI 采用阶段的组织提供了灵活性。团队可以先从有人监督的校正开始，逐步建立对系统的信心，然后随着信任的增长过渡到更自动化的方式。

该系统有助于减少拖慢跨组织协作的摩擦。云原生架构可随组织规模扩展，模块化设计则允许按具体机构需求进行定制。随着数据量持续增长，自动化元数据协调在组织扩展时会愈发重要。请查看我们的 [GitHub 仓库](https://github.com/aws-samples/sample-intelligent-metadata-harmonization) 开始使用该方案。
