# Clarus Care 如何借助 Amazon Bedrock 交付对话式联络中心交互

*本文由 Clarus Care 的 Rishi Srivastava 与 Scott Reynolds 共同撰写。*

如今，许多医疗机构都在为如何高效处理大量患者来电而苦恼。从预约挂号、处方续配，到账单咨询和紧急医疗问题，机构面临的挑战是在维持高质量患者照护的同时及时作出响应。传统电话系统往往导致漫长的等待、沮丧的患者，以及每天要人工处理和排定优先级数百通电话、不堪重负的员工。这些沟通瓶颈不仅影响患者满意度，还可能延误关键的照护协调。

本文介绍医疗联络中心解决方案提供商 [Clarus Care](https://claruscare.com/) 如何与 [AWS Generative AI Innovation Center](https://aws.amazon.com/ai/generative-ai/innovation-center/)（GenAIIC）团队合作，开发一个由[生成式 AI](https://aws.amazon.com/ai/generative-ai/) 驱动的联络中心原型。该方案通过自动化语音机器人和聊天界面实现对话式交互与多意图解析。它还包含可扩展的服务模型以支撑业务增长、人工转接能力（在患者要求或紧急情况下启用），以及用于获取性能洞察的分析 pipeline。

Clarus Care 是一家医疗科技公司，通过 AI 驱动的来电管理系统帮助医疗机构管理患者沟通。Clarus 自动转写、排定优先级并路由患者留言，从而缩短响应时间、降低员工工作量并尽量减少等待时长。Clarus 是增长最快的医疗来电管理公司，服务 40 多个专科的 16,000 多名用户。该公司每年处理 1,500 万通患者来电，并保持 99% 的客户留存率。

## 用例概览

Clarus 踏上了一条创新之路，要把其患者沟通系统从传统的菜单式交互式语音应答（IVR）转变为更自然的对话式体验。公司的目标是彻底改变患者与医疗服务提供者的互动方式，打造一个由生成式 AI 驱动的联络中心，能够在单次交互中理解并处理患者的多种意图。此前，患者需要在僵化的菜单选项中导航来留下语音留言，这些留言随后被转写和处理。这种方式虽然可用，但限制了系统高效处理复杂患者需求的能力。意识到需要更直观、更灵活的方案，Clarus 与 GenAIIC 合作开发了一个 AI 驱动的联络中心，能够理解自然语言对话、管理多种意图，并在语音和网页聊天两种界面上提供无缝体验。该项目的关键成功标准包括：

- 自然语言语音界面，能在同一通来电中理解并处理账单咨询、预约、处方续配等多种患者意图
- 后端处理与向用户响应的延迟低于 3 秒
- 能够转写、记录并分析来电信息
- 面向紧急来电或患者要求直接与提供者通话的情形，具备智能转接能力
- 同时支持语音来电与网页聊天界面，以适配患者的不同偏好
- 可扩展的基础，支撑 Clarus 不断增长的客户群和持续扩张的医疗机构网络
- 高可用性，满足 99.99% 的 SLA 要求，以保障可靠的患者沟通

## 方案概览与架构

GenAIIC 团队与 Clarus 合作，使用 [Amazon Connect](https://aws.amazon.com/connect/) 和 [Amazon Lex](https://aws.amazon.com/lex/) 构建了一个由生成式 AI 驱动的联络中心，并通过 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 集成了 [Amazon Nova](https://aws.amazon.com/ai/generative-ai/nova/) 与 [Anthropic 的 Claude 3.5 Sonnet](https://www.anthropic.com/news/claude-3-5-sonnet) 基础模型。之所以选择 Connect 作为核心系统，是因为它能在语音和聊天渠道上提供全面的联络中心能力，同时保持 [99.99% 的可用性](https://aws.amazon.com/connect/sla/)。

Bedrock 的模型灵活性是该系统的核心，可根据准确率和延迟为不同任务选择模型。Claude 3.5 Sonnet 之所以被采用，是因为它具有高质量的自然语言理解能力；Nova 系列模型则针对低延迟进行了优化，并具备相当的自然语言理解与生成能力。下图展示了主联络中心方案的解决方案架构：

![AWS 架构图，展示一个对话式预约挂号系统：用户界面通过 Amazon Connect 连接到 Amazon Lex、Lambda fulfillment 函数和 Amazon Bedrock，数据源包括服务模型、消息系统和预约数据库。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/01/07/ml-193561.png)

该工作流由以下高层步骤组成：

- 患者通过电话或网页聊天界面发起联系。
- Connect 处理初始联系，并通过配置好的 contact flow 进行路由。
- Lex 负责转写并维护对话状态。
- 一个 [AWS Lambda](https://aws.amazon.com/pm/lambda/) fulfillment 函数通过 Bedrock 调用 Claude 3.5 Sonnet 和 Nova 模型来处理对话，以：划分紧急程度与意图 提取所需信息 生成自然回复 在适用时管理预约挂号

每个具体功能所使用的模型将在解决方案细节章节中说明。

- 当检测到紧急情况或患者要求与提供者通话时，会启动向员工的智能转接。
- 对话数据会经过分析 pipeline 处理，用于监控和报告（本文后文会介绍）。

团队在开发过程中应对的若干挑战包括：

- 以尽可能少的代码和配置改动，将联络中心通话流和服务模型格式化到可在不同客户之间互换的程度
- 满足自然对话体验的延迟要求
- 患者姓名的转写与理解

### 对话处理细节

该方案采用了一套复杂的对话管理系统，通过 Bedrock 的多模型能力和精心设计的 prompt 分层来编排自然的患者交互。该系统的核心在于 Bedrock 能够提供对多个基础模型的访问，使团队可以依据准确率、成本和延迟要求为每项具体任务选择最优模型。下图展示了对话管理系统的流程；NLU 代表自然语言理解。

![对话管理系统的流程](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/01/07/ml-193567.png)

对话流程以问候和紧急程度评估开始。当患者来电时，系统会立即使用 Bedrock API 评估情况是否需要紧急处理。这第一步确保紧急情况能被快速识别并得到适当路由。系统使用一个聚焦的 prompt，依据预定义的紧急意图类别列表分析患者的开场陈述，返回“urgent”或“non_urgent”以指导后续处理。

接下来，系统进入意图检测。这里的一项关键创新是系统能够在单次交互中处理多种意图。系统不再强迫患者走僵化的菜单树，而是可以借助强大的语言模型来理解患者同时提到处方续配和账单问题的情形，在保持自然对话流的同时把这些意图排队以便顺序处理。在提取过程中，我们会确保同时提取意图和来自用户输入的原文引用。这产生两个结果：

- 结合模型推理，确保提取到正确的意图
- 引用导致意图提取的对话历史，这样除非用户明确要求，否则同一意图不会被提取两次

一旦系统开始按顺序处理意图，它就开始向用户询问服务当前意图所需的数据。这发生在两个相互依赖的阶段：

- 检查缺失的信息字段，并生成自然语言 prompt 向用户索取信息
- 解析用户话语，分析并提取已收集的字段以及仍然缺失的字段

这两个步骤循环进行，直到收集到所需信息。系统在这一阶段还考虑提供者专属的服务，即按提供者收集所需字段。该方案会自动将患者提到的提供者姓名匹配到系统中正确的提供者。这能处理诸如“Dr. Smith”匹配到“Dr. Jennifer Smith”或“Jenny Smith”之类的差异，消除了传统 IVR 系统对严格姓名匹配或分机号的要求。该方案还包含智能转交能力。当系统需要判断患者是否应与某位特定提供者通话时，它会分析对话上下文，考虑所表达意图的紧急程度和路由需求。这一过程会保留对话上下文和已收集的信息，从而在请求人工介入时提供无缝体验。在整个对话过程中，系统通过 Lex 会话属性维护全面的状态跟踪，而自然语言处理则通过 Bedrock 模型调用来完成。这些属性充当对话的记忆，存储从用户已收集信息和对话历史，到检测到的意图和已收集信息的全部内容。这种状态管理使系统能够在多次 Bedrock API 调用之间保持上下文，营造更自然的对话流。

### 意图管理

意图管理系统通过一个分层的服务模型结构来设计，反映患者表达需求的自然方式。为了遍历这个分层服务模型，用户输入会被解析为自然语言理解结果，这些解析通过 Bedrock API 调用来完成。

该分层服务模型把意图组织为三个主要层级：

- **紧急程度层级**：将紧急服务与非紧急服务区分开，便于采取适当的处理和路由。
- **服务层级**：把预约、处方、账单等相关服务归组，形成合乎逻辑的类别。
- **提供者专属层级**：进一步细化，以适配特定提供者的要求和子服务

这一结构使系统能够高效地在可能的意图中导航，同时为不同医疗机构的定制保持灵活性。模型中的每个意图都包含自定义指令，这些指令可以动态注入 Bedrock prompt，从而无需改动代码即可实现高度可配置的行为。意图提取过程借助一个 prompt 利用 Bedrock 的高级语言理解能力，该 prompt 指示模型识别患者自然语言输入中存在的意图。prompt 中包含关于什么构成新意图的全面说明、所有可能意图的完整列表，以及响应的格式要求。我们并不强制把输入分类为单一意图，而是希望检测同时表达的多种需求。一旦识别出意图，它们就会被加入处理队列。系统随后按顺序处理每个意图，在多个层次上进行额外的模型调用，通过自然对话收集所需信息。为了同时优化质量和延迟，该方案以类似方式利用 Bedrock 的模型选择灵活性来应对各种对话任务：

- **意图提取** 通过 Bedrock 使用 Anthropic 的 Claude 3.5 Sonnet 进行详细分析，能够从自然语言中识别多种意图，确保患者无需重复信息。
- **信息收集** 通过 Bedrock 采用更快的模型 Amazon Nova Pro 进行结构化数据提取，同时保持对话语气。
- **回复生成** 通过 Bedrock 采用更小的模型 Nova Lite，基于对话状态生成低延迟、自然且富有同理心的回复。

这样做有助于确保该方案能够：

- 保持对话语气与同理心
- 只询问具体缺失的信息
- 确认已经提供的信息
- 处理诸如逐个字母拼写姓名之类的特殊情况

整个意图管理 pipeline 都受益于 Bedrock 统一的 Converse API，它提供：

- **一致的接口**，适用于各次模型调用，简化开发与维护
- **模型版本控制**，有助于在多次部署之间保持稳定的行为
- **面向未来的架构**，可在新模型可用时无缝采用

通过实施这套分层意图管理系统，Clarus 能为患者提供更自然、更高效的沟通体验，同时保留正确路由和信息收集所需的结构。把 Bedrock 的多模型能力与可配置的服务模型相结合，这种灵活性使得每家医疗机构都能直接定制，同时让核心对话逻辑保持一致且易于维护。随着 Bedrock 中可用新模型，系统可以更新以利用更强的能力，而无需进行重大架构改动，从而支持长期的扩展性与性能优化。

#### 预约

该方案的预约组件在独立的、专用模块中处理。如果在主处理器中检测到“appointment”意图，处理就会转交给预约模块。该模块以状态机的形式运行，由对话状态和下一步构成。预约系统的整体流程如下所示：

```
Scheduling System Flow

1. Initial State
   - Mention office hours
   - Ask for scheduling preferences
   - Move to GATHERING_PREFERENCES

2. GATHERING_PREFERENCES State
   - Extract and process time preferences using LLM
   - Check time preferences against existing scheduling database
   - Three possible outcomes:
     a. Specific time available
        - Present time for confirmation
        - Move to CONFIRMATION
     
     b. Range preference
        - Find earliest available time in range
        - Present this time for confirmation
        - Move to CONFIRMATION
     
     c. No availability (specific or range)
        - Find alternative times (±1 days from requested time)
        - Present available time blocks
        - Ask for preference
        - Stay in GATHERING_PREFERENCES
        - Increment attempt counter

3. CONFIRMATION State
   - Two possible outcomes:
     a. User confirms (Yes)
        - Book appointment
        - Send confirmation message
        - Move to END
     
     b. User declines (No)
        - Ask for new preferences
        - Move to GATHERING_PREFERENCES
        - Increment attempt counter

4. Additional Features
   - Maximum attempts tracking (default MAX_ATTEMPTS = 3)
   - When max attempts reached:
     - Apologize and escalate to office staff
     - Move to END

5. END State
   - Conversation completed
   - Either with successful booking or escalation to staff
```

预约流程中使用了三个主要的 LLM prompt：

- 提取时间偏好（使用 Nova Lite 以获得低延迟，并利用其偏好理解能力）

```
Extract current scheduling preferences from the conversation. The response must be in this format:<reasoning>

Explain:

- What type of preferences were expressed (specific or range)
- How you interpreted any relative dates or times
- Why you structured and prioritized the preferences as you did
- Any assumptions you made

</reasoning>
<json>
[
  {{
    "type": "specific",
    "priority": n,
    "specificSlots": [
      {{
        "date": "YYYY-MM-DD",
        "startTime": "HH:mm",
        "endTime": "HH:mm" 
      }}
    ]
  }},

  <!-- Repeat for each distinct preference -->

  {{
    "type": "range",
    "priority": n,
    "dateRange": {{
      "startDate": "YYYY-MM-DD",
      "endDate": "YYYY-MM-DD",
      "daysOfWeek": [], // "m", "t", "w", "th", "f"
      "timeRanges": [
        {{
          "startTime": "HH:mm",
          "endTime": "HH:mm"
        }}
      ]
    }}
  }}
  <!-- Repeat for each distinct preference -->
]

</json>

Guidelines:
- If time preferences have changed throughout the conversation, only extract current preferences
- You may have multiple of the same type of preference if needed
- Ensure proper JSON formatting, the JSON portion of the output should work correctly with json.loads(). Do not include comments in JSON.
- Convert relative dates (tomorrow, next Tuesday) to specific dates
- Keywords:
    * morning: 09:00-12:00
    * afternoon: 12:00-17:00
- Convert time descriptions to specific ranges (e.g. "morning before 11": 09:00-11:00, "2-4 pm": 14:00-16:00)
- Appointments are only available on weekdays from 9:00-17:00
- If no end time is specified for a slot, assume a 30-minute duration

Example:
(Example section removed for brevity)

Now, extract the scheduling preferences from the given conversation.

Current time: {current_time}
Today is {current_day}
Conversation:
<conversation>
{conversation_history}
</conversation>
```

- 判断用户是在确认还是拒绝时间（针对简单任务使用 Nova Micro 以获得低延迟）

```
Determine if the user is confirming or declining the suggested appointment time. Return "true" if they are clearly confirming, "false" otherwise.
<confirm>true|false</confirm>
User message: {user_message}
```

- 基于下一步生成自然回复（使用 Nova Lite 以获得低延迟并生成回复）

```
Given the conversation history and the next step, generate a natural and contextually appropriate response to the user.

Output your response in <response> tags:
<response>Your response here</response>

Conversation history:
{conversation_history}

Next step:
{next_step_prompt}
```

可能的步骤如下：

- **初始问候**

```
Ask the user when they would like to schedule their appointment with {provider}. Do not say Hi or Hello, this is mid-conversation.

Mention that our office hours are {office_hours}.
```

- **确认时间**

```
The time {time} is available with {provider}. 

Ask the user to confirm yes or no if this time works for them before proceeding with the booking.
Do not say the appointment is already confirmed.
```

- **展示备选时间**

```
Inform the user that their requested time {requested_time} is not available.
Offer these alternative time or time ranges with {provider}: {blocks}
Ask which time would work best for them.
```

- **询问新的偏好**

```
Acknowledge that the suggested time doesn't work for them.
Ask what other day or time they would prefer for their appointment with {provider}.
Remind them that our office hours are {office_hours}.
```

- **告知用户将转交到诊所**

```
Apologize that you haven't been able to find a suitable time.
Inform the user that you'll have our office staff reach out to help find an appointment time that works for them.

Thank them for their patience.
```

- **以预约确认结束对话**

```
VERY BRIEFLY confirm that their appointment is confirmed with {provider} for {time}.

Do not say anything else.

Example: Appointment confirmed for June 5th with Dr. Wolf
```

## 系统扩展

未来，Clarus 可以把联络中心的语音机器人（voicebot）与 [Amazon Nova Sonic](https://aws.amazon.com/ai/generative-ai/nova/speech/) 集成。Nova Sonic 是一种语音到语音的 LLM，能够以领先的性价比和低延迟提供实时、类人的语音对话。Nova Sonic 现已[与 Connect 直接集成](https://aws.amazon.com/about-aws/whats-new/2025/12/amazon-nova-2-sonic-real-time-conversational-ai/)。

Bedrock 还有若干附加服务，有助于扩展该方案并将其部署到生产环境，包括：

- 通过 [Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 原生支持检索增强生成（RAG）和[结构化数据检索](https://aws.amazon.com/about-aws/whats-new/2024/12/amazon-bedrock-knowledge-bases-structured-data-retrieval/)
- [Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 用于实施内容和 PII/PHI 防护措施
- [Bedrock Evaluations](https://aws.amazon.com/bedrock/evaluations/) 用于自动化与人工的对话评估
