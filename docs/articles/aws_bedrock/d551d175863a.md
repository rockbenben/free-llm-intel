# 使用 Amazon Nova Forge 为多轮强化学习定制奖励函数

在多轮强化学习（RL）中，你的自定义奖励函数决定了模型究竟学到什么。一个微妙地写错的奖励，可能在每条训练曲线看起来都很健康的同时悄悄教错东西。设计一个能在多轮、agentic 任务上站得住的奖励，是定制 [Amazon Nova 模型](https://aws.amazon.com/nova/)时最困难的部分之一。对于多轮训练，[Amazon Nova Forge](https://aws.amazon.com/nova/forge/) 通过其 [Bring Your Own Orchestration（BYOO）](https://docs.aws.amazon.com/nova/latest/nova2-userguide/nova-hp-rft-forge.html) 能力，在你自己的环境中运行你的奖励逻辑。你可以专注于定义什么才算好的结果，而由 Nova Forge 协调 rollout、消息传递以及跨轮次的对话状态。Nova Forge 还提供一个无服务器的多轮 RL 选项（现已正式可用），适合不希望自行管理该环境的团队。本文走的是 BYOO 路径。

Amazon Nova 提供多种定制方式，其中[强化微调](https://docs.aws.amazon.com/nova/latest/nova2-userguide/nova-reinforcement-fine-tuning.html)（RFT）尤为突出，因为它能通过迭代反馈把你想让模型具备的行为教给它。RFT 与监督微调（SFT）的思路不同。它不要求准备带标注推理路径的精选示例，而是从模型自身输出上的评估信号中学习。多轮 RFT 把这一点扩展到会在一系列步骤上行动的 agent，例如调用工具、执行代码或从错误中恢复。它优化的是整条轨迹上的累计奖励，而不是给单个回复打分。RFT 的核心是奖励函数：引导模型的打分机制，也正是由你设计的那部分。

本文聚焦奖励函数本身：如何设计一个 [GRPO](https://arxiv.org/pdf/2402.03300) 能从中学习的复合多轮奖励。本文还会展示如何在奖励内部安全地执行模型生成的代码，以及为什么要为每个组件加上度量，好让你能信任训练究竟在学什么。[本系列第 1 部分](https://aws.amazon.com/blogs/machine-learning/deploying-multi-turn-rl-infrastructure-for-amazon-nova-on-amazon-sagemaker-hyperpod/)介绍了 Amazon SageMaker HyperPod 与 Nova Forge 基础设施，也介绍了运行这些奖励的训练配置。最后我们会讨论那些可能悄悄让奖励崩塌的陷阱，它们来自一次真实运行——在那次运行中，权重最高的组件实际上完全没有贡献任何学习信号。我们会说明如何发现它们。全文代码仅作示意，可作为你自己奖励实现的起点。

- 熟悉强化微调与 GRPO。

## 使用 Amazon Nova Forge 构建自定义奖励

RFT 的工作方式是：从当前模型采样 completion，并用一个奖励函数为它们打分。在 Nova Forge 中，奖励函数是你在代码里写的评分器，而不是另外训练出来的奖励模型。它可以是校验输出的基于规则的检查（带可验证奖励的强化学习），也可以调用另一个大语言模型（LLM）来评判回复，这种做法称为 LLM-as-Judge。

随后 RFT 调整模型权重，使高奖励的 completion 更可能出现。Nova Forge 使用 GRPO。对于每段对话，GRPO 用奖励函数对 K 个模型 rollout 排序。GRPO 根据这一批次归一化后的奖励（优势值，advantage）用排名最高的那些 completion 更新模型。使用 GRPO 的 RFT 是一项基础技术，相对初始的 SFT 能带来明显的性能提升。

> 奖励信号只能通过它在一个组内制造出的差异来影响学习。如果某一项在组内每个 completion 上都取相同的值，它对优势值毫无贡献，因此对梯度也毫无贡献。

你的奖励函数在 Nova Forge 中如何运行取决于任务。对于单轮 RFT，你把奖励注册为一个 AWS Lambda 函数，并通过 `reward_lambda_arn` 让 recipe 指向它。像本文这样的多轮任务超出了单次 Lambda 调用所能支持的范围。多轮对话与长时间运行的打分都会超过 Lambda 15 分钟的调用上限。对这类任务，Nova Forge 使用 BYOO。你设置 `rollout.delegate: true`，并在环境容器中（例如在 Amazon ECS 上）运行你的环境与奖励逻辑。Nova Forge 把每个 rollout 委派给你的环境，然后把完成的 episode 收集回来用于训练。你的容器管理多轮交互与对话状态：它运行用户模拟器、执行代码并调用 verifier，然后为每个样本返回一个聚合奖励（`aggregate_reward_score`），外加一个可选的各组件分数列表（`metrics_list`）。[本系列第 1 部分](https://aws.amazon.com/blogs/machine-learning/deploying-multi-turn-rl-infrastructure-for-amazon-nova-on-amazon-sagemaker-hyperpod/)介绍了这套基础设施及其 AWS Cloud Development Kit（AWS CDK）部署。本文聚焦奖励。

## 奖励评估如何工作

训练任务会针对每个 prompt 从 Nova 模型生成候选 rollout。在多轮任务中，一个 rollout 是一个完整的*episode*，包含一系列轮次（一条*trajectory*），而不是单个回复。你的奖励函数会接收每个 rollout 并执行三个步骤：

- **运行任务逻辑。** 对于对话式任务，这可能包括一个逐轮回应模型的用户模拟器。
- **为完成的轨迹打分**，跨一个或多个奖励组件（例如任务正确性、某个中间行为信号以及惩罚项），并通过 `metrics_list` 报告每一项。
- **为每个 rollout 返回一个聚合奖励**（`aggregate_reward_score`），训练会把它转化为组内优势值。

![多轮 rollout 示意图：Nova Forge 委派给环境容器，容器为 GRPO 返回奖励分数](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/07/30/ML-20735-2.png)

*图 2 —— 一次多轮 rollout：Nova Forge 委派给你的环境容器，容器询问模拟器或运行已提交的代码，然后为 GRPO 返回奖励分数*

这个循环会在许多训练步上重复，逐步把模型塑造成最大化整条序列上的累计奖励。模型会朝你的奖励实际奖励的方向优化——而正如我们将展示的，这并不总是你写下那些东西时以为的方向。

## 选择多轮奖励的结构

单一标量奖励很容易被钻空子，而单一的终局奖励在多轮任务中往往过于稀疏、难以学习。因此，大多数生产环境中的多轮奖励会组合三类信号：结果奖励、行为奖励和惩罚项。

episode 级（结果）奖励反映最终产物是否达成了目标。例如，单元测试是否通过，或者工作流是否完成。它们针对的是你最终关心的东西，但往往稀疏，而且在训练早期接近零。

轮次级（行为）奖励反映模型是否表现出你想要的中间行为，例如行动前先询问、调用正确的工具，或避免陷入循环。当结果奖励过于稀疏、无法教会这些行为时，它们最适合用来塑造行为；不过如果设计不慎，它们也可能在毫无实际进展的情况下被拿到。惩罚项则明确抑制某种失败模式，例如猜测、重复或停滞。它们把好的策略与坏的策略区分开，让优化器看得到梯度。

把这些组合起来，让模型既学到行为*也*学到结果，同时不让某一个组件掩盖或饿死另一个组件。本文余下部分会把这一点具体化。我们会为一个真实任务设计一个四组件奖励，并在其中安全地执行模型生成的代码。然后我们会梳理可能让这类奖励崩塌的陷阱以及如何修复。

## 实战示例：教 Amazon Nova Lite 2.0 先问再写代码

我们在 500 个不重复的编程任务上构建了一个多轮协作编码任务。我们在 [Amazon SageMaker HyperPod](https://aws.amazon.com/sagemaker/ai/hyperpod/) 上，用结合 Low-Rank Adaptation（LoRA）的 GRPO 做多轮 RFT，在其上训练 Amazon Nova Lite 2.0，并把奖励实现在一个客户托管的环境容器内（即 Nova Forge 的 BYOO 路径）。

机制如下：

- 模型看到的是一个简短、**描述不充分**的编码请求。
- 一个**用户模拟器**私下持有完整规格，只有在模型询问时才透露某个细节。
- 每一轮，模型要么提出澄清问题，要么提交代码。如果它提问，模拟器作答，对话继续。如果它提交代码，rollout 结束，你的奖励处理器会拿这段代码去跑隐藏的单元测试，为正确性打分。（安全地运行模型生成的代码是一个问题，我们稍后再回到它。）

设计意图是：猜测会产出错误的代码，而询问会揭示隐藏的细节并导向正确的代码。「先问」应当由任务本身强制产生。

### 设计奖励

让目标行为可以被直接、独立地奖励，并明确惩罚失败模式。对这个任务，奖励是四个组件的加权和：

| **组件** | **权重** | **定义** |
| --- | --- | --- |
| `correctness` | 1.0 | 最终代码通过的隐藏单元测试比例 |
| `asked_before_coding` | 0.6 | 若第 1 轮先问、随后提交则为 1.0；若稍后询问再提交则为 0.6；否则为 0（未设门控） |
| `guessed_immediately` | 0.4 | 惩罚：若第一轮就是代码且没有提问，则为 -1.0 |
| `loop_penalty` | 0.2 | 若最后两轮相似度超过 80%，则为 -0.5 |

两条原则驱动这个设计。第一，把你想要的行为解除门控：`asked_before_coding` 单独计分，而不以 `correctness` 为条件，但它确实要求模型最终提交代码，这堵上了「一直问、永不作答」的漏洞。第二，惩罚失败模式：`guessed_immediately` 让猜测严格劣于询问，从而在 GRPO 组内恢复策略之间的差异——正是算法产生梯度所需的差异。

在环境容器的奖励处理器中调用这些组件打分器，并通过 `metrics_list` 报告每个值：

```
def asked_before_coding(completion, answer, **kw) -> float:
    msgs = _messages(completion, kw)
    first_q = _first_question_turn(msgs, parser)
    final = _final_code(completion, parser)
    committed = bool(final) and not _is_question(final)
    if first_q == 1 and committed:
        return 1.0          # asked first, then committed (ideal)
    if first_q is not None and committed:
        return 0.6          # asked later, then committed
    return 0.0              # never asked, or asked but never committed

def guessed_immediately(completion, answer, **kw) -> float:
    for m in _assistant_turns(completion, kw):
        code = _code_of(parser.parse(m["content"]))
        return -1.0 if (code and not _is_question(code)) else 0.0
    return 0.0
```

### 安全地执行模型生成的代码

`correctness` 组件会把模型生成的代码拿去跑单元测试。**RL 下的模型输出会通过探索被持续优化，因此应把它视为未经校验。** 容器运行在它自己的隔离执行环境中，但你仍然应当采取预防措施。不要向生成的代码暴露凭证或网络。施加资源限制，并在临时目录中运行。使用每次运行随机的哨兵值，使模型无法通过把预期标记写到 stderr 来伪造结果。对于需要额外隔离的执行，调用专用的沙箱。下面这个 harness 展示了该模式：

```
import resource, secrets, subprocess, sys, tempfile
from pathlib import Path

def run_tests(code: str, test: str, timeout_s: int = 30) -> float:
    nonce = secrets.token_hex(8)                       # unforgeable per-run marker
    harness = (
        "import sys, unittest, json\n"
        f"{code}\n\n{test}\n\n"
        'if __name__ == "__main__":\n'
        "    r = unittest.TextTestRunner(stream=sys.stderr, verbosity=0).run(\n"
        "        unittest.TestLoader().loadTestsFromModule(sys.modules[__name__]))\n"
        f"    sys.stderr.write('__{nonce}__' + json.dumps("
        "{'total': r.testsRun, 'passed': r.testsRun - len(r.failures) - len(r.errors)}) + '__"
        f"{nonce}__')\n"
    )
    def _limit():
        resource.setrlimit(resource.RLIMIT_CPU, (timeout_s, timeout_s))
        resource.setrlimit(resource.RLIMIT_AS, (2 * 1024**3, 2 * 1024**3))   # 2 GB
        resource.setrlimit(resource.RLIMIT_NPROC, (64, 64))
    with tempfile.TemporaryDirectory() as cwd:
        path = Path(cwd) / "h.py"
        path.write_text(harness)
        try:
            proc = subprocess.run(
                [sys.executable, str(path)], capture_output=True, text=True,
                timeout=timeout_s, cwd=cwd, env={"PATH": "/usr/bin"},   # no creds, no network env
                preexec_fn=_limit,
            )
        except Exception:
            return 0.0
    # parse the nonce-delimited summary and validate the test count before scoring
    ...
```

还要把实际运行的测试数量与预期数量做校验，这样模型就无法用自己那些轻易通过的测试来稀释分数。对于部署在真实环境中的奖励函数，请落实这些安全措施，而不是把它们当作可选项。

## 陷阱：什么会让奖励崩塌，以及如何修复

多轮奖励设计有一组众所周知的失败模式。奖励黑客（reward hacking）是指模型钻代理指标的空子而不是真正达成目标。训练不稳定是指更新发散、熵崩塌，或 Kullback-Leibler（KL）项爆炸。奖励崩塌是指信号退化到组内差异消失、学习悄无声息地停止。前两种通常会在转录文本或 loss 与 KL 曲线中自己暴露出来。崩塌才是危险的那个：聚合奖励、loss 和 completion 长度曲线看起来都可能很健康，而你指望的那个组件却什么也没贡献。本节讨论在这个任务上让我们花掉最多时间的两种崩塌失效，以及如何发现它们。

### 当奖励坍缩为单一策略

这个奖励的早期版本把询问奖励门控在 `correctness` 之后。只有当最终代码也通过时，你才能拿到询问奖励。它同时还加了一个奖励更短对话的效率项。训练崩了。模型收敛到第一轮就猜。平均奖励冻结，GRPO 优势值归零。

造成它的是两个设计错误。第一，门控设在一个无法达成的条件之后。在这些困难任务上正确性接近零，于是询问奖励几乎从不触发。我们想奖励的行为对优化器不可见。第二，效率项有一个退化的最优点。轮次越少它越大，于是策略坍缩到单一、不作承诺的一轮。每个 completion 都长得一样，组内差异消失，学习停止。

修复方案就是上一节的设计：把你想要的行为解除门控，并明确惩罚失败模式。两者到位之后，不同策略会在组内持续产出不同的奖励，从而保住 GRPO 学习所需的方差。

### 悄然死掉的组件

当一个奖励组件对一个 GRPO 组内的每个 completion 都返回相同的值时，它的组内方差为零。因此，即使它的权重最高，它对优势值或梯度也毫无贡献。仍在变化的那些组件会让聚合奖励、策略 loss、优势值和 completion 长度看起来都很健康，所以曲线永远不会揭示问题。在代码类奖励中，一个常见原因是正确性打分器对每个 rollout 都返回 0，因为 harness 从未真正执行模型的输出。这可能源于入口点名称不匹配、导入失败，或某个设置错误导致每个测试在断言运行之前就失败。在我们的运行中，情况正是如此：模型的澄清提问率上升到大约 34–96%，而代码正确性几乎没动，因为 `correctness` 打分器对每个 rollout 都返回了相同的值。

要发现死掉的组件，请跟踪每个组件的组内标准差，而不是聚合奖励曲线。聚合曲线会用那些活着的通道掩盖死掉的通道。如果这个离散度停在零或接近零，那么无论权重多高，这个组件都没有在训练。代码类奖励中通常的根因是正确性打分器卡在 0，因为 harness 实际上从未绑定并运行模型的输出。修好它，并确认离散度变成非零。

### 做好度量，以便尽早发现这些问题

有几个习惯能发现这些失效，它们本可以在第一天就发现我们的问题：

- **度量每个组件对优势值的贡献，而不只是每个组件的奖励。** 通过 `metrics_list` 报告每个组件，并跟踪它的均值*以及*组内标准差。任何组内方差接近零的组件，无论权重多高，对学习都没有贡献。你也许会把 0.000 的平坦奖励均值当作「这些任务本来就难」而放过，但平坦的组内方差是毫无歧义的。把这自动化成一张按组件统计的优势方差面板，让死掉的通道被自动标出，而无需人工检视。
- **按你正在检验的组件排序阅读转录文本，而不是按总奖励排序。** 按总奖励排序会把死掉的组件藏在活着的组件后面。按可疑组件排序则能立刻暴露问题。
- **对你声称在起作用的每个组件做消融或复活实验。** 如果移除一个组件后没有任何变化，那它并没有在起作用。如果复活一个组件后，你原以为已经优化好的指标有所回升，那它并没有在目标函数里。
- **为组内方差而设计。** GRPO 从同一 prompt 的不同 completion 之间的差异中学习。不可达的门控、退化的塑形最优点和饱和项都会压缩这种差异，即使奖励看起来正常，学习也会停止。把目标行为解除门控，并惩罚失败模式，让策略彼此区分开。
- **小心一个稠密奖励饿死另一个。** 我们那个稠密的询问奖励一旦饱和，稀疏的 `correctness` 奖励就无法再推动策略。如果某个行为塑形项占据主导，你真正关心的结果项可能永远拿不到梯度。可以考虑在塑形项饱和后调低它的权重，或者调高结果项的权重。
- **把模型输出视为未经校验。** 对生成的代码的任何执行都做沙箱隔离（无凭证、无网络、限制资源），并让 verifier 无法被伪造（随机哨兵值、校验测试数量）。

## 清理

本文中的训练运行与环境使用了 SageMaker HyperPod 和 Amazon ECS 资源，在运行期间会产生费用。实验结束后，请按本系列第 1 部分中的拆除步骤删除 SageMaker HyperPod 集群与 Amazon ECS 环境，以停止最大的那部分费用。如果不再需要，请从你的 Amazon S3 存储桶中删除 rollout 数据与检查点。

## 结论

奖励函数是 RFT 中由你设计的那部分，也是微妙失效藏身之处。在你的运行中，模型可能学到了你为之训练的行为，而你关心的某一项对学习毫无贡献，却没有任何聚合指标揭示这一点。真正解决问题的是更好的度量，而不是更好的算法。度量每个组件对优势值的贡献，透过你正在检验的组件的视角去读转录文本，并对你声称在起作用的东西做消融。在 Amazon Nova Forge 上使用自定义奖励函数，意味着你对奖励有完全的控制，也就意味着把它做对的责任在你身上。关于让这些运行可复现的基础设施与 AWS CDK 部署，见[本系列第 1 部分。](https://aws.amazon.com/blogs/machine-learning/deploying-multi-turn-rl-infrastructure-for-amazon-nova-on-amazon-sagemaker-hyperpod/)
