# 由 Amazon Bedrock 驱动的 Text-to-SQL 方案

用 Amazon Bedrock 构建 text-to-SQL 方案，可以缓解数据驱动型组织中最顽固的瓶颈之一：从提出业务问题到拿到清晰、有数据支撑的答案之间的延迟。你可能也熟悉这样的困境：自己那一次性的问题只能在队列里排在高影响力工作的后面，还要在相互竞争的优先级之间周旋。text-to-SQL 方案能为现有团队补充能力——业务用户自助完成日常分析问题，从而为组织释放技术产能，用于复杂、高价值的计划。“我们按客户分群的营收同比增长是多少？”这类问题，现在任何人都能问到，而不会给技术团队增加额外的工作量。

许多组织发现，获取数据洞察仍然是业务决策过程中的一大瓶颈。传统做法要么需要学习 SQL 语法，要么需要等待技术资源，要么只能将就使用预置仪表板，而它们未必能回答你的具体问题。

在本文中，我们将展示如何使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 构建一套自然语言 text-to-SQL 方案，把业务问题转换为数据库查询，并返回可据以行动的答案。模型返回的不只是原始 SQL，还包括执行结果，这些结果会在数秒而非数小时内被综合成清晰的自然语言叙述。我们会带你了解架构、实现策略，以及在大规模部署该方案过程中总结的经验教训。读完后，你将理解如何构建自己的 text-to-SQL 系统，弥合业务问题与数据可访问性之间的鸿沟。

## **为什么传统商业智能力有不逮**

值得一提的是，像 Amazon Quick 这样的工具已经能有效满足许多自助式分析需求，包括用自然语言查询仪表板和自动生成洞察。当你的分析需求与结构化仪表板、经过整理的数据集和受治理的报告工作流相匹配时，这类工具是非常合适的选择。而当用户必须在带有深厚组织业务逻辑和领域特定术语的复杂多表 schema 之间查询，并提出超出预配置仪表板数据集支持范围的一次性问题时，定制的 text-to-SQL 方案才显得有价值。

构建 text-to-SQL 方案会暴露出三个根本挑战，正是它们让需求超出传统 Business Intelligence（BI）工具的能力范围：

- **SQL 专业能力门槛阻碍了快速分析。**大多数业务用户缺乏访问复杂数据所需的 SQL 技术知识。看似简单的问题往往需要多表 join、时间计算和层次聚合。这种依赖形成了瓶颈：业务用户要长时间等待定制报表，而分析师则把宝贵时间花在重复的查询请求上，而不是战略性分析。
- **即便现代 BI 系统也有灵活性边界**。现代 BI 工具在自然语言查询和自助式分析方面已取得长足进步。但这些能力通常只在预先整理的语义层、受治理的数据集或预先建模的仪表板内效果最好。当业务用户需要探索整理边界之外的内容——一次性 join、临时性的组织特有计算，或查询语义层之外的原始数仓表——他们仍然会受制于必须由技术介入的限制。定制的 text-to-SQL 方案直接针对你的数据仓库 schema 运行，并动态检索业务上下文，而不是依赖预先配置的语义模型，从而填补了这一空白。
- **上下文与语义理解造成转换鸿沟。**即便有了 SQL 访问权限，把业务术语转换成正确的数据库查询依然颇具挑战。*attainment*、*pipeline* 和 *forecast* 这类术语各自有独特的计算逻辑、特定的数据源要求，以及因组织而异的业务规则。要弄清该 join 哪些表、指标如何定义、该应用哪些过滤条件，需要深厚的机构知识，而大多数用户并不容易获得这些知识。

在构建自己的方案时，请考虑系统将如何编码这些深厚的业务上下文（战略原则、客户分群规则和运营流程），让用户无需理解复杂的数据库 schema 或 SQL 语法，也能更快地做出数据驱动的决策。

## **工作原理：使用体验**

在深入架构之前，先看看从用户视角来看这套体验是什么样的。

一位业务用户在对话式界面里输入问题，比如*“与去年相比，今年我们的营收在头部客户分群中呈现怎样的趋势？”*在幕后，系统会在几秒内完成以下几件事：

- **理解问题。**它判断这是一个单步查询，还是需要拆分成多个部分的复杂问题。在这个例子中，它识别出“营收趋势”“同比比较”和“头部客户分群”各自需要不同的数据检索步骤。
- **检索业务上下文。**系统在编码了贵组织特定指标定义、业务术语、表关系和数据规则的知识图谱中进行搜索。它知道在你的环境中 *revenue* 意味着什么、哪些表包含它，以及*客户分群*是如何定义的。
- **生成并校验 SQL。**系统产出一条结构化的 SQL 查询，用确定性检查校验其正确性与安全性，然后针对你的数据仓库执行。如果校验发现问题，它会自动修改并重试，无需人工介入。
- **综合答案。**原始查询结果会被还原成带支撑数据的自然语言叙述，让用户既得到洞察，也拥有足以信任它的透明度。

结果是，业务用户能在数秒到数分钟内得到复杂分析问题的答案，并能完全看清背后的逻辑。分析师则从重复的查询工作中解脱出来，专注于价值更高的战略分析。

## **方案总览**

为了交付这套体验，该方案组合了三项核心能力：

- 用于自然语言理解和 SQL 生成的 [Amazon Bedrock](https://aws.amazon.com/bedrock/) foundation models（基础模型，FMs）
- 用于业务上下文检索的 Graph Retrieval-Augmented Generation（GraphRAG）
- 用于快速执行查询的高性能数据仓库。

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 在这套架构中扮演核心角色，同时提供 large language model（LLM）推理层和 agent 编排运行时。[Amazon Bedrock](https://aws.amazon.com/bedrock/) 提供对大量 FMs 的访问，因此团队可以依据不断变化的性能、成本和延迟要求选择并替换模型，而无需重新设计系统架构。

如架构图所示，

- [Amazon Bedrock AgentCore Runtime](https://aws.amazon.com/bedrock/agentcore/) 作为中心编排层，承载一个 supervisor Agent，协调端到端工作流。它路由用户问题，调用 GraphRAG Search Tool 进行上下文检索，强制执行行级安全（Row-Level Security），触发 SQL 生成与校验，并针对数据库（Amazon Redshift）执行查询。该运行时支持多种入口，包括 MCP 和 HTTP 协议，从而既能与 AWS Quick Sight 这类嵌入式分析界面集成，也能与自定义 Web 界面集成。
- [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 还提供内置的可观测性，把 agent 的执行轨迹和性能指标送入 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)，用于监控、调试和持续优化。这个托管运行时免去了构建自定义 agent 基础设施这类无差别的繁重工作，让团队可以专注于业务逻辑、prompt 调优和领域知识积累。

该架构作为一个经过编排的多 agent 系统运行，包含五个关键阶段：

### **阶段 1：问题分析与拆解**

问题到达后，问题处理器首先对它进行分类。像*“Q4 的总营收是多少？”*这样直白、原子化、基于事实的问题，会被直接路由到数据检索 pipeline。复杂或多部分的问题则被拆解成自包含、相互独立的子问题，可以由不同的 agent 团队并行处理。正是这一拆解步骤，让系统能够处理横跨多个数据域、时间段或业务维度的复杂分析问题。

### **阶段 2：知识图谱与 GraphRAG 上下文检索**

系统正是在这里解决了上下文障碍，这也是它与朴素 text-to-SQL 方法之间最关键的差异所在。

基于 [Amazon Neptune](https://aws.amazon.com/neptune/) 和 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 构建的知识图谱构成语义基础。它存储贵组织的表本体（table ontology），并刻画业务实体、指标、术语与组织层级之间的关系。关键在于，这张图谱会用表所有者和主题专家提供的领域知识加以丰富——包括业务特定的描述、指标定义、术语映射，以及从结构化配置文件中加载的分类标签。

系统处理问题时，会执行一次轻量级的 GraphRAG 搜索，分三个阶段进行：

- 向量搜索（使用 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/)）：找出与用户问题中概念语义相关的列值、列名和表描述。
- 图遍历（使用 [Amazon Neptune](https://aws.amazon.com/neptune/)）：沿知识图谱中的关系游走，从匹配到的值到其所属列再到其所属表，从而完整呈现哪些数据资产相关以及它们如何连接。
- 相关性评分与过滤：对检索到的上下文排序并组织，让 SQL 生成器恰好收到它需要的信息——正确的表、正确的列、正确的 join 路径和正确的业务逻辑。

知识图谱及其关联数据会定期刷新，以反映 schema 变更、新表以及不断演进的业务定义。这一上下文层越丰富，下游 SQL 生成就越准确。

### **阶段 3：结构化 SQL 生成与校验**

系统使用 Amazon Bedrock 的[函数调用](https://docs.aws.amazon.com/bedrock/latest/userguide/tool-use.html)能力，把 SQL 查询作为结构化数据产出。这会强制严格的输出格式，免去对脆弱的后处理或复杂正则表达式的需求，并显著提升可靠性。

生成的查询随后会经过在 Abstract Syntax Tree（AST）层面运行的确定性 SQL 校验器。这些校验器会主动标记潜在高风险操作，即语法正确但语义危险的查询（例如无界扫描、缺少过滤条件、聚合逻辑错误）。当校验器标记出问题时，它会返回详细反馈，说明问题所在并建议修改。

为进一步提升稳健性，整个循环被封装在一个轻量级的 SQL 生成 agent 中，它会自动迭代，直到产出有效、可执行的查询，或用尽可配置的重试次数。这种方法的目标是交付远高于仅靠 prompt engineering 的可靠性。

### **阶段 4：测试时并行计算**

对于有歧义或复杂的问题，系统可以把同一个问题同时提交给多个并行 agent，从而生成多个潜在答案或推理路径。结果通过多数投票综合，选出最可靠的输出。这对于可以有多种解读的问题尤其有价值，并能有意义地同时提升准确性和稳健性。

### **阶段 5：回答综合**

最后，包括数字、data frame 和执行日志在内的原始查询结果会被综合成自然语言叙述，用户得到的就是可据以行动的答案。查询全程保持透明：用户随时可以检查生成的 SQL 和底层数据，从而建立对系统输出的信任。

## **获得生产级质量的关键策略**

只有架构还不够。以下策略来自大规模部署该方案的实践，对于达到生产使用所要求的准确性、安全性与响应速度至关重要。

### **让最终用户塑造 prompt**

即便在经验丰富的用户中，每个人对歧义术语的默认解读也常常不同，对含糊问题的回答预期也各异。我们建议构建一个**定制化界面**（例如 Web 应用），让表所有者和指定的高级用户能够在受治理的边界内定制 prompt。定制内容应当经过校验护栏，这些护栏会强制执行内容策略、限制 prompt injection 尝试，并确保修改不超出已批准的模板和参数范围。这有助于在防止不受限制的自由文本修改的同时，仍把领域知识和偏好纳入系统。事实证明，这项定制能力对于获得不同业务领域所需的细致理解至关重要。你的方案应当容纳这些差异，而不是强制推行一刀切的做法。

### **把 SQL 校验当作安全关键层**

仅靠 prompt engineering 无法消除那些产出语法有效但语义错误的 SQL 的错误。这类错误尤其危险，因为它们返回看似合理的结果，会悄无声息地侵蚀用户信任或导致错误决策。由于 SQL 是一种定义良好的语言，确定性校验器可以在查询到达数据库之前捕获一大类此类错误。在内部测试中，这一校验层有效避免了生成查询中的严重错误。请把它作为不可妥协的安全机制优先对待。

### **大力优化延迟**

习惯了对话式 AI 的用户期待近乎即时的响应。虽然检索实时数据并执行计算本身就比从静态知识库作答更慢，但延迟仍必须作为一等用户体验问题被主动管理。性能分析显示，该工作流涉及多个步骤，而这些步骤的累计时间相对于单纯的 SQL 执行时间而言，才是最大的优化空间。

优化时应聚焦于：

- **agent 并行执行** – 并行而非串行地处理多部分问题。这能大幅缩短复杂查询的总耗时。
- **高性能分析存储** – 使用列式数据库，它们在商业智能中常见的重聚合工作负载上表现出色。
- **Token 优化** – 通过 prompt 优化和响应格式标准化，尽量减少每次 agent 交互的输入与输出 token。减少对工具调用型 agentic 框架的依赖——在这类框架中，每次调用都会迫使 agent 重新摄入不断增长的上下文。

经过这些优化，在我们的部署中，简单的 SQL 查询通常能在约 3–5 秒内生成。实际响应时间会因数据仓库性能、查询复杂度、模型选择和知识图谱规模等因素而不同。我们建议以你自己的环境做基准测试，为交互式业务分析设定现实的延迟目标。

### **从一开始就内建安全与治理**

实现 Row-Level Security（RLS）集成，让用户始终只能看到其有权访问的数据。系统维护复合授权表（entitlement tables），以强制执行来自你现有组织系统的访问控制策略。当用户提交查询时，相应的 RLS 过滤条件会在执行前自动注入到生成的 SQL 中。这些过滤对用户是透明的，但执行起来十分严格。请设计这一层，使其在坚持严格数据治理标准的同时，不为用户体验增加摩擦。

## **实施结果与影响**

在你遵循本文所述的架构与策略之后，text-to-SQL 方案可以在数据可访问性和分析生产力方面带来显著改善：

- **速度提升**让复杂业务问题的答案在几分钟内给出，而传统方法需要数小时甚至数天。那些以前需要定制 SQL 开发、涉及多表 join、时间计算和层次聚合的问题，现在可以通过自然语言获得答案。
- **分析民主化**帮助销售运营、财务规划和高管层的非技术业务用户在不懂 SQL 的情况下完成复杂数据分析。这通常能减轻数据工程团队的分析负担，让他们专注于战略举措，而不是重复的查询请求。
- **复杂查询处理**通过以下能力支持多维营收分析：自动分群；带差异说明的同比和环比趋势；细颗粒度且结合使用模式的客户洞察；带目标对比的预测差异分析；跨时间段和业务单元的功能间基准比较。

## **展望**

由 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 驱动的 text-to-SQL 方案，是让业务用户更易获得数据分析能力的一大进步。使用 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 的多 agent 架构支持复杂查询拆解与并行处理，而知识图谱提供业务上下文与语义理解。这些组件共同交付准确、快速、易用的分析能力，让业务用户在没有技术障碍的情况下做出数据驱动的决策。

在构建自己的方案时，可以考虑把知识图谱的覆盖范围扩展到更多业务域、通过高级缓存策略优化响应延迟，以及与更多企业数据源集成。[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 提供值得探索的增强输出校验与安全能力，而 [Amazon Bedrock Flows](https://aws.amazon.com/bedrock/flows/) 为 agentic 工作流提供精细的编排模式。

通过 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 获得的 FM 灵活性、agent 编排能力和知识库集成仍在持续演进，使数据分析对各类组织的业务用户来说变得越来越直观、越来越强大。
