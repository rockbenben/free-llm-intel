# 扩展 agentic AI：避免厂商锁定的企业级模式

在企业范围内扩展 agentic AI，需要既能保持灵活性、又能避免厂商锁定的架构模式。本文是我们“规模化多 agent 系统”系列的第二部分。在本文中，我们考察机器学习（ML）团队如何在由框架、模型与厂商构成的“multi-everything”环境中运行 agentic AI 系统。我们也会讨论让这些系统共同扩展的原则。

在[《面向 Amazon 大规模多 agent 编排模式的高级微调技术》](https://aws.amazon.com/blogs/machine-learning/advanced-fine-tuning-techniques-for-multi-agent-orchestration-patterns-from-amazon-at-scale/)一文中，我们探讨了如何在单个用例或领域内设计与优化多 agent 编排。那篇文章聚焦于需要多个 agent 通过协调工作流、分解任务、以及借助结构化协作提升准确性来应对复杂性的场景。

然而在实践中，企业 AI 系统很少只停留在单一领域。

随着采用范围扩大，大型企业中的 ML 平台团队会遇到另一种挑战。问题不再是“如何在一个系统内编排 agent”，而是“如何在 multi-everything 环境中运营许多这样的系统”。多个框架、模型、厂商与团队共存于同一家企业内，各自以自己的节奏演进。

随着组织扩展这些系统，一致地构建、定制与部署模型的能力变得至关重要。实践中，这要求对模型生命周期管理与规模化推理采取统一的方法。正是在这一领域，Amazon SageMaker 发挥着基础性作用：在支持企业级一致性的同时不限制灵活性。

本文探讨扩展 agentic AI 系统所需的架构原则与模式，同时保持灵活性并避免厂商锁定。

## multi-everything 环境的现实

企业 AI 系统默认会演化为异构格局。不同团队依据自身需求采用不同框架。有些团队优先考虑结构化工作流，有些专注于 agent 之间的协作交互，还有一些则优化确定性的、模型驱动的 pipeline。与此同时，组织会把自建 agent 与软件即服务（SaaS）能力以及既有企业系统组合在一起。

模型层又引入另一个维度的差异。基础模型（FM）持续快速演进，每个模型在成本、延迟与能力上都有不同的取舍。因此，多数企业跨多个模型厂商运营，而不是统一到单一选项上。

随着时间推移，这会形成一种稳态现实：多模型、多框架、多厂商的系统，跨多个团队与用例运行。

挑战不在于如何避免这种结局，而在于如何在不引入碎片化的前提下管理这种结局。

## 把可选性当作需要管理的约束

在[第一部分](https://aws.amazon.com/blogs/machine-learning/advanced-fine-tuning-techniques-for-multi-agent-orchestration-patterns-from-amazon-at-scale/)中，我们专注于优化特定系统内的 agent 行为。到了企业层面，问题就变了。可选性不再只是试验，而成为一种必须有意识地加以管理的约束。

试图在框架层或模型层强制标准化，往往会制造摩擦。团队会绕过约束、采用速度变慢，或者系统偏离已批准的架构。与此同时，把应用与特定模型或厂商紧密耦合，又会限制随格局演进而调整的能力。

更有效的做法是在应用层之下做标准化，聚焦于共享的控制平面，例如身份、策略执行、可观测性与路由，同时允许 agent 的构建与执行方式保持灵活。

这种做法并不消除异构性，而是限制它的影响，使系统能够演进，同时不破坏整体架构的稳定。

## multi-everything 系统的核心挑战

随着系统在多样性上增长，会出现一组可预期的挑战。治理难以在各自定义控制模型的框架之间一致地执行。随着 agent、工具与服务暴露出互不兼容的接口，集成复杂度上升。成本与性能的取舍在没有动态优化的情况下变得更难管理，常常导致资源使用效率低下。

与此同时，随着 agent 与工具、数据及其他 agent 动态交互，安全边界不断扩大，访问模式变得更难预测。持久化记忆在数据保留、隔离与一致性方面带来额外复杂度。最后，企业用例要求领域特定的性能，仅靠通用配置无法达到。

这些挑战相互关联，并随时间叠加。管理它们需要系统级方法，而不是孤立的解决方案。

## 一套在规模上管理复杂度的实用准则

下图总结了在成功的 multi-everything 环境中反复出现的核心架构原则：控制平面与执行平面分离、统一可观测性、集中治理、动态路由、内建韧性、分阶段演进编排，以及内建优化。

图 1：在 multi-everything 环境中管理复杂度的核心架构原则

在 multi-everything 环境中成功运作的组织，会收敛到一组在灵活性与控制之间取得平衡的架构原则。

一项基础原则是控制平面与执行平面分离。身份、策略执行、可观测性与成本归集被集中化，以促进企业级一致性；而 agent 执行与开发保持去中心化，以支持团队自主与可扩展性。

可观测性成为有效运营这些系统的前提。通过建立统一的遥测层，组织能够获得跨框架、跨环境的 agent 行为可见性。这种可见性帮助它们监控性能、追踪故障并持续改进系统，而无需依赖框架专属工具。

治理在作为平台能力（而不是嵌入各个 agent 内部）实现时最为有效。即便框架、模型与执行环境不断演进，集中执行也能支持一致的安全与合规。

随着工作负载多样化，路由成为核心系统功能。组织不再静态分配模型或基础设施，而是依据成本、延迟与准确性要求，把任务动态匹配到资源。这帮助系统实时适应，并在规模上保持效率。

生产系统还必须以明确的保证来设计。延迟、可用性与隔离要求应当被清晰定义，并配套失败处理机制。重试、熔断器与回退路径有助于在真实条件下保持韧性。

许多组织一开始采用集中式编排模型，以便对 agent 交互保持可见性与控制。随着系统增长，它们会演进到更分布式、事件驱动的架构，从而在保持一致性的同时提供更强的可扩展性。

最后，优化必须从一开始就嵌入系统。成本与性能考量是规模化运营的基础，而动态模型选择、缓存与高效执行模式等技术有助于实现长期效率。

这些原则共同构成一个实用框架，用来管理 multi-everything 环境固有的复杂度。

## 如何用 AWS 服务实现与框架无关的规模化

前面概述的架构原则，需要具备跨框架、跨模型、跨团队一致运作的能力。AWS 服务提供了这些构建块，组织可用它们实现与框架无关的平台，同时保持灵活性。

在规模上，模型层会成为复杂度的主要来源之一。不同用例需要不同模型、定制策略与推理模式。

[Amazon SageMaker](https://aws.amazon.com/sagemaker/) 是用于在规模上管理这种复杂度的核心执行与定制层。它为模型开发、微调、部署与推理提供统一层，让组织能够统一企业内模型的构建与运营方式。通过支持实时、异步与批量推理，以及 [Inference Components](https://aws.amazon.com/blogs/aws/amazon-sagemaker-adds-new-inference-capabilities-to-help-reduce-foundation-model-deployment-costs-and-latency/) 与模型监控等能力，Amazon SageMaker 帮助团队让基础设施与工作负载需求相匹配，从而在整个企业内维持一致的运营模型。

与之互补，[Amazon Bedrock](https://aws.amazon.com/bedrock/) 提供简化、托管的接口来访问基础模型，支持快速试验而无需管理底层基础设施。Amazon Bedrock 加速模型访问与集成，Amazon SageMaker 则提供定制与生产级推理所需的深度、控制与可扩展性。二者结合，使组织能够把模型访问与模型执行分开，从而支持灵活且有韧性的架构。

编排与控制通过 AWS Lambda、AWS Step Functions 与 Amazon API Gateway 等服务实现，它们支持动态路由与工作流协调。

[Agent Orchestration on AWS](https://aws.amazon.com/marketplace/build-learn/ai-agent-learning-series/agent-orchestration) 等新兴能力进一步扩展了这一层。它们为 agent 编排提供专门构建的抽象，帮助团队以更高的一致性与控制力管理复杂的多 agent 工作流。

身份与治理仍通过 AWS Identity and Access Management（IAM）与 AWS Organizations 保持集中，可观测性则通过 Amazon CloudWatch 与 AWS X-Ray 实现标准化。

Amazon EventBridge、Amazon ElastiCache 与 Amazon CloudFront 支持集成与性能优化。

在这一架构中，Amazon SageMaker 实际上成为模型执行的运营骨干，而 Amazon Bedrock 加速获取新兴的基础模型能力。二者共同帮助组织在创新与控制之间取得平衡。

**核心要点**

Amazon SageMaker 为规模化的模型定制与推理提供运营骨干，Amazon Bedrock 则支持快速访问托管的基础模型。二者共同支撑企业级的、灵活且与框架无关的架构。

## multi-everything 系统的企业级模式

当这些原则被应用时，组织往往会收敛到少数几种架构模式上。这些模式并非规定性的。它们反映的是团队依据工作负载需求与运营约束来组织 agent 系统的方式。

重要的是，这些模式并不互斥。多数企业会在不同业务单元与用例中组合使用它们。挑战不在于选择某一种模式，而在于帮助它们共存于共享环境中。

### 模式 1：用于业务流程自动化的内部 agent 平台

一个常见的起点是内部 agent 平台，它随着多个团队开始独立构建 agent 而出现。随着时间推移，这可能导致基础设施重复、治理不一致以及组织内复用受限。

为解决这一问题，组织引入集中式或混合式平台模型。共享的平台层提供模型访问、治理、可观测性与成本管理等通用能力，而各个团队保留对如何构建与部署 agent 的自主权。

在这一模型中，平台充当控制平面，统一 agent 访问模型、执行策略与发出遥测的方式。与此同时，执行保持去中心化。业务单元继续拥有自己的应用逻辑、数据集成、持续集成与持续交付（CI/CD）pipeline 以及框架选择。

这种分离减少了重复、在不限制创新的前提下强制一致性，同时支持在多个用例中复用通用能力。

图 2：具有集中控制平面、业务单元执行去中心化的内部 agent 平台

### 模式 2：面向客户的 agent 平台（ISV 与 SaaS）

当 agent 对外暴露时，架构重点转向多租户、隔离与可靠性。

在这一模式中，系统的设计强调强租户边界。每个请求在整个系统中都携带租户上下文，确保 agent 只访问限定给该租户的数据与工具。身份与访问管理成为核心关注点，通常要与外部身份提供商集成，同时在平台内部保持一致执行。

基础设施决策也随之演进。许多组织采用混合租户模型，把面向标准工作负载的共享基础设施与面向监管或性能要求更严格客户的专用环境结合起来。这种做法在成本效率与隔离、合规需求之间取得平衡。

可靠性是这一模式的标志性特征。系统必须在工作负载不均衡的情况下，仍满足对延迟、可用性与吞吐量的明确预期。因此，故障转移、限流与优雅降级等韧性机制成为核心平台能力。

图 3：具备租户感知身份、隔离与共享基础设施的多租户 agent 平台

### 模式 3：在实时应用中优化推理延迟

对于实时系统，延迟成为主导性的架构约束。对话式助手与交互式工作流等应用要求在严格的时间范围内给出响应，延迟会直接影响用户体验。

在这些环境中，优化必须被设计进系统。路由决策是动态的，依据复杂度、延迟敏感度与成本考量评估每个请求。这样的路由会实时选出最合适的模型与基础设施层级。

执行策略也会演进以支持并行，让相互独立的操作并发运行，从而缩短整体响应时间。缓存通过减少冗余计算发挥关键作用，同时改善延迟与成本效率。

这一模式强调系统级优化，把性能视为首要设计约束，而不是事后补充。

图 4：具备动态路由、并行执行与多层缓存的延迟优化 agent 架构

## 以统一平台衔接各种模式

这些模式各自应对一组特定需求。然而在 multi-everything 环境中，它们很少孤立存在。企业常常同时运行内部自动化 agent、面向客户的系统与实时应用。这些系统往往由不同团队使用不同框架与模型构建。

如果没有共享底座，这些模式可能会变成孤岛。治理出现分歧，集成数量膨胀，优化工作在各系统间重复。

统一 agent 平台通过提供一组位于各模式之下的通用能力来应对这一挑战。它把身份、策略执行、可观测性与路由等横切关注点标准化，同时允许每个系统独立演进。

这一区分很重要。模式描述的是 agent 系统如何针对特定工作负载来组织。平台则确保这些系统能够作为统一企业架构的一部分共同扩展。

## 结论

在本系列的第一部分中，我们聚焦于单个用例内的多 agent 编排，即需要多个 agent 在既定领域内应对复杂性的场景。

在本文中，我们把范围扩展到企业层面，挑战变成了如何在 multi-everything 环境中管理许多这样的系统。

成功的组织不是消除复杂度的组织，而是为复杂度建立结构的组织。通过标准化身份、策略、可观测性与路由等关键控制层，同时在执行层保持灵活，它们就能在不失去控制的前提下运营异构系统。

要开始应用这些模式，请了解 [Amazon SageMaker](https://aws.amazon.com/sagemaker/)、[Amazon Bedrock](https://aws.amazon.com/bedrock/) 与 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 如何支持模型定制与框架无关的访问，并就本文提到的控制平面实践参阅 [AWS Well-Architected Framework](https://aws.amazon.com/architecture/well-architected/)。欢迎在评论区分享哪些模式正在塑造你的企业 agent 架构。
