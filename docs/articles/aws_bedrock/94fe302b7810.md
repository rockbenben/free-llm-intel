# Automated Reasoning checks 重写式 chatbot 参考实现

今天，我们发布了一个新的[开源示例 chatbot](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/responsible_ai/automated-reasoning-rewriting-chatbot)，它展示了如何利用 Automated Reasoning checks 的反馈来迭代生成内容、提出澄清性问题，并证明某个答案的正确性。

该 chatbot 实现还会产出一份审计日志，其中包含针对答案有效性的、可用数学方式验证的解释；同时提供一个用户界面，向开发者展示幕后正在进行的迭代重写过程。Automated Reasoning checks 使用逻辑推演来自动证明某条陈述是正确的。与大型语言模型不同，Automated Reasoning 工具不是在猜测或预测准确性，而是依靠数学证明来验证是否符合策略。本文将进一步深入剖析 Automated Reasoning checks 重写式 chatbot 的实现架构。

## 用 Automated Reasoning checks 提升准确性与透明度

LLM 有时会生成听起来很有说服力但包含事实错误的回答——这种现象被称为幻觉。Automated Reasoning checks 会验证用户的问题和 LLM 生成的答案，并给出重写反馈，指出含糊的表述、过于宽泛的断言，以及基于 Automated Reasoning 策略中编码的基准事实而得出的、事实上不正确的说法。

一个使用 Automated Reasoning checks 在把答案呈现给用户之前对其进行迭代的 chatbot，有助于**提升准确性**，因为它可以做出精确的陈述，明确回答用户的是/否问题而不留歧义空间；同时**有助于提升透明度**，因为它可以提供可数学验证的证明，说明其陈述为何正确，从而让生成式 AI 应用即便在受监管环境中也可审计、可解释。

了解了这些好处之后，接下来我们看看如何在自己的应用中实现它。

## 迭代重写循环如何运作

[开源参考实现](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/responsible_ai/automated-reasoning-rewriting-chatbot)通过迭代处理 Automated Reasoning checks 的反馈并重写回答，自动帮助改进 chatbot 的答案。当被要求验证一个 chatbot 问答（Q&A）时，Automated Reasoning checks 会返回一组 finding（发现）。每个 finding 代表在该输入问答中识别出的一条独立逻辑陈述。例如，对于问答“S3 存储要多少钱？在 US East (N. Virginia)，S3 前 50Tb 的价格是每 GB $0.023；在 Asia Pacific (Sydney)，S3 前 50Tb 的价格是每 GB $0.025”，Automated Reasoning checks 会产生两个 finding，一个验证 us-east-1 中 S3 的价格是 $0.023，另一个验证 ap-southeast-2 的价格。

在解析某个问答的 finding 时，Automated Reasoning checks 会把输入拆分为一组事实性前提（premise）以及针对这些前提提出的主张（claim）。前提可以是用户问题中的事实陈述，比如“我是弗吉尼亚州的一名 S3 用户”，也可以是答案中给出的假设，比如“对于发送到 us-east-1 的请求……”。主张代表一条待验证的陈述。在上面 S3 定价的例子中，区域就是前提，价格点则是主张。

每个 finding 都包含一个验证结果（`VALID`、`INVALID`、`SATISFIABLE`、`TRANSLATION_AMBIGUOUS`、`IMPOSSIBLE`），以及把答案重写成 `VALID` 所必需的反馈。反馈内容随验证结果而变化。例如，含糊的 finding 会包含对输入文本的两种解释，可满足的 finding 会包含两种情形，说明主张在某些情况下为真、在另一些情况下为假。你可以在[我们的 API 文档](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_GuardrailAutomatedReasoningFinding.html)中查看可能的 finding 类型。

交代完这些背景，我们可以深入看看参考实现是如何运作的：

### **初始响应与验证**

当用户通过 UI 提交问题时，应用会先调用所配置的 Bedrock LLM 生成答案，然后调用 [ApplyGuardrail](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ApplyGuardrail.html) API 来验证这个问答。

利用 `ApplyGuardrail` 响应中来自 Automated Reasoning checks 的输出，应用进入一个循环：每次迭代都会检查 Automated Reasoning checks 的反馈，执行某个动作（例如要求 LLM 根据反馈重写答案），然后再次调用 `ApplyGuardrail` 验证更新后的内容。

### **重写循环（系统的核心）**

初始验证之后，系统使用 Automated Reasoning checks 的输出决定下一步。首先，它按优先级对 finding 排序——优先处理最重要的：`TRANSLATION_AMBIGUOUS`、`IMPOSSIBLE`、`INVALID`、`SATISFIABLE`、`VALID`。然后，它选出优先级最高的 finding，并用下面的逻辑处理它。由于 `VALID` 排在优先级列表的最后，系统只有在处理完其他 finding 之后才会把某条答案接受为 `VALID`。

- 对于 `TRANSLATION_AMBIGUOUS` finding，Automated Reasoning checks 会返回对输入文本的两种解释。对于 `SATISFIABLE` finding，Automated Reasoning checks 会返回两种情形，分别证明和证伪相关主张。应用利用这些反馈，要求 LLM 决定：是尝试重写答案以澄清歧义，还是向用户提出追问以收集更多信息。例如，`SATISFIABLE` 反馈可能会说，只有当区域是 US East (N. Virginia) 时，$0.023 的价格才有效。LLM 可以利用这一信息去询问应用所在的区域。当 LLM 决定提出追问时，循环暂停并等待用户回答，然后 LLM 根据澄清信息重新生成答案，循环重新开始。
- 对于 `IMPOSSIBLE` finding，Automated Reasoning checks 会返回与前提（输入内容中被接受的事实）相矛盾的规则列表。应用利用这些反馈，要求 LLM 重写答案以避免逻辑不一致。
- 对于 `INVALID` finding，Automated Reasoning checks 会返回 Automated Reasoning 策略中的规则，这些规则依据前提和策略规则判定上述主张无效。应用利用这些反馈，要求 LLM 重写答案，使其与规则保持一致。
- 对于 `VALID` finding，应用退出循环，把答案返回给用户。

每次重写答案之后，系统都会把问答发送到 `ApplyGuardrail` API 进行验证；循环的下一次迭代从这次调用的反馈开始。每次迭代都会把 finding 和带完整上下文的 prompt 存入会话线程的数据结构，从而形成一条记录系统如何得出最终答案的审计轨迹。

## 开始使用 Automated Reasoning checks 重写式 chatbot

要试用我们的参考实现，第一步是创建一个 Automated Reasoning 策略：

- 在美国或欧洲的[受支持区域](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-automated-reasoning-checks.html)中，从 AWS Management Console 导航到 **Amazon Bedrock**。
- 在左侧导航栏中，打开 **Build** 类别下的 **Automated Reasoning** 页面。
- 使用 **Create policy** 按钮的下拉菜单，选择 **Create sample policy**。
- 为策略输入一个名称，然后在页面底部选择 **Create policy**。

创建好策略后，就可以下载并运行参考实现了：

- 克隆 Amazon Bedrock [Samples 仓库。](https://github.com/aws-samples/amazon-bedrock-samples)
- 按照 [README 文件](https://github.com/aws-samples/amazon-bedrock-samples/blob/main/responsible_ai/automated-reasoning-rewriting-chatbot/README.md)中的说明安装依赖、构建前端并启动应用。
- 使用你常用的浏览器访问 [http://localhost8080](http://localhost8080) 并开始测试。

### 后端实现细节

如果你打算把这套实现改造用于生产环境，本节将介绍后端架构中的关键组件。你可以在仓库的 [backend](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/responsible_ai/automated-reasoning-rewriting-chatbot/backend) 目录中找到这些组件。

- **ThreadManager：**负责统筹对话生命周期管理。它处理会话线程的创建、检索和状态跟踪，在整个重写过程中维护正确的状态。ThreadManager 使用锁实现线程安全的操作，以帮助避免多个操作同时尝试修改同一会话时产生的竞态条件。它还会跟踪等待用户输入的线程，并能识别已超过可配置超时时间的陈旧线程。
- **ThreadProcessor：**使用状态机模式处理重写循环，以获得清晰、易维护的控制流。该处理器管理各阶段之间的状态转换，例如 `GENERATE_INITIAL`、`VALIDATE`、`CHECK_QUESTIONS`、`HANDLE_RESULT` 和 `REWRITING_LOOP`，让对话正确地推进到每个阶段。
- **ValidationService：**与 Amazon Bedrock Guardrails 集成。该服务接收每个由 LLM 生成的响应，并通过 `ApplyGuardrail` API 提交验证。它负责与 AWS 通信、针对瞬时故障以指数退避方式管理重试逻辑，并把验证结果解析为结构化的 finding。
- **LLMResponseParser：**在重写循环中解读 LLM 的意图。当系统要求 LLM 修正一个无效响应时，模型必须决定是尝试重写（`REWRITE`）、提出澄清性问题（`ASK_QUESTIONS`），还是因前提相互矛盾而宣告任务不可能完成（`IMPOSSIBLE`）。解析器会检查 LLM 响应中诸如“`DECISION:`”“`ANSWER:`”和“`QUESTION:`”这类特定标记，从自然语言输出中提取结构化信息。它能妥善处理 markdown 格式，并对问题数量施加限制（最多 5 个）。
- **AuditLogger：**把结构化 JSON 日志写入专用的审计日志文件，记录两类关键事件：`VALID_RESPONSE`（响应通过验证时）和 `MAX_ITERATIONS_REACHED`（系统用尽设定的重试次数时）。每条审计记录都会捕获时间戳、线程 ID、prompt、响应、模型 ID 和验证 finding。该日志记录器还会提取并记录澄清迭代中的问答往来，包括用户是回答了问题还是跳过了问题。

这些组件共同构成一个稳固的基础，用于构建既具备大型语言模型灵活性、又具备数学验证严谨性的可信 AI 应用。
