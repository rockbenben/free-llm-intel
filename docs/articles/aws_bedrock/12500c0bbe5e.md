# 使用 Strands Evals 进行 AI Agent 故障检测与根因分析

当你的 AI agent 在生产环境中失败时，仅仅知道它*失败*了还只是开始。更难回答的问题是它*为什么*失败以及该修复什么。传统评估会告诉你"这个 agent 在目标完成率上得了 60 分"，却让你手动审查执行追踪来理解哪里出了问题。对于大规模运行 agent 的团队来说，这种人工诊断成了从发现问题到交付修复之间的瓶颈。[Strands Evals SDK](https://github.com/strands-agents/evals) 中的检测器（detector）通过自动识别 agent 执行追踪中的故障并执行根因分析，消除了这一瓶颈，让你能把诊断时间从数小时缩短到数分钟。

在本文中，我们将带你了解如何调用检测器函数来诊断真实的 agent 故障。你将学习如何解读它们的结构化输出：带置信度评分的分类故障、将根因与下游症状关联起来的因果链，以及指明改动应放在系统 prompt 还是工具定义中的修复建议。你还将学习如何将检测集成到评估流水线中，以便每次测试运行都能自动诊断。

检测器补充了[上一篇文章中介绍的](https://aws.amazon.com/blogs/machine-learning/evaluating-ai-agents-for-production-a-practical-guide-to-strands-evals/)评估框架，它不仅回答"agent 做得有多好？"，还回答"它为什么失败，我该如何修复？"

## 前提条件

要跟随本文操作，你必须具备以下前提条件。

- Python 3.10 或更高版本。
- 已安装 Strands Evals SDK，使用 `pip install strands-agents-evals`。
- 已启用 Amazon Bedrock 模型访问权限（检测器使用基于大语言模型（large language model，LLM）的分析）。
- 对于 Amazon CloudWatch 示例，已配置具备 `logs:StartQuery` 和 `logs:GetQueryResults` 权限的 AWS 凭据。

## 为什么仅有分数不够

Strands Evals 框架通过 Case、Experiment 和 Evaluator 提供可靠的质量信号：目标成功率、工具选择准确率和有用性评分。这些指标对于发现回归和在统计层面理解性能很重要。但考虑一下检测到回归之后会发生什么。在一次部署之后，或在构建时测试中 prompt 或工具发生改动之后，你的 agent 目标成功率从 85% 降到了 70%。Evaluator 确认了这一下降。接下来怎么办？

你必须找出具体是哪些行为导致了失败，区分根因与下游症状，确定修复应放在系统 prompt 还是工具定义中，并按影响排定优先级。这一诊断工作流传统上需要高级工程师手动逐段检查追踪，并在数百个步骤之间关联故障，而这个过程无法扩展。

检测器实现了这一工作流的自动化。Evaluator 通过在单个 Case 层面生成分数来回答"agent 做得有多好？"。检测器则通过在单个 span 层面生成诊断来回答"它为什么失败？"，包括分类故障、因果链和修复建议。

## 检测器如何工作

检测器流水线分两个阶段运行，每个阶段都由基于 LLM 的执行追踪分析驱动。要了解 agent 的会话（session）、追踪（trace）和 span，请参阅 [了解 Amazon Bedrock AgentCore 中 agentic 资源的可观测性](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-telemetry.html)。

阶段 1：故障检测会根据一个全面的故障分类法扫描会话中的每个 span，该分类法分为九大父类别：hallucination、incorrect actions、orchestration errors、task instruction non-compliance、execution errors、context handling errors、repetitive behavior、LLM output issues 以及 configuration mismatch。对于识别出的每个故障，它会返回 span 位置、一个或多个类别、置信度评分，以及从追踪中提取的证据。

阶段 2：根因分析接收检测到的故障，并追溯它们之间的因果链。一个上游错误往往会级联成多个下游故障。根因分析将原因与症状分开。它对每个故障的因果性进行分类（PRIMARY、SECONDARY 或 TERTIARY），确定传播影响，并生成按修复归属（系统 prompt、工具描述或其他）分类的修复建议。

两个阶段都通过分层策略处理不同规模的会话：对于能装入所选 Detector 模型上下文窗口的会话，采用直接分析；对于中等规模的会话，采用故障路径剪枝，只保留祖先和后代 span；对于非常大的会话，采用分块分析并合并，将追踪拆分为重叠的窗口并协调结果。

## 故障检测入门

以下示例使用来自 [Evaluating AI agents for production: A practical guide to Strands Evals](https://aws.amazon.com/blogs/machine-learning/evaluating-ai-agents-for-production-a-practical-guide-to-strands-evals/) 中药物发现研究助手的会话追踪。该 agent 构建于 Strands Agents 和 Amazon Bedrock 之上。要跟随操作，请在启用 [OpenTelemetry](https://opentelemetry.io/) 追踪的情况下运行你的 agent，并将会话导出为 JSON；或者使用本文后面介绍的 `CloudWatchProvider` 来获取现有追踪。关于如何设置追踪和导出会话，请参阅 [Strands Agents SDK 文档中的 User Simulation](https://strandsagents.com/docs/user-guide/evals-sdk/simulators/user_simulation/#complete-example-customer-service-evaluation)。

`detect_failures` 函数接收一个 `Session` 对象（Strands Evals 中的标准追踪格式）并返回结构化故障。每个故障包括其发生的 span、来自预定义故障分类法的一个或多个类别、置信度评分，以及从追踪中提取的证据。

```
import json
from strands_evals.detectors import detect_failures
from strands_evals.types.trace import Session
from strands_evals.detectors import ConfidenceLevel

with open("agent_trace.json") as f:
    session = Session.model_validate_json(f.read())

result = detect_failures(session, confidence_threshold=ConfidenceLevel.MEDIUM)

for failure in result.failures:
    for cat, conf, ev in zip(failure.category, failure.confidence, failure.evidence):
        print(f"[{conf}] {cat} at span {failure.span_id}")
        print(f"  Evidence: {ev}")
```

以下是一个研究 agent 的输出，该 agent 被要求"研究为现实世界中的 AI 供电所需的能源要求所产生的影响。"。该 agent 遇到了工具配置问题，并逐步退化：

```
[0.9] execution-error-category-tool-schema at span f503a7d546fa4157
  Evidence: Tool execution failed due to missing required parameter
  'knowledgeBaseId'. Error: 'Parameter validation failed: Invalid type
  for parameter knowledgeBaseId, value: None'

[0.75] hallucination-category-hall-usage at span 0466979670d14099
  Evidence: Agent claims 'I don't have access to the specific knowledge
  base needed' and then proceeds to provide detailed information about AI
  energy requirements 'based on general knowledge' without using any tools.

[0.9] orchestration-related-errors-category-goal-deviation at span d98d578e61233d33
  Evidence: Agent completely abandons the original task about AI energy
  requirements and instead provides a lengthy response about marine
  biology, stating 'I'm going to pivot to discuss marine biology instead.'
```

在一次遍历中，检测器就能识别多个层级的故障：执行错误（工具参数校验）、语义问题（基于"general knowledge"的幻觉）以及编排问题（完全偏离目标）。单个 span 可能表现出多个故障类别，每个类别都有独立的置信度和证据。

## 添加根因分析

识别故障很有用，但理解故障为何发生才能推动修复。`analyze_root_cause` 函数接收检测到的故障，并追溯它们之间的因果链，将根因与下游症状分开，并建议每个修复应归属何处。如果没有向 `analyze_root_cause` 提供故障，它会自动运行故障检测。

```
from strands_evals.detectors import detect_failures, analyze_root_cause

failures = detect_failures(session)
rca_result = analyze_root_cause(session, failures=failures.failures)

for rc in rca_result.root_causes:
    print(f"Causality: {rc.causality}")
    print(f"  Span: {rc.failure_span_id} | Fix type: {rc.fix_type}")
    print(f"  Root cause: {rc.root_cause_explanation}")
    print(f"  Recommendation: {rc.fix_recommendation}")
```

继续沿用同一个研究 agent 会话，根因分析揭示了其因果结构：

```
Causality: PRIMARY_FAILURE
  Span: f503a7d546fa4157 | Fix type: TOOL_DESCRIPTION_FIX
  Root cause: Agent called retrieve tool without required knowledgeBaseId
    parameter because tool description does not clearly document that
    knowledgeBaseId is mandatory. This caused parameter validation failure
    and forced agent into multiple retry attempts with different parameter
    combinations.
  Recommendation: Update retrieve tool description to explicitly mark
    knowledgeBaseId as a required parameter with clear documentation
    including format constraints and example values.

Causality: SECONDARY_FAILURE
  Span: 0466979670d14099 | Fix type: SYSTEM_PROMPT_FIX
  Root cause: Agent fabricated detailed AI energy consumption information
    claiming it is 'based on general knowledge' after all retrieval attempts
    failed, because system prompt lacks instruction prohibiting generation
    of factual content without tool-retrieved evidence.
  Recommendation: Add instruction to system prompt requiring agent to
    explicitly acknowledge inability to complete research tasks when
    retrieval tools fail, and prohibit generating detailed factual content
    without tool-verified sources.
```

修复类型之间的区分正是让根因分析具有可操作性的原因。工具 schema 错误属于 `TOOL_DESCRIPTION_FIX`，因为 retrieve 工具的 `knowledgeBaseId` 没有清晰说明。下游的幻觉属于 `SYSTEM_PROMPT_FIX`，因为缺少关于如何处理持续性工具故障的指令。只修复其中一类，另一类就会悬而未决。

## 使用 diagnose_session 进行集成诊断

为方便起见，`diagnose_session` 将两个阶段作为一个流水线运行（先检测故障，再分析根因），并返回一个统一的 `DiagnosisResult`，其中的建议已去重：

```
from strands_evals.detectors import diagnose_session, ConfidenceLevel

result = diagnose_session(session, confidence_threshold=ConfidenceLevel.MEDIUM)
print(f"Found {len(result.failures)} failures, {len(result.root_causes)} root causes")

for rec in result.recommendations:
    print(f"  - {rec}")
```

这会产生与前面示例相同的故障和根因，并打包为单一结果，其中所有根因的建议都已去重。只需一次函数调用，你就能得到一份按归属分类、排定优先级的具体改动清单。

## 与评估流水线集成

当你将检测器集成到现有评估工作流中时，它们能提供额外价值。`DiagnosisConfig` 可将自动诊断附加到任意 Experiment，这样每个失败的测试用例都会自动生成诊断：

```
from strands_evals import Experiment
from strands_evals.evaluators import GoalSuccessRateEvaluator
from strands_evals.detectors import ConfidenceLevel, DiagnosisConfig, DiagnosisTrigger
from strands_evals.types.evaluation_report import EvaluationReport

experiment = Experiment(
    cases=test_cases,
    task_function=my_agent_task,
    evaluators=[GoalSuccessRateEvaluator()],
    diagnosis_config=DiagnosisConfig(
        trigger=DiagnosisTrigger.ON_FAILURE,
        confidence_threshold=ConfidenceLevel.MEDIUM
    ),
)

report = experiment.run()
report.display(include_recommendations=True)
```

有两种触发模式。`ON_FAILURE`（默认）仅在至少一个 Evaluator 返回 `test_pass=False` 时运行诊断，这使其对持续集成与持续交付（CI/CD）回归检测具有成本效益。`ALWAYS` 无论结果如何都会对每个 Case 运行诊断，这有助于发现名义上通过的 Case 中潜藏的次优路径。

通过这种集成，你的 CI/CD 流水线不仅告诉你"3 个测试失败"，还会告诉你失败的原因以及该改什么。这就闭合了反馈回路：定义 Case、运行 Experiment、同时获得分数和诊断、应用建议的修复，然后重新运行以确认。

**注意：** 运行检测器会使用 Amazon Bedrock 推理进行基于 LLM 的分析，这会产生费用。详情请参阅 [Amazon Bedrock pricing](https://aws.amazon.com/bedrock/pricing/)。Amazon CloudWatch Logs 存储也会产生费用。详情请参阅 [Amazon CloudWatch pricing](https://aws.amazon.com/cloudwatch/pricing/)。请在 AWS Cost Explorer 中监控你的用量，尤其是在将检测器集成到频繁运行的 CI/CD 流水线时。

## 从 CloudWatch 诊断生产会话

前面的示例使用本地会话文件，但在生产中，你的 agent 追踪保存在 Amazon CloudWatch Logs 中，并通过 OpenTelemetry 导出。`CloudWatchProvider` 直接从 Amazon CloudWatch 获取追踪，并将其转换为你可以用检测器分析的 `Session` 对象：

```
from strands_evals.providers import CloudWatchProvider
from strands_evals.detectors import diagnose_session, ConfidenceLevel

provider = CloudWatchProvider(agent_name="my-research-agent", region="us-east-1")
data = provider.get_evaluation_data(session_id="abc-123-def-456")
session = data["trajectory"]

result = diagnose_session(session, confidence_threshold=ConfidenceLevel.MEDIUM)

for rc in result.root_causes:
    print(f"[{rc.fix_type}] {rc.fix_recommendation}")
```

在底层，该 provider 会查询 Amazon CloudWatch Logs Insights 以查找与会话 ID 匹配的 OTEL 记录，从 span 元数据中自动检测 agent 框架（Strands、LangChain 或其他），并将 span 映射为标准化的 `Session`。检测器适用于任何将 OpenTelemetry 追踪导出到 Amazon CloudWatch 的框架，不仅限于 Strands Agents。

你还可以将其与实验流水线结合用于离线评估：使用 `CloudWatchProvider` 评估和诊断历史生产会话，而无需重新运行 agent。你也可以使用 `LangfuseProvider` 或 `OpenSearchProvider` 从 Langfuse 或 OpenSearch 检索追踪。

## 最佳实践

**从 MEDIUM 置信度开始。** `LOW` 阈值会捕获更多潜在问题，但也包含更多噪声，适合对某个失败 Case 进行深入调查。`MEDIUM` 在日常使用中提供良好的信噪比。将 `HIGH` 留给你只想要高确定性发现的生产监控。

**在 CI/CD 中使用 `ON_FAILURE`，定期审计使用 `ALWAYS`。** `ON_FAILURE` 使 LLM 成本与失败率成正比，适合每次测试运行。安排 `ALWAYS` 模式每周或每个发布版本运行一次，以捕捉隐藏在通过 Case 中的次优行为。

**优先修复 `PRIMARY` 故障。** 次要和三级故障往往在根因得到解决后随之消失。在实施多项建议之前，先检查修复主要故障是否会消除下游故障。这能减少迭代周期。

**按修复类型对建议分组。** 将 `TOOL_DESCRIPTION_FIX` 改动批量放在一起，`SYSTEM_PROMPT_FIX` 改动也放在一起。这样在重新运行评估时，每类改动的影响都可以独立衡量。

**将预先检测到的故障传给 `analyze_root_cause`。** 如果你已经运行了 `detect_failures` 并想在运行根因分析前检查结果，可以直接将它们传入以避免重复检测：

```
failures = detect_failures(session)
# ... inspect or filter failures ...
rca = analyze_root_cause(session, failures=failures.failures)
```

**使用测试会话进行实验。** 本文使用的 `flawed_session.json` 可在 [Strands Evals test suite](https://github.com/strands-agents/evals) 中获取，方便你在本地试用检测器。

## 清理资源

检测器函数本身不会配置任何持久的 AWS 资源。不过，如果你为 agent 追踪配置了 Amazon CloudWatch Logs 导出，可能需要检查以下内容：

- **Amazon CloudWatch 日志组：** 删除日志组会永久移除所有日志数据，且无法撤销。在继续之前，请确认你已经导出了需要保留的任何日志。如果你专门为测试创建了日志组，请通过 Amazon CloudWatch 控制台或运行 `aws logs delete-log-group --log-group-name <your-log-group>` 将其删除。
- **Amazon Bedrock 模型访问权限：** LLM 分析使用 Amazon Bedrock。如果你仅为本次演练启用了模型访问权限，请通过 Amazon Bedrock 控制台的 **Model access** 撤销该权限。

## 结论

检测器闭合了衡量 agent 质量与改进质量之间的回路。通过自动化此前需要人工检查追踪的故障检测和根因分析，你可以在数分钟而非数小时内从"测试失败"推进到"这是需要修复的地方"。

要开始使用，请参阅 [Strands Evals SDK Detectors documentation](https://strandsagents.com/docs/user-guide/evals-sdk/detectors/) 和 [Strands Evals GitHub repository](https://github.com/strands-agents/evals)。试用附带的示例追踪文件，然后将 `DiagnosisConfig` 添加到评估流水线中的一个现有测试用例中，亲眼看看自动诊断的实际效果。
