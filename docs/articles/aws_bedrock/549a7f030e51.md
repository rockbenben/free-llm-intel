# 使用 Amazon Nova 的结构化输出：面向构建者的指南

构建 AI 应用的开发者面临一个共同挑战：把非结构化数据转换为结构化格式。对于机器与机器之间通信的用例，结构化输出至关重要，因为它使下游用例能够更有效地消费与处理生成的输出。无论是从文档中抽取信息、创建从 API 获取数据的助手，还是开发会执行动作的 agent，这些任务都要求基础模型以特定的结构化格式生成输出。

我们推出了约束解码（constrained decoding），在使用工具实现结构化输出时提供可靠性。现在，工具可与 [Amazon Nova](https://aws.amazon.com/nova) 基础模型（FM）配合使用，基于复杂 schema 抽取数据，把工具使用错误减少 95% 以上。

本文中，我们探讨如何将 Amazon Nova FM 用于结构化输出用例。

## 实现结构化输出的技术

在应对结构化输出用例的需求时，有两种常见的实现方式：修改 system prompt，或者利用工具调用（tool calling）。例如，在客户支持用例中，你可能希望模型输出一个 JSON，其中包含给用户的答复与当前情绪。于是，system prompt 会被修改为包含期望的结构：

```
Make sure your final response is valid JSON that follows the below response schema: 

##Response schema
```json
{
   "response": "the response to the customer",
   "sentiment": "the current customer sentiment"
}```
```

另一种选择是提供一个[工具配置](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ToolConfiguration.html)。工具调用是指通过 [Converse API](https://docs.aws.amazon.com/bedrock/latest/userguide/tool-use-inference-call.html) 的请求 schema，把最终应用所需的 API、代码函数或 schema（或结构）提供给模型。这种做法在构建 agentic 应用时最为常用，但由于能够定义模型应当遵循的固定 schema，它在结构化输出用例中也经常被采用。

```
tool_config = {
    "tools": [ 
        {
            "toolSpec": {
                "name": "respondToUser",
                "description": "the formatted response to the customer",
                "inputSchema": {
                    "type": "object",
                    "properties": {
                        "response": {
                            "description": "the response to the customer",
                            "type": "string"
                        },
                        "sentiment": {
                            "description": "the current customer sentiment",
                            "type": "string"
                        }
                    },
                    "required": [
                        "response",
                        "sentiment"
                    ]
                }
            }
        }
    ]
}
```

两种方式都可以成为影响模型输出的有效 prompt 技巧。然而，输出仍然是非确定性的，仍存在失败空间。我们与客户一起实施 agentic workflow 与应用、结构化抽取等用例时观察到，随着 schema 变得更复杂，模型的准确率往往下降。

## 使用 Amazon Nova 模型实现结构化输出

基于这些经验，我们在系统中实现了[约束解码](https://arxiv.org/pdf/2305.13971)，以帮助确保生成输出的高度模型可靠性，并让模型能够轻松应对复杂 schema。约束解码依靠语法（grammar）来*约束*模型在每一步可以输出的候选 token。这与过去使用的 prompt 技巧有所不同，因为它改变的是模型在生成输出时实际可选的 token。例如，在闭合一个 JSON 对象时，模型会被约束为只能选择 `}` 这一个 token。每次传入工具配置时都会使用约束解码。因为工具使用本身已经向我们提供了一个具体 schema，我们可以据此动态生成语法，依据的是开发者期望的 schema。约束解码阻止模型生成非法的键，并依据所定义的 schema 强制使用正确的数据类型。

## Schema 定义过程

使用 Amazon Nova 实现结构化输出的一个关键步骤是创建工具配置。工具配置提供定义期望输出 schema 的标准接口。虽然工具配置的主要目的是为模型提供外部功能，但这个 JSON 接口也同样用于结构化输出用例。可以用一个从在线内容中抽取食谱的用例来说明。为开始集成，我们创建一个工具配置，表示我们希望从发票中抽取的具体字段。创建工具配置时，清楚与简洁很重要，因为属性名与描述正是让模型了解字段应如何填充的依据。

工具配置创建完成后，我们可以把它连同食谱一起通过[ Converse API](https://boto3.amazonaws.com/v1/documentation/api/latest/reference/services/bedrock-runtime/client/converse.html) 传入，食谱将包含在 user prompt 中。过去，结构化输出用例需要 system prompt 来引导模型如何输出内容；在这里，我们可以用它传入关于 system 角色与 persona 的细节。

```
import boto3

model_response = client.converse(
    modelId="us.amazon.nova-lite-v1:0",
   system=[{"text": "You are an expert recipe extractor that compiles recipe details from blog posts"}],
    messages=[{"role": "user", "content": content}],
    inferenceConfig={"temperature": 0},
    toolConfig=tool_config
)
```
