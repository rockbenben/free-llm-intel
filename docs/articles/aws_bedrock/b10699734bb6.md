# 规模化 tokenomics：Jamf 如何为 Amazon Bedrock 构建实时支出管控

生成式 AI 的支出表现得与此前任何一项成本都不同。传统算力随预置容量扩展，而 AI 支出随*行为*扩展：一名工程师用高端模型跑 agentic 编码循环，几个小时内烧掉的 token 可能比一个团队一周还多。这就是 tokenomics 问题：用量在账单到来之前不可见，使得成本控制与投资回报率（ROI）都难以证明。在扩大 AI 使用范围之前，管理层想要三个答案：我们人均花多少钱？能否在不拖慢工程师的情况下封顶？生产力提升是否足以证明成本合理？

受超过 76,000 家组织信赖、大规模管理和保护 Apple 设备的 [Jamf](https://www.jamf.com/) 直接面对了这一挑战。为加速 AI 辅助开发，Jamf 为其工程组织授予了 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 的广泛访问权限。生产力提升了，但对 AI FinOps 的需求也随之提升：按用户的可见性与成本问责。

Jamf 构建了一套在生产环境中把这问题解决到个人层面的系统。在本文中，你将了解如何使用 [AWS Identity and Access Management](https://aws.amazon.com/iam)（IAM）的[客户管理策略](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_create.html)（CMP）、基于 [Amazon Athena](https://aws.amazon.com/athena/) 的成本视图，以及 serverless 的 [AWS Lambda](https://aws.amazon.com/lambda/) 管控循环来构建这一架构。读完之后，你将拥有一个经过生产验证的可用模式，它能在不打断进行中会话的情况下，近乎实时地实施分级支出限额。这是一种 AI 成本治理能力。

## 解决方案概览

Jamf 的解决方案会跟踪每位工程师每天的 Amazon Bedrock 支出，并在他们接近预算时施加分级的模型限制。例如，它在消耗每日预算 80% 时拒绝访问 [Anthropic Claude](https://aws.amazon.com/bedrock/anthropic/) Opus，在 100% 时拒绝访问 Anthropic Claude Sonnet。它不会阻止 Anthropic Claude Haiku，因此工程师仍保留一个低成本模型可以继续工作。这些限制在几分钟内生效、无需重新身份验证，并会在下一次每日重置时自动恢复。对于确实需要更多的工程师，一个有文档记录的例外流程会授予有时间上限的更高限额。

## 架构图

该架构解决三类问题：度量支出、决定限制谁并通知他们、以及执行该限制。每一类都由一个专门构建的 serverless 组件处理。

端到端流程如下：

### 度量

- 调用与日志记录 — 当工程师通过其 [AWS IAM Identity Center](https://aws.amazon.com/iam/identity-center/) 单点登录（SSO）会话调用 Amazon Bedrock（[bedrock:InvokeModel](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_InvokeModel.html)）时，Amazon Bedrock 会把调用日志（包括模型 ID、输入与输出 token 数量以及用户身份）写入你配置的 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）存储桶。

### 决策与通知

- 成本度量 — 一个 Amazon Athena [视图](https://docs.aws.amazon.com/athena/latest/ug/views.html)（`bedrock_cost_today`）读取这些日志，用 token 数量乘以公布的模型费率，计算每位用户的每日支出。Athena [查询](https://docs.aws.amazon.com/athena/latest/ug/querying-athena-tables.html)会就地读取原始日志，无需单独的数据流水线。
- 管控决策 — 一个 AWS Lambda 管控处理器由 [Amazon EventBridge](https://aws.amazon.com/eventbridge/) 计划触发，每 15 分钟运行一次。它从 Athena 视图读取当天的支出，并与一张 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 例外表交叉核对，该表保存授予个别工程师的任何自定义、有时间上限的限额。
- 通知 — 同一个管控处理器会从 Amazon DynamoDB 状态表读取每个用户的先前状态，并在支出跨过新阈值时，向该工程师发送一条仅针对该档位的一次性 Slack 私信，使限制不至于成为意外。

### 强制实施

- 管控动作 — 对于每位超过阈值的工程师，Lambda 通过 [iam:CreatePolicyVersion](https://docs.aws.amazon.com/IAM/latest/APIReference/API_CreatePolicyVersion.html) 发布相应 CMP 的新版本。该策略通过 [saml:sub](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_saml.html#CreatingSAML-userid) 条件键定位到特定用户。
- 实时评估 — 这些 CMP 附加到 IAM [权限集](https://docs.aws.amazon.com/singlesignon/latest/userguide/permissionsets.html)上。在工程师下一次调用 Amazon Bedrock 时，IAM 会评估更新后的策略，并据此允许或拒绝请求，无需重新身份验证。

## 前提条件

要部署该解决方案，你需要：

- 一个 [AWS 账户](https://signin.aws.amazon.com/signup?request_type=register)，且具有创建 IAM 角色、客户管理策略、AWS Lambda 函数、Amazon Athena [工作组](https://docs.aws.amazon.com/athena/latest/ug/workgroups-manage-queries-control-costs.html)、Amazon S3 存储桶和 Amazon DynamoDB 表的权限。
- 一个 AWS IAM Identity Center，其中包含你配置并分配给用户的权限集。
- 配置 Amazon Bedrock [模型调用日志](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html)，把日志投递到你的 Amazon S3 存储桶。
- 已配置好相应凭证的 [AWS Command Line Interface](https://aws.amazon.com/cli/)（AWS CLI）。
- 一个 Slack 工作区，其中有一个为斜杠命令、交互性和 bot 消息配置好的应用。

## 部署步骤

你可以从 [https://github.com/aws-samples/sample-bedrock-spend-enforcement](https://github.com/aws-samples/sample-bedrock-spend-enforcement) 获取本文的代码。概括来说，部署步骤可以总结如下：

### 第 1 步：创建 Amazon Athena 成本视图

Amazon Bedrock 的调用日志以 JSON 形式落到 Amazon S3 上。首先在日志位置之上创建一个 Athena 表，然后创建一个把 token 数量换算为美元金额的视图。该视图会按用户身份和当前日期分组，把输入与输出 token 乘以每个模型公布的每 token 费率。

请把费率常量替换为你所在区域当前的 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)。每个模型系列都需要一个明确的价格分支。未映射的模型会按最高档位计价作为故障保护（而不是 $0），这样未识别的模型就无法绕过管控。请关注随附的告警，并及时补上该模型的真实费率。

### 第 2 步：创建客户管理策略

创建管控策略，对特定的一组用户（由其 `saml:sub` 值标识）拒绝某个模型系列。从空用户列表开始，Lambda 会在运行时通过发布新的策略版本填充它。把这些策略附加到 IAM 权限集上。当你使用 iam:CreatePolicyVersion 更新这些客户管理策略时，改动会立即生效，无需重新预置。

### 第 3 步：部署管控 Lambda 与调度

部署管控处理器，并用 Amazon EventBridge 把它调度为每 15 分钟运行一次。每次运行时，处理器查询 Athena 视图、读取 DynamoDB 例外表、计算每个档位的受限用户列表，并发布更新后的 CMP 版本。

这一设计在构造上就是幂等的：每次运行都根据当天的累计支出重新计算完整的受限用户列表，而不是施加增量改动。连续运行两次处理器，或完全漏掉一次运行，在追上进度后都会产生相同结果。没有会被重复应用的东西，也没有需要回滚的东西。每日重置同样是隐式的。Athena 视图把支出限定在一个滚动的一天窗口内（以你选择的参考时区的 00:00 为界）。一旦该窗口翻页，下一次运行重新计算出的列表就会略去那些不再超阈值的用户，他们的 CMP 限制会在随后一次 iam:CreatePolicyVersion 调用中自动解除。没有单独的解除封锁代码路径需要维护或担心失步。

### 第 4 步：添加例外工作流

有些工程师因大规模迁移、客户升级或模型评估而确实需要更高限额。与其手动编辑策略，不如暴露一个 Slack 斜杠命令（`/bedrock-limit`），让管理员用它授予有时间上限的自定义限额。该命令会向 DynamoDB 例外表写入一条记录，包含工程师身份、提高后的限额和过期时间戳。它还会记录一条审计线索，说明是谁授予的、何时授予的，以及（可选）由哪张工单批准。在过期时间戳上设置 DynamoDB Time to Live（TTL）属性，例外就会自动清理。在下一次运行时，管控 Lambda 会读取生效中的例外，并相应调整每位工程师的阈值。

## 经验教训

在生产环境中运行这套系统，浮现出一些值得分享的经验。

- **成本：** 对于这一用例，AWS Lambda、DynamoDB 和 S3 在服务数百名工程师的情况下，每月成本远低于 $10。Amazon Athena 是需要仔细估算规模的那一项：账单随扫描范围和运行频率增长，因此请保持调用日志 schema 精简（只保留 token 数量和身份/模型元数据），并每次运行只查询一次预先聚合的成本视图，而不是反复扫描原始日志。
- **JSON 日志意味着无论选择哪些列，每次查询都会扫描每一个字节。** Athena 必须先反序列化每一行才能应用任何过滤条件，因此针对同一视图的四个不同过滤查询各自都扫描了相同的约 11 GB。列裁剪和谓词下推对面向行的 JSON 没有帮助。解决办法是把派生查询合并为一个 `SELECT ... GROUP BY` 并在应用代码中拆分结果，或者更进一步，把日志转换为 Parquet 之类的列式格式。
- **治理会加速采用，而不是限制采用。** 这里有一个反直觉的战略洞见：设置严格的按用户上限，反而让管理层*愿意扩大访问范围*，而不是收缩。因为支出现在可观测了，Jamf 可以放心地增加启用 AI 的工程师人数。
- **始终保持可用模型。** 让一个低成本模型始终可用是有意为之。一个已经用满 100% 预算的工程师仍然能完成工作，因此管控不会彻底阻断生产力。
- **新模型需要明确的价格分支。** 把价格映射当作一等运营资产来对待，并在启用新模型的那一刻补上它的费率。
- **IAM 策略版本上限。** 一个托管策略最多保留五个版本。管控 Lambda 必须先删除最旧的非默认版本，再创建新版本，否则 iam:CreatePolicyVersion 会失败。
- **要考虑 Amazon Athena 的异步查询模型。** Athena 查询是先提交再轮询的，不是同步返回的。Lambda 处理器必须启动查询、等待完成，然后读取结果。请据此设置函数超时。
