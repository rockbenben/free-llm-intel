# 使用 Strands Agents 通过高级编排技术自定义 agent 工作流

大语言模型（LLM）agent 把基础模型的推理能力与专门工具、领域知识结合起来，彻底改变了我们处理复杂、多步任务的方式。虽然使用 ReAct 等框架的单 agent 系统在直白任务上表现良好，但现实挑战往往需要多个专用 agent 协同工作。想象一次商务出行规划：需要一个 agent 依据日程约束研究航班，另一个寻找会议地点附近的住宿，第三个协调地面交通——每个都需要不同的工具与领域知识。这种多 agent 方法带来一个关键架构挑战：编排 agent 之间的信息流，以确保可靠、可预测的结果。缺少恰当的编排，agent 交互会变得不可预测，使系统在生产环境中难以调试、监控与扩展。Agent 编排通过定义显式工作流来应对这一挑战，规定 agent 如何通信、何时执行，以及它们的输出如何整合为连贯的解决方案。编排不是让 agent 随意交互，而是建立结构化路径，让推理透明、让信息流有意图。

[Strands Agents](https://strandsagents.com/latest/) 是一个专为构建可编排的人工智能（AI）系统而设计的开源 SDK。它提供灵活的 agent 抽象、无缝的工具集成、完整的可观测性，以及 [GraphBuilder](https://github.com/strands-agents/sdk-python/blob/main/src/strands/multiagent/graph.py) 这类编排组件，让开发者能够精准可控地把 agent 连接成有向工作流。

本文探讨用 Strands Agents 实现的两种强大的编排模式。我们使用同一套旅行规划工具，演示不同编排策略如何通过各自不同的推理方式解决同一个问题：[ReWOO](https://arxiv.org/pdf/2305.18323)（Reasoning Without Observation，无观察推理）把规划、执行与综合拆成相互独立的阶段；[Reflexion](https://arxiv.org/pdf/2303.11366) 则通过结构化的批评与改进循环实现迭代优化。这些示例将展示 Strands 如何对多 agent 工作流实现精准控制，从而得到更可靠、更透明、更易维护的 AI 系统。

## 使用 Strands Agents 入门

[Strands Agents ](https://strandsagents.com/latest/)是 AWS 近期推出的开源框架，用于构建可上生产的 AI agent。它通过把 [agent loop](https://strandsagents.com/latest/documentation/docs/user-guide/concepts/agents/agent-loop/) 抽象为三个核心组件来简化 agent 开发：

- **Model Provider**：推理引擎（例如 Amazon Bedrock 上的 Claude）
- **System Prompt**：塑造 agent 角色与约束的指令
- **Toolbelt**：agent 可调用的 API 或函数集合

这种模块化设计让用户从简单的单 agent 系统起步，再扩展到复杂的多 agent 架构。Strands 内建支持[异步操作](https://strandsagents.com/latest/documentation/docs/user-guide/concepts/streaming/async-iterators/)、会话状态管理，并与包括 [Amazon Bedrock](https://aws.amazon.com/bedrock/?refid=978e13b6-fa37-4872-9001-1825f3ca3367)、Anthropic 与 Mistral 在内的多个提供方集成。它还能与 [Lambda](https://strandsagents.com/latest/documentation/docs/user-guide/deploy/deploy_to_aws_lambda/)、[Fargate](https://strandsagents.com/latest/documentation/docs/user-guide/deploy/deploy_to_aws_fargate/) 与 [AgentCore](https://aws.amazon.com/bedrock/agentcore/) 等 AWS 服务无缝集成。

让 Strands 尤其强大的是它的[多 agent 编排](https://aws.amazon.com/blogs/opensource/introducing-strands-agents-1-0-production-ready-multi-agent-orchestration-made-simple/)能力。用户可以通过多种方式组合 agent：把一个 agent 当作另一个 agent 的工具、通过 handoff 在 agent 之间传递控制权，或协调多个 agent 并行工作。该 SDK 的 GraphBuilder 特性让用户把 agent 连接成结构化工作流，使它们能以可控、可预测的方式在复杂任务上协作。

针对生产部署，Strands 通过 [OpenTelemetry](https://strandsagents.com/latest/documentation/docs/user-guide/observability-evaluation/traces/) 集成提供企业级[可观测性](https://strandsagents.com/latest/documentation/docs/user-guide/observability-evaluation/observability/)。这带来了覆盖整个 agent 系统的分布式追踪，让用户在从原型扩展到生产负载时能轻松调试问题并监控性能。

## Strands 的 agent 编排基础

[ReAct 模式](https://arxiv.org/pdf/2210.03629)是如今多数 AI agent 的默认做法。它把规划、工具调用与答案综合合并进单个 agent 循环。这在简单任务上可行，但在复杂场景中会带来问题。agent 可能在没有清晰策略的情况下反复调用工具、把证据收集与结论混在一起，或在未经验证时急于给出答案。在需要结构化推理、合规检查或多步校验的应用中，这些问题会变得关键。这正是编排发挥作用之处。

不是让一个 agent 做所有事，Strands 支持创建在解决问题中各司其职的专用 agent。例如，一个 agent 负责规划方法，另一个执行计划，第三个综合结果。用户把这些 agent 连接到符合确切需求的受控工作流中。在 Strands 中，编排模式采用图执行模型。可以把它想成一张流程图：

- 每个节点是一个专用 agent
- 边定义信息如何在 agent 之间流动
- 该结构让推理步骤可见、可调试

与 ReAct 隐藏的决策过程不同，图会暴露每一步。用户可以追踪哪个 agent 产出了什么输出、何时可用，以及下一个 agent 如何使用它。这种透明性对构建可靠系统至关重要。Strands 为任何编排模式提供四个基础组件：

- **Nodes**：封装特定逻辑或专业知识的 agent
- **Edges**：定义执行顺序与数据流的连接
- **AgentResult**：每个 agent 输出的标准化格式
- **GraphResult**：包含耗时、输出与所走路径的完整执行轨迹

GraphBuilder API 让用户把这些组件接线在一起，定义哪些 agent 参与、数据如何在它们之间流动，以及用户输入从何处进入系统。运行时，图会确定性地执行并返回结构化结果。

[![带节点、边、AgentResult 与 GraphResult 的 Strands 典型 agent 编排模式](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/25/agent_orchestration.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/25/agent_orchestration.jpg)

考虑一个文档问答 pipeline：

```
User Query → Retriever Agent → Summarizer Agent → Final Answer
builder = GraphBuilder()
builder.add_node(retriever, "retriever")
builder.add_node(summarizer, "summarizer")
builder.add_edge("retriever", "summarizer")
builder.set_entry_point("retriever")
```

Retriever 检索相关文档。Summarizer 对它们做浓缩。每个 agent 只在需要时看到自己需要的数据。流程显式、可预测、易于调试。同一做法可扩展到复杂模式。用户可以加入针对不同推理路径的分支、用于迭代优化的循环，或用于探索多种策略的并行执行。关键在于：对信息如何在系统中流动始终保有控制。

在接下来的章节中，我们实现第一种模式：ReWOO，它把规划与执行分离，以构建更可靠的 agent 工作流。

## 数据集与默认编排

### 数据集详情

我们在 τ-Bench 航空领域数据集（Yao 等，2024）上评估系统，它包含 300+ 条航班记录、500 个合成用户档案、2,000+ 条预生成的预订、详细的航空公司政策、用于预订操作的模拟 API，以及 50 个结构化的真实场景。这一全面的基准提供了一个受控而接近真实的试验场，用于评估 agent 如何解读政策、执行恰当的 API 调用，并在包括升舱、行程变更与取消的复杂航空运营中保持一致。原始数据集把每个任务呈现为多轮对话，但为便于展示编排模式，本教程把它们简化为单轮查询。

### 架构速览：使用 ReAct 的默认编排

ReAct（Reasoning + Acting）在单个 agent 循环内交替进行两个阶段。agent 用自然语言推理以决定下一步、按需调用工具、观察工具输出，再带着该观察继续推理，直到能给出最终答案。

在 Strands Agents 中，**ReAct** 基线干净地映射为单个 `Agent`，它持有 τ-Bench 航空工具集——一组航空工具（搜索航班、预订/修改/取消预订、查询档案等）。这些工具是 Tau-Bench 数据集中提供的 python 函数，通过 `@tool` 装饰器转换为 Strands 工具。

### 架构速览：ReWOO（无观察推理）

**ReWOO** 重构的是“工具如何使用”，而不是“存在哪些工具”。我们为所有航空 API 保留单个 tool-executor，但在其外围强制 plan → execute → synthesize 的分离。在 Strands 中，这变成一张小而显式的图，每个节点返回带类型的结果（`AgentResult`），运行时以确定性的方式把这些结果向下游传递。这带来了治理性、可观测性与可重复性。

- **Planner（只做规划）。** 产出严格格式化的计划。
- **Worker（只做执行**）。解析计划、解析参数、调用工具，并以规范化结构累积证据。把执行与规划解耦，使工具使用可预测且可强制执行策略（worker 只能运行计划授权的内容）。
- **Solver（只做综合）**。读取证据——来自工具的结果，而非直接调用工具——然后组织最终答案。它让工具副作用与决策过程可审计，避免在最后一步出现“隐藏”的后续调用。

[![ReWOO 编排：一个 planner 制定计划，executor 执行计划的各步骤，solver 综合最终答案](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/25/rewoo.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/25/rewoo.jpg)

用 Strands 的 `GraphBuilder`（节点、边、入口点）构建后，这就成为一个确定性的 DAG。运行时把原始任务加上上游节点的输出交给每个下游节点——这些都记录在 `AgentResult` 中。

```

b = GraphBuilder()
b.add_node(planner_agent, "planner")
b.add_node(worker_agent,  "worker")
b.add_node(solver_agent,  "solver")
b.add_edge("planner", "worker")
b.add_edge("worker",  "solver")
b.set_entry_point("planner")
graph = b.build()
```

### Planner：使用严格语法的纯规划 agent

planner 生成的是描述工具使用的声明式程序，而不是答案。以下是设计有效 planner prompt 的重要特性：

- 枚举允许的工具名及其参数集合
- 提供 few-shot 示例，向 LLM 演示如何规划以回答给定的用户查询。
- 强制输出形状。我们使用了如下形式：

```
Plan 1: <short intent>
#E1 = <tool_name>[key=value, ...]

Plan 2: <short intent>
#E2 = <tool_name>[key=value, ...]

#E4 = REPEAT(<analysis_or_count>) {
    <tool_a>[...]
    <tool_b>[...]
}
```

计划以 `AgentResult` 返回。严格的计划可直接用于审计，并最大程度减少歧义。它还使静态检查成为可能（例如“只允许这些工具；每步一个”），且在任何东西运行之前完成。

### Worker：具备参数与循环解析的确定性执行器

worker 只执行计划授权的内容；参数解析是数据驱动的。这使行为在不同运行与模型版本之间可复现。worker 把计划当作可执行的规格说明。

- **统一的计划解析器：** 它同时解析常规步骤与 REPEAT 块，按证据 ID 排序并按顺序执行。它同时解析常规步骤与 REPEAT 块，按证据 ID 排序并按顺序执行。

- **证据账本：** 每个步骤都会产出一条结构化记录（`#E{id}`，含描述与结果）。错误会被记录为证据，而不是静默失败。step_evidence[f’#E{eid}’] = {  `step_evidence[f'#E{eid}'] = { 'evidence_id': f'#E{eid}', 'description': f"Execute {tool} with {kwargs or 'no parameters'}", 'results': result_text<br /> } all_evidence.update(step_evidence)`
- **上下文感知的动态参数解析：** 从 *(a)* 原始任务与 *(b)* 前 N 条证据构建上下文。从该上下文中填充占位符（例如机场代码、预订 ID）——不要在原始字符串上使用脆弱的正则。这可以有几种不同做法。一种是用 LLM 从构建好的上下文推断参数值。第二种是用正则匹配来解析参数值。
- **带特殊分支的动态工具派发：** 使用 `getattr.` 直接调用工具。

### Solver：构建最终答案并呈现给用户

Solver 把 Worker 的执行证据与原始用户查询结合起来生成最终响应。它接收结构化的证据字典，并将其综合为自然语言答案。solver 从不调用工具。它做以下几件事：

- **证据解析** – 从 worker agent 节点读取原始任务与 worker 的证据。
- **计划重建** —— 把证据规范化为紧凑、有序的“plan + evidence”文本块。
- **最终答案生成** – 使用 LLM 配合恰当的 prompt 产出最终答案，显式处理各项约束与取舍。

```
solve_prompt = """Solve the following task or problem. 
To solve the problem, we have made step-by-step Plan and retrieved 
corresponding Evidence to each Plan. Use them with caution since long 
evidence might contain irrelevant information.

{plan}

Now solve the question or task according to provided Evidence above. 
Respond with the answer directly with no extra words.

Task: {task}
Response:"""
```

把综合与执行分离，可以得到清晰的决策日志与稳定的延迟。它还让你无需改动规划/执行逻辑就能轻松替换综合阶段的 prompt 或模型。

## 架构速览：Reflexion（自我批评）

Reflexion 是一种编排模式：agent 生成候选答案以及对该答案的批评，再用这份批评在有界循环中修订答案。目标不是盲目“重试”，而是依据显式、机器可解析的反馈（例如违反的约束、遗漏的检查、薄弱的论证）有针对性地修订。换句话说，Reflexion 把模型反馈转成结构化的控制信号，用它支配一轮或多轮额外处理，一旦答案满足既定标准就停止。

Reflexion 用刻意的 draft → critique →（可选）revision 循环包裹既有的航班 tool-executor。系统不再直接接受第一次输出，而是生成候选答案、按显式标准评估它，并且只在批评认为应当修订时才修订。其动机是这种方法能带来更高的答案质量。Reflexion 图用 `GraphBuilder` 构建，包含 2 个节点。

- **Draft（只做规划）。** 产出初始答案与初始反思。
- **Revisor（只做执行**）。在改进查询、修订答案与反思答案之间循环。

[![Reflexion 编排：包含 draft agent、reflection agent 与 revisor agent](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/25/reflexion.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/25/reflexion.jpg)

虽然编排被建模为 DAG，revisor 节点内部封装了最多三轮修订循环，并按需调用工具。每个节点返回 `AgentResult`；运行时把上游结果转发给下游节点，并把完整轨迹记录在 `GraphResult` 中。

### Draft：生成初始答案与批评

draft 节点使用与其他模式相同的航空 tool-executor 产出初始答案。紧接着，它用一段反思 prompt 调用 LLM，执行一次聚焦的“反思”过程，标出缺口（违反的约束、遗漏的检查、薄弱的论证），并输出一份紧凑、带标签的 payload，供 revisor 确定性地解析：

```
reflection_system_prompt="""You are analyzing a flight assistant's response that uses real flight database tools.
        
IMPORTANT: The flight data comes from real database queries, NOT hallucination.
        
Analyze the response quality on these dimensions:
: Does it address all parts of the user's query? 
: If the user query clearly states the final goal and if it can be 
fulfiled as per the policy, then does the response show that?
: Is the information presented clearly and logically?
: Are next steps or options clearly presented?
: Is the tone helpful and appropriate?
: What important details are missing?
: REVISE or ACCEPT
: Why this decision was made
"""
```

修订后的格式化 payload：`**Answer**: …**Self-Reflection**: …**Needs-Revision**: True|False**User-Query**: …`

### Revisor：在修订与生成阶段之间循环

revisor 读取 draft 的 payload，解析其中的标签（Answer、Self-Reflection、Needs-Revision、User-Query），并判定是否需要修订。若需要，它用批评改进原始用户查询（例如“限制为 ≥ 11:00 出发、≤ 1 次中转、最短停留 70m”），并再次调用 tool-executor 产出修订后的答案。随后它用同样的标签再次反思。该循环是有界的（例如最多 3 轮），一旦批评返回 `Needs Revision:False` 就停止。查询由一个 LLM 使用专门设计的 prompt 来改进。

```
query_improver_system_prompt="""You are a query improvement specialist. 
Based on reflection analysis, improve the original user query to address 
identified issues and guide better responses.

Examples:
Original: "Book me a flight from NYC to LA tomorrow"
Issue: "Agent booked immediately without showing options"
Improved: "Please SEARCH and SHOW ME available flight options from NYC to
 LA tomorrow. I want to see different times, prices, and airlines before deciding. 
DO NOT book anything until I confirm."
Now improve the provided query based on the specific reflection issues identified."""
```

## 结果：不同编排模式的响应

本节我们看数据集中的一些示例，以及每种编排模式的表现。

**示例 1：**

*“用户查询：我是 Lucas Brown（user id 是 lucas_brown_4047）。由于家庭急事，我需要修改我的航班预订 EUJUY6 的日期，并把它推后 2 天。”*

**胜出者：** ReWOO（28s）—— *符合政策地拒绝，且未做不安全变更*

**小结**

- ReAct（17s）：快但不正确——声称可以对 Basic Economy 票价改期并收费。ReWOO（28s）：正确——阻止修改，指向取消/重订路径。Reflexion（60s）：不符合政策——承认是 Basic Economy，却仍说可以继续改期；自我评估为“ACCEPT”，没有捕捉到这一违规。

**示例 2：**

**用户查询：***“我的 user id 是 mohamed_silva_9265。我想知道我的礼品卡余额合计与礼券余额合计……然后我想把最近的预订改成最便宜的商务往返，且不改日期……如果 basic economy 不能改，那就取消并重订一张……先用礼券，再用礼品卡，最后用 Mastercard；告诉我 Mastercard 会被扣多少。”*

**胜出者：** Reflexion（116s）—— *遵循用户预先授权的“取消 → 重订”路径，保留日期，给出合计，并算出精确的 Mastercard 余额。*

**小结**

- ReAct（67s）：搜索与支付计划详细，但改了一个日期（5 月 29 日），并在明确确认之前就做了变更；与用户约束冲突。
- ReWOO（43s）：计划扎实，正确识别 Basic Economy 与合计金额，建议取消 → 重订；整段往返的定价不一致，且没有最终的 Mastercard 金额。
- Reflexion（116s）：端到端完成：合计 → 约束检查 → 同日期最便宜往返 → 取消（已获授权）→ 计算 Mastercard = $1,286。最慢，但最贴合用户的确切指令。

**示例 3：**

**用户查询：***“我的 user id 是 james_taylor_7043。我想把我即将出行的从 LAS 到 IAH 的一次中转航班改成直飞。我的预订 ID 是 1N99U6。我还想去掉我的托运行李，并希望 agent 为此退款给我。”*

**胜出者：** **Reflexion（27s）** —— *给出有效的直飞选项，并按政策正确拒绝行李移除退款，且没有提前变更。*

**小结**

- ReAct（9s）：安全但信息不足——没有给出任何选项；提出了一项违反政策的操作。
- ReWOO（25s）：变更过于急切——用两个航班更新预订，并在用户选择之前就发起退款；行李问题被不必要地转交人工。
- Reflexion（27s）：符合政策且以用户为中心——给出具体的直飞选项，说明行李不予退款，并等待用户选择。

**示例 4：**

**用户查询：***“我是 Anya Garcia（ID：anya_garcia_5901）。我订了一张航班（3RK2T9），我想把乘客姓名从 Mei Lee 改成 Mei Garcia。请完成这项修改。”*

**胜出者：** ReAct（8s）—— *正确且路径最短：展示精确的更新预览，并等待一次是/否确认。*

**小结**

- ReAct（8s）：正确预览 → 一键确认；最快且忠实于用户意图。
- ReWOO（14s）：拆解得当（身份校验 + 更新调用），但证据不一致（在 `#E4` 中乘客仍是“Lee”）。
- Reflexion（40s）：对一次直接的编辑过度思考；最终没有执行任何修改。

### 何时使用哪种模式

- ReAct（快速、线性的“做显而易见的事”）使用时：简单、无歧义的更新或查询，只需 1–2 次工具调用且没有取舍（例如改名、开关、查询 → 回复）。优势：延迟最低；规划最少，但如果过度调用工具，延迟可能上升。注意：可能跳过政策/资格检查，若不谨慎会做出不安全变更。
- ReWOO（带治理的 plan → execute → synthesize）使用时：你需要*有序依赖*与在变更前的*政策闸门*（例如先确认票价等级，再搜索，然后更新）。优势：数据流透明；Graph/Agent 结果可审计；设计上更安全。注意（参数）：如果不使用 LLM，参数解析/校验必须极其细致（类型/枚举/必填）。如果使用 LLM 解析参数，请传入丰富上下文（schema + 示例）以便正确绑定——会增加延迟，但提升复杂参数的可靠性。
- Reflexion（先分析选项，再行动）使用时：多约束决策、取舍或政策细节需要比较选项（例如在支付规则下最便宜的行程）。优势：更擅长在备选方案之间推理并给出有依据的选择。注意：较慢；除非给反思设上限，否则会在琐碎编辑上反复追问。

## 架构速览：混合编排——由 ReWOO 引导的 ReAct

综合考虑 ReWOO（治理与可审计）、ReAct（速度与灵活）与 Reflexion（通过批评提升质量）的优缺点，我们采用一种混合方式，兼具 ReWOO 的计划纪律与 ReAct 在步骤内的敏捷性。先由 ReWOO Planner 产出一段严格、按步骤索引的程序（#E1…#En），指明所用工具及其顺序。随后执行切换为计划引导的 ReAct 循环，在每个步骤内部运行：agent 思考 → 用先前的证据校验参数 → 调用被授权的工具 → 观察，并按需做一次轻量改进。这在保留全局保证（不新增工具、不重排顺序、变更前有政策闸门）的同时，保留了参数绑定与微观决策的局部灵活性。在 Strands 中，这种混合映射为一张两节点图：

**Planner（ReWOO）**：只生成步骤程序（该节点内不调用工具）。输出是带 #E 步骤的带类型计划产物（例如：获取余额 → 拉取最近的预订 → 搜索选项 → 比较成本 → 有条件地执行变更）。

**计划引导的 ReAct Worker：** 消费计划与用户任务；对每个 #E 步骤执行一次局部 ReAct 循环，但绝不重排步骤或调用计划之外的工具。它校验参数、应用政策闸门（例如 Basic Economy ⇒ 取消 → 重订），并综合最终答案。planner 与 executor 使用同一套 τ-Bench 航空工具集（搜索/预订/修改/取消、用户/预订查询、数学运算等），以 Strands 工具形式暴露。

[![混合编排：包含 planner 与 react 风格 executor](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/25/hybrid.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/25/hybrid.jpg)

**局部 ReAct 循环（每个步骤 #Ek，有界）：**

```
THINK: derive & validate args from {task, policy, evidence #E1..#Ek-1}
ACT: call the authorized tool for #Ek (no placeholders, no extra tools)
OBSERVE: parse result; at most one refinement pass if needed
COMMIT: append #Ek evidence and advance strictly to #Ek+1
```

与原生 ReAct 相比，计划带来了治理性与幂等性——agent 不会游荡或提前变更。与纯 ReWOO 相比，步骤内的循环能处理现实中的凌乱（参数绑定、小规模重试）而无需重新规划。与 Reflexion 不同，它对直白任务避免了多轮批评的开销，同时仍产出可审计的轨迹（计划 + 每步证据）。在实践中，我们看到它在需要有序检查的多步请求上表现出色（例如合计 → 票价规则 → 搜索 → 取消/重订 → 支付拆分），同时受益于每次工具调用内部的小范围局部推理。

## 结语

本文展示了 Amazon Strands 上的自定义编排如何帮助用户超越单一、庞大的 agent，对推理、工具使用与信息流实现显式控制。使用同一套 τ-Bench 航空工具包，我们在真实约束下比较了 ReAct、ReWOO 与 Reflexion 三种模式，并观察到它们在延迟、成本与答案质量上各有不同取舍。对简单查询与单字段更新，ReAct 仍是开销最低的路径。当正确性取决于良好规划与有序依赖时，ReWOO 是合适的默认选择：用户可以在变更前设置政策闸门、用更丰富的上下文解析参数，并保留带类型的证据轨迹以供审计。Reflexion 增加了自我批评，以处理多约束选择与支付/行程取舍，代价是额外的思考开销。Strands 的图执行模型提供带类型的交接、执行轨迹与可强制执行的工具契约，让用户能按用例调整这些模式——CRUD 用紧凑循环、受治理的更新用 plan → execute → synthesize、选项分析用 reflect → revise——同时对副作用与模型漂移设界。

要构建生产级 agent，应把编排当作控制面：选择与你的依赖结构和风险画像相匹配的模式，然后为其加上可观测埋点。访问[这个 GitHub 仓库](https://github.com/baishch/strands-samples/tree/main/02-samples/15-custom-orchestration-airline-assistant) 获取端到端示例、prompt 与可运行的图。
