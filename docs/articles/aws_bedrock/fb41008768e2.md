# 使用 AWS Quick 与 Snowflake Cortex AI 自动化 AML 告警分级

在 AWS 与 [Snowflake](https://aws.amazon.com/marketplace/pp/prodview-3gdrsg3vnyjmo) 上运行的金融机构，可以从一个[深度集成的框架](https://www.snowflake.com/en/why-snowflake/partners/all-partners/aws/)中受益：该框架把 [Snowflake 的 AI Data](https://www.snowflake.com/en/why-snowflake/what-is-data-cloud/) Cloud 与 AWS 云基础设施结合起来，包括与 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/)、[AWS Glue](https://aws.amazon.com/glue/)、[Amazon SageMaker](https://aws.amazon.com/sagemaker/) 和 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 等 AWS 服务的集成。AWS 服务与 Snowflake 之间拥有 50 多项原生集成，组织可以构建既能保持数据安全、又能加速实现价值时间的合规工作流。

本文通过自动化金融服务中最耗人力的工作流之一——反洗钱（anti-money laundering，AML）告警分级——来演示这一集成的实际效果。你将使用 [AWS Quick Flows](https://docs.aws.amazon.com/quick/latest/userguide/creating-flows.html) 与 [Snowflake Cortex](https://www.snowflake.com/en/product/features/cortex/) 构建一个分级工作流，并通过 [AWS Quick](https://aws.amazon.com/quick/) 的 Model Context Protocol（MCP）集成连接两者。在我们的测试环境中，使用 AWS Quick 构建的自动化工作流把告警调查时间从 30-90 分钟缩短到 5 分钟以内。实际结果会因告警复杂度与数据量而有所不同。

随着 AI 应用的成熟，组织发现影响力最大的部署并不止于独立的助手，而是可重复的工作流——它们跨团队已在使用的工具进行编排，把多步骤手工流程变成一键体验。AWS Quick 是一项企业 AI 服务，提供由生成式 AI 驱动的聊天 agent、研究能力、用于任务自动化的 Quick Flows，以及用于流程自动化的 AWS Quick Automate；它汇聚来自多个来源的数据，包括原生索引、自定义知识库和用户上传的文件。作为 AWS Quick 的一部分，Quick Flows 把用户请求转换为标准化的 MCP 协议（一种开放协议标准）调用，从而无需自定义连接器，同时通过 OAuth 身份验证维持企业级安全。Quick Flows 非常适合 AML 分级，因为调查每次都遵循相同的结构化步骤：收集输入、运行调查、产出输出。同样的 MCP 方法也适用于团队目前仍需手工打通系统的可重复工作流，例如 FinOps 成本分级、SRE 事件响应或合规调查。

中大型银行的 AML 分析师通常每条告警要花 30 到 90 分钟手工收集数据并撰写处置说明（disposition narrative）。根据[行业研究](https://datos-insights.com/blog/are-you-too-negative-about-false-positives/)，金融机构通常会发现 90-95% 的 AML 告警是误报，因此高效的分级至关重要。这种规模的人工调查流程会给合规团队带来沉重的工作量。自动化让分析师能够更高效地处理告警、缩短调查时间，同时维持合规标准。

下面是从 Quick Flow 输入步骤到生成完整调查报告的端到端分析师体验。分析师打开已发布的 flow，输入告警 ID（例如 `ALT-2026-03-02-002`），并可选地指定时间窗口。随后该 flow 会：

- 校验输入并确认该告警存在。
- 通过 MCP 调用 Snowflake Cortex Agent，跨交易数据、客户画像、历史记录与合规政策对该告警进行调查。
- 产出结构化的调查报告：告警摘要、交易模式、客户画像、历史 SAR、政策引用、风险评分、处置建议以及说明草稿。

## 实施

本节逐步介绍构建 AML 分级工作流的过程，从准备 Snowflake 数据层到配置 Quick Flows 编排。我们从开始前所需的前提条件入手，每个步骤都建立在前一步之上，因此到最后你将拥有一个功能完整、端到端、可供分析师使用的自动化调查 pipeline。

### 前提条件

- 一个 AWS Quick 账户，且具备配置 MCP action 连接器的能力。
- 一个 [Snowflake 账户](https://signup.snowflake.com/)，可访问 Cortex Agents、Cortex Search 以及由 Snowflake 托管的 MCP 服务器功能。你需要有创建 `AGENT`、`MCP SERVER`、`CORTEX SEARCH SERVICE` 和 `SECURITY INTEGRATION` 对象的权限。
- Snowflake 中的 AML 数据。交易监控告警（来自你的 TMS，例如 Actimize、Norkom 或自研规则引擎）、客户/账户主数据以及 KYC/CDD 记录。一个为告警、交易、客户与处置维度建模的语义视图（semantic view）。
- Snowflake 中的合规文档语料。BSA/AML 政策手册、SAR 申报指南、既往调查笔记以及监管指引（FinCEN 咨询通告、FFIEC BSA/AML 手册节选），需加载到表中以供 Cortex Search 建立索引。
- 熟悉 SQL、Snowflake 管理以及 [AWS Identity and Access Management（IAM）](https://aws.amazon.com/iam/)相关概念。

### 步骤 1：准备 AML 语义视图（Snowflake）

当你提供给 Cortex Analyst 的[语义视图](https://www.snowflake.com/en/developers/guides/snowflake-semantic-view/)符合合规团队思考告警与调查的方式时，它的效果最好。由 Snowflake 托管的 MCP 服务器支持[配合 Cortex Analyst 使用语义视图](https://www.snowflake.com/en/developers/guides/best-practices-semantic-views-cortex-analyst/)。在 Snowsight 中依次进入 AI & ML、Semantic Views，并针对你在 Snowflake 中的 AML 表（维度与度量）[创建语义视图](https://docs.snowflake.com/en/sql-reference/sql/create-semantic-view)：

- **告警元数据：**alert_id、alert_date、rule_name、rule_category、severity、status、alert_score。
- **交易明细：**txn_id、txn_date、txn_type、amount、currency、channel、originator、beneficiary、beneficiary_country。
- **客户画像：**customer_id、full_name、risk_rating、country、industry、onboarding_date、pep_flag、sanctions_flag。
- **账户活动：**account_id、account_type、current_balance、avg_monthly_volume、status。
- **处置历史：**prior alerts、prior SARs、last disposition outcome、analyst notes。

定义告警、交易、客户、账户与处置之间的关系（join），使 agent 能够在单次查询中遍历数据模型。

### 步骤 2：为合规文档构建 Cortex Search 服务（Snowflake）

AML 分级高度依赖非结构化上下文。在你的合规文档语料之上创建一个 Cortex Search 服务，使 agent 能在每次分级时检索相关政策章节、SAR 申报模板与既往调查笔记。

```
CREATE OR REPLACE CORTEX SEARCH SERVICE aml_policy_search
ON search_content
ATTRIBUTES doc_type, effective_date, regulatory_body
WAREHOUSE = AML_WH
TARGET_LAG = '1 hour'
EMBEDDING_MODEL = 'snowflake-arctic-embed-l-v2.0'
AS (
    SELECT
        doc_id,
        doc_type,
        effective_date,
        regulatory_body,
        content AS search_content
    FROM FINCRIMES_DB.AML_SCHEMA.COMPLIANCE_DOCS
);
```

需要建立索引的文档包括贵机构的 BSA/AML 政策手册、SAR 申报阈值与说明模板、FinCEN 咨询通告、FFIEC BSA/AML 手册节选、既往调查笔记（按需脱敏）以及制裁/PEP 筛查指引。

### 步骤 3：创建 AML 分级 Cortex Agent（Snowflake）

创建一个[可编排的 Cortex Agent](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-manage)，在你的交易语义视图（Cortex Analyst）与合规文档搜索服务（Cortex Search）之上编排。agent 规范中包含一个系统指令块，用于编码贵机构的调查方法论。这个块是有意设置的，预期需要定制。此处提供的默认指令反映的是常见的 AML 分级工作流，但在部署到生产环境之前，你应调整它们以匹配贵组织的具体流程、升级标准与监管义务。

请审阅系统指令块中的编号步骤，并重新排序或删除不适用于你工作流的步骤。添加机构特有的上下文，例如你所在的司法辖区与适用的监管框架。更新响应格式块，使其匹配你的案件管理系统所期望的输出结构。用你环境中有代表性的告警 ID 或查询模式更新 `sample_questions` 块，以帮助在测试期间验证 agent 行为。

请让编排预算保持保守，使 agent 能在 AWS Quick MCP 超时限制（目前为 300 秒）之内充分完成。agent 创建完成后，前往 Snowsight 更新 Cortex Analyst 工具所使用的默认 warehouse。

```
CREATE OR REPLACE AGENT aml_triage_agent
COMMENT = 'Daily AML alert triage agent'
FROM SPECIFICATION
$$
orchestration:
  budget:
    seconds: 120
    tokens: 16000
instructions:
  system: |
    You are an AML alert triage assistant for a regulated
    financial institution.
    Your job is to:
    (1) Retrieve and summarize the flagged transaction pattern.
    (2) Pull the customer profile and account activity baseline.
    (3) Check for prior alerts, SARs, or investigations on this
    customer.
    (4) Retrieve relevant policy sections and SAR filing
    thresholds.
    (5) Produce a structured investigation brief with a risk
    score and disposition recommendation.
    Never fabricate transaction data. If data is missing, say so.
  response: |
    Always use this output format:
    1. Alert Summary (alert ID, rule, severity, date)
    2. Transaction Pattern (amounts, counterparties, channel,
    frequency)
    3. Customer Profile (risk rating, onboarding, country,
    industry)
    4. Prior History (past alerts, SARs, dispositions)
    5. Policy Reference (applicable thresholds, guidance)
    6. Risk Assessment (score 1-10, rationale)
    7. Disposition Recommendation (close / escalate / file SAR)
    8. Draft Narrative (2-3 paragraphs for case notes or SAR)
  sample_questions:
    - question: "Review alert ALT-2026-03-02-002"
      answer: "I will pull the transaction details, customer
      profile, check prior history, and produce an
      investigation brief."
tools:
  - tool_spec:
      type: cortex_analyst_text_to_sql
      name: TxnAnalyst
      description: TxnAnalyst
  - tool_spec:
      type: cortex_search
      name: PolicySearch
tool_resources:
  TxnAnalyst:
    semantic_view: FINCRIMES_DB.AML_SCHEMA.AML_SEMANTIC_VIEW
  PolicySearch:
    name: FINCRIMES_DB.AML_SCHEMA.AML_POLICY_SEARCH
$$;
```

### 步骤 4：创建由 Snowflake 托管的 MCP 服务器

Snowflake Cortex Agents 不会自动暴露给外部 MCP 客户端。创建一个 `MCP SERVER` 对象，列出你希望 AWS Quick 发现的工具。

```
CREATE OR REPLACE MCP SERVER aml_mcp_server
FROM SPECIFICATION
$$
tools:
  - title: "AML Triage Agent"
    name: "aml_triage"
    type: "CORTEX_AGENT_RUN"
    identifier: "FINCRIMES_DB.AML_SCHEMA.AML_TRIAGE_AGENT"
    description: "Runs the AML alert triage agent for daily
    compliance investigation."
  - title: "Transaction Analyst"
    name: "txn_analyst"
    type: "CORTEX_ANALYST_MESSAGE"
    identifier: "FINCRIMES_DB.AML_SCHEMA.AML_SEMANTIC_VIEW"
    description: "Governed natural-language queries over
    transaction monitoring data."
  - title: "Policy Search"
    name: "policy_search"
    type: "CORTEX_SEARCH_SERVICE_QUERY"
    identifier: "FINCRIMES_DB.AML_SCHEMA.AML_POLICY_SEARCH"
    description: "Search BSA/AML policy, SAR guidelines,
    and prior investigation notes."
$$;
```

### 步骤 5：为 AWS Quick 设置 Snowflake OAuth

AWS Quick 的 MCP 集成支持 OAuth。Snowflake 托管的 MCP 服务器支持 OAuth 2.0，但不支持动态客户端注册（Dynamic Client Registration），因此你将使用 AWS Quick 中的手动配置选项。

- 在 Snowflake 中创建一个类型为 `OAUTH` 的 `SECURITY INTEGRATION`，并注册 AWS Quick 的重定向 URL。  `-- CREATE ROLES CREATE OR REPLACE ROLE IDENTIFIER('AML_MCP_ROLE'); -- Create a security integration for quicksight CREATE OR REPLACE SECURITY INTEGRATION aml_quick_oauth TYPE = OAUTH OAUTH_CLIENT = CUSTOM ENABLED = TRUE OAUTH_CLIENT_TYPE = 'CONFIDENTIAL' OAUTH_REDIRECT_URI = 'https://{region}.quicksight.aws.amazon.com/sn/oauthcallback' OAUTH_ISSUE_REFRESH_TOKENS = TRUE OAUTH_REFRESH_TOKEN_VALIDITY = 86400 PRE_AUTHORIZED_ROLES_LIST = ('AML_MCP_ROLE');`  请在 AWS Quick 控制台中确认你部署区域的准确 URL，并相应更新前一条命令中 `OAUTH_REDIRECT_URI` 的值。
- 运行以下命令以获取 client ID 与 client secret：  `SELECT SYSTEM$SHOW_OAUTH_CLIENT_SECRETS('AML_QUICK_OAUTH');`  记下 `OAUTH_CLIENT_ID` 与 `OAUTH_CLIENT_SECRET` 的值。
- 运行以下命令以获取 Snowflake OAuth 端点的值：  `DESC INTEGRATION aml_quick_oauth;`  记下 `OAUTH_AUTHORIZATION_ENDPOINT` 与 `OAUTH_TOKEN_ENDPOINT` 的值。

### 步骤 6：应用最小权限访问控制（Snowflake）

为 AWS Quick 的 MCP 访问创建一个专用角色。授予 MCP 服务器及其底层工具的 `USAGE` 权限。对 MCP 服务器的访问不会自动授予对其所暴露工具的访问权限。

```
CREATE OR REPLACE USER {quickuser} PASSWORD='{password}' DEFAULT_ROLE = AML_MCP_ROLE DEFAULT_WAREHOUSE='{DEFAULT_WAREHOUSE}';

GRANT USAGE ON DATABASE FINCRIMES_DB TO ROLE AML_MCP_ROLE;
GRANT USAGE ON SCHEMA FINCRIMES_DB.AML_SCHEMA TO ROLE AML_MCP_ROLE;
GRANT USAGE ON MCP SERVER FINCRIMES_DB.AML_SCHEMA.AML_MCP_SERVER
    TO ROLE AML_MCP_ROLE;
GRANT USAGE ON AGENT FINCRIMES_DB.AML_SCHEMA.AML_TRIAGE_AGENT
    TO ROLE AML_MCP_ROLE;
GRANT SELECT ON SEMANTIC VIEW
    FINCRIMES_DB.AML_SCHEMA.AML_SEMANTIC_VIEW TO ROLE AML_MCP_ROLE;
GRANT USAGE ON CORTEX SEARCH SERVICE
    FINCRIMES_DB.AML_SCHEMA.AML_POLICY_SEARCH TO ROLE AML_MCP_ROLE;
```

### 步骤 8：构建 AML 分级 Quick Flow

导航到 **Quick Flows** 并选择 **Create flow**。你可以用自然语言描述工作流，也可以使用可视化编辑器逐步构建。该 flow 由四个部分组成：输入步骤、包含 MCP action 步骤的 reasoning 组、输出步骤，以及可选的追问聊天。

#### 输入步骤：收集告警 ID

添加一个 **User input** 步骤，提示分析师输入告警 ID（例如 `ALT-2026-03-02-002`）和可选的时间窗口。这使 flow 可重复且具备自说明性。每次运行都以相同的结构化输入开始，因此不同分析师之间不存在 prompt 差异。

![Quick Flow 编辑器中的输入步骤，用于从分析师处收集告警 ID 与可选时间窗口](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/23/ML-20391-9.png)

*图 8：Quick Flow 编辑器：配置为从分析师处收集告警 ID 与可选时间窗口的输入步骤*

#### Reasoning 组：通过 MCP 调查告警

添加一个 Reasoning 组，包含用于调查该告警的分支逻辑。在本示例中我们使用 Reasoning 组，以便 flow 支持条件化的分级路径，例如把 `CRITICAL` 告警升级以便 BSA Officer 立即审阅、对 `HIGH_RISK_GEO` 告警应用强化审查，或在发现历史 SAR 时建议升级。如果你的工作流总是运行相同的 `aml_triage` 操作而没有任何条件分支，你也可以不使用 Reasoning 组来构建该 flow——把 Snowflake MCP 应用操作直接放在输入步骤之后即可。

![Quick Flow 编辑器，已向 flow 添加配置了调查逻辑的 reasoning 组节点](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/23/ML-20391-10.png)

在 reasoning 组内，添加一个 **Application actions** 步骤，并选择你在步骤 7 中创建的 Snowflake MCP 集成。选择 `aml_triage` 操作。为该 action 步骤编写 prompt 指令：

```
Investigate alert {alert_id} using the AML triage agent.
Pull the customer profile, summarize the flagged transaction
pattern, check for prior alerts and SARs, retrieve relevant
BSA/AML policy sections, and produce a structured investigation
brief with a risk score and disposition recommendation.
Use the eight-section output format: Alert Summary, Transaction
Pattern, Customer Profile, Prior History, Policy Reference,
Risk Assessment, Disposition Recommendation, Draft Narrative.
```

`{alert_id}` 变量的默认值会自动从输入步骤填充，你也可以手动覆盖它。reasoning 组可以使用自然语言指令加入额外的分支逻辑，以处理不同的告警场景。

对于 `CRITICAL` 严重级别的告警，reasoning 组会指示 agent 检查制裁名单，并将该案件标记为需 BSA Officer 立即审阅。当告警类别为 `HIGH_RISK_GEO` 时，agent 会把受益国与当前的 FATF 高风险司法辖区清单交叉比对，并检索 OFAC 筛查指引。如果该客户有历史 SAR 记录，agent 会检索既往调查说明，并建议升级而不是结案。

## 安全与治理考量

在把该 flow 共享给合规团队之前，有几项安全与治理方面的考量值得处理。

在访问控制方面，MCP 集成以 OAuth 身份验证后的角色（`AML_MCP_ROLE`）权限运行。请把该角色限定为对 MCP 服务器、agent、语义视图与搜索服务的最小 `USAGE` 与 `SELECT` 权限，并避免授予 `SYSADMIN` 或 `ACCOUNTADMIN`。

Cortex AI 在 Snowflake 的安全边界内处理数据，这意味着你的数据不会离开你的 Snowflake 账户。请确认你的 Snowflake 区域满足贵机构对受监管金融数据的数据驻留要求。

在许多司法辖区，AML 调查数据受「不得泄密」（tipping-off）限制的约束。请仅与获授权的合规人员共享该 Quick Flow，不要把它发布到全组织的 flow 库，也不要在面向客户的岗位上暴露它。

从审计角度看，AWS Quick 会记录 MCP 工具调用与 flow 执行，而 Snowflake 的 `ACCESS_HISTORY` 与 `ACCOUNT_USAGE` 视图会记录 Cortex Agent 执行的每一次查询。两者共同构成可供检查人员审阅的调查审计轨迹，每次 flow 运行都是一个独立、可追溯的事件。

该 flow 产出调查简报草稿与处置建议，但每一次 SAR 申报或结案都必须由人工合规分析师审阅并批准。该 flow 是调查的加速器，而不是自动化决策者。

请记录 Cortex Agent 使用哪个 LLM 模型，在你的模型清单中为其设定版本，并依据 [SR 11-7 / OCC 2011-12](https://www.federalreserve.gov/supervisionreg/srletters/sr1107.htm) 将其纳入贵机构的 AI/ML 模型风险管理框架。

请按照贵组织的密钥轮换策略轮换 Snowflake OAuth 凭证，并把 refresh token 的有效期设为满足运营需要的最短窗口。

随着调查方法论演进，请更新该 flow 并重新发布。Quick Flows 支持迭代细化，分析师会自动获得最新版本。

## 为什么选择 Quick Flows 而不是聊天 agent

Quick Flows 每次都会强制执行相同的调查步骤，这是本方案背后的核心设计决策。聊天 agent 松散地遵循 prompt 指令，输出会因每位分析师如何表述请求而变化；而 flow 促成确定性的结果：每条告警都经过相同的结构化输入、相同的推理逻辑与相同的格式化输出，无论由谁触发。

正是这种一致性，让调查报告默认就可供审计。每次 flow 运行都是一个独立、被记录的事件。reasoning 组中的条件分支会把 `CRITICAL` 告警导向强化步骤，并自动升级有历史 SAR 的客户，从而强制执行聊天 agent 无法可靠复现的逻辑。对于分级工作流之外的临时性问题，同一套 Snowflake MCP 集成在 Quick 聊天 agent 上同样适用。Quick Flows 与聊天 agent 共享同一基础，它们只是面向不同用例的不同界面。

## 结论

本文展示了如何使用 AWS Quick Flows 构建一个日常的 AML 告警分级工作流，通过由 Snowflake 托管的 MCP 服务器连接到 Snowflake Cortex Agent。从结构化输入步骤开始，该 flow 通过 MCP 调用 Cortex Agent，编排 Cortex Analyst（用于结构化交易与客户数据）与 Cortex Search（用于 BSA/AML 政策与既往调查笔记），随后呈现包含风险评分与处置建议的完整调查报告。

与输出随 prompt 措辞变化的聊天 agent 不同，Quick Flows 通过内置的输入校验、推理逻辑与格式化输出，强制执行可预测、可重复的序列。这让分析师无需学习 prompt 工程就能运行一致、高质量的分级，并可一键把工作流分发给整个团队。每位分析师都运行相同的结构化分级。输出格式是可预测的，每次运行都是独立、可审计的事件。同时，Quick Flows 中的 agentic 运行时让分析师能够与工作流对话以细化输出、提出追问，把结构化流程的严谨性与对话界面的灵活性结合起来。

这里的关键模式是：把 Cortex Agent 通过由 Snowflake 托管的 MCP 服务器发布为 MCP 工具，并从 AWS Quick 以 OAuth 连接它。同一套 MCP 集成可用于 Quick Flows、聊天 agent 与 AWS Quick Automate，因此你可以从用于日常分级的结构化 flow 起步，随着需求增长扩展到临时性聊天 agent 或企业级自动化。

要开始使用，请参阅[使用 AWS Quick Flows](https://docs.aws.amazon.com/quicksuite/latest/userguide/using-amazon-quick-flows.html)、[MCP 集成](https://docs.aws.amazon.com/quick/latest/userguide/mcp-integration.html)、[由 Snowflake 托管的 MCP 服务器](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-mcp)以及 [AWS Quick 用户指南](https://docs.aws.amazon.com/quicksuite/latest/userguide/)。如需进一步了解 AWS Quick 的功能与能力，请参阅 [AWS Quick 文档](https://docs.aws.amazon.com/quick/)并在 [AWS Quick 社区](https://community.amazonquicksight.com/)关注我们。
