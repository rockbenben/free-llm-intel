# 大规模组织 agent 的记忆：AgentCore Memory 中的命名空间设计模式

***2026 年 9 月：本文经过复核与更新，以确保内容准确。***

能够跨会话记住上下文的 AI agent，需要一套有条理、可检索且安全的记忆系统。在 AgentCore memory（Amazon Bedrock AgentCore 的一项能力）中，**命名空间**决定了长期记忆如何组织、如何检索，以及谁可以访问它们。命名空间设计一旦出错，检索时就可能冒出无关的上下文；更糟的是，某个用户的记忆会泄漏到另一个用户的对话中。

在本文中，你将学习如何为每种记忆策略设计命名空间层级、在精确检索与层级检索之间做出选择、用自定义命名空间变量扩展层级以支持多租户应用，以及如何借助 AWS Identity and Access Management（IAM）强制实施命名空间边界。如果你刚接触 AgentCore memory，请先阅读我们的入门文章：[Amazon Bedrock AgentCore memory：构建具备上下文感知能力的 agent](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-agentcore-memory-building-context-aware-agents/)。

## 什么是命名空间？

命名空间是在 AgentCore memory 资源中组织长期记忆记录的层级路径，其工作方式类似文件系统中的目录路径。当 AgentCore memory 从你的对话中提取长期记忆时，每条记录都会存储在某个命名空间下，例如 `/actor/customer-123/preferences/` 或 `/actor/customer-123/session/session-789/summary/`。

如果你用过 Amazon DynamoDB 中的分区键或 Amazon Simple Storage Service（Amazon S3）中的前缀布局，那么这一心智模型很容易迁移过来。选择分区键之前要先想清楚访问模式，设计命名空间之前同样要先想清楚检索模式。要明确谁需要访问这些记忆、细化到什么程度，以及哪些隔离边界绝不能跨越。与分区键的主要区别在于，命名空间支持层级检索。你可以在层级的任意层级发起查询，因此同一个记忆资源既能服务于限定在单个会话内的记忆，也能服务于跨会话的单个用户记忆，或更大范围的分组记忆。

## 命名空间模板与解析

创建记忆资源时，你需要在每个策略配置中定义 `namespaceTemplate`。模板支持三个内置变量：`{actorId}`、`{sessionId}` 和 `{memoryStrategyId}`。记忆资源通过 `bedrock-agentcore-control` 客户端管理。本文后面会讲到的事件与检索，则通过 `bedrock-agentcore` 数据面客户端完成。

```
control_client = boto3.client("bedrock-agentcore-control")

response = control_client.create_memory(
    name="CustomerSupportMemory",
    description="Memory for customer support agents",
    eventExpiryDuration=30,
    memoryStrategies=[
        {
            "semanticMemoryStrategy": {
                "name": "customer-facts",
                "namespaceTemplates": ["/actor/{actorId}/facts/"]
            }
        },
        {
            "summaryMemoryStrategy": {
                "name": "session-summaries",
                "namespaceTemplates": ["/actor/{actorId}/session/{sessionId}/summary/"]
            }
        }
    ]
)
```

当 `actorId=customer-456`、`sessionId=session-789` 的事件到达时，解析后的命名空间会变成 `/actor/customer-456/facts/` 和 `/actor/customer-456/session/session-789/summary/`。

这三个内置变量描述的都是对话本身：谁在对话、处于哪个会话、由哪个策略处理。如果你还需要按租户或团队等维度进行隔离，可以用自定义变量扩展模板，本文后面会介绍。

## 针对每种记忆策略设计命名空间

每种记忆策略对作用域的需求各不相同，命名空间应当反映这些数据的访问方式。

### Semantic 与 User Preferences：按 actor 划分作用域

Semantic memory 从对话中捕捉事实（例如「该客户所在的公司有 500 名员工」）。UserPreference memory 捕捉选择和风格（例如「用户偏好 Python」）。两者都会随时间不断积累，并且跨会话仍然相关。1 月获知的事实，到 3 月应该依然可以检索到。将它们的作用域限定在 actor：

```
/actor/{actorId}/facts/
/actor/{actorId}/preferences/
```

这样一来，无论用户的事实和偏好来自哪个会话，都会被归拢到同一个命名空间下。合并引擎会在同一命名空间内合并相关记忆，因此命名空间边界也就是合并边界，如图 1 所示。

![示意图：命名空间边界同时也是用户记忆记录的合并边界](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/22/REVBLOG-1294-1-1.png)

图 1：命名空间边界同时也是用户记忆记录的合并边界

如果你的应用需要跨 actor 检索，比如客服 agent 要查询其他客户报告的问题，那就把 actor ID 放在记忆类型之下：

```
/facts/{actorId}/
/preferences/{actorId}/
```

此时查询 `/facts/` 子树会横跨所有 actor，而精确命名空间 `/facts/customer-123/` 仍然只返回某一个 actor 的事实。代价是没有任何单一子树能表示「我们所知道的关于 customer-123 的一切」，而且按用户划分的 IAM 策略需要为每种记忆类型各写一条语句。只有当跨 actor 检索是主要访问模式时，才采用这种布局。

### Summary：按会话划分作用域

Summary memory 会为一段对话生成持续更新的叙述，这样你只需检索一份精简摘要，而不必把完整历史塞进模型的上下文窗口。由于摘要隶属于某一次对话，因此需要包含会话 ID：

```
/actor/{actorId}/session/{sessionId}/summary/
```

每个会话都有自己的摘要，并按 actor 组织，因此你仍然可以跨会话检索摘要。把两种策略放在一起，一个记忆资源的结构如下：

```
Memory Resource: CustomerSupportMemory
│
├── /actor/customer-123/
│   ├── facts/
│   │   ├── "Company has 500 employees across Seattle, Austin, Boston"
│   │   └── "Currently migrating from on-premises to cloud"
│   ├── preferences/
│   │   └── "Prefers email communication over phone"
│   ├── session/session-001/summary/
│   │   └── "Inquired about enterprise pricing, requested follow-up demo"
│   └── session/session-002/summary/
│       └── "Confirmed Q3 timeline, discussed CRM integration"
│
└── /actor/customer-456/
    ├── facts/
    │   └── "Startup with 20 employees, serverless architecture"
    └── preferences/
        └── "Prefers concise, high-level summaries"
```

### Episodic：按会话划分作用域并带层级化反思

Episodic memory 会捕捉完整的推理轨迹：目标、采取的步骤、结果以及反思。一个 episode 记录的是一次交互中发生的事，例如某个机票预订 agent 如何处理票价等级限制并为客户重新预订，因此 episode 的作用域限定在会话。reflection 则是跨 episode 的洞察，例如「当票价等级限制阻止修改时，应搜索其他航班，而不只是解释政策」。reflection 的命名空间必须是 episode 命名空间的前缀：也就是同一条路径去掉末尾一个或多个层级。

```
Episodes:    /actor/{actorId}/session/{sessionId}/episodes/
Reflections: /actor/{actorId}/
```

这里的 reflection 是跨某个 actor 的全部 episode 生成的。如果把 reflection 的命名空间缩减为 `/`，它就会横跨所有 actor，这意味着从某位客户交互中得出的洞察，在其他每位客户的上下文中都能被检索到。只有在 episode 中不包含任何客户特有信息时，才这样做。

## 检索记忆

当你需要与某个查询在语义上相关的记忆时，使用 `RetrieveMemoryRecords`。这是 agent 交互过程中的主要检索方式。

```
agentcore_client = boto3.client("bedrock-agentcore")

memories = agentcore_client.retrieve_memory_records(
    memoryId="CustomerSupportMemory-8f3k2j9d1a",
    namespace="/actor/customer-123/facts/",
    searchCriteria={
        "searchQuery": "What cloud migration approach is the customer using?",
        "topK": 5
    }
)
```

当用户的问题能自然对应到已存储的记忆时（例如「我的预算是多少？」），可以直接把它作为搜索查询传入。对于更模糊的输入，例如「帮我规划下一次旅行」，则让 agent 的大型语言模型（LLM）拟定一个更有针对性的查询，比如「旅行偏好、目的地历史、预算限制」。这会在检索之前增加一次模型调用，从而带来额外延迟。

当你需要枚举某个命名空间下的全部内容时，使用 `ListMemoryRecords`，例如向用户展示其已存储的偏好，或审计现有内容。`GetMemoryRecord` 和 `DeleteMemoryRecord` 针对单条记录 ID 操作，支持用户查看、更正或删除特定记忆的管理工作流。

### namespace 与 namespacePath 的对比

`RetrieveMemoryRecords` 和 `ListMemoryRecords` 都接受两个看起来可以互换、实际行为却大不相同的范围限定字段。

![对比精确匹配的 namespace 字段与层级匹配的 namespacePath 字段的示意图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/22/REVBLOG-1294-2-1.png)

图 2：namespace 字段只匹配一条精确路径，而 namespacePath 会返回整棵子树

`namespace` 字段执行**精确匹配**，只返回存储在该精确路径下的记录。前面那个例子只会返回 `/actor/customer-123/facts/` 中的记录，别无其他。当你需要精确限定范围时使用它，例如只要用户的偏好，而不要其事实或摘要。

`namespacePath` 字段执行**层级匹配**，返回命名空间位于该路径之下的所有记录：

```
# Returns records from facts/, preferences/, and session/*/summary/
records = agentcore_client.retrieve_memory_records(
    memoryId="CustomerSupportMemory-8f3k2j9d1a",
    namespacePath="/actor/customer-123/",
    searchCriteria={"searchQuery": "cloud migration", "topK": 5}
)
```

可以用它实现「展示我们所知道的关于这位客户的一切」这类功能。由于它会返回路径下的全部内容，你选择的起始层级就是你所信任调用方的层级。模板和 `namespacePath` 值中务必同时包含开头和结尾的斜杠。如果没有结尾斜杠，`/actor/customer-1` 还会匹配 `/actor/customer-12/`，从而返回其他用户的记录。

|  | **场景** | **API** | **字段** | **示例** |
| --- | --- | --- | --- | --- |
| 1 | 检索语义相关的用户偏好 | `RetrieveMemoryRecords` | `namespace` | `/actor/customer-123/preferences/` |
| 2 | 检索某次特定会话的摘要 | `ListMemoryRecords` | `namespace` | `/actor/customer-123/session/session-001/summary/` |
| 3 | 列出某用户的全部偏好 | `ListMemoryRecords` | `namespace` | `/actor/customer-123/preferences/` |
| 4 | 搜索某用户的全部记忆 | `RetrieveMemoryRecords` | `namespacePath` | `/actor/customer-123/` |
| 5 | 列出某用户跨会话的摘要 | `ListMemoryRecords` | `namespacePath` | `/actor/customer-123/session/` |

## 用于多租户层级的自定义命名空间变量

到目前为止，我们都是按 actor 和会话进行隔离，这正是面向消费者的 AI 助手所需要的。多租户和企业级应用通常至少还需要一个边界。

以独立软件供应商 AnyCompany DevTools 为例，它向大型企业销售工程支持 agent。每个客户都是一个租户。在一个租户内部，该 agent 支持许多服务，每项服务又有各自的组件和团队，工程师们会与 agent 开启会话。关于 Octank 支付账本中连接池死锁的记忆，绝不能出现在另一个租户面前，大概也不应该出现在 Octank 内部一个无关团队的面前。

内置变量没有一个能表达「租户」或「团队」。两种变通做法都站不住脚。把租户硬编码进模板（`/tenant/octank/actor/{actorId}/facts/`）意味着每个客户都要新建一套策略或记忆资源。把 `octank:payments:dev-123` 这样的复合键塞进 `actorId`，会破坏该工程师的跨会话合并，也会让按用户身份限定范围的 IAM 策略对不上。

自定义命名空间变量正好补上这一缺口。你通过 `namespaceKeys` 在记忆资源上声明变量名，在模板中与内置变量一起引用它们，并在运行时为每个事件提供具体值。一个记忆资源和一组策略就能服务所有租户。

![多租户命名空间层级示意图，包含 tenant、service、component、team、actor 和 session 各层级](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/22/REVBLOG-1294-3.png)

图 3：多租户命名空间层级依次嵌套 tenant、service、component、team、actor 和 session 各层级

### 定义命名空间键

在自定义层级之下，前面针对每种策略的指导依然适用。事实仍按 actor 划分作用域，摘要则追加会话层级：

```
response = control_client.create_memory(
    name="EngineeringSupportMemory",
    description="Memory for the engineering support agent",
    eventExpiryDuration=30,
    memoryStrategies=[
        {
            "semanticMemoryStrategy": {
                "name": "engineering-facts",
                "namespaceTemplates": ["/tenant/{tenant}/service/{service}/component/{component}/team/{team}/actor/{actorId}/facts/"]
            }
        },
        {
            "summaryMemoryStrategy": {
                "name": "session-summaries",
                "namespaceTemplates": ["/tenant/{tenant}/service/{service}/component/{component}/team/{team}/actor/{actorId}/session/{sessionId}/summary/"]
            }
        }
    ],
    namespaceKeys=[
        {"key": "tenant", "validation": {"regexPattern": "^[a-z][a-z0-9-]*$"}},
        {"key": "service", "validation": {"allowedValues": ["payments", "checkout", "search"]}},
        {"key": "component"},
        {"key": "team", "validation": {"regexPattern": "^[a-z][a-z0-9-]*$"}}
    ]
)
```

每个记忆资源最多可定义 5 个命名空间键，每个模板中最多可引用 5 个。键名最长 32 个小写字母数字字符，且不能重用内置变量名。值为小写，最长 64 个字符。`allowedValues` 最多接受 10 个值，适合环境或固定服务列表这类封闭集合。对于随客户数量增长的租户名单，可使用 `regexPattern`（最长 64 个字符），并用 IAM 强制校验真实的租户身份。同时指定两种规则时，两者都会生效。键并不一定需要被某个策略引用，同一个键也可以出现在多个模板中。

即使校验看起来有些多余，也要设置。这些值是在请求时由应用代码传入的，而租户隔离的 bug 恰恰出自这里：重试路径中的一个陈旧变量、指向错误环境的配置项。未通过校验的值会被 `CreateEvent` 拒绝，于是你能立刻发现问题，而不是几周后才发现一个游离的命名空间。注意：如果 namespaceKey 上配置了多个校验规则，所有校验都会强制执行；只要其中一个失败，整个请求就会失败。

### 在运行时提供变量值

在每次 `CreateEvent` 调用中，通过 `extractionConfig.namespaceVariables` 传入这些值：

```
agentcore_client.create_event(
    memoryId="EngineeringSupportMemory-abc325j329f",
    actorId="dev-123",
    sessionId="debug-1",
    payload=[{
        "conversational": {
            "role": "USER",
            "content": {"text": "Our connection pool deadlocks under high concurrency. Where do I start?"}
        }
    }],
    extractionConfig={
        "namespaceVariables": {
            "tenant": "octank",
            "service": "payments",
            "component": "ledger",
            "team": "core-ledger"
        }
    }
)
```

在提取过程中，服务会把这些值代入所有引用它们的模板，从而生成位于以下命名空间下的记忆：

```
/tenant/octank/service/payments/component/ledger/team/core-ledger/actor/dev-123/facts/
/tenant/octank/service/payments/component/ledger/team/core-ledger/actor/dev-123/session/debug-1/summary/
```

横跨多个租户时，单个记忆资源看起来像这样：

```
Memory Resource: EngineeringSupportMemory-abc325j329f
│
└── /tenant/
  ├── octank/
  │   └── service/payments/
  │       ├── component/ledger/team/core-ledger/
  │       │   ├── actor/dev-123/
  │       │   │   ├── facts/
  │       │   │   │   └── "Connection pool mutex deadlocks under high concurrency"
  │       │   │   └── session/debug-1/summary/
  │       │   │       └── "Investigated ledger deadlock, traced to lock ordering"
  │       │   └── actor/dev-456/facts/
  │       │       └── "Batch writes throttle at peak load"
  │       └── component/settlement/team/reconciliation/
  │           └── actor/dev-789/facts/
  │               └── "Cross-region replication lag spikes during failover"
  │
  └── examplecorp/
      └── service/search/component/relevance/team/ranking/
          └── actor/ml-eng-42/facts/
              └── "Embedding model v3 degrades recall on long-tail queries"
```

自定义变量只影响写入路径。当你读回记忆时，命名空间已经完全解析完毕，因此 `namespace` 和 `namespacePath` 的工作方式与之前完全一致，不需要新增任何参数。

### 层级的排列顺序

各层级的顺序是最关键的设计决策。每一次 `namespacePath` 查询都会从你指定的层级向下遍历，因此最宽泛的隔离边界应当放在最顶层。把 tenant 放在最前，那么跨 payments 服务所学全部内容的搜索，从结构上就会被限制在同一个租户之内：

```
records = agentcore_client.retrieve_memory_records(
    memoryId="EngineeringSupportMemory-abc325j329f",
    namespacePath="/tenant/octank/service/payments/",
    searchCriteria={"searchQuery": "deadlocks under load", "topK": 10}
)
```

把这两个层级调换顺序，同样的查询形式就会触及你的整个客户群。基于前缀的 IAM 策略继承了这一特性，这也是为什么 tenant 优先的层级更容易加固。

你增加的每一层级，都是每个事件都必须提供的一个值，而且会让检索变得碎片化：位于两个不同 component 下的记忆分属两棵子树，只有服务层级的 `namespacePath` 查询才能把它们重新汇聚起来。只有在确实会按某一层级查询或隔离时，才添加该层级。

### 缺失值与键的更新

缺失自定义变量与变量值无效的表现不同。如果模板引用了 `CreateEvent` 请求未提供的变量，命名空间就无法解析，该策略的长期提取会被跳过。`CreateEvent` 调用本身仍然成功，事件也会持久化到短期记忆中，因此对话照常进行，只是背后不再积累任何长期记忆。请监控 `NamespaceResolutionFailure` 指标（该指标带有 `Operation`、`Resource`、`StrategyType` 和 `StrategyId` 维度），并为其配置告警。这是发现某个客户端在重构后悄悄停止发送某个变量的直接办法。

`UpdateMemory` 中的 `namespaceKeys` 值会替换现有键集合，而不是与之合并，因此要把它当作一次读-改-写操作：先调用 `GetMemory`，把新键追加到返回的列表中，再将完整列表传回。如果遗漏了某个模板仍在引用的键，就会抛出 `ValidationException`。要停用某个键，先从模板中移除它，再从 `namespaceKeys` 中移除。

### 自定义命名空间变量与元数据的对比

AgentCore memory 还支持[结构化元数据](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/long-term-memory-metadata.html)，它会从事件传递到提取出的记录。两项功能回答的是不同的问题。命名空间变量定义的是**记忆存放在哪里**：它们设定检索和 IAM 所依据的边界，而每条记录只属于一个命名空间。元数据描述的则是在你已经划定的边界之内**记忆是关于什么的**，让你能够按类别、优先级或风险等级缩小检索范围。忘记应用的过滤器会返回全部内容，因此元数据并不适合用来做租户隔离。如果弄错了会构成安全问题，那就应该放在命名空间里；如果弄错了只是得到不相关的搜索结果，那就应该放在元数据里。

## 编写 IAM 策略以控制命名空间访问

命名空间通过条件键与 IAM 集成，这些条件键可以限制主体在 Memory API 请求中能够包含哪些命名空间。

### 精确匹配与层级匹配的读取策略

将 `StringEquals` 与 `bedrock-agentcore:namespace` 配合使用，可以把主体限制在单个命名空间内。下面的策略使用了在身份验证时注入的 `userId` 主体标签，因此每个用户只能读取自己的偏好：

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "bedrock-agentcore:RetrieveMemoryRecords",
        "bedrock-agentcore:ListMemoryRecords"
      ],
      "Resource": "arn:aws:bedrock-agentcore:us-east-1:123456789012:memory/CustomerSupportMemory-8f3k2j9d1a",
      "Condition": {
        "StringEquals": {
          "bedrock-agentcore:namespace": "/actor/${aws:PrincipalTag/userId}/preferences/"
        }
      }
    }
  ]
}
```

对于层级访问，将 `StringLike` 与 `bedrock-agentcore:namespacePath` 配合使用。把前面的条件替换为以下内容，用户就可以搜索自己所有的命名空间（事实、偏好、摘要），同时有助于防止访问其他用户的数据：

```
"Condition": {
  "StringLike": {
    "bedrock-agentcore:namespacePath": "/actor/${aws:PrincipalTag/userId}/*"
  }
}
```

### 针对自定义命名空间变量的写入路径策略

读取路径的条件键作用于已经完全解析好的命名空间。自定义变量则引入了一条同样值得加固的写入路径：`CreateEvent` 请求中的值决定了记忆落入哪个命名空间，而校验规则无法告诉系统调用方*应该*属于哪个租户。

`bedrock-agentcore:namespaceVariable/<variableName>` 条件键用于匹配某个自定义变量所提供的值。为每个租户的角色打上租户名称标签，一条策略就能把每个调用方锁定在其自己的子树上：

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "WriteOnlyToOwnTenant",
      "Effect": "Allow",
      "Action": "bedrock-agentcore:CreateEvent",
      "Resource": "arn:aws:bedrock-agentcore:us-east-1:123456789012:memory/EngineeringSupportMemory-abc325j329f",
      "Condition": {
        "StringEquals": {
          "bedrock-agentcore:namespaceVariable/tenant": "${aws:PrincipalTag/tenant}"
        }
      }
    }
  ]
}
```

一个配置错误或已被攻破的 Octank 客户端，可以在 `namespaceVariables` 中发送任意内容。除非 `tenant` 与其自身主体的标签一致，否则写入会被拒绝。有一种行为需要提前设计应对：如果请求省略了某条策略所依赖的变量，该条件键就不会出现在请求上下文中，`Allow` 无法匹配，除非另一条语句授予权限，否则请求将被拒绝。这使得该变量对策略覆盖的所有调用方都成为必填项，因此在上线策略之前，请确保客户端已经设置了它。

## 结论

命名空间设计决定了你的 agent 能检索到什么、哪些内容会被合并在一起，以及一个调用方能看到另一方的哪些数据。在第一个事件写入之前做出这些决策，要比在错误的层级下积累了一整年的记忆之后再来做容易得多。

- **从访问模式出发进行设计。** 决定谁检索什么、细化到哪个层级，以及哪些边界绝不能跨越。把最宽泛的隔离边界放在最顶层。
- **按策略划分作用域。** 事实和偏好归属于 actor，以便跨会话合并；摘要和 episode 归属于会话。
- **慎重选择检索字段。** `namespace` 只匹配一条精确路径。`namespacePath` 返回整棵子树。保留开头和结尾的斜杠，避免前缀相互碰撞。
- **当隔离边界不是 actor 或会话时，使用自定义命名空间变量。** 用 `allowedValues` 或 `regexPattern` 约束取值，并为 `NamespaceResolutionFailure` 配置告警。
- **用 IAM 条件键强制实施边界：** 读取时使用 `bedrock-agentcore:namespace` 和 `bedrock-agentcore:namespacePath`，写入时使用 `bedrock-agentcore:namespaceVariable/<key>`。
