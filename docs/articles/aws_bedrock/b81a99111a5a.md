# 全新的 AgentCore runtime：弹性、优化，且启动始终快速

agent 不再是实验品。它们处理理赔、编写与审查代码、跨系统协同，并在无人监督的情况下连续运行数小时。随着 agent 承担更复杂、运行更久的工作，支撑它们的底层基础设施也必须以同样快的速度演进。

我们构建 Amazon Bedrock AgentCore，是为了帮助开发者在安全的前提下大规模构建、连接和优化 agent。AgentCore runtime 是 Amazon Bedrock AgentCore 的一项能力，它是托管计算层，为开发者提供完全托管的环境，让他们无需构建或维护基础设施，就能部署和运行 agent。

自发布以来，已有数千个团队用它运行生产环境的 agent。与这些团队的每一次交流，都让我们更了解 agent 下一步需要什么：随工作负载扩展而提升的响应速度、对资源分配更精细的控制，以及精确跟踪实际用量的成本模型。

今天，我们宣布推出全新的 AgentCore runtime，它专为生产级 agent 所要求的速度、灵活性和成本效率而打造。

它带来更好的内存管理：在会话释放内存时即刻回收，而不是一直把内存占在峰值水平。它还能在容器大小或 agent 并发度不同的情况下，提供一致的冷启动时间。你依然拥有此前青睐的 serverless 模式，只是现在更有弹性。会话一结束，内存立刻归还；无论镜像大小或并发度如何，启动时间都保持一致；账单则只跟随 agent 实际完成的工作。

# 从对话到工作负载

许多 agent 最初是聊天机器人：你提问，它回答，交流在几秒内结束。随后出现了编码 agent，它们工作几分钟到几小时，在多个步骤之间保持上下文，你盯着看或走开时都在运行。如今 agent 正在变得无处不在、始终在线：由事件触发、无人值守地运行，只在任务完成或遇到需要人来做的决定时才现身。而且它们的数量多得多：不再是什么新鲜玩意，而是运行在各处。它们嵌入在产品里，藏在日常功能背后，并且越来越多地由其他 agent 启动。

第一版 AgentCore runtime 为这一整个谱系的 agent 打下了坚实基础：serverless、会话隔离、缩容到零，以及只为实际用量付费。今天发布的新 runtime 把这一基础扩展到整个谱系：对交互式 agent 保持快速一致，对长时间运行、更自主的 agent 保持持久且成本可负担。

# AgentCore runtime 提供什么

使用 AgentCore runtime，你可以专注于 agent 本身，而不必操心它底下所需的那套可扩展基础设施。有两点让这成为可能，也正是客户选择它的原因：

- 你只为实际消耗付费，而不必为等待 I/O 的空闲 CPU 买单。计费跟随资源使用量，因此不存在为你「以防万一」而预留的容量支付的固定费用。
- 平台可以一路缩容到零。当 agent 没有在处理工作时，什么都不会运行，也就没有费用。当工作到来时，平台会为你提供所需的容量。

两者结合，让大量 agent 在大部分时间处于空闲的成本很低，甚至让持续繁忙的单个 agent 运行起来也不贵。消耗模型会顺应工作负载，而不是强迫工作负载去顺应它。

当 agent 从简短的问答式会话转向无处不在、始终在线的工作时，同一套模型会遇到两个挑战。

**内存是昂贵的，而今天你要为峰值付费。** 会话从分配内存的那一刻起就一直占着它，直到会话结束，因为中途没有任何机制回收它。当已分配的内存确实会被用于服务后续请求、从而省去重新获取的延迟时，这样做是合理的。然而，一个长时间运行或流量突发的 agent，会在整个运行期间一直为它的最高点付费——即便它早已不再使用那块内存。对于一个偶尔出现峰值、但一天中大部分时间都空闲的 agent 来说，这就是「全天候为峰值付费」与「为真实用量付费」之间的差距。

**启动时间参差不齐。** 每个新会话都必须先启动才能做任何工作，因此快速、可预测的启动是良好体验的核心。当一个人正在等待一个因等待输入而暂停、需要恢复的 agent 时，这一点尤其重要。问题在于这些会话所依赖的硬件强制隔离：一个落在已初始化环境上的会话可以在 100 毫秒内启动，但要让环境保持足够「热」以保证这一点，就意味着要预留算力。因此大多数会话都是从冷启动开始：启动一个全新环境、拉取镜像、初始化 agent，然后第一个请求才能运行。这一延迟代价会随镜像大小和并发度增长，在突发流量下最糟——而那恰恰是大多数会话涌来、可用就绪环境最少的时刻。用户等待时感受到的，正是这种不一致。

**变通方案很笨重。** 为了应对这两个挑战，客户常常自己搭建一整套机制：预留备用环境让请求避开冷启动、优化内存分配，再为了控制账单把它们全部拆掉。提前备好容量对任何人来说都既昂贵又复杂：无论算力是否在工作，都要把它占住；而一旦突发流量超出预留量，这套机制依然会失效。这些都是没有差异化的繁琐工作，没有一项属于 agent 本身。

# 新 AgentCore runtime 的优势

增强后的 AgentCore runtime 为你解决了这两个挑战，首先是把内存消耗降到与实际用量挂钩的水平。新 runtime 现在让每个会话都从一个小而高效的内存配置启动，而不是完整的预留占用。随着工作负载需要，额外内存会按需分配并换入。基于对数十亿次会话分配模式的分析，我们调整了新 runtime，使其在内存变冷、不太可能再被访问时将其回收。它不再把这块内存一直占到会话结束。在原来的 runtime 中，即使已分配的内存不再被后续请求使用，它也仍然保持占用，因此用量跟踪的是最高水位。在新 runtime 中，被释放或变冷的内存会被回收，账单则跟随会话生命周期内的这些变化。

图 1：原 runtime 与新 runtime 的会话内存使用对比

更快、更一致的冷启动，直接得益于启动时更小的配置。增强后的 runtime 会把环境准备一次、做快照，然后为每个新实例恢复该快照。由于快照始终很小且一致，启动也就保持一致——无论镜像多大、并发多高。平台不再在每次冷启动时重复启动与初始化的流程，而是恢复一个已经就绪的环境。现在，runtime 能在很窄、可预测的区间内提供一致的启动时间。

**我们测了什么。** 为了单独衡量平台本身在冷启动上增加的开销，我们测试了一个空的 echo agent：它只原样返回输入，不调用任何模型和工具。计时反映的是 runtime 的启动路径，而不是任何应用逻辑。位于 us-west-2 的一台 Amazon Elastic Compute Cloud（Amazon EC2）实例上的 Python 客户端，使用 `boto3` SDK 通过公网调用 us-east-1 的 agent，未建立虚拟私有云（VPC）对等连接。这些都是客户端侧的数字，因此每一个都包含两个 AWS 区域之间的往返时间，再叠加平台自身的启动时间。在默认账户配额内，我们对两个版本、五种镜像大小各发送了每个 agent 5,000 次冷调用。

按这种方式测量，新 runtime 的 P75 冷启动延迟从 200 MB 镜像一直到 2 GB 都约为 2 秒，因为镜像大小对它没有影响。相比之下，原 runtime 的延迟会随镜像大小上升，从大约 5.4 秒升到接近 30 秒。

为了正确看待这一延迟，有必要把冷启动延迟与用户实际等待的时间区分开。启动时间是指从开始到获得一个就绪环境、你的 agent 代码得以处理第一个请求所花的时间，它不是 agent 工作的时间。在生产级 agent 中，用户感受到的大部分实际耗时来自 agent 循环及其模型调用，每次调用往往就要几秒。在我们的 echo 测试里，agent 自身代码在 P75 下只运行了约 34 毫秒，因此这里几乎全部时间都是平台启动时间。新 runtime 让启动时间中属于平台的那部分变得快速且可预测，而当有人在等待一个交互式 agent 时，这一点最为重要。

**给交互式 agent 的实用建议。** 你几乎可以完全把启动时间藏起来：在用户一开始接触时就开启会话，例如在他们打开聊天窗口时、甚至在他们在输入框中打字之前，而不是等他们提交。会话在他们被问候、输入第一个请求的过程中就已经预热，因此等他们发出那条消息时，环境已经就绪。

# 新 runtime 如何工作

新一代 runtime 重塑了会话使用内存的方式、agent 加载的方式，以及你付费的内容。

- **按需换入内存，并在内存被释放时回收。** 新 runtime 不再在分配之后一直占住会话的峰值内存，而是用更小的常驻占用支撑会话，并在工作负载访问到时换入更多内存。当你的 agent 通过释放每次请求的缓冲区、让缓存数据在请求之间过期等方式把内存交还时，平台会把它收回，而不是让它一直被占用到会话结束。
- **只加载一次 agent，然后做快照。** 当你创建或更新新 runtime 的实例时，AgentCore 会启动你的容器并等待其上报健康，然后对运行中的环境做快照。到那时，你的一次性初始化已经执行完毕，因此加载模型产物、获取静态配置这类工作都已固化进快照。之后每个新实例都通过恢复该快照来启动，而不是从头初始化。昂贵的启动工作只需付出一次，每个实例都能立即继承。
- **让快照保持小且大小稳定。** 对一个运行中进程做朴素快照，会抓到远多于恢复实例所需的内容，包括缓存和临时内存，它们会撑大快照，使恢复时间随镜像大小增长。新 runtime 会剥掉这些多余部分，让快照只保留实例恢复所需的工作状态，而不是完整的常驻占用。结果是：随着容器镜像增大，快照大小大致保持平稳，而正是这一点让恢复延迟在很宽的镜像大小范围内保持稳定。
- **单价更高，账单更低。** 新 runtime 按你的 agent 实际使用的内存计费——按需加载、空闲时回收——而不是为整个会话期间一直把整个容器镜像留在内存里付费。你支付的单价更高，但 GB-小时数少得多；对大多数 agent 来说，占用的下降幅度大于单价的上升幅度，因此账单反而更低。

# 后续计划（即将推出）

除了今天发布的内容，还有多项能力正在路上，让你在定价、算力、兼容性和控制力上有更多选择。

**承诺基线折扣。** 今天的按量计费模式会保留，它很适合有突发峰值和缩容到零的工作负载。与之并行，新 runtime 将增加基线定价选项：你为会话预留一个内存下限，需要时可超出该下限突发。基线定价适合稳定、始终活跃、希望成本可预测的 agent 会话，而按量计费则继续提供更强的弹性。

**更大的算力与存储。** 通过更多 RAM、vCPU 和会话存储扩展你的 agent 环境。

**x86 支持。** 用 x86 microVM 运行你已有的 agent、工具或环境。代码或依赖面向 x86 的团队，可以把 agent、工具或执行环境原样迁移到 AgentCore。

**更强的生命周期控制。** 借助内存快照挂起和恢复会话。挂接到 runtime 钩子，在活跃会话终止前把状态序列化，从而让会话可以无限期恢复。

**为无人值守 agent 提供作用域化身份。** 无人值守的 agent 提出了一个聊天轮次从未提出的问题：在无人看着它行动时，这个 agent 被允许做什么？会话上下文密钥将为每个会话提供各自的作用域化身份，因此无人值守的 agent、工具或环境只会以明确为其定义的权限行事，不多一分。

# 开始使用

要开始使用新 runtime，请在创建或更新 runtime 时把 `platformVersion` 参数设置为 `V2`。有关使用 runtime 的更多细节，请参阅 [AgentCore Developer Guide](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html#runtime-platform-versions)。

你可以在 [AgentCore GitHub samples 仓库](https://github.com/awslabs/agentcore-samples/tree/main/01-features/02-host-your-agent/01-runtime/01-hosting-agents/01-http-protocol)中找到示例。一个[配套的负载测试示例](https://github.com/awslabs/agentcore-samples/tree/main/01-features/02-host-your-agent/01-runtime/05-measure-your-runtime)展示了如何在你自己的 AWS 账户中验证新 runtime 一致的冷启动延迟。
