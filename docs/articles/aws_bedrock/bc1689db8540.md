# 了解 Amazon Health Services 如何借助 AWS ML 与生成式 AI 改进 Amazon 搜索中的发现体验

电商域中的医疗健康发现（healthcare discovery）会带来传统商品搜索在设计上从未处理过的独特挑战。与搜索图书或电子产品不同，医疗健康查询涉及症状、疾病、治疗与医疗服务之间的复杂关系，需要对医学术语与顾客意图有深入的理解。

随着 Amazon 从传统电商扩展到全面的医疗健康服务，这一挑战对我们变得尤为切身相关。Amazon 现在通过 [Amazon Pharmacy](https://pharmacy.amazon.com/) 提供处方药的直接获取途径，通过 [One Medical](https://health.amazon.com/prime) 提供初级医疗照护，并通过 [Health Benefits Connector](https://health.amazon.com/health-condition-programs) 提供专科医疗的合作渠道。这些医疗健康服务与传统的 Amazon.com 商品有显著差别，既带来令人振奋的机遇，也带来独特的技术挑战。

在本文中，我们展示 [Amazon Health Services](https://health.amazon.com/)（AHS）如何利用 [Amazon SageMaker](https://aws.amazon.com/sagemaker/)、[Amazon Bedrock](https://aws.amazon.com/bedrock/) 与 [Amazon EMR](https://aws.amazon.com/emr/) 等 AWS 服务，解决 Amazon.com 搜索中的可发现性挑战。通过结合[机器学习](https://aws.amazon.com/ai/machine-learning/)（ML）、自然语言处理与向量搜索能力，我们提升了把顾客与相关医疗健康服务连接起来的能力。该解决方案如今每天都在处理与健康相关的搜索查询，帮助顾客找到从处方药到初级医疗照护服务的各类内容。

在 AHS，我们的使命是改变人们获取医疗健康服务的方式。我们致力于让顾客更容易找到、选择、负担并参与到他们保持健康所需的医疗服务、产品与专业人士之中。

## 挑战

把医疗健康服务整合进 Amazon 的电商业务，为改善顾客在医疗健康旅程中的搜索体验带来了两个独特的着力点：理解查询中的健康搜索意图，以及把顾客的查询意图与最相关的医疗健康产品和服务匹配起来。

理解健康搜索意图的难点在于症状（如背痛或咽喉痛）、疾病（如椎间盘突出或普通感冒）、治疗（如物理疗法或药物）与 Amazon 提供的医疗服务之间的关系。这需要精细的查询理解能力，能够解析医学术语，并把它映射到医疗领域之外的外行顾客可能使用的常见搜索用语。

AHS 的各项服务在搜索匹配方面也带来独特挑战。例如，搜索“back pain treatment”的顾客可能在寻找各种解决方案：从 [Tylenol](https://www.amazon.com/Tylenol-Arthritis-Extended-Release-Reliever/dp/B0077VYSYY) 这类非处方止痛药，到 [cyclobenzaprine](https://pharmacy.amazon.com/Cyclobenzaprine-Generic-Flexeril-Oral-Tablet/dp/B084BWZF8T)（一种肌肉松弛剂）这类处方药，再到预约医生或使用虚拟物理治疗。针对实体商品优化的既有搜索算法可能无法匹配这些以服务为基础的医疗产品，从而可能漏掉相关结果，例如 One Medical 的初级医疗[服务](https://health.amazon.com/prime?ie=UTF8&keywords=doctor&ASIN=B0CZYRCB2B)，或 [Hinge Health 的虚拟物理治疗项目](https://health.amazon.com/health-condition-programs/dp/B0DLJ5PQ5K)——后者通过个性化锻炼与专属治疗师的一对一支持来帮助减轻关节与肌肉疼痛。医疗健康服务的这种独特性，要求我们开发专门的方法来把顾客与相关服务连接起来。

## 解决方案概述

为应对这些挑战，我们开发了一套综合解决方案，把用于查询理解的 ML、用于商品匹配的向量搜索，以及用于相关性优化的[大语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）结合起来。该解决方案由三个主要部分组成：

- **查询理解 pipeline** – 使用 ML 模型识别并分类与健康相关的搜索，区分具体的药物查询与更宽泛的健康状况搜索
- **商品知识库** – 把既有的商品元数据与 LLM 增强的健康信息相结合，为语义搜索创建全面的商品嵌入
- **相关性优化** – 采用混合方法，同时使用人工标注与基于 LLM 的分类，在搜索与医疗健康服务之间生成高质量匹配

该解决方案完全构建在 AWS 服务之上：Amazon SageMaker 驱动我们的 ML 模型，Amazon Bedrock 提供 LLM 能力，Amazon EMR 与 [Amazon Athena](https://aws.amazon.com/athena/) 负责满足我们的数据处理需求。

## 解决方案架构

现在我们来看架构的技术实现细节，探讨每个组件是如何被设计以应对 Amazon.com 上医疗健康搜索的独特挑战的。

### 查询理解：识别健康类搜索

我们从顾客搜索旅程两端的显著差异入手。一端是我们所称的“鱼叉式查询”（spearfishing queries），即漏斗下层的搜索：顾客有明确的产品搜索意图，并对商品属性有具体了解。对 Amazon Health Services 而言，这类搜索通常包括查找特定处方药并带有精确剂量与剂型，例如“atorvastatin 40 mg”或“lisinopril 20 mg”。

另一端是宽泛的漏斗上层查询：顾客寻求灵感、信息或推荐，产品搜索意图较为笼统，可能涵盖多种商品类型。此类搜索的例子包括“back pain relief”、“acne”或“high blood pressure”。在 Amazon 搜索能力的基础上，我们开发了额外的查询理解模型，以覆盖医疗健康搜索的完整光谱。

为了识别鱼叉式搜索意图，我们分析了 Amazon 商品的匿名化顾客搜索互动数据，并训练了一个分类模型，用来判断哪些搜索关键词只导向与 Amazon Pharmacy 的 Amazon Standard Identification Numbers（ASIN）的互动。该过程使用 Amazon EMR 上的 PySpark 与 Athena，大规模收集并处理 Amazon 搜索数据。下图展示了这一架构。

为了识别宽泛的健康搜索意图，我们训练了一个命名实体识别（NER）模型，在医学术语层面标注搜索关键词。为构建这一能力，我们使用了一组健康本体（health ontology）数据源语料，用于识别健康状况、疾病、治疗、损伤与药物等概念。对于知识库中缺少足够同义表述的健康概念，我们使用 LLM 来扩充知识库。例如，疾病“acid reflux”的替代表述可能是“heart burn”、“GERD”、“indigestion”等。我们把该 NER 模型置于由 [Amazon 搜索查询到商品类型模型](https://arxiv.org/abs/2408.02215)预测出的健康相关商品类型之后，作为门控条件。下图展示了 NER 模型的训练过程。

### 构建商品知识

在具备识别健康相关搜索的能力之后，我们需要为医疗健康产品与服务构建全面的知识库。我们从既有服务出发，收集了所有可获得的、最能描述各项产品或服务的商品知识信息。

为强化这一基础，我们使用了一个[大语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM），配合精心调优的 prompt 与 few-shot 示例，为每个产品或服务叠加相关的健康状况、症状与治疗相关关键词。我们借助 Amazon Bedrock 的[批量推理](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference.html)能力完成这一工作。这一做法意味着我们用医学相关信息大幅扩展了商品知识。

随后，整个知识库使用 [Facebook AI Similarity Search](https://github.com/facebookresearch/faiss)（FAISS）转换为嵌入，我们还创建了索引文件以实现高效的相似度搜索。我们仔细维护了从每个嵌入回到原始知识库条目的映射，确保在需要时能够进行准确的反向查找。

该过程使用了多项 AWS 服务，包括用 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）存储知识库与嵌入文件。需要注意的是，[Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 也是实现向量数据库能力的可行选项。大规模的知识库嵌入作业通过按计划运行的 SageMaker [Notebook Jobs](https://docs.aws.amazon.com/sagemaker/latest/dg/notebook-auto-run.html) 执行。通过组合这些技术，我们构建了医疗健康商品知识的坚实基础，能够被高效搜索并与顾客查询匹配。

### 把健康搜索意图映射到最相关的产品与服务

我们解决方案的核心组件是实现[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）设计模式。该模式的第一步是确定一组已知关键词与 Amazon 商品，为我们的解决方案建立初始的 ground truth。

在基于 Amazon 目录元数据与 ASIN 属性构建好商品知识库之后，我们就准备好支持顾客的新查询了。当顾客的搜索查询到来时，我们将其转换为嵌入，并用它作为搜索键在我们的索引中进行匹配。这一相似度搜索使用 FAISS，匹配判定依据相似度得分的阈值。

为验证为健康搜索关键词识别出的这些查询-商品对的质量，我们需要维护每一对的相关性。为此，我们采用了两条并行的相关性标注路径。我们使用一套既定的方案，把每项服务标记为与关键词的关系是 exact（完全匹配）、substitute（替代）、complement（补充）还是 irrelevant（不相关）。这套方案被称为 exact、substitute、complement、irrelevant（ESCI）框架，源自学术研究。更多信息请参阅 [ESCI challenge](https://www.aicrowd.com/challenges/esci-challenge-for-improving-product-search) 与 [esci-data](https://github.com/amazon-science/esci-data?tab=readme-ov-file) GitHub 仓库。

首先，我们与人工标注团队合作，在相当大的样本规模上建立 ground truth，并基于该方案为系统性能创建了可靠的基准。我们向标注团队提供了基于 ESCI 框架、并针对 AHS 产品与服务定制的指导。

其次，我们使用 Amazon Bedrock 与批处理作业实现了基于 LLM 的标注。在上一步找到匹配之后，我们检索出排名靠前的商品，并把它们作为生成式模型的 prompt 上下文。我们在 prompt 中加入了 ESCI 指导的 few-shot 示例。通过这种方式，我们对排名靠前的健康搜索进行了大规模推理，利用相似度搜索把它们与最相关的服务连接起来。我们对被判定为与 AHS 相关的查询-商品对大规模执行了这一过程，并把输出存储在 Amazon S3 中。

通过混合使用高置信度的人工标注与基于 LLM 的标注，我们建立了真实的 ground truth。借助这一过程，我们仅利用聚合搜索关键词与商品元数据中的语义数据，就成功为顾客识别出了相关的产品与服务。

## 这如何帮助了顾客？

我们的使命是让人们更容易找到、选择、负担并参与到他们保持健康所需的医疗服务、产品与专业人士之中。如今，在 Amazon 上搜索健康解决方案的顾客——无论是针对痤疮、链球菌性咽喉炎与发热等急性病症，还是关节炎、高血压与糖尿病等慢性疾病——都将开始看到经过医学审核的相关服务，与 [Amazon.com](http://Amazon.com) 上其他相关的产品和服务并列呈现。

顾客现在可以在熟悉的体验中快速找到并选择与医生会诊、获取处方药以及使用其他医疗健康服务。通过把 Amazon 强大的电商搜索能力延伸到医疗健康领域的特定需求，我们为相关健康服务创造了更多发现路径。

我们利用对健康查询的语义理解与全面的商品知识建立连接，帮助顾客在合适的时机找到合适的医疗健康解决方案。

## 关键要点

回顾我们在 Amazon 上改进医疗健康发现的历程，有几点关键洞察值得强调，或许对正在应对类似挑战的人有价值：

- **使用领域特定本体** – 我们从深入理解顾客的健康搜索入手，具体弄清了顾客在寻找哪些疾病、症状与治疗。通过使用既有的健康本体数据集，我们丰富了 NER 模型，使其能够在搜索查询中检测这些实体，为更好的匹配打下基础。
- **基于商品知识的相似度搜索** – 我们利用既有的商品知识，加上 LLM 增强的真实世界知识，构建了一个可以映射到我们所提供服务的综合数据语料。通过这一方法，我们在顾客查询与相关医疗健康解决方案之间建立了语义连接，而不依赖单个顾客的数据。
- [**生成式 AI**](https://aws.amazon.com/generative-ai/)**远不止聊天机器人** – 在整个项目中，我们依赖了多项对成功至关重要的 AWS 服务。Amazon SageMaker 为我们的 ML 模型提供了基础设施。然而，使用 Amazon Bedrock 批量推理是关键差异所在。它为我们提供了强大的 LLM 用于知识增强与相关性标注，而 Amazon S3 与 Amazon EMR 等服务则支撑了我们的数据存储与处理需求。若以人工方式扩展到同等规模，所需预算将高出好几个数量级。请把生成式 AI 应用视为一种规模化能力，而不仅仅是聊天助手。

通过组合这些方法，我们为顾客创造了更直观、更有效的方式来发现 Amazon 上的医疗健康服务。

## 实施考量

如果你打算为医疗健康或搜索场景实施类似的解决方案，请考虑以下几点：

- **安全与合规**：确保你的解决方案遵循 [Health Insurance Portability and Accountability Act](https://aws.amazon.com/compliance/hipaa-compliance/)（HIPAA）等医疗健康数据隐私法规。我们的方法不使用单个顾客的数据。
- **成本优化**：批处理作业使用 [Amazon EMR on EC2 Spot Instances](https://aws.amazon.com/ec2/spot/use-case/emr/)；为高频搜索的查询实现缓存；为你的工作负载选择合适的实例类型
- **可扩展性**：设计你的向量搜索基础设施以应对峰值流量；为推理端点使用自动扩缩容；实现完善的监控与告警
- **维护**：定期更新健康本体数据集；监控模型性能并按需重新训练；保持商品知识库的时效性

## 结论

在本文中，我们展示了 Amazon Health Services 如何利用 AWS 的 ML 与生成式 AI 服务，解决 Amazon.com 上医疗健康发现的独特挑战，并说明了如何用 Amazon SageMaker、Amazon Bedrock 与 Amazon EMR 构建精细的领域特定搜索体验。我们展示了如何创建查询理解 pipeline 来识别与健康相关的搜索、构建由 LLM 能力增强的全面商品知识库，以及使用向量搜索与 ESCI 相关性框架实现语义匹配，从而把顾客与相关的医疗健康服务连接起来。

这一可扩展的、基于 AWS 的方法展示了 ML 与生成式 AI 如何改变专门的搜索体验，并推进我们的使命：让顾客更轻松地找到、选择、负担并参与医疗健康服务。我们鼓励你探索这些 AWS 服务如何应对你自己医疗健康或专门搜索应用中的类似挑战。关于在 AWS 上实施医疗健康解决方案的更多信息，请访问 [AWS for Healthcare & Life Sciences](https://aws.amazon.com/health/) 页面。
