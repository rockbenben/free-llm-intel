# 基于托管式 Amazon Bedrock 知识库，用 AWS CloudFormation 构建可观测的企业级 agentic retrieval

为某个基础模型（foundation model）加入检索增强生成（Retrieval Augmented Generation，RAG）的团队，通常都从一个知识库上的单次检索起步。这在问题变难之前一直有效——一旦答案横跨多个来源，或者系统必须先决定去查哪个来源才能作答，这种做法就不够用了。

企业级 agentic retrieval 解决了这个问题：agent 对问题做推理，把它路由到正确的知识库，迭代地检索，并返回带引用的答案。但它也带来了一个更棘手的运维问题。一旦 agent 在循环中推理与检索，你就不再看得清它到底做了什么、答案是否足够好。

此前的一篇文章[使用 Amazon Bedrock Knowledge Bases 与 AWS CloudFormation 构建端到端 RAG 方案](https://aws.amazon.com/blogs/machine-learning/build-an-end-to-end-rag-solution-using-knowledge-bases-for-amazon-bedrock-and-aws-cloudformation/)，用自管理（向量存储）知识库自动化了单次 RAG 工作流。随着托管式知识库（managed knowledge base）的推出，Amazon Bedrock Knowledge Bases 已从 RAG 演进到 agentic retrieval。托管式知识库的 agentic retrieval 会进行多轮规划、执行检索工具，并生成有依据、带引用的答案。

本文再往前一步：给出一个企业级 agentic retrieval 方案，agent 在其中推理、跨多个知识库检索，并综合作出带引用的答案。它构建在 Amazon Bedrock 托管式知识库与 Amazon Bedrock AgentCore 之上，从一开始就把可观测性与评估内置进来。你可以用一条 AWS CloudFormation 链完成全部部署。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/28/architecture_v2-Page-1.png)

图 1：端到端架构——从 Amazon S3 中的合成语料出发，经过两个托管式知识库、AgentCore Gateway（Amazon Bedrock AgentCore 的一项能力）与运行时 agent，最终到七层可观测性与评估，全部由 AWS CloudFormation 部署

架构图中的编号步骤对应本方案的工作流，具体如下：

- 用户把问题发送给托管在 [Amazon Bedrock AgentCore 运行时](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime.html)上的 agent。运行时会用 OpenTelemetry span 自动为每一步插桩，因此从第一次调用起，这个「推理—行动」循环就是可观测的。
- agent 的推理模型规划任务并执行跨知识库路由：每个知识库各暴露一个检索工具，模型会选择主题与问题相匹配的那个工具（金融或天气）。
- 选中的工具调用由 [Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)通过 Model Context Protocol（MCP）代理转发，由它在托管式知识库上调用该知识库的 `AgenticRetrieveStream` API。
- `AgenticRetrieveStream` 负责知识库内部的工作：把问题分解成子查询，从托管数据存储（由 [Amazon Simple Storage Service（Amazon S3）](https://docs.aws.amazon.com/s3/)中的语料灌入）中迭代检索，并综合出有依据、带引用的答案，经 Gateway 流式返回给 agent。
- agent 检查返回的上下文是否充分。若不充分，它会在下一轮循环中再次检索，然后再组织最终答案；若充分，就把带引用的答案返回给用户。
- 整个过程里，运行时把 span、token 用量与指标发送到 [Amazon CloudWatch](https://docs.aws.amazon.com/cloudwatch/)与 AWS X-Ray，填充七层可观测性数据，并为按需评估与持续评估提供分数输入。

## 一、背景

在动手演练之前，先明确三件事会很有帮助：是什么让 RAG 变成 agentic，为什么托管式知识库是它合适的基础，以及为什么可观测性与评估应该属于设计的一部分，而不是事后补装。

### 从 RAG 到企业级 agentic retrieval

经典 RAG 做一次检索、一次生成。企业级 agentic retrieval 则把推理 agent 放进循环里：它决定是否需要检索、检索什么，可以多次检索以逐步细化，选择相关的知识库（语义路由），然后才组织出有依据、带引用的答案。这正是 Amazon Bedrock 托管式知识库现在通过其 `AgenticRetrieveStream` API 作为一等能力提供的东西。检索不再是单次查找，而是由 agent 驱动的多步过程。这能在复杂问题上产出更好的答案，但也让系统更难运维——这正是本文从一开始就把可观测性与评估内置进来的原因。

### 托管式与自建知识库的对比

Amazon Bedrock 现在提供托管式知识库（`Type: MANAGED`）：由 Amazon Bedrock 代管摄取、存储、索引与检索，默认使用服务托管模型完成 embedding 与重排序，因此你不需要再预置、扩缩或修补向量数据库。

下表展示了 Amazon Bedrock 托管式与客户自管理知识库的区别：

| 能力 | **Bedrock 托管式** | **客户自管理（DIY）** |
| --- | --- | --- |
| **Agentic retrieval**（AgenticRetrieveStream） | ✅ 支持 | ❌ 不支持 |
| **AgentCore Gateway 集成** | ✅ 支持 | ❌ 不支持 |
| 数据存储 | 自动扩缩，完全由 Amazon Bedrock 托管 | 由你预置、扩缩与维护 |
| Embedding + 重排序 | 内置托管模型（你可以选择 Amazon Bedrock 上可用的其他模型） | 由你配置 |
| 需要管理的基础设施 | **无** | 向量数据库及更多 |

### 为什么需要可观测性与评估

一个只会「返回答案」的 agentic 系统不足以支撑生产。你需要看到它的行为表现（延迟、调用量、token 用量），看到检索与答案的质量，而且需要持续获得这些信号。本方案附带两个 CloudWatch 仪表板，覆盖七层遥测数据，外加两种评估形式（按需与持续），全部由同一套模板预置。

## 二、方案概览

该方案以四个原生 [AWS CloudFormation](https://docs.aws.amazon.com/cloudformation/) 堆栈部署，每个堆栈的输出都接入下一个。

- `01-knowledge-bases` 创建一个 [Amazon Simple Storage Service](https://docs.aws.amazon.com/s3/)（Amazon S3）存储桶、两个托管式知识库（分别存放金融与天气语料，好让 agent 有可路由的对象）、它们的数据源与 IAM，以及一个摄取自定义资源，用于上传文档并执行首次同步。
- `02-agentic-gateway` 创建一个 [Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)（`AWS_IAM` 鉴权、MCP），并为每个知识库配置基于原生 `bedrock-knowledge-bases` 连接器的目标，这样每个知识库都对外暴露自己的 `AgenticRetrieveStream` 工具，无需 [AWS Lambda](https://docs.aws.amazon.com/lambda/) 函数或额外容器。
- `03-agent-runtime` 预置一个 Amazon Elastic Container Registry（Amazon ECR）仓库，以及一个用 AWS CodeBuild 构建已插桩 OpenTelemetry 的 Strands agent 镜像的项目；还预置托管该镜像的 [Amazon Bedrock AgentCore 运行时](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime.html)、日志与 trace 的投递配置，以及在线评估配置。
- `04-dashboards` 创建那两个 [Amazon CloudWatch](https://docs.aws.amazon.com/cloudwatch/) 仪表板。

路由发生在两个层面，值得把它们区分开。跨知识库的路由由 agent 的推理模型完成：每个知识库一个检索工具，再加上一条要求挑选与问题主题相匹配的工具的系统提示词（system prompt），由它决定该查哪个知识库。随后 `AgenticRetrieveStream` API 负责知识库内部的工作，把问题分解为子查询、迭代检索，并综合出带引用的答案。因此 agent 跑的是一个「推理—行动」循环：它调用大语言模型（LLM），决定调用哪个知识库工具，读取经 Gateway 返回的内容，往往还会再次检索，然后才组织出最终带引用的答案。每一步都由运行时自动插桩，所以七层可观测性数据都来自真实流量。

这七层各自回答一个不同的运维问题，合起来端到端地覆盖整个 agent。第 1、4、5 层是自动发出的，第 3、6、7 层则由 driver notebook 以自定义指标的形式发布。

| **层级** | **它捕获什么** | **它回答的运维问题** |
| --- | --- | --- |
| L1 — KB 原生指标 | 每个 KB 的检索调用次数、错误、限流 | 每个知识库是否健康、是否在承载流量？ |
| L2 — 摄取 | 摄取任务状态与逐文档结果 | 我的文档是否成功进入知识库？ |
| L3 — Agentic retrieval 质量 | 无参考利用率、有据覆盖率、重复率 | agent 检索到的上下文是否相关、是否有充分依据？ |
| L4 — Gateway / MCP 指标 | Gateway 工具调用量与延迟 | 检索工具层是否快速可靠？ |
| L5 — OTEL span 树 | agent 完整的「推理—行动」span 轨迹 | agent 究竟一步步做了什么？ |
| L6 — Token 用量 | 按会话与模型统计的 `gen_ai.usage` token | 每次查询花掉多少 token？ |
| L7 — 评估分数 | 正确性、忠实性、工具选择、回答相关性 | 答案是否真的足够好？ |

### 为什么选这些服务

本方案中的每一项选择，都源于「可运维的企业级 agentic retrieval」这一目标。托管式知识库是基础，因为 agentic retrieval 与 AgentCore Gateway 连接器只在它上面可用；它还免去了你原本要预置、扩缩和修补的向量数据库。AgentCore Gateway 把每个知识库的 `AgenticRetrieveStream` 暴露为 MCP 工具，于是 agent 对每个知识库各拿到一个工具，且无需维护 Lambda 或额外容器。AgentCore 运行时托管 agent 并自动发出 OpenTelemetry span，这才让第 5 至第 7 层无需额外接线即可实现。CloudFormation 把这一切串成一条可复现的链，因此整个系统（包括仪表板与持续评估）每次都能以同样的方式起来。

## 三、数据集说明

本方案自带两个小型合成语料，打包在仓库的 `data/` 目录下：

- **金融：** 一份合成的 Octank Financial 10-K 年报（`octank_financial_10K.pdf`，约 198 KB）。
- **天气：** 一份真实、公开可得的美国国会研究服务局（U.S. Congressional Research Service）关于龙卷风的报告（[IF12695](https://sgp.fas.org/crs/misc/IF12695.pdf)，`tornadoes_report.pdf`，约 560 KB）。

这两份语料刻意保持彼此不同，好让 agent 必须把每个问题路由到正确的知识库——这就是语义路由的故事。我们刻意使用两个独立的知识库，而不是一个知识库挂两个数据源。每个知识库都作为独立的检索工具暴露，因此 agent 必须在两者之间做出真实的路由决策；仪表板上所有按知识库区分的信号（索引大小、检索质量、token 用量与评估分数，均以 `KnowledgeBaseId` 为键）也能保持清晰可分离。

如果只用一个知识库挂两个数据源，agent 就只有一个工具，既没有路由可演示，按语料区分的信号也会被合并在一起。由于这些是托管式知识库，我们不配置分块（chunking）、embedding 或索引。摄取时，Amazon Bedrock 会解析每个 PDF、对其分块、用其托管模型生成 embedding，并自动建立索引。

## 四、部署方案

部署本方案只需一条命令，但了解这条命令需要什么、产出什么会很有帮助。本节介绍前置条件、单个部署脚本，以及如何确认每个堆栈都已起来。

### 前置条件

- 一个 AWS 账户，并具备以下服务的权限：[Amazon Bedrock](https://docs.aws.amazon.com/bedrock/)、[Amazon Bedrock AgentCore 运行时](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime.html)与 [Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)、[AWS Identity and Access Management（IAM）](https://docs.aws.amazon.com/iam/)、[Amazon CloudWatch](https://docs.aws.amazon.com/cloudwatch/)、[AWS X-Ray](https://docs.aws.amazon.com/xray/)、[Amazon ECR](https://docs.aws.amazon.com/ecr/)、[AWS CodeBuild](https://docs.aws.amazon.com/codebuild/)、[Amazon Simple Storage Service（Amazon S3）](https://docs.aws.amazon.com/s3/)、[AWS Lambda](https://docs.aws.amazon.com/lambda/)与 [AWS CloudFormation](https://docs.aws.amazon.com/cloudformation/)。此外还需要为 agent 所用模型开通 [Amazon Bedrock 模型访问权限](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)。
- 该账户中可用 agent 所用的模型（默认为 `us.anthropic.claude-haiku-4-5-20251001-v1:0`）。参见 [Amazon Bedrock 支持的基础模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)。
- 已启用 **CloudWatch Transaction Search**，这样 OpenTelemetry span 会落到 `aws/spans`，供第 5–7 层使用。参见 [CloudWatch Transaction Search](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Transaction-Search.html)。
- AWS Command Line Interface（AWS CLI）v2。运行 notebook 需要 Python 3.13 与 `boto3>=1.43`。本地不需要 Docker（agent 镜像由 CodeBuild 构建）。参见[安装 AWS CLI](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html)与 [Boto3 文档](https://boto3.amazonaws.com/v1/documentation/api/latest/index.html)。

## 七、评估：按需与持续

质量以两种方式衡量，二者都由堆栈预置。

**按需评估。** driver notebook 会针对每个会话的 span 调用 AgentCore Evaluate（LLM-as-judge），使用内置评估器（正确性、忠实性、工具选择准确性），并把分数发布到 CloudWatch，在仪表板 A 上作为第 7 层呈现。

**⚠️ 采样与成本。** 本方案把 `SamplingPercentage: 100` *纯粹是为了这篇博客的实验*，好让每个会话都被打分、结果立即可见。**这不是生产环境的推荐做法。** 在线评估会对每个被采样的会话调用一次 LLM-as-judge，因此成本**随采样率和流量规模增长**。真实部署时，请选择符合你质量监控需求与预算的采样百分比，并在启用前**让配置与贵组织自身的策略和成本治理要求保持一致**。该比例是 `templates/03-agent-runtime.yaml` 中的单个属性（`OnlineEvaluationConfig.Rule.SamplingConfig.SamplingPercentage`）。

**何时用哪种。** 按需评估适合开发与发布前检查：当你想按需了解质量时，可以对选定的一组会话刻意跑一次，而且只在运行时才付费。持续（在线）评估适合生产监控：它对线上流量采样并自动打分，这样质量回退无需任何人手工触发任务就会浮现，代价是成本随采样率增长。常见做法是迭代期间依赖按需评估，等 agent 开始服务真实用户后，再以适度的采样百分比启用持续评估。

## 九、结论

我们在托管式 Amazon Bedrock 知识库与 AgentCore 之上构建了一套完整的 agentic retrieval 方案（多知识库语义路由、推理 agent、七层可观测性，以及按需与持续两种评估），并用一条 AWS CloudFormation 链把全部内容部署起来。使用托管式知识库彻底去掉了向量存储基础设施，同时带来了 agentic retrieval 与 AgentCore Gateway 连接器——这些是客户自管理知识库所不具备的。

这一模式适合「正确答案分散在多个地方、系统必须自己选择去哪里找」的工作负载。例子包括：在产品文档知识库与计费知识库之间路由的客服助手；横跨彼此独立的监管语料与科学语料的研究助手；以及把 HR、IT 与财务内容放在相互隔离的知识库中、以实现访问与成本分离的内部服务台。在这些场景里，agent 跨知识库路由，agentic retrieval 在单个知识库内完成多步工作，而七层数据则显示它运行得如何、成本多少。

接下来，你可以把数据源指向自己的语料，把 agent 放进虚拟私有云（VPC），按预算与策略调整在线评估的采样率，或者给路由器增加更多知识库。模板、driver notebook 与自包含的工具都在配套仓库里。
