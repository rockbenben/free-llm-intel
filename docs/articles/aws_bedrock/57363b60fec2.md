## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# Octave 如何在 Amazon Bedrock 上构建安全的多租户 AI 基础

在受监管行业的质量管理中，解决问题的机构记忆几乎总是被埋藏在客户历史的某个地方。去年调查了类似的缺陷，纠正和预防措施（CAPA）解决了根本原因，审计结果也标记了相同的差距。这些知识存在于数十亿份文档中，人类无法通过跨语言和格式的语义相似性进行搜索，因此每项调查都从头开始。 Octave Reliance 帮助每个组织跨多个系统收集文档，以帮助他们更轻松地搜索并跟踪他们拥有的一切。 [Octave](https://www.octave.com/en) Reliance 团队将解锁这段历史视为帮助客户更快工作并保持合规性的最大机会。障碍同样明显：投诉记录、审计结果和纠正措施具有平台最严格的隔离要求，而这些正是人工智能需要读取的记录。在一个为医疗设备、制药和食品制造领域超过 14,000 名客户提供服务的平台中，一个客户向另一个客户无意中泄露信息所带来的监管后果将远远超过人工智能带来的任何好处。

Octave 的业务遍及 180 个国家/地区，为超过 [60% 的全球财富 500 强企业](https://www.octave.com/newsroom/press-releases/2026/octave-intelligence-plc-listed-on-nasdaq-new-york) 提供服务。其云原生质量管理系统 [Reliance](https://www.octave.com/products/asset-performance-management/reliance) 通过 40 多个应用程序支持 650 多家企业客户，涵盖从投诉管理和 CAPA 跟踪到审计管理和供应商质量的各个方面。每个人都会生成人工智能可以推理的受监管数据。每个客户都是一个单独的租户，任何数据都不能跨越租户边界。

面对这种情况，Reliance 团队做出了一个不同寻常的决定：它没有发布一个人工智能功能，而是在第一个周期中为未来的每个功能奠定了基础。此后，该基金会已将每个用例的部署时间缩短了 50%。如果您将人工智能引入软件即服务 (SaaS) 平台，其中数据很有价值，但隔离是不可协商的，那么推理就超出了质量管理的范围。在这篇文章中，我们将介绍塑造设计的四种张力以及使用 Cohere Embed v4 在 Amazon Bedrock 上构建的三层基础 Octave。然后，我们跟踪嵌入 20 亿份文档的管道以及在生产中证明了这一点的投诉分类助手。

## 为什么是基础，而不是功能

AWS 的设想研讨会提出了四个高影响力的用例：投诉总结和分类、审计准备情况监控、事件叙述生成和预测质量风险评分。他们还提出了在数十个应用程序之后塑造一切的洞察力，每个应用程序都有不同的文档类型和工作流程。在孤岛中为一个人构建人工智能意味着为下一个人重建基础设施。

因此，团队颠倒了计划：先构建水平平台，然后将垂直功能切片切入其中。首先进行投诉总结和分类，以证明架构，然后再进行其余的工作。

## 四种张力

在选择单个模型之前，团队花了很多时间解决四个不同方向的问题。没有一个可以被交易掉。

**在不存在无意泄露风险的情况下提供数据。** 投诉记录、CAPA、标准操作程序 (SOP) 和审计结果属于一个租户，其他租户必须无法访问。即使是错误的人工智能查询也无法跨越。矢量存储、检索逻辑和生成上下文都必须限定在单个租户范围内。

**隔离执行代理。** 管理代理工具、数据存储和模型端点的权限必须限定在请求用户而不是共享服务角色，仅在执行期间可用，并尊重该用户的访问权限。具有静态凭据的共享代理池未能满足所有三个要求。

**阅读不可信的内容。** 此处的代理从组织外部获取投诉、电子邮件附件、扫描的 PDF 和图像。 OWASP 大型语言模型 (LLM) 应用程序十大威胁 (2025) 列出了直接适用的威胁：通过摄取内容进行提示注入 (LLM01)、敏感信息泄露 (LLM02)、不正确的输出处理 (LLM05) 和过度代理 (LLM06)。所附 PDF 中的隐藏说明在本卷中并不是假设的。

**无需四分之一的等待即可嵌入 20 亿份文档。** Reliance 托管超过 20 亿份文档，各个租户存储数百万个 Word 文件、PDF、扫描表单、电子表格、图像和电子邮件。该团队致力于在一个工作日内为最大的租户提供服务。由于这些文件为监管决策提供信息，因此质量不能换取吞吐量。错过投诉会削弱对整个系统的信任。

## 架构落地的地方

同时保持四种张力大大缩小了选择范围。 Amazon Bedrock 将它们视为一个平台：通过单个 API 进行多模型访问、AWS 区域驻留和 AWS 账户已经强制实施的 AWS Identity and Access Management (IAM) 治理，以及 Guardrails 作为生产内容控制而不是构建的东西。

该基础分为三层，如图 1 所示。数据准备使用 [Amazon Bedrock 上的 Cohere Embed v4](https://aws.amazon.com/bedrock/cohere/) 嵌入高质量文档，并将它们写入 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 上的每租户向量存储。安全执行通过 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 传递用户请求，这是 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 的一项功能，它在将请求传递给调用 Amazon Bedrock 上的 Anthropic Claude 模型的隔离 microVM 会话之前应用身份验证和策略。将两者包装在一起，内容保护会应用 Amazon Bedrock Guardrails 两次：在进入时进行输入过滤，在任何内容到达处理程序之前进行输出过滤。检索、执行和筛选处于不同的阶段，因此每个阶段都可以单独执行和证明。

### 选择如何表示数据

在文件可检索之前，其他任何方法都不起作用。这意味着准确地跨语言和格式，而不是跨租户边界。该团队根据自己的语料库而不是公共排行榜评估嵌入模型。决定性的问题是针对这些数据的：破裂房屋的照片与描述它的段落有什么关系，以及德国的投诉与英国的 CAPA 有何关系。

Amazon Bedrock 上的 Cohere Embed v4 在五项方面获胜，而且它们并不是相互独立的。首先决定的是有多少管道是不必要的。质量记录包含缺陷产品的照片、扫描的检验表以及带注释的图表和文本。 Embed v4 将两种模态放置在一个向量空间中。破裂外壳的照片和描述该缺陷的段落可以通过单个查询检索，每种模式没有单独的管道。原生多语言支持沿着另一个轴执行相同的工作：文档以多种语言到达，通常位于一个租户的语料库中，并且不需要翻译预处理。团队从来不需要构建两条管道，并且减少了两个文档无法检索的位置。

剩下的三项计算确定了媒介可以生存的地方以及它们的成本。客户数据不能离开其 AWS 区域，即使是为了推理，因此 Amazon Bedrock 上的区域内模型可用性是一个先决条件，而不是一种便利。 Embed v4 支持美国东部（弗吉尼亚北部）区域 (us-east-1)、欧洲（爱尔兰）区域 (eu-west-1) 和亚太（东京）区域 (ap-northeast-1) 的区域内推理，涵盖了 Octave 的三个区域合规性要求。型号和功能可用性因地区而异，并随时间而变化。有关当前覆盖范围，请参阅 Amazon Bedrock 用户指南中的[按模型划分的区域可用性](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。在每个区域内，Amazon OpenSearch Service 成本随着维度计数呈线性增长。这使得 Embed v4 的可配置输出尺寸 256-1,536 值得测试，而不是默认接受。针对代表性生产查询的测试显示，512 个维度保持了目标准确性，同时与 1,536 个默认维度相比，存储空间减少了大约 66%。 128K 令牌上下文窗口在其他地方完全得到了回报：大约 4K 令牌的块将许多令牌打包到一个请求中，这就是加载吞吐量的来源。

### 在运行时保持租户分开

更困难的问题是在哪里强制执行租户分离。应用程序代码本来可以工作，但这意味着未来的每个功能团队都可以在每个代码路径上都正确执行，其中一个错过的检查可能会导致无意中的跨租户泄露。相反，团队将隔离推入运行时。 AgentCore 运行时是 Amazon Bedrock AgentCore 的一项功能，强制应用程序层以下的分离，并且由于它保持框架和模型独立，因此为投诉分类助手选择的代理框架和模型不受隔离决策的限制。

每个用户会话都在专用的 microVM 中运行，具有自己的 CPU、内存和文件系统，并在会话结束时停止并清理。这是硬件级的分离，旨在无论代理的行为如何。 AgentCore 在整个执行链中携带经过身份验证的用户身份：每用户 OAuth 令牌库验证代理针对特定用户而不是共享服务身份的行为，并且凭证的范围针对每个代理，并且仅在会话期间有效。 AgentCore Gateway 在工具、操作和参数级别进行授权。自动推理根据定义的规则提供形式验证。 IAM 和 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/pm/serv-s3/) 策略验证背后的规则相同。图 2 追踪了两个租户之间的分离情况。

![跨两个租户的 AgentCore 会话分离，每个 microVM 停止并在使用后清理其内存](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/31/ML-21094-2.png)

图 2：租户之间的 AgentCore 会话分离。每个 microVM 在使用后停止并清理内存。

因此，租户 A 的质量处理人员提交的投诉仅到达租户 A 的令牌库、工具和 AgentCore 代码解释器（Amazon Bedrock AgentCore 的一项功能）中的沙箱。租户 B 的会话没有通往其中任何一个的路径。

### 将摄取的内容视为不可信

这种紧张没有明确的答案。投诉附件是不受信任的输入，但也是代理要阅读的内容，因此无法拒绝可疑内容。球队选择了深度防守。

Octave 在投诉工作流程中的三个点将 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/) 应用到代理逻辑上而不是内部。 ApplyGuardrail API 在嵌入之前评估从附件中提取的文本，在进入代理上下文之前评估检索的文档和工具输出，以及在处理程序看到之前合成的摘要。附件派生内容通过输入标记传递，将其标记为数据而不是指令。这就是隐藏在文档中间的注入可以被检测到的原因。个人身份信息 (PII) 在进入时会被隐藏。

仅靠检测是不够的，所以有界机构位于下面。无论代理被要求做什么，AgentCore Gateway 仍然控制它可以调用哪些工具，并且文档提取在 AgentCore 代码解释器沙箱中运行，没有网络出口，也没有会话之外的持久性。隐藏在 PDF 中的有效负载必须击败每一层，而不是一层。

**效果：** 跟踪每个租户的检测率和屏蔽率，因此筛查发现的内容是 Octave 可以提供证据而不是断言的内容。

## 通过管道获取 20 亿份文档

在嵌入模型之前面临着更困难的问题：从 Word 文件、电子表格、数字 PDF、扫描页面、照片和电子邮件线程中提取可用内容。多种语言会出现，有时会出现在一份记录中。而且它必须运行得足够快，以至于入职需要一天而不是四分之一的时间。图 3 端到端地跟踪了生成的管道。

![提取管道：文档事件通过 Step Functions 编排流向每租户 OpenSearch 索引](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/31/ML-21094-3.png)

图 3：摄取管道：从应用程序平台通过 Step Functions 编排到每租户 OpenSearch 索引的事件驱动文档处理。

文档事件通过 Amazon Simple Notification Service (Amazon SNS) 和 Amazon Simple Queue Service (Amazon SQS) 扇出到 AWS Step Functions 状态机。该状态机协调专用 Amazon Virtual Private Cloud (Amazon VPC) 内并发 AWS Lambda 执行的解析、分块和嵌入。由于并行性来自于跨执行的扇形批次，而不是扩展一种资源，因此吞吐量无需重新架构即可增长。

解析处理异质性：从 Word 文件和电子表格中保留语义层次结构，应用于缺乏文本层的扫描 PDF 的光学字符识别 (OCR)，将嵌入图像视为一流内容。块携带元数据：租户、文档类型、源应用程序、语言和内容哈希。该元数据驱动检索过滤和每租户命名空间实施。

吞吐量来自包装。将许多 4K 块交织成针对 Embed v4 的 128K 上下文窗口的单个请求，可以将大型语料库的 API 调用减少大约一个数量级。在 Octave 对 Amazon Bedrock 的内部测试中，Embed v4 每分钟交付 2800 万个代币。在与 Cohere 的解决方案架构师一起调整批量大小直至内存瓶颈被清除后，管道每 24 小时为每个租户工作负载维持 140 万个文档。这就是单一工作日承诺成为现实的原因。

## 投诉分类助理

一家医院向医疗设备制造商报告有缺陷的注​​射器，记录会附上电子邮件、受损部件的照片以及所附的支持文件。质量处理人员必须将这些格式的上下文拼凑在一起，确定以前是否报告过类似的情况，并找到解决问题的方法。只有这样才能分配优先级，通常是在以天为单位的报告窗口内。

该助手是使用 AWS 开源的 Strands Agents SDK 构建的，它将代理工作流程组成为图形，节点作为工具调用或模型调用，边作为它们之间的数据依赖关系。 AgentCore 运行时运行该图表并在每个会话中隔离它，五个阶段包含从原始附件到完成的摘要的投诉。

文档提取是第一位的。 PDF、图像、电子邮件附件和视频都进入 AgentCore Code Interpreter，它将每个工件解析为结构化的中间表示。然后，Amazon Bedrock 上的 Claude 模型会对记录进行汇总，并且该汇总（而不是原始的数千个令牌源）将成为检索查询。检索针对租户的 Embed v4 嵌入的 OpenSearch 索引运行它，显示过去类似的投诉及其 CAPA，并使用 AgentCore Gateway 强制只有授权的命名空间才能访问。

仅凭相似性并不能信任返回的结果。单独的模型调用根据置信度对结果进行评分，并丢弃共享词汇但根本原因不同的匹配。剩下的内容将被综合，亚马逊 Bedrock 上的 Anthropic Claude Sonnet 会收集输出：关键事实、情绪、紧迫性指标、最接近的历史记录及其结果，以及推荐的分类优先级。

完成的摘要会缓存在 Amazon DynamoDB 中，并具有每个环境的生存时间 (TTL)，因此重复查看不会产生任何额外费用。处理程序不再从零开始，而是从机构记忆开始。

图 4 将该引擎置于私有 API 边界后面。门户请求通过私有 Amazon API Gateway 和 Lambda 函数到达 AgentCore 运行时，检索通过使用预签名 URL 的基于角色的访问来读取文档索引，而附件则保留在 Amazon S3 中。缓存的摘要和 OpenTelemetry 跟踪退出到摘要表和评估仪表板。

## 证明代理做了什么

这里的可观察性不仅是工程团队如何调试，还包括他们如何与系统审计功能集成以满足合规性要求。审计员可以询问为什么特定的投诉会按照原来的方式进行分类，而“模型决定”将无法在谈话中幸存下来。

AgentCore 跨图形的每个节点捕获与 OpenTelemetry 兼容的跟踪：每个模型调用、检索和 AgentCore 代码解释器运行。几个月后，Octave 可以显示哪些检索到的文档和提示生成了给定的摘要。 Amazon Bedrock 的模型调用日志记录添加了每个请求和响应的每个租户记录，范围通过 IAM 身份 AgentCore 传播，成本由 Amazon CloudWatch 中的发起租户承担。

离线时，AgentCore Evals 在对提示、模型或检索参数进行任何更改后，根据专家注释的基本事实重新运行工作流程，报告摘要可信度、K 的检索精度和输出完整性。读起来更好但检索效果更差的提示在用户看到之前就被捕获了。

## 结果

投诉分类助手已在生产环境中运行了三个月，以下数字反映了该期间的情况。

过去，处理者一无所获地展开调查，现在则在已收集到相关历史记录的情况下展开调查。每次调查 4-6 小时的 Octave 测量是管道吸收的工作：跨格式提取、寻找先例，以及从措辞巧合中找出真正相似的缺陷所需的阅读。

该基金会还改变了 Octave 的发布速度。根据其自己的统计，新人工智能功能的开发周期从几个月缩短到几周。共享数据准备、安全执行和检索是图 1 中的三个层。它们将每个用例的部署时间缩短了 50%，因为每个新功能都会继承它们而不是重建它们。这使得语义搜索在第二季度实现，比最初的第四季度目标提前了两个季度。

## 回顾过去

首先建立基金会的决定是团队事后猜测最多的决定。当利益相关者想要他们可以看到的人工智能功能时，数月的基础设施工作就很难捍卫。下一轮的用例已经证明了这一点。有两种选择可以实现这一目标：将隔离推入 microVM 会话和身份传播而不是应用程序代码中，以及根据 Octave 自己的语料库评估嵌入模型，从而呈现出基准测试无法显示的 512 维权衡。

该团队还划定了一条选择不跨越的界限。助理会展示背景和先例。质量处理人员仍然会打电话。在这个要求具有监管影响力的行业中，这个边界决定了哪些自动化，哪些没有自动化。
