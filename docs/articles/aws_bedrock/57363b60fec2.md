## [Artificial Intelligence](https://aws.amazon.com/blogs/machine-learning/)

# Octave 如何在 Amazon Bedrock 上构建安全的多租户 AI 基础

在受监管行业的质量管理里，真正能解决问题的机构记忆几乎总是埋在客户历史记录的某个角落：去年调查过的类似缺陷、修复了根因的纠正与预防措施（CAPA）、标记出同一处缺口的审计发现。这些知识存在于数十亿份文档之中，没有人能跨语言、跨格式地按语义相似度把它们检索出来，所以每一次调查都从零开始。Octave Reliance 帮助各组织把分散在多个系统中的文档汇集起来，让检索更容易，也让手里的东西都能被跟踪。[Octave](https://www.octave.com/en) Reliance 团队把“解锁这段历史”视为帮助客户更快工作、保持合规的最大单点机会。障碍同样清楚：投诉记录、审计发现和纠正措施承载着平台最严格的隔离要求，而这些恰恰是 AI 需要读取的记录。在一个服务医疗设备、制药和食品制造领域超过 14,000 家客户的平台里，任何一次从一个客户无意泄露到另一个客户，其监管后果都会远远超过 AI 带来的任何收益。

Octave 的业务覆盖 180 个国家，服务超过 [60% 的全球财富 500 强企业](https://www.octave.com/newsroom/press-releases/2026/octave-intelligence-plc-listed-on-nasdaq-new-york)。其云原生质量管理系统 [Reliance](https://www.octave.com/products/asset-performance-management/reliance) 以 40 多个应用支撑 650 多家企业客户，涵盖从投诉管理和 CAPA 跟踪到审计管理和供应商质量的各个环节。每一家都在产生 AI 可以推理的受监管数据。每个客户都是独立的租户，任何数据都不能跨越租户边界。

面对这样的局面，Reliance 团队做了一个不太寻常的决定：与其先交付一个 AI 功能，它把第一个周期用来搭建未来每个功能都会立在其上的基础。这套基础此后把每个用例的部署时间缩短了 50%。如果你正要把 AI 引入一个数据很有价值、但隔离不可妥协的软件即服务（SaaS）平台，这套推理并不局限于质量管理。本文将梳理塑造设计的四重张力，以及 Octave 用 Amazon Bedrock 上的 Cohere Embed v4 搭起的三层基础；随后我们会追踪那条嵌入了 20 亿份文档的流水线，以及在生产中验证了它的 Complaint Triage Assistant。

## 为什么先建基础，而不是先做功能

与 AWS 一起做的构想工作坊浮现出四个高影响力用例：投诉摘要与分诊、审计就绪度监控、事件叙述生成、预测性质量风险评分。它们同时带出一个影响后续一切的认识：这里有几十个应用，每个应用有着不同的文档类型和工作流。在一个孤岛里为其中一个应用做 AI，意味着下一个应用要把基础设施重搭一遍。

于是团队把计划倒过来：先建横向平台，再把纵向的功能切片切进去。投诉摘要与分诊排在第一位，用来在其余功能跟进之前验证架构。

## 四重张力

在选定任何一个模型之前，团队把时间花在四个彼此拉扯的问题上。哪一个都不能被交换掉。

**让数据可用，又不冒无意泄露的风险。** 投诉记录、CAPA、标准操作程序（SOP）和审计发现属于某一个租户，必须对另一个租户不可达。哪怕是一条写错的 AI 查询也不能越界。向量存储、检索逻辑和生成上下文都必须限定在单个租户之内。

**隔离地执行 agent。** 支配 agent 工具、数据存储和模型端点的权限必须限定到发起请求的用户，而不是一个共享的服务角色，只在执行期间可用，并且尊重该用户自身的访问权限。一个带静态凭证的共享 agent 池三条全都不满足。

**读取不可信的内容。** 这里的 agent 要接收来自组织外部的投诉、邮件附件、扫描 PDF 和图片。OWASP 大语言模型（LLM）应用十大风险（2025）点出了直接适用的几类威胁：通过被摄取内容实施的提示注入（LLM01）、敏感信息泄露（LLM02）、输出处理不当（LLM05）和过度代理（LLM06）。在这个体量下，附件 PDF 里藏着指令并不是假设。

**嵌入 20 亿份文档，而不用等上一个季度。** Reliance 托管着 20 多亿份文档，单个租户就存有数百万份 Word 文件、PDF、扫描表单、电子表格、图片和邮件。团队承诺在一个工作日内完成哪怕最大租户的接入。由于这些文档会影响监管决策，质量不能用吞吐量来换。漏掉一条投诉会侵蚀对整个系统的信任。

## 架构最终落在哪里

同时握住四重张力，把选项范围收得很窄。Amazon Bedrock 把它们当作一个平台来回应：通过单一 API 访问多个模型；AWS 账户本来就强制执行的 AWS Region 数据驻留与 [AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 治理；以及把 Guardrails 直接当作生产级内容控制，而不是需要自己造的东西。

这套基础分成三层，如图 1 所示。数据准备层用 [Amazon Bedrock 上的 Cohere Embed v4](https://aws.amazon.com/bedrock/cohere/) 嵌入质量文档，并把它们写入 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 上按租户划分的向量存储。安全执行层让用户请求先经过 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)（[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 的一项能力），由它施加身份认证和策略，再把请求交给一个隔离的 microVM 会话，该会话调用 Amazon Bedrock 上的 Anthropic Claude 模型。内容保护层包住前两者，把 Amazon Bedrock Guardrails 用两次：入口处做输入过滤，任何内容到达处理人之前做输出过滤。检索、执行和筛查各自处在独立的阶段，因此每一层都能被单独强制执行、单独举证。

### 选择如何表示数据

在文档变得可检索之前，别的都无从谈起。而“可检索”意味着准确，跨语言、跨格式，并且不越过租户边界。团队用自己的语料而不是公开榜单来评估嵌入模型。决定性的问题都针对这批数据：一张外壳开裂的照片和描述它的那段文字有什么关系，一份德文投诉和一份英文 CAPA 又有什么关系。

Amazon Bedrock 上的 Cohere Embed v4 在五个方面胜出，而这五点并不彼此独立。最先定下的是它让流水线里有多少环节变得不必要。质量记录在文字之外还带着缺陷产品照片、扫描的检验表单和带标注的示意图。Embed v4 把两种模态放进同一个向量空间。一张外壳开裂的照片和描述该缺陷的那段文字可以用同一条查询检索出来，不必为每种模态单独建一条流水线。原生多语言支持在另一个维度上做同样的事：文档以多种语言到达，而且常常出现在同一个租户的语料里，不需要任何翻译预处理。两条团队本来要建的流水线不用建了，文档掉出检索的地方也少了两处。

剩下三点决定了向量能放在哪里、要花多少钱。客户数据不能离开其所在的 AWS Region，即便只是为了推理，所以在 Amazon Bedrock 上的区域内模型可用性是前提条件，而不是便利项。Embed v4 支持在美国东部（弗吉尼亚北部）区域（us-east-1）、欧洲（爱尔兰）区域（eu-west-1）和亚太（东京）区域（ap-northeast-1）做区域内推理，覆盖了 Octave 三项区域合规要求。模型与功能的可用性因区域而异，并会随时间变化。要了解当前覆盖范围，请参阅 Amazon Bedrock 用户指南中的[按模型划分的区域可用性](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。在每个区域内部，Amazon OpenSearch Service 的成本随维度数线性增长。这让 Embed v4 可配置的 256–1,536 维输出值得实测，而不是照默认值接受。用有代表性的生产查询做测试后，512 维在保持目标准确率的同时，把存储相对 1,536 维的默认值削减了约 66%。128K token 的上下文窗口则在完全不同的地方兑现了价值：约 4K token 的分块可以把许多块塞进一次请求，接入吞吐量正来自这里。

### 在运行时把租户隔开

更棘手的问题是在哪里强制租户隔离。写在应用代码里也能奏效，但那样后面每个功能团队都要在每条代码路径上做对，只要漏掉一处检查，就有无意跨租户泄露的风险。团队把隔离推进到运行时。AgentCore runtime 是 Amazon Bedrock AgentCore 的一项能力，在应用层之下强制隔离；由于它保持框架与模型无关，为 Complaint Triage Assistant 选定的 agent 框架与模型不会被隔离决策绑死。

每个用户会话都跑在专用的 microVM 里，有自己的 CPU、内存和文件系统，会话结束时被停止并清洗。这是硬件级隔离，设计上不依赖 agent 的行为方式。AgentCore 在整条执行链上携带已认证用户的身份：按用户划分的 OAuth token 保险库验证 agent 是代这个具体用户行事，而不是一个共享的服务身份；凭证按 agent 划分作用域，并且只在会话期间存在。AgentCore Gateway 在工具、操作和参数级别做授权。自动推理针对既定规则提供形式化验证。IAM 和 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/pm/serv-s3/) 的策略校验背后是同一套纪律。图 2 追踪了这种隔离如何跨越两个租户。

![跨两个租户的 AgentCore 会话隔离，每个 microVM 在使用后停止并清洗内存](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/31/ML-21094-2.png)

图 2：租户之间的 AgentCore 会话隔离。每个 microVM 在使用后停止，内存被清洗。

因此，租户 A 的质量处理人提交的一条投诉，只会到达租户 A 的 token 保险库、工具以及 AgentCore Code Interpreter（Amazon Bedrock AgentCore 的一项能力）中的沙箱。租户 B 的会话没有通往其中任何一个的路径。

### 把被摄取的内容视为不可信

这重张力没有干净的答案。投诉附件是不可信输入，但它同时又是 agent 存在的意义所在——它要读的东西，所以不能把可疑内容直接拒掉。团队最终选择纵深防御。

Octave 把 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/) 加在 agent 逻辑之上而不是之内，位于投诉工作流的三个点上。ApplyGuardrail API 会评估嵌入之前从附件中抽取的文本、进入 agent 上下文之前的检索文档与工具输出，以及处理人看到之前合成的简报。来自附件的内容通过输入标记传递，被标记为数据而非指令。正因如此，埋在文档中部的注入才可能被检出。个人身份信息（PII）在入口处被遮蔽。

只有检测还不够，所以下面还垫着有界代理权。无论要求 agent 做什么，AgentCore Gateway 仍然管着它能调用哪些工具，而文档抽取跑在 AgentCore Code Interpreter 沙箱里，没有网络出口，也没有超出会话的持久化。藏在 PDF 里的载荷必须攻破每一层，而不是只攻破一层。

**效果：** 检测率和遮蔽率按租户跟踪，所以筛查抓到了什么，是 Octave 能举证的事情，而不是一句断言。

## 让 20 亿份文档走完流水线

嵌入模型之前是更难的问题：从 Word 文件、电子表格、数字 PDF、扫描页、照片和邮件线程中抽取可用内容。文中会出现多种语言，有时就在同一条记录里。而且它必须跑得足够快，让接入用一天而不是一个季度。图 3 端到端追踪了由此形成的流水线。

![摄取流水线：文档事件经 Step Functions 编排流向按租户划分的 OpenSearch 索引](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/31/ML-21094-3.png)

图 3：摄取流水线：从应用平台出发、由事件驱动的文档处理，经 Step Functions 编排写入按租户划分的 OpenSearch 索引。

文档事件通过 Amazon Simple Notification Service (Amazon SNS) 和 Amazon Simple Queue Service (Amazon SQS) 扇出到一个 AWS Step Functions 状态机。该状态机在专用 Amazon Virtual Private Cloud (Amazon VPC) 内的并发 AWS Lambda 执行之上协调解析、分块和嵌入。由于并行度来自把批次扇出到多个执行、而不是扩容单一资源，吞吐量无需重新架构就能增长。

解析负责处理异构性：从 Word 文件和电子表格中保留语义层级，对没有文本层的扫描 PDF 施加光学字符识别（OCR），把嵌入图片当作一等内容。分块携带元数据：租户、文档类型、来源应用、语言和一个内容哈希。这些元数据同时驱动检索过滤和按租户的命名空间强制。

吞吐量来自打包。把许多 4K 分块交织进针对 Embed v4 的 128K 上下文窗口的单次请求，把大语料所需的 API 调用削减了约一个数量级。在 Octave 于 Amazon Bedrock 上做的内部测试中，Embed v4 达到每分钟 2,800 万 token。在与 Cohere 的解决方案架构师一起调整批量大小、直到内存瓶颈消除之后，这条流水线按每个租户工作负载维持每 24 小时 140 万份文档。正是这一点让“一个工作日内完成”的承诺真正成立。

## Complaint Triage Assistant

一家医院向医疗器械制造商报告有缺陷的注射器，这条记录连同邮件、受损部件的照片和支持文档一起落进系统。质量处理人必须跨这些格式把上下文拼起来，弄清以前是否报告过类似情况，并找出当时是怎么解决的。只有做到这些才能定优先级，而报告窗口往往以天计。

这个助手用 AWS 开源的 Strands Agents SDK 构建，它把 agent 工作流组合成图：节点是工具调用或模型调用，边是它们之间的数据依赖。AgentCore runtime 运行这张图，并按会话隔离；五个阶段把一条投诉从原始附件带到成稿简报。

文档抽取排在第一位。PDF、图片、邮件附件和视频都进入 AgentCore Code Interpreter，由它把每个工件解析成结构化的中间表示。随后 Amazon Bedrock 上的 Claude 模型对记录做摘要，而这个摘要（而不是原始的数千 token 源文件）成为检索查询。检索拿它去查该租户由 Embed v4 嵌入构成的 OpenSearch 索引，浮现出相似的过往投诉及其 CAPA，同时由 AgentCore Gateway 强制只有被授权的命名空间可达。

返回的结果不能只凭相似度就相信。另一次模型调用按置信度为结果打分，丢弃那些词面重合但根因不同的匹配。存活下来的部分进入合成阶段，由 Amazon Bedrock 上的 Anthropic Claude Sonnet 组装输出：关键事实、情绪、紧迫性指标、最接近的历史记录及其结果，以及建议的分诊优先级。

完成的简报以按环境设置的存活时间（TTL）缓存在 Amazon DynamoDB 中，所以重复查看不再产生额外成本。处理人不再从零开始，而是从机构记忆开始。

图 4 把这台引擎放在一个私有 API 边界之后。门户请求经私有 Amazon API Gateway 和 Lambda 函数到达 AgentCore runtime，检索通过基于角色的访问加预签名 URL 读取文档索引，附件则留在 Amazon S3 中。缓存的摘要和 OpenTelemetry 追踪导出到摘要表和评估仪表板。

## 证明 agent 做了什么

这里的可观测性不只是工程团队怎么调试，也是他们如何对接系统审计能力以满足合规要求。审计员可以问：为什么这条投诉被这样分诊？“模型决定的”撑不过那场对话。

AgentCore 在图中的每一个节点上采集 OpenTelemetry 兼容的追踪：每一次模型调用、每一次检索、每一次 AgentCore Code Interpreter 运行。几个月后，Octave 能指出是哪些被检索的文档和提示词生成了某份简报。Amazon Bedrock 的模型调用日志补充了按租户的每一次请求与响应记录，作用域由 AgentCore 传播的 IAM 身份划定，成本在 Amazon CloudWatch 中归属到发起请求的租户。

在离线侧，只要提示词、模型或检索参数有任何变更，AgentCore Evals 就会针对专家标注的基准真值重跑工作流，报告摘要忠实度、K 处检索精确率和输出完整性。一个读起来更好但检索更差的提示词，会在用户看到它之前被抓住。

## 结果

Complaint Triage Assistant 已在生产中运行三个月，以下数字反映这一期间的情况。

过去处理人打开调查时手里什么都没有，现在打开时相关历史已经组装好了。Octave 测得的每次调查 4–6 小时，就是流水线吸收掉的工作：跨格式抽取、寻找先例，以及为了把真正相似的缺陷和措辞巧合区分开所需的阅读。

这套基础也改变了 Octave 的交付速度。按其自己的统计，新 AI 能力的开发周期从数月缩短到数周。共享的数据准备、安全执行和检索就是图 1 的三层。它们把每个用例的部署时间缩短 50%，因为每项新能力都继承它们，而不是重建它们。这让语义搜索在第二季度落地，比原定的第四季度目标提前两个季度。

## 回顾

先建基础这个决定，是团队事后质疑最多的一次。当利益相关方想要一个能看见的 AI 功能时，数月的基础设施工作很难辩护。下一轮用例证明了它值得。有两个选择撑住了它：把隔离推进到 microVM 会话和身份传播、而不是写在应用代码里；以及用 Octave 自己的语料评估嵌入模型——正是后者暴露出任何基准测试都不会显示的 512 维权衡。

团队还划了一条选择不越过的线。助手呈现上下文和先例，做判断的仍然是质量处理人。在一个该判断带有监管分量的行业里，这条边界决定了什么被自动化、什么没有。
