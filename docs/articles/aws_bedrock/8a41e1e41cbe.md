# Amazon SageMaker AI 上的多轮强化学习：实践指南

大多数微调都会教会模型对单个提示产生更好的答案。代理任务是不同的。提交费用报告或对支持票证进行分类的代理会采取一系列操作，每个步骤都取决于之前发生的操作。很少有一个正确的序列可以模仿，唯一可靠的反馈是整个序列是否成功。监督微调没有这方面的标签，单轮强化学习不能相信在结果之前三步做出的决定。

Amazon SageMaker AI 上的多轮强化学习 (MTRL) 正是根据该信号训练模型。 SageMaker AI 通过 [AWS Lambda 转发器](https://docs.aws.amazon.com/sagemaker/latest/dg/model-customize-mtrl-agent.html) 向您在 Amazon Bedrock AgentCore 或您自己的基础设施（例如 Amazon Elastic Kubernetes Service (Amazon EKS)、Amazon Elastic Compute Cloud (Amazon EC2) 或 AWS Fargate）上托管的代理发送提示。这里的示例使用 AgentCore。代理调用正在训练的策略模型，根据任务需要在您的环境中执行尽可能多的回合，并在情节结束时报告一项奖励。您无需指定正确的轨迹，只需指定如何对结果进行评分。

这篇文章以 [Wordle](https://en.wikipedia.org/wiki/Wordle) 为例，这是一款玩家有六次尝试猜测隐藏的五个字母单词的游戏。每次猜测后，如果每个字母位置正确，则它会变成绿色；如果它在单词中但位置不同，则变成黄色；如果不在单词中，则变成灰色。这款游戏适合MTRL，因为规则很少，每次猜测都取决于上次的反馈，并且结果是客观评分的。 Wordle 是一个教学示例，前沿模型已经很好地发挥了作用。在实践中，您可以使用 MTRL 制作一个小型、低成本模型，擅长执行特定于您的业务的多步骤任务，例如公共模型从未接受过训练的内部工作流程。相同的管道适用于该设置。

在我们的运行中，MTRL 将 gpt-oss-20b 在其默认推理努力下对保留单词的解决率从 61% 提高到 84%，在低努力训练时将其解决率从 15% 提高到 69%，训练代币约为 339 美元。在这篇文章中，我们将端到端地介绍整个管道：将代理和奖励部署到 AgentCore、准备数据集、训练、在 MLflow 中进行监控以及在服务设置中进行评估。我们还分享了我们遇到的奖励设计错误和培训失败。您的数据集、代理和经过训练的模型保留在您的 AWS 账户中，[不用于训练基本模型](https://aws.amazon.com/sagemaker/ai/jumpstart/)。所有代码都位于随附的 [aws-samples 存储库](https://github.com/aws-samples/sample-multi-turn-rl-wordle)中。

## 解决方案概述

该系统有两半。 SageMaker AI 拥有训练作业和策略模型。 AgentCore 托管代理、Wordle 环境和奖励函数。下图显示了它们的连接方式。

![连接到 AgentCore 托管代理、Wordle 环境和奖励函数的 SageMaker AI 训练作业](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/12/ML-22014-1.png)

图 1：SageMaker AI 上的 MTRL，其中训练作业每次部署都会调用 AgentCore 托管的代理一次，以对策略模型进行采样、玩游戏并报告奖励

每次部署时，MTRL 服务都会调用 AgentCore 运行时（Amazon Bedrock AgentCore 的一项功能），其中一个训练行包含一个秘密单词。运行时中的 Strands 代理通过 SageMaker 作业运行时的 OpenAI 兼容端点调用策略模型。该模型通过一个工具“guess_word”进行最多六次猜测，每次猜测后，环境都会返回每个字母的反馈和已知内容的摘要。当游戏结束时，代理返回一份奖励。 [组相对策略优化 (GRPO)](https://arxiv.org/abs/2402.03300) 使用同一个单词的多次部署中的奖励分布来更新策略模型上的低阶适应 ([LoRA](https://arxiv.org/abs/2106.09685)) 适配器。

以下三个设计要点很重要：

- **代理和奖励位于一处。** 部署到 AgentCore 的单个 Python 文件包含环境、工具和评分函数。
- **数据集仅包含秘密单词。** 与代理捆绑的单词列表是根据开源 [SCOWL](http://wordlist.aspell.net/) 单词列表构建的，仅用于评分。
- **奖励以结果为主。** 根据速度，解决支付 1.05–1.55，失败支付 -0.5，从未做出有效猜测支付 -1.5。一个小的塑造期限会奖励每一层中的良好策略。

### 定价

您无需选择实例或调整集群大小。您可以在三个维度上按每百万代币支付费用，按基本模型定价：

- **预填充：** 策略模型处理的输入令牌。这些在多轮任务中累积，因为每一轮都会重新读取历史记录。

## 先决条件

要完成本演练，您需要具备以下条件。另请参阅 [MTRL 先决条件](https://docs.aws.amazon.com/sagemaker/latest/dg/model-customize-mtrl-prereqs.html)。

- Python 3.10 或更高版本、uv、Node 20 或更高版本以及 AgentCore CLI (`npm install -g @aws/agentcore`)。请参阅 [Amazon Bedrock AgentCore 入门](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-get-started-cli.html) 了解安装以及 CLI 所需的 IAM 权限。
- botocore 1.43.37 或更高版本，在启动作业的计算机上。这是第一个包含“AgentRFT”“CreateJob”操作的版本。
- 两个 AWS Identity and Access Management (IAM) 角色，如步骤 1 中所述。
- 与代理位于同一区域的 Amazon Simple Storage Service (Amazon S3) 存储桶。训练作业也必须在该区域中运行，因为“CreateJob”拒绝跨区域运行时 ARN。

## 步骤 1：创建 IAM 角色

MTRL 使用两个角色，其中之一具有一般 SageMaker AI 文档中未提及的信任策略。

**代理运行时角色。** `agentcore deploy` 会为您创建此角色。它信任“bedrock-agentcore.amazonaws.com”并需要“AmazonSageMakerJobRuntimeAccess”托管策略，该策略允许代理调用策略模型并报告奖励。示例存储库中的 CDK 堆栈会自动附加此策略。

**培训工作角色。** 您创建这个角色。它必须信任具有 `sts:AssumeRole` 和 `sts:TagSession` 的 `job.sagemaker.amazonaws.com`，并且需要 `AmazonSageMakerJobFullAccess` 托管策略。
```
{
    "Version": "2012-10-17",
    "Statement": [{
        "Effect": "Allow",
        "Principal": {"Service": "job.sagemaker.amazonaws.com"},
        "Action": ["sts:AssumeRole", "sts:TagSession"]
    }]
}
```
**注意：** 信任主体是“job.sagemaker.amazonaws.com”，而不是“sagemaker.amazonaws.com”。使用通用主体时，“CreateJob”会失败并显示“无法承担角色”，并且消息仅在重试后才会指定正确的主体。

## 步骤 2：将代理部署到 Amazon Bedrock AgentCore

克隆[示例存储库](https://github.com/aws-samples/sample-multi-turn-rl-wordle)，在 Wordle/agentcore/`aws-targets.json` 中设置您的帐户和区域，然后部署：
```
git clone https://github.com/aws-samples/sample-multi-turn-rl-wordle
cd sample-multi-turn-rl-wordle/Wordle
agentcore validate
agentcore deploy
```
CLI 为运行时的 Linux ARM64 平台构建代理的依赖项，创建附加了“AmazonSageMakerJobRuntimeAccess”的执行角色，并通过 AWS CloudFormation 进行部署。我们建议您不要在控制台上上传代码包，因为控制台上通常会出现大约 700 MB 的已编译依赖项或策略附件错误。请注意训练作业输出中的运行时 ARN。

![Amazon Bedrock AgentCore 控制台显示 Wordle 代理运行时状态为就绪](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/12/ML-22014-2.png)

图 2：Amazon Bedrock AgentCore 控制台中状态为 Ready 的 Wordle 代理运行时

运行时从“agentcore.json”读取两个环境变量。 `REASONING_EFFORT=low` 在对策略模型的每个请求上设置 `reasoning_effort`。在我们的评估工作中，低努力度游戏每场比赛使用的样本令牌比中等努力度游戏少 63% 到 83%。 `REASONING_PROMPT_HINT=true` 还在系统提示中添加了“Reasoning: low”，这就是 gpt-oss 以 Harmony 聊天格式读取设置的方式。这两个变量都没有给模型提供任何有关秘密单词的提示。

![AgentCore 控制台环境变量面板，REASONING_EFFORT 设置为低](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/12/ML-22014-3.png)

图 3：运行时环境变量显示 REASONING_EFFORT 设置为低

代理是一个文件“main.py”。简化后，其入口点如下所示。对于您自己的任务，您可以更改任务解析、工具和奖励：
```
app = BedrockAgentCoreApp()

@app.entrypoint  # outermost: starts the HTTP server AgentCore invokes
@sagemaker_rft_handler  # reports the returned reward to SageMaker AI
def handle_rollout(payload):
    prompt, answer = parse_task(payload["prompt"])
    game = WordleGame(answer)

    @tool
    def guess_word(guess: str) -> str:
        """Submit a 5-letter Wordle guess and get feedback."""
        return game.guess(guess)

    agent = Agent(model=build_model(), system_prompt=SYSTEM_PROMPT, tools=[guess_word])
    agent(prompt)
    return {"reward": game.final_reward()}
```
**重要提示：** `sagemaker_rft_handler` 装饰器不会自行启动 HTTP 服务器。用 `BedrockAgentCoreApp` 和 `@app.entrypoint` 包裹它，入口点装饰器在最外面。如果没有这个，每次调用都会在 30 秒后超时。

## 步骤 3：验证运行时

在花费 GPU 时间之前，请确认整个链可以使用与训练服务发送的负载类似的有效负载。该存储库包括 Wordle/`payload.json` 之一：
```
{
  "prompt": "{\"prompt\": \"Guess the 5-letter word\", \"answer\": \"beach\", \"id\": \"smoke-test\"}",
  "metadata": {
    "jobArn": "arn:aws:sagemaker:us-east-1:111122223333:job/AgentRFT/smoke-test",
    "rolloutId": "r1"
  }
}
```
假作业 ARN 预计会失败，它失败的方式就是证明。首先将您自己的账户 ID 放入其中：对于另一个账户中的作业 ARN，该服务会在检查作业是否存在之前返回 403，这看起来像是一个损坏的 IAM 设置。从 Wordle 目录运行：
```
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
sed "s/111122223333/$ACCOUNT/" payload.json > /tmp/payload.json

aws bedrock-agentcore invoke-agent-runtime \
  --agent-runtime-arn <RUNTIME_ARN> \
  --runtime-session-id smoke-test-$(date +%s)000000000000000 \
  --payload fileb:///tmp/payload.json /dev/stdout
```
在运行时的 Amazon CloudWatch 日志中，您会看到代理解析提示、对作业运行时终端节点进行身份验证，并收到 400 错误，内容为“无法找到作业”。该失败证实了解析、身份验证和错误报告工作正常。命令本身打印 {“reward”: -1.5}，因为代理从未达到策略模型。 403 读取“无权访问此资源”意味着作业 ARN 仍指定另一个帐户。相反，30 秒超时意味着 HTTP 服务器未启动（请参阅步骤 2 中的重要说明）。

## 步骤 4：准备数据集

MTRL 数据集没有目标响应、转录本或标签。每一行都是代理要尝试的一项任务。以下是训练文件的前三行：
```
{"prompt": "{\"prompt\": \"Guess the 5-letter word\", \"answer\": \"riser\", \"id\": \"wordle_train_0000\"}"}
{"prompt": "{\"prompt\": \"Guess the 5-letter word\", \"answer\": \"swoon\", \"id\": \"wordle_train_0001\"}"}
{"prompt": "{\"prompt\": \"Guess the 5-letter word\", \"answer\": \"dirty\", \"id\": \"wordle_train_0002\"}"}
```
该服务读取“提示”列（或第一列）并将字符串逐字传递给您的代理，而不对其进行解析。我们将字符串制作为一个包含三个字段的小型 JSON 对象：

- **提示：**代理显示策略模型的指令，每一行都相同。
- **答案：** 秘密词。只有环境和奖励函数使用它。政策模型从来没有看到它。
- **id：** 用于将日志中的转出跟踪回其源行的行 ID。

示例存储库的“make_dataset.py”从答案列表中提取了 640 个训练单词（五个完整批次，每批 128 个）和 128 个验证单词，没有重叠，因此验证解决率衡量泛化能力。该服务还接受 Apache Parquet、JSON 数组和 CSV。将这两个文件上传到 Amazon S3：
```
uv run python make_dataset.py
aws s3 cp training-data.jsonl s3://<YOUR_BUCKET>/wordle-mtrl/train/
aws s3 cp validation-data.jsonl s3://<YOUR_BUCKET>/wordle-mtrl/validation/
```
由于该服务从不检查“提示”字符串，因此生产任务可以将完整的消息列表、工具配置或奖励规范打包到其中。有关示例，请参阅 [MTRL 文档](https://docs.aws.amazon.com/sagemaker/latest/dg/model-customize-mtrl-assets.html)，包括如何保护字符串中的敏感内容。

## 步骤 5：启动训练作业

启动器使用“sagemaker-train”SDK 中的“MultiTurnRLTrainer”类。将其指向步骤 2 中的运行时 ARN、步骤 1 中的角色、步骤 4 中的数据集以及用于指标的 MLflow 应用程序。 MLflow 应用程序是必需的，因此如果您没有，请先使用“aws sagemaker create-mlflow-app”创建它：
```
uv run python run_mtrl_training.py \
  --model openai-reasoning-gpt-oss-20b \
  --agent-runtime-arn <RUNTIME_ARN> \
  --role-arn arn:aws:iam::<ACCOUNT>:role/<JOB_ROLE> \
  --train-dataset s3://<YOUR_BUCKET>/wordle-mtrl/train/training-data.jsonl \
  --val-dataset s3://<YOUR_BUCKET>/wordle-mtrl/validation/validation-data.jsonl \
  --s3-output-path s3://<YOUR_BUCKET>/wordle-mtrl/output/ \
  --mlflow-app-arn arn:aws:sagemaker:<REGION>:<ACCOUNT>:mlflow-app/<APP_ID>
```
启动器会覆盖三个超参数，并将其他所有参数保留为 gpt-oss-20b 默认值。它将“sampling_max_tokens”设置为服务最大值 8192，因为在默认值 4096 下，gpt-oss 在第一次工具调用之前的推理过程中经常会耗尽令牌。它将“max_epochs”设置为 20，将“max_steps”设置为 100：默认“global_batch_size”为 128 时，有 640 行，每个 epoch 5 步，默认“group_size”为 8，每步玩 1,024 场比赛。作业将依次经历“正在启动”、“正在下载”和“待定”，然后再进入“培训”。训练结束后，您的 AgentCore 运行时开始接收部署调用。

**重要提示：** 不要在作业运行时重新部署代理。重新部署会重新启动运行时，正在进行的部署不会看到任何采样请求，并且服务会导致整个作业失败。

## 步骤 6：监控 MLflow 中的训练

该服务记录每一步的奖励、令牌和回合统计数据，并在每个“val_every”步骤运行验证。需要关注的指标是“val/reward/pass_at_1”，即解决的保留单词的分数。每个解决方案的得分至少为 1.01，因此它清除了服务的“success_threshold” 1.0，并且 pass@1 对其进行计数。下图是根据本次运行的 MLflow 历史记录构建的：

![两个折线图跟踪每场比赛的平均奖励和超过 100 个训练步骤的验证解决率](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/12/ML-22014-4.png)

图 4：100 步运行的训练曲线，左侧为每场比赛的平均奖励，右侧为验证解决率

训练奖励在 15 步内攀升至约 +0.57 并保持不变。验证奖励保持较低，主要是因为温度 1.0 与 0，而不是过度拟合（参见步骤 7）。在前 10 个步骤中，验证解决率从 2% 跃升至 31%，然后在 35% 至 48% 之间移动。 128 个单词中，这些波动大部分都是噪音。我们没有测试更多步骤是否有助于服务设置。

CloudWatch 中运行时的 OpenTelemetry 跟踪记录了每个模型转动和工具调用。这是经过训练的模型在评估工作中玩的一款游戏（中等难度，温度 1.0），推理经过修剪。秘密词是粘贴：
```
[model] Reasoning: [...] "CRANE" has 5 distinct letters: C,R,A,N,E. [...]
We'll guess "CRANE".
Tool call: guess_word(guess="CRANE")
[tool] Guess 1/6: CRANE -> C=gray, R=gray, A=yellow, N=gray, E=green
```

## 深入探讨：设计奖励

我们的奖励需要修改一次，而这个错误是很常见的。

第一个设计总结了整个游戏中 [wordle-lora-rl](https://github.com/charbull/wordle-lora-rl) 项目的每次猜测得分。这种评分之所以有效，是因为每个猜测都是一个独立的训练样本。总结为每场比赛一个奖励，它产生了我们仅通过读取痕迹发现的两个反转：

- **输掉的游戏获得正奖励。** 六回合奖金加起来约为+0.49。
- **第 1 回合的解决得分低于第 3 回合的解决得分。** 第一个猜测的解决方案获得了 +0.99，第三个猜测的解决方案获得了 +1.61，因为额外的回合获得了更多的奖金。

该修复将主要结果项与小的有界塑造项分开：
```
reward = outcome + w * clip(shaping, -1, 1), w = 0.04 if solved, else 0.15
```
结果项完全由游戏的结束方式决定：

| **结果** | **价值** |
| --- | --- |
|根据猜测 n 解决 | 1.05 + 0.5 * (6 – n) / 5，因此猜测 1 的 1.55 降至猜测 6 的 1.05 |
|六种猜测全部猜完，未解 | -0.5 | -0.5
|从未做出过有效的猜测| -1.5 | -1.5

塑造术语是每场比赛的猜测得分：

- 与已知的绿色、黄色或灰色字母相矛盾、重复猜测以及词典之外的单词的处罚。
- 强有力的开头词的熵奖励。
- 尝试新字母和缩小剩余可能性的奖励。

总和被剪裁为 [-1, 1]，解决时按 0.04 缩放，失败时按 0.15 缩放，因此它将具有相同结果的游戏分开，但永远不会将游戏移至另一层。具有典型的成型值：

| **场景** | **奖励** |
| --- | --- |
|解决猜测 1 | +1.550 |
|解决猜测 3 | +1.375 |
|解决猜测 6 | +1.069 |
|六次猜测后落败 | -0.427 | -0.427
|从未做出过有效的猜测| -1.500 | -1.500

现在，更快的解决方案总是会击败较慢的解决方案，每一次解决都会击败每一次失败，而从不玩是最糟糕的结果。我们的第一个修复使用了 0.15 的单一权重，这使得具有完全整形 (+1.45) 的猜测 3 求解优于具有最小值 (+1.25) 的猜测 2 求解。相邻猜测计数相距 0.1，因此较小的求解权重 0.04 可以消除重叠，并且最差的求解 (+1.01) 仍然可以清除 1.0 的成功阈值。塑造仍然很重要，因为 GRPO 从群体内的奖励差异中学习，因此线索一致性不同的两场失败的游戏仍然可以教会模型一些东西。正如 SageMaker AI 文档所建议的那样，从基于结果的奖励开始，谨慎地添加塑造，并检查真实轨迹上的奖励。

## 深入探讨：出了什么问题，按顺序排列

其中每一项都至少需要一次训练。

- **并发下的不记名令牌。** 每次调用使用新的 botocore 会话铸造令牌会在 32 个并发部署中导致凭证提供程序饥饿，并且在凭证轮换时缓存令牌一小时会返回 403 错误。修复方法是一个自刷新会话、一个短缓存以及在 403 上重新签名。
- **从未到达策略模型的部署会使整个作业失败。** 当部署中的每个模型调用都失败身份验证时，服务会以“未收到采样请求”结束作业。返回错误状态也会失败，所以总是返回奖励。模型被采样但从未做出有效猜测的游戏很好：它的得分为 -1.5，并且 100 步运行在大约 105,000 次部署中出现了 51 步。
- **工具调用变成纯文本。** 在学习率过高时，模型将工具调用写为文本，每次推出都会获得相同的楼层奖励，并且梯度消失。现在，代理可以从原始文本中恢复猜测，并具有较小的格式损失。
- **高原。训练奖励在大约第 15 步后停止上升，验证在大约第 30 步后停止改善，尽管在温度 0 时验证低估了模型（第 7 步）。 ** 接下来我们将尝试使用预先猜测的游戏种子，或者每个单词的推出次数多于默认的“group_size”8 的课程。

＃＃ 结论

SageMaker AI 上的 MTRL 根据整个事件的结果训练模型。这适合代理任务，其中正确的轨迹是未知的，只能对结果进行评分。我们使用了单集级别的奖励。当中间步骤也可以计分时，MTRL 还通过 [UpdateReward API](https://docs.aws.amazon.com/sagemaker/latest/APIReference/API_job_runtime_UpdateReward.html) 每回合接受一个奖励。在这篇文章中，开放权重 20B 模型在服务设置中达到了 84% 的解决率，高于 61%，训练代币约为 339 美元，AgentCore 运行时使用量约为 79 美元。训练曲线报告的 37% 是训练作业如何对验证进行评分的产物，因此请根据您将使用的设置进行评估。

同样的管道适用于公共模型从未接受过培训的内部程序、工具和工作流程。

首先，克隆[示例存储库](https://github.com/aws-samples/sample-multi-turn-rl-wordle)，按照前面的步骤操作，并在提交 GPU 时间之前运行步骤 3 中的冒烟测试。有关底层 API，请参阅 [SageMaker AI MTRL 文档](https://docs.aws.amazon.com/sagemaker/latest/dg/model-customize-mtrl.html)。
