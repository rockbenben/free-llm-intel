# 使用 Amazon Bedrock 和开源框架设计具备推理能力的多 agent 编排

***2026 年 7 月：** 本文已为提升准确性做过编辑，并更新了模型。*

随着生成式 AI 能力的演进，业务能否成功采用取决于能否构建出稳健的问题解决能力。处于这场变革最前沿的是 agentic 系统，它们利用基础模型（FM）的能力来应对复杂的真实世界挑战。通过无缝集成多个 agent，这些创新方案能在多样化环境中实现自主协作、决策和高效的问题解决。Amazon Web Services（AWS）的科学家与学术研究者联合开展的[实证研究](https://assets.amazon.science/4f/31/0777380647d2aec66281827eaef5/comm-collaborative-multi-agent-multi-reasoning-path-prompting-for-complex-problem-solving.pdf)表明，通过 agent 协作在竞赛类任务上增强推理能力已取得显著进展。

本文提供分步指引，教你创建一个具备推理能力的协作式多 agent 框架，从而把业务应用与 FM 解耦。文中演示如何把 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 与开源多 agent 框架结合，使 agent 之间能够协作与推理，动态执行各种任务。本练习将引导你使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/)、[Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)、Amazon Bedrock Agents 和 FM 构建一个推理编排系统。我们还会探讨把 Amazon Bedrock Agents 与开源编排框架 [LangGraph](https://langchain-ai.github.io/langgraph/) 和 [CrewAI](https://github.com/crewAIInc/crewAI) 集成，以进行任务分派和推理。

AWS 为 Amazon Bedrock 推出了[多 agent 协作能力](https://aws.amazon.com/blogs/aws/introducing-multi-agent-collaboration-capability-for-amazon-bedrock/)，使开发者能够构建、部署和管理多个协同处理复杂任务的 AI agent。该功能支持创建专门处理流程不同环节的专用 agent，并由一个 supervisor agent 来协调：它拆解请求、分派任务并汇总输出。这种方法提升了任务成功率、准确性和生产率，对于复杂的多步骤任务尤其如此。

关于本文讨论的示例代码与演示，请参阅 agentic-orchestration 的 [GitHub](https://github.com/aws-samples/agentic-orchestration) 仓库和[这场 AWS Workshop](https://catalog.us-east-1.prod.workshops.aws/workshops/d2131e02-4fff-4090-bff9-0c85ecfcf143/en-US)。你也可以参阅 [Amazon Bedrock 多 agent 协作代码示例的 GitHub 仓库](https://github.com/awslabs/amazon-bedrock-agent-samples)。

## agentic 服务的关键特征

在生成式 AI 语境中，“agent”指的是一个自主的功能单元，它可以与环境交互、收集数据并做出决策，从而执行复杂任务以达成预设目标。生成式 AI agent 是自主的、目标导向的系统，它们使用大语言模型（LLM）等 FM 与环境交互并适应环境。这些 agent 擅长规划、问题解决和决策，会使用思维链提示等技术来拆解复杂任务。它们能够自我反思、改进流程，并通过工具使用以及与其他 AI 模型的协作来扩展自身能力。这些 agent 可以独立运作，也可以协同运作，在各个领域执行任务，同时持续适应新信息和变化的情境。agent 能带来更高的创造力并规模化产出内容，自动化重复性任务，让人专注于战略性工作，从而减少重复操作并带来成本节省。下图展示了该方案的高层架构。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/13/ML-17568-IMG1-new.png)

要在 AWS 上实现一个 agent，可以使用如下代码示例中的 Amazon Bedrock Agents Boto3 客户端。在为该 agent 创建所需的 AWS 与 Identity and Access Management（IAM）角色之后，使用 create_agent API。该 API 需要一个 agent 名称、一个 FM 标识符和一个指令字符串。你也可以选择提供 agent 描述。创建出的 agent 尚未准备好使用。我们重点讲如何准备该 agent，然后用它来调用动作并与其他 API 交互。使用以下代码示例获取你的 agent ID；它对于用该 agent 执行操作至关重要。

```
# Use the Python boto3 SDK to interact with Amazon Bedrock Agent service

bedrock_agent_client = boto3.client('bedrock-agent')

# Create a new Bedrock Agent
response = bedrock_agent_client.create_agent(
    agentName=<agent_name>, #customized text string
    agentResourceRoleArn=<agent_role['Role']['Arn']>, #IAM role assigned to the agent
    description=<agent_description>, #customized text string
    idleSessionTTLInSeconds=1800, 
    foundationModel=<agent_foundation_model>, #e.g. "anthropic.claude-sonnet-4-5-20250514-v1:0"
    instruction=<agent_instruction>, #agent instruction text string
)
agent_id = response['agent']['agentId']
```

## 用于 agent 内协作的多 agent pipeline

多 agent pipeline 是 AI 系统内部的编排流程，涉及多个专用 agent 协同完成复杂任务。在 pipeline 中，agent 按顺序结构组织，不同的 agent 在整体工作流中负责特定子任务或角色。agent 之间会相互交互，通常通过共享的“草稿区”或消息系统，从而交换信息并在彼此成果之上继续推进。每个 agent 维护自己的状态，状态可以随着流程推进用新信息更新。复杂项目被拆解为可管理的子任务，然后分派给各专用 agent。工作流包含明确定义的流程，规定任务应如何编排，从而促进高效的任务分派并与目标对齐。这些流程既可以约束 agent 之间的交互，也可以约束 agent 内部的运作（例如 agent 如何与工具交互或如何处理输出）。可以为 agent 分配特定角色（例如检索器或注入器），以处理问题的不同方面。

作为一个实际示例，考虑一条用多 agent 框架 CrewAI 实现的博客写作多 agent pipeline。要用 CrewAI 创建多 agent pipeline，先定义将参与该 pipeline 的各个 agent。下面示例中的 agent 是 Planner Agent、Writer Agent 和 Editor Agent。接着把这些 agent 编排进 pipeline，指定任务执行顺序以及数据在它们之间流动的方式。CrewAI 提供了让 agent 之间传递信息并协调行动的机制。CrewAI 的模块化与可扩展设计使其非常适合开发简单和复杂的多 agent AI 应用。下图展示了这条多 agent pipeline。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/13/ML-17568-IMG2.png)

```
from crewai import Agent, Task, Crew, Process

# Create a blog writing multi-agent pipeline, which is comprised of a planner, a writer, and an editor agent
# This code snippet shows only the planner agent, which calls web search tools 
# and Amazon Bedrock for the LLM
# Note: This example uses the prerelease CrewAI API. 
# See https://github.com/crewAIInc/crewAI for changes in 1.0.
class blogAgents():
   def __init__(self, topic, model_id):
       self.topic = topic
       self.model_id = model_id
    
   def planner(self, topic, model_id):
       return Agent(
           role="Content Planner",
           goal=f"""Plan engaging and factually accurate content on {topic}.""", 
           backstory=f"""You're working on planning a blog article about the topic: {topic}. \n
                     You collect information by searching the web for the latest developments that directly relate to the {topic}. \n
                     You help the audience learn something to make informed decisions regarding {topic}. \n 
                     Your work is the basis for the Content Writer to write an article on this {topic}.""",
           allow_delegation=False,
           tools=<tools_to_use>,
           llm=<Bedrock_foundation_model>,
           verbose=True
       )
......

# Create the associated blog agent tasks which are comprised of a planner, writer, and editor tasks.
# This code snippet shows only the planner task.
class blogTasks():
   def __init__(self, topic, model_id):
       self.topic = topic
       self.model_id = model_id

   def plan(self, planner, topic, model_id):  
       return Task(
           description=(
                 f"""1. Prioritize the latest trends, key players, and noteworthy news on {topic}.\n
                 2. Identify the target audience, considering their interests and pain points.\n
                 3. Develop a detailed content outline including an introduction, key points, and a call to action.\n
                 4. Include SEO keywords and relevant data or sources."""
           ),
           expected_output=f"""Convey the latest developments on the {topic} with sufficient depth as a domain expert.\n
               Create a comprehensive content plan document with an outline, audience analysis,
SEO keywords, and resources.""",
           agent=planner
       )
......

# Define planner agent and planning tasks
planner_agent = agents.planner(self.topic, self.model_id)
plan_task = tasks.plan(planner_agent, self.topic, self.model_id)
......
 
# Define an agentic pipeline to chain the agent and associated tasks
# with service components, embedding engine, and execution process
crew = Crew(
        agents=[planner_agent, writer_agent, editor_agent],
        tasks=[plan_task, write_task, edit_task],
        verbose=True,
        memory=True,
        embedder={
            "provider": "huggingface",
            "config": {"model": "sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2"},
        },
        cache=True,
        process=Process.sequential # Sequential process will have tasks executed one after the other
       )
result = crew.kickoff()
```

如该代码示例所示，多 agent pipeline 通常是简单的线性结构，易于搭建和理解。它们具有从一个 agent 到下一个 agent 的清晰顺序流程，对于操作顺序明确的直白工作流效果很好。同时，这种 pipeline 结构对于复杂、非线性的 agent 交互不够灵活，因此处理分支逻辑或循环的能力较弱。对于需要在 agent 之间来回往复的问题，这可能效率较低。下一节将介绍面向多 agent 系统的图框架，它更适合更复杂的场景。

## 用于异步编排与推理的多 agent 图框架

多 agent 框架为智能、动态的问题解决提供了巨大潜力，使协作式的专用任务执行成为可能。这些系统虽然能通过动态激活和协调 agent 来提升推理准确性和响应效率，但也带来关键挑战，包括潜在偏见、推理能力受限，以及对稳健监督的需求。有效的多 agent 框架需要审慎的设计考量，例如明确的领导、动态的团队构建、有效的信息共享、思维链提示之类的规划机制、用于上下文学习的记忆系统，以及对专用语言模型的策略性编排。随着技术演进，在 agent 自主性与人类监督、伦理保障之间取得平衡，对于释放这些智能系统的全部潜力并降低潜在风险至关重要。

多 agent 图框架是一种用基于图的表示来建模多个自主 agent 之间交互与关系的系统。在这类框架中，agent 被表示为图中的节点，每个 agent 都有自己的能力集合、目标和决策过程。图中的边表示 agent 之间的交互、通信或依赖关系。这些可以包括信息共享、任务分派、协商或协调等。图结构允许对 agent 之间复杂、动态的关系建模，包括环、反馈回路和层级结构。下图展示了这一架构。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/16/Multi-agent-orchestration-and-reasoning.png)

基于图的方法提供了一种灵活、可扩展的方式来表示多 agent 系统的结构，使得分析、模拟和推理由 agent 交互涌现出的行为变得更容易。下面的代码片段展示了使用 LangGraph 构建面向多 agent 编排的图框架的过程。该框架对于管理和协调系统内多个 agent 之间的交互至关重要，能促进高效、有效的沟通与协作。值得注意的是，它强调即插即用特性，允许动态变更并灵活接纳第三方 agent。具备这种能力的框架可以无缝适应新需求并与外部系统集成，从而提升整体的通用性与可用性。

```
from langgraph.graph import StateGraph, END
......
# Create a graph to orchestrate multiple agents (i.e. nodes) 
orch = StateGraph(MultiAgentState)
orch.add_node("rewrite_agent", rewrite_node)
orch.add_node('booking_assistant', bedrock_agent_node)
orch.add_node('blog_writer', blog_writer_node)
orch.add_node("router_agent", router_node)
orch.add_node('search_expert', search_expert_node)
....

# Create edges to connect agents to form a graph
orch.set_entry_point("rewrite_agent")
orch.add_edge('rewrite_agent', 'router_agent')
orch.add_conditional_edges(
    "RAG_agent",
    decide_to_search,
    {
        "to_human": "human",
        "do_search": "search_expert",
    },
)
orch.add_edge('blog_writer', 'text2image_generation')
......

# Compile the graph for agentic orchestration
graph = orch.compile(checkpointer=memory, interrupt_before = ['human'])
```

多 agent 图方法对于需要建模和分析自主实体之间复杂、动态交互的领域尤其有用，例如机器人、物流和社交网络等。与线性的多 agent pipeline 方法相比，基于图的多 agent 方法有多项优点和缺点，下面予以归纳。

## 优势与局限

agentic 服务的出现代表了系统设计的一种变革性方法。与传统遵循固定、预设工作流的 AI 模型不同，agentic 系统的特征是能够在实时中协作、适应并做出决策。从被动 AI 到主动 AI 的这一转变，既带来了令人兴奋的机会，也为开发者和架构师带来了独特的设计挑战。agentic 服务的核心是 agentic 推理这一概念，它体现了一种灵活、迭代的问题解决方法，反映了人类的认知过程。通过引入反思、自我改进和工具利用等设计模式，我们可以开发出能够持续增强并在各领域具备更广功能的 AI agent。

agentic 服务虽然前景可期，但存在若干局限，要在生产环境中成功落地就必须加以解决。管理多个自主 agent 的复杂性——尤其当它们的数量和范围扩大时——对维持系统的一致性和稳定性构成重大挑战。此外，这些系统的涌现行为可能难以预测和理解，从而妨碍透明性与可解释性，而这两者对于建立信任与问责至关重要。安全与稳健性是最重要的关切，因为非预期的行为或失败可能带来深远后果，因此需要稳健的保障措施和错误处理机制。随着 agentic 服务规模扩大，保持高效性能变得越来越有挑战，需要优化的资源利用和负载均衡。最后，基于 agent 的系统缺乏被广泛采用的标准与协议，造成互操作性问题，使这些服务难以与既有基础设施集成。解决这些局限对于 agentic 服务在各领域的广泛采用与成功至关重要。

优势：

- 使用图结构更灵活地表示 agent 交互
- 更适合具有非线性 agent 通信的复杂工作流
- 更容易表示 agent 之间的环和分支逻辑
- 对大型多 agent 系统可能更具可扩展性
- 整体 agent 系统结构的可视化更清晰

劣势：

- 相比线性 pipeline，初始搭建更复杂
- 可能需要更多前期规划来设计图结构
- 可能带来额外的资源消耗和更长的响应时间

## 后续步骤

在多 agent 编排的下一阶段，我们将聚焦于增强 agent 的推理、反思和自我纠错能力。这涉及开发先进算法（例如思维树（ToT）提示、蒙特卡洛树搜索（MCTS）等），使 agent 能够从与同伴的交互中学习、适应新情境，并根据反馈纠正自身行为。此外，我们正在构建一个可容纳各类 agentic 服务的生产级框架。该框架在设计上将兼顾灵活性与可扩展性，实现不同类型 agent 与服务的无缝集成。这些工作目前正在进行，我们将在下一篇博文中详细更新进展。请继续关注我们在多 agent 编排创新方法上的更多洞见。

## 结论

多 agent 编排与推理代表了生成式 AI 生产化采用的一大跃进，为复杂的问题解决和决策提供了前所未有的潜力，并使你的应用与单个 FM 解耦。同时，承认并解决其局限也很重要，包括可扩展性挑战、长延迟以及不同 agent 之间可能的不兼容。展望未来，增强 agent 的自身推理与 agent 内推理、反思和自我纠错能力将至关重要。这将涉及开发更复杂的元认知算法、改进 agent 间通信协议，以及实现稳健的错误检测与纠正机制。
