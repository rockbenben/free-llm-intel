# 在 AWS 上用 X.509 PKI 保护 AI agent 身份

当 AI agent 访问数据库、API 和敏感业务操作时，通过 X.509 public key infrastructure（PKI）建立加密身份就成为一项关键要求。核心挑战在于证明是哪个 agent 发出了请求、防止 agent 之间相互伪造，并确认每个 agent 只代表某个已获授权的用户行事。在组件之间共享 API key，或在 agent 链中传递 OAuth token 之类的传统做法，无法满足企业部署所要求的零信任标准。

多 agent 的 AI 框架越来越多地使用 Model Context Protocol（MCP）把 agent 连接到外部工具和数据源。MCP 定义了由 large language model（LLM）驱动的 agent 如何调用数据库查询或电子邮件操作之类的工具。然而，MCP 没有内置的身份验证标准。它在设计上与传输方式无关。这就造成了一个关键缺口：如果没有恰当的身份机制，任何组件都可能冒充某个 agent、重放被截获的凭证，或在未获授权的情况下调用工具。

在本文中，我们展示如何结合 Keyfactor EJBCA 与 AWS 服务来填补这一缺口。EJBCA 是一个 PKI 平台，支持高可用部署、REST API 自动化和 Online Certificate Status Protocol（OCSP）验证。该参考架构使用四种互补的安全机制。第一，签名请求信封在每次 agent 调用上提供加密的存在性证明（proof-of-possession）。第二，用户签名的委派声明无需共享凭证即可授权 agent。第三，RFC 8693 作用域 token 限制任何单个 token 泄露所造成的暴露范围。第四，实时 OCSP 吊销检查把凭证变更立即传播到所有 agent。

该解决方案使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 通过 [AWS Strands Agents SDK](https://github.com/strands-agents/sdk-python) 进行 LLM 推理。虽然这一参考架构使用数据库作为受保护资源，但同样的身份验证模式适用于任何与 MCP 兼容的工具服务器。所有示例的完整源代码都在配套的 GitHub 仓库中提供。

AWS 与 Keyfactor 的合作把 AWS 托管服务（Amazon Bedrock、AWS Secrets Manager、Amazon Relational Database Service（Amazon RDS））与支持证书生命周期管理、自动化注册和实时吊销的 PKI 基础设施结合在一起。这一组合填补了 AI agent 生态中的一个缺口。AWS 提供计算、存储和 AI 推理层，而 Keyfactor 提供加密身份层，把 agent 绑定到可验证、可吊销、短生命周期的凭证上。这一联合参考架构由 AWS 和 Keyfactor 的工程团队协作开发，展示了如何集成这些技术。你可以把这里展示的模式调整后用于自己的多 agent 部署。

## 解决方案概览

该架构实现三个身份验证层，每一层针对 agent 通信链中不同的信任边界。这三个层使用前文介绍的四种安全机制：用于存在性证明的签名信封、用于无凭证授权的委派声明、用于限制暴露范围的作用域 token，以及用于实时吊销的 OCSP。这些机制在各层之间的组合方式如下表所示。

| **层** | **信任边界** | **机制** | **验证内容** |
| --- | --- | --- | --- |
| 1. 用户认证 | 用户到系统 | OAuth + X.509 证书 + 委派声明生成 | 用户身份、凭证绑定 |
| 2. Agent 到 Agent | Agent 到 Agent | 签名信封（PoP + nonce + 时间戳） | 调用方身份、请求新鲜度、不可重放 |
| 3. MCP 认证 | Agent 到工具服务器 | 作用域 token + 信封 + 委派 | 全部身份、授权链、OCSP |

## 解决方案详解

以下步骤逐一讲解架构中的每个组件，从用户初始登录一直到会话清理。每一步都建立在前一步之上，构建起一条把人类用户连接到最终工具执行的信任链。

### 先决条件

- 一个有效的 AWS 账户，可访问 Amazon Bedrock、Amazon RDS for MySQL、Amazon SES 和 AWS Secrets Manager。
- Keycloak 26.2 或更高版本（RFC 8693 标准 token 交换所需。更早的版本使用不兼容的旧式交换）。
- Keyfactor EJBCA Enterprise，已配置 REST API V1 和 OCSP responder。
- 用于 REST API 身份验证的 EJBCA API 管理员证书（`api-admin.p12`）。
- Python 3.9+ 开发环境。
- 熟悉 X.509 证书、OCSP、OAuth 2.0、RSA 数字签名和 PKCS#12 密钥库。

### 步骤 1：用户登录、证书签发和委派声明生成

登录流程通过三种机制建立用户身份，然后在不共享用户凭证的前提下把权限委派给 AI agent。这种分离至关重要：agent 获得的是授权证明，而从不持有用户的私钥或完整的会话 OAuth token。

首先，应用使用 OAuth 2.0 密码授权模式对用户在 Keycloak 上进行身份验证，获得一个完整会话的访问 token 和一个刷新 token。紧接着，应用执行一次 RFC 8693 token 交换以获得降权 token。该 token 的受众被限制为 MCP server。只有这个受限 token 会被交给 agent。即使它被意外暴露，也无法访问组织中的任何其他服务。

其次，应用在本地生成 RSA 2048+ 密钥对，并通过 `pkcs10enroll` REST API 端点向 EJBCA 提交 Certificate Signing Request（CSR）。EJBCA 对 CSR 签名并返回证书。应用把证书和私钥打包成一个 PKCS12 容器，并存入 AWS Secrets Manager。私钥从不离开应用边界。它不会被发送给 EJBCA，不会与 agent 共享，也不会存储在文件系统上。三个 agent 证书使用同样的基于 CSR 的流程签发，每个 agent 角色一个。

第三，用户的私钥对一份委派声明签名。这是一个 JSON 文档，列出三个 agent 证书的 SHA-256 指纹，以及用户的主体名称、签发时间和过期时间。这份委派证明用户授权了这些特定 agent 代表其行事。agent 携带的是这份委派，而不是用户的证书。

```
# RFC 8693 Token Exchange - downscope to MCP audience
downscoped_token = keycloak.token_exchange(
    original_token, audience="mysql-mcp-server", scope="database:write"
)
# Client-side key generation (user key never leaves this flow)
private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
csr = build_csr(private_key, f"CN={username},E={username}@org.com")
user_cert = ejbca.pkcs10enroll(csr, ca_name="UserCA")
# User signs delegation over agent cert fingerprints
delegation = mint_delegation(
    username=username,
    user_cert_pem=user_cert,
    user_key_pem=private_key_pem,
    agent_cert_pems=[orch_cert, mysql_cert, email_cert]
)
# Result: {sub, agent_fingerprints[], iat, exp, user_cert_pem, signature_b64}
```

### 步骤 2：agent 之间的签名信封

当编排器 agent 把请求路由给子 agent（例如 MySQL agent 或 Email agent）时，它并不只是传递自己的证书来表明身份。相反，它使用 `RSA-PSS-SHA256` 和自己的私钥对整个请求负载签名，包括工具名称、参数、时间戳和一个加密随机 nonce。由此产生的签名信封提供了存在性证明。接收方的 agent 可以验证调用方确实持有与所出示证书相对应的私钥。

接收方 agent 在处理请求之前，会对信封执行六项校验：

- **签名验证：** 证明发送方持有私钥（存在性证明）。
- **时间戳新鲜度：** 信封必须在当前时间的 `ENVELOPE_MAX_AGE_SECONDS`（默认 60 秒）之内。
- **Nonce 唯一性：** `ReplayCache` 会拒绝任何此前出现过的 nonce，从而防止请求重放。
- **CA 链验证：** 发送方的证书必须能链接到受信任的 CA（`UserCA.pem`）。
- **角色授权：** 证书 CN 的角色后缀必须在该 agent 的 `ALLOWED_CALLER_ROLES` 中。
- **OCSP 吊销检查：** 对 EJBCA 的实时检查确认该证书未被吊销。

如果编排器需要重新发送同一个提示（例如在瞬时故障之后），它必须用新的 nonce 创建新的信封。旧信封无法被重放，即使是合法发送方也不行。

```
# Orchestrator signs request to sub-agent
envelope = sign_envelope(
    payload={"tool": "query_database", "args": {"sql": "SELECT ..."}},
    cert_pem=orchestrator_cert_pem,
    private_key_pem=orchestrator_key_pem
)
# envelope: {payload_b64, cert_pem, timestamp, nonce, signature_b64, alg}
# Sub-agent verifies (six checks)
verified_payload = verify_envelope(
    envelope,
    allowed_role="orchestrator-agent",
    ca_cert_pem=ca_pem,
    replay_cache=cache
)
```

### 步骤 3：MCP server 身份验证

MCP server（FastMCP）是任何数据库操作运行之前的最后一道信任边界。它对每次工具调用执行四项校验，实现纵深防御。即使某个凭证遭到未授权访问，其余检查仍能阻止未授权的操作。

身份验证序列：

- **Token 自省：** 向 Keycloak 的 `/token/introspect` 端点发起 POST，验证 token 处于活动状态且其受众包含 “mcp-server”。受众不正确的完整会话 token 会被拒绝。
- **信封验证：** 验证 agent 的签名信封的签名正确性、时间戳新鲜度、nonce 唯一性、CA 链信任、角色匹配（`mysql-agent`）以及 OCSP 未吊销状态。
- **委派验证：** 验证用户的委派声明。签名证明用户密钥的持有者授权了这份委派，调用 agent 的证书指纹出现在授权列表中，并且用户的证书通过 OCSP 检查。
- **身份交叉核对：** token 用户名、委派主体和 agent 证书 CN 前缀必须全部一致。这确认了从用户到工具执行的一条单一且一致的身份链。

```
# MCP Server - Four validation checks
# 1. Token: must be active with correct audience
info = introspect(token)
assert info["active"] and "mcp-server" in info["aud"]
# 2. Envelope: proof-of-possession + freshness + replay + CA + role + OCSP
payload = verify_envelope(envelope, "mysql-agent", ca_pem, replay_cache)
# 3. Delegation: user authorized this agent + user cert not revoked
claims = verify_delegation(delegation, agent_cert_pem, ca_pem)
# 4. Cross-check: consistent identity chain
assert token_username == claims["sub"] == agent_cn.rsplit("_", 1)[0]
# All checks passed - execute tool
result = execute_sql(payload["args"]["sql"])
```

### 步骤 4：防止重放

每个签名信封都携带一个唯一 nonce，即一个用 Python 的 secrets 模块生成的 128 位加密随机十六进制字符串。`ReplayCache` 是一个线程安全的内存存储，会记住每个 nonce，直到其新鲜度窗口（2 倍 `ENVELOPE_MAX_AGE_SECONDS`）到期。如果同一个 nonce 出现在第二个请求中，该信封会被立即拒绝，即使其签名有效、时间戳新鲜。

时间戳验证与 nonce 检查相辅相成。信封的时间戳必须在服务器当前时间的 `ENVELOPE_MAX_AGE_SECONDS`（默认 60 秒）之内。这些机制共同应对四种未授权访问场景：

- **录制重放：** 未授权用户捕获了一个有效信封并在之后重新提交。该 nonce 此前已被记录。
- **延迟投递：** 在传输中被截获的信封在新鲜度窗口之后才到达。时间戳检查失败。
- **过期请求复用：** 被代理缓存的旧信封被重新提交。nonce 与时间戳检查都会失败。
- **预先计算的伪造：** 未授权用户无法预测未来的 nonce 来预先签名信封。

### 步骤 5：客户端生成密钥

该架构的一项关键安全属性是私钥在本地生成，并且从不传输到任何外部系统。应用使用 Python cryptography 库生成 RSA 2048+ 密钥对。它构建一个只包含公钥和主体信息的 CSR，并且只把 CSR 通过 `pkcs10enroll` 端点发送给 EJBCA。

EJBCA 验证 CSR、应用证书配置文件（7 天有效期、密钥用途约束）、用 CA 密钥签名，并返回签发的证书。然后应用把本地持有的私钥与返回的证书打包成 PKCS12 容器，并存放在 AWS Secrets Manager 中。

这一设计提供了若干安全属性：

- 用户的私钥只在登录时用于对委派声明签名。它从不与 agent 共享。
- 每个 agent 的私钥只由该 agent 用于对信封签名。它从不在 agent 之间共享。
- EJBCA 从来不会看到或存储私钥。它完全作为证书颁发机构运行。
- 如果 Secrets Manager 遭到未授权访问，PKCS12 密码（单独存放）会增加一层额外防护。
- 密钥材料可以通过在下次登录时用新的 CSR 重新注册来独立轮换。

### 步骤 6：完整注销与凭证吊销

注销会触发一次吊销级联，立即让所有未到期的凭证失效。该序列完成后不会留下任何有效凭证：

- **在 EJBCA 中吊销用户证书：** 这会立即使所有未到期的委派失效，因为委派验证会通过 OCSP 实时检查用户的证书。
- **吊销全部三个 agent 证书：** 这会使所有未到期的签名信封失效，因为信封验证包含 OCSP。
- **从 AWS Secrets Manager 删除所有密钥：** 使用 `ForceDeleteWithoutRecovery` 立即删除，不保留恢复窗口。
- **终止 Keycloak 会话：** 通过会话终止端点使降权 token 失效。

吊销级联是关键的安全属性。在 PKI 层吊销单个用户证书，就能及时撤销所有下游 agent 的权限，而无需逐个吊销 token、删除会话或联系每个 agent。OCSP 提供了传播机制，而且由于每个请求都会检查 OCSP，效果是即时的。

## 安全考量

该架构中的设计选择满足了若干对生产级多 agent 部署十分重要的安全属性。

私钥隔离。用户的私钥只在登录流程期间存在，并且仅用于签署委派。agent 密钥按 agent 划分作用域，从不在彼此之间共享。没有任何密钥材料跨越信任边界。

委派与凭证共享的对比。agent 通过一条加密链（委派到 agent 指纹再到信封签名）证明其权限，而从不持有用户凭证。如果某个 agent 密钥泄露，暴露的只是该 agent 的密钥，而不是用户的密钥。

作用域 token。RFC 8693 token 交换产生的 token 只被 MCP server 接受。一个意外泄露的降权 token 无法对 Keycloak 管理 API、其他服务，甚至另一个不同的 MCP server 实例进行身份验证。

防止重放。逐请求 nonce 与 60 秒新鲜度窗口的组合，确认每个请求都是一次性且有时间限制的。`ReplayCache` 是线程安全且自动清理的。

失效即拒绝设计。任何验证失败都会导致立即拒绝。OCSP 不可达：拒绝。签名无效：拒绝。时间戳过期：拒绝。nonce 重放：拒绝。受众错误：拒绝。安全检查没有任何优雅降级。

吊销级联。吊销一个用户证书即可及时使所有委派、所有 agent 权限和所有未到期信封失效。这一效果通过实时 OCSP 传播，无需逐个清理凭证。

单向信任链。`ALLOWED_CALLER_ROLES` 映射强制只有 `orchestrator-agent` 可以调用 `mysql-agent` 和 `email-agent`。子 agent 之间不能相互调用，不能向上调用编排器，也不能冒充用户。

### AI 治理考量

PKI 架构为该系统中的 AI agent 提供了内建的行为边界。生产部署应在本文所述的基于 PKI 的访问控制之外，使用 Amazon Bedrock Guardrails 对 agent 响应实施内容过滤、话题规避和 grounding 检查。

- **工具边界**：AI agent 在严格的工具约束下运行。它只能调用预定义的 MCP 工具（`execute_sql`、`describe_table`、`list_tables`）。agent 无法执行任意代码，也无法访问其证书作用域之外的资源。
- **人工监督**：所有 agent 操作都会被记录并可审计。AWS CloudTrail 捕获 AWS API 调用，MCP server 记录每次通过验证的工具调用及其完整身份链（用户、agent、时间戳和操作）。
- **数据处理**：用户查询和结果都留在经过身份验证的会话边界之内。作用域 token 把数据访问限制在特定的 MCP server 实例上。
- **基于证书的行为边界**：agent 只能调用其持有有效证书的工具。没有 `mysql-agent` 证书的 agent 无法访问数据库，无论 LLM 可能生成什么指令。

## 扩展该架构

你可以扩展该架构以支持更多 agent 类型、横向扩展和多租户隔离。以下段落介绍最常见的扩展点。

- 要添加新的 agent 类型，你只需在 `ALLOWED_CALLER_ROLES` 中添加一个条目。证书会在登录时自动签发，委派声明会动态包含新 agent 的指纹。无需改动基础设施。
- 对于横向扩展，你可以把 EJBCA 的 OCSP responder 以高可用模式部署在负载均衡器之后。AWS Secrets Manager 支持适合该工作负载的高请求速率。对于分布式部署，`ReplayCache` 可以基于 Amazon ElastiCache 实现。
- 要把架构加固到生产级，你可以通过 AWS CloudHSM 或本地 HSM 使用由 hardware security module（HSM）支持的 EJBCA 签名密钥。OCSP 响应装订（stapling）可降低验证延迟，Certificate Transparency 日志则提供已签发证书的完整审计轨迹。
- 对于多租户部署，你可以创建按租户划分的 Certificate Authority 或按租户划分的委派机构，以实现加密层面的租户隔离。结合按租户划分的 AWS 账户，这能在租户之间提供强隔离。
- 你还可以用 AWS Identity and Access Management（IAM）角色补充基于 PKI 的 agent 身份。用 PKI 进行 agent 之间的身份验证，用 IAM 进行 AWS 服务授权。两个系统独立工作，提供纵深防御。

## 结论

在本文中，我们展示了一个使用 X.509 PKI 结合 Keyfactor EJBCA 与 AWS 服务来保护 AI agent 通信的参考架构。该架构通过四种互补机制解决了多 agent AI 系统中根本性的身份缺口：

- 签名请求信封在每次 agent 间调用上提供加密的存在性证明，使未授权方伪造 agent 身份或重放其请求变得困难得多。
- 用户签名的委派声明把授权与凭证共享解耦。agent 无需持有用户的私钥或完整会话 token，即可证明其有权代表用户行事。
- RFC 8693 作用域 token 把任何 token 泄露的暴露范围限制在单个服务边界之内。
- 实时 OCSP 吊销检查确认凭证吊销在整个系统中立即生效。吊销一个用户证书即可及时终止所有下游 agent 的权限。

该架构与框架无关。虽然我们用 AWS Strands Agents SDK 和 FastMCP 进行了演示，但同样的 PKI 模式适用于 LangChain、CrewAI、AutoGen 或任何使用工具协议的其他多 agent 框架。随着 AI agent 的数量不断增加并接触到越来越敏感的操作，agent 身份基础设施正从可选变为必需。
