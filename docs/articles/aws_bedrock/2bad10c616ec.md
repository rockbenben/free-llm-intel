## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 在 AWS 上使用 X.509 PKI 保护 AI 代理身份

当 AI 代理访问数据库、API 和敏感业务操作时，通过 X.509 公钥基础设施 (PKI) 建立加密身份成为一项关键要求。核心挑战是证明哪个代理发出了请求，防止代理之间的伪造，并确认每个代理仅代表授权用户行事。传统方法（例如在组件之间共享 API 密钥或通过代理链传递 OAuth 令牌）无法满足企业部署所需的零信任要求。

多代理 AI 框架越来越多地使用模型上下文协议 (MCP) 将代理连接到外部工具和数据源。 MCP 定义了大型语言模型 (LLM) 支持的代理如何调用数据库查询或电子邮件操作等工具。然而，MCP没有内置的身份验证标准。它的设计与传输无关。这就造成了一个关键的差距：如果没有适当的身份机制，任何组件都可以冒充代理、重放截获的凭据或未经授权调用工具。

在这篇文章中，我们将向您展示如何结合使用 Keyfactor EJBCA 和 AWS 服务来弥补这一差距。 EJBCA 是一个 PKI 平台，支持高可用性部署、REST API 自动化和在线证书状态协议 (OCSP) 验证。该参考架构使用四种互补的安全机制。首先，签名的请求信封为每个代理呼叫提供加密的所有权证明。其次，用户签名的委派断言在不共享凭据的情况下授权代理。第三，RFC 8693 受众范围的代币限制了任何单一代币披露的暴露范围。第四，实时 OCSP 吊销检查会立即在所有代理之间传播凭证更改。

该解决方案使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 通过 [AWS Strands Agents SDK](https://github.com/strands-agents/sdk-python) 进行 LLM 推理。虽然此参考架构使用数据库作为受保护资源，但相同的身份验证模式适用于任何 MCP 兼容的工具服务器。附带的 GitHub 存储库中提供了所有示例的完整源代码。

## 解决方案概述

该架构实现了三个身份验证层，每个层都解决代理通信链中不同的信任边界。这三层使用之前介绍的四种安全机制：用于所有权证明的签名信封、用于无凭证授权的委托断言、用于限制暴露的受众范围的令牌以及用于实时撤销的 OCSP。这些机制跨层组合，如下表所示。

| **层** | **信任边界** | **机制** | **验证** |
| --- | --- | --- | --- |
| 1. 用户认证 |用户到系统| OAuth + X.509 证书 + 委托铸造 |用户身份、凭证绑定 |
| 2. 代理对代理 |代理对代理|签名信封（PoP + 随机数 + 时间戳）|来电身份、请求新鲜、无重播 |

## 解决方案演练

以下步骤将逐步介绍该架构的每个组件，从初始用户登录到会话清理。每个步骤都建立在前一个步骤的基础上，建立一条将人类用户与最终​​工具执行连接起来的信任链。

### 先决条件

- 一个有效的 AWS 账户，可以访问 Amazon Bedrock、Amazon RDS for MySQL、Amazon SES 和 AWS Secrets Manager。
- Keycloak 26.2 或更高版本（RFC 8693 标准令牌交换所需。以前的版本使用不兼容的旧版交换）。
- 配置了 REST API V1 和 OCSP 响应程序的 Keyfactor EJBCA Enterprise。
- 用于 REST API 身份验证的 EJBCA API 管理员证书 (`api-admin.p12`)。
- Python 3.9+ 开发环境。
- 熟悉 X.509 证书、OCSP、OAuth 2.0、RSA 数字签名和 PKCS#12 密钥存储。

### 第 1 步：用户登录、证书颁发和委托铸造

登录流程通过三种机制建立用户身份，然后将权限委托给人工智能代理，而无需共享用户的凭据。这种分离至关重要：代理无需持有用户的私钥或完整会话 OAuth 令牌即可接收授权证明。

首先，应用程序使用 OAuth 2.0 密码授予针对 Keycloak 对用户进行身份验证，接收完整会话访问令牌和刷新令牌。之后，应用程序立即执行 RFC 8693 令牌交换以获得范围缩小的令牌。该令牌的受众仅限于 MCP 服务器。只有这个有限的令牌才会交给代理。如果它无意中暴露，它就无法访问组织中的任何其他服务。

其次，应用程序在本地生成 RSA 2048+ 密钥对，并通过“pkcs10enroll”REST API 端点向 EJBCA 提交证书签名请求 (CSR)。 EJBCA 签署 CSR 并返回证书。该应用程序将证书和私钥捆绑到 PKCS12 容器中，并将其存储在 AWS Secrets Manager 中。私钥永远不会离开应用程序边界。它不会发送到 EJBCA，不会与代理共享，也不会存储在文件系统上。使用相同的基于 CSR 的流程颁发三个代理证书，每个代理角色一个。

第三，用户的私钥签署委托断言。这是一个 JSON 文档，列出了所有三个代理证书的 SHA-256 指纹，以及用户的主题名称、颁发时间和到期时间。该委托证明用户授权这些特定代理代表他们行事。代理携带此委托而不是用户的证书。
```
# RFC 8693 Token Exchange - downscope to MCP audience
downscoped_token = keycloak.token_exchange(
    original_token, audience="mysql-mcp-server", scope="database:write"
)
# Client-side key generation (user key never leaves this flow)
private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
csr = build_csr(private_key, f"CN={username},E={username}@org.com")
user_cert = ejbca.pkcs10enroll(csr, ca_name="UserCA")
# User signs delegation over agent cert fingerprints
delegation = mint_delegation(
    username=username,
    user_cert_pem=user_cert,
    user_key_pem=private_key_pem,
    agent_cert_pems=[orch_cert, mysql_cert, email_cert]
)
# Result: {sub, agent_fingerprints[], iat, exp, user_cert_pem, signature_b64}
```
### 第 2 步：代理对代理签名的信封

当 Orchestrator 代理将请求路由到子代理（例如 MySQL 代理或电子邮件代理）时，它不会简单地传递其证书以进行识别。相反，它使用带有“RSA-PSS-SHA256”的私钥对整个请求负载进行签名，包括工具名称、参数、时间戳和加密随机数。由此产生的签名信封提供了所有权证明。接收代理可以验证调用者是否确实持有与所提供的证书相对应的私钥。

接收代理在处理请求之前对信封执行六次验证检查：

- **签名验证：** 证明发送者拥有私钥（拥有证明）。
- **时间戳新鲜度：** 信封必须在当前时间的“ENVELOPE_MAX_AGE_SECONDS”（默认 60 秒）内。
- **Nonce 唯一性：** `ReplayCache` 拒绝任何以前看到的 Nonce，从而防止请求重播。
- **CA 链验证：** 发送者的证书必须链接到受信任的 CA (`UserCA.pem`)。
- **角色授权：** 证书 CN 的角色后缀必须位于该代理的“ALLOWED_CALLER_ROLES”中。
- **OCSP 吊销检查：** 针对 EJBCA 的实时检查确认证书尚未被吊销。

如果编排器需要重新发送相同的提示（例如，在短暂故障后），它必须使用新的随机数创建一个新信封。旧信封无法重播，即使是合法发件人也是如此。
```
# Orchestrator signs request to sub-agent
envelope = sign_envelope(
    payload={"tool": "query_database", "args": {"sql": "SELECT ..."}},
    cert_pem=orchestrator_cert_pem,
    private_key_pem=orchestrator_key_pem
)
# envelope: {payload_b64, cert_pem, timestamp, nonce, signature_b64, alg}
# Sub-agent verifies (six checks)
verified_payload = verify_envelope(
    envelope,
    allowed_role="orchestrator-agent",
    ca_cert_pem=ca_pem,
    replay_cache=cache
)
```
### 步骤 3：MCP 服务器身份验证

MCP 服务器 (FastMCP) 是任何数据库操作运行之前的最终信任边界。它对每个工具调用执行四次验证检查，实现深度防御。即使一个凭证受到未经授权的访问，其余的检查也可以防止未经授权的操作。

认证顺序：

- **令牌内省：** 到 Keycloak `/token/introspect` 端点的 POST 验证令牌是否处于活动状态并且其受众包含“mcp-server”。没有正确受众的完整会话令牌将被拒绝。
- **信封验证：** 验证代理签名信封的签名正确性、时间戳新鲜度、随机数唯一性、CA 链信任、角色匹配（`mysql-agent`）和 OCSP 不可撤销。
- **委托验证：** 用户的委托断言得到验证。签名证明用户的密钥持有者授权了该委托，调用代理的证书指纹出现在授权列表中，并且通过 OCSP 检查用户的证书。
- **身份交叉检查：** 令牌用户名、委托主题和代理证书 CN 前缀必须全部匹配。这确认了从用户到工具执行的单一一致身份链。
```
# MCP Server - Four validation checks
# 1. Token: must be active with correct audience
info = introspect(token)
assert info["active"] and "mcp-server" in info["aud"]
# 2. Envelope: proof-of-possession + freshness + replay + CA + role + OCSP
payload = verify_envelope(envelope, "mysql-agent", ca_pem, replay_cache)
# 3. Delegation: user authorized this agent + user cert not revoked
claims = verify_delegation(delegation, agent_cert_pem, ca_pem)
# 4. Cross-check: consistent identity chain
assert token_username == claims["sub"] == agent_cn.rsplit("_", 1)[0]
# All checks passed - execute tool
result = execute_sql(payload["args"]["sql"])
```
### 步骤 4：预防重播

每个签名的信封都带有一个唯一的随机数，即使用 Python 的 Secrets 模块生成的 128 位加密随机十六进制字符串。 “ReplayCache”是一个线程安全的内存存储，它会记住每个随机数，直到其新鲜度窗口到期（2x“ENVELOPE_MAX_AGE_SECONDS”）。如果第二个请求中出现相同的随机数，则该信封将立即被拒绝，即使其签名有效并且时间戳是最新的。

时间戳验证是对随机数检查的补充。信封的时间戳必须在服务器当前时间的“ENVELOPE_MAX_AGE_SECONDS”（默认 60 秒）内。这些机制共同解决了四种未经授权的访问场景：

- **录制的重播：**未经授权的用户捕获有效信封并稍后重新提交。随机数已经被看到了。
- **延迟递送：** 在运输途中截获的信封在新鲜度窗口之后到达。时间戳检查失败。
- **陈旧请求重用：** 重新提交代理缓存的旧信封。随机数和时间戳检查均失败。
- **预先计算的伪造：**未经授权的用户无法预测未来的随机数来预先签署信封。

### 步骤 5：客户端密钥生成

该架构的一个关键安全属性是私钥在本地生成，并且永远不会传输到任何外部系统。该应用程序使用 Python 加密库生成 RSA 2048+ 密钥对。它构造一个仅包含公钥和主题信息的 CSR，并通过“pkcs10enroll”端点仅将 CSR 发送到 EJBCA。

EJBCA 验证 CSR、应用证书配置文件（7 天有效期、密钥使用限制）、使用 CA 密钥对其进行签名，然后返回颁发的证书。然后，应用程序将本地保存的私钥与返回的证书捆绑到 PKCS12 容器中，并将其存储在 AWS Secrets Manager 中。

此设计提供了几个安全属性：

- 用户的私钥仅在登录时使用来签署委托断言。它永远不会与代理共享。
- 每个代理的私钥仅供该代理用来签署信封。它永远不会在代理之间共享。
- EJBCA 从不查看或存储私钥。它纯粹作为证书颁发机构运作。
- 如果 Secrets Manager 受到未经授权的访问，则 PKCS12 密码（单独存储）会添加一个附加层。
- 密钥材料可以通过在下次登录时使用新的 CSR 重新注册来独立轮换。

### 第 6 步：完成注销和凭证吊销

注销会触发撤销级联，立即使所有未完成的凭据失效。该序列在完成后不会产生剩余的有效凭据：

- **撤销 EJBCA 中的用户证书：** 这会立即使所有未完成的委派失效，因为委派验证会通过 OCSP 实时检查用户的证书。
- **撤销所有三个代理证书：** 这会使所有未完成的签名信封失效，因为信封验证包括 OCSP。
- **从 AWS Secrets Manager 中删除所有密钥：** 使用“ForceDeleteWithoutRecovery”立即删除，无需恢复窗口。
- **终止 Keycloak 会话：** 通过会话终止端点使范围缩小的令牌无效。

撤销级联是关键的安全属性。在PKI层撤销单个用户证书会立即撤销所有下游代理权限，而无需单独撤销令牌、删除会话或联系每个代理。 OCSP 提供了传播机制，并且由于每个请求都会检查 OCSP，因此效果是立竿见影的。

## 安全考虑

此架构中的设计选择解决了对生产多代理部署很重要的几个安全属性。

私钥隔离。用户的私钥仅在登录流程中存在，并且仅用于签署委托。代理密钥的范围仅限于每个代理，并且从不共享。任何关键材料都不会跨越信任边界。

委派与凭证共享的比较。代理通过加密链（委托代理指纹到信封签名）证明其权限，而无需持有用户凭据。如果代理密钥被公开，则只会公开该代理的密钥，而不是用户的密钥。

受众范围的代币。 RFC 8693 令牌交换生成仅由 MCP 服务器接受的令牌。无意中泄露的缩小范围令牌无法针对 Keycloak 管理 API、其他服务甚至不同的 MCP 服务器实例进行身份验证。

预防重播。每个请求的随机数和 60 秒新鲜度窗口的组合确认每个请求都是一次性的且有时间限制的。 `ReplayCache` 是线程安全且自清理的。

故障关闭设计。每次验证失败都会导致立即拒绝。 OCSP 无法访问：拒绝。无效签名：拒绝。过期时间戳：拒绝。重播随机数：否认。错误的受众：否认。安全检查没有适度降级。

撤销级联。撤销一份用户证书会立即使所有委派、所有代理权限和所有未完成的信封失效。这是通过实时 OCSP 传播的，无需清除单独的凭据。

仅前向信任链。 “ALLOWED_CALLER_ROLES”映射强制只有“orchestrator-agent”可以调用“mysql-agent”和“email-agent”。子代理不能互相调用，不能向上调用编排器，也不能冒充用户。

### 人工智能治理考虑因素

PKI 架构为该系统中的 AI 代理提供了内置的行为边界。生产部署应使用 Amazon Bedrock Guardrails 来强制执行内容过滤、主题避免和对代理响应的接地检查，以及本文中描述的基于 PKI 的访问控制。

- **工具边界**：AI 代理在严格的工具约束下运行。它只能调用预定义的 MCP 工具（`execute_sql`、`describe_table`、`list_tables`）。代理无法执行任意代码或访问其证书范围之外的资源。
- **人工监督**：所有代理操作都会被记录并可审核。 AWS CloudTrail 捕获 AWS API 调用，MCP 服务器使用完整的身份链（用户、代理、时间戳和操作）记录每个经过验证的工具调用。
- **数据处理**：用户查询和结果保留在经过身份验证的会话边界内。受众范围的令牌限制对特定 MCP 服务器实例的数据访问。
- **基于证书的行为边界**：代理只能调用他们持有有效证书的工具。没有“mysql-agent”证书的代理无法访问数据库，无论 LLM 可能生成什么指令。

## 扩展架构

您可以扩展此架构以支持其他代理类型、水平扩展和多租户隔离。以下段落描述了最常见的扩展点。

- 要添加新的代理类型，您只需在“ALLOWED_CALLER_ROLES”中添加一个条目。证书在登录时自动颁发，并且委派断言动态包含新代理的指纹。无需更改基础设施。
- 对于水平扩展，您可以在负载均衡器后面以高可用性模式部署 EJBCA 的 OCSP 响应器。 AWS Secrets Manager 支持适合此工作负载的高请求率。 Amazon ElastiCache 可以支持“ReplayCache”以进行分布式部署。
- 要强化生产架构，您可以通过 AWS CloudHSM 或本地 HSM 使用硬件安全模块 (HSM) 支持的 EJBCA 签名密钥。 OCSP 响应装订可减少验证延迟，证书透明度日志提供已颁发证书的完整审核跟踪。
- 对于多租户部署，您可以创建每租户证书颁发机构或每租户委派机构以进行加密租户隔离。与每个租户的 AWS 账户相结合，可以在租户之间提供强大的隔离。
- 您还可以使用 AWS Identity and Access Management (IAM) 角色来补充基于 PKI 的代理身份。使用 PKI 进行代理间身份验证，使用 IAM 进行 AWS 服务授权。两个系统独立工作，提供纵深防御。

## 结论

在这篇文章中，我们演示了一个参考架构，用于使用 X.509 PKI 与 Keyfactor EJBCA 和 AWS 服务来保护 AI 代理通信。该架构通过四种互补机制解决了多智能体人工智能系统中的基本身份差距：

- 签名的请求信封为每个代理间呼叫提供加密的所有权证明，使未经授权的一方更难以伪造代理的身份或重放其请求。
- 用户签名的委托断言将授权与凭证共享分离。代理证明他们有权代表用户行事，而无需持有用户的私钥或完整会话令牌。
- RFC 8693 受众范围的令牌将任何令牌披露的暴露范围限制到单个服务边界。
- 实时 OCSP 吊销检查确认凭证吊销在整个系统中立即生效。吊销一份用户证书将立即终止所有下游代理权限。

这种架构与框架无关。虽然我们使用 AWS Strands Agents SDK 和 FastMCP 进行了演示，但相同的 PKI 模式也适用于 LangChain、CrewAI、AutoGen 或使用工具协议的任何其他多代理框架。随着人工智能代理的激增并获得越来越敏感的操作，代理身份基础设施从可选变为必需。
