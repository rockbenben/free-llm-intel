# Social Department 如何构建具备文化感知能力的视频发现系统

*本文由 AWS 的 Mariah Miller、Sirajus Salekin 与 Social Department 的 Nicholas Chase 共同撰写。*

娱乐营销团队管理着横跨制片厂、电视网和流媒体应用的数万个视频素材。大多数营销活动都始于同一个视频发现问题：在素材中找到那个能与受众产生共鸣的瞬间。简报一到，倒计时就开始，而他们需要的东西几乎从来不是数据库能够描述的。

语义搜索本身存在上限：它只能回答你能够清晰表述的问题。让它找一个拿着咖啡杯的角色，它会在上千集内容里找出每一个咖啡杯。而真正驱动娱乐营销活动的查询与此截然不同。它们是判断力的问题：一档节目里哪个瞬间会传播开来，哪句台词值得引用，哪一帧画面能成为梗图。

这些问题无法输入搜索框。回答它们需要搜索索引所不具备的两样东西：针对特定内容库，对“值得引用”或“适合做梗图”的编辑层面定义；以及对内容库之外正在流行什么的持续更新视角。过去，回答这些问题意味着让一位对该节目有深入了解的人观看一周素材，而这样的人无法在整个片库规模上扩展。

在本文中，我们介绍娱乐营销领域的 AI 操作系统 Social Department 如何着手将这些编辑层面的问题编码为可执行的检索流水线。其成果就是 QuickSearch——一组单动作查询，无需营销人员描述需求即可返回他们想要的片段：Shareable Scenes、Quotable Quotes、Memeable Moments 和 Trend Align。

该解决方案中的模型运行在 Amazon Bedrock 上，因此客户数据始终处于 AWS 数据边界之内。数据不会与模型提供方共享，也不会用于训练底层模型。

Social Department 的负责任 AI 理念是：AI 提出建议，人来做决定。在生产环境中，代码会将生成输出与原始素材核对（例如，如果某句台词不在剧集文字记录中，就会被丢弃）。Amazon Bedrock Guardrails 帮助筛查客户搜索文本中的 prompt 攻击，并且客户团队中的人员会在每条帖子发布前进行审核。

Social Department 拥有流水线架构、检索系统以及每个动作背后的编辑标准。AWS Premier Tier Services Partner TrackIt 按照该设计进行实施与交付。[Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的 TwelveLabs Marengo 3.0 和 Pegasus 1.2 模型提供了流水线所依赖的场景级视频推理能力。AWS 提供基础设施、模型访问（包括 Anthropic 的 Claude 模型）以及 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/)，并使用其 serverless 选项 Amazon OpenSearch Serverless 进行检索。

**关于范围的说明：**本文描述系统中属于 AWS 的部分：摄取与索引流水线、检索路径以及运行它们的服务。Social Department 自有的组件，包括其媒体与数据主干、内容分析与发现引擎、编辑标准和评估机制，仅在理解架构所需的深度上加以说明。下文提及的服务是本文的重点，并非 Social Department 完整系统的清单。

## 关于 Social Department

Social Department 是面向娱乐营销的 AI 操作系统，服务于大型制片厂、电视网、流媒体平台和 FAST 应用。它跨客户的整个内容库实现活动策略、素材创作、发布和效果优化的自动化。其中大多数功能都依赖于首先定位到素材中的正确瞬间，而语义片段发现从一开始就一直是产品的核心。

## 为何仅有语义搜索并不够

娱乐营销受制于两个通用搜索层无法满足的约束。

### 有价值的查询恰恰是无人能表述的那些

营销人员可以描述一个物体、一个地点或一句台词，却无法描述什么会传播开来。这种“这个瞬间能打动人、那个不能”的判断力，正是这份工作中真正的技能。它过去无法自动化，因为它取决于对受众行为的了解，而非视频包含什么内容。一个只理解内容的搜索层需要人来提供意图，而要提供好这个意图，前提是已经看过那部剧。

### 趋势信号存在于内容库之外，且遵循不同的节奏

再强的视频理解能力也无法告诉你今天早上受众在谈论什么。这类信息产生在内容库之外，并且每小时都在变化，而内容库只有在添加新内容时才会变化。一个能回答这类查询的系统必须持续获取趋势信号，并在请求到来时将其与内容库对照。

这一区别决定了核心架构决策：内容理解与趋势获取作为独立流水线按各自的调度运行，只有在用户选择某个 QuickSearch 动作时才汇合。

## 解决方案概览

借助 QuickSearch，团队可以以一种不同的方式与视频库交互——由系统主动提出建议，而非被动等待。它提供四个动作，每个动作都有自己的检索策略、编辑标准和排序模型。接下来的逐步介绍会说明各自的实现方式。此处的列表先介绍它们的作用。

- *Shareable Scenes* 呈现内容充实、自成一体的场景，例如较长的对峙、高潮和重头戏，倾向于展开充分的桥段而非短暂的反应镜头。
- *Quotable Quotes* 找出有力且值得引用的对白，片段长度限制在较短范围；在该剧集有相关信号可用时，会对已被证实传播过的台词加权。
- *Memeable Moments* 识别出适合做梗图的单帧画面，并生成基于该帧实际内容的文字说明。它会通过专门的提取与评分步骤来选定这一帧，而非直接取缩略图。
- *Trend Align* 获取当前正在流行的趋势，并在内容库中找到与之确有联系的瞬间，从而使多年前播完的剧集能够重新进入当下的热议。

除此之外，Social Department 还保留自然语言搜索，以覆盖这些动作未涉及的需求；同时提供基于图片的搜索，即给出一张参考图片，返回整个内容库中视觉上相似的内容。

## 架构详解

系统包含三个按独立调度运行的部分。其中两部分负责获取并结构化信息，第三部分则将用户的一次选择解析为跨越二者的多阶段检索操作。

### 内容理解流水线

该流水线让内容库变得可读。它在摄取时异步工作。[AWS Step Functions](https://aws.amazon.com/step-functions/) 状态机端到端编排大约二十多个 Python [AWS Lambda](https://aws.amazon.com/lambda/) 函数。以下步骤追踪一个视频从上传到成为已索引片段的全过程。

- **上传与触发 –** 视频进入每个团队各自的 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) bucket。经 [Amazon EventBridge](https://aws.amazon.com/eventbridge/) 路由的 S3 Object Created 事件会启动 Step Functions 执行。
- **元数据 –** 第一个 Lambda 函数对照 Social Department 的媒体与数据主干解析出片名、团队、剧集和公开标识符，将视频元数据写入 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/)，并将该素材标记为处理中。
- **转码 –** AWS Elemental MediaConvert 将该素材转码为 480p H.264，并启用自适应去隔行；它使用 Step Functions task token，使状态机等待任务完成而非轮询。
- **镜头检测 –** [Amazon Rekognition](https://aws.amazon.com/rekognition/) 通过 [Amazon Simple Notification Service (Amazon SNS)](https://aws.amazon.com/sns/) 回调执行异步镜头分割检测。第二个 Lambda 函数将原始镜头合并与切分，形成时长约 10–20 秒、贴合内容语义的区间。流水线后续部分正是在这些区间上展开。在每个区间内，Social Department 以固定间隔对嵌入进行分段，这一设计选择是针对剧集类电视的节奏调整的。被索引的片段较短且长度固定，但其所处的区间则跟随镜头剪辑。
- **嵌入 –** 各区间在 Step Functions Distributed Map 中处理。每次调用通过异步调用将起止时间传递给 Amazon Bedrock 上的 TwelveLabs Marengo 3.0。该调用生成涵盖视觉、音频和文字记录维度的多模态嵌入，此路径上无需拆分文件。
- **场景描述 –** Amazon Bedrock 上的 TwelveLabs Pegasus 1.2 在并行的 Distributed Map 中逐段运行，生成场景级的叙事描述、情绪、主题、对白类型和叙事位置，这些内容构成排序模型后续推理所依据的文本层。Pegasus 接收的是预先切分好的文件而非时间区间，因此会由另一个 Lambda 函数先对每个区间进行切分，并在两侧各留几秒填充，以保留场景转场。
- **转录与增强 –** 与嵌入并行，流水线运行带自动回退的语音转文字，并使用 Amazon Rekognition 提取屏幕文字、视觉标签及用于角色锚定的人脸集合。Amazon Bedrock 上的 Anthropic Claude 模型提取该剧的角色图谱，并生成剧集层级的概念和角色设定。
- **索引 –** Amazon Bedrock 将嵌入输出写入 Amazon S3。最后一个 Distributed Map 随后将嵌入、文字记录、屏幕文字、场景描述字段和标签索引到 Amazon OpenSearch Serverless 中。

该流水线端到端采用事件驱动。每个 Lambda 任务都通过指数退避进行重试。场景描述阶段额外增加了带完整抖动的专用节流重试。非关键增强步骤会优雅降级，而不会导致整次运行失败；硬性失败则会路由到错误处理器，由后者记录原因并将该素材标记为失败。

为 Marengo 进行同区域暂存。Marengo 仅在一组特定的 AWS Region 中可用。Amazon Bedrock 中的异步调用会从与 endpoint 相同的 Region 中的 Amazon S3 bucket 读取输入，并将输出写入该 bucket。流水线正是围绕这些参数构建的。它会在调用 Marengo 之前将每个视频暂存到 US East (N. Virginia) 的专用 bucket 中，然后从同一 bucket 读回嵌入输出。其余基础设施仍留在各自的本地 Region，而每个嵌入任务则与模型一同运行。有关各 Region 的模型可用性，请参阅 [Amazon Bedrock 中各 AWS Region 的模型支持情况](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

### 趋势获取

该流水线持续运行，独立于任何内容库，正是它让 Trend Align 成为可能。

- **两条通道，一个数据源 –** 趋势数据通过两条机制刻意不同的通道获取。每日通道使用 Amazon EventBridge cron，每个地区每天定时抓取一次，时间对准各地区的当地早晨，而非固定的 UTC 时间。热度通道（Heat Seeker）读取处于早期阶段、按势头排序的趋势，仅在用户明确要求时抓取，如果已存储的数据足够新则直接复用。这种拆分是出于成本考虑。cron 无论是否有人在工作，每次触发都会为所有地区付费；而由 TTL 支撑的按需抓取在清淡的日子里不产生任何成本。
- **各地区数据源是彼此独立的群体 –** 趋势按地理区域获取，目前有四个数据源：全球、美国、英国和澳大利亚。一个地区并非对全球列表的筛选。每个地区都按自己的调度独立发现趋势，因此同一天的趋势在各地之间确实不同。
- **解读与编辑关口 –** 原始趋势数据不会展示给客户。Amazon Bedrock 上的 Anthropic Claude Haiku 将每条趋势规范化到 Social Department 自有的类别体系，统一其描述，对近似项去重，并限制每个类别最终保留的数量。在同一轮处理中，一个编辑关口会剔除主要内容涉及死亡、暴力、自残、自然灾害、政治、抗议、犯罪或公共卫生危机的趋势。无论这类趋势热度多高，都不会提供给营销客户。被剔除的趋势会被记录下来，以免每次抓取都重复筛查。
- **作为一等公民行的存储 –** 经过解读的趋势按稳定指纹进行 upsert，因此同一趋势日复一日会复用其数据行和缓存的派生结果。不再出现的趋势会逐渐淘汰，最终下线。刷新任务会获取一个 claim，确保两次刷新不会重叠。

Quotable Quotes 还会使用第二个更窄的输入：外部对白热度信号，仅用于对已经传播过的台词加权。它在设计上是可选的，因此如果该信号不可用，台词只是不会获得加权，而不会导致任务失败。

### QuickSearch 任务层

在这一层，一次选择会转化为一套检索策略。它异步执行每个动作，并返回一组经过排序的片段。

- **请求路径 –** Web 应用是一个 React 单页应用，通过 [Amazon CloudFront](https://aws.amazon.com/cloudfront/) 从 Amazon S3 提供服务。其 API 是运行在 AWS Lambda 上的 Fastify 服务，位于 [Amazon API Gateway](https://aws.amazon.com/api-gateway/) HTTP API 之后，并使用 [Amazon Aurora PostgreSQL-Compatible Edition](https://aws.amazon.com/rds/aurora/) 存储关系型数据。
- **异步执行 –** 选择某个 QuickSearch 动作会向 Amazon DynamoDB 写入一条任务记录，并将一条 [Amazon Simple Queue Service (Amazon SQS)](https://aws.amazon.com/sqs/) 消息入队。一个 worker Lambda 函数取出消息并运行该动作对应的流水线。瞬时故障通过 Amazon SQS 重试，而被判定为不可重试的错误则直接进入死信队列。
- **查询构造 –** 每个动作都会根据其编辑标准展开为一组检索查询。对于 Trend Align，大部分专有工作就在这里：趋势以文化话题的形式到来，而视频索引能够匹配的是画面和音频中出现的内容。将二者桥接起来是一个翻译问题，由 Amazon Bedrock 上的 Claude 模型处理。输出是一组索引可以直接执行的查询。
- **多通道检索 –** 每条查询都会交给处理混合检索的搜索 Lambda 函数。Marengo 将查询嵌入一次，形式可以是文本、图片，或图文组合查询。嵌入后的查询随后在六个 k-NN 通道（视觉、音频、文字记录、屏幕文字、场景描述和标签）以及七个 BM25 文本通道上执行。各模态的权重来自查询本身。查询类型路由会调整通道加权，使对白类查询更倚重文字记录和情绪通道，而视觉类查询则抑制这些通道。
- **融合与重排 –** 各通道通过 Reciprocal Rank Fusion 合并，该方法使用排名位置而非原始分数，从而避免 k-NN 与 BM25 相似度之间的量纲不匹配。随后，排名靠前的候选会经过 Amazon Rerank 模型——一个通过 Amazon Bedrock 中的 Rerank API 调用的 cross-encoder——进行最后一轮文本对文本的相关性处理，之后再对最优结果执行 Claude 验证步骤。
- **聚合 –** 索引中存储的是较短的固定长度片段。在返回结果之前，视觉嵌入相似度较高的相邻片段会被合并为连贯的瞬间，因此针对某个场景的查询返回的是一个 20–60 秒的结果，而不是同一场景的五段碎片。
- **编辑排序 –** Amazon Bedrock 上的 Claude 模型依据该动作的编辑标准，对去重并增强后的候选进行排序。候选池设有上限，以免模型输出被截断。模型按动作选择：在文化层面的召回会改变答案时使用 Claude Sonnet，在任务边界明确且成本敏感时使用 Claude Haiku。
- **帧提取 –** 对于 Memeable Moments，一个专门的 Lambda 函数会从胜出的片段中提取若干候选帧，并使用 Amazon Rekognition 对人脸质量、对图像清晰度进行评分。随后它以全分辨率重新提取胜出帧，裁掉黑边，并返回一个签名的 Amazon CloudFront URL。
- **缓存 –** 完成的结果存储在 Amazon DynamoDB 中并复用 30 天。缓存键包含每个动作的流水线版本，对于 Trend Align 还包含当前趋势集合的哈希，因此标准变更、模型升级或趋势目录刷新都会干净地使缓存失效，而不会返回过时的答案。

## 设计决策

三个选择让具备文化感知的检索变得可行。

### 将趋势获取与内容理解分离

内容库在添加新内容时才会变化。趋势每天都在变化，而早期趋势变化得更快。将二者耦合意味着要么依据新信号重新处理内容——这在计算上难以承受——要么提供过时的趋势判断。将它们保持为独立的流水线、在请求时才汇合，意味着信号始终保持最新，而无需再次触碰内容库。多年前播完的剧集也能重新进入当下的热议。

### 将每个动作拆分为低成本检索与高成本判断

朴素的设计是把一个大模型放在整个内容库之前。QuickSearch 则使用低成本、高召回的向量与关键词检索来构建候选池，然后只在数量受限的真实候选上投入模型预算进行排序。上限依据排序模型的输出 token 限制来设定，因为中途被截断的排序器会静默地丢弃结果。这也使 Amazon Bedrock 的单次查询成本保持可预测：一次嵌入调用、一次重排调用以及数量很少且固定的 Claude 调用，与内容库规模无关。

### 让缓存失效成为明确的编辑行为

结果会缓存 30 天。若不加以干预，某个动作的标准或模型发生变化后，用户要等到缓存过期才能看到变化。每个动作都带有一个流水线版本号，在改变其行为的同一次变更中，该版本号会递增。递增会立即让先前的结果失效，因此编辑判断是作为产品的版本化变更来细化的，而不是在每次查询时重新争论。

## 成果

Social Department 报告了客户使用 QuickSearch 所取得的以下成果。这些是该公司自身的观察，而非受控基准测试。

- **此前不可能的查询如今只需一次选择 –** 要识别粉丝群体奉为经典的瞬间，或对特定受众而言能成为梗图的画面，过去需要一位对该剧集非常熟悉的人观看素材，而且无法在片库规模上扩展。
- **发现不再依赖手动逐段浏览 –** 据 Social Department 称，过去需要 3–4 天的活动素材发现工作，如今使用 QuickSearch 约 10 分钟即可完成。营销人员原本花在逐集拖拽寻找合适瞬间上的时间，得以回到更高价值的营销工作中。
- **营销人员无需编写查询即可获得候选片段 –** 这消除了搜索者必须足够了解内容库、才能描述自己想要内容的前提；正是这一限制让素材发现依赖于少数看过该剧的人。
- **归档片库变得可检索 –** 那些因已完结、已归档且无法被元数据搜索找到而实际难以触达的内容，如今可用于营销工作，多年前停播的剧集也能重新进入当下的文化讨论。
- **行业认可 –** Social Department 在 NAB 2026 上作为顶尖初创公司亮相，并在 Entertainment Loft 中获得展示。

> “这里的难点从来都不是搜索本身，而是想清楚要搜索什么：如何把优秀营销人员凭直觉完成的事情——哪个瞬间能打动人、为什么——转化为系统能够执行上千次的标准。我们在这上面花了很长时间。与 TrackIt 在紧凑的时间表下合作，我们从规格说明走到了 NAB 上的现场演示。TwelveLabs 让我们具备理解素材内容的智能，AWS 则为我们提供了在片库规模上做到这一切的基础设施。我们的职责就是知道该把它指向哪里。”
>         — Jonathan Verk，Social Department 创始人兼 CEO

> “媒体行业的每个人都在谈给自己的内容库添加元数据，但给内容打标签本身并不能收回成本。这个项目让我喜欢的一点是它形成了闭环。它把躺在归档库里的剧集变得对真实营销活动有用，而且成本足以支持每天运行。这正是行业一直缺失的部分。”
>         — Chris Marchitelli，TrackIt 副总裁

## 我们的经验教训

以下是该项目中最突出的四条经验。

### 难点在于表达判断力，而非检索内容

检索在很大程度上已经得到解决。尚未解决的是如何足够精确地表达意图，使检索在没有营销专家参与的情况下依然有用。大部分工程投入都用在了定义什么才算一个可分享的场景或一帧适合做梗图的画面，并且定义要足够严谨，能够在调性各异、受众不同的内容库中反复执行。这一定义来自一个常态化评估机制，其中包含带编号的迭代，每一轮都依据各剧集的真值集和一个受跟踪的基线来衡量，从而依据结果而非直觉来调整标准。

### 基于 Amazon Bedrock 的多模型架构

QuickSearch 采用多模型架构，每个模型都被分配到最适合它的工作。Claude Haiku 处理边界明确、成本敏感的输出，Claude Sonnet 处理那些文化层面的召回会改变答案的任务。TwelveLabs Marengo 生成多模态嵌入，TwelveLabs Pegasus 提供场景级视频推理，Amazon Rerank 模型负责重排。Amazon Bedrock 使这一架构的构建和运行切实可行。来自 TwelveLabs、Anthropic 和 Amazon 的模型可通过一个 API 获取，因此当实测质量发生变化时，Social Department 可以更换某项任务背后的模型，而无需构建新的集成。异步调用可在片库规模上运行耗时较长的视频嵌入任务，Rerank API 则无需单独托管基础设施即可增加一轮相关性处理。Amazon Bedrock Guardrails 可在同一服务中帮助筛查搜索输入，客户数据始终处于 AWS 数据边界之内。由于 Amazon Bedrock 是全托管的，团队无需自行运维任何模型服务基础设施。

### 会衰减的信号需要专属架构

把趋势数据当作内容流水线的又一个输入来处理是行不通的，因为二者的生命周期互不相容。及早认识到内容库中的内容与实时文化是两个独立的系统，各自拥有不同的刷新频率、存储和失败模式，正是后续整个设计所依赖的决策。

### 清晰的层边界让多方协作项目得以成立

Social Department 拥有流水线架构、检索系统和编辑标准。TrackIt 按照该架构进行构建和交付，TwelveLabs 提供视频理解模型。AWS 与 AWS 生成式 AI 创新中心为 AWS 相关组件提供基础设施、模型访问和解决方案架构。由于每一方的职责范围都清晰界定，8 周的生产时间表得以守住。

## 结论

我们介绍了 Social Department 如何与 TrackIt、TwelveLabs 和 AWS 合作，运用自身的流水线与检索架构，为娱乐营销构建具备文化感知能力的视频发现系统。本文所描述的这一层由若干 AWS 组件构成。TwelveLabs Marengo 负责多模态嵌入，TwelveLabs Pegasus 负责场景级视频推理，二者均运行在 Amazon Bedrock 上。Amazon Bedrock 上的 Anthropic Claude 模型负责解读和编辑排序，Amazon OpenSearch Serverless 负责混合检索。AWS Step Functions、AWS Lambda、AWS Elemental MediaConvert、Amazon Rekognition、Amazon DynamoDB 和 Amazon SQS 则运行其周围的流水线。其成果是一组单动作查询：返回受众已经在意的片段、他们已经在引用的台词、能够成为梗图的画面，以及与当下流行趋势相联系的瞬间。

要开始在 AWS 上实现多模态视频理解，可以了解 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 和 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/)。要了解更多关于 Amazon Bedrock 上可用的 TwelveLabs 模型，请访问 [AWS Marketplace 上的 TwelveLabs 页面](https://aws.amazon.com/marketplace/pp/prodview-qr4lokt4ueeu2)。要了解 AWS 生成式 AI 创新中心如何帮助你的组织，请访问 [AWS 生成式 AI 创新中心页面](https://aws.amazon.com/ai/generative-ai/innovation-center/)。
