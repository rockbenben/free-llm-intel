# 用 Amazon Bedrock 构建可靠的 Agentic AI 方案：从 Pushpay 的 GenAI 评估之路学到的经验

*本文由来自 Pushpay 的 Saurabh Gupta 和 Todd Colby 共同撰写。*

[Pushpay](https://pushpay.com/) 是一个市场领先的数字化奉献与互动平台，旨在帮助教会和信仰类组织高效地推动社区互动、管理捐赠并强化慷慨奉献的募款流程。Pushpay 的教会管理系统为教会管理者和事工负责人提供由洞察驱动的报表、捐赠者发展看板和财务流程自动化。

借助生成式 AI 的能力，Pushpay 开发了一项专为事工独特需求打造的创新型 agentic AI 搜索功能。该方案使用自然语言处理，让事工人员用日常英语提问，并从其社区数据中实时生成可付诸行动的洞见。这项 AI 搜索功能解决了事工负责人面临的一个关键难题：无需具备技术专长，也能快速获取社区洞察。例如，事工负责人可以输入“显示那些在某个小组里是成员、但今年还没有奉献的人”或“显示那些没有参与我教会活动的人”，并利用结果采取有意义的行动，更好地支持社区中的个人。多数社区领袖时间紧张、缺乏技术背景；他们可以用这套方案，通过自然语言查询在数秒内获得关于会众的有意义数据。

通过让事工人员更快地获取社区洞察，这项 AI 搜索功能支持了 Pushpay 鼓励慷慨奉献、促进教会与社区成员之间连接的使命。早期采用该功能的用户反馈，这套方案把他们的洞察获取时间从数分钟缩短到数秒。为达成这一结果，Pushpay 团队在 [Amazon Web Services（AWS）](https://aws.amazon.com/) 上利用 agentic AI 能力构建了该功能，同时落实了稳健的质量保障措施，并建立了快速迭代的反馈闭环以持续改进。

本文带你走过 Pushpay 构建这一方案的历程，并探讨 Pushpay 如何用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 打造自定义的生成式 AI 评估框架，在 AWS 上实现持续的质量保障和快速迭代的反馈闭环。

## 方案概览：AI 驱动的搜索架构

该方案由若干关键组件构成，它们协同工作以提供增强的搜索体验。下图展示了方案架构图和整体工作流。

![图 1：AI 搜索方案架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/01/22/solution_architecture.jpg)

图 1：AI 搜索方案架构

- **用户界面层：** 方案始于 Pushpay 用户通过现有的 Pushpay 应用界面提交自然语言查询。借助自然语言查询，教会事工人员无需学习新工具或新界面，就能利用 AI 能力获得数据洞察。
- **AI 搜索 agent：** 系统的核心是 AI 搜索 agent，它由两个关键组件构成：  **System prompt**：包含大语言模型（LLM）的角色定义、指令和应用说明，用于引导 agent 的行为。 **动态 prompt 构造器（DPC）**：根据用户的具体信息自动构造额外的定制 system prompt，例如教会上下文、示例查询和应用筛选项清单。它还会用语义搜索，在数百个可用的应用筛选项中只挑选相关的那些。DPC 提升了响应准确性和用户体验。
- **Amazon Bedrock 高级特性：** 该方案使用了以下 Amazon Bedrock 托管服务：  [**Prompt caching**](https://aws.amazon.com/bedrock/prompt-caching/)：通过缓存频繁使用的 system prompt 来降低延迟和成本。 **LLM 处理**：使用 Claude Sonnet 4.5 处理 prompt，并生成应用所需的 JSON 输出，以便把想要的查询结果作为洞见展示给用户。
- **评估系统：** 评估系统实现了一套闭环改进方案：用户交互会被埋点、捕获并离线评估。评估结果汇入看板，供产品和工程团队分析，并驱动对 AI 搜索 agent 的迭代改进。在此过程中，数据科学团队收集一个黄金数据集，并基于真实用户查询加已验证的响应持续维护该数据集。

## 最初没有评估的方案所面临的挑战

为打造 AI 搜索功能，Pushpay 开发了 AI 搜索 agent 的第一个版本。该方案实现单个 agent，并配置了精心调优的 system prompt，其中包含系统角色、指令、用户界面的工作方式，以及每个筛选工具及其子设置的详细说明。system prompt 使用 [Amazon Bedrock prompt caching](https://aws.amazon.com/bedrock/prompt-caching/) 缓存，以降低 token 成本和延迟。agent 借助 system prompt 调用 Amazon Bedrock 上的 LLM，生成 JSON 文档，Pushpay 的应用再用它来应用筛选条件并向用户呈现查询结果。

不过，这第一个版本很快暴露出一些局限。虽然它在基础业务查询上表现出 60-70% 的成功率，但团队遭遇了准确率平台期。对 agent 的评估是一个手工且繁琐的过程。考虑到用户查询的多样光谱，以及应用覆盖了 100 多个不同的可配置筛选项，想把 system prompt 调过这一准确率阈值颇为困难。这些成为团队走向生产道路上的关键阻碍。

## **通过增加自定义生成式 AI 评估框架来改进方案**

为应对衡量和改进 agent 准确率的挑战，团队实现了一个生成式 AI 评估框架，并将其集成到现有架构中，如下图所示。该框架由四个关键组件构成，它们协同工作以提供全面的性能洞察，并支撑数据驱动的改进。

![图 3：引入 GenAI 评估框架](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/01/22/genai_eval_framework-1024x605.jpg)

图 3：引入 GenAI 评估框架

- **黄金数据集：** 一个经过整理的黄金数据集包含 300 多条有代表性的查询，每条都配有其对应的预期输出，构成自动化评估的基础。产品和数据科学团队精心构建并验证了该数据集，以全面覆盖真实用例和边界情况。此外还有一个持续维护流程，不断加入有代表性的真实用户查询及其已验证结果。
- **评估器：** 评估器组件处理用户输入的查询，并使用 [LLM as a judge 模式](https://aws.amazon.com/blogs/machine-learning/llm-as-a-judge-on-amazon-bedrock-model-evaluation/)把 agent 生成的输出与黄金数据集进行比较。这种方法产出核心准确率指标，同时捕获详细日志和性能数据（例如延迟），供进一步分析和调试。
- **领域类别**：领域类别通过生成式 AI 领域摘要与人工定义的正则表达式（regular expression）相结合来构建，从而有效地对用户查询分类。评估器为每个查询判定领域类别，使基于类别的细致评估成为评估指标的一个额外维度。
- **生成式 AI 评估看板：** 该看板是 Pushpay 产品和工程团队的指挥中心，展示领域类别层面的指标，用于评估性能和延迟并指导决策。它让团队从单一的聚合得分转向细致的、基于领域的性能洞察。

**准确率看板：按领域定位弱点**

由于用户查询会被归入领域类别，看板结合了统计置信度可视化，使用 95% [Wilson 得分区间](https://en.wikipedia.org/wiki/Binomial_proportion_confidence_interval#Wilson_score_interval)来展示各领域层面的准确率指标和查询量。通过分类，团队可以按领域精确定位 AI agent 的弱点。在下面的示例中，“activity”领域的准确率明显低于其他类别。

![图 4：按领域定位 agent 的弱点](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/01/22/performance_by_domain-1024x462.jpg)

图 4：按领域定位 agent 的弱点

此外，下图所示的性能看板在领域类别层面可视化延迟指标，包括从 p50 到 p90 百分位的延迟分布。在下面的示例中，activity 领域的延迟明显高于其他领域。

![按领域识别延迟瓶颈](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/01/22/latency_by_domain-1024x460.jpg)

图 5：按领域识别延迟瓶颈

**通过领域层面的洞察做策略性放量**

基于领域的指标揭示了不同语义领域之间参差不齐的表现，为判断 agent 的有效性提供了关键洞察。Pushpay 利用这种细粒度可见性做出策略性的功能放量决策。通过在进行优化的同时暂时屏蔽表现不佳的类别（例如 activity 类查询），系统实现了 95% 的整体准确率。借助这种做法，用户只会体验到表现最好的功能，而团队则把其余部分打磨到生产标准。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/01/22/domain_rollout-1024x462.jpg)

图 6：通过领域层面的功能放量实现 95% 准确率

**策略性排序：聚焦高影响领域**

为系统化地安排改进优先级，Pushpay 采用了一个 2×2 矩阵框架，把各主题按两个维度绘制（如下图所示）：业务优先级（纵轴）和当前表现或可行性（横轴）。这种可视化把既有高业务价值、又有良好现有表现的主题放在右上象限。团队随后重点投入这些领域，因为从本就不错的水准进一步提升到面向业务主题的卓越 95% 准确率，所需的额外工作量更小。

实施遵循一个迭代循环：每一轮增强之后，他们都会重新分析结果，以确定下一批高潜力主题。这种系统化、循环往复的做法实现了持续优化，同时保持对业务关键领域的聚焦。

![图 7：领域类别优化的策略性排序框架](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/01/22/prioritization_framework-1024x837.jpg)

图 7：领域类别优化的策略性排序框架

**动态 prompt 构造**

从评估框架中获得的洞察带来了架构上的增强：引入动态 prompt 构造器。该组件通过对 agent 可以处理哪些领域类别做细粒度控制，实现了快速的迭代改进。结构化的字段清单——此前嵌在 system prompt 里——被改造为动态元素，使用语义搜索为每个用户查询构造与上下文相关的 prompt。这种做法基于三个关键的上下文维度来裁剪 prompt 中的筛选项清单：查询内容、用户画像和租户特有的需求。其结果是更精确、更高效的系统，既能生成高度相关的响应，又保持了持续优化所需的灵活性。

### **业务影响**

生成式 AI 评估框架成为 Pushpay 开发 AI 功能的基石，在三个方面带来了可衡量的价值：

- **用户体验**：AI 搜索功能把从提问到获得洞察的时间从约 120 秒（熟练用户需要手动在复杂 UX 中层层点击）缩短到 4 秒以内——15 倍的提速，直接帮助提升了事工负责人的工作效率和决策速度。该功能让数据洞察走向大众，使不同技术水平用户都能获得有意义的智能，而无需专业专长。
- **开发速度**：科学化的评估方法改变了优化循环。团队不再为 prompt 的改法争论，而是如今在数分钟内就能验证改动并衡量其对特定领域的影响，用数据驱动的迭代取代了冗长的讨论。
- **生产就绪度**：借助高性能领域，准确率从 60–70% 提升到 95% 以上，这为面向客户的上线提供了所需的量化信心，同时该框架的架构也支持在其他领域类别上持续打磨。

## **给你的 AI agent 之路的关键要点**

以下是 Pushpay 经验中的关键要点，你可以在自己的 AI agent 之路上借鉴。

**1/ 从第一天起就带着生产环境的意识来构建**

构建 agentic AI 系统本身并不复杂，但把它们扩展到生产环境却很有挑战。开发者应在概念验证阶段就采用可扩展的思维，而不是等到之后。早早实现稳健的链路追踪和评估框架，能为从实验走向生产提供清晰的路径。用这种方法，团队可以系统化地发现并解决准确率问题，避免它们变成阻碍。

**2/ 充分利用 Amazon Bedrock 的高级特性**

Amazon Bedrock prompt caching 通过缓存频繁使用的 system prompt，显著降低 token 成本和延迟。对于 system prompt 很大且稳定的 agent，这一特性对达到生产级性能必不可少。

**3/ 不要只看聚合指标**

聚合的准确率得分有时会掩盖关键的性能差异。通过在领域类别层面评估 agent 表现，Pushpay 发现了单一准确率指标无法捕捉的弱点。这种细粒度的做法支持有针对性的优化和有依据的放量决策，确保用户只会体验到表现良好的功能，而其他功能则同步打磨。

**4/ 数据安全与负责任的 AI**

在开发 agentic AI 系统时，要从一开始就考虑信息保护和 LLM 安全方面的因素，遵循 [AWS 责任共担模型](https://aws.amazon.com/compliance/shared-responsibility-model/)，因为安全要求会从根本上影响架构设计。Pushpay 的客户是教会和信仰类组织，它们是敏感信息的托管者——包括教牧关怀对话、财务奉献模式、家庭困境、代祷请求等等。在这个实现示例中，Pushpay 为在产品生态内合乎伦理地融入 AI 制定了清晰方针，维持严格的安全标准，确保教会数据和个人可识别信息（PII）留在其安全的合作生态内。数据只在应用了安全且适当的数据保护措施的前提下共享，并且绝不会用于训练外部模型。要进一步了解 Pushpay 在产品中融入 AI 的标准，请访问 [Pushpay 知识中心](https://support.pushpay.com/s/article/How-Pushpay-Builds-AI-for-Faith-Communities)，深入了解该公司标准的细节。

## 结论：通往生产就绪 AI agent 之路

Pushpay 从一个准确率 60–70% 的原型走到准确率 95% 的生产就绪 AI agent，这段历程表明：构建可靠的 agentic AI 系统，靠的不只是精巧的 prompt——它需要对评估和优化采取科学、数据驱动的方法。关键的突破并不在 AI 技术本身，而在于实现了一个建立在坚实可观测性基础之上的完整评估框架，它能对 agent 在不同领域中的表现提供细粒度的可见性。这种系统化的做法实现了快速迭代、策略性的放量决策和持续改进。

**准备好构建你自己的生产就绪 AI agent 了吗？**

- **探索 Amazon Bedrock**：用 [Amazon Bedrock](https://aws.amazon.com/bedrock) 开始构建你的 agent
- **实现 LLM-as-a-judge**：参照 [LLM-as-a-judge on Amazon Bedrock Model Evaluation](https://aws.amazon.com/blogs/machine-learning/llm-as-a-judge-on-amazon-bedrock-model-evaluation/) 中描述的模式，创建你自己的评估系统
- **构建你的黄金数据集**：开始为你自己的具体用例整理有代表性的查询和预期输出
