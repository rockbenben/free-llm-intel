在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上用智能体式 AI 扩展云迁移，会提出一个实际问题。一个大型迁移项目的哪些部分属于一个托管服务，哪些部分需要定制自动化？一个企业项目在 300 多个应用和一个固定财年期限上回答了这个问题。本文中的四智能体模式，把一个应用的 IaC（基础设施即代码）开发时间从 3–4 周缩减到几分钟，基于内部项目跟踪数据。

这一模式与 [AWS Transform](https://docs.aws.amazon.com/transform/) 并行运行，而非取代它，作为一个在你项目需要之处加上定制智能体的混合体。AWS Transform 覆盖迁移和现代化工作，[AWS Database Migration Service (AWS DMS)](https://docs.aws.amazon.com/dms/) 覆盖数据库层。本文中的智能体附加到那些服务上，并携带另一项要求：通过你组织构建和维护的 Model Context Protocol (MCP) 工具触达源和目标。

AWS Professional Services 为有该要求的项目构建一套专用 AI 智能体。这些智能体使用 [Strands Agents SDK](https://strandsagents.com/)，并运行在 Amazon Bedrock AgentCore 上——一个以任意框架或模型大规模构建、连接并优化智能体的平台。每个智能体通过 AgentCore Gateway 暴露的 MCP 工具触达其源和目标。

在本文中，你探索一个用于 MCP 连接环境的四智能体模式的架构。你还会看到定义一个智能体、把它连接到其工具、并应用负责任的 AI 控制的代码。该模式含四个智能体：

- Intake Agent，通过 MCP 工具从文档和协作系统读取迁移输入。
- IaC Agent，生成本着你的、组合你已批准内部模块的 IaC。
- Migration Intelligence and Governance Agent（迁移智能与治理智能体），在你自己的项目工具内做报告和治理。
- 用于切换（cutover）后运维的 Site Reliability Engineering (SRE) Agent。

要跟随本文，你需要一个 AWS 账户，可访问 Amazon Bedrock AgentCore 和 Amazon Bedrock 基础模型。你还需要熟悉 Strands Agents SDK 和 MCP server 模式，加上你组织所用的 IaC 工具。首先确认某个 AWS 托管服务是否已经覆盖你的迁移路径。

## 何时适用这一模式

AWS Transform 作为一个托管服务，为服务器、网络、大型机、.NET 和应用代码工作负载提供迁移和现代化，AWS DMS 覆盖数据库。这一模式为那些仍然专属于你组织的要求添加智能体。

在本文所描述的项目上，三个条件同时成立。

- **MCP 连接的源和目标**：持有迁移输入的系统，以及接收输出的系统，通过交付团队构建和维护的 MCP 工具来触达。它们包括一个持有安全标准的内部 wiki、一个工单系统、一个协作平台，以及一个内部开通 API。
- **组织特定的 IaC 组合**：生成的基础设施代码必须组合一个由安全办公室审阅和批准的内部模块库。手写那份组合每个应用要 3–4 周，跨 300 多个应用的组合折算下来是数年的工程工作量。
- **工作延续到切换之后**：项目范围包括交接之后的运维，那超出迁移服务之外。

## 架构概览

这一模式使用四个专用智能体。该架构在三个点上接入一个迁移项目：持有迁移输入的系统、IaC 组合，以及切换后的运维。该模式在每个这些点上施加安全。下图展示智能体、工具和 AWS 服务如何连接。

图 1：智能体如何通过 Model Context Protocol 工具调用跨迁移和运维旅程连接

该模式把智能体组织为两个旅程。迁移旅程的智能体处理从发现到部署。运维旅程的智能体处理迁移后的监控。

迁移旅程智能体：

- **Intake Agent（阶段 1）：** 通过 MCP 工具读取架构文档、问卷和依赖记录，然后定义目标状态架构。
- **IaC Agent（阶段 2）：** 为每个应用生成组合你已批准内部模块的 IaC。
- **Migration Intelligence and Governance Agent：** 跨 Jira、Confluence 和 Webex 提供自动化的组合报告、架构良好的评估和治理。

运维旅程智能体：

- **SRE Agent（阶段 3）：** 在切换之后提供监控和自动化修复。

AWS 托管服务承担迁移并补充定制智能体：

- [AWS Database Migration Service (AWS DMS)](https://docs.aws.amazon.com/dms/)：用于数据库迁移的、由生成式 AI 辅助的 schema 转换和自动化切换。
- [AWS Transform](https://docs.aws.amazon.com/transform/)：为大型机、虚拟化和 .NET 工作负载的发现、波次规划、着陆区创建、网络转换、重新托管或重新上平台执行，以及现代化。

### 各组件如何连接

本节描述框架组件在运行时如何交互。

每个智能体都是一个 Strands 智能体，由一个基础模型、一个 system prompt 和一组工具定义。Amazon Bedrock AgentCore runtime 在一个带会话隔离和多智能体编排的无服务器环境中托管它们。Amazon Bedrock 基础模型驱动那些解释文档、生成代码并推动多步工作流的推理。关于按 AWS 区域的模型可用性，参见 [Amazon Bedrock 中受支持的基础模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

每个智能体通过 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-quick-start.html)（Amazon Bedrock AgentCore 的一项能力）调用限定到其功能的 MCP 工具，它把你的 API、AWS Lambda 函数和现有服务转换成兼容 MCP 的工具。[AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html)（Amazon Bedrock AgentCore 的一项能力）通过限定范围的 AWS Identity and Access Management (IAM) 角色和你的身份提供方认证每次调用。

Amazon Bedrock 的 [AgentCore memory](https://docs.aws.amazon.com/bedrock/latest/devguide/memory.html) 存储智能体会话状态和共享上下文。智能体用这份共享上下文持久化输出并跨 300 多个应用跟踪迁移进度。当 Intake Agent 完成发现时，它把目标架构和依赖映射写入 AgentCore memory。IaC Agent 读取这份共享上下文，无需手动交接即可开始代码生成。

### 用代码定义一个智能体

下面的 Python 例子定义 IaC Agent 并为 Amazon Bedrock AgentCore runtime 做准备。该智能体通过 AgentCore Gateway 触达你的 MCP 工具，并通过附带一个 [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 策略的 Amazon Bedrock 调用一个基础模型。

```
 import json
 import logging
 import os
 import uuid
 from bedrock_agentcore.runtime import BedrockAgentCoreApp
 from strands import Agent
 from strands.models import BedrockModel
 from strands.tools.mcp import MCPClient
 from strands.tools.mcp.mcp_types import MCPClientCredentials

 logger = logging.getLogger(__name__)
 app = BedrockAgentCoreApp()

 REGION = os.environ["AWS_REGION"]

 # url+auth lets the SDK run the client_credentials grant and re-mint the
 # token on expiry. A statically captured bearer token would go stale.
 gateway = MCPClient(
     url=os.environ["GATEWAY_MCP_URL"],
     auth=MCPClientCredentials(
         client_id=os.environ["GATEWAY_CLIENT_ID"],
         client_secret=get_secret("gateway/client_secret"),
         scopes=[os.environ["GATEWAY_SCOPE"]],
     ),
 )

 model = BedrockModel(
     model_id=os.environ["MODEL_ID"],
     region_name=REGION,
     guardrail_id=os.environ["GUARDRAIL_ID"],
     guardrail_version=os.environ.get("GUARDRAIL_VERSION", "1"),
     guardrail_trace="enabled",
 )



 @app.entrypoint
 def invoke(payload, context):
     prompt = (payload.get("prompt") or "").strip()
     if not prompt:
         return {"status": "error", "error": "missing required field: prompt"}

     try:
          with gateway:
              # Fetch the approved policies for this wave first, so the rules
              # travel in the system prompt instead of depending on the model
              # to ask for them.
              lookup = gateway.call_tool_sync(
                  tool_use_id=str(uuid.uuid4()),
                  name="get_policies",
                  arguments={
                      "resource_types": payload.get("resource_types", []),
                      "wave": payload.get("wave"),
                  },
              )
              if lookup["status"] != "success":
                  return {"status": "error", "error": "policy lookup failed"}
              policies = lookup.get("structuredContent", {})
 
              # tools=[gateway]: SDK owns the connection lifecycle and paginates
              # tool discovery, which list_tools_sync() alone does not.
              agent = Agent(
                  model=model,
                  system_prompt=(
                      f"{IAC_AGENT_PROMPT}\n\n"
                      f"Generated IaC satisfies these approved policies:\n"
                      f"{json.dumps(policies.get('policies', []), indent=2)}"
                  ),
                  tools=[gateway],
              )
              result = agent(prompt)
 
          if result.stop_reason == "guardrail_intervened":
              logger.warning("guardrail blocked request, session_id=%s",
                             getattr(context, "session_id", None))
              return {"status": "blocked_by_guardrail"}
 
          return {
              "status": "ok",
              "iac": str(result),
              "policy_set_version": policies.get("version"),
              "waived_policies": policies.get("waived", []),
          }
 
      except Exception as e:
          logger.exception("invocation failed, session_id=%s",
                           getattr(context, "session_id", None))
          return {"status": "error", "error": str(e)}
 
 
  if __name__ == "__main__":
      app.run()
```

该入口点把生成的 IaC 连同塑造它的策略集版本一起返回，于是审阅者能把输出追溯回一份签署过的标准。AgentCore Runtime 处理会话隔离和伸缩。关于可部署的例子，参见 GitHub 上的 [Amazon Bedrock AgentCore samples 仓库](https://github.com/awslabs/amazon-bedrock-agentcore-samples) 和 [Strands Agents samples 仓库](https://github.com/strands-agents/samples)。关于部署步骤，参见[开始使用 AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-getting-started.html)。

## 阶段 1：用于自动化发现的 Intake Agent

Intake Agent 读取那些活在你文档和协作系统里的迁移输入。在这个项目上，那些系统通过交付团队构建和维护的 MCP 工具可及。

该智能体通过那些工具摄入架构文档、应用清单列表、入站问卷和依赖记录。然后它产出一个推荐的迁移模式的、含资源规模规格和合规验证报告的目标 AWS 架构。

输出直接喂给 IaC Agent，创建一个从入站到基础设施开通的自动化交接。

## 阶段 2：用于自动化基础设施代码生成的 IaC Agent

AWS Professional Services 最先在组合中部署 IaC Agent，而它交付最直接可测量的影响。它生成遵循你安全最佳实践和标准的 IaC 代码。

### 它如何工作

该智能体工作流经过五个步骤推进：

**步骤 1：摄入指导文档。** 该智能体从波次团队读取指导文档。它提取部署范围、合规约束，以及安全办公室批准的、波次特定的覆盖项。

**步骤 2：解读目标状态架构图。** 借助 Intake Agent 的输出，IaC Agent 识别基础设施组件、它们的关系和依赖。

**步骤 3：生成 IaC。** 基于这份解读，智能体用你定义并确立的模式生成 IaC。它用波次特定参数填充配置并配置远程状态管理。然后它应用强制性打标签并添加组织标准所要求的监控配置。

**步骤 4：通过 AgentCore 中的 Policy 验证。** 在执行之前，AgentCore 中的 Policy 针对 Cedar 规则评估每次工具调用。它计算潜在变更的范围、检查与并发波次的依赖冲突，并确认合规窗口有效性。

**步骤 5：执行并报告。** 集中的执行平面触发 IaC、监控部署，并通过 AgentCore Observability（Amazon Bedrock AgentCore 的一项能力）报告结果。部署后验证自动运行，合规指标实时更新。

### 定制 MCP 工具：安全基础

每个动作都通过 Amazon Bedrock AgentCore Gateway 暴露、并受 AgentCore Identity 和 AgentCore 中的 Policy 治理的定制 MCP 工具。AgentCore Identity 通过带最小权限的限定 IAM 角色认证每个智能体动作。该框架对照定义的 schema 验证输入，并在边界处拒绝畸形输入。

没有凭证或敏感值通过智能体上下文，因为 AgentCore Identity 在一个集中凭证提供方处运行时解析 secret。AgentCore Observability 和 AWS CloudTrail 把每个智能体动作写入一个不可变、集中的审计轨迹。[AgentCore 中的 Policy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html) 强制执行帮助防止单个操作影响超过一个定义阈值的 [Cedar](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-understanding-cedar.html) 规则。

### 作为 MCP 工具的策展组织策略

安全办公室策展策略集，而非智能体。一个版本化文档持有每条规则、它所覆盖的资源类型、一个机器可校验的断言，以及批准记录。下面的例子展示三条策略和一个波次例外。

```
{
    "policy_set": "security-office/baseline",
    "version": "2026.09.1",
    "policies": [
      {
        "id": "SEC-ENC-001",
        "applies_to": ["aws_s3_bucket", "aws_ebs_volume", "aws_rds_cluster"],
        "requirement": "Encrypt data at rest with a customer managed KMS key",
        "assertion": "kms_key_id != null and sse_algorithm == 'aws:kms'",
        "severity": "blocking",
        "source": "SecOffice/Encryption-Standard-v4"
      },
      {
        "id": "SEC-NET-014",
        "applies_to": ["aws_security_group_rule"],
        "requirement": "No ingress from 0.0.0.0/0 on administrative ports",
        "assertion": "not (cidr_blocks contains '0.0.0.0/0' and to_port in [22, 3389])",
        "severity": "blocking",
        "source": "SecOffice/Network-Standard-v7"
      },
      {
        "id": "OPS-TAG-003",
        "applies_to": ["*"],
        "requirement": "Carry owner, cost-center, data-classification, and wave tags",
        "assertion": "tags has_keys ['owner', 'cost-center', 'data-classification', 'wave']",
        "severity": "blocking",
        "source": "SecOffice/Tagging-Standard-v2"
      }
    ],
    "wave_overrides": [
      {
        "wave": "wave-14",
        "policy_id": "SEC-NET-014",
        "decision": "exception",
        "expires_on": "2026-10-31",
        "approved_by": "security-office"
      }
    ]
  }
```

一个 AWS Lambda 函数服务那份文档，而 AgentCore Gateway 把该函数作为一个名为 get_policies 的 MCP 工具暴露。IaC Agent 只请求它为之生成的那个波次中、在所请求资源类型范围内的策略。

```
  import json
  from datetime import date
  from pathlib import Path
 
  POLICY_SET = Path("policies/security-office-baseline.json")
 
  def get_policies(event, context):
      """Return the approved policies for the requested resource types and wave.

      AgentCore Gateway exposes this function as the get_policies MCP tool.
      """
      doc = json.loads(POLICY_SET.read_text())
      requested = set(event.get("resource_types") or [])
      today = date.today()
      waived = {
          o["policy_id"]
          for o in doc["wave_overrides"]
          if o["wave"] == event.get("wave")
          and date.fromisoformat(o["expires_on"]) >= today
      }
      policies = [
          p for p in doc["policies"]
          if (p["applies_to"] == ["*"] or requested & set(p["applies_to"]))
          and p["id"] not in waived
      ]
      return {
          "version": doc["version"],
          "policies": policies,
          "waived": sorted(waived),
      }
```

响应携带策略集版本，于是生成的代码记录了哪些规则产出了它，而审阅者能把一个资源追溯回一份签署过的标准。被豁免的策略随它们自己的字段一起传输而非消失，而合规报告为该波次列出它们。每个例外带一个过期日期，于是一份失效的豁免在无人工清理的情况下停止适用。

这里运作着两层策略，它们回答不同的问题。AgentCore Policy 评估 Cedar 规则以决定一个智能体到底要不要调用一个工具。策展的策略集决定生成的基础设施满足什么。

### 基于你模式的 IaC 生成

IaC Agent 基于你定义并确立的模式生成基础设施代码。这些模式把组织标准编码成可复用的构造。它们包括网络配置、安全组规则、IAM 角色、[Amazon CloudWatch](https://docs.aws.amazon.com/cloudwatch/) 告警、[Amazon Elastic Compute Cloud (Amazon EC2)](https://docs.aws.amazon.com/ec2/) 配置、[Amazon Virtual Private Cloud (Amazon VPC)](https://docs.aws.amazon.com/vpc/) 布局，以及强制打标签。

这种方法提供跨波次的一致性、为不从零编写基础设施代码的波次团队提供速度，并在安全更新于消费者下一个部署周期传播给他们之处提供治理。

### 输出产物

该智能体为每个应用产出 IaC 代码、自动化测试用例、合规报告和部署手册。

IaC Agent 把生成的代码直接推送到你的代码仓库（如 [AWS CodeCommit](https://docs.aws.amazon.com/codecommit/)、GitLab 或 Bitbucket）。从那里，它进入你现有的审阅和部署流水线，而无需改动你现有的工具链。

## Migration Intelligence and Governance Agent：全组合可见性

一个 300 多个应用的组合需要状态报告、进度跟踪、后续动作和架构良好验证。在这个项目上，那工作在客户自己的 Jira、Confluence 和 Webex 内进行。手动执行它给项目经理和交付负责人造成重大开销。

Migration Intelligence and Governance Agent 通过跨组合的自动化、按需智能和治理来应对这一点。它通过 AgentCore Gateway 从三个来源聚合数据。Jira 提供冲刺进度和障碍。Confluence 提供架构文档和手册。Webex 提供会议纪要和行动项。

该智能体提供跨已迁移工作负载的架构良好评估、合规与治理验证，以及架构模式遵循度跟踪。

自动化动作包括用最新迁移状态更新 Confluence 页面、为识别出的行动项创建 Jira 任务，以及为升级生成 ServiceNow 工单。这些动作在执行前需要明确的人工批准。这种批准把关的架构是贯穿四个智能体的一个核心设计原则。智能体支持人类决策而非取代它。

跨 300 多个应用组合的按需报告取代了手动聚合，基于内部项目跟踪数据。你的结果可能因组合规模和工具集成而不同。

## 阶段 3：用于主动迁移后运维的 SRE Agent

SRE Agent 覆盖交接之后的阶段。迁移服务在切换时完成。在应用运行于 AWS 上之后，SRE Agent 把团队从被动响应转向主动改进。

该智能体监控 [Amazon CloudWatch](https://docs.aws.amazon.com/cloudwatch/) 指标、应用性能数据和历史模式。它在问题影响生产之前发起告警。该智能体还为常见失败模式发布自动化修复手册，并推荐效率改进。

目标领域（带人在回路批准）包括数据库集群合理配置、性能调优、存储分层，以及计算伸缩与效率改进。

SRE Agent 把这一模式延伸到迁移之外。应用不会落到 AWS 上就止步。它们随时间持续改进。

## 用 AWS DMS 做数据迁移

在这些定制 AI 智能体旁，两个 AWS 托管服务处理数据和应用现代化、服务器与网络迁移层。

[带生成式 AI 的 DMS Schema Conversion](https://docs.aws.amazon.com/dms/latest/userguide/schema-conversion-convert.databaseobjects.html) 减少手动的 schema 映射工作。它转换基于规则转换未能完成的代码对象，如存储过程、函数和触发器。这一能力在一部分 AWS 区域中正式可用，因此在波次规划期间确认区域支持。AWS DMS 随后用自动化迁移任务缩短切换窗口。该服务直接集成进智能体流水线。IaC Agent 开通目标基础设施，然后 AWS DMS 迁移数据。

AWS Transform 覆盖同一项目的服务器、网络和代码层。[AWS Transform 用户指南](https://docs.aws.amazon.com/transform/latest/userguide/what-is-service.html) 按工作负载类型列出当前的能力。

## 安全与合规：内建而非事后附加

该架构从一开始就内建安全，而非作为事后想法，并在迁移生命周期的每个阶段应用它。贯穿整个智能体套件的关键控制：

- **安全标准执行：** IaC Agent 直接从 Confluence 拉取你安全办公室的标准，并用定制 MCP 工具应用它们到生成的 IaC 上。
- **着陆区验证：** 该框架在部署前对照企业着陆区的合规要求验证生成的基础设施。
- **人在回路审批关卡：** 整个套件中所有智能体的自动化动作在执行前需要明确的人工批准。没有智能体在生产系统上自主行动。
- **AgentCore Gateway 协调：** Amazon Bedrock AgentCore Gateway 跨智能体协调上下文和安全控制，在整个迁移生命周期维持一致的策略应用。
- **持续集成与持续交付（CI/CD）集成：** 该框架把安全控制集成进 CI/CD 流水线，与 IaC 一起生成自动化测试用例，以在合规问题到达生产之前抓住它们。
- **推理层的负责任的 AI 控制：** Amazon Bedrock Guardrails 对每个 prompt 和每个模型响应应用内容过滤器、禁用主题、敏感信息过滤器和上下文接地检查。智能体只对清过护栏的输出行动。护栏 trace 随工具调用审计轨迹一起流入 AgentCore Observability。

这种方法与 AWS 责任共担模型保持一致。AWS 提供底层基础设施的安全，而你负责云内的安全。智能体自动化你的配置职责，同时为审批决定保持人工监督。

在这一实现中，该模式以人工流程无法企及的速度，在 300 多个应用组合上维持了企业安全标准。你的结果可能因你的安全要求和组织标准而不同。

## 可测量的影响

在整个迁移项目中，该框架交付了以下结果。这些指标反映这一具体实现。你的结果可能因应用复杂度、团队规模和组织要求而不同。

- **IaC 开发时间从数周降到几分钟：** 从每应用 3–4 周降到几分钟的自动化生成（基于内部项目跟踪数据）。
- **模式一致性应用于各波次：** 没有波次能偏离已批准的 IaC 模式基线。
- **安全合规：** 在每次部署自动验证，带一个零人工努力的完整审计轨迹。
- **架构到部署的保真度提升：** 智能体解读图表，而 IaC 按设计实现它。
- **跨 300 多个应用的按需组合报告**，带精确指标和零手动聚合。
- **波次团队上手改善：** 团队上传文档，智能体产出 IaC 和报告。

## 成本考量

运行这一模式在几个可预测的地方增加成本。基础模型 token 通常占大头，因为入站和 IaC 生成把文档、策略和架构上下文推过一个模型并返回生成的代码。Amazon Bedrock AgentCore 按消费计费。Runtime 按一个会话使用的 CPU 和内存每秒计费，而当一个智能体等待模型响应或人工批准时 CPU 缩到零。Gateway、Memory、Policy 和 Guardrails 各按使用单位计费，而 Observability 遥测按 Amazon CloudWatch 费率计费。

在一个 300 多个应用的组合上，这些智能体在迁移项目的整个时长内运行而非作为单个作业，因此把它当作一项随波次活动变动的运行成本。Token 量更随文档大小和工具调用数而非应用数变动，因此一个试点波次给你一个每应用基线。在 AWS Transform 一侧，虚拟化、Windows 和大型机工作负载的评估与迁移智能体免费提供。迁移所创建的资源正常计费，而定制转换按智能体分钟定价。当前费率参见 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)、[Amazon Bedrock AgentCore 定价](https://aws.amazon.com/bedrock/agentcore/pricing/)、[AWS Transform 定价](https://aws.amazon.com/transform/pricing/)、[Amazon CloudWatch 定价](https://aws.amazon.com/cloudwatch/pricing/) 和 [AWS Pricing Calculator](https://calculator.aws/)。

## 清理资源

要在测试完该框架后避免持续产生费用，移除你创建的资源：

- 从 AgentCore runtime 删除智能体，然后移除 Gateway 目标和 Gateway。
- 删除持有会话状态和共享上下文的 AgentCore memory 资源。
- 删除护栏、AgentCore 中的 Policy 定义，以及为智能体创建的 IAM 角色。
- 如果你不再需要历史，删除 AgentCore Observability 写入的 CloudWatch 日志组。
- 删除为测试迁移配置的任何 AWS DMS 复制实例和端点。

在 Amazon Bedrock AgentCore 控制台确认没有智能体会话仍处于活跃。

## 结论

在一个紧迫的时间表上把 300 多个应用迁移到 AWS，需要的不只是增加工程师。托管服务承担其中大部分工作。当某个要求落在它们之外时，一个智能体模式能弥合差距，而人类保留决策、批准和战略。

这一模式在一个源和目标坐落在 MCP 工具之后的项目上交付了可测量的结果。专用的 Strands 智能体应对了那些特定要求，Amazon Bedrock AgentCore 结构性地应用安全，而人在回路的设计让自动化支持决策而非取代它。用 AWS Transform 和 AWS DMS 做迁移，并在 MCP 连接的源和目标需要之处与它们一起运行这些智能体。
