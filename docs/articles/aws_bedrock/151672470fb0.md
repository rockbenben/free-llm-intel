# 在 GxP 环境中构建 AI agent 指南

医疗保健与生命科学组织正在用生成式 AI agent 改变药物发现、医疗器械和患者护理。在受监管的行业中，任何影响产品质量或患者安全的系统都必须遵守 GxP（Good Practice，良好规范）法规，例如 Good Clinical Practice (GxP)、Good Laboratory Practice (GLP)、Good Manufacturing Practice (GMP)。组织必须向监管机构证明其 AI agent 安全、有效并符合质量标准。为这些 GxP 环境构建 AI agent 需要一种战略方法，在创新、速度与监管要求之间取得平衡。

**可以为 GxP 环境构建 AI agent**：关键在于理解如何根据其风险特征恰当地构建它们。生成式 AI 在可解释性、概率性输出和持续学习方面引入了独特的挑战，这些需要深思熟虑的风险评估，而非一刀切的验证方法。传统 GxP 合规方法与现代 AI 能力之间的脱节，给实施设置了障碍、增加了验证成本、放慢了创新速度，并限制了产品质量和患者护理方面的潜在收益。

GxP 合规的监管格局正在演进，以应对 AI 的独特特性。传统的 Computer System Validation (CSV) 方法通常采用统一的验证策略，正由 Computer Software Assurance (CSA) 框架加以补充，后者强调灵活、基于风险的验证方法，并根据每个系统的实际影响和复杂性量身定制（[FDA 最新指南](https://www.fda.gov/files/medical%20devices/published/US-FDA-Artificial-Intelligence-and-Machine-Learning-Discussion-Paper.pdf)）。

在本文中，我们讨论基于风险的实施、跨不同风险级别的实际实施考量、用于合规的 AWS 责任共担模型，以及风险缓解策略的具体示例。

## 基于风险的实施框架

要让 agentic AI 系统有效实现 GxP 合规，需要基于运营环境而非仅基于技术特性来评估风险。为支持风险分类，[FDA 的 CSA 草案指南](https://www.fda.gov/media/161521/download) 建议从三个因素评估预期用途：潜在危害的严重性、发生概率，以及失效的可检测性。

在图 1 中，该评估模型将传统的运营角色与现代的基于风险的级别相结合。组织应评估 AI agent 在工作流中的运作方式及其对受监管流程的潜在影响。

**图 1. ** AI agent 的 GxP 合规将传统的基于角色方式与 CSA 现代的基于风险的级别相结合

相同的 AI agent 能力，根据部署方式的不同，可能需要截然不同的验证方法。agentic AI 是如何被使用的，又处于现有 GxP 流程中的什么位置？人工监督或 human-in-the-loop 控制的程度如何？AI agent 本身是否被添加为一项额外控制？AI 失效对产品质量、数据完整性或患者安全的潜在影响是什么？

以一个用于科学文献综述的 AI agent 为例。当它为内部团队会议创建文献摘要时，属于**低风险，**只需最少的控制。当科学家利用这些见解来指导研究方向时，它变为**中风险，**需要结构化控制，例如人工审核检查点。当它用于支持药物批准的监管申报时，它变为**高风险并需要全面的控制 **，因为其输出直接影响监管决策和患者安全。

这种基于风险的方法使组织能够在创新与合规之间取得平衡，方法是根据实际风险级别定制验证工作，而非对所有 AI 实施应用统一的控制。

## 实施考量

成功的 AI agent 设计需要在所有风险级别上一致适用的通用控制。组织应保留 AI 决策的清晰记录、证明数据未被篡改、在需要时复现结果，并安全地管理系统更新。AWS 通过合格的基础设施和各项合规认证（如 ISO、SOC 和 NIST）支持这些要求。更完整的列表请参阅我们的 [Healthcare & Life Sciences Compliance](https://aws.amazon.com/health/healthcare-compliance/) 页面。Amazon Bedrock AgentCore 的详细合规验证信息可在[合规文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/compliance-validation.html)中找到。为了有效实施这些控制，组织可以参考 National Institute of Standards and Technology (NIST) 的 [AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework) 来获取 AI 风险指导，并参考 ALCOA+ 原则来促进数据完整性。

***可追溯性与可复现性***

AWS 提供以下支持：

- [Amazon Bedrock](https://aws.amazon.com/bedrock/) – 提供不可变的模型版本控制，有助于在整个系统生命周期中实现可复现的 AI 行为。
- [AWS Config](https://aws.amazon.com/config/) – 自动跟踪和验证系统配置，持续监控与已验证基线的偏差。
- [AWS CloudTrail](https://aws.amazon.com/cloudtrail/) – 生成具有密码学完整性的审计跟踪，捕获模型调用及完整元数据，包括时间戳、用户身份和模型版本。通过 [AWS CloudFormation](https://aws.amazon.com/cloudformation/) 提供基础设施即代码支持，实现版本控制、可重复的部署。

客户责任：组织必须对其基础设施部署和 prompt 模板进行版本控制，以确保 AI 行为一致，并维护 prompt 变更的审计跟踪。工具依赖必须被跟踪并锁定到已验证环境中的特定版本，以帮助防止可能影响 AI 输出的意外更新。

***可观测性与性能指标***

AWS 提供以下支持：

- [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) – 为 agentic AI 引入的独特风险提供全面解决方案，包括对复杂多步骤 agent 任务的端到端可视性，以及编排推理链的运行时要求。Amazon Bedrock AgentCore Observability 捕获完整的决策链和工具调用，使你可以检查 agent 的执行路径、审计中间输出并排查失败。面向 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 的 Bedrock Retrieval API 支持从检索到的文档追溯到 AI 生成的输出。
- [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) – 提供实时监控以及可定制的告警和仪表板，汇总跨 agent 调用的性能指标。组织可以根据风险配置日志级别，例如低风险应用使用基本的 CloudTrail 日志，中风险使用详细的 AgentCore trace，高风险监管申报使用完整的可追溯链。

客户责任：组织定义与其风险级别相适应的验收标准和监控阈值——例如，我们的文献综述 agent 的引用准确性要求。团队必须决定何时需要 human-in-the-loop 触发器，例如在 AI 建议影响研究决策或监管申报之前进行强制专家审核。

***用户管理、会话隔离与安全***

AWS 提供以下支持：

- Amazon Bedrock AgentCore – 使用专用 microVM 提供会话隔离，有助于防止不同项目或监管申报之间的交叉污染。该服务支持 VPC 端点，在你的 Amazon VPC 与 Amazon Bedrock AgentCore 资源之间建立私有连接，实现网络间流量的隐私性。在所有支持的区域中，与 Amazon Bedrock AgentCore 端点的所有通信一律使用 HTTPS，不支持 HTTP，因此所有通信都经过数字签名以确保认证和完整性。

Amazon Bedrock AgentCore 维持稳健的加密标准，所有 API 端点最低要求 TLS 1.2（推荐 TLS 1.3）。控制平面和数据平面流量均使用 TLS 协议加密，并限制为最低 TLS 1.2，不允许未加密的通信。Amazon Bedrock AgentCore Identity 通过安全的 token 保管库管理凭证，提供细粒度权限和企业身份集成，以应对身份管理的复杂性。

[AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 使组织能够按照最小权限原则配置基于角色的访问控制。内置加密有助于保护传输中和静态的数据，而网络隔离和合规认证（SOC、ISO 27001、HIPAA）则支持监管要求。Amazon Bedrock 提供可配置的数据驻留，允许组织指定数据处理的区域。

客户责任：组织配置符合 GxP 用户访问要求的 IAM 角色和策略，促进最小权限访问和适当的职责分离。访问控制必须形成文档，并作为质量管理体系的一部分加以维护。

### **面向 AI agent 的 GxP 控制**

AI agent 的 GxP 风险控制实施可以从三个关键阶段来考虑。

**风险评估**依据组织基于风险的验证框架来评估 GxP 工作负载。通过结构化的反馈循环维持持续的质量保证，范围从实时验证（见持续验证）到每半年一次的审查。该流程确保审核人员针对不断演进的 AI 形势接受培训、适应用户反馈并应用适当的干预标准。在实践中，风险评估定义风险类别和重新评估的触发条件。

**控制选择**是根据 1. 风险分类、2. 具体的设计属性，以及 3. AI agent 的运营环境，精心选择最少必需的控制。这种有针对性的、经风险调整的方法确保控制既符合技术要求，也符合合规目标。在实践中，风险类别决定必需和可选的控制。中等风险的例子可能需要 Agent and Prompt Governance 控制以及两个或更多 Detective Controls，而高风险可能需要 Traditional Testing (IQ, OQ, PQ) 控制，外加两个额外的纠正性控制。

**持续验证 **是一种方法，包括传统的适用性验证，以及后续利用真实世界数据 (RWD)（例如运营日志和/或用户反馈）的流程，以创建补充的真实世界证据 (RWE)，证明系统保持已验证状态。作为一种控制机制本身，持续验证方法有助于应对包括 SaaS 模式、模型漂移和不断演进的云基础设施在内的现代云端设计。通过对性能和功能的持续监控，该方法有助于维持系统的 GxP 合规，同时支持监管检查。在实践中，对于低风险类别，这可能是一个与合规保持一致的用户门户，用于跟踪用户问题趋势；而对于高风险系统，则包含定期自检并生成合规报告。

## 结论

医疗保健与生命科学组织可以通过采用在创新与监管要求之间取得平衡的基于风险的框架，来构建符合 GxP 的 AI agent。成功需要适当的风险分类、与系统影响相匹配的适度控制，以及对[责任共担模型](https://docs.aws.amazon.com/whitepapers/latest/aws-risk-and-compliance/shared-responsibility-model.html)的理解。AWS 提供合格的基础设施和全面的服务，而组织则配置适当的控制、维护版本管理，并实施符合其验证需求的风险缓解策略。

我们鼓励组织探索使用 AWS 服务构建符合 GxP 的 AI agent。如需了解更多关于在受监管环境中实施合规一致的 AI 系统的信息，请联系你的 AWS 客户团队，或访问我们的 Healthcare and Life Sciences [解决方案页面](https://aws.amazon.com/health/)。
