# 不止于每 token 的价格：为你的工作负载选择合适的 Amazon Bedrock OpenAI 模型

构建生成式 AI 应用的组织通常用同一种方式比较模型：每百万 token 多少美元。这是每个定价页面上都会出现的数字，于是也就成了每个表格里的数字。但生产工作负载买的不是 token，而是结果：一个被解决的工单、一份完成的研究简报、一份正确的财务摘要。在定价页面与最终结果之间，还隔着标签价格所忽略的乘数：模型的正确率有多高、达到该结果需要多少 token，以及对于 agentic 工作负载而言需要多少轮，因为每一轮都会重新发送不断增长的对话内容。

本文分享了一个开源基准测试 harness 的结果，该 harness 会针对 Amazon Bedrock 上的 OpenAI 模型（gpt-5.6-luna、gpt-5.6-terra 和 gpt-5.6-sol）以及 OpenAI API 上两个广泛使用的低成本模型（gpt-5.4-mini 和 gpt-5.4-nano）测量这些乘数。我们选择后两个模型，是因为它们是许多团队起步时使用的成本优化基线，而不是把它们当作同代可比的对照，因为我们听到最多的问题是：“我们今天用的是 mini 或 nano，Amazon Bedrock 上更新的模型值得吗？”我们聚焦三个问题：

- **一个正确答案的成本是多少？** 而不是一个 token 的成本是多少。
- **agent 轨迹的成本是多少？** 轮数可能主导账单。
- **它能产出专业人士认可的工作成果吗？** 这一项是在真实的职业交付物上测量的，而不是在测验题上。

本文的核心基准测试是可复现的：该 harness——[openai-on-aws/benchmarks-openai](https://github.com/openai-on-aws/benchmarks-openai)——对两个应用运行同一条完全相同的代码路径（OpenAI Responses API），我们鼓励你在做出任何决定之前，先在自己的任务上运行一遍。

## 解决方案概览

该 harness 通过同一个 Responses API 客户端评估全部五个模型，只切换后端与模型 ID，并保持评估逻辑不变。结果仍然反映了模型本身、提供商基础设施以及模型特定配置的差异。特别是，Amazon Bedrock 上的模型在关闭推理（reasoning disabled）的情况下运行，而 OpenAI API 基线则以各自的默认设置运行。这是对实际部署配置的比较，而不是对模型内在能力的受控估计。

我们测量三件事：在仍能区分前沿模型的基准测试（AIME 竞赛数学、GPQA Diamond 研究生水平科学以及 MMLU-Pro）上的单次调用准确率与成本；在真实网络研究任务上的多轮 agent 轨迹；以及按评分标准打分的职业交付物。评分结合了确定性检查与一个大型语言模型（LLM）评审（gpt-5.5，不属于被评估的模型），使用的是冻结的 prompt，其哈希记录在每个结果文件中。每次运行都会写出一份带时间戳的结果 JSON，本文中的每一个数字和每一张图表都是在构建时由这些文件生成的。

如何解读这些结果：样本量在 48–198 项之间。除非同时给出不确定性估计，否则请把较小的差距视为方向性信号，并在选择模型之前在自己的工作负载上复现评估。

## 衡量一个正确答案的成本

对每个基准测试，我们用模型的总支出（包含正确与错误的尝试）除以正确答案的数量。这估算出在我们的样本中观察到的单次正确答案成本。下图展示了全部五个模型在 AIME 上的准确率与每次正确答案成本。这一模式在 GPQA Diamond 和 MMLU-Pro 上同样重复出现（完整表格见仓库）。

![五个模型在 AIME 上的准确率与每次正确答案成本图表：luna 成本最低，sol 准确率最高](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/09/ML-21634-1.png)

图 1：五个模型在 AIME 上的准确率与每次正确答案成本

有两点格外突出：

- **在这个样本中能力分层清晰可见。** Sol 解决了 75% 的 AIME 题目，而 mini 为 37%；Sol 在 GPQA Diamond（68% 对 43%）和 MMLU-Pro（82% 对 59%）上也领先。如果各次尝试相互独立且准确率保持不变，那么 37% 的准确率意味着平均每次成功大约需要 2.7 次尝试。真实的重复尝试之间存在相关性，因此请测量你实际的重复策略，而不要假设该估算可以直接套用。
- **即使在价格变动之前，token 效率就已经决定了账单，而随后价格又发生了变动。** 按其最初的标价（约为 mini 的 1.5 倍），在这种配置下 luna 每个 AIME 正确答案的成本已经便宜了 25%，因为在关闭推理的情况下，它使用的计费 token 比采用默认设置的 mini 更少。在 [2026 年 7 月 30 日 Amazon Bedrock 上 GPT-5.6 Luna 和 Terra 降价](https://aws.amazon.com/about-aws/whats-new/2026/07/openai-gpt-terra-luna-pricing-bedrock/)（luna −80%，terra −20%）之后，我们记录的每个 AIME 正确答案成本为 luna 0.0021 美元，而 mini 为 0.0139 美元。在这些样本中，luna 观察到的每个正确答案成本是最低的，即便与 nano 相比也是如此，尽管在结果文件记录的价格假设下 nano 的名义 token 价格略低。**定价说明：** 结果文件目前对 luna 采用每 100 万输入/输出 token 0.22/1.32 美元，对 terra 采用 2.20/13.20 美元。在发布之前，请对照实时定价页面确认适用的 Amazon Bedrock 推理档位和区域。7 月 30 日的公告描述的是第一方价格对等，而定价页面的更新可能滞后。对客户而言，更有用的模型选择问题不仅是“哪个每 token 最便宜？”，而是“在我的业务可接受的质量水平上，哪个每个*结果*最便宜？”

## 衡量 agent 轨迹成本

单次调用定价漏掉了我们 agentic 工作负载的一个决定性特征。该 harness 使用客户端管理的对话历史（`store: false`），因此每一轮都会重新发送 system prompt、先前的工具结果以及对话上下文。每轮的上下文大致呈线性增长，因此累计计费的输入量可能随轮数呈近似二次方增长。每一轮还会额外增加一次延迟往返。一个用五轮而不是八轮就完成任务的模型，其节省可能超过轮数减少 37% 本身所暗示的程度。

为了在真实工作负载上测量这一点，我们让 [DeepSearchQA](https://arxiv.org/abs/2601.20975)（多步网络研究问题）的 50 题分层样本跑过一个在线 agent 循环，其中使用了真实的 `web_search` 和 `fetch_page` 工具。答案先经过一次确定性的预检，再由冻结的 gpt-5.5 自动评分器打分。F1 ≥ 0.7 即视为该问题通过。下图展示了轮数如何驱动输入 token 量（左）以及每个通过答案的最终成本（右）。

![双图对照：轮数如何驱动每题输入 token 量，以及各模型每个通过的 DeepSearchQA 答案成本](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/09/ML-21634-2.png)

图 2：轮数如何驱动输入 token 量以及每个通过的 DeepSearchQA 答案的成本

左图展示的是机制，右图展示的是结果。在所有模型中，mini 每题花费的轮数最多（7.6 轮，主要是反复搜索的循环），而每一轮额外增加都会重新发送一个包含已累积搜索结果的上下文。到结束时，这达到了 terra 输入 token 量的 2.3 倍（每题 114k 对 50k token）。在这个样本中，terra 更高的 token 价格被更少的轮数和更高的质量抵消：它每个通过答案花费 0.31 美元，而 mini 为 0.40 美元，平均 F1 为 0.50 对 0.39。三个 GPT-5.6 配置记录的平均 F1 都高于两个基线，而 luna 在轮数少于 mini 的同时，每个通过答案花费 0.05 美元，对比 mini 的 0.40 美元。nano 的名义 token 价格更低，但在 18% 的通过率下，其观察到的每个通过答案成本为 0.07 美元，而 luna 为 0.05 美元。只有 50 个问题，请把差距不大的情况视为方向性信号。

给客户的启示：轮次效率是一个定价变量，而它在定价页面上是看不见的。如果你的 agent 会串联工具调用（研究、多跳查询、迭代检索），请把轨迹成本与调用成本一起做基准测试。

## 用 GDPval 评估职业交付物

基准测试评的是答案。而客户实际交付的很大一部分是文档，例如合规简报、财务计划和护理规程，在这些场景中“正确”是一个评分标准，而不是字符串匹配。因此我们运行了 GDPval 的 48 个任务切片：这些是由平均拥有 14 年经验的专业人士创作的真实职业交付物，每个都按其人工编写的评分标准打分。加权评分标准得分 ≥70% 即视为交付物通过。下图展示了通过率与每个通过交付物的成本。

![五个模型在 GDPval 上的通过率与每个通过交付物成本图表](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/09/ML-21634-3.png)

图 3：GDPval 的通过率与每个通过交付物的成本

在关闭推理的情况下，三个 gpt-5.6 配置观察到的评分标准得分都高于 mini 和 nano。观察到差异最大的是法律、护理和财务建议类任务，这类评分标准要求具体的注意事项、结构和完整性。各类别样本量很小，因此请把这个模式视为探索性的。在 48 个交付物中，luna 有 31 个得分高于 mini，9 个更低，8 个持平。它通过了 27 个交付物，而 mini 通过了 20 个。

该工作负载是单次调用，不存在轮数效应，因此在降价之前，mini 和 nano 每个通过交付物的成本更低，gpt-5.6 只买到了通过*率*。降价之后，luna 在这个样本中观察到的成本最低：每个通过交付物 0.010 美元，而 mini 为 0.030 美元、nano 为 0.012 美元；其通过率为 56%，而 mini 为 42%、nano 为 35%。terra 和 sol 每次通过仍然存在溢价，同时记录了更高的评分表现。这种溢价是否值得，取决于目标工作流中审阅与返工的成本。

**GDPval 注意事项：** 输出被限制在 8,192 token，导致 luna 6 个、terra 9 个、sol 7 个、mini 0 个、nano 1 个交付物被截断。这些是在所测试上限下的真实结果。更高的上限可能提升质量，但也可能增加成本。请把两者放在一起测试。

## 综合起来：一个决策框架

如果你目前运行的是 gpt-5.4-mini 或 nano，那么迁移问题就归结为工作负载的形态：

| **你的工作负载看起来像…** | **建议优先尝试** | **理由** |
| --- | --- | --- |
| 高并发量、低复杂度的任务。失败代价很低 | **Amazon Bedrock 上的 gpt-5.6-luna** | 在这些样本中，luna 记录的每个成功结果成本最低。在记录的价格假设下，nano 的名义 token 价格仍略低 |
| 交互式应用。准确性很重要。对延迟有服务级别目标（SLOs） | **先在 Amazon Bedrock 上对 gpt-5.6-luna 做基准测试** | 观察到的每次成功成本较优。延迟结果是某一时刻的区域快照。请对照你的 SLO 重新测量 |
| 会串联工具调用的 agent（研究、多跳） | **在 Amazon Bedrock 上对 gpt-5.6-luna 和 -terra 做基准测试** | 两者都以比 mini 更少的轮数记录了更高的 DeepSearchQA F1。在这个 50 题的样本中，luna 每个通过答案的成本约低 8 倍 |
| 有质量门槛的文档生产 | **Amazon Bedrock 上的 gpt-5.6-luna** | 在 GDPval 上，这是低成本模型中通过率最高的（27/48，对比 mini 的 20/48），同时每个通过交付物的成本最低（0.010 美元对比 0.030 美元） |
| 在真正困难的工作上，准确性是硬性门槛 | **在 Amazon Bedrock 上对 gpt-5.6-sol 做基准测试** | 这属于不同的能力与价格档位（AIME 75%，GDPval 31/48）。当更低成本的配置无法通过你的质量门槛时，可以考虑它 |

我们还用同一套流式 harness 测量了两个应用上同模型的延迟。在我们 2026 年 7 月的运行中（us-west-2、单区域、某一时点），在 12 组匹配配置上，Amazon Bedrock 上 luna 的首 token 时间中位数平均低 21%，terra 平均低 5%。共享服务会随负载变化，因此请把这些视为快照并重新测量。在输出 ≥500 token 时，luna 在 Amazon Bedrock 上的吞吐量平均高出 43%（terra 高 4%）。观察到的 `TTFT-to-median`（首 token 时间与中位数之比）最差值为 Amazon Bedrock 上的 2.1–2.5 倍，对比 OpenAI API 上的 4.6–6.6 倍。这些最大值表明尾部波动性，但并不是 p99 延迟的估计。Sol 的表现有所不同：它是一个深度推理模型，首 token 时间本身就长且波动大，而且它在 Amazon Bedrock 上的运行使用的是 us-east-1。三个模型各配置的细节记录在仓库的 [performance 章节](https://github.com/openai-on-aws/benchmarks-openai#-performance)中，performance/`run_all.sh` 可以在你自己的账户上复现这一比较。

## 在你的工作负载上运行

这些结果反映的是我们的样本量和配置选择：每套基准 50–198 个问题（DeepSearchQA 50、AIME 60、MMLU-Pro 140、GPQA Diamond 198）、48 个交付物，以及 Amazon Bedrock 上的模型关闭推理——这是刻意设定的成本下限。开启推理会同时提升质量与支出。你的任务并不是我们的任务。方法论才是可以长期沿用的部分：

```
git clone https://github.com/openai-on-aws/benchmarks-openai
pip install -r requirements.txt
export OPENAI_API_KEY=sk-... # your own key; not stored
export AWS_REGION=us-west-2 # plus your standard AWS credentials
python quality/quick_evals.py # accuracy + cost per correct answer
python quality/deepsearchqa/run_deepsearchqa.py # live-web agent trajectories
python quality/gdpval_eval.py # professional deliverables, rubric-judged
performance/run_all.sh # latency, both applications
```

替换成 50–100 个带有已知正确输出的你自己的任务，同一批脚本就能在你的领域、用你的账户，产出每次成功的成本数字。

## 结论

每 token 的价格是决策的一个输入，而不是决策本身。在我们测试的配置中，一旦把准确率、token 效率和轨迹长度纳入考量，改用成功结果来归一化成本就改变了模型的排名。定价页面也会变动，2026 年 7 月 GPT-5.6 的降价就是例证。定义你的应用所需的结果与质量门槛，测量成功与失败的完整成本，并在价格、模型或工作负载模式发生变化时重新运行评估。

要开始在 Amazon Bedrock 上使用 OpenAI 模型，请参阅 [Amazon Bedrock 文档](https://docs.aws.amazon.com/bedrock/)。要在自己的任务上复现这些基准测试，请克隆 [openai-on-aws/benchmarks-openai](https://github.com/openai-on-aws/benchmarks-openai)，并按照上一节的步骤操作。
