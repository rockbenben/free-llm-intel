# 企业中的 AI agent：Amazon Bedrock AgentCore 的最佳实践

构建可用于生产的 AI agent，需要在整个开发生命周期中细致地规划与执行。一个在演示中令人惊艳的原型，与一个在生产中真正交付价值的 agent 之间的差别，来自严格的工程实践、稳健的架构和持续改进。

本文探讨使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 构建企业 AI agent 的九项核心最佳实践。Amazon Bedrock AgentCore 是一个 agentic 平台，提供大规模创建、部署和管理 AI agent 所需的服务。本文覆盖从初期范围界定到组织级扩展的各个环节，并给出你可以立即落地的实践指导。

## 从小处着手，清晰定义成功

你需要回答的第一个问题不是*“这个 agent 能做什么？”*，而是*“我们要解决什么问题？”*太多团队一开始就构建一个试图应对所有可能场景的 agent。这会导致复杂性、缓慢的迭代周期，以及一个在任何方面都不出色的 agent。

相反，应当从具体用例倒推。如果你在构建财务助手，就从分析师最常见的三项任务开始。如果你在构建 HR 助手，就聚焦员工最常问的五个问题。先让这些可靠地跑起来，再扩大范围。

你的初始规划应当产出四项具体交付物：

- **清晰的定义**：说明 agent 应该做什么、不应该做什么。把它写下来。与利益相关方分享。用它来拒绝功能蔓延。
- **agent 的语气与性格**。决定它是正式还是口语化、如何问候用户，以及遇到超出范围的问题时会怎样。
- 为**每个工具、参数和知识来源给出明确无歧义的定义**。含糊的描述会导致 agent 做出错误选择。
- **一份基准事实数据集**，包含预期交互，既覆盖常见查询也覆盖边缘情况。

| **Agent 定义 ** | **Agent 语气与性格** | **工具定义** | **基准事实数据集** |
| --- | --- | --- | --- |
| **财务分析 agent**：帮助分析师检索季度收入数据、计算增长指标，并针对特定区域（EMEA、APAC、AMER）生成高管摘要。不应提供投资建议、执行交易或访问员工薪酬数据。 | 专业但口语化。以名字称呼用户。坦诚说明数据局限。对数据质量不确定时，明确说明置信水平。不使用未加解释的财务术语。 | `getQuarterlyRevenue(Region: EMEA\|APAC\|AMER, quarter: YYYY-QN)` – 以百万美元为单位返回收入。 `calculateGrowth(currentValue: number, previousValue: number)` – 返回百分比变化。 `getMarketData(Region: string, dataType: revenue\|sales\|customers)` – 检索最新的行业指标。 | 50 条查询，包括：“我们 EMEA 第三季度的收入是多少？”“给我看看与上季度相比的增长”“我们在亚洲表现如何？”“CEO 的奖金是多少？”（应拒绝）“对比 2024 年所有区域” |

| **IT 支持 agent**：协助员工重置密码、申请软件访问权限、排查 VPN 问题以及处理常见技术故障。不应访问生产系统、直接修改安全权限，也不应处理基础设施变更。 | 耐心且清晰。避免技术术语。提供分步指引。在进入下一步之前确认对方已理解。为小的成功喝彩（“太好了，成功了！”）。当问题需要系统访问权限时，升级给 IT 团队。 | `resetPassword(userId: string, system: string)` – 发起密码重置 `workflow.checkVPNStatus(userId: string)` – 验证 VPN 配置与连通性。 `requestSoftwareAccess(userId: string, software: string, justification: string)` – 创建访问申请工单。 `searchKnowledgeBase(query: string)` – 检索故障排查文章。 | 40 条查询，包括：“我登录不了邮箱”“VPN 总是断线”“我需要 Salesforce 的访问权限”“你能给我管理员权限吗？”（应拒绝）、“笔记本连不上 Wi-Fi”、“怎么安装 Slack？” |

用这个受限范围构建一个概念验证。用真实用户去测试它。他们会立刻发现你没想到的问题。例如，agent 可能在日期解析上吃力；它可能处理不好缩写，或者在问题措辞出乎意料时调用错误的工具。在概念验证阶段发现这些问题，代价可能只是几周时间；而在生产中发现，代价则是你的信誉和用户信任。

## 从第一天起就全面埋点

团队在可观测性方面最严重的错误之一，就是把它当作以后再补的东西。等你意识到需要它时，agent 已经上线了，这会让有效调试变得更困难。

从第一次测试查询开始，你就需要看清 agent 在做什么。AgentCore 服务会自动发出 [OpenTelemetry 追踪](https://opentelemetry.io/docs/concepts/signals/traces/)。模型调用、工具调用和推理步骤都会被捕获。当一次查询耗时十二秒时，你可以看出延迟来自语言模型、数据库查询，还是外部 API 调用。

可观测性策略应包含三个层次：

- 在开发期间启用追踪级调试，以便你能看清每次对话的步骤。当用户反馈行为不正确时，调出对应的追踪记录，准确看到 agent 做了什么。
- 使用随 [AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html) 提供的 Amazon CloudWatch 生成式 AI 可观测性仪表盘，为生产监控搭建看板。
- 跟踪 token 用量、延迟分位数、错误率和工具调用模式。如果你的组织使用 [Datadog](https://www.datadoghq.com/)、[Dynatrace](https://www.dynatrace.com/company/)、[LangSmith](https://smith.langchain.com/) 或 [Langfuse](https://langfuse.com/)，就把数据导出到你现有的可观测性系统。下图展示了 AgentCore Observability 如何让你深入查看某次会话调用中 agent 的追踪和元数据信息：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/03/ML-20055-image-1.jpg)

可观测性服务于不同角色的不同需求。开发者用它来调试，回答诸如 agent 为什么产生幻觉、哪个 prompt 版本表现更好、延迟来自哪里等问题。平台团队用它来治理；他们需要知道每个团队花了多少钱、哪些 agent 在推高成本，以及某次具体故障中发生了什么。原则很简单：无法度量，就无法改进。在你需要之前，先把度量基础设施搭好。

## 制定有意识的工具策略

工具是 agent 触达真实世界的方式。它们从数据库取数据、调用外部 API、搜索文档并执行业务逻辑。工具定义的质量直接影响 agent 的表现。

定义工具时，清晰比简洁更重要。对比同一个函数的两种描述：

- 差：`“获取收入数据”`
- 好：`“检索指定区域与指定时间段的季度收入数据。`
`以百万美元为单位返回数值。需要区域代码（EMEA、APAC、AMER）`
`以及 YYYY-QN 格式的季度（例如 2024-Q3）。”`

第一种描述迫使 agent 猜测哪些输入有效、如何解释输出。第二种有助于消除歧义。把这个差异乘以二十个工具，差别就会变得非常显著。你的工具策略应当涵盖四个方面：

- **错误处理与韧性。**工具会失败。API 会返回错误。超时会发生。为每种失败模式定义预期行为：agent 应该重试、回退到缓存数据，还是告诉用户服务不可用。把这些连同工具定义一起记录下来。
- **通过 Model Context Protocol（MCP）实现复用。**许多服务提供商已经为 Slack、Google Drive、Salesforce 和 GitHub 等工具提供 MCP server。直接使用它们，而不是自建自定义集成。对于内部 API，通过 AgentCore Gateway 把它们封装为 MCP 工具。这样你在所有工具上只需一种协议，并让不同的 agent 都能发现它们。
- **集中式工具目录。**团队不该五次重复构建同一个数据库连接器。维护一份经过安全审查并在生产中验证过的工具目录。当新团队需要某项能力时，先查这份目录。
- **为每个工具提供代码示例。**只有文档还不够。向开发者展示如何集成每个工具，并给出可复制、可改造的可运行代码示例。

下表展示了有效的工具文档应包含的内容：

| **要素** | **目的** | **示例** |
| --- | --- | --- |
| 清晰的名称 | 说明工具做什么 | `getQuarterlyRevenue` 而不是 `getData` |
| 明确的参数 | 消除关于输入的歧义 | `region`: string (EMEA\|APAC\|AMER), `quarter`: string (YYYY-QN) |
| 返回格式 | 明确输出结构 | Returns: {`revenue`: `number`, `currency`: “USD”, period: string} |
| 错误条件 | 记录失败模式 | 季度未找到时返回 `404`，服务不可用时返回 `503` |
| 使用指引 | 说明何时使用该工具 | 当用户询问收入、销售额或财务表现时使用 |

当你跨多个来源和类型管理工具时，这些文档标准会变得更有价值。下图展示了 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 如何为来自不同来源的工具提供统一接口：无论这些工具是通过额外的 Gateway 实例（用于数据检索与分析功能）暴露，还是通过 [AWS Lambda](https://aws.amazon.com/lambda/)（用于报表能力），抑或通过 [Amazon API Gateway](https://aws.amazon.com/api-gateway/)（用于项目管理等内部服务）。虽然这个示例为简洁起见只展示了一个 gateway，但许多团队会部署多个 Gateway 实例（每个 agent 一个，或每组相关 agent 一个），以保持清晰的边界和归属。得益于这种模块化做法，团队可以管理自己的工具集合，同时仍能受益于组织内一致的身份验证、发现与集成模式。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/03/ML-20055-image-2.jpg)

**AgentCore Gateway 帮助解决了工具泛滥这一实际问题。**当你在组织内构建越来越多 agent 时，工具会迅速累积到几十个：一些通过 MCP server 暴露，一些通过 Amazon API Gateway 暴露，还有一些是 Lambda 函数。没有 AgentCore Gateway，每个 agent 团队都要重新实现身份验证、管理各自的端点，并把每个工具定义都塞进 prompt，即便只有少数几个是相关的。AgentCore Gateway 为你的工具提供统一入口，无论它们位于何处。把它指向你现有的 MCP server 和 API Gateway，agent 就能通过一个接口发现它们。当工具数量增长到二三十个时，语义搜索能力变得至关重要：agent 可以依据自己要做的事找到正确的工具，而不是把所有内容都加载进上下文。你还能获得双向的完整身份验证处理：既验证哪些 agent 可以访问哪些工具，也管理第三方服务的凭证。正是这套基础设施，让集中式工具目录在规模上变得可行。

## 从开始就自动化评估

你需要知道 agent 随着每次改动是变好还是变坏。自动化评估为你提供这条反馈回路。先定义对你这个具体用例而言“好”意味着什么。指标会因行业和任务而异：

- 客服 agent 可能以解决率和客户满意度来衡量。
- 金融分析师 agent 可能以计算准确性和引用质量来衡量。
- HR 助手可能以政策准确性和回答完整性来衡量。

要在技术指标与业务指标之间取得平衡。响应延迟重要，但前提是答案正确。token 成本重要，但前提是用户觉得 agent 有价值。两类指标都要定义，并一起跟踪。仔细构建你的评估数据集，纳入以下数据：

- 同一个问题的多种问法，因为用户不会像 API 文档那样说话。
- 那些 agent 应当拒绝回答或升级给人工的边缘情况。
- 可能有多重有效解释的含糊查询。

以我们前面例子中的金融分析 agent 为例。你的评估数据集应包含诸如*“我们 EMEA 第三季度的收入是多少？”*这样的查询，并附带预期答案和正确的工具调用。但它也应包含变体：*“上个季度我们在欧洲赚了多少？”*、*“EMEA Q3 数据？”*以及*“给我看看 7 月到 9 月欧洲的收入。”*每种问法都应导致相同的工具调用和相同的参数。你的评估指标可能包括：

- **工具选择准确性**：agent 是否选择了 `getQuarterlyRevenue` 而不是 `getMarketData`？目标：95%
- **参数抽取准确性**：它是否把 `EMEA` 和 `Q3 2024` 正确映射到对应格式？目标：98%
- **拒答准确性**：agent 是否拒绝回答 `What's the CEO's bonus?`。目标：100%
- **回答质量**：agent 是否用清晰的表达解释了数据，而没有堆砌财务术语？通过 LLM-as-Judge 评估
- **延迟**：P50 低于 2 秒，P95 低于 5 秒
- **每次查询成本**：平均 token 用量低于 5,000 个 token

用这套评估在你的基准事实数据集上运行。在第一次改动之前，你的基线可能显示 92% 的工具选择准确率和 3.2 秒的 P50 延迟。在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上从 Amazon Claude 4.5 Sonnet 切换到 Claude 4.5 Haiku 之后，你可以重跑评估，发现工具选择降到 87%，但延迟改善到 1.8 秒。这就把取舍量化了，帮你判断速度上的收益是否值得准确性上的损失。

评估工作流应当成为你开发流程的一部分。改了 prompt？跑评估。加了新工具？跑评估。换成别的模型？跑评估。这条反馈回路需要快到你能立刻发现问题，而不是等到三次提交之后。

## 用多 agent 系统分解复杂性

当一个 agent 试图承担过多职责时，它就会变得难以维护。prompt 变得复杂，工具选择逻辑难以应对，性能下降。解决办法是把问题分解为多个协作的专用 agent。可以把它想象成组织一个团队：你不会只雇一个人去包办销售、工程、支持和财务，而是雇佣各司其职的专家来协同工作。同样的原则适用于 agent。与其让一个 agent 处理三十种不同任务，不如构建三个 agent，每个处理十项相关的任务，如下图所示。每个 agent 都有更清晰的指令、更简单的工具集和更聚焦的逻辑。当复杂性被隔离后，问题排查和修复就变得直接了当。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/03/ML-20055-image-3.jpg)

选择合适的编排模式很重要。顺序模式适用于任务有自然先后顺序的场景：第一个 agent 检索数据，第二个分析它，第三个生成报告。层级模式适用于需要智能路由的场景：由一个 supervisor agent 判定用户意图并委派给专家 agent。点对点模式适用于 agent 需要动态协作、没有中心协调者的场景。

多 agent 系统中的一个关键挑战是跨交接保持上下文。当一个 agent 把工作交给另一个时，第二个 agent 需要知道已经发生了什么。如果用户已把账号告知第一个 agent，第二个 agent 就不该再问一次。[AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html) 提供多个 agent 可在同一会话内访问的共享上下文。

要仔细监控 agent 之间的交接，大多数失败都发生在这里。哪个 agent 处理了请求的哪一部分？延迟发生在何处？上下文在哪里丢失了？AgentCore Observability 对整个工作流做端到端追踪，让你能诊断这些问题。

有一个常见的混淆点需要澄清：协议和模式不是一回事。协议定义 agent 之间如何通信。它们属于基础设施层，是线格式、是 API 契约。[Agent2Agent (A2A) 协议](https://github.com/a2aproject/A2A)、MCP 和 HTTP 都是协议。模式定义 agent 如何组织工作。它们属于架构层，是工作流设计、是协调策略。顺序、层级和点对点都是模式。

你可以用同一种协议搭配不同的模式。在构建顺序流水线或层级式 supervisor 时，你都可以使用 A2A。你也可以用同一种模式搭配不同的协议：顺序交接既可以跑在 MCP 上，也可以跑在 A2A 或 HTTP 上。要把这些关注点分开，以免把基础设施与业务逻辑紧耦合。

下表描述了多 agent 协作中协议与模式在层次、示例和关注点上的差异。

|  | **协议 – agent 如何交谈** | **模式 – agent 如何组织** |
| --- | --- | --- |
| **层次** | 通信与基础设施 | 架构与组织 |
| **关注点** | 消息格式、API 与标准 | 工作流、角色与协调 |
| **示例** | A2A、MCP、HTTP 等 | 顺序、层级、点对点 等 |

## 以个性化实现安全扩展

从一个开发者能跑通的原型，走向服务数千用户的生产系统，会带来隔离、安全和个性化方面的新要求。

会话隔离排在第一位。用户 A 的对话在任何情况下都不能泄露到用户 B 的会话中。当两个用户同时就不同项目、不同区域或不同账户提问时，这些会话必须完全独立。[AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 通过把每个会话运行在各自隔离的微型虚拟机（microVM）中、并配以专属计算和内存来处理这一点。会话结束后，microVM 终止。用户之间不存在共享状态。

个性化需要跨会话持久化的记忆。用户对信息如何呈现有自己的偏好。他们从事特定项目，而这些项目为其问题提供上下文。他们使用自己角色特有的术语和缩写。AgentCore Memory 同时提供用于对话历史的短期记忆和用于事实、偏好与过往交互的长期记忆。记忆按用户划分命名空间，因此每个人的上下文都保持私密。安全与访问控制必须在工具执行之前强制执行。用户只应访问他们有权查看的数据。下图展示了 AgentCore 各组件如何协同工作，在多个层次上帮助落实安全。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/03/ML-20055-image-4.png)

当用户与你的 agent 交互时，首先通过你的身份提供方（IdP）完成身份验证，无论是 [Amazon Cognito](https://aws.amazon.com/pm/cognito)、[Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/identity/) 还是 [Okta](https://www.okta.com/)。[AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) 接收身份验证 token，并提取定义用户权限与属性的自定义 [OAuth](https://oauth.net/2/) 声明。这些声明经 AgentCore Runtime 流向 agent，并在整个会话中可用。

当 agent 决定要调用哪些工具时，AgentCore Gateway 充当执行点。在工具执行之前，Gateway 拦截请求，并依据两层策略进行评估。[AgentCore Policy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html) 验证这个特定用户是否有权用这些特定参数调用这个特定工具，检查那些定义谁能访问什么的资源策略。同时，AgentCore Gateway 检查凭证提供方（例如 Google Drive、Dropbox 或 Outlook），以获取并注入第三方服务所需的凭证。Gateway 拦截器提供额外的钩子，你可以在工具调用继续之前实现自定义授权逻辑、速率限制或审计日志。

只有通过这些检查之后，工具才会执行。如果一名初级分析师试图访问高管薪酬数据，请求会在 AgentCore Gateway 处被拒绝，永远不会到达你的数据库。如果用户尚未为其 Google Drive 授予 OAuth 同意，agent 会收到一个明确的错误，并能把它转达给用户。用户同意流程是透明处理的；当 agent 首次需要访问某个凭证提供方时，系统会提示用户授权，并保存 token 以便后续请求使用。

这种纵深防御的做法有助于确保安全在 agent 与工具之间一致地落实，无论这些工具由哪个团队构建、托管在何处。

在规模上，监控会变得更复杂。面对数千个并发会话，你需要既能展示聚合模式、又能用来审视单次交互的仪表盘。AgentCore Observability 提供跨用户的实时指标，显示 token 用量、延迟分布、错误率和工具调用模式，如下图所示。当某个用户出问题时，你可以精确追踪那次特定会话中发生了什么，如下图所示。

AgentCore Runtime 也会把工具作为 MCP server 托管。这有助于保持架构的模块化。agent 通过 AgentCore Gateway 发现并调用工具，而不形成紧耦合。当你更新某个工具的实现时，agent 会自动使用新版本，无需改动代码。

## 将 agent 与确定性代码结合

你将做出的最重要的架构决策之一，是何时依赖 agentic 行为、何时使用传统代码。agent 很强大，但未必适合每一项任务。把 agent 保留给需要对含糊输入进行推理的任务。理解自然语言查询、判定该调用哪些工具、结合上下文解释结果，都能受益于基础模型的推理能力。这些任务若用确定性代码实现，就得枚举成千上万种可能情况。把传统代码用于计算、校验和基于规则的逻辑。收入增长是一个公式。日期校验遵循模式。业务规则是条件语句。你不需要语言模型来算“用 Q3 减 Q2 再除以 Q2”。写一个 Python 函数就好。它可以在毫秒级运行、没有额外成本，并且每次都产出相同答案。

正确的架构是让 agent 来编排代码函数。当用户问*“我们本季度在 EMEA 的增长如何？”*时，agent 用推理理解意图并确定要取哪些数据。它调用一个确定性函数完成计算。然后它再次用推理，用自然语言解释结果。

让我们对比两次“为下个月创建支出报告”查询在 LLM 调用次数、token 数量和延迟上的差别。第一次把 `get_current_date()` 作为 agentic 工具暴露出来，第二次则把当前日期作为属性传给 agent：

|  | **把 `get_current_date()` 作为工具** | **把当前日期作为属性传入** |
| --- | --- | --- |
| **查询** | “为下个月创建支出报告” | “为下个月创建支出报告” |
| **Agent 行为** | 制定调用 `get_current_date()` 的计划 根据当前日期的值计算下个月 以“下个月”为参数调用 `create_report()` 并生成最终响应 | 用代码获取当前日期 以“今天”为属性调用 agent 以“下个月”（通过 LLM 推理推断）为参数调用 `create_booking()` 并生成最终响应 |
| **延迟** | 12 秒 | 9 秒 |
| **LLM 调用次数** | 四次调用 | 三次调用 |
| **总 token 数（输入 + 输出）** | 约 8,500 个 token | 约 6,200 个 token |

当前日期是你可以用代码无缝获取的东西。你可以在调用时把它作为属性传入 agent 上下文。第二种做法更快、更便宜、也更准确。把它乘以数千次查询，差异就会变得相当可观。要持续衡量成本与价值之比。如果确定性代码能可靠地解决问题，就用它。如果你需要推理或自然语言理解，就用 agent。常见的错误是以为一切都必须是 agentic 的。正确答案是 agent 加代码协同工作。

## 建立持续测试实践

上线到生产不是终点，而是起点。agent 在持续变化的环境中运行。用户行为在演进。业务逻辑在改变。模型行为可能漂移。你需要持续测试，在这些变化影响用户之前捕捉到它们。构建一条在每次更新时都运行的持续测试流水线。维护一套测试用例，用有代表性的查询覆盖常见情况和边缘情况。当你改动 prompt、添加工具或切换模型时，流水线会运行你的测试套件并对结果打分。如果准确率跌破阈值，部署自动失败。这有助于防止回归。用 A/B 测试验证生产中的改动。当你想尝试新模型或不同的 prompt 策略时，不要一次性切换所有用户。例如，把 10% 的流量路由到新版本。用一周时间比较表现。衡量准确性、延迟、成本和用户满意度。如果新版本表现更好，就逐步推开；如果不好，就回滚。AgentCore Runtime 内置支持版本管理和流量拆分。要在生产中监控漂移。用户模式会随时间变化。曾经罕见的提问变得常见。新产品上线。术语发生变化。持续对线上交互采样，并依据你的质量指标打分。当你检测到漂移时，例如准确率在两周内从 92% 降到 84%，就要调查并解决根本原因。

[AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 简化了运行这些评估的机制。它提供两种评估模式，以适配开发生命周期的不同阶段。按需评估让你针对预定义的测试数据集评估 agent 表现、在部署前运行测试套件、并排比较两个 prompt 版本，或依据基准事实样本验证模型变更。在线评估持续监控线上生产流量，对真实用户交互采样并打分，从而在质量下降时及时发现。两种模式都支持包括 Strands 和 LangGraph 在内的流行框架，通过 OpenTelemetry 和 OpenInference 插桩实现。当你的 agent 执行时，追踪会被自动捕获、转换为统一格式，并使用 LLM-as-Judge 技术打分。你可以使用内置评估器来评估有用性、有害性和准确性等常见质量维度。对于领域特定需求，可以用自己的打分逻辑创建自定义评估器。下图展示了在 AgentCore Evaluations 上显示的一个指标评估示例。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/03/ML-20055-image-7.jpg)

要建立自动化回滚机制。如果关键指标突破阈值，就自动回退到上一个已知良好的版本。例如，如果幻觉率升到 5% 以上，就回滚并提醒团队。不要等用户来报告问题。

你的测试策略应包含以下要素：

- 每次改动都运行自动化回归测试
- 对重大更新做 A/B 测试
- 在生产中持续采样与评估
- 漂移检测与自动告警
- 质量下降时自动回滚

对 agent 而言，测试不能停止，因为环境不会停止变化。

## 建设组织能力

你的第一个生产 agent 是一项成就。但企业价值来自把这种能力扩展到整个组织。这需要*平台*思维，而不只是*项目*思维。

要持续收集用户反馈和交互模式。关注可观测性仪表盘，识别哪些查询成功、哪些失败，以及生产中出现了哪些测试集里没有的边缘情况。用这些数据扩展你的基准事实数据集。最初五十个测试用例，会基于真实的生产交互增长到数百个。

建立一个平台团队来制定标准并提供共享基础设施。这个平台团队：

- 维护一份经安全团队审查通过的批准工具目录。
- 就可观测性、评估和部署实践提供指导。
- 运行展示各 agent 表现的集中式仪表盘。当新团队想要构建 agent 时。

当新团队想要构建 agent 时，他们从*平台*的工具箱开始。当团队把它们自己的工具和/或 agent 部署到生产后，就可以回馈给*平台*。在规模上，平台团队向组织提供可复用的资产和标准，各团队创建自己的资产，并用经过验证的资产回馈给*平台*。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/03/ML-20055-image-9.jpg)

要在组织内的各 agent 之间实施集中监控。一个仪表盘就能展示所有 agent、会话和成本。当 token 用量异常飙升时，*平台*负责人可以立刻看到。他们可以按团队、按 agent 或按时间段查看，以了解发生了什么变化。

要促进跨团队协作，让团队之间相互学习。三个团队不该构建三个版本的数据库连接器。相反，他们应当通过 AgentCore Gateway 共享工具、共享评估策略，并定期举办会议，让各团队演示自己的 agent 并讨论挑战。这样做，共性问题会浮现，共享的解决方案也会涌现。

组织级扩展的模式是一个爬、走、跑的过程：

- **爬行阶段。**先在内部为一个小型试点团队部署第一个 agent。聚焦学习与迭代。失败的代价很低。
- **行走阶段。**把 agent 部署给受控的外部用户群体。更多用户、更多反馈、发现更多边缘情况。对可观测性和评估的投入开始见效。
- **奔跑阶段。**自信地把 agent 扩展到外部用户。平台能力让其他团队能更快构建自己的 agent。组织能力不断复利增长。

这就是如何从一个开发者构建一个 agent，走向数十个团队构建数十个 agent，同时保持一致的质量、共享的基础设施和不断加快的速度。

## 结论

构建生产就绪的 AI agent，远不只是把基础模型接到你的 API 上。它需要在全生命周期中贯彻严格的工程实践，包括：

- 从小处着手，清晰定义问题
- 从第一天起就全面埋点
- 制定有意识的工具策略
- 自动化你的评估
- 用多 agent 架构分解复杂性
- 以个性化实现安全扩展
- 将 agent 与确定性代码结合
- 持续测试
- 以平台思维建设组织能力

Amazon Bedrock AgentCore 提供落实这些实践所需的服务：

- [AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 在隔离环境中托管 agent 和工具
- [AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html) 支持个性化交互
- [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) 和 [AgentCore Policy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html) 帮助落实安全
- [AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html) 提供可见性
- [AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 支持持续质量评估
- [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 使用标准协议统一 agent 与工具之间的通信
- [AgentCore Browser](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html) 提供一个安全、基于云的浏览器，让 AI agent 能与网站交互；[AgentCore Code Interpreter](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/code-interpreter-tool.html) 让 AI agent 能在沙箱环境中更安全地编写并执行代码。

这些最佳实践并非纸上谈兵。它们来自构建生产 agent、处理真实工作负载的团队经验。在演示中令人惊艳的 agent，与实际交付业务价值的 agent 之间的差别，最终归结为对这些基本功的执行。
