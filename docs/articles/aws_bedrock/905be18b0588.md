# ShipStation Global 如何在 Amazon Bedrock AgentCore 上搭建 AI IT 服务台

*本文由 ShipStation Global 的 Kenneth Salmon、Edward Boswell、Jack Armstrong、Robert Bahn 与 Nick Ciubotariu 共同撰写。*

回答反复出现的同类 IT 问题、清理例行工单，会消耗掉 IT 团队本可用于别处的时间。为了把这段时间夺回来，ShipStation Global 工程团队在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上构建了 *Deckhand*，一个在 Slack 里运行的 AI 驱动 IT 服务台智能体。

[ShipStation Global](https://www.shipstationglobal.com/) 是面向中小发货商的领先智能运输与物流平台，它信奉一个朴素的道理：团队效率越高，给客户的交付就越好。Deckhand 把这一信念落到了实处。它基于一个精心整理的知识库回答常见的 IT 与公司相关问题，能读懂报错信息的截图，并创建和更新 Jira Service Management 工单。

在本文中，我们会介绍 ShipStation 如何设计 Deckhand 的架构，这套设计最终解决了 97.5% 的入站频道提问，并获得员工 96% 的好评（图 1）。

## 业务挑战

Deckhand 要解决的，是每个 IT 团队都会认出的问题：同样的问题被反复提出，报错信息在下班后被贴出来，而所需信息得从不同团队那里收集。在 ShipStation Global，这些对话都发生在一个繁忙的 IT 服务台 Slack 频道里，员工提问、IT 回答，一次一个线程。答案其实通常早就存在——在 Confluence 的一篇操作指南文章里，在公司内网的某个页面上，或者八个月前的某条线程里。难的是把它们找出来。

频道的数据让这一规模变得具体。在上线前的 12 个月里：

- 员工发出了超过 1,500 条线程，而且数量还在持续增长。
- 员工分布在美国、英国、西班牙、波兰、澳大利亚和菲律宾，超过五分之一的提问出现在美国工作时间之外。
- 答案散落在不同地方：Confluence 文章、内网页面和 PDF、IT 维护的指南，以及频道自身的历史。
- 重复性问题占用了本可以由结构化的自助步骤处理掉的时间。

> 「寻求帮助本该像在 Slack 里问一句话那样简单，而不是去琢磨一张工单表单，或者把一封邮件扔进无人应答的虚空。我们相信工单是运营中存在摩擦的信号，而不是生产力的体现。Deckhand 当场解决常见问题；解决不了时，它一键把这段对话转成一张上下文完整的工单，既改善了员工体验，也让我们的团队不必再没完没了地重复那句话：『请先提一张工单。』」
>         — Chris Collins, Senior Director IT at ShipStation Global

## 方案概览

Deckhand 在 Slack 里就像一位同事那样工作——加入频道、阅读对话、从 Slack 个人资料中汲取上下文，就地回答 IT 问题。我们把它运行在 Amazon Bedrock AgentCore 上，这是一个以任意框架、任意模型大规模构建、连接并优化智能体的平台。AgentCore runtime 是 Amazon Bedrock AgentCore 的一项能力，它在隔离的会话中托管智能体，因此我们不必运行任何服务器或容器。

整套方案有四个主要组件，见图 2：

- **Slack 服务：** 一个 FastAPI 与 Slack Bolt 应用，托管在 [AWS App Runner](https://docs.aws.amazon.com/apprunner/latest/dg/what-is-apprunner.html) 上。它接收 Slack 事件，判断机器人是否应当回复，并从提问者的 Slack 个人资料构建用户上下文载荷，包括姓名、邮箱、时区和经理。
- **智能体服务：** 一个 Strands 智能体，以容器形式部署在 [Amazon Bedrock AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html) 上，使用 [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html) 中的 Anthropic Claude 管理多轮的工具调用智能体循环。
- **工具与知识：** 单个 [AWS Lambda](https://docs.aws.amazon.com/lambda/latest/dg/welcome.html) 函数，通过 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-core-concepts.html)（Amazon Bedrock AgentCore 的一项能力）以 Model Context Protocol（MCP）工具的形式对外暴露，负责给请求分类、创建和更新 Jira 工单、分析图像。一个 [Amazon Bedrock 知识库](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html) 索引来自 Confluence、公司内网、Slack 和市场页面的内容，并把它们存入 [Amazon Simple Storage Service (Amazon S3)](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)。
- **运维与反馈。** [Amazon DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Introduction.html) 存储反馈，[AWS X-Ray](https://docs.aws.amazon.com/xray/latest/devguide/aws-xray.html) 借助 OpenTelemetry 追踪请求路径，各服务把日志写入 [Amazon CloudWatch](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/WhatIsCloudWatchLogs.html)。

## Deckhand 工作流

本节逐步介绍 Deckhand 的实现方式，从前置条件到可用的部署。

### 前置条件

要实现这一模式，你需要以下内容：

- 一个 AWS 账户，可访问 Amazon Bedrock、AgentCore runtime 和 AgentCore Gateway。
- 一个 Slack 应用，具备事件订阅、签名密钥（signing secret），以及按你的用例划定权限范围的 bot token。
- 一个容器镜像仓库，例如 Amazon Elastic Container Registry (Amazon ECR)。
- 一个 Amazon S3 桶和一个 Amazon Bedrock 知识库。
- 为每个 runtime 和工具分别限定范围的 AWS Identity and Access Management (IAM) 角色，以及用于存放第三方凭据的 AWS Secrets Manager 条目。

### 用 Strands Agents 与 AgentCore 构建智能体

这个智能体刻意保持轻量。借助开源的 [Strands Agents SDK](https://aws.amazon.com/blogs/opensource/introducing-strands-agents-an-open-source-ai-agents-sdk/)，一个智能体由模型、一组工具和一段系统提示词构成。SDK 负责管理推理循环，让模型挑选工具、处理结果并反复迭代，直到给出答案。Deckhand 的智能体服务用几行 Python 就实现了。

```
from strands import Agent
from strands.models import BedrockModel
from strands.tools.mcp import MCPClient
from strands_tools import retrieve
from mcp.client.streamable_http import streamablehttp_client

model = BedrockModel(
    model_id=MODEL_ID,
    max_tokens=2048,
    temperature=0.3,
)

gateway = MCPClient(lambda: streamablehttp_client(url=GATEWAY_URL))

agent = Agent(
    model=model,
    tools=[gateway, retrieve],
    system_prompt=SYSTEM_PROMPT,
)
```

模型 ID 通过环境变量设置，因此切换模型无需修改应用代码。

工具以两种方式接入智能体。Amazon Bedrock Knowledge Bases 检索是 Strands 的一个原生工具，只需一次 import 就能支持知识库搜索。其余功能——包括分类、工单管理、用户信息解析和图像分析——由注册在 AgentCore Gateway 上的一个 Lambda 函数承担。Gateway 把这些功能以 MCP 工具暴露出来，Lambda 再按工具名路由每一次调用。这种分离让工具逻辑可以独立更新，智能体能直接从 Gateway 获得新工具，无需重新构建。

AgentCore runtime 以容器形式托管智能体，从而不必做服务器或会话管理。Slack 服务对每条消息同步调用智能体，把线程对话记录和用户上下文一并提供，然后发布最终回复。由于上下文（包括员工的个人资料）随每个请求一并传入，智能体能够自动补全工单细节。

### 知识库设计与答案路由

Deckhand 从一个 Amazon Bedrock 知识库作答，该知识库包含以下以 S3 为底层存储的核心数据源：

- 从 Confluence 同步的文章。
- 从公司内网同步的内部页面、PDF 和活动。
- 从 Slack 中挖掘出的已解决支持线程（下一节会展开）。

每份文档都带有元数据，例如标题、来源 URL、内容类型和活动日期。这让智能体能够过滤内容，比如用户询问即将举办的活动，或奥斯汀办公室的每周午餐菜单。

### 用 Recursive Language Models（RLMs）挖掘 Slack 历史

最有价值的数据源是已解决支持线程的归档。在 Deckhand 出现之前，Slack 正是问题被解决的地方：多年来员工描述问题、IT 带着他们一步步完成修复。这段历史是一座有机的知识库，而且经过了最好的审阅者验证——问题被解决的那个人。它同时也很嘈杂：原始导出里混着玩笑寒暄、自动告警，以及那些其实从未解决的线程。把一条未经验证的修复方法或一份残缺的摘要索引进来，知识库就会以同样的自信给出错误答案，所以提取必须精确。

挖掘流程遵循一条三阶段流水线（图 5）：

- 一个脚本通过 Slack API 导出频道的完整历史，为每个线程取回完整回复，并写出一份结构化转储，其中包含线程标记、时间戳和回复数量。
- DSPy 的 Recursive Language Model（RLM）在 Amazon Bedrock 上运行 Claude，把那份导出当作一个可导航的内存空间来对待，置于沙箱化的 Python read-eval-print loop（REPL）之中，而不是当成单个提示词。它在这份数据上迭代作业，把每个线程判定为已解决、未解决或已升级，并过滤掉公告类内容与非提问内容。严格的判定标准保证质量：只有当完整且可执行的修复方案在线程本身里清晰可见时，这个线程才算已解决。
- 对每个已解决的线程，RLM 编排递归的 sub-LLM（large language model）调用来抽取结构化字段，每个字段都用 Pydantic 模型校验。这些字段包括问题摘要、原始提问和处理结果，还记录该修复属于自助解决还是需要建工单、自助步骤、涉及的应用与系统、错误信息以及标签。当某次 sub-LLM 调用返回的内容不符合 schema，RLM 基于代码的循环会在解释器里捕获校验错误并重试。结果被写成一份按问题组织的 markdown 文档，流水线把它上传到 Amazon S3，供知识库索引。

![三阶段流水线图：导出 Slack 频道历史、把线程判定为已解决或未解决、抽取结构化字段](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/08/ML-21795-5.png)

图 5：Slack 会话的导出、判定与抽取工作流

我们选择 [RLM](https://dspy.ai/diving-deeper/rlm)，是因为它把整个 Slack 历史保存在一个持久的沙箱变量空间里，既能对导出内容做迭代式推理，又能保证输出结构一致。带来的结果是：当员工遇到的问题曾被同事解决过，Deckhand 就能给出那个经过验证的方案，而且常常是可直接执行的编号步骤。

### 知道什么时候不该作答

在共享频道里，AI 机器人往往先在社交层面失败，才在技术层面失败。Deckhand 最精细的一块逻辑，就是决定什么时候保持沉默：

- 智能体对每条消息做的第一个判断，是它属于公告、社交消息，还是人与人之间的对话。若是，就输出「SKIP」，Slack 服务随即不发出回复。
- 在线程里，它只回复最初发帖的人。
- 如果最后一条回复来自另一位人类助手，它就保持沉默，因为已经有人接手了。
- 如果一条回复以 @ 提及某个人的方式开头，那这条消息就不是发给机器人的。

### 收集反馈

每条回答都带反馈按钮。点赞会直接记录，点踩则提示填写一段简短的「哪里出了问题」。评分连同原始提问和机器人的回复一起存入 DynamoDB。

负面反馈是一份很有价值的数据集，用来改进系统提示词和智能体行为，并更新知识库里错误的信息。

### 安全与校验

提示词规则能强化行为，但不能取代访问控制。强制约束由代码和基础设施来落实：

- 创建工单需要显式确认。当 Deckhand 提出创建工单时，Slack 服务会加一个 **Create Ticket** 按钮，选择它即通过智能体发出确认。更新工单只接受符合帮助台项目模式的合法工单号，并拒绝空评论。
- 分类在生效前先经过校验。请求分类作为一次独立的 [Amazon Bedrock Converse API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html) 调用执行，返回结构化的工单字段，在任何东西进入 Jira 之前先用 Pydantic 校验。
- 图像工具被限制为只能从 Slack 的文件主机下载。它用 bot token 认证，每次请求限制为最多 5 张图、单张不超过 5 MB，并通过 Converse API 把文件发给视觉模型。
- 凭据不落在代码里。Slack token、签名密钥和 Jira 凭据都存放在 [AWS Secrets Manager](https://docs.aws.amazon.com/secretsmanager/latest/userguide/intro.html) 中，每个服务和工具都在各自限定范围的 IAM 角色下运行。
- 提示词强制行为层面的防护：绝不索取密码或多因素认证（MFA）验证码，绝不在工单评论里写凭据，绝不暴露用于填充工单字段的个人资料元数据。

## 成果

Deckhand 于 2026 年 4 月上线。起初每天约 30 条消息，到初夏最多时达到 100 条。前三个月它处理了 1,935 条消息，发起了 1,221 次智能体对话，开出 409 张 Jira 工单。它对 97.5% 的消息作出了回复。三分之一的提问出现在下班时间，那时 IT 团队无人值班，而 Deckhand 回答了其中 94%。本来要等到第二天早上才有答复的人，当晚就拿到了答案。

随着团队持续打磨，反馈也在变好。好评率从 4 月的 82% 升到 6 月的 96%，此前他们修订了系统提示词和知识库，针对大家抱怨的问题逐一修正。

最明显的收益是工单拦截。一次智能体对话，对应的是一个原本会变成 Jira 工单的问题。在 1,221 次对话中，只有 409 次最终变成工单，其余 812 次都在对话里处理掉了。提交一张工单、再推进并关闭它大约要花 30 分钟。这 812 次对话三个月累计约 406 小时，一年约 1,600 小时。员工把这段时间留给了自己的工作，IT 也不必再把它花在工单受理上。

## 总结

Deckhand 把重复的 IT 提问从人们的日程上摘了下来，把时间还给员工和 IT 团队。它之所以行得通，是因为技术栈里每一块只承担一件事，并且都以托管服务形式运行：AgentCore runtime 托管智能体，AgentCore Gateway 把一个 Lambda 函数变成智能体可调用的 MCP 工具，Amazon Bedrock Knowledge Bases 负责检索。团队上线它时没有自建服务器，也不用维护编排代码。

要构建类似的方案，请从一处维护良好的知识来源和一个定义清晰的动作开始。智能体开发参见 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html) 和 [Strands Agents SDK](https://aws.amazon.com/blogs/opensource/introducing-strands-agents-an-open-source-ai-agents-sdk/)，内容源接入参见 [Amazon Bedrock Knowledge Bases 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html)。

如果你想讨论适合你组织的 agentic AI 用例，请联系你的 AWS 客户经理团队。
