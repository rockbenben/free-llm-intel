通用智能体能处理广泛的任务，但你仍需要它们遵循那些驱动你业务的规程：合规检查、文档处理工作流、升级策略、工程约定。把所有这些塞进一个 system prompt 或应用逻辑里，会变得难以维护和更新。技能（skills）是一种模块化的替代。一个技能是一组可复用的指令，通常存储在一个 `SKILL.md` 文件里，它教会智能体一项领域特定的任务，例如编辑一份合同、对账一张发票，或遵循一个团队的 pull-request 约定。因为技能遵循开放的 Agent Skills 标准，它们可在兼容的 harness 之间移植，且智能体在运行时只加载它所需的技能，而不必把每条规程都带在其核心指令里。

一个技能把一个或多个工具连同智能体正确使用它们所需的上下文一起打包：

- **指令（Instructions）**：注入智能体上下文的领域特定指导和约束。
- **工具绑定（Tool bindings）**：技能所依赖的 API、Model Context Protocol (MCP) 服务器或本地命令。
- **知识（Knowledge）**：参考材料和实作示例。
- **工作流（Workflow）**：技能所遵循的多步规程或决策逻辑。
- **护栏（Guardrails）**：格式要求、范围限制和校验规则。

这种模块化方法帮助团队更快地专业化智能体、跨智能体和工作流复用已验证的规程、保持一致的行为，并在不微调底层模型、不重写智能体核心逻辑的情况下更新领域特定的指导。

智能体中这种技能可组合性引入了两种通用输出质量指标可能漏掉的失败模式：智能体调用了一个不适合该任务的技能，以及智能体调用了正确的技能却跳过或只部分遵循了其指令。这两种失败都能在不使用你预设领域知识的情况下产出一个流畅、看似合理的响应。因此一次评估不能只检视最终响应。

为了让这些失败可度量，[Strands Evals SDK](https://strandsagents.com/docs/user-guide/evals-sdk/quickstart/) 和 Amazon Bedrock AgentCore 的一项能力 [Amazon Bedrock AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 增加了以技能为焦点的评估器：

- Skill Selection Accuracy 判定每个被调用的技能对该任务是否为一个合适的选择。它对每个被调用的技能返回一个二元结果。
- Skill Instruction Following 判定智能体在多大程度上遵循了一个被调用技能的指令。它对每条规定步骤返回一个基于证据的五级评分。
- 此外在 Strands Evals 上，Skill Invoked 是一个确定性的检查，判断一个具名技能是否已被成功加载。

在本文中，你将学习如何在 Strands Evals 中从一条记录下来的轨迹评估技能选择和指令遵循、如何给一个测试套件添加确定性路由检查、如何用 AgentCore Evaluations 从 OpenTelemetry trace 评估技能行为，以及如何解读逐技能结果以选择正确的修复——全部通过 AgentCore CLI 完成。

## 理解每个评估器衡量什么

智能体接收一个任务和一份技能目录，选择一个技能、加载它并行动。这次运行在 Strands Evals 中被记录为一条轨迹，或在你的可观测层中被记录为一个 OpenTelemetry trace。这份记录现在可以用于全部三个技能评估器。[Skill Selection Accuracy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/skill-evaluators.html#skill-evaluators-ssa) 检查每个被调用的技能是否契合任务，以及智能体是否调用了正确的技能。下图展示智能体如何从提供给它的 1:n 技能中选择一个技能。Skill Selection Accuracy 随后为所选技能是否是针对该任务的正确那个打分。你可以在 [prompt 模板文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/prompt-templates-builtin.html#skill-selection-accuracy)中找到该评估器的 prompt 模板和评分细则。

图 1：Skill Selection Accuracy 检查智能体是否为任务选择了一个合适的技能

[Skill Instruction Following](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/skill-evaluators.html#skill-evaluators-sif) 问的是智能体在多大程度上遵循了那个技能规定的步骤。你可以在 [prompt 模板文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/prompt-templates-builtin.html#skill-instruction-following)中找到该评估器的 prompt 模板和评分细则。

图 2：Skill Instruction Following 衡量智能体在多大程度上完整地遵循了技能的步骤

`SkillInvoked` 是确定性的。它不调用任何模型，且是 Strands Evals 特有的。

下面这张图以图示方式展示了这些技能评估器的概览。

图 3：三个技能评估器的概览

考虑一个带休假（PTO）规划和讨论员工福利技能的 [HR 助手智能体](https://github.com/awslabs/agentcore-samples/tree/main/01-features/06-observe-evaluate-optimize-your-agent/02-evaluate/skills-evaluation)。一名员工询问其牙科和视力福利。如果智能体调用福利技能，它可能产出一个更完善的响应。如果工具调用成功了但智能体选错了操作手册（playbook），Skill Selection Accuracy 会隔离出那个路由决定。

现在假设智能体为一个相关请求正确调用了 PTO 规划技能。该技能指示智能体识别 `employee_id`、查 PTO 余额、对照最新 HR 政策检查结转规则，然后在条件允许时提交一个 PTO 请求。如果智能体查了 PTO 余额却跳过了结转规则，它可能仍返回一个看似合理的响应，同时违反了规定流程。Skill Instruction Following 会隔离出那个执行失败并识别被跳过的步骤。

这些失败需要不同的修复。一次不合适的选择通常指向重叠或有歧义的技能描述。不完整的指令遵循可能需要更清晰的步骤、一种不同的技能结构，或一个更强大的智能体模型。

| **评估器** | **可用性** | **评分** | **回答的问题** |
| --- | --- | --- | --- |
| **Skill Selection Accuracy** | Strands Evals 和 AgentCore Evaluations | 二元，逐被调用技能 | 调用这个技能对该任务合适吗？ |
| **Skill Instruction Following** | Strands Evals 和 AgentCore Evaluations | 五级，逐被调用技能 | 智能体在多大程度上遵循了这个技能规定的步骤？ |
| **Skill Invoked** | Strands Evals | 二元，确定性 | 这个具名技能是否被成功加载？ |

因为基于判断（judge-based）的评估器返回逐被调用技能的结果，多技能运行仍可诊断：你能识别是哪个选择或指令遵循结果拉低了总分数。若没有技能被调用，基于判断的评估器不产生分数。当一个回归测试有已知路由要求时，把它们与 `SkillInvoked` 配对使用。

## 前提条件

- Python 3.10 或更高版本。
- 一个具有 Amazon Bedrock 访问权限的 AWS 账户，以及为判断（judge）模型带 `InvokeModel` 权限的凭证。

**要跟随 Strands Evals 一节，安装这些 SDK：**

```
pip install strands-agents-evals strands-agents
```

你还需要一条记录下来的智能体运行。技能评估器接受 Strands Evals Session 或一个原始消息列表作为轨迹。在发布时，技能提取能识别来自 Strands AgentSkills 插件、Claude Code、Claude Agent SDK、OpenAI Agents SDK、Codex、Gemini CLI、OpenHands、Google ADK 和通用 `SKILL.md` 文件读取的信号。

**要跟随 AgentCore Evaluations 一节，你需要：**

- 一个托管在 Amazon Bedrock AgentCore runtime 或其他地方的智能体。我们用 [HR 助手智能体](https://github.com/awslabs/agentcore-samples/blob/main/01-features/06-observe-evaluate-optimize-your-agent/02-evaluate/utils/hr_assistant_agent.py) 的例子，你可以在你的账户中部署它。
- 为该智能体启用可观测性，使它把遥测投递到 Amazon CloudWatch。
- 在 CloudWatch 中启用 Transaction Search。

本文的例子使用 AgentCore CLI：

```
npm install -g @aws/agentcore
```

## 用 Strands Evals 评估一条记录下来的轨迹

当你控制测试用例并能在开发或持续集成期间重跑智能体时，Strands Evals 很有用。为 HR 助手智能体创建的完整 Strands evals 代码示例见[完整代码示例](https://github.com/awslabs/agentcore-samples/blob/main/01-features/06-observe-evaluate-optimize-your-agent/02-evaluate/skills-evaluation/inner_loop_eval.py)。

## 1. 定义用例和评估器

```
from strands_evals import Case, Experiment
from strands_evals.evaluators import (
    SkillInstructionFollowingEvaluator,
    SkillInvoked,
    SkillSelectionAccuracyEvaluator,
)

case = Case(
    name="q3-revenue-tables",
    input="Summarize the revenue tables in q3-report.pdf",
)

evaluators = [
    SkillSelectionAccuracyEvaluator(),
    SkillInstructionFollowingEvaluator(),
    SkillInvoked(skill_name="pdf-table-extraction"),
]
```

## 2. 运行智能体并捕获其轨迹

技能评估器读取这次运行的轨迹。TracedHandler 收集智能体的 span 并把它们作为轨迹附加：

```
from strands import Agent
from strands_evals import TracedHandler, eval_task

@eval_task(TracedHandler())
def task_function():
    return Agent(...) # your skill-equipped agent

experiment = Experiment(cases=[case], evaluators=evaluators)
report = experiment.run_evaluations(task_function)
report.run_display()
```

## 3. 解读报告

假设智能体加载了 `pdf-table-extraction`、运行了 `pdftotext -layout`，但从未打开提取出的文件或定位表格边界。一个简化后的报告：

```
SkillSelectionAccuracyEvaluator: score=1.00, pass=True
pdf-table-extraction: The skill directly matches the request.
SkillInstructionFollowingEvaluator: score=0.50, pass=False
pdf-table-extraction: The extraction phase was completed,
the table-boundary phase was skipped.
Steps:
- Extract text with layout preservation: covered
- Locate table boundaries: skipped
- Summarize each table's headline figure: partial
SkillInvoked: score=1.00, pass=True
skill 'pdf-table-extraction' was invoked
```

Skill Instruction Following 使用五个等级：Fully Followed（1.0）、Mostly Followed（0.75）、Partially Followed（0.5）、Minimally Followed（0.25）和 Not Followed（0.0）。它在 Mostly Followed 或更好时通过。

## 把检查变成一道部署关卡

- 为每一个特定回归用例必须调用的关键技能添加 `SkillInvoked`。因为它不调用模型，它是一个快速的路由断言。
- 用 `report.test_passes` 对构建把关：`if not all(report.test_passes): raise SystemExit(1)`。
- 用总分数跟踪更广泛的趋势，但在强制执行阈值前，先在你自己的用例上校准它。

## 用 AgentCore Evaluations 评估生产 trace

AgentCore Evaluations 直接作用于现有的 OpenTelemetry trace，支持按需评估、对存储会话的批处理，以及对实时流量的持续采样。遥测被组织为会话（sessions）、trace 和 span。因为技能评估器在工具调用级运作，每个结果都带一个 `spanContext`，其中含有被识别技能调用的 `sessionId`、`traceId` 和 `spanId`。

一次技能调用通过 `SKILL.md` 文件系统读取来识别（这跨框架都适用），或通过 Strands Agents、LangGraph Deep Agents、Google ADK 或 Claude Agent SDK 中原生的技能加载工具来识别。

## 用于自定义评估器的 trace 占位符

AgentCore Evaluations 为技能内建了两个基于判断的评估器。要为内建评估器未覆盖的东西打分，在 `TOOL_CALL` 级创建一个自定义评估器。工具级模板可以引用技能占位符：

| **占位符** | **内容** |
| --- | --- |
| `{invoked_skill}` | 本次工具调用上加载的技能名 |
| `{skill_content}` | 加载的 SKILL.md 正文 |
| `{available_skills}` | 运行时提供的目录，或“(not recorded by this harness)” |
| `{user_message}` | 触发该调用的请求 |
| `{context}` | 对话记录 |

例如，一个检查技能运行某一项特定属性的模板：

```
## Skill instructions

{skill_content}

## Conversation record

{context}

## Evaluation Question

Did the agent complete every numbered step in the skill instructions above, in the order given? Answer Yes or No.
```

你引用的占位符也决定了评估器何时运行。一个含 `{invoked_skill}` 的模板只在技能调用 span 上运行，而一个含 `{skill_content}` 的还额外需要加载的正文。

下面的命令针对那个单独启用了技能的运行时。用 skills-evaluation/`agent_config.json` 中的运行时名（`agent_id` 或 `agent_arn`）替换 `<skill-runtime>`。`Strands.SkillInvoked` 只在客户端侧，没有 CLI 等价命令。

## 运行一次按需评估

用按需评估来调查一个会话、验证一个近期改动，或评估灰度（staged）流量：

```
agentcore run eval \
  --runtime <skill-runtime> \
  --evaluator Builtin.SkillSelectionAccuracy Builtin.SkillInstructionFollowing \
  --session-id <session-id>
```

## 运行一次批量评估

用批量评估一次性为大量存储的会话打分，例如在一次技能目录改动前建立一个基线：

```
agentcore run batch-evaluation \
  --runtime <skill-runtime> \
  --evaluator Builtin.SkillSelectionAccuracy Builtin.SkillInstructionFollowing
```

## 配置持续在线评估

在线评估采样实时流量，好让你检测出精心挑选的测试集未曾预料到的行为：

```
agentcore add online-eval \
  --name HRSkillsProductionEval \
  --runtime <skill-runtime> \
  --evaluator Builtin.SkillSelectionAccuracy Builtin.SkillInstructionFollowing \
  --sampling-rate 100 \
  --enable-on-create
```

然后部署以配置在线评估配置：

```
agentcore deploy
```

持续评估对检测目录漂移（当一个新技能与一个现有描述重叠时）、预料之外的措辞（当真实请求与精心挑选的测试 prompt 不同时）和长会话失败（当指令遵循随上下文增长而退化时）尤其有用。

## 最佳实践

在评估智能体技能时，首先要内化的是路由和执行是两种不同的失败模式，而你的评估策略需要干净地把它们分开。如果你看到一个高选择分数却低的指令遵循分数，那表明路由器挑了正确的技能但它没被完整执行。相反的模式意味着这个技能本来会正常工作，只是它没被调用。同时跑这两个评估，而不是把它们坍缩成一个通过/失败数字，正是让你能区分这两个故事的关键。

在构建任何自定义东西之前，先用内建评估器建立一个基线，这样你之后加的任何自定义逻辑才能覆盖基线实际漏掉的缺口。对于你已经知道正确路由行为的要求，不要依赖一个判断模型去捕获它。为每个必须触发的技能加一个确定性的 `SkillInvoked` 断言。

在你运行评估之后，要抵制只看总分数的冲动。逐步骤的证据才是真正诊断发生的地方。它告诉你一条指令是完全覆盖、部分完成还是整个被跳过，而这种细节才是让一个失败的评估变成可执行修复的东西。这也正是为什么你应该在每个生命周期阶段评估，而不是等最终输出。末端的失败并不告诉你路由器是把请求送到了错误的地方，还是正确的技能执行得糟糕，而你需要两个信号才知道该修什么。

技能级和端到端评估应当配对进行，因为一个技能可能完美执行，却对它面前这个请求而言是错误的技能。通过撰写真正具区分度的技能描述，你能在上游消除大量这种歧义。同样的逻辑适用于一个技能的范围。一个为处理六种不相关功能而打造的技能没有单一的“正确行为”定义，这使它几乎无法被一致地评估。

清楚声明只应评估某次运行中实际走的那条路径，否则未走的分支会被误计为被跳过的步骤，悄然破坏你的通过率。而在你信任任何这些分数之前，先验证你的提取流水线在实际对着实时 trace 是正常工作的。

当你跨工具扩展这一做法时，阈值可能无法干净地迁移。每个评估面都需要按其自身条件校准，因为在 Strands Evals 上的一个通过分数与在 AgentCore Evaluations 上的一个通过分数并不保证意味着同一件事。而最终，这一切都不该活在部署流水线之外。技能质量回归需要像一个失败的单元测试那样阻断发布，否则你到此为止做的评估工作实际上并没有保护生产。

## 结论

技能让智能体的专业化变得廉价，但一个看似合理的最终答案并不证明智能体选择了正确的规程或遵循了它。Skill Selection Accuracy 和 Skill Instruction Following 把这些失败模式分开，并为每个被调用的技能返回证据。在 Strands Evals 中，`SkillInvoked` 为已知路由要求加上一道确定性的守卫。在 AgentCore Evaluations 中，这两个基于判断的指标可以针对特定会话按需运行、作为对存储会话的一批运行，或对采样流量持续运行。

当你有可重跑的测试用例和记录下来的轨迹时，用 Strands Evals。当你想评估来自灰度或实时智能体的 OpenTelemetry trace 时，用 AgentCore Evaluations。许多团队会两者都用：部署前用确定性和基于判断的关卡，随后在生产中用基于 trace 的监控。
