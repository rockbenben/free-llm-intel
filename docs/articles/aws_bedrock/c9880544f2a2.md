# 使用 Amazon Bedrock AgentCore Evaluations 评估任何 agent 框架

构建生产级 agent 的 AI 团队面临一种令人沮丧的不对称：agent 框架的多样性持续增长，但评估工具却没跟上。大多数评估系统假定你以某种特定方式构建 agent：特定的 SDK、特定的大语言模型（LLM）客户端、特定的追踪模式。一旦走出这个狭窄的兼容区间，评估 pipeline 就会失效。

团队选择 LangGraph，是看中它的工作流编排模型；选择 LlamaIndex，是因为它与检索 pipeline 紧密集成；当组织统一采用 GPT 模型时，则选用 OpenAI Agents SDK。他们用 Google ADK 做多 agent 协同，或用 Claude Agent SDK 取得 Anthropic 的原生能力。他们也会选用 Strands Agents——它的模型驱动循环能让一个可用 agent 在几分钟而不是几天内跑在 Amazon Bedrock AgentCore 上。而且越来越多的情况下，他们把这些都部署在 [Amazon Bedrock AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 上，这是 Amazon Bedrock AgentCore 的一项能力。它负责托管、扩缩容、记忆与可观测性基础设施，而这些原本要为每个项目重新搭建。

[Amazon Bedrock AgentCore evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 通过把评估与框架选择解耦，解决了这种碎片化问题。每个主流框架都支持 OpenTelemetry，要么原生支持，要么通过社区埋点库支持。只要 agent 的遥测通过 OpenTelemetry 流转，评估服务就能给它打分，无论底层是哪个 SDK。本文解释这套机制如何工作：服务读取哪些遥测、如何决定读取你的 span、哪些属性承载评估数据，以及覆盖范围如何延伸到点名列表之外的框架。

## 作为共同语言的 OpenTelemetry

OpenTelemetry 是一个厂商中立的埋点框架，用于标准化分布式系统输出 trace、metric 与日志的方式。一条 trace 是一棵 span 树，每个 span 表示请求中的单个步骤：一个工作单元，带有名称、时间戳、一组带类型的属性，以及可选的 span event。span 通过 OpenTelemetry Protocol（OTLP）导出，并由遥测后端收集。在 AgentCore runtime 上，该后端是 AWS Distro for OpenTelemetry（ADOT），它会把 span 与 event 记录路由到 Amazon CloudWatch。

agent 的执行会产生许多种 span，因为 agent 会做许多种工作。单次用户轮次就可能生成以下 span：模型调用、工具调用、从向量存储或数据库检索文档、对检索结果重排序、生成 embedding、guardrail 检查、prompt 模板渲染、memory 读写，以及把它们串联起来的编排步骤。两套约定对这些操作给出了明确命名：[OpenTelemetry GenAI conventions](https://github.com/open-telemetry/semantic-conventions-genai) 定义了 `chat`、`embeddings`、`retrieval`、`execute_tool`、`invoke_agent`、`create_agent`、`plan` 等操作，以及一系列 memory 操作。[OpenInference](https://github.com/Arize-ai/openinference) 则定义了 `LLM`、`TOOL`、`RETRIEVER`、`RERANKER`、`EMBEDDING`、`AGENT`、`CHAIN`、`GUARDRAIL`、`EVALUATOR` 和 `PROMPT` 等 span kind。生产环境的 trace 常常会混合其中好几种。

在这完整集合中，评估服务需要三类 span 角色，才能重建一个 session 中发生的事并对其打分：

- 一个 **invoke agent span**，表示顶层的请求-响应周期，也就是对话中的一次用户轮次。它携带用户 prompt 与 agent 的最终响应。
- **inference span**，表示单次模型调用，每个都携带传给模型的消息历史与模型的回复。
- **execute tool span**，表示 agent 调用的每个工具，携带工具名、输入参数与结果。

这三类正是评估器所处理的对象。服务会对收到的每个 span 分类，从这三类角色中读取所需的值，并跳过其余部分。携带 retrieval、reranking、guardrail 或 memory span 的更丰富 trace 无需任何特殊配置即可处理。那些 span 只是补充了评估器并不需要的上下文。随着框架与约定不断新增 span 类型，这种设计保持向前兼容：不熟悉的 span 类型会被当作可以跳过的上下文，而不是错误。

```
Session (one runtimeSessionId)
└── Trace (one user turn, one trace_id)
    ├── invoke agent span ← read: user prompt + final agent response
    ├── inference span ← read: messages to model + model reply
    ├── execute tool span ← read: tool name + parameters + result
    ├── retriever span (context; not required by evaluators)
    ├── inference span ← read: next model call with tool result in history
    └── ... (guardrail, memory, reranker, orchestration spans, and more)
```

服务读取三类被标记的 span 角色，并把其他 span 视为额外的上下文。

不同框架与埋点库会用不同的属性名、嵌套结构和 span 命名约定来记录这三类角色。OpenTelemetry GenAI 语义约定与 OpenInference 规范都为记录这三类 span 角色定义了 schema，但二者使用不同的属性键与不同的 span kind 词表。AgentCore Evaluations 会把两种 schema 桥接到相同的结果。

## AgentCore Evaluations 如何读取你的 trace

当你运行一次评估时（无论是按需触发还是通过在线评估配置），服务都会从 CloudWatch 取回 agent 的 span 与 event 记录，并重建 session。一个 **session** 按 `session.id` 分组。在一个 session 内，每条 **trace**（一个 `trace_id`）是一次用户轮次。每个轮次都由前面描述的三类 span 组成。

服务会对每个 span 分类，抽取所需的值，并把重建出的 session 交给评估器。从这时起，评估完全与框架无关：同一批评估器——GoalSuccessRate、Correctness、Helpfulness 以及自定义的 LLM-as-a-judge——会以完全相同的方式给每个框架打分。下图对此做了可视化展示。

**以上这些你都不需要配置。** 每个 OpenTelemetry 埋点库都会在它产生的 span 与 event 记录上打一个 `scope.name`，评估服务用该值来决定如何读取它们。正确的处理会根据你安装的埋点包自动生效，无需改动 agent 代码。每个受支持的框架及其 scope 名称都列在 Supported agent frameworks 文档中，目前涵盖 Strands Agents、LangGraph、OpenAI Agents SDK、LlamaIndex、Google ADK 和 Claude Agent SDK，其中大多数同时支持 OpenTelemetry 与 OpenInference 埋点。

覆盖范围不限于这些点名的框架。任何 scope 名称落在 `opentelemetry.instrumentation.*`（遵循 OpenTelemetry GenAI 语义约定）或 `openinference.instrumentation.*`（遵循 OpenInference 规范）下的库，都会通过通用路径被读取。实践中，支持一个新框架通常只需安装一个符合规范的埋点包：scope 名称前缀就是库选择加入的方式。名为 `mycompany.agent.tracing` 的 scope 不会被识别，即使它的 span 完全遵循约定。该前缀是埋点作者有意遵循某个有明确文档的 schema 的信号。

要让一个 session 端到端地被评估，归结为两项要求。第一是分组：agent 的 span 必须携带 `session.id` 属性，且其值与你调用 agent 时使用的 `runtimeSessionId` 一致。正是这个属性让服务能把 span 组装成 trace、把 trace 组装成 session。在 AgentCore runtime 上，ADOT 会自动注入该属性，因此无需改动 agent 代码。

第二项要求是数据源必须包含消息内容，而不只是 span。对于启用了[统一可观测性](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-configure.html)的 agent（新建 agent 的默认配置），这是自动的：消息内容与 span 存放在同一个按 agent 划分的日志组中，因此单个日志组就足够。但对于仍在运行统一配置之前那套配置的既有 agent，span 会落到共享的 `aws/spans` 日志组，而消息内容会以关联 event 记录的形式单独存放在该 agent 的日志组中。在这种配置下，如果你的数据源只覆盖 `aws/spans`，span 分类仍会成功，但消息内容会是空的，任何评估响应质量的评估器都会返回错误。

## OpenTelemetry GenAI 语义约定：驱动评估的属性

OpenTelemetry GenAI 语义约定为 LLM 框架产生的 span 定义了一套 schema。AgentCore Evaluations 读取其中一组特定的属性，用来对 span 分类并抽取评估数据。当你调试一次评估或编写自定义埋点时，知道哪些属性承载这些数据会很有用。

span 分类从 `gen_ai.operation.name` 开始：

- `invoke_agent` 标记 invoke agent span，即每个轮次的顶层 span，携带用户 prompt 与最终响应。
- `chat` 标记 inference span。服务读取消息历史与模型的回复。
- `execute_tool` 标记 execute tool span。服务读取工具名、输入参数与结果。

当 `gen_ai.operation.name` 缺失时（这在某些 LlamaIndex 的 trace 中很常见），服务会退回到 `traceloop.span.kind`：其中 `workflow` 映射到 invoke agent span，`tool` 映射到 execute tool span，`llm` 映射到 inference span。

工具身份来自 `gen_ai.tool.name`，而 `gen_ai.tool.call.id` 是关联 ID，用于把 inference span 上请求的工具调用与对应 execute tool span 上的结果关联起来。inference span 上的 `gen_ai.tool.definitions` 属性携带 JSON 编码的工具 schema 数组，GoalSuccessRate 评估器用它来核实 agent 调用的工具确实在其声明可用的工具之中。

消息内容存放的位置取决于遥测是如何采集的，共有两种可能。当遥测被拆分存储时，内容位于关联的 event 记录主体中（`body.input.messages` 与 `body.output.messages`）。当遥测未被拆分时，内容留在 span 上，作为 `gen_ai.input.messages` 或 `gen_ai.output.messages` 属性，或作为行内 span event。服务会从实际存放内容的位置读取，所以你不需要知道某次部署走的是哪条路径。关于内容存放位置的完整说明，请参阅 Spans, event records, and telemetry signals。

## OpenInference 约定：另一种语义层

OpenInference 是由 Arize AI 维护的开放规范，在 LlamaIndex、Haystack 与 Phoenix 生态中被广泛采用。它用与 OpenTelemetry GenAI 约定不同的属性名来表示 LLM 操作。包括使用 `openinference-instrumentation-openai-agents` 的 OpenAI Agents SDK、Google ADK 以及 Claude Agent SDK 在内的多个框架都会产生 OpenInference span。

OpenInference 中的 span 分类使用 `openinference.span.kind`。取值 `LLM`、`TOOL`、`AGENT` 与 `CHAIN` 分别对应 inference、execute tool、invoke agent 与结构性容器 span。

inference span 的消息内容采用扁平、带索引的属性约定。输入消息遵循 `llm.input_messages.{i}.message.role` 与 `llm.input_messages.{i}.message.content` 的模式，其中 `i` 从零开始，消息历史中每条消息递增一次。工具结果消息会额外携带 `llm.input_messages.{i}.message.tool_call_id`，用于把它们关联到对应的工具调用。输出消息遵循同样的索引模式，其中工具调用再嵌套一层：

```
llm.output_messages.0.message.role = "assistant"
llm.output_messages.0.message.tool_calls.0.tool_call.function.name = "get_pto_balance"
llm.output_messages.0.message.tool_calls.0.tool_call.function.arguments = "{\"employee_id\":\"EMP-001\"}"
llm.output_messages.0.message.tool_calls.0.tool_call.id = "call_abc123"
```

inference span 上的工具 schema 使用 `llm.tools.{i}.tool.json_schema`，每个值都是一个 JSON 字符串，编码了普通函数 schema 或 OpenAI 风格的 `{"type": "function", "function": {...}}` 包装。服务两种都能处理，并读取 `name`、`description` 与 `parameters` 字段。

execute tool span 使用三个属性：`tool.name` 表示 ID，`input.value` 表示参数（多参数工具是 JSON 编码的对象，单参数工具是普通字符串），`output.value` 表示结果。`output.value` 的格式在 OpenInference 埋点库的不同版本中有所演进，服务会同时读取新旧两种形态，因此你不会被绑定到某个特定版本。

## 评估任何符合规范的框架

点名的框架是被直接覆盖的，但该设计刻意保持开放。对于该列表之外的任何框架，只要埋点遵循有文档的约定，前面介绍的两条通用路径就能提供广泛覆盖：

- **OpenInference 路径** 处理 `openinference.instrumentation.*` 下的任何 scope。它用 `openinference.span.kind` 对 span 分类，从带索引的 `llm.input_messages` 与 `llm.output_messages` 属性读取 inference 内容，并为工具 span 读取 `tool.name`、`input.value` 与 `output.value`。这覆盖了大多数采用 OpenInference 规范的框架，包括在某些框架被显式点名之后才发布的框架。
- **OpenTelemetry 路径** 处理 `opentelemetry.instrumentation.*` 下的任何 scope。它用 `gen_ai.operation.name` 对 span 分类，从 event 记录主体或 span 读取消息内容，并用 `gen_ai.tool.name` 确定工具身份。

scope 名称前缀决定了某个库被路由到哪条路径。对于编写自定义埋点、并希望被通用评估的团队，把 scope 命名在 `opentelemetry.instrumentation.*` 或 `openinference.instrumentation.*` 下就是选择加入的方式。

## 从 agent 代码到评估分数：完整走查

为说明具体做法，[AgentCore samples 仓库](https://github.com/awslabs/agentcore-samples/tree/main/01-features/06-observe-evaluate-optimize-your-agent/02-evaluate/supported-frameworks) 提供了完整可运行的示例，例如分别用 OpenAI Agents SDK、Google ADK、LlamaIndex 和 Claude Agent SDK 实现的 HR 助手。每个示例都会部署到 AgentCore runtime，并用同一批内置评估器与自定义评估器进行评估。

**两个 agent 的埋点配置都不需要写显式代码。** 在 AgentCore runtime 上，AWS Distro for OpenTelemetry（ADOT）会在启动时发现已安装的埋点包并自动启用。对于 OpenAI Agents SDK 示例，只需把 `opentelemetry-instrumentation-openai-agents` 加入 `requirements.txt`。对于 LlamaIndex 示例，`opentelemetry-instrumentation-llamaindex` 起同样的作用。OpenAI Agents SDK 的 agent 唯一必须避免的是调用 `set_tracing_disabled(True)`：埋点会挂接到 SDK 自身的追踪 pipeline，因此禁用 SDK 追踪会让评估 span 静默消失。

**具体到 LlamaIndex，agent 的结构很关键。** agent 必须构建为 `FunctionAgent` 或 `ReActAgent`（工作流 agent），而不是普通的 `AgentExecutor`。工作流 agent 会发出顶层的 invoke agent span，它是整条 trace 的锚点。没有它，就没有顶层 span 可用来重建该轮次，session 也无法仅凭 inference span 组装出来。

**要可靠地把遥测投递到 CloudWatch，请在调用处理程序结束、返回响应之前执行 flush。** AgentCore runtime 会在处理程序返回后挂起执行环境，而 OTel SDK 会在客户端批处理器中缓冲遥测，并按周期定时导出。因此，返回时未导出的数据可能还留在缓冲区里，且无法保证导出能在挂起之前完成。实践中，遗漏 flush 导致的遥测缺失是评估失败最常见的来源。OpenAI Agents SDK 与 LlamaIndex 示例用以下模式实现这一点：

```
def _flush_telemetry():
    from opentelemetry import trace as _trace
    from opentelemetry._logs import get_logger_provider as _get_lp
    for provider in (_trace.get_tracer_provider(), _get_lp()):
        flush = getattr(provider, "force_flush", None)
        if flush:
            flush()

@app.entrypoint
async def invoke(payload, context):
    prompt = payload.get("prompt", "")
    try:
        result = await run_agent(prompt)
    finally:
        _flush_telemetry()
    return str(result)
```

flush 必须同时覆盖 tracer provider（span）与 logger provider（event 记录）：span 与 event 记录分别经过不同的客户端批处理器，只 flush 其中一个会让另一个的缓冲区未被处理。

**在等待 CloudWatch 摄入 90–150 秒之后，AgentCore Evaluations 对两种框架都同样使用 `EvaluationClient`**：

```
from bedrock_agentcore.evaluation import EvaluationClient
from bedrock_agentcore.evaluation.client import ReferenceInputs
from datetime import timedelta

ec = EvaluationClient(region_name=REGION)
# The client resolves each evaluator's level (SESSION, TRACE, or TOOL_CALL)
# automatically, so no level configuration is needed here.
results = ec.run(
    evaluator_ids=[
        "Builtin.GoalSuccessRate",
        "Builtin.Correctness",
        "Builtin.Helpfulness",
        CUSTOM_RESPONSE_QUALITY_ID,
        CUSTOM_SESSION_COMPLETENESS_ID,
    ],
    agent_id=AGENT_ID,
    session_id=SESSION_ID,
    look_back_time=timedelta(hours=1),
    reference_inputs=ReferenceInputs(
        assertions=ASSERTIONS,
        expected_trajectory=EXPECTED_TRAJECTORY,
        expected_response=EXPECTED_RESPONSES[-1],
    ),
)
```

GoalSuccessRate 评估器在 session 层运行，检查 agent 的工具调用历史是否在所有轮次上匹配预期轨迹。Correctness 与 Helpfulness 是 trace 层评估器，对每个轮次单独打分。[内置评估器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/prompt-templates-builtin.html) 已按 session、trace、tool 层级配置好，并可作为模板使用。对于你配置的[自定义评估器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/custom-evaluators.html)，由你定义它作用在 session、trace 还是 tool 层。可以把不同层级的评估器组合进同一次评估调用。不同框架示例的评估代码在结构上完全相同，差别只在 agent 名称与资源 ID。

## 按需评估与在线评估两种模式

示例仓库演示了两种评估模式，它们在生产 agent 工作流中服务于不同目的。

**按需评估** 天然适合持续集成与持续交付（CI/CD）pipeline 以及回归测试。你先调用 agent 生成一个 session，然后在同一脚本中调用 `EvaluationClient.run()` 给它打分。由于调用由你控制，你可以通过 `ReferenceInputs` 提供 ground truth：预期响应、预期工具轨迹与行为断言。一个在每次 pull request 上运行的 pipeline 可以调用一组固定的测试 prompt、对照 ground truth 打分，并在任一评估器低于阈值时让构建失败。

**在线评估** 持续监控真实 agent 流量。你只需创建一次 `OnlineEvaluationConfig`，把它指向 agent 的 CloudWatch 日志组并指定采样率。服务会在新 session 到达时自动接手：

```
_cp.create_online_evaluation_config(
    onlineEvaluationConfigName="hr_agent_online_eval",
    rule={"samplingConfig": {"samplingPercentage": 25.0}},
    dataSourceConfig={
        "cloudWatchLogs": {
            "logGroupNames": [CW_LOG_GROUP],
            "serviceNames": [OTEL_SERVICE_NAME],
        }
    },
    evaluators=[
        {"evaluatorId": "Builtin.GoalSuccessRate"},
        {"evaluatorId": "Builtin.Correctness"},
        {"evaluatorId": "Builtin.Helpfulness"},
    ],
    evaluationExecutionRoleArn=ONLINE_EVAL_ROLE_ARN,
    enableOnCreate=True,
)
```

在线评估只能使用不需要 ground truth 的评估器，因为真实流量没有关联的预期响应。内置评估器在两种模式下都能用。自定义 LLM-as-a-judge 评估器如果在指令中引用了 `{expected_response}` 或 `{assertions}` 占位符，则只能用于按需评估。

在线评估结果会落到 CloudWatch 日志组 `/aws/bedrock-agentcore/evaluations/results/{config_id}`。基于这些数据构建 CloudWatch 告警或仪表板，你就能通过统一的界面，对生产环境中所有框架的 agent 质量保持持续可见。由于同一条评估 pipeline 对按需流量与在线流量的处理方式完全相同，当 agent 行为稳定时，CI 测试运行的分数与生产流量的分数是可直接比较的。

## 结论

AgentCore Evaluations 与框架无关。无论你用 LangGraph、OpenAI Agents SDK、LlamaIndex、Google ADK、Claude Agent SDK 还是 Strands Agents 构建，同一批评估器都会以相同方式应用于按需模式与在线模式，因为集成契约建立在 OpenTelemetry 标准之上。只要你的 agent 在受认可的 scope 名称下发出 span、在 inference span 上包含工具 schema，并通过 span 属性或 event 记录呈现消息内容，评估服务就会产出分数，你这一侧不需要任何框架专属代码。对于点名列表之外的框架，只要遵循 OpenTelemetry GenAI 约定或 OpenInference 规范，并配上正确的 scope 前缀，就足够了。借助一套评估套件，你现在可以以一致的方式评估每一个在受认可 scope 下发出遥测的 agent。

准备好自己试试了吗？请从 AgentCore Evaluations 的[功能示例](https://github.com/awslabs/agentcore-samples/tree/main/01-features/06-observe-evaluate-optimize-your-agent/02-evaluate/supported-frameworks)开始，并参考[受支持的 agent 框架](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/supported-frameworks.html)文档，了解接入你所选框架的完整细节。
