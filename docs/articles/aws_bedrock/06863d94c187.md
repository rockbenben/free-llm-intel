# Amazon SageMaker Inference：2026 年发布回顾，第 2 部分

模型进入生产环境后，问题就变了。团队想知道：流量已是真实流量，模型现在应该跑在哪种配置上；如何把更多模型塞进已经在付费的 GPU；下一个模型大到一台机器装不下时该怎么办；为什么请求在一个区域排队，而另一个区域的 GPU 却闲着；以及为什么没人动过任何东西，延迟却上升了。本文按团队通常遇到这些问题的顺序逐一展开。

在 HyperPod Inference 方面，它列出了更多路由策略、对模型服务框架更广泛的支持，以及扩展的多区域网络。Inference Gateway 负责路由，托管版 NVIDIA Dynamo 是新的服务框架。对于托管端点，路线图指向与 AWS AI 其余版图更深的集成。Inference recommendations 现在可以从 Amazon SageMaker AI Studio、SageMaker Python SDK，以及工程师已经在用的编码代理中运行，端点现在也可以跨区域和跨账户路由请求。

为了让每一节都具体，我们在整篇博客中跟随一个假设团队。春天，他们借助第 1 部分的发布成果，在单个 SageMaker AI 端点后面、基于 70B 参数模型上线了一个客户支持助手。到了秋天，他们需要支持更多产品线、采用更大的推理模型、在第二个区域服务客户，并保持 GPU 账单不增长。

## 无论在哪里工作，都能选对配置

团队根据 4 月的一次基准测试运行选定了第一套配置。自那以后，他们新增了四个 LoRA（Low-Rank Adaptation）适配器，每条产品线一个，产品团队还设定了峰值负载下首 token 时延（TTFT）500 毫秒的目标。4 月的配置从未针对这两项变化测试过。要重新运行分析的工程师在 notebook 和编码代理中工作，很少有人使用控制台。

Inference recommendations 于 4 月以 API 形式发布。此后的四次更新让它进入团队工作的更多场所，并让它能回答两个更难的问题：一个端点能承载多少个适配器，以及在达不到延迟目标之前它能承受多少并发。一项新的 agent skill 把同样的专业能力带入编码代理。

### SageMaker AI Studio 中的 inference recommendations（2026 年 7 月）

*博客：* [Launching UI for generative AI inference recommendations in Amazon SageMaker AI](https://aws.amazon.com/blogs/machine-learning/launching-ui-for-generative-ai-inference-recommendations-in-amazon-sagemaker-ai/)

4 月的发布通过 API 自动完成实例、容器和优化选择。Inference recommendations 现在也以引导式、低代码工作流的形式在 SageMaker AI Studio 中提供。在 Studio 中，选择 **Jobs**，然后选择 **Inference optimization**。选择一个用例配置（Interact、Generate、Summarize 或 Custom）、一个优化目标（最小化延迟、最大化吞吐量或最小化成本），以及一个来自 SageMaker JumpStart、Amazon Simple Storage Service（Amazon S3）、Model Registry 或现有 SageMaker 模型的模型。

SageMaker AI 在真实 GPU 基础设施上使用 NVIDIA AIPerf 对候选配置进行基准测试，并应用与目标匹配的技术，例如为吞吐量使用投机解码，或为延迟进行内核调优。你可以按 TTFT、token 间延迟、吞吐量和成本比较排名结果，然后从 Studio 将所选配置部署到实时端点。

### SageMaker Python SDK v3 中的 inference recommendations（2026 年 8 月）

*博客：[LLM optimization integration for Amazon SageMaker Python SDK](https://aws.amazon.com/blogs/machine-learning/llm-optimization-integration-for-amazon-sagemaker-python-sdk/)*

此前，基准测试和推荐需要 SageMaker AI Studio 或直接调用 Boto3。现在它们成为 SageMaker Python SDK v3（3.17.0 及更高版本）的一部分，这是团队用于训练和部署的同一接口，因此该工作流可以融入 notebook、CI 流水线和 MLOps 工作流。你可以针对工作负载流量对实时端点进行基准测试，为延迟、吞吐量或成本目标生成排名推荐，并在一次调用中将排名最高的配置部署到实时端点。

该 SDK 还支持更长的工作流。你可以并行运行推荐作业，以比较 LMI 和 vLLM 等服务框架；也可以从已完成的作业恢复，从而在不同的 notebook 或流水线阶段进行部署，而无需重新运行基准测试。

### Inference recommendations 中的 LoRA 适配器支持（2026 年 9 月）

*开发人员指南*：[Get recommendations for models with LoRA adapters](https://docs.aws.amazon.com/sagemaker/latest/dg/generative-ai-inference-recommendations-adapters.html)

许多团队使用 LoRA 适配器让一个基础模型专用于多个用例。每个保留在 GPU 内存中的适配器都会减少端点可服务的并发请求数，而合适的平衡取决于实例类型、适配器数量和流量特征。

Inference recommendations 现在接受适配器以 Model Package Amazon Resource Name（ARN）形式提供（适用于 SageMaker 微调生成的适配器），或以 S3 URI 形式提供（适用于来自 Hugging Face PEFT 等外部流水线的适配器）。SageMaker AI 在真实 GPU 基础设施上对适配器数量与并发的组合进行基准测试，并针对你的工作负载返回排名结果。输出会列出每个适配器的两种格式。推荐的部署使用 SageMaker Inference Components，基础模型一个组件，每个适配器一个组件，因此你可以在不中断基础模型或其他适配器的情况下添加、更新或移除适配器。

### 基于 SLA 的并发搜索（2026 年 9 月）

*博客：* [Right-size generative AI endpoints with concurrency sweeps on Amazon SageMaker AI](https://aws.amazon.com/blogs/machine-learning/right-size-generative-ai-endpoints-with-concurrency-sweeps-on-amazon-sagemaker-ai/)

为端点做合理配置，意味着找到它能够持续承受且不违反延迟或错误目标的最高并发。到目前为止，这意味着要手动挑选并发级别、运行扫描、根据服务等级协议（SLA）检查结果，并在模型或实例变化时用更窄的范围重复。

Inference recommendations 现在包含一种直接找到该边界的搜索。将 `search_recipe` 设置为 `max-concurrency-under-sla`，并提供最大 TTFT、每个输出 token 的最长时间、最大端到端延迟和最大错误率的任意组合目标。基准测试引擎（AIPerf）从较宽的范围开始，根据哪些探测通过或失败缩小范围，并以比线性扫描更少的迭代次数收敛。结果报告通过的最大并发（`feasible_max`），或者如果没有级别合格，则报告最小的失败并发（`infeasible_min`）。

该搜索使用与并发扫描相同的 `CreateAIWorkloadConfig` 和 `CreateAIBenchmarkJob` API。可选参数（`concurrency_min`、`concurrency_max`、`search_max_iterations` 和 `search_initial_points`）可限制成本并加速收敛。

### 用于优化生成式 AI 推理的 agent skill（2026 年 10 月）

*博客：* [New agent skill: Amazon SageMaker optimized generative AI inference for your coding agent](https://aws.amazon.com/blogs/machine-learning/new-agent-skill-amazon-sagemaker-optimized-generative-ai-inference-for-your-coding-agent/)

工程师越来越多地问他们的编码代理该用哪个实例和容器。没有扎实的知识和对真实基准测试的访问，代理只能猜测，而错误的实例选择日后会表现为未达延迟目标或浪费支出。

aws-ai-ml skill 可通过 [Agent Toolkit for AWS](https://aws.amazon.com/products/developer-tools/agent-toolkit-for-aws/) 获取，为 Kiro 等编码代理提供内置的 SageMaker AI 推理专业知识。工程师用自然语言描述他们的需求，代理可以执行以下操作：

- **找到合适的实例。** 为 Amazon S3、SageMaker JumpStart 或 Hugging Face Hub 中的模型提供按吞吐量、延迟和 TTFT 衡量的排名部署选项。
- **对实时端点进行基准测试。** 一份来自真实负载的报告，涵盖吞吐量、P50 和 P99 延迟、token 间延迟以及支持的并发。
- **比较运行结果。** 每个指标的百分比变化，显示配置变更是否有帮助。

答案基于实测性能，并以 SageMaker Python SDK v3 代码形式交付，由工程师审查并在自己的凭证下运行。设置大约需要 10 分钟。该 skill 可与任何支持 Model Context Protocol（MCP）的代理配合使用，也可在 SageMaker AI Studio JupyterLab 空间中使用。

对于支持团队来说，一个包含全部四个适配器的推荐作业，随后针对 500 毫秒 TTFT 目标进行并发搜索，取代了他们 4 月手动运行的扫描。负责此事的工程师可以从 notebook 启动作业，或让编码代理运行它。

## 在每个 GPU 上装更多模型

支持助手并非独自运行。一个嵌入模型、一个重排器和一个用于路由工单的小型分类器位于同一账户中，每个都只使用 GPU 的一小部分。在标准端点上，每个模型副本仍然占用整个加速器，因此团队在 GPU 内存闲置的情况下用完了放置槽位。

### SageMaker AI 控制台中的 Inference Components（2026 年 10 月）

使用 Inference Components，你可以在一个端点上托管多个模型，并分别调整每个模型的大小和扩缩容。此前，它们只能通过 SDK 和 AWS Command Line Interface（AWS CLI）使用。每次创建、调整大小和扩缩容策略都必须编写脚本，而且没有单一视图显示每个模型正在使用什么。

在 SageMaker AI 控制台中，你现在可以创建、查看、更新和删除 inference components：

- **创建和编辑。** 创建带 inference components 的端点，之后添加或删除组件，并更改每个组件的加速器、CPU、内存和副本数。
- **分别扩缩容每个模型。** 为每个组件设置自动扩缩容策略，最低可至零副本，这样空闲模型就不再占用加速器。
- **监控。** 在同一页面上查看告警和每个组件的指标。

控制台调用与 SDK 和 CLI 相同的 SageMaker AI API，因此团队可以从控制台开始，之后再自动化，或以可视化方式管理脚本化组件。

### 使用 NVIDIA Multi-Instance GPU 进行 GPU 分区（2026 年 10 月）

*博客：* [SageMaker Inference now supports Multi-Instance GPU to maximize GPU utilization for model endpoints](https://aws.amazon.com/blogs/machine-learning/sagemaker-inference-now-supports-multi-instance-gpu-to-maximize-gpu-utilization-for-model-endpoints/)

[GPU 分区](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-components-accelerator-partitioning.html)使用 NVIDIA Multi-Instance GPU（MIG）技术，根据加速器不同，将一个物理 GPU 划分为最多七个分区。每个分区都有专用的 GPU 计算和内存，并具有完全的硬件隔离。你在为 inference components 创建端点时定义分区布局，并为每个组件选择分区类型。应用程序仍然通过 inference component 名称调用模型，因此客户端代码不变。

MIG 在分区之间隔离 GPU 计算和内存。同一实例上的模型仍然共享主机 CPU、主机内存、网络、存储和端点路由。你按完整的实例小时支付标准费率，因此节省来自在每个实例上放置更多模型，而不是更低的小时价格。

对于支持团队来说，嵌入模型、重排器和分类器现在运行在单个端点上一个 GPU 的不同分区中，团队从控制台管理每个组件，包括助手及其适配器。

## 服务大于单个实例的模型

团队的下一个模型是一个推理模型，仅其权重就超过了任何单个实例的 GPU 内存。他们还注意到，长的、检索密集型提示会拖慢端点上所有其他用户的 token 生成。对于这种规模的模型，他们将工作负载移到 HyperPod Inference，这为他们提供了专用集群和 Kubernetes 原生控制。支持助手仍留在托管端点上。

### HyperPod Inference 上的托管 NVIDIA Dynamo（2026 年 11 月）

*博客：* [Managed NVIDIA Dynamo on Amazon SageMaker HyperPod Inference](https://aws.amazon.com/blogs/machine-learning/managed-nvidia-dynamo-on-amazon-sagemaker-hyperpod-inference/)

第 1 部分介绍了 HyperPod 上大模型的两个构建块：Inference Operator v3.2 中的分离式预填充和解码，以及作为托管分层 KV 缓存一部分的 KV 感知路由。本次发布增加了多节点服务，并改变了由谁运维整个栈。NVIDIA Dynamo 是一个开源推理框架，提供多节点分片服务、分离式预填充和解码，以及 KV 感知路由。团队已经可以在自己的 Kubernetes 集群上运行 Dynamo，但必须构建并运维周围的一切：将一个副本的所有节点放在一起，接好 Elastic Fabric Adapter（EFA）网络以便预填充能以硬件速度将其 KV 缓存交给解码，维护服务镜像，以及在一个故障节点导致多节点副本宕机时恢复。

借助本次发布，Dynamo 作为 HyperPod 上的托管服务引擎运行。Dynamo 做出服务决策：模型如何分片、预填充和解码如何拆分，以及每个请求去往哪里。HyperPod 提供这些决策所依赖的基础：

- **容量和网络。** GPU 容量和 EFA 网络，自动预置并接好。
- **节点恢复。** 节点健康监控和替换，节点故障时自动重新调度多节点 worker。
- **端点运维。** 自动扩缩容、端点注册、TLS 和可观测性。
- **一条安装和升级路径。** Inference Operator 附加组件将 Dynamo、服务镜像以及 Grove 和 KAI 调度器作为一个单元安装，并一起升级。

Dynamo 为 HyperPod 带来的能力包括：

- **多节点（分片）服务。** 模型的一个副本跨多个节点，因此你可以服务任何单个实例都装不下的模型。
- **分离式预填充和解码。** 提示处理和 token 生成在不同的 GPU 池上运行，每个池都使用适合其工作的实例类型，因此长提示不再拖慢其他用户的响应。
- **KV 感知路由。** 每个请求都发往已经持有其 KV 缓存的 worker，从而降低 TTFT。

有三种开始方式。在自管理 Kubernetes 上运行 Dynamo 的团队可以基本原样带入现有的 `DynamoGraphDeployment`（DGD）清单。已经在使用 HyperPod Inference 的团队可以更新附加组件，并在现有的 `InferenceEndpointConfig` 中添加一小段 `dynamoSpec` 块，HyperPod 会将其转换为 DGD，而现有端点继续服务。对两者都不熟悉的团队可以从控制台创建启用了附加组件和 Dynamo 的集群。无论哪种情况，客户端都调用标准的 OpenAI 兼容端点，因此客户端代码不变。

托管 Dynamo 支持 vLLM、SGLang 和 TensorRT-LLM，并在 [Amazon SageMaker HyperPod](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod.html#sagemaker-hyperpod-available-regions) 可用的区域提供。

![托管 NVIDIA Dynamo 在 Amazon SageMaker HyperPod Inference 上运行的架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ML-22497-3.png)

图 3：HyperPod Inference 上的托管 NVIDIA Dynamo

对于支持团队来说，推理模型作为跨多个节点的一个分片副本运行，预填充和解码池分开。节点故障时，HyperPod 会替换它并重新调度副本，而无需呼叫待命工程师。

## 把每个请求发往能服务它的 GPU

支持助手现在为北美和欧洲的客户服务，因此团队在两个区域运行端点和 HyperPod 集群。在美国早高峰期间，请求在美国区域排队，而团队已经付费的 GPU 却在欧洲闲置。一些欧洲流量还必须留在欧洲。

路由决定团队拥有的容量是否做有用功。它发生在四个层级，下面的发布各覆盖一个层级：端点内哪个实例服务请求、HyperPod 集群内哪个 pod、整个集群群组中哪个集群，以及跨区域和账户时哪个区域端点。

### 端点的 KV 缓存感知路由（2026 年 11 月）

*博客：* [Amazon SageMaker AI real-time endpoints now support KV cache aware routing](https://aws.amazon.com/blogs/machine-learning/amazon-sagemaker-ai-real-time-endpoints-now-support-kv-cache-aware-routing/)

具有长提示或多轮对话的应用程序会在请求之间重复大量前缀。模型服务器可以复用匹配的 KV 缓存，但前提是下一个请求到达持有该缓存的实例。第 1 部分介绍的 prefix-aware routing 会对每个提示的开头进行指纹识别，并将匹配的提示发送到同一实例。由于它基于请求历史工作，随着模型服务器添加和逐出条目，它对每个实例缓存的视图会变得不那么准确。

KV-cache-aware routing 使用模型容器报告的缓存状态。容器将缓存创建和逐出事件发布到中央缓存索引，SageMaker AI 将每个请求路由到持有最长匹配缓存前缀的合格实例。这提高了长上下文提示、多轮对话以及共享动态提示前缀的工作负载的缓存复用率。

它适用于单模型端点和使用 inference components（包括 LoRA 适配器）的端点。它支持 `InvokeEndpoint`、`InvokeEndpointWithResponseStream`，以及用于 Completions 和 Chat Completions 负载的 OpenAI 兼容 API。你在端点配置中启用它。首个版本要求使用 AWS 验证的模型容器，该容器实现缓存事件、tokenization、指标和 OpenAI 兼容接口。你可以在详细推理可观测性中跟踪 KV 缓存命中率。

**该用哪一个。** Prefix-aware routing 适用于任何容器，无需更改容器。KV-cache-aware routing 需要经过验证的容器并跟踪实际缓存，当前缀变化或缓存快速更替时最有帮助。

### 用于 HyperPod 的 Inference Gateway（2026 年 9 月）

*博客：* [Introducing Amazon SageMaker HyperPod Inference Gateway](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-sagemaker-hyperpod-inference-gateway/)

在 HyperPod 集群内，容量和需求很少正好匹配。一个 pod 可能正在处理长上下文请求且其 KV 缓存几乎已满，而下一个 pod 却空闲，或者已经持有下一个请求所需的前缀或 LoRA 适配器。若无法看到该 GPU 状态，新请求会在繁忙 pod 后面排队，团队为了保护延迟而增加 GPU，而不是使用已有的 GPU。每个模型还都有自己的端点，因此客户端必须为每个模型跟踪一个端点。

Inference Gateway 是一个 GPU 感知路由器，随 HyperPod Inference Operator 附加组件安装，为每个集群的所有模型提供一个 OpenAI 兼容端点。对于每个请求，它读取每个模型 pod 的实时信号并选择最佳 pod，权重可按工作负载调整：

- **KV 缓存利用率。** 避开缓存几乎已满的 pod。
- **队列深度和运行中请求。** 避开有积压的 pod，并平衡活跃工作。
- **前缀缓存命中率。** 优先选择可能持有提示前缀的 pod。
- **LoRA 适配器驻留。** 优先选择已经持有请求适配器的 pod，从而避免交换延迟。

与轮询路由相比，它在混合 GPU 代际上将 P99 TTFT 降低了最多 97%，在突发流量下降低了最多 98%。它在 SageMaker HyperPod 可用的所有区域提供。

### Amazon SageMaker AI 中的跨区域推理路由

*博客：* [Keep inference running through regional capacity shortfalls with cross-Region inference routing in Amazon SageMaker AI](https://aws.amazon.com/blogs/machine-learning/keep-inference-running-through-regional-capacity-shortfalls-with-cross-region-inference-routing-in-amazon-sagemaker-ai/)

在托管端点上，同样的理念体现为 Cross-Region Inference Routing，即托管路由，将实时和异步请求发送到团队已经部署的区域端点，这些端点可以位于同一账户或不同账户。你将服务同一模型的端点分组到一个路由目标下，应用程序调用该目标，而不是特定的区域端点。路由器不增加容量、不复制模型、不部署端点，现有调用路径继续工作。

该路由器取代了团队目前自行构建的故障转移逻辑：

- **一条调用路径。** SageMaker 先尝试本地端点，当本地端点无法服务请求时，将流量转移到另一个已注册端点。
- **一个路由策略。** 该策略结合端点指标与服务侧容量信号，包括客户自己无法观察到的容量不足错误。
- **私有连接。** 跨区域流量通过 AWS PrivateLink 运行，并采用托管的跨账户授权模型，因此路由到另一个区域或账户不需要互联网或 NAT 网关。
- **溢出和驻留护栏。** 端点所有者可以限制回退端点接受的跨区域流量，应用程序可以限制哪些区域可以服务请求。

## 上线后持续调优端点

迁移两个月后，团队为支持助手添加了检索，平均提示长度大约翻倍。TTFT 现在高于上线时，但没有出现故障，因此所有告警都保持绿色。当团队找到更好的配置时，他们需要在难以获取更多的大 GPU 实例上推出。

### 持续性能监控（2026 年 11 月）

博客：[Amazon SageMaker AI now detects latency drift, idle GPUs, and missed optimizations on your inference endpoints](https://aws.amazon.com/blogs/machine-learning/amazon-sagemaker-ai-now-detects-latency-drift-idle-gpus-and-missed-optimizations-on-your-inference-endpoints/)

Amazon SageMaker AI 现在持续监控你的生成式 AI 推理端点，并在变更可以改善性能或降低成本时告知你。监控默认对 SageMaker AI 推理端点开启，无需设置，你可以选择退出某些端点。SageMaker AI 仅查看运营信号：延迟、GPU 利用率和端点的服务配置。它不读取你的请求或响应。当发现项达到其置信度阈值时，AWS Management Console 上会出现通知，对于在 notebook 和 CLI 中工作的团队，同一消息也会通过电子邮件送达。推荐操作会打开 SageMaker AI Studio 中的 SageMaker AI 代理体验，并已填入发现项，因此分析、比较和部署变更都在一次对话中完成。在你应用之前不会部署任何内容，你可以随时关闭监控。

发现项有三种类型：

- **流量变化后的延迟漂移。** 当添加检索等变化延长提示时，TTFT 会上升。该发现项量化逐周回归，并建议针对近期流量重新运行 inference recommendations，以找到让 TTFT 回落的配置。
- **部署以来存在的配置差距。** 端点从未针对其工作负载做好调优，发现项指出可弥补差距的变更。
- **空闲 GPU 容量。** 当容量周复一周未被使用时，发现项标记出调整端点规模和降低成本的机会。

### 原地滚动模型更新（2026 年 11 月）

标准滚动更新一次替换一批端点，每批都在新预置的实例上运行。在大型 GPU 集群上，这意味着每一步都要寻找新容量，而当下一批实例不可用时，更新可能中途失败。每个释放的实例还必须完成清理才能再次使用，这拖慢了推出速度。

SageMaker AI 现在原地更新模型。它在开始时预置一小批额外实例，将流量转移到该批，然后更新它释放的实例，复用它们将变更滚动到集群其余部分。更新仍然分阶段推出，但只需要一次新容量。对于 20 个实例、批大小为 2 的集群，更新获取 2 个新实例，而不是 20 个。客户无需更改任何内容。与第 1 部分中的容器缓存一样，这一改进自动应用于滚动模型更新。

![标准滚动更新每一步获取新实例，与复用集群的原地更新对比](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ML-22497-6.png)

图 6：滚动更新在每一步获取新实例。原地滚动更新在开始时获取一批，并复用集群其余部分

对于支持团队来说，Drift Watch 发现项量化了 TTFT 回归，并针对近期流量打开新的推荐作业。他们用一批额外实例推出更新后的模型，而不是为集群中的每个实例寻找新的 GPU 容量。

## 总结：13 项发布，接续第 1 部分

编号接续第 1 部分的 13 项发布。

> 14. SageMaker AI Studio 中的 inference recommendations（2026 年 7 月）。引导式、低代码工作流，提供排名、基准测试后的配置，并从 Studio 部署。
>         15. SageMaker Python SDK v3 中的 inference recommendations（2026 年 8 月）。从 notebook 或流水线进行基准测试、推荐和部署，支持并行和可恢复作业。
>         16. Inference recommendations 中的 LoRA 适配器支持（2026 年 9 月）。对适配器数量与并发进行基准测试，并将适配器作为 inference components 部署。
>         17. 基于 SLA 的并发搜索（2026 年 9 月）。找到满足 TTFT、延迟和错误率目标的最高并发。
>         18. 用于优化生成式 AI 推理的 agent skill（2026 年 10 月）。从兼容 MCP 的编码代理进行实例选择、基准测试和运行比较。
>         19. SageMaker AI 控制台中的 Inference Components（2026 年 10 月）。无需脚本即可在多模型端点上创建、扩缩容和监控每个模型。
>         20. 使用 NVIDIA MIG 进行 GPU 分区（2026 年 10 月）。每个 GPU 最多七个隔离分区，按 inference component 分配。
>         21. HyperPod Inference 上的托管 NVIDIA Dynamo（2026 年 11 月）。多节点和分离式服务，由 HyperPod 在底层运维平台。
>         22. KV 缓存感知路由（2026 年 11 月）。根据容器提供的缓存事件，将每个请求路由到持有最长缓存前缀的实例。
>         23. 用于 HyperPod 的 Inference Gateway（2026 年 9 月）。每个集群一个端点，具备 GPU 感知路由，P99 TTFT 比轮询低最多 97%。
>         24. 跨区域推理路由器。通过 PrivateLink 在区域和跨账户端点之间路由，并具备溢出和驻留护栏。
>         25. 持续性能监控。检测延迟漂移、配置差距和空闲容量，并在 SageMaker AI Studio 中提供引导式修复。
>         26. 原地滚动模型更新（2026 年 11 月）。开始时用一批额外实例推出模型更新，然后在整个集群中复用现有实例。

到年底，支持团队从一个基础模型服务四条产品线，在共享 GPU 上运行小模型，服务一个任何单实例都装不下的推理模型，并在两个区域之间路由流量且带驻留控制。他们无需构建自己的基准测试工具、故障转移逻辑或漂移监控就能做到这一点。

第 1 部分论证了 AI 推理的优势来自运营高效的推理栈。这 13 项发布将该论点应用于上线后的数月。AWS Experience-Based Acceleration 计划可以帮助你的团队将它们投入使用，根据你的 SLA 和成本目标对工作负载进行基准测试并配置推理栈。
