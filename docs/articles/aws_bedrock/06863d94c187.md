# Amazon SageMaker Inference：2026 年发布回顾（下）

模型一旦上了生产，问题就变了。流量已经是真流量，模型该跑在哪套配置上；怎么把更多模型塞进已经在付钱的 GPU；下一个模型大到一台机器装不下，怎么办；为什么请求在一个区域排队，另一个区域的 GPU 却闲着；为什么没人动过任何东西，延迟却上去了。本文按团队通常碰上这些问题的顺序逐条展开。

针对 HyperPod Inference，它列出了更多路由策略、对模型服务框架更广的支持，以及扩展的多区域网络。路由由 Inference Gateway 承担，托管版 NVIDIA Dynamo 则是新的服务框架。对托管端点而言，路线图指向与 AWS AI 其余部分更深的集成。Inference recommendations 现在可以从 Amazon SageMaker AI Studio、SageMaker Python SDK，以及工程师已经在用的编码 agent 中运行，端点也可以跨区域、跨账户路由请求。

为了让每一节都落到实处，全文跟随一个虚构团队。春天，他们借助第 1 部分的发布成果，把 70B 参数模型上的客户支持助手放在单个 SageMaker AI 端点后面上线。到了秋天，他们要支持更多产品线、换用更大的推理模型、在第二个区域服务客户，同时让 GPU 账单保持不变。

## 无论在哪里工作，都能选对配置

团队依据 4 月的一次基准测试选定了第一套配置。此后他们加了四个 LoRA（Low-Rank Adaptation）适配器，每条产品线一个，产品团队还把峰值负载下的首 token 时延（TTFT）目标定在 500 毫秒。4 月那套配置从未针对这两项变化测过。要重跑分析的工程师在 notebook 和编码 agent 里干活，很少有人用控制台。

Inference recommendations 在 4 月以 API 形式发布。此后的四次更新让它进入团队干活的更多场所，也让它能回答两个更难的问题：一个端点能挂多少个适配器，以及在打不中延迟目标之前能扛多少并发。一个新的 agent skill 把同样的专业能力带进了编码 agent。

### SageMaker AI Studio 中的 Inference recommendations（2026 年 7 月）

*博客：* [Amazon SageMaker AI 推出生成式 AI 推理推荐 UI](https://aws.amazon.com/blogs/machine-learning/launching-ui-for-generative-ai-inference-recommendations-in-amazon-sagemaker-ai/)

4 月那次发布通过 API 把实例、容器和优化选择自动化了。现在 inference recommendations 也以引导式、低代码工作流的形式出现在 SageMaker AI Studio 里。在 Studio 中先选 **Jobs**，再选 **Inference optimization**，然后选用例画像（Interact、Generate、Summarize 或 Custom）、优化目标（最小化延迟、最大化吞吐量或最小化成本），以及一个来自 SageMaker JumpStart、Amazon Simple Storage Service（Amazon S3）、Model Registry 或现有 SageMaker 模型的模型。

SageMaker AI 在真实 GPU 基础设施上用 NVIDIA AIPerf 对候选配置做基准测试，并施加与目标匹配的技术，例如为吞吐量用投机解码，为延迟做内核调优。你可以按 TTFT、token 间延迟、吞吐量和成本比较排名结果，然后从 Studio 把选中的配置部署到实时端点。

### SageMaker Python SDK v3 中的 Inference recommendations（2026 年 8 月）

*博客：[Amazon SageMaker Python SDK 集成 LLM 优化](https://aws.amazon.com/blogs/machine-learning/llm-optimization-integration-for-amazon-sagemaker-python-sdk/)*

以前做基准测试和推荐，要么开 SageMaker AI Studio，要么直接调 Boto3。现在它们是 SageMaker Python SDK v3（3.17.0 及更高版本）的一部分，也就是团队训练和部署用的同一套接口，因此这套工作流能嵌进 notebook、CI 流水线和 MLOps 流程。你可以拿真实工作负载流量对线上端点做基准测试，针对延迟、吞吐量或成本目标生成排名推荐，并在一次调用里把排名最高的配置部署到实时端点。

SDK 也支持更长的工作流。你可以并行跑多个推荐作业，比较 LMI、vLLM 这类服务框架；也可以从已完成的作业接着往下做，让部署发生在另一个 notebook 或流水线阶段，而无需重跑基准测试。

### Inference recommendations 中的 LoRA 适配器支持（2026 年 9 月）

*开发人员指南*：[获取带 LoRA 适配器的模型推荐](https://docs.aws.amazon.com/sagemaker/latest/dg/generative-ai-inference-recommendations-adapters.html)

很多团队用 LoRA 适配器让一个基础模型服务多个用例。每个常驻 GPU 内存的适配器都会压低端点能支撑的并发请求数，而合适的平衡取决于实例类型、适配器数量和流量特征。

Inference recommendations 现在接受以 Model Package Amazon Resource Name（ARN）形式给出的适配器（用于 SageMaker 微调产出的适配器），也接受以 S3 URI 形式给出的适配器（用于 Hugging Face PEFT 等外部流水线的适配器）。SageMaker AI 在真实 GPU 基础设施上对适配器数量与并发的各种组合做基准测试，针对你的工作负载返回排名结果。输出里会为每个适配器同时列出这两种形式。推荐的部署方式用 SageMaker Inference Components，基础模型一个组件，每个适配器各一个组件，这样增删改某个适配器都不会打断基础模型或其他适配器。

### 基于 SLA 的并发搜索（2026 年 9 月）

*博客：* [用并发扫描为 Amazon SageMaker AI 上的生成式 AI 端点定容](https://aws.amazon.com/blogs/machine-learning/right-size-generative-ai-endpoints-with-concurrency-sweeps-on-amazon-sagemaker-ai/)

给端点定容，就是找出它在不突破延迟或错误目标的前提下能承受的最高并发。在这之前，做法是手工挑几个并发档位、跑一轮扫描、拿结果对照服务等级协议（SLA），一旦模型或实例变了，再用更窄的区间重来一遍。

Inference recommendations 现在自带一种直接去找这条边界的搜索。把 `search_recipe` 设为 `max-concurrency-under-sla`，再给出目标：最大 TTFT、每个输出 token 的最长时间、最大端到端延迟、最大错误率，任意组合都可以。基准测试引擎（AIPerf）从一个较宽的区间起步，根据哪些探测通过、哪些失败来收窄，迭代次数比线性扫描少。结果报告的是通过的最大并发（`feasible_max`）；若没有任何档位合格，则报告最小的失败档位（`infeasible_min`）。

这项搜索与并发扫描用的是同一组 `CreateAIWorkloadConfig` 和 `CreateAIBenchmarkJob` API。可选参数（`concurrency_min`、`concurrency_max`、`search_max_iterations`、`search_initial_points`）可以限定成本、加快收敛。

### 用于优化生成式 AI 推理的 agent skill（2026 年 10 月）

*博客：* [新 agent skill：面向编码 agent 的 Amazon SageMaker 优化生成式 AI 推理](https://aws.amazon.com/blogs/machine-learning/new-agent-skill-amazon-sagemaker-optimized-generative-ai-inference-for-your-coding-agent/)

工程师越来越常问自己的编码 agent：该用哪个实例、哪个容器。没有扎实的知识、也拿不到真实基准测试数据，agent 只能猜，而实例选错的代价日后会以没打中延迟目标或白花钱的形式出现。

通过 [Agent Toolkit for AWS](https://aws.amazon.com/products/developer-tools/agent-toolkit-for-aws/) 提供的 aws-ai-ml skill，把 SageMaker AI 推理的专业能力内建给 Kiro 这类编码 agent。工程师用大白话讲清自己要什么，agent 就能做下面这些事：

- **找准实例。** 针对 Amazon S3、SageMaker JumpStart 或 Hugging Face Hub 里的某个模型，给出带实测吞吐量、延迟和 TTFT 的排名部署方案。
- **给线上端点做基准测试。** 一份来自真实负载的报告，覆盖吞吐量、P50 与 P99 延迟、token 间延迟以及可支撑的并发。
- **对比多次运行。** 每个指标的百分比变化，一眼看出配置改动有没有帮上忙。

答案基于实测性能，以 SageMaker Python SDK v3 代码的形式交付，由工程师自行审阅并在自己的凭证下运行。配置大约花 10 分钟。该 skill 适用于任何支持 Model Context Protocol（MCP）的 agent，也能在 SageMaker AI Studio 的 JupyterLab 空间里用。

对支持团队来说，跑一个包含全部四个适配器的推荐作业，再针对 500 毫秒的 TTFT 目标做一次并发搜索，就替代了他们 4 月手工跑的那些扫描。负责这件事的工程师可以从 notebook 启动作业，也可以让编码 agent 去跑。

## 让每个 GPU 装下更多模型

支持助手不是一个人在跑。同一个账户里还住着一个嵌入模型、一个重排器和一个负责工单分流的小分类器，每个都只用得到 GPU 的一小部分。在标准端点上，每份模型副本仍然占住整块加速器，结果团队把放置槽位用光了，GPU 内存却闲着。

### SageMaker AI 控制台中的 Inference Components（2026 年 10 月）

用 Inference Components，你可以在一个端点上托管多个模型，并分别给每个模型定量、做扩缩容。在此之前，它们只能通过 SDK 和 AWS Command Line Interface（AWS CLI）使用，每次创建、调整规模和扩缩容策略都得写脚本，而且没有一个统一视图能看到每个模型占用了什么。

在 SageMaker AI 控制台里，你现在可以创建、查看、更新和删除 inference component：

- **创建与编辑。** 创建带 inference component 的端点，之后增删组件，修改每个组件的加速器、CPU、内存和副本数。
- **分别扩缩容。** 为每个组件设置自动扩缩容策略，最低可缩到零副本，空闲模型就不再占着加速器。
- **监控。** 在同一页看到告警和分组件指标。

控制台调用的是与 SDK、CLI 相同的 SageMaker AI API，团队可以先在控制台上手，之后再自动化，也可以把脚本化的组件拿来做可视化管理。

### 用 NVIDIA Multi-Instance GPU 做 GPU 分区（2026 年 10 月）

*博客：* [SageMaker Inference 现支持 Multi-Instance GPU，最大化模型端点的 GPU 利用率](https://aws.amazon.com/blogs/machine-learning/sagemaker-inference-now-supports-multi-instance-gpu-to-maximize-gpu-utilization-for-model-endpoints/)

[GPU 分区](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-components-accelerator-partitioning.html)用 NVIDIA Multi-Instance GPU（MIG）技术把一块物理 GPU 切成最多七个分区，具体数目取决于加速器。每个分区都有专属的 GPU 算力和内存，硬件上完全隔离。你在为 inference components 创建端点时定义分区布局，并为每个组件选择分区类型。应用仍然按 inference component 名称调用模型，客户端代码不用改。

MIG 隔离的是分区之间的 GPU 算力和内存。同一实例上的模型仍然共享宿主机 CPU、宿主机内存、网络、存储和端点路由。你按整实例小时的标准费率付费，所以省钱来自每个实例上多放几个模型，而不是小时单价变低。

![三个小模型分别跑在三块 GPU 上，与同样三个模型共享一块 GPU 的多个分区对比](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ML-22497-2.png)

图 2：三个小模型跑在三块 GPU 上，与同样三个模型跑在一块 GPU 的多个分区里对比

对支持团队来说，嵌入模型、重排器和分类器现在跑在同一个端点上、同一块 GPU 的不同分区里，团队从控制台管理每一个组件，包括助手本身和它的适配器。

## 服务比单个实例更大的模型

团队的下一个模型是个推理模型，光权重就超过任何单个实例的 GPU 内存。他们还注意到，带大量检索的长 prompt 会拖慢端点上其他所有用户的 token 生成。对这种体量的模型，他们把工作负载挪到 HyperPod Inference，那里有专属集群和 Kubernetes 原生控制。支持助手仍留在托管端点上。

### HyperPod Inference 上的托管 NVIDIA Dynamo（2026 年 11 月）

*博客：* [Amazon SageMaker HyperPod Inference 上的托管 NVIDIA Dynamo](https://aws.amazon.com/blogs/machine-learning/managed-nvidia-dynamo-on-amazon-sagemaker-hyperpod-inference/)

第 1 部分讲过大模型在 HyperPod 上的两个构件：Inference Operator v3.2 中的解耦式预填充与解码，以及作为托管分层 KV 缓存一部分的 KV 感知路由。这次发布加上了多节点服务，也换掉了这套栈的运维方。NVIDIA Dynamo 是一个开源推理框架，提供多节点分片服务、解耦式预填充与解码，以及 KV 感知路由。团队本来就能在自己的 Kubernetes 集群上跑 Dynamo，但周围的一切都得自己搭、自己运维：把一个副本的所有节点摆在一起，把 Elastic Fabric Adapter（EFA）网络接通，好让预填充以硬件速度把 KV 缓存交给解码，维护服务镜像，以及在一个节点故障拖垮整个多节点副本时恢复过来。

有了这次发布，Dynamo 作为 HyperPod 上的托管服务引擎运行。服务层面的决策由 Dynamo 来做：模型怎么分片、预填充与解码怎么拆、每个请求去哪。HyperPod 则提供这些决策所依赖的东西：

- **容量与网络。** GPU 容量和 EFA 网络，自动预置、自动接通。
- **节点恢复。** 节点健康监控与替换，节点故障时自动重新调度多节点 worker。
- **端点运维。** 自动扩缩容、端点注册、TLS 和可观测性。
- **一条安装与升级路径。** Inference Operator 附加组件把 Dynamo、服务镜像以及 Grove、KAI 调度器作为一个单元安装，并一起升级。

Dynamo 带给 HyperPod 的能力有：

- **多节点（分片）服务。** 模型的一份副本横跨多个节点，于是任何单个实例装不下的模型也能服务。
- **解耦式预填充与解码。** prompt 处理和 token 生成跑在不同的 GPU 池上，各自用适合自身工作的实例类型，长 prompt 不再拖慢其他用户的响应。
- **KV 感知路由。** 每个请求都送到已经持有其 KV 缓存的 worker，从而降低 TTFT。

起步有三种方式。在自管理 Kubernetes 上跑 Dynamo 的团队，基本可以原样带上现有的 `DynamoGraphDeployment`（DGD）清单。已经在用 HyperPod Inference 的团队，更新附加组件，在现有 `InferenceEndpointConfig` 里加一小段 `dynamoSpec`，HyperPod 会把它转成 DGD，现有端点照常服务。两边都是新手的团队，从控制台创建集群时把附加组件和 Dynamo 一起启用即可。无论哪种，客户端调用的都是标准的 OpenAI 兼容端点，客户端代码不用改。

托管 Dynamo 支持 vLLM、SGLang 和 TensorRT-LLM，在 [Amazon SageMaker HyperPod](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod.html#sagemaker-hyperpod-available-regions) 可用的区域均可使用。

![托管 NVIDIA Dynamo 在 Amazon SageMaker HyperPod Inference 上运行的架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ML-22497-3.png)

对支持团队来说，推理模型作为一个分片副本横跨多个节点运行，预填充池和解码池分开。某个节点故障时，HyperPod 会替换它并重新调度副本，不必再呼叫待命工程师。

## 把每个请求送到能服务它的 GPU

支持助手现在服务北美和欧洲的客户，团队因此在两个区域跑端点和 HyperPod 集群。美国早高峰时，请求在美国区域排队，团队已经在付费的 GPU 却在欧洲闲着。另外，一部分欧洲流量必须留在欧洲。

路由决定团队手里的容量有没有做有用的功。它发生在四个层级，下面每个发布各覆盖一层：端点内部由哪个实例服务请求、HyperPod 集群内部由哪个 pod、整个机群里由哪个集群、跨区域跨账户时由哪个区域端点。

### 端点的 KV-cache-aware routing（2026 年 11 月）

*博客：* [Amazon SageMaker AI 实时端点现支持 KV 缓存感知路由](https://aws.amazon.com/blogs/machine-learning/amazon-sagemaker-ai-real-time-endpoints-now-support-kv-cache-aware-routing/)

长 prompt 或多轮对话的应用，会在请求之间重复大段前缀。模型服务器可以复用匹配的 KV 缓存，前提是下一个请求能到达持有该缓存的那个实例。第 1 部分介绍过的 prefix-aware routing 会对每个 prompt 的开头做指纹，把前缀相同的 prompt 发到同一实例。它靠请求历史工作，所以随着模型服务器不断加入和逐出条目，它对每个实例缓存的判断会越来越不准。

KV-cache-aware routing 使用的是模型容器上报的缓存状态。容器把缓存创建和逐出事件发布到中央缓存索引，SageMaker AI 再把每个请求路由到持有最长匹配缓存前缀的合格实例。这让长上下文 prompt、多轮对话，以及共享动态 prompt 前缀的工作负载获得更高的缓存复用率。

它适用于单模型端点和用 inference components（包括 LoRA 适配器）的端点，支持 `InvokeEndpoint`、`InvokeEndpointWithResponseStream`，以及面向 Completions 和 Chat Completions 负载的 OpenAI 兼容 API。在端点配置里打开即可。首个版本要求使用经过 AWS 验证的模型容器，该容器需实现缓存事件、分词、指标和 OpenAI 兼容这几组接口。KV 缓存命中率可以在详细推理可观测性里跟踪。

**该用哪个。** Prefix-aware routing 对任何容器都适用，不需要改容器。KV-cache-aware routing 需要经过验证的容器，跟踪的是真实缓存，在前缀变化多或缓存更替快的时候收益最大。

### 用于 HyperPod 的 Inference Gateway（2026 年 9 月）

*博客：* [推出 Amazon SageMaker HyperPod Inference Gateway](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-sagemaker-hyperpod-inference-gateway/)

在 HyperPod 集群内部，容量和需求很少刚好对上。某个 pod 可能正处理一个长上下文请求、KV 缓存快满了，旁边那个 pod 却闲着，或者恰好已经持有下一个请求需要的 prompt 前缀或 LoRA 适配器。看不到这些 GPU 状态，新请求就只能在忙碌的 pod 后面排队，团队为了保护延迟去加 GPU，而不是把手里已有的用起来。而且每个模型还各有自己的端点，客户端得为每个模型记一个端点。

Inference Gateway 是一个 GPU 感知路由器，随 HyperPod Inference Operator 附加组件一起安装，为每个集群的全部模型提供一个 OpenAI 兼容端点。它针对每个请求读取各个模型 pod 的实时信号，选出最合适的那个，权重可以按工作负载调：

- **KV 缓存利用率。** 避开缓存快满的 pod。
- **队列深度与运行中请求数。** 避开有积压的 pod，让活跃工作更均衡。
- **前缀缓存命中率。** 优先选可能持有该 prompt 前缀的 pod。
- **LoRA 适配器驻留。** 优先选已经持有所需适配器的 pod，省掉换入换出的延迟。

与轮询路由相比，在混合 GPU 代际的环境里它把 P99 TTFT 最多降低了 97%，在突发流量下最多降低 98%。SageMaker HyperPod 可用的所有区域都能用。

### Amazon SageMaker AI 中的跨区域推理路由

*博客：* [借助 Amazon SageMaker AI 的跨区域推理路由，在区域容量不足时保持推理不中断](https://aws.amazon.com/blogs/machine-learning/keep-inference-running-through-regional-capacity-shortfalls-with-cross-region-inference-routing-in-amazon-sagemaker-ai/)

在托管端点上，同样的思路体现为 Cross-Region Inference Routing：一种托管路由，把实时请求和异步请求发到团队已经部署的各个区域端点，同账户、跨账户都可以。你把服务同一模型的端点归到一个路由目标下，应用调用这个目标，而不是某个具体的区域端点。路由器不增加容量、不复制模型、不部署端点，现有调用路径照旧工作。

这个路由器取代了团队目前要自己写的故障转移逻辑：

- **一条调用路径。** SageMaker 先试本地端点，本地端点服务不了某个请求时，再把流量转到另一个已注册端点。
- **一套路由策略。** 策略把端点指标和服务侧的容量信号结合起来，其中包含客户自己看不到的容量不足错误。
- **私有连接。** 跨区域流量走 AWS PrivateLink，配一套托管的跨账户授权模型，因此路由到其他区域或账户既不需要公网，也不需要 NAT 网关。
- **溢出与驻留 guardrails。** 端点所有者可以给回退端点能接的跨区域流量设置上限，应用也可以限定哪些区域可以服务某个请求。

## 上线之后继续调优端点

迁移两个月后，团队给支持助手加上了检索，平均 prompt 长度差不多翻了一倍。TTFT 比上线时高了，但没出任何故障，所以所有告警都还是绿的。等团队找到更好的配置，还得把它推上那些已经很难再申请到的大 GPU 实例。

### 持续性能监控（2026 年 11 月）

博客：[Amazon SageMaker AI 现可检测推理端点上的延迟漂移、空闲 GPU 和错过的优化机会](https://aws.amazon.com/blogs/machine-learning/amazon-sagemaker-ai-now-detects-latency-drift-idle-gpus-and-missed-optimizations-on-your-inference-endpoints/)

Amazon SageMaker AI 现在会持续监控你的生成式 AI 推理端点，一旦某项变更能提升性能或降低成本就告诉你。对 SageMaker AI 推理端点，监控默认开启、无需配置，你也可以把某些端点排除在外。SageMaker AI 只看运维信号：延迟、GPU 利用率和端点的服务配置，不读你的请求或响应。某个发现项过了置信度阈值，AWS Management Console 上会出现通知；对在 notebook 和 CLI 里干活的团队，同一条消息还会发到邮箱。点开建议的操作，SageMaker AI Studio 里的 SageMaker AI agentic 体验会带着这个发现项一起打开，分析、对比和部署改动都在一次对话里完成。你不点应用就不会部署任何东西，监控也随时可以关掉。

发现项分三类：

- **流量变化后的延迟漂移。** 加了检索之类的变化把 prompt 拉长，TTFT 就会上升。该发现项量化逐周的退化幅度，并建议针对近期流量重跑 inference recommendations，找出能把 TTFT 压回去的配置。
- **部署时就存在的配置缺口。** 端点从未针对其工作负载调好，该发现项指出能补上缺口的那项改动。
- **闲置的 GPU 容量。** 容量一周接一周闲着，该发现项就标出一个重新给端点定容、降低成本的机会。

### 原地滚动模型更新（2026 年 11 月）

标准滚动更新一次换掉一批端点，每一批都跑在新预置的实例上。在大型 GPU 机群里，这意味着每一步都要去找新容量，下一批实例拿不到时更新还可能中途失败。每个释放出来的实例还得先清理完才能重新使用，又拖慢了推出速度。

SageMaker AI 现在原地更新模型。它在开头预置一小批额外实例，把流量切过去，然后更新被它释放出来的实例，再复用这些实例把变更铺到机群其余部分。更新仍然分阶段推出，但只需要一次新容量。20 个实例、批大小为 2 的机群，更新只需获取 2 个新实例，而不是 20 个。客户什么都不用改。与第 1 部分讲的容器缓存一样，这项改进自动作用于滚动模型更新。

![滚动更新每一步都获取新实例，与复用机群的原地更新对比](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ML-22497-6.png)

图 6：滚动更新在每一步都获取新实例；原地滚动更新只在开头获取一批，其余复用机群现有实例

对支持团队来说，一个 Drift Watch 发现项量化了 TTFT 的退化，并针对近期流量开出一个新的推荐作业。他们用一批额外实例就把更新后的模型推了出去，不必为机群里每个实例去找新的 GPU 容量。

## 总结：13 项发布，接续第 1 部分

编号接续第 1 部分那 13 项发布。

> 14. SageMaker AI Studio 中的 Inference recommendations（2026 年 7 月）。引导式、低代码工作流，给出经过基准测试的排名配置，并可从 Studio 部署。
>         15. SageMaker Python SDK v3 中的 Inference recommendations（2026 年 8 月）。在 notebook 或流水线里完成基准测试、推荐和部署，作业可并行、可续跑。
>         16. Inference recommendations 支持 LoRA 适配器（2026 年 9 月）。针对并发基准测试适配器数量，并把适配器作为 inference component 部署。
>         17. 基于 SLA 的并发搜索（2026 年 9 月）。找出满足 TTFT、延迟和错误率目标的最高并发。
>         18. 面向优化生成式 AI 推理的 agent skill（2026 年 10 月）。从兼容 MCP 的编码 agent 里完成实例选择、基准测试和运行对比。
>         19. SageMaker AI 控制台中的 Inference Components（2026 年 10 月）。无需脚本，即可在多模型端点上创建、扩缩容和监控每个模型。
>         20. 用 NVIDIA MIG 做 GPU 分区（2026 年 10 月）。每块 GPU 最多七个隔离分区，按 inference component 分配。
>         21. HyperPod Inference 上的托管 NVIDIA Dynamo（2026 年 11 月）。多节点与解耦式服务，底层平台由 HyperPod 运维。
>         22. KV-cache-aware routing（2026 年 11 月）。依据容器上报的缓存事件，把每个请求路由到持有最长缓存前缀的实例。
>         23. 用于 HyperPod 的 Inference Gateway（2026 年 9 月）。每个集群一个端点，具备 GPU 感知路由，P99 TTFT 比轮询最多低 97%。
>         24. Cross-Region Inference Router。通过 PrivateLink 在区域端点和跨账户端点之间路由，带溢出与驻留 guardrails。
>         25. 持续性能监控。检测延迟漂移、配置缺口和闲置容量，并在 SageMaker AI Studio 中提供引导式修复。
>         26. 原地滚动模型更新（2026 年 11 月）。开头用一批额外实例推出模型更新，随后在机群里复用现有实例。

到年底，这个支持团队用一个基础模型服务四条产品线，把几个小模型放在共享 GPU 上跑，服务一个任何单实例都装不下的推理模型，并在两个区域之间路由流量、还带着驻留控制。做到这些，他们不需要自己攒一套基准测试 harness、故障转移逻辑或漂移监控。

第 1 部分论证过，AI 推理上的优势来自把推理栈运营得高效。这 13 项发布把这个论点落到了上线之后的几个月里。AWS Experience-Based Acceleration 计划可以帮你的团队把它们用起来：针对你的 SLA 和成本目标，对工作负载做基准测试、把推理栈配置到位。
