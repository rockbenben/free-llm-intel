# Amazon Bedrock 在泰国、马来西亚、新加坡、印度尼西亚和台湾为最新的 Anthropic Claude Opus、Sonnet 和 Haiku 模型提供 Global cross-Region inference

泰国、马来西亚、新加坡、印度尼西亚和台湾的组织现在可以通过 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的 [Global cross-Region inference（CRIS）](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html) 访问 Anthropic Claude Opus 4.6、Sonnet 4.6 和 Claude Haiku 4.5，该能力通过一个为规模而设计的全球分布式推理架构来交付基础模型。Global CRIS 提供三项关键优势：更高的配额、成本效率，以及把请求路由到跨 AWS 商业区域的推理容量，以支持聊天机器人、自主编码 agent 和金融分析系统等 AI 用例。

在本文中，我们宣布面向泰国、马来西亚、新加坡、印度尼西亚和台湾的客户推出 Global CRIS。我们将逐步介绍技术实现步骤，并涵盖配额管理和生产部署的最佳实践，帮助你最大化 AI 推理部署的价值。

## Global cross-Region inference 概述

[CRIS](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html) 是 Amazon Bedrock 的一项能力，可用于把推理请求路由到其他 AWS 区域。该能力扩大了请求可触达的资源池，因此任何给定工作负载都不会受限于单个区域所能提供的能力。

你通过[推理配置文件](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles.html)（inference profile）访问 CRIS，它基于两个关键概念：

- 源区域（Source Region）– 你发起 API 请求的区域。
- 目标区域（Destination Region）– Amazon Bedrock 可以把请求路由到其中进行推理的区域。

CRIS 通过安全的 AWS 网络运行，对传输中和静态存储的数据都提供端到端加密。当你从源区域提交推理请求时，CRIS 会通过 Amazon Bedrock 托管网络把请求路由到为该推理配置文件配置的某个目标区域。推理请求经由 [AWS 全球网络](https://aws.amazon.com/about-aws/global-infrastructure/global-network/)传输，响应会返回到源区域中你的应用。

关键区别在于：虽然推理处理（即瞬时的计算）可能发生在另一个区域，但静态数据（包括日志、知识库和存储的配置）始终只留在你的源区域内。Amazon Bedrock 提供两类跨区域推理配置文件：Geographic CRIS（在特定地理范围内路由，例如 US、EU、APAC、Australia、Japan）和 Global CRIS（路由到全球受支持的商业区域）。泰国、马来西亚、新加坡、台湾和印度尼西亚的客户现在可以通过 Global CRIS 访问 Claude Opus 4.6、Sonnet 4.6 和 Haiku 4.5。

### 为什么泰国、马来西亚、新加坡、台湾和印度尼西亚需要 Global CRIS

Global CRIS 通过一个为满足生产规模自主系统需求而设计的架构来交付 Claude Opus 4.6、Sonnet 4.6 和 Haiku 4.5。Global CRIS 在全球范围内的 AWS 区域之间路由推理请求。借助这种路由能力，你的 agentic 应用可以在需求模式变化时保持业务连续性。

## 前提条件

在使用 Global CRIS 之前，你需要为推理请求的跨区域路由配置 IAM 权限。

### 配置 IAM 权限

在通过 Global CRIS 调用 Claude 模型之前，你必须配置能考虑跨区域路由架构的 IAM 权限。以下小节将介绍该策略的结构，并解释为什么需要三个独立的 statement。

完成以下步骤来为 Global CRIS 配置 IAM 权限。该 IAM 策略授予通过 Global CRIS 调用 Claude 模型的权限。由于 CRIS 会跨区域路由请求，该策略需要三个 statement。你在源区域（Singapore 或 Jakarta）调用推理配置文件，它随后在 CRIS 选定的目标区域中调用基础模型。第三个 statement 使用 `"aws:RequestedRegion": "unspecified"` 来授予 Global CRIS 跨区域路由你的请求所需的权限。

将 `<ACCOUNT>` 替换为你的 AWS 账户 ID，如果你使用 Jakarta（`ap-southeast-3`）而不是 Singapore（`ap-southeast-1`），请相应调整源区域。

            "Action": "bedrock:InvokeModel",

如果贵组织的服务控制策略（SCP）拒绝访问 `unspecified` 区域，Global CRIS 将无法工作。我们建议在部署依赖全球路由的生产工作负载之前先验证你的 SCP 配置。

如果你的组织把 AWS API 调用限制在特定区域，请确保你的 SCP 在允许的区域列表中包含 `"unspecified"`。以下示例展示了如何配置允许 Global CRIS 路由的 SCP。请把 Global CRIS 的源区域（Singapore `ap-southeast-1` 或 Jakarta `ap-southeast-3`）以及你组织使用的其他区域一并加入：

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "DenyAllOutsideApprovedRegions",
            "Effect": "Deny",
            "Action": "*",
            "Resource": "*",
            "Condition": {
                "StringNotEquals": {
                    "aws:RequestedRegion": [
                        "ap-southeast-1",
                        "unspecified"
                    ]
                }
            }
        }
    ]
}
```

配置好 IAM 权限后，你就可以使用推理配置文件和 Converse API 通过 Global CRIS 调用 Claude 模型。

### 使用跨区域推理配置文件

全球推理配置文件通过其模型 ID 中的 `global.` 前缀来标识，这是一种命名约定，可用于区分全球路由配置文件与区域级或单区域模型 ID。发起 API 调用时请使用这些推理配置文件 ID，而不是标准模型 ID：

| **模型** | **基础模型 ID** | **全球推理配置文件 ID** |
| --- | --- | --- |
| Claude Sonnet 4.6 | anthropic.claude-sonnet-4-6 | **global**.anthropic.claude-sonnet-4-6 |
| Claude Opus 4.6 | anthropic.claude-opus-4-6-v1 | **global.**anthropic.claude-opus-4-6-v1 |
| Claude Sonnet 4.5 | anthropic.claude-sonnet-4-5-20250929-v1:0 | **global**.anthropic.claude-sonnet-4-5-20250929-v1:0 |
| Claude Haiku 4.5 | anthropic.claude-haiku-4-5-20251001-v1:0 | **global**.anthropic.claude-haiku-4-5-20251001-v1:0 |

[InvokeModel](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_InvokeModel.html) 和 [Converse](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html) API 都支持跨区域推理配置文件。我们推荐使用 Converse API，它在不同基础模型之间提供简化的接口和一致的请求/响应格式，因此你可以在模型之间切换而无需重写集成代码。

### 发起你的第一次 API 调用

开始使用 Global CRIS 只需对现有应用代码做少量修改。以下代码片段演示了如何在 Python 中使用 boto3 SDK 通过 Global CRIS 调用 Claude Opus 4.6：

```
import logging
import os

import boto3
from botocore.exceptions import ClientError

# Configure logging
logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

# Load configuration from environment variables with defaults
REGION = os.getenv(
    "AWS_REGION", "ap-southeast-1"
)  # Singapore or Jakarta (ap-southeast-3)
MODEL_ID = os.getenv("MODEL_ID", "global.anthropic.claude-opus-4-6-v1")
MAX_TOKENS = int(os.getenv("MAX_TOKENS", "8000"))
TEMPERATURE = float(os.getenv("TEMPERATURE", "1"))
THINKING_TYPE = os.getenv("THINKING_TYPE", "adaptive")
EFFORT_LEVEL = os.getenv("EFFORT_LEVEL", "medium")

# Initialize Bedrock Runtime client for your Region
bedrock_runtime = boto3.client(service_name="bedrock-runtime", region_name=REGION)

# Example: Architecture trade-offs analysis
user_query = "Analyze the trade-offs between microservices and monolithic architectures for a mid-size SaaS company."

# Make inference request using Converse API with adaptive thinking
try:
    response = bedrock_runtime.converse(
        modelId=MODEL_ID,
        messages=[{"role": "user", "content": [{"text": user_query}]}],
        inferenceConfig={"maxTokens": MAX_TOKENS, "temperature": TEMPERATURE},
        additionalModelRequestFields={
            "thinking": {"type": THINKING_TYPE},
            "output_config": {"effort": EFFORT_LEVEL},
        },
    )
except ClientError as e:
    logger.error("Failed to invoke model %s: %s", MODEL_ID, e)
    raise

# Extract response content
output_message = response["output"]["message"]
has_thinking = any(block.get("type") == "thinking" for block in output_message["content"])

logger.info("Effort level: %s", EFFORT_LEVEL)
logger.info("Claude decided to think: %s", has_thinking)

for block in output_message["content"]:
    if block.get("type") == "thinking":
        thinking_tokens = len(block["thinking"].split())
        logger.info("[Thinking]: ~%d words", thinking_tokens)
    elif block.get("text"):
        logger.info("[Response]: %s", block["text"])
```

如果你是第一次使用跨区域能力，可能会以为把请求路由到多个区域会让监控设置变得复杂。使用 Global CRIS 并非如此。即使推理请求在其他地方处理，你的 Amazon CloudWatch 指标、CloudWatch 日志和 AWS CloudTrail 审计日志仍保留在源区域。你现有的仪表板、告警和审计轨迹会完全照常工作。

有关 Converse API 和可用参数的更多信息，请参阅 [Amazon Bedrock API Reference](https://docs.aws.amazon.com/bedrock/latest/APIReference/welcome.html)。

### 理解配额并为规模做规划

Amazon Bedrock 通过执行服务配额来支持公平的资源分配和系统稳定性。对于 Global CRIS，配额按两个维度衡量，每个维度在容量管理中各有不同用途：

- **每分钟 token 数（TPM）** – 每分钟可处理的 token（输入 + 输出）最大数量。
- **每分钟请求数（RPM）** – 每分钟可发起的推理请求最大数量。

默认配额因模型而异，并按源区域分配。你可以进入源区域（Singapore 或 Jakarta）的 Amazon Bedrock 服务配额，在 [AWS Service Quotas 控制台](https://console.aws.amazon.com/servicequotas/) 中查看当前配额。

Amazon Bedrock 使用 [token 消耗速率](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-token-burndown.html)（token burndown rate），在计算配额消耗时对输出 token 的权重高于输入 token。该速率为 5:1，意味着输出 token 消耗的配额是输入 token 的五倍，因为生成 token 比处理输入需要更多计算。

`Quota consumption = Input tokens + (Output tokens × 5)`

以[示例](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-token-burndown.html)来说，如果你的请求使用 10,000 个输入 token 并生成 5,000 个输出 token：

`Total quota consumption = 10,000 + (5,000 × 5) = 35,000 tokens`

出于限流计算，该请求会对你的 TPM 配额消耗 35,000 个 token。在规划容量需求和申请配额提升时，你需要在计算中考虑这一消耗速率。如果你的应用以相同的 token 模式每分钟处理 100 个请求，总配额消耗将是 3,500,000 TPM（100 个请求 × 每个请求 35,000 token）。与 AWS Account Manager 一起处理配额提升申请时，请提供你预期的请求量、每个请求的平均输入 token 数和平均输出 token 数，以便他们用这个消耗倍数计算合适的配额分配。

### 有效管理配额

我们建议在配额使用率达到 70–80% 时设置 CloudWatch 告警，以便在触及限流上限之前申请提升。CloudWatch 指标 `InputTokenCount` 和 `OutputTokenCount` 会实时跟踪你的消耗，而 `InvocationClientErrors` 指标在出现尖峰时说明发生了限流，为容量规划提供早期预警信号。有关可用指标以及如何为 Amazon Bedrock 工作负载配置监控的详细指导，请参阅[监控 Amazon Bedrock 的性能](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring.html)。

对于对时间不敏感的工作负载，Claude Haiku 4.5 支持批处理推理，可节省 50% 的成本。批处理请求会在 24 小时内异步处理，且不计入你的实时 TPM 配额。

### 申请配额提升

在判断是否需要提升配额时，请考虑以下因素：工作负载规模（峰值流量期间每分钟的请求数）、输出 token 占比（大量生成输出会更快消耗配额），以及增长预期（考虑 6–12 个月的扩展需求）。如果你的工作负载需要超出默认上限的配额，可以通过 [AWS Service Quotas 控制台](https://console.aws.amazon.com/servicequotas/) 申请提升。

完成以下步骤，通过 AWS Service Quotas 控制台申请配额提升：

- 在源区域登录 AWS Service Quotas 的 AWS Management Console。
- 进入 AWS services 并选择 **Amazon Bedrock**。
- 搜索你所用模型对应的 `Global cross-Region model inference tokens per minute`。
- 选择该配额，然后选择 **Request increase at account level**。
- 输入你期望的配额值并说明提升理由。
- 提交请求以供 AWS 审核。

申请配额提升时要提前规划，以便在发布或扩容活动之前确保容量可用。对于大规模部署或时间敏感的发布，我们建议与你的 AWS 客户团队合作，规划合适的容量并加快审核。

## 从 Claude 3.x 迁移到 Claude 4.5 / 4.6

对于使用 Opus、Sonnet 或 Haiku 版本的组织来说，从 Claude 3.x 迁移到 Claude 4.5 / 4.6 是一次重要升级。Claude 的混合推理架构在工具集成、memory 管理和上下文处理能力方面带来了改进。

如需更多技术实现指导，请参阅 AWS 博客文章[在 Amazon Bedrock 上从 Anthropic 的 Claude Sonnet 3.x 迁移到 Claude Sonnet 4.x](https://aws.amazon.com/blogs/machine-learning/migrate-from-anthropics-claude-sonnet-3-x-to-claude-sonnet-4-x-on-amazon-bedrock/)，其中提供了对迁移到新的 Claude Sonnet 4.6 模型同样有效的重要最佳实践。此外，Anthropic 的[迁移文档](https://docs.claude.com/en/docs/about-claude/models/migrating-to-claude-4)提供了针对具体模型的优化策略，以及迁移到 Claude 4.5 / 4.6 模型时的注意事项。

## 最佳实践

考虑以下优化技术，以最大化性能并最小化工作负载成本：

**1. 对重复上下文使用 prompt caching**

对于反复使用相同上下文的工作负载，prompt caching 可带来最高[缓存 token 成本降低 90%、延迟改善 85%](https://aws.amazon.com/bedrock/prompt-caching/) 的效果。请缓存超过 500 个 token 的 system prompt、文档内容、few-shot 示例和工具定义。构造 prompt 时把静态内容放在前面，随后是动态查询。实现细节请参阅 [Prompt caching for faster model inference 用户指南](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)。

**2. 模型选择策略**

在模型之间做选择时，请考虑任务复杂度、延迟要求、成本约束和准确性需求。对于需要前沿智能的最复杂任务，例如复杂的多步骤推理、精密的自主 agent 和对精度至关重要的分析，我们推荐 Claude Opus 4.6。Claude Sonnet 4.6 非常适合需要 agent 规划与执行的复杂问题。Claude Haiku 4.5 以更低的成本提供接近前沿的性能，因此适合高吞吐运营和对延迟敏感的场景。对于多 agent 架构，可以考虑用 Opus 4.6 或 Sonnet 4.6 作为编排者，用 Haiku 4.5 作为并行执行的工作者。

**3. 面向复杂任务的自适应思考与扩展思考**

Claude Opus 4.6 支持 adaptive thinking，它是 extended thinking 的演进，让 Claude 可以在它判断需要推理时自由决定是否思考。你可以使用 effort 参数引导 Claude 分配多少思考量，从而同时优化性能和速度。Sonnet 4.6 和 Haiku 4.5 支持 extended thinking，模型通过问题分解、自我纠错和探索多条解题路径来生成中间推理步骤。这些思考能力可在复杂推理任务上提升准确性，因此请有选择地启用它们，只在准确性提升足以抵消额外配额消耗的场景使用。

**4. 通过负载测试验证配额**

在生产发布前运行负载测试，以测量峰值流量下的实际配额消耗。为测试客户端配置自适应重试模式（`Config(retries={'mode': 'adaptive'})`）以处理测试期间的限流。使用 Locust 或带 threading 的 boto3 等工具模拟并发请求，并在负载测试期间监控 CloudWatch 指标，观察 TPM 和 RPM 的消耗模式。用 20 个并发线程持续发起请求的测试可以快速揭示你的配额分配是否匹配预期负载。

## 总结与后续步骤

Amazon Bedrock 上的 Global cross-Region inference 为泰国、马来西亚、新加坡、台湾和印度尼西亚的组织交付 Claude Opus 4.6、Sonnet 4.6 和 Haiku 4.5 模型，并带来两项关键优势：相比区域级配置文件更低的成本，以及跨 20 多个 AWS 区域路由请求，从而获得更高的可用性和规模。

该基础设施为东南亚各地的生产级 AI 应用提供支持，从实时客户服务到金融分析和自主编码助手。Claude Opus 4.6 为最苛刻的企业工作负载提供智能，Sonnet 4.6 为日常生产用例提供均衡的性能，Haiku 4.5 支持高性价比的高吞吐运营。对于多 agent 架构，可以组合使用这些模型，在质量与经济性之间取得优化。
