# 评估并改善 Amazon Bedrock Knowledge Bases 的性能

[Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 是一项全托管能力，帮助实现从摄取到检索再到 prompt 增强的完整检索增强生成（RAG）工作流，而无需为数据源构建自定义集成，也无需管理数据流。

优化知识库性能没有唯一方法：每个用例受配置参数的影响各不相同。因此，重要的是频繁测试、快速迭代，找出适合每个用例的最佳配置。

在本文中，我们讨论如何评估知识库的性能，包括应使用哪些指标和数据来评估。我们还会讨论一些能够改善特定指标的战术与配置变更。

## 衡量知识库的性能

RAG 是一个复杂的 AI 系统，由若干关键步骤组合而成。为了找出是什么在影响 pipeline 的性能，重要的是独立评估每一个步骤。知识库评估框架把评估拆分为以下阶段：

- **检索** – 基于查询检索文档相关部分，并把检索到的元素作为上下文加入知识库最终 prompt 的过程
- **生成** – 把用户 prompt 和检索到的上下文发送给大语言模型（LLM），然后把 LLM 的输出返回给用户

下图说明了 RAG pipeline 中的标准步骤。

### 评估检索

我们建议先独立评估检索过程，因为这一基础阶段的准确性与质量会显著影响 RAG 工作流下游的性能指标，可能引入会传播到后续 pipeline 阶段的错误或偏差。

[![仅检索的评估](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/13/ML-17061-3-retrieval-only.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/13/ML-17061-3-retrieval-only.jpg)

用于评估检索的指标有两个：

- **上下文相关性** – 评估检索到的信息是否直接针对查询意图。它关注检索系统的精确性。
- **上下文覆盖度** – 衡量检索到的文本覆盖预期 ground truth 的全面程度。它需要 ground truth 文本作对比，以评估检索信息的召回率与完整性。

上下文相关性与上下文覆盖度指标，是通过把 RAG pipeline 的检索结果与测试数据集中的期望答案进行比较而汇总得出的。下图说明了该工作流。

[![带检索指标的 RAG pipeline](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/13/ML-17061-4-context-relevance-coverage.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/13/ML-17061-4-context-relevance-coverage.jpg)

运行评估需要您提供符合特定格式规范的数据集。数据集必须采用 [JSON Lines 格式](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-evaluation-prompt-retrieve.html)，每一行代表一个有效的 JSON 对象。为保持最佳性能，每次评估的数据集应限制在最多 1,000 个 prompt。数据集中的每个 prompt 都必须是结构良好、有效的 JSON 对象，能够被评估系统正确解析和处理。

如果您选择评估上下文覆盖度，就需要提供 ground truth，即作为衡量覆盖度基线的文本。ground truth 必须包含 referenceContexts，且 ground truth 中的每个 prompt 都必须有对应的 reference context，才能进行准确评估。

以下示例代码展示了必需字段：

```
{
    "conversationTurns": [{
        "referenceContexts": [{
            "content": [{
                "text": "ground truth text"
            }]
        }],
        "prompt": {
            "content": [{
                "text": "query text"
            }]
        }
    }]
}
```

更多详情见[为仅检索评估任务创建 prompt 数据集](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-evaluation-prompt-retrieve.html)。

### 评估生成

在确认您的 RAG 工作流能够成功从向量数据库检索相关上下文并符合预先设定的性能标准之后，就可以继续评估 pipeline 的生成阶段。Amazon Bedrock 评估工具提供了一个全面的评估框架，包含八项指标，覆盖回答质量与负责任 AI 两个方面。

回答质量包括以下指标：

- **有用性** – 评估生成的回答在回答问题方面有多大用处、覆盖多全面
- **正确性** – 评估回答问题的准确程度
- **逻辑连贯性** – 检查回答中的逻辑跳跃、不一致或自相矛盾
- **完整性** – 评估回答是否覆盖了问题的所有方面
- **忠实度** – 衡量事实准确性以及抵抗幻觉的能力

负责任 AI 包括以下指标：

- **有害性** – 评估回答中是否存在仇恨、侮辱或暴力内容
- **刻板印象** – 评估是否存在针对群体或个体的概括性表述
- **拒答** – 衡量系统在何种程度上恰当地拒绝回答不当问题

回答质量与负责任 AI 指标，是通过把 RAG pipeline 的检索结果和生成的回答与 ground truth 答案进行比较而汇总得出的。下图说明了该工作流。

[![带回答质量指标的 RAG pipeline](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/13/ML-17061-5-response-quality-metrics.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/13/ML-17061-5-response-quality-metrics.jpg)

用于评估的数据集必须符合特定的结构要求，采用 JSON Lines 格式，每次评估最多 1,000 个 prompt。每个 prompt 必须是具有明确结构的有效 JSON 对象。在该结构中，有两个关键字段发挥重要作用：prompt 字段包含用于模型评估的查询文本，referenceResponses 字段存储用于衡量模型表现的期望 ground truth 回答。这种格式有助于在不同测试场景下以标准化、一致的方式评估模型输出。

以下示例代码展示了必需字段：

```
{
    "conversationTurns": [{
        "referenceResponses": [{
            "content": [{
                "text": "This is a reference text"
            }]
        }],

        ## your prompt to the model
        "prompt": {
            "content": [{
                "text": "This is a prompt"
            }]
        }
    }]
}
```

更多详情见[为检索并生成评估任务创建 prompt 数据集](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-evaluation-prompt-retrieve-generate.html)。

以下截图展示了 Amazon Bedrock 评估结果的示例仪表板。

[![指标汇总示例](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/13/ML-17061-6-metric-summary.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/13/ML-17061-6-metric-summary.jpg)

处理完成后，评估会提供全面的洞见，既给出聚合指标，也给出每项指标的细粒度表现拆解。这些详细结果包含示例对话，用以说明表现上的细微差异。为获得最大价值，我们建议进行定性复核，尤其关注在任何指标上得分较低的对话。这种深入分析有助于您理解造成表现不佳的深层因素，并为 RAG 工作流的战略性改进提供依据。

## 构建全面的测试数据集：策略与考量

创建稳健的测试数据集对有意义评估至关重要。本节讨论数据集开发的三种主要方法。

### 人工标注的数据收集

人工标注仍然是领域专属、高质量数据集的黄金标准。您可以：

- 使用贵组织的专有文档与答案
- 使用开源文档集合，如 [Clueweb](https://arxiv.org/abs/2211.15848)（一个 100 亿网页文档库）
- 采用专业的数据标注服务，如 [Amazon SageMaker Ground Truth](https://docs.aws.amazon.com/sagemaker/latest/dg/sms.html)
- 使用众包市场，如 [Amazon Mechanical Turk](https://www.mturk.com/) 进行分布式标注

对于领域专属、高质量且需要细致区分的结果，建议采用人工数据标注。然而，使用人工标注者生成和维护大型数据集是耗时且昂贵的方法。

### 使用 LLM 生成合成数据

合成数据生成提供了一种更自动化、可能更具成本效益的替代方案，主要有两种方法：

- 自指导（self-instruct）方法： 使用单个目标模型的迭代过程 模型针对查询生成多个回答 提供持续反馈与优化
- 知识蒸馏方法： 使用多个模型 基于已有的模型训练生成回答 通过复用已训练好的模型加快数据集创建

合成数据生成需要谨慎处理若干关键考量。组织通常必须取得最终用户许可协议（EULA），并且可能需要访问多个 LLM。尽管该过程对人工专家验证的需求很少，但这些战略性要求凸显了高效生成合成数据集的复杂性。该方法为传统数据标注方法提供了一种简化的替代方案，在 legal compliance 与技术创新之间取得平衡。

### 持续改进数据集：反馈闭环策略

制定一种动态、迭代的数据集增强方法，把用户交互转化为宝贵的学习机会。以现有数据作为基础基线，然后实现一套稳健的用户反馈机制，系统性地捕获并评估真实世界的模型交互。建立结构化流程来复核并整合被标记的回答，把每条反馈都当作数据集的潜在改进点。关于在 AWS 中实现此类反馈闭环的示例，请参阅[在 Amazon SageMaker 上借助人工与 AI 反馈为 Amazon Engineering 提升 LLM 性能](https://aws.amazon.com/blogs/machine-learning/improve-llm-performance-with-human-and-ai-feedback-on-amazon-sagemaker-for-amazon-engineering/)。

这种方法把数据集开发从一次性静态工作转变为活的、自适应的系统。通过用户驱动的洞见不断扩展和优化数据集，您就创建了一种自我改进机制，逐步提升模型表现与评估指标。请记住：数据集的演进不是终点，而是持续渐进优化的旅程。

开发测试数据集时，应力求取得战略平衡，准确代表用户将遇到的各种场景。数据集应全面覆盖潜在用例与边缘用例，同时避免不必要的重复。由于每个评估示例都会产生成本，应专注于创建能最大化洞见、最大化性能理解的数据集，选择能揭示独特模型行为的示例，而非冗余的重复。目标是打造一个有针对性的高效数据集，在不把资源浪费在多余测试上的前提下提供有意义的性能评估。

## 性能改进工具

全面的评估指标不只是性能指示器——它们是持续改进 RAG pipeline 的战略路线图。这些指标提供关键洞见，把抽象的性能数据转化为可执行的智能，使您能够：

- 诊断 pipeline 的具体薄弱环节
- 确定改进工作的优先级
- 客观评估知识库的就绪程度
- 做出数据驱动的优化决策

通过系统性地分析指标，您可以明确回答关键问题：您的知识库是否足够稳健、可以部署？哪些具体组件需要改进？为获得最大影响，应把优化精力集中在哪里？

把指标视为一种诊断工具，它照亮从当前表现通往卓越 AI 系统可靠性的道路。它们不只是度量——更是指引，为战略性提升提供清晰的量化框架。

尽管真正全面地探讨 RAG pipeline 优化需要一部长篇专著，本文提供了一个系统化框架，用于在关键维度上实现变革性改进。

### 数据基础与预处理

数据基础与预处理包括以下最佳实践：

- 清洗并预处理源文档以提升质量，去除噪声、统一格式并保持数据一致性
- 用相关的外部来源扩充训练数据，扩大数据集的多样性与覆盖面
- 实现命名实体识别与链接以改进检索，增强语义理解与上下文识别
- 使用文本摘要技术压缩长文档，在保留关键信息的同时降低复杂度

### 分块策略

请考虑以下分块策略：

- 使用语义分块而非固定大小分块来保留上下文，维持有意义的信息边界。
- 探索多种分块大小（128–1,024 个字符），适应语义文本结构，并通过智能切分来保留含义。有关 Amazon Bedrock 分块策略的更多细节，请参阅[知识库的内容分块工作方式](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking-parsing.html)。
- 实现带重叠的滑动窗口分块，最大限度减少分块之间的信息损失，通常使用 10–20% 的重叠以提供上下文连续性。
- 对长文档考虑层级分块，同时捕获局部与全局的上下文差异。

### 嵌入技术

嵌入技术包括以下内容：

- 如果您的文本包含多种语言，可以尝试使用 Cohere Embed (Multilingual) 嵌入模型。这可以改善语义理解与检索相关性。
- 试验不同的嵌入维度，在性能与计算效率之间取得平衡。
- 实现句子级或段落级嵌入，超越词级表示。

### 检索优化

请考虑以下检索优化最佳实践：

- 以静态或动态方式调整检索分块的数量，优化信息密度。在您的 [RetrieveAndGenerate](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_RetrieveAndGenerate.html#API_agent-runtime_RetrieveAndGenerate_RequestSyntax)（或 [Retrieve](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_Retrieve.html)）请求中，修改 `"retrievalConfiguration": { "vectorSearchConfiguration": { "numberOfResults": NUMBER }}`。
- 实现[元数据过滤](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-knowledge-bases-now-supports-metadata-filtering-to-improve-retrieval-accuracy/)，为分块检索添加上下文层次。例如，在时间敏感场景中优先考虑较新的信息。有关使用 Amazon Bedrock Knowledge Bases 进行元数据过滤的代码示例，请参阅以下 [GitHub 仓库](https://github.com/aws-samples/amazon-bedrock-samples/blob/main/docs/rag/knowledge-bases/features-examples/03-advanced-concepts/dynamic-metadata-filtering/dynamic-metadata-filtering-KB.md)。
- 使用[混合搜索](https://aws.amazon.com/blogs/machine-learning/knowledge-bases-for-amazon-bedrock-now-supports-hybrid-search/)，结合稠密与稀疏检索，融合语义搜索与关键词搜索两种方式。
- 应用重排序（reranking）模型提升精确性，按相关性重新组织检索到的上下文。
- 试验多种相似度度量，探索标准余弦相似度之外的选项。
- 实现查询扩展技术，转换查询以获得更有效的检索。一个例子是查询分解，把复杂查询拆解为有针对性的子问题。

### Prompt 工程

选定模型后，您可以编辑 prompt 模板：

- 设计上下文感知的 prompt，明确引导模型使用检索到的信息
- 实现 few-shot prompting，使用动态的、与查询匹配的示例
- 基于查询与文档创建动态 prompt，因地制宜地调整指令策略
- 为检索到的信息加入明确的使用说明，实现忠实且精确的回答生成

### 模型选择与 guardrails

选择模型与 guardrails 时，请考虑以下内容：

- 依据具体任务要求选择 LLM，让模型能力与用例相匹配
- 在领域专属数据上微调模型，增强专业化表现
- 试验不同的模型规模，在性能与计算效率之间取得平衡
- 考虑专门的模型配置，用较小的模型做检索、较大的模型做生成
- 实现上下文 grounding 检查，确保回答忠于所提供的信息，例如使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 的[上下文 grounding](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-contextual-grounding-check.html)（见以下截图）
- 探索高级搜索范式，例如知识图谱搜索（GraphRAG）

## 应对知识库改进：关键考量

优化 RAG 系统时，理解您的性能要求至关重要。可接受的性能标杆完全取决于应用的语境——它是内部工具、增强人工的系统，还是面向客户的服务。0.95 的指标得分对某些应用可能足够（毕竟 20 个回答里可能有 1 个存在轻微不准确），但对高风险场景则可能不可接受。关键在于让优化工作与您特定用例对可靠性和精确性的需求相匹配。

另一个关键是优先改进检索机制，然后再处理生成。上游表现会直接影响下游指标，因此检索优化至关重要。某些技术，特别是分块策略，在两个阶段都会产生微妙影响。例如，增大分块尺寸可以通过降低搜索复杂度提升检索效率，但同时可能引入无关细节，进而损害生成的正确性。这种微妙的平衡需要谨慎、渐进式的调整，以确保检索精确性与回答质量都得到系统性提升。

### 诊断问题

针对某个特定性能指标时，请采用类似取证、以人为本的诊断方式。把您的 AI 系统当作一位同事，对其工作需要给予深思熟虑的建设性反馈。这包括以下步骤：

- 失败模式识别： 系统性地梳理总是表现不佳的问题类型 找出触发不良表现的具体特征，例如： 列表类查询 专业词汇领域 复杂主题交叉 上下文检索取证： 进行细粒度的分块相关性分析 量化无关或不正确的检索上下文 绘制检索集合内的精确性分布（例如 15 个分块中前 5 个相关、后 10 个不相关） 了解检索机制的上下文区分能力 ground truth 对比分析： 严格把生成的回答与参考答案对比 诊断 ground truth 可能存在的局限 制定有针对性的改进说明——思考什么样的具体指引能提升回答准确性，以及可能缺少哪些细微的上下文

### 制定战略性的改进方法

面对复杂的 RAG pipeline 挑战时，请采用有条理、有策略的方法，把性能优化从令人生畏的任务转变为系统性、渐进式提升的旅程。

关键在于识别那些对您特定目标指标有直接、可衡量影响的战术，把精力集中在潜在投入产出比最高的优化点上。这意味着要透过可能带来多大性能提升的视角，仔细分析每一种潜在策略，重点关注那些能以最小系统性扰动带来有意义收益的技术。下图说明了在努力改善指标时应优先考虑哪几组技术。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/17/ML-17061-11-mind-map-new.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/13/ML-17061-11-mind-map.jpg)

此外，您应优先考虑低摩擦的优化战术，例如知识库中的可配置参数，或者对基础设施扰动最小的实现方式。除非必要，建议避免对向量数据库做整体重构。

您应采取精简的路线——把 RAG pipeline 的改进变成一个有条理、科学的持续优化过程。拥抱战略性渐进主义：做出有目的、有针对性的调整，小到可以精确衡量，又足以推动性能向前。

每一次修改都成为一次实验性干预，经过严格测试以了解其具体影响。建立完善的版本跟踪体系，不仅记录所做的变更，还记录每次调整背后的理由、变更前后的性能指标以及获得的洞见。

最后，请以整体、共情的方法来做性能评估，超越纯粹的量化指标。把评估过程视为一场关于成长与理解的协作对话，就像你在辅导一位有才华的团队成员时会采取的那种细致方式。不要只把表现简化为冰冷的数字指标，而应努力揭示底层动态、语境挑战与发展潜力。要认识到，有意义的评估超越表面测量，需要深入洞察能力、局限以及表现所处的独特语境。

为 RAG 优化 Amazon Bedrock Knowledge Bases 是一个需要系统性测试与优化的迭代过程。成功来自有条理地运用 prompt 工程和分块等技术，改善 RAG 的检索与生成两个阶段。通过在整个过程中跟踪关键指标，您可以衡量优化带来的影响，并确保它们满足应用的要求。
