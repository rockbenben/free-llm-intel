# OfferUp 借助 Amazon Bedrock 与 Amazon OpenSearch Service 上的多模态搜索，将本地结果提升 54%、相关性召回率提升 27%

*本文由 OfferUp 的 Andrés Vélez Echeveri 和 Sean Azlin 共同撰写。*

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/18/OfferUp-147x300.jpeg)

[OfferUp](https://offerup.com/) 是一个在线、移动优先的市场平台，旨在促进本地交易与发现。OfferUp 以其易用的 app 和建立信任的特性（包括用户评分和应用内聊天）而闻名，它让用户能够买卖物品，并探索广泛的工作机会与本地服务。作为持续提升用户体验、推动业务增长这一使命的一部分，OfferUp 不断寻求改进其搜索能力，让用户在自己的本地社区中发现、交易和连接变得更快、更直观。

在这个分两篇的博客系列中，我们探讨 OfferUp 在其旅程中把握的关键机会——把现有的搜索解决方案从传统的词法搜索升级并转变为由 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 和 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 驱动的现代多模态搜索。OfferUp 发现，多模态搜索将相关性召回率提升了 27%，把地理分散度（这意味着更多本地结果）降低了 54%，并使搜索深度增长了 6.5%。本系列深入介绍各种策略、架构模式、业务收益以及技术步骤，帮助你实现自有搜索解决方案的现代化

## 基础搜索架构

OfferUp 托管着数以百万计的活跃商品条目，其用户每月还会新增数百万条。此前，OfferUp 的搜索引擎构建在 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2/)（Amazon EC2）上的 Elasticsearch（v7.10）之上，使用关键词搜索算法来查找相关条目。下图展示了基础搜索架构中用于索引和查询的数据管道。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/02/05/Foundational_architecture_new.jpg)

##### 图 1：基础搜索架构

数据索引工作流包含以下步骤：

- 当 OfferUp 用户创建或更新商品条目时，任何新图片都会通过带签名的上传 URL 直接上传到 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）。
- OfferUp 用户把新增或更新的条目详情（标题、描述、图片 id）提交给 posting 微服务。
- posting 微服务随后通过 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 中的 listing writer 微服务持久化这些变更。
- listing writer 微服务把条目变更事件发布到一个 [Amazon Simple Notification Service](https://aws.amazon.com/sns/)（Amazon SNS）主题，由 [Amazon Simple Queue Service](https://aws.amazon.com/sqs/)（Amazon SQS）队列订阅该主题。
- listing indexer [AWS Lambda](https://aws.amazon.com/lambda/) 函数持续轮询该队列，并处理传入的条目更新。
- indexer 通过 listing reader 微服务从 DynamoDB 表中获取完整的条目详情。
- 最后，indexer 把这些条目详情更新或插入到 Elasticsearch 中。

这一流程确保新增或更新的条目被索引，并可在 Elasticsearch 中供搜索查询使用。

数据查询工作流包含以下步骤：

- OfferUp 用户执行文本搜索，例如“夏季衬衫”或“跑鞋”。
- search 微服务处理查询请求，并使用关键词搜索（以 BM25 作为排序算法）从 Elasticsearch 中检索相关条目。

## 基础搜索架构面临的挑战

OfferUp 持续努力提升用户体验，尤其专注于改善搜索相关性，因为这直接影响卖家响应互动率（Engagement with Seller Response，EWSR）并驱动广告展示。尽管基础搜索架构能够有效地呈现广泛而多样的库存，OfferUp 仍遇到了一些限制，使其无法取得最优结果。这些挑战包括：

- **上下文理解** – 关键词搜索不考虑词语被使用时的上下文。如果同一个关键词有不同的含义或用法，就可能导致不相关的结果。仅凭关键词无法辨别用户意图。例如，“apple”在不同语境下可能指水果、科技公司或品牌名。
- **同义词与变体识别** – 如果搜索词有变化或使用了同义词，关键词搜索可能会漏掉结果。例如，搜索“car”可能不会返回“sedan”的结果。同样，搜索 iPhone 11 可能返回 iPhone 10 和 iPhone 12 的结果。
- **复杂查询的处理** – 基础搜索方法难以应对像“红色跑鞋”这样包含多个概念的复杂查询，常常返回其他颜色的鞋，或者并非为跑步设计的鞋类。

以 BM25 作为排序算法的关键词搜索缺乏理解词语之间语义关系的能力，如果结果不包含精确的关键词，往往会漏掉语义上相关的结果。

## 解决方案概览

为提升搜索质量，OfferUp 探索了多种软件与硬件方案，重点在于提升搜索相关性，同时保持成本效益。最终，OfferUp 选择了 [Amazon Titan Multimodal Embeddings](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-multiemb-models.html) 和 Amazon OpenSearch Service，因为它们是全托管服务，支持构建稳健的多模态搜索解决方案，能够在搜索和推荐用例中提供高精度与快速响应。这一选择还简化了 OfferUp app 上大规模搜索能力的部署与运维，满足了高吞吐和低延迟的要求。

### **Amazon Titan Multimodal Embeddings G1 模型**

该模型已在大型数据集上预训练，因此你可以直接使用它，也可以针对特定任务用自己的数据微调来定制该模型。该模型适用于按文本搜图、按图搜图，或按文本与图片的组合进行相似性搜索与个性化等用例。它把输入的图片或文本转换为 embedding，在同一语义空间中包含图片和文本两者的语义含义。通过比较 embedding，该模型能产生比单纯关键词匹配更相关、更贴合上下文的响应。

Amazon Titan Multimodal Embeddings G1 提供以下配置：

- **模型 ID** – amazon.titan-embed-image-v1
- **最大输入文本 token 数** – 256
- **最大输入图片大小** – 25 MB
- **输出向量维度** – 1,024（默认）、384、256
- **推理类型** – On-Demand、Provisioned Throughput

### **OpenSearch Service 的向量数据库能力**

向量数据库支持在存储向量的同时存储元数据并建立索引，从而便于以低延迟查询基于相似性发现资产。这类数据库通常使用 k 最近邻（k-NN）索引，这些索引由 Hierarchical Navigable Small Worlds（HNSW）和 Inverted File（IVF）系统等先进算法构建。除基本的 k-NN 功能之外，向量数据库还为需要数据管理、容错、资源访问控制以及高效查询引擎的应用提供了稳健的基础。

OpenSearch 是一套强大的开源套件，为搜索、分析、安全监控和可观测性提供可扩展且灵活的工具——全部基于 Apache 2.0 许可证。借助 Amazon OpenSearch Service，你可以获得完全托管的解决方案，在 AWS 云中简单轻松地部署、扩展和运维 OpenSearch。通过把 Amazon OpenSearch Service 用作向量数据库，你可以把传统搜索、分析和向量搜索合并为一个全面的解决方案。[OpenSearch 的向量能力](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/knn.html)有助于加速 AI 应用开发，让团队更容易把 AI 驱动的资产投入运营、进行管理并完成集成。

为进一步增强这些能力，OpenSearch 提供如下高级特性：

- **Amazon Bedrock 连接器** – 你可以通过内置的服务连接器，把 Amazon Bedrock 机器学习（ML）模型无缝集成到 OpenSearch，从而直接访问高级 ML 特性。
- [**Ingest Pipeline**](https://opensearch.org/docs/latest/ingest-pipelines/) – 借助 ingest pipeline，你可以高效地处理、转换和路由数据，保持顺畅的数据流以及搜索所需的实时可访问性。
- [**Neural Search**](https://opensearch.org/docs/latest/search-plugins/neural-search/) – 神经搜索把文本和图片转换为向量，并在摄取时和搜索时都支持向量搜索。这让你无需离开 OpenSearch 就能端到端地配置 ingest pipeline、search pipeline 以及必要的连接器
- **改造后的多模态搜索架构** – OfferUp 借助 Amazon Bedrock Titan Multimodal 和 Amazon OpenSearch Service 改造了其基础搜索架构。

数据索引工作流包含以下步骤：

- 当 OfferUp 用户创建或更新商品条目时，任何新图片都会通过带签名的上传 URL 直接上传到 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）。
- OfferUp 用户把新增或更新的条目详情（标题、描述、图片 id）提交给 posting 微服务。
- posting 微服务随后通过 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 中的 listing writer 微服务持久化这些变更。
- listing writer 微服务把条目变更事件发布到一个 [Amazon Simple Notification Service](https://aws.amazon.com/sns/)（Amazon SNS）主题，由 [Amazon Simple Queue Service](https://aws.amazon.com/sqs/)（Amazon SQS）队列订阅该主题。
- listing indexer [AWS Lambda](https://aws.amazon.com/lambda/) 函数持续轮询该队列，并处理传入的条目更新。
- indexer 通过 listing reader 微服务从 DynamoDB 表中获取完整的条目详情。
- Lambda indexer 依赖 image 微服务获取条目图片，并以 base64 格式对它们进行编码。
- indexer lambda 把条目详情和 base 64 编码的图片作为插入和更新发送到 Amazon OpenSearch Service 域。
- OpenSearch ingest pipeline 调用面向 Amazon Bedrock 的 OpenSearch 连接器。Titan Multimodal Embeddings 模型为条目图片和描述生成多维向量 embedding。
- 随后，条目数据和 embedding 被存储在 Amazon OpenSearch 索引中。

数据查询工作流包含以下步骤：

- OfferUp 用户同时执行文本搜索和图片搜索，例如“灰色仿皮沙发”或“跑鞋”。
- search 微服务捕获查询并转发到 Amazon OpenSearch Service 域，由该域调用神经搜索管道。神经搜索管道把每个搜索请求转发给同一个 Amazon Titan Multimodal Embeddings 模型，以把文本和图片转换为多维向量 embedding。
- 随后，OpenSearch Service 使用这些向量查找与向量化后的搜索词和图片最接近的 k 个最近邻（KNN），以检索相关条目。

在对各种 k 值做了大量 A/B 测试后，OfferUp 发现 k 取 128 时能在优化计算资源的同时带来最佳的搜索结果。

## OfferUp 多模态搜索的迁移路径

OfferUp 采用三步流程，把多模态搜索功能引入其基础搜索架构。

- **确定指定市场区域（DMA）** – OfferUp 把其 DMA 分为高密度和低密度两类。高 DMA 密度指用户集中度更高的地理位置，而低 DMA 密度指用户较少的地区。OfferUp 最初确定了三个对业务至关重要的高密度地区，多模态搜索解决方案在这些地区的离线实验中展现出有希望的结果，使它们成为多模态搜索的理想候选。
- **搭建基础设施并完成必要配置** – 这包括以下内容  **OpenSearch Service：**OpenSearch 域部署在 3 个可用区（AZ）上以提供高可用性。集群由 3 个 cluster manager 节点（m6g.xlarge.search 实例）组成，专门负责管理集群操作。在数据处理方面，使用 24 个 data 节点（r6gd.2xlarge.search 实例），针对存储和处理两方面都做了优化。索引配置为 12 个 shard 和三个读副本，以提升读取性能。每个 shard 大约占用 11.6GB 内存。**Embeddings 模型：**该基础设施支持访问 Amazon Bedrock 中的 Amazon Titan Multimodal Embeddings G1。
- **使用回填** – 回填使用 Amazon Titan Multimodal Embeddings 把每个活跃条目的图片转换为向量，并存储到 OpenSearch Service 中。在第一阶段，OfferUp 回填了 1,200 万个活跃条目。

OfferUp 在这三个 DMA 中推出了多模态搜索实验，其中输入 token 的大小可能在 3 – 15 之间变化。

## 多模态搜索的收益

本节我们讨论多模态搜索的收益

### **业务指标**

OfferUp 通过 A/B 测试评估多模态搜索的影响，以管理流量控制和用户实验分组的变化。在该实验中，对照组使用现有的基于关键词的搜索，实验组则体验新的多模态搜索功能。测试覆盖了相当规模的用户基础，从而能够进行稳健的对比。

- 多模态搜索实施的结果颇具说服力。
- 用户参与度提升了 2.2%，EWSR 改善了 3.8%，凸显了搜索结果相关性的提升
- 搜索深度增长了 6.5%，因为用户更彻底地浏览了结果，这表明除最靠前的搜索结果之外的相关性也有所提升
- 重要的是，fanout 搜索（更宽泛的搜索查询）的需求下降了 54.2%，表明更多用户很快就找到了相关的本地结果
- 广告展示次数也上升了 0.91%，在提升搜索性能的同时维持了广告可见度

### **技术指标**

OfferUp 还开展了额外实验来评估技术指标，利用 6 个月的生产系统数据考察相关性召回率，重点关注高密度和低密度 DMA 中最相关的前 k=10 条结果。通过对这些地区进行分群，OfferUp 深入了解了不同市场密度下用户分布的差异如何影响系统性能，从而更深入地理解多样化市场中相关性召回的效率。

```
relevance recall (RR)= sum(listing relevance score) / number of retrieved listings
```

条目的相关性被标记为（1, 0），依据是查询与所检索条目之间的相关程度。

我们很高兴与更广泛的社区分享这些洞见，并支持那些正在开启自身多模态搜索之旅、或希望提升搜索精度的组织。基于我们的经验，我们强烈推荐使用 Amazon Bedrock 和 Amazon OpenSearch 服务来取得类似的效果。
