# 使用 Amazon Bedrock 生成结构化数据响应：Prompt Engineering 与 Tool Use

生成式 AI 正在通过精简运营、推动创新来改变各个行业。尽管与 GenAI 的文本对话交互依然流行，但真实世界的应用往往依赖结构化数据，用于 API、数据库、数据驱动的工作负载与丰富的用户界面。结构化数据还能增强对话式 AI，使其输出更可靠、更可执行。一个关键挑战在于，LLM（大语言模型）本身具有不可预测性，因此很难稳定地生成 JSON 这类结构化输出。这一挑战的根源是它们的训练数据主要是文章、书籍、网站等非结构化文本，结构化格式的样本相对很少。结果就是，LLM 在生成 JSON 输出时的精确性可能不够稳定，而这对于无缝集成到现有 API 与数据库至关重要。不同模型在支持结构化响应方面的能力存在差异，包括识别数据类型以及有效管理复杂层级结构。这些能力在选择合适的模型时会带来差别。

本文通过展示两种可选的方案，说明 [Amazon Bedrock](https://aws.amazon.com/bedrock/?trk=a9c05117-53bb-40a3-89b2-a3ee2d23e7d2&sc_channel=ps&ef_id=Cj0KCQiAouG5BhDBARIsAOc08RTIRnbZdU_ZU3sFVtfBEz5-DlIIK_V5EWzecbvxUGEKOcztISVOMXMaAgE4EALw_wcB:G:s&s_kwcid=AL!4422!3!691967569326!e!!g!!amazon%20bedrock!21054971690!157173594137&gbraid=0AAAAADjHtp-IaOcjyBDPKF1aS_xtnvv5O&gclid=Cj0KCQiAouG5BhDBARIsAOc08RTIRnbZdU_ZU3sFVtfBEz5-DlIIK_V5EWzecbvxUGEKOcztISVOMXMaAgE4EALw_wcB) 这一用于安全访问顶级 AI 模型的托管服务如何帮助应对这些挑战：

- **Prompt Engineering：** 一种直接的做法，用精心设计的 prompt 来塑造结构化输出。
- **结合 Bedrock Converse API 的 Tool Use：** 一种更进阶的方法，可带来更好的控制力、一致性，以及原生的 [JSON schema](https://json-schema.org) 集成。

我们将以一个客户评论分析的例子，配合简化的 Python 代码，演示 Bedrock 如何生成情感分数这类结构化输出。

## 构建 prompt engineering 方案

本节将演示如何有效地使用 prompt engineering，借助 Amazon Bedrock 生成结构化输出。prompt engineering 指的是精心设计输入 prompt，引导大语言模型（LLM）产出稳定且结构化的响应。它是开发生成式 AI 应用的一项基础技术，尤其是在需要结构化输出时。以下是我们将遵循的五个关键步骤：

- 配置 Bedrock 客户端与运行时参数。
- 为结构化输出创建 JSON schema。
- 精心编写 prompt，用清晰的指令与示例引导模型。
- 添加一条客户评论作为待分析的输入数据。
- 调用 Bedrock、调用模型并处理响应。

我们以客户评论分析来生成 JSON 输出作为演示，但这些方法同样可用于 XML 或 CSV 等其他格式。

首先，我们会设置一些常量，并使用 [Python Boto3 SDK for Bedrock runtime](https://boto3.amazonaws.com/v1/documentation/api/latest/reference/services/bedrock-runtime.html) 初始化一个 Python 的 Bedrock 客户端连接对象，以便与 Bedrock 交互：

![配置 AWS Bedrock 客户端及 Anthropic Claude 模型与参数的 Python 代码](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/12/ML-17009-image-1.png)

*`REGION` 指定模型执行所在的 AWS 区域，而 `MODEL_ID` 标识具体的 [Bedrock 模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)。`TEMPERATURE` 常量控制输出的随机性，值越高创造性越强，值越低则保持精确，例如在生成结构化输出时。`MAX_TOKENS` 决定输出长度，在成本效率与数据完整度之间取得平衡。*

### 步骤 2：定义 Schema

让我们为客户评论创建一个 JSON schema，包含三个必填字段：`reviewId `（string，最长 50 字符）、`sentiment`（number，-1 到 1）以及 `summary `（string，最长 200 字符）。

### 步骤 3：编写 Prompt 文本

要获得稳定、结构化且准确的响应，prompt 必须清晰且结构良好，因为 LLM 依赖精确的输入来产出可靠的输出。设计不佳的 prompt 会导致歧义、错误或格式问题，打乱结构化的流程，因此我们遵循以下最佳实践：

- 清晰界定 AI 的角色与目标，避免歧义。
- 把任务拆分为更小、可管理的编号步骤，以保持清晰。
- 说明将会提供 JSON schema（见下方步骤 5），以维持一致且有效的结构。
- 使用带示例输出的 [one-shot prompting](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-engineering-guidelines.html) 来引导模型；如为保持一致性需要，可增加更多示例，但不要过多，否则可能限制模型处理新输入的能力。
- 定义如何处理缺失或无效的数据。

### 步骤 5：调用 Bedrock

本节中，我们通过定义一个 body 对象来构造 Bedrock 请求，该对象包含 JSON schema、prompt 以及前几步得到的评论输入数据。这种结构化请求可确保模型收到清晰的指令、遵循预定义的 schema，并正确处理示例输入数据。请求准备就绪后，我们调用 Amazon Bedrock 生成结构化的 JSON 响应。

![AWS Bedrock 客户端设置，包含模型参数、消息内容以及用于客户评论分析的 API 调用](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/12/ML-17009-image-5.png)

我们复用步骤 1 中定义的 `MAX_TOKENS`、`TEMPERATURE` 与 `MODEL_ID` 常量。body 对象包含必要的推理配置，例如用于模型兼容性的 `anthropic_version `，以及 messages 数组——其中包含一条消息，向模型提供任务指令、schema 与输入数据。role 定义交互语境中的“说话者”，其 user 取值代表发送请求的程序。另一种做法是把指令、schema 与数据合并成一段文本 prompt 来简化输入，这种方式管理起来很直接，但模块化程度较低。

## 使用 Amazon Bedrock Converse API 的 Tool Use

上一章我们探讨了使用 Bedrock Prompt Engineering 的方案。现在，我们来看另一种用 Bedrock 生成结构化响应的方法。

我们将通过 Amazon Bedrock [Converse API](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html) 扩展前面的方案，这是一个一致的接口，旨在方便与生成式 AI 模型进行多轮对话。该 API 抽象掉了包括推理参数在内的各类模型特定配置，从而简化集成。

Converse API 的一个关键特性是 [Tool Use](https://docs.aws.amazon.com/bedrock/latest/userguide/tool-use-inference-call.html)（也称为 Function Calling），它让模型能够执行外部工具，例如调用外部 API。该方法支持把标准 JSON schema 直接集成到工具定义中，从而使输出与预定义格式对齐。并非所有 Bedrock 模型都支持 Tool Use，因此请务必查阅哪些[模型兼容这些特性](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference-supported-models-features.html)。

## 测试结果：Amazon Bedrock 上的 Claude 模型

理解基础模型在结构化响应生成方面的能力，对于保持可靠性、优化性能以及用 Amazon Bedrock 构建可扩展且面向未来的生成式 AI 应用至关重要。为评估模型处理结构化输出的能力，我们对 Anthropic 的 Claude 模型做了大量测试，针对每个模型分别以基于 prompt 与基于工具的方式各运行 1,000 次迭代进行对比。每次迭代处理 100 条随机生成的条目，从而在不同输入变体上获得广泛的测试覆盖。本文前面展示的示例是为了演示而有意简化的，在这些示例中 Bedrock 运行顺畅、毫无问题。为在真实世界的挑战下更好地评估模型，我们使用了一个更复杂的 schema，其中包含嵌套结构、数组与多样化的数据类型，以便发现边界情况与潜在问题。输出结果按是否符合 JSON 格式与 schema 进行了校验，以保证一致性与准确性。下图汇总了结果，展示每种模型在所演示的两种方法（Prompt Engineering 与 Tool Use）下成功且有效的 JSON 响应数量。

![柱状图展示 haiku 与 sonnet AI 模型在结构化生成中 prompt 与 tool 两种方法的成功率](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/12/ML-17009-image-8.jpg)

结果表明，所有模型在两种方法下的成功率都超过 93%，而 Tool Use 方法始终优于基于 prompt 的方法。尽管本次评估使用的 JSON schema 极为复杂，但更简单的 schema 会显著减少问题，通常几乎为零。预计模型未来的更新会进一步提升表现。

## 最终思考

总之，我们演示了用 Amazon Bedrock 生成结构化响应的两种方法：Prompt Engineering 与配合 Converse API 的 Tool Use。Prompt Engineering 灵活，可适用于各类 Bedrock 模型（包括不支持 Tool Use 的模型），并能处理多种 schema 类型（例如 Open API schema），因此是一个很好的起点。不过它可能比较脆弱，需要精确的 prompt，面对复杂需求时也容易吃力。另一方面，Tool Use 提供更高的可靠性、一致的结果、无缝的 API 集成，以及对 JSON schema 的运行时校验，从而增强控制力。

为简明起见，本文并未演示若干方面。生成结构化响应的其他技术还包括：调用模型时使用内建支持可配置响应格式（如 JSON）的模型，或者借助 [LMQL](https://lmql.ai/docs/language/overview.html) 这类第三方库利用约束解码技术。此外，用 GenAI 生成结构化数据也可能因 JSON 无效、字段缺失或格式错误等问题而颇具挑战。为保持数据完整性并处理意外输出或 API 失败，有效的错误处理、充分的测试与校验都是必需的。

如需试用本文演示的 Bedrock 技术，请按步骤[通过 AWS SDK for Python（Boto3）运行示例 Amazon Bedrock API 请求](https://docs.aws.amazon.com/bedrock/latest/userguide/getting-started-api-ex-python.html)。按用量付费的定价模式意味着你只需为 API 调用付费，因此测试之后几乎无需任何清理。关于最佳实践的更多细节，请参阅 [Bedrock prompt engineering 指南](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-engineering-guidelines.html) 与各模型专属文档，例如 [Anthropic 的最佳实践](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)。

在 API、数据驱动的工作负载以及超越文本对话的丰富用户界面等真实场景中，结构化数据是发挥生成式 AI 价值的关键。今天就开始使用 Amazon Bedrock，释放其在可靠结构化响应方面的潜力。
