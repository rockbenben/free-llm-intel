# 使用 NVIDIA NeMo Switchyard 将编码代理请求路由到 Amazon Bedrock 上的正确模型

Claude Code 和 OpenAI Codex CLI 等编码代理在任务中工作。开发人员请求更改，代理读取文件、编辑代码并运行测试，直到工作完成。一项任务可能需要几个或几十个模型调用。开发人员支付的是任务，而不是一次调用。

仅每个代币的价格并不能告诉您整个任务的成本。总数取决于模型需要多少轮、每轮重播多少历史记录以及任务必须重试或永远无法完成的频率。您为每次尝试付费，包括尝试从未完成的任务。因此，当您在模型之间路由编码代理的请求时，请根据每个已解决任务的成本来判断路由：运行的总成本除以测试通过的运行数量。

[NVIDIA NeMo Switchyard](https://github.com/NVIDIA-NeMo/Switchyard) 是一个开源库，可帮助 AI 代理选择处理每个请求的模型。您定义它可以使用的模型及其遵循的策略。其[LiteLLM集成](https://github.com/NVIDIA-NeMo/Switchyard/blob/21075c6652152dac88a5fbc6b878ca37d7617c1c/examples/litellm/README.md)支持两种策略。阶段路由读取最近的工具活动和请求历史记录中的结果，然后选择两个候选模型之一。从配置的模型中进行随机路由选择，并具有可选的权重，用于流量分割和 A/B 比较。您可以探索的另一个选择是 LiteLLM，它最近还提供了一个本机内置 [Switchyard stage router](https://docs.litellm.ai/blog/switchyard-tool-aware-routing) 作为自动路由器策略。

在本文中，您将使用 AWS 云开发工具包 (AWS CDK) 部署 LiteLLM，这是一种用于大型语言模型 (LLM) 的开源网关，并在您的 AWS 账户中使用 Switchyard 路由插件。 LiteLLM 在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上调用模型。然后，您可以使用示例的基准运行程序来衡量路由模型组和单模型基线组的每个已解决任务的成本，以便您可以根据自己的工作负载评估路由。

> 注意：该示例从 crates.io 安装 switchyard-server 0.3.0 并运行已发布的 LiteLLM v1.102.0 映像。 NVIDIA 将 switchyard-server 0.3.0 记录为演示和评估组件，其配置可能会在不同版本之间发生变化。此示例使用实验性 Switchyard LiteLLM 集成，其配置和 API 可能会因版本而异。这是示例代码，用于非生产用途。与您的安全和法律团队合作，在部署之前满足您组织的安全、监管和合规性要求。在非生产帐户中部署示例并在依赖它之前对其进行测试。

图 1：解决方案架构

请求会经过这些步骤。数字与图表相符。

- 编码代理发送 OpenAI 兼容请求，其中模型字段设置为“switchyard”、Switchyard 路由的 LiteLLM 模型组以及“Authorization”标头中的共享网关密钥。终端节点是您通过 HTTPS 的主机名，在负载均衡器上具有 [AWS Certificate Manager (ACM)](https://aws.amazon.com/certificate-manager/) 证书，并且只有您允许的 IPv4 CIDR 范围才能访问它。通过 [Amazon Route 53](https://aws.amazon.com/route53/) 中的托管区域，Route 53 将主机名解析为负载均衡器。
- [AWS WAF](https://aws.amazon.com/waf/) 使用 IP 信誉、已知错误输入和每个 IP 速率限制规则过滤请求。 [Application Load Balancer](https://aws.amazon.com/elasticloadbalancing/application-load-balancer/) 仅将 `/v1/chat/completions`、`/v1/models` 和 `/health/liveiness` 转发到私有子网中的 ECS 任务，并使用 404 应答所有其他路径。
- 该任务运行一个容器：带有嵌入式 Switchyard 插件的 LiteLLM。 LiteLLM 验证网关密钥并调用插件来选择模型。 Stage 在有能力的模型和低成本高效模型之间进行选择。它读取工具活动并生成请求历史记录，因此代理必须发送完整的对话历史记录。从加权池中随机选择。这两种策略都没有调用法官模型。
- LiteLLM 通过 Amazon Bedrock `Converse` 或 `ConverseStream` API 调用选定的模型，并使用任务的 [AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 角色作为凭证。该调用通过 [Amazon Virtual Private Cloud (Amazon VPC)](https://aws.amazon.com/vpc/) 中的 Amazon Bedrock Runtime 接口终端节点，因此推理流量保留在 AWS 网络上。
- 响应或令牌流通过 LiteLLM 和负载均衡器返回。 `x-litelm-model-name` 响应标头命名了应答的模型。响应主体的“model”字段仍然是“switchyard”。

LiteLLM 侦听容器中的端口 4000，并且是负载均衡器的目标，并且任务的安全组仅允许负载均衡器。路径允许列表使 LiteLLM 管理 UI、API 文档和密钥管理路由无法访问。 [Amazon Elastic Container Registry (Amazon ECR)](https://aws.amazon.com/ecr/) 保存网关映像。 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 生成网关密钥后面的密钥，容器在启动时添加“sk-”前缀。任务定义传递“LITELLM_CONFIG_TEXT”和“SWITCHYARD_CONFIG_TEXT”中的配置文件，启动脚本在启动 LiteLLM 之前将它们写入“/tmp”。日志会保存到一个 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 日志组“/<stack name>/litellm”，该组会将日志保留 30 天，并且 Container Insights 会收集指标。 VPC 跨越两个可用区，一个 NAT 网关为映像拉取和其他 AWS 服务提供出站访问。

该插件支持阶段路由（仅需要两个候选者）和随机路由（至少需要两个候选者）并按权重拆分流量以进行 A/B 测试。分类器支持的策略（例如任务和复合路由）需要此集成不支持的中间模型调用。有关完整目录，请参阅 [Switchyard 路由概述](https://nvidia-nemo.github.io/Switchyard/routing_algorithms/overview/)。

## 演练

您定义模型组、配置阶段、部署和测试网关以及测量成本。首先克隆示例存储库：
```
git clone https://github.com/aws-samples/sample-route-coding-agent-requests-Amazon-Bedrock-nemo-switchyard.git
cd sample-route-coding-agent-requests-Amazon-Bedrock-nemo-switchyard
```
### 步骤 1：在 LiteLLM 中定义模型组

LiteLLM 模型组是一个公共模型名称，其后面有一个或多个部署。该示例将其配置保存在“profiles/”下的部署配置文件中。每个配置文件都将定义模型和网关设置的“litellm.yaml”与控制 Switchyard 如何选择模型的“switchyard.toml”配对。以下“profiles/stage/litellm.yaml”摘录定义了路由的“switchyard”组、两个单模型基线组和插件注册：
```
model_list:
  - model_name: switchyard
    litellm_params:
      model: bedrock/converse/global.anthropic.claude-opus-5-5
      aws_region_name: os.environ/AWS_REGION
  - model_name: switchyard
    litellm_params:
      model: bedrock/converse/nvidia.nemotron-super-3-120b
      aws_region_name: os.environ/AWS_REGION
  # One-model baseline groups, same model strings as the routed candidates.
  - model_name: claude-opus-5-5
    litellm_params:
      model: bedrock/converse/global.anthropic.claude-opus-5-5
      aws_region_name: os.environ/AWS_REGION
  - model_name: nemotron-super-3-120b
    litellm_params:
      model: bedrock/converse/nvidia.nemotron-super-3-120b
      aws_region_name: os.environ/AWS_REGION

# The same object selects a deployment and applies supported request changes.
router_settings:
  plugins:
    - switchyard_gateway.configured.ROUTING_PLUGIN
litellm_settings:
  callbacks:
    - switchyard_gateway.configured.ROUTING_PLUGIN
  drop_params: true
  request_timeout: 600
  num_retries: 2
general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
```
两个候选人共享 `model_name: switchyard`，因此您的客户发送 `"model": "switchyard"` 并且 Switchyard 选择一个候选人。首先列出有能力的模型，然后列出高效的模型，因为 Stage 按此顺序读取角色。

`claude-opus-5-5` 和 `nemotron-super-3-120b` 组是单模型基线。每个模型始终使用自己的模型进行回答，因此您可以将路由组的成本和通过率与同一部署中单独的每个模型进行比较。 Stage 插件单独拒绝没有两个候选者的组，因此映像注册了一个小包装器“switchyard_gateway.configured.ROUTING_PLUGIN”。它将 Switchyard 应用于具有两个或更多唯一候选者的组，并让单一模型组通过。配置注册包装器两次：选择模型并应用 Switchyard 记录的请求更改。

每个模型都使用“bedrock/converse/<id>”，因此每个候选者都会通过 Amazon Bedrock“Converse” API，并且验证会拒绝任何其他路线。 LiteLLM“request_timeout”为 600 秒，与负载均衡器的 10 分钟空闲超时相匹配。

该文件不包含任何凭据。 LiteLLM 从环境中读取网关密钥，任务角色提供 AWS 凭证。切勿在“litellm_params”下添加“aws_access_key_id”、“aws_secret_access_key”或“api_key”等凭证：堆栈以纯文本形式将整个“litellm.yaml”复制到任务定义和 AWS CloudFormation 模板中。

堆栈从此文件中派生任务角色的 Amazon Bedrock 权限。对于全局跨区域推理配置文件，基础模型资源使用“*”区域和尾随“*”，因此它还匹配具有相同前缀的其他模型 ID。在部署之前查看派生策略。

“global.”前缀标记[全球跨区域推理配置文件](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)，Amazon Bedrock 可能会在全球受支持的商业 AWS 区域中处理这些请求。如果处理位置很重要，请改用地理配置文件或区域内模型 ID。对于 Nemotron 3 Super，配置文件使用区域内模型 ID“nvidia.nemotron-super-3-120b”，您可以将其切换为任何模型进行测试。

### 第 2 步：配置 Stage 路由

Switchyard 从“switchyard.toml”读取其算法和设置。默认配置文件“profiles/stage/switchyard.toml”配置 Stage：
```
# Model inventory is in litellm.yaml. This file configures selection behavior.
algorithm = "stage"
# Prefer the efficient candidate when history signals are inconclusive.
picker = "efficient_first"
confidence_threshold = 0.5
# Inspect the three most recent tool results for execution signals.
recent_window = 3
only_on_wrong_signal_escalation = true
```
设置的工作原理如下：

- `picker = "efficient_first"`：当历史信号不确定时，Stage 使用高效模型。新请求尚未有工具结果，因此将发送至 Nemotron 3 Super。
- `confidence_threshold`：阶段得分执行信号的置信度截止值，从 0 到 1。
- `recent_window = 3`：阶段检查三个最新的工具结果。
- `only_on_wrong_signal_escalation = true`：Switchyard 默认值。它控制 Stage 何时添加可选的升级注释，并且此配置文件不设置注释。

Stage 还接受可选的移交注释和每层系统提示（“escalation_note”、“deescalation_note”、“capable_system_prompt”和“efficient_system_prompt”）。示例配置文件没有设置其中任何一个。

对于 A/B 测试，`profiles/random/` 中的随机配置文件使用与 `algorithm = "random"` 和 `weights = [0.5, 0.5]` 相同的模型，按声明顺序每个唯一候选者有一个权重。要部署它，请将“-croutingProfile=random”添加到步骤 3 中的“cdk diff”和“cdk deploy”命令中。

堆栈在合成时一起验证两个文件，并且预检脚本运行相同的检查。要在不调用 AWS 的情况下自行检查配置文件更改，请运行“npm run validate:profile -- stage”。无效的设置会在 LiteLLM 启动时停止它，并且不受支持的消息形状会在推理之前失败。

### 可选：本地运行网关

在部署任何内容之前，您可以在计算机上尝试网关。 Docker Compose 构建相同的映像并读取堆栈部署到 Amazon ECS 的相同配置文件。从存储库根运行：
```
npm ci
cp .env.example .env

export LITELLM_MASTER_KEY="sk-$(openssl rand -hex 24)"
eval "$(aws configure export-credentials --format env)"

ROUTING_PROFILE=stage docker compose up --build --wait
GATEWAY_URL=http://127.0.0.1:4000 ROUTING_PROFILE=stage scripts/smoke-test.sh
```
您导出的密钥优先于“.env”中的占位符，因此 Compose 和冒烟测试使用相同的密钥。 AWS 凭证仅来自您的 shell，绝不会进入“.env”或配置文件中。 Compose 仅​​在“127.0.0.1”上发布网关。本地没有负载均衡器，因此冒烟测试会跳过其封闭路径检查。本地网关仍然呼叫 Amazon Bedrock，并且这些呼叫需要付费。完成后，运行“docker compose down”。

### 步骤 3：部署网关

网关在您拥有的主机名上提供 HTTPS 服务。将“GATEWAY_DOMAIN”设置为该主机名，将“HOSTED_ZONE”设置为包含该主机名的现有 Route 53 公共托管区域。然后，AWS CDK 创建经过 DNS 验证的 ACM 证书和别名记录。从存储库根目录，安装依赖项，运行只读预检检查，然后部署：
```
npm ci

export AWS_REGION=us-east-1
export AWS_DEFAULT_REGION="$AWS_REGION"
eval "$(aws configure export-credentials --format env)"
export CDK_DEFAULT_REGION="$AWS_REGION"
export CDK_DEFAULT_ACCOUNT="$(aws sts get-caller-identity --query Account --output text)"
export ALLOWED_CIDR="$(curl -4 -fsS --connect-timeout 5 --max-time 15 https://checkip.amazonaws.com)/32"
export GATEWAY_DOMAIN=llm-gateway.example.com
export HOSTED_ZONE=example.com

scripts/preflight.sh
npx cdk diff -c allowedCidr="$ALLOWED_CIDR" \
  -c domainName="$GATEWAY_DOMAIN" -c hostedZone="$HOSTED_ZONE"
npx cdk deploy -c allowedCidr="$ALLOWED_CIDR" \
  -c domainName="$GATEWAY_DOMAIN" -c hostedZone="$HOSTED_ZONE"
```
如果您的域的 DNS 不在 Route 53 中，请改用现有的 ACM 证书。将“CERTIFICATE_ARN”设置为部署区域中主机名的 ACM 证书，并在两个命令中将“-cHostedZone="$HOSTED_ZONE"”替换为“-ccertificateArn="$CERTIFICATE_ARN"”。然后，AWS CDK 不会创建任何证书和 DNS 记录。部署后，创建一个 CNAME 记录（或 Route 53 别名），将主机名指向“LoadBalancerDnsName”输出。

所需的“allowedCidr”值限制哪些网络可以到达负载均衡器，并且该命令将其设置为您当前的公共 IPv4 地址。将其保留为您自己的“/32”：共享允许地址（例如办公室 NAT 或 VPN 出口）的每个人都可以到达该端点。如果没有“allowedCidr”、具有世界开放范围（例如“0.0.0.0/0”）或具有 IPv6 范围，堆栈将拒绝进行合成。

预检会检查配置、您的工具和 AWS 访问权限，包括对配置文件中每个模型的访问权限，而无需发出推理请求。 AWS CDK 构建网关映像，将其发布到 Amazon ECR，并部署堆栈。部署打印这些输出：

| **输出** | **它是什么** |
| --- | --- |
|网关地址 |基本 URL。 OpenAI 兼容 API 位于“/v1”下。 |
| MasterKeySecretArn |网关密钥背后的 Secrets Manager 秘密。完整的密钥是“sk-”，后跟秘密值。 |
|主键命令 |打印网关密钥的命令。 |
|烟雾测试命令 |烟雾测试命令，其中填写了堆栈名称、区域和配置文件。
|路由配置文件 |活动路由配置文件，默认为阶段。 |
|集群名称、服务名称 | ECS 集群和服务。关键旋转步骤使用它们。 |
| LoadBalancerDns 名称 |仅适用于certificateArn：指向主机名的名称。 |

始终为客户端提供“https://”URL。端口 80 保持打开状态仅用于重定向到 HTTPS，并且配置为“http://”的客户端在重定向到达时已经以明文形式发送了密钥及其第一个请求。

对于长时间代理响应，负载均衡器空闲超时为 10 分钟。 Web ACL 使用 Amazon IP 信誉列表和已知的不良输入规则组。它还将每个 IP 地址限制为每 5 分钟 2,000 个请求。它省略了代理请求中的源代码触发的跨站点脚本、SQL 注入和正文大小的通用正文规则。 “allowedCidr”范围和网关密钥仍然适用。

**通过普通 HTTP 进行快速测试。** 如果没有 HTTPS 设置，合成器会因错误而停止。对于没有域的简短测试，您可以选择在负载均衡器的 DNS 名称上使用纯 HTTP：
```
npx cdk deploy -c allowedCidr="$ALLOWED_CIDR" -c allowPlainHttp=true
```
使用“allowPlainHttp=true”，AWS CDK 在每次合成堆栈时都会打印一条警告。 “Authorization”标头中的网关密钥、您的提示、代理发送的工具结果和源代码，以及在客户端和负载均衡器之间通过未加密的网络传输的模型响应。仅将选择加入用于对您自己的“/32”中的非敏感代码进行简短测试。然后旋转密钥，完成后运行“cdk destroy”。稍后要将同一堆栈移动到 HTTPS，请使用 HTTPS 设置重新部署它，但不要使用“allowPlainHttp”。

### 步骤 4：测试网关

在用于部署的同一终端中，读取 [AWS CloudFormation](https://aws.amazon.com/cloudformation/) 堆栈输出并构建网关密钥：
```
export STACK_NAME=SwitchyardGateway

output() {
  aws cloudformation describe-stacks --region "$AWS_REGION" --stack-name "$STACK_NAME" \
    --query "Stacks[0].Outputs[?OutputKey=='$1'].OutputValue" --output text
}

export GATEWAY_URL="$(output GatewayUrl)"
export LITELLM_MASTER_KEY="sk-$(aws secretsmanager get-secret-value --region "$AWS_REGION" \
  --secret-id "$(output MasterKeySecretArn)" --query SecretString --output text)"
```
向“switchyard”模型组发送请求：
```
curl -sS -i --connect-timeout 10 --max-time 180 "$GATEWAY_URL/v1/chat/completions" \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"switchyard","messages":[{"role":"user","content":"Reply with the word hello."}],"max_tokens":128}'
```
查找 HTTP 200 和响应。 `x-litellm-model-name` 响应标头将所选模型显示为完整的 LiteLLM 模型字符串。新请求没有可评分的工具结果，因此 Stage 选择高效模型“bedrock/converse/nvidia.nemotron-super-3-120b”。

要检查运行状况、身份验证和路由，请运行冒烟测试：
```
ROUTING_PROFILE="$(output RoutingProfile)" scripts/smoke-test.sh
```
冒烟测试检查运行状况端点，“/ui”等封闭路径会得到负载均衡器自己的 404，没有密钥的请求会得到 401，而“/v1/models”会列出每个模型组。对于 Stage，它检查普通请求是否选择有效模型，以及记录的重复失败历史记录是否升级为有能力的模型。然后它向每个基线组发送一个请求。该请求和冒烟测试会拨打可计费的 Amazon Bedrock 电话。

要尝试您自己的代理，请使用“$GATEWAY_URL/v1”作为其与 OpenAI 兼容的基本 URL，使用网关密钥作为其 API 密钥，并使用“switchyard”作为模型。 Stage 需要每个请求的完整支持的请求历史记录。上游适配器支持文本消息、函数工具调用和文本工具结果，不支持的消息形状在推理之前会失败。负载均衡器转发聊天完成路径，但不转发 OpenAI 响应或人性消息路径。使用这些 API 的客户端会收到 404 错误，直到您添加路径、针对本地容器进行测试并重新部署。

### 步骤 5：衡量每个已解决任务的成本

该示例的编码运行程序“bench/run.py”让小型编码代理列出并读取文件、替换源文件并通过网关运行提供的单元测试。当任务的测试最终通过时（默认情况下在六个模型轮次内），任务就得到解决。列出任务并从路由组上的“slugify”开始：
```
python3 bench/run.py --list-tasks
python3 bench/run.py --tasks slugify --model switchyard --max-turns 6
```
终端显示任务、所选模型、工具操作、测试结果和最终代码差异。每次运行都会将其起始文件、最终工作区、脚本、补丁和结果保存在“bench/results/”下。

| **任务** | **代理人必须做什么** |
| --- | --- |
| slugify | slugify修复一个构建 URL slug 的短函数。 |
|罗马 |编写一个将整数转换为罗马数字的函数。 |
|计算 |编写一个不带“eval”、具有优先级、幂运算符、函数和错误处理的表达式解析器。 |
| lru_ttl |编写一个线程安全的最近最少使用 (LRU) 缓存，其中包含每个条目的到期时间和精确计数器。 |

为了给算术解析器任务空间来运行测试和尝试修复，请提高轮数限制：
```
python3 bench/run.py --tasks calc --model switchyard --max-turns 12
```
运行后，运行程序会为每个模型组打印一行，其中包含 RUNS、SOLVED、ERRORS、COST/TASK 和 COST/SOLVED 列。每个已解决任务的成本是组中所有运行的估计成本除以测试通过的运行的结果。跑步者使用“bench/run.py”中的价格表，在“x-litellm-model-name”标头中对模型的每一轮进行定价，并在响应中使用令牌。具有缓存输入的回合、没有 PRICES 条目的模型或没有标头或令牌计数的响应保持未定价，而不是计数为零。将模型添加到配置文件时添加价格条目，并检查 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/) 了解当前价格。对两个任务的几次运行演示了工作流程。它们不足以得出有关成本或质量的结论。

当某个组的任何运行未定价时，该组会显示 n/a 并给出原因，而当没有运行得到解决时，COST/SOLVED 将显示“-”。要查看成本的去向，请检查轮次：终端打印服务于每个轮次的模型，并且“bench/results/”下的记录会记录它。

为了比较整个对话，“bench/multiturn.py”对每个编码任务运行一个代理循环，第一个提示中的项目文件和每次编辑后反馈的测试输出。它还运行四个脚本化的聊天，共七轮，将简单的轮流与设计、调试和代码编写轮流交替进行，并且每轮都会重播完整的历史记录。使用简单的检查（预期文本、字数限制、项目符号或针对返回函数的断言）记录检查是否通过。设计回答不评分。
```
python3 bench/multiturn.py --tasks slugify --scripts backend api --max-spend 2
```
`--max-conv-cost` 选项（默认 1 美元）限制每个对话，而 `--max-spend` 则阻止跑步者开始新的对话。摘要显示了每个模型组通过的编码对话、通过的聊天检查以及每个编码对话、每个聊天和总计的估计成本。

运行程序在您的计算机上执行模型编写的 Python。运行测试的子进程在其环境中没有凭据，但它不是操作系统沙箱：代码可以读取用户可以读取并可以访问网络的任何文件。使用磁盘上没有长期 AWS 凭证的一次性开发环境，并保护“bench/results/”下的文件，其中包含提示、模型响应、工具输出和生成的代码。

## 解释你的结果

该示例的任务很小且具有说明性。要确定路由是否适合您的工作负载，请用代表您自己的代码库的任务替换或扩展它们，并在阅读运行器的输出时记住以下几点。

- **从已解决开始，然后阅读成本/已解决 –** 解决较少任务的小组可以显示较低的成本/任务，但每个已解决任务的成本仍然较高，因为失败的运行会增加成本而不增加已解决的任务。仅在比较了每个组解决的任务数量后，才将路由组的成本/已解决的成本与每个基准组的成本/已解决的成本进行比较。
- **单独查看困难任务 –** 总数可以隐藏驱动结果的单个任务。按任务细分结果。阶段是根据历史中的失败来决定的，因此它不能提前将艰巨的任务交给有能力的候选人。升级的转弯还会重播整个失败的尝试，这可能会使恢复比在有能力的候选者上开始运行更昂贵。如果一些困难任务占据了您的成本，请考虑将它们路由到专门的模型组，或者选择一个能够解决更多问题的高效候选模型。
- **运行足够的重复次数 –** 模型输出因运行而异。由于每组只有几次运行，一两个已解决任务的差异可能会产生噪音。增加“--repeats”直到您关心的差异稳定，并在对差距采取行动之前应用统计测试，例如费舍尔精确测试解决率。
- **考虑轮次限制 –** 较低的“--max-turns”值会惩罚在编辑之前进行探索的模型，因为它会留下更少的轮次来修复失败的编辑。设置限制以匹配代理在实践中的运行方式。
- **考虑输出上限 –** 如果一个组的回复达到“max_tokens”，则测量的成本是下限，并且缩短的回复也会缩短稍后重放的历史记录。在比较聊天费用之前，请检查文字记录中是否有被截断的回复。
- **将成本视为估算 –** 跑步者根据代币使用情况和价格表估算成本，而不是根据您的账单。提示缓存、批量推理和定价更改都会影响您的实际成本。通过 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/) 以及您的 AWS 成本和使用情况报告进行确认。
- **测试您计划运行的设置 –** 结果仅适用于您测量的模型、配置文件设置和任务。如果您更改候选人、阶段设置或切换到随机配置文件，请重新测量。

使用这些读数为每个工作负载在三个选项中进行选择：路由组、单模型组或具有不同候选项或设置的配置文件。当您更改模型、提示或代理行为时，重新运行相同的测量。

## 清理

为了避免持续产生费用，请删除堆栈。 AWS CDK 需要一个“allowedCidr”值来合成应用程序，但该值在这里并不重要：
```
npx cdk destroy -c allowedCidr=203.0.113.0/24
```
CloudFormation 会删除主密钥，并且没有恢复窗口，因此如果需要，请先复制密钥。网关映像保留在 Amazon ECR 中的 AWS CDK 引导存储库中。

## 结论

在这篇文章中，我们展示了如何在 AWS 上使用 NVIDIA NeMo Switchyard 路由插件部署 LiteLLM，在 Amazon Bedrock 上跨模型配置阶段和随机路由，以及测量路由模型组和单模型基线的每个已解决任务的成本。由于代理任务的总成本取决于轮次、历史记录和重试，因此每个代币的价格本身并不能作为可靠的指导。测量您自己的任务中每个已解决任务的成本可为您提供选择配置的证据。
