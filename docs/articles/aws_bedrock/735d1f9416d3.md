# Amazon SageMaker AI 现在能检测推理端点上的延迟漂移、空闲 GPU 与漏掉的优化

每个推理端点在上线那天都是调优过的：团队会挑选适合该模型和上线时流量的实例类型、服务配置与扩缩容设置。端点跑得顺畅，团队自然就转向下一个优先级。可工作负载很少一成不变。流量模式在变，prompt 变长，vLLM 这类服务引擎发布新版本，SageMaker 推理不断推出新的优化手段，新的微调 checkpoint 也会改变模型所需的资源。时间一长，一个调优良好的端点就悄悄漂移了：延迟和首 token 延迟一点点往上走；某个从来就谈不上理想的配置持续错过可得的性能收益；为一份始终没出现的需求预置的 GPU，一周接一周地空转。因为没有任何东西故障，也就没有告警响起，这种漂移一直无人察觉，直到用户感受到，或者账单体现出来。

[Amazon SageMaker AI](https://aws.amazon.com/sagemaker/ai/) 现在会监控你的生成式 AI 推理端点，并借助 [Amazon SageMaker Studio](https://aws.amazon.com/sagemaker/ai/studio/) 中带 Agentic 体验的[生成式 AI 优化推理建议](https://aws.amazon.com/blogs/machine-learning/amazon-sagemaker-ai-now-supports-optimized-generative-ai-inference-recommendations/)功能，告诉你哪项改动可以提升性能或降低成本。对于使用 vLLM 服务容器和 GPU 实例的 SageMaker AI 推理端点，监控默认开启，无需任何设置，也可以选择让端点退出监控。SageMaker AI 只看运营信号：延迟、GPU 利用率和端点的服务配置，不读取你的请求或响应。基于这些信号，它会给出三类发现：

- **延迟漂移：** 中位数（p50）端到端延迟或首 token 延迟出现周环比上升。
- **未使用的容量：** 你付了钱、却大部分时间闲置的 GPU。
- **配置缺口：** 服务容器缺少较新的性能改进或安全补丁；或者模型支持的某项优化——例如推测解码或 GPU 内核调优——端点没有启用。

SageMaker AI 通过 AWS Health 发送发现，每个端点一条通知，覆盖该端点的全部发现。收到通知后，你可以在一个地方处理。它会打开 Amazon SageMaker Studio 中的 SageMaker AI agentic 体验，端点及其近期流量已经填好。在那里运行推理建议，就能把当前配置与备选方案一起做基准测试，并在响应时间、吞吐量和每百万 token 成本上并排比较，把主观判断变成有数据支撑的决策。基准测试在独立的计算资源上运行，在你选择应用结果之前，端点不会有任何变化。

本文介绍 SageMaker AI 如何监控你的端点，以及如何解读它通过 AWS Health 发出的通知；随后演示如何从一条通知走到 SageMaker Studio 中一个经过基准测试的决策。我们会走一遍三个示例场景，说明如何安全地应用或忽略建议，并解释如何让端点退出监控。

## 解决方案概述

SageMaker AI 推理建议遵循四步循环：观察、通知、建议、决策。每一步都让你保持掌控，没有你的明确操作，生产端点不会被改动。

- **观察 –** 对符合条件的端点，延迟和容量使用情况的监控默认开启。它不读取你的请求或响应，也不产生额外的 GPU 成本。
- **通知 –** 当出现值得处理的情况时，你会在 AWS Health 中收到通俗易懂的通知，同时还有邮件，说明观察到了什么、为什么重要、建议的下一步是什么。
- **建议（需主动启用）–** 一次点击即可打开 SageMaker Studio 中的 SageMaker AI agentic 体验，端点及其观测到的流量已经预填，方便你在独立计算资源上对备选方案做基准测试。
- **决策 –** 并排比较响应时间、吞吐量和成本。在你应用结果之前，生产环境不会改变。

该功能会产生几种发现。下表汇总了每种发现的触发条件，以及你选择做基准测试时会测什么。

| **发现** | **触发条件** | **基准测试测什么** |
| --- | --- | --- |
| 延迟漂移 | 响应时间相对于该端点的周环比趋势发生变化 | 张量并行设置，以及备选实例类型或规格 |
| GPU 利用率不足 | GPU 利用率在观察窗口内持续远低于容量 | 在观测到的峰值流量下更便宜的实例类型和更小的规格 |
| 未启用推测解码 | 模型和容器都支持，但处于关闭状态（基于配置判断） | 当前配置与启用推测解码后的对比 |
| 服务容器 | 端点的服务容器有更新版本，包含性能改进以及针对关键和高危常见漏洞与暴露（CVE）的安全补丁 | 当前容器与更新后容器的对比 |
| 未调优的 GPU 内核 | 内核配置未针对模型和硬件调优 | 默认配置与调优后内核的对比 |

## 前提条件

监控本身无需设置，默认开启。以下前提条件适用于你决定对发现采取行动——运行基准测试，并可选地应用改动——的时候：

- 能访问 AWS Health 和 AWS User Notifications 控制台。
- 有一个 SageMaker Studio 域，并具备运行推理建议作业和更新端点所需的 AWS Identity and Access Management（IAM）权限。
- 要测试的基准测试实例有足够的服务配额。

**成本说明：** 监控不产生 GPU 成本。基准测试按标准 SageMaker AI 费用计费，如果你有机器学习（ML）预留，则使用预留。

## 理解发现通知

你会在控制台的 AWS Health 中以及通过邮件收到通知，每条通知结构相同，扫一眼就能读完：

- **端点：** 该发现适用于哪个端点。
- **我们注意到：** 平实陈述的观测结果，估计值会明确标注为估计值。
- **为什么重要：** 对延迟、容量或成本的影响。
- **建议操作：** 一次点击即可进入 SageMaker Studio 中的 agentic 体验进行调查。

通知只报告观测结果并标注估计值，此时还没有跑过任何基准测试。一条有代表性的通知如下：

| 主题：[可能需要操作] 针对你的端点的 SageMaker AI 推理改进 SageMaker AI 默认跟踪你推理端点的延迟和容量使用情况，并在其中一个端点上发现了改进空间。它不会读取你的请求或响应。*我们注意到：过去一周，该端点的首 token 延迟相比前一周有所增加。* 建议操作：打开 SageMaker Studio，在独立计算资源上对备选方案做基准测试。你的生产端点不会被改动。 |
| --- |

**频率**：每个端点收到一条通知，覆盖适用的发现。同一时间每个端点最多一条通知，涵盖其全部发现，SageMaker AI 也会限制一个账户同时收到的通知数量。通知与 AWS 区域绑定，因此你需要登录到端点所在区域才能看到它的发现。

## 演练：从通知到决策

本节回顾几个端点优化场景，它们都会触发发现上报。

### 场景 1：抓住周环比延迟回退

一个团队在单个 SageMaker AI 端点上运行聊天助手。为了提高答案质量，他们加入了检索，于是每个请求都带上好几页检索到的 context，prompt 也长了很多。系统没有出故障，他们设置的告警也没有触发，但响应开始变慢。

SageMaker AI 会把该端点的中位数（p50）首 token 延迟和中位数端到端延迟与前一周比较。只要其中任一项在一周内上升得足够多，它就会标记这一变化。由于比较对象是该端点自身的历史，团队不需要事先设定阈值。

- **通知：** AWS Health 报告首 token 延迟相比前一周有所上升。
- **Studio 会话：** 一次点击打开 agentic 体验，端点及其观测到的流量已经预填。
- **基准测试：** 会话在独立计算资源上测试张量并行设置以及其他实例类型或规格。
- **决策：** 团队比较延迟、吞吐量和成本，然后把胜出的配置应用到一个变体上。

### 场景 2：开启一项你的流量能受益的优化

一个平台团队在 SageMaker AI 端点上托管内部的代码补全模型。他们用默认服务设置部署，之后就没再回头看过。模型和服务容器都支持推测解码——一种让响应更快的技术——但没有启用。SageMaker AI 把这标记为一个机会。它是否真能带来帮助，取决于端点的流量，比如有多少请求并发、prompt 和响应有多长。通知会建议运行推理建议，用端点近期的流量对推测解码做基准测试，看它是否值得开启。

- **通知：** AWS Health 报告一项旨在加快响应的技术已被支持但未启用。
- **Studio 会话：** agentic 体验打开，端点配置已经载入。
- **基准测试：** 会话把当前配置与启用推测解码后的配置作比较。峰值流量下的结果可能与低谷时段不同。
- **决策：** 如果增益在真正重要的流量下依然成立，团队就应用它；否则保留当前配置。

### 场景 3：把利用率不足的 GPU 调到合适规格

一个摘要端点按某次发布的预期规模配置，但实际吸引到的受众只有计划的一小部分，于是它的 GPU 一周里大部分时间都在闲置。这个场景也说明，有时候正确的决策可能是什么都不改。

- **通知：** AWS Health 报告该端点付费购买的 GPU 容量大部分未被使用。
- **Studio 会话：** agentic 体验打开，带上端点及其观测到的峰值流量。
- **基准测试：** 会话在观测到的峰值流量下测试更便宜的实例类型和更小的规格。
- **决策：** 团队权衡每月节省与计划增长所需的余量，也可能决定维持当前规格。

## 应用或忽略建议

整个过程由你掌控，不会自动部署任何东西。当你在通知的推荐操作中选择 **Open in SageMaker AI** 时，[Amazon SageMaker Studio](https://aws.amazon.com/sagemaker/ai/studio/) 会打开一个 JupyterLab 空间，并显示即将在 agentic 聊天中运行的 prompt。以下截图展示的是一个同时运行着较旧 vLLM 服务容器的端点，其延迟漂移发现对应的 prompt：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ml-22416-edit1.png)

当你选择 **Run** 时，agentic 体验会在 SageMaker Studio 的 JupyterLab 空间里以聊天面板形式打开。它会用平实的语言总结这条发现，重述你让它做的事，并在采取任何行动前与你确认。以下截图中，agent 正在总结发现并请求继续：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ml-22416-edit2.png)

你确认之后，agent 会生成一个 notebook，为该端点创建推理建议作业。notebook 使用 SageMaker Python SDK，从端点获取模型、从指标获取流量画像，并用 AWS Health 事件给作业打标签，方便你把结果追溯到那条发现。每个步骤都是独立的 notebook 单元格，运行前可以查看或修改。

以下截图展示了记录作业详情、并在三种候选实例类型上启动建议作业的 notebook 单元格。

作业完成后，你可以把当前配置与备选方案在响应时间、吞吐量和成本上做比较。当你准备就基准测试结果采取行动时，我们建议采用这样的安全发布方式：

- 应用前先审查拟议的改动，包括配置差异以及基准测试得到的延迟、吞吐量和成本。
- 先应用到一个生产变体，并保留当前配置以便回滚。
- 暂缓或忽略一条发现是正常结果。通知会留在你的 AWS Health 事件历史中。

## 管理监控与通知

你可以管理监控方式以及通知方式：

- 在 AWS User Notifications 控制台中管理你如何接收通知。
- 可选地安排周期性建议，例如每月一次。

**收集与不收集的内容：** 监控读取的是端点级别的聚合延迟与容量遥测，不读取你的请求或响应内容，也不产生 GPU 成本。

**退出监控：** 如果你不希望 SageMaker AI 监控某个端点，请在模型的容器上设置 `OPT_OUT_TRACKING` 环境变量，值可自选。你在调用 `CreateModel` 时于 `Environment` 映射中设置它，可以设在 `PrimaryContainer` 上，也可以设在模型中的其他容器上。

如果端点上的某个容器带了这个变量，SageMaker AI 就不会为该端点收集任何监控遥测，包括引擎指标、GPU 指标和启动配置详情。因此它也不会为该端点发送任何通知。

## 结论

随着 SageMaker AI 推理建议开始自动监控你的端点，优化从某个时间点的快照变成了一条持续的信号。

你的端点会不断告诉你：它何时发生了漂移、何时错过了一项改进、何时在为闲置容量付费。一次点击，就能带你进入一个由你掌控、经过基准测试的并排决策。
