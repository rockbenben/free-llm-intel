# Amazon SageMaker AI 现可检测推理端点的延迟漂移、闲置 GPU 与错失的优化机会

每个推理端点在投入生产的那一天都是调优良好的。团队会选择适合模型及其启动时流量的实例类型、服务配置和扩缩容设置。端点运行顺畅后，他们自然会转向下一个优先事项。然而，工作负载很少一成不变。流量模式会演变，提示词会变长，vLLM 等服务引擎会发布新版本，SageMaker 推理会发展出新的优化技术，新的微调检查点会改变模型所需的资源。随着时间推移，一个曾经调优良好的端点会悄然漂移。延迟和首 token 延迟缓慢上升。一个从未真正理想的配置持续错失可用的性能收益。为从未出现的需求而预置的 GPU 一周又一周地闲置。由于没有任何故障发生，不会有告警响起，这种漂移也就无人察觉，直到用户感受到它，或者账单反映出它。

[Amazon SageMaker AI](https://aws.amazon.com/sagemaker/ai/) 现在会监控你的生成式 AI 推理端点，并通过 [Amazon SageMaker Studio](https://aws.amazon.com/sagemaker/ai/studio/) 中带有 Agentic 体验的[生成式 AI 优化推理建议](https://aws.amazon.com/blogs/machine-learning/amazon-sagemaker-ai-now-supports-optimized-generative-ai-inference-recommendations/)功能，告诉你何时某项变更可以提升性能或降低成本。对于使用 vLLM 服务容器和 GPU 实例的 SageMaker AI 推理端点，监控默认开启，无需任何设置，你也可以选择退出对端点的监控。SageMaker AI 仅查看运营信号：延迟、GPU 利用率和端点的服务配置。它不会读取你的请求或响应。基于这些信号，它会呈现三类发现：

- **延迟漂移：** 中位数（p50）端到端延迟或首 token 延迟出现周环比上升。
- **未使用的容量：** 你付费但大部分时间闲置的 GPU。
- **配置缺口：** 服务容器缺少较新的性能改进或安全补丁，或者模型支持但端点未使用的优化，例如推测解码或 GPU 内核调优。

SageMaker AI 通过 AWS Health 发送发现，每个端点一条通知，涵盖该端点的所有发现。收到通知后，你可以在一个地方采取行动。它会在 Amazon SageMaker Studio 中打开 SageMaker AI 的 agentic 体验，并已填入该端点及其近期流量。在那里，你可以运行推理建议，将当前配置与备选方案进行基准测试，并在响应时间、吞吐量和每百万 token 成本方面并排比较。这将主观判断转变为有数据支持的决策。基准测试在独立的计算资源上运行，在你选择应用结果之前，端点不会有任何变化。

在这篇博文中，我们展示 SageMaker AI 如何监控你的端点，以及如何解读它通过 AWS Health 发送的通知。然后我们展示如何从通知转到 SageMaker Studio 中经过基准测试的决策。我们逐一介绍三个示例场景，展示如何安全地应用或忽略建议，并说明如何让端点退出监控。

## 解决方案概述

SageMaker AI 推理建议遵循四步循环：观察、通知、建议和决策。每一步的设计都让你保持掌控，生产端点不会在没有你明确操作的情况下被更改。

- **观察 –** 对于符合条件的端点，延迟和容量使用情况的监控默认开启。它不会读取你的请求或响应，也不会产生额外的 GPU 成本。
- **通知 –** 当有值得采取行动的事项时，你会在 AWS Health 中收到通俗语言的通知，外加电子邮件，说明观察到了什么、为什么重要以及推荐的下一步。
- **建议（需主动启用）–** 一次选择即可打开 SageMaker Studio 中的 SageMaker AI agentic 体验，预填端点及其观察到的流量，以便你在独立计算资源上对备选方案进行基准测试。
- **决策 –** 并排比较响应时间、吞吐量和成本。在你应用结果之前，生产环境不会发生变化。

该功能会产生几种类型的发现。下表总结了每种发现的触发条件，以及当你选择进行基准测试时会测试什么。

| **发现** | **触发条件** | **基准测试内容** |
| --- | --- | --- |
| 延迟漂移 | 响应时间相对于端点的周环比趋势发生变化 | 张量并行设置以及备选实例类型或规格 |
| GPU 利用率不足 | GPU 利用率在观察窗口内持续远低于容量 | 在观察到的峰值流量下更便宜的实例类型和更小的规格 |
| 未启用推测解码 | 模型和容器支持，但未开启（基于配置） | 当前配置与启用推测解码后的对比 |
| 服务容器 | 端点的服务容器有更新版本，包含性能改进和针对关键及高危常见漏洞和暴露（CVE）的安全补丁 | 当前版本与更新后容器的对比 |
| 未调优的 GPU 内核 | 内核配置未针对模型和硬件进行调优 | 默认配置与调优后内核的对比 |

## 前提条件

监控本身无需设置，默认开启。以下前提条件适用于你选择通过运行基准测试并对变更进行可选应用来对发现采取行动时：

- 访问 AWS Health 和 AWS User Notifications 控制台。
- 一个 SageMaker Studio 域，以及运行推理建议任务和更新端点的 AWS Identity and Access Management（IAM）权限。
- 要测试的基准测试实例有足够的服务配额。

**成本说明：** 监控不产生 GPU 成本。基准测试按标准 SageMaker AI 费用计费，或者使用你已有的机器学习（ML）预留。

## 了解发现通知

你会在控制台的 AWS Health 中以及通过电子邮件收到通知，每条通知都遵循相同的结构，因此可以快速浏览：

- **端点：** 该发现适用于哪个端点。
- **我们注意到：** 以平实语言陈述的观察结果，估计值会明确标注为估计值。
- **为什么重要：** 对延迟、容量或成本的影响。
- **建议操作：** 一次选择即可进入 SageMaker Studio 中的 agentic 体验进行调查。

通知报告观察结果并标注估计值。此时尚未运行任何基准测试。一条代表性通知如下：

| 主题：[可能需要操作] 针对你的端点的 SageMaker AI 推理改进 SageMaker AI 默认跟踪推理端点的延迟和容量使用情况，并发现其中一个端点有改进空间。它不会读取你的请求或响应。*我们注意到：过去一周，该端点的首 token 延迟相比前一周有所增加。* 建议操作：打开 SageMaker Studio，在独立计算资源上对备选方案进行基准测试。你的生产端点不会被更改。 |
| --- |

**频率**：每个端点收到一条涵盖适用发现的通知。你一次最多收到每个端点一条通知，涵盖其所有发现，SageMaker AI 会限制一个账户同时收到的通知数量。通知特定于 AWS 区域，因此当你登录到端点所在区域时才能看到该端点的发现。

## 演练：从通知到决策

在本节中，我们回顾几个端点优化场景，这些场景会触发发现报告。

### 场景 1：捕捉周环比延迟回退

一个团队在单个 SageMaker AI 端点上运行聊天助手。他们添加了检索以提高答案质量，因此现在每个请求都携带数页检索上下文，提示词变得长得多。没有任何故障，他们设置的告警也没有触发，但响应开始变慢。

SageMaker AI 将端点的中位数（p50）首 token 延迟和中位数端到端延迟与前一周进行比较。当其中任一项在一周内上升足够多时，它会标记该变化。由于比较是针对端点自身的历史数据，团队无需预先设置阈值。

- **通知：** AWS Health 报告首 token 延迟相比前一周有所增加。
- **Studio 会话：** 一次选择即可打开 agentic 体验，预填端点和观察到的流量。
- **基准测试：** 会话在独立计算资源上测试张量并行设置以及其他实例类型或规格。
- **决策：** 团队比较延迟、吞吐量和成本，然后将胜出的配置应用到一个变体。

### 场景 2：开启你的流量能受益的优化

一个平台团队在 SageMaker AI 端点上托管内部代码补全模型。他们使用默认服务设置部署，之后从未重新审视。模型和服务容器支持推测解码（一种加快响应的技术），但未启用。SageMaker AI 将其标记为一个机会。它是否有帮助取决于端点的流量，例如有多少请求并发运行、提示词和响应有多长。通知建议运行推理建议，它会根据端点近期流量对推测解码进行基准测试，并显示是否值得开启。

- **通知：** AWS Health 报告一种旨在加快响应的技术受支持但未启用。
- **Studio 会话：** agentic 体验打开，已加载端点配置。
- **基准测试：** 会话将当前配置与启用推测解码后的配置进行比较。峰值流量下的结果可能与低谷流量下不同。
- **决策：** 如果增益在重要流量下保持不变，团队就应用它。否则，他们保持当前配置。

通知解释说，推测解码可以加快响应，基准测试会根据端点近期流量比较启用和不启用时的响应时间。

### 场景 3：调整利用率不足的 GPU 规格

一个摘要端点是为一次发布而配置的，但实际吸引的受众只是计划的一小部分，因此其 GPU 大部分时间闲置了一周。这个场景也展示了一种情况：正确的决策可能是完全不改变。

- **通知：** AWS Health 报告端点为其付费的 GPU 容量大部分未被使用。
- **Studio 会话：** agentic 体验打开，包含端点及其观察到的峰值流量。
- **基准测试：** 会话在观察到的峰值流量下测试更便宜的实例类型和更小的规格。
- **决策：** 团队权衡每月节省与计划增长所需的余量，可能决定保持当前规格。

## 应用或忽略建议

整个过程由你掌控，不会自动部署任何内容。当你从通知的推荐操作中选择 **Open** in SageMaker AI 时，[Amazon SageMaker Studio](https://aws.amazon.com/sagemaker/ai/studio/) 会打开一个 JupyterLab 空间，并显示将在 agentic 聊天中运行的提示词。以下截图显示了针对一个同时运行较旧 vLLM 服务容器的端点的延迟漂移发现的提示词：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ml-22416-edit1.png)

当你选择 **Run** 时，agentic 体验会在 SageMaker Studio 中 JupyterLab 空间的聊天面板中打开。它用平实语言总结发现，重述你要求它做的事情，并在采取任何行动之前与你确认。以下截图显示了 agent 总结发现并请求继续：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ml-22416-edit2.png)

在你确认后，agent 会生成一个 notebook，为端点创建推理建议任务。该 notebook 使用 SageMaker Python SDK，从端点获取模型，从指标获取流量概况，并用 AWS Health 事件标记任务，以便你可以将结果追溯到该发现。每个步骤都是单独的 notebook 单元格，因此你可以在运行前查看或编辑它。

以下截图显示了记录任务详情并在三种候选实例类型上启动建议任务的 notebook 单元格。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ml-22416-edit3.png)

任务完成后，你可以将当前配置与备选方案在响应时间、吞吐量和成本方面进行比较。当你准备好对基准测试结果采取行动时，我们推荐一种安全的发布模式：

- 在应用之前审查提议的变更，包括配置差异以及基准测试的延迟、吞吐量和成本。
- 先应用到一个生产变体，并保留当前配置以便回滚。
- 暂缓或忽略发现是正常的结果。通知会保留在你的 AWS Health 事件历史中。

## 管理监控和通知

你可以管理监控以及通知方式：

- 在 AWS User Notifications 控制台中管理你接收通知的方式。
- 可选地，安排定期建议，例如每月一次。

**收集与不收集的内容：** 监控在端点级别读取聚合的延迟和容量遥测数据。它不会读取你的请求或响应内容，也不会产生 GPU 成本。

**退出监控：** 如果你不希望 SageMaker AI 监控某个端点，请在模型的容器上设置 `OPT_OUT_TRACKING` 环境变量，值可自选。你在调用 `CreateModel` 时在 `Environment` 映射中设置它，可以设置在 `PrimaryContainer` 上，也可以设置在模型中的其他容器上。

如果端点上的某个容器带有此变量，SageMaker AI 不会为该端点收集任何监控遥测数据，包括引擎指标、GPU 指标和启动配置详情。因此，它不会为该端点发送任何通知。

## 结论

随着 SageMaker AI 推理建议现在自动监控你的端点，优化从时间点快照转变为持续的信号。
