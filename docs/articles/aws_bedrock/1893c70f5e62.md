# 使用 Amazon Bedrock AgentCore 与 Strands Agents 集成构建长时间运行的 MCP server

AI agent 正从单纯的聊天界面迅速演变为能够处理复杂、耗时任务的精密自主执行者。随着各组织部署 agent 来训练[机器学习](https://aws.amazon.com/ai/machine-learning/) (ML) 模型、处理大型数据集并运行长时间仿真，[Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro) (MCP) 已成为 agent 与 server 集成的标准。但一个关键挑战依然存在：这些操作可能需要数分钟甚至数小时才能完成，远远超出典型的会话时间范围。通过使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 和 [Strands Agents](https://strandsagents.com/latest/) 实现持久化状态管理，你可以在生产环境中实现无缝的跨会话任务执行。想象一下：你的 AI agent 启动了一个耗时数小时的数据处理作业，用户合上了笔记本电脑，数天后用户回来时系统无缝取回已完成的结果——任务进度、结果和错误全都可见。这种能力把 AI agent 从对话式助手转变为能够处理企业级运营的可靠自主执行者。没有这些架构模式，当连接意外终止时，你会遇到超时错误、资源利用效率低下以及潜在的数据丢失。

本文为你提供一套实现这一目标的完整方法。首先，我们介绍一种 context message 策略，在长时间操作期间保持 server 与 client 之间的持续通信。接下来，我们构建一个异步任务管理框架，让你的 AI agent 能够启动长时间运行的流程而不阻塞其他操作。最后，我们演示如何把这些策略与 Amazon Bedrock AgentCore 和 Strands Agents 结合起来，构建可用于生产的 AI agent，可靠地处理复杂、耗时的操作。

## 处理长时间运行任务的常见方法

为长时间运行的任务设计 MCP server 时，你会面临一个根本性的架构抉择：server 应该保持活动连接并提供实时更新，还是应该把任务执行与初始请求解耦？这一选择引出两种截然不同的方法：**context messaging** 和** 异步任务管理**。

### 使用 context messaging

context messaging 方法在任务执行期间保持 MCP server 与 client 之间的持续通信。做法是使用 MCP 内置的 context 对象向 client 定期发送通知。这种方法最适合任务通常在 10–15 分钟内完成且网络连通性稳定的场景。context messaging 方法有以下优势：

- 实现简单
- 无需额外的轮询逻辑
- client 实现简单
- 开销极小

### 使用异步任务管理

异步任务管理方法把任务启动与执行、结果取回分离。MCP tool 执行后立即返回一条任务启动消息，同时在后台执行任务。这种方法特别适合要求苛刻的企业场景：任务可能运行数小时，用户需要灵活断开并重新连接，而系统可靠性至关重要。异步任务管理方法有这些优势：

- 真正的 fire-and-forget 操作
- client 可以安全断开，任务继续处理
- 通过持久化存储防止数据丢失
- 支持长时间运行的操作（数小时）
- 抵御网络中断的韧性
- 异步工作流

## Context messaging

让我们先探讨 context messaging 方法，它为处理时长适中的操作提供了直接方案，同时保持连接活动。这种方法直接建立在 MCP 已有能力之上，只需极少量的额外基础设施，是延长 agent 处理时间限制的绝佳起点。假设你为一个 AI agent 构建了 MCP server，帮助数据科学家训练 ML 模型。当用户要求 agent 训练一个复杂模型时，底层流程可能需要 10–15 分钟——远远超过大多数环境中典型的 30 秒到 2 分钟 HTTP 超时限制。没有合适的策略，连接会断开，操作会失败，用户只会感到沮丧。在用于 MCP client 实现的 Streamable HTTP 传输中，这些超时限制尤其棘手。当任务执行超过超时限制时，连接中止，agent 的工作流被打断。这正是 context messaging 派上用场的地方。下图展示了实现 context messaging 方法时的工作流。context messaging 使用 MCP 内置的 context 对象，从 server 向 MCP client 定期发送信号，在较长的操作期间有效地保持连接活跃。你可以把它想象成发送"心跳"消息，防止连接超时。

下面是实现 context messaging 的代码示例：

```
from mcp.server.fastmcp import Context, FastMCP
import asyncio

mcp = FastMCP(host="0.0.0.0", stateless_http=True)

@mcp.tool()
async def model_training(model_name: str, epochs: int, ctx: Context) -> str:
    """Execute a task with progress updates."""

    for i in range(epochs):
        # Simulate long running time training work
        progress = (i + 1) / epochs
        await asyncio.sleep(5)
        await ctx.report_progress(
            progress=progress,
            total=1.0,
            message=f"Step {i + 1}/{epochs}",
        )

    return f"{model_name} training completed. The model artifact is stored in s3://templocation/model.pickle . The model training score is 0.87, validation score is 0.82."

if __name__ == "__main__":
    mcp.run(transport="streamable-http")
```

这里的关键要素是 tool 定义中的 `Context` 参数。当你包含一个带 `Context` 类型标注的参数时，FastMCP 会自动注入该对象，让你能使用 `ctx.info()` 和 `ctx.report_progress()` 等方法。这些方法会向已连接的 client 发送消息，而不会终止 tool 的执行。

训练循环中的 `report_progress()` 调用就是这些关键的心跳消息，确保 MCP 连接在整个较长的处理期间保持活动。

在许多真实场景中，精确进度并不容易量化——例如处理不可预测的数据集或发起外部 API 调用时。在这种情况下，你可以实现基于时间的心跳机制：

```
from mcp.server.fastmcp import Context, FastMCP
import time
import asyncio

mcp = FastMCP(host="0.0.0.0", stateless_http=True)

@mcp.tool()
async def model_training(model_name: str, epochs: int, ctx: Context) -> str:
    """Execute a task with progress updates."""
    done_event = asyncio.Event()
    start_time = time.time()

    async def timer():
        while not done_event.is_set():
            elapsed = time.time() - start_time
            await ctx.info(f"Processing ......: {elapsed:.1f} seconds elapsed")
            await asyncio.sleep(5)  # Check every 5 seconds
        return

    timer_task = asyncio.create_task(timer())

    ## main task#####################################
    for i in range(epochs):
        # Simulate long running time training work
        progress = (i + 1) / epochs
        await asyncio.sleep(5)
    #################################################

    # Signal the timer to stop and clean up
    done_event.set()
    await timer_task

    total_time = time.time() - start_time
    print(f"⏱️ Total processing time: {total_time:.2f} seconds")

    return f"{model_name} training completed. The model artifact is stored in s3://templocation/model.pickle . The model training score is 0.87, validation score is 0.82."

if __name__ == "__main__":
    mcp.run(transport="streamable-http")
```

这个模式会创建一个与主任务并行运行的异步定时器，每隔几秒发送一次状态更新。使用 `asyncio.Event()` 进行协调，便于在主工作完成时干净地关闭定时器。

### 何时使用 context messaging

context messaging 最适合以下情况：

- 任务需要 1–15 分钟完成*
- 网络连接总体稳定
- client 会话能在整个操作期间保持活动
- 你需要在处理过程中获得实时进度更新
- 任务具有可预测的有限执行时间和明确的终止条件

*注："15 分钟"基于 Amazon Bedrock AgentCore 提供的同步请求最大时长。有关 Bedrock AgentCore 服务配额的更多细节，请参阅 [Quotas for Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html)。如果承载 agent 的基础设施没有设置硬性时间限制，用这种方法处理可能挂起或无限运行的任务时要极其谨慎。没有适当防护措施，卡住的任务可能无限期保持连接打开，导致资源耗尽、进程无响应，甚至可能出现系统范围的稳定性问题。

以下是一些需要考虑的重要限制：

- **需要持续连接** – client 会话必须在整个操作期间保持活动。如果用户关闭浏览器或网络掉线，工作就会丢失。
- **资源消耗** – 保持连接打开会消耗 server 和 client 资源，可能增加长时间运行的成本。
- **依赖网络** – 网络不稳定仍可能中断流程，需要完全重启。
- **最终超时限制** – 大多数基础设施都有硬性超时限制，无法用心跳消息绕过。

因此，对于可能耗时数小时、真正长时间运行的操作，或者用户需要断开并稍后重新连接的场景，你需要更稳健的异步任务管理方法。

## 异步任务管理

与 client 必须保持持续连接的 context messaging 方法不同，异步任务管理模式遵循"fire and forget"模型：

- **任务启动** – client 发出启动任务的请求，立即收到一个任务 ID
- **后台处理** – server 异步执行工作，无需 client 保持连接
- **状态检查** – client 可以随时重新连接，用任务 ID 查看进度
- **结果取回** – 任务完成后，client 无论何时重新连接都可以取回结果

图 2：异步任务管理方法的工作流示意

这个模式类似于你在企业环境中与批处理系统交互的方式——提交作业、断开连接，之后方便时再回来查看。下面是一个体现这些原则的实际实现：

```
from mcp.server.fastmcp import Context, FastMCP
import asyncio
import uuid
from typing import Dict, Any

mcp = FastMCP(host="0.0.0.0", stateless_http=True)

# task storage
tasks: Dict[str, Dict[str, Any]] = {}

async def _execute_model_training(
        task_id: str, 
        model_name: str, 
        epochs: int
    ):
    """Background task execution."""
    tasks[task_id]["status"] = "running"
    
    for i in range(epochs):
        tasks[task_id]["progress"] = (i + 1) / epochs
        await asyncio.sleep(2)

    tasks[task_id]["result"] = f"{model_name} training completed. The model artifact is stored in s3://templocation/model.pickle . The model training score is 0.87, validation score is 0.82."
    
    tasks[task_id]["status"] = "completed"

@mcp.tool()
def model_training(
    model_name: str, 
    epochs: int = 10
    ) -> str:
    """Start model training task."""
    task_id = str(uuid.uuid4())
    tasks[task_id] = {
        "status": "started", 
        "progress": 0.0, 
        "task_type": "model_training"
    }
    asyncio.create_task(_execute_model_training(task_id, model_name, epochs))
    return f"Model Training task has been initiated with task ID: {task_id}. Please check back later to monitor completion status and retrieve results."

@mcp.tool()
def check_task_status(task_id: str) -> Dict[str, Any]:
    """Check the status of a running task."""
    if task_id not in tasks:
        return {"error": "task not found"}
    
    task = tasks[task_id]
    return {
        "task_id": task_id,
        "status": task["status"],
        "progress": task["progress"],
        "task_type": task.get("task_type", "unknown")
    }

@mcp.tool()
def get_task_results(task_id: str) -> Dict[str, Any]:
    """Get results from a completed task."""
    if task_id not in tasks:
        return {"error": "task not found"}
    
    task = tasks[task_id]
    if task["status"] != "completed":
        return {"error": f"task not completed. Current status: {task['status']}"}
    
    return {
        "task_id": task_id,
        "status": task["status"],
        "result": task["result"]
    }

if __name__ == "__main__":
    mcp.run(transport="streamable-http")
```

这个实现创建了一个包含三个不同 MCP tool 的任务管理系统：

- `model_training()` – 启动新任务的入口。它不直接执行工作，而是：使用 Universally Unique Identifier (UUID) 生成唯一任务标识符；在存储字典中创建初始任务记录；用 `asyncio.create_task()` 把实际处理作为后台任务启动；立即返回任务 ID，让 client 可以断开连接。
- `check_task_status()` – 让 client 随时查看进度：在存储字典中按 ID 查找任务；返回当前状态和进度信息；对任务不存在的情况提供适当的错误处理。
- `get_task_results()`– 在结果就绪时取回已完成结果：验证任务存在且已完成；返回后台处理期间存储的结果；在结果尚未就绪时提供清晰的错误信息。

实际工作在私有的 `_execute_model_training()` 函数中进行，它在初始 client 请求完成后独立在后台运行。随着工作推进，它会更新共享存储中的任务状态和进度，使这些信息可供后续状态检查使用。

### 需要考虑的限制

虽然异步任务管理方法有助于解决连接问题，但它也带来了一系列自身限制：

- **用户体验摩擦** – 这种方法要求用户手动检查任务状态、跨会话记住任务 ID，并显式请求结果，增加了交互复杂度。
- **易失内存存储** – 使用内存存储（如我们的示例）意味着 server 重启后任务和结果都会丢失，没有持久化存储就不适合用于生产。
- **Serverless 环境约束** – 在短暂的 serverless 环境中，实例会在一段时间不活动后自动终止，导致内存中的任务状态永久丢失。这造成一种悖论：为处理长时间运行操作而设计的方案，恰恰在它想要支持的时长上变得脆弱。除非用户定期"签到"以避免触发会话时间限制，否则任务和结果都可能消失。

### 迈向更稳健的方案

要解决这些关键限制，你需要引入能在 server 重启和实例终止后依然存在的外部持久化能力。这时与专用存储服务的集成就变得至关重要。通过使用外部 agent memory 存储系统，你可以从根本上改变任务信息的保存位置和方式。这种方法不依赖 MCP server 的易失内存，而是使用持久化的外部 agent memory 存储服务，无论 server 状态如何都保持可用。

这一增强方案的关键创新在于：当 MCP server 运行长时间任务时，它把中间结果或最终结果直接写入 agent 可访问的外部 memory 存储，例如 [Amazon Bedrock AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html)，如下图所示。这有助于抵御两类运行时故障：

- 运行 MCP server 的实例可能在任务完成后因不活动而被终止
- 承载 agent 本身的实例可能在短暂的 serverless 环境中被回收

![时序图，展示带事件驱动同步和 memory 管理的 Model Context Protocol (MCP) 架构。五个组件：User、Agent（AI 处理器）、AgentCore Memory（事件存储）、MCP Server 和 MCP Tool（任务执行器）。流程：User 向 Agent 提问 → Agent 经 Event Sync 向 AgentCore Memory 请求 MCP Server → Server 调用 MCP Tool → Tool 立即发出通知 → User 收到通知 → Tool 执行并输出结果，同时向 AgentCore Memory 添加事件 → Agent 与 AgentCore Memory 之间发生多次 Event Sync → User 查看任务状态 → Agent 通过 Event Sync 取回信息 → Agent 回复 User。展示了跨 agent 会话、带同步 memory 管理的事件驱动架构。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/07/image-5-1.png)

图 3：MCP 与外部 memory 的集成

有了外部 memory 存储，当用户回来与 agent 交互时——无论是几分钟、几小时还是几天后——agent 都能从持久化存储中取回已完成的任务结果。这种方法把运行时依赖降到最低：即使 MCP server 和 agent 实例都被终止，任务结果仍被安全保存，需要时可访问。

下一节将探讨如何实现这一稳健方案：用 [Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 作为 serverless 托管环境，用 AgentCore Memory 持久化 agent memory 存储，并用 Strands Agents 框架把这些组件编排成一个连贯的系统，跨会话边界维护任务状态。

## Amazon Bedrock AgentCore 与 Strands Agents 实现

在深入实现细节之前，有必要了解 Amazon Bedrock AgentCore 上 MCP server 可用的部署选项。主要有两种：[Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 和 AgentCore Runtime。AgentCore Gateway 的调用超时为 5 分钟，因此不适合托管那些提供需要更长响应时间或长时间运行操作的 tool 的 MCP server。AgentCore Runtime 灵活得多：同步请求的超时为 15 分钟，还可调整最大会话时长（异步流程，默认 8 小时）和空闲会话超时。虽然你可以在传统的 serverful 环境中托管 MCP server 以获得无限执行时间，但 AgentCore Runtime 为大多数生产场景提供了理想的平衡。你既能获得 serverless 的好处，如自动扩缩、按使用付费和无需管理基础设施，同时可调的最大会话时长覆盖了大多数真实世界的长时间任务——从数据处理、模型训练到报告生成和复杂仿真。你可以用这种方法构建精密的 AI agent，而无需承担管理服务器的运维开销，只在极少数确实需要跨天执行的场景下才保留 serverful 部署。有关 AgentCore Runtime 和 AgentCore Gateway 服务配额的更多信息，请参阅 [Quotas for Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html)。

接下来我们逐步讲解实现，如下图所示。该实现由两个相互连接的组件构成：执行长时间任务并把结果写入 AgentCore Memory 的 MCP server，以及管理对话流程并在需要时取回结果的 agent。这一架构带来无缝体验：用户可以在漫长流程中断开连接，稍后回来时结果已经等在那里。

### MCP server 实现

下面来看看我们的 MCP server 实现如何利用 AgentCore Memory 实现持久化：

```
from mcp.server.fastmcp import Context, FastMCP
import asyncio
import uuid
from typing import Dict, Any
import json
from bedrock_agentcore.memory import MemoryClient

mcp = FastMCP(host="0.0.0.0", stateless_http=True)
agentcore_memory_client = MemoryClient()

async def _execute_model_training(
        model_name: str, 
        epochs: int,
        session_id: str,
        actor_id: str,
        memory_id: str
    ):
    """Background task execution."""
    
    for i in range(epochs):
        await asyncio.sleep(2)

    try:
        response = agentcore_memory_client.create_event(
            memory_id=memory_id,
            actor_id=actor_id,
            session_id=session_id,
            messages=[
                (
                    json.dumps({
                        "message": {
                            "role": "user",
                            "content": [
                                {
                                    "text": f"{model_name} training completed. The model artifact is stored in s3://templocation/model.pickle . The model training score is 0.87, validation score is 0.82."
                                }
                            ]
                        },
                        "message_id": 0
                    }),
                    'USER'
                )
            ]
        )
        print(response)
    except Exception as e:
        print(f"Memory save error: {e}")

    return

@mcp.tool()
def model_training(
        model_name: str, 
        epochs: int,
        ctx: Context
    ) -> str:
    """Start model training task."""

    print(ctx.request_context.request.headers)
    mcp_session_id = ctx.request_context.request.headers.get("mcp-session-id", "")
    temp_id_list = mcp_session_id.split("@@@")
    session_id = temp_id_list[0]
    memory_id= temp_id_list[1]
    actor_id  = temp_id_list[2]

    asyncio.create_task(_execute_model_training(
            model_name, 
            epochs, 
            session_id, 
            actor_id, 
            memory_id
        )
    )
    return f"Model {model_name}Training task has been initiated. Total training epochs are {epochs}. The results will be updated once the training is completed."


if __name__ == "__main__":
    mcp.run(transport="streamable-http")
```

该实现依赖两个关键组件来实现持久化和会话管理。

- `agentcore_memory_client.create_event()` 方法是 tool 执行与持久化 memory 存储之间的桥梁。后台任务完成后，该方法用指定的 memory ID、actor ID 和 session ID 把结果直接保存到 AgentCore Memory 中 agent 的 memory 里。传统做法中结果可能只是临时存储或需要手动取回，而这一集成让任务结果成为 agent 对话 memory 的永久组成部分。agent 随后可以在未来的交互中引用这些结果，跨多个会话形成持续积累知识的体验。
- 第二个关键组件是通过 `ctx.request_context.request.headers.get("mcp-session-id", "")` 提取会话上下文。`"Mcp-Session-Id"` 是[标准 MCP 协议](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports" \l "session-management)的一部分。你可以用这个请求头传递一个复合标识符，以分隔符格式包含三条关键信息：`session_id@@@memory_id@@@actor_id`。这种方法让我们的实现能从单个请求头值中取回所需的上下文标识符。之所以必须用请求头而不是环境变量，是因为这些标识符会随每次对话动态变化，而环境变量从容器启动起就保持静态。在多租户场景中，这一设计选择尤为重要：单个 MCP server 同时处理多个用户的请求，每个用户都有各自不同的会话上下文。

这个例子中另一个重要方面是存储事件时消息格式要正确。保存到 AgentCore Memory 的每条消息都需要两个组成部分：内容和角色标识符。这两个部分需要按 agent 框架能识别的方式格式化。下面是 Strands Agents 框架的示例：

```
messages=[
    (
        json.dumps({
            "message": {
                "role": "user",
                "content": [
                    {
                        "text": <message to the memory>
                    }
                ]
            },
            "message_id": 0
        }),
        'USER'
    )
]
```

内容是内部的 JSON 对象（用 `json.dumps()` 序列化），包含消息详情，包括角色、文本内容和消息 ID。外层的角色标识符（本例中为 USER）帮助 AgentCore Memory 对消息来源分类。

### Strands Agents 实现

使用 [Bedrock AgentCore SDK](https://github.com/aws/bedrock-agentcore-sdk-python/?tab=readme-ov-file) 中的 `AgentCoreMemorySessionManager` 类，把 Amazon Bedrock AgentCore Memory 与 Strands Agents 集成非常简单。如下面的代码示例所示，实现只需极少配置：用你的会话标识符创建一个 `AgentCoreMemoryConfig`，用这个配置初始化 session manager，然后直接把它传给 agent 构造函数。session manager 在幕后透明处理 memory 操作，在多次交互之间维护对话历史和上下文，并用 `session_id`、`memory_id` 和 `actor_id` 的组合来组织 memory。更多信息请参阅 [AgentCore Memory Session Manager](https://strandsagents.com/latest/documentation/docs/community/session-managers/agentcore-memory/)。

```
from bedrock_agentcore.memory.integrations.strands.config import AgentCoreMemoryConfig
from bedrock_agentcore.memory.integrations.strands.session_manager import AgentCoreMemorySessionManager

@app.entrypoint
async def strands_agent_main(payload, context):

    session_id = context.session_id
    if not session_id:
        session_id = str(uuid.uuid4())
    print(f"Session ID: {session_id}")

    memory_id = payload.get("memory_id")
    if not memory_id:
        memory_id = ""
    print(f"? Memory ID: {memory_id}")

    actor_id = payload.get("actor_id")
    if not actor_id:
        actor_id = "default"
        
    agentcore_memory_config = AgentCoreMemoryConfig(
        memory_id=memory_id,
        session_id=session_id,
        actor_id=actor_id
    )

    session_manager = AgentCoreMemorySessionManager(
        agentcore_memory_config=agentcore_memory_config
    )
    
    user_input = payload.get("prompt")

    headers = {
        "authorization": f"Bearer {bearer_token}",
        "Content-Type": "application/json",
        "Mcp-Session-Id": session_id + "@@@" + memory_id + "@@@" + actor_id
    }

    # Connect to an MCP server using SSE transport
    streamable_http_mcp_client = MCPClient(
        lambda: streamablehttp_client(
                mcp_url,
                headers,
                timeout=30
            )
        )

    with streamable_http_mcp_client:
        # Get the tools from the MCP server
        tools = streamable_http_mcp_client.list_tools_sync()

        # Create an agent with these tools        
        agent = Agent(
            tools = tools,
            callback_handler=call_back_handler,
            session_manager=session_manager
        )
```

这里的会话上下文管理尤为精巧。agent 通过 AgentCore Runtime 提供的 payload 和 context 参数接收会话标识符。这些标识符构成关键的上下文桥梁，把跨多个会话的用户交互连接起来。`session_id` 可以从 context 对象中提取（必要时生成一个新的），`memory_id` 和 `actor_id` 则从 payload 中取回。然后这些标识符被打包进一个自定义 HTTP 请求头 (`Mcp-Session-Id`)，在建立连接时传给 MCP server。

要在多次交互中维持这种持久化体验，client 在调用 agent 时必须始终提供相同的标识符：

```
# invoke agentcore through boto3
boto3_response = agentcore_client.invoke_agent_runtime(
    agentRuntimeArn=agent_arn,
    qualifier="DEFAULT",

            }
        ),

)
```

通过在每次调用中始终提供相同的 `memory_id`、`actor_id` 和 `runtimeSessionId`，用户可以获得连续的对话体验，任务结果独立于会话边界持久保存。当用户数天后回来时，agent 能自动取回对话历史以及用户不在期间完成的任务结果。

这一架构代表了 AI agent 能力的重大进步——把长时间运行的操作从脆弱的、依赖连接的过程，转变为稳健、持久的任务，无论连接状态如何都继续工作。最终得到的系统能提供真正异步的 AI 辅助：复杂工作在后台持续进行，用户回到对话时结果被无缝整合进来。
