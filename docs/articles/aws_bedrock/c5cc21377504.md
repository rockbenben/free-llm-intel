# 第 2 部分：使用 Amazon Athena 与 CUDOS 进行 Amazon Bedrock 成本归集

[第 1 部分](https://aws.amazon.com/blogs/machine-learning/introducing-granular-cost-attribution-for-amazon-bedrock/)介绍了 Amazon Bedrock 的细粒度成本归集。该功能会自动把每一次推理请求追溯到发起调用的 IAM principal。它展示了新增的 `line_item_iam_principal` 列如何为你带来按用户、按应用的可见性。借助可选的成本分配标签，你还可以使用 AWS Cost Explorer 按团队、项目或租户汇总支出。采用这种方法，对于任何由 Bedrock 驱动的服务或应用——无论是 Claude Code、Codex 这类第三方工具，还是你自己的定制构建——你通常都能按自己想要的粒度跟踪用量。本文展示如何通过 Amazon Athena 查询与 CUDOS 仪表板来可视化和分析 Amazon Bedrock 的成本归集。

首先，本文说明如何通过带 IAM principal 数据的 [Data Exports](https://docs.aws.amazon.com/cur/latest/userguide/dataexports-create.html) 来设置成本与使用报告（CUR）2.0。接着，本文说明如何用 Amazon Athena 查询 CUR 数据以进行分析。然后介绍 CUDOS 仪表板的新能力，包括细粒度的 Bedrock 成本与用量数据。Athena 在聚合、与不同商业智能（BI）工具集成以及费用分摊流程方面提供了灵活性，而 CUDOS 提供针对你组织具体结构定制的预置可视化。

示例查询输出，展示按 IAM principal 与用量类型划分的 Amazon Bedrock 成本

## 设置成本与使用报告（CUR 2.0）

在分析 Amazon Bedrock 成本之前，请先设置一个 CUR 2.0 数据导出，并把它连接到 Amazon Athena。

### 前提条件

你需要以下条件：

- 一个可访问账单 console 的 AWS 账户。
- 针对成本与使用报告、S3 和 Athena 的 IAM 权限。
- 一个用于存放 CUR 数据的 S3 桶。
- 对 SQL 与 AWS Management Console 有基本了解。
- （可选）用于自动化设置的 Claude Code 或 Kiro-CLI。

请确认你具备[所需的 IAM 权限](https://github.com/aws-samples/sample-cur-iam-principal-bedrock-tracking/tree/main#required-iam-permissions)。

对于 Amazon Bedrock 成本归集，你需要在 CUR 2.0 导出中启用 IAM principal 数据，以便填充 `line_item_iam_principal` 列及相关的 IAM principal 标签。

### 创建带 IAM principal 数据的 CUR 2.0 数据导出

按照[创建标准数据导出](https://docs.aws.amazon.com/cur/latest/userguide/dataexports-create-standard.html)中的说明设置你的 CUR 2.0 导出。在配置导出时，请确保以下选项包含在你的最终配置中：

创建一个启用了调用方身份（IAM principal）分配数据的 CUR 2.0 标准数据导出

- 在 **Additional export content** 中，勾选以下复选框：**Include caller identity (IAM principal) allocation data** —— 这是关键的设置，它会填充 `line_item_iam_principal` 列，并在你的成本数据中呈现 IAM principal 标签（前缀为 `iamPrincipal/`）。
- 在 **Data table configurations** 中：**Time granularity**：选择 Hourly 以获得最大细节。
- 在 **Data export delivery options** 中：**File versioning**：选择 Overwrite existing report，以避免存储重复数据。

***重要：** 启用 IAM principal 数据会增大 CUR 文件体积，因为此前只有一行的用量现在会展开为多行，每个对用量有贡献的 IAM principal 各占一行。对于包含大量不同 principal 的高流量工作负载，请相应规划你的 Amazon S3 存储，并考虑对较旧的 CUR 文件使用 [Amazon S3 生命周期策略](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html)。*

AWS 最多可能需要 24 小时才会把你的第一份 CUR 2.0 报告投递到 S3 桶。

### 将 CUR 2.0 连接到 Amazon Athena

使用 Amazon Athena，你可以用标准 SQL 查询 CUR 数据，无需管理任何基础设施。为简化这一设置，我们提供了一个可选的 agent.md 技能仓库，可与 Claude Code、Kiro-CLI 或 Codex 等 AI 助手配合使用。它把「将你的 Athena 环境连接到 CUR 数据」这一端到端流程自动化。

- 克隆该仓库（`git clone https://github.com/aws-samples/sample-cur-iam-principal-bedrock-tracking`）。
- 在该目录中启动 Claude Code（`claude`）或 Kiro CLI（`kiro`）。
- 输入 prompt：“阅读 agent.md，按照其中的工作流设置成本与使用报告跟踪，并运行本月的按 principal 统计 Amazon Bedrock 成本的查询。”

你也可以按照[手动设置步骤](https://github.com/aws-samples/sample-cur-iam-principal-bedrock-tracking/blob/main/manual_setup.md)操作。

如果你还计划部署 CUDOS 仪表板，可以从 [AWS CloudFormation 部署它](https://docs.aws.amazon.com/guidance/latest/cloud-intelligence-dashboards/deployment-in-global-regions.html)。该过程还会同时部署 Athena 查询数据库。

部署完成后，下面是你可以使用的一个示例测试查询，位于 [Athena Query Editor](https://us-east-1.console.aws.amazon.com/athena/home?region=us-east-1#/query-editor/history) 中：

```
SELECT
    line_item_iam_principal,
    line_item_usage_type,
    line_item_unblended_cost
    --# Note: replace your_cur_table_name, like `cid_data_export.cur2`
FROM your_cur_table_name
WHERE line_item_product_code in ('AmazonBedrock', 'AmazonBedrockService')
    AND line_item_iam_principal IS NOT NULL
LIMIT 10;
```

如果它返回带有 IAM principal ARN 与 Bedrock 用量类型的行，说明你的设置已完成，可以进行更深入的分析。

## 用于 Bedrock 成本跟踪的 Athena 查询模式

CUR 2.0 数据在 Athena 中可用之后，你现在可以用 SQL 回答细粒度的成本归集问题。本节提供三种逐步进阶的查询模式，覆盖最常见的分析场景。

**注意：** 在下面的查询中，请把 `your_cur_table_name` 替换为你的 CUR Athena 表的实际名称（例如 `cid_data_export.cur2`）。

### 查询 1：按 IAM principal 与用量类型划分的 Bedrock 成本

该查询提供按调用方身份与模型用量划分的 Amazon Bedrock 支出完整明细。它回答这个问题：*「谁在调用哪些模型，他们花了多少钱？」*

```
SELECT
    line_item_iam_principal,
    line_item_usage_type,
    SUM(line_item_usage_amount) AS total_tokens,
    SUM(line_item_unblended_cost) AS total_cost
FROM your_cur_table_name
WHERE line_item_product_code in ('AmazonBedrock', 'AmazonBedrockService')
    AND billing_period = DATE_FORMAT(CURRENT_DATE, '%Y-%m')
    AND line_item_iam_principal IS NOT NULL
    -- AND line_item_usage_type LIKE '%Sonnet%input%'
GROUP BY
    line_item_iam_principal,
    line_item_usage_type
ORDER BY total_cost DESC;
```

**示例输出：**

| **line_item_iam_principal** | **line_item_usage_type** | **total_tokens** | **total_cost** |
| --- | --- | --- | --- |
| arn:aws:sts::123456789012:assumed-role/ChatApp/session-1 | USW2-anthropic.claude-opus-4-8-mantle-cache-write-tokens-standard | 1629.5 | $11.2029 |
| arn:aws:sts::123456789012:assumed-role/DocProcessor/batch-7 | USW2-Claude4.6Sonnet-output-tokens | 68.579 | $1.131 |
| arn:aws:sts::123456789012:assumed-role/ClaudeCode/chat | USW2-Claude4.6Sonnet-cache-write-input-token-count | 831.74 | $3.4309 |
| arn:aws:iam::123456789012:user/alice | USW2-Claude4.6Sonnet-input-tokens | 17.33 | $0.0572 |

**分析提示：**

- 使用 `line_item_usage_type LIKE '%Sonnet%output%'` 或 `%nova%` 这样的 LIKE 模式来筛选特定模型。
- `line_item_iam_principal` 列包含完整的 ARN。对于 assumed role，最后一个 `/` 之后的会话名标识了具体的用户或会话。

### 查询 2：按已知 IAM principal 标签细分的成本

当你为 IAM principal 打了 `team`、`project` 或 `costcenter` 之类的维度标签（并把这些标签激活为成本分配标签）后，它们会出现在 CUR 2.0 数据中，作为 *tags* 列的一部分，前缀为 `iamPrincipal/`，后面跟你的标签键。该查询按这些标签对成本分组，以回答诸如：*「工程团队本月在 Bedrock 上花了多少钱？」*或*「chatbot 项目的 Bedrock 总成本是多少？」*这类问题。

**按项目：**

```
SELECT
    tags['iamPrincipal/project'] AS project,
    line_item_usage_type,
    SUM(line_item_usage_amount) AS total_tokens,
    SUM(line_item_unblended_cost) AS total_cost
FROM your_cur_table_name
WHERE line_item_product_code in ('AmazonBedrock', 'AmazonBedrockService')
    AND billing_period = DATE_FORMAT(CURRENT_DATE, '%Y-%m')
    AND line_item_iam_principal IS NOT NULL
GROUP BY
    tags['iamPrincipal/project'],
    line_item_usage_type
ORDER BY total_cost DESC;
```

**示例输出：**

| **project** | **line_item_usage_type** | **total_tokens** | **total_cost** |
| --- | --- | --- | --- |
| data-science | USW2-Claude4.5Sonnet-cache-write-input-token-count | 433.893 | 1.789808625 |
| data-science | USW2-Claude4.6Sonnet-cache-read-input-token-count | 5372.659 | 1.77297747 |
| engineering | USW2-Claude4.5Sonnet-input-tokens | 29.481 | 0.0972873 |
| engineering | USW2-Claude4.5Sonnet-output-tokens | 31.102 | 0.513183 |

**注意：** 只有当你的 IAM principal 已用相关键打上标签，且这些标签已被激活为成本分配标签时，该查询才会返回结果。

### 查询 3：针对未知标签 schema，使用 UNNEST 动态发现标签

在大型组织中，你可能无法预先知道所有 IAM principal 上都打了哪些标签。不同团队可能使用不同的标签键，新标签也可能随时间被引入。下面的示例展示如何使用 Athena 的 UNNEST 函数进行动态探索。

该查询发现你的 Bedrock 工作负载中正在使用的所有 IAM principal 标签，并展示每个标签键值对的成本分配：

```
WITH iam_principal_costs AS (
    SELECT
        t.key AS tag_name,
        t.value AS tag_value,
        line_item_usage_type,
        line_item_unblended_cost
    FROM your_cur_table_name
    CROSS JOIN UNNEST(tags) AS t(key, value)
    WHERE line_item_product_code IN ('AmazonBedrock', 'AmazonBedrockService')
        AND line_item_iam_principal IS NOT NULL
        AND line_item_iam_principal != ''
        AND t.key LIKE 'iamPrincipal/%'
)
SELECT
    tag_name || ': ' || tag_value AS tags,
    line_item_usage_type,
    SUM(line_item_unblended_cost) AS total_cost
FROM iam_principal_costs
GROUP BY tag_name, tag_value, line_item_usage_type
ORDER BY total_cost DESC;
```

## 真实用例：多服务成本对比

设想一个运行多个 AI 驱动服务的平台团队。例如，该团队可能运行一条文档摘要 pipeline（DocProcessor）和一个面向客户的 chatbot（ChatApp）。团队可以为每个服务分配各自的 IAM 角色。借助上一节的查询模式，你可以用下面的查询单独观察每个服务的支出趋势：

```
SELECT
    line_item_iam_principal,
    line_item_usage_type,
    SUM(line_item_usage_amount) AS total_usage,
    SUM(line_item_unblended_cost) AS total_cost
FROM your_cur_table_name
WHERE line_item_product_code IN ('AmazonBedrock', 'AmazonBedrockService')
    AND billing_period = DATE_FORMAT(CURRENT_DATE, '%Y-%m')
    AND line_item_iam_principal IS NOT NULL
    AND (
        line_item_iam_principal LIKE '%DocProcessor%'
        OR line_item_iam_principal LIKE '%ChatApp%'
    )
GROUP BY
    line_item_iam_principal,
    line_item_usage_type
ORDER BY total_cost DESC;
```

示例输出：

| **line_item_iam_principal** | **line_item_usage_type** | **total_usage** | **total_cost** |
| --- | --- | --- | --- |
| arn:aws:sts::123456789012:assumed-role/ChatApp/session-1 | USE1-Claude4.6Sonnet-output-tokens | 4,800,000 | $72.00 |
| arn:aws:sts::123456789012:assumed-role/ChatApp/session-1 | USE1-Claude4.6Sonnet-input-tokens | 2,900,000 | $8.70 |
| arn:aws:sts::123456789012:assumed-role/DocProcessor/batch-7 | USE1-NovaLite-output-tokens | 6,100,000 | $1.46 |
| arn:aws:sts::123456789012:assumed-role/DocProcessor/batch-7 | USE1-NovaLite-input-tokens | 3,200,000 | $0.19 |

从这份输出中，平台团队可以回答如下问题：

**哪个应用是本月 Bedrock 支出的最大贡献者？** 在本例中，ChatApp 使用 Claude 4.6 Sonnet，占用了超过 80 美元；而 DocProcessor 使用 Nova Lite，成本不到 5 美元。

**我们能否通过为每个工作负载使用不同模型来降低成本？** DocProcessor 已经在用 Nova Lite（适合直白的摘要任务），但团队可以评估 ChatApp 是否能用更轻量的模型处理部分交互，以降低 72 美元的输出 token 成本。

## Athena 查询的成本

你只需为实际运行的查询付费。费用基于每个查询扫描的数据量计算。console 会在每次查询后显示这一信息，该信息也可在 Athena console 的 Recent Queries 标签页中查看。

Athena 查询按每 TB 扫描数据 5 美元计费（每次查询最低按 10 MB 计）。由于我们的表在 billing_period 上自动使用 [hive 分区投影](https://docs.aws.amazon.com/athena/latest/ug/partition-projection.html)，限定在单个月的查询只会扫描该月文件夹中的 parquet 文件。扫描量通常远低于 10 MB，费用约为每次查询 0.00005 美元（即 10 MB 的下限）。

为保持低成本，请始终加上 `WHERE billing_period = ...` 过滤条件，并只选择你需要的列，而不是 `SELECT *`。

## Cloud Intelligence Dashboards 框架

[CUDOS 仪表板](https://docs.aws.amazon.com/guidance/latest/cloud-intelligence-dashboards/cudos-cid-kpi.html#foundational-cudos-dashboard)是开源 [Cloud Intelligence Dashboards（CID）框架](https://docs.aws.amazon.com/guidance/latest/cloud-intelligence-dashboards/getting-started.html)的一部分，你可以使用提供的基础设施即代码（IaC）模板把它部署到自己的 AWS 账户中。该框架帮助你在各个 AWS organization 中推动财务问责并提升运营效率。CUDOS 仪表板提供详尽且可执行的洞察，为你的 AWS 基础设施实现成本效益提供数据驱动的决策支持。

### CUDOS 中的 Amazon Bedrock 成本与用量洞察

[CUDOS 5.8 版](https://github.com/aws-solutions-library-samples/cloud-intelligence-dashboards-framework/blob/main/changes/CHANGELOG-cudos.md#cudos---580)在 AI/ML 标签页中引入了完整的 Amazon Bedrock 部分，全面支持 IAM principal 成本归集。该仪表板提供：

- **灵活的分组维度：** 按 IAM Principal、IAM Principal 标签（例如 Project 或 Team）、模型/资源组、区域，或仪表板部署期间配置的任何其他成本分类字段，对你的 Amazon Bedrock 支出分组。
- **每百万 token 成本跟踪：** 在你的支出图上叠加一条趋势线，展示每百万 token 成本随时间的变化，帮助你衡量模型选择变化或 prompt 优化工作（例如缓存）所带来的影响。

下图展示了 CUDOS 仪表板 AI/ML 标签页中的 Amazon Bedrock Summary 部分，按 IAM principal 分组，并带有按 principal 的成本明细与每百万 token 成本趋势。

CUDOS 仪表板，展示按 IAM principal 分组的 Amazon Bedrock 支出

- **交互式下钻过滤：** 在顶层支出图中选择任意值（例如某个项目、principal 或账户），其他所有可视化会自动过滤到该选择，让你从高层概览下钻到按模型与按用量类型的细节，而无需离开仪表板。
- **细粒度的模型与用量明细：** 由顶层图表过滤的其他可视化会展示每个模型、每种用量类型的支出，以及按模型划分的每百万 token 成本，因此你可以识别出对给定团队或项目而言是哪些模型与 token 类型在推高成本。

当你把分组切换为 IAM Principal Tag Project 并选择某个具体项目（在本例中为 “chatbot-v2”）时，其他所有可视化都会过滤为只显示该项目的支出。这些可视化会把该支出按模型、用量类型与单位成本趋势细分。

CUDOS 仪表板，展示按 IAM principal 标签 Project 分组的 Amazon Bedrock 支出，并过滤到 chatbot-v2 项目

借助这些可视化，你可以快速回答诸如“哪个项目导致的输出 token 成本最高？”、“我们的 chatbot 团队在使用成本高效的模型吗？”或“自从我们从 Opus 切换到 Sonnet 后，每百万 token 成本有何变化？”这样的问题，而无需写任何 SQL。

## 清理

首先，删除 Athena 表与 AWS Glue 数据库（这些是元数据，因此不会有计算资源在运行）：

警告：删除 Athena 表与 Glue 数据库会使你无法再查询 CUR 数据。如果你将来还想分析账单数据，就需要按上一节重新创建这些资源。

```
aws glue delete-table --region us-east-1 --database-name your_cur_table_name --name curexport
aws glue delete-database --region us-east-1 --name your_cur_table_name
```

其次，如果你不再需要成本数据本身，请在 AWS Billing and Cost Management console 的 Data Exports 下停用该导出，并清空它写入的 S3 前缀。请注意这是你的原始账单历史，只有在确定的情况下才删除。

最后，清除累积下来的 Athena 查询结果：

```
aws s3 rm s3://<your-cur-bucket>/athena-results/ --recursive
```

没有 crawler、AWS Lambda 函数或调度需要删除。分区投影意味着唯一的持续成本就是 CUR 文件本身的 S3 存储费用，通常每月只需几分钱。

关于清理 CUDOS，请参阅 [CUDOS 仪表板拆除说明](https://docs.aws.amazon.com/guidance/latest/cloud-intelligence-dashboards/dashboard-teardown.html)。
