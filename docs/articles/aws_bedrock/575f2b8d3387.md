# 使用 Amazon SageMaker HyperPod 跨团队共享 GPU 集群，同时保证隔离与公平

同一家公司里的多个团队，越来越需要共享昂贵的 GPU 集群来支撑各自的生成式 AI 业务，同时又要求保住隔离边界、资源公平性和操作上的独立性。设想一个训练大语言模型的数据科学团队、一个跑推理工作负载的计算机视觉小组，再加一个尝试新模型架构的研究团队——他们可能都需要用同一个集群。多租户（多团队）架构设计得不好，组织就会面临资源消耗失控、团队之间隔离薄弱、共享 GPU 的成本无法归到真正消耗它的团队头上，以及拖慢创新的管理开销。

Amazon SageMaker HyperPod 是一项专为 AI 打造的服务，把生成式 AI 工作负载所需的大规模计算集群的管理变得简单。它提供有韧性、经过调优的集群，由 Amazon Elastic Kubernetes Service（Amazon EKS）或 Slurm 编排，让组织能够大规模地运行分布式训练、交互式开发和模型推理；与此同时，节点健康监控、故障恢复和集群生命周期管理都由它自动处理。

这篇文章给出一套参考架构，用于在 Amazon SageMaker HyperPod（配合 EKS）上搭建多租户环境。这套架构用 AWS IAM Identity Center 做集中认证，用按团队划分的 SageMaker AI 域提供贴合各团队的使用体验，用 Kubernetes 命名空间做工作负载隔离，用 HyperPod Task Governance 做公平的资源分配，再用命名空间级别的成本分摊拿到每个团队的支出可见性与 chargeback。读完这篇文章，你会得到一份清晰的蓝图，让多个团队高效共用一个 HyperPod EKS 集群。

## 架构总览

下面的图示给出了多租户 HyperPod EKS 部署的高层架构。这个例子里，两个团队（Team A 和 Team B）共用一个 HyperPod EKS 集群，各自在自己的隔离命名空间内运行。

图 1：两个团队共用一个 HyperPod EKS 集群的多租户高层架构

整张架构按从左到右的分层流程组织：从用户身份出发，经过授权控制，一路连到集群上相互隔离的工作负载命名空间。

### 用户与认证

最左边是每个团队的具体用户（Team A 的 User 1、Team B 的 User 2），他们通过两条路径与系统交互。两条路径都要经过 AWS IAM Identity Center Portal 认证，该门户与左下角所示的外部身份提供商（例如 Microsoft Entra ID）做联邦。

第一条路径是 CLI 访问。用户用 `aws sso login` 认证，它会把用户重定向到 Identity Center 门户，之后从所在团队的权限集拿到临时凭证，用 `kubectl` 把任务直接提交到 EKS 集群。图里那条粉色箭头从 CLI 终端出发，沿上方一路进入 HyperPod EKS 集群。

第二条路径是直接进入 Identity Center 门户，用户在那里选择 SageMaker Studio 应用，登录到本团队专属的 SageMaker AI 域。

每个团队都有对应的权限集（TeamA permission set、TeamB permission set），其中带有 CLI 工作流所需的 AWS Identity and Access Management（IAM）策略。Identity Center 会为每个权限集自动开通一个 IAM 角色，图中就是 `TeamA-permissionset-role` 和 `TeamB-permissionset-role`（标注为「CLI/Console role」）。用户通过 `aws sso login` 认证时，这个角色就是实际发起访问的 IAM 主体。

### SageMaker AI 域

用户从 Identity Center 门户被导向各自团队的 SageMaker AI 域。每个域（SageMaker AI domain Team A 和 SageMaker AI domain Team B）都提供独立的 Amazon SageMaker Studio 图形界面，并配置了团队专属的执行角色（分别是 `TeamA-role` 和 `TeamB-role`）。这些域是主要的工作台入口，用户可以直接在图形界面里提交任务（即图中朝 EKS 流动的那几条粉色箭头）。

### EKS 访问控制

在 EKS 的边界上，access entry 把 IAM 角色映射到 Kubernetes 权限。图中列出了 `TeamA-role` 和 `TeamB-role`（即 Studio 执行角色）的 access entry，负责放行来自 SageMaker Studio 图形界面的请求。Identity Center 开通的那两个 CLI/Console 角色（`TeamA-permissionset-role` 和 `TeamB-permissionset-role`）同样必须配置 access entry，才能放行经 `kubectl` 发来的请求。所有 access entry 都关联到托管或自定义的基于角色的访问控制（RBAC）策略（图中的钥匙图标），并且限定在该团队指定的命名空间内。于是，不管访问来自 Studio 还是 CLI，用户只能操作自己命名空间里的资源。

### HyperPod EKS 集群

集群本身在图顶部横着两层贯穿式的平台能力：HyperPod Observability（监控与仪表盘）和 HyperPod Task Governance（计算配额管理与调度优先级）。这两层之下，集群被划分为 Namespace A（Team A）和 Namespace B（Team B）。每个命名空间内，团队可以运行自己的 HyperPod Spaces（交互式开发环境）、HyperPod PyTorch 任务（分布式训练工作负载）和 HyperPod Inference 端点（模型服务）。

### 存储

集群下方是两层存储。第一层是 POSIX 兼容的文件系统（Amazon FSx for Lustre 或 Amazon FSx for OpenZFS），按团队共享目录（`/fsx/TeamA`、`/fsx/TeamB`）和用户主目录（`/home/User1`、`/home/User2`）来组织。第二层是对象存储，使用按团队划分或共享的 Amazon Simple Storage Service（Amazon S3）桶，由团队的 IAM 执行角色管辖。

这套架构从认证到授权再到工作负载执行，一路把每个团队彼此隔开，同时又把昂贵的 GPU 基础设施高效地共享起来。

## 认证与访问控制

多租户系统的地基是可靠的认证：在用户接触任何资源之前，先确认他们是谁。这套架构里，AWS IAM Identity Center 承担集中认证层，与外部身份提供商联邦，统一管理用户身份和组成员关系。

### 为什么选 AWS IAM Identity Center

AWS IAM Identity Center（AWS Single Sign-On 的继任者）提供一个统一的地方，管理跨 AWS 账户和应用的员工身份。对多租户 HyperPod 部署来说，它有几项关键能力：

- **集中身份管理**：不必为每个 AWS 服务各自维护一套用户库，Identity Center 是所有用户身份及其组成员关系的唯一权威来源。
- **与现有身份提供商联邦**：多数企业已经在 Microsoft Entra ID（前身是 Azure AD）、Okta 或 Ping Identity 这类系统里管理员工身份。Identity Center 能与这些提供商集成，组织可以直接复用现有的身份基础设施，不必重复建一套用户账户。
- **与 SageMaker AI 原生集成**：SageMaker AI 域支持 Identity Center 认证，用户通过企业身份提供商单点登录（SSO）就能进入 SageMaker Studio。
- **AWS 账户访问**：Identity Center 还能用特定权限集授予用户对底层 AWS 账户的访问权，这些权限集在 Studio 图形界面之外支撑 CLI 工作流。
- **Amazon Managed Grafana 的必需项**：Amazon Managed Grafana 用 Identity Center 作为员工用户的认证机制。团队既要访问可观测性仪表盘来监控自己的工作负载，选它自然顺理成章。

了解更多：[什么是 IAM Identity Center](https://docs.aws.amazon.com/singlesignon/latest/userguide/what-is.html)

### 用外部身份提供商配置 Identity Center

在这套参考架构中，我们用 Microsoft Entra ID 作为外部身份提供商，不过同样的模式适用于大多数标准的 Security Assertion Markup Language（SAML）2.0 提供商。

配置涉及以下几项：

- **身份提供商侧的分组结构**：在 Entra ID 里创建与组织团队一一对应的组。我们的例子中定义了三个组：`TeamA`、`TeamB` 和 `Admin`，每个组装着属于该团队的用户（例如 `TeamA` 组里的 `user1-teamA@example.com`）。
- **SCIM 开通**：启用 Entra ID 与 AWS IAM Identity Center 之间的 SCIM（System for Cross-domain Identity Management）同步。SCIM 负责用户与组的自动开通与自动注销。Entra ID 的 `TeamA` 组里新增一个用户，他会被自动同步到 Identity Center 并拿到相应访问权，无需人工介入。
- **基于 SAML 的认证**：配置 SAML 2.0 联邦，让用户的认证实际发生在 Entra ID 一侧。Identity Center 充当服务提供商，信任来自你的 Entra ID 租户的断言。

这样配置之后，团队成员关系（它决定下游所有的授权判断）就在现成的企业目录里维护，变更会自动传播到 AWS。

## 授权

认证解决之后，下一层是授权：管住每个团队在 AWS 服务和 Kubernetes 集群里能做哪些操作。这套架构的授权分两层——IAM 负责服务级访问，Kubernetes RBAC 负责集群级访问。

### 按团队划分的 IAM 角色

每个团队需要一个专属 IAM 角色，把该团队 AI 与机器学习（ML）工作流所需的 AWS 层权限收拢在一起。这些角色充当 SageMaker AI 域的执行角色，界定该团队能访问哪些 AWS 服务。

一个典型的团队 IAM 角色应包含授予以下访问权的策略：

- **Amazon SageMaker AI**：通过 SageMaker AI API 管理 HyperPod 集群、MLflow 跟踪服务器以及其他 SageMaker AI 资源。
- **Amazon S3**：读取训练数据集，写入模型产物、检查点和日志。这些权限要限定到团队专属的桶前缀。
- **Amazon CloudWatch**：查看与本团队工作负载相关的日志和指标。
- **Amazon EKS**：具体是 `eks:AccessKubernetesApi` 和 `eks:MutateViaKubernetesApi` 这两项权限，SageMaker Studio 图形界面需要它们代表用户发起 Kubernetes API 调用（例如列出 Spaces 或提交任务）。

每个 IAM 角色的信任策略都必须把 `sagemaker.amazonaws.com` 列为可信主体，这样用户通过 Studio 操作时，SageMaker AI 才能代表他们承担该角色。如果打算把同一个执行角色复用为 EKS Pod Identity 关联，供集群内工作负载使用（后文 Amazon S3 存储一节会讲到），信任策略还得把 `pods.eks.amazonaws.com` 也列为可信主体。经 Identity Center 的 CLI 访问用的是另一个独立权限集及其自有策略（见「通过 Identity Center 访问 AWS 账户」一节），因此 CLI 的权限可以单独划定范围。

了解更多：[如何使用 SageMaker AI 执行角色](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-roles.html)

### 通过 Identity Center 访问 AWS 账户

除了 SageMaker Studio，团队常常还要直接访问 AWS 账户来做 CLI 操作，比如运行 `kubectl` 命令、用脚本编排工作流，或者以编程方式访问资源。Identity Center 的权限集提供的正是这种能力。

对于 **Admin** 组，按你公司策略的要求分配一个具备管理员访问权的权限集，授予集群管理与运维操作所需的账户访问权。

对于 **Team A** 和 **Team B**，创建权限集，用内联策略或托管策略直接授予 CLI 工作流所需的权限。典型的团队权限集包含 `eks:AccessKubernetesApi`（用于在 AWS Console 里查看 Kubernetes 资源）、限定到本团队数据的 S3 访问权，以及用于监控的 CloudWatch 读取权。这些策略与 Studio 执行角色各自独立定义，管理员可以针对团队在命令行里实际执行的那些操作来裁剪 CLI 权限。

用户用 `aws sso login` 通过 AWS Command Line Interface（AWS CLI）取回临时凭证，再用它配置 `kubectl`，直接与 EKS 集群交互。

下图是 AWS IAM Identity Center 里按团队划分的权限集，它们提供限定范围的 AWS 账户访问，支撑针对 EKS 集群运行 `kubectl`、`aws sso login` 这类 CLI 工作流。

### 配置 AWS CLI

团队成员运行 `aws configure sso`，让 AWS CLI 走 Identity Center 认证。这会在 `~/.aws/config` 里创建若干 profile，各自引用相应的 Identity Center 会话和权限集。成员从命令行与集群交互时使用本团队专属的 profile，无论访问来自 Studio 还是本地终端，授权边界都保持不变。

生成的配置包含一个供 Identity Center 门户使用的共享 `sso-session` 块，以及每个团队一个具名 profile，各自指向本团队的权限集。成员随后运行 `aws sso login --profile <team>`，取得限定在本权限集范围内的临时凭证：

```
[sso-session my-sso]
sso_start_url = https://d-xxxxxxxxxx.awsapps.com/start
sso_region = us-west-2
sso_registration_scopes = sso:account:access

[default]
sso_session = my-sso
sso_account_id = 123456789012
sso_role_name = OpsAdmin
region = us-west-2

[profile team-a]
sso_session = my-sso
sso_account_id = 123456789012
sso_role_name = TeamA-permission-set
region = us-west-2

[profile team-b]
sso_session = my-sso
sso_account_id = 123456789012
sso_role_name = TeamB-permission-set
region = us-west-2
```

了解更多：[使用 AWS CLI 配置 IAM Identity Center 身份验证](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sso.html)

## SageMaker AI 域

SageMaker AI 域为每个团队划出工作台的边界，提供贴合需求的使用体验、预先配置好的执行角色，并内置了与 Identity Center 认证的集成。

### 为什么用 SageMaker AI 域

一个团队一个 SageMaker AI 域，是组织多团队环境的成熟做法。这种思路有几项优势：

- **成熟的多团队模式**：AWS 对用多个域分隔业务线或团队这一做法有充分的文档，是一套经过验证、受官方支持的配置。
- **原生支持 Identity Center 认证**：每个域都可以配置为使用 Identity Center 认证，用户通过企业身份提供商登录一次，就直达本团队的 Studio 环境。
- **开箱即用的团队配置能力**：域本身就提供了为用户和团队指定配置的机制，不需要再引入额外的自定义实体。例如团队执行角色这类设置可以在域级别指定，再在用户配置文件级别覆盖，灵活性最大化。
- **导航定制**：借助域设置，管理员可以隐藏与团队工作流无关的导航项，呈现一个聚焦 HyperPod 场景的界面。

了解更多：[SageMaker AI 域的实体与状态](https://docs.aws.amazon.com/sagemaker/latest/dg/sm-domain.html) · [多域概述](https://docs.aws.amazon.com/sagemaker/latest/dg/domain-multiple.html)

### 搭建按团队划分的域

为每个团队创建一个使用 Identity Center 认证的 SageMaker AI 域。我们的例子里创建了 `TeamA-domain` 和 `TeamB-domain`，每个域都按以下方式配置：

- **默认执行角色**：把域的默认执行角色设为授权步骤中创建的那个团队专属 IAM 角色，通过 Studio 执行的所有动作因此都继承到相应权限。
- **Identity Center 组分配**：把对应的 Identity Center 组（例如 `TeamA` 组）加入该域。这一步会为该组所有成员启用 SageMaker Studio 应用，让他们能访问 Studio 界面。
- **核对应用分配**：配好组访问之后，回到 Identity Center 检查应用分配，确认正确的组映射到了正确的域。
- **导航定制**：为每个域配置默认导航设置，只呈现相关的能力。例如可以隐藏与 HyperPod 工作流无关的条目，打造一个 *专注 HyperPod* 的精简体验，让只需要操作 HyperPod 资源的成员少一些认知负担。

## HyperPod EKS 集群配置

工作负载真正运行的地方是 HyperPod EKS 集群。集群层面的多租户，靠 Kubernetes 命名空间做隔离、靠 EKS access entry 做授权来实现。

### 命名空间隔离

为每个团队创建专用的 Kubernetes 命名空间，例如 `hyperpod-ns-team-a` 和 `hyperpod-ns-team-b`。命名空间在集群内部划出一道逻辑边界，把各团队的工作负载（Spaces、训练任务、推理端点）彼此隔开。

> 注：命名空间是隔离边界，不是硬性安全边界。这套架构面向的是同一个组织内部的多团队：这些团队在一个共同的管理域之下、彼此有基本的信任，共用一个集群。它并不是为互不信任的租户之间的多客户隔离而设计的。
>         命名空间、RBAC 和配额能防住误伤——团队互相覆盖对方的资源、或者超出各自的计算配额——但挡不住存意的恶意租户：命名空间里的 Pod 共用同样的节点和内核，而集群级资源（节点、PersistentVolume、CRD、某些 operator 组件）根本不在任何命名空间之内。
>         如果是互不信任的租户，或者要满足严格的合规隔离，就得用更强的边界，例如分开的集群或账户、专用节点池、运行时沙箱。就这里的多团队场景而言，命名空间隔离加上 RBAC、Task Governance 配额，以及后文会讲到的 POSIX 身份控制，在分离程度与运维简洁性之间是合适的取舍。

命名空间既可以手动用 `kubectl create namespace` 创建，也可以由 HyperPod Task Governance 自动开通——它把命名空间作为自身配额与调度配置的一部分来管理。

下图是集群的命名空间（由 HyperPod Task Governance 管理），每个团队一个专用命名空间（`hyperpod-ns-team-a`、`hyperpod-ns-team-b`），以此实现工作负载隔离。

图 7：为工作负载隔离而设的按团队专用 Kubernetes 命名空间

### 网络隔离

命名空间不限制网络流量。Kubernetes 的网络默认是扁平的：所有命名空间里，每个 pod 都能连到任何其他 pod。也就是说，不加额外控制的话，`hyperpod-ns-team-a` 里的 pod 可以直接向 `hyperpod-ns-team-b` 里的 pod 发起连接。要让 pod 之间的可达范围跟着团队边界走，就用 Kubernetes 的 `NetworkPolicy` 资源。

推荐的做法是每个命名空间都 *默认拒绝*：先拒掉全部入站流量（出站流量也可一并拒掉），再显式放行各团队确实需要的流量，通常是命名空间内部通信，加上必需的出站，比如 DNS、存储端点和 AWS API。下面的例子先在团队命名空间里拒绝所有入站，然后只放行来自同一命名空间内 pod 的流量：

```
# 1. Default-deny all ingress in the team's namespace.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: hyperpod-ns-team-a
spec:
  podSelector: {}  # applies to all pods in the namespace
  policyTypes:
  - Ingress
---
# 2. Allow ingress only from pods within the same namespace.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-namespace
  namespace: hyperpod-ns-team-a
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector: {}  # any pod in this namespace
```

`NetworkPolicy` 能否生效，取决于容器网络接口（CNI）是否支持它。在 EKS 上，可以在 Amazon Virtual Private Cloud（Amazon VPC）CNI 中开启网络策略支持。

和命名空间一样，`NetworkPolicy` 减少的是*无意*造成的跨团队可达，并把暴露面收窄；在共享节点上，它本身并不构成一道对抗恶意行为的安全边界。需要更强的分离，就按前文所说考虑按团队专用节点池或分开的集群。

了解更多：[Kubernetes 网络策略](https://kubernetes.io/docs/concepts/services-networking/network-policies/) · [Amazon VPC CNI 网络策略](https://docs.aws.amazon.com/eks/latest/userguide/cni-network-policy.html)

### EKS access entry

EKS access entry 把 IAM 主体连到 Kubernetes RBAC 权限上。每个团队要创建两个 access entry：

- **Studio 侧的 access entry**：IAM 主体是本团队 SageMaker AI 域的执行角色。操作来自 SageMaker Studio 图形界面时走的就是它。
- **CLI 侧的 access entry**：IAM 主体是 Identity Center 为该团队权限集开通的 SSO 角色，命名形如 `AWSReservedSSO_<permission-set-name>_<unique-id>`。用户通过 `kubectl` 与集群交互时走的是它。

两个 entry 都用托管或自定义的 Kubernetes 策略限定在该团队的命名空间内。例如 Team A 的两个 entry 只在 `hyperpod-ns-team-a` 范围内授予权限。如果愿意，两个 entry 可以挂不同的 RBAC 策略：比如 CLI 那个把某些资源类型的写权限收紧，而 Studio 那个放开完整访问。

有了这层限定，无论访问来自 Studio 还是 CLI，用户都只能操作自己命名空间里的资源。想去列出或修改别的团队命名空间中的资源，会得到 Kubernetes 的 `Forbidden` 错误。

更复杂的场景下，可以在 access entry 里使用 Kubernetes 组，把用户映射到自定义的 ClusterRole 或 Role，拿到标准托管策略覆盖不到的细粒度权限。

### HyperPod Task Governance

集群启用 Task Governance 后，它在资源管理上又叠了一层：

- **计算配额**：规定每个团队能消耗多少 GPU 和 CPU 容量，避免某一个团队在训练期间独占共享硬件。
- **优先级**：为各团队或各类工作负载指定调度优先级，资源吃紧时，生产环境的关键推理负载可以抢占实验性的训练任务。
- **公平调度**：有了 Task Governance，多个团队争夺资源时按配置好的策略来分配，而不是先到先得。

按团队命名空间给 Task Governance 配置合适的配额与优先级，在保证最低配给和应对突发负载的弹性容量之间做好平衡。

## 存储

存储是团队共用的人工智能与机器学习（AI/ML）环境里的关键一环。团队需要高性能文件系统来放训练数据、检查点和模型产物，同时还要在团队之间保持恰当的访问边界。

### POSIX 兼容的文件系统

需要共享的高性能 POSIX 文件系统时（分布式训练里多个节点读同一份数据集或写检查点，这种情形很常见），可以考虑以下几种方案：

- **Amazon FSx for Lustre**：提供高吞吐、低延迟的并行文件系统访问，适合需要高速读取海量数据的大规模训练负载。
- **Amazon FSx for OpenZFS**：通用文件系统，POSIX 语义完整，支持快照和压缩。既要传统文件系统特性又要高性能的负载很适合它。
- **Amazon Elastic File System（Amazon EFS）**：全托管的弹性 Network File System（NFS）存储。EFS 还支持访问点（access point），把不同挂载点映射到不同目录并强制指定 UID 和 GID，从而简化按团队的目录隔离。

存储布局通常按这个结构组织：

- **按团队划分的共享目录**：每个团队一个共享目录（例如 `/fsx/TeamA`、`/fsx/TeamB`），放全体成员都要访问的数据集、模型和产物。
- **按用户划分的主目录**：每个用户一个个人主目录（例如 `/home/User1`、`/home/User2`），放自己的工作、实验和 notebook。

这些文件系统的 POSIX 权限模型靠 UID、GID 和附加组（supplemental groups）来落实访问边界。用户启动 HyperPod Space 或提交训练任务时，这些 POSIX 身份要一并传进 pod 的 security context，文件系统访问才会按配置好的归属与权限来。我们建议用 Kubernetes 的变更型准入 webhook（mutating admission webhook）从你的身份存储里取 POSIX 身份信息：工作负载提交时，webhook 在运行时查出对应身份，据此改写 Pod 的 security context。

```
# 1. Extract the caller's session identity from the admission request.
# On EKS, requests from IAM-assumed roles (including IAM Identity Center)
# surface the STS session name in userInfo.extra["sessionName"]. Its format
# depends on how the session is created (e.g., an SSO short name, an email,
# or a role-session-name); align your identity mapping with this value.
def extract_username(admission_request):
    extra = admission_request["userInfo"]["extra"]
    ...
    return extra["sessionName"][0]

# 2. Look up the POSIX identity from a mapping table (e.g. DynamoDB).
def lookup_posix_identity(username):
    item = posix_table.get_item(Key={"username": username})["Item"]
    ...
    return {
        "uid": int(item["uid"]),
        "gid": int(item["gid"]),
        "supplementalGroups": [int(g) for g in item["supplementalGroups"]],
    }

# 3. Patch the Pod security context with the resolved POSIX identity.
def build_security_context_patch(pod, posix):
    ...
    return [{
        "op": "add",
        "path": "/spec/securityContext",
        "value": {
            "runAsUser": posix["uid"],
            "runAsGroup": posix["gid"],
            "fsGroup": posix["gid"],
            "supplementalGroups": posix["supplementalGroups"],
        },
    }]
```

了解更多：[FSx for Lustre](https://docs.aws.amazon.com/fsx/latest/LustreGuide/what-is.html) · [FSx for OpenZFS](https://docs.aws.amazon.com/fsx/latest/OpenZFSGuide/what-is-fsx.html) · [Amazon EFS](https://docs.aws.amazon.com/efs/latest/ug/whatisefs.html)

### Amazon S3 存储

对象存储方面，S3 桶的访问由团队的 IAM 执行角色管辖。你可以为每个团队单独建桶，也可以共用一个桶、按团队划前缀，靠 IAM 策略来落实隔离。集群内的 pod 需要配置合适的服务账户，用 IAM Roles for Service Accounts（IRSA）或 Pod Identity 向 S3 认证。为了简单起见，可以把 SageMaker AI 域上配置的那个执行角色直接关联到团队命名空间内的一个 Kubernetes 服务账户，这样无论从 Studio 还是从集群内工作负载访问 S3，表现都一致。

了解更多：[服务账户的 IAM 角色（IRSA）](https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html) · [EKS Pod Identity](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html)

## HyperPod Spaces

HyperPod Spaces 提供直接跑在集群节点上的交互式开发环境（IDE）。在共享集群上，Spaces 必须正确限定到各团队的命名空间，并配上合适的资源模板。

### Space 模板

为每个团队创建限定命名空间的 Space 模板。模板定义了成员创建 Spaces 时可用的资源配置（实例类型、存储卷、环境变量）。把模板限定在某个命名空间内，就确保了每个团队只能在自己被划定的边界内启动 Spaces。

启用 HyperPod Task Governance 时，模板要包含治理系统要求的默认标签（例如团队标识和优先级标签）。这些标签由集群管理员预先配好，成员启动 Spaces 时不必再手动指定。

下面的例子是一个限定给 Team A 的 JupyterLab Space 模板。与团队相关的部分是 `metadata.namespace`、`baseLabels` 下的 Task Governance 队列标签，以及挂载团队共享文件系统和用户主目录的 `defaultVolumes`：

```
apiVersion: workspace.jupyter.org/v1alpha1
kind: WorkspaceTemplate
metadata:
  name: jl-smd-custom
  namespace: hyperpod-ns-team-a  # scopes the template to Team A's namespace
spec:
  displayName: "JupyterLab (team-a)"
  description: "SageMaker Distribution"
  appType: jupyterlab
  baseLabels:
  - key: kueue.x-k8s.io/queue-name  # Task Governance (Kueue) local queue for Team A
    value: hyperpod-ns-team-a-localqueue
  ...
  # container command, default CPU/memory resources, security context, access type, etc.
  ...
  defaultVolumes:
  - name: home-dir  # per-user home directory
    mountPath: /home
    persistentVolumeClaimName: fsx-openzfs-claim
  - name: shared-data  # Team A's shared directory
    mountPath: /fsx
    persistentVolumeClaimName: fsx-lustre-claim
  ...
  # primary (EBS) storage defaults and limits
  ...
```

### Persistent Volume Claim

在各团队的命名空间里创建合适的 Persistent Volume Claim（PVC），指向共享文件系统。这些 PVC 把团队共享目录和用户主目录挂进 Space，从而可以访问训练数据、检查点和个人工作空间。

### 仅所有者可用与共享的 Spaces

结合组织对 Space 共享的要求来做取舍：

- **仅所有者可用的 Spaces**：每个 Space 只有创建它的用户能访问。这是默认配置，适合团队在做敏感或彼此独立的项目。
- **共享的 Spaces**：多名团队成员访问同一个 Space，适合结对编程、协作调试或共用的开发环境。开启共享 Spaces 时，要确保 POSIX 权限和附加组配置到位，让 Space 内创建的文件能被恰当访问。

了解更多：[Amazon SageMaker HyperPod EKS 集群上的交互式开发环境](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-cluster-ide.html)

## HyperPod Training Operator

HyperPod Training Operator 让团队把分布式训练任务作为 Kubernetes 自定义资源提交（例如 HyperPodPyTorchJob）。在这套多租户架构里，训练任务按命名空间划定，会自动继承所在团队的隔离边界。

团队可以从 CLI 用 `kubectl apply` 加上合适的任务 manifest 提交训练任务。任务跑在本团队的命名空间里，消耗本团队的计算配额（前提是启用了 Task Governance），能访问的也是本团队的存储卷。

启用 Task Governance 后，训练任务受本团队配额与优先级设置的约束。团队用完了保证配给，任务就可能排队，等资源腾出来，或者等低优先级的工作负载被抢占。

把一个任务锚定到某个团队的要素有两个：`metadata.namespace`（把任务限定在团队的隔离边界内）和 Task Governance 标签。Task Governance 建立在 [Kueue](https://kueue.sigs.k8s.io/) 之上，因此任务通过 `kueue.x-k8s.io/queue-name` 被路由到本团队的本地队列；调度优先级则通过 `kueue.x-k8s.io/priority-class` 指定，取值是集群上定义的某个 `WorkloadPriorityClass` 的名字：

```
apiVersion: sagemaker.amazonaws.com/v1
kind: HyperPodPyTorchJob
metadata:
  name: team-a-training-job
  namespace: hyperpod-ns-team-a  # scopes the job to Team A's namespace
  labels:
    kueue.x-k8s.io/queue-name: hyperpod-ns-team-a-localqueue  # Task Governance (Kueue) local queue
    kueue.x-k8s.io/priority-class: training-priority  # name of a WorkloadPriorityClass
spec:
  ...
  # replicaSpecs, container image, command, resources, volumes, etc.
  ...
```

了解更多：[使用 HyperPod Training Operator](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-eks-operator.html)

## HyperPod Inference Operator

HyperPod Inference Operator 让团队把模型作为推理端点直接部署在集群上。和训练任务一样，推理端点按命名空间划定，受本团队的 RBAC 策略和 Task Governance 配额约束。

团队可以从 CLI 在本团队命名空间里创建推理端点的自定义资源来部署模型。端点按命名空间彼此隔离，Team A 访问不到、也干扰不了 Team B 的推理端点。

对可用性要求高的生产推理负载，考虑给推理端点配上比训练任务更高的调度优先级，让模型服务不被批量训练负载打断。

和训练任务一样，推理端点也放在本团队的 `metadata.namespace` 里，并带上 Task Governance 标签。这里的 `kueue.x-k8s.io/priority-class` 指向一个优先级更高的 `WorkloadPriorityClass`，这样团队资源吃紧时模型服务可以抢占批量训练：

```
apiVersion: inference.sagemaker.aws.amazon.com/v1
kind: InferenceEndpointConfig
metadata:
  name: team-a-inference-endpoint
  namespace: hyperpod-ns-team-a  # scopes the endpoint to Team A's namespace
  labels:
    kueue.x-k8s.io/queue-name: hyperpod-ns-team-a-localqueue  # Task Governance (Kueue) local queue
    kueue.x-k8s.io/priority-class: inference-priority  # higher-priority WorkloadPriorityClass
spec:
  ...
  # model source, instance type, replica count, autoscaling, etc.
  ...
```

## HyperPod Observability

集群健康、工作负载性能和资源利用率的可见性，对所有团队都是刚需。HyperPod Observability 借助 Amazon Managed Grafana 提供内置的监控与仪表盘能力。

### 配置团队对 Grafana 的访问

团队需要访问可观测性仪表盘，用来监控自己的工作负载、排查性能问题、弄清资源消耗。但在多租户环境里，这种访问通常应当是只读的：

- **为 Amazon Managed Grafana 配置 Identity Center 认证**：在 Amazon Managed Grafana 控制台进入 Authentication，启用 AWS IAM Identity Center。之后用户用登录 SageMaker Studio 的那套企业凭证就能登录 Grafana。
- **把团队组设为 Viewer**：将 Identity Center 的组（`TeamA`、`TeamB`）映射到 Grafana 的 Viewer 角色。团队成员因此获得仪表盘和指标的只读访问，但不能改动仪表盘或数据源。
- **管理员访问**：把 `Admin` 组分配到 Grafana 的 Admin 或 Editor 角色，让他们能创建和修改仪表盘、配置告警、管理数据源。
- **团队专属仪表盘**：考虑创建按命名空间过滤数据的专用仪表盘，让每个团队只看到自己工作负载的指标。Amazon Managed Grafana 支持 Grafana Teams（这是 Grafana 自身的 RBAC 概念，与本架构里说的组织团队不是一回事），可以从 Identity Center 组映射过来，用来收窄仪表盘的可见范围，再加一层数据隔离。

下图是 Amazon Managed Grafana 里的角色分配。团队组（`TeamA`、`TeamB`）分到 Viewer 角色，只读访问仪表盘和指标；管理员组分到 Admin 角色，可以创建和修改仪表盘、配置告警、管理数据源。

## 成本分摊与 chargeback

团队共用昂贵 GPU 基础设施的多租户环境里，搞清楚谁消耗了什么，是责任归属、预算编制和 chargeback 的前提。[Kubecost](https://github.com/kubecost) 满足的正是这个需求：它把集群内的开销按 Kubernetes 的原生概念（命名空间、标签、Deployment、Service）拆开，再映射到团队、项目、环境这类组织概念上。

这套架构本来就把每个团队隔离在专用命名空间里（`hyperpod-ns-team-a`、`hyperpod-ns-team-b`），所以命名空间级的成本分摊与团队边界天然对齐。平台管理员不用给工作负载加任何额外标签，就能清楚看到每个团队在 GPU、CPU、内存、存储和网络上的消耗。关于在 HyperPod 集群上部署和配置 Kubecost 的分步说明，参见 [SageMaker HyperPod 上的 Kubecost](https://awslabs.github.io/ai-on-sagemaker-hyperpod/docs/category/kubecost-on-sagemaker-hyperpod)。

### 开启团队侧的可见性

Kubecost 开始采集数据后，在 Allocations 仪表盘里按命名空间对成本分组，就能看到每个团队的支出。每个团队各占一个命名空间，于是直接得到一份覆盖计算、内存、存储和网络的按团队成本明细。和可观测性仪表盘一样，团队也能从看到自己的成本数据中获益：

- **把视图限定在各团队的命名空间**：Kubecost 支持按命名空间过滤和保存报表，每个团队可以查看自己的消耗与趋势，看不到其他团队的数据。
- **设置预算与告警**：为每个命名空间配置预算阈值和告警，支出逼近上限时团队和平台管理员都会收到通知，这与 HyperPod Task Governance 追求的资源公平目标一致。
- **支撑 chargeback 与 showback**：命名空间级的分摊报表可以直接喂给内部的 chargeback（按用量向团队结算费用）或 showback（只报用量、不计费）流程，让财务和平台团队拿到把共享 GPU 成本公平归到各团队头上所需的数据。

## 总结

这篇文章给出了在 Amazon SageMaker HyperPod（配合 EKS）上搭建多租户环境的参考架构。AWS IAM Identity Center 负责认证，按团队划分的 IAM 角色负责 AWS 层的授权，SageMaker AI 域提供贴合各自需求的工作台体验，Kubernetes 命名空间负责工作负载隔离，HyperPod Task Governance 负责公平的资源分配，命名空间级的成本分摊提供每个团队的支出可见性——这几样组合起来，多个团队就能高效共用一个 HyperPod EKS 集群。

这是一套灵活、可组合的做法，把若干积木拼成一个自洽的方案，能适配不同的使用场景和组织结构。例如，组织可以把这个模式扩展开，在 EKS 之外让团队接入 HyperPod Slurm 集群，在不同编排后端上提供一致的多租户体验。

这套做法确实要求你把若干组件拼装、配置起来，换来的是很高的控制度和可定制性，能够贴合每个组织在隔离、合规和运维上的具体要求。而其中那些基础模式——身份联邦、命名空间隔离、RBAC、基于配额的治理、成本分摊——会一直适用。

想动手，就在你自己的 Amazon SageMaker HyperPod EKS 集群上把这套多租户配置搭起来，按组织在隔离、治理和成本分摊上的要求调整这些积木。
