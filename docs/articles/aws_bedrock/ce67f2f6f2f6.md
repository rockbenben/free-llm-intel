# Amazon Bedrock AgentCore harness 新增 Strands harness 默认值、内置工具与生命周期钩子

构建 AI agent 时，选模型只是第一步。agent 还需要工具、完成任务的指令、在长会话里管理上下文增长的手段，以及在执行任何有后果的操作（比如发放退款）之前的一道护栏。

我们正在升级 Amazon Bedrock AgentCore harness，让它改用 Strands harness——这是我们今年早些时候发布的开源 agent harness，采用 Apache 2.0 许可证。AgentCore harness 还引入了生命周期钩子，让你可以在 agent 循环的指定节点运行自己的确定性检查与通知。

经过这次升级，依赖托管默认值的 agent 会得到一个推荐模型、一份面向任务的系统 prompt、自动 prompt 缓存（初期面向 Amazon Bedrock 上的 Anthropic 模型）以及主动上下文管理。它们还会获得额外的内置工具，覆盖规划、Web 检索、文件系统访问、上下文卸载和任务委派。这让 agent 在长任务中能力更强，能跟踪子任务、减少上下文窗口占用、把工作委派出去。借助钩子，你可以在特定的生命周期检查点运行确定性代码，把非确定性的 AI 行为变成可预测、安全、可治理的工作流。

不需要引入新的资源类型或集成。你已经在用的 AgentCore harness 会自动获得这两项更新。

## 在 AWS 上拿到 Strands 的能力

[Strands harness](https://strandsagents.com/docs/user-guide/harness/) 提供一套组装好的 agent 基础，包含推荐指令、工具和上下文管理。[Amazon Bedrock AgentCore harness](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness.html) 把这份基础作为托管 AWS 服务来运行。结果就是一个生产级默认 agent，你既不用自己组装 harness，也不用运维它的基础设施。

你不需要预置计算资源，不需要打包并托管 agent 循环，不需要管理会话扩缩容，也不需要运维工具执行的基础设施。每个会话都运行在 AgentCore runtime（Amazon Bedrock AgentCore 的一项能力）里一个安全、内核隔离的 microVM 中，计算、扩缩容和高可用性都由托管层负责。

AgentCore 的做法是把 harness 接到生产级 agent 所需的各种服务上，包括会话持久化、流式响应、用量元数据、可观测性、AgentCore memory、Identity、Gateway、Browser、Code Interpreter 以及客户自己提供的容器。模型、指令、工具、权限和生命周期策略仍由你掌控，AgentCore 只管底层的执行环境。

## 能力更强的托管 harness

当你使用 harness 的托管默认值时，现在的体验更强了：

- **当前推荐模型。** 省略模型时，Harness 会使用一个推荐默认模型；这个模型随新模型发布而演进，让你的 harness 始终保持最新。显式的 harness 级配置和单次调用级配置仍然优先。
- **面向任务的指令。** 托管系统 prompt 会引导 agent 收集相关上下文、使用合适的工具、一直做到任务解决、对失败或被拒绝的操作做出调整，并在报告完成之前先自查。默认系统 prompt 会随时间改进，以支撑最新的 harness 行为。
- **自动 prompt 缓存。** 对于在 Amazon Bedrock 上使用 Converse 的受支持模型，Harness 会缓存系统 prompt、工具定义和对话历史。用同样的 prompt 和工具集重复调用时，可以使用价格更低的缓存读取 token，从而降低输入处理延迟和成本。
- **主动上下文管理。** 默认情况下，一旦上下文窗口达到可配置的阈值，Harness 就会总结较早的对话轮次，同时保留近期上下文。这样把上下文保持精简，有助于 Harness [比其他领先 harness 低约 34% 的 token 成本](https://strandsagents.com/blog/we-ran-94000-trials-to-measure-the-cost-of-harness-choice/)运行。
- **上下文卸载。** 大型工具结果可以被移出模型当下的上下文。agent 会收到一份预览，需要时再取回完整结果，既减少了上下文的重复占用，又不丢失对数据的访问。
- **跨调用规划。** `todo_write` 工具维护结构化的任务计划，该计划可以在同一会话的后续调用中恢复，包括在对话总结之后。
- **聚焦式委派。** `subagent` 工具把一件自包含的任务交给一个全新的 worker，再把结果返回给父 agent。该 worker 属于调用内部，不是单独管理的 harness 资源，共享调用限制，也共享你的工具调用生命周期钩子。
- **Web 检索。** `web_fetch` 工具从指定网页取回内容，让你的 harness 获得最新的外部上下文。
- **细粒度文件系统访问。** 借助独立的 `read`、`write` 和 `edit` 工具，你可以只授予 agent 所需的那些细粒度文件系统能力。

客户提供的 Model Context Protocol (MCP) 服务器、AgentCore Gateway（Amazon Bedrock AgentCore 的一项能力）、Browser、Code Interpreter、内联函数、skills、memory 以及客户自己提供的容器，仍然可以通过现有的 harness 接口使用。

## 默认推荐，需要时可配置

Harness 会管理好自己的默认值，这样当模型、指令、上下文管理和内置能力改进时，使用这些默认值的 agent 就能获得 AgentCore 当下的推荐体验。

显式配置始终优先：

- 配置模型 ID，继续使用某个特定模型。
- 配置 `systemPrompt`，完全替换托管的系统 prompt。
- 配置 `truncation`，保留特定的上下文管理策略。
- 逐个列出 `allowedTools` 选择器，维持固定的工具集。

当 `allowedTools` 被省略或设为 `["*"]` 时，Harness 提供当前推荐的内置工具集。由于这个工具集会随时间增加能力，对安全或能力边界有固定要求的应用应当只列出自己需要的工具。

例如，下面这份配置只允许只读的文件系统访问和 Web 检索，不授予 shell 访问或修改文件的权限：

```
{
    "allowedTools": [
        "read",
        "web_fetch"
    ]
}
```

## 用生命周期钩子管控有后果的操作

借助生命周期钩子，你可以在 agent 循环的指定节点运行自己的确定性代码。例如，AWS Lambda 函数可以放行或拒绝一个请求或一次工具调用，Amazon Simple Notification Service (Amazon SNS) 主题或 Amazon EventBridge 事件总线则可以收到通知，用来记录活动或启动异步工作流。

Harness 支持四种生命周期事件：

| **事件** | **运行时机** | **Lambda 拒绝的影响** |
| --- | --- | --- |
| `before_invocation` | agent 处理请求之前 | 以 `hook_stopped` 停止本次调用 |
| `before_tool_call` | 模型提出工具调用之后、执行之前 | 跳过这次工具调用。agent 循环继续 |
| `after_tool_call` | 工具结果产生之后 | 保留结果，并在进一步推理之前停下 |
| `after_invocation` | 调用完成之后 | 报告决策。已经流式输出的内容无法收回 |

只有 Lambda 钩子能改变 agent 循环。它们同步运行，返回 allow 或 deny，可以附带一个原因。SNS 和 Amazon EventBridge 钩子只是通知，不会阻塞 agent 循环。

举个例子：一个客服 agent 可以自己去查订单，而 `before_tool_call` 钩子在退款工具运行之前，按审批限额逐笔核对退款。下面这份配置把这个 Lambda 函数挂到 harness 上：

```
[
    {
        "beforeToolCall": {
            "name": "refund_policy",
            "target": {
                "lambda": {
                    "arn": "arn:aws:lambda:us-west-2:123456789012:function:refund-policy",
                    "timeoutSeconds": 10,
                    "failureMode": "deny"
                }
            }
        }
    }
]
```

该函数在钩子负载中收到建议的工具调用，然后返回一个决策：

```
def lambda_handler(event, _context):
    tool = event["context"]
    if tool["toolName"] == "issue_refund" and tool["toolInput"]["amount"] > 500:
        return {"decision": "deny", "reason": "Refund exceeds the $500 auto-approval limit."}
    return {"decision": "allow"}
```

当函数拒绝这次调用时，harness 会跳过退款，agent 继续往下走，于是它可以告诉客户这个请求已经上报。每个决策还会以 `hookEvent` 的形式出现在 `InvokeHarness` 的响应流里：

```
{
    "hookEvent": {
        "name": "refund_policy",
        "type": "before_tool_call",
        "decision": "deny",
        "reason": "Refund exceeds the $500 auto-approval limit."
    }
}
```

钩子同样作用于 subagent。当 agent 委派任务时，subagent 发起的每次工具调用都会经过同一套 `beforeToolCall` 和 `afterToolCall` 钩子，所以委派绕不过你的退款策略。调用级钩子（`beforeInvocation`、`afterInvocation`）对整个调用只运行一次。

钩子通过 `CreateHarness` 或 `UpdateHarness` 配置。如果 Lambda 函数超时或返回错误，钩子会按其 `failureMode` 处理，默认是 deny。关于超时、负载字段和上下文限制，请参阅 [Amazon Bedrock AgentCore 开发人员指南](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-lifecycle-hooks.html)中的 Lifecycle hooks。

想看看所有事件和目标类型一起工作的样子，可以试一下 Amazon Bedrock AgentCore [GitHub 上的示例仓库](https://github.com/awslabs/agentcore-samples/tree/main/01-features/01-harness/02-use-cases/05-refund-desk-hooks)里的 Refund Desk 示例。六步引导式演示会走完四种生命周期事件，以及 AWS Lambda、Amazon SNS 和 Amazon EventBridge 三种目标。它还演示了如何校验客户端提供的内联函数结果，以及 `failureMode` 取 deny 与 allow 时的差别。

## 用 AgentCore CLI 跑一个多 agent 研究协调器

创建一个 harness 只需一条命令。你给它起个名字，再设好想要的指令、上下文策略和限制。下面这个例子创建一个 Research Coordinator：一个带面向任务系统 prompt、采用基于总结的截断策略的 harness。在一次调用中，它把 researcher、synthesizer 和 reviewer 作为 subagent 运行，最后返回一份汇总报告。你不用预置基础设施，也不用自己接委派逻辑，就能得到多 agent 编排和上下文管理。

`agentcore harness` 系列命令直接调用 harness API，所以你不需要 CLI 项目，也不需要部署步骤。用 npm 安装 AgentCore CLI（Amazon Bedrock AgentCore 的一项能力）：

```
npm install -g @aws/agentcore
```

CLI 使用你的默认 AWS 凭证。它没有 `--profile` 参数，所以要用特定配置文件时请设置 `AWS_PROFILE` 环境变量。把示例里协调器的指令保存为工作目录下的 `system_prompt.md`。

### 创建 harness

这条命令传入协调器的系统 prompt、一条在对话增长时保留最近 30 条消息不变的总结策略，以及足够跑完整个流程的限制值。因为它省略了模型、memory 和执行角色，harness 会使用 AgentCore 当前的推荐模型和托管 memory，CLI 则会替你在 IAM 里创建一个执行角色。

```
HARNESS_ID=$(agentcore harness create --region us-west-2 --json \
--name ResearchCoordinator \
--system-prompt "$(cat system_prompt.md)" \
--truncation '{"strategy":"summarization","config":{"summarization":{"summaryRatio":0.3,"preserveRecentMessages":30}}}' \
--max-iterations 100 \
--timeout-seconds 3600 \
| jq -r '.harness.harnessId')
```

创建是异步的。等它建完，最后一条命令应当输出 `READY`：

```
while [ "$(agentcore harness get --region us-west-2 --id "$HARNESS_ID" --json | jq -r '.harness.status')" = CREATING ]; do sleep 10; done

agentcore harness get --region us-west-2 --id "$HARNESS_ID" --json | jq -r '.harness.status'
```

### 发送 prompt

用一个新会话 ID 调用你的 harness。先问个简单问题。协调器会直接回答，不调用它的 subagent：

```
SESSION_ID=$(uuidgen)
agentcore harness invoke --region us-west-2 \
--id "$HARNESS_ID" \
--session-id "$SESSION_ID" \
--prompt "What is the current trending topic in AI?"
```

然后在同一个会话里要一份完整的研究报告。协调器会规划工作，按顺序委派给 researcher、synthesizer 和 reviewer。如果 reviewer 提出要求，它最多跑一个修订轮次，然后交付最终报告。复用会话 ID 就会在同一个环境里继续对话。

```
agentcore harness invoke --region us-west-2 \
--id "$HARNESS_ID" \
--session-id "$SESSION_ID" \
--prompt "Perform a full research report on how data shapes innovations in the tech industry. Use specialized subagents to complete this task. In the final output, clearly state which part each subagent was responsible for, followed by their specific findings."
```

带上 `--prompt` 时，CLI 会在这轮结束时把完成的对话记录以 JSON 打印出来。整次研究大约要跑 10 到 15 分钟。想边跑边看，就去掉 `--prompt`，CLI 会打开一个交互式聊天。

同一个示例的 Python (boto3) 版本，含完整的系统 prompt，可以在 GitHub 上的 AgentCore 示例仓库里找到。

### 清理

用完就把 harness 删掉。除非传入 `--delete-managed-memory false`，否则这也会删掉它的托管 memory。CLI 创建的执行角色会留在你的账户里，不再需要的话请到 IAM 控制台删除。

```
agentcore harness delete --region us-west-2 --id "$HARNESS_ID"
```

## 推出与兼容性

11 月 11 日起，AgentCore harness 开始向新的和已有的 harness 推出由 Strands harness 支撑的体验。客户无需做任何操作。

你显式提供的配置保持不变。省略模型、系统 prompt 或 `truncation` 配置的 harness，以及使用 `allowedTools: ["*"]` 的 harness，会获得升级后的托管默认值。

如果你的应用要求固定行为或固定的能力边界，请显式配置这些设置。
