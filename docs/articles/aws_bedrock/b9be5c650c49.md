# 使用 Amazon Textract 为 Amazon Bedrock 上的知识库定制处理大型复杂文档

对于每月处理数千张水电燃气账单（utility bill）的客服团队来说，准确解析并分析复杂的多页文档是一个长期难题。格式不一致、表格密集、版式多样，使得快速提取正确信息变得困难。这会导致响应延迟、账单错误和客户不满。随着文档量增长，这些低效会不断累积，使组织无法利用已经握在手中的数据。

与 [Amazon Textract](https://aws.amazon.com/textract/) 集成的 Amazon Bedrock 提供了解决这一问题的检索与生成能力。把 Amazon Textract 对结构化与非结构化内容的高精度提取能力，与 Amazon Bedrock 的生成式 AI 能力结合起来，组织就能从人工翻查文档，转向以编程方式查询文档。这可以大规模释放账单中的可执行洞察，并带来更快、更准确的客户交互。

本文将演示如何与复杂 PDF 和图片格式的账单“对话”：解析它们、分析内容，并给相关表格打上标签，以帮助大语言模型（LLM）提取最有用的信息。本文的代码可在 [GitHub](https://github.com/aws-samples/sample-agentic-rag-solution) 上找到。

## 用例概览

某客户支持团队会收到大量与账单相关的查询，涉及计费、用量、支付和客户服务等多个领域。这些查询以 PDF、DOCX、TXT、HTML 和 XLSX 等多种格式到达，团队难以高效地解析与分析。人工从这些文档中提取相关信息的流程耗时且容易出错，导致响应时间延迟和客户不满。

为解决该问题，客户最初尝试直接使用账单原文实现检索增强生成（RAG）方案。然而他们很快遇到了重大问题。用于从这些文档中提取信息的大语言模型（LLM）漏掉了关键细节，在某些情况下甚至产生幻觉，给出不正确或不相关的信息。这让客户意识到，直接把文档和账单以原始形态加载进去，无法得到可靠、准确的回答。

客服支持团队需要一个稳健的方案，从多种格式（PDF、DOCX、TXT、HTML、PNG 和 XLSX）的各类账单中准确提取并分析信息。团队的目标是构建一个基于 RAG 的方案，能够可靠地提取账号、账单明细和支付说明等相关信息，从而对客户查询给出准确、及时的答复。

客户最初的做法是把账单原文直接送入 RAG 模型。这种方法有几个缺点：

- **数据提取不完整：** LLM 难以提取全部必要信息，常常漏掉到期日、支付金额和账号等关键细节。
- **幻觉：** 模型偶尔生成不正确或不相关的信息，造成客服答复中的混乱与错误。
- **格式多变：** 账单的不同格式（PDF、DOCX、TXT、HTML、XLSX）给 LLM 带来挑战，导致它在不同文档类型上表现不一致。

观察到这些问题后，客户很快意识到需要更精细的做法。仅把原始文档载入 RAG 模型是不够的。团队需要一种方法对账单进行预处理与增强，使 LLM 能够准确提取并使用必要信息。

## 支持的文件类型

目前支持以下文件类型：PDF、DOCX、TXT、HTML、XLSX 和 PNG。

- **PDF（Portable Document Format）**。Amazon Textract 可以从多页 PDF 文档中提取文本，包括版式复杂、内嵌图片的文档。
- **DOCX（Microsoft Word Document）**。Amazon Textract 可以解析并提取 Word 文档中的文本，包括表格、图片和其他内嵌对象。
- **TXT（Plain Text Files）**。纯文本文件可以被解析以提取文本内容。
- **HTML（HyperText Markup Language）**。Amazon Textract 可以从 HTML 文件中提取文本，包括标签内的结构化数据。
- **XLSX（Microsoft Excel Spreadsheet）**。虽然主要用于文本提取，Amazon Textract 也能从 Excel 电子表格中提取文本，包括单元格内容与表格数据。
- **PNG（Portable Network Graphics）**。Amazon Textract 可以从 PNG 文件中提取文本。

## 解决方案概览

为应对这些挑战，客户可以选择把文本提取服务 Amazon Textract 与 Amazon Bedrock 集成。这种集成提供以下能力：

- **高级文本提取：** Amazon Textract 对账单进行预处理，从多种格式中提取文本并捕获所有相关信息。
- **数据清洗与增强：** 对提取出的数据进行清洗和增强，去除噪声与无关信息，只把最相关的细节送入 RAG 模型。
- **上下文理解：** Amazon Textract 借助上下文理解对提取的数据进行准确标注和打标签，让 LLM 更容易处理并生成准确的答复。

通过实施这一做法，客服团队希望构建一个更可靠的基于 RAG 的方案。该方案能够准确提取并使用账单中的信息，从而改善响应时间和客户满意度。

### 部署解决方案

为部署该方案，已经编写了一个 shell 脚本，用于创建 AWS CloudFormation 堆栈并按需部署方案所需的依赖资源。

运行该 shell 脚本，请按以下步骤操作：

- 从 [GitHub](https://github.com/aws-samples/sample-agentic-rag-solution) 克隆代码仓库。
- 进入 `custom-knowledge-base` 目录。
- 打开终端并运行 `bash custom_kb_deployment_setup.sh`。它会为你部署 AWS CloudFormation 堆栈。

该 CloudFormation 堆栈会在你的账户中创建以下资源：

- AWS Lambda 执行角色。
- 用于 Lambda 函数的 Lambda 层。
- 两个 Lambda 函数。
- 一个 Amazon Simple Storage Service（Amazon S3）存储桶。
- 一个 Amazon OpenSearch Serverless 集群。
- Amazon Bedrock Knowledge Bases。
- 用于 Amazon Bedrock 知识库的 AWS Identity and Access Management（IAM）角色。

## 部署后步骤

堆栈部署完成后，完成以下步骤来配置该方案。

### 配置 Amazon S3

- 打开 Amazon S3 控制台。
- 找到创建的、名为 `document-<stack-name>-<partial-stack-id>` 的 S3 存储桶。
- 创建名为 `raw_files` 的文件夹。
- 把仓库中提供的账单上传到 `raw_files`。

### 自动化处理

- 文件上传会触发 `document-parser` Lambda 函数。
- Amazon Textract 作业处理原始文件。
- 处理后的文件保存到 `parsed_files` 文件夹。
- 第二个 Lambda 函数把文件处理为 TXT 格式。
- 最终输出保存到 `parsed_kb_documents` 文件夹。

### 知识库设置

- 打开 Amazon Bedrock 控制台，导航到 **Amazon Bedrock Knowledge Bases**——用于构建检索增强生成方案的全托管能力。
- 在左侧导航窗格中，选择 **Knowledge Bases**。
- 选择新建的知识库。
- 选择 **Data source**。
- 选择该数据源，然后选择 **Sync**。
- 等待同步完成。

## 小结

本指南概述了使用 AWS 服务部署自定义知识库方案的流程。该方案使用 AWS CloudFormation 自动创建必要资源，包括 Lambda 函数、S3 存储桶、OpenSearch Serverless 集群和 Amazon Bedrock 知识库。部署流程会运行一个 shell 脚本，触发部署该方案所需的 CloudFormation 堆栈创建。

部署后步骤包括配置 S3 存储桶、上传样本文档，以及设置 Amazon Bedrock 知识库。该方案会自动处理上传的文档，把它们转换为适合知识库的格式。

## 结论

这个自定义知识库方案展示了如何集成多个 AWS 服务，构建智能的文档处理与查询系统。通过使用 CloudFormation 进行部署，该方案可在不同环境中创建一致、可重复的基础设施。从原始文件上传到知识库集成的自动化文档处理 pipeline，展示了可扩展、高效地处理大规模文档集合的潜力。

### 负责任 AI 的考量

在生产环境部署基于 RAG 的方案时，实施防护措施以获得可靠、可信的输出非常重要。[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 提供可配置的控制项，用于过滤有害内容、拦截被禁止的主题，并从输入和输出中抹除敏感信息。此外，grounding 校验通过评估模型回答是否得到检索到的源文档支持，帮助检测并减少幻觉。对于生产部署，我们建议开启这些控制项，以在知识库交互中保持准确性、合规性与用户信任。

该方案对那些处理大量结构化文档的组织尤其有价值，例如本文中的账单场景。它提供了一种精简的方式来提取、处理并查询这些文档中的信息，有可能提升运营效率并支持更复杂的数据分析。未来的增强可以包括扩展所处理的文档类型、与其他 AWS 服务集成以进行更复杂的分析，或开发易用的前端界面，让与知识库的交互更方便。

总体而言，对于希望在 AWS 上构建智能文档处理与查询系统的组织，该方案是一个扎实的起点，并且可以根据具体业务需求灵活定制与扩展。
