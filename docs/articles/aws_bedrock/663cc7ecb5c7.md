# 使用 Amazon Bedrock 和 AWS Lambda 构建 agentic 应用部署器

许多企业都有一长尾永远没被构建出来的内部工具。某个团队需要一个运费计算器、一个直白的录入表单、一个架在电子表格之上的小型看板，但每一个都需要一名开发者、一个 backlog 排期和一条部署 pipeline。这些工具太小，小到排不上优先级；又太多，多到无法忽视。

[PDI Technologies](https://pditechnologies.com/) 服务于便利店零售与石油批发行业，通过安全地连接企业的数据与运营，帮助全球各地的企业提升效率与盈利能力。PDI 拥有 40 年经验、约 4,000 名员工，为 200 多个国家和地区的超过 200,000 个客户网点提供服务。PDI 意识到，传统的部署 pipeline 正在阻碍非技术团队交付他们所需的工具。

为弥合这一缺口，PDI Technologies 构建了 PDI Brew。非技术员工用平实的英语描述他们想要的工具，几秒之内就会得到一个完全预置好的多租户 Web 应用，由单点登录（SSO）保护，运行在 AWS 上。不需要 Git、不需要终端，也不需要 DevOps 知识。需要工具的人，就是交付工具的人。由于每个应用都继承同一个平台，每一个都可以选择启用一项受治理的 AI 能力（对话、摘要、分类），其后端由 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 支撑。而这一切发生时，应用作者从未接触过模型端点或 API key。

在本文中，我们展示 PDI Technologies 如何围绕 [agentic 预置模式](https://aws.amazon.com/blogs/compute/effectively-building-ai-agents-on-aws-serverless/) 构建 PDI Brew。规划 agent 借助 AI 助手（例如 Claude、ChatGPT 或 Claude Code）中的一个 skill，或在 AWS 信任边界内通过一次 Amazon Bedrock 模型调用，把用户意图捕获为结构化的 manifest。随后，运行在 [AWS Lambda](https://aws.amazon.com/lambda/) 上的预置 agent 会分解该 manifest，对工作负载进行分类、选择工具，并在一次请求中[编排每一个下游 AWS 资源的创建](https://aws.amazon.com/blogs/machine-learning/streamline-workflow-orchestration-of-a-system-of-enterprise-apis-using-chaining-with-amazon-bedrock-agents/)。接着我们展示同一平台如何把应用内 AI 作为通往 Amazon Bedrock 的受治理、最小权限网关开放出来。我们描述架构、安全模型、Lambda 内部的长时运行预置步骤、AI guardrail 与预算设计，以及大规模运行这套系统的成本特征。

## 先决条件

要理解这个架构，熟悉以下 AWS 服务会有所帮助：AWS Lambda、Amazon API Gateway、Amazon DynamoDB、Amazon Simple Storage Service（Amazon S3）、Amazon CloudFront 和 Amazon Bedrock。认证相关章节还需要你具备 Microsoft Entra ID（原 Azure AD）和 MSAL.js 的经验。如果你打算在自己的环境中实现类似的模式，请确认已安装 AWS Command Line Interface（AWS CLI），并已配置具备足够权限、可创建 AWS Identity and Access Management（IAM）角色和策略的凭证。

## 内部工具的挑战

传统的内部工具交付方式，把一个直白的业务需求与完整的软件交付生命周期绑在一起。哪怕只是一个单页计算器，也要背上代码仓库、构建 pipeline、认证集成、托管选型、TLS 证书、DNS、日志以及持续维护的成本。结果就是一条永远排不完的小工具队列，它们总是被排在创收功能之后。

我们想要一个具备四项特性的系统：

- **输入意图，输出应用。** 需求方描述工具，平台负责预置。无需移交给工程团队。
- **默认安全且受治理。** 每个应用都继承企业 SSO、作用域受限的 IAM、HTTPS 和集中式可观测性。不存在“不安全”的路径。
- **Serverless 且可缩容至零。** 数百个小应用在空闲时必须几乎不产生成本，没有需要打补丁的共享服务器，也不需要规划容量。
- **AI 不是任人自取的。** 应用可以使用生成式 AI，但只能通过一条带有 guardrail、配额和完整审计轨迹的受控路径。绝不允许自行嵌入模型密钥。

## 解决方案概览

“Agentic” 并不一定意味着“每一次决策都要在请求路径上放一个大语言模型”。我们把 agent 定义为一个接收目标、分解目标、选择工具并朝该目标行动的系统。PDI Brew 把这一定义的两半拆成两个信任特征截然不同的 agent。

规划 agent 负责捕获意图。它会与用户访谈、帮助用户细化需求、生成应用前端，并且关键的一步是产出一份结构化的部署 manifest：一份用 JSON 描述用户意图的文档（应用名称、类型、data schema 以及访问控制设置）。规划逻辑被打包为 Vibe App Builder skill，运行在员工已经在用的任意 AI 助手之中。把规划器放在助手里运行，既能给用户一个丰富的对话式体验——在他们已经打开的某个工具里，又能让 AWS 一侧的暴露面保持很小。

预置 agent 是一个 [AWS Lambda](https://aws.amazon.com/lambda/) 函数。它接收 manifest，并充当一个确定性、可审计、会使用工具的编排者。它校验请求、对工作负载分类，并选择一条预置路径。然后它把 AWS 与 Microsoft Graph API 当作工具来调用，通过异步自调用处理长时步骤，并返回一个可用 URL。把预置逻辑放在 Lambda 而不是放在聊天会话里是有意为之：预置恰恰是那种每一个决策都必须被记录、可复现、且不能有幻觉的工作负载。

## 可插拔的规划器：自带 AI 助手

意图可以来自任何地方，因此规划器被设计成一个可插拔的层，包含两条可互换的路径。单个环境变量（`PLANNER_MODE`）决定哪一条处于激活状态，而两条路径产出的部署 manifest 完全相同，所以下游的一切都不用改。

路径 A——任意 AI 助手里的 Vibe Skill。Vibe App Builder skill（下文简称 Vibe Skill）打包了规划逻辑，运行在员工已经在用的任意 AI 助手之中。该助手与用户访谈、生成前端，并产出 manifest。规划器运行在 AWS 之外，从而让用户在他们已经打开的某个工具里获得丰富的对话式体验。

路径 B——AWS 信任边界内的 [Amazon Bedrock](https://aws.amazon.com/bedrock/)。对于 Teams、Web 表单或 IDE 这类渠道，请求会被发送到 Amazon Bedrock。一次 Bedrock 模型调用（`InvokeModel`）充当规划器：它对工作负载分类、产出同样的 manifest，并可在预置之前校验或修复 data schema。这条路径完全在 AWS 内部运行，因此每个决策都被记录进 [AWS CloudTrail](https://aws.amazon.com/cloudtrail/) 并与模型调用 ID 关联，且没有任何意图数据离开 AWS 边界。这对有严格数据驻留要求的团队很重要。

一份契约，一个预置 agent。由于两个规划器产出相同的 manifest JSON，Lambda 上的预置 agent 以及整个按应用划分的运行时都与路径无关、完全一致。新增 Bedrock 路径是一次增量改动，而不是重写。而且 `PLANNER_MODE` 可以按组织、工作区或用户固定，因此一家企业可以要求使用 Bedrock 路径，而另一家继续保留助手内的体验。它还留下了一条清晰的前进路径：日后可以把这次 Bedrock 调用替换为[更丰富的托管 agent 运行时](https://aws.amazon.com/blogs/machine-learning/getting-started-with-amazon-bedrock-agents-custom-orchestrator/)，而无需改动路径 A 或预置 agent。

## 架构

下图展示了端到端架构。它有三层：可插拔的意图与规划层、统一的 agentic 预置运行时，以及按应用划分的运行时，并由共享的边缘、身份和可观测性服务支撑。

![Vibe Deployer 架构，包含意图与规划层、基于 Lambda 的 agentic 预置运行时，以及按应用划分的运行时](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/07/28/ML-21066-1.png)

下面的演练将追踪一次请求穿过每一层的过程：

- 在**意图与规划层**，员工用平实的英语描述工具。取决于 `PLANNER_MODE`，规划器要么是运行在其助手中的 Vibe Skill（路径 A），要么是 Slack 或 Teams 这类渠道背后的 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 调用（路径 B）。无论哪种方式，规划器都以 JSON 形式产出相同的部署 manifest。
- manifest 通过 HTTPS 发送到 [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 上的 `POST /deploy`，并使用 Entra ID bearer token（MSAL.js）进行认证。由于两条规划器路径都汇聚到同一个端点和契约，从这里开始的一切都完全相同。
- API Gateway 调用 **Deploy Lambda（即预置 agent）**。它校验 Entra JWT（租户与过期时间）、强制要求请求中存在访问控制模式，并在应用注册表中原子性地检查 slug 归属。
- agent 对**工作负载进行分类**（static（计算器或图表）、full-stack（需要数据持久化）），并选择匹配的预置路径。
- 对于 **static 应用**，agent 把 HTML 包进一个 Entra 认证外壳，上传到 [Amazon S3](https://aws.amazon.com/s3/)，使 [Amazon CloudFront](https://aws.amazon.com/cloudfront/) 缓存失效，并在 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 中注册该应用。
- 对于 **full-stack 应用**，agent 还会预置一张按应用划分的 DynamoDB 表、一个按应用划分并带有作用域受限 [AWS IAM](https://aws.amazon.com/iam/) 角色的 [AWS Lambda](https://aws.amazon.com/lambda/) 函数，以及一个按应用划分的 API Gateway。随后它把新的 API URL 注入前端，再进行包装和上传。
- 长时步骤（例如创建 Microsoft 365 组）由**异步自调用**处理：agent 把自身的第二个副本作为后台任务调用，让用户的请求快速返回。
- 最终用户通过 CloudFront 以 HTTPS 访问线上应用，[CloudFront Function](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-functions.html) 把 `<slug>.domain` 路由到 S3 中正确的应用。每个应用都位于 Entra 单点登录之后，并可在 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 中观测。

## 预置 agent 的工作方式

预置 agent 执行两项核心功能：对工作负载分类，以及编排长时运行的预置步骤。

### 工具选择与工作负载分类

Deploy Lambda 把 AWS SDK for JavaScript v3 和 Microsoft Graph API 当作它的工具带。它依据 manifest 决定调用哪些工具、以什么顺序调用。static 应用只会触及 S3、CloudFront 和 DynamoDB 注册表。full-stack 应用还会驱动 DynamoDB 和 API Gateway，而对于带能力的应用，还会用到 Lambda 和 IAM。访问控制则会伸入 Microsoft Graph，创建并管理应用的 M365 组。分类是确定性的，并且完整记录日志：同一份 manifest 永远产出同一份计划。

### Lambda 内部的长时运行工作

有些预置步骤的耗时超过用户愿意等待同步请求的时间，尤其是创建 M365 组之后的目录传播。与其让请求一直挂着，agent 改用异步自调用：它对自己调用 `lambda:InvokeFunction`，调用类型为 `Event`，立即返回线上 URL，让后台副本完成慢速工作。这就是 agent“后台任务”模式在 serverless 中的等价实现，并且从容地保持在 Lambda 执行包络之内。

## 按应用划分的运行时：双层计算模型

并非每个应用都需要自己的计算资源。大多数 full-stack 应用都是对自身 DynamoDB 表的简单增删改查（CRUD）操作，因此它们运行在一个共享的、由平台管理的 CRUD Lambda 上，前面是一个带预置并发的加权别名。这样提供了一条热的、可审计的代码路径来服务众多应用，并带有自动的金丝雀回滚防护。只有当应用的 manifest 声明了封闭白名单中的某项能力时（例如发送电子邮件、调用特定的外部 HTTPS 域名，或从指定的数据源读取），该应用才会升级到拥有专属的、作用域受限 IAM 角色的按应用 Lambda。这种升级需要一步管理员审批。审批以对提交代码的静态分析，以及对生成 IAM 角色的漂移检测为依据。默认路径是共享且廉价的。特权路径是按应用划分、最小权限且需要闸门放行的。

## 受治理的应用内 AI

已部署的应用越来越想要 AI 功能：概括一条记录、对录入表单分类、就应用自身的数据回答问题。天真的做法是让每个应用各自嵌入模型厂商的 SDK 和一个 API key。这会让凭证四处散落、破坏集中治理，并使支出无法控制。PDI Brew 采取相反的做法：AI 是一项平台能力，通过一个端点访问，而不是每个应用各自拥有的集成。

每次调用前后都会运行三重控制。第一，一个强制的 [Amazon Bedrock Guardrail](https://aws.amazon.com/bedrock/guardrails/) 在每次调用时处理个人可识别信息（PII）脱敏、内容过滤和 prompt 注入防御。应用无法关闭它。第二，一个**12 计数器原子预算**强制执行支出上限。在任何 Bedrock 调用之前，一次 DynamoDB 的 `TransactWriteItems` 会在四个范围（global、app、user 和 app-user）上预留支出，每个范围跨三个窗口（每日、每周、每月）。十二个计数器中任何一个被突破，都会以 `429 Too Many Requests` 和一个指明触发限制的结构化响应体短路该请求。这让失控的成本——无论来自 bug、循环还是滥用——成为一个有界、可观测的事件，而不是一张意外的账单。管理员可以为应用所有者授予更高的应用范围预算。全局和每用户上限不能被所有者放宽。第三，一个**双层终止开关**让管理员的禁用始终压过所有者的启用，而且一个平台级标志可以在所有地方禁用 AI，因此平台团队保有一个独立于任何应用的硬性急停开关。

每次调用都会被审计（UPN、应用、模型、token 数量、预估成本和 guardrail 结果），因此支出与用量可以端到端地归因到具体的应用和用户。

## 安全与最小权限

由于该 agent 会预置基础设施，它的安全模型是设计中最重要的一部分。若干原则支配着它。

**IAM 层的纵深防御。** 预置 agent 持有创建资源所需的较宽权限。但它所创建的按应用 Lambda 函数继承的是一个独立的、作用域受限的角色，只能访问以 `pdi-brew-{env}-app-` 为前缀的 DynamoDB 表。该 agent 从不给已部署的应用授予超出其所需的权限，因此某个租户代码中的 bug 无法读取另一个租户的数据。

**每条路径都有身份。** 通往已部署应用的路线上不存在未认证的路由。部署 API 在预置之前校验 Entra JWT，而每个生成的应用都被包在一个 MSAL.js 认证外壳中，每次访问时都通过 Microsoft Graph 检查 **Microsoft 365 组成员资格**。

*关于身份提供方的说明：本架构使用 Microsoft Entra ID 配合 MSAL.js 进行认证，而不是 Amazon Cognito。这是由 PDI Technologies 现有企业 SSO 需求驱动的有意设计选择。PDI 的员工已经通过 Microsoft Entra ID 进行认证。直接与其既有的身份提供方集成，降低了最终用户的使用摩擦，也与现有安全策略保持一致。对于没有既有身份提供方偏好的组织，[Amazon Cognito](https://aws.amazon.com/cognito) 提供了一个与 AWS 服务原生集成、并支持类似联合登录流程的替代方案。*

AI 在设计上就是最小权限的。AI Lambda 角色授予 `bedrock:InvokeModel` 和 `InvokeModelWithResponseStream`，按资源限定为白名单中的模型 ARN（而不是 `*`），账户中其他任何东西都不能调用 Bedrock。Lambda 函数没有 Bedrock 权限，只能通过网关以 HTTPS 访问 AI，而 guardrail 和预算就在那里生效。

额外的控制措施在每个已部署应用上强化了安全姿态。Amazon S3 的公有访问被完全封锁。只有 CloudFront（通过 Origin Access Control）可以读取对象。CloudFront 通过 HSTS 和严格的 Content-Security-Policy 强制重定向到 HTTPS。API Gateway 对部署端点限流（持续每秒 50 个请求，突发 100 个）。Amazon S3 版本控制和 DynamoDB 时间点恢复可防止数据丢失，而防销毁生命周期规则守护着注册表和存储桶。

## Serverless 原生的多租户

每个已部署的应用都是一个租户，架构为每个租户提供自己的子域名（由 CloudFront Function 路由）、在适用情况下自己的 DynamoDB 表，以及一个限定于自身数据的 Lambda 角色。没有共享计算，也没有嘈杂邻居风险；而且由于每个组件都是 serverless，每个租户在空闲时都独立缩容至零。在有人使用之前，新增第一百个应用几乎不产生任何成本。

## 可观测性

预置 agent 和每个按应用 Lambda 函数都会把结构化 JSON 日志写入 Amazon CloudWatch。`PDIBrew` 命名空间中的自定义指标跟踪部署次数、应用浏览、认证失败、组与列表创建以及预置延迟。一个管理面板通过 Amazon CloudWatch Logs Insights 查询按应用划分的活动，Grafana 仪表板则可视化平台范围的用量。预置调用会出现在 AWS CloudTrail 中，而当 Bedrock 规划器（路径 B）处于激活状态时，每个规划决策也会作为一次 `InvokeModel` 调用记录在 CloudTrail 中，从而给出从意图到已预置资源的端到端审计轨迹。

## 成本

这套技术栈中的每个服务都是按用量付费、没有固定成本，因此平台的价格跟随实际用量，而不是已部署应用的数量。

| **服务** | **你为以下内容付费** |
| --- | --- |
| Amazon S3 | 存储（$0.023/GB）+ 请求 |
| Amazon CloudFront | 数据传输 + 请求 |
| AWS Lambda（部署 + 按应用） | 调用次数 + 持续时间 |
| Amazon DynamoDB | 按需读写请求单位 |
| Amazon API Gateway | 每百万请求 $3.50 |
| Amazon Bedrock（路径 B 规划器） | 按 token 的 InvokeModel 定价，按每次部署计 |

在实践中，一个 20 人团队运行约 10 个应用，成本大致为**每月 $5–$15**。

## 成果

自发布以来，PDI Brew 已扩展到服务整个组织内的数百个应用，与传统的订阅制工具相比带来了显著的成本节约。真正非凡之处在于，部署不再局限于工程团队。非开发者如今可以独立编写并部署应用，并通过 Entra UPN 打标进行追踪，这说明由 AI 驱动的工具化把创作权大幅扩展到了传统开发团队之外。按 PDI Technologies 的经验，过去需要数周的事情（在工单、基础设施预置和构建流程之间来回周旋）缩短到了几分钟——这是按 Deploy Lambda 的时间戳衡量的。成本经济性同样引人注目。该平台实现了可观的成本效率，空闲时的每应用成本显著低于传统订阅制工具。

在运营层面，该平台实现了真正的自给自足。部署者通过 S3 版本控制的托管独立管理和回滚自己的应用，日常维护无需依赖其他团队。应用的生命周期通过一段时间内的 AppViews 来跟踪，使 PDI 能够区分持久的业务工具与一次性的实验，并衡量长期的组织价值。

该平台还解锁了以往用订阅制工具无法实现的用例。由于 PDI Brew 完全运行在 PDI 自有云与身份边界之内，它可以承载数据不得离开组织边界的受监管、敏感数据工作负载。AI 作为内置的平台能力交付：Amazon Nova [在 Amazon Bedrock 中可用的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards.html) 以共享 guardrail 和按应用 token 上限的方式开放，消除了通常拖慢企业内 AI 采用的项目级模型采购开销。

## 结论

PDI Brew 表明，agentic 预置模式可以干净地映射到 serverless AWS 原语上。一个可插拔的规划器（任意助手中的 Vibe Skill，或对 Slack、Teams 这类渠道而言位于 AWS 信任边界内的 Amazon Bedrock）把平实的英语意图转成结构化的 manifest。随后，AWS Lambda 上的预置 agent 把该 manifest 变成一个完全预置好、已认证的多租户应用。这套技术栈使用 AWS Lambda、Amazon API Gateway、Amazon DynamoDB、Amazon S3 和 Amazon CloudFront 作为“平台即产品”的构件。那些让 Lambda 成为出色 API 运行时的特性（无状态、可缩容至零、IAM 作用域受限、可观测），也让它成为预置 agent 的出色运行时——而在预置 agent 里，确定性与可审计性最为重要。

许多手头积压着内部工具的组织都可以复用这些模式：在单一的 manifest 契约之后把规划器与预置 agent 解耦，让意图可以从任意助手或渠道到达。让预置保持确定性且最小权限，并让 serverless 负责多租户与缩容至零。要开始在 serverless AWS 上构建 agent，请参阅关于 agentic AI 架构的 [AWS Prescriptive Guidance](https://aws.amazon.com/prescriptive-guidance/agentic-ai/)、[AWS Samples](https://github.com/aws-samples/)、[Amazon Bedrock 开发者指南](https://docs.aws.amazon.com/bedrock/latest/userguide/)，以及 [AWS AI/ML 博客](https://aws.amazon.com/blogs/machine-learning/)。
