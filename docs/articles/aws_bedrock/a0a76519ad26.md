# 使用 Amazon Bedrock prompt caching 为 Anthropic 模型优化成本与延迟

当你反复把相同的上下文发送给基础模型时，Amazon Bedrock 中的 prompt caching 最多可将输入 token 成本降低 90%（依据 [Amazon Bedrock prompt caching 定价](https://aws.amazon.com/bedrock/pricing/)）。如果不做缓存，一份 10,000 token 的合同随 50 个用户问题一起发送，就意味着 500,000 个输入 token 要按全价计费，而这些内容模型其实已经处理过了。

***编辑说明（2026 年 10 月）：** 本文已更新，以明确其适用范围。文中描述的 prompt caching 模式、代码示例和定价假设适用于 Amazon Bedrock 上支持显式 prompt caching 的 Anthropic 模型。开放权重模型不在本文讨论范围之内。*

*此外，本文中的缓存模式同样适用于 Amazon Bedrock 上的 **Anthropic Claude Sonnet 5.5 和 Claude Opus 5.5**。这两个模型都通过 Converse API 支持针对 system prompt、消息内容和工具定义的显式 prompt caching，使用的是示例中展示的同一套 `cachePoint` 语法。它们最多支持四个缓存检查点、最小累计 prompt 前缀为 512 token，TTL 可选 5 分钟或 1 小时。要使用这些模型，请在你的应用中更新模型 ID 和模型特定的推理设置。有关最新支持的模型和缓存限制，请参阅 [Amazon Bedrock prompt caching 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)。*

*对于**开放权重模型**，prompt caching 的可用性与行为因模型、API 和端点而异，具体如 Amazon Bedrock 文档所述。例如，[Mistral Large 3](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-mistral-ai-mistral-large-3.html) 在 `bedrock-runtime` 端点上支持隐式 prompt caching，它会自动尝试复用符合条件的 prompt 前缀，无需显式的缓存检查点。开放权重模型不在本文讨论范围之内，本文给出的显式缓存配置、代码示例和定价假设并不直接适用于它们。请查阅模型自己的文档，了解其支持的缓存机制与 API。*

你可以通过缩短 prompt、减小上下文窗口或在应用层实现缓存来缓解这个问题。每种方案都各有权衡：

- **缩短 prompt** 能减少 token 数量，但也可能降低上下文质量。
- **更小的上下文窗口** 降低了成本，代价是模型对完整信息进行推理的能力。
- **响应缓存** 能很好地处理完全相同的查询，但当同一份上下文配上不同的问题时就毫无收益。

Amazon Bedrock 中的 prompt caching 有助于在基础设施层面缓解这一挑战。当你缓存对话上下文的一部分（system prompt、文档、工具定义）时，Amazon Bedrock 会在后续请求中直接读取缓存的 token，而不是重新处理它们。这可以降低首 token 时间（time-to-first-token，TTFT），并在缓存命中时把缓存输入 token 的成本最多降低 90%，同时不改变你的模型或 prompt 质量。

本文通过 Amazon Bedrock 中的 Converse API 讲解六个实用的 prompt caching 场景，从基础模式逐步过渡到高级模式：

- **消息内容缓存**：为多问题分析缓存长文档。
- **System prompt 缓存**：跨对话缓存人设定义与指令。
- **工具定义缓存**：为 agentic 工作流缓存工具 schema。
- **混合 TTL 缓存**：为不同内容层级分配不同的缓存生命周期。
- **租户隔离**：在多租户应用中实现按租户分离的缓存。
- **LangChain 集成**：在 LangChain 框架中使用 prompt caching。

## prompt caching 的工作原理

prompt caching 会存储部分已处理输入的快照，使后续具有相同前缀的请求跳过重复计算。本节介绍请求流程、支持的模型以及定价。

当你在请求中包含 `cachePoint` 标记时，Amazon Bedrock 会评估该标记之前的内容是否与已有的缓存条目匹配。如果匹配（*缓存命中*），模型就可以跳过对这些 token 的重复处理，并从缓存状态开始生成。如果不存在匹配（*缓存未命中*），模型会处理全部内容，并把结果写入缓存，供将来可能的请求使用。

图 1：prompt caching 请求流程，其中第一个请求写入缓存，第二个请求从缓存读取，从而降低 TTFT 与输入 token 成本

理解这一流程之后，有四个关键概念决定了缓存的实际行为：

- **缓存范围**：缓存条目的作用域是单个 AWS 账户和 AWS 区域。
- **token 阈值**：每个缓存检查点必须满足最低 token 阈值才会生效。例如，Anthropic Claude Sonnet 4.5 和 Sonnet 4.6 每个检查点至少需要 1,024 个 token，而 Opus 模型至少需要 4,096 个。
- **存活时间（TTL）**：缓存条目会按请求中指定的 TTL 过期。默认是 5 分钟，部分模型最多支持 1 小时。
- **与模型无关的语法**：Converse API 的 `cachePoint` 语法在受支持的模型系列之间完全一致，包括 Anthropic Claude 和 Amazon Nova。

有关最新的模型支持信息，请参阅 [Amazon Bedrock Prompt Caching 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)。

### 定价

除标准的输入和输出 token 之外，prompt caching 还引入了两个 token 类别：

| **token 类型** | **说明** | **相对标准输入的成本** |
| --- | --- | --- |
| `cacheWriteInputTokens` | 写入缓存的 token（首次请求） | 比标准输入高 25% |
| `cacheReadInputTokens` | 从缓存读取的 token（后续请求） | 比标准输入低 90% |
| `cacheWriteInputTokens (1-hour TTL)` | 以 1 小时 TTL 写入缓存的 token | 比标准输入高 100%（2 倍） |

对于上下文重复的工作负载，输入 token 成本可节省约 75%。例如，如果你把一份 10,000 token 的文档配上 10 个不同的问题发送，第一个请求会产生一次缓存写入成本，其余九个请求各自以降低 90% 的成本从缓存读取，最终在该文档上下文的输入 token 成本上净节省约 75%。这假设所有后续请求都发生在 TTL 窗口之内。过期之后的请求会触发一次新的缓存写入，从而降低净节省幅度。详细定价信息请参阅 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)。

## 场景 1：消息内容缓存

prompt caching 的一个常见用例是缓存你反复查询的长文档或参考内容。例如，在检索增强生成（Retrieval Augmented Generation，RAG）应用中，你会针对同一份文档提出多个问题；又或者编码助手需要引用一个大型代码库。

在这个场景中，你把 `cachePoint` 标记放在静态文档与动态问题之间。Amazon Bedrock 会在首次调用时缓存该文档，并可能在后续调用中复用它。

### 消息内容缓存的工作原理

把 `cachePoint` 内容块放在静态内容之后、动态问题之前。Amazon Bedrock 会缓存检查点之前的所有内容，并在后续请求中复用：

```
content = [
    {"text": "<static document content>"},
    {"cachePoint": {"type": "default"}},   # cache everything above
    {"text": "<user question>"}             # dynamic, changes per request
]
```

接下来，定义缓存函数。关键元素是放在静态文档与动态问题之间的 `cachePoint` 块：

```
def converse_with_cache(document, question):
    """Query a document with prompt caching enabled."""
    content = [
        {"text": document},
        {"cachePoint": {"type": "default"}},
        {"text": question}
    ]

    response = bedrock.converse(
        modelId=MODEL_ID,
        messages=[{"role": "user", "content": content}],
        inferenceConfig={"maxTokens": 512}
    )
    return response["usage"]
```

运行两次请求来观察缓存行为。第一次调用会填充缓存，随后改用不同问题的一次调用会复用它：

```
# Request 1: cache write (first time seeing this content)
usage1 = converse_with_cache(DOCUMENT, "What are the key points?")
print("Request 1 (cache write expected):")
print(json.dumps(usage1, indent=2))

time.sleep(1)

# Request 2: cache read (same document, different question)
usage2 = converse_with_cache(DOCUMENT, "Summarize the conclusions.")
print("\nRequest 2 (cache read expected):")
print(json.dumps(usage2, indent=2))
```

### 读取缓存指标

响应中的 `usage` 对象包含两个缓存专用字段：

| **字段** | **说明** |
| --- | --- |
| `cacheWriteInputTokens` | 写入缓存的 token（首次请求中出现） |
| `cacheReadInputTokens` | 从缓存读取的 token（后续请求中出现） |

在我们使用 Anthropic Claude Sonnet 4.5 和一份超过 1,024 token 的文档进行的测试中，初始响应显示的是一次缓存写入：

```
{
  "inputTokens": 28,
  "outputTokens": 253,
  "cacheWriteInputTokens": 1898,
  "cacheReadInputTokens": 0
}
```

使用相同文档前缀的后续请求则产生一次缓存读取：

```
{
  "inputTokens": 28,
  "outputTokens": 294,
  "cacheWriteInputTokens": 0,
  "cacheReadInputTokens": 1898
}
```

注意，`cacheReadInputTokens` 现在反映的是从缓存读取的 1,898 个 token。整个文档前缀都被复用，没有再重新处理。只有 28 个 token（即问题本身）作为标准输入被处理。这些缓存 token 按降低后的缓存读取费率计费（比标准输入低 90%）。

### 简化缓存管理

Amazon Bedrock 上的 Claude 模型支持*简化的缓存管理*。你可以只放一个 `cachePoint`，Amazon Bedrock 会自动在该标记之前最多约 20 个内容块的范围内检查前缀是否命中缓存。你不需要手动放置多个缓存检查点，就能让对话中更早的部分命中缓存。

如果需要更细粒度的控制，你可以在每段内容之后放置多个 `cachePoint` 标记：

```
content = [
    {"text": SECTION_1},
    {"cachePoint": {"type": "default"}},
    {"text": SECTION_2},
    {"cachePoint": {"type": "default"}},
    {"text": SECTION_3},
    {"cachePoint": {"type": "default"}},
    {"text": QUESTION}
]
```

这种做法支持部分缓存命中。如果只有前两段与之前的请求匹配，模型会复用这两段的缓存并处理剩余内容。

### 流式变体

同一套缓存语法也适用于 `converse_stream`。关键区别在于：缓存指标不是在即时响应中返回，而是在流的末尾通过 `metadata` 事件送达：

```
def converse_stream_with_cache(document, question):
    content = [
        {"text": document},
        {"cachePoint": {"type": "default"}},
        {"text": question}
    ]

    response = bedrock.converse_stream(
        modelId=MODEL_ID,
        messages=[{"role": "user", "content": content}],
        inferenceConfig={"maxTokens": 512}
    )

    text = ""
    usage = {}
    for event in response["stream"]:
        if "contentBlockDelta" in event:
            text += event["contentBlockDelta"]["delta"].get("text", "")
        elif "metadata" in event:
            usage = event["metadata"].get("usage", {})

    return usage, text
```

### TTFT 基准测试

为了量化延迟改进，你可以测量启用与不启用缓存时的 TTFT：

```
def measure_ttft(document, question, use_cache=True, iterations=5):
    """Measure TTFT using ConverseStream."""
    ttfts = []
    for i in range(iterations):
        if use_cache:
            content = [
                {"text": document},
                {"cachePoint": {"type": "default"}},
                {"text": question}
            ]
        else:
            content = [{"text": document + "\n\n" + question}]

        start = time.time()
        response = bedrock.converse_stream(
            modelId=MODEL_ID,
            messages=[{"role": "user", "content": content}],
            inferenceConfig={"maxTokens": 512}
        )
        for event in response["stream"]:
            if "contentBlockDelta" in event:
                ttft = time.time() - start
                ttfts.append(ttft)
                for _ in response["stream"]:
                    pass
                break
        time.sleep(0.5)
    return ttfts
```

prompt caching 可以降低 TTFT，而且缓存前缀越大，收益越明显。对于较小的文档（约 2,000–5,000 token），在迭代次数较少时改进可能不具备统计显著性。具体的改进幅度取决于文档大小、模型和当前负载。对于较大的缓存前缀（超过 10,000 token），TTFT 的降低会更加明显。

## 场景 2：System prompt 缓存

许多应用使用详细的 system prompt 来定义模型的人设、准则和领域专长。这些 system prompt 可能长达数千 token，并在用户交互之间保持不变。使用 system prompt 缓存，你只需支付一次完整的处理成本，之后每一条消息都复用已缓存的 system prompt。

缓存点位于 `system` 参数内部，与用户消息分开。

### 配置

Converse API 的 `system` 参数接受一个内容块数组。把 `cachePoint` 放在 system 文本之后：

```
system = [
    {"text": "<detailed system prompt>"},
    {"cachePoint": {"type": "default"}}
]
```

下面这个缓存函数把 `cachePoint` 放在 `system` 参数中，使它与用户消息保持分离：

```
def converse_system_cached(question):
    response = bedrock.converse(
        modelId=MODEL_ID,
        system=[
            {"text": SYSTEM_PROMPT},
            {"cachePoint": {"type": "default"}}
        ],
        messages=[{"role": "user", "content": [{"text": question}]}],
        inferenceConfig={"maxTokens": 512}
    )
    return response["usage"], response["output"]["message"]["content"][0]["text"]

# Request 1: cache write
usage1, _ = converse_system_cached("What are the most promising locations for finding microbial life?")
print("Request 1 (cache write expected):")
print(json.dumps(usage1, indent=2))

time.sleep(1)

# Request 2: different question, same system prompt (cache read)
usage2, _ = converse_system_cached("How do gravitational waves help us study the universe?")
print("\nRequest 2 (cache read expected, different user question):")
print(json.dumps(usage2, indent=2))
```

用户消息在请求之间会变化，但 system prompt 保持完全一致。Amazon Bedrock 的设计就是要缓存 system prompt 前缀并复用它，无论用户问的是什么。

### 何时使用 system prompt 缓存

system prompt 缓存非常适合以下场景：

- **基于人设的助手**，带有详细的角色描述与行为准则。
- **agentic 工作流**，其大量指令在各轮之间保持不变。
- **客服机器人**，带有复杂的公司政策与响应流程。
- **特定领域的助手**，在 system prompt 中内嵌了知识库。

## 场景 3：工具定义缓存

agentic 应用常常定义几十个工具，每个都带有完整的 JSON schema。这些工具定义加起来可能包含数千 token，而且在请求之间很少变化。工具定义缓存可以避免在每一轮重复处理这些 schema。

### 设置

在 `toolConfig` 内的 `tools` 数组末尾追加一个 `cachePoint` 作为最后一个元素：

```
toolConfig = {
    "tools": [
        {"toolSpec": {"name": "tool_1", "description": "...", "inputSchema": {"json": {...}}}},
        {"toolSpec": {"name": "tool_2", "description": "...", "inputSchema": {"json": {...}}}},
        {"cachePoint": {"type": "default"}}   # after the tool definitions
    ]
}
```

我们把定义转换成 Converse API 的工具格式，并追加 `cachePoint`：

```
def build_converse_tools():
    """Convert tool definitions to Converse API format with cache point."""
    tools = []
    for tool in TOOLS_LIST:
        tools.append({
            "toolSpec": {
                "name": tool["name"],
                "description": tool["description"],
                "inputSchema": {"json": tool["input_schema"]}
            }
        })
    # Append cachePoint after the tool specs
    tools.append({"cachePoint": {"type": "default"}})
    return tools


def converse_tools_cached(question):
    response = bedrock.converse(
        modelId=MODEL_ID,
        messages=[{"role": "user", "content": [{"text": question}]}],
        toolConfig={"tools": build_converse_tools()},
        inferenceConfig={"maxTokens": 512}
    )
    return response["usage"]

# Request 1: cache write

print("Request 1 (cache write expected):")
print(json.dumps(usage1, indent=2))

time.sleep(1)

# Request 2: different question, same tools (cache read)
usage2 = converse_tools_cached("Calculate the escape velocity from Mars.")
print("\nRequest 2 (cache read expected):")
print(json.dumps(usage2, indent=2))
```

工具定义缓存适用于那些在许多对话轮次中调用同一组工具的 agentic 工作流。只要把工具 schema 缓存一次，就能避免在每一轮重复处理数千 token 的 schema 定义。

## 场景 4：混合 TTL 缓存

缓存内容并不只有一种生命周期。核心参考资料（领域知识、产品目录、合规规则）很少变化，适合更长的缓存时长。会话特定的上下文（最近的对话轮次、用户偏好）变化更频繁，适合更短的过期时间。借助混合 TTL 缓存，你可以在单个请求内为不同的内容层级指定不同的过期时间。

### 方法

每个 `cachePoint` 都可以包含一个 `ttl` 字段。只有一个顺序约束：在请求中，TTL 更长的检查点必须出现在 TTL 更短的检查点之前：

```
content = [
    {"text": "<core reference material>"},
    {"cachePoint": {"type": "default", "ttl": "1h"}},    # longer TTL first
    {"text": "<session-specific context>"},
    {"cachePoint": {"type": "default", "ttl": "5m"}},    # shorter TTL second
    {"text": "<user question>"}
]
```

### 理解 cacheDetails

Converse API 的响应包含一个 `cacheDetails` 字段，用于展示按 TTL 划分的 token 明细。这能显示两个 TTL 层级是否都在正常工作。当两个部分都独立超过模型的最低 token 阈值时，你会看到每个 TTL 对应一条记录：

```
"cacheDetails": [
    {"ttl": "1h", "inputTokens": 1547},
    {"ttl": "5m", "inputTokens": 1823}
]
```

如果只有一个部分超过阈值，响应只会显示一条 TTL 记录。每个内容层级都必须独立满足模型的最低 token 要求，才能为每个 TTL 获得各自独立的缓存条目。

### TTL 的顺序约束

在单个请求内，缓存检查点必须按 **TTL 从最长到最短** 的顺序排列。如果较短的 TTL 出现在较长的 TTL 之前，API 会返回错误：

- ✅ 有效：`1h` 在前，`5m` 在后。
- ❌ 无效：`5m` 在前，`1h` 在后。

该约束适用于所有缓存检查点位置（messages、system prompt 和工具定义）。

### 何时使用混合 TTL

下表根据内容变化的频繁程度，把内容类型映射到推荐的 TTL：

| **内容类型** | **推荐的 TTL** | **示例** |
| --- | --- | --- |
| 领域知识 | 1 小时 | 产品目录、合规规则、参考文档 |
| 会话上下文 | 5 分钟 | 最近的对话轮次、用户偏好、会话状态 |
| 工具定义 | 1 小时 | 很少变化的 API schema、函数签名 |
| 动态数据 | 不缓存 | 实时数据、用户特定的查询 |

在配置好混合 TTL 之后，下一个场景要解决一个常见的多租户难题：防止一个租户的缓存内容被另一个租户读取。

## 场景 5：租户隔离

在多租户应用中，你必须防止一个租户的缓存内容被另一个租户读取。Amazon Bedrock 中的 prompt caching 按账户和区域划定条目范围，但在同一账户、同一区域内，缓存条目可能会在请求之间共享。SHA-256 哈希前缀模式只需约 16 个 token 的开销就能实现租户隔离，无需使用独立的 AWS 账户。

### 模式

把 `tenant_id` 的 SHA-256 哈希前置到缓存内容之前。由于哈希改变了内容前缀，Amazon Bedrock 会为每个租户创建独立的缓存条目：

```
import hashlib

sha256_hash = hashlib.sha256(tenant_id.encode()).hexdigest()
instructions = f"{sha256_hash}:{instructions}"
```

### 实现

下面的函数把 SHA-256 租户前缀应用到缓存内容上：

```
import hashlib

def chat_with_document(document, user_query, tenant_id):
    """Chat with a document using tenant-isolated prompt caching."""
    instructions = INSTRUCTIONS  # detailed analysis instructions

    if tenant_id:
        sha256_hash = hashlib.sha256(tenant_id.encode()).hexdigest()
        instructions = f"{sha256_hash}:{instructions}"

    document_content = f"Here is the document: <document>{document}</document>"

    response = bedrock.converse(
        modelId=MODEL_ID,
        messages=[{
            "role": "user",
            "content": [
                {"text": instructions},
                {"text": document_content},
                {"cachePoint": {"type": "default"}},
                {"text": user_query}
            ]
        }],
        inferenceConfig={"maxTokens": 500, "temperature": 0}
    )

    usage = response["usage"]
    text = response["output"]["message"]["content"][0]["text"]
    return usage, text
```

你可以检查跨租户的隔离行为：

```
# Tenant 1: first request (cache write)
usage, _ = chat_with_document(DOCUMENT, "What is prompt caching?", tenant_id="tenant1")
print("Tenant 1, Request 1 (cache write expected):")
print(json.dumps(usage, indent=2))

# Tenant 1: second request (cache read)
usage, _ = chat_with_document(DOCUMENT, "What are the use cases?", tenant_id="tenant1")
print("Tenant 1, Request 2 (cache read expected):")
print(json.dumps(usage, indent=2))

# Tenant 2: first request (separate cache write)
usage, _ = chat_with_document(DOCUMENT, "What is prompt caching?", tenant_id="tenant2")
print("Tenant 2, Request 1 (cache write expected, separate from tenant1):")
print(json.dumps(usage, indent=2))

# Tenant 2: second request (reads from tenant2's cache)
usage, _ = chat_with_document(DOCUMENT, "What are the use cases?", tenant_id="tenant2")
print("Tenant 2, Request 2 (cache read expected):")
print(json.dumps(usage, indent=2))
```

这四次请求的预期行为如下：

| **请求** | **租户** | **预期的缓存行为** |
| --- | --- | --- |
| 1 | tenant1 | `cacheWriteInputTokens > 0`（新建缓存条目） |
| 2 | tenant1 | `cacheReadInputTokens > 0`（复用 tenant1 的缓存） |
| 3 | tenant2 | `cacheWriteInputTokens > 0`（新条目，哈希前缀不同） |
| 4 | tenant2 | `cacheReadInputTokens > 0`（复用 tenant2 的缓存） |

这一模式有三个优点：

- **无需服务端配置**：完全通过内容前缀实现隔离。
- **每个租户拥有独立的缓存条目**：各租户的缓存内容彼此分开。
- **开销极小**：SHA-256 哈希只为 prompt 增加 64 个字符（约 16 个 token）。

## 场景 6：LangChain 集成

对于使用 LangChain 框架的团队，prompt caching 可以与 `ChatBedrockConverse` 类集成。LangChain 提供 `create_cache_point()` 方法，可以生成正确的 `cachePoint` 内容块，无需你自己管理原始 API 格式。

### 实现：带缓存点的 LCEL 链

对于可复用的链式模式，你可以把缓存点直接集成到 `ChatPromptTemplate` 中：

```
import boto3
import json
import time
from langchain_aws import ChatBedrockConverse
from langchain_core.messages import HumanMessage, SystemMessage
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

MODEL_ID = "global.anthropic.claude-sonnet-4-5-20250929-v1:0"
AWS_REGION = "us-west-2"

template = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant that answers questions about documents."),
    ("human", [
        {"type": "text", "text": f"Here is a document: {DOCUMENT}"},
        ChatBedrockConverse.create_cache_point()
    ]),
    ("human", "{question}")
])

chain = template | llm | StrOutputParser()

# Run multiple questions: first writes to cache, subsequent reads from cache
questions = [
    "What are the ice giant planets?",
    "What discoveries has New Horizons made?",
    "How does Jupiter's Great Red Spot compare to storms on Earth?",
]

for i, q in enumerate(questions):
    start = time.time()
    result = chain.invoke({"question": q})
    elapsed = time.time() - start
    print(f"\nQ{i+1}: {q}")
    print(f"A: {result[:150]}...")
    print(f"Time: {elapsed:.2f}s")
    time.sleep(0.5)
```

## 对比 Converse API 与 InvokeModel API

本文的场景使用 Converse API，它提供了与模型无关的 `cachePoint` 语法。如果你的应用使用 InvokeModel API，请注意缓存语法因模型系列而异：

| **特性** | **Converse API（受支持的模型）** | **InvokeModel API（Anthropic）** |
| --- | --- | --- |
| 缓存标记 | `{"cachePoint": {"type": "default"}}` | `"cache_control": {"type": "ephemeral", "ttl": "5m"}` |
| 放置位置 | 在缓存内容之后的独立内容块 | 在被缓存的内容块内部 |
| TTL 支持 | `{"cachePoint": {"type": "default", "ttl": "1h"}}` | `cache_control` 内的 `"ttl"` 字段 |
| `cacheDetails` 响应 | 支持 | 不支持 |
| usage 键格式 | `cacheWriteInputTokens` | `cache_creation_input_tokens` |

新应用建议使用 Converse API，因为 `cachePoint` 语法在受支持的模型系列之间表现完全一致。这意味着你可以在 Anthropic Claude 与 Amazon Nova 之间切换，而无需改动缓存代码。

## 最佳实践

基于本文演示的模式，我们为生产部署推荐以下最佳实践：

- **梳理你的 prompt**：识别哪些部分是静态的（system prompt、工具 schema、参考文档），哪些是动态的（用户问题、会话上下文）。缓存静态部分。
- **满足 token 阈值**：每个缓存检查点都必须超过模型的最低 token 要求。低于阈值的内容，Amazon Bedrock 会正常处理而不做缓存。
- **选择合适的 TTL**：对很少变化的内容（领域知识、工具定义）使用 1 小时 TTL，对会话特定上下文使用 5 分钟 TTL。请记住，更长的 TTL 必须排在更短的 TTL 之前。
- **监控缓存指标**：在应用日志中跟踪 `cacheWriteInputTokens` 和 `cacheReadInputTokens`。缓存命中率偏低可能说明你的内容变化过于频繁，或者 TTL 太短。
- **应用负责任的 AI 控制措施**：对于生产部署，在缓存模式之外使用 [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 添加内容过滤与接地（grounding）校验。
- **为多租户系统实现租户隔离**：当你在同一 AWS 账户下服务多个客户时，使用 SHA-256 哈希前缀模式防止跨租户的缓存共享。
- **使用简化的缓存管理**：对于 Anthropic Claude 模型，单个 `cachePoint` 可以覆盖前面多个内容块。你并不总需要在每一段之后都放置检查点。
- **组合多个缓存位置**：你可以在单个请求中同时缓存 system prompt、消息内容和工具定义。这样可以在三个位置叠加节省。
