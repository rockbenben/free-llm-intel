# Amazon AMET Payments 团队如何用 Strands Agents 加速测试用例生成

在 [Amazon.ae](https://www.amazon.ae/)，我们每月为中东和北非地区五个国家——阿联酋（UAE）、沙特阿拉伯、埃及、土耳其和南非——约 1000 万客户提供服务于。我们的 AMET（非洲、中东和土耳其）Payments 团队负责这些不同国家的支付选项、交易、体验和可负担性功能，平均每月发布五个新功能。每项功能都需要全面的测试用例生成，传统上每个项目要耗费 1 周的人工投入。我们的质量保证（QA）工程师把这些时间花在分析业务需求文档（BRD）、设计文档、UI mock 和历史测试准备工作上——这一过程每年仅测试用例编写就需要一名全职工程师。

为了改进这一人工流程，我们开发了 SAARAM（QA Lifecycle App），这是一个多 agent AI 解决方案，帮助将测试用例生成时间从 1 周缩短到几小时。我们使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 搭配 Anthropic 的 Claude Sonnet，以及 [Strands Agents SDK](https://strandsagents.com/latest/)，将生成测试用例所需时间从 1 周缩短到仅几小时，同时提升了测试覆盖质量。我们的方案表明，研究人类的认知模式，而非仅仅优化 AI 算法，能够打造出可用于生产的系统，增强而非取代人类的专业能力。

在这篇博文中，我们解释如何通过以人为中心的方法克服单 agent AI 系统的局限，如何实现结构化输出以显著减少幻觉，并构建了一个可扩展的方案，目前已准备好扩展到 AMET QA 团队，进而推广到 International Emerging Stores and Payments（IESP）Org 的其他 QA 团队。

## 方案概览

AMET Payments QA 团队负责验证影响支付功能的代码部署，这些代码面向不同监管环境和支付方式下的数百万客户。我们的人工测试用例生成流程拉长了产品周期中的周转时间（TAT），把宝贵的工程资源消耗在重复的测试准备和文档工作上，而非战略性测试举措。我们需要一个自动化方案，既能保持质量标准，又能减少时间投入。

我们的目标包括将测试用例创建时间从 1 周缩短到几小时以内，沉淀资深测试人员的机构知识，在各团队间标准化测试方法，并最大限度减少 AI 系统中常见的幻觉问题。该方案需要能够处理跨多种支付方式、区域法规和客户群体的复杂业务需求，同时生成与现有测试管理系统相契合的、具体且可执行的测试用例。

该架构采用了精密的多 agent 工作流。为实现这一目标，我们经历了 3 次不同的迭代，并随着新技术的发展和更多模型的部署持续改进与增强。

## 传统 AI 方法的挑战

我们最初的尝试沿用了传统的 AI 方法，将整份 BRD 喂给单个 AI agent 来生成测试用例。这种方法经常产出诸如“验证支付是否正常工作”之类的笼统输出，而不是我们 QA 团队所需的具体、可执行的测试用例。例如，我们需要这样具体的测试用例：“验证当一位 UAE 客户对一笔超过 1,000 AED 的订单选择货到付款（COD），且已保存信用卡时，系统会显示 11 AED 的 COD 费用，并通过 COD 网关处理该笔支付，订单状态转为‘待配送’。”

单 agent 方法暴露出几个关键局限。上下文长度限制妨碍了有效处理大型文档，而缺乏专门的处理阶段意味着 AI 无法理解测试优先级或基于风险的方法。此外，幻觉问题会产生无关的测试场景，可能误导 QA 工作。根本原因很明确：AI 试图压缩复杂的业务逻辑，却缺少资深测试人员分析需求时所用的迭代思考过程。

## 以人为中心的突破

我们的突破来自方法上的根本转变。我们不再问“AI 应该如何思考测试？”，而是问“经验丰富的人类是如何思考测试的？”，从而专注于遵循一套特定的分步流程，而不是依赖 [大语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）自行实现这一点。这一理念上的转变促使我们对资深 QA 专业人士开展研究访谈，详细研究他们的认知工作流。

我们发现，经验丰富的测试人员并不会整体性地处理文档——他们会经历若干专门的思维阶段。首先，他们通过提取验收标准、识别客户旅程、理解 UX 需求、梳理产品需求、分析用户数据以及评估工作流能力来分析文档。然后，他们通过一套系统化流程来设计测试：旅程分析、场景识别、数据流映射、测试用例开发，最后是整理与优先级排序。

随后，我们将最初的 agent 拆解为依次进行的思考动作，每个动作作为一个独立步骤。我们使用 [Amazon Q Developer for CLI](https://aws.amazon.com/developer/learning/q-developer-cli/) 构建并测试了每一步，以确保基本思路可靠，并纳入了主要和次要输入。

这一洞见促使我们设计 SAARAM，用专门 agent 来映射这些专家级的测试方法。每个 agent 专注于测试流程的某个特定方面，就像人类专家在思维上把不同分析阶段区分开来一样。

## 基于 Strands Agents 的多 agent 架构

基于对人类 QA 工作流的理解，我们最初尝试从头构建自己的 agent。我们必须自行实现循环、串行或并行执行，还自行创建了编排和工作流图，这需要大量手工工作。为应对这些挑战，我们迁移到了 Strands Agents SDK。它提供了多 agent 编排能力，对于协调复杂且相互依赖的任务、同时保持清晰的执行路径至关重要，帮助我们提升了性能并缩短了开发时间。

## 工作流迭代 1：端到端测试生成

SAARAM 的第一次迭代采用单一输入，并创建了我们的第一批专门 agent。它通过五个专门 agent 处理一份工作文档，以生成全面的测试覆盖。

**Agent 1** 称为 Customer Segment Creator，专注于客户细分分析，使用四个 subagent：

- **Customer Segment Discovery** 识别产品用户群体
- **Decision Matrix Generator** 创建基于参数的矩阵
- **E2E Scenario Creation** 为每个细分群体开发端到端（E2E）场景
- **Test Steps Generation** 详细的测试用例开发

**Agent 2** 称为 User Journey Mapper，使用四个 subagent 来全面梳理产品旅程：

- Flow Diagram 和 Sequence Diagram 是使用 Mermaid 语法的创建器。
- E2E Scenarios 生成器在这些图的基础上构建。
- Test Steps Generator 用于详细的测试文档。

**Agent 3** 称为 Customer Segment x Journey Coverage，它结合 agent 1 和 agent 2 的输入，创建细致的、针对各细分群体的分析。它使用四个 subagent：

- [基于 Mermaid 的流程图](https://mermaid.js.org/)
- 用户旅程
- 每个客户细分群体的时序图
- 相应的测试步骤。

**Agent 4** 称为 State Transition Agent。它分析客户旅程流程中的各种产品状态点。它的 subagent 创建表示不同旅程状态的 Mermaid 状态图、针对特定细分群体的状态场景图，并生成相关的测试场景和步骤。

如下图所示，该工作流最后是一个基本的提取、转换和加载（ETL）过程，对各 agent 的数据进行整合与去重，并将最终输出保存为文本文件。

这种系统化方法有助于全面覆盖客户旅程、细分群体和各种图表类型，通过 agent 与 subagent 的迭代处理实现详尽的测试覆盖生成。

## 应对局限并增强能力

在使用 Strands Agents 开发更稳健、更高效工具的过程中，我们发现了最初方法中的五个关键局限：

- **上下文与幻觉挑战** – 我们的第一个工作流受限于彼此隔离的 agent 操作，各个 agent 独立收集数据并创建可视化表示。这种隔离导致上下文理解有限，使输出准确性下降、幻觉增多。
- **数据生成效率低下** – agent 可用的上下文有限，引发了另一个关键问题：生成大量无关数据。由于缺乏恰当的上下文感知，agent 产出的内容不够聚焦，产生的噪声掩盖了有价值的洞察。
- **解析能力受限** – 初始系统的数据解析范围过窄，仅限于客户细分、旅程映射和基本需求。这一限制使 agent 无法获取全面分析所需的完整信息。
- **单一来源输入限制** – 该工作流只能处理 Word 文档，形成了明显的瓶颈。现代开发环境需要来自多个来源的数据，而这一限制妨碍了全面的数据收集。
- **架构僵化问题** – 重要的是，第一个工作流采用了编排僵化的紧耦合系统。这种架构难以修改、扩展或复用组件，限制了系统适应变化需求的能力。

在第二次迭代中，我们需要实施战略性的解决方案来应对这些问题。

## 工作流迭代 2：全面分析工作流

我们的第二次迭代是对 agentic 工作流架构的彻底重构。我们没有零敲碎打地修补单个问题，而是从头重建，以模块化、上下文感知和可扩展性为核心原则：

**Agent 1** 是智能网关。文件类型决策 agent 作为系统的入口和路由器。它处理文档文件、Figma 设计和代码仓库，对数据进行分类并分发给合适的下游 agent。这种智能路由对于在整个工作流中保持效率和准确性至关重要。

**Agent 2** 负责专门的数据提取。Data Extractor agent 使用六个专门的 subagent，每个专注于特定的提取领域。这种并行处理方式有助于实现全面覆盖，同时保持实用的速度。每个 subagent 都基于特定领域的知识运行，能够提取通用方法可能忽略的细微信息。

**Agent 3** 是 Visualizer agent，它将提取的数据转换为六种不同的 Mermaid 图表类型，每种都服务于特定的分析目的。实体关系图映射数据关系和结构，流程图可视化流程和工作流。需求图阐明产品规格，UX 需求可视化图展示用户体验流程。过程流程图详细描述系统操作，思维导图揭示功能之间的关系和层次。这些可视化为同一信息提供了多个视角，帮助人工审核者和下游 agent 理解复杂数据集中的模式与关联。

**Agent 4** 是 Data Condenser agent，它通过智能上下文蒸馏完成关键的综合处理，确保每个下游 agent 恰好获得其专门任务所需的信息。该 agent 由其压缩信息生成器驱动，在进行复杂分析的同时合并来自 Data Extractor 和 Visualizer agent 的输出。

该 agent 从完整文本上下文中提取关键要素——验收标准、业务规则、客户细分和边界情况——创建结构化摘要，在保留必要细节的同时减少 token 用量。它将每个文本文件与对应的 Mermaid 图进行比较，捕捉仅靠可视化表示可能遗漏的信息。这种细致的处理维护了 agent 交接过程中的信息完整性，确保重要数据在流经系统时不会丢失。最终得到一组精简的补充内容，用全面的上下文丰富 Mermaid 图。这一综合处理确保信息进入测试生成环节时是完整的、结构化的，并针对处理做了优化。

**Agent 5** 是 Test Generator agent，它将收集、可视化和压缩后的信息汇集起来，生成全面的测试套件。该 agent 结合六张 Mermaid 图以及来自 Agent 4 的压缩信息，采用由五个 subagent 组成的流水线。Journey Analysis Mapper、Scenario Identification Agent 和 Data Flow Mapping subagent 根据各自对来自 Agent 4 的输入数据的理解，生成全面的测试用例。在从三个关键视角生成测试用例后，Test Cases Generator 对它们进行评估，并按照内部指南重新格式化以保持一致性。最后，Test Suite Organizer 执行去重和优化，交付一份兼顾全面性与效率的最终测试套件。

现在，系统处理的内容远不止工作流 1 的基本需求和旅程映射——它处理产品需求、UX 规格、验收标准和工作流提取，同时接受来自 Figma 设计、代码仓库和多种文档类型的输入。最重要的是，向模块化架构的转变从根本上改变了系统的运行和演进方式。与僵化的第一个工作流不同，这一设计允许复用早期 agent 的输出、集成新的测试类型 agent，并根据用户需求智能选择测试用例生成器，使系统具备持续适应能力。

## Strands Agents 的其他功能

Strands Agents 为我们的多 agent 系统提供了基础，其模型驱动的方法简化了复杂的 agent 开发。由于该 SDK 能够通过高级推理能力将模型与工具连接起来，我们仅用几行代码就构建了复杂的工作流。除核心功能外，还有两项关键特性对我们的生产部署至关重要：用结构化输出减少幻觉，以及工作流编排。

### 用结构化输出减少幻觉

Strands Agents 的结构化输出功能使用 Pydantic 模型，将传统上不可预测的 LLM 输出转换为可靠、类型安全的响应。这一方法解决了生成式 AI 中的一个根本挑战：尽管 LLM 擅长生成类似人类的文本，但它们可能难以产出生产系统所需的格式一致的响应。通过 Pydantic 校验强制实施 schema，我们确保响应符合预定义结构，从而与现有测试管理系统无缝集成。

以下示例实现展示了结构化输出在实践中的工作方式：

```
from pydantic import BaseModel, Field
from typing import List
import json

# Define structured output schema
class TestCaseItem(BaseModel):
    name: str = Field(description="Test case name")
    priority: str = Field(description="Priority: P0, P1, or P2")
    category: str = Field(description="Test category")

class TestOutput(BaseModel):
    test_cases: List[TestCaseItem] = Field(description="Generated test cases")

# Agent tool with validation
@tool
def save_results(self, results: str) -> str:
    try:
        # Parse and validate Claude's JSON output
        data = json.loads(results)
        validated = TestOutput(**data)
        
        # Save only if validation passes
        with open("results.json", 'w') as f:
            json.dump(validated.dict(), f, indent=)
        return "Validated results saved"
    
    except ValidationError as e:
        return f"Invalid output format: e"
```

Pydantic 会根据定义的 schema 自动校验 LLM 响应，以促进类型正确性和必填字段的存在。当响应与预期结构不匹配时，校验错误会清楚反馈需要修正之处，从而防止格式错误的数据在系统中传播。在我们的环境中，无论 prompt 如何变化或模型如何更新，这一方法都在各 agent 之间产出了稳定、可预测的输出，消除了一整类数据格式错误。因此，我们的开发团队在完整的 IDE 支持下工作效率更高。

### 工作流编排的优势

Strands Agents 的工作流架构提供了多 agent 系统所需的精密协调能力。该框架支持结构化协调，具备明确的任务定义、对独立任务的自动并行执行，以及对依赖操作的顺序处理。这意味着我们可以构建复杂的 agent 间通信模式，而这些模式若手工实现将十分困难。


该工作流系统为我们的用例提供了三项关键能力。首先，并行处理优化让旅程分析、场景识别和覆盖分析能够同时进行，独立的 agent 处理不同方面而互不阻塞。系统根据可用性自动分配资源，最大化吞吐量。

其次，智能依赖管理确保测试开发等待场景识别完成，整理任务则依赖于测试用例的生成。上下文在相互依赖的阶段之间得到保留并高效传递，在整个工作流中维护了信息完整性。

最后，内置的可靠性特性提供了系统所需的韧性。自动重试机制妥善处理瞬时故障，状态持久化使长时间运行的工作流具备暂停与恢复能力，而全面的审计日志同时支持调试和性能优化工作。

### 与 Amazon Bedrock 集成

Amazon Bedrock 是我们 AI 能力的基础，通过 Strands Agents 内置的 AWS 服务集成，可无缝访问 Anthropic 的 Claude Sonnet。我们选择 Anthropic 的 Claude Sonnet，是因为它出色的推理能力以及理解复杂支付领域需求的能力。Strands Agents 灵活的 LLM API 集成让这一实现变得直接。以下代码片段展示了如何在 Strands Agents 中轻松创建 agent：

```
import boto3
from strands import Agent
from strands.models import BedrockModel


bedrock_model = BedrockModel(
    model_id="anthropic.claude-sonnet-4-20250514-v1:0",
    region_name="us-west-2",
    temperature=0.3,
)

agent = Agent(model=bedrock_model)
```

Amazon Bedrock 的托管服务架构降低了我们部署中的基础设施复杂度。该服务提供自动扩缩容，可根据工作负载需求进行调整，无论流量模式如何，都能在各 agent 之间保持一致的性能。内置的重试逻辑和错误处理显著提升了系统可靠性，减少了大规模管理 AI 基础设施通常带来的运维开销。Strands Agents 的精密编排能力与 Amazon Bedrock 的稳健基础设施相结合，打造出一个可用于生产的系统，既能处理复杂的测试生成工作流，又能保持高可靠性和性能标准。

## 成果与业务影响

SAARAM 的落地改进了我们的 QA 流程，在多个维度带来了可衡量的提升。在 SAARAM 之前，QA 工程师需要花 3–5 天手工分析 BRD 文档和 UI mock，以创建全面的测试用例。这一人工流程如今缩短到几小时，系统实现了：

- **测试用例生成时间**：有望从 1 周缩短到几小时
- **资源优化**：QA 投入从 1.0 名全职员工（FTE）降至验证阶段的 0.2 FTE
- **覆盖提升**：相比人工流程多识别出 40% 的边界情况
- **一致性**：100% 遵循测试用例标准和格式

测试用例生成的加速推动了核心业务指标的改善：

- **支付成功率**：通过全面的边界情况测试和基于风险的测试优先级排序得到提升
- **支付体验**：客户满意度提升，因为团队现在可以在设计阶段迭代测试覆盖
- **开发速度**：产品和开发团队在设计阶段生成初步测试用例，从而实现早期质量反馈

SAARAM 捕获并保留了此前依赖个别 QA 工程师的机构知识：

- 资深专业人士的测试模式如今已固化下来
- 历史测试用例的经验教训会自动应用到新功能上
- 在不同支付方式和行业之间采用一致的测试方法
- 缩短了新 QA 团队成员的上手时间

这种迭代改进意味着系统会随着时间推移变得更有价值。

## 经验教训

我们开发 SAARAM 的历程为构建可用于生产的 AI 系统提供了关键洞见。我们的突破来自研究领域专家如何思考，而非优化 AI 处理信息的方式。理解测试人员和 QA 专业人士的认知模式，带来了一个与人类推理自然契合的架构。相比纯技术优化，这一方法产生了更好的结果。构建类似系统的组织应在设计 AI 架构之前，投入时间观察和访谈领域专家——所获得的洞见能直接转化为更有效的 agent 设计。

将复杂任务拆解给专门的 agent，显著提升了准确性和可靠性。借助 Strands Agents 的编排能力，我们的多 agent 架构能够处理单体方法始终会忽略的细微之处。每个 agent 职责聚焦，既能深化领域专业能力，又能提供更好的错误隔离和调试能力。

一项关键发现是，Strands Agents 的工作流和基于图的编排模式，显著优于传统的 supervisor agent 方法。尽管 supervisor agent 会做出动态路由决策，可能引入不确定性，但工作流提供了“agents on rails”——一条结构化路径，有助于获得一致、可复现的结果。Strands Agents 提供多种模式，包括基于 supervisor 的路由、用于带依赖的顺序处理的工作流编排，以及用于复杂场景的基于图的协调。对于一致性至关重要的测试生成，工作流模式凭借其显式的任务依赖和并行执行能力，在灵活性与可控性之间取得了最佳平衡。这种结构化方法与可靠性比理论灵活性更重要的生产环境完美契合。

通过 Strands Agents 的结构化输出功能实现 Pydantic 模型，有效减少了系统中与类型相关的幻觉。通过强制 AI 响应遵循严格的 schema，我们获得了可靠且可通过编程使用的输出。当一致性和可靠性不容妥协时，这一方法已被证明至关重要。类型安全的响应和自动校验已成为系统可靠性的基础。

我们的压缩信息生成器模式展示了智能上下文管理如何在多阶段处理中保持质量。这种明确知道在 agent 之间保留什么、压缩什么、传递什么的方法，有助于防止在 token 受限环境中通常出现的上下文退化。该模式广泛适用于面临类似限制的多阶段 AI 系统。

## 下一步

我们用 Strands Agents 构建的模块化架构，能够直接适配 Amazon 内部的其他领域。生成支付测试用例的同样模式，可应用于零售系统测试、支持工作流的客服场景生成，以及移动应用的 UI 和 UX 测试用例生成。每次适配只需特定领域的 prompt 和 schema，核心编排逻辑可复用。在 SAARAM 的整个开发过程中，团队成功解决了测试用例生成中的诸多挑战——从通过结构化输出减少幻觉，到实现精密的多 agent 工作流。然而，仍存在一个关键缺口：系统尚未获得高质量测试用例在实践中究竟是什么样子的示例。

为弥补这一缺口，将 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 与经过整理的历史测试用例库集成，可以在生成过程中为 SAARAM 提供具体的真实世界示例。借助 Strands Agents 与 Amazon Bedrock Knowledge Bases 的集成能力，系统可以在生成新用例之前，搜索过去成功的测试用例以找到相似场景。在处理一项新支付功能的 BRD 时，SAARAM 会先查询知识库寻找可比的测试用例——无论是相似的支付方式、客户细分还是交易流程——并将其作为上下文示例来引导输出。

未来的部署将使用 Amazon Bedrock AgentCore 进行全面的 agent 生命周期管理。[Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 提供生产执行环境，具备短暂的、会话级的状态管理，在活跃会话期间维持对话上下文，同时促进不同用户交互之间的隔离。Bedrock AgentCore 的可观测性能力有助于详细可视化 SAARAM 多 agent 工作流中的每一步，团队可以借此追踪贯穿五个 agent 的执行路径，审计 Data Condenser 和 Test Generator agent 的中间输出，并通过由 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 驱动的实时仪表盘（采用标准化的 OpenTelemetry 兼容遥测）识别性能瓶颈。

该服务支持多项对生产部署至关重要的高级能力：通过 Amazon Bedrock AgentCore 控制平面进行集中式 agent 管理与版本控制；在 Test Generator 内的五个 subagent 之间对不同工作流策略和 prompt 变体进行 A/B 测试；通过跟踪并行执行阶段的 token 用量和延迟等指标进行性能监控；在不中断活跃测试生成工作流的情况下自动更新 agent；以及在 QA 工程师迭代优化测试套件输出时保持上下文的会话持久化。这一集成使 SAARAM 具备企业级部署条件，同时提供运营可见性和可靠性控制，将其从概念验证转变为生产系统，能够支撑 AMET 团队超越 Payments QA、服务更广泛组织的宏大目标。

## 结语

SAARAM 展示了当 AI 以人类专业能力为核心进行设计时，能够如何改变传统 QA 流程。我们将测试用例创建从 1 周缩短到几小时，同时提升了质量和覆盖率，从而加快了功能上线，并改善了 MENA 地区数百万客户的支付体验。我们成功的关键不仅仅是先进的 AI 技术——而是人类专业能力、周密的架构设计和稳健的工程实践的结合。通过仔细研究资深 QA 专业人士的思考方式、实现映射这些认知模式的多 agent 系统，以及通过结构化输出和上下文工程最大限度减少 AI 的局限，我们打造出一个增强而非取代人类专业能力的系统。

对于考虑开展类似计划的团队，我们的经验强调了三个关键成功因素：投入时间理解领域专家的认知过程；实现结构化输出以最大限度减少幻觉；设计映射人类问题解决方式的多 agent 架构。这些 QA 工具并非要取代人类测试人员，而是通过智能自动化放大他们的专业能力。如果你有兴趣开启基于 AWS 的 agent 之旅，请查看我们的 [Strands Agents 示例实现仓库](https://github.com/strands-agents/samples/tree/main/02-samples)，或我们最新推出的 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)，以及我们 [Amazon Bedrock AgentCore 示例仓库](https://github.com/awslabs/amazon-bedrock-agentcore-samples)中带部署的端到端示例。
