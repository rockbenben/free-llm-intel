# 使用 Amazon Bedrock 托管知识库进行单次和代理检索

一名银行业务员工早上一开始就询问内部人工智能助理需要哪些文件才能开设企业账户。答案就在一个清单中。几个小时后，同一名员工询问独资企业、有限责任公司和多个所有者的合伙企业的这些要求有何不同。这个答案遍布多个政策指南。一名助手必须处理这两个问题，第一个问题要快速而廉价，第二个问题要彻底。应用程序需要一种方法来将检索工作与每个请求相匹配，而无需为简单和复杂的问题构建单独的系统。

Amazon Bedrock 托管知识库现在支持通过“AgenticRetrieveStream”进行单次检索增强生成 (RAG) 和仅检索请求。通过单次 RAG，该服务会搜索您的知识库一次，并使用基础模型 (FM) 从找到的段落中生成答案。对于仅检索请求，服务会返回匹配的段落而不生成答案，因此您的应用程序或用户可以直接使用源文本。这些模式加入了现有的代理检索，其中服务在回答之前计划​​并运行多次搜索。现在，您可以对员工的两个问题使用相同的 API：用于清单查找的单次 RAG 和用于跨策略比较的代理检索。

在这篇文章中，我们将解释新设置的工作原理以及何时使用每种模式。我们使用示例性的内部银行政策助理来展示单次 RAG 如何处理直接问题以及代理检索如何支持跨政策文档的比较。我们还展示了当员工需要查看源段落而不是生成的答案时如何配置仅检索请求。

## 主要优点

[代理检索](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html) 可帮助助理回答需要多次搜索的问题。基础模型将问题分解为子查询，搜索相关知识库，并评估结果是否提供足够的信息来回答原始问题。如果它发现了差距，它可以在配置的迭代限制内优化搜索并检索更多证据。

对于应用程序构建者来说，这提供了几个好处：

- **更好地支持多部分问题 –** 有针对性的搜索可以找到问题每个部分的证据，而不是依靠一次搜索来涵盖所有内容。在银行业示例中，助理可以在比较之前分别查找独资经营者和有限责任公司的要求。
- **信息缺失时进行后续搜索 –** 计划者可以使用找到的内容来决定下一步要搜索的内容。当段落没有提供足够的上下文时，它还可以检索完整的文档，帮助解决单次检索可能无法解决的空白。
- **带有支持证据的答案 –** 启用响应生成后，该服务会将检索到的信息合并到带有引文的答案中。跟踪事件显示规划和检索步骤，帮助开发人员检查答案是如何生成的。
- **减少自定义编排 –** 该服务通过一个 API 管理规划、检索、评估和响应生成工作流程。应用程序不需要实现自己的循环来协调这些步骤。

这些代理能力对于复杂问题仍然很有价值。对于直接查找，应用程序还需要一种无需额外规划即可检索和应答的方法。扩大的“maxAgentIteration”范围缩小了这一差距。通过一个参数，您可以为每个请求选择三种模式之一：

- **仅检索**返回段落而不生成答案。
- **单次 RAG** 检索一次并生成答案，无需计划轮次。
- **代理检索**计划并运行针对复杂问题的多次搜索。

单次 RAG 使用一个基础模型调用来生成答案，与代理检索相比，这可以减少延迟和模型使用。仅检索请求不会调用基础模型。您可以平衡每个请求的速度和应答质量，而无需集成第二个 API 或为简单和复杂查询维护单独的代码路径。

## 检索迭代如何计数

在遍历新值之前，它有助于确定迭代的计数方式，因为这使得行为可预测。

一次迭代等于一次基础模型调用。循环始终以单个应答生成调用结束。 *n* 值最多购买 *n* 减去 1 轮代理规划，最后一次迭代保留用于生成响应。每轮计划都是一次查询重写和一次检索。更多的迭代意味着更多的计划轮次和更好的解决难题的结果。更少的迭代意味着更低的延迟。

有一件事不算数：推测性检索。在第一个计划步骤之前运行的初始检索是检索，而不是迭代。它永远不会影响您的 maxAgentIteration 值，并且只会使请求更快。当您阅读以下值时，请记住这种区别。

## 新消息

现在范围为 0–5。

所有三种模式都支持多个知识库，包括“maxAgentIteration=0”和“1”。单次检索并不意味着单一的知识库。代理模式增加了查询分解、证据评估和迭代搜索，而不是对多个知识库的独占访问。

### maxAgentIteration = 1：基本 RAG（标题用例）

这是单次 RAG：一次检索，然后一个答案。没有代理计划，没有查询重写。 API 根据您的查询检索一次，并生成基于这些段落的响应。这是“检索一次，然后生成响应”模式，以前无法通过此 API 表达。

将其与“generateResponse=true”配对，以获得基于检索到的段落的生成答案。如果您只需要段落，请改用“maxAgentIteration=0”，如下一节所述。

如果您的大部分流量都是范围明确的直接问题，那么这可能是您想要的默认设置。

### maxAgentIteration = 0：仅通道，零 LLM 调用

这将运行一次有保证的检索并且不会生成任何内容。没有调用基础模型。相当于直接调用Retrieve API。这对于已经在“AgenticRetrieveStream”上进行标准化并且宁愿更改参数而不是切换 API 的调用者来说非常有用。

由于没有调用大型语言模型 (LLM)，因此无法生成答案。将 `generateResponse=true` 设置为该值无效并返回 4xx 错误，因为生成答案需要 LLM 调用。

### maxAgentIteration = 2 到 5：代理模式，不变

在[代理模式](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html)中，基础模型将复杂的问题分解为重点子查询，并分多个步骤检索证据，包括跨多个知识库。它会评估检索到的信息，并在证据缺失时改进搜索。这种方法可以提高单个搜索可能无法完全解决的多部分和比较问题的检索准确性。

启用响应生成后，*n* 值最多允许 *n* 减去 1 轮规划，然后才能生成基于检索到的证据的答案。使用 2-5 值的现有请求保留其当前行为。

## 选择一个值

一种推理方法：

| **`最大代理迭代`** | **你得到什么** | **最适合** |
| --- | --- | --- |
| 0 |一次检索，无需生成，零LLM调用 |段落检索。想要检索式行为的调用者对此 API 进行了标准化 |
| 1 |一检索一答案 |用于直接、范围明确的问题的单次 RAG |
| 2 至 5 |最多 *n* 减 1 轮规划，然后得出答案 |多部分、比较性、探索性和跨知识库问题 |

值越低，调用越快且更可预测。值越高，规划者就越能分解和细化真正困难的问题。对于简单流量，从较低的值开始；当复杂查询的准确性比延迟更重要时，提高它。

## 实践：内部银行政策助理

考虑一家虚构的银行，其运营团队使用一名内部助理，并以开户程序、文件清单和政策指南的知识库为后盾。员工使用助手来查找和了解银行的书面要求。以下示例说明了应用程序如何为每个工作流程选择检索模式。它们没有描述客户部署或测量结果。

图1：银行助理如何为每个请求选择检索模式

一名员工向助理询问问题。应用程序选择检索模式并将请求发送到“AgenticRetrieveStream”。使用单次 RAG，服务搜索知识库一次并生成答案。通过代理检索，该服务将问题分成几个部分，进行多次搜索，然后生成带有引用的答案。对于仅检索，该服务返回源段落而不生成答案。以下部分解释了每种模式。

### 回答直接文档问题

一位员工问：“个体工商户开立商业支票账户需要什么文件？”在此示例中，银行维护一个包含答案的专用清单。应用程序设置“maxAgentIteration=1”和“generateResponse=true”来检索相关段落并生成响应，无需重写查询或代理规划。

这是单次 RAG 模式：一次检索，然后是一次应答生成调用。当问题和支持内容已经确定范围时，它可以避免计划步骤。

### 比较不同政策文件的要求

另一位员工问道：“独资经营者和有限责任公司的开户要求有何不同？根据我们的政策，哪些额外检查（如果有）适用于非居民所有者？”回答这个问题可能需要来自单独程序和所有权验证指南的信息。

对于此工作流程，应用程序可以设置“maxAgentIteration=4”和“generateResponse=true”，从而在生成答案之前最多允许进行三轮规划。规划者可以将问题分解为子查询，检索相关证据，并在信息丢失时优化其搜索。应根据代表性问题评估适当的迭代限制，而不是假设较高的值总是会产生更好的答案。

### 显示源段落而不生成答案

审查开户程序的员工可能需要相关的政策文本，而不是生成的摘要。应用程序设置“maxAgentIteration=0”和“generateResponse=false”以返回没有语言模型调用的段落。然后，它可以显示这些段落及其来源参考，供员工查看。

所有三个工作流程都使用“AgenticRetrieveStream”。应用程序选择迭代限制以及是否返回生成的答案。选择模式是应用程序逻辑，而不是该参数提供的自动路由。助手支持策略查找和比较。它不会批准账户或取代银行的审查和授权流程。

## 解决方案概述

以下示例显示了完整的代理请求。它后面的部分将其调整为单次 RAG 和仅检索模式。

### 选择银行助手的检索方式

示例代码使用虚构的策略文档演示了三个工作流程。
```
{
    "messages": [
        { 
            "content": { 
                "text": "How do account-opening requirements differ for sole proprietors and LLCs, and what additional checks, if any, apply to nonresident owners under our policy?" 
            }, 
            "role": "user" 
        }
    ],
    "retrievers": [
        {
            "description": "Knowledge base of account-opening procedures, documentation checklists, and policy guides",
            "configuration": { 
                "knowledgeBase": { 
                    "knowledgeBaseId": "KB12345678" 
                } 
            }
        }
    ],
    "generateResponse": true,
    "agenticRetrieveConfiguration": {
        "foundationModelType": "MANAGED",
        "rerankingModelType": "MANAGED",
        "maxAgentIteration": 4
    }
}
```
## 示例：单次 RAG

设置基本 RAG 是对代理呼叫的单行更改。将 maxAgentIteration 设置为 1 并保持响应生成。
```
{
    "messages": [
        { 
            "content": { 
                "text": "What documents are required to open a business checking account for a sole proprietor?" 
            }, 
            "role": "user" 
        }
    ],
    "retrievers": [
        {
            "description": "Knowledge base of account-opening procedures, documentation checklists, and policy guides",
            "configuration": { 
                "knowledgeBase": { 
                    "knowledgeBaseId": "KB12345678" 
                } 
            }
        }
    ],
    "generateResponse": true,
    "agenticRetrieveConfiguration": {
        "foundationModelType": "MANAGED",
        "rerankingModelType": "MANAGED",
        "maxAgentIteration": 1
    }
}
```
您可以像往常一样使用流。区别在于其中的内容：一次检索和一个有依据的答案，其间没有计划跟踪事件。

## 示例：仅限段落

对于不生成的检索，请将“maxAgentIteration”设置为 0。在此值处必须关闭响应生成。
```
{
    "messages": [
        { 
            "content": { 
                "text": "Show the policy text for the business account-opening procedure." 
            }, 
            "role": "user" 
        }
    ],
    "retrievers": [
        {
            "description": "Knowledge base of account-opening procedures, documentation checklists, and policy guides",
            "configuration": { 
                "knowledgeBase": { 
                    "knowledgeBaseId": "KB12345678" 
                } 
            }
        }
    ],
    "generateResponse": false,
    "agenticRetrieveConfiguration": {
        "foundationModelType": "MANAGED",
        "rerankingModelType": "MANAGED",
        "maxAgentIteration": 0
    }
}
```
这将返回已删除重复的源段落，但没有生成答案。检索行为与直接 Retrieve 调用匹配，但响应格式不同：段落到达流的“result”事件，没有“score”或“location”字段。

## 结论

借助 Amazon Bedrock 托管知识库，您现在可以通过“AgenticRetrieveStream”将单次 RAG、代理检索和仅检索请求组合到一个助手中。在银行业示例中，您可以使用“maxAgentIteration=1”回答开户清单问题并启用响应生成，这样无需计划调用即可生成答案。对于跨业务结构的比较，您可以设置 maxAgentIteration=4 以允许在生成响应之前进行额外的搜索。当员工需要阅读策略文本时，您可以设置“maxAgentIteration=0”并禁用响应生成，以返回段落而无需调用语言模型。您的应用程序选择模式，员工继续使用同一个助手。

要在现有应用程序中采用新模式，请从您自己的文档中的一组代表性问题和预期答案开始。使用相同的知识库将单次 RAG 与当前代理配置进行比较。测量响应延迟和请求成本，并检查答案是否正确以及检索到的段落是否支持。包括答案跨越多个文档的问题以及文档无法回答的问题，因此更快的响应不会隐藏缺失的证据或不受支持的结论。

使用这些结果来选择满足每个工作流程质量要求的最低迭代限制。在额外的搜索可以改善答案的情况下保持代理检索，在一次检索就足够的情况下使用单次 RAG，并在任务是源代码审查时禁用生成。值从 2 到 5 的现有请求保持不变，因此您可以有选择地引入新模式，而不用重新设计整个应用程序。

首先，使用 [AgenticRetrieveStream API 参考](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_AgenticRetrieveStream.html) 在请求中配置 `maxAgentIteration` 和 `generateResponse`，然后根据应用程序的问题和响应时间目标评估设置。要了解有关该服务的更多信息，请访问 [Amazon Bedrock 托管知识库](https://aws.amazon.com/bedrock/knowledge-bases/) 服务页面。
