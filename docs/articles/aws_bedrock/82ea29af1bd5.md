你是一位采购总监，负责数百乃至数千份供应商合约。每一份都塞满了关键数据：合约金额、到期日、签署状态和主要联系人。由于这些信息锁在 PDF 里，你和你的团队要花数小时人工提取、维护电子表格，并回答同样的那些反复出现的问题：“我们在哪家供应商身上花得最多？”或“哪些合约即将到期？”

于是你求助于 AI 聊天工具和企业问答方案。你上传一份合约、用自然语言提问，对于单个文档、甚至是一小把，它确实工作得很好。真正的挑战在规模化时、在跨数百份合约时才显现。

这些工具大多依赖一种叫检索增强生成（RAG）的技术。RAG 把长文本切成块（chunk）并逐个索引。搜索时，RAG 只检索与问题最相关的前 k 个文本块，这一方法更广为人知的名字是语义搜索。当答案就在一个地方时，这没问题。但当一个问题横跨每一份合约——比如总敞口或即将到来的续约——语义搜索就力不从心了。答案需要跨整个数据集做聚合，而不只是几个块。更好的 prompt 修不好这个，另一种架构才行。

在本文中，我们分享一个在 AWS 上的合约智能平台背后的架构。它用 AI 智能体提取合约数据、用多模型方法验证准确性，并通过嵌入式分析和自然语言查询提供即时答案。一切都在一个 Web 应用里运行。

# 挑战：当 AI 聊天工具触及上限

假设你的组合里有 250 份供应商合约，而领导层反复问同样四个问题：

- 整个组合的合约总额。
- 哪些合约已经过期。
- 组合中最贵的一笔协议。
- 最近签署的一笔交易。

这些都是基本问题，但答案被埋没了。你的 250 份合约每份长达 10–20 页，也就是多达 5,000 页非结构化数据。要回答这些问题，一名分析师逐个打开 PDF、搜索那些重要字段、把值复制进电子表格，然后重复这一过程 250 次。在一份新合约到来之前，这就是超过一周的工作量才能清完积压。领导层每一个追问都意味着又一轮过滤和分析。每一轮都有基于陈旧数据工作或在新数据上破坏硬编码公式的风险。

于是你把整个组合上传到一个领先的 AI 聊天工具，问它总金额。答案来得很快、很自信，而且是错的。

## RAG 适合什么，何时需要聚合

那个错误答案不是偶然。它被烤进了这些工具的构建方式里。在内部，它们把每个文档切成向量并存进一个知识库。当你问一个问题时，它们拉回与之最匹配的前 k 个块，然后只用那些块作为上下文构建答案。

对于一个针对性查找，这正是你想要的。问“AnyCompany 合约的付款条款是什么？”，正确的块会带着一个干净的答案浮现。而一个组合级问题是在与这一机制作对，而非配合它。当你问“250 份合约的总金额是多少？”时，系统仍然只返回前 k 个块并只对它们求和。它无法跨组合求和、计数或比较，因为组合从未摆到模型面前。这不是某个工具的缺陷，而是 RAG 本身工作方式的问题。

## 关键洞见

答案是有结构的提取，而非更好的检索。要回答跨数百文档的聚合问题，你把关键字段提取进一个数据库，然后用专为聚合而构建的分析工具查询它们。AI 负责大规模的非结构化到结构化转换，数据库负责数学运算。你把原始文档留在知识库里，用于它擅长的单份合约问题。结果是一个能同时回答两类问题的系统：组合级聚合和精确的单文档查找。

# 方案概览

该平台是一个在 AWS 上的 React Web 应用，它把一个合约 PDF 组合转成结构化、可查询的数据。AI 智能体从每份合约提取关键字段并独立验证它们，签名分歧由 Amazon Textract 来裁定。用户随后通过嵌入式仪表盘和自然语言聊天智能体来探索结果，既得到组合级答案，也得到单份合约的细节。

流水线如下工作：

- 你把合约 PDF 存进一个 Amazon Simple Storage Service (Amazon S3) 桶，它触发一条自动处理流水线。
- 一个 AI 提取智能体（由 Claude Sonnet 系列模型驱动）读取 PDF 并提取八个关键字段，每个都带一个置信度分数。
- 一个单独的 AI 验证智能体（由更轻量的 Claude Haiku 模型驱动）独立读取同一份 PDF 并验证提取结果。
- 如果两个智能体在签名检测上有分歧，Amazon Textract 用计算机视觉提供一个确定性的决胜裁定。
- 系统把验证过的结果存进 Amazon Aurora PostgreSQL。
- 用户通过 WebSocket 看到实时流水线状态，并能立即通过嵌入式仪表盘和自然语言聊天智能体查询数据。

在典型条件下，整条流水线能在几秒内处理一份合约，而无服务器架构旨在帮助伸缩以并行处理大量合约。以下是该方案的参考架构。

# 走进 AI 提取流水线

流水线把每份上传的合约转成已验证的结构化数据。它从两个智能体开始——一个提取字段，一个独立检查它们——两者都运行在完全托管的基础设施上。下面一节讲述它们如何协同，以及其背后的模型。

## 用 Strands Agents 在 Amazon Bedrock AgentCore 上做双模型验证

提取和验证智能体用 [Strands Agent SDK](http://docs.aws.amazon.com/sap/latest/general/rise-agenticai-strands-agent.html) 构建，并部署在 AgentCore runtime 上（Amazon Bedrock AgentCore 的一项能力）。Strands Agent SDK 是一个开源、模型驱动的构建自主智能体的框架。AgentCore 处理无服务器托管、自动伸缩和会话隔离，因此 AI 组件无需你管理任何基础设施。

用 [AgentCore 中的 Policy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html)，你可以定义并强制执行安全控制，作为智能体操作周围的一道保护边界。这安全地处理了敏感数据，如定价条款、财务承诺和供应商关系。基于 Cedar 的策略存在于智能体代码之外，你可以在强制执行前用自动推理来验证它们。智能体和用户只能访问他们被授权查看的合约。

我们刻意选择了两个不同的基础模型用于提取和验证：

- **提取用 Claude Sonnet 4.6：** 高级文档理解能力，原生读取完整 PDF（不需要光学字符识别 OCR 预处理），并为每个字段返回带置信度分数的结构化 JSON。
- **验证用 Claude Haiku 4.5：** 快速、经济，并提供一个独立视角。因为它是另一个训练数据不同的模型，它能抓住重跑同一模型会漏掉的错误。

关于按区域的模型可用性，参考 Amazon Bedrock 中的[按 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。

这一双模型模式是在合约数据上取得高准确率的关键，那里的错误代价高昂。单个模型可能以高置信度幻觉出一个值。两个独立模型发生分歧，是需要人工审阅的一个强信号。

## Amazon Textract：签名检测的决胜裁定

在测试期间，我们发现了一个颇能说明问题的失败模式。验证模型有时会在根本没有签名时，以 95–100% 的置信度把一份合约标记为“已签署”，与提取器发生分歧——而提取器正确地读出了未签署。该模型误读了空的签名区块，把签名栏（“Signature: __________”）的存在当作了签名的证据。

我们没有接受这一幻觉，也没有写复杂的 prompt 去绕过它，而是加了 Amazon Textract 基于计算机视觉的签名检测，作为一个架构层的决胜裁定。Amazon Textract 用视觉分析而非语言理解，来检测页面上真实的手写或数字签名。它只在两个模型在 `is_signed` 字段上有分歧时运行，因此在抓住误报的同时把成本压到最低。

这阐明了一个重要模式：把大语言模型（LLM）用在其擅长的地方（文档理解、字段提取、上下文理解），把确定性服务用在其吃力的地方（视觉元素检测、精确计数、数学运算）。

## 数据驱动的模型选择

流水线的准确率最依赖于处理提取的那个模型，因此我们测试了多种提取器和验证器组合后才定下一个。用我们 20 份合约的样本数据集，我们对全部 8 个字段人工标注（共 160 个值）以建立真值，然后测量每个组合与之匹配的程度。

这一评测浮现出两个模式。提取是更高影响的步骤。一个更强的提取模型即便配上较轻的验证器也能保持准确率，而一个较轻的提取模型无论配什么验证器都会把准确率拉低。更强的能力并不总值得那个成本。在我们数据上，最强的模型并没有显著优于一个能力足够、成本更低的验证器。

Amazon Bedrock 给你广泛的模型选择，而正确的组合取决于你的数据。这是在 20 份合约上的一次小型、方向性测试，不是详尽的评测，结果会随合约格式和字段复杂度而不同。我们强烈建议你用自己的基准和成功标准、用构建时你可用的模型跑一次自己的评测。

# 用 Amazon Quick 大规模查询

提取并验证数据只解决了问题的一半。人们仍需对它提问，从宽泛的组合总额到单份合约的细节。Amazon Quick 在一个单一界面背后同时连接结构化记录和原始文档，于是任何人都能问任一类问题。在 Amazon Quick 内，Amazon Quick Sight 能力驱动仪表盘，而自然语言查询和聊天处理大白话问题。

## 桥接结构与非结构

合约数据现在已提取进一个 PostgreSQL 数据库，我们把它连接到 Amazon Quick，用户可以借可视化仪表盘和自然语言查询来探索它。结果是一个能回答两类问题的单一界面：

- **聚合查询**（通过结构化数据和 Topic）：“我们的合约总额是多少？” → “20 份合约，共 5000 万美元。”
- **文档专属查询**（通过知识库）：“AnyCompany 合约的付款条款是什么？” → 从源 PDF 里取出的确切条款。

## 嵌入式仪表盘

Amazon Quick Sight 仪表盘通过 Amazon Quick Sight Embedding SDK 直接嵌入 React 应用。用户无需离开应用就能获得所需的合约分析，不需要导出或单独的 BI（商业智能）工具。我们直接查询数据而非在 SPICE（Super-fast, Parallel, In-memory Calculation Engine）中缓存并产生额外成本，因此仪表盘始终是实时的。一份合约处理完的那一刻就显示出来。

仪表盘包含几个视图：

- **概览（Overview）：** 关键绩效指标（KPI），如合约总数和总额、一张已签署与未签署的饼图，以及一张带过滤器的完整提取表。
- **详情（Details）：** 来自提取器和验证器两个智能体的置信度分数，带逐字段的匹配状态。
- **成本（Costs）：** 一个突出无服务器架构的服务级成本分解。

## 聊天智能体：自然语言遇上分析

借助 Amazon Quick 中的嵌入式聊天智能体，你可以用自然语言就你的合约组合提问。因为它同时连接一个 Topic（用于结构化数据库查询）和一个知识库（用于文档级搜索），你可以问全谱系的问题：

- “我有多少份合约，总额是多少？” → 20 份合约，5000 万美元。
- “有多少份合约已过期，它们的总额是多少？” → 3 份过期，370 万美元。
- “已签署与未签署各有多少？” → 17 份已签署，3 份未签署。
- “我最该优先处理的 3 份合约是哪些？” → 那些即将到期的未签署合约，按金额排序。

在一次聊天里同时做结构化分析和文档问答——这就是回报：聚合和文档查找从一个界面得到解答。

## 实时流水线透明化

一个改善了用户体验的设计决定是加入基于 WebSocket 的实时状态更新。当合约进入流水线时，React 前端在每个处理阶段发生时就显示它。这把一个不透明的上传-等待体验变成一个透明过程，用户能看到到底是哪个服务在处理他们的合约。它建立信任，并让多模型流程一目了然。

# 关键要点

- **先提取，再查询：** 对于跨大量文档的聚合用例，把关键字段提取进一个结构化数据库。RAG 擅长在文档里查找信息，数据库擅长跨文档聚合。两者都用。
- **用独立性来验证：** 用两个不同的基础模型做提取和验证，能抓住单个模型会漏掉的错误。第二个更便宜的模型的成本，相对于在高风险数据上得到的准确率提升而言微乎其微。
- **用确定性服务做确定性任务：** 当 LLM 产生幻觉时（签名检测、精确计数），引入像 Amazon Textract 这样专为该任务打造的服务，而不是加第三个 LLM。把工具匹配到任务。
- **让 AI 可见：** 实时流水线状态建立用户信任，并使多智能体架构对利益相关方可感。透明把一个不透明的 AI 流水线变成一个可理解的工作流。
- **这一模式在合约之外可扩展：** 那些拥有大量非结构化文档、需要组合级查询的领域都从这一方法中受益：采购、法律合规、保险理赔、HR 入职文档、房地产租约。

# 结论

我们从一位对自己的合约都得不到确切答案的总监开始。通过先为结构化提取做设计、并把分析工具与 AI 智能体配对，这一架构把一个难以管理的合约组合变成一个能在几秒内回答问题的组合。无论问题是跨数百份合约的一个总额，还是一份合约里的付款条款，这都成立。模式很直接：用 LLM 做文本分析，用数据库做数值查询。当两个模型以确定性服务也无法裁定的方式分歧时，下一步是把该合约路由给一个人工审阅者，而不是自动解决。这把人类恰当地留在判断最重要的那个环节之中。
