# Amazon Bedrock Custom Model Import 如何为 Salesforce 简化 LLM 部署

*本文由 Salesforce AI 平台团队成员 Srikanta Prasad、Utkarsh Arora、Raghav Tanaji、Nitin Surya、Gokulakrishnan Gopalakrishnan 和 Akhilesh Deepak Gotmare 共同撰写。*

[Salesforce](https://www.salesforce.com/) 的人工智能（AI）平台团队运行着定制的大语言模型（LLM）——即 [Llama](https://www.llama.com/)、[Qwen](https://qwen.ai/research) 和 [Mistral](https://mistral.ai/) 的微调版本——用于支撑 [Agentforce](https://www.salesforce.com/agentforce/) 等 agentic AI 应用。部署这些模型带来了运营开销：团队要花费数月优化实例族、服务引擎和配置。这一过程耗时、在频繁发版下难以维护，而且由于要为峰值用量预留 GPU 容量而成本高昂。

Salesforce 通过采用 [Amazon Bedrock Custom Model Import](https://aws.amazon.com/bedrock/custom-model-import/) 解决了这一问题。借助 Amazon Bedrock Custom Model Import，团队可以通过统一的 API 导入并部署定制模型，在最大限度减少基础设施管理的同时，与 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)、[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 和 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 等 Amazon Bedrock 功能集成。这一转变让 Salesforce 得以专注于模型和业务逻辑，而不是基础设施。

本文展示 Salesforce 如何将 Amazon Bedrock Custom Model Import 集成到其机器学习运维（MLOps）工作流中、在不改动应用的情况下复用现有端点，并对可扩展性进行基准测试。我们分享关于运营效率和成本优化收益的关键指标，并提供简化你的部署策略的实用洞见。

## 集成方式

Salesforce 从 [Amazon SageMaker Inference](https://aws.amazon.com/sagemaker/ai/deploy/) 迁移到 Amazon Bedrock Custom Model Import，需要与其现有 MLOps pipeline 谨慎集成，以避免中断生产工作负载。团队的首要目标是保持当前的 API 端点和模型服务接口不变，实现零停机且无需下游应用做任何改动。借助这一方式，他们可以利用 Amazon Bedrock 的无服务器能力，同时保留对现有基础设施和工具的投资。集成策略聚焦于在其当前部署工作流与 Amazon Bedrock 托管服务之间建立无缝桥梁，从而实现渐进式迁移而不引入额外运营风险。

如下面的部署流程图所示，Salesforce 在现有的模型交付 pipeline 上只增加了一个步骤来使用 Amazon Bedrock Custom Model Import。在他们的持续集成与持续交付（CI/CD）流程把模型产物保存到模型存储（一个 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）存储桶）之后，他们现在会调用 Amazon Bedrock Custom Model Import API 向 Amazon Bedrock 注册模型。由于 Amazon Bedrock 直接从 Amazon S3 拉取模型，这一控制面操作很轻量，只给部署时间线增加极小的开销（5–7 分钟，取决于模型大小）——其整体模型发布流程仍保持在约 1 小时。这一集成带来了立竿见影的性能收益：由于 Amazon Bedrock 会预加载模型，SageMaker 不再需要在容器启动时下载权重。主要的配置变更包括授予 Amazon Bedrock 权限以实现对其 S3 模型存储桶的[跨账户访问](https://aws.amazon.com/blogs/machine-learning/how-to-configure-cross-account-model-deployment-using-amazon-bedrock-custom-model-import/)，以及更新 [AWS Identity and Access Management](https://aws.amazon.com/iam/identity-center/)（IAM）策略以允许推理客户端调用 Amazon Bedrock 端点。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/26/image-1-28.png)

下面的推理流程图说明了 Salesforce 如何在利用 Amazon Bedrock 无服务器能力的同时保持其现有应用接口。客户端请求流经其既有的[预处理](https://docs.djl.ai/master/docs/serving/serving/docs/lmi/user_guides/input_formatter_schema.html)层，处理 prompt 格式化等业务逻辑，然后到达 Amazon Bedrock，并对原始模型输出应用[后处理](https://docs.djl.ai/master/docs/serving/serving/docs/lmi/user_guides/output_formatter_schema.html)。为处理复杂的加工需求，他们部署了轻量的 SageMaker CPU 容器充当智能代理——运行其自定义的 model.py 逻辑，同时把实际推理转发给 Amazon Bedrock 端点。这种混合架构保住了他们现有的工具框架：其预测服务继续调用 SageMaker 端点而无需变更路由，他们也保留了面向预处理和后处理逻辑的成熟 SageMaker 监控与日志。代价是多一次网络跳转，增加 5–10 毫秒延迟，以及常驻 CPU 实例的成本；但这种方式在保持与现有集成向后兼容的同时，让 GPU 密集的推理完全通过 Amazon Bedrock 实现无服务器化。

## 可扩展性基准测试

为验证 Amazon Bedrock Custom Model Import 的性能能力，Salesforce 在各种并发场景下开展了全面的负载测试。其测试方法聚焦于衡量 Amazon Bedrock 的透明自动扩缩容行为——服务按需自动启动模型副本并在高负载下横向扩展——会如何影响真实世界性能。每次测试都通过其代理容器向 Amazon Bedrock 端点发送包含模型 ID 和输入数据的标准化负载，并在不同负载模式下测量延迟和吞吐。结果（见下表）显示，在低并发下，Amazon Bedrock 的延迟比 ml.g6e.xlarge 基线（bf16 精度）低 44%。在更高负载下，Amazon Bedrock Custom Model Import 保持着稳定的吞吐与可接受的延迟（低于 10 毫秒），这证明无服务器架构能够处理生产工作负载而无需手动扩缩容。

| **并发数（Count）** | **P95 延迟（秒）** | **吞吐（每分钟请求数）** |
| --- | --- | --- |
| 1 | 7.2 | 11 |
| 4 | 7.96 | 41 |
| 16 | 9.35 | 133 |
| 32 | 10.44 | 232 |

结果展示了 ApexGuru 模型（微调后的 QWEN-2.5 13B）在不同并发水平下的 P95 延迟和吞吐表现。当并发达到 32 时，Amazon Bedrock Custom Model Import 自动从一个副本扩展到三个副本。每个模型副本使用 1 个模型单元。

## 结果与指标

除了可扩展性的提升，Salesforce 还从两个关键业务维度评估了 Amazon Bedrock Custom Model Import：运营效率和成本优化。运营效率方面的收益相当可观——团队将模型迭代并部署到生产的时间缩短了 30%。这一改善源于摆脱了围绕实例选择、参数调优以及在 [vLLM](https://github.com/vllm-project/vllm) 与 [TensorRT-LLM](https://github.com/NVIDIA/TensorRT-LLM) 等服务引擎之间选择所做的复杂决策。简化的部署流程让开发者可以专注于模型性能而不是基础设施配置。

成本优化带来的结果更为显著，Salesforce 通过 Amazon Bedrock 实现了最高 40% 的成本降低。这一节省主要来自其各生成式 AI 应用多样的流量模式——从低到高的生产流量——而过去他们必须为峰值工作负载预留 GPU 容量。按用量付费的模式对开发、性能测试和预发布环境尤其有利，因为这些环境只在活跃开发周期内需要 GPU 资源，从而避免了对常常闲置的全天候预留容量的需求。

## 经验总结

Salesforce 使用 Amazon Bedrock Custom Model Import 的历程揭示了若干关键洞见，可以指导其他考虑类似方式的组织。首先，尽管 Amazon Bedrock Custom Model Import 支持流行的开源模型架构（Qwen、Mistral、Llama）并会依据需求频繁扩充其组合，但使用前沿架构的团队可能需要等待支持。因此，用最新模型架构做微调的组织应当在确定部署时间线之前先核实兼容性。

在推理前后的处理方面，Salesforce 评估了使用 [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 和 [AWS Lambda](https://aws.amazon.com/pm/lambda/) 函数的替代方案，这些方案提供完全无服务器的扩缩容和细至毫秒执行时间的按用量付费定价。不过，他们发现这种方式与现有集成的向后兼容性较差，并且在处理逻辑中使用较大库时会观察到冷启动影响。

冷启动延迟成为一个关键考量，尤其是对较大的（超过 7B 参数）模型。Salesforce 在 26B 参数模型上观察到几分钟的冷启动延迟，且延迟随模型大小变化。对于无法容忍此类延迟的延迟敏感型应用，他们建议通过每 14 分钟一次健康检查调用、至少保持一个模型副本处于活动状态来让端点保持预热。这一做法在生产工作负载的成本效率与性能要求之间取得平衡。

## 结论

Salesforce 采用 Amazon Bedrock Custom Model Import 的做法表明，如何在不牺牲可扩展性或性能的前提下简化 LLM 部署。他们实现了部署速度提升 30%、成本节省 40%，同时通过使用 SageMaker 代理容器配合 Amazon Bedrock 无服务器推理的混合架构保持了向后兼容性。对于高度定制的模型或不支持的架构，Salesforce 继续使用 SageMaker AI 作为托管的机器学习方案。

他们的成功源于有条不紊的执行：充分的负载测试，以及从非关键工作负载开始的渐进式迁移。结果证明无服务器 AI 部署在生产中可行，尤其是在流量模式多变的情况下。ApexGuru 现已在他们的生产环境中部署。

对于大规模管理 LLM 的团队，本案例研究提供了一份清晰的蓝图。检查你的模型架构兼容性，为较大模型的冷启动做好规划，并保留现有接口。Amazon Bedrock Custom Model Import 提供了一条经过验证的通向无服务器 AI 的路径，可以降低开销、加快部署并削减成本，同时满足性能要求。
