# 用多 agent 工作流扩展内容审查运营

企业正在管理不断增长的内容量，从产品目录、支持文章到知识库和技术文档。要确保这些信息始终保持准确、相关并与最新的业务事实一致，是一项艰巨的挑战。人工内容审查流程往往缓慢、昂贵，且无法跟上动态变化的业务需求。根据一项 [McKinsey 研究](https://www.mckinsey.com/capabilities/mckinsey-digital/our-insights/the-economic-potential-of-generative-ai-the-next-productivity-frontier)，把生成式 AI 用于知识工作（包括内容审查和质量保障）的组织，可提升高达 30–50% 的生产率，并大幅减少花在重复性核验任务上的时间。同样，[Deloitte 的研究](https://www.deloitte.com/us/en/services/consulting/services/intellidoc-document-review-automation.html)也指出，AI 驱动的内容运营不仅能提升效率，还能帮助组织维持更高的内容准确性并降低运营风险。

[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 是专为大规模部署和运行 AI agent 而构建的基础设施，它与用于构建 AI agent 的开源 SDK [Strands Agents](https://strandsagents.com/) 相结合，让组织能够自动化端到端的内容审查工作流。这种基于 agent 的做法使企业可以评估内容的准确性、对照权威来源核验信息，并生成可付诸行动的改进建议。通过让专用 agent 自主协同工作，人类专家可以专注于策略性审查任务，而 AI agent 系统则承担大规模的内容校验。

我们所介绍的这种基于 agent 的做法适用于任何类型的企业内容，从产品文档、知识库到营销材料和技术规格。为展示这些理念的实际运作，我们走一遍审查博客内容技术准确性的实践示例。通过调整 agent 配置、工具和核验来源，这些模式和技术可以直接适配到各种内容审查需求。

## 方案概览

该内容审查方案实现了[多 agent 工作流](https://strandsagents.com/latest/documentation/docs/user-guide/concepts/multi-agent/workflow/)模式：三个用 Strands Agents 构建并部署在 Amazon Bedrock AgentCore 上的专用 AI agent 以协同的 pipeline 方式工作。每个 agent 接收上一个 agent 的输出，按自己的专门职能处理，再把丰富后的信息传给序列中的下一个 agent。这形成了一个渐进式精炼的过程，其中：

- **内容扫描 agent** 分析原始内容并提取相关信息
- **内容核验 agent** 接收这些提取出的要素，并对照权威来源进行校验
- **建议 agent** 把核验发现转化为可付诸行动的内容更新

技术内容维护需要多个专用 agent，因为手工扫描、核验和更新文档效率低下且容易出错。每个 agent 都有聚焦的角色——扫描者识别对时间敏感的要素，核验者检查当前的准确性，建议 agent 则拟定精确的更新。该系统模块化的设计、清晰的接口与职责划分，使得随着内容复杂度增长，新增 agent 或扩展能力都很容易。为说明这套基于 agent 的内容审查系统在实践中如何运作，我们走一遍审查技术博客文章准确性的实现。科技公司经常发布介绍新功能、更新和最佳实践的博客文章。然而，创新的快节奏意味着某些功能会被弃用或更新，使得在数百甚至数千篇已发布文章中保持信息最新变得颇具挑战。虽然我们用博客内容来演示这一模式，该架构与内容类型无关，只要为 agent 配置适当的 prompt、工具和数据源，就能支持任何内容类型。

## 多 agent 工作流

### 内容扫描 agent：为检测过时内容做智能提取

内容扫描 agent 是多 agent 工作流的入口。它负责识别可能已过时技术信息。这个 agent 专门针对那些随时间推移很可能变得过时的要素。该 agent 分析内容并产出结构化输出，按类型、在博客中的位置以及时间敏感度对每个技术要素分类。这种结构化格式让核验 agent 能收到组织良好、可高效处理的数据。

### 内容核验 agent：基于证据的校验

内容核验 agent 从扫描 agent 接收结构化的技术要素，并对照权威来源执行校验。核验 agent 使用 AWS 文档 MCP server 访问当前的技术文档。对于从扫描 agent 收到的每个技术要素，它会遵循由特定 prompt 引导的系统化核验流程，聚焦于客观、可度量的判据。

该 agent 被要求检查以下方面：

- **版本特定信息**：所提及的版本号、API 端点或配置参数是否仍然存在？
- **功能可用性**：所描述的服务功能在指定区域或层级中是否仍然可用？
- **语法准确性**：代码示例、CLI 命令或配置片段是否与当前文档一致？
- **前置条件有效性**：所列的要求、依赖或设置步骤是否仍然准确？
- **价格与配额**：所提及的费用、配额或服务限制是否与当前公布的信息相符？

对于从扫描 agent 收到的每个技术要素，该 agent 会执行以下步骤：

- 基于要素类型和内容生成有针对性的搜索查询
- 查询文档服务器以获取当前信息
- 使用上述具体判据，把原始主张与权威来源进行比较
- 把核验结果分类为 `CURRENT`、`PARTIALLY_OBSOLETE` 或 `FULLY_OBSOLETE`
- 记录具体的差异及证据

**核验实际运行的示例：** 当扫描 agent 识别出主张“Amazon Bedrock 仅在 us-east-1 和 us-west-2 区域可用”时，核验 agent 生成搜索查询“Amazon Bedrock available regions”，并从 AWS 文档中检索当前的区域可用性。在发现 Bedrock 现已在包括 eu-west-1 和 ap-southeast-1 在内的 8 个以上区域可用后，它把该主张分类为 `PARTIALLY_OBSOLETE`，证据为：“原始主张列出 2 个区域，但截至核验日期，当前文档显示在 us-east-1、us-west-2、eu-west-1、ap-southeast-1 以及其他 4 个区域可用。”

核验 agent 的输出保留扫描 agent 的要素结构，同时加入这些核验细节和基于证据的分类。

### 建议 agent：生成可执行的更新

建议 agent 代表多 agent 工作流的最后阶段，把核验发现转化为可直接实施的内容更新。该 agent 接收核验结果并生成具体建议，在纠正技术不准确之处的同时保持原有内容的风格。

## 把你的内容审查用例适配到这一多 agent 工作流模式

这一多 agent 工作流模式可以快速适配到任何内容审查场景，而无需改动架构。无论是审查产品文档、营销材料还是监管合规文档，同样这三个 agent 的顺序工作流都适用。只需修改每个 agent 的 system prompt，使其聚焦于特定领域的要素，并可能替换工具或知识来源。例如，我们的博客审查示例使用 `http_request` 工具抓取博客内容，并使用 AWS Documentation MCP Server 做核验，而产品目录审查系统则可能使用数据库连接工具检索产品信息，并查询库存管理 API 做核验。同样，合规审查系统会调整扫描 agent 的 prompt，让它识别监管声明而不是技术性主张，把核验 agent 连接到法律数据库而非技术文档，并配置建议 agent 生成可供审计的报告而不是内容更新。核心的顺序步骤——提取、核验和建议——在所有这些场景中都保持不变，提供了一个经过验证、可从技术博客扩展到任何企业内容类型的模式。要把该方案定制到其他内容类型，我们建议做以下改动。

- 把 `CONTENT_SCANNER_PROMPT`、`CONTENT_VERIFICATION_PROMPT` 和 `RECOMMENDATION_PROMPT` 变量的值替换为你自定义的 prompt 指令：

```
  python
  CONTENT_SCANNER_PROMPT = """<replace with your prompt instructions>"""
  CONTENT_VERIFICATION_PROMPT = """<replace with your prompt instructions>"""
  RECOMMENDATION_PROMPT = """<replace with your prompt instructions>"""
```

- 为内容核验 agent 更新官方文档 MCP server：

```
  python
   product_db_mcp_client = MCPClient(
       lambda: stdio_client(StdioServerParameters(
           command="uvx", args=["<replace with your official documentation MCP server>"]
       ))
   )
```

- 当 `http_request` 工具不够用时，为内容扫描 agent 添加合适的内容访问工具，例如 `database_query_tool` 和 `cms_api_tool`：

```
python
   scanner_agent = Agent(
       model="us.anthropic.claude-3-7-sonnet-20250219-v1:0",
       system_prompt=CONTENT_SCANNER_PROMPT,
       tools=[database_query_tool, cms_api_tool]  # Replace http_request
   )
```

这些有针对性的改动让同一套架构模式能够处理任何内容类型，同时保持经过验证的三 agent 工作流结构，确保在不同内容领域之间的一致性和可靠性，而无需改动核心的编排逻辑。

## 结论与后续步骤

本文介绍了如何用 Amazon Bedrock AgentCore 和 Strands Agents 架构一个由 AI agent 驱动的内容审查系统。我们演示了多 agent 工作流模式：专用 agent 协同工作，扫描内容、对照权威来源核验技术准确性，并生成可付诸行动的建议。此外，我们还讨论了如何通过修改 agent 的 prompt、工具和数据源，把这一多 agent 模式适配到不同内容类型，同时保持同样的架构框架。

我们鼓励你在自己的账户中试用 [GitHub](https://github.com/aws-samples/sample-multi-agent-content-reviewer) 上提供的示例代码，以获得对该方案的第一手体验。作为后续步骤，可以考虑先在你内容的一个子集上开展试点项目，为你的具体领域定制 agent prompt，并为你自己的用例接入合适的核验来源。这一架构的模块化特性，让你可以随着系统扩展以满足组织完整的内容审查需求，逐步迭代完善每个 agent 的能力。
