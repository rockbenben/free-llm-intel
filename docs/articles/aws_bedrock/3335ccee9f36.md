# 使用 FloTorch 对 Amazon Nova 与 GPT-4o 模型进行基准测试

*基于 FloTorch.ai CTO Dr. Hemant Joshi 的原始文章*

最近，[FloTorch](https://www.flotorch.ai/) 开展的一项评估比较了 [Amazon Nova](https://aws.amazon.com/ai/generative-ai/nova/) 模型与 OpenAI GPT-4o 的性能。

Amazon Nova 是新一代前沿基础模型（FM），提供前沿智能与业界领先的性价比。Amazon Nova 系列模型包括 Amazon Nova Micro、Amazon Nova Lite 和 Amazon Nova Pro，它们支持文本、图像和视频输入，并生成基于文本的输出。这些模型为企业提供了一系列能力，在准确性、速度和成本效益之间取得平衡。

FloTorch 使用其企业级软件，借助 Comprehensive Retrieval Augmented Generation（CRAG）[基准数据集](https://github.com/facebookresearch/CRAG/)，对 Amazon Nova 模型与 OpenAI 的 GPT-4o 模型进行了广泛比较。FloTorch 的评估聚焦三个关键因素——延迟、准确性和成本——覆盖五个不同主题。

该基准研究的主要发现：

- GPT-4o 在准确性上相对 Amazon Nova Pro 略有优势
- Amazon Nova Pro 在效率上优于 GPT-4o，运行速度**快 97%**，同时成本效益**高 65.26%**
- Amazon Nova Micro 和 Amazon Nova Lite 在准确性上比 GPT-4o-mini 领先**2 个百分点**
- 在可负担性方面，Amazon Nova Micro 和 Amazon Nova Lite 分别比 GPT-4o-mini **便宜 10% 和 56.59%**
- Amazon Nova Micro 和 Amazon Nova Lite 还展现出**更快的响应时间**，分别提升 **48% 和 26.60%**

本文将更详细地讨论这次基准测试的发现。

## 对高性价比 AI 模型日益增长的需求

生成式 AI 的格局正在快速演变。OpenAI 于 2024 年 5 月推出 GPT-4o，Amazon 则在 2024 年 12 月的 AWS re:Invent 上推出 Amazon Nova 模型。尽管 GPT-4o 在 AI 社区中获得了关注，但由于更低的延迟和更好的成本效益，企业对 Amazon Nova 的兴趣正在增加。

大语言模型（LLM）通常擅长回应用户查询，但有时会生成过于宽泛或不准确的响应。此外，LLM 可能给出超出公司特定上下文的答案，这使它们不适合某些企业用例。

如今 LLM 最关键的应用之一是检索增强生成（RAG），它让 AI 模型把响应建立在 PDF、内部文档和结构化数据等企业知识库之上。对于希望 AI 系统严格在既定范围内给出响应的企业来说，这是一项至关重要的要求。

为了更好地服务企业客户，这次评估旨在回答三个关键问题：

- **在延迟、成本和准确性方面，Amazon Nova Pro 与 GPT-4o 相比如何？**
- **在这些相同指标上，Amazon Nova Micro 与 **Amazon Nova **Lite 相对 GPT-4o mini 表现如何？**
- **这些模型在不同行业领域的 RAG 用例中表现如何？**

通过回答这些问题，该评估为企业提供了可操作的洞察，帮助它们针对自身具体需求选择合适的 AI 模型——无论是优化速度、准确性还是成本效益。

## CRAG 基准数据集概览

[CRAG 数据集](https://github.com/facebookresearch/CRAG/blob/main/docs/dataset.md)由 Meta 发布，用于跨五个领域、八种问题类型和大量问答对进行事实性问题测试。CRAG 数据集中的五个领域是 Finance、Sports、Music、Movie 和 Open（杂项）。八种问题类型分别是 `simple`、`simple_w_condition`、`comparison`、`aggregation`、`set`、`false_premise`、`post-processing` 和 `multi-hop`。下表给出示例问题及其领域和问题类型。

| **领域** | **问题** | **问题类型** |
| --- | --- | --- |
| Sports | 在高尔夫球一轮比赛中，你可以携带的球杆数量少于上限吗？ | `simple` |
| Music | 你能告诉我到第 60 届格莱美（2017 年）为止，Arlo Guthrie 共获得过多少个格莱美奖吗？ | `simple_w_condition` |
| Open | 我可以用空气炸锅做曲奇吗？ | `simple` |
| Finance | Meta 在 2022 年有过并购吗？ | `simple_w_condition` |
| Movie | 2016 年，哪部电影在奥斯卡上因其视觉效果而获奖？ | `simple_w_condition` |

该评估从该数据集中选取了 200 条查询，覆盖五个领域和两种问题类型：`simple` 与 `simple_w_condition`。这两类问题在用户中都很常见，而对诸如*“Can you tell me how many grammies were won by arlo guthrie until 60th grammy (2017)?”*这样的查询做一次典型 Google 搜索，并不能得到正确答案（一个格莱美奖）。FloTorch 使用这些查询及其真实答案创建了一个子集基准数据集。CRAG 数据集还为每个查询提供前五个搜索结果页面。这五个网页充当知识库（源数据），以限制 RAG 模型的回答。目标是使用通用嵌入算法动态索引这五个网页，然后使用检索（与重排序）策略从已索引的知识库中检索数据片段，以推断最终答案。

## 评估设置

RAG 评估 pipeline 由若干关键组件构成，如下图所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/07/ml-18337-Picture2.png)

本节我们将更详细地探讨每个组件。

### 知识库

FloTorch 使用 CRAG 数据集为每个查询提供的前五个 HTML 网页作为知识库源数据。HTML 页面被解析以提取文本，供嵌入阶段使用。

### 分块策略

FloTorch 使用固定分块策略，chunk 大小为 512 个 token（通常四个字符约等于一个 token），chunk 之间重叠 10%。未来几周将针对不同分块策略、chunk 大小和重叠比例开展进一步实验，并更新本文。

### 嵌入策略

FloTorch 在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上使用 [Amazon Titan Text Embeddings V2](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html) 模型，输出向量大小为 1024。该模型的最大输入 token 上限为 8,192，系统成功且高效地嵌入了来自知识库源数据的 chunk 以及来自 CRAG 数据集的短查询。Amazon Bedrock API 让使用 Amazon Titan Text Embeddings V2 嵌入数据变得非常简单。

### 向量数据库

FloTorch 选择 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 作为向量数据库，看中的是其高性能指标。该实现包含一个预置的三节点分片 OpenSearch Service 集群。每个[预置节点](https://aws.amazon.com/ec2/instance-types/r7g/)都是 r7g.4xlarge，选择它是因为其可用性以及足以满足性能要求的容量。FloTorch 在 OpenSearch Service 中使用 [HSNW](https://en.wikipedia.org/wiki/Hierarchical_navigable_small_world) 索引。

### 检索（与重排序）策略

FloTorch 采用 k 最近邻（k-NN）为 5 的检索策略来获取检索到的 chunk。实验排除了重排序算法，以确保在针对给定查询推断答案时，两个模型获得的检索 chunk 保持一致。以下代码片段对给定查询进行嵌入，并把嵌入传入搜索函数：

```
def search_results(interaction_ids: List[str], queries: List[str], k: int):
   """Retrieve search results for queries."""
   results = []
   embedding_max_length = int(os.getenv("EMBEDDING_MAX_LENGTH", 1024))
   normalize_embeddings = os.getenv("NORMALIZE_EMBEDDINGS", "True").lower() == "true"

   for interaction_id, query in zip(interaction_ids, queries):
       try:
           _, _, embedding = create_embeddings_with_titan_bedrock(query, embedding_max_length, normalize_embeddings)
           results.append(search(interaction_id + '_titan', embedding, k))
       except Exception as e:
           logger.error(f"Error processing query {query}: {e}")
           results.append(None)
   return results
```

### 推理

FloTorch 使用现有 API key 调用 OpenAI 的 [GPT-4o 模型](https://openai.com/index/hello-gpt-4o/)，并通过对话 API 使用 Amazon Nova Pro 模型。GPT-4o 支持 128,000 的上下文窗口，而 Amazon Nova Pro 的上下文窗口为 300,000。GPT-4o 的最大输出 token 上限为 16,384，而 Amazon Nova Pro 的最大输出 token 上限为 5,000。基准实验未使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 功能。该实现使用 FloTorch 企业版提供的通用网关，以便用同一个函数发起一致的 API 调用，并统一跟踪 token 数量和延迟指标。推理函数代码如下：

```
def generate_responses(dataset_path: str, model_name: str, batch_size: int, api_endpoint: str, auth_header: str,
                        max_tokens: int, search_k: int, system_prompt: str):
   """Generate response for queries."""
   results = []

   for batch in tqdm(load_data_in_batches(dataset_path, batch_size), desc="Generating responses"):
       interaction_ids = [item["interaction_id"] for item in batch]
       queries = [item["query"] for item in batch]
       search_results_list = search_results(interaction_ids, queries, search_k)

       for i, item in enumerate(batch):
           item["search_results"] = search_results_list[i]

       responses = send_batch_request(batch, model_name, api_endpoint, auth_header, max_tokens, system_prompt)

       for i, response in enumerate(responses):
           results.append({
               "interaction_id": interaction_ids[i],
               "query": queries[i],
               "prediction": response.get("choices", [{}])[0].get("message", {}).get("content") if response else None,
               "response_time": response.get("response_time") if response else None,
               "response": response,
           })

   return results
```

### 评估

两个模型均通过运行批量查询进行评估。选择批大小为 8，以符合 Amazon Bedrock 的[配额限制](https://docs.aws.amazon.com/general/latest/gr/bedrock.html)以及 GPT-4o 的[速率限制](https://platform.openai.com/docs/guides/rate-limits)。查询函数代码如下：

```
def send_batch_request(batch: List[Dict], model_name: str, api_endpoint: str, auth_header: str, max_tokens: int,
                      system_prompt: str):
   """Send batch queries to the API."""
   headers = {"Authorization": auth_header, "Content-Type": "application/json"}
   responses = []

   for item in batch:
       query = item["query"]
       query_time = item["query_time"]
       retrieval_results = item.get("search_results", [])

       references = "# References \n" + "\n".join(
           [f"Reference {_idx + 1}:\n{res['text']}\n" for _idx, res in enumerate(retrieval_results)])
       user_message = f"{references}\n------\n\nUsing only the references listed above, answer the following question:\nQuestion: {query}\n"

       payload = {
           "model": model_name,
           "messages": [{"role": "system", "content": system_prompt},
                        {"role": "user", "content": user_message}],
           "max_tokens": max_tokens,
       }

       try:
           start_time = time.time()
           response = requests.post(api_endpoint, headers=headers, json=payload, timeout=25000)
           response.raise_for_status()
           response_json = response.json()
           response_json['response_time'] = time.time() - start_time
           responses.append(response_json)
       except requests.RequestException as e:
           logger.error(f"API request failed for query: {query}. Error: {e}")
           responses.append(None)

   return responses
```

## 在 CRAG 数据集上的基准测试

本节我们讨论在 CRAG 数据集上做基准测试时的延迟、准确性和成本度量。

### 延迟

每个查询响应的延迟按两个时间戳之差计算：向推理 LLM 发起 API 调用时的时间戳，以及从推理端点收到完整响应时的第二个时间戳。这两个时间戳之差即为延迟。延迟越低，说明 LLM 性能越快，越适合需要快速响应的应用。研究表明，通过优化和缓存技术，两个模型的延迟都可以进一步降低；不过，本次评估聚焦于测量两个模型的开箱即用延迟表现。

### 准确性

FloTorch 使用 CRAG 基准随附 [local_evaluation.py](https://github.com/facebookresearch/CRAG/blob/main/local_evaluation.py) 脚本的修改版本来进行准确性评估。该脚本经过增强，可以对正确、错误和缺失的响应进行恰当分类。评估脚本中默认的 GPT-4o 评估 LLM 被替换为 `mixtral-8x7b-instruct-v0:1` 模型 API。脚本的其他修改使其能够按前述方式监控输入和输出 token 以及延迟。

### 成本

成本计算很直接，因为 Amazon Nova Pro 和 GPT-4o 都分别公布了每百万输入 token 和输出 token 的价格。计算方法是用输入 token 数乘以相应费率，对输出 token 也做同样处理。运行 200 条查询的总成本由输入 token 成本与输出 token 成本相加得出。本次分析不包含 OpenSearch Service 预置集群成本，因为成本比较只聚焦于 Amazon Nova Pro 与 GPT-4o LLM 在推理层面的差异。

### 结果

下表汇总了结果。

| ** .** | **Amazon Nova Pro** | **GPT-4o** | **观察结果** |
| --- | --- | --- | --- |
| 在 CRAG 数据集子集上的准确性 | 51.50%（200 个响应中 103 个正确） | 53.00%（200 个响应中 106 个正确） | GPT-4o 在准确性上比 Amazon Nova Pro 高 1.5% |
| 运行 200 条查询推理的成本 | $0.00030205 | $0.000869537 | 与 GPT-4o 相比，Amazon Nova Pro 节省 65.26% 的成本 |
| 平均延迟（秒） | 1.682539835 | 2.15615045 | Amazon Nova Pro 比 GPT-4o 快 21.97% |
| 输入与输出 token 的平均值 | 1946.621359 | 1782.707547 | GPT-4o 的典型响应比 Amazon Nova 的响应更短 |

对于 simple 查询，Amazon Nova Pro 与 GPT-4o 的准确性相近（分别为 55 和 56 个正确响应），但对于带条件的 simple 查询，GPT-4o 的表现略好于 Amazon Nova Pro（50 对 48 个正确答案）。设想你所在的组织运营着一项 AI 助手服务，每月处理来自 10,000 名用户的 1,000 个问题（即每月 10,000,000 条查询）。与 GPT-4o 相比，Amazon Nova Pro 每月可为你的组织节省 $5,674.88（每年 $68,098）。

我们来看看 Amazon Nova Micro、Amazon Nova Lite 和 GPT-4o mini 模型在同一数据集上的类似结果。

|  | **Amazon Nova Lite** | **Nova Micro** | **GPT-4o mini** | **观察结果** |
| --- | --- | --- | --- | --- |
| 在 CRAG 数据集子集上的准确性 | 52.00%（200 个响应中 104 个正确） | 54.00%（200 个响应中 108 个正确） | 50.00%（200 个响应中 100 个正确） | Amazon Nova Lite 与 Amazon Nova Micro 分别比 GPT-4o mini 高 2 个和 4 个百分点 |
| 运行 200 条查询推理的成本 | $0.00002247（比 GPT-4o mini 便宜 56.59%） | $0.000013924（比 GPT-4o mini 便宜 73.10%） | $0.000051768 | Amazon Nova Lite 与 Amazon Nova Micro 分别比 GPT-4o mini 便宜 56.59% 和 73.10% |
| 平均延迟（秒） | 1.553371465（比 GPT-4o mini 快 26.60%） | 1.6828564（比 GPT-4o mini 快 20.48%） | 2.116291895 | Amazon Nova 模型至少比 GPT-4o mini 快 20% |
| 输入与输出 token 的平均值 | 1930.980769 | 1940.166667 | 1789.54 | GPT-4o mini 返回的答案更短 |

相比 GPT-4o mini，Amazon Nova Micro 明显更快、更便宜，同时提供更准确的答案。如果你运营的服务每月处理约 1,000 万条查询，它平均能为你节省下原本要为 GPT-4o mini 模型略低准确性结果所支付费用的 73%。

## 结语

基于这些针对 RAG 用例的测试，与 GPT-4o 和 GPT-4o mini 模型相比，Amazon Nova 模型以显著更低的成本和延迟达到相当或更高的准确性。FloTorch 正在继续对其他相关 LLM 进行进一步实验以作比较。未来研究将包含针对多种查询类型的额外实验，例如 `comparison`、`aggregation`、`set`、`false_premise`、`post-processing` 和 `multi-hop` 查询。
