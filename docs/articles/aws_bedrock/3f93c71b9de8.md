# 从原型到生产：借助 Agent DLC 工程化构建 agent

过去一年，AI agent 已从探索走向工程化。企业团队正在交付大型语言模型（LLM）系统，这些系统能调用工具、编排 API，并基于内部知识回答问题。

一次成功的演示能展示 agent 具备哪些能力。发布之前，团队还需要回答另一个问题："*这个 agent 是否准备好投入生产？*" 负责这一决策的人需要证据，证明该 agent 满足商定的要求。

要始终如一地做出这一决策，团队需要一种可重复、成本可控的方法，用来评估 agent 当前的行为，以及最新一次改动是否带来了改进。

在传统软件开发中，团队用单元测试、持续集成与持续交付（CI/CD）以及通过的构建来回答这些问题。这些机制对 agent 而言必要但并不充分，原因有三，每个都要求额外的检查。本文说明这三个属性，并给出一个实测案例：一个聚合指标掩盖了覆盖问题。随后介绍 Agent Development Lifecycle（Agent DLC）：一个生命周期、两个循环，以及一个用于判定每次改动的单一明确标准。

**关于术语的说明：** 本文通篇，*黄金标准* 指一个特定的工件：一组可验证的准则、各自的阈值，以及核验这些准则时所对照的获批示例。业务负责人批准这一标准，作为验收决策的依据。

## 1. 需要额外工程实践的 agent 的三个属性

常规的软件测试和 CI/CD 仍然适用于 agent，但有三个属性要求额外的检查。其一，agent 是非确定性的：相同的输入可能产生不同的输出和执行路径。其二，对 prompt、工具描述、检索设置或 memory 配置的改动，都可能以纯文本审查无法察觉的方式改变行为。其三，model endpoint、知识库和外部 API 可能独立于代码仓库发生变化，并影响 agent 的行为。表 1 总结了应对每个属性所需的工程实践。

*表 1. 每个属性让哪些做法失效，又需要什么来替代。*

| **属性** | **常规做法** | **为何不够** | **Agent DLC 的要求** |
| --- | --- | --- | --- |
| 非确定性 | 在 CI 中每个用例只做一次断言 | 衡量的是一个分布里的单个样本，通过或失败可能源于与改动无关的原因 | 每个示例运行 k 次，按通过率和失败分布判定 |
| prompt 即源代码 | 审查 diff、批准改动 | 行为无法从 prompt 的文本里读出来 | prompt、工具、检索、memory 的每次改动都附带评估纳入版本管理，并保留沿袭关系 |
| 依赖会自行变化 | 锁定版本、升级时验证 | 不会触发，因为代码仓库里没有任何改动 | 按计划重跑标准，并在偏离基线时告警 |

## 2. 一个实测示例：高检索精度可能掩盖信息缺失

下面的示例说明，指标的选择会怎样影响诊断。

我们构建了一个参考实现，端到端地跑通这套方法：一个内部政策助手，基于文档知识库回答 HR 政策问题。我们选了一个边界清晰、范围很窄的领域，好让评估和诊断更容易跟进。以下结果都在这个参考实现上测得，既不是客户成效，也不是基准测试结果。

[配套的 AWS Samples 仓库](https://github.com/aws-samples/sample-eval-first-building-enterprise-agents-with-agentcore) 包含基础设施部署、HR agent、自定义评估器，以及用于基线评估和 prompt 改动后重新评估的脚本（`09-run-eval.sh` 和 `10-optimize-prompt.sh`）。它还提供针对裁判可重复性、模型对比、成本和延迟的可选检查。这些脚本可复现整套工作流。分数可能随运行批次和仓库版本而变化。

三个黄金问题，每个各有五项度量：

- **有据性**：把答案拆解为断言，逐条对照检索到的来源核验。
- **块级源精度**：每个检索到的块，作为整体，对这个问题是否必要？
- **事实级源精度**：把每个块拆成单条事实，逐条检查是否必要。
- **检索覆盖率**：对每个子问题，是否有某个检索到的块能回答它？
- **响应精度**：答案里的断言中，有多少是必要的？

*表 2. 第一轮评估。在参考实现上测得。非客户成效。*

| **问题** | **有据性** | **块级精度** | **事实级精度** | **检索覆盖率** | **判定** |
| --- | --- | --- | --- | --- | --- |
| 绩效考核 | 0.83 | 1.00 | 0.59 | 1.00 | 通过 |
| 福利登记 | 0.90 | 1.00 | 0.53 | 1.00 | 通过 |
| 病假证明 | 0.39 | 1.00 | 0.09 | 0.00 | 未通过 |

三个问题的块级精度都是 1.00。如果发布门槛只看这一项指标，三个答案都会放行。

事实级精度讲的就是另一回事了：0.59、0.53、0.09。对第三个问题，检索到的材料里约九成事实与所问无关。块级精度只问一段文字是否切题，并不衡量其中有多少内容是相关的。

接着我们只改了一处：系统 prompt。我们加了三条约束：严格以检索到的内容为依据、忽略无关的检索内容、保持答案聚焦。agent、知识库、评估器和问题都未改动，因此前后只有一个变量不同。

*表 3. 仅改动 prompt 之后。一处改动，两种相反结果。*

|  | **绩效考核，改动前** | **绩效考核，改动后** | **病假，改动前** | **病假，改动后** |
| --- | --- | --- | --- | --- |
| 有据性 | 0.83 | 0.87 | 0.39（未通过） | 0.31（仍未通过） |
| 事实级精度 | 0.59 | 0.85 | 0.09 | 0.04 |
| 响应精度 | 0.58 | 0.73 | 0.33 | — |

第一个问题明显改善，第三个反而更糟了。

在改动之前，评估就已经提示了该往哪里排查。再看表 2 第三行：块级精度 1.00、事实级精度 0.09、检索覆盖率 0.00。这些分数合在一起指向一个知识覆盖问题：检索到的材料名义上切题，却没有回答问题。让模型"严格以检索到的内容为依据"，补不上缺失的信息。

我们拿实验中用到的源文档核验了这一诊断。语料库里没有专门的病假政策文件，只有休假管理政策里对病假略有提及。下一步该补上政策覆盖，再去检查检索，而不是继续改 prompt。

在这个案例里，源材料缺少回答问题所需的信息，因此仅靠改动 prompt 无法解决这一失败。

在这个示例中，评估帮助我们在进一步改动之前，先明确了需要排查什么。

另一个结果说明，为什么有据性必须和其他准则一起核验。福利登记那个答案以有据性 0.90 通过，里面却有这么一句：*"我还从你的个人资料里注意到，你偏好的联系方式是 Social Media。"* 根本不存在这样的资料。

政策文档在一个流程步骤里把联系偏好列为可选项。公开的、众包的、噪声很大的 FAQ 语料里，有一组问答用 "social media" 回答了这个问题。模型把一个政策选项和一条无关的 FAQ 答案拼在一起，当作关于用户的事实说了出来。高有据性分数没能抓出这条关于用户的虚假断言。通过质量门槛，并不能证明责任约束已得到满足。

这些分数在不同运行之间可能波动，勉强通过也可能变成未通过。解读分数差异时，要结合重复运行的结果和背后的证据。第 5 节讨论如何检验评估器的可靠性。

这个小型参考实现示例，说明的是评估如何指导诊断。它既不能给出通用的改进率，也不能用来验证一次生产发布。

## 3. Agent DLC：一个生命周期，两个循环

Agent DLC 围绕一个明确的黄金标准，把六项活动串起来：**定义**、**构建**、**评估**、**发布**、**观察**和**反馈**。

早期工作已经描述过评估驱动的开发，包括 Xia 等人的[LLM agent 评估驱动开发：流程模型与参考架构](https://arxiv.org/abs/2411.13768)。Agent DLC 把这种方法落实到交付环节，通过六项活动，并配上明确的验收条件、发布权限和证据要求。

这种验收优先的做法也出现在 [Fotor 发布的 AWS 客户案例研究](https://aws.amazon.com/cn/solutions/case-studies/hengtukeji/) 中。该团队在迁移到 AgentCore runtime（Amazon Bedrock AgentCore 的一项能力）之前，先定下了可扩展性、成本、隔离性和架构灵活性方面的准则，再用运营数据验证各项改动。案例报告说，不算模型推理，工作流开销从几分钟降到几秒，并支持数千个并发活跃会话。它记录的是 Agent DLC 指导下的架构交付，质量评估被列为下一步。

定义把业务目标转化为准则、阈值和获批示例。构建设计 prompt、工具、上下文、memory 和必须满足这些准则的运行时机制。评估产出证据，判定某个候选版本是否达标。达标之后，该版本进入受控发布。观察在生产环境中持续盯着它。反馈把生产环境给出的经验回传给定义。

![围绕中央黄金标准排布的六项活动（定义、构建、评估、发布、观察、反馈）。每项活动与该标准都有明确的关系：定义产生它、构建遵循它、评估使用它、发布对照它核验、观察复用它、反馈迭代它。下方列出五个评估维度：领域理解、质量、责任、成本、性能。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/10/ML-22085-1.png)

图 1：Agent DLC 的六项活动各自与中央的黄金标准相关联。定义产生它、构建遵循它、评估使用它；发布对照它核验、观察复用它、反馈迭代它。标准下方列出五个维度

图 1 展示了每项活动如何使用或更新这一标准，从而明确它在开发与发布中的角色。

在这个外循环内部，跑着一个更快的内循环：**评分 → 检查路径 → 改一处 → 重新评估。** 它针对单个候选版本运作，回答两个问题：改哪里，以及改了有没有用。

两个循环各司其职，区别很关键。*内循环* 在标准固定不变的前提下改进 agent，*外循环* 则允许标准本身变化。开发阶段发现 agent 不查库存就推荐商品，属于内循环问题。假设生产环境的用户让 agent 替家人查询信息，却没有哪条准则覆盖这种情况，那就要动用外循环：划定授权边界、补上示例，再用内循环去满足更新后的标准。

把两者混为一谈，团队就可能想靠改 prompt 去补救一条缺失的准则。团队还可能在改进周期里扩大标准，结果说不清到底是哪处改动拉动了分数。

两个循环都会沉淀可复用的资产：业务准则、获批示例、评估器，以及过往失败如何处理的记录。这些资产比模型和框架更持久。更换模型时，用同一套准则和示例去评估替代模型。

接下来四节先讲如何把*好*定义到可核查的程度（第 4 节），以及如何对照该标准改进 agent（第 5 节）；再讲如何通过生产反馈更新标准（第 6 节），以及如何设计架构来提供评估证据（第 7 节）。

## 4. 定义*好*：五个维度，三个层级

从业务负责人定义的业务成果出发。对推荐 agent 来说，它可能是："向回头客推荐合适的产品，同时保护他们的信息。" 再把这条要求转化为覆盖五个维度的可验证准则。

*表 4. 定义准则时要兼顾全部五个维度。*

| **维度** | **关键问题** | **关注重点** |
| --- | --- | --- |
| 领域理解 | 它真的理解你的业务吗？ | 术语、别名、多跳关系、企业内部知识 |
| 质量 | 内容是否正确、完整、前后一致？ | 正确性、完整性、一致性、引用支持 |
| 责任 | 权限、边界、合规与可审计性是否都覆盖到了？ | 越权访问、信息泄露、合规硬约束、可追溯性 |
| 成本 | 每次运行花多少？规模上去后还划算吗？ | token 消耗、评估器成本、冗余步骤 |
| 性能 | 是否够快、够稳、扛得住负载？ | 延迟、吞吐量、稳定性、可用性 |

每条准则都要写清如何验证、由谁批准。"必须准确"只是目标，"每条事实断言都能追溯到检索到的来源"才是可验证的。业务专家应当批准那些把预期行为落到实处的示例。

*表 5. 准则分三个层级。决定一条准则是否卡住发布的，是层级而不是维度。*

| **层级** | **是否阻断发布？** | **如何表达** | **示例** |
| --- | --- | --- | --- |
| 硬约束 | 是 | 布尔值，每次运行判定 | 泄露其他客户的信息 |
| 发布门槛 | 达标前阻断 | k 次运行的通过率阈值 | 引用的条款至少 95% 可追溯到来源 |
| 仅监控 | 否 | 跟踪并复核，之后再升级 | 语气得体性，直到其评估器校准完成 |

给每条准则定好各自的层级，适用时再定阈值。绝不能让别处的高分抵消一次硬约束违规。

在推荐这个例子里，推荐质量是质量维度下的发布门槛，而保护其他客户的信息是责任维度下的硬约束。一条业务要求会派生出分属不同维度、不同层级的准则，各自按自己的验收条件来判定。

这些准则还决定了系统必须暴露哪些证据。下一节用这些证据来改进 agent 并决定是否发布；第 7 节讲证据要求如何反过来塑造架构。

## 5. 内循环：评估、诊断与改进

评分。让评估器与准则相匹配：明确的规则用代码判定，成本和延迟用运行时遥测，容量和可用性用负载测试与运营数据。需要判断的准则用基于模型的裁判，并以人工审核过的示例校准。评估信息保护时，除了检查禁用字段，还要纳入授权与跨用户隔离测试。每个示例运行 k 次，以衡量行为的波动。

对基于模型的裁判，要重复评估以衡量打分的波动，并把它们的判断与人工审核过的示例对照。分数小幅提升必须有佐证，才算得上改进。

检查路径。在会话、轨迹、步骤三个层次上定位失败。如果某条推荐泄露了电话号码，就顺着受影响的会话追到响应生成环节，查看资料字段是在哪里进入草稿的。根因可能藏在可见症状的上游，第 2 节已经演示过。

改一处，再重新评估。修正定位到的根因，在相同条件下对照不变的标准重复评估，确认泄露已经停止，且推荐质量仍满足其门槛。

对每种任务类型（也就是意图）分别评估发布就绪度。只发布达标的那些；未发布意图若有回退方案，该方案同样要满足商定的发布条件。

*表 6. 按维度、层级和意图划分的发布决策。*

| **网格状态** | **决策** |
| --- | --- |
| 任一硬约束失败 | 不发布。 |
| 所有硬约束通过，但有一个或多个发布门槛未达标 | 除非事先批准了有限放量，并配有明确的保障措施和终止条件，否则不发布受影响的意图；其他情况转人工处理。 |
| 所有硬约束通过，且所有发布门槛达标 | 全量发布。 |

有限放量需要在评估之前就商定验收条件、保障措施和停止条件。结果失败之后，它既不能推翻硬约束，也不能下调阈值。

发布之前，把被拦截和被拒绝的请求也纳入评估，逐一检查是否按预期处理。记录准则、阈值、评估器版本和发布决策，方便团队追溯某个版本为何获批。

通过这些检查，支持在已测试范围内发布。随后由生产监控检查：随着使用方式和依赖变化，agent 是否仍持续满足标准。

## 6. 外循环：让数据持续流动

从第一个测试请求起就记录执行轨迹，这样无论开发还是生产环境都能诊断失败。对生产交互抽样并评估以找出失败，再与业务负责人一起复核，确认预期行为。把已被现有准则覆盖的案例加入回归集。当某个案例暴露出缺失的要求时，更新标准，并用内循环去满足它。

定期运行评估，捕捉外部依赖引起的行为变化。标准变更时，把新旧两版下的结果对照，区分是 agent 退化还是测试覆盖变广了。把每条结果关联到对应的标准、测试集、评估器和 agent 版本。

## 7. 设计支撑评估的架构

评估与反馈循环需要证据，而这些证据必须由架构提供。从每条准则往回推，倒推出验证它所需的系统行为和记录。

比如，要区分工具选错还是执行失败，就得定义工具的用途、可接受的输入、输出和错误条件，并在轨迹里暴露真实的输入、结果与错误，让评估器能够定位失败。

可见，验收准则同时塑造评估与架构。打好这些基础后，从一项业务任务入手，建立基线。

## 8. 在 AWS 上起步

选一项边界明确的业务任务，争取在一周内建立初步评估基线。

- **第 1–2 天。** 让业务负责人和工程师就验收准则、层级和阈值达成一致。准备 20–30 个黄金示例，覆盖常见请求和重要边界情况，预期行为由业务负责人批准。
- **第 3–5 天。** 实现第 5 节描述的评估器，反复运行黄金集。公布基线，包括失败项以及排查这些失败所需的证据。
- **第 2 周。** 改一处，在相同条件下重新评估。记录发布决策及其支撑证据。

复盘基线之后，把评估接入发布流程并定期运行，以发现漂移。指定一名负责人复核生产失败，把确认过的案例回灌到标准里。

在 AWS 上，用 Amazon Bedrock 提供的模型来构建 agent。[Amazon Bedrock AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 是 Amazon Bedrock AgentCore 的一项能力，借助[内置评估器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/built-in-evaluators-overview.html)评估 agent 行为，并支持针对业务专属准则的自定义评估器。[AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html) 也是 Amazon Bedrock AgentCore 的一项能力，提供执行可见性，并由 Amazon CloudWatch 补足运行时监控与诊断。AgentCore runtime、Gateway、Identity 和 Memory 分别支撑执行、工具集成、身份管理与 memory 管理。
