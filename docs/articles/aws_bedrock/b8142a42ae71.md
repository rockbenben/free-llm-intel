## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 规模化 tokenomics：用 CUR 2.0 和 AWS Budgets 按 IAM 主体跟踪并封顶 Amazon Bedrock 支出

生成式 AI 的支出很难归因。在组织扩大 AI 使用范围之前，CFO 和 CTO 通常想要三个答案：每个人或每个团队花了多少，能不能封顶，以及做到这一点要投入多少工作量。

在上一篇 [Tokenomics at Scale：Jamf 如何为 Amazon Bedrock 构建实时支出管控](https://aws.amazon.com/blogs/machine-learning/tokenomics-at-scale-how-jamf-built-real-time-spend-enforcement-for-amazon-bedrock/) 里，我们讲解了一套基于 [AWS IAM Identity Center](https://aws.amazon.com/iam/identity-center/)、[Amazon Athena](https://aws.amazon.com/athena/)（对 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 的[模型调用日志](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html) 做查询）和 [AWS Lambda](https://aws.amazon.com/lambda/) 构建的自建管控闭环。这套做法能做到近实时控制，但代码要由你自己拥有和运维。

本文展示如何只用 AWS 原生功能，就获得按身份划分的 Amazon Bedrock 成本可见性和可强制执行的支出上限，常见情形下无需编写任何应用代码。这套做法依赖三样东西：Amazon Bedrock 自动记录的 [IAM 主体归属](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-iam-principal-tracking.html)；用于出报告的 [AWS Cost and Usage Reports](https://docs.aws.amazon.com/cur/latest/userguide/table-dictionary-cur2.html)（CUR）2.0 或 [AWS Cost Explorer](https://aws.amazon.com/aws-cost-management/aws-cost-explorer/)；以及带预算操作来做强制的 [AWS Budgets](https://aws.amazon.com/aws-cost-management/aws-budgets/)。读完之后，你会拿到按身份划分的成本报告，以及一道在越过阈值时自动限制 Amazon Bedrock 访问的护栏。

## 解决方案概述

方案分三部分：归属、报告、强制。

**归属。** Amazon Bedrock 会为每一次推理请求记录 AWS Identity and Access Management（IAM）主体身份，即 [IAM 用户](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_users.html) 或[角色](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles.html)。这一步自动发生，不用改动你的 Amazon Bedrock 模型推理调用。如果多人共用一个角色，就用在担任角色时传入的会话标签补充每用户明细。如果每个人或每个应用都有自己的角色，角色上的主体标签就够了。

**报告。** 把这些标签激活为成本分配标签，然后在 Cost Explorer 里读数据，得到纯控制台视图；或在 CUR 2.0 数据导出里读数据，做详细的逐项分析和 SQL 查询。

**强制。** 创建一个范围限定到 Amazon Bedrock、并按某个身份或标签值过滤的 AWS 预算，再挂上一个在越过阈值时应用 Deny IAM 策略的[预算操作](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-controls.html)。

下面各节结合实施步骤，逐一展开这三部分。

## 先决条件

部署这套方案，你需要：

- 一个启用了 Amazon Bedrock 模型访问的 [AWS 账户](https://aws.amazon.com/account/)。
- 给 [IAM 主体](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-iam-principal-tracking.html#cost-mgmt-iam-principal-tracking-principal-types) 打标签、激活[成本分配标签](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-alloc-tags.html)、[创建数据导出](https://docs.aws.amazon.com/cur/latest/userguide/dataexports-create.html)，以及创建预算和预算操作的权限。
- 通过 IAM 角色或 IAM 用户访问 Amazon Bedrock。
- 配置了相应凭证的 [AWS Command Line Interface](https://aws.amazon.com/cli/)（AWS CLI）。
- 一个 CUR 2.0 数据导出，以及一个用来接收它的 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（*Amazon S3*）存储桶。*（可选，用于详细的逐项分析）*。
- Amazon Athena。*（可选，用于查询导出）*。

[AWS Billing Console](https://aws.amazon.com/aws-cost-management/aws-billing/) 的访问权与大多数 IAM 权限分开管理。动手前先确认你已经具备。

## 演练

配置任何东西之前，先看看你已经有什么。Amazon Bedrock 会自动记录每次推理请求的调用方身份。打开 Cost Explorer，把 Service 过滤到 Amazon Bedrock，再按可用的身份或标签维度分组。对于每个应用或每个人都已使用各自独立 IAM 角色的账户，这份可见性可能就够了。

要配置更多可见性：

- 第 1 步给你身份级别的可见性。
- 第 2 到第 4 步加上标签维度和详细报告。
- 第 5 步加上强制。

### 第 1 步：确定身份如何映射到你的用户

怎么打标签，取决于你的 IAM 主体是怎么组织的。

**每人或每个应用一个角色。** 把主体标签直接挂到每个 IAM 角色或用户上。它们是静态的，对该主体发出的每个请求都生效。用 IAM 控制台，或者 AWS CLI：

```
aws iam tag-role \
  --role-name BedrockDeveloperRole-alice \
  --tags Key=user,Value=alice@example.com Key=team,Value=platform Key=CostCenter,Value=CC-1001
```

**多人共用的共享角色，或网关。** 主体标签区分不了共享角色上的用户，因为每个会话带的标签都一样。改用会话标签，在担任角色时传入。会话标签是动态的，可以逐个会话变化。如果会话标签和主体标签用了同一个键，该会话里以会话标签为准。

角色的信任策略必须允许 `sts:TagSession`。会话标签有三种传法：

- `sts:AssumeRole` 配 `--tags`，适用于为每个用户或租户担任角色的网关。
- `AssumeRoleWithWebIdentity`，标签放在 OpenID Connect（OIDC）ID token 的 https://aws.amazon.com/tags claim 里（这是 claim 名，不是可以打开浏览的 URL）。
- `AssumeRoleWithSAML`，通过在身份提供商的 Security Assertion Markup Language（SAML）断言里映射 `PrincipalTag:*` 属性。

如果你的组织已经为别的用途采集了 `saml:sub` 之类的 claim，单凭这一点并不会让它在这里可用。你的身份提供商必须另外把该属性映射到 `PrincipalTag:*` SAML 属性语句，并且角色的信任策略允许 `sts:TagSession`，它才会作为会话标签流进来。两个集成取自同一份 SAML 断言，但配置彼此独立。常用的标签键有 user、team、Department、CostCenter 和 Environment。每个 IAM 用户或角色最多可以应用 50 个主体标签或会话标签。

### 第 2 步：激活成本分配标签

标签不激活，就不会出现在账单数据里。

- 打开 [AWS Billing and Cost Management Console](https://aws.amazon.com/aws-cost-management/billing-and-cost-management-console-home/)。
- 选择 **Cost allocation tags**。
- 按类型 **IAM principal** 过滤。
- 选中你的标签键，选择 **Activate**。

在 [AWS Organization](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_introduction.html) 里，要在[管理账户](https://docs.aws.amazon.com/managedservices/latest/userguide/management-account.html)（付款方）中激活 IAM 主体成本分配标签。成员账户无法自行激活。

有两点要心里有数：

- 标签键要等该主体至少发起过一次 Amazon Bedrock 调用之后，才会出现在这个列表里；所以如果列表看着是空的，先做一次测试调用。
- 新打上的标签键最多要 24 小时才会出现以供激活，激活之后还可能再要最多 24 小时才开始填充账单数据。

激活默认不追溯生效，所以要在需要数据之前就把标签激活好。

### 第 3 步：创建包含调用方身份的 CUR 2.0 数据导出

如果 Cost Explorer 足够满足你的报告需求，跳过这一步。

- 在 Billing and Cost Management 控制台里，选择 **Data Exports**。
- 选择 **Create**，创建一个 CUR 2.0（Standard）导出。
- 在 **Additional export content** 下，勾选 **Include caller identity (IAM principal) allocation data**。
- 在 **Time granularity** 下，选 **Hourly**。
- 在 **Report data integration** 下，选 **Amazon Athena**。这会把文件格式设为 Parquet，更重要的是，会把一份设置脚本连同导出数据一起投递到你的 S3 存储桶。
- 选定目标 Amazon S3 存储桶。
- 把投递的设置脚本（或它定义的 Glue crawler / DDL）跑一次。真正创建出第 4 步要查的 Glue Data Catalog 表的，正是这一步；前面那套控制台流程不会替你自动建好。

如果你在启用身份归属之前就已经建过 CUR 2.0 导出，它不会追溯补上身份数据。新建一个导出，并勾选调用方身份选项。在导出里，主体标签和会话标签显示为前缀 `iamPrincipal/` 的列，资源标签显示为 `resourceTags/`。比如标签键 team 会显示为 `iamPrincipal/team`。AWS 在 [aws-samples/sample-cur-iam-principal-bedrock-tracking](https://github.com/aws-samples/sample-cur-iam-principal-bedrock-tracking) 里发布了一套针对这一模式的现成查询。

### 第 4 步：读取数据

下图对比读取数据的两种方式：一条是走 Cost Explorer 的纯控制台路径，另一条是借助 Amazon Athena 对 CUR 2.0 导出的 SQL 路径。

![两条报告路径：Cost Explorer 控制台视图，以及在 Amazon Athena 中对 CUR 2.0 导出跑 SQL 查询](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/11/21962-2.png)

图 2：用 Cost Explorer 出报告，对比 CUR 2.0 与 Amazon Athena

**控制台路径，零自定义代码。** 把 Cost Explorer 过滤到 Amazon Bedrock、按你的标签键分组，就能以图表和表格看到每个团队或每个用户的支出。这覆盖了大多数日常报告需求，不用写查询。

**SQL 路径，低代码。** 把 Amazon Athena 指向 CUR 2.0 导出，按 `iamPrincipal/team` 和用量类型分组汇总支出：

```
SELECT
    tags['iamPrincipal/team'] AS team,
    line_item_usage_type,
    SUM(line_item_unblended_cost) AS cost
FROM cur2_view
WHERE product_servicecode IN ('AmazonBedrock', 'AmazonBedrockService')
AND billing_period = '2026-09'
GROUP BY 1, 2
ORDER BY 3 DESC
```

几点注意：

- **服务代码**：Amazon Bedrock 支出可能记在多个 `product_servicecode` 值下，例如 `AmazonBedrock` 和 `AmazonBedrockService`。
- **表名**：表名（`cur2_view`）就是第 3 步的设置脚本创建 Glue 表时给它起的名字。若不一致，去查脚本或你的 Glue catalog。不管表名怎么变，列名都与 CUR 2.0 的 Parquet schema 一致。
- **计费周期列。** 确认你的导出是怎么给出周期的。有些导出用 `billing_period`（YYYY-MM），另一些按起始日期或年 / 月列做分区。

有两点值得带进你写的任何查询里。

- **算上所有 token 类型**：Amazon Bedrock 对四种 token 计费，费率各不相同：input、output、cache read、cache write。每种都是单独的行项目，有自己的用量类型和单价，所以只把 input 和 output 加起来会少算。对大量使用 prompt caching 的工作负载，缺口最大。最新信息见 AWS 文档 [Understanding Amazon Bedrock pricing in CUR](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-understanding-cur-data.html#cost-mgmt-cur-pricing)。
- **把费率对到行项目，而不是对到模型**：CUR 里 Amazon Bedrock 的定价由三件事决定：token 类型、服务层级，以及请求是否经由跨区域推理路由。区域内与跨区域请求定价不同，服务层级也体现在用量类型里。用量类型带一个表示跨区域路由和服务层级的后缀，所以如果你的工作负载混用这些，就把费率对到每个行项目，而不是给每个模型套一个费率。示例见 [CUR usage type examples](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-understanding-cur-data.html#cost-mgmt-cur-usage-type-examples)。

### 第 5 步：用 AWS Budgets 和预算操作加上强制

挂接这件事由 AWS Budgets 完成，所以这个流程没有自定义代码。预算操作挂在某个具体的 IAM 用户、组或角色上。只有当这个人本来就有自己的角色时，这才能只隔离他一个人的访问。如果你的 Amazon Bedrock 流量走的是很多人共用的角色，挂到该角色上的 Deny 操作会挡住这个角色上的所有人，而不只是越过阈值的那个人。下图解释了这套强制流程。

![AWS Budgets 阈值触发一个挂上 Deny IAM 策略的预算操作](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/11/21962-3.png)

图 3：用 AWS Budgets 和预算操作做强制

AWS Budgets 能在越过阈值时执行一个操作。可用操作包括应用自定义 IAM 策略、应用 service control policy（SCP），以及针对 Amazon Elastic Compute Cloud（Amazon EC2）或 Amazon Relational Database Service（Amazon RDS）实例。对本用例来说，相关的是 IAM 策略操作。

先建好操作要挂的 Deny 策略。下面这个例子拒绝成本较高的模型，同时留一个成本较低的模型可用，让用户还能继续干活：

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": [
        "arn:aws:bedrock:*::foundation-model/[HIGHER-COST-MODEL-ID]"
      ]
    }
  ]
}
```

把 `[HIGHER-COST-MODEL-ID]` 换成你在自己环境里想拒绝的模型 ID。

然后设置权限和预算本身。

这里有两个不同的角色，而 AWS 托管策略只覆盖其中一个：

**你自己的用户或角色**（配置预算的那个）需要 AWS 托管策略 `AWSBudgetsActionsWithAWSResourceControlAccess`。它授予预算权限，外加把预算操作角色交给 AWS Budgets 所需的、带条件的 `iam:PassRole`。

**AWS Budgets 为执行操作而担任的 IAM 角色**，在本用例里没有哪一个具名的托管策略能覆盖。创建它时，信任策略要允许主体 `budgets.amazonaws.com` 担任（用 `aws:SourceArn` 和 `aws:SourceAccount` 条件限定范围），权限策略要授予 `iam:AttachRolePolicy` 和 `iam:DetachRolePolicy`（如果还用 SCP，再加 `organizations:AttachPolicy` 和 `organizations:DetachPolicy`）。可授予的权限见 [为 AWS Budgets 设置运行预算操作所用的角色](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-action-role.html)。

- 创建前面说的那个预算操作角色。
- 创建一个范围限定到 Amazon Bedrock、并按你想封顶的身份或标签值过滤的成本预算。
- 在 **Configure alerts** 里加一个告警阈值。选 **Actual** 针对已发生的支出，选 **Forecasted** 则在支出落地之前就行动。
- 在 **Attach actions** 下选 **Add Action**，选定预算操作角色，再选 IAM 策略操作。选中 Deny 策略，以及要挂到它上面的 IAM 用户、组或角色。
- 要做自动强制，选 **Yes** 让操作自动执行。选 **No** 则要求人工在 **Alert details** 页逐条批准每个操作。
- 至少配一个通知，让受影响的用户知道访问为什么变了。

一个阈值可以挂多个操作，一个预算也可以设多个阈值。分层就是这么搭出来的：比如在 80% 时拒绝高端模型，在 100% 时拒绝中端模型，而始终不拒绝低成本模型。

只有管理账户能应用 SCP，而且从管理账户可以把 SCP 应用到别的账户。

## 注意事项

**AWS Budgets 不是近实时的**：预算数据每天最多刷新三次，所以在操作执行之前，支出可能已经越过阈值。

**成本分配标签不追溯**：新打上的标签键最多要 24 小时才会出现，激活之后还可能再要最多 24 小时才开始填充账单数据。

**CUR 不含逐请求的行项目**：经典 CUR 和 CUR 2.0 都是按一小时或一天，把 Amazon Bedrock 成本按用量类型、操作和定价 / 资源属性聚合起来。

**IAM 主体字段需要 CUR 2.0**：旧版 CUR 格式不含这些字段。两种格式都提供按 token 的成本明细。

**会话标签绑定在 AssumeRole 时刻，而不是按请求绑定。** 用该会话凭证发起的每一次调用，它们的值都固定不变，而且只以聚合账单数据的形式出现。会话标签不会写进模型调用日志，日志记录的是调用方的 `identity.arn`。要在请求级别区分共享会话上的用户，可以给每个用户设 `RoleSessionName`，或在每次调用的请求元数据里带上用户。

**预算操作挂在 IAM 用户、组和角色上。** 如果你的用户是联邦身份、没有常设 IAM 身份，操作就需要一个角色作为目标。这正是「每个人或每个应用各有自己的角色」时这套模式最顺的原因。如果用户共用一个角色，或者以联邦方式接入却没有自己的角色，见我们上一篇[文章](https://aws.amazon.com/blogs/machine-learning/tokenomics-at-scale-how-jamf-built-real-time-spend-enforcement-for-amazon-bedrock/)，那里有按用户强制的做法。

**共享网关角色默认会折叠归属。** 对于大型语言模型（LLM）网关，捕获到的身份是网关的执行角色。

**新模型要留意。** 用量类型是跟模型绑定的。启用新模型时，确认它按预期出现在你的查询和预算过滤里，别想当然以为已经覆盖到了。
