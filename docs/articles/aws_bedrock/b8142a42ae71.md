## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 大规模代币经济学：使用 CUR 2.0 和 AWS 预算跟踪和限制每个 IAM 主体的 Amazon Bedrock 支出

生成式人工智能的支出很难归因。在组织扩展人工智能访问之前，首席财务官和首席技术官通常需要三个答案：我们每个人或每个团队的支出是多少，我们是否可以对其进行限制，以及需要多少工作才能实现这一目标。

在我们之前的文章中，[大规模的 Tokenomics：Jamf 如何为 Amazon Bedrock 构建实时支出执行](https://aws.amazon.com/blogs/machine-learning/tokenomics-at-scale-how-jamf-built-real-time-spend-enforcement-for-amazon-bedrock/)，我们解释了基于 [AWS IAM Identity] 构建的自定义执行循环Center](https://aws.amazon.com/iam/identity-center/)、[Amazon Athena](https://aws.amazon.com/athena/) over [Amazon Bedrock](https://aws.amazon.com/bedrock/) [模型调用日志](https://docs.aws.amazon.com/bedrock/latest/userguide/model-inspiration-logging.html) 和 [AWS Lambda](https://aws.amazon.com/lambda/)。这种方法提供了近乎实时的控制，但它需要您拥有并操作代码。

本文展示了如何仅使用 AWS 原生功能来获取每个身份的 Amazon Bedrock 成本可见性和可执行的支出限制，而无需为常见情况编写应用程序代码。该方法依赖于三件事：[IAM 主体归属](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-iam-principal-tracking.html)，Amazon Bedrock 自动记录； [AWS 成本和使用情况报告](https://docs.aws.amazon.com/cur/latest/userguide/table-dictionary-cur2.html) (CUR) 2.0 或 [AWS Cost Explorer](https://aws.amazon.com/aws-cost-management/aws-cost-explorer/) 用于报告；以及 [AWS 预算](https://aws.amazon.com/aws-cost-management/aws-budgets/) 以及执行预算行动。最后，您将获得每个身份的成本报告和一个自动护栏，当超过阈值时，该护栏会限制 Amazon Bedrock 访问。

## 解决方案概述

该解决方案分为三个部分：属性、报告和强制。

**属性。** Amazon Bedrock 为每个推理请求捕获 AWS Identity and Access Management (IAM) 委托人身份、[IAM 用户](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_users.html) 或[角色](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles.html)。此过程会自动发生，无需更改您的 Amazon Bedrock 模型推理调用。如果多人共享一个角色，您可以添加每个用户的详细信息以及在角色假设时传递的会话标签。如果每个人或应用程序都有自己的角色，角色上的主体标签就足够了。

**报告。** 将这些标签激活为成本分配标签，然后在 Cost Explorer 中读取数据以获取仅限控制台的视图，或在 CUR 2.0 数据导出中读取数据以获取详细的行项目分析和 SQL 查询。

**强制执行。** 创建一个范围为 Amazon Bedrock 的 AWS 预算并筛选为一个身份或标签值，然后附加一个在超过阈值时应用拒绝 IAM 策略的[预算操作](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-controls.html)。

以下部分更详细地显示了每个部分以及实施步骤。

## 先决条件

要部署此解决方案，您需要：

- 启用了 Amazon Bedrock 模型访问的 [AWS 账户](https://aws.amazon.com/account/)。
- 标记 [IAM 主体](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-iam-principal-tracking.html#cost-mgmt-iam-principal-tracking-principal-types) 的权限，激活 [成本分配[创建数据导出](https://docs.aws.amazon.com/cur/latest/userguide/dataexports-create.html)，并创建预算和预算操作。
- 通过 IAM 角色或 IAM 用户访问 Amazon Bedrock。
- [AWS 命令​​行界面](https://aws.amazon.com/cli/) (AWS CLI) 配置了适当的凭证。
- CUR 2.0 数据导出和用于接收它的 [Amazon Simple Storage Service](https://aws.amazon.com/s3/) (*Amazon S3*) 存储桶。 *（可选，用于详细的行项目分析）*。
- 亚马逊雅典娜。 *（可选，用于查询导出）*。

[AWS 账单控制台](https://aws.amazon.com/aws-cost-management/aws-billing/) 访问权限与大多数 IAM 权限分开管理。开始之前请确认您已拥有它。

## 演练

在配置任何内容之前，请检查您已有的内容。 Amazon Bedrock 会自动记录每个推理请求的呼叫者身份。打开 Cost Explorer，筛选到 Amazon Bedrock 的服务，并按可用身份或标签维度进行分组。对于每个应用程序或个人已使用不同 IAM 角色的账户，这可能就是您所需的全部可见性。

要配置附加可见性：

- 第 1 步为您提供身份级别的可见性。
- 步骤 2 到 4 添加标签维度和详细报告。
- 第 5 步增加了强制执行。

### 第 1 步：决定如何将身份映射到您的用户

您的标记方式取决于您的 IAM 委托人的组织方式。

**每人或每个应用程序一个角色。** 将委托人标签直接附加到每个 IAM 角色或用户。这些是静态的，适用于该主体的每个请求。使用 IAM 控制台或 AWS CLI：
```
aws iam tag-role \
  --role-name BedrockDeveloperRole-alice \
  --tags Key=user,Value=alice@example.com Key=team,Value=platform Key=CostCenter,Value=CC-1001
```
**多人使用的共享角色，或网关。**主体标签无法区分共享角色上的用户，因为每个会话都带有相同的标签。请改用会话标签，在担任角色时传递。会话标签是动态的，并且每个会话可能会有所不同。如果会话标签和主体标签共享密钥，则会话标签胜出该会话。

角色的信任策略必须允许“sts:TagSession”。会话标签可以通过三种方式传递：

- `sts:AssumeRole` 与 `--tags`，用于为每个用户或租户承担角色的网关。
- `AssumeRoleWithWebIdentity`，在 OpenID Connect (OIDC) ID 令牌的 https://aws.amazon.com/tags 声明中包含标签（这是声明名称，而不是您浏览到的 URL）。
- `AssumeRoleWithSAML`，通过在身份提供者的安全断言标记语言 (SAML) 断言中映射 `PrincipalTag:*` 属性。

如果您的组织已经出于其他目的捕获了诸如“saml:sub”之类的声明，那么仅此一项并不能使其在此处可用。您的身份提供者必​​须将该属性单独映射到 `PrincipalTag:*` SAML 属性语句，并且角色的信任策略必须允许 `sts:TagSession`，然后它才能作为会话标签流动。这两个集成源自相同的 SAML 断言，但独立配置。常见的标签键有用户、团队、部门、成本中心和环境。每个 IAM 用户或角色最多可以应用 50 个委托人或会话标签。

### 步骤 2：激活成本分配标签

在您激活标签之前，标签不会出现在账单数据中。

- 打开 [AWS 账单和成本管理控制台](https://aws.amazon.com/aws-cost-management/billing-and-cost-management-console-home/)。
- 选择**成本分配标签**。
- 按类型 **IAM 主体** 过滤。
- 选择您的标签键并选择**激活**。

在 [AWS 组织](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_introduction.html) 中，激活 [管理账户](https://docs.aws.amazon.com/managementservices/latest/userguide/management-account.html)（付款人）中的 IAM 主体成本分配标签。会员账户无法独立激活。

有两件事值得期待：

- 标签键仅在委托人至少进行一次 Amazon Bedrock 调用后才会出现在此列表中，因此如果列表看起来为空，请先进行测试调用。
- 新应用的标签密钥最多可能需要 24 小时才会显示以进行激活，然后在激活后最多需要 24 小时才能开始填充账单数据。

默认情况下，激活不会追溯应用，因此请在需要数据之前激活标签。

### 步骤 3：创建包含呼叫者身份的 CUR 2.0 数据导出

如果 Cost Explorer 足以满足您的报告，请跳过此步骤。

- 在计费和成本管理控制台中，选择“**数据导出**”。
- 选择 **创建** 并创建 CUR 2.0（标准）导出。
- 在 **其他导出内容** 下，选择 **包括调用者身份（IAM 主体）分配数据**。
- 在**时间粒度**下，选择每小时。
- 在 **报告数据集成** 下，选择 **Amazon Athena**。这会将文件格式设置为 Parquet，重要的是，会将设置脚本与导出数据一起传送到您的 S3 存储桶。
- 选择目标 Amazon S3 存储桶。
- 运行一次交付的设置脚本（或其定义的 Glue 爬虫/DDL）。这实际上是创建您将在步骤 4 中查询的 Glue 数据目录表的内容。前面的控制台流程不会自动为您创建它。

如果您在启用身份归因之前已创建 CUR 2.0 导出，则它将不会追溯包含身份数据。创建一个新的导出并选择呼叫者身份选项。在导出中，主体和会话标签显示为前缀为“iamPrincipal/”的列，资源标签显示为“resourceTags/”。例如，标签关键团队显示为“iamPrincipal/team”。 AWS 在 [aws-samples/sample-cur-iam-principal-bedrock-tracking](https://github.com/aws-samples/sample-cur-iam-principal-bedrock-tracking) 中发布了针对此确切模式的现成查询集。

### 第四步：读取数据

下图比较了读取数据的两种方法：通过 Cost Explorer 的纯控制台路径，以及使用 Amazon Athena 通过 CUR 2.0 导出的 SQL 路径。

![两个报告路径、Cost Explorer 控制台视图和通过 Amazon Athena 中的 CUR 2.0 导出的 SQL 查询](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/11/21962-2.png)

图 2：使用 Cost Explorer 进行报告与 CUR 2.0 和 Amazon Athena 的比较

**控制台路径，无自定义代码。** Cost Explorer，过滤到 Amazon Bedrock 并按您的标签键分组，以图表和表格的形式提供每个团队或每个用户的支出。这涵盖了大多数重复的报告需求，并且不需要编写查询。

**SQL 路径，低代码。** 将 Amazon Athena 指向 CUR 2.0 导出，以按“iamPrincipal/team”和使用类型分组支出：
```
SELECT
    tags['iamPrincipal/team'] AS team,
    line_item_usage_type,
    SUM(line_item_unblended_cost) AS cost
FROM cur2_view
WHERE product_servicecode IN ('AmazonBedrock', 'AmazonBedrockService')
AND billing_period = '2026-09'
GROUP BY 1, 2
ORDER BY 3 DESC
```
注意事项：

- **服务代码**：Amazon Bedrock 支出可以记录在多个“product_servicecode”值下，例如“AmazonBedrock”和“AmazonBedrockService”。
- **表名称**：表名称 (`cur2_view`) 是步骤 3 中的设置脚本在创建 Glue 表时命名的名称。检查脚本或 Glue 目录是否不同。无论表名称如何，列名称都与 CUR 2.0 Parquet 架构匹配。
- **计费周期列。** 确认您的导出如何公开该周期。某些导出使用“billing_period”(YYYY-MM)。其他分区则按开始日期或年/月列进行分区。

有两个注释值得您在编写的任何查询中携带。

- **计算所有令牌类型**：Amazon Bedrock 对四种令牌类型进行计费，每种令牌类型的速率不同：输入、输出、缓存读取和缓存写入。每个都是一个单独的行项目，具有自己的使用类型和单价，因此仅对输入和输出进行求和会导致计数不足。对于大量使用即时缓存的工作负载来说，差距最大。请参阅 AWS 文档 [了解以 CUR 表示的 Amazon Bedrock 定价](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-understanding-cur-data.html#cost-mgmt-cur-pricing) 了解最新信息。
- **将费率与订单项相匹配，而不是与模型相匹配**：CUR 中的 Amazon Bedrock 定价由三个因素决定：令牌类型、服务层级以及请求是否通过跨区域推理进行路由。区域内和跨区域请求的定价不同，服务等级也反映在使用类型中。使用类型带有表示跨区域路由和服务层的后缀，因此，如果您的工作负载混合使用这些内容，请将费率与每个行项目相匹配，而不是对每个模型应用一种费率。请参阅 [CUR 使用类型示例](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-understanding-cur-data.html#cost-mgmt-cur-usage-type-examples) 了解示例。

### 步骤 5：通过 AWS 预算和预算操作添加强制执行

AWS Budgets 执行附加，因此此工作流程没有自定义代码。预算操作附加到特定的 IAM 用户、组或角色。仅当某人已经拥有自己的角色时，这才会隔离该人的访问权限。如果您的 Amazon Bedrock 流量通过许多人共享的角色，则附加到该角色的拒绝操作会阻止该角色上的所有人，而不仅仅是越过阈值的人。下图解释了执行工作流程。

![触发附加拒绝 IAM 策略的预算操作的 AWS 预算阈值](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/11/21962-3.png)

图 3：AWS 预算和预算行动的执行

AWS Budgets 可以在超过阈值时运行操作。可用的操作包括应用自定义 IAM 策略、应用服务控制策略 (SCP) 以及定位 Amazon Elastic Compute Cloud (Amazon EC2) 或 Amazon Relational Database Service (Amazon RDS) 实例。对于此用例，IAM 策略操作是相关的。

首先，创建操作将附加的拒绝策略。此示例拒绝较高成本的模型，同时保留较低成本的模型可用，以便用户可以继续工作：
```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": [
        "arn:aws:bedrock:*::foundation-model/[HIGHER-COST-MODEL-ID]"
      ]
    }
  ]
}
```
将“[HIGHER-COST-MODEL-ID]”替换为您要在环境中拒绝的模型 ID。

然后设置权限和预算本身。

这里有两个不同的角色，AWS 托管策略仅涵盖其中之一：

**您自己的用户或角色**（配置预算的用户或角色）需要 AWS 托管策略“AWSBudgetsActionsWithAWSResourceControlAccess”。它授予预算权限以及将预算操作角色移交给 AWS Budgets 所需的条件“iam:PassRole”。

**AWS Budgets 假定执行操作的 IAM 角色**不包含在此用例的单个命名托管策略中。使用允许主体“budgets.amazonaws.com”代入它的信任策略（范围为“aws:SourceArn”和“aws:SourceAccount”条件）以及授予“iam:AttachRolePolicy”和“iam:DetachRolePolicy”（以及“organizations:AttachPolicy”和“organizations:DetachPolicy”，如果您也使用的话）的权限策略来创建它SCP）。有关可授予的权限，请参阅[设置 AWS Budgets 角色以运行预算操作](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-action-role.html)。

- 创建前面描述的预算行动角色。
- 创建以 Amazon Bedrock 为范围的成本预算，并筛选出您想要限制的身份或标签值。
- 在**配置警报**中，添加警报阈值。选择**实际**以实现已实现的支出，或选择**预测**以在支出落地之前采取行动。
- 在 **附加操作** 下，选择 **添加操作**，选择预算操作角色，然后选择 IAM 策略操作。选择拒绝策略以及要将其附加到的 IAM 用户、组或角色。
- 对于自动执行，选择 **是** 以自动运行操作。选择**否**，要求人工批准**警报详细信息**页面中的每个操作。
- 至少配置一个通知，以便受影响的用户知道访问权限发生变化的原因。

您可以将多个操作附加到一个阈值，并将多个阈值附加到一个预算。这就是构建层级的方式：例如，拒绝 80% 的高级模型和 100% 的中端模型，同时从不拒绝低成本模型。

只有管​​理账户才能应用 SCP，并且您可以从管理账户将 SCP 应用于其他账户。

## 注意事项

**AWS 预算不是近乎实时的**：预算数据每天刷新最多 3 次，因此在操作运行之前支出可能会超过阈值。

**成本分配标签不具有追溯力**：新应用的标签密钥预计最多 24 小时内会出现，然后在激活后最多 24 小时内才会开始填充计费数据。

**CUR 不包含每个请求行项目**：经典 CUR 和 CUR 2.0 均按一小时或一天的使用类型、操作和定价/资源属性汇总 Amazon Bedrock 成本。

**IAM 主体字段需要 CUR 2.0**：旧版 CUR 格式不包含它们。每个代币的成本细目都有两种格式。

**会话标签是在 AssumeRole 时绑定的，而不是按请求绑定的。** 对于使用该会话凭证进行的每次调用，它们的值都是恒定的，并且它们仅作为聚合的计费数据显示。会话标签不会写入模型调用日志。日志捕获调用者的“identity.arn”。要在请求级别区分共享会话上的用户，请使用每个用户的“RoleSessionName”，或在每次调用的请求元数据中设置用户。

**预算操作附加到 IAM 用户、组和角色。** 如果您的用户是联合的并且没有常设 IAM 身份，则该操作需要一个目标角色。这就是为什么当每个人或应用程序都有自己的角色时该模式效果最好的原因。如果您的用户共享角色或在没有自己角色的情况下联合，请参阅我们之前的[帖子](https://aws.amazon.com/blogs/machine-learning/tokenomics-at-scale-how-jamf-built-real-time-spend-enforcement-for-amazon-bedrock/)，了解每用户强制执行方法。

**默认情况下，共享网关角色会折叠归因。** 对于大型语言模型 (LLM) 网关，捕获的身份是网关的执行角色。

**新模型需要注意。** 使用类型特定于模型。当您启用新模型时，请确认它按预期出现在您的查询和预算过滤器中，而不是假设它已被覆盖。
