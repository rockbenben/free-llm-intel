# 借助 AWS HealthOmics 与 Amazon Bedrock AgentCore 加速基因组变异解读

基因组研究正处在一个具有变革意义的十字路口：测序数据的指数级增长，要求同样先进的分析能力。根据[千人基因组计划（1000 Genomes Project）](https://www.nature.com/articles/nature15393)，一个典型的人类基因组与参考序列在 410 万至 500 万个位点上存在差异，其中大多数变异是 SNP 与短 indel。这些变异在个体之间汇总后，通过多基因风险评分（PRS）体现出疾病易感性的差异。基因组分析工作流难以将如此大规模的变异数据转化为可付诸行动的洞见。这些流程仍然割裂，需要研究人员手工编排复杂的流水线，涵盖变异注释、质量过滤以及与 [ClinVar](https://pubmed.ncbi.nlm.nih.gov/29165669/) 等外部数据库的集成。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/18/Picture-1-7.png)

[AWS HealthOmics](https://aws.amazon.com/healthomics/) 工作流连同 [Amazon S3 Tables](https://aws.amazon.com/s3/features/tables/) 与 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 一起，为这些挑战提供了一套具有变革意义的解决方案。HealthOmics 工作流支持将 Variant Call Format（VCF）文件的注释与富有洞见的本体无缝集成。随后，经 VEP 注释的 VCF 文件需要转换为结构化数据集，存储在经过优化的 S3 Tables 中，以提升在大型变异队列上的查询性能。运行在 Amazon Bedrock AgentCore 上的 [Strands Agents SDK](https://strandsagents.com/latest/) 提供了一套安全且可扩展的 AI agent 应用，使研究人员无需专业的查询技能即可与复杂的基因组数据集交互。

在这篇博文中，我们展示 agentic 工作流如何借助自然语言界面，大规模加速基因组流水线的处理与解读。我们演示一个完整的基因组变异解读 agent，它将自动化数据处理与智能分析相结合，覆盖从原始 VCF 文件摄入到对话式查询界面的整个工作流。最重要的是，该解决方案消除了长期以来把基因组分析局限于专业生物信息学家的技术门槛。这使临床研究人员能够上传原始 VCF 文件，并立即提出诸如“哪些患者在 BRCA1 中存在致病变异？”或“给我看这个队列中的耐药变异”之类的问题。该解决方案的代码可在 AWS 生命科学起始 agent 的[开源工具包 ](https://github.com/aws-samples/amazon-bedrock-agents-healthcare-lifesciences/tree/main/agents_catalog/17-variant-interpreter-agent)仓库中获取。

## 理解基因组分析中的变异注释

基因组变异解读的基础，依赖于将原始遗传变异与生物学及临床语境联系起来的完整注释流水线。Variant Effect Predictor（VEP）与 ClinVar 代表了现代基因组分析工作流中的两个必要组成部分，各自提供互补的信息，研究人员必须将其整合才能得出有意义的洞见。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/18/Picture-2-1.png)

这张对比可视化图展示了 ClinVar 与 VEP 在基因组变异解读方面各自不同却又互补的注释能力。ClinVar 注释（左）主要聚焦于临床意义评估，提供经人工整理的致病性分类（CLNSIG）、证据质量指标（CLNREVSTAT）以及与临床决策直接相关的疾病关联（CLNDN）。VEP 注释（右）则提供全面的功能信息，包括后果类型（missense_variant、synonymous_variant、intron_variant）、影响严重程度分级（HIGH、MODERATE、LOW、MODIFIER）、基因符号，以及带详细位置信息的转录本特异性效应。

## 当前注释工作流面临的挑战

变异注释工作流通常遵循一个顺序流程，包含：

- 初始 VCF 处理：来自测序系统的原始变异调用格式（VCF）文件需要预处理，以规范化表示并过滤低质量调用。
- VEP 注释：运行 Variant Effect Predictor 工具需要大量计算资源，对每个样本含数百万变异的全基因组测序数据尤其如此。取决于可用计算资源与注释深度，单个基因组的 VEP 分析可能需要 2 至 8 小时。
- ClinVar 集成：临床注释必须从 ClinVar 检索，并通过一个独立流程与变异匹配，这需要数据库查询与格式转换。
- 多样本集成：创建队列级分析需要跨样本进行复杂的连接操作，通常要借助专用工具完成，而这些工具会生成难以高效查询的大型扁平文件。
- 解读：科学家随后必须使用各种工具对注释后的数据进行筛选、排序与分析——这一过程往往需要自定义脚本和深厚的生物信息学专业知识。这一技术瓶颈意味着临床研究人员无法独立探索自己的基因组数据，从提出生物学问题到获得答案之间会产生数天乃至数周的延迟。

## 数据集的复杂性与规模

[千人基因组计划第 3 阶段 DRAGEN 再分析](https://registry.opendata.aws/ilmn-dragen-1kgp/)等数据集体现了基因组变异分析的规模，其中包含：

- 来自多样化人群的 2,500 多个体样本
- 所有样本合计约 8,500 万个独特变异
- 必须协调统一的多个注释版本（DRAGEN 3.5、3.7、4.0 与 4.2）
- 与 SNP、indel 并存的复杂结构变异

这种复杂性给依赖扁平文件处理与手工集成步骤的传统分析流水线造成了显著瓶颈。

## 解决方案概览

跨多名患者构建基因组队列或计算 PRS，需要大量计算资源，以便使用 [Variant Effect Predictor](https://genomebiology.biomedcentral.com/articles/10.1186/s13059-016-0974-4)（VEP）等工具生成联合变异调用表与完整的注释。最关键的是，这些工作流形成了一道技术壁垒：只有具备 SQL 专业能力、深入理解变异文件格式的生物信息学家才能提取有意义的洞见，使临床研究人员在基础基因组查询上依赖专业技术团队。

我们这套 AI 驱动方法的变革性优势在于：通过自然语言交互实现基因组分析的大众化。传统 VEP 流水线需要数天的技术投入才能回答诸如“哪些患者在耐药基因中存在高影响变异？”这类临床问题，而借助我们的解决方案，研究人员可以以对话方式提出这些问题，并在数分钟内得到答案。这标志着从技术依赖转向自助式基因组洞见，使临床研究人员、肿瘤委员会与基因组团队能够直接探索自己的数据，无需等待生物信息学支持。

我们的解决方案演示了一个生成式 AI 驱动的基因组变异解读 agent，它将自动化数据处理与智能自然语言分析相结合。该架构覆盖整个基因组分析工作流，从原始 VCF 文件摄入到对话式查询界面。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/18/Picture-3-1.png)

该解决方案遵循六个关键步骤，将原始基因组数据转化为可付诸行动的洞见：

- **原始 VCF 处理**：来自测序服务商的原始 VCF 文件上传至 [Amazon S3](https://aws.amazon.com/s3/) 存储，通过 S3 事件通知触发 [AWS Lambda](https://aws.amazon.com/pm/lambda/) 函数，由其编排 AWS HealthOmics 工作流。
- **VEP 注释**：[AWS HealthOmics](https://aws.amazon.com/healthomics/) 工作流使用 Variant Effect Predictor（VEP）自动处理原始 VCF 文件，并行地为变异补充功能预测与临床注释，随后将注释结果存回 S3。
- **事件协调**：[Amazon EventBridge](https://aws.amazon.com/eventbridge/) 监控工作流完成情况，并触发 Lambda 函数在 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 中更新任务状态，同时由 [AWS Batch Fargate](https://aws.amazon.com/batch/) 计算环境作为 PyIceberg 模块，将 VEP 注释后的 VCF 文件与 ClinVar 注释转换为 Iceberg 格式
- **数据组织**：PyIceberg 加载器与 [Amazon S3 Tables](https://aws.amazon.com/s3/features/tables/) Iceberg Rest Endpoint 交互。Amazon S3 Tables 连接并在 [AWS Glue Data Catalog](https://docs.aws.amazon.com/glue/latest/dg/start-data-catalog.html) 中注册表元数据。模式信息（列、数据类型、分区）会针对注释后的 VCF 与 ClinVar 注释被编目。它还会为下游分析建立分析连接器。
- **SQL 驱动的分析**：[Amazon Athena](https://aws.amazon.com/athena/) 通过列式存储格式对基因组数据提供基于 SQL 的查询能力，从而在数百万变异上实现大规模分析与理想的查询响应。
- **自然语言交互**：由 AgentCore Runtime 上的 Amazon Bedrock LLM 驱动的 Strands 编排 agent，通过五个专用工具提供自然语言界面来执行 Athena 查询：query_variants_by_gene：检索与特定基因相关的变异；query_variants_by_chromosome：支持按染色体进行变异分析；compare_sample_variants：实现跨患者样本的比较基因组学；analyze_allele_frequencies：提供群体遗传学洞见；execute_dynamic_genomics_query：支持灵活、即席的分析请求

该架构通过 AWS IAM 实现细粒度访问管理、通过 Amazon CloudWatch 提供监控，从而包含全面的安全控制。这条自动化、事件驱动的流水线支持 VCF 文件的可扩展并行处理，能够随基因组数据集增长自动调整，同时保持一致的注释质量与分析能力。

## 结合 PyIceberg 使用 Amazon S3 Tables：将 VCF 转化为结构化队列

结合 PyIceberg 使用 Amazon S3 Tables，可将经 VEP 注释的 VCF 文件转化为结构化队列、可查询的数据集，并针对 AI 驱动的分析进行优化。这为自然语言界面高效地与复杂基因组数据交互奠定了数据基础。

PyIceberg 以 S3 Tables 格式创建 Apache Iceberg 表，带来以下优势：

- 最优查询：agent 可以通过优化的列式存储，以极低延迟在数百万变异上执行复杂的基因组查询，把以往需要数小时 SQL 开发与执行的分析，变成即时的对话式响应。
- 丰富的注释访问：VEP 与 ClinVar 注释可以通过 Amazon Athena 用 SQL 直接查询，使 AI agent 能够提取特定的基因组洞见
- 队列级分析：结构化 Iceberg 格式（PyIceberg）支持跨患者队列的高效比较，以自然语言完成群体级查询。

在 S3 Tables 中将变异数据与注释数据分离，为 AI 驱动的分析奠定了理想基础，因为基因组变异 S3 表包含 agent 可快速筛选的核心位置信息，而注释/临床 S3 表则承载解读所需的大量功能与临床语境。借助这一结构，Strands agent 可以通过 AWS Glue Data Catalog Connector 构建有针对性的查询，精准回答用户问题。

正是从原始 VCF 文件到结构化表的这一转换，使研究人员能够通过 Amazon Bedrock AgentCore 上的 Strands 编排 agent [KM1] 以对话方式查询复杂的基因组数据集。

## 借助 Strands Agents 与 AgentCore Runtime 实现智能基因组分析

对话式界面是我们基因组 AI 解决方案的核心创新，它使用 Strands Agents SDK 构建，并部署在 Amazon Bedrock AgentCore Runtime 上。这个先进的 AI agent 理解复杂的基因组概念，并将自然语言查询转化为针对结构化基因组数据集的相应分析操作。

AgentCore Runtime 是一个安全、无服务器的运行时，专为部署与扩展动态 AI agent 与工具而打造。该解决方案为基因组分析提供了多项关键优势：

- 模型与框架灵活性：AgentCore 服务可组合，既可与开源或自定义框架与模型配合使用，也可与 Amazon Bedrock 内外的模型配合使用
- 多小时的 agentic 工作负载：支持最长 8 小时的长时间运行工作负载以及最大 100MB 的负载
- 安全性：为每个用户会话提供完全隔离的专用 microVM
- 企业级集成：通过 AgentCore Identity 与 AWS IAM 提供内置身份验证
- 可观测性：全面追踪 agent 推理过程与工具调用
- 私有资源访问：可连接 Amazon Virtual Private Cloud 内的数据库与 API
- 更快的上市时间：缩短 AI agent 解决方案的部署与开发周期

有关 Amazon Bedrock AgentCore 能力的详细信息，请参阅 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)。

[Strands Agents](https://github.com/strands-agents/sdk-python) 通过一种模型驱动的方法，以 agentic 循环概念编排基因组分析工具，为构建具备专门能力的领域专用 AI agent 提供了稳健基础。这一迭代式推理框架使 agent 能够根据分析需求动态选择并执行合适的工具。我们的基因组变异解读器实现了五个关键工具，利用 Amazon S3 Tables 创建的结构化数据：

- 变异查询：将基于基因的问题转化为精确的 Athena SQL 查询，以检索相关变异。
- 染色体分析：通过自然语言实现区域特异性的基因组探查。
- 样本比较：无需 SQL 连接即可完成跨患者的基因组分析。
- 群体频率分析：将发现与千人基因组等参考数据集进行对照解读。
- 动态查询生成：把复杂的自然语言请求转化为经过优化的 SQL。

## 自然语言查询

该 agent 在处理多种查询类型方面展现出卓越能力。在传统模式下，临床研究人员必须等待生物信息学团队编写自定义脚本并运行复杂分析。如今，研究人员不必再花数天时间编写 SQL 查询、与 VCF 文件格式纠缠，而可以像与基因组学专家对话一样自然地探索自己的基因组数据。

## 队列级分析

`用户："请以表格形式总结本队列中每位患者的变异总数与致病性？"`

针对该查询，agent 会：

- 使用 execute_dynamic_genomics_query 工具。
- 分析该样本队列中的变异数据。
- 生成包含患者数量与变异统计的完整队列摘要。
- 以结构化表格形式呈现发现的摘要。

## 队列级频率分析

`用户："请给出本队列与千人基因组中共享的致病或可能致病变异的等位基因频率？"`

agent 会将其转化为以下查询：

- 通过运行 execute_dynamic_genomics_query 与 analyze_allele_frequencies 工具，检索该患者的致病变异列表。
- 筛选出具有临床相关性的致病变异。
- 从 ClinVar 提取疾病层面信息，从 VEP 提取等位基因频率。
- 结合相关语境呈现结果。

## 共病风险关联

`用户：" 哪些患者在 chr10:111079820 处的 ADRA2A 基因中存在变异，这些患者是否还有其他与他汀或胰岛素抵抗相关的高影响变异？ "`

针对该查询，agent 会：

- 在特定疾病语境下，检索耐药通路中的其他风险变异。
- 将个体患者层面的临床意义与共病情况关联起来。
- 给出临床与耐药通路联合作用的临床含义。

这一自然语言界面最大限度减少了研究人员掌握复杂 SQL 语法或理解底层数据结构的需求，使临床与研究团队无论技术背景如何，都能大众化地获取基因组洞见。

## 高级分析处理

除查询之外，基因组变异解读 agent 还展现出超越基础变异识别的高级分析能力。研究人员可以探索以往需要数天分析的复杂问题。

## 临床决策支持

- 分析疾病通路基因中的变异、药物基因组学信息，并给出基于证据的建议。

## 药物基因组学指导的给药策略

研究人员可以利用该 agent，通过如下查询在大型队列上开展复杂的药物基因组学通路分析：

`用户：" 本患者队列中哪些主要药物相关通路被遗传变异显著富集？请给出影响最大的药物基因组学通路及相关患者 ID "`

由此可以探索不同人群中的变异频率分布、后果类型模式与基因层面的变异负荷——全部通过对话式界面完成，无需复杂的 SQL 或生物信息学流水线。

## 优势与局限

该解决方案有助于解决当前的挑战：

| **挑战** | **解决方案** |
| --- | --- |
| 初始 VCF 处理——低质量调用 | agent 在做出变异解读决策之前，会自动预先检查变异的质量调用 |
| 大规模 VEP 注释 | 该解决方案以 20 个为一批自动化大规模 VCF 注释，使用恰当的计算资源来达到相应性能。 |
| ClinVar 集成 | agent 评估查询语境，并根据用户兴趣动态构建联合查询。 |
| 多样本集成 | 以 Iceberg 格式集成 Amazon S3 Tables，使 VCF 文件队列能以理想性能被查询。 |
| 基因组解读 | agent 理解语境与用户兴趣，依据来自注释与内部资料的适当证据审慎推理，做出有依据的决策。 |

该解决方案存在以下局限：

- Lambda 运行时限制：当前实现使用 AWS Lambda 处理 VCF/GVCF，其最大执行时间为 15 分钟。对于将大型 VCF 文件、尤其是超大型 GVCF 文件加载到 Iceberg S3 Tables 这类可能远超 Lambda 超时限制的操作而言，这一限制可能不够。对于包含大型基因组数据集的生产工作负载，可考虑使用执行时间更长的 AWS HealthOmics 工作流、AWS Batch、ECS 任务或 EC2 实例来处理数据加载过程。
- 模式优化的权衡：该模式实现采用样本与染色体分区，针对患者级分析进行了优化。然而，队列级分析通常需要不同的分区策略与模式设计，才能在大规模下获得最优性能。随着队列规模增长到数百个样本以上，要在单一模式内同时让患者级与队列级分析都保持高性能，会变得越来越困难。对于大规模队列研究（数千到数万个样本），可考虑针对特定分析模式实现独立的模式或物化视图，或探索更能支持群体级查询的反规范化结构。

## 未来技术演进

该解决方案的模块化架构为 AI 驱动的基因组分析持续创新奠定了基础。未来版本可以集成更多注释数据库、外部 API，并支持将基因组数据与临床记录、影像相结合的多模态分析。针对基因组数据的领域专用微调可以进一步提升解读准确度，而与电子健康记录的集成则能提供床旁基因组洞见。

一个尤为值得期待的方向是药物研发中的多 agent 协作，届时这个基因组变异解读 agent 可以与负责药物画像、靶点识别、文献证据与假设生成的专用 agent 协同工作。这种协作式 agent 框架能够将变异层面的洞见直接连接到治疗开发，从而大幅加速药物发现流水线，简化从遗传发现到临床应用的转化。

## 结语

这套新一代基因组 agentic AI 解决方案，代表着研究人员与临床医生和基因组数据交互方式的根本性转变。通过将用于自动化变异注释与数据转换的 AWS HealthOmics 与用于智能解读的 Amazon Bedrock AgentCore 无缝集成，我们打造了一套覆盖整个基因组分析工作流的完整解决方案。

自动化 VEP 注释工作流、将 VCF 数据转化为可查询 Iceberg 表的 S3 Tables，以及在 Amazon Bedrock AgentCore 上提供自然语言交互的 Strands Agents，三者结合构建出一个系统，最大限度消除了变异注释、数据处理与临床解读之间的传统壁垒。通过自动化复杂的技术流程并提供直观的交互方式，研究人员如今可以专注于生物学问题，而非技术实现细节。

随着基因组数据持续指数级增长、临床应用日益复杂，这样的系统将成为推进精准医疗与加速科学发现的关键基础设施。借助千人基因组计划第 3 阶段再分析数据集所演示的解决方案表明，即便是大规模基因组队列，也能通过简单的对话式界面进行分析，从而实现高级基因组洞见的大众化获取。
