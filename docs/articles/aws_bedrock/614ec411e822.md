# Amazon Bedrock AgentCore 上的 Web Answer 入门

今天，我们宣布 Amazon Bedrock AgentCore 上的 Web Answer 正式普遍可用（general availability）。借助 Web Answer，agent 开发者只用一次 tool call，就能针对一个自然语言问题拿到经过综合、且标注了来源的答案，不必再自己去搭建搜索、取回、综合与引用这条 pipeline。

如果你构建过需要依据当前 web 来源作答的 agents，你一定熟悉这套套路：调用 search API，判断哪些结果可信，取回页面内容并清洗，提示模型做综合，还要专门工程化地实现引用抽取，好让输出能回溯到来源。每一步都是你要维护的代码，而每一步也都是可能出问题的地方：证据不足时出现幻觉，索引更新后拿到过期内容，论断与它的来源对不上时归属关系就断了。

Web Answer 把这一整条 pipeline 收敛成一次请求。你发出一个问题，几秒后就拿回一个带引用的答案。本文说明 Web Answer 做什么、它与 AgentCore 上的 Web Search 相比如何、它怎么工作、返回什么，并走一遍把 Web Answer 加到 gateway、再从 agent 里调用它的过程。

## Web Answer 做什么

![Web Answer 请求的架构图：agent 调用 Gateway，Gateway 对请求鉴权后调用 Web Answer connector，后者规划并并行执行 web 搜索、在关键页面上核实事实，再经 Gateway 返回带引用的答案](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22248-1.png)

图 1：请求从 agent 出发，经 Gateway 到达 Web Answer 再返回的流向

你的 agent 把问题发给你的 AgentCore Gateway，这是 Amazon Bedrock AgentCore 的一项能力。Gateway 用 AWS Identity and Access Management（AWS IAM）或 JSON Web Token（JWT）对这个调用做鉴权。Gateway 再以自己的 service role 调用 Web Answer——一条由 AWS 持有的托管 connector。Web Answer 自行规划搜索、并行发起多次搜索，并阅读关键页面来核对事实。证据不足时，它会再搜一轮。然后它写出一份把每条论断都绑定到其来源 URL 的答案。Gateway 把答案及其引用作为 Model Context Protocol（MCP）tool result 返回给你的 agent。

Web Answer 是一个托管的 AgentCore Gateway 工具，接收一个自然语言问题，几秒内返回一个以当前 web 来源为依据的综合答案。你能拿回的内容如下：

- 一个有依据、带引用的答案，其中每条有依据的论断都对应一条引用，在有来源 URL 时会给出该 URL。
- 当前的来源。Web Answer 对每个问题都会发起新的搜索，而且它的模型会拿到今天的日期，因此可以检索最新信息。
- Agentic search：Web Answer 自己规划搜索、并行执行多次搜索、阅读页面核实事实，并自行判断何时证据已经足够作答。
- Responsible AI 安全措施：Web Answer 在设计阶段就纳入并测试了 responsible AI 安全措施。

## 它与 Web Search 有何不同

Web Answer 与 Web Search 工具都服务于检索类场景，只是集成复杂度层次不同。分界线在于由谁来运行模型：

- **Web Search：** 返回排序后的 URL、标题、摘要和元数据。你保留自己的模型，并掌控综合过程。想要完全控制结果的处理方式时，用 Web Search。
- **Web Answer：** 替你运行模型、agentic 检索循环、综合与归属标注。你直接拿到一份完整的、带引用的答案。当问题只是某个更大 agent 内部的一个子任务、而你不想为它自建检索 pipeline 时，用 Web Answer。

很多客户会两者一起用。agent 可以用 Web Search 处理需要原始结果的宽泛研究任务，用 Web Answer 回答那些需要一个快速的、带引用答案的具体事实性问题。

## Web Answer 的配置与调用

Web Answer 是一条由 AWS 持有的 connector。你按 ID 引用它，Gateway 负责 tool schema、参数治理、endpoint 解析以及对后端的鉴权。在这份演练里，你要给 Gateway 的 service role 授予调用 Web Answer 的权限，添加一个 Web Answer target，然后从一个 Strands agent 里调用它。

### 上手

上手只要几分钟。Gateway 管理员把 Web Answer 作为 target 加到已有的 AgentCore Gateway 上，任何挂载的 agent 就能通过 MCP 的 `tools/list` 和 `tools/call` 看到这个工具。

### 前置条件

- 一个可访问 AgentCore Gateway 的 AWS 账号。
- 一个位于 us-east-1、使用 IAM（`AWS_IAM`）入站鉴权的 AgentCore Gateway。创建方法见 Developer Guide 中的 [Create an Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-create.html)。
- 某个身份的 AWS 凭证，该身份对 Gateway 拥有 `bedrock-agentcore:InvokeGateway`，并且你的 agent 所用模型具备 Amazon Bedrock 访问权限。
- Python 3.10 或更高版本，并安装所需依赖包：  `pip install boto3 strands-agents mcp mcp-proxy-for-aws`

注意：按这些步骤操作会创建产生费用的 AWS 资源。Gateway 与 Web Answer 的调用都是计费的。详情见后文的 Pricing 一节，完成后请删除你创建的资源（见 “Clean up resources” 一节）。

### 第 1 步：为 Gateway 的 service role 授予 Web Answer 访问权限

Gateway 用它的 [service role](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-prerequisites-permissions.html#gateway-service-role-permissions) 代你行事。该角色的 trust policy 允许 `bedrock-agentcore.amazonaws.com` 承担该角色，并限定在你的账号范围内。就 Web Answer 而言，这个角色需要：

- `bedrock-agentcore:InvokeWebAnswer`，用于调用 Web Answer。Gateway 在每次请求时都会针对那个由 AWS 持有的 ARN `arn:aws:bedrock-agentcore:us-east-1:aws:tool/web-answer.v1` 校验这项权限。

把这条策略以内联策略的形式挂到 service role 上：

```
import json
import boto3

iam = boto3.client("iam")

iam.put_role_policy(
    RoleName="<gateway-service-role>",
    PolicyName="WebAnswerGuide",
    PolicyDocument=json.dumps({
        "Version": "2012-10-17",
        "Statement": [
            {
                "Sid": "InvokeWebAnswer",
                "Effect": "Allow",
                "Action": "bedrock-agentcore:InvokeWebAnswer",
                "Resource": "arn:aws:bedrock-agentcore:us-east-1:aws:tool/web-answer.v1",
            }
        ],
    }),
)
```

这个角色只管 Gateway 的出站调用。谁能调用你的 Gateway，由它的入站授权器决定。这个角色也不需要 `bedrock:InvokeModel`：你 agent 的模型是在 agent 自身的身份下运行的。

### 第 2 步：创建 Web Answer target

把 Web Answer 作为 connector target 添加。`connectorId` 告诉 Gateway 要开通哪一项托管集成：在本例中，是一个会搜索 web 并撰写带引用答案的 agent。

```
import boto3

gateway_client = boto3.client("bedrock-agentcore-control", region_name="us-east-1")

target_response = gateway_client.create_gateway_target(
    name="web-answer-tool",
    gatewayIdentifier=gateway_id,
    targetConfiguration={
        "mcp": {
            "connector": {
                "source": {"connectorId": "web-answer"},
                "configurations": [{"name": "WebAnswer", "parameterValues": {}}],
            }
        }
    },
    credentialProviderConfigurations=[
        {"credentialProviderType": "GATEWAY_IAM_ROLE"}
    ],
)
target_id = target_response["targetId"]
```

connector 的出站鉴权是自动的。使用 `GATEWAY_IAM_ROLE` 时，Gateway 用第 1 步里的 service role 去调用 Web Answer 后端，所以你不用为这个工具创建或保存任何凭证。等 `get_gateway_target` 把 target 状态报告为 `READY` 之后再调用它。

作为 Gateway 管理员，你还可以在该 target 上设置域名过滤器。过滤器对经由该 target 的每一次调用都生效。要把 target 限定在一组域名上，把 `parameterValues` 设为 `{"domainFilter": {"include": ["bis.org"], "exclude": ["unreliable-source.net"]}}`。

### 第 3 步：从 Strands agent 调用 Web Answer

你的 agent 通过 Gateway 的 `tools/list` 发现 Web Answer，并像对其他 MCP 工具一样用 `tools/call` 调用它。这与 Strands Agents、LangChain、LangGraph、CrewAI 或任何其他兼容 MCP 的客户端都能配合。

```
from strands import Agent
from strands.models.bedrock import BedrockModel
from strands.tools.mcp import MCPClient
from mcp_proxy_for_aws.client import aws_iam_streamablehttp_client

gateway_url = "https://gateway-<id>.gateway.bedrock-agentcore.us-east-1.amazonaws.com/mcp"

mcp_client = MCPClient(lambda: aws_iam_streamablehttp_client(
    endpoint=gateway_url,
    aws_region="us-east-1",
    aws_service="bedrock-agentcore",
    aws_profile="<aws-profile-id>",  # identity with bedrock-agentcore:InvokeGateway on the Gateway
))

model = BedrockModel(model_id="us.anthropic.claude-sonnet-5", max_tokens=1024)

with mcp_client:
    tools = mcp_client.list_tools_sync()  # Web Answer tool discovered from the Gateway
    agent = Agent(model=model, tools=tools)

    result = agent("What are the Basel III minimum requirements for Tier 1 capital?")
    print(result.message)
```

当某个问题需要最新信息时，你的 agent 会调用 Web Answer 工具（`web-answer-tool___WebAnswer`）。Web Answer 执行 agentic 搜索，并返回一份带引用的完整答案。

除了问题本身，Web Answer 工具还接受一些可由你的 agent 在每次调用时设置的可选参数：用于纳入或排除站点的域名过滤器、发布日期范围，以及用于本地化结果的国家。agent 的域名过滤器会与 target 的过滤器合并：agent 可以多排除一些域名，也可以把结果限制在 target 已纳入域名的其中一部分，但不能加上被 target 过滤器挡掉的域名。

### 响应格式

Web Answer 返回一个同时带有 content 和 structuredContent 字段的 MCP tool result。答案是 markdown 文本，内含形如 [[1](https://aws.amazon.com/cn/blogs/machine-learning/getting-started-with-web-answer-on-amazon-bedrock-agentcore/url)] 的行内引用标记；structuredContent.answer 带着同样的文本，并附一个结构化的 citations 列表：

```
{
  "content": [
    {
      "type": "text",
      "text": "Under Basel III, banks must hold Common Equity Tier 1 capital of at least 4.5% of risk-weighted assets [[1](https://www.bis.org/...)]..."
    }
  ],
  "structuredContent": {
    "answer": [
      {
        "text": "Under Basel III, banks must hold Common Equity Tier 1 capital of at least 4.5% of risk-weighted assets [[1](https://www.bis.org/...)]...",
        "citations": [
          { "domain": "bis.org", "url": "https://www.bis.org/..." }
        ]
      }
    ]
  },
  "isError": false,
  "_meta": {
    "latencyMs": 5210
  }
}
```

structuredContent.answer 通常只包含一个块。每条引用都带上来源 url，并在可获得时附上域名。

### 清理资源

不再需要时，删除 Web Answer target：

```
gateway_client.delete_gateway_target(gatewayIdentifier=gateway_id, targetId=target_id)
```

如果你创建这个 Gateway 只是为了这份演练，那么先删除它的各个 target，再删除 Gateway（delete_gateway），最后删除 service role 及其策略。除了这些资源，AWS 侧没有别的使用中会持续存在的常驻基础设施。它们被移除之后，你就不再继续产生费用。

## 内置的企业级管控

Web Answer 继承了与其他 AgentCore 工具相同的企业级管控：

- **Gateway 鉴权。** Web Answer 不需要单独申请、轮换或管理的 API key。调用方按你配置的入站方式对 gateway 鉴权，例如 AWS IAM（SigV4）或来自你身份提供方的 JSON Web Token。随后 gateway 用自己的 service role 调用 Web Answer，该角色需要 `bedrock-agentcore:InvokeWebAnswer` 权限。
- **VPC 与 AWS PrivateLink。** 你的 agent 可以通过 interface virtual private cloud（VPC）endpoint（`com.amazonaws.us-east-1.bedrock-agentcore.gateway`）调用 gateway，让流量不走公网。
- **零数据外流。** 你的查询与结果都留在你的 AWS 环境之内。
- **Amazon CloudWatch 指标。** 从第一次调用起，运维指标就会发布到 CloudWatch。
- **按账号的速率限制。** 上线即生效，在美国东部（弗吉尼亚北部）（us-east-1）为每个账号每秒 10 次交易。需要申请提升请联系 AWS Support。
- **管理员设定的策略边界。** Gateway 管理员在配置 target 时设定域名过滤器的边界。agent 可以在每次调用时收窄这些边界，但不能放宽。
- **查询不出 AWS。** Web Answer 搜索的是 Amazon 运营的 web 索引和 Amazon 的知识图谱，不会把你的问题发送给第三方搜索引擎或外部网站。

## 使用场景

Web Answer 帮助 agents 检索最新的、带引用的信息，以支撑一系列知识密集型工作流。示例场景包括：

- **金融服务。** 监管问答 agents，回答有关合规要求、市场监管和政策变化的问题，这里每条答案都必须能追溯到权威来源。
- **医疗健康。** 临床支持 agents，把回复建立在当前医学文献以及 web 上发布的治疗指南之上。
- **客户服务。** 支持类 agents 实时回答产品与政策问题——这种情况下十个排序链接并不管用，一个带引用的答案才管用。
- **法律与合规。** 研究助理回答关于判例法、监管备案和政策解释的问题，并给出可审计的引用。
- **企业知识工作者。** 内部 copilot 基于当前的公开信息回答问题，员工不必再自己搭一套搜索与综合的工作流。

## 可用性

Web Answer 已在美国东部（弗吉尼亚北部）（us-east-1）提供，更多 AWS Regions 即将推出。

## 定价

Amazon Bedrock AgentCore 上的 Web Answer 定价为每 1,000 次 tool call 10 美元。

## 结论

本文中，我们展示了 Web Answer 如何通过 agentic search 给你的 agents 提供最新的、带引用的答案，而你无需搭建或维护任何搜索 pipeline。我们给 Gateway 的 service role 授予了 Web Answer 的访问权限，添加了一个 Web Answer target，从 Strands agent 里调用它，并从响应中读出答案及其引用。当你希望自己的模型直接在原始结果上推理时，用 AgentCore 上的 Web Search；当你的 agent 需要一份完整的、带引用的答案时，用 Web Answer。
