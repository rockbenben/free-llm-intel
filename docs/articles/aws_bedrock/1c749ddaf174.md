# 使用 Amazon Bedrock 批处理推理对呼叫中心对话进行分类

本文演示如何结合 [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html) 的批处理推理能力与 [Anthropic 的 Claude Haiku](https://aws.amazon.com/bedrock/claude/) 模型，构建端到端的文本分类解决方案。Amazon Bedrock [批处理推理](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference.html)相比按需价格提供 50% 的折扣，这在处理大量请求时是一个重要因素。我们会走一遍把旅行社呼叫中心对话划分到不同类别的过程，展示如何生成合成训练数据、处理海量文本数据，以及用 AWS 服务自动化整个工作流。

## 大批量文本分类的挑战

各行各业的组织都面临一个共同挑战：需要高效处理大批量分类任务。从旅行社呼叫中心对客户咨询进行分类，到销售团队分析失掉的销售机会、财务部门对发票进行分类，这些人工流程都是日常必需。但这些任务伴随着不小的挑战。

分析并归类这些分类请求的人工方式不仅耗时，而且容易出现不一致。随着团队处理海量数据，出错和低效的可能性也在增长。通过实施自动化系统来对这些交互进行分类，多个部门都能获得可观的收益。他们可以发现数据中被隐藏的趋势，显著提升客户服务质量，并精简运营以提高效率。

不过，实现有效的自动化分类本身也有其挑战。组织必须应对这一复杂性：既要高效处理海量文本信息，又要在分类结果中保持一致准确度。本文演示如何创建一个全自动工作流，同时把运营成本控制在合理范围。

## 数据

本方案使用了合成的呼叫中心对话数据。为了在保护用户隐私的同时获得逼真的训练数据，我们使用 Anthropic 的 [Claude](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-claude.html) 3.7 Sonnet 生成合成对话。我们使用以下 prompt 生成合成数据：

```
Task: Generate <N> synthetic conversations from customer calls to an imaginary travel
company. Come up with 10 most probable categories that calls of this nature can come 
from and treat them as classification categories for these calls. For each generated 
call create a column that indicates the category for that call. 
Conversations should follow the following format:
"User: ...
Agent: ...
User: ...
Agent: ...
...

Class: One of the 10 following categories that is most relevant to the conversation."
Ten acceptable classes:
1. Booking Inquiry - Customer asking about making new reservations
2. Reservation Change - Customer wanting to modify existing bookings
3. Cancellation Request - Customer seeking to cancel their travel plans
4. Refund Issues - Customer inquiring about getting money back
5. Travel Information - Customer seeking details about destinations, documentation, etc.
6. Complaint - Customer expressing dissatisfaction with service
7. Payment Problem - Customer having issues with billing or payments
8. Loyalty Program - Customer asking about rewards points or membership status
9. Special Accommodation - Customer requesting special arrangements
10. Technical Support - Customer having issues with website, app or booking systems

Instructions:
- Keep conversations concise
- Use John Doe for male names and Jane Doe for female names
- Use john.doe@email.com for male email address,jane.doe@email.com for female email 
address and corporate@email.com for corporate email address, whenever you need to 
generate emails.Use \" or ' instead of " whenever there is a quote within the
conversation
```

该合成数据集包含以下信息：

- 关于航班预订的客户咨询
- 酒店预订讨论
- 旅行套餐议价
- 客户服务投诉
- 一般旅行咨询

## 方案概览

方案架构采用无服务器、事件驱动且可扩展的设计，以有效处理和分类大量分类请求。它构建在 AWS 上，当新的分类请求数据到达 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）存储桶时会自动开始工作。随后系统使用 Amazon Bedrock 批处理在大规模上分析和归类内容，尽可能减少持续的人工盯守。

下图展示了方案架构。

![架构图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/27/architecture-diagram.png)

该架构遵循结构良好的流程，有助于可靠地处理分类请求：

- **数据准备** —— 当用户或应用把分类请求提交到 S3 存储桶时，流程开始（步骤 1）。这些请求被写入 [Amazon Simple Queue Service](https://aws.amazon.com/sqs/)（Amazon SQS）队列，为进入的数据提供可靠缓冲，确保高峰期不会丢失请求。由 [AWS Lambda](https://aws.amazon.com/lambda) 函数实现的无服务器数据处理器从队列中读取消息并开始数据处理工作（步骤 2）。它为批处理推理准备数据，将其整理成 Amazon Bedrock 所需的、符合 schema 的 JSONL 格式。它把文件存储在单独的 S3 存储桶中，以便与客户应用共享的原始 S3 存储桶保持清晰隔离，从而增强安全性和数据管理。
- **批处理推理** —— 当数据到达 S3 存储桶时，会向 SQS 队列发起通知。该队列激活 Lambda 函数 batch initiator，由它启动批处理推理流程。该函数通过 `CreateModelInvocationJob` API 提交 Amazon Bedrock 批处理推理作业（步骤 3）。这个 initiator 充当排队数据与 Amazon Bedrock 强大分类能力之间的桥梁。随后 Amazon Bedrock 以批处理方式高效处理数据。这种批处理方式可以在保持高吞吐的同时实现资源的最优利用。当 Amazon Bedrock 完成任务后，分类结果会存储在输出 S3 存储桶中（步骤 4），供后处理和分析使用。
- **分类结果处理** —— 分类完成后，系统通过另一个 SQS 队列（步骤 5）和专用 Lambda 函数处理结果，后者把分类结果整理成易读的文件，例如 CSV、JSON 或 XLSX（步骤 6）。这些文件立即可供客户应用以及需要访问这些信息的支持团队使用（步骤 7）。
- **分析** —— 我们构建了一个分析层，自动编目并组织分类结果，把原始分类数据转化为可用于行动的洞察。[AWS Glue](https://aws.amazon.com/glue) 爬虫会为所有内容编目，以便之后快速找到（步骤 8）。现在你的业务团队可以使用 [Amazon Athena](https://aws.amazon.com/athena) 对数据运行 SQL 查询，发掘已分类类别中的模式与趋势。我们还构建了 [AWS Quick Sight](https://aws.amazon.com/quicksight) 仪表板，提供可视化能力，让相关方能够把数据集转化为可用于决策的报告。（步骤 9）。

本方案采用 AWS 最佳实践，包括用事件驱动和批处理实现资源最优利用、用批量操作实现成本效益、用解耦组件实现独立扩展，以及最小权限访问模式。我们使用 [AWS Cloud Development Kit](https://aws.amazon.com/cdk/)（AWS CDK）以 TypeScript 编写基础设施即代码（IaC），以 Python 编写应用逻辑，确保实现无缝自动化、动态扩展和高效的分类请求处理，使其既能有效应对当前需求，也能满足未来要求。

## 先决条件

要实施本方案，你必须具备以下先决条件：

- 一个处于活跃状态的 [AWS 账户](https://signin.aws.amazon.com/signup?request_type=builderId)。
- 一个位于 Amazon Bedrock 批处理推理[支持的 Region 列表](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference-supported.html)中的 AWS Region。
- 对托管在 Amazon Bedrock 上你选定模型的访问权限。请确保已在 Amazon Bedrock 中[启用所选模型](https://docs.aws.amazon.com/bedrock/latest/userguide/getting-started.html)。该方案默认配置为使用 Anthropic 的 Claude 3 Haiku。
- 在将部署主应用的同一 [Region](https://docs.aws.amazon.com/quicksight/latest/user/regions-qs.html) 中[注册 Quick Sight](https://docs.aws.amazon.com/quicksight/latest/user/signing-up.html)。订阅时，请确保配置对 Athena 和 Amazon S3 的访问权限。
- 在 Quick Sight 中创建名为 `quicksight-access` 的[组](https://docs.aws.amazon.com/quicksight/latest/user/creating-groups-console.html)，用于管理仪表板访问权限。请务必把自己的角色加入该组，以便在仪表板部署后访问它。如果你使用不同的组名，请相应修改[代码](https://github.com/aws-samples/sample-genai-bedrock-batch-classifier/blob/main/cdk/lib/constants/mutable.ts#L23)中的对应名称。
- 要配置 AWS CDK，请安装 AWS CDK 命令行界面（CLI）。相关说明见 [AWS CDK CLI reference](https://docs.aws.amazon.com/cdk/v2/guide/cli.html)。

## 部署方案

该方案可在 [GitHub 仓库](https://github.com/aws-samples/sample-genai-bedrock-batch-classifier)中获取。

完成以下步骤来设置并部署该方案：

- **克隆仓库**：运行以下命令：`git clone git@github.com:aws-samples/sample-genai-bedrock-batch-classifier.git`
- **设置 AWS 凭证**：创建一个具有相应权限的 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）用户，生成用于 [AWS Command Line Interface](https://aws.amazon.com/cli)（AWS CLI）访问的凭证，并创建配置文件。相关说明见 [Authenticating using IAM user credentials for the AWS CLI](https://docs.aws.amazon.com/cli/v1/userguide/cli-authentication-user.html)。测试时可以使用 Admin Role，但它违反最小权限原则，生产环境应避免使用，改为使用仅具备最低所需权限的自定义角色。
- **引导应用程序**：在 CDK 文件夹中运行命令 `npm install & cdk bootstrap --profile {your_profile_name}`，把 `{your_profile_name}` 替换为你的 AWS 配置文件名称。
- **部署方案**：运行命令 `cdk deploy --all --profile {your_profile_name}`，把 `{your_profile_name}` 替换为你的 AWS 配置文件名称。

完成部署过程后，你会看到 AWS 账户中共创建了六个 stack，如下图所示。

![stack 列表](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/27/stacks.jpg)

**`SharedStack`** 充当系统多个部分都需要访问的资源枢纽。该 stack 内有两个 S3 存储桶：一个在幕后处理内部操作，另一个作为系统与客户之间的桥梁，让双方都能提交分类请求并取回结果。

**`DataPreparationStack`** 充当数据转换引擎。它被设计用来处理三种特定格式的传入文件：XLSX、CSV 和 JSON，在撰写本文时这是仅有的受支持输入格式。该 stack 的主要作用是把这些输入转换为 Amazon Bedrock 所需的专用 JSONL 格式。数据处理脚本可在 [GitHub 仓库](https://github.com/aws-samples/sample-genai-bedrock-batch-classifier/blob/main/app/lambda/dataPreparation/__init__.py)中获取。这一转换确保传入数据无论原始格式如何，都会在被 Amazon Bedrock 处理之前正确结构化。格式如下：

```
{
 "recordId": ${unique_id}, 
 "modelInput": {
     "anthropic_version": "bedrock-2023-05-31", 
     "max_tokens": 1024,
     "messages": [ { 
           "role": "user", 
           "content": [{"type":"text", "text": ${initial_text}]} ],
      },
      "system": ${prompt}
}

where:
initial_text - text that you want to classify
prompt       - instructions to Bedrock service how to classify
unique_id    - id coming from the upstream service, otherwise it will be 
               automatically generated by the code
```

**`BatchClassifierStack`** 负责分类操作。虽然目前由 Anthropic 的 Claude Haiku 驱动，但系统通过允许按需直接切换到其他模型来保持灵活性。这种适应性得益于一个充当系统控制中心的综合常量文件。可用的配置如下：

- **PREFIX** —— 资源命名约定（默认 `genai`）。
- **BEDROCK_AGENT_MODEL** —— 模型选择。
- **BATCH_SIZE** —— 每个输出文件的分类数量（启用并行处理）；最小值应为 100。
- **CLASSIFICATION_INPUT_FOLDER** —— S3 存储桶中用于上传传入分类请求的输入文件夹名称。
- **CLASSIFICATION_OUTPUT_FOLDER** —— S3 存储桶中的输出文件夹名称，分类完成后输出文件会出现在这里。
- **OUTPUT_FORMAT** —— 支持的格式（CSV、JSON、XLSX）。
- **INPUT_MAPPING** —— 一种灵活的数据集成方式，它适配你现有的文件结构，而不需要你去适配我们的结构。它由两个关键字段组成：**record_id** —— 可选的唯一标识符（未提供时自动生成）。**record_text** —— 用于分类的文本内容。
- **PROMPT** —— 用于引导模型分类行为的模板。示例 prompt 模板可在 [GitHub 仓库](https://github.com/aws-samples/sample-genai-bedrock-batch-classifier/blob/main/cdk/lib/constants/prompts/travel.ts)中获取。请注意该模板的结构，它引导 AI 模型完成决策过程。模板不仅汇总了一组可能类别，还包含指令，要求模型选择一个单一类别并用 `<class>` 标签呈现。这些指令有助于保持模型处理传入请求和保存输出时的一致性。

**`BatchResultsProcessingStack`** 作为数据后处理阶段，把 Amazon Bedrock 的 JSONL 输出转换为易用的格式。在撰写本文时，系统支持 CSV、JSON 和 XLSX。处理后的文件随后被存储在 S3 存储桶的指定输出文件夹中，按日期组织，便于快速检索和管理。转换脚本可在 [GitHub 仓库](https://github.com/aws-samples/sample-genai-bedrock-batch-classifier/blob/main/app/lambda/batchResultsProcessing/__init__.py)中获取。输出文件具有以下 schema：

- **ID** —— 资源命名约定
- **INPUT_TEXT** —— 用于分类的初始文本
- **CLASS** —— 分类类别
- **RATIONALE** —— 对给定分类的推理或说明

![Excel 文件示例](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/27/excel_sample.jpg)

**`AnalyticsStack`** 提供商业智能（BI）仪表板，展示分类列表，并允许按 prompt 中定义的类别进行筛选。它提供以下关键配置选项：

- **ATHENA_DATABASE_NAME** —— 定义 Athena 数据库名称，它被用作 Quick Sight 仪表板的主要数据源。
- **QUICKSIGHT_DATA_SCHEMA** —— 定义标签在仪表板上的显示方式，并指定哪些列可筛选。
- **QUICKSIGHT_PRINCIPAL_NAME** —— 指定可以访问 Quick Sight 仪表板的 principal 组。该组应在部署该 stack 之前手动创建。
- **QUICKSIGHT_QUERY_MODE** —— 你可以选择 SPICE 或直接查询来获取数据，具体取决于[你的用例](https://aws.amazon.com/blogs/business-intelligence/best-practices-for-amazon-quicksight-spice-and-direct-query-mode/)、数据量和数据新鲜度要求。默认设置为直接查询。

现在你已成功部署系统，可以准备数据文件了——它可以是真实的客户数据，也可以是我们为测试提供的[合成数据集](https://github.com/aws-samples/sample-genai-bedrock-batch-classifier/tree/main/sample_files)。文件准备好后，前往名为 `{prefix}-{account_id}-customer-requests-bucket-{region}` 的 S3 存储桶，把文件上传到 `input_data` 文件夹。批处理推理作业完成后，你就可以在仪表板上查看分类结果。仪表板的名称是 `{prefix}-{account_id}-classifications-dashboard-{region}`。下面的截图展示了你将看到的效果预览。

![BI 仪表板](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/27/bi_dashboard-1.jpg)

在 Amazon Bedrock 完成批处理推理作业处理、且 AWS Glue 爬虫创建 Athena 表之前，仪表板不会显示数据。这些步骤未完成时，仪表板无法连接该表，因为表还不存在。此外，你必须更新预部署期间设置的 Quick Sight 角色权限。要更新权限，请完成以下步骤：

- 在 Quick Sight 控制台上，选择顶部导航栏中的用户图标，然后选择 **Manage Quick Sight**。
- 在导航窗格中，选择 **Security & Permissions**。
- 确认该角色已被授予对具有以下路径格式的 S3 存储桶的适当访问权限：`{prefix}-{account_id}-internal-classifications-{region}`。

## 结果

为测试方案的表现和可靠性，我们在多次运行中测试了来自单个 Excel 文件的 1,190 条合成旅行社对话。在连续 10 次运行中结果非常一致，每批处理时间在 11–12 分钟之间（单批 200 条分类）。我们的方案取得了以下结果：

- **速度** —— 保持约 11–12 分钟的一致处理时间
- **准确率** —— 在合成数据集上达到 100% 的分类准确率
- **成本效益** —— 通过高效的批处理优化了支出

### 挑战

在某些情况下，生成的类别与 prompt 中给出的类别名称并不完全匹配。例如，多次输出的是“Hotel/Flight Booking Inquiry”，而不是 prompt 中定义为类别的“Booking Inquiry”。这通过 prompt 工程解决：要求模型检查最终类别输出，使其与提供的类别之一完全匹配。

### 错误处理

为便于排查问题，方案包含一个跟踪批处理状态的 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 表，以及 [Amazon CloudWatch Logs](https://aws.amazon.com/cloudwatch)。错误跟踪并未自动化，需要人工监控和验证。

### 要点

虽然我们的测试聚焦于旅行社场景，但方案架构是灵活的，可以适配不同行业和用例的各种分类需求。

## 已知限制

以下是该分类方案的主要限制，在规划使用时应当考虑：

- **最小批量** —— Amazon Bedrock 批处理推理要求每批至少 100 条分类。
- **处理时间** —— 批处理推理作业的完成时间取决于作业规模等多种因素。虽然 Amazon Bedrock 力争在 24 小时内完成典型作业，但该时间范围只是尽力估算，并不保证。
- **输入文件格式** —— 该方案目前仅支持 CSV、JSON 和 XLSX 格式的输入数据。

## 清理

为避免产生额外费用，在不再需要时运行命令 `cdk destroy --all --profile {your_profile_name}` 清理 AWS 资源，把 `{your_profile_name}` 替换为你的 AWS 配置文件名称。

要删除与本项目相关的资源，请完成以下步骤：

- 删除 S3 存储桶：在 Amazon S3 控制台的导航窗格中，选择 **Buckets**。通过搜索你的 `{prefix}` 定位存储桶。删除这些存储桶以完成恰当的清理。
- 清理 DynamoDB 资源：在 DynamoDB 控制台的导航窗格中，选择 **Tables**。删除表 `{prefix}-{account_id}-batch-processing-status-{region}`。

这种彻底的清理有助于确保本项目不会在你的 AWS 账户中留下残余资源。
