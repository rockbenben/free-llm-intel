# 在 Amazon ECS 与 Amazon Bedrock 上用 LiteLLM 配置 OpenAI ChatGPT Codex

OpenAI ChatGPT Codex 配合 LiteLLM 可以为生成式 AI 编码 agent 提供集中的企业级控制。这些 agent 帮助开发者理解代码仓库、编写代码、运行测试并完成多步工程任务。随着组织从个人试验走向受管采用，团队需要一种一致的方式来控制模型访问并归属用量。他们还必须施加预算和速率限制，并观测模型访问路径。

OpenAI Codex（下称 Codex）在开发者工作站上运行其任务循环。它在本地沙箱和审批设置下读取本地文件并运行已获批准的工具。客户仍然可以把模型推理的流量路由到客户 AWS 账户内的基础设施。

本文带你完成在 Amazon Elastic Container Service（Amazon ECS）上部署一个由客户自运营的 LiteLLM 网关。我们演示如何把它连接到 Amazon Bedrock 上的 OpenAI 模型，并配置 Codex 使用该网关的 Responses API。我们还会演示如何验证语义延续、流式传输和函数调用。最后，我们说明在什么情况下直接用 AWS IAM Identity Center 访问，或使用 Portkey 这类托管网关会更合适。

完整实现位于 [guidance-codex 仓库](https://github.com/openai-on-aws/guidance-codex/tree/main)。本文的主要路径请遵循 [LiteLLM on AWS 快速入门](https://github.com/openai-on-aws/guidance-codex/blob/feat/enterprise-gateway-readiness/docs/QUICKSTART_LLM_GATEWAY_LITELLM.md)。

## 解决方案概览

下面的架构把 LiteLLM 放在 Codex 与 Amazon Bedrock 之间。LiteLLM 成为模型认证、路由、预算、速率限制和网关遥测的共享控制点。Codex 仍负责本地任务与工具执行循环。

下图展示了从开发者工作站经网关到 Amazon Bedrock 再返回的端到端请求流。请留意那五个编号步骤，它们追踪一次模型回合穿越基础设施的完整过程。

![Codex 经 AWS 上的 LiteLLM 发出请求的流程](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/01/ML-21675-1.png)

图 1：Codex 经 LiteLLM 发送模型请求，而本地工具执行仍留在开发者工作站

请求流分为五个步骤：

- Codex 把当前任务上下文和可用工具定义发送到网关的 `/v1/responses` 端点。
- Application Load Balancer 和 AWS WAF 先施加网络层与 Web 层控制，再把请求转发给运行在 AWS Fargate 上的 LiteLLM。
- LiteLLM 认证调用方，检查已配置的模型与用量策略，并使用其 ECS 任务角色调用 Amazon Bedrock 上已批准的模型。
- Amazon Bedrock 经 LiteLLM 返回文本或函数调用。
- 如果模型请求某个工具，Codex 会在其沙箱和审批策略下在本地运行该工具。Codex 在下一次 Responses 请求中经 LiteLLM 发送工具结果，循环继续。

参考部署还使用了：

- Amazon Relational Database Service（Amazon RDS）for PostgreSQL，用于存放 LiteLLM 的状态、用量和预算数据。
- AWS Secrets Manager 和 AWS Key Management Service（AWS KMS），用于存放网关密钥和 scoped key。
- Amazon CloudWatch 日志、CloudWatch Container Insights、告警和部署健康状态。
- Amazon Elastic Container Registry（Amazon ECR），用于存放不可变的网关镜像。
- 可选的 AWS WAF 托管防护和源 IP 速率限制。

这种分离很重要。该网关并不会获得 AWS 账户中的通用 shell，也不取代 Codex 的本地审批。它治理的是每一次模型回合。

## 为什么这个模式要使用 LiteLLM

[LiteLLM](https://docs.litellm.ai/docs/simple_proxy) 是一个开源 AI 网关，在 API 兼容的端点背后提供模型路由、虚拟密钥、预算、速率限制和用量遥测。在这个模式中，客户在自己的 AWS 账户内运营 LiteLLM 及其支撑基础设施。

当原生 AWS 身份、AWS Identity and Access Management（IAM）策略和 AWS CloudTrail 日志已满足客户要求时，直接访问 Amazon Bedrock 是复杂度最低的选项。当系统团队需要在开发者、团队或模型提供商之间保持一致的其他控制时，网关才有用武之地。

当你需要以下能力时，LiteLLM 是一个有用的客户自运营选项：

- 只允许已批准的模型别名。
- 签发按用户或团队限定范围的网关密钥。
- 施加硬性预算以及每分钟请求数或每分钟 token 数限制。
- 集中管理路由与回退策略。
- 在上游模型使用共享 ECS 任务角色时，仍保留网关层的身份。
- 在你自己的 AWS 账户中运营网关、数据库、网络、日志和升级流程。

运维责任是主要的取舍。你的团队要负责网关可用性、数据库生命周期、版本升级、事件响应和容量规划。

## 在 Amazon ECS 上为 Codex 部署 LiteLLM 网关

本节带你完成部署 LiteLLM 网关、将其连接到 Amazon Bedrock，以及配置 Codex 通过该网关发送请求。

### 前置条件

本演练需要：

- 一个 AWS 账户，以及创建虚拟私有云（VPC）、Amazon ECS、Elastic Load Balancing、Amazon RDS、Amazon ECR、AWS WAF、IAM、AWS KMS、Secrets Manager 和 CloudWatch 资源的权限。
- 在部署所用 AWS 区域中对 Amazon Bedrock 上所选 OpenAI 模型的访问权限。
- AWS Command Line Interface（AWS CLI）版本 2，并配好已认证的 profile。
- 带 Buildx 的 Docker。
- Codex CLI。
- Python 3。
- 若采用 HTTPS 部署，需要一个公有的 Amazon Route 53 托管区域，或同一区域内已有的 AWS Certificate Manager（ACM）证书。

本演练已在美国东部（弗吉尼亚北部）区域（us-east-1）用网关别名 `openai.gpt-5.5` 验证通过，该别名在 LiteLLM 配置中映射到 `bedrock_mantle/openai.gpt-5.5`。模型的可用性因账户和区域而异。

> 成本提示：该解决方案会创建计费资源，包括 Application Load Balancer、Fargate 任务、Amazon RDS、AWS WAF、日志和模型推理。示例 VPC 也可能产生网络费用。请查看你所在区域的当前定价，并在演练结束后执行清理章节。

### 在 Amazon ECS 上部署 LiteLLM

克隆仓库并创建本地部署环境文件：

```
git clone https://github.com/openai-on-aws/guidance-codex.git
cd guidance-codex
git checkout feat/enterprise-gateway-readiness

cp deployment/litellm/.env.deploy.example \
deployment/litellm/.env.deploy
```

真正的 `.env.deploy` 文件被 Git 忽略。请设置你打算使用的 AWS profile、区域、源 CIDR 以及 DNS 或证书值。下面的节选展示了面向生产环境的设置：

```
AWS_PROFILE=your-profile
AWS_REGION=us-east-1
BEDROCK_REGION=us-east-1

ENABLE_TLS=true
GATEWAY_DOMAIN_NAME=codex-gateway.example.com
ROUTE53_HOSTED_ZONE_ID=Z0123456789EXAMPLE
ALB_CERTIFICATE_ARN=
ALLOWED_CIDR=203.0.113.10/32

ENABLE_WAF=true
DB_MULTI_AZ=true
DESIRED_COUNT=2
MIN_TASK_COUNT=2
MAX_TASK_COUNT=10
```

通过设置 `ALB_CERTIFICATE_ARN` 而不是 `ROUTE53_HOSTED_ZONE_ID`，可使用现有证书。对于客户 landing zone，还需按生产部署指南所述提供现有 VPC，以及相互分离的公有子网、私有应用子网和私有数据库子网。

运行只读预检：

```
make litellm-check
# Direct helper invocation used by Make:
# deployment/scripts/litellm-stack.sh check
```

预检会校验 AWS CLI v2、AWS 身份、Docker、不可变镜像引用、区域一致性、CIDR 限制、TLS 输入、本地文档链接，以及在 cfn-lint 可用时的 AWS CloudFormation 语法。

构建经审查的 LiteLLM 镜像并推送到 Amazon ECR：

```
CONFIRM_AWS_WRITE=1 make litellm-build
# Direct helper invocation used by Make:
# CONFIRM_AWS_WRITE=1 deployment/scripts/litellm-stack.sh build
```

构建使用以摘要（digest）固定版本的 LiteLLM 基础镜像，并把生成的 ECR 摘要记录到本地一个被忽略的状态文件中。CloudFormation 接收到的是不可变摘要，而不是可变的镜像标签。在内部，辅助脚本会创建或复用一个不可变的 Amazon ECR 仓库、登录 Amazon ECR、运行 `docker buildx build --push`，并解析出已推送镜像的摘要。

创建一个不执行的 CloudFormation 变更集：

```
make litellm-plan
# Direct helper invocation used by Make:
# deployment/scripts/litellm-stack.sh plan
```

它会针对网络或网关模板调用 `aws cloudformation deploy --no-execute-changeset`。这会创建一个可供审查的变更集，但不会执行它。

审查变更集，然后部署：

```
CONFIRM_AWS_WRITE=1 make litellm-deploy
make litellm-status
# Direct helper invocations used by Make:
# CONFIRM_AWS_WRITE=1 deployment/scripts/litellm-stack.sh deploy
# deployment/scripts/litellm-stack.sh status
```

部署辅助脚本先针对网络堆栈、再针对 LiteLLM 网关堆栈运行 `aws cloudformation deploy`。状态辅助脚本运行 `aws cloudformation describe-stacks`，打印堆栈状态和输出。

ECS 服务使用部署断路器回滚和 Application Load Balancer 健康检查。参考模板还配置了目标跟踪自动扩缩容、加密的日志与数据、RDS 备份、ALB 访问日志和运维告警。

在客户环境中，请保持 `ENABLE_TLS=true`，使用可信的 DNS 名称和 ACM 证书，并把 Application Load Balancer 限制在已批准的企业或 VPN CIDR 范围内。把 ECS 任务和 Amazon RDS 放在私有子网中。不要公开暴露 ECS 任务的 4000 端口或 PostgreSQL 的 5432 端口。

### 创建限定范围的网关身份

不要把 LiteLLM 的主密钥分发给开发者。在被忽略的部署文件中配置用户或团队身份与策略：

```
CODEX_API_SECRET_ID=codex-litellm-gateway/alice-key
CODEX_KEY_ALIAS=alice@example.com
CODEX_KEY_USER_ID=alice@example.com
CODEX_KEY_MODELS=gpt-5.5
CODEX_KEY_MAX_BUDGET=50
CODEX_KEY_BUDGET_DURATION=30d
CODEX_KEY_TPM_LIMIT=100000
CODEX_KEY_RPM_LIMIT=1000
```

配置密钥：

```
CONFIRM_AWS_WRITE=1 make litellm-provision-key
# Direct helper invocation used by Make:
# CONFIRM_AWS_WRITE=1 deployment/scripts/litellm-stack.sh provision-key
```

辅助脚本在子进程中解析主凭证，带着已配置的模型、预算和速率策略调用 LiteLLM 的 `/key/generate` API，并把生成的密钥直接写入由 KMS 加密的 Secrets Manager 密钥。它不会把任一凭证放进命令行参数，也不会打印到终端。

在企业推广时，请为每个开发者 profile 授予权限：只能读取分配给自己的 scoped key 密钥，并用堆栈的 KMS 密钥解密。为不同团队或环境使用分离的密钥路径和 IAM 策略。

### 配置 Codex

生成 provider 配置块：

```
make litellm-codex-config
# Direct helper invocation used by Make:
# deployment/scripts/litellm-stack.sh codex-config
```

该辅助脚本从 CloudFormation 读取已部署的网关端点，并打印如下的 Codex provider 配置。它不会自动写入用户配置。

把输出添加到用户级的 ~/.codex/`config.toml`。provider 和认证设置属于用户级配置。Codex 会忽略项目本地 .codex/`config.toml` 文件中的这些设置。

生成的配置形如：

```
model = "gpt-5.5"
model_provider = "litellm-gateway"
web_search = "disabled"

[model_providers.litellm-gateway]
name = "LiteLLM Gateway"
base_url = "https://codex-gateway.example.com/v1"
wire_api = "responses"

[model_providers.litellm-gateway.auth]
command = "/absolute/path/to/python3"
args = [
"/absolute/path/to/deployment/scripts/aws-secret-auth.py",
"--aws-cli", "/absolute/path/to/aws",
"--region", "us-east-1",
"--secret-id", "codex-litellm-gateway/alice-key",
"--field", "LITELLM_API_KEY",
"--profile", "developer-profile",
"print-token"
]
timeout_ms = 30000
refresh_interval_ms = 300000
```

Codex 在不提供标准输入的情况下运行该认证命令，并从其标准输出读取 bearer token。辅助脚本使用指定的 AWS profile 获取当前密钥，因此 token 不会被存进 `config.toml`。

在 LiteLLM 管理界面中，**Models + Endpoints** 展示开发者可用的稳定别名及其上游 Amazon Bedrock 映射。这提供了一个快速的目视检查，确认开发者看到的是网关别名，而不是把他们的 Codex 配置直接耦合到某个提供商专属的模型 ID。

### 通过 LiteLLM 测试 Codex

启动一个新的交互式 Codex 会话，用 `/status` 确认所选 provider 是 `litellm-gateway`。若要做可重复的非交互测试，先运行一个最小的冒烟请求：

```
codex exec --sandbox read-only --ephemeral \
"Reply with exactly LITELLM_GATEWAY_OK and no other text."
```

该命令应成功退出并打印 `LITELLM_GATEWAY_OK`。接下来，用一个同时需要模型推理和本地工具的任务来演练 agent 循环：

```
codex exec --sandbox read-only --ephemeral \
"Read README.md with shell tools and summarize the deployment architecture. Do not modify files."
```

Codex 把任务和工具定义经 LiteLLM 发送出去。如果模型要求读取该文件，Codex 会在本地运行那条命令，并通过同一个网关回传工具结果。

在 LiteLLM 管理界面打开 **Logs**，选择 **Request Logs**，并筛选到测试时间窗口。确认：

- 请求状态为 `Success`。
- 密钥别名能识别出本次演练专用密钥或开发者密钥。
- 模型解析到预期的 Amazon Bedrock 映射。
- token 数、请求时长和费用都有值。
- 使用工具的任务产生了多行记录，因为 Codex 在后续的 Responses 请求中发送工具结果。

如果在 LiteLLM 中出现记录行之前就返回 `403`，通常意味着上游网络或 AWS WAF 的阻断。返回 `401` 则表示缺少网关认证或认证无效。不要在截图中公开 prompt、响应、原始密钥、完整请求 ID 或真实员工身份。

### 验证 Responses API 契约

一次成功的文本 prompt 并不能证明 agent 工作流是兼容的。Codex 依赖的不止是基础的 chat-completions 响应。请运行随附的严格探针：

```
make litellm-validate
# Direct helper invocation used by Make:
# deployment/scripts/litellm-stack.sh validate
```

该辅助脚本把 scoped key 解析到子进程环境中，并针对已部署的网关运行 deployment/scripts/`validate-responses-contract.py`。

该探针校验：

- Responses 对象必需字段与输出形状。
- 使用 `previous_response_id` 的语义延续。
- 带已完成终止响应的 server-sent event 流式传输。
- 带有调用 ID 的强制函数工具调用。

延续测试在第一个响应中记录一个唯一的测试标记，并验证它能在后续响应中被召回。这能抓出那些在语法上接受 `previous_response_id`、但实际上并不保留先前响应状态的网关。

实际部署通过了完整的契约校验。CloudFormation 成功完成，ECS 服务达到期望的任务数，部署滚动更新完成，ALB 目标健康，加密的 PostgreSQL 数据库可用且未公开可访问。

### 将 LiteLLM 投入企业级运营

成功的 `codex exec` 与契约测试表明 Codex 可以使用该网关，但兼容性只是起点。在让开发者接入之前，请先定义网关将如何控制模型访问、归属用量、执行用量策略，以及为每次模型请求留下运维记录。

从允许开发者使用的模型面入手。只为组织批准的模型发布稳定的网关别名，并在 deployment/litellm/`litellm_config.yaml` 中固定每个上游映射。重新构建网关镜像，并把同一个 Amazon ECR 摘要逐环境晋升。开发者可以继续配置稳定的别名，而系统团队仍掌控其背后的 Amazon Bedrock 模型。

当每个请求都可归因时，模型策略才更有用。为用户、团队或工作负载签发各自独立的 scoped key，而不是分发 LiteLLM 主密钥。Amazon Bedrock 在上游请求中看到的是 LiteLLM 的 ECS 任务角色，因此要把发起方身份带进 scoped key、LiteLLM 记录和导出的遥测中。这样就在网关层保留了开发者或团队的归因，并让请求 ID 可以与 AWS 服务日志关联，而无需记录凭证。

同一个 scoped 身份还可以执行用量策略。在配置密钥时设置 `CODEX_KEY_MAX_BUDGET`、`CODEX_KEY_BUDGET_DURATION`、`CODEX_KEY_TPM_LIMIT` 和 `CODEX_KEY_RPM_LIMIT`。用一个可弃用的身份越过已配置的阈值，确认 LiteLLM 拒绝了下一个请求，以此验证这些控制。这样测试的是策略本身，而不只是确认设置被接受。

运营网关还需要对完整请求路径的可见性。AWS 基础设施信号表明服务是否健康，而 LiteLLM 记录表明谁使用了哪个模型、该请求消耗了多少容量或预算。监控 ECS 期望与实际运行的任务数、部署回滚、Application Load Balancer 的目标健康与延迟、Amazon RDS 健康、LiteLLM 的请求与拒绝、token 用量、支出、密钥访问、IAM 变更和 AWS WAF 阻断。

在开发者接入之前，先决定 prompt 和响应是否可以记录。把这类内容视为可能敏感的客户数据，并据此定义脱敏、加密、访问控制和保留策略。生产部署应在模型访问路径上启用 Amazon Bedrock Guardrails，用于内容过滤、拒绝话题检测和接地（grounding）检查。网关层控制（预算、速率限制和路由）只是补充，不能取代在模型层施加的负责任 AI 防护。

下图展示了 LiteLLM 的 Usage 页面，它聚合所有使用该网关的开发者的请求与 token 指标。用这个视图监控采用情况、发现费用异常，并在调整预算或速率限制之前按用户或时间范围隔离流量。

### 两种替代访问路径

LiteLLM 是主要演练路径，因为它能让额外的网关控制显得直观可见。但它并非适合每个客户。

#### 通过 IAM Identity Center 直接访问

当原生 AWS 身份与审计控制已经够用时，使用内置的 `amazon-bedrock` Codex provider：

```
model_provider = "amazon-bedrock"
model = "openai.gpt-5.5"

[model_providers.amazon-bedrock.aws]
profile = "codex-bedrock"
region = "us-east-1"
```

开发者使用一个具名的 IAM Identity Center profile 登录：

```
aws sso login --profile codex-bedrock
```

这条路径去掉了网关、数据库及相关运维。它在 AWS CloudTrail 日志中保留开发者的 AWS 会话身份，但不会增加集中的网关级硬预算或路由策略。

仓库中的 [IAM Identity Center 快速入门](https://github.com/openai-on-aws/guidance-codex/blob/feat/enterprise-gateway-readiness/docs/QUICKSTART_NATIVE_AWS_ACCESS.md) 包含 CloudFormation 和辅助命令，用于创建隔离的组与权限集、把组分配到 AWS 账户、打印客户端配置，并针对 Amazon Bedrock 校验已登录的 profile。在增加网关之前，请先把这条直接路径作为基线。

#### 使用 Portkey 的托管或混合访问

当客户想要托管控制平面、集中路由与策略，或想要一个受支持的混合数据平面而不愿运营 LiteLLM 参考堆栈时，Portkey 可能很有用。

做 Codex 评估时，配置一个 Portkey workspace key、一个 Amazon Bedrock Model Catalog provider，以及 Responses wire 协议：

```
model_provider = "portkey"
model = "@bedrock-validation/<approved-model-id>"

[model_providers.portkey]
name = "Portkey"
base_url = "https://api.portkey.ai/v1"
env_key = "PORTKEY_API_KEY"
wire_api = "responses"
```

在正式推广之前，运行同样的严格 Responses 探针。特别要验证语义化的 `previous_response_id` 延续、流式传输、函数调用、实际的 Amazon Bedrock 路由，以及 IAM 角色与 external ID 设计。仅有产品文档或一次认证响应，并不能证明预期的模型路径满足完整的 Codex 契约。

当托管或混合运营模式比完全在你自己的 AWS 账户中运行网关更重要时，选择 Portkey。请把厂商许可、数据处理、区域可用性、故障模式和支持边界作为架构决策的一部分加以审查。

### 清理

预览 CloudFormation 将删除与保留的内容：

```
make litellm-cleanup-plan
# Direct helper invocation used by Make:
# deployment/scripts/litellm-stack.sh cleanup-plan
```

它会读取堆栈并列出资源与保留行为，不删除任何东西。

确认确切的堆栈名称之后，再删除网关：

```
CONFIRM_STACK_DELETE=codex-litellm-gateway \
make litellm-cleanup
# Direct helper invocation used by Make:
# CONFIRM_STACK_DELETE=codex-litellm-gateway \
# deployment/scripts/litellm-stack.sh cleanup
```

该辅助脚本会检查 Amazon RDS 的删除保护，调用 `aws cloudformation delete-stack`，并等待网关堆栈删除完成。

对于非共享的示例网络堆栈，需另行显式选择并确认：

```
CONFIRM_STACK_DELETE=codex-litellm-gateway \
DELETE_NETWORKING=1 \
CONFIRM_NETWORKING_DELETE=codex-networking \
make litellm-cleanup
# Direct helper invocation used by Make:
# CONFIRM_STACK_DELETE=codex-litellm-gateway \
# DELETE_NETWORKING=1 \
# CONFIRM_NETWORKING_DELETE=codex-networking \
# deployment/scripts/litellm-stack.sh cleanup
```

这会在网关堆栈之后额外删除示例网络堆栈。不要在共享网络时使用该选项。

参考堆栈会创建最终的 Amazon RDS 快照，并保留 KMS 密钥、Secrets Manager 密钥、CloudWatch 日志组和 ALB 访问日志存储桶。ECR 镜像和已配置的 scoped key 密钥同样不在堆栈删除范围内。请根据你的数据保留策略审查并移除这些保留资源。

## 结论

让 Codex 经由 LiteLLM 路由，为模型选择、限定身份、预算、速率限制和遥测提供了一个客户自运营的控制点，同时保留 Codex 的本地任务与工具执行模型。重要的生产门槛不是网关能否返回文本，而是网关能否保住 agent 工作流所需的那些 Responses 行为，以及系统团队能否可靠地运营新增的基础设施。

当原生 AWS 控制满足要求时，从直接的 IAM Identity Center 访问起步。当客户自运营的网关策略足以证明运维投入的合理性时，再加上 LiteLLM。当托管或混合运营模式更适合组织时，评估 Portkey，并对每一条路径施加相同的契约测试。
