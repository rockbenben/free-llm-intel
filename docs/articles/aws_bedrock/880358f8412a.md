# Amazon Finance 如何利用 Amazon Bedrock 和 Amazon Kendra 构建 AI 助手，为分析师的数据发现与业务洞察提供支持

Amazon Finance 各团队的财务分析师在财务规划与分析流程中面临日益加剧的复杂性。在处理横跨多个系统、数据湖和业务单元的海量数据集时，分析师会遇到若干关键挑战。第一，他们要花大量时间手动浏览数据目录、核对来自不同来源的数据，留给有价值的分析与洞察生成的时间因此减少。第二，历史数据与以往的业务决策往往散落在各类文档和遗留系统中，使得在规划周期中难以借鉴过去的经验。第三，随着业务语境快速演变，分析师需要快速获取相关指标、规划假设和财务洞察，以支撑数据驱动的决策。

传统工具与流程不足以应对这些挑战。基于关键词的搜索常常错过财务数据中的上下文关联，僵硬的查询结构限制了分析师动态探索数据的能力。此外，缺乏机构知识的留存意味着宝贵的洞察和决策理据往往被孤立在各自角落，或随着时间流失，导致重复分析，以及各团队之间规划假设不一致。这些挑战严重影响了财务规划的效率、决策的敏捷性以及业务洞察的整体质量。分析师需要一种更直观的方式，来访问、理解并使用其组织积累的财务知识与数据资产。

Amazon Finance 技术团队负责开发和管理一整套技术解决方案，为财务决策和运营效率提供支撑，同时在 Amazon 的全球运营中推行标准化。本文说明该团队如何借助 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 发挥生成式 AI 的能力，并结合 [Amazon Kendra](https://aws.amazon.com/kendra/) 的智能搜索，构思并落地了一套应对这些业务挑战的方案。

## 解决方案概览

为应对这些业务挑战，Amazon Finance 开发了一套由生成式 AI 和企业级搜索能力驱动的 AI 助手方案。该方案帮助分析师通过自然语言查询与各类财务数据源和文档交互，尽可能减少跨多个系统进行复杂手动搜索的需要。这个助手访问一个由财务文档、历史数据和业务语境构成的综合知识库，在维持企业安全标准的同时给出相关且准确的回答。这种做法不仅简化了数据发现，还留存了机构知识，并使整个组织能够做出更一致的决策。

该 AI 助手的方法论由两个关键解决方案组件构成：智能检索与增强生成。检索系统使用向量存储（vector store），这是一类专门用于高效存储和搜索文本含义高维表示的数据库。与传统依赖关键词匹配的数据库不同，向量存储把用户查询转换为向量表示，并在数据库中寻找相近的向量，从而实现语义搜索。在这个检索基础之上，系统采用增强生成来产出准确、契合上下文的回答。这种做法在生成回答时引入外部知识来源，从而增强传统语言模型，显著减少幻觉并提升事实准确性。整个过程分三步：用语义搜索从知识来源中检索相关信息，用这些上下文对语言模型进行条件化，再生成融合了所检索信息的精炼回答。通过结合这些技术，该助手给出的回答既有恰当的上下文，又植根于经过核实的组织知识，因而特别适合财务运营与规划这类知识密集型应用。

我们通过在 Amazon Bedrock 上组合使用大语言模型（LLM）与 Amazon Kendra 的智能搜索，实现了这套检索增强生成（Retrieval Augmented Generation，RAG）系统。

在以下章节中，我们讨论方案中使用的关键架构组件，并说明整体方案如何运作。

### Amazon Bedrock

我们选择了 Anthropic 的 Claude 3 Sonnet 这一强大的语言模型，因为它具备出色的语言生成能力，以及理解和推理复杂主题的能力。通过 Amazon Bedrock 把 Anthropic 的 Claude 接入 RAG 模块后，AI 助手能够生成贴合上下文且信息丰富的回答，把从向量存储检索到的知识与模型自身的自然语言处理与生成能力顺畅地结合起来，从而带来更像人类、更具吸引力的对话体验。

### Amazon Kendra（Enterprise Edition Index）

Amazon Kendra 为 AI 助手类应用提供了强大的自然语言处理能力。它擅长理解用户问题，并通过语义搜索找到相关答案。该服务能与生成式 AI 模型顺畅协作，在 RAG 方案中尤其如此。Amazon Kendra 中的企业级安全功能为数据保护和合规提供支持。它理解用户意图并能直接连接 Amazon Bedrock 的能力，使其非常适合业务助手。这有助于基于业务文档和数据目录展开有意义的对话。

我们没有选择 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/)，而是选择了 Amazon Kendra Enterprise Edition Index，主要原因是它具备成熟的内置能力，且对人工配置的需求更少。OpenSearch Service 需要大量定制和技术专长，而 Amazon Kendra 则提供开箱即用的自然语言理解、对 40 多种文件格式的自动文档处理、预置的企业级连接器，以及包括同义词识别和查询优化建议在内的智能查询处理。该服务会自动结合关键词、语义和向量三种搜索方式，而 OpenSearch Service 需要手动实现这些特性。Amazon Kendra 的这些特性适合我们金融领域的用例，在该领域准确性对可用性至关重要。

在信息检索方面，我们同样没有选择 [Amazon Q Business](https://aws.amazon.com/q/business/)，而是选择了 Amazon Kendra Enterprise Edition Index，因为它是一个更稳健、更灵活的方案。尽管这两个工具都旨在简化对企业信息的访问，但 Amazon Kendra 提供更出色的检索准确性，以及对搜索参数更强的控制力。借助 Amazon Kendra，您可以调整相关性调优、定制文档属性，并实现自定义同义词以提升搜索精度。这种定制能力帮助我们针对 Amazon Finance 领域的具体需求来调整搜索体验，并在用户对话中进入增强生成步骤之前先行监控搜索结果。

### Streamlit

我们选择 [Streamlit](https://streamlit.io/) 这一基于 Python 的交互式 Web 应用框架来构建 AI 助手的 UI，原因是它开发速度快、能与 Python 及助手的后端组件顺畅集成、提供交互式且响应灵敏的 UI 组件、具备数据可视化的潜力，并且部署方式简单直接。借助 Streamlit UI，该助手提供了友好且富有吸引力的界面，既便于自然语言交互，也支持应用的高效迭代和部署。

### Prompt 模板

Prompt 模板用于格式化用户查询、整合检索到的知识，并为回答生成提供指令或约束；这对于生成既融入 Anthropic 的 Claude 的语言生成能力、又结合 Amazon Kendra 搜索所检索到的相关知识的上下文丰富回答而言，是必不可少的。以下是一个 prompt 示例：

```
"""
H: Use the following pieces of context to provide a concise answer to the question at the end. If you don't know the answer, just say that you don't know, don't try to make up an answer.
<context>
{context}
</context>

Question: {question}

A:
"""
```

### 解决方案架构

下面的解决方案架构图展示了关键架构组件如何协同支撑这套方案。

![展示用户、Streamlit 应用、Amazon Bedrock LLM 与 Kendra 索引之间数据流的示意图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/20/ML-17902-arch-diag-1.png)

该工作流由以下步骤组成：

- 用户通过身份验证后在聊天框中提出问题。
- Streamlit 应用把查询发送给 Amazon Kendra 检索器，以检索相关文档。
- Amazon Kendra 把相关段落和文档引用发送给 RAG 方案。
- RAG 方案使用 Amazon Bedrock 中 Anthropic 的 Claude，配合 prompt 模板和作为上下文的相关段落。
- LLM 的回复被送回 Streamlit UI。
- 回复连同反馈功能和会话历史一并展示给用户。
- 用户对回答的反馈单独存储在 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）中
- Amazon Kendra 为存储在 S3 存储桶中的相关文档建立索引，以便进行文档搜索和检索。

### 前端架构

考虑到方案的可扩展性和安全性，我们设计了如下前端架构，以便快速修改和部署。

![使用 Route 53、CloudFront、Lambda 以及在 VPC 中通过负载均衡运行的 AWS Fargate 与 ECS 的身份验证工作流示意图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/20/ML-17902-arch-diag-2.png)

该工作流由以下步骤组成：

- 用户在浏览器中访问应用 URL。
- [Amazon Route 53](https://aws.amazon.com/route53/) 把用户的请求解析到 [Amazon CloudFront](https://aws.amazon.com/cloudfront/) 分配，CloudFront 随后选择距离用户最近的服务器（以尽量降低延迟）。
- CloudFront 运行一个 [AWS Lambda](https://aws.amazon.com/lambda) 函数，确认用户已完成身份验证。若未验证，用户会被重定向去登录。成功登录后，用户被重定向回应用网站。整个流程重复一次，CloudFront 再次触发该 Lambda 函数，这一次用户就能访问网站了。
- 此时已完成身份验证，CloudFront 返回 Web 应用的静态资源。
- [AWS Fargate](https://aws.amazon.com/fargate) 让您无需管理底层 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2)（Amazon EC2）实例即可运行容器。这使容器可以作为真正的无服务器服务运行。[Amazon Elastic Container Service](https://aws.amazon.com/ecs)（Amazon ECS）配置了自动扩缩容（目标跟踪自动扩缩容，依据每个目标的 [Application Load Balancer](https://aws.amazon.com/elasticloadbalancing/application-load-balancer/)（ALB）请求数进行扩缩）。

## 方案性能评估

我们实现了一套全面的评估框架，以严格评估该 AI 助手的表现，确保其达到金融应用所需的高标准。我们的框架既设计了用于衡量可量化表现的定量指标，也设计了用于衡量用户体验和回答质量的定性指标。在与分析师一起进行的基准测试中，我们发现该方案把搜索时间大幅缩短了 30%，因为分析师现在可以用自然语言搜索；同时搜索结果准确性提升了 80%。

### 定量评估

我们主要聚焦精确率与召回率测试，构建了一个包含 50 多个业务查询的多样化测试集，覆盖分析师日常遇到的典型用例。以人工标注的答案作为 ground truth，我们在两大类场景中评估系统表现：数据发现和知识搜索。在数据发现场景中（系统帮助分析师定位特定数据源和指标），在对数据源未做元数据增强的情况下，我们取得了 65% 的初始精确率和 60% 的召回率。这些数字看起来或许不算高，但相比此前的手动搜索流程已是显著改善——旧流程的估计成功率只有 35%，且通常需要在不同系统中反复多次。新系统当前达到这些数字的主要原因，是数据源缺少丰富的元数据；这也是一个很好的信号，促使团队着手改善数据资产的元数据采集，相关工作目前正在推进。

知识搜索能力在对数据源未做元数据增强的情况下，取得了 83% 精确率和 74% 召回率的初始成绩。相比传统的基于关键词的搜索方法（在我们的内部测试中通常只能达到 45–50% 的精确率），这是实质性的提升。这一改善尤其有意义，因为它意味着分析师大约十次中有八次能在第一次搜索时就找到正确信息，而过去平均需要尝试 3–4 次才能定位到同样的信息。

### 定性指标

定性评估围绕忠实度（faithfulness）这一概念展开——对以准确性和可靠性为根本的金融应用来说，这是一项关键指标。我们采用了一种创新的 LLM-as-a-judge 方法，评估该 AI 助手的回答在多大程度上与来源文档一致，以及在多大程度上避免了幻觉或无依据的断言。结果显示不同用例之间存在明显差异：数据发现达到 70% 的忠实度，业务知识搜索则达到了令人印象深刻的 88% 忠实度。这些分数显著优于我们此前的文档搜索系统——那套系统没有内置的核实机制，常常导致分析师使用过时或错误的信息。

最重要的是，新系统把找到相关信息所需的平均时间从 45–60 分钟缩短到仅 5–10 分钟——效率提升了 85%。用户满意度调查显示，92% 的分析师更偏爱新系统而非传统搜索方式，并把更高的准确性和节省的时间列为主要优点。

这些评估结果不仅验证了我们的做法，也凸显了未来需要增强的具体方面。随着系统演进，我们会持续改进评估框架，确保它在满足财务分析师动态需求的同时保持高标准的准确性与可靠性。评估框架在业务用户群体中建立信任方面发挥了关键作用，它提供了透明的指标，证明系统有能力处理复杂的财务查询，同时维持财务运营所必需的准确性标准。

## 用例

我们的方案改变了财务用户与复杂财务和运营数据的交互方式，让他们可以通过自然语言查询来访问这些数据。本节讨论几个关键示例，展示系统如何简化数据发现。

### 顺畅的数据发现

该方案让用户能够通过自然语言查询找到数据源，而不必具备数据库结构方面的技术知识。它精巧地结合向量存储与企业级搜索能力，把用户的问题与相关数据源匹配起来，不过必须注意上下文管理，并防止过度依赖此前的交互。在 AI 助手方案之前，财务分析师需要深厚的技术知识才能在复杂的数据库结构中导航，往往要花几个小时浏览多个文档来源，只为找到某张特定的数据表。理解系统工作流需要大量查阅技术文档，或联系领域专家，这造成了瓶颈并降低了生产力。即便是经验丰富的用户，也很难从散落在不同系统中的碎片信息里拼出完整的业务流程全貌。现在，分析师只需用自然语言提问，例如“我在哪里能找到生产率指标？”“我如何访问设施信息？”或“哪个仪表盘展示运营数据？”，就能得到精确且贴合上下文的答案。该方案把企业级搜索能力与 LLM 结合起来，理解用户意图，并从结构化和非结构化数据源中提供相关信息。分析师现在能获得指向具体汇总报表的准确指引、对业务流程的清晰解释，以及在需要时的相关技术细节。在我们的基准测试中，仅就数据发现任务而言，系统在未做元数据增强的情况下达到 70% 忠实度和 65% 精确率，而文档搜索表现更强，达到 83% 精确率和 88% 忠实度。

### 借助知识文档帮助理解内部业务流程

财务分析师过去在接触企业规划工具时面临陡峭的学习曲线。这些系统的复杂性意味着即便是基础任务也需要大量查阅文档，或等待不堪重负的领域专家提供支持。新团队成员可能需要数周甚至数月才能熟练上手，而即便是经验丰富的用户也难以跟上系统更新与变化。这在财务运营和规划流程中形成了长期瓶颈。AI 助手的引入从根本上改变了分析师学习和使用这些规划工具的方式。分析师不再需要翻阅数百页技术文档，而是可以直接问一些简单的问题，例如“我如何为新资产预测折旧？”“季度规划流程是怎么运作的？”或“季度规划周期需要哪些输入？”系统会基于经过核实的文档和系统规格，给出清晰且贴合上下文的解释。我们的基准测试显示，在检索和解释技术与业务信息方面，它达到了 83% 精确率和 88% 忠实度。新分析师可以在几周内就变得高效，经验丰富的用户可以快速核对流程，领域专家则可以把精力放在更复杂的挑战上，而不是回答例行问题。这标志着在让企业系统更易用、更高效方面的一大进步，同时维持了财务运营所要求的准确性与可靠性。尽管这项技术仍在演进，尤其是在处理微妙查询和保持对系统更新的全面覆盖方面，但它已经独立地改变了团队与规划工具打交道的方式。

## 结论

本文讨论的 AI 助手方案在数据发现和业务洞察生成方面都体现出显著改善，为 Amazon Finance 带来了多项关键收益。分析师现在可以通过自然语言查询快速找到相关信息，大幅缩短搜索时间。系统从不同数据源综合洞察的能力明显增强了数据驱动的决策；其对话式界面和贴合上下文的回答推动了自助式数据探索，有效减轻了集中式数据团队的负担。

这套创新的 AI 助手方案展示了 AWS 生成式 AI 在改造企业数据发现与文档搜索方面的实际威力。通过结合 Amazon Kendra Enterprise Edition Index、Amazon Bedrock 和先进的 LLM，这一实现取得了令人瞩目的精确率，证明复杂的 AI 驱动搜索既可实现也切实有效。这一成功表明，AWS 生成式 AI 服务既能满足当前业务需求，也能推动企业搜索未来的创新。对于希望用自然语言改善数据发现流程、支撑智能化企业应用的组织而言，这些服务提供了坚实的基础。如需进一步了解如何实现 AI 驱动的搜索方案，请参阅 [Build and scale the next wave of AI innovation on AWS](https://aws.amazon.com/ai/) 和[探索 AWS AI 用例](https://aws.amazon.com/machine-learning/ai-use-cases/)。

**![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/20/hs-amdhanda-1.png)Amit Dhanda** 是 Amazon 全球运营财务团队的高级科学家，他在那里运用 AI/ML 技术解决复杂的电商挑战。加入 Amazon 之前，他是 Adore Me（现为 Victoria's Secret 的一部分）的数据科学总监，通过推荐系统提升数字零售体验。他曾在 EXL 和 Thomson Reuters 担任科学领域的领导职位，为那里的客户互动/增长和文本分类开发 ML 模型。
