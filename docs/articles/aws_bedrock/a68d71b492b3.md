# Halliburton 借助 Amazon Bedrock 与生成式 AI 增强地震工作流创建

地震数据分析是能源勘探的关键环节，但配置复杂的处理工作流历来是一项耗时且容易出错的工作。Halliburton 的 Seismic Engine 是一款用于地震数据处理的云原生应用，功能强大，但此前要创建工作流，需要手动配置约 100 个专用工具。这一过程不仅耗时，还要求深厚的专业知识，可能限制了该软件的可及性与使用效率。

为解决这一难题，Halliburton 与 AWS 生成式 AI 创新中心（AWS Generative AI Innovation Center）合作，为 Seismic Engine 开发了一款 AI 驱动的助手。该方案使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/)、[Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)、[Amazon Nova](https://aws.amazon.com/nova/) 和 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/)，把复杂的工作流创建转化为对话。地球科学家与数据科学家可以通过自然语言交互来配置处理工具，而无需手动配置。

本文将介绍我们如何构建一个概念验证（proof-of-concept），它既能将自然语言查询转换为可执行的地震工作流，又能为 Seismic Engine 的工具与文档提供问答能力。我们会讲解该方案的技术细节，分享显示工作流提速最高达 95% 的评测结果，并讨论一些关键经验，帮助其他组织用生成式 AI 改进其复杂的技术工作流。

> 与 AWS 的合作在加速地下解释工作流方面发挥了关键作用。通过将 Amazon Bedrock 服务与 Halliburton Landmark 的 DS365 Seismic Engine 集成，我们得以把传统上耗时的工作流构建任务缩短了一个数量级。这款由生成式 AI 驱动的工作流助手不仅提升了效率与准确性，还让我们先进的地球物理工具更易于被更广泛的用户使用。AWS 上可扩展的云原生架构使我们能够交付无缝的对话式体验，从根本上改善地下工作流的整体生产力。
>         —— Phillip Norlund，Halliburton Landmark 地下技术经理
>          —— Slim Bouchrara，Halliburton Landmark 地下研发高级产品负责人

## 方案概览

本项目旨在解决两个核心目标：把自然语言查询转换为可执行的地震工作流，以及为 Seismic Engine 文档提供智能问答（Q&A）系统。为此，我们基于 Amazon Bedrock 开发了一套方案，让地球科学家能够通过自然对话与复杂的地震工具交互。整个系统的骨干是部署在 AWS App Runner 上的 FastAPI 应用，它通过流式接口处理用户查询。当用户提交查询时，由 Amazon Nova Lite 驱动的意图路由器（intent router）会分析请求，判断用户是要生成工作流，还是想获取技术信息。对于问答类请求，系统使用 Amazon Bedrock Knowledge Bases 与 Amazon OpenSearch Serverless，从已建立索引的文档中给出相关答案。对于工作流类请求，一个使用 Amazon Bedrock 上 Anthropic Claude 的生成 agent 会从 82 个可用的 Seismic Engine 工具中进行选择，生成 YAML 工作流。

为了保持上下文并支持多轮对话，我们集成了 Amazon DynamoDB 来存储聊天历史和交互日志。系统对问答和工作流生成都支持流式响应，在用户请求处理过程中即时给出反馈。这一架构让复杂的技术工作流可以通过自然对话创建和修改，同时保留地震数据处理所需的精确控制。下图展示了该方案的架构。

### 查询路由与意图分类

用户查询进入系统后，Intent Router 会通过 Amazon Bedrock API 调用 Amazon Nova Lite，对给定查询的意图标签进行分类。系统向该大语言模型（LLM）提供 prompt，要求它输出三个意图标签之一：“Workflow_Generation”、“QnA” 和 “General_Question”。标签 “Workflow_Generation” 用于路由与工作流生成相关的查询，包括读取/加载数据集、数据处理操作，以及涉及操作特定数据集的各种请求。意图标签 “QnA” 用于与具体工具相关的问题、请求示例工作流，或询问 Seismic Engine 文档。标签 “General_Question” 则保留给与 Seismic Engine 操作或工作流无关的查询。在我们的实现中，Amazon Nova Lite 高效地完成了路由任务，在准确性与延迟之间取得了良好平衡。

### 问答功能实现

问答组件通过 Amazon Bedrock Knowledge Bases 处理与 Seismic Engine 相关的查询，这是一个为端到端检索增强生成（RAG）工作流提供的全托管服务。我们选择 Bedrock Knowledge Bases，是因为它免去了管理向量数据库、分块（chunking）策略和嵌入 pipeline 的运维负担。作为全托管服务，它会自动处理基础设施扩缩容、安全与维护，使我们的团队可以专注于方案开发，而不是 RAG 基础设施运维。该服务原生支持多种分块策略，包括分层分块（hierarchical chunking）——它维护父子关系，在细粒度检索与更宽的文档上下文之间取得平衡。数据源包括工具文档的 markdown 文件以及存放在 S3 中的 Seismic Engine 手册。由于工具文档相对较短，我们未对其做分块，以保留单个工具的完整上下文。对于 Seismic Engine 手册这类较长的文档，我们使用默认设置的分层分块。我们使用 Amazon Titan Text Embeddings V2 生成嵌入，并用 OpenSearch Serverless 作为向量数据库。系统还会为每个已索引条目存储元数据，例如文件名、URL 和文档类型，供下游使用。在检索和响应生成两方面，我们都使用 Amazon Bedrock Knowledge Bases 的 retrieve_and_generate API，模型为 Claude 3.5 Haiku。系统通过维护会话上下文支持多轮对话，响应带有行内引用，以增强可追溯性。

*注：本方案在开发与评测时使用的是 Claude 3.5 Sonnet V2 和 Claude 3.5 Haiku。此后，这些模型已相继由 Claude Sonnet 4.5 以及最新的 Claude Sonnet 4.6 接替，另外还有 Claude Haiku 4.5，它们均可通过 Amazon Bedrock 使用。该方案架构支持无需修改代码即可升级模型，因此你可以用上最新的模型能力。*

这一做法使我们的系统能够针对用户关于 Seismic Engine 工具与工作流的问题，给出结合上下文的相关回答。

### 工作流生成

对于被归类为 “Workflow_Generation” 的查询，我们的方案使用 LLM agent 将自然语言转换为可执行的 YAML 工作流。该 agent 绑定了 Seismic Engine 上可用的 82 个工具。根据用户查询以及定义输入、参数和输出的工具规格，agent 会选择合适的工具、确定正确的执行顺序，并生成满足用户需求的 YAML 工作流。下图展示了工作流生成过程。

![示意图：工具调用 LLM 一步处理用户查询与聊天历史，生成输出 YAML](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/09/ML-20026-image-2.jpg)

我们在实现中同时使用了 Claude 3.5 Sonnet V2 和 Claude 3.5 Haiku，并通过 LangChain 框架进行编排，以管理 agent 和绑定工具。我们为模型提供了详细的工具说明与规格，使其能够理解每个工具的能力与要求。生成工作流时，系统不仅考虑用户查询中的明确要求，还会在未给出具体值时补上必要的默认参数。工作流生成过程支持多轮对话，用户可以用自然语言请求修改先前生成的工作流。借助存放在 Amazon DynamoDB 中的对话历史，LLM 可以根据用户当前的查询生成新的工作流，或修改已有的工作流。

## 评测

为了评估方案的有效性，我们构建了一个较全面的查询—工作流配对测试数据集，其中既包含低复杂度工作流，也包含中等复杂度工作流。这些数据来自真实的历史工作流，并由领域专家校验，以确认它们能准确代表典型的用户请求。

### 工作流生成结果

| **模型** | **复杂度** | **成功率** | **平均生成时间（秒）** | **生成时间中位数（秒）** |
| --- | --- | --- | --- | --- |
| Claude Haiku 3.5 | 简单 | 84% | 8.3 | 5.9 |
|  | 中等 | 90% | 12.4 | 9.1 |
| Claude Sonnet 3.5 V2 | 简单 | 86% | 11.2 | 11.5 |
|  | 中等 | 97% | 15.8 | 16.6 |

两个模型都表现出色，其中 Claude Sonnet 3.5 V2 的成功率更高，尤其是在中等复杂度的工作流上。系统以流式方式返回响应，让用户在工作流生成过程中即时获得反馈，完整工作流在 5.9-16.6 秒内交付。Claude Haiku 3.5 的生成速度更快，提供了在速度与准确性之间权衡的选项。

### 与基线表现对比

| **用户类型** | **成功率 %** | **失败率 %** | **构建简单流程耗时（分钟）** | **构建复杂流程耗时（分钟）** |
| --- | --- | --- | --- | --- |
| 新用户 | 70% | 20% | 4 | 20 |
| 有经验的用户 | 85% | 10% | 2 | 5 |
| 我们的方案 | 84-97% | 3-16% | 0.13-0.26 | 0.21-0.28 |

我们的生成式 AI 方案带来以下改进：

- 84-97% 的成功率超过了新用户和有经验的用户。
- 工作流创建时间从数分钟缩短到数秒，时间降幅超过 95%。

这些结果表明，不同经验水平的用户都能将生产力提升 95% 以上，同时保持或超过手动创建工作流的准确性。

## 结论

本文展示了我们如何借助 Amazon Bedrock 将复杂的技术流程转化为自然对话。通过实现一个集成了问答能力的 AI 驱动助手，我们取得了 84-97% 的工作流生成成功率，同时相比手动流程将创建时间缩短了 95% 以上。系统既能处理低复杂度也能处理中等复杂度的工作流，加上对 Seismic Engine 工具的上下文理解，说明生成式 AI 可以在不牺牲准确性的前提下改善工业软件的易用性。

这一做法也能很好地推广到其他领域——那些具有复杂的多步 agentic 工作流、且需要专门工具知识与配置的场景。后续步骤可以考虑探索多 agent 架构，使用 [Strands Agents SDK](https://strandsagents.com/) 配合 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 之类的框架，通过专门化的子 agent 提升准确性。
