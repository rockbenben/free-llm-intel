# Orca Security 用 Amazon Bedrock 实现自然语言安全查询

安全分析师需要快速得到关于自家云基础设施的答案，而不必对特定领域的查询语言了如指掌。[Orca Security](https://orca.security/) 的工具覆盖 900 多种云模型（即 Sonar 跟踪的资源类型，例如 Amazon Elastic Compute Cloud (Amazon EC2) 实例或 Amazon Simple Storage Service (Amazon S3) 存储桶）。要查询这些数据，就得给出精确的模型名称、沿嵌套关系逐层导航，并从 18 种运算符中挑选（即用于筛选结果的比较函数，如「等于」或「包含」）。

为解决这个问题，Orca Security 与 AWS 合作，在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上构建了 Discovery AI——一个自然语言查询智能体。Orca 为云、代码和 AI 提供上下文感知的安全能力，Sonar 则是它专有的领域查询系统，用户可在整张数据图上搜索、筛选和探查。

本文中，我们会分享 Discovery AI 的架构与成果：它把一个自然语言问题转换成一条 Sonar 查询。相比最初的基线，Orca 将查询成本降低了 90%，输入 token 降低了 93%，延迟降低了 75%。

## 打通自然语言与结构化查询

Orca Security 的 Sonar 查询系统支持 900 多种云基础设施与应用模型，这些模型之间的关系错综复杂。要查询这些数据，用户得构造 JSON 对象：指定精确的模型名称、从 18 种运算符中挑选、再跨云服务商沿父子层级逐层导航。想把这件事做对，必须对 Sonar schema 非常熟悉。

为了建立这种能力，Orca 团队着手打造一层自然语言接口，让它能从纯文本生成有效的 Sonar 查询。

他们最初的可行性验证，是把完整的 Sonar schema 塞进一个可用的最大模型的单个提示词里。这包含 900 多个模型定义、每一种关系类型，以及一大批示例查询。输出质量不错（设计合作伙伴和内部用户都给了正面反馈），但在生产规模下暴露出三个明显短板。

token 消耗很不经济，每个工作负载约要 200 万输入 token，把成本推高。延迟也很高，每个工作负载的端到端响应时间约 60 秒。复杂的多模型查询准确率有限，因为嵌套关系和多条件查询往往还需要额外打磨。

Orca 团队已经验证这套思路可行。下一个挑战，是让它既划算、又够快、够准，能上生产。为此，Orca 团队设计并部署了一套方案：基于 Amazon Bedrock，每天处理数千条查询，响应时间 15 秒。

## 方案概览

Orca 把 Discovery AI 设计成 Amazon Bedrock 上的一套混合方案，将检索增强生成（RAG）与 schema 感知的查询构造结合起来。系统通过一条多阶段流水线，把自然语言问题转换成有效的 Discovery 过滤器，每个阶段都配上最合适的 Amazon Bedrock 模型。

Orca 选择 Amazon Bedrock，是因为它通过单个 API 提供多模型访问，让团队能给流水线的各个阶段分配不同的基础模型，而不必单独维护一套套集成。Amazon Bedrock 还能借助 AWS Identity and Access Management (IAM)、虚拟专有云 (VPC) 端点和 AWS CloudTrail 继承 AWS 的治理控制，满足 Orca 的安全要求。这种与模型无关的架构，意味着团队可以随新版本发布就替换进更新的模型，而不必重构流水线。

图 1：多阶段 Discovery AI 流水线架构，展示在 Amazon Bedrock 上用基础模型把自然语言输入转换为经过校验的 Discovery 过滤器查询的流程

Discovery AI 流水线经过九个步骤，把一条自然语言请求转换成经过校验的 Discovery 过滤器。

- 请求入口与上下文准备：流水线先把用户的自然语言请求与相关上下文合并，这些上下文包括用户所在的组织、已连接的云服务商以及请求元数据。这些上下文帮助流水线准确理解请求，并生成一个贴合客户环境的 Discovery 过滤器。
- 快速确定性匹配器（Quick Matcher）：快速匹配器识别 IP 地址、Common Vulnerabilities and Exposures (CVE)、ARN、文件哈希、Amazon Machine Image ID、Oracle Cloud Identifier、EC2 ID、URL 和告警 ID 等结构化输入。它用正则和基于规则的匹配来检测高置信度的模式。一旦命中，流水线可以走一条快速路径，直接返回一个预先定义的 Discovery 过滤器，无需动用大语言模型（LLM）推理。若未命中，请求继续进入下一步。
- LLM Guardrail 筛查：Guardrail 组件检查请求是否安全、相关、属于技术范畴且在支持范围内。它在提示词注入攻击、跑题请求和不受支持的输入抵达流水线其余部分之前就把它们拦下。未通过 Guardrail 检查的请求会被拒绝，并返回相应的错误信息。通过检查的请求继续进入示例检索。
- 基于嵌入的语义候选召回：流水线用 Amazon Titan Text Embeddings 检索以往经过校验的相关查询示例。它根据语义相似度从向量库中取回最近的 20 个示例。这些候选为流水线提供了参考——看看类似的自然语言请求此前是如何被转换成 Discovery 过滤器的。
- 神经相关性重排：取回的候选用 Amazon Bedrock 上的 Cohere Rerank 3.5 重新排序。它找出与当前请求最相关的示例，选出信号最强的 5 个。当找到精确匹配或高置信度匹配时，流水线可以直接复用已验证有效的过滤器。否则，重排后的示例会被交给生成阶段。
- 由 LLM 驱动的相关模型选择：模型选择把 900 多个 Sonar 模型收窄到与请求相关的少数几个。选模型时，它会综合考虑用户的请求、已连接的云服务商和检索到的示例。选中的模型按合适的 schema 粒度提供给生成器，粒度从紧凑的 micro schema 到更详尽的 mini schema 不等。这样减少了不必要的上下文，让生成更高效。
- 工具增强的智能体式过滤器生成：生成器用一个工具增强的智能体来构造最终的 Discovery 过滤器。它围绕所选模型的 schema、检索到的示例、用户上下文和可用工具进行推理。这个智能体可以在逼近用户请求的有效表示时，反复打磨过滤器。
- 静态校验与 API 校验：生成的过滤器要接受语法和语义正确性检查。流水线先做静态校验，再拿过滤器去对照 Orca 的 Sonar API 验证。校验失败时，错误会返回给生成器，让智能体修正过滤器再试一次。若达到最大重试次数仍未得到有效的过滤器，流水线就返回一个「过滤器无效」的响应。生成器被约束在重排后的示例和选中的 schema 之内。静态校验会把每一个模型、字段和运算符都回溯到那些 schema 定义。每一次校验错误都会回到智能体手里，并指出出错的具体元素，因此重试是重新基于事实作答，而不是重新猜测。
- 后处理与响应：在产出有效过滤器之后——无论来自快速匹配器、复用已验证有效的示例，还是智能体式生成——流水线着手准备最终响应。团队根据各阶段的需求，在 Amazon Bedrock 上为不同组件分配了不同的基础模型。[Anthropic Claude Haiku 4.5](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-anthropic-claude-haiku-4-5.html) 支撑模型选择器和生成器，这两个组件需要很强的推理能力来准确构造查询。[Amazon Nova 2 Lite](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-amazon-nova-2-lite.html) 负责 Guardrail 和校验器，这里优先考虑的是低成本下的快速推理。Amazon Titan 为示例检索组件提供语义搜索所用的嵌入。Cohere Rerank 3.5 对检索到的候选重新排序，以最大化相关性。各 AWS Region 的模型可用性，请参考[按模型划分的区域可用性](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。

## 在示例检索中把相关性和多样性拉满

示例检索最终成了整条流水线里对准确率影响最大的一个杠杆。好的示例能比单靠 schema 更高效地教会生成器如何把问题翻译成 Sonar 查询，所以 Orca 团队在 Amazon Bedrock 上给几种检索策略做了基准对比。每种策略都在相关性、多样性或速度之间做了不同的取舍，把它们直接摆在一起比，就能看出哪种组合最好。

纯 top-K 语义检索基于 Amazon Titan 嵌入，跑起来很快，但它倾向于返回近乎重复的示例，让生成器缺少多样性。最大边际相关性 (MMR) 改善了多样性，但当排第一的候选本来就是正确答案时，它却牺牲了相关性。先检索更大的候选集再重排，能拉进一个更大的池子，并用重排器挑出最相关的子集——这已经指向了最终的取胜方案。

胜出方案是用 Amazon Titan 嵌入做 top-20 最近邻检索。随后 Orca 用 Cohere Rerank 3.5 把这些结果重排到前 5 个。这种做法给生成器提供的是一组规模小、多样、高度相关的示例，而不必在检索时牺牲覆盖度或精度。

## 把 900 多个模型装进上下文

一条核心约束决定了这套架构的走向。把 900 多个 Sonar 模型的 schema 塞进每一个提示词并不现实。即使用长上下文模型，这么做也会同时拖高成本、拉低准确率。

模型选择器解决了这个问题。它跑在 Anthropic Claude Haiku 4.5 上，针对每个模型的紧凑而语义丰富的表示（名称、用途、关键字段和关键关系）工作。拿到用户的问题后，它只返回生成器真正需要的模型。于是生成器只对被选中的那些模型，再加上把它们连接起来的关系，才拿到完整的 schema 细节。

## 评估方法

为了能有底气地迭代，Orca 团队在项目早期就搭起了一套持续评估的框架。这套框架把一份精心整理的数据集、一层自动化打分，以及一种按切片度量的方法结合在一起，让团队在每次改动上线前都能信任它。这几样合在一起，把评估变成了例行步骤，而不是事后补的作业。

这份整理好的评估数据集涵盖了生产中会遇到的各类问题、模型家族和复杂度层级，因而能反映真实用法。一层 LLM 作为评判（LLM-as-judge）的打分机制，从正确性、完整性，以及与参考查询的语义等价性三方面给生成的查询打分，为团队提供一致的质量信号。度量方法再把差异按切片拆开，让团队能精确定位退化发生在哪里、该修什么。

每一次对提示词、模型、检索参数或示例的改动，上线到生产之前都要先过一遍这套框架。

## 领域专家在环的标注体系，支撑持续改进

要在客户环境不断演变、新问题模式不断涌现的情况下守住准确率，光有一个扎实的首发部署还不够。Orca 团队为产品经理、支持工程师和安全研究员做了一个内部标注工具。用它，他们可以标记查询、修正输出，并在一步之内把修正推进示例库。此外，系统会自动收集那些匹配示例置信度偏低的生产查询，把它们路由给对应的领域专家做每日标注。下一次流水线运行时，Cohere Rerank 3.5 就会检索到这条新示例，那一类问题的准确率当场就提升，无需重新部署。

> 「标注界面是我们为长期质量做的最重要的一笔投入。它把 Discovery AI 从一个静态部署，变成一套活的系统——让我们的领域专家在日常工作流里持续打磨它。」
>         — Or Gabay，Orca Security AI 总监

再加上覆盖整条流水线的端到端可观测性，以及横跨产品、工程和面向客户团队的共享看板，正是这套反馈闭环让 Discovery AI 在首发之后仍能持续进步。

## 结果

Discovery AI 部署到生产后，在成本、延迟和准确率上都超过了最初的基线。输入 token 用量下降 93%，在可比较的工作负载上从约 200 万 token 降到 14 万。总体成本下降 90%，一方面靠的是 token 消耗降低，另一方面靠的是在 Amazon Bedrock 上按阶段分配模型。

延迟也改善了，端到端响应时间下降 75%，从约 60 秒降到 15 秒。复杂多模型查询的准确率同样提升，并通过团队的评估框架持续度量。

自 2026 年 3 月起，Discovery AI 已在生产环境中每天处理数千条查询，由内部领域专家和客户反馈共同验证质量。

## 结论

本文中，我们分享了 Orca Security 如何在 Amazon Bedrock 上构建 Discovery AI。相比最初的基线，这套方案将查询成本降低了 90%、输入 token 用量降低了 93%、延迟降低了 75%。方案结合了多项关键技术：用 Cohere Rerank 3.5 做基于 RAG 的示例检索、在 Anthropic Claude Haiku 4.5 和 Amazon Nova 2 Lite 之间按阶段分配模型、由 Amazon Titan 驱动的语义搜索。此外，一套持续的人在环（human-in-the-loop）标注体系提供源源不断的改进。这套组合让 Orca 把一个能跑的原型，变成了一套既更省钱又更准确的生产级方案。
