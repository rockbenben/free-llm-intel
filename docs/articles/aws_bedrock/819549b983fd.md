# SageMaker Inference 现在支持多实例 GPU，以最大限度地提高模型端点的 GPU 利用率

当您将模型部署到 GPU 端点时，您可以请求的最小 GPU 单元是整个加速器。

这种限制可能会让你付出双倍的代价。首先，一个实例上托管的模型数量不能超过其加速器数量。一台“ml.p4d.24xlarge”有八个 A100，因此它可以容纳八个型号，无论每个型号需要 40 GB 还是 14 GB。其次，不太明显的是，它使每次部署都归结为选择要部署到哪个完整 GPU。随着并发量和提示长度的增加，旧实例上的完整 GPU 不再足够，但较新实例上的完整 GPU 超出了您的模型可以使用的范围。您最终要么服务不足，要么为您从未达到的能力付费。

目前，Amazon SageMaker Inference 支持 GPU 分区，即使用 [NVIDIA 多实例 GPU](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/) (MIG) 将物理 GPU 划分为独立的分区。每个分区都接收固定份额的 GPU 计算单元和专用内存块，并在硬件中强制执行隔离。这改变了这两个限制：您可以在每个分区中放置不同的模型，并且可以选择较新加速器的一小部分而不是任一代的整个加速器。

这篇文章涵盖了两者。第一部分是直接好处：部署比 GPU 数量更多的模型，并且它们之间是隔离的。第二个问题是当问题转向成本时客户会问的一个问题：分区的粒度如何帮助您选择合适大小的单元，以及我们在这样做时测量了什么。

在进一步阅读之前需要了解一件事：GPU 分区适用于使用 [推理组件](https://aws.amazon.com/blogs/machine-learning/reduce-model-deployment-costs-by-50-on-average-using-sagemakers-latest-features/) 的端点，这是一种用于将多个模型部署到一个端点并设置每个模型获得的计算的构造。分区直接建立在它的基础上。分区是组件请求的资源，在同一位置它已经请求 CPU 和内存。如果您还没有使用过推理组件，这篇文章将介绍它们。单模型端点、无服务器端点和异构实例池无法分区。

## 客户今天做什么，以及为什么每个选项都达不到要求

如果您的模型多于加速器，那么您有三种选择。

**运行更少、更大的端点并更努力地进行批处理 – **这会提高利用率，但前提是模型可以互换。微调变体或每租户模型的组合则不然。

**使用多模型端点 –** 这些按需从共享 GPU 加载和卸载模型，适合稀疏、突发的流量。但模型共享设备而不进行隔离，因此对一种模型的大量请求会影响其他模型。未加载的模型在首次使用时也会付出负载惩罚。

**转向自我管理的 Kubernetes –** 这是需要真正 GPU 分区的客户已经离开的地方。 MIG 在那里工作，但您负责驱动程序版本控制、分区配置、设备插件、调度，并使其在整个队列中保持一致。对于您的实例已有的硬件功能来说，这是一项大量的工作。

## 为什么选择米格

NVIDIA 多实例 GPU (MIG) 将一个 GPU 拆分为多达七个实例，具体取决于 GPU。每个实例都有自己的计算、缓存、内存和内存带宽。由于分割是在硬件而不是软件中进行的，因此您可以获得其他共享方法无法提供的保证：

- **可预测的延迟 –** 每个分区都有专用的内存带宽，因此一种型号的流量峰值不会出现在另一种型号的 p99 中。
- **故障隔离 –** 崩溃或内存错误保留在其分区内，而不是取消 GPU 上的每个模型。
- **大小合适的容量 –** 中小型型号获得适合它们的切片而不是整个 GPU。您可以在一台设备上混合切片大小。
- **无冷启动 –** 每个模型都保留自己的分区并保持加载状态，没有负载惩罚，也没有驱逐。
- **租户隔离 –** 分区之间的内存保护在硬件中强制执行，这使得安全性和合规性审查更加简单。
- **可靠的规划和退款 –** 无论其邻居如何，分区都会以相同的方式执行，因此负载测试可以预测生产。 GPU 成本也清晰地映射到模型、团队或租户。

分区有值得预先了解的边界。分区的最大数量取决于加速器，并且永远不会超过七个。 MIG 本身仅允许在其分区空闲时更改布局，在 SageMaker AI 上，这意味着在创建终端节点时选择布局。需要多个 GPU 的模型仍然需要整个设备。在这些边界内，您可以隔离单独的 GPU，而无需为每个模型分配一个专用 GPU。

## 无需平台工作的分区

到目前为止，获取 MIG 意味着您自己运行 Kubernetes 堆栈。 Amazon SageMaker AI 上的 GPU 分区消除了该步骤：您为模型选择分区配置文件，SageMaker AI 处理 GPU 配置、放置和扩展。您可以在托管端点上获得硬件隔离的 GPU 共享，而无需在其下方运行平台。

## 它是如何工作的

GPU 分区向您已进行的 API 调用添加两个可选字段。没有新的 API 操作、没有新的资源类型、也没有新的 AWS Identity and Access Management (IAM) 操作，并且省略这两个字段的终端节点的行为与现在完全相同。

`AcceleratorPartitionLayouts` 在 `CreateEndpointConfig` 中进行了生产变体，并声明了每个加速器的划分方式：
```
{
  "EndpointConfigName": "multi-model-partitioned",
  "ExecutionRoleArn": "<execution-role-arn>",
  "ProductionVariants": [
    {
      "VariantName": "AllTraffic",
      "InstanceType": "ml.p4d.24xlarge",
      "InitialInstanceCount": 1,
      "AcceleratorPartitionLayouts": [
        { "AcceleratorPartitionTypes": ["mig-4g.20gb", "mig-2g.10gb", "mig-1g.5gb"] }
      ]
    }
  ]
}
```
A100 有七个计算切片可供划分。前面的布局使用全部七个，因此 p4d 实例上的八个 A100 中的每一个都承载三个分区，并且端点提供 24 个分区，每种类型八个。

雕刻统一适用。一个布局条目描述了如何划分一个加速器，并且变体中每个实例上的每个加速器都以相同的方式划分。该列表不是位置性的，因此条目不会映射到特定的 GPU。

`AcceleratorPartitionType` 继续推理组件并选择模型在哪个分区上运行：
```
{
  "InferenceComponentName": "summarizer",
  "EndpointName": "multi-model-partitioned",
  "VariantName": "AllTraffic",
  "Specification": {
    "ModelName": "summarizer-model",
    "ComputeResourceRequirements": {
      "AcceleratorPartitionType": "mig-4g.20gb",
      "NumberOfAcceleratorDevicesRequired": 1,
      "NumberOfCpuCoresRequired": 1,
      "MinMemoryRequiredInMb": 2048
    }
  },
  "RuntimeConfig": { "CopyCount": 1 }
}
```
每个组件副本占用所请求类型的一个分区。对于实例上每种类型有八个分区，提高“CopyCount”会在空闲分区上放置额外的副本。这对于服务高并发的小型模型非常有用，其中单个进程让 GPU 等待请求。

这里“NumberOfAcceleratorDevicesRequired”始终为 1。设置分区类型意味着一个分区而不是一个加速器。 `NumberOfCpuCoresRequired` 和 `MinMemoryRequiredInMb` 仍然描述主机 CPU 和主机内存，因为 GPU 内存来自分区类型。

调用不会改变。 `InvokeEndpoint` 通过推理组件名称来寻址模型，并且它占用的分区永远不会出现在请求中。

分区在配置端点时发生。当它到达“InService”时，每个加速器都会被雕刻并且分区是空的，这是一个有效的状态，因为组件随后会降落在它们上。在我们的测试中，雕刻加速器的配置时间增加了大约 17 秒。剩下的时间就是通常的实例启动和容器拉取。

## 按 GPU 划分配置文件

您可用的配置文件是 GPU 的一个属性，因此首先要找出您的实例类型搭载的 GPU，并在 [NVIDIA 支持的 MIG 配置文件](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/latest/supported-mig-profiles.html) 中查找，这是完整配置文件集和在一台设备上有效的组合的权威。

| **实例家族** | **加速器** | **GPU内存** | **粒度（计算/内存）** | **可用的分区配置文件** | **每个 GPU 的最大分区** |
| --- | --- | --- | --- | --- | --- |
| P4d | P4d |英伟达 A100 | 40GB| 7 / 8 | mig-1g.5gb、mig-1g.10gb *（请参阅驱动程序说明）*、mig-2g.10gb、mig-3g.20gb、mig-4g.20gb、mig-7g.40gb | 7 |
| P5|英伟达 H100 | 80GB| 7 / 8 | mig-1g.10gb、mig-1g.20gb、mig-2g.20gb、mig-3g.40gb、mig-4g.40gb、mig-7g.80gb | 7 |
| G7 | NVIDIA RTX PRO 4500 布莱克韦尔 | 32GB| 2 / 2 | 2 mig-1g.16gb、mig-2g.32gb | 2 |
| G7e | NVIDIA RTX PRO 6000 Blackwell 服务器版 | 96GB | 4 / 4 | mig-1g.24gb、mig-2g.48gb、mig-4g.96gb | 4 |

将配置文件名称读取为计算单元，后跟 GPU 内存：“mig-3g.40gb”需要三个计算单元和 40 GB。粒度列限制了布局。 A100 和 H100 在计算上分为七分之一，在内存上分为八分之一，而 G7 分为两半，G7e 分为四分之一。即使切片计数匹配，GPU 之间的配置文件名称也会有所不同，因此，在未对照此表进行检查的情况下，请勿将布局从一个实例系列转移到另一个实例系列。

在这些限制内，你有真正的选择。在 P4d 或 P5 上，您可以雕刻七个最小的配置文件，或两个 3g 分区，或前面示例中使用的 4g 加 2g 加 1g 布局，或将整个设备作为一个整体。在 G7e 上，您可以携带四个最小的设备，或者两个 1g 设备和一个 2g 设备，或者两个 2g 设备，或者整个设备。在 G7 上，可以是两个分区，也可以是一个分区。

3g 配置文件是需要了解的一个，因为它的两个维度不匹配：它需要七个计算单元中的三个，但需要八个内存单元中的四个。其中两个填满了 GPU，除了它们之外没有其他东西可以容纳。

**高级规则：** 布局中的每个配置文件都必须是您的 GPU 提供的配置文件，并且您的配置文件添加的计算和内存单元不得超过一台设备提供的计算和内存单元。创建端点配置时都会检查两者，其中任何一个失败都是拒绝，而不是回退到整个加速器。

**P4d 驱动程序说明：** mig-1g.10gb 需要 R525 或更新的 NVIDIA 驱动程序，默认 P4d 映像附带 470.256.02。在默认图像上请求它，并且雕刻失败，并且命名配置文件时出现错误。在生产变体上将“InferenceAmiVersion”设置为“al2023-ami-sagemaker-inference-gpu-4-1”，以获取提供该功能的 580 驱动程序系列上的图像。

## 选择适合您的工作负载的布局

选择好的布局与选择仅仅被接受的布局是不同的问题。分区以固定比例为您提供计算和内存，并且两者在推理过程中执行不同的工作。

**计算单元是预填充所需的。**预填充读取提示并构建其表示。这是计算密集型阶段，它会随着流式多处理器的扩展而扩展，因此您的分区可以容纳 TFLOP。您的输入越长，同时到达的提示越多，它就越能控制您返回第一个令牌的速度。

**内存单元是解码和容量所需的。**生成令牌会在每一步重新读取模型权重，因此解码受内存带宽而不是数学的限制，并且内存还限制了您可以容纳的 KV 缓存量。该上限又设置了您可以服务的上下文长度以及您可以同时服务的序列数。

**几乎没有真正的工作负载只执行其中一个，因此目标不是选择一个维度，而是选择一个支持您的用例的组合。**选择一个配置文件，其比例覆盖您最繁重的阶段，同时让其他阶段得到充分服务。在计算方面，重要的是提示的长度以及一次到达的数量。在内存方面，它是你的输出长度、你的上下文窗口和你的并发性。

两者中内存是更容易被低估的一个，因为分区必须保存三件事，而不仅仅是模型：权重，对于 FP16 的 8B 模型来说，权重约为 16 GB。 KV 缓存，根据上下文长度和您打算允许的并发序列数量确定大小，这是人们遗漏的术语，并且随着流量而增长。 CUDA 上下文和服务进程需要 1-2 GB 的运行时开销。在选择配置文件之前将它们添加起来，因为仅根据权重调整大小的分区将加载模型，然后在负载下失败，或者悄悄地提供比您配置的短得多的上下文。作为具体参考点，FP16 上的相同 8B 模型可以轻松地在 40 GB 分区上提供 8,000 个令牌的上下文。

## MIG 增加最大价值的地方

**中小型型号组合 –** 直接案例。经过微调的变体、嵌入模型、重新排序器和分类器，每个加速器的大部分都未使用，现在共享一个。

**多租户模型服务 –** 当您为每个客户托管一个模型时，MIG 会在它们之间提供硬件边界：一个分区中的进程无法读取另一个分区的内存或获取其吞吐量。不过，准确地界定索赔范围。同一实例上的模型仍然共享主机 CPU、系统内存、存储、网络和端点路由，因此分区是 GPU 的隔离机制，而不是完整的租赁边界。

**一个实例上的多级管道 –** 转录模型、二值化模型和语言模型，或嵌入器、重排序器和生成器。每个阶段都是其自己分区上的可单独寻址的组件，并且阶段之间的网络跃点消失。

**请求路径中的小模型 –** 安全分类器或护栏模型，必须针对每个请求运行，但不能证明加速器的合理性，具有可预测的延迟，因为它不是针对主模型的时间切片。

**挑战者和金丝雀 –** 在服务生产流量的模型旁边的一个小分区上运行候选模型，而不是建立第二个端点。

## 性能：较新 GPU 的一部分与整个较旧 GPU 的对比

除了装箱之外，您获得的另一个好处是高端 GPU 的粒度：有更多用于部署模型的 GPU 选项，以及您可以选择哪个。每个受支持的加速器都会有多种尺寸，而不是一种尺寸，因此考虑的实际方法是，每个配置文件本身就是一个 GPU 选项，与您已经选择的整个加速器并存。当您考虑更大或更新的实例类型时，这一点最为重要，因为升级不再是全有或全无的情况：您可以根据工作负载的需要，以它发布的任何大小使用更大或更少的更大 GPU，而不是为整个加速器付费。

为了看看这是否有效，我们将 H100 的一个“mig-3g.40gb”分区与整个未雕刻的 A100-40GB 分区进行了比较。两者具有相当的 GPU 内存，这使得它能够以一种清晰的方式来了解更高级实例的一部分有多强大。

我们使用 [genai-bench](https://github.com/sgl-project/genai-bench) 生成负载，从同一客户端驱动两个端点，因此 GPU 是唯一的变量。双方都在生产 SageMaker 实时端点上运行 Llama-3.1-8B-Instruct，各一个模型副本，具有相同的容器映像、标记生成器和客户端配置。两者都是通过 SageMaker AI 原生 OpenAI 兼容路径调用。我们扫描了五种流量形状，写为 D（输入标记，输出标记），范围从短提示到长上下文摘要，每种流量形状都跨越从 2 到 512 的并发阶梯。

有四件事很突出。

- **分区在任何地方都更快 –** 它在每种并发情况下的每种场景中每秒交付更多的输出令牌，在每种场景的成本效益最大的负载下，输出令牌增加了 53% 到 89%，并且每种场景中的令牌间延迟也降低了 8.9% 到 42.1%。间隙随着负载而变宽。
- **在每种情况下，获得第一个令牌的时间都会缩短，从 5.6% 到 47.5%。**
- **就成本而言，每百万输出代币便宜 18-34%，高于随着提示延长而提前移动的交叉。** 100 个代币提示的并发性为 64，8,000 个代币提示的并发性为 4。在分频器之下，整个 A100 是更便宜的单元。这些价格都是按需的，在分析时，在美国西部（俄勒冈）AWS 区域，“ml.p4d.24xlarge”的价格为 25.251286 美元/小时，“ml.p5.48xlarge”的价格为 63.296000 美元/小时。纯粹为了我们自己的分析，我们通过将整个实例成本除以其上的单元数量来得出单位成本：p4d 上为 8，p5 上为 16，其中我们的分区是 GPU 的一半。
- **在长上下文流量的阶梯顶部，A100 停止了服务。** 在 6,000 个和 8,000 个令牌的工作负载上，它在服务路径截止日期内失败了三分之一到一半的请求，而分区则没有失败。这就是为什么这两个小组比其他小组结束得早。

**将此视为个案比较，而不是结论。** 有用的心智模型是将可用的 GPU 分数视为其本身的 GPU 类型。将它们与整个加速器一起列出，计算出您的流量对计算和内存的实际需求，并将它们与您自己的工作负载进行比较。对于高并发、长输入流量，分区在性能和成本上都获胜。对于短输入或低并发工作负载，整个 A100 仍然更便宜。分区并不是一刀切的解决方案。它为您提供了更多尺寸可供选择，因此您可以选择适合您工作负载的一款。

## 在进行布局之前需要了解什么

分区会改变端点的形状，在设计端点之前，有一些属性值得了解。

组件的分区类型在该组件的生命周期内是固定的。将模型移动到不同的配置文件意味着创建一个新组件。更改端点的雕刻意味着新的端点和流量迁移，因为更新端点配置不会重新雕刻已经运行的主机。这使得分区非常适合稳定的投资组合，但不适合每天重新调整的组合。

请求的配置文件必须存在于端点的布局中。整个加速器没有后备方案，因此请求变体未声明的配置文件的组件会被拒绝。

分区适用于推理组件端点上的实时推理。不支持无服务器端点和异构实例池，并且异步调用无法解决推理组件，因此异步工作负载超出了范围。

就像今天一样，您需要为完整的 GPU 实例付费。分区提高了您可以使用该实例的数量。它不会改变每小时的价格。

最后，真正需要完整加速器或多个加速器的模型应该继续拥有一个。没有分区跨越加速器。

## 支持的实例和区域

GPU 分区适用于 P4d、P5、G7 和 G7e 实例系列。支持是在家庭层面上进行的，因此可以覆盖家庭中较小的规模。

它已在以下 AWS 区域推出：美国东部（弗吉尼亚北部）、美国东部（俄亥俄）、美国西部（俄勒冈）、亚太地区（新加坡）、亚太地区（东京）、欧洲（法兰克福）和欧洲（爱尔兰）。

实例可用性因区域而异，因此请确认您选择的实例类型在您的区域中提供，并且您有该实例的终端节点使用配额。

## 开始使用

要对 GPU 端点进行分区，请计算出内存并计算每个模型的需求，选择适合的配置文件，在端点配置上声明布局，并将每个模型部署为从该布局请求配置文件的推理组件。关于调用模型的方式没有任何改变。

有关 API 参考、每个实例系列的完整配置文件表以及分步演练，请参阅 Amazon SageMaker AI 开发人员指南中的 [GPU 分区](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-components-accelerator-partitioning.html)。

要亲自尝试，请运行 [GPU 分区示例笔记本](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/03-features/GPU-partitions)，它将多个模型部署到单个 GPU 端点的分区上。

在规划容量时，值得牢记更广泛的变化。现在，每个受支持的加速器都有多种尺寸，而不是一种。较新 GPU 的分区或较旧 GPU 的整个加速器是否是给定模型的正确单元，不再是您需要通过四舍五入来回答的问题。这是你可以衡量的。
