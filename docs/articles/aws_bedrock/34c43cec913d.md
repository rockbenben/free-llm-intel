Quick Apps 此前已能从连接器和内容源把实时数据带入一个应用：动作连接器（如 Jira、Slack 和 Google Drive 这类服务）、Spaces 文档、网络搜索和 AI 推理都在查看（view）时而非构建时运行。这一方案引入了来自你数据湖、数据库和其他分析数据存储的*实时结构化数据*。

你受治理的 Amazon Quick Sight 数据集——那些保存你业务指标的 SPICE 和 Direct Query 表——无法从一个应用被实时查询。应用所展示的任何数据集数字，都是在智能体构建它时烤进去的。一个在发布时被冻结的快照。

这对一个静态报告没问题，但一旦你想要一个指标反映你数据今天状态、并尊重谁被允许看哪些行的应用时，它就失效了。

Amazon Quick 是一个 AI 驱动的统一智能服务，它连接所有受治理的企业数据和企业内容，让团队可以在一处探索、分析和行动。借助 Quick Apps，你可以用大白话描述一个应用，让一个 AI 智能体编写并部署一个可用的 Web 应用，而无需动手编码或 DevOps 步骤。

在本文中，我们介绍 *Live Data in Apps*，AI 构建的 Amazon Quick 应用可以用它实时查询受治理的 Quick Sight 数据集，而非依赖静态的、构建时的快照。我们逐步讲解如何用自然语言 prompt 构建、发布并分享一个实时数据应用，并涵盖关键考量、同意要求和查询护栏。

## 新增内容：Live Data in Apps

有了 *Live Data in Apps*，一个已发布的 Quick 应用在每次用户打开它时都实时查询你受治理的 Quick Sight 数据集。假设你的支持团队一直在问：“我们上周关闭了多少工单，按区域分解？”如今某人打开数据、写查询、导出一个图表、并把它粘贴到 Slack。每周都如此。你真正想要的是一个团队里任何人都能打开、得到今天答案、而不碰 SQL 的应用。

你现在可以用自然语言描述你想要的应用。智能体自行找到相关的策展数据集，然后在构建应用时编写回答你问题所需的 SQL。应用发布后，它在每次有人打开时重新运行同一段 SQL，因此数字始终是最新的。而关键在于，查询是以查看它的那个人身份执行的。结果是每个用户恰好看到他们被允许看的数据。

借着这次上线，我们把受治理的结构化数据集从 Quick 带入应用。

## 面向谁以及为何重要

Live Data in Apps 通过应对组织中不同角色的多重关切来扩展应用的实用性，下表列出这些角色。

| 受众 | 收益 |
| --- | --- |
| 业务运营负责人 | 用自然语言在实时数据集之上构建应用。无需手动数据刷新、无需快照管理、无需定制 API 管道。 |
| 知识工作者（用户） | 打开一个应用并看到你的数字。截至当下的最新，并过滤到你被允许看的内容。 |
| 数据与应用管理员 | 现有的行级安全（RLS）和列级安全（CLS）规则自动适用。无需学习新的权限模型。同意在每次查询上于服务器端强制执行。 |

## 前提条件

开始前，确认你具备以下内容：

- 访问已经[创建](https://docs.aws.amazon.com/quick/latest/userguide/creating-data-sets.html)、带或不带[行级安全（RLS）和列级安全（CLS）](https://docs.aws.amazon.com/quick/latest/userguide/restrict-access-to-a-data-set-using-row-level-security.html#apply-row-level-security)的数据集。
- 受支持的数据集模式：SPICE（内存）和 Direct Query 数据集都受支持。Direct Query 支持的数据源列表见文档。
- 同意：每个查看者必须为首次使用逐数据集同意。构建者在构建流程中批准数据集。
- 认证：查看者必须是经认证的 Quick 用户。使用实时数据集的应用不支持匿名或公共访问。这在多层上强制执行。

## 用例

在 Amazon Quick 中，Live Data in Apps 建立在两条流程之上，其余一切都建立在它们之上。有两个角色贯穿始终：*builder*（其智能体构建应用的 user）和 *users*（之后打开已发布应用的任何人）。成为 builder 或 user 所需的最低角色是 Reader Pro（Professional）。

AnyCompany 为其客户提供一套软件即服务（SaaS）应用，而区域销售负责人的一项常见任务是审阅交易续约并采取措施。要让这一工作流奏效，企业战略内容和企业收入数据需要汇聚到一起，还需要构建一个联系客户的工作流。这通常需要一个月的工作量来确保为每个客户拉取正确的数据。借助 Amazon Quick 中新的 live data in apps 功能，一位销售负责人可以从他们已经有权访问的一个数据集构建它，并分享给其他销售负责人而无需等待 IT。Amazon Quick 应用和数据住在被设计为安全的 AWS 基础设施中，带客户的行级和列级安全。

## 需要知道的事

以下是使用 Live Data in Apps 时一些重要的考量：

- 因为查询实时运行，应用始终显示数据集中最新的数据。如果数据集用 SPICE，[刷新数据集](https://docs.aws.amazon.com/quick/latest/userguide/refreshing-imported-data.html)会更新应用中显示的数据。如果数据集用 Direct Query，无需刷新。
- 查询和结果大小护栏已就位。如果一个查询返回的数据超过传输所能承载，应用会呈现一条清晰的“缩小查询”消息，而非交付截断或不完整的数据。修改 prompt 以获得聚合数据，或让它实现分页。
- 与 spaces 和连接器类似，你必须给 Quick 一次性同意，代表你在应用中使用特定数据集。
- 来自同一数据源的 SPICE 数据集或 Direct Query 数据集可以在单个应用中使用。来自不同数据源的 Direct Query 数据集不能在同一应用中使用。更多信息见[应用中支持 Direct Query 的数据源](https://docs.aws.amazon.com/quick/latest/userguide/apps-limitations.html)。
- 重命名或移除列需要在应用中重建查询。用更新后的信息编辑应用。
- 构建者有行数限制。在构建和行检索流程期间，数据检索有一个初始行限制。你必须观察这一限制，并建议构建智能体在加载时通过多次分页调用数据集来检索应用中的所有数据。更多细节见[文档](https://docs.aws.amazon.com/quick/latest/userguide/apps-limitations.html)。
- 在数据集发现期间，智能体从你的数据拉入相关的列。如果它漏了一列，你可以在应用 prompt 中直接指定它。
- 应用基于它最初收到的数据来理解数据集列。如果构建者的行级安全（RLS）没有返回数据，应用无法用那个数据集构建。与应用所有者或你的安全团队协作以获得数据集的行级访问。
- 如果智能体没有发现你想要的数据集，缩小你的搜索，或提供数据集名称或 ID 以浮现正确结果。

## 开始上手

这里是你今天如何开始构建并分享实时数据应用。

- **立即试用：** 打开 [Amazon Quick Apps](https://docs.aws.amazon.com/quick/latest/userguide/using-amazon-quick-apps.html)，在一个你受治理的 Quick Sight 数据集之上构建一个应用。用大白话描述你想要的，让智能体处理 SQL。
- **阅读文档：** 访问 [Amazon Quick 文档](https://docs.aws.amazon.com/quick/) 获取 Live Data in Apps 的详细设置指南、API 参考和最佳实践。
- **分享反馈：** 我们想听听 Live Data in Apps 对你团队如何运作。使用产品内反馈机制或联系你的 AWS 团队。

## 结论

有了 Live Data in Apps，一个 AI 构建的 Quick 应用可以服务实时的、受治理的数据，而非一个构建时的快照。智能体在构建应用时对你 Quick Sight 数据集发现并验证 SQL。已发布的应用为每个读者重新运行那段 SQL，以那个读者身份执行，于是 RLS 和 CLS 逐人适用。在一道逐读者同意门之后，后端在每次查询上重新验证。

数据权威保持在一处。Quick Sight 查询引擎针对每个查看者的身份强制执行授权，于是应用、前端和代理从不处理访问决定。

要开始上手，在你受治理的数据集之上构建一个 Quick 应用，让读者以他们自己的权限适用来探索实时数据。关于 Quick Apps 和数据集集成，参见 [Amazon Quick 文档](https://docs.aws.amazon.com/quick/)。
