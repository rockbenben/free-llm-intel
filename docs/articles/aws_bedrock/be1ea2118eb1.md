# 加速创新：BMW 用于云事件分析的生成式 AI 解决方案

*本文由 BMW Group 的 Johann Wildgruber、Dr. Jens Kohl、Thilo Bindel 和 Luisa-Sophie Gloger 共同撰写。*

[BMW Group](https://www.bmwgroup.com/)总部位于德国慕尼黑，是一家拥有超过 154,000 名员工的汽车制造商，在全球拥有 30 个生产与装配工厂，并在 17 个国家设有研发机构。今天，BMW Group（BMW）是全球领先的高档汽车与摩托车制造商，也是高档金融与出行服务的提供商。

[BMW Connected Company](https://www.bmwusa.com/explore/connecteddrive.html) 是 BMW 内部的一个部门，负责为 BMW 的联网车队开发和运营高档数字服务，该车队目前在全球拥有超过 2,300 万辆车。许多 BMW 车主每天都在使用这些数字服务；例如，用手机上的应用远程锁闭或开启车门、远程启动车窗除霜、从车内菜单购买导航地图更新，或者在车内收听通过互联网串流播放的音乐。

本文介绍 BMW 如何在 AWS 上使用生成式 AI 技术，帮助以高可用方式运行这些数字服务。具体而言，BMW 使用 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 加快修复（部分）服务中断的速度：它加速了原本繁琐耗时的根本原因分析（RCA）过程。全自动的 RCA agent 在大多数情况下都能正确识别出真正的根本原因（实测为 85%），并在具体案例中帮助工程师理解系统、获得实时洞察。这一表现在概念验证期间得到了进一步验证：在代表性用例上使用 RCA agent 清楚展示了该解决方案的价值，使 BMW 显著缩短了诊断时间。

## 根本原因分析的挑战

数字服务通常通过把多个软件组件串联起来实现，而这些组件可能由不同团队构建和运行。以远程开启和锁闭车门这项服务为例：可能有一个开发团队负责构建和运行 iOS 应用，另一个团队负责 Android 应用，还有一个团队负责构建和运行 iOS 与 Android 应用共用的 backend-for-frontend，等等。此外，这些团队可能在地理上分散，并在不同位置和区域运行各自的工作负载；许多托管在 AWS 上，也有的在别处。

现在设想一个（虚构的）场景：车主们纷纷投诉，用应用远程锁车不再有效。是 iOS 应用导致的中断，还是 backend-for-frontend？是某处的防火墙规则改了？还是内部 TLS 证书过期了？MQTT 系统是否出现了延迟？最近的 API 变更中是否有不经意的破坏性变更？他们到底是在什么时候部署的？又或者中央订阅服务的数据库密码又被轮换了？

在这种情况下，确定问题的根本原因可能很困难。它需要检查许多系统和团队，其中许多可能因为相互依赖而同时出故障。开发者需要对系统架构进行推理、提出假设，并沿着组件链一路追查，直到定位到罪魁祸首。他们常常不得不回退、重新评估假设，再沿着另一条组件链继续调查。

理解了这类复杂系统中的挑战，就能看出我们需要一种稳健且高效的根本原因分析方法。基于这一背景，我们来看看 BMW 与 AWS 如何合作开发出一个使用 Amazon Bedrock Agents 的解决方案，以精简并增强 RCA 流程。

## 解决方案概览

从高层看，该解决方案使用一个 Amazon Bedrock agent 执行自动化 RCA。这个 agent 有一些自建工具可供使用。这些工具由 [AWS Lambda](https://aws.amazon.com/lambda/) 函数实现，利用 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 和 [AWS CloudTrail](https://aws.amazon.com/cloudtrail/) 等服务来分析系统日志和指标。下图展示了该解决方案的架构。

![High level diagram of the solution](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/02/25/ML-17213-Image-001-Architecture.png)

发生事件时，值班工程师把当前问题的描述交给 Amazon Bedrock agent。随后，agent 会利用自己的工具开始调查问题的根本原因，完成那些原本需要值班工程师手动执行的任务，例如搜索日志。根据发现的线索，agent 会向值班工程师提出若干可能的假设。工程师可以据此解决问题，或给 agent 一些提示，以引导调查进一步深入。下一节我们将详细介绍该 agent 使用的工具。

## Amazon Bedrock agent 工具

Amazon Bedrock agent 执行 RCA 的高效性，源于它能与自定义工具无缝集成。这些工具被设计为 Lambda 函数，利用 CloudWatch 和 CloudTrail 等 AWS 服务来自动化那些通常需要工程师手动完成、耗时较长的任务。通过把能力组织为专用工具，Amazon Bedrock agent 确保 RCA 既高效又精准。

### Architecture Tool

Architecture Tool 使用 [C4 diagram](https://c4model.com/) 提供系统架构的全面视图。这些 diagram 通过 [Structurizr](https://structurizr.com/) 增强，让 agent 对组件关系、依赖和 workflow 形成分层理解。这使得 agent 在 RCA 过程中能够聚焦最相关的区域，根据不同系统的交互方式有效缩小潜在故障原因的范围。

例如，如果某个问题影响了特定服务，Architecture Tool 可以识别上游或下游依赖，并提出聚焦于这些系统的假设。这让 agent 能够结合架构上下文进行推理，而不是盲目搜索日志或指标，从而加速诊断。

### Logs Tool

Logs Tool 使用 CloudWatch Logs Insights 实时分析日志数据。它通过搜索模式、错误或异常，并与上一时段的趋势做对比，帮助 agent 定位与特定事件相关的问题，例如认证失败或系统崩溃。

例如，在涉及数据库访问失败的场景中，Logs Tool 可能发现“FATAL: password authentication failed”这类错误消息的数量相比前一小时出现了新的激增。这一洞察让 agent 能把故障与潜在根本原因（例如数据库密码轮换不当）快速关联起来。

### Metrics Tool

Metrics Tool 通过 CloudWatch 监控关键指标，为 agent 提供系统健康状况的实时洞察。该工具能识别延迟、错误率、资源利用率等关键性能指标中的统计异常，或使用模式中的异常峰值——这些往往预示着潜在问题或偏离正常行为。

例如，在 Kubernetes 内存过载的场景中，Metrics Tool 可能检测到故障发生前内存消耗的急剧上升或异常的资源分配。通过呈现针对此类异常的 CloudWatch 指标告警，该工具让 agent 能优先考虑与资源管理不当、阈值配置错误或意外系统负载相关的假设，更有效地引导调查走向问题解决。

### Infrastructure Tool

Infrastructure Tool 使用 CloudTrail 数据分析关键的控制平面事件，例如配置变更、安全组更新或 API 调用。该工具在识别可能引发级联故障的错误配置或破坏性变更方面尤其有效。

设想一个安全组入站规则被无意移除、导致服务之间出现连接问题的案例。Infrastructure Tool 可以检测到这一事件，并将其与上报的事件关联起来，为 agent 提供可操作的洞察，以引导其 RCA 过程。

通过组合这些工具，Amazon Bedrock agent 在机器速度执行任务的同时，模仿了经验丰富的工程师的逐步推理过程。这些工具的模块化特性带来了灵活性与可定制性，确保 RCA 能够贴合 BMW 复杂、多区域云基础设施的独特需求。

下一节我们讨论这些工具如何在 agent 的 workflow 中协同工作。

## Amazon Bedrock agent：ReAct 框架的实践

BMW 快速 RCA 的核心是 [ReAct](https://arxiv.org/abs/2210.03629)（Reasoning and Action）agent 框架，这是一种把逻辑推理与任务执行动态结合的创新方法。通过把 ReAct 与 Amazon Bedrock 集成，BMW 获得了一个用于诊断和解决复杂云上事件的灵活解决方案。与依赖预定义 workflow 的传统方法不同，ReAct agent 使用实时输入和迭代式决策，以适应事件的具体情况。

BMW RCA 解决方案中的 ReAct agent 使用一种结构化又具自适应性的 workflow 来诊断和解决问题。首先，它解读事件的文字描述（例如“车辆无法通过应用上锁”），以确定系统中最可能受影响的部分。在 ReAct 框架迭代式推理的引导下，agent 随后调用专用工具收集证据，所用数据集中汇聚在[跨账户可观测性设置](https://aws.amazon.com/blogs/aws/new-amazon-cloudwatch-cross-account-observability/)中。通过持续重新评估每次工具调用的结果，agent 逐步缩小潜在原因——无论是证书过期、防火墙规则被撤销，还是流量激增——直到隔离出根本原因。下图展示了这一 workflow。

ReAct 框架带来以下好处：

- **动态且自适应** —— ReAct agent 针对具体事件调整方法，而非采用一刀切的方式。这种适应性在 BMW 多区域、多服务的架构中尤为关键。
- **高效的工具利用** —— 通过对调用哪些工具、何时调用进行推理，ReAct agent 将冗余查询降到最少，在不过载 CloudWatch 或 CloudTrail 等 AWS 服务的前提下提供更快的诊断。
- **类人的推理** —— ReAct agent 模仿资深工程师的逻辑思考过程，迭代式地探索假设，直到识别出根本原因。这种能力弥合了自动化与人类专业知识之间的差距。

通过采用 Amazon Bedrock ReAct agent，诊断时间显著缩短。这些 agent 不仅提升了运营效率，还让工程师能够专注于战略性改进，而不是耗费大量人力的诊断工作。

## 案例研究：根本原因分析“通过 iOS 应用解锁车辆”

为了说明 Amazon Bedrock agent 在实践中的威力，我们来看一个可能的真实场景，它涉及 BMW 联网车队与运行在云后端的数字服务之间的相互作用。

我们在测试环境中故意修改中央网络账户的安全组。其结果是来自车队的请求被（正确地）被修改后的安全组阻止，无法到达后端托管的服务。因此，一位测试用户无法远程锁闭或解锁她的车门。

### 事件详情

BMW 工程师收到一位测试人员的报告，指出移动应用上的远程锁闭/解锁功能无法使用。

这份报告立刻引出一系列问题：问题出在应用本身，还是 backend-for-frontend 服务，抑或是系统更深层的地方，例如 MQTT 连接或认证机制？

### ReAct agent 如何应对该问题

问题被描述给 Amazon Bedrock ReAct agent：“iOS 应用的用户无法远程解锁车门。”agent 立即开始分析：

- agent 首先调用 Architecture Tool 了解整体系统架构。Architecture Tool 的输出显示，iOS 应用与 Android 应用一样，连接到一个 backend-for-frontend API，而该 backend-for-frontend API 本身又连接到若干其他内部 API，例如 Remote Vehicle Management API。Remote Vehicle Management API 负责通过 MQTT 消息向车辆发送指令。
- agent 有针对性地使用其他可用工具：只扫描与远程解锁车门相关组件的日志、指标和控制平面活动，例如 iOS 应用的远程日志、backend-for-frontend API 日志等。agent 发现了几条线索：表明存在连接问题的异常日志（网络超时）；Remote Vehicle Management API 成功调用次数急剧下降；控制平面活动：测试环境中中央网络账户的多个安全组被修改。
- 基于这些发现，agent 推断并定义出若干假设，并按可能性高低呈现给用户。在本例中，第一个假设就是真正的根本原因：中央网络账户中的某个安全组被无意修改，导致 backend-for-frontend 与 Remote Vehicle Management API 之间的网络流量现在被阻止。agent 正确地关联了日志（“fetch timeout error”）、指标（调用次数下降）与控制平面变更（安全组入站规则被移除），从而得出这一结论。
- 如果值班工程师想了解更多信息，现在可以向 agent 追问，或指示 agent 也去其他地方调查。

整个过程——从事件检测到解决——只花了几分钟，而用传统 RCA 方法可能要花上数小时。ReAct agent 动态推理、访问跨账户可观测性数据并对假设不断迭代的能力，免去了繁琐的人工排查。

## 结语

通过使用 Amazon Bedrock ReAct agent，BMW 展示了如何改进其根本原因分析方法，把复杂的手工流程转变为高效的自动化 workflow。集成在 ReAct 框架中的工具显著缩小了潜在的推理空间，并实现了动态假设生成与针对性诊断，在机器速度运行的同时模仿资深工程师的推理过程。这一创新缩短了识别和解决服务中断所需的时间，进一步提升了 BMW 联网服务的可靠性，也改善了全球数百万客户的体验。

该解决方案已取得可量化的成效：agent 在 85% 的测试用例中识别出了根本原因，并在其余用例中提供了详细洞察，大大加快了工程师的调查。它还降低了初级工程师的上手门槛，让经验较少的团队成员也能有效诊断问题，从而在 BMW 的各项运营中保持可靠性与可扩展性。

把生成式 AI 纳入 RCA 流程，展现了 AI 在现代云上运营中的变革潜力。动态适应、结合上下文推理以及处理复杂多区域基础设施的能力，使 Amazon Bedrock Agents 成为希望让数字服务保持高可用的组织的颠覆性工具。

随着 BMW 持续扩展其联网车队和数字产品，采用 Amazon Bedrock 这类生成式 AI 驱动的解决方案，将在保持运营卓越和为客户提供无缝体验方面发挥重要作用。效仿 BMW 的做法，你的组织同样可以借助 Amazon Bedrock Agents 进行根本原因分析，以提升服务可靠性。

你可以从探索 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 开始，以优化事件诊断；也可以使用 [CloudWatch Logs Insights](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/AnalyzingLogData.html) 识别系统日志中的异常。如果你想动手学习如何创建自己的 Amazon Bedrock agent（含代码示例和最佳实践），请查看以下 [GitHub 仓库](https://github.com/awslabs/amazon-bedrock-agent-samples/)。这些工具正在为高效 RCA 与运营卓越树立新的行业标准。
