# 控制 AI agent 可以访问的域名

能够浏览 Web 的 AI agent 开启了强大的可能性——从研究自动化到实时数据收集。然而，让 AI agent 无限制地访问互联网会带来安全与合规问题。如果 agent 访问了未经授权的网站怎么办？如果敏感数据被外泄到外部域名怎么办？

[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 提供托管工具，使 AI agent 能够与 Web 交互（Browser）、执行代码（Code Interpreter）以及托管 agent（Runtime）。当部署在 Amazon Virtual Private Cloud（Amazon VPC）中时，你可以使用 AWS Network Firewall 控制工具的网络访问，实现基于域名的过滤。AWS Network Firewall 还提供托管规则，帮助减少访问僵尸网络、已知恶意软件域名及其他高风险资源。

本文介绍如何配置 [AWS Network Firewall](https://aws.amazon.com/network-firewall/) 将 AgentCore 资源限制在经批准的互联网域名白名单内。你可以使用该架构来：

- 仅允许访问指定域名（例如 wikipedia.org、stackoverflow.com）
- 使用规则模板显式屏蔽某些类别（例如社交媒体网站）
- 记录连接尝试，以支持审计和合规
- 对未指定的域名实施默认拒绝策略

本文重点介绍使用 SNI 检查进行域名级过滤——这是纵深防御方案的第一层。关于 DNS 级过滤和内容检查技术，请参阅本文末尾的 **Going further**。关于入站访问控制（限制谁可以调用你的 agent），还可以参阅 [Amazon Bedrock AgentCore 的基于资源的策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/resource-based-policies.html)。这些策略支持 `aws:SourceIp`、`aws:SourceVpc` 和 `aws:SourceVpce` 等条件。这些控制手段在纵深防御策略中是相互补充的层次。

## **为何重要：企业安全要求**

在受监管行业部署 AI agent 的客户，在网络入站和出站控制方面有着一致的安全要求：

**安全要求较高的企业组织**

受监管行业的客户在对 AI agent 部署进行安全审查时，总会问到网络隔离和出站控制，要求详细说明 agent 流量如何被控制和审计。这些客户希望确认 agent runtime endpoint 保持私有，并且可以使用 Web 应用防火墙保护等额外安全控制。

**多租户 SaaS 提供商**

企业级软件即服务（SaaS）提供商需要 DNS 级的 `allowlisting` 和 `denylisting`，因为它们的多租户架构需要针对每个客户的网络策略。例如，客户 A 可能需要放行客户 B 屏蔽的域名。常见要求包括：

- 按执行过程屏蔽（在特定浏览器会话期间阻止访问某些域名）
- 区域限制（在特定区域屏蔽某些网站类别）
- 基于类别的规则（通过预置规则集禁用赌博或社交媒体网站）

**安全漏洞缓解与合规审计要求**

评估 AI agent 的安全团队已经发现，agent 可能通过 prompt injection 攻击被诱骗访问非预期网站。自定义 URL `allowlists` 通过将浏览器限制在批准的域名内来缩小攻击面，无论 agent 被指示做什么。基于域名的出站过滤提供了日志记录和访问控制可见性，而这正是安全团队在其安全监控流程中通常所需要的。

## **解决方案概览**

该解决方案将 AgentCore Browser 部署在没有直接互联网访问的私有子网中。出站流量经过 AWS Network Firewall，后者检查 TLS Server Name Indication（SNI）头部以确定目标域名并应用过滤规则。你还可以通过 Network Firewall 与 Amazon CloudWatch 指标的原生集成，监控其为限制流量所采取的动作。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/03/23/ML-20452-image-1.png)

*图 1：使用 AWS Network Firewall 和基于域名的出站过滤的 AgentCore 部署*

该架构包括：

- **私有子网**：托管没有公有 IP 地址的 AgentCore Browser 实例
- **公有子网**：包含用于出站连接的 NAT Gateway
- **防火墙子网**：托管 Network Firewall endpoint
- **四张路由表**：控制出站请求和返回流量经过防火墙的流量路径

**流量路径**

- AgentCore Runtime 执行 agent 并调用 AgentCore Browser 工具
- AgentCore Browser 从私有子网发起 HTTPS 请求
- 私有子网的路由表将流量导向公有子网中的 NAT Gateway
- NAT Gateway 转换私有 IP 地址，并将请求转发到 Network Firewall endpoint
- Network Firewall 检查 TLS SNI 头部以识别目标域名
- 如果域名匹配 `allowlist` 规则，防火墙会将流量转发到 Internet Gateway
- Internet Gateway 将批准的流量路由到外部目标
- 返回流量沿对称路径经防火墙回到 agent

该架构有助于确保浏览器流量无论发往何处都会受到检查和过滤。

**注意**：基于 SNI 的过滤有助于在 TLS 层控制 agent 连接到哪些域名。要实现 DNS 级控制（包括帮助防止 DNS 隧道和数据外泄的控制），请将它与 Amazon Route 53 Resolver DNS Firewall 配合使用。DNS Firewall 有助于解决 SNI 检查的一个局限：agent 有可能通过 DNS 解析被屏蔽的域名，然后直接用 IP 地址连接。

## **前提条件**

开始前，请确保你已具备：

- 一个拥有创建 VPC 资源、Network Firewall 和 IAM 角色权限的 AWS 账户
- 配置了适当凭据的 AWS Command Line Interface（AWS CLI）2.x 版本
- 拥有 Amazon Bedrock AgentCore 的访问权限
- 基本熟悉 VPC 网络概念

## **演练**

有关 VPC 和 Network Firewall 的完整分步配置，请参阅 [Amazon Bedrock AgentCore VPC 配置文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-vpc.html)。

本节重点介绍 AgentCore Browser 特有的配置。

**步骤 1：使用 CloudFormation 模板部署资源**

从代码仓库启动 [CloudFormation 模板](https://github.com/awslabs/amazon-bedrock-agentcore-samples/blob/main/01-tutorials/05-AgentCore-tools/02-Agent-Core-browser-tool/09-browser-with-domain-filtering/agentcore-browser-firewall.yaml)。你可以保留堆栈的默认值。不过，请务必在「Stack name」字段中填写堆栈名称（例如「**agentcore-egress**」），在「Availability Zone」菜单中选择一个可用区，并在「**BucketConfigForOutput**」参数中填入一个有效的现有存储桶名称。等待堆栈创建完成，通常需要 10 分钟。堆栈状态变为 **CREATE_COMPLETE** 后，再继续后续步骤。

**步骤 2：检查 IAM 执行角色**

AgentCore Browser 需要一个针对 bedrock-agentcore.amazonaws.com 服务配置信任策略的 IAM 角色：

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "bedrock-agentcore.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

**步骤 3：配置 Network Firewall 白名单 **

用你批准的域名创建有状态规则组。注意开头的点号（.）用于匹配子域名：

```
cat > allowlist-rules.json << 'EOF'
{
  "RulesSource": {
    "RulesSourceList": {
      "Targets": [
        ".wikipedia.org",
        ".stackoverflow.com",
        ".docs.aws.amazon.com",
        ".amazonaws.com",
        ".pypi.org",
        ".pythonhosted.org"
      ],
      "TargetTypes": ["HTTP_HOST", "TLS_SNI"],
      "GeneratedRulesType": "ALLOWLIST"
    }
  },
  "StatefulRuleOptions": {
    "RuleOrder": "STRICT_ORDER"
  }
}
EOF

aws network-firewall create-rule-group \
  --rule-group-name browser-allowed-domains \
  --type STATEFUL \
  --capacity 100 \
  --rule-group file://allowlist-rules.json \
  --region us-east-2
```

**重要**：如果浏览器需要访问 AWS 服务，请在 `allowlist` 中包含 `.amazonaws.com`，或者改用 VPC Endpoints。

**安全考量：** .amazonaws.com 域名是一个范围很广的 `allowlist`，允许访问 AWS 上托管的 endpoint，包括公有 Amazon Simple Storage Service（Amazon S3）存储桶、Amazon API Gateway endpoint 和 AWS Lambda 函数 URL。要进行更严格的控制，请使用 VPC Endpoints 访问 AWS 服务，并且只将 agent 确实需要的特定外部域名加入 `allowlist`。

**对于 Code Interpreter**：如果需要通过 pip 安装软件包，可考虑添加 ".pypi.org" 和 ".pythonhosted.org"。大多数常见软件包已预装，因此这些域名对你的用例而言是可选的。

**步骤 4：配置防火墙策略 **

防火墙策略必须使用 `aws:drop_established` 作为默认动作。这样既能让 TCP 握手完成（TLS SNI 检查所必需），又能丢弃到非允许域名的连接：

```
cat > firewall-policy.json << 'EOF'
{
  "StatelessDefaultActions": ["aws:forward_to_sfe"],
  "StatelessFragmentDefaultActions": ["aws:forward_to_sfe"],
  "StatefulRuleGroupReferences": [
    {
      "ResourceArn": "arn:aws:network-firewall:us-east-2:ACCOUNT_ID:stateful-rulegroup/browser-allowed-domains",
      "Priority": 1
    }
  ],
  "StatefulEngineOptions": {
    "RuleOrder": "STRICT_ORDER"
  },
  "StatefulDefaultActions": ["aws:drop_established"]
}
EOF
```

**不要使用 aws:drop_strict**，因为它会在 TLS 握手之前阻断 TCP SYN 数据包，导致无法进行 SNI 检查。

**步骤 5：创建安全组**

创建一个允许出站流量的安全组。域名过滤由 Network Firewall 负责，因此安全组只需允许出站流量：

```
# Create security group
aws ec2 create-security-group \
  --group-name agentcore-egress-sg \
  --description "AgentCore tools - egress only, filtered by Network Firewall" \
  --vpc-id vpc-XXXXXXXXX \
  --region us-east-2

# Allow all outbound traffic (Network Firewall handles filtering)
aws ec2 authorize-security-group-egress \
  --group-id sg-XXXXXXXXX \
  --protocol -1 \
  --port -1 \
  --cidr 0.0.0.0/0 \
  --region us-east-2

# Remove default inbound rules if present (AgentCore tools don't need inbound)
aws ec2 revoke-security-group-ingress \
  --group-id sg-XXXXXXXXX \
  --protocol -1 \
  --port -1 \
  --cidr 0.0.0.0/0 \
  --region us-east-2
```

**步骤 6：创建 AgentCore Browser **

创建浏览器，并在 VPC 配置中指向你的私有子网：

```
aws bedrock-agentcore-control create-browser \
  --name my_secure_browser \
  --execution-role-arn arn:aws:iam::ACCOUNT_ID:role/AgentCoreBrowserExecutionRole \
  --network-configuration '{
    "networkMode": "VPC",
    "vpcConfig": {
      "securityGroups": ["sg-XXXXXXXXX"],
      "subnets": ["subnet-XXXXXXXXX"]
    }
  }' \
  --region us-east-2
```

**步骤 6b：创建 AgentCore Code Interpreter（可选）** 

你也可以在同一个 VPC 中部署 AgentCore Code Interpreter，并享受同样的防火墙保护：

```
aws bedrock-agentcore-control create-code-interpreter \
  --name my_secure_code_interpreter \
  --network-configuration '{
    "networkMode": "VPC",
    "vpcConfig": {
      "securityGroups": ["sg-XXXXXXXXX"],
      "subnets": ["subnet-XXXXXXXXX"]
    }
  }' \
  --region us-east-2
```

AgentCore Code Interpreter 使用与 Browser 相同的网络路径。如果你需要 pip 安装软件包，请确保 .pypi.org 和 .pythonhosted.org 在白名单中。

**步骤 6c：在 AgentCore Runtime 上部署 agent（可选）** 

对于基于容器的 agent 部署，使用相同的 VPC 配置：

```
aws bedrock-agentcore-control create-agent-runtime \
  --agent-runtime-name my_vpc_agent \
  --role-arn arn:aws:iam::ACCOUNT_ID:role/AgentCoreRuntimeRole \
  --agent-runtime-artifact '{
    "containerConfiguration": {
      "containerUri": "ACCOUNT_ID.dkr.ecr.us-east-2.amazonaws.com/my-agent:latest"
    }
  }' \
  --network-configuration '{
    "networkMode": "VPC",
    "networkModeConfig": {
      "securityGroups": ["sg-XXXXXXXXX"],
      "subnets": ["subnet-XXXXXXXXX"]
    }
  }' \
  --protocol-configuration '{"serverProtocol": "HTTP"}' \
  --region us-east-2
```

AgentCore Runtime 的域名要求取决于你的模型提供商。对于 Amazon Bedrock 模型 API 调用，请包含 .amazonaws.com；对于 agent 使用的其他模型提供商，则添加相应的域名。此外，还要放行 agent 必须访问的自定义域名。

**步骤 7：测试配置 **

启动一个浏览器会话，验证防火墙规则是否正常工作：

```
# Start browser session
aws bedrock-agentcore start-browser-session \
  --browser-identifier my_secure_browser-ABC123xyz \
  --region us-east-2
```

将返回的 WebSocket URL 与 Playwright 等浏览器自动化工具配合使用，测试允许和屏蔽的域名：

```
# test_firewall_rules.py

from playwright.sync_api import sync_playwright
import boto3
from botocore.auth import SigV4Auth
from botocore.awsrequest import AWSRequest

WEBSOCKET_URL = "wss://your-session-url"  # From start-browser-session response
REGION = "us-east-2"

# Sign the WebSocket URL with SigV4
session = boto3.Session(region_name=REGION)
credentials = session.get_credentials().get_frozen_credentials()
request = AWSRequest(method="GET", url=WEBSOCKET_URL.replace("wss://", "https://"))
SigV4Auth(credentials, "bedrock-agentcore", REGION).add_auth(request)
headers = dict(request.headers)

def test_domain(page, url, expected_success):
    try:
        response = page.goto(url, timeout=10000)
        success = response and response.status < 400
        status = "PASS" if success == expected_success else "FAIL"
        print(f"{status}: {url} - {'loaded' if success else 'blocked'}")
        return success == expected_success
    except Exception as e:
        success = False
        status = "PASS" if not expected_success else "FAIL"
        print(f"{status}: {url} - blocked ({type(e).__name__})")
        return not expected_success

with sync_playwright() as p:
    browser = p.chromium.connect_over_cdp(WEBSOCKET_URL, headers=headers)
    page = browser.new_page()

    # Test allowed domains (should load)
    test_domain(page, "https://wikipedia.org", expected_success=True)
    test_domain(page, "https://docs.aws.amazon.com", expected_success=True)

    # Test blocked domains (should timeout/fail)
    test_domain(page, "https://example.com", expected_success=False)
    test_domain(page, "https://twitter.com", expected_success=False)

    browser.close()
```

**预期结果：**

- 允许的域名（.wikipedia.org、.amazonaws.com）应能成功加载。
- 被屏蔽的域名应在 TCP 握手后超时，或返回连接错误。

**注意**：某些允许的域名（如 docs.aws.amazon.com）依赖来自 awsstatic.com 和 cloudfront.net 等域名的 CDN 资源。如果允许的域名上的页面无法完整渲染，请将所需的 CDN 域名加入 `allowlist`。

你还可以在 CloudWatch 中查看防火墙日志，了解被阻止的连接尝试：

```
# View recent alert logs (blocked connections)
aws logs filter-log-events \
  --log-group-name "/aws/network-firewall/agentcore-egress/alerts" \
  --filter-pattern '{ $.event.alert.action = "blocked" }' \
  --region us-east-2 \
  --start-time $(($(date +%s) - 300))000

# Verify firewall sync status before testing
aws network-firewall describe-firewall \
  --firewall-name agentcore-egress-firewall \
  --region us-east-2 \
  --query 'FirewallStatus.ConfigurationSyncStateSummary'
```

**故障排查**：如果允许的域名被屏蔽，请检查：

- 防火墙同步状态显示 IN_SYNC（规则变更需要几分钟生效）
- 域名条目包含开头的点号（是 .wikipedia.org，而不是 wikipedia.org）
- 路由表配置正确，支持对称路由
- 如果在允许的域名上收到 HTTP 403 错误，这通常是目标站点的机器人检测，而非防火墙拦截。请查看 CloudWatch ALERT 日志确认——被阻止的连接会有明确的告警条目。

## **最佳实践**

- **使用 STRICT_ORDER 评估**：在组合使用 `allowlists` 和 `denylists` 时，这有助于实现可预测的规则处理。
- **为 AWS 服务访问包含 .amazonaws.com**：或者使用 VPC Endpoints，避免让 AWS API 调用经过互联网。
- **配置 IGW 入站路由表**：这对对称路由至关重要。缺少它时，返回流量会绕过防火墙。
- **同时启用 ALERT 和 FLOW 日志**：ALERT 日志记录被阻止的连接，FLOW 日志提供流量的连接元数据。
- **等待防火墙同步**：规则变更需要几分钟才能传播。测试前请确认 ConfigurationSyncStateSummary 为 IN_SYNC。
- **为多 VPC 架构配置 HOME_NET**：默认情况下，Network Firewall 的域名检查只过滤来自部署 VPC 的无类别域间路由（CIDR）范围的流量。如果你使用带 AWS Transit Gateway 的集中式防火墙来检查来自多个 VPC 的流量，必须在规则组的 HOME_NET 变量中包含来源 CIDR 范围。否则，来自其他 VPC 的流量可能绕过域名过滤。

## **局限性与成本考量**

- **内容检查需要 TLS 检查**：默认情况下，域名过滤针对未加密的 TLS 元数据（SNI 头部）进行，无法检查加密的请求或响应体。要检查 HTTPS 内容，请在 Network Firewall 上启用 TLS 检查，并添加匹配 HTTP 正文内容的 Suricata 规则。**SNI/Host 头部绕过风险**：Network Firewall 使用 TLS SNI 头部和 HTTP Host 头部（而非 IP 地址）来确定目标域名。如果这些头部被篡改，流量就可能绕过域名过滤。对于高安全性部署，请将域名规则与针对关键屏蔽目标的基于 IP 的规则结合使用，或增加 DNS 过滤作为额外一层。此外，可考虑将基于 SNI 的规则与 Route 53 DNS Firewall 搭配使用，帮助防止 agent 通过 DNS 解析被屏蔽的域名并直接用 IP 地址连接。
- **多 VPC 部署中的 HOME_NET 范围**：默认情况下，Network Firewall 的域名检查只适用于来自部署 VPC CIDR 范围的流量。如果你使用带 AWS Transit Gateway 的集中式防火墙（多个 VPC 通过共享防火墙路由），必须在规则组的 HOME_NET 变量中包含来源 CIDR 范围。否则，来自分支 VPC 的流量会绕过域名检查。详情请参阅[有状态域名列表规则组](https://docs.aws.amazon.com/network-firewall/latest/developerguide/stateful-rule-groups-domain-names.html)。
- 费用因使用情况而异。当前费率请参阅 [NAT Gateway 定价](https://aws.amazon.com/vpc/pricing/)和 [Network Firewall 定价](https://aws.amazon.com/network-firewall/pricing/)。

## **清理资源**

按以下顺序删除资源，以避免持续产生费用：

- 删除 AgentCore Browser
- 删除 Network Firewall（先禁用保护设置）
- 删除 NAT Gateway
- 释放 Elastic IP 地址
- 删除子网和路由表
- 分离并删除 Internet Gateway
- 删除 VPC

**注意**：AgentCore Browser 和 Code Interpreter 会在你的 VPC 中创建弹性网络接口。删除这些资源后，请等待几分钟，让网络接口释放，再删除安全组、子网或 VPC。如果删除失败，请检查子网中是否仍有残留的网络接口，并等待其分离。

## **结论**

通过将 Amazon Bedrock AgentCore 工具与 AWS Network Firewall 结合，你可以在保持安全与合规的前提下，为 AI agent 提供受控的 Web 访问。基于域名的过滤方法帮助你精确定义 agent 可以访问哪些网站、屏蔽不需要的目标，并记录连接尝试以供审计。该架构回应了企业客户提出的安全顾虑：

- **FSI 合规**：提供 CISO 级别安全审查所需的网络隔离和审计日志。
- **多租户控制**：使 SaaS 提供商能够按客户或按执行过程制定域名策略。
- **prompt injection 防御**：将 agent 的浏览范围限制在批准的域名内，有助于缩小 prompt injection 的攻击面。
- **审计证据**：生成支持合规审计要求的 CloudWatch 日志。

对于部署 AI agent 并需要互联网访问以进行研究、数据收集或 API 集成的企业，这一模式提供了一种可用于生产的方式，能够严格控制访问的目的地。你无需维护自定义的 squid proxy 或复杂的网络基础设施，只需使用 AWS 托管服务，就能在几小时而非几周内实现企业级的出站过滤。
