# 使用 NLP 在 Amazon Bedrock AgentCore 上构建 AI 驱动的仪表板自动化 agent

业务分析师在应对不断变化的业务需求时，往往要等上好几天才能完成仪表板修改。传统流程是向 IT 团队提交修改请求，由他们解读需求、查阅 API 文档、理解表结构并部署变更。虽然这种方式能保持适当的监督和质量控制，但当需要快速更新仪表板时，它可能导致长达数天的周转时间。

本方案结合了 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)、[Strands Agents](https://github.com/strands-agents/sdk-python/tree/main) 和 [AWS Quick](https://aws.amazon.com/quick/) 的变革之力，提供一个安全、可扩展且智能的系统，用于构建和运营 AI agent，同时将数据转化为可落地的业务洞察。

## **方案概览**

在本方案中，我们使用基于 Amazon Bedrock AgentCore 和 Strands 框架构建的多 agent 架构。Amazon Bedrock AgentCore 是一个 agentic 平台，用于大规模安全地构建、部署和运营高效的 agent，无需管理基础设施。它通过智能记忆和一个 gateway 实现对工具和数据的安全、受控访问，从而加速 agent 投入生产。它以生产级安全性和动态扩缩容运行 agent，并在生产环境中监控性能和质量。Strands Agents 是一个 code-first 框架，用于构建与 AWS 服务集成的 agent。本方案还使用 AWS Quick，它提供 AI 驱动的 BI 能力，将你分散的数据转化为人人可用的战略洞察，让你更快决策并取得更好的业务成果。

该架构由三个协同工作的专用 agent 组成。*Find Dashboard Agent* 执行发现操作，包括搜索仪表板以及从仪表板和数据集检索列元数据。*Modify Dashboard Agent* 通过校验列、更新表格可视化以及创建新的仪表板版本来执行配置变更。*Orchestrator Agent* 基于意图分类将用户请求路由到相应的专用 agent。

Orchestrator Agent 是用户交互的入口。当用户提交自然语言查询（如“Add lastname to the testing dashboard”）时，Amazon Nova 会将请求分类为对话类或操作类。对话类查询利用 Nova 的大语言模型（LLM）能力直接给出响应。操作类请求则通过 Strands 框架路由到专用 agent，这些 agent 依据可用的数据集列校验变更，并自主执行修改，同时保持安全控制、审计轨迹，并保留原始仪表板以便回滚。下图展示了该方案的架构和工作流程。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/20/image-35.png)

该架构包括以下组件：

- **Amazon Bedrock AgentCore** – 托管 Strands Agent orchestrator 和专用子 agent。
- **Amazon Nova** – 提供自然语言处理（NLP）和推理能力。
- **AWS Quick** – 仪表板发现和修改操作的目标服务。
- **AgentCore Memory** – 维护对话上下文和会话状态。
- **Amazon Bedrock AgentCore Observability** – 记录 agent 决策并追踪 API 交互。

要实现面向 Quick 自助服务的 agentic AI 方案，请完成以下高层步骤：

- 构建 agent（Find Dashboard Agent、Modify Dashboard Agent 和 Orchestrator Agent）。
- 将 agent 部署到 Amazon Bedrock AgentCore。
- 通过 AWS Management Console 测试 agent。

## **先决条件**

要实现本方案，你必须具备以下先决条件：

- 一个拥有 Amazon Bedrock、AWS Quick 和 AWS Identity and Access Management (IAM) 权限的 AWS 账户。有关创建新仪表板的信息，请参阅[创建 AWS Quick 仪表板](https://docs.aws.amazon.com/quick/latest/userguide/example-create-a-dashboard.html)。
- 一个拥有现有仪表板的有效 AWS Quick 账户（[创建指南](https://docs.aws.amazon.com/quick/latest/userguide/example-prepared-data-set.html)）。
- 已配置 IAM 权限，授予 agent 访问 Quick 应用程序编程接口（API）的权限：`quicksight:ListDashboards` `quicksight:DescribeDashboard` `quicksight:DescribeDashboardDefinition` `quicksight:DescribeDataSet` `quicksight:CreateDashboard`
- Python 3.10 或更高版本（直接代码部署支持 Python 3.10-3.13）。
- 已安装 uv 包管理器（[安装指南](https://docs.astral.sh/uv/getting-started/installation/)）。
- 已使用适当凭证配置 AWS Command Line Interface (AWS CLI)。
- 具备 Python 和 AWS 服务的基础知识。

## **操作演练**

要使用 Amazon Bedrock AgentCore 构建、部署和测试你的 AI 驱动的仪表板自动化解决方案*，*请按照以下四个步骤：

### **步骤 1：构建用于查找和修改仪表板的 Quick 自助式 agent**

构建支撑 Quick 自助式方案的三个核心 agent：

- Find Dashboard Agent，负责发现操作。
- Modify Dashboard Agent，负责修改操作。
- Orchestrator Agent，负责在两者之间进行协调。

下面逐一了解每个 agent 的角色和实现。

**1.1 构建 Find Dashboard Agent**

该 agent 处理后续查看或修改操作所需的仪表板发现任务。例如，当用户提交自然语言查询（如“show me a report with name 'testing'”）时，orchestrator 会调用该 agent，后者执行 `list_dashboards` API 以检索仪表板元数据，根据搜索条件过滤结果，并以结构化格式返回匹配的仪表板。

这个发现 agent 提供三项核心能力：支持精确和部分名称匹配的仪表板搜索、列出账户中可用的仪表板，以及从仪表板及其底层数据集检索列信息。这些发现功能是仪表板操作的前提，因为在执行修改或检索之前必须先确定目标仪表板。

每项能力都以 Strands @tool 函数的形式实现。以下代码片段展示了 find dashboard tool，它调用 `list_dashboards` API 并使用部分名称匹配来过滤结果：

```
from strands import Agent, tool
from strands.models import BedrockModel

@tool

def find_dashboard_tool(dashboard_name: str = "") -> str:
  """Find Quick dashboards by name (supports partial matching)"""
  client = boto3.client('quicksight', region_name=REGION)

  response = client.list_dashboards(AwsAccountId=AWS_ACCOUNT_ID)

  dashboards = response.get('DashboardSummaryList', [])

  # List all dashboards if no search term provided

  if not dashboard_name or dashboard_name.strip() == "":
   all_names = [d['Name'] for d in dashboards]
   return f"All dashboards ({len(all_names)}): {all_names}"

  # Filter using case-insensitive partial matching

  matches = [d['Name'] for d in dashboards if dashboard_name.lower() in d['Name'].lower()]
      return f"Found {len(matches)} dashboards: {matches}"
```

随后，该 agent 将这些 tool 函数包装在 Strands Agent 中，并将自身暴露为一个 @tool，以便 orchestrator 用自然语言查询调用它：

```
_find_agent = Agent(
  model=BedrockModel(model_id=MODEL_ID),
  tools=[find_dashboard_tool, get_columns_tool],
  system_prompt="You are the Find Dashboard Agent. Help users find dashboards and view columns."

)

@tool

def find_dashboard_agent(query: str) -> str:
 """Agent wrapper exposed as a tool for the orchestrator to invoke"""
 response = _find_agent(query)
 return str(response)
```

正是这种 agent-as-tool 模式支撑了多 agent 架构。orchestrator 并不直接调用 Quick API，而是调用这个 agent，由后者在内部处理自然语言理解和 API 调用。

**1.2 构建 Modify Dashboard Agent**

在具备发现能力之后，下一个 agent 通过 validation-first 的工作流处理仪表板配置变更。以用户请求“add lastname to the testing dashboard”为例。orchestrator 将其路由到 Modify Dashboard Agent，后者校验该列是否存在于数据集 schema 中，使用 `describe_dashboard_definition` API 检索完整的仪表板定义，更新表格可视化的 field wells 和字段选项，并使用 create_dashboard API 创建新的仪表板版本。

这个修改 agent 支持两项主要操作：向仪表板添加列（在校验所请求的列存在于底层数据集但尚未出现之后）以及从仪表板移除列（在确认该列当前正在显示之后）。它不会修改现有仪表板，而是创建带有唯一标识符的新仪表板，保留原始仪表板以供审计，并在需要时支持回滚。

这种 validation-first 方法有助于校验数据完整性并防止配置错误，而保留原始仪表板则有助于满足治理要求的合规性，并为修改提供审计轨迹。

以下代码片段展示了核心修改 tool。它校验请求、更新仪表板定义中的表格可视化 field wells，并创建新的仪表板：

```
@tool

def modify_dashboard(dashboard_name: str, action: str, column_name: str) -> str:
"""Modify a dashboard by adding or removing columns"""
client = boto3.client('quicksight', region_name=REGION)
info = _get_dashboard_and_dataset_info(dashboard_name)

# Validation-first: verify column state before making changes
if action == "add":
if column_name in info["dashboard_columns"]:
return f"Column '{column_name}' is already in the dashboard."
if column_name not in info["dataset_columns"]:
return f"Column '{column_name}' doesn't exist in dataset."
elif action == "remove":
if column_name not in info["dashboard_columns"]:
return f"Column '{column_name}' is not in the dashboard."

# Update table visual field wells in the dashboard definition
updated_definition = info["definition"]
for sheet in updated_definition.get('Sheets', []):
for visual in sheet.get('Visuals', []):
if 'TableVisual' in visual:
field_wells = visual['TableVisual']['ChartConfiguration']['FieldWells']
existing_fields = field_wells['TableAggregatedFieldWells']['GroupBy']
if action == "add":
existing_fields.append({
'CategoricalDimensionField': {
'FieldId': str(uuid.uuid4()),
'Column': {
'DataSetIdentifier': dataset_id,
'ColumnName': column_name
}
}
})

elif action == "remove":
existing_fields = [f for f in existing_fields
if f['CategoricalDimensionField']['Column']['ColumnName'] != column_name]

# Create new dashboard with UUID suffix, original is preserved for rollback
new_uuid = str(uuid.uuid4())[:8]
client.create_dashboard(
AwsAccountId=AWS_ACCOUNT_ID,
DashboardId=f"dashboard_{new_uuid}",
Name=f"{info['dashboard_name']}_dashboard_{new_uuid}",
Definition=updated_definition
)

Like the Find Dashboard Agent, this tool is wrapped inside a Strands Agent and exposed as a @tool for the orchestrator:
_modify_agent = Agent(
model=BedrockModel(model_id=MODEL_ID),
tools=[modify_dashboard],
system_prompt="You are the Modify Dashboard Agent. You add or remove columns from dashboards."
)

@tool
def modify_dashboard_agent(query: str) -> str:
"""Agent wrapper for the orchestrator to invoke with natural language"""
response = _modify_agent(query)
return str(response)
```

该 agent 从用户的自然语言查询中提取仪表板名称、操作和列名，并将其传递给 `modify_dashboard` tool，由后者负责校验和执行。

**1.3 创建 Orchestrator Agent**

最后一个组件在 Strands 框架中将 Find Dashboard Agent 和 Modify Dashboard Agent 作为 tool 进行协调。这个 orchestrator 定义了用于指导路由逻辑的 system prompt，明确哪个 agent 处理发现操作、哪个处理修改操作。该配置包含两个专用 agent 的 tool 注册，使 orchestrator 能够根据分类后的意图调用它们。

路由逻辑通过自然语言理解处理多种查询模式。包含仪表板名称和列名等明确参数的直接请求会立即被委派给相应的专用 agent。缺少必需参数的模糊请求则会触发后续追问，以在路由前收集缺失信息。这种实现模式使 orchestrator 充当协调者而非执行者，将 Quick API 操作委派给专用 agent，自身只专注于意图分析和路由决策。

以下代码片段展示了 orchestrator 如何将两个 agent 注册为 tool，并通过其 system prompt 定义路由逻辑：

```
from find_dashboard_agent import find_dashboard_agent
from modify_dashboard_agent import modify_dashboard_agent
orchestrator = Agent(
model=BedrockModel(model_id=MODEL_ID),
tools=[find_dashboard_agent, modify_dashboard_agent],
system_prompt="""You are an AWS Quick Orchestrator. Route user requests to specialized agents.

AGENTS:
- find_dashboard_agent: Finding dashboards, listing, showing columns
- modify_dashboard_agent: Adding/removing columns

ROUTING LOGIC:
- "find", "show", "list", "get", "columns" → find_dashboard_agent
- "add", "remove", "modify", "delete" → modify_dashboard_agent"""
)
```

Bedrock AgentCore 集成将这个 orchestrator 暴露为接收用户请求的入口点：

```
app = BedrockAgentCoreApp()
@app.entrypoint
def invoke(payload):
user_input = payload.get("prompt", "")
response = orchestrator(user_input)
return response.message['content'][0]['text']
```

由于 `find_dashboard_agent` 和 `modify_dashboard_agent` 各自被包装为 @tool 函数，orchestrator 将它们与其他 tool 一样对待。Amazon Nova 分析用户意图并自动调用相应的 agent。

### **步骤 2：为 agent 部署设置项目**

使用直接代码部署将 agent 部署到 Amazon Bedrock AgentCore。这包括初始化项目、添加依赖项、创建 agent 文件以及部署到运行时环境。

**2.1 初始化项目**

使用 uv 包管理器创建一个新的 Python 项目，然后进入项目目录uv init quicksight-selfservice-agentcd quicksight-selfservice-agent这将创建一个新的项目结构，其中包含用于管理依赖项和部署 agent 的必要配置文件。

**2.2 为项目添加依赖项**

为你的项目安装所需的 Amazon Bedrock AgentCore 库和开发工具。在本示例中，使用 uv add 命令添加依赖项：

```
uv add bedrock-agentcore strands-agents strands-agents-tools

uv add --dev bedrock-agentcore-starter-toolkit
```

激活虚拟环境：

```
# For Linux/macOS

source .venv/bin/activate

# For Windows

source .venv/Scripts/activate
```

这些依赖项提供了用于构建和部署 agent 的核心框架，包括用于创建 agent 的 Strands SDK 以及用于部署管理的 Amazon Bedrock AgentCore 工具包。

**2.3 创建 agent.py 文件**

从 [GitHub 仓库](https://github.com/aws-samples/sample-bedrock-agentcore-quicksight)以 zip 文件形式下载完整实现。解压 zip，并将以下文件复制到项目根目录：

- `agent.py` – 主 orchestrator agent 入口点，集成 Amazon Bedrock AgentCore
- `find_dashboard_agent.py` – 负责仪表板发现操作的专用 agent
- `modify_dashboard_agent.py` – 负责仪表板修改操作的专用 agent
- `shared/` 文件夹 – 包含用于共享 AWS 服务客户端配置的 config.py

其他必需文件（如 pyproject.toml 和配置文件）已在初始化步骤中作为项目设置的一部分创建。这些文件就位后，你就可以将 Quick 自助式 agent 部署到 Amazon Bedrock AgentCore。

## **清理**

为避免产生后续费用，请删除以下资源：

- **删除 AgentCore Runtime 部署**：使用 AWS 控制台或 CLI：  `aws bedrock-agentcore delete-agent-runtime --agent-id <agent-id> --region <region>`
- **移除 ECR 仓库** – 导航到 [Amazon Elastic Container Registry (Amazon ECR) 控制台](https://console.aws.amazon.com/ecr/)并删除部署期间创建的容器仓库，或使用以下 CLI 命令：  `aws ecr delete-repository --repository-name <repository-name> --region <region> --force`
- **移除测试用 Quick 仪表板** – 导航到 [AWS Quick 控制台](https://quicksight.aws.amazon.com/)并删除测试期间创建的带 UUID 后缀的修改版仪表板，或使用以下 CLI 命令：  `aws quicksight delete-dashboard --aws-account-id <account-id> --dashboard-id <dashboard-id> --region <region>`
- **删除 Amazon CloudWatch Log groups** – 导航到 [Amazon CloudWatch 控制台](https://console.aws.amazon.com/cloudwatch/)并移除与 agent 关联的日志组（格式：`/aws/bedrock/agentcore/<agent-id>`），或使用以下 CLI 命令：  `aws logs delete-log-group --log-group-name /aws/bedrock/agentcore/<agent-id> --region <region>`
