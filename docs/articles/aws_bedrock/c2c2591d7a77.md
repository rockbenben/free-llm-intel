# 使用 CrewAI 和 Amazon Bedrock 构建 agentic 系统

*本文由 CrewAI 的 Joao Moura 和 Tony Kipkemboi 共同撰写。*

随着 agentic 系统从实验性工具转变为任务关键型的业务资产，企业 AI 格局正在经历剧烈转变。2025 年，AI agent 预计将成为业务运营的组成部分，[Deloitte](https://www.deloitte.com/global/en/about/press-room/deloitte-globals-2025-predictions-report.html) 预测，使用生成式 AI 的企业中有 25% 将部署 AI agent，到 2027 年这一比例将增长到 50%。[全球 AI agent 市场](https://aimresearch.co/ai-startups/vertical-ai-agents-will-dominate-2025) 预计将从 2024 年的 $5.1 billion 激增至 2030 年的 $47.1 billion，反映出这些技术的变革性潜力。

在本文中，我们探讨 [CrewAI 的开源 agentic 框架](https://docs.crewai.com/introduction)与 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 结合，如何支持创建能够改变企业运营方式的精密多 agent 系统。通过实际示例和实现细节，我们演示如何构建、部署和编排 AI agent，使其能够在最少人工监督下处理复杂任务。尽管“agents”是 2025 年的流行词，但理解什么是 AI agent、以及在哪里部署 agentic 系统能带来收益，仍然很重要。

## Agentic 设计

AI agent 是一个自主的智能系统，它使用 large language model（LLM）和其他 AI 能力，在最少人工监督下执行复杂任务。与传统软件遵循预定义规则不同，AI agent 可以独立运行、从其环境中学习、适应变化的条件，并做出结合上下文的决策。它们由模块化组件设计而成，例如推理引擎、记忆、认知技能和工具，这些组件使它们能够执行精密的工作流。传统 SaaS 解决方案针对水平可扩展性和通用适用性而设计，这使它们适合管理跨不同行业的重复性任务，但它们往往缺乏领域专属的智能，也缺乏应对动态环境中独特挑战的灵活性。另一方面，agentic 系统旨在通过把上下文感知系统的灵活性与领域知识相结合来弥合这一差距。考虑一个软件开发用例：AI agent 可以生成、评估和改进代码，把软件工程师的注意力从日常编码转移到更复杂的设计挑战上。例如，在 CrewAI 的 git 仓库中，pull request 由一组 CrewAI agent 来评估，它们依据代码文档、实现一致性和安全考量来审查代码。另一个用例可见于供应链管理：传统库存系统可能跟踪库存水平，但缺乏预判供应链中断或基于行业洞察优化采购的能力。相比之下，agentic 系统可以使用实时数据（例如天气或地缘政治风险）来主动重新规划供应链并重新分配资源。下图描述了 agentic AI 系统的组件：

## CrewAI 概述

CrewAI 是一个企业套件，其中包含一个基于 Python 的开源框架。它简化了使用 AI flow、多 agent 系统或两者组合来创建和管理 AI 自动化的过程，使 agent 能够无缝协作，通过协作智能处理复杂任务。下图展示了 CrewAI 企业版产品的能力：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/28/image003-1.png)

CrewAI 的设计围绕通过 flow 以及 AI agent 组成的 crew 来构建 AI 自动化的能力展开。它擅长处理 agent 与任务之间的关系：每个 agent 都有定义好的 role、goal 和 backstory，并可以访问特定工具来完成其目标。这个框架允许 agent 之间自主委派，agent 可以相互委派任务并相互询问，从而提升问题求解效率。这种增长由医疗、金融和零售等行业对智能自动化和个性化客户体验日益增长的需求所推动。

CrewAI 的 agent 不仅在自动化日常任务，还在创造需要高级技能的新角色。CrewAI 通过其模块化设计和简洁性原则强调团队协作，旨在超越传统自动化，在简化决策、增强创造力以及应对复杂挑战方面达到更高水平。

## CrewAI 关键概念

CrewAI 的架构建立在一个模块化框架之上，该框架由若干关键组件构成，它们促进多 agent 环境中的协作、委派和自适应决策。让我们逐一详细探讨每个组件，以理解它们如何支撑多 agent 交互。

从高层看，CrewAI 提供两种主要方式来创建 agentic 自动化：flow 和 crew。

### Flow

[CrewAI Flows](https://docs.crewai.com/guides/flows/first-flow) 提供一个结构化、事件驱动的框架，用于无缝编排复杂的多步 AI 自动化。Flow 使用户能够定义精密的工作流，通过条件逻辑、循环和实时状态管理，把常规代码、单次 LLM 调用以及可能的多组 crew 组合起来。这种灵活性使企业能够构建动态、智能的自动化 pipeline，适应变化的条件和不断演进的业务需求。下图展示了 Crew 与 Flow 之间的区别：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/28/image005.png)

与 Amazon Bedrock 集成后，CrewAI Flows 释放出更大的潜力。Amazon Bedrock 通过提供对强大基础模型（FM）的访问，奠定了健壮的基础。

例如，在客户支持场景中，通过 Amazon Bedrock 编排的 CrewAI Flow 可以自动把客户查询路由到专门的 AI agent crew。这些 crew 协作诊断客户问题、与后端系统交互以检索数据、生成个性化响应，并且只在必要时才把复杂问题动态升级给人工坐席。

同样，在金融服务领域，CrewAI Flow 可以监控行业状况，触发基于 agent 的分析，以根据行业波动性和投资者偏好主动管理投资组合。

CrewAI Flows 与 Amazon Bedrock 共同形成强大的协同效应，使企业能够实施自适应、智能的自动化，高效且规模化地应对真实世界的复杂性。

### Crew

CrewAI 中的 crew 由若干关键组件构成，我们在本节中讨论这些组件。

#### Agent

CrewAI 中的 agent 是自主实体，被设计为在多 agent 系统中执行特定角色。这些 agent 具备多种能力，包括推理、记忆，以及与其环境动态交互的能力。每个 agent 由四个主要要素定义：

- **Role**——决定 agent 在系统中的职能和职责
- **Backstory **——提供引导 agent 决策过程的上下文信息
- **Goals **——指明 agent 力图达成的目标
- **Tools**——扩展 agent 的能力，使其能够访问更多信息并采取行动

CrewAI 中的 agent 被设计为协作工作，做出自主决策、委派任务，并使用工具高效执行复杂工作流。它们可以相互通信、使用外部资源，并根据观察到的结果改进自身的策略。

#### Task

CrewAI 中的 task 是基本的构建块，定义 agent 为达成目标需要执行的具体动作。任务可以组织为独立的作业，或需要多个 agent 协作的相互依赖的工作流。每个任务包含关键参数，例如：

- **Description**——清楚定义任务所包含的内容
- **Agent assignment**——指明哪个 agent 负责执行该任务

#### Tool

CrewAI 中的 tool 为 agent 提供扩展能力，使其能够执行超出自身内在推理能力的动作。这些工具允许 agent 与 API 交互、访问数据库、执行脚本、分析数据，甚至与其他外部系统通信。CrewAI 支持模块化的工具集成系统，可定义工具并将其分配给特定 agent，从而实现高效且具上下文感知的决策。

#### Process

CrewAI 中的 process 层管控 agent 如何交互、协调和委派任务。它通过管理 agent 之间的任务执行、通信和同步，确保多 agent 工作流无缝运转。

关于 CrewAI 概念的更多细节，请参阅 [CrewAI 文档](http://docs.crewai.com)。

## 开始使用 CrewAI 与 Amazon Bedrock

Amazon Bedrock 与 CrewAI 的集成支持创建由最先进语言模型驱动的生产级 AI agent。

以下是关于如何设置这一集成的代码片段：

```
from crewai import Agent, Crew, Process, Task, LLM
from crewai_tools import SerperDevTool, ScrapeWebsiteTool
import os

# Configure Bedrock LLM
llm = LLM(
    model="bedrock/anthropic. anthropic.claude-3-5-sonnet-20241022-v2:0",
    aws_access_key_id=os.getenv('AWS_ACCESS_KEY_ID'),
    aws_secret_access_key=os.getenv('AWS_SECRET_ACCESS_KEY'),
    aws_region_name=os.getenv('AWS_REGION_NAME')
)

# Create an agent with Bedrock as the LLM provider
security_analyst = Agent(
    config=agents_config['security_analyst'],
    tools=[SerperDevTool(), ScrapeWebsiteTool()],
    llm=llm
)
```

关于如何为 AI agent 配置 LLM 的详细说明，请参阅 [CrewAI LLM 文档](https://docs.crewai.com/concepts/llms#aws-bedrock)。

Amazon Bedrock 为 CrewAI 应用提供若干关键优势：

- **可访问 Anthropic’s Claude 和 Amazon Nova 等最先进的语言模型**——这些模型提供支撑 agent 决策的认知能力。这些模型使 agent 能够理解复杂指令、生成类人响应，并基于上下文做出细微的判断。
- **企业级安全与合规功能**——这对需要严格管控自身数据、并落实各类法规合规要求的组织至关重要。
- **由 AWS 基础设施支撑的可扩展性与可靠性**——这意味着你的 agent 系统可以处理不断增长的工作负载，同时保持一致的性能。

### Amazon Bedrock Agents 与 Amazon Bedrock Knowledge Bases 作为原生 CrewAI 工具

[Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 让你能够以完全托管、无服务器的方式在 Amazon Bedrock 上构建和配置自主 agent。你无需预置容量、管理基础设施或编写自定义代码。Amazon Bedrock 负责管理 prompt engineering、记忆、监控、加密、用户权限和 API 调用。`BedrockInvokeAgentTool` 使 CrewAI agent 能够调用 Amazon Bedrock agent，并在你的工作流中使用它们的能力。

借助 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)，你可以安全地把 FM 和 agent 连接到公司数据，从而提供更相关、更准确、更定制化的响应。`BedrockKBRetrieverTool` 使 CrewAI agent 能够使用自然语言查询从 Amazon Bedrock Knowledge Bases 检索信息。

以下代码展示了 Amazon Bedrock Agents 集成的示例：

```
from crewai import Agent, Task, Crew

from crewai_tools.aws.bedrock.agents.invoke_agent_tool import BedrockInvokeAgentTool

# Initialize the Bedrock Agents Tool

agent_tool = BedrockInvokeAgentTool(
    agent_id="your-agent-id",
    agent_alias_id="your-agent-alias-id"
)

# Create an CrewAI agent that uses the Bedrock Agents Tool

aws_expert = Agent(
    role='AWS Service Expert',
    goal='Help users understand AWS services and quotas',
    backstory='I am an expert in AWS services and can provide detailed information about them.',
    tools=[agent_tool],
    verbose=True
)
```

以下代码展示了 Amazon Bedrock Knowledge Bases 集成的示例：

```
# Create and configure the BedrockKB tool 
kb_tool = BedrockKBRetrieverTool(
    knowledge_base_id="your-kb-id",
    number_of_results=5
)

# Create an CrewAI agent that uses the Bedrock Agents Tool
researcher = Agent(
    role='Knowledge Base Researcher',
    goal='Find information about company policies',
    backstory='I am a researcher specialized in retrieving and analyzing company documentation.',
    tools=[kb_tool],
    verbose=True
)
```

## 在 AWS 上通过监控、追踪和可观测性实现 CrewAI 的运维卓越

与任何软件应用一样，在生产环境中部署 agentic 应用时，实现运维卓越至关重要。这些应用是复杂系统，由确定性和概率性组件构成，这些组件以串行或并行的方式交互。因此，全面的监控、可追踪性和可观测性是实现运维卓越的关键因素。这包括三个关键维度：

- **应用级可观测性**——保障整个系统的顺畅运行，包括 agent 编排框架 CrewAI 以及可能存在的其他应用组件（例如前端）
- **模型级可观测性**——保障可靠的模型性能（包括准确率、延迟、吞吐量等指标）
- **Agent 级可观测性**——维持单 agent 或多 agent 系统内的高效运行

在 AWS 上使用 CrewAI 和 Amazon Bedrock 运行基于 agent 的应用时，你可以获得这些维度上一整套全面的内置能力：

- **应用级日志**——[Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 会自动从运行在你所选 AWS 计算平台上的应用代码中收集应用级日志和指标，这些平台例如 [AWS Lambda](https://aws.amazon.com/lambda)、[Amazon Elastic Container Service](https://aws.amazon.com/ecs)（Amazon ECS）或 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2)（Amazon EC2）。CrewAI 框架提供应用级日志记录，默认配置为最小级别。若需更详细的洞察，可在初始化时设置 verbose=True 来在 agent 或 crew 级别启用详细日志。
- **模型级调用日志 **——此外，CloudWatch 会自动从 Amazon Bedrock 收集模型级调用日志和指标。这包括关键的性能指标。
- **Agent 级可观测性 **——CrewAI 可与流行的第三方监控和可观测性框架无缝集成，例如 [AgentOps](https://docs.crewai.com/how-to/agentops-observability)、[Arize](https://docs.arize.com/phoenix/tracing/integrations-tracing/crewai)、[MLFlow](https://docs.crewai.com/how-to/mlflow-observability)、[LangFuse](https://docs.crewai.com/how-to/openlit-observability) 等。这些框架可对 agent 系统的性能进行全面追踪、调试、监控和优化。

## 解决方案概述

云安全态势管理（CSPM）是一项重要能力，它通过持续扫描云基础设施中的错误配置和合规风险，为组织提供对其云安全状况的全面视图。

传统安全评估往往需要多位专家、协调排期以及无数的检查。借助 CrewAI Agents，你可以精简整个流程：自动梳理你的资源、分析配置，并生成清晰、按优先级排序的修复步骤。

下图展示了解决方案架构。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/28/image011.png)

我们的用例演示实现了一个由三个 agent 组成的专门团队，每个 agent 都有不同的职责，对应你可能在专业安全咨询公司中见到的角色：

- **基础设施梳理器**——充当我们的系统架构师，有条不紊地记录 AWS 资源及其配置。像一位经验丰富的云架构师，它创建详细的清单，作为我们安全分析的基础。
- **安全分析师**——充当我们的网络安全专家，检查基础设施图谱中的潜在漏洞，并研究当前的最佳实践。它带来关于安全威胁和缓解策略的深入知识。
- **报告撰写者**——履行我们的技术文档专家职能，把复杂的发现综合为清晰、可操作的建议。它确保技术洞察能够有效传达给技术与非技术的利益相关方。

## 实现该解决方案

在本节中，我们逐步介绍一个安全评估多 agent 系统的实现。该示例的代码位于 [GitHub](https://github.com/aws-samples/3P-Agentic-Frameworks/tree/main/crewai/aws-security-auditor-crew)。请注意，并非该解决方案的所有代码产物都在本文中明确覆盖。

### 第 1 步：配置 Amazon Bedrock LLM

在把环境变量传给 LLM 类之前，我们已将它们保存在根目录的 .env 文件中：

```
from crewai import Agent, Crew, Process, Task, LLM 
from crewai.project import CrewBase, agent, crew, task 

from aws_infrastructure_security_audit_and_reporting.tools.aws_infrastructure_scanner_tool import AWSInfrastructureScannerTool 
from crewai_tools import SerperDevTool, ScrapeWebsiteTool 
import os 

@CrewBase 
class AwsInfrastructureSecurityAuditAndReportingCrew():  
    """AwsInfrastructureSecurityAuditAndReporting crew""" 
    def __init__(self) -> None: 
        self.llm = LLM( model=os.getenv('MODEL'),
        aws_access_key_id=os.getenv('AWS_ACCESS_KEY_ID'),
        aws_secret_access_key=os.getenv('AWS_SECRET_ACCESS_KEY'),
        aws_region_name=os.getenv('AWS_REGION_NAME') 
    )
```

### 第 2 步：定义 agent

这些 agent 已在 `agents.yaml` 文件中定义，我们在 crew.py 文件中把它们导入到各个 agent 函数中：

```
...
# Configure AI Agents

@agent 	 
def infrastructure_mapper(self) -> Agent:
    return Agent( 	 
        config=self.agents_config['infrastructure_mapper'],
        tools=[AWSInfrastructureScannerTool()],
        llm=self.llm 	 
    ) 	 	 

@agent 	 
def security_analyst(self) -> Agent:
    return Agent( 	 
        config=self.agents_config['security_analyst'], 	 
        tools=[SerperDevTool(), ScrapeWebsiteTool()],
        llm=self.llm 	 
    ) 	 	

@agent 	 
def report_writer(self) -> Agent: 	 
    return Agent( 	 
        config=self.agents_config['report_writer'], 	 
        llm=self.llm 	 
    )
```

### 第 3 步：为 agent 定义 task

与前面代码中的 agent 类似，我们把 `tasks.yaml` 导入到 `crew.py` 文件中：

```
...
# Configure Tasks for the agents

@task 
def map_aws_infrastructure_task(self) -> Task: 
    return Task( 
        config=self.tasks_config['map_aws_infrastructure_task']
    ) 

@task

class AWSInfrastructureScannerTool(BaseTool):
    name: str = "AWS Infrastructure Scanner"
    description: str = (
        "A tool for scanning and mapping AWS infrastructure components and their     configurations. "
        "Can retrieve detailed information about EC2 instances, S3 buckets, IAM configurations, "
        "RDS instances, VPC settings, and security groups. Use this tool to gather information "
        "about specific AWS services or get a complete infrastructure overview."
    )
    args_schema: Type[BaseModel] = AWSInfrastructureScannerInput

    def _run(self, service: str, region: str) -> str:
        try:
            if service.lower() == 'all':
                return json.dumps(self._scan_all_services(region), indent=2, cls=DateTimeEncoder)
            return json.dumps(self._scan_service(service.lower(), region), indent=2, cls=DateTimeEncoder)
        except Exception as e:
            return f"Error scanning AWS infrastructure: {str(e)}"

    def _scan_all_services(self, region: str) -> Dict:
        return {
            'ec2': self._scan_service('ec2', region),
            's3': self._scan_service('s3', region),
            'iam': self._scan_service('iam', region),
            'rds': self._scan_service('rds', region),
            'vpc': self._scan_service('vpc', region)
        }                                       
   
   # More services can be added here
