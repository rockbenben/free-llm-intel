# 借助 Amazon Bedrock Automated Reasoning checks 最大限度减少生成式 AI 幻觉

基础模型（Foundation models，FMs）与生成式 AI 正在改变各行各业的企业的运营方式。[McKinsey & Company](https://www.mckinsey.com/capabilities/mckinsey-digital/our-insights/the-economic-potential-of-generative-ai-the-next-productivity-frontier) 近期的研究估计，生成式 AI 每年可为全球经济贡献最高 4.4 万亿美元，其途径包括提升运营效率、实现每年 0.1% 至 0.6% 的生产率增长、通过个性化互动改善客户体验，以及加速数字化转型。

如今，企业在把生成式 AI 应用从实验环境推向生产环境时，仍在与 AI 幻觉作斗争。模型幻觉——即 AI 系统生成看似合理却不正确的信息——依然是首要关切。[2024 年 Gartner CIO 生成式 AI 调查](https://www.gartner.com/en/documents/5705151) 指出了三大风险：幻觉导致的推理错误（59% 的受访者）、恶意行为者制造的错误信息（48%），以及隐私担忧（44%）。

为了提升大语言模型（LLM）回答的事实准确性，AWS 在 AWS re:Invent 2024 上发布了 [Amazon Bedrock Automated Reasoning checks](https://aws.amazon.com/blogs/aws/prevent-factual-errors-from-llm-hallucinations-with-mathematically-sound-automated-reasoning-checks-preview/)（受限预览）。该功能通过基于逻辑的算法与数学验证，对照编码在 Automated Reasoning 策略中的领域知识来校验 LLM 输出，从而帮助预防事实性错误。Automated Reasoning checks 是 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 的一部分，后者是一个综合性框架，还提供内容过滤、个人可识别信息（PII）脱敏以及增强的安全措施。这些能力共同帮助组织落实可靠的生成式 AI 防护——其中 Automated Reasoning checks 负责事实准确性，而 Amazon Bedrock Guardrails 的其他功能则帮助防范有害内容、保护敏感信息。

本文将讨论如何借助 Amazon Bedrock Automated Reasoning checks 帮助预防生成式 AI 幻觉。

## Automated Reasoning 概述

Automated Reasoning 是计算机科学的一个专门分支，它运用数学证明技术与形式化逻辑演绎，在给定假设下以绝对的确定性验证对规则与要求的符合情况。随着组织越来越需要以数学上的确定性来验证复杂的规则与要求，自动推理技术提供了强大的能力。例如，AWS 客户可以直接使用基于自动推理的功能，如 [IAM Access Analyzer](https://docs.aws.amazon.com/IAM/latest/UserGuide/what-is-access-analyzer.html)、[S3 Block Public Access](https://aws.amazon.com/blogs/aws/amazon-s3-block-public-access-another-layer-of-protection-for-your-accounts-and-buckets/)，或 [VPC Reachability Analyzer](https://docs.aws.amazon.com/vpc/latest/reachability/what-is-reachability-analyzer.html)。

与机器学习中普遍存在的概率性方法不同，Automated Reasoning 依赖形式化数学逻辑，就什么能被证明、什么不能被证明给出确定的保证。这种做法类似于审计师核实财务报表、合规官验证监管要求时的严谨程度，但具有数学上的精确性。通过使用严谨的逻辑框架与定理证明方法，Automated Reasoning 能够在给定假设下确凿地判定陈述为真还是为假。这使它对于需要高保证度、且需要向用户给出明确无歧义结论的应用而言极具价值。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/27/ML-18268-image001-new.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image001.jpg)

Automated Reasoning 中广泛使用的一种技术是 SAT/SMT 求解，它把规则与要求的表示编码为逻辑公式。逻辑公式是一种数学表达式，用变量与逻辑运算符来表示条件与关系。规则与要求被编码进这些公式之后，会使用称为求解器（solver）的专门工具来计算满足这些约束的解。这些求解器判定公式是否可满足——即是否存在使公式为真的变量取值。

这一过程始于两类主要输入：以逻辑公式表达的系统形式化表示（例如代码或策略），以及待分析的属性（例如某些条件是否可能成立、要求能否被满足）。求解器可能返回三种结果之一：

- **可满足（Satisfiable）**——求解器找到一组使公式为真的取值赋值，证明系统能够满足给定要求。求解器会给出这组赋值，它可作为正确行为的具体示例。
- **不可满足（Unsatisfiable）**——求解器证明不存在使所有公式为真的赋值，从而证明这些要求无法被满足。这通常还会附带哪些约束相互冲突的信息，帮助找出系统中的错误假设。
- **未知（Unknown）**——在某些情况下，求解器可能无法在合理的计算限度内判定可满足性，或者编码中可能没有足够的信息来得出结论。

这一技术确保你得到的要么是该属性成立的确认（附具体示例），要么是它无法被满足的证明（附冲突约束的信息），要么是需要重新表述或以不同方式分析该问题的提示。

## Automated Reasoning checks 的关键特性

Automated Reasoning checks 提供以下关键特性：

- **数学验证框架**——该特性使用数理逻辑演绎来校验 LLM 输出。与概率性方法不同，它使用可靠的数学方法来就在既定参数范围内的系统行为给出确定的保证。
- **基于策略的知识表示**——组织可以创建 Automated Reasoning 策略，把自身的规则、流程与指南编码为结构化、数学化的格式。组织可以上传包含 HR 指南或运营工作流的 PDF 等文档，这些文档随后会被自动转换为形式化逻辑结构。策略变更会自动以唯一的 Amazon Resource Name（ARN）进行版本化，从而支持变更跟踪、审计与回滚能力，以维持策略执行的一致性。
- **赋能领域专家**——该特性旨在让 HR 人员或运营管理者等领域专家无需技术中介即可直接编码其知识。这确保业务规则与策略由最了解它们的人准确捕获与维护。
- **自然语言到逻辑的转换**——系统采用两种互补的方法：LLM 负责自然语言理解，符号推理引擎执行数学验证。这种混合架构让用户能够以平实语言输入策略，同时保持数学上严谨的验证。
- **可解释的验证结果**——每次校验都会产生详细的核查结果（finding），指明内容是有效（Valid）、无效（Invalid）还是无数据（No Data）。该特性为其判定提供清晰的解释，包括抽取出的事实陈述，以及针对无效内容的修改建议。
- **交互式测试环境**——用户可以在 Amazon Bedrock 控制台访问聊天测试场，实时测试与打磨策略。该特性既支持通过 Amazon Bedrock 控制台进行交互式测试，也支持通过 API 集成进行自动化测试，并能以 JSON 格式导出测试用例，以便集成到持续测试流水线或文档工作流中。
- **无缝的 AWS 集成**——该特性直接与 Amazon Bedrock Guardrails 集成，可与其他可配置的防护措施（如 Contextual Grounding checks）搭配使用。它既可通过 Amazon Bedrock 控制台访问，也可通过 API 访问，因而能灵活适应各种实施需求。

这些特性结合在一起构成了一个强大的框架，帮助组织在 AI 应用中维持事实准确性，同时提供透明且数学上可靠的验证过程。

## 解决方案概览

了解了 Automated Reasoning checks 的关键特性之后，我们来看看这项能力在 Amazon Bedrock Guardrails 中是如何运作的。下一节将全面概述其架构，并展示各组件如何协同工作，以提升事实准确性、帮助预防生成式 AI 应用中的幻觉。

Amazon Bedrock Guardrails 中的 Automated Reasoning checks 提供了一套端到端方案，基于数学上可靠的原理来校验 AI 模型输出。这一自动化过程使用形式化逻辑与数学证明，对照既定策略验证回答，给出确定的验证结果，可显著提升 AI 应用的可靠性。

下面的解决方案架构遵循一套系统化的工作流，可实现对模型输出的严格校验。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image002.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image002.png)

该工作流包含以下步骤：

- 源文档（例如 HR 指南或操作流程）被上传到系统。这些文档连同可选的意图描述一起被处理，生成结构化的规则与变量，构成 Automated Reasoning 策略的基础。
- 领域专家审阅并检查所创建的策略，核实业务规则是否被准确表达。每个通过校验的策略都会被版本化，并被分配唯一的 ARN，以便跟踪与治理。
- 通过校验的 Automated Reasoning 策略与 Amazon Bedrock Guardrails 关联，可在其中选择具体的策略版本用于实施。这一集成实现了对生成式 AI 输出的自动校验。
- 当生成式 AI 应用产生回答时，Amazon Bedrock Guardrails 会触发 Automated Reasoning checks。系统为输入问题与应用的回答分别创建逻辑表示，并对照既定策略规则进行评估。
- Automated Reasoning 检查提供详细的验证结果，包括陈述是有效、无效还是无数据。对每一项核查结果，它会解释考虑了哪些规则与变量，并提供把无效陈述变为有效的建议。

有了这套解决方案架构，组织可以放心地部署生成式 AI 应用，因为回答会基于数学上可靠的原理、对照你既定的策略被自动校验。

## 使用 Amazon Bedrock 控制台启动 Automated Reasoning 检查

第一步是把你的知识——在此即 LoAP 策略样例——编码为一个 Automated Reasoning 策略。请完成以下步骤，以通过 Amazon Bedrock 控制台启动 Automated Reasoning 检查：

- 在 Amazon Bedrock 控制台上，在导航窗格的 **Safeguards** 下选择 **Automated Reasoning Preview **。
- 选择 **Create policy**。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image004.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image004.jpg)

- 填写策略名称与策略描述。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image005.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image005.jpg)

- 上传你的源文档。源内容在创建后无法修改，且不得超过 6,000 个字符，同时对表格大小与图像处理也有限制。
- 说明你正在创建的 Automated Reasoning 策略的意图。对于示例策略，可以使用以下意图：

```
Create a logical model of the Leave of Absence, Paid (LoAP) policy in this document.
Employees will ask questions about what are the eligibility requirements for the program,
whether they are allowed to take LOAP and for how long, duration and benefits during the
time off, and return to work. 
Below is an example question:
QUESTION: I am a temporary contractor working in operations. Am I eligible for LOAP?
ANSWER: No, only full-time employees are eligible for LoAP.
```

策略创建过程需要几分钟才能完成。规则与变量会在策略创建完成后生成，它们可以被编辑、删除，也可以为其添加新的规则或变量。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image006.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image006.jpg)[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image007.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image007.jpg)

策略文档版本在详细信息部分列出，同时还有意图描述与构建状态。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image008.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image008.jpg)

接下来，你在 Amazon Bedrock 中按需配置过滤器来创建护栏。

- 在 Amazon Bedrock 控制台上，在导航窗格的 **Safeguards ** 下选择 **Guardrails**。
- 选择 **Create guardrail**。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image009.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image009.jpg)

- 填写护栏的详细信息，例如名称与可选的描述。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image010.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image010.jpg)

- 通过选择 **Enable Automated Reasoning policy** 添加 Automated Reasoning 检查，并选择策略名称与版本。
- 选择 **Next ** 并完成护栏的创建。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image011.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image011.jpg)

- 返回 Amazon Bedrock 控制台的 Automated Reasoning 部分，打开新建的策略。你可以使用测试场，输入能代表真实用户与 LLM 交互的示例问题与回答。
- 选择你创建的护栏，然后选择 **Submit**，评估你的策略如何处理这些问答交互。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image012.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image012.jpg)

提交之后，你会看到一个或多个核查结果（finding）。一项核查结果包含一组从输入问答中抽取出来的事实，这些事实会被独立分析。每项核查结果包含四个关键组成部分：

- **验证结果**——显示 Automated Reasoning checks 的结论。系统通过对照你定义的策略规则评估抽取出的变量赋值来确定这些结果。
- **应用的规则**——显示你的策略中用于得出验证结论的具体规则。
- **抽取的变量**——列出在验证过程中被识别并使用的变量。
- **建议**——显示能让无效回答变为有效的变量赋值；对于有效回答，则指明必要的假设。这些内容可用于为你的 LLM 生成反馈。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image013.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/23/ML-18268-image013.jpg)

最后，你可以利用这些反馈建议来改进 LLM 的回答。

- 从带建议的有效结果与无效结果中收集规则。
- 把这些收集到的变量与规则反馈给 LLM，让它修订原有回答。
- 打磨你的策略：用自然语言编辑不正确的规则。当 Automated Reasoning checks 无法为变量赋值时，改进变量描述。要让变量描述有效，应同时包含技术定义与用户的常见表述。例如，对于名为 `is_full_time, "works more than 20 hours per week"` 的变量，从技术上讲这是正确的，因为这是源策略中的原话，但这无助于 Automated Reasoning checks 理解用户说“part-time”时是什么意思。应改用 `"works more than 20 hours per week; set to true if user says 'full-time' and false if user says 'part-time'"`。

## 使用 Python SDK 与 API 启动 Automated Reasoning 检查

首先，你需要按上一节所述，使用 Amazon Bedrock 控制台从文档创建 Automated Reasoning 策略。接下来，你可以使用借助 `ApplyGuardrail` API 创建的策略来校验你的生成式 AI 应用。

要使用 Python SDK 通过 Automated Reasoning checks 进行校验，请按以下步骤操作：

- 首先，设置所需的配置：

```
import boto3
import botocore
import os
import json

# Configuration parameters
DEFAULT_GUARDRAIL_NAME = "<YOUR_GUARDRAIL_NAME>"  # e.g., "my_policy_guardrail"
DEFAULT_AR_POLICY_VERSION = "1"

# AWS configuration
region = "us-west-2"
ar_policy = "<YOUR_AR_POLICY_ID>"  # e.g., "ABC123DEF456"
```

```
    """
    Finds the ID and version of a guardrail by its name.
    
    Args:
        client: The Bedrock client object
        name (str): Name of the guardrail to find

        tuple[str, str]: Guardrail ID and version if found, None otherwise

        ) if next_token is None else client.list_guardrail(nextToken=next_token)

        # Search for matching guardrail

                return g["id"], g["version"]

        # Handle pagination
        if "nextToken" in resp and resp["nextToken"] != "":
            next_token = resp["nextToken"]
        else:
            break
    return None, None
```

## 实施最佳实践

要成功实施 Automated Reasoning checks，需要细致入微并采用系统化的方法，才能获得最佳的校验准确性与可靠结果。以下是一些关键最佳实践：

- **文档准备**——使用结构化的文本型 PDF 文档。内容应限制在 6,000 个字符以内。避免可能干扰逻辑模型生成的复杂格式。
- **意图描述工程**——用清晰的格式编写精确的策略意图。意图应全面覆盖预期用例与潜在边界情况。例如：`Create a logical model for [USE CASE] with policy rules. Users will ask questions about [SPECIFIC TOPICS]. Example Q&A: [INCLUDE SAMPLE].`
- **策略校验**——审阅生成的规则与变量，确保它们准确表达你的业务逻辑与策略要求。定期审计这些规则有助于保持与当前业务策略一致。
- **全面测试**——在测试场中设计多样化的示例问答，以评估不同的校验场景（有效、有效但带建议、以及无效回答）。加入边界情况与复杂场景，以提供稳健的校验覆盖。
- **迭代改进**——根据校验反馈定期更新规则与 LLM 应用，特别关注被建议的变量与无效结果，以提升回答准确性。维持反馈闭环以持续打磨。
- **版本控制管理**——对策略版本化采取系统化方法，维护详细的变更文档，并在部署新版本之前进行充分测试。这有助于跟踪策略演进，并在需要时便于回滚。
- **错误处理策略**——制定一份全面的计划来处理不同的校验结果，包括管理无效回答的具体流程，以及把建议的改进纳入回答生成过程。
- **运行时优化**——理解并监控两步校验过程（事实抽取与逻辑校验）以达到最佳性能。定期审阅校验结果，找出可能表明需要改进变量描述或规则定义的模式。
- **反馈整合**——建立系统化的流程来收集与分析校验反馈，尤其关注返回 NO_DATA 的情形，或事实性主张被错误抽取的情形。利用这些信息持续改进变量描述与策略规则。
