# Thomson Reuters 如何用 Amazon Bedrock AgentCore 打造 Agentic Platform Engineering Hub

*本文与 Thomson Reuters 的 Naveen Pollamreddi 和 Seth Krause 合作撰写。*

[Thomson Reuters](https://www.thomsonreuters.com/en)（TR）是一家领先的 AI 与技术公司，致力于交付可信内容与工作流自动化解决方案。凭借 150 多年的专业积累，TR 在快速演进的世界中为法律、税务、会计、风险、贸易与媒体等行业提供关键解决方案。AI 在 TR 扮演着关键角色。它深植于 TR 帮助客户创建、增强、连接与交付可信信息的方式之中。它支撑着全球专业人士所使用的产品。TR 的 AI 以专业级 AI 武装专业人士，帮助他们厘清复杂难题。

本文介绍 TR 的平台工程（Platform Engineering）团队——一个地理上分散、负责 TR 服务可用性的团队——如何借助 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 从手工流程转向自动化的 agentic 系统，从而提升运营生产力。

## 业务挑战

平台工程团队要为内部客户规模化提供无缝的自助式体验，在数据库管理、信息安全与风险管理（ISRM）运营、landing zone 维护、基础设施配置、密钥管理、持续集成与部署（CI/CD）pipeline 编排、合规自动化等运营活动中面临重大挑战。在 TR，平台工程团队通过提供关键云基础设施与赋能服务（包括云账户开通与数据库管理）支撑多条业务线。然而，手工流程以及运营任务在各团队之间反复协调的需求造成了延迟，拖慢了创新。

“*我们的工程师花了大量时间在不同团队之间回答同样的问题、执行完全相同的流程，*”TR 的 Distinguished Engineer Naveen Polalmreddi 说。“*我们需要一种方式，在保持安全与合规标准的同时把这些交互自动化。*”

## 现状

平台工程团队为 TR 内部的多个产品团队（包括 Product Engineering 与 Service Management）提供服务。这些团队把这些内部自研解决方案作为服务来消费，以便在 AWS 服务上大规模构建并运行应用。经过一段时间，这些服务不仅作为工具提供，也通过 TR 的内部流程提供，遵循 Information Technology Infrastructure Library（ITIL）标准，并使用第三方软件即服务（SaaS）系统。

其中一些服务依赖人工执行一组预定义步骤，且被重复许多次，造成对工程师的显著依赖：他们要针对多个应用反复执行相同任务。当前流程是半自动化的，具体表现为：

- **重复且耗费人力** – 由于工作流的性质以及多团队协作模式，这些运营流程往往劳动密集且重复。平台工程团队花了大量时间做无差异的重体力活。
- **实现价值周期更长** – 由于流程之间存在相互依赖，这些运营工作流并非完全自主，与完全自动化的流程相比，要花很长时间才能兑现价值。
- **资源与成本密集** – 手工执行需要专门的工程资源，而这些时间本可以更好地用于创新而非重复任务。每个运营请求都会在多个团队中消耗工程师工时，用于协调、执行与验证。

平台工程团队正在通过构建自主的 agentic 解决方案来解决这个问题：在多个服务领域与团队中使用专用 agent。云账户开通 agent 按内部标准自动完成新云账户的创建与配置，处理诸如建立组织单元、套用安全策略、配置基线网络等任务。数据库补丁 agent 管理端到端的数据库补丁生命周期与版本升级。网络服务 agent 处理网络配置请求，例如 VPC 搭建、子网分配以及环境之间的连通性建立。架构评审 agent 协助依据最佳实践、安全需求与合规标准评估拟定架构，提供自动化的反馈与建议。AgentCore 则作为这些 agent 的基础编排层，提供实现智能决策、自然语言理解、工具调用与 agent 之间（A2A）通信的核心 agentic 能力。

## 解决方案概览

TR 的平台工程团队以可扩展性、可延展性与安全性为核心原则构建了该方案，并使其设计能让非技术用户快速创建并部署由 AI 驱动的自动化。该架构面向广泛的企业受众设计，让业务用户通过基本的自然语言请求即可与专用 agent 交互，无需理解底层的技术复杂性。TR 选择 Amazon Bedrock AgentCore，因为它提供了大规模构建、部署与运营企业级 AI agent 所需的完整基础基础设施，省去了从零自建这套基础设施的工作。平台工程团队由此获得了用自己偏好的框架进行创新的灵活性，同时让其自主 agent 以企业级的安全性、可靠性与可扩展性运行——这是在规模化生产环境中管理运营工作流的关键要求。

TR 使用 AgentCore 构建了一个由 AI 驱动的平台工程中枢。该方案包含：

- 一个自定义 Web 门户，用于更安全的 agent 交互
- 一个中央编排 agent，负责路由请求并管理交互
- 多个服务专用 agent，处理诸如 AWS 账户开通与数据库补丁等专门任务
- 一个人机协同（human-in-the-loop）校验服务，用于敏感操作

TR 决定采用 AgentCore，因为它帮助其开发者借助全托管服务从原型加速走向生产：既把基础设施的复杂性降到最低，又能用不同的框架、模型与工具构建 AI agent，同时完全掌控 agent 的运作方式以及它们与既有系统的集成方式。

## 解决方案工作流

团队采用以下工作流来开发并部署这套 agentic AI 系统。

- 发现与架构规划：评估既有 AWS 资源与代码库，设计一套纳入 AgentCore 的完整方案，聚焦服务目标与集成需求。
- 核心开发与迁移：采用双轨推进，一边把既有方案迁移到 AgentCore，一边构建 TRACK（部署引擎）以实现 agent 的快速创建。实现了注册表系统，作为 agent 与编排器之间的模块化桥梁。
- 系统增强与部署：完善编排器功能，开发直观的 UX，并执行团队导入流程以完成新 agentic 系统的部署。

### 构建编排器 agent

TR 的平台工程团队把他们的编排器服务（名为 Aether）设计为基于 [LangGraph](https://www.langchain.com/langgraph) 框架的模块化系统。编排器从其 agent 注册表获取上下文，以判定每种情形应使用哪个 agent。当需要某个 agent 执行动作时，编排器会发起一次工具调用，以代码方式填入注册表中的数据，从而帮助防范潜在的 prompt injection 攻击，并让各端点之间的通信更安全。

为了在保持系统无状态的同时维持对话上下文，编排器在会话级与用户级两个层面集成了 [AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html) 服务能力。短期记忆维持单次会话内的上下文，长期记忆则随时间跟踪用户偏好与交互模式。这种双记忆方式让系统能够从过往交互中学习，避免重复以往的错误。

### 服务 agent 开发框架

平台工程团队开发了自己的框架 TR-AgentCore-Kit（TRACK），以简化全组织的 agent 部署。TRACK 是一套自研方案，使用了 [Bedrock AgentCore Starter Toolkit](https://github.com/aws/bedrock-agentcore-starter-toolkit) 的定制版本。团队对该工具包做了定制，以满足 TR 特定的合规对齐要求，其中包括资产标识标准与资源标签标准。该框架负责连接 [AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)、工具管理、[AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 连通性以及基线 agent 配置，让开发者可以专注于实现业务逻辑，而不必处理基础设施层面的问题。AgentCore Gateway 为开发者提供了一种直接且更安全的方式，用于大规模构建、部署、发现与连接工具。TRACK 还通过在自建的 A2A 注册表中部署 agent card，来处理服务 agent 向 Aether 环境的注册。TRACK 把向 AWS 部署与向自建服务注册打包为一体，为开发者保持了无缝的流程。通过把 agent card 部署到注册表，服务团队构建的 agent 要完成全面接入，只需继续走该流程，便能让该 agent 从顶层编排器处可用。

### Agent 发现与注册系统

为了实现无缝的 agent 发现与通信，TR 使用 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 与 [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 实现了一套自定义的 A2A 方案。该系统支持跨账户的 agent 调用，这对他们的模块化架构至关重要。注册流程通过 TRACK 项目进行，团队可以直接把自己的 agent 注册到编排器服务。A2A 注册表会完整保留 agent 版本历史以供审计，并在允许新 agent 进入生产环境之前要求人工验证。这一治理模型在帮助符合 TR 的 ISRM 标准的同时，也为未来的扩展保留了灵活性。

### Aether Web 门户集成

团队使用 React 开发了一个 Web 门户，托管在 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）之上，为 agent 交互提供更安全、更直观的界面。该门户基于 TR 的企业单点登录（SSO）对用户进行身份认证，并按用户权限开放相应的 agent 流程。这一做法有助于确保诸如 AWS 账户开通或数据库补丁之类的敏感操作只有获授权人员才能访问。

### 人机协同校验服务

系统包含 Aether Greenlight，这是一个校验服务，确保关键操作获得适当的人工监督。该服务超出了基本的请求者审批范畴，让初始对话之外的团队成员也能参与校验过程。系统为审批与操作保留完整的审计留痕，以支撑 TR 的合规要求。

## 成果

通过在 AgentCore 上构建自助式 agentic 系统，TR 落地了一批自主 agent，它们利用 AI 编排端到端处理复杂的运营工作流。

**生产力与效率**

- 通过日常任务的智能自动化实现 **生产力提升 15 倍**
- 首次上线即实现 **70% 自动化率**，大幅降低人工工作量
- 由 agent 全天候执行可重复 runbook 带来的 **持续可靠性**

**速度与敏捷性**

- **更快的价值兑现**：通过自动化环境搭建、策略执行与日常运维，加速产品交付
- **自助式工作流**：以清晰的标准与铺好的路径工具赋能团队

**安全与合规**

- **更强的安全态势**：默认应用 guardrail 与数据库补丁
- **人机协同审批**：在自动化变更校验的同时保持监督

**成本与资源优化**

- **更好的成本效率：** 自动化的基础设施用量优化
- **战略性人才配置：** 让工程团队腾出精力专注于最高优先级、高价值的工作
- **减少运维苦工：** 通过标准化消除重复任务与偏差

**开发者体验**

- **更高的满意度：** 以直观的自助能力简化工作流
- **一致的标准：** 建立了可供其他团队采用并扩展的可重复模式

## 结语

本文描述的这套 agentic 系统建立了一个可复制的模式，组织内各团队都可用它来获得类似的自动化能力，为运营卓越带来乘数效应。Aether 项目旨在通过免去那些本可自动化任务的人工执行，来改善工程师的体验，从而支撑进一步的创新与创造性思考。随着 Aether 持续改进，团队希望这一模式能被更广泛地采用，开始帮助平台工程之外的团队在全组织范围突破生产力标准，从而巩固 TR 在人工智能时代领跑者的地位。

借助 Amazon Bedrock AgentCore，TR 把其平台工程运营从手工流程转变为由 AI 驱动的自助式中枢。这一做法不仅提升了效率，也强化了安全与合规管控。
