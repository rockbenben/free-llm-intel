# 使用 Amazon Bedrock Knowledge Bases 构建多租户 RAG

组织一直在不断寻找利用其专有知识和领域专长获取竞争优势的方法。随着基础模型（FM）的出现及其卓越的自然语言处理能力，一个释放数据资产价值的新机会已经出现。

当组织力求使用生成式 AI 为客户提供个性化体验时，用自己的数据以及客户的数据来定制 FM 的行为就变得至关重要。[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）已成为一种简单而有效的方法，用以达到所需的定制程度。

[Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 是一项完全托管的能力，可简化整个 RAG 工作流的管理，让组织能够为 FM 和 agent 提供来自公司私有数据源的上下文信息，从而交付更贴合其特定需求的、更相关、更准确的回答。

对于开发多租户产品的组织，例如创建软件即服务（SaaS）产品的独立软件供应商（ISV），为每个客户（其 SaaS 应用中的租户）个性化体验的能力尤为重要。这种个性化可以通过实施有选择地使用租户特定数据的 RAG 方式来实现。

本文讨论并举例说明如何使用 Amazon Bedrock Knowledge Bases 实现个性化。我们尤其关注应对 ISV 面临的多租户挑战，包括数据隔离、安全性、租户管理和成本管理。我们聚焦于 RAG 架构集成在 ISV 应用中、而不直接暴露给租户的场景。尽管本文给出的具体实现使用 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 作为向量数据库来存储租户数据，但这里提出的挑战与架构方案可以扩展并适配到其他向量存储实现，包括 [Amazon S3 Vectors](https://aws.amazon.com/s3/features/vectors/) 和 [Amazon OpenSearch Managed Clusters](https://aws.amazon.com/opensearch-service/features/managed/)。

## 多租户设计考量

在为多租户 RAG 系统做架构设计时，组织需要考虑若干因素：

- **租户隔离** – 设计多租户系统时的一项关键考量，是与每个租户相关的数据和资源之间的隔离程度。这些资源包括数据源、摄取 pipeline、向量数据库和 RAG 客户端应用。隔离程度通常由解决方案的安全性、性能和可扩展性要求以及你的监管要求共同决定。例如，你可能需要用不同的加密密钥加密每个租户相关的数据。你可能还需要确保某个租户产生的高活动量不会影响其他租户。

- **租户差异化** – 一个相似但不同的考量，是提供给每个租户的功能的差异化程度。在 RAG 系统的语境下，租户对数据摄取频率、文档分块策略或向量搜索配置可能有不同要求。

- **租户管理简易性** – 多租户解决方案需要一套租户上线与下线的机制。这一维度决定了该流程的复杂程度，其中可能涉及置备或拆除租户专属基础设施，例如数据源、摄取 pipeline、向量数据库和 RAG 客户端应用。该流程还可能涉及在其数据源中增加或删除租户特定数据。

- **成本效率** – 多租户解决方案的运行成本取决于它为租户提供隔离机制的方式，因此为该解决方案设计一个成本高效的架构至关重要。

这四项考量需要仔细平衡与权衡，以适应具体解决方案的需求。本文提出一个模型来简化决策过程。我们借助 [SaaS 租户隔离策略白皮书](https://docs.aws.amazon.com/whitepapers/latest/saas-tenant-isolation-strategies/core-isolation-concepts.html)中定义的孤岛（silo）、共享池（pool）和桥接（bridge）三种核心隔离概念，提出了三种使用 Amazon Bedrock Knowledge Bases、[Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）和 OpenSearch Service 实现多租户 RAG 解决方案的模式。

一个使用 Amazon Bedrock Knowledge Bases 的典型 RAG 解决方案由若干组件构成，如下图所示：

- 一个数据源，例如一个 S3 桶

- 一个知识库，其中包含一个数据源

- 一个向量数据库，例如一个 [Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/) 集合与索引，或[其他受支持的向量数据库](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-setup.html)

- 一个 RAG 客户端应用

![典型 RAG 解决方案架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/05/ML-17210-image-1.jpg)

将这一架构适配到多租户的主要挑战，在于确定如何为每个组件在租户之间提供隔离。我们提出了三种规范化的模式，以适应不同的用例，并在隔离性、差异化、管理简易性和成本效率方面提供不同程度的支持。下图展示了这三种架构模式在实现租户隔离、差异化、成本效率和租户管理易用性方面的取舍。

## 多租户模式

本节我们描述这三种不同的多租户模式在基于 Amazon Bedrock Knowledge Bases 的 RAG 架构中的实现，并讨论它们的用例及其优缺点。

### 孤岛（Silo）

下图所示的孤岛模式提供最高级别的租户隔离，因为整个技术栈都是为每个单一租户独立部署和管理的。

![孤岛模式的解决方案架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/05/ML-17210-image-3.png)

在 Amazon Bedrock Knowledge Bases 实现的 RAG 架构语境下，该模式规定如下：

- **每个租户一个独立的数据源** – 本文考虑将需要向量化的租户文档存放在 Amazon S3 中的场景，因此为每个租户置备一个独立的 S3 桶。这样就能使用按租户划分的 [AWS Key Management Service](https://aws.amazon.com/kms)（AWS KMS）加密密钥，以及按租户划分的 S3 生命周期策略（用于管理对象到期）和对象版本控制策略（用于维护对象的多个版本）。每个租户使用独立的桶可以提供隔离，并允许基于租户需求进行定制配置。

- **每个租户一个独立的知识库** – 这样可以按租户设置不同的分块策略，如果你预计各租户的文档基础在性质上不同，这一点尤其有用。例如，某个租户的文档基础可能由纯文本文档构成，可以用固定大小分块处理；而另一个租户的文档基础可能带有明确的章节，对这种情况语义分块更适合按节切分。每个租户使用不同的知识库也让你可以决定不同的 embedding 模型，从而能够选择不同的向量维度，在准确性、成本和延迟之间取得平衡。你可以为临时数据存储为每个租户选择不同的 KMS 密钥，Amazon Bedrock 用它来实现端到端的按租户加密。你还可以选择按租户的数据删除策略，以控制在删除知识库时是否从向量数据库中删除你的向量。独立的知识库还意味着你可以为每个租户设置不同的摄取计划，从而能够与客户约定不同的数据新鲜度标准。

- **每个租户一个独立的 OpenSearch Serverless 集合** – 每个租户一个独立的 OpenSearch Serverless 集合，让你可以为每个租户使用独立的 KMS 加密密钥，保持按租户的端到端加密。对每个租户专属集合，你可以创建一个独立的向量索引，从而为每个租户在欧氏距离和点积之间选择距离度量，以便决定对文档长度赋予多少重要性。你还可以为每个租户选择 HNSW 算法的具体设置，以控制内存消耗、成本和索引时间。每个向量索引配合知识库中元数据映射的设置，可以为每个租户设置不同的元数据集，用于执行带过滤的搜索。在孤岛模式中，元数据过滤可用于把搜索限制到具有特定特征的一部分文档。例如，某个租户可能上传带日期的文档，希望按特定年份过滤文档；而另一个租户可能上传来自不同公司部门的文档，希望按某个特定公司部门的文档进行过滤。

由于孤岛模式提供了租户在架构上的独立性，让一个租户上线和下线就意味着为该租户创建和销毁 RAG 技术栈，包括 S3 桶、知识库和 OpenSearch Serverless 集合。你通常会使用基础设施即代码（IaC）来完成。视你的应用架构而定，你可能还需要为每个租户更新日志接收端和监控系统。

尽管孤岛模式提供了最高级别的租户隔离，但它也是实现成本最高的，主要原因是需要为每个租户创建一个独立的 OpenSearch Serverless 集合，理由如下：

- **最低容量费用** – 每个 OpenSearch Serverless 集合都有一个最低容量的 [OpenSearch Compute Units](https://aws.amazon.com/opensearch-service/pricing/)（OCU），具体取决于冗余设置。启用冗余时最低为 2 个 OCU，禁用冗余时最低降到 1 个 OCU。此外，OpenSearch Serverless 现在支持缩容到零（scale-to-zero），可以为闲置租户消除空闲计算成本。当使用按租户的 KMS 加密密钥时，在孤岛模式和桥接模式之间做选择时请考虑每个租户的这些成本。

- **可扩展性开销** – 每个集合会根据使用情况分别以 6 GB 内存为步长扩缩 OCU，以及相应的 vCPU 和快速访问存储。这意味着资源可能无法在租户之间被充分、最优地利用。

选择孤岛模式时请注意，每个 AWS 账户最多支持 100 个知识库。这使得孤岛模式更适合那些有特定隔离要求的最大型租户。每个租户一个独立的知识库也降低了配额对并发摄取作业（每个 KB 最多一个并发作业，每账户五个）、作业大小（每个作业 100 GB）和数据源（每个数据源最多 500 万份文档）的影响。它还能改善租户所感知的性能公平性。

 在租户下线时删除知识库可能比较耗时，这取决于数据源的大小和同步过程。为缓解这一点，你可以把租户知识库中的数据删除策略设置为 `RETAIN`。这样，删除知识库的流程就不会从 OpenSearch Service 索引中删除租户数据。你可以通过删除 OpenSearch Serverless 集合来删除该索引。

### 共享池（Pool）

与孤岛模式相反，在下图所示的共享池模式中，整个端到端 RAG 架构由你的租户共享，这使它特别适合承载大量小型租户。

![共享池模式的解决方案架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/05/ML-17210-image-4.png)

共享池模式规定如下：

- **单一数据源** – 租户数据存储在同一个 S3 桶中。这意味着共享池模式支持用于静态加密的共享 KMS 密钥，无法提供按租户加密密钥的可能。为了在下游识别上传到 Amazon S3 的每份文档的租户归属，必须生成并上传一个对应的 JSON 元数据文件。元数据文件的生成过程可以是异步的，甚至可以对多个文件批量处理，因为 Amazon Bedrock Knowledge Bases 需要显式触发摄取作业。元数据文件必须与其关联的源文档文件同名，并在文件名末尾追加 `.metadata.json`，且必须存储在 S3 桶中与源文件相同的文件夹或位置。以下代码是一个格式示例：

```
{
  "metadataAttributes" : {
    "tenantId" : "tenant_1",
  ...
  }
}
```

在上面的 JSON 结构中，`tenantId` 键是特意选定的，可以改成你希望用来表达租户归属的任意键。租户字段将在运行时用于过滤属于特定租户的文档，因此运行时的过滤键必须与用于索引文档的 JSON 中的元数据键一致。此外，你还可以加入其他元数据键，以执行并非基于租户归属的进一步过滤。如果你不上传 `object.metadata.json` 文件，客户端应用就无法通过元数据过滤找到该文档。

- **单一知识库** – 创建一个单一知识库来处理你的租户的数据摄取。这意味着你的租户将共享相同的分块策略和 embedding 模型，并共享相同的静态加密 KMS 密钥。此外，由于摄取作业是按每个 KB 的每个数据源触发的，你只能向租户提供相同的数据新鲜度标准。

- **单一 OpenSearch Serverless 集合与索引** – 你的租户数据被池化在单个 OpenSearch Service 向量索引中，因此租户共享相同的向量数据 KMS 加密密钥，以及相同的索引和查询 HNSW 参数。由于租户数据在物理上没有隔离，查询客户端能够为单个租户过滤结果就至关重要。这可以通过 Amazon Bedrock Knowledge Bases 的 `Retrieve` 或 `RetrieveAndGenerate` 高效实现，把租户过滤条件表达为 retrievalConfiguration 的一部分（更多细节参见 [Amazon Bedrock Knowledge Bases 现已支持元数据过滤以提升检索准确性](https://aws.amazon.com/blogs/machine-learning/knowledge-bases-for-amazon-bedrock-now-supports-metadata-filtering-to-improve-retrieval-accuracy/)）。如果你想把向量搜索限制为只返回 `tenant_1` 的结果，下面是一个基于 [AWS SDK for Python (Boto3)](https://boto3.amazonaws.com/v1/documentation/api/latest/reference/services/bedrock-agent-runtime/client/retrieve_and_generate.html) 执行 `RetrieveAndGenerate` 的客户端实现示例：

```
import boto3

bedrock_agent_runtime = boto3.client(
    service_name = "bedrock-agent-runtime"
)

tenant_filter = {
    "equals": {
        "key": "tenantId",
        "value": "tenant_1"
    }
}

retrievalConfiguration = {
    "vectorSearchConfiguration": {
        "filter": tenant_filter
    }
}

bedrock_agent_runtime.retrieve_and_generate(
    input = {
        'text': 'The original user query'
    },
    retrieveAndGenerateConfiguration = {
        'type': 'KNOWLEDGE_BASE',
        'knowledgeBaseConfiguration': {
            'knowledgeBaseId': <YOUR_KNOWLEDGEBASE_ID>,
            'modelArn': <FM_ARN>,
            'retrievalConfiguration': retrievalConfiguration
        }
    }
)
```

`text` 包含需要被回答的原始用户查询。结合文档基础，`<YOUR_KNOWLEDGEBASE_ID>` 需要替换为用于池化租户的知识库标识符，`<FM_ARN>` 需要替换为你希望用来回复用户查询的 Amazon Bedrock 模型 Amazon Resource Name（ARN）。上述代码中的客户端经过精简，以展示租户过滤功能。在生产环境中，我们建议实现会话与错误处理、日志与重试逻辑，并把租户过滤逻辑与客户端调用分离，使开发者无法访问它。

由于这一模式中端到端架构是池化的，租户上线与下线不需要创建新的物理或逻辑构件，只需启动或停止，并把特定的租户文档上传到 Amazon S3。这意味着没有可用于端到端注销并彻底遗忘某个租户的 AWS 托管 API。要删除属于特定租户的历史文档，你只需删除 Amazon S3 中的相关对象。通常，客户会有一个外部应用来维护可用租户列表及其状态，以便于上线与下线流程。

在这一模式中共享监控系统和日志能力，可以降低管理大量租户时的运维复杂度。不过，它要求你从客户端侧采集租户特定的指标，以完成特定租户的归因。

共享池模式优化了你的 RAG 架构的端到端成本，因为跨租户共享 OCU 可以最大化每个 OCU 的利用率，并最小化租户的空闲时间。跨租户共享同一组 OCU 意味着该模式在向量存储层面不提供性能隔离，因此规模最大、最活跃的租户可能会影响其他租户的体验。

为你的 RAG 架构选择共享池模式时，你应当知道单个摄取作业最多可以摄取或删除 100 GB。此外，数据源最多可以有 500 万份文档。如果解决方案有许多地理上分散的租户，考虑每天多次触发摄取作业，以免触及摄取作业大小上限。另外，视待同步文档的数量和大小，摄取时间将由 embedding 模型的调用速率决定。例如，考虑以下场景：

- 待同步的租户数 = 10

- 每个租户的平均文档数 = 100

- 每份文档的平均大小 = 2 MB，包含约 200,000 个 token，按每块 1,000 个 token 切分为 220 个分块以留出重叠

- 使用按需的 Amazon Titan Embeddings v2，允许 2,000 RPM 和 300,000 TPM

这将得到以下结果：

- embedding 请求总数 = 10*100*220 = 220,000

- 待处理的 token 总数 = 10*100*1,000=1,000,000

- 完成 embedding 所花的总时间由 RPM 主导，因此 220,000/2,000 = 1 小时 50 分钟

这意味着你可以每天触发 12 次摄取作业，以获得良好的待摄取数据时间分布。这一计算是最佳情况，没有考虑 FM 从分块创建向量时引入的延迟。如果你预计需要同时同步大量租户，考虑使用预置吞吐来减少创建向量 embedding 所需的时间。这种方式还有助于分散 embedding 模型上的负载，减少 Amazon Bedrock runtime API 调用被限流的情况。

### 桥接（Bridge）

下图所示的桥接模式在孤岛模式与共享池模式之间取得平衡，提供一个兼顾租户数据隔离与安全性的中间方案。

![桥接模式的解决方案架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/05/ML-17210-image-5.png)

桥接模式具备以下特点：

- **在同一个 S3 桶中为每个租户提供独立数据源** – 租户数据存储在同一 S3 桶中，但以租户标识符作为前缀。虽然每个租户使用不同前缀无法提供按租户加密密钥的可能，但它确实形成了逻辑隔离，可用于在知识库中下游隔离数据。

- **每个租户一个独立的知识库** – 这一模式规定为每个租户创建一个独立的知识库，与孤岛模式类似。因此孤岛模式中的考量同样适用。使用桥接模式构建的应用通常在租户之间共享查询客户端，因此它们需要识别要查询的特定租户的知识库。它们可以通过把租户到知识库的映射存放在一个用来管理租户特定配置的外部数据库中，来识别知识库。下面的示例展示了如何把这个租户特定信息存放在一个 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 表中：  `import boto3 # Create a DynamoDB resource dynamodb = boto3.resource('dynamodb') table_name = 'tenantKbConfig' attribute_definitions = [ {'AttributeName': 'tenantId', 'AttributeType': 'S'} ] key_schema = [ {'AttributeName': 'tenantId', 'KeyType': 'HASH'} ] #Create the table holding KB tenant configurations tenant_kb_config_table = dynamodb.create_table( TableName=table_name, AttributeDefinitions=attribute_definitions, KeySchema=key_schema, BillingMode='PAY_PER_REQUEST' # Use on-demand billing mode for illustration ) #Create a tenant tenant_kb_config_table.put_item( Item={ 'tenantId': 'tenant_1', 'knowledgebaseId': <YOUR_KNOWLEDGEBASE_ID>, 'modelArn': <FM_ARN>  } )`  在生产环境中，你的应用会在数据存储中存放属于其他功能的租户特定参数。视你的应用架构而定，你可能选择把 `knowledgebaseId` 和 `modelARN` 与其他租户特定参数放在一起，或者专门为你的 RAG 架构创建一个独立的数据存储（例如 `tenantKbConfig` 表）。这个映射随后可由客户端应用通过调用 `RetrieveAndGenerate` API 来使用。下面是一个示例实现：  `import json import boto3 # Create a DynamoDB resource dynamodb = boto3.resource('dynamodb') # Create a Bedrock Runtime client bedrock_runtime = boto3.client('bedrock-agent-runtime') # Define the table name table_name = 'tenantKbConfig' # Define function returning tenant config def get_tenant_config(tenant_id): table = dynamodb.Table(table_name) response = table.get_item( Key = { 'tenantId': tenant_id } ) if 'Item' in response: return { 'knowledgebaseId':response['Item'].get('knowledgebaseId'), 'modelArn': response['Item'].get('modelArn')} else: return None # Retrieve the tenant configurations from DynamoDB tenant_config = get_tenant_config('tenant_1') #Invoke the Retrieve and Generate API bedrock_runtime.retrieve_and_generate( input = { 'text': 'What type of info do your documents contain?' }, retrieveAndGenerateConfiguration = { 'type': 'KNOWLEDGE_BASE', 'knowledgeBaseConfiguration': { 'knowledgeBaseId': tenant_config['knowledgebaseId'], 'modelArn': tenant_config['modelArn'] } } )`

- **每个租户一个独立的 OpenSearch Service 索引** – 你把数据存储在同一个 OpenSearch Serverless 集合中，但为每个租户创建一个向量索引。这意味着你的租户共享相同的 KMS 加密密钥和同一组 OCU，从而优化 OpenSearch Service 资源在索引和查询上的使用。向量索引的隔离让你可以灵活地为每个租户选择不同的 HNSM 参数，从而为你不同的租户定制 k-NN 索引和查询的性能。

桥接模式最多支持 100 个租户，让一个租户上线和下线需要创建和删除一个知识库以及 OpenSearch Service 向量索引。要删除属于某个特定租户的数据，你可以删除已创建的资源，并在 Amazon S3 API 调用中把租户特定前缀作为逻辑参数使用。与孤岛模式不同，桥接模式不允许按租户的端到端加密；它在优化成本的同时，提供与孤岛模式相同程度的租户定制能力。

## 结语

本文探讨了使用 Amazon Bedrock Knowledge Bases 和 OpenSearch Service 实现多租户 RAG 架构的三种不同模式。孤岛、共享池和桥接模式提供不同程度的租户隔离、差异化、管理简易性和成本效率，适应不同的用例与需求。通过理解每种模式相关的取舍与考量，组织可以做出有依据的决策，并选择最契合自身需求的方式。
