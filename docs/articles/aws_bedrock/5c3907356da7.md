# First Orion 借助 Amazon Nova Act 加速 QA 自动化

*本文由 First Orion 的 Mark Himelfarb 与 Garrett Wilkerson 共同撰写。*

在 Amazon Nova Act 改变 QA 自动化之前，[First Orion](https://firstorion.com) 的各工程团队交付的速度已经超过了质量保证（QA）能够测试的速度。作为一家品牌通信公司，其解决方案覆盖美国、加拿大、英国和德国运营商网络上数亿通电话，First Orion 需要让 QA 跟上快速的开发节奏。解决方案是从基于脚本的测试自动化，转向由 AI 驱动、能像人一样理解 Web 界面的 agent。本文介绍 First Orion 如何采用 Amazon Nova Act、围绕它构建的架构，以及所取得的成果。

[First Orion](https://firstorion.com) 成立于 2008 年，秉持一个信念：每一次通信都应当清晰、可信、可识别。如今他们拥有 300 多名团队成员，办公室分布在小石城北部、西雅图、伦敦和迪拜。他们的解决方案运行在美国所有主要运营商网络上，包括 T-Mobile、Verizon、AT&T 与 [Boost Mobile](https://firstorion.com/press-releases/first-orion-boost-mobile-inform-branded-calling)，也运行在加拿大的主要运营商、英国的 [Vodafone](https://firstorion.com/press-releases/vodafone-uk-branded-calling-launch) 以及德国的 [Deutsche Telekom](https://firstorion.com/press-releases/first-orion-deutsche-telekom-branded-calling-germany) 网络上。随着他们的 [Global Exchange](https://firstorion.com/press-releases/first-orion-previews-april-2026-global-exchange) 推出，覆盖范围还在扩大。他们通过品牌呼叫、短信与身份解决方案帮助企业连接客户，同时保护双方免受垃圾信息、诈骗与号码伪造之害。他们的客户范围很广，从中小企业到全球性企业，其中包括财富 500 强公司。其产品套件覆盖完整的通信生命周期：[INFORM Branded Calling](https://firstorion.com/inform)、[ENRICH Branded Messaging](https://firstorion.com/enrich)、[AFFIRM Number Monitoring](https://firstorion.com/affirm)、[SENTRY Call Blocking](https://firstorion.com/sentry) 与 [PROTECT+ Risk Detection.](https://firstorion.com/products/protect-risk-detection)

他们相信通信的未来建立在信任、透明与智能技术之上，而创新是其战略的核心。他们投入 AI、对话智能与数据驱动平台，以持续改进品牌与客户互动的方式。这种增长带来了一个工程挑战。随着 First Orion 在企业客户之外向中小企业（SMB）市场扩张，他们的 Web 应用数量成倍增加，测试这些应用的 QA 负担也随之倍增。

## 去中心化的门户让 QA 团队应接不暇

First Orion 从单体 Web 门户迁移到去中心化、面向具体产品、模块化且基于单元（cell）的架构。在这种模式下，每个团队拥有自己业务线对应的应用，彼此只在一小块共享的底层平台上做同步。这让各团队可以并行、以更高速度推进，尽管这需要对平台进行大量重构才能支撑。与此同时，随着 First Orion 进一步深入 SMB 市场，客户所使用的设备形态与浏览器版本范围显著扩大，每个应用必须测试的组合也随之成倍增加。

UI 测试很快成为瓶颈。QA 团队无法跟上不断蔓延的 Web 应用集合，后果层层叠加：发布速度停滞，新功能以更低的质量交付，工程时间越来越多地被回归问题吞噬，而不是用于新能力。

First Orion 的 QA 团队中既有 QA 分析师，也有 QA 自动化工程师。自动化工程师依据测试用例定义与其他文档构建可长期维护的测试套件，而 QA 分析师专注于需求分析、测试用例定义、探索性测试与软件质量风险管理。但他们所依赖的现有测试自动化框架本身就十分脆弱，其中三个问题尤其拖慢了团队。

第一，回归测试无法自助完成。开发人员需要一种简单直接的方式，在把代码交付到测试环境之前，针对自己改动的路径运行回归测试，但现有的测试用例带有大量依赖，使其难以按需运行。

第二，新功能受困于测试用例的空档。要为某个新功能编写测试，就必须先把该功能开发完成并部署到测试环境，这样 QA 自动化工程师才能拿到他们在文档对象模型（DOM）中所需的选择器、标签与其他元素。这迫使 QA 分析师与工程师在等待期间切换到其他工作，而如此多的功能接连快速交付，结果是认知负担不断加重，还要不停地处理依赖关系。

第三，测试脚本本身很脆弱。QA 自动化工程师通常要等开发人员写完代码后才能拿到应用，而此时总是临近发布。当他们逐个处理 Selenium 与 Playwright 脚本时，元素 ID、class 以及其他 DOM 和 JavaScript 属性的变化速度超过了他们修复的速度。传统自动化对人工工作的补充速度不够快，无法在某个具体版本中发挥作用，发布因此可能被拖延。扩大 QA 团队规模只能在边际上有所帮助，却解决不了这个根本原因。

First Orion 意识到，他们需要的不是更多同类做法，而是一种根本不同的方法。与其编写代码去描述如何操作 UI，他们更希望用平实的英语描述要测什么，让一个智能 agent 处理其余部分。这一需求把他们引向了 Amazon Nova Act。

## 为什么 Amazon Nova Act 契合 First Orion 的需求

First Orion 的需求最终归结为两个问题：基于选择器的测试会随 UI 变化而失效，以及编写新测试所需的时间。Nova Act 通过让 QA 分析师用平实的英语描述测试、而不必编写与维护代码，同时解决了这两个问题。2025 年 3 月，AWS 客户团队向他们介绍 Nova Act 时，First Orion 成为了预发布阶段的采用者，并在正式可用之前很久就发现了它的价值。

借助 Nova Act，First Orion 用自然语言描述他们想要达成什么，而不是如何达成。例如：「登录门户，进入账单页面，并核对发票总额。」agent 会推理当前的 UI 状态、识别元素，并自主执行多步序列。这是与 Selenium 和 Playwright 的关键区别。那些框架要求 QA 自动化工程师编写和维护显式的元素选择器，而它们每个 sprint 都会失效。Nova Act 则推理它在屏幕上看到的内容：标签、布局与上下文。像「点击 Submit 按钮」这样的 Nova Act 指令，无论底层的 CSS class 如何都能生效。模型会适应变化的页面布局、处理动态内容、关闭弹窗，并在无人干预的情况下从错误中恢复。开发者还可以把 Python 代码、断言、断点与并行化直接与 Nova Act 命令交织使用。

对 First Orion 而言，这意味着三件事：

- **QA 分析师可以直接编写测试**——无需等待自动化工程师把测试用例翻译成代码。
- **测试能够在 UI 变化中存活**——因为 Nova Act 不依赖固定选择器，脚本不再每个 sprint 都失效。
- **无需管理浏览器基础设施**——AgentCore Browser 负责预置、会话录制与并行执行。

## First Orion 如何使用 Nova Act

First Orion 使用 Amazon Nova Act 的主要场景是测试其客户门户应用。他们围绕 Amazon Nova Act SDK 构建了一套端到端系统，把 QA 分析师从用英语编写测试用例，一路带到自动化执行与集成报表。下图展示了该架构，我们将在下文中逐一介绍每个组件。

图 1：First Orion 的 Nova Act 测试自动化系统架构概览

工作流始于 Test Case Authoring UI，这是一个 React 前端，QA 分析师在这里用平实的英语浏览、创建、编辑与校验测试用例。一个自定义模板引擎处理动态变量（电话号码、电子邮件地址、企业名称），使同一套测试集合在每次运行时都生成独一无二且贴近真实的数据。测试集合以 JSON 形式存储在 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）中，后者充当中央存储库。

当 QA 分析师触发一次测试运行时，Nova Act Test Runner 会从 Amazon S3 取出测试用例。这个 runner 是运行在 [Amazon Elastic Container Service](https://aws.amazon.com/ecs/)（Amazon ECS）与 AWS Fargate 上的 Python 应用，通过 Amazon Nova Act SDK 编排执行。runner 并不直接管理浏览器，而是把浏览器操作委托给 [Amazon Bedrock AgentCore Browser](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html)。AgentCore Browser 负责预置托管的浏览器实例、处理会话录制，并支持在多因素身份验证（MFA）之后并行执行，而无需改动目标应用的身份验证流程。浏览器配置文件可以让测试从特定的浏览器状态启动，从而避免每次运行都走完整的登录流程。

Amazon Nova Act 模型从测试运行器接收自然语言指令，推理目标 Web 应用的当前 UI 状态，并自主执行指定的动作。Nova Act 自行处理浏览器操作，调用方代码无需管理选择器、等待或页面跳转。

结果流入一个 [Allure](https://allurereport.org/) 报表控制面板，并集成 Microsoft Teams 用于通知。First Orion 依靠 AgentCore 进行会话录制，并在报表中直接链接视频回放。Microsoft Teams 与 Allure 需要自定义集成。Nova Act 测试运行器使用一个 Python 脚本来编排 SDK 调用。

采用这套架构后，QA 团队与工程团队之间的集成更加紧密。随着更多测试进入 agentic 流程，对其他厂商的依赖随之缩小。First Orion 还采用 Kiro IDE 进行原型开发与日常开发。Kiro 内置的 AWS 服务知识以及读取代码库的能力，让把所有环节串起来变得简单直接。

下图展示了在 React UI 中编写的一个示例测试用例。QA 分析师用平实的英语编写指令（例如「进入 Billing 页面，核对发票总额与预期金额一致，然后下载 PDF」）。Amazon Nova Act SDK 在运行时把这些指令翻译成浏览器操作，既不需要元素选择器，也不要求测试作者具备编程知识。

在 Nova Act 之前，一名 QA 自动化工程师需要手动识别 DOM 选择器、编写脚本、调试脆弱的选择器，并反复迭代。这个过程每个测试用例可能要花上数天。有了这套架构，一名 QA 分析师拿同一个英文测试用例，几分钟内就能运行起来。在受支持的场景中，从定义测试用例到自动化运行的周期已从数天缩短到数分钟。

## 成果与影响

虽然 Amazon Nova Act 仍处于采用期，First Orion 也在它周围增加功能以贴合自身环境，但他们在特定类型的测试上已经把 QA 周期缩短了多达 20–25%。随着覆盖范围扩展到更多应用模块，他们预计效率还会进一步提升。

他们估计借助 Nova Act 节省了 25–30% 的工程时间，并减少了在功能之间来回切换的次数。此前用于支撑 QA 职能的工程产能已被重新分配到功能工程与价值创造上，使 First Orion 能够专注于更好地服务客户。

完全自动化的 Nova Act 运行带来了早期回归检测与快速的新功能测试，在某些情况下把测试覆盖率提升了 15% 以上。通过对每次构建都运行测试、而不必等待人工 QA 有空，First Orion 能在开发生命周期中更早地捕获回归，使其在上线前就被发现。

## 经验与最佳实践

组织层面的认同很重要。First Orion 勇于尝试新事物、快速交付的文化使采用成为可能。考虑采用 agentic 自动化的团队需要领导层的支持与试错空间。给正在考虑 agentic 自动化的团队的建议是：要有计划，但保持灵活。这个领域发展很快，上个月行不通的做法，今天可能因为一次模型更新就能奏效。

早期的一个挑战是模型导航路径的可预测性。First Orion 的 QA 工程师希望在相同前置条件下确认 agent 走过站点的同一路线，但最初 Nova Act 会经由不同路径到达目标状态。通过调整 Amazon Nova Act SDK 暴露的参数，他们显著提升了行为一致性。

另一条经验是清晰 prompt 的重要性。虽然可以为 SDK 编写英文测试用例，但这些 prompt 仍需要调优才能与模型良好配合。遵循 AWS 文档中关于 prompt 结构化的指导，提升了测试的可靠性。

一个相关但不同的问题是，AI agent 并不共享组织内的既有知识。那些未言明的前置条件、导航模式与业务规则，必须在 prompt 中显式提供。把这些上下文写进测试用例定义，是取得一致结果的关键。

## 下一步

First Orion 围绕 Amazon Nova Act 的路线图颇为宏大。他们在 QA 场景上的下一步包括使用 Kiro 与 Model Context Protocol（MCP）server 实现自动化测试生成，这些 server 让 AI 工具能够访问代码改动与需求文档。通过让 Kiro 查看代码改动并核对需求，First Orion 设想了一条完全自动化的测试生成 pipeline，直接输送给他们的 Nova Act 实现，从而进一步把 QA 工程师解放出来从事更高价值的任务。

他们还计划把 Nova Act 用于关键路径分析，理解 AI 如何在其站点中导航，从而找出产品可以改进之处。把这些信息输入其他系统，可以为网页设计师与营销团队提供反馈，帮助他们构建更高效的网页，带来更好的客户体验。

## 结语

First Orion 对 Amazon Nova Act 的采用，展示了 agentic AI 如何把 QA 工作流从瓶颈转变为竞争优势。通过从脆弱的、基于选择器的自动化转向自然语言驱动的测试，First Orion 缩短了 QA 周期、为功能开发释放了工程产能，并提升了及早捕获回归的能力。他们愿意尽早采用新技术，并作为发布合作伙伴与我们的团队紧密协作，这使他们能够更快前进，并构建出一套随其不断增长的产品组合而扩展的测试架构。

First Orion 的 CTO Mark Himelfarb 总结道：

> 「这不只是一个工具，而是一种竞争优势。过去要花上数小时的任务，现在几分钟就能完成，因此我们能在扩张的同时保持高标准。」

—— Mark Himelfarb，First Orion 的 CTO
