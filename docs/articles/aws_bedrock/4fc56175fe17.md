# 使用 Amazon Bedrock AgentCore 和 GitHub Actions 实现自动化的 agent 评估

*构建一个持续集成与持续交付（CI/CD）质量门，它会部署一个带有基于角色的 MCP 工具的 agent、对其进行评估，并在评估分数下降时阻止 PR 合并。*

你已经在 [Amazon Bedrock AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is.html)上发布了一个 AI agent。它通过受 OAuth 保护的 [MCP 服务器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-mcp.html)调用工具。现在你希望 CI 能在一项代码变更到达生产之前就告诉你：它是否让 agent 的性能变差了。

本文详细讲解一条 GitHub Actions pipeline，它将 agent 部署到 AgentCore runtime，并使用 evaluation prompt 通过 [AgentCore Evaluate API](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_Evaluate.html)对 agent 进行评估。如果 agent 出现回归，该 PR 就会失败。

我们会覆盖完整的技术栈：一个连接到带基于角色访问控制的 MCP 服务器的 [Strands](https://strandsagents.com/) agent、一个同时服务于机器对机器（M2M）和用户范围认证流程的共享 Cognito 池、CDK 基础设施即代码，以及一个统一的评估脚本。完整的参考实现可在[配套仓库](https://github.com/awslabs/agentcore-samples/tree/main/01-features/06-observe-evaluate-optimize-your-agent/02-evaluate/cicd-gated-evaluation)中获取。

## 本文涵盖的内容

- 使用 CDK 将 agent + MCP 服务器部署到 AgentCore runtime。
- MCP 工具上的基于角色的访问控制（三层认证模式）。
- 从 CI 调用受 OAuth 保护的 runtime（M2M `client_credentials` 流程）。
- 使用内置评估器运行按需评估。
- 强制执行在出现回归时阻止合并的质量门。
- 处理 OAuth 难题：CI pipeline 在没有用户上下文的情况下如何完成身份验证。

## 关键概念

在深入之前，先快速介绍这些构建块。如果你已经熟悉它们，可以直接跳过。

- [**AgentCore runtime**](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime.html) 是一个用于 AI agent 的托管平台。你部署 agent 代码（Python，任意框架），AgentCore 负责伸缩、会话隔离和基础设施。可以把它看作面向 agent 的 AWS Lambda。
- [**AgentCore Evaluations**](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations-types.html)，Amazon Bedrock AgentCore 的一项能力，使用大语言模型（LLM）作为评审来为 agent 行为打分。它从 Amazon CloudWatch 读取 [OpenTelemetry](https://opentelemetry.io/) trace，并在有用性、正确性和工具选择准确性等维度上对响应进行评分。
- [**MCP（Model Context Protocol）**](https://modelcontextprotocol.io/) 是一种开放协议，agent 通过它使用标准化接口调用外部工具。MCP 服务器暴露工具，agent 发现并调用它们。AgentCore runtime 可以[托管 MCP 服务器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-mcp.html)并将 agent 连接到它们。
- [**OpenID Connect（OIDC）联合**](https://docs.github.com/en/actions/security-for-github-actions/security-hardening-your-deployments/configuring-openid-connect-in-amazon-web-services) 是 GitHub Actions 在不存储长期凭证的情况下担任 AWS Identity and Access Management（AWS IAM）角色的方式。GitHub 签发一个短期 token，AWS 验证它，workflow 随即获得临时凭证。
- **质量门（Quality Gate）** 是一种 CI/CD 模式：pipeline 中的某个步骤必须通过阈值，构建才能继续。在我们的场景中，agent 的评估分数必须达到最低标准（例如 1.0 分制中的 0.8），否则 PR 会保持被阻止状态。

**为什么这很重要：** 没有自动化评估，agent 质量就是主观的。开发者改动了一个 system prompt，agent 开始给出更差的答案，而在用户抱怨之前没有人会注意到。质量门能在 PR 阶段、到达生产之前就捕获这种情况。

## 问题

场景是这样的。你有一个部署在 AgentCore runtime 上的 agent。它通过一个 MCP 服务器调用工具，其中一些工具是公开的，另一些则受用户角色限制。每当有人修改 system prompt、更换模型或更新工具配置时，你都想知道：这个 agent 是变好了还是变差了？

手动测试无法扩展。你需要在 CI 中进行自动化评估。这意味着在 dev 环境中自动部署 agent、用有代表性的 prompt 调用它、对响应打分，并在质量下降时阻止合并。

复杂之处在于：你的 MCP 服务器使用 OAuth 并带基于角色的访问控制。CI pipeline 没有用户上下文。你如何让一条无头 pipeline 通过受 OAuth 保护的 agent 的身份验证，而该 agent 又要把 token 转发给一个期望用户角色的 MCP 服务器？

## AgentCore Evaluations：它的定位

[AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 是 Amazon Bedrock AgentCore 平台中的质量测量层。它与托管你的 agent 的 [AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime.html)、以及捕获 trace 的 [AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-get-started.html)（Amazon Bedrock AgentCore 的一项能力）并列，共同构成 build → deploy → observe → evaluate 的生命周期。

该服务默认使用 LLM-as-a-judge 为 agent 交互打分，也可以选择通过 AWS Lambda 进行基于代码的评估。它作用于 OpenTelemetry trace，也就是你的 agent 已经通过 AgentCore Observability 发出的那些 trace。对于按需评估，你在 API 调用中直接提供 span 数据；在线评估和批量评估则从 CloudWatch 读取。

**三种评估模式**覆盖不同阶段：

- **按需评估**可以随时评估特定的会话。你提供 span 数据、选择评估器，然后拿回分数。这正是 CI/CD 质量门的动力来源，也是本文的重点。
- **在线评估**以可配置的采样率持续监控生产流量。结果会进入 CloudWatch 仪表板用于趋势监控。
- **批量评估 **在单个异步作业中对多个会话打分。你指向你的 CloudWatch Logs、选择评估器，然后获得聚合结果和各会话结果。这正是基线测量和改动前后回归测试的动力来源。

评估器分为四类：

- 内置评估器覆盖常见的质量维度：Helpfulness、Correctness、GoalSuccessRate、ToolSelectionAccuracy、ToolParameterAccuracy 等。它们在会话、trace 和工具调用层运作。三个轨迹评估器（`TrajectoryExactOrderMatch`、`TrajectoryInOrderMatch`、`TrajectoryAnyOrderMatch`）会将实际的工具调用序列与期望轨迹进行比较。
- 自定义评估器使用你自己的 LLM-as-a-judge prompt 进行领域特定的打分。ground truth 字段（expectedResponse、assertions、expectedTrajectory）在自定义评估器 prompt 中也可作为占位符使用。
- 基于代码的评估器对每个 trace 或会话运行一个 Lambda 函数，并返回由你的自定义实现计算出的分数、标签和说明。可将它们用于确定性检查，例如正则匹配、schema 验证或关键词是否存在，而且不产生 LLM 成本。
- 来自 DeepEval 和 AutoEval 开源库的第三方评估器由该服务像内置评估器一样管理。只需按 ID 选择一个，无需模型或配置。你也可以从内置或第三方评估器派生一个自定义评估器，用自己的模型运行其逻辑。

Evaluate API 接受 `sessionSpans`（来自 CloudWatch 的 OpenTelemetry trace 数据）并返回结构化分数。每次 `evaluate()` 调用只能包含来自单个会话的 span。混合会话会导致 `ValidationException`。

该 API 还通过 `evaluationReferenceInputs` 接受可选的 ground truth。你可以提供 `expectedResponse`（供 Correctness 使用）、`assertions`（供 GoalSuccessRate 使用）或 `expectedTrajectory`（供轨迹评估器使用）。没有 ground truth 的 trace 会退回到无 ground truth 的评估，因此你只需为关心的轮次提供它。

## 在 CI 中处理受 OAuth 保护的 MCP 服务器

当你的 agent 调用受 OAuth 保护的 MCP 服务器时，CI pipeline 面临一个难题：它们没有用户上下文。MCP 服务器期望一个带角色声明的 JWT，但无头的 CI runner 无法完成交互式的 OAuth 同意流程。

评估该 agent 有三种方法，各有不同的取舍：

### 方法 A：评估已存储的 trace

将评估与实时的 MCP 调用完全解耦。一条 staging pipeline 用有代表性的 prompt 运行 agent、捕获 trace，并将它们作为 JSON fixture 提交。在 PR 阶段，CI 评估这些已存储的 trace。不需要实时调用。

Evaluate API 不需要正在运行的 agent。它为你提供的 OpenTelemetry span 打分。你的 CI pipeline 变得确定（检查已有的 trace），你也完全绕开了 OAuth 问题。

**取舍：** 你评估的是 staging 部署的行为，而不是当前 PR 中的代码。配套仓库包含 [scripts/evaluate_stored_traces.py](https://github.com/awslabs/agentcore-samples/blob/main/01-features/06-observe-evaluate-optimize-your-agent/02-evaluate/cicd-gated-evaluation/scripts/evaluate_stored_traces.py) 和 `fixtures/` 中的示例 fixture，可用于上手这一方法。

### 方法 B：使用预先授权的服务账户

在你的身份提供方中创建一个专用测试用户。一次性（交互式）完成 OAuth 同意流程，将 refresh token 缓存在 [AWS Secrets Manager](https://docs.aws.amazon.com/secretsmanager/latest/userguide/intro.html)中。CI 使用该 token 以该测试用户的身份调用 agent。

**取舍：** refresh token 会过期。你需要一套轮换机制，或定期手动重新授权。

### 方法 C：M2M 认证（本文采用的方法）

将你的 MCP 服务器配置为同时支持 M2M 和用户范围的授权类型。CI 使用 M2M token，而交互式用户走标准的 OAuth 同意流程。

MCP 服务器中间件会区分 token 类型：M2M token 包含 scope 但没有角色，因此跳过角色检查，所有工具都可访问。用户 token 携带 `custom:roles` 声明，因此会强制执行工具级访问控制。这种绕过是安全的，因为 M2M token 需要一个从不会暴露给最终用户的 client secret。只有 CI pipeline 和 agent runtime 能获得这些 token，从而防止不受信任的调用方拿到无角色 token。

**取舍：** 按设计，M2M token 会绕过角色检查。如果你需要 CI 专门测试角色限制，请使用方法 B。

## MCP 服务器：三层认证

对于方法 C，MCP 服务器使用三层来同时支持 M2M 和用户范围的 token。这是让 CI 评估与生产环境角色限制并存的关键模式。

**第 1 层 JWT 验证（AgentCore）：** 平台在请求到达你的代码之前验证签名、签发方、受众和有效期。无需任何实现。AgentCore 通过 [Custom JWT Authorizer](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html)处理这一点。

**第 2 层 Header 透传：** 在两个 runtime 上都设置 `request_header_allowlist=["Authorization"]`，确保 JWT 到达 agent 和 MCP 容器。AgentCore 会将调用方的 Authorization header 原样转发到你的容器。

```
# infrastructure/stack.py — on both CfnRuntime constructs
request_header_configuration=CfnRuntime.RequestHeaderConfigurationProperty(
    request_header_allowlist=["Authorization"]
)
```
**第 3 层 基于角色的工具访问（AuthMiddleware）：** 一个 FastMCP 原生中间件，它通过 `fastmcp.server.dependencies.get_http_headers()` 读取 JWT、使用 PyJWT 解码声明，并依据工具的 `meta` 强制执行 `custom:roles`。M2M token（有 scope 但无角色）获得全部访问权限。用户 token 则需要正确的角色。

该中间件直接添加到 FastMCP 服务器实例上：

```
mcp.add_middleware(AuthMiddleware())
app = mcp.http_app(stateless_http=True)
```

## 评估脚本

统一的评估脚本（[scripts/agentcore_eval.py](https://github.com/awslabs/agentcore-samples/blob/main/01-features/06-observe-evaluate-optimize-your-agent/02-evaluate/cicd-gated-evaluation/scripts/agentcore_eval.py)）处理完整 pipeline：获取 token、等待 runtime、调用 agent、等待 trace、运行评估，并按阈值进行门禁。

token 获取使用标准的 `client_credentials` 授权。

```
# scripts/agentcore_eval.py (key excerpt)
def get_token() -> str:
    """Client-credentials grant"""
    resp = http_requests.post(
        os.environ["TOKEN_ENDPOINT"],
        data={
            "grant_type": "client_credentials",
            "client_id": os.environ["OAUTH_CLIENT_ID"],
            "client_secret": os.environ["OAUTH_CLIENT_SECRET"],
            "scope": os.environ.get("OAUTH_SCOPE", ""),
        },
    )
    resp.raise_for_status()
    return resp.json()["access_token"]
```
agent 调用使用带 Bearer token 的 HTTPS（而不是 boto3）：

```
def invoke_agent(agent_arn, session_id, prompt, region, token):
    """Invoke via HTTPS with Bearer token"""
    escaped_arn = urllib.parse.quote(agent_arn, safe="")
    url = f"https://bedrock-agentcore.{region}.amazonaws.com" \
          f"/runtimes/{escaped_arn}/invocations?qualifier=DEFAULT"
    headers = {
        "Authorization": f"Bearer {token}",
        "Content-Type": "application/json",
        "X-Amzn-Bedrock-AgentCore-Runtime-Session-Id": session_id,
    }
    resp = http_requests.post(url, headers=headers,
                              data=json.dumps({"prompt": prompt}))
    resp.raise_for_status()
    return resp.json()
```
该脚本使用 bedrock-agentcore-starter-toolkit 的 Evaluation 类来运行评估，它会自动处理从 CloudWatch 收集 trace：

```
from bedrock_agentcore_starter_toolkit import Evaluation

results = Evaluation(region=region).run(
    agent_id=agent_id,
    session_id=session_id,
    evaluators=[
        "Builtin.GoalSuccessRate",
        "Builtin.Correctness",
        "Builtin.ToolSelectionAccuracy",
        "Builtin.ToolParameterAccuracy",
    ],
    output="evals_results/ci_output.json",
)
```
评估 prompt 覆盖 agent 的完整工具面，包括内置工具、公开 MCP 工具和受角色限制的 MCP 工具：


## GitHub Actions workflow

该 workflow 会在每个改动 agent 代码、MCP 服务器、基础设施或脚本的、发往 main 的 PR 上运行。它部署 CDK 栈、调用 agent、运行评估、将结果作为 PR 评论发布，并拆除栈。完整实现见[完整 workflow](https://github.com/awslabs/agentcore-samples/blob/main/01-features/06-observe-evaluate-optimize-your-agent/02-evaluate/cicd-gated-evaluation/.github/workflows/agentcore-eval.yml)。

关键步骤如下所示：

```
jobs:
  evaluate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ap-southeast-2

      # Deploy both runtimes + Cognito via CDK
      - name: CDK deploy
        run: npx cdk deploy --require-approval never --outputs-file outputs.json

      # Extract CDK outputs (agent ARN, runtime IDs, Cognito endpoints)
      - name: Extract CDK outputs
        id: cdk
        run: |
          STACK="AgentCoreCICDStack-dev"
          AGENT_ARN=$(jq -r ".[\"$STACK\"].AgentRuntimeArn" outputs.json)
          echo "agent_arn=$AGENT_ARN" >> "$GITHUB_OUTPUT" # ... extract all outputs

      # Restart runtimes to pick up new container images + inject M2M secret
      - name: Restart runtimes
        run: python3 -c "..." # update_agent_runtime() with env vars

      # Run the unified evaluation script
      - name: Run evaluation
        working-directory: scripts
        run: python3 agentcore_eval.py
        env:
          AGENT_RUNTIME_ARN: ${{ steps.cdk.outputs.agent_arn }}
          EVAL_THRESHOLD: "0.8"

      # Always tear down — even if evaluation fails
      - name: CDK destroy
        if: always()
        run: npx cdk destroy --force
```
**警告：** CDK 部署返回后，runtime 会在 CREATING 状态停留几分钟，在其处于 READY 之前调用会失败并返回 424 Failed Dependency。该 workflow 会轮询 `get_agent_runtime`（通过 `bedrock-agentcore-control` 客户端），直到两者都变为 READY，然后在评估之前预热 MCP 服务器。

## 内置评估器参考

AgentCore 提供[多种内置评估器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/prompt-templates-builtin.html)，按其评估的内容组织：

| **类别** | **评估器** | **何时使用** |
| --- | --- | --- |
| SESSION | GoalSuccessRate | 对话是否达成了用户的目标？ |
| TRACE | Helpfulness、Correctness、Coherence、Conciseness、Faithfulness、InstructionFollowing、ResponseRelevance、ContextRelevance、Harmfulness、Refusal、Stereotyping | 每次请求的质量与安全性 |
| TOOL_CALL | ToolSelectionAccuracy、ToolParameterAccuracy、TrajectoryExactOrderMatch、TrajectoryInOrderMatch、TrajectoryAnyOrderMatch、SkillSelectionAccuracy、SkillInstructionFollowing | 是否以正确的参数调用了正确的工具？轨迹评估器检查工具调用顺序（需要 expectedTrajectory ground truth）。Skill 评估器检查 skill 选择与指令遵循情况。 |

本文使用四个评估器：GoalSuccessRate、Correctness、ToolSelectionAccuracy 和 ToolParameterAccuracy。工具调用类评估器对使用 MCP 工具的 agent 尤其相关。它们验证 agent 是否选择了正确的工具并传入了正确的参数。

**提示：** CI 先从四到五个评估器开始。为使用工具调用的 agent 添加轨迹评估器，为面向客户的 agent 添加安全评估器（Harmfulness、Stereotyping、Refusal）。使用基于代码的评估器进行确定性检查。定期的深度评估则使用完整集合。

## 测试 pipeline：失败、修复、通过

要对一个质量门建立信心，一种可靠的方法是看它捕获一次真实的回归。

**故意制造失败：** 将 agent 的 system prompt 改成无用的内容：

```
# agent/src/assistant_agent.py — deliberately bad prompt
system_prompt="Respond to every question with exactly: 'I cannot help you.'"
```
推送到功能分支并打开一个 PR。pipeline 会运行，你会看到：

```
──────────────────────────────────────────────────
Evaluator                        Score    Result
──────────────────────────────────────────────────
Builtin.GoalSuccessRate          0.0      Failed
Builtin.Correctness              0.0      Failed
Builtin.ToolSelectionAccuracy    1.0      Passed
Builtin.ToolParameterAccuracy    0.0      Failed
──────────────────────────────────────────────────
FAILED: metrics below 0.8
```
**注意：** ToolSelectionAccuracy 可能仍然通过，因为即使 system prompt 很差，agent 也可能选对工具。各评估器独立地测量不同维度。

**修复并通过：** 恢复一个正常的 system prompt，再次推送。pipeline 会重新运行：

```
──────────────────────────────────────────────────
Evaluator                        Score    Result
──────────────────────────────────────────────────
Builtin.GoalSuccessRate          1.0      Passed
Builtin.Correctness              0.9      Passed
Builtin.ToolSelectionAccuracy    1.0      Passed
Builtin.ToolParameterAccuracy    1.0      Passed
──────────────────────────────────────────────────
All evaluations PASSED (threshold: 0.8)
```
该 PR 解除阻止。

**警告：** `LLM-as-judge` 的分数存在固有方差。因此，同一个 prompt 评估两次可能产生略有不同的分数。设置阈值时，请在你的目标可靠性之下留出一定余量，以容纳这种方差。

## 测试中得到的经验

我们端到端运行了这条 pipeline。以下是踩到的坑。可以帮你省下调试时间。

- 要调用受 OAuth 保护的 AgentCore runtime，请直接向 HTTPS 端点 POST 并携带 Bearer token，而不是使用 `boto3` 中的 `invoke_agent_runtime()` 方法。
- **trace 传播需要 30-90 秒。** 评估脚本每 30 秒重试一次，最多 10 分钟。不要在调用后立即查询 CloudWatch。
- **需要 ARM64 镜像。** AgentCore runtime 要求 ARM64 容器。GitHub runner 是 x86_64 架构。因此，请使用 QEMU + Docker Buildx 进行交叉编译。
- **CDK 部署后需要重启 runtime。** 在 runtime 处于 READY 之前调用会失败并返回 424 Failed Dependency，因此该 workflow 会轮询 `get_agent_runtime`，直到两个 runtime 都就绪（并预热 MCP 服务器）之后才发起调用。
- **`sessionSpans` 是 API 参数名。** Evaluate API 接受 `evaluationInput: {"sessionSpans": [...]}`。每次调用只能包含来自单个会话的 span。混合会话会导致 `ValidationException`。
- **时间戳必须是整数。** 像 `startTimeUnixNano` 这样的 OpenTelemetry 纳秒时间戳必须是 JSON 整数，而不是带引号的字符串。字符串时间戳会导致 `ValidationException`。

## 适配 Microsoft Entra ID

本文使用 Amazon Cognito，但该架构与身份提供方无关。如果你的组织使用 Microsoft Entra ID（原 Azure AD），同一条 pipeline 只需做有针对性的修改即可工作：

- **Token 端点：** 将 Amazon Cognito 的区域端点改为 `https://login.microsoftonline.com/{tenant_id}/oauth2/v2.0/token`。
- **Discovery URL：** 改为 `https://login.microsoftonline.com/{tenant_id}/v2.0/.well-known/openid-configuration`。
- **Client credentials：** 将 Cognito 的客户端 ID 和受众替换为 Entra ID 的应用 ID 和作用域 URI。

其余一切保持不变。部署脚本的 `authorizerConfiguration.customJWTAuthorizer` 结构完全相同，评估脚本不涉及身份验证（它通过 `boto3` 使用 IAM），GitHub Actions workflow 的结构也不变。

## 取舍与限制

- **pipeline 大约需要 10 分钟。** CDK 部署 + runtime 启动 + trace 传播 + 评估。对 PR 门禁来说没问题，但对 pre-commit 来说太慢。
- **`LLM-as-judge` 存在固有方差。** 同一 trace 评估两次可能产生略有不同的分数。设置阈值时请留出余量。
- **每次运行的成本。** 每次评估器调用都会调用评审模型。4 个评估器 × 5 个 prompt = 每个 PR 20 次评审调用。大规模使用时请监控 Bedrock 成本。
- **M2M token 绕过角色检查。** 按设计，CI 需要访问所有工具。如果你需要 CI 测试角色限制，请使用方法 B（服务账户）。

**注意：** 尽管有这些限制，自动化评估仍然严格优于没有评估。即便是不完美的质量门，也能捕获人工评审会漏掉的明显回归。

## 清理

配套仓库会预置两个 AgentCore runtime、一个 Cognito 用户池、IAM 角色和预创建用户，因此完成后请拆除所有资源以停止产生费用。一条命令即可全部移除：

```
source .venv/bin/activate
cdk destroy --force
```
如果你使用 npx 而不是全局 CDK CLI 进行部署，请改运行 `npx aws-cdk@2 destroy --force`。在 dev 栈中，`cdk destroy` 会移除两个 runtime、Cognito 池及其应用客户端、预创建的用户、IAM 角色，以及 AWS Secrets Manager 中的 M2M 客户端密钥。该 secret 的删除策略设置为 destroy，因此重复部署和拆除都能保持干净。CI workflow 在每次运行结束时都会自动拆除同一个栈，因为它的 CDK destroy 步骤以 `if: always()` 运行。只有你自己在跟随本文实践时部署的栈才需要这条命令。

## 关键要点

- **三层 MCP 认证**（平台 JWT 验证 → 中间件声明提取 → 工具级角色检查）干净地分离了关注点，并支持 M2M 和用户范围两种流程，无需修改代码。
- **CDK 部署一切。** 一次 `cdk deploy` 即可创建 Cognito 池、两个 runtime、IAM 角色和预创建用户。一次 `cdk destroy` 即可全部拆除。
- **`bedrock-agentcore-starter-toolkit` 简化了评估。** Evaluation 类负责从 CloudWatch 收集 trace 并打分，因此无需手动查询日志组并用 `sessionSpans` 调用原始的 Evaluate API。
- **token 转发连接了 CI 与生产。** agent 会检查传入的 JWT，判断它是用户 token（转发给 MCP 做角色检查）还是 M2M token（使用共享客户端，绕过角色）。同一份代码同时服务两类调用方。
- **Evaluate API 与 agent runtime 解耦。** 你不需要运行中的 agent 就能评估 trace。这是让方法 A（存储的 trace）可行的关键洞见，也是通往 CI 质量门的直接路径。
- **从四个评估器开始并逐步扩展。** GoalSuccessRate、Correctness、ToolSelectionAccuracy 和 ToolParameterAccuracy 覆盖了基础。为面向客户的 agent 添加安全评估器。
- ground truth 和基于代码的评估器扩展了工具箱。轨迹评估器是程序化的，并且不额外收费，非常适合 CI。基于代码的评估器在同一次评估调用中与 `LLM-as-judge` 打分并行运行确定性的 Lambda 检查。
