# 为 Amazon Bedrock 构建主动式 AI 成本管理系统——第 2 部分

在本系列[第 1 部分](https://aws.amazon.com/blogs/machine-learning/build-a-proactive-ai-cost-management-system-for-amazon-bedrock-part-1/)中，我们为 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 介绍了一套主动式成本管理方案，其中包含健壮的成本哨兵（cost sentry）机制，用于强制执行实时的 token 使用上限。我们探讨了核心架构、token 跟踪策略，以及帮助组织控制生成式 AI 支出的初始预算执行技术。

在此基础上，本文进一步探讨生成式 AI 部署的高级成本监控策略。我们引入细粒度的自定义标签方式以实现精确的成本分摊，并开发全面的报表机制。

### 增强的 API 输入

我们还演进 API 输入以支持自定义标签。新的输入结构引入了用于模型特定配置与自定义标签的可选参数：

```
{
  "model": "string",     // e.g., "claude-3" or "anthropic.claude-3-sonnet-20240229-v1:0"
  "prompt": {
    "messages": [
      {
        "role": "string",    // "system", "user", or "assistant"
        "content": "string"
      }
    ],
    "parameters": {
      "max_tokens": number,    // Optional, model-specific defaults
      "temperature": number,   // Optional, model-specific defaults
      "top_p": number,         // Optional, model-specific defaults
      "top_k": number          // Optional, model-specific defaults
    }
  },
  "tags": {
    "applicationId": "string",  // Required
    "costCenter": "string",     // Optional
    "environment": "string"     // Optional - dev/staging/prod
  }
}
```

该输入结构由三个关键组件构成：

- **model**——把简单名称（例如 `claude-3`）映射到完整的 Amazon Bedrock 模型 ID（例如 `anthropic.claude-3-sonnet-20240229-v1:0`）
- **input**——为 prompt 提供 messages 数组，同时支持单轮与多轮对话
- **tags**——支持应用级跟踪，其中 `applicationId` 为必填字段，`costCenter` 与 `environment` 为可选字段

在本例中，我们为 `sales`、`services` 与 `support` 使用不同的成本中心，以模拟使用业务属性来跟踪 Amazon Bedrock 中推理的使用量与支出。例如：

```
{
  "model": "claude-3-5-haiku",
  "prompt": {
    "messages": [
      {
        "role": "user",
        "content": "Explain the benefits of using S3 using only 100 words."
      },
      {
        "role": "assistant",
        "content": "You are a helpful AWS expert."
      }
    ],
    "parameters": {
      "max_tokens": 2000,
      "temperature": 0.7,
      "top_p": 0.9,
      "top_k": 50
    }
  },
  "tags": {
    "applicationId": "aws-documentation-helper",
    "costCenter": "support",
    "environment": "production"
  }
}
```

### 校验与打标

工作流新增了一个用于打标的校验步骤。该步骤使用 [AWS Lambda](https://aws.amazon.com/lambda) 函数添加校验检查，并把请求的模型映射到 Amazon Bedrock 中具体的模型 ID。它为 `tags` 对象补充下游分析所需的标签。

下面的代码是一个简单映射的示例，用于从指定的模型得到合适的模型 ID：

```
MODEL_ID_MAPPING = {
    "nova-lite": "amazon.nova-lite-v1:0",
    "nova-micro": "amazon.nova-micro-v1:0",
    "claude-2": "anthropic.claude-v2:0",
    "claude-3-haiku": "anthropic.claude-3-haiku-20240307-v1:0",
    "claude-3-5-sonnet-v2": "us.anthropic.claude-3-5-sonnet-20241022-v2:0",
    "claude-3-5-haiku": "us.anthropic.claude-3-5-haiku-20241022-v1:0"
}
```

### 日志与分析

通过把 CloudWatch 指标与自定义生成的标签、维度配合使用，你可以跨模型类型、成本中心、应用与环境等多个维度跟踪详细指标。自定义标签与维度能反映团队如何使用 AI 服务。为查看这类分析，我们实现了生成自定义标签、存储指标数据与分析指标数据的步骤：

- 我们包含一组唯一的标签，用于捕获上下文信息。这既可以包括用户提供的标签，也可以包括动态生成的标签，例如 `requestId` 与 `timestamp`：  ` "tags": { "requestId": "ded98994-eb76-48d9-9dbc-f269541b5e49", "timestamp": "2025-01-31T14:05:26.854682", "applicationId": "aws-documentation-helper", "costCenter": "support", "environment": "production" }`
- 随着每个工作流的执行，系统会评估每个模型的限额，以确保请求处于预算准则之内。工作流会以三种可能的结果之一结束：限流通过且调用成功；限流通过但调用失败；限流被拒绝。自定义指标数据保存在 CloudWatch 的 `GenAIRateLimiting` 命名空间中。该命名空间包含以下关键指标：**TotalRequests**——统计每次调用尝试，不论结果如何；**RateLimitApproved**——跟踪通过限流检查的请求；**RateLimitDenied**——跟踪被限流拦截的请求；**InvocationFailed**——统计在模型调用期间失败的请求；**InputTokens**——衡量成功请求的输入 token 消耗；**OutputTokens**——衡量成功请求的输出 token 消耗。每个指标都包含 `Model`、`ModelId`、`CostCenter`、`Application` 与 `Environment` 维度，便于数据分析。
- 我们使用 CloudWatch 的指标查询能力与数学表达式来分析工作流收集的数据。数据可以多种可视化格式展示，以便按所提供的维度（例如模型或成本中心）获得请求的细粒度视图。下面的截图展示了一个示例看板，其中某个模型已达到其限额。

## 成本打标与报表

Amazon Bedrock 推出了[应用推理配置文件（application inference profiles）](https://aws.amazon.com/blogs/machine-learning/track-allocate-and-manage-your-generative-ai-cost-and-usage-with-amazon-bedrock/)，这是一项新能力，组织可借此应用自定义成本分摊标签，以跟踪并管理其按需基础模型（FM）的使用。该功能解决了此前的一个限制：按需 FM 无法打标，导致难以跟踪不同业务部门与应用的成本。现在你可以为基础 FM 创建自定义推理配置文件，并应用部门、团队、应用标识符等成本分摊标签。这些标签与 AWS 成本管理工具集成，包括 [AWS Cost Explorer](https://aws.amazon.com/aws-cost-management/aws-cost-explorer/)、[AWS Budgets](https://aws.amazon.com/aws-cost-management/aws-budgets/) 与 [AWS Cost Anomaly Detection](https://aws.amazon.com/aws-cost-management/aws-cost-anomaly-detection/)，从而实现细致的成本分析与预算控制。

### 应用推理配置文件

首先，你必须为每种要跟踪的使用类型创建应用推理配置文件。在本例中，方案为 `costCenter`、`environment` 与 `applicationId` 定义了自定义标签。推理配置文件还会基于已有的 Amazon Bedrock 模型配置文件，因此你必须把所需的标签与模型组合进该配置文件中。撰写本文时，你必须使用 [AWS Command Line Interface](https://aws.amazon.com/cli)（AWS CLI）或 AWS API 来创建。参见下面的示例代码：

```
aws bedrock create-inference-profile \
  --inference-profile-name "aws-docs-sales-prod" \
  --model-source '{"copyFrom":  "arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-3-haiku-20240307-v1:0"}' \
  --tags '[
    {"key": "applicationId", "value": "aws-documentation-helper"},
    {"key": "costCenter", "value": "sales"},
    {"key": "environment", "value": "production"}
  ]'
```

该命令使用 Anthropic 的 Claude Haiku 3.5 模型，为 sales 成本中心与 production 环境创建一个配置文件。该命令的输出是一个 Amazon Resource Name（ARN），你将把它用作模型 ID。在该方案中，`ValidateAndSetContext` Lambda 函数经过修改，允许按成本中心（例如 `sales`）指定模型。如需查看你创建了哪些配置文件，请使用以下命令：

`aws bedrock list-inference-profiles --type-equals APPLICATION`

配置文件创建完成、校验逻辑也已更新为把成本中心映射到配置文件 ARN 之后，工作流就会使用对齐后的配置文件开始运行推理请求。例如，当用户提交请求时，他们会把模型指定为 `sales`、`services` 或 `support`，以对上已定义的三个成本中心。下面的代码与上例是类似的映射：

```
MODEL_ID_MAPPING = {
    "sales": "arn:aws:bedrock:<region>:<account>:application-inference-profile/<unique id1>",
    "services": "arn:aws:bedrock:<region>:<account>:application-inference-profile/<unique id2>",
    "support": "arn:aws:bedrock:<region>:<account>:application-inference-profile/<unique id3>"
   }
```

在使用应用推理配置文件时，要正确查询 CloudWatch 中模型使用情况的指标，你必须指定该配置文件的唯一 ID（ARN 的最后一部分）。CloudWatch 会基于该唯一 ID 存储 token 使用量等指标。为同时支持配置文件用法与直接模型用法，Lambda 函数经过修改，新增了 `modelMetric` 标签，使其成为查询 token 使用量时应使用的合适取值。参见下面的代码：

```
  "tags": {
    "requestId": "ded98994-eb76-48d9-9dbc-f269541b5e49",
    "timestamp": "2025-01-31T14:05:26.854682",
    "applicationId": "aws-documentation-helper",
    "costCenter": "support",
    "environment": "production",    
    "modelMetric": "<unique id> | <model id>"
  }
```

### Cost Explorer

Cost Explorer 是一款强大的成本管理工具，可对包括 Amazon Bedrock 在内的各 AWS 服务的云支出提供全面的可视化与分析。它提供直观的看板，用于跟踪历史成本、预测未来支出，并深入了解你的云消耗。借助 Cost Explorer，你可以按服务、标签与自定义维度拆分支出，做细致的财务分析。该工具每天更新。

当你把应用推理配置文件与 Amazon Bedrock 一起使用时，AI 服务的使用会自动打标，并直接流入 Billing and Cost Management。这些标签支持按成本中心、应用与环境等不同维度进行细致的成本跟踪。这意味着你可以生成按特定业务部门、项目或组织层级拆分 Amazon Bedrock AI 费用的报表，从而清楚了解生成式 AI 支出。

### 成本分摊标签

成本分摊标签是键值对，帮助你在整个组织内对 AWS 资源成本进行分类与跟踪。在 Amazon Bedrock 的语境下，这些标签可以包含应用名称、成本中心、环境或项目 ID 等属性。要激活成本分摊标签，你必须先在 Billing and Cost Management 控制台上启用它。激活后，这些标签会出现在你的 AWS 成本与使用报告（CUR）中，帮助你以细粒度拆分 Amazon Bedrock 费用。

要激活成本分摊标签，请完成以下步骤：

- 在 Billing and Cost Management 控制台的导航窗格中，选择 **Cost Allocation Tags**。
- 找到你的标签（本示例中名为 `costCenter`），选择 **Activate**。
- 确认激活。

激活后，`costCenter` 标签会出现在你的 CUR 中，并会在 Cost Explorer 中使用。该标签在你的账单报表中完全生效可能需要 24 小时。

![AWS Billing 控制台中的成本分摊标签管理，含筛选与激活控件](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/30/ML-17734-part2-image5.jpeg)

### Cost Explorer 报表

要在 Cost Explorer 中基于你的标签创建 Amazon Bedrock 使用报表，请完成以下步骤：

- 在 Billing and Cost Management 控制台的导航窗格中选择 **Cost Explorer**。
- 设置所需的日期范围（相对时间范围或自定义时段）。
- 选择 **Daily** 或 **Monthly** 粒度。
- 在 **Group by** 下拉菜单中选择 **Tag**。
- 选择 `costCenter` 作为标签键。
- 查看展示的 Amazon Bedrock 成本，按每个唯一的成本中心值拆分。
- 可选：在 **Filters** 区域应用筛选，以过滤取值：选择 **Tag** 筛选器；选择 **costCenter** 标签；选择你想分析的具体成本中心取值。

生成的报表会给出 Amazon Bedrock AI 服务费用的详细视图，帮助你精确比较不同组织单位或项目之间的支出。

![AWS Cost Explorer 界面，展示 sales、services 与 support 的 Bedrock 成本拆分](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/30/ML-17734-part2-image6.jpeg)

## 小结

AWS 成本与使用报告（包括预算）属于滞后指标，因为它们展示的是你在 Amazon Bedrock 上已经花掉的钱。通过把来自 Step Functions 的实时告警与全面的成本报表结合起来，你可以获得 Amazon Bedrock 用量的 360 度视图。这类报表可以在你超支之前发出告警，并帮助你了解实际消耗。这种做法让你能够主动管理 AI 资源，让创新预算保持在轨、项目平稳运行。

不妨在你自己的用例中试试这套成本管理方法，并在评论区分享你的反馈。
