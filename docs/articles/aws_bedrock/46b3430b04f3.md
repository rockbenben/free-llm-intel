# 加州大学洛杉矶分校借助 AWS 生成式 AI 服务打造沉浸式戏剧体验

*本文由 UCLA 的 Andrew Browning、Anthony Doolan、Jerome Ronquillo、Jeff Burke、Chiheb Boussema 与 Naisha Agarwal 共同撰写。*

加州大学洛杉矶分校（[UCLA](https://www.ucla.edu/)）走出了 16 位诺贝尔奖得主，并连续 8 年被评为全美排名第 1 的公立大学。UCLA 的先进研究计算办公室（[OARC](https://oarc.ucla.edu/)）是研究事业的技术扩展伙伴，提供智力与技术诀窍，把研究转化为现实。UCLA 媒体与表演研究与工程中心（[REMAP](https://remap.ucla.edu/)）找到 OARC，希望构建一套 AI 微服务，支持音乐剧 *Xanadu* 的沉浸式演出。

REMAP 版 *Xanadu* 与 UCLA 戏剧系 Ray Bolger 音乐剧项目合作，被设计为一场沉浸式、参与式的演出：观众在演出中用手机手势在 13 x 9 英尺的 LED 屏幕（称为 shrines）上共同作画，这些屏幕由 [4Wall Entertainment](https://www.4wall.com/) 提供，并通过 [Mo-Sys StarTrackers](https://www.mo-sys.com/products/startracker/) 进行位置跟踪。观众的画作随后送入 AWS 微服务进行推理，生成的媒体再被投射回 shrines，以 AI 生成的 2D 图像与 3D 网格的形式出现在演出的数字布景中（运行在 [Unreal Engine](https://www.unrealengine.com/) 上，硬件由 [Boxx](http://boxx.com/) 提供）。OARC 为 7 场演出以及此前的大量试演与排练成功设计并实现了这套方案。演出于 2025 年 5 月 15 日至 5 月 23 日举行，观众总数约 500 人，演出期间最多有 65 人同时参与共同创作媒体。

在本文中，我们将介绍演出面临的约束以及 OARC 与 REMAP 的设计选择，包括 AWS [无服务器](https://aws.amazon.com/serverless/)基础设施、AWS 托管服务与生成式 AI 服务如何支撑我们快速设计并部署方案。我们还会介绍 [Amazon SageMaker AI](https://aws.amazon.com/sagemaker-ai/) 的使用方式，以及如何在沉浸式现场体验中可靠地使用它。我们会概述所用的模型，并说明它们如何促成观众共同创作的媒体。我们也会回顾在排练与演出期间控制成本的机制。最后，我们会给出经验教训，以及为该项目第二阶段计划做出的改进。

# 方案概览

OARC 的方案旨在让现场演出期间能够进行近实时（NRT）推理，包含以下高层需求：

- 微服务对并发有严格要求：每场演出至少支持 80 名手机用户（可容纳 65 名观众加 12 名演员）
- 从手机绘图到媒体呈现的平均往返时间（MRTT）必须低于 2 分钟，才能在演出进行时准备好内容，带来最佳观众体验
- AWS GPU 资源在排练与演出期间必须容错且高可用，不允许降级运行
- 需要一套人在回路（human-in-the-loop）的看板，在需要人工介入时对基础设施资源进行手动控制
- 架构必须足够灵活，以便开发者找到新解法时能在不同场次之间做修改

考虑到上述约束，我们对大部分工作负载采用无服务器优先的架构设计。我们在 Amazon SageMaker AI 上部署 [HuggingFace](https://huggingface.co/) 模型，并使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 中可用的模型，构建了一条完整的推理流水线，兼用两个服务的灵活性与优势。Amazon Bedrock 提供对基础模型（如 [Anthropic Claude](https://aws.amazon.com/bedrock/anthropic/)、[Amazon Nova](https://nova.amazon.com/)、[Stable Diffusion](https://aws.amazon.com/bedrock/stability-ai/)）的简化托管访问，而 Amazon SageMaker AI 为来自 HuggingFace 的开源模型提供完整的机器学习生命周期控制。

# 方案详解

OARC 微服务应用设计采用无服务器优先的方式，为事件驱动架构奠定基础。用户绘图通过低延迟的 Firebase 编排层传给微服务，工作由一系列处理步骤协调，把用户绘图转换为 2D 图像与 3D 网格。图中左侧的若干本地 MacOS 工作站负责启动工作流、监听任务完成、执行人在回路复核，以及把完成的素材发回演出媒体服务器。

# 消息流水线

入站的观众绘图与元数据消息从本地 MacOS 工作站发送到 [Amazon SQS](https://aws.amazon.com/sqs/)，再由一个 [AWS Lambda](https://aws.amazon.com/lambda/) 辅助函数把它们分拣到各子队列。每个队列根据用户绘图所需的推理处理类型（例如 2D 图像、3D 网格）负责启动一条流水线。这种分拣机制让应用可以精确控制处理速率，因此繁忙的流水线不会用占用中的资源阻塞其他流水线的新消息。

[![端到端 AWS 生成式 AI 工作流图，展示 Lambda 编排与存储、消息传递及 AI 模型集成](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/26/ML-18988-image-2.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/26/ML-18988-image-2.png)

# 消息处理

第二个更复杂的 Lambda 函数监听各分拣后子队列的消息，并提供把用户绘图准备好用于推理的逻辑。该函数负责校验、错误/成功消息、并发处理，以及预处理推理与后处理步骤的编排。这种设计采用模块化方式，让开发者可以快速集成新功能，同时把合并冲突降到最低。由于存在人在回路，我们不对图像做自动后处理。我们可以放心认为问题会在素材发到 shrines 之前被发现。未来，我们打算使用 Amazon Bedrock 中的 guardrails 以及其他目标检测方法，结合人在回路复核，来校验 SageMaker AI 端点返回的素材。

我们的处理步骤需要大型 Python 依赖（包括 PyTorch）。这些依赖最大可达 5GB，体积太大而无法放进 Lambda 层。我们使用 [Amazon EFS](https://aws.amazon.com/efs/) 把依赖存放在独立卷中，在运行时挂载到 Lambda 函数。依赖的体积增加了服务启动所需的时间，但初次实例化之后，后续的消息处理性能表现良好。启动阶段增加的延迟是应用 Lambda 冷启动与延迟改进建议的理想场景。不过我们没有实施，因为这需要在项目后期对我们的开发流程做一些调整。

推理请求由 24 个 SageMaker AI 端点处理，其中 8 个端点负责承载三条流水线。我们使用 [Amazon EC2 G6](https://aws.amazon.com/ec2/instance-types/g6/) 实例族托管模型，采用 8 台 g6.12xlarge 与 16 台 g6.4xlarge 实例。每条流水线都包含一套定制工作流，对应演出所需的那类请求。每个 SageMaker AI 端点都同时利用内部加载的模型与托管在 Amazon Bedrock 上的大型 LLM 来完成每次请求（完整工作流在后面的 AI 工作流一节详述）。从 Amazon SageMaker AI 任务启动到生成素材返回 AWS Lambda 的平均处理时间，在 g6.4xlarge 实例上为 40-60 秒，在 g6.12xlarge 实例上为 20-30 秒。

推理完成后，Lambda 函数把消息发送到 [Amazon SNS](https://aws.amazon.com/sns/) 主题，由该主题负责发送成功邮件、发布到 Amazon SQS，并更新 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 表以供日后分析。本地 MacOS 工作站轮询最终的队列，在素材完成时取回新素材。

下图展示了我们方案中 Amazon SageMaker AI 与 Amazon Bedrock 各自使用的模型。Amazon SageMaker AI 的模型包括：DeepSeek VLM、SDXL、Stable Diffusion 3.5、SPAR3D、用于 openpose 的 ControlNet、Yamix-8、ControlNet Tile、用于 canny 边缘的 ControlNet、CSGO、IP Adapter、InstantID、来自 InsightFace 的 antelopev2 模型。Amazon Bedrock 使用的模型包括：Nova Canvas、Stable Diffusion 3.5 与 Claude 3.5 Sonnet。

# AI 工作流

方案利用 AWS 完成三个不同的推理循环，称为模块。每个模块都有一套量身定制的 AI 工作流，使用小型与大型 AI 模型的子集，生成用于呈现的 2D 图像与 3D 网格对象。每个模块都从观众 prompt 开始，请参与者为特定任务绘制草图，例如创建背景、渲染 3D 对象的 2D 表示，或者为缪斯摆放自定义姿势并搭配服装。AI 工作流随后按各模块的要求处理这些图像。

每个模块都先为用户的草图以及随附的预设计参考图生成文本描述。为此，我们使用加载在 Amazon SageMaker AI 端点上的 DeepSeek VLM，或通过 Amazon Bedrock 使用 [Anthropic 的 Claude 3.5 Sonnet](https://aws.amazon.com/bedrock/anthropic/) 模型。预设计图像包括各种戏剧姿势、设计师服装，以及用于引导模型输出的辅助素材。接下来，这些描述、用户草图与补充素材作为输入，提供给本地扩散模型，并搭配 ControlNet 或类似框架来生成目标图像。在其中两个模块中，先生成较低分辨率的图像以缩短推理时间。这些质量较低的图像再按模块不同，被送入 Amazon Bedrock 中的 [Nova Canvas](https://aws.amazon.com/ai/generative-ai/nova/) 或 Stable Diffusion 3.5，以快速生成质量更高的图像。例如，在使用 Nova Canvas 时，我们采用 IMAGE_VARIATION 任务类型，从 DeepSeek VLM 生成的低分辨率背景草图得到 2048 x 512 像素的图像。这种做法把一部分推理负载外移，使我们能够使用更小的 Amazon SageMaker AI 实例类型，而不牺牲质量或速度。

随后，工作流按各输出类型特定的最终处理例程继续。对背景图像，会把一名演员合成到图像底边附近的不同位置。自定义姿势被转换为纹理对象，对象草图则通过 image-to-3D 模型转换为 3D 网格对象。最后，Amazon SageMaker AI 把图像素材存入 [Amazon S3](https://aws.amazon.com/s3/) 存储桶，主 AWS Lambda 函数可从那里取回。

# 持续部署与管理

Lambda 函数的代码部署由 [AWS CodeBuild](https://aws.amazon.com/codebuild/) 处理。该任务负责监听 GitHub 上的拉取请求合并、更新 EFS 中的 Python 依赖，并把更新部署到主 Lambda 函数。这一代码部署策略支持在我们的开发、预发与生产环境之间做一致可靠的更新，免除了手动部署与更新代码的需要，也降低了随之而来的风险。

SageMaker AI 端点由一个自定义 Web 界面管理，管理员可通过它部署“已知良好”的端点配置，从而实现基础设施的快速部署、迅速重新部署与简单关停。该看板还包含 Amazon SQS 中运行任务与 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) Logs 的指标，以便剧组从流水线中清除消息。

# 经验教训与改进

在完成这些演出之后，事后回顾，我们有一些建议与考量，对未来的迭代会有帮助。我们建议使用 [AWS CloudFormation](https://aws.amazon.com/cloudformation/) 或类似工具，减少应用中所用服务的手动部署与更新。许多开发者遵循开发、预发、生产的流水线来做修改与增强，因此自动化配置服务相比手动部署能减少产生的错误。

通过采用模块化、无服务器、事件驱动的方式，我们构建了一套可靠且易于维护的云架构。借助 AWS 托管服务，开发者与管理员可以专注于系统设计而非系统维护。总体而言，我们发现 AWS 托管服务表现非常出色，提供了在高风险环境中开发复杂技术架构以支持实时图像推理的手段。

这个项目的性质造就了一个独特的用例。我们需要一种方式来处理某一时刻突然涌入的大量推理请求。这波请求只持续 15 分钟，因此我们需要一个既可靠又短暂存在的方案。我们评估了 Amazon EC2 与 Amazon SageMaker AI，作为按需部署 20 多台实例的主要选项。为了决定最佳系统，我们考察了以下几点：按需请求的可靠性、维护负担、复杂度、部署与负载均衡。Amazon EC2 完全有能力满足这些需求，但要获得所需的按需实例很有挑战，而维护那么多主机也带来过重的维护负担。Amazon SageMaker AI 满足了我们所有标准：配置直接、部署简单可靠，并有集成的负载均衡服务。最终，我们选择把大部分模型托管在 SageMaker AI 上，同时由 Amazon Bedrock 提供对 Nova Canvas、Stable Diffusion 3.5 与 Claude 3.5 Sonnet 等模型的托管无服务器访问。[Amazon EKS](https://aws.amazon.com/eks/) 是另一个可能满足我们需求的选项。它擅长快速部署且可无缝扩展，但我们认为 Amazon SageMaker AI 是这个项目的正确选择，因为它的配置速度快。

虽然 SageMaker AI 在现场演出期间被证明对实时推理可靠，但它也占了我们项目成本的最大份额——约占云总支出的 40%。在排练与开发期间，我们观察到空闲或未使用的 SageMaker AI 端点可能成为成本攀升的主要来源。为缓解这一点，我们用 [Amazon EventBridge](https://aws.amazon.com/eventbridge/) 调度器与 AWS Lambda 实现了每晚自动关停流程。这一简单的自动化步骤避免了资源被无意中一直开着，帮助我们在不牺牲性能的前提下保持成本可预测。我们也在为第二阶段研究其他降本策略。

# 结语

通过有意识地选择使用 AWS 生成式 AI 服务与 AWS 托管服务来支持 REMAP 的音乐剧 *Xanadu* 沉浸式演出，我们得以证明：用 AWS 支持新型、动态的娱乐形式是可行的。

我们展示了[无服务器](https://aws.amazon.com/serverless/)事件驱动架构是构建这类服务的一种快速且低成本的方式，也展示了 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 与 [Amazon SageMaker AI](https://aws.amazon.com/sagemaker-ai/) 如何协同工作，用上全部可用的生成式 AI 模型。我们介绍了自己的消息流水线以及其中进行的消息处理。我们讨论了所用的生成式 AI 模型及其功能与实现。最后，我们展示了在这套系统上继续发展沉浸式音乐剧的潜力。
