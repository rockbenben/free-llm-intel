# 在 AWS 上构建超低延迟语音 AI 应用

对话式 AI 正在改变人与技术的交互方式。从虚拟助手、AI 驱动的联络中心，到实时翻译和无障碍工具，语音优先的界面正迅速成为全球数百万用户的默认交互方式。

然而，交付真正自然的语音体验仍然是 AI 基础设施中最难的挑战之一。用户期待的是接近真人的响应速度。延迟过高会打断对话节奏、侵蚀信任。要让人感到自然，AI 生成的语音必须落在与人类轮流发言相同的时间窗口内。

本文介绍 AWS 合作伙伴、专注实时语音 AI 的 [Cartesia](https://www.cartesia.ai/)，如何用专门构建的状态空间模型（State Space Models，SSM）和 AWS 基础设施，在全球规模下交付 100ms 以内的文本转语音与语音转文本。开发者可以据此构建出与真人对话几乎无从分辨的语音体验。

## 对话式 AI 的兴起与延迟预期

各行业对实时语音 AI 的需求都在快速增长：

- **联络中心：** 处理数百万次客户交互的 AI agent 需要即时生成语音，才能维持自然的对话。
- **远程医疗：** 远程问诊需要低延迟语音，才能实现准确、有共情的沟通。
- **游戏与虚拟世界：** 沉浸式体验需要为非玩家角色（NPC）和玩家交互实时合成语音。
- **无障碍：** 屏幕阅读器和语音接口必须即时响应，才能服务视障用户。
- **呼入与呼出销售：** AI 销售 agent 必须不带尴尬停顿地回应，才能筛选线索、处理异议、让潜在客户继续留在通话中。

传统的基于 transformer 的文本转语音（TTS）模型在流式延迟上表现吃力，因为它们要处理完整个序列才开始产出输出。这一架构限制造成了一种根本性的张力：质量更高往往意味着延迟更高。一类新的模型——状态空间模型（State Space Models）——化解了这一权衡。

## 面向语音的 AI：状态空间模型（SSM）

状态空间模型（SSM）处理序列的方式，与当今多数 AI 背后的架构 transformer 有根本差异。transformer 使用一种叫注意力（attention）的机制，把序列里的每一个元素与其他每一个元素逐一比较，结果是计算量随序列变长成平方级增长。SSM 则把序列看作一个随时间连续演化的系统，逐步处理它，并把一个紧凑的内部状态向前携带。这种方式可以转换成计算机高效处理的形式，从而在某些长序列上保持低成本。正是这种效率让 SSM 非常适合实时语音这类实时、流式数据。

SSM 在音频处理上的主要优势包括：

- 高质量的长程依赖：结构化 SSM 是线性递归的一种形式，但其状态参数化能在很长的音频序列上保留信息，避免了长程信号衰减——而这正是限制经典循环神经网络（RNN）、例如长短期记忆（LSTM）网络的问题。
- 恒定的内存占用：与缓存所有历史 token 的 transformer 不同，SSM 只维持一个固定大小的隐藏状态。
- 原生流式支持：递归结构逐个 token 处理输入，因此无需改动架构就能支持真正的流式。

这些特性使 SSM 格外适合质量与延迟都不容妥协的实时语音应用。

## 工作原理：用于实时语音的 SSM

Cartesia 把这些 SSM 优势落地到两个生产级语音模型中：负责语音生成的 Sonic 和负责转写的 Ink。

### Cartesia 介绍

Cartesia 是一家实时多模态智能公司，构建了一款专门基于状态空间模型（State Space Model）架构的语音 AI 应用。Cartesia 由率先推动 SSM 进展的研究者创立，其应用的设计目标是在人类感知的极限处完成流式推理。

该应用有两个核心模型：负责文本转语音的 Sonic 和负责语音转文本的 Ink，两者都针对 100ms 以内的首字节延迟做了优化，同时保持录音室级别的输出质量。

### Sonic（文本转语音）

Sonic 是 Cartesia 的旗舰流式文本转语音模型，以 100ms 以内的延迟交付超真实的语音合成：

- **首个音频字节约 90ms：** 用户几乎在瞬间就能听到语音回应。
- **超真实的语音质量：** 在 44 种以上语言上具备自然的韵律、情感与表现力。
- **极少数据的声音克隆：** 用 10 秒的音频样本即可创建听感自然的自定义音色。
- **流式原生的架构：** 在完整的文本输入接收完毕之前，音频就开始生成。
- **上下文感知的合成：** 在长段落中保持一致的语气与风格。

Sonic 推荐给那些希望以最少运维开销实现最快投产的团队。调用 API，即可实时收到流式音频。

### Ink（语音转文本）

Ink 是 Cartesia 的流式语音转文本模型，专为对话式 AI 应用而构建：

- **原生轮次检测：** 自动识别说话人何时说完自己这一轮，无需单独的语音活动检测（VAD）或端点检测模型就能缓解尴尬的停顿。
- **上下文感知的端点检测：** 用语义理解区分句子中间的停顿与真正的对话边界。
- **流式转写：** 在用户说话的同时实时输出部分转写结果，因此下游大语言模型（LLM）在对方这一轮说完之前就能开始组织回应。
- **噪声鲁棒性：** 在真实部署常见的嘈杂环境中保持准确度。
- **多说话人支持：** 从容处理重叠语音与说话人切换。

Sonic 与 Ink 一起提供了构建对话式 agent 所需的完整语音 AI 技术栈，让交互体验贴近真人。

## 在 AWS 上部署 Cartesia

如果你需要数据主权、延迟控制或合规性，可以把 Cartesia 模型直接部署进你自己的 AWS 账户。Sonic 以 Amazon SageMaker AI 模型包的形式通过 AWS Marketplace 交付，你把它部署到完全运行在自己虚拟私有云（VPC）内的 SageMaker AI 端点上。推理数据不会离开你的账户。

本节介绍的部署模式针对 Sonic。Ink 目前通过 Cartesia API 提供，你可以通过 AWS Marketplace 里的 [Cartesia Voice AI Platform](https://aws.amazon.com/marketplace/pp/prodview-bcf67mlwzvkce) 列表页购买。Sonic 有两种主要模式。

### 模式 1：Amazon SageMaker AI（AWS Marketplace 模型包）

在 Amazon SageMaker AI 上部署，是获得托管的、VPC 内 Sonic 端点最快的路径。Sonic 以 AWS Marketplace 模型包的形式交付，因此有一次性的订阅步骤，它会为你的账户授予一个按 AWS Region 划分的模型包 ARN。随后你从该 ARN 创建 SageMaker AI 端点，可以从控制台操作，也可以用 SageMaker 或 Boto3 SDK。下面的步骤遵循 Cartesia 官方的部署 notebook。

#### 前提条件

请在 Amazon SageMaker Notebook Instance 或 SageMaker Studio 中运行。

AWS Identity and Access Management（IAM）执行角色需要 `AmazonSageMakerFullAccess`。

要完成订阅，你的角色（以及你本人）需要 `aws-marketplace:Subscribe`、`aws-marketplace:Unsubscribe` 和 `aws-marketplace:ViewSubscriptions`。否则，该账户必须已经订阅了这个列表页。

部署之前，请从模型包的 `SupportedRealtimeInferenceInstanceTypes` 字段中挑选一种受支持的实例类型：``

- `ml.g6e.xlarge` 或更大
- `ml.g7e.2xlarge` 或更大
- `ml.g7.2xlarge` 或更大
- `ml.p5.48xlarge`
- `ml.p5en.48xlarge`

如果你所选实例类型的 applied value 低于你当前用量加上计划的端点实例数，你可能需要申请提高服务配额。详见 [SageMaker AI 配额](https://docs.aws.amazon.com/general/latest/gr/sagemaker.html#limits_sagemaker)。

### 模式 2：在 EC2 GPU 实例上自管理

有些团队已有 GPU 基础设施、有严格的网络要求，或者需要把 Cartesia 与其他服务共置。针对这些情况，你可以自己在 Amazon Elastic Compute Cloud（Amazon EC2）GPU 实例上运行模型容器。这会让你完全掌控运行时、扩缩容和网络路径。它使用的是从 Cartesia 获取的容器镜像，而不是 AWS Marketplace 模型包。

![自管理方式在 Amazon EC2 GPU 实例上部署 Cartesia Sonic 的八步流程，从获取容器镜像到加入可观测性与韧性](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/22/ML-21700-5.png)

图 5：在 Amazon EC2 GPU 实例上自管理部署 Cartesia Sonic 的流程

**获取容器镜像。** 向 Cartesia 索取 Sonic 容器镜像及许可条款。把它复制进你自己的私有 Amazon Elastic Container Registry（Amazon ECR）仓库，这样你的计算面就能用受 IAM 范围限制的凭据拉取镜像，而不必大规模地去访问外部 registry。

**选择 GPU 实例系列。** Sonic 运行在 NVIDIA GPU 实例上。G6（L4）和 G6e（L40S）系列是实时 TTS 的最佳平衡点，更早的 G5（A10G）也可以用。让 GPU 显存与 vCPU 匹配你的目标并发数，并且为了让扩缩容最简单，每个模型副本优先选用单 GPU 实例。

**搭建计算面（Amazon Elastic Container Service（Amazon ECS）或 Amazon Elastic Kubernetes Service（Amazon EKS））。** 走 ECS：注册一个 GPU 任务定义（设置容器的 GPU 资源需求，例如把 `resourceRequirements` 的 type 设为 GPU），并把它作为服务运行在 Application Load Balancer 后面。走 EKS：使用 EKS 的 GPU 优化 AMI 创建 GPU 节点组（或 Karpenter provisioner），安装 NVIDIA device plugin，把容器以 Deployment 形式部署，前面由 Service/Ingress 承接流量。

**为低延迟配置网络。** 把推理节点放进 cluster placement group 以把节点间延迟降到最低，把副本保持在同一个可用区内以获得最短路径，并为 ECR/S3 的拉取使用 VPC 终端节点。对于混合云或本地（on-premises）调用方，通过 AWS Direct Connect 或私有 Network Load Balancer 终止流量，以避免公网跳数。

**高效加载模型权重。** 把模型权重存放在跨副本挂载的共享低延迟卷（Amazon Elastic File System（Amazon EFS）或 Amazon FSx for Lustre）上，这样新启动的 pod/任务不必各自重新下载数 GB 的模型产物。在容器启动时预热模型，并暴露健康检查，让负载均衡器只把流量路由给就绪的副本。

**调优批处理与并发。** 把容器的最大批大小与并发流上限设置成与你的流量画像匹配。更大的批大小能提升 GPU 利用率，但会增加首字节延迟，所以要对照你 100ms 以内的目标来调优。对 `streams-per-GPU` 做基准测试，找出你据以扩缩容的副本容量。

**实现自定义自动扩缩容。** 用真正反映负载的信号来扩缩容——活跃的音频流数量或 GPU 利用率——而不是 CPU。在 Amazon ECS 上，使用 AWS Application Auto Scaling 配合自定义的 Amazon CloudWatch 指标。在 Amazon EKS 上，使用由 GPU 或流数量指标驱动的 HPA/KEDA，并用 Karpenter（或 Cluster Autoscaler）随副本增长补充 GPU 节点。

**增加可观测性与韧性。** 把延迟（首字节时间）、流数量和 GPU 指标上报到 CloudWatch。跨节点至少运行两个副本以保证可用性。设置滚动更新或 draining 策略，避免部署时丢掉正在传输中的音频流。

当你需要把 Cartesia 集成进已有的机器学习（ML）系统、满足托管服务无法覆盖的网络或合规要求，或者用 Reserved 或 Spot GPU 容量优化成本时，推荐采用这种方式。代价在于，本该由 SageMaker 替你处理的资源供给、扩缩容、打补丁和监控都要自己承担。

**了解更多：** 参见 [面向 GPU 工作负载的 Amazon ECS 任务定义](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs-gpu.html)、[在 Amazon EKS 上管理 NVIDIA GPU 设备](https://docs.aws.amazon.com/eks/latest/userguide/device-management-nvidia.html) 与 [GPU 加速 EC2 实例入门](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/gpu-instances-started.html)。

### 选择合适的部署模式

AWS 提供了两种运行 Sonic 的方式，各自适配不同的起点。

托管路径，即使用 AWS Marketplace 里的 Amazon SageMaker AI 模型包，是大多数团队的默认选择：完成订阅，几分钟内部署出一个 VPC 内的端点，把扩缩容和运维交给 SageMaker。

自管理路径，即自己在 EC2 GPU 实例上运行模型容器，是为有特定约束的团队设计的：已有的 GPU 基础设施、严格的网络要求，或者需要把 Cartesia 与其他服务共置。对这些团队来说，对运行时、扩缩容和网络路径的完全掌控，比部署速度更重要。

下表总结了两者的对比。

| **判断标准** | **SageMaker（Marketplace）** | **EC2 GPU（自管理）** |
| --- | --- | --- |
| 部署耗时 | 订阅之后几分钟 | 数小时到数天 |
| 计算 | 实时端点。受支持的实例见 `SupportedRealtimeInferenceInstanceTypes`。 | EC2 GPU 实例 |
| 运维控制 | 由 AWS 托管 | 完全掌控 |
| 扩缩容 | SageMaker 自动扩缩容 | 自定义扩缩容策略 |
| 成本模型 | 软件费用 + 每实例小时 + 基础设施 | EC2（Reserved/Spot 节省） |
| 网络 | VPC 内端点（网络隔离） | placement group、Direct Connect |
| 最适合 | 快速、托管、VPC 内 | 自定义基础设施、最大化控制 |

除了把 Cartesia 部署在你自己的账户中，这些模型已经在 Amazon 的服务内部经过生产环境验证，而很少有环境比实时语音的联络中心更苛刻。Amazon Connect 正是这样一个试炼场。

## 生产中：Amazon Connect

本节展示 Cartesia 的语音模型如何在 Amazon Connect 内部以生产规模运行。

### Amazon Connect 是什么？

[Amazon Connect](https://aws.amazon.com/connect/) 是一项基于云的联络中心服务，企业用它搭建并运营客户支持，处理呼入与呼出的语音通话、聊天和消息。凭借按需付费的定价和与 AWS 服务的深度集成，Amazon Connect 每天支撑着从金融服务到医疗等各行业数百万次客户交互。

### Cartesia 如何支撑 Amazon Connect 的体验

Cartesia 的语音 AI 模型与 Amazon Connect 原生集成，带来新一代联络中心体验：

- **即时响应：** 消除不自然的停顿，避免客户对 AI 驱动的交互失去信心。
- **实时转写：** Ink 提供带智能轮次检测的实时转写，服务坐席辅助工作流。
- **多语言支持：** 以一致的音色质量和自然韵律，服务 44 种以上语言的客户。
- **可扩展的基础设施：** 在高峰时段流量激增时，语音质量与延迟都不降级。

把 Amazon Connect 的全渠道编排能力与 Cartesia 的实时语音 AI 结合起来，你就能在自动化复杂客户交互的同时，保持那种建立信任与忠诚所需的自然、敏捷的体验。
