# 在 AWS 上构建超低延迟语音 AI 应用程序

对话式人工智能正在改变人类与技术互动的方式。从虚拟助理和人工智能驱动的联络中心到实时翻译和辅助工具，语音优先界面正在迅速成为全球数百万用户的默认交互模式。

然而，提供真正自然的语音体验仍然是人工智能基础设施中最艰巨的挑战之一。用户期望像人类一样的响应能力。过多的延迟会破坏对话流程并削弱信任。为了感觉自然，人工智能生成的语音必须与人类轮流在同一时间窗口内到达。

本文介绍了专注于实时语音 AI 的 AWS 合作伙伴 [Cartesia](https://www.cartesia.ai/) 如何使用专门构建的状态空间模型 (SSM) 和 AWS 基础设施在全球范围内提供 100 毫秒以下的文本到语音和语音到文本。开发人员可以构建与人类对话没有区别的语音体验。

## 对话式人工智能的兴起和延迟预期

各行业对实时语音人工智能的需求正在快速增长：

- **联络中心：** 处理数百万客户交互的人工智能代理需要即时生成语音以保持自然对话。
- **远程医疗：** 远程患者咨询需要低延迟语音，以实现准确、富有同理心的沟通。
- **游戏和虚拟世界：** 沉浸式体验需要非玩家角色 (NPC) 和玩家交互的实时语音合成。
- **辅助功能：** 屏幕阅读器和语音界面必须立即响应，才能为有视觉障碍的用户提供服务。
- **入站和出站销售：** 人工智能销售代理必须毫不尴尬地做出回应，以筛选潜在客户、处理异议并保持潜在客户的在线状态。

传统的基于转换器的文本转语音 (TTS) 模型面临着流延迟的问题，因为它们在生成输出之前会处理整个序列。这种架构限制造成了根本性的紧张：更高的质量通常意味着更高的延迟。一类新的模型，即状态空间模型，解决了这种权衡问题。

## 语音人工智能：状态空间模型 (SSM)

状态空间模型 (SSM) 采用与Transformer（当今大多数人工智能背后的架构）截然不同的方法来处理序列。 Transformer 使用一种称为注意力的机制，它将序列中的每个元素与其他每个元素进行比较。因此，随着序列变长，计算量呈二次方增长。相反，SSM 将序列视为一个随时间不断演化的系统，逐步对其进行处理并向前推进紧凑的内部状态。这可以转换成计算机有效处理的形式，从而使某些长序列的成本保持较低。这种效率使 SSM 非常适合实时流数据，例如现场语音。

SSM 用于音频处理的主要优势包括：

- 高质量的长程依赖性：结构化 SSM 是线性递归的一种形式，但其状态参数化保留了长音频序列上的信息，避免了限制长短期记忆 (LSTM) 网络等经典循环神经网络 (RNN) 的长程信号衰减。
- 恒定的内存占用：与缓存所有先前令牌的转换器不同，SSM 维护固定大小的隐藏状态。
- 原生流支持：循环结构逐个处理输入令牌，因此无需架构修改即可支持真正的流。

这些特性使 SSM 特别适合质量和延迟都不可协商的实时语音应用。

## 工作原理：用于实时语音的 SSM

Cartesia 将这些 SSM 优势应用于两种生产语音模型：用于语音生成的 Sonic 和用于转录的 Ink。

### 笛卡尔简介

Cartesia 是一家实时多模式情报公司，专门基于状态空间模型架构构建了语音 AI 应用程序。 Cartesia 的应用程序由 SSM 进步的先驱研究人员创建，专为人类感知边缘的流式推理而设计。

该应用程序具有两个核心模型：用于文本转语音的 Sonic 和用于语音转文本的 Ink，这两个模型均针对低于 100 毫秒的第一字节延迟进行了优化，同时保持工作室质量的输出。

### 索尼克（文本转语音）

Sonic 是 Cartesia 的旗舰流式文本转语音模型，可提供超逼真的语音合成，延迟低于 100 毫秒：

- **大约 90 毫秒内的第一个音频字节：** 用户几乎立即听到语音响应。
- **超真实的语音质量：** 超过 44 种语言的自然韵律、情感和表现力。
- **用最少的数据进行语音克隆：** 从 10 秒的音频样本中创建听起来自然的自定义语音。
- **流媒体本机架构：** 音频在收到全文输入之前开始生成。
- **上下文感知合成：** 在长段落中保持一致的语气和风格。

建议希望以最小的运营开销实现最快的生产时间的团队使用 Sonic。调用API并实时接收流媒体音频。

### 墨水（语音转文本）

Ink 是 Cartesia 的流式语音转文本模型，专为对话式 AI 应用程序而构建：

- **本机转弯检测：** 自动识别发言者何时完成转弯，从而减轻尴尬的停顿，而无需单独的语音活动检测 (VAD) 或端点模型。
- **上下文感知结束指向：** 使用语义理解来区分句子中间的停顿和真正的对话边界。
- **流式转录：** 在用户说话时实时发出部分转录，因此下游大语言模型 (LLM) 可以在回合结束之前开始形成其响应。
- **噪声鲁棒性：** 在现实部署中常见的噪声环境中保持准确性。
- **多扬声器支持：** 优雅地处理重叠语音和扬声器转换。

Sonic 和 Ink 共同提供了构建人性化对话代理所需的完整语音 AI 堆栈。

本节中的部署模式涵盖 Sonic。 Ink 目前可通过 Cartesia API 获取，您可以通过 AWS Marketplace 中的 [Cartesia Voice AI Platform](https://aws.amazon.com/marketplace/pp/prodview-bcf67mlwzvkce) 购买。索尼克有两种主要模式可用。

### 选项 2：在 EC2 GPU 实例上进行自我管理

一些团队拥有现有的 GPU 基础设施、严格的网络要求，或者需要将 Cartesia 与其他服务共置。对于这些情况，您可以在 Amazon Elastic Compute Cloud (Amazon EC2) GPU 实例上自行运行模型容器。这使您可以完全控制运行时、扩展和网络路径。它使用从 Cartesia 获取的 Cartesia 容器映像，而不是 AWS Marketplace 模型包。

![Amazon EC2 GPU 实例上自管理 Cartesia Sonic 的八步部署流程，从获取容器镜像到添加可观察性和弹性](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/22/ML-21700-5.png)

图 5：Amazon EC2 GPU 实例上 Cartesia Sonic 的自我管理部署流程

**获取容器映像。** 向 Cartesia 请求 Sonic 容器映像和许可条款。将其复制到您自己的私有 Amazon Elastic Container Registry (Amazon ECR) 存储库中，以便您的计算平面可以使用 IAM 范围的凭证提取它，而不是大规模访问外部注册表。

**选择您的 GPU 实例系列。** Sonic 在 NVIDIA GPU 实例上运行。 G6 (L4) 和 G6e (L40S) 系列是实时 TTS 的最佳平衡。早期的 G5 (A10G) 也可以使用。将 GPU 内存和 vCPU 与您的目标并发量相匹配，并且更喜欢每个模型副本使用单 GPU 实例以实现最简单的扩展。

**配置计算平面（Amazon Elastic Container Service (Amazon ECS) 或 Amazon Elastic Kubernetes Service (Amazon EKS)）。** 对于 ECS：注册 GPU 任务定义（设置容器的 GPU 资源要求，例如，类型为 GPU 的“resourceRequirements”）并将其作为 Application Load Balancer 背后的服务运行。对于 EKS：使用 EKS GPU 优化的 AMI 创建 GPU 节点组（或 Karpenter 配置程序），安装 NVIDIA 设备插件，并将容器部署为以服务/入口为前端的 Deployment。

**配置网络以实现低延迟。** 将推理节点放置在集群放置组中以最大程度地减少节点间延迟，将副本保留在单个可用区中以获得最紧密的路径，并使用 VPC 端点进行 ECR/S3 拉取。对于混合或本地呼叫者，终止通过 AWS Direct Connect 或专用网络负载均衡器的流量，以避免公共互联网跃点。

**高效加载模型权重。** 将模型权重存储在跨副本安装的共享低延迟卷（Amazon Elastic File System (Amazon EFS) 或 Amazon FSx for Lustre）上，以便新的 pod/任务启动时无需重新下载多 GB 工件。在容器启动时预热模型并公开运行状况检查，以便负载均衡器仅路由到就绪的副本。

**调整批处理和并发性。** 设置容器的最大批处理大小和并发流限制以匹配您的流量配置文件。较高的批量大小可以提高 GPU 利用率，但会增加第一个字节的延迟，因此请根据低于 100 毫秒的目标进行调整。对“每 GPU 流数”进行基准测试以查找您将扩展的副本容量。

**实现自定义自动缩放。** 根据反映实际负载、活动音频流计数或 GPU 利用率（而不是 CPU）的信号进行缩放。在 Amazon ECS 上，将 AWS Application Auto Scaling 与自定义 Amazon CloudWatch 指标结合使用。在 Amazon EKS 上，使用由 GPU 或流计数指标驱动的 HPA/KEDA，并随着副本的增长通过 Karpenter（或 Cluster Autoscaler）添加 GPU 节点。

**增加可观察性和弹性。** 将延迟（第一个字节的时间）、流计数和 GPU 指标发送到 CloudWatch。跨节点运行至少两个副本以确保可用性。设置滚动更新或耗尽策略，以便部署不会丢弃正在进行的音频流。

当将 Cartesia 集成到现有机器学习 (ML) 系统、满足托管服务无法提供的网络或合规性要求，或者使用预留或 Spot GPU 容量优化成本时，建议使用此方法。权衡是您自己负责配置、扩展、修补和监控，否则 SageMaker 将为您处理。

**了解更多信息：** 请参阅[GPU 工作负载的 Amazon ECS 任务定义](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs-gpu.html)、[在 Amazon EKS 上管理 NVIDIA GPU 设备](https://docs.aws.amazon.com/eks/latest/userguide/device-management-nvidia.html) 和[GPU 加速 EC2 入门实例](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/gpu-instances-started.html)。

### 选择正确的部署模式

AWS 提供两种运行 Sonic 的方法，每种方法都适合不同的起点。

使用 AWS Marketplace 中的 Amazon SageMaker AI 模型包的托管路径是大多数团队的默认路径：您可以订阅、在几分钟内部署到 VPC 内终端节点，并让 SageMaker 处理扩展和操作。

自我管理路径是在 EC2 GPU 实例上自行运行模型容器，专为具有特定限制的团队而设计：现有 GPU 基础设施、严格的网络要求或需要将 Cartesia 与其他服务共置。对于这些团队来说，对运行时、扩展和网络路径的完全控制比部署时间更重要。

下表总结了两者的比较。

| **标准** | **SageMaker（市场）** | **EC2 GPU（自我管理）** |
| ---| ---| ---|
|部署时间 |订阅后几分钟 |几小时到几天 |
|计算|实时端点。有关支持的实例，请参阅“SupportedRealtimeInferenceInstanceTypes”。 | EC2 GPU 实例 |
|操作控制|由 AWS 管理 |完全控制|
|缩放| SageMaker 自动扩展 |自定义扩展策略 |
|成本模型|软件费用 + 每个实例小时 + 基础设施 | EC2（预留/现货储蓄）|
|网络| VPC 内端点（网络隔离）|归置组、直接连接 |
|最适合 |快速、托管、VPC 内 |定制基础设施，最大控制 |

除了在您自己的账户中部署 Cartesia 之外，这些模型已经在 Amazon 服务中的生产中得到了验证，很少有环境比实时联络中心对实时语音的要求更高。 Amazon Connect 正是这样的试验场。

### 什么是 Amazon Connect？

[Amazon Connect](https://aws.amazon.com/connect/) 是一项基于云的联络中心服务，企业用它来设置和运行处理入站和出站语音呼叫、聊天和消息传递的客户支持操作。凭借即用即付定价以及与 AWS 服务的深度集成，Amazon Connect 每天为从金融服务到医疗保健等各行业的数百万次客户交互提供支持。

### Cartesia 如何推动 Amazon Connect 体验

Cartesia 的语音 AI 模型与 Amazon Connect 本地集成，以提供下一代联络中心体验：

- **即时响应：** 减少不自然的停顿，以免削弱客户对人工智能交互的信心。
- **实时转录：** Ink 为座席辅助工作流程提供带有智能轮流检测的实时转录。
- **多语言支持：** 以超过 44 种语言为客户提供一致的语音质量和自然的韵律。
- **可扩展的基础设施：** 处理高峰时段的流量高峰，而不会降低语音质量或延迟。

通过将 Amazon Connect 的全渠道编排与 Cartesia 的实时语音 AI 相结合，您可以自动执行复杂的客户交互，同时保持自然、响应迅速的体验，从而建立信任和忠诚度。
