# 构建由 Amazon Nova 2 Lite 和 AWS Quick 驱动的智能保险核保 agent

保险核保需要分析多个数据源、评估风险，并做出符合监管要求的决策。核保人员面临三个核心挑战：

- 数据孤岛分散在客户关系管理（CRM）系统、文档存储库和事务型数据库中
- 监管要求决策可解释、可审计，而传统的[黑箱 AI](https://jolt.law.harvard.edu/assets/articlePDFs/v31/The-Artificial-Intelligence-Black-Box-and-the-Failure-of-Intent-and-Causation-Yavar-Bathaee.pdf) 无法满足这一要求
- 需要在整个业务组合中一致地执行自动化核保规则，并主动进行欺诈检测

本文介绍如何用一套企业级核保方案来克服这些挑战：借助 [Amazon Nova 2 Lite](https://aws.amazon.com/nova/) 统一你的数据源，并给出可审计的风险评估。

## 方案概述

该方案使用 [Model Context Protocol (MCP) 工具](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)完成保险欺诈检测、申请人风险评估和核保决策。当工具基于用户查询被调用时，它会从所需数据源获取数据——例如 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）这样的文档存储库，以及 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 这样的数据库——并调用 [Amazon Nova 2 Lite](https://aws.amazon.com/ai/generative-ai/nova/understanding/) 大语言模型（LLM）进行分析与决策。在获取相应的 system prompt 和所提供的上下文之后，LLM 按工具期望的结构返回响应。MCP 服务器部署在 [Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-mcp.html) 中，并采用 [OAuth 2.0](https://auth0.com/intro-to-iam/what-is-oauth-2) 入站授权。[AWS Quick](https://aws.amazon.com/quicksuite/) MCP 客户端使用服务认证进行配置，以允许对 MCP 服务器的入站连接。用户以自然语言与 Quick [聊天 agent](https://docs.aws.amazon.com/quicksuite/latest/userguide/working-with-agents.html)交互。该 agent 调用所需的 MCP 工具，并与用户进行多轮对话。

*图 1：架构与数据流*

该工作流包含以下步骤：

- 通过认证的 [Quick 用户](https://docs.aws.amazon.com/quicksuite/latest/userguide/user-types.html)访问 [Quick 聊天 agent](https://docs.aws.amazon.com/quicksuite/latest/userguide/working-with-agents.html)，并通过助手聊天界面提交 prompt。例如：“评估申请人 APP-0900 的风险。”
- 该聊天 agent 与 [AWS Quick MCP Actions Integrations](https://docs.aws.amazon.com/quicksuite/latest/userguide/mcp-integration.html)集成，以便对[部署在 AgentCore Runtime 中的 MCP 服务器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-mcp.html)调用操作。agent 分析 prompt 以理解意图、识别关键实体（例如申请人 ID 和理赔编号），并决定调用哪些 [MCP 工具](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)。
- [Quick MCP 客户端](https://docs.aws.amazon.com/quicksuite/latest/userguide/mcp-integration.html)使用 OAuth 客户端凭证向 [Amazon Cognito](https://aws.amazon.com/cognito/) 请求[访问令牌](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-the-access-token.html)。Amazon Cognito 校验凭证并签发一个短期有效的访问令牌。Quick 将该令牌包含在发往 AgentCore Runtime 的请求中，由后者向 Amazon Cognito 校验该令牌。
- AgentCore Runtime 内置转换能力，会把传入请求转换为 MCP [JSON-RPC 2.0](https://www.jsonrpc.org/specification) 格式，并在 MCP 服务器上调用相应工具。可以在 AgentCore Runtime 上启用日志记录，将事件记录到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)。
- MCP 服务器执行工具逻辑，从 DynamoDB 和 Amazon S3 检索数据，并通过 [Amazon Bedrock Converse API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html) 调用 Amazon Nova 2 Lite，生成带有详细推理过程的响应。
- 最终响应会被转换回与 Quick 传入请求协议相匹配的格式，并通过由聊天 agent 驱动的助手界面返回给用户。

Amazon Nova 2 Lite 可以请求工具并理解工具 schema。它会进行推理，根据用户查询确定需要哪些工具，然后生成带有已校验参数的工具请求，交由 MCP 服务器执行。方案部署包括以下高层步骤：

- 在 Amazon Bedrock AgentCore 上托管 MCP 服务器。
- 将 Quick 与 MCP 服务器集成。
- 测试集成。
- 创建并启动 Quick 聊天 agent。

## 前置条件

部署该方案需要满足以下前置条件：

- 一个 [AWS 账户](https://docs.aws.amazon.com/accounts/latest/reference/getting-started.html#getting-started-step1)
- Quick 已配置 Author Pro 订阅
- 具备创建 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色与策略以及 AWS 资源（包括 DynamoDB 表、S3 存储桶、Amazon Cognito 用户池和 AgentCore Runtime）的权限
- 可访问已安装 AWS SDK 和 Python 的命令行环境

## 在 Amazon Bedrock AgentCore 上托管 MCP 服务器

请完成以下步骤，在 Amazon Bedrock AgentCore 上托管 MCP 服务器：

- 克隆[代码仓库。](https://github.com/aws-samples/sample-quicksuite-chatagent-insurance-underwriting.git)

```
git clone https://github.com/aws-samples/sample-quicksuite-chatagent-insurance-underwriting.git
```

- 编辑配置文件 `config/enterprise_config.yaml`，填写 MCP 服务器的名称、Amazon Cognito 用户池、存放申请人和理赔数据的 DynamoDB 表，以及存放病历的 S3 存储桶。
- 设置虚拟环境：

```
python -m venv smart_insurance_agent_venv
source smart_insurance_agent_venv/bin/activate
pip install -r deployment/requirements.txt
```

- 可选：生成合成的申请人、病历和理赔数据。如果不需要生成合成数据，可跳过此步骤。

```
python deployment/load_data.py
```

合成数据生成使用 [faker](https://pypi.org/project/Faker/) 库生成申请人记录和理赔记录（写入 DynamoDB），以及以 JSON 格式写入 Amazon S3 的病历。你可以通过定制 load_data.py 来修改记录 schema 或格式，以按需生成数据。

- 将 MCP 服务器部署到 Amazon Bedrock AgentCore。

```
./deployment/deploy.sh
```

此步骤会创建 Amazon Cognito 用户池、构建 Docker 镜像、将其部署到 Amazon Bedrock AgentCore、配置 IAM 权限，并生成 `docs/QUICK_SUITE_INTEGRATION.md`，其中包含 MCP 服务器端点 URL 和用于与 Quick 集成的 OAuth 配置。

- 测试 MCP 工具的功能：

```
python tests/test_mcp_functionality.py
```

## 将 Quick 与 MCP 服务器集成

接下来，从 Quick 到 Amazon Bedrock AgentCore 端点建立服务到服务的 OAuth 连接。这样你的 Quick 聊天 agent 就能调用 MCP 服务器的操作来满足用户请求。

- 使用具备 Quick Author Pro 角色的凭证登录 Quick。
- 在 Quick 控制台的导航窗格中选择 **Integrations**。
- 选择 **Model Context Protocol** 旁边的加号，创建新的集成。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/02/image-4.png)

*图 3：创建 MCP 集成*

- 在 **Connect** 页面上，填写你托管在 Amazon Bedrock AgentCore 上的 MCP 服务器的集成详情：在 **Name** 中输入名称（例如 Insurance Underwriting Expert）。在 **Description** 中输入可选描述（例如 Integration with Insurance Underwriting MCP Server hosted in Bedrock AgentCore Runtime）。在 **MCP server endpoint** 中输入 MCP 服务器的 URL。选择 **Next**。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/02/image-5.png)

*图 4：MCP 端点配置*

- 在 **Authenticate **页面上提供以下信息：在 **Authentication settings** 中选择 **Service authentication**。在 **Authentication type** 中选择 **Service-to-service OAuth**。在 **Client ID** 中输入你的 OAuth 客户端 ID。在 **Client secret** 中输入你的 OAuth 客户端密钥。在 **Token URL** 中输入你的 OAuth 令牌 URL。
- 选择 **Create and continue**。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/02/image-6.png)

*图 5：认证配置*

- 在 **Review **页面上检查集成详情，然后选择 **Next**。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/02/image-7.png)

*图 6：检查所有配置*

- 在 **Share integration **页面上选择 **Next**。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/02/image-8-1.png)

*图 7：完成集成设置*

## 创建并启动 Quick 聊天 agent

在本节中，你将在 Quick 中创建一个自定义[聊天 agent](https://docs.aws.amazon.com/quicksuite/latest/userguide/custom-agents.html"%20\l%20"create-custom-agents)。请完成以下步骤：

- 在 Quick 控制台的导航窗格中选择 **Chat agents**。
- 选择 **Create chat agent**。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/02/image-13-1.png)

- 在 **Agent creator** 页面上选择 **Skip**。
- 为你的自定义聊天 agent 添加名称。聊天 agent 将以该名称被识别。
- 为你的自定义聊天 agent 添加可选描述，帮助用户理解该聊天 agent 的用途。
- 在 **Configure chat agent** 页面上提供以下信息：在 **Agent identity** 中定义聊天 agent 的身份。例如：你是 Nova，一位 AI 驱动的核保分析师，在可解释的风险评估和欺诈检测方面拥有深厚专长。借助高级推理能力，你可以访问企业保险数据，包括 1000+ 申请人档案、病历和理赔历史。在 **Persona instructions** 中输入聊天 agent 在对话中如何与用户交互的说明。例如：透明度和推理能力是你的关键差异化优势。始终说明建议的置信水平，并承认局限性。把复杂的保险决策拆解为清晰、合乎逻辑的步骤。在有数据时引用具体的申请人档案、病历和理赔记录。给出风险评分，并详细解释影响因素。在所有建议中纳入监管合规考量与业务影响。适时提出后续问题以深化分析。在 **Actions** 下选择 **Link actions**，选择你创建的操作连接器，然后选择 **Link**。选择 **Launch chat agent** 创建自定义聊天 agent。你会看到进度提示 Launching chat agent…（正在启动聊天 agent），几分钟后你会看到 Successfully launched chat agent（聊天 agent 启动成功）。

## 结论

该方案解决了核保的三个核心挑战：数据分散在各个系统中、监管要求决策可解释，以及需要在整个业务组合中检测欺诈。我们通过组合三个关键组件构建了该方案：Amazon Nova 2 Lite 为每个核保决策生成透明的逐步推理；Amazon Bedrock AgentCore 提供托管的 MCP 服务器基础设施，具备 OAuth 2.0 认证和自动扩缩容能力；Quick 提供自然语言查询与多轮对话上下文。该架构统一了 DynamoDB 和 Amazon S3 中的数据，通过无状态组件处理请求以实现横向扩展，并在 CloudWatch 中保留完整审计轨迹以满足监管合规要求。借助该方案，核保人员可以提出“评估申请人 APP-0900 的风险”这样的问题，并立即获得详细分析。调查人员可以查询“显示保单生效后 30 天内提交的所有理赔”，以识别可能存在不可信活动的线索。业务负责人则可以通过自然语言交互获得实时的业务组合洞察。

要试用该方案，请克隆 [GitHub 仓库](https://github.com/aws-samples/sample-quicksuite-chatagent-insurance-underwriting)并按照实施步骤操作。
