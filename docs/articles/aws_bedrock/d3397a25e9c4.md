# 在 Parcel Perform 用 text-to-SQL 推动数据民主化，支撑及时决策

*本文与 Parcel Perform 的 Le Vy 共同撰写。*

获取准确的数据，往往才是做出卓越且及时决策的真正分水岭。对于面向客户的决策与行动，这一点更为关键。正确实施的前沿 AI 可以帮助你的组织为面向客户的业务团队简化数据访问，从而做出准确、及时的决策，同时减少数据团队承担的无差别重体力工作。本文分享 [Parcel Perform](https://www.parcelperform.com/)——一家面向全球电商企业、领先的 AI 配送体验平台——如何落地这样一套方案。

准确的购后物流跟踪对许多电商商家至关重要。Parcel Perform 为电商商家提供 AI 驱动的智能端到端数据与配送体验，以及软件即服务（SaaS）系统。该系统使用 AWS 服务与前沿 AI，处理每天数亿条包裹配送轨迹数据，为商家提供跨承运商的统一跟踪能力，并强调准确与简洁。

Parcel Perform 的业务团队经常需要访问数据，以回答与商家包裹配送相关的问题，例如"上周配送延迟是否出现激增？如果有，在哪些中转设施观察到，问题的主要原因是什么？"以前，数据团队必须手工编写查询并执行才能取到数据。借助 Parcel Perform 新的生成式 AI 驱动的 text-to-SQL 能力，业务团队可以通过一个 AI 助手界面自助满足数据需求。本文讨论 Parcel Perform 如何通过 AWS 服务把生成式 AI、数据存储与数据访问结合起来，以做出及时的决策。

## 数据分析架构

方案从数据摄取、存储与访问开始。Parcel Perform 采用了下图所示的数据分析架构。

![Parcel Perform 包裹事件数据摄取架构图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/02/ML-18476-data-architecture.png)

Parcel Perform 包裹监控应用中的一类关键数据是包裹事件数据，其规模可达数十亿行。它包括包裹的物流状态变更、位置变更等等。这些来自多个业务部门的日常数据会落到托管在 [Amazon Relational Database Service](https://aws.amazon.com/rds/)（Amazon RDS）上的关系型数据库中。

关系型数据库适合应用侧快速的数据摄取与消费，但仍需要一套独立的分析栈，以可扩展、高性能的方式承担分析工作，同时不干扰主应用。这些分析需求包括回答诸如"上周有多少包裹延迟？"这类问题所对应的聚合查询。

Parcel Perform 使用 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）配合由 [Amazon Athena](https://aws.amazon.com/athena/) 提供的查询引擎来满足其分析需求。采用这种做法，Parcel Perform 既能享受高性价比的存储，又能按需通过 Athena 对数据运行 SQL 查询，而 Athena 按使用量计费。

Amazon S3 中的数据以 [Apache Iceberg](https://iceberg.apache.org/) 数据格式存储，该格式允许数据更新——这在本场景中有用，因为包裹事件有时会被更新。它还支持分区以获得更好的性能。2024 年底推出的 [Amazon S3 Tables](https://aws.amazon.com/s3/features/tables/) 是一项托管的 Iceberg 表功能，对你来说也可以成为一个选项。

Parcel Perform 使用由 [Amazon Managed Streaming for Apache Kafka](https://aws.amazon.com/msk/)（Amazon MSK）托管的 [Apache Kafka](https://kafka.apache.org/) 集群作为流，把数据从源端搬到 S3 存储桶。[Amazon MSK Connect](https://aws.amazon.com/msk/features/msk-connect/) 配合 [Debezium](https://debezium.io/) 连接器，以变更数据捕获（CDC）方式把数据从 Amazon RDS 流式传输到 Amazon MSK。

运行在 [Amazon Elastic Kubernetes Service](https://aws.amazon.com/eks/)（Amazon EKS）上的 [Apache Flink](https://flink.apache.org/) 处理来自 Amazon MSK 的数据流。它按 Iceberg 格式把这些数据写入 S3 存储桶，并更新 [AWS Glue Data Catalog](https://docs.aws.amazon.com/glue/latest/dg/catalog-and-crawler.html) 中的数据 schema。数据 schema 让 Athena 能够正确查询 S3 存储桶中的数据。

了解了数据的摄取与存储方式之后，我们来看看 Parcel Perform 的业务团队如何通过生成式 AI 驱动的数据服务助手来消费数据。

这项功能帮助 Parcel Perform 团队及其客户节省了时间，我们会在本文后段讨论。下一节将介绍支撑该功能的架构。

## Text-to-SQL AI agent 架构

Parcel Perform 的数据服务 AI 助手架构如下图所示。

![AI 助手架构图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/02/ML-18476-ai-assistant-architecture.png)AI 助手的 UI 由基于 [Fast API](https://fastapi.tiangolo.com/) 框架构建、托管在 Amazon EKS 上的应用提供支持。它前面还挂了一个 [Application Load Balancer](https://aws.amazon.com/elasticloadbalancing/application-load-balancer/)，以支持潜在的水平扩展。

该应用使用 [LangGraph](https://www.langchain.com/langgraph) 来编排大语言模型（LLM）调用、工具使用与记忆检查点（memory checkpointing）的工作流。该图使用多个工具，包括来自 [SQLDatabase Toolkit](https://python.langchain.com/docs/integrations/tools/sql_database/) 的工具，通过 Athena 自动获取数据 schema。该图还使用 [Amazon Bedrock Knowledge Bases retriever](https://python.langchain.com/docs/integrations/retrievers/bedrock/) 从知识库中检索业务信息。Parcel Perform 使用 [Amazon Bedrock 中的 Anthropic Claude 模型](https://aws.amazon.com/bedrock/claude/)来生成 SQL。

Athena 作为查询引擎查询 Amazon S3 上包裹事件数据的作用很清楚，但 Parcel Perform 仍然需要一个知识库。在这个用例中，当 LLM 掌握更多业务上下文信息、能够帮助解读数据库字段并把物流术语转换为数据表示时，SQL 生成表现更好。下面两个例子可以更好地说明这一点：

- Parcel Perform 的数据湖操作使用特定编码：`c` 表示创建，`u` 表示更新。分析数据时，Parcel Perform 有时只需关注最初的创建记录，即操作码等于 `c` 的记录。由于这类业务逻辑一般并不内在于 LLM 的训练之中，Parcel Perform 会在业务上下文中显式定义它。
- 在物流术语中，*transit time*（运输时效）有特定的行业惯例。它以天为单位计量，当日达的配送记录为 `transit_time = 0`。虽然这对物流从业者很直观，但 LLM 可能把"给我所有当日达的运单"这类请求理解错，在生成的 SQL 语句中使用 `WHERE transit_time = 1` 而不是 `WHERE transit_time = 0`。

因此，每个传入的问题都会进入检索增强生成（RAG）工作流，寻找可能相关的已存储业务信息，以丰富上下文。这一机制有助于提供具体规则与解读——即使先进的 LLM 也可能无法从通用训练数据中推导出这些内容。

Parcel Perform 使用 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 作为 RAG 工作流的托管方案。他们通过把文件上传到 Amazon S3 来摄取业务上下文信息。Amazon Bedrock Knowledge Bases 会处理这些文件，将其切分为 chunk，使用嵌入模型生成向量，并把向量存入向量数据库使其可被检索。这些步骤完全由 Amazon Bedrock Knowledge Bases 托管。Parcel Perform 选择 [Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/) 作为向量数据库来存储向量，以简化基础设施管理。

Amazon Bedrock Knowledge Bases 提供 [Retrieve API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_Retrieve.html)，它接收输入（例如来自 AI 助手的问题），将其转换为向量嵌入，在向量数据库中搜索相关的业务上下文信息 chunk，并返回最相关的文档 chunk。它通过[调用 invoke 方法](https://python.langchain.com/api_reference/aws/retrievers/langchain_aws.retrievers.bedrock.AmazonKnowledgeBasesRetriever.html#langchain_aws.retrievers.bedrock.AmazonKnowledgeBasesRetriever.invoke)与 [LangChain](https://www.langchain.com/) 的 Amazon Bedrock Knowledge Bases retriever 集成。

下一步是以提供的业务上下文信息与 SQL 生成 prompt 来调用 AI agent。该 prompt 受 [LangChain Hub 中的一个 prompt](https://smith.langchain.com/hub/langchain-ai/sql-agent-system-prompt) 启发。下面是该 prompt 的代码片段：

```
You are an agent designed to interact with a SQL database.
Given an input question, create a syntactically correct {dialect} query to run, then look at the results of the query and return the answer.
Unless the user specifies a specific number of examples they wish to obtain, always limit your query to at most {top_k} results.
Relevant context:
{rag_context}
You can order the results by a relevant column to return the most interesting examples in the database.
Never query for all the columns from a specific table, only ask for the relevant columns given the question.
You have access to tools for interacting with the database.
- Only use the below tools. Only use the information returned by the below tools to construct your final answer.
- DO NOT make any DML statements (INSERT, UPDATE, DELETE, DROP etc.) to the database.
- To start querying for final answer you should ALWAYS look at the tables in the database to see what you can query. Do NOT skip this step.
- Then you should query the schema of the most relevant tables
```

这段 prompt 示例是 agent 初始指令的一部分。数据 schema 会在该 agentic 工作流的后续步骤中由 SQLDatabase Toolkit 中的工具自动插入。用户在此 AI 助手 UI 中输入问题后，会发生以下步骤：

- 该问题触发一次 LangGraph 图的运行。
- 以下处理并行发生：  该图通过 SQLDatabase Toolkit 从 Athena 获取数据库 schema。该图把问题传给 Amazon Bedrock Knowledge Bases retriever，并获得与该问题相关的一批业务信息。
- 该图通过传入问题、对话上下文、数据 schema 与业务上下文信息，使用 Amazon Bedrock 调用 LLM。结果是生成的 SQL。
- 该图再次使用 SQLDatabase Toolkit，通过 Athena 执行 SQL 并取回数据输出。
- 数据输出被传入 LLM，以基于最初提出的问题生成最终回复。这里使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 作为防护措施，避免不当的输入与回复。
- 最终回复通过 AI 助手 UI 返回给用户。

下图展示了这些步骤。

![带编号步骤的 AI 助手架构图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/02/ML-18476-ai-assistant-architecture-numbered.png)

这一实现展示了 Parcel Perform 如何把原始咨询转化为可执行的数据，以支撑及时的决策。安全也在多个组件中落地。从网络角度看，EKS pod 被放在 [Amazon Virtual Private Cloud](https://aws.amazon.com/vpc)（Amazon VPC）的私有子网中，以提升 AI 助手应用的网络安全。这个 AI agent 被置于需要身份验证的后端层之后。在数据安全方面，敏感数据在 S3 存储桶中静态存储时被掩码处理。Parcel Perform 还限制了用于访问 S3 存储桶的 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色的权限，使其只能访问特定的表。

在接下来的几节中，我们讨论 Parcel Perform 构建这套数据转换方案的做法。

## 从想法到生产

Parcel Perform 的出发点，是把数据团队从手工响应业务团队请求中解放出来，同时提升数据可用性的及时程度，以支撑业务团队的决策。

在 AWS 解决方案架构师团队的帮助下，Parcel Perform 使用 AWS 服务与 [Amazon SageMaker Studio](https://aws.amazon.com/sagemaker-ai/studio/) 中的 [Jupyter notebook](https://jupyter.org/) 完成了概念验证。在初步成功之后，Parcel Perform 把方案集成到他们选用的编排工具 LangGraph 中。

在进入生产之前，Parcel Perform 做了大量测试以确认结果一致。他们加入了 [LangSmith Tracing](https://docs.smith.langchain.com/observability)，记录 AI agent 的步骤与结果，以评估其表现。

Parcel Perform 团队在这一过程中遇到了若干挑战，我们将在下一节讨论。他们通过 prompt engineering 来应对这些挑战。最终，AI agent 被集成到生产环境供业务团队使用。此后，Parcel Perform 在内部收集用户反馈，并监控来自 LangSmith Tracing 的日志，以确认性能得以保持。

## 遇到的挑战

这段旅程并非没有挑战。首先，一些电商商家在数据湖中可能以不同名称存在多条记录。例如，名为"ABC"的商家可能有多条记录，比如"ABC Singapore Holdings Pte. Ltd."、"ABC Demo Account"、"ABC Test Group"等等。对于"上周 ABC 是否有包裹发运延迟？"这样的问题，生成的 SQL 会带有 `WHERE merchant_name LIKE '%ABC%'` 这样的元素，可能造成歧义。在概念验证阶段，这个问题曾导致结果匹配错误。

针对这一挑战，Parcel Perform 依靠细致的 prompt engineering，指示 LLM 识别名称何时可能存在歧义。随后 AI agent 会再次调用 Athena 查找匹配的名称。LLM 基于多个因素决定使用哪个商家名称，包括该名称在数据量贡献上的重要程度以及它在数据湖中的账户状态。未来，Parcel Perform 打算实现更精细的技术，通过提示用户来消解歧义。

第二个挑战是关于不受限制的问题：这类问题可能产生开销很高的查询，扫描大量数据并导致更长的查询等待时间。其中一些问题在查询中可能没有施加 LIMIT 子句。为解决这一点，Parcel Perform 指示 LLM 在用户未指定期望结果数量时，添加带一定最大结果数的 LIMIT 子句。未来，Parcel Perform 计划利用查询的 EXPLAIN 结果来识别重查询。

第三个挑战与跟踪这个特定方案的使用量与产生的成本有关。由于启动了多个使用 Amazon Bedrock 的生成式 AI 项目，有时还使用相同的 LLM ID，Parcel Perform 必须区分各项目产生的使用量。Parcel Perform 为每个项目创建一个[推理配置文件](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles.html)，把该配置文件与[标签](https://docs.aws.amazon.com/whitepapers/latest/tagging-best-practices/what-are-tags.html)关联，并在该项目的每次 LLM 调用中带上该配置文件。借助这一设置，Parcel Perform 能够按项目拆分成本，从而提升成本可见性与监控。

## 带来的影响

要取数，业务团队需要与数据团队确认细节、提交请求、检查可行性，然后等待有人力空档。当需求来自客户或不同时区的团队时，这个过程会更长——由于异步沟通，每一次澄清都会增加 12–24 小时。工作日早些时候提出的简单请求可能在 24 小时内完成，而更复杂的请求或繁忙时段的请求则可能耗时 3–5 个工作日。

有了 text-to-SQL AI agent，这个过程被大幅精简——需求澄清的往返沟通降到最少，不再依赖数据团队的人力空档，结果解读也实现了自动化。

Parcel Perform 的测算显示，text-to-SQL AI agent 将平均 time-to-insight 缩短了 99%，从 2.3 天降到平均 10 分钟，在所有请求方合计每月节省约 3,850 小时等待时间，同时保持数据准确性。

用户可以直接查询数据，无需中间环节，几分钟内即可拿到结果，而不必等上几天。跨时区的团队现在一天中的任何时间都能获取洞察，缓解了"等亚洲上班"或"赶在 EMEA 下班前"这类令人沮丧的延迟，从而带来更满意的客户与更快的故障排查。

这一转变深刻影响了数据分析团队的产能与注意力分配：数据团队被释放出来做更具战略性的工作，也让每个人都能更快、更有依据地做决策。此前，分析师把约 25% 的工作时间用于处理例行的取数请求——相当于整个团队每月超过 260 小时。如今，基础与中级查询已自动化，这一比例降到仅 10%，每月释放出近 160 小时用于高价值工作。分析师现在专注于复杂的数据分析，而不是把时间花在基础的取数任务上。

## 结语

Parcel Perform 的方案展示了如何利用生成式 AI 提升生产力与客户体验。Parcel Perform 构建了一个 text-to-SQL AI agent，把业务团队的问题转换为能够取到真实数据的 SQL。这提升了涉及客户的决策中数据可用性的及时程度。此外，数据团队得以避开无差别的重体力工作，专注于复杂的数据分析任务。

该方案使用了 Amazon Bedrock 等多个 AWS 服务以及 LangGraph 等工具。你可以从概念验证开始，并咨询你的 AWS 解决方案架构师，或与 [AWS Partners](https://partners.amazonaws.com/) 合作。如果有疑问，可以在 [AWS re:Post](https://repost.aws/) 上提出。你也可以借助 [Amazon Q Developer](https://aws.amazon.com/q/developer/) 让开发变得更直接。遇到挑战时，可以通过迭代找到解法，其中可能包括 prompt engineering 或为工作流增加额外步骤。

安全是首要任务。请确保你的 AI 助手设置了适当的护栏（guardrails），以防范 prompt 威胁、不当话题、粗俗内容、数据泄露以及其他安全问题。你可以通过 API 把 Amazon Bedrock Guardrails 集成到生成式 AI 应用中。了解更多信息，请参阅以下资源：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/02/junkai.png)**Loke Jun Kai** 是 AWS 的 GenAI/ML 专项解决方案架构师，覆盖东盟地区的战略客户。他与从初创公司到大型企业的客户合作，构建前沿用例与可扩展的 GenAI 平台。他对 AI 领域的热忱、持续的研究与阅读，催生了许多带来明确业务成果的创新方案。工作之外，他喜欢打网球和下棋。
