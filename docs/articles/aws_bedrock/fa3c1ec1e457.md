# Duco 如何使用 Amazon Bedrock AgentCore 转变财务数据自动化

金融机构面临着严峻的挑战：在全球最严格的监管框架下运营的同时，快速、准确且合规地处理大量数据。 Duco是金融服务代理运营平台，服务于一级银行及其他金融机构。它每月为 200 多个客户处理 200 亿笔交易，其中包括排名前 20 的银行中的 7 家和排名前 20 的资产管理公司中的 10 家。为了跟上数据处理需求的增长，Duco 从传统的机器学习模型发展到 Amazon Bedrock 和 Amazon Bedrock AgentCore 的代理 AI 功能。在这篇文章中，我们将分享 Duco 如何在这些服务上重建其代理 AI 堆栈，从而缩短部署时间和入门成本，同时保持每家银行的数据隔离。

## 挑战：在受监管的环境中扩展智能

Duco 的平台使团队能够使用人工智能和无代码模型自动化关键任务数据处理，处理从数据提取到下游发布的所有事务。它已经使用传统的机器学习模型进行预测标签和模式识别，帮助银行整合和自动化 20,000 多个流程。

然而，这些经典的机器学习方法具有固有的局限性。他们需要大量的历史数据进行培训，与新的场景作斗争，并要求对每个新用例进行大量定制。最关键的是，他们无法快速适应现代金融运营所特有的多样化、不断发展的数据格式和业务规则。

> “经典的预测模型在一定程度上有效，但不够敏捷或灵活。传统的机器学习模型只能放大他们已经学到的东西——他们无法帮助下一步或发现新问题。”

— Rob Gates，Duco 首席架构师兼创新官

## 解决方案：Amazon Bedrock 和 Bedrock AgentCore

Duco 做出了战略决定，采用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 来管理对基础模型的访问，并采用 Amazon Bedrock AgentCore 来大规模运行代理。这不仅仅是技术升级。这是其系统如何理解、推理和处理金融数据的根本性转变。

**关于 Amazon Bedrock 和 Bedrock AgentCore**

Amazon Bedrock 是一项完全托管的服务，通过单一 API 提供来自领先 AI 公司的高性能基础模型选择，以及用于构建具有安全性、隐私性和负责任的 AI 的生成式 AI 应用程序的广泛功能。 [了解有关 Amazon Bedrock 的更多信息](https://aws.amazon.com/bedrock)。

Amazon Bedrock AgentCore 是大规模构建、连接和优化 AI 代理的平台。使用任何开源框架和任何模型进行构建。通过内置的身份验证和访问控制将代理连接到您的工具和数据。通过跟踪和评估来监控和改进生产中的代理。 AgentCore 负责处理基础设施，因此您可以专注于代理逻辑，而不是后端管道，并且您可以在不放弃开源灵活性的情况下获得企业安全性和可靠性。

请访问 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 产品页面了解更多信息。

### 为什么选择Amazon Bedrock？

有几个因素使 Amazon Bedrock 成为 Duco 受监管的金融服务行业 (FSI) 环境的理想选择：

- **安全性和合规性第一：** 使用 Amazon Bedrock，客户数据保留在 AWS 环境中，并且不用于训练模型。借助虚拟私有云 (VPC) 中的私有端点，Duco 可以连接到内部系统，同时保持它们完全隔离，这对于敏感的财务数据处理很重要。
- **模型灵活性：** 通过单个 API 访问 Amazon Nova 2 系列、Anthropic、OpenAI、Cohere、Meta 和 Mistral AI 的领先基础模型意味着 Duco 可以为每项任务选择正确的模型。 Duco 可以通过更改配置参数来在模型之间切换。
- **专为金融服务而构建：** Amazon Bedrock 提供金融服务所需的强大治理控制和合规框架，避免基础设施复杂性，同时维持一级银行要求的安全标准。

### 选择 AgentCore 作为运行时

Duco现有的代理基础设施是建立在LangChain和LangGraph之上的，两者都已经投入生产。在评估其代理工作负载的运行时选项时，AgentCore 成为明确的选择，原因有以下三个：

- **与现有原语的兼容性：** AgentCore 与 Duco 现有的 LangChain 和 LangGraph 代码完全兼容，因此大多数现有代码无需修改即可继续工作。
- **托管运行时：** AgentCore 不是运行自己的代理基础设施，而是提供完全托管的运行时，从而减少了工程团队的运营开销。
- **受监管的环境适用性：** AgentCore 满足在受监管的金融服务环境中部署的严格要求，具有内置的安全性和合规性控制。

## 多租户架构：设计隔离

Duco 的平台作为多租户软件即服务 (SaaS) 产品运行，具有严格的租户隔离（图 1）。这是对受监管机构不可协商的要求。该架构在每个层都体现了这一点，从底层云基础设施一直到人工智能代理运行时。

![Duco 多租户架构，在基础设施、安全和代理层之间实现每个租户的隔离](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/02/ML-20525-1.png)

图 1：多租户架构

### 基础设施层

- **Amazon Elastic Kubernetes Service (Amazon EKS) 集群** 具有每个租户的命名空间隔离和网络隔离，有助于维持 Kubernetes 层的工作负载分离。
- **每租户专用 AWS 服务**：每个租户都会收到专用的 Amazon Aurora MySQL 数据库、Amazon Simple Storage Service (Amazon S3) 存储桶、AWS Key Management Service (AWS KMS) 加密密钥、Amazon Simple Email Service (Amazon SES) 和 Amazon Simple Queue Service (Amazon SQS) 消息堆栈、Amazon ElastiCache 层和 Amazon Cognito 用户池。客户端之间零共享数据基础设施。
- **每租户自动扩展**有助于最大限度地减少一个客户端的计算密集型工作负载对另一租户性能的影响。

### 安全和访问控制

通过身份和基础设施强制隔离，用户及其数据之间的每一跳都经过身份验证（图 2）：

- **租户范围的身份验证**：每个请求都携带由租户的专用 Cognito 用户池颁发的 JSON Web 令牌 (JWT)，并在代理逻辑运行之前由 AgentCore 运行时的入站授权者（Amazon Bedrock AgentCore 的一项功能）进行验证。
- **网关介导的工具访问**：代理仅通过租户的专用 AgentCore 网关访问工具，这是 Amazon Bedrock AgentCore 的一项功能，它将调用传递给租户在 Amazon EKS 中运行的基于容器的模型上下文协议 (MCP) 服务。
- **端到端用户身份**：用户的身份传递到下游服务，每个 MCP 服务器根据租户的 Cognito 用户池验证代理和用户的身份，因此每个工具调用都被授权为由可信代理进行的调用用户。
- **私有网络**：租户共享 VPC 和 Amazon EKS 集群，按命名空间和网络策略隔离，私有终端节点将流量保持在 AWS 网络上的 Amazon Bedrock 和 AgentCore。每个租户的AgentCore运行时都在VPC网络模式下运行，网络接口位于私有子网中，因此其出站流量进入VPC并受安全组管理。

### 代理层

隔离原则完全延伸到代理架构中：

- **每个租户一个 AgentCore 运行时和网关**：每个租户由专用运行时和网关提供服务，并根据该租户自己的 Cognito 用户池和 Amazon EKS 命名空间进行配置。与 AgentCore 的内置会话隔离相结合，这意味着客户端之间不存在共享内存、上下文或工具。每家银行独特的模式、命名约定和机构知识仍然与其他租户完全隔离。
- **每租户 MCP 服务器**：每个租户都有自己的一组 MCP 服务器，提供特定于服务的功能，并在启动时动态发现。

该架构有助于维护一个模型，其中每个代理只能访问一家银行的数据、上下文和推理，从而促进跨银行上下文的真正隔离。

## 解决上下文膨胀：MCP 技能架构

Duco 最重要的技术创新之一解决了构建生产代理系统的任何人都熟悉的挑战：上下文窗口管理。

＃＃＃ 问题

每个租户通过 AgentCore Gateway（每个底层 Duco 服务都有一个单独的 MCP 服务器）公开 300-400 个工具，在工作开始之前，大约 200,000 个工具描述标记已加载到上下文中。这导致了“上下文过载”：响应质量随着对话的延长而下降，并且模型失去了早期推理的线索。该团队强调，感觉特工的能力正在下降，这本身并不足以作为证据。做出工程决策之前必须进行评估。

### 解决方案：按需加载技能

Duco 使用 MCP 资源类型创建了一个技能架构，将工具描述移出静态上下文，并仅在需要时加载它们：

- `skill:// resources` — 仅在需要技能时加载按需工具描述。
- `system:// resources` — 在运行时组成的动态系统提示部分，保持基本系统提示的精简。
- `ui:// resources` — UI 特定资源，与操作工具隔离。

在 Duco 的代理工具中实现的三个新元工具取代了臃肿的工具描述有效负载：

- `load_skill` — 仅当代理确定需要技能时才按需获取技能描述。
- `find_tool` — 定位相关工具，而不将所有模式加载到上下文中。
- `invoke_tool` — 一旦识别就执行选定的工具。

![按需加载 MCP 技能，其中元工具获取技能和工具描述，而不是将所有工具架构预加载到上下文中](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/02/ML-20525-3.jpg)

图 3：上下文加载和 MCP 连接

### 结果

- **上下文减少 90%**：通过将工具描述移出静态上下文并限制工具响应的大小，主要上下文从 200,000 个标记减少到大约 20,000 个标记。
- **保留提示缓存**：静态提示前缀（系统提示加上三个元工具）保持小而稳定，并且技能加载到对话中而不是工具列表中，因此加载技能不会使缓存失效。
- **显着提高座席响应质量：**通过严格的评估框架进行验证。
- **需要零基础设施变更**：相同的底层模型、相同的工具和相同的任务，具有明显更好的结果。

## MCP 工具发现：部署服务，获得能力

一个关键的架构决策是在启动时实现 MCP 工具发现。部署新服务时，作为部署的一部分，其 MCP 服务器将注册为租户 AgentCore 网关上的目标。当代理启动时，工具会为网关公开的每个工具构建一个注册表，并仅共享工具名称。然后，代理使用 find_tool 和 invoke_tool 来发现详细信息并按需调用工具。因此，代理会自动获得该功能，无需重新部署或重新配置代理。访问控制由底层服务本身强制执行：因为用户的身份是通过网关传递的，因此只有允许该用户执行操作时，每个工具调用才会成功。

这提供了操作敏捷性：平台团队可以通过部署新的微服务向代理提供新功能，而无需触及代理配置或需要停机。对于一个为 200 多个客户提供多样化且不断变化的运营需求的平台来说，这种动态能力模型是一个显着的竞争优势。

## 大规模部署代理

Duco 实施了 Amazon Bedrock 和 Bedrock AgentCore，为之前需要大量手动工作的两个关键工作流程提供支持：

### 1. 智能入职

以前，启动新的对账流程是一项手动、耗时的工作，需要大量的专业服务资源。银行需要数年时间才能迁移数千个流程，迁移速度大约为每周一个。

借助 Amazon Bedrock 和 Bedrock AgentCore，Duco 现在可以：

- 自动理解传统和现代系统中的各种文件格式和数据结构。
- 将现有系统的遗留配置转换为结构化的 Duco 流程。
- 解析几十年前编写、无人完全理解的复杂电子表格宏。
- 部署新协调的速度比以前快 10 倍。

一家全球银行通过更好的匹配率和分配规则，新对账的启动成本降低了 70%，直通处理成本提高了 20% 以上。

### 2. AI驱动的异常调查

金融机构在系统之间运行数千个质量关卡，每天都会产生无数异常情况。传统上，大量分析师会手动调查每次中断，以确定是否值得担心、是否已经接受调查，或者是否代表了新的风险。

杜科的特工现在负责调查的“第一英里”：

- **对新中断进行分类**，将具有可能根本原因的相关异常进行分组。
- **检查上下文**，例如是否已知休息、是否已经在进行工作或预计要清除的时间差异。
- **调查**，通过从源数据和系统中提取证据来追踪每个不一致的根本原因，无论是数据质量问题、记录丢失或延迟、映射或参考数据问题还是真正的不匹配，并解释发生的原因。
- **推荐**可供决策的案例：可能的原因、拟议的解决方案（例如调整、规则更改或升级）、考虑的替代方案以及支持证据。
- **将每个案例发送给正确的分析师，由分析师审查证据并做出最终决定，并将每个决定记录在审计跟踪中。

这种代理方法之所以出色，是因为财务工作流程涉及高度可变的信息路径，而这正是基础模型能够很好处理的复杂、上下文密集的推理。

## 在受监管的环境中运营

在金融服务中部署人工智能代理需要的不仅仅是技术能力。它需要严格的合规性、可审计性和风险管理。 Duco 在 Amazon Bedrock 上的实施通过四个核心原则满足了这些要求：

- **全面的可观察性：** 每个代理决策都记录在完整的审计跟踪中。审核者可以追踪每个决定，以根据监管要求进行检查。
- **人机交互控制：** 高风险操作需要明确授权，对于超出代理置信阈值的复杂场景有明确的升级路径。
- **故障安全架构：** 系统默认为客户端提供高于运营效率的保护，即使在代理遇到边缘​​情况或意外数据时也支持安全。
- **监管一致性：** 该平台支持符合 SOC 2 和 DORA 要求的工作负载，并按机构进行数据驻留控制。
