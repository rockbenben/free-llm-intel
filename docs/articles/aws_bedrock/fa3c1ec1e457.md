# Duco 如何借助 Amazon Bedrock AgentCore 变革财务数据自动化

金融机构面临一项关键挑战：要在全球最严格的一些监管框架下运营，同时以速度、准确性和合规性处理海量数据。Duco 是面向金融服务的 agentic Operations 平台，服务于一级银行及其他金融机构。它每月为 200 多家客户处理 200 亿笔交易，客户包括前 20 大银行中的 7 家、前 20 大资产管理公司中的 10 家。为了跟上不断增长的数据处理需求，Duco 从传统机器学习模型演进到 Amazon Bedrock 与 Amazon Bedrock AgentCore 提供的 agentic AI 能力。本文介绍 Duco 如何在这些服务上重建自己的 agentic AI 技术栈，在缩短部署时间、降低客户接入成本的同时，让每家银行的数据保持隔离。

## 挑战：在受监管环境中扩展智能能力

Duco 的平台让团队能用 AI 和 no-code 模型自动化关键任务的数据流程，从数据抽取一直处理到下游发布。它此前已经用传统机器学习模型做预测性标注和模式识别，帮助银行整合并自动化了超过 20,000 个流程。

然而，这些经典机器学习方法有固有的局限。它们需要大量历史数据来训练，面对新场景时常常乏力，而且每出现一个新用例就要做大量定制。最关键的是，它们无法快速适应现代金融运营中多样且不断变化的数据格式和业务规则。

> “经典预测模型在一定程度上是有效的，但它们不够敏捷、也不够灵活。传统机器学习模型只能放大它已经学到的东西——它没法帮你走下一步，也发现不了新问题。”

— Rob Gates，Duco 首席架构师兼创新官

## 解决方案：Amazon Bedrock 与 Bedrock AgentCore

Duco 做出了一项战略决策：采用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 以托管方式访问 foundation models，并采用 Amazon Bedrock AgentCore 大规模运行 agents。这不只是一次技术升级，而是其系统理解、推理和处理金融数据方式的一次根本转变。

**关于 Amazon Bedrock 与 Bedrock AgentCore**

Amazon Bedrock 是一项全托管服务，通过单一 API 提供来自领先 AI 公司的一系列高性能 foundation models，并提供一整套能力，帮助你以安全、私密和负责任 AI 的方式构建生成式 AI 应用。[进一步了解 Amazon Bedrock](https://aws.amazon.com/bedrock)。

Amazon Bedrock AgentCore 是用于大规模构建、连接和优化 AI agents 的平台。你可以用任何开源框架、任何模型来构建。它内置认证和访问控制，把 agents 连接到你的工具和数据；它提供 tracing 和评测能力，让你在生产环境中监控并改进 agents。AgentCore 负责基础设施，让你专注于 agent 逻辑而非后端管线，同时在不牺牲开源灵活性的前提下获得企业级安全性和可靠性。

前往 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 产品页了解更多。

### 为什么选择 Amazon Bedrock？

有几个因素让 Amazon Bedrock 成为 Duco 所处的受监管金融服务行业（FSI）环境的理想选择：

- **安全与合规优先：**使用 Amazon Bedrock，客户数据留在 AWS 环境内，不会被用于训练模型。借助其 virtual private cloud（VPC）中的私有 endpoint，Duco 可以连接内部系统，同时让这些系统完全隔离——这对敏感的金融数据处理至关重要。
- **模型灵活性：**通过单一 API 就能访问来自 Amazon Nova 2 系列、Anthropic、OpenAI、Cohere、Meta 和 Mistral AI 的领先 foundation models，这意味着 Duco 可以为每项任务选择最合适的模型。Duco 只需改一个配置参数就能在模型之间切换。
- **为金融服务而构建：**Amazon Bedrock 提供金融服务所需的稳健治理控制与合规框架，在避免基础设施复杂度的同时保持一级银行要求的安全标准。

### 选择 AgentCore 作为运行时

Duco 现有的 agent 基础设施构建在 LangChain 和 LangGraph 之上，两者都已投入生产。在评估 agentic 工作负载的运行时选项时，AgentCore 凭借三个关键原因成为明确的选择：

- **与现有原语兼容：**AgentCore 与 Duco 现有的 LangChain 和 LangGraph 代码完全兼容，因此大部分现有代码无需修改就能继续运行。
- **托管运行时：**Duco 不必自己运行 agent 基础设施，AgentCore 提供全托管运行时，降低了工程团队的运维开销。
- **适合受监管环境：**AgentCore 满足在受监管金融服务环境中部署的严苛要求，并内置安全与合规控制。

## 多租户架构：隔离即设计

Duco 的平台以具有严格租户隔离的多租户 software as a service（SaaS）形式运行（图 1）。对受监管机构来说，这是不可妥协的要求。架构在每一层都体现了这一点，从底层云基础设施一直到 AI agent 运行时。

![Duco 多租户架构：在基础设施、安全和 agent 层实现按租户隔离](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/02/ML-20525-1.png)

图 1：多租户架构

### 基础设施层

- **Amazon Elastic Kubernetes Service（Amazon EKS）集群**：按租户划分 namespace 并做网络隔离，在 Kubernetes 层维持工作负载分离。
- **按租户专属的 AWS 服务**：每个租户都获得专属的 Amazon Aurora MySQL 数据库、Amazon Simple Storage Service（Amazon S3）存储桶、AWS Key Management Service（AWS KMS）加密密钥、Amazon Simple Email Service（Amazon SES）与 Amazon Simple Queue Service（Amazon SQS）消息栈、Amazon ElastiCache 层，以及 Amazon Cognito 用户池。客户之间没有任何共享的数据基础设施。
- **按租户自动伸缩**：尽量降低某个客户的计算密集型工作负载对其他租户性能的影响。

### 安全与访问控制

隔离不仅通过基础设施实现，也通过身份来落实：用户与其数据之间的每一跳都要经过认证（图 2）：

- **租户范围内的认证**：每个请求都携带由该租户专属 Cognito 用户池签发的 JSON Web Token（JWT），在 agent 逻辑运行之前，由 AgentCore runtime 的入站授权器（inbound authorizer，Amazon Bedrock AgentCore 的一项能力）校验。
- **经网关访问工具**：agents 只能通过该租户专属的 AgentCore Gateway（Amazon Bedrock AgentCore 的一项能力）访问工具，它把调用透传到该租户运行在 Amazon EKS 中的容器化 Model Context Protocol（MCP）服务。
- **端到端用户身份**：用户身份会被透传到下游服务，每个 MCP server 都会对照该租户的 Cognito 用户池，同时校验 agent 的身份和用户的身份，因此每次工具调用都以发起调用的用户身份获得授权，并由可信的 agent 发起。
- **私有网络**：租户共享一个 VPC 和 Amazon EKS 集群，通过 namespace 和网络策略相互隔离；私有 endpoint 让发往 Amazon Bedrock 和 AgentCore 的流量留在 AWS 网络内。每个租户的 AgentCore runtime 以 VPC 网络模式运行，网络接口位于私有子网中，因此其出站流量进入 VPC 并受安全组管控。

### Agent 层

隔离原则完整延伸到 agent 架构中：

- **每个租户一个 AgentCore runtime 和一个 Gateway**：每个租户由专属的 runtime 和 Gateway 提供服务，并针对该租户自己的 Cognito 用户池和 Amazon EKS namespace 进行配置。再加上 AgentCore 内置的会话隔离，这意味着客户之间没有共享的记忆、上下文或工具。每家银行独有的 schema、命名约定和机构知识都与其他租户完全隔离。
- **按租户的 MCP servers**：每个租户都有自己的一套 MCP servers，提供各项服务专属的能力，并在启动时被动态发现。

这种架构维持了这样一种模型：每个 agent 只能访问一家银行的数据、上下文和推理过程，从而实现银行之间上下文的真正隔离。

## 多模型策略

Duco 不押注单一 foundation model，而是为每项工作选用合适的模型，把 agent 设计中的每个角色分配给最适合它的模型。这种做法把恰当的模型能力匹配到具体工作负载上，从而兼顾质量和成本效率：

| **模型** | **主要角色** | **使用场景** |
| --- | --- | --- |
| **Anthropic Claude Opus** | 规划 agent | 用于复杂推理与理解，为其他 agents 预先制定可供执行的计划 |
| **Anthropic Claude Sonnet** | 主要推理与复杂决策 | 异常调查、对账逻辑、规则解读 |
| **Anthropic Claude Haiku** | 轻量工具路由决策 | 快速路由选择、低延迟分类、成本高效的首轮分诊 |
| **Amazon Nova 2 Pro** | 工具输出摘要 | 压缩 MCP 工具响应，为分析师生成易读的摘要 |

这种多模型方案在架构上支持在不打乱整个技术栈的情况下更换模型，而在模型能力快速演进的格局中，这一点至关重要。

## 解决上下文膨胀：MCP skills 架构

Duco 最重要的技术创新之一，解决的正是每个构建生产级 agent 系统的人都熟悉的挑战：context window 管理。

### 问题

每个租户通过 AgentCore Gateway 暴露 300–400 个工具（Gateway 在前面代理每一个底层 Duco 服务各自的 MCP server），在工作开始之前，约 200,000 个 token 的工具描述就被加载进上下文。这造成了*上下文过载*：对话越长，回复质量越差，模型会丢失先前推理的线索。团队强调，感觉一个 agent 变得越来越不中用，本身并不足以作为证据。做工程决策之前必须先跑评测。

### 解决方案：按需加载 skills

Duco 用 MCP resource 类型搭建了一套 skills 架构，把工具描述移出静态上下文，只在需要时才加载：

- `skill:// resources` — 按需的工具描述，仅在需要某个 skill 时加载。
- `system:// resources` — 在运行时动态组合的 system prompt 片段，让基础 system prompt 保持精简。
- `ui:// resources` — UI 专用资源，与运维工具隔离开。

在 Duco 的 agent harness 中实现了三个新的 meta-tool，取代了臃肿的工具描述负载：

- `load_skill` — 按需获取 skill 描述，只在 agent 判断需要某个 skill 时调用。
- `find_tool` — 定位相关工具，而无需把所有 schema 都加载进上下文。
- `invoke_tool` — 在确定所选工具后执行它。

![按需加载 MCP skills：meta-tools 按需获取 skill 和工具描述，而不是把所有工具 schema 预加载进上下文](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/02/ML-20525-3.jpg)

图 3：上下文加载与 MCP 连接

### 结果

- **上下文减少 90%**：把工具描述移出静态上下文，并限制工具响应的长度，主上下文从 200,000 个 token 降到约 20,000 个 token。
- **保留 prompt caching**：静态 prompt 前缀（system prompt 加三个 meta-tools）保持小巧稳定，skills 加载进对话而不是工具列表，因此加载 skill 不会让缓存失效。
- **agent 响应质量可测量地提升：**经由严格的评测框架验证。
- **无需任何基础设施改动**：同样的底层模型、同样的工具、同样的任务，结果却有可测量的改善。

## MCP 工具发现：部署一个服务，就获得一项能力

一项关键的架构决策是在启动时实现 MCP 工具发现。部署一个新服务时，它的 MCP server 会作为部署的一部分注册为该租户 AgentCore Gateway 上的一个 target。agent 启动时，harness 会建立一个注册表，记录 Gateway 暴露的每个工具，但只共享工具名称。随后 agent 用 find_tool 和 invoke_tool 按需发现细节并调用工具。结果是，agent 无需重新部署或重新配置，就自动获得了这项能力。访问控制由底层服务自身执行：由于用户身份会经 Gateway 透传，每次工具调用只有在该用户被允许执行此操作时才会成功。

这带来了运维上的敏捷性：平台团队只要部署一个新的微服务，就能把新能力交付给 agents，既不用改动 agent 配置，也不需要停机。对于一个服务 200 多家客户、且客户运营需求多样且不断演进的平台来说，这种动态能力模型是显著的竞争优势。

## 大规模部署 agents

Duco 落地了 Amazon Bedrock 和 Bedrock AgentCore，用来支撑两个此前需要大量人工投入的关键工作流：

### 1. 智能客户接入

此前，新对账流程的接入是一项人工密集、耗时的工作，需要投入大量专业服务资源。银行迁移数千个流程要花上数年，速度大约每周一个。

借助 Amazon Bedrock 和 Bedrock AgentCore，Duco 现在可以：

- 自动理解遗留系统与现代系统中多样的文件格式和数据结构。
- 把现有系统中的遗留配置转换为结构化的 Duco 流程。
- 解析几十年前编写、如今已无人完全看懂的复杂电子表格宏。
- 以比过去快 10 倍的速度部署新的对账流程。

一家全球性银行的新对账接入成本下降了 70%，并通过更好的匹配率和分配规则，把直通处理率提升 20% 以上。

### 2. AI 驱动的异常调查

金融机构在系统之间设置了成千上万个质量关卡，每天产生不计其数的异常。传统上，大批分析师要人工调查每一个中断（break），判断它是否值得关注、是否已在调查中，还是代表了一种新风险。

Duco 的 agents 现在负责调查的“第一英里”：

- **分诊**：新中断一出现就做初步判断，把可能共享同一根因的相关异常归为一组。
- **检查上下文**：比如这个中断是已知问题、已经在处理中，还是预期会自行消除的时点差异。
- **调查**：从源数据和源系统中提取证据，追踪每一处不一致的根因——无论是数据质量问题、记录缺失或延迟、mapping 或参考数据问题，还是真实的错配——并解释它为什么会发生。
- **建议**：给出一个可直接用于决策的案件材料：可能的原因、建议的处理方式（例如调整、规则变更或升级上报）、考虑过的替代方案，以及支撑证据。
- **分派**：把每个案件交给合适的分析师，由他审阅证据并做最终决定，每项决定都记录在审计轨迹中。

这种 agentic 方法之所以出色，是因为金融工作流在信息之间穿行的路径高度多变，而这正是 foundation models 擅长的、复杂且上下文密集的推理。

## 在受监管环境中运营

在金融服务中部署 AI agents，需要的不仅是技术能力，还要求严格的合规、可审计性和风险管理。Duco 在 Amazon Bedrock 上的实现通过四项核心原则来满足这些要求：

- **全面的可观测性：**每个 agent 决策都记录在完整的审计轨迹中。评审者可以追溯每一项决策，对照监管要求进行核查。
- **human-in-the-loop 控制：**高风险操作需要明确授权；对于超出 agent 置信度阈值的复杂场景，有清晰的升级路径。
- **故障安全架构：**系统默认优先保护客户，而不是优先运营效率，即使 agents 遇到边界情况或意外数据，也能保障安全。
- **符合监管要求：**平台支持受 SOC 2 和 DORA 要求约束的工作负载，并按机构提供数据驻留控制。

## 路线图：人类—agent 协作的未来

Duco 的架构旨在提升员工，而不是取代他们。随着 agentic 能力成熟，平台设想了人类角色一条清晰的演进路径：

**任务执行者** → **调查者** → **决策者**

未来不是由人来执行重复性任务，而是由运营团队并行编排多个 agents，人基于 agent 准备好的分析做最终审批决策。该架构还设计为支持 agent 与 agent 之间的通信，包括不同金融机构的 agents 可以彼此协调的跨机构场景。

对受监管的金融机构来说，Duco 的架构表明 agentic AI 不只可行，它已经在生产规模上交付价值。Duco 在 Amazon Bedrock 和 Amazon Bedrock AgentCore 上重建了其 agentic AI 技术栈，把严格的按租户隔离、为每项工作选择合适的模型，以及将上下文开销削减 90% 的 MCP skills 架构结合在一起。成果包括：对账部署速度提升 10 倍；对一家全球性银行而言，接入成本下降 70%、直通处理率提升 20% 以上。要搭建类似的多租户环境，请先阅读 [Amazon Bedrock AgentCore Developer Guide](https://docs.aws.amazon.com/bedrock-agentcore/)，然后阅读 AWS Machine Learning Blog 上的 [Building multi-tenant agents with Amazon Bedrock AgentCore](https://aws.amazon.com/blogs/machine-learning/building-multi-tenant-agents-with-amazon-bedrock-agentcore/)。关于这项工作背后的运营模式，请参阅 Duco 的 [Agentic Operations: a new operating model for post-trade](https://du.co/agentic-operations-new-operating-model-for-post-trade/)。
