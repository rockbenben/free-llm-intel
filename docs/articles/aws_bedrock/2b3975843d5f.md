# 为金融服务工作流构建可验证的可解释性：Amazon Bedrock Guardrails 的 Automated Reasoning checks

[基础模型（Foundational models）](https://aws.amazon.com/what-is/foundation-models/)（FM）与[生成式 AI](https://aws.amazon.com/generative-ai/)正在改变金融服务机构（FSI）运营其核心业务职能的方式。包括 NASDAQ、State Bank of India 和 Bridgewater 在内的 AWS FSI 客户，已经使用 FM 重新构想其业务运营，并交付了更好的成果。

FM 本质上是概率性的，会产生一系列不同的输出。尽管这些模型能够通过[预训练、微调](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-models.html)与 [prompt engineering](https://aws.amazon.com/what-is/prompt-engineering/)的相互作用生成精密的输出，其决策过程仍不如经典的预测方法那样透明。尽管[工具使用](https://docs.aws.amazon.com/bedrock/latest/userguide/tool-use.html)和[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）等新兴技术旨在提升透明度，但它们同样依赖概率机制——无论是在检索相关上下文，还是在选择合适的工具时。即便是注意力可视化和 prompt 追踪等方法，产出的也只是概率性洞察，而非确定性的解释。

在保险、银行、支付和资本市场等受监管行业运营的 AWS 客户，决策透明度至关重要，他们希望以与依赖传统确定性软件同样的信心来上线由 FM 驱动的应用。为应对这些挑战，我们在 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 中推出 [Automated Reasoning checks](https://aws.amazon.com/about-aws/whats-new/2024/12/amazon-bedrock-guardrails-automated-reasoning-checks-preview/)。Automated Reasoning checks 能够检测幻觉、提出修正建议，并揭示你的生成式 AI 应用回答中未明说的假设。更重要的是，Automated Reasoning checks 可以使用数学上可验证的、确定性的形式逻辑，解释某条陈述为何准确。

要使用 Automated Reasoning checks，你首先需要基于可用的源文档编码一组逻辑规则和变量，创建一个 Automated Reasoning 策略。随后，Automated Reasoning checks 可以使用严谨的数学技术，验证问题（prompt）与 FM 给出的回答是否与 Automated Reasoning 策略中定义的规则一致。这从根本上改变了 FM 应用实现透明度的思路，为 FSI 组织中常见的流程型工作流增加了确定性验证。

在本文中，我们将通过保险法务分诊、承保规则验证和理赔处理等多个常见的 FSI 场景，探讨 Automated Reasoning checks 的工作方式。

## 什么是 Automated Reasoning，它有何帮助？

Automated Reasoning 是计算机科学的一个领域，专注于数学证明与逻辑演绎——类似于审计师核对财务报表，或合规官确认监管要求是否得到满足。Automated Reasoning 工具并不采用传统[机器学习](https://aws.amazon.com/ai/machine-learning/)（ML）等概率性方法，而是依靠数学逻辑来确定性地验证对策略的遵从，并就系统会做什么、不会做什么给出确定性（在给定假设下）。Amazon Bedrock Guardrails 中的 Automated Reasoning checks，是生成式 AI 领域首个由主要云服务商提供的此类产品。

下面的金融示例可用作说明。

考虑一条基础交易规则：“如果一笔交易的金额超过 100 万美元，并且客户不属于 tier-1 评级，那么需要额外的审批。”

Automated Reasoning 系统会将该规则拆解为若干逻辑组成部分来分析：

- 交易金额 > $1,000,000
- 客户评级 ≠ tier-1
- 结果：需要额外审批

在面对某个具体场景时，系统可以就“是否需要额外审批”给出确定性的（是或否）答案，并附带它得出该结论所使用的确切逻辑路径。例如：

- **场景 A** – 150 万美元的交易，tier-2 客户 → 需要额外审批（两个条件均满足）
- **场景 B** – 200 万美元的交易，tier-1 客户 → 无需额外审批（第二个条件未满足）

Automated Reasoning 的独特之处，在于它从根本上背离了生成式 AI 中常见的概率性方法。其核心是给出确定性的结果：相同的输入始终产生相同的输出，并由可验证的证明链支撑，把每个结论追溯到最初的规则。这种基于形式逻辑而非统计推断的数学确定性，使得在既定规则范围内（以及给定假设下）对可能的场景做完整验证成为可能。

FSI 经常运用 Automated Reasoning 来验证监管合规、校验交易规则、管理访问控制并执行策略框架。不过，理解它的局限同样重要。Automated Reasoning 无法预测未来事件，也无法处理含糊不清的情形，更不能像 ML 模型那样从新数据中学习。它要求对规则做出精确、形式化的定义，不适合需要人类判断的主观决策。这正是生成式 AI 与 Automated Reasoning 相结合发挥作用的地方。

随着各机构寻求将生成式 AI 融入其决策流程，Amazon Bedrock Guardrails 的 Automated Reasoning checks 提供了一种把 Automated Reasoning 纳入生成式 AI 工作流的方式。Automated Reasoning checks 依据有文档记载的规则对模型输出进行确定性验证，并附带审计线索和策略遵从性的数学证明。这一能力使其对准确性与治理至关重要的受监管流程尤其有价值，例如风险评估、合规监控和欺诈检测。最重要的是，通过确定性的规则检查与可解释的审计线索，Automated Reasoning checks 有效化解了生成式 AI 落地的主要障碍之一：模型幻觉，即模型针对给定任务生成不可靠或不忠实的回答。

## 在金融服务中使用 Amazon Bedrock 的 Automated Reasoning checks

在 FSI 中应用 Automated Reasoning 的一个理想场景，是某个流程或工作流可以被转化为一组逻辑规则的情形。把规则硬编码为程序函数可以获得确定性的结果，但维护起来会变得复杂，而且需要高度结构化的输入，可能损害用户体验。另一种做法是用 FM 作为决策引擎，灵活性更高，却引入了不确定性。这是因为 FM 以黑箱方式运行，其内部推理过程不透明且难以审计。此外，FM 存在幻觉或误解输入的可能，这意味着其结论需要人工核验才能确认准确性。

## 解决方案概述

这正是 Automated Reasoning checks 的用武之地。下图展示了将生成式 AI 与 Automated Reasoning 相结合、兼用两种方法的工作流。

![ARC 策略示意图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/02/12/ML-18103image001.png)

以下步骤详细说明该工作流：

- 源文档连同意图说明（intent instructions）一并传给 Automated Reasoning checks 服务，用于构建规则和变量并创建 Automated Reasoning checks 策略。
- 创建 Automated Reasoning checks 策略并为其创建版本。
- 将 Automated Reasoning checks 策略及其版本与某个 Amazon Bedrock guardrail 关联。
- 向关联的 Amazon Bedrock guardrail 发起 ApplyGuardrail API 调用，传入问题和 FM 的回答。
- 使用来自 ApplyGuardrail API 的输入触发 Automated Reasoning checks 模型，构建输入与 FM 回答的逻辑表示。
- 基于从源文档创建的规则和变量以及输入的逻辑表示，完成一次 Automated Reasoning 检查。
- Automated Reasoning 检查的结果会呈现给用户，同时说明判定中使用了哪些规则、变量和变量取值，以及如何修改才能使该断言成立的建议。

## 用于保险承保规则验证的 Automated Reasoning checks

设想一家汽车保险公司承保规则验证流程的场景。

承保是保险业的一项基本职能，是风险评估与管理的基础。核保人员负责评估保险申请、确定每位申请人的风险水平，并依据保险公司的指引和风险偏好决定是接受还是拒绝该申请。

承保中的关键挑战之一是规则验证，即核实文档中提供的信息是否符合保险公司的承保指引。这是一项复杂的工作，需要处理非结构化数据和格式各异的文档。

本例使用一家汽车保险公司的承保规则指引文档。一份典型的承保手册会包含定义不可接受驾驶员、不可接受车辆以及其他定义，如下例所示：

**不可接受的驾驶员**

- 有 *3* 次或以上 DUI（饮酒或服药后驾驶）记录的驾驶员。
- 对于新业务或附加驾驶员，有 3 次或以上事故（无论是否有责任）的驾驶员。
- 有 2 次以上重大违规的驾驶员。
- 有 3 次以上需计费事故（chargeable accidents）的驾驶员。
- 未驻扎在加利福尼亚州的军人。
- 75 岁及以上且未完成公司医师报告表（Physician's Report）的驾驶员。
- 任何披露可能影响其安全驾驶机动车能力的身体或精神状况的驾驶员，都可能被要求填写公司医师报告表以核实其驾驶能力。此外，如果在调查过程中发现未披露的医疗问题，则必须提交已填写的公司医师报告表。
- 任何未列入名单或未披露、但属于家庭成员或经常使用被保险车辆的驾驶员。

**不可接受的车辆**

- 主要停放地在加利福尼亚州以外的车辆。
- 车轮数多于或少于 4 个的车辆。
- 载货能力超过 1 吨的车辆。
- 不具备公路使用许可资格的机动车辆。
- 出租车、豪华轿车、应急车辆、护送车辆和公交车。
- 任何时间用于取送货物的车辆，包括配送披萨、杂志和报纸的车辆。
- 用于公共承运、载客服务和公司车队的车辆。
- 提供给未列入名单的驾驶员作任何用途（包括销售、农业或手工艺等商业用途）的车辆（例如共用车）。
- 用于运载托儿所或学校儿童、外来务工人员，或酒店、汽车旅馆住客的车辆。
- 带有永久性或可移除的商业招揽标识或广告的车辆。
- 由合伙企业或公司拥有或租赁的车辆。
- 厢式送货车、封闭式货车、自卸卡车、平板卡车、两栖车辆、沙丘越野车、摩托车、踏板车、房车、旅行拖车、微型车或套件车、古董车或经典车，以及定制、翻新、改装或改造过的车辆。
- 对车型年为 2010 及以前且 ISO 符号大于 20，或车型年为 2011 及以后且 ISO 符号为 41 的车辆，不提供物理损坏（车损）保障。
- 对车型年为 2010 及以前且 ISO 符号大于 25，或车型年为 2011 及以后且 ISO 符号为 59 的车辆，不提供责任保障。
- 报废修复车辆（salvaged vehicles）不提供综合险和碰撞险。仅投保责任险的报废修复车辆保单可以接受。
- 对新业务中车龄超过 15 年的车辆，或在保单期内新增的车辆，不提供物理损坏保障。

在本例中，我们为 Automated Reasoning 检查输入了以下内容：

- **Name **– Auto Policy Rule Validation（汽车保单规则验证）。
- **Description **– 一份策略文档，说明界定不可接受驾驶员和不可接受车辆的规则与标准。
- **Source content **– 一份描述公司承保手册与指引的文档。你可以复制粘贴所提供的示例并创建 PDF 文档，然后将该文档作为源内容上传。
- **Describe the source content **– 为汽车保险承保保单审批创建一个逻辑模型。核保助理会提供驾驶员画像和车辆类型，并询问能否为该潜在客户出单。承保指引文档使用不可接受驾驶员画像清单和不可接受车辆清单。请确保为文档中列出的每一种不可接受情形分别创建一条规则，并创建一个变量来记录该驾驶员是否属于可接受风险。未违反任何规则的客户即为可接受。示例如下：“某驾驶员具有以下画像，其风险是否可接受？该驾驶员有 4 次车祸，将该车用作 Uber-Taxi，且有 4 次 DUI。”模型应当判定：“该驾驶员属于不可接受风险。”

模型会根据源内容创建规则和变量。视源内容的规模而定，该过程可能需要 10 分钟以上。

规则和变量的创建过程本质上是概率性的，我们强烈建议你编辑已创建的规则和变量，使其更好地贴合你的源内容。

该过程完成后，将生成一组规则和变量，你可以对其进行审查和编辑。

## 用于保险法务分诊的 Automated Reasoning checks

下一个示例中，设想核保人员正在评估一份长期护理（LTC）理赔是否需要法律介入。

在本例中，我们输入了以下内容：

- **Name **– Legal LTC Triage（LTC 法务分诊）
- **Description – **一份工作流文档，说明将 LTC 理赔转交法律调查的标准、流程和要求
- **Source content **– 一份描述你的 LTC 法务分诊流程的文档。你需要上传自己的 LTC 法务分诊文档，格式为 PDF。该文档应说明将 LTC 理赔转交法律调查的标准、流程和要求。
- **Describe the source content **– 创建一个逻辑模型，用于验证处于法律调查中的 LTC 理赔的合规要求。该模型必须评估各项保单条件，包括触发调查的给付门槛、护理时长和文档要求。它应核查时间线约束、操作顺序是否正确以及保单限额。每项要求都必须独立评估，只要有任意一项不满足即判定为不合规。示例如下：“一份理赔在 90 天内有两次护理计划修订，服务提供方记录覆盖 10 个月，并在第 12 天召开了审查会议。该理赔是否合规？”模型应当判定：“不合规，因为：多次修订需要调查，服务提供方记录必须覆盖 12 个月，审查会议必须在 10 天内召开。”

规则和变量的创建过程本质上是概率性的，我们强烈建议你编辑已创建的规则和变量，使其更好地贴合你的源内容。

该过程完成后，将生成一组规则和变量。要审查和编辑某条规则或变量，请在 **Actions** 下选择更多选项图标，然后选择 **Edit**。以下截图展示了 **Rules** 和 **Variables** 界面。

## 用于保险理赔处理的 Automated Reasoning checks

最后一个示例展示 Automated Reasoning checks 在理赔处理中的应用。

理赔处理是保险公司内的另一项基本职能，它是保单持有人行使保单、就某起事件（例如车祸）获得赔偿所经历的流程。理赔处理人员负责验证理赔和受益人、确定赔偿金额，并推进理赔结案。该过程包括核实相关人员、事件举证，以及一系列他们必须遵守的法律准则。

理赔处理中的关键问题之一是验证理赔本身及相关各方。在本例中，我们使用 Automated Reasoning checks 为遭遇住宅火灾、试图提出理赔的个人提供建议。

与前几个示例一样，我们按如下方式创建 Automated Reasoning guardrail 策略：

- **Name **– Home Owners Insurance Claims Policy（房主保险理赔策略）
- **Description – **该策略用于验证房主保险理赔，并包含提出理赔所需的流程和程序。
- **Source content **– 一份描述公司房主保险理赔流程的文档。该文档应概述提出理赔所需的必要流程和程序。
- **Describe the source content **– 创建一个逻辑模型，用于验证房主理赔的各项要求。该模型必须评估各项保单条件，包括给付门槛、时长，以及创建理赔所需的文档要求。它应核查时间线约束、操作顺序是否正确以及保单限额。每项要求都必须独立评估，只要有任意一项不满足即判定为不合规。例如：“我家发生了火灾。要提出理赔需要哪些文件？”模型应当判定：“你需要提供消防部门报告、警方报告、照片以及你的保单号。”

## 结论

在本文中，我们展示了 Automated Reasoning checks 如何解决 FM 的一个核心挑战：能够以可验证的方式说明决策的推理过程。通过将 Automated Reasoning checks 纳入我们的工作流，我们得以验证一个复杂的分诊场景，并确定做出某项决策的确切原因。Automated Reasoning 是确定性的，这意味着在相同的规则集、相同的变量，以及相同的输入和 FM 回答下，判定结果可复现。这意味着你可以为合规或监管报送复现 findings。

Amazon Bedrock Guardrails 中的 Automated Reasoning checks 通过对面向决策的文档中的 FM 回答提供确定性验证，使金融服务专业人士能够更有效地运用生成式 AI。它通过降低幻觉风险并建立可复现、可解释的保障机制，增强人类的决策能力，帮助专业人士更好地理解和信任 FM 生成的洞察。
