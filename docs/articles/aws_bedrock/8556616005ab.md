# DXC Technology 如何在 Amazon Bedrock 上构建多模型 AI 底座

*本文与 DXC Technology 的 Nick Tamburro 合著。*

当一个 AI agent 能在银行或医院的生产服务器上采取行动，用得上一个能力强大的基础模型只是起点。近期的公开事故里，自主 agent 做出了运营者从未打算让其执行的破坏性动作——这说明真正的风险很少单独出在模型上，而出在 agent 握着超出任务所需的权限，架构里却没有任何东西能拦住它。要避免这一点，先要有一层在基础设施级别治理模型访问的底座。

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 提供的正是这层底座。通过一个托管接口，它让 DXC OASIS 用上多个基础模型：Anthropic Claude、[Amazon Nova](https://aws.amazon.com/ai/generative-ai/nova/)、Meta Llama 以及开放权重系列。[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 在每个模型上统一执行内容过滤、personally identifiable information（PII）脱敏和拒绝话题策略。[AWS PrivateLink](https://aws.amazon.com/privatelink/) 把推理流量留在客户的 virtual private cloud（VPC）内，而无服务器扩缩容避免了把自管 GPU 基础设施变成单点故障。由于这些是系统级控制、而非事后外挂，它们给了 [DXC Technology](https://dxc.com/) 一个受治理的地基，去承载任何模型层单靠自己都给不了的东西：一个在企业 IT 运维中大规模编排、治理并审计 AI agent 的可信 harness。

模型的可用性因 AWS Region 而异。参见 [Supported models by AWS Region in Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

DXC Technology 为全球一些监管最严的组织运营托管 IT 服务：银行、医院和政府机构。DXC 在 70 个国家有逾 11.5 万名员工，运维着韧性与治理不容妥协的关键任务系统。当 DXC 着手构建 DXC OASIS（面向关键任务 IT 运维的 harness）时，团队把问题拆成两层。第一层是构建在 Amazon Bedrock 之上的受治理模型底座，第二层是建在它之上的可信 harness：DXC 自己的编排、治理与保障层。

本文里，我们探究 DXC 如何在 Amazon Bedrock 上为 DXC OASIS 搭起那层有韧性、够灵活的模型底座，也会说明 DXC 在哪里划清了「底座提供什么」与「harness 必须提供什么」的界线。自 2026 年 3 月正式可用以来，DXC OASIS 在 56 个实测用例中平均把解决时间缩短了 95%。

在所有模型上，客户数据都留在 AWS 数据边界内：prompt 和 completion 不与第三方模型供应商共享，也不用于训练底层基础模型。

> 「我们的客户运行在复杂、业务关键的环境里，采用 AI 时既需要选择，也需要韧性。Amazon Bedrock 让我们用上一个广泛的模型生态，并带有企业级规模所需的治理、安全与运维控制。这份灵活性让我们能为对的任务挑对的模型，随技术演进而调整，并始终专注于为客户交付可衡量的业务成果。」
>         — Dan Gray, President, GIS, DXC Technology

## 方案概览

DXC OASIS 把「用哪个模型」和「活儿怎么干」这两个问题分开。Amazon Bedrock 是底座：一个受治理的、通向基础模型（FMs）的网关，通过一个一致的 API 即可访问，并配有让流量留在 AWS 边界内的安全与网络控制。harness 则是 DXC 在其上构建的一切：跨工具与系统的编排、取自 60 年 runbook 和升级逻辑的运维上下文、策略执行、人工监督闸，以及对每个 agent 动作的完整可审计性。

设计目标是：

- 韧性：模型层没有单点故障。
- 灵活性：按成本、时延和能力把每项任务路由到最合适的模型。
- 监管主权：满足受监管租户对数据处理的期待。
- 设计即安全：限定每个 agent 能做什么，使任何有运维影响的动作都不可能绕过策略检查，必要时还须人工批准。

DXC 主要防的风险，是系统与某个单一供应商、框架或部署目标绑死。下图展示 DXC DXC OASIS 架构里的关键 AWS 服务。

工程师和运维人员通过 Amazon Route 53 与客户 [Amazon Virtual Private Cloud (Amazon VPC)](https://aws.amazon.com/vpc/) 内的一个 Application Load Balancer 接入系统。DXC OASIS 的 agent runtime 跑在私有子网里的 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/) 上。在那里，一个 supervisor agent 把任务委派给若干 capability agent，后者会调用知识库、AWS Secrets Manager、Amazon EventBridge 和 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/)。每一次模型调用都经由 VPC interface endpoint 和 AWS PrivateLink 离开子网去往 Amazon Bedrock，因此推理流量不经过公网。[AWS Identity and Access Management (AWS IAM)](https://aws.amazon.com/iam/)、[AWS Key Management Service (AWS KMS)](https://aws.amazon.com/kms/)、TLS 1.2、Amazon CloudWatch、VPC Flow Logs、AWS CloudTrail 和 OpenTelemetry 在每一层提供安全与可观测性。

## 构建 DXC OASIS 底座

DXC 在 2025 年初以原型起步构建 DXC OASIS。一个跨职能团队在 2026 年 3 月达到正式可用，并在 Amazon EKS 上以按租户的 namespace 和 GitOps 发布，向 130 个客户环境扩展。构建底座涉及以下工作：

- 通过 Amazon Bedrock 建立受治理的多模型访问。
- 把韧性工程化到架构的每一层。
- 把每个工作负载路由到最合适的模型。
- 划清底座与 harness 的界线。

### 通过 Amazon Bedrock 建立受治理的多模型访问

DXC OASIS 使用的每个模型（Anthropic Claude、Amazon Nova、Meta Llama 和开放权重系列）都经 Amazon Bedrock model inference 访问。因此，一次供应商故障或模型下线只是一个路由决策，而不是系统重建。不过，「统一访问」并不等于「统一行为」：模型在能力、回答风格和失效模式上各不相同。用一个模型替换另一个，既是路由变更，也同样是一次保障活动。模型进入生产路由之前，由 harness（而非 API）拿 DXC OASIS 的任务套件来评估它。更多信息见 [Getting started with Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/getting-started.html)。

### 把韧性工程化到每一层

DXC OASIS 的韧性不是某一项控制，而是好几项叠加的结果。下表汇总了这些韧性控制，以及各自为 DXC OASIS 做了什么。

| **韧性控制** | **为 DXC OASIS 做了什么** |
| --- | --- |
| 不依赖单一供应商 | 每个模型都经 Amazon Bedrock model inference 访问。供应商故障或模型下线是路由决策而非系统重建，切换上线前由 harness 确认模型间的行为差异。 |
| 无服务器模型层 | Amazon Bedrock 是无服务器的，Amazon EKS 控制面由 AWS 托管，消除了单点故障。 |
| 影响范围遏制 | Amazon Bedrock Guardrails 不管哪个模型，都一致施加内容过滤、拒绝话题、PII 过滤和上下文控制，把任何单次失败的影响范围圈住。 |
| 私有加密链路 | Amazon VPC 与 AWS PrivateLink 让模型流量不经过公网。传输中 TLS 1.2、静态 AWS KMS 保护数据。 |
| 弹性容量 | Amazon EKS 自动扩缩容配合按租户的 namespace，让新租户上线变成一件容量规划的事。 |

除韧性外，DXC OASIS 也处理数据驻留与主权。区域推理控制与 AWS PrivateLink 把推理留在获批的 AWS Region 内、且不走公网，满足受监管租户对数据处理的期待。

### 把每个工作负载路由到最合适的模型

DXC 建在 Amazon Bedrock 上的战略性理由是「可选性」。因为每个模型都藏在同一套 API 之后，团队可以按成本、时延和能力把每项任务路由到最合适的模型，并在新的前沿模型出现时直接接入，无需给系统重新铺管。

#### 模型选择是一项工作负载决策

每项任务对能力、时延和成本的要求决定它用哪个模型，而不是由系统约束决定。

**Intelligent prompt routing –** 一个无服务器 endpoint 预测回答质量，在同一模型家族的模型之间路由请求。它把较简单的 prompt 发给成本更低的模型，把复杂推理交给能力更强的模型。prompt caching 进一步压低时延和成本。更多信息见 Amazon Bedrock 文档里的 [Intelligent prompt routing](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.html)。

**Custom model import –** 借 [Custom Model Import](https://docs.aws.amazon.com/bedrock/latest/userguide/model-customization-import-model.html)，同样的治理与工具链也延伸到 DXC 或其客户自行带来的模型。

#### 开放与闭源模型并用

Amazon Bedrock 同时支持开放权重模型与专有模型，因此 DXC 能把前沿推理，与客户可自行调整、部署的开放权重模型配在同一套 guardrails 之下。

### 划清底座与 harness 的界线

每个企业级 agent 都需要六项能力。有些是 Amazon Bedrock 直接提供的底座能力，另一些只有 harness 能给，因为它们依赖 DXC 的运维上下文与问责模型。这条界线也正是 agent 安全成败所在。对模型输入与输出设 guardrails 是必要的，但只有 harness 能限定 agent 被允许做什么。下表划出了这条线。

| **能力** | **Bedrock 提供什么** | **harness 补上什么** |
| --- | --- | --- |
| 编排 | 一个由 harness 调用、包装或扩展的基础服务层。 | 基于开源 LangGraph runtime，跨工具、系统和多步工作流做 supervisor 与 capability-agent 委派。 |
| 上下文 | 用于检索的知识库基础设施与 prompt caching。 | 60 年的 runbook、升级逻辑，以及实时的 IT service management（ITSM）数据。 |
| 治理 | AWS IAM、区域推理控制，以及按租户隔离的模型访问。 | 逐请求策略执行、按 persona 授权，以及字段级约束。 |
| Guardrails | Amazon Bedrock Guardrails：内容过滤、拒绝话题、PII 过滤。 | 在底座过滤之上执行运维策略：分层知识层级、范围受限且可审计的 agent 角色，以及「agent 能对什么采取行动」的客户专属规则。 |
| 人工监督 | 不是底座职能。 | 四层权限（observe、propose、act with approval、act within scope），每个 persona 一律从只读起步，外加审批闸与升级路径。 |
| 保障 | 加密、可审计的基础设施，以及 VPC Flow Logs。 | 每个动作都有 OpenTelemetry trace、各带唯一 execution ID，从意图到动作端到端可追溯。 |

## 一个工作负载如何流经 DXC OASIS

为了让架构更具体，下面这些用例来自 DXC OASIS 演示环境。该环境围绕 AnyCompany Airlines 搭建——一家虚构的中型航空公司，跑着本地与 AWS 混合的资产。

- **事故解决：** 诊断并修复一台有风险的生产服务器，从告警到解决不到 10 分钟。
- **问题管理：** ITSM agent 给排名前五的事故类别排序，并给出各自的削减建议，这项人工做要 2–3 小时。
- **云成本分析：** 面向 AWS 云工程师，Metrics agent 按服务和区域拆解 90 天成本趋势，并可按要求排查支出峰值。

事故解决工作流展示了底座与 harness 如何配合：

- **以业务语言告警 –** 一条 runbook 没能清掉 FlightOps 服务器上的磁盘空间。CIO 看到的告警是一个业务风险：4 小时内 Flight Operations 排班可能受影响。同一刻，Linux 工程师看到的同一条告警则带着处置所需的技术细节。
- **规划与委派 –** 工程师从 dashboard widget 打开 AI Assist，那项指标作为上下文带进聊天。一个 supervisor agent 把请求拆成计划，委派给 capability agent（DXC OASIS Metrics、Linux System、ITSM），每次模型调用都经 Amazon Bedrock。
- **有依据的诊断 –** DXC OASIS Metrics agent 确认服务器已用满 99%，并引用支撑其回答的知识库文章。Linux System agent 把问题追到一个 5 GB 的临时文件。
- **人工批准 –** agent 亮出完整执行计划，工程师确认之前什么都不会跑。在这个工作流里，agent 处于 act-with-approval 层：它可以自由诊断，但没有明确、记录在案的批准，就不能改动生产服务器。
- **受治理的执行 –** 修复运行，DXC OASIS 记下跑了什么、在哪台服务器、谁批准的、何时。审计轨迹来自 harness，而不是 agent 对自己所作所为的自述。
- **学习与观察 –** 工程师可以把这段对话转成一篇知识文章草稿。Query Metrics 视图展示这个回答背后的 agent 时间线、委派流程和 token 用量。

| 文件系统事故 | 53–90 mins | 3–6 mins | ~89–97% |
| 数据库性能事故 | 2–3 hours | 5–12 mins | ~90–97% |

## 经验教训与下一步

有四项架构决策被证明最有价值：

### 把模型选择与编排分开

让模型选型、编排框架和部署目标各自成为独立决策，某一层演进时 DXC 就不必重做平台。

### 把韧性控制叠加起来

没有哪一项单独的控制能让系统有韧性。无服务器基础设施、模型层 guardrails、私有网络与人工监督闸组合起来，才形成纵深防御。

### 把底座与 harness 的界线讲明白

清楚区分「云提供什么」与「你必须自己建什么」，既避免工程不足（指望模型自我治理），也避免工程过度（重造底座已有的能力）。

在规模化之前先给自主权设边界。每个 DXC OASIS persona 都从只读起步，更广的权限一次一层、审慎授予。把自主权当成按任务授予、而非默认给的东西，正是 DXC 能放心把 agent 放到生产系统面前的原因。

## 结语

本文里，我们展示了 DXC Technology 如何在 Amazon Bedrock 上一层受治理的多模型底座之上，构建出面向关键任务 IT 运维的 harness——DXC OASIS。把模型推理与运维编排分开，从一开始就把韧性、灵活性和监管合规写进架构。回报是可衡量的：56 个实测用例中解决时间平均下降 95%。对正在自建 agentic 系统的团队，经验是把底座（Amazon Bedrock 提供的）与 harness（你在其上构建的）当作两个独立层，尽早定下哪些能力归哪一层。随着对自主 AI 的审视趋严，正是这条清晰的界线，加上有限、可审计的 agent 权限，让一套系统能在规模化中赢得信任。
