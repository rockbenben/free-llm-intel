## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 在 Amazon Bedrock AgentCore 上构建 Agentic AI 平台

如果您尝试将代理投入生产，那么模型和工具的使用并不是障碍。主要瓶颈在于他们周围的一切：有多少团队可以在安全的环境中构建，哪个团队拥有每个模型和工具，AgentOps 和错误处理如何保持在预定义的边界内，以及平台、工作流和财务团队如何查看跨账户的成本和运行状况。对于想要支持许多代理用例的平台团队来说，这是一个需要设计和操作的平台产品。在这篇文章中，我们将管理平台的团队称为平台团队，将基于平台构建的团队称为工作流团队。工作流团队是在平台上构建和拥有代理的领域或产品团队。

每个工作流团队都需要一条铺好的道路，其中包括经过批准的模型和工具、短期工作负载身份、隔离的运行时和内存、自动评估、回滚、遥测和成本归因。当工作流团队自定义提示、工具、数据访问和应用程序行为时，这些控制需要保持一致。当每个团队组装它们时，控制漂移，共享服务成为瓶颈，并且所有权难以审计。

在这篇文章中，我们将介绍 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 和 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上的企业 Agentic AI 平台的架构和参考实现。我们涵盖多账户操作模型、平台控制平面、可重复的每个工作流部署模式、单独的推理和工具网关，以及在升级到生产之前控制每个代理的评估管道。最后，您应该能够从配套蓝图部署受管理的工作流，验证其安全性和生命周期合同，并将其用作组织中您自己的代理 AI 平台的基础。

[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 提供用于大规模构建、部署和操作代理的模块化服务，包括运行时、网关、身份、内存、策略、注册表和评估。基于 AgentCore 构建的 [企业 Agentic AI 平台蓝图](https://github.com/aws-samples/sample-ai-agent-factory/tree/main/enterprise-agentic-ai-platform-b​​lueprint) 将周围的企业合同添加为可部署基础设施即代码：所有权、账户边界、软件交付、可观察性、成本治理和报废。

## 架构原则

在深入了解解决方案详细信息之前，了解驱动平台架构的组织需求会有所帮助。我们从建立代理平台的客户那里听到的常见挑战分为以下五类：

- **受控模型访问：** 每个不受信任的推理请求都必须通过批准的推理网关。网关应用组织的护栏（例如，[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 或第三方提供商），限制每个工作流可以使用的模型和推理 AWS 区域，并强制执行每个工作流的速率限制、令牌配额和预算，以便任何团队都无法耗尽共享容量。它还携带工作负载身份并发出归因数据。
- **受控工具访问：** 代理必须通过经过身份验证的模型上下文协议 (MCP) 网关仅发现和调用经过批准的工具，并具有准确的目标、最低权限执行角色、策略决策和可审核的所有者。
- **委托交付：**工作流团队（例如产品团队）需要在预先批准的边界内独立交付和回滚，而无需等待平台团队部署每个应用程序或向开发人员授予直接基础设施写入路径。
- **队列运营和成本：** 多个角色需要跨帐户的可见性，而无需获得对团队工作负载的写入权限。代理运营工程师需要日志、指标、跟踪和配额。工作流所有者需要根据其预算了解每个座席的成本。 FinOps 和财务团队需要通过 [AWS Cost Explorer](https://aws.amazon.com/aws-cost-management/aws-cost-explorer/) 和 [AWS 成本和使用报告 (CUR)](https://aws.amazon.com/aws-cost-management/aws-cost-and-usage-reporting/) 按团队或业务部门进行退款。安全和治理主管需要证据表明哪个工作负载调用了哪个模型和工具。
- **有界证据和生命周期：** 每个代理版本都需要在其触及的每个边界提供证据： **模型访问：** 已批准的模型调用成功，而对未经批准的模型或区域的调用将被拒绝。 **工具访问：** 订阅的工具调用成功，对代理订阅之外的工具的调用被拒绝并出现预期错误。 **身份：** 来自另一个工作流的帐户或身份的请求被拒绝。 **发布：** 可以恢复之前的代理运行时版本。 **退役：** 拆卸会按依赖顺序删除代理的运行时、内存、工具网关和工具授权，并确认没有留下任何内容。

该蓝图通过四个互联层面满足这些需求：开发人员体验、平台控制、工作流执行以及保障和运营。规模单位是工作流单元，而不是手动配置的代理或一个共享工作负载帐户。蓝图 [README](https://github.com/aws-samples/sample-ai-agent-factory/tree/main/enterprise-agentic-ai-platform-b​​lueprint) 详细记录了每个平面的职责。您将在后面的段落中阅读主要平面：**Agentic AI Platform 控制平面**和**可重复工作流单元**。

## 运营模式和平台组件

企业通常采用代理人工智能的三种运营模式之一：

- **集中化：** 单个人工智能和机器学习 (AI/ML) 团队构建并运行每个代理。治理是一致的，但随着用例数量的增长，该团队很快就会成为瓶颈。
- **去中心化：** 每个业务部门都建立和运营自己的代理。团队可以快速行动，但如果没有共享标准，控制往往会发生变化，工作会重复，成本可见性也会受到影响。
- **联合：** 中央平台团队提供共享的受管服务，而域团队保留其代理、工具和数据的所有权。这种模式平衡了团队自主权和一致的护栏，是大多数企业的落脚点。
- 如需选择帮助，请参阅[有关治理模型的 AWS 规范指南页面](https://docs.aws.amazon.com/prescriptive-guidance/latest/govern-architect-agentic-ai/governance-models.html)。

根据我们在客户参与中观察到的模式，该蓝图实现了联合模型。平台团队是中心，通常是平台产品经理、架构师、平台工程师、代理运营工程师以及安全和治理主管。工作流团队是辐条，由代理开发人员、领域技术主管和 AI/ML 工程师组成。执行发起人和 CISO 位于两者之上。

在此蓝图中，平台团队拥有每个组件的定义：模板、版本、策略和准入。每个工作流帐户运行自己的每个团队组件实例（运行时、内存、工具网关），因此故障或回滚保留在一个团队的边界内。

## 解决方案概述

该解决方案提供了一个受管理的多帐户 Agentic AI 平台，平台团队可以运营该平台，内部产品和工程团队等工作流团队可以通过版本化的自助服务界面使用该平台。

在企业规模上，开发人员体验平面是组织批准的版本化代理模板的目录。该蓝图提供了 [Strands](https://github.com/strands-agents)、[LangGraph](https://www.langchain.com/langgraph) 和 [CrewAI](https://crewai.com/) 的参考模板，但当模板保留相同的推理网关、工具网关、身份、策略、评估和交付合约时，您可以使用您选择的框架。应用程序团队拥有提示、代理逻辑、工具和评估案例。平台团队拥有通用的控制和发布要求。

在四个平面中，两个承载了大部分架构：

- **Agent AI Platform 控制平面：** 平台帐户发布版本化模板和界面，操作 AWS Agent Registry 治理记录和共享推理网关，接纳模型和 Guardrails，编排经过审核的版本，并聚合车队信号。团队通过代码、描述符和管道而不是管理员会话或部署票证来使用这些功能。
- **可重复工作流单元：** 每个产品或域都会收到一个隔离边界，其中包含团队拥有的源存储库、工作负载管道和三个 Amazon Bedrock AgentCore 功能：AgentCore 运行时、参与者范围的 AgentCore 内存以及使用 AWS_IAM 授权并仅公开批准的工具目标的 AgentCore 网关。该单元还包含本地客户管理的 AWS KMS 密钥、标签、警报、预算和 CloudWatch Observability Access Manager (OAM) 源链接。一个单元可以在不与另一团队的版本协调的情况下进行部署、失败、回滚或退役。

- **Agentic AI Platform 的平台层**。单独的平台环境拥有黄金路径、治理目录、Guardrails、共享推理网关、精确的工具别名、管道、兼容性、配额和通用操作接口。在更广泛的推广之前，平台更改会针对代表性单元进行测试。
- **工作流队列层。** 每个产品、域或受监管的边界都接收一个或多个非生产和生产单元。团队拥有运行时、内存、工具网关、工具、数据、提示、评估案例、应用程序事件和服务级别目标 (SLO)。可以在多个单元中重复相同的基线，同时保持帐户级别的隔离。

### 帐户拓扑和组织单位

该蓝图定义了将企业治理、共享平台服务和团队拥有的执行分开的逻辑帐户角色：

| **角色** | **着陆区放置** | **目的** |
| ---| ---| ---|
|管理基础|根/安全与管理|组织、身份中心、预防策略、审计、保留和成本策略 |
|安全和日志归档 |安全| CloudTrail、AWS Config、Security Hub、GuardDuty 和保留的审核数据 |
|可观察性|安全或运营 | CloudWatch OAM 接收器和队列日志、指标、跟踪和成本视图 |

此拓扑集成到现有的登陆区域中，这是一个预配置的、安全的、可扩展的多账户 AWS 环境，其中管理、平台和工作流标签描述职责，而不是固定的三账户资产。组织可以运行多个经过验证的平台环境和许多工作流帐户对。从一个代表性单元开始，并在重复基线之前证明加入、生产升级、回滚、集中可观察性和零剩余退役。

### 服务控制策略

服务控制策略限制平台和工作流帐户可用的最大权限。它们补充而不是取代 IAM、网关授权、Guardrails、资源策略、网络控制和管道证据。该蓝图呈现并审查针对确切账户和区域的有效策略，而不是仅仅依赖于源代码意图。

- **模型和区域准入：** 组织策略和网关执行角色将推理限制为已批准的模型和支持的区域。添加模型或区域需要服务可用性、驻留、IAM、质量、成本、回滚、可观察性和拒绝验证。
- **Guardrail 和推理执行：** 代理不会直接调用模型提供者。推理跨越受管网关，其中应用了阶段 Guardrail 和模型允许列表。
- **仅管道工作流突变：**工作流团队打开拉取请求并使用工作负载管道。开发人员直接部署到工作流帐户超出了支持的操作模型，这使得经过审查的发布和证据路径不可绕过。
- **注册表和网关治理：** 当订阅的注册表记录丢失、更改或未批准时，工作流网关综合失败。
- **范围部署角色：** 每个账户和区域都会生成引导策略，使用 AWS Identity and Access Management Access (IAM) 分析器进行验证，并通过有效策略模拟进行检查。管理员访问权限保留用于初始设置，而不是例行管道执行。
- **职责分离和对抗性证明：** 平台控制模型、Guardrail、注册表和共享服务准入。工作流团队控制应用程序行为。每一条被拒绝的路径都与一个授权的肯定调用和一个突变配对，证明预期的控制导致了拒绝。

Workstream 帐户内的管理员无法围绕这些控件创建受支持的快速路径。新的或更改的组织策略需要沙箱或代表性单元浸泡、精确的允许和拒绝测试以及广泛附加之前的回滚计划。

### 具有评估门的 CI/CD 管道

该蓝图使用经过审查的平台和工作负载管道来强制执行以下升级顺序：

- **来源和审查：** 拉取请求建立不可变的源修订。管道固定预期分支，因此未合并的更改无法默默地构建存储库默认分支。
- **构建和合成：** 管道编译代码、运行测试和 linting、创建代理清单、扫描摘要绑定图像、验证策略、解析批准的注册表描述符以及检查合成的 AWS CloudFormation 和 cdk-nag 输出。
- **稳定的角色和权限切换：** 工作负载管道创建稳定的工作流角色并暂停。平台管道向确切的网关角色授予准确的工具别名，验证实时策略，然后工作负载管道才会继续。
- **部署到非生产：** 管道将运行时、内存、工具网关、可观察性、警报、预算、标签和应用程序资源部署到单元的非生产边界中。
- **评估已部署的代理：** 门调用真实的运行时并测量回归、质量、工具成功、拒绝行为、第一个令牌延迟和成本。每个授权调用都与一个对抗性双胞胎配对：门调用一个已批准的模型并确认成功，然后调用一个未经批准的模型并确认拒绝。同样的模式适用于工具、跨账户身份和限制。如果缺少预期的拒绝，则门将导致构建失败。
- **人工批准：** 审核者检查已部署的证据、已知限制和残余风险。当缺少所需的探测、资源或预期拒绝时，通用的绿色构建是不够的。
- **提升、观察和回滚：** 生产提升使用经过审查的修订和连续性检查。通过更新、取消、回滚、恢复和重新运行对运行时会话进行采样，以便管道证明前向路径和恢复路径。

没有任何工作流部署步骤具有手动快速通道。平台团队拥有发布合同，但工作流团队运营自己的管道实例和部署节奏。撤销遵循严格的依赖顺序：首先撤销平台别名授予，然后撤销工作流网关和工具角色，然后撤销运行时、内存和应用程序资源。每个步骤在继续之前都会经过验证，最终库存确认剩余资源为零。

## 安全和治理

该蓝图通过加强身份、策略、交付、数据和证据控制来实施深度防御：

- **身份和信任边界：** AgentCore Identity 是 Amazon Bedrock AgentCore 的一项功能，Amazon Cognito 提供短期推理凭证。 AWS_IAM 和 SigV4 对工具流量进行身份验证。确切的运行时和网关角色、发行者和受众检查、帐户和区域上下文以及范围引导信任将每个主体限制在其预期路径上。
- **模型安全和准入：** 推理流经解决方案概述中描述的受管网关，在每次调用之前应用 Guardrails 和模型允许列表。
- **工具授权：** 工具网关仅调用注册机构批准的别名，如解决方案概述中详述。 Cedar 策略提供授权，并保留 AWS Lambda 包装器以进行深度防御。
- **租户数据保护：** 工作流帐户隔离应用程序状态。 AgentCore 内存使用参与者范围的命名空间和客户管理的 KMS 密钥。工具和应用程序数据仍然属于团队所有，并且保留、删除和访问策略是明确的，而不是从共享的可变工作负载帐户继承的。
- **软件供应链和发布：** 审查源、清单哈希、可重复构建、摘要绑定图像扫描、策略验证、cdk-nag 检查、部署运行时评估、人工批准、回滚和按依赖关系排序的拆卸形成一份发布合同。缺少检查无法关闭。
- **审计、可观察性和成本治理：** CloudTrail 和保留的控制平面数据证实了管道证据。 OAM 与中央操作员共享日志、指标和跟踪。标准分配标签、预算、配额以及 AWS 成本和使用情况报告协调分配所有权，而无需授予代理重写其自身归属的权限。

该存储库是一个参考实现。开发人员可以对其进行调整以满足他们的需求。部署和可用功能基于 eu-west-1（爱尔兰）区域。替代组件、另一个区域或更广泛的组织部署需要其自己的可用性、安全性、负载、回滚、可观察性和拆卸证据。

## 结论

在这篇文章中，我们介绍了基于 Amazon Bedrock AgentCore 构建的企业 Agentic AI 平台。该架构将集中管理的平台控制平面与可重复的、团队拥有的工作流单元分开，具有独特的推理和工具网关，以及由部署的运行时评估控制的生产升级。

配套存储库包括一个蓝图，可以端到端地验证这些控制，从管道门和对抗性边界测试到零残留拆卸。支持声明在该测试边界处停止。

首先，从配套存储库部署一个代表性工作流单元，证明其完整生命周期，然后自动化来自同一版本化基线的其他单元。
