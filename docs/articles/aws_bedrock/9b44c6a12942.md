# 降低 Amazon Bedrock AgentCore JSON 工作负载中的令牌成本和延迟

随着企业使用数十种工具和大量结构化输入构建生产代理，令牌消耗和延迟成为良好用户体验的主要障碍。当这些代理处理大型 JSON 数据时，每个额外的工具调用都会将完整的有效负载注入到大型语言模型 (LLM) 上下文窗口中，从而导致令牌使用和响应延迟激增。在多轮对话中，这种压力会加剧，从而增加成本并降低响应质量。有效管理代理系统中的上下文窗口压力是大规模可靠性和响应能力的关键。在这篇文章中，我们分享了三种可组合策略，用于为 Flightscape 构建可处理 20 MB 以上 JSON 有效负载的生产代理。您可以应用它们来降低令牌成本、降低延迟并在扩展会话中保持完整的推理能力。总之，这些优化在典型的 23 MB 有效负载上运行的基准测试中，将令牌消耗减少了高达 71%，并将平均延迟减少了高达 80%。

## 解决方案概述

Flightscape 是一个航空公司运营平台，可帮助航空公司规划和管理其机组人员、航班和运营。作为 Flightscape 机组人员管理功能的一部分，我们构建了一个培训计划优化代理，用于根据业务规则验证机组人员培训计划分配。借助 40 多种工具和以兆字节为单位的 JSON 输入，该代理可以回答有关人员分配、调度和资源分配的复杂查询。尽管代理提供了所需的功能，但大多数呼叫的平均请求延迟超过 15 秒。每个工具调用都将其全部有效负载注入到模型上下文中，从而增加了令牌数量和成本。在较大的数据集上，上下文窗口在代理完成推理之前就已填满。下图（图1）详细介绍了代理架构和数据流：

## 优化策略

配套代码可在此 [GitHub 存储库](https://github.com/aws-samples/sample-reducing-token-costs-and-latency-in-amazon-bedrock-agentcore-json-workloads) 中找到。

### 策略 1：保留轻量级会话状态，卸载繁重工件

我们的第一个优化是改变我们保存会话状态的方式。最初，大量有效负载的存储位置距离会话状态太近。因此，我们将大量工件（请求 JSON、响应 JSON、验证数据和其他大型派生负载）移至 Amazon S3。然后，AgentCore 内存仅保留对这些对象的稳定引用，从而保持会话状态的轻量级。

为了支持这一点，我们引入了专用的持久状态模式，仅保留轻量级字段和工件引用。实时图状态仍然包括用于工具执行的解析域对象，但持久性现在写入脱水形式。在运行时，工具使用这些引用按需水合重型有效负载，而不是每次都加载所有内容。

此 `PersistedState` 模式是写入 AgentCore 内存的内容：
```
class PersistedState(TypedDict, total=False):
    """Serialized session state for AgentCore Memory.

    Heavy fields (request, responses) are stored in S3 and referenced by key.
    Lightweight fields are stored inline.
    """
    messages: List[Any]  # LangChain-serialized messages
    request_ref: Optional[str]  # S3 key for raw request JSON
    responses_ref: Optional[str]  # S3 key for raw responses JSON list
    cache_data_ref: Optional[str]  # S3 key for cache_data payload
    validation_report_ref: Optional[str]  # S3 key for validation_report payload
    basic_stats_ref: Optional[str]  # S3 key for basic_stats payload
```
更新后的 `GraphState` 将这些引用与活动域对象一起镜像：
```
class GraphState(TypedDict):
    """LangGraph state that combines messages with application data."""
    messages: Annotated[List[BaseMessage], add_messages]
    # ... (same domain fields as original graph state)
    # Artifact references for persistence
    request_ref: Optional[str]  # S3 key reference for raw request JSON
    responses_ref: Optional[str]  # S3 key reference for raw responses JSON list
    cache_data_ref: Optional[str]  # S3 key ref for cache_data payload
    validation_report_ref: Optional[str]  # S3 key ref for validation_report payload
    basic_stats_ref: Optional[str]  # S3 key ref for basic_stats payload
```
`dehydrate_state` 函数从实时状态中剥离大量负载，并返回轻量级持久形式以及要上传的工件：
```
def dehydrate_state(state: GraphState) -> Tuple[PersistedState, Dict[str, Any]]:
    persisted: PersistedState = {

    }

        artifacts["request_ref"] = state["request_raw"]
```

补液可逆转这一过程。当会话恢复时，我们重建实时图状态：反序列化 LangChain 消息，将原始有效负载重新解析为域对象，并恢复每个引用密钥，以便稍后可以找到它们的工件：
```
def hydrate_state(
    persisted: PersistedState,
    request_raw: Optional[Dict[str, Any]] = None,
    responses_raw: Optional[List[Dict[str, Any]]] = None,
) -> GraphState:
    """Reconstruct a live GraphState from its persisted form."""
    messages = [load(m, allowed_objects="messages") for m in persisted.get("messages") or []]
    request = TOPTRequest.from_dict(request_raw) if request_raw else None
    responses = [TOPTResponse.from_dict(r) for r in (responses_raw or [])]
    return {
        "messages": messages, "request": request, "responses": responses,
        # ... (remaining fields restored from persisted refs, see GitHub repository)
    }
```
脱水和再水化都依赖于工件存储为每个有效负载返回一致的引用。我们不是创建随机密钥，而是从有效负载本身获取引用。这种方法称为内容寻址，它使用排序键和紧凑分隔符序列化 JSON，并使用这些字节的 SHA-256 摘要作为参考。

`_content_hash` 帮助程序从 JSON 可序列化有效负载生成确定性 SHA-256 引用：
```
def _content_hash(payload: Any) -> str:
    return hashlib.sha256(_canonical_bytes(payload)).hexdigest()
```
内容寻址使写入具有幂等性。相同的有效负载映射到相同的密钥，因此重新序列化未更改的请求 JSON 的回合会重用存储桶中已有的对象，而不是再次上传它。 S3 支持的存储公开 `put_json` 和 `get_json` 接口。它还保留一个小型进程内缓存，因此在当前调用期间已读取或写入的有效负载不需要第二次 S3 往返。

`S3ArtifactStore` 类使用进程内缓存和内容寻址键包装 `put_json`/`get_json` 接口：
```
class S3ArtifactStore:
    """Content-addressed artifact store backed by Amazon S3."""
    def __init__(self, bucket=None, prefix=None, region=None) -> None:
        self.bucket = bucket or os.getenv("SESSION_STATE_BUCKET")
        self.prefix = (prefix or os.getenv("ARTIFACT_STORE_PREFIX", "artifacts")).strip("/")
        # ... (boto3 session setup, see GitHub repository)
        self._cache: Dict[str, Any] = {}

    def put_json(self, payload: Any) -> str:
        ref = _content_hash(payload)
        with self._lock:
            if ref in self._cache:
                return ref  # Identical content already uploaded, skip PUT
            self._s3.put_object(Bucket=self.bucket, Key=self._key(ref), Body=_canonical_bytes(payload))
            # ... (cache update)
            return ref

    def get_json(self, ref: str) -> Any:
        with self._lock:
            if ref in self._cache:
                return self._cache[ref]
        # ... (S3 fetch and cache, see GitHub repository)

artifact_store = S3ArtifactStore()
```
将繁重的工件卸载到 S3 并仅保留轻量级引用可减少每轮延迟和存储在 AgentCore 内存中的数据量。随着繁重的有效负载不再持续内联，工具调用响应成为上下文令牌的主要消费者，促使我们引入结果分页。

### 策略 2：按需分页大型结果列表

即使将大量负载持久性转移到 Amazon S3 后，我们在工具响应时间仍然存在主要的令牌瓶颈。许多工具结果太大，从而产生了两个问题。首先，即使模型只需要一小部分，我们也会向模型发送完整的列表，这使得每个回合速度更慢且成本更高。其次，这些完整列表的有效负载被注入到上下文中，这在多轮对话中快速消耗了上下文窗口。

在某些情况下，单个工具响应超过 80,000 个令牌，并且随着用户继续与代理交互，成本会变得更加复杂。我们希望保留完整的数据访问权限，而不是默认发送所有内容。为了解决这个问题，我们为大型工具输出引入了按需结果分页。现在，工具不再返回完整列表，而是返回包含总计数、小样本和结果句柄的紧凑有效负载。

当工具结果超过样本大小阈值时，完整列表将存储在 S3 中，并且仅将紧凑摘要返回给模型：
```
if len(result) > _LLM_SAMPLE_SIZE:
    handle = artifact_store.put_json(result)
    return json.dumps(
        {
            "_oversized": True,
            "_result_handle": handle,
            "total": len(result),
            "sample": result[:_LLM_SAMPLE_SIZE],
        },
        default=str,
    )
```
该句柄指向存储在S3中的完整结果。当代理需要更多详细信息时，它会使用句柄调用分页工具，并仅请求所需的切片，例如使用偏移和限制。

`get_result_page_tool` 函数允许模型通过句柄、偏移量和限制检索存储结果的附加切片：
```
def get_result_page_tool(handle: str, field: Optional[str] = None, offset: int = 0, limit: int = 50):
    payload = artifact_store.get_json(handle)
    if isinstance(payload, list):
        return {
            "handle": handle, "offset": offset, "limit": limit,
            "total": len(payload),
            "items": payload[offset: offset + limit],
        }
    # ... (dict field extraction, see GitHub repository)
```
按需分页将完整列表保留在 S3 中，并且每轮仅提供所请求的切片，从而控制上下文增长并显着减少令牌使用。然而，并非所有超大输出都是列表。一些工具返回需要不同压缩方法的大型字典。

### 策略 3：紧凑的超大字典输出

与列表不同，字典输出包含深度嵌套的结构化数据，这些数据对于推理很有用，但通常成本太高，无法在每轮中逐字包含。我们需要一种紧凑的表示形式，既能保留结构线索，又能大幅减少代币占用空间。

为了解决这个问题，我们针对超大字典输出引入了基于描述符的压缩。我们不返回完整的超大字典，而是返回一个紧凑的描述符：

- 列表字段由计数和样本表示。
- 嵌套字典按键数进行汇总。
- 标量值在有用的地方保持内联。

完整的有效负载存储在工件存储中，响应包括结果句柄。当代理需要更深入的详细信息时，它使用该句柄仅获取所需的数据。这种响应格式对于模型来说仍然是可导航的，同时显着减少了不必要的令牌使用。

`_oversized_descriptor` 函数构建字典有效负载的紧凑结构摘要，保留字段类型和示例数据，而无需完整内容：
```
def _oversized_descriptor(payload: Dict[str, Any], handle: str) -> Dict[str, Any]:
    fields: Dict[str, Any] = {}
    for key, value in payload.items():
        if key.startswith("_"):
            continue
        if isinstance(value, list):
            fields[key] = {"type": "list", "count": len(value), "sample": value[:5]}
        elif isinstance(value, dict):
            fields[key] = {"type": "dict", "keys": len(value)}
        else:
            fields[key] = {"type": "scalar", "value": value}
    return {"_oversized": True, "_result_handle": handle, "fields": fields}
```
如果序列化输出仍然超出字符限制，则回退将存储完整的有效负载并用其描述符替换响应：
```
content = json.dumps(llm_view, default=str)
if len(content) > _MAX_TOOL_CONTENT_CHARS:
    if handle is None:
        handle = artifact_store.put_json(full_view)
    content = json.dumps(_oversized_descriptor(full_view, handle), default=str)
return content
```
通过轻量级持久状态、按需分页和字典压缩，令牌增长变得可预测，并且代理即使在多兆字节数据集上也能保持响应。

这些变化还改善了较长对话中的行为。上下文增长变得更加可预测，即使用户针对大型数据集提出后续问题，代理也能保持响应。在实践中，这将系统从复合代币成本转变为更受控制、需求驱动的访问模式。

最重要的是，这些成果的实现并没有牺牲能力。完整的有效负载保留在工件存储中，并且可以在需要更深入检查时通过句柄进行检索。在 Flightscape，这种模式为将对话式 AI 功能引入复杂的航空公司运营工作流程奠定了基础，从而保持底层 AI 体验的可扩展性和成本效益。
