# 为 Amazon Bedrock 上的应用优化规模与可靠性

随着生成式 AI 应用扩展到服务更多用户、处理日益复杂的工作负载，理解如何通过恰当的错误处理来优化应用可用性，就变得至关重要。`429 ThrottlingException` 与 `503 ServiceUnavailableException` 这两类错误是重要信号，表明你的应用正在逼近需要关注的运行阈值。虽然这些错误通常都可以重试，但你处理它们的方式会直接影响用户体验。响应延迟会打断对话的自然流程，降低用户参与度。一个可靠、可用于生产的应用，与一个在负载下挣扎的应用，差别往往就在于是否从一开始就落实了正确的错误处理策略与配额管理实践。

本文给出在 Amazon Bedrock 上构建可靠应用的实用策略。我们会探讨经过验证的错误处理、配额优化与架构韧性模式，帮助你的应用可靠地扩展。无论你是在上线第一个 AI 功能，还是在优化一个成熟的生产系统，都能找到在任何规模下从容运营的可操作指导。Amazon Bedrock 在设计上随你的应用一同扩展，提供对业界领先基础模型的访问能力，并内置可配置吞吐量等能力。本文介绍的模式能帮助你充分利用这些能力，同时让应用在需求增长时依然保持响应。

## 前提条件

- 具有 Amazon Bedrock 访问权限的 AWS 账户
- 已安装 Python 3.x 与 boto3
- 对 AWS 服务有基本了解
- **IAM 权限**：请确保至少具备以下权限：针对你所使用模型的 `bedrock:InvokeModel` 或 `bedrock:InvokeModelWithResponseStream`，用于监控的 `cloudwatch:PutMetricData`、`cloudwatch:PutMetricAlarm`，以及在使用 SNS 通知时的 `sns:Publish`。遵循最小权限原则——只授予用例所需的权限

**注意：** 本演练会用到可能产生费用的 AWS 服务，包括用于监控的 Amazon CloudWatch 和用于通知的 Amazon SNS。详情请参阅 [AWS 定价页面](https://aws.amazon.com/bedrock/pricing/)。

## 快速参考：503 与 429 错误

下表比较这两类错误：

| 方面 | 503 ServiceUnavailable | 429 ThrottlingException |
| --- | --- | --- |
| 主要原因 | 临时的服务不可用 | 超出账户配额（RPM/TPM） |
| 是否与配额相关 | 与配额无关 | 直接与配额相关 |
| 恢复时间 | 短暂，恢复较快 | 需要等待配额刷新 |
| 重试策略 | 立即重试并采用指数退避 | 必须与 60 秒配额周期同步 |
| 用户应对 | 等待并重试，考虑替代方案 | 优化请求模式，提高配额 |

## 深入剖析 429 ThrottlingException

ThrottlingException 意味着 Amazon Bedrock 正在有意拒绝你的部分请求，以便把总体用量控制在你所配置的配额或默认分配的配额之内。实践中，你最常遇到的限流有三种：基于速率的、基于 token 的，以及针对特定模型的。

### 1. 基于速率的限流（RPM – 每分钟请求数）

**错误信息：**

```
ThrottlingException: Too many requests, please wait before trying again.
```

或者：

```
botocore.errorfactory.ThrottlingException: An error occurred (ThrottlingException) when calling the InvokeModel operation: Too many requests, please wait before trying again
```

**这说明什么**

当针对某个模型、某个 Region 的 Bedrock 每分钟请求总数超过你账户的 RPM 配额时，就会触发基于速率的限流。关键在于，这一限制作用于某个账户内的所有调用方，而不只是针对单个应用或微服务。

想象咖啡店里一条共享的排队队伍：谁站在队伍里并不重要；咖啡师每分钟只能做出固定数量的饮品。当需求超过咖啡师的处理能力时，一些顾客就会被要求等待或稍后再来。那条“稍后再来”的消息，就是你的 429。

**多应用流量尖峰场景**

假设你有三个生产应用，它们都在同一个 Region 调用同一个 Amazon Bedrock 模型：

- 应用 A 通常在每分钟 2,000 个请求左右达到峰值。
- 应用 B 同样在 2,000 rpm 左右达到峰值。
- 应用 C 在自己的峰值时段通常运行在约 2,000 rpm。

于是你为该模型申请了 6,000 RPM，这看起来合理，因为 2,000 + 2,000 + 2,000 = 6,000，而且历史仪表盘显示每个应用都维持在其预期峰值附近。

然而现实中你的流量并不会完美平坦。也许在闪购或营销活动期间，应用 A 短暂冲到 2,400 rpm，而 B 和 C 仍保持在 2,000。那一分钟的合计总量变成 6,400 rpm，超过你 6,000 rpm 的配额，于是部分请求开始以 ThrottlingException 失败。

当任何一个应用的需求上移（而其他应用保持不变）时，你也可能遭遇限流。设想一种新的流量模式，峰值流量如下：

- 应用 A：3,000 rpm
- 应用 B：2,000 rpm
- 应用 C：2,000 rpm

尽管原配额是按 6,000 规划的，你新的真实峰值已是 7,000 rpm。在这种情况下，即使日均流量看起来仍然“正常”，当三个应用同时处于峰值流量时，你就会看到 429 错误。

对于基于速率的限流，缓解措施包含两部分：客户端行为与配额管理。

**在客户端侧：**

- 实施请求速率限制，为每个应用每秒或每分钟可发送的调用数设上限。API、SDK 封装层，或 API gateway 之类的 sidecar，都可以实施按应用划分的预算，使某个吵闹的客户端不会饿死其他客户端。
- 对 429 错误使用带 jitter 的指数退避，使重试逐步变得不那么频繁，并在各实例之间去同步。AWS 建议使用 jitter（在发起或重试请求之前等待一段随机时间），通过分散到达速率来帮助避免大规模突发。
- 实施考虑配额刷新周期的重试策略：由于 RPM 是按 60 秒的[窗口](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-token-burndown.html)执行的，把重试分散到接下来的一分钟内会提高成功概率。AWS 建议把请求分散到 1 分钟内的多个秒上，并在触及按分钟计的[配额](https://repost.aws/knowledge-center/bedrock-throttling-error)时确保重试退避持续满 1 分钟。使用带 jitter 的指数退避，让负载在时间上自然分散，防止同步的重试突发。在配额一侧：
- 分析每个应用的 CloudWatch 指标，确定真实峰值 RPM，而不是依赖平均值。
- 把同一模型/Region 下各应用的峰值相加，再加上安全余量，必要时通过 AWS Service Quotas 申请提高 RPM。

在前面的例子中，如果应用 A 峰值 3,000 rpm、B 和 C 峰值 2,000 rpm，你应至少按 7,000 rpm 规划，实际目标则建议设在 8,000 rpm 左右，为增长和意外突发留出空间。

### 2. 基于 token 的限流（TPM – 每分钟 token 数）

**错误信息：**

```
botocore.errorfactory.ThrottlingException: An error occurred (ThrottlingException) when calling the InvokeModel operation: Too many tokens, please wait before trying again.
```

#### 为什么 token 上限很重要

即使你的请求数不大，一个很大的 prompt，或一个会产出长输出的模型，也可能一次消耗数千 token。当每分钟处理的输入 token、输出 token 以及由 `max_tokens` 预留的 token 之和超过你账户在该模型上的 TPM 配额时，就会发生基于 token 的限流。关键的是，如果请求里没有显式设置 `max_tokens`，它会默认为模型的最大输出容量（例如 [Claude Sonnet 为 64,000 token](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-reasoning.html)）。这意味着一个不大的请求可能悄悄预留远超预期的配额，这也是意外限流的常见原因。完整的配额生命周期公式见下文第 3 节。

例如，如果你的应用使用 Claude Opus 4.6，默认配额为每分钟 2,000,000 token（TPM），每个请求有 500 个输入 token，且 `max_tokens` 设为 1,000，那么 Bedrock 会先从你的配额中为每个请求预留 1,500 token（500 输入 + 1,000 `max_tokens`）。这给你约 1,333 个并发请求/分钟的理论容量（2M ÷ 1,500）。但如果你不设置 max_tokens，让它默认取 64,000，同一个请求就会预留 64,500 token，把你从同样的 2M TPM 配额能获得的容量降到每分钟仅约 31 个并发请求。所有主流 Bedrock 模型都有 [TPM 配额，范围从 200K 到 8M TPM](https://docs.aws.amazon.com/general/latest/gr/bedrock.html)，具体取决于模型，像 Claude Sonnet 4.6 这样的新模型提供 5M TPM。这些配额可通过 [AWS Service Quotas](https://docs.aws.amazon.com/general/latest/gr/bedrock.html) 调整，允许你在应用扩展时申请提高。

**这在实践中是什么样**

你可能会注意到，应用在正常工作负载下运行顺畅，但当用户粘贴大文档、上传长转写稿，或运行批量摘要任务时，它突然开始失败。这些症状说明瓶颈在 token 吞吐量，而不是请求频率。对于批量任务，你应该使用[批量推理](https://docs.aws.amazon.com/bedrock/latest/userguide/capacity-limits-cost-optimization.html)，它有独立配额（每个批次最多 10,000 条记录，处理窗口为 24 小时），并且相比按需推理提供[降低 50%](https://aws.amazon.com/bedrock/pricing/)的价格。

#### 如何应对

要缓解基于 token 的限流：

- **申请更高的 TPM 配额** – 如果你持续触及上限，可通过 AWS Service Quotas [申请提高配额](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-increase.html)。对于已经超出默认分配的生产工作负载，这是最直接的解决办法。
- **把 max_tokens 参数调到合适大小 –** 这是影响最大的优化。完整解释与示例见下文第 3 节。
- **监控 token 用量**，跟踪 Bedrock 调用的 `InputTokenCount`、`OutputTokenCount` 与 `max_tokens`。三者都会消耗配额。`InputTokenCount` 与 `OutputTokenCount` 可作为 CloudWatch 指标获取；启用[模型调用日志](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html)后，`max_tokens` 可通过 CloudWatch Logs 捕获。
- **实现感知 token 的限速器**，维护一个 60 秒的滑动窗口记录已消耗的 token，只有剩余预算足够时才发出新请求。
- **在合适时使用流式响应；** 流式通常让你更能控制何时停止生成，从而不会产出不必要的长输出。

### 3. max_tokens 如何影响基于 token 的限流

#### 幕后发生了什么

监控 `InputTokenCount` 与 `OutputTokenCount` 有助于你了解实际的 token 消耗，但 `max_tokens` 参数同样重要，因为它决定了 Amazon Bedrock 在生成第一个输出 token 之前预先预留多少配额。如果请求中没有显式设置 `max_tokens`，它会默认为模型的最大输出容量。对 Claude Sonnet 4 来说，这是 [64K](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-reasoning.html) token。这种默认行为是基于 token 的意外限流的常见原因，因为你的应用可能看起来只用了不多的 token，而 Bedrock 在每次请求开始时都在悄悄预留远超预期的配额。

#### 如何应对

为此，我们进一步了解 token 生命周期。当你向 Bedrock 发出请求时，配额系统通过三个阶段管理 token：

| **阶段** | **何时** | **公式** | **目的** |
| --- | --- | --- | --- |
| 1 — 初始预留 | 请求到达时 | 输入 token 总数 + `max_tokens` | 决定该请求是否被限流 |
| 2 — 动态调整 | 生成过程中 | （随着实际输出产生，Bedrock 逐步释放未使用的预留 token） | 为并发请求腾出配额 |
| 3 — 最终结算 | 请求完成时 | `InputTokenCount` + `CacheWriteInputTokens` + (`OutputTokenCount` × burndown rate) | 实际消耗的配额；未使用的 token 归还 |

`CacheReadInputTokens` 不计入配额。Anthropic Claude 4.8 版本模型对输出 token 的 burndown rate 为 15x（1 个输出 token 消耗你配额中的 15 个 token）。对 Anthropic Claude Sonnet 5，输出 token 的 burndown rate 为 10x。对版本 4.7 及以下的所有其他 Anthropic 模型，输出 token 的 burndown 为 5x（1 个输出 token 消耗你配额中的 5 个 token）。

**为什么这对基于 token 的限流很重要**

如果你实际 token 用量不大，却比预期更早触及 TPM 配额，那几乎可以肯定是 max_tokens 参数造成的。看这个例子：模型没有 5× burndown（1:1 比例），输入 8,000 个 token，实际输出 1,000 个 token：

| 阶段 | max_tokens = 32,000（过高） | max_tokens = 1,250（合适） |
| --- | --- | --- |
| 1 — 初始预留 | 8,000 + 32,000 = 40,000 token | 8,000 + 1,250 = 9,250 token |
| 2 — 动态调整 | 随着输出生成，Bedrock 逐步释放未使用的预留 token | 相同——但预留的配额少得多，因此需要的调整也更少 |
| 3 — 最终消耗 | 8,000 + 1,000 = 9,000 token | 8,000 + 1,000 = 9,000 token |
| 配额被临时超额预留 | 31,000 token | 仅 250 token |

在那段初始期间，较高的 max_tokens 值会临时削减你 token 桶中可用的并发请求容量。两种情况下最终扣除的配额都是 9,000 token，但在请求进行期间，未优化的调用占用的配额超过 4 倍。

再看最坏的情况：如果完全不设置 `max_tokens`，它会默认为模型的最大输出容量。同样的请求在第 1 阶段会预留多得多的 token，足以在寥寥几个并发请求内耗尽你的 TPM 配额，尽管每个请求在最终结算时只消耗 9,000 token。

关键结论：始终显式设置 `max_tokens`，使其接近你预期的补全长度。使用 CloudWatch 的 `OutputTokenCount` 指标来把它调到合适大小。

这里我们必须追踪 `max_tokens` 参数。CloudWatch 指标会跟踪 `InputTokenCount` 与 `OutputTokenCount`，而在启用[模型调用日志](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html)时，`max_tokens` 参数可通过 CloudWatch Logs 捕获。你可以分析这些模式，找出 `max_tokens` 设置与实际输出 token 用量之间的差距。如需自动化监控，请参阅 [TPM & RPM 配额监控仪表盘](https://repost.aws/articles/ARfUsSkaWeSLiWZbv0OVSG1Q/tpm-rpm-quota-monitoring-dashboard-for-amazon-bedrock)，它会自动计算初始预留与最终消耗。

**优化策略**

为更好地利用配额而优化 `max_tokens`：

- ** 根据用例调到合适大小：** 把 `max_tokens` 设为接近你预期的补全长度，而不是随意设成很高的值或干脆不设
- ** 使用 CloudWatch 指标：** 检查 `InputTokenCount` 与 `OutputTokenCount` 的模式，为你的 `max_tokens` 决策提供依据
- ** 按请求类型区分：** 根据具体请求动态调整 `max_tokens`，而不是对所有场景都用一个很高的值
- ** 考虑 burndown rate：** 记住 Claude Opus 4、Sonnet 4.5、Sonnet 4、Claude 3.7 Sonnet 和 Haiku 4.5 等模型对输出 token 有 5x 的 burndown rate，这意味着如果输出较大，最终结算可能高于预期，但不设 `max_tokens` 导致的初始预留几乎总是更大的问题

## 实现稳健的重试与速率限制

一旦理解了各类限流，下一步就是把这些知识固化为可复用的客户端组件。

### 带 jitter 的指数退避

处理限流时，带 jitter 的指数退避对优雅恢复至关重要。下面的示例演示使用 Anthropic Python SDK、通过 bedrock-mantle endpoint 实现的自适应重试逻辑，它会以指数退避和 jitter 自动处理 429（限流）与 503（瞬时）错误：

```
""" Bedrock Mantle: Streaming Claude Haiku 4.5 with Adaptive Retry 
Calls Claude Haiku 4.5 via the bedrock-mantle endpoint using the Anthropic Python SDK with streaming and adaptive retry. 
Endpoint: https://bedrock-mantle.{region}.api.aws/anthropic 
Prerequisites: pip install anthropic 
Usage: 

python bedrock_mantle_adaptive.py """ 
import random import time import anthropic 

--- Configuration --- 
REGION = "us-east-1" MODEL = "anthropic.claude-haiku-4-5" BASE_URL = f"https://bedrock-mantle.{REGION}.api.aws/anthropic" API_KEY = "Your API Key" # Generate at: AWS Console → Bedrock → API keys 
#Retry settings 
MAX_RETRIES = 5 BASE_DELAY = 1.0 MAX_DELAY = 60.0 

--- Client --- 
client = anthropic.Anthropic( base_url=BASE_URL, api_key=API_KEY, ) 

--- Stream with adaptive retry --- 
prompt = "What is Amazon Bedrock in one sentence?" 
for attempt in range(MAX_RETRIES): try: print(f"Q: {prompt}") print("A: ", end="", flush=True) 
   with client.messages.stream( 
        model=MODEL, 
        max_tokens=256, 
        messages=[{"role": "user", "content": prompt}], 
    ) as stream: 
        for text in stream.text_stream: 
            print(text, end="", flush=True) 
    print() 
    break  # Success, exit retry loop 
 
except Exception as e: 
    error = str(e) 
    retryable = any(c in error for c in ("429", "500", "503")) 
 
    if not retryable or attempt == MAX_RETRIES - 1: 
        print(f"\nError: {error}") 
        break 
 
    delay = min(BASE_DELAY * (2 ** attempt), MAX_DELAY) + random.uniform(0, 1) 
    print(f"\n⏳ Throttled. Retrying in {delay:.1f}s...") 
    time.sleep(delay)
```

上面展示的带 jitter 的指数退避模式会根据连续失败情况智能调整重试间隔，性能优于固定延迟。通过捕获 429（限流）与 503（瞬时）错误并逐步增加等待时间，你的应用既能避免压垮服务，又能最大化成功请求的吞吐。

**替代方案：自定义重试实现**

对于需要自定义重试逻辑的场景（例如特定的日志记录、指标采集，或非标准重试模式），你可以实现自己的重试机制：

```
import time 
import random 
from botocore.exceptions import ClientError 

def bedrock_request_with_retry(bedrock_client, operation, **kwargs): 
"""Secure retry implementation with sanitized logging.""" 
    max_retries = 5 
    base_delay = 1 
    max_delay = 60 

    for attempt in range(max_retries): 
        try: 
            if operation == 'invoke_model': 
                return bedrock_client.invoke_model(**kwargs) 
            elif operation == 'converse': 
                return bedrock_client.converse(**kwargs) 
        except ClientError as e: 

# Security: Log error codes but not request/response bodies 
            # which may contain sensitive customer data 
            if e.response['Error']['Code'] == 'ThrottlingException': 
                if attempt == max_retries - 1: 
                    raise 
      
                # Exponential backoff with jitter 
                delay = min(base_delay * (2 ** attempt), max_delay) 
                jitter = random.uniform(0, delay * 0.1) 
                time.sleep(delay + jitter) 
                continue 
            else: 
                raise 
```

这种模式可防止在一次限流事件之后立刻压垮服务，并帮助把重试分散到不同时间，降低多个实例同步重试的可能性。不过对大多数用例来说，boto3 内置的重试配置更受推荐，因为它更简单、经过充分测试，并由 AWS 自动维护。

### 感知 token 的速率限制

针对基于 token 的限流，下面这个类维护一个 token 用量的滑动窗口，并向调用方给出简单的“是/否”答案，说明是否可以安全地再发一个请求：

```
import time
from collections import deque

class TokenAwareRateLimiter:
    def __init__(self, tpm_limit):
        self.tpm_limit = tpm_limit
        self.token_usage = deque()
    
    def can_make_request(self, estimated_tokens):
        now = time.time()
        # Remove tokens older than 1 minute
        while self.token_usage and self.token_usage[0][0] < now - 60:
            self.token_usage.popleft()
        
        current_usage = sum(tokens for _, tokens in self.token_usage)
        return current_usage + estimated_tokens <= self.tpm_limit
    
    def record_usage(self, tokens_used):
        self.token_usage.append((time.time(), tokens_used))
```

实践中，你会在发送请求前估算 token 数，调用 `can_make_request`，只有它返回 True 时才继续，然后在收到响应后调用 `record_usage`。

### **重要：多应用的配额共享**

上面的实现适用于单个应用，但 Amazon Bedrock 的配额是账户级、按 Region 划分的，这意味着同一 AWS 账户与 Region 内的所有应用共享同一个配额池。如果你有多个应用，这个本地限速器无法防止配额耗尽，因为每个应用只跟踪自己的用量。

**多应用环境的推荐做法：**

最佳做法取决于你的组织结构与隔离要求：

- [独立的 AWS 账户](https://docs.aws.amazon.com/whitepapers/latest/organizing-your-aws-environment/organizing-your-aws-environment.html)（对大多数组织推荐）：把每个应用或团队部署在各自的 AWS 账户中，以获得独立的配额分配，彻底消除配额争用。这符合 AWS 关于账户隔离的最佳实践，能提供清晰的成本归属，并简化安全边界。对于生产工作负载尤其重要，因为一个应用的用量不应影响另一个应用的可用性。

**针对特定场景的替代方案：**

- [应用推理配置文件（AIPs）](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles.html)：最适合需要共享配额、但又想按应用做细粒度成本跟踪与监控的组织。把 AIPs 与 CloudWatch 告警结合使用，监控用量并在超出阈值时触发自动化响应。
- 集中式速率限制：适用于开发/测试环境，或需要对配额分配做细粒度控制的场景。实现一个共享的限速服务（使用 DynamoDB、Redis 或 API Gateway），让所有应用在发出 Bedrock 请求前先查询它，以保证账户范围的配额感知。
- [预留容量（Provisioned Throughput）](https://docs.aws.amazon.com/bedrock/latest/userguide/prov-throughput.html)：对于可预测的高流量工作负载，为关键应用预留专用容量，确保它们不受其他应用用量的影响，无论账户结构如何。

## 理解 503 ServiceUnavailableException

503 `ServiceUnavailableException` 告诉你 Amazon Bedrock 暂时无法处理你的请求。与 429 不同，这与你的配额无关；它关乎模型相关的临时状况。

### 临时的服务资源问题

**它长什么样：**

```
botocore.errorfactory.ServiceUnavailableException: An error occurred (ServiceUnavailableException) when calling the InvokeModel operation: Service temporarily unavailable, please try again.
```

在这种情况下，Bedrock 服务是在发出瞬时问题或基础设施问题的信号，通常在需求尖峰期间影响按需模型。此时你应把该错误视为临时中断，专注于智能重试与优雅失效转移：

- 使用指数退避重试，方式与处理 429 类似，但参数要针对更慢的恢复速度进行调整。
- 考虑使用不同的 service tier，为你最关键的工作负载获得更可预测的容量包络。

### 熔断器模式

面向关键任务系统的高级韧性：当你运营关键任务系统时，单纯重试并不够，你还要避免让糟糕的局面变得更糟。熔断器模式是任何依赖外部服务的应用都应采用的标准分布式系统实践。它通过在瞬时状况下暂时暂停请求，而不是反复尝试那些不太可能成功的调用，帮助应用优雅应对，从而维持整体应用稳定性。无论调用的是数据库、第三方 API 还是 AI 服务，这一模式都推荐用于所有集成。详细指导请参阅 [AWS Prescriptive Guidance 关于熔断器模式](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/circuit-breaker.html)，以及 AWS 博客文章[将熔断器模式与 AWS Step Functions 和 Amazon DynamoDB 配合使用](https://aws.amazon.com/blogs/compute/using-the-circuit-breaker-pattern-with-aws-step-functions-and-amazon-dynamodb/)

熔断器阻止你的应用持续发出会失败的请求。在检测到反复失败后，它会自动切换到“打开”（open）状态，在冷却期内阻断新请求，这一段也就是恢复期。

- **CLOSED**（正常）：请求正常流动。
- **OPEN**（失败）：在反复失败之后，新请求会被立即拒绝，有助于减轻服务压力并节省客户端资源。
- **HALF_OPEN**（测试）：超时之后，允许少量试探请求；如果它们成功，熔断器重新闭合。

#### 为什么这对 Amazon Bedrock 很重要

当任何服务遭遇高需求时，实施熔断器有助于维持整体系统稳定性，并让恢复更快

- 减轻服务压力，帮助它更快恢复
- 快速失败，而不是把时间浪费在很可能失败的请求上
- 通过定期测试服务是否恢复健康，提供自动恢复
- 快速返回错误而不是超时，从而改善用户体验

**实现建议：**

为把维护开销降到最低，你可以使用成熟的库而不是自定义实现。维护良好的选项包括：

- [pybreaker](https://github.com/danielfm/pybreaker) – 成熟的熔断器实现，支持多种失败检测策略
- [tenacity](https://github.com/jd/tenacity) – 灵活的重试库，具备熔断能力与丰富的配置选项

这些库提供经过实战检验的实现，具备恰当的状态管理、线程安全与监控钩子。只有当你有现有库无法满足的特定需求时，才应考虑自定义实现，例如与专有监控系统集成，或需要超越标准错误率阈值的独特失败检测逻辑。

**注意**：AWS SDK 的自适应重试模式（本文另有讨论）内置 token 桶速率限制与自动退避，可应对许多限流场景。熔断器则通过在应用层增加显式状态管理与快速失败行为来补充它。

**跨 Region 推理与容量分布**

Amazon Bedrock 的[跨 Region 推理](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)（CRIS）允许你的应用通过一个跨多个 Region 的 inference profile 调用模型，而不是直接指向单个 Region。可用的 profile 类型有两种：

- **全球 inference profile**：把请求分布到该模型部署的每一个 Region，并根据实时容量选择目的地。

- **地理 inference profile**：把路由限制在特定地理区域（US、EU 或 APAC），让数据留在这个边界内，同时仍享有跨 Region 容量。

CRIS 是一种容量分布机制。它拓宽了你的请求可以落到的计算资源池，从而提升吞吐并平滑负载尖峰期间的性能。不过它并不充当灾难恢复或自动故障转移系统，也不应被当作那样的系统。

**用多个 profile 构建韧性**

为限制某个 Region 受损带来的影响，可以配置多个面向不同地理区域的地理 inference profile（例如一个用于 US，一个用于 EU，一个用于 APAC）。如果某个地理区域出现劣化，经由分配给其他地理区域的 profile 路由的工作负载不受影响。采用这一模式之前，请核实你的数据驻留与合规要求允许把请求路由到每一个目标地理区域。GDPR、HIPAA 或 FedRAMP 等法规可能限制 prompt 与补全结果可以在哪里处理，而把请求路由到未经批准的地理区域——哪怕只是在事故期间临时如此——也可能构成合规违规。在配置更多 profile 之前，请与合规团队确认哪些地理区域可以接受。把这一方法与本文前面介绍的客户端重试与速率限制模式配合使用。在 profile 之间迁移流量时，请遵循 [Amazon Bedrock 文档中的分流（ramp）指导](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-support.html)，以避免接收 profile 出现突发的负载尖峰。

**在后端之间迁移流量时会发生什么**

重路由流量（无论是手动操作还是通过重配 profile）都不是零成本操作。有两个影响值得提前规划：

- **Prompt 缓存未命中。** prompt 缓存位于处理过你此前请求的服务槽位上。当流量落到不同的后端时，每个请求都要从冷 prefill 开始。对于系统 prompt 很大或有多轮历史的工作负载，这会增加首 token 时间，并重新产生缓存写入的 token 成本。由于缓存 TTL 只有 5 分钟，低频工作负载在切换之后可能永远无法完全重新预热。
- **已存储的对话状态。** 如果你的应用使用 OpenAI Responses API 并设置 store=true，每个响应都会持久化在生成它的后端上（保留 30 天）。response ID 编码了该来源，因此后续通过 `GET /responses/{id}` 进行的检索，或通过 `previous_response_id` 进行的对话串联，总是会路由回同一个后端。在对话进行中迁移客户会打断这条链。设置 `background=true` 时也是如此，因为它会隐式启用存储。

## 429 与 503 错误的监控与可观测性

看不见的东西就无法管理，因此在应对配额驱动的错误与服务可用性时，稳健的监控至关重要。搭建全面的 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 监控，是主动管理错误并保持应用可靠性的必要条件。

**注意：** CloudWatch 自定义指标、告警与仪表盘会按使用量收费。详情请查看 [CloudWatch 定价](https://aws.amazon.com/cloudwatch/pricing/)。

### 必不可少的 CloudWatch 指标

请监控这些 CloudWatch 指标：

- **Invocations**：成功的模型调用
- **InvocationClientErrors**：包括限流在内的 4xx 错误
- **InvocationServerErrors**：包括服务不可用在内的 5xx 错误
- **InvocationThrottles**：429 限流错误
- **InvocationLatency**：响应时间
- **InputTokenCount/OutputTokenCount**：用于 TPM 监控的 token 用量

为获得更好的洞察，请创建这样的仪表盘：

- 把 429 与 503 放在不同的 widget 中，这样你能看出尖峰是与配额相关还是服务端的问题。
- 按 ModelId 与 Region 拆分指标，以识别哪些模型或 Region 出现了流量升高。
- 并列展示当前流量与前几周的对比，在趋势演变为事故之前发现它们。

### 关键告警

不要等到用户发现失败才行动。请基于如下阈值配置带 Amazon SNS 通知的 CloudWatch 告警：

#### 429 错误

- 5 分钟窗口内出现大量限流事件。
- 连续多个周期出现非零限流计数，说明压力持续存在。
- 配额利用率超过选定阈值（例如 RPM/TPM 的 80%）。

要有效监控配额利用率，你需要同时跟踪实际用量与 Service Quota 限额。对 Bedrock 来说，这需要发布自定义 CloudWatch 指标，把 `max_tokens` 参数与输入、输出 token 计数一并记录下来。Bedrock 的 token 配额系统会在请求开始时根据 `max_tokens` 预留容量，再应用模型特定的 burndown rate（大多数模型为 1x，Claude 4+ 系列为 5x）来计算最终消耗。把这些指标发布到 CloudWatch 后，你就可以创建告警，在计算出的配额消耗接近 Service Quota 限额的 80% 时触发。

这些自定义指标就绪后，使用指标数学表达式设置 CloudWatch 告警，计算你的利用率百分比：`current_usage/SERVICE_QUOTA()*100`。配置告警在该百分比超过你的阈值（例如 80%）时进入 ALARM 状态，并挂上一个 Amazon SNS topic 以通过邮件、短信或其他渠道接收通知。详细的实施指导请参阅[可视化服务配额并设置告警](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Quotas-Visualize-Alarms.html)文档，以及 [Amazon Bedrock 的 TPM 与 RPM 配额监控仪表盘](https://github.com/aws-samples/sample-quota-dashboard-for-amazon-bedrock)示例实现。

#### 503 错误

- 服务成功率低于你的 SLO（例如 10 分钟内低于 95%）。

注意：服务水平目标（SLO）是一个内部性能目标，定义你希望为应用达到的可靠性。虽然 AWS 提供了[服务水平协议（SLA）](https://aws.amazon.com/bedrock/sla/)，保证 Amazon Bedrock 每月 99.9% 的可用性，但你应用的 SLO 应当更严格，以便在触及 SLA 阈值之前留出缓冲。例如，你可以把 SLO 设为在 10 分钟窗口内测量的 95% 成功率，意味着该时段内失败请求不超过 5%。要监控它，请用 CloudWatch 指标跟踪成功请求与总请求的比率。成功率计算为 `(TotalRequests - Errors) / TotalRequests * 100`，其中 Errors 包括 503 `ServiceUnavailableException` 之类的 500 系列响应。设置 CloudWatch 告警，在该成功率低于 SLO 阈值时触发。由于 [Bedrock 中的 503 错误](https://repost.aws/knowledge-center/bedrock-service-unavailable-error)通常表示瞬时问题或临时资源紧张，突破 SLO 就是早期预警，提示你应在客户影响变严重之前实施缓解策略，例如指数退避或切换到某个 [service tier](https://docs.aws.amazon.com/bedrock/latest/userguide/service-tiers-inference.html)。

- 503 计数突然激增，且与特定 Region 或模型相关。
- 服务可用性（例如成功率 <95%）
- 客户端指标出现连接池饱和的迹象。

#### 告警配置最佳实践

- 使用 [Amazon Simple Notification Service (Amazon SNS)](https://aws.amazon.com/sns/) topic 把告警路由到团队的沟通渠道（Slack、PagerDuty、邮件）
- 设置不同的严重级别：Critical（立即行动）、Warning（尽快排查）、Info（趋势性问题）
- 在合适的地方配置告警操作以触发自动化响应
- 在告警描述中包含详细的排障步骤与 runbook 链接
- 定期测试告警，确保通知正常工作
- 不要在告警消息中包含敏感的客户数据

### 日志分析查询

CloudWatch Logs Insights 查询帮助你从“我们看到错误”走向“我们理解模式”。示例包括：

**查找 429 错误模式：**

```
fields @timestamp, @message
| filter @message like /ThrottlingException/
| stats count() by bin(5m)
| sort @timestamp desc
```

**分析 503 错误与请求量的相关性：**

```
fields @timestamp, @message
| filter @message like /ServiceUnavailableException/
| stats count() as error_count by bin(1m)
| sort @timestamp desc
```

对于并发工作负载，请在客户端设置中配置合适的连接池，这将确保最佳用户体验。

```
config = Config(
max_pool_connections=50, # Adjust based on concurrency requirements
retries={'mode': 'adaptive', 'max_attempts': 5}
) 
```

默认连接池大小（10）对高并发应用可能不够。监控连接池指标并根据工作负载特征进行调整，对生产级应用来说是必要的。

## 小结：构建有韧性的应用

本文涉及的内容很多，我们把它们汇总起来。要成功处理 Bedrock 错误，需要：

- **理解根本原因**：区分配额限制（429）与瞬时问题（503）
- **实施恰当的重试**：对每种错误类型使用不同参数的指数退避
- **为规模而设计**：使用连接池与熔断器
- **主动监控**：搭建全面的 CloudWatch 监控与告警
- **为增长做规划**：申请提高配额并实施回退策略

## 结论

有效处理 `429 ThrottlingException` 与 `503 ServiceUnavailableException` 错误，是在 Amazon Bedrock 上运行生产级生成式 AI 工作负载的关键一环。把配额感知的设计、智能重试、客户端韧性模式与强大的可观测性结合起来，你就能让应用在不可预测的负载下依然保持响应。

作为下一步，找出你最关键的 Bedrock 工作负载，启用本文介绍的重试与速率限制模式，并构建能暴露真实峰值而非仅有平均值的仪表盘与告警。随着时间推移，用真实流量数据来调整配额、回退模型与区域部署，使你的 AI 系统在扩展时既保持响应又值得信赖。对于希望加速事故解决的团队，可以考虑启用 [AWS DevOps Agent](https://aws.amazon.com/devops-agent/)，这是一个由 AI 驱动的 agent，能像经验丰富的 DevOps 工程师那样，通过关联 CloudWatch 指标、日志与告警来调查 Bedrock 错误。它会学习你的资源关系，配合你的可观测性工具与 runbook，并能通过自动识别根因、建议补救措施，显著降低 429 与 503 错误的平均解决时间（MTTR）。
