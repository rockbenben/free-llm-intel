# Amazon Bedrock AgentCore Memory：构建具备上下文感知能力的 agent

五分钟前你刚告诉过它的事就忘掉的 AI 助手，用处并不大。大语言模型（LLM）虽然擅长生成类人的回复，但它们本质上无状态——不会在多次交互之间保留信息。这迫使开发者自建记忆系统来跟踪对话历史、记住用户偏好并跨会话维持上下文，结果常常是在不同应用里反复解决同样的问题。

在 2025 年 AWS Summit New York City 上，我们推出了 [Amazon Bedrock AgentCore Memory](https://aws.amazon.com/bedrock/agentcore/)，这是一项面向 agent 记忆管理的服务。AgentCore Memory 消除了复杂记忆基础设施的管理负担，让开发者可以轻松构建具备上下文感知能力的 agent，同时又能完全掌控 AI agent 记住什么。它提供了强大的能力，可同时维护短期工作记忆（捕获会话内即时的对话上下文）和长期智能记忆（跨会话保存持久的洞见与偏好），从而让 AI agent 能够保留上下文、从交互中学习，并交付真正个性化的体验。

AgentCore Memory 把一次性对话转变为人与 AI agent 之间持续演进的关系。agent 不再反复索要同样的信息（“你的账号是多少？”），也不会忘记关键偏好（“我对贝类过敏”），而是能维持上下文，并自然地在上一次交互的基础上继续。AgentCore Memory 可与其他 agent 构建工具无缝集成，因此开发者不必管理复杂的基础设施，就能为现有 agent 增加持久记忆能力。DIY 的记忆方案要求开发者手动编排多个组件——原始对话存储、向量数据库、会话缓存系统以及自定义检索逻辑——而 AgentCore Memory 提供的是全托管服务，内置存储、智能抽取和高效检索。

本文探讨 AgentCore Memory 所解决的具体难题，介绍其核心概念，并分享最佳实践。

## **AI agent 的记忆难题**

记忆能力是建立有意义的人际关系的基础。我们记住过去的对话，随着时间了解彼此的偏好，并建立加深联系的共同语境。而构建 AI agent 的开发者，历来在实现这些同样基本的能力时面临重大技术挑战，从而在类人的理解与机器交互之间造成了相当大的落差。

在为 AI agent 实现记忆时，开发者会遇到几个根本性挑战：

- **上下文窗口约束**：现代 LLM 处理对话历史的能力有限。为了处理持续进行的客户对话并保持在 token 上限之内，开发者必须实现上下文窗口管理策略（往往是手动剪枝或摘要早期的往来内容）。
- **状态管理复杂**：没有专用记忆系统时，开发者常常自建方案来跟踪对话历史、用户偏好和 agent 状态——在各个项目间反复重造类似的轮子。
- **记忆召回难题：** 只存原始对话数据是不够的。若没有智能抽取和结构化的记忆组织，开发者必须实现复杂系统，才能在恰当的时机识别并呈现相关信息。
- **有持久化而无智能**：现有方案大多聚焦数据存储，而非智能的记忆形成，不提供内置机制来抽取相关洞见或识别对用户重要的模式。

这些限制不仅造成技术障碍——它们还会从根本上影响用户体验，例如：

- 财务顾问 agent 丢失了同一会话中早先讨论过的用户退休目标与策略的相关上下文
- 编码助手无法获取此前已确立的用户编程风格偏好或环境配置细节

没有有效的记忆实现，对话会变得断裂而重复，而不是连续且不断演进的。这会产生不必要的来回交互，增加成本与延迟，同时让用户感到沮丧。

## **认识 Amazon Bedrock AgentCore Memory**

Amazon Bedrock AgentCore Memory 是一项全托管服务，通过同时维护即时知识与长期知识，让你的 AI agent 交付智能、具备上下文感知且个性化的交互。该服务建立在五条关键设计原则之上：

- **抽象化存储**：AgentCore Memory 处理短期与长期信息的存储复杂性，无需开发者管理底层基础设施。
- **安全：** 数据在静态存储和传输过程中均加密。
- **连续性**：会话内的事件按时间顺序存储，以保持准确的叙述流与上下文。
- **数据组织与访问控制**：层级命名空间提供结构化的记忆组织，并为共享的记忆上下文提供细粒度的访问控制。
- **可扩展性与性能：** 以低延迟高效处理海量记忆数据，随用量增长仍能保持快速可靠的检索。

该服务与 Bedrock AgentCore 中的其他服务（如 AgentCore Runtime 和 AgentCore Observability）无缝集成。它把 API 优先的设计与预先验证的默认值结合起来，因此开发者既能快速实现基础记忆能力，又保留了面向高级场景的可扩展性。

## **AgentCore Memory 的核心组件**

AgentCore Memory 由若干关键组件构成，它们协同工作，为你的 agent 同时提供短期上下文与长期智能。

### **1. AgentCore Memory 资源**

记忆资源（memory resource）是 AgentCore Memory 中的逻辑容器，同时封装原始事件与处理后的长期记忆。可以把记忆资源看作 agent 记忆系统的地基——它定义了数据保留多久、如何受到保护，以及原始交互如何转化为有意义的洞见。

创建记忆资源时，你可以指定事件过期时长（最长 365 天），以控制原始对话数据在短期记忆中保留多久。AgentCore Memory 内的数据在静态存储和传输中均加密。默认使用 AWS 托管密钥进行加密，但你也可以选择启用自己客户管理的 KMS 密钥，以获得更强的控制力。

### **2. 短期记忆 **

短期记忆以不可变事件的形式捕获原始交互数据，并按 actor 与 session 组织。这种组织方式支持结构化存储用户与 agent 之间的对话、系统事件、状态变更以及其他交互数据。它接收事件并同步存储到 AgentCore Memory 资源中。这些事件可以是“**Conversational**”（USER/ASSISTANT/TOOL 或其他消息类型），也可以是“**blob**”（包含二进制内容，可用于存储检查点或 agent 状态）。在这两类事件中，只有 Conversational 事件会用于长期记忆抽取。

创建一个事件通常需要 3 个标识符。

- `memoryId:`创建新的记忆资源时会自动生成，并在响应中返回。
- `actorId:`通常用于标识你系统中的实体（用户、agent、项目或其组合），
- `sessionId:`把相关事件归为一组。

这种层级结构可以精确检索相关的对话上下文，而无需加载无关数据。下面我们看如何用 Boto3 client 为客服 agent 创建记忆资源：

```
# Creating a new memory resource 
response = agentcore_client.create_memory(
    name="CustomerSupportMemory",
    description="Memory store for our customer support agent",
    eventExpiryDuration=30,  # Store raw events for 30 days
    encryptionKeyArn="arn:aws:kms:us-east-1:123456789012:key/abcd1234-...",  # Optional customer-managed KMS key
)

# Storing a user message as an event
response = agentcore_client.create_event(
    memoryId="mem-123abcd",
    actorId="customer-456",
    sessionId="session-789",
    eventTimestamp=int(time.time() * 1000),
    payload=[
        {
            "conversational": {
                "content": {"text": "I'm looking for a waterproof camera under $300"},
                "role": "USER"
            }
        }
    ]
)

# Retrieving recent conversation history
events = agentcore_client.list_events(
    memoryId="mem-123abcd",
    actorId="customer-456",
    sessionId="session-789",
    maxResults=10,
)
```

### **3. 长期记忆**

长期记忆包含从原始事件中抽取出的洞见、偏好与知识。与逐字存储数据的短期记忆不同，长期记忆捕获的是跨会话持续存在的有意义信息——例如用户偏好、对话摘要和关键洞见。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/08/memory_extraction.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/08/memory_extraction.png)

抽取过程在事件创建之后异步进行，使用你在记忆资源中定义的记忆策略。这一托管的异步过程会抽取并合并长期记忆记录，以便高效检索。

下面我们看如何为此前的客服 agent 创建长期记忆资源：

```
# Creating a new memory resource with long term
response = agentcore_client.create_memory(
    name="CustomerSupportMemory",
    description="Memory store for our customer support agent",
    eventExpiryDuration=30,  # Store raw events for 30 days
    encryptionKeyArn="arn:aws:kms:us-east-1:123456789012:key/abcd1234-...",  # Optional customer-managed KMS key
    memoryStrategies=[{
        "userPreferenceMemoryStrategy": {
            "name": "UserPreferences",
            "namespaceTemplate": ["/customer-support/{actorId}/preferences/"]
        }
    }]
)
```

### **3.a 命名空间**

命名空间是长期记忆中至关重要的组织概念，为你的记忆资源提供层级结构。它们的作用类似文件系统路径，你可以用它们对记忆进行逻辑分组与分类。在多租户系统中——无论是多 agent、多用户，还是两者兼具——命名空间尤其强大。命名空间有以下几个重要作用：

- **组织结构**：把不同类型的记忆（偏好、摘要、实体）分到不同的逻辑容器中
- **访问控制**：控制不同 agent 或不同上下文中可访问哪些记忆
- **多租户隔离**：用 `/org_id/user_id/preferences/` 之类的模式，为不同用户或组织隔离记忆
- **聚焦检索**：查询特定类型的记忆，而不必在无关信息中翻找

例如，你可以这样组织命名空间：

- `/retail-agent/customer-123/preferences/`：用于某个特定客户的偏好
- `/retail-agent/product-knowledge/`：用于用户可访问的共享产品信息
- `/support-agent/customer-123/case-summaries/session-001/`：用于过往支持案例的摘要

上面的动态命名空间创建，使用了命名空间定义中的特殊占位变量：

- `{actorId}`：使用正在处理的事件中的 actor 标识符
- `{sessionId}`：使用事件中的 session 标识符
- `{strategyId}`：使用策略标识符用于组织

这样就能优雅地构建命名空间结构，而无需硬编码标识符。检索记忆时，你需指定要搜索的确切命名空间：

```
# Retrieving relevant memory records using semantic search
memories = agentcore_client.retrieve_memory_records(
    memoryId="mem-12345abcdef",
    namespace="/customer-support/user-1/preferences/",
    searchCriteria={
        "searchQuery": "Which camera should I buy?",
        "topK": 5
    }
)
```

### **3.b 记忆策略**

记忆策略构成智能层，把原始事件转化为有意义的长期记忆。它们决定应抽取哪些信息、如何处理这些信息，以及产生的记忆应存放在何处。每个策略都配置了特定的命名空间，抽取出的记忆将在其中存储与合并，从而为不同类型的记忆建立清晰的组织结构。所有策略默认都会从长期记忆记录中忽略个人可识别信息（PII）数据。AgentCore Memory 提供 3 种内置策略：

- **语义策略（Semantic Strategy）**：存储对话中提到的事实与知识，供日后参考。例如，“该客户的公司有 500 名员工，分布在 Seattle、Austin 和 Boston 的 3 个办公地点。”
- **摘要策略（Summary Strategy）**：存储对话的滚动摘要，捕获要点与决策，作用范围限定到一个会话。例如，“客户咨询了企业版定价，讨论了实施时间线要求，并要求安排一次后续演示。”
- **用户偏好策略（User Preferences Strategy）**：存储用户的偏好、选择或风格。例如，“用户偏好详细的技术解释而非高层摘要”，“用户偏好用 Python 做开发工作”。

以下是在创建 AgentCore Memory 资源时定义内置记忆策略的几个示例：

```
# defining Memory Strategies
strategies = [{
    "semanticMemoryStrategy": {
        "name": "semantic-facts",
        "namespaceTemplate": ["/customer/{actorId}/facts/"],
    },
    "summaryMemoryStrategy": {
        "name": "conversation-summary",
        "namespaceTemplate": ["/customer/{actorId}/{sessionId}/summary/"],
    },
    "userPreferenceMemoryStrategy": {
        "name": "user-preferences",
        "namespaceTemplate": ["/customer/{actorId}/preferences/"],
    }
]
```

为了提供灵活性，Bedrock AgentCore 还提供**自定义记忆策略（Custom memory strategies）**，允许你选择特定的 LLM，并覆盖用于抽取与合并的 prompt，以适配你的特定领域或用例。例如，你可能想往语义记忆的 prompt 后追加内容，使其只抽取特定类型的事实或记忆。

## **高级特性**

除了核心记忆能力，Amazon Bedrock AgentCore Memory 还提供高级特性，以支撑复杂的 agent 工作流并提升用户体验。

#### **分支（Branching）**

分支允许 agent 从事件历史中的某个特定点创建替代的对话路径。可以把分支想象成路上的岔口——对话可以从同一出发点沿多条不同路径继续。这一强大特性支持若干高级用例：

- **消息编辑**：当用户编辑此前的消息时，分支既保留原始对话流，也保留新的方向。即使早先的输入发生变化，agent 也能保持连贯的上下文。
- **假设情景**：agent 可以在决策过程中探索假设性的路径，而不丢失主对话线索。例如，财务顾问 agent 可以探索不同的投资策略，同时保持原始咨询完好无损。
- **替代方案**：对于复杂的问题求解，agent 可以同时维护多个解决路径，让用户并排比较不同选项。

分支的运作方式是在现有记忆资源内创建一个具名分支，沿用相同的 `actor_id` 和 `session_id`。创建分支事件时，你指定分支名称以及分支起源的 `rootEventId`。这样就能实现替代的对话路径，而无需新的 actor 或 session 标识符。例如：

```
{
  "memoryId": "mem-12345abcdef",
  "actorId": "agent-support-123/customer-456",
  "sessionId": "session-789",
  "eventTimestamp": 1718806000000,
  "payload": [
    {
      "conversational": {
        "content": {"text": "I'm looking for a waterproof action camera for extreme sports."},
        "role": "USER"
      }
    }
  ],
  "branch": {
    "name": "edited-conversation",
    "rootEventId": "evt-67890"
  }
}
```

这种做法让 agent 能在同一记忆资源内管理多条对话路径，提供强大的对话管理能力。

#### **检查点（Checkpointing）**

借助检查点，agent 可以保存并标记对话中的特定状态，形成日后可返回的参照点。这就像在复杂的游戏或应用中保存进度。该特性对以下场景尤其有价值：

- **多会话任务**：把复杂任务拆分到多个会话中，同时保留上下文。用户可以在数天或数周后回来，agent 能恰好从上次离开的地方继续。
- **工作流恢复**：借助工作流恢复，用户可以暂停复杂流程（如抵押贷款申请或旅行规划），并无缝恢复，无需从头开始或重复提供信息。
- **对话书签**：标记日后可能需要参照的重要决策点，例如用户选择了特定偏好或做出关键决定时。

检查点可以通过不同隔离维度（actor 与 session）下的原始事件来实现，之后可通过 `GetEvent` API 取回。blob 负载类型可用于写入各种格式的数据，且不必是对话性的。请注意，这些事件在长期记忆抽取时会被忽略。这些高级特性把 AgentCore Memory 的能力从简单的上下文保留向外延伸，支撑更复杂的 agent 体验，更接近类人的记忆与对话管理。把分支和检查点纳入 agent 设计，你可以打造更自然、更灵活、更个性化的用户交互。

## **最佳实践**

在你的 agent 系统中优化记忆，应当从每个 agent 的核心目标倒推。agent 如何记忆、何时记忆，都应以这些目标为出发点。

### **1. 结构化的记忆架构**

有意识地设计记忆架构，为不同需求实现不同的记忆类型。用短期记忆承载即时的对话上下文，用长期记忆承载持久知识与用户偏好。用层级命名空间（例如 `/org_id/user_id/preferences/`）组织记忆，以实现精确的记忆隔离与检索。根据应用需求与数据隐私政策，考虑合适的存活时间（TTL）设置。例如，支持聊天记录可能保留 30 天，而持久性的客户偏好可能保留更久。

### **2. 记忆策略**

长期记忆的效果在很大程度上取决于你的记忆策略。对于用户偏好抽取、对话摘要等常见需求，使用内置策略；同时也不必犹豫，在你的特定用例上以自定义策略在其之上扩展。定义自定义记忆策略时，聚焦于只抽取直接支持 agent 目标的相关信息。例如，旅行预订 agent 应优先抽取旅行偏好、重要日期和预算约束。

### **3. 高效的记忆操作**

建立一种记忆操作的节奏，在性能与上下文感知之间取得平衡：

- 在每次用户交互中检索相关记忆，以补充上下文（context hydration）
- 使用有针对性的检索方法（用 list events 获取近期的原始上下文，用摘要获取会话上下文，用语义搜索获取相关的长期记忆记录）
- 用 `CreateEvent` API 及时存储新的交互，以维护准确的历史

请注意，长期记忆的抽取与合并是异步过程，因此把新信息写入长期记忆时会有刷新延迟。对于时间敏感的应用，应相应规划，实施合适的缓存、会话处理以及组合式的上下文补充技术。

### **4. 安全与隐私考量**

记忆往往包含敏感信息，因此应落实适当的安全措施：

- 正确使用 actor 与命名空间来组织数据
- 使用基于 [AWS Identity and Access Management（IAM）](https://aws.amazon.com/iam/) 的访问控制，为记忆资源访问实施最小权限控制
- 存储个人信息时考虑隐私影响，并遵循数据保留方面的相关合规要求
- 对高度敏感的数据使用客户管理的 KMS 密钥进行加密
- 实施 guardrails 以[防止 prompt 注入与记忆投毒](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/storage-encryption.html)

### **5. 可观测性**

利用内置的事件跟踪与记忆操作日志，保持对记忆系统的可见性。监控记忆抽取模式，确认它们捕获了正确的信息，并跟踪记忆策略的有效性。定期依据 agent 性能指标与不断演进的用例需求，审视并调整记忆架构。关键在于在全面的记忆保留与高效的资源利用之间取得平衡，同时始终聚焦于 agent 的核心目标。

## **结论**

构建高效 AI agent 最富挑战的方面之一，是维持上下文并从交互中学习，Amazon Bedrock AgentCore Memory 为此提供了完整方案。借助 AgentCore Memory，把灵活的短期事件存储与智能的长期记忆抽取结合起来，你就能在无需管理复杂记忆基础设施的情况下，打造更个性化、更有上下文、更有帮助的 AI 体验。该服务的层级命名空间、可定制的记忆策略以及高级特性，为更复杂的 agent 行为奠定了基础，使其感觉更自然、更接近人类。
