# Amazon Bedrock 上线 Gemma 4 模型

今天，我们宣布 Gemma 4 系列已在 Amazon Bedrock 上线。Gemma 4 由 Google DeepMind 构建，以 Apache 2.0 许可证发布，是一个 open-weight 模型家族，设计上注重在广泛的部署场景中实现每参数智能水平。该系列包含三个经过指令微调的变体：Gemma 4 31B、Gemma 4 26B-A4B 和 Gemma 4 E2B。它们涵盖稠密（dense）和 mixture-of-experts (MoE) 架构，后者每次请求只激活模型参数的一小部分。这些变体提供内置推理、原生 function calling，以及涵盖文本和图像的多模态输入。

独立基准测试反映了 Gemma 4 对每参数智能水平的侧重：[Artificial Analysis](https://artificialanalysis.ai/models/gemma-4-31b) 报告 Gemma 4 31B 的 Intelligence Index 为 39，远高于 4B–40B open-weight 级别 15 的中位数。

采用 open-weight 基础模型 (FM) 投入生产的组织始终面临一个两难：既要使用领先模型，又不能牺牲数据保护、合规一致性和运营控制权。Amazon Bedrock 消除了这一取舍。它通过全托管服务提供领先的 open-weight FM，推理完全运行在 AWS 运营的基础设施上，并具备你期望从 Amazon Bedrock 获得的安全与隐私控制。

本文逐步介绍如何在 Amazon Bedrock 上开始使用 Gemma 4 模型。我们涵盖这些模型支持的能力、可用的服务层级、按需推理如何扩展以处理你的工作负载，以及可用于访问它们的不同 API。借助这些模型，你可以在 Amazon Bedrock 上构建多模态 agent、轻量级应用、文档理解流水线和软件工程工作流。你的 prompt 和补全结果不会被用于训练任何模型，你的内容也不会与第三方共享。

## Gemma 4 的关键能力

Amazon Bedrock 上的 Gemma 4 系列跨越从 23 亿有效参数的紧凑模型到 307 亿参数的稠密模型，让你能选择匹配不同成本和延迟特征的变体。所有变体都支持内置推理模式、面向 agentic 工作流的原生 function calling、结合文本和图像的多模态输入，并开箱即用支持 35 种以上语言，预训练覆盖 140 多种语言。由于模型是 open-weight 的，你可以独立评估模型架构和训练方法，在自己的工作负载上进行基准测试，并在需要定制时用专有数据做 fine-tune。你可以通过全托管的 AWS 服务访问这些模型，无需自行配置基础设施、托管模型权重或运营推理栈。anno

有关受支持模型的最新列表，请参阅 [Amazon Bedrock 模型目录](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)。

### 选择变体

选择最匹配你工作负载性能和成本要求的变体。下表根据用例提供了选择模型的指导：

| **如果你的工作负载……** | **选择** | **原因** |
| --- | --- | --- |
| 推理密集或编码密集，且希望使用单一稠密模型 | **Gemma 4 31B** | 系列中最大的稠密变体；推理和编码性能强劲，具备 256K 上下文窗口。 |
| 高吞吐下成本敏感，同时要求知识广度 | **Gemma 4 26B-A4B** | MoE 设计让推理成本和延迟接近 4B 稠密模型，同时保留大得多的模型的知识容量。 |
| 延迟敏感、端侧风格或多模态分类 | **Gemma 4 E2B** | 最小、最快的变体；适合成本最低或响应最快的多模态工作负载。对该变体设置 `reasoning_effort=high`（见 *启用推理模式*）。 |

整个系列中，Gemma 4 模型共享统一的接口：system prompt、结构化 tool calling、图像输入，以及可按请求切换的 thinking 模式。你只需针对这套 API 开发一次应用，就能根据适合工作负载的成本和延迟特征在各变体之间切换。

### 架构亮点

所有 Gemma 4 变体都采用混合注意力设计，交错使用局部注意力和全局注意力，在 31B 和 26B-A4B 上支持最长 256K tokens 的长上下文，同时保持较小的内存占用。26B-A4B 变体是 mixture-of-experts 模型：总参数 252 亿，但每个 token 只激活 38 亿，以大致 4B 级别的成本和延迟获得更大模型的知识容量。E2B 变体使用 Per-Layer Embeddings (PLE)，把有效参数量（51 亿总参数中的 23 亿）保持在小规模，降低内存和计算成本。架构细节请参阅 [Gemma 4 模型卡](https://ai.google.dev/gemma/docs/core/model_card_4)。

> 注意：Gemma 4 模型请使用 bedrock-mantle 端点。

### 推理模式

Gemma 4 内置推理模式。启用后，模型会在给出最终答案之前输出其内部思考过程。在 `bedrock-mantle` 端点上，你通过 Responses API 的 `reasoning` 参数启用推理，思考过程会作为单独的 reasoning 项与最终答案一同返回（见演练中的 *启用推理模式*）。

在多轮对话中，只把此前各轮的最终答案发回，不要发送它们的 reasoning 项。把先前的推理重放给模型可能降低其回复质量。你仍然可以把推理保留在自己的日志或审计轨迹中。在下一轮发送的历史记录中将其剥离。

## 在 Amazon Bedrock 上访问 Gemma 4 模型

你通过 `bedrock-mantle` 端点访问 Amazon Bedrock 上的 Gemma 4 模型，这是专为 Amazon Bedrock 下一代推理引擎打造的 OpenAI 兼容 API。其端点 URL 为 `https://bedrock-mantle.{region}.api.aws/openai/v1`, 提供 Chat Completions 和 Responses API。

把端点与引擎区分开来很有帮助：*引擎*是底层服务基础设施——设计时采用 Model Deployment Account 隔离和零操作员访问——而*端点*是你调用的 HTTPS API 界面。`bedrock-mantle` 端点就是该下一代推理引擎的公共 API，暴露其完整功能集。要深入了解底层推理引擎，请参阅 [Exploring the zero operator access design of Amazon Bedrock's next-generation inference engine](https://aws.amazon.com/blogs/machine-learning/exploring-the-zero-operator-access-design-of-mantle/)。

`bedrock-mantle` 端点使用与 OpenAI Python 和 TypeScript SDK 相同的接口，因此已经在使用这些 SDK 的团队只需更新 base URL 和 model ID，就能切换到 Amazon Bedrock 上的 Gemma 4 模型。它还支持 Amazon Bedrock API keys、projects 和 client-side tool calling。

## 开始使用 Amazon Bedrock 上的 Gemma 4 系列模型

完成以下步骤，开始在 Amazon Bedrock 上使用 Gemma 4。

### 前置条件

要使用 Gemma 4 模型，你需要一个有权在 `bedrock-mantle` 端点上运行推理的 AWS 账户。授予这些权限的最简单方式是把 AWS 托管策略 `AmazonBedrockMantleInferenceAccess` 附加到你的 AWS Identity and Access Management (IAM) 主体上。它授予对 Mantle 的读取和创建推理权限——即本文示例所需的权限。其中包括 `bedrock-mantle:CreateInference`（授权 Chat Completions 和 Responses 推理调用）和 `bedrock-mantle:CallWithBearerToken`（授权使用 Amazon Bedrock API key 调用端点）。有关创建和管理 API key 的详情，请参阅 [Amazon Bedrock API keys](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html)。

如果你还需要管理 projects、fine-tuning、自定义模型等，可改为附加 `AmazonBedrockMantleFullAccess`，它授予完整的 `bedrock-mantle` 操作集。

### 控制台 Playground

[Amazon Bedrock 控制台](https://console.aws.amazon.com/bedrock)内置一个 chat/text playground，你可以不写任何代码就快速测试模型。按以下步骤加载 Gemma 4 模型并准备好交互：

- 导航到 Amazon Bedrock 控制台。
- 在左侧菜单中选择 **Test playgrounds**。
- 选择 **Chat/Text** playground。
- 在 playground 左上角选择 **Select model**。
- 在类别列表中选择 **Google**。
- 选择一个 Gemma 4 模型。
- 选择 **Apply** 加载模型。
- 确认模型加载成功：模型名称出现在 playground 头部，聊天界面已可输入。

要展示 Gemma 4 31B 的推理和代码生成能力，可在 playground 中尝试以下 prompt：*"设计一个 Python 微服务，暴露一个用于管理任务队列的 REST API。包含错误处理、输入校验，并编写单元测试。解释你的设计决策。"*

### 从 OpenAI SDK 调用 bedrock-mantle 端点

下面的示例使用 OpenAI Python SDK 作为客户端库来调用 `bedrock-mantle` 端点。使用 OpenAI SDK 时，你需要一个 Amazon Bedrock API key。对于生产工作负载，请使用短期 API key。它们会自动过期（最长 12 小时），并继承生成它们的 IAM 角色的权限。如果你已经在使用原生 AWS 凭证而没有 API key，[aws-bedrock-token-generator](https://pypi.org/project/aws-bedrock-token-generator/) 包可以从这些凭证生成短期 bearer token。

```
from openai import OpenAI

client = OpenAI(
    api_key="<your-short-term-bedrock-api-key>",
    base_url="https://bedrock-mantle.us-east-1.api.aws/openai/v1",
)

response = client.chat.completions.create(
    model="google.gemma-4-31b",
    messages=[
        {"role": "user", "content": "Explain the benefits of mixture-of-experts architectures for production inference."}
    ],
    max_tokens=512,
)
print(response.choices[0].message.content)
```

如果你要迁移一个已经使用 OpenAI SDK 格式搭配其他模型的现有应用，迁移通常只需更新 base URL 和 model ID。要控制生成和使用 API key 的权限，请参阅 [Control permissions for generating and using Amazon Bedrock API keys](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys-permissions.html)。

> 注意：本文代码示例从环境变量读取 API key 仅用于演示。在生产环境中，应从 AWS Secrets Manager 或 AWS Systems Manager Parameter Store 等托管 secrets 服务存储和获取凭证，而不是环境变量。

### 多模态输入（图像）

由于 Gemma 4 所有变体都支持图像输入，同一个 Chat Completions API 即可用于视觉任务。`bedrock-mantle` 端点接受内联的 base64 编码 data URL 形式的图像，或 Amazon Simple Storage Service (Amazon S3) URL（`s3://`）形式的图像；不支持任意公共 `https://` 图像 URL。下面的示例读取一个本地图像文件，将其编码为 base64 data URL，并与文本 prompt 一起放入消息内容中：

```
import base64

# Read a local image file and encode it as a base64 data URL.
with open("chart.png", "rb") as image_file:
    image_b64 = base64.b64encode(image_file.read()).decode("utf-8")
data_url = f"data:image/png;base64,{image_b64}"

response = client.chat.completions.create(
    model="google.gemma-4-31b",
    messages=[{
        "role": "user",
        "content": [
            {"type": "image_url", "image_url": {"url": data_url}},
            {"type": "text", "text": "Describe the trend shown in this chart."}
        ]
    }],
)
print(response.choices[0].message.content)
```

或者，你可以传入一个 `s3://` URL 代替 data URL 来引用 Amazon S3 中存储的图像（例如 `{"url": "s3://my-bucket/chart.png"}`）。这避免了在请求体中内联大图像。为获得最佳效果，请把图像内容放在 prompt 中文本之前，这与 Google DeepMind 推荐的 Gemma 4 多模态输入顺序一致。

### 流式响应

对于希望在 token 生成时就展示给用户的聊天和 agent 用例，设置 `stream=True`。响应会变成增量 delta 事件的迭代器：

```
stream = client.chat.completions.create(
    model="google.gemma-4-31b",
    messages=[
        {"role": "user", "content": "Write a short poem about distributed systems."}
    ],
    stream=True,
)

for chunk in stream:
    delta = chunk.choices[0].delta.content
    if delta:
        print(delta, end="", flush=True)
print()
```

流式调用与非流式调用使用相同的 `bedrock-mantle:CreateInference` 权限——前面展示的 IAM 策略已经涵盖。

### Tool calling

Gemma 4 为 agentic 工作流提供原生 function calling。下面的示例展示一个完整的 tool-calling 循环：定义工具、接收模型的 tool call、执行函数，并把结果回传。

```
import json
from openai import OpenAI

client = OpenAI(
    api_key="<your-short-term-bedrock-api-key>",
    base_url="https://bedrock-mantle.us-east-1.api.aws/openai/v1",
)

tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Get the current weather for a given location",
            "parameters": {
                "type": "object",
                "properties": {
                    "location": {
                        "type": "string",
                        "description": "City and country (e.g., Seattle, US)"
                    },
                    "unit": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"],
                        "description": "Temperature unit"
                    }
                },
                "required": ["location"]
            }
        }
    }
]

# Step 1: Send the user request with tool definitions
messages = [
    {"role": "user", "content": "What's the weather like in Seattle?"}
]

response = client.chat.completions.create(
    model="google.gemma-4-31b",
    messages=messages,
    tools=tools,
    tool_choice="auto",
)

assistant_message = response.choices[0].message

# Step 2: Check if the model wants to call a tool
if assistant_message.tool_calls:
    messages.append(assistant_message)

    for tool_call in assistant_message.tool_calls:
        function_name = tool_call.function.name
        arguments = json.loads(tool_call.function.arguments)

        # Step 3: Validate the function name and run it (your implementation)
        if function_name == "get_weather":
            location = arguments.get("location", "Unknown")
            unit = arguments.get("unit", "fahrenheit")
            result = {
                "location": location,
                "temperature": 18 if unit == "celsius" else 64,
                "unit": unit,
                "condition": "Partly cloudy",
                "humidity": 72,
            }
        else:
            result = {"error": f"Unknown function: {function_name}"}

        # Step 4: Return the function result to the model
        messages.append({
            "role": "tool",
            "tool_call_id": tool_call.id,
            "content": json.dumps(result),
        })

    # Step 5: Get the final response incorporating tool results
    final_response = client.chat.completions.create(
        model="google.gemma-4-31b",
        messages=messages,
        tools=tools,
    )

    print(final_response.choices[0].message.content)
else:
    print(assistant_message.content)
```

### Responses API

除 Chat Completions 之外，`bedrock-mantle` 端点还支持 OpenAI Responses API，它用单个 `input` 字段代替 `messages` 列表，并在顶层返回 `output_text` 作为生成的响应。这非常适合单轮生成，以及已经基于 Responses 接口构建的应用：

```
response = client.responses.create(
    model="google.gemma-4-31b",
    input="Explain the benefits of mixture-of-experts architectures for production inference.",
    max_output_tokens=512,
)
print(response.output_text)
```

Responses API 使用与 Chat Completions 示例相同的 Amazon Bedrock API key 和 base URL；只有方法和响应结构不同。需要多轮消息历史或 client-side tool-calling 循环时用 Chat Completions；需要简化的单轮生成，或想获取模型的推理过程时用 Responses API（见下一节）。

### 启用推理模式

Gemma 4 能在最终答案之前产生明确的思考过程，这对复杂的多步骤任务很有用，但代价是更多延迟和 token 消耗。在 `bedrock-mantle` 端点上，你通过 Responses API 设置 `reasoning` 参数来启用。模型会把思考过程作为输出中单独的 reasoning 项返回，最终答案则在 `output_text` 中：

```
response = client.responses.create(
    model="google.gemma-4-31b",
    input="If a train leaves at 3pm at 60 km/h and another leaves an hour later at 90 km/h from the same station, when does the second catch up?",
    reasoning={"effort": "high"},
)

# Final answer.
print(response.output_text)

# The thought process is returned as a separate output item of type "reasoning".
for item in response.output:
    if item.type == "reasoning":
        for block in item.content:
            print(block.text)
```

`effort` 值（`low`、`medium` 或 `high`）控制模型在回答前推理的程度。对于多轮对话，只把最终答案作为历史回传——下一轮输入中排除先前的 reasoning 项。

对于 Gemma 4 E2B，我们建议把 `reasoning_effort` 设为 `high`。最小的变体默认倾向于大量推理，而较高的推理强度会把这些思考保留在专用的推理通道中——既提升输出质量，又防止推理文本泄漏到最终答案里。

### 推荐的采样参数

在 `bedrock-mantle` 端点上，采样由 `temperature` 和 `top_p` 控制。对于 Gemma 4，我们推荐 `temperature=1.0` 和 `top_p=0.95`，它们在推理和非推理模式下都表现良好。

## 清理

按需推理只在调用时产生费用，因此没有需要拆除的基础设施。为避免意外费用：

- 如果你为测试生成了短期 Amazon Bedrock API key，这些 key 会自动过期（最长 12 小时）。要提前吊销，请在控制台中[删除 API key](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html)。删除 API key 会立即吊销所有使用该 key 的应用的访问权限，因此删除前请确保没有活跃应用依赖它。
- 如果你为测试选择了 Priority 层级，请从调用中移除 `service_tier` 参数，把非延迟敏感的流量切回 Standard。
- 有关各层级和各模型的定价详情，请参阅 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)。

## 服务层级

Amazon Bedrock 提供多个服务层级，以匹配不同的工作负载需求：

| **层级** | **最适合** | **特点** |
| --- | --- | --- |
| Priority | 需要最快响应时间的关键任务、面向客户的工作流 | 相比 Standard，每秒输出 token 数 (OTPS) 延迟最多改善 25%。优先于 Standard 和 Flex 请求处理。相比标准按需定价有溢价。无需预付预留或承诺。 |
| Standard | 日常 AI 任务，如内容生成、文本分析和常规文档处理 | 以标准按需定价提供稳定性能。未指定层级时的默认层级。无需承诺。 |
| Flex | 能容忍较长处理时间的工作负载，如模型评估、内容摘要和 agentic 工作流 | 相比 Standard 有折扣定价。延迟更高，尤其在流量高峰时，因为 Flex 请求在 Standard 之后处理。无需承诺。 |

有关每个模型的最新层级可用性，请参阅 [Amazon Bedrock 模型目录](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards.html)。

## 按需推理的扩展

在 Amazon Bedrock 上调用 Gemma 4 模型时，请求默认使用按需推理（Standard 层级），按 token 付费，无需预留容量。按需吞吐量是共享的，并按 AWS 区域分配，因此在区域需求旺盛时，请求可能短暂排队或被限流。对于需要在生产中可靠扩展的应用，针对这一点进行设计很重要。

在 `bedrock-mantle` 端点上，没有每分钟请求数 (RPM) 配额。推理由按模型、按区域的 token 配额管理——分别有每分钟输入 token 和每分钟输出 token 的限制。Gemma 4 和其他开放模型目前没有在 Service Quotas 控制台中公布按账户的 token 配额。它们的吞吐量由内部服务容量决定，因此请使用带指数退避的重试逻辑来处理瞬时限流。通过 prompt caching 读取的缓存输入 token 不计入输入 token 配额。详情请参阅 [bedrock-mantle 端点的配额](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-mantle.html)。

Amazon Bedrock 会返回两个表示请求无法得到服务的 HTTP 错误码：

| **错误** | **含义** | **应对措施** |
| --- | --- | --- |
| HTTP 429 | 该模型的每分钟 token 配额已超出。 | 降低提交速率并用指数退避重试；若持续触及限制，可通过 AWS Support 申请提高配额。 |
| HTTP 503 | 该模型的区域容量压力较大。 | 偶发响应用指数退避重试；持续出现则降低提交速率。 |

在排查生产流量问题时，区分这两种响应很重要。429 表示每分钟 token 配额已超出，最好通过降低提交速率或通过 AWS Support 申请提高配额来解决。503 表示该模型的区域容量压力较大。遵循下一节的渐进扩容指导，可让应用在不中断的情况下继续使用按需推理。

### 处理偶发的 503 响应

当模型需求旺盛时，某些按需推理请求可能偶尔遇到 503 响应。推荐的处理方式是带抖动的指数退避，并限制重试次数。OpenAI SDK 通过其内置的 `max_retries` 设置支持这一点，会用指数退避重试失败的请求。下面的示例配置了用于 `bedrock-mantle` 端点的客户端：

```
from openai import OpenAI

# Retry transient failures with exponential backoff.
client = OpenAI(
    api_key="<your-short-term-bedrock-api-key>",
    base_url="https://bedrock-mantle.us-east-1.api.aws/openai/v1",
    max_retries=6,
)
```

退避与重试是处理 `bedrock-mantle` 端点上这些瞬时响应的推荐方式。

如果 503 响应持续出现，仅靠重试无法解决问题，因为实际请求速率已超出模型可用容量。此时可考虑把延迟敏感的流量路由到 Priority 层级，在需求旺盛时它会优先于 Standard 和 Flex 请求得到处理。

### 处理陡峭的流量爬升

使用 Standard 层级按需推理时，应用的入站流量应与模型区域容量的扩展节奏保持一致。请求速率突然大幅跃升，比系统能够消化的渐进增长更容易触发 503。每当提高对 Gemma 4 模型的请求速率时，请按有节制的增量扩容，而不是直接跳到新的目标量。推荐的爬升流程如下：

- 从你的目标请求速率开始。
- 如果收到 503 响应，把速率降低 50%，并继续降低直到请求稳定成功。
- 在该稳定状态下保持 15 分钟。
- 将速率提高 50%，再保持 15 分钟。
- 重复以上步骤，直到达到目标量。

举个具体例子：如果你的目标是 2,000 RPM 且遇到 503，就降到 1,000 RPM，若错误持续再降到 500。一旦 500 RPM 稳定 15 分钟，就升到 750，再到 1,125，依此类推。跳过 15 分钟的保持期会让每次升档都变成一次全新的负载测试。

### 为延迟敏感的工作负载选择 Priority 层级

除了在 503 持续时被动使用外，Priority 层级也是减少 503 出现、同时继续使用按需推理的有效手段。相比 Standard，Priority 每秒输出 token 数最多提升 25%，且无需预付预留或承诺。应用通过在每次调用中把 `service_tier` 参数设为 `priority` 来选择加入，同一应用内可以混合使用不同层级。面向客户的 prompt、实时 agent，以及其他响应时间直接影响体验的用户交互，都适合使用 Priority。对于后台和批处理式工作，Standard 或 Flex 通常是正确选择，可避免为不会受益的请求支付 Priority 溢价。

### 更多面向生产规模的最佳实践

以下几项实践有助于让推理工作负载在规模化时平稳运行：

- 把大型工作负载分散到数分钟内，而不是集中突发发送，以减轻区域容量压力。
- 把生产流量迁移到新的 Gemma 4 模型版本时，使用 feature flag 逐步提高流量占比，而不是一次性全部切换。
- 把异步工作——模型评估、内容摘要、agentic 回填——路由到 Flex 层级，以获得更好的性价比。
- 对没有数据驻留要求的工作负载，可分布到多个区域，以提升区域需求激增时的韧性。
- 对预期会增长的工作负载，预留两到三倍于预期峰值的余量，作为流量激增的缓冲。

完整指导请参阅 Amazon Bedrock 用户指南中的 [Scaling and throughput best practices](https://docs.aws.amazon.com/bedrock/latest/userguide/scaling-throughput-best-practices.html)。

### 用隐式 prompt caching 降低延迟

Amazon Bedrock 上的 Gemma 4 模型支持隐式 prompt caching，且自动启用。共享相同 prompt 前缀的连续请求可能命中缓存，让模型复用缓存的内部状态而不必重新计算。缓存命中会降低匹配 token 上的推理延迟，无需修改代码或添加缓存标记。

隐式 prompt caching 适用于所有按需服务层级（Standard、Priority 和 Flex），因此无论流量如何路由，应用都能利用它。并非每个请求都会命中缓存，但在具有稳定前缀的工作负载中很常见，例如多轮 agent、retrieval-augmented generation 和长上下文分析——这些场景中 system prompt、tool 定义或源文档会在请求间复用。如果把静态内容放在 prompt 前面、动态内容放在后面，应用就能在缓存命中时获益。
