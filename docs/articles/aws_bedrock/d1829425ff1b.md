# 使用 Amazon Bedrock AgentCore Gateway 治理 AI agent 的工具访问

过去几个月里，在与客户的交流中，有一种情形反复出现。无论他们面对的是编码 agent、自主 agent，还是与人交互的 agent，也无论工作负载的成熟度如何，我们都会从同一个问题开始：“哪些 AI agent 有权访问客户数据，是谁授予了这项权限，如果某个凭证今天泄露，暴露面会是什么样？”如果你组织里没有人能在一分钟之内回答这个问题，那么这篇文章就是为你写的。

当 AI agent 在没有集中治理的情况下连接内部工具时，组织会遭遇难以察觉的访问风险。设想一位基础设施工程师打开同事的笔记本电脑来调试一次构建。配置文件夹里躺着一个名为 `mcp.json` 的文件，里面以明文存着生产数据库密码，旁边还有一条注释写着 TODO: rotate this。安全团队既看不到有哪些 AI agent 正在访问内部工具，也看不到是谁授予了访问权限，更看不到如果那个凭证被不慎暴露会带来怎样的风险敞口。

建议的解决方案使用支持 Model Context Protocol（MCP）的助手，包括 [Kiro](https://kiro.dev/)、[Claude Code](https://docs.anthropic.com/en/docs/claude-code/overview)、Cursor 这类 IDE 辅助工具，以及 [Amazon Quick](https://aws.amazon.com/quick/) 这类 AI 工具。本文聚焦于 AWS 托管服务 Amazon Bedrock AgentCore——一个可以用任意框架或模型大规模构建、连接和优化 agent 的平台。借助 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)（Amazon Bedrock AgentCore 的一项能力），你可以为 agentic 流量提供一个统一、安全的入口来访问组织内的工具。它依赖 [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html)（Amazon Bedrock AgentCore 的一项能力）来完成安全的身份验证、授权和凭证管理。要定义并强制执行 AI agent 与工具交互的安全控制，你可以使用 [AgentCore Policy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html)。之后，你还可以用 [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 为策略补充安全与隐私控制，并用 [AWS Agent Registry](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry.html) 构建集中式目录，用于组织、甄选和发现工具。自托管方案（[Kong Gateway](https://konghq.com/products/kong-gateway)、[Open Policy Agent](https://www.openpolicyagent.org/)、[NeMo Guardrails](https://docs.nvidia.com/nemo/guardrails/home) 和 [LangFuse](https://langfuse.com/)）同样存在，本文会在相关之处提及它们。

## 问题所在

在企业系统中，采用 MCP 部署时存在五种结构性的失效模式，通常被描述为：凭证蔓延（机密散落在每一处本地配置里）、策略漂移（N×M 份配置悄悄产生分歧）、审计缺口（无法回答“谁在何时调用了什么”）、成本不透明（支出无法归因到团队）以及影子 IT（集成在评审之外部署）。

以策略漂移为例。每个 AI 助手都自带一个 `mcp.json`，这是一个包含后端凭证与工具端点的本地文件，且无人监管。一个拥有 10 个助手、连接 5 个内部 API 的团队要维护 50 套彼此独立的凭证，每一套都靠手工配置。当某个后端变更了策略时，这 50 处都得逐一更新。

回想一下前面的问题：哪些助手能访问客户数据，又是谁授予的？大多数团队的应对方式是，在允许任何 AI 使用之前先建一个完整的网关，这要花上几个月，而且交付出来的东西往往并不对症。我们更推荐让控制强度与实际需求相匹配。

## 解决方案：四个范围的成熟度之旅

一个受治理的网关提供单一的受治理端点，知道谁在调用、依据什么权限调用，在工具级和参数级强制执行策略，并记录每一次决策。团队还可以无需工单即可发布工具。每个范围都能独立交付价值，同时保留通往下一范围的路径。

**范围 1：连接。** 一扇受治理的门，让 AI agent 能够触达组织资源。当 MCP 凭证散落在本地配置中、安全团队毫无清单时，就应启用 SSO 身份验证、集中管理凭证，并打开 CloudTrail 审计。

**范围 2：控制。** 知道谁做了什么，并在数据流经的途中清洗敏感数据。当你无法回答“谁在何时、依据哪条策略调用了哪个工具”时，就应引入 Cedar RBAC/ABAC、PII 脱敏、3LO 同意和 DCR。

**范围 3：目录。** 让团队自己去发现和发布工具，包括本地部署的工具。当工具注册需要开工单、本地系统被排除在外时，就应部署 Registry、Resources MCP、OPA，以及按工具的成本归因。

**范围 4：加固。** 锁死边缘、全面监控，并为故障做好准备。当你覆盖超过 1,000 名用户、却还没有熔断机制、仍在用公共 DNS、也没有故障转移时，就应加入私有连接、治理仪表板、弃用工作流和多区域故障转移。

每个范围都能独立交付价值。只有当下一处痛楚出现时才继续推进。下图是范围决策的参考。

## 解决方案演练

以下各节按范围逐个构建网关。先看前置条件，然后随着新的治理问题出现，逐范围推进。

### 前置条件

要跟着本文动手，你需要一个具备创建 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 和 [Amazon Cognito](https://aws.amazon.com/pm/cognito/) 资源权限的 AWS 账户，熟悉 OAuth 2.0 和 AWS Identity and Access Management（IAM），具备基本的 AWS Command Line Interface（AWS CLI）使用经验，并了解 [Model Context Protocol（MCP）](https://modelcontextprotocol.io/specification)。

### 范围 1：连接，最小化的受治理网关

下图展示了范围 1 的最小拓扑：

图 2：MCP 客户端连接 AgentCore Gateway，Amazon Cognito 签发用于身份验证的 JWT，AgentCore Identity 管理出站凭证，一个已注册的目标接收工具调用

**何时需要此范围**：1–20 名试点用户、低风险工具、开始出现影子 MCP。

**关键决策：** 网关归属（基础设施工程团队、安全团队，还是共用）。第一个工具的选择。是强制只走网关，还是与遗留的 `mcp.json` 并存。

**有哪些变化**

你搭建起带 Cognito 支撑的 JWT 授权器的 AgentCore Gateway，并注册一个低风险的 Lambda 目标（例如只读的工单搜索）。授权仍是粗粒度的：任何通过身份验证的客户端都能调用任何已注册的工具。`mcp.json` 在现有公共资源之外新增了一条条目，强调的是缓慢的、增量式的变更。

你可以接入自己的身份提供商（IdP），例如 Amazon Cognito，并与 AgentCore Identity 集成，由它通过 OAuth 2.0 处理[机器对机器（M2M）身份验证](https://aws.amazon.com/blogs/mt/configuring-machine-to-machine-authentication-with-amazon-cognito-and-amazon-api-gateway-part-2/)、为你的 AWS 资源做出站身份验证，或通过 AWS Secrets Manager 处理基于 API key 的身份验证。借助原生的 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) Logs 和 [AWS CloudTrail](https://aws.amazon.com/cloudtrail/)，你现在能知道组织资源在何时被访问、被访问的是哪些。

**客户端流程**

- 助手使用预先配置好的 client_id/client_secret 和网关 URL 完成引导。
- 每个会话中，它获取一个 Cognito token，并把 bearer 附加到 tools/list 和 tools/call 上。
- 网关校验 JWT 并路由到目标。
- 后端凭证始终不离开 AWS。

**实现片段**。

创建一个网关，其 JWT 授权器指向你的 IdP（例如 Cognito），并配置 allowedClients：

```
aws bedrock-agentcore-control create-gateway \
  --name pilot-gateway \
  --role-arn arn:aws:iam::<account-id>:role/GatewayRole \
  --protocol-type MCP \
  --authorizer-type CUSTOM_JWT \
  --authorizer-configuration '{
  "customJWTAuthorizer": {
    "discoveryUrl": "https://cognito-idp.<region>.amazonaws.com/<pool-id>/.well-known/openid-configuration",
    "allowedClients": ["pilot-gateway-client"]
  }
}'
```

这条命令让 Cognito 签发的 JWT 成为网关唯一接受的凭证。

然后注册一个 AWS Lambda 目标（例如只读的工单搜索）：

```
aws bedrock-agentcore-control create-gateway-target \
  --gateway-identifier pilot-gateway \
  --name TicketSearch \
  --target-configuration '{
  "mcp": { "lambda": { "lambdaArn": "arn:aws:lambda:<region>:<account-id>:function:ticket-search", "toolSchema": {"inlinePayload": "<tool-schema-json>"} } }
}'
```

这个 Lambda 现在可以作为 MCP 工具被访问，客户端侧无需任何接线。改为分发一份 `mcp.json`，取代本地服务器条目：

```
{
  "mcpServers": {
    "enterprise-tools-gateway": {
      "url": "https://<gateway-name>.gateway.bedrock-agentcore.<region>.amazonaws.com/mcp",
      "type": "http"
    }
  }
}
```

由于用户基数很小，把这个条目分发到现有的 `mcp.json` 文件中即可。

**上线推进**

**阶段 1（第 1 天）：** 创建一个 Cognito User Pool。部署网关。注册一个低风险的 Lambda 目标。**阶段 2（第 2–3 天）：** 通过 MDM 分发更新后的 `mcp.json`。做端到端验证：获取 token → tools/list → tools/call。**阶段 3（第 1 周）：** 确认每次调用都会出现 CloudWatch Logs 和 CloudTrail 记录。

**结果**。端到端链路跑通，`mcp.json` 现在包含一个能触达全组织资源的端点，管理层也能看到生产力与管控是同步交付的。

走过这一阶段后，如果你开始收到这样的问题：

- 用户是否正在通过工具调用传递 PII（个人身份信息）？我们如何防止这一点？
- 我们是否会征求用户同意，以代表他们执行操作？我们如何核验问责？
- 不同用户组应当对工具拥有不同的访问权限。这能做到吗？

那么你就可以扩大范围了。如果范围 2 已经满足你当前的需求，可直接跳到“注意事项”了解运维指引。

### 范围 2：控制，身份感知的授权与护栏

门已经打开，范围 2 负责指明调用者是谁，并清洗流经的数据。

下图展示了范围 2 中身份、策略与护栏如何集成：

图 3：Gateway、Identity 与 Policy 被带有 Amazon Bedrock Guardrails 的请求和响应拦截器夹在中间；Identity 增加了 DCR 接口（用于 .well-known 端点的 Lambda 和 Amazon API Gateway）、AWS IAM 和 Amazon DynamoDB，而 3LO 引导会把用户重定向到浏览器进行同意

**何时：** 用户基数在增长，合规团队开始问“谁依据哪条策略做了什么”。你需要一个答案，而且 PII 要在落地之前就被清洗掉。

**关键决策：** 身份提供商的选择。认证模型的过渡（code flow 与 client credentials 的取舍）。ENFORCE 之前 LOG_ONLY 持续多久。第一条 Cedar 拒绝规则。

**有哪些变化**

你把网关从机器级信任转向用户级信任。客户端现在通过 [Dynamic Client Registration（DCR）](https://www.runlayer.com/blog/what-is-dynamic-client-registration) 机制被动态加入 AgentCore Gateway 的 allowedClients。在对网关发起第一次 tools/list 调用时，客户端会收到（RFC 9728/8414）元数据，用来调用一个 DCR 中间层；该中间层是位于 Amazon API Gateway 之后的 Lambda，它在 POST /register 时创建 Cognito 应用客户端，并通过 UpdateGateway 把新的 client_id 追加到 AllowedClients。

用户使用 SSO 登录，完成 Authorization Code 流程。此时访问令牌的 sub 声明就是真实用户。自此之后，每个请求都携带该用户身份。第一道安全闸门 AgentCore Policy 会在 Cedar 规则依据 IdP 组声明、token 声明和参数闸门执行 RBAC 的地方介入。例如，可以限制 `DeployCI___invoke` 仅在 `context.input.environment == "staging"` 时可用，从而对特定用户放行或禁止访问。

如果放行，AgentCore Policy 会通过原生 [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 集成来评估请求，在网关层无需自定义代码即可施加 PII 过滤、内容策略和 prompt 攻击检测。对于 Guardrails 覆盖不到的结构性转换或 ABAC 规则，由请求拦截器 Lambda 处理剩余部分。当目标资源需要以用户身份访问某个 SaaS 系统（例如 GitHub 或 Figma）时，AgentCore Identity Credential Providers 会处理 3LO Authorization Code 流程。网关会发出一个 MCP elicitation（-32042 错误），让助手可以在浏览器中引导用户完成同意。

在响应阶段，拦截器清洗非预期数据。每条日志记录都携带 principal、命中的策略 ID、护栏标记和延迟。

**客户端流程：从 M2M 到用户委托**。

- MCP 客户端访问网关 URL，收到一个带 WWW-Authenticate 的 401。
- 它遵循 RFC [9728](https://datatracker.ietf.org/doc/html/rfc9728) / [8414](https://datatracker.ietf.org/doc/html/rfc8414) / [7591](https://datatracker.ietf.org/doc/html/rfc7591) 发现流程，调用你的 DCR 中间层，签发一个以用户为作用域的客户端。
- 用户通过托管 UI（背后是企业 SSO）使用 Authorization Code + PKCE 登录。token 的 sub 声明就是真实用户。
- tools/list 返回由 AgentCore Policy 过滤后的目录。不同组的两名用户会收到不同的工具列表。
- 调用依次流经：Policy、请求拦截器、Guardrails、目标、响应拦截器、Guardrails。
- 当某个目标需要以用户身份访问 SaaS（GitHub、Slack）时，网关会发出带授权 URL 的 -32042 elicitation。对于共享同一入站身份链的目标，OBO token 交换会完全取代浏览器重定向。助手打开浏览器，在用户同意时调用 [CompleteResourceTokenAuth](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_CompleteResourceTokenAuth.html) 并重试。

**实现**

使用 `update-gateway` 命令以 LOG_ONLY 模式挂载策略引擎。

下面这条 Cedar 策略同时结合了 RBAC 和参数级 ABAC：

```
// Payments deployers can deploy, but only to staging
permit (
  principal,
  action == AgentCore::Action::"DeployCI___invoke",
  resource
)
when {
  principal.hasTag("groups") &&
  principal.getTag("groups").contains("repo-payments-service") /* Note: for Cognito, the claim is cognito:groups, not groups. Refer to your deployed Gateway Cedar schema for the precise tag names. */ &&
  context.input.environment == "staging"
};

// Read-only tools are open to any authenticated principal with a group
permit (
  principal,
  action in [
    AgentCore::Action::"TicketSearch___invoke",
    AgentCore::Action::"DocsSearch___invoke"
  ],
  resource
) when { principal.hasTag("groups") };
```

第一条规则把有风险的部署钉在 staging 上。第二条让低风险读取保持顺畅。以下 OpenTelemetry span 属性（输出到 aws/spans 日志组）展示了一次 Deny 决策：

```
{
  "principal": "user:alice@example.com",
  "action": "DeployCI___invoke",
  "resource": "gateway/pilot-gateway/target/DeployCI",
  "decision": "Deny",
  "matchedPolicy": "policy-payments-deploy-staging",
  "reason": "context.input.environment != 'staging'"
}
```

这条记录就是你的合规团队一直在要的审计线索。

借助 AgentCore Policy 中与 Amazon Bedrock Guardrails 的原生集成（2026 年 7 月发布），护栏可以直接在 Cedar 策略内部用 suppressOutput 效果和 when guardrails 条件来表达。对于护栏覆盖不到的结构性转换，仍可使用拦截器 Lambda 的方式。下面展示用原生 Cedar 做 PII 过滤的写法：

```
{
  "contentPolicyConfig": {
    "filtersConfig": [{ "type": "PROMPT_ATTACK", "inputStrength": "HIGH", "outputStrength": "NONE" }]
  },
  "sensitiveInformationPolicyConfig": {
    "piiEntitiesConfig": [
      { "type": "EMAIL", "action": "ANONYMIZE" },
      { "type": "US_SOCIAL_SECURITY_NUMBER", "action": "BLOCK" },
      { "type": "CREDIT_DEBIT_CARD_NUMBER", "action": "BLOCK" }
    ]
  }
}
```

SSN 和卡号永远到不了模型。电子邮件会被掩码处理。

部署 DCR 中间层：一个位于 Amazon API Gateway 之后的 Lambda，在 POST /register 时创建 Cognito 应用客户端，并把新的 client_id 追加到 allowedClients。同时提供指向 Cognito 的 RFC 9728 .well-known/oauth-protected-resource 元数据。

创建 3LO 凭证提供者并把它挂到一个目标上。下面是客户端必须处理的最小 -32042 elicitation：

```
{
  "jsonrpc": "2.0", "id": 7,
  "error": {
    "code": -32042,
    "message": "authorization_required",
    "data": {
      "authorization_url": "https://oauth.example.com/auth?session_uri=urn:session:9f3a",
      "session_uri": "urn:session:9f3a"
    }
  }
}
```

当下游资源信任与入站 token 相同的身份链时（例如某个内部微服务，或受 Microsoft Entra ID 保护的 API），网关可以改用 [On-Behalf-Of（OBO）token 交换](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/on-behalf-of-token-exchange.html)。OBO 会把入站访问令牌换成一个新的、限定作用域的 token，它同时携带用户身份和 agent 身份，既没有浏览器重定向，也没有额外的同意流程。在目标上现有的 OAuth 凭证提供者里加上一个 `onBehalfOfTokenExchangeConfig` 块，网关就会透明地完成交换（依据你的 IdP 采用 RFC 8693 或 RFC 7523）。

**上线推进**

**阶段 1（第 1–2 天）：** 部署 DCR 中间层 Lambda 与 API Gateway 端点。更新网关授权器以接受动态注册的客户端。**阶段 2（第 1–2 周）：** 以 LOG_ONLY 模式接入 AgentCore Policy。以仅检测模式部署 Guardrails。监控 aws.agentcore.policy.log_only_decision_flipping_policies，找出那些一旦提升就会改变决策的策略。**阶段 3（第 3 周及以后）：** 把 Policy 切到 ENFORCE。把 Guardrails 切到主动阻断。向用户说明 SSO 同意提示。

**结果**。审计人员拿到答案：谁在何时、依据哪条策略调用了哪个工具。助手收到响应之前，PII 已被清洗。

走过这一阶段后，如果你开始收到这样的问题：

- 平台工程师是不是被“请加上这个工具”的工单淹没了？用户能否无需提交工单就发现并订阅工具？
- 用户是否需要访问不在 AWS 上的系统，例如本地数据库、另一个云，或外部 SaaS？
- 财务能否把网关支出归因到真正驱动它的团队？

### 范围 3：目录，自助服务、注册表与跨环境触达

现在让它变成自助式，并触达 AWS 之外的系统。

下图展示了范围 3 扩展后的架构，包括跨环境连接：

图 4：组织资源既包括通过 AWS PrivateLink 或 AWS Direct Connect 触达的本地系统，也包括通过出站 OAuth 触达的外部 SaaS；一个 Discovery 块承载 AWS Agent Registry 与一个 Resources MCP 服务器，一个 OPA 拦截器接入请求与响应路径，一个 FinOps 块采集 AWS Budgets 和 AWS Cost Explorer

**何时：** “加上这个工具”的工单堆积起来，或者你需要触达另一个厂商或本地环境。用户超过 100 人后，集中式目录和超出 AWS 的触达能力就不再是可选项。

**关键决策：** 带审批的自助发布，还是工单闸门。第一个本地或多云目标。用 OPA 承载全组织策略规则，还是只用更复杂的 ABAC 逻辑或纯 Cedar。

**有哪些变化**

你不再是工具接入的瓶颈，网关也延伸到 AWS 之外的系统。工具负责人现在编写 YAML manifest 来申请新工具，并提交一个会触发安全扫描和平台评审的 pull request。合并后，你的持续集成流水线会调用 create-gateway-target 并自动更新 Cedar 策略。无需工单，也无需手工 UpdateGateway。

你现在可以把 IDE 可能需要的 skill 集中起来：它查询 AWS Agent Registry（现位于 `agent-registry` 命名空间，在九个 AWS 区域可用）来列出 skill，并下载与当前任务相关的那些。管理员通过审批工作流治理可发现性，因此人们只会拿到自己需要的东西，无关的 skill 不会进入助手的上下文，从而减少 prompt 污染。

当请求离开网关时，目标可能位于任何地方：AWS Lambda；你通过 Gateway VPC Egress（使用 `managedVpcResource` 或 `selfManagedLatticeResource` 配置）并经其后的 AWS Direct Connect 或 AWS Site-to-Site VPN 触达的本地数据库；或者你通过 NAT 出站并经出站 OAuth 触达的 SaaS API。客户端分辨不出差别。

在请求路径内部，Open Policy Agent（OPA）评估被加进现有的请求拦截器 Lambda，以覆盖 Cedar 无法原生表达的规则：时间窗口、载荷内容检查、基于速率的访问，以及变更工单要求。第二个 MCP 连接（Resources MCP 服务器）会在会话启动时自动拉取并分发组织上下文，例如 steering 文件、编码规范、prompt 模板、发布清单和 on-call runbook。组织内每个助手都能拿到同样的上下文，无需按开发者逐个配置。

在 FinOps 方面，Amazon CloudWatch 指标过滤器和 AWS Cost Explorer 标签可以把成本归因到每个工具和每个组。财务终于能回答是谁造成的账单。`mcp.json` 现在集中管理，无法自行添加公共配置，并通过 MDM 或中央 MCP registry 分发。除网关之外，你还可以集中管理控制行为的 IDE 管理员配置。

**客户端流程**。引导过程与范围 2 相同，没有新的认证流程。为 Resources MCP 服务器新增的第二个 `mcp.json` 条目会在会话启动时自动拉取，提供组织标准和已批准的 skill。调用仍然经过网关。目标可能位于本地，也可能在 SaaS 中，客户端分辨不出差别。范围 3 在客户端侧是纯增量的，因此上线风险很低。

**实现片段**。

下面这条 OPA Rego 策略处理一条 Cedar 无法原生表达的规则。`db_write` 只允许在工作日的 09:00 到 17:00 UTC 之间、且附带变更工单时执行：

```
package mcp.tools

import rego.v1

default allow := false

allow if {
  input.tool == "db_write"
  clock := time.clock(time.now_ns())
  clock[0] >= 9
  clock[0] < 17
  weekday := time.weekday(time.now_ns())
  not weekday in {"Saturday", "Sunday"}
  input.claims.change_ticket_id != ""
}
```

OPA 原生处理时钟与星期检查，与 Cedar 基于身份和资源的策略形成互补。

工具归属、访问权限和风险等级与你的其余基础设施一起存放在版本控制中。你的持续集成流水线会校验 manifest、运行安全扫描、提交 pull request 供评审，并在合并时调用 create-gateway-target 并更新 Cedar 策略。


组织内每个助手现在都能访问相同的编码规范和 runbook，无需手工配置。

网关流量现在始终留在 AWS 网络上。从那里起，由 AWS Direct Connect 完成到本地的最后一跳。对于非 MCP 端点（A2A agent URL、遗留 REST API），HTTP 直通目标会直接路由流量，不做协议转换。

**上线推进**

**阶段 1（第 1 周）：** 建立 YAML manifest schema 和 CI 流水线。把现有目标迁移到 manifest 驱动的注册方式。**阶段 2（第 2–3 周）：** 部署 OPA 拦截器。创建 Resources MCP 服务器。为本地目标建立 PrivateLink 或 Direct Connect。**阶段 3（第 4 周及以后）：** 配置成本分配标签和 Budgets 告警。分发更新后的 `mcp.json`。逐个组上线，从提交工具申请工单最多的团队开始。

**结果**。范围 2 中工单驱动的接入方式被消除。自然语言发现缩短了上手时间，网关无需迁移工作负载即可触达本地和多云环境。

走过这一阶段后，如果你开始收到这样的问题：

- 你的网关是否仍可从公网访问，监管机构会对此放心吗？
- 如果你的主区域在工作时间发生故障，用户应当遵循的、有文档记录的恢复路径是什么？
- 上个季度有多少已注册工具的调用次数为零，又是谁在为把它们留在账上付费？

那么你就可以扩大范围了。如果范围 3 已经满足你当前的需求，可直接跳到“注意事项”了解运维指引。

### 范围 4：加固，韧性与治理

目录和触达已经可用。范围 4 负责加固边缘，并为故障做好准备。

下图展示了带私有入口和治理仪表板的加固架构：

图 5：新的入口栈包含 Amazon CloudFront、位于公有子网的受 CloudFront 限制的 Application Load Balancer、位于私有子网的 VPC 端点、PrivateLink 以及网关；一个治理面板承载 Amazon Athena、自定义仪表板，以及一个标记未使用资源的 Lambda 函数

**何时**：需要高可用与韧性的 AI 工作负载、受到严格监管的行业，或者对低延迟和灾备有要求的全球用户群。

**关键决策：** 熔断的影响范围。主动-主动还是主动-被动灾备。网关的 SLO 目标。弃用权限的归属。

**有哪些变化**

你加固了边界，并让治理变成监管机构一眼就能读懂的东西。请求现在从你的企业网络内部发起。你的 IDE 不再解析公共网关主机名。取而代之的是，它经由边缘的 Amazon CloudFront（靠近用户）路由，CloudFront 再用共享密钥头转发到公有子网中受 CloudFront 限制的 Application Load Balancer，该密钥头可防止流量绕过 CloudFront。随后请求经私有子网中的 VPC 端点进入 PrivateLink，最终到达网关。公网 DNS 暴露消失了，网关只能通过你的私有路径访问。对于由 Runtime 托管的 agent，启用仅入站强制，使 Runtime 拒绝任何非源自网关的调用。这可以防止调用方绕过策略、护栏和审计。

请求沿着与范围 3 相同的路径，但现在每一次决策都会流入 Amazon CloudWatch 和 AWS CloudTrail，由 [Amazon Athena](https://aws.amazon.com/athena/) 查询回答合规级的问题。例如：“上周哪些 principal 的拒绝率最高，是哪些策略拒绝了他们？”自定义仪表板会呈现调用量、延迟分位数、护栏介入率、每条策略的拒绝率、被拒最多的 principal，以及带异常告警的管理层合规视图。

对于全球用户，Multi-AZ 在单个区域内提供很强的韧性。你可以进一步用 [Amazon Route 53](https://aws.amazon.com/route53/) 健康检查故障转移和多区域主动-被动部署来扩展，其中网关定义和注册表状态通过你的流水线复制。把工具设计成幂等的，这样 DNS 故障转移后的第一次重试才是安全的。

最后，一个每晚运行的弃用 Lambda 会读取 Amazon CloudWatch 调用指标，并对任何 30 天内零使用的工具提交 pull request。负责人会收到通知，注册表会标记该工具，策略转为 LOG_ONLY，90 天后目标被移除。你的网关永远不会堆积僵尸工具。

**客户端流程**。认证与发现流程与范围 3 保持不变。助手在企业网络上运行，并且有一条通往网关 PrivateLink 端点的路由，主机名可能只在网内可解析。使用 Route 53 故障转移时，失败的请求会触发 DNS 重新解析并落到次要区域。客户端现在还需要处理向用户呈现的 Deprecation 头（RFC 8594）、配额耗尽时的 429 与 Retry-After，以及可选地通过 `traceparent` 与网关 span 关联的 OpenTelemetry trace。

**实现**。

下面的 Amazon Route 53 故障转移记录集在两个区域中配置网关端点：

```
[
  {
    "Name": "gateway.example.com.", "Type": "CNAME", "SetIdentifier": "primary-us-west-2",
    "Failover": "PRIMARY", "TTL": 30,
    "HealthCheckId": "hc-0123456789abcdef0",
    "ResourceRecords": [{"Value": "dxxxxxxxxxxxxx.cloudfront.net"}]
  },
  {
    "Name": "gateway.example.com.", "Type": "CNAME", "SetIdentifier": "secondary-eu-west-1",
    "Failover": "SECONDARY", "TTL": 30,
    "ResourceRecords": [{"Value": "dyyyyyyyyyyyyy.cloudfront.net"}]
  }
]
```

当主健康检查失败时，DNS 会在一个 TTL 内切换到次要区域。

下面这条针对 AWS CloudTrail 的 Amazon Athena 查询回答“上周哪些 principal 的拒绝率最高，是哪些策略拒绝了他们？”：

```
SELECT attributes.`aws.agentcore.policy.determining_policies` as policies, COUNT(*) AS denies,
  DATE_TRUNC('day', from_iso8601_timestamp(event_time)) AS day
FROM aws_spans_export
WHERE attributes.`aws.agentcore.policy.authorization_decision` = 'DENY'
  AND from_iso8601_timestamp(event_time) > current_date - INTERVAL '7' DAY
GROUP BY principal, matched_policy, DATE_TRUNC('day', from_iso8601_timestamp(event_time))
ORDER BY denies DESC
LIMIT 25;
```

这条 CloudWatch Logs Insights 查询（在网关上启用 tracing 后针对 aws/spans 日志组运行）为仪表板磁贴提供数据，让偏差在用户开始提交工单之前就暴露出来。

下面的 AWS Cloud Development Kit（AWS CDK）片段搭建 CloudFront、受 CloudFront 限制的 Application Load Balancer 和 VPC 端点栈：

```
distribution = cloudfront.Distribution(self, "GatewayEdge",
    default_behavior=cloudfront.BehaviorOptions(
        origin=origins.LoadBalancerV2Origin(alb,
            custom_headers={"X-Origin-Verify": origin_secret.secret_value.unsafe_unwrap()}),
        allowed_methods=cloudfront.AllowedMethods.ALLOW_ALL,
        viewer_protocol_policy=cloudfront.ViewerProtocolPolicy.HTTPS_ONLY,
    ),
    web_acl_id=waf_acl.attr_arn,)

ec2.InterfaceVpcEndpoint(self, "GatewayEndpoint",
    vpc=vpc, service=ec2.InterfaceVpcEndpointAwsService("bedrock-agentcore.gateway"),
    subnets=ec2.SubnetSelection(subnet_type=ec2.SubnetType.PRIVATE_WITH_EGRESS))
```

共享密钥头确保流量只能经由 CloudFront 到达 ALB，而不能走直接的 DNS。

下面这个每晚运行的弃用 Lambda（伪代码）读取 Amazon CloudWatch 指标并提交弃用 pull request：

```
def handler(event, _ctx):
    for tool in list_registry_tools():
        datapoints = cw.get_metric_statistics(
            Namespace="AWS/BedrockAgentCore",
            MetricName="Invocations",
            Dimensions=[{"Name":"ToolName","Value":tool.name}],
            StartTime=now()-timedelta(days=30), EndTime=now(),
            Period=86400, Statistics=["Sum"],
        )["Datapoints"]
        if sum(p["Sum"] for p in datapoints) == 0:
            open_pr(f"deprecate/{tool.name}",
                body="No invocations in 30d; moving to LOG_ONLY, removal in 90d.")
```

僵尸工具会沿着创建它们的同一套代码评审流程被自动退役。

**上线推进**

**阶段 1（第 1–2 周）：** 部署 CloudFront + ALB + VPC 端点栈。更新 DNS。验证公共端点已无法解析。**阶段 2（第 3–4 周）：** 部署 Athena 表和治理仪表板。建立 Route 53 健康检查与故障转移记录。把网关定义复制到次要区域。**阶段 3（第 2 个月）：** 部署弃用 Lambda。做一次故障转移演练：禁用主健康检查并验证 DNS 切换。

**结果**。零信任网络控制、私有连接、边缘的全球低延迟访问，以及有文档记录的恢复路径。治理变成了一个看得见的产品。

以上就是完整的四范围构建，但大多数团队并不需要每一个范围。本文余下部分帮你判断在哪里停下，给出一个真实案例，并讨论运维注意事项。

## 注意事项

这些注意事项横跨所有范围。请注意 Amazon Bedrock AgentCore Gateway 和 Amazon Bedrock Guardrails 的可用性因 AWS 区域而异。当前区域支持情况请参阅 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/)。

**网关运维**。从第一天起，就以等同于生产服务的运维实践对待网关。越晚改动代价越高。把 dev、staging 和 production 分别放在不同的 AWS 账户、IdP 客户端 ID 和策略引擎中，并通过 IaC 晋级。选择单一的全组织网关，还是按业务单元划分以实现隔离。在接入时强制命名规范。按风险等级、数据分类、负责人 SLA 和认证模型契合度来评估新工具。注册流程：申请、评审、扫描、staging、观察期、生产。

**安全**。明文凭证和无作用域的出站访问会带来意外访问的机会。把凭证存放在 AWS Secrets Manager 或 HashiCorp Vault 中并配置轮换，或者通过 Private Key JWT 客户端认证彻底消除共享机密（私钥放在 AWS KMS 中，每次签名操作都记录在 CloudTrail 里）。绝不要把凭证存在环境变量中。通过 MDM 分发集中管理的 `mcp.json`。在企业代理或端点检测与响应（EDR）上阻断助手流向非网关 MCP 端点的流量。要求 TLS 1.2+ 以及使用 AWS Key Management Service（AWS KMS）的静态加密。使用带 `aws:CalledViaAWSMCP` 或 `aws:ViaAWSMCPService` 的 AWS IAM 服务控制策略（SCP）来拒绝通过 AWS 托管的 MCP 服务器发起的破坏性操作（这些键不适用于经由你自己的 AgentCore Gateway 的流量。对于你自己的网关，请改为限制目标执行角色）：

```
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyDestructiveFromMCP",
    "Effect": "Deny",
    "Action": ["s3:DeleteBucket","kms:ScheduleKeyDeletion","dynamodb:DeleteTable"],
    "Resource": "*",
    "Condition": { "Bool": { "aws:ViaAWSMCPService": "true" } }
  }]
}
```

即使某条 Cedar 策略溜过了评审，SCP 这道兜底也能挡住最坏的结果。

**韧性**。网关宕机时，所有依赖它的助手都不可用。每个网关、目标、策略和注册表条目都以代码形式交付。联邦化的区域网关可以覆盖数据驻留要求（EU、中国、俄罗斯）。复制的是*策略*，不是*数据*。一个网关同时服务 Kiro、Claude Code、Amazon Quick 和 Glean。

**成本**。成本意外总比用量报表来得快。按 principal 和按工具做速率限制（Gateway 可配置的速率限制原生支持这一点，且不额外收费，可按 JWT 声明、目标和工具名做维度作用域）。按组设置预算和配额，并设置软告警先于硬性停止。对幂等的只读工具，在拦截器处缓存响应以减少重复调用。作为价格参考，约 50 名开发者每月总共执行 572,000 次操作，Gateway 与 Policy 合计约需 17 美元（Gateway InvokeTool 每百万次 5 美元，Policy 授权每百万次 25 美元；通过 Gateway 消费时 Identity 为 0 美元）（当前费率请参阅 [Amazon Bedrock AgentCore 定价页](https://aws.amazon.com/bedrock/agentcore/pricing/)）。

**范围 3 资源**：

- 删除 AWS Budgets 告警和成本分配标签。
- 移除用于本地连接的 PrivateLink VPC 端点。
- 从网关中删除 Resources MCP 服务器目标。
- 移除由 YAML manifest 创建的已注册工具目标。
- 删除 OPA 拦截器 Lambda。

**范围 2 资源**：

- 删除 Guardrails 配置。
- 删除请求与响应拦截器 Lambda。
- 删除 DCR 中间层 Lambda 及其 Amazon API Gateway 端点。
- 从 AgentCore Policy 中移除 Cedar 策略。
- 删除用于 ABAC 规则的 DynamoDB 表。

**范围 1 资源**：

- 使用 [DeleteGatewayTarget](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_DeleteGatewayTarget.html) 删除网关目标（例如 TicketSearch）。
- 删除网关本身：`aws bedrock-agentcore-control delete-gateway --gateway-identifier pilot-gateway`（参见 [DeleteGateway](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_DeleteGateway.html)）。
- 删除 Cognito User Pool 应用客户端，以及（如果为此目的创建的话）User Pool。
- 删除网关使用的 IAM 角色（`GatewayRole`）。

## 持续改进

治理是一个活的系统。

**每季度**。回顾拒绝日志并调整策略，收紧过于宽松的规则，放宽那些徒增摩擦却不降低风险的规则。审计 PrivateLink 端点和出站规则。移除任何未使用的东西。收窄网关执行角色。保持 Resources MCP 内容新鲜，并给 steering 文件做版本管理。坚持执行弃用机制，让你的注册表里零僵尸工具。

**每月**。回顾成本异常、护栏介入尖峰和被拒最多的 principal。被拒最多的 principal 往往意味着策略太紧。

**持续**。每一次工具注册和策略变更都以 pull request 形式交付，并由安全与平台团队评审。

## 结论

在本文中，我们走过了治理 AI agent 工具访问的四范围成熟度模型，从单一受治理端点到企业级加固。借助这种方法，团队可以把 AI 生产力与治理控制一同交付，只在真实的痛楚要求时才继续推进。

如果你刚刚起步，先在一个开发账户里搭起范围 1 的网关，让一个助手指向它，并分发新的 `mcp.json`。

如果你需要合规，先以范围 1 作为基础（一天即可完成），再叠加范围 2：加上 DCR 中间层、以 LOG_ONLY 接入 Cedar，并以仅检测模式启用 Guardrails。这两个范围可以在一个 sprint 内一起部署。

如果你正在扩展生产，范围 3 的注册表和自助发布能带来立即可见的用户收益。按工具打标签让财务获得归因能力。逐个组上线。

随着由 IDE 驱动的助手趋于成熟，同一个网关会成为自主 agent 的控制平面。网关不仅提供工具访问，还提供 agent 到 agent 的任务委派，每一次调用都流经策略。

选择与当下痛楚相匹配的范围，并用 [Amazon Bedrock AgentCore Gateway 开发者指南](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 部署你的第一个网关。先从一个位于网关之后的低风险工具开始，与你的身份提供商一起验证端到端的 token 流程，只有当团队提出下一个治理问题时才扩大范围。

本指南为你示范了如何[使用 AgentCore Gateway 构建治理层与工具网关](https://github.com/aws-samples/sample-ai-agent-factory/tree/main/enterprise-mcp-governance-gateway)的示例实现。
