# Kyruus 在 AWS 上构建生成式 AI 医疗服务匹配方案

*本文由 Kyruus Health 的 Zach Heath 共同撰写。*

当健康计划会员需要就医时，他们不该还需要一本词典。然而数以百万计的人正面临这样的困境——用日常语言描述症状，而医疗体系却使用临床术语和复杂的专科分类。这种脱节迫使会员变成业余的医学翻译，试图把“我爬楼梯时膝盖疼”这样的说法转换成骨科或物理医学等专门的搜索条件。传统的医疗服务目录又以繁杂的筛选选项和医学行话加剧了这一问题，导致会员感到挫败、就医受阻，最终给个人和健康计划都带来更高的成本。

[Kyruus Health](https://kyruushealth.com/) 是一家领先的就医通道解决方案提供商，服务于 1,400 多家医院、550 个医疗集团和 100 个健康计划品牌——将 50 万多名医疗服务者与寻求就医的患者连接起来，每年促成 100 多万次预约。为应对医疗导航的挑战，他们开发了 [Guide](https://kyruushealth.com/solutions/guide-for-health-plans/)，这是一个由 AI 驱动、理解自然语言并将会员与合适的医疗服务者匹配起来的解决方案。借助 Guide，会员可以用自己的话表达健康顾虑，并获得个性化的医疗服务者匹配结果，而无需具备临床知识。实施该方案的健康计划报告称，会员体验得到改善、净推荐值（Net Promoter Score，NPS）更高，同时就医转化率和预约安排率也有所提升。

在本文中，我们展示 Kyruus Health 如何使用 AWS 服务构建 Guide。我们将说明 [Amazon Bedrock](https://aws.amazon.com/bedrock/)（一项全托管服务，通过单一 API 提供来自领先 AI 公司和 Amazon 的基础模型（FM）访问）与 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/)（一项托管搜索与分析服务）如何协同工作，理解关于健康顾虑的日常用语，并将会员与合适的医疗服务者连接起来。我们探讨该方案架构、分享实施经验，并审视这一方法如何为健康计划及其会员带来可衡量的业务价值。

## 方案概览

Guide 通过将自然语言的健康顾虑转化为精准匹配的医疗服务者推荐，革新了医疗服务者搜索。该方案使用 Amazon Bedrock 搭配 Anthropic 的 Claude 3.5 Sonnet 来理解对健康顾虑的日常描述，并将其转换为结构化的医学参数。随后使用 OpenSearch Service 将这些参数与全面的医疗服务者数据进行匹配，给出有针对性的推荐。

这一架构使会员能够用通俗语言表达健康需求，同时确保医疗服务者匹配符合临床要求。整个方案通过端到端加密和细粒度访问控制保持 HIPAA 合规，使 Kyruus Health 得以专注于改善会员体验，而无需管理复杂的基础设施。

下图展示了该方案的架构。

![这张 AWS 云架构图勾勒出一个医疗服务者匹配系统。工作流从健康计划应用 UI 开始，通过 Amazon API Gateway 连接到两条主要路径。一条通向 Amazon ECS 对话服务和 Amazon Bedrock 进行 AI 处理，另一条使用 Amazon ECS 医疗服务者搜索服务和 Amazon OpenSearch 进行匹配。系统还包含一个用于存储医疗服务者数据的 Amazon S3 存储桶。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/07/ML-18861_image-1.png)

该架构通过以下步骤将自然语言查询转换为结构化的医疗参数：

- 会员通过健康计划应用输入一条查询，例如“我两周来一直有刺痛沿着腿往下窜”。[Amazon API Gateway](https://aws.amazon.com/api-gateway/) 安全地接收会员的查询请求。
- API Gateway 将请求路由到运行在 [Amazon Elastic Container Service](https://aws.amazon.com/ecs/)（Amazon ECS）上的 Guide 对话服务。
- Guide 的对话服务调用 Amazon Bedrock，由 Anthropic 的 Claude 3.5 Sonnet 处理自然语言。模型识别出可能的坐骨神经痛，并将这段日常描述转换为结构化的医学参数，包括神经科或骨科等合适的专科。
- 健康计划应用使用前面步骤得到的结构化参数，通过 API Gateway 向运行在 Amazon ECS 上的医疗服务者搜索服务发起一次新的 API 调用。
- 医疗服务者搜索服务查询 OpenSearch Service，其中包含此前从 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）摄取的全面医疗服务者数据，包括专科、临床重点领域、所在地以及保险网络参与情况。

匹配到的医疗服务者随后返回健康计划应用，并通过直观的对话式界面呈现给会员。这一架构展示了 Amazon Bedrock FM 与 OpenSearch Service 等专用 AWS 服务的强大组合，形成一个端到端的解决方案，弥合了复杂医疗数据与直观会员体验之间的鸿沟。

## 与 Tribe AI 携手构建

为加速 AI 转型，Kyruus Health 与 [Tribe AI](https://www.tribe.ai/) 合作，这是一家在大规模构建和实施企业级生成式 AI 解决方案方面经验丰富的 AWS 合作伙伴。Tribe AI 在医疗等复杂监管环境中部署 FM 的成熟经验，帮助 Kyruus 降低了采用生成式 AI 的风险。这一合作让 Kyruus 得以专注于自身的医疗领域专业知识，同时借助 Tribe AI 的技术实施经验将 Guide 从概念推向生产。

## 实施经验

Kyruus Health 成功实施 Guide 的过程中积累了一些关键经验，可帮助正在构建医疗 AI 项目的组织：

- **针对医疗行业的测试基础设施必不可少** – Kyruus Health 从一开始就优先使用真实医疗场景进行测试。这一过程确保 Guide 能够准确地把日常描述转换为合适的医疗服务者专科，在匹配决策直接影响健康结果和计划成本的场景下保持可靠性。
- **以用户为中心的设计原则必须指导 AI 实施 **– 通过首先关注会员需求而非技术能力，Kyruus Health 确保其方案解决了医疗导航中真正的痛点。这一做法直接带来了满意度的显著提升和搜索放弃率的下降，说明 AI 实施应当从人的需求出发，而非从技术上的可能性出发。
- **战略性的模型选择驱动业务成果 **– Kyruus Health 发现，与其对所有任务使用单一模型，不如针对医疗导航的不同环节（包括复杂的症状解读和临床专科映射）有策略地部署专门的模型。这种有针对性方法通过将特定 AI 能力与匹配流程的不同部分对齐，提升了医疗服务者匹配的准确性，在优化性能与成本的同时提供更精准的推荐。

这些经验表明，周全的实施方法能够把复杂的医疗导航挑战转化为直观的会员体验，并带来可衡量的业务成果。

## 结论

Guide 展示了由 AWS 驱动的生成式 AI 如何通过弥合日常语言与临床术语之间的鸿沟来改变医疗导航。在本文中，我们探讨了结合 Amazon Bedrock 与 OpenSearch Service 的架构如何将自然语言查询处理为个性化的医疗服务者匹配，帮助会员用自然语言描述症状来找到合适的医疗服务者。

对于正在评估数字化举措的健康计划，Guide 提供了一个解决复杂医疗挑战的蓝图，同时可显著提升会员满意度和预约转化率。要构建自己的生成式 AI 解决方案，可以探索 Amazon Bedrock 以托管方式访问 FM。有关医疗行业的具体指导，请查阅 [AWS Healthcare Industry Lens](https://docs.aws.amazon.com/wellarchitected/latest/healthcare-industry-lens/healthcare-industry-lens.html)，并在 [AWS 医疗与生命科学博客](https://aws.amazon.com/blogs/industries/category/industries/healthcare/)中浏览实施示例、用例和技术指导。
