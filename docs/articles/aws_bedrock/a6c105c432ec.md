# 在 AWS 上用 agentic AI 加速飞机 IFEC 诊断

[Panasonic Avionics Corporation](https://www.panasonic.aero/) 为遍布全球的大型机队提供机上娱乐与连接（IFEC）系统，每年服务数百家航空公司和数十亿乘客。当系统问题在这个量级上影响乘客体验时，工程师必须在数千种各不相同的部署配置中快速定位根因。手工完成这件事——跨不同机队变体关联日志、指标与工单数据——可能要耗费数小时，并且依赖深厚的组织经验。

本文将介绍 Panasonic Avionics Corporation 如何与 AWS 以及 AWS Generative AI Innovation Center 合作、借助其架构指导构建一套 agentic AI 系统。该方案使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/)、[Amazon SageMaker](https://aws.amazon.com/sagemaker/) 和 [AWS Glue](https://aws.amazon.com/glue/)，在保持高准确率的同时显著缩短诊断时间。

## 挑战：让维护在大规模下持续演进

Panasonic Avionics Corporation 的运营数据是监控机队 IFEC 健康状况的关键资产。公司依赖建立在 AWS 上的数据湖与数据系统来存储和整理从整个机队采集的运营数据，每天处理大量数据。

尽管拥有这样稳健的数据基础设施，把原始运营数据转化为可执行的诊断结论，在大规模下仍然存在运营层面的挑战。Panasonic Avionics Corporation 部署服务时，会按各运营主体的需求定制配置。每次部署都会产生独特的日志模式，这让机队范围的性能评估变得复杂。团队只能通过人工复核来关联多个运营数据源中的指标。

这一过程在运营效率与工程生产力方面留下了若干优化空间：

- **人工分析投入** – 跨不同配置做关联需要细致的人工排查。这有助于保证诊断准确性，却也拉长了整体分析周期。
- **平均检测时间（MTTD）** – 检测主要依赖工单生成与人工复核，这影响了新出现模式被识别的速度。
- **平均解决时间（MTTR）** – 解决周期中包含在开始纠正措施之前的大量排查投入，导致端到端解决周期变长。
- **自动化机会** – 重复性的排查任务与日志复核带来了显著的智能自动化机会，在活动高峰期间尤其如此。
- **知识规模化** – 人工关联流程要求对系统有深入的熟悉度，这为用 AI 把组织知识更广泛地扩展到各工程团队创造了机会。
- **资源优化** – 工程师在诊断活动上反复投入时间，压缩了用于创新、功能开发和长期可靠性改进的余力。

Panasonic Avionics Corporation 明确看到了向主动健康监控与机队级模式识别演进的机会，同时又不牺牲诊断的严谨性。目标是在保持分析深度的同时显著改善 MTTD 与 MTTR，让工程师能把更多精力放在方案设计、优化和战略性可靠性提升上，而不是排查性的额外负担上。

## 方案概览

Panasonic Avionics Corporation 与 AWS 以及 AWS Generative AI Innovation Center 合作，探索生成式 AI 如何增强其机队 IFEC 运营中的内部诊断工作流。这次合作把 Panasonic Avionics Corporation 在 IFEC 运营上的深厚领域专长，与通过 AWS 服务提供的生成式 AI 能力、以及创新中心在系统设计上的架构指导结合起来。

### 架构

下图展示了 AWS 上的诊断架构。该方案使用一套多 agent 工作流系统，数据处理要经过三个协同工作的不同层次。*Trend Analyzer* 通过分析关键绩效指标与服务劣化指标来识别异常。*Parallel Diagnostic Agents* 执行具体的诊断功能，包括关联分析、系统检查和日志模式匹配。由大型语言模型（LLM）驱动的 *Summarizer* 把各项输出整合成条理清晰的诊断报告，包含根因分析与建议措施。

### 方案走查

系统通过以下五个阶段处理运营数据：

**1. 摄取与规范化**

系统摄取来自整个机队的原始运营数据，将其转换为标准化的服务指标，并使用 Apache Iceberg 存入 Amazon Simple Storage Service（Amazon S3）数据湖仓。AWS Glue 与 Amazon EMR 承担这条抽取、转换、加载（ETL）pipeline。一个领域本体（domain ontology）——定义机队实体及其关系的共享词汇表——会规范化各机队变体之间的术语。这种一致性让来自不同配置的数据可以在机队规模上比较。该本体还把性能指标与配置元数据、工单信息关联起来，形成用于跨机队诊断的统一视图。

**2. 检测**

Trend Analyzer agent 持续评估关键绩效指标、服务级别达成情况和劣化指标。机队范围的关系建模能发现孤立查看单个部署时看不见的模式，例如只影响共享某个特定配置变体的部署的渐进式劣化。

这让 Panasonic Avionics Corporation 从依赖工单生成的被动检测，转向在问题升级之前主动识别新出现的问题。

**3. 诊断**

当 Trend Analyzer 标记出疑虑时，多个并行诊断 agent 会同时从不同角度展开排查：

- **Correlation Analyzer：** 在共享配置的部署之间发现重复出现的模式，判断问题是孤立的还是系统性的。
- **System Checks：** 对照工单流程校验元数据与服务状态，判断已知的维护活动能否解释所观察到的行为。
- **Log Analyzer：** 使用基于规则和基于模式的检测，把当前日志模式与已知故障模式库进行匹配。

Amazon SageMaker 使用 LangGraph 编排这些 agent——LangGraph 是一个用于管理有状态 AI 工作流的开源框架。Strands Agents SDK（一个用于构建 AI agent 的开源 Python 框架）提供 agent 的实现与执行能力。两者结合让这些 agent 并行运行；在 Panasonic Avionics Corporation 的内部测试中，这把原本需要数小时人工复核的排查缩短为几分钟的自动分析。

**4. 上下文化**

系统会查询过往事件及其解决产物——它们以向量表示形式存放在带 pgvector（用于向量相似度搜索的 PostgreSQL 扩展）的 Amazon Relational Database Service（Amazon RDS）中。语义搜索能召回相似模式及其解决方式，即使具体症状并不相同，从而为系统提供可扩展至整个工程组织的组织记忆。

**5. 建议与行动**

Amazon Bedrock 上的 Anthropic Claude 汇总 Correlation Analyzer、System Checks 与 Log Analyzer 的结论，生成结构化的诊断报告。每份报告都包含根因假设、对受影响机队分段的影响分析，以及按优先级排序的修复建议。

系统按严重程度对报告分类。对于关键发现，系统会自动创建告警、确定事件优先级，并连同建议的解决措施一起路由给相应的工程团队，从而减轻人工分诊负担，同时保留工程团队对修复决策的监督。

AI 生成的建议以召回的运营数据与历史事件为依据，并通过确定性业务规则校验，同时附带支撑证据呈现。人工工程师会审阅诊断结论，并对运营上影响重大的事件批准修复措施。系统还保留 agent 决策与建议的可追溯性，以支撑可审计性与持续改进。

贯穿这五个阶段，构建机队规模的诊断系统需要能随需求增长的基础设施。通过 AWS Glue 与 Amazon EMR 实现的无服务器数据处理、Amazon Bedrock 的模型灵活性，以及 Amazon SageMaker 受治理的 agent runtime，让 Panasonic Avionics Corporation 得以专注于诊断逻辑而不是基础设施。

## 从概念到生产

Panasonic Avionics Corporation 在 AWS Generative AI Innovation Center 顾问团队的指导下验证了该方案，指导内容涵盖事件驱动设计模式、并行处理策略，以及面向生产可扩展性的性能优化技巧。

**尽早建立严格的验证：** Panasonic Avionics Corporation 实施了对照真实基准数据的交叉验证，在整个测试过程中准确率始终超出要求。

**围绕模块化与透明性设计：** 设计原则强调 agent 操作的原子化、prompt 与逻辑的透明性，以及人在环（human-in-the-loop）的复核能力。这种模块化做法允许在方案扩展时独立更新各个 agent，而无需全系统改动。

**有策略地优化 AI 组件：** 指导强调使用调好的参数配置来获得确定性的输出与聚焦的响应。团队把 LLM 的使用限定在摘要与错误推理这类生成式能力能带来明确价值的任务上。

**以持续反馈迭代：** 只有当自动动作与人工专家评估相符时，方案才进入生产，因此系统在缩短解决时间的同时保持了诊断准确率。系统现在每天生成覆盖在用机队的诊断报告。

## 结语

Panasonic Avionics Corporation 在 AWS 上的 AI 驱动诊断系统在多项关键运营指标上带来了可度量的改善。人工分析投入显著下降，平均检测时间（MTTD）和平均解决时间（MTTR）双双改善。在针对性用例中，该系统已显示出 20%–40% 的运营效率提升。支持团队确认重复性排查负担大幅减轻，因为系统现在承担了以往需要数小时人工投入的工作。独立开展诊断的工程能力显著提升，团队因此能够诊断并解决过去必须上报的问题。随着系统规模增长，这些改进从根本上改变了运营模式：团队可以通过 AI agent 应对规模增长，同时降低成本和运营风险。
