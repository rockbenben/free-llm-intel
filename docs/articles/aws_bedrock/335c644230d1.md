# 使用 Amazon Bedrock 构建 just-in-time 知识库

管理多个租户的软件即服务（SaaS）公司面临一个关键挑战：既要高效地从海量文档集合中提取有意义的洞察，又要控制成本。传统做法常常在不必要的存储与处理资源上产生支出，从而影响运营效率与盈利能力。组织需要能够根据租户的实际使用模式智能扩缩处理与存储资源、同时保持数据隔离的解决方案。传统的检索增强生成（RAG）系统会为可能永远不会被查询的文档摄取并维护 embedding，从而消耗宝贵资源，造成不必要的存储成本并降低系统效率。为处理大量中小型租户而设计的系统，可能会超出成本结构与基础设施的上限，或者必须采用孤岛式部署来把每个租户的信息与用量隔离开。更添复杂的是，许多项目本质上是临时的，工作以间歇方式进行，导致数据长期占用知识库系统中的空间，而这些空间本可被其他活跃租户使用。

为应对这些挑战，本文提出一种 just-in-time 知识库方案，通过智能文档处理减少闲置消耗。该方案仅在需要时处理文档，并自动移除未使用的资源，因此组织可以扩展其文档库，而不必按比例增加基础设施成本。

借助可按租户配置限额的多租户架构，服务提供商可以在提供分级定价模式的同时保持严格的数据隔离，这使其非常适合为需求各异的多个客户提供服务的 SaaS 应用。通过 Time-to-Live（TTL）实现的文档自动过期，可确保系统保持精简并聚焦于相关内容；而为频繁访问的文档刷新 TTL，则能让重要信息维持最佳性能。该架构还使限制每个租户在特定时间内可摄取的文档数量、以及租户查询一组文件的速率成为可能。该方案使用无服务器技术来减轻运维开销并提供自动扩缩，让团队可以专注于业务逻辑而不是基础设施管理。通过把文档组织成组并结合基于 metadata 的过滤，系统支持上下文相关的查询，在保持租户间安全边界的同时交付更相关的结果。该架构的灵活性支持自定义租户配置、查询速率和文档保留策略，使其无需大幅重构就能适应不断变化的业务需求。

## 解决方案概述

该架构组合多项 AWS 服务，构建出一个经济高效、按需处理文档的多租户知识库方案。关键组件包括：

- **基于向量的知识库** – 使用 [Amazon Bedrock](https://aws.amazon.com/bedrock) 与 [Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/) 实现高效的文档处理与查询
- **按需文档摄取** – 使用 Amazon Bedrock 的 [CUSTOM](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-data-source-connector.html) 数据源类型实现 just-in-time 处理
- **TTL 管理** – 使用 [Amazon DynamoDB](https://aws.amazon.com/dynamodb) 中的 [TTL 功能](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TTL.html)自动清理未使用的文档
- **多租户隔离** – 通过可配置的资源限额，在用户与组织之间强制实施安全的数据隔离

该方案通过在用户、租户和文件层面进行基于 metadata 的过滤来实现细粒度控制。DynamoDB 的 TTL 跟踪系统支持分级定价结构，租户可以为不同的 TTL 时长、文档摄取限额和查询速率付费。

该工作流包含以下步骤：

- 用户登录系统，系统会为当前用户附加一个租户 ID，用于调用 Amazon Bedrock 知识库。这个认证步骤至关重要，因为它建立了安全上下文，确保后续交互被正确关联到对应的租户。租户 ID 成为基础性的 metadata，使整个工作流中的多租户隔离与资源管理得以正确实施。
- 认证之后，用户创建一个项目，作为其想要查询的文件的容器。这一项目创建步骤建立了把相关文档归组管理所需的组织结构。系统会生成合适的 metadata，并创建必要的数据库条目来跟踪该项目与特定租户的关联，从而在项目层面实现恰当的访问控制与资源管理。
- 项目建立后，用户即可开始上传文件。系统通过生成预签名 URL 来管理这一过程，以保证上传安全。文件上传后会存储在 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）中，系统会自动在 DynamoDB 中创建条目，把每个文件同时与项目和租户关联起来。这种三方关系（文件—项目—租户）对于维持恰当的数据隔离并在后续实现高效查询至关重要。
- 当用户请求针对某个特定项目创建一个与知识库对话的 chat 时，系统开始使用 CUSTOM 数据源摄取该项目的文件。just-in-time 处理正是从这里开始。摄取期间，系统会根据租户所属层级对应的 TTL 间隔设置一个 TTL 值。该 TTL 确保项目文件在 chat 会话期间保持可用，同时为后续的自动清理搭好框架。这一步是按需处理策略的核心，因为文件只在需要时才会被处理。
- 每个 chat 会话都会主动更新所用项目文件的 TTL。这种动态 TTL 管理确保频繁访问的文件留在知识库中，同时让很少使用的文件自然过期。系统会基于实际使用情况持续刷新 TTL 值，在资源可用性与成本优化之间形成高效平衡。这种做法为活跃使用的内容维持最佳性能，同时有助于防止在未使用文档上浪费资源。
- chat 会话结束且 TTL 值到期后，系统会自动从知识库中移除文件。该清理过程由 [Amazon DynamoDB Streams](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Streams.html) 监控 TTL 过期事件来触发，进而激活一个 [AWS Lambda](https://aws.amazon.com/lambda) 函数来移除已过期的文档。这一最后步骤降低了底层 OpenSearch Serverless 集群的负载并优化了系统资源，确保知识库保持精简高效。

## 前提条件

在继续实施方案之前，你需要以下前提条件。本文使用 `us-east-1` AWS 区域。

- 一个处于活跃状态的 AWS 账户，且具有在 `us-east-1` 中创建资源的权限
- 已[安装](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html)的 [AWS Command Line Interface](https://aws.amazon.com/cli)（AWS CLI）
- 已[安装](https://docs.aws.amazon.com/cdk/v2/guide/getting-started.html)的 [AWS Cloud Development Kit](https://aws.amazon.com/cdk/)（AWS CDK）
- 已安装 Git，用于克隆仓库

## 验证知识库并运行查询

在允许用户与其文档对话之前，系统会执行以下步骤：

- 执行校验检查，判断文档是否需要摄取。该过程对用户透明，包括检查 DynamoDB 与知识库中的文档状态。
- 在允许查询之前，验证所需文档已成功摄取并正确建立索引。
- 同时返回 AI 生成的答案与指向源文档的相关引用，从而保持可追溯性，并让用户能够核实响应的准确性。

## 用 TTL 管理文档生命周期

为进一步优化资源使用与成本，你可以使用 DynamoDB 的 TTL 功能实现一套智能的文档生命周期管理系统。它包含以下步骤：

- 文档被摄取到知识库时，会创建一条记录，其中带有可配置的 TTL 值。
- 文档被访问时，该 TTL 会被刷新。
- 使用针对 TTL 过期事件配置了特定过滤条件的 DynamoDB Streams 来触发清理用的 Lambda 函数。
- 该 Lambda 函数从知识库中移除已过期的文档。

见以下代码：

```
# Lambda function triggered by DynamoDB Streams when TTL expires items
def lambda_handler(event, context):
    """
    This function is triggered by DynamoDB Streams when TTL expires items.
    It removes expired documents from the knowledge base.
    """
    
    # Process each record in the event
    for record in event.get('Records', []):
        # Check if this is a TTL expiration event (REMOVE event from DynamoDB Stream)
        if record.get('eventName') == 'REMOVE':
            # Check if this is a TTL expiration
            user_identity = record.get('userIdentity', {})
            if user_identity.get('type') == 'Service' and user_identity.get('principalId') == 'dynamodb.amazonaws.com':
                # Extract the file ID and tenant ID from the record
                keys = record.get('dynamodb', {}).get('Keys', {})
                file_id = keys.get('id', {}).get('S')
                
                # Delete the document from the knowledge base
                bedrock_agent.delete_knowledge_base_documents(
                    clientToken=str(uuid.uuid4()),
                    knowledgeBaseId=knowledge_base_id,
                    dataSourceId=data_source_id,
                    documentIdentifiers=[
                        {
                            'custom': {
                                'id': file_id
                            },
                            'dataSourceType': 'CUSTOM'
                        }
                    ]
                )
```

## 多租户隔离与分级服务级别

我们的架构支持精细的多租户隔离与分级服务级别：

- **按租户过滤文档** – 每次查询都包含用户、租户和文件级别的过滤条件，使系统能够减少被查询的文档数量。
- **可配置的 TTL 值** – 不同的租户层级可以有不同的 TTL 配置。例如：  免费层：摄取 5 个文档，TTL 为 7 天，每分钟 5 次查询。标准层：摄取 100 个文档，TTL 为 30 天，每分钟 10 次查询。高级层：摄取 1,000 个文档，TTL 为 90 天，每分钟 50 次查询。你还可以配置额外的限制，例如每月总查询次数，或每天、每月的摄取文件总数。

## 结论

本文提出的 just-in-time 知识库架构通过仅在查询时处理文档来改变跨多个租户的文档管理方式，减少了传统 RAG 系统的闲置消耗。这一无服务器实现使用 Amazon Bedrock、OpenSearch Serverless 以及 DynamoDB 的 TTL 功能，构建出一个精简的系统，具备智能的文档生命周期管理、可配置的租户限额和严格的数据隔离，这对提供分级定价模式的 SaaS 提供商至关重要。

该方案直面传统系统在成本结构与基础设施上的局限，尤其适用于需要承载大量拥有临时项目的中小型租户的部署。这一架构把按需文档处理与自动化生命周期管理结合起来，交付一种经济高效、可扩展的资源，让组织能够专注于提取洞察而不是管理基础设施，同时保持租户间的安全边界。
