# 使用 Bedrock AgentCore Gateway interceptor 实施细粒度访问控制

随着企业迅速采用 AI agent 来自动化工作流并提升生产力，它们面临一个关键的规模化挑战：在整个组织内管理对数千个工具的安全访问。现代 AI 部署不再只是少数 agent 调用几个 API——企业正在构建统一的 AI 平台，其中数百个 agent、面向消费者的 AI 应用和自动化工作流需要访问跨越不同团队、组织和业务单元的数千个 Model Context Protocol（MCP）工具。

这种规模增长带来了一个根本性的安全与治理问题：如何确保每个调用主体——无论是 AI agent、用户还是应用——只访问其获授权使用的工具？如何根据用户身份、agent 上下文、发起访问的渠道以及不断变化的权限，动态过滤可用工具？如何保护敏感数据在从 agent 到工具再到下游 API 的多跳工作流中流转时的安全？又如何在不牺牲性能、不造成运维瓶颈、也不迫使团队为每个租户或用例部署单独 MCP server 实例的前提下完成这一切？

为应对这些挑战，我们推出一项新功能：[Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 的 gateway interceptor。这一强大的新能力提供细粒度安全、动态访问控制和灵活的 schema 管理。

## 针对工具访问的细粒度访问控制

企业客户正在部署通过统一 AgentCore Gateway 提供服务的数千个 MCP 工具。这些客户使用这一个 MCP gateway 访问来自不同团队、组织、面向消费者的 AI 应用和 AI agent 的工具，每个工具都有对应的访问权限分配给调用主体。挑战在于根据调用主体的访问权限保护 MCP 工具访问，并针对发往 AgentCore Gateway 的 ListTools、InvokeTool 和 Search 调用做出上下文相关的响应。

工具过滤必须基于多个动态因素，包括 agent 身份、用户身份和执行上下文；其中权限可能根据用户上下文、用户访问 agent 的渠道、workspace 访问级别及其他上下文属性动态变化。这需要具有安全意识的过滤机制：权限变更应立即影响工具可用性，且不缓存过期的权限状态。

## MCP 与下游 API 之间的 schema 转换与数据保护

客户在管理 AI agent 与下游 API 之间的契约，同时保持安全性和灵活性方面，面临复杂挑战。组织必须动态地将 MCP 请求 schema 映射到相应的下游 API schema，从而实现关键的数据保护能力，例如脱敏或移除用户可能作为 prompt 一部分发送给 agent 的敏感数据，如个人身份信息（PII）或敏感个人信息（SPI）。当 API 调用不需要这些信息时，这可以防止敏感数据泄露到下游 API。

此外，客户需要 schema 转换能力来应对 API 契约变更，同时保持 MCP schema 完整并与下游实现解耦。这种解耦让 API 演进和版本管理更加顺畅，而不会破坏 AI agent 与工具的契约，因此后端团队可以修改 API 实现、更改字段名、重构载荷或更新认证要求，而无需强制修改 agent 层，也无需重新训练已学习特定工具 schema 的 AI 模型。

## 多租户 SaaS 的租户隔离

以 agent 即服务或工具即服务形式提供服务的组织面临复杂的多租户要求。客户必须为其所有用户部署 MCP server，同时保持恰当的租户隔离，这就要求 tenant ID 和 user ID 都被传递并校验。多租户 MCP server 架构要求不同客户和 workspace 保持完全隔离，工具访问严格按租户边界控制。挑战还延伸到确定是否需要为每个租户部署单独的 gateway，或者单个 gateway 能否在提供适当隔离保障的前提下安全处理多租户场景。

## 动态工具过滤

客户需要实时的、具备上下文感知的工具过滤，以适应不断变化的权限和用户上下文。组织需要统一的 MCP server，能够分两个阶段过滤工具：先按 agent 权限和 workspace 上下文，再按语义搜索——其关键要求是，对动态过滤出的工具列表不得进行缓存，因为权限随时可能变化。

## 自定义 header 传递与身份上下文管理

AI agent 与传统微服务有本质区别：它们的行为是自主且非确定性的。传统的微服务间授权方法通常依赖服务间信任和授权技术，而 AI agent 需要代表终端用户执行工作流，并基于用户执行上下文访问下游工具、API 和资源。然而，将原始授权 token 发送给下游服务会带来重大安全漏洞，例如凭证被盗、权限提升，以及 confused deputy 问题——即权限更高的服务被诱骗代表权限较低的攻击者执行操作。

## Impersonation 与 act-on-behalf 方式

在身份上下文如何穿越多跳工作流（agent 到 agent 到工具再到 API）这一问题上，客户面临一个根本性的安全决策：采用 impersonation 方式还是 act-on-behalf 方式。

采用 impersonation 方式时，原始用户的 JWT token 在调用链的每一跳中都原样传递。尽管实现更简单，但这种方式带来重大安全风险。由于以下风险，我们不推荐这种方式：

- 下游服务收到的 token 权限超出必要范围
- 若任何组件被攻破，权限提升风险增加
- token 范围无法限定到特定的下游目标
- 易受 confused deputy 攻击，被攻破的服务可能滥用权限过高的 token

采用 act-on-behalf 方式时，工作流中的每一跳都会收到一个单独的、专门为该下游目标签发且限定范围的 token，并使用 JWT 在整个过程中传播执行上下文。推荐采用这种方式，因为它具有以下好处：

- **最小权限原则** – 每项服务只获得访问特定下游 API 所需的权限
- **减小影响范围 **– 被盗 token 的范围有限，无法在其他地方重复使用
- **更好的可审计性 **– 借助 AgentCore Observability，清晰的保管链可显示哪个服务代表用户执行了操作
- **token 范围限制 **– 每个下游目标只收到专门针对其 API 限定范围的 token 或凭证
- **安全边界 **– 调用链中的不同服务之间实施恰当的隔离
- **防范 confused deputy **– 范围受限的 token 和凭证可防止服务被诱骗执行未授权操作

act-on-behalf 模型要求 gateway 从传入请求中提取执行上下文，为每个下游目标生成新的限定范围的授权 token，并注入适当的 header，同时保留用户的身份上下文用于审计和授权决策——且不会向下游服务暴露权限过高的凭证。这种安全方法确保 AI agent 能够代表用户执行工作流，同时在调用链的每一跳都维持严格的安全边界。

下图对比了 impersonation 与 act-on-behalf 方式的工作流。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/26/ml-20137-image-3-1.png)

在 impersonation 方式（上图）中，当 User A 连接到 agent 时，agent 会将 User A 的完整身份 token 及其全部 scope（`"order: read, promotions:write"`）原样传递给 Order 工具和 Promotions 工具，这意味着每个工具获得的权限都超出其所需。相比之下，act-on-behalf 方式（下图）展示了 agent 为每个工具创建单独的、限定范围的 token——Order 工具只获得 `"order: read"` scope，Promotions 工具只获得 `"promotions:write"` scope，并且每个 token 都包含一个 `"Act: Agent"` 字段，从而建立清晰的责任链，表明 agent 正在代表 User A 执行操作。这展示了委派如何通过将每个下游服务限制为其所需的具体权限来实现最小权限原则，降低安全风险并防止潜在的 token 滥用。

## AgentCore Gateway：面向 AI agent 的安全 MCP 集成

AgentCore Gateway 将你现有的 API 和 [AWS Lambda](https://aws.amazon.com/lambda) 函数转换为 agent 可用的工具，连接到现有 MCP server，并与重要的第三方业务工具和服务（如 Jira、Asana 和 Zendesk）无缝集成。这一统一访问点支持跨企业系统的安全集成。借助 AgentCore Identity，agent 可以使用 OAuth 标准，在适当的认证和授权下安全访问并操作这些工具。

随着 gateway interceptor 的推出，AgentCore Gateway 帮助组织在两个关键点上通过自定义 Lambda 函数实施细粒度访问控制和凭证管理：

- **Gateway request interceptor **– request interceptor Lambda 函数在传入请求到达目标工具之前对其进行处理，支持基于用户凭证、会话上下文和组织策略的细粒度访问控制、审计轨迹创建、schema 转换等。
- **Gateway response interceptor** – response interceptor Lambda 函数在外发响应返回给调用 agent 之前对其进行处理，支持审计轨迹创建、工具过滤、schema 转换，以及对搜索和列出工具的细粒度访问控制。

```
{

  "mcp": {
    "gatewayRequest": {
        "headers": { "Authorization": "Bearer eyJhbG...", ... },
        "body": { "jsonrpc": "2.0", "method": "tools/list", ... }
    },
    "requestContext": { ... }
  }
}
```

你的 gateway request interceptor Lambda 函数必须返回一个带有 `transformedGatewayRequest` 字段的响应：

```
{
  "interceptorOutputVersion": "1.0",
  "mcp": {
    "transformedGatewayRequest": {  // <-- This field must be added by your code
        "headers": { ... },
        "body": { ... }
    }
  }
}
```

目标服务响应后，gateway response interceptor 会以包含原始请求和响应的事件被调用：

```
{
  "interceptorInputVersion": "1.0",
  "mcp": {
    "gatewayRequest": { ... },
    "requestContext": { ... },
    "gatewayResponse": {  // <-- This field contains the target's response
        "statusCode": 200,
        "headers": { ... },
        "body": { 
            "jsonrpc": "2.0",
            "result": { "tools": [ ... ] }
        }
    }
  }
}
```

你的 gateway response interceptor Lambda 函数必须返回一个带有 `transformedGatewayResponse` 字段的响应：

```
{
  "interceptorOutputVersion": "1.0",
  "mcp": {
    "transformedGatewayResponse": {  // <-- This field must be added by your code
        "statusCode": 200,
        "headers": { ... },
        "body": { ... }
    }
  }
}
```

理解这一请求-响应结构对于实现本文后面探讨的自定义 interceptor 逻辑至关重要。Gateway interceptor 为保护和管理 agentic AI 工作流提供关键能力：

- **Header 管理** – 通过自定义 header 传递认证 token、关联 ID 和元数据
- **请求转换** – 在请求到达目标服务之前修改请求载荷、添加上下文或丰富数据
- **安全增强** – 实现自定义认证、授权和数据清理逻辑
- **细粒度访问控制** – 根据调用主体的访问权限保护 MCP 工具访问，并针对发往 AgentCore Gateway 的 ListTools、InvokeTool 和 Search 调用做出上下文相关的响应
- **多租户 MCP 工具的租户隔离** – 在多租户环境中基于调用用户、agent 和租户身份实施租户隔离与访问控制
- **可观测性** – 添加日志、指标和追踪信息以监控 agentic 工作流

Gateway interceptor 适用于 AgentCore Gateway 的目标类型，包括 Lambda 函数、OpenAPI endpoint 和 MCP server。

## Gateway interceptor 的用例

Gateway interceptor 为 agentic AI 系统带来灵活的安全与访问控制模式。本文介绍三种方式：为工具调用实施细粒度访问控制、基于用户权限动态过滤工具，以及跨分布式系统的身份传播。

### 为工具调用实施细粒度访问控制

AgentCore Gateway 通过统一的 MCP endpoint 暴露多个后端工具。不同角色的用户需要不同的工具权限。你可以结合 JWT scope 与 gateway interceptor 实施细粒度访问控制，确保用户只能调用获授权的工具，并只能发现属于其角色或 workspace 的工具。细粒度访问控制使用由 [Amazon Cognito](https://aws.amazon.com/cognito/)（或其他 OAuth 2 提供商）签发的 JWT scope 值。你也可以使用带有权限映射的 YAML 文件或数据库来实现。我们遵循一个简单的命名约定：用户要么获得对某个 MCP target 的完整访问权限（例如 `mcp-target-123`），要么获得工具级访问权限（例如 `mcp-target-123:getOrder`）。这些 scope 作为传入 OAuth token 的一部分，直接映射到 scope claim 中的工具权限，使授权模型可预测且易于审计。

下图展示了这一工作流。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/26/ml-20137-image-8.jpg)

request interceptor 通过以下步骤在执行时强制实施权限：

- 提取并解码 JWT，获取 scope claim。
- 识别正在调用哪个工具（使用 `tools/call`）。
- 如果根据配置文件或访问策略数据存储，用户既没有完整的 target 访问权限也没有特定工具权限，则阻断请求。
- 对未授权调用返回结构化的 MCP 错误，阻止后端工具处理器执行。

核心授权函数刻意保持极简：

```
def check_tool_authorization(scopes, tool, target):
    if target in scopes:
        return True
return f"{target}:{tool}" in scopes
```

这一模式让调用和发现两条路径（下一节将进一步讨论）都能获得可预测的强制实施效果。你可以为多租户架构添加额外 claim（例如 `tenantId` 和 `workspaceId`）来扩展该模型。

出于运维安全考虑，应让 interceptor 保持确定性，避免复杂分支逻辑，并完全依赖 token claim，而不是 large language model（LLM）指令。通过在 gateway 边界——在 LLM 看到或执行任何工具之前——强制实施授权，你可以在不修改工具实现或 MCP target 的情况下，实现跨角色、租户和域的强隔离。

### 动态工具过滤

agent 通过两种主要方式发现可用工具：允许自然语言查询的语义搜索能力（例如“查找与订单管理相关的工具”），以及提供可用工具完整清单的标准（`tools/list`）操作。这种发现机制是 agent 功能的基础，但也带来重大安全考量。如果没有适当的过滤控制，MCP server 将返回所有可用工具的完整列表，而不考虑发起请求的 agent 或用户的授权级别。这种不受限制的工具发现会向未授权用户或 agent 暴露敏感能力，从而产生潜在安全漏洞。

当目标针对语义搜索或 MCP tools/list 请求返回工具列表时，可以使用 gateway response interceptor 强制实施细粒度访问控制。该 interceptor 在响应到达请求 agent 之前对其进行处理，因此用户只能发现其获授权访问的工具。工作流包括以下步骤：

- 目标校验传入的 JWT token，并返回完整工具列表或基于语义搜索的过滤结果，而不考虑细粒度访问控制。
- 配置的 response interceptor 由 AgentCore Gateway 调用。response interceptor 从载荷中提取并解码 JWT，获取定义用户权限的 scope claim。
- 对列表中的每个工具，interceptor 根据 JWT scope 评估用户的授权情况。
- 用户无权访问的工具会从列表中移除。
- response interceptor 返回一个仅包含获授权工具的转换后响应。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/26/ml-20137-image-10.png)

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/26/ml-20137-image-12.png)

以下是 response interceptor Lambda handler 的代码片段，它执行 JWT token 提取、工具列表检索和基于权限的过滤，然后返回包含获授权工具的转换后响应：

```
def lambda_handler(event, context):
    # Extract gateway response and authorization header
    gateway_response = event['mcp']['gatewayResponse']
    auth_header = gateway_response['headers'].get('Authorization', '')
    token = auth_header.replace('Bearer ', '')

    # Extract scopes from JWT token
    claims = decode_jwt_payload(token)
    scopes = claims.get('scope', '').split()
    
    # Get tools from gateway response (for list tools)
    tools = gateway_response['body']['result'].get('tools', [])
    # from structuredContent(in case of semantic search)
    if not tools:
        tools = gateway_response['body']['result'].get('structuredContent', {}).get('tools', [])
    
    # Filter tools based on scopes
    filtered_tools = filter_tools_by_scope(tools, scopes)
    
    # Return transformed response with filtered tools
    return {
        "interceptorOutputVersion": "1.0",
        "mcp": {
            "transformedGatewayResponse": {
                "statusCode": 200,
                "headers": {"Authorization": auth_header},
                "body": {
                    "result": {"tools": filtered_tools}
                }
            }
        }
    }
```

`filter_tools_by_scope` 函数针对用户允许的 scope 对每个工具实施授权检查：

```
def filter_tools_by_scope(tools, allowed_scopes):
    """Filter tools based on user's allowed scopes"""
    filtered_tools = []
    for tool in tools:
        target, action = tool['name'].split('___')
        # Check if user has full target access or specific tool access
        if target in allowed_scopes or f"{target}:{action}" in allowed_scopes:
            filtered_tools.append(tool)
            
    return filtered_tools
```

### 自定义 header 传递

随着 AI agent 与多个下游服务交互，跨服务边界维护用户身份对于安全、合规和审计轨迹变得至关重要。当 agent 通过 AgentCore Gateway 调用工具时，原始用户的身份必须从 agent 流向 gateway，再从 gateway 流向目标服务。如果没有恰当的身份传播，下游服务就无法实施针对用户的授权策略、维护准确的审计日志或实现租户隔离。在多租户环境中，这一挑战更加突出——不同用户共享同一套 agent 基础设施，却需要严格的数据隔离。

Gateway request interceptor 从传入请求 header 和上下文中提取身份信息，将其转换为下游服务期望的格式，并通过以下步骤在请求到达目标服务之前对其进行丰富：

- gateway request interceptor 从传入请求中提取授权 header，并为下游服务进行转换。
- AgentCore Gateway 编排请求流并管理 interceptor 的执行。
- 目标调用收到经过丰富、且身份信息格式正确的请求。

gateway request interceptor 帮助组织获得对用户操作的端到端可见性，跨服务边界实施一致的授权策略，并保持对数据主权要求的合规。

工作流包括以下步骤：

- MCP 客户端调用 AgentCore Gateway。
- AgentCore Gateway 对传入请求进行认证。
- AgentCore Gateway 调用自定义 interceptor。
- gateway request interceptor 通过添加授权 token 作为参数来转换传入请求载荷，再发送给下游 Lambda target。（我们不推荐将传入的 JWT 原样发送给下游 API，因为存在权限提升和凭证被盗风险，并不安全。不过，也可能存在例外情况：agent 需要使用访问令牌调用 MCP server 以访问下游 API。）或者，你可以移除请求中传入的 JWT，并添加一个新的 JWT，其中使用最小权限的缩小范围 token 来调用相关下游 API。
- AgentCore Gateway 使用转换后的请求调用目标。目标持有由 interceptor Lambda 函数传递的授权 token。
- AgentCore Gateway 返回来自目标的响应。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/26/ml-20137-image-14.png)

以下是执行自定义 header 传递的 interceptor Lambda handler 代码片段：

```
import json
import uuid

def lambda_handler(event, context):
    # Extract the gateway request from the correct structure
    mcp_data = event.get('mcp', {})
    gateway_request = mcp_data.get('gatewayRequest', {})
    headers = gateway_request.get('headers', {})
    body = gateway_request.get('body', {})
    extended_body = body
    
    # Pass through the Authorization header
    auth_header = headers.get('authorization', '') or headers.get('Authorization', '')
    if "arguments" in extended_body["params"]:
        extended_body["params"]["arguments"]["authorization"] = auth_header
    # Return transformed request with Authorization header preserved
    response = {
        "interceptorOutputVersion": "1.0",
        "mcp": {
            "transformedGatewayRequest": {
                "headers": {
                    "Accept": "application/json",
                    "Authorization": auth_header,
                    "Content-Type": "application/json"
                },
                "body": extended_body
            }
        }
    }
    return response
```

## 无认证与基于 OAuth 的授权

许多企业需要灵活的授权模型，在可发现性与安全性之间取得平衡。设想这样一个场景：你希望允许 AI agent 和应用在无需授权的情况下发现和搜索可用的 MCP 工具，从而实现无缝的工具探索和跨工具目录的语义搜索。然而，在真正调用这些工具时，你需要严格的基于 OAuth 的授权，确保只有获授权的 agent 和用户才能执行工具调用。你甚至可能需要按工具制定授权策略：有些工具需要认证，另一些则保持公开可访问；或者不同工具根据调用主体的身份和上下文要求不同的权限级别。

AgentCore Gateway 现在通过在 gateway 层面为所有传入调用引入“No Auth”授权类型，支持这种灵活性。启用后，所有 target 和工具都可在无需认证的情况下访问，以便进行发现。要在方法级别（ListTools 与 CallTools）强制实施 OAuth 授权，或实现按工具的授权策略，你可以使用 gateway interceptor 检查传入 JWT，使用授权服务器的 discovery URL 按照 RFC [6749](https://datatracker.ietf.org/doc/html/rfc6749) 的要求对其进行验证，并以编程方式允许或拒绝对特定方法或工具调用的访问。这一方法为你提供细粒度控制：对 ListTools 和 SearchTools 请求开放发现，同时对 CallTools 请求强制实施严格的 OAuth 校验；甚至可以实现按工具、用户角色、执行上下文或组织所需其他业务逻辑而变化的自定义授权逻辑——同时始终保持 MCP 调用的安全并符合你的安全策略。

下图展示了这一工作流。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/26/ml-20137-image-16.png)

该流程以对 AgentCore Gateway 发起的 No Auth ListTools 调用开始，该 gateway 对所有传入调用配置了通用的 `no-auth`。在此配置下，用户无需授权即可发现可用工具。然而，当用户随后发出 CallTool 请求以调用特定工具时，就需要授权。AgentCore Gateway 调用自定义 request interceptor Lambda 函数，该函数校验授权 header 中的 JWT token，并对照被调工具检查用户的 scope 和权限。如果获授权，interceptor 会转换请求并注入必要的授权上下文以丰富请求，然后 AgentCore Gateway 将转换后的请求转发给目标服务。目标处理请求并返回响应，AgentCore Gateway 再将响应返回给客户端——对实际工具执行强制实施严格的基于 OAuth 的授权，同时保持工具列表的开放发现。

要创建对传入调用配置 No Auth 的 gateway，请将 `authorizerType` 设为 `NONE`，如下面的 CreateGateway API 所示：

```
  "protocolType": "MCP",
  "protocolConfiguration": {
    "mcp": {
      "supportedVersions": ["2025-03-26"]
    }
  },
  "authorizerType": "NONE",
  "roleArn": <role_arn>
}
```

## 可观测性

AgentCore Observability 提供的全面可观测性，对于监控、调试和审计通过 AgentCore Gateway 与多个工具和服务交互的 AI agent 工作流至关重要。Gateway interceptor 在下游服务执行之前强制实施授权、转换请求并过滤数据，使可观测性层成为关键的安全边界。这带来以下关键好处：

- **安全决策可见性** – interceptor 为授权结果生成权威日志，包括允许/拒绝决策和经过评估的 JWT scope。这为审查被拒请求、验证策略行为以及分析授权规则如何跨工具调用实施提供了清晰的审计轨迹。
- **请求与响应可追溯性** – interceptor 捕获 MCP 请求和响应如何被修改，例如 header 丰富、schema 转换和敏感数据脱敏。这实现了载荷变更的完整可追溯性，并支持跨 agent 工作流的安全、合规数据处理。
- **下游工具可观测性 **– interceptor 记录下游工具行为，包括状态码、延迟和错误响应。这在各 target 之间形成一致的可见性，帮助团队排查故障、识别可靠性问题，并理解端到端执行特征。

这些日志还捕获身份和上下文属性，帮助团队在多个用户组或租户共享同一 gateway 的环境中验证授权行为并隔离问题。Gateway interceptor 会自动与 AgentCore Observability 集成，提供以下功能：

- 对授权决策的**实时监控**
- 通过持续时间和调用指标进行**性能瓶颈识别**
- 跨多跳 agentic 工作流的**端到端可追溯性**
- 用于在多租户环境中验证授权行为的**身份和上下文属性**

## 结语

带 gateway interceptor 的 AgentCore Gateway 解决了组织在大规模部署 agentic AI 系统时面临的基本安全与访问控制挑战。所展示的三种模式——工具调用的细粒度访问控制、动态工具过滤和身份传播——为安全的 agentic 架构提供了基础构建块，能够弥合认证缺口、保持凭证隔离并实施自定义安全策略。通过为请求和响应都提供可编程的拦截点，组织可以在不修改底层工具实现或 MCP server 架构的情况下实施细粒度访问控制。随着组织扩展到数百个 agent 和数千个工具，gateway interceptor 提供了所需的灵活性和控制力，在复杂 agentic AI 部署中维持安全、合规和运营可见性，同时契合企业集成模式与安全最佳实践。带 gateway interceptor 的 AgentCore Gateway 为跨 agentic AI 架构实施企业级安全控制提供了灵活基础。要进一步了解如何应用 gateway interceptor 解决常见企业挑战，请参阅以下代码示例：
