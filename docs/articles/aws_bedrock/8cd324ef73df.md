# 使用 Amazon Bedrock 实现向量 prompt 文档分类

在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上进行向量 prompt 分类，可以帮助保险公司准确地对每天数以千计的文档进行分类：保单（policy）、宣誓书（affidavit）、批单（endorsement）和监管表单，用于合规、理赔和客户服务。人工分类耗时且容易出错，而传统的自动化方法则难以处理那些看起来相似、用途却不同的文档。一份保单批单和一份监管宣誓书可能包含相似的术语，但把它们分错类可能导致合规违规或处理延误。

本文演示如何用 [Strands Agents SDK](https://strandsagents.com/latest/) 构建一个多 agent 方案。该方案编排三个专职 agent：负责文本推理的 Document Analysis Agent、负责版式模式识别的 Vector Similarity Search Agent，以及负责质量保证的 Validation Agent。每个 agent 都在自己的专长范围内自主工作，然后通过一个 Orchestrator 协作产出结果。

你将学会如何把这套多 agent 架构用在你自己的文档分类需求上，文中附有代码示例与技术指引。这一多 agent 方法把 [Anthropic 的 Claude Haiku 4.5](https://aws.amazon.com/bedrock/anthropic/) 的先进推理能力，与 [Amazon Bedrock](https://aws.amazon.com/bedrock) 上可用的 [Amazon Titan Multimodal Embeddings](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-models.html) 的视觉模式识别能力结合起来，以获得更好的分类准确率。

## 方案概览

该方案架构组合了多个专职 AI agent，每个都针对文档分析的某个特定方面做了优化，并通过协同编排一起工作。这一多 agent 方法通过利用 Amazon Bedrock 上可用的不同基础模型与技术的独特优势，解决了单模型分类的局限。

### 使用 Strands Agents SDK 进行多 agent 协同

在我们的测试中，单模型方法难以处理既需要文本分析又需要视觉分析的边缘情况和复杂文档。多 agent 系统通过把分类任务拆解为多个专职子任务来解决这个问题，每个 agent 专注于自己的专长领域。

我们选择 [Strands Agents SDK](https://strandsagents.com/)，是因为它实现了 [agents as tools](https://strandsagents.com/docs/user-guide/concepts/multi-agent/agents-as-tools/) 模式，而我们的分类系统需要一个能把专职 agent 作为可调用工具来调用的编排器。Validation Agent 调用各个专家、比较它们的分类结果，并在不需要自定义编排代码的情况下解决分歧。这一模式带来几个优势：

- **模块化**：每个 agent 都可以独立开发、测试和改进。
- **透明度**：每个 agent 都为它的决策给出推理，形成可审计的记录。
- **灵活性**：可以在不重构整个系统的前提下新增 agent。
- **可靠性**：编排器负责 agent 协同、错误处理和结果综合。

### 架构组件

架构的核心是*Validation Agent*，它充当编排器，并用 Strands Agents SDK 实现*agents as tools*模式。这个 agent 通过交叉验证与置信度打分提供质量保证。它比较来自*Document Analysis Agent*和*Vector Similarity Search Agent*的输出，识别一致与分歧之处，然后生成最终分类以及相应的置信度分数。这一步校验帮助系统保持高准确率，同时把边缘情况标记出来交由人工复核。Validation Agent 与两个专职 agent 协作：

**Document Analysis Agent**：该 agent 在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上使用 [Anthropic 的 Claude Haiku 4.5](https://aws.amazon.com/bedrock/anthropic/)，进行先进的文本推理与法律语言解读。Claude 擅长理解复杂文档、抽取关键信息，并识别文本中指示文档类型的细微模式。该 agent 分析文档内容、元数据和语言特征，以生成分类假设。

**Vector Similarity Search Agent**：该 agent 使用 [Amazon Titan Multimodal Embeddings G1](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-models.html)，把文档转换成高维向量表示，用于视觉相似度搜索。Claude Haiku 4.5 擅长理解文档内容：分析文本、抽取关键信息、识别语言模式。Vector Similarity Search Agent 则通过聚焦视觉与结构特征来补充这一点。该 agent 捕捉的是文档看起来如何，而不是它说了什么。它识别表单版式、表格结构和排版约定等格式模式——即使文本内容有变化，这些模式也能区分文档类型。该 agent 使用 [FAISS](https://faiss.ai/index.html)（Facebook AI Similarity Search）做高效的向量相似度搜索，从而支持与已知文档模板的快速比对。

通过把文本分析与相似度分析结合，并内建校验，这套多 agent 架构获得了更高的分类准确率，并为自动化决策提供可靠的置信度分数。

在接下来的各节中，你将学会如何实现每个组件并部署完整方案。

## 实现多 agent 文档分类系统

下面我们逐步实现多 agent 系统的每个组件。完整代码可在我们的 GitHub 仓库中获取。

### 步骤 1：配置基础模型

首先，通过一个 Amazon Bedrock 推理配置文件（inference profile）配置对 Claude 模型的访问。这可以在各区域之间提供一致的性能与可用性。

```
def create_bedrock_model(
    model_id: str = "anthropic.claude-haiku-4-5-20251001-v1:0", #
    temperature: float = 0.1,
    max_tokens: int = 4096
) -> BedrockModel:
    """Create a configured Bedrock model instance."""
    return BedrockModel(
        model_id=model_id,
        region_name="us-east-1",
        temperature=temperature,
        max_tokens=max_tokens
    )
```

**提示：** 为了获得更低的延迟和更高的可用性（HA），你可以使用跨区域推理配置文件，方法是在模型 ID 前加上与部署区域匹配的地理前缀（us.、eu. 或 ap.）。

### 步骤 2：创建 Document Analysis Agent

Document Analysis Agent 使用 Claude Haiku 4.5 的先进推理能力，专门做文本内容分析。该 agent 使用结构化输出，返回一致的、机器可解析的分类结果。

```
class TextualAnalysisOutput(BaseModel):
    """Structured output for document text analysis."""
    classification: str = Field(description="Document category: POLICY, AFFIDAVIT, or MISCELLANEOUS")
    confidence: float = Field(description="Classification confidence score from 0.0 to 1.0")
    reasoning: str = Field(description="Explanation of textual features that led to this classification")

@tool
def analyze_document_text(document_text: str) -> str:
    """Analyze document text content to classify the insurance document."""

    TEXTUAL_ANALYSIS_PROMPT = """You are a Document Analysis Specialist for insurance documents.
    Analyze the provided document text and classify it into exactly one category:
    - POLICY: Insurance policies, endorsements, declarations, coverage documents
    - AFFIDAVIT: Sworn statements, notarized documents, legal declarations, regulatory filings
    - MISCELLANEOUS: Any document that doesn't clearly fit the above categories

    Provide your classification with a confidence score (0.0-1.0) and detailed reasoning
    explaining what textual features led to your decision."""

    text_agent = Agent(
        model=create_bedrock_model(),
        system_prompt=TEXTUAL_ANALYSIS_PROMPT,
        conversation_manager=NullConversationManager(),
    )

    result = text_agent(
        f"Classify this document:\n\n{document_text}",
        structured_output_model=TextualAnalysisOutput,
    )
    return str(result.structured_output)
```

### 步骤 3：构建 Vector Similarity Search Agent

Vector Similarity Search Agent 使用 Amazon Titan Multimodal Embeddings 分析文档版式与视觉特征。

```
# Load FAISS index once at module level.
# allow_dangerous_deserialization=True is required because FAISS uses pickle internally;
# safe here since we created the index ourselves from our own training documents.
db = FAISS.load_local("hybrid_docs.vdb", embeddings=embeddings,
                      allow_dangerous_deserialization=True)

VECTOR_ANALYSIS_PROMPT = """You are a Vector Similarity Search Specialist.
Analyze the similarity search results and determine the document classification.
Consider the confidence scores and consistency of matches across pages."""


@tool
def analyze_document_vectors(pdf_path: str) -> str:
    """Classify document using vector similarity search with agentic reasoning."""
    base64_pages = pdf_to_base64(pdf_path)
    first_embedding = create_multimodal_embedding(image_base64=base64_pages[0])
    results = db.similarity_search_by_vector(embedding=first_embedding, k=3)

    labels = [r.metadata["label"] for r in results]
    classification = Counter(labels).most_common(1)[0][0]
    confidence = labels.count(classification) / len(labels)

    vector_agent = Agent(
        model=create_bedrock_model(),
        system_prompt=VECTOR_ANALYSIS_PROMPT,
        conversation_manager=NullConversationManager(),
    )

    result = vector_agent(
        f"Vector search results for {pdf_path}:\n"
        f"Top match: {classification} (confidence: {confidence:.2f})\n"
        f"All matches: {labels}\n"
        f"Provide final classification with reasoning.",
        structured_output_model=VectorAnalysisOutput,
    )
    return str(result.structured_output)
```

该 agent 使用 `perform_vector_classification` 执行 FAISS 向量相似度搜索，把文档与存储在向量数据库中的预训练视觉模式进行匹配。

### 步骤 4：实现 Validation Agent

Validation Agent 使用 agents as tools 模式来协调各个专家 agent。

```
class OrchestratorOutput(BaseModel):
    """Structured output for the validation orchestrator."""
    textual_analysis: str = Field(description="Textual agent classification: POLICY, AFFIDAVIT, or MISCELLANEOUS")
    textual_confidence: float = Field(description="Textual agent confidence 0.0-1.0")
    vector_analysis: str = Field(description="Vector agent classification: POLICY, AFFIDAVIT, or MISCELLANEOUS")
    vector_confidence: float = Field(description="Vector agent confidence 0.0-1.0")
    final_classification: str = Field(description="Final validated classification")
    confidence: float = Field(description="Overall confidence score")
    requires_human_review: bool = Field(description="Whether edge case needs human review")
    decision_logic: str = Field(description="Brief explanation of decision")
    justification: str = Field(description="Detailed reasoning from both specialists")


class MultiAgentDocumentClassifier:
    def __init__(self, model=None):
        self.model = model or create_bedrock_model()

        self.orchestrator = Agent(
            model=self.model,
            tools=[analyze_document_text, analyze_document_vectors],
            system_prompt="""You are a Document Classification Orchestrator.

Your workflow:
1. Use analyze_document_text for textual analysis
2. Use analyze_document_vectors for visual similarity analysis
3. Synthesize both into a final classification

Reasoning guidelines:
- Both agree → high confidence (0.85-0.95)
- Disagree → textual is more reliable for content-rich docs, vector for visually distinctive formats
- Very short text (<50 chars) or low textual confidence (<0.3) → defer to vector analysis
- Endorsements are POLICY documents
- Flag for human review when evidence is contradictory

Always use both tools before deciding."""
        )
```

Validation Agent 交叉核对两个专家 agent 的结果，以保证质量与一致性。

### 步骤 5：对文档进行分类

组件就位之后，`MultiAgentDocumentClassifier` 端到端处理一个文档的过程如下：

```
    # Method of MultiAgentDocumentClassifier
    def classify_document(self, pdf_path: str) -> OrchestratorOutput:
        """Classify a document using multi-agent orchestration."""
        filename = os.path.basename(pdf_path)
        text_content = extract_pdf_text(pdf_path, max_chars=3000)

        query = f"""Classify this insurance document: {filename}

Document text content (first 3000 characters):
{text_content}

Document file path for vector analysis: {pdf_path}

Use both analyze_document_text and analyze_document_vectors, then synthesize."""

        result = self.orchestrator(query, structured_output_model=OrchestratorOutput)
        return result.structured_output
```

要使用该分类器：

```
classifier = MultiAgentDocumentClassifier()

result = classifier.classify_document("documents/sample_policy.pdf")
print(f"Classification: {result.final_classification}")
print(f"Confidence: {result.confidence:.2f}")
print(f"Reasoning: {result.justification}")
```

系统让每个文档经过各个专家 agent 处理，把它们的分析综合成一份带有完整推理的最终分类结果。

## 理解结果

### 模型选择

针对这一工作负载，我们选择 Amazon Bedrock 上的 Claude Haiku 4.5 作为推理模型。Haiku 4.5 满足了我们的准确率要求，同时带来更低的延迟与成本，单份文档分类平均耗时 19.3 秒，置信度 93%。这使它非常适合那些把速度和成本效率放在优先位置、同时又不牺牲正确性的生产工作负载。

### 常见方案对比

我们把这套多 agent 系统与三种常用的 AWS 方案做了基准对比。目标很直接：找出在合规敏感的工作负载上能满足准确率要求的最简单方案。

Amazon Textract 与 Amazon Comprehend 是为文本抽取和实体识别专门构建的，它们在这些任务上表现优异。然而，它们并非为多类别文档分类而设计——在这种场景下，文档之间共享大量重叠的法律术语。在我们的测试集上，两者都只达到 25% 的准确率。Amazon Bedrock Data Automation（BDA）表现明显更好，达到 70%，能正确处理大多数宣誓书和杂项文档，但总体上仍然把近三分之一的文档分错。多 agent 系统是唯一在所有文档类别上都达到 100% 准确率的方法。

|  | **方案** | **准确率** | **平均耗时** | **复杂度** | **成本** |
| --- | --- | --- | --- | --- | --- |
| 1 | Amazon Textract + Keywords | 25% | 2.88s | 低 | 低 |
| 2 | Amazon Comprehend + Entities | 25% | 3.26s | 中 | 低 |
| 3 | Amazon Bedrock Data Automation | 70% | 25.7s | 中 | 中 |
| 4 | Multi-Agent System | 100% | 23.3s | 高 | 中 |

### 按类别与方案看准确率

准确率的差距在保单类文档上最为明显：密集的法律文本，其术语与其他文档类别高度重叠。只有多 agent 系统把这些文档全部分对。宣誓书呈现类似的规律：BDA 处理得很好，但 Amazon Textract 和 Amazon Comprehend 无法把它们与相邻的法律文档类型区分开。杂项文档含有独特的结构标记，因此所有方案都分类正确。

|  | **类别** | **数量** | **Amazon Textract** | **Amazon Comprehend** | **BDA** | **Multi-Agent** |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Policy | 8 | 25% | 25% | 25% | 100% |
| 2 | Affidavit | 10 | 10% | 10% | 100% | 100% |
| 3 | Miscellaneous | 2 | 100% | 100% | 100% | 100% |

在我们这次评估范围为 20 份文档、3 个类别的有限测试中，多 agent 系统达到 100% 的准确率，比次优方案（BDA 的 70%）高出 30 个百分点。生产环境的准确率可能会随更大、更多样的文档集而变化。Amazon Textract 和 Amazon Comprehend 分别专为文本抽取和实体识别而构建，并在这些任务上表现出色。然而，它们并非为细致区分的多类别文档分类而设计——在这种场景下，文档之间共享重叠的术语。这些结果反映的是未做微调、也未使用自定义分类逻辑的初次运行。通过额外配置，特定用例的准确率还可以进一步提升。

多 agent 系统用处理时间（每份文档约 23 秒）换取显著更高的准确率，这使它非常适合那些分类错误会带来合规或财务风险的用例。在多 agent 框架内，Claude Haiku 4.5 的准确率与 Claude Sonnet 4.5 相当，而运行速度快 17%。这使它在更低延迟与成本下成为生产工作负载的更优选择。

### 生产环境防护措施

[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 为模型交互提供内容过滤和安全控制。可配置的策略支持拒绝话题、内容过滤器、词语过滤器和敏感信息脱敏，以便在应用层负责任地部署 AI。对于处理敏感保险文档的文档分类 pipeline，必须有明确的控制措施，确保输出保持准确、得体且可审计。缺少这些控制，分类 pipeline 可能产出幻觉出来的类别、在日志或下游系统中泄露敏感数据，或者做出自信却错误的决策从而违反合规要求。

在部署这套多 agent 分类系统时，我们推荐以下最佳实践：

- 应用个人可识别信息（PII）脱敏过滤器，帮助防止投保人信息流入分类日志。
- 配置拒绝话题策略，把 agent 限制在其分类范围内。
- 开启 Amazon Bedrock 模型调用日志，以捕捉完整的请求-响应链路（包括 guardrail 干预事件），用于审计。

在我们的方案中，Validation Agent 的 `requires_human_review` 标志会在置信度低于既定阈值时触发自动升级。这确保不确定的分类会交给人工复核，而不是继续向下游传播。

## 结论

本文演示了如何通过 Amazon Bedrock 基础模型与 Strands Agents SDK 构建多 agent 工作流，来提升文档分类准确率。通过编排三个专职 AI agent，你可以获得更准确的分类结果，兼具文本分析与视觉分析的优势。该方案由一个由 Anthropic 的 Claude Haiku 4.5 驱动的 Document Analysis Agent、一个使用 Amazon Titan Multimodal Embeddings 的 Vector Similarity Search Agent，以及一个负责质量保证的 Validation Agent 组成。

相比传统的单模型分类系统，这一多 agent 方法有几个优势。专职 agent 在各自的专长领域内自主工作，然后通过 Orchestrator 协作，交付既准确又可解释的结果。你可以先从用你自己的文档类型实现 Document Analysis Agent 开始，然后加入 Vector Similarity Search Agent 来提升在视觉上具有区分度的文档上的准确率。尝试不同的人工复核置信度阈值，以在自动化与质量保证之间取得平衡。
