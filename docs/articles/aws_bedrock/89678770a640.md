# 通过 Amazon SageMaker AI 中的跨区域推理路由，在区域容量不足的情况下保持推理运行

从多个 AWS 区域提供模型是一种行之有效的高可用推理模式：当一个区域的 GPU 容量不足时，请求会转移到另一个区域。该模式描述简单，操作困难。到目前为止，如果您在 Amazon SageMaker AI 托管终端节点上提供模型，则跨区域路由仍然需要您自己构建。

今天，我们在 Amazon SageMaker AI 中引入跨区域推理路由。它使用一种新资源，即推理路由器，为您的应用程序提供一个跨您已在一个或多个 AWS 区域和 AWS 账户中运行的终端节点和推理组件的调用路径。您注册为模型提供服务的目标，并且您的应用程序调用路由器而不是特定端点。当本地目标健康时，路由器将请求保留在自己的区域中，当本地目标健康时，将新请求转移到另一个注册的目标，并在恢复后逐渐返回流量。

在这篇文章中，我们将解释跨区域推理路由如何决定每个请求的运行位置，演练两个区域中一个模型的示例，并涵盖监控、限制和支付费用。对于服务多个模型的跨账户部署，请参阅[Salesforce 如何通过 Amazon SageMaker AI 中的跨区域推理路由推进全球规模模型服务](https://aws.amazon.com/blogs/machine-learning/how-salesforce-is-advancing-global-scale-model-serving-with-cross-region-inference-routing-in-amazon-sagemaker-ai/)。

## 当一个区域容量不足时

SageMaker AI 终端节点在一个 AWS 区域和一个账户中运行。当自动扩展无法添加端点所需类型的实例时，即使同一模型在另一个区域有空闲容量，也会请求限制并超时。要使用该容量，您的应用程序必须检测陷入困境的端点并切换区域，确定哪些错误可以安全地重试而无需运行模型两次，在恢复后将流量移回而不发生波动，并管理对其他帐户中端点的访问。该代码位于每个请求的关键路径上，跨区域提供模型服务的每个团队都维护自己的版本。

## 跨区域推理路由的工作原理

跨区域推理路由基于以下几个核心思想：

- **您决定模型可能在哪里运行 –** 对于每个模型，您选择路由器可能使用哪些端点和推理组件。
- **SageMaker AI 决定哪个目的地服务每个请求 –** 路由器更喜欢自己的区域，并且仅当本地无法可靠服务时才将新请求转移到另一个目的地。
- **您的端点保持不变 –** 您可以像现在一样部署端点，并使用相同的模型、配置、实例池和自动扩展。直接 `InvokeEndpoint` 调用继续工作，并且路由器传递 `InferenceId` 和 `CustomAttributes`，就像 `InvokeEndpoint` 一样。
- **您可以看到每个决定 –** 每个实时响应都会告诉您哪个目的地满足了请求以及原因。

一些术语描述了这些作品：

- **推理路由器** – 您的帐户中应用程序调用的区域 SageMaker AI 资源。
- **路由目标** – 路由器上一个逻辑模型的名称，例如 `fraud-model`。路由器可以容纳许多路由目标，并且每个目标的故障转移独立于其他目标。
- **目的地** – 在路由目标下注册的实时终端节点、推理组件或异步终端节点，由其完整的 Amazon 资源名称 (ARN) 标识，该名称告诉路由器其区域和账户。路由目标可以包含实时目的地（可以跨区域和帐户混合端点和推理组件），也可以仅包含异步端点。
- **本地目的地** – 路由器区域中的目的地，在健康状况良好时首选。
- **路由原因** – 每个实时响应返回的值，解释请求的去向和原因。

您在其中创建路由器的区域是其本地区域。要选择不同的区域，请在那里创建一个路由器。路由器不会创建容量、扩展端点、部署模型或复制模型工件和容器映像。每个目标必须已在其区域中运行。

### 路由决策是如何做出的

路由器仅考虑在路由目标上注册且有权调用的目的地。其中，它更喜欢自己区域内的目的地，并且当多个本地目的地运行良好时，它会在这些目的地之间平均分配请求。仅当本地目的地无法可靠地提供服务时，请求才会离开该区域。为了检测这一点，SageMaker AI 根据每个目的地最近的请求计算健康状况评分（在目的地自己的区域中进行测量）。服务器错误 (5xx)、限制和超时会降低分数。来自 SageMaker AI 平台的错误（例如，运行状况检查失败）使该值降低得最多。请求本身引起的错误（例如无效输入）不会降低它，因为相同的请求在任何区域都会失败。模型延迟不是输入，因此持续返回成功响应的端点会保持其流量。实例启动失败或端点运行的实例少于其自动缩放目标等信号会使路由器做出更快的反应，但前提是目标开始失败请求之后。

路由器评估每个目标的运行状况并将其作为三种状态之一发布到 Amazon CloudWatch。 `healthy` 目的地服务正常。 `overloaded` 目的地仍在服务，并且路由器将其部分流量移走。 `degraded` 目的地发生故障或无法提供服务，因此路由器将其大部分流量移走并保留一小部分流量以检测恢复情况。

图 2：每个目标健康状态如何改变路由器发送给它的流量

SageMaker AI 管理故障转移阈值和时间，因此您无需调整任何阈值。如果远程目标的运行状况信息过时，路由器会将流量保留在自己的区域中，因此监控间隙永远不会自行移动流量。

### 流量何时移动以及何时返回

失败的请求越多，移动的流量就越多，因此目的地不必首先完全失败。在持续错误发生后大约一分钟内，交通开始移动，对于交通量很少的目的地，则需要更长的时间。离开本地区域的流量按照其健康状况按比例分布到健康的远程目的地。您无法设置权重或后备订单。恢复后，流量会在几分钟内恢复，速度比离开时要慢。正在进行的请求不会被中断。

当目标在未运行模型的情况下未能满足实时请求时，路由器会在不同的目标上重试该请求一次。例如，这包括限制、503 错误、模型未准备好、跨区域流量上限拒绝或目的地拒绝访问。路由器绝不会重试超时、500 错误或模型错误。

对于异步请求，路由器会尝试每个符合条件的目标一次，首先是本地目标，直到接受该请求。

## 你可以路由什么

以下用例展示了在 Amazon SageMaker AI 中使用跨区域推理路由的常见方法。

- **当一个区域 GPU 容量不足时继续提供服务。** 当您的 G 系列实例类型在美国东部（俄亥俄）流量高峰期间出现短缺并且请求开始受到限制时，路由器会将新请求转移到美国西部（俄勒冈）的同一型号，其中自动扩展会吸收溢出，并在美国东部（俄亥俄）恢复后逐渐将流量移回。
- **跨不同 AWS 账户拥有的终端节点进行路由。** 当中央平台账户拥有路由器而其他账户拥有终端节点时，每个终端节点所有者都会授予对一个指定路由器的访问权限，并且请求仅通过该路由器到达这些终端节点。我们将在此列表之后介绍设置。
- **从一个路由器为多个模型提供服务。** 创建一个路由器，每个模型具有一个路由目标，每个路由器都列出该模型的目的地，并在每个请求上传递路由目标名称。每个模型独立进行故障转移。
- **将路由器放在您自己的网关后面。** 如果您操作 API 或模型网关，您可以将其 SageMaker AI 集成指向路由器，以便 SageMaker AI 处理 SageMaker 托管模型的区域选择，而您的网关则决定何时使用不同的提供商。例如，请参阅 [Salesforce 帖子](https://aws.amazon.com/blogs/machine-learning/how-salesforce-is-advancing-global-scale-model-serving-with-cross-region-inference-routing-in-amazon-sagemaker-ai/)。
- **路由异步请求。** 路由器帐户或其他帐户中的异步端点可以是目的地。您的应用程序使用路由目标名称和 Amazon Simple Storage Service (Amazon S3) 输入位置调用 `InvokeInferenceRouterAsync`，并返回 `InferenceId` 以及输出和故障位置，与 `InvokeEndpointAsync` 一样。
- **保护接收端点免受其他区域的溢出。** 在实时端点上，您可以设置可选的跨区域流量上限，以便来自其他区域的请求只能使用其部分容量。您端点的本地呼叫者保留其余部分。我们将在本节后面介绍详细信息。

当目标属于与路由器不同的帐户时，两个帐户都必须允许每个请求。在端点一侧，所有者附加一个基于资源的策略，允许路由器帐户调用端点，并且 `sagemaker:SourceInferenceRouterArn` 条件键限制对一个指定路由器的访问。以下策略仅允许账户 444455556666 中的 `my-router` 调用终端节点。它的第二条语句没有路由器条件，并让路由器帐户读取端点的状态。如果没有该声明，目的地将显示其状态为未知。
```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowOneRouter",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::444455556666:root"},
      "Action": ["sagemaker:InvokeEndpoint", "sagemaker:InvokeEndpointAsync"],
      "Resource": "arn:aws:sagemaker:us-west-2:111122223333:endpoint/my-endpoint",
      "Condition": {"ArnEquals": {
        "sagemaker:SourceInferenceRouterArn": "arn:aws:sagemaker:us-east-2:444455556666:inference-router/my-router"}}
    },
    {
      "Sid": "AllowStatusVisibility",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::444455556666:root"},
      "Action": "sagemaker:DescribeEndpoint",
      "Resource": "arn:aws:sagemaker:us-west-2:111122223333:endpoint/my-endpoint"
    }
  ]
}
```
在路由器帐户中，呼叫者在路由器上需要 `sagemaker:InvokeInferenceRouter`（或 `sagemaker:InvokeInferenceRouterAsync`），在每个目的地上需要 `sagemaker:InvokeEndpoint`（或 `sagemaker:InvokeEndpointAsync`），因为路由器代表呼叫者调用每个目的地。路由器永远不会让调用者访问他们无法直接调用的端点。为了让 `DescribeInferenceRouter` 报告每个目标的状态，调用者还需要端点上的 `sagemaker:DescribeEndpoint` 和推理组件上的 `sagemaker:DescribeInferenceComponent`。其他帐户中的应用程序通过承担路由器帐户中的角色来调用路由器。有关演练，请参阅 [Salesforce 如何在 Amazon SageMaker AI 中通过跨区域推理路由推进全球规模模型服务](https://aws.amazon.com/blogs/machine-learning/how-salesforce-is-advancing-global-scale-model-serving-with-cross-region-inference-routing-in-amazon-sagemaker-ai/) 和 [跨账户目标用户指南](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-router-cross-account.html)。

### 使用跨区域流量上限保护接收端点

当路由器将请求移出容量不足的区域时，这些请求会到达已经为其自己区域的调用者提供服务的端点。默认情况下，接收端点接受任意数量的跨区域流量，因此溢出激增可能会导致其受到限制。通过跨区域流量上限，终端节点所有者可以决定其他区域可以使用多少终端节点容量。

您可以使用 `CrossRegionTrafficConfig` 设置 `CreateEndpointConfig` 中的上限，它采用两个必需的值。 `MaxInvocationsPerSecondPerInstance` 是一个实例每秒可以执行的调用次数，您可以通过模型、实例类型和典型负载的负载测试来测量该调用次数。 `MaxCrossRegionPercentPerEndpoint` 是其他区域可能使用的容量份额。 SageMaker AI 将每个实例的费率乘以服务中的实例并应用百分比，因此上限遵循自动扩展。例如，如果每个实例每秒 50 次调用，上限为 20%，并且有 4 个实例处于服务状态，则终端节点每秒最多接受来自其他区域的 40 个请求。当自动扩展添加 2 个实例时，上限将升至每秒 60 个请求。
```
sm = boto3.client("sagemaker", region_name="us-west-2")
sm.create_endpoint_config(
    EndpointConfigName="my-model-config-us-west-2",
    ProductionVariants=[...],  # your existing variants, unchanged
    CrossRegionTrafficConfig={
        "MaxInvocationsPerSecondPerInstance": 50,
        "MaxCrossRegionPercentPerEndpoint": 20,
    },
)
```
只有来自其他区域的请求才会计入上限。来自端点自己区域的请求，包括直接 `InvokeEndpoint` 调用和来自同一区域中的路由器的调用，永远不会受到它的限制。当跨区域请求超过上限时，终端节点会在模型运行之前拒绝额外的请求，并且路由器会在不同的目标上重试每个请求一次。如果没有其他目的地可以接受该请求，您的应用程序将收到限制错误。

该上限适用于实时端点，端点上的所有推理组件都共享该上限。对于托管推理组件的端点，使用推理组件和有效负载的通常组合对一个实例进行负载测试，以测量 `MaxInvocationsPerSecondPerInstance`，并在该组合或有效负载发生变化时再次运行测试。如果您省略 `CrossRegionTrafficConfig`，终端节点将接受任意数量的跨区域流量。

## 开始使用：一个模型在两个区域

在此示例中，我们在美国东部（俄亥俄）和美国西部（俄勒冈）的一个账户中部署带有 vLLM 容器的 Qwen3-4B 作为推理组件。由于推理路由器不支持响应流，因此应用程序发送非流请求，并且每个请求必须在大约一分钟内完成，与 `InvokeEndpoint` 的限制相同。然后，我们在美国东部（俄亥俄州）创建一台路由器，其中一个路由目标列出了两者：
```
sm = boto3.client("sagemaker", region_name="us-east-2")
rt = boto3.client("sagemaker-inference-router-runtime", region_name="us-east-2")

sm.create_inference_router(
    InferenceRouterName="my-router",
    RoutingTargets=[{
        "Name": "my-model",
        "Destinations": [
            {"ResourceArn": "arn:aws:sagemaker:us-east-2:111122223333:inference-component/ic-us-east-2"},
            {"ResourceArn": "arn:aws:sagemaker:us-west-2:111122223333:inference-component/ic-us-west-2"},
        ],
    }],
)
```
在发送流量之前，运行 `DescribeInferenceRouter` 并确认每个目的地的 `RoutingStatus` 是 `Routable`。

应用程序使用路由目标名称和将发送到 `InvokeEndpoint` 的相同有效负载调用路由器，并从响应中读取服务目的地和路由原因：
```
resp = rt.invoke_inference_router(
    InferenceRouterName="my-router",
    RoutingTargetName="my-model",
    ContentType="application/json",
    Body=json.dumps({"messages": [{"role": "user", "content": "Who are you?"}]}),
)
print("Served by:", resp["InvokedRoutedResourceArn"])
print("Reason:   ", resp["RoutingReason"])
```
### 我们观察到的情况

| **步骤** | **`DescribeInferenceRouter` 中的 `RoutingStatus` (us-east-2 / us-west-2)** | **服务者** | **路由原因** |
| --- | --- | --- | --- |
|两个推理组件都在运行 | `Routable` / `Routable` |美国东2 | `local-preferred` |
| us-east-2 推理组件已删除 | `Unroutable` / `Routable` |美国西2 | `only-healthy` |
| us-east-2 推理组件已恢复 | `Routable` / `Routable` |美国西2 | `only-healthy` |
| us-east-2 的流量返回 | `Routable` / `Routable` |美国东2 | `local-preferred` |

当推理组件运行时，流量留在美国东部（俄亥俄州），当我们删除它时，流量移至美国西部（俄勒冈州），应用程序没有任何变化，并在我们恢复它后返回。

此示例的完整[笔记本](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/03-features/inference-router) 可在 GitHub 上找到。

**提示：**将实例池和跨区域推理路由一起使用。借助容量感知实例池，SageMaker AI 可以在创建和横向扩展期间使用同一区域中的其他实例类型。当整个本地端点无法提供服务时，路由器会将新请求移动到另一个区域。有关详细信息，请参阅[容量感知推理：SageMaker AI 端点的自动实例回退](https://aws.amazon.com/blogs/machine-learning/capacity-aware-inference-automatic-instance-fallback-for-sagemaker-ai-endpoints/)。

## 查看每个请求去了哪里

推理路由器为您提供两种路由视图：每个实时响应的记录和 CloudWatch 中的指标。

### 每个请求的路由记录

每个实时响应都包含 `InvokedRoutedResourceArn` 中为请求提供服务的目的地的 ARN，以及 `RoutingReason` 中的路由原因。路由原因是以下之一：

- `local-preferred` – 由路由器区域中的健康目的地提供服务。
- `capacity-available` – 由具有可用容量的目的地提供服务。
- `failover` – 离开无法可靠服务的目的地。
- `only-healthy` – 由唯一符合条件且健康的目的地提供服务。

我们建议使用应用程序自己的请求日志记录这两个值。

异步响应不包括服务目的地。 CloudWatch 中的路由器指标显示异步请求的放置位置。

### CloudWatch 中的路由器指标

路由器将 OpenTelemetry 指标发布到其自己的账户和区域中的 CloudWatch，并标有路由器、路由目标和目的地：

- `aws.sagemaker.inference_router.invocations` – 每个目的地的请求，失败时带有 `error.type` 标签（`invocation_4xx`、`invocation_5xx` 或 `invocation_model_error`）。
- `aws.sagemaker.inference_router.destination.duration` – 到达目的地的时间，包括您的型号。
- `aws.sagemaker.inference_router.overhead.duration` – 路由器自身的工作加上往返另一个区域的网络时间。
- `aws.sagemaker.inference_router.destination.status` – 每个目的地为 `healthy`、`overloaded` 或 `degraded`。

对不健康的目的地以及所有错误类型的错误率发出警报。请参阅[使用 Amazon CloudWatch 和 AWS CloudTrail 监控推理路由器](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-router-monitor.html)。

每个目标端点不断在自己的账户和区域中发布其现有的 SageMaker AI 指标。要在一处查看它们，请使用 CloudWatch 跨账户可观察性和跨账户跨区域控制面板。

AWS CloudTrail 将路由器的 API 调用（创建、更新、删除、描述和列出）记录为管理事件，将路由器调用记录为数据事件。您可以像启用其他 SageMaker AI 数据事件一样启用跟踪中的数据事件。

## 规划您的部署

使用推理路由器进行设计时，请记住以下几点：

- **将路由器放在大部分流量来源的区域中。** 路由器始终优先选择其自己区域中的目的地。
- **根据每个区域自身的流量以及您希望其吸收的溢出来调整每个区域的大小。** 默认情况下，接收端点接受任意数量的跨区域流量，因此请为您期望的溢出配置自动缩放和余量。为了保护终端的本地呼叫者，请设置跨区域流量上限，如[使用跨区域流量上限保护接收终端](https://aws.amazon.com/blogs/machine-learning/keep-inference-running-through-regional-capacity-shortfalls-with-cross-region-inference-routing-in-amazon-sagemaker-ai/#protect-a-receiving-endpoint-with-a-cross-region-traffic-cap)中所述。如果每个远程目标都达到其上限，则超出组合上限的请求将返回限制错误。
- **保留低成本备用区域。** 您可以在另一个区域注册推理组件并保持其低成本，但要规划它如何获得容量。具有零副本的远程推理组件在故障转移期间仅接收一小部分流量，并且这些请求会失败，直到它有副本为止。保持至少一个副本运行，或者在副本上配置自动缩放并确认其在依赖备用区域之前进行横向扩展。
- **规划入口点的弹性。** 路由器是区域性的，因此如果其区域受损，对其的调用就会失败。在两个区域创建路由器并在客户端在它们之间切换。
- **仅注册可能处理您的数据的目标。** 可以在路由器的区域或您注册了目标的任何区域中处理请求。对于必须保留在一个地理位置的数据，请使用单独的路由器，例如一个用于美国数据，一个用于欧盟数据。您负责配置路由器以符合您的数据驻留和合规性义务。
- **保持自己的重试适度。** 限制错误意味着每个目的地都很忙，而服务不可用错误意味着没有目的地可以接受请求。大约一分钟后出现服务不可用错误意味着请求超时并且模型可能已运行，因此不要自动重试。
- **从路由器中删除已删除的目的地。** 流量已避开已删除的端点，但路由器永远不会自行删除目的地。
- **私下调用路由器。** Virtual Private Cloud (VPC) 中的应用程序可以通过接口 VPC 终端节点 (AWS PrivateLink) 调用路由器，该终端节点支持 IPv4（不支持 IPv6/双栈）。

另请注意以下限制：

- 不支持响应流。
- 目标在大约一分钟内未响应的实时请求会失败，并出现服务不可用错误。
- 每个路由器最多可容纳 20 个路由目标，每个路由目标最多可容纳 10 个目的地，实时负载可达 6 MB。有关默认配额（例如每个账户的路由器和请求率）以及如何请求增加配额，请参阅 [Amazon SageMaker AI 文档中的服务配额](https://docs.aws.amazon.com/general/latest/gr/sagemaker.html#limits_sagemaker)

## 结论

Amazon SageMaker AI 中的跨区域推理路由为您的应用程序提供了一种跨多个 AWS 区域和 AWS 账户中已运行的终端节点和推理组件的调用路径。路由器更喜欢自己的区域，当目的地无法可靠服务时转移新请求，恢复后逐渐返回流量，并向您显示每个请求运行的位置及其原因。您的端点、模型、容器和自动扩展策略不会改变。

从今天开始，跨区域推理路由在大多数商业 AWS 区域（me-south-1 和 me-central-1 除外）普遍可用，用于实时和异步推理。

Amazon SageMaker AI 中的跨区域推理路由不收取额外费用。您可以按照标准 SageMaker AI 定价为 SageMaker AI 端点和推理组件付费，无论请求是直接到达还是通过推理路由器到达它们，它们都能满足您的请求。推理路由器将指标发布到路由器账户中的 Amazon CloudWatch，您需要为这些指标以及对它们运行的​​任何查询支付标准 CloudWatch 费率。有关详细信息，请参阅 [Amazon SageMaker AI 定价。](https://aws.amazon.com/sagemaker/ai/pricing/)

要开始使用，请参阅有关跨区域推理路由的 [Amazon SageMaker AI 文档](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-router.html) 并浏览 GitHub 上的示例 [笔记本](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/03-features/inference-router)。
