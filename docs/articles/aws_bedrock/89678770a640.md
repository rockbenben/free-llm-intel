# 通过 Amazon SageMaker AI 中的跨区域推理路由，在区域容量不足的情况下保持推理运行

用多个 AWS 区域共同服务一个模型，是实现高可用推理的成熟做法：某个区域 GPU 容量吃紧时，把请求转到另一个区域。这个模式说起来简单，运维起来很难。在此之前，如果你在 Amazon SageMaker AI 托管 endpoint 上部署模型，跨区域路由这一块仍然得自己搭。

今天我们推出 Amazon SageMaker AI 的跨区域推理路由。它引入一种新资源——inference router，为你的应用在已运行于一个或多个 AWS 区域、AWS 账户中的 endpoint 和 inference component 之上，提供统一的调用路径。你注册为某个模型提供服务的各个 destination，应用改为调用 router，而不是某个具体 endpoint。本地 destination 健康时，router 把请求留在自己所在区域；本地 destination 不健康时，把新请求转到另一个已注册 destination；恢复后再逐步把流量引回。

本文说明跨区域推理路由如何决定每个请求在哪里执行，用一个模型部署在两个区域的示例走一遍流程，并介绍监控、限制和计费。若要了解服务多个模型的跨账户部署，请参阅 [Salesforce 如何借助 Amazon SageMaker AI 的跨区域推理路由推进全球规模模型服务](https://aws.amazon.com/blogs/machine-learning/how-salesforce-is-advancing-global-scale-model-serving-with-cross-region-inference-routing-in-amazon-sagemaker-ai/)。

## 当一个区域容量不足时

一个 SageMaker AI endpoint 只运行在一个 AWS 区域、一个账户中。当自动扩缩容无法添加你的 endpoint 所需类型的实例时，请求会被限流、超时——即便同一个模型在另一个区域还有空闲容量。要用上那部分容量，应用必须自己发现吃力的 endpoint 并切换区域，判断哪些错误可以安全重试而不会让模型跑两遍，在恢复后把流量移回且不来回抖动，还要管理对其他账户中 endpoint 的访问。这段代码位于每个请求的关键路径上，而每个跨区域服务模型的团队都各自维护一份。

## 跨区域推理路由的工作方式

跨区域推理路由建立在几个核心设计上：

- **模型可能在哪里运行，由你决定——** 对每个模型，你选择 router 可以使用哪些 endpoint 和 inference component。
- **每个请求由哪个 destination 服务，由 SageMaker AI 决定——** router 优先使用自己所在区域，只有当本地 destination 无法可靠服务时，才把新请求转到另一个 destination。
- **你的 endpoint 保持原样——** 部署方式与现在一致，模型、配置、instance pool、自动扩缩容都不变。直接调用 `InvokeEndpoint` 依旧可用；router 会像 `InvokeEndpoint` 一样透传 `InferenceId` 和 `CustomAttributes`。
- **每个决策都可见——** 每个实时响应都会告诉你请求由哪个 destination 服务、原因是什么。

几个术语解释各个组成部分：

- **Inference router**——账户中的一个区域级 SageMaker AI 资源，由你的应用调用。
- **Routing target**——router 上一个逻辑模型的名称，例如 `fraud-model`。一个 router 可以承载多个 routing target，各自独立故障转移。
- **Destination**——注册在某个 routing target 下的实时 endpoint、inference component 或异步 endpoint，用完整 Amazon Resource Name（ARN）标识，router 从中得知它所在区域和账户。一个 routing target 要么承载实时 destination（可以混合跨区域、跨账户的 endpoint 与 inference component），要么只承载异步 endpoint。
- **Local destination**——位于 router 所在区域的 destination，健康期间优先使用。
- **Routing reason**——随每个实时响应返回的取值，说明请求去了哪里、为什么。

创建 router 的区域即为其本地区域。若想以别的区域为优先，就在那里创建 router。router 不创建容量、不扩缩你的 endpoint、不部署模型，也不复制模型产物和容器镜像。每个 destination 都必须已在其所在区域运行。

### 路由决策如何做出

router 只考虑注册在该 routing target 上、且自己有权调用的 destination。在这些 destination 中，它优先选择本区域的；若多个本地 destination 都健康，就把请求均匀分摊。只有本地 destination 无法可靠服务时，请求才会离开本区域。为检测这一点，SageMaker AI 根据每个 destination 近期的请求（在 destination 自己所在区域统计）计算健康分。服务端错误（5xx）、限流和超时都会降低分数。来自 SageMaker AI 平台的错误（例如健康检查失败）降分最多。请求本身导致的错误（例如输入非法）不降分，因为同样的请求在任何区域都会失败。模型延迟不参与计算，因此一个持续返回成功响应的 endpoint 会保住自己的流量。实例启动失败、endpoint 运行实例数少于自动扩缩容目标之类的信号能让 router 反应更快，但也要等 destination 开始请求失败之后才起作用。

router 评估每个 destination 的健康状况，并以三种状态之一发布到 Amazon CloudWatch。`healthy` 的 destination 正常服务。`overloaded` 的 destination 仍在服务，但 router 会移走一部分流量。`degraded` 的 destination 已经失败或无法服务，router 会移走大部分流量，只保留一小部分用于探测恢复。

图 2：每种 destination 健康状态如何改变 router 发给它的流量

故障转移的阈值和时序由 SageMaker AI 管理，你无需调参。如果远端 destination 的健康信息过期，router 会把流量留在本区域，因此监控出现空档绝不会自行触发流量迁移。

### 流量何时迁走，何时回来

失败的请求越多，迁走的流量越多，所以 destination 不必先彻底挂掉。持续出错约一分钟内流量就开始迁移；流量很少的 destination 会更久。离开本区域的流量按健康程度成比例分摊到各健康的远端 destination。你无法设置权重或回退顺序。恢复之后，流量在几分钟内逐步回流，回得比走时慢。进行中的请求不会被打断。

当某个 destination 在未运行模型的情况下让一个实时请求失败时，router 会在另一个 destination 上重试该请求一次。这涵盖例如限流、503 错误、模型未就绪、被跨区域流量上限拒绝，或 destination 拒绝访问等情况。router 从不重试超时、500 错误或模型错误。

对于异步请求，router 会依次在每个合格 destination 上尝试一次，先试本地 destination，直到有一个接受为止。

## 可以路由哪些场景

以下场景展示了 Amazon SageMaker AI 跨区域推理路由的常见用法。

- **某个区域 GPU 容量不足时继续服务。** 高峰期你在 US East (Ohio) 的 G 系列实例类型不够用、请求开始被限流时，router 把新请求转到 US West (Oregon) 的同一模型，由那里的自动扩缩容吸收溢出；US East (Ohio) 恢复后再逐步把流量移回。
- **跨不同 AWS 账户拥有的 endpoint 路由。** 中央平台账户持有 router、其他账户持有 endpoint 时，每个 endpoint 所有者只授权给一个指定名称的 router，请求也只能经由该 router 到达这些 endpoint。具体配置在本文列表之后介绍。
- **用一个 router 服务多个模型。** 创建一个 router，为每个模型建一个 routing target，各自列出该模型的 destination，请求时传入 routing target 名称。每个模型独立故障转移。
- **把 router 放在自己的网关之后。** 如果你运营 API 或模型网关，可以让它的 SageMaker AI 集成指向 router，这样 SageMaker 托管的模型由 SageMaker AI 负责选择区域，而何时换用其他供应商由你的网关决定。示例见 [Salesforce 的这篇文章](https://aws.amazon.com/blogs/machine-learning/how-salesforce-is-advancing-global-scale-model-serving-with-cross-region-inference-routing-in-amazon-sagemaker-ai/)。
- **路由异步请求。** router 所在账户或其他账户中的异步 endpoint 都可以作为 destination。应用调用 `InvokeInferenceRouterAsync`，传入 routing target 名称和 Amazon Simple Storage Service（Amazon S3）输入位置，拿回 `InferenceId` 以及输出位置和失败位置，与 `InvokeEndpointAsync` 一致。
- **保护接收方 endpoint 不被其他区域的溢出流量打满。** 在实时 endpoint 上可以设置可选的跨区域流量上限，让来自其他区域的请求只能使用其部分容量，其余留给本区域的调用方。细节在本节后面介绍。

当 destination 与 router 不属于同一账户时，两个账户都必须放行每个请求。在 endpoint 一侧，所有者挂上基于资源的策略，允许 router 账户调用该 endpoint，并用 `sagemaker:SourceInferenceRouterArn` 条件键把访问限定到某一个指定名称的 router。下面的策略只允许账户 444455556666 中的 `my-router` 调用该 endpoint。第二条语句没有 router 条件，用于让 router 账户读取 endpoint 状态；没有这条语句，destination 的状态会显示为未知。

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowOneRouter",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::444455556666:root"},
      "Action": ["sagemaker:InvokeEndpoint", "sagemaker:InvokeEndpointAsync"],
      "Resource": "arn:aws:sagemaker:us-west-2:111122223333:endpoint/my-endpoint",
      "Condition": {"ArnEquals": {
        "sagemaker:SourceInferenceRouterArn": "arn:aws:sagemaker:us-east-2:444455556666:inference-router/my-router"}}
    },
    {
      "Sid": "AllowStatusVisibility",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::444455556666:root"},
      "Action": "sagemaker:DescribeEndpoint",
      "Resource": "arn:aws:sagemaker:us-west-2:111122223333:endpoint/my-endpoint"
    }
  ]
}
```

在 router 账户中，调用方需要拥有 router 上的 `sagemaker:InvokeInferenceRouter`（或 `sagemaker:InvokeInferenceRouterAsync`），以及每个 destination 上的 `sagemaker:InvokeEndpoint`（或 `sagemaker:InvokeEndpointAsync`），因为 router 是代表调用方去调用各个 destination 的。router 绝不会让调用方访问它本来无法直接调用的 endpoint。要让 `DescribeInferenceRouter` 报告每个 destination 的状态，调用方还需要 endpoint 上的 `sagemaker:DescribeEndpoint` 和 inference component 上的 `sagemaker:DescribeInferenceComponent`。其他账户中的应用通过代入 router 账户中的角色来调用 router。完整步骤见 [Salesforce 如何借助 Amazon SageMaker AI 的跨区域推理路由推进全球规模模型服务](https://aws.amazon.com/blogs/machine-learning/how-salesforce-is-advancing-global-scale-model-serving-with-cross-region-inference-routing-in-amazon-sagemaker-ai/) 和 [跨账户 destination 用户指南](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-router-cross-account.html)。

### 用跨区域流量上限保护接收方 endpoint

当 router 把请求从容量不足的区域移走时，这些请求会落在本来就在服务本区域调用方的 endpoint 上。默认情况下，接收方 endpoint 接受任意数量的跨区域流量，因此一阵溢出就可能把它推到限流。设置跨区域流量上限后，由 endpoint 所有者决定其他区域最多能用掉多少容量。

在 `CreateEndpointConfig` 中用 `CrossRegionTrafficConfig` 设置上限，它有两个必填值。`MaxInvocationsPerSecondPerInstance` 是单个实例每秒能承接的调用数，需针对你的模型、实例类型和典型 payload 做压测得出。`MaxCrossRegionPercentPerEndpoint` 是其他区域最多可用的容量占比。SageMaker AI 用单实例速率乘以在服务实例数，再乘以该百分比，因此上限会随自动扩缩容变化。例如单实例每秒 50 次调用、上限 20%、在服务实例 4 个时，endpoint 每秒最多接受来自其他区域的 40 个请求；自动扩缩容增加 2 个实例后，上限升到每秒 60 个请求。

```
sm = boto3.client("sagemaker", region_name="us-west-2")
sm.create_endpoint_config(
    EndpointConfigName="my-model-config-us-west-2",
    ProductionVariants=[...],  # your existing variants, unchanged
    CrossRegionTrafficConfig={
        "MaxInvocationsPerSecondPerInstance": 50,
        "MaxCrossRegionPercentPerEndpoint": 20,
    },
)
```

只有来自其他区域的请求计入上限。来自 endpoint 本区域的请求，包括直接调用 `InvokeEndpoint` 以及同区域 router 发来的调用，永远不会被它限流。跨区域请求超出上限时，endpoint 会在模型运行之前拒掉多出的请求，router 再逐个在另一个 destination 上重试一次。如果没有其他 destination 能接下这个请求，你的应用会收到限流错误。

该上限适用于实时 endpoint，一个 endpoint 上的所有 inference component 共用它。对于承载 inference component 的 endpoint，要用其常规的 inference component 与 payload 组合对单个实例做压测，得出 `MaxInvocationsPerSecondPerInstance`；组合或 payload 变化后需重新压测。如果不填 `CrossRegionTrafficConfig`，endpoint 会接受任意数量的跨区域流量。

## 上手实践：一个模型，两个区域

在这个示例中，我们在同一个账户里，把用 vLLM 容器部署的 Qwen3-4B 作为 inference component 分别部署到 US East (Ohio) 和 US West (Oregon)。由于 inference router 不支持响应流式返回，应用发送的是非流式请求，每个请求必须在约一分钟内完成，与 `InvokeEndpoint` 的限制相同。然后在 US East (Ohio) 创建一个 router，其中只有一个 routing target，列出这两个 destination：

```
sm = boto3.client("sagemaker", region_name="us-east-2")
rt = boto3.client("sagemaker-inference-router-runtime", region_name="us-east-2")

sm.create_inference_router(
    InferenceRouterName="my-router",
    RoutingTargets=[{
        "Name": "my-model",
        "Destinations": [
            {"ResourceArn": "arn:aws:sagemaker:us-east-2:111122223333:inference-component/ic-us-east-2"},
            {"ResourceArn": "arn:aws:sagemaker:us-west-2:111122223333:inference-component/ic-us-west-2"},
        ],
    }],
)
```

发送流量之前，先运行 `DescribeInferenceRouter`，确认每个 destination 的 `RoutingStatus` 都是 `Routable`。

应用调用 router 时传入 routing target 名称，以及本来要发给 `InvokeEndpoint` 的同一份 payload，再从响应中读出服务方 destination 和 routing reason：

```
resp = rt.invoke_inference_router(
    InferenceRouterName="my-router",
    RoutingTargetName="my-model",
    ContentType="application/json",
    Body=json.dumps({"messages": [{"role": "user", "content": "Who are you?"}]}),
)
print("Served by:", resp["InvokedRoutedResourceArn"])
print("Reason:   ", resp["RoutingReason"])
```

### 我们观察到的结果

| **步骤** | **`DescribeInferenceRouter` 中的 `RoutingStatus`（us-east-2 / us-west-2）** | **服务方** | **Routing reason** |
| --- | --- | --- | --- |
| 两个 inference component 均在运行 | `Routable` / `Routable` | us-east-2 | `local-preferred` |
| 移除 us-east-2 的 inference component | `Unroutable` / `Routable` | us-west-2 | `only-healthy` |
| 恢复 us-east-2 的 inference component | `Routable` / `Routable` | us-west-2 | `only-healthy` |
| 流量回到 us-east-2 | `Routable` / `Routable` | us-east-2 | `local-preferred` |

inference component 运行时流量留在 US East (Ohio)；我们移除它后，流量转到 US West (Oregon)，应用侧无需任何改动；恢复后流量又回到原处。

本示例的完整 [notebook](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/03-features/inference-router) 已在 GitHub 上提供。

**提示：** 把 instance pool 与跨区域推理路由一起用。使用容量感知的 instance pool 时，SageMaker AI 可以在创建时和扩容期间改用同区域的另一种实例类型。而当本地 endpoint 整体无法服务时，router 会把新请求转到另一个区域。详情见 [容量感知推理：SageMaker AI endpoint 的自动实例回退](https://aws.amazon.com/blogs/machine-learning/capacity-aware-inference-automatic-instance-fallback-for-sagemaker-ai-endpoints/)。

## 查看每个请求去了哪里

inference router 提供两种路由视图：每个实时响应上的记录，以及 CloudWatch 中的指标。

### 单请求路由记录

每个实时响应都在 `InvokedRoutedResourceArn` 中带上服务该请求的 destination 的 ARN，在 `RoutingReason` 中带上 routing reason。routing reason 为以下之一：

- `local-preferred`——由 router 所在区域的健康 destination 服务。
- `capacity-available`——由仍有可用容量的 destination 服务。
- `failover`——已从无法可靠服务的 destination 迁走。
- `only-healthy`——由唯一健康的合格 destination 服务。

建议把这两个值一并写入应用自己的请求日志。

异步响应不包含服务方 destination。CloudWatch 中的 router 指标可以看到异步请求被放到了哪里。

### CloudWatch 中的 router 指标

router 把 OpenTelemetry 指标发布到其所在账户和区域的 CloudWatch，标签包含 router、routing target 和 destination：

- `aws.sagemaker.inference_router.invocations`——每个 destination 的请求数，失败时带 `error.type` 标签（`invocation_4xx`、`invocation_5xx` 或 `invocation_model_error`）。
- `aws.sagemaker.inference_router.destination.duration`——在 destination 上的耗时，包含你的模型。
- `aws.sagemaker.inference_router.overhead.duration`——router 自身的工作，加上往返另一区域的网络时间。
- `aws.sagemaker.inference_router.destination.status`——每个 destination 的状态，取 `healthy`、`overloaded` 或 `degraded`。

对不健康的 destination 以及所有错误类型的整体错误率设置告警。参见 [使用 Amazon CloudWatch 和 AWS CloudTrail 监控 inference router](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-router-monitor.html)。

## 规划部署

用 inference router 做设计时，请注意以下几点：

- **把 router 放在大部分流量来源的区域。** router 总是优先选择自己所在区域的 destination。
- **为每个区域按其自身流量加上你希望它吸收的溢出量来规划容量。** 默认情况下接收方 endpoint 接受任意数量的跨区域流量，因此配置自动扩缩容时要为预期的溢出留出余量。要保护 endpoint 的本区域调用方，可设置跨区域流量上限，方法见 [用跨区域流量上限保护接收方 endpoint](https://aws.amazon.com/blogs/machine-learning/keep-inference-running-through-regional-capacity-shortfalls-with-cross-region-inference-routing-in-amazon-sagemaker-ai/#protect-a-receiving-endpoint-with-a-cross-region-traffic-cap)。如果所有远端 destination 都达到上限，超出各上限之和的请求会返回限流错误。
- **保留一个低成本的备用区域。** 你可以在另一个区域注册 inference component 并把成本压得很低，但要规划它如何获得容量。副本数为 0 的远端 inference component 在故障转移时只会分到很小一部分流量，而且在它有副本之前这些请求都会失败。请至少保持一个副本运行，或为副本配置自动扩缩容，并在依赖备用区域之前确认它确实能扩容。
- **为入口点规划容灾。** router 是区域级资源，其所在区域受损时对它的调用会失败。请在两个区域各建一个 router，并在客户端侧切换。
- **只注册数据可能被处理的 destination。** 请求可能在 router 所在区域处理，也可能在你注册过 destination 的任何区域处理。对于必须留在某一地理范围内的数据，请使用独立的 router，例如一个处理美国数据、一个处理欧盟数据。你有责任让 router 的配置符合数据驻留与合规要求。
- **自身重试要克制。** 限流错误意味着所有 destination 都忙；服务不可用错误意味着没有 destination 能接下请求。约一分钟后出现的服务不可用错误表示请求已超时、模型可能已经运行过，因此不要自动重试。
- **从 router 中移除已删除的 destination。** 流量本来就会避开已删除的 endpoint，但 router 绝不会自行移除 destination。
- **以私有方式调用 router。** 虚拟私有云（VPC）中的应用可以通过 interface VPC endpoint（AWS PrivateLink）调用 router，支持 IPv4（不支持 IPv6/dual-stack）。

另请注意以下限制：

- 不支持响应流式返回。
- destination 在约一分钟内未响应的实时请求会以服务不可用错误失败。
- 每个 router 最多容纳 20 个 routing target，每个 routing target 最多 10 个 destination，实时 payload 最大 6 MB。每个账户的 router 数量、请求速率等默认配额以及如何申请提升，见 [Amazon SageMaker AI 文档中的 Service Quotas](https://docs.aws.amazon.com/general/latest/gr/sagemaker.html#limits_sagemaker)。

## 结语

Amazon SageMaker AI 的跨区域推理路由，让你在多个 AWS 区域、AWS 账户中已运行的 endpoint 和 inference component 之上，为应用提供统一的调用路径。router 优先本区域，在 destination 无法可靠服务时迁移新请求，恢复后逐步回流，并告诉你每个请求在哪里执行、为什么。你的 endpoint、模型、容器和自动扩缩容策略都无需改动。

跨区域推理路由从今天起在大多数商业 AWS 区域（me-south-1 和 me-central-1 除外）正式可用，支持实时推理与异步推理。

Amazon SageMaker AI 的跨区域推理路由不额外收费。为请求提供服务的 SageMaker AI endpoint 和 inference component 按标准 SageMaker AI 价格计费，无论请求是直接到达还是经 inference router 到达。inference router 会把指标发布到 router 账户下的 Amazon CloudWatch，这些指标以及你对它们发起的查询按标准 CloudWatch 费率计费。详情见 [Amazon SageMaker AI 定价](https://aws.amazon.com/sagemaker/ai/pricing/)。

要开始使用，请参阅 [Amazon SageMaker AI 文档](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-router.html) 中关于跨区域推理路由的部分，并在 GitHub 上查看示例 [notebook](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/03-features/inference-router)。
