## 多臂赌博机在生成式 AI 时代日益增长的角色

[多臂赌博机（MAB）](https://en.wikipedia.org/wiki/Multi-armed_bandit)是一种为多选项、有限流量的环境而打造的强化学习方法。它在继续服务客户的同时学会哪个选项表现最好。它把每个内容变体当作一条“臂”，对每条臂用实时流量尝试，并稳步地把展示转向那些表现好的臂，同时留出一小部分继续测试其余的。这就是利用（服务当前最好的臂）与探索（尝试不确定度更高的臂以收集证据）之间的基本权衡。因为赌博机从不停止两者，它会随新变体的加入而持续改进，也从不必须等一个测试结束。A/B/n 测试仍有一席之地，但随着生成式 AI 加速了需要学习的变体数量，我们预期赌博机会扮演越来越大的角色。

文献中有若干赌博机选择策略：epsilon-greedy、上界置信（UCB）、Thompson 采样等。要更深入地了解这些方法及其在 AWS 上的部署，参见我们更早的文章 [Dynamic A/B testing for machine learning models with Amazon SageMaker MLOps Projects](https://aws.amazon.com/blogs/machine-learning/dynamic-a-b-testing-for-machine-learning-models-with-amazon-sagemaker-mlops-projects/)。

在 Amazon Payments，我们选择 UCB——一种选取估计奖励加不确定度奖励最高的臂的策略，天然地平衡利用与探索。它的确定性选择规则为每一次展示给出一个可审计、可复现的决定，这确保每个服务决定在需要时都能被解释和复现。然而，一个标准赌博机为整个受众学一条最好的臂。个性化要求以访问者是谁为条件，而上下文赌博机正是提供这一点。

### 用上下文赌博机加入上下文

上下文赌博机不问“哪个内容总体最好？”，而是以关于访问的信号为条件做决定。分段赌博机为每个手工定义的组运行一个独立实例，但那些组是任意的，且每个都需要自己的流量。上下文赌博机直接以一个特征向量（属性的数字表示）为条件，因此一个上下文中学到的模式会转移到每个相似的访问，而无需逐组的独立流量。我们的生产系统把每个客户表示为一个行为信号的上下文向量（支付行为、交易组合等特征），而非一个固定细分。实体 ID（一个诸如 `entity_id` 的不透明键）仅用于把学到的推荐路由回正确的访问者。它从不是模型输入。

### LinUCB：在特征级学习

对于上下文方法，我们选择了线性 UCB（LinUCB），由 [Li 等人（2010）](https://arxiv.org/pdf/1003.0146)提出。尽管有较新的赌博机算法存在，LinUCB 仍是一个久经考验的方法：计算高效、可审计（确定性臂选择），并能在有限的预热启动数据下天然处理一个大的臂空间。它的关键假设是一条臂的期望奖励是上下文向量的线性函数，这使它能把学到的东西泛化到它没见过的访问者。

每条臂在每次展示时更新两个累积量：

- **`b`，奖励账本**：哪些访问者信号导致了转化（b += reward · x）。
- **`A`，经验账本**：这条臂见过哪些访问者（A += x·xᵀ，从单位阵开始）。

用奖励除以经验得到估计（θ = A⁻¹·b）。经验账本还在证据增长时收缩探索奖励。臂的分数是：

```
score(a, x) = θᵀ·x + α · √(xᵀ · A⁻¹ · x)
              \_____/   \________________/
               estimate   uncertainty bonus
```

这个奖励是上下文相关的。它对一条臂很少见到的那种访问者很大，对它常见的那种很小。一个普通赌博机以单一的全局速率探索，而 LinUCB 为它评分的每个访问者调整探索多少。

## 优化整个漏斗

我们用例中的客户旅程包含三个步骤：申请开始、提交和批准。因此目标是一个多阶段的结果，而非单一指标。这些阶段并不齐步走。为开始而优化的内容往往吸引广泛受众，而批准取决于那个报价是否真正适合申请人。孤立地优化一个阶段可能使另一个退化。我们把这称为跷跷板问题。相反，只为批准优化会让模型信号匮乏，因为批准稀少且滞后。

我们的方法通过为每个阶段（start、submit、approve）各运行一个 LinUCB 模型、并通过一个线性组合把它们的 UCB 分数结合起来，从而同时优化整个漏斗：

```
selected_arm = argmax_a [ w_start   · UCB_start(a, x)
                        + w_submit  · UCB_submit(a, x)
                        + w_approve · UCB_approve(a, x) ]
```

阶段权重可以基于业务优先级来指派，或由一个单独的校准步骤学出。我们用了大致相等的权重。在实践中，一旦模型预热好可以对批准加更重的权重，或在权衡真有争议时使用帕累托前沿。

下面是模型在 Python 中的核心。每个 LinUCBDisjoint 为每条臂维护独立的参数，而 MultiObjectiveLinUCB 组合其中三个：

```
import numpy as np


class LinUCBDisjoint:
    """LinUCB with disjoint (independent) parameters per arm.
    Each arm maintains its own reward and experience matrices."""

    def __init__(self, n_arms, n_features, alpha=1.0):
        self.n_arms = n_arms
        self.n_features = n_features
        self.alpha = alpha  # exploration-exploitation trade-off parameter
        # A: experience matrix (d x d); b: reward vector (d) - one per arm
        self.A = [np.eye(n_features) for _ in range(n_arms)]
        self.b = [np.zeros(n_features) for _ in range(n_arms)]

    def update(self, arm, context, reward):
        """Exact, incremental update - no retraining needed."""
        self.A[arm] += np.outer(context, context)
        self.b[arm] += reward * context


class MultiObjectiveLinUCB:
    """Combines one LinUCB per funnel stage via weighted sum."""

    def __init__(self, n_arms, n_features, alpha=1.0,
                 weights=(1/3, 1/3, 1/3)):  # stage weights (start, submit, approve)
        self.n_arms = n_arms
        self.alpha = alpha
        self.weights = weights  # [start, submit, approve]
        self.app_start_bandit = LinUCBDisjoint(n_arms, n_features, alpha)
        self.app_submit_bandit = LinUCBDisjoint(n_arms, n_features, alpha)
        self.app_approved_bandit = LinUCBDisjoint(n_arms, n_features, alpha)

    def select_arm(self, context):
        combined = []
        for a in range(self.n_arms):
            score = 0.0
            for w, bandit in zip(
                self.weights,
                [self.app_start_bandit,
                 self.app_submit_bandit,
                 self.app_approved_bandit],
            ):
                A_inv = np.linalg.inv(bandit.A[a])
                theta = A_inv @ bandit.b[a]
                ucb = theta @ context + self.alpha * np.sqrt(
                    context @ A_inv @ context)
                score += w * ucb
            combined.append(score)
        return int(np.argmax(combined))

    def update(self, arm, context, r_start, r_submit, r_approve):
        self.app_start_bandit.update(arm, context, r_start)
        self.app_submit_bandit.update(arm, context, r_submit)
        self.app_approved_bandit.update(arm, context, r_approve)
```

我们构建了[一个快速上手 Jupyter notebook](https://github.com/aws-samples/sample-multi-objective-contextual-bandit-with-sagemaker/blob/main/notebooks/walkthrough.ipynb)来在 Amazon SageMaker AI 上测试这一方法。[该仓库](https://github.com/aws-samples/sample-multi-objective-contextual-bandit-with-sagemaker)还含一个命令行演示和单元测试。

**调优 alpha。** α 参数控制利用-探索平衡。更高的值鼓励对测试不足的臂的探索，更低的值偏向利用。α = 1.0 是一个合理的默认值（Li 等人，2010）。在实践中，当臂空间大而历史有限时从较高开始，然后随证据累积降低 α。一个典型范围是 0.1 到 2.0。太高的值会把流量浪费在弱臂上，太低的值有锁定到一个次优臂的风险。因为 α 是一个单一标量，网格搜索很直接。

**处理延迟反馈。** 在我们的环境中，批准决定滞后数天，因此漏斗最后阶段的奖励在展示之后很久才被观察到。我们用一段归因窗口来处理这一点。开始和提交立即更新模型，而批准结果被保留到后续批处理周期，从而避免来自待处理申请的向下偏置。这自然地与我们的每周处理节奏对齐。

## 大规模发布安全内容

一个赌博机只和它的臂池一样好。在保持内容监督的同时，负责任地构建一个丰富的臂池是下一个需要在规模上解决的问题。

关键想法是用一小组经过审阅的构件组合出许多变体。我们的内容由两类部件拼装：*行业主题图像*和*利益导向标语*。臂空间是这些部件的笛卡尔积，因此每条臂是一个（图像，标语）配对，而一小批构件就产出大量各不相同的页面变体。

图 1：构件逐个被审查，然后组合成完整的臂池

那一结构还通过几层控制，让这一方法在不牺牲监督的情况下可扩展。

**审查部件，而非组合。** 有些内容元素由干系人需求固定。我们没有审阅每一个可能的组合（那会随空间增长而不切实际），而是预先审查每个单独的构件。因为构件数量保持小而可审、而组合飞速增长，一次审查部件就能对整个组合空间提供保证。

**为一致性而用的设计系统。** 如我们早前文章所述，把内容锚定到一个设计系统（已批准的颜色、布局、组件和模式）让变体在构造上而非偶然地保持视觉上的一致和符合品牌。

**用生成式 AI 扩展臂池。** 在我们最初的部署中，构件是在详尽的人工监督下策展的，即便生产是由生成式 AI 工具辅助。我们看到把部件池（文本、图像、布局）大幅增强的清晰潜力，这会拓宽赌博机的选择空间。随着这一池增长，赌博机和生成流水线形成一个良性循环。生成式 AI 拓宽候选集，而赌博机识别哪些组合为每个访问者产出最强结果。

## 在 AWS 上部署

Amazon SageMaker AI 是一个支持完整模型生命周期的 AI 模型开发服务。它是我们端到端流水线背后的主要 AWS 服务，在一个统一的工具中提供模型训练、批处理、版本控制和监控。我们采用批处理架构出于两个原因：选择问题的离线本质（反馈在数天内累积），以及访问者选择行为变化不够快、不需要实时模型更新这一观察。一个预定的 SageMaker AI Processing 作业读取上一周期的反馈、更新模型，并为下一周期写出新的推荐。

### 架构概览

我们运行一个每周的 SageMaker AI 批处理作业，从 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 读取客户结果、更新赌博机模型，并把逐客户的推荐发布到一个低延迟的键值存储。从每周的节奏开始提供一个保守的基线。一旦模型展示出稳定的提升，提高频率很简单。可能滞后数天的批准反馈，被纳入后续的批次。

图 2：带 Amazon S3 模型状态和键值服务的端到端批处理赌博机架构

**1. 数据收集。** 客户的展示和结果（开始、提交、批准）在会话结束时记录，并作为观察数据流入 Amazon S3。

**2. 模型更新与推理**。一个 Amazon SageMaker AI Processing 作业运行 Python 入口点。它从 Amazon S3 加载最近的模型状态，自动发现最新的带日期模型前缀，因此多次运行之间无需重新配置任何东西。然后它把数据分成反馈行和推理行，在反馈上更新模型（增量更新），并对每个潜在客户打分以选择一条臂。我们用 Processing 作业，因为我们的工作负载是一个既更新又打分的单一自包含步骤，带定制的 S3 I/O。Training 作业或 Batch Transform 都不能干净地映射到这一模式。

**3. 持久化与输出。** 该作业把更新后的模型状态写回 Amazon S3（在一个新的带日期路径中，这给了内建的版本历史和直接的回滚），连同观察数据和臂内容一起。逐客户的推荐（每个客户映射到其选中的臂）被发布到一个面向实时流量的低延迟键值存储（如 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/)）。

**预热模型。** 我们从一段随机化内容指派周期来预热启动每个模型，这提供无偏的数据，让赌博机在没有选择偏置的情况下初始化其信念，并从第一天起更高效地花费其探索预算。

**高效伸缩推理。** 为一大潜在客户群体打分是计算密集的。两项优化把它保持在预算之内：预计算臂矩阵求逆一次（它们在批次内不变），以及用 Python 的 `multiprocessing.Pool` 把潜在客户集拆成分数并行的块。

**页面如何被服务。** 服务路径很简单，因为繁重的计算已经在批处理作业中完成了。个性化页面由一个持有每个客户预先计算推荐的低延迟键值存储（如 Amazon DynamoDB）来交付。当一个客户到来时，页面按实体 ID 做一次查找并渲染预先计算臂的内容。没有实时模型推理。

对于需要实时打分的用例——上下文只在请求时才已知、或内容必须在一次会话内自适应——Amazon SageMaker AI 实时推理端点是天然的替代，把一个模型托管在一个低延迟 API 之后。

该设计还有一个值得指出的稳健性属性。如果对某个访问者没有推荐存在，页面退回到默认静态体验，因此没有客户会比基线更差。这一退避兜住了下行风险并让增量上线更安全。

## 经验教训

在生产中部署这一系统教会了我们若干在我们特定用例之外可泛化的东西。

### 模型设计

*当群体差异很大时，分开训练。* 如果你的受众分成特征或转化率显著不同的组，一个单一共享模型会让更大或更嘈杂的组主导所学到的东西。为每组训练一个模型，各自配自己的特征集和臂空间，能让每个受众的信号清晰地透出来。

*优化漏斗，而非一个代理。* 最重要的单一设计决定是转向多目标。一个单阶段赌博机会让我们在一个上游指标上“取胜”、却在最终决定业务价值的下游指标上退化性能。我们在部署前用实证验证了这一点。为单一漏斗阶段优化的策略，始终在别处至少产出一个负的方向性提升。多目标的表述是唯一能在所有三个阶段同时保持非负估计的方法。如果你的业务目标离第一次点击有好几步，就把所有步骤编码进奖励。

### 内容策略

选择算法只应对了挑战的一半。内容池的质量同样重要。在我们的 A/B 测试中，一个客户群体在全部三个漏斗指标上都看到方向性正向的提升，目前最后一阶段有高个位数百分比的相对提升。对第二个群体，模型探索了其臂池的绝大部分，却找不到一个胜过静态页的组合。提升是负的，而批准退化在统计上显著。这不是一个模型失败。彻底的探索能够确认一个内容池中没有赢家。

如果一个赌博机广泛探索了各臂、仍无法击败对照（静态体验，无赌博机），那么需要重新审视的是各臂而非算法。这正是像我们[早前文章](https://aws.amazon.com/blogs/machine-learning/reinvent-personalization-with-generative-ai-on-amazon-bedrock-using-task-decomposition-for-agentic-workflows/)里那样的生成式内容流水线变得不可或缺之处。它们扩展并刷新赌博机从中取样的池，让模型有更大的机会找到一个赢家组合。

考虑把基线做成一条臂。把现有的默认体验作为各臂之一，意味着对某个给定客户，如果没有个性化臂胜过默认，UCB 会自然地趋向于服务它，从而兜住系统能退化多远。

### 评估

离线评估和 A/B 测试回答不同的问题。离线重放（在留出数据上把策略与随机比较）告诉你“模型是否胜过随机指派”，作为一个初步验证。但只有传统的 A/B 测试（赌博机个性化与静态基线比较）才决定个性化是否优于你现有的体验。我们两者都用。离线估计给了上线的信心，而 A/B 测试给出了权威判决，包括“内容池质量是某个群体的约束瓶颈”这一发现。

权重告诉你是什么在驱动结果。LinUCB 学到的 θ 向量是直接可解释的。某个特征上一个大的正权重意味着在该信号上强的客户更可能在那条臂上转化。几周之后你可以问“什么信号区分了对这张图像的响应者？”，并得到可信的洞见。这产出了无需额外工具的内建可解释性，并为内容策略提供直接输入。

### 运维

批处理是一种正当的部署模式。你不需要一个实时的在线学习应用来在生产中运行一个赌博机。一个每周的 Processing 作业——读反馈、更新一个精确更新模型、把推荐写到 S3——可审计、资源高效，并天然契合延迟反馈。

## 结论

生成式 AI 消除了产出个性化内容的约束。剩下的挑战是决定把哪个内容给谁、并从真实客户反馈中学会答案。多臂赌博机专为这一点而打造。用上下文的、多目标的表述，你可以基于个体行为做个性化，同时优化整个转化漏斗。

该系统在 AWS 上易于运营。一个预定的 SageMaker AI Processing 作业，加 Amazon S3 做版本化的模型状态，就给了你增量学习、一条审计轨迹，以及一个安全的退避，而无需一个专门的实时工具。

如果生成式 AI 已经在填满你的内容池，一个上下文赌博机就是其之上天然的优化层，为每个人识别哪个内容变体产出最强的结果。本系列文章中的这两项技术相辅相成。

要开始上手，打开 [Amazon SageMaker AI 控制台](https://console.aws.amazon.com/sagemaker/)，探索 [SageMaker AI 开发者指南](https://docs.aws.amazon.com/sagemaker/)，克隆[代码示例](https://github.com/aws-samples/sample-multi-objective-contextual-bandit-with-sagemaker)并打开它的演练 notebook 来亲自运行赌博机，并审阅我们早前关于 [Amazon Bedrock 上的生成式 AI 个性化](https://aws.amazon.com/blogs/machine-learning/reinvent-personalization-with-generative-ai-on-amazon-bedrock-using-task-decomposition-for-agentic-workflows/)的文章。
