# 在 AWS 上使用 LangGraph 与 Mistral 构建多 agent 系统

agent 正在革新[生成式 AI](https://aws.amazon.com/generative-ai/)的格局，充当[大语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）与现实世界应用之间的桥梁。这些智能的自主系统有望成为各行各业采用 AI 的基石，开启人机协作与问题解决的新时代。通过利用 LLM 的能力，并将其与专用工具和 API 相结合，agent 可以处理以往传统 AI 系统无法企及的复杂多步任务。本文展示的 Multi-Agent City Information System 正是基于 agent 的架构潜力的体现——它可以构建精巧、可适应且能力极强的 AI 应用。

展望未来，agent 将在以下方面发挥非常重要的作用：

- 通过更深入、具备上下文感知的信息来改进决策
- 跨客户服务到科学研究等各个领域自动化复杂工作流
- 实现更自然、更直观的人机交互
- 通过汇聚多样的数据源和专业知识来产生新想法
- 通过提供更透明、更可解释的 AI 系统来应对伦理关切

构建和部署类似本文这样的多 agent 系统，是释放生成式 AI 全部潜力的一步。随着这些系统的演进，它们将改变行业、拓展可能性，并为人工智能打开新的大门。

## 解决方案概览

在本文中，我们探讨如何在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上使用 [LangGraph](https://www.langchain.com/langgraph) 和 [Mistral 模型](https://aws.amazon.com/bedrock/mistral/)构建一个强大的多 agent 系统，通过协作式问题解决来处理复杂的工作流。这种集成使得能够创建可以协同工作以解决复杂问题的 AI agent，模拟人类式的推理与协作。

其结果是一个能够提供指定城市的活动、天气、活动建议和餐厅推荐等全面详情的系统，展示了如何在 [Amazon Web Services](https://aws.amazon.com/)（AWS）上构建和部署有状态的多 agent 应用，以应对现实世界的挑战。

LangGraph 对我们的解决方案至关重要，它提供了一种组织良好的方法来定义和管理 agent 之间的信息流。它内置对状态管理和检查点（checkpointing）的支持，保证流程的平滑连续。该框架还支持对 agent 工作流进行直观可视化，增强清晰度和理解。它能轻松与 LLM 和 Amazon Bedrock 集成，提供了一种通用而强大的解决方案。此外，它对条件路由的支持使得可以根据中间结果动态调整工作流，在处理不同场景时具备灵活性。

我们展示的多 agent 架构提供几个关键收益：

- **模块化 –** 每个 agent 专注于特定任务，使系统更易于维护和扩展
- **灵活性 –** 可以快速添加、移除或修改 agent，而不影响整个系统
- **复杂工作流处理 –** 通过在多个 agent 之间分配任务，系统可以管理高级且复杂的工作流
- **专业化 –** 每个 agent 都针对其特定任务进行优化，改善延迟、准确性和整体系统效率
- **安全性 –** 通过确保每个 agent 只能访问其任务所需的工具，系统增强了安全性，降低了未经授权访问敏感数据或其他 agent 任务的可能性

## 我们的多 agent 系统如何运作

在本节中，我们基于 GitHub 上 [Mistral on AWS examples for Bedrock & SageMaker](https://github.com/aws-samples/mistral-on-aws) 仓库中的多 agent LangGraph Mistral Jupyter notebook，探讨我们的 Multi-Agent City Information System 如何运作。

该 agent 工作流以城市名称为输入并提供详细信息，展示了在处理不同场景时的适应性：

- **活动 –** 它在本地数据库和在线来源中搜索该城市即将举行的活动。当本地数据库信息不可用时，它会使用 [Tavily API](https://tavily.com/) 触发在线搜索。这确保无论活动信息存储在本地还是需要从网上检索，用户都能获得最新的活动信息
- **天气 –** 系统使用 [OpenWeatherMap API](https://openweathermap.org/api) 获取当前天气数据，为所查询的地点提供准确及时的天气信息。基于天气情况，系统还会提供贴合条件的着装和活动建议，为每个城市提供相关推荐
- **餐厅 –** 推荐通过[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）系统提供。该方法将预存信息与实时生成相结合，提供相关且最新的餐饮建议

系统处理不同信息水平的能力通过其自适应方式得以体现，这意味着无论不同城市的数据可得性如何变化，用户都能获得尽可能全面和最新的信息。例如：

- 当本地数据库数据不可用时，某些城市可能需要使用搜索工具来获取活动信息
- 其他城市可能在本地数据库中有可用数据，无需在线搜索即可快速获取活动信息
- 当某个特定城市没有餐厅推荐时，系统仍可基于可用的活动和天气数据提供有价值的洞察

## 数据源

Multi-Agent City Information System 可以利用两类数据源。

### 本地活动数据库

这个 SQLite 数据库用来自 [JSON 文件](https://github.com/aws-samples/mistral-on-aws/blob/main/notebooks/mistral-langgraph/data/eventsDB_data.json)的城市活动数据填充，可快速访问从社区活动到文化活动和全市性活动的本地活动信息。该数据库由 `events_database_tool()` 使用，以高效查询和检索城市活动详情，包括地点、日期和活动类型。

### 餐厅 RAG 系统

对于餐厅推荐，`generate_restaurants_dataset()` 函数会生成合成数据，创建一个专为我们的推荐系统定制的数据集。`create_restaurant_vector_store()` 函数处理这些数据，使用 [Amazon Titan Text Embeddings](https://aws.amazon.com/bedrock/amazon-models/titan/) 生成嵌入，并用 [Facebook AI Similarity Search](https://python.langchain.com/docs/integrations/vectorstores/faiss/)（FAISS）构建向量存储。尽管这种方式适合原型验证，但对于更具可扩展性的企业级解决方案，我们建议使用 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)。

## 构建多 agent 架构

Multi-Agent City Information System 的核心是一组专用函数和工具，用于从各种来源收集、处理和综合信息。它们构成了我们系统的骨干，使其能够提供关于城市的全面且最新的信息。在本节中，我们探讨驱动系统的关键组件：使用 Mistral 模型的 `generate_text()` 函数，以及用于本地数据库查询、在线搜索、天气信息和餐厅推荐的专用数据检索函数。这些函数和工具共同构成了一个稳健而通用的系统，能够为用户提供有价值的洞察。

### 文本生成函数

该函数是我们各 agent 的核心，让它们可以按需使用 Mistral 模型生成文本。它使用 [Amazon Bedrock Converse API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html)，后者支持文本生成、流式传输以及[外部函数调用](https://docs.aws.amazon.com/bedrock/latest/userguide/tool-use-inference-call.html)（工具）。

该函数的工作方式如下：

- 使用 Amazon Bedrock Converse API 向 Mistral 模型发送用户消息
- 调用相应的工具并将结果并入对话
- 继续对话，直到生成最终响应

以下是实现：

```
def generate_text(bedrock_client, model_id, tool_config, input_text):
    ......
    
    while True:
        response = bedrock_client.converse(**kwargs)
        output_message = response['output']['message']
        messages.append(output_message) # Add assistant's response to messages
        
        stop_reason = response.get('stopReason')

        if stop_reason == 'tool_use' and tool_config:
            tool_use = output_message['content'][0]['toolUse']
            tool_use_id = tool_use['toolUseId']
            tool_name = tool_use['name']
            tool_input = tool_use['input']

            try:
                if tool_name == 'get_upcoming_events':
                    tool_result = local_info_database_tool(tool_input['city'])
                    json_result = json.dumps({"events": tool_result})
                elif tool_name == 'get_city_weather':
                    tool_result = weather_tool(tool_input['city'])
                    json_result = json.dumps({"weather": tool_result})
                elif tool_name == 'search_and_summarize_events':
                    tool_result = search_tool(tool_input['city'])
                    json_result = json.dumps({"events": tool_result})
                else:
                    raise ValueError(f"Unknown tool: {tool_name}")
                
                tool_response = {
                    "toolUseId": tool_use_id,
                    "content": [{"json": json.loads(json_result)}]
                }
                
            ......
            
            messages.append({
                "role": "user",
                "content": [{"toolResult": tool_response}]
            })
            
            # Update kwargs with new messages
            kwargs["messages"] = messages
        else:
            break

    return output_message, tool_result
```

### 本地数据库查询工具

`events_database_tool()` 通过连接数据库、执行查询以获取指定城市即将举行的活动，并把结果作为格式化字符串返回，从而查询本地 SQLite 数据库以获取活动信息。它由 `events_database_agent()` 函数使用。以下是代码：

```
def events_database_tool(city: str) -> str:
    conn = sqlite3.connect(db_path)
    query = """
        SELECT event_name, event_date, description 
        FROM local_events 
        WHERE city = ?
        ORDER BY event_date
        LIMIT 3
    """
    df = pd.read_sql_query(query, conn, params=(city,))
    conn.close()
    print(df)
    if not df.empty:
        events = df.apply(
            lambda row: (
                f"{row['event_name']} on {row['event_date']}: {row['description']}"
            ),
            axis=1
        ).tolist()
        return "\n".join(events)
    else:
        return f"No upcoming events found for {city}."
```

### 天气工具

`weather_tool()` 通过调用 OpenWeatherMap API 获取指定城市的当前天气数据。它由 `weather_agent()` 函数使用。以下是代码：

```
def weather_tool(city: str) -> str:
    weather = OpenWeatherMapAPIWrapper()
    tool_result = weather.run("Tampa")
    return tool_result
```

### 在线搜索工具

当本地活动信息不可用时，`search_tool()` 使用 Tavily API 执行在线搜索，以查找指定城市即将举行的活动并返回摘要。它由 `search_agent()` 函数使用。以下是代码：

```
def search_tool(city: str) -> str:
    client = TavilyClient(api_key=os.environ['TAVILY_API_KEY'])
    query = f"What are the upcoming events in {city}?"
    response = client.search(query, search_depth="advanced")
    results_content = "\n\n".join([result['content'] for result in response['results']])
    return results_content  
```

### 餐厅推荐函数

`query_restaurants_RAG()` 函数使用 RAG 系统提供餐厅推荐：在向量数据库中对相关餐厅信息执行相似性搜索，筛选指定城市中评分较高的餐厅，并使用 Amazon Bedrock 配合 Mistral 模型，根据检索到的信息生成顶级餐厅的摘要。它由 `query_restaurants_agent()` 函数使用。

有关这些函数和工具的详细实现、环境设置以及用例，请参阅 [Multi-Agent LangGraph Mistral Jupyter notebook](https://github.com/aws-samples/mistral-on-aws/blob/main/notebooks/mistral-langgraph/Multi_Agent_LangGraph_Mistral.ipynb)。

## 使用 LangGraph 实现 AI agent

我们的多 agent 系统由多个专用 agent 组成。该架构中的每个 agent 在 LangGraph 中由一个 [Node](https://langchain-ai.github.io/langgraph/concepts/low_level/#nodes) 表示，而每个 Node 又与前面定义的各工具和函数交互。下图展示了该工作流：

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/03/LangGraph-Multi-Agent-Workflow.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/03/LangGraph-Multi-Agent-Workflow.png)

该工作流遵循以下步骤：

- **活动数据库 agent（events_database_agent）–** 使用 `events_database_tool()` 查询本地 SQLite 数据库并查找本地活动信息
- **在线搜索 agent（search_agent）–** 每当数据库中缺少本地活动信息时，该 agent 使用 `search_tool()` 通过在线搜索给定城市来查找即将举行的活动
- **天气 agent（weather_agent）–** 使用 `weather_tool()` 获取指定城市的当前天气数据
- **餐厅推荐 agent（query_restaurants_agent）–** 使用 `query_restaurants_RAG()` 函数为指定城市提供餐厅推荐
- **分析 agent（analysis_agent）–** 汇总其他 agent 的信息以提供全面的建议

以下是我们创建天气 agent 的示例：

```
def weather_agent(state: State) -> State:
    ......
    
    tool_config = {
        "tools": [
            {
                "toolSpec": {
                    "name": "get_city_weather",
                    "description": "Get current weather information for a specific city",
                    "inputSchema": {
                        "json": {
                            "type": "object",
                            "properties": {
                                "city": {
                                    "type": "string",
                                    "description": "The name of the city to look up weather for"
                                }
                            },
                            "required": ["city"]
                        }
                    }
                }
            }
        ]
    }
    
    input_text = f"Get current weather for {state.city}"
    output_message, tool_result = generate_text(bedrock_client, DEFAULT_MODEL, tool_config, input_text)
    
    if tool_result:
        state.weather_info = {"city": state.city, "weather": tool_result}
    else:
        state.weather_info = {"city": state.city, "weather": "Weather information not available."}
    
    print(f"Weather info set to: {state.weather_info}")
    return state
```

## 编排 agent 协作

在 Multi-Agent City Information System 中，若干关键原语负责编排 agent 协作。`build_graph()` 函数在 LangGraph 中定义工作流，利用节点、路由和条件。该工作流是动态的，基于事件搜索结果进行条件路由，并引入了内存持久化，以便在不同执行之间存储 agent 的状态。以下概述该函数的行为：

- **初始化工作流 –** 该函数首先创建一个名为 `workflow` 的 [StateGraph](https://langchain-ai.github.io/langgraph/concepts/low_level/#stategraph) 对象，该对象以 [State](https://langchain-ai.github.io/langgraph/concepts/low_level/#state) 初始化。在 LangGraph 中，`State` 表示 agent 执行任务时在工作流中传递的数据或上下文。在我们的示例中，状态包含来自先前 agent 的结果（例如事件数据、搜索结果和天气信息）、输入参数（例如城市名称），以及 agent 可能需要处理的其他相关信息：

```
# Define the graph
def build_graph():
    workflow = StateGraph(State)
    ...
```

- **添加节点（agent）–** 每个 agent 都与一个特定函数关联，例如检索事件数据、执行在线搜索、获取天气信息、推荐餐厅或分析收集到的信息：

```
    workflow.add_node("Events Database Agent", events_database_agent)
    workflow.add_node("Online Search Agent", search_agent)
    workflow.add_node("Weather Agent", weather_agent)
    workflow.add_node("Restaurants Recommendation Agent", query_restaurants_agent)
    workflow.add_node("Analysis Agent", analysis_agent)
```

- **设置入口点和条件路由 –** 工作流的入口点被设置为 `Events Database Agent`，这意味着工作流的执行从该 agent 开始。此外，该函数使用 `add_conditional_edges` 方法定义一个条件路由。`route_events()` 函数根据 `Events Database Agent` 的结果决定下一步：

```
 workflow.set_entry_point("Events Database Agent")
    
    def route_events(state):
        print(f"Routing events. Current state: {state}")
        print(f"Events content: '{state.events_result}'")
        if f"No upcoming events found for {state.city}" in state.events_result:
            print("No events found in local DB. Routing to Online Search Agent.")
            return "Online Search Agent"
        else:
            print("Events found in local DB. Routing to Weather Agent.")
            return "Weather Agent"

    workflow.add_conditional_edges(
        "Events Database Agent",
        route_events,
        {
            "Online Search Agent": "Online Search Agent",
            "Weather Agent": "Weather Agent"
        }
    )
```

- **在 agent 之间添加 [Edges](https://langchain-ai.github.io/langgraph/concepts/low_level/#edges) –** 这些边定义了 agent 在工作流中交互的顺序。各 agent 将按特定顺序推进：从 `Online Search Agent` 到 `Weather Agent`，从 `Weather Agent` 到 `Restaurants Recommendation Agent`，再从那里到 `Analysis Agent`，最终到达 `END`：

```
    workflow.add_edge("Online Search Agent", "Weather Agent")
    workflow.add_edge("Weather Agent", "Restaurants Recommendation Agent")
    workflow.add_edge("Restaurants Recommendation Agent", "Analysis Agent")
    workflow.add_edge("Analysis Agent", END)
```

- **初始化内存以实现状态持久化 –** 使用 [`MemorySaver`](https://langchain-ai.github.io/langgraph/reference/checkpoints/#langgraph.checkpoint.memory.MemorySaver) 类来确保工作流的状态在多次运行之间得以保留。这在多 agent 系统中尤其有用，因为 agent 交互时需要维护系统状态：

```
    # Initialize memory to persist state between graph runs
    checkpointer = MemorySaver()
```

- **编译工作流并可视化图 –** 工作流会被编译，并包含内存保存对象（`checkpointer`），以确保状态在多次执行之间持久化。然后，它输出工作流的图形表示：

```
    # Compile the workflow
    app = workflow.compile(checkpointer=checkpointer)
    
    # Visualize the graph
    display(
        Image(
            app.get_graph().draw_mermaid_png(
                draw_method=MermaidDrawMethod.API
            )
        )
    )
```

### 三个示例用例

对于示例 1（Tampa），下图展示了 agent 工作流如何针对用户的问题“Tampa 正在发生什么，我应该穿什么？”生成输出。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/03/Multi-Agent-City-Information-System-Sequence-Diagram-v2.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/03/Multi-Agent-City-Information-System-Sequence-Diagram-v2.png)

系统产生了以下结果：

- **活动 –** 本地数据库中未找到，触发搜索工具，该工具调用 Tavily API 找到若干即将举行的活动
- **天气 –** 从天气工具获取。当前天气状况包括中雨、28°C 和 87% 湿度
- **活动建议 –** 系统根据活动和天气推荐了各种室内和室外活动
- **着装建议 –** 考虑到温暖、潮湿多雨的条件，系统推荐了轻便透气的衣物和防雨装备
- **餐厅 –** 通过 RAG 系统提供推荐

对于示例 2（Philadelphia），agent 工作流在本地数据库中识别出了活动，包括文化活动和节庆。它从 OpenWeatherMap API 获取天气数据，然后基于本地活动和天气状况建议活动。着装建议与天气预报保持一致，餐厅推荐通过 RAG 系统提供。

对于示例 3（New York），工作流在本地数据库中识别出了百老汇演出和城市景点等活动。它从 OpenWeatherMap API 获取天气数据，并基于多样的本地活动和天气状况建议活动。着装建议针对纽约的天气和城市环境进行了定制。然而，RAG 系统无法为 New York 提供餐厅推荐，因为此前创建的合成数据集不包含这座城市的任何餐厅。

这些示例展示了系统适应不同场景的能力。有关这些示例的详细输出，请参阅 [Multi-Agent LangGraph Mistral Jupyter notebook](https://github.com/aws-samples/mistral-on-aws/blob/main/notebooks/mistral-langgraph/Multi_Agent_LangGraph_Mistral.ipynb) 的结果与分析部分。

## 结论

在我们开发的 Multi-Agent City Information System 中，agent 在灵活、模块化的框架内整合各种数据源和 API，提供关于不同城市的活动、天气、活动建议、着装建议和餐饮选择的有价值信息。使用 Amazon Bedrock 和 LangGraph，我们创建了一个精巧的基于 agent 的工作流，能够根据可用信息水平的不同无缝调整，按需在本地和在线数据源之间切换。这些 agent 自主地收集、处理并将数据整合为可执行的洞察，编排并自动化业务逻辑，以简化流程并提供实时洞察。因此，这种多 agent 方式能够创建稳健、可扩展且智能的 agent 系统，拓展生成式 AI 的可能性边界。
