# 当您的编码代理使用 Amazon Bedrock AgentCore 运行时构建 Web 应用程序时，实时预览它们

编码代理现在构建工作网络应用程序：仪表板、产品页面、产品团队想要尝试的原型。审查该工作的最快方法是打开应用程序、使用它、请求更改并检查结果。当应用程序在代理编辑的地方继续运行时，该循环效果很好，因此每个更改都会在几秒钟内显示在浏览器中。当应用程序必须首先复制并部署到其他地方时，每个更改都会等待部署，并且审核速度会减慢。

[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 是一个用于大规模构建、连接和优化代理的平台，您可以选择代理框架和基础模型 (FM)。 [AgentCore 运行时](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 是 Amazon Bedrock AgentCore 的一项功能，可在其自己的隔离 microVM 中运行每个代理会话。使用[会话端点](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-session-endpoints.html)，您可以从自己的浏览器打开在该会话中运行的应用程序。会话端点为每个会话提供一个经过身份验证的 URL，该 URL 将每个请求的 HTTP 方法、路径、查询字符串和正文以及 WebSocket 连接转发到您允许的端口。您可以在代理保存每个文件时观看页面更新。

在这篇文章中，您将部署一个编码代理，使 Vite 网站在其会话中保持运行，然后打开一个本地页面，左侧是聊天窗口，右侧是实时网站。您要求代理将网站切换为深色主题，按照其流入的步骤进行操作，然后观察网站的变化而无需刷新。最后，您看看内部发生了什么：同一会话中的第二个端口，以及会话端点拒绝的请求。

完整的示例（包括本文后面的笔记本）位于 [agentcore-samples GitHub 存储库](https://github.com/awslabs/agentcore-samples) 的 [14-remote-access 文件夹](https://github.com/awslabs/agentcore-samples/tree/main/01-features/02-host-your-agent/01-runtime/03-advanced/16-session-endpoints)。

## 会话端点如何工作

每个会话都有自己的会话端点，六个细节决定了您如何使用它。

**您可以选择它到达的端口。** 您可以在调用 [CreateAgentRuntime](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_CreateAgentRuntime.html) 时设置 `allowedPorts`：1–5 个条目，每个条目一个端口或 8000–12000 范围内的端口，不包括 [保留平台]端口](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-service-contract.html#runtime-reserved-ports)。允许端口不会启动服务器，因此您的应用程序必须侦听该端口，并绑定到“0.0.0.0”。

**URL 随会话一起到达。** [InvokeAgentRuntime](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_InvokeAgentRuntime.html) 响应在“X-Amzn-Bedrock-AgentCore-Runtime-Session-Endpoint-Url”标头中携带该 URL，将其建模的 SDK 将其公开为“sessionEndpointUrl”。

**每个请求都经过身份验证。** 对于使用 [AWS Identity and Access Management (IAM)](https://docs.aws.amazon.com/IAM/latest/UserGuide/introduction.html) 的运行时，每个 HTTP 请求、HTTP/2 流和 WebSocket 握手都携带 [签名版本 4 (SigV4)](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv.html) 签名。调用者还需要运行时及其运行时端点上的“bedrock-agentcore:InvokeAgentRuntimeProxy”。对于具有[入站 JSON Web 令牌 (JWT) 授权者](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html) 的运行时，每个请求都会携带一个不记名令牌。知道 URL 并不授予访问权限。

**主机名选择端口。** 无论目标端口是什么，您的客户端都会在端口 443 上连接，并且主机名上的前缀选择会话内的端口：
```
https://8090--<session-endpoint-id>.runtime.bedrock-agentcore.<region>.on.aws/index.html
https://8081--<session-endpoint-id>.runtime.bedrock-agentcore.<region>.on.aws/status
```
**它承载服务器使用的协议。** HTTP/1.1 和 HTTP/2 请求，包括服务器发送的事件和 gRPC，以及 WebSocket 连接都会通过。本演练使用 HTTP/1.1 和 WebSocket。

**其范围仅限于一个会话。** URL 在每个请求上都需要凭据，并且仅在会话期间持续，因此使用它来构建、测试和检查代理生成的内容。要向您的用户提供应用程序，请将其部署到托管服务，例如 [AWS Amplify Hosting](https://aws.amazon.com/amplify/hosting/)。

浏览器无法将 SigV4 签名或不记名令牌添加到页面自行发出的请求，因此 [bedrock-agentcore SDK](https://github.com/aws/bedrock-agentcore-sdk-python) 中的会话端点客户端可以在您的计算机上打开本地端点。您的浏览器打开“http://localhost:8088”，本地端点将您的凭据添加到每个请求和 WebSocket 握手中，然后再转发。

会话端点与 AgentCore 运行时已提供的运行时端点不同。使用运行时端点（例如“DEFAULT”）来访问您的代理，该代理控制调用者将访问的代理版本。 InvokeAgentRuntime 调用通过它进行解析，因此您可以在不同版本上进行开发和生产，并在不更改调用者的情况下进行升级或回滚。使用会话端点查看代理在其会话中运行的内容，例如 Web 预览。它是一个经过身份验证的 URL，仅到达您允许的端口，适用于会话运行的任何版本，并在会话结束时停止工作。有关完整文档，请参阅[通过会话终端节点连接到运行时会话](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-session-endpoints.html)。

## 解决方案概述

该示例有四个部分。编码代理在端口 8080 上的会话中运行，并使用四种工具编辑网站的文件：列表、读取、写入和编辑。该代理在端口 8090 上启动一个 [Vite](https://vite.dev/) 开发服务器，该服务器为网站提供服务，并通过其热重载 WebSocket 将每个保存的更改推送到浏览器。在您的计算机上，“PreviewApp”提供预览页面，将提示发送到“InvokeAgentRuntime”，并打开网站的本地端点。如图 1 所示，预览页面通过本地端点和会话端点从 Vite 开发服务器的 8090 端口加载网站，并通过 InvokeAgentRuntime 将提示发送到代理的 8080 端口。数字显示了一个请求的步骤顺序。

在第1步之前，PreviewApp已经调用了一次InvokeAgentRuntime来启动会话，从而启动代理和Vite开发服务器。 “PreviewApp”从该响应中读取会话端点 URL，并打开端口 8090 的本地端点。然后，图 1 中的编号步骤遵循一个更改请求：

- 预览页面的站点窗格从“localhost:8088”上的本地端点加载网站。本地端点将您的凭据添加到每个请求和 WebSocket 握手中，并将它们转发到会话端点。 **会话端点**根据“allowedPorts”检查签名和端口，然后将它们转发到端口8090上的Vite开发服务器。该页面保持Vite热重载WebSocket打开。

端口 8080 不在“allowedPorts”中，因为“InvokeAgentRuntime”无需通过会话端点即可到达代理。

## 先决条件

要按照演练操作，您需要：

- AgentCore 运行时会话终端节点可用且配置了凭证的 AWS 区域中的 AWS 账户。
- 创建 AWS Identity and Access Management (IAM) 角色、上传到 [Amazon Simple Storage Service (Amazon S3)](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html) 以及创建运行时以及该运行时及其“DEFAULT”运行时终端节点上的“bedrock-agentcore:InvokeAgentRuntime”和“bedrock-agentcore:InvokeAgentRuntimeProxy”的权限。有关详细信息，请参阅 [AgentCore 运行时的 IAM 权限](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-permissions.html)。
- Python 3.10 或更高版本，带有 `bedrock-agentcore` 1.25.2 或更高版本以及 `boto3` 1.43.122 或更高版本。
- [Git](https://git-scm.com/)，用于克隆示例存储库，以及 [Jupyter](https://jupyter.org/) 环境，例如 JupyterLab 或带有 Jupyter 扩展的 Visual Studio Code，用于运行笔记本。
- 访问 Amazon Bedrock 中的 [Claude Haiku 5.5](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-anthropic-claude-haiku-5-5.html)。有关按区域划分的模型可用性，请参阅[按模型划分的区域可用性](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。
- [Node.js](https://nodejs.org/) 22 或更高版本，使用“npm”，部署脚本使用它来打包代理和网站。

该示例使用 [Node.js 的直接代码部署](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-code-deploy-node.html) 将代理作为 zip 文件部署在 Amazon S3 中，因此您不需要 Docker 或 [Amazon Elastic Container Registry (Amazon ECR)](https://aws.amazon.com/ecr/) 存储库。会话端点与 microVM 运行时一起使用，而不是与实例计算类型一起使用，并且会话端点 URL 可通过公共 HTTPS 访问。入站连接不支持 AWS PrivateLink。

## 部署代理及其网站

首先，您部署运行时，您在此处选择的配置决定会话端点可以到达哪些端口。部署脚本将代理捆绑到一个文件中，为运行时的 Linux on Arm64 系统添加网站及其依赖项，将 zip 上传到 Amazon S3，然后创建运行时。

以下摘录自“deploy.py”，显示了对本文重要的两个设置。 “protocolConfiguration”表示代理侦听“InvokeAgentRuntime”的位置，“allowedPorts”列出会话端点可以到达的端口：8090 用于网站，8081 用于代理的状态路由。端口 8080 不在列表中，因为“InvokeAgentRuntime”在没有它的情况下到达代理。有关端口和路径设置，请参阅[配置代理的服务端口和调用路径](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-configure-inspiration.html)。
```
agentRuntimeArtifact={"codeConfiguration": {
    "code": {"s3": {"bucket": code_bucket(), "prefix": S3_PREFIX}},
    "runtime": "NODE_22",
    "entryPoint": ["app.js"],
}},
protocolConfiguration={"serverProtocol": "HTTP", "port": 8080, "path": "/invocations"},
allowedPorts=[{"port": 8090}, {"port": 8081}],
```
该网站的 Vite 配置使开发服务器可以从会话端点访问。它在端口 8090 上侦听“0.0.0.0”，并且不限制“Host”标头（“server.allowedHosts”为 true），因为请求是在运行时分配的主机名下到达的，而不是“localhost”。会话端点在每个请求到达服务器之前对其进行身份验证，因此服务器不需要自己的主机检查。

2. 从示例文件夹中打开“session_endpoints_preview.ipynb”。

## 打开预览

运行时准备就绪后，您可以开始预览。一次调用会执行三件事：启动一个会话（启动网站）、打开端口 8090 的本地端点，并在“localhost:8087”上提供预览页面。
```
from preview_app import PreviewApp

app = PreviewApp().start()
print("Open", app.url)
```
在“start()”内部，使用会话端点的调用很短。第一个“InvokeAgentRuntime”调用在响应标头中返回 URL，“session_endpoint_url”读取它，并且会话端点客户端打开端口 8090 的本地端点：
```
answer = client.invoke_agent_runtime(
    agentRuntimeArn=runtime_arn, runtimeSessionId=session_id,
    payload=json.dumps({"prompt": ""}).encode(), contentType="application/json",
)
endpoint = client.session_endpoint_client(session_endpoint_url(answer))
local = endpoint.open_local_endpoint(port=8090, local_port=8088).start()
```
要打开预览：

- 运行启动“PreviewApp”的单元。
- 在浏览器中打开打印的链接“http://localhost:8087”。

该页面右侧显示网站，在会话中通过端口 8090 提供服务，左侧显示包含建议请求的简短指南。

## 在同一会话中到达第二个端口

该网站并不是您可以访问的唯一服务器。该代理在端口 8081 上提供“/status”，其中列出了每个提示及其更改的文件。相同的会话端点到达它，唯一的区别是端口参数。
```
status = app.endpoint.request("GET", "/status", port=8081)
print("GET /status on port 8081: HTTP", status.status)
for edit in status.json()["edits"]:
    print("  ", edit["prompt"], "->", ", ".join(edit["files"]))
```
此 Python 脚本的输出应类似于以下内容：
```
GET /status on port 8081: HTTP 200
   Make the Order ahead button green -> src/style.css
```
## 会话端点拒绝什么

当运行时拒绝请求时，它会在响应标头中返回 HTTP 状态、空正文和错误代码，以便您可以从应用程序返回的错误中判断其拒绝。笔记本向 allowedPorts 之外的端口发送请求以及没有凭据的请求，运行时会以 403 AccessDenied 拒绝这两个请求。

下表列出了使用 **会话端点** 进行构建时可能会遇到的拒绝。

| **请求** | **来自运行时的响应** |
| ---| ---|
|不在“allowedPorts”中的端口 | `403 访问被拒绝` |
|没有有效凭据的请求 | `403 AccessDenied` 或 `401 AuthenticationRequired` |
|一个允许的端口，没有任何东西在监听它 | `502 端口无法访问` |
|会话不再存在的 URL | `404 会话未找到` |

## 如何保护对会话的访问

运行时在转发请求之前删除自己的身份验证标头，因此网站不会收到您的签名。请求在 [AWS CloudTrail](https://aws.amazon.com/cloudtrail/) 中记录为“InvokeAgentRuntimeProxy”事件，事件源为“bedrock-agentcore.amazonaws.com”。本地端点使用您的凭据进行操作，因此它限制了可以使用它的人。它仅侦听“127.0.0.1”，仅应答发送至其自己的本地地址的请求，并拒绝来自其他来源的页面打开的 WebSocket 连接。仅在使用预览时运行本地端点。有关更多信息，请参阅[在 CloudTrail 中记录会话终端节点请求](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-session-endpoints.html#runtime-session-endpoints-cloudtrail)。

访问控制不会将网站与代理分开。两者都在同一会话中运行，因此仅向执行角色授予代理所需的权限。如果运行时替换会话的计算，打开的连接将关闭，并且代理的编辑可能无法保留，除非会话使用持久存储。如果您需要文件比计算更持久，请参阅 [AgentCore 运行时的文件系统配置](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-filesystem-configurations.html)。

代理的文件工具解析站点文件夹内的每个路径并拒绝其外部的路径，因此提示无法使代理更改会话中的其他文件。如果其他人可以向您的编码代理发送提示，请考虑使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 来过滤有害的提示和响应，并在发布代理的更改之前查看它们。

## 清理

为了避免持续产生费用，请停止预览并删除示例创建的资源。代理编辑的网站存在于会话中，因此它与会话一起存在。

清理：

1. 运行停止单元格，并在笔记本出现询问时按 Enter。这将停止预览页面、本地端点和会话。

2. 运行 %run `cleanup.py` 单元，这将删除运行时、上传的代码和 IAM 角色。

## 结论

会话端点使您可以在您允许的端口上通过 HTTP/1.1、HTTP/2 和 WebSocket 从您自己的工具对 AgentCore 运行时会话中的应用程序进行经过身份验证的访问。在本文中，您在会话中部署了一个带有 Vite 网站的编码代理，通过本地端点在浏览器中打开了实时网站，向代理询问了深色主题，并在代理保存文件时观察了更改的到达。您还到达同一会话中的第二个端口并确认会话端点拒绝的内容。

要更进一步，请在站点文件夹中使用您自己的站点运行笔记本，或者更改代理的工具以匹配您的编码代理的工作方式。有关完整的选项集，包括端口范围、OAuth、HTTP/2 和 gRPC，请参阅[通过会话终端节点连接到运行时会话](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-session-endpoints.html)。

要更改“InvokeAgentRuntime”在您自己的代理中使用的端口或路径，请参阅[配置代理的服务端口和调用路径](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-configure-inspiration.html)。如果您的代理还需要在同一会话中运行构建或测试命令，请参阅[在 AgentCore 运行时会话中执行 shell 命令](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-execute-command.html)。要按照此示例的方式从 zip 文件部署您自己的 Node.js 代理，请参阅 [Node.js 的直接代码部署](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-code-deploy-node.html)。对于该服务提供的其他所有内容，请从 [具有 Amazon Bedrock AgentCore 运行时的主机代理或工具](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 开始，并在 [agentcore-samples GitHub 存储库](https://github.com/awslabs/agentcore-samples) 中查找更多示例。
