# 改造你的 MCP 架构：通过 AgentCore Gateway 统一多个 MCP 服务器

随着 AI agent 被大规模采用，开发者团队可以构建数十到数百个专门的 [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro)（MCP）服务器，分别针对特定的 agent 用例与领域、组织职能或团队量身定制。组织还需要把自有的现有 MCP 服务器或开源 MCP 服务器集成到其 AI 工作流中。因此，需要一种方式，把这些现有 MCP 服务器——无论是自建、公开可用还是开源的——高效地组合为一个统一接口，让 AI agent 可以直接使用，团队也可以在整个组织内无缝共享。

今年早些时候，我们推出了 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) Gateway，这是一项完全托管的服务，充当集中式的 MCP 工具服务器，提供统一接口，让 agent 可以发现、访问并调用工具。今天，我们以新的目标类型形式，扩展了对现有 MCP 服务器的支持，并将其纳入 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)。借助这一能力，你可以把多个围绕 agent 目标、面向特定任务的 MCP 服务器归组到一个可管理的 MCP 网关接口之后。这降低了维护多个独立网关的运维复杂度，同时提供与 REST API 及 [AWS Lambda](https://aws.amazon.com/pm/lambda/) 函数既有的相同的集中式工具与身份验证管理能力。

如果没有集中式方案，客户会面临显著挑战：跨组织发现与共享工具变得割裂，在多个 MCP 服务器之间管理身份验证愈发复杂，而为每个服务器维护独立的网关实例很快就会难以管理。Amazon Bedrock AgentCore Gateway 通过把现有 MCP 服务器当作原生目标来处理，帮助解决这些挑战，为客户提供路由、身份验证与工具管理的单点控制——让集成 MCP 服务器变得和向网关添加其他目标一样简单。

### 打破 MCP 孤岛：企业团队为何需要统一网关

我们通过一个电商下单系统的真实示例来探讨这一点，其中不同团队为各自的领域维护专门的 MCP 服务器。设想一个企业电商系统，不同团队开发了专门的 MCP 服务器：

- 购物车团队维护一个带购物车管理工具的 MCP 服务器
- 产品目录团队运行面向商品浏览与搜索的 MCP 服务器
- 促销团队运营一个处理促销逻辑的 MCP 服务器

过去，下单 agent 需要分别与这些 MCP 服务器交互，管理多条连接与多个身份验证上下文。借助 AgentCore Gateway 新增的 MCP 服务器目标支持，这些专门的服务器现在可以统一到一个网关之下，同时保持各团队自己的归属与访问控制。这种方式的力量在于其组织灵活性。团队可以根据多种逻辑准则对 MCP 服务器分组：

- **业务单元归属**：按业务单元组织 MCP 服务器
- **产品特性边界**：每个产品团队拥有自己的 MCP 服务器与领域专用工具，从而在为其 agent 提供统一接口的同时保持清晰的归属
- **安全与访问控制**：不同的 MCP 服务器需要不同的身份验证机制。网关负责处理身份验证的复杂性，使经过授权的 agent 能轻松访问所需工具

下图展示了下单 agent 如何通过 AgentCore Gateway 与多个 MCP 服务器交互。agent 连接到网关并发现可用工具。每个团队仍掌控自己的领域专用工具，同时共同构成一致的 agent 体验。网关处理工具命名冲突、身份验证，并在所有工具之上提供统一的语义搜索。

AgentCore Gateway 在现代 agentic 架构中充当集成枢纽，为把多样化的 agent 实现与广泛的工具提供方连接起来提供统一接口。如图所示，该架构展示了网关如何弥合 agent 实现与工具实现方式之间的鸿沟，如今又通过直接集成 MCP 服务器目标的能力得到增强。

### AgentCore Gateway 集成架构

在 AgentCore Gateway 中，目标（target）定义了网关将作为工具提供给 agent 的 API、Lambda 函数或其他 MCP 服务器。目标可以是 Lambda 函数、OpenAPI 规范、Smithy 模型、MCP 服务器或其他工具定义。

该架构中的目标集成一侧，展现了网关在工具集成方面的多面性。借助新增的 MCP 服务器目标支持，网关可以直接纳入来自公开 MCP 服务器的工具，把它们与其他目标类型一样视为一等公民。这一能力还延伸到联邦场景：一个 AgentCore Gateway 实例可以作为另一个实例的目标，从而跨组织边界实现分层的工具组织。网关可以与把 agent 暴露为工具的 AgentCore Runtime 实例、客户维护的私有 MCP 服务器、传统的 AWS Lambda 函数，以及 Smithy 与 AWS 服务 API 无缝集成。

除目标多样性之外，网关的身份验证架构还带来额外的运维收益。网关将入站身份验证与目标系统解耦，让 agent 通过单一接口访问使用多个身份提供方的工具。这种集中式方式简化了 AI agent 的开发、部署与维护。如今，同样的方式也可用于 MCP 服务器目标：网关使用为目标配置的身份提供方，负责处理与服务器对接的复杂性。

有了这一身份验证基础，你就能通过统一架构获得精细的工具管理能力。当 agent 请求发现工具时，网关在集成的各目标之间提供一致的视图，来自 MCP 服务器的工具与 Lambda 函数、传统 API 的工具一并呈现。语义搜索能力在各工具类型上统一运作，因此无论工具如何实现，agent 都能发现相关工具。在工具调用期间，网关处理必要的协议转换、身份验证流程与数据转换，向 agent 呈现干净一致的接口，同时在幕后管理不同目标系统的复杂性。

MCP 服务器目标支持的加入，代表着网关能力的重大演进。组织现在可以直接集成 MCP 原生工具，同时保留在传统 API 与 Lambda 函数上的既有投入。这种灵活性支持渐进式迁移策略：团队可以按自己的节奏采用 MCP 原生实现，同时维持现有集成的持续运行。网关的同步机制确保工具定义在不同目标类型之间保持最新，而其身份验证与授权系统无论底层工具如何实现，都提供一致的安全控制。

网关把 MCP 服务器、传统 API 与无服务器函数组合成一个协调一致的工具环境。这一能力连同企业级的安全与性能，使其成为 agentic 计算的一项有益基础设施。

## 开始将 MCP 服务器添加到 AgentCore Gateway

开始之前，你需要创建一个 AgentCore Gateway，并把 MCP 服务器添加为目标。

### 前提条件

请确认已具备以下前提条件：

- 拥有可访问 Amazon Bedrock AgentCore 的 AWS 账户。更多信息请参阅 [AgentCore Runtime 的权限](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-permissions.html)文档。
- Python 3.12 或更高版本
- 对 [OAuth 2.0](https://oauth.net/2/) 有基本了解

你可以通过多种界面创建网关并添加目标：

- [适用于 Python 的 AWS SDK（Boto3）](https://aws.amazon.com/sdk-for-python/)
- [AWS 管理控制台](https://aws.amazon.com/console/)
- [AWS 命令行界面](https://aws.amazon.com/cli/)（AWS CLI）
- [AgentCore 起始工具包，用于快速简捷的设置](https://aws.github.io/bedrock-agentcore-starter-toolkit/user-guide/gateway/quickstart.html)

以下实践示例与代码片段演示如何设置并使用 Amazon Bedrock AgentCore Gateway。若需交互式演练，可以使用这些 [GitHub 上的 Jupyter Notebook 示例](https://github.com/awslabs/agentcore-samples/tree/main/01-features/07-centralize-and-govern-your-ai-infrastructure/01-gateway/01-attach-targets/mcp/mcp-servers)。

### 创建网关

要创建网关，你可以使用 AgentCore 起始工具包，配合 [Amazon Cognito](https://aws.amazon.com/cognito/) [创建默认的授权配置](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-inbound-auth.html#gateway-inbound-auth-jwt)，用于基于 JWT 的入站授权。你也可以改用其他[兼容 OAuth 2.0 的身份验证提供方](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-idps.html)来替代 Cognito。

```
import time
import boto3

gateway_client = boto3.client("bedrock-agentcore-control")

# Create an authorization configuration, that specifies what client is authorized to access this Gateway
auth_config = {
    "customJWTAuthorizer": {
        "allowedClients": ['<cognito_client_id>'], # Client MUST match with the ClientId configured in Cognito.
        "discoveryUrl": '<cognito_oauth_discovery_url>',
    }
}

# Call the create_gateway API
# This operation is asynchronous so may take time for Gateway creation
# This Gateway will leverage a CUSTOM_JWT authorizer, the Cognito User Pool we reference in auth_config
def deploy_gateway(poll_interval=5):
    create_response = gateway_client.create_gateway(
        name="DemoGateway",
        roleArn="<IAM Role>", # The IAM Role must have permissions to create/list/get/delete Gateway
        protocolType="MCP",
        authorizerType="CUSTOM_JWT",
        authorizerConfiguration=auth_config,
        description="AgentCore Gateway with MCP Server Target",
    )
    gatewayID = create_response["gatewayId"]
    gatewayURL = create_response["gatewayUrl"]
    
    # Wait for deployment
    while True:
        status_response = gateway_client.get_gateway(gatewayIdentifier=gatewayID)
        status = status_response["status"]
        if status == "READY":
            print("✅ AgentCore Gateway is READY!")
            break
        elif status in ["FAILED"]:
            print(f"❌ Deployment failed: {status}")
            return None
        print(f"Status: {status} - waiting...")
        time.sleep(poll_interval)

if __name__ == "__main__":
    deploy_gateway()

# Values with < > needs to be replaced with real values
```

### 创建一个示例 MCP 服务器

作为示例，我们来创建一个示例 MCP 服务器，其中包含三个返回静态响应的简单工具。该服务器使用 FastMCP，并设置 `stateless_http=True`，这是 [AgentCore Runtime 兼容性所要求的](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-mcp.html#runtime-mcp-how-it-works)。

```
@mcp.tool()

    """Get an order"""
    return 123

@mcp.tool()
def updateOrder(orderId: int) -> int:
    """Update existing order"""
    return 456

@mcp.tool()
def cancelOrder(orderId: int) -> int:
    """cancel existing order"""
    return 789

if __name__ == "__main__":
    mcp.run(transport="streamable-http")
```

```
import time

def poll_for_status(interval=5):
    # Poll for READY status
    while True:
        gateway_target_response = gateway_client.get_gateway_target(gatewayIdentifier=gatewayID, targetId=gatewayTargetID)
        status = gateway_target_response["status"]
        if status == 'READY':

        elif status in ['FAILED', 'UPDATE_UNSUCCESSFUL', 'SYNCHRONIZE_UNSUCCESSFUL']:
```

## 在 AgentCore Gateway 中刷新 MCP 服务器的工具定义

[SynchronizeGatewayTargets](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_SynchronizeGatewayTargets.html) API 是一项新的异步操作，支持按需从 MCP 服务器目标同步工具。MCP 服务器承载的工具可供 agent 发现与调用。随着时间推移，这些工具可能需要更新，或在现有 MCP 服务器目标中引入新工具。你可以通过 SynchronizeGatewayTargets API 与外部 MCP 服务器连接，该 API 会执行协议握手并索引可用工具。该 API 让客户可以明确控制何时刷新工具定义，在修改 MCP 服务器的工具配置之后尤为有用。

当目标配置了 OAuth 身份验证时，该 API 会先与 AgentCore Identity 服务交互，从指定的凭证提供方检索所需凭证。在与 MCP 服务器开始通信之前，这些凭证会经过新鲜度与可用性校验。如果凭证检索失败或返回过期 token，同步操作会立即失败并给出相应的错误详情，使目标转入 FAILED 状态。对于未配置身份验证的目标，该 API 会直接进入工具同步。

工具处理工作流首先向 MCP 服务器发起 initialize 调用以建立会话。初始化成功后，该 API 会分页调用 MCP 服务器的 tools/list 能力，以 100 个工具为一批进行处理，从而优化性能与资源利用率。每一批工具都会经过规范化处理，该 API 会添加目标特定的前缀，以帮助避免与其他目标的工具发生命名冲突。在处理过程中，工具定义会被规范化，以促进不同目标类型之间的一致性，同时保留原始 MCP 服务器定义中的关键元数据。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/04/ML-19938-image-6.png)

同步流程在以下情形下开始：

- 运维管理员发起 `SynchronizeGatewayTargets` API，触发 AgentCore Gateway 刷新已配置的 MCP 目标。
- 网关从 AgentCore Identity 获取 OAuth token，以安全访问 MCP 目标。
- 随后网关与 MCP 服务器初始化一个安全会话，以获取版本能力信息。
- 最后，网关分页调用 MCP 服务器的 tools/list 端点以检索工具定义，确保网关始终维护一份最新且准确的工具清单。

`SynchronizeGatewayTargets` API 解决了在 AgentCore Gateway 中管理 MCP 目标的一个关键难题：在优化系统性能与资源利用率的同时，保持对可用工具的准确呈现。这一显式同步方式之所以有价值，原因如下：

**模式一致性管理**：如果没有显式同步，AgentCore Gateway 要么需要在 `ListTools` 操作期间实时调用 MCP 服务器（影响延迟与可靠性），要么就得冒提供陈旧工具定义的风险。`SynchronizeGatewayTargets` API 提供了一种受控机制，客户可以在关键时刻刷新工具模式，例如在 MCP 服务器中部署新工具或更新现有工具之后。这种方式确保网关中的工具定义准确反映目标 MCP 服务器的能力，同时不牺牲性能。

- **性能影响的权衡**：该 API 在同步期间实现乐观锁，以帮助防止可能引发状态不一致的并发修改。这意味着如果有竞争，多个同步请求可能需要重试，但这一权衡是可以接受的，因为：工具模式变更通常是低频的运维事件，而非日常运行时的高频事件；同步的性能开销只在显式请求时产生，而不在常规工具调用期间产生；缓存的工具定义使得两次同步之间的 `ListTools` 操作能够保持稳定的高性能

#### 调用同步网关 API

使用以下示例调用同步网关操作：

```
import requests
import json

def search_tools(gateway_url, access_token, query):
    headers = {
        "Content-Type": "application/json",
        "Authorization": f"Bearer {access_token}"
    }

    payload = {
        "jsonrpc": "2.0",
        "id": "search-tools-request",
        "method": "tools/call",
        "params": {
            "name": "x_amz_bedrock_agentcore_search",
            "arguments": {
                "query": query
            }
        }
    }

    response = requests.post(gateway_url, headers=headers, json=payload, timeout=5)
    response.raise_for_status()
    return response.json()

# Example usage
token_response = utils.get_token(user_pool_id, client_id, client_secret, scopeString, REGION)
access_token = token_response['access_token']
results = search_tools(gatewayURL, access_token, "order operations")
print(json.dumps(results, indent=2))
```

### 工具模式的隐式同步

在 `CreateGatewayTarget` 与 `UpdateGatewayTarget` 操作期间，AgentCore Gateway 会执行与显式 `SynchronizeGatewayTargets` API 不同的隐式同步。这种隐式同步确保 MCP 目标创建或更新时具备有效且最新的工具定义，与 AgentCore Gateway 所作出的“处于 READY 状态的目标即可立即使用”的保证相一致。这可能使创建/更新操作比其他目标类型耗时更长，但有助于避免出现没有经过校验的工具定义的目标所带来的复杂性与潜在问题。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/04/ML-19938-image-7.png)

隐式同步流程在以下情形下开始：

- 运维管理员使用 `CreateGatewayTarget` 或 `UpdateGatewayTarget` 操作创建或更新 MCP 目标。
- AgentCore Gateway 配置新建或更新后的 MCP 目标。
- 网关异步触发同步流程以更新工具定义。
- 网关从 AgentCore Identity 获取 OAuth token 以实现安全访问。
- 随后网关与 MCP 服务器初始化一个安全会话，以获取版本能力信息。
- 最后，网关分页调用 MCP 服务器的 tools/list 端点以检索工具定义，确保网关始终维护一份最新且准确的工具清单。

### MCP 目标的 ListTools 行为

AgentCore Gateway 中的 `ListTools` 操作提供对先前从 MCP 目标同步而来的工具定义的访问，遵循缓存优先的方式，以优先保障性能与可靠性。与工具定义静态声明的传统 OpenAPI 或 Lambda 目标不同，MCP 目标的工具是通过同步操作发现并缓存的。当客户端调用 `ListTools` 时，网关从其持久化存储中检索工具定义，而不是实时调用 MCP 服务器。这些定义此前已通过目标创建/更新期间的隐式同步，或通过显式调用 `SynchronizeGatewayTargets` API 填充完成。该操作返回分页的规范化工具定义列表。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/04/ML-19938-image-9.png)

### MCP 目标的 InvokeTool（tools/call）行为

MCP 目标的 `InvokeTool` 操作负责实际执行通过 `ListTools` 发现的工具，管理与目标 MCP 服务器的实时通信。与基于缓存的 `ListTools` 操作不同，tools/call 需要与 MCP 服务器进行主动通信，从而引入了特定的身份验证、会话管理与错误处理要求。当 tools/call 请求到达时，AgentCore Gateway 首先校验该工具存在于其已同步的定义中。对于 MCP 目标，AgentCore Gateway 会先发起 initialize 调用，与 MCP 服务器建立会话。如果目标配置了 OAuth 凭证，AgentCore Gateway 会在发起 `initialize` 调用之前，从 AgentCore Identity 获取最新凭证。这确保即便 ListTools 返回的是带过期凭证的缓存工具，实际调用仍使用有效的身份验证。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/04/ML-19938-image-11.png)

入站授权流程在以下情形下开始：

- MCP 客户端向 AgentCore Gateway 发起一个携带 MCP 协议版本的请求。
- 客户端随后向网关发送 tools/call 请求。
- 网关从 AgentCore Identity 获取 OAuth token 以实现安全访问。
- 网关与 MCP 服务器初始化一个安全会话，以调用并处理该工具的实际执行。

### MCP 目标的搜索工具行为

AgentCore Gateway 的搜索能力支持跨不同目标类型（包括 MCP 目标）对工具进行语义发现。对于 MCP 目标，搜索功能作用于同步操作期间捕获并索引的规范化工具定义，无需与 MCP 服务器实时通信即可提供高效的语义搜索。

当工具定义从 MCP 目标同步时，AgentCore Gateway 会自动为每个工具的名称、描述与参数描述生成嵌入向量。这些嵌入向量与规范化工具定义一起存储，使语义搜索能够理解搜索查询的意图与语境。与传统的关键词匹配不同，这使 agent 即便在术语并不完全一致时也能发现相关工具。

## 结语

今天宣布的将 MCP 服务器作为 Amazon Bedrock AgentCore Gateway 中的一种目标类型来支持，是企业 AI agent 开发方面的一项进步。这项新能力解决了在扩展 MCP 服务器实现时保持安全与运营效率的关键挑战。通过将现有 MCP 服务器与 REST API、Lambda 函数一同集成，AgentCore Gateway 为大规模工具集成提供了更统一、更安全且更易管理的解决方案。组织现在可以通过单一的集中式界面管理工具，同时享受统一的身份验证、简化的工具发现以及更低的维护开销。
