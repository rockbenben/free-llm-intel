# Amazon 如何使用 Amazon Nova 模型为新履约中心自动化运营准备测试

Amazon 是一家全球性的电商与科技公司，运营着庞大的履约中心网络，用于存储、处理和向全球客户发货。Amazon Global Engineering Services（GES）团队负责推动公司快速扩张的履约中心网络实现运营就绪。在启用新的履约中心时，Amazon 必须核实每个设施都配备到位并具备运营条件。这一过程称为运营准备测试（ORT），通常每个设施需要 2,000 小时的人工投入，以核实 10,500 个工作站上的 200,000 多个组件。使用 [Amazon Nova](https://aws.amazon.com/ai/generative-ai/nova) 模型，我们开发了一套自动化方案，在提升准确率的同时显著缩短核实时间。

本文讨论如何利用 [Amazon Bedrock](https://aws.amazon.com/bedrock) 中的 [Amazon Nova](https://aws.amazon.com/ai/generative-ai/nova) 实现一个 AI 驱动的图像识别方案，自动完成模块组件的检测与校验，从而显著减少人工核实工作量并提升准确率。

## 理解 ORT 流程

ORT 是一个全面的核实流程，确保在履约中心准备启用之前各组件已正确安装。物料清单（BOM）充当总检查清单，详细列出设施内每个模块应当出现的所有组件。履约中心里的每个组件或物品都会被分配一个唯一识别号（UIN），作为它的唯一标识。在 ORT 流程及之后的工作中，这些组件对于准确的追踪、核实和库存管理至关重要。本文中 UIN 与组件将互换使用。

ORT workflow 包含五个组成部分：

- **测试计划：** 测试人员收到一份测试计划，其中包含详细列出所需组件及数量的 BOM
- **实地巡检：** 测试人员在履约中心内走动，在每个模块处停留，对照 BOM 检查安装情况。模块是一个物理工作站或运营区域
- **核实：** 他们核实每个 UIN 的安装与配置是否正确
- **测试：** 他们对每个组件执行功能测试（例如供电、连通性等）
- **记录：** 他们记录每个 UIN 的结果，然后转向下一个模块

## 寻找合适的方案

我们评估了多种方案来应对 ORT 自动化挑战，重点是利用基础模型（FM）的图像识别能力。决策过程中的关键因素包括：

**图像检测能力：** 在测试了多个 AI 模型（包括 [Anthropic Claude Sonnet](https://www.anthropic.com/claude)、[Amazon Nova Pro](https://aws.amazon.com/ai/generative-ai/nova/understanding/)、[Amazon Nova Lite](https://aws.amazon.com/ai/generative-ai/nova/understanding/) 和 [Meta AI Segment Anything Model（SAM）](https://segment-anything.com/)）之后，我们选择 [Amazon Nova Pro](https://aws.amazon.com/ai/generative-ai/nova/understanding/) 来做图像检测。Nova Pro 满足了投入生产实施的标准。

**Amazon Nova Pro 的特性：**

目标检测能力

- 专为目标检测而构建
- 提供精确的边界框坐标
- 检测结果与边界框保持稳定一致

图像处理

- 内置图像缩放至固定宽高比
- 无需手动调整尺寸

性能

- 在 Amazon Bedrock 上拥有更高的每分钟请求数（RPM）配额
- 更高的每分钟 token 数（TPM）吞吐量
- 对大规模检测具有成本效益

**无服务器架构：** 我们使用 [AWS Lambda](https://aws.amazon.com/pm/lambda) 和 [Amazon Bedrock](https://aws.amazon.com/bedrock)，保持方案具备成本效益与可扩展性，且不需要复杂的基础设施管理或模型托管。

**额外的上下文理解：** 为改进检测并减少误报，我们使用 Anthropic Claude Sonnet 4.0 为每个 UIN 生成文本描述并创建检测参数。

## **方案概览**

智能运营就绪（Intelligent Operational Readiness，IORA）方案包含多个关键服务，如下面的架构图所示：

- **API Gateway：** [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 处理用户请求并路由到相应的 Lambda 函数
- **同步图像处理：** Amazon Bedrock Nova Pro 分析图像，响应时间为 2-5 秒
- **进度追踪：** 系统追踪 UIN 检测进度（每个模块已检测到的 UIN 百分比）
- **数据存储：** [Amazon Simple Storage Service（S3）](https://aws.amazon.com/s3/) 用于存储模块图像、UIN 参考图片和结果。[Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 用于存储结构化的核实数据
- **计算：** [AWS Lambda](https://aws.amazon.com/lambda/) 用于图像分析和数据操作
- **模型推理：** Amazon Bedrock 用于目标检测的实时推理，以及描述生成的批量推理

### 描述生成 pipeline

描述生成 pipeline 是共同实现 ORT 流程自动化的几个关键系统之一。第一个是描述生成 pipeline，它构建用于组件识别的标准化知识库，并在引入新模块时作为批处理运行。在履约中心拍摄的图像具有不同的光照条件和相机角度，这会影响模型稳定检测出正确组件的能力。通过使用高质量的参考图像，我们可以为每个 UIN 生成标准化描述。然后我们使用 BOM 生成检测规则，BOM 列出了每个模块中所需的 UIN 及其关联数量和规格。这一过程确保每个 UIN 都有标准化描述和合适的检测规则，为后续的检测与评估流程打下坚实基础。

workflow 如下：

- 管理员上传 UIN 图像和 BOM 数据
- Lambda 函数触发两个并行流程：  路径 A：UIN 描述生成  通过 Claude Sonnet 4.0 处理每个 UIN 的参考图像 生成详细的 UIN 描述 把多份描述合并为每个 UIN 一份描述 将合并后的描述存入 DynamoDB  路径 B：检测规则创建  把 UIN 描述与 BOM 数据结合 生成模块专属的检测规则 创建误报检测模式 将规则存入 DynamoDB

```
# UIN Description Generation Process
def generate_uin_descriptions(uin_images, bedrock_client):
    """
    Generate enhanced UIN descriptions using Claude Sonnet
    """
    for uin_id, image_set in uin_images.items():
        # First pass: Generate initial descriptions from multiple angles
        initial_descriptions = []
        for image in image_set:
            response = bedrock_client.invoke_model(
                modelId='anthropic.claude-4-sonnet-20240229-v1:0',
                body=json.dumps({
                    'messages': [
                        {
                            'role': 'user',
                            'content': [
                                {'type': 'image', 'source': {'type': 'base64', 'data': image}},
                                {'type': 'text', 'text': 'Describe this UIN component in detail, including physical characteristics, typical installation context, and identifying features.'}
                            ]
                        }
                    ]
                })
            )
            initial_descriptions.append(response['content'][0]['text'])

        # Second pass: Consolidate and enrich descriptions
        consolidated_description = consolidate_descriptions(initial_descriptions, bedrock_client)

        # Store in DynamoDB for quick retrieval
        store_uin_description(uin_id, consolidated_description)
```

### 误报检测模式

为提升输出一致性，我们通过为常见误报添加额外规则来优化 prompt。这有助于过滤掉与检测无关的对象。例如，三角标识应当带有门号（gate number）和箭头，而通用标识不应被检测出来。

```
3:
generic_object: "Any triangular sign or warning marker"
confused_with: "SIGN.GATE.TRIANGLE"
▼ distinguishing_features:
0: "Gate number text in black at top (e.g., 'GATE 2350')"
1: "Red downward-pointing arrow at bottom"
2: "Red border with white background"
3: "Black mounting system with suspension hardware"

trap_description: "Generic triangle sign ≠ SIGN.GATE.TRIANGLE without gate number and red arrow"
```

### UIN 检测评估 pipeline

该 pipeline 负责实时组件核实。我们把测试人员拍摄的图像、模块专属的检测规则以及 UIN 描述，通过 Amazon Bedrock 输入 Nova Pro。输出为检测到的 UIN 及其边界框，以及安装状态、缺陷识别结果和置信度分数。

Lambda 函数使用所选配置处理每个模块图像：

```
def detect_uins_in_module(image_data, module_bom, uin_descriptions):
    """
    Detect UINs in module images using Nova Pro
    """
    # Retrieve relevant UIN descriptions for the module
    relevant_descriptions = get_descriptions_for_module(module_bom, uin_descriptions)

    # Construct detection prompt with descriptions
    detection_prompt = f"""
    Analyze this module image to detect the following components:
    {format_uin_descriptions(relevant_descriptions)}
    For each UIN, provide:
    - Detection status (True/False)
    - Bounding box coordinates if detected
    - Confidence score
    - Installation status verification
    - Any visible defects
    """

    # Process with Amazon Bedrock Nova Pro
    response = bedrock_client.invoke_model(
        modelId='amazon.nova-pro-v1:0',
        body=json.dumps({
            'messages': [
                {
                    'role': 'user',
                    'content': [
                        {'type': 'image', 'source': {'type': 'base64', 'data': image_data}},
                        {'type': 'text', 'text': detection_prompt}
                    ]
                }
            ]
        })
    )
    return parse_detection_results(response)
```

### 端到端应用 pipeline

该应用把各部分整合起来，为履约中心的测试人员提供可直接投产的用户界面。它还提供全面的分析，包括精确的 UIN 识别、边界框坐标、安装状态核实，以及带置信度评分的缺陷检测。

反映在 UI 中的 workflow 如下：

- 测试人员从前端把图像安全地上传到 Amazon S3——可以拍照，也可以手动上传。图像在 S3 中使用 [AWS Key Management Service（AWS KMS）](https://aws.amazon.com/kms) 自动进行静态加密。
- 这会触发核实流程，调用用于 UIN 核实的 API 端点。服务之间的 API 调用使用 [AWS Identity and Access Management（IAM）](https://aws.amazon.com/ima) 基于角色的认证。
- 一个 Lambda 函数从 S3 取回图像。
- Amazon Nova Pro 从每张图像中检测所需的 UIN。
- UIN 检测结果存储在已启用加密的 DynamoDB 中。

## 结果与经验

在构建原型之后，我们使用 Amazon Kindle 平板在多个履约中心测试了该方案。在一组有代表性的测试模块上，我们达到了 92% 的精确率，每张图像的延迟为 2–5 秒。与人工运营准备测试相比，IORA 将总测试时间缩短了 60%。Amazon Nova Pro 还能识别出 ground truth 数据中缺失的标签，这让我们有机会提升数据集质量。

> “精确率的结果直接转化为时间节省 —— 40% 的覆盖率对我们的现场团队来说就等于减少 40% 的时间。当该方案检测到某个 UIN 时，我们履约中心的团队就可以放心地只专注于寻找缺失的组件。”
>         —— Wayne Jones，Amazon General Engineering Services 高级项目经理

关键经验：

- 在提供丰富上下文描述的情况下，Amazon Nova Pro 在视觉识别任务上表现出色，其准确率优于仅做独立图像比对。
- ground truth 数据质量会显著影响模型表现。该方案识别出了原始数据集中缺失的标签，并有助于改进人工标注数据。
- UIN 少于 20 个的模块表现最佳；对于 40 个或更多 UIN 的模块，我们观察到性能下降。超过 40 个组件的模块需要采用分层处理。
- 使用 Lambda 和 Amazon Bedrock 的无服务器架构提供了具备成本效益的可扩展性，且不带来基础设施复杂性。
