# IDIADA 如何借助 Amazon Bedrock 优化其智能聊天机器人

*本文与来自 Applus+ Idiada 的 Xavier Vizcaino、Diego Martín Montoro 和 Jordi Sánchez Ferrer 合写。*

2021 年，[Applus+ IDIADA](https://www.applusidiada.com/global/en/) 成立了 Digital Solutions 部门。Applus+ IDIADA 是汽车行业的全球合作伙伴，拥有 30 多年经验，通过设计、工程、测试和认证服务支持客户的产品开发活动。这一战略举措旨在通过使用数字工具和流程来推动创新。此后，我们优化了数据策略，为客户开发了定制解决方案，并为重塑行业的技术革命做好准备。

AI 现在在 Applus+ IDIADA 所处的汽车行业的开发与演进中发挥着关键作用。在这一格局中，我们开发了一个智能聊天机器人 AIDA（Applus Idiada Digital Assistant）——一个由 [Amazon Bedrock](https://aws.amazon.com/bedrock) 驱动的虚拟助手，作为 IDIADA 员工队伍的多用途伙伴。

Amazon Bedrock 是一项完全托管的服务，通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、Meta、Stability AI 和 Amazon 等领先 AI 公司的高性能基础模型（FM）选择，并提供一整套能力，让你以安全、隐私和负责任 AI 的方式构建生成式 AI 应用。

借助 Amazon Bedrock，AIDA 可以协助完成大量任务，从解答疑问到处理涉及代码、数学和翻译的复杂技术挑战。它的能力确实无限。

借助 AIDA，我们向着提供全球化、一体化数字解决方案以为客户创造价值的愿景又迈进了一步。其内部部署巩固了我们在开发数据分析、认证和车辆工程解决方案方面的领导地位。此外，IDIADA 计划在中期内将 AIDA 作为可集成产品提供给客户环境，并开发可无缝集成到现有系统中的“轻量”版本。

在本文中，我们展示使用 Amazon Bedrock 为这一基于 AI 的环境开发人类交互分类器的研究过程。目标是准确识别智能 agent 所接收的交互类型，从而把请求路由到合适的 pipeline，提供更专业、更高效的服务。

## 挑战：优化智能聊天机器人的响应、更有效地分配资源并提升整体用户体验

AIDA 构建在灵活且安全的架构之上，为集成多种数据源提供了多用途环境，包括来自企业数据库的结构化数据，以及来自 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）等内部来源的非结构化数据。它拥有与数据对话、高级检索增强生成（RAG）和 agent 等能力，可实现推理、代码执行或 API 调用等复杂任务。

随着 AIDA 与人的交互激增，建立一个连贯的系统来对这些多样化的交流进行分类，变得十分迫切。

最初，用户向 AIDA 提出的是简单查询，但随着时间推移，他们开始要求更具体、更复杂的任务。这些任务包括文档翻译、关于 IDIADA 内部服务的咨询、文件上传以及其他专门请求。

进行这种分类的主要原因是开发能够更有效处理各类请求的独立 pipeline。通过把交互分门别类，AIDA 可以被优化以更高效地处理特定类型的任务。这种方式可以为不同类型的用户需求提供定制化的响应和流程，无论是简单问题、文档翻译，还是关于 IDIADA 服务的复杂咨询。

首要目标是通过为对话、文档翻译和服务等不同场景创建专用 pipeline，提供更专业的服务，从而为用户日益多样化和专业化的请求给出更准确、更相关、更高效的响应。

## 解决方案概览

通过把交互分为三大类——对话、服务和文档翻译，系统可以更好地理解用户意图并相应作答。`Conversation` 类涵盖一般性咨询和交流，`Services` 类涵盖对特定功能或支持的请求，`Document_Translation` 类处理文本翻译需求。

为每种用例专门设计的专用 pipeline，可以显著提升 AIDA 响应的效率和准确性。这通过几种方式实现：

- **提升效率** – 通过为特定类型的任务配备专用 pipeline，AIDA 可以更快地处理请求。每个 pipeline 都针对其特定用例进行了优化，从而减少了生成合适响应所需的计算时间。
- **提高准确性** – 专用 pipeline 配备了针对每类任务的专用工具和知识。这使 AIDA 能够提供更准确、更相关的响应，因为它为每类请求使用了最合适的资源。
- **优化资源配置** – 通过对交互进行分类，AIDA 可以更高效地分配计算资源，为每类任务分配合适的处理能力。
- **缩短响应时间** – 更高的效率与优化的资源配置相结合，带来更快的用户响应时间。
- **增强适应性** – 该系统让 AIDA 能更好地适应不同类型的请求，从简单查询到文档翻译或关于 IDIADA 服务的专门咨询等复杂任务。

基于大语言模型（LLM）的这一分类器的研究与开发，是在 Applus IDIADA 环境中持续提升智能 agent 能力的重要一步。

这一次，我们使用了一个包含 1,668 条预先分类的人类交互示例的数据集。这些示例被划分为 666 条用于训练、1,002 条用于测试。采用了 40/60 的划分，赋予测试集相当重要的权重。

## 基于 LLM 的分类器：简单 prompt

在本例中，我们开发了一个基于 LLM 的分类器，把输入归入三个类别：`Conversation`、`Services` 和 `Document_Translation`。我们不依赖预定义的刚性定义，而是遵循“通过集合来理解”的原则。该原则包括分析属于每个类别的示例或实例中共有的特征和模式。通过研究一个类别内输入的共同特征，我们可以推导出对该类别本身的理解，而不受先入之见的束缚。

需要注意的是，学到的定义可能与通常的预期不同。例如，`Conversation` 类不仅包含典型的对话式交流，还包括文本摘要等任务，因为它们在语言和上下文特征上与对话输入相似。

通过遵循这种数据驱动的方式，分类器可以根据新输入与各类别所学特征的相似性来准确归类，捕捉每个类别中的细微差别和多样性。

该代码由以下关键部分组成：库、prompt、模型调用和输出解析器。

### 库

该代码使用的编程语言是 Python，并辅以 LangChain 模块，后者专为便于集成和使用 LLM 而设计。该模块提供了一套全面的工具和抽象，简化了这些先进 AI 模型的整合与部署过程。

为了发挥这些语言模型的能力，我们使用 Amazon Bedrock。与 Amazon Bedrock 的集成通过 Boto3 Python 模块实现，该模块作为访问 AWS 的接口，从而能够与 Amazon Bedrock 顺畅交互并部署分类模型。

### Prompt

任务是为给定的句子（由 `question:` 表示）分配三个类别之一（`Conversation`、`Services` 或 `Document_Translation`）。

- **Conversation 类** – 该类涵盖闲聊消息、摘要请求、一般性问题、肯定回应、问候及类似文本。它还包括文本翻译请求、摘要请求，或对特定语言中单词或句子含义的明确询问。
- **Services 类** – 属于该类的文本由明确的服务请求构成，例如房间预订、酒店预订、餐饮服务、影院信息、旅游相关咨询以及类似的服务导向请求。
- **Document_Translation 类** – 该类的特征是请求把文档翻译成特定语言。与 `Conversation` 类不同，这些请求不涉及摘要。此外，还要指明待翻译文档的名称和目标语言。

该 prompt 提示了一种分层式的分类流程。首先，应评估该句子，判断它能否被归类为对话。如果该句子不符合 `Conversation` 类，则应分配另外两个类别之一（`Services` 或 `Document_Translation`）。

优先考虑 `Conversation` 类的原因在于，99% 的交互实际上是关于各类事务的简单问题。

### 模型调用

我们使用 Anthropic 的 Claude 3 Sonnet 模型来完成自然语言处理任务。该 LLM 具有 200,000 token 的上下文窗口，能够处理多种语言并检索高度准确的答案。我们使用两个关键参数：

- **max_tokens** – 该参数把语言模型在输出中可生成的 token（单词或子词）最大数量限制为 50。
- **temperature** – 该参数控制语言模型输出的随机性。温度为 0.0 表示模型将根据其训练产生最可能的输出，不引入随机性。

### 输出解析器

另一个重要组件是输出解析器，它让我们能够以 JSON 格式收集所需信息。为此，我们使用 LangChain 的 `output_parsers` 参数。

以下代码展示了简单 prompt 的实现方式：

```
def classify_interaction(question):
   response_schemas = [
        ResponseSchema(name="class", description="the assigned class")
    ]
    output_parser = StructuredOutputParser.from_response_schemas(response_schemas)
    format_instructions = output_parser.get_format_instructions()
    prompt =f"""
    We have 3 classes Conversation (for example asking for assistance), Services and Document_Translation.
    Conversation:text consist of casual messages, summarization requests, general questions, afirmations, greetings, 
    and similar. Requests for text translation, text summarisation or explicit text translation requests, 
    questions about the meaning of words or sentences in a concrete language.
    Services:the text consist of explicit requests for rooms, hotels, eating services, cinema, tourism, and similar.
    Document_Translation: A translation of a document to a specific language is requested, and a summary is not requested. 
    The length of the document is specified.
    Assign a class to the following sentence.
    {question}
    Try to understand the sentence as a Conversation one, if you can't, then asign one of the other classes.
    {format_instructions} 
    """          
    response = bedrock_runtime.invoke_model(
            modelId='anthropic.claude-3-sonnet-20240229-v1:0',
            body=json.dumps(
                {
                    "anthropic_version": "bedrock-2023-05-31",
                    "max_tokens": 20,
                    "temperature":0,
                    "messages": [
                        {
                            "role": "user",
                            "content": [{"type": "text", "text": prompt}],
                        }
                    ],
                }
            ),
        )
    result_message = json.loads(response.get("body").read())
    texto = result_message['content'][0]['text']
    try:
        output_dict = output_parser.parse(texto.replace('\'', '"'))['class']
    except:
        output_dict = 'Conversation' 
    return output_dict
```

## 基于 LLM 的分类器：示例增强推理

我们使用 RAG 技术来增强模型的响应能力。我们不只依赖压缩的定义，而是通过外延的方式为模型提供一种准定义。具体来说，我们为每个类别向模型呈现一组多样化的示例，让它学习界定每个类别的内在特征和模式。例如，除了对 `Conversation` 类的简明定义之外，模型还会接触到各种对话式输入，从而能够识别诸如非正式语言、开放式问题、来回往复的交流等共同特征。这种以示例驱动的方式补充了所提供的初始描述，让模型能够捕捉每个类别中的细微差别和多样性。通过把简明定义与代表性示例相结合，RAG 技术帮助模型更全面地理解这些类别，增强其根据新输入的内在本质和特征进行准确归类的能​​力。

以下代码以 JSON 格式提供用于 RAG 的示例：

```
{
    "Conversation":[
       ""Could you give me examples of how to solve it?",
       "cool but anything short and sweet",
       "..."
    ],
    "Services":[
       "make a review of my investments in the eBull.com platform",
       "I need a room in IDIADA",
       "schedule a meeting with",
       "..."
    ]"Document_Translation":[
       "Translate the file into Catalan",
       "Could you translate the document I added earlier into Swedish?",
       "Translate the Guía_Rápida.doc file into Romanian",
       "..."
    ]
 }
```

为每个类别提供的示例总数如下：

- **Conversation** – 500 个示例。这是最常见的类别，但由于信息量庞大，只向模型提供 500 个样本，否则可能造成基础设施溢出（极高的延迟、限流、连接中断）。这是一个需要注意的关键点，因为它代表着显著的瓶颈。为该方式提供更多示例有可能提升性能，但问题依然存在：需要多少示例？显然，需要相当大的数量。
- **Services** – 26 个示例。这是最不常见的类别，在这种情况下已使用了全部可用的训练数据。
- **Document_Translation** – 140 个示例。同样，该类别已使用了全部可用的训练数据。

这种方式的关键挑战之一是可扩展性。尽管模型性能会随着训练示例的增多而提升，但计算需求会迅速超出我们当前基础设施的承受能力。所需数据量之大会导致 Amazon Bedrock 出现配额问题，以及不可接受的长响应时间。快速响应时间对于提供令人满意的用户体验至关重要，而这种方式在这方面表现不足。

在这种情况下，我们需要修改代码以嵌入所有示例。以下代码展示了应用于分类器第一版的改动。prompt 已修改为在“Here you have some examples”部分下以 JSON 格式包含所有示例。

```
def classify_interaction(question, agent_examples):
    response_schemas = [
        ResponseSchema(name="class", description="the assigned class")
    ]
    output_parser = StructuredOutputParser.from_response_schemas(response_schemas)
    format_instructions = output_parser.get_format_instructions()
    prompt =f"""
    We have 3 classes Conversation (for example asking for assistance), Services and Document_Translation.
    Conversation:text consist of casual messages, summarization requests, general questions, afirmations, greetings, 
    and similar. Requests for text translation, text summarisation or explicit text translation requests, 
    questions about the meaning of words or sentences in a concrete language.
    Services:the text consist of explicit requests for rooms, hotels, eating services, cinema, tourism, and similar.
    Document_Translation: A translation of a document to a specific language is requested, and a summary is not requested. 
    The length of the document is specified.
    
    Here you have some examples:
    {agent_examples}

    Assign a class to the following sentence.
    {question}

    Try to understand the sentence as a Conversation one, if you can't, then asign one of the other classes.
    {format_instructions}   
    """
    
    response = bedrock_runtime.invoke_model(
            modelId='anthropic.claude-3-sonnet-20240229-v1:0',
            body=json.dumps(
                {
                    "anthropic_version": "bedrock-2023-05-31",
                    "max_tokens": 50,
                    "messages": [
                        {
                            "role": "user",
                            "content": [{"type": "text", "text": prompt}],
                        }
                    ],
                }
            ),
        )

    result_message = json.loads(response.get("body").read())
    texto = result_message['content'][0]['text']
    output_dict = output_parser.parse(texto.replace('\'', '"'))['class']
    
    return output_dict
```

## 基于 K-NN 的分类器：Amazon Titan Embeddings

在本例中，我们采用另一种方式，认识到尽管可能的交互数量庞大，它们往往具有相似性和重复模式。我们不再把每个输入视为完全独特，而是可以使用诸如 k 最近邻（k-NN）这样的基于距离的方式，根据输入周围最相似的示例来分配类别。为此，我们需要把文本交互转换为一种允许代数运算的格式。这正是嵌入的用武之地。嵌入是文本的向量表示，可捕捉语义和上下文信息。通过把文本转换为这些向量表示、比较它们的向量并确定它们在嵌入空间中的接近程度，我们可以计算不同交互之间的语义相似度。

为适应这种方式，我们需要相应地修改代码：

```
from langchain.embeddings import BedrockEmbeddings
from sklearn.neighbors import KNeighborsClassifier

bedrock_runtime = boto3.client(
    service_name='bedrock-runtime',
    region_name='us-west-2'
)

bedrock_embedding = BedrockEmbeddings(
    client=bedrock_runtime,
    model_id="amazon.titan-embed-text-v1",
)
df_train = pd.read_excel('coordinator_dataset/casos_coordinador_train.xlsx')
df_test = pd.read_excel('coordinator_dataset/casos_coordinador_test.xlsx')

X_train_emb = bedrock_embedding.embed_documents(df_train['sample'].values.tolist())
X_test_emb = bedrock_embedding.embed_documents(df_test['sample'].values.tolist())
y_train = df_train['agent'].values.tolist()
y_test = df_test['agent'].values.tolist()
neigh = KNeighborsClassifier(n_neighbors=3)
neigh.fit(X_train_emb, y_train)
y_pred = neigh.predict(X_test_emb)
print(classification_report(y_test, y_pred, target_names=['Conversation', 'Document_Translation', 'Services']))
```

我们使用了 Amazon Titan Text Embeddings G1 模型，它生成 1,536 维的向量。该模型经训练可接受多种语言，同时保留所嵌入短语的语义。

对于分类器，我们采用经典的 ML 算法 k-NN，使用 scikit-learn Python 模块。该方法接受一个参数，我们将其设为 3。

下图展示了各类别的 F1 分数随 k-NN 算法中所用邻居数（k）的变化。如图所示，k 的最优值为 3，可为此类别中占比最高的 `Document_Translation` 带来最高的 F1 分数。尽管这并非 `Services` 类的绝对最高分，但 `Document_Translation` 明显更为常见，因此 k=3 是最大化所有类别整体性能的最佳选择。

## 基于 K-NN 的分类器：Cohere 的多语言嵌入模型

在上一节中，我们使用流行的 Amazon Titan Text Embeddings G1 模型生成文本嵌入。然而，其他模型可能提供不同的优势。在本节中，我们探索在 Amazon Bedrock 上使用 Cohere 的多语言模型来生成嵌入。我们选择 Cohere 模型，是因为它在处理多种语言方面表现出色，且不会损害短语的向量化。正如我们将要展示的，与其他模型相比，该模型在生成的向量上并没有引入显著差异，这使其更适合在像 AIDA 这样的多语言环境中使用。

要使用 Cohere 模型，我们需要修改 `model_id`：

```
from langchain.embeddings import BedrockEmbeddings
from sklearn.neighbors import KNeighborsClassifier

bedrock_runtime = boto3.client(
    service_name='bedrock-runtime',
    region_name='us-west-2'
)

bedrock_embedding = BedrockEmbeddings(
    client=bedrock_runtime,
    model_id=" cohere.embed-multilingual-v3",
)
df_train = pd.read_excel('coordinator_dataset/casos_coordinador_train.xlsx')
df_test = pd.read_excel('coordinator_dataset/casos_coordinador_test.xlsx')
data_train = [s[:1500] for s in df_train['sample']]
data_test = [s[:1500] for s in df_test['sample']]

y_train = df_train['agent'].values.tolist()
y_test = df_test['agent'].values.tolist()
X_test = df_test['sample'].values.tolist()

X_train_emb = bedrock_embedding.embed_documents(data_train)
X_test_emb = bedrock_embedding.embed_documents(data_test)

neigh = KNeighborsClassifier(n_neighbors=11)
neigh.fit(X_train_emb, y_train)
y_pred = neigh.predict(X_test_emb)
print(classification_report(y_test, y_pred, target_names=['Conversation', 'Document_Translation', 'Services']))
```

我们使用 Cohere 的多语言嵌入模型生成 1,024 维的向量。该模型经训练可接受多种语言，并保留所嵌入短语的语义。

## 基于 SVM 的分类器：Amazon Titan Embeddings

在此场景中，属于三大类别（`Conversation`、`Services` 和 `Document_Translation`）的用户交互很可能在嵌入空间中形成不同的簇或组。每个类别都具有特定的语言和语义特征，这些特征会体现在嵌入向量的几何结构中。此前对嵌入空间的可视化只展示了该空间的一个二维变换。这并不意味着这些簇在更高维度上无法高度可分。

支持向量机（SVM）等分类算法尤其适合利用数据的这种隐式几何结构。SVM 力求找到能在嵌入空间中分隔不同组或类别的最优超平面，并最大化它们之间的间隔。SVM 利用数据底层几何结构的这种能力，使其成为这一用户交互分类问题的有趣选项。

此外，SVM 是一种稳健且高效的算法，能够有效处理高维数据集，例如文本嵌入。这使其特别适合本场景，因为用户交互的嵌入向量预期具有较高的维度。

以下代码展示了实现：


我们使用 Amazon Titan Text Embeddings G1。该模型生成 1,536 维的向量，经训练可接受多种语言，并保留所嵌入短语的语义。

为实现分类器，我们采用经典的 ML 算法 SVM，使用 scikit-learn Python 模块。SVM 算法需要调优多个参数才能达到最佳性能。为确定最佳参数值，我们使用 F1 多类分数作为评估指标，进行了 10 折交叉验证的网格搜索。这种系统化的方式让我们识别出以下能为分类器带来最高性能的参数组合：

- **C** – 我们将该参数设为 1。该参数控制允许训练误差与强制刚性间隔之间的权衡。它充当正则化参数。C 值越高（例如 10）表示对误分类错误的惩罚越大。这会产生一个更复杂的模型，试图更紧密地拟合训练数据。当数据中的类别分隔良好时，较高的 C 值可能有益，因为它允许算法构建更精细的决策边界以准确分类样本。另一方面，C 值为 1 表示在拟合训练集与模型泛化能力之间取得合理平衡。当数据结构简单、不需要更灵活的模型来捕捉底层关系时，该值可能是合适的。在我们的情况下，所选的 C 值为 1 表明数据结构相对简单，具有中等复杂度的平衡模型足以实现准确分类。
- **class_weight** – 我们将该参数设为 `None`。该参数在训练过程中调整各类别的权重。将 `class_weight` 设为 `balanced` 会自动按与输入数据中类别频率成反比的方式调整权重。这在处理类别不平衡的数据集时特别有用，即某一类明显比其他类更普遍。在我们的情况下，`class_weight` 参数取值为 `None` 表明次要类别对整体分类任务没有太大相关性或影响。这一选择意味着模型学到的隐式几何结构或决策边界可能并未针对有效区分不同类别进行优化。
- **Kernel** – 我们将该参数设为 `linear`。该参数指定 SVC 算法使用的核函数类型。`linear` 核是一个简单而高效的选择，因为它假设类别之间的决策边界可以在特征空间中由一个线性超平面表示。该取值表明，在更高维的向量空间中，这些类别可以由一个超平面线性分开。

## 基于 ANN 的分类器：Amazon Titan 与 Cohere 的多语言嵌入模型

鉴于使用 SVM 取得了令人鼓舞的结果，我们决定通过采用人工神经网络（ANN）方式来探索另一种基于几何的方法。

在本例中，我们对输入向量执行了归一化，以利用使用神经网络时归一化带来的优势。在使用 ANN 时，对输入数据进行归一化是关键步骤，因为它有助于在训练期间改善模型的表现。我们应用了最小/最大缩放进行归一化。

使用基于 ANN 的方式能够捕捉数据中复杂的非线性关系，而这些关系可能难以用 SVM 等传统线性方法建模。将几何洞察与输入归一化相结合，有可能比之前的 SVM 结果带来更好的预测准确性。

该方式由以下参数构成：

- **模型定义** – 我们使用 TensorFlow 的 Keras 库定义一个顺序式深度学习模型。
- **模型架构** – 该模型由三个全连接层组成。第一层有 16 个神经元并使用 ReLU 激活函数。第二层有 8 个神经元并使用 ReLU 激活函数。第三层有 3 个神经元并使用 softmax 激活函数。
- **模型编译** – 我们使用 `categorical_crossentropy` 损失函数、学习率为 0.01 的 Adam 优化器以及 `categorical_accuracy` 来编译模型。我们加入了 `EarlyStopping` 回调，如果 `categorical_accuracy` 指标在 25 个 epoch 内没有改善就停止训练。
- **模型训练** – 我们使用训练集对模型最多训练 500 个 epoch，并在测试集上验证。批量大小设为 64。所用的性能指标是训练期间获得的最大分类准确率（`categorical_accuracy`）。

```
    return result
```
