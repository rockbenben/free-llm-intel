# Amazon Bedrock 的有效成本优化策略

客户越来越频繁地使用[生成式 AI](https://aws.amazon.com/ai/generative-ai/)来提升效率、个性化体验，并推动各行业的创新。例如，生成式 AI 可用于执行文本摘要、支撑个性化的营销策略、构建业务关键的聊天式助手，等等。然而，随着生成式 AI 的采用规模扩大，相关成本也可能在多个方面攀升，包括推理、部署和模型自定义的成本。有效的成本优化有助于确保生成式 AI 计划在财务上保持可持续，并带来正向的投资回报。主动的成本管理让企业能够充分利用生成式 AI 的变革潜力，同时维持自身的财务健康。

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 是一项完全托管的服务，通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、DeepSeek、Luma、Meta、Mistral AI、Stability AI 和 Amazon 等领先 AI 公司的多种高性能[基础模型](https://aws.amazon.com/what-is/foundation-models/)（FM），并提供构建生成式 AI 应用所需的一整套能力，涵盖安全、隐私和[负责任的 AI](https://aws.amazon.com/ai/responsible-ai/)。借助 Amazon Bedrock，你可以针对自己的用例试验和评估顶级 FM，使用微调和[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）等技术以你的数据对其进行私有化自定义，并构建能够使用企业系统和数据源执行任务的 agent。

随着 Amazon Bedrock 的采用日益广泛，优化成本已成为必需之举，以帮助将部署和运行生成式 AI 应用相关的支出保持在可控范围内，并与组织的预算保持一致。在本文中，你将了解使用 Amazon Bedrock 时的战略性成本优化技术。

## 了解 Amazon Bedrock 定价

Amazon Bedrock 提供基于 FM 及相关服务实际用量的全面定价模型。核心定价组成部分包括模型推理（提供按需、批量和预置吞吐量三种选项）、模型自定义（对训练、存储和推理收费）以及自定义模型导入（导入免费，但对推理和存储收费）。通过 [Amazon Bedrock Marketplace](https://aws.amazon.com/bedrock/marketplace/)，你可以访问 100 多个模型，专有模型和公开模型的定价结构各不相同。你可以查看 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)以了解定价概览和关于定价模型的更多细节。

## Amazon Bedrock 中的成本监控

你可以使用以下方法监控 Amazon Bedrock 用量的成本：

- **应用程序推理配置文件** – Amazon Bedrock 提供应用程序推理配置文件，你可以用它们应用自定义的[成本分配标签](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-alloc-tags.html)，以跨不同工作负载和租户跟踪、管理和控制按需 FM 的成本与用量。
- **成本分配打标签** – 你可以[为所有 Amazon Bedrock 模型打标签](https://docs.aws.amazon.com/bedrock/latest/userguide/tagging.html)，把用量对齐到成本中心、业务部门、团队和应用等特定的组织分类法，从而实现精确的费用跟踪。要执行打标签操作，你需要[Amazon Resource Name](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference-arns.html)（ARN），也就是你希望在其上执行打标签操作的那个资源。
- **与 AWS 成本工具集成** – Amazon Bedrock 的成本监控可与 [AWS Budgets](https://aws.amazon.com/aws-cost-management/aws-budgets/)、[AWS Cost Explorer](https://aws.amazon.com/aws-cost-management/aws-cost-explorer/)、[AWS Cost and Usage Reports](https://aws.amazon.com/aws-cost-management/aws-cost-and-usage-reporting/) 和 [AWS Cost Anomaly Detection](https://aws.amazon.com/aws-cost-management/aws-cost-anomaly-detection/) 集成，[使组织能够设置基于标签的预算、在用量达到阈值时收到告警，并检测异常的支出模式](https://aws.amazon.com/blogs/machine-learning/track-allocate-and-manage-your-generative-ai-cost-and-usage-with-amazon-bedrock/)。
- [**Amazon CloudWatch**](https://aws.amazon.com/cloudwatch/)** 指标监控** – 组织可以使用 [Amazon CloudWatch 监控 Amazon Bedrock 应用的运行时指标](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring.html)，按推理配置文件查看，基于阈值设置告警，并接收通知以实时管理资源用量和成本。你可以使用 Amazon CloudWatch 监控 Amazon Bedrock 应用的所有部分，它收集原始数据并将其处理为可读的准实时指标。你可以使用 CloudWatch 的 [AWS 管理控制台](https://aws.amazon.com/console/)绘制指标图表。你还可以设置告警，监视特定阈值，并在数值超过这些阈值时发送通知或采取行动。
- **特定资源可见性** – CloudWatch 提供 `Invocations`、`InvocationLatency`、`InputTokenCount`、`OutputTokenCount` 等指标以及各类错误指标，这些指标可按模型 ID 和其他维度过滤，从而对 Amazon Bedrock 的用量和性能进行细粒度监控。

### 为你的用例选择合适的模型

Amazon Bedrock 通过单一 API 提供[多样化的 FM 组合](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)。该服务不断以新的模型和提供商扩充其供给，每个模型和提供商都有不同的定价结构和能力。

例如，考虑美国东部（俄亥俄）[AWS 区域](https://docs.aws.amazon.com/glossary/latest/reference/glos-chap.html#region)中 [Amazon Nova](https://aws.amazon.com/nova/) 模型之间按需定价的差异。此定价截至 2025 年 5 月 21 日有效。有关最新数据，请参阅 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)页面。

Amazon Bedrock 的关键优势之一是其统一 API，它抽象掉了使用不同模型的复杂性。你只需在请求中更改模型 ID，就能以最少的代码修改在模型之间切换。借助这种灵活性，你可以选择最符合自身成本和性能要求、且满足需求的模型，并且只在必要时升级。

**最佳实践：**使用 Amazon Bedrock 的原生功能来评估[基础模型在你的用例中的性能](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html)。先运行自动模型评估作业来缩小范围。随后根据用例需要，使用 [LLM as a judge](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-judge.html) 或[人工评估](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-human.html)。

### 按正确顺序执行模型自定义

在 Amazon Bedrock 中为让回答贴合上下文而自定义 FM 时，按正确顺序选择策略可以在最大化性能的同时显著降低支出。你有四种主要策略可用，每种都有不同的成本影响：

- [**Prompt Engineering**](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-engineering-guidelines.html) – 首先编写高质量的 prompt，有效地引导模型生成期望的回答。这种方法所需资源极少，除标准的推理调用之外没有额外的基础设施成本。
- [**RAG**](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html) – [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 是一项完全托管的功能，内置会话上下文管理和来源归属，可帮助你在不必构建自定义数据源集成、也不必管理数据流的情况下，实现从数据摄入到检索与 prompt 增强的整个 RAG 工作流。
- [**Fine-tuning**](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-model-fine-tuning.html) – 这种方法需要提供带标签的训练数据，以提升模型在特定任务上的性能。尽管它很有效，但微调需要额外的计算资源，并会生成带有相关托管成本的自定义模型版本。
- [**Continued pre-training**](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-model-fine-tuning.html) – 资源消耗最大的选项，需要提供未标注数据，让 FM 在特定领域的内容上继续训练。这种方法成本最高、实施时间最长。

**最佳实践：**逐步实施这些策略。以 prompt 工程作为你的基础——它成本效益高，往往能以最小的投入带来令人印象深刻的结果。参阅“针对清晰简洁的 prompt 进行优化”一节，了解编写良好 prompt 可以遵循的不同策略。接下来，当你需要把专有信息纳入回答时，集成 RAG。这两者结合起来应能覆盖大多数用例，同时保持高效的成本结构。只有当你有前两种方法无法满足的特定需求，且用例足以证明额外支出合理时，才去探索微调和持续预训练。

### 使用 Amazon Bedrock 原生模型蒸馏功能

[Amazon Bedrock Model Distillation](https://aws.amazon.com/bedrock/model-distillation/) 是一项强大的功能，你可以用它获得更小、更具成本效益的模型，同时不牺牲针对具体用例的性能和准确度。

- **提升更小（学生）成本效益模型的准确度** – 借助 Amazon Bedrock Model Distillation，你可以选择一个教师模型，达到你希望在自己的用例中实现的准确度水平，然后选择一个想要微调的学生模型。模型蒸馏会自动完成整个过程：从教师模型生成回答，再用这些回答微调学生模型。
- **通过专有数据合成最大化蒸馏模型的性能** – 针对你的具体用例，把更小、更省成本的模型微调到接近更大模型的准确度，是一个迭代过程。为减轻达成更好结果所需的迭代负担，Amazon Bedrock Model Distillation 可能会选择应用最适合你用例的不同数据合成方法。例如，Amazon Bedrock 可能通过生成相似的 prompt 来扩充训练数据集，也可能以客户提供的 prompt-回答对作为黄金示例，生成高质量的合成回答。
- **通过引入你的生产数据降低成本** – 使用传统微调时，你必须创建 prompt 和回答。而借助 Amazon Bedrock Model Distillation，你只需提供 prompt，这些 prompt 会被用来生成合成回答并微调学生模型。

**最佳实践：**当你有一个具体、定义明确的用例，其中更大的模型表现良好但成本超出预期时，考虑使用模型蒸馏。这种方法对高用量推理场景尤其有价值，因为持续的成本节省会很快抵消在蒸馏上的初始投入。

### 使用 Amazon Bedrock 智能 prompt 路由

借助 [Amazon Bedrock Intelligent Prompt Routing](https://aws.amazon.com/bedrock/intelligent-prompt-routing/)，你现在可以在调用模型时组合使用同一模型家族中的多个 FM，以帮助在质量和成本之间取得优化。例如，你可以根据 prompt 的复杂程度，在 Anthropic 的 Claude 模型家族内部——在 Claude 3.5 Sonnet 和 Claude 3 Haiku 之间——进行路由。这对客服助手这类应用尤其有用：不复杂的查询可以由更小、更快、更具成本效益的模型处理，而复杂查询则被路由到能力更强的模型。智能 prompt 路由可以在不牺牲准确度的情况下将成本最多降低 30%。

**最佳实践：**为需要处理各种复杂程度查询的应用实施[智能 prompt 路由](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.html)。

### 针对清晰简洁的 prompt 进行优化

在 Amazon Bedrock 中针对清晰和简洁优化 prompt，侧重于与模型进行结构化、高效的沟通，以最小化 token 用量并最大化回答质量。通过清晰的指令、特定的输出格式和精确的角色定义等技巧，你可以获得更好的结果，同时降低与 token 消耗相关的成本。

- **结构化指令** – 把[复杂的 prompt 拆解为清晰的编号步骤或要点](https://docs.aws.amazon.com/bedrock/latest/userguide/design-a-prompt.html#prompt-instructions)。这有助于模型遵循逻辑顺序，并提高回答的一致性，同时减少 token 用量。
- **输出规范** – 明确[定义回答所需的格式和约束](https://docs.aws.amazon.com/bedrock/latest/userguide/design-a-prompt.html#prompt-output-indicators)。例如，指定字数限制、格式要求，或使用 `Please provide a brief summary in 2-3 sentences` 这样的指示来控制输出长度。
- **避免冗余** – 移除不必要的上下文和重复的指令。让 prompt 聚焦于基本信息和要求，因为多余的内容会增加成本，并可能让模型困惑。
- **使用分隔符** – [采用清晰的分隔符](https://docs.aws.amazon.com/bedrock/latest/userguide/design-a-prompt.html#prompt-separators)（例如三引号、短横线或 XML 风格标签）来分隔 prompt 的不同部分，帮助模型区分上下文、指令和示例。
- **角色与上下文精度** – 从清晰的角色定义和与任务相关的具体上下文开始。例如，`You are a technical documentation specialist focused on explaining complex concepts in simple terms` 比泛化的角色描述提供了更好的指引。

**最佳实践：**Amazon Bedrock 提供一项完全托管的功能，可针对选定的模型[优化 prompt](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-management-optimize.html)。这通过提升 prompt 的效率和有效性来降低成本，以更少的 token 和模型调用获得更好的结果。prompt 优化功能会自动让你的 prompt 遵循每个特定模型的最佳实践，从而免去可能需要数月实验的大量手动 prompt 工程。使用 Amazon Bedrock 中内置的 prompt 优化功能上手，并根据需要进一步优化以获得更好的结果。试验 prompt，使其清晰简洁，在不损害回答质量的前提下减少 token 数量。

### 使用 Amazon Bedrock prompt 缓存优化成本与性能

你可以在 Amazon Bedrock 上对受支持的模型使用 [prompt 缓存](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)，以降低推理响应延迟和输入 token 成本。通过把部分上下文加入缓存，模型可以利用缓存跳过对输入的重复计算，使 Amazon Bedrock 得以分享计算节省，并降低你的响应延迟。

- **显著降低成本** – 与标准模型推理成本相比，prompt 缓存可将成本最多降低 90%，因为缓存 token 的计费费率低于未缓存的输入 token。
- **理想用例** – prompt 缓存对上下文长且重复的应用尤其有价值，例如用户针对同一文档提出多个问题的文档问答系统，或维护代码文件上下文的编码助手。
- **改善延迟** – 对受支持的模型，实施 prompt 缓存可消除重新处理已见内容的需要，将响应延迟最多降低 85%，使应用响应更及时。
- **缓存保留期** – 每次访问后，缓存内容最多可保留 5 分钟，计时器会在每次成功命中缓存时重置，这使其非常适合围绕同一上下文的多轮对话。
- **实施方式** – 要实施 prompt 缓存，开发者需要找出被频繁复用的 prompt 部分，在 API 调用中使用 cachePoint 块标记这些区段，并在响应元数据中监控缓存使用指标（`cacheReadInputTokenCount` 和 `cacheWriteInputTokenCount`）以优化性能。

**最佳实践：**prompt 缓存在应用反复处理同一上下文的场景中很有价值，例如多个用户查询相同内容的文档问答系统。在处理不常变化的稳定上下文、围绕相同信息的多轮对话、需要快速响应的应用、请求重复的高用量服务，或在不牺牲模型性能的前提下成本优化至关重要的系统时，这项技术能带来最大收益。

### 在客户端应用内缓存 prompt

客户端 prompt 缓存通过在应用本地存储常用的 prompt 和回答来帮助降低成本。这种方法最小化了对 Amazon Bedrock 模型的 API 调用，从而带来显著的成本节省并改善应用性能。

- **本地存储实现** – 在应用内实现缓存机制，存储常用 prompt 及其对应的回答，可使用内存缓存（Redis、Memcached）或[应用级缓存](https://aws.amazon.com/caching/general-cache/)系统等技术。
- **缓存命中优化** – 在向 Amazon Bedrock 发起 API 调用之前，检查本地缓存中是否已存在该 prompt 或类似的变体。这减少了对 FM 的可计费 API 调用次数，直接影响成本。你可以查看[缓存最佳实践](https://aws.amazon.com/caching/best-practices/)了解更多。
- **过期策略** – 实施基于时间的缓存过期策略，例如 Time To Live（TTL），以帮助确保缓存回答在保持成本收益的同时仍然有效。这与 Amazon Bedrock 为实现最优成本节省而使用的 5 分钟缓存窗口一致。
- **混合缓存方式** – 将客户端缓存与 Amazon Bedrock 内置的 prompt 缓存结合使用，以实现最大程度的成本优化。精确匹配使用本地缓存，部分上下文复用使用 Amazon Bedrock 缓存。
- **缓存监控** – 实施缓存命中与未命中比率的监控，以持续优化你的缓存策略，并找出通过复用缓存 prompt 进一步降低成本的机会。

**最佳实践：**在性能关键的系统和高流量网站中，客户端缓存可以改善响应时间和用户体验，同时最小化对持续的 Amazon Bedrock API 交互的依赖。

### 构建相互交互的小而专注的 agent，而不是单个大型单体 agent

在 Amazon Bedrock 中创建相互交互的小型专用 agent，可以带来显著的成本节省，同时提升方案质量。这种方法利用 Amazon Bedrock 的[多 agent 协作](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-multi-agent-collaboration.html)能力，构建更高效、更具成本效益的生成式 AI 应用。

**多 agent 架构的优势**：你可以使用 Amazon Bedrock 多 agent 协作来编排多个专用 AI agent，让它们协同解决复杂的业务问题。通过创建更小、专为特定目的构建的 agent 而不是单个大型 agent，你可以：

- **根据具体任务优化模型选择** – 对更简单的任务使用更经济的 FM，把高级模型保留给复杂的推理任务
- **启用并行处理** – 多个专用 agent 可以同时处理问题的不同方面，缩短总体响应时间
- **提升方案质量** – 每个 agent 专注于自己的专长，从而带来更准确、更相关的回答

**最佳实践：**为每个专用 agent 选择合适的模型，在优化成本的同时让能力匹配任务要求。根据任务的复杂程度，你可以选择低成本模型或高成本模型来优化成本。使用仅检索必要数据的 [AWS Lambda](https://aws.amazon.com/lambda) 函数，以减少 Lambda 执行中不必要的成本。用一个轻量的 supervisor agent 编排你的系统，它能够高效处理协调工作而不消耗高级资源。

### 根据用量选择所需的吞吐量

Amazon Bedrock 提供两种不同的吞吐量选项，各自面向不同的使用模式和需求：

- **按需模式** – 提供无需前期承诺的按用量付费方式，非常适合开发与测试环境中的早期概念验证（POC），以及流量不可预测、具有季节性、偶发或波动显著的应用。

使用按需定价时，你根据实际用量付费：

- **文本生成模型** – 按处理的输入 token 和生成的输出 token 付费 **Embedding 模型** – 按处理的输入 token 付费 **图像生成模型** – 按生成的图像付费
- **预置吞吐量模式** – 通过使用预置吞吐量，你可以为特定的 FM 购买专用模型单元，以固定成本获得该模型更高水平的吞吐量。这使预置吞吐量适合需要可预测性能且不会被限流的生产工作负载。如果你自定义了某个模型，则必须购买预置吞吐量才能使用它。

每个模型单元提供以每分钟处理的最大 token 数衡量的既定吞吐容量。预置吞吐量按小时计费，承诺期限可选 1 个月或 6 个月，承诺期限越长折扣越大。

**最佳实践：**如果你正在进行 POC，或某个用例的工作负载是偶发的、使用 Amazon Bedrock 中的一个基础 FM，请使用按需模式以享受按用量付费定价的好处。不过，如果你面对的是必须避免限流的稳态工作负载，或者你在使用自定义模型，则应选择与你的工作负载相匹配的预置吞吐量。请仔细计算你的 token 处理需求，以避免超额预置。

### 使用批量推理

使用批量模式，你可以通过提供一组 prompt 作为单个输入文件、并以单个输出文件接收回答，来同时获得大规模预测。回答会被处理并存储在你的 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3)桶中，以便你之后访问。Amazon Bedrock 为来自 Anthropic、Meta、Mistral AI 和 Amazon 等领先 AI 提供商的选定 FM 提供批量推理，价格比按需推理定价低 50%。详情请参阅[批量推理支持的 AWS 区域和模型](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference-supported.html)。这种方法非常适合你需要高效处理大量内容的非实时工作负载。

**最佳实践：**找出应用中不需要实时响应的工作负载，将它们迁移到批处理。例如，不要在用户查看时按需生成产品描述，而是在每晚的批处理作业中为新商品预先生成描述并存储结果。这种方法可以在保持相同输出质量的同时大幅降低你的 FM 成本。
