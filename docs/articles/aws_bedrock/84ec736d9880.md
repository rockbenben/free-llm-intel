# Agent 即自动扶梯：使用 Amazon Bedrock Agents 和视频流进行实时 AI 视频监控

部署视频监控系统的组织面临一个关键挑战：在处理连续视频流的同时保持准确的态势感知。采用基于规则的检测或基础计算机视觉的传统监控方法往往会漏掉重要事件，或产生过多的误报，从而导致运营效率低下和告警疲劳。

在本文中，我们展示如何构建一套可完整部署的解决方案：它使用 [OpenCV](https://opencv.org/) 处理视频流，使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 进行上下文场景理解，并通过 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 实现自动化响应。该解决方案扩展了[使用 Amazon Bedrock Agents 和 Knowledge Bases 实现文档与数据检索聊天机器人自动化](https://aws.amazon.com/blogs/machine-learning/automate-chatbot-for-document-and-data-retrieval-using-amazon-bedrock-agents-and-knowledge-bases/)所演示的能力，那篇文章讨论了如何使用 Amazon Bedrock Agents 进行文档和数据检索。在本文中，我们把 Amazon Bedrock Agents 应用于实时视频分析和事件监控。

## 当前视频监控系统的局限

部署视频监控系统的组织面临一个根本性的两难。尽管摄像头技术和存储能力不断进步，但解读视频流的智能层往往仍停留在初级水平。这就造成了一个棘手的局面：安全团队必须在监控方式上做出重大权衡。当前的视频监控解决方案通常迫使组织在以下选项之中做选择：

- **可扩展的简单规则**，但会产生过多误报
- **需要**持续维护和定制的**复杂规则**
- **人工监控**，依赖人的注意力且无法扩展
- **单点解决方案**，只能处理特定场景，但缺乏灵活性

这些权衡给有效的视频监控造成了根本性障碍，在各行各业影响着安全、治安与运营效率。基于我们与客户合作的经验，我们总结出由这些局限带来的三大关键挑战：

- **告警疲劳 **– 传统运动检测和目标识别系统会为任何检测到的变化或识别出的物体生成告警。安全团队很快就会被正常活动的通知量淹没。这导致在真正关键的事件发生时注意力下降，削弱安全效果，并因不断人工核实误报而增加运营成本。
- **有限的上下文理解能力 **– 基于规则的系统在本质上难以处理细微的场景解读。即使是精密的传统系统，由于缺乏上下文感知，它们在理解所监控的环境时也能力有限，因为它们很难轻松做到以下几点：  区分正常行为与可疑行为 理解诸如每周重复事件之类的时间模式 考虑一天中的时间或位置等环境上下文 关联多个可能指示某种模式的事件
- **缺乏语义记忆 **– 传统系统缺乏随时间积累并使用知识的能力。它们无法做到以下几点：  建立常规事件与异常事件的基线 对历史数据提供自然语言搜索能力 支持对新兴模式的推理

缺少这些能力，你就无法从监控基础设施中获得累积收益，也无法进行复杂的回溯分析。要有效应对这些挑战，你需要一种从根本上不同的方法。通过将 FM 的上下文理解能力与用于事件分类和响应的结构化框架相结合，你可以构建更智能的监控系统。Amazon Bedrock Agents 为这种下一代方法提供了理想的平台。

### Agent 即自动扶梯

第一个组件使用 Amazon Bedrock Agents 检查检测到的运动事件，具备以下能力：

- 对场景和活动提供自然语言理解，以实现上下文解读
- 在帧序列之间保持时间感知，以理解事件的演进过程
- 参考历史模式，区分异常事件与常规事件
- 对行为应用上下文推理，考虑一天中的时间、位置和动作序列等因素

我们实现了一个分级响应框架，按严重程度和所需操作对事件进行分类：

- **第 0 级：仅记录 **– 系统记录正常或预期内的活动。例如，当快递员在工作时间到达，或一辆已识别的车辆驶入车道时，这些事件会被记录下来，用于模式分析和日后参考，但不需要立即采取行动。它们在事件历史中仍然可搜索。
- **第 1 级：通知人工** – 该级别处理值得人工关注但不关键的异常事件。附近停放的不明车辆、意外的访客或异常的运动模式会触发向安保人员的通知。这些事件需要人工核实和评估。
- **第 2 级：立即响应** – 保留给关键安全事件。未授权访问尝试、检测到烟雾或火情，或可疑行为会通过 API 调用触发自动响应动作。系统通过短信或电子邮件告警通知人员，并附带事件信息和上下文。

该解决方案通过一个 Streamlit 应用提供交互式的处理与监控界面。借助 Streamlit UI，用户可以给出指令并与 agent 交互。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/12/image-4-9.png)

该应用包含以下关键功能：

- **直播流或视频文件输入 –** 应用接受来自网络摄像头或安防视频源的 M3U8 流 URL，或常见格式（MP4、AVI）的本地视频文件。两者都使用同一套运动检测 pipeline 处理，触发的事件会保存到 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）供 agent 分析。
- **自定义指令 –** 用户可以给出具体的监控指引，例如“下班后如果有陌生人出现在装卸货区附近就提醒我”，或“重点关注停车区域的车辆活动”。这些指令会调整 agent 解读检测到的运动事件的方式。
- **通知配置 –** 用户可以为不同的告警级别指定联系人信息。系统使用 [Amazon Simple Notification Service](https://aws.amazon.com/sns/)（Amazon SNS）按事件严重程度发送电子邮件或短信，从而可以针对潜在问题与关键情况分别通知不同的人员。
- **关于历史事件的自然语言查询 –** 界面包含一个用于检索历史事件的聊天组件。用户可以问“这周有哪些车辆在车道上出现过？”，或“给我看看昨晚的可疑活动”，系统会基于事件记忆给出回答。

### 视频处理 pipeline

该解决方案使用多项 AWS 服务，通过模块化的处理 pipeline 采集并准备视频数据以供分析。该解决方案支持多种类型的视频源：

- 实时视频流（M3U8 格式）
- 本地视频文件（mp4、avi 等）
- [Amazon Kinesis Video Streams](https://aws.amazon.com/kinesis/video-streams/)（Kinesis 视频 URL）
- 本地摄像头

使用流时，OpenCV 的 VideoCapture 组件负责建立连接和提取帧。为便于测试，我们附带了演示不同场景的示例事件视频。视频处理的核心是用 Python 实现的模块化 pipeline。关键组件包括：

- **SimpleMotionDetection** – 识别视频流中的运动
- **FrameSampling** – 在检测到运动时按时间采集帧序列
- **GridAggregator** – 将多帧组织成可视网格以提供上下文
- **S3Storage** – 将采集到的帧序列存储到 Amazon S3

这一多进程框架通过并发运行各组件并维护待处理帧的队列来优化性能。视频处理 pipeline 会以结构化方式组织采集到的帧数据，然后将其传递给 Amazon Bedrock agent 进行分析：

- **帧序列存储 –** 检测到运动时，系统会采集一段持续 10 秒的帧序列。这些帧使用基于时间戳的路径结构（YYYYMMDD-HHMMSS）存储在 Amazon S3 中，以便按日期和时间高效检索。如果运动超过 10 秒，则会创建多个事件。
- **图像网格格式 –** 系统不会逐帧单独处理，而是把多个连续帧排列成网格格式（通常为 3×4 或 4×5）。这种呈现方式提供了时间上下文，并被发送给 Amazon Bedrock agent 进行分析。网格格式使系统能够理解运动如何随时间推进，这对准确的场景解读至关重要。

下图是发送给 agent 的一个图像网格示例。使用经典图像模型很难识别包裹盗窃。大语言模型（LLM）对图像序列进行推理的能力，使其能够就意图做出判断。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/12/image-5-4.jpeg)

视频处理 pipeline 的输出——存储在 Amazon S3 中、带时间戳的帧网格——作为 Amazon Bedrock agent 各组件的输入，我们将在下一节讨论这些组件。

### Amazon Bedrock agent 组件

该解决方案集成了多项 Amazon Bedrock 服务，构建出一套智能分析系统：

- **核心 agent 架构 **– agent 编排以下关键工作流：  在检测到运动时从 Amazon S3 接收帧网格 协调多步分析流程 做出分类决策 触发相应的响应动作 维护事件上下文和状态
- **知识管理 **– 该解决方案使用 Amazon Bedrock Knowledge Bases 搭配 [Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/) 来：  存储并索引历史事件 建立基线活动模式 支持自然语言查询 跟踪时间模式 支持上下文分析
- **操作组 **– agent 可通过 API schema 定义的多个操作：  **分析网格** – 处理来自 Amazon S3 的传入帧网格 **告警** – 根据严重程度通过 Amazon SNS 发送通知 **记录** – 记录事件详情以供日后参考 **按日期搜索事件** – 根据日期范围检索过去的事件 **查询车辆（Text-to-SQL）** – 查询车辆数据库以获取信息

对于结构化数据查询，系统利用 FM 将自然语言转换为 SQL 的能力。这支持以下操作：

- 查询包含事件记录的 [Amazon Athena](https://aws.amazon.com/athena) 表
- 检索已登记车辆的信息
- 基于结构化事件数据生成报告

这些组件协同工作，构成一套完整的系统，能够分析视频内容、维护事件历史，并通过自然语言交互同时支持实时告警和回溯分析。

## 视频处理框架

视频处理框架实现了一套多进程架构，通过可组合的处理链来处理视频流。

### 模块化 pipeline 架构

该框架采用基于组合的方式，围绕 `FrameProcessor` 抽象基类构建。

处理组件实现一致的接口，其中的 `process(frame)` 方法接收一个 Frame 并返回一个可能已被修改的 Frame：

```
```
class FrameProcessor(ABC):
    @abstractmethod
    def process(self, frame: Frame) -> Optional[Frame]: ...
```
```

`Frame` 类封装了图像数据以及时间戳、索引和可扩展的元数据：

```
```
@dataclass
class Frame:
    buffer: ndarray  # OpenCV image array
    timestamp: float
    index: float
    fps: float
    metadata: dict = field(default_factory=dict)
```
```

### 可定制的处理链

该架构支持配置多条可按顺序连接的处理链。该解决方案使用两条主要的链。检测与分析链处理传入的视频帧，以识别关注的事件：

```
```
chain = FrameProcessorChain([
    SimpleMotionDetection(motion_threshold=10_000, frame_skip_size=1),
    FrameSampling(timedelta(milliseconds=250), threshold_time=timedelta(seconds=2)),
    GridAggregator(shape=(13, 3))
])
```
```

存储与通知链负责存储已识别的事件并调用 agent：

```
```
storage_chain = FrameProcessorChain([
    S3Storage(bucket_name=TARGET_S3_BUCKET, prefix=S3_PREFIX, s3_client_provider=s3_client_provider),
    LambdaProcessor(get_response=get_response, monitoring_instructions=config.monitoring_instructions)
])
```
```

你可以根据具体的监控需求，独立地修改这些链，以添加或替换组件。

### 组件实现

该解决方案包含若干处理组件，用于演示框架的能力。你可以修改每个处理步骤，或添加新的步骤。例如，对于简单的运动检测，我们使用简单的像素差分，但你可以按需改进运动检测功能，或按照同样的格式实现其他检测算法，例如目标检测或场景分割。

其他组件包括用于控制采集时机的 `FrameSampling` 处理器、用于创建可视帧网格的 `GridAggregator`，以及保存事件数据并触发 agent 分析的存储处理器，这些都可以按需定制和替换。例如：

- **修改现有组件** – 调整阈值或参数，以针对特定环境进行调优
- **创建替代的存储后端** – 将输出定向到不同的存储服务或数据库
- **实现预处理和后处理步骤** – 添加图像增强、数据过滤或额外的上下文生成

最后，`LambdaProcessor` 通过调用 [AWS Lambda](https://aws.amazon.com/lambda) 函数把信息以请求的形式发送给已部署的 agent，从而充当通往 Amazon Bedrock agent 的桥梁。此后，Amazon Bedrock agent 接手，分析事件并据此采取行动。

## Agent 实现

部署解决方案后，一个 Amazon Bedrock agent 别名即可使用。该 agent 充当智能分析层，处理采集到的视频事件，并根据其分析执行适当的操作。你可以直接在 Amazon Bedrock 控制台上测试该 agent 并查看其推理轨迹，如下图所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/12/image-6-6.png)

该 agent 会缺少 Streamlit 应用提供的一些元数据（例如当前时间），因此给出的答案可能与完整应用不同。

### 调用流程

agent 通过一个 Lambda 函数调用，该函数负责请求-响应周期并管理会话状态。它会找到已发布的最高版本 ID，用它来调用 agent，并解析响应。

### 操作组

agent 的能力通过操作组定义，这些操作组使用 `BedrockAgentResolver` 框架实现。这种方式会自动生成 agent 所需的 OpenAPI schema。

agent 被调用时会收到一个事件对象，其中包含 API 路径以及其他参数，用于告知 agent 框架如何把请求路由到相应的处理程序。你可以按照相同的模式定义额外的端点处理程序并生成新的 OpenAPI schema，来添加新的操作：

```
```
if __name__ == "__main__":
    print(app.get_openapi_json_schema())

### Text-to-SQL 集成

这项能力使用户可以用自然语言查询结构化数据。如下例所示，系统会把关于车辆的自然语言查询转换为 SQL，并从数据库返回结构化信息。

数据库连接通过 SQL Alchemy 引擎配置。用户可以通过更新 `create_sql_engine()` 函数以使用自己的连接参数，从而连接到现有数据库。

这一事件记忆存储使系统能够随时间积累知识，随着数据不断累积，提供的洞察也越来越有价值。结构化数据库查询与跨事件描述的语义搜索相结合，造就了一个对所有过往事件都具备可搜索记忆的 agent。

## 部署解决方案

AWS CDK 部署会创建以下资源：

- **存储** – 用于存放资产和查询结果的 S3 存储桶
- **Amazon Bedrock 资源** – agent 和知识库
- **计算** – 用于操作、调用和更新的 Lambda 函数
- **数据库** – 用于结构化查询的 Athena 数据库，以及用于数据发现的 [AWS Glue](https://aws.amazon.com/glue) 爬虫

使用以下命令部署解决方案：

```
```

python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
#3. Deploy AWS resources
cdk bootstrap && cdk deploy
#4. Run the streamlit app
cd code/streamlit_app && streamlit run app.py
```
```

#### 进一步扩展

此外，你可以使用以下方法扩展 FM 的能力：

- **针对特定监控场景的微调** – 使模型能够识别特定领域的对象、行为和场景
- **针对特定用例的精细化 prompt** – 创建专门的指令，以优化 agent 在工业设施、零售空间或住宅环境等特定环境中的表现

你还可以扩展 agent 采取行动的能力，例如：

- **直接控制智能家居和智能建筑系统** – 与物联网（IoT）设备 API 集成，以控制灯光、门锁或报警系统
- **与安保和安全规程集成** – 连接到现有的安防基础设施，以遵循既定流程
- **自动化响应 workflow** – 创建可由特定事件触发的多步动作序列

你也可以考虑增强事件记忆系统：

- **长期模式识别** – 识别较长时间段内重复出现的模式
- **跨摄像头关联** – 把多个摄像头的观察结果关联起来，以追踪空间内的移动
- **基于历史模式的异常检测** – 自动识别偏离既定基线的行为

最后，可以考虑把监控能力扩展到固定摄像头之外：

- **面向机器人视觉系统的监控** – 把同样的智能应用到巡逻或巡检区域的移动机器人上
- **基于无人机的监控** – 处理航拍影像，以实现全面的现场监控
- **移动安防应用** – 扩展平台，以处理来自安保人员随身摄像头或移动设备的视频流

这些增强可以把系统从被动的监控工具转变为安防运营中的主动参与者，对正常模式和异常事件的理解也越来越精细。
