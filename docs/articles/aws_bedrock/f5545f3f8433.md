[Reactiv](https://www.reactiv.ai/) 提供一款移动商务产品，帮助 Shopify 商家上线并管理原生移动应用——购物者在其上的转化率是 Web 访客的 2–4 倍。对这些商家来说，一个陈旧的首页或一个错过的促销窗口都意味着真金白银的收入损失。然而让一个应用保持新鲜需要持续的人工工作：挑选要主推哪些商品、重排区块、生成新素材并按时发布更新。多数商家没有每周都做这件事的精力。Reactiv 用 Amazon Bedrock AgentCore 自动化了这些更新，把商家配置时间减少了 80%，并把到生产的时间快了 33%。

Reactiv 着手用一个按计划自主更新商家应用的 AI 调度器（AI Scheduler）来解决这一点。商家用自然语言描述他们想要的，比如“每周一 9 点用畅销品刷新我的首页”，系统处理其余的一切。他们把它构建为一个在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上用 [Strands Agents](https://github.com/strands-agents) SDK 的三智能体系统，并在数周内投产。然后他们把交互式智能体和计划智能体统一到一套技术栈上，在两种模式之间实现了共享记忆。

在本文中，我们演练这些结果背后的架构、Reactiv 为什么选择 Amazon Bedrock AgentCore，以及他们的产品自发布以来的演进。

## 挑战：不会自我更新的内容

Reactiv 为 Shopify 商家构建原生 iOS 和 Android 应用。他们的工具包括一个低代码应用构建器、分析仪表盘和 AI 驱动的功能。在 AI 调度器之前，Reactiv 已经构建了一个对话式 AI 构建器。商家可以在 Reactiv 控制台里与一个 AI 助手对话，实时修改他们的应用。

那套系统对交互式使用有效，但 Reactiv 的商家要求一种不同的东西：按计划在无任何人工干预下发生的自主更新。构建这需要现有架构不支持的能力：

- **多智能体编排。** 计划任务需要一个主管来分类意图、一个分析智能体来查询商家数据，以及一个构建器智能体来生成配置。Reactiv 需要一个专为专用智能体的有向图而打造的托管运行时，这把他们引向了 Amazon Bedrock AgentCore。
- **持久记忆。** 每个会话都从零开始。智能体没有办法记住一个商家跨多次运行的偏好，或从过往批准中学习。
- **原生 Model Context Protocol (MCP) 支持。** Reactiv 的配置 schema 服务器（*Config MCP*）运行在 Amazon Elastic Container Service (Amazon ECS) 上，配一个定制的 Amazon Cognito 认证层，并在每次调用时手动做 JSON-RPC 握手。
- **工具定义开销。** 每个工具都需要一份 OpenAPI 规范、AWS Lambda 接线和动作组映射。约 100 个规范文件维护在两处。

Reactiv 需要一个能托管多智能体图、跨会话持久化记忆、原生连接到 MCP 服务器，并自动隔离每个商家数据的方案。

## 为什么选 Amazon Bedrock AgentCore

Amazon Bedrock AgentCore 是一个以任意框架或模型大规模构建、连接并优化智能体的平台。Reactiv 用它的三项能力应对了全部四项要求。AgentCore runtime（Amazon Bedrock AgentCore 的一项能力）处理托管的智能体执行。AgentCore memory（Amazon Bedrock AgentCore 的一项能力）提供跨会话的持久上下文。AgentCore Identity（Amazon Bedrock AgentCore 的一项能力）处理服务到服务的认证。

**托管的智能体运行时。** AgentCore 在 Firecracker microVM 中运行智能体，也就是 AWS Lambda 背后的同一套隔离技术。Reactiv 把他们的 Strands 智能体图打包成一个 Docker 镜像、推送到 Amazon Elastic Container Registry (Amazon ECR)，并部署到 AgentCore。智能体在计划触发时启动、完成时关闭。没有 Amazon ECS 集群、伸缩策略或空闲计算。

> “我们不管理容器、编排器或伸缩策略。我们把智能体代码打包成一个 Docker 镜像、部署到 AgentCore，它处理其余的一切。”— Adam Gibicar，Reactiv 高级 AI 开发者

**内建记忆。** AgentCore 提供跨智能体会话持久化的长期记忆。Reactiv 使用三种策略。一个会话摘要器把每次作业的动作浓缩为未来运行的上下文。一个偏好学习器跟踪商家随时间批准或拒绝哪些布局。一个语义事实抽取器存储关于商家店铺的知识，如产品类别、畅销品和品牌指南。记忆按商家限定范围，让每个商家的数据保持私密。无需定制的向量数据库或检索流水线。

**原生 MCP 托管。** Reactiv 把他们的 Config MCP 托管在 Amazon Bedrock AgentCore runtime 上。该 MCP 作为一个有状态的服务器运行，在会话开始时初始化商家当前的应用配置。Builder 智能体对这份实时状态执行变更，并在每次调用时对照 schema 验证。借助 AgentCore Identity，Reactiv 原生处理服务到服务的认证，去掉了他们此前构建和维护的定制认证层和 JSON-RPC 握手代码。

**多租户隔离。** 每个商家的执行上下文、记忆和智能体状态都在其自己的 Firecracker microVM 中运行。商家 A 的偏好与商家 B 的会话保持隔离。AgentCore 在基础设施层处理租户路由和隔离。

## 架构概览

下图展示 AI 调度器的端到端流程。

图 1：Reactiv AI 调度器的端到端流程。Amazon EventBridge 触发一个 Lambda 执行器，它调用 AgentCore runtime，在那里三个 Strands 智能体跨 MCP 工具、Lambda 函数、AgentCore memory 和 Amazon Bedrock 协调，产出存进 Amazon DynamoDB 供商家审批的应用配置

下表总结了方案中的服务：

| **服务** | **角色** |
| --- | --- |
| Amazon Bedrock AgentCore | 托管智能体运行时、持久记忆、MCP 托管、AG-UI 支持、多租户隔离 |
| Amazon Bedrock | 基础模型访问、护栏 |
| Amazon EventBridge | 为商家定义的更新节奏做 cron 调度 |
| AWS Lambda | 作业执行器和被智能体调用的 17 个工具函数 |
| Amazon DynamoDB | 供商家审阅和批准的结果存储 |
| Amazon Redshift | 为 Analytics 智能体的 `text-to-SQL` 查询提供数据的分析数据存储 |

系统从商家开始。商家从 Reactiv 控制台，通过一个聊天机器人界面（“每周一 9 点用畅销品刷新我的首页”）或一个选择 prompt、频率和时间的表单，创建一个计划任务。两者都产出一个由一个 Amazon EventBridge cron 规则支撑的计划记录。

当计划触发时，流程经过五个组件：

- Amazon EventBridge 触发一个 Job Executor（AWS Lambda），它验证商家的账户、获取一个并发锁，并从数据库拉取商家当前的应用配置。
- Lambda 函数带着智能体所需的全部上下文调用 AgentCore runtime：商家的 prompt、当前应用配置和会话元数据。
- 在运行时内部，一个 Strands 多智能体图执行：  Supervisor 智能体分类商家的意图并路由到正确的流水线（仅分析、仅构建器，或先分析后构建）。Analytics 智能体通过对 Amazon Redshift 的 `text-to-SQL` 查询商家表现数据，呈现趋势、热销品和可行动洞察。Builder 智能体接过那些洞察并产出更新后的应用配置。为此它调用超过 50 个工具，包括通过 Config MCP 的配置变更、通过 Lambda 函数的数据查询、从 Shopify Storefront SDK 的产品查找，以及用一个图像生成 SDK 做的素材创建。
- Config MCP（托管在 AgentCore 上）对照 Reactiv 的应用 schema 验证 Builder 智能体做出的每一次变更。Builder 智能体无法产出一个无效配置，因为该 MCP 既是参考也是护栏。
- 生成的配置存进 Amazon DynamoDB 供商家审阅。没有商家的明确批准，什么都不会上线。

在整个执行过程中，AgentCore memory 在一个隔离的命名空间里读写商家的长期记忆。每个计划作业都在该特定商家先前会话中积累的偏好和事实之上构建。三个智能体通过 Amazon Bedrock 访问基础模型，后者提供无服务器推理和内建护栏，而无需 Reactiv 管理模型托管或 GPU 基础设施。

## 统一交互式与计划智能体

上线调度器后，Reactiv 有两套分开的智能体系统：交互式控制台智能体（用 Amazon Bedrock 的定制 UI 适配器构建）和计划智能体（基于 Strands 配 AgentCore 构建）。它们不共享记忆、工具或基础设施。

Reactiv 通过把交互式智能体迁移到 Amazon Bedrock AgentCore 上的 AG-UI 协议来统一它们。控制台智能体现在与调度器共享同样的 Strands 框架、AgentCore 托管的 MCP 服务器和 AgentCore 记忆实例。结果是两个智能体之间一个共享的框架、运行时、记忆层和 UI 协议。其实际效果是双向的记忆共享。在一次交互式控制台会话中学习到的偏好和事实直接喂入下一次计划运行，反之亦然。随着商家更多地使用前端智能体，计划作业变得越来越聪明。

## 结果

迁移到 Amazon Bedrock AgentCore 后，Reactiv 在开发速度、运行时性能和商家体验上都收获了提升。据 Reactiv 的内部测量：

- **商家配置时间减少 80%**。过去需要 17 小时人工工作的上线任务如今 3 小时完成，而上线后的改动在几分钟而非几天内发生。
- **简化的工具和更低的成本**。Strands SDK 的 `@tool` 装饰器取代了约 100 个 OpenAPI 规范文件，AgentCore runtime 和 AgentCore Identity 去掉了定制基础设施，而这次迁移仅在计算成本上每年节省近 6,000 美元。
- **零定制基础设施的持久记忆**。每商家三种长期记忆策略，完全由 AgentCore memory 托管，无需构建或维护向量数据库或检索流水线。
- **到生产的时间快 33%**。一个三人团队在 10 周内交付了这个三智能体系统，而此前单智能体构建用了 15 周。有了 AgentCore 和 Strands，团队把工程时间集中在智能体逻辑上，而非基础设施管道上。
- **作业执行快 2 倍**。使用 AgentCore runtime 中原生的流式传输，计划作业从超过 10 分钟降到约 5 分钟，它用单次实时调用取代了一个四步轮询链。

## 下一步

在交互式与计划智能体统一到一套技术栈之后，Reactiv 正在扩展商家可用的创作面。贯穿其中的主线是：商家可以用自然语言、以逐渐更深的程度定制他们的移动应用。

第一步是把 Reactiv 现有的设计属性（颜色、排版、间距、组件变体）作为一个托管在 Amazon Bedrock AgentCore 上的新 MCP 服务器提供给智能体。这复现了 Config MCP 的做法：一个可共享的工具面，调度器、交互式构建器，以及最终的外部集成都能消费它。商家可以说“让我的应用匹配我的品牌”，而智能体会在一个受治理的设计词汇内应用改动，而非生成无约束的输出。

那套设计系统还解锁了一个重建的上手体验。当一个新商家提供其品牌名和网站时，智能体分析其现有的网络形象并为移动应用产出一个强起点。因为设计系统已就位，智能体可以瞄准真实的设计属性和组件，而非凭空生成布局。

更远一些，Reactiv 计划让商家通过自然语言请求全新的布局区块。智能体会生成所请求布局一个经验证的 JSON 表示，移动应用使用 Reactiv 的设计系统组件即时渲染它。这把智能体的创作能力延伸到预构建区块类型之外，进入仍遵循品牌指南的商家自定义布局。

## 结论

Reactiv 从一个自托管基础设施上的单智能体起步，成长为一个 Amazon Bedrock AgentCore 上统一的多智能体系统。今天他们的生产系统运行三个专用智能体、超过 50 个工具，以及在交互式和自主模式之间共享的持久记忆。多个 MCP 服务器运行在一个托管运行时上。他们更快地交付了它，用了更少的基础设施代码，并具备了否则需要数月定制工程才能实现的能力。

基于 MCP 的架构已被证明尤其可复用。Reactiv 的 Config MCP 模式如今延伸到一个设计系统 MCP，并最终延伸到外部开发者工具。每个新能力都从定义工具、把它们托管到 AgentCore 并跨智能体共享开始。

如果你正在构建需要多租户隔离、长期记忆或托管 MCP 的智能体式 AI 系统，你可以用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 通过 AgentCore runtime、AgentCore memory 和 AgentCore Identity 访问这些。要开始上手，参考 [AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/) 和 [Strands Agents SDK](https://github.com/strands-agents)。
