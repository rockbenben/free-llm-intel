# Amazon SageMaker AI 上的 Mixture-of-Experts kernel 工程

Mixture-of-Experts（MoE）是一种稀疏激活架构，它能在把每 token 计算量保持很低的同时，扩展大语言模型（LLM）的容量。由于 MoE 相关运算在总计算时间中占比很高，这部分一旦低效，就会直接抬高请求延迟和成本。因此，通过 kernel 工程优化 MoE 运算，是性能收益最大的一条路。

Fused MoE 是 MoE 架构的一项关键优化技术。fused MoE 系统把 token 路由、数据 shuffle 与专用网络的计算合并成 GPU 上的一个批量操作，不再把路由和各 expert 的计算当作彼此分离、顺序执行的循环来跑。这样做在延迟上有好处，但也让 kernel 实现和调试能力变得更复杂。要让这种架构跑上高 GPU 利用率，必须做针对硬件的优化。

本文介绍我们为 fused MoE 模型实现的各项 kernel 优化，并说明你能如何从中受益。我们选用一个有代表性的 MoE 模型作为主要示例。

## 用 Swap-AB 提升 WGMMA 利用率

要把张量处理的吞吐量拉到最高，NVIDIA Hopper 架构依赖 Warp Group Matrix Multiply Accumulate（WGMMA）指令协议，它由一个 128 线程协作的 warpgroup 集体执行。这种操作数不对称本质上是指令集架构（ISA）层面的属性。在底层的 `wgmma.mma_async` 汇编定义中，硬件把矩阵的行维度 (M) 固定为 64 这一恒定规模，以此确定并行的线程映射拓扑；列维度 (N) 则可以高度变化。操作数 A 严格映射在这个固定的 M 维度上（使用寄存器或共享内存），操作数 B 映射在可变的 N 维度上（通过共享内存描述符）。因此这些操作数槽位在结构上不可互换。也正因如此，硬件 tile 利用率的上限由这些刚性的形状编码决定：M 维度必须等于或大于 64，否则计算执行通道会空转。

这种结构偏好源自 Hopper Tensor Core 划分内存块的方式。硬件对第一个操作数的主维度强制规定了一个最小布局形状，把块高锁死为 64（M=64）。当矩阵在这个主槽位上拥有较大且连续的主维度时，Hopper 内部的硬件调度器就能把数据干净地映射并铺展到物理计算网格上。

到了 MoE 网络的 decode 阶段，这种结构不对称会变成严重的性能瓶颈。在标准 MoE 层里，支配 expert 计算的线性代数用传统矩阵记法写成：

A[M,K] x B[K,N] —> C[M,N]

其中 (M) 表示 token 行数（也就是 batch size），(K) 表示 hidden 特征维度，(N) 表示很大的 expert 输出维度。

在 decode 阶段，系统每次只处理每条用户序列的一个 token。于是 batch 空间、也就是 token 行数极薄，常常落到 (M < 64) 的形状，很多时候只剩一行 (M = 1)。在这种标准结构布局下：

矩阵 (A) 退化成一个又薄又碎的横向向量（例如 1 x 4096）。

矩阵 (B)（也就是 expert 权重本体）仍然保持为一个大而密集的纵向块（例如 4096 x 8192）。

由于行数 (M) 极小，矩阵 (A) 在物理上填不满硬件为操作数 A 预设的 (64) 行布局槽位。WGMMA 指令按这种布局执行时，会有很大一部分 Tensor Core 的物理算力处于饥饿状态：芯片把时钟周期花在处理空位上，硬件利用率因此很低。

在标准 dense LLM 层里，权重矩阵是静态、统一、完全连续的。而在 MoE 层里，负载被拆散到一大批相互独立的子网络（expert）上。这带来了特有的内存与布局瓶颈，使它对 Hopper GPU 的 WGMMA 约束异常敏感。标准 dense 层的矩阵乘法是一个 token 向量乘以一个层权重矩阵，输出维度 (N) 就是模型的 hidden size（例如 4096）。

在 fused MoE kernel 里，GPU 不只是与一个 expert 做乘法：它把所有被激活的 expert 的运算分组、同时执行，以免为每个 expert 单独启动 kernel。标准 dense 层的 N 是 hidden size（4,096）；fused MoE 层的 N 是被选中的 expert 数量乘以 expert 的中间层尺寸。对一个走 `topk=8` 流程的模型来说，fused kernel 内部的有效 N 维度会膨胀到几万甚至几十万参数。跟极小的 decode token 规模 (M=1) 相比，N 维度大得不成比例，布局不对称因此被推到极端。把矩阵转置后，这个合并起来的巨大 MoE 维度就移进了主槽位，从而释放出标准 dense 层无法企及的硬件预取规模。

为了在不改变模型底层数学含义的前提下解决这一硬件错配，我们利用矩阵转置的代数性质：

BT[N,K] x AT[K,M] —> CT[N,M]

在矩阵乘法抵达 PTX 汇编层之前，我们在程序层面把它翻转过来，让软件重新对齐 Hopper 硅片的实际布局。这次转置在 GPU 上带来两项直接的架构优势。第一，它把物理布局填满：较大的 expert 维度 (N = 8192) 被提升到第一个操作数的位置 (BT)，由于 (N) 很大，轻松越过硬件强制的 (64) 行下限，Tensor Core 于是以最高局部密度运行，没有浪费的执行周期。第二，它启动了异步预取：Hopper 专用的硬件拷贝引擎可以在数学执行块启动之前，异步地把内存地址从共享内存直接预取进寄存器。把连续的大块权重 (BT) 放在主维度槽位，这些引擎就能顺着数据布局平滑推进，无需 CPU 介入便让计算流水线保持满载。在 H200 上的大规模 MoE 模型中，这带来了 2–4% 的端到端输出吞吐提升。我们把这项优化上游合入了 vLLM，0.24.0 及之后的版本可用。

## FP8 张量量化的后端路由

除了 kernel 内部实现，由哪个后端来执行 MoE 计算也极大影响性能。vLLM 的 MoE oracle 会把不同量化方案路由到 Triton、FlashInfer+CUTLASS 或其他后端。Profiling 显示，对 Hopper 上的 FP8 张量量化模型，Triton 后端始终快过默认的 `FLASHINFER_CUTLASS` 路径。

在低并发的 MoE 负载下，Triton 后端胜过 CUTLASS，主要是它用自定义的算子级寄存器融合取代了僵硬的框架级矩阵运算配置。CUTLASS 依赖标准的 C++ 模板结构，把 FP8 张量缩放、矩阵乘法、expert 结果聚合当成彼此离散的数学操作。Triton 后端则把这整条流水线合并成一次硬件遍历：数据只从全局高带宽内存（HBM）取一次，全部在 GPU 极快的片上 SRAM 寄存器与计算执行单元里处理完，再流式写回最终的目标矩阵。这就消掉了那些拖累 CUTLASS 的全局 VRAM 往返读写——当它被迫一步步走过中间张量的缩放环节时，这些开销尤其明显。

此外，这种寄存器级融合还专门配合了围绕可变 token 分桶设计的动态调度布局，补上了传统编译模板里一个严重的结构缺陷。CUTLASS 原生是为稠密、巨大、可预测的矩阵维度优化的。一旦遇到线上 decode 生成阶段那种流动、极薄的 batch 形状（M < 64 或 M = 1），它默认的 block tiling 与线程映射结构就会极度低效，结果要么是 warp 大面积利用不足，要么付出昂贵的内存 padding 开销。反过来，Triton 的 MoE 后端擅长把这些细碎的小 token 数组动态映射到激活 expert 权重的物理边界上，即使在 batch size 很低、负载极不稳定的情况下，也能让硬件内部的预取流和 Tensor Core 流水线保持满载。

更新路由策略是纯配置改动，没有修改任何 kernel 代码，但仍然让 H200 上 FP8 量化的 fused MoE 模型拿到 **10% 的端到端吞吐提升**。这一改进在 AWS Large Model Inference（LMI）v28 容器中可用。

## 消除 Triton 的 JIT 重编译

GPU 推理中最伤性能的问题之一，恰恰也最不明显：不必要的 kernel 重编译。Triton 是 vLLM 许多自定义 kernel 底层的编译框架，它默认会对整数实参做特化。只要有一次 kernel 调用用到了某个特化参数此前没出现过的取值，Triton 就触发一次新的即时编译（JIT）。在序列长度和 batch size 持续变化的服务负载里，这会源源不断产生编译开销，把延迟抬高，尤其是首 token 时间（Time to First Token，TTFT）。

在 MoE 模型服务中，`_fused_inv_rope_fp8_quant_per_head` kernel（负责融合旋转位置编码与 FP8 量化）每遇到一个新的 `num_tokens` 取值就要重编译一次。给这些长度可变的参数加上 `do_not_specialize` 标注后，这些重编译被彻底消除：在 H200、8 路 tensor parallelism 下，TTFT 改善了 **9%**（PR #42849）。

在多 GPU 集群里，8 张 GPU 的 kernel 必须以微秒级精度严格同步执行。只要有一张 GPU 因为本地的 token batch 计数变化而停下来重编译它本地的 `_fused_inv_rope_fp8_quant_per_head` kernel，其余七张就得空着等它。通过在整个集群上消除重编译，我们抹平了多 GPU 的协调开销，为用户的初始响应延迟带来 9% 的加速。这里的思路是把编译器当作一等的优化对象：弄清 Triton 如何做语义特化、识别哪些参数是死的或可变的，就能用极小的代码改动换到延迟改善。

我们把这项优化上游合入了 vLLM，0.22.0 及之后的版本可用。

## 结论

借助与 vLLM 社区的合作，我们实现并开源了多项 fused MoE 模型的 kernel 优化，并在 Amazon SageMaker AI 的 LMI Deep Learning Container 中应用了这些优化。综合起来，它们带来了最高 10% 的吞吐提升与最高 9% 的 TTFT 加速。要开始自定义模型托管，请参阅 [Amazon SageMaker AI 托管文档](https://docs.aws.amazon.com/sagemaker/latest/dg/deploy-model.html)。
