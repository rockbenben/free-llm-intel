# AgentCore Memory 中基于元数据的结构化记忆过滤

假设你的客户支持 agent 查询“账单问题”，拿回来的却是技术支持工单、带收据问题的销售对话和账单争议混在一起。这就是团队在 agent 积累了几周交互历史后撞上的检索精度之墙：相似度搜索会找出对当前客户语义上接近的一切，却无法把范围限定到你真正需要的相关维度：问题类型、状态或时间。

[Amazon Bedrock AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html) 是一项全托管记忆服务，让 AI agent 具备跨对话记忆与召回信息的能力。它把 agent 的记忆记录组织到命名空间（namespace）中，这些命名空间定义相互隔离的作用域，例如 `clients/client-123`，因此每个实体的数据保持独立。你可以阅读博文 [Organizing Agents' memory at scale: Namespace design patterns in AgentCore Memory](https://aws.amazon.com/blogs/machine-learning/organizing-agents-memory-at-scale-namespace-design-patterns-in-agentcore-memory/) 来进一步了解命名空间的编排方式。随着记忆不断增长，相关信号会淹没在语义相似但上下文无关的结果中，仅靠命名空间划分无法把它们区分开。

元数据过滤（metadata filtering）填补了这一空白。现在你可以在命名空间隔离之上叠加细粒度的、基于属性的过滤器，在相似度搜索运行之前就按优先级、部门或时间范围等业务维度限定检索范围。在我们基于长期记忆基准（LoCoMo 风格的多会话对话）构建的 151 道题测试集上，它带来了改善。在所有题型上启用元数据过滤后，整体问答（QA）准确率从 40% 提升到 64%。收益集中在依赖上下文边界的题目子集上，例如带时间边界的查询、基于优先级的过滤或按部门限定的搜索。对于这些题目，准确率从 16% 跃升至 69%。

在本文中，你将了解元数据在配置、摄取与检索三个环节中如何工作，探索包括多 agent 与多租户架构在内的企业用例，并掌握实施过程中的最佳实践。

## 构建命名空间与元数据的结构

AgentCore Memory 使用命名空间沿着主要实体边界来组织和隔离记忆。你把检索范围限定到某个具体命名空间，例如 `clients/client-123/sessionABC` 或 `patients/patient-456`，这样 agent 就不会误取到其他客户或患者的数据。命名空间提供了最基础的隔离层。更多内容请阅读[关于命名空间设计模式的博文](https://aws.amazon.com/blogs/machine-learning/organizing-agents-memory-at-scale-namespace-design-patterns-in-agentcore-memory/)。

![漏斗图展示检索范围如何从 10,000+ 条记忆记录收窄到约 500 条的命名空间作用域，再经元数据过滤收窄到约 100 条，最后由语义搜索返回前 10 个匹配结果](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/19/ML-20840-1.png)

随着部署规模扩大，命名空间内的语义搜索会遇到一些限制。设想一个金融服务 agent，为每位客户分配一个命名空间，已积累六个月的交互历史。当客户经理要求 agent 回忆某位特定客户的“*投资组合再平衡讨论*”时，命名空间能正确地把搜索限定在该客户的记忆范围内。但结果会横跨该客户历史中不同的投资策略、时间段和优先级。agent 无法把上周一场高优先级的再平衡对话与三个月前的一次例行询问区分开来。这些信息在语义上相似，但上下文完全不同。

多租户环境清晰地展示了这种分层。命名空间已经为租户之间提供了完整的数据隔离。在每个租户的命名空间内，你的 IT 服务台 agent 在搜索解决方案模式之前仍然需要按工单类型过滤。**命名空间是“谁”这一维度上的逻辑隔离。元数据过滤则处理这些边界内部的再分组：类别、解决状态、日期、优先级和标签。**

## AgentCore Memory 中的元数据

AgentCore Memory 中的元数据同时作用于短期记忆和长期记忆，并遵循三阶段生命周期：配置、摄取和检索。接下来的章节将逐一说明元数据在每个记忆层上的工作方式，先从短期记忆讲起，再深入长期记忆的完整三阶段生命周期。

### 短期记忆中的元数据

在短期记忆层，你把基于字符串的键值对附加到事件（event）上，用一些并不属于对话本身、但对后续检索至关重要的上下文信息为交互打标签。

短期记忆的元数据支持在事件上使用基于字符串的键值对，可用于过滤。这些标签会在抽取与整合（consolidation）过程中带入长期记忆，并在那里成为可过滤的维度。

### 长期记忆中的元数据

长期记忆才是元数据充分发挥作用的地方。下面描述的三个阶段让你能够精确控制结构化上下文如何声明、如何传播以及如何查询。简而言之，你在配置阶段声明哪些键重要；在摄取阶段附加这些键的值，或让模型推断其值；在检索阶段用它们过滤。当一次会话中的多个事件携带相同的键时，AgentCore Memory 会按照你在 `llmExtractionInstruction` 中定义的消解行为把它们合并成一个值。

#### 阶段 1：配置

创建记忆资源（memory resource）时，你声明要索引哪些元数据键，以便在记忆记录之间快速过滤与检索。你需要在每个记忆策略（memory strategy）上定义元数据 schema，指示 AgentCore Memory 如何抽取并消解元数据值。被索引的键以针对查询过滤优化的格式存储，而非索引键则与记忆记录一同存储，仅用于信息展示。

下面的代码创建了一个带有元数据配置的客户支持记忆资源：

```
response = agentcore_client.create_memory(
    name="CustomerSupportMemory",
    eventExpiryDuration=30,
    indexedKeys=[
        {"key": "priority", "type": "STRING"},
        {"key": "agent_type", "type": "STRING"},
        {"key": "channel", "type": "STRING"},
        {"key": "ticket_id", "type": "STRING"}
    ],
    memoryStrategies=[{
            "semanticMemoryStrategy": {
                "name": "SupportSemanticStrategy",
                "description": "Captures support interaction details",
                "namespaces": ["support/{actorId}"],
                "memoryRecordSchema": {
                    "metadataSchema": [
                        {
                            "key": "priority",
                            "type": "STRING",
							"extractionType": "STRICTLY_CONSISTENT",
                            "extractionType": "STRICTLY_CONSISTENT""extractionConfig": {
                                "llmExtractionConfig": {
                                    "definition": "Issue priority level based on customer impact.",
                                    "llmExtractionInstruction": "LATEST_VALUE",
                                    "validation": {
                                        "stringValidation": {
                                            "allowedValues": ["critical", "high", "medium", "low"]
                                        }
                                    }
                                }
                            }
                        },
                        {
                            "key": "agent_type",
                            "type": "STRING",
							"extractionType": "STRICTLY_CONSISTENT",
                            "extractionConfig": {
                                "llmExtractionConfig": {
                                    "definition": "Support agent classification.",
                                    "llmExtractionInstruction": "Prefer the most specialized agent type. Hierarchy: specialist > tier3 > tier2 > tier1 > bot."
                                }
                            }
                        },
                        {
                            "key": "sentiment",
                            "type": "STRING",
							"extractionType": "STRICTLY_CONSISTENT",
                            "extractionConfig": {
                                "llmExtractionConfig": {
                                    "definition": " Customer sentiment during the interaction. ",
                                    "llmExtractionInstruction": "Classify the overall customer sentiment based on tone and language used.",
                                    "validation": {
                                        "stringValidation": {
                                            "allowedValues": ["positive", "neutral", "negative", "frustrated"]
                                        }
                                    }
                                }
                            }
                        }
                    ]
                }
            }
    }]
)
```

每个 schema 条目的 `extractionConfig` 在元数据抽取过程中指导大语言模型（LLM）。`definition` 字段描述该字段代表什么，而 `llmExtractionInstruction` 提供额外的抽取指引与冲突消解行为。内置的 `LATEST_VALUE` 操作提供基于时间新近性的消解，而自定义的自然语言指令则处理领域特定逻辑。可选的 `validation` 字段用于约束抽取出的值，例如 STRING 和 STRINGLIST 的 `allowedValues`、STRINGLIST 的 `maxItems`，以及 NUMBER 的最小—最大范围。这样可以保证下游过滤使用的值保持一致。注意（在前面的代码示例中）`sentiment` 在 schema 中定义，但并没有声明为索引键。因此 LLM 会完全从对话内容推导它的值，并写入抽取出的记录，但它不能用于元数据过滤表达式。

注意 `ticket_id` 在记忆层面被声明为索引键，却没有包含在该策略的 `memoryRecordSchema` 中。这个键不会写入抽取出的记忆记录。抽取之后，只有定义在策略 `memoryRecordSchema` 中的键才会出现在记录上。不在 schema 中的索引键会被忽略，即使源事件上存在匹配的值。如果你需要某个键出现在抽取出的记录上，它必须有一条 schema 条目。

![使用元数据代码块创建记忆资源的可视化示意](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/30/image5_v2.png)

你可以在 [AgentCore Memory 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/long-term-memory-metadata.html) 中进一步了解配置方面的约束。除了已配置的元数据键，还可以通过系统生成的 `dateTimeValue` 字段进行时间过滤（如果相关，用于应对记忆衰减），这些字段是 `x-amz-agentcore-memory-createdAt` 和 `x-amz-agentcore-memory-updatedAt`，它们支持 `BEFORE` 和 `AFTER` 操作符，无需你声明 datetime 索引键。

#### 针对已知值的严格一致元数据

有些元数据键是组织层面的分类器，例如 `department`、`compliance_level` 或 `interaction_type`。它们承载的是调用方在创建事件时就已经知道的值，并且必须以给定的原样落到最终的记忆记录上。LLM 抽取会为这些键引入变化：同一段对话可能在一条记录上产出“eng”，在另一条上产出“Engineering”，而事件上提供的值也可能在抽取过程中被重新推断。AgentCore Memory 用 `STRICTLY_CONSISTENT` 抽取类型来解决这个问题，它是 `LLM_INFERRED` 抽取类型的一个可选项。当某个键如此配置时，事件上提供的值会原样经过抽取与整合，且 LLM 不会参与该键的处理。

```
"metadataSchema": [
    {
        "key": "department",
        "type": "STRING",
        "extractionType": "STRICTLY_CONSISTENT"
    },
    {
        "key": "priority",
        "type": "STRING",
        "extractionType": "STRICTLY_CONSISTENT"
    }
    {
        "key": "topic",
        "type": "STRING",
        "extractionType": "LLM_INFERRED"
        "extractionConfig": {
            "llmExtractionConfig": {
                "definition": "Primary topic of the conversation",
                "llmExtractionInstruction": "Identify the main topic discussed"
            }
        }
    }
]
```

`STRICTLY_CONSISTENT` 键所做的不只是跳过推断。它们会对抽取进行分区。取值相同的事件总是一起抽取，并与取值不同的事件隔离，因此一条记录该带哪个值不存在歧义。

这种隔离同样支配整合过程。由一组确定性取值产出的记录只会与共享相同取值的记录整合。携带 `department: "billing"` 的记录不会与携带 `department: "engineering"` 的记录合并，无论它们的内容在语义上多么相似。

设想一次支持会话，客户的问题跨越了多个部门：

```
# Event 1: Initial billing inquiry
agentcore_client.create_event(
    memoryId="mem-support-abc123",
    actorId="customer-123",
    sessionId="session-escalation-001",
    payload=[{"conversational": {"role": "USER",
                "content": {"text": "I'm seeing duplicate charges on my last invoice for the enterprise plan."}}}],
    metadata={"department": {"stringValue": "billing"}, "priority": {"stringValue": "high"}}
)

# Event 2: Still billing context
agentcore_client.create_event(
    memoryId="mem-support-abc123",
    actorId="customer-123",
    sessionId="session-escalation-001",
    payload=[{"conversational": {"role": "USER",
                "content": {"text": "The charges appeared after we upgraded from the standard to enterprise tier last week."}}}],
    metadata={"department": {"stringValue": "billing"}, "priority": {"stringValue": "high"}}
)

# Event 3: Escalated to engineering (technical root cause)
agentcore_client.create_event(
    memoryId="mem-support-abc123",
    actorId="customer-123",
    sessionId="session-escalation-001",
    payload=[{"conversational": {"role": "USER",
                "content": {"text": "Your team found a provisioning bug that triggered the duplicate charge during tier migration."}}}],
    metadata={"department": {"stringValue": "engineering"}, "priority": {"stringValue": "high"}}
)
```

如果没有确定性隔离，这三个事件会被一起抽取。LLM 可能会以不确定的方式把 `department: "billing"`、`department: "engineering"`，甚至 `department: "account_management"` 赋给最终产出的事实。而在 `department` 上配置了 `STRICTLY_CONSISTENT` 之后：

- 事件 1 和事件 2 共享相同的确定性取值（`department=billing`、`priority=high`），会被一起抽取。产出的记忆记录携带的正是这些值。
- 事件 3 的确定性取值不同（`department=engineering`、`priority=high`），会被独立抽取。它的记录精确携带 `department: "engineering"`。

一个用 `department=billing` 查询的账单 agent 只会取回关于重复扣费与套餐升级的事实，而不会取回工程上下文中的开通配置缺陷细节。整合过程遵循同样的分隔：账单记录与工程记录不会被合并，即使它们的内容在语义上相关。

这使得确定性键非常适配合规隔离（HIPAA 记录与标准记录不会混在一起）、组织路由（按部门限定检索而不会相互污染），以及任何调用方在事件时刻已知某个值、并且需要它在最终记忆上被精确保留的场景。

配置为 `STRICTLY_CONSISTENT` 的键还必须在记忆资源上声明为索引键。整合会按索引键上的元数据过滤器来划定范围，正是这种范围划定防止了具有不同确定性取值的记录被合并。缺少某个确定性元数据键取值的事件仍会被处理，只是该键在最终记录上缺席。

每个策略最多支持三个 `STRICTLY_CONSISTENT` 键。每个这样的键都会占用记忆资源上十个索引键配额中的一个，而索引键一旦添加就无法移除。如果你计划使用该特性，请提前预留配额。

#### 阶段 2：摄取

配置好元数据 schema 之后，下一步是摄取带有元数据的数据。元数据通过两条路径进入系统。事件驱动路径把元数据附加到事件上，AgentCore Memory 会自动在抽取与整合过程中（依据抽取指令）把它传播到长期记忆记录中：

```
# Initial contact event
agentcore_client.create_event(
    memoryId="mem-support-abc123",
    actorId="customer-123",
    sessionId="session-001",
    eventTimestamp="2024-01-23T10:00:00Z",
    payload=[{
            "conversational": {
                "role": "USER",
                "content": {"text": "I have a question about my bill"}
            }
    }],
    metadata={
        "priority": {"stringValue": "medium"},
        "channel": {"stringValue": "email"},
        "ticket_id": {"stringValue": "TKT-5001"}
    }
)
```

当一次会话中有多个事件为同一个键携带不同的取值时，LLM 会使用该 schema 条目上的 `llmExtractionInstruction` 来消解冲突。例如，如果后续某个工单事件把优先级从“medium”升级为“high”，`LATEST_VALUE` 指令会保留“high”这个优先级值（图 3）。像 `agent_type` 字段中那样的自定义层级，则会保留处理链中最为专业化的 agent（图 3）。请注意，只有定义在该策略 `memoryRecordSchema` 中的元数据键才会写入最终的记忆记录。不在 schema 中的事件元数据键在抽取过程中会被忽略。

确定性键走的是另一条摄取路径。你在事件上提供的值就是落到最终记录上的值。这里没有 LLM 推断，也没有冲突消解，因为 AgentCore Memory 会在抽取之前按确定性键的取值对事件分组。标记为 `department: "engineering"` 的事件和标记为 `department: "finance"` 的事件会在相互独立的批次中处理，整合也只在这些分组内部进行。因此，携带 `compliance_level: "hipaa"` 的记录不会与标记为 `compliance_level: "standard"` 的记录合并。正因如此，确定性抽取非常适合合规隔离与路由类键。

如果某个事件到达时没有设置确定性键，该键就会从该事件的分组中被排除，并在最终记录上缺席。直接写入路径（`BatchCreateMemoryRecords` 和 `BatchUpdateMemoryRecords`）完全绕过抽取，因此 `STRICTLY_CONSISTENT` 抽取类型对它们没有影响。像你目前使用这些 API 那样直接提供元数据即可。

![整合合并规则消解元数据冲突：LATEST_VALUE 保留较新的优先级值，自定义层级保留最专业化的 agent_type](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/19/ML-20840-3.png)

事件元数据并不是 schema 键产出取值的必要条件。当某个 schema 键在源事件上没有匹配的元数据时，LLM 会使用该键的 definition 与 llmExtractionInstruction，完全从对话内容推导取值。设想一个含三个键的 schema，其中没有任何一个键在事件上被提供：

```
# Schema keys defined on the strategy
"metadataSchema": [
    {"key": "domain", "type": "STRING", "definition": "Primary technical domain discussed\..."},
    {"key": "tags", "type": "STRINGLIST", "definition": "AWS services referenced\..."},
    {"key": "priority", "type": "NUMBER", "definition": "Importance from 1 to 10\..."}
]

# Event created with NO metadata
agentcore_client.create_event(
    memoryId="mem-abc123",
    actorId="user-1",
    sessionId="session-001",
    payload=[{"conversational": {"role": "USER",
                "content": {"text": "How do I set up VPC peering across two accounts?"}}}]

    # no metadata parameter
)
```

抽取出的记忆记录会用全部三个从内容推断出的字段填充：

```
{
    "content": {"text": "The user asked how to set up VPC peering across two AWS accounts."},
    "metadata": {
        "domain": {"stringValue": "Networking"},
        "tags": {"stringListValue": ["VPC"]},
        "priority": {"numberValue": 7.0}
    }
}
```

校验规则仍然生效：无论取值来自事件元数据还是内容推断，LLM 的输出都会受到你所声明的 `allowedValues` 约束。这种隐式抽取对于只存在于对话本身的维度很有用，例如主题分类、情感或重要性，而无需调用方在创建事件时提供它们。

对于直接创建记忆记录的场景，例如导入知识库或摄取来自外部系统的预处理记录，你需要显式提供元数据：

```
agentcore_client.batch_create_memory_records(
    memoryId="mem-support-abc123",
    records=[{
            "requestIdentifier": "import-001",
            "namespaces": ["support/customer-456"],
            "content": {"text": "Customer prefers phone support for urgent billing issues"},
            "timestamp": "2024-01-15T10:00:00Z",
            "metadata": {
                "priority": {"stringValue": "high"},
                "agent_type": {"stringValue": "billing_agent"},
                "channel": {"stringValue": "phone"},
                "ticket_id": {"stringValue": "TKT-7890"}
            }
    }]
)
```

批量创建记录上的元数据行为取决于你是否在每条记录上提供可选的 `memoryStrategyId`。

提供 `memoryStrategyId` 时，服务会依据该策略的 `memoryRecordSchema` 过滤输入的元数据。只有定义在 schema 中的键才会存储在记录上。其他键会被静默丢弃，包括不在 schema 中的索引键以及任何地方都未声明的键。这为你提供了由 schema 强制的一致性，确保批量创建的记录与事件驱动抽取产出的记录具有相同的元数据形态。

省略 `memoryStrategyId` 时，服务会把 payload 中的元数据键原样存储在记录上，包括已索引的键、属于某个策略 schema 的键，以及两者都不是的键。不过，只有索引键可以用于过滤。尝试对非索引键过滤会返回 `ValidationException`。非索引键在 `getMemoryRecord` 和 `listMemoryRecords` 响应中仍然可见，但不能用于过滤表达式。

#### 阶段 3：检索

元数据已被索引并写入你的记忆记录之后，你现在可以把语义搜索与元数据过滤器结合起来限定结果范围。AgentCore Memory 采用**预过滤**架构：元数据过滤器在向量相似度搜索运行*之前*就被应用。这会先缩小候选集，使 K 近邻（KNN）搜索在一个更小、更相关的子集上运行。请注意下面的示例：在语义搜索匹配“账单问题”之前，结果已经被限定为仅来自当前年度的高优先级记录。

```
results = agentcore_client.retrieve_memory_records(
    memoryId="mem-support-abc123",
    namespace="support/customer-123",
    searchCriteria={
        "searchQuery": "billing issues",
        "topK": 10,
        "metadataFilters": [{
                "left": {"metadataKey": "priority"},
                "operator": "EQUALS_TO",
                "right": {"metadataValue": {"stringValue": "high"}}
            },
            {
                "left": {"metadataKey": "x-amz-agentcore-memory-createdAt"},
                "operator": "AFTER",
                "right": {"metadataValue": {"dateTimeValue": "2026-01-01T00:00:00Z"}}
        }]
    }
)
```

注意，把自定义元数据过滤器与系统生成的时间戳结合使用，可以在相似度搜索运行之前沿着业务优先级和时间新近性这两个维度压缩候选集。AgentCore Memory 提供了[多种操作符](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/long-term-memory-metadata.html#long-term-memory-metadata-query)，覆盖常见的查询模式。

AgentCore Memory 还会添加使用 `x-amz-agentcore-memory-*` 前缀的服务生成元数据字段，你可以用同样的过滤操作符查询它们，从而无需自定义 datetime 键即可支持时间范围查询。

#### 为什么时间过滤带来最大的准确率提升

在我们的实验中，带时间边界约束的查询在启用元数据过滤后提升最为明显。使用 `BEFORE` 和 `AFTER` 操作符的结构化 DATETIME 过滤会把这类查询转化为确定性的索引查找，从而避免歧义。

对于不基于搜索的检索，`ListMemoryRecords` 可以在没有语义搜索的情况下提供元数据过滤。当你需要枚举符合特定元数据条件的记录、而非查找语义相似的内容时，这很有用。例如，你可以列出某客户的高优先级记录，或拉取带有特定部门标签的记录。

下面的示例列出在某个特定日期之后创建的高优先级记录：

```
records = agentcore_client.list_memory_records(
    memoryId="mem-support-abc123",
    namespace="support/customer-123",
    metadataFilters=[
        {
            "left": {"metadataKey": "priority"},
            "operator": "EQUALS_TO",
            "right": {"metadataValue": {"stringValue": "high"}}
        },
        {
            "left": {"metadataKey": "x-amz-agentcore-memory-createdAt"},
            "operator": "AFTER",
            "right": {"metadataValue": {"dateTimeValue": "2024-01-20T00:00:00Z"}}
        }
    ]
)
```

## 企业用例

下面的示例展示了元数据过滤如何在各行业中应对常见的企业检索挑战。

### 多租户 SaaS 应用

如果你经营一家为多个企业客户提供 AI 助手的 SaaS 公司，命名空间已经提供了主要的租户隔离，每个租户的记忆都存放在像 `/tenants/{actorId}/` 这样的专用命名空间中。元数据在这些边界内部增加细粒度过滤，加入业务维度。通过索引 `customer_segment`、`department` 或 `subscription_tier` 这类元数据键，你可以把检索直接映射到业务层级，而无需为每个组织维度维护独立的记忆存储。

**分层组织过滤：** 在租户的命名空间内，元数据支持下钻式检索，把范围限定到具体的部门、团队或项目。例如，当一位平台工程师询问认证服务的问题时，你可以只取回带有 `department: "engineering"` 和 `team: "platform"` 的记忆。这可以直接映射到企业组织架构图，而无需为每个组织单元建立独立的命名空间。

**感知订阅层级的检索：** SaaS 模式可以用元数据按客户层级区分记忆行为。企业级租户可能获得完整历史检索，而入门级租户只获得限定在近期记忆内的检索（使用 `x-amz-agentcore-memory-createdAt` 上的 `AFTER` datetime 过滤器）。这在记忆层支持功能分级，而无需为每个层级部署独立的基础设施。

### 医疗健康与合规敏感领域

如果你的医疗健康 AI agent 管理跨多个部门的患者交互，像 `patients/patient-123` 这样的命名空间已经隔离了每位患者的记忆。但在单个患者的命名空间内，对“用药史”做宽泛搜索会返回每个部门的结果：心血管科、内分泌科和初级保健。通过索引 `department`、`record_type`、`severity` 和 `symptoms` 这类元数据键，agent 可以在患者命名空间内沿着多个临床维度收窄检索。

```
results = agentcore_client.retrieve_memory_records(
    memoryId="mem-healthcare-001",
    namespace="patients/patient-123",
    searchCriteria={
        "searchQuery": "medication history",
        "topK": 10,
        "metadataFilters": [
            {
                "left": {"metadataKey": "department"},
                "operator": "EQUALS_TO",
                "right": {"metadataValue": {"stringValue": "Cardiology"}}
            },
            {
                "left": {"metadataKey": "symptoms"},
                "operator": "CONTAINS",
                "right": {"metadataValue": {"stringValue": "chest pain"}}
            }
        ]
    }
)
```

`symptoms` 这个 STRINGLIST 上的 `CONTAINS` 操作符会检查列表是否包含指定的值，从而把检索限定到特定的临床指标。

在合规方面，元数据过滤有助于对齐监管要求。

- **HIPAA**：部门级过滤确保心血管科医生的查询只取回与心血管科相关的记录，降低暴露无关临床数据的风险。
- **GDPR**：`x-amz-agentcore-memory-createdAt` 上的元数据过滤器有助于识别保留窗口之外的记录。你可以通过 `DeleteMemoryRecord` 或按命名空间范围删除来处理删除。
- **SOC 2**：系统生成的时间戳提供了一条可验证的轨迹，证明检索被正确地限定了范围。你还可以索引 `data_classification` 键（取值如 `PII`、`confidential` 或 `general`）来实现感知敏感度的检索。

### 基于优先级路由的客户支持

如果你的支持组织要处理数千个工单，你需要 agent 能依据紧急程度和升级状态来排列上下文的优先级。元数据支持像“找出最近 30 天的高优先级账单记忆”这样的检索模式，做法是把自定义元数据过滤器与系统时间戳过滤器结合起来。在实时会话中，agent 会拉取最相关的高优先级上下文，而不必在已解决的、低优先级的工单中跋涉。当工单从低升级到紧急时，合并规则会让整合后记忆上的元数据与最新的升级状态保持一致，而不是停留在最初的分类。

### 金融服务与时间精度

金融数据天然对时间敏感。关于“第三季度投资组合讨论”的查询必须返回 Q3 专属的记录，而不是其他季度的记录。财富管理 agent 可以把 DATETIME 过滤与自定义元数据结合起来精确限定检索范围，从而帮助避免来自其他资产类别和时间段的噪声：

```
results = agentcore_client.retrieve_memory_records(
    memoryId="mem-wealth-001",
    namespace="clients/client-789",
    searchCriteria={
        "searchQuery": "portfolio rebalancing strategy",
        "topK": 10,
        "metadataFilters": [
            {
                "left": {"metadataKey": "asset_class"},
                "operator": "EQUALS_TO",
                "right": {"metadataValue": {"stringValue": "equities"}}
            },
            {
                "left": {"metadataKey": "x-amz-agentcore-memory-createdAt"},
                "operator": "AFTER",
                "right": {"metadataValue": {"dateTimeValue": "2024-07-01T00:00:00Z"}}
            },
            {
                "left": {"metadataKey": "x-amz-agentcore-memory-createdAt"},
                "operator": "BEFORE",
                "right": {"metadataValue": {"dateTimeValue": "2024-09-30T23:59:59Z"}}
            }
        ]
    }
)
```

### 多 agent 系统与记忆协同

随着 agent 系统日益成熟并变得更加普遍，元数据对于多个 agent 如何通过共同的记忆层共享与协同变得至关重要。

- **Agent 来源（provenance）：** 在多 agent 工作流中，知道一条记忆由哪个 agent 创建，对于信任、调试和路由都至关重要。通过索引 `source_agent`、`agent_role` 和 `workflow_step` 这类键，supervisor agent 可以过滤出由特定 agent 存储的记忆。例如，你可以在客户的命名空间内过滤 `source_agent: "billing_agent"`，来回答“账单 agent 在上次会话中得出了什么结论？”
- **Agent 范围的记忆可见性：** 在多 agent pipeline（分诊机器人到一线 agent 再到专家）中，你可以用元数据控制每个 agent 能取回哪些记忆。分诊机器人写入的记忆带有 `workflow_step: "triage"`。处理升级事件的专家会按 `workflow_step: "triage"` 过滤，以了解最初的分类；或按 `agent_role: "tier1"` 过滤，以复核已经尝试过什么，避免重复工作。为 `agent_role` 自定义的 `llmExtractionInstruction` 会整合记忆以反映专业度最高的处理结果，而不只是最近一次接触。
- **检索增强生成（RAG）pipeline 中由元数据把守的检索：** 检索 agent 按 `source_type: "knowledge_base"` 过滤以获取事实依据；个性化 agent 按 `interaction_type: "preference"` 过滤以获取用户特定上下文；安全 agent 按 `content_flag: "reviewed"` 过滤以获取经审核的内容。三者查询同一个命名空间，却得到完全不同的结果集，而无需维护多个记忆存储。

## 元数据 schema 演进

生产环境的记忆系统并非一成不变，元数据 schema 需要与它所服务的应用一同演进。AgentCore Memory 通过**仅追加**（additive-only）的更新模型支持 schema 演进。你可以按需向已有的记忆资源添加新的索引元数据键：

```
agentcore_client.update_memory(
    memoryId="mem-support-abc123",
    addIndexedKeys=[
        {"metadataKey": "customer_segment", "metadataValueType": "STRING"}
    ]
)
```

新键会立即对新到达的事件和记忆记录可用。已有记录不会追溯获得新字段，但随着旧记忆与较新的记忆一起经历整合，它们会自然获得新的元数据。你无法移除此前已索引的键，这有助于防止在现有数据上意外丧失过滤能力。随着抽取需求演进，你可以自由添加、移除或修改策略级元数据 schema 中的非索引键。

## 最佳实践

**从 agent 真正需要的过滤维度开始。** 不要一开始就索引所有想得到的元数据字段。每个被索引的字段都会占用一个索引键配额，并在两条路径上增加成本：摄取时每次写入要做更多工作，读取时的查询压缩也带来额外开销。先从三到五个直接影响检索质量的键开始，等具体需求出现时再增加。

**编写清晰、具体的定义。** `definition` 字段与 `llmExtractionInstruction` 合起来是 LLM 在元数据抽取时收到的主要指令。不要写“工单的优先级”，而应写“基于客户影响的问题优先级。对影响生产的服务中断使用 ‘critical’，对性能下降使用 ‘high’，对功能请求使用 ‘medium’，对文档或外观类问题使用 ‘low’。”

**选择与领域语义相符的合并规则。** 对大多数字段来说，`LATEST_VALUE` 是安全的默认值，但并不总是正确。对于支持升级工作流中的 `agent_type`，应当保留资历最高的 agent 类型，而不是最新的那个。自定义合并指令可以表达这种领域逻辑。

**用校验规则约束 LLM 输出。** 在 `validation` 字段中定义 `allowedValues`，以强制使用受控词表。没有校验时，LLM 可能对同一概念产出“High”、“high”、“HIGH”或“critical”，从而破坏下游的过滤匹配。

**为事件驱动路径而设计**，适用于那些在事件时刻就已知、并且在一次会话的多个事件之间保持不变的键（例如 `department` 或 `tenant_tier`）。把元数据附加到事件上，让 AgentCore Memory 在抽取过程中传播它，从而实现自动的冲突消解与整合处理。把直接批量 API 路径留给批量导入和预处理内容，这些场景下你已经知道正确的元数据值。

**在策略层面规划元数据 schema。** 每个记忆策略都可以有自己的元数据 schema，使不同策略能以不同方式抽取和处理相同的键。语义策略可能使用自定义抽取指令从对话上下文中分类优先级，而摘要策略可能使用针对摘要专用元数据调优的不同定义。这种灵活性支持按策略优化元数据处理，同时不损害共享的索引键基础设施。

**谨慎对待批量创建记录上的 `memoryStrategyId`。** 当你在批量创建请求中包含 `memoryStrategyId` 时，服务会把输入的元数据过滤为该策略 schema 中的键，其他键会被静默丢弃。这对于强制与抽取产出的记录保持一致很有用。当你省略它时，payload 中的元数据会原样存储。请根据用例来选择：对需要与抽取产出的记录保持一致的场景，采用 schema 强制的一致性；对你在外部管理元数据的批量导入，则需要完全控制。

**用非索引的 schema 键做上下文增强。** 并非每个元数据键都需要可过滤。未声明为索引键的 schema 键仍会写入抽取出的记录，并在 get 与 list 响应中可见，但不能用于过滤表达式。对于为下游消费方丰富记录内容、又不想消耗索引键配额的元数据（例如 `sentiment`、`summary_notes` 或 `source_url`），这很有用。把索引键留给你会主动过滤的维度。

**对已经知道的值使用确定性抽取。** 如果某个键代表 agent 在创建事件时就已掌握的固定组织属性，例如 `department`、租户层级或合规范围，就把它配置为 `STRICTLY_CONSISTENT`，并在每个事件上都提供它。这能保证最终记录上的取值精确无误，并消除 LLM 抽取可能引入的归一化漂移（“eng”与“Engineering”之分）。把 `llmExtractionConfig` 留给必须从对话内容推断的维度，例如情感或主题。

**避免这些反模式：**

- 不要索引描述或全名这类高基数的自由文本字段，它们会膨胀索引却没有有用的过滤边界。
- 不要用元数据承载每次交互都会变化的值；元数据对稳定或缓慢变化的属性最有效。
- 不要仅靠元数据复制命名空间隔离。没有命名空间隔离的 `tenant_id` 元数据字段是一种“靠约定实现的安全”模型，只要漏掉一个过滤器就会失效。

## 结论

AgentCore Memory 中的元数据过滤解决了一个根本性的检索挑战。命名空间已经按用户、租户或项目等主要实体隔离了记忆。在命名空间范围之上叠加结构化元数据过滤，你可以在相似度匹配运行之前就把 agent 的检索收窄到精确的上下文边界，带来可度量的准确率提升，并为合规、基于优先级的上下文管理和细粒度组织过滤提供实用基础。由 LLM 驱动的抽取免去了人工打标签的负担，而可配置的抽取指令则在大规模下处理元数据的传播与冲突消解。

要开始使用，先确定三到五个对你的用例检索质量影响最直接的过滤维度。用一个假的记忆资源做概念验证（PoC），测试相关策略，然后随着具体需求出现再扩展 schema。以下资源提供了实操指引：

- [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html)。
- [AgentCore Memory 代码示例](https://github.com/awslabs/agentcore-samples/tree/main/01-features/04-manage-context-of-your-agent/memory)。
