# Wipro PARI 如何使用 Amazon Bedrock 加速 PLC 代码生成

*本文由 Wipro Enterprises Limited 的 Rejin Surendran 与 ShellKode 的 Bakrudeen K 共同撰写。*

在制造环境中，工业自动化工程师面临着一项重大挑战：如何快速把复杂的工艺需求转换成可编程逻辑控制器（PLC）梯形图文本代码。这一传统的人工流程通常每个查询要花 3–4 天，在生产工作流中形成瓶颈。其复杂性来自多方面因素：工程师必须把高层需求细致地转换为精确的机器指令，同时管理多个状态与转换；还要满足国际 PLC 编程标准 [IEC 61131-3](https://en.wikipedia.org/wiki/IEC_61131-3) 的合规要求，处理复杂的变量声明，维护用于工业合规的详细文档，并对安全协议与执行路径进行充分测试。

[Wipro PARI](https://www.wipropari.com/) 是全球最大的自动化公司之一，拥有 3,000 多名员工，在世界多地设有工厂，总部位于印度浦那。Wipro PARI 的愿景是利用自身的专业能力与资源，为客户带来自动化与机器人领域的最佳解决方案。

在本文中，我们分享 Wipro 如何运用先进的 prompt 工程技巧、自定义校验逻辑与自动化代码纠错，借助 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 大规模简化工业自动化代码的开发。我们会介绍整体架构与关键用例，解释核心组件与工作流，并分享真实成效，展示其对制造运营的变革性影响。

## 为什么 Wipro PARI 选择 Amazon Bedrock？

Wipro PARI 与 AWS、ShellKode 合作，开发出一套创新方案，借助 AI 改造这一耗时的 PLC 代码生成流程。使用 Amazon Bedrock 与 Anthropic 的 Claude 模型，我们构建了这样一个系统：

- 把 PLC 代码生成时间从 3–4 天缩短到每个需求约 10 分钟
- 把代码准确率提升至最高 85%
- 自动完成针对行业标准的校验
- 自动处理复杂的状态管理与转换逻辑
- 便于实现规范的变量声明与命名约定
- 维护合规文档与审计轨迹
- 为工业工程师提供易用的界面

Wipro PARI 之所以选择 Amazon Bedrock 作为这套 PLC 代码生成方案的基础，是因为其企业级能力的独特组合与工业自动化需求高度契合。借助 Amazon Bedrock 中丰富的模型选择，团队可以用 Anthropic 的 Claude 3.5 Sonnet 完成复杂代码生成，同时保持灵活性：当更新、更强的版本出现时，无需改动基础设施即可切换模型。这项全托管服务降低了托管与扩缩机器学习（ML）基础设施的运维负担，帮助 Wipro PARI 的工程师专注于领域特定的自动化逻辑，而不是模型部署。

对工业应用而言至关重要的是，Amazon Bedrock 确保客户数据——包括专有控制逻辑与制造规范——保留在 AWS 环境内，且不会被用于训练底层基础模型（FM），从而维持严格的数据隐私与知识产权保护。这种安全态势结合 AWS 的合规认证，提供了处理敏感运营数据的制造环境所需的企业级治理能力。

### 架构组件

该架构由以下关键组件构成：

- **前端客户端层**——前端客户端层由一个基于 React 的响应式 Web 应用构成，使工业工程师能够上传控制逻辑电子表格、配置生成参数，并以完整的可追溯性核验生成的梯形图代码。
- **后端应用服务层**——WIPRO PARI 方案采用 React 与 [FastAPI](https://fastapi.tiangolo.com/) 微服务架构，在安全虚拟私有云（VPC）环境中的负载均衡 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2/)（Amazon EC2）实例上部署了 30 多个专用 API，用于工业自动化 PLC 代码生成，并计划在后续迭代中迁移到 [Amazon Elastic Container Service](https://aws.amazon.com/ecs)（Amazon ECS）。VPC 配置包含公有与私有子网隔离，并配合堡垒机访问控制，实现对工业控制系统开发服务的安全远程管理。后端应用服务层划分为多个独立组件，包括处理请求的控制器、承载业务逻辑的核心服务、管理用户身份的认证模块、处理电子表格的文件处理引擎，以及从工业自动化文档中提取控制逻辑规范的电子表格解析器。
- **AI/ML 处理层**——方案包含专门的 AI/ML 处理层，与 Amazon Bedrock 集成，并根据任务复杂度与需求使用多种 Anthropic Claude 模型。大语言模型（LLM）集成服务把控制逻辑需求转换成结构化的中间伪查询，再经多轮迭代处理转换为标准化的 PLC 梯形图文本代码。系统可处理复杂的工业自动化场景，包括制造控制系统中常见的并行执行路径、fork/de-fork 逻辑与布尔表达式。
- **数据与存储层**——生成的 PLC 代码会经过智能纠错，修复梯形图逻辑编程特有的语法与逻辑错误，随后按预定义工业准则进行系统化校验，以保证代码质量与安全合规。[Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）存储桶用于存放生成的代码产物、模板与版本历史，服务于工业项目管理。系统使用 [Amazon Relational Database Service (Amazon RDS) for PostgreSQL](https://aws.amazon.com/rds/postgresql/) 数据库进行持久状态管理、项目跟踪，并维护控制逻辑规范与生成代码之间的关联。

### 用户工作流

代码生成工作流包含以下步骤：

- **用户输入与身份认证**——工业工程师登录 React Web 应用，通过基于角色的访问控制完成认证，并上传 Excel 电子表格。
- **数据处理与转换**——系统通过 Excel 解析器处理上传的电子表格，其中包含 PLC 编程需求的控制逻辑规范。它提取控制逻辑数据，按工业标准校验输入规范，并把原始数据转换为适合 AI 处理的结构化格式。
- **AI 驱动的代码生成**——LLM 集成服务使用 Anthropic 的 Claude 3.5 Sonnet，把结构化需求发送到 Amazon Bedrock；后者生成中间伪查询，将其转换为标准化 PLC 梯形图文本代码，并处理包括并行执行路径与布尔表达式在内的复杂工业自动化场景。伪查询是一种中间结构化表示，把 Excel 电子表格中人类可读的控制逻辑需求转成标准格式，以便 AI 模型处理并生成 PLC 代码。**示例规范**——当温度 > 80°C 且压力 < 5 bar 时，打开冷却泵。**伪查询**——`IF (TEMP_SENSOR > 80) AND (PRESSURE_SENSOR < 5) THEN SET COOLING_PUMP = TRUE`
- **校验与存储**——生成的 PLC 代码按 [IEC 61131-3](https://en.wikipedia.org/wiki/IEC_61131-3) 标准接受自动化质量校验，智能纠错修复语法与逻辑错误，通过校验的代码产物存入 Amazon S3，并具备版本控制与可追溯性。
- **工程师复核**——工业工程师通过 Web 界面复核生成的梯形图代码，核验代码质量与安全合规性，下载通过校验的 PLC 代码用于部署，并以完整的审计轨迹维护项目历史，满足工业合规要求。

- 用户通过 UI 界面以上传电子表格的方式提供控制逻辑作为输入。

## PLC 代码生成器

为了最大限度地提升梯形图文本生成的准确率，方案采用精细的 prompt 工程技术，并使用 Anthropic 的 Claude 3.5 Sonnet 进行代码生成。方案中这一部分的工作流步骤如下图所示。

![PLC 代码生成器](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/14/image-5-6.png)

### 构造 prompt

prompt 构造过程包含以下步骤：

- 来自数据格式化器的中间伪查询被传入 PLC 代码生成器模块，由后者启动 prompt 构造过程。
- prompt 构造器构建一条详细的任务 prompt，用于生成首批 PLC 代码，后续批次亦然。其中包含：PLC 编程领域知识（状态/转换变量命名约定、fork/de-fork 的网络创建模式、条件网络结构）；演示伪查询到梯形图文本转换的 few-shot 示例；关于处理状态转换、变量声明与复杂布尔表达式的明确指令。
- prompt 构造器还会创建续写 prompt（continuation prompt），指示 FM 从上一轮迭代中断处继续生成 PLC 代码。

### Few-shot 采样

我们采用 few-shot 学习策略，通过在 prompt 上下文中提供相关示例来生成领域特定的输出。伪查询及相关元数据（包括状态转换、动作、控制流模式等结构特征）被索引到向量库中。推理时，一种混合检索策略结合语义相似度与基于元数据的词法匹配，取回结构上最对齐的示例及其对应的 PLC 代码，再动态注入 prompt。见下面的代码：

```
PLC_PROMPT = """You are expert in writing code in PLC text ladder code …
##DYNAMIC EXAMPLES
{retrieved_examples}
##DOMAIN VARIABLES
{business_specific_variables}
##USER INPUT
{user_pseudo_code}
##FUNCTIONAL GUIDELINES
{custom_instructions}
"""
```

### PLC 代码生成

PLC 代码生成过程包含以下步骤（编号与上图对应）：

- 任务 prompt 被传给 Anthropic 的 Claude 3.5 Sonnet，它处理该 prompt 并生成初始梯形图文本代码，最多包含 4,096 个 token（即该 FM 的最大输出 token 上限）。
- 由于梯形图文本通常会超出这一上限，我们的方案采用迭代生成方法，配合专门的续写 prompt。系统会检查生成是否完成，并按需请求额外的续写 prompt。
- 这种续写方法在连续生成之间保持上下文，有助于维持整个代码库的一致性。
- 该过程迭代进行，直到完整生成 PLC 梯形图代码。随后，已完成的代码片段被合并并传给代码纠错模块做进一步处理。

下面的代码块展示了一段生成的 PLC 代码示例：

```
FUNCTION_BLOCK "Machine_Safety_Monitoring"
{ S7_Optimized_Access := 'FALSE' }
VERSION : 0.1
   VAR_INPUT 
      iSafetyDoorClosed : Bool;
      iEmergencyButtonReleased : Bool;
      iEmergencyButtonPressed : Bool;
      iAutoRunning : Bool;
      iReset_fault : Bool;
   END_VAR

   VAR 
      s25_MchSafetyCheck : Bool;
      s25_MchSafetyCheck_T1 : Bool;
      s25_MchSafetyCheck_T2 : Bool;
      SEQ01_ResetComplete : Bool;
      sStWtResetRel_T1 : Bool;
   END_VAR

NETWORK
TITLE = Transition for STATE Num:25 Machine Safety Check
      A #s25_MchSafetyCheck;
      AN #sStWtResetRel;
      A #sSst;
      A #iSafetyDoorClosed;
      A #iEmergencyButtonReleased;
      = #s25_MchSafetyCheck_T1;
      A #s25_MchSafetyCheck;
      AN #sStWtResetRel;
      A #sSst;
      AN #iSafetyDoorClosed;
      O #iEmergencyButtonPressed;
      = #s25_MchSafetyCheck_T2;
NETWORK
TITLE = STATE Num:25 Machine Safety Check
      A(;
      O #s25_MchSafetyCheck;
      O #sStWtResetRel_T1;
      );
      AN #sStWtResetRel;
      AN #s25_MchSafetyCheck_T1;
      AN #s25_MchSafetyCheck_T2;
      = %L1.0;
      A %L1.0;
      BLD 102;
      = #s25_MchSafetyCheck;
      A %L1.0;
      JNB Label_25;
      L 25;
      T #StateNo;
Label_25:      NOP 0;
```

## 代码纠错器

由于 PLC 梯形图逻辑本身就很复杂，LLM 在初始代码生成时可能遗漏关键功能。方案引入了精细的纠错系统来弥补这些缺口并保证高质量输出。纠错采用混合方式：既包含承载业务准则的自定义逻辑，也使用 FM 来执行纠错任务。下图展示了该工作流。

![PLC 代码纠错器](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/11/14/image-7-5.png)

纠错模块执行以下步骤以帮助提升代码准确率：

- 由生成器模块生成的 PLC 代码被移交到纠错模块进行增强。
- 该模块负责正确处理并行执行路径：序列在此分裂为多个分支、之后又重新汇合，同时在整个 PLC 程序中保持正确的逻辑流。这一步通过调用 Anthropic 的 Claude 3.7 Sonnet 完成；该模型提供复杂并行执行路径修正所需的增强推理能力，调用时携带专门的 prompt 与生成的 PLC 代码。节点/网络映射脚本用于跟踪状态转换与序列跟踪。
- 该模块借助格式化器提取的数据（包括存放在 Amazon S3 中的转换变量源状态与目标状态）经历以下阶段：**识别阶段**——使用专门的 Python 算法分析 PLC 代码结构，并把转换变量与其声明的源状态和目标状态交叉比对，标记出错误连接。**修复阶段**——使用有针对性的 Python 例程系统化地移除错误连接，同时保持整体逻辑结构的完整性。**重建阶段**——实现自定义 Python 逻辑，按正确的顺序执行模式在各状态之间建立正确连接。
- 生成的代码可能包含语法错误、未声明的变量或不符合规范的命名。使用 Anthropic 的 Claude 3.5 Sonnet 与自定义逻辑，这一过程包括：找出代码中使用但未声明的缺失变量；把缺失变量补充到声明区；规范化变量名，确保变量遵循 Siemens S7-1517 PLC 命名约定。
- 纠错后的 PLC 代码及相关元数据存入 Amazon S3。

## 代码评估器

纠错之后，代码还要经过一轮全面校验：

- 校验模块根据关键准则分析纠错后的梯形图文本：**唯一状态标志**——核验每个状态都有唯一标识符且无重复。**唯一转换标志**——确认转换标识符在整个代码中唯一。**连接正确性校验**——校验每个转换都连接到正确的目标状态。**输入转换完整性**——确保每个状态至少有一个可触发状态变化的输入转换条件。**条件互斥**——检查同一状态内的转换变量彼此互斥，以帮助防止逻辑冲突。
- 对每项校验，系统都会给出详细的通过/失败结果，并附上检测到问题的具体信息。
- 系统汇总生成一份全面的校验报告，突出显示仍需工程师人工关注的问题，并清楚标明其在代码中的位置与性质。
- 这种多层次的纠错与校验方法显著有助于提升生成的梯形图文本质量，减少人工干预的需求，加快整体代码开发流程。

## 结语

在本文中，我们探讨了 AWS 如何与 Wipro PARI 合作，开发出由 AI 驱动的 PLC Code Generator，改造根据给定控制逻辑创建梯形图文本代码这一耗时流程。通过使用 Amazon Bedrock 配合多种 Anthropic Claude 模型以及一套自定义校验框架，该方案实现了 85% 的平均准确率，同时把代码生成时间从 3–4 天缩短到每个查询约 10 分钟。

Wipro PLC Code Generator 代表了工业自动化编程领域的一个里程碑，直接回应了 Wipro PARI 工程顾问所面临的生产力挑战。该方案的做法——把 prompt 工程、迭代式代码生成、自动纠错与系统化校验结合起来——形成了一个稳健的框架，可应用于各种 PLC 编程场景。

在当前实现的基础上，Wipro PARI 计划利用更多 Amazon Bedrock 功能扩展该方案的能力。团队将实施 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 以帮助执行内容过滤策略，在模型输出层面防止生成不安全的控制逻辑，并促进对 IEC 61131-3 标准的合规。路线图包括使用 [AWS Strands Agents](https://docs.aws.amazon.com/prescriptive-guidance/latest/agentic-ai-frameworks/strands-agents.html) 构建多 agent 工作流——这是一个为自主 AI agent 设计的开源 SDK——由专门的 agent 分别处理不同任务：一个 agent 负责需求分析，另一个负责代码生成，第三个负责自动化文档生成。为在生产环境中扩展这些 agent，Wipro PARI 将使用 [Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)，它提供无服务器基础设施，以企业级安全性、会话隔离与内置身份管理来部署和扩展 agent。[Amazon Bedrock AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-get-started.html) 将使系统能够跨工程会话保持上下文，让 agent 记住此前的交互并在既有工作之上继续推进；[Amazon Bedrock AgentCore gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-using.html) 则帮助把 agent 安全地连接到现有的 PLC 校验工具与内部自动化系统。Wipro PARI 打算构建用于自动化测试、安全扫描与自动化文档生成的 agent。此外，Wipro PARI 计划通过引入更多校验规则、改进 UI，以及增加对复杂序列类型的支持并与 SIEMENS 软件集成以实现代码直接部署，来扩展该方案。

随着工业自动化的复杂度持续演进，像 Wipro PLC Code Generator 这样的 AI 辅助编程工具有助于加快开发周期并提升代码质量。通过减轻代码生成与校验的人工负担，工程师可以专注于系统优化与创新等更高价值的任务，最终助力各行业实现更高效、更可靠的制造运营。
