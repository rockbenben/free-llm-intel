# 在 Amazon Bedrock 上对开放权重模型使用提示缓存

许多生成式人工智能应用程序都会为每个请求发送相同的长上下文，并且提示缓存可以避免每次都再次处理它。该上下文可以是系统提示、参考文档、工具定义或迄今为止的对话。 Amazon Bedrock 上的开放权重模型可以跨请求重用它，这有助于降低输入成本和响应延迟。

[提示缓存](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html) 重用匹配提示前缀的计算状态，因此从缓存中读取重复的上下文，而不是再次处理。 Amazon Bedrock 为您管理缓存。根据模型的不同，您可以使用自动运行的隐式缓存和/或标记可重用前缀的显式缓存。您重复使用的上下文越多、重复使用的频率越高，您可以节省的资源就越多。

与 Amazon Bedrock 上的其他模型一样，您的提示和输出不会与模型提供商共享或用于训练模型。有关更多信息，请参阅 Amazon Bedrock 用户指南中的[数据保护](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html)。

Amazon Bedrock 上的开放权重模型现在支持显式提示缓存。在这篇文章中，我们通过 [Chat Completions API](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-chat-c​​ompletions.html) 将这两种模式与开放权重模型一起使用，并展示如何从每个响应中读取缓存使用情况。然后，我们将隐式缓存应用于同一 API 上的 OpenCode 编码代理会话，并以最佳实践结束。

## 在 Amazon Bedrock 上提示缓存开放权重模型

当请求以与先前请求相同的内容开始时，Amazon Bedrock 从缓存中读取该前缀并仅处理其余部分。缓存读取的计费费率低于标准输入，因此每次重用前缀时，节省的费用都会增加。根据型号的不同，缓存写入的计费费率可能高于标准输入的费率。有关每个型号的费率，请参阅 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)。

支持的模式取决于型号和 API。有关每个模型的缓存模式、最小前缀长度以及条目的缓存时间，请参阅[模型概览](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards.html)。两种模式对比如下：

| **功能** | **隐式缓存** | **显式缓存** |
| --- | --- | --- |
|请求更改 |无 |在聊天完成 API 上，“prompt_cache_options”模式设置为显式，加上一个或多个“prompt_cache_breakpoint”标记 |
|缓存了什么 |尽最大努力自动选择符合条件的前缀 |直到并包括每个断点的内容 |
|身材好|已经以稳定前缀开头的提示，例如对话和代理循环 |带有变化问题的固定共享前缀，或您想要控制的分层前缀 |

**隐式缓存**：Amazon Bedrock 会尽力自动重用符合条件的前缀。在对话中，每个请求都会重新发送完整的上下文，因此前一个请求将成为下一个请求的缓存前缀（图 1）。正如[提示缓存指南](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)建议的那样，将静态内容放在前面，将动态内容放在最后。保持提示的开​​头稳定可以让以后的每个请求重用它。如果早期部分发生更改（如图 1 的第 4 步所示），将从该点重建缓存。

![对话轮流重用每个先前的请求作为缓存的前缀，并在早期轮流发生变化时重建缓存](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22160-1.gif)

图 1：对话轮次中的隐式提示缓存

**显式缓存**：您使用缓存断点标记每个可重用前缀的末尾。您可以添加多个断点（最多可达模型支持的最大断点）来缓存以不同速率变化的层，如图 2 所示。每个断点之前的内容都会写入缓存一次，然后在以后的请求中读取，并且在每个请求上处理最后一个断点之后的内容。检查模型卡中断点之前的最小令牌计数、断点的最大数量以及生存时间 (TTL)，该时间会在每次缓存命中时重置。

![标记共享前缀结尾的缓存断点，缓存一次，然后在以后的请求中读取](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22160-2.gif)

图 2：在共享前缀后使用断点进行显式提示缓存

通过隐式缓存，Amazon Bedrock 还可以将内容写入缓存，以后的请求永远不会重复使用，例如每次都不同的问题。当共享前缀后面的内容在每次请求时发生更改时，请使用显式缓存来限制对共享前缀的缓存写入。最后一个断点之后的内容按标准输入费率计费。在对缓存写入收取更高费用的模型上，您无需为从不读回的内容支付更高的写入速率。

## 通过 Chat Completions API 缓存产品手册

该示例是虚构的水过滤器 AnyCompany AquaPure 500 的支持助手。系统提示符包含一行指令和用户手册，这是可重复使用的前缀。每个请求都会询问不同的客户问题。

### 设置客户端

这些示例将 OpenAI Python SDK 与 Amazon Bedrock Chat Completions 终端节点结合使用。对于身份验证，“aws-bedrock-token-generator”包中的“provide_token()”函数会将您的 AWS 凭证转换为[短期 Amazon Bedrock API 密钥](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html)，有效期最长为 12 小时。您不需要创建或存储长期密钥。

1.创建虚拟环境并安装软件包：
```
python3.12 -m venv .venv
source .venv/bin/activate
pip install "openai>=3.26.0" "aws-bedrock-token-generator>=1.1.0"
```
2. 创建手册。我们的 Markdown 代币大约有 4,000 个。以下摘录显示了其格式：
```
# AnyCompany AquaPure 500 Owner's Manual

### 7.1 Replacement schedule
| Stage | Cartridge | Part number | Replace every |
| ----- | ------------------- | ----------- | ------------- |
| 1 | Sediment pre-filter | AP-F1 | 6 months |
| 4 | Carbon post-filter | AP-F4 | 12 months |

### 9. Error codes
| Code | Description | What to do |
| ---- | ----------------------- | -------------------------------------------- |
| E01 | Low feed water pressure | Check that the feed water valve is open. |
| E07 | Drain line restriction | Check the black concentrate tube for kinks. |

### 11. Warranty
- Faucet: 3 years from the date of purchase. The 3 V cell is not covered.
```
将其另存为“manual.md”并添加部分，直到其长度超过型号卡上的最小前缀长度。占位符文本有效，因为缓存只需要相同的前缀。保留显示的三个部分，它们回答了示例问题。

3. 将以下设置代码保存为同一目录中的“common.py”。您接下来创建的示例将从中导入。
```
from pathlib import Path

from aws_bedrock_token_generator import provide_token
from openai import OpenAI

REGION = "<AWS_REGION>"
MODEL_ID = "<MODEL_ID_OR_INFERENCE_PROFILE_ID>"

MANUAL = Path(__file__).with_name("manual.md").read_text()

SYSTEM_PROMPT = (
    "You are the AnyCompany AquaPure support assistant. Answer the customer's question in at "
    "most three sentences, using only the owner's manual below.\n\n" + MANUAL
)

QUESTIONS = [
    "My filter shows error code E07. What does it mean and how do I fix it?",
    "How often do I need to replace the AP-F4 post-filter?",
    "Is the 3 V battery in the smart faucet covered by the warranty?",
]

# Chat Completions API client: the OpenAI SDK pointed at the Amazon Bedrock OpenAI-compatible endpoint
client = OpenAI(
    api_key=provide_token(region=REGION),
    base_url=f"https://bedrock-runtime.{REGION}.amazonaws.com/openai/v1",
)


def report(call_number, response):
    """Print the cache fields from the response usage."""
    usage = response.usage
    read = usage.prompt_tokens_details.cached_tokens or 0
    written = usage.prompt_tokens_details.cache_write_tokens or 0
    print(
        f"Call {call_number}: prompt_tokens={usage.prompt_tokens} cached_tokens={read} "
        f"cache_write_tokens={written} uncached={usage.prompt_tokens - read - written}"
    )
```
如果您的模型返回推理标记，它们将计入“max_tokens”。示例设置“max_tokens=1024”，以便简短的答案有空间完成。

## 隐式缓存

隐式缓存不需要缓存控制。将手册放在系统消息中，将问题放在用户消息中。将两者作为一条用户消息的一部分发送不会获得隐式缓存命中。将以下内容保存为“implicit.py”并使用“pythonimplicit.py”运行它：
```
from common import MODEL_ID, QUESTIONS, SYSTEM_PROMPT, client, report

for i, question in enumerate(QUESTIONS, start=1):
    response = client.chat.completions.create(
        model=MODEL_ID,
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT}, # static, same every call
            {"role": "user", "content": question}, # changes every call
        ],
        max_tokens=1024,
    )
    report(i, response)
```
### 验证隐式缓存

每个响应都会报告“usage.prompt_tokens_details”中的缓存活动。图 4 显示了如何读取这些字段以及每个示例的三个调用中预期的模式。

![跨三个调用的缓存使用字段，显示隐式和显式模式的缓存、写入和未缓存令牌](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22160-4.png)

图 4：如何读取缓存使用字段（示例）

在隐式模式下，调用 1 将提示写入缓存。调用 2 和 3 从缓存中读取系统消息以及指令和手册。他们还各自写入一些标记，因为隐式模式扩展了缓存的前缀以涵盖每个新问题。每次调用时，最后一条消息之后的一些令牌都不会被缓存。这是第一次运行的模式。如果您在 TTL 内再次运行该示例，则每次调用都会从缓存中读取，并且不会写入。

## 显式缓存

选择显式缓存来准确控制缓存的内容。如图 4 所示，隐式运行的调用 2 和 3 均将一些令牌写入缓存，而显式缓存的相同调用则不写入任何内容。通过多个断点，您可以缓存分层前缀，例如共享指令和工具，后跟每个客户的文档（图 2）。

对于显式缓存，请将以下内容添加到请求中：

- 模式设置为“显式”的“prompt_cache_options”选择显式模式。这是一个 Amazon Bedrock 请求字段，OpenAI SDK 通过“extra_body”发送它。
- 文本内容部分上的“prompt_cache_breakpoint”标记可重用前缀的结尾。直到并包括该部分的内容都会被缓存，并且在每次请求时再次处理后的内容。

将同一循环的显式版本保存为“explicit.py”：
```
from common import MODEL_ID, QUESTIONS, SYSTEM_PROMPT, client, report

for i, question in enumerate(QUESTIONS, start=1):
    response = client.chat.completions.create(
        model=MODEL_ID,
        messages=[
            {
                "role": "system",
                "content": [
                    {
                        "type": "text",
                        "text": SYSTEM_PROMPT,
                        # Cache everything up to and including this content part.
                        "prompt_cache_breakpoint": {"mode": "explicit"},
                    }
                ],
            },
            {"role": "user", "content": question}, # after the breakpoint, not cached
        ],
        max_tokens=1024,
        extra_body={"prompt_cache_options": {"mode": "explicit"}},
    )
    report(i, response)
```
将两个部分放在一起。没有断点的显式模式不会缓存任何内容，而没有显式模式的断点的行为类似于隐式缓存。对于“prompt_cache_options”的可选“ttl”字段，请检查型号卡以获取支持的值。

### 验证显式缓存

如果您在“implicit.py”之后运行“explicit.py”，则它的第一次调用已经是缓存命中。对于首次冷调用，请在系统提示符中添加唯一的第一行，例如 `SYSTEM_PROMPT = f"Run ID: {uuid.uuid4()}\n" + SYSTEM_PROMPT`（在 `explicit.py` 顶部添加 `import uuid`）。

如图 4 中的显式条所示，只有第一个调用会写入。每次重复都会读取断点之前的整个前缀并且不写入任何内容，断点之后的问题构成未缓存的剩余部分。

## 通过 OpenCode 编码代理使用提示缓存

编码代理在每一步上都会重新发送一个大的、稳定的前缀：系统提示、工具定义和到目前为止的对话。这使得它们自然适合隐式缓存。 [OpenCode](https://opencode.ai/) 是一个开源编码代理。它可以通过自定义 OpenAI 兼容提供商调用任何聊天完成终端节点，因此它可以使用与 Python 示例相同的 Amazon Bedrock 终端节点。图 5 显示了 OpenCode 在一轮中发送的请求以及 Amazon Bedrock 从缓存中读取的部分。

![OpenCode 一轮中的两个请求，其中请求 2 从缓存中读取请求 1 并仅处理新的尾部](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22160-5.png)

图 5：OpenCode 在一轮中发送到 Amazon Bedrock 的请求

一轮中，OpenCode 发送请求 1 及其系统提示、工具定义和您的提示，Amazon Bedrock 将其写入缓存。该模型通过工具调用进行响应，OpenCode 在您的计算机上运行该工具调用。然后，OpenCode 发送请求 2，其中包含请求 1 以及工具调用及其结果。 Amazon Bedrock 从缓存中读取请求 1，仅写入新尾部，然后返回响应。

## 配置 OpenCode

安装 OpenCode 并检查版本：
```
npm install --prefix ~/.local/opt/opencode opencode-ai@1.18.35
export PATH="$HOME/.local/opt/opencode/node_modules/.bin:$PATH"
opencode --version
```
接下来，将以下“opencode.json”添加到存储库的根目录，或将其另存为“~/.config/opencode/opencode.json”以将其应用到每个项目。它定义了一个名为“bedrock”的提供商，该提供商使用 OpenAI 兼容包来调用 Amazon Bedrock Chat Completions 终端节点：
```
{
  "$schema": "https://opencode.ai/config.json",
  "model": "bedrock/<MODEL_ID_OR_INFERENCE_PROFILE_ID>",
  "small_model": "bedrock/<MODEL_ID_OR_INFERENCE_PROFILE_ID>",
  "provider": {
    "bedrock": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Amazon Bedrock (Chat Completions)",
      "options": {
        "baseURL": "https://bedrock-runtime.<AWS_REGION>.amazonaws.com/openai/v1",
        "apiKey": "{env:BEDROCK_API_KEY}"
      },
      "models": {
        "<MODEL_ID_OR_INFERENCE_PROFILE_ID>": { "name": "Open-weight model on Amazon Bedrock" }
      }
    }
  }
}
```
OpenCode 使用“small_model”作为会话标题，因此将其指向同一模型可使每个请求保持在您已启用的模型上。提供者从“BEDROCK_API_KEY”读取其密钥。在第一个示例的虚拟环境中，将其设置为来自“provide_token()”的短期 Amazon Bedrock API 密钥。如果密钥过期，请再次运行命令以获取新密钥：
```
export BEDROCK_API_KEY="$(python -c '
from aws_bedrock_token_generator import provide_token
print(provide_token(region="<AWS_REGION>"))')"
```
确认 OpenCode 列出了型号：
```
opencode models bedrock
```

## 最佳实践

这些实践适用于任何支持提示缓存的模型：

- **在两种模式下都将静态内容放在前面。** 将系统提示、工具定义和参考文档放在更改的内容之前，并在请求之间保持它们相同。在显式模式下，将每个断点放置在其覆盖的静态内容之后。时间戳和请求 ID 位于提示的末尾。
- **使前缀足够长。** 满足模型卡上最小令牌计数的前缀有资格进行缓存。
- **使用使用字段确认命中。** 在任一模式下检查每个响应中的缓存读取和写入。在整个工作负载中，跟踪“CacheReadInputTokenCount”和“CacheWriteInputTokenCount”[运行时指标](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-runtime-metrics.html)。
- **保持缓存温暖。** 稳定的流量会缓存前缀，因为 TTL 会随着每次命中而重置。在超过 TTL 的空闲间隙后，下一个请求会再次写入前缀。
- **缓存您重复使用的内容。** 节省来自缓存读取，因此缓存稍后请求再次读取的内容，特别是在缓存写入成本高于标准输入的情况下。通过跨区域推理，预计在高需求时会进行一些额外的缓存写入。

＃＃ 清理

这些示例仅进行推理调用，不会在您的 AWS 账户中创建任何资源。缓存条目在 TTL 内未被读取后就会过期。来自“provide_token()”的短期 API 密钥也会自行过期，并且样本永远不会将其写入磁盘。要更快地从 shell 中清除它，请运行“unset BEDROCK_API_KEY”。

删除本地文件：

1. 删除示例目录及其Python虚拟环境。

2. 从存储库中删除`opencode.json`，或者如果您全局保存了`~/.config/opencode/opencode.json`。

3. 如果不再需要 OpenCode，请删除 `~/.local/opt/opencode`。

## 结论

提示缓存允许 Amazon Bedrock 上的开放权重模型重用重复的上下文，而无需对代码进行很少的更改或无需更改。在这篇文章中，隐式缓存涵盖了支持助手和 OpenCode 会话，根本没有缓存设置。显式缓存通过一个请求选项和每个可重用层的断点提供了精确控制。在每种情况下，每个响应上的使用字段都会显示来自缓存的内容，因此您可以衡量自己流量的收益。

首先，选择 [Amazon Bedrock 上支持提示缓存的开放权重模型](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards.html)。使用您自己的参考内容运行本文中的示例，并将缓存读取与未缓存的输入进行比较。 [提示缓存指南](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html) 涵盖了每个模型的限制和选项，Amazon Bedrock [运行时指标](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-runtime-metrics.html) 可让您跟踪应用程序中的缓存读取和写入情况。如有疑问，请通过 [AWS Support](https://aws.amazon.com/support/) 或 [AWS re:Post 社区](https://repost.aws/) 联系。
