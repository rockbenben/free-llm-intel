# 在 Amazon Bedrock 上对开放权重模型使用提示缓存

许多生成式 AI 应用每次请求都会带上同一段很长的上下文，而 prompt 缓存可以避免每次都把它重新处理一遍。这段上下文可以是 system prompt、参考文档、工具定义，或者到目前为止的对话。Amazon Bedrock 上的开放权重模型可以跨请求复用它，从而帮助降低输入成本和响应延迟。

[prompt 缓存](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)会复用匹配的 prompt 前缀已经计算好的状态，于是重复的上下文直接从缓存读取，不必再处理一遍。缓存由 Amazon Bedrock 替你管理。视模型而定，你可以使用自动生效的隐式缓存、由你标记可复用前缀的显式缓存，或者两者都用。复用的上下文越多、复用越频繁，能省下的就越多。

与 Amazon Bedrock 上的其他模型一样，你的 prompt 和输出不会与模型提供方共享，也不会被用于训练模型。更多信息见 Amazon Bedrock 用户指南中的[数据保护](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html)一节。

Amazon Bedrock 上的开放权重模型现在支持显式 prompt 缓存。本文中，我们通过 [Chat Completions API](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-chat-completions.html) 在一个开放权重模型上使用这两种模式，并展示如何从每次响应里读取缓存使用情况。随后，我们在同一 API 上把隐式缓存应用到一次 OpenCode 编码 agent 会话，最后以最佳实践收尾。

## 在 Amazon Bedrock 上为开放权重模型使用 prompt 缓存

当一次请求的开头与更早的某次请求内容相同时，Amazon Bedrock 会从缓存中读取该前缀，只处理剩下的部分。缓存读取的计费低于标准输入，所以前缀每被复用一次，省下的钱就可能更多。视模型而定，缓存写入的计费可能高于标准输入。各模型的费率见 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)。

支持哪些模式取决于模型和 API。各模型支持的缓存模式、最小前缀长度以及缓存条目的保留时长，请见[模型一览](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards.html)。两种模式的对比见下表：

| **特性** | **隐式缓存** | **显式缓存** |
| --- | --- | --- |
| 请求侧的改动 | 无 | 在 Chat Completions API 上，把 `prompt_cache_options` 的 mode 设为 explicit，并加一个或多个 `prompt_cache_breakpoint` 标记 |
| 缓存的内容 | 符合条件的前缀，由系统在尽力而为的基础上自动挑选 | 直到并包含每个 breakpoint 为止的内容 |
| 适用场景 | 本来就以稳定前缀开头的 prompt，例如多轮对话和 agent loop | 固定的共享前缀配上会变化的问题，或者你希望自己掌控的分层前缀 |

**隐式缓存**：Amazon Bedrock 会在尽力而为的基础上自动复用符合条件的前缀。在一段对话里，每次请求都会重发完整上下文，所以上一次请求就成了下一次请求的缓存前缀（图 1）。正如 [prompt 缓存指南](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)所建议的，把静态内容放在前面、动态内容放在后面。保持 prompt 开头稳定，后续每一次请求就都能复用它。如果靠前的部分发生变化——就像图 1 的第 4 轮那样——缓存会从那个点开始重建。

![对话的每一轮复用上一次请求作为缓存前缀，并在靠前的轮次变化时重建缓存](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22160-1.gif)

图 1：一段对话各轮之间的隐式 prompt 缓存

**显式缓存**：你用 cache breakpoint 标记每一段可复用前缀的结尾。可以添加多个 breakpoint（最多到模型支持的上限），用来缓存变化频率不同的各层内容，如图 2 所示。每个 breakpoint 之前的内容会被写入缓存一次，之后的请求直接读取；最后一个 breakpoint 之后的内容则每次请求都要重新处理。关于 breakpoint 之前的最小 token 数、breakpoint 的最大数量，以及存活时间（TTL，每次缓存命中都会重置），请查看模型卡。

![cache breakpoint 标记共享前缀的结尾，该前缀只缓存一次，之后由后续请求读取](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22160-2.gif)

图 2：在共享前缀之后设一个 breakpoint 的显式 prompt 缓存

使用隐式缓存时，Amazon Bedrock 也可能把后续请求根本不会复用的内容写进缓存，比如每次都不同的问题。当共享前缀之后的内容每次都变时，就用显式缓存把缓存写入限制在共享前缀上。最后一个 breakpoint 之后的内容按标准输入费率计费。在那些缓存写入收费更高的模型上，你就不必为永远不会被读回的内容支付更高的写入费率。

## 通过 Chat Completions API 缓存一份产品手册

这个示例是一个虚构净水器 AnyCompany AquaPure 500 的客服助手。system prompt 里放一句指令和用户手册，用户手册就是可复用的前缀。每次请求问的是另一位客户的不同问题。

### 配置客户端

这些示例使用 OpenAI Python SDK，配合 Amazon Bedrock 的 Chat Completions endpoint。认证方面，`aws-bedrock-token-generator` 包里的 `provide_token()` 函数会把你的 AWS 凭证换成一个[短期 Amazon Bedrock API key](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html)，最长有效 12 小时。你不需要创建或保存长期 key。

1. 创建虚拟环境并安装依赖包：

```
python3.12 -m venv .venv
source .venv/bin/activate
pip install "openai>=3.26.0" "aws-bedrock-token-generator>=1.1.0"
```

2. 创建手册。我们这份是约 4,000 token 的 Markdown。下面的片段展示了它的格式：

```
# AnyCompany AquaPure 500 Owner's Manual

### 7.1 Replacement schedule
| Stage | Cartridge | Part number | Replace every |
| ----- | ------------------- | ----------- | ------------- |
| 1 | Sediment pre-filter | AP-F1 | 6 months |
| 4 | Carbon post-filter | AP-F4 | 12 months |

### 9. Error codes
| Code | Description | What to do |
| ---- | ----------------------- | -------------------------------------------- |
| E01 | Low feed water pressure | Check that the feed water valve is open. |
| E07 | Drain line restriction | Check the black concentrate tube for kinks. |

### 11. Warranty
- Faucet: 3 years from the date of purchase. The 3 V cell is not covered.
```

把它保存为 `manual.md`，并继续添加章节，直到长度超过你模型卡上的最小前缀长度。占位文本也可以，因为缓存只需要前缀完全一致。保留上面展示的三个章节，它们正是回答示例问题所需要的。

3. 把下面的初始化代码保存为同目录下的 `common.py`。接下来创建的示例都会从它导入。

```
from pathlib import Path

from aws_bedrock_token_generator import provide_token
from openai import OpenAI

REGION = "<AWS_REGION>"
MODEL_ID = "<MODEL_ID_OR_INFERENCE_PROFILE_ID>"

MANUAL = Path(__file__).with_name("manual.md").read_text()

SYSTEM_PROMPT = (
    "You are the AnyCompany AquaPure support assistant. Answer the customer's question in at "
    "most three sentences, using only the owner's manual below.\n\n" + MANUAL
)

QUESTIONS = [
    "My filter shows error code E07. What does it mean and how do I fix it?",
    "How often do I need to replace the AP-F4 post-filter?",
    "Is the 3 V battery in the smart faucet covered by the warranty?",
]

# Chat Completions API client: the OpenAI SDK pointed at the Amazon Bedrock OpenAI-compatible endpoint
client = OpenAI(
    api_key=provide_token(region=REGION),
    base_url=f"https://bedrock-runtime.{REGION}.amazonaws.com/openai/v1",
)


def report(call_number, response):
    """Print the cache fields from the response usage."""
    usage = response.usage
    read = usage.prompt_tokens_details.cached_tokens or 0
    written = usage.prompt_tokens_details.cache_write_tokens or 0
    print(
        f"Call {call_number}: prompt_tokens={usage.prompt_tokens} cached_tokens={read} "
        f"cache_write_tokens={written} uncached={usage.prompt_tokens - read - written}"
    )
```

如果你的模型会返回 reasoning token，它们也计入 `max_tokens`。示例里把 `max_tokens` 设为 1024，好让简短的回答有空间写完。

## 隐式缓存

隐式缓存不需要任何缓存控制。把手册放进 system 消息、把问题放进 user 消息。我们试过把两者都作为同一条 user 消息的不同部分发送，结果没有拿到任何隐式缓存命中。把下面的代码保存为 `implicit.py`，用 `python implicit.py` 运行：

```
from common import MODEL_ID, QUESTIONS, SYSTEM_PROMPT, client, report

for i, question in enumerate(QUESTIONS, start=1):
    response = client.chat.completions.create(
        model=MODEL_ID,
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT}, # static, same every call
            {"role": "user", "content": question}, # changes every call
        ],
        max_tokens=1024,
    )
    report(i, response)
```

### 验证隐式缓存

每次响应都会在 `usage.prompt_tokens_details` 中报告缓存活动。图 4 展示了如何读这些字段，以及每个示例三次调用中应当出现的模式。

![三次调用中的缓存使用字段，展示隐式与显式模式下的缓存读取、写入与未缓存 token](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22160-4.png)

图 4：如何读取缓存使用字段（示意）

在隐式模式下，第 1 次调用会把 prompt 写入缓存。第 2、3 次调用则从缓存读回 system 消息（含指令和手册）。它们各自还会写进少量 token，因为隐式模式会把缓存前缀延长，覆盖每个新问题。每条消息末尾之后的少量 token 在每次调用中都保持未缓存。这是第一次运行时的模式。如果你在 TTL 内再次运行同一示例，那么每次调用都只读缓存，不再写入。

## 显式缓存

如果想精确控制缓存哪些内容，就选显式缓存。如图 4 所示，隐式运行的第 2、3 次调用各自往缓存写了少量 token，而同样的调用在显式缓存下什么都不写。用多个 breakpoint，你可以缓存分层的前缀，例如共享指令和工具，后面再接每个客户专属的文档（图 2）。

使用显式缓存，需要在请求里加上以下内容：

- 把 `prompt_cache_options` 的 mode 设为 **explicit**，即选中显式模式。它是 Amazon Bedrock 的请求字段，OpenAI SDK 会通过 `extra_body` 把它发出去。
- 在某个文本 content part 上设置 `prompt_cache_breakpoint`，用于标记可复用前缀的结尾。直到并包含该 part 的内容会被缓存，它之后的内容每次请求都要重新处理。

把同一个循环的显式版本保存为 `explicit.py`：

```
from common import MODEL_ID, QUESTIONS, SYSTEM_PROMPT, client, report

for i, question in enumerate(QUESTIONS, start=1):
    response = client.chat.completions.create(
        model=MODEL_ID,
        messages=[
            {
                "role": "system",
                "content": [
                    {
                        "type": "text",
                        "text": SYSTEM_PROMPT,
                        # Cache everything up to and including this content part.
                        "prompt_cache_breakpoint": {"mode": "explicit"},
                    }
                ],
            },
            {"role": "user", "content": question}, # after the breakpoint, not cached
        ],
        max_tokens=1024,
        extra_body={"prompt_cache_options": {"mode": "explicit"}},
    )
    report(i, response)
```

这两部分要一起设置。只开显式模式而没有 breakpoint，什么都不会被缓存；只加 breakpoint 而不开显式模式，行为等同于隐式缓存。`prompt_cache_options` 里可选的 `ttl` 字段支持哪些取值，请查看模型卡。

### 验证显式缓存

如果你紧接着 `implicit.py` 运行 `explicit.py`，它的第一次调用就已经是缓存命中。想要一次冷启动的首次调用，可以在 system prompt 里加一行唯一的内容，例如 `SYSTEM_PROMPT = f"Run ID: {uuid.uuid4()}\n" + SYSTEM_PROMPT`（并在 `explicit.py` 顶部 `import uuid`）。

如图 4 中显式缓存的条柱所示，只有第一次调用会写入。之后每次重复都读取直到 breakpoint 的整个前缀，什么都不写；breakpoint 之后的问题构成未缓存的剩余部分。

## 在 OpenCode 编码 agent 中使用 prompt 缓存

编码 agent 每一步都会重发一段很大且稳定的前缀：system prompt、工具定义，以及到目前为止的对话。这让它们天然适合隐式缓存。[OpenCode](https://opencode.ai/) 是一个开源编码 agent。它可以通过自定义的 OpenAI 兼容 provider 调用任何 Chat Completions endpoint，因此也能使用与 Python 示例相同的 Amazon Bedrock endpoint。图 5 展示了 OpenCode 在一轮交互中发出的请求，以及 Amazon Bedrock 从缓存读取的部分。

![OpenCode 一轮交互中的两次请求，其中请求 2 从缓存读回请求 1，只处理新增的尾部](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22160-5.png)

图 5：OpenCode 在一轮交互中发给 Amazon Bedrock 的请求

在一轮交互中，OpenCode 发出请求 1，包含它的 system prompt、工具定义和你的 prompt，Amazon Bedrock 将其写入缓存。模型返回一个工具调用，OpenCode 在你的机器上执行它。随后 OpenCode 发出请求 2，内容包含请求 1 再加上这次工具调用及其结果。Amazon Bedrock 从缓存读取请求 1，只写入新增的尾部，然后返回响应。

## 配置 OpenCode

安装 OpenCode 并检查版本：

```
npm install --prefix ~/.local/opt/opencode opencode-ai@1.18.35
export PATH="$HOME/.local/opt/opencode/node_modules/.bin:$PATH"
opencode --version
```

接下来，把下面的 `opencode.json` 加到仓库根目录；如果你希望它对每个项目都生效，就保存为 `~/.config/opencode/opencode.json`。它定义了一个名为 `bedrock` 的 provider，使用 OpenAI 兼容包来调用 Amazon Bedrock 的 Chat Completions endpoint：

```
{
  "$schema": "https://opencode.ai/config.json",
  "model": "bedrock/<MODEL_ID_OR_INFERENCE_PROFILE_ID>",
  "small_model": "bedrock/<MODEL_ID_OR_INFERENCE_PROFILE_ID>",
  "provider": {
    "bedrock": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Amazon Bedrock (Chat Completions)",
      "options": {
        "baseURL": "https://bedrock-runtime.<AWS_REGION>.amazonaws.com/openai/v1",
        "apiKey": "{env:BEDROCK_API_KEY}"
      },
      "models": {
        "<MODEL_ID_OR_INFERENCE_PROFILE_ID>": { "name": "Open-weight model on Amazon Bedrock" }
      }
    }
  }
}
```

OpenCode 用 `small_model` 生成会话标题，所以把它指向同一个模型，就能让每个请求都落在你已经启用的模型上。这个 provider 从 `BEDROCK_API_KEY` 读取 key。请把它设为第一个示例的虚拟环境里由 `provide_token()` 生成的短期 Amazon Bedrock API key。如果 key 过期，重新运行命令取一个新的：

```
export BEDROCK_API_KEY="$(python -c '
from aws_bedrock_token_generator import provide_token
print(provide_token(region="<AWS_REGION>"))')"
```

确认 OpenCode 能列出该模型：

```
opencode models bedrock
```

### 在编码会话中验证隐式缓存

我们在一个只放了一个简短 Python 文件的小仓库上跑了一次三轮会话。第 1 轮请求 bug review，第 2 轮请求修复，第 3 轮问一个简短的追问：

```
opencode run --format json --title "cache-demo" \
"Read src/inventory.py and list any bugs in Inventory.remove. Do not edit files."
```

```
opencode run --format json -s <sessionID> \
"Now propose a fixed version of Inventory.remove as a code block. Do not edit files."
```

```
opencode run --format json -s <sessionID> \
"In one sentence, what does low_stock return?"
```

把 `<sessionID>` 替换成第 1 轮 JSON 输出里的 `sessionID` 值。`opencode export <sessionID>` 命令会列出每个请求的 token 用量：`cache.read` 是来自 Amazon Bedrock 的 `cached_tokens` 值，`input` 是其余部分。OpenCode 1.18.35 不会为 OpenAI 兼容 provider 记录 `cache_write_tokens`，所以 `cache.write` 一直是 0。

图 6 展示了这次会话中每个请求有多大比例是从缓存读取的。

![一次 OpenCode 会话中的缓存读取，每个请求都复用上一个请求结尾之前的全部内容](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22160-6.png)

图 6：一次 OpenCode 会话中的缓存读取（示意）

第一个请求处理了整个 prompt——其中大部分是 OpenCode 的 system prompt 和工具定义——Amazon Bedrock 把它写入缓存。之后每个请求都从缓存读取直到上一个请求结尾的全部内容，所以只有对话新增的尾部会被处理。这一切不需要任何缓存配置就能生效。

## 最佳实践

以下实践适用于任何支持 prompt 缓存的模型：

- **两种模式下都把静态内容放前面。** 把 system prompt、工具定义和参考文档放在会变化的内容之前，并保证它们在请求之间完全一致。在显式模式下，把每个 breakpoint 放在它所覆盖的静态内容之后。时间戳和请求 ID 应当放在 prompt 的末尾。
- **让前缀足够长。** 达到模型卡上最小 token 数的前缀才有资格被缓存。
- **用 usage 字段确认命中。** 在两种模式下，都检查每次响应里的缓存读取与写入。从整个工作负载的层面，可以跟踪 `CacheReadInputTokenCount` 和 `CacheWriteInputTokenCount` 这两项[运行时指标](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-runtime-metrics.html)。
- **让缓存保持热态。** 稳定的流量能让前缀一直留在缓存里，因为每次命中都会重置 TTL。空闲时间超过 TTL 之后，下一次请求会重新写入该前缀。
- **缓存你确实会复用的内容。** 省下的钱来自缓存读取，所以要缓存后续请求会再次读取的内容，尤其是在缓存写入比标准输入更贵的场景。使用跨区域推理（cross-Region inference）时，在需求高峰时段要预期会有一些额外的缓存写入。

## 清理

这些示例只发起推理调用，不会在你的 AWS 账号里创建任何资源。缓存条目在 TTL 内未被读取就会过期。由 `provide_token()` 生成的短期 API key 也会自行过期，示例从不把它写到磁盘。如果想让它在 shell 里更早清除，运行 `unset BEDROCK_API_KEY`。

要删除本地文件：

1. 删除示例目录及其 Python 虚拟环境。

2. 从仓库里删除 `opencode.json`；如果是全局保存的，则删除 `~/.config/opencode/opencode.json`。

3. 如果不再需要 OpenCode，删除 `~/.local/opt/opencode`。

## 结论

prompt 缓存让 Amazon Bedrock 上的开放权重模型能够复用重复的上下文，而你的代码几乎不用改、甚至完全不用改。本文中，隐式缓存在完全没有缓存设置的情况下就覆盖了客服助手和 OpenCode 会话。显式缓存则通过一个请求选项加上每个可复用层一个 breakpoint，提供了精确的控制。无论哪种情况，每次响应里的 usage 字段都会显示哪些内容来自缓存，因此你可以用自己的流量来衡量收益。

要上手的话，选一个[支持 prompt 缓存的 Amazon Bedrock 开放权重模型](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards.html)。用你自己的参考内容运行本文的示例，把缓存读取量和未缓存的输入量做对比。[prompt 缓存指南](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)介绍了各模型的限制与选项，Amazon Bedrock 的[运行时指标](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-runtime-metrics.html)则让你能跨应用跟踪缓存读写。如有问题，可以通过 [AWS Support](https://aws.amazon.com/support/) 或 [AWS re:Post 社区](https://repost.aws/) 联系。
