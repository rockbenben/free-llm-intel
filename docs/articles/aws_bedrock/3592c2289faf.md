# 使用 Amazon Nova Act 通过代理 QA 自动化加速软件交付 - 第 3 部分

随着质量保证 (QA) 自动化在组织内部的采用不断增长，出现了一个与编写测试无关的新问题。一个平台团队支持测试自动化，然后第二个团队想要加入，然后是十几个团队。很快，数百个测试用例属于不同的产品和团队，每个人都可以看到其他人的测试。没有人能够一眼就回答一个基本问题：这个应用程序的测试覆盖率现在是否健康？测试创作不再是瓶颈。组织测试并控制谁可以接触它们成为工作。

第二个相关问题紧随其后：谁拥有此应用程序及其测试，以及当覆盖率下降时谁负责？没有明确的主人，健康问题就无从下手。

在第一篇文章中，我们介绍了 QA Studio，这是一个使用 Amazon Nova Act 构建的参考解决方案(https://aws.amazon.com/ai/agentic-ai/nova-act/)。团队使用它以自然语言定义测试，并通过人工智能驱动的视觉导航运行它们。在[第二篇文章](https://aws.amazon.com/blogs/machine-learning/acceleating-software-delivery-with-agentic-qa-automation-using-amazon-nova-act-part-2/)中，我们添加了测试套件和 CLI，用于在持续集成和持续交付 (CI/CD) 管道中进行批量回归测试。在这篇文章中，我们将介绍有助于 QA Studio 在整个组织中扩展的两项功能。第一个是**应用程序**，组织测试并报告健康指标。第二个，**基于团队的用户管理**，控制谁可以查看和更改什么。

## 使用应用程序组织测试

QA Studio 中的应用程序代表被测系统：网站、Web 应用程序、服务前端。它是一个提供测试集合、一个家和一个所有者的容器。用例（第 1 部分中的各个测试）和测试套件（第 2 部分中的回归集合）属于应用程序，并且它们继承其所有权。每个团队都在他们拥有的应用程序内工作，而不是部署中每个测试的简单列表。

创建应用程序需要名称、基本 URL 和一组可选的环境（例如开发、登台和生产）。从应用程序页面，团队直接在上下文中创建新用例，添加现有用例，并将它们分组到测试套件中。这也是 QA Studio 报告其运行的测试运行状况的地方。

## 通过指标了解应用程序运行状况

测试产生结果。随着时间的推移了解这些结果可以告诉团队应用程序的开发生命周期是否健康，而不仅仅是单个构建是否已准备好发布。 QA Studio 将每次执行的结果记录为 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 自定义指标，按应用程序和环境确定维度。它将这些指标转化为应用程序页面上的运行状况视图。

页面顶部用三个数字回答了直接问题：所选窗口的通过率、执行总数和当前失败计数。除此之外，QA Studio 还会计算 0-100 的健康评分。分数从通过率开始，减去不稳定测试的罚分。这样，测试通过但在通过和失败之间切换的应用程序就不会呈现出虚假的完美画面。扫描应用程序组合的团队可以区分稳定的应用程序和需要关注的应用程序，而无需打开每个结果。

指标选项卡从当前快照移至趋势。团队选择每小时粒度的 7 天窗口或每日粒度的 30 天窗口，QA Studio 会绘制该期间的执行、成功、失败和平均持续时间的图表。由于底层指标包含环境维度，因此团队将视图过滤到单个环境。例如，他们可以比较同一组测试的暂存与生产的行为方式。

有两种视图针对花费团队时间最多的测试。片状测试视图根据用例在过去 7 天内在通过和失败之间切换的频率对用例进行排名。这暴露了间歇性故障，这些故障在变成生产失误之前会削弱人们对套件的信任。最近的失败视图列出了最新失败的执行，以便快速分类。每个链接都链接回第 1 部分中描述的 Amazon Nova Act 轨迹日志和会话记录。这样，只需单击一下即可从“此测试失败”转变为“这正是代理所看到的内容”。

## 控制团队和角色的访问

指标告诉团队他们的应用程序运行情况如何。基于团队的用户管理首先决定哪些应用程序属于他们。 QA Studio 围绕团队组织访问，并且应用程序只属于一个团队。该团队的成员使用其应用程序。其他人都看不到他们。

每个团队成员都拥有五个角色之一，每个角色都包含其下面角色的权限：

- **管理员**：工作室范围内对每个团队、应用程序和用户的访问权限，包括创建团队和分配应用程序。管理员是整个工作室的角色，而不是每个团队的任务。
- **团队负责人**：管理自己的团队成员并为团队创建应用程序。
- **编辑器**：在团队的应用程序中创建和编辑用例和测试套件。
- **执行器**：运行用例和套件，但不修改它们。
- **查看者**：对团队的应用程序和结果的只读访问权限。

由于角色是累积性的，因此团队负责人拥有编辑者所拥有的一切，依此类推，直至查看者。对用例或测试套件的访问遵循包含它的应用程序。如果成员可以使用该应用程序，那么他们就可以使用其测试，但受其角色的限制。这使得权限管理保持在应用程序级别，而不是数千个单独的测试。

管理员可以看到整个工作室。用户页面在一个位置列出了每个帐户及其团队和角色。管理员可以知道谁担任哪个团队的团队领导以及谁拥有工作室范围的管理员权限。在此处显示的参考部署中，四个用户分布在两个团队中：两名团队主管、一名查看者和一名工作室范围管理员。团队页面按团队汇总相同的数据，并排显示每个团队的成员数量和应用程序数量。管理员可以在打开任何一个团队之前查看哪些团队正在扩展。

## 在团队之间共享应用程序

团队很少会完全孤立地工作。平台团队可能拥有功能团队需要运行的应用程序，但不移交更改它的能力。 QA Studio 通过共享访问支持这一点：拥有团队向另一个团队授予应用程序的查看、执行或完整级别访问权限。

共享访问遵循上限规则。用户对共享应用程序的有效权限是其自己的角色和授予级别中的较低者。被授予对共享应用程序的完全访问权限的查看者仍然只能查看，因为他们的角色是上限。这样，拥有团队就可以广泛共享，而无需授予超出接收者角色允许的权限。

## 它是如何工作的

QA Studio 在前面的文章中描述的相同无服务器基础上构建基于团队的访问控制和指标，并添加了一些 AWS 服务：

- **[Amazon Cognito](https://aws.amazon.com/cognito/)**：每个团队映射到一组 Cognito 组，每个角色一个。 [AWS Lambda](https://aws.amazon.com/lambda/) 授权方将每个请求的调用者组解析为 API 范围和团队上下文。
- **[Amazon DynamoDB](https://aws.amazon.com/dynamodb/)**：团队、成员资格、应用程序所有权和跨团队共享授予存储在现有的单表设计中。
- **Amazon CloudWatch**：每次执行都会在 QAStudio/Executions 命名空间中发出自定义指标，按应用程序和环境确定尺寸。指标 API 读回它们以构建运行状况视图和趋势图。
- **AWS Lambda 和 [Amazon API Gateway](https://aws.amazon.com/api-gateway/)**：后端强制执行两层访问：调用者角色授予的范围，以及确认调用者团队拥有或已与应用程序共享的资源检查。

由于访问权限源自 Cognito 组成员资格，因此第 2 部分中的 OAuth 客户端凭据流适合相同的模型。 CI 管道使用其所需的范围来验证机器身份，仅此而已。

＃＃ 入门

应用程序、指标和基于团队的访问控制是 QA Studio 参考解决方案的一部分，您可以使用 [AWS 云开发工具包 (AWS CDK)](https://aws.amazon.com/cdk/) 将其部署在您自己的 AWS 账户中。所有测试数据、结果和指标均保留在您的帐户范围内。部署后，管理员创建团队、分配成员和角色，并将应用程序分配给团队。每个团队的健康指标随着测试的运行而开始填充。

有关部署说明和配置详细信息，请参阅 [QA Studio GitHub 存储库](https://github.com/aws-samples/sample-qa-studio) 及其文档。

## 结论

在这篇文章中，我们展示了 QA Studio 如何将代理 QA 自动化从个人测试扩展到组织。应用程序为每个团队提供了一个存放用例和测试套件的家。他们通过通过率、趋势图、不稳定的运行状况评分以及基于 Amazon CloudWatch 指标构建的故障分类来报告运行状况。基于团队的用户管理在 Amazon Cognito 的支持下，让每个团队在自己拥有的应用程序内工作，跨团队共享受到明确的上限规则的限制。

这些功能建立在第 1 部分的自然语言测试编写以及第 2 部分的套件和 CI/CD 集成的基础上。它们共同帮助 QA 自动化在多个团队中发展，而不会失去可见性或控制力。要在您自己的环境中尝试，请从 QA Studio GitHub 存储库部署参考解决方案，创建您的第一个团队和应用程序，然后运行一些用例来观察指标的形成。要了解有关其背后代理的更多信息，请参阅 [Amazon Nova Act 产品页面](https://aws.amazon.com/ai/agentic-ai/nova-act/)。
