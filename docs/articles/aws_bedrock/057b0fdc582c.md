# 使用 Amazon Bedrock AgentCore 构建 AI 驱动的设备维修助手

管理重型农业机械的设备维修往往需要技术人员在缺少合适零件的情况下诊断问题，导致多次上门、停机时间延长以及重大经济损失，尤其是在收获季节。

在本文中，你将使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 构建一个 AI 驱动的设备维修助手，帮助农民和现场技术人员通过自然语言诊断设备问题、识别所需零件，并获取制造商认可的维修流程。该方案使用 AgentCore Runtime 搭配 [Strands Agents SDK](https://strandsagents.com/)，以 [Amazon Nova 2 Lite](https://aws.amazon.com/nova/models/) 作为基础模型，使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) Knowledge Base 实现检索增强生成（RAG），并使用 AgentCore Memory 保持对话状态。

## 解决方案概述

该方案将 Web 前端与托管在 AgentCore 上的 agent 相结合，后者利用已建立索引的制造商文档回答设备诊断问题。

[Amazon Cognito](https://aws.amazon.com/cognito/) 负责用户认证，[AWS Amplify](https://aws.amazon.com/amplify/) 托管 Web 应用。设备维修 agent 运行在 AgentCore Runtime 上，使用 Strands Agents SDK 构建。它查询一个 Bedrock Knowledge Base，其中包含已建立索引的设备手册、零件目录和维修文档。AgentCore Memory 跨会话维护对话历史，使技术人员可以追问而无需重复背景信息。

**该架构包含以下关键部分：**

**部分 A** – **认证与前端**：CloudFormation 堆栈部署 Amazon Cognito（User Pool、Identity Pool）用于认证，并部署 AWS Amplify 用于托管 React Web 应用。用户通过 Cognito 认证，前端直接与 AgentCore Runtime endpoint 通信。

**部分 B** – **AgentCore Runtime**：AgentCore Runtime 托管基于 Strands 的 agent，并暴露 /invocations endpoint。前端使用 Cognito Bearer token 直接调用该 endpoint。agent 的 invoke() 入口点根据 payload 中的 path 字段在内部路由请求（/chat 用于 AI 查询，/issues 用于 CRUD 操作），为后端操作提供单一入口，并内置会话管理和健康检查。

**部分 C** – **AI 处理**：Strands Agent 使用一个自定义的 search_equipment_knowledge 工具，该工具通过 retrieve_and_generate API 调用 Bedrock Knowledge Base。Knowledge Base 对存储在 Amazon S3 中的设备文档建立索引，使用 Amazon OpenSearch Serverless 进行向量搜索，并使用 Amazon Titan Embeddings 进行语义匹配。

以下代码片段展示了 agent 的 Knowledge Base [检索](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_RetrieveAndGenerate.html)工具如何查询制造商文档：

```
@tool
def search_equipment_knowledge(query: str) -> str:
    """Search equipment manuals, parts catalogs, and repair docs."""
    response = bedrock_agent_runtime.retrieve_and_generate(
        input={"text": query},
        retrieveAndGenerateConfiguration={
            "type": "KNOWLEDGE_BASE",
            "knowledgeBaseConfiguration": {
                "knowledgeBaseId": KNOWLEDGE_BASE_ID,
                "modelArn": f"arn:aws:bedrock:{REGION}::foundation-model/{MODEL_ID}",
            },
        },
    )
    return response.get("output", {}).get("text", "No results found.")
```

**部分 D** – **数据与记忆**：Amazon DynamoDB 存储设备服务工单（issue CRUD 操作）。AgentCore Memory 为会话内上下文提供短期记忆，为跨会话的事实持久化提供长期记忆。Amazon CloudWatch 和 AWS X-Ray 提供自动可观测性。

以下步骤描述了技术人员提问时的请求流程：

- 技术人员打开 Web 应用，并通过 Amazon Cognito 完成认证。
- 技术人员通过聊天界面提交问题。
- 前端携带 Cognito Bearer token 将查询发送到 AgentCore Runtime 的 /invocations endpoint。
- AgentCore 验证 token，将请求路由到 agent，并从过往对话中检索相关上下文。
- Strands Agent 将查询发送给 Amazon Nova 2 Lite 进行推理。
- 模型调用 search_equipment_knowledge 工具，该工具查询 Bedrock Knowledge Base。
- Knowledge Base 搜索已建立索引的设备手册，并返回带有来源引用的相关文档。
- 模型综合生成诊断响应，包含维修流程和零件建议。
- 响应连同来源标注一并返回给技术人员，以便核验。

## 前置条件

开始之前，请确认你已具备：

- 一个具备部署 AgentCore agent 所需权限的 AWS 账户。有关所需的 IAM 权限，请参阅 [AgentCore Runtime 的 IAM 权限](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-permissions.html)。
- 在部署所在 AWS Region 中拥有 Amazon Nova 2 Lite 的 Amazon Bedrock 模型访问权限。你也可以选择其他受支持的模型。有关当前模型可用性，请参阅[按 AWS Region 划分的模型支持情况](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。
- 已安装并配置好具备相应凭证的 [AWS Command Line Interface（AWS CLI）](https://aws.amazon.com/cli/) v2.0 或更高版本。
- 已安装 Python 3.10 或更高版本。
- 可使用终端或命令提示符。

**成本估算：** 测试时，主要成本来自 Amazon Bedrock 模型调用（Amazon Nova 2 Lite 为每百万输入/输出 token $0.30/$2.50）和 Bedrock Knowledge Base（OpenSearch Serverless 活跃时约 $0.24/小时）。其他服务（AgentCore Runtime、Amazon DynamoDB、Amazon S3、Amazon Cognito、AWS Amplify）在测试用量下均处于 AWS Free Tier 范围内。如需详细估算，请使用 [AWS Pricing Calculator](https://calculator.aws/)。

***重要****：在同一个 AWS Region 中部署所有资源。CloudFormation 堆栈、Knowledge Base 和 AgentCore 启动命令必须使用同一个 Region。*

## 创建 Knowledge Base

在部署 agent 之前，先使用农业设备文档创建并填充 Amazon Bedrock Knowledge Base。该 Knowledge Base 为诊断建议和维修指导提供原始资料。

### 步骤 1：准备文档

测试时，可从 [John Deere Technical Information Store](https://techpubs.deere.com/) 下载设备手册。你也可以使用自己组织的设备文档。本文中我们使用 John Deere 1023E 和 1025R Compact Utility Tractor 的操作手册。

收集并整理你的农业设备文档：

- 设备手册（推荐 PDF 格式）
- 技术服务指南和故障排查文档
- 包含零件编号和规格的零件目录
- 维护计划和预防性保养说明
- 安全规程和制造商警告

文档准备提示：

- 确认文档可搜索文本（而非扫描图片）
- 使用一致的命名规范（例如 Manufacturer_Model_DocumentType.pdf）
- 移除不应向所有用户开放的专有信息

### 步骤 2：为 Knowledge Base 创建 S3 存储桶

```
aws s3 mb s3://agriculture-kb-documents-<unique-suffix>
aws s3 cp ./equipment-docs s3://agriculture-kb-documents-<unique-suffix> --recursive
```

### 步骤 3：创建 Bedrock Knowledge Base

按照[说明](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-create.html)创建 Knowledge Base，设置如下：

- **Knowledge Base 名称**：Agriculture-Equipment-Repair-KB
- **数据源**：s3://agriculture-kb-documents-<unique-suffix>（步骤 2 中创建的存储桶）
- **解析策略**：Amazon Bedrock 默认解析器
- **分块策略**：默认分块
- **Embeddings 模型**：Amazon Titan Embeddings G1 – Text
- **向量存储**：快速创建新的向量存储（Amazon OpenSearch Serverless）

### 步骤 4：同步并测试 Knowledge Base

Knowledge Base 创建完成后，同步数据源以开始摄取文档（通常需要 10–20 分钟）。详情请参阅[同步以摄取数据源](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-data-source-sync-ingest.html)。使用 Bedrock 控制台中的[测试功能](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-retrieve.html)验证 Knowledge Base 能否响应示例查询。在详情页记录 Knowledge Base ID。

## 部署方案

- 在堆栈参数中，模板 URL 会自动预填。对于 Stack name，输入你的部署名称（默认：ag-repair-assist）。对于 KnowledgeBaseId，输入上一节中记录的 **Knowledge Base ID**。检查并创建堆栈。

### 步骤 6：部署 agent（从本地机器）

*在本地终端中配置好 AWS 凭证后运行以下命令。需要 Python 3.10 或更高版本。*

## 清理

**重要：** 本方案部署的 AWS 资源在删除前会持续产生费用。这包括 Amazon DynamoDB、Amazon S3、AWS Amplify 托管和 Amazon Cognito。AgentCore Runtime 和 Amazon Bedrock 仅在使用时产生费用。请完成以下所有清理步骤以停止计费。

***警告****：删除 S3 存储桶会永久移除其中存储的所有设备文档。在继续之前，请备份任何想要保留的文件。*

- 删除 agent：

```
agentcore destroy
```

- 删除 CloudFormation 堆栈：

```
aws cloudformation delete-stack --stack-name ag-repair-assist
```

- 删除 Knowledge Base：

在 [Amazon Bedrock Knowledge Bases 控制台](https://ap-south-1.console.aws.amazon.com/bedrock/home?/knowledge-bases)中，选择 Agriculture-Equipment-Repair-KB 并点击 **Delete**。

- 清空并删除 S3 存储桶：

```
aws s3 rm s3://agriculture-kb-documents-<unique-suffix> --recursive
aws s3 rb s3://agriculture-kb-documents-<unique-suffix>
```

## 实施考量

**数据管理与 Knowledge Base 设置**
 随着制造商发布新设备型号并修订现有文档，Knowledge Base 必须相应更新。定期同步计划配合自动化工作流，使系统能够无缝处理新上传的内容。

**Amazon Bedrock AgentCore 配置**
 不同的故障排查场景对技术复杂度和响应准确度有不同要求。Strands Agents 的 code-first 方法让你通过更改 MODEL_ID 环境变量来切换模型。AgentCore Memory 配置增加了对话智能。短期记忆在诊断会话内维护上下文，而长期记忆则跨会话持久化技术人员的专长、农户机队详情和反复出现的问题模式。检索配置中的 top_k 和 relevance_score 阈值应根据文档语料的广度和深度进行调整。

**可扩展性
**要添加新能力（库存检查、零件订购、经销商沟通），只需在 agent 代码中添加一个新的 @tool 函数。无需更改基础设施。

**合规与安全
**每一条维修建议都必须符合制造商保修和安全准则。嵌入整个系统的安全规程确保用户能主动收到有关维修流程相关危险的警告。农业设备涉及高压液压、电气系统、旋转机械及其他潜在危险部件。系统必须突出显示关键安全问题。

**扩展到企业级规模**
 本方案专为测试和评估而设计，力求轻量。扩展到生产环境时，请考虑以下增强措施：

- [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html)：增加 prompt 攻击检测和内容过滤，以防范设备描述中的恶意输入。配置拒答主题，防止 agent 提供其领域之外的指导。
- API 保护：在 AgentCore Runtime endpoint 前面部署 Amazon CloudFront，并结合 [AWS WAF](https://aws.amazon.com/waf/) 实现速率限制和 OWASP 防护。
- 多因素认证：启用 Amazon Cognito MFA（基于 TOTP 的软件 token），以加强用户认证。
- 可观测性与告警：AgentCore 自动生成指标、日志和追踪，可通过 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 的生成式 AI 可观测性仪表板查看。为 agent 错误率和响应延迟配置告警。启用 Amazon Bedrock 模型调用日志以支持审计追踪。
- 数据生命周期：为设备文档版本管理实施 Amazon S3 生命周期策略，并为 issue 数据备份实施 Amazon DynamoDB 时间点恢复。
- 多区域部署：对于全球现场服务团队，可在多个 AWS Region 部署 AgentCore Runtime，并配以包含本地化设备文档的特定区域 Knowledge Base。

## 后续步骤

部署并测试本方案后，可以考虑以下增强措施：

- 零件订购集成：添加一个连接到零件库存系统的 @tool，使 agent 能够检查库存情况并直接在诊断对话中下单。
- 经销商沟通：添加一个 @tool，通过 [Amazon Simple Email Service](https://aws.amazon.com/ses/)（Amazon SES）或 [Amazon Simple Notification Service](https://aws.amazon.com/sns/)（Amazon SNS）将诊断摘要发送给最近的授权经销商。
- IoT 遥测集成：通过 [AWS IoT Core](https://aws.amazon.com/iot-core/) 连接设备传感器，在检测到异常读数时自动创建 issue，并为 agent 预填诊断上下文。
- 移动端现场应用：构建针对移动设备优化的前端，供技术人员在现场使用，并在连接受限的地区提供离线缓存。

## 结论

这个 AI 驱动的设备维修助手展示了 Amazon Bedrock AgentCore 如何改进农业现场服务运营。通过将 code-first 的 Strands Agent 与通过 Bedrock Knowledge Base 提供的全面制造商文档相结合，该方案使技术人员在到达现场之前就能获得精准的诊断建议和零件识别。

该实现的主要优势包括：

- 缩短平均解决时间：通过基于制造商文档的 AI 驱动分析，更快完成诊断和维修
- 提高首次修复率：全面的服务前分析确保技术人员携带正确的零件和流程到场
- 对话记忆：AgentCore Memory 跨多轮诊断会话维护上下文，并跨会话持久化知识
- 简化运维：单个 AgentCore Runtime endpoint 取代了分别部署 API Gateway、Lambda 和 Bedrock Agent 资源的需要
- 内置可观测性：自动的 X-Ray 追踪和 CloudWatch 集成提供端到端可见性，无需额外设置
- Code-first 开发：Strands Agent 的 @tool 装饰器模式让你能够扩展能力并在部署前进行本地测试

这一可扩展架构确保组织能够根据自身特定的设备组合和服务需求调整这一基础。添加新工具（用于零件订购、库存检查或经销商沟通）只需新增一个 @tool 函数，无需更改基础设施。
