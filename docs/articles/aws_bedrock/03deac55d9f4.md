# 建立对 AI 智能体的信任：基于 Amazon Bedrock AgentCore 的生产级评测框架

## 北极星

每一家争相部署 AI 智能体的组织，都要面对同样的拷问：一个在演示里表现漂亮的智能体，可能在生产环境中悄悄退化；等到人察觉时，信任已经碎了。传统软件会大声地失败，智能体则是无声地失败。它给出的答案看起来自信、读起来流畅，却是错的。当这个答案驱动了一个真实的业务决策，代价不是一个坏掉的功能，而是与用户之间破裂的关系。

这就是质量问题的内核。因此挑战不在于构建一个能跑通一次的智能体，而在于证明它们能持续跑通——在规模之下，覆盖每一个子智能体、每一个工作流、每一次发布。赢得智能体时代的团队，是那些不把质量当作最后一道 QA 环节、而是把它当作智能体自身的操作系统来对待的团队：持续度量、自动守护，并在每一次交互中改进。在这篇文章里，我们展示如何用 Amazon Bedrock AgentCore 为生产就绪的 agentic 方案构建一个大规模的持续质量闭环。

### 业务问题

这套方案供内部使用，用到了 Amazon Bedrock AgentCore 和其他 AWS 服务，让销售和销售管理者能在 Amazon Quick 里用日常英语提出业务问题。在这一个体验的背后，是多个各司其职的子智能体在协同工作：Performance Insights Agent 负责按销售区域归口的营收与业绩，Customer Insights Agent 负责客户情报，Data Insights Agent 负责在基础数据集上做 text-to-SQL，此外还能直接进入 dashboard。答案的可见范围受每个用户的销售区域和角色级安全策略限定。一线团队用这些答案来协助规划客户策略、准备客户会议，所以数字必须是对的。最具破坏性的失败不是崩溃，而是一个流畅、自信、却悄悄出错的答案。上线之前，我们在评测 Customer Insights Agent 时正好发现了这种答案：

- 它把某客户在某服务上三个月的 $410.08 营收报成了 “$410.08 Million.”
- 它把 Sales Revenue 标注成了 Sales Revenue excluding Adjustments。
- 它给出了一个 Annual Recurring Revenue 估算值，而数据里根本没有这个东西。
- 它把自己算出来的结果当作有出处的既成事实呈现。

在历次运行中，监控一直是绿的。它只告诉我们系统做出了响应，却没告诉我们答案对不对。

如果这些错误没被拦住就上了线，代价要由一线来承担。一名销售把被放大的数字复述给客户，就会在客户那里失去可信度。这正是我们要在上线前把它抓出来的原因。风险不会止于上线：每新增一个智能体，每次改动数据、prompt、代码或模型，它都在增长。它甚至会在没有任何发布的情况下增长，因为上游 pipeline 每周都在刷新数据。协同发布还会带来一个相关的风险：当一个数据改动、一个工具改动和配套的 prompt 更新本该一起上线却分头落地时，在所有改动追平之前，系统会带着错配状态运行。在一次预生产测试中，仅这个错配窗口就把通过率从 78% 降到了 38%。要抓住这类失败——在每次发布之前、并在生产里持续地——我们需要一个框架，它能显示答案是否有依据、是否正确，并能把每一次失败追溯到数据、prompt 或智能体代码里的根因。

在 AWS，销售、市场与全球服务（SMGS）运营团队开发了一套生产级的多智能体系统，服务于全球的 AWS Field Sales。它面向两类截然不同的受众。对一线销售团队，它把数小时的手工数据分析换成按需的、对话式的情报，帮助销售理解自己业务的健康度、发现风险与机会，并更快地采取行动。对管理层，它支撑包括 Weekly Business Reviews（WBRs）在内的业务管理例会节奏，把整个业务组合里真正要紧的信号浮现出来，而不需要人工准备报表。同一套 agentic 系统，既服务冲锋在前线的销售，也服务在规模上复盘业绩的管理者。

这套 agentic 系统编排着一个不断扩张的专业子智能体组合，每个子智能体各自拥有一个独立的能力域。其中包括：[Performance Insights Agent](https://aws.amazon.com/blogs/machine-learning/how-aws-smgs-uses-an-ai-powered-conversational-assistant-to-transform-business-management-with-amazon-bedrock-agentcore/) 从复杂的销售数据里生成自然语言的商业智能叙述，把原始指标变成可落地的销售洞察。[Customer Insights Agent](https://aws.amazon.com/blogs/machine-learning/build-unified-intelligence-with-amazon-bedrock-agentcore/) 通过综合产品使用、支持历史、合同状态与互动数据上的信号，为每个客户拼出一张 360 度视图，帮助销售判断客户正处在旅程的哪一段、下一步需要什么。[Data Insights Agent](https://aws.amazon.com/blogs/machine-learning/text-to-sql-solution-powered-by-amazon-bedrock/) 是一个 text-to-SQL 智能体，客户团队用它以日常英语查询结构化分析数据，一行 SQL 都不用写。这三个智能体就是本文其余部分反复提到的那三个。

要在规模上可靠地协调这些智能体，一件事变得再清楚不过：agentic 质量不是一个可以以后再处理的运维顾虑，而是能否运转起来的前提。一个退化的子智能体就能悄无声息地污染它下游的每一条响应，而传统监控抓不到它。这一现实让一整套覆盖全生命周期的评测框架从“可有可无”变成“必须如此”。AgentCore Evaluations 是 Amazon Bedrock AgentCore 的一项能力，正是它为这套框架提供了结缔组织；与之协同的还有 Amazon Bedrock Guardrails（安全）、Amazon CloudWatch（指标、告警、追踪）、Amazon Simple Storage Service（Amazon S3）和 Amazon Redshift（评测持久化）、Amazon Quick（dashboard），以及 AWS Lambda（自定义评测器）。

在这篇文章里，我们分享如何攻克在企业规模下运行 AI 智能体最难的那些运维挑战，以及 Amazon Bedrock AgentCore Evaluations 如何成为智能体质量的脊梁。具体来说，我们会讲到：

- **智能体玩的是另一套规则 **– 为什么智能体需要一种不同的运维纪律，以及为什么传统监控（延迟、错误率、可用性）会让你对最致命的失败视而不见。
- **一张覆盖全程的地图 **– 我们基于 AgentCore Evaluations 搭建的九阶段评测框架，覆盖智能体开发生命周期从第一次 commit 到生产的每一个阶段。
- **从理论到实践 **– 具体模式（持续集成与持续交付（CI/CD）回归闸门、金丝雀评分、漂移检测、自动化反馈闭环），以及 AgentCore Evaluations 究竟如何支撑其中的每一个。
- **真正要紧的指标 **– 这些做法在我们整个智能体组合上，对部署信心、回归防范和迭代速度带来的可度量影响。

## 为什么智能体需要结构化的评测框架

传统软件是确定性的：同样的输入产生同样的输出。机器学习（ML）模型引入了概率性输出，MLOps 随之出现，用来管理它们的训练、版本、监控与再训练。AI 智能体又叠上了第三层运维复杂度：自主的多步推理。此时问题从“是不是坏了？”变成“智能体在整条推理链上做出的是否是可靠的决策？”

智能体继承了两位前辈的难题，又添了几道新的。它们是非确定性的：面对相同的输入会走不同的推理路径。它们在路由、工具选择与综合汇总之间做出级联决策，其中任意一步都可能悄无声息地失败，并污染下游的一切。最关键的是，它们是静默退化的：延迟依旧很低，错误率依旧平稳，而智能体响应的质量却在被侵蚀——因为智能体仍然在*响应*，只是响应得*错了*。

智能体评测要抓的正是这件事。它横跨五个维度：**安全**（它是否在定义好的边界内行事？）、**质量**（它产出的是否是正确、连贯、有依据的响应？）、**性能**（它是否足够快、足够可靠？）、**成本**（它在规模上运行得是否高效？）、以及**运营控制**（我们能否快速发现、诊断并处置问题？）一套成熟的评测实践，会在智能体的完整生命周期中持续应对这五个维度。

在这篇文章里，我们分享如何把五个评测维度在一个生产级的多智能体系统里落到实处。安全与保障是我们的第一优先级。达不到它的安全基线，就没有智能体能上线，也没有智能体能继续运行。质量在本文占的篇幅最多，因为在五个维度里它最难做对、也最受益于一个专门的框架，但它并不凌驾于安全之上。性能、成本和运营控制则与前两者一起，编织进生命周期的每一个阶段。关键在于，这套框架适用于智能体层级结构的每一层。在**工具层**，每项能力（一个客户消歧工具、一个图检索工具）都有自己的评测契约。在**智能体层**，每个子智能体做端到端评测。在**多智能体层**，编排路径要评测其连贯性、路由正确性，以及跨智能体边界的综合准确度。

这九个阶段同时在三个层级上适用，而这个层级结构并非本产品的特例。当我们构建或集成新的生产智能体时，它就是那个正确的心智模型。多数团队从智能体层开始评测，然后就停在那里。但智能体层的质量，只和它所依赖的工具一样好；而多智能体系统还引入了第三个失败面，这两个层级单看都看不见它。一套稳健的评测实践要覆盖这三层，每一层都在自己的 golden set、自己的评测器和自己的晋级标准下，跑完这九个阶段。

## 智能体评测框架：九个阶段，一个闭环

这九个阶段沿着智能体的生命周期，从第一次 commit 一路走到线上生产，每一个都回答团队在智能体逐渐成熟时面对的那个问题。

### 智能体生命周期与九个常见问题

**阶段 2：实验（The Experiment）：** *“哪个版本更好？”*

**阶段 3：合并（CI）：** *“我是不是搞坏了什么？”*

### 阶段 1：地基。定义质量

评测一个智能体的根基不在于选对工具，而在于问对问题：这个智能体的成功是什么样子，我们怎么知道它在失败？答案必须来自客户，而不是来自模型。这是一个迭代的过程。随着我们观察智能体在生产里实际做了什么，我们对成功的定义也愈发锐利。在这里定义的一切（失败阈值、评测器栈、golden set、安全规则、延迟预算和成本目标）就是后续每一个阶段都要执行的契约。如果阶段 1 含糊，下游的每一道闸门都是在猜。

**阶段 1.1：先定义你的业务指标。** 先问这个智能体是为交付什么而存在的。两类终端用户画像对成功的定义不同：

- 对销售而言，成功意味着走进一场客户对话时，带着准确、最新的情报，颗粒度合适、时机也合适。
- 对管理层而言，成功意味着每周复盘和跨业务复盘的输入是可靠的，而不需要冗长的人工准备。这些是业务结果，不是模型属性。

**阶段 1.2：把这些业务指标翻译成评测指标。** 对每一个结果，找出能确认智能体交付了它的信号。每个信号都成为一个被追踪的指标，配有明确的阈值和告警条件。准确的客户情报对应实体解析准确率和 grounding rate；销售的信任对应 faithfulness 和 hallucination rate；销售能否据此行动对应 helpfulness 和范围遵从率。管理层复盘的可靠性对应准确率通过率和响应覆盖率。这一翻译必须覆盖五个维度：除了质量阈值，还要定义安全 guardrail 策略，为每个工具和每个智能体设定 p50、p90 和 p99 延迟目标，确立每次查询的成本预算，并定义服务等级协议（SLA）——它决定告警何时触发、以及触发之后走哪本 runbook。

具体到准确率，由于这套方案直接影响营收决策、续约策略和高管复盘，标准定得很高。一个自信的错误答案不只是浪费销售的时间，它会在一个真实的业务时刻导致一个错误的决策。我们从真实的生产错误中归纳出六种失败类型，其中任何一种都会把一次响应判为不准确：

- **指标错换：** 客户对、期间对，返回的指标错了。按每 100 次响应中的出现次数追踪。
- **期间错误：** 一个时间窗口的数据被标成了另一个，例如把同比（YoY）数字呈现给销售时当成环比（MoM），或反之。按引用正确窗口的百分比追踪。
- **实体错误：** 客户名称或子公司被混淆。按实体解析准确率的百分比追踪。
- **纯粹幻觉：** 没有可追溯来源的、无依据的数字。按 grounding rate 的百分比追踪。
- **符号错误：** 指标对，货币或单位符号错。按范围遵从率的百分比追踪。
- **越权计算：** 源数据里并不存在、却被自行推导出来的数字。按每 100 次响应中的出现次数追踪。

整体准确率通过率是头条指标，而按维度拆分追踪才让它可行动。除准确率之外，我们还追踪 [Response relevance](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/prompt-templates-builtin.html#response-relevance)、[Faithfulness](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/prompt-templates-builtin.html#faithfulness)、[Helpfulness](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/prompt-templates-builtin.html#helpfulness)、[Instruction Following](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/prompt-templates-builtin.html#instruction-following),[Tool Selection Accuracy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/prompt-templates-builtin.html#tool-selection-accuracy)。一个正确的答案埋在三个段落里，或者来得太晚，同样是对销售的失败。

**阶段 1.3：构建一个能反映这些指标的评测器栈。** 没有任何单一评测器类型能覆盖各种可能的失败模式。我们组合四种类型：

- **AgentCore 内置评测器**，提供宽泛的基线覆盖。Relevance、Faithfulness 和 Helpfulness 直接对应 [AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 中原生可用的评测模板。
- **定制化评测器**，我们的分类表中每种失败类型各一个：一个指标错换评测器、一个期间错误评测器、一个错误客户评测器、一个纯粹幻觉评测器、一个符号错误评测器，以及一个越权计算评测器。这六种都不在原生模板的覆盖范围之内，它们是我们建立在 AgentCore 框架之上的领域专用信号。提前弄清哪些指标已有原生模板覆盖、哪些必须自建定制化评测器，本身就是设计决策的一部分。
- **第三方评测器，** 我们部署了来自第三方开源库 DeepEval 和 AutoEval 的托管评测器。
- **确定性评测器**，用于正确答案可被精确已知的 ground truth 校验，例如营收、续约日期和合同状态。

在推理质量和 helpfulness 没有唯一正确答案的地方，我们改用 LLM-as-judge 评分细则：除了 Relevance、Faithfulness 和 Helpfulness 的内置细则，还支持完全自定义的细则。AgentCore Evaluations 原生同时提供 ground truth 评测和 LLM-as-judge 评测，正是这一点让我们能把两条评测路径都立起来，而不必自己构建任何一个打分引擎。确定性评测给出事实上的精度，LLM-as-judge 给出推理上的广度。

**阶段 1.4：构建一套 golden set 来检验你的评测指标。** 在**工具层**，每个关键工具都有自己的确定性 ground truth 配对：客户识别必须解析到精确的规范实体，否则就是失败。在**智能体层**，对真实用户查询做主题分析，产出一个横跨四种提问类型（综合性、报表型、推理型和含糊型）的数据集，每种类型都需要不同的评测策略，并按月复核。在**多智能体层**，端到端的编排场景能抓住那些只有在智能体相互作用时才浮现的错误。golden set 不只是一份质量数据集，它同样包含安全测试用例、延迟基准用例和成本参考用例，因此阶段 3 和阶段 4 可以对着同一份精编数据集检查五个维度。

golden set 是一份活文档，来自三个来源。生产来源的用例从真实销售和高管的查询里采样，包括阶段 7 里被晋级的低分线上会话。失败来源的用例来自在预生产或生产里抓到的每一次回归，包括阶段 3 晋级的哨兵用例和阶段 9 晋级的永久回归守卫。合成的边缘用例是刻意构造出来的，用来保证覆盖那些我们知道很重要、却不能等着在生产里遇到的场景，例如上面的四种提问类型，以及阶段 4 里的母公司与子公司、股票代码消歧用例。这套数据集受版本控制，会被评审，并从三个来源持续扩充。

### 阶段 2：实验。知道哪个版本胜出

在一个改动合并之前，我们会跑一次 *AgentCore On-Demand Evaluation*，用同一套评测器对着同一份 golden set 打分。开发团队使用质量、延迟、成本和 context token 这些指标来筛选后续的对比，而对比会同时在五个维度上被评测，如 **Figure 3** 中并排呈现的那样。一个把准确率提升 5%、却把延迟翻倍、成本翻三倍的模型，并不会自动胜出。

### 阶段 3：合并（CI）。在合并时挡住回归

阶段 3 是一道预生产闸门。它跑在 staging 环境里，由代码和配置变更触发，职责是在一个坏改动抵达生产之前就把它拦下。如果阶段 3 抓到了一次回归，什么都不发布。

工程师或研究员会以很多方式改动系统：prompt、底层数据、工具或模型。改动在本地看起来干净，测试也过了，但一个让科技类客户响应变好的 prompt，可能悄悄让金融服务类客户的响应变差。没有自动化的闸门，它就会上线。

我们的 CI 评测使用 AgentCore On-Demand Evaluation，在每次 staging 部署时自动触发。工程师不需要记着去跑一次评测。没有任何部署能悄无声息地跳过闸门。这次运行几分钟就能完成，因为它只评测哨兵集，而不是完整的 golden set。快是刻意设计的：哨兵集足够窄，能在每次部署上跑；又足够有代表性，能抓住最要紧的那些失败。

哨兵集是横跨五个维度、精心挑选出的最高风险场景。超出容差的质量回归会阻断部署。一次安全边界违例同样硬性阻断。一个把 p90 延迟翻倍的改动，不经一个刻意的决策就不会放行。token 成本尖峰会在规模上累积之前被标记出来。每次哨兵运行都把自己的分数作为自定义指标发布到 CloudWatch，与质量分数、每次查询的延迟、成本和安全通过率并列，全部在每次运行后发出；CloudWatch 告警也已配置成在任何指标突破阶段 1 阈值时触发。每次运行还会被记录和存储，喂给阶段 8 和阶段 9 依赖的审计轨迹。我们在每个层级各维护一份独立的哨兵：工具、智能体和多智能体。一个改善了智能体层质量却让某个关键工具退化的改动，依然会被阻断。哨兵集按月复审，而一旦有回归漏到生产，会立刻被晋级为永久用例，不让它第二次触达用户。

**一个它能抓住什么的具体例子。** 在一次数据归一化更新之后，一个消歧工具对一部分客户名称格式开始返回未解析的实体。智能体收到一个未解析的实体后，用一个最佳猜测的匹配来回应，把另一个真实客户的数据返回了回去。我们的工具层哨兵恰好包含这一类边缘用例：在受影响的客户名称格式上，实体解析的 ground truth 校验失败，部署被自动阻断。这个改动从未到达生产。

### 阶段 4：闸门（CD）。带着量化信心发布

哨兵覆盖 15 个用例。生产环境覆盖的则是数以万计的查询形态，横跨数百种客户类型、地域和销售分层。通过哨兵是必要的，但并不充分。

在一个候选版本发布之前，我们会对着完整的 golden set、在所有评测器维度上跑一次 AgentCore On-Demand Evaluation。我们把它称为*质量闸门（Quality Gate）。*它用一个量化的发布决策取代了“看起来还行”。

**沙箱化执行与工具 mock。** 把它想象成一次回放，而不是一次真实调用。提前，我们会冻结一份已知的、带版本号的正确工具行为数据集。候选版本在闸门期间发起的每一次工具调用都会被拦截，并从那份冻结的数据集里得到应答，而不是从真实系统。我们用两步构建这份冻结数据集。第一步，我们单独测试每个工具：给它发一份来自 golden set 的留存测试集，其中每道题的正确答案都是已知的，然后把它实际返回的结果对着已知答案打分。这告诉我们工具本身是否可用（实体解析、检索、SQL 生成），此时智能体还没有参与。第二步，在工具的响应被确认正确之后，我们把同样这些经过验证的答案冻结成候选在闸门评测中看到的那份回放数据集。这意味着智能体纯粹是在它自己的推理上被测试，而不是受真实工具的速度或可用性影响；又因为每个候选都从同一份冻结数据集回放，任何两两对比之间的分数差异都关于智能体本身，而不是工具抖动。

**聚合的端到端打分。** 闸门还会跑一次整体评审：完整的候选智能体端到端回答 200 道留存题目，由 LLM-as-judge 细则在所有评测器维度上打分。三种条件中的任意一种都会自动关闸：总分相对该候选自己上一次运行出现回归；没能超过当前的生产基线；或者 200 道题里超过某个既定百分比的题目落在单题阈值以下。候选必须三项全过，这能抓住简单平均值掩盖的东西：一个提升了均值、却在更大比例的单选题上悄悄失败的模型，过不去。

**一个它能抓住什么的具体例子。** 正是在这里，mock 测的是智能体自己的推理，而不只是它底下的那些工具。我们的 golden set 里有一个层级错配用例：Customer Insights Agent 和 Data Insights Agent 对同一个客户返回两个不同、各自都正确的营收数字，一个限定在母公司账户，另一个限定在子公司。两个数字都没有错。这个用例测的是智能体能否从查询的语义和请求者的画像推断出正确的层级范围（一名销售大概率想要子公司，而一次管理层的查询大概率想要母公司汇总），而不是默认取一个、求平均，或者让销售自己去消歧。当时候选失败了，它对一道子公司范围的题目返回了母公司层的数字。golden set 对这个用例的 ground truth 明确规定了问题期望哪个范围，于是质量闸门立刻标记出这个错配：不是错的数字，而是给错了范围的正确的数字。

### 阶段 5：金丝雀。抓住部署后的静默失败

阶段 5 是一个生产后的监视器。它在生产环境里持续运行，对着真实流量和合成评测用例，职责是抓住那些没有任何代码改动触发、因此阶段 3 看不见的问题。阶段 3 防的是工程师改出来的东西。阶段 5 防的是其余一切，例如上游数据位移、不断演化的模型行为、第三方依赖的变化，或其他只在真实负载下才显形的状况，例如延迟升高、流量结构变化。

这个产品背后是一整套由数千个上游 schema 和数据 pipeline 喂养的数据资产。在任意一天里，其中数十条 pipeline 会刷新，而不触发任何部署或 CI 闸门。智能体代码没变，模型没变，但它推理所依赖的数据变了，质量就可能因此静默退化。我们是吃过苦头才学会的：一条上游 pipeline 带着 schema 变更刷新，智能体开始引用错误时间窗口的数据，而第一个信号来自一位销售的问询，不是自动告警。阶段 5 就是我们如何在第一个 30 分钟评测窗口内把它抓住的方式。

我们按两套互补的节奏运行 AgentCore Batch Evaluation，而节奏的选择是刻意的。

我们从两个方向吸取教训后才定在 30 分钟一轮：15 分钟会产生太多误报；60 分钟则会让两小时过去之后真实退化才被记录。我们把每 30 分钟一轮称为一个评测窗口。30 分钟能在 90 分钟内（连续三个窗口）抓住一个真实的趋势，同时过滤掉单次查询的噪声。每个窗口都对 golden set 做轮转式抽样打分，24 小时内即可覆盖全量。

阈值是刻意低于 CI/CD 闸门的。单个窗口失败是一条运维信号，不是一起事故。只有在连续三个窗口突破阈值之后我们才呼叫 oncall。这条规则同样是硬学来的：第一个月我们用单窗口阈值，oncall 从此完全不信任这套系统。每天一次，完整 golden set 会按闸门阈值跑一次，作为权威的每日记分卡。30 分钟窗口把趋势浮现出来，每日运行确认它并开出一张工单。

每次运行都向 CloudWatch 发布（准确率、hallucination 率、grounding rate、延迟和成本），配套的告警逻辑会区分这两种节奏。金丝雀在三个层级上运行：工具层的分数能在一个退化的检索工具污染智能体层响应之前把它暴露出来。

**另一个它能抓住什么的例子。** 在一次上游索引刷新之后，一个检索工具开始返回松松相关的 chunk，而不是回答问题所需的精确上下文。延迟是正常的，错误率为零。智能体继续产出流畅、自信的响应——它在一个依据很弱的上下文上推理，给出的答案看起来正确，引用的数字却是错的。没有任何基础设施告警触发。金丝雀在第一个 30 分钟窗口就抓住了它：grounding rate 和检索精度在工具层哨兵上一同下滑，在销售基于退化答案采取行动之前触发了 CloudWatch 告警。低的评测器分数标记出了那条确切的 trace。顺着它，值班工程师在 AgentCore 里打开那条 trace，几分钟内就把退化的上下文追回到了那个检索工具。

### 阶段 6：对手。防住滥用

并非每一段坏输出都来自一个退化的模型。在一个服务数千名用户、承载敏感业务数据的系统里，精心构造以套取未授权客户数据的查询，以及嵌在被检索文档里的 prompt 注入，都是可预期的模式。

安全不是一个阶段，它贯穿全部九个阶段。我们在每次交互的两个点上应用 Amazon Bedrock Guardrails。在输入侧，我们校验查询范围并筛查 prompt 注入。在输出侧，我们确认没有敏感数据被呈递给未授权用户，并且智能体没有被人操纵成违反策略。这些检查在 100% 的流量上同步执行，在响应到达用户之前。

我们配置了两层 guardrail，各自覆盖一类不同的威胁：

**内容过滤器** 检测并阻断输入和输出中的有害或不当内容。我们在包括 `VIOLENCE`、`HATE`、`SEXUAL`、`MISCONDUCT` 和 `INSULTS` 在内的类别上强制启用过滤器。触发这些过滤器的请求或响应会被阻断，不会送到销售那里、也不会呈现给用户。

**Prompt 安全过滤器** 在单一的 `PROMPT_ATTACK` guardrail 类别下保护智能体免受对抗性操纵，涵盖三个子类型：`JAILBREAK`（试图覆盖智能体的系统指令或绕过其运行边界）、`PROMPT_INJECTION`（嵌在检索到的文档、工具输出或用户查询里的非预期指令），以及 `PROMPT_LEAKAGE`（试图套取系统 prompt 或内部配置）。在一个使用检索增强生成（RAG）的多智能体系统里，经由检索内容的 prompt 注入是一个真实风险。一位销售的客户数据里的一份非预期文档，可能试图在推理过程中改变智能体的行为。

安全规则在阶段 1 定义，在阶段 3 和阶段 4 检查回归，并在生产中被持续执行。

### 阶段 7：漂移。维持质量并用真实流量验证

质量会从多个方向退化：上游数据变化却不触发部署，模型逐渐过时，用户则用任何 golden set 都没完全预料到的查询去试探边界。阶段 7 要在销售之前发现它，并在全面铺开之前用真实用户流量验证候选版本。

**漂移检测。** 我们使用 AgentCore Online Evaluation，把 10% 的真实流量持续采样穿过阶段 1 定义的那些不同的评测器，因此漂移会立即显现为对离线建立起来的基线的偏离。分数汇入一个 Quality-State Calculator，在同一时间窗口内监控质量、延迟和成本。

一个生产中的例子。我们用于客户识别的 golden set 是用合成边缘用例搭起来的：名称变体、子公司查询、缩写。它在离线上表现不错。但在真实流量里，销售会用股票代码查询（“AMZN 那边怎么样了？”）、简称和拼写错误，这些是合成用例没有演练过的。Quality-State Calculator 在连续三个 30 分钟窗口里把漂移显示出来：凌晨 1:30 是 98%，2:00 是 81%，2:30 是 80%。滚动阈值被突破时 CloudWatch 呼叫了 oncall。值班工程师问了智能体一个问题：*“1 点到 3 点之间，客户识别准确率出了什么事？”* 得到的是一份趋势总结，把股票代码查询和简称点名为失败的驱动因素。智能体的 trace 让根因一眼可见。修复方式：把这些低分的线上会话扩充进 golden set，并更新消歧工具，让它在解析之前先归一化输入格式。在下一个评测周期内准确率就回到了基线。

真实流量喂养两条持续改进的闭环：低分会话被晋级为新的边缘用例进入 golden set；低分 trace 的聚类为 prompt 修订、工具更新和路由调整提供依据。

**A/B 测试：** 候选在过了质量闸门之后，AgentCore Gateway——Amazon Bedrock AgentCore 的一项能力——会在当前智能体与候选智能体之间切分并路由一部分真实流量。On-demand 确认在已知用例上没有回归；Online 确认它扛得住只有真实用户才会产出的长尾输入和新奇表述。候选必须在所有评测器维度上取胜或持平，才能全量铺开。

### 阶段 8：脉搏。实时质量可见性

一次对智能体的调用可能牵动三个子智能体、五个工具和两条检索路径。当质量告警响起时，“智能体流水线里某个地方”不是一本 runbook。阶段 8 正是阶段 5、6 和 7 的信号汇合成一层可观测性的地方，其分辨率高到足以采取行动。

AgentCore Observability 是 Amazon Bedrock AgentCore 的一项能力，也是这一层的地基。对托管在 AgentCore runtime——Amazon Bedrock AgentCore 的一项能力——上的智能体，每次执行都会通过 OpenTelemetry 自动插桩，为每一个推理步骤发出结构化遥测数据：调用了哪些工具、调用顺序、输入与输出、延迟以及 token 消耗，直接发布到 CloudWatch 成为自定义指标和日志，前提是启用了 CloudWatch Transaction Search（一次性的设置步骤）。评测器分数是另一条独立的管道：它们来自 evaluation configs，而不是执行插桩，落在各自的 CloudWatch log group 里。每次评测运行还会把完整输出持久化到 S3 和我们的数据湖，喂养两个 dashboard：

- 一个对话式 dashboard，用于查询评测与可观测性结果。
- 一个 Amazon Quick dashboard，用于趋势分析、记分卡追踪，以及横跨全部历史的跨智能体对比。

### 阶段 9：反馈闭环。持续改进

这个阶段把观察变成行动。系统随时间复利式地累积质量。我们用 AgentCore optimization——Amazon Bedrock AgentCore 的一项能力——来闭合这个环。

- **系统 prompt 推荐：** 分析智能体 trace，生成一个数据驱动的、经过优化的系统 prompt，以提升目标评测器上的表现。这套方案会利用失败模式，并加入具体的行为指令。
- **工具描述推荐：** 分析智能体 trace，生成更锐利的工具描述，以减少工具选择上的混淆，尤其是在智能体面对含糊请求选错工具的时候。

我们来看一个例子：

> AgentCore optimization 实战
>         要改进什么：目标评测器：hallucination——模型在不相关的语境里逐字复现 few-shot 示例中硬编码的取值。
>         为什么会这样：few-shot 示例里含有真实的美元金额和客户名称（例如 “$4.2M”、“Acme Corp”），模型把它们记住并泄漏进不相关的查询里。
>         如何修复：把 few-shot 示例里的硬编码取值换成通用占位符（例如 $[AMOUNT]、[CUSTOMER_NAME]），让模型学习响应的结构，而不记住具体的数据点。
>         影响与结果：修复已应用。纯粹幻觉的发生次数从每 10,000 次响应 138 次降到 52 次以下，整体 grounding rate 从 93% 提升到 96%。

AgentCore optimization 用这些推荐，基于真实的智能体 trace 和一个目标评测器，产出数据驱动的系统 prompt 与工具描述改动。AgentCore optimization 建立在 [AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 之上。低分的 trace 会被晋级进 golden set，成为永久的回归守卫，于是每一次失败都不会第二次触达用户。

## 智能体评测关键指标速览

评测指标在阶段 1 定义，在九个阶段中执行，并在生产里被持续监控。这一组指标不是静态的。随着我们从生产中的智能体身上学到东西，新的失败模式会浮现，新的维度变得可度量，指标也随之演化。下面这些是我们的起点，以及我们今天追踪的内容。

| **层级** | **指标** | **它衡量什么** | **如何追踪** |
| --- | --- | --- | --- |
| 质量：智能体 | 整体准确率通过率 | 零分类失败的响应占比 | 记分卡头条指标 |
| 质量：智能体 | 指标错换率 | 客户与期间都对，返回的指标错 | 每 100 次响应出现次数 |
| 质量：智能体 | 期间错误率 | 来自错误时间窗口的数据 | 引用正确时间窗口的百分比 |
| 质量：智能体 | 客户错误率 | 混淆了客户名称或子公司 | 实体解析准确率 % |
| 质量：智能体 | grounding rate | 数字可追溯到某个检索来源 | 有依据的报告数字占比 |
| 质量：智能体 | 范围遵从率 | 针对所问问题作答的响应 | 切题响应百分比 |
| 质量：智能体 | 越权计算率 | 未经批准的推导数字 | 每 100 次响应出现次数 |
| 质量：智能体 | Relevance / Faithfulness / Helpfulness | 响应质量横跨 AgentCore 内置维度 | AgentCore 内置评测器分数（0–1） |
| 质量：工具 | 客户识别准确率 | 工具解析到精确的规范实体 | 正确解析百分比（确定性） |
| 质量：工具 | 工具选择准确率 | 智能体为查询选对了工具 | AgentCore 内置评测器分数（0–1） |
| 质量：工具 | 检索精度 | 检索到的上下文包含所需信息 | 含相关上下文的检索百分比 |

## 结语

这套九阶段智能体评测框架的影响是具体且可度量的。过去需要数天乃至数周才浮现、而且通常是经由一条销售投诉才浮出来的质量回归，如今在四小时内就会被自动化评测抓住。过去依赖主观判断的发布决策，如今要求每一个评测器都通过一道量化阈值。prompt 迭代周期从数天降到数分钟。安全从周期性审计变成对每个请求 100% 的 guardrail 覆盖。延迟回归在抵达生产之前就在 CI 闸门被抓住。过去几周后才在账单里冒出来的成本意外，如今在阶段 2 就会被评测，并在改动上线之前由质量闸门把关。而“智能体流水线里某个地方”这件事，变成了一键从 CloudWatch 告警抵达一条完整的智能体执行 trace，其中每个推理步骤都清晰可见。

更宽的那条教训，行业以前就学过。DevOps 告诉我们，不带自动化测试就发布代码是鲁莽的。MLOps 告诉我们，不带监控就部署模型是危险的。AgentOps 就 AI 智能体告诉我们同一件事：不做持续的、多层级的评测就运行它们，等于蒙眼飞行。

这里描述的九阶段框架并不是销售情报智能体的专属。任何部署多智能体系统的团队——那些会推理、调用子智能体和工具、并综合响应的系统——都会在同样的生命周期里面对同样的问题。你的失败分类表会长得不同。你的 golden set 会反映你的领域。你的评测器栈会针对你的用户调优。保持不变的是那条原则：评测不是最后一道 QA 环节，它就是智能体自身的操作系统——持续度量、自动守护，并在每一次交互中改进。

如果你在构建生产智能体，并希望把这种评测纪律带到你的系统里，Amazon Bedrock AgentCore Evaluations 就给了你这样做的平台：面向实验的 on-demand 评测、面向持续监控的 batch 评测、面向真实流量的 online 评测、内置与定制化评测器、数据集评测（公开预览中）、CloudWatch 集成，以及 AgentCore optimization 的推荐和 A/B 测试这些能力，用来闭合反馈环。从阶段 1 开始，为你的智能体定义“好”是什么样子，然后让框架完成其余的事。
