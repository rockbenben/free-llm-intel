# 使用 Amazon Bedrock 流式 API 与 AWS AppSync 改善企业级应用的对话式 AI 响应时间

许多企业正在使用 [Amazon Bedrock](https://aws.amazon.com/bedrock) 中的大语言模型（LLM）从内部数据源中获取洞察。Amazon Bedrock 是一项全托管服务，通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、Meta、Mistral AI、Stability AI 和 Amazon 等领先 AI 公司的高性能基础模型（FM）供你选择，并提供广泛的能力来构建兼顾安全、隐私和负责任 AI 的生成式 AI 应用。

实施对话式 AI 系统的组织常常面临一个共同挑战：尽管它们的 API 能够快速找到针对性问题的答案，但需要 reasoning-actioning（ReAct）逻辑的复杂查询可能要花很长时间处理，从而对用户体验造成负面影响。这个问题在受监管行业中尤为突出，因为安全要求会带来额外的复杂性。例如，一家管理着超过 1.5 万亿美元资产的全球金融服务机构就遇到了这一确切挑战。尽管该机构已成功实施了与多个 LLM 和数据源集成的对话式 AI 系统，但仍需要一个既能维持其严格安全协议（包括在虚拟私有云（VPC）环境中运行的 AWS 服务和企业 OAuth 集成），又能改善复杂查询响应时间的解决方案。

[AWS AppSync](https://aws.amazon.com/appsync/) 是一项全托管服务，让开发者能够构建具备实时能力的无服务器 GraphQL API。本文演示如何把 AWS AppSync 订阅与 Amazon Bedrock 流式端点结合起来，以增量方式交付 LLM 响应。我们提供了一份企业级实施蓝图，帮助受监管行业中的组织在保持安全合规的同时，通过即时交付实时响应来优化用户体验。

## 解决方案概览

本文讨论的解决方案使用 AWS AppSync 启动异步对话工作流。由 [AWS Lambda](https://aws.amazon.com/lambda) 函数承担与 Amazon Bedrock 流式 API 交互的重活。当 LLM 产出 token 时，这些 token 会通过 AWS AppSync 的 mutation 与 subscription 流式发送到前端。

本文的示例代码提供了 Lambda 函数与 AWS AppSync API 的参考实现。下图展示了参考架构，并给出了各项 AWS 服务如何集成以实现预期结果的高层概览。

[![解决方案架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/24/ML-15925-image-1.png)](https://aws.amazon.com/blogs/machine-learning/improve-conversational-ai-response-times-for-enterprise-applications-with-the-amazon-bedrock-streaming-api-and-aws-appsync/images/image-1.png)

下面我们逐步梳理该解决方案如何处理用户请求，以及用户如何从 Amazon Bedrock 中的 LLM 获得实时响应：

- 当用户加载 UI 应用时，应用会订阅 GraphQL 订阅 `onSendMesssage()`，该订阅会返回 WebSocket 连接是否成功。
- 用户输入查询后，应用会调用 GraphQL 查询（`getLLMResponse`），并触发数据源 Lambda 函数。
- 数据源 Lambda 函数向 [Amazon Simple Notification Service](https://aws.amazon.com/sns)（Amazon SNS）主题发布一个事件，并向用户返回一条 201 消息，同步流程到此结束。

这些步骤在下方的时序图中展示得更清楚。

![时序图 1](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/24/ML-15925-image-2.png)

- Orchestrator Lambda 函数被发布到 SNS 的事件触发，并通过 Amazon Bedrock 的 API 调用 `InvokeModelWithResponseStream` 发起流式传输。
- Amazon Bedrock 接收用户查询、启动流式传输，并开始把流式 token 回传给该 Lambda 函数。
- 当 Orchestrator Lambda 函数收到来自 Amazon Bedrock 的流式 token 时，该函数会调用 GraphQL mutation `sendMessage`。
- 该 mutation 触发包含 LLM 部分响应的 `onSendMessage` 订阅，UI 在收到这些流式 token 时就将其打印出来。

### 数据与 API 设计

[AppSync API GraphQL schema](https://github.com/aws-samples/bedrock-appsync-streaming/blob/main/bedrock-appsync-api/schema.graphql) 由 query、subscription 和 mutation 三类操作组成。

下面的代码是 query 操作：

```
input GetLlmResponseInput {
	sessionId: String!
	message: String!
	locale: String!
}
type Query {
	getLlmResponse(input: GetLlmResponseInput!): GetLlmResponse
		@aws_api_key
}
```

query 操作 `getLLMResponse` 是同步的，接受 `sessionId`、`locale` 和用户提供的 `message`。

前端必须发送唯一的 `sessionId`；该会话 ID 唯一标识用户的聊天会话。在活跃对话期间，会话 ID 保持不变。例如，如果用户重新加载前端，就会生成一个新的 `sessionId` 并发送给 query 操作。

前端还必须发送 `locale`，表示用户偏好的语言。受支持的区域设置列表参见 [Amazon Lex V2 支持的语言和区域设置](https://docs.aws.amazon.com/lexv2/latest/dg/how-languages.html)。例如，我们使用 `en_US` 表示北美英语。

最后，用户的消息（或查询）放在 `message` 属性中。`message` 属性的值会传给 LLM 进行分析。

下面的代码是 subscription 操作：

```
type Subscription {
	onSendMessage(sessionId: String!): SendMessageResponse
		@aws_subscribe(mutations: ["sendMessage"])
        @aws_api_key
}
```

AWS AppSync 的 subscription 操作 `onSendMessage` 接受 `sessionId` 作为参数。前端调用 `onSendMessage` subscription 操作，以 `sessionId` 订阅一个 WebSocket 连接。这使前端能够在针对给定 `sessionId` 的 mutation 操作成功执行时，随时从 AWS AppSync API 接收消息。

下面的代码是 mutation 操作：

```
input SendMessageInput {
	sessionId: String!
	message: String!
	locale: String!
}
type Mutation {
	sendMessage(input: SendMessageInput!): SendMessageResponse
		@aws_api_key
        @aws_iam
}
```

mutation 操作 `sendMessage` 接受 `SendMessageInput` 类型的载荷。调用方必须提供 `SendMessageInput` 类型中的所有必需属性（在 GraphQL schema 片段中以感叹号标示），才能通过该 mutation 操作成功向前端发送消息。

Orchestrator Lambda 函数调用 `sendMessage` mutation，把已部分收到的 LLM token 发送给前端。我们会在本文后面更详细地讨论 Orchestrator Lambda 函数。

### AWS AppSync 数据源 Lambda 函数

当前端调用 GraphQL query 操作 `getLLMResponse` 时，AWS AppSync 会调用 AWS AppSync 数据源 Lambda 函数。该 GraphQL query 是一个同步操作。

AWS AppSync 数据源 Lambda 函数的实现位于以下 [GitHub 仓库](https://github.com/aws-samples/bedrock-appsync-streaming/tree/main/bedrock-appsync-ds-lambda)，名为 `bedrock-appsync-ds-lambda`。该 Lambda 函数从传入的 GraphQL query 操作中提取用户的 `message`，并把该值发送到 SNS 主题。随后该 Lambda 函数向调用方返回成功状态码，表示消息已提交到后端进行处理。

### AWS AppSync Orchestrator Lambda 函数

只要有事件发布到 SNS 主题，AWS AppSync Orchestrator Lambda 函数就会运行。该函数使用 `converse_stream` [Boto3](https://boto3.amazonaws.com/v1/documentation/api/latest/reference/services/bedrock-runtime/client/converse_stream.html) API 调用发起 Amazon Bedrock 流式 API。

下面的代码片段展示了 Orchestrator Lambda 函数如何接收 SNS 事件、处理它，然后调用 Boto3 API：

```
brt = boto3.client(service_name='bedrock-runtime', region_name="us-west-2")
messages = []
message = {
    "role": "user",
    "content": [{"text": parsed_event["message"]}]
}
messages.append(message)
response = brt.converse_stream(
    modelId=model_id,
    messages=messages
)
```

代码首先使用 `bedrock-runtime` 服务名实例化 Boto3 客户端。Lambda 函数接收 SNS 事件，并用 Python 的 JSON 库解析它。解析后的内容存放在 `sns_event` 字典中。代码会创建一个 Amazon Bedrock [Messages API](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-anthropic-claude-messages.html) 风格的 prompt，包含 `role` 和 `content` 属性：

```
message = {
    "role": "user",
    "content": [{"text": parsed_event["message"]}]
}
```

`content` 属性的值来自 SNS 事件中的 `sns_event["message"]` 属性。`role` 的取值列表请参阅 `converse_stream` [Boto3](https://boto3.amazonaws.com/v1/documentation/api/latest/reference/services/bedrock-runtime/client/converse_stream.html) API 文档。

`converse_stream` API 接受 `modelId` 和 `messages` 参数。`modelId` 的值来自 Lambda 函数上设置的环境变量。`messages` 参数的类型是 `dictionary`，且只能包含 Amazon Bedrock [Messages API](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-anthropic-claude-messages.html) 风格的 prompt。

`converse_stream` API 成功运行后会返回一个对象，Lambda 代码会进一步分析该对象，把部分 token 发送给前端：

```
stream = response.get('body')
if stream:
    self.appsync = AppSync(locale="en_US", session_id=session_id)
    self.appsync.invoke_mutation(DEFAULT_STREAM_START_TOKEN)
    event_count = 0
    buffer = ""
    for event in stream:
        if event:
            if list(event)[0] == "contentBlockDelta":
                event_count += 1
                buffer += event["contentBlockDelta"]["delta"]["text"]
            if event_count > 5:
                self.appsync.invoke_mutation(buffer)
                event_count = 0
                buffer = ""
        if len(buffer) != 0:
            self.appsync.invoke_mutation(buffer)
```

当 LLM 针对收到的 prompt 生成 token 时，Lambda 会先使用 AWS AppSync mutation 操作向前端发送 `DEFAULT_STREAM_START_TOKEN`。这个 token 是一种通知前端开始渲染 token 的机制。当 Lambda 函数收到 `converse_stream` API 的分块时，它会调用 AWS AppSync mutation 操作，把部分 token 发送给前端渲染。

为了改善用户体验并降低网络开销，Lambda 函数不会对从 Amazon Bedrock `converse_stream` API 收到的每个分块都调用 AWS AppSync mutation 操作。相反，Lambda 代码会缓冲部分 token，在收到五个分块后才调用 AWS AppSync mutation 操作。这样避免了 AWS AppSync 网络调用的开销，从而降低延迟并改善用户体验。

在 Lambda 函数发送完 token 后，它会发送 `DEFAULT_STREAM_END_TOKEN`：

`self.appsync.invoke_mutation(DEFAULT_STREAM_END_TOKEN)`该 token 通知前端 LLM 流式传输已完成。

更多细节请参阅 [GitHub 仓库](https://github.com/aws-samples/bedrock-appsync-streaming/tree/main/bedrock-orchestrator-lambda)，其中包含名为 `bedrock-orchestrator-lambda` 的 Orchestrator Lambda 函数参考实现。

## 部署解决方案

按以下步骤部署该解决方案：

- 打开一个命令行终端窗口。
- 切换到 [deployment](https://github.com/aws-samples/sample-bedrock-appsync-streaming/tree/main/deployment) 文件夹。
- 编辑 [sample.tfvars](https://github.com/aws-samples/bedrock-appsync-streaming/blob/main/deployment/sample.tfvars) 文件，替换其中的变量值以匹配你的 AWS 环境。

```
region = "us-west-2"
lambda_s3_source_bucket_name = "YOUR_DEPLOYMENT_BUCKET"
lambda_s3_source_bucket_key  = "PREFIX_WITHIN_THE_BUCKET"
```

- 运行以下命令部署该解决方案：

```
$ terraform init
$ terraform apply -var-file=”sample.tfvars”
```

详细的部署步骤见随附 GitHub 仓库中[部署解决方案](https://github.com/aws-samples/bedrock-appsync-streaming/blob/main/README.md#deploy-the-solution)一节。

## 结论

本文演示了把 Amazon Bedrock 流式 API 与 AWS AppSync 订阅集成如何显著提升 AI 助手的响应速度和用户满意度。通过采用这种流式传输方式，该全球金融服务机构把复杂查询的初始响应时间缩短了约 75%——从 10 秒降到仅 2–3 秒——使用户能够在响应生成过程中就查看内容，而不必等待完整答案。业务收益十分明确：更低的放弃率、更高的用户参与度，以及更灵敏的 AI 体验。组织可以使用提供的 Lambda 和 Terraform 代码快速实施该解决方案，把这些改进迅速引入自己的环境。

如果需要更大的灵活性，[AWS AppSync Events](https://catalog.us-east-1.prod.workshops.aws/workshops/2fc0fd60-6cb8-48ba-b339-df6046826ced/en-US/003-appsync) 提供了另一种实现模式，可通过全托管的 WebSocket API 进一步增强实时能力。这种流式传输方式化解了全面 AI 响应与速度之间的根本矛盾，使组织能够在维持高质量交互的同时，提供现代用户所期待的灵敏体验。
