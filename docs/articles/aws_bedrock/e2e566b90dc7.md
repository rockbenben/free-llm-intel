# 在 Amazon ECS 上使用 Amazon Bedrock AgentCore Identity 保护 AI agent

生产环境中的 AI agent 需要安全地访问外部服务。Amazon Bedrock AgentCore Identity 可作为独立服务使用，它为 AI agent 访问外部服务的方式提供安全保障，无论这些 agent 运行在 [Amazon ECS](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html)、[Amazon EKS](https://docs.aws.amazon.com/eks/latest/userguide/what-is-eks.html)、[AWS Lambda](https://docs.aws.amazon.com/lambda/latest/dg/welcome.html) 这类计算平台上，还是运行在本地。

早前的一篇[文章](https://aws.amazon.com/blogs/security/securing-ai-agents-with-amazon-bedrock-agentcore-identity/)介绍了面向 AI agent 的 AgentCore Identity 凭据管理。在 ECS 这类计算环境中运行 agent 会引出两个问题：如何构建由应用自有的 Session Binding endpoint，以及如何管理工作负载访问 token 的生命周期？

本文在 Amazon ECS 上实现 Authorization Code Grant（三腿 OAuth），并配合安全的 session 绑定与范围化 token。本文给出的可运行实现包括：

- 防止 CSRF 与浏览器替换（browser-swapping）攻击的安全 session 绑定
- 按每个用户会话限定作用域的 auth token，遵循最小权限原则
- agent 工作负载与会话绑定服务之间的关注点分离

## 使用 OAuth 2.0 与 OIDC 做认证与授权

本方案使用 OAuth 2.0（[RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749)）与 OpenID Connect（OIDC）。OIDC 认证用户（他们是谁），OAuth 2.0 授权他们的操作（他们能做什么）。

我们聚焦于用于用户委派访问的 Authorization Code Grant。用户使用身份提供商完成认证并授予同意。应用随后用授权码换取访问 token，由此形成审计轨迹。在这一流程中，用户使用身份提供商完成认证，并授予同意让 agent 代表其访问特定资源。应用用得到的授权码换取范围化的访问 token，由 Amazon Bedrock AgentCore Identity 保存在其 token vault 中。由于每个 token 都绑定到具体的用户身份并带有明确同意，本方案在从用户认证到 agent 行为的整条链上保持了可审计性。

Authorization Code Grant 适合代表用户行动的 agent 工作负载，因为它在 agent 能够行动之前就取得用户同意，提供[会话绑定](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/oauth2-authorization-url-session-binding.html)（校验发起授权请求的用户与授予同意的用户是同一个人），以及范围化委派（把 agent 限制在用户批准的权限之内）。

## Callback URL 与 session binding URL

在这个语境下，Authorization Code Grant 流程会用到两个常被混淆的 URL：

- **Callback URL：** 在 [AgentCore Identity 中创建 OAuth client](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-oauth-client.html)时自动生成。它指向 AgentCore Identity，必须作为重定向目标注册到授权服务器，用户认证后授权码就发送到这里。
- **Session Binding URL：** 指向**客户自行管理的服务**的 URL，由该服务完成已认证用户与 OAuth 流程之间的[会话绑定](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/oauth2-authorization-url-session-binding.html)。这个 endpoint 由客户实现并托管。

## 方案概览

这张架构图展示了 AgentCore Identity 如何保护在 Amazon ECS 上自托管的 AI agent。本演练使用 Microsoft Entra ID 作为身份提供商，但也支持其他符合 OIDC 的提供商。本演练的完整源代码与前置条件见配套的 [GitHub 仓库](https://github.com/awslabs/agentcore-samples/tree/main/06-workshops/03-AgentCore-identity/07-Outbound_Auth_3LO_ECS_Fargate)。

本方案在 Application Load Balancer 之后的 Amazon ECS 上部署两个服务。Agentic Workload 运行 AI agent 并处理用户请求。Session Binding Service 处理 OAuth 回调，把用户会话与第三方访问 token 关联起来。两个服务都使用 Amazon Bedrock AgentCore Identity 通过 OIDC 认证入站用户，并代表用户授权出站操作。图中的编号标注对应下列说明。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/29/ML-20517-image-1.png)

- **入站认证与流量路由：** 请求到达 Amazon Application Load Balancer（ALB），由 ALB 内置的 OIDC 认证流程对用户进行认证。流量使用来自 AWS Certificate Manager 的证书以 HTTPS 加密，Amazon Route 53 公有托管区中的别名 A 记录把流量路由到负载均衡器。通过 OIDC 认证用户之后，ALB 把请求转发到 Amazon ECS 集群。ALB 注入一个 `x-amzn-oidc-data` header，其中以 JWT 格式包含用户的 claim，`sub` 字段唯一标识该用户。
- **Agent 工作负载：** Agentic Workload 暴露一个 FastAPI server，提供接受 sessionId 与 message 的 `/invocations` endpoint。FastAPI server 把它们传给用 [Strands Agents](https://strandsagents.com/) 构建的 agent。你也可以使用 LangChain 或其他 agent SDK，因为该 server 独立于 agent 框架处理请求。agent 调用 Amazon Bedrock 上的大语言模型（LLM），其他模型提供商同样可用。agent 把会话状态存放在 Amazon S3 存储桶中，并以用户的 sub claim 作为键前缀来隔离不同用户的会话。agent 还带有工具，可代表用户在 GitHub 上执行操作，这需要用户的 OAuth 访问 token。
- **使用 AgentCore Identity 做出站认证：** 当 agent 需要在 GitHub 这类第三方服务中代表用户行动时，它通过 AgentCore Identity 请求 OAuth 访问 token。若不存在有效 token，AgentCore Identity 会发起 Authorization Code Grant 流程，提示用户授权访问。
- **OAuth 回调处理：** 用户授权访问后，Session Binding Service 通过 AgentCore Identity 把该授权绑定到正确的用户会话，从而完成 OAuth 流程。
- **用户界面：** 承载 agent 工作负载的 FastAPI server 暴露 `/docs` endpoint，把 OpenAPI 规范渲染为可交互的 HTML 页面。最终用户通过该页面与 agent 交互，它提供了一个用于演示的最小 UI

Amazon CloudWatch 捕获日志，一个专用 S3 存储桶存放负载均衡器与数据桶双方的访问日志。ECS 从 Amazon ECR 拉取容器镜像。一组基础 AWS WAF 规则挂载在负载均衡器上，为常见 Web 攻击提供基线防护。Amazon KMS 客户管理密钥（CMK）加密数据，但访问日志桶除外——它需要使用 Amazon S3 托管加密（SSE-S3）。

## Amazon Bedrock AgentCore Identity：Authorization Code Grant

本演练把[通用的 AgentCore Identity 会话绑定流程](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/oauth2-authorization-url-session-binding.html)适配到自托管架构：用 ALB 做认证、使用专用的 Session Binding Service，并直接调用 API 而不是使用 AgentCore SDK 与 Runtime。

该时序图展示了 [AgentCore Identity 的工作负载身份](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/understanding-agent-identities.html)、[工作负载访问 token](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/get-workload-access-token.html) 与 [OAuth 2.0 凭据提供商](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/resource-providers.html) 如何协同工作，代表用户安全地把 OAuth token 提供给 agent。该流程假定已认证用户尚未授权 agent 访问其资源，也就是说 [AgentCore Identity Token Vault](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/key-features-and-benefits.html#secure-credential-storage) 中不存在有效 token。

## ![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/29/ML-20517-image-2.png)

- 已认证用户向 agent 工作负载发送请求。agent 工作负载从 ALB 签名的 JWT（`x-amzn-oidc-data` header）中的 sub claim 提取用户 ID，以识别该用户。
- agent 工作负载调用 [GetWorkloadAccessTokenForUserId](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_GetWorkloadAccessTokenForUserId.html) API，传入 `userId` 与 `workloadName`，以获得代表该 agent 身份、且作用域限定到该用户的 workload access token。
- AgentCore Identity 把 workload access token 返回给 agent 工作负载。
- agent 工作负载调用 [GetResourceOauth2Token](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_GetResourceOauth2Token.html) API，传入 workload access token、已配置 OAuth 2.0 凭据提供商的 provider 名称、session binding URL（参见 [callbackUrl 参数](https://aws.github.io/bedrock-agentcore-starter-toolkit/api-reference/identity.html)）以及所需的 scope，例如 GitHub 的 `read:user` scope。这会为该第三方服务（此例为 GitHub）请求一个 OAuth token。
- 由于该用户不存在有效 token，AgentCore Identity [创建一个 sessionURI](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/oauth2-authorization-url-session-binding.html#:~:text=Invoke%20agent%20%E2%80%93%20Your%20agent%20code,user%20of%20the%20authorization%20request.) 来跟踪 OAuth 2.0 认证过程中后续请求与响应之间的授权流程状态。
- AgentCore Identity 向工作负载返回授权 URL 与 session URI
- agent 工作负载把授权 URL 返回给用户，提示其授权访问。
- 用户点击授权 URL，并在第三方提供商的同意页面上授予 agent 权限。
- 授权服务器把授权码发送给 AgentCore Identity。
- AgentCore Identity 把用户重定向到附加了 session URI 的 Session Binding URL，将其路由到 Session Binding Service。
- 用户的浏览器沿该重定向通过 Session Binding URL 访问 Session Binding Service。ALB 在 `x-amzn-oidc-data` header 中注入 JWT。
- Session Binding Service 用 session URI 与用户 ID（从 JWT 中提取）调用 [CompleteResourceTokenAuth](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_CompleteResourceTokenAuth.html) API，把已完成的授权绑定到正确的用户会话。成功后，它返回一个由应用自有的静态 HTML 页面，确认授权成功。
- AgentCore Identity 与授权服务器交换授权码，换取 OAuth2 访问 token。
- 授权服务器返回 OAuth2 访问 token。
- AgentCore Identity 把 token 保存在 Token Vault 中。
- AgentCore Identity 向 Session Binding Service 返回成功。
- Session Binding Service 向用户显示“Authorization complete”。

在后续请求中，用户是否需要重新授权取决于授权服务器签发的凭据。AgentCore Identity 会把访问 token 与刷新 token（若可用）都存放在 Token Vault 中。存在刷新 token 时——例如启用了 User-to-server token expiration 的 GitHub——AgentCore Identity 会在原 token 过期后自动用它获取新的访问 token，无需再次提示用户。如果未签发刷新 token 而访问 token 过期，用户会被提示重新授权。注意 token 也可能在提供商侧被撤销；这种情况下，设置 forceAuthentication: true 会强制走一次全新的认证流程。

**会话绑定：**

会话绑定可防御两类安全威胁：

**跨站请求伪造（CSRF）：** 攻击者试图把自己的 OAuth token 绑定到受害者的身份上，使受害者的 agent 在不知情的情况下访问攻击者的资源，从而实现数据外泄与数据注入。

**浏览器替换攻击（Browser Swapping Attack）：** 攻击者诱使受害者代表其授予同意，把受害者的 OAuth token 绑定到攻击者的身份上，使攻击者可以直接访问受害者的资源。

会话绑定通过确保 agent 工作负载处的用户 ID 与 Session Binding Service 处的用户 ID 一致来防止这两种攻击，两个身份都通过认证链做了加密验证。

AgentCore Identity 还支持在 [GetResourceOauth2Token](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_GetResourceOauth2Token.html) API 中使用可选的 customState 参数，按 OAuth 2.0 规范的建议，可用于传入加密随机的 nonce，以保护你的 callback endpoint 免受 CSRF 攻击。

### 为什么在 AWS ALB 与 Microsoft Entra ID 场景下使用 GetWorkloadAccessTokenForUserId

获取 workload access token 的推荐 API 是 [GetWorkloadAccessTokenForJWT](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_GetWorkloadAccessTokenForJWT.html)。本方案改用 [GetWorkloadAccessTokenForUserId](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_GetWorkloadAccessTokenForUserId.html)。

[GetWorkloadAccessTokenForJWT](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_GetWorkloadAccessTokenForJWT.html) 要求 JWT 可动态校验：其签名能在运行时对照签发方公布的签名密钥验证，且 aud claim 匹配你的应用。要从 Microsoft Entra ID 获得这样的 token，你必须在 OIDC 授权请求的 scope 中包含你的 Application ID，详见 [AgentCore Microsoft 入站文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-idp-microsoft.html#identity-idp-microsoft-inbound)。

***然而，这与 AWS ALB 的 OIDC 流程不兼容。***

在其 OIDC 握手过程中（参见 [ALB OIDC 文档](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/listener-authenticate-users.html#authentication-flow)），ALB 会把访问 token 发送到 Entra 的 UserInfo endpoint，以获取已认证用户的 claim，这是 ALB 认证流程中的必经步骤。该 UserInfo endpoint 托管在 Microsoft Graph（[https://graph.microsoft.com/oidc/userinfo](https://graph.microsoft.com/oidc/userinfo)）上，只接受作用域为 Microsoft Graph 的 token。当你在 scope 中包含 Application ID 时，得到的访问 token 以你的应用为受众，UserInfo endpoint 会以 401 拒绝它，ALB 则返回 561。

如果你从 scope 中移除 Application ID，Entra 会把访问 token 的受众默认为 Microsoft Graph（`00000003-0000-0000-c000-000000000000`）。ALB 握手成功，但得到的 JWT 无法被 AgentCore 动态校验，因此不能用于 [GetWorkloadAccessTokenForJWT](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_GetWorkloadAccessTokenForJWT.html)。

本方案的做法：ALB 使用 Graph 作用域的 token 完成握手。ALB 在 `x-amzn-oidc-data` header 中转发一个 ALB 签名的 JWT，其中包含来自 UserInfo endpoint 的用户 claim，含一个唯一标识已认证用户的 sub claim。我们用 AWS 公布的签名密钥校验这个 ALB 签名的 JWT，提取 `sub`，并把它传给 [GetWorkloadAccessTokenForUserId](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_GetWorkloadAccessTokenForUserId.html)。

### 获取 Workload Access Token

server 从 JWT 的 sub claim 提取用户 ID，并向 AgentCore Identity 请求 workload access token。随后 server 用该 token、session ID 与 message 代表用户调用 agent。注意这里的 session ID 指 agent 的对话会话，而不是授权流程中的 OAuth session URI。

```
@router.post("/invocations")
async def invoke_agent(
    request: InvocationRequest,
    user_id: str = Depends(get_current_user),
    settings: Settings = Depends(get_settings),
    agent_service: AgentService = Depends(get_agent_service),
) -> StreamingResponse:
    """Invoke agent with streaming response."""
    try:
        agentcore = boto3.client("bedrock-agentcore", region_name=settings.identity_aws_region)
        response = agentcore.get_workload_access_token_for_user_id(
            workloadName=settings.workload_identity_name, userId=user_id
        )
        workload_access_token = response["workloadAccessToken"]        
return StreamingResponse(
            content=agent_service.stream_response(
                user_message=request.user_message,
                session_id=request.session_id,
                user_id=user_id,
                workload_access_token=workload_access_token,
            ),
            media_type="text/event-stream",
        )
```

### 请求访问 token

server 使用 [AgentCore SDK](https://github.com/aws/bedrock-agentcore-sdk-python/blob/main/src/bedrock_agentcore/identity/auth.py#L22-L34) 中的 `require_access_token` 装饰器获取 OAuth 2.0 访问 token，参见[获取 OAuth 2.0 访问 token](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-authentication.html)。我们修改了该装饰器，使其把 workload access token 作为显式参数接收，而不是在内部解析，从而可直接控制 token 生命周期管理，同时保留 SDK 的 token 获取与错误处理逻辑

```
def requires_access_token(
    *,
    provider_name: str,
    scopes: list[str],
    auth_flow: Literal["M2M", "USER_FEDERATION"],
    workload_access_token: str | None = None,
    session_binding_url: str | None = None,
    on_auth_url: Callable[[str], Any] | None = None,
    force_authentication: bool = False,
    token_poller: TokenPoller | None = None,
    custom_state: str | None = None,
    custom_parameters: dict[str, str] | None = None,
    into: str = "access_token",
    region: str | None = None,
) -> Callable[[Callable[..., Any]], Callable[..., Any]]:
    """Fetch OAuth2 access token with explicit workload token.

    Args:
        provider_name: The credential provider name
        scopes: OAuth2 scopes to request
        auth_flow: Authentication flow type ("M2M" or "USER_FEDERATION")
        workload_access_token: The workload access token (explicit, not from context)
        session_binding_url: Session Binding URL pointing to the customer-managed service that completes the session binding
        on_auth_url: Handler invoked with the authorization URL when user authorization is required
        force_authentication: Force re-authentication
        token_poller: Custom token poller implementation
        custom_state: State for callback verification
        custom_parameters: Additional OAuth parameters
        into: Parameter name to inject the token into
        region: AWS region

    Returns:
        Decorator function

    """

def decorator(func: Callable[..., Any]) -> Callable[..., Any]:
    client = IdentityClient(region)

    @wraps(func)
    async def wrapper(*args: Any, **kwargs: Any) -> Any:
        try:
            if not workload_access_token:
                raise ValueError("workload_access_token is required")
            token = await client.get_token(
                provider_name=provider_name,
                agent_identity_token=workload_access_token,
                scopes=scopes,
                auth_flow=auth_flow,
                callback_url=session_binding_url,
                on_auth_url=on_auth_url,
                force_authentication=force_authentication,
                token_poller=token_poller,
                custom_state=custom_state,
                custom_parameters=custom_parameters,
            )
            kwargs[into] = token
            return await func(*args, **kwargs)
        except Exception:
            logger.exception("Error in requires_access_token decorator")
            raise

    return wrapper

return decorator
```

我们的工具类使用该装饰器，在调用 GitHub API 时提供访问 token。

```
class GitHubTools:
    """Tools for interacting with GitHub using OAuth authentication."""

def _on_auth_url(self, url: str) -> None:
    """Handle authorization URL by raising AuthorizationRequiredError.

    This URL must be presented to the user to grant access.
    """
    raise AuthorizationRequiredError(provider="GitHub", auth_url=url)

async def _call_github_api(
    self, endpoint: str, scopes: list[str], params: dict | None = None
) -> Any:
    """Make authenticated GitHub API call.

    Raises:
        ApiError: When API call fails

    """

    @requires_access_token(
        provider_name=self.config.provider_name,
        scopes=scopes,
        auth_flow="USER_FEDERATION",
        workload_access_token=self.config.workload_access_token,
        session_binding_url=self.config.session_binding_url,
        on_auth_url=self._on_auth_url,
        region=self.config.aws_region,
    )
    async def make_request(*, access_token: str) -> Any:
        async with httpx.AsyncClient() as client:
            response = await client.get(
                f"{self.config.github_api_base}{endpoint}",
                headers={
                    "Authorization": f"Bearer {access_token}",
                    "Accept": "application/vnd.github+json",
                    "X-GitHub-Api-Version": "2022-11-28",
                },
                params=params or {},
                timeout=10.0,
            )
            response.raise_for_status()
            return response.json()

    try:
        return await make_request()
```

该类中的每个工具都使用这个方法，如下所示：

```
from strands import tool
class GitHubTools:
    @tool
    async def get_github_user(self) -> GitHubUser:
        """Get the authenticated GitHub user's profile information.
 
        Use this tool when the user wants to:
        - See their GitHub profile
        - Check who they are authenticated as
        - View their GitHub account details
        Returns:
            GitHub user profile
        Raises:
            ApiError: When API call fails
        """
        result: dict[str, Any] = await self._call_github_api(
            "/user", scopes=["read:user"]
        )
        return GitHubUser.model_validate(result)
```

三个关键设计选择：

- **用 [Pydantic BaseModel](https://pydantic.dev/docs/validation/latest/api/pydantic/base_model/) 作为返回类型：** GitHubUser 与 GitHubProject 都是 `BaseModel` 的子类。Strands 会自动从它们的 schema 与 docstring 推导工具描述，为 LLM 提供关于每个工具返回类型的结构化上下文。
- **类型一致的错误处理：** 当不存在 token 且 AgentCore Identity 返回授权 URL 时，`on_auth_url` 回调会抛出 `AuthorizationRequiredError` 而不是返回字符串——一个声明以 GitHubUser 为返回类型的工具不可能返回 URL。agent 的流式层会捕获该异常，并把 URL 呈现给用户。
- **按工具限定 scope：** 每个工具只声明它需要的 OAuth scope，使同意范围与最小权限原则保持一致。

### 完成 OAuth 会话绑定流程

接下来我们看会话绑定服务。当用户在 GitHub 中授权访问后，GitHub 会把其重定向到 `{session_binding_url}?session_id={session_id}`，其中 `session_id` 对应 AgentCore Identity 在原始授权 URL 中包含的 session URI。这就把会话绑定请求与 agent 发起的那个具体 OAuth 流程关联起来。

```
@router.get("/session-binding", response_class=HTMLResponse)
async def oauth_session_binding(
    session_id: str = Query(..., description="Session URI from AgentCore Identity"),
    user_id: str = Depends(get_current_user),
    settings: Settings = Depends(get_settings),
) -> HTMLResponse:
    """Handle OAuth2 session binding from external providers.""" 
    client = boto3.client("bedrock-agentcore", region_name=settings.identity_region)
 
    try:
        client.complete_resource_token_auth(
            sessionUri=session_id,
            userIdentifier={"userId": user_id},
        )
```

该服务从 `x-amzn-oidc-data` header 的 sub claim 中提取用户 ID，确保整个流程中的身份一致。随后它用 session URI 与用户 ID 调用 [complete_resource_token_auth](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_CompleteResourceTokenAuth.html)，把得到的访问 token 绑定到正确的用户会话。
