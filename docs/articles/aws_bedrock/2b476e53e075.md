# 用 Amazon Nova Multimodal Embeddings 驱动视频语义搜索

视频语义搜索正在为各行各业释放新的价值。以视频为先的体验需求正在重塑组织交付内容的方式，客户期待能够快速、准确地访问视频中的特定瞬间。例如，体育转播机构需要找出球员得分的准确瞬间，以便立刻为球迷提供精彩片段。影视制作公司需要在数千小时的存档内容中找出包含特定演员的每一个场景，用于制作个性化预告片和宣传素材。新闻机构需要按情绪、地点或事件检索素材，以比竞争对手更快地发布突发报道。目标始终一致：把视频内容迅速交付到终端用户手中，抓住那个瞬间，并让这种体验产生收益。

视频天然比文本或图像等其他模态更复杂，因为它融合了多种非结构化信号：屏幕上展开的视觉场景、环境音频与音效、对话语音、时间信息，以及描述该素材的结构化元数据。用户搜索“有警笛声的紧张追车戏”时，同时问的是一个视觉事件和一个音频事件。用户按姓名搜索某位运动员时，可能想找的是那个在画面上很显眼、却从未被念出名字的人。

当前的主流做法是把所有视频信号都归一到文本——无论是通过转录、人工标注还是自动生成字幕——然后再用文本 embedding 做搜索。这对对话密集的内容有效，但把视频转成文本不可避免会丢失关键信息。时间层面的理解消失了，视觉和音频质量问题还会带来转录错误。如果你有一个模型能处理所有模态，并直接把它们映射进一个可搜索的表示而不丢失细节，会怎样？Amazon Nova Multimodal Embeddings 就是一个统一的 embedding 模型，它原生地把文本、文档、图像、视频和音频处理进一个共享的语义向量空间，并提供领先的检索准确率与成本效率。

在本文中，我们展示如何在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上使用 Nova Multimodal Embeddings 构建视频语义搜索方案：它能智能理解用户意图，并同时跨所有信号类型检索出准确的视频结果。我们还分享了一个参考实现，你可以部署它并用你自己的内容进行探索。

## **方案概览**

我们的方案建立在 Nova Multimodal Embeddings 之上，结合一套智能的混合搜索架构，在所有视频模态上融合语义信号与词法信号。词法搜索匹配精确的关键词和短语，语义搜索则理解含义与上下文。我们将在后面的章节中解释为何选择这种混合方法，以及它的性能收益。

图 2：端到端方案架构

该架构由两个阶段组成：一个是摄取 pipeline（步骤 1-6），把视频处理成可搜索的 embedding；另一个是搜索 pipeline（步骤 7-10），把用户查询智能地路由到这些表示之上，并把结果合并成排序列表。下面逐步说明细节：

- **上传**——通过浏览器上传的视频存储在 Amazon Simple Storage Service（Amazon S3）中，触发 Orchestrator [AWS Lambda](https://aws.amazon.com/lambda/) 更新 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 状态并启动 [AWS Step Functions](https://aws.amazon.com/step-functions/) pipeline
- **镜头切分**——[AWS Fargate](https://aws.amazon.com/fargate/) 使用 [FFmpeg](https://ffmpeg.org/) 场景检测，把视频切分成语义连贯的分段
- **并行处理**——三个并发分支处理每个分段：**Embeddings：**Nova Multimodal Embeddings 为视觉和音频生成 1024 维向量，存放在 Amazon S3 Vectors 中。**转录：**[Amazon Transcribe](https://aws.amazon.com/transcribe/) 把语音转成文本，并按分段对齐。Amazon Nova Multimodal Embeddings 生成文本 embedding，存放在 Amazon S3 Vectors 中。**名人识别：**[Amazon Rekognition](https://aws.amazon.com/rekognition/) 识别已知人物，并按时间戳映射到分段
- **字幕与类型生成**——[Amazon Nova 2 Lite](https://aws.amazon.com/nova/models/) 依据视觉内容和转录文本，合成分段级字幕与类型标签
- **合并**——AWS Lambda 汇总所有元数据（字幕、转录、名人、类型），并从 [Amazon S3 Vectors](https://aws.amazon.com/s3/features/vectors/) 取回 embedding
- **索引**——带有元数据和向量的完整分段文档被批量索引进 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/)
- **身份验证**——用户通过 [Amazon Cognito](https://aws.amazon.com/cognito/) 认证，并通过 [Amazon CloudFront](https://aws.amazon.com/cloudfront/) 访问前端
- **查询处理**——[Amazon API Gateway](https://aws.amazon.com/api-gateway/) 把请求路由到 Search Lambda，后者并行执行两项操作：意图分析和查询 embedding
- **意图分析**——[Amazon Bedrock](https://aws.amazon.com/bedrock/)（使用 [Anthropic Claude Haiku](https://aws.amazon.com/bedrock/anthropic/)）为视觉、音频、转录和元数据模态分配相关性权重（0.0-1.0）
- **查询 embedding**——Nova Multimodal Embeddings 对查询做三次 embedding，分别用于视觉、音频和转录相似度搜索

这套灵活的架构回应了多数视频搜索系统会忽视的四个关键设计决策：保持时间上下文、处理多模态查询、在超大内容库上扩展，以及优化检索准确率。完整参考实现已在 [GitHub 上](https://github.com/aws-samples/sample-video-semantic-search-multimodal-embeddings/tree/main/video-semantic-search-w-nove-mme) 提供，我们建议你跟着下面的讲解走一遍，看看每个决策如何共同促成了跨所有信号类型的准确、可扩展搜索。

## **为上下文连续性做分段**

在生成任何 embedding 之前，你需要先把视频划分成可搜索的单元，而你画下的边界会直接影响搜索准确率。每个分段都是检索的原子单元。分段太短，就会失去赋予某个瞬间含义的周边上下文。分段太长，就会把多个主题或场景融合在一起，稀释相关性，让搜索系统更难找出正确的瞬间。为简单起见，你可以从固定长度的分块开始。Nova Multimodal Embeddings 每次 embedding 最多支持 30 秒，让你能灵活捕获完整场景。但要注意，固定边界可能武断地在动作中途截断一个场景，或在思路中途切断一个句子，破坏让某个瞬间可被检索的语义含义，如下图所示。

图 3：视频分段策略

目标在于语义连续性：每个分段都应代表一个连贯的意义单元，而不是任意一段时间的切片。固定 10 秒的块很容易产出，但它们忽略了内容的自然结构。分段中途的场景切换会把一个视觉概念拆到两个块里，同时降低检索精度与 embedding 质量。

为解决这个问题，我们使用 [FFmpeg](https://www.ffmpeg.org/) 的场景检测来识别视觉内容实际发生变化的位置。FFmpeg 是一个开源多媒体框架，广泛用于视频处理、格式转换和分析。下面的 `_detect_scenes` 函数对视频运行 `ffprobe`（FFmpeg 配套的媒体检视工具），并返回一组时间戳，每个都标记一个场景边界：

```
def _detect_scenes(video_path):
    result = subprocess.run(
        ['ffprobe', '-v', 'quiet', '-show_entries', 'frame=pts_time', '-of', 'csv=p=0',
         '-f', 'lavfi', f"movie={video_path},select='gt(scene\\,{SCENE_THRESHOLD})'"],
        capture_output=True, text=True
    )
```

输出就是一个简单的时间戳列表，例如 12.345、28.901、45.678，每个都标记了场景切换处的自然边界。

拿到这些边界后，分段算法会把每个切点吸附到可接受窗口内最近的场景变化处，目标约 10 秒，距当前起点最少 5 秒、最多 15 秒。如果该范围内没有场景变化，它就回退到在目标时长处硬切。结果是一组感觉自然的分段：8.3s、11.1s、9.8s、12.4s、7.6s，每个都对齐到真实的场景边界，而不是固定的计时器。

这种简单的基于镜头的分段能确保分段边界对齐自然的视觉转换，而不是任意切割。目标分段时长应根据你的内容类型和使用场景来校准：剪辑频繁、动作密集的内容可能受益于这种视觉分段，而长镜头较多的纪录片或访谈内容可能更适合更长、基于主题的分段。关于更进阶的分段技术，包括基于音频的主题分段以及视听结合的方法，我们建议阅读 [Media2Cloud on AWS Guidance: Scene and Ad-Break Detection and Contextual Understanding for Advertising Using Generative AI.](https://aws.amazon.com/blogs/media/media2cloud-on-aws-guidance-scene-and-ad-break-detection-and-contextual-understanding-for-advertising-using-generative-ai/)

## **为视觉、音频和转录信号分别生成 embedding**

分段确定之后，embedding 模型的选择正是不同方法之间质量差距最大的地方。当前的主流做法是在生成 embedding 之前把所有视频信号归一到文本，但正如我们前面所说，视频承载的含义远超任何转录或字幕所能表达。视觉动作、环境声音、屏幕文字和实体上下文，要么完全丢失，要么只能通过不精确的描述来近似。

Nova Multimodal Embeddings 从根本上改变了这一点，因为它是视频原生模型，能以两种模式生成 embedding。组合模式把视觉与音频信号融合成一个统一表示，把最重要的信号一并捕获。这种做法每个分段只需要一个 embedding，有利于存储成本和检索延迟。另一种 `AUDIO_VIDEO_SEPARATE` 模式则生成彼此独立的视觉 embedding 和音频 embedding。这种做法在模态专属的 embedding 中提供最大化的表示，并让你更好地控制何时搜索视觉内容、何时搜索音频内容。

在我们的实现中，我们还加入了第三个由 Amazon Transcribe 得到的语音 embedding。这个 embedding 是把完整句子的转录对齐到分段的时间戳（向前和向后都算）而生成的，既保住了口语的语义完整性，也确保一个完整的思想绝不会被拆到两个 embedding 里。

图 4：每个视频分段的视觉、音频和语音 embedding 生成

这三个 embedding 合起来覆盖了视频分段的完整信号空间。视觉 embedding 捕获摄像机看到的东西：物体、场景、动作、颜色和空间构图。音频 embedding 捕获麦克风听到的东西：音乐、音效、环境噪声和场景的声学质感。转录 embedding 捕获人们说的话，表示对话和旁白的语义含义。把三种信号压进一个组合 embedding，就是把不同的模态挤压进一个向量。这会模糊所见、所听与所说之间的边界，并丢失让每种信号各自有价值的细粒度细节。让它们保持独立，你就能根据查询意图精确地把每个模态调高或调低，让搜索 pipeline 去匹配最可能包含答案的那个模态。

## **结合元数据与 embedding 实现混合搜索**

即使有三个独立的 embedding 覆盖视觉、音频和口语内容，仍有一类查询是系统答不好的。embedding 的设计目标是捕获语义相似度。它们擅长找到“紧张的人群时刻”或“水上的日落”，因为这些概念具有丰富的视觉和音频含义。但当用户搜索某个具体姓名、产品型号、地理位置或某个特定日期时，embedding 很可能失败。这些是离散实体，本身几乎没有语义信号。这正是混合搜索的用武之地。系统不只依赖 embedding，而是运行两条并行的检索路径，如下图所示：一条语义路径，针对你的视觉、音频和转录 embedding 做匹配，以捕获概念相似度；一条词法路径，针对结构化元数据执行精确的关键词和实体匹配。

图 5：结合语义检索与词法检索的混合搜索 pipeline

你需要多少元数据？答案取决于你的内容类型、组织和使用场景，而预先捕获所有内容并不现实。为便于说明，我们挑选了几类元数据，用来代表媒体与娱乐内容中常见的元数据类型。

首先，我们选择视频标题和日期时间，用来代表直接从内容目录或文件元数据中提取的技术元数据。接着我们加入分段字幕、类型和名人识别，用来代表上下文元数据，这些由 Amazon Nova 2 Lite 和 Amazon Rekognition 生成。字幕由每个分段的视频和转录生成，让模型同时获得视觉和口语上下文。类型则根据所有分段的完整视频转录预测，这比把每个视频片段都重新发一遍更便宜也更可靠。名人识别由 Amazon Rekognition 处理，它能识别出现在画面中的知名公众人物，无需自定义训练。

用于字幕生成和类型分类的示例 prompt 如下所示：

```
# Caption generation
Describe this video clip in 3-5 sentences. Include:
- What is happening, who is visible, actions, setting, and environment
- Any text on screen: titles, subtitles, signs, logos, watermarks, or credits
- If the screen is mostly black or blank, state "Black frame" or "Blank screen"
Transcription: {segment_transcript}
Return ONLY the descriptive caption, nothing else.

# Genre classification
Based on all the video segments described below, classify the overall video
into exactly ONE genre from this list: Sports, News, Entertainment,
Documentary, Education, Music, Gaming, Cooking, Travel, Technology,
Business, Lifestyle, Sci-Fi, Mystery, Other

Segment descriptions:
{all_captions}

Return ONLY the genre name, nothing else.
```

这一思路可以自然地扩展到其他元数据类型。技术元数据可能包括分辨率或文件大小，而上下文元数据可能包括地点、情绪或品牌。合适的平衡取决于你的搜索使用场景。此外，在检索时叠加元数据过滤，可以在语义匹配之前缩小搜索空间，进一步提升搜索的可扩展性与准确率。

## **用意图感知的查询路由优化搜索相关性**

现在你有了三个 embedding 和元数据，也就是四个可搜索的维度。但你怎么知道针对某个查询该用哪一个？意图就是一切。为此，我们构建了一个智能的意图分析路由器，用 Haiku 模型分析每个传入的查询，并为每个模态通道分配权重：视觉、音频、转录和元数据。示例搜索查询见下图。

*“Kevin 在一辆老爷车旁接电话”*

图 6：按搜索意图智能分配权重的示例查询

Haiku 模型被要求返回一个 JSON 对象，其中各权重之和为 1.0，并附上一段简短的推理说明来解释这次分配。prompt 如下：

```
Analyze this video search query and assign weights (0.0–1.0) for four modalities.
Weights must sum to 1.0.

Return ONLY valid JSON in this exact format:
{"visual": 0.0, "audio": 0.0, "transcription": 0.0, "metadata": 0.0, "reasoning": "..."}

Guidelines:
- visual: appearance, colors, objects, actions, scenes
- audio: sounds, music, noise, non-speech audio
- transcription: spoken words, dialogue, narration
- metadata: person names, genre, captions, factual attributes

Examples:
- "red car driving"      → visual=0.9, metadata=0.1
- "person saying hello"  → transcription=0.5, visual=0.2, audio=0.2, metadata=0.1
- "dog barking loudly"   → audio=0.6, visual=0.3, metadata=0.1
```

权重直接决定哪些子查询会被执行。任何低于 5% 权重阈值的模态都会被完全跳过，从而消除不必要的 embedding API 调用，在不牺牲准确率的前提下降低搜索延迟。其余通道并行执行，各自独立搜索自己的索引。随后，所有活跃通道的结果用加权算术平均来打分。[BM25 分数](https://en.wikipedia.org/wiki/Okapi_BM25)（一种基于词频和文档长度的词法相关性度量）和 [余弦相似度分数](https://en.wikipedia.org/wiki/Cosine_similarity)（一种衡量两个 embedding 向量指向同一方向的接近程度的几何度量）处在非常不同的量级上。为此，每个子查询的分数会先归一化到 0-1 区间，再用路由器的意图权重组合：

```
final_score = w₁ × norm_bm25 + w₂ × norm_visual + w₃ × norm_audio + w₄ × norm_transcription
```

我们选择加权算术平均作为重排序技术，因为它通过路由器的权重直接融入了查询意图。与 [Reciprocal Rank Fusion（RRF）](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion) 不同——后者不管意图如何都平等对待所有活跃通道——加权平均会放大路由器认为对当前查询最相关的那些通道。从我们的测试来看，这为我们的搜索任务带来了更准确的结果。

## **为向量与元数据选择合适的存储策略**

最后一个设计决策是把这一切存在哪里、怎么存。每个视频分段最多产生三个 embedding 和一组元数据字段，而如何存储它们既决定你的搜索性能，也决定规模放大后的成本。我们把它拆到两个角色互补的服务上：Amazon S3 Vectors 负责向量存储，Amazon OpenSearch Service 负责混合搜索。

**S3 Vectors** 为每个项目存储三个向量索引，每种 embedding 类型一个：

- `nova-visual-{project_id}` # 视觉 embedding
- `nova-audio-{project_id}` # 音频 embedding
- `nova-transcription-{project_id}` # 转录 embedding

**OpenSearch** 为每个项目持有一个索引，其中每个文档代表单个视频分段，同时包含用于 BM25 搜索的文本字段和用于 k 近邻（kNN）搜索的向量字段：

```
{
  "_id": "f953ceba_seg_0012",
  "start_sec": 118.45,
  "end_sec":   128.72,
  "caption":   "A presenter walks through a rice paddy in rural Jakarta, discussing how rice cultivation has shaped local civilization for thousands of years.",
  "people":    ["presenter_name"],
  "genre":     "Documentary",
  "visual_vector":        [0.023, -0.118, 0.045, ...],
  "audio_vector":         [0.045,  0.091, -0.033, ...],
  "transcription_vector": [-0.067, 0.134,  0.012, ...]
}
```

我们选择 S3 Vectors 是看中它的性价比。与替代的专用方案相比，Amazon S3 Vectors 把存储和查询向量的成本降低最多 90%。如果搜索延迟对你的使用场景不关键，S3 Vectors 是一个很好的默认选择。如果你需要尽可能低的延迟，我们建议使用 OpenSearch 的 Hierarchical Navigable Small World（HNSW）引擎，把向量放在内存里。

最后值得指出的是，有些使用场景需要在更长、语义更密集的视频分段内部搜索，例如完整访谈、长达数分钟的纪录片场景，或冗长的产品演示。包括 Nova Multimodal Embeddings 在内的大多数多模态 embedding 模型，最大输入时长都是 30 秒，这意味着一个 3 分钟的片段无法作为单个单元来 embedding。硬要这么做，要么失败，要么被迫分块从而丢失更广的上下文。

OpenSearch 的嵌套向量支持解决了这个问题：它允许单个文档包含多个子分段 embedding：

```
{
  "_id": "f953ceba_scene_003",
  "start_sec": 118.45,
  "end_sec":   298.10,
  "sub_segments": [
    { "start_sec": 118.45, "end_sec": 128.72, "visual_vector": [...] },
    { "start_sec": 128.72, "end_sec": 139.10, "visual_vector": [...] },
    { "start_sec": 139.10, "end_sec": 150.30, "visual_vector": [...] }
  ]
}
```

查询时，OpenSearch 依据最佳匹配的子分段来给文档打分，而不是用一个平均后的表示，因此一个长场景可以在自身内部匹配到某个具体的视觉瞬间，同时仍作为一个连贯的结果返回。

## **性能结果：优化后的方法如何超越基线**

为验证我们的设计决策，我们用 10 个内部长视频（5-20 分钟）、跨 20 个查询（涵盖以视觉、音频、转录和元数据为重点的搜索）把优化后的混合搜索与 Nova Multimodal Embeddings 基线 `AUDIO_VIDEO_COMBINED` 模式做了基准测试。基线对每个 10 秒分段使用单个统一向量，只有一个索引、一次 kNN 查询。我们优化后的方法生成彼此独立的视觉、音频和转录 embedding，用结构化元数据丰富分段，并应用意图感知路由动态加权各模态通道。下图展示了四项标准检索指标上的结果：

图 7：混合搜索（使用 Nova MME）与基线在各项检索指标上的性能对比

下表汇总了关键指标：

|  | **Recall@5** | **Recall@10** | **MRR** | **NDCG@10** |
| --- | --- | --- | --- | --- |
| 使用 Nova Multimodal Embeddings 的混合搜索 | 90% | 95% | 90% | 88% |
| 基线 | 51% | 64% | 48% | 54% |

**关键指标说明：**

- **Recall@5**：在所有相关分段中，有多大比例出现在前 5 条结果里？这衡量搜索结果的覆盖度。
- **Recall@10**：在所有相关分段中，有多大比例出现在前 10 条结果里？这衡量搜索结果的覆盖度。
- **MRR（Mean Reciprocal Rank）**：第一个相关结果的名次取倒数，再对所有查询求平均。它衡量你多快能找到相关的内容。
- **NDCG@10**：Normalized Discounted Cumulative Gain 会奖励排名更高的相关结果，并惩罚排名更低的结果。这是一个标准的排序质量指标。

结果显示出各项指标的大幅提升。优化后的混合搜索达到 90%+ 的 Recall@5 和 Recall@10，而基线为 51% 和 64%（覆盖率准确率提升约 40%）。MRR 从 48% 跃升到 90%，NDCG@10 从 54% 升到 88%。这 30-40 个百分点的增益验证了我们的核心架构决策：语义分段保持内容连续性，独立 embedding 提供精确的搜索控制，元数据丰富捕获事实性实体，意图感知路由确保正确的信号驱动每个查询。通过独立对待每个模态、同时又根据查询意图智能地组合它们，系统能适应多样的搜索模式，并在你的视频档案扩张时持续交付相关的结果。
