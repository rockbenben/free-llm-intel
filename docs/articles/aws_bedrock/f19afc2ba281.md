AI 编码智能体已经成为开发者编写、调试和重构软件方式的核心部分。Amazon Bedrock 上的开放权重模型如今让这些智能体可以在私密、经济的前提下运行。但多数选项要求你把专有数据发给一个第三方 API、把你锁定到一个单一模型提供方，或无论你用多少都按席位收费。如果你有数据驻留要求、成本敏感的工作负载，或对模型灵活性的需要，这些约束会造成实实在在的摩擦。

如果你能运行一个把数据留在你自己 AWS 账户、按需在前线开放权重模型之间切换、且只为你所消费的付费的 AI 编码智能体，会怎样？

[OpenCode](https://opencode.ai) 是一个开源、终端原生的、用 Go 编写的 AI 编码智能体。它通过语言服务器协议（LSP）诊断来读取和编辑文件、运行 shell 命令并理解项目结构。它连接到 75 多个大语言模型（LLM）提供方，包括 [Amazon Bedrock](https://aws.amazon.com/bedrock/)。当你把 OpenCode 与 Bedrock 上的开放权重模型配对时，你得到一个在本地运行、而推理安全地在你 AWS 账户内发生的编码助手。没有基础设施要管理，也没有按席位费用。

在本文中，我们展示如何在 Amazon Bedrock 上把 OpenCode 与开放权重模型一起设置、配置为每个任务匹配正确模型的多模型工作流，并用 [Moonshot AI Kimi K3](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-moonshot-ai-kimi-k3.html)、[OpenAI GPT-OSS 120B](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-openai-gpt-oss-120b.html) 和 [NVIDIA Nemotron 3 Super 120B](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-nvidia-nemotron-super-3-120b.html) 演练实用的编码示例。我们还分享 [Ethara.AI](http://ethara.ai/) 如何用多智能体编排在生产中部署这一架构，以大规模支持 AI 工程和研究工作流。

## 为什么用开放权重模型做 AI 辅助编码

业界正转向开放权重模型。据 [McKinsey 的 Open-source technology in the age of AI 报告（2025）](https://www.mckinsey.com/capabilities/quantumblack/our-insights/open-source-technology-in-the-age-of-ai)，76% 的组织预计会增加开源 AI 用量，而领先的 AI 采用者使用开放权重模型的可能度高 40%。对编码工作负载，五个因素驱动这一转变：

**性能持平：** 微调过的开放权重模型能在领域特定任务上胜过专有替代品。[CrowdStrike 微调的 NVIDIA Nemotron](https://www.crowdstrike.com/en-us/blog/crowdstrike-journey-in-customizing-nvidia-nemotron-models/) 达到 96% 的有效查询准确率，胜过 GPT-4o（61%）和 Claude Sonnet 4.5（94%）。

**成本效率：** 据 [Gartner 的 2026 分析](https://neuralwired.com/2026-06-20/gartner-llm-inference-cost-enterprise/)，智能体式工作流会把 token 消耗成倍放大 5–30 倍，使每-token 成本变得关键。在规模上——每月数千万次对话的量级——切换到 Bedrock 上的开放权重模型能降低年化成本。

**定制与控制：** 开放权重支持微调、蒸馏和领域适配。更小的模型能替代昂贵的通用模型，同时保持质量。

**模型灵活性：** 用开放权重，你可以为每个任务采用正确的模型，并随新模型涌现而演进。在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上切换模型是一个 API 参数的改动。

**透明度：** 可检视的模型架构和行为，支持那些有 AI 治理要求的受监管行业。

## 为什么用 Amazon Bedrock 作为后端

Amazon Bedrock 提供完全托管、无服务器的开放权重模型访问。没有 GPU 配置或推理基础设施要管理。对企业编码工作流，Bedrock 相比自托管或直接模型提供方有几个优势：

**数据驻留与合规：** 代码、prompt 和响应留在你的 AWS 账户。通过区域内或地理配置访问的模型在该区域或地理内运行。你可以通过一个跨区域推理配置调用 Kimi K3。对于没有区域限制的工作负载，我们推荐使用 global 配置 `global.moonshotai.kimi-k3`，它把每个请求路由到全球任意受支持的商业 AWS 区域。全球跨区域推理比地理配置便宜约 10%。美国地理配置 `us.moonshotai.kimi-k3` 把处理保持在美国地理内，以满足数据驻留要求。Amazon Bedrock 在常见合规项目的范围内，包括 HIPAA、SOC 2、ISO 27001、FedRAMP 和 GDPR。完整列表见[按合规项目划分的、在范围内的 AWS 服务](https://aws.amazon.com/compliance/)。

**企业安全控制：** 开放权重模型继承与专有模型相同的 [AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 策略、[AWS CloudTrail](https://aws.amazon.com/cloudtrail/) 日志、AWS PrivateLink 连通性和加密控制。无需单独的安全栈。

**灵活定价：** 三个层级把成本与工作负载匹配：Priority 用于延迟敏感的生产，Standard 用于按需推理（按 token 付费），Flex 对可变延迟工作负载低 50% 成本。

**不用你的数据训练模型：** Bedrock 不用你的输入或输出来训练或改进基础模型（FM）。

**高默认容量：** 每分钟 1 亿 token 和每分钟 1 万请求的默认限制，帮助在团队扩展时减少吞吐瓶颈。

## 为任务选择正确的模型

不是每个编码任务都需要同一个模型。把 OpenCode 与 Bedrock 一起用的关键优势之一，就是能够根据你正在做什么来在各模型之间选择和切换。

**在哪里评估模型：** [Artificial Analysis Coding Index](https://artificialanalysis.ai/coding) 在真实世界软件工程任务（SWE-Bench、Terminal-Bench、SWE-Atlas）上提供一个综合基准。用它来比较模型性能、每任务成本和延迟。要针对你自己的 prompt 和数据做评估，你可以用 [Amazon Bedrock Evaluations](https://aws.amazon.com/bedrock/evaluations/) 运行并排比较，用自动打分、`LLM-as-a-judge` 或人工审阅。

### 原始性能之外的考量

- **推理深度**：对于复杂调试、架构决定或计划生成，推理模型会逐步追踪问题。Kimi K3 在回答前推理。你用 `reasoning_config`（low、high 或 max）设定深度。你在难题上用延迟换正确性。
- **生成速度与延迟**：对于代码补全、样板生成和交互式结对编程，更低延迟比峰值推理更重要。NVIDIA 报告 Nemotron 3 Super 120B 凭借只激活每 token 2.8T 总参数中 12B 的混合专家架构，交付高达 7 倍的吞吐。
- **每-token 成本**：对于高流量工作负载（批量重构、大型代码库），成本会累积。Bedrock 上的开放权重模型比专有替代品提供更低每-token 定价。
- **上下文窗口**：Kimi K3 支持 100 万 token 上下文，大约数万行代码。你可以载入一整个仓库而非几个文件来做跨文件推理。
- **区域可用性**：确认哪些模型在你的目标区域可用。这对数据主权和延迟要求很重要。

对本文，我们推荐三个覆盖全谱的模型：

| **模型** | **强项** | **最适合** |
| --- | --- | --- |
| Moonshot AI Kimi K3 | 带 100 万 token 上下文的常开推理 | 调试、架构分析、复杂逻辑 |
| OpenAI GPT-OSS 120B | 前线代码生成（120B 参数） | 全服务生成、多文件实现 |
| NVIDIA Nemotron 3 Super 120B | 优化的吞吐，企业验证 | 高流量生成工作负载 |

## 方案概览

架构有两部分：OpenCode 作为终端用户界面（TUI）在你本地机器上运行，并调用 Amazon Bedrock Converse API 做推理。Bedrock 把模型作为完全托管、无服务器的端点托管。

图 1：Amazon Bedrock 上开放权重模型配 OpenCode 的方案架构。开发者在终端与 OpenCode 交互，它通过 Bedrock Converse API 向开放权重模型发送请求。AWS IAM 认证每个请求，而 AWS CloudTrail 记录 API 活动

OpenCode 的智能体架构支持给不同角色指派不同模型：一个用于规划的推理模型，和一个用于代码生成的更快模型。这在单个会话内创建一个多模型工作流。

开始前，确认你有：

- 一个启用了 [Amazon Bedrock 访问](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html) 的有效 [AWS 账户](https://aws.amazon.com/free/)。
- 在 Amazon Bedrock 控制台中为 Kimi K3、GPT-OSS 120B 和 NVIDIA Nemotron 3 Super 120B 授予的[模型访问](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)。
- 配置好的 AWS 凭证（[IAM 访问密钥](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_access-keys.html)、AWS IAM Identity Center，或一个 [Bedrock API key](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html)）。

## 安装并配置 OpenCode

本节演练安装 OpenCode CLI 并配置它与 Amazon Bedrock 认证。

### 安装 OpenCode

选择以下方法之一：

```
# Install script (recommended)
curl -fsSL https://opencode.ai/install | bash

# Or via npm
npm install -g opencode-ai

# Or via Homebrew (macOS/Linux)
brew install sst/tap/opencode
```

验证安装：

```
$ opencode --version
1.18.20
```

### 配置 AWS 凭证

OpenCode 的 Bedrock 提供方使用标准 AWS 凭证链。配置以下选项之一：

#### 选项 A：AWS IAM Identity Center（企业推荐）

```
aws sso login --profile my-bedrock-profile
export AWS_PROFILE=my-bedrock-profile
export AWS_REGION=us-west-2
```

#### 选项 B：IAM 访问密钥

```
export AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMPLE
export AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
export AWS_REGION=us-west-2
```

用你自己的凭证替换这些。对于生产使用，优先 IAM Identity Center 或 IAM 角色，而非长期访问密钥。

#### 选项 C：Bedrock API key

```
export AWS_BEARER_TOKEN_BEDROCK=your-bedrock-api-key
export AWS_REGION= us-west-2
```

你也可以把这些存到你项目根目录的一个 `.env` 文件里以做持久配置。

## 配置一个多模型工作流

借助 OpenCode 的智能体系统，你可以给不同角色指派不同模型。在你的项目根目录创建或编辑 `opencode.json`：

```
{
  "$schema": "https://opencode.ai/config.json",
  "model": "amazon-bedrock/us.openai.gpt-oss-120b-1:0",
  "agent": {
    "plan": {
      "model": " amazon-bedrock/global.moonshotai.kimi-k3"
    },
    "build": {
      "model": "amazon-bedrock/us.nvidia.nemotron-super-3-120b"
    }
  }
}
```

这一配置把规划和架构任务（受益于深度推理的那些）路由给 Kimi K3，而代码生成和实现交给为优化吞吐的 Nemotron 3 Super 120B。顶层的 model 字段把 GPT-OSS 120B 设为其他上下文的默认。

要以交互方式浏览可用的 Bedrock 模型，启动 OpenCode 并输入 `/models`。

## 用开放权重模型编码

下面的例子展示如何把每个模型匹配到它最擅长处理的任务类型。

### 用 GPT-OSS 120B 生成一个事件溯源的订单服务

GPT-OSS 120B 是 OpenAI 的 1,200 亿参数开放权重模型。它把强推理与代码生成结合，使它很适合那些跨多个文件的、架构复杂的实现。有了上一节的多模型配置，你可以内联覆盖默认模型，或用 `/model` 显式切换：

```
$ opencode
> /model us.openai.gpt-oss-120b-1:0
> Build an event-sourced CQRS order service in Python (FastAPI) with:
> - Command side: append-only event store in DynamoDB, idempotent handlers
> - DynamoDB Streams triggering a projection Lambda that builds a read-model
> - Query side: denormalized read-model optimized for "orders by customer"
>   and "orders by status" access patterns
> - Event replay CLI to rebuild projections from scratch
> - Snapshotting every 50 events per aggregate to bound replay time
> Include CDK infrastructure.
```

图 2：OpenCode 用 GPT-OSS 120B 生成事件溯源的 CQRS 订单服务

OpenCode 通过带 IAM 认证的 Bedrock Converse API 把这路由给 GPT-OSS 120B。模型生成完整的服务结构，包括 handler、事件存储、投影和 CDK 栈，直接写进你本地的文件系统。CloudTrail 记录这次调用，而你的 prompt 和响应留在你的 AWS 账户内。

### 用 Kimi K3 诊断一个分布式死锁

Kimi K3 擅长那些需要追踪多个执行路径的推理任务。它每一轮都推理，而 `reasoning_config` 字段设定推理多深：quick pass 用 low，难的是用 max。如果你把 Kimi K3 配置为你的 plan 智能体，它已经是分析任务的默认。你也可以用 `/model` 显式切换：

```
> /model amazon-bedrock/global.moonshotai.kimi-k3
> This Step Functions workflow hangs ~2% of the time under load.
> The pattern: Task A does a DynamoDB conditional put that expects
> status="PENDING", Task B (triggered by SQS) sets status="READY"
> but only after Task A's callback confirms receipt. Both tasks
> wait on each other. Trace the deadlock, explain why it only
> manifests under concurrency, and propose a fix that doesn't
> require redesigning the state machine.
> @order_workflow.asl.json @task_a_handler.py @task_b_handler.py
```

@file 引用把你的本地代码注入为上下文，无需手动复制粘贴。Kimi K3 的混合专家架构每 token 只激活其 2.8T 总参数中的 104B，以高效的吞吐交付前线推理。你可以看着模型实时追踪各并发路径。因为推理可见，你可以在接受提议的修复之前判断分析是否站得住。

### 会话中途切换模型

你不必锁定到单个模型。在会话期间输入 `/models` 来切换。一个实用的模式：用 Nemotron 3 Super 120B 或 GPT-OSS 120B 做快速代码生成和样板，然后在遇到复杂调试问题或需要就架构权衡做推理时切换到 Kimi K3。

有了前面展示的多模型 `opencode.json` 配置，这一路由自动发生。plan 智能体用 Kimi K3 做推理，而 build 智能体用 Nemotron 做实现。

### 用 Flex 层级为批处理编码任务降低成本

有些编码工作是交互式的。跨大型代码库的批量重构、为现有模块生成测试套件，或从代码产出文档。这些任务对延迟宽容，可以异步运行。Amazon Bedrock Flex 层级对这些工作负载比 Standard 低 50% 成本。

你可以把它与 OpenCode 的 CLI 模式结合，脚本文批处理操作：

```
# Process multiple files through GPT-OSS 120B for test generation
for file in src/**/*.py; do
  opencode run -m amazon-bedrock/us.openai.gpt-oss-120b-1:0 \
    "Generate comprehensive unit tests for @${file}. Use pytest with fixtures."
done
```

把你的层级叠起来：交互式会话用 Standard，批处理用 Flex，延迟敏感的生产用 Priority。

## 扩展到多模型路由架构

本文中展示的 OpenCode + Bedrock 模式是一个单开发者的工作流。对团队和生产系统，同样的多模型原则延伸为一个路由架构，其中编排器把每个子任务导向最优模型：

图 3：在 Amazon Bedrock 上用开放权重模型的多模型路由架构。一个路由器分析传入的请求，并把子任务派发到最优模型层级，以相比把所有任务都通过单一模型路由降低总拥有成本

在这一模式中：

- **意图分类** 路由到一个低成本模型（小、快的推理）。
- **代码生成** 路由到一个为吞吐优化的中档开放权重模型。
- **复杂推理**（架构决定、安全分析）路由到一个高级推理模型。

相比把所有东西都通过一个昂贵的单一模型发送，这一路由帮助降低整体总拥有成本（TCO）而不退化质量。Amazon Bedrock 统一的 API 让这变得可行：切换模型是一个参数改动，而各模型共享同样的认证、日志和护栏基础设施。

对于准备好超越单开发者使用的团队，把 OpenCode 的本地智能体路由与一个服务器端编排层（[Amazon Bedrock Agents](https://aws.amazon.com/bedrock/managed-agents-openai/) 或 [AWS Step Functions](https://aws.amazon.com/step-functions/)）结合，创建一个完整的多模型编码流水线。

## 生产部署：大规模多智能体编排

Ethara.AI，一个 AWS 客户，在生产中部署这一架构，把 OpenCode 用作 AI 工程和研究工作流的基础运行时。[Oh-My-OpenAgent](https://omo.dev/docs) 充当与专用 AI 智能体协作的编排层。Ethara.AI 不依赖单个编码助手，而是运营一支针对不同任务优化的智能体舰队，如规划、执行、代码评审、架构分析、知识检索、多模态理解和基准测试。通过 Oh-My-OpenAgent 的基于类别的路由系统，工程师请求一种能力（如深度推理、快速执行、视觉工程或写作辅助），系统把工作委派给最合适的那个智能体。这一抽象帮助团队专注于结果而非模型管理，同时在演进的 AI 框架间保持灵活性。

Amazon Bedrock 和 OpenCode 提供方无关的架构为 Ethara.AI 的模型选择策略提供动力。OpenCode 支持访问广泛的基础模型，而 Amazon Bedrock 提供对前线模型的安全访问。他们不用单一模型，而是根据推理复杂度、延迟要求、成本效率和任务类型等因素动态路由工作负载。Amazon Bedrock、OpenCode 和 Oh-My-OpenAgent 的结合帮助他们把智能体能力与底层模型层分离。这帮助确保最合适的智能体-模型组合执行每个任务，同时保留随模型格局演进而评估和采用新模型的能力。

展望未来，Ethara.AI 正在投资自我改进的智能体系统，借鉴像 [SkillClaw](https://github.com/AMAP-ML/SkillClaw) 这样的研究。他们正在开发一些机制，让技能和智能体行为基于成功和失败的执行轨迹而演进，创造一种让智能体通过真实使用持续改进的基础设施。这一愿景建立在 OpenCode 的可扩展架构、Oh-My-OpenAgent 的委派框架和 Amazon Bedrock 模型目录之上，以创造随时间变得更强大、更自适应、更高效的 AI 系统。

## 面向企业使用的安全考量

Bedrock 上的开放权重模型继承与专有模型完全相同的企业控制。权重的来源不改变你的安全态势。用遵循最小权限的 IAM 策略限制哪些用户能调用哪些模型：

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": [
        "arn:aws:bedrock:us-west-2::foundation-model/openai.gpt-oss-120b-1:0",
        "arn:aws:bedrock:us-west-2::foundation-model/nvidia.nemotron-super-3-120b",
        "arn:aws:bedrock:us-west-2:{account-id}:inference-profile/global.moonshotai.kimi-k3",
        "arn:aws:bedrock:*::foundation-model/moonshotai.kimi-k3"
      ]
    },
    {
      "Effect": "Allow",
      "Action": ["bedrock:CallWithBearerToken"],
      "Resource": ["*"]
    }
  ]
}
```

你可以进一步叠加 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/)，跨调用做内容过滤和可识别个人身份信息（PII）脱敏。CloudTrail 记录每一次 `InvokeModel` 调用以供审计，而 Bedrock 不用你的输入或输出来训练模型。

## 清理

本演练除了启用模型访问之外，不创建持久的 AWS 基础设施。如果你仅为测试启用了模型访问，可以在 Amazon Bedrock 控制台的 **Model catalog** 下禁用它。没有其他资源需要清理，而当你不进行 API 调用时也不产生费用。

## 结论

我们展示了如何在 Amazon Bedrock 上把 OpenCode 与开放权重模型配置，以构建一个安全、灵活、按用付费的 AI 编码工作流。你得到开放权重模型的成本效率和定制潜力、Bedrock 的企业安全和托管基础设施，以及一个融入现有开发者工作流的终端原生体验，并带把不同任务自动路由到不同模型的能力。
