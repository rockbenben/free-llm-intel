# 在 Amazon Bedrock 上自动化模型配额申请与运维问题分诊

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 为全球超过 100,000 家组织提供生成式 AI 能力——从初创公司到各行各业的大型企业。它提供经过验证的基础设施和全面的能力，让你可以放心构建在生产环境中运行的应用程序和 agent，并具备所需的灵活性、企业级安全性和久经考验的可扩展性，从而大胆创新、交付真正带来业务影响的 AI。随着组织把由 Amazon Bedrock 驱动的生成式 AI 应用扩展到多个基础模型和生产工作负载，主动的运维管理成为保持创新速度的关键。

随着生成式 AI 在各团队间的采用不断增长，组织可以从一套专门构建的运维监控方案中获益，它提供：1）主动的多层监控，通过跟踪使用模式预判采用规模扩大带来的配额提升需求，并加速由 Amazon Bedrock 驱动的生成式 AI 工作负载的运维问题分诊；2）上下文感知的支持案例自动化，为 AWS 支持工程师提供所需信息，从而缩短平均解决时间；3）重复案例防护，当同一告警类别已有未解决的案例时抑制新案例创建，避免干扰正在进行的排查；4）情境化通知，让 AI SRE 团队能够快速行动；5）通过减少人工运维开销，持续专注于创新。

在本文中，我们介绍 Amazon Bedrock Ops Alert——一套三层自动化监控方案：它主动发现运维问题、动态调整告警阈值、按类别对告警分类、自动创建上下文感知的支持案例、在同一告警类别已有未解决案例时帮助避免重复案例，并向 AI SRE 团队发送情境化通知。我们会讲解该方案的架构，以及如何在你自己的环境中部署它。

## 为生成式 AI 工作负载提升运维成熟度

Amazon Bedrock 为每分钟请求数（RPM）和每分钟 token 数（TPM）提供服务配额，以帮助在客户之间管理资源分配。随着工作负载增长，这些配额可以通过 AWS Support 案例提升。常见的初始做法是用由 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 指标支撑的第三方仪表盘方案，配合人工流程来监控配额消耗并在需要时申请提升。这种做法在采用初期对团队足够有效。

随着采用规模扩大，组织常常发现：优化工作负载比提升配额更能有效满足容量需求。[跨区域推理（cross-region inference）](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html) 通过使用不同 AWS 区域中的算力，帮助组织应对计划外的流量突发。当使用绑定到特定地理范围的推理配置文件（inference profile）时，Amazon Bedrock 会自动选择该地理范围内最优的商业 AWS 区域来处理推理请求。[全局跨区域推理](https://docs.aws.amazon.com/bedrock/latest/userguide/global-cross-region-inference.html) 把这一点延伸到地理边界之外，将推理请求路由到全球各地的商业 AWS 区域，从而优化可用资源并提供更高的模型吞吐。使用全局推理配置文件时，工作负载不再受单个区域容量的约束，可以访问大得多的资源池，并且与地理范围的跨区域推理相比大约节省 10% 的成本。在博文 [Unlock global AI inference scalability using new global cross-Region inference on Amazon Bedrock with Anthropic’s Claude Sonnet 4.5](https://aws.amazon.com/blogs/machine-learning/unlock-global-ai-inference-scalability-using-new-global-cross-region-inference-on-amazon-bedrock-with-anthropics-claude-sonnet-4-5/) 中，我们详述了全局推理配置文件如何跨 AWS 全球基础设施动态路由请求，以吸纳原本需要提升配额才能满足的需求。

[Prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html) 是一项可选功能，可降低推理响应延迟和输入 token 成本。通过把部分上下文放入缓存，模型会跳过对输入的重复计算，让 Amazon Bedrock 分享算力节省并降低响应延迟。当工作负载包含较长且重复、被多个查询频繁复用的上下文时，prompt caching 很有帮助：它最多可降低 90% 的成本、最多降低 85% 的延迟，从而直接减少每分钟 token 的消耗。在博文 [Effectively use prompt caching on Amazon Bedrock](https://aws.amazon.com/blogs/machine-learning/effectively-use-prompt-caching-on-amazon-bedrock/) 中，我们讲解了如何组织 prompt，以便在多次 API 调用中最大化缓存命中。批处理推理和 [Intelligent Prompt Routing](https://aws.amazon.com/bedrock/cost-optimization/) 等其他技术，通过为每次调用动态选择最具成本效益的模型，进一步降低单次请求开销。

通过优化 [max_tokens](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-token-burndown.html) 参数，你可以高效利用分配到的那部分配额。`max_tokens` 的值会在每次请求开始时从你的配额中扣除。处理过程中，消耗的配额会按实际生成的输出 token 数定期调整；请求结束时，未使用的 token 会补回你的配额。在博文 [Improve operational visibility for inference workloads on Amazon Bedrock with new CloudWatch metrics for TTFT and Estimated Quota Consumption](https://aws.amazon.com/blogs/machine-learning/improve-operational-visibility-for-inference-workloads-on-amazon-bedrock-with-new-cloudwatch-metrics-for-ttft-and-estimated-quota-consumption/) 中，我们详述了如何监控 InputTokenCount 和 OutputTokenCount 这两项 CloudWatch 指标，以指导针对不同请求类型的 `max_tokens` 决策。

随着组织采纳这些优化策略，并把范围扩展到多个基础模型和生产工作负载，AI SRE 团队希望用自动化运维监控来补充它们，以保持创新速度并缩短平均解决时间。具体来说，团队通常会找出四个可改进的方面：

- **被动运维**：AI SRE 团队往往只在业务用户报告影响之后才得知运维问题。这迫使团队被动应对，在影响扩大之前可用于排查和响应的时间很有限。
- **案例上下文补充的机会**：配额问题出现时，支持案例如果能带上更丰富的上下文，把单纯的配额提升与需要深入排查的问题区分开，就能帮助支持工程师更快解决案例。
- **运维工作成倍增加**：随着组织为不同用例采用新的基础模型，每个新模型都需要自己的监控设置和配额提升申请。这种没有差异性的重复劳动会随模型组合线性增长。
- **告警阈值是移动靶**：每次配额提升获批，AI SRE 团队都要手动重算并更新 CloudWatch 告警阈值，既带来运维开销，也有配置漂移的风险。

## 方案概览

Amazon Bedrock Ops Alert 是一套基于 [AWS CloudFormation](https://aws.amazon.com/cloudformation/) 的方案，通过三个互为补充的检测层实现全面的生成式 AI 可观测性。每一层提供对生成式 AI 工作负载的不同可见性，从即时发现运维问题到预测性识别异常。

该方案使用 Amazon CloudWatch 告警、[AWS Lambda](https://aws.amazon.com/lambda/) 函数、[Amazon Simple Notification Service (Amazon SNS)](https://aws.amazon.com/sns/)、[Service Quotas](https://docs.aws.amazon.com/servicequotas/latest/userguide/intro.html) API 以及 [AWS Support API](https://docs.aws.amazon.com/awssupport/latest/user/about-support-api.html)。

下图展示了该方案的架构。

![Amazon Bedrock Ops Alert 方案架构图，展示三个监控层、复合告警、SNS 主题、Lambda 通知处理器，以及自动化支持案例创建工作流](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/02/ML-20534-1.png)

工作流步骤如下：

- 部署期间，一个 Lambda 函数（Quota Calculator）查询 Service Quotas API 获取当前的 RPM 和 TPM 配额值，并按配置的百分比计算告警阈值。
- 计算出的阈值存入 AWS Systems Manager Parameter Store，AI SRE 团队的邮件联系人存入 AWS Secrets Manager。
- Amazon Bedrock 把运行时指标（调用次数、token 计数、错误、限流和延迟）发布到 CloudWatch。三个独立的监控层评估这些指标：  **第 1 层（严重错误检测）** 监控限流、客户端错误和服务端错误，用于即时告警。**第 2 层（使用率监控）** 把 RPM、TPM 和延迟与动态计算出的阈值做比较。**第 3 层（异常检测）** 使用 CloudWatch 机器学习识别指标中的异常模式。
- 子告警触发时，一个复合告警（composite alarm）汇总状态。
- 复合告警发布到一个 SNS 主题（Raw Alarm Topic）。
- 该 SNS 主题调用一个 Lambda 通知处理器函数，它轮询复合告警以确定哪些子告警被触发，并判定告警严重程度（critical 或 warning）。
- 通知处理器查询 Service Quotas API，获取当前的 RPM 和 TPM 配额值。
- 通知处理器查询 CloudWatch 获取当前使用指标，包括过去 14 天的稳态与峰值 RPM/TPM，以及每次请求的平均 token 数。它还会从 Parameter Store 读取已存储的告警阈值，把峰值用量与阈值比较，以确定支持案例场景。
- 如果启用了自动化支持案例创建，该函数会把告警归类为配额相关或非配额，用类别感知的重复检测（回溯窗口可配置，默认 60 天）检查是否存在未解决的案例，然后要么向现有案例追加一条沟通记录，要么创建新的 AWS Support 案例。对于配额相关告警，案例包含经用量校验的、预填好的配额数据。对于非配额告警（例如持续错误或延迟异常），则提供有助于根因分析的上下文。
- 支持案例处理完成后，该函数通过第二个 SNS 主题（Formatted Notification Topic）向相关方发送格式化邮件通知，并按通知偏好（全部、仅 critical、仅 warning）过滤。如果创建了支持案例，邮件会包含案例 ID 和指向 AWS Support 控制台的直接链接。
- 格式化后的通知以邮件形式投递给已订阅的相关方。
- 按可配置的计划，一条 [Amazon EventBridge](https://aws.amazon.com/eventbridge/) 规则会触发一个 Lambda 函数（Alarm Updater）。
- Alarm Updater 查询 Service Quotas API 获取当前的 RPM 和 TPM 配额值。
- Alarm Updater 按配置的百分比重新计算告警阈值，并用新阈值更新 CloudWatch 告警。
- 更新后的阈值连同时间戳一起存入 Parameter Store，以便跟踪历史。

### 三层监控架构

该方案用 CloudWatch 告警实现三个监控层，它们各自独立工作，在不同阶段发现运维问题。

**第 1 层：严重错误检测**

第一层监控指示运维问题的错误指标：

- **ClientErrors 告警**：监控 InvocationClientErrors 指标，识别因客户端问题被拒绝的请求，例如超出配额上限、校验错误或参数无效。
- **ServerErrors 告警**：监控 InvocationServerErrors 指标，识别可能需要排查的服务端错误。
- **Throttles 告警**：监控 InvocationThrottles 指标，识别达到速率上限时被明确限流的请求。

这些告警使用可配置的阈值和评估周期。把错误阈值设为 0 并只设一个评估周期，就能在发生错误时立即触发告警；更高的取值则为瞬时问题留出容忍度。

**第 2 层：使用率监控**

第二层把使用指标与动态计算出的阈值做比较，在触及配额上限之前提供主动告警：

- **HighInvocationRate 告警**：监控 Invocations 指标，当 API 请求速率超过配额中配置的 RPM 阈值百分比时触发。
- **HighTPMQuotaUsage 告警**：监控 [EstimatedTPMQuotaUsage](https://aws.amazon.com/about-aws/whats-new/2026/03/amazon-bedrock-observability-ttft-quota/) 指标，当估计的每分钟 token 配额消耗超过配额中配置的 TPM 阈值百分比时触发（包含缓存写入 token 和输出 burndown 乘数）。
- **HighLatency 告警**：监控 InvocationLatency 指标，当响应时间超过配置的延迟阈值时触发。

该方案通过查询 Service Quotas API 并应用可配置的百分比来自动计算告警阈值。例如，阈值为 80%、RPM 配额为 100 时，RPM 告警会在每分钟 80 个请求时触发。对于 TPM，同样的 80% 阈值作用在 1,000,000 TPM 配额上，得到 800,000 有效 token 的阈值。TPM 告警使用 EstimatedTPMQuotaUsage 指标，它跟踪估计的 TPM 配额消耗，包含缓存写入 token 和输出 burndown 乘数。

**第 3 层：异常检测**

第三层使用 CloudWatch 异常检测作为阈值类型，识别指标中的异常模式：

- **InvocationAnomaly 告警**：用异常检测监控 Invocations 指标，识别异常的请求量变化。
- **InputTokenAnomaly 告警**：用异常检测监控 InputTokenCount 指标，识别异常的输入 token 用量。
- **OutputTokenAnomaly 告警**：用异常检测监控 OutputTokenCount 指标，识别异常的输出 token 用量。
- **LatencyAnomaly 告警**：用异常检测监控 InvocationLatency 指标，识别性能劣化趋势。

CloudWatch 机器学习分析历史数据以建立正常行为基线，然后当当前指标超出预期区间的上阈值时告警。该方案只监控向上偏离：用量下降是积极信号，无需干预。这种做法能发现静态阈值漏掉的问题，例如配额消耗的逐步攀升或意外的用量激增。

### 自动化阈值管理

该方案通过自动重算阈值来动态适应配额变化：

- **初始计算**：部署期间，一个 Lambda 函数查询 Service Quotas API，并根据当前配额和配置的百分比计算告警阈值。
- **计划更新**：一条 EventBridge 规则按可配置的计划触发阈值重算（默认：每 1 天一次）。
- **自动更新告警**：当获批的配额提升改变了配额值时，该方案会用新阈值更新 CloudWatch 告警。
- **阈值历史**：计算出的阈值连同时间戳存入 [Parameter Store, a capability of AWS Systems Manager](https://docs.aws.amazon.com/systems-manager/latest/userguide/systems-manager-parameter-store.html)。

当后续的配额提升申请获批时，这套自动化减轻了手工维护阈值的负担。AI SRE 团队不再需要跟踪配额变化并手动更新告警配置：系统会自我校正。

下表说明告警阈值如何从 Service Quotas 的值推导出来。

| **阈值** | **公式** | **示例** |
| --- | --- | --- |
| RPM 阈值 | RPM 配额 × (RequestsPerMinuteThresholdPercent / 100) | 10,000 RPM 配额 × 80% = 8,000 |
| TPM 阈值 | TPM 配额 × (TokensPerMinuteThresholdPercent / 100) | 6,250,000 TPM 配额 × 80% = 5,000,000 |

TPM 阈值百分比直接作用在 TPM 配额上。在确定支持案例场景时，用量校验会把 14 天峰值 TPM 与该阈值做比较。

### 自动化支持案例创建

当检测到运维问题时，该方案可选地自动化 AWS Support 案例的创建。此功能需要 AWS Business 或 Enterprise Support 计划才能访问 Support API。

工作流运行如下：

- 当某个子告警进入 ALARM 状态时，复合告警触发。
- 一个 Lambda 函数轮询复合告警的状态，检查符合条件的子告警。
- 该函数从 Parameter Store 读取已存储的告警阈值，把 14 天峰值用量与阈值比较，以确定支持案例场景。
- 该函数把告警归类为配额相关或非配额，并用类别感知的重复检测（回溯窗口可配置，默认 60 天）向 Support API 查询是否存在未解决的案例。
- 如果存在同一类别的未解决案例，系统会向现有案例追加一条沟通记录，包含完整告警详情、更新后的指标和紧急程度上下文。如果不存在重复案例，系统会创建内容与场景相称的新支持案例：要么是带有用量校验细节的配额提升请求，要么是不含配额细节的服务排查请求。

系统把告警分为两类，并决定相应的响应方式。

**配额相关告警**会触发一个内容经用量校验的“Quota Request（配额请求）”支持案例：

- **RPM 专属告警**（HighInvocationRate、InvocationAnomaly）只申请 RPM 配额提升。
- **TPM 专属告警**（HighTPMQuotaUsage、InputTokenAnomaly、OutputTokenAnomaly）只申请 TPM 配额提升。
- **无法确定配额的告警**（Throttles、ClientErrors）同时申请 RPM 和 TPM 配额提升，并提供有助于判断触及了哪个上限的上下文。

**非配额告警**（ServerErrors、HighLatency、LatencyAnomaly）会触发“Investigation Request（调查请求）”支持案例，提供告警上下文和用量数据以协助根因分析，不含配额提升细节。

下表汇总告警分类与配额路由。

| **分类** | **告警** | **案例类型** | **申请的配额** |
| --- | --- | --- | --- |
| RPM 专属告警 | HighInvocationRate, InvocationAnomaly | 配额请求 | 仅申请 RPM 配额提升 |
| TPM 专属告警 | HighTPMQuotaUsage, InputTokenAnomaly, OutputTokenAnomaly | 配额请求 | 仅申请 TPM 配额提升 |
| 无法确定配额的告警 | Throttles, ClientErrors | 配额请求 | RPM 和 TPM 配额提升都申请 |
| 非配额告警 | ServerErrors, HighLatency, LatencyAnomaly | 调查请求 | 不申请配额提升 |

**经用量校验的场景决策树**

在创建配额相关的支持案例之前，该方案会把 14 天峰值用量指标与已存储的告警阈值比较，以确定合适的响应。这项用量校验确保支持案例带有恰当的上下文和语气，便于支持工程师处理。

**经用量校验的场景详情**

以下各节逐一说明每个场景，包括触发条件、支持案例内容和示例。

**非配额（Non-quota）**：ServerErrors、HighLatency 或 LatencyAnomaly 触发，且没有其他类型告警。不含配额提升细节。案例为支持工程师提供告警上下文、用量指标和触发条件，以协助根因分析。

| **字段** | **详情** |
| --- | --- |
| 案例类型 | 调查请求 |
| 告警 | ServerErrors-Critical (InvocationServerErrors), HighLatency-Warning (InvocationLatency), LatencyAnomaly-Warning (InvocationLatency) |

**支持案例管理与邮件通知**

该方案使用类别感知的重复检测来帮助避免冗余案例。当新告警触发、而同一类别（配额请求或调查请求）已有未解决案例时，系统会向现有案例追加一条沟通记录，而不是创建重复案例。追加的记录包含完整告警详情、更新后的用量指标，以及（如适用的）配额提升申请，并在开头附上表明情况正在升级的紧急程度上下文。这确保支持工程师能获知新信号，又不会产生相互冲突的案例。针对某种告警类型的配额请求案例，不会阻止针对另一种告警类型的调查请求案例，反之亦然。

支持案例的参数存储在 Parameter Store 中，无需重新部署 CloudFormation 栈即可更新。你可以启用或停用自动化案例创建、调整配额提升百分比（0–100%），并配置邮件通知过滤（全部告警、仅 critical 或仅 warning）。

## 成果

Amazon Bedrock Ops Alert 带来以下成果：

- **提升运维效率**：AI SRE 团队从手工监控转向更高价值的工作。
- **智能告警分类**：非配额告警（服务端错误、延迟异常）被路由到调查类案例，而不是配额提升申请，从而为支持工程师提供有针对性的案例上下文，加速根因解决。
- **经用量校验的支持案例**：该方案在创建支持案例之前把峰值用量与阈值比较，确保配额提升申请反映真实用量模式，并包含适合支持工程师的上下文。
- **缩短平均解决时间**：自动创建案例把每起事件的人工投入从数小时降到数分钟。
- **主动的配额管理**：在生产应用触及速率上限之前就发起配额提升申请。
- **无需手动维护阈值**：配额提升获批、目标值改变时，告警依然准确，无需工程师介入。
- **可扩展的基础**：通过部署更多栈实例即可监控更多 Bedrock 模型，支撑不断扩张的生成式 AI 组合。

## 结论

生成式 AI 监控不同于传统基础设施监控。随着生成式 AI 的采用模糊了业务团队与技术团队之间的界限——非工程团队现在也在使用由 Amazon Bedrock 托管的基础模型驱动的自建生成式 AI 应用——组织需要重新思考自己的运维监控策略，以匹配这一新现实。

在本文中，我们介绍了 Amazon Bedrock Ops Alert：一套由 AWS 原生服务组成的多层运维监控方案，用于满足大规模运行生成式 AI 工作负载的运维需求。三层监控架构由严重错误检测、使用率监控和异常模式识别构成，为生成式 AI 工作负载提供全面可见性，覆盖运维问题、使用趋势和异常行为。该方案的智能告警分类把客户端问题、延迟顾虑和配额相关信号路由到合适的支持案例类型，每个案例都补充了支持工程师快速行动所需的上下文。在创建支持案例之前，用量校验关卡会把近期峰值用量与已存储阈值比较，确认案例确有必要；重复案例防护则在同一告警类别已有未解决案例时抑制新案例，让排查保持聚焦。情境化邮件通知让 AI SRE 团队全程了解情况，并与自动化案例保持一致。通过自动化 CloudWatch 告警阈值重算，该方案还免去了每次配额提升获批后人工查明新配额值、计算合适告警阈值并更新告警的工作，从而保持告警准确，降低阈值陈旧的风险。

这些能力合在一起，把运维从被动监控转向主动运维监控：缩短平均解决时间，在采用增长时预判进一步的配额提升需求，并让 AI SRE 团队腾出精力去构建生成式 AI 应用，而不是监控基础设施。
