# 在满足数据驻留要求的同时，使用 AWS 混合与边缘服务实现 RAG

随着 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 正式可用，你可以快速开发生成式 AI 应用，在众多企业系统和数据源上执行多步任务。然而，一些受数据保护与隐私法规约束的地区和受监管行业，希望把云端的生成式 AI 服务与本地的受监管数据结合起来。本文展示如何将 Amazon Bedrock Agents 扩展到 [AWS Outposts](https://aws.amazon.com/outposts/) 和 [AWS Local Zones](https://aws.amazon.com/about-aws/global-infrastructure/localzones/) 等混合与边缘服务，以构建基于本地数据的分布式检索增强生成（RAG）应用，从而改善模型效果。借助 Outposts，我们还会介绍一种完全本地化 RAG 应用的参考模式，该模式要求基础模型（FM）和数据源都驻留在本地。

## 解决方案概览

对于处理或存储敏感信息（例如个人可识别信息，PII）的组织，客户希望 [AWS 全球基础设施](https://aws.amazon.com/about-aws/global-infrastructure/) 能够覆盖这些特定地点，包括能够确保数据存储与处理符合当地法律法规的机制。借助 Local Zones 和 Outposts 等 AWS 混合与边缘服务，你可以同时获得 AWS 云的可扩展性与灵活性，以及本地（或区域化）基础设施的低延迟与本地处理能力。这种混合方式让组织能够在更靠近数据源头的地方运行应用、处理数据，从而降低延迟、改善对时间敏感工作负载的响应能力，并满足数据法规要求。

尽管围绕 [Outposts 机架](https://aws.amazon.com/blogs/compute/architecting-for-data-residency-with-aws-outposts-rack-and-landing-zone-guardrails/) 和 [Local Zone](https://aws.amazon.com/blogs/compute/best-practices-for-managing-data-residency-in-aws-local-zones-using-landing-zone-controls/) 进行数据驻留架构设计已被广泛讨论，但生成式 AI 与 FM 带来了额外的一组架构考量。随着生成式 AI 模型日益强大、无处不在，客户一直在问我们：如何考虑把模型部署到更靠近产生和消费数据的设备、传感器与最终用户的位置。此外，对能够让资源受限设备执行复杂功能（例如自然语言处理和预测性自动化）的小语言模型（SLM）的兴趣也在增长。要了解更多关于客户使用 SLM 的机会，请参阅我们 AWS Industries 博客上的[面向电信业的小语言模型机会：来自 AWS 与 Meta 的洞察](https://aws.amazon.com/blogs/industries/opportunities-for-telecoms-with-small-language-models/)。

除了 SLM，边缘生成式 AI 受到的关注主要由两个主要因素驱动：

- **延迟** – 在边缘基础设施上运行这些计算密集型模型可以显著降低延迟、改善实时响应能力，这对虚拟助手、增强现实和自主系统等许多时间敏感型应用至关重要。

- **隐私与安全 **– 在边缘处理敏感数据，而不是将其发送到云端，可以通过尽量减少数据暴露来增强隐私与安全性。这在医疗、金融服务和法律领域尤为有用。

本文介绍两种主要的架构模式：完全本地 RAG 和混合 RAG。

### 完全本地 RAG

在 Outposts 机架上为 RAG 用例部署大语言模型（LLM）时，LLM 将自托管在 [G4dn 实例](https://aws.amazon.com/ec2/instance-types/g4/%20) 上，知识库将在 Outpost 机架上创建，可使用 [Amazon Elastic Block Storage (Amazon EBS)](https://aws.amazon.com/ebs) 或 [Outposts 上的 Amazon S3](https://aws.amazon.com/s3/outposts/?whats-new-cards.sort-by=item.additionalFields.postDateTime&whats-new-cards.sort-order=desc)。上传到机架上知识库的文档可能是私密且敏感的文档，因此它们不会被传输到 AWS 区域，而是完全保留在 Outpost 机架上。你可以使用本地向量数据库来存储 embedding，该数据库可以托管在 [Amazon Elastic Compute Cloud (Amazon EC2)](https://aws.amazon.com/ec2) 上，或在 Outpost 机架上使用 [Amazon Relational Database Service (Amazon RDS) for PostgreSQL](https://aws.amazon.com/rds/postgresql/) 配合 [pgvector](https://github.com/aws-samples/rds-postgresql-pgvector) 扩展。示例见下图。

### 混合 RAG

某些客户因数据保护或隐私法规要求，必须将数据保留在特定的州界之内。为满足这些要求同时仍将这类数据用于生成式 AI，拥有混合与边缘环境的客户需要同时在区域和边缘托管其 FM。这种设置让你既能把数据用于生成式用途，又能保持符合安全法规。要编排这样一个分布式系统的行为，你需要一个能够理解 prompt 的细微差别、并把你导向在合规环境中运行的合适 FM 的系统。Amazon Bedrock Agents 使混合系统中的这种分布式系统成为可能。

Amazon Bedrock Agents 让你可以在应用中构建和配置自主 agent。agent 负责编排 FM、数据源、软件应用和用户对话之间的交互。这种编排包括调用 [AWS Lambda](https://aws.amazon.com/lambda) 函数来调用其他 FM 的能力，从而开启了在边缘运行自管理 FM 的可能性。借助这一机制，你可以为受数据驻留要求约束的高监管行业构建分布式 RAG 应用。在混合部署场景中，[Amazon Bedrock](https://aws.amazon.com/bedrock) 可以针对客户 prompt 在指定区域执行部分操作，并将其他操作交给 Local Zone 中自托管的 FM 处理。下面的示例展示了混合 RAG 的高层架构。

## 完全本地 RAG：解决方案深入解析

首先，你需要在 Outpost 机架上为虚拟私有云（VPC）配置一个边缘子网。要在 Outpost 上创建边缘子网，你需要找到要在其上创建子网的 Outpost 的 Amazon Resource Name（ARN），以及该 Outpost 的可用区。创建好互联网网关、路由表和子网关联之后，在 Outpost 机架上启动一系列 EC2 实例来运行你的 RAG 应用，包括以下组件。

- **向量存储** – 为支持 RAG（检索增强生成），在 AWS Outposts 的 EC2 实例（C5 系列）上部署开源向量数据库，例如 ChromaDB 或 Faiss。该向量数据库将存储文档的向量表示，作为本地知识库的关键组件。你所选用的 embedding 模型将用于把文本（文档和查询）转换为这些向量表示，从而实现高效的存储与检索。实际的知识库由原始文本文档及其存储在向量数据库中的对应向量表示构成。要查询该知识库并基于检索结果生成回答，你可以使用 LangChain 把向量搜索检索到的相关文档串接到喂给大语言模型（LLM）的 prompt 中。这种方式可以将相关信息检索并整合进 LLM 的生成过程，用本地、领域特定的知识增强其回答。

- **聊天机器人应用 **– 在第二个 EC2 实例（C5 系列）上部署以下两个组件：一个后端服务，负责接收 prompt 并将请求代理回运行在 Outpost 上的 LLM；以及一个简单的 React 应用，让用户可以向本地生成式 AI 聊天机器人提问。

- **LLM 或 SLM**– 在第三个 EC2 实例（G4 系列）上，通过 [Ollama](https://ollama.com/) 等流行框架部署 LLM 或 SLM 以执行边缘推理。此外，你还可以使用 SageMaker SDK 的 [ModelBuilder](https://docs.aws.amazon.com/sagemaker/latest/dg/how-it-works-modelbuilder-creation.html) 部署到本地端点，例如在边缘运行的 EC2 实例。

可选地，你底层的专有数据源可以存储在 Outposts 上的 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3) 中，或使用运行在带 EBS 卷的 Amazon EC2 实例上的、兼容 Amazon S3 的解决方案。

各组件通过下图所示的流量流相互通信。

![Loc](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/13/local-rag-architecture.png)

该工作流包含以下步骤：

- 用户使用前端应用上传将作为知识库的文档，这些文档存储在 Outpost 机架上的 Amazon EBS 中。应用会将这些文档分块，并发送给 embedding 模型。

- 与本地 LLM API 推理服务器托管在同一 EC2 实例上的 embedding 模型，将文本块转换为向量表示。

- 生成的 embedding 被发送到向量数据库并存储，从而完成知识库创建。

- 用户通过前端应用在聊天机器人界面中输入问题。

- prompt 被转发到本地 LLM API 推理服务器实例，在那里 prompt 被分词，并使用本地 embedding 模型转换为向量表示。

- 问题的向量表示被发送到向量数据库，在那里执行相似度搜索，以从知识库中获取匹配的数据源。

- 本地 LLM 获得查询以及来自知识库的相关上下文后，会处理 prompt、生成回答，并将其发送回聊天机器人应用。

- 聊天机器人应用通过其界面把 LLM 的回答呈现给用户。

要了解更多关于完全本地 RAG 应用的信息，或动手实践示例应用，请参阅我们公开 AWS Workshop 的模块 2：[AWS 混合与边缘服务上的生成式 AI 动手实践](https://catalog.workshops.aws/hybrid-and-edge-generative-ai/en-US)。

## 混合 RAG：解决方案深入解析

首先，你需要配置一个带边缘子网的 VPC，该子网根据用例对应该 Outpost 机架或 Local Zone。创建好互联网网关、路由表和子网关联之后，在 Outpost 机架（或 Local Zone）上启动一个 EC2 实例来运行你的混合 RAG 应用。在 EC2 实例本身上，你可以复用与完全本地 RAG 相同的组件：向量存储、后端 API 服务器、embedding 模型和本地 LLM。

在这一架构中，我们大量依赖 Lambda 和 Amazon Bedrock 等托管服务，因为只有与高度受监管数据对应的特定 FM 和知识库需要位于边缘，编排器本身并不需要。为此，我们将使用一个示例 [FM 驱动的客服机器人](https://github.com/aws-samples/agentsforbedrock-retailagent)把现有的 Amazon Bedrock Agents 工作流扩展到边缘。

在这个客服机器人示例中，我们是一个鞋类零售商机器人，通过类人对话提供购买鞋子的选项，从而为购买鞋子提供客户服务支持。我们还假设，围绕制鞋工艺的知识库属于专有信息，因此驻留在边缘。因此，围绕制鞋的问题将由运行在边缘的知识库与本地 FM 来处理。

为确保用户 prompt 被有效代理到正确的 FM，我们依赖 Amazon Bedrock Agents 操作组（action group）。操作组定义了 agent 可以执行的操作，例如 `place_order` 或 `check_inventory`。在我们的示例中，可以在名为 `hybrid_rag` 或 `learn_shoemaking` 的现有操作组中定义一个额外操作，专门处理那些只能由 AWS 混合与边缘位置应对的 prompt。

作为 agent `InvokeAgent` API 的一部分，agent 会用 FM 解释 prompt（例如“制鞋时皮革是怎么用的？”），并为它应采取的下一步生成逻辑，包括预测操作组中最审慎的操作。在本例中，我们希望 prompt“你好，我想获得一些买鞋的建议。”被导向 `/check_inventory` 操作组，而 prompt“制鞋时皮革是怎么用的？”则可能被导向 `/hybrid_rag` 操作组。

下图展示了这种编排，它由 Amazon Bedrock agent 的编排阶段实现。

![混合 RAG 参考架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/11/hybrid-rag-workflow.png)

要创建这个额外的边缘专用操作组，新的 OpenAPI schema 必须反映新操作 `hybrid_rag`，并用详细的描述、结构和参数来定义该操作组中的这一操作，使其成为一个专门面向仅在特定边缘位置可用的数据域的 API 操作。

使用 OpenAPI 规范定义操作组之后，你可以定义一个 Lambda 函数来编写该操作组的业务逻辑。这个 Lambda handler（见以下代码）可以包含支持函数（例如 `queryEdgeModel`），用于实现每个操作组对应的具体业务逻辑。

```
def lambda_handler(event, context):
    responses = []
    global cursor
    if cursor == None:
        cursor = load_data()
    id = ''
    api_path = event['apiPath']
    logger.info('API Path')
    logger.info(api_path)
    
    if api_path == '/customer/{CustomerName}':
        parameters = event['parameters']
        for parameter in parameters:
            if parameter["name"] == "CustomerName":
                cName = parameter["value"]
        body = return_customer_info(cName)
    elif api_path == '/place_order':
        parameters = event['parameters']
        for parameter in parameters:
            if parameter["name"] == "ShoeID":
                id = parameter["value"]
            if parameter["name"] == "CustomerID":
                cid = parameter["value"]
        body = place_shoe_order(id, cid)
    elif api_path == '/check_inventory':
        body = return_shoe_inventory()
    elif api_path == "/hybrid_rag":
        prompt = event['parameters'][0]["value"]
        body = queryEdgeModel(prompt)
        response_body = {"application/json": {"body": str(body)}}
        response_code = 200
    else:
        body = {"{} is not a valid api, try another one.".format(api_path)}

    response_body = {
        'application/json': {
            'body': json.dumps(body)
        }
    }
```

然而，在与边缘 LLM 对应的操作组中（见下面的代码），业务逻辑不会包含基于区域的 FM 调用，例如使用 Amazon Bedrock API。相反，它会调用客户管理的端点，例如使用 Local Zone 或 Outpost 中托管边缘 FM 的 EC2 实例的私有 IP 地址。这样，Lambda 和 Amazon Bedrock 等 AWS 原生服务就能编排复杂的混合与边缘 RAG 工作流。

```
def queryEdgeModel(prompt):
    import urllib.request, urllib.parse
    # Composing a payload for API
    payload = {'text': prompt}
    data = json.dumps(payload).encode('utf-8')
    headers = {'Content-type': 'application/json'}
    
    # Sending a POST request to the edge server
    req = urllib.request.Request(url="http://<your-private-ip-address>:5000/", data=data, headers=headers, method='POST')
    with urllib.request.urlopen(req) as response:
        response_text = response.read().decode('utf-8')
        return response_text
```

解决方案完全部署后，你可以访问 Amazon Bedrock Agents 控制台上的 chat playground 功能，并提问“鞋子的橡胶鞋跟是如何制造的？”。尽管大多数 prompt 都会只聚焦于订购鞋子的零售客户服务操作，Amazon Bedrock Agents 的原生编排支持会无缝地把该 prompt 导向运行制鞋 LLM 的边缘 FM。

## 结语

本文演示了如何将 Amazon Bedrock Agents 扩展到 Local Zones 或 Outposts 等 AWS 混合与边缘服务，以在受数据驻留要求约束的高监管行业构建分布式 RAG 应用。此外，对于为符合最严格数据驻留要求而进行的 100% 本地部署，我们给出了把知识库、计算和 LLM 汇聚在 Outposts 硬件本身的架构。
