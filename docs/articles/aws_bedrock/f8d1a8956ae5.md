# 使用 Amazon Bedrock 构建多模态生成式 AI 助手，用于预测性维护中的根因诊断

预测性维护是一种策略，它利用设备传感器的数据和高级分析来预测机器可能在何时发生故障，从而可以主动开展维护以避免停机。这使各行业能够减少意外故障、提升运营效率，并延长关键设备的使用寿命。它适用于各种部件，包括电机、风扇、齿轮箱、轴承、输送机、执行器等等。

本文演示如何使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/?gclid=EAIaIQobChMIis-s9tm2iQMVSkn_AR259TXSEAAYASAAEgL3V_D_BwE&trk=36201f68-a9b0-45cc-849b-8ab260660e1c&sc_channel=ps&ef_id=EAIaIQobChMIis-s9tm2iQMVSkn_AR259TXSEAAYASAAEgL3V_D_BwE:G:s&s_kwcid=AL!4422!3!692006004850!e!!g!!amazon%20bedrock!21048268689!159639953975) 上的基础模型（FM）实现预测性维护方案，并以 Amazon 履约中心内的制造设备为案例。该方案适应性很强，可针对其他行业定制，包括石油与天然气、物流、制造业和医疗。

## 预测性维护概述

预测性维护可分为两个关键阶段：传感器告警生成与根因诊断。这两个阶段共同构成完整的预测性维护方法，使干预能够及时有效，从而最大限度减少停机并最大化设备性能。在简要介绍每个阶段之后，我们将详细说明用户如何借助生成式 AI 让第二阶段更高效，帮助维护团队更快解决设备问题。

### 阶段 1：传感器告警生成

该阶段侧重于通过传感器监测设备状态——例如温度和振动——并在检测到异常模式时触发告警。

## 方案概述

在根因诊断与问题解决阶段，告警触发后生成的工单中有超过 50% 的根因仍被标记为“未确定”（Undetermined）。为应对这一挑战，我们开发了一个聊天机器人，用于增强预测性维护的诊断能力，让技术人员更容易发现故障并定位设备问题。该方案显著减少了停机时间，同时提升了整体运营效率。

该方案的关键特性包括：

- **时间序列数据分析与诊断** – 助手处理并分析传感器数据以给出精确诊断，识别模式与异常，支持准确、由数据驱动的故障排查。
- **以主动多轮对话引导的故障排查 **– 助手保留对话历史，实现无缝、具备上下文感知的交互。它以目标为导向，通过主动的多轮对话聚焦设备问题的根因，由系统向用户提出有针对性的问题，收集高效排查所需的关键信息。
- **多模态能力 **– 用户可以把各种格式——手册、图片、视频和音频——上传到助手的知识库，助手能够在这些模态之间理解并回应。这通过 Claude 3 Haiku 和 Claude 3 Sonnet 实现，它们是可通过 [Amazon Bedrock](https://aws.amazon.com/bedrock/?gclid=EAIaIQobChMIis-s9tm2iQMVSkn_AR259TXSEAAYASAAEgL3V_D_BwE&trk=36201f68-a9b0-45cc-849b-8ab260660e1c&sc_channel=ps&ef_id=EAIaIQobChMIis-s9tm2iQMVSkn_AR259TXSEAAYASAAEgL3V_D_BwE:G:s&s_kwcid=AL!4422!3!692006004850!e!!g!!amazon%20bedrock!21048268689!159639953975) 获得的高能力多模态模型。
- **带倒数排名融合的高级多模态 RAG **– 多模态检索增强生成（RAG）使助手能够给出同时包含维修手册中图片和文本的回复。倒数排名融合确保检索到的信息既相关，又在语义上与用户查询对齐。
- **面向安全与合规的 Guardrails **– 助手使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/)，在整个诊断过程中帮助维护安全性、准确性与合规性。这些 guardrails 包含敏感信息和有害内容的过滤器、不当内容阻断，以及帮助预防错误建议的校验步骤。

在接下来的章节中，我们概述实施该方案的关键前置条件，并全面介绍上述每个关键特性，剖析它们的功能、实现方式，以及它们如何促成更快的诊断、更少的停机和更高的整体运营效率。

## 前置条件

要成功构建并集成这一预测性维护方案，必须具备一些基础条件。这些前置条件是确保方案能够有效部署并达成预期效果的必要前提：

- **确定用于预测性维护的关键资产** – 首先判断哪些资产对运营最为关键、一旦意外失效会造成重大中断。优先考虑维修成本高、故障频繁或在生产过程中承担关键角色的设备。
- **采集并记录可用的数据 – **搭建一套系统，以 1 分钟为间隔持续监测振动和温度。建立到 AWS 云端的自动化数据传输，以获得更安全的存储和更高效的分析，使方案能够为每台资产生成准确的洞察。
- **收集设备维修手册** – 获取原始设备制造商（OEM）手册，其中详述每台资产的维护要求、建议的服务间隔和安全操作流程。同时补充资深技师的机构知识。这些信息对于让预测性洞察与实际维护需求保持一致至关重要。
- **维护历史维护记录**（可选，但强烈建议）– 保留以往维护活动与工单的准确记录。虽然可选，但拥有历史数据有助于改进预测模型，并提升系统在预测潜在故障方面的准确率。

具备这些基础之后，接下来的章节将探讨聊天机器人中可用的各项功能，以实现更快、更智能、更可靠的根因诊断。

## 时间序列分析与引导式故障排查对话

时间序列分析和引导式对话分为六个关键步骤，如下图所示。

[![温度与振动分析工作流，结合 ISO 标准校验](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/08/ML-17789-image-3-uploadSensorDataAndClassify.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/08/ML-17789-image-3-uploadSensorDataAndClassify.jpg)

步骤如下：

- 用户在 Streamlit 应用中上传包含传感器数据（振动和温度数据）的 Excel 文件。数据通过基于 Python 的辅助脚本进行提取与处理，为后续分析打下基础。
- 系统使用 Matplotlib 绘制温度与振动随时间变化的曲线，并用红色竖线突出显示偏离正常模式的偏差，指示设备可能存在潜在问题。这一可视化步骤确保异常清晰可辨。
- 系统通过将振动数据与 ISO 振动标准（ISO 20816-1）比较来评估，该标准依据设备等级设定振动水平的国际基准。这些基准被称为评估区间（evaluation zone），为以速度均方根（VRMS）度量的振动设定固定阈值。VRMS 表示一段时间内振动的平均强度，有助于准确判断资产是正常运行还是出现异常振动。当资产从 B 区进入 C 区时生成 Warning（警告）。当资产从 C 区进入 D 区时生成 Alarm（告警）。

```
def classify_vibration(class_number, vibration_value):
    # Classification thresholds for each machine class
    if class_number == "I":  # Small machines (<15kW)
        if vibration_value < 0.71:
            return "A (Very Good)"
        if vibration_value < 1.8:
            return "B (Satisfactory)"
        if vibration_value < 4.5:
            return "C (Warning)"
        else:
            return "D (Alarm)"
    elif class_number == "II":  # Medium machines (15–75kW)
        if vibration_value < 1.12:
            return "A (Very Good)"
        if vibration_value < 2.8:
            return "B (Satisfactory)"
        if vibration_value < 7.1:
            return "C (Warning)"
        else:
            return "D (Alarm)"
    #### ....
```

- 基于传感器数据，系统把每个时间戳的振动等级分类为 Very Good、Satisfactory、Unsatisfactory 或 Severe，从而给出设备健康方面的洞察。
- 从分析中得出结论，例如识别出振动正常，但在某个特定时间范围内触发了高温告警。
- 使用 Python 发起引导式故障排查对话，基于分析结果构造初始诊断问题。随后流程转交给由生成式 AI 驱动的大语言模型（LLM），它扮演虚拟技师的角色，通过多轮对话进一步推进诊断过程。LLM 会根据用户回答做出调整，类似于与专业医生问诊，提供有针对性的指导以解决问题。凭借对先前回答的记忆，LLM 在整个交互过程中给出更准确、更贴合需要的故障排查建议。此外，还实施了 guardrails 以让对话保持聚焦，提供安全性、适当性和相关性，最终提升诊断指导的质量与可靠性。

## 多模态能力

为增强诊断能力并提供全面支持，系统允许用户通过多种输入模态进行交互。这种灵活性确保技术人员可以用最适合其需求的形式沟通，无论是图片、音频还是视频。借助生成式 AI，系统能够分析并整合这三种模态的信息，给出更深入的洞察和更有效的故障排查方案。

系统支持以下多模态输入：

- **图片** – 上传设备或特定部件的图片，进行视觉分析和故障检测
- **音频 **– 录制并上传语音描述或机器声音，让系统转写并分析语音输入或异常噪声
- **视频 **– 提供记录设备运行或故障的视频，支持逐帧分析和音视频一体化诊断

在接下来的章节中，我们将探讨这些输入各自如何处理，以及如何整合进系统的诊断工作流，从而提供整体的维护方案。

### 用于诊断评估的图像分析

助手利用多模态能力分析图片，这在技术人员需要上传退化或故障部件照片时尤其有用。使用 Amazon Bedrock 上的 Anthropic Claude Sonnet 3.5 等多模态 LLM，系统处理图像并生成详细描述，帮助理解设备状态。例如，操作员可能上传一张磨损轴承的照片，助手可以给出可见磨损模式的文字摘要，例如变色或裂纹，从而无需人工判读即可定位问题。

该工作流包含以下步骤：

- 用户通过助手界面上传图片——例如一张磨损部件的照片。
- 图片会被调整尺寸或处理，以满足模型的输入约束，确保符合文件大小和分辨率限制。
- 图片会被转换为 base64 格式，从而可以标准化地作为多模态 LLM 输入载荷的一部分进行传输。
- 使用预定义的 prompt 指示模型描述图片，例如：“描述这张图片所示部件中任何可见的缺陷或异常。”
- 模型生成基于文本的图片描述。例如，如果上传的图片显示一个有表面裂纹和变色的轴承，模型可能输出类似：“该部件显示出磨损迹象，可见表面裂纹以及与热相关的变色。”

分析图片的能力为技术人员提供了一种直观方式，可以在传感器数据之外诊断问题。这种视觉上下文与助手的知识库结合，可实现更准确、更高效的维护操作，减少停机并提升整体运营效率。

该工作流包含以下步骤：

- 技术人员可以录制一段音频，例如描述设备当前状态的语音备忘，或关于某个维护问题的提问。系统支持直接在助手界面内快速录音。
- 音频录制完成后，会经过自动语音识别（ASR）系统（[Amazon Transcribe](https://aws.amazon.com/pm/transcribe/?gclid=EAIaIQobChMI84ye0tm2iQMVOEL_AR1kzSNREAAYAiAAEgI2M_D_BwE&trk=8217174a-004c-4464-9374-7f64e3ed195f&sc_channel=ps&ef_id=EAIaIQobChMI84ye0tm2iQMVOEL_AR1kzSNREAAYAiAAEgI2M_D_BwE:G:s&s_kwcid=AL!4422!3!652240143553!e!!g!!amazon%20transcribe!19878157838!144181888781)）处理，将话语转写为文本。转写结果准确呈现所说内容，用作后续分析或对话的输入。
- 转写完成后，文本会呈现给技术人员，让他们检查转写内容并确认其准确表达了自己的意图。
- 转写可用后，对话由 LLM 发起并引导，技术人员可以提出后续问题或请求进一步分析。例如，他们可能会问：“基于这段音频，你能推荐解决问题的后续步骤吗？”转写文本会与用户的问题一起传给 LLM，并在 Amazon Bedrock guardrails 的约束下生成回复。这些 guardrails 确保答案保持相关、适当和安全，在整个交互过程中提供聚焦、可靠的洞察或指导。
- 系统还会保留对话上下文，支持多轮交互。这意味着技术人员后续提出的问题会以初始音频录制和转写为背景，从而得到更准确的回复并持续排查。

		# Set the API endpoint
		url = 'https:' + read_key_value(config_filename, "api_endpoint_amazon_transcribe")

		# Make the POST request to your API Gateway
		response = requests.post(url, json={'audio_file_uri': s3_uri})

		result = response.json()
		return result.get('transcript_uri', 'No transcription found.')
	
```

下面是一个用于处理音频转写作业的 [AWS Lambda](https://aws.amazon.com/lambda) 函数。该函数使用 Amazon Transcribe 处理通过 S3 统一资源标识符（URI）提供的音频文件，监控转写作业状态，并返回生成的转写 URI。该函数针对异步转写任务和健壮的错误处理进行了优化：

```
import boto3
	import json
	import time

	transcribe = boto3.client('transcribe')

	def lambda_handler(event, context):
		# Log the incoming event data
		print("Received event: " + json.dumps(event, indent=2))

		try:
			# Extract the body from the event
			body = json.loads(event.get('body', '{}'))

			# Extract the audio_file_uri from the body
			audio_file_uri = body.get('audio_file_uri')

			if not audio_file_uri:
				return {
					'statusCode': 400,
					'body': json.dumps({'error': 'audio_file_uri is missing'})
				}

			# Assuming the S3 URI is in the format s3://bucket/key
			s3_bucket = audio_file_uri.split('/')[2]  # Extract the bucket name
			s3_key = '/'.join(audio_file_uri.split('/')[3:])  # Extract the key

			job_name = f"transcription-job-{int(time.time())}"

			# Start the transcription job
			response = transcribe.start_transcription_job(
				TranscriptionJobName=job_name,
				Media={'MediaFileUri': audio_file_uri},
				MediaFormat=s3_key.split('.')[-1],  # Extract file format
				LanguageCode='en-US'
			)

			# Poll for completion...
			while True:
				status = transcribe.get_transcription_job(TranscriptionJobName=job_name)
				if status['TranscriptionJob']['TranscriptionJobStatus'] in ['COMPLETED', 'FAILED']:
					break
				time.sleep(5)

			if status['TranscriptionJob']['TranscriptionJobStatus'] == 'COMPLETED':
				transcript_uri = status['TranscriptionJob']['Transcript']['TranscriptFileUri']
				return {
					'statusCode': 200,
					'body': json.dumps({'transcript_uri': transcript_uri})
				}
			else:
				return {
					'statusCode': 500,
					'body': json.dumps({'error': 'Transcription job failed.'})
				}

		except Exception as e:
			# Handle any other errors
			return {
				'statusCode': 500,
				'body': json.dumps({'error': str(e)})
			}
```

这段代码从 S3 URI 获取音频文件，使用 Amazon Transcribe 转写，并返回转写结果。转写结果此后可用于助手交互，让技术人员用语音记录观察，并即时获得反馈或指导。它简化了故障排查流程，在适合免手操作的环境中尤其有利。

### 通过多模态分析处理视频数据

为支持这一功能，我们开发了一套自定义视频处理工作流，用于提取音频和视觉两部分以进行多模态分析。虽然这种方法在开发当时是必要的，但更近期的进展——例如 Amazon Bedrock 中 [Amazon Nova](https://aws.amazon.com/ai/generative-ai/nova/understanding/) 的原生视频理解能力——如今为希望集成类似功能的组织提供了更简洁、可扩展的替代方案。

- 系统按固定间隔（例如每三秒）抽取单帧视频画面，并转换为 base64 编码的帧。这样可以高效处理和分析视频内容。每个抽取出的帧都会经过多模态 LLM，由其生成该帧的说明文字。这有助于概括视频的视觉内容，聚焦设备状态、磨损或异常运动等关键方面。为保持视频帧与语音内容的对应关系，系统使用抽帧时间戳，并将其映射到转写音频中相应的时间范围。这促成了跨视觉与听觉输入的一致多模态解读。
- 系统充当基于 LLM 的路由器，也就是根据分类把查询导向合适的处理路径。路由器判定查询类型并据此路由，以提供准确高效的回复。在此场景中，系统根据技术人员与视频的交互方式对其查询分类。查询可归入不同类别，例如：**视频说明** – 如果技术人员请求对视频内容进行总结或描述。**问答** – 如果技术人员基于视频提出具体问题（例如“根据视频，这个部件有什么问题？”）。**其他** – 如果查询不属于标准类别但仍需处理（例如更通用的请求）。
- 当查询和说明文字就绪后，系统使用 LLM 基于处理后的视频和音频内容生成答案。这使助手能够就设备状态或后续解决步骤给出准确、具备上下文感知的回复。生成的回复会指导技术人员完成故障排查步骤，基于视觉与听觉输入给出解决所检测问题的详细指令。答案内置 guardrails，以帮助保持指导的质量、安全性和相关性。

## 用于综合判定解决方案的多模态 RAG

多模态 RAG 让技术人员可以与手册文档、以往培训文件或诊断记录组成的数据库交互。借助多模态能力，技术人员不仅能够访问手册中的文本，还能访问有助于诊断和解决问题的相关图表或图片。以下截图展示了该功能的一个示例。

以下步骤逐步说明系统如何处理文本与图片数据，以促成全面的检索与回复生成：

### 创建文档 embedding

第一步是从 PDF 手册这类文档中提取文本和图片，生成 embedding，以便后续检索相关信息。下图展示了该过程的工作方式。

[![PDF 文档分析架构，并行处理文本提取与图像分析](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/08/ML-17789-image-9-PDFExtraction.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/08/ML-17789-image-9-PDFExtraction.jpg)

该工作流包含以下步骤：

- 使用 PyMuPDF 库从 PDF 的每一页提取文本数据。这使方案能够捕获结构化数据（例如表格）和非结构化内容用于 embedding。每个提取出的文本片段使用 Amazon Titan v2 模型转换为 embedding，并存入 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 以便高效检索。
- 图片同样从 PDF 每一页中以类似方式提取，并通过过滤去除过小或不相关的图片。每张图片由 Amazon Bedrock 上的 Anthropic Claude Sonnet 3.5 等多模态 LLM 处理，生成详细描述，其中包含可见元素以及页面周边文本提供的上下文。系统保存这些图片，并基于描述生成 embedding。收集的图片元数据包括：图片名称、图片在 PDF 中的位置、图片描述的 embedding，以及文档中图片周围的上下文文本。

通过不仅捕获图片描述，还捕获周围的上下文文本，系统对图片的相关性和含义获得更全面的理解。这种方法提升了检索准确率，并确保图片在其更广泛的文档语境中被正确解读。

### 检索与生成

在检索与生成方面，系统区分文本检索与图片检索，以确保语义文本上下文和视觉信息都被有效纳入最终回复。这种方法让技术人员获得同时利用文字洞察与视觉辅助的更全面的答案，提升整体故障排查流程。

### 文本检索与生成

从文本开始，我们使用倒数排名融合（reciprocal rank fusion），这种方法确保检索结果既相关，又在语义上与用户查询对齐。倒数排名融合的工作方式是：把单个用户查询转换为由 LLM 生成的多个相关查询，每个查询检索出一组不同的文档。这些文档使用倒数排名融合算法重新排序，确保最重要的信息被优先考虑。下图说明了这一过程。

[![基于 prompt 的问答工作流，使用向量存储、文档排序和大语言模型](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/08/ML-17789-image-10-ReciprocalRankFusion.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/08/ML-17789-image-10-ReciprocalRankFusion.jpg)

该工作流包含以下步骤：

- 用户输入问题或查询。例如：“为什么我的输送机电机振动异常？”
- 查询连同用于生成多个相关搜索查询的 prompt 一起发送给 LLM。通过生成这些相关查询，系统实现全面的信息检索。举例来说，最初用户查询可拆分为：查询 1：“输送带异常振动的可能原因有哪些？”查询 2：“针对高振动水平的输送机电机故障排查，有哪些步骤？”查询 3：“输送系统的振动阈值和告警设置是什么？”查询 4：“有振动问题的输送机电机的维护历史是什么？”

        "max_tokens": max_tokens,

    raw_queries = generate_queries_pipeline.invoke({"question": question})
```

- 生成的查询被发送到语义搜索检索器，以从向量数据库中查找相关文档。对每个查询，检索器基于 embedding 相似度产出一份相关文档的排序列表。
- 排序结果使用倒数排名融合（RRF）公式重新排序（见下图）。对于集合 Q 中的每个查询 q，公式评估文档 d 在该特定查询下的排名表现（表示为 rq(d)）。加上常数 k 有助于控制单个查询对总分的影响，因为它能防止单个查询对最终排名产生不成比例的影响，使各相关查询的贡献更均衡。分数被累加。这意味着如果一个文档 d 在多个相关查询中排名都很高，它就会获得更高的 RRF 分数。

[![用于文档相关性打分的倒数排名融合公式](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/08/ML-17789-image-10-ReciprocalRankFusion-1.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/08/ML-17789-image-10-ReciprocalRankFusion-1.jpg)

- 生成模型使用排名最高的文档生成最终答案，给出诊断输送带异常振动根因的指导。

### 图片检索与生成

对于基于图片的查询，系统遵循独立的检索流程，确保视觉信息也被纳入回复。下图展示了这一过程的工作方式。

[![基于 embedding 的图像检索示意图，带余弦相似度过滤](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/08/ML-17789-image-12-ImageSelection.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/08/ML-17789-image-12-ImageSelection.jpg)

该工作流包含以下步骤：

- 当用户输入查询时，系统首先把该查询转换为 embedding，这是一种捕获查询语义含义的数值表示。该 embedding 作为参照点，用于识别相关的图片描述。
- 系统计算 prompt embedding（上一步生成）与数据库中存储的图片描述 embedding 之间的余弦相似度，以检索最相关的图片。在本例中，对于关于输送机电机振动的查询，相关图片可能包括电机部件示意图、振动模式的可视化表示，或描绘设备不对中的图片。
- 计算相似度分数后，系统过滤结果，仅保留分数足够高的图片。该过滤阈值经验性地设为 0.4，以确保只有与用户查询高度契合的最相关图片进入后续分析。这一步有助于防止纳入不相关或关联很弱的图片，保持回复的准确性。
