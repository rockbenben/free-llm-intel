# 用自动生成的过滤器提升 Amazon Bedrock 中的合同搜索准确度

企业依赖大量复杂的法律协议来做出关键业务决策——确定权利、续约选项、地域限制和合规义务。在娱乐与传媒等行业，组织要跨多个司法辖区管理数千份合同，这项工作在很大程度上仍是手工完成：耗时、昂贵且难以扩展。

我们基于 AWS 的 AI-Driven Annotation（AIDA）方案通过把非结构化合同转化为可检索、可执行的洞察来应对这一挑战。AIDA 让用户可以在大型合同库上以自然语言提问——但要给出精确答案，仅有语义搜索远远不够。法律文档高度依赖上下文，而基于检索增强生成（RAG）的系统召回的内容往往超出语言模型能够有效处理的范围。如果对召回哪些片段缺乏精细控制，又缺少足够的文档级上下文，重要条款就有被忽略或误读的风险。

本文概要介绍 AIDA 的工作方式，以及它如何帮助应对这些挑战——让用户落在正确的合同、正确的法律上下文与正确的访问边界之内。具体而言，我们会探讨 AIDA 如何结合隐式过滤、显式过滤以及 Amazon Bedrock Knowledge Bases 中的元数据增强分块，大幅提升合同搜索的准确度。

## 方案概览

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/12/Screenshot-2026-08-11-at-11.45.38 PM.png)

参考架构图展示了 AIDA 如何基于 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 构建 RAG 架构，形成一个智能文档查询系统。组件之间的数据传输通过 HTTPS/TLS 1.2+ 实现传输中加密，包括把文档上传到 Amazon Bedrock Knowledge Bases、对嵌入模型的 API 调用、向量数据库查询，以及把响应交付给客户端应用。[AWS 责任共担模型](https://aws.amazon.com/compliance/shared-responsibility-model/) 适用于存储在 Amazon Bedrock 中的数据。实现遵循一套系统化的工作流：

### 数据摄取流程

**步骤 1：文档摄取与元数据配置**

架构从文档摄取开始：合同连同结构化元数据文件一起同步到 Amazon Bedrock Knowledge Bases。元数据应包含关键的合同属性，例如当事方、生效日期、终止日期、司法辖区，以及其他能够让下游具备强大过滤能力的关键属性。

**步骤 2：分块机制实现**

知识库配置阶段实现了一套精细的分块机制，把合同切成语义上有意义、且针对检索优化的片段。这种分块策略让每个片段既带有足够的上下文，又保持足够精简以便高效处理。摄取时提供的元数据在系统实施智能过滤的能力中起关键作用，尤其是通过隐式过滤机制——这正是该架构区别于标准 RAG 实现的地方。

**步骤 3：向量数据库存储**

文档摄取并处理完成后，系统把文档片段转换成向量嵌入，并存入 Amazon Bedrock Knowledge Bases 提供的若干向量数据库选项之一，例如 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 或 [Amazon S3 Vectors](https://aws.amazon.com/s3/features/vectors/)（Amazon Simple Storage Service（Amazon S3）的一项能力），两者都应启用静态加密。该向量数据库是语义搜索的基础，使系统能够找出概念上相似的内容，而不是仅依赖关键词匹配。

对知识库的访问和模型调用由 [AWS Identity and Access Management（IAM）](https://aws.amazon.com/iam/?c=sc&sec=srvm&trk=7ad0b48b-3532-4cda-87b0-c63aef99e9cc&sc_channel=ps) 策略治理，并启用 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/?nc2=type_a) 日志，以留存用于合规的审计轨迹。

在安全方面，AIDA 使用基于角色的访问控制，在 AIDA 的应用层通过项目范围角色以 AWS IAM 策略强制执行，从而限制每个用户能做什么。

### 用户交互流程

**步骤 4：生成查询嵌入**

当用户提交查询时，AIDA 使用 Amazon Bedrock Guardrails 帮助防范 prompt 注入与数据泄露；随后系统走一条增强的 RAG 工作流，首先使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 的嵌入模型把查询转换成嵌入。这一转换使系统能够在用户的问题与已存储的文档片段之间做语义比较。

**步骤 5：隐式与显式过滤**

在执行语义搜索之前，系统会同时应用隐式与显式过滤机制——这是显著提升检索准确度的关键创新。隐式过滤会在执行向量搜索前自动施加基于元数据的条件，例如按生效日期区间或特定合同当事方过滤。这种两阶段做法先用元数据约束收窄搜索空间，再在过滤后的子集内做语义相似度匹配，从而让召回的文档既上下文相关、又满足特定的业务条件。

**步骤 6：语义搜索与文档召回**

向量数据库依据语义相似度分数召回最相关的文档片段，通常使用余弦相似度指标找出与用户查询最接近的匹配。该语义搜索只在过滤后的文档子集上运行，从而在结果中提供高精确度与相关性。

**步骤 7：prompt 增强**

随后，召回的片段被用来增强用户原始查询，构成一个精心格式化的 prompt，把用户的问题与相关合同节选、元数据上下文组合在一起。这个增强后的 prompt 为大型语言模型（LLM）提供了生成精确且有依据的回答所需的具体信息。

**步骤 8：生成 LLM 响应**

增强后的 prompt 经由 Amazon Bedrock 传给 LLM，由它生成有实际合同文档作为依据、且上下文精确的回答，而不是仅依赖模型的训练数据。这种方法有助于让回答反映组织合同的真实内容。

此外，AIDA 使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 施加内容过滤、敏感信息（PII）防护和 prompt 安全控制，使响应保持安全并符合企业与法律标准。

**步骤 9：带来源溯源的响应交付**

最终响应通过 Retrieve API 返回给用户，因此答案不仅相关，还可以溯源到具体的源文档。这种可溯源性能减少幻觉这一 LLM 的常见问题，并提供可验证的合同洞察，让用户在关键业务决策中放心使用。

## 调优 RAG

在开发用于法律合同分析的 RAG 系统时，核心挑战之一是管理潜在相关信息的体量。请看下面这个问题：

“*请找出任何受加利福尼亚州法律管辖且已过期的许可协议？这些协议如何续约？*”

这样的查询可能命中跨多个文档的数百个相关文本片段。用 RAG 的术语来说，这些节选通常被称为候选片段（candidate chunk）。

当 Amazon Bedrock 执行语义搜索来查找相关文档节选时，它的设计是返回 top k（最多 100）个相关候选片段。被过滤掉的其余候选片段可能包含关键上下文。因此，LLM 的回答可能不完整、漏掉关键信息，甚至不准确。

法律文档结构高度规范，且深度依赖上下文。在我们的例子中，一份加州许可协议里的续约条款，可能与受其他司法辖区管辖的许可协议中的续约条款运作方式不同。如果召回步骤没有正确过滤出许可协议和加州管辖法律，系统可能返回无关的合同，例如服务协议、NDA，或受其他州法律管辖的协议。即便这些文档含有到期或续约的措辞，它们也回答不了最初的问题。有效的元数据过滤因此变得不可或缺：把候选池收窄到最相关的子集，让后续的 LLM 调用获得给出更精确、更完整回答所需的上下文。

需要指出的是，尽管这些召回改进显著提升了准确度，AI 生成的合同解读在使用于业务决策之前，始终应由合格的法律专业人士复核。AIDA 的定位是决策支持工具，可以增强而不是取代法律专业能力。

有助于精细调优 RAG 的两种方式——隐式过滤与显式过滤——我们接下来分别讨论。

## 隐式过滤

隐式过滤是 Amazon Bedrock Knowledge Bases 中的一项强大能力，它让你可以基于元数据属性自动过滤搜索结果，而无需在每个查询中写出显式的过滤表达式。这种做法让系统在执行语义搜索之前就依据文档元数据对向量库做预过滤，把搜索空间显著收窄到最相关的文档。

隐式过滤机制通过两阶段过程运作：

**阶段 1：元数据预过滤**

在执行语义相似度搜索之前，系统会自动施加基于元数据的条件。你可以为知识库中的每份文档提供一个自定义元数据文件（每份文档最大 10 KB），其中包含生效日期、文档类型、涉及当事方，或与你的用例相关的自定义字段等属性。

**阶段 2：语义搜索**

通过元数据过滤器收窄文档集合之后，系统仅在这个过滤后的子集内执行向量相似度搜索。这有助于减少噪声与无关信息，同时提升召回准确度。

## 显式过滤

显式过滤在应用层一致地施加，与用户输入无关。这种做法有助于让搜索结果始终符合业务策略、合规要求和组织约束，而不是完全交给检索引擎自行解释。因此显式过滤器可以充当一道防护，帮助确保每个查询都遵守关键边界。

常见用例包括：

- 应用层约束 – 依据预定义的系统规则限制检索结果，地域限制 – 用于限制特定区域的用户只能访问符合当地法规的文档（例如欧洲用户仅限访问 EU 范围内的合同）。
- 时间约束 – 只返回特定时间范围内的文档（例如过去两年内有效的合同）。
- 分类与敏感度 – 只把搜索结果限制在带有必需保密级别或分类级别的文档上。

我们的显式过滤示例：

```
{
  "andAll": [
    { "listContains": { "key": "region", "value": "Germany" } },
    { "stringEquals": { "key": "confidentiality_level", "value": "Public" } }
  ]
}
```

## 超越过滤：用元数据值增强片段

隐式与显式过滤虽然收窄了候选片段池，但它们并不会自动把文档元数据所描述的结构化文档级上下文提供给 LLM。

元数据指的是在原始文本之外描述文档的结构化属性。这些属性在文档摄取与索引之后生成。缺少这些元数据值和上下文，模型可能生成不完整或不够精确的回答，在涉及大量彼此相似且本身复杂的合同的场景下尤其如此。

对于法律合同分析，常见的元数据字段包括：

- 合同类型（例如许可协议）
- 管辖法律（例如加利福尼亚州）
- 生效日期
- 到期日期
- 当事方
- 业务单元
- 保密级别

这个结构化层支撑过滤、策略执行和更丰富的推理。

让我们回到那个引导性问题：

“*请找出任何受加利福尼亚州法律管辖且已过期的许可协议？这些协议如何续约？*”

假设某个召回的片段包含以下条款：

*“本协议将自动续期，每次续期一年，除非任何一方在到期日前至少 60 天发出不续约的书面通知。”*

如果把这个条款交给 LLM 时没有附带文档级的相关元数据值，模型就无法判断以下事项：

- 该协议是否为许可协议。
- 它是否受加利福尼亚州法律管辖。
- 它是否已经到期。
- 实际的到期日期。

缺少这些元数据值，模型可能生成不完整或不够准确的回答。

为弥补这一局限，我们用文档级元数据值增强候选片段。我们没有为每个片段都重复一份元数据（那会浪费输入 token），而是先把片段按文档分组，然后只附加一次相关元数据。这让每个片段获得更丰富的上下文，帮助 LLM 更有效地推理，从而产出更准确、更一致、更可靠的输出。

最后，需要认识到改进效果的好坏取决于我们所选元数据的相关性与恰当性。当查询与可用元数据相匹配时，过滤与增强效果最好；反之，与这些元数据值无关的查询未必能获得同样的收益。因此，精心的设计与审慎的元数据字段选择，是让这种方法发挥最大作用的关键。

## 评估过滤与增强的影响

为了评估过滤与元数据增强的影响，我们用那个引导性问题做了测试：

“*请找出任何受加利福尼亚州法律管辖且已过期的许可协议？这些协议如何续约？*”

实验在 [Contract Understanding Atticus Dataset（CUAD）](https://www.atticusprojectai.org/cuad)（许可与联合品牌协议）上进行。每次测试的召回深度设为 top-k = 15。我们比较了四种逐级增强的配置。

- **基线 RAG（无过滤、无元数据）。** 在基线设置中，召回完全依赖语义相似度。系统在多个文档中召回了 55 个潜在候选条款。然而，只有一小部分相关上下文进入传给模型的前 15 条结果。
 观察：   模型正确识别出一份已过期协议（Snap/United）。续约条款只得到部分描述。回答缺乏信心，也未完全基于上下文。
- **仅显式过滤。** 接下来我们施加显式过滤器（例如把结果限制为美国合同）。这缩小了候选池，但准确度并未稳定提升。
 观察：   有一份协议被错误地判定为已过期。续约条款被误读。  单靠过滤收窄了搜索空间，但未提供足够的结构化上下文来支撑精确推理。
- **隐式与显式过滤。** 我们随后把从查询推导出的过滤器（加州法律）与应用层约束（美国合同）组合起来。这减少了相互竞争的文档数量，改善了上下文聚焦。
 观察：   模型识别出了正确的协议。但它犹豫于明确其是否已过期。续约机制虽被描述，措辞却相当谨慎。  过滤提升了召回精度，但不确定性依然存在。
- **过滤与元数据增强。** 最后，我们用文档级元数据（如管辖法律、到期日期和合同类型）增强召回的片段。
 观察：   系统仅正确地把 Snap/United 识别为已过期。续约条款得到了清晰准确的解释。回答同时基于条款文本与结构化属性。  该配置产出了最准确、最有把握的输出。

| **配置** | **候选池（n）** | **覆盖率（15/k）** | **识别出的已过期协议** | **续约条款说明** | **回答质量** |
| --- | --- | --- | --- | --- | --- |
| 基线 RAG | 55 | **27.3%** | 正确识别出 *Snap/United*（已于 2000/12/31 过期） | 续约细节不完整 | 部分正确 – 找到过期，但依据薄弱 |
| 仅显式过滤 | 40 | **37.5%** | 误判为已过期 | 续约条款被误解 | 不精确 |
| 隐式与显式过滤 | 20 | **75.0%** | 识别出 *Snap/United*，但仅认定为「可能已过期」 | 描述了续约机制 | 喜忧参半 – 对是否过期含糊其辞 |
| 隐式与显式过滤 + 元数据增强 | 20（+ 元数据） | **75.0%** | 仅正确识别出 *Snap/United* 已过期 | 对其他协议的续约条款解释清晰 | 最可靠 – 精确且基于条款 |

## 结语

本文展示了 AIDA 如何借助 AI 帮助客户评估法律文档。具体来说，我们介绍了 AIDA 如何利用显式与隐式过滤，以及用元数据值增强片段，来改进 RAG 的结果、提升准确度。

通过把这些控制直接嵌入召回 pipeline，AIDA 能够为用户提供源自其有权访问的合同的洞察，同时保留做出有把握决策所需的法律与业务上下文。最终得到的是一套务实、可直接用于企业的合同情报方案：减少人工复核工作量、提升回答质量，并帮助组织释放合同数据的整体价值。
