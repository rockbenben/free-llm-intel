# 在AWS上实现Claude Platform多环境访问

你需要从三个环境发起 Claude Platform on AWS (CPonAWS) 推理：AWS 上的生产工作负载、用于本地迭代的开发者笔记本，以及其他云服务商或本地持续集成与持续交付（CI/CD）流水线上的外部服务。每个环境的身份验证要求各不相同，但都应共用一份订阅，并在生产流量与开发流量之间实现 workspace 级隔离。对于还有更多环境的组织，可为每个团队或工作负载各建一个 workspace，并对每个 workspace 重复这套跨账户 role 模式。

本文会带你走完整个配置过程。你将在组织内部署一个专用的 AI Services 账户，为 AWS 工作负载配置跨账户 SigV4；还会为开发者生成 workspace 级的 API key，并为外部环境接通 OIDC 联合。每一步都配有 CLI 命令、控制台操作说明或代码片段。如果你正在评估哪种账户结构适合自己的组织、或者哪条身份验证路径契合你的工作负载，请参阅相关的 [架构模式](https://builder.aws.com/content/3FHxzkL7fPp6EmkRIjVkXyau4YF/architecture-patterns-for-claude-platform-on-aws) 与 [身份验证路径](https://builder.aws.com/content/3I6LCdWZzOJL1qb1f18gnvxMr0U/authentication-paths-for-claude-platform-on-aws) 两篇文章。本文从这些决策收尾处接着往下讲：给出一份完整的、分步的实现。

## 架构

专用 AI Services 账户模式把 CPonAWS 订阅放进组织内一个专用的 AI Services 关联账户里。这个账户持有订阅、workspace、API key 和跨账户 role。工作负载账户不直接碰订阅：它们代入 AI Services 账户里的 role 来发起推理调用。最终形成一个三账户结构：一个负责计费与治理的付款方（管理）账户、一个承载 CPonAWS 订阅与 workspace 的 AI Services 账户，以及一个或多个通过跨账户 role 消费推理的工作负载账户，如下图所示。

我们将配置三种访问模式：

- 通过跨账户 SigV4 接入的 AWS 工作负载账户：工作负载账户中托管在 Amazon Elastic Kubernetes Service (Amazon EKS) 上的 pod 代入 AI Services 账户里的一个 role，随后发起经 SigV4 签名的推理调用。无需存储 API key，也无需轮换密钥。
- 通过 workspace 级 API key 接入的开发者笔记本：一把锁定到开发 workspace 的长期 API key。开发者在本地用标准 Anthropic SDK 使用它。
- 通过 OpenID Connect (OIDC) 联合与短期密钥接入的外部工作负载：托管在 AWS 之外的工作负载通过 OIDC 完成身份验证、拿到临时 AWS 凭证，再生成一个短期 token，在完全不保留持久凭证的情况下发起推理调用。

## 前提条件

开始之前，请确认你已具备：

- AWS Organizations 中的一个组织，其中包含： 一个付款方（管理）账户。一个用于 AI Services 订阅的 AWS 关联账户（将承载 CPonAWS 订阅）。一个用于承载工作负载的 AWS 关联账户（例如 “Prod”）。
- 已安装 AWS Command Line Interface (AWS CLI) v2，并为这两个账户配置了命名 profile。
- Python 3.12+，并安装以下包：anthropic[aws]、boto3、token-generator-for-aws-external-anthropic。

## 分步指南

本走查分为四个部分。每部分配置架构的一层：CPonAWS 订阅与 workspace 结构、面向 AWS 工作负载的跨账户 SigV4 访问、面向开发者的 workspace 级 API key，以及面向外部环境的 OIDC 联合。请按顺序完成；每一部分都建立在前一部分所创建资源的基础之上。

## 第 1 部分：设置 AI Services 账户

按照 [介绍 Claude Platform on AWS](https://aws.amazon.com/blogs/machine-learning/introducing-claude-platform-on-aws-anthropics-native-platform-through-your-aws-account/) 指南，把你的 AI Services 账户订阅到 CPonAWS。订阅完成后，创建两个 workspace 来隔离生产流量与开发流量：

- 进入 AI Services 账户的 AWS Management Console，导航到 Claude Platform on AWS。
- 导航到 **Access**，以 Admin 身份登录。
- 在 Claude Console 中，点击左上角的下拉菜单，选择 **Create Workspace**。输入名称 production，然后选择 **Create**。

![Claude Console 仪表板，左上角展开了 workspace 菜单并显示 Create Workspace 选项](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/21/ML-21203-3.png)

图 3：展示如何创建 workspace 的 Claude Console 仪表板

- 记下 workspace ARN（例如 `wrkspc_PROD`）。
- 重复操作，创建第二个名为 development 的 workspace（例如 `wrkspc_DEV`）。

**提示**：现在就把两个 workspace ARN 都记下来，本指南后面的 IAM policy 和代码都会引用它们。workspace 创建在特定的 AWS Region 中，你的 API 调用必须指向与之匹配的 Regional endpoint（例如 `aws-external-anthropic.us-east-1.api.aws`）。请注意，决定 API endpoint 的是 workspace 所在的 Region，而不是推理实际运行的位置；推理地域由 Claude Console 中 workspace 的 Security 设置单独控制，当前选项为 “US” 和 “Global routing”。对短期密钥而言，这一点在生成与使用两端都会强制校验：token 只在生成它的那个 Regional endpoint 上有效。长期 API key 不受 Region 锁定。关于支持的 Region 与可用模型，请参阅 Claude Platform on AWS User Guide 中的 [支持的 Region 和模型](https://platform.claude.com/docs/en/about-claude/models/overview)。

## 第 2 部分：面向 AWS 工作负载的跨账户 SigV4

本节配置 Workload 账户中的一个 EKS pod（或其他工作负载），让它通过 SigV4 签名发起推理调用。该工作负载代入 AI Services 账户里的一个 role，后者只授予对生产 workspace 的访问权限。

### 2.1 创建跨账户 role（AI Services 账户）

首先，在 AI Services 账户中创建 trust policy 文件。它允许 Workload 账户中某个特定的 role 代入这个跨账户 role。

- 进入 AI Services 账户的 AWS Management Console，打开 AWS CloudShell。
- 将这个文件保存为 `trust-policy.json`。

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": {
                "AWS": "arn:aws:iam::WORKLOAD_ACCOUNT_ID:role/EKS-Pod-Role"
            },
            "Action": "sts:AssumeRole",
            "Condition": {
                "StringEquals": {
                    "aws:PrincipalOrgID": "YOUR_ORG_ID"
                }
            }
        }
    ]
}
```

- 运行以下命令创建该 role。

```
# From the AI Services account profile
aws iam create-role \
    --role-name CrossAccount-ClaudePlatform-Prod \
    --assume-role-policy-document file://trust-policy.json \
    --description "Allows workload account to invoke CPonAWS production workspace" \
    --profile ai-services
```

### 2.2 附加 permission policy（AI Services 账户）

- 将这个文件保存为 `permission-policy.json`。

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "CPonAWSInference",
            "Effect": "Allow",
            "Action": [
                "aws-external-anthropic:CreateInference",
                "aws-external-anthropic:CountTokens",
                "aws-external-anthropic:GetModel",
                "aws-external-anthropic:ListModels"
            ],
            "Resource": "arn:aws:aws-external-anthropic:YOUR_REGION:AI_SERVICES_ACCOUNT_ID:workspace/WORKSPACE_PROD_ID"
        },
        {
            "Sid": "CPonAWSResourceless",
            "Effect": "Allow",
            "Action": "aws-external-anthropic:GetAccountStatus",
            "Resource": "*"
        },
        {
            "Sid": "STSWebIdentity",
            "Effect": "Allow",
            "Action": ["sts:GetWebIdentityToken", "sts:TagGetWebIdentityToken"],
            "Resource": "*"
        }
    ]
}
```

- 把该 policy 附加到 role 上：

```
aws iam put-role-policy \
    --role-name CrossAccount-ClaudePlatform-Prod \
    --policy-name CPonAWS-Inference-Prod \
    --policy-document file://permission-policy.json \
    --profile ai-services
```

**注意**：`CreateInference` 被限定在 `WORKSPACE_PROD_ID` 这个 workspace ARN 上。该 role 无法访问 *development* workspace，也无法访问账户中的其他 workspace。

### 2.3 授予 AssumeRole（Workload 账户）

Workload 账户中的 EKS pod role 需要代入跨账户 role 的权限。首先创建该 policy。

- 进入 Workload 账户的 AWS Management Console，打开 AWS CloudShell。
- 将这个文件保存为 `allow-assume-cponaws.json`。

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": "sts:AssumeRole",
            "Resource": "arn:aws:iam::AI_SERVICES_ACCOUNT_ID:role/CrossAccount-ClaudePlatform-Prod"
        }
    ]
}
```

- 创建并附加该 policy。

```
aws iam create-policy \
    --policy-name AllowAssumeCPonAWSRole \
    --policy-document file://allow-assume-cponaws.json \
    --profile workload-prod

aws iam attach-role-policy \
    --role-name EKS-Pod-Role \
    --policy-arn arn:aws:iam::WORKLOAD_ACCOUNT_ID:policy/AllowAssumeCPonAWSRole \
    --profile workload-prod
```

### 2.4 测试（从 Workload 账户）

- 在带有 `EKS-Pod-Role` 凭证的机器（或 pod）上运行以下 Python 脚本。

```
import boto3, os
from anthropic import AnthropicAWS

# Assume the cross-account role in the AI Services account
sts = boto3.client("sts")
assumed = sts.assume_role(
    RoleArn="arn:aws:iam::AI_SERVICES_ACCOUNT_ID:role/CrossAccount-ClaudePlatform-Prod",
    RoleSessionName="prod-workload"
)
creds = assumed["Credentials"]
os.environ["AWS_ACCESS_KEY_ID"] = creds["AccessKeyId"]
os.environ["AWS_SECRET_ACCESS_KEY"] = creds["SecretAccessKey"]
os.environ["AWS_SESSION_TOKEN"] = creds["SessionToken"]

# Make an inference call
client = AnthropicAWS(aws_region="YOUR_REGION", workspace_id="WORKSPACE_PROD_ID")
resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=128,
    messages=[{"role": "user", "content": "Hello from the workload account!"}]
)
print(resp.content[0].text)
```

## 第 3 部分：面向开发者访问的 workspace 级 API key

开发者可以用 API key 从自己的笔记本调用 Claude，无需配置跨账户 role 链。在下一节中，你将生成一把 key、把它限定到开发 workspace，并验证隔离效果。

### 3.1 生成 API key（AI Services 账户）

- 在 AWS Management Console 上登录 AI Services 账户。
- 导航到 Claude Platform on AWS，然后进入 **API keys**。
- 选择 **Generate long-term key**，选定 API key 的有效期，然后选择 **Generate**。
- 立即复制 key 的值（妥善保管：之后不会再显示）。

![Claude Console 的 API Keys 页面，展示带有效期选项的长期 key 生成对话框](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/21/ML-21203-4.png)

图 4：在 Claude Console（API Keys 页面）生成可配置有效期的长期 API key

### 3.2 将 key 限定到开发 workspace（AI Services 账户）

默认情况下，所生成 key 对应的支撑 IAM user（`AeaApiKey-*`）附加了 `AnthropicLimitedAccess` 托管 policy。该 policy 授予对所有 workspace 的访问权限。要强制实现 workspace 隔离：

- 在 AWS Management Console（AI Services 账户）中，导航到 **IAM**，然后进入 **Users**。
- 搜索以 `AeaApiKey-` 开头的 user。
- 找到最近创建的那个 user（创建时间应与生成 key 的时间吻合）。
- 选中该 user，然后选择 **Permissions** 选项卡。
- 选中 `AnthropicLimitedAccess` policy，选择 **Remove** 以解绑该托管 policy。
- 选择 **Add permissions**，然后选择 **Create inline policy**。
- 切换到 **JSON** 选项卡，粘贴以下内容。

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "InferenceDevWorkspaceOnly",
            "Effect": "Allow",
            "Action": [
                "aws-external-anthropic:CreateInference",
                "aws-external-anthropic:CountTokens"
            ],
            "Resource": "arn:aws:aws-external-anthropic:YOUR_REGION:AI_SERVICES_ACCOUNT_ID:workspace/wrkspc_DEV"
        },
        {
            "Sid": "BearerTokenAndStatus",
            "Effect": "Allow",
            "Action": [
                "aws-external-anthropic:CallWithBearerToken",
                "aws-external-anthropic:GetAccountStatus"
            ],
            "Resource": "*"
        },
        {
            "Sid": "STSWebIdentity",
            "Effect": "Allow",
            "Action": ["sts:GetWebIdentityToken", "sts:TagGetWebIdentityToken"],
            "Resource": "*"
        }
    ]
}
```

- 将该 policy 命名为 `CPonAWS-DevWorkspace-Only`，然后选择 **Create policy**。

### 3.3 将 key 分发给开发团队（Workload 账户或开发者环境）

管理员把这把已限定了范围的 API key 分发给开发团队，并存入团队惯用的密钥管理方案。对于基于 AWS 的团队，把它存入工作负载或开发者 AWS 账户内的 AWS Secrets Manager：

```
aws secretsmanager create-secret \
    --name cponaws/dev-api-key \
    --secret-string "YOUR_API_KEY_VALUE" \
    --region YOUR_REGION \
    --profile workload-prod
```

**注意**：API key 是自带认证能力的。无论从哪个 AWS 账户（或非 AWS 环境）调用，它都能生效。请把它存放在开发者能安全取用的位置。

### 3.4 测试（从开发者笔记本）

- 在你的笔记本上运行以下代码，该笔记本需配置上一步创建密钥所在同一账户的 profile。

```
import boto3
from anthropic import Anthropic

# Retrieve the API key from Secrets Manager
secrets = boto3.client('secretsmanager', region_name='YOUR_REGION')
api_key = secrets.get_secret_value(SecretId='cponaws/dev-api-key')['SecretString']

# Create the client pointing to the CPonAWS endpoint
client = Anthropic(
    api_key=api_key,
    base_url='https://aws-external-anthropic.YOUR_REGION.api.aws'
)

# Make an inference call to the development workspace
resp = client.messages.create(
    model='claude-sonnet-4-6',
    max_tokens=128,
    messages=[{"role": "user", "content": "Hello from my laptop!"}],
    extra_headers={'anthropic-workspace-id': 'WORKSPACE_DEV_ID'}
)
print(resp.content[0].text)
```

**预期输出**：一条来自 Claude 的响应，确认开发 workspace 可访问。

### 3.5 验证 workspace 隔离（从开发者笔记本）

- 确认开发 key 无法访问生产 workspace。

```
# Attempt to call the production workspace with the dev key
try:
    resp = client.messages.create(
        model='claude-sonnet-4-6',
        max_tokens=32,
        messages=[{"role": "user", "content": "test"}],
        extra_headers={'anthropic-workspace-id': 'wrkspc_PROD'}
    )
    print("ERROR: Key accessed production workspace!")
except Exception as e:
    print(f"GOOD: Access denied as expected - {e}")
```

**预期输出**：先是 `GOOD: Access denied as expected`，随后跟一条权限错误。如果这把 key 成功访问了生产 workspace，请回到步骤 3.2，确认托管 policy 已解绑。

## 第 4 部分：面向外部工作负载的 OIDC 联合

对于运行在 Google Cloud Platform (GCP)、AWS 之外的 Kubernetes 集群，或 CI/CD 流水线（GitHub Actions、GitLab CI）上的工作负载，OIDC 联合能在不存储 AWS 凭证的情况下完成身份验证。流程是：外部身份提供商签发一个 token，AWS Security Token Service (STS) 把它换成临时凭证，这些凭证再生成一个短期的 CPonAWS bearer token。

### 4.1 创建 IAM OIDC 身份提供商（AI Services 账户）

在 AI Services 账户中，为外部工作负载的 issuer 配置一个 IAM OIDC 身份提供商。例如，GCP 工作负载可参照 [使用 Google Cloud Platform 原生工作负载身份访问 AWS](https://aws.amazon.com/blogs/security/access-aws-using-a-google-cloud-platform-native-workload-identity/) 指南完成完整配置。

### 4.2 为外部工作负载创建 role（AI Services 账户）

- 进入 AI Services 账户的 AWS Management Console，打开 AWS CloudShell。
- 保存为 `oidc-trust-policy.json`。

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": {
                "Federated": "arn:aws:iam::AI_SERVICES_ACCOUNT_ID:oidc-provider/YOUR_OIDC_ISSUER"
            },
            "Action": "sts:AssumeRoleWithWebIdentity",
            "Condition": {
                "StringEquals": {
                    "YOUR_OIDC_ISSUER:aud": "sts.amazonaws.com"
                },
                "StringLike": {
                    "YOUR_OIDC_ISSUER:sub": "YOUR_WORKLOAD_IDENTITY_FILTER"
                }
            }
        }
    ]
}
```

- 创建该 role：

```
aws iam create-role \
    --role-name OIDC-ClaudePlatform-Prod \
    --assume-role-policy-document file://oidc-trust-policy.json \
    --description "Allows external OIDC workloads to invoke CPonAWS production workspace" \
    --profile ai-services
```

- 将 permission policy 保存为 `oidc-permission-policy.json`。

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "CPonAWSInference",
            "Effect": "Allow",
            "Action": [
                "aws-external-anthropic:CreateInference",
                "aws-external-anthropic:CountTokens",
                "aws-external-anthropic:GetModel",
                "aws-external-anthropic:ListModels"
            ],
            "Resource": "arn:aws:aws-external-anthropic:YOUR_REGION:AI_SERVICES_ACCOUNT_ID:workspace/WORKSPACE_PROD_ID"
        },
        {
            "Sid": "CPonAWSResourceless",
            "Effect": "Allow",
            "Action": [
                "aws-external-anthropic:CallWithBearerToken",
                "aws-external-anthropic:GetAccountStatus"
            ],
            "Resource": "*"
        },
        {
            "Sid": "STSWebIdentity",
            "Effect": "Allow",
            "Action": ["sts:GetWebIdentityToken", "sts:TagGetWebIdentityToken"],
            "Resource": "*"
        }
    ]
}
```

- 附加该 policy：

```
aws iam put-role-policy \
    --role-name OIDC-ClaudePlatform-Prod \
    --policy-name CPonAWS-OIDC-Inference-Prod \
    --policy-document file://oidc-permission-policy.json \
    --profile ai-services
```

**重要**：`CallWithBearerToken` 必须授予在 `Resource: "*"` 上。若把它限定到某个 workspace ARN，所有 token 生成调用都会失败。`CreateInference` 仍限定在 workspace ARN 上以实现隔离：生成的 token 会继承这一 workspace 限制。

### 4.3 生成并使用短期 token（从外部环境）

- 在外部工作负载通过 OIDC 拿到 AWS 凭证之后（完整的凭证交换流程见 [使用 Google Cloud Platform 原生工作负载身份访问 AWS](https://aws.amazon.com/blogs/security/access-aws-using-a-google-cloud-platform-native-workload-identity/)）：

```
from token_generator_for_aws_external_anthropic import TokenGenerator
from anthropic import Anthropic
from datetime import timedelta

# Step 1: Generate a short-term token (requires the OIDC-assumed role's AWS credentials)
generator = TokenGenerator(region='YOUR_REGION')
token = generator.get_token(expiry=timedelta(hours=1))

# Step 2: Use the token (no AWS credentials needed from this point forward)
client = Anthropic(
    api_key=token,
    base_url='https://aws-external-anthropic.YOUR_REGION.api.aws'
)
resp = client.messages.create(
    model='claude-sonnet-4-6',
    max_tokens=128,
    messages=[{"role": "user", "content": "Hello from GCP via OIDC!"}],
    extra_headers={'anthropic-workspace-id': 'wrkspc_PROD'}
)
print(resp.content[0].text)
```

**关键点**：生成的 token 在 1 小时后过期（可配置，最长 12 小时）。生成之后，token 就是一个独立的 bearer 凭证：外部工作负载发起推理调用时不再需要 AWS 凭证。对于持续运行的服务（例如 GCP Cloud Run 容器），要通过在过期前刷新 token 来实现 token 续期。

## 第 5 部分：清理

如果你只是在评估，为避免持续产生费用：

- 撤销 API key：在 AWS Management Console 中，导航到 Claude Platform on AWS、API keys，删除所有已生成的 key。
- 删除支撑 IAM user：导航到 IAM > Users，搜索 `AeaApiKey-*`，删除由 key 生成过程创建的所有 user。
- 删除 IAM role：

```
# Remove inline policies first, then delete the roles
aws iam delete-role-policy \
    --role-name CrossAccount-ClaudePlatform-Prod \
    --policy-name CPonAWS-Inference-Prod \
    --profile ai-services

aws iam delete-role \
    --role-name CrossAccount-ClaudePlatform-Prod \
    --profile ai-services

aws iam delete-role-policy \
    --role-name OIDC-ClaudePlatform-Prod \
    --policy-name CPonAWS-OIDC-Inference-Prod \
    --profile ai-services

aws iam delete-role \
    --role-name OIDC-ClaudePlatform-Prod \
    --profile ai-services
```

- 删除 OIDC provider：

```
aws iam delete-open-id-connect-provider \
    --open-id-connect-provider-arn arn:aws:iam::AI_SERVICES_ACCOUNT_ID:oidc-provider/YOUR_OIDC_ISSUER \
    --profile ai-services
```

- 删除密钥。

```
aws secretsmanager delete-secret \
    --secret-id cponaws/dev-api-key \
    --force-delete-without-recovery \
    --region YOUR_REGION \
    --profile ai-services
```

- 取消订阅 CPonAWS：导航到 AWS Marketplace、Your Subscriptions，取消 Claude Platform 订阅。

## 后续步骤

配置好跨账户 SigV4、workspace 级 API key 和 OIDC 联合之后，你的 CPonAWS 部署即可在 workspace 级隔离下支撑 AWS 工作负载、开发者访问和外部环境。要进一步加固以用于生产：

- 监控：为 `aws-external-anthropic` 服务配置 AWS CloudTrail 数据事件，以获得逐次调用、可追溯到 principal 的审计能力。
- 成本分摊：给每个 workspace 打标签（例如 `team:payments`、`environment:prod`），并在 Billing Console 的 Cost Allocation Tags 下激活这些标签。激活后（需等待 24–48 小时），即可在 AWS Cost Explorer 中按 workspace 筛选，把 Claude 开销归到具体项目、团队或环境上。

要开始使用 Claude Platform on AWS，请访问 [Claude Platform on AWS 服务页](https://aws.amazon.com/claude-platform/)，或直接前往 [AWS Management Console](https://console.aws.amazon.com/)。完整文档请参阅 [Claude Platform on AWS 用户指南](https://docs.aws.amazon.com/claude-platform/latest/userguide/welcome.html) 和 [Anthropic 文档](https://platform.claude.com/docs/en/build-with-claude/claude-platform-on-aws)。
