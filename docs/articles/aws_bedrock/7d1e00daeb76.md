## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# CrossnoKaye 如何通过 Amazon Bedrock AgentCore 打造物理 AI

工业运营带来了典型企业软件中不会出现的人工智能挑战。在大多数设施中，工厂数据和控制逻辑分布在来自不同供应商的不同系统中：可编程逻辑控制器 (PLC) 和分布式控制系统 (DCS) 运行设备逻辑，历史记录器根据特定站点的命名方案记录时间序列标签，监控和数据采集 (SCADA) 系统驱动操作员屏幕，独立优化工具或报警记录器位于侧面。在实践中，将外部人工智能代理连接到该堆栈上很少能发挥良好作用。每个系统都使用自己的命名约定。实际控制设备行为的逻辑（控制序列、状态机和安全联锁）被锁定在外部工具无法检查的专有控制器代码内。为附加代理提供跨多个运营技术 (OT) 系统的访问权限还意味着在整个工厂网络中分发凭证。

[CrossnoKaye](https://crossnokaye.com/) 采用不同的方法，使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 将物理 AI 引入重工业。其软件定义的自动化平台 ATLAS 将实时工厂数据和人工智能推理连接到食品和饮料厂、工业制冷设施、骨料采石场和制造工厂运行设备的闭环控制。 CrossnoKaye 在 100 多个工业设施和 13,000 多个受控资产中存储了超过 22 万亿个机器数据点，每天获取超过 500 亿个新读数，并运行超过 1,000 个实时高级过程控制 (APC) 应用程序； CrossnoKaye 报告称，这些应用将生产吞吐量提高了 11% 至 17%，同时将设施总能源成本平均降低了 21%。由于 ATLAS 已在 AWS 上的一个平台上管理设施模型、基础控制软件、历史记录和优化应用程序，因此 CrossnoKaye 的代理智能系统 AURA 可以在单一安全边界内本地访问工厂的完整运行状态。

不过，拥有植物背景只是问题的一半。大型语言模型 (LLM) 擅长解释工程环境和规划调查，但它们无法快速可靠地计算数百万个传感器读数的统计数据或物理平衡。为了用真实的数学来支持每个数字答案，AURA 使用 Amazon Bedrock AgentCore 中的代码解释器功能，在运行时在隔离的、AWS 管理的 microVM 沙箱内编写和运行 Python 工作负载，以及 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 和本地边缘安全控制。本文介绍了 CrossnoKaye 如何在 AWS 上构建 ATLAS 和 AURA、AURA 如何在交互式聊天、可重复任务和自动化例程中使用 Amazon Bedrock AgentCore，以及团队在生产中运行物理 AI 时学到的知识。

## 解决方案概述

ATLAS 控制现有 PLC 和 DCS 基础设施的工业流程，从窑炉、破碎机、干燥室、烤箱和螺旋冷冻机到冷水机、涡轮机、阀门和压缩机，无需客户拆除和更换工厂硬件。图 1 说明了本地 ATLAS 边缘集群、持续云优化和 AURA 如何在 AWS 上协同工作。

图 1：使用 Amazon Bedrock AgentCore 的 CrossnoKaye AURA 和 ATLAS 物理 AI 架构

ATLAS 和 AURA 围绕三个核心层构建：

首先，工厂是在软件中从边缘向上定义的。在每个设施中，本地 ATLAS 控制面板配有冗余计算机、电源和网络交换机（因此在更换故障硬件组件时，本地控制可以不间断地继续）运行使用合同优先微服务的本地 Kubernetes 集群，将 AWS 上的 ATLAS 云平台扩展到工厂车间。在云端，ATLAS 编写、验证和版本化设施的基本控制叙述（定义设备状态机、序列、操作边界、联锁和警报规则），这些叙述被下载到边缘设备并针对现有设备和控制器在本地运行。 CrossnoKaye 报告每年部署超过 9,000 次控制软件，运行时间超过 100 万小时，安全事故为零。每个边缘设备还充当仅出站的信息技术/运营技术 (IT/OT) 网关，在工厂内打开零入站防火墙端口，通过 [Amazon VPC Lattice](https://aws.amazon.com/vpc/lattice/) 和 [Amazon Managed Streaming for Apache Kafka (Amazon MSK)](https://aws.amazon.com/msk/) 将高频遥测数据流式传输到 AWS。如果云连接中断，工厂将继续在本地边缘集群上的基本控制叙述上安全运行。

其次，派生的工程信号和闭环优化应用程序使用相同的共享工厂模型在基础控制之上运行。在云中，CrossnoKaye 的调度系统从 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 中的版本化 Python 包运行两个连续管道，在工厂设置更改时按可配置的每个实例节奏和事件驱动触发器进行操作。综合读取算法计算派生的工程指标，例如热流分布、资产健康指数、能源强度和质量平衡偏差，并将它们与物理 I/O 一起写回历史数据库。闭环优化应用程序在基础控制层之上运行，将这些派生的综合读数与物理模型、模型预测控制 (MPC)、强化学习、公用事业费率和天气预报相结合，以计算最佳设定点计划。 [Amazon Simple Queue Service (Amazon SQS)](https://aws.amazon.com/sqs/) FIFO 队列按设施对每个计划和状态更新进行排序，然后将设置点分派到边缘集群上的本地基本控制叙述，据 CrossnoKaye 报告，该队列每天运行 650,000 个闭环控制操作。

第三，AURA 在 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/) 上的平台边界内作为微服务和持久的 [Temporal](https://temporal.io/) 工作流程运行。在调用者的企业权限下，AURA 代理查询内部 Atlas Data 网关，以一种一致的模型读取设施或车队的运行状态：上游和下游设备拓扑、部署的基础控制叙述和联锁、物理 I/O 和综合读数、设置更改和警报历史记录、主动优化计划以及 [Amazon Bedrock 知识库](https://aws.amazon.com/bedrock/knowledge-bases/) 中索引的工厂文档。

在诊断工厂问题时，将设备布局、基本控制逻辑和传感器数据放在同一系统中会产生具体的影响。在运行初级、二级和三级岩石破碎机的骨料采石场，设备的后半部在一个班次中跳闸两次。操作员在控制室看到了二级破碎机故障，清除了警报，并重新启动了生产线，但数小时后再次跳闸。仅在历史时间戳中，二级破碎机在三级破碎机发生故障几秒后出现故障，这使得它看起来像是破碎机问题。由于 AURA 还读取传送带布局和部署的底座控制联锁，因此其调查遵循实际控制逻辑。三级破碎机下方的循环皮带打滑，导致三级破碎机的过载联锁装置跳闸。该联锁装置的上游安全联锁装置立即停止二级破碎机，以防止将停止的下游破碎机埋在石头中。工厂经理没有去追查破碎机的幽灵故障，而是派了一名操作员检查循环皮带，在几分钟内确认并修复了打滑问题。

图 1 中的编号流程跟踪了 AURA 调查如何在 AWS 上运行：

- 客户端和边缘入口：工程师和模型上下文协议 (MCP) 客户端通过 [AWS WAF](https://aws.amazon.com/waf/) 和公共应用程序负载均衡器进行连接，其中 API 网关验证企业单点登录 (SSO) 或 MCP 凭证。边缘遥测和控制计划流经 Amazon VPC Lattice（使用 AWS Identity and Access Management (IAM) 签名版本 4 (SigV4) 进行身份验证）和 Amazon MSK。
- 上下文检索和受保护的推理：AURA 工作流程通过 Atlas Data 网关读取工厂状态，并通过模型网关将提示和组织范围的检索增强生成 (RAG) 查询路由到基础模型、Amazon Bedrock Guardrails 和 Amazon Bedrock 知识库。
- 运行时计算调度：对于统计、热力学或多数据集数学，工作流程通过 gRPC 将输入数据集流式传输到 AURA 的内部 Sandbox Orchestrator 服务。
- 会话协调和实时流式传输：在交互式会话中，Sandbox Orchestrator 跟踪活动沙箱会话 ID 并通过 [Amazon ElastiCache](https://aws.amazon.com/elasticache/) for Valkey 流式传输实时进度。
- 独立的 Python 执行：Sandbox Orchestrator 使用 AWS 开发工具包调用 Amazon Bedrock AgentCore 运行时的终端节点（Amazon Bedrock AgentCore 的一项功能）、暂存数据集并在独立的代码解释器 microVM 内运行模型编写的 Python。
- 工件存储和简报交付：经过验证的 Apache Parquet 输出、图表和引用的简报通过 [AWS PrivateLink](https://aws.amazon.com/privatelink/) 保存到 Amazon S3，并且 [Amazon Simple Email Service (Amazon SES)](https://aws.amazon.com/ses/) 向工厂团队提供自动化简报。

## 演练

AURA 将 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的基础模型（有关 AWS 区域的模型可用性，请参阅《Amazon Bedrock 用户指南》中的 [AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)）上的基础模型与 Amazon Bedrock AgentCore Code Interpreter（Amazon Bedrock AgentCore 的一项功能）中的隔离 Python 沙箱相结合，跨三种操作模式：

- 聊天：跨越单个单元、生产线或多站点组合（单轮最多 200 个设施）的交互式多回合工程对话。
- 任务：可重复的、参数化的调查绑定到不可变的版本快照，生成带有引用的证据表和图表的结构化技术简介。
- 例程：由时间表、传感器阈值、变化率窗口、警报或设备模式转换触发的自动后台观察程序。

以下部分研究了这些工作流程背后的四个架构决策。

### 与干净的单运行管道相比，温暖的对话沙箱

交互式调试和自动化工厂报告具有不同的状态要求：

- 在交互式聊天中，工程师逐步探索假设：在 94 个设施中加载 24 小时的关键警报，过滤掉某个地点的颤动的罐液位传感器，并将压缩机跳闸与环境湿球温度相关联。每次启动冷沙箱都会擦除内存表并增加延迟。对于聊天，Sandbox Orchestrator 将一个热 Amazon Bedrock AgentCore 会话绑定到 Amazon ElastiCache for Valkey 中的对话，并具有 15 分钟的滑动生存时间 (TTL)，如果工程师在空闲超时到期后返回，则可以透明地配置替换会话。
- 在计划任务或凌晨 2:00 例行程序中，可重复性是第一位的。每次运行都必须在干净的环境中开始，并且没有先前运行的剩余状态。对于任务和例程，Sandbox Orchestrator 在每次运行时都会提供一个全新的一次性 AgentCore microVM，并在计算完成后立即使用“StopCodeInterpreterSession”停止会话，从而防止交叉运行污染和空闲沙箱费用。

这种热会话设计使得整个车队的分类在一次对话中变得实用。当运营总监要求 AURA 检查过去 24 小时内 94 个设施的所有关键警报并识别主要机械风险时，代理会将车队警报摘要从 Atlas Data 网关加载到其 AgentCore 沙箱中，并按设施、规则和到达间隔时间对激活进行分组。 Python 分析不是按原始警报计数对站点进行排名，而是将一个工厂（其中 103 个关键激活来自两个重复的转储罐液位规则）与一个工厂（其中 58 个激活涉及氨检测、蒸发器故障和热气阀在一秒内）分开，从而将安全和维护团队直接指向存在级联设备故障的设施。

### 可验证的计算而不是未经验证的模型数学

当工程师要求 AURA 分析流程趋势或审核班次绩效时，响应中的数字必须准确。在 AURA 开发的早期，团队发现让模型编写自由格式的 Python 脚本来将 JSON 或文本摘要打印到标准输出太脆弱：模型偶尔会错误命名列、删除部分时间窗口或以破坏下游图表渲染的方式格式化输出。

为了使运行时计算可验证，AURA 对每个 Amazon Bedrock AgentCore 运行强制执行严格的数据契约：

- 前期合同验证和多源暂存：在分配沙箱会话之前，Sandbox Orchestrator 会验证输入合同，并将最多 50 个数据集暂存到 microVM 工作区中，结合物理 I/O、派生综合读数、设置日志、警报历史记录和利用率表。
- 沙箱内 DataFrame 架构验证：该服务不是从标准输出解析自由格式的文本，而是将确定性验证工具附加到模型的 Python 脚本中。在沙箱内，该工具会验证每个声明的输出表是否作为包含所有必需列和类型的“pandas.DataFrame”存在于内存中，并将经过验证的表直接序列化为二进制 Apache Parquet 文件。
- 自动自我更正：如果脚本引发 Python 异常或省略必填列，则用户不会收到未经验证的数字。临时工作流程捕获回溯和模式不匹配作为结构化重试提示，以便代理修复其 Python 逻辑并在发布任何结论之前在干净的沙箱中重新运行计算。

### 通过 Amazon SES 自动夜班例程和引用的摘要

工厂工程师无法全天候观察 100 个设施的仪表板，许多设备问题都是从夜班缓慢漂移开始的。 AURA 例程在后台运行，监视特定的工艺条件（例如制冷阶段的吸入压力漂移、落后于规格的批量干燥曲线或计划外的手动设定点覆盖），并在触发时自动启动调查。

工业冷水机组的夜班捕获展示了其端到端的工作原理：

- 自动检测和沙盒根本原因分析（02:00–02:03 AM）：在凌晨 2:00，例程检测低阶段吸入压力漂移并以只读模式启动其固定任务。在 Amazon Bedrock AgentCore 沙箱内，该代理将冷凝器接近温度与物理和合成读数中的低级吸入压力相关联，排除传感器漂移和低制冷剂充注量，并隔离冷凝器侧污垢。
- 确定性引文验证 (02:04 AM)：在发布摘要之前，AURA 会解析每个内联引文并验证每个声明是否链接到 Amazon S3 中保存的遥测窗口、设置更改记录或沙箱输出工件。不会自动进行控制更改。
- 通过 Amazon SES 发送简短消息和一键聊天交接：触发后四分钟内，AURA 通过 Amazon SES 向工厂工程团队发送格式化的 HTML 简短电子邮件，其中包含诊断、引用的信号跟踪和“调查 AURA”按钮。当首席工程师在早班前选择该按钮时，AURA 会验证工程师的现场设施权限，并打开一个预先加载了简报证据的交互式聊天，以便团队可以提出后续问题或立即发出工作指令。

### 纵深防御工业安全

在工业工厂中，操作安全不能依赖于LLM遵循提示中的说明。由于 ATLAS 和 AURA 从云端到工厂车间的边缘 Kubernetes 集群共享相同的平台，因此 CrossnoKaye 对 AI 和优化工作负载可以在四个独立层中执行的操作执行严格的界限：

- Amazon Bedrock Guardrails 和可验证来源（观察）：通过 AURA 模型网关路由的每个提示和完成都由 Amazon Bedrock Guardrails 进行评估，以强制执行内容、主题和安全策略。知识库检索按组织隔离，每个摘要都需要经过验证的内联引用，并注明分析了哪些时间窗口以及传感器数据不可用的任何时期。
- 气隙只读沙箱和人工批准的提案（提案）：Amazon Bedrock AgentCore Code Interpreter microVM 在隔离的 AWS 托管环境中运行，没有网络路由、凭证或通往工厂设备的 API 路径。自动化例程严格以只读模式运行。当工程师使用交互式会话提出设置更改时，该平台需要以运营商的企业身份进行明确的人工批准，并随后验证工厂遥测中的物理结果。
- 边缘不可绕过的确定性 1 级基本控制（有界和基本控制）：云优化应用程序不直接驱动现场硬件。它们通过在工程批准的范围内调度设定点时间表来在平台的基础控制层之上运行。在工厂车间，边缘 Kubernetes 集群在本地实时运行下载的基本控制叙述，实施云服务、优化应用程序或 AI 代理无法绕过的确定性状态机防护、变化率钳位、操作界限和设备联锁。
- 独立的物理硬件保护：在ATLAS软件定义的控制器之下，工厂的物理机械和现场接线强制执行独立的硬连线保护层，包括安全继电器、本地可编程跳闸以及机械泄压和过热设备。

## 结果和经验教训

CrossnoKaye 报告称，在食品加工、工业制冷、骨料和采矿以及制造工厂中，结合软件定义的边缘控制、持续云优化和 AURA，已将批量干燥时间标准偏差减少了 34%（目标产量规格内的产品精加工量增加了 6%），并确定了采石场作业中每年超过 50,000 吨的可恢复生产缺口。超过 5,000 个 AI 代理监控客户设施中的 10,000 多个工厂资产（包括 ATLAS 车队中的 13,000 多个受控设备和设备单元），以前需要花费数小时导出历史记录 CSV、交叉引用 PLC 梯形逻辑和构建电子表格的调查现在只需不到四分钟即可完成，并在早班会议之前通过 Amazon SES 提供引用的技术摘要。

在跨工业设施建设和运营 AURA 过程中，我们得出了三个教训：

- 在添加人工智能之前统一工厂模型和控制逻辑：代理只能在一个一致的模型中读取过程拓扑、部署的基础控制叙述和联锁、设置更改历史记录以及优化器状态，​​而不是将六个断开连接的工厂系统缝合在一起，才能诊断真正的物理根本原因，例如区分下游循环带打滑与二级破碎机故障。
- 在操作员的日常工作流程中提供价值，而不是作为单独的工具来使用：工厂团队正忙于运行设备。如果人工智能助手是一个单独的目的地，工程师必须从空白提示开始，那么日常采用就会陷入停滞。将 AURA 嵌入到每日轮班节奏中（后台例程在夜间捕获异常情况，在 Amazon Bedrock AgentCore 中运行 Python 分析，并通过一键切换到预加载的聊天中，将引用的简报发送到工程师的收件箱）意味着操作员可以在正常例程中看到价值，而无需使用单独的产品。
- 在代码中而不是提示中执行数据、覆盖范围和安全合同：在工厂中，缺少传感器数据的一小时与没有事件的一小时不同，未经验证的计算可能会将维护人员发送到错误的机器。在工具合约中明确数据覆盖差距，在提取二进制 Apache Parquet 输出之前验证 AgentCore 沙箱内的“pandas.DataFrame”模式，并在边缘 Kubernetes 集群上强制执行确定性基本控制边界，以在概率模型错误到达操作员或设备之前捕获它们。

## 结论

Reliable physical AI in heavy industry requires grounding models in the actual equipment topology and control logic of the plant, and backing every quantitative claim with verifiable Python calculations. Together with Amazon Bedrock Guardrails and isolated Python sandboxes in Amazon Bedrock AgentCore, ATLAS and AURA allow agents to reason over live facility ontology, base control narratives, setting histories, physical I/O, optimization state, and synthetic readings, delivering checkable engineering answers and cited technical Briefs through Amazon SES while keeping deterministic safety controls firmly on the plant floor.
