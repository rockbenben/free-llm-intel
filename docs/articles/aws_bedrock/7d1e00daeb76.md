# CrossnoKaye 如何用 Amazon Bedrock AgentCore 让物理 AI 落地

工业运营呈现出典型企业软件中不会出现的 AI 挑战。在大多数设施中，工厂数据和控制逻辑分散在不同供应商的独立系统里：可编程逻辑控制器（PLC）和分布式控制系统（DCS）运行设备逻辑，历史数据库按站点特定的命名方案记录时间序列标签，监控与数据采集（SCADA）系统驱动操作员画面，独立的优化工具或报警记录器则置于一旁。在这样的技术栈上外挂一个 AI agent，在实践中很少能奏效。每个系统都使用自己的命名约定。真正支配设备行为的逻辑（控制序列、状态机和安全联锁）被锁在专有控制器代码里，外部工具无法检查。让一个外挂 agent 跨多个运营技术（OT）系统访问，还意味着要在整个工厂网络中分发凭证。

[CrossnoKaye](https://crossnokaye.com/) 采取了一条不同的路径，借助 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 将物理 AI 带入重工业。其软件定义自动化平台 ATLAS 将实时工厂数据与 AI 推理连接到设备的闭环控制，这些设备运行着食品饮料工厂、工业制冷设施、骨料采石场 和制造站点。在超过 100 个工业设施和 13,000 个受控资产中，CrossnoKaye 存储了超过 22 万亿个机器数据点，每天摄入超过 500 亿条新读数，并运行超过 1,000 个实时高级过程控制（APC）应用；CrossnoKaye 报告称，这些应用将生产吞吐量提高了 11–17%，同时将设施总能源成本平均降低了 21%。由于 ATLAS 已经在 AWS 上的一个平台中管理设施模型、基础控制软件、历史数据库和优化应用，CrossnoKaye 的 agentic 智能系统 AURA 得以在单一安全边界内原生访问工厂的完整运营状态。

不过，拥有工厂上下文只是问题的一半。大语言模型（LLM）擅长解读工程上下文和规划调查，但无法在一个 prompt 中对数百万条传感器读数可靠地计算统计量或物理平衡。为了让每个数值答案都有真实数学支撑，AURA 使用 Amazon Bedrock AgentCore 中的 Code Interpreter 能力，在运行时于隔离的、AWS 托管的 microVM 沙箱内编写并运行 Python 工作负载，同时配合 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 与本地边缘安全控制。本文将介绍 CrossnoKaye 如何在 AWS 上架构 ATLAS 和 AURA，AURA 如何在交互式 Chats、可重复的 Tasks 和自动化 Routines 中使用 Amazon Bedrock AgentCore，以及团队在生产环境中运行物理 AI 学到了什么。

## 解决方案概览

ATLAS 在现有 PLC 和 DCS 基础设施之上控制工业流程，从窑炉、破碎机、干燥室、烘箱和螺旋冷冻机，到冷水机组、涡轮机、阀门和压缩机，无需客户拆换工厂硬件。图 1 展示了本地部署的 ATLAS 边缘集群、持续的云端优化和 AURA 如何在 AWS 上协同工作。

图 1：基于 Amazon Bedrock AgentCore 的 CrossnoKaye AURA 与 ATLAS 物理 AI 架构

ATLAS 和 AURA 围绕三个核心层构建：

首先，工厂从边缘开始用软件定义。在每个设施，一台本地部署的 ATLAS 控制面板配备冗余计算机、电源和网络交换机（以便在更换故障硬件组件时本地控制持续不间断），运行一个本地 Kubernetes 集群，该集群采用契约优先的微服务，将 AWS 上的 ATLAS 云平台延伸到车间。在云端，ATLAS 编写、验证并版本化设施的基础控制叙述（定义设备状态机、序列、操作界限、联锁和报警规则），这些叙述被下载到边缘设备，并针对现有设备和控制器在本地运行。CrossnoKaye 报告每年超过 9,000 次控制软件部署，以及超过 100 万运行小时且零安全事故。每个边缘设备还充当一个仅出站的 IT/OT（信息技术/运营技术）网关，在工厂内部不开放任何入站防火墙端口，通过 [Amazon VPC Lattice](https://aws.amazon.com/vpc/lattice/) 和 [Amazon Managed Streaming for Apache Kafka (Amazon MSK)](https://aws.amazon.com/msk/) 将高频遥测流式传输到 AWS。如果云连接中断，工厂依靠本地边缘集群上的基础控制叙述继续安全运行。

其次，派生工程信号和闭环优化应用使用同一个共享工厂模型，运行在基础控制之上。在云端，CrossnoKaye 的 Scheduling 系统从 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 中的版本化 Python 包运行两条持续管道，按可配置的每实例节奏运行，并在工厂设置变更时由事件驱动触发。合成读数算法计算派生工程指标，例如热流分布、资产健康指数、能源强度和物料平衡偏差，并将它们与物理 I/O 一起写回历史数据库。闭环优化应用运行在基础控制层之上，将这些派生合成读数与物理模型、模型预测控制（MPC）、强化学习、公用事业费率和天气预报相结合，计算最优设定值计划。[Amazon Simple Queue Service (Amazon SQS)](https://aws.amazon.com/sqs/) FIFO 队列按设施对每个计划和状态更新排序，然后再向边缘集群上的本地基础控制叙述分发设定值，CrossnoKaye 报告这每天运行 650,000 次闭环控制动作。

第三，AURA 作为微服务和持久化的 [Temporal](https://temporal.io/) 工作流，在 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/) 上运行于平台边界之内。在调用者的企业权限下，AURA agents 查询内部 Atlas Data 网关，以一个一致模型读取某个设施或机群的运营状态：上下游设备拓扑、已部署的基础控制叙述和联锁、物理 I/O 和合成读数、设置变更和报警历史、活动优化计划，以及在 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 中索引的工厂文档。

设备布局、基础控制逻辑和传感器数据处于同一个系统，在诊断工厂问题时会产生切实的差异。在一个运行初级、二级和三级破碎机的骨料采石场，工厂后半段在一个班次内跳闸了两次。从控制室看，操作员看到二级破碎机故障，清除报警并重启产线，结果几小时后再次跳闸。仅从历史数据库的时间戳看，二级破碎机在三级破碎机之后几秒发生故障，看起来像是破碎机的问题。由于 AURA 还能读取输送机布局和已部署的基础控制联锁，它的调查遵循了实际的控制逻辑。三级破碎机下方的一条回流皮带正在打滑，触发了三级破碎机的过载联锁。该联锁的上游安全联锁立即停止了二级破碎机，以防止石头掩埋已停机的下游破碎机。工厂经理没有去追查一个幻影般的破碎机故障，而是派一名操作员去检查回流皮带，几分钟内就确认并修复了打滑。

图 1 中的编号流程追踪了一次 AURA 调查如何在 AWS 上运行：

- 客户端与边缘入口：工程师和 Model Context Protocol（MCP）客户端通过 [AWS WAF](https://aws.amazon.com/waf/) 和一个公共 Application Load Balancer 连接，API 网关在此验证企业单点登录（SSO）或 MCP 凭证。边缘遥测和控制计划流经 Amazon VPC Lattice（使用 AWS Identity and Access Management (IAM) Signature Version 4 (SigV4) 认证）和 Amazon MSK。
- 上下文检索与受护栏保护的推理：AURA 工作流通过 Atlas Data 网关读取工厂状态，并将 prompt 和组织范围的检索增强生成（RAG）查询通过 Model Gateway 路由到基础模型、Amazon Bedrock Guardrails 和 Amazon Bedrock Knowledge Bases。
- 运行时计算分发：对于统计、热力学或多数据集数学计算，工作流通过 gRPC 将输入数据集流式传输到 AURA 的内部 Sandbox Orchestrator 服务。
- 会话协调与实时流式传输：在交互式会话中，Sandbox Orchestrator 跟踪活动的沙箱会话 ID，并通过 [Amazon ElastiCache](https://aws.amazon.com/elasticache/) for Valkey 流式传输实时进度。
- 隔离的 Python 执行：Sandbox Orchestrator 使用 AWS SDK 调用 Amazon Bedrock AgentCore 运行时（Amazon Bedrock AgentCore 的一项能力）的 endpoint，在隔离的 Code Interpreter microVM 中准备数据集并运行模型编写的 Python。
- 工件存储与 Brief 交付：经过验证的 Apache Parquet 输出、图表和带引用的 Brief 通过 [AWS PrivateLink](https://aws.amazon.com/privatelink/) 保存到 Amazon S3，[Amazon Simple Email Service (Amazon SES)](https://aws.amazon.com/ses/) 向工厂团队交付自动化 Brief。

## 演练

AURA 将 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的基础模型（按 AWS Region 的模型可用性，请参阅 Amazon Bedrock 用户指南中的[按 AWS Region 划分的支持模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)）与 Amazon Bedrock AgentCore Code Interpreter（Amazon Bedrock AgentCore 的一项能力）中的隔离 Python 沙箱相结合，跨越三种操作模式：

- Chats：交互式、多轮的工程对话，涵盖单个机组、一条工艺线或多站点组合（单轮最多 200 个设施）。
- Tasks：可重复、参数化的调查，绑定到不可变的版本快照，产出带有引用证据表格和图表的结构化技术 Brief。
- Routines：由计划、传感器阈值、变化率窗口、报警或设备模式切换触发的自动化后台监视器。

以下各节审视这些工作流背后的四个架构决策。

### 热会话沙箱与干净的单次运行管道之比较

交互式调试和自动化工厂报告有不同的状态需求：

- 在交互式 Chat 中，工程师逐步探索假设：加载 94 个设施过去 24 小时的关键报警，过滤掉某个站点抖动的罐液位传感器，并将压缩机跳闸与环境湿球温度相关联。每一轮都启动一个冷沙箱会清空内存中的表并增加延迟。对于 Chats，Sandbox Orchestrator 在 Amazon ElastiCache for Valkey 中为对话绑定一个热的 Amazon Bedrock AgentCore 会话，设置 15 分钟滑动存活时间（TTL），如果工程师在空闲超时到期后返回，则透明地配置一个替换会话。
- 在计划的 Task 或凌晨 2:00 的 Routine 中，可复现性优先。每次运行都必须从一个干净的环境开始，没有先前运行遗留的状态。对于 Tasks 和 Routines，Sandbox Orchestrator 为每次运行配置一个全新的、单次使用的 AgentCore microVM，并在计算完成后立即用 `StopCodeInterpreterSession` 停止会话，既防止跨运行污染，也避免空闲沙箱费用。

这种热会话设计让全机群分诊在单次对话中变得可行。当一位运营总监要求 AURA 审查 94 个设施过去 24 小时的所有关键报警并识别主要机械风险时，agent 将机群报警摘要从 Atlas Data 网关加载到它的 AgentCore 沙箱中，并按设施、规则和到达间隔时间对激活进行分组。Python 分析不是按原始报警数量给站点排名，而是区分出两种情况：一个工厂的 103 次关键激活来自两条重复的排放罐液位规则，另一个工厂的 58 次激活则跨越氨检测、蒸发器故障和热气阀，且彼此在一秒之内，从而将安全和维护团队直接指向存在级联设备故障的那个设施。

### 可验证的计算，而非未经验证的模型数学

当工程师要求 AURA 分析工艺趋势或审计班次绩效时，响应中的数字必须精确。在 AURA 开发早期，团队发现让模型编写自由形式的 Python 脚本、向标准输出打印 JSON 或文本摘要过于脆弱：模型偶尔会错误命名列、丢掉部分时间窗口，或以破坏下游图表渲染的方式格式化输出。

为了让运行时计算可验证，AURA 围绕每次 Amazon Bedrock AgentCore 运行强制执行严格的数据契约：

- 预先契约验证与多源准备：在分配沙箱会话之前，Sandbox Orchestrator 验证输入契约，并将最多 50 个数据集准备到 microVM 工作区中，组合物理 I/O、派生合成读数、设置日志、报警历史和公用事业费率表。
- 沙箱内 DataFrame 模式验证：该服务不是解析标准输出中的自由形式文本，而是向模型的 Python 脚本追加一个确定性的验证挂具。在沙箱内部，该挂具验证每个声明的输出表都作为 `pandas.DataFrame` 存在于内存中，且具备所有必需的列和类型，并将经过验证的表直接序列化为二进制 Apache Parquet 文件。
- 自动化自我纠正：如果脚本抛出 Python 异常或遗漏必需的列，任何未经验证的数字都不会到达用户。Temporal 工作流将回溯和模式不匹配捕获为一个结构化重试 prompt，让 agent 修复其 Python 逻辑，并在干净的沙箱中重新运行计算，然后才发布任何结论。

### 自动化夜班 Routines 与通过 Amazon SES 交付的带引用 Brief

工厂工程师无法全天候盯着 100 个设施的仪表板，而许多设备问题始于夜班上的缓慢漂移。AURA Routines 在后台运行，监视特定的工艺条件（例如某个制冷级的吸气压力漂移、落后于规格的批次干燥曲线，或计划外的手动设定值覆盖），并在条件触发时自动启动调查。

一个工业冷水机组工厂的夜班捕获展示了这一切如何端到端运作：

- 自动化检测与沙箱内根因分析（凌晨 02:00–02:03）：凌晨 2:00，一个 Routine 检测到低压级吸气压力漂移，并以只读模式启动其固定的 Task。在 Amazon Bedrock AgentCore 沙箱内，agent 将冷凝器趋近温度与低压级吸气压力在物理读数和合成读数之间进行关联，排除传感器漂移和制冷剂充注不足，并隔离出冷凝器侧结垢。
- 确定性引用验证（凌晨 02:04）：在发布 Brief 之前，AURA 解析每个内联引用，并验证每个声明都链接到 Amazon S3 中保存的遥测窗口、设置变更记录或沙箱输出工件。不会自动进行任何控制变更。
- 通过 Amazon SES 交付 Brief 与一键 Chat 交接：触发后四分钟内，AURA 通过 Amazon SES 向工厂工程团队发送一封格式化的 HTML Brief 电子邮件，包含诊断、引用的信号轨迹和一个“Investigate in AURA”按钮。当首席工程师在早班前晨会之前点击该按钮时，AURA 验证该工程师的实时设施权限，并打开一个预加载了该 Brief 证据的交互式 Chat，让团队可以立即提出后续问题或发出工作订单。

### 纵深防御的工业安全

在工业工厂中，运营安全不能依赖 LLM 遵循 prompt 中的指令。由于 ATLAS 和 AURA 从云端一直到车间的边缘 Kubernetes 集群共享同一个平台，CrossnoKaye 在四个独立层上对 AI 和优化工作负载能做什么强制执行严格边界：

- Amazon Bedrock Guardrails 与可验证溯源（Observe）：经由 AURA 的 Model Gateway 路由的每个 prompt 和 completion 都由 Amazon Bedrock Guardrails 评估，以强制执行内容、主题和安全策略。Knowledge Base 检索按组织隔离，每个 Brief 都要求经过验证的内联引用，注明分析了哪些时间窗口以及传感器数据不可用的任何时段。
- 气隙隔离的只读沙箱与人工批准的提案（Propose）：Amazon Bedrock AgentCore Code Interpreter microVM 运行在隔离的、AWS 托管的环境中，没有通往工厂设备的网络路由、凭证或 API 路径。自动化 Routines 严格以只读模式运行。当工程师使用交互式会话提议设置变更时，平台要求以操作员的企业身份进行明确的人工批准，并事后在工厂遥测中验证物理结果。
- 边缘不可绕过的确定性 Level 1 基础控制（Bounded and Base Control）：云优化应用不直接驱动现场硬件。它们运行在平台的基础控制层之上，在工程批准的包络内分发设定值计划。在车间，边缘 Kubernetes 集群在本地实时运行下载的基础控制叙述，强制执行确定性的状态机守卫、变化率钳制、操作界限和设备联锁，云服务、优化应用或 AI agents 都无法绕过。
- 独立的物理硬件保护：在 ATLAS 软件定义控制器之下，工厂的物理机械和现场接线强制执行独立的硬接线保护层，包括安全继电器、本地可编程跳闸，以及机械泄压和超温装置。

## 结果与经验教训

跨食品加工、工业制冷、骨料和采矿以及制造站点，CrossnoKaye 报告称，结合软件定义边缘控制、持续云端优化和 AURA，已将批次干燥时间标准差降低了 34%（在目标产量规格内完成的产品增加了 6%），并在采石场运营中识别出每年超过 50,000 吨的可回收生产缺口。超过 5,000 个 AI agents 监控着客户设施中超过 10,000 个工厂资产（包括 ATLAS 机群中超过 13,000 个受控设备和设备单元），以往需要数小时导出历史数据库 CSV、交叉比对 PLC 梯形逻辑并构建电子表格的调查，现在不到四分钟即可完成，在早班会议之前通过 Amazon SES 交付带引用的技术 Brief。

在跨工业设施构建和运营 AURA 的过程中，有三条经验尤为突出：

- 在添加 AI 之前先统一工厂模型和控制逻辑：只有当 agent 能够在一个一致模型中读取工艺拓扑、已部署的基础控制叙述和联锁、设置变更历史以及优化器状态，而不是拼凑六个互不连通的工厂系统时，它才能诊断真实的物理根因，例如区分打滑的下游回流皮带与二级破碎机故障。
- 在操作员的日常工作流中交付价值，而不是作为一个要单独去使用的工具：工厂团队忙于运行设备。如果 AI 助手是一个独立的目的地，工程师必须从一个空白 prompt 开始，日常采用就会停滞。将 AURA 嵌入日常班次节奏（后台 Routines 在夜间捕获异常，在 Amazon Bedrock AgentCore 中运行 Python 分析，并将带引用的 Brief 交付到工程师的收件箱，附带一键交接到预加载的 Chat），意味着操作员在正常例行工作中就能看到价值，而不必去使用一个单独的产品。
- 在代码而非 prompt 中强制执行数据、覆盖率和安全契约：在工厂中，缺失一小时的传感器数据与没有事件的一小时不是一回事，而一次未经验证的计算可能把维护人员派往错误的机器。在工具契约中明确数据覆盖缺口，在提取二进制 Apache Parquet 输出之前于 AgentCore 沙箱内验证 `pandas.DataFrame` 模式，并在边缘 Kubernetes 集群上强制执行确定性基础控制界限，都能在概率性模型错误到达操作员或某台设备之前将其捕获。

## 结论

重工业中可靠的物理 AI，要求将模型扎根于工厂实际的设备拓扑和控制逻辑，并用可验证的 Python 计算支撑每一个定量声明。借助 Amazon Bedrock Guardrails 和 Amazon Bedrock AgentCore 中的隔离 Python 沙箱，ATLAS 和 AURA 让 agents 能够对实时设施本体、基础控制叙述、设置历史、物理 I/O、优化状态和合成读数进行推理，通过 Amazon SES 交付可核查的工程答案和带引用的技术 Brief，同时将确定性安全控制牢牢保持在车间。
