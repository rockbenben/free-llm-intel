# 使用 Amazon Bedrock AgentCore 构建统一智能

要在整个组织范围内构建连贯、统一的客户智能，首先要减少销售代表在 Salesforce、支持工单和 Amazon Redshift 之间来回切换时所面临的摩擦。一位销售代表在为客户会议做准备时，可能要花上几个小时逐个点击浏览多个不同的仪表板——产品推荐、互动指标、收入分析等等——才能拼出客户处境的完整图景。在 AWS，我们的销售组织在全球化扩张的过程中亲身经历了这一点。我们需要一种方法，把分散在指标数据库、文档仓库和外部行业数据源中的孤立客户数据统一起来，同时不必构建复杂的自定义编排基础设施。

我们构建了 Customer Agent & Knowledge Engine（CAKE），一个以客户为中心的聊天 agent，使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 来解决这一挑战。CAKE 协调多个专用的检索工具——在 [Amazon Neptune](https://aws.amazon.com/neptune/) 中查询知识图谱、在 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 中查询指标、在 [Amazon OpenSearch](https://aws.amazon.com/opensearch-service/) Service 中查询文档，并通过 web 搜索 API 获取外部市场数据，同时使用行级安全（RLS）工具实施安全管控，从而能够在 10 秒内通过自然语言查询交付客户洞察（依据 agent 负载测试的观测结果）。

本文通过 CAKE 这一真实实现，演示如何使用 Amazon Bedrock AgentCore 构建统一智能系统。你可以构建自定义 agent，从而获得以下特性和收益：

- 通过动态意图分析和并行执行来协调专用工具
- 将专用数据存储（Neptune、DynamoDB、OpenSearch Service）与并行编排集成
- 在工作流内实施行级安全与治理
- 面向可靠性的生产工程实践，包括基于模板的报告以符合业务语义和风格
- 通过模型灵活性实现性能优化

这些架构模式可以帮助你加速不同用例的开发，包括客户智能系统、企业 AI 助手，或跨不同数据源协调的多 agent 系统。

## 为什么客户智能系统需要统一

随着销售组织在全球扩张，它们往往面临三个关键挑战：数据分散在各类专用工具中（产品推荐、互动仪表板、收入分析等），要汇集完整的客户视图需要数小时；传统数据库丢失了业务语义，无法刻画解释“指标为什么重要”的语义关系；人工整合流程无法随数据量的增长而扩展。你需要一个能够聚合客户数据、理解语义关系并在业务语境中推理客户需求的统一系统，这使 CAKE 成为各地企业不可或缺的关键支点。

## 方案概览

CAKE 是一个以客户为中心的聊天 agent，把碎片化的数据转化为统一、可执行的智能。通过将内部和外部数据源/表整合到一个对话式端点，CAKE 依托上下文丰富的知识图谱交付个性化的客户洞察——全部在 10 秒内完成。与仅仅汇报数字的传统工具不同，CAKE 的语义基础刻画了业务指标、客户行为、行业动态和战略语境之间的含义与关系。这使 CAKE 不仅能解释客户身上发生了什么，还能解释为什么会发生以及该如何行动。

Amazon Bedrock AgentCore 以托管服务的形式提供多 agent AI 系统所需的运行时基础设施，包括 agent 间通信、并行执行、对话状态跟踪和工具路由。这帮助团队把精力集中于定义 agent 行为和业务逻辑，而不是自行实现分布式系统基础设施。

针对 CAKE，我们在 Amazon Bedrock AgentCore 上构建了一个自定义 agent，协调五个专用工具，每个工具都针对不同的数据访问模式进行了优化：

- Neptune 检索工具，用于图关系查询
- DynamoDB agent，用于即时指标查询
- OpenSearch 检索工具，用于语义文档搜索
- web 搜索工具，用于外部行业情报
- 行级安全（RLS）工具，用于安全管控

针对一个问题（例如“这个客户最大的扩张机会有哪些？”），该方案会流经几个关键阶段：

- **分析意图并路由查询**——运行在 Amazon Bedrock AgentCore 上的 supervisor agent 分析自然语言查询以确定其意图。该问题需要客户理解、关系数据、使用指标和战略洞察。该 agent 的工具调用逻辑使用 Amazon Bedrock AgentCore Runtime，识别出应当激活哪些专用工具。
- **并行分派工具**——编排层并不顺序执行工具调用，而是使用 Amazon Bedrock AgentCore Runtime 的可扩展执行环境并行分派多个检索工具。该 agent 管理执行生命周期，自动处理超时、重试和错误情况。
- **综合多个结果**——随着专用工具返回结果，Amazon Bedrock AgentCore 将这些部分响应流式传输给 supervisor agent，后者把它们综合成一个连贯的答案。该 agent 会推理不同数据源之间的相互关系、识别模式，并生成跨越多个知识领域的洞察。
- **实施安全边界**——在数据检索开始之前，该 agent 会调用 RLS 工具，以确定性的方式实施用户权限。随后，自定义 agent 会验证后续工具调用遵守这些安全边界，自动过滤结果并帮助防止未授权数据访问。该安全层在基础设施层面运行，降低了实现错误的风险。

该架构在两个并行轨道上运行：Amazon Bedrock AgentCore 为实时服务层提供运行时，以最低延迟响应用户查询；离线数据 pipeline 则定期从分析型数据仓库刷新底层数据存储。在接下来的章节中，我们讨论 agent 框架设计以及核心方案组件，包括知识图谱、数据存储和数据 pipeline。

## **Agent 框架设计**

我们的多 agent 系统利用 AWS Strands Agents 框架来提供结构化推理能力，同时保持法规合规和可预测性能所需的企业管控。该多 agent 系统构建在 AWS Strands Agents 框架之上，该框架为使用多种不同模型构建 agent 提供了模型驱动的基础。supervisor agent 会分析输入的问题，智能地选择要调用哪些专用 agent 和工具，以及如何分解用户查询。该框架暴露 agent 状态和输出，以便在 agent 和 supervisor 两个层级实施去中心化评估。在模型驱动方法的基础上，我们通过 GraphRAG 推理链实现 agentic 推理，这些推理链通过遍历知识关系来构建确定性的推理路径。我们的 agent 在其专用领域内执行自主推理，以预定义本体为基础，同时保持企业应用所需的可预测、可审计的行为模式。

supervisor agent 采用多阶段选择协议：

- **问题分析**——解析并理解用户意图
- **源选择**——智能路由决定需要哪些工具组合
- **查询分解**——原始问题被拆解为针对每个所选工具优化的专用子问题
- **并行执行**——所选工具通过无服务器的 AWS Lambda action group 并发执行

工具通过分层组合模式暴露（考虑数据模态——结构化 vs. 非结构化），其中高层 agent 和工具协调多个专用子工具：

- **图推理工具**——管理实体遍历、关系分析和知识提取
- **客户洞察 agent**——并行协调多个 fine-tuned 模型，从表格生成客户摘要
- **语义搜索工具**——编排非结构化文本分析（例如现场记录）
- **web 研究工具**——协调 web/新闻检索

我们在核心 AWS Strands Agents 框架之上扩展了企业级能力，包括客户访问校验、token 优化、用于抵御模型限流的多跳 LLM 选择，以及结构化的 GraphRAG 推理链。这些扩展交付了现代 agentic 系统的自主决策能力，同时有助于实现可预测的性能并符合法规要求。

## 构建知识图谱基础

CAKE 在 Neptune 中的知识图谱以结构化格式表示客户关系、产品使用模式和行业动态，使 AI agent 能够高效推理。与孤立存储信息的传统数据库不同，CAKE 的知识图谱刻画了业务实体及其关系的语义含义。

### 图的构建与实体建模

我们围绕 AWS 销售本体设计知识图谱——即销售团队日常讨论的核心实体和关系：

- **客户实体**——其属性从数据源中提取，包括行业分类、收入指标、云采用阶段和互动评分
- **产品实体**——表示 AWS 服务，并与用例、行业应用和客户采用模式建立连接
- **解决方案实体——** 把产品与业务成果和战略举措关联
- **机会实体**——跟踪销售 pipeline、交易阶段和相关干系人
- **联系人实体**——映射客户组织内的关系网络

Amazon Neptune 擅长回答需要理解连接关系的问题——找出两个实体如何相关、识别账户之间的路径，或发现跨越多个跳数的间接关系。离线数据构建过程会针对 Redshift 集群运行定时查询，以准备要加载到图中的数据。

### 捕捉关系上下文

CAKE 的知识图谱捕捉关系如何连接实体。当图谱通过“使用量增加”这一关系把客户与产品连接起来时，它还会存储上下文属性：增长速率、业务驱动因素（来自客户计划），以及相关的产品采用模式。这种上下文的丰富度帮助 LLM 理解业务语境，并给出以真实关系为依据、而非仅凭统计相关性的解释。

### 专用数据存储

CAKE 不把数据存放在单一数据库中，而是使用专用数据存储，每种存储都按其被查询的方式设计。我们运行在 Amazon Bedrock AgentCore 上的自定义 agent 负责协调这些存储——把查询发送到正确的数据库、同时运行它们并合并结果——从而让用户和开发者都像是在与单一数据源打交道：

- **Neptune 用于图关系**——Neptune 存储客户、账户、干系人和组织实体之间连接构成的网络。Neptune 擅长多跳遍历查询，而这类查询在关系型数据库中需要开销高昂的 join——例如找出彼此不相关账户之间的关系路径，或发现某个行业中已采用特定 AWS 服务的客户。当 Amazon Bedrock AgentCore 识别出需要关系推理的查询时，它会自动路由到 Neptune 检索工具。
- **DynamoDB 用于即时指标**——DynamoDB 作为键值存储，存放预先计算好的聚合结果。离线 pipeline 会预先计算客户健康评分或互动指标，而不是按需计算，并按客户 ID 建立索引存储这些值。DynamoDB 随后提供 10 毫秒以内的查询，支持即时生成报告。Amazon Bedrock AgentCore 中的工具链式调用使它能够从 DynamoDB 检索指标、传给 magnifAI agent（我们的自定义表格转文本 agent）进行格式化，并返回润色后的报告——全程无需自定义集成代码。
- **OpenSearch Service 用于语义文档搜索**——OpenSearch Service 存储账户计划和现场记录等非结构化内容。借助 embedding 模型，OpenSearch Service 把文本转换为支持语义匹配的向量表示。例如，当 Amazon Bedrock AgentCore 收到关于“数字化转型”的查询时，它会识别出需要语义搜索，并自动路由到 OpenSearch Service 检索工具，而后者即使文档使用了不同术语也能找到相关段落。
- **S3 用于文档存储**——Amazon Simple Storage Service（Amazon S3）为 OpenSearch Service 提供基础。账户计划在被索引之前以 Parquet 文件形式存储在 Amazon S3 中，因为源数据仓库（Amazon Redshift）存在截断限制，会切断大文档。这一多步骤过程——Amazon S3 存储、生成 embedding、OpenSearch Service 索引——在保留完整内容的同时维持了实时查询所需的低延迟。

基于 Amazon Bedrock AgentCore 构建，让这些多数据库查询感觉就像一个单一、统一的数据源。当一次查询需要来自 Neptune 的客户关系、来自 DynamoDB 的指标以及来自 OpenSearch Service 的文档上下文时，我们的 agent 会自动并行向这三者分派请求、管理它们的执行，并把结果综合为一个连贯的响应。

### 数据 pipeline 与持续刷新

CAKE 离线数据 pipeline 以批处理进程的方式运行，按计划节奏执行，使服务层与最新业务数据保持同步。该 pipeline 架构把数据构建与数据服务分离，因此实时查询层可以维持低延迟，而批处理 pipeline 负责计算密集型的聚合和图构建。

Data Processing Orchestration 层协调跨多个目标数据库的转换。对于每个数据库，pipeline 执行以下步骤：

- 使用优化的查询从 Amazon Redshift 提取相关数据
- 应用针对各数据存储要求定制的业务逻辑转换
- 把处理后的数据连同适当的索引和分区加载到目标数据库

对于 Neptune，这涉及提取实体数据、构建带属性特征的图节点和边，并加载带有语义关系类型的图结构。对于 DynamoDB，pipeline 计算聚合和指标，把数据组织成为客户 ID 查询优化的键值对，并应用原子更新以保持一致性。对于 OpenSearch Service，pipeline 走一条专用路径：大文档先从 Amazon Redshift 导出到 Amazon S3 成为 Parquet 文件，再通过 embedding 模型处理以生成向量表示，最后连同用于过滤和检索的适当元数据加载到 OpenSearch Service 索引中。

## **面向生产环境的工程化：可靠性与准确性**

在把 CAKE 从原型推向生产的过程中，我们实施了几项关键工程实践，以提升 AI 生成洞察的可靠性、准确性和可信度。

### **模型灵活性**

Amazon Bedrock AgentCore 架构把编排层与底层 LLM 解耦，从而实现灵活的模型选择。我们实现了模型跳跃（model hopping），在发生限流时自动回退到备选模型。这种韧性在 AgentCore 的 Runtime 内透明地发生——检测限流状况、把请求路由到可用的模型，并在不让用户感知到质量下降的情况下维持响应质量。

### **行级安全（RLS）与数据治理**

在数据检索发生之前，RLS 工具会基于用户身份和组织层级实施行级安全。该安全层对用户透明地运行，同时维持严格的数据治理：

- 销售代表只能访问分配给他们辖区的客户
- 区域经理查看其区域内的聚合数据
- 高管拥有与其职责相符的更广视野

RLS 工具会把查询路由到适当的数据分区，并在数据库查询层面应用过滤，因此安全可以在数据层实施，而不必依赖应用层过滤。

## 结果与影响

CAKE 改变了 AWS 销售团队获取和运用客户智能的方式。通过自然语言查询即时获取统一洞察，根据用户的调查/反馈，CAKE 把用于查找信息的时间从数小时缩短到数秒，帮助销售代表专注于战略性客户互动，而不是收集数据。

该多 agent 架构对大多数查询都能在数秒内返回响应，其并行执行模型支持同时从多个数据源检索数据。知识图谱支持超越简单数据聚合的高级推理——CAKE 能解释趋势为何发生、识别看似无关的数据点之间的模式，并生成以业务关系为依据的建议。或许最重要的是，CAKE 在整个组织内实现了客户智能的普及。销售代表、客户经理、解决方案架构师和高管都与同一套统一系统交互，在提供一致的客户洞察的同时维持适当的安全和访问控制。

## 结论

本文展示了 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 如何支撑 CAKE 的多 agent 架构。传统上，构建多 agent AI 系统需要大量基础设施投入，包括实现自定义 agent 协调协议、管理并行执行框架、跟踪对话状态、处理故障模式，以及构建安全管控层。Amazon Bedrock AgentCore 通过在 Amazon Bedrock 内以托管服务形式提供这些能力，减少了这类无法体现差异性的繁重工作。

Amazon Bedrock AgentCore 提供用于编排的运行时基础设施，而专用数据存储则在各自特定的访问模式上表现出色。Neptune 负责关系遍历，DynamoDB 提供即时指标查询，OpenSearch Service 支持语义文档搜索；而我们在 Amazon Bedrock AgentCore 上构建的自定义 agent 负责协调这些组件——自动把查询路由到正确的工具、并行执行它们、综合其结果，并在整个工作流中维持安全边界。CAKE 的实践表明，Amazon Bedrock AgentCore 如何帮助团队构建多 agent AI 系统，把过程从数月的基础设施开发加速到数周的业务逻辑实现。通过以托管服务形式提供编排基础设施，Amazon Bedrock AgentCore 帮助团队专注于领域专业知识和客户价值，而不是从零构建分布式系统基础设施。
