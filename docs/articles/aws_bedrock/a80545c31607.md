# Amazon Finance Automation 如何使用 Amazon Bedrock 构建生成式 AI 问答聊天助手

如今，Amazon Finance 运营中的应付账款（AP）和应收账款（AR）分析师通过电子邮件、案例、内部工具或电话接收客户查询。当出现查询时，分析师必须经历耗时的流程：联系领域专家（SME），并翻阅包含与查询相关的标准操作流程（SOP）的多份政策文档。这种往返沟通流程往往需要数小时到数天，主要原因是分析师（尤其是新员工）无法立即获取必要信息。他们要花数小时咨询 SME 并审阅大量政策文档。

为应对这一挑战，Amazon Finance Automation 在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上开发了一个基于 [large language model](https://aws.amazon.com/what-is/large-language-model/)（LLM）的问答聊天助手。该解决方案让分析师能够快速检索客户查询的答案，在同一条沟通线程内即时生成响应。因此，它大幅缩短了处理客户查询所需的时间。

在本文中，我们分享 Amazon Finance Automation 如何使用 Amazon Bedrock 构建这个[生成式 AI](https://aws.amazon.com/generative-ai/) 问答聊天助手。

## 解决方案概述

该解决方案基于运行在 Amazon Bedrock 上的 [Retrieval Augmented Generation](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）pipeline，如下图所示。当用户提交查询时，RAG 的工作方式是先从知识库中检索相关文档，然后由 LLM 基于检索到的文档生成响应。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/22/ML-16420-SheldonBlogArchitecture.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/22/ML-16420-SheldonBlogArchitecture.png)

该解决方案由以下关键组件构成：

- **知识库** – 我们使用 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 作为文档 embedding 的向量存储。为进行性能评估，我们处理了多份 Amazon 财务政策文档并将其索引到知识库中。另一种选择是 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)，它为端到端 RAG workflow 提供全托管支持。我们计划迁移到 Amazon Bedrock Knowledge Bases，以省去集群管理并为我们的 pipeline 增加可扩展性。
- **Embedding 模型** – 撰写本文时，我们使用 Amazon Bedrock 上的 [Amazon Titan Multimodal Embeddings G1](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-multiemb-models.html) 模型。该模型在来自 Amazon 的大型独特数据集和语料上预训练，根据我们的对比分析，其准确率高于或相当于市场上其他 embedding 模型。
- **生成模型** – 我们使用 Amazon Bedrock 提供的[基座模型](https://aws.amazon.com/what-is/foundation-models/)（FM），因为它在快速交付高度准确的答案方面能力均衡。
- **多样性排序器（diversity ranker）** – 它负责重新排列从向量索引获得的结果，以避免偏向任何特定文档或章节而造成偏斜。
- **Lost in the middle 排序器** – 它负责把最相关的结果高效地分布到 prompt 的顶部和底部，从而最大化 prompt 内容的影响。
- **Guardrails** – 我们使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 检测个人可识别信息（PII），并防范 prompt injection 攻击。
- **校验引擎** – 从响应中移除 PII，并检查生成的答案是否与检索到的上下文一致。若不一致，则返回硬编码的“我不知道”响应，以防止幻觉。
- **聊天助手 UI** – 我们使用 [Streamlit](https://streamlit.io/) 开发 UI，这是一个面向 [machine learning](https://aws.amazon.com/ai/machine-learning/)（ML）用例的 Web 应用开发的开源 Python 库。

## 评估 RAG 性能

聊天助手的准确率是对 Amazon Finance Operations 而言最关键的性能指标。构建第一版聊天助手后，我们通过向聊天助手提交问题来测量 bot 的响应准确率。SME 逐条人工评估 RAG 响应，发现只有 49% 的响应是正确的。这远低于预期，解决方案需要改进。

然而，人工评估 RAG 不可持续——它需要财务运营团队和工程团队投入数小时的工作。因此，我们采用了以下自动化性能评估方法：

- 准备测试数据 – 我们构建了一个包含三个数据字段的测试数据集：  `question` – 该字段由 100 个来自政策文档的问题组成，其答案分布在多种来源中，例如政策文档和工程 SOP，覆盖嵌入表格和图片等复杂文本格式。 `expected_answer` – 这些是由 Amazon Finance Operations 的 SME 人工标注的答案。 `generated_answer` – 这是 bot 生成的答案。
- **NLP 分数** – 我们使用一个测试数据集计算 [ROUGE](https://en.wikipedia.org/wiki/ROUGE_(metric)) 分数和 [METEOR](https://en.wikipedia.org/wiki/METEOR) 分数。由于这些分数只使用词匹配算法而忽略文本的语义，它们与 SME 的评分并不一致。根据我们的分析，与人工评估相比，差异约为 30%。
- **基于 LLM 的评分** – 我们使用 Amazon Bedrock 提供的 FM 为 RAG 性能打分。我们设计了专门的 LLM prompt，通过比较生成的答案与预期答案来评估 RAG 性能。我们生成了一组基于 LLM 的指标，包括准确性、可接受性和事实性，以及代表评估推理过程的引用。这种方法与人工分析的差异约为 5%，因此我们决定沿用这一评估方法。如果你的 RAG 系统构建在 Amazon Bedrock Knowledge Bases 上，你可以使用新的 [RAG evaluation for Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/evaluations) 工具，以 LLM 作为评判者来评估 retrieve 或 retrieve and generate 功能。它提供上下文相关性和上下文覆盖率等检索评估指标，也提供正确性、完整性和有用性等 retrieve and generate 评估指标，以及有害性和拒绝回答等负责任 AI 指标。

## 提升 RAG pipeline 的准确率

基于上述评估技术，我们聚焦 RAG pipeline 中的以下方面来提升整体准确率。

### 增加文档语义分块，将准确率从 49% 提升到 64%

在诊断 RAG pipeline 中的错误响应时，我们发现 14% 的不准确源于发送给 LLM 的上下文不完整。这些不完整的上下文最初是由基于固定 chunk 大小（例如 512 个 token 或 384 个词）的分割算法生成的，该算法没有考虑章节和段落等文档边界。

为解决这个问题，我们使用 QUILL Editor、Amazon Titan Text Embeddings 和 OpenSearch Service 设计了一种新的文档分割方法，具体步骤如下：

- 使用 QUILL Editor 将非结构化文本转换为结构化 HTML 文档。这样，HTML 文档会保留文档格式，从而把内容划分为逻辑 chunk。
- 识别 HTML 文档的逻辑结构，并基于 HTML 标签插入分隔字符串以进行文档分割。
- 使用 embedding 模型生成文档 chunk 的语义向量表示。
- 基于章节中的重要关键词分配标签，以识别章节之间的逻辑边界。
- 将分割后文档的 embedding 向量插入 OpenSearch Service 向量存储。

下图展示了文档检索器的拆分 workflow。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/27/ML-16420-doc_retriever_split-1.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/22/ML-16420-doc_retriever_split.png)

处理文档时，我们遵循以下具体规则：

- 精确提取文档章节的开头和结尾
- 提取章节标题，并将它们与章节内容准确配对
- 基于章节中的重要关键词分配标签
- 索引时保留政策中的 markdown 信息
- 初版中不处理图片和表格

采用这种方法，我们可以把 RAG 准确率从 49% 提升到 64%。

### 使用 prompt engineering 将准确率从 64% 提升到 76%

Prompt engineering 是提升 LLM 性能的关键技术。我们从项目中认识到，不存在放之四海而皆准的 prompt engineering 方法；针对具体任务设计 prompt 才是最佳实践。我们采用以下方法提升 prompt-to-RAG 生成器的效果：

- 在约 14% 的情况下，我们发现即使 RAG 没有检索到相关上下文，LLM 也会生成响应，从而导致幻觉。针对这种情况，我们设计了 prompt，要求 LLM 在未提供相关上下文时不生成任何响应。
- 在约 13% 的情况下，我们收到用户反馈，称 LLM 的响应过于简短，缺乏完整上下文。我们设计了鼓励 LLM 更全面的 prompt。
- 我们设计了 prompt，使其具备为用户同时生成简洁答案和详细答案的能力。
- 我们使用 LLM prompt 生成引用，以正确标注生成答案所用的来源。在 UI 中，引用会以超链接形式列在 LLM 响应之后，用户可以用这些引用验证 LLM 的表现。
- 我们改进了 prompt，引入更好的思维链（CoT）推理：  LLM 使用内部生成推理的独特特性有助于提升性能，并使响应具备类人的连贯性。由于 prompt 质量、推理请求和模型固有能力之间的这种相互作用，我们得以优化性能。鼓励 CoT 推理会促使 LLM 考虑对话的上下文，使其更不易产生幻觉。在既有上下文的基础上构建，模型更可能生成在逻辑上契合对话叙事的响应，从而降低给出不准确或幻觉答案的可能。我们加入了此前已回答问题的示例，为 LLM 建立模式，鼓励 CoT。

随后，我们使用 Amazon Bedrock 提供的 FM 进行 meta-prompting，以撰写满足上述要求的 prompt。

下面的示例是一个用于生成快速摘要和详细答案的 prompt：

```
You are an AI assistant that helps answer questions based on provided text context. I will give you some passages from a document, followed by a question. Your task is to provide the best possible answer to the question using only the information from the given context. Here is the context:

<context>
{}
</context>

And here is the question:
<question>
{}
</question>

Think carefully about how the context can be used to answer the question.
<thinkingprocess>
- Carefully read the provided context and analyze what information it contains
- Identify the key pieces of information in the context that are relevant to answering the question
- Determine if the context provides enough information to answer the question satisfactorily
- If not, simply state "I don't know, I don't have the complete context needed to answer this
question"
- If so, synthesize the relevant information into a concise summary answer
- Expand the summary into a more detailed answer, utilizing Markdown formatting to make it clear and
readable
</thinkingprocess>

If you don't have enough context to answer the question, provide your response in the following
format:

Your concise 1-2 sentence summary goes here.

Your expanded answer goes here, using Markdown formatting like **bold**, *italics*, and Bullet points to improve readability.

Remember, the ultimate goal is to provide an informative, clear and readable answer to the question
using only the context provided. Let's begin!
```

通过实施这些 prompt engineering 方法，我们把 RAG 准确率从 64% 提升到 76%。

### 使用 Amazon Titan Text Embeddings 模型将准确率从 76% 提升到 86%

实施文档分割方法后，我们仍看到检索到的上下文相关性得分偏低（55–65%），而且在超过 50% 的情况下，错误的上下文排在靠前位置。这表明仍有改进空间。

我们试验了多种 embedding 模型，包括第一方和第三方模型。例如，与其他顶级 embedding 模型（如 all-mpnet-base-v2）相比，bge-base-en-v1.5 等上下文 embedding 模型在上下文检索上表现更好。我们发现，使用 Amazon Titan Embeddings G1 模型把检索到上下文的可能性从约 55–65% 提升到 75–80%，并且 80% 的检索上下文排名比之前更高。

最后，通过采用 [Amazon Titan Text Embeddings G1](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html) 模型，我们把整体准确率从 76% 提升到 86%。

## 结论

通过在 Amazon Bedrock 上使用 RAG pipeline 和 LLM，我们在为 Amazon Finance Automation 开发生成式 AI 问答聊天助手方面取得了显著进展。通过持续评估和迭代改进，我们解决了幻觉、文档摄取问题和上下文检索不准确等挑战。我们的结果显示，RAG 准确率从 49% 显著提升到 86%。
