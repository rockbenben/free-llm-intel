# 借助 Amazon Bedrock Agents 与 AWS Support Automation Workflows 简化 AWS 资源故障排查

随着 AWS 环境复杂度不断提升，对资源问题进行故障排查可能成为一项令人望而生畏的任务。人工调查并解决问题既耗时又容易出错，尤其是在面对复杂系统时。幸运的是，AWS 提供了一个强大的工具 [AWS Support Automation Workflows](https://aws.amazon.com/premiumsupport/technology/saw/)，它是一组经过筛选的 [AWS Systems Manager](https://aws.amazon.com/systems-manager/) 自助式自动化 runbook。这些 runbook 由 AWS Support Engineering 依据解决客户问题过程中总结的最佳实践创建。它们使 AWS 客户能够排查、诊断并修复其 AWS 资源中的常见问题。

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 是一项完全托管的服务，通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、Meta、Mistral AI、Stability AI 与 Amazon 等领先 AI 公司的高性能基础模型（FM）供你选择，并提供构建生成式 AI 应用所需的一整套能力，兼顾安全性、隐私与负责任的 AI。使用 Amazon Bedrock，你可以针对自己的用例试验并评估顶级 FM，使用微调与检索增强生成（RAG）等技术以你的数据对其进行私有化定制，并构建可利用企业系统与数据源执行任务的 agent。由于 Amazon Bedrock 是无服务器的，你无需管理基础设施，也能使用你已经熟悉的 AWS 服务，安全地把生成式 AI 能力集成并部署到你的应用中。

本文探讨如何借助 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 与 AWS Support Automation Workflows 的能力，创建一个能够排查 AWS 资源问题的智能 agent。

## 方案概览

尽管该方案通用性强、可适配多种 AWS Support Automation Workflows，我们聚焦于一个具体示例：排查一个未能加入集群的 [Amazon Elastic Kubernetes Service](https://aws.amazon.com/eks/)（Amazon EKS）工作节点。下图提供了使用 Amazon Bedrock 的故障排查 agent 的高层概览。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/04/Bedrock_SAW.jpg)

我们的方案围绕以下关键组件构建，它们协同工作，提供顺畅高效的故障排查体验：

- **Amazon** **Bedrock Agents** – Amazon Bedrock Agents 充当用户与 AWS Support Automation Workflows 之间的智能接口。它处理自然语言提问以理解问题上下文，并管理对话流程以收集所需信息。该 agent 使用 Anthropic 的 Claude 3.5 Sonnet 模型进行高级推理与回答生成，在整个故障排查过程中实现自然交互。
- **Amazon** **Bedrock agent action groups **– 这些 action group 定义了 Amazon Bedrock agent 可以调用的结构化 API 操作。它们使用 OpenAPI 规范，界定 agent 与 [AWS Lambda](https://aws.amazon.com/lambda) 函数之间的接口，明确可用操作、必需参数与预期响应。每个 action group 都包含 API schema，告诉 agent 在与 Lambda 函数交互时应如何正确格式化请求并解释响应。
- **Lambda Function **– Lambda 函数充当 Amazon Bedrock agent 与 AWS Support Automation Workflows 之间的集成层。它校验来自 agent 的输入参数，并启动相应的 SAW runbook 执行。它在处理技术输出的同时监控自动化进度，将其转换为结构化格式。工作流完成后，它把格式化后的结果返回给 agent 以便向用户呈现。
- **IAM role **– [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色为 Lambda 函数提供执行 AWS Support Automation Workflows 并与所需 AWS 服务交互的必要权限。该角色遵循最小权限原则，以维持安全最佳实践。
- **AWS Support Automation Workflows **– 这些预置的诊断 runbook 由 AWS Support Engineering 开发。工作流依据 AWS 最佳实践，以标准化、可重复的方式执行全面的系统检查。它们覆盖广泛的 AWS 服务与常见问题，封装了 AWS Support 深厚的故障排查专业知识。

以下步骤概述了该方案的工作流：

- 用户首先通过 Amazon Bedrock 聊天控制台用自然语言描述其 AWS 资源问题。例如：“为什么我的 EKS 工作节点无法加入集群？”
- Amazon Bedrock agent 分析用户的提问，并将其匹配到其 OpenAPI schema 中定义的相应操作。如果缺少关键信息，例如集群名称或实例 ID，agent 会进行自然对话以收集所需参数。这确保在进入故障排查工作流之前已收集到必要数据。
- Lambda 函数接收已校验的请求并触发相应的 AWS Support Automation Workflow。这些 SAW runbook 包含由 AWS Support Engineering 开发的全面诊断检查，用于识别常见问题及其根因。这些检查自动运行，无需用户干预。
- SAW runbook 系统地执行其诊断检查并汇总发现。这些结果（包括已识别的问题与配置问题）以 JSON 格式结构化并返回给 Lambda 函数。
- Amazon Bedrock agent 基于 [ReAct](https://arxiv.org/pdf/2210.03629.pdf)（协同*推理*与*行动*）技术，使用思维链（CoT）推理处理诊断结果。这使 agent 能够分析技术发现、识别根因、生成清晰的解释，并提供分步的修复指导。

在 agent 的推理阶段，用户可以[查看推理步骤](https://aws.amazon.com/blogs/aws/agents-for-amazon-bedrock-is-now-available-with-improved-control-of-orchestration-and-visibility-into-reasoning/)。

## 故障排查示例

让我们更仔细地看看前面提到的一个常见问题，以及我们的 agent 如何协助排查它。

### EKS 工作节点未能加入 EKS 集群

当 EKS 工作节点未能加入 EKS 集群时，可以用相关信息调用我们的 Amazon Bedrock agent：集群名称与工作节点 ID。该 agent 将执行相应的 AWS Support Automation Workflow，后者会执行诸如验证工作节点的 IAM 角色权限、验证必要的网络连通性等检查。

自动化工作流会运行所有检查。随后 Amazon Bedrock agent 会摄取排查结果，向用户解释问题的根因，并基于 `AWSSupport-TroubleshootEKSWorkerNode` 的输出建议修复步骤，例如更新工作节点的 IAM 角色或解决网络配置问题，使用户能够采取必要的行动来解决问题。

### OpenAPI 示例

在 Amazon Bedrock 中创建 action group 时，你必须定义 agent 需要向用户获取的参数。你还可以定义 agent 使用这些参数可以调用的 API 操作。要定义 API 操作，我们将用 JSON 创建一个 OpenAPI schema：

```
"Body_troubleshoot_eks_worker_node_troubleshoot_eks_worker_node_post": {
        "properties": {
          "cluster_name": {
            "type": "string",
            "title": "Cluster Name",
            "description": "The name of the EKS cluster"
          },
          "worker_id": {
            "type": "string",
            "title": "Worker Id",
            "description": "The ID of the worker node"
          }
        },
        "type": "object",
        "required": [
          "cluster_name",
          "worker_id"
        ],
        "title": "Body_troubleshoot_eks_worker_node_troubleshoot_eks_worker_node_post"
      }
```

该 schema 由以下组件构成：

- **Body_troubleshoot_eks_worker_node_troubleshoot_eks_worker_node_post** – 这是 schema 的名称，对应 `troubleshoot-eks-worker_node` POST 端点的请求体。
- **Properties** – 该部分定义 schema 的属性（字段）：  **“cluster_name”** – 该属性表示 EKS 集群的名称。它的类型为 string，并带有 title 与 description。 **“worker_id**” – 该属性表示工作节点的 ID。它同样是 string 类型，并带有 title 与 description。
- **Type** – 该属性指定 schema 为 “object” 类型，意味着它是键值对的集合。
- **Required** – 该属性列出 schema 的必填字段，在本例中为 “cluster_name” 与 “worker _id”。这些字段必须在请求体中提供。
- **Title** – 该属性为 schema 提供人类可读的标题，可用于文档用途。

该 OpenAPI schema 定义了请求体的结构。要了解更多，请参阅[在 Amazon Bedrock 中为 agent 的 action group 定义 OpenAPI schema](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-api-schema.html) 与 [OpenAPI 规范](https://github.com/OAI/OpenAPI-Specification/blob/main/versions/3.0.3.md#schemaObject)。

### Lambda 函数代码

现在我们来看 Lambda 函数代码：

```
@app.post("/troubleshoot-eks-worker-node")
@tracer.capture_method
def troubleshoot_eks_worker_node(
    cluster_name: Annotated[str, Body(description="The name of the EKS cluster")],
    worker_id: Annotated[str, Body(description="The ID of the worker node")]
) -> dict:
    """
    Troubleshoot EKS worker node that failed to join the cluster.

    Args:
        cluster_name (str): The name of the EKS cluster.
        worker_id (str): The ID of the worker node.

    Returns:
        dict: The output of the Automation execution.
    """
    return execute_automation(
        automation_name='AWSSupport-TroubleshootEKSWorkerNode',
        parameters={
            'ClusterName': [cluster_name],
            'WorkerID': [worker_id]
        },
        execution_mode='TroubleshootWorkerNode'
    )
```

该代码由以下组件构成

- **app.post(“/troubleshoot-eks-worker-node”, description=”Troubleshoot EKS worker node failed to join the cluster”)** – 这是一个装饰器，为发往 `/troubleshoot-eks-worker-node` 端点的 POST 请求设置路由。description 参数简要说明了该端点的作用。
- **@tracer.capture_method** – 这是另一个装饰器，很可能用于追踪或监控，也许作为应用性能监控（APM）工具的一部分。它捕获有关函数执行的信息，例如耗时、错误与其他指标。
- **cluster_name: str = Body(description=”The name of the EKS cluster”),** – 该参数指定 `cluster_name` 为 string 类型，并预期在请求体中传入。Body 装饰器用于表明该参数应从请求体中提取。description 参数简要说明了该参数代表什么。
- **worker_id: str = Body(description=”The ID of the worker node”)** – 该参数指定 `worker_id` 为 string 类型，并预期在请求体中传入。
- ** -> Annotated[dict, Body(description=”The output of the Automation execution”)] **– 这是函数的返回类型，即字典。Annotated 类型用于提供关于返回值的额外元数据，特别是它应被包含在响应体中。description 参数简要说明了该返回值代表什么。

要为 Lambda 函数链接新的 SAW runbook，你可以沿用同样的模板。

## 先决条件

请确保你具备以下先决条件：

- 一个 AWS 账户
- [Anthropic 的 Claude 3.5 Sonnet](https://aws.amazon.com/blogs/aws/anthropics-claude-3-5-sonnet-model-now-available-in-amazon-bedrock-the-most-intelligent-claude-model-yet/) 模型[已在 Amazon Bedrock 中启用](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access-modify.html)的访问权限
- 已在 [AWS Command Line Interface](https://aws.amazon.com/cli/)（AWS CLI）中[配置好你的凭证](https://docs.aws.amazon.com/cli/v1/userguide/cli-configure-files.html)
- 已安装 Javascript
- [AWS Cloud Development Kit](https://aws.amazon.com/cdk/)（AWS CDK）[143.0](https://github.com/aws/aws-cdk/releases/tag/v2.143.0)

## 部署该方案

完成以下步骤以部署该方案：

- 克隆 GitHub 仓库并进入下载后的仓库文件夹根目录：

```
$ git clone https://github.com/aws-samples/sample-bedrock-agent-for-troubleshooting-aws-resources.git
```

```
$ cd bedrock-agent-for-troubleshooting-aws-resources
```

- 安装本地依赖：

```
$ npm install
```

- 使用 AWS CLI 登录你的 AWS 账户，方式为[配置凭证](https://docs.aws.amazon.com/cli/v1/userguide/cli-chap-configure.html)文件（把 <PROFILE_NAME> 替换为你部署所用 AWS 账户的 profile 名称）：

```
$ export AWS_PROFILE=PROFILE_NAME
```

- 引导（bootstrap）AWS CDK 环境（这是一次性操作，如果你的 AWS 账户已完成引导则无需执行）：

```
$ cdk bootstrap
```

- 运行脚本，替换配置文件中针对你的 AWS 账户与 AWS Region 的占位符：

```
$ cdk deploy --all
```

## 测试该 agent

在你的 Region 中导航到 Amazon Bedrock Agents 控制台，找到你部署的 agent。你可以在 `cdk deploy` 命令的输出中找到 agent ID。

现在你可以与该 agent 交互，测试排查一个未能加入 EKS 集群的工作节点。以下是一些示例问题：

- 我想排查为什么我的 Amazon EKS 工作节点没有加入集群。你能帮我吗？
- 为什么这个实例 <instance_ID> 无法加入 EKS 集群 <Cluster_Name>？

## 清理

实施 Amazon Bedrock Agents 时，资源构建不会产生额外费用。不过，Amazon Bedrock 上的 embedding 模型与文本模型调用会产生费用，具体按所用各 FM 的价格计费。在本用例中，你还会因 Lambda 调用而产生费用。

为避免今后产生费用，请通过 AWS CDK 删除已创建的资源。在你的仓库文件夹根目录下运行以下命令：

```
$ npm run cdk destroy --all
```

## 结论

Amazon Bedrock Agents 与 AWS Support Automation Workflows 是强大的工具，二者结合可以变革 AWS 资源故障排查。本文探讨了一个使用 AWS CDK 构建的无服务器应用，演示了如何将这些技术集成起来，创建一个智能故障排查 agent。通过在 Amazon Bedrock agent 中定义 action group，并将它们与特定场景和自动化工作流关联，我们开发出了一套高效流程，用于诊断并解决诸如 Amazon EKS 工作节点失败之类的问题。

我们的方案展示了自动化复杂故障排查任务的潜力，既节省时间又简化运维。在 Anthropic 的 Claude 3.5 Sonnet 驱动下，该 agent 在理解并以英语之外的语言（例如法语、日语与西班牙语）作答方面表现出改进，使其在保持技术准确性与有效性的同时，能够服务全球团队。该智能 agent 能快速识别根因并提供可执行的洞察，同时自动执行相关的 AWS Support Automation Workflows。这种方法不仅将停机时间降至最低，还能有效扩展以适配各种 AWS 服务与用例，为希望强化 AWS 基础设施管理的组织奠定了通用的基础。

探索 AWS Support Automation Workflow 的更多用例，并考虑把该方案作为起点，构建更全面的、贴合你组织需求的故障排查 agent。要了解更多关于使用 agent 编排工作流的信息，请参阅[使用对话式 agent 在应用中自动化任务](https://docs.aws.amazon.com/bedrock/latest/userguide/agents.html)。关于使用 guardrails 保护生成式 AI 应用的细节，请参阅[使用 Amazon Bedrock Guardrails 阻止模型中的有害内容](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html)。
