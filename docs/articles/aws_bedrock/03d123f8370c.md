# ArisGlobal 如何在 Amazon Bedrock 上扩展生成式 AI 推理

ArisGlobal 是一家涵盖药物警戒、监管、医疗事务、临床和质量职能的生命科学技术提供商，开发了 NavaX，这是一款专为 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的生命科学而构建的 AI 引擎，用于自动处理不良事件案例。 ArisGlobal 选择 Amazon Bedrock 来管理对基础模型的访问、欧盟地理跨区域推理和托管提示缓存。随着企业客户增加了不同的合规性要求，共享提示前缀在 6 个月内增长了约 150%，而每个案例的推理成本则增加了 200% 以上。

ArisGlobal 首先缓存每个源文档，因为它是请求的最大部分。这使得不断增长的共享提示符前缀留在缓存之外。通过颠倒顺序并缓存共享前缀，ArisGlobal 降低了有效输入成本，并在成本不成比例增长的情况下支持更多租户。

## ArisGlobal 是谁？

ArisGlobal 是 LifeSphere 的创建者，LifeSphere 是一个用于药物警戒、监管事务、质量和医疗信息的统一 SaaS 平台。 LifeSphere 为全球制药公司提供服务，其中包括多家收入排名前 20 名的制药组织（来源：[ArisGlobal 新闻稿](https://www.arisglobal.com/media/press-release/arisglobal-reports-strong-q1-2026-momentum-with-accelerating-enterprise-ai-transformation/)）。整个系统运行在AWS上。

[LifeSphere NavaX](https://www.arisglobal.com/navax/) 是 ArisGlobal 的人工智能引擎，它将药品安全从记录系统转变为战略优势系统。 ArisGlobal 于 2025 年 3 月在 [Amazon Bedrock 与 Anthropic 的 Claude](https://aws.amazon.com/bedrock/claude/) 上生产了他们的第一个生成式 AI 解决方案。根据 ArisGlobal 的内部生产遥测数据，他们已在受监管的制药环境中处理了超过 100 万笔真实交易，跨多个企业租户处理了数十亿个代币。型号可用性因地区而异。请参阅[AWS 区域的型号支持](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

## NavaX 如何处理不良事件案例

当制药公司收到不良事件报告（通常是描述患者对药物反应的多页 PDF）时，NavaX 的动态数据提取 (DDE) 代理会提取大约 130 个字段。这些字段包括患者人口统计、可疑药物、报告者信息、事件时间表、严重性标准和监管分类。由于此内容包含受保护的健康信息，ArisGlobal 将负责任的人工智能控制作为其生产部署的标准部分。它利用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 等功能来过滤内容并检测或屏蔽敏感信息。提取的字段也会根据模式进行验证并以源文档为基础。

此提取发生在对模型的多个连续请求中。每个请求都侧重于案例表格的不同部分，并且每个请求都包含：

- 系统指令——模型行为规则、输出格式规范和法规遵从性约束。
- 客户特定的规则 - 每个租户的提取逻辑、字段映射和因制药公司而异的业务规则。
- 提取模式 — 大约 130 个目标字段，包含类型、验证规则和少量示例。
- 源文档——不良事件 PDF（通常 10-200 页）。

两个输入在不同范围内重复。共享提示前缀包括系统规则、提取模式和少量示例。它使用同一代理在请求、案例和租户之间重复。源文档仅针对与一种案例关联的请求重复。

## 提示膨胀问题

当 NavaX 推出第一个企业租户时，系统提示是精简的。随着 ArisGlobal 加入更多制药公司，每家制药公司都提出了具体要求：

- 自定义字段映射（租户 A 映射反应起始点的方式与租户 B 不同）。
- 监管管辖权规则（EU ICSR 与 FDA MedWatch 和 PMDA 格式相比）。
- 用于严重性评估和因果关系的公司特定业务逻辑。
- 根据每个公司的历史案例校准的每个租户的少数示例。

在 6 个月的时间里，共享提示前缀从大约 72,000 个令牌增长到 180,000 个令牌，增长了 150%。由于每个案例有多个顺序请求，每个案例的推理成本增加了 200% 以上。

前缀随着每个租户的增长而增长，并根据每个请求进行重新处理，因此快速增长与交易量相结合。

表 1 将原始文档优先请求订单与生产提示优先设计进行了比较。

| **方面** | **第一种方法** | **生产设计** |
| --- | --- | --- |
|请求订单 |每例文档、缓存检查点、共享提示前缀 |共享提示前缀、缓存检查点、按案例文档 |
|缓存前缀 |该文件根据每个案例而变化 |共享提示前缀，在请求之间重复 |
|复用范围|只剩下1个案例的请求 |使用同一代理的跨案例和跨租户请求 |
|成本效应|以全输入速率重复处理不断增长的提示 |整个舰队的快速重用支持次线性成本增长
|欧盟路线|欧盟地理跨区域推断保持不变 |欧盟地理跨区域推断保持不变 |

## Amazon Bedrock 提示缓存策略

Amazon Bedrock 提示缓存通过缓存检查点从请求开始缓存连续的提示前缀，从而减少延迟和输入令牌成本。具有相同前缀的后续请求可以以降低的速率读取缓存的令牌，而不是再次处理它们。缓存条目具有生存时间 (TTL)，该生存时间会在成功缓存命中后重置。

缓存是基于前缀的而不是基于块的。请求部分按照工具、系统、消息的顺序进行评估，因此更改较早的部分会使后面的匹配内容无效。

### 缓存检查点（显式控制）

通过显式缓存检查点，您可以选择准确的前缀边界。支持的 Claude 模型允许每个请求最多有四个检查点。

- 将每个检查点放置在稳定的、可重复使用的前缀之后。
- 满足特定于型号的最小前缀大小。对于 Claude Sonnet 4.5，最小值为 1,024 个令牌（请参阅[支持的型号和区域](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)）。
- 检查点按以下顺序评估：工具、系统和消息。
- 更改较早的部分会使后面部分的缓存匹配无效。
- 默认 TTL 为 5 分钟。通过设置 `"ttl": "1h"`，部分型号支持 1 小时 TTL。较长 TTL 条目必须位于较短 TTL 条目之前。

### 简化的缓存管理（自动）

通过[简化的缓存管理](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)，您可以在静态内容之后放置一个检查点。 Amazon Bedrock 从该点向后搜索最长的匹配前缀，最多约 20 个内容块。

- 一个检查点可以自动定位最长匹配的前缀。
- 当稳定内容超出回溯范围时，使用显式检查点。

### ArisGlobal 缓存了什么，以及他们故意不缓存什么

ArisGlobal 在首先发送的共享提示前缀之后立即使用一个显式检查点。每个案例的文档遵循检查点并根据每个请求进行处理。

这会颠倒初始请求顺序。由于只能缓存前缀，因此排序决定了可以重用哪些内容。

## 启动设计：优先考虑文档重用

第一个设计将 10-200 页的源文档放在每个请求的开头，并在其后面放置检查点。检查点后面是共享提示前缀和特定于部分的问题。
```
{
  "modelId": "anthropic.claude-sonnet-4-5-20250929-v1:0",
  "messages": [
    {
      "role": "user",
      "content": [
        {
          "text": "[Full adverse event PDF content]..." // <-- Document sent FIRST
        },
        {
          "cachePoint": {"type": "default"} // <-- Checkpoint right after the document
        },
        {
          "text": "[System instructions + compliance rules + schema +
          few-shot examples + customer-specific prompt]..."
          // <-- After the checkpoint: never cached
        },
        {
          "text": "Extract fields for Section 3: Suspect Drug Information"
        }
      ]
    }
  ]
}
```
该设计在一种情况下重用了文档：第一个请求将其写入缓存，随后针对该情况的请求以降低的速率读取它。

下一个案例使用了不同的文档，并且需要新的缓存写入，因此重用永远不会跨案例或租户扩展。

更重要的是，共享提示前缀在检查点之后保留，并在每个请求上以完整输入速率进行处理。驱动成本曲线的内容被排除在缓存之外。

## 改进的生产设计：优先考虑共享前缀重用

生产设计改变了顺序，而不是添加另一个检查点：共享提示前缀首先出现，检查点紧随其后，文档最后出现。

同一检查点现在创建一个可重用的舰队范围的缓存条目：

- 之前 — 缓存的文档前缀对于一种情况是唯一的，并且共享提示从未被缓存。
- 之后 — 缓存的共享提示前缀在使用同一代理的请求、案例和租户之间重复。

ArisGlobal 在一个案例中放弃了有限的文档重用，并在整个车队中得到了迅速的重用。共享前缀也是随着客户增加而增长的部分。

### 更新实施
```
{
  "modelId": "anthropic.claude-sonnet-4-5-20250929-v1:0",
  "system": [
    {
      "text": "[Shared system instructions + compliance rules +
      base extraction schema + few-shot examples]..."
    },
    {
      "cachePoint": {"type": "default"} // <-- Checkpoint after the stable prompt
    }
  ],
  "messages": [
    {
      "role": "user",
      "content": [
        {
          "text": "[Full adverse event PDF content — sits after the
          checkpoint, not cached]..."
        },
        {
          "text": "Extract fields for Section 5: Event Assessment"
          // <-- Only this changes per request
        }
      ]
    }
  ]
}
```
对于大多数活跃帐户，每个租户大约每 5 分钟收到一次案例，并且多个租户同时运行。此流量在工作时间内使共享前缀保持温暖，因为每次缓存命中都会重置 TTL。

### 缓存提示和文档

文档之后的第二个检查点将缓存由共享提示和该案例的文档组成的组合前缀。该条目对于一个案例来说仍然是唯一的。

因此，ArisGlobal 优先考虑其读取在整个机群中摊销的前缀。共享提示前缀可跨案例和租户扩展。每个案例的文档没有。

在生产中，典型请求中 65% 的输入令牌是从共享提示缓存提供的。图 1 显示缓存读取始终超过缓存写入。

## 结果

在欧盟地理跨区域推理配置文件保持不变的情况下，缓存共享提示前缀会产生以下结果：

- 65% 的输入令牌以降低的读取速率从缓存提供。
- 缓存生产请求的端到端延迟降低高达 25%。
- 有效投入成本降低约 50%。
- 每月超过 190 亿个代币的总体每月推理支出减少约 40%。
- 入驻的企业租户数量增加约 15%，而成本却没有成比例增加。
- 欧盟地理路线不变。提示缓存在现有推理配置中运行。

根据 ArisGlobal 的生产计费数据，从缓存中提供 65% 的输入令牌可将有效输入成本降低约 50%。每月超过 190 亿个代币，这使得每月推理支出总体节省了约 40%。

## 生产学习

ArisGlobal 的经验为许多具有大量重复提示前缀的工作负载提供了指导：

**缓存重复的内容，而不是最大的内容。** 每个案例的大型文档提供有限的重用，而字节相同的共享提示前缀可以为整个队列中的请求提供服务。

**将稳定的内容放在第一位。** 在检查点之前排列工具定义、系统指令、模式和示例。随后放置租户标识符、案例数据和每个请求的问题。

**使用队列流量来分摊缓存写入。** 使用同一代理的租户发出的请求可以读取相同的前缀，并且缓存命中会重置 TTL。对于零星流量，请在支持的型号上评估 1 小时 TTL。

**减少可避免的调用。** 每个调用仍然处理未缓存的文档，因此在输出限制和架构要求允许的情况下捆绑顺序问题。

**保持前缀字节相同。** 时间戳、请求 ID、租户名称和重新排序的工具定义可能会导致丢失。移动检查点之后的每个动态元素。

**监控生产基线。** 跟踪 CloudWatch 中的缓存读取、缓存写入和总输入令牌。当缓存命中率持续低于正常的 65% 缓存命中基线时发出警报，而不是使用不兼容的 80% 阈值。

**检查特定于型号的限制。** 前缀最小值和 TTL 选项因型号而异。 Claude Sonnet 4.5 需要至少 1,024 个令牌用于缓存检查点。

## 结论

ArisGlobal 将欧盟地理跨区域推理与针对正确内容的快速缓存相结合。缓存稳定的共享前缀而不是每个案例的文档，可将有效输入成本降低约 50%，每月整体推理节省约 40%，并在成本不成比例增加的情况下支持约 15% 的企业租户。

关键的教训是缓存价值取决于重用，而不是大小。对于多租户代理工作负载，重复的共享提示前缀可能比针对每种情况进行更改的较大文档更有价值。
