# ArisGlobal 如何在 Amazon Bedrock 上扩展生成式 AI 推理

ArisGlobal 是一家生命科学科技提供商，业务覆盖药物警戒、法规事务、医学事务、临床与质量等职能。它在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上开发了 NavaX——一个专为生命科学打造、用来自动化不良事件个例处理的 AI 引擎。ArisGlobal 选择 Amazon Bedrock，是为了获得对基础模型的托管访问、EU 地理跨区域推理（cross-Region inference）以及托管的 prompt caching。随着企业客户不断追加各自的合规要求，共享 prompt 前缀在 6 个月内增长了约 150%，而每个个例的推理成本上涨了 200% 以上。

ArisGlobal 最初缓存的是每份源文档，因为它是请求中最大的一块。这让不断增长的共享 prompt 前缀被留在了缓存之外。把顺序反过来、改为缓存共享前缀之后，ArisGlobal 降低了有效输入成本，并在成本没有等比例增长的情况下支撑了更多租户。

## ArisGlobal 是谁？

ArisGlobal 是 LifeSphere 的创造者。LifeSphere 是一个统一的 SaaS 平台，面向药物警戒、法规事务、质量与医学信息。LifeSphere 服务全球的制药公司，其中包括多家按收入排名前 20 的制药组织（来源：[ArisGlobal press release](https://www.arisglobal.com/media/press-release/arisglobal-reports-strong-q1-2026-momentum-with-accelerating-enterprise-ai-transformation/)）。整个系统运行在 AWS 上。

[LifeSphere NavaX](https://www.arisglobal.com/navax/) 是 ArisGlobal 的 AI 引擎，把药物安全从记录系统变成战略优势系统。ArisGlobal 于 2025 年 3 月在 [Amazon Bedrock 上接入 Anthropic 的 Claude](https://aws.amazon.com/bedrock/claude/)，把他们的第一个生成式 AI 方案投入生产。根据 ArisGlobal 内部的生产遥测，他们已在受监管的制药环境中处理超过 100 万笔真实交易，跨多个企业租户处理了数十亿 token。模型可用性因 Region 而异。参见 [Model support by AWS Region](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

## NavaX 如何处理一个不良事件个例

当制药公司收到一份不良事件报告——通常是一份多页 PDF，描述患者对某种药物的反应——NavaX 的 Dynamic Data Extraction（DDE）agent 会抽取大约 130 个字段。这些字段包括患者人口统计信息、可疑药物、报告人信息、事件时间线、严重性判定标准以及监管分类。由于这些内容包含受保护的健康信息，ArisGlobal 把负责任 AI 控制作为生产部署的标准组成部分，借助 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 等能力过滤内容、检测或掩码敏感信息。抽取出的字段还会按 schema 校验，并以源文档为依据。

这次抽取会拆成多次顺序请求发给模型。每次请求聚焦个例表单的不同部分，各自携带：

- system instructions——模型行为规则、输出格式规范与监管合规约束。
- 客户特定规则——按租户区分的抽取逻辑、字段映射，以及因制药公司而异的业务规则。
- 抽取 schema——约 130 个目标字段，带类型、校验规则与 few-shot 示例。
- 源文档——不良事件 PDF（通常 10–200 页）。

有两类输入在不同范围内重复。共享 prompt 前缀包含系统规则、抽取 schema 与 few-shot 示例，它在请求之间、个例之间、以及使用同一个 agent 的租户之间重复。源文档只在一份个例所关联的那几次请求之间重复。

## prompt 膨胀问题

NavaX 随第一个企业租户上线时，system prompt 还很精简。随着 ArisGlobal 陆续接入更多制药公司，每一家都带来了特定要求：

- 自定义字段映射（租户 A 对反应发生时间的映射方式与租户 B 不同）。
- 监管辖区规则（EU ICSR 与 FDA MedWatch、PMDA 的格式差异）。
- 公司特定的严重性评估与因果关系业务逻辑。
- 按租户区分的 few-shot 示例，依据各公司的历史个例校准。

在 6 个月内，共享 prompt 前缀从大约 72,000 个 token 增长到 180,000 个 token，增幅 150%。由于每个个例都要发多次顺序请求，每个个例的推理成本上涨了 200% 以上。

每接入一个租户，前缀就增长一次，而每次请求都要重新处理它，于是 prompt 增长与交易量叠加在一起。

表 1 对比了最初文档在前的请求顺序与生产环境 prompt 在前的设计。

| **维度** | **最初的做法** | **生产设计** |
| --- | --- | --- |
| 请求顺序 | 每个个例的文档、缓存检查点、共享 prompt 前缀 | 共享 prompt 前缀、缓存检查点、每个个例的文档 |
| 缓存的前缀 | 文档——每份个例都会变 | 共享 prompt 前缀——在请求之间重复 |
| 复用范围 | 仅限同一个个例剩余的请求 | 跨个例、跨使用同一 agent 的租户的请求 |
| 成本效果 | 不断增长的 prompt 按完整输入费率被反复处理 | 全体客户范围的 prompt 复用支撑次线性成本增长 |
| EU 路由 | EU 地理跨区域推理保持不变 | EU 地理跨区域推理保持不变 |

## Amazon Bedrock 的 prompt caching 策略

Amazon Bedrock 的 prompt caching 通过缓存从请求开头到某个缓存检查点的一段连续 prompt 前缀，来降低延迟与输入 token 成本。之后前缀相同的请求可以按更低的价格读取缓存的 token，而不用重新处理它们。缓存条目有一个生存时间（TTL），在成功命中一次缓存后重新计时。

缓存基于前缀，而不是基于块。请求的各部分按顺序评估——tools、system、然后是 messages——因此改动靠前的部分会让其后本可匹配的内容失效。

### 缓存检查点（显式控制）

使用显式缓存检查点，你可以指定精确的前缀边界。受支持的 Claude 模型每个请求最多允许四个检查点。

- 把每个检查点放在稳定、可复用的前缀之后。
- 满足特定模型的最小前缀大小。对 Claude Sonnet 4.5，最小为 1,024 个 token（见[受支持的模型与 Region](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)）。
- 检查点按以下顺序评估：tools、system、messages。
- 改动靠前的部分会让后续部分的缓存匹配失效。
- 默认 TTL 为 5 分钟。部分模型支持通过设置 `"ttl": "1h"` 使用 1 小时的 TTL。TTL 更长的条目必须放在 TTL 更短的条目之前。

### 简化的缓存管理（自动）

使用[简化的缓存管理](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)时，你在静态内容之后放一个检查点。Amazon Bedrock 从该点向后搜索最长的匹配前缀，最多约 20 个内容块。

- 一个检查点就能自动定位最长匹配前缀。
- 当稳定内容超出回看范围时，改用显式检查点。

### ArisGlobal 缓存了什么，以及刻意没有缓存什么

ArisGlobal 在共享 prompt 前缀之后紧接着使用一个显式检查点，而共享前缀是最先发送的。每个个例的文档跟在检查点之后，每次请求都会被处理。

这颠倒了最初的请求顺序。由于只能缓存前缀，顺序决定了哪部分内容可以被复用。

## 上线时的设计：优先复用文档

最初的设计把 10–200 页的源文档放在每个请求的开头，检查点放在它之后。共享 prompt 前缀与针对具体小节的问题跟在检查点后面。

```
{
  "modelId": "anthropic.claude-sonnet-4-5-20250929-v1:0",
  "messages": [
    {
      "role": "user",
      "content": [
        {
          "text": "[Full adverse event PDF content]..." // <-- Document sent FIRST
        },
        {
          "cachePoint": {"type": "default"} // <-- Checkpoint right after the document
        },
        {
          "text": "[System instructions + compliance rules + schema +
          few-shot examples + customer-specific prompt]..."
          // <-- After the checkpoint: never cached
        },
        {
          "text": "Extract fields for Section 3: Suspect Drug Information"
        }
      ]
    }
  ]
}
```

这个设计在单个个例内复用了文档：第一次请求把它写入缓存，该个例后续的请求以更低的价格读取它。

下一个个例用的是另一份文档，需要一次新的缓存写入，因此复用从未跨个例或跨租户延伸。

更重要的是，共享 prompt 前缀位于检查点之后，每次请求都按完整输入费率被处理。真正驱动成本曲线的那部分内容被排除在缓存之外。

## 演进后的生产设计：优先复用共享前缀

生产设计改变的是顺序，而不是再加一个检查点：共享 prompt 前缀放在最前，检查点紧随其后，文档放在最后。

同一个检查点现在创建的是一个可复用的、全体客户共享的缓存条目：

- 改动前——被缓存的文档前缀只对单个个例唯一，而共享 prompt 从未被缓存。
- 改动后——被缓存的共享 prompt 前缀在使用同一 agent 的请求、个例与租户之间重复。

ArisGlobal 放弃了单个个例内有限的文档复用，换来了全体客户范围上的 prompt 复用。共享前缀也正是随着客户增加而增长的那部分。

### 更新后的实现

```
{
  "modelId": "anthropic.claude-sonnet-4-5-20250929-v1:0",
  "system": [
    {
      "text": "[Shared system instructions + compliance rules +
      base extraction schema + few-shot examples]..."
    },
    {
      "cachePoint": {"type": "default"} // <-- Checkpoint after the stable prompt
    }
  ],
  "messages": [
    {
      "role": "user",
      "content": [
        {
          "text": "[Full adverse event PDF content — sits after the
          checkpoint, not cached]..."
        },
        {
          "text": "Extract fields for Section 5: Event Assessment"
          // <-- Only this changes per request
        }
      ]
    }
  ]
}
```

对大多数活跃账户来说，每个租户大约每 5 分钟就有一个个例到来，而且多个租户并发运行。这种流量让共享前缀在营业时间内保持温热，因为每次缓存命中都会重置 TTL。

### 同时缓存 prompt 与文档

如果在文档之后再放一个检查点，缓存的就是「共享 prompt + 该个例文档」组合起来的前缀。这个条目仍然只对单个个例唯一。

因此 ArisGlobal 优先选择读取能在全体客户之间摊薄的前缀。共享 prompt 前缀可以跨个例、跨租户扩展；每个个例的文档则不行。

在生产环境中，一个典型请求 65% 的输入 token 由共享 prompt 缓存提供。图 1 显示缓存读取持续高于缓存写入。

## 结果

在 EU 地理跨区域推理 profile 保持不变的前提下，缓存共享 prompt 前缀带来了以下结果：

- 65% 的输入 token 按更低的读取费率由缓存提供。
- 缓存了的生产请求端到端延迟最多降低 25%。
- 有效输入成本降低约 50%。
- 在每月超过 190 亿 token 的规模下，整体月度推理支出降低约 40%。
- 多接入了约 15% 的企业租户，而成本没有等比例上升。
- EU 地理路由不变。prompt caching 在既有推理配置之内运行。

## 生产心得

ArisGlobal 的经验，对许多带有大型、重复 prompt 前缀的工作负载都有借鉴意义：

**缓存重复出现的，而不是最大的。** 为每个个例准备的大型文档能提供的复用有限，而逐字节完全相同的共享 prompt 前缀可以服务全体客户范围的请求。

**把稳定内容放在最前。** 把工具定义、system instructions、schema 与示例排在检查点之前，把租户标识、个例数据与每次请求的问题放在之后。

**用全体客户的流量摊薄缓存写入。** 使用同一 agent 的各租户请求可以读到同一个前缀，而缓存命中会重置 TTL。对零散流量，可以在受支持的模型上评估 1 小时 TTL。

**减少可避免的调用。** 每次调用仍要处理未缓存的文档，因此在输出上限与 schema 要求允许时，把顺序提问合并起来。

**保持前缀逐字节一致。** 时间戳、request ID、租户名称以及被重新排序的工具定义都可能造成未命中。把每个动态元素都移到检查点之后。

**监控生产基线。** 在 CloudWatch 中跟踪缓存读取、缓存写入与输入 token 总量。告警要盯住持续低于正常 65% 缓存命中基线的情况，而不要套用一个不适配的 80% 阈值。

**检查特定模型的限制。** 前缀最小值与 TTL 选项因模型而异。Claude Sonnet 4.5 的缓存检查点至少需要 1,024 个 token。

## 结论

ArisGlobal 把 EU 地理跨区域推理与瞄准正确内容的 prompt caching 结合起来。缓存稳定的共享前缀而非每个个例的文档，使有效输入成本降低约 50%，贡献了约 40% 的整体月度推理节省，并多支撑了约 15% 的企业租户而成本没有等比例上升。

关键经验是：缓存的价值取决于复用，而不是大小。对多租户的 agentic 工作负载来说，一个重复出现的共享 prompt 前缀，可能比一份每个个例都在变化的更大文档更有价值。
