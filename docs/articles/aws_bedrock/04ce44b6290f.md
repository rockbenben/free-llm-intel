# 将 Amazon Bedrock Agents 与 Slack 集成

随着越来越多的公司采用[生成式 AI](https://aws.amazon.com/ai/generative-ai/)应用，能够提供切实业务价值的 AI agent 已成为关键组成部分。在这种背景下，将定制构建的 AI agent 集成到 [Slack](https://slack.com/) 等聊天服务中可能带来变革性意义，让企业能够无缝使用由先进[基础模型](https://aws.amazon.com/what-is/foundation-models/)（foundation model，FM）驱动的 AI 助手。AI agent 开发完成后，下一个挑战在于如何以直接高效的方式将它整合进来。组织有几种选择：集成到现有 Web 应用中、[开发自定义前端界面](https://github.com/aws-samples/sample-cognito-integrated-bedrock-agents-chat-ui)，或者与 Slack 等通信服务集成。第三种选择——将定制 AI agent 与 Slack 集成——提供了一条更简单、更快速的实施路径，你可以在熟悉的工作环境中按需调用 AI agent。

该方案通过更快的查询响应和自动化的任务处理来提升团队生产力，同时最大限度降低运营开销。按量付费模式会随着使用规模扩大而优化成本，因此对刚开始 AI 之旅或正在扩展现有能力的组织尤其有吸引力。

AI agent 有众多实用的业务用例，与传统方式相比，每一种都能带来可衡量的收益和显著的时间节省。例如，Knowledge Base agent 可以即时呈现公司文档，将搜索时间从几分钟缩短到几秒。合规检查 agent 可以实时帮助遵循策略，可能节省数小时的人工审查。销售分析 agent 提供即时洞察，免去耗时的数据整理与分析。用于 IT 支持的 AI agent 可帮助处理常见技术问题，通常比人工支持人员更快地解决问题。

这些由 AI 驱动的解决方案通过上下文对话提升用户体验，根据当前对话和查询上下文提供相关帮助。这种自然的交互模式提高了支持质量，并有助于在整个组织内推动用户采用。在快速获取 AI 驱动洞察有益于团队工作流的用例中，你可以按照这种实施方法将方案提供给 Slack 用户。通过集成定制 AI agent，组织可以跟踪关键绩效指标（key performance indicator，KPI）的改善，例如平均解决时间（mean time to resolution，MTTR）、首次呼叫解决率和整体生产力提升，从而展示由[大语言模型](https://aws.amazon.com/what-is/large-language-model/)（large language model，LLM）驱动的 AI agent 的实际收益。

在本文中，我们提出一个将 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 纳入 Slack 工作区的方案。我们将指导你配置 Slack 工作区、在 [Amazon Web Services](https://aws.amazon.com/)（AWS）中部署集成组件，以及使用该方案。

## 解决方案概览

该方案由两个主要组件构成：Slack 到 Amazon Bedrock Agents 的集成基础设施，以及你现有的 [Amazon Bedrock](https://aws.amazon.com/bedrock/) agent 或我们提供的用于测试的示例 agent。集成基础设施负责 Slack 与 Amazon Bedrock agent 之间的通信，agent 则处理查询并作出响应。

该方案使用 [Amazon API Gateway](https://aws.amazon.com/api-gateway/)、[AWS Lambda](https://aws.amazon.com/lambda/)、[AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 和 [Amazon Simple Queue Service](https://aws.amazon.com/sqs/)（Amazon SQS）实现 serverless 集成。它免除了对常驻基础设施的需求，有助于降低总体成本，因为你只需为实际使用量付费。

Amazon Bedrock agent 可以自动化工作流和重复性任务，同时安全地连接到组织的数据源以提供准确的响应。

[action group](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-action-create.html) 定义了 agent 可以帮助用户执行的操作。通过这种方式，你可以让 agent 处理和管理传入请求，从而将业务逻辑与后端服务集成。agent 还会在整个对话过程中维护上下文、使用思维链（chain of thought）过程，并实现更个性化的交互。

下图展示了该方案的架构，其中包含两个关键部分：

- **Section A** – 本节包含 Amazon Bedrock agent 及其组件。借助方案的这一部分，你可以连接现有 agent，或使用提供的 [AWS CloudFormation](https://aws.amazon.com/cloudformation) 模板部署我们的示例 agent
- **Section B** – 本节包含由 CloudFormation 模板部署的集成基础设施（API Gateway、Secrets Manager、Lambda 和 Amazon SQS）。

[![Solutions Overview Slack Integration with Amazon Bedrock Agents](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/12/1-Solutions-Overview-Slack-Integration-with-Amazon-Bedrock-Agents.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/12/1-Solutions-Overview-Slack-Integration-with-Amazon-Bedrock-Agents.png)

请求流程包含以下步骤：

- 用户通过在 Slack 中使用 `@appname` 向 bot 发送消息。
- Slack 向 API Gateway endpoint 发送 webhook POST 请求。
- 请求被转发到验证用的 Lambda 函数。
- Lambda 函数获取 Slack signing secret 和 bot token，以验证请求的真实性。
- 验证通过后，消息被发送到第二个 Lambda 函数。
- 在将消息放入 SQS 队列之前，Amazon SQS 集成 Lambda 函数会在原始消息下的线程中，向 Slack 中的用户发送一条 “🤔 Processing your request…” 消息。
- 消息被发送到 FIFO（First-In-First-Out，先进先出）队列进行处理，并使用频道和线程 ID 来帮助防止消息重复。
- SQS 队列触发 Amazon Bedrock 集成 Lambda 函数。
- Lambda 函数用用户查询调用 Amazon Bedrock agent，agent 处理请求并给出答案作为响应。
- Lambda 函数会用 agent 的最终响应（如果启用了 debug 模式，则用 agent 的推理过程）更新 Slack 线程中最初的 “🤔 Processing your request…” 消息。

## 前提条件

要完成本文中的方案，你必须具备以下条件：

- 一个 [AWS 账户](https://signin.aws.amazon.com/signup?request_type=builderId)
- 一个 [Slack 账户](https://slack.com/get-started?entry_point=help_center#/createnew)（两种选择）：  对于公司 Slack 账户，请与管理员合作创建并发布集成应用，或者你可以使用 sandbox 组织 也可以自行创建 Slack 账户和工作区，用于测试和试验
- 在 Amazon Bedrock 中，针对 Anthropic 的 Claude 3.5 Sonnet 的[模型访问权限](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)，且需与你部署该方案的 [AWS 区域](https://docs.aws.amazon.com/glossary/latest/reference/glos-chap.html#region)相同（如果你使用自己的 agent，可以跳过此要求）
- [GitHub 仓库](https://github.com/aws-samples/sample-Integrate-Amazon-Bedrock-Agents-with-Slack)中提供的配套 CloudFormation 模板：  示例 Amazon Bedrock agent（`virtual-meteorologist`） 将 Slack 集成到 Amazon Bedrock Agents

## 使用 AWS CloudFormation 部署示例 Amazon Bedrock agent 资源

如果你已经配置了一个 Amazon Bedrock agent，可以从 agent 详情中复制其 [ID](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-view.html) 和 [alias](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-alias-view.html)。如果没有，那么当你运行示例 Amazon Bedrock agent（`virtual-meteorologist`）的 CloudFormation 模板时，将部署以下资源（所用 AWS 资源会产生费用）：

- Lambda 函数：  **GeoCoordinates** – 将地点名称转换为经纬度坐标 **Weather** – 使用坐标获取天气信息 **DateTime** – 获取特定时区的当前日期和时间
- [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色：  **GeoCoordinatesRole** – `GeoCoordinates` Lambda 函数的角色 **WeatherRole** – `Weather` Lambda 函数的角色 **DateTimeRole** – `DateTime` Lambda 函数的角色 **BedrockAgentExecutionRole** – Amazon Bedrock agent 执行的角色
- Lambda 权限：  **GeoCoordinatesLambdaPermission** – 允许 Amazon Bedrock 调用 `GeoCoordinates` Lambda 函数 **WeatherLambdaPermission** – 允许 Amazon Bedrock 调用 `Weather` Lambda 函数 **DateTimeLambdaPermission** – 允许 Amazon Bedrock 调用 `DateTime` Lambda 函数
- Amazon Bedrock agent：  **BedrockAgent** – 配置了三个 action group 的虚拟气象学家 agent
- Amazon Bedrock agent 的 action group：  `obtain-latitude-longitude-from-place-name` `obtain-weather-information-with-coordinates` `get-current-date-time-from-timezone`

选择 **Launch Stack **以部署资源：

## 使用 AWS CloudFormation 部署将 Slack 集成到 Amazon Bedrock Agents 的资源

当你运行 CloudFormation 模板将 Slack 与 Amazon Bedrock Agents 集成时，将部署以下资源（所用 AWS 资源会产生费用）：

- API Gateway：  **SlackAPI** – 用于 Slack 交互的 REST API
- Lambda 函数：  **MessageVerificationFunction** – 验证 Slack 消息签名和 token **SQSIntegrationFunction** – 处理向 Amazon SQS 发送消息排队 **BedrockAgentsIntegrationFunction** – 使用 Amazon Bedrock agent 处理消息
- IAM 角色：  **MessageVerificationFunctionRole** – `MessageVerificationFunction` Lambda 函数权限的角色 **SQSIntegrationFunctionRole** – `SQSIntegrationFunction` Lambda 函数权限的角色 **BedrockAgentsIntegrationFunctionRole** – `BedrockAgentsIntegrationFunction` Lambda 函数权限的角色
- SQS 队列：  **ProcessingQueue** – 用于有序消息处理的 FIFO 队列 **DeadLetterQueue** – 用于处理失败消息的 FIFO 队列
- Secrets Manager 密钥：  **SlackBotTokenSecret** – 安全存储 Slack 凭据

选择 **Launch Stack **以部署这些资源：

[![cloudformation-launch-stack-slack-bedrockagent-integration](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/12/cloudformation-launch-stack-slack-bedrockagent-integration.png)](https://console.aws.amazon.com/cloudformation/home?region=us-east-1#/stacks/new?stackName=slack-bedrock-agent-integration&templateURL=https://aws-blogs-artifacts-public.s3.us-east-1.amazonaws.com/artifacts/ML-18564/cfn-amazon-bedrock-agents-slack-integration.json)

## 将 Amazon Bedrock Agents 与 Slack 工作区集成

完成以下步骤，将 Amazon Bedrock Agents 与 Slack 工作区集成：

- 前往 [Slack API](https://api.slack.com/apps) 并选择 `virtual-meteorologist` 应用

[![Slack Select Your Apps](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/12/12-Slack-Select-YourApps.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/12/12-Slack-Select-YourApps.png)

- 在导航窗格中，选择 **Event Subscriptions**
- 在 **Event Subscriptions** 页面上，打开 **Enable Events**
- 在 **Request URL** 中输入你先前复制的 API Gateway URL——验证将自动进行
- 对于 **Subscribe to bot events**，选择 **Add Bot User Event** 按钮，添加 `app_mention` 和 `message.im`
- 选择 **Save Changes**
- 选择 **Reinstall your app**，并在接下来的页面上选择 **Allow**

[![Slack Event Subscriptions](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/12/13-SlackEventSubscriptions-Compressed-2.gif)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/12/13-SlackEventSubscriptions-Compressed-2.gif)

## 清理

如果你决定停止使用该方案，请完成以下步骤，移除它及使用 AWS CloudFormation 部署的相关资源：

- 删除 Slack 集成的 CloudFormation 堆栈：  在 AWS CloudFormation 控制台上，在导航窗格中选择 **Stacks** 找到你在部署过程中为 Slack 集成 Amazon Bedrock Agents 创建的堆栈（你为它指定了名称） 选中该堆栈并选择 **Delete**

## 注意事项

设计 serverless 架构时，按用途拆分 Lambda 函数在维护和灵活性方面具有显著优势。这种设计模式允许直接修改行为和进行定制，而不影响整体系统逻辑。每个请求涉及两个 Lambda 函数：一个用于 token 验证，另一个用于 SQS 载荷处理。在高流量期间，管理这两个函数的并发执行需要注意 Lambda 的[并发](https://docs.aws.amazon.com/lambda/latest/dg/lambda-concurrency.html)限制。对于扩展能力至关重要的用例，可以将这些函数合并为单个 Lambda 函数作为替代方案，或者考虑使用 [Amazon EventBridge](https://aws.amazon.com/eventbridge/) 等服务来帮助管理组件之间的事件流。在这些架构方案之间做选择时，请考虑你的用例和流量模式。
