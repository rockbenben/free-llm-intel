# TReNDS 如何借助 Amazon Bedrock 自动化根因分析

*本文是与佐治亚州立大学 TReNDS 中心的 Vitaly Omelchenko 合写的客座文章。*

在[神经影像与数据科学转化研究中心（TReNDS）](https://trendscenter.org)——佐治亚州立大学、佐治亚理工学院与埃默里大学共建的联合中心——我们开发并应用先进的分析方法与神经信息学工具，用于大脑健康研究。自 2019 年起，我们的基础设施一直运行在 Amazon Web Services（AWS）上，多年来我们构建了多样化的应用，包括研究工具与 API，全部运行在 [Amazon Elastic Kubernetes Service（Amazon EKS）](https://aws.amazon.com/eks/) 上，日志通过 [FluentBit](https://fluentbit.io/) 发送到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)。

随着应用增长，我们需要排查的错误数量也在增长。当我们开始探索 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 时，看到了一个我们期盼已久的机会：可以把事件响应中最耗时的部分——根因调查本身——自动化。

在本文中，我们分享在 TReNDS 生产环境中构建并使用的架构。它结合了 [Amazon CloudWatch 订阅筛选器](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/SubscriptionFilters.html)、[AWS Lambda](https://aws.amazon.com/lambda/)、[Strands Agents SDK](https://strandsagents.com/latest/)与 Amazon Bedrock，实时检测错误，用日志上下文和来自 GitHub 的源代码对其加以丰富，并把 AI 驱动的根因分析交付给我们的团队。

*本文中的架构与建议反映我们团队在 TReNDS 中心的经验，不代表佐治亚州立大学、佐治亚理工学院或埃默里大学的官方指导意见。*

## 我们要解决的问题

和许多团队一样，我们有告警与监控。我们知道东西什么时候坏了。然而，知道某个东西失败了，和弄清楚它为什么失败，是两回事。我们的工程师仍然要打开 Amazon CloudWatch Logs，通读堆栈跟踪，找到相关的源文件，并在脑中推演执行路径。对于直白的错误，这要花 15–30 分钟。对于跨多个服务的复杂问题，时间要长得多。

我们意识到，这个调查过程正是带有合适工具的基础模型能胜任的工作。模型做的不只是总结错误信息，它会通过拉取周边日志上下文、阅读源代码并产出结构化分析来调查这个错误。这正是我们着手构建的东西。

## 架构

以下是我们最终确定的架构：

![Amazon EKS 的日志经 CloudWatch 订阅筛选器流入运行在 Amazon Bedrock 上的 AWS Lambda Strands Agent，再发送到 Amazon SNS](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/07/29/ML-21106-1.png)

*图 1 —— 自动化根因分析的架构*

我们在 EKS 上的应用使用 FluentBit 把日志发送到 CloudWatch。CloudWatch 订阅筛选器监视错误级别的模式（`ERROR`、`Exception`、`FATAL`、`CRITICAL`），在匹配时调用一个 Lambda 函数。该 Lambda 运行一个由 Amazon Bedrock 驱动的 Strands Agent，由它调查该错误，然后把分析结果发布到 Amazon Simple Notification Service（Amazon SNS）主题，投递给我们的团队。

系统的核心是 Amazon Bedrock。基础模型（FM）负责对错误、代码和根因做实际的推理。我们在 Amazon Bedrock 之上使用 Strands Agents SDK 处理工具使用的编排。我们定义有哪些工具可用，由模型决定何时以及如何调用它们。给定一段堆栈跟踪，agent 可能会获取相关源文件、意识到需要更多上下文、搜索相关的错误处理，并产出结构化分析，而无需我们硬编码这条调查路径。

由于 TReNDS 处理与健康相关的研究数据，数据驻留与合规是重要的考量。Amazon Bedrock 在我们的 AWS 账户内处理请求，因此日志数据和源代码与应用的其他部分处于同一环境。AI 分析不需要把数据发送到外部端点。这让数据流始终停留在我们已经管控的边界之内。这对我们的工作尤为重要，因为 TReNDS 处理的与健康相关的研究数据可能受 HIPAA 要求约束。关于符合《健康保险携带与责任法案》（HIPAA）要求的 AWS 服务，请参阅 [AWS HIPAA 合规服务参考](https://aws.amazon.com/compliance/hipaa-eligible-services-reference/)。

尽管我们的部署使用 EKS 与 FluentBit，这一模式同样适用于其他把日志发送到 CloudWatch 的应用，包括 ECS、Lambda、EC2，或使用 CloudWatch Agent 的本地部署工作负载。

## 前提条件

要实现本方案，你需要以下条件：

- 一个可访问 Amazon Bedrock（具体为 Anthropic Claude Sonnet）的 AWS 账户。
- 一个 Amazon EKS 集群，其应用通过 FluentBit 把日志发送到 CloudWatch。
- 已配置订阅筛选器的 CloudWatch 日志组。
- 一个包含你的应用源代码的 GitHub 仓库。
- 已安装 Strands Agents SDK（可通过官方 Lambda layer 获取）。
- 熟悉 Python。
- 一个为通知配置好的 Amazon SNS 主题。
- 一个具有相应 IAM 权限的 AWS Lambda 函数，可访问 Amazon Bedrock、CloudWatch Logs、AWS Secrets Manager 和 SNS。

## 使用 Strands Agents SDK 构建工具

agent 的能力来自我们给它的工具。在我们构建的所有工具中，源代码检索是最关键的。堆栈跟踪会引用文件路径和行号，但如果不能访问真正的实现，agent 就只能做日志模式匹配。通过赋予 agent 读取源文件的能力，它可以追踪执行路径并定位导致失败的具体代码。使用 Strands Agents SDK，你只需用 `@tool` 装饰一个 Python 函数即可定义自定义工具。以下是我们构建的、用于从 GitHub 仓库获取源代码的工具：

```
import base64
import boto3
import requests
from strands import Agent, tool

# Retrieve the GitHub token from AWS Secrets Manager
secrets_client = boto3.client("secretsmanager")
github_token = secrets_client.get_secret_value(
    SecretId="trends/github-token"
)["SecretString"]

@tool
def fetch_source_code(file_path: str, repo: str) -> str:
    """Fetch a source file from a GitHub repository.

    Args:
        file_path: Path to the file in the repository
        repo: Repository in 'owner/repo' format
    """
    response = requests.get(
        f"https://api.github.com/repos/{repo}/contents/{file_path}",
        headers={"Authorization": f"token {github_token}"}
    )
    if response.status_code != 200:
        return f"Could not fetch {file_path} from {repo}: HTTP {response.status_code}"
    content = base64.b64decode(response.json()["content"])
    return content.decode("utf-8")
```

docstring 和类型提示很重要。Strands 用它们告诉模型这个工具做什么、需要哪些参数。模型随后根据在错误中发现的内容决定何时调用这个工具。更多模式参见[自定义工具文档](https://strandsagents.com/latest/documentation/docs/user-guide/concepts/tools/custom-tools/)。

部署时，我们使用 Strands Agents 的[官方 Lambda layer](https://strandsagents.com/latest/documentation/docs/user-guide/deploy/deploy_to_aws_lambda/)。无需手动打包 SDK。

## pipeline 如何工作

当我们的某个应用发生错误时，pipeline 会自动经过四个阶段。首先，CloudWatch 检测到错误模式，带着压缩后的日志数据调用我们的 Lambda 函数。Lambda 解码事件，之后由 Strands Agent 接手。agent 从同一容器获取额外的日志上下文，从 GitHub 检索相关源代码，并对根因进行推理。最后，它把结构化分析发布到 SNS，投递给我们的团队。以下各节详细讲述每个阶段。

### 接收并解码 CloudWatch 事件

CloudWatch 订阅筛选器把经过 base64 编码、gzip 压缩的日志事件发送给 Lambda。每次调用包含在很短时间窗口内匹配筛选模式的一个或多个日志事件。Lambda 处理函数解码这些信息，提取日志组名称和匹配的事件，并把它们传给 agent 进行分析。标准解码模式参见 [CloudWatch Logs 订阅筛选器文档](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/SubscriptionFilters.html#LambdaFunctionExample)。

### 获取扩展上下文

订阅筛选器只投递匹配的那一行日志，但单独一行很少够用。CloudWatch 事件信息中包含 logStream，它标识了产生该错误的具体容器。我们构建了第二个 `@tool`，用于从同一日志流中获取周边日志。这让 agent 拿到完整的堆栈跟踪，以及导致失败的请求上下文，而不掺杂其他并发请求的噪声：

```
@tool
def fetch_log_context(log_group: str, log_stream: str, timestamp: int,
                      window_seconds: int = 30) -> str:
    """Fetch log lines from the same log stream surrounding an error.

    Args:
        log_group: CloudWatch Log Group name
        log_stream: Log stream that produced the error
        timestamp: Error event timestamp in milliseconds
        window_seconds: Time window before and after the error
    """
    response = logs_client.filter_log_events(
        logGroupName=log_group,
        logStreamNames=[log_stream],
        startTime=timestamp - (window_seconds * 1000),
        endTime=timestamp + (window_seconds * 1000),
    )
    events = response.get("events", [])
    if not events:
        return f"No log events found in {log_stream} within {window_seconds}s of the error."
    return "\n".join(e["message"] for e in events)
```

通过把范围限定在日志流上，我们得到来自同一容器的干净、按时间顺序排列的事件序列。其中包括触发该错误的请求、之前的警告，以及完整的异常堆栈。

### agent 分析

agent 收到错误及其上下文后，自主决定要调查什么。与遵循预定义决策树的规则系统不同，agent 会解释错误信息、识别堆栈跟踪中的文件路径和类名，并确定要检索哪些源文件。如果初步的代码审阅发现错误源自某个依赖或共享工具，agent 会沿着这条链路追下去，无需我们再额外提示。我们通过 system prompt 塑造输出格式：

```
SYSTEM_PROMPT = """You are a senior Site Reliability Engineer analyzing production errors.

Given an error and its surrounding log context:
1. Identify the root cause by analyzing the stacktrace
2. Use fetch_source_code to read the relevant source files
3. Provide a structured analysis with:
   - Severity (CRITICAL/HIGH/MEDIUM/LOW)
   - Root cause explanation
   - Relevant source code context
   - Suggested fix
   - Related areas that may be affected
"""
```

system prompt 定义了结构化输出格式，但把调查策略留给模型。agent 根据在错误中发现的内容决定调用哪些工具。带有清晰文件路径的堆栈跟踪会触发 fetch_source_code 调用。没有堆栈跟踪的错误则可能让 agent 去代码库中搜索错误信息字符串。这种灵活性是 agentic 方法的核心价值。我们不需要预判应用可能产生的每一种错误类型。

Lambda 处理函数把所有部分串起来：

```
agent = Agent(
    model=BedrockModel(model_id="us.anthropic.claude-sonnet-4-20250514"),
    system_prompt=SYSTEM_PROMPT,
    tools=[fetch_source_code, search_github_code, fetch_log_context]
)

result = agent(
    f"Analyze this error from {log_group}:\n\n{error_message}"
)
```

处理函数用我们选定的 Amazon Bedrock 模型、定义输出格式的 system prompt，以及可用工具列表创建一个 Agent 实例。随后它把错误信息和日志组名称一起传给 agent，触发自主调查循环。

### 交付结果

agent 完成分析后，我们把结果发布到 [Amazon SNS](https://aws.amazon.com/sns/) 主题，并扇出到电子邮件和 Slack。以下是一条典型通知的样子：

```
Error Analysis — order-service

Severity: HIGH
Error: NullPointerException at OrderService.java:142

Root Cause: The method processPayment() calls paymentGateway.charge()
which can return null on gateway timeout, but line 142 accesses
response.getTransactionId() without a null check.

Source Context (OrderService.java:138-148):
[relevant code shown]

Suggested Fix: Add null check for gateway response before accessing
fields. Consider retry mechanism for gateway timeouts.

Related: Similar pattern in RefundService.java:89
```

agent 在没有人指导的情况下自主调查了这个错误。它读取了相关源代码，找到了缺失的空值检查，甚至还标出了另一个文件中的类似模式。这体现了 agentic 方法的价值。与其遵循固定的检查清单，agent 会根据每一步发现的内容调整调查策略，就像一位经验丰富的工程师那样。

## 结果

自部署这套系统以来，我们看到它明显改变了团队处理生产错误的方式。最直接的变化是速度。调查时间从 15 到 30 分钟降到 60 秒以内。由于 agent 的分析中包含建议的修复方案，我们的工程师常常在收件箱里就拿到现成的解决方案。他们可以直接开始实施修复，而不必花时间做诊断。

运行这套系统的成本可以忽略不计。每次分析只产生极少的 Amazon Bedrock 推理费用，通常每个错误涉及两到三轮工具使用。就我们的工作负载而言，这只是同等工程师时间成本的一小部分。

我们的开发者通过电子邮件收到 agent 的分析，反馈一直很正面。即使面对工程师此前没遇到过的错误，这些分析也提供了清晰的解决起点。工程师无需再做额外调查，就能快速理解发生了什么、该怎么处理。

一次发布之后，同一段代码路径可能反复产生相同错误。我们使用 Amazon DynamoDB 做去重，确保只有首次出现才触发分析。其余的会被静默过滤，让收件箱保持干净、Amazon Bedrock 成本保持低廉。

## 选择合适的 Amazon Bedrock 模型

Amazon Bedrock 让我们通过单一 API 访问一系列基础模型。我们测试了多个模型，为错误分析这一用例寻找最佳匹配，评估维度包括推理质量（理解代码与错误）、工具使用的可靠性（调用我们的 GitHub 与 CloudWatch 工具）、延迟，以及每次分析的成本。

| **模型** | **最适用于** | **工具使用** | **延迟** | **相对成本** |
| --- | --- | --- | --- | --- |
| Anthropic Claude Sonnet | 复杂的多文件推理、细微的代码问题 | 可靠 | 快 | 中等 |
| Anthropic Claude Haiku | 直白的错误、大批量分诊 | 良好 | 最快 | 低 |
| Anthropic Claude Opus | 深入的跨服务调查 | 可靠 | 中等 | 高 |
| Amazon Nova Pro | 通用分析、成本效益高 | 良好 | 快 | 低 |
| Amazon Nova Lite | 简单的错误分类、预算受限的工作负载 | 良好 | 最快 | 最低 |

我们选择 Claude Sonnet 作为主力模型。在我们的测试中，它稳定产出了最准确的根因分析。它能追踪跨多个文件的调用链，识别像缺失空值检查这样的细微问题，并对并发问题做出推理。对于成本或延迟要求不同的团队，表中的其他模型是应对更简单错误模式的可靠替代方案。

在 Strands 中切换模型只需改一行，这让我们的评估变得简单直接：

```
# We tested multiple models by changing this single line.
# Check Amazon Bedrock documentation for the latest available model IDs.
model = BedrockModel(model_id="us.anthropic.claude-sonnet-4-20250514")
```

**注意：** 模型 ID 会定期更新。当前模型 ID 请参阅 [Amazon Bedrock 受支持模型文档](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards.html)。

## 后续规划

我们正在探索这套系统的若干扩展。首要任务是把检索增强生成（RAG）与我们的内部 runbook 连接起来。

- 通过把 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 与我们的内部 runbook 和过往事件报告集成，agent 将能在分析中引用 TReNDS 特有的流程。
- 我们还计划实施分层模型策略。简单、已知的错误模式会路由到 Haiku 做快速、低成本的分诊，而复杂或新颖的错误则升级到 Sonnet 做深入分析。这将在我们的错误总量上同时优化成本与响应时间。
- 最后，我们正朝着自动创建 GitHub issue 和 pull request 的方向努力。当 agent 识别出潜在的修复方案时，它会自动创建一个带有分析内容的 GitHub issue，并开一个包含建议代码改动的 pull request，减少从诊断到解决之间的手工步骤。

随着我们进一步扩大规模，我们也在考察 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)，用于托管式 agent 运行时、可观测性和身份管理。多 agent 与部署模式参见 [Strands Agents 示例](https://strandsagents.com/latest/documentation/docs/examples/)。

## 结论

我们在 TReNDS 构建这套系统，是因为我们希望应用中的每个错误都得到即时、结构化的调查，而不只是一条告警。Amazon Bedrock 与 Strands Agents SDK 让实现变得直接。我们定义了少量工具，写了一个 system prompt。现在我们有了一个 agent，它能像经验丰富的工程师那样对生产错误进行推理，并在数秒内交付结果。

新增一项能力，意味着再写一个 `@tool` 函数和几行 Python。无论是需要 Jira 集成、带建议修复的 GitHub PR，还是连接运行中 pod 做更深入调查的工具，模式都是一样的。基础模型负责推理与编排，我们则把它连接到所需的系统上。
