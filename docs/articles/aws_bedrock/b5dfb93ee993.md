# 使用 Amazon Bedrock AgentCore 的 AI 驱动开发生命周期

采用 AI 驱动开发生命周期（AI-DLC）、并使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 与 [Kiro](https://kiro.dev/) 这类编码 agent 的工程团队，常常苦于概念框架与可运行代码之间的落差。Amazon Bedrock AgentCore 是一项用于以任意框架或模型大规模构建、连接并优化 agent 的服务。AI-DLC 把 AI 定位为贯穿软件开发生命周期的核心协作者，承担例行执行，而人类保留对关键决策的监督。本文用可运行的参考实现来弥合这一落差。

本文深入介绍两个参考实现背后的架构、设计决策与关键代码模式，它们展示了如何使用 Amazon Bedrock AgentCore、Kiro 和本地 agentic 编码工具来实现 AI-DLC 构建阶段的模式。第一个实现使用 AgentCore runtime（Amazon Bedrock AgentCore 的一项能力）从 SQL schema 生成 Mermaid 实体关系图。第二个实现通过多 agent 架构提供自动化的代码安全分析，其中用到 AgentCore Gateway（Amazon Bedrock AgentCore 的一项能力）、AgentCore memory（Amazon Bedrock AgentCore 的一项能力）以及外部工具集成。两者共同说明了如何组织 AI 驱动的 workflow，在加速交付的同时保持 human-in-the-loop 治理。两个实现都在各自的 GitHub 仓库中提供了完整的部署说明链接。

## 实践中的 AI-DLC 构建模式

AI-DLC 的构建阶段让 AI 提出架构、生成实现计划、产出代码并创建部署制品，团队成员则实时对技术决策作出澄清。这里描述的实现直接对应这一模式：

- **自动化制品生成**：agent 接收结构化输入（SQL schema 文件），制定详细计划，生成输出（Mermaid ER 图），并存储结果以供人工审核。
- **持续的代码质量把关**：多 agent 系统分析通过持续集成与持续交付（CI/CD）pipeline 推送的代码，产出安全评估、通用漏洞与暴露（CVE）检查以及策略合规报告，为人工决策提供依据。

两个系统共享一套构建在 AgentCore 之上的共同架构基础，展示了团队如何用模块化、易管理的组件组合出 AI 驱动的 workflow。

## 方案 1：从 SQL schema 生成 ER 图

这个 AWS Samples 项目使用 Amazon Bedrock AgentCore 上的 agentic AI workflow，从 SQL schema 文件自动生成 Mermaid ER 图。开发者检入 SQL 代码后，由 Amazon Simple Storage Service（Amazon S3）触发器与 AWS Lambda 函数构成的 workflow 会调用 AgentCore runtime，runtime 解析数据定义语言（DDL）生成 `.mmd` 图并保存回 Amazon S3。它只读取 schema 元数据（表、约束和外键），从不读取行数据，因此是 schema 到图自动化的一个干净参考。

### 业务挑战

管理持续演进 SQL schema 的数据库团队需要最新的实体关系文档。手工创建 ER 图耗时，而且文档经常与实际 schema 脱节。当 schema 变更通过 pull request 落地时，团队需要更新后的图，同时又不希望在开发 workflow 中增加手工文档步骤。

### 架构

该系统采用 serverless、事件驱动的架构，包含以下组件：

![Amazon S3 上传触发一个 Lambda 函数，该函数调用 AgentCore agent 生成 Mermaid ER 图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/31/ML-21366-1.png)

图 1：SQL schema 到 ER 图生成的事件驱动架构

- **S3 事件触发器**：上传到 Amazon S3 存储桶的 SQL 文件触发 AWS Lambda 函数，由它启动分析 workflow。
- **身份验证**：Amazon Cognito 提供 OAuth2 机器对机器（M2M）身份验证。客户端凭证存储在 AWS Systems Manager Parameter Store 中。
- **AgentCore runtime**：用 [Strands 框架](https://github.com/strands-agents/sdk-python)构建的容器化 agent 运行在 AgentCore runtime 上。该 agent 通过 Amazon Bedrock 使用 Claude Sonnet 4 解析 SQL DDL 语句并生成 Mermaid ER 图语法。（各 AWS 区域的模型可用性，请参阅[按模型的区域可用性](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。）
- **AgentCore memory**：提供持久化的会话上下文，90 天后过期，并支持在以往分析之间进行语义搜索以及增量的 schema 理解。
- **输出存储**：生成的 `.mmd` 图文件保存到 Amazon S3 的专用前缀下，并带有追踪源文件与生成时间戳的元数据。

workflow 按以下顺序推进：

- SQL 文件被上传到 Amazon S3（手动或通过 CI/CD pipeline）。
- Lambda 触发器读取文件内容，并通过 Cognito OAuth 完成身份验证。
- 触发器以 SQL 内容作为 payload 调用 AgentCore runtime agent。
- agent 分析 schema，识别表、列、约束和外键关系，然后生成完整的 Mermaid erDiagram。
- 图被保存到 Amazon S3，分析会话则存储在 AgentCore memory 中。

### 实现细节

agent 实现使用 `BedrockAgentCoreApp` 运行时封装，并通过 `@app.entrypoint` 装饰器注册处理函数：

```
from bedrock_agentcore.runtime import BedrockAgentCoreApp
from bedrock_agentcore.memory import MemoryClient
from strands import Agent
from strands.models import BedrockModel

app = BedrockAgentCoreApp()
model = BedrockModel(model_id="us.anthropic.claude-sonnet-4-5-20250929-v1:0", region_name="us-west-2")
erdiagram_agent = Agent(model=model)
memory_client = MemoryClient(region_name="us-west-2")

@app.entrypoint
async def generate_er_diagram(payload: Dict[str, Any]) -> Dict[str, Any]:
    sql_content = payload.get("sql_content", "")
    file_name = payload.get("file_name", "unknown_file.sql")
    # Generate diagram, store in memory, save to S3
    ...
```

关键设计决策包括：

- **分块处理**：大型 SQL 文件被切分为易处理的片段，分别独立分析，再合并为统一的图。这样可以在不超出上下文限制的前提下处理包含数百张表的 schema。
- **结构化 prompt**：agent 使用一套系统化的分析 prompt，在生成图语法之前先提取表、列、数据类型、主键与外键关系。
- **OpenTelemetry tracing**：每一步都以 span 与属性埋点，从而对处理时长、分块数量和错误归因提供可观测性。

完整实现（包括 OpenAI Codex skills 与 MCP server 集成）位于 sample-to-create-mermaid-entity-diagrams-from-sql-using-agentic-ai-on-agentcore 这个[仓库](https://github.com/aws-samples/sample-to-create-mermaid-entity-diagrams-from-sql-using-agentic-ai-on-agentcore)中。

## 方案 2：安全的软件交接

这个 serverless 代码安全分析方案使用 Amazon Bedrock AgentCore 自动扫描 Python 或 Java 代码，检查安全漏洞、依赖中的 CVE 风险以及策略违规。分析在代码从 GitLab pipeline 推送到 Amazon S3 时触发。随后基于 Strands 的 agent 使用 Amazon Bedrock 上的 Anthropic Claude Sonnet 模型评估代码，并调用运行在 AWS Lambda 上的 Model Context Protocol（MCP）工具进行 CVE 与策略检查。（各区域的模型可用性，请参阅[按模型的区域可用性](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。）结果（包括 1 到 10 分的质量分数和建议）存储在带语义搜索的 AgentCore memory 中，并通过实时的、基于会话的 Web 仪表板呈现。Amazon Cognito 提供身份验证，AgentCore Observability（Amazon Bedrock AgentCore 的一项能力）与 Amazon CloudWatch 提供监控。

### 业务挑战

为安全合规进行代码审查，需要横跨 CVE 数据库、组织编码策略和特定语言安全模式的专门知识。人工安全审查会在交付 pipeline 中造成瓶颈，而各团队对标准执行不一致又导致代码质量参差不齐。

### 架构

该方案通过多 agent 架构提供自动化的代码安全分析，用于在开发阶段之间实现安全的软件交接：

![上传的代码由 AgentCore agent 分析，该 agent 通过 AgentCore Gateway 调用 policy-check 与 CVE-scanner 工具](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/31/ML-21366-2.png)

图 2：用于自动化代码安全分析的多 agent 架构

- 代码文件被上传到 Amazon S3 存储桶（手动或通过 CI/CD pipeline）。AWS Lambda 触发器检测到新上传，并以 OAuth2 身份验证启动 AgentCore 分析 workflow。
- **带 MCP 工具的 AgentCore Gateway**：该 gateway 编排对外部工具集成的调用：**Policy Check Lambda**：按组织特定的安全策略校验代码。**CVE Database Check Lambda**：扫描依赖文件中的已知漏洞。
- **AgentCore runtime（Strands 框架）**：核心分析 agent 执行深度代码审查，包括结构评估、逻辑质量评价、内存与性能分析、安全问题检测，以及最佳实践合规性。
- **AgentCore memory**：存储分析结果并提供语义搜索能力，支持历史对比与趋势分析。
- **Dashboard Lambda**：提供 Web UI，以基于会话的方式展示结果，支持搜索以及在文件、违规项和质量指标之间多标签页导航。

### 关键能力

- **多维分析**：系统从结构质量、算法效率、安全态势和标准合规性几个维度评估代码，产出质量分数和具体建议。
- **memory 策略**：三种不同的自管理 memory 策略满足不同需求：*语义策略*：存储详细的代码分析发现、CVE 结果与策略违规，供按上下文检索。*汇总策略*：维护聚合指标与趋势，用于仪表板可视化。*用户偏好策略*：跨会话跟踪仪表板布局与筛选偏好。想进一步了解，请参阅 [AgentCore memory 策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-strategies.html)。
- **通过 AgentCore Gateway 集成 MCP 工具**：这项能力让 agent 在分析过程中按需调用外部工具（策略检查器、CVE 扫描器），而无需把工具调用或外部 API 逻辑硬编码进 agent 自身。

分析 agent 沿用与方案 1 相同的 AgentCore runtime 模式，并额外增加了经 AgentCore Gateway 路由的 MCP 工具调用：

```
from bedrock_agentcore.runtime import BedrockAgentCoreApp
from bedrock_agentcore.memory import AgentCoreMemory
from strands import Agent
from strands.models import BedrockModel

app = BedrockAgentCoreApp()
model = BedrockModel(model_id="us.anthropic.claude-sonnet-4-5-20250929-v1:0", region_name="us-west-2")
analysis_agent = Agent(model=model, tools=[analyze_code, check_quality])
memory = AgentCoreMemory(namespace="code-analysis")

@app.entrypoint
async def analyze_uploaded_code(payload: Dict[str, Any]) -> Dict[str, Any]:
    file_content = payload.get("file_content", "")
    file_name = payload.get("file_name", "unknown.py")
    session_id = payload.get("session_id", "")
    # Analyze code, store results in memory, return quality score
    ...
```

agent 从 AWS Lambda 触发器接收代码内容，使用基础模型（FM）执行多维分析，然后按需通过 AgentCore Gateway 调用外部工具（策略检查器、CVE 扫描器）。结果持久化到 AgentCore memory，供仪表板读取与历史对比。

关键设计决策包括：

- 多 agent 分离：代码分析 agent 只专注于质量评估。策略检查与 CVE 扫描委托给通过 AgentCore Gateway 调用的专用 AWS Lambda 函数，使每个组件职责单一、可独立更新。
- 基于会话的结果持久化：每次分析运行都会在 AgentCore memory 中创建唯一会话。仪表板按 session ID 读取结果，让开发者可以跨多次代码提交比较质量分数。
- 经 Gateway 中介的工具调用：外部工具通过 AgentCore Gateway 以 MCP 方式注册，而不是直接调用。这使 agent 与工具实现细节解耦，并允许在不修改 agent 代码的情况下新增工具。

完整实现位于 sample-agentic-secure-software-handoffs 这个[仓库](https://github.com/aws-samples/sample-agentic-secure-software-handoffs)中。

## 集成本地 agentic 工具：Kiro、OpenAI ChatGPT Codex 和 Claude Code

AgentCore 为已部署的、事件驱动的 agent 工作负载提供云上运行时，而开发 workflow 本身则受益于在开发者工作站上实现 AI-DLC 模式的本地 agentic 工具。

### Kiro agent 与 skills

[Kiro](https://kiro.dev) 通过结构化规格（specification）与自定义 agent skills 支持 AI-DLC 的 inception 与构建阶段：

- **规格驱动开发**：Kiro 把自然语言需求转换为带验收标准的结构化规格，再根据这些规格生成实现计划。这直接对应 AI-DLC 中“由 AI 制定计划、在执行前寻求人工确认”的模式。
- **自定义 skills**：团队可以定义可复用的 Kiro [agent skills](https://kiro.dev/docs/skills/)，把组织标准（编码模式、安全要求、架构准则）编码其中，使 AI 生成的代码始终达到企业质量门槛。
- **agentic 任务执行**：Kiro 的 agent 模式通过自主使用工具（创建文件、终端命令、搜索）完成跨多文件的实现任务，同时在每个规格检查点保持 human-in-the-loop 复核。

### OpenAI ChatGPT Codex（MCP server 与 skills）

该仓库还包含一个 OpenAI Codex 集成，展示同一套 ER 图生成 workflow 如何通过 MCP 与自定义 skills 扩展到其他编码 agent：

- **用于实时数据库 schema 访问的 MCP server**：一个本地基于 stdio 的 MCP server 通过 `INFORMATION_SCHEMA` 把 Codex 连接到 MySQL 或 Amazon Aurora MySQL 数据库。该 server 暴露三个工具（`schema_summary`、`generate_er_markdown` 和 `generate_mermaid`），让 Codex 可以查询表结构、列、索引和外键关系，而不访问表的行数据。
- **自定义 Codex skill**：一个 `SKILL.md` 文件把 ER 图生成 workflow 编码为可复用的 Codex skill，引导 agent 以稳定一致的质量完成 schema 分析与图创建。
- **安全的凭证管理**：数据库凭证从 AWS Secrets Manager 获取，并强制启用 TLS 校验，沿用 AgentCore 实现中所用的同一套安全模式。

### Claude Code（本地 agent）

Claude Code 作为本地命令行 agent 运行，与 AgentCore 部署形成互补：

- **快速原型**：在部署到 AgentCore runtime 之前，开发者用 Claude Code 在本地迭代 agent 逻辑、测试 prompt 并验证工具集成模式。
- **基础设施即代码生成**：Claude Code 生成部署脚本、Dockerfile、AWS Identity and Access Management（IAM）策略和 AWS CloudFormation 模板。这些制品遵循 AI-DLC 构建阶段产出的架构规格。
- **代码审查与重构**：本地 agent 依据项目规则与自定义指令执行第一轮审查，在代码进入 CI/CD pipeline 之前发现问题；代码进入 pipeline 后，则由安全软件交接系统提供权威的安全分析。

### 组合后的 workflow

使用这些工具的一个典型 AI-DLC bolt（短而高强度的工作周期）遵循这样的模式：

- **Inception**（Kiro）：把业务需求转换为带验收标准的规格。团队在一次 mob elaboration（集体细化）会议中校验 AI 生成的规格。
- **Construction**（Claude Code 与 Kiro）：生成实现代码、部署脚本和测试套件。本地 agent 负责文件生成与迭代细化，Kiro 负责任务编排。
- **Validation**（AgentCore）：通过 CI/CD 推送的代码触发自动化安全分析。多 agent 系统在合并之前给出质量评估。
- **Operations**（AgentCore）：生产 agent（例如 ER 图生成器）在 AgentCore runtime 上持续运行，由事件触发，以完整可观测性处理大规模工作负载。

## 最佳实践

基于这些系统的实现经验，我们建议以下做法：

- **分离 agent 的关注点**：为每个 agent 设计单一、定义清晰的职责。ER 图 agent 只生成 ER 图。可组合性来自编排，而不是把过多职责压在单个 agent 上。
- **用 AgentCore memory 维护上下文连续性**：持久化 memory 让 agent 能够从以往交互中学习、把当前分析与历史基线对比，并在无需重复处理的情况下跨会话保持状态。
- **从第一天就用 OpenTelemetry 埋点**：tracing 让 agent 行为、处理时长和失败模式变得可见。这对调试 prompt 效果和定位性能瓶颈至关重要。
- **把配置存放在 Parameter Store**：让配置与代码解耦。Cognito 凭证、memory ID、模型选择和存储桶名称都应能在运行时读取。
- **为大型输入实现分块处理**：把 agent 设计为能处理超出模型上下文窗口的输入：切分、独立分析，再合并结果。
- **用 Cognito M2M 身份验证保障安全**：服务间通信使用 OAuth2 客户端凭证流程。避免硬编码凭证或长期有效的 token。
- **通过 CI/CD 集成，而不是手工上传**：在生产环境中，把 agent 连接到仓库事件（merge request、pipeline 阶段），而不是要求手工上传文件。这里展示的 S3 触发器模式可以直接对应到 GitLab webhook 或 GitHub Actions 集成。
- **对生产环境的 agent 输出应用 Amazon Bedrock Guardrails：** 配置内容过滤策略、被禁止主题检测和 grounding 校验，确保 agent 生成的回答符合负责任 AI 标准。对于代码分析 agent，guardrails 可以拦截包含不安全代码模式或虚构 CVE 引用的输出。对于图生成 agent，grounding 检查会校验输出是否准确反映源 schema。把 guardrails 与自动化评估 pipeline 结合，以持续监控 agent 行为并标记偏离预期输出质量的情况。

## 结论

当有具体的实现模式作支撑时，AI-DLC 方法论才变得可落地。Amazon Bedrock AgentCore 提供运行时基础设施（容器化 agent、持久化 memory、安全的 gateway 以及外部工具集成），而 Kiro、Claude Code 这类本地工具则加速开发 workflow 本身。

从 `SQL-to-ER-Diagram` 示例开始，部署你的第一个 AgentCore agent。按顺序执行部署脚本，然后用 Secure software handoffs 示例，把这一模式扩展到多 agent 协作、MCP 工具集成以及由 CI/CD 驱动的触发器。
