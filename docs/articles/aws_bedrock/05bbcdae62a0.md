# Amazon Bedrock Custom Model Import 性能增强

现在，使用 [Amazon Bedrock Custom Model Import](https://aws.amazon.com/bedrock/custom-model-import/) 可获得显著的性能提升：通过先进的 PyTorch 编译和 CUDA graph 优化，降低端到端延迟、缩短首 token 时间（time-to-first-token），并提高吞吐量。借助 Amazon Bedrock Custom Model Import，你可以自带基础模型，在 Amazon Bedrock 中进行大规模部署和推理。

这些性能增强通常会带来模型初始化开销，可能影响容器冷启动时间。Amazon Bedrock 通过编译产物缓存来解决这一问题。这一创新在带来性能提升的同时，保持了客户对 CMI 既有的冷启动性能指标预期。

在使用这些优化部署模型时，客户会在首次启动模型时经历一次性的初始化延迟，但此后的每个模型实例都将不再有这一开销——在性能与扩缩容时的快速启动之间取得平衡。

本文介绍如何使用 Amazon Bedrock Custom Model Import 中的这些改进。

## 优化如何运作

推理引擎会缓存编译产物，消除启动时的重复计算工作。当第一个模型实例启动时，它会生成编译产物，包括优化后的计算图和 kernel 配置。这些产物会被存储起来供后续实例复用，从而跳过编译过程，启动更快。

系统会根据模型配置参数（如 batch size、上下文长度和硬件规格）计算一个唯一标识符。该标识符用于确认缓存产物与每个模型实例的要求相匹配，从而可以安全地复用。

存储的产物包含完整性校验，以检测传输或存储过程中是否损坏。如果发生损坏，系统会清除缓存并重新生成产物。在此过程中模型仍保持可用。

## 性能提升

我们测试了不同模型规模和工作负载模式下的性能。基准测试对比了编译缓存优化前后的模型，在 1 到 32 个并发请求的不同并发级别下测量关键推理指标。

## 技术实现：编译缓存架构

采用编译缓存架构后，性能得以提升，因为系统不再在启动时重复计算工作。当模型的第一个实例启动时，推理引擎会执行若干计算密集型操作：

- **计算图优化**：引擎分析模型的神经网络架构，生成针对目标硬件定制的优化执行计划。这包括算子融合、内存布局优化以及识别并行执行的机会。
- **Kernel 编译**：针对特定的模型配置、batch size 和序列长度编译并优化 GPU kernel。该编译过程生成高度优化的 CUDA 代码，最大化 GPU 利用率。
- **内存规划**：引擎确定最优的内存分配策略，包括张量放置和缓冲区复用模式，以最小化内存碎片和数据移动。

过去，每个新模型实例都会独立重复这些操作，消耗大量初始化时间。有了编译缓存，第一个实例生成这些产物并帮助安全地存储它们。后续实例检索并复用这些预编译产物，完全跳过编译阶段。系统使用基于配置的标识符（包含模型架构、batch size、上下文长度和硬件规格），确保缓存产物与实例要求精确匹配，在保持正确性的同时，使各实例都能获得一致优化的性能。系统还包含校验和验证，以检测损坏的缓存文件。如果验证失败，系统会自动回退到完整编译，在缓存可用时既保证可靠性又保持性能优势。

## 基准测试设置

我们在贴近生产环境的条件下进行基准测试：

**测试配置：** 每次基准测试运行都在每个实例上部署单个模型副本，且未启用自动扩缩容。这种隔离配置确保性能测量反映优化的真实能力，不受扩缩容行为或多个模型副本之间资源争用的干扰。通过维持这一受控环境，我们可以将性能提升直接归因于编译缓存增强，而非基础设施扩缩容效应。

**工作负载模式**：我们评估了两种代表性的 I/O 模式，覆盖常见用例：

- **1000/250 token**（1000 输入、250 输出）：代表中等长度的 prompt 和适中的响应长度，典型场景包括对话式 AI 应用、代码补全任务和交互式问答系统
- **2000/500 token**（2000 输入、500 输出）：代表更长的上下文窗口和更充实的响应，常见于文档分析、详细代码生成和全面的内容创作任务

我们选择这些模式是因为延迟会随输入输出比例而变化。跨不同的 token 分布，延迟特性会因输入处理与输出生成的比例不同而有显著差异。

**并发级别**：测试在六个并发级别（1、2、4、8、16、32 个并发请求）下进行，以评估不同负载条件下的性能。这一递进遵循 2 的幂次，使我们能够观察系统如何从单用户场景扩展到中等多用户负载。并发测试揭示了优化在负载增加时是否仍能保持优势，并有助于识别在更高请求量下出现的潜在瓶颈。

**指标：** 我们在各次测试运行中采集了全面的延迟统计数据，包括最小值、最大值、平均值、P50（中位数）、P95 和 P99 百分位值。这一完整的统计分布有助于洞察典型性能和尾部延迟表现。下一节中的图表显示平均延迟，可均衡地反映整体性能。希望深入分析延迟分布的读者可以参考附带数据表获取完整的统计明细。

## 性能指标定义

我们测量了以下性能指标：

- **首 token 时间（Time to First Token，TTFT）** – 从提交请求到模型生成并返回其响应的第一个 token 所经过的时间。该指标对交互应用的用户体验至关重要，因为它决定了用户多快能看到模型开始响应。较低的 TTFT 值会带来更强的响应感，对于用户等待响应开始的流式应用尤其重要。
- **端到端延迟（End-to-End Latency，E2E）** – 从提交请求到完整响应送达的总时间，涵盖输入处理、token 生成和输出交付等处理阶段。它代表获得完整响应的全部等待时间。
- **吞吐量（Throughput）** – 在并发请求中每秒处理的 token 总数（包括输入和输出）。吞吐量越高，意味着同样的硬件可以服务更多用户。
- **每秒输出 token 数（Output Tokens Per Second，OTPS）** – 模型在响应生成阶段生成输出 token 的速率。该指标专门衡量生成速度，对于用户能实时看到 token 出现的流式应用尤其相关。更高的 OTPS 值带来更流畅、看起来更快的文本生成，提升流式响应的感知响应速度。

## 推理性能提升

编译缓存优化在各项测量指标上都带来了显著改善，从根本上帮助提升用户体验和基础设施效率。以下结果展示了两个代表性模型所取得的性能提升，说明这些优化如何横跨不同模型架构和用例发挥作用。

#### **Granite 20B Code Model**

作为针对代码生成任务优化的较大模型，Granite 20B 从编译缓存中获得的收益尤为显著。以下 P50（中位数）指标使用 1000 输入 / 250 输出的 token 工作负载模式测得：

- **首 token 时间（TTFT）**：从 989.9ms 降至 120.9ms（**提升 87.8%**）。用户看到初始响应的速度提升 8 倍。
- **端到端延迟（E2E）**：从 12,829ms 降至 5,290ms（**提升 58.8%**）。完整请求在一半时间内完成，对话轮转更快。
- **吞吐量**：从 360.5 提升至 450.8 token/秒（**提升 25.0%**）。每个实例每秒多处理 25% 的 token。
- **每秒输出 token 数（OTPS）**：从 44.8 提升至 48.3 token/秒（**提升 7.8%**）。更快的 token 生成提升流式响应质量。
