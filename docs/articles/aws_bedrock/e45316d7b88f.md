# 使用 Amazon Bedrock AgentCore 情节记忆构建能从经验中学习的 agent

如今，大多数 agent 只基于当前交互中可见的信息运行：它们能访问事实与知识，却记不住自己此前是如何解决类似问题的，也记不住某些方法为什么会奏效或为什么会失败。这让它们在随时间学习和改进方面的能力出现了明显缺口。[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 情节记忆（episodic memory）通过捕获经验层面的知识并将其呈现出来，弥补了这一局限。语义记忆帮助 agent 记住自己知道什么，而情节记忆记录的是它如何走到那里：目标、推理步骤、行动、结果和反思。通过把每次交互转换为结构化的 episode（情节），你可以让 agent 既能回忆知识，又能解读并复用此前的推理。这有助于 agent 跨会话适应、避免重复犯错，并让规划随时间不断演进。

[Amazon Bedrock AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html) 是一项全托管服务，帮助开发者通过短期记忆和长期智能记忆两种能力，构建具备上下文感知能力的 AI agent。要了解更多，请参阅 [Amazon Bedrock AgentCore Memory：构建具备上下文感知的 agent](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-agentcore-memory-building-context-aware-agents/) 和 [构建更聪明的 AI agent：AgentCore 长期记忆深入解析](https://aws.amazon.com/blogs/machine-learning/building-smarter-ai-agents-agentcore-long-term-memory-deep-dive/)。

本文带你走完组织与存储 episode 的完整架构，讨论反思模块，并分享有力的基准测试结果，这些结果展示了 agent 任务成功率的显著提升。

## 设计 agent 情节记忆的关键挑战

情节记忆让 agent 能够保留自身经验并对其推理。不过，设计这样一个系统需要解决若干关键挑战，以确保经验保持连贯、可评估、可复用：

- 保持时间与因果上的连贯性 – episode 需要保留推理步骤、行动和结果的顺序与因果流，使 agent 能理解自己的决策是如何演变的。
- 检测并切分多个目标 – 一次会话中常常出现重叠或漂移的目标。情节记忆必须识别并把它们分开，避免把不相关的推理轨迹混在一起。
- 从经验中学习 – 每个 episode 都应判定成功或失败。反思随后应比较过去相似的 episode，找出可泛化的模式和原则，让 agent 把这些洞见适配到新目标，而不是重放此前的轨迹。

下一节将介绍如何构建 AgentCore 情节记忆策略，涵盖其提取、存储、检索和反思 pipeline，以及这些组件如何协同把经验转化为自适应智能。

### Episode 提取模块

episode 提取模块是情节策略中的基础步骤，它把原始的用户与 agent 交互数据转换为结构化、有意义的 episode。我们采用两阶段方法：这两个阶段既捕获每次交互中细粒度的分步机制（称为 turn 提取），又捕获更宏观的、按 episode 组织的知识以形成连贯的叙事（称为 episode 提取）。打个比方，可以把它想成开会时做记录（turn 层级）和在会议结束时写会议纪要（episode）。两个阶段都有价值，但在从经验中学习时，它们服务于不同的目的。

在 episode 提取的第一阶段，系统进行 turn 级处理，以弄清哪些做对了、哪些做错了。这里会把用户与 agent 之间称为对话轮次（conversational turn）的单次交互单元识别出来、切分，并转换为以下维度的结构化摘要：

- **Turn 情境** – 简要描述本轮中 assistant 所回应的情况与上下文。这包括即时上下文、可能跨多个轮次的用户总体目标，以及塑造了本次交流的相关历史。
- **Turn 意图** – assistant 在本轮的具体目的和主要目标，实质上回答的是“assistant 此刻想完成什么？”
- **Turn 行动** – 详细记录交互过程中所采取的具体步骤，说明使用了哪些具体工具、向每个工具提供了什么输入参数，以及 assistant 如何把意图转化为可执行的行动。
- **Turn 思考** – assistant 决策背后的推理，解释选择某个工具和某种做法背后的“为什么”。
- **Turn 评估** – 诚实评估 assistant 是否成功达成本轮声明的目标，就所选方法和所采取行动的有效性给出即时反馈。
- **目标评估** – 从更宽的视角判断用户在整段对话中的总体目标看起来是否已被满足，或正在推进至完成，超越单个轮次来评估整体成功。

处理并结构化各个 turn 之后，系统会在用户完成其目标（由大语言模型检测）或交互结束时进入 episode 提取阶段。这有助于捕获完整的用户旅程，因为用户的目标常常跨越多个轮次，仅凭单个 turn 的数据无法说明总体目标是否达成，也无法说明整体策略是什么样子。在这一阶段，按顺序相关的多个 turn 会被综合为连贯的情节记忆，捕获从最初请求到最终解决的完整用户旅程：

- **Episode 情境** – 引发用户需要帮助的更宏观的背景情况
- **Episode 意图** – 清晰表述用户最终想完成什么
- **成功评估** – 针对每个 episode，明确判定该段对话是否达成了其预期目的
- **评估依据** – 成功或失败判定的具体理由，落在能体现用户目标被推进或被推远的特定对话片段上
- **Episode 洞见** – 针对当前 episode，捕捉已被证明有效的做法，并识别需要避免的坑

### 反思模块

反思模块体现了 Amazon Bedrock AgentCore 情节记忆从过去经验中学习的能力，它生成洞见以帮助改进未来的表现。正是在这里，单个 episode 中的学习成果演化为可泛化的知识，能够指导 agent 应对各种不同场景。

反思模块通过跨多个 episode 的反思（cross-episodic reflection）运作：它基于用户意图检索过去相似的、成功的 episode，并在多个 episode 之间进行反思，以获得更具泛化性的洞见。当新的 episode 被处理时，系统会执行以下动作：

- 以用户意图作为语义键，系统从向量存储中识别历史上成功的、相关的 episode，这些 episode 共享相似的目标、上下文或问题领域。
- 系统分析主 episode 与相关 episode 之间的模式，寻找关于哪些做法能在不同上下文中稳定奏效的可迁移洞见。
- 现有反思知识会被审查，要么用新洞见加以增强，要么用跨 episode 分析新发现的模式加以扩展。

流程结束时，每条反思记忆记录包含以下信息：

- **用例** – 该洞见在何时、何地适用，包括相关的用户目标和触发条件
- **提示（洞见）** – 可操作的指导，涵盖工具选择策略、有效做法和需要避免的坑
- **置信度评分** – 一个分数（0.1–1.0），表示该洞见在不同场景间的泛化程度

episode 为 agent 提供了类似问题此前是如何被解决的具体样例。这些案例展示了所用到的具体工具、所施加的推理以及取得的结果，既包括成功也包括失败。这形成了一个学习框架，让 agent 能沿用已被证明有效的策略，并避开已被记录下来的错误。

反思记忆则从多个 episode 中提取模式，给出战略层面的洞见。它呈现的不是单个案例，而是哪些工具效果最好、哪些决策方式会成功、哪些因素会左右结果。这些经过提炼的原则为 agent 应对复杂场景提供了更高层的指引。

### 自定义覆盖配置

尽管内置的记忆策略已经覆盖了常见用例，但很多领域仍需要量身定制的记忆处理方式。系统支持通过自定义 prompt 覆盖内置策略，这些 prompt 扩展了内置逻辑，帮助团队把记忆处理适配到自己的具体需求。你可以实现以下自定义覆盖配置：

- **自定义 prompt** – 这类 prompt 聚焦于判据和逻辑，而非输出格式，帮助开发者定义以下内容：提取判据 – 哪些信息会被提取或被过滤掉。整合规则 – 相关记忆应如何整合。冲突消解 – 如何处理相互矛盾的信息。洞见生成 – 跨 episode 的反思如何综合。
- **自定义模型：** AgentCore Memory 支持在记忆提取、整合和反思操作中选择自定义模型。这种灵活性帮助开发者根据自身具体需求在准确性和延迟之间取得平衡。你可以在创建作为策略覆盖的 `_memory_resource_` 时通过 API 定义它们，也可以通过 Amazon Bedrock AgentCore 控制台定义（如下图所示）。
- **命名空间：** 命名空间为 episode 和反思提供层级化的组织方式，让你能以不同粒度访问 agent 的经验，并带来自然的逻辑分组。例如，为旅行应用设计命名空间时，episode 可以存放在 `travel_booking/users/userABC/episodes` 下，反思则可以位于 `travel_booking/users/userABC`。注意，反思的命名空间必须是 episode 命名空间的子路径。

## 性能评估

我们在零售和航空领域的真实目标完成基准上评估了 Amazon Bedrock AgentCore 情节记忆（样本取自 [τ2-bench）](https://arxiv.org/abs/2506.07982)。这些基准包含的任务复刻了真实的客服场景，其中 agent 需要帮助用户达成特定目标。

实验中我们比较了三种不同的设置：

- 对于**基线**，我们运行 agent（基于 Anthropic 的 Claude 3.7 构建），不接入记忆组件。
- 对于记忆增强的 agent，我们探索了两种使用记忆的方法：**上下文学习示例** – 第一种方法把提取出的 episode 作为上下文学习（in-context learning）示例。具体来说，我们构建了一个名为 `retrieve_exemplars` 的工具（工具定义见附录），agent 可以通过发起查询（例如“如何获得退款？”）来使用它，从 episode 仓库中取得分步说明。当 agent 遇到类似问题时，检索到的 episode 会被加入上下文，引导 agent 采取下一步行动。**以反思作为指引** – 我们探索的第二种方法是 reflection-as-guidance。具体来说，我们构建了一个名为 `retrieve_reflections` 的工具（工具定义见附录），agent 可以用它来访问来自过去经验的更宏观的洞见。与 `retrieve_exemplars` 类似，agent 可以生成查询来检索反思作为上下文，从而获得洞见，就策略和方法做出有依据的决策，而不是取得具体的分步动作。

我们采用了以下评估方法：

- 基线 agent 先处理一批历史客户交互，这些交互成为记忆提取的素材来源。
- 随后 agent 接收来自 τ2-bench 的新用户查询。
- 每个查询并行尝试四次。
- 评估时，在这四次尝试上衡量通过率指标。Pass^k 衡量的是 agent 在四次尝试中至少成功 k 次的任务占比：  Pass^1：至少成功一次（衡量能力） Pass^2：至少成功两次（衡量可靠性） Pass^3：至少成功三次（衡量一致性）

下表中的结果显示出两个领域、多次尝试上的明显改进。

| 系统 | agent 使用的记忆类型 | 零售 |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- | --- | --- |
|  |  | Pass^1 | Pass^2 | Pass^3 | Pass^1 | Pass^2 | Pass^3 |
| 基线 | 无记忆 | 65.80% | 49.70% | 42.10% | 47% | 33.30% | 24% |
| 记忆增强 agent | 以 episode 作为 ICL 示例 | 69.30% | 53.80% | 43.40% | 55.00% | 46.70% | 43.00% |
|  | 跨 episode 反思记忆 | 77.20% | 64.30% | 55.70% | 58% | 46% | 41% |

记忆增强的 agent 在各领域、各一致性水平上都稳定优于基线。关键在于，这些结果表明不同的记忆检索策略更适合不同的任务特征。跨 episode 反思相对基线把 Pass^1 提升了 +11.4%，Pass^3 提升了 +13.6%，这说明在处理交互模式多样的开放式客服场景时，泛化的战略洞见尤其有价值。相比之下，航空领域的特点是复杂、基于规则的策略和多步骤流程，更受益于以 episode 作为示例的做法，它取得了最高的 Pass^3（43.0%，反思为 41.0%）。这表明具体的分步示例能帮助 agent 可靠地走通结构化的流程。相对提升在更高的一致性阈值（Pass^3）上最为明显，在那里记忆帮助 agent 避开那些导致间歇性失败的失误。

## 使用情节记忆的最佳实践

用好情节记忆的关键在于知道何时使用，以及哪种类型适合你的情况。本节讨论我们总结出的最有效做法。

### 何时使用情节记忆

当你把合适的记忆类型匹配到当前需求时，情节记忆能带来最大价值。它非常适合上下文很重要、过去经验影响显著的复杂多步任务，例如调试代码、规划行程和数据分析。对于重复性工作流——从前几次尝试中学习能显著改善结果——以及积累的专业经验确实能带来差别的领域特定问题，它尤其有价值。

不过，情节记忆并不总是合适的选择。对于简单的一次性提问，比如查天气或不需要推理和上下文的基础事实，可以跳过它。简单的客服对话、基础问答或闲聊，也不需要情节记忆所增加的高级能力。情节记忆的真正收益要随时间才能显现。对短任务而言，会话摘要就提供了足够的信息。但对复杂任务和重复性工作流，情节记忆帮助 agent 在过去经验的基础上继续积累，并持续提升表现。

### 选择 episode 还是反思

当你面对相似的具体问题、需要清晰的指引时，episode 效果最好。如果你在调试一个无法渲染的 React 组件，episode 能确切地展示类似问题此前是如何被修好的，包括所用的具体工具、思考过程和结果。当一般性建议不够用时，它们给你真实案例，展示从定位问题到解决问题的完整路径。

当你需要在更宽的上下文里获得战略层面的指引，而不是具体的分步解决方案时，反思记忆效果最好。当你面对的是新类型的问题、需要理解一般原则时，就用反思，例如“数据可视化任务最有效的方法是什么？”或“对于 API 集成问题，哪些调试策略往往效果最好？”当你要就工具选择和采用哪种方法做高层决策，或者想理解某些模式为何总是成功或失败时，反思尤其有价值。

在开始任务之前，查看反思以获取策略指引，查看相似的 episode 以寻找解法模式，并找出此前尝试中被记录下来的高置信度失误。在任务进行中，遇到障碍时查看 episode，在选工具时使用反思洞见，并想一想你当前的处境与过去的例子有何不同。

## 结论

情节记忆填补了当前 agent 能力中的一个关键缺口。通过存储完整的推理路径并从结果中学习，agent 可以避免重复犯错，并在成功的策略上继续积累。

情节记忆与摘要记忆、语义记忆和偏好记忆一起，构成了 Amazon Bedrock AgentCore 的完整记忆框架。它们各有分工：摘要记忆管理上下文长度，语义记忆存储事实，偏好记忆处理个性化，情节记忆捕获经验。这种组合让 agent 既有结构化的知识，又有实用的经验，从而更有效地处理复杂任务。

要了解更多关于情节记忆的内容，请参阅[情节记忆策略（Episodic memory strategy）](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/episodic-memory-strategy.html)、如何最好地[检索 episode 以提升 agentic 表现](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/episodic-memory-strategy.html#memory-episodic-retrieve-episodes)，以及 [AgentCore Memory GitHub 示例](https://github.com/awslabs/amazon-bedrock-agentcore-samples/tree/main/01-tutorials/04-AgentCore-memory)。

#### Episode 示例

下面是一个把提取出的 episode 用作上下文学习示例的例子：

```
** Context **
A customer (Jane Doe) contacted customer service expressing frustration 
about a recent flight delay that disrupted their travel plans and wanted 
to discuss compensation or resolution options for the inconvenience they 
experienced.

** Goal **
The user's primary goal was to obtain compensation or some form of resolution 
for a flight delay they experienced, seeking acknowledgment of the disruption 
and appropriate remediation from the airline.

---

### Step 1:

**Thought:**
The assistant chose to gather information systematically rather than making 
assumptions, as flight delay investigations require specific reservation and 
flight details. This approach facilitates accurate assistance and demonstrates 
professionalism by acknowledging the customer's frustration while taking concrete 
steps to help resolve the issue.

**Action:**
The assistant responded conversationally without using any tools, asking the 
user to provide their user ID to access reservation details.

--- End of Step 1 ---

...

** Episode Reflection **:
The conversation demonstrates an excellent systematic approach to flight 
modifications: starting with reservation verification, then identifying 
confirmation, followed by comprehensive flight searches, and finally processing 
changes with proper authorization. The assistant effectively used appropriate 
tools in a logical sequence - get_reservation_details for verification, get_user_details 
for identity/payment info, search_direct_flight for options, and update tools for 
processing changes. Key strengths included transparent pricing calculations, 
proactive mention of insurance benefits, clear presentation of options, and proper 
handling of policy constraints (explaining why mixed cabin classes aren't allowed). 
The assistant successfully leveraged user benefits (Gold status for free bags) and 
maintained security protocols throughout. This methodical approach made sure user 
needs were addressed while following proper procedures for reservation modifications.
```

#### 反思示例

**Use Cases:**
This applies when customers request flight modifications or changes that 
are blocked by airline policies (such as basic economy no-change rules, 
fare class restrictions, or booking timing limitations). Rather than simply 
declining the request, this pattern involves immediately searching for 
alternative solutions to help customers achieve their underlying goals. 
It's particularly valuable for emergency situations, budget-conscious travelers, 
or when customers have specific timing needs that their current reservations 
don't accommodate.

**Hints:**
When policy restrictions prevent the requested modification, immediately pivot 
to solution-finding rather than just explaining limitations. Use search_direct_flight

separate bookings or different approaches. Present both the policy constraint 
explanation AND viable alternatives in the same response to maintain momentum toward 
resolution. Consider the customer's underlying goal (getting home earlier, 
changing dates, etc.) and search for flights that accomplish this objective. 
When presenting alternatives, organize options clearly by date and price, highlight 
budget-friendly choices, and explain the trade-offs between keeping existing reservations 
versus canceling and rebooking. This approach transforms policy limitations into problem-solving 
opportunities and maintains customer satisfaction even when the original request cannot be fulfilled.
