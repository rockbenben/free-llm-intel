# 在 Amazon Bedrock 上运行 MiniMax 模型

越来越多的组织采用开放权重的基础模型（foundation model，FM）来支撑生产环境的 AI 工作负载，从 agentic 编程助手到长上下文文档分析。随着这些工作负载从试验走向企业部署，每一项模型选型决策都受两个要求支配：模型必须提供工作负载所需的能力，推理环境必须满足组织的安全与合规要求。客户希望在不牺牲数据保护、法规对齐或运营控制的前提下，获得前沿的第三方模型。

为满足这一需求，Amazon Bedrock 提供了一项完全托管的服务，用于访问来自独立模型提供商的领先 FM，推理完全运行在 AWS 运营的基础设施上。你的 prompt 与补全结果不会被用于训练任何模型，你的内容也不会与模型提供商共享。

[MiniMax](https://minimax.io) 系列已在 Amazon Bedrock 上可用，为你提供三个开放权重模型，以匹配不同的生产工作负载。该系列专为软件工程与 agentic 用例打造。Amazon Bedrock 上最新的模型 [MiniMax M2.5](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-minimax-minimax-m2-5.html) 专门针对 agent 原生执行训练。以下章节将介绍每个模型提供的能力，以及如何在它们之间做选择。

在本文中，我们逐步介绍如何在 Amazon Bedrock 上开始使用 MiniMax 模型，包括这些模型支持的能力、可用的服务层级、按需推理如何扩展以支撑你的工作负载，以及你可以用来访问它们的多种 API。借助这些模型，客户可以构建 agentic 应用、长上下文文档分析 pipeline 和软件工程 workflow，这一切都由 AWS 的安全与运营保障提供支撑。

## 关于 MiniMax

[MiniMax](https://minimax.io/) 是一家全球化的 AI 技术公司，开发多模态基础模型，其研究重点是面向生产规模负载的高效架构。它的 M2 系列大语言模型以完全托管的开放权重模型形式在 Amazon Bedrock 上提供，构建在混合专家（mixture-of-experts，MoE）架构之上：每个 token 只激活总参数中的一小部分，从而以一小部分推理成本提供大得多的稠密模型的知识容量。

M2 系列在编程与 agentic 工作负载上表现出色，其中 M2.5 通过侧重工具调用、多步任务分解和长周期编程任务的训练，专为 agent 原生执行而打造。由于模型是开放权重的，你可以独立评估模型架构与训练方法，在代表性工作负载上运行自己的 benchmark，并在需要定制时基于专有数据做 fine-tune。以上这些都可以通过一项完全托管的 AWS 服务完成，无需自行准备基础设施、托管模型权重或运维推理栈。

完整的模型目录请参阅 [Amazon Bedrock 上的 MiniMax 模型文档](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards-minimax.html)。

## Amazon Bedrock 上的 MiniMax 模型

Amazon Bedrock 支持 MiniMax M2 系列中的三个模型。MiniMax M2（`minimax.minimax-m2`）最先发布，确立了该系列的核心能力：强大的多语言文本生成、扎实的推理与编程表现，以及 100 万 token 的上下文窗口。随后是 MiniMax M2.1（`minimax.minimax-m2.1`），在推理深度、编程准确度和指令遵循方面带来了有针对性的改进。MiniMax M2.5（`minimax.minimax-m2.5`）是 Amazon Bedrock 上最新的模型，专门针对 agent 原生执行训练。随着新版本的推出，Amazon Bedrock 会持续扩充其 MiniMax 模型目录。最新列表请参阅 [MiniMax 的 Amazon Bedrock 模型文档](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards-minimax.html)。下表汇总了主要差异。

|  | **MiniMax M2** | **MiniMax M2.1** | **MiniMax M2.5** |
| --- | --- | --- | --- |
| **模型 ID** | `minimax.minimax-m2` | `minimax.minimax-m2.1` | `minimax.minimax-m2.5` |
| **上下文窗口** | 1M tokens | 196K tokens | 196K tokens |
| **最大输出 token 数** | 8K | 8K | 8K |
| **训练重点** | 多语言、推理、编程 | 改进的推理、编程与指令遵循 | agent 原生、在 agentic 脚手架上的强化学习（RL） |
| **服务层级** | Standard、Priority、Flex | Standard、Priority、Flex | Standard、Priority、Flex |
| **最适合** | 长上下文或多语言、通用场景 | 复杂指令遵循或多步推理 | agentic、工具调用或编程密集型 |

MiniMax M2.5 采用[混合专家](https://huggingface.co/MiniMaxAI/MiniMax-M2)（MoE）架构，总参数 2300 亿，每个 token 激活 100 亿。就推理成本而言，MoE 的路由机制是关键因素。它提供 230B 模型的知识容量，而每次前向传播消耗的算力只与 10B 的激活参数成正比。

## 在 Amazon Bedrock 上访问 MiniMax 模型的两个端点

Amazon Bedrock 提供两个用于调用 MiniMax 模型的端点：`bedrock-mantle` 与 `bedrock-runtime`。

Amazon `bedrock-mantle` 端点（`https://bedrock-mantle.{region}.api.aws/v1`）是 Amazon Bedrock 下一代推理引擎的公共 API。它使用 Chat Completions API，也就是与 OpenAI Python 和 TypeScript SDK 相同的接口，因此已经使用该 SDK 的团队只需更新 base URL 和模型 ID，即可切换到 Amazon Bedrock 上的 MiniMax 模型。它支持 Amazon Bedrock API key、project 以及客户端侧的工具调用。对大多数工作负载，我们推荐 `bedrock-mantle` 端点。

`bedrock-runtime` 端点（`https://bedrock-runtime.{region}.amazonaws.com`）通过 AWS SDK 使用 Converse 和 InvokeModel API。当你需要 Amazon Bedrock 的原生功能，例如 Guardrails、Agents、Flows 和模型评估时，请使用这个端点——这些功能目前通过 `bedrock-runtime` 提供。

在接下来的章节中，我们将演示这两个端点，先从推荐的 `bedrock-mantle` 端点与 Chat Completions API 开始。

## 在 Amazon Bedrock 中开始使用 MiniMax M2.5

完成以下步骤，即可开始在 Amazon Bedrock 中使用 MiniMax M2.5。

### 控制台 playground

- 打开 [Amazon Bedrock 控制台](https://console.aws.amazon.com/bedrock/)，在左侧菜单的 **Test** 分区中选择 **Chat/Text playground**。
- 在 playground 中间选择 **Select model**。
- 在类别列表中选择 **MiniMax**，然后选择 **MiniMax M2.5**。
- 选择 **Apply** 以加载模型。
- 确认模型已加载。模型名称会出现在 playground 页眉中，聊天界面已可输入。

要演示 M2.5 的推理与代码生成能力，可以在 playground 中试试下面这个 prompt：

*“设计一个 Python 微服务，对外暴露用于管理任务队列的 REST API。要包含错误处理、输入校验，并编写单元测试。解释你的设计决策。”*

### 使用 bedrock-mantle 端点（推荐）

#### 前置条件

使用 `bedrock-mantle` 端点，你需要一个 [Amazon Bedrock API key](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html)，或为 SigV4 配置好的 AWS 凭证。要授予对 `bedrock-mantle` 端点的访问权限，请使用以下最小策略：

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "BedrockMantleInference",
            "Effect": "Allow",
            "Action": [
                "bedrock-mantle:CreateInference",
                "bedrock-mantle:Get*",
                "bedrock-mantle:List*"
            ],
            "Resource": "arn:aws:bedrock-mantle:us-east-1:111122223333:project/*"
        },
        {
            "Sid": "BedrockMantleApiKeyAccess",
            "Effect": "Allow",
            "Action": "bedrock-mantle:CallWithBearerToken",
            "Resource": "*"
        }
    ]
}
```

把 111122223333 替换为你的 AWS 账户 ID，并把 AWS Region 限定为你实际使用的区域。第一条 statement 覆盖 SigV4 认证。第二条覆盖 Amazon Bedrock API key（bearer token）认证。如果你只用 SigV4，可以省略第二条。要控制哪些身份可以生成或使用 Amazon Bedrock API key，请参阅[控制生成和使用 Amazon Bedrock API key 的权限](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys-permissions.html)。要把组织限制为只使用已批准的模型，请使用[服务控制策略（SCP）](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html)。

下面的示例使用 [OpenAI Python SDK](https://github.com/openai/openai-python) 作为客户端库来调用 `bedrock-mantle` 端点。使用 OpenAI SDK 时，你需要一个 [Amazon Bedrock API key](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html)。对于生产负载，请使用短期 API key：它们会自动过期（最长 12 小时），并继承生成它们的 AWS Identity and Access Management（IAM）角色的权限。如果你已经在使用 AWS 凭证而没有 API key，可以用 [aws-bedrock-token-generator](https://pypi.org/project/aws-bedrock-token-generator/) 包基于这些凭证生成短期 bearer token。

**注意：** 本文中的代码示例会调用 MiniMax M2.5，每次模型调用都会产生按 token 计的费用。当前费率请参阅 [Amazon Bedrock 定价页面](https://aws.amazon.com/bedrock/pricing/)。

```
import boto3
from openai import OpenAI

# Retrieve the Amazon Bedrock API key from AWS Secrets Manager
secrets_client = boto3.client("secretsmanager", region_name="us-east-1")
api_key = secrets_client.get_secret_value(SecretId="bedrock-api-key")["SecretString"]

client = OpenAI(
    base_url="https://bedrock-mantle.us-east-1.api.aws/v1",
    api_key=api_key,
)

response = client.chat.completions.create(
    model="minimax.minimax-m2.5",
    messages=[
        {"role": "user", "content": "Explain the benefits of mixture-of-experts architectures for production inference."}
    ],
    max_tokens=512,
)

print(response.choices[0].message.content)
```

**注意：** 这些示例从 [AWS Secrets Manager](https://docs.aws.amazon.com/secretsmanager/) 获取 Amazon Bedrock API key。本地开发时，你也可以改为从环境变量读取 key，但在生产环境中要避免这种做法。请使用 AWS Secrets Manager 或其他密钥存储。

#### 工具调用

MiniMax M2.5 专为 agentic workflow 设计，因此非常适合工具调用场景。在工具调用 workflow 中，你定义模型可以调用的函数（工具），模型根据用户请求决定何时调用它们，你的应用执行该函数并返回结果，供模型纳入最终回答。

下面的示例端到端演示了这一模式。我们定义一个 `get_weather` 工具，发送一条用户消息，让模型请求工具调用，用模拟数据运行该函数，再把结果传回去，让模型生成自然语言回答。

```
import json
import boto3
from openai import OpenAI

# Retrieve the Amazon Bedrock API key from AWS Secrets Manager
secrets_client = boto3.client("secretsmanager", region_name="us-east-1")
api_key = secrets_client.get_secret_value(SecretId="bedrock-api-key")["SecretString"]

client = OpenAI(
    base_url="https://bedrock-mantle.us-east-1.api.aws/v1",
    api_key=api_key,
)

tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Get the current weather for a given location",
            "parameters": {
                "type": "object",
                "properties": {
                    "location": {
                        "type": "string",
                        "description": "City and country (e.g., Seattle, US)"
                    },
                    "unit": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"],
                        "description": "Temperature unit"
                    }
                },
                "required": ["location"]
            }
        }
    }
]

# Step 1: Send the user request with tool definitions
messages = [
    {"role": "user", "content": "What's the weather like in Seattle?"}
]

response = client.chat.completions.create(
    model="minimax.minimax-m2.5",
    messages=messages,
    tools=tools,
    tool_choice="auto",
)

assistant_message = response.choices[0].message

# Step 2: Check if the model wants to call a tool
if assistant_message.tool_calls:
    messages.append(assistant_message)

    for tool_call in assistant_message.tool_calls:
        function_name = tool_call.function.name
        arguments = json.loads(tool_call.function.arguments)

        # Step 3: Validate function name and run
        if function_name == "get_weather":
            location = arguments.get("location", "Unknown")
            unit = arguments.get("unit", "fahrenheit")
            result = {
                "location": location,
                "temperature": 18 if unit == "celsius" else 64,
                "unit": unit,
                "condition": "Partly cloudy",
                "humidity": 72,
            }
        else:
            result = {"error": f"Unknown function: {function_name}"}

        # Step 4: Return the function result to the model
        messages.append({
            "role": "tool",
            "tool_call_id": tool_call.id,
            "content": json.dumps(result),
        })

    # Step 5: Get the final response incorporating tool results
    final_response = client.chat.completions.create(
        model="minimax.minimax-m2.5",
        messages=messages,
        tools=tools,
    )

    print(final_response.choices[0].message.content)
else:
    print(assistant_message.content)
```

### 使用 bedrock-runtime 端点（boto3）

#### 前置条件

使用 `bedrock-runtime` 端点，你需要配置好具有模型调用权限的 AWS 凭证（IAM 用户或角色）。请使用以下最小策略：

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "bedrock:InvokeModel",
                "bedrock:InvokeModelWithResponseStream"
            ],
            "Resource": "arn:aws:bedrock:us-east-1::foundation-model/minimax.minimax-m2.5"
        }
    ]
}
```

生产部署时，请把 Resource 限定为你实际使用的具体区域。要把组织限制为只使用已批准的模型，请使用[服务控制策略（SCP）](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html)。

下面的示例使用 [AWS SDK for Python（Boto3）](https://boto3.amazonaws.com/v1/documentation/api/latest/index.html) 通过 Converse API 向 MiniMax M2.5 发送单轮请求，并打印模型的响应：

```
import boto3

client = boto3.client("bedrock-runtime", region_name="us-east-1")

response = client.converse(
    modelId="minimax.minimax-m2.5",
    messages=[{
        "role": "user",
        "content": [{"text": "What is mixture of experts?"}]
    }],
    inferenceConfig={"maxTokens": 2048, "temperature": 1.0, "topP": 0.95},
)

content_blocks = response["output"]["message"]["content"]
response_text = next(
    (block["text"] for block in content_blocks if "text" in block),
    None
)

if response_text:
    print(response_text)
else:
    print("No text response.")
```

**注意：** 在 Converse API 上，MiniMax M2.5 会在 `text` 块之前返回一个 `reasoningContent` 块。代码会遍历这些内容块，以提取最终的文本响应。

### 使用 AWS CLI

你也可以在终端里通过 [AWS Command Line Interface（AWS CLI）](https://aws.amazon.com/cli/) 访问 MiniMax M2.5：

```
aws bedrock-runtime converse \
```

## 服务层级

Amazon Bedrock 提供多个[服务层级](https://docs.aws.amazon.com/bedrock/latest/userguide/service-tiers-inference.html)，以匹配不同的工作负载需求：

| **层级** | **最适合** | **特点** | **MiniMax M2.5 支持** |
| --- | --- | --- | --- |
| **Priority** | 需要最快响应时间的任务关键型、面向客户的 workflow | 与 Standard 相比，每秒输出 token 数（OTPS）最多改善 25%。在 Standard 与 Flex 请求之前优先处理。在标准按需定价之上收取溢价。无需预付预留或承诺。 | 是 |
| **Standard** | 内容生成、文本分析和常规文档处理等日常 AI 任务 | 以标准按需定价提供一致的性能。未指定层级时的默认层级。无需承诺。 | 是 |
| **Flex** | 可以容忍较长处理时间的工作负载，例如模型评估、内容摘要和 agentic workflow | 相对于 Standard 的折扣定价。延迟更高，尤其在流量高峰期间，因为 Flex 请求在 Standard 之后处理。无需承诺。 | 是 |

**注意：** Reserved 层级目前不适用于 MiniMax 模型。关于 Reserved 层级可用性的更新，请联系你的 AWS 客户团队。

## 按需推理的扩展

在 Amazon Bedrock 上调用 MiniMax 模型时，请求默认使用按需推理（Standard 层级），按 token 付费而无需预留容量。按需吞吐是按 AWS Region 共享并分配的，因此在区域需求高峰期间，请求可能被短暂排队或限流。对于需要在生产环境中可靠扩展的应用，把这考虑进设计很重要。

在 `bedrock-mantle` 端点上，没有每分钟请求数（RPM）配额。吞吐由基于 token 的限制而非请求数量控制。MiniMax 模型目前没有在 Service Quotas 控制台中发布按账户的 token 配额，因此其吞吐由端点的内部调度与容量管理。请使用带指数退避的重试逻辑来处理瞬时限流。通过 prompt caching 读取的缓存输入 token 不计入输入 token 配额。详情请参阅 [bedrock-mantle 端点的配额](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-mantle.html)。

| **错误** | **含义** | **应对措施** |
| --- | --- | --- |
| HTTP 429 | 该模型的每分钟 token 配额已被超出。 | 降低提交速率并以指数退避重试。如果持续触达上限，请通过 AWS Support 申请提高配额。 |
| HTTP 503 | 该模型在区域内的容量承压。 | 对瞬时错误以指数退避重试。对持续性错误则降低提交速率。 |

这两种错误需要不同的应对方式。遇到 429，降低提交速率或通过 AWS Support 申请提高配额。遇到 503，对瞬时错误重试并逐步爬坡，如下一节所述。

**处理偶发的 503 响应。** 当模型需求很高时，一些按需推理请求可能偶尔收到 503 响应，推荐的处理方式是指数退避加抖动，并设定有界的重试次数。AWS SDK 和大多数流行的 HTTP 客户端都通过标准重试配置支持这一点。下面的示例使用 Boto3：

```
import boto3
from botocore.config import Config

config = Config(retries={"total_max_attempts": 6, "mode": "standard"})
client = boto3.client("bedrock-runtime", config=config)
```

如果 503 响应变成持续性，仅靠重试无法解决问题，因为有效请求速率已超出该模型的可用容量。这种情况下，可以考虑把对延迟敏感的流量路由到 Priority 层级——在需求高峰期间，它会先于 Standard 与 Flex 请求被优先处理。

**处理陡峭的流量爬坡。** 使用 Standard 层级按需推理时，应用的流入流量应与模型区域容量的扩展方式相协调。请求速率突发的大幅跳升，比系统能容纳的渐进增长更容易触发 503。每当你要提高打向 MiniMax 模型的请求速率时，都应当以经过衡量的小步增量爬坡，而不是一步跳到新的目标量。推荐的爬坡流程是：

- 从你的目标请求速率开始。
- 如果收到 503 响应，把速率降低 50%，并持续降低，直到请求稳定成功。
- 在该稳态上保持 15 分钟。
- 把速率提高 50%，再保持 15 分钟。
- 重复该过程，直到达到目标量。

举一个具体的例子：如果你的目标是每分钟 2,000 次请求并遇到了 503，你会先降到 1,000，如果错误持续再降到 500。500 稳定运行 15 分钟后，你升到 750，再到 1,125，依此类推。15 分钟的保持是大多数团队会跳过的环节，而这恰恰是最重要的一环。没有它，每一次提速本质上都是一次全新的压力测试。

**为对延迟敏感的工作负载选择 Priority 层级。** 除了在持续性 503 期间的被动使用之外，Priority 层级还是继续使用按需推理的同时减少 503 发生频次的一个有用杠杆。与 Standard 相比，Priority 提供最多提升 25% 的每秒输出 token 数，且没有预付预留或承诺。应用在每次调用时把 `service_tier` 参数设为 `priority` 即可选用，同一应用内还可以混用不同层级。面向客户的 prompt、实时 agent，以及其他响应时间直接影响体验的用户交互，都适合选用 Priority。对于后台与批处理类工作，Standard 或 Flex 通常是正确选择，也能避免为不会从中受益的请求支付 Priority 溢价。

**面向生产规模的其他最佳实践。** 还有若干实践有助于让推理工作负载在大规模下平稳运行。把大负载分散到多分钟内，而不是在紧凑的突发中打出去，可以减轻对区域容量的压力。把生产流量迁移到新的 MiniMax 模型版本时，可以用 feature flag 逐步提高流量百分比，而不是一次性全量切换。异步工作，例如模型评估、内容摘要和 agentic 回填，可以路由到 Flex 层级——它专为成本高效地处理可容忍延迟的工作负载而设计。对于没有数据驻留要求的工作负载，跨多个区域分布可以提升在区域需求尖峰期间的韧性。对于预期会增长的工作负载，为预期峰值预留两到三倍的余量，可以为流量激增提供缓冲。

完整指导请参阅 Amazon Bedrock 用户指南中的[扩展与吞吐最佳实践](https://docs.aws.amazon.com/bedrock/latest/userguide/scaling-throughput-best-practices.html)。

## 用隐式 prompt caching 降低延迟

Amazon Bedrock 上的 MiniMax 模型支持隐式 prompt caching。当连续请求共享同一段 prompt 前缀时，可能产生缓存命中，让模型复用已缓存的内部状态，而不必重新计算。缓存命中会降低匹配 token 上的推理延迟，且无需修改代码，也不需要任何缓存标记。

隐式 prompt caching 在所有按需服务层级（Standard、Priority 和 Flex）上都可用，因此无论流量如何路由，应用都能利用它。并非每个请求都保证缓存命中，但在前缀稳定的工作负载中命中很常见。例子包括多轮 agent、检索增强生成 pipeline，以及在请求之间复用 system prompt、工具定义或源文档的长上下文分析 workflow。要最大化缓存命中率，请把静态内容（system prompt、工具定义、参考文档）放在 prompt 开头，把动态内容（用户消息、可变上下文）放在末尾。

## 清理

按需推理只在调用模型时产生费用，因此没有需要拆除的基础设施。为避免意外费用，请考虑以下几点：

- 如果你为测试生成了短期 Amazon Bedrock API key，它们会在 12 小时内自动过期。要提前撤销，请在 [Amazon Bedrock 控制台](https://console.aws.amazon.com/bedrock/)中删除该 API key。删除 key 会立即撤销任何使用它的应用的访问权限，因此请先确认没有活跃应用依赖它。
- 如果你为测试选用了 Priority 层级，请从请求中移除 `service_tier` 参数，让不属于延迟敏感的流量回到 Standard 定价。

在本文中，我们介绍了如何在 Amazon Bedrock 上开始使用 MiniMax M2 系列模型。我们探讨了两个推理端点 `bedrock-mantle` 与 `bedrock-runtime`，用 Chat Completions API 演示了工具调用，介绍了用于匹配工作负载需求的服务层级选项，并讨论了扩展策略，包括用隐式 prompt caching 降低延迟。

开始使用：

- 打开 [Amazon Bedrock 控制台](https://console.aws.amazon.com/bedrock/)，在 Chat/Text playground 中试用 MiniMax M2.5。
