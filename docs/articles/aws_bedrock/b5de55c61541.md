# 为 Amazon Bedrock Knowledge Bases 构建并部署自动同步方案

借助 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)，你可以把组织私有数据源中的上下文信息提供给[基础模型](https://aws.amazon.com/what-is/foundation-models/)（FM）和 agent，从而给出更相关、更准确、更贴合需求的回答。随着数据增长，在 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）与知识库之间维持实时同步，对于给出准确、最新的回答变得至关重要。

本文介绍一个自动化方案：它检测 S3 事件并触发摄取作业，同时遵守[服务配额](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas.html)，并提供全面的监控。这个无服务器方案采用事件驱动架构，让知识库保持最新，又不会把 Amazon Bedrock 的 API 压垮。

## 挑战

在 Amazon Bedrock 中，每当 S3 里的文档（包括元数据文件）被新增、修改或删除时，知识库都需要手动同步。组织需要自动化同步来应对这些场景：频繁的内容更新；团队全天不断上传文档的多用户环境；客户支持系统这类需要即时获取最新信息的实时应用；以及通过消除容易延误或被遗忘的手动同步流程来提升运营效率。要实现可靠的自动化，组织必须在遵守 Amazon 服务配额和速率限制的前提下，精心编排同步操作。

## 服务设计考量

在实现自动化同步时，客户必须考虑 Amazon Bedrock 的保护性约束。Amazon Bedrock 的服务配额把并发摄取作业限制为：

- 每个 AWS 账号五个作业（有助于防止资源耗尽）
- 每个知识库一个作业（便于集中处理）
- 每个数据源一个作业（保持数据一致性）

关于 Amazon Bedrock 服务配额的更多信息，请参阅 Amazon Bedrock 参考指南中的 [Amazon Bedrock 服务配额](https://docs.aws.amazon.com/general/latest/gr/bedrock.html#limits_bedrock)。这些限制针对每个 [AWS Region](https://docs.aws.amazon.com/glossary/latest/reference/glos-chap.html#region) 各自生效，且未来可能变化，请查阅文档获取最新的配额信息。

知识库的 [StartIngestionJob API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent_StartIngestionJob.html) 在每个受支持的 Region 中都有 0.1 请求/秒的限流（即每 10 秒一个请求）。

设想一个内容团队在发版期间更新了多个文件。如果没有协调机制，同步请求会因服务限制而排队，还需要人工盯守。采用编排式做法可以无缝应对，既确保变更被高效处理，又遵守服务约束。

## 方案概览

这个事件驱动的方案会自动把 Amazon S3 中的文档与 Amazon Bedrock Knowledge Bases 同步。当你的 S3 存储桶中的文档（包括元数据文件）被新增、修改或删除时，方案会自动触发同步作业，同时遵守服务配额和速率限制。方案使用简洁的 [AWS Serverless Application Model](https://aws.amazon.com/serverless/sam/)（AWS SAM）部署方式，以完全无服务器的架构运行，无需管理基础设施。

该方案实现了事件驱动架构，把关键 AWS 服务组合起来实时处理 Amazon S3 变更，并智能地管理摄取作业。以下组件协同工作，在遵守服务配额的同时实现可靠同步：

- [Amazon EventBridge](https://aws.amazon.com/eventbridge/) 捕获来自 Amazon S3 的实时变更
- [AWS Lambda](https://aws.amazon.com/lambda/) 函数处理事件并管理同步
- [Amazon Simple Queue Service](https://aws.amazon.com/sqs/)（Amazon SQS）队列缓冲请求，以遵守服务配额
- [AWS Step Functions](https://aws.amazon.com/step-functions/) 编排同步工作流
- [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 跟踪文档变更和作业元数据

下图展示了该方案如何使用 AWS 服务构建事件驱动的同步系统。

该方案的架构由五个相互连接的组件构成，它们协同管理完整的同步工作流。下面逐一介绍每个组件在系统中的职责，并用代码示例说明这个可直接部署的方案背后的技术实现。

### 阶段 1：文档变更检测

初始阶段建立对 S3 存储桶中文档变更的自动检测与处理。以下是该阶段执行的主要动作：

- **EventBridge 捕获 S3 事件** – 文档被上传、修改或删除时，S3 会自动向 EventBridge 发送事件
- **Lambda 顺序处理事件** – EventBridge 触发事件处理器 Lambda 函数，该函数提取文档元数据（文件路径、变更类型和时间戳），并在 DynamoDB 中创建跟踪记录以供审计
- **SQS 排队同步请求** – 同一个 Lambda 函数立即向 Amazon SQS 发送同步请求消息，由 SQS 缓冲请求，从而管理速率限制并实现可靠处理

以下代码展示事件处理器 Lambda 函数如何处理传入的 S3 事件，并协调跟踪与排队流程：

```
# Event Processor Lambda extracts change information
def lambda_handler(event, context):
    for record in event.get('Records', []):
        # Extract S3 information
        bucket = record['s3']['bucket']['name']
        key = record['s3']['object']['key']
        event_name = record['eventName']
        
        # Determine change type
        change_type = get_change_type(event_name)
        
        # Create tracking entry in DynamoDB
        tracking_table.put_item(
            Item={
                'change_id': str(uuid.uuid4()),
                'knowledge_base_id': kb_id,
                'change_type': change_type,
                'key': key,
                'processed': False,
                'timestamp': datetime.utcnow().timestamp()
            }
        )
        
        # Send immediate notification to SQS
        sqs.send_message(
            QueueUrl=QUEUE_URL,
            MessageBody=json.dumps({
                'change_type': change_type,
                'bucket': bucket,
                'key': key,
                'knowledge_base_id': kb_id
            })
        )
```

### 阶段 2：队列管理

为保持处理节奏稳定并遵守服务配额，方案实现了一套队列机制来管理文档变更请求。队列管理阶段包含以下关键步骤：

- **Amazon SQS 缓冲请求** – 阶段 1 的消息进入队列，以确保同步作业请求之间的速率限制得到满足
- **Lambda 处理消息** – 同步处理器 Lambda 函数一次从 SQS 队列消费一条消息
- **启动工作流** – 每条消息都会触发一次新的 Step Functions 执行，携带文档变更详情和知识库配置

以下代码演示同步处理器 Lambda 函数如何消费 SQS 消息并启动编排工作流：

```
def lambda_handler(event, context):
    for record in event.get('Records', []):
        message = json.loads(record['body'])
        kb_id = message['knowledge_base_id']
        
        # Get or discover data source ID
        data_source_id = get_data_source_id(kb_id)
        
        # Start Step Functions workflow
        sfn_input = {
            'knowledge_base_id': kb_id,
            'data_source_id': data_source_id,
            'message': message
        }
        
        response = sfn.start_execution(
            stateMachineArn=STEP_FUNCTION_ARN,
            name=f"sync-{kb_id}-{int(datetime.utcnow().timestamp())}",
            input=json.dumps(sfn_input)
        )
```

### 阶段 3：编排式同步

编排阶段使用 AWS Step Functions 协调同步过程，同时管理服务配额并处理失败。该工作流包含：

- **配额校验** – 检查当前 Region 中各知识库正在运行的摄取作业，确认未超出服务限制
- **条件执行** – 若配额允许，立即启动同步作业；否则等待 5 分钟后再次检查
- **作业监控** – 跟踪同步作业进度，并处理成功完成与失败两种情况
- **错误处理** – 为失败的同步尝试实现重试逻辑和死信处理

以下 Step Functions 状态机定义展示了配额管理与作业执行的决策逻辑：

### 阶段 4：知识库处理

在该阶段，知识库处理已同步的内容并使其可供使用。具体步骤如下：

- **文档处理** – Amazon Bedrock 扫描同步作业中识别出的变更文档
- **向量转换** – 文档被切分为块，并使用配置的嵌入模型转换为向量嵌入
- **索引更新** – 新嵌入写入向量数据库，过期的嵌入被移除
- **内容可用** – 更新后的内容立即可用于语义搜索与检索

### 阶段 5：监控与告警

最后一个阶段实现全面的监控与告警，确保方案可靠运行。包括：

- **状态跟踪** – 随着作业成功完成或失败，在 DynamoDB 中更新文档变更状态
- **通知投递** – 通过 Amazon SNS 向配置的电子邮件地址或端点发送成功或失败告警
- **性能监控** – [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 指标跟踪同步作业时长、成功率和配额使用率
- **自动告警** – 当错误率超过阈值或作业长时间卡住时触发 CloudWatch 告警

## 关键特性

该方案提供了若干必要能力，帮助在 Amazon S3 与知识库之间实现高效、可靠的同步。下面逐一介绍每项关键特性及其价值。

### 实时事件处理

该方案会对 S3 变更立即响应。EventBridge 集成实时捕获 S3 事件。系统利用 S3 事件通知，在 Amazon S3 对象变更发生时即时处理，自动触发摄取作业。响应及时，无需等待定时任务。

### 全面的配额管理

该方案遵守 Amazon Bedrock 的服务配额：

```
# Service quotas validation
MAX_CONCURRENT_JOBS_PER_ACCOUNT = 5
MAX_CONCURRENT_JOBS_PER_DATA_SOURCE = 1
MAX_CONCURRENT_JOBS_PER_KB = 1
MAX_FILE_SIZE_BYTES = 50 * 1024 * 1024 * 1024  # 50 GB
MAX_TOTAL_SIZE_BYTES = 100 * 1024 * 1024 * 1024  # 100 GB

def check_quotas(kb_id, data_source_id):
    # Get current active jobs
    response = bedrock.list_ingestion_jobs(
        knowledgeBaseId=kb_id,
        dataSourceId=data_source_id
    )
    
    active_jobs = [job for job in response['ingestionJobSummaries'] 
                   if job['status'] in ['STARTING', 'IN_PROGRESS']]
    
    return {
        'all_quotas_ok': len(active_jobs) == 0,
        'kb_quota_ok': len(active_jobs) < MAX_CONCURRENT_JOBS_PER_KB
    }
```

### 健壮的错误处理

该方案实现了完善的错误处理：用死信队列承载失败消息，为瞬时故障提供自动重试逻辑，并通过 CloudWatch 提供详细日志，从而实现可靠运行和便捷排障。

## 方案实操

本节带你一步步在你的 AWS 环境中部署这个自动同步方案。部署步骤如下：

- 克隆 [GitHub 仓库](https://github.com/aws-samples/sample-automatic-sync-for-bedrock-knowledge-bases)：

```
git clone https://github.com/aws-samples/sample-automatic-sync-for-bedrock-knowledge-bases
cd sample-automatic-sync-for-bedrock-knowledge-bases
```

- 构建并部署方案：

```
sam build
sam deploy --guided
```

部署过程中会提示你提供以下参数：

- Stack Name [`kb-auto-sync`] – 你的 CloudFormation 堆栈名称
- AWS Region [`us-west-2`] – 你的 Amazon Bedrock 知识库所在的 Region
- KnowledgeBaseId – 你的 Amazon Bedrock 知识库标识符
- S3BucketName – 存放文档的 S3 存储桶名称
- S3KeyPrefix（可选）– 要同步的特定文件夹前缀（例如 `documents/`）
- NotificationsEmail（可选）– 用于接收同步作业通知的电子邮件地址
- MaxConcurrentJobs [5] – 并发同步作业的最大数量
- Allow AWS SAM CLI IAM role creation [Y/n] – 是否允许创建 IAM 角色
- Save arguments to configuration file [Y/n] – 是否保存设置以便后续部署复用

该方案用到多个 AWS 服务，各自计费模型不同：

- [Amazon SQS 定价](https://aws.amazon.com/sqs/pricing/) – 按请求计费
- [AWS Step Functions 定价](https://aws.amazon.com/step-functions/pricing/) – 按状态转换计费
- [Amazon DynamoDB 定价](https://aws.amazon.com/dynamodb/pricing/) – 按存储和吞吐计费
- [Amazon CloudWatch 定价](https://aws.amazon.com/cloudwatch/pricing/) – 按看板创建、指标告警和日志存储计费
- [Amazon SNS 定价](https://aws.amazon.com/sns/pricing/) – 按每月 API 请求数量计费

以下是每 10,000 份文档的典型用量下，估算的月度成本：

- Lambda 调用：约 $0.20
- EventBridge 事件：约 $1.00
- 其他服务：成本极低

对于需要实时文档同步、频繁处理文档更新，并且希望以最少人工干预自动维护知识库的组织，这个方案非常合适。在一个用户上传文档的真实场景中，流程会依次执行以下动作：

- 用户在下午 2:00 把文档上传到 Amazon S3
- EventBridge 立即捕获 S3 事件
- 事件处理器 Lambda 函数创建跟踪记录并发送 SQS 消息
- 同步处理器 Lambda 函数收到消息并启动 Step Functions 工作流
- 配额检查确认该知识库没有正在运行的作业
- 摄取作业立即启动
- 监控函数跟踪进度，直到下午 2:05 完成
- 该变更在 DynamoDB 中标记为已处理

## 故障排查

同步作业失败和限流是常见问题，可按以下方式解决：

- **同步作业失败** – 权限配置有误或文档大小超限时会出现。解决方法：在 Amazon Bedrock 控制台中查看知识库数据源同步历史下的摄取作业警告。确认 IAM 权限配置正确。确认文档大小在允许范围内。
- **限流** – 同时处理的同步请求过多或触及服务配额时会发生。解决方法：监控 CloudWatch 指标以定位瓶颈。按需调整并发设置，保持在限制范围内。
