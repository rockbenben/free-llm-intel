# 在 Amazon Bedrock 上实现 programmatic tool calling

Programmatic tool calling（PTC）是大型语言模型（LLM）与外部工具交互方式的一次范式转变。在传统的 tool-calling 工作流中，每一次工具调用都需要完整地往返模型一次：模型调用一个工具、接收结果、对其推理、再调用下一个工具，如此往复。对涉及多次工具调用的工作流来说，这会带来不断叠加的延迟与 token 消耗，因为每一个中间结果都必须经过模型的上下文窗口。

![Programmatic tool calling using LLMs](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/30/ML20707-image-1.png)

PTC 另辟蹊径。模型不再逐个编排工具调用，而是编写代码（通常是 Python），在沙箱化的执行环境中以编程方式调用多个工具。这些代码可以包含循环、条件判断、过滤与聚合逻辑。模型只为生成代码被采样一次。执行环境随后负责工具调用，只有最终处理结果返回模型的上下文。这大幅降低了多工具工作流的延迟与 token 用量。PTC 在大数据处理、精确数值计算、多步骤流程编排，以及原始数据不应进入模型上下文的隐私敏感场景中尤为有效。

![Underlying pattern for prorammatic tool calling](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/30/ML20707-image-2.png)

PTC 最初是某个模型提供方的专有功能，但其底层模式——模型生成代码、沙箱执行代码、只有最终输出回到上下文——与模型无关。本文将展示在 Amazon Bedrock 上实现 PTC 的三种方式：在 ECS 上自托管 Docker sandbox 以获得最大控制力；使用 Amazon Bedrock AgentCore Code Interpreter 的托管方案；以及经由代理的 Anthropic SDK 兼容路径，适合偏好该开发体验的团队。

## **传统工具调用中的瓶颈**

看这个例子：“哪些工程团队成员超出了他们第三季度的差旅预算？”在使用传统 tool calling（假设没有并行函数调用）的情况下，模型必须：

- 调用一个工具获取团队成员名单——20 个人。
- 为每个人调用工具获取费用记录——20 次独立的工具调用，每次返回 50–100 条明细。
- 再调用工具获取预算阈值。
- 把 2,000 多条费用记录接收进上下文窗口。
- 用自然语言对整个数据集推理，以完成过滤、比较与汇总。

上述每一次工具调用都要完整地经过模型一次往返。模型生成一次工具调用、暂停、接收结果、对其推理、再生成下一次工具调用，如此往复。这会造成三个叠加的问题：

- **Token 消耗：** 每一个中间结果，包括模型最终会丢弃的数千条费用明细，都要经过上下文窗口。
- **延迟：** 每次工具调用都要求一次完整的模型推理周期。20 次串行工具调用意味着 20 次推理往返。
- **准确性：** 要求语言模型用自然语言对数千条记录做过滤、聚合与比较容易出错。这些操作只需几行 Python 就能精确完成。

## **PTC 如何解决这个问题**

PTC 把这个模式反过来。模型编写一个 Python 代码块，用它编排工具调用、处理结果，并只返回最终输出。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/30/ML20707-image-3.png) ![How Programmatic tool calling works](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/30/ML20707-image-4.png)

仍以同一个费用审计为例，下面是启用 PTC 时模型生成的内容：

```
import asyncio
import json

# Step 1: Get team members
team_json = await get_team_members(department="engineering")
team = json.loads(team_json)

# Step 2: Fetch all expense records in parallel
expense_tasks = [
get_expenses(employee_id=m["id"], quarter="Q3")
for m in team
]
expenses_results = await asyncio.gather(*expense_tasks)

# Step 3: Filter and check budgets
exceeded = []
for member, exp_json in zip(team, expenses_results):
expenses = json.loads(exp_json)
total_travel = sum(
e["amount"] for e in expenses
if e["category"] == "travel" and e["status"] == "approved"
)

if total_travel > 5000:
budget_json = await get_custom_budget(user_id=member["id"])
budget = json.loads(budget_json)
limit = budget["budget_limit"]

if total_travel > limit:
exceeded.append({
"name": member["name"],
"spent": total_travel,
"limit": limit,
"exceeded_by": total_travel - limit
})

# Step 4: Only the summary enters the model's context
print(f"{len(exceeded)} members exceeded budget:")
print(json.dumps(exceeded, indent=2))
```

这里有两点值得注意。第一，`asyncio.gather()` 让全部 20 次费用查询并行发起而非串行，这些工具调用几乎同时发生。第二，过滤、聚合与预算比较都在 Python 中完成，而不是用自然语言。只有最终的 `print()` 输出回到模型的上下文窗口，超过 2,000 条原始费用记录根本不会触碰上下文。模型只被采样两次：一次生成代码，一次解释最终输出。中间的一切（工具调用、数据处理、过滤）都在容器内完成，不产生额外的模型推理。

## **第 1 部分：基于 Amazon Bedrock 与 Amazon ECS 的自托管 PTC**

### **为什么要自托管**

托管的 PTC 实现依赖提供方管理的沙箱环境。但自托管有充分的理由：

- **与模型无关：** 支持 Amazon Bedrock 上可用的模型（例如 Claude、Qwen、MiniMax、Llama、Nova 等）。
- **完全可控：** 可定制沙箱环境、安装领域专用的 Python 包，并按需求配置安全策略。
- **私有部署：** 让代码执行与中间数据留在你自己的 AWS 账户内。

### **架构**

自托管方案包含两个组件：

- **Orchestrator** —— 你的应用（Amazon Elastic Container Service（Amazon ECS）任务、AWS Lambda 或某台计算资源），用 Boto3 调用 InvokeModel API、管理 Docker sandbox 生命周期，并处理工具调用循环。
- **Docker sandbox** —— 一个隔离容器，执行模型生成的 Python 代码。它通过基于 stdin/stderr 的 IPC 与编排器通信。

![How to implement PTC with ECS containers](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/05/ML20707-image-5.png)

核心思路很直接：把平时放在 tool_config 里的工具定义改为注入 system prompt，并指示模型编写编排这些工具的 Python 代码。生成的代码在 Docker sandbox 中运行。编排器充当控制面，通过 IPC 拦截工具调用、在外部执行它们，并把结果注回沙箱。

### **system prompt**

system prompt 是让模型表现得像原生支持 PTC 的关键一环。它描述了执行环境、可用工具以及生成代码的规则。下面给出一个精简版本：

```
# Code Execution Environment Description
## Core Function
You can use the `execute_code` tool to run Python code. The code can call
asynchronous tool functions.
{tools_doc}

## Key Rules
### 1. Stateless Environment
- Each `execute_code` call is a fresh environment.
- Variables are not retained between calls.
- All operations must be completed in a single code block.

### 2. Basic Syntax
- Tool calls must use `await`.
- Use `print()` to output results.
- Data processing, filtering, and aggregation are allowed.

## Best Practices
### Correct: One code block completes all tasks
import json
import asyncio
data = await get_orders(days=7)
orders = json.loads(data)
tasks = [get_detail(id=o['id']) for o in orders]
details = await asyncio.gather(*tasks)
for order, detail in zip(orders, details):
print(f"{order['name']}: {detail}")

### Incorrect: Multiple code blocks
# First execution
data = await get_orders()
# Second execution - NameError: data does not exist
for item in data:
pass
```

这个 prompt 引导模型产出结构良好的 Python 代码，遵循与原生 PTC 实现相同的模式：单个代码块、异步工具调用，以及用 print() 输出。

### **核心组件**

#### **SandboxExecutor —— Docker sandbox 执行器**

SandboxExecutor 是核心组件。它管理隔离 Docker 容器的生命周期、安全地执行模型生成的代码，并处理工具调用的 IPC 协议。系统采用双进程架构。编排器（运行在你的 ECS 任务中）为每个代码执行请求启动一个 Docker 容器。通信通过标准 I/O 流进行：容器把工具调用请求写到 stderr，编排器通过 stdin 注入工具结果。

#### **runner 脚本**

runner 脚本由编排器动态生成，并在启动时注入每个 Docker 容器。它负责：

- **代码执行 ——** 把模型生成的代码包进异步上下文、捕获输出并处理异常。
- **IPC 协议 ——** 使用结构化消息标记（例如 `__PTC_TOOL_CALL__`、`__PTC_END_CALL__`、`__PTC_OUTPUT__`）在文本流中区分工具调用请求、结果与最终输出。
- **工具函数生成 ——** 为配置中定义的每个工具动态创建异步 Python 函数。当模型代码调用 await get_team_members(department=”engineering”) 时，生成的函数会序列化参数、向 stderr 写入工具调用请求、阻塞等待编排器通过 stdin 注入结果，然后返回反序列化的结果。

runner 脚本支持两种执行模式：

- **Single 模式 ——** 代码执行一次后退出。适合无状态的一次性任务。
- **Loop 模式 ——** 保持容器运行以接受多次代码执行，支持会话复用与调用之间的状态保留。

#### **IPC 协议**

为了在文本流中可靠地区分不同消息类型，系统定义了边界标记：

- `__PTC_TOOL_CALL__` / `__PTC_END_CALL__` —— 包裹一次工具调用请求（工具名 + 以 JSON 表示的参数）。
- `__PTC_OUTPUT__` —— 标记代码执行的最终输出。

当 runner 脚本在执行中的代码里遇到工具调用时，它把该调用序列化为 JSON、写在标记边界之间的 stderr 上，并阻塞在 stdin 上等待结果。编排器读取 stderr、解析工具调用、执行该工具，并把结果写回 stdin。runner 脚本解除阻塞并继续执行。

### **编排器循环**

在 Amazon Bedrock 上启用 PTC 需要三个要素：

- 一个 **system prompt**，指示模型编写用于工具编排的 Python 代码。
- 一个 **execute_code 工具定义**，模型用它把代码提交给沙箱。
- 嵌入 system prompt 的**业务工具描述**（而不是作为独立的 Amazon Bedrock 工具）。

编排器把 Amazon Bedrock 与 Docker sandbox 串起来。下面是核心循环：import boto3import json

```
import subprocess
import tempfile
import os

# ── Configuration ──
MODEL_ID = "us.anthropic.claude-sonnet-4-5-20250929-v1:0"
REGION = "us-west-2"
SANDBOX_IMAGE = "ptc-sandbox"

SYSTEM_PROMPT = "..." # Full system prompt as shown above

TOOLS = [
{
"name": "execute_code",
"description": "Execute Python code in a sandboxed environment.",
"input_schema": {
"type": "object",
"properties": {
"code": {"type": "string", "description": "Python code to execute."}
},
"required": ["code"]
}
}
]

# ── Bedrock call ──
def call_bedrock(client, messages):
body = json.dumps({
"anthropic_version": "bedrock-2023-05-31",
"max_tokens": 4096,
"system": [{"type": "text", "text": SYSTEM_PROMPT}],
"tools": TOOLS,
"messages": messages,
})
response = client.invoke_model(
modelId=MODEL_ID,
contentType="application/json",
accept="application/json",
body=body,
)
return json.loads(response["body"].read())

# ── Sandbox execution ──
def execute_in_sandbox(code):
"""Run code in a hardened Docker container. Returns stdout."""
with tempfile.NamedTemporaryFile(mode="w", suffix=".py", delete=False) as f:
f.write("import json\n" + code)
tmp_path = f.name
try:
result = subprocess.run(
["docker", "run", "--rm",
"--network", "none", "--read-only",
"--tmpfs", "/tmp:size=64m",
"--user", "sandbox", "--cap-drop", "ALL",
"--memory", "256m", "--cpus", "0.5",
"-v", f"{tmp_path}:/sandbox/user_code.py:ro",
SANDBOX_IMAGE],
capture_output=True, text=True, timeout=30,
)
return result.stdout.strip() if result.returncode == 0 else result.stderr.strip()
finally:
os.unlink(tmp_path)

# ── PTC orchestration loop ──
client = boto3.client("bedrock-runtime", region_name=REGION)
query = "Which engineering team members exceeded their Q3 travel budget?"

# Step 1: Send user query — model generates Python code
messages = [{"role": "user", "content": query}]
response = call_bedrock(client, messages)

# Step 2: Extract code from tool_use block
for block in response["content"]:
if block["type"] == "tool_use":
code = block["input"]["code"]
tool_id = block["id"]

# Step 3: Execute in Docker sandbox
output = execute_in_sandbox(code)

# Step 4: Send sandbox output back as tool_result
messages.append({"role": "assistant", "content": response["content"]})
messages.append({
"role": "user",
"content": [{"type": "tool_result", "tool_use_id": tool_id, "content": output}]
})

# Step 5: Model interprets the result and produces final answer
final = call_bedrock(client, messages)
for block in final["content"]:
if block["type"] == "text":
print(block["text"])
```

编排器把用户查询发给 Amazon Bedrock，从 tool_use 响应中取出模型生成的代码，在 Docker sandbox 中运行，并把输出作为 tool_result 回送。模型随后产出最终的人类可读答案，全程只被采样两次。

### **Docker sandbox 安全性**

沙箱容器以严格隔离方式运行。下面是一条强制这些安全层的 docker run 命令示例：

```
docker run --rm \
  --network none \
  --read-only \
  --tmpfs /tmp:size=64m \
  --user sandbox \
  --cap-drop ALL \
  --memory 256m \
  --cpus 0.5 \
  -v /path/to/code.py:/sandbox/user_code.py:ro \
  ptc-sandbox
```

它实现了：无网络访问、只读文件系统（外加一小块 tmpfs 作为临时空间）、非 root 用户、丢弃 Linux capabilities，以及硬性的内存/CPU 限制。模型生成的代码无法逃出沙箱、持久化数据或消耗过多资源。

## **第 2 部分：基于 Amazon Bedrock AgentCore Code Interpreter 的托管 PTC**

对于不想管理 Docker 容器与 ECS 基础设施的团队，Amazon Bedrock AgentCore 提供了一个托管 Code Interpreter，实现同样的 PTC 模式。模型编写代码、托管沙箱执行代码，只有最终输出回到模型上下文。下面是改用 AgentCore Code Interpreter 执行代码后的同一架构：

![How to implement PTC with AgentCore code interpreter](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/05/ML20707-image-6.png)

与自托管方案的关键区别在于：工具是预加载*进*沙箱会话的，而不是通过 IPC 分派回客户端。你启动一个 Code Interpreter 会话、以 Python 代码形式注入工具函数定义，然后让模型生成代码直接调用这些预加载的函数。

AgentCore 使用 bedrock-agentcore 的 boto3 client：

```
import boto3
import json

bedrock = boto3.client("bedrock-runtime", region_name="us-west-2")
agentcore = boto3.client("bedrock-agentcore", region_name="us-west-2")

# Start a Code Interpreter session
session = agentcore.start_code_interpreter_session(
codeInterpreterIdentifier="aws.codeinterpreter.v1",
name="ptc-tools",
sessionTimeoutSeconds=900,
)
session_id = session["sessionId"]

# Pre-load tool functions into the sandbox.
# Replace this string with your actual tool function definitions.
tool_functions_code = """
def get_team_members(department):
# Your implementation here — return JSON string
pass

def get_expenses(employee_id, quarter="Q3"):
# Your implementation here — return JSON string
pass

def get_custom_budget(user_id):
# Your implementation here — return JSON string
pass

print("Tools loaded.")
"""

agentcore.invoke_code_interpreter(
codeInterpreterIdentifier="aws.codeinterpreter.v1",
sessionId=session_id,
name="executeCode",
arguments={"language": "python", "code": tool_functions_code}
)
```

### **自托管与托管方案对比**

| **方面** | **自托管（第 1 部分）** | **AgentCore（第 2 部分）** |
| --- | --- | --- |
| 基础设施 | 你管理 ECS + Docker | 完全托管 |
| 定制能力 | 完全控制沙箱 | 标准运行时 |
| 工具执行 | 客户端侧（IPC） | 沙箱内部 |
| 网络访问 | 可配置 | 默认关闭，可用 PUBLIC 模式 |

对于想获得 PTC 的 token 节省与准确性收益、又不想承担运行 Docker 容器的运维开销的团队，推荐托管方案。当你需要自定义 Python 包、特定的安全配置，或对执行环境有完全的掌控时，自托管方案更合适。

## **第 3 部分：经由代理实现 Anthropic SDK 兼容**

如果你的团队偏好 Anthropic SDK 的开发体验，并希望以 Amazon Bedrock 作为后端，可以构建一个轻量的 API 转换代理，置于 Anthropic SDK 与 Amazon Bedrock 之间。

![Anthropic SDK compatibility](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/05/ML20707-image-7.png)

该代理部署在 Amazon ECS 上，把 Anthropic API 调用转换为 Amazon Bedrock InvokeModel 调用。它还会透明地管理 Docker sandbox 生命周期与完整的 PTC 协议。要迁移，只需把 base_url 改为指向该代理：

```
import anthropic

# Point the Anthropic SDK at the proxy deployed on ECS.
# The proxy translates these calls to Bedrock InvokeModel under the hood.
client = anthropic.Anthropic(
api_key="your-proxy-api-key", # API key configured in the proxy
base_url="http://your-proxy-url.com" # Your proxy's ECS endpoint
)

# Define PTC tools — same format as Anthropic's native PTC API
ptc_tools = [
{"type": "code_execution_20250825", "name": "code_execution"},
{
"name": "get_team_members",
"description": "Get department team member list",
"input_schema": {
"type": "object",
"properties": {"department": {"type": "string"}},
"required": ["department"]
},
"allowed_callers": ["code_execution_20250825"]
}
# Add get_expenses, get_custom_budget similarly
]

response = client.beta.messages.create(
model="claude-sonnet-4-5-20250929", # Proxy routes to Bedrock model
betas=["advanced-tool-use-2025-11-20"],
tools=ptc_tools,
messages=[{"role": "user", "content": "Which team members exceeded Q3 travel budget?"}]
)

# The proxy handles sandbox execution and tool call interception transparently.
```

对于偏好 Anthropic SDK 接口、同时用 Amazon Bedrock 做模型推理并享受在自有 AWS 账户内运行之利的团队，推荐这种方式。代理会透明地处理模型转换、沙箱管理与完整的 PTC 协议。

## **实验结果**

为验证自托管 PTC 方案，我们在 Amazon Bedrock 上多个可用模型上跑了同一个费用审计任务。

**业务设定：**

- **团队数据：** 八名不同层级的工程团队成员。
- **费用数据：** 每人每季度 20–50 条记录，每条包含 15 个以上字段（expense_id、date、amount、category、status）。
- **预算规则：** 标准季度差旅预算为 $5,000，高级职位有自定义例外。只统计*已批准*的费用。

**任务 prompt：** “哪些工程团队成员超出了他们第三季度的差旅预算？标准季度差旅预算为 $5,000。不过部分员工有自定义预算上限。对任何超出 $5,000 标准预算的人，请检查其是否有自定义预算例外。”

### **关键发现**

- **各模型的 token 消耗都下降了 87–92%。** 在 PTC 模式下，不再是数十万 tokens 流过上下文窗口，只有代码与最终摘要进入模型。
- **准确性显著提升。** 在 PTC 模式下，全部八个模型都给出了正确答案（姓名与金额完全一致）。在非 PTC 模式下，只有 Claude 模型（Sonnet 4.6 与 Opus 4.6）给出了完全正确的答案。其他模型对大型表格数据的自然语言处理在过滤、聚合或两者上都引入了错误。
- **跨模型兼容性得到验证。** Claude、Qwen、DeepSeek、MiniMax、Kimi、GLM 各模型在 PTC 模式下都取得了正确结果，说明这一范式在不同模型家族中都能有效工作。token 节省幅度为 87% 到 92%。
- **自托管方案在各模型上表现一致。** 同一个 Docker sandbox、同一套 IPC 协议、同一个编排器，测试之间只改了 model_id 参数。

关键结论是：PTC 作为一种范式并不绑定任何单一模型。通过自托管沙箱方案，任何支持 tool use 的模型都能从代码编排的工具调用中受益。

## **成本与价值分析**

### **规模化下的 token 节省**

以 Claude Sonnet 4.6 为例，费用审计任务在 PTC 与非 PTC 模式之间显示出约 90% 的 token 消耗降幅。原因很直接：在非 PTC 模式下，每一个中间工具结果都会进入上下文窗口；在 PTC 模式下，只有代码与最终摘要会进入。

**成本预估**（基于 Claude Sonnet 每 1M 输入/输出 token 分别为 $3/$15 的定价）：

如果这项任务在生产环境中每天执行 1,000 次：

| **指标** | **非 PTC 模式** | **PTC 模式** |
| --- | --- | --- |
| 预估日成本 | ~$520 | ~$52 |
| 预估月成本 | ~$15,600 | ~$1,560 |
| 每月节省 |  | ~$14,040（90%） |

这些数字会随任务复杂度与数据量变化，但规律是一致的：PTC 降低成本的程度，大致与它让多少中间数据不进入上下文窗口成正比。

## **结论**

Programmatic tool calling 代表了 AI agent 与工具交互方式的一次转变：从对话式的、一次一个的调用，转向代码编排、并行、带过滤的执行。我们的测试结果印证了其核心价值主张：

- 通过让中间数据不进入模型上下文，token 消耗下降 87–92%。
- 因为数据处理发生在 Python 而不是自然语言中，准确性提升。
- 因为工具调用可以并行运行、且模型只被采样两次，延迟下降。

我们介绍了在 Amazon Bedrock 上实现 PTC 的三种方式：

- **在 ECS 上自托管** —— 用 Boto3 与 Docker sandbox 获得完全控制，适合需要自定义环境与最大灵活性的团队。
- **通过 AgentCore Code Interpreter 托管** —— 为希望降低运维开销的团队提供完全托管的沙箱。
- **兼容 Anthropic SDK** —— 为偏好 Anthropic SDK 接口、同时在 Amazon Bedrock 上运行的团队提供基于代理的路径。

这三种方式都与模型无关、在你自己的 AWS 账户内私有部署，并能随着 Amazon Bedrock 上线新模型而扩展。Amazon Bedrock 提供按量付费的模型推理后端、在你 AWS 账户内的数据主权，以及通过单一 API 访问多样化模型集合的能力。
