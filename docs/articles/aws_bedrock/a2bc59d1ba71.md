# 使用 Strands Agents、NVIDIA NIM 和 Amazon Bedrock AgentCore 构建高性能生成式 AI 系统

构建高性能的生成式 AI agent，需要一套能够提供快速推理、协调多个 agent，并在生产负载下可靠运行的架构。如果你正在构建生成式 AI agent，用于自动化审查、驱动数字助理、支撑复杂的决策工作流，那么这些 agent 必须具备良好的性能。它们要能减少人工投入、近乎实时地响应，并且在不额外管理基础设施的前提下扩展到数千次交互。在本文中，你将了解如何在 AWS 上结合 [GPU](https://aws.amazon.com/what-is/gpu/) 加速推理、无服务器编排、共享内存和内置可观测性来构建这类高性能 agent。当你从实验原型走向能持续交付业务价值的系统时，这些能力不可或缺。

随着 agent 负载在生产环境中增长，并发请求下的推理延迟可能显著上升，导致响应变慢、用户体验下降。无状态的执行环境常常让 agent 在多次交互之间丢失对话或任务上下文，从而造成重复工作和不一致的输出。对 agent 执行过程的可见性有限，会让你难以诊断失败、理解推理路径或控制运营成本。这些挑战在多 agent 系统中更加突出——多个 agent 必须并行运行、共享上下文并汇总结果。

你将构建一个多 agent 的营销活动审查系统，用一套集成架构来展示并行推理、上下文持久化和可追踪的执行路径。该架构结合 [NVIDIA NIM](https://developer.nvidia.com/nim) 提供 GPU 加速推理，[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 提供托管运行时、共享内存和内置可观测性，[Strands Agents](https://strandsagents.com/latest/) 提供无服务器的多 agent 编排。这种做法兼顾生产环境中的性能、可扩展性和运营洞察。虽然示例聚焦于营销内容审查，但同样的模式也适用于数字助理、审查自动化和检索增强生成（RAG）流水线。

为了让这些概念更具体，下面几节会介绍一套参考架构与实现，展示这些组件在实践中如何协同工作。

## 方案概览

你将构建一个由三个并行工作的专用 agent 组成的系统。persona reviewer（受众画像评审）agent 从多个受众视角评估营销活动内容，并给出共鸣度分数。validator（校验）agent 依据法律与品牌准则检查内容。finalizer（汇总）agent 聚合各方输出，产出一套整合后的建议。你通过一个基于 [React](https://react.dev/) 的前端提交文档，前端会异步轮询结果，并在 agent 反馈陆续产生时显示出来。

我们的方案通过 [build.nvidia.com](https://build.nvidia.com/) 提供的托管 NVIDIA NIM API，以全托管服务的形式交付高性能、GPU 加速的推理。这些端点运行在 NVIDIA 托管的 GPU 后端上，跑的是经过优化的大语言模型。后端采用 [Compute Unified Device Architecture (CUDA)](https://developer.nvidia.com/cuda/toolkit) 和 [TensorRT-LLM](https://github.com/NVIDIA/TensorRT-LLM) 等技术，为 agent 工作流提供低延迟、高吞吐的响应。由于对外暴露 [OpenAI](https://openai.com/) 兼容的 Chat Completion API，NIM 可以直接与基于 Strands 的多 agent 编排层集成，无需针对模型做专门适配。

你将使用 Strands Agents 实现 agent 编排——这是 AWS 用于协调基于工具的推理工作流的多 agent 框架。借助 Strands，你可以显式地为 agent 之间的交互建模，从而更容易管理跨多个 agent 的并行执行、控制流和结果聚合。你把 Strands 编排器和各专用 agent 一起打包成一个 Docker 容器，部署到 Amazon Bedrock AgentCore Runtime 中。AgentCore Runtime 提供带检查点和恢复能力的托管执行环境。这些特性帮助你的 agent 在中断后优雅恢复，并在无需手动管理基础设施的情况下扩展到数千个并发调用。

你使用 Amazon Bedrock AgentCore Observability 为 agent 工作流的每个步骤提供详细的可视化，让开发者能够检查执行路径、审计中间输出、调试性能瓶颈。你可以通过 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 监控延迟、token 用量和错误率等运营指标。这种可见性帮助你理解 agent 的行为，并找出生产环境中的性能瓶颈。

你还使用 Amazon Bedrock AgentCore Memory 在多次 agent 调用之间共享上下文，并支持多轮对话。由于 AgentCore Memory 内置支持存储对话状态和历史，你可以扩展这套实现，为 AI 助理提供自然语言界面。

该方案的一个核心特点是易于部署：借助 [AWS Serverless Application Model（AWS SAM）](https://aws.amazon.com/serverless/sam/) 模板，可以方便地部署到 Bedrock AgentCore Runtime。你调用由该模板预置的 [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 接口，它会把你的 Strands agent 及其全部依赖打包部署，同时启用 AgentCore Observability 和 AgentCore Memory。

## 前提条件

在部署该方案之前，你需要先在开发环境中安装以下工具作为前提条件。

- 安装 [AWS Command Line Interface](https://aws.amazon.com/cli)（AWS CLI）。
- 安装 [AWS SAM CLI v1.100.0+](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/install-sam-cli.html)
- 安装 [Docker v20.x+](https://docs.docker.com/engine/install/)。
- 安装 [Node.js v18.x+](https://nodejs.org/)
- 安装 [Python v3.11+](https://www.python.org/downloads/)

## 依赖项

Strands Agents 的实现还需要以下依赖，它们会被打包在 DockerFile 中：

- AWS Strands 多 agent 框架：strands-agents
- Strands agent 工具与实用程序：strands-agents-tools
- 用于 API 调用的 HTTP 库：requests
- Amazon Bedrock AgentCore 功能：bedrock-agentcore
- Python 的 AWS SDK：boto3

## 部署方案

现在你已经了解了架构，下面的步骤将带你把这个方案部署到你的 AWS 环境中。请注意，使用 NVIDIA NIM 需要接受 NVIDIA AI Enterprise 的 EULA（可在订阅 AWS Marketplace 或注册 NGC 时接受）。

我们的方案可在 [GitHub 仓库](https://github.com/aws-samples/sample-agentic-genai-agentcore/tree/main/aws-genai-campaign-review-strands-agentcore) 下载。请按照下面的分步指引（GitHub 仓库的[部署章节](https://github.com/aws-samples/sample-agentic-genai-agentcore/blob/main/aws-genai-campaign-review-strands-agentcore/DEPLOYMENT.md) 中也有完全相同的说明），在你的 AWS 环境中部署并访问该方案：

### 第 1 步：克隆仓库

```
git clone <respository url>
cd aws-genai-campaign-review-strands-agentcore
```

### 第 2 步：配置 AWS 凭证

配置 AWS CLI：

```
aws configure
```

校验凭证：

```
aws sts get-caller-identity
```

### 第 3 步：创建 Amazon DynamoDB persona 表

让脚本可执行：

```
chmod +x scripts/setup_persona_table.sh
```

运行安装脚本：

```
./scripts/setup_persona_table.sh
```

### 第 4 步：构建 AWS SAM 应用

```
sam build
```

### 第 5 步：部署基础设施

使用引导式部署，按提示提供堆栈名称、agent 名称和 AWS region，其余各项接受默认值即可。

```
sam deploy --guided
```

### 第 6 步：获取部署输出

获取 API 端点：

```
aws cloudformation describe-stacks --stack-name <Your stack name> --query 'Stacks[0].Outputs' --output table
```

记录以下值：

- ApiEndpoint – HTTP API 地址
- CampaignOrchestratorApi – Agent API 地址
- CloudFrontURL – 前端地址
- FrontendBucket – 前端所用的 S3 存储桶

### 第 7 步：把 agent 部署到 AgentCore Runtime

这一步会把你的 Strands agent 部署到 Bedrock AgentCore，并把 Agent ARN 写入 Systems Manager：

```
curl -X POST <DeployAgentApiEndpoint> -H "Content-Type: application/json" -d '{"action":"deploy","agent_name":"<your agent name>"}'
```

这大约需要 5 分钟。API Gateway 会超时（29 秒），但 AWS Lambda 函数会继续运行。

监控进度：

```
aws logs tail /aws/lambda/deploy-agentcore --region <your AWS region> –follow
```

等到你看到：*Agent Core Runtime is READY! and Wrote Agent ARN to SSM.*

校验：

```
aws ssm get-parameter --name /agentcore/<your agent name>/agent-arn --region <your AWS region>
```

### 第 8 步：配置前端环境

```
PI_URL=$(aws cloudformation describe-stacks --stack-name <your stack name> --query 'Stacks[0].Outputs[?OutputKey==`ApiEndpoint`].OutputValue' --output text)

AGENT_API_URL=$(aws cloudformation describe-stacks --stack-name <your stack name> -review --query 'Stacks[0].Outputs[?OutputKey==`CampaignOrchestratorApi`].OutputValue' --output text)
```

创建 .env 文件

```
cat > .env << EOF
VITE_API_URL=$API_URL
VITE_AGENT_API_URL=$AGENT_API_URL
VITE_AWS_REGION= <your AWS region>
EOF
```

### 第 9 步：构建并部署前端

安装依赖：

```
npm install
```

构建前端：

```
npm run build
```

获取前端存储桶名称：

```
FRONTEND_BUCKET= $(aws cloudformation describe-stacks --stack-name unified-campaign-review --query 'Stacks[0].Outputs[?OutputKey==`FrontendBucket`].OutputValue' --output text)
```

部署到 S3：

```
aws s3 sync dist/ s3://$FRONTEND_BUCKET --delete
```

刷新 CloudFront 缓存（可选，用于更新）：

```
DISTRIBUTION_ID=$(aws cloudfront list-distributions --query "DistributionList.Items[?Origins.Items[0].DomainName=='${FRONTEND_BUCKET}.s3.us-west-2.amazonaws.com'].Id" --output text)

aws cloudfront create-invalidation --distribution-id $DISTRIBUTION_ID --paths "/*"
```

### 第 10 步：访问应用

获取 CloudFront URL：

```
aws cloudformation describe-stacks --stack-name unified-campaign-review --query 'Stacks[0].Outputs[?OutputKey==`CloudFrontURL`].OutputValue' --output text
```

在浏览器中打开该 URL 即可访问应用。把 [campaign_brief.md](https://github.com/aws-samples/sample-agentic-genai-agentcore/blob/main/aws-genai-campaign-review-strands-agentcore/campaign_brief.md) 文件作为示例营销活动文档，在左侧面板上传。随后你就可以在右侧面板查看多 agent 编排产出的活动审查结果，如下图所示：

[![活动上传界面：左侧面板用于上传活动简报，右侧面板用于查看 agent 生成的审查结果](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/02/image-ml-20164-2.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/02/image-ml-20164-2.png)

进入 [Bedrock AgentCore Observability 控制台](https://us-west-2.console.aws.amazon.com/cloudwatch/home?region=us-west-2#gen-ai-observability/agent-core?region=us-west-2)，选择你的 agent，即可看到 agent 工作流中每一步的详细可视化，如下图所示：

[![AgentCore 可观测性看板，展示 agent 调用中的 span、trace 和会话](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/02/image-ml-20164-3.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/02/image-ml-20164-3.png)

## 清理

为避免持续产生费用，试用完该方案后请清理你的 AWS 账号中的资源。

- 删除 AWS CloudFormation 堆栈：

```
sam delete --stack-name unified-campaign-review
```

- 删除 DynamoDB 表：

```
aws dynamodb delete-table --table-name PersonaTable --region us-west-2
```

## 结论

在本文中，你了解了如何结合 NVIDIA NIM 提供的 GPU 加速推理，以及 AWS 上 Amazon Bedrock AgentCore 与 Strands Agents 提供的无服务器编排，构建一套可用于生产的生成式 AI agent 系统。通过把推理与 agent 协调分离，这套架构支持独立扩展、跨 agent 交互的共享上下文，以及对执行过程和性能的细致可见性。

本文介绍的做法为需要并行推理、上下文持久化和运营洞察的多 agent 系统提供了实用基础。无论你是在构建审查自动化、数字助理还是其他 agent 驱动的应用，这里展示的模式都能帮助你从实验原型走向可在 AWS 上可靠部署、观测和扩展的系统。
