# 在 serverless pipeline 中异步调用 Amazon Bedrock AgentCore agent 的模式

在 serverless pipeline 中异步调用 Amazon Bedrock AgentCore agent 的模式，可以在 AI agent 处理请求期间消除闲置算力成本。一个常见例子是文档校验：在房地产融资后台，agent 可以读取房产记录或贷款合同，推理其中的信息是否完整、一致，并返回一个供下游步骤据以行动的判定结论。[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 提供了以任意框架或模型大规模构建、连接与优化 agent 的平台。

这类 agent 带来一个传统 pipeline 步骤所没有的特征：它们在回答之前会思考一段时间。思考多久取决于 prompt、模型与文档，但很少是瞬时的，而这个延迟会改变你调用它的方式。最常见的初始实现是使用一个计算服务（例如 [AWS Lambda](https://aws.amazon.com/lambda/) 函数）调用 agent 并等待响应。该函数在等待期间什么也不做，但它仍在运行，而你仍要为它运行的每一秒付费。

看清成本实际落在哪一侧会很有帮助，因为调用的两端计费方式不同。Amazon Bedrock AgentCore runtime（Amazon Bedrock AgentCore 的一项能力）采用按消费计费的模型，agent 空闲时不收取 CPU 费用。例如，当它等待大语言模型生成响应，或等待工具、Model Context Protocol（MCP）调用返回时，这段时间只收内存费用，不收 CPU 费用。而调用 agent 的计算服务没有这种行为。一个发出同步调用的 Lambda 函数、容器或 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2/)（Amazon EC2）实例会被阻塞挂起，在 agent 响应之前一直占用（并且付费）其全部算力配额。所以浪费不在 agent 一侧，而在调用方——它空转在一条打开的连接上。

这使得调用方的成本会跟随 agent 的运行时长。阻塞等待 agent 的函数，基本上要为整个处理时间付费；而启动 agent 后立即返回的函数，只需为那一小段派发付费。解决办法是在等待期间释放调用方的算力，只在 agent 有结果时才恢复 pipeline。本文介绍三种做到这一点的模式（任务令牌回调、直接服务集成与 durable function），并把它们与阻塞式反模式做对比。

## 一个示例 pipeline

为在同等条件下比较这些模式，我们让每一种都跑过同一条 pipeline，只改动调用 agent 的那一步。这条 pipeline 是一个刻意保持简单的虚构场景（校验房地产融资相关文档），选它是为了让编排逻辑清晰。它不是本文的重点。它可以代表任何“调用 agent（或其他慢速服务）、然后依据结果行动”的工作流，请把它替换成你自己的用例来理解。

这条 pipeline 有五个阶段：

- **Extract（提取）**：一个 AWS Lambda 函数执行光学字符识别（OCR）与文本提取。（提取是模拟的，因此该场景无需真实文档即可运行。）
- **Identify（识别）**：一个 Lambda 函数对文档分类并设置路由标志（`shouldOrganize`、`shouldValidate`）。
- **Route（路由）**：一个 Choice 状态依据这些标志决定流向。
- **Organize and Validate（整理与校验）**：一个 Parallel 状态在整理文档的同时，在另一分支中由 Amazon Bedrock AgentCore agent 对其进行校验。这个 Validate 分支是各模式之间唯一变化的部分。
- **Result（结果）**：一个 Lambda 函数处理 agent 的判定结论，并决定下一步动作（批准，或退回修改）。

下图展示了这条 pipeline。它在所有情况下都保持一致，只有 Validate 分支被替换，以演示各种调用模式。

图 1：示例 pipeline。各模式之间只有高亮的 Validate 分支会变化

四个案例共用同一个 Amazon Bedrock AgentCore agent。该 agent 会检查每次调用并选择如何响应：如果收到 [AWS Step Functions](https://aws.amazon.com/step-functions/) 的*任务令牌（task token）*，它会在完成后唤醒该执行；如果收到 durable function 的*回调 ID（callback ID）*，它会唤醒对应的 durable function；如果两者都没有，它就直接在响应中返回判定结论。这意味着你可以在不修改、不重新部署 agent 的情况下切换编排模式。

## agent 如何在不阻塞调用方的情况下交还控制权

机制是 agent 动作组中的一个“交还控制权”动作。当 agent 完成推理后，它调用一个 Lambda，把结果与任务令牌回传到 Step Functions。（后文介绍的模式 2 通过让 Step Functions 直接与 AgentCore 集成，彻底省去了这个 Lambda。）

以下代码展示了该 Lambda 的核心：

```
# The tool the agent calls once it reaches a verdict
@tool
def conclude_validation(approved: bool, issues: list, summary: str) -> str:
    verdict = {"approved": approved, "issues": issues,
               "summary": summary, "source": "agentcore"}

    # A Step Functions task token was passed: resume that execution
    if task_token:
        sfn.send_task_success(taskToken=task_token, output=json.dumps(verdict))
        return "Step Functions resumed."

    # A durable-function callback ID was passed: resume the durable function
    if callback_id:
        lambda_client.send_durable_execution_callback_success(
            CallbackId=callback_id, Result=json.dumps(verdict).encode("utf-8"))
        return "Durable function resumed."

    # Neither was passed: this is a synchronous call, return the verdict inline
    return "Verdict recorded."
```

入口点依据同一组信号决定是在后台运行还是同步运行：

```
@app.async_task
async def validate_document_async(prompt, document, extracted_text):
    # Background work; conclude_validation fires the right callback when done
    agent = build_agent()
    await agent.invoke_async(message(prompt, document, extracted_text))

@app.entrypoint
async def handler(event):
    task_token  = event.get("taskToken")    # passed by the task-token pattern
    callback_id = event.get("callbackId")   # passed by the durable-function pattern

    # Asynchronous: start the work and return "accepted" right away
    if task_token or callback_id:
        asyncio.create_task(validate_document_async(...))
        return {"status": "accepted"}

    # Synchronous: run now and return the verdict in the response
    agent = build_agent()
    await agent.invoke_async(message(...))
    return verdict
```

agent 就位之后，本文余下部分聚焦于调用它的四种方式。

## 调用 agent：四种方式

我们先从阻塞式反模式开始，以建立成本基线，然后展示三种避免它的模式。全文中的代码与基础设施定义都是示例的摘录，用于说明每种模式。

### 阻塞式反模式

最直接的实现是在同一个 Lambda 函数中调用 agent 并等待答案。它能工作，实现也直截了当，这正是它如此常见的原因，但该函数在 agent 思考的整个期间都必须存活。

```
// The Lambda function blocks here until the agent responds
const response = await agentcore.send(
  new InvokeAgentRuntimeCommand({
    agentRuntimeArn: AGENT_RUNTIME_ARN,
    payload: new TextEncoder().encode(JSON.stringify(payload)),
    runtimeSessionId: sessionId,
  })
);
// The function stays alive and billed for the entire time the agent is thinking.
```

该函数的计费时长最终大致等于 agent 的处理时间。接下来的三种模式消除了这部分闲置成本，各自做出不同的取舍。特别是模式 2 使用针对 [AgentCore Harness (InvokeHarness)](https://docs.aws.amazon.com/step-functions/latest/dg/connect-bedrockagentcore.html) 的 Step Functions 优化集成，把 Lambda 完全去掉。

### 模式 1：带派发函数的任务令牌回调

该模式在路径中保留一个 Lambda 函数以承载自定义逻辑，但消除了闲置成本。Step Functions 通过 `waitForTaskToken` 集成调用该函数，后者传入一个任务令牌，然后暂停该执行。函数用该令牌启动 agent，几秒后返回。执行保持暂停、不产生算力费用，直到 agent 用该令牌调用 `SendTaskSuccess` 将其恢复。

```
// Start the agent, pass the task token, and return without waiting
const response = await agentcore.send(
  new InvokeAgentRuntimeCommand({
    agentRuntimeArn: AGENT_RUNTIME_ARN,
    payload: new TextEncoder().encode(JSON.stringify({ ...payload, taskToken })),
    runtimeSessionId: sessionId,
  })
);
// Returning here does not complete the step. Step Functions stays paused until
// the agent calls SendTaskSuccess with this task token.
return { dispatched: true };
```

对应的状态从上下文中取得令牌，并设置超时与心跳作为安全网，这样当 agent 沉默时，执行会干净地失败，而不是无限期停在那里：

```
"ValidateDispatch": {
  "Type": "Task",
  "Resource": "arn:aws:states:::lambda:invoke.waitForTaskToken",
  "Parameters": {
    "FunctionName": "${ValidateDispatcherFunctionArn}",
    "Payload": {
      "taskToken.$": "$$.Task.Token",
      "document.$": "$.document",
      "extractedText.$": "$.extract.extractedText",
      "executionId.$": "$$.Execution.Id"
    }
  },
  "TimeoutSeconds": 120,
  "HeartbeatSeconds": 60,
  "Next": "AgentCoreValidation"
}
```

**成本。** 会运行一个 Lambda 函数，但只运行到启动 agent 并返回为止：几秒钟，无论 agent 随后需要多久。你为这一小段派发付费，而不是为等待付费，因为 agent 工作时该函数已经关闭。等待由暂停的 Step Functions 执行持有，而它不收取闲置算力费用。这就是与阻塞版本的关键区别——后者的函数计费时长会跟随 agent 的处理时间。

### 模式 2：直接服务集成

当你不需要在 agent 调用周围写自定义代码时，可以去掉派发函数，把 Lambda 完全移出路径。Step Functions 可以通过其 AWS SDK 服务集成直接调用 Amazon Bedrock AgentCore，因此 agent 的响应会直接流入下一个状态。Validate 分支于是变成一个单独的 Task 状态：

```
"ValidateDirect": {
  "Type": "Task",
  "Resource": "arn:aws:states:::aws-sdk:bedrockagentcore:invokeAgentRuntime",
  "Parameters": {
    "AgentRuntimeArn": "${AgentRuntimeArn}",
    "RuntimeSessionId.$": "States.Hash($$.Execution.Id, 'SHA-256')",
    "Payload.$": "States.JsonToString($.prep.agentInput)"
  },
  "ResultSelector": { "raw.$": "$.Response" },
  "TimeoutSeconds": 120,
  "Next": "ParseVerdict"
}
```

**成本。** 路径中没有 Lambda 函数，因此没有闲置的 Lambda 算力需要付费。等待由 Step Functions 持有，而 Standard 工作流按状态转换计费，而不是按等待时长计费，所以处理期间真正有意义的成本就是 agent 本身。

### 模式 3：Lambda durable function

如果你更愿意把编排集中写在一处的代码，而不是写成状态机，Lambda durable function（持久函数）能提供相同的成本表现。使用 `@aws/durable-execution-sdk-js` SDK，pipeline 的各阶段变成 `context.step` 调用，并行部分变成 `context.parallel`，对 agent 的等待变成 `context.waitForCallback`。在等待期间函数挂起，不计收算力费用。agent 通过 `SendDurableExecutionCallbackSuccess` 恢复它。

```
// Suspend the function until the agent calls back
const result = await ctx.waitForCallback(
  "validate-agentcore",
  async (callbackId) =>
    dispatchAgentCore(callbackId, document, extractedText, executionId),
  { timeout: { seconds: 120 } }
);
```

**成本。** 单个函数持有整条 pipeline，但它在挂起等待 agent 期间不计收算力费用。你只为挂起之间的短暂执行片段付费，与任务令牌模式的经济性相同，而不是为等待付费。

## 量化差异

重点不在某个具体数字。agent 的运行时长会随 prompt、模型与文档变化。真正重要的是任务令牌模式中两个值之间的*关系*：Validate 状态处于活动状态多久，对比派发函数实际计费多久。我们测试中的一次运行让这种关系变得可见：

```
Step Functions, ValidateDispatch state
   Returned (TaskSubmitted): 14:08:19   <- the function returned and shut down
   Resumed  (TaskSucceeded): 14:08:34   <- the agent woke the execution
   State active ........ 19.6s

Lambda, dispatcher function (CloudWatch REPORT)
   Billed duration ..... 4.8s

Result: the state was active for 19.6s, but the function was billed for 4.8s.
The ~14.8s in between is wait time with no Lambda function running.
```

你可以在 Step Functions 的事件历史中看到同样的情况：采用任务令牌模式时，`TaskSubmitted` 事件（函数已返回）与 `TaskSucceeded`（agent 恢复了流程）之间隔着 agent 的处理时间。同步调用则没有这样的间隔。

下表总结了 Validate 分支（在上图中高亮）在各模式中的实现方式：

|  | **阻塞式（反模式）** | **模式 1：任务令牌** | **模式 2：直接集成** | **模式 3：durable function** |
| --- | --- | --- | --- | --- |
| 编排器 | Step Functions | Step Functions | Step Functions | Lambda（代码） |
| 路径中的 Lambda 函数 | 有，全程存活并计费 | 有，但会提前返回 | 无 | durable function（会挂起） |
| 等待期间的闲置 Lambda 算力 | 承担整个等待时间 | 无 | 无 | 无 |
| agent 调用周围的自定义代码 | 有 | 有 | 有限（状态变换） | 有 |
| 让调用方与 agent 解耦 | 否 | 是 | 否 | 是 |
| 相对复杂度 | 最低 | 较高（令牌与回调 IAM） | 最低 | 中等（checkpoint/replay） |

解读这张表有一个前提：pipeline 的*总*时长并不是有用的比较指标，因为它主要由 agent 自身的推理时间决定，而这一时间每次运行都不同，在各个场景中又基本相同。有意义的差异是你在那段等待期间为多少算力付费——这正是表格与计费时长读数所反映的。agent 运行时长增长时，派发函数的计费时长保持平稳。上面的数字来自单次运行，请把它们当作对这种关系的说明，而不是基准测试，并实测你自己的负载。

## 如何选择模式

下表总结了各项取舍，以帮助你选择模式：

|  | **阻塞式（反模式）** | **模式 1：任务令牌** | **模式 2：直接集成** | **模式 3：durable function** |
| --- | --- | --- | --- | --- |
| **调用方成本** | 完整的 agent 处理时间 | 数秒（仅派发） | 零（无 Lambda） | 数秒（仅派发） |
| **集成工作量** | 低 | 中高（IAM、心跳、超时） | 低（单个 Task 状态） | 中等（checkpoint-and-replay 模型） |
| **业务逻辑所在位置** | Lambda 中（调用前后） | Lambda 中（调用前后） | 仅在 Amazon States Language（ASL）中（内置函数） | Lambda 中（顺序代码） |
| **最适合** | 原型、短时 agent | 自定义前后处理逻辑 | 纯编排、无自定义代码 | 单函数内的复杂异步工作流 |

## 最佳实践

**防范 agent 永不回答。** 为每个 `waitForTaskToken` 状态设置 `TimeoutSeconds`，让执行以 `States.Timeout` 失败，而不是无限期挂起。如果你的 agent 会发送心跳，还要设置 `HeartbeatSeconds`，以便更快检测到 agent 已死。捕获该错误并路由到失败或人工审查路径。

**在重试之间使用稳定的 session ID。** 把 `sessionId` 设为由执行上下文派生的值（例如 Step Functions 执行名称），这样重试会恢复同一个 agent session，而不是从头开始。在任务令牌模式中，在派发函数里设置它；在直接集成模式中，在 Task 状态参数里设置它。

**启用 AWS X-Ray。** 在 Step Functions 与 Lambda 配置中启用 `Tracing: Active`。X-Ray 会准确显示 agent 思考了多久、调用方等待了多久，从而确认你的模式确实在间隙期间释放了算力。

**按速度而非按 agent 的工作负载来确定派发函数的规格。** 派发函数只负责序列化请求并调用端点。256 MB 内存与 30 秒超时通常就足够。繁重的工作发生在 agent 一侧。

## 成本

这些模式会产生 Lambda 算力、Step Functions 状态转换、durable function 执行存储的费用，以及所有方案共同的 Amazon Bedrock AgentCore runtime 与 Amazon Bedrock 模型推理费用。agent 与模型的成本在四种情况下相同。架构只改变编排开销，以及在阻塞式反模式中浪费的闲置 Lambda 算力。最新价格请参阅各服务的定价页面。

## 结论

把 AI agent 放进 pipeline 是直截了当的部分。以经济的方式调用它，才是区分原型与生产设计的关键。一个阻塞等待 agent 的 Lambda 函数实现简单，却会悄悄变得昂贵，它把大部分计费时间花在等待上。本文展示了三种避免这种情况的方式：在需要在路径中保留 Lambda 函数时使用任务令牌回调，在最简单的情况下使用直接服务集成，在你更愿意把编排写成代码时使用 durable function。三者都由同一个 Amazon Bedrock AgentCore agent 驱动，该 agent 会根据被调用的方式调整响应。

完整示例（包括完整的 agent、状态机定义与 durable function）可在 GitHub 上的 [sample-bedrock-agentcore-async-stepfunctions](https://github.com/aws-samples/sample-bedrock-agentcore-async-stepfunctions) 仓库中获取。如需深入了解，请参阅 Amazon Bedrock AgentCore 关于异步任务处理的文档。

对于生产部署，请使用 [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 对 agent 的输入与输出实施负责任的 AI 管控。
