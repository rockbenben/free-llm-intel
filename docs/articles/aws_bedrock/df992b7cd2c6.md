# UAEF：一套不依赖框架、用于 AI agent 闭环评估的系统

在 AWS 上构建 AI agent 的团队用着各种框架，包括 LangGraph、LangChain、Strands Agents 和 Amazon Bedrock AgentCore。每个框架记录 agent 执行过程的方式都不一样，因此消息、工具调用以及 agent 之间交接的结构，彼此各不相同。评估工具往往也跟着划界：团队针对某一个框架的 trace 格式去建指标、评分逻辑和结果存储，一旦换了框架、或同时在不止一个框架上跑 agent，就得把这些重做一遍。

这种耦合让一个基本的开发问题更难回答：改了 prompt、模型或工具之后，agent 到底变好了没有？要回答它，需要跨 agent 版本保持一致的可比指标，还要有一份共享的历史结果记录来作对照。agent 的质量还横跨好几个维度，光靠一个准确率分数是捕捉不到的：工具调用、回答质量、responsible AI、性能、多轮对话、多 agent 协同，以及推理。

本文里，我们介绍 Universal Agent Evaluation Framework（UAEF）。来自电信、医疗和金融服务行业 12 家组织的客户用 UAEF、以同一套一致的指标评估他们的 AI agent，并在发布前比较 agent 各版本。UAEF 是一套不依赖框架的评估系统：它用 adapters 把各框架的 trace 转成统一格式，再用横跨 7 个维度、36 个内建指标给这些 trace 打分。它把结果存进 Amazon DynamoDB 和 Amazon Simple Storage Service（Amazon S3），并生成报告与洞察，为 agent 的下一轮迭代提供依据。本文说明 UAEF 如何工作，给出挑选指标、准备数据集的实操手册，并指向每个受支持框架可跑的 notebooks。

## UAEF：给 agent 框架的一层统一评估

UAEF 是一套不依赖框架的 AI agent 评估系统。它拿团队手头已有的 agent，在受支持的框架与 runtime 上以同样的方式打分。UAEF 有两个输入：待测 agent，以及用来跑它的数据集。数据集为每个测试用例提供输入，也可以带上 ground-truth 答案，即每个输入对应的预期输出。ground truth 是可选的，只有那些把 agent 回答与参考答案作比较的指标才用它。要评估工具调用，ground truth 还得包含每个测试用例预期发生的工具调用：agent 该调哪些工具、按什么顺序、带什么参数。之后的一切都在 UAEF 内部完成。

图 1 展示一次评估从输入到报告与洞察所走的路径。首先，一个 adapter 读入 agent 原生的执行记录（消息、工具调用、agent 之间的交接），把它规范化成一条 canonical trace，于是无论 agent 由哪个框架产出，后续步骤都完全相同。接着，UAEF 在数据落盘之前筛查 trace 里的 personally identifiable information（PII），例如邮箱地址、电话号码和信用卡号。随后评估引擎从横跨 7 个质量维度、36 个内建指标里选出一组，给这条 trace 打分。当你持久化一次运行时，UAEF 把它作为一个 experiment 记进 Amazon DynamoDB 和 Amazon S3：Amazon DynamoDB 存用于列举与比较的逐 experiment 元数据，Amazon S3 存完整结果。运行记录存下来后，团队就能拿某个 agent 版本与 baseline 对比、检测回归，并生成报告与洞察，解释变了什么、为什么变。这些报告把环闭合：团队评估 agent，弄清哪里退步、哪里改善，改 prompt、模型或工具，再评估一次。

### canonical trace 与 adapters

adapters 正是 UAEF 不依赖框架的关键。一个 adapter 读入 agent 一次运行的记录，包括消息、工具调用和 agent 之间的交接。它把这份记录转成一种叫做 `AgentTrace` 的 canonical 表示，而这也是 UAEF 其余部分唯一打分的对象。有了这层转换，UAEF 就能配合任何 SDK 构建出的 agent 工作（例如 LangGraph、LangChain 或 Strands Agents）。它可以在本地跑、在 HTTP endpoint 之后跑，也可以在 Amazon Bedrock AgentCore 这类托管 runtime 上跑；trace 可以放在 Langfuse 里，也可以完全没采集。UAEF 为上述每种情形都提供了 adapter，它们产出同样的 `AgentTrace`，因此指标、分数和比较在所有情形下都保持一致。

trace 有两种进入 UAEF 的方式。如果已经存在——来自过去的一次运行、一份日志或某个可观测性存储——就把它交给 UAEF，由对应的 adapter 规范化。如果没有，UAEF 会替你调用 agent：给定一个 runtime Amazon Resource Name（ARN）或一个 HTTP endpoint，它对数据集里的每个输入调用 agent，收集回答，并一步完成适配。两种路径的输出都是同一个 `AgentTrace`。

因为每个指标、每种模式和每份报告都作用在 `AgentTrace` 上、而非某个框架原生格式上，所以无论 trace 从哪儿来，后续打分都完全相同。先规范化、再打分，正是这层分离让团队能把一个框架上构建的 agent 与另一个框架上的 agent 放在同一把尺子上比较。

### 评估引擎

评估引擎给一条 canonical trace 在 7 个质量维度上打分，每个维度捕捉 agent 行为里一个单独的侧面，而一个准确率数字会把这些侧面全都盖住。Tool calling 衡量 agent 是否选对了工具、调用顺序是否合理、参数是否有效。Response quality 衡量最终回答是否相关、完整、准确，且以给定上下文为依据而非凭空捏造。

Responsible AI 衡量安全性、偏见、毒性，以及抵御 prompt injection 的能力。Performance 衡量时延、token 用量和吞吐上的运营成本。Multi-turn 衡量 agent 把一场对话维持得多好，包括跨轮次的上下文保持、连贯性和目标完成度。Multi-agent 衡量协作式 agent 系统里的协同，例如任务委派与工作划分。Reasoning 衡量 agent 思维链的内在逻辑，包括一致性和有没有谬误。

每个维度由 36 个内建指标中的一个或多个算出，每个指标都返回 [0, 1] 区间里一个归一化分数，1 为最好，因此各维度与总结果共用同一把尺子。指标分两类。Deterministic metrics 直接从 trace 和 ground truth 算出分数，重复运行时结果完全一致。Large language model（LLM）-as-a-judge metrics 通过对 Amazon Bedrock 上的一个 judge 模型下 prompt，给那些难以用闭式定义刻画的性质（如回答相关性或安全性）打分。你也可以加自己的 custom metrics，或借用 RAGAS 与 DeepEval 的集成。

由于 judge 指标会把 agent 自己的输出回灌进一条 prompt，那些内容被当作不可信输入：能影响 judge 的 agent，就能影响自己的分数。rubric 与内容分开发送，并且内容会做转义，使它无法越出分隔符、被当成指令来读。每条 judge 回答都被严格解析，且必须引用它所评内容里一段逐字的原文。证据找不到的分数会被拒掉，而不是记下来。judge 分数是评估信号，不是安全决策，不应用来把关某个安全控制。要在 agent 本身上做运行时强制，就在它自己的调用路径里施加 Amazon Bedrock Guardrails。完整模型见 SECURITY.md。

### experiment 管理与比较

UAEF 把每次评估记成一个 experiment，这样不同 agent 版本的结果日后可以比较。以 `persist=True` 调用 `evaluate()` 或 `batch_evaluate()` 会新建一个 experiment，由一个可选的 name 和 objective 标识，并把它写进两个职责互补的存储。Amazon DynamoDB 为每个 experiment 存一行，放用于列举与比较的元数据：评估次数、每个指标的平均分，以及总体平均分。Amazon S3 存一个带完整评估结果的 JSON 文件，包括逐指标分数和 judge 的推理。处理敏感数据的团队可以为落盘的那份副本打开 PII 脱敏。

Python 库还建了一层更细的结构。一个 experiment 包含若干 runs，每次 run 记下待测的 agent 设计：框架、模型、工具、system prompt 和参数。一次 run 还可以记一份配置快照和一个 Git commit。你可以把某次 run 标成该 experiment 的 baseline。这样每个分数都挂到产出它的那次改动上——不管是一个新 prompt、一个不同的模型，还是新加的一个工具。

比较作用在存下来的逐指标平均值上。对两次 run 共有的每个指标，比较引擎算出绝对变化和百分比变化，然后用一个可配阈值（默认 5%）把该指标判为 regression、improvement 或 unchanged。一次调用就能把若干 runs 与同一个 baseline 比较。回归检测器还为每个回归定一个严重度：minor（5–10%）、moderate（10–20%）或 severe（超过 20%）。它按维度给回归分组，由此能看出，比如一次 prompt 改动是否影响了 tool calling 却没影响 response quality。

在 web UI 里，Compare 标签页列出已存的 experiments，并可按框架或数据集筛选。你选中两个或更多 experiments，第一个被用作 baseline，UI 展示逐指标分数，并高亮 regressions 与 improvements。UI 调的是同一个库比较引擎，因此结果与 Python API 返回的一致。

### 报告与洞察生成

一次评估存下来之后，UAEF 在三个层次上给出报告，各自回答一个不同的问题：这次 run 表现如何？为什么会得这个分？跟早先的版本比怎么样？

**Results view。** 评估结束时，web UI 展示 experiment 的概要：总分、评估过的测试用例数、框架，以及运行失败的 queries。逐指标平均值配上一张维度雷达图和一张指标柱状图。一张表列出每个测试用例的 query、agent 的回答、预期答案和分数。展开一行可以看到完整回答，连同它的维度分与指标分。对多轮对话，它展示每一轮各自的分数以及 agent 调用过的工具。

**Detailed report。** 从 results view 或 experiment 列表，你可以按需生成一份统计报告。UAEF 从 Amazon S3 载入已存结果，并在新的浏览器标签页里打开报告。报告按维度和按指标拆解结果，展示每个指标的置信区间与离群值、分数分布、指标之间的相关性、一份 responsible AI 摘要，以及报告了失败的测试用例。结尾给出建议，指向得分最低的维度和跨测试用例波动最大的指标。报告只由分数算出、不经过 LLM，因此同样的结果会产出同样的报告。

**LLM 生成的洞察。** 在 Python 库里，你可以把一份报告交给 Amazon Bedrock 上的模型去分析。对单次 run，分析涵盖优势、关键短板、关于根因的假设，以及排好优先级的建议。对若干次 runs 的比较，它涵盖总体趋势、regressions 与 improvements 的可能成因、每个回归带来的风险，以及下一步。这些洞察提示你在下一轮评估之前，该改 prompt、模型或工具里的什么。

### 两种用法

同一套引擎上，UAEF 有两种跑法。用 Python 库，你可以在代码里从 notebooks、脚本和 continuous integration and continuous delivery（CI/CD）流水线评估 agent。用可部署的 AWS 服务，你可以通过一个低代码 web 界面评估 agent：上传数据集、选框架和指标、跑评估、看分数。两条路径跑的是同一个评估引擎、写的是同一批存储，因此结果不取决于它由哪条路径产出。你可以从界面起步，再转到代码，而不必改变结果的打分或比较方式。

### 挑选流水线

指标决定你测什么，六个彼此独立的选择决定评估怎么跑。用每一行里的问题把它们定下来。

| **选择** | **问自己** | **于是用** | **在代码里** |
| --- | --- | --- | --- |
| **被动还是主动** | 我是已经有 trace 了，还是需要在受控条件下生成它们？ | **被动（Passive）：** 评估一条你已有的 trace。**主动（Active）：** 调一个 invoke_* helper，让 UAEF 来跑 agent。 | evaluate(trace=recorded, adapter=“langgraph”) *或* raw = invoke_http_agent_for_framework( ENDPOINT, query, “strands”) |
| **一条 trace 还是一个数据集** | 我是在调一个 case，还是在衡量一次发布？ | 一条 trace 或一场对话用 evaluate()。数据集用 batch_evaluate()。 | evaluate(trace=trace) *或* batch_evaluate(traces=traces, max_workers=4) |
| **单轮还是多轮a** | 有没有哪个测试用例依赖先前的一轮？ | **多轮：** 给数据集加 session_id 和 turn_id，把每一轮都交给 adapter，由它拼出各场对话。 | sessions = adapter.transform_to_canonical( turn_payloads) batch_evaluate(traces=sessions) |
| **单 agent 还是多 agent** | 一次请求是否由不止一个 agent 处理？ | 无需配置。adapter 返回 AgentTrace 或 MultiAgentTrace，UAEF 选对应的 evaluator。 | adapter = get_adapter(FRAMEWORK) trace = adapter.transform_to_canonical(raw) |
| **离线还是在线** | 我是在发布前测试，还是在监控生产？ | **离线：** 开发与 CI 里一份准备好的数据集。**在线：** 实时对话，逐轮打分。 | batch_evaluate(…) *或* OnlineEvaluator().evaluate_response( trace=trace) |
| **临时还是持久化b** | 我会不会拿这次 run 与之后的一次比较？ | **持久化：** 设 persist=True 并给一个 experiment name。否则用返回的结果。 | batch_evaluate(traces=traces, persist=True, experiment_name=“Support agent v2”) |

**a** **多轮 –** 详见 [multi-turn evaluation workflow guide](https://awslabs.github.io/uaef/Advanced/multi-turn-evaluation-workflow/)。

**b** **只有持久化的 runs 才能比较**。

### 准备数据集

在 CSV 或 XLSX 文件里，每个测试用例给一行。只有 `Question` 是必需的。

| **列** | **是否必需** | **用途** |
| --- | --- | --- |
| `Question` | 是 | 发给 agent 的输入 |
| `Answer` | 否 | 预期回答 |
| `context` | 否 | 用于检索式评估的参考文档 |
| `expected_tool_calls` | 否 | 以 JSON array 给出的预期工具调用 |
| `session_id` | 仅多轮 | 把若干行归为一场对话 |
| `turn_id` | 仅多轮 | 给一场对话里的轮次排序，从 1 开始 |

`Question` 和 `Answer` 匹配时不区分大小写，也接受 `Query`、`Expected_Output` 这类常见别名，所以既有测试文件通常不用改名就能用。

**多轮数据集。** 共享同一个 `session_id` 的行会按顺序发给同一个 agent session，因此后面的轮次可以依赖前面的轮次。你的 agent endpoint 必须自己维护会话状态，因为 UAEF 发每一轮时只带其 session ID，并不重放历史。请用小写的 `session_id` 和 `turn_id`，否则文件会被当作单轮来评估。

**保护敏感数据。** 分享或持久化一份取自真实流量的数据集之前，用 `uaef.security.PIIDetector` 检测并脱敏 personally identifiable information，例如邮箱地址、电话号码和信用卡号。

## 清理

跑这个库本身不会创建任何东西，但持久化一次 run 会把 experiment 元数据写进 Amazon DynamoDB、把完整结果写进 Amazon S3。不再需要已存的 experiments 时，把两处都删掉。默认名字是 `uaef-experiments` 和 `uaef-results`，可通过 `UAEF_DYNAMODB_TABLE` 与 `UAEF_S3_BUCKET` 环境变量覆盖。bucket 要先清空才能删除。

如果你部署过这套服务，[service deployment guide](https://github.com/awslabs/uaef/blob/main/uaef-service/README.md) 给了两种部署模式各自的拆除顺序。别想当然以为拆完就干净了，先读它的保留资源说明：DynamoDB 表、S3 buckets 和 Amazon Cognito user pool 都以 retain policy 创建，所以删掉 stack 会把它们连同内容一起留下。这是有意为之，好让一次拆除不至于毁掉已存的 experiments，但也意味着存储在你自己动手移除之前会一直产生费用。

## 结语

UAEF 把 agent 评估与产出 agent 的框架分开了。adapters 把来自 LangGraph、LangChain、Strands Agents、Amazon Bedrock AgentCore 和 Langfuse 的 traces 转成统一格式，一个通用 JSON adapter 处理其它框架。随后，横跨 7 个维度、同样的 36 个内建指标一律适用，与团队怎么构建 agent 无关。UAEF 既评估单条 trace，也在历史 traces 上跑批量评估，再把结果按 experiment 存进 Amazon DynamoDB 和 Amazon S3。团队于是能跨 agent 版本比较 runs、检测回归，并用生成的报告与洞察决定下一轮迭代该改什么。web UI 与 Python 库共用同一个评估引擎，因此团队可以从低代码起步、再转到代码，而不必改变打分或存储的工作方式。

要上手，见 [open source repository](https://github.com/awslabs/uaef)。
