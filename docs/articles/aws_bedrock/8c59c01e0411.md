# 用 Amazon Bedrock AgentCore 把 AI agent 从概念验证推向生产环境

构建一个能在生产环境中处理真实用例的 AI agent 是一项复杂的工程。虽然做一个概念验证可以展示潜力，但走向生产需要解决在开发环境中不会暴露的可扩展性、安全性、可观测性和运维问题。

本文探讨 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 如何帮助你让 agentic 应用从实验性的概念验证过渡到生产就绪的系统。我们跟随一个客户支持 agent 的演进历程：它从一个简单的本地原型，发展为能够处理多个并发用户、同时保持安全与性能标准的完整企业级解决方案。

Amazon Bedrock AgentCore 是一套全面的服务，旨在帮助你构建、部署和扩展 agentic AI 应用。如果你是 AgentCore 的新手，我们建议先阅读我们已有的各项服务深度解析文章：[AgentCore Runtime](https://aws.amazon.com/blogs/machine-learning/securely-launch-and-scale-your-agents-and-tools-on-amazon-bedrock-agentcore-runtime/) 用于安全地部署和扩展 agent，[AgentCore Gateway](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-bedrock-agentcore-gateway-transforming-enterprise-ai-agent-tool-development/) 用于企业工具开发，[AgentCore Identity](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-bedrock-agentcore-identity-securing-agentic-ai-at-scale/) 用于在大规模场景下保护 agentic AI，[AgentCore Memory](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-agentcore-memory-building-context-aware-agents/) 用于构建具备上下文感知的 agent，[AgentCore Code Interpreter](https://aws.amazon.com/blogs/machine-learning/introducing-the-amazon-bedrock-agentcore-code-interpreter/) 用于代码执行，[AgentCore Browser Tool](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-bedrock-agentcore-browser-tool/) 用于 Web 交互，以及 [AgentCore Observability](https://aws.amazon.com/blogs/machine-learning/build-trustworthy-ai-agents-with-amazon-bedrock-agentcore-observability/) 用于洞悉 agent 的行为。本文演示这些服务如何在真实场景中协同工作。

## 客户支持 agent 的演进历程

客户支持是 agentic AI 最常见、最有说服力的用例之一。现代企业每天要处理成千上万的客户咨询，从简单的政策问题到复杂的技术故障排查。传统做法往往力有未逮：基于规则的 chatbot 用僵化的回答让客户沮丧，而纯人工的支持团队则在可扩展性和一致性上苦苦挣扎。一个智能的客户支持 agent 需要无缝处理各种场景：管理客户订单和账户、查询退货政策、搜索产品目录、通过网络检索排查技术问题，以及在多次交互中记住客户偏好。最重要的是，它必须在做到这一切的同时，维持企业环境所要求的安全与可靠性标准。设想许多组织在构建此类 agent 时通常经历的演进路径：

- **概念验证阶段** – 团队从一个简单的本地原型开始，展示核心能力，例如一个能回答政策问题并搜索产品的基础 agent。这对演示来说足够好，但缺乏真实客户交互所需的健壮性。
- **现实的检验** – 一旦你尝试扩展到少数测试用户之外，挑战就出现了。agent 忘记之前的对话，工具在负载下变得不可靠，没有办法监控性能，而安全成为首要关切。
- **生产的挑战** – 走向生产需要解决会话管理、安全的工具共享、可观测性、身份认证，以及构建客户真正愿意使用的界面。许多前景看好的概念验证就因这些需求的复杂性而停滞在这一阶段。

在本文中，我们逐一系统性地应对每个挑战。我们从配备三个基本工具的 agent 原型开始：退货政策查询、产品信息检索，以及用于故障排查的网络搜索。在此基础上，我们添加上生产部署所需的能力：用于保持对话连续性和超个性化体验的持久记忆、用于可靠性和安全性的集中式工具管理、用于监控和调试的完整可观测性，最后是面向客户的 Web 界面。这一演进过程映射了从概念验证到生产的真实路径，展示了 Amazon Bedrock AgentCore 各项服务如何协同解决 agentic 应用走向成熟时出现的运维挑战。为简化和演示起见，我们采用单 agent 架构。在真实用例中，客户支持 agent 常常以多 agent 架构构建，这些场景同样受到 Amazon Bedrock AgentCore 服务的支持。

## 解决方案概览

每个生产系统都始于概念验证，我们的客户支持 agent 也不例外。在第一个阶段，我们构建一个可运行的原型，展示客户支持所需的核心能力。在这个案例中，我们使用开源 agent 框架 [Strands Agents](https://strandsagents.com/latest/) 构建概念验证，并使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上 Anthropic 的 Claude 3.7 Sonnet 作为驱动 agent 的大语言模型（LLM）。你的应用可以使用其他 agent 框架和模型。

agent 依靠工具来执行操作，并与真实运行的系统交互。客户支持 agent 会用到多种工具，但为让示例保持简单，我们聚焦三项核心能力来处理最常见的客户咨询：

- **退货政策查询** – 客户经常询问退货窗口、条件和流程。我们的工具基于产品类别提供结构化的政策信息，涵盖从退货时限到退款处理和配送政策的所有内容。
- **产品信息检索** – 技术规格、保修细节和兼容性信息对购买前咨询和故障排查都至关重要。该工具作为通往你产品目录的桥梁，提供客户能够理解的格式化技术细节。
- **用于故障排查的网络搜索** – 复杂的技术问题往往需要内部文档中没有的最新解决方案或社区给出的修复方法。网络搜索能力让 agent 可以实时访问网络，获取最新的排查指南和技术方案。

该用例的工具实现和端到端代码可在我们的 [GitHub repository](https://github.com/awslabs/amazon-bedrock-agentcore-samples/tree/main/01-tutorials/07-AgentCore-E2E) 中获取。本文聚焦与 Amazon Bedrock AgentCore 对接的主要代码，但你可以按照仓库中的端到端流程实践。

```
    # check github for full code

@tool
def web_search(keywords: str, region: str = "us-en", max_results: int = 5) -> str:
    """Search the web for updated troubleshooting information."""
    # Provides access to current technical solutions and guides
    # check github for full code
    return "results from websearch"
    
# Initialize the Bedrock model
model = BedrockModel(
    model_id="us.anthropic.claude-3-7-sonnet-20250219-v1:0",
    temperature=0.3
)

# Create the customer support agent
agent = Agent(
    model=model,
    tools=[
        get_product_info, 
        get_return_policy,

    Use the appropriate tools to provide accurate information and always offer additional help."""
)
```

## 概念验证的现实检验

我们的概念验证成功证明了 agent 可以借助合适的工具组合与推理来处理多样的客户支持场景。agent 在你的本地机器上运行完美，也能正确处理查询。然而，概念验证的差距恰恰在这里显现。这些工具在 agent 代码中被定义为本地函数，agent 响应很快，一切看起来都已生产就绪。但只要你开始考虑单用户测试之外的情形，若干关键限制就会立刻显现：

- **会话之间的记忆丢失** – 如果你重启 notebook 或应用，agent 会完全忘记之前的对话。昨天还在讨论笔记本退货的客户，今天不得不从头开始，重新解释整个情况。这不仅不方便——它还是一种糟糕的客户体验，破坏了让 AI agent 具有价值的对话连贯性。
- **只能服务单个客户** – 你当前的 agent 一次只能处理一段对话。如果两位客户同时尝试使用你的支持系统，他们的对话会相互干扰，更糟的是，一位客户可能会看到另一位客户的对话历史。系统没有任何机制为不同用户维护独立的对话上下文。
- **工具内嵌在代码中** – 你的工具直接定义在 agent 代码里。这意味着：你无法在不同的 agent（销售 agent、技术支持 agent 等）之间复用这些工具。更新一个工具需要修改 agent 代码并重新部署所有内容。不同团队无法各自独立地维护不同的工具。
- **没有生产基础设施** – agent 在本地运行，完全没有考虑可扩展性、安全性、监控和可靠性。

这些根本性的架构障碍会阻碍真实的客户部署。agent 构建团队可能要花数月来处理这些问题，既延迟了工作产生价值的时间，也为应用增加了大量成本。这正是 Amazon Bedrock AgentCore 服务变得不可或缺的地方。与其花数月从零构建这些生产级能力，Amazon Bedrock AgentCore 提供了托管服务，系统性地填平每一处差距。

让我们从先解决记忆问题开始走向生产之旅，把 agent 从每次对话都会遗忘，变为能够跨对话记住客户，并能使用 Amazon Bedrock AgentCore Memory 实现超个性化对话。

## 添加持久记忆，打造超个性化的 agent

我们在概念验证中识别出的第一个主要限制是记忆丢失——我们的 agent 在会话之间忘记一切，迫使客户每次都重复他们的上下文。这种“金鱼 agent”行为破坏了让 AI agent 具有价值的对话体验。

Amazon Bedrock AgentCore Memory 通过提供在两个互补层级上运作的托管持久记忆来解决这个问题：

- **短期记忆** – 即时的对话上下文和基于会话的信息，用于在单次交互内保持连续性
- **长期记忆** – 跨多次对话提取的持久信息，包括客户偏好、事实和行为模式

### 创建记忆资源

Amazon Bedrock AgentCore Memory 使用可配置的策略来决定提取和存储哪些信息。对于我们的客户支持用例，我们使用两种互补的策略：

- **USER_PREFERENCE **– 自动提取并存储客户偏好，例如“偏好 ThinkPad 笔记本”“使用 Linux”或“玩竞技类 FPS 游戏”。这可以在多次对话之间实现个性化推荐。
- **SEMANTIC **– 使用向量 embedding 捕获事实信息，例如“客户有 MacBook Pro 订单 #MB-78432”或“报告在视频剪辑时出现过热问题”。这为故障排查提供了相关上下文。

参见以下代码：

```
from bedrock_agentcore.memory import MemoryClient
from bedrock_agentcore.memory.constants import StrategyType

memory_client = MemoryClient(region_name=region)

strategies = [
    {
        StrategyType.USER_PREFERENCE.value: {
            "name": "CustomerPreferences",
            "description": "Captures customer preferences and behavior",
            "namespaces": ["support/customer/{actorId}/preferences"],
        }
    },
    {
        StrategyType.SEMANTIC.value: {
            "name": "CustomerSupportSemantic", 
            "description": "Stores facts from conversations",
            "namespaces": ["support/customer/{actorId}/semantic"],
        }
    },
]

# Create memory resource with both strategies
response = memory_client.create_memory_and_wait(
    name="CustomerSupportMemory",
    description="Customer support agent memory",
    strategies=strategies,
    event_expiry_days=90,
)
```

### 与 Strands Agents 的 hook 集成

让记忆无缝工作的关键在于自动化——客户不应该需要考虑它，agent 也不应该需要手动管理记忆。Strands Agents 提供了强大的 [hook 系统](https://strandsagents.com/latest/documentation/docs/user-guide/concepts/agents/hooks/)，让你可以拦截 agent 生命周期事件并自动处理记忆操作。该 hook 系统使内置组件和用户代码都能通过强类型事件回调来响应或修改 agent 行为。对于我们的用例，我们创建 `CustomerSupportMemoryHooks` 来检索客户上下文并保存支持交互：

- **MessageAddedEvent hook** – 当客户发送消息时触发，该 hook 自动检索相关的记忆上下文并注入到查询中。agent 无需人工干预即可同时收到客户的问题和相关的历史上下文。
- **AfterInvocationEvent hook** – 在 agent 响应之后触发，该 hook 自动将本次交互保存到记忆中。对话会立即成为客户持久历史的一部分。

参见以下代码：

```
class CustomerSupportMemoryHooks(HookProvider):
    def retrieve_customer_context(self, event: MessageAddedEvent):
        """Inject customer context before processing queries"""
        user_query = event.agent.messages[-1]["content"][0]["text"]
        
        # Retrieve relevant memories from both strategies
        all_context = []
        for context_type, namespace in self.namespaces.items():
            memories = self.client.retrieve_memories(
                memory_id=self.memory_id,
                namespace=namespace.format(actorId=self.actor_id),
                query=user_query,
                top_k=3,
            )
            # Format and add to context
            for memory in memories:
                if memory.get("content", {}).get("text"):
                    all_context.append(f"[{context_type.upper()}] {memory['content']['text']}")
        
        # Inject context into the user query
        if all_context:
            context_text = "\n".join(all_context)
            original_text = event.agent.messages[-1]["content"][0]["text"]
            event.agent.messages[-1]["content"][0]["text"] = f"Customer Context:\n{context_text}\n\n{original_text}"

    def save_support_interaction(self, event: AfterInvocationEvent):
        """Save interactions after agent responses"""
        # Get last customer query and agent response check github for implementation
        customer_query = "This is a sample query"
        agent_response = "LLM gave a sample response"
        
        # Extract customer query and agent response
        # Save to memory for future retrieval
        self.client.create_event(
            memory_id=self.memory_id,
            actor_id=self.actor_id,
            session_id=self.session_id,
            messages=[(customer_query, "USER"), (agent_response, "ASSISTANT")]
        )
```

在这段代码中可以看到，正是我们的 hook 在与 Amazon Bedrock AgentCore Memory 交互，保存和检索记忆事件。

### 将记忆与 agent 集成

为现有 agent 添加记忆只需要极少的代码改动；你只需实例化记忆 hook 并将它们传给 agent 构造函数。agent 代码随后只需要与记忆 hook 对接，即可使用 Amazon Bedrock AgentCore Memory 的全部能力。我们会为每个会话创建一个新的 hook，这有助于我们处理不同的客户交互。参见以下代码：

```
# Create memory hooks for this customer session
memory_hooks = CustomerSupportMemoryHooks(
    memory_id=memory_id, 
    client=memory_client, 
    actor_id=customer_id, 
    session_id=session_id
)

# Create agent with memory capabilities
agent = Agent(
    model=model,

    tools=[get_product_info, get_return_policy, web_search],
    system_prompt=SYSTEM_PROMPT
)
```

### Amazon Bedrock AgentCore Memory 的优势

集成 Amazon Bedrock AgentCore Memory 之后，我们的 agent 现在带来以下优势：

- **对话连续性** – 客户可以从上次离开的地方继续，即使跨越不同会话或支持渠道
- **个性化服务** – 推荐和响应针对个人偏好和过往问题量身定制
- **上下文化故障排查** – 可以访问之前的问题与解决方案，从而实现更有效的支持
- **无缝体验** – 记忆操作自动发生，无需客户或 agent 介入

不过，我们仍有局限需要解决。我们的工具仍内嵌在 agent 代码中，无法在不同的支持 agent 或团队之间复用。安全与访问控制非常有限，而且在生产环境中我们仍然无法同时处理多个客户。

在下一节中，我们通过使用 Amazon Bedrock AgentCore Gateway 集中管理工具，并用 Amazon Bedrock AgentCore Identity 实施恰当的身份管理，来应对这些挑战，为客户支持系统打造可扩展且安全的基础。

## 用 Amazon Bedrock AgentCore Gateway 和 Amazon Bedrock AgentCore Identity 集中管理工具

记忆问题解决后，下一个挑战是工具架构。目前，我们的工具直接内嵌在 agent 代码中——这种模式适合原型，但在规模化时会带来显著问题。当你需要多个 agent（客户支持、销售、技术支持）时，每一个都会重复相同工具，导致大量冗余代码、不一致的行为和难以维护的困境。

Amazon Bedrock AgentCore Gateway 通过将工具集中为可供 agent 访问的可复用、安全的端点来简化这一过程。结合用于身份认证的 Amazon Bedrock AgentCore Identity，它构建了企业级的工具共享基础设施。

我们现在更新 agent，改用 Amazon Bedrock AgentCore Gateway 和 Amazon Bedrock AgentCore Identity。架构将如下图所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/03/image-5-1.png)

在这个案例中，我们把网络搜索工具改造成可在 gateway 中使用，而把退货政策和产品信息工具保留为该 agent 的本地工具。这很重要，因为网络搜索是组织内可跨不同用例复用的通用能力，而退货政策和产品信息则是通常与客户支持服务关联的能力。借助 Amazon Bedrock AgentCore 服务，你可以决定使用哪些能力以及如何组合它们。在这个案例中，我们还使用了两个本可由其他团队开发的新工具：查询保修（check warranty）和获取客户档案（get customer profile）。由于这些团队已经通过 [AWS Lambda](https://aws.amazon.com/lambda) 函数暴露了这些工具，我们可以把它们作为 Amazon Bedrock AgentCore Gateway 的目标。Amazon Bedrock AgentCore Gateway 还支持将 REST API 作为目标。这意味着，如果我们有 [OpenAPI specification](https://swagger.io/specification/) 或 [Smithy model](https://smithy.io/)，也可以使用 Amazon Bedrock AgentCore Gateway 快速暴露我们的工具。

### 将现有服务转换为 MCP

Amazon Bedrock AgentCore Gateway 使用 [Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) 来标准化 agent 访问工具的方式。将现有 Lambda 函数转换为 MCP 端点所需改动很小——主要是添加工具 schema 并处理 MCP 上下文。为使用这一功能，我们把本地工具转换为 Lambda 函数，并创建工具 schema 定义，使这些函数可被 agent 发现：

```
# Original Lambda function (simplified)
def web_search(keywords: str, region: str = "us-en", max_results: int = 5) -> str:
    # web_search functionality
        
def lambda_handler(event, context):
    if get_tool_name(event) == "web_search":
        query = get_named_parameter(event=event, name="query")
        
        search_result = web_search(keywords)
        return {"statusCode": 200, "body": search_result}
```

以下代码是工具 schema 的定义：

```
{
        "name": "web_search",
        "description": "Search the web for updated information using DuckDuckGo",
        "inputSchema": {
            "type": "object",
            "properties": {
                "keywords": {
                    "type": "string",
                    "description": "The search query keywords"
                },
                "region": {
                    "type": "string",
                    "description": "The search region (e.g., us-en, uk-en, ru-ru)"
                },
                "max_results": {
                    "type": "integer",
                    "description": "The maximum number of results to return"
                }
            },
            "required": [
                "keywords"
            ]
        }
    }
```

为演示起见，我们从零构建一个新的 Lambda 函数。在现实中，组织已有各种以 REST 服务或 Lambda 函数形式提供的功能，而这种方式让你无需重建即可把现有企业服务暴露为 agent 工具。

### 用 Amazon Bedrock AgentCore Gateway 配置安全并与 Amazon Bedrock AgentCore Identity 集成

Amazon Bedrock AgentCore Gateway 对入站和出站连接都要求身份认证。Amazon Bedrock AgentCore Identity 通过标准 [OAuth](https://oauth.net/2/) 流程处理这一点。设置好 OAuth 授权配置后，你可以创建一个新的 gateway 并把该配置传给它。参见以下代码：

```
# Create gateway with JWT-based authentication
auth_config = {
    "customJWTAuthorizer": {
        "allowedClients": [cognito_client_id],
        "discoveryUrl": cognito_discovery_url
    }
}

gateway_response = gateway_client.create_gateway(
    name="customersupport-gw",
    roleArn=gateway_iam_role,
    protocolType="MCP",
    authorizerType="CUSTOM_JWT",
    authorizerConfiguration=auth_config,
    description="Customer Support AgentCore Gateway"
)
```

对于入站认证，agent 必须出示有效的 [JSON Web Token (JWT)](https://en.wikipedia.org/wiki/JSON_Web_Token) token（来自 [Amazon Cognito](https://aws.amazon.com/cognito/)、Okta、EntraID 等身份提供方），作为一种紧凑、自包含的标准，用于在各方之间安全传输信息，从而访问 Amazon Bedrock AgentCore Gateway 的工具。

对于出站认证，Amazon Bedrock AgentCore Gateway 可以使用 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色、API 密钥或 OAuth token 向下游服务进行认证。

为演示起见，我们创建了一个带有虚拟用户名和密码的 Amazon Cognito 用户池。对于你的用例，应设置合适的身份提供方并相应管理用户。这种配置确保只有获授权的 agent 才能访问特定工具，并提供完整的审计轨迹。

### 添加 Lambda 目标

设置好 Amazon Bedrock AgentCore Gateway 后，把 Lambda 函数添加为工具目标非常直接：

```
lambda_target_config = {
    "mcp": {
        "lambda": {
            "lambdaArn": lambda_function_arn,
            "toolSchema": {"inlinePayload": api_spec},
        }
    }
}

gateway_client.create_gateway_target(
    gatewayIdentifier=gateway_id,
    name="LambdaTools",
    targetConfiguration=lambda_target_config,
    credentialProviderConfigurations=[{
        "credentialProviderType": "GATEWAY_IAM_ROLE"
    }]
)
```

现在 gateway 会把你的 Lambda 函数作为 MCP 工具暴露出来，获授权的 agent 可以发现并使用它们。

### 将 MCP 工具与 Strands Agents 集成

把 agent 改为使用集中式工具需要更新工具配置。我们把一些工具保留在本地，例如客户支持特有的产品信息和退货政策，这些在其他用例中很可能不会被复用；而对于共享能力则使用集中式工具。由于 Strands Agents 已[原生集成 MCP 工具](https://strandsagents.com/latest/documentation/docs/user-guide/concepts/tools/mcp-tools/)，我们可以直接使用 Strands 的 `MCPClient` 配合 `streamablehttp_client`。参见以下代码：

```
# Get OAuth token for gateway access
gateway_access_token = get_token(
    client_id=cognito_client_id,
    client_secret=cognito_client_secret,
    scope=auth_scope,
    url=token_url
)

# Create authenticated MCP client
mcp_client = MCPClient(
    lambda: streamablehttp_client(
        gateway_url,
        headers={"Authorization": f"Bearer {gateway_access_token['access_token']}"}
    )
)

# Combine local and MCP tools
tools = [
    get_product_info,     # Local tool (customer support specific)
    get_return_policy,    # Local tool (customer support specific)
] + mcp_client.list_tools_sync()  # Centralized tools from gateway

agent = Agent(
    model=model,
    tools=tools,
    hooks=[memory_hooks],
    system_prompt=SYSTEM_PROMPT
)
```

### 测试增强后的 agent

集成集中式工具后，我们的 agent 现在可以使用保修查询等企业能力：

```
# Test web search using centralized tool  
response = agent("How can I fix Lenovo ThinkPad with a blue screen?")
# Agent uses web_search from AgentCore Gateway
```

agent 无缝地把本地工具与集中式工具结合起来，在保持安全与访问控制的同时，提供全面的支持能力。

不过，我们仍有一个重要限制：整个 agent 运行在开发机器本地。生产部署需要可扩展的基础设施、全面的可观测性，以及处理多个并发用户的能力。

在下一节中，我们通过把 agent 部署到 Amazon Bedrock AgentCore Runtime 来解决这一点，把本地原型转变为具备 Amazon Bedrock AgentCore Observability 和自动扩展能力的生产就绪系统。

## 用 Amazon Bedrock AgentCore Runtime 部署到生产环境

工具实现集中化和安全化之后，最后一个主要障碍是生产部署。我们的 agent 目前运行在你的笔记本本地，这对实验很理想，但不适合真实客户。生产环境中需要可扩展的基础设施、全面的监控、自动的错误恢复，以及可靠地处理多个并发用户的能力。

Amazon Bedrock AgentCore Runtime 只需极少的代码改动，就能把你的本地 agent 转变为生产就绪的服务。结合 Amazon Bedrock AgentCore Observability，它提供了运维团队在生产中维护 agentic 应用所需的企业级可靠性、自动扩展和全面监控能力。

我们的架构将如下图所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/03/image-7-1.png)

### 面向生产的最小代码改动

转换你的本地 agent 只需添加四行代码：

```
# Your existing agent code remains unchanged
model = BedrockModel(model_id="us.anthropic.claude-3-7-sonnet-20250219-v1:0")
memory_hooks = CustomerSupportMemoryHooks(memory_id, memory_client, actor_id, session_id)
agent = Agent(
    model=model,
    tools=[get_return_policy, get_product_info],
    system_prompt=SYSTEM_PROMPT,
    hooks=[memory_hooks]
)

def invoke(payload):
    user_input = payload.get("prompt", "")
    response = agent(user_input)
    return response.message["content"][0]["text"]

if __name__ == "__main__":
```

`BedrockAgentCoreApp` 会自动创建一个带有必需 `/invocations` 和 `/ping` 端点的 HTTP 服务器，处理恰当的内容类型和响应格式，按照 AWS 标准管理错误处理，并在你的 agent 代码与 Amazon Bedrock AgentCore Runtime 之间提供基础设施桥梁。

### 安全的生产部署

生产部署需要恰当的身份认证和访问控制。Amazon Bedrock AgentCore Runtime 与 Amazon Bedrock AgentCore Identity 集成，以提供企业级安全。使用 [Bedrock AgentCore Starter Toolkit](https://github.com/aws/bedrock-agentcore-starter-toolkit)，我们可以通过三个简单步骤部署应用：配置、启动和调用。

在配置过程中，会生成一个 Docker file 来指导 agent 的部署。它包含 agent 及其依赖的信息、Amazon Bedrock AgentCore Identity 配置，以及要使用的 Amazon Bedrock AgentCore Observability 配置。在启动阶段，使用 [AWS CodeBuild](https://aws.amazon.com/codebuild) 运行该 Dockerfile，并创建一个 [Amazon Elastic Container Registry](https://aws.amazon.com/ecr/)（Amazon ECR）仓库来存储 agent 依赖。随后创建 Amazon Bedrock AgentCore Runtime agent，使用 ECR 仓库的镜像，并生成一个端点用于在应用中调用该 agent。如果你的 agent 像我们的一样，通过 Amazon Bedrock AgentCore Identity 配置了 OAuth 认证，那么在调用 agent 的步骤中还需要传入认证 token。下图展示了这一过程。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/03/image-9-1.png)

在 Amazon Bedrock AgentCore Runtime 上配置和启动 agent 的代码如下：

```
from bedrock_agentcore_starter_toolkit import Runtime

# Configure secure deployment with Cognito authentication
agentcore_runtime = Runtime()

response = agentcore_runtime.configure(
    entrypoint="lab_helpers/lab4_runtime.py",
    execution_role=execution_role_arn,
    auto_create_ecr=True,
    requirements_file="requirements.txt",
    region=region,
    agent_name="customer_support_agent",
    authorizer_configuration={
        "customJWTAuthorizer": {
            "allowedClients": [cognito_client_id],
            "discoveryUrl": cognito_discovery_url,
        }
    }
)

# Deploy to production
launch_result = agentcore_runtime.launch()
```

这个配置会创建一个安全端点，只接受来自你的身份提供方（如 Amazon Cognito、Okta 或 Entra）的有效 JWT token 请求。对于我们的 agent，我们使用 Amazon Cognito 的虚拟设置，但你的应用可以选择自己的身份提供方。部署过程会自动把 agent 构建为容器，创建必要的 AWS 基础设施，并建立监控和日志 pipeline。

### 会话管理与隔离

对 agent 来说，最关键的生产特性之一是恰当的会话管理。Amazon Bedrock AgentCore Runtime 自动处理会话隔离，确保不同客户的对话互不干扰：

```
# Customer 1 conversation
response1 = agentcore_runtime.invoke(
    {"prompt": "My iPhone Bluetooth isn't working. What should I do?"},
    bearer_token=auth_token,
    session_id="session-customer-1"
)

# Customer 1 follow-up (maintains context)
response2 = agentcore_runtime.invoke(
    {"prompt": "I've turned Bluetooth on and off but it still doesn't work"},
    bearer_token=auth_token,
    session_id="session-customer-1"  # Same session, context preserved
)

# Customer 2 conversation (completely separate)
response3 = agentcore_runtime.invoke(
    {"prompt": "Still not working. What is going on?"},
    bearer_token=auth_token,
    session_id="session-customer-2"  # Different session, no context
)
```

客户 1 的追问完整保留了关于其 iPhone 蓝牙问题的上下文，而客户 2 的消息（在另一个会话中）没有上下文，agent 会恰当地要求提供更多信息。这种自动的会话隔离对生产的客户支持场景至关重要。

### 使用 Amazon Bedrock AgentCore Observability 实现全面可观测性

生产环境的 agent 需要全面监控来诊断问题、优化性能并保持可靠性。Amazon Bedrock AgentCore Observability 自动为你的 agent 代码插桩，并把遥测数据发送到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch)，你可以在那里分析模式并实时排查问题。可观测性数据包含会话级跟踪，因此你可以追踪单个客户会话的交互，准确了解一次支持交互中发生了什么。你可以在 Amazon Bedrock AgentCore Runtime 中托管或不在其中托管的任意 agent 上使用 Amazon Bedrock AgentCore Observability。由于 Amazon Bedrock AgentCore Runtime 自动与 Amazon Bedrock AgentCore Observability 集成，我们无需额外工作即可观测 agent。

借助 Amazon Bedrock AgentCore Runtime 部署，你的 agent 已可在生产中使用。但我们仍有一个限制：agent 只能通过 SDK 或 API 调用访问，客户需要编写代码或使用技术工具才能与之交互。要实现真正面向客户的部署，我们需要一个客户可以通过浏览器访问的友好 Web 界面。

在下一节中，我们通过用 Streamlit 构建一个示例 Web 应用来演示完整旅程，提供一个可以与生产就绪的 Amazon Bedrock AgentCore Runtime 端点交互的直观聊天界面。所暴露的端点保持了我们在从概念验证到生产的整个旅程中构建的安全、可扩展和可观测能力。在真实场景中，你会把这个端点与现有的面向客户的应用和 UI 框架集成。

我们从原型到生产的旅程展示了 Amazon Bedrock AgentCore 服务如何应对部署企业级 agentic 应用的传统障碍。一个起初简单的本地客户支持 chatbot，转变为能够服务多个并发用户的完整生产级系统，具备持久记忆、安全的工具共享、全面的可观测性和直观的 Web 界面——而无需数月的定制基础设施开发。
