# 如何让 Amazon Finance 借助 AWS 上的生成式 AI 精简监管问询处理

Amazon 的财务技术（FinTech）团队为 Amazon 各团队构建并运营系统，用于在符合不同司法辖区要求的前提下管理监管问询。这些团队处理来自监管机构的监管问询，每一份问询在要求、文档格式和复杂程度上都各不相同。

处理这些监管问询涉及审阅文档、抽取相关信息、从 Amazon 基础设施内的多个系统检索支撑数据，并在监管时限内汇编回复。随着问询频率和业务复杂度上升，Amazon 需要一种更具扩展性的方法。

本文中，我们演示 Amazon FinTech 团队如何借助 [Amazon Bedrock](https://aws.amazon.com/bedrock/?nc2=type_a) 和其他 AWS 服务构建可扩展的 AI 应用，以改变监管问询的处理方式。使用该方案的每个团队都会创建并维护自己专属的知识库，其中填充该团队特有的文档与参考资料。

## **挑战**

监管问询管理工作的规模与复杂度带来了若干相互关联的挑战：

**知识碎片化与检索复杂度**

监管问询需要从成千上万份历史文档中综合信息。这些文档格式各异（PDF、PPT、Word、CSV），并包含领域专属术语。团队需要一种方法，能在这庞大的语料中快速定位相关先例与支撑信息，同时保持准确性和监管合规。

**对话上下文与状态管理**

监管问询需要多轮对话，早前交互的上下文对生成准确回复至关重要。跨会话维护对话状态，以及在团队成员通过迭代交互打磨答案时跟踪回复的演变，都带来了显著的复杂度。

**可观测性与持续改进**

对于生成式 AI 系统，理解某个回复为何被生成与回复本身同样重要。团队需要对检索过程、模型决策和用户交互拥有全面的可见性，以识别可改进之处并遵守负责任 AI 原则。例如，团队必须检测模型何时虚构了源文档中并不存在的信息，或捕捉系统何时检索到过时的合规指南——后者可能导致违反监管要求。随着模型、prompt 和文档语料的变化，AI 系统的准确度会随时间漂移，因此需要持续监控。

## **解决方案概览 **

为应对这些挑战，Amazon FinTech 团队构建了一套智能监管回复自动化系统，使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/)、[AWS Lambda](https://aws.amazon.com/lambda/) 和支持性的 AWS 服务。该方案用 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 与 [Amazon OpenSearch Serverless ](https://aws.amazon.com/opensearch-service/features/serverless/)实现[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）并进行向量存储，从而能从成千上万份历史文档中检索信息。由 [Claude Sonnet 4.5](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html) 通过 [Converse Stream API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ConverseStream.html) 驱动的实时聊天交互，结合 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 管理对话历史，提供具备上下文感知能力的多轮对话。通过 [OpenTelemetry](https://opentelemetry.io/) 与自托管 Langfuse 实现的全面可观测性，确保对 AI 系统性能的持续监控与改进。系统不缓存大语言模型（LLM）响应或中间结果，因为监管问询高度依赖上下文，缓存命中率往往很低。

## **知识库摄取流程**

知识库摄取流程提供一条自动化的文档处理 pipeline，在用户上传文档后启动。它的职责是把文档数据嵌入 [Amazon Bedrock Knowledge Base](https://aws.amazon.com/bedrock/knowledge-bases/)。流程如下：

你可以使用知识库摄取工作流批量上传文档，并通过自动化 pipeline 把它们转换为可检索的向量嵌入。以下详细流程在上图中有所体现。

- **用户上传文档**：用户通过客户端应用上传文档。
- **生成预签名 URL**：客户端应用向 [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 发送请求，后者调用知识库摄取的 AWS Lambda 函数，生成[预签名 S3 URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ShareObjectPreSignedURL.html)。
- **上传文档**：客户端应用使用生成的预签名 URL 上传文档。
- **触发摄取与数据处理**：文档成功上传到 Amazon Simple Storage Service（Amazon S3）后，客户端应用触发 Amazon API Gateway 启动文档处理的 AWS Lambda，后者负责格式转换并管理文档的并发摄取。我们无需预处理这些文档中的图像、图表和表格，因为 Amazon Bedrock Knowledge Base 配置了 Amazon Bedrock Data Automation（BDA），可以高效抽取这些多模态内容。随后 AWS Lambda 函数调用 [Amazon Bedrock Knowledge Bases](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent_StartIngestionJob.html)。
- **向量存储：**Amazon Bedrock Knowledge Base 使用[分层分块策略](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html)对文档内容分块，[使用 Amazon Titan Text Embeddings 生成嵌入](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html)，并把生成的向量存入 OpenSearch Serverless。分层分块会创建嵌套的父子关系，映射财务文档的分节结构。该策略很适合结构化且复杂的文档，因为它索引小块以实现精确检索，同时返回较大的父块，为连贯的回复提供足够的上下文。

构建自动化摄取 pipeline 解决了知识碎片化这一核心挑战：它高效处理多种格式的成千上万份历史文档，同时优化内容索引以产生相关的 AI 回复。这种并行化方法使系统能够有效扩展，适应逐年增长的监管问询活动量，并在大文档量下保持一致的处理性能。

## **聊天应用 **

聊天应用提供由 AWS 无服务器架构驱动的实时对话界面，支持与系统进行自然语言交互。我们选择把响应以流式方式发给用户，让他们能更早开始阅读 AI 回复，该能力通过 WebSocket 连接实现。借助这些 WebSocket 连接与 Claude Sonnet 4.5 模型，它在 DynamoDB 中维护对话状态的同时交付与上下文相关的回复。工作流运行如下：

- **发起聊天会话：**用户通过客户端应用发起或打开已有聊天会话。
- **WebSocket 连接**：应用使用 WebSocket 与 Amazon API Gateway 建立持久的双向连接。
- **提交消息**：应用通过 WebSocket 连接提交用户问题，消息被传递到 Chat service 的 AWS Lambda 函数。
- **查询增强**：Chat Service 的 AWS Lambda 函数使用 [Claude 3.5 Haiku](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html) 模型，配合[查询扩展策略](https://arxiv.org/html/2407.12325v1)生成用户问题的多个变体。
- **知识检索**：Chat Service Lambda 针对每个扩展后的查询调用 [Amazon Bedrock Knowledge Bases Retrieve API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_Retrieve.html)。该 API 对底层 OpenSearch Serverless 索引执行向量相似度检索，返回最相关的文档块及其来源元数据和相关性分数。
- **上下文组装**：Chat Service 的 AWS Lambda 函数从 Amazon DynamoDB 取出对话历史（对已有对话，按该具体对话 ID 取回），并与检索到的知识库结果及用户问题合并。
- **生成回复**：Chat Service 的 AWS Lambda 函数使用 Converse Stream API 配合 Claude Sonnet 4.5 和回复生成 prompt，基于组装好的上下文产出与上下文相关的答案。
- **用户交互：**Chat Service 的 AWS Lambda 函数通过 WebSocket 连接把生成的响应以 [Markdown 格式](https://medium.com/@bingzead/why-ai-prefers-markdown-the-logic-behind-this-format-revolution-237675f33a8b)流式返回给客户端应用，并把整段对话存入 Amazon DynamoDb 的 Conversational History Table。
- **可观测性**：在整个流程中，Chat Service 使用 [OpenTelemetry（OTEL）SDK](https://opentelemetry.io/) 把端到端 trace 发布到自托管的 Langfuse 实例。由此捕获详细的遥测数据，包括延迟指标、token 用量、prompt 模板和模型响应。

## **多轮对话体验**

监管问询讨论往往要经过多轮交流，团队在过程中打磨回复并引用更多数据源。为支持这一迭代过程，Amazon FinTech 团队使用 Amazon API Gateway（WebSocket API）、AWS Lambda 和 Amazon DynamoDB 实现了多轮对话工作流，并与 Amazon Bedrock ConverseStream API 集成，以实现低延迟、上下文感知的对话。每个聊天会话通过 Amazon Cognito 安全认证，并被分配唯一的对话 ID。DynamoDB 按时间顺序存储消息，以跨会话保留上下文，因此用户可以无缝续接此前的讨论并保持连贯性。

用户提交查询时，系统会对输入做净化处理，以防止 prompt 注入攻击。净化之后，系统对意图进行分类，并判断是否需要从 Amazon Bedrock Knowledge Base 检索。该判断通过一次 LLM 调用完成，把用户查询归类为对话型或知识密集型。对于复杂的知识密集型问题，工作流采用查询扩展策略，以应对用户大量使用缩略词和简写提问的普遍情况。该层使用 Claude 3.5 Haiku 生成最多五个查询变体，随后并行向 Knowledge Base 发起 Retrieve API 调用，通过 OpenSearch 向量相似度检索取回相关结果。为在大规模下保持性能，工作流使用多线程对这些检索调用做并行处理。该优化把检索延迟从 10 秒（顺序处理）降到 2 秒以内，从而使对话保持响应性。检索到的信息——结合最近的对话历史——通过 ConverseStream API 传给 Claude Sonnet 4.5，并辅以 [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-components.html)，后者实现[敏感信息过滤器](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-sensitive-filters.html)，可自动检测并从输入和输出中移除 PII 与财务数据。这对保护监管文档至关重要。当检测到 prompt 注入尝试时，系统会回复 “Sorry, the model cannot answer that question,”，在保持对话流畅性的同时维护安全合规的交互。

该架构带来连续性、透明度与可扩展性。用户在检索与生成阶段都能收到实时的流式响应和状态更新，从而提升参与度并降低延迟。DynamoDB 中的持久化日志为合规审查提供不可篡改的审计轨迹，而无服务器、事件驱动的设计可自动扩展以支持并发会话。这些能力共同让 Amazon FinTech 团队能够进行复杂、迭代的对话——产出由 Amazon Bedrock 驱动、与上下文相关、安全且符合监管要求的回复。

## **可观测性**

可观测性在理解并改进 AI 驱动的工作流方面起着关键作用。为了对监管问询回复系统实现完整可见性，Chat Service 的 AWS Lambda 把 OpenTelemetry（OTEL）与自托管 Langfuse 实例集成，捕获每次交互的详细端到端 trace。这套设置让工程师和应用科学家获得关于 prompt 如何被处理、知识如何被检索、回复如何被生成的细粒度遥测。这使系统性能与准确度得以近乎持续地改进。选择 OTEL 而非 Langfuse 原生 SDK，带来了厂商中立的灵活性，使遥测数据可以路由到多个可观测性后端，并适应不断变化的监控需求。

在运行时，Chat Service AWS Lambda 的每个阶段都使用 [OTEL Java SDK ](https://opentelemetry.io/docs/languages/java/)手工插桩，按照 [OTEL Generative AI 语义标准](https://opentelemetry.io/docs/specs/semconv/gen-ai/)记录延迟、token 用量、模型决策和 prompt 元数据。[Span](https://langfuse.com/docs/observability/data-model) 近实时发布到 Langfuse，让团队透明地看到 Amazon Bedrock ConverseStream API、Knowledge Base 检索与 Claude Sonnet 4.5 在单个请求内如何交互。详细的遥测使团队能够识别性能瓶颈、优化 prompt 策略并提升检索精度，同时保持负责任的 AI 实践。

这套可观测性框架维护了对系统行为的信任与问责。工程师可以把用户操作与模型结果关联起来，跨多个服务追踪数据血缘，并在不中断运营的情况下微调配置。通过把 OpenTelemetry 的互操作性与 Langfuse 的可视化和分析能力结合起来，Amazon FinTech 团队获得了可扩展、可延伸的基础，用于大规模评估生成式 AI 系统——把每次交互转化为可用于持续改进的洞察。

## **结论**

本文中，你看到了 Amazon FinTech 团队如何使用 Amazon Bedrock 构建可扩展的 AI 方案，通过自动化知识检索、对话工作流和回复生成来支撑监管问询。通过把文档摄取 pipeline、多轮有状态对话，以及经 OpenTelemetry 与 Langfuse 实现的详细可观测性结合起来，该架构让团队能够以受治理、可追溯且合规的方式处理监管问询。

由于整个技术栈构建在 AWS 无服务器服务之上，它提供了企业级部署所需的运维可扩展性、安全性和弹性。无论你面对的是法律合规、监管问询，还是高并发的内部知识工作流，这一模式都提供了可以按业务领域裁剪和扩展的实用基础。

如果你已准备好用生成式 AI 现代化你的知识密集型流程，请浏览 [Amazon Bedrock 文档](https://aws.amazon.com/bedrock/)，了解如何开始构建你自己的安全、受治理且可扩展的 AI 驱动工作流。
