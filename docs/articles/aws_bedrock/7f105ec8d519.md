# Infosys Topaz 如何借助 Amazon Bedrock 改造技术帮助台运营

如今，AI 驱动的应用与 AI 驱动的服务交付是企业市场的关键差异化因素。基于生成式 AI 的资源可以大幅缩短新员工的上手时间、增强企业搜索、协助起草内容、检查合规性、理解数据的法律表述，等等。

[生成式 AI](https://aws.amazon.com/generative-ai/) 应用在企业领域的客户关怀中心、客户关系管理中心和帮助台中，是新兴且备受追捧的解决方案。

[Infosys Topaz](https://www.infosys.com/services/data-ai-topaz.html) 是一项以 AI 为先的服务，帮助企业在使用生成式 AI 的过程中加速实现业务价值；它正在集成 AWS 的生成式 AI 能力，让包括 [Infosys Cortex](https://www.infosys.com/products-and-platforms/cortex.html)、[Infosys Personalized Smart Video](https://www.infosys.com/services/incubating-emerging-technologies/offerings/personalized-smart-video.html)（PSV）、Infosys Conversational AI Suite、[Infosys Live Enterprise Automation Platform (LEAP)](https://www.infosys.com/services/application-development-maintenance/service-offerings/application-management-platform.html) 和 [Infosys Cyber Next](https://www.infosys.com/services/cyber-security/offerings/platform-powered-services.html) 在内的企业 AI 解决方案具备面向未来的能力。

本文考察一家大型能源供应商的用例：该公司的技术帮助台支持人员负责接听客户电话，并为现场的电表技师提供支持。我们使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/)，并结合 Infosys Topaz 的能力，构建了一个生成式 AI 应用，可缩短通话处理时长、自动化任务，并提升技术支持的总体质量。

## 业务挑战

电表技师会前往客户现场安装、更换、维护和修理电表。有时他们会致电技术帮助台的支持人员，寻求指导与支持，以解决自己无法处理的问题。这类通话每周约 5,000 次，每月约 20,000 次。

支持人员和电表技师面临的部分挑战包括：

- 找到恰当的信息或资源，以有效回应问询或关切。
- 这些通话的平均处理时长视问题类别而不同，但在占通话总量 60% 以上的前 10 大类别中，通话时长均超过 5 分钟。
- 60–70% 的问题属于重复性问题，其余为新问题。

维持足够的人力以提供及时响应，成本可能很高。增聘支持人员并培训其掌握提供支持所需的知识，既昂贵又难以扩展。我们构建了一个 AI 驱动的技术帮助台，可以近实时地摄取历史通话记录和新的通话记录。这有助于支持人员基于过往通话给出解决方案，从而减少手工检索时间，让他们能处理其他优先事项。

## 解决方案概览

该方案通过摄取和处理通话记录来创建知识库，使 AI assistant 能够基于历史给出解决方案。AI 驱动的技术帮助台带来的收益包括：

- 提供全天候可用性
- 为帮助台人员节省精力
- 让企业得以专注于新问题
- 减少等待时间、缩短通话时长
- 依据帮助台人员对问题的分析，自动执行他们在后台采取的操作
- 提升技术帮助台响应的质量，进而改善沟通与结果

本文展示实现细节，包括基于用户的访问控制、用于高效检索和更新 FAQ 的缓存机制、用户指标跟踪，以及具备时间跟踪能力的响应生成。

## 构建知识库：数据流

技术帮助台的通话会被录制下来，用于质量与分析目的，通话记录以 JSON 格式存储在 [AWS Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 存储桶中。

这些对话会被解析成 CSV 文件以便排序，然后使用诸如 Amazon Bedrock 上 [Anthropic 的 Claude Sonnet](https://aws.amazon.com/bedrock/claude/) 这样的大语言模型（LLM），依据通话时长、指示相关上下文的关键词等，对对话进行摘要，并判断其上下文是否包含有用信息。

入选的对话会被切分为若干块，生成嵌入向量（embedding）并存入 [Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/) 向量存储。被判定为无关的对话则放入另一个 S3 存储桶以备后续参考。该过程是自动化的，如下图所示。

![流程](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/04/image-2-2.png)

随后在知识库之上构建了一个虚拟 assistant，用来协助支持人员。

对话会被解析成 CSV 文件以便简单排序，并使用诸如 Amazon Bedrock 上 [Anthropic 的 Claude Sonnet](https://aws.amazon.com/bedrock/claude/) 的 LLM 对对话进行摘要，依据通话时长、指示相关上下文的关键词等，判断其上下文是否包含有用信息。

当新的通话记录被载入 S3 存储桶时，会触发一个[事件驱动](https://docs.aws.amazon.com/lambda/latest/operatorguide/event-driven-architectures.html)的 [AWS Lambda](https://aws.amazon.com/lambda) 函数。由此再触发一个 Step Functions 工作流。

从通话记录的原始 CSV 文件中，只抽取少量字段：某个 contact ID（客户与支持人员之间某次通话会话的唯一标识）、标明说话人的 `participant` 列（说话人可以是支持人员，也可以是客户），以及作为对话内容的 `content` 列。

为构建知识库，我们使用 Step Functions 摄取原始 CSV 文件，如下图所示的工作流。

![构建知识库](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/04/image-3-1.png)

当用户把 JSON 文件上传到 S3 存储桶时，这个自动化工作流就会启动。

- Step Functions 工作流通过一个 Lambda 函数获取这些 CSV 通话记录的 Amazon S3 URL。`contactid` 对于客户与 agent（即参与者）之间的某次通话会话是唯一的，而 `content` 是实际的对话内容。
- 该 Lambda 函数（Parse Transcripts from CSV）使用这个 Amazon S3 URL 下载 CSV 文件，并用 Pandas 把 CSV 预处理成只含 contact ID 与通话记录的形式。相同 contact ID 的对话会被拼接为一行。
- 第二步是分类任务，负责摄取、分类并保留或丢弃对话。对话会传入 map state。在 map state 中，对话被并发处理。对于每一行对话，该状态会触发另一个 Lambda 函数（Check for Irrelevant Conversations）的并发执行，把每条对话分类为相关或无关。在这个分类任务中，Lambda 函数使用 Amazon Bedrock 上的 Anthropic Claude Sonnet 模型。它采用零样本思维链（zero-shot chain-of-thought）提示，先对对话做摘要，再判定相关性。如果对话因信号干扰或其他原因而中断、不连贯，或者没有有意义的上下文（即 agent 无法给出解决方案），就会被判为无关。
- 最后，map state 会把每条对话实例（已分类为相关或无关）传给 choice state，由后者把无关对话记录到 S3 存储桶，相关对话则传给另一个 Lambda 函数（Handle Relevant Conversations）进一步处理。
- 最后一个 Lambda 函数（Log Irrelevant Conversations）读取相关对话，并使用 Anthropic 的 Claude Sonnet 生成摘要、问题与解决步骤。生成的摘要用于创建摘要嵌入向量。

## 构建高效的 RAG pipeline

检索系统的成效取决于有效的嵌入模型。[Amazon Titan Text Embeddings](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-titan-embed-text.html) 模型针对文本检索做了优化，可支撑检索增强生成（RAG）。我们没有同时处理海量文档，而是采用切分策略来提升检索效果。我们使用 1,000 的 chunk 大小，配合 150–200 的重叠窗口，以获得最佳结果。把切分与页边界结合，是一种简单却非常有效的做法。句子窗口检索同样能得到准确的结果。

提示技巧对获得有效结果至关重要。例如，与其用“guidelines for smart meter installation”，不如使用扩展后的 prompt ：“instructions, procedures, regulations, and best practices along with agent experiences for installation of a smart meter”，效果会更好。

构建生产可用的 RAG 应用还需要一个高性能的向量数据库。[vector engine for OpenSearch Serverless](https://aws.amazon.com/opensearch-service/serverless-vector-engine) 提供可扩展、高性能的向量存储与检索能力；关键特性包括近实时地新增、更新和删除向量嵌入，且不影响查询性能。更多信息请参阅 [Build a contextual chatbot application using Amazon Bedrock Knowledge Bases](https://aws.amazon.com/blogs/machine-learning/build-a-contextual-chatbot-application-using-knowledge-bases-for-amazon-bedrock/)。

## 安全考量

该架构在各组件上实施了全面的安全措施。我们使用 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 安全存储和管理敏感凭证、API key 与数据库密码，并配置了自动轮换策略。S3 存储桶使用 [AWS Key Management Service](https://aws.amazon.com/kms)（AWS KMS）配合 AES-256 加密，并启用版本控制以满足审计需要。个人身份信息（PII）受到极为谨慎的处理——PII 数据会加密，访问权限通过 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）策略和 AWS KMS 严格管控。在 OpenSearch Serverless 实现中，我们确保数据既通过 AWS KMS 加密静态存储，也通过 TLS 1.2 加密传输。会话管理包含非活动会话超时，需要重新认证才能继续访问。系统通过一层安全中间件与存储在 DynamoDB 中的访问控制列表（ACL）数据交互，该 DynamoDB 表使用 AWS 托管 KMS 密钥进行静态加密。服务间的数据传输通过 TLS 1.2 加密，我们在整个基础设施范围内维持端到端加密。访问控制按细粒度定义，并通过 [AWS CloudTrail](https://aws.amazon.com/cloudtrail) 定期审计。

## **实施基于角色的访问控制**

我们使用三种不同的角色来实现基于角色的访问控制：拥有完全访问权限的管理员、具备中等访问权限的技术台分析师，以及访问权限最小的技术 agent。我们使用 OpenSearch Serverless collection 来管理不同的访问级别。不同的通话记录会被摄取到不同的 collection 中，目的是让用户按自己的角色访问被授权的内容。用户 ID 及其角色、允许的访问范围列表，会连同 OpenSearch collection 和索引名称一起存储在 DynamoDB 表中。

我们在 [Streamlit](https://streamlit.io/generative-ai) authenticator 中使用 `authenticate.login` 方法来获取用户 ID。

## 缓存管理

我们在 Streamlit 中使用 `st.cache_data()` 函数把有效结果存到内存中。结果会在用户会话之间保持。

该缓存函数采用内部哈希机制，必要时可以覆盖。缓存数据既可以存放在内存中，也可以存放在磁盘上。此外，我们可以按用例需要设置数据持久化的时长。缓存失效或更新可以在数据变化时进行，也可以每小时执行一次。这一点结合 FAQ 区块，显著提升了技术帮助台的性能，带来更快的响应时间，也改善了客户与支持人员的体验。
