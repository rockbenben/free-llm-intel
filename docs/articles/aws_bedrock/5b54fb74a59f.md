# 在 EKS 上使用 Ray Train DLC 和 EFA 进行分布式训练

通常阻止 [PyTorch](https://pytorch.org/) 训练扩展到集群的是容器，而不是模型代码。每个容器都需要相同的 [CUDA 运行时](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html)、针对其编译的 PyTorch 构建、[NCCL](https://developer.nvidia.com/nccl) (NVIDIA Collective Communications Library)、[Elastic Fabric Adapter (EFA)](https://aws.amazon.com/hpc/efa/) 用户空间库、将 NCCL 连接到 EFA 的 [AWS OFI NCCL](https://github.com/aws/aws-ofi-nccl) 插件，以及集群运营商同意的 [Ray](https://docs.ray.io/en/latest/) 版本。构建该图像并在每次其中一个块移动时重建它本身就是一个项目，它与您打算训练的模型无关。 [Ray Train 深度学习容器](https://aws.github.io/deep-learning-containers/ray-train/) (DLC) 就是由 AWS 构建的镜像。 AWS 组装该堆栈，将其作为一个单元进行测试，将其发布在 Amazon Elastic Container Registry (Amazon ECR) Public 中并对其进行修补。

![EKS 集群，其中一个运行 KubeRay 和 Ray head 的 CPU 系统节点，以及两个支持 EFA 的 g6.12xlarge GPU 工作节点在一个可用性中区域](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/19/ML-22002-1-1.png)

图 1：一个 EKS 集群，其控制平面由 AWS 管理，一个运行 KubeRay Operator 和 Ray head 的 CPU 系统节点 (m7i.xlarge)，以及一个可用区中的两个支持 EFA 的 g6.12xlarge 节点。 KubeRay 从一个 RayCluster 清单构建它，Ray Train 放置 8 个工作线程，每个 GPU 一个，并且节点间集体跨越 EFA。

Ray 将作业作为具有两个角色的单个集群跨机器运行。 Ray 头协调并运行跟踪集群状态的全局控制存储、仪表板和您向其提交作业的作业服务器。 Ray 工作节点提供 GPU 并运行训练过程。每个工作进程在启动时都通过连接到头的地址来加入集群。在 Kubernetes 上，每个都是一个 pod。 Kubernetes 没有 Ray 集群的内置概念，因此必须创建头 Pod 和工作 Pod，在每个 Pod 中以正确的角色启动 Ray，将工作节点指向头，并替换失败的 Pod。 [KubeRay](https://aws.github.io/deep-learning-containers/ray-train/deployment/eks/) 就是这样做的。它是一个开源 Kubernetes 操作器，添加了 RayCluster 资源：您在一个清单中描述一个头组和一个工作组，KubeRay 从中构建和维护集群。

无论 KubeRay 在 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/) 上启动还是您自己在 Amazon Elastic Compute Cloud (Amazon EC2) 上启动，单个标记的映像都会作为 Ray head 和 Ray Worker 运行。您添加的是配置：哪些实例、每个 Pod 获得多少个 GPU、NCCL 使用哪种网络传输以及作业需要哪些额外的 Python 包。所有这一切都是从图像外部设置的。

本文将介绍一个示例，该示例使用与发布的完全相同的 DLC，通过 PyTorch 全分片数据并行 (FSDP) 在两个 g6.12xlarge 实例上的 8 个 NVIDIA L4 GPU 上微调 Qwen2.5-1.5B。训练代码是一个函数，集群是一个 RayCluster 清单加上一个变量文件，并且在任何时候都不会构建图像。由于 DLC 已经承载 EFA 堆栈，因此只要 Pod 请求，两个实例之间的集合就会通过 [EFA](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html) 运行。整个解决方案都在这个[示例存储库](https://github.com/aws-samples/sample-aws-deep-learning-containers/tree/main/training/ray-train)中，它使用与我们的[多节点 Ray Serve] 相同的 `KubeRay-on-EKS` 基础演练](https://aws.amazon.com/blogs/machine-learning/run-multi-node-inference-workloads-using-ray-llm-deep-learning-containers/)。

## 不构建任何东西你会得到什么

Ray Train DLC 是 PyTorch 训练映像，顶部有 Ray 的训练库。此示例提取的标签“public.ecr.aws/deep-learning-containers/ray:train-ml-cuda-v1.1”替换了原本如下所示的构建：

| **层** | **否则您将构建并保持一致的内容** | **在射线列车 DLC 中** |
| ---| ---| ---|
|分布式运行时 | Ray 带有仪表板和作业服务器，KubeRay 支持的版本 | Ray 2.58.0 与训练、调整和数据 |
|框架|为您的 CUDA 版本编译的 PyTorch | PyTorch 2.13.0、torchvision 0.28.0 |
| GPU 运行时 | CUDA、cuDNN 和 NCCL 版本相互一致 | CUDA 13.0.2、cuDNN、NCCL 2.29.7 |
|网络| EFA 安装程序、libfabric 和“aws-ofi-nccl”，针对 NCCL 构建 | EFA 最新、AWS OFI NCCL 插件、GDRCopy |
|培训图书馆|为您的 CUDA 编译的 DeepSpeed、flash-attn 和 Transformer Engine | DeepSpeed、flash-attn、Transformer Engine、PyTorch Lightning、Hugging Face 库 |
|诊断 |从源代码构建的 NCCL 测试 | `all_reduce_perf` 已在路径上 |

网络行是大多数团队最不希望拥有的行。不匹配不会产生错误。 NCCL 下降到 TCP 套接字，作业以一小部分速度运行完成。在 DLC 中，这些库是一起构建和测试的，AWS 在多节点 EFA 和多节点 KubeRay 训练测试上对每个版本进行控制，这正是该示例使用的路径。

还有一些属性可以消除您原本需要为每个集群执行的工作：

- **没有注册表设置 –** 镜像是公共的，因此节点无需凭据即可拉取它，并且不会在途中构建或推送任何内容。
- **没有驱动程序匹配 –** 启动时，入口点会检查主机的 NVIDIA 驱动程序，如果它比映像的 CUDA 旧，则会自动打开捆绑的 CUDA 前向兼容性库。
- **没有头部与工人的图像 –** 该图像没有固定的角色。无论容器启动什么，都会提供“ray start”命令，因此一个标签为每个 Pod 提供服务。
- **没有单独的推理图像系列 –** Ray Train 与 [Ray Serve DLC](https://aws.github.io/deep-learning-containers/ray/) 和 [Ray LLM DLC](https://aws.github.io/deep-learning-containers/ray-llm/) 共享“ray” ECR 存储库，位于“train-ml”标签前缀下。

## 配置它，不要重建它

一项训练工作与另一项训练工作之间的所有差异都是围绕图像设置的。该示例使用以下每种机制：

| **你控制什么** | **如何设置** | **在此示例中** |
| ---| ---| ---|
|主管或工人角色 |每个 Pod 组的 KubeRay `rayStartParams`两者的“DLC_IMAGE”相同。 Head 以 `num-gpus: "0"` 运行 |
|每个 Pod 的 GPU 和 EFA | Kubernetes 资源请求 | `nvidia.com/gpu: 4`, `vpc.amazonaws.com/efa: 1` |
|网络传输| Pod 或作业上的环境变量 | `FI_PROVIDER`、`NCCL_NET_PLUGIN`、`NCCL_SOCKET_IFNAME`、`NCCL_DEBUG` |
|额外的 Python 包 |提交时的 Ray `runtime_env` |作业需要的任何包，在提交时安装 |
|图片版| `DLC_IMAGE` 中的版本化或摘要固定标签 | `train-ml-cuda-v1.1` |
|簇状 | scripts/`env.sh` 中的变量 |实例类型、节点数量、每个节点的 GPU、区域、可用区 |
|培训工作| `train.py` 的参数 |模型、步骤、序列长度、批量大小 |

**每个作业的包。** 该图像附带了 HuggingFace 训练堆栈，因此此示例的作业不需要添加任何内容。当实验确实需要图像未携带的库时，Ray 在提交时通过“runtime_env”为该作业安装它，并且图像保持不变。没有新图像，没有新标签。

**每个作业的传输。** 映像默认为“FI_PROVIDER=efa”，其 NCCL 配置不包括环回和 Docker 桥接口。在 EKS 上，您将“NCCL_SOCKET_IFNAME”指向 pod 的“eth0”。无论如何，该示例都会在清单中设置所有四个网络变量，因此该行为在一个文件中可见，并且不依赖于图像默认值。因为这些是普通的环境变量，所以单个作业可以通过其“runtime_env”覆盖它们。

**您选择的版本。** 示例固定当前次要版本“train-ml-cuda-v1.1”，因此集群可以从一次运行复制到下一次运行。 “vX.Y”标签随着安全重建而移动。完全限定的“vX.Y.Z”标签在原始版本构建中保持冻结状态，因此当您需要字节相同的运行时固定摘要。私有 ECR URI 也提供相同的图像。

图 2：样本的集群。每个 Pod 都运行来自 Amazon ECR Public 的相同 Ray Train DLC。 CPU系统节点运行KubeRay算子和没有GPU的Ray头。每个启用 EFA 的 g6.12xlarge（均位于一个可用区）运行一个四 GPU Ray 工作容器。

所有节点都位于一个虚拟私有云 (VPC) 的私有子网中，仅通过 NAT 网关访问互联网，这就是每个节点从 Amazon ECR Public 提取 DLC 以及工作人员从 Hugging Face 下载模型权重的方式。一个 m7i.xlarge 形成系统节点组，托管 kube-system 附加组件、KubeRay 运算符和 Ray head。头部在端口 8265 上运行作业服务器，在端口 6379 上运行 Ray 的控制存储，并且它不通告 GPU，因此不会有任何训练工作落在其上。作业是通过 EKS API 使用“kubectl exec”从 head pod 内部提交的，因此端口 8265 永远不会暴露在集群外部。

训练在两个 [g6.12xlarge](https://aws.amazon.com/ec2/instance-types/g6/) 实例上运行，每个实例配备 4 个 NVIDIA L4 GPU、48 个 vCPU、192 GiB 内存、40 Gbps 网络和 1 个 EFA 接口。每个 Pod 都运行一个 Ray Worker pod，该 Pod 占用所有四个 GPU 和 EFA 接口，Ray Train 在每个 Pod 中放置四个工作器：在一个实例上排名 0-3，在另一个实例上排名 4-7。由于 EFA 流量不会跨可用区，因此脚本将两个实例放置在一个已检查提供 g6.12xlarge 的区域中。

## Ray Train 在容器内做什么

DLC 提供堆栈。 [Ray Train](https://docs.ray.io/en/latest/train/train.html) 提供了原本是启动器代码的部分。多节点 PyTorch 通常意味着在每台主​​机上为每个 GPU 启动一个进程，并为每个进程提供其等级、世界大小和集合地址。使用 Ray Train，您可以将训练循环编写为函数，并使用“ScalingConfig”将其传递给“TorchTrainer”。无论集群有 GPU，Ray 都会为每个 GPU 启动一个工作线程，形成“torch.distributed”进程组，并在每个工作线程上运行您的函数。

此示例向 Ray Train 请求 [FSDP](https://docs.pytorch.org/docs/stable/fsdp.html)，它将模型的权重、梯度和优化器状态拆分到所有八个 GPU 上，而不是将它们复制到每个 GPU 上。 bfloat16 中的 Qwen2.5-1.5B 需要大约 12 GB 用于这四个张量。每个 L4 GPU 分为八种方式，可容纳大约 1.5 GB。代价是沟通：FSDP 在使用前收集每一层的权重，然后减少分散梯度，因此整个模型在每一步都会在不同的等级之间交叉。在两个实例之间，该流量是 DLC 的 EFA 堆栈承载的流量。

## 训练代码：一个函数和一个训练器

`code/train.py` 是整个工作，它不包含任何特定于容器、集群或网络的内容。 Ray 在每个 GPU 上运行一次“train_func”。它询问 Ray 的等级，加载模型，将其交给 FSDP 的“prepare_model”，并运行一个普通的 PyTorch 循环：

**`code/train.py` — 每个 GPU 函数（删节）**
```
def train_func(config):
    ctx = ray.train.get_context()
    world_size, rank = ctx.get_world_size(), ctx.get_world_rank()
    device = ray.train.torch.get_device()

    model = AutoModelForCausalLM.from_pretrained(config["model_id"], torch_dtype=torch.bfloat16)

    # Any submodule above 10M parameters becomes its own FSDP unit. Wrapping by
    # size, not by a model-specific layer class, keeps the script model-agnostic.
    auto_wrap_policy = partial(size_based_auto_wrap_policy, min_num_params=int(1e7))
    model = ray.train.torch.prepare_model(
        model,
        parallel_strategy="fsdp",
        parallel_strategy_kwargs={"auto_wrap_policy": auto_wrap_policy},
    )
    optimizer = torch.optim.AdamW(model.parameters(), lr=config["learning_rate"])

    for step in range(config["steps"]):
        input_ids = torch.randint(0, model.config.vocab_size,
            (config["batch_size"], config["seq_len"]), device=device)
        optimizer.zero_grad()
        loss = model(input_ids=input_ids, labels=input_ids).loss
        loss.backward()  # parameters gathered again, gradients reduce-scattered
        optimizer.step()  # local: each rank updates only its own slice
        ray.train.report({"step": step, "loss": loss.item()})
```
驱动程序加入正在运行的集群，计算其 GPU 数量并启动训练器。由于工作线程计数来自集群，因此相同的脚本在一个或多个节点上运行不变：

**`code/train.py` — 驱动程序（删节）**
```
ray.init(address="auto")  # join the RayCluster
num_workers = int(ray.cluster_resources().get("GPU", 0))  # 8 here

trainer = TorchTrainer(
    train_func,
    train_loop_config={...},
    scaling_config=ScalingConfig(num_workers=num_workers, use_gpu=True),
    run_config=RunConfig(name="ray-train-fsdp-llm"),
)
result = trainer.fit()
```
这些批次是随机令牌 ID，因此运行只依赖于集群。该样本根据真实的 FSDP 集体是否跨越两个节点以及作业是否完成来进行判断。要进行真正的微调，请用 Ray Data 或 DataLoader 管道替换随机张量。函数中的其他内容没有变化。

## 清单：配置 DLC 的唯一位置

`manifest/raycluster.yaml` 是图像与集群相遇的地方，它很短，因为图像需要的东西很少。 head 唯一的特殊设置是“NVIDIA_VISIBLE_DEVICES=void”，它可以阻止容器运行时的 NVIDIA 挂钩在没有 GPU 的节点上失败。工人团体拥有其他一切：

**`manifest/raycluster.yaml` — 工作组（删节）**
```
workerGroupSpecs:
  - groupName: gpu-workers
    replicas: 2
    rayStartParams:
      num-gpus: "${GPUS_PER_NODE}"  # keeps Ray's GPU count equal to the pod's
    template:
      spec:
        nodeSelector: { role: gpu-worker }
        containers:
          - name: ray-worker
            image: "${DLC_IMAGE}"  # the DLC as published; same tag as the head
            env:
              - { name: NCCL_DEBUG, value: "INFO" }  # print the chosen transport
              - { name: NCCL_SOCKET_IFNAME, value: "eth0" }  # pod network on EKS
              - { name: FI_PROVIDER, value: "efa" }  # libfabric: EFA, nothing else
              - { name: NCCL_NET_PLUGIN, value: "ofi" }  # load the AWS OFI plugin
            resources:
              limits: { nvidia.com/gpu: "${GPUS_PER_NODE}", vpc.amazonaws.com/efa: "1",
                cpu: "40", memory: 160Gi }
              requests: { nvidia.com/gpu: "${GPUS_PER_NODE}", vpc.amazonaws.com/efa: "1",
                cpu: "40", memory: 160Gi }
```
将其解读为三个决定。

**哪个图像：** `${DLC_IMAGE}`，未修改，适用于头部和工人。

**哪些硬件：** 每个 Pod 有四个 GPU 和节点的单个 EFA 接口。请求“vpc.amazonaws.com/efa”使 EFA 设备插件将接口挂载到容器中。如果没有它，NCCL 将无法看到 EFA 并退回到套接字。

**哪种传输：** 四个环境变量，因此无需自动检测。

两个较小的细节可以保持多节点作业的稳定。首先，请求应该等于限制，这将工作人员置于 Kubernetes 的保证服务质量 (QoS) 类别中。这很重要，因为单个被限制或驱逐的排名会阻碍其他七个排名。其次，“num-gpus”源自与 GPU 请求相同的变量，因此 Ray 的容量视图始终与 Kubernetes 相匹配。

## 提出来：基础设施的一个命令，然后是工作

配置位于一处“scripts/env.sh”：集群名称、区域、Kubernetes 版本、节点类型和计数、镜像、KubeRay 和两个设备插件的固定版本以及训练参数。导出其中任何一个以更改它以进行运行。所有五个脚本都是幂等的并且可以安全地重新运行。在创建或接触集群资源之前，会分别提示“deploy_cluster.sh”、“deploy_node_group.sh”和“deploy_ray_train_job.sh”。 `install_gpu_plugins.sh` 和 `install_kuberay.sh` 是协调器并直接运行。
```
cd training/ray-train/scripts
source ./env.sh
```
`./deploy_all.sh` – 查找容量的实际位置，然后在那里构建基础设施。

g6.12xlarge 容量每天在区域和可用区之间变化，因此这是起点，而不是在“env.sh”中预先猜测的区域。它首先运行“find_gpu_capacity.sh”，检查每个候选区域：每个可用区是否提供 g6.12xlarge、账户的按需 G/VT 系列 vCPU 配额是否有空间容纳请求的节点数，以及作为容量信号的 EC2 Spot 放置分数。使用“deploy_all.sh”默认传递的“--probe”，它通过在每个候选区域中创建并立即取消实际的容量预留来获得明确的答案。然后它会显示计划并询问一次：
```
Proceed with the whole chain without further prompts? (y/N):
```
回答 **y** 按顺序运行推荐区域中的 `deploy_cluster.sh`、`deploy_node_group.sh`、`install_gpu_plugins.sh` 和 `install_kuberay.sh`，每个都跳过自己的重复确认，因为这已经询问过（`-y` 也会跳过此提示，而 `--plan` 显示计划而不创建任何内容）。如果 GPU 节点组无法在最佳区域中启动，脚本会将其删除并尝试探测确认的下一个区域。 `GPU_AZ` 也会针对集群的实际私有子网进行交叉检查，不仅是在提供 g6.12xlarge 的情况下，因此 GPU 节点组最终不能固定到集群没有子网的可用区。所选区域和区域将保存到 `scripts/.placement.env`，每个其他脚本都会读取该子网，因此后面的命令会针对同一位置而无需重新导出任何内容。在新区域上，这四个步骤总共需要 20 到 30 分钟。检测并重用现有集群或节点组。

`deploy_cluster.sh` 创建 EKS 控制平面、VPC、OpenID Connect (OIDC) 提供商、核心附加组件和 m7i.xlarge 系统节点组，并在实际提供 g6.12xlarge 的区域中选择子网。 `deploy_node_group.sh` 添加两个打开 EFA 的 g6.12xlarge 实例，标记为 `role=gpu-worker` 和 `nvidia.com/gpu.present=true`。第二个标签是团队经常忽视的一个标签。如果没有它，NVIDIA 设备插件图表的 DaemonSet 将在零个节点上运行，并且不会出现指出原因的错误。 `install_gpu_plugins.sh` 确保两个设备插件都存在。最近的 eksctl 将它们捆绑到启用 EFA 的节点组中，因此在新的集群上它会找到它们并跳过。否则，它将安装在固定图表版本中。无论哪种方式，它都会验证“nvidia.com/gpu”和“vpc.amazonaws.com/efa”是否可以在每个 GPU 节点上分配，而不是信任成功的 Helm 版本。 `install_kuberay.sh` 将 KubeRay 运算符安装到系统节点上，使其远离 GPU 实例。

默认情况下，“deploy_all.sh”不执行训练作业。这仍然是一个单独的步骤，您可以根据需要随时重新运行，因为它是真正的作业运行而不是基础设施，并且失败的作业永远不会通过集群设置将您送回。通过 `--train` 来链接它：

`./deploy_ray_train_job.sh` **— RayCluster、作业和检查。**

使用“envsubst”渲染清单并应用它。然后，它会在等待任何 pod 之前重新读取每个 GPU 节点的可分配资源：如果设备插件没有出现，您会在此处收到明显的错误，而不是 pod 处于待处理状态直至超时。一旦 head 就绪并且两个工作线程都就绪，它就会将 `code/` 复制到 head 上，并通过 `kubectl exec` 从内部提交：
```
ray job submit --address http://localhost:8265 --working-dir /tmp/ray-train-code \
python3 train.py --model_id Qwen/Qwen2.5-1.5B
```
提交调用会流式传输所有八个级别的日志，并在作业完成时返回。然后，该脚本会检查 NCCL 使用的传输，如果作业失败或 EFA 不在路径中，则退出并显示错误，这也使其可用作持续集成 (CI) 门。 `./deploy_ray_train_job.sh status` 打印 RayCluster 状态、哪个实例托管每个 Pod 以及 GPU 容量。正确配置的集群如下所示：

## 根据您的工作负载进行调整

由于图像按已发布的方式使用，并且作业从集群中了解其规模，因此大多数更改只涉及一个文件：

| **你想改变** | **哪里** | **无需更改** |
| ---| ---| ---|
|型号 | `型号_ID` |代码、清单、图像 |
|步骤、序列长度、批量大小 | `STEPS`、`SEQ_LEN`、`BATCH_SIZE` |代码、清单、图像 |
|训练循环本身 | `train_func` 的主体 |培训师、清单、图像、脚本 |
|额外的 Python 包 | `--runtime-env-json` pip 列表 |图片|
|固定 DLC 发布 | `DLC_IMAGE` 到版本化标签 |其他一切|
| GPU 实例系列 | `GPU_NODE_TYPE`、`GPUS_PER_NODE` |代码、图像 |
|有多少 GPU 实例 | `GPU_NODE_COUNT`，加上清单中的`replicas`、`minReplicas` 和`maxReplicas` |代码（计算 GPU 数量）|
|地区或地区 | `REGION`，可选的`GPU_AZ` |其他一切|

除非另有说明，表中的变量位于“env.sh”中。切换实例系列时，“GPUS_PER_NODE”必须与硬件匹配，并且该系列需要 EFA 支持以及 EFA 设备插件允许的实例类型列表中的位置。已知此处固定的插件版本包括 g6.12xlarge。迁移到 p5 或其他支持 GPUDirect 的系列不需要更改图像或训练代码。

## 拆掉它

GPU 实例是昂贵的部分，加上控制平面和 NAT 网关，每小时约为 9.50 美元。按照与创建顺序相反的顺序删除事物：
```
./delete_ray_train_job.sh        # RayCluster
./install_kuberay.sh cleanup     # KubeRay operator
./install_gpu_plugins.sh cleanup # NVIDIA and EFA device plugins
./delete_node_group.sh           # GPU instances
./delete_cluster.sh              # EKS cluster, VPC and system node
```
## 下一步去哪里

两个实例和八个 GPU 使用无人构建的容器在 EKS 上运行分片微调。 Ray Train DLC 提供了从 CUDA 到 EFA 的经过测试的堆栈。 KubeRay 一开始是作为来自同一个标签的 head 和workers 的。 Ray Train 安排了工人并组建了流程组。从硬件到传输再到 Python 包的所有变化都是从映像外部设置的。该映像所提供的 EFA 路径涉及四个环境变量，并且在未更改代码的情况下使 TCP 吞吐量增加了一倍。

自然的下一步行动：

- 将随机批次替换为真实数据集，并将检查点设置为 Amazon Simple Storage Service (Amazon S3) 或 Amazon FSx for Lustre。
- 将“DLC_IMAGE”固定到版本标记以实现可重复运行。
- 打开“FailureConfig”，以便长时间运行能够在丢失的实例中幸存下来。
- 迁移到 GPUDirect RDMA 系列上的更大模型，例如 p5。图像和代码保持不变。
