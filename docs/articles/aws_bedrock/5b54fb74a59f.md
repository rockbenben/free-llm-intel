## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 在 EKS 上使用 Ray Train DLC 和 EFA 进行分布式训练

通常阻碍 [PyTorch](https://pytorch.org/) 训练扩展到集群的，往往是容器而不是模型代码。每个容器都需要同一套东西：[CUDA runtime](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html)、针对它编译的 PyTorch 构建、[NCCL](https://developer.nvidia.com/nccl)（NVIDIA 集合通信库）、[Elastic Fabric Adapter (EFA)](https://aws.amazon.com/hpc/efa/) 的用户态库、把 NCCL 连到 EFA 的 [AWS OFI NCCL](https://github.com/aws/aws-ofi-nccl) 插件，以及集群运维方认可的那个 [Ray](https://docs.ray.io/en/latest/) 版本。构建这个镜像，并在其中任何一块变动时重新构建，本身就是一个独立的项目，而且跟你原本要训练的模型毫无关系。[Ray Train 深度学习容器](https://aws.github.io/deep-learning-containers/ray-train/)（DLC）就是这个镜像，由 AWS 构建。AWS 组装起整套技术栈，把它作为一个整体进行测试，发布到 Amazon Elastic Container Registry（Amazon ECR）Public，并持续修补。

![一个 EKS 集群：CPU 系统节点运行 KubeRay 和 Ray head，同一个可用区里有两台启用 EFA 的 g6.12xlarge GPU 工作节点](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/19/ML-22002-1-1.png)

图 1：一个 EKS 集群，控制平面由 AWS 托管，CPU 系统节点（m7i.xlarge）运行 KubeRay operator 和 Ray head，同一个可用区里有两台启用 EFA 的 g6.12xlarge 节点。KubeRay 根据一份 RayCluster 清单构建集群，Ray Train 放置八个 worker，每块 GPU 一个，节点之间的集合通信则跨越 EFA。

Ray 把一个任务作为单个集群跨多台机器运行，集群中有两种角色。Ray head 负责协调并运行全局控制存储，用来跟踪集群状态，同时提供你提交任务所用的 dashboard 和作业服务器。Ray worker 节点提供 GPU 并运行训练进程。每个 worker 启动时连接到 head 的地址，从而加入集群。在 Kubernetes 上，这些角色各自对应一个 pod。Kubernetes 内置并不了解 Ray 集群，所以需要有东西来创建 head 和 worker 的 pod、在每个 pod 里以正确的角色启动 Ray、把 worker 指向 head，并替换失败的 pod。[KubeRay](https://aws.github.io/deep-learning-containers/ray-train/deployment/eks/) 正是做这件事的。它是一个开源的 Kubernetes operator，增加了 RayCluster 资源：你在一份清单里描述 head 组和 worker 组，KubeRay 据此构建并维护集群。

同一个带标签的镜像既充当 Ray head 也充当 Ray worker，无论是由 KubeRay 在 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/) 上启动，还是你自己在 Amazon Elastic Compute Cloud (Amazon EC2) 上启动。你额外添加的只是配置：用什么实例、每个 pod 分到多少块 GPU、NCCL 使用哪种网络传输，以及任务需要哪些额外的 Python 包。所有这些都从镜像外部设置。

本文会讲解一个示例，它原封不动地使用发布出去的 DLC，在两台 g6.12xlarge 实例的八块 NVIDIA L4 GPU 上用 PyTorch Fully Sharded Data Parallel（FSDP）微调 Qwen2.5-1.5B。训练代码只有一个函数，集群只是一份 RayCluster 清单加一个变量文件，全程不需要构建任何镜像。由于 DLC 已经带上了 EFA 技术栈，两台实例之间的集合通信只要 pod 申请了 [EFA](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html) 就会走 EFA。完整方案在这个[示例仓库](https://github.com/aws-samples/sample-aws-deep-learning-containers/tree/main/training/ray-train)里，它与我们[多节点 Ray Serve 实践](https://aws.amazon.com/blogs/machine-learning/run-multi-node-inference-workloads-using-ray-llm-deep-learning-containers/)用的是同一套 `KubeRay-on-EKS` 基础架构。

## 不构建任何东西也能得到什么

Ray Train DLC 就是在 PyTorch 训练镜像之上叠加 Ray 的训练库。这个示例拉取的标签 `public.ecr.aws/deep-learning-containers/ray:train-ml-cuda-v1.1`，取代了原本要这样构建出来的东西：

| **层次** | **原本需要自行构建并保持对齐的东西** | **Ray Train DLC 中** |
| --- | --- | --- |
| 分布式运行时 | 带 dashboard 和作业服务器、且版本为 KubeRay 所支持的 Ray | Ray 2.58.0，含 Train、Tune 和 Data |
| 框架 | 针对你的 CUDA 版本编译的 PyTorch | PyTorch 2.13.0、torchvision 0.28.0 |
| GPU 运行时 | 彼此版本一致的 CUDA、cuDNN 和 NCCL | CUDA 13.0.2、cuDNN、NCCL 2.29.7 |
| 网络 | 针对该 NCCL 构建的 EFA 安装程序、libfabric 和 `aws-ofi-nccl` | 最新的 EFA、AWS OFI NCCL 插件、GDRCopy |
| 训练库 | 针对你的 CUDA 编译的 DeepSpeed、flash-attn 和 Transformer Engine | DeepSpeed、flash-attn、Transformer Engine、PyTorch Lightning、Hugging Face 系列库 |
| 诊断工具 | 从源码构建的 NCCL 测试 | `all_reduce_perf` 已在 PATH 中 |

网络这一行是最多团队最不愿自己维护的。那里出现不匹配不会报错：NCCL 会退回到 TCP socket，任务照跑到底，速度却只剩一小部分。在 DLC 里，这些库是一起构建、一起测试的，而且 AWS 每次发布都要通过多节点 EFA 和多节点 KubeRay 的训练测试才算过关——这正是本示例走的那几条路径。

另外还有几个特性，免去了你原本要为每个集群重复做的事情：

- **无需配置镜像仓库 –** 镜像是公开的，节点拉取时不需要凭据，过程中也没有任何构建或推送。
- **无需匹配驱动 –** 启动时入口脚本会检查宿主机的 NVIDIA 驱动，如果它比镜像里的 CUDA 更旧，就自动启用随镜像附带的 CUDA 前向兼容库。
- **不需要区分 head 与 worker 镜像 –** 镜像本身没有固定角色，由启动容器的一方提供 `ray start` 命令，因此一个标签就能服务所有 pod。
- **不需要单独的推理镜像系列 –** Ray Train 与 [Ray Serve DLC](https://aws.github.io/deep-learning-containers/ray/) 和 [Ray LLM DLC](https://aws.github.io/deep-learning-containers/ray-llm/) 共用同一个 `ray` ECR 仓库，标签前缀为 `train-ml`。

## 配置它，而不是重建它

训练任务之间所有存在差异的东西，都是在镜像之外设置的。这个示例用到了以下每一种机制：

| **你控制什么** | **怎么设置** | **本示例中** |
| --- | --- | --- |
| head 还是 worker 角色 | 每个 pod 组的 KubeRay `rayStartParams` | 两者都用同一个 `DLC_IMAGE`，head 以 `num-gpus: "0"` 运行 |
| 每个 pod 的 GPU 与 EFA | Kubernetes 资源请求 | `nvidia.com/gpu: 4`、`vpc.amazonaws.com/efa: 1` |
| 网络传输 | pod 或作业上的环境变量 | `FI_PROVIDER`、`NCCL_NET_PLUGIN`、`NCCL_SOCKET_IFNAME`、`NCCL_DEBUG` |
| 额外的 Python 包 | 提交时的 Ray `runtime_env` | 作业需要的任意包，在提交时安装 |
| 镜像版本 | `DLC_IMAGE` 中带版本号或按 digest 固定的标签 | `train-ml-cuda-v1.1` |
| 集群形态 | `scripts/env.sh` 中的变量 | 实例类型、节点数、每节点 GPU 数、Region、AZ |
| 训练任务 | `train.py` 的参数 | 模型、步数、序列长度、批大小 |

**按作业安装包。** 镜像自带 HuggingFace 训练栈，所以这个示例的作业不需要额外加任何东西。当某个实验确实需要镜像里没有的库时，Ray 会在提交时通过 `runtime_env` 为该作业安装它，镜像本身保持不变。不用新镜像，也不用新标签。

**按作业设置传输方式。** 镜像默认 `FI_PROVIDER=efa`，其 NCCL 配置排除了回环接口和 Docker 网桥接口。在 EKS 上，你需要把 `NCCL_SOCKET_IFNAME` 指向 pod 的 `eth0`。这个示例干脆把四个网络变量都写进清单，这样行为都集中在一个文件里看得见，也不依赖镜像的默认值。由于它们都是普通环境变量，单个作业可以通过自己的 `runtime_env` 覆盖它们。

**版本由你选择。** 示例把版本固定在 `train-ml-cuda-v1.1`，也就是当前的小版本发布，这样集群从一次运行到下一次都是可复现的。`vX.Y` 标签会随着安全重建而移动；完整版本号的 `vX.Y.Z` 标签则冻结在最初的发布构建上，因此需要逐字节一致的结果时请固定 digest。同一个镜像也可以从私有 ECR URI 获取。

## 集群是怎么布局的

![示例集群：CPU 系统节点运行 KubeRay operator 和一个不带 GPU 的 Ray head，两台启用 EFA 的 g6.12xlarge 节点各自运行一个四 GPU 的 Ray worker pod](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/19/ML-22002-2-1.png)

图 2：示例的集群。每个 pod 都运行来自 Amazon ECR Public 的同一个 Ray Train DLC。CPU 系统节点运行 KubeRay operator 和一个不带 GPU 的 Ray head。两台启用 EFA 的 g6.12xlarge 同处一个可用区，各自运行一个四 GPU 的 Ray worker pod。

所有节点都位于同一个 virtual private cloud (VPC) 的私有子网中，只能通过 NAT Gateway 访问互联网——节点正是这样从 Amazon ECR Public 拉取 DLC，worker 也就是这样从 Hugging Face 下载模型权重的。一台 m7i.xlarge 组成系统节点组，承载 kube-system 附加组件、KubeRay operator 和 Ray head。head 在 8265 端口运行作业服务器，在 6379 端口运行 Ray 的控制存储，并且不对外宣告任何 GPU，所以不会有训练任务落到它身上。作业通过 `kubectl exec` 在 head pod 内部提交，走 EKS API，因此 8265 端口从不暴露到集群之外。

训练在两台 [g6.12xlarge](https://aws.amazon.com/ec2/instance-types/g6/) 实例上运行，每台有四块 NVIDIA L4 GPU、48 个 vCPU、192 GiB 内存、40 Gbps 网络和一个 EFA 接口。每台实例运行一个 Ray worker pod，独占全部四块 GPU 和那个 EFA 接口；Ray Train 在每个 pod 中放置四个 worker：一台实例上是 rank 0–3，另一台上是 4–7。由于 EFA 流量不能跨可用区，脚本会把两台实例放在同一个已确认提供 g6.12xlarge 的可用区里。

## Ray Train 在容器里做什么

DLC 提供了整套技术栈。[Ray Train](https://docs.ray.io/en/latest/train/train.html) 提供了原本要自己写的启动器代码。多节点 PyTorch 通常意味着在每台主机上每块 GPU 起一个进程，并给每个进程分配它的 rank、world size 和一个会合地址。用 Ray Train，你把训练循环写成一个函数，配上一个 `ScalingConfig` 传给 `TorchTrainer`。Ray 会在集群里有 GPU 的地方每块 GPU 起一个 worker，建立 `torch.distributed` 进程组，并在每个 worker 上运行你的函数。

这个示例向 Ray Train 请求 [FSDP](https://docs.pytorch.org/docs/stable/fsdp.html)：它把模型的权重、梯度和优化器状态切分到全部八块 GPU 上，而不是复制到每块 GPU。在 bfloat16 下，Qwen2.5-1.5B 的这四个张量大约需要 12 GB。切成八份之后，每块 L4 GPU 大约持有 1.5 GB。代价在通信：FSDP 在使用每一层之前先把该层权重聚合起来，之后再把梯度做 reduce-scatter，因此每一步整个模型都要在各个 rank 之间流动。两个实例之间的这部分流量，正是 DLC 的 EFA 技术栈所承载的。

## 训练代码：一个函数加一个 trainer

`code/train.py` 就是整个作业，其中没有任何专属于容器、集群或网络的内容。Ray 为每块 GPU 运行一次 `train_func`：向 Ray 询问自己的 rank，加载模型，交给 `prepare_model` 做 FSDP，然后运行一段普通的 PyTorch 循环：

**`code/train.py` —— 每块 GPU 的函数（节选）**

```
def train_func(config):
    ctx = ray.train.get_context()
    world_size, rank = ctx.get_world_size(), ctx.get_world_rank()
    device = ray.train.torch.get_device()

    model = AutoModelForCausalLM.from_pretrained(config["model_id"], torch_dtype=torch.bfloat16)

    # Any submodule above 10M parameters becomes its own FSDP unit. Wrapping by
    # size, not by a model-specific layer class, keeps the script model-agnostic.
    auto_wrap_policy = partial(size_based_auto_wrap_policy, min_num_params=int(1e7))
    model = ray.train.torch.prepare_model(
        model,
        parallel_strategy="fsdp",
        parallel_strategy_kwargs={"auto_wrap_policy": auto_wrap_policy},
    )
    optimizer = torch.optim.AdamW(model.parameters(), lr=config["learning_rate"])

    for step in range(config["steps"]):
        input_ids = torch.randint(0, model.config.vocab_size,
            (config["batch_size"], config["seq_len"]), device=device)
        optimizer.zero_grad()
        loss = model(input_ids=input_ids, labels=input_ids).loss
        loss.backward()  # parameters gathered again, gradients reduce-scattered
        optimizer.step()  # local: each rank updates only its own slice
        ray.train.report({"step": step, "loss": loss.item()})
```

driver 加入正在运行的集群，统计 GPU 数量并启动 trainer。由于 worker 数量来自集群，同一个脚本在一台节点和多台节点上都能原样运行：

**`code/train.py` —— driver（节选）**

```
ray.init(address="auto")  # join the RayCluster
num_workers = int(ray.cluster_resources().get("GPU", 0))  # 8 here

trainer = TorchTrainer(
    train_func,
    train_loop_config={...},
    scaling_config=ScalingConfig(num_workers=num_workers, use_gpu=True),
    run_config=RunConfig(name="ray-train-fsdp-llm"),
)
result = trainer.fit()
```

批次是随机的 token ID，这样整个运行就只依赖集群。判断这个示例的标准是：真实的 FSDP 集合通信是否跨越了两个节点，以及作业是否完成。要做真正的微调，把随机张量换成 Ray Data 或 DataLoader 流水线即可，函数里其他部分都不用改。

## 清单：唯一配置 DLC 的地方

`manifest/raycluster.yaml` 是镜像与集群相遇的地方，它之所以这么短，是因为镜像需要的配置本来就很少。head 唯一的特殊设置是 `NVIDIA_VISIBLE_DEVICES=void`，它避免了容器运行时的 NVIDIA hook 在没有 GPU 的节点上出错。其余全部内容都在 worker 组里：

**`manifest/raycluster.yaml` —— worker 组（节选）**

```
workerGroupSpecs:
  - groupName: gpu-workers
    replicas: 2
    rayStartParams:
      num-gpus: "${GPUS_PER_NODE}"  # keeps Ray's GPU count equal to the pod's
    template:
      spec:
        nodeSelector: { role: gpu-worker }
        containers:
          - name: ray-worker
            image: "${DLC_IMAGE}"  # the DLC as published; same tag as the head
            env:
              - { name: NCCL_DEBUG, value: "INFO" }  # print the chosen transport
              - { name: NCCL_SOCKET_IFNAME, value: "eth0" }  # pod network on EKS
              - { name: FI_PROVIDER, value: "efa" }  # libfabric: EFA, nothing else
              - { name: NCCL_NET_PLUGIN, value: "ofi" }  # load the AWS OFI plugin
            resources:
              limits: { nvidia.com/gpu: "${GPUS_PER_NODE}", vpc.amazonaws.com/efa: "1",
                cpu: "40", memory: 160Gi }
              requests: { nvidia.com/gpu: "${GPUS_PER_NODE}", vpc.amazonaws.com/efa: "1",
                cpu: "40", memory: 160Gi }
```

把它读作三个决定。

**用哪个镜像：** `${DLC_IMAGE}`，不做修改，head 和 worker 都用它。

**用什么硬件：** 每个 pod 四块 GPU，以及节点上的那一个 EFA 接口。正是对 `vpc.amazonaws.com/efa` 的请求让 EFA device plugin 把该接口挂载进容器。没有它，NCCL 就看不到 EFA，只能退回 socket。

**用什么传输方式：** 四个环境变量，不给自动探测留任何余地。

还有两个小细节能让多节点作业保持稳定。第一，requests 应当等于 limits，这会把 worker 放进 Kubernetes 的 Guaranteed（保证）服务质量（QoS）等级。这一点很重要，因为只要有一个 rank 被限流或被驱逐，其余七个就会卡住。第二，`num-gpus` 与 GPU 请求取自同一个变量，因此 Ray 看到的容量始终与 Kubernetes 一致。

## 把它跑起来：一条命令搭基础设施，然后是作业

配置都集中在一处：`scripts/env.sh`，包括集群名称、Region、Kubernetes 版本、节点类型与数量、镜像、固定版本的 KubeRay 和两个 device plugin，以及训练参数。导出其中任意一项即可改变某次运行的行为。五个脚本都是幂等的，可以安全地重复运行。`deploy_cluster.sh`、`deploy_node_group.sh` 和 `deploy_ray_train_job.sh` 在创建或改动集群资源前都会先询问。`install_gpu_plugins.sh` 和 `install_kuberay.sh` 是收敛式的，直接跑完。

```
cd training/ray-train/scripts
source ./env.sh
```

`./deploy_all.sh` —— 先找到容量真正所在的地方，再在那里搭建基础设施。

g6.12xlarge 的容量每天都在不同 Region 和可用区之间流动，所以这才是起点，而不是在 `env.sh` 里事先猜一个 Region。它首先运行 `find_gpu_capacity.sh`，对每个候选 Region 检查：各可用区是否提供 g6.12xlarge、账户的 G/VT 系列按需 vCPU 配额能否容纳请求的节点数，以及以 EC2 Spot 放置分数作为容量信号。加上 `deploy_all.sh` 默认会传入的 `--probe`，它会在每个候选可用区创建并立即取消一个真实的容量预留，从而得到确定答案。随后它会展示计划并询问一次：

```
Proceed with the whole chain without further prompts? (y/N):
```

回答 **y** 后，脚本会依次在推荐的 Region 中运行 `deploy_cluster.sh`、`deploy_node_group.sh`、`install_gpu_plugins.sh` 和 `install_kuberay.sh`，由于刚才已经问过，每个脚本都跳过自己的重复确认（`-y` 会跳过这次询问，`--plan` 则只展示计划而不创建任何东西）。如果 GPU 节点组在最佳可用区启动不了，脚本会把它删掉，转而尝试探测确认过的下一个可用区。`GPU_AZ` 还会与集群实际的私有子网交叉核对，而不只是看 g6.12xlarge 恰好在哪些地方提供，这样 GPU 节点组就不会被钉在一个集群根本没有子网的可用区上。选定的 Region 和可用区会保存到 `scripts/.placement.env`，其他所有脚本都会读取它，因此后续命令无需重新导出任何东西就指向同一位置。在全新的 Region 上，这四步总共需要 20 到 30 分钟。已存在的集群或节点组会被检测出来并复用。

`deploy_cluster.sh` 创建 EKS 控制平面、VPC、OpenID Connect (OIDC) provider、核心附加组件和 m7i.xlarge 系统节点组，子网选择在真正提供 g6.12xlarge 的可用区。`deploy_node_group.sh` 加入两台开启 EFA 的 g6.12xlarge 实例，标签为 `role=gpu-worker` 和 `nvidia.com/gpu.present=true`。第二个标签常常被团队忽略：没有它，NVIDIA device plugin 的 chart 部署出来的 DaemonSet 会落在零个节点上，而且没有任何错误指向真正的原因。`install_gpu_plugins.sh` 确保两个 device plugin 都已就位。较新的 eksctl 会把它们打包进启用 EFA 的节点组，所以在全新集群上它会发现并跳过；否则就按固定的 chart 版本安装。无论哪种情况，它都会验证每个 GPU 节点上 `nvidia.com/gpu` 和 `vpc.amazonaws.com/efa` 都可分配，而不是仅凭 Helm 发布成功就相信没问题。`install_kuberay.sh` 把 KubeRay operator 装到系统节点上，让它不占用 GPU 实例。

默认情况下 `deploy_all.sh` 不会去跑训练作业。训练保留为单独一步，你想重跑多少次都可以，因为那是一次真正的作业运行而不是基础设施搭建，作业失败也不会把你打回集群设置这一步。要串起来执行，加上 `--train`：

`./deploy_ray_train_job.sh` **—— RayCluster、作业和各项检查。**

它用 `envsubst` 渲染清单并应用，然后在等待任何 pod 之前重新读取每个 GPU 节点的可分配资源：如果某个 device plugin 没有起来，你会在这里得到一个明确的错误，而不是一个一直 Pending 到超时的 pod。等 head 和两个 worker 都 Ready 之后，它把 `code/` 复制到 head 上，并通过 `kubectl exec` 从 head 内部提交：

```
ray job submit --address http://localhost:8265 --working-dir /tmp/ray-train-code \
python3 train.py --model_id Qwen/Qwen2.5-1.5B
```

提交调用会流式输出全部八个 rank 的日志，并在作业结束时返回。脚本随后检查 NCCL 使用了哪种传输方式，如果作业失败或 EFA 不在路径上，就以错误退出——这同时也让它可以直接用作持续集成（CI）门禁。`./deploy_ray_train_job.sh status` 会打印 RayCluster 状态、每个 pod 落在哪台实例上，以及 GPU 容量。正确配置的集群看起来是这样的：

## 适配到你的工作负载

由于镜像直接按发布版使用，而作业的规模从集群中得知，大多数改动只需动一个文件：

| **你想改什么** | **在哪里改** | **不需要改** |
| --- | --- | --- |
| 模型 | `MODEL_ID` | 代码、清单、镜像 |
| 步数、序列长度、批大小 | `STEPS`、`SEQ_LEN`、`BATCH_SIZE` | 代码、清单、镜像 |
| 训练循环本身 | `train_func` 的函数体 | trainer、清单、镜像、脚本 |
| 额外的 Python 包 | `--runtime-env-json` 的 pip 列表 | 镜像 |
| 固定的 DLC 发布版本 | 把 `DLC_IMAGE` 改成带版本号的标签 | 其他一切 |
| GPU 实例系列 | `GPU_NODE_TYPE`、`GPUS_PER_NODE` | 代码、镜像 |
| GPU 实例数量 | `GPU_NODE_COUNT`，以及清单中的 `replicas`、`minReplicas` 和 `maxReplicas` | 代码（它会统计 GPU） |
| Region 或可用区 | `REGION`，可选的 `GPU_AZ` | 其他一切 |

表中变量除特别说明外都放在 `env.sh` 里。切换实例系列时，`GPUS_PER_NODE` 必须与硬件匹配，而且该系列要支持 EFA，并出现在 EFA device plugin 的允许实例类型列表中。这里固定的插件版本已知包含 g6.12xlarge。换到 p5 或其他支持 GPUDirect 的系列，不需要改动镜像或训练代码。

## 拆除

GPU 实例是最贵的部分，连同控制平面和 NAT Gateway 合计每小时约 $9.50。请按与创建时相反的顺序拆除：

```
./delete_ray_train_job.sh        # RayCluster
./install_kuberay.sh cleanup     # KubeRay operator
./install_gpu_plugins.sh cleanup # NVIDIA and EFA device plugins
./delete_node_group.sh           # GPU instances
./delete_cluster.sh              # EKS cluster, VPC and system node
```

## 接下来可以做什么

两台实例、八块 GPU，在一个没人构建过的容器上于 EKS 完成了一次分片微调。Ray Train DLC 提供了从 CUDA 一直到 EFA 的、经过测试的技术栈。KubeRay 用同一个标签把它启动为 head 和 worker。Ray Train 放置 worker 并建立进程组。所有会变化的东西——从硬件到传输方式到 Python 包——都是在镜像之外设置的。镜像自带的 EFA 路径靠四个环境变量启用，在代码完全不变的情况下把吞吐量提升到 TCP 的两倍。

自然的后续动作：

- 把随机批次换成真实数据集，并把 checkpoint 写入 Amazon Simple Storage Service (Amazon S3) 或 Amazon FSx for Lustre。
- 把 `DLC_IMAGE` 固定到带版本号的标签，以获得可复现的运行。
- 打开 `FailureConfig`，让长时间运行能挺过实例丢失。
- 换到支持 GPUDirect RDMA 的系列（如 p5）上更大的模型。镜像和代码保持不变。
