# 使用 Amazon Bedrock AgentCore 优化 agent 的 system prompt

在一篇[此前发布的文章](https://aws.amazon.com/blogs/machine-learning/introducing-agent-quality-optimization-in-agentcore-now-in-preview/)中，我们介绍了 AgentCore optimization——[Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/optimization.html) 的一项能力，可以帮助你提升 agent 的质量。传统上，改进一个得分较低的 agent 是一个手动过程。你要翻阅大量 trace，找出 agent 出错的地方，调整 prompt、工具描述和 skills 等单个组件，然后重新运行评估以检查是否有改进。

借助 AgentCore optimization，你可以利用生产环境的 trace 提出配置变更，通过离线批量评估和线上流量的 A/B testing 加以验证，然后推广表现最佳的方案。AgentCore Observability 是 Amazon Bedrock AgentCore 的一项能力，可洞察 agent 行为，而评估则提供有关 agent 质量的信号。[recommendations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/optimization-recommendations.html)、[configuration bundles](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/configuration-bundles.html) 以及通过 [A/B testing](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/ab-testing.html) 进行的验证，共同构成了一套改进 agent 的 workflow。

AgentCore 中的 system prompt optimizer 使用 AgentCore Observability 记录的 agent trace，结合 reward 信号，生成改进后的 system prompt。对于 [market trends agent](https://github.com/awslabs/agentcore-samples/tree/main/02-use-cases/01-conversational-agents/market-trends-agent)，该 recommendation 会将现有的 system prompt 与修订版本进行对比，并说明促使这些变更的 trace 模式。

## Optimizer 设计

system prompt optimizer 由一个 agentic reflector 执行，它是该 optimizer 的推理组件。它会审阅经过评估的 agent 行为，识别出区分成功运行与失败运行的模式，并针对 agent 配置提出有针对性的变更。在 system prompt 优化 workflow 中，它的主要输出是一份修订后的 system prompt，并附带说明所提议的变更为何能提升 agent 质量。

agent trace 通常很长，即便只有几十条也可能很快超出模型的上下文窗口。因此，把每条 trace 直接传入 reflector prompt 并不现实。我们没有截断或预先摘要 trace 以适配窗口，而是通过文件系统让 reflector 可以访问完整的 trace 语料。

该设计采用极简的 workflow。一个 evaluator 为一组 trace 打分，并将它们写入 reflector agent 可访问的目录。reflector 获得一个 shell 工具，被引导至该目录，并被要求通过检查这些 trace 中的成功与失败模式来提出对 agent 配置的更新。

reflector 可以按需检查语料。它可以列出文件、用 `grep` 搜索、用 `cat` 读取 trace、用 `diff` 比较输出，并有选择地检查成功和失败的运行。我们不强制采用固定的信号提取或 trace 摘要 pipeline。相反，由 reflector 自行判断哪些证据重要、进行哪些比较，以及如何将这些发现转化为配置变更。

随后它返回对 agent 配置提议的编辑。任何提议在应用之前，都必须通过平台级的 guardrails。

Responsible AI 方面的考量是这一 workflow 的一部分。recommendations 在使用前应经过审阅和测试，本文后面描述的 guardrails 会在候选更新被推广之前对其进行筛选。

### Single Agent Reflector

目前，Single Agent Reflector 负责驱动 AgentCore optimization 中的 system prompt recommendation。一个 reflector agent 单次遍历即可处理完整的 trace 集。它先审视得分分布，深入查看单条 trace 中最具信息量的片段，将成功案例与失败案例对比，然后返回一组连贯的 agent 配置编辑。每个优化 epoch 都会重复这一循环：为 trace 打分、反思、接受通过 guardrails 的编辑。你可以运行更多 epoch，用优化时间换取进一步的质量提升。

图 3 展示了这一 flow。经过评估的 trace 被写入一个共享目录，由单个 reflector 检查证据并生成推荐的配置编辑。guardrails 会在这些编辑被接受之前进行筛选。

图 3：Single Agent Reflector 分析经过评估的 trace，并返回经过 guardrails 筛选的配置编辑

### Sub-Agent Reflector

Sub-Agent Reflector 是对 Single Agent Reflector 的扩展。它牺牲一部分效率以换取更高的质量上限：使用一个由 agent 组成的 [swarm](https://strandsagents.com/docs/user-guide/concepts/multi-agent/swarm/) 动态探索 trace 集的不同部分。单次 reflector 遍历可能只关注它最初检查的 5–10 条 trace 中的模式，从而遗漏仅出现在语料较小部分中的失败模式。

每个 sub-agent 对单条 trace 执行三个层级的分析：

- **表层：** 提取 reward、difficulty 和 outcome。
- **轮次级：** 定位 trajectory 偏离最优路径的决策点，使用 `jq` 和 `grep` 等 shell 命令解析 rollout JSON。
- **认知层：** 诊断 agent 为何在该决策点失败，并提供反思性指导。

每个 sub-agent 返回一条简洁的发现和一条纠正规则。由于每个 sub-agent 都在自己的上下文窗口中运行，它可以专注于一条 trace 而不受其他 trace 的影响。orchestrator 汇总这些发现，归纳反复出现的模式，去除重复项，并将所得洞见凝练为配置变更。

图 4 展示了多 agent 的 flow。orchestrator 将单条 trace 分析委托给 sub-agent，收集它们的发现，并将这些发现综合为一组经过 guardrails 筛选的配置编辑。

图 4：Sub-Agent Reflector 利用独立的 trace 分析来指导经过 guardrails 筛选的配置编辑

### Guardrails

简单的配置优化可能以可预见的方式发生偏移：prompt 在优化后可能变长，prompt 可能引用 trace 中的术语作为示例，安全约束可能为追求 evaluator 得分而被放宽或弱化。我们对每一项候选更新都会先应用基于评分标准的 guardrails，然后才予以接受：

- **长度上限。** 若候选方案使配置比上一版本增加超过 20%，则予以拒绝，并要求 optimizer 收紧配置。
- **安全检查。** 候选方案在推广前会依据安全标准进行筛查。
- **不得照搬 trace 中的原话。** 候选方案不能复用其优化所依据的 trace 中的精确措辞。这有助于避免对训练 trace 的表面特征产生过拟合。

## 评估结果

我们在两个公开 benchmark——[AppWorld](https://appworld.dev/appworld/) 和 [WebShop](https://webshop-pnlp.github.io/)——上评估了 Single Agent Reflector 和 Sub-Agent Reflector，并与两个成熟的基线方法 [GEPA](https://github.com/gepa-ai/gepa) 和 [MIPROv2](https://dspy.ai/api/optimizers/MIPROv2/) 进行比较。对于每种方法，我们遍历配置空间，并报告最佳结果及其轮次数和优化实际耗时。

有两个趋势尤为突出：

**Single Agent Reflector 在质量与成本之间提供了最佳权衡。** 在 AppWorld 上，它用 6 分钟和 20 轮次达到 81.55%，在得分相当或更高的情况下，比 GEPA 快 18 倍、比 MIPROv2 快 36 倍。在 WebShop 上，它用 5 轮次和 1 分钟的实际耗时达到 78.31%。当你需要快速迭代周期时，这个变体非常合适。

**Sub-Agent Reflector 在两个 benchmark 上都取得了最高质量。** 在 AppWorld 上，它达到 95.83%，比基线提升 23 个百分点，比次优方法高出 16 个百分点。在 WebShop 上，它达到 79.15%，比基线提升 4 个百分点。逐条 trace 的 sub-agent 分析在 AppWorld 上效果最为显著，因为那里的失败模式多样，单次 reflector 遍历可能遗漏少数模式。

这些结果反映了前面描述的两种设计。整集反思赋予 Single Agent Reflector 效率优势：与迭代式方法相比，它只需远少的轮次数和分钟数就能达到有竞争力的得分。sub-agent 分解则让 Sub-Agent Reflector 拥有更高的质量上限：在汇总发现之前先独立分析每条 trace。这种方式有助于它识别出单次遍历大量 trace 时可能遗漏的失败模式。

图 5 汇总了四种方法在 AppWorld 和 WebShop 上的对比。Sub-Agent Reflector 取得了最高的成功率，而且在 AppWorld 和 WebShop 上，Single Agent Reflector 和 Sub-Agent Reflector 都优于 GEPA 和 MIPROv2。

## 最佳实践与展望

- **从小规模 trace 集开始。** 根据我们的经验，10–50 条多样化的 trace 就能为优化提供有用的起点。从小规模开始，只有当 recommendations 过于局限时才扩大数据集。
- **在适当时候使用标量 reward 之外的信号。** reflector 将 trace 作为文件读取，因此写入 trace 的任何信号它都能获取。除标量得分外，自由文本反馈（例如 evaluator 的理由、人工标注或用户投诉）也可以写入同一 trace 文件供反思使用。
- **审阅并验证 recommendations。** 在将所提议的配置推广到生产环境之前，利用 recommendation 说明、离线评估和受控 A/B testing 对其进行评估。
- **针对多样化的失败模式采用独立 trace 分析。** 实验性开源 Sub-Agent Reflector 会在汇总发现之前独立分析各条 trace。当不同的 trace 子集揭示出不同的失败模式时，可以考虑采用这种方式。
- **将分析扩展到 system prompt 之外。** trace 证据还可以揭示改进工具描述和可复用 skills 的机会。在评估这类配置变更时，应用相同的 guardrails 和验证 workflow。
- **从托管优化 workflow 开始。** 对于大多数生产用例，AgentCore optimization 提供从 trace 到 recommendations 和验证的推荐路径。有特殊研究或集成约束的团队，可以将同样的 trace、评估和验证模式应用于自定义的反思 workflow。

AgentCore optimization 将基于 trace 的证据与推荐的配置更新及验证 workflow 连接起来。要开始使用，请访问 [Amazon Bedrock AgentCore 详情页](https://aws.amazon.com/bedrock/agentcore/)、阅读[优化文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/optimization.html)、打开 [Amazon Bedrock AgentCore 控制台](https://console.aws.amazon.com/bedrock-agentcore/home)，并探索 [AgentCore 示例仓库](https://github.com/awslabs/agentcore-samples/tree/main/02-use-cases/01-conversational-agents/market-trends-agent)。
