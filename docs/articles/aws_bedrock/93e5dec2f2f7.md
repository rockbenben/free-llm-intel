# 在 Amazon Bedrock AgentCore 中使用时间策略保护 AI agent

在 AI agent 出现之前，访问控制把每个动作当作独立事件处理通常就足够了。应用依靠确定性的业务逻辑来约束动作是否按正确顺序发生，或者数据是否为最新。AI agent 的行为方式与传统应用有本质不同：它们在运行时决定调用哪些工具、传入哪些参数、以什么顺序调用。这种灵活性，加上越来越智能的模型，使 agent 既强大又难以控制。某一次工具调用单独看可能是安全的，但放在前一次调用的上下文中就有害，例如在从未受信任的数据源读取之后。于是问题就变成：如何执行那些把 agent 会话历史考虑在内的授权规则，并且让 agent 无法绕过？

[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 中的[时间策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-temporal.html)让你定义有状态规则，通过把当前请求放在 agent 轨迹中先前事件的上下文中求值，来决定是否授权访问 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 目标。由于这些策略运行在 AgentCore Gateway 边界上、位于 agent 自身代码之外，agent 无法拦截或操纵它们。

在本文中，你将了解什么是时间策略、它们如何工作，并通过一个示例进行演示。我们会展示如何用时间策略强制工作流顺序、防止工具调用之间的数据伪造、限制每个会话的累计财务敞口，以及要求高金额动作获得人工批准。你还会看到当 agent 在没有人工参与的情况下运行时，如何自动收紧权限。不过在此之前，我们先更详细地探讨有状态策略的需求与用例。

## 为什么 agent 需要有状态的策略执行

AgentCore Policy 中现有的访问控制对每个单独请求执行无状态、确定性的规则：谁能调用哪个工具、在什么条件下。无状态控制是必要的，但对 agent 来说往往不够。考虑以下场景，现有无状态控制无法捕捉其中的关键问题：

- 一个 agent 调用 `lookup_customer` 工具，幻觉出一个与返回值不同的账号，并把它传给 `transfer_funds` 工具，结果把钱转到了错误客户的账户。
- 一个失控的 agent 在循环中执行了数十笔交易，因为没有任何机制跟踪累计敞口已经超出风险限额。
- 一个 agent 在几秒之内既批准又拒绝了同一份保险理赔。

这些场景中的每一次工具调用单独来看都会通过无状态策略检查。问题只有在你查看 agent 的轨迹——即会话中按顺序排列的动作序列——时才会显现。时间策略为 AgentCore 中的 Policy 扩展出这一轨迹感知的执行层。时间策略运行在 gateway 上、位于 agent 代码之外，因此无论 agent 做什么、被如何提示，或 agent 代码中存在什么 bug，都无法绕过。一些常见的时间策略用例包括：

- **在串联工具之间强制输出完整性。** 要求传给当前工具调用的参数与先前某次工具调用的输出完全一致，防止 agent 在步骤之间幻觉或替换数值。
- **强制工具调用顺序。** 要求一个工具在另一个工具之前被调用，以验证标准操作流程（SOP）是否被遵守。
- **在特权动作前要求人工批准。** 在轨迹中记录到显式的人工批准事件之前，阻止破坏性或敏感的工具调用。
- **强制数据新鲜度。** 要求数据查询在给定时限内完成，之后才授权依赖它的动作，防止基于过期信息做决策。时间策略是一种授权控制，回答的问题是：「给定 AgentCore Gateway 上观察到的近期轨迹，这个特定请求是否被授权？」它们基于当前请求*以及*近期轨迹（即会话内的事件）来评估经由 gateway 路由的请求是否应被允许。它们不转换请求、不调用工具、不做分析，也不直接编排 agent。

时间策略作用于流经 AgentCore Gateway 的流量。由于 Gateway 通过单一端点路由 agent 的 Model Context Protocol（MCP）工具调用、agent 间调用和模型推理调用，只要你的 agent 经由 gateway 发起这些调用，一条时间策略就能同时治理这三类调用。这为你提供了一个一致的位置，随时间推移推理 agent 的行为，无论 agent 正在发起哪一类调用。

## 时间策略如何工作

时间策略构建在已用于无状态访问控制的现有策略引擎之上。它们引入了 agent 轨迹的概念，即由[主体（principal）](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-core-concepts.html#concept-principal-types)与会话 ID 标识的、有界的动作序列。agent 永远看不到策略逻辑，也永远接触不到状态存储，无法改动这些控制。与现有的 AgentCore Policy 功能一样，时间策略默认拒绝，并且 forbid 优先于 permit。

当 gateway 收到一次工具调用时，策略引擎会：

- 查询轨迹状态，获取与正在评估的策略相关的动作、输入与输出。
- 把每条时间策略放在其历史范围（即客户定义的轨迹内的先前事件）的上下文中，对当前请求进行求值。
- 返回确定性的 ALLOW 或 DENY 决定，并记录该决定的完整上下文。

每一条被时间策略求值的请求都必须携带 `x-amzn-bedrock-agentcore-policy-session-id` 请求头，用于标识该请求所属的会话。会话的起点和终点由你决定。这个边界可以反映任何对你的应用有意义的工作单元，无论是单次用户对话、多步任务，还是运行更久的工作流。由于每个会话最多只能有一个并发的授权请求，我们建议把会话范围保持得尽可能窄。如果没有传入请求头，系统会代你生成一个。但请注意，新的会话 ID 意味着策略引擎会针对一条全新的、没有任何历史的空轨迹求值。

会话从不由其 ID 单独定义。AgentCore 会把会话 ID 与最终用户的身份结合起来生成唯一会话，这意味着两个不同身份可以携带相同的会话 ID，却仍被视为完全独立的会话。由于底层身份不同，策略会独立作用于每条轨迹。在一个活动会话内，agent 轨迹的向前回溯窗口最长为 24 小时，任何更早的轨迹事件都会被自动删除。还有一条规则管辖会话与策略本身之间的关系：每当策略引擎中的策略发生变更，现有会话都会失效。这确保每个会话都按当前策略集求值，并且每个相关的轨迹事件都以预期 schema 记录。

## 将时间策略应用于私人银行投资组合 agent

为了让这些概念更具体，我们走一遍时间策略如何保护一个假设的私人银行 agent。该 agent 帮助金融服务公司的财富顾问管理客户投资组合。它会检索客户档案、加载投资组合持仓、获取实时市场价格、执行分析，并代表顾问执行交易。

在本场景中，以下 MCP 工具通过 AgentCore Gateway 暴露：

| **工具** | **描述** |
| --- | --- |
| get_client_profile | 检索客户的风险承受能力、投资政策、账户限制以及关联的投资组合 ID |
| load_portfolio | 检索客户的投资组合持仓与当前头寸 |
| get_market_price | 获取某只证券的当前市场价格 |
| execute_trade | 针对某个投资组合执行买入或卖出订单 |
| rebalance_portfolio | 调整投资组合内各持仓的配置比例 |

这里有三类不同的顾问角色：初级顾问（交易权限有限）、高级顾问（完整交易权限）和合规官（只读监控访问）。在本示例中，我们使用 [Amazon Cognito](https://aws.amazon.com/cognito/) 做身份认证，并把 JWT 作为入站认证传给承载 agent 工具的 AgentCore Gateway。要了解 AgentCore Gateway 以及如何为 Gateway 配置认证，请阅读 [AgentCore Gateway 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)。时间策略使用 [Dogwood](https://dogwood-policy.github.io/dogwood/index.html)，这是一种专为 agent 及其工具设计的新开源治理语言。Dogwood 支持对现有 [Cedar 策略](https://docs.cedarpolicy.com/)求值，并支持时间条件。由于 Dogwood 与现有 Cedar 策略兼容，客户可以继续使用当前的 Cedar 策略，无需迁移。有关 Dogwood 及其语义的更多细节，可阅读[语言文档](https://dogwood-policy.github.io/dogwood/index.html)或[这篇博客文章](https://aws.amazon.com/blogs/opensource/introducing-dogwood-runtime-verification-for-ai-agents/)。

合规团队要求在 agent 上线生产之前具备以下时间控制：

- agent 必须先拉取客户档案，再加载投资组合，之后才能执行任何交易。
- 交易中使用的 `portfolio_id` 必须与 `get_client_profile` 的输出完全一致。
- 市场价格必须在交易执行前 1 分钟内获取。
- 单个会话的总交易金额不得超过 $60,000。
- 任何超过 $25,000 的单笔交易都需要顾问批准，且每笔交易需要一次单独批准。
- 在同一轨迹内，如果卖出会造成亏损，agent 不能先买入再卖出同一只证券。
- 在 15 分钟没有顾问交互后，agent 将失去写操作的访问权限。

## 请求经由 gateway 与 policy 的流转

图 1：请求经由 AgentCore Gateway 与 Policy 的流转

此图演示了发往 gateway 的请求如何被 AgentCore 中的 Policy 拦截并求值。当投资组合 agent 发起一次工具调用时，会发生以下步骤：

- 请求到达 AgentCore Gateway。顾问已通过 AgentCore Identity 完成认证。请求携带当前会话的轨迹 ID。
- 策略引擎检索该轨迹累积的状态。
- 每条时间策略针对这段历史对当前请求求值。
- 如果所有策略都允许，请求继续前往 MCP 工具。如果任一策略禁止，请求被拒绝，且拒绝会被记录。
- 执行成功后，该动作及其结果会追加到轨迹状态中，供后续求值使用。

## 实现时间策略

如果你已有处于 `ENFORCE` 模式的策略引擎，可以把它的执行模式改为 `LOG_ONLY`，也可以单独修改各条策略的执行模式。不建议把现有策略或策略引擎切换到 `LOG_ONLY` 模式用于生产工作负载，因为策略将不再执行这些安全规则。

### 前提条件

在实现本方案之前，请确认已满足以下前提条件：

- 一个已启用 Amazon Bedrock AgentCore 的有效 AWS 账户。
- 一个已配置至少一个 MCP 目标的 AgentCore Gateway。
- 一个附加到该 gateway 的策略引擎。
- 创建和管理策略资源所需的相应 Identity and Access Management（IAM）权限（见文档）。

### 策略 1：工作流顺序（多跳链）

合规团队要求 agent 依次执行 `get_client_profile`、`load_portfolio`，然后 `rebalance_portfolio`。没有客户档案，agent 就没有经过系统验证的上下文来判断哪些投资组合属于该客户、客户的风险承受能力如何，以及适用哪些账户限制。

```
permit (principal, action == AgentCore::Action::"FinTarget___load_portfolio", resource == AgentCore::Gateway::<GATEWAY_ARN>)
when temporal {
    formerly within 5m (AgentCore::Action::"FinTarget___get_client_profile"::response{eventResource: resource})
};

permit (principal, action == AgentCore::Action::"FinTarget___rebalance_portfolio", resource == AgentCore::Gateway::<GATEWAY_ARN>)
when temporal {
    formerly within 5m (AgentCore::Action::"FinTarget___load_portfolio"::response{eventResource: resource})
};
```

除非 `get_client_profile` 与 `load_portfolio` 已在本轨迹内按正确顺序完成，否则该策略禁止 `rebalance_portfolio`。跳过加载档案步骤、直接跳到再平衡的 agent，无论收到什么指令都会被拒绝。

| **轨迹状态** | **尝试的动作** | **预期结果** |
| --- | --- | --- |
| 空 | rebalance_portfolio (portfolio_id: ” 8821”, amount: 15000) | DENY |
| get_client_profile 已完成 | rebalance_portfolio (portfolio_id: ” 8821”, amount: 15000) | DENY |
| get_client_profile 后 load_portfolio 已完成 | rebalance_portfolio(portfolio_id: ” 8821”, amount: 15000) | ALLOW |

### 策略 2：输出到输入的完整性

传给 `execute_trade` 的 `portfolio_id` 必须与 `get_client_profile` 返回的某个投资组合 ID 完全一致。agent 不能伪造或替换成其他投资组合 ID。

```
permit (
    principal,
    action == AgentCore::Action::"execute_trade",
    resource
)
when temporal {
    formerly within 24h (
        AgentCore::Action::"get_client_profile"::response{
            input.profile_id: context.input.profile_id,
            eventResource: resource
        }
    )
};
```

该策略防止攻击者利用 prompt 注入把 agent 引向另一个客户的投资组合进行交易。攻击者可以说服 LLM 使用伪造的 ID，但策略会拿该值与 CRM 系统实际返回的内容做校验。

| **get_client_profile 返回值** | **execute_trade portfolio_id** | **预期结果** |
| --- | --- | --- |
| port-8821 | port-8821 | ALLOW |
| port-8821 | port-3347 | DENY |

### 策略 3：数据新鲜度

在 `execute_trade` 获得授权之前，必须在最近 30 秒内完成过一次 `get_market_price` 调用。agent 不能基于过期的报价行动。

```
permit (
    principal,
    action == AgentCore::Action::"execute_trade",
    resource
)
when temporal {
    formerly within 30s (
        AgentCore::Action::"get_market_price"::response{eventResource: resource}
    )
};
```

在剧烈波动的市场中，即使只有 60 秒前的报价也可能意味着显著的价格漂移。该策略强制 agent 在每笔交易前刷新市场数据，确保决策基于当前信息。

| **距 get_market_price 的时间** | **动作** | **预期结果** |
| --- | --- | --- |
| 4 秒前 | BUY Stock A | ALLOW |
| 2 分钟前 | BUY Stock A | DENY |
| 从未调用 | BUY Stock A | DENY |

### 策略 4：每条轨迹的累计预算上限

单个策略会话（或轨迹）内的交易总金额不得超过 $60,000。这可以限制失控 agent 或成功攻击造成的影响范围。

```
permit (
    principal,
    action == AgentCore::Action::"execute_trade",
    resource
)
when temporal {
    exists (total: Long). ((sum amount for (amount: Long), (t: Timepoint). where (formerly within 24h (
        AgentCore::Action::"get_market_price"::request{input.cost: amount, eventResource: resource} && tp(t)))) == total && total < 60000
    )
};
```

一个被攻陷的 agent 执行数十笔单独看都没问题的小额交易，仍可能累积出灾难性的敞口。累计超过 $60,000 后，所有交易都会被拒绝，直到新的轨迹开始。

| **此前累计交易额** | **当前交易金额** | **合计** | **预期结果** |
| --- | --- | --- | --- |
| $0 | $15,000 | $15,000 | Allow |
| $15,000 | $22,000 | $37,000 | Allow |
| $37,000 | $30,000 | $67,000 | DENY |

### 策略 5：大额交易的人工批准（一次性消耗）

任何超过 $25,000 的交易都需要顾问的显式批准。每次批准会被一笔交易消耗掉。第二笔大额交易需要新的批准。

```
permit (
    principal,
    action == AgentCore::Action::"execute_trade",
    resource
)
when {
    context.input.cost < 25000 || temporal {
        !(
            AgentCore::Action::"execute_trade"::response{eventResource: resource}
        )
        since within 24h (
            AgentCore::Action::"approve_trade"::response{ input.status: "approved", eventResource: resource}
        )
    }
};
```

这可以防止 agent 把一次批准理解成多笔大额交易的概括许可。每次批准恰好覆盖一次执行。

| **交易金额** | **轨迹中的批准** | **预期结果** |
| --- | --- | --- |
| $15,000 | 无 | Allow（低于阈值） |
| $30,000 | 无 | DENY |
| $30,000 | 已批准（未消耗） | ALLOW |
| $30,000（第二笔交易） | 仅有先前的批准（已消耗） | DENY |

### 策略 6：互斥

在同一轨迹内，如果卖出会造成亏损，agent 不能先买入再卖出同一只证券。

```
permit (
    principal,
    action == AgentCore::Action::"execute_sell",
    resource
)
unless {
    context.input.profit < 0 && temporal {
        formerly within 24h (
            AgentCore::Action::"execute_buy"{
                stock_symbol: context.input.stock_symbol, eventResource: resource}
        )
    }
}
};
```

如果 agent 两分钟前卖出了 AAPL，现在又试图买入 AAPL，请求会被拒绝。这种自相矛盾本身就是信号，说明出了问题，该会话应当被复核。

| **先前动作** | **当前动作** | **时间间隔** | **预期结果** |
| --- | --- | --- | --- |
| SELL Stock A | BUY Stock A | 2 分钟 | DENY |
| SELL Stock A | BUY Stock A | 7 分钟 | ALLOW |
| SELL Stock A | BUY Stock B | 2 分钟 | ALLOW（不同证券） |

### 策略 7：渐进式信任衰减

在 15 分钟没有顾问交互后，agent 会失去写操作（`execute_trade`、`rebalance_portfolio`）的访问权限。顾问可随时重新介入以恢复完整访问权限。

```
permit (
    principal,
    action in [
        AgentCore::Action::"execute_trade",
        AgentCore::Action::"rebalance_portfolio"
    ],
    resource == AgentCore::Gateway::"<arn>"
)
when temporal {
    formerly within 15m AgentCore::Action::"interact_advisor"::response{eventResource: resource}
};
```

如果顾问离开，agent 会自然收敛到只读行为。这确保长时间自主运行不会累积不受约束的风险。

| **距上次顾问交互的时间** | **尝试的动作** | **预期结果** |
| --- | --- | --- |
| 3 分钟 | execute_trade | ALLOW |
| 20 分钟 | execute_trade | DENY |
| 20 分钟 | get_market_price | ALLOW（只读） |

## 成本考量

你只需为 agent 执行期间发生的授权请求付费。每当 agent 通过 AgentCore Gateway 调用工具，Policy 都会按你的规则检查该动作，以判定允许还是拒绝。每个策略引擎的前 100 条时间策略已包含在现有的按授权请求计价中（详情见 [AgentCore 定价页面](https://aws.amazon.com/bedrock/agentcore/pricing/)）。

## 清理资源

为避免持续产生费用，请移除你在本次演练中创建的资源。按顺序删除资源：先从策略引擎中删除时间策略，再把策略引擎从 gateway 上分离，最后删除策略引擎本身。只要策略引擎中还包含策略或仍附加在 gateway 上，就无法删除它。如果你为本演练专门创建了 gateway 及其 MCP 目标，也请一并删除。注意，删除或变更策略会使任何活动的策略会话失效，因此请仅在测试会话全部结束后再执行清理。

列出并删除策略引擎上的策略。对七条策略分别重复执行 delete-policy 命令：

```
aws bedrock-agentcore-control list-policies $
  --policy-engine-id <POLICY_ENGINE_ID>

aws bedrock-agentcore-control delete-policy $
  --policy-engine-id <POLICY_ENGINE_ID> $
  --policy-id <POLICY_ID>
```

在不带策略引擎配置的情况下更新 gateway，从而把策略引擎从 gateway 上分离：

```
aws bedrock-agentcore-control create-gateway $
  --name my-gateway $
  --role-arn arn:aws:iam::123456789012:role/my-gateway-service-role $
  --protocol-type MCP $
  --authorizer-type CUSTOM_JWT $
  --authorizer-configuration '{
    "customJWTAuthorizer": {
      "discoveryUrl": "https://cognito-idp.us-west-2.amazonaws.com/some-user-pool/.well-known/openid-configuration",
      "allowedClients": ["clientId"]
    }
  }'
```

删除策略引擎：

```
aws bedrock-agentcore-control delete-policy-engine $
  --policy-engine-id <POLICY_ENGINE_ID>
```

（可选）如果你为本演练创建了 gateway 目标与 gateway，请将其删除：

```
aws bedrock-agentcore-control delete-gateway-target $
  --gateway-identifier <GATEWAY_ID> $
  --target-id <TARGET_ID>

aws bedrock-agentcore-control delete-gateway $
  --gateway-identifier <GATEWAY_ID>
```

## 结论

在本文中，你了解了时间策略如何为 agentic AI 系统带来有状态、轨迹感知的授权。你把七种策略模式应用到一个假设的私人银行投资组合 agent 上。这些模式涵盖工作流顺序、输出到输入的完整性、数据新鲜度、累计预算上限、human-in-the-loop 批准、互斥，以及渐进式信任衰减。在 agent 于运行时与敏感工具交互的各类领域中，这些模式都具普遍适用性。由于执行发生在 AgentCore Gateway 边界上、位于 agent 自身推理循环之外，无论模型行为如何，这些保护都不可篡改。这为你提供了一种声明式、可审计的方式来约束操作边界，同时不限制让 agent 有价值的灵活性。要开始使用，请查阅 [AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-create-policies.html)。
