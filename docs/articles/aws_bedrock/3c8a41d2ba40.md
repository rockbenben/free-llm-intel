# 将 Amazon Bedrock AgentCore 连接到跨账户知识库

组织常常使用 Amazon Bedrock AgentCore 部署 agent——这是一个用于以任何框架或模型大规模构建、连接与优化 agent 的平台。这些 agent 可能需要访问托管在其他 AWS 账户中的受治理知识库。这种跨账户隔离有助于维持清晰的工作负载边界，但也可能带来集成挑战。

本文说明一个账户中的 AgentCore agent 如何从另一个账户中由 Amazon Redshift Serverless 支撑的知识库（使用 Amazon Bedrock Knowledge Bases 这一全托管检索增强生成能力）生成答案，而无需复制源数据。

本文涵盖两种已正式可用的 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 编排模型各自的架构、安全边界、请求流程与选择标准。所链接的 [GitHub 示例](https://github.com/aws-samples/sample-for-strands-agentcore-connect-cross-account-kb)提供了两种变体的部署流程与实现细节：

- 基于代码的 [Strands agent](https://strandsagents.com/)，运行在 [AgentCore runtime（Amazon Bedrock AgentCore 的一项能力）](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)上。
- 声明式的 [AgentCore harness（Amazon Bedrock AgentCore 的一项能力）](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness.html)。

## 挑战

使用 Amazon Bedrock 构建 AI agent 的组织可以在 Amazon Redshift Serverless 中维护结构化数据。这些数据存储库可以与其 AI agent 位于不同的 AWS 账户中。Amazon Bedrock Knowledge Bases 的资源策略支持 `Retrieve` 与 `GetDocumentContent` 用于跨账户操作。受支持的资源策略操作不包括 `RetrieveAndGenerate`。由于本方案需要 `RetrieveAndGenerate` 返回的生成答案，该工具会在调用 API 之前，在知识库账户中代入一个权限范围很窄的 AWS Identity and Access Management（IAM）角色。

这给采用多账户架构、并希望做到以下几点的企业带来了挑战：

- 在 Amazon Redshift Serverless 的结构化数据之上生成自然语言答案。
- 在 agent 工作负载与数据工作负载之间维持账户边界。
- 避免把受治理的源数据复制到 agent 账户中。
- 通过专用的跨账户 IAM 角色授予最小权限访问。

## 方案概览

本方案以两种方式实现跨账户查询模式。变体 1 把 Strands agent 部署到 AgentCore runtime。变体 2 使用声明式的 [AgentCore harness](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness.html)。两种实现使用相同的数据访问边界。由模型控制的工具使用 AWS Security Token Service（AWS STS）代入知识库访问角色，调用 `RetrieveAndGenerate`，并把生成的答案与引用返回给编排层。两种变体的差异在于谁拥有 agent 循环，以及工具如何托管。图 1 对比了两条编排路径及其共享的跨账户数据访问边界。

## 请求流程

请求按以下顺序进行：

- 用户通过 Streamlit UI 或某个 AgentCore API 提交一个自然语言问题。
- [Amazon Nova](https://aws.amazon.com/nova/) Pro 决定调用 `query_knowledge_base` 工具。
- 在变体 1 中，该工具运行在随 AgentCore runtime 一起打包的本地 Model Context Protocol（MCP）子进程中。在变体 2 中，AgentCore harness 通过 [AgentCore Gateway（Amazon Bedrock AgentCore 的一项能力）](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)调用一个 AWS Lambda 工具。
- 该工具使用 AWS STS 代入知识库账户中的 `bedrock_kb_access_role`。
- 该 assumed-role 会话使用 Claude Haiku 4.5 调用 `RetrieveAndGenerate`。知识库把问题转换为针对 Amazon Redshift Serverless 的结构化查询。
- 生成的答案沿选定的编排路径返回给用户。

## 选择最简单的够用模式

在选择 agent 实现之前，先判断该工作负载究竟是否需要 agent。这样可以让设计与所需行为保持相称。

- 如果应用只需要检索到的内容，请评估使用知识库资源策略的原生跨账户 Retrieve。
- 如果每个请求确定地只需要一个生成答案，请先确认该工作负载不需要工具选择、多步推理或对话状态。如果确实不需要，就直接从应用或 AWS Lambda 函数中代入知识库账户角色并调用 `RetrieveAndGenerate`。
- 当模型必须在更广泛的对话或使用工具的工作流中决定何时以及如何查询知识库时，才使用 agent。

### 何时使用哪种 AgentCore 变体

跨账户需求本身并不偏向任何一种变体。请根据你的团队需要自定义并运维多少编排循环来选择。

| **决策维度** | **基于代码的 Strands agent** | **声明式 AgentCore harness** |
| --- | --- | --- |
| 最适合 | 需要自定义编排、hook、中间件、重试行为、埋点，或需要对工具与流式进行直接控制的团队。 | 用例适合托管循环、偏好配置优先生命周期的团队。 |
| Agent 循环 | 你的 Python 代码使用 Strands Agents SDK 运行该循环。 | AgentCore 依据 harness 定义运行该循环。 |
| 工具路径 | AgentCore runtime → 本地 MCP 子进程 → 知识库。 | AgentCore harness → AgentCore Gateway → AWS Lambda → 知识库。 |
| 跨账户 principal | AgentCore runtime 执行角色。 | AgentCore Gateway 背后的 AWS Lambda 执行角色。 |
| 你需要维护什么 | `agent.py`、依赖、MCP 服务器、工具逻辑与 runtime 配置。 | AgentCore harness 配置、system prompt、AWS Lambda 工具、IAM 与应用行为。 |
| 调用 API | `InvokeAgentRuntime`。 | `InvokeHarness`。 |

这项决策的本质是自定义控制与托管编排之间的取舍。

## 前提条件

在开始之前，请确认你具备以下前提条件：

- 两个 AWS 账户：一个 ***agent*** 账户和一个 ***agent-kb*** 账户。
- AWS Command Line Interface（AWS CLI）v2.24.22 或更高版本，并具备两个账户的凭证。
- Python 3.10 或更高版本，以及 `jq`。
- 一个连接到 Amazon Redshift Serverless 的结构化 Amazon Bedrock 知识库。
- 在 US West（Oregon）的模型访问权限：agent 账户中的 `us.amazon.nova-pro-v1:0`，以及 ***agent-kb*** 账户中的 `us.anthropic.claude-haiku-4-5-20251001-v1:0`。关于按区域划分的模型可用性，请参阅 [Amazon Bedrock 中各 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。
- 对于 harness 变体，除了基于代码的变体所用的 Python `bedrock-agentcore` CLI 之外，还需安装当前的 `@aws/agentcore` Node.js CLI。

## 假设

示例使用以下本地 profile 别名与占位账户 ID：

| **Profile** | **示例账户** | **用途** |
| --- | --- | --- |
| agent | 111122223333 | 承载 AgentCore 资源。 |
| agent-kb | 999999999999 | 承载知识库与 Redshift Serverless。 |

示例使用 US West（Oregon）区域（`us-west-2`）。profile 名称是本地别名，请把它们替换为你配置的 profile 名称，并通过查询获取账户 ID，而不是硬编码。

```
AGENT_PROFILE=agent
AGENT_KB_PROFILE=agent-kb
REGION=us-west-2

AGENT_ACCOUNT=$(aws sts get-caller-identity \
--profile "$AGENT_PROFILE" --query Account --output text)
AGENT_KB_ACCOUNT=$(aws sts get-caller-identity \
--profile "$AGENT_KB_PROFILE" --query Account --output text)
aws bedrock-agent list-knowledge-bases \
--profile "$AGENT_KB_PROFILE" --region "$REGION"
```

## 推荐做法

在部署与验证任一变体时，请采用以下做法：

- 对独立的事实对比使用新的 session ID。
- 记录准确的工具查询、知识库 ID、模型 ID 与检索结果条数。
- 使用经批准的策展 SQL 与列描述来定义派生的业务指标。
- 对行级问题使用明确的行数、日期范围与排序顺序加以限定，以避免过大的 SQL 结果集。
- 把跨账户角色的范围限定在所需的知识库与模型资源上。
- 在长时运行的 runtime 与预热（warm）的 AWS Lambda 环境中使用可刷新的 STS 凭证。
- 对两种变体都测试 system prompt、工具描述、IAM 与应用行为。
- 应用 Amazon Bedrock Guardrails 来评估用户问题与生成的答案，检查有害内容、被禁止的话题与敏感信息。Guardrails 是对最小权限访问、源数据治理、基于引用的验证以及重大决策的人工复核的补充，而不是替代。

## 清理资源

请按照示例的[清理章节](https://github.com/aws-samples/sample-for-strands-agentcore-connect-cross-account-kb#cleanup)获取当前命令与所需顺序。当两种变体都已部署时，请先完成 [harness 清理](https://github.com/aws-samples/sample-for-strands-agentcore-connect-cross-account-kb#harness-cleanup)，以便从共享的知识库访问角色中移除其 AWS Lambda 执行角色的信任授权。然后再移除基于代码的 runtime 与共享 IAM 资源。这些脚本不会删除由项目管理的 AgentCore memory、知识库或 Redshift Serverless 资源。当它们不再需要时，请单独删除。

## 总结

本文描述了 AgentCore agent 如何跨 AWS 账户边界，从结构化的 Amazon Bedrock 知识库返回生成的答案。两种实现都在数据账户中使用最小权限角色。架构上的选择在于谁拥有 agent 循环以及工具如何托管。当原生 `Retrieve` 或直接调用 `RetrieveAndGenerate` 就能满足工作负载时，请从这些方式开始。当需要由模型控制的工具或对话式编排时，选择基于代码的 Strands 变体，以获得自定义循环行为与直接控制。当托管循环适合你的场景、且团队偏好配置优先的运营模式时，选择 AgentCore harness。两者都是有效且已正式可用的路径。这里是 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/)，你可以在此[开始使用 Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-get-started-cli.html)，并查看[代码示例](https://github.com/awslabs/agentcore-samples/tree/main)。
