当组织从单一用途的智能体走向多智能体系统时，基础设施要求也随之改变。一个单独处理客户查询的智能体可以运行在无服务器、会话短时的环境里。但当你要让三个智能体协作完成一个跨越数天的创造性工作流、共享上下文并在彼此产出上继续构建时，那些几小时就封顶的无服务器会话就不够用了。

在本文中，我们演练部署一条音乐制作流水线：一个智能体在实例自己的 GPU 上运行一个生成式音频模型。另外两个打开它写到共享卷上的 .wav 文件。到最后，你会得到一条可以播放的曲子，并且学会了如何创建 capacity provider、从不同产物类型部署智能体、用共享会话编排智能体之间的协作，以及跨多天持久化工作流。

[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 为托管智能体提供两种计算选项。*MicroVM* 是无服务器选项：快速冷启动、会话隔离和按消费计价。*Runtime Instances* 是新选项：由 AWS 托管的 EC2 基础设施，用于持久的、长时间运行的智能体工作流。两者使用相同的运行时 API，但 Instances 增加了跨天会话、GPU、持久卷，以及把多个智能体共置到单个实例上的能力。

## Runtime Instances 与 MicroVM 的区别

两个选项都支持自定义框架（CrewAI、LangGraph、LlamaIndex、Strands Agents），配合你选择的任何基础模型，与 MCP 和 A2A 集成，并共享同样的 AgentCore 运行时 API。差别在于底层的计算模型。

| 能力 | MicroVM（无服务器） | Runtime Instances |
| --- | --- | --- |
| 计算 | 完全由 AWS 托管 | 由 AWS 托管的 EC2 实例 |
| 会话时长 | 最多 8 小时 | 最多 14 天 |
| 每计算的智能体数 | 一个运行时（microVM）托管一个智能体（1:1） | 一个实例（EC2）可托管多个智能体（1:N） |
| 产物类型 | 容器镜像和 Amazon S3 源 | 容器镜像和 Amazon S3 源 |
| GPU 访问 | 不支持 | 支持，在受支持的实例系列上 |
| 会话持久化 | 会话作用域 | 持久存储（Amazon EBS） |
| 定价 | 按消费计价 | EC2 实例在你的账户中运行。使用你的 AWS Savings Plans 和按需容量预留（ODCR） |
| 伸缩 | 按需伸缩 | 由 capacity provider 管理 |

一个智能体是在一个会话内运行的工作负载。与一个运行时托管一个智能体的 MicroVM 模型不同，一个 Instances 会话可以托管多个智能体。当两个智能体运行时共享同一个 capacity provider 时，你可以用同一个 `runtimeSessionId` 调用它们，让两个智能体落到同一台 EC2 实例上。在那里它们共享一个文件系统，并可以在同一任务上协作。

## 方案概览

图 1：三个智能体的流水线（Compose、Deliver、Screen）共享一台 GPU 实例和一个会话

我们要构建一个使用三个专用智能体的音乐制作系统：

- **作曲智能体**（Audio AI 团队）：用 Claude Sonnet 4.6 把制作人的请求转化为一份音乐简报，然后用一个生成式音乐模型（[ACE-Step](https://github.com/ace-step/ACE-Step)，一个用于音乐生成的开源基础模型 FM）在实例自己的 GPU 上渲染实际音频。打包为 Amazon Elastic Container Registry (Amazon ECR) 中的容器镜像。
- **交付智能体**（Audio Engineering 团队）：从共享文件系统读取渲染好的曲子并测量它，然后基于那些测量结果（而非音频本身）向 Claude Sonnet 4.6 请求一条交付链（EQ、压缩、限幅）。真正的信号处理应用到这条链上，并再次测量结果以确认它达到了交付目标。打包为 Amazon ECR 中的容器镜像。
- **合规智能体**（Release Engineering 团队）：独立地重新测量完成的交付、对照交付智能体所声称的交付目标检查它，并针对录音棚自己的历史目录筛查它的谐波相似度。如果筛查提出异议，该智能体会回调作曲智能体请求替换并重新筛查。以 Amazon Simple Storage Service (Amazon S3) 上的一个 zip 文件交付。

工作流：一位制作人发起一首曲子。作曲智能体写一份简报并在实例的 GPU 上渲染真实音频。交付智能体打开那个文件、测量它、应用一条由这些测量推导出的链，并再次测量以证明结果落到了目标上。接着合规智能体独立重新测量、检查交付目标，并把音频对照录音棚的历史目录筛查。如果筛查标记出一处匹配，它就回调作曲智能体生成一个替代。制作人最终得到一条可播放的 .wav 和三份解释每一个决定的报告。

让这一切在 Runtime Instances 上成为可能的因素：

- **通过共享会话 ID 共置。** 每个智能体有自己的运行时，但通过在同一 capacity provider 上用同一个 `runtimeSessionId` 调用它们，AgentCore 把它们放到同一台实例上、挂载同样的卷。它们共享一个文件系统并能访问彼此的输出。
- **一块可用的 GPU。** 作曲智能体直接在实例的 NVIDIA L4 上运行 ACE-Step 基础模型，大约 9 秒渲染出 20 秒的 48 kHz 立体声。模型及其依赖位于一个持久卷上。在一个会话中构建一次，之后该会话里的每次调用都会复用——包括过夜停止之后。
- **独立部署。** 每个团队按自己的节奏交付自己的产物。Audio AI 团队推送一个新的作曲镜像，无需与 Audio Engineering 或 Release Engineering 协调，另外两个原封不动地继续运行。
- **跨天持久化。** 制作人周一做作曲、夜里停掉会话、周二恢复交付。实例自动空闲并在下一次调用时恢复。
- **混合产物。** 来自 ECR 的容器和来自 S3 的代码包共存于同一个 capacity provider 上。团队选择适合自己工作流的打包方式。

- 本地安装了 [Finch](https://github.com/runfinch/finch) 或另一个兼容 OCI 的容器工具。
- 已安装 Python 3.10+。

完整可运行代码见 GitHub 上的 [AgentCore samples 仓库](https://github.com/awslabs/agentcore-samples/tree/main/02-use-cases/02-workflow-automation-agents/gpu-music-production-agent)。

### 步骤 1：定义你的智能体

AgentCore Runtime Instances 支持任意智能体框架。在本示例中，每个智能体都是一个用 [Strands Agents](https://github.com/strands-agents/) 构建的 Python 应用。

有两个细节常被配错，且都以令人困惑的方式失败：

```
@app.entrypoint
def invoke(payload, context):  # the parameter must be NAMED "context"
    session_id = getattr(context, "session_id", None) or "local-session"
```

SDK 依据参数名来分派（它检查 `params[1] == "context"`）。那是读取会话 ID 的唯一方式，而智能体需要它来找到彼此的文件并相互调用。

其次，把 `Agent` 构建在 handler 内部，而非模块作用域：

```
def build_agent(session_id: str, track_id: str) -> Agent:
    return Agent(
        name=AGENT_NAME,
        model=BedrockModel(model_id=MODEL_ID, region_name=REGION),
        system_prompt=SYSTEM_PROMPT,
        session_manager=FileSessionManager(
            session_id=f"{session_id}-{AGENT_NAME}",
            storage_dir=str(track_path(track_id) / f".sessions-{AGENT_NAME}"),
        ),
    )
```

一个模块级的 `Agent` 会在并发请求间共享，而 Strands 会以 `Agent is already processing a request` 拒绝重入调用。历史通过 `FileSessionManager` 留在卷上，这正是几天后恢复的会话能记住先前决定的原因。

#### 作曲智能体

作曲智能体用 Claude Sonnet 4.6 把制作人请求（prompt）转化为一份音乐简报，然后用 ACE-Step 基础模型渲染实际音频：

```
@app.entrypoint
def invoke(payload, context):
    session_id = getattr(context, "session_id", None) or "local-session"
    track_id = payload.get("track_id", "demo-track")
    if payload.get("mode") == "prepare":
        return {"status": "ok", "model_stack": prepare_model_stack()}
    ensure_track_dir(track_id)
    brief = build_agent(session_id, track_id)(
        payload["prompt"], structured_output_model=CompositionBrief
    ).structured_output
    wav = track_path(track_id) / "composition.wav"
    render = render_audio(wav, brief, duration_s=payload.get("duration_s", 30.0))
    write_text(track_id, "composition.md", brief.to_markdown(render))
    return {"status": "ok", "render": render, "host": host_info(),
            "artifacts": [publish(track_id, wav)]}
```

`mode=prepare` 调用把技术栈构建到卷上——一个带 CUDA PyTorch 和 ACE-Step 的 virtualenv。渲染作为该卷解释器下的一个子进程运行：

```
proc = subprocess.run(
    [status["python"], status["runner"], "--out", str(out_path),
     "--prompt", brief.style_tags, "--duration", str(duration_s)],
    capture_output=True, text=True, check=False,
    timeout=RENDER_TIMEOUT_S, env=gpu_env(),
)
```

#### 交付智能体

交付智能体从共享文件系统读取渲染好的曲子并测量它。它用 Claude Sonnet 4.6 选择 EQ 频段、压缩器设置以及要保留不动的部分。然后应用数字信号处理（DSP）。接着再次测量输出，于是这个计划被校验而非盲信。

```
before = audio.measure(str(source))  # ITU-R BS.1770-4
plan = build_agent(session_id, track_id)(
    f"Prepare this for {platform} delivery.\n{json.dumps(before.to_dict())}",
    structured_output_model=DeliveryPlan,
).structured_output
data, rate = audio.read_audio(str(source))
bands = [b.model_dump() for b in plan.eq_bands]
if bands:
    data = audio.apply_filters(data, rate, bands)
if plan.compressor.enabled:
    data, _ = audio.compress(
        data, rate,
        threshold_db=plan.compressor.threshold_db,
        ratio=plan.compressor.ratio,
        attack_ms=plan.compressor.attack_ms,
        release_ms=plan.compressor.release_ms,
        knee_db=plan.compressor.knee_db,
    )
data, _ = audio.normalise_loudness(data, rate, plan.target_lufs)
data, _ = audio.limit(data, rate, ceiling_dbtp=plan.target_true_peak_dbtp)
audio.write_audio(str(delivery), data, rate, subtype="PCM_24")
after = audio.measure(str(delivery))  # verify, don't trust
```

### 步骤 2：创建一个 capacity provider

capacity provider 告诉 AgentCore 为你的智能体配置什么样的计算基础设施。你指定实例类型和 VPC 位置。AgentCore 负责配置和生命周期管理。

你需要**两个** IAM 角色，两者的区分很重要：

- 一个 **operator 角色**，AgentCore 代入它来代表你配置 EC2：启动、打标签和终止实例及其网络接口。附加托管策略 `BedrockAgentCoreRuntimeInstancesOperatorRolePolicy`。
- 一个 **execution 角色**，你的智能体进程在运行时代入它以调用 Bedrock 和 S3。`CreateAgentRuntime` 要求它，缺少它会失败。

两者都信任 `bedrock-agentcore.amazonaws.com`。

现在创建 capacity provider。注意名称必须使用下划线（不允许连字符）：

```
control = boto3.client("bedrock-agentcore-control", region_name=REGION)
resp = control.create_capacity_provider(
    name="music_production_capacity",
    permissionsConfiguration={"capacityProviderOperatorRoleArn": operator_arn},
    computeConfiguration={
        "ec2Configuration": {
            "launchTemplateSource": {
                "launchParameters": {
                    "operatingSystem": "LINUX_X86_64", "instanceRequirements": {"allowedInstanceTypes": ["g6.xlarge"]},
                }
            },
            "vpcConfiguration": {"subnets": subnets, "securityGroups": groups},
            "volumes": [
                {"ebsConfiguration": {"name": "tracks", "sizeGiB": 20,
                    "volumeType": "gp3", "encrypted": True}},
                {"ebsConfiguration": {"name": "models", "sizeGiB": 60,
                    "volumeType": "gp3", "encrypted": True,
                    "throughput": 500}},
            ],
            "rootVolume": {"freeSpaceGiB": 30, "volumeType": "gp3"},
            "lifecycleConfiguration": {"idleInstanceTimeout": 600,
                "maxLifetime": 86400},
        }
    },
)
```

⚠️ **GPU 容量。** 如果你在多个可用区（AZ）尝试分配一台 GPU 实例时遇到 `InsufficientInstanceCapacity`，你可以切换到另一个 GPU 实例类型，例如 `g5.xlarge`。相应地更新 `allowedInstanceTypes`。

### 步骤 3：部署智能体运行时

这里每个智能体都有自己的运行时。运行时在调用时被凑到一起。当两个运行时共享一个 capacity provider 且你用同一个 `runtimeSessionId` 调用它们时，AgentCore 会把两个智能体放到同一台 EC2 实例上，在那里它们共享一个文件系统并能在同一任务上协作。这就是交付智能体读取作曲智能体所写 .wav 的方式。

接下来，把每个运行时指向 capacity provider 并声明它挂载哪些卷：

```
composition = control.create_agent_runtime(
    agentRuntimeName="music_production_composition",
    roleArn=execution_arn,  # required
    agentRuntimeArtifact={"containerConfiguration": {"containerUri": image_uri}},
    protocolConfiguration={"serverProtocol": "HTTP"},
    capacityProviderConfiguration={"capacityProviderArn": cp_arn},
    filesystemConfigurations=[
        {"capacityProviderVolume": {"volumeName": "tracks", "mountPath": "/mnt/tracks"}},
        {"capacityProviderVolume": {"volumeName": "models", "mountPath": "/mnt/models"}},
    ],
    lifecycleConfiguration={"idleRuntimeSessionTimeout": 600, "maxLifetime": 86400},
    environmentVariables={"AWS_REGION": REGION, "WORKSPACE_DIR": "/mnt/tracks",
        "MODELS_DIR": "/mnt/models", "MODEL_ID": MODEL_ID},
)
```

合规智能体是同一个调用，只是产物不同——一个 zip 而非镜像——并且只有工作区卷：

agentRuntimeArtifact={"codeConfiguration": {

### 步骤 4：用共享会话编排多智能体工作流

现在调用这些智能体。这一步让三个智能体变成一条流水线：你把同一个 `runtimeSessionId` 传给每次调用。第一次调用较慢，因为它配置实例。之后的每次调用都路由到那台已在运行的实例。

```
client = boto3.client(
    "bedrock-agentcore", region_name=REGION,
    config=Config(read_timeout=900, retries={"max_attempts": 2, "mode": "standard"}),
)
session_id = f"music-production-{uuid.uuid4()}"  # 33-100 characters

def invoke_agent(runtime_arn, payload):
    response = client.invoke_agent_runtime(
        agentRuntimeArn=runtime_arn, qualifier="DEFAULT",
        runtimeSessionId=session_id, payload=json.dumps(payload).encode(),
    )
    return json.loads(response["response"].read())

invoke_agent(COMPOSITION_ARN, {"mode": "prepare"})
invoke_agent(COMPOSITION_ARN, {"mode": "catalogue", "track_id": track_id, "duration_s": 20})
invoke_agent(COMPOSITION_ARN, {"mode": "compose", "track_id": track_id, "duration_s": 30,
    "prompt": "Create an upbeat electronic track with heavy bass and synth melodies."})
invoke_agent(DELIVERY_ARN, {"track_id": track_id, "platform": "spotify",
    "prompt": "Prepare this for streaming delivery."})
result = invoke_agent(COMPLIANCE_ARN, {"track_id": track_id,
    "prompt": "Screen this delivery for release."})
print(result["outcome"])  # cleared | review_required | not_cleared
```

这是它在美国东部（俄亥俄）us-east-2 的一台实际 `g6.xlarge` 上的产出：

   host : ip-172-31-11-83.us-east-2.compute.internal
   stack : ready=True in 125s
2. render back-catalogue  66s

当你调用 `StopRuntimeSession` 时，实例会自动降到低功耗空闲。空闲期间不产生计算费。当你再次调用该会话时，AgentCore 会恢复它，**前提是它落在同一个可用区**。Amazon Elastic Block Store (Amazon EBS) 卷锁定到可用区。如果原可用区容量耗尽，卷无法重新挂载，持久性就会丢失。使用一个 AZ 固定的 ODCR 或 `MODELS_SNAPSHOT_ID`，以便被重新放置的恢复能找回。会话最多可持续 14 天。

### 步骤 5：独立更新智能体

这一架构的优势之一是独立部署。当 Audio AI 团队发布作曲智能体的新版本时，他们只更新自己的运行时：

```
# Audio AI team pushes new container version
finch build --platform linux/amd64 \
  -f Dockerfile.composition \
  -t "$ECR/music-production/composition-agent:v2" .
finch push "$ECR/music-production/composition-agent:v2"
```

```
control.update_agent_runtime(
    agentRuntimeId=composition_id,  # all three are required
    roleArn=execution_arn,
    agentRuntimeArtifact={"containerConfiguration": {"containerUri": new_uri}},
    capacityProviderConfiguration={"capacityProviderArn": cp_arn},

```

交付和合规智能体原样继续运行。无需协调、无共享部署流水线，也没有用你的更新破坏另一个团队智能体的风险。

## 清理

先删除会话。那是停止 EC2 和 Amazon EBS 费用最直接的方式。删除一个会话会撤销其 EC2 资源：实例、网络接口和 Amazon EBS 卷。删除 capacity provider 也会停止并删除其关联的会话及其持久存储。不过，你必须先把每个运行时和运行时版本与之解除关联，而这种解除是异步的。删除会话是快速路径，如果你想避免持续产生费用就该走这条。

```
data = boto3.client("bedrock-agentcore", region_name=REGION)
data.delete_capacity_provider_session(capacityProviderId=cp_id, sessionId=session_id)
for rid in runtime_ids:
    control.delete_agent_runtime(agentRuntimeId=rid)
# Versions detach from the capacity provider asynchronously, so poll here.
control.delete_capacity_provider(capacityProviderId=cp_id)
```

然后删除 ECR 仓库、S3 产物、IAM 角色和 Amazon CloudWatch 日志组。

## 结论

在本文中，我们在 Amazon Bedrock AgentCore Runtime Instances 上部署了一个多智能体音乐制作系统。三个由不同团队用不同打包格式构建的智能体，在一台 GPU 实例上的一个会话内协作，产出了一条你可以播放的曲子。

该架构演示了几个适用于音乐制作之外的模式：

- **通过共享会话共置。** 同一个 capacity provider 上的多个智能体运行时，用同一个会话 ID 调用时会共享一台实例，这给了它们同一台主机：同一块 GPU、同一个本地卷、同一个进程空间。
- **独立团队部署。** 每个智能体有自己的运行时生命周期。团队按自己的节奏交付而无需协调。
- **混合产物类型。** 容器和代码包共存于同一基础设施上。使用适合你团队工作流的任何打包方式。
- **跨天持久化。** 工作暂停时停掉会话，再次调用即恢复。会话最多持续 14 天（恢复取决于落在同一个可用区）。

音乐是一个方便的载体，但该架构没有任何与音乐绑定之处。换掉渲染步，同样的三智能体形态就契合 AWS 为 GPU Instances 点出的工作负载：3D 渲染、仿真、模型推理、媒体处理。或者一个长时间运行的作业：一条流水线产出一个大产物，交给第二个智能体做变换，再让第三个在发布前检查结果。

要了解更多，参见 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/agentcore.html)。要获取本文的完整可运行代码，探索 [AgentCore samples 仓库](https://github.com/awslabs/agentcore-samples)。要了解更多高级编排模式，如 Graph、Swarm 或 Workflow，参见 [Strands Agents 文档](https://strandsagents.com/)。
