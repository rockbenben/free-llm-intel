# 使用应用推理配置文件管理多租户 Amazon Bedrock 成本

成功的生成式 AI 软件即服务（SaaS）系统需要在服务可扩展性与成本管理之间取得平衡。在构建面向庞大且多样化客户群、同时需要严格成本控制和全面用量监控的多租户生成式 AI 服务时，这一点尤为关键。

此类系统的传统成本管理方法常常暴露出局限。运维团队难以准确地把成本归因到各个租户，尤其是当使用模式呈现极大波动时。企业客户可能有不同的消费行为——一些客户在高峰期出现用量突增，而另一些客户则保持稳定的资源消耗模式。

一个稳健的解决方案需要一套超出常规监控标准的、由上下文驱动的多级告警系统。通过实施分级告警级别——从绿色（正常运行）到红色（需要关键干预）——系统可以形成智能、自动化的响应，动态适应不断变化的使用模式。这种方法可实现主动的资源管理、精确的成本分摊，以及快速、有针对性的干预，帮助防止潜在的财务超支。

临界点往往在你遭遇显著成本超支时到来。这些超支并非源于单一因素，而是多个企业租户增加用量的同时，你的监控系统未能足够早地发现趋势所共同导致的。你现有的告警系统可能只提供二元通知——要么一切正常，要么出了问题——缺少主动成本管理所需的细致、多级方式。分层定价模型让情况更加复杂：不同客户有不同的 SLA 承诺和用量配额。如果没有一套能够区分正常用量突增与真正问题的精密告警系统，你的运维团队可能会发现自己一直在采取被动措施，而非主动措施。

本文探讨如何使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 中名为[应用推理配置文件](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-create.html)的功能，为多租户 AI 部署实施稳健的监控方案。我们演示如何构建一个系统，在复杂的多租户环境中实现细粒度用量追踪、精确成本分摊和动态资源管理。

## 什么是应用推理配置文件？

Amazon Bedrock 中的应用推理配置文件可实现跨部署的细粒度成本追踪。你可以为每个推理请求关联元数据，在不同应用、团队或访问你基础模型（FM）的客户之间建立逻辑隔离。通过采用与应用推理配置文件一致的标记策略，你可以系统地追踪每次 API 调用由哪个租户发起，以及相应的消费量。

例如，你可以定义 `TenantID`、`business-unit` 或 `ApplicationID` 等键值对标签，并随每个请求发送这些标签，从而对你的用量数据切分。你也可以在请求中发送应用推理配置文件 ID。与 AWS 资源标记相结合时，这些支持标签的配置文件可让你洞察 Amazon Bedrock 模型的使用情况。这种标记方法引入准确的计费回摊（chargeback）机制，帮助你按实际用量而非任意分摊方式来分配成本。要为推理配置文件附加标签，请参阅[为 Amazon Bedrock 资源添加标签](https://docs.aws.amazon.com/bedrock/latest/userguide/tagging.html)和[使用 AWS 成本分配标签组织和跟踪成本](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-alloc-tags.html)。此外，你可以使用应用推理配置文件识别各租户特有的优化机会，帮助你实施有针对性的改进，从而在性能与成本效率两方面产生最大影响。

## 方案概览

设想这样一个场景：一个组织拥有多个租户，每个租户各自的生成式 AI 应用都在使用 Amazon Bedrock 模型。为演示多租户成本管理，我们在 [GitHub](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/poc-to-prod/inference-profiles/inference-profile-cost-tracing) 上提供了一个可部署的示例方案。该方案在一个 AWS 区域内为两个租户各部署两个应用。方案使用应用推理配置文件进行成本追踪，使用 [Amazon Simple Notification Service](https://aws.amazon.com/sns)（Amazon SNS）发送通知，并使用 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 生成租户专属仪表板。你可以修改方案的源代码以适配自身需求。

下图展示了该方案的架构。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/11/Slide1.jpeg)

该方案处理跨租户收集和聚合用量数据的复杂性，存储历史指标以进行趋势分析，并通过直观的仪表板呈现可行动的洞察。该方案提供了管理 Amazon Bedrock 成本所需的可见性与控制力，同时保留灵活性，可将各组件定制以匹配你所在组织的具体需求。

## 先决条件

在搭建该项目之前，你必须具备以下先决条件：

- **AWS 账户** – 一个有效的 AWS 账户，具有创建和管理 Lambda 函数、API Gateway 端点、CloudWatch 仪表板和 SNS 告警等资源的权限
- **Python 环境** – 本地机器上安装 Python 3.12 或更高版本
- **虚拟环境** – 建议使用虚拟环境来管理项目依赖

## 创建虚拟环境

第一步是克隆 [GitHub](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/poc-to-prod/inference-profiles/inference-profile-cost-tracing) 仓库，或将代码复制到新项目中，以创建虚拟环境。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/11/Screenshot-2025-07-11-at-3.24.51 PM.png)

## 更新 models.json

审阅并更新 [models.json](https://github.com/aws-samples/amazon-bedrock-samples/blob/main/poc-to-prod/inference-profiles/inference-profile-cost-tracing/config/models.json) 文件，依据你所在组织的合同反映正确的输入与输出 token 价格，或使用默认设置。在此阶段确认数据正确，对于准确的成本追踪至关重要。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/11/Screenshot-2025-07-11-at-3.25.45 PM.png)

## 更新 config.json

修改 [config.json](https://github.com/aws-samples/amazon-bedrock-samples/blob/main/poc-to-prod/inference-profiles/inference-profile-cost-tracing/config/config.json) 以定义你想要为成本追踪设置的配置文件。每个配置文件可以包含多个用于标签的键值对。对每个配置文件而言，每个标签键必须唯一，且每个标签键只能有一个值。运行时每个传入请求都应包含这些标签或配置文件名称作为 HTTP 头。

作为方案的一部分，你还要配置一个专用的 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）桶用于保存配置产物，以及一个管理员电子邮件别名，在突破特定阈值时接收告警。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/11/Screenshot-2025-07-11-at-3.26.07 PM.png)

## 创建用户角色并部署方案资源

修改完 config.json 和 models.json 之后，在终端运行以下命令以创建资产（包括用户角色）：

```
python setup.py --create-user-roles
```

或者，你也可以在不创建用户角色的情况下创建资产，方法是运行以下命令：

```
python setup.py
```

请确保你在项目目录中执行此命令。请注意，不建议为[生产用例](https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html#grant-least-privilege)使用完全访问策略。

setup 命令会触发一系列流程：创建推理配置文件、构建 CloudWatch 仪表板以采集每个配置文件的指标、部署执行 Amazon Bedrock Converse API 并提取推理元数据和相关指标的推理 Lambda 函数、设置 SNS 告警，最后创建 API Gateway 端点以调用该 Lambda 函数。

设置完成后，你将看到推理配置文件 ID 和 API Gateway ID 列在 config.json 文件中。（API Gateway ID 也会列在终端输出的最后部分。）

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/11/Screenshot-2025-07-11-at-3.32.45 PM.png)

当 API 上线并从中发起推理请求后，CloudWatch 仪表板将显示成本追踪情况。如果你遭遇显著流量，告警将触发 SNS 告警邮件。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/11/Screenshot-2025-07-11-at-3.33.50 PM.png)

本操作指南的视频版本，请参阅 [Track, Allocate, and Manage your Generative AI cost & usage with Amazon Bedrock](https://youtu.be/OTbVOuAmsZk?si=rXfE1m02MW0u19lF)。

现在你已准备好使用 Amazon Bedrock 模型配合这套成本管理方案。请确保你通过 API Gateway 端点来消费这些模型，并在请求中以 HTTP 头形式发送你在 config.json 文件中提供的标签或应用推理配置文件 ID。该方案会自动记录调用次数，并按租户追踪你应用的成本。

## 告警与仪表板

该方案会创建以下告警和仪表板：

- **BedrockTokenCostAlarm-{profile_name}** – 当 {profile_name} 的 token 总成本在 5 分钟内超过 {cost_threshold} 时告警
- **BedrockTokensPerMinuteAlarm-{profile_name}** – 当 {profile_name} 的每分钟 token 数超过 {tokens_per_min_threshold} 时告警
- **BedrockRequestsPerMinuteAlarm-{profile_name}** – 当 {profile_name} 的每分钟请求数超过 {requests_per_min_threshold} 时告警

你可以跨多个区域监控你的 AWS 资源和应用并接收告警。

指标告警可能处于以下状态：

- **OK** – 指标或表达式处于定义的阈值范围内
- **ALARM** – 指标或表达式超出定义的阈值范围
- **INSUFFICIENT_DATA** – 告警刚刚启动、指标不可用，或数据不足以判定告警状态

将告警添加到仪表板后，告警在 INSUFFICIENT_DATA 状态下显示为灰色，在 ALARM 状态下显示为红色。当告警处于 OK 状态时不显示颜色。

告警仅在状态从 OK 变为 ALARM 时触发操作。本方案中，会通过你的 SNS 订阅向 config.json 文件中指定的管理员发送邮件。你还可以指定在告警状态于 OK、ALARM 和 INSUFFICIENT_DATA 之间变化时要执行的额外操作。

## 注意事项

尽管 API Gateway 的最大集成超时（30 秒）低于 Lambda 超时（15 分钟），但长时间运行的模型推理调用仍可能被 API Gateway 截断。Lambda 和 Amazon Bedrock 对负载与 token 大小施加严格限制，因此请确保你的请求和响应都在这些边界之内。例如，Lambda 同步调用的最大负载大小为 6 MB，而 API Gateway 负载的请求行与头值合计不得超过 10,240 字节。如果你的工作负载能够适配这些限制，你就可以使用该方案。

## 清理

要删除你的资产，请运行以下命令：

```
python unsetup.py
```

## 结论

本文中，我们演示了如何使用应用推理配置文件、CloudWatch 指标和自定义 CloudWatch 仪表板，为多租户 Amazon Bedrock 部署实施有效的成本监控。借助该方案，你可以跨不同租户追踪模型用量、准确分摊成本并优化资源消耗。你可以根据你所在组织的具体需求定制该方案。

该方案提供了构建智能系统的框架：这样的系统能够理解上下文——区分可能代表健康业务增长的用量渐进上升与可能预示潜在问题的突然激增。有效的告警系统需要足够精细，在判定告警级别时考虑历史模式、一天中的时段以及客户层级。此外，这些告警可以依据告警级别触发不同类型的自动化响应：从简单通知，到自动的客户沟通，再到立即的限流操作。
