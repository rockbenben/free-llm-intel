# 使用 AtScale 和 Amazon Bedrock AgentCore 在 AWS 上为 agentic AI 构建语义层

在[本系列的第一篇文章](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/)中，我们使用 Stardog 的知识图，在 [Amazon Aurora](https://aws.amazon.com/rds/aurora/) 和 [Amazon Redshift](https://aws.amazon.com/redshift/) 之上于 AWS 构建了一个语义层。我们针对该层在 [Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/) 上运行了一个 [Strands](https://docs.aws.amazon.com/prescriptive-guidance/latest/agentic-ai-frameworks/strands-agents.html) agent。[第二篇文章](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-denodo-and-amazon-bedrock-agentcore/)保留了相同的 customer 360（C360）模式，换成 Denodo 的数据虚拟化平台，并把数据源组合扩展到包含一个本地 PostgreSQL 集群。本文再次沿用相同的 C360 模式，语义层则换成 [AtScale](https://www.atscale.com/)。

AtScale 的形态与前两篇不同。它的语义模型是维度式的（维度、层次结构和度量），而不是三元组图或一组视图。AtScale 用[语义建模语言（Semantic Modeling Language，SML）](https://github.com/semanticdatalayer/SML)来创作模型，这是一种在 Git 中做版本控制的、基于 YAML 的开放规范，并从同一个已部署的模型出发，同时通过三种协议对外暴露：SQL、XML for Analysis（XMLA）和 Model Context Protocol（MCP）。Strands agent 与企业已经在用的商业智能（BI）工具，从同一套定义得到同一个计算结果。

这套模式的其余部分沿袭此前几篇。[Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的基础模型（本演练使用 Anthropic Claude Sonnet 4.6）负责规划并编写查询。Amazon Bedrock AgentCore 托管 Strands agent，并管理 agent 向 AtScale 出示的出站凭证。适用于调用者的连接、度量定义以及行与列筛选都位于语义层内部，而不是在 prompt 里。

我们假设你已经熟悉本系列[第一篇文章](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/)中的语义层架构：什么是语义层、它用来做什么，以及为什么模型在规划查询时并不拥有那些连接。如果有任何内容对你是新的，第一篇文章已经覆盖了这些基础。

读完本文，你将了解：

- 如何用语义建模语言（SML）对 C360 域建模：数据集、维度与层次结构、事实、度量、计算度量和 perspective，并在 Git 中做版本控制。
- AtScale 如何针对 Amazon Redshift 规划维度查询，以及 AtScale 的自主聚合管理如何加速 agent 生成的查询模式。
- 如何通过 AtScale MCP server 把模型暴露给由 AgentCore 托管的 Strands agent，以及如何把该 MCP server 注册到 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)（Amazon Bedrock AgentCore 的一项能力）。
- 人类用户的身份如何从企业身份提供商经 [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html)（Amazon Bedrock AgentCore 的一项能力）传播到 AtScale，以及 AtScale 如何在查询时强制执行基于角色的访问控制（RBAC）、行安全和 perspective。
- 如何使用 AtScale Helm chart 和 [AtScale K8S Blueprints](https://github.com/AtScaleInc/atscale-k8s-blueprints) 仓库在 [Amazon Elastic Kubernetes Service（Amazon EKS）](https://aws.amazon.com/eks/) 上部署 AtScale。

本演练的事实来源是 [AtScale C2026.7 版本](https://documentation.atscale.com/container/release-notes/C2026.7)。在涉及具体工具名或端点的地方，我们引用 [AtScale 文档](https://documentation.atscale.com/container/atscale)。

## 示例：Amazon Redshift 上的 Customer 360

前两篇文章中的 customer 360 模式保持不变。一家零售企业的客户记录、订单、产品和奖励计划登记分散在各个系统中，业务用户希望在不了解哪个系统持有哪个事实的前提下提出跨领域问题。我们为本系列第一篇文章改编的 [Stardog C360 Knowledge Kit](https://github.com/stardog-union/knowledge-kits/tree/main/examples/c360) 用 Customer、Order、Product 和 Address 实体对这个场景建模，这些实体通过一个整数 `cid` 连接：它在 customer 表中是主键，在 purchase 表中则是普通列。

本文与前两篇的不同之处在于数据的物理位置。Stardog 和 Denodo 在查询时跨两个引擎联邦。AtScale 把维度查询规划为原生仓库 SQL，并在每次查询时下推到单个引擎，因此跨引擎数据在上游完成整合。在本演练中，所有分析型 C360 数据都位于 [Amazon Redshift Serverless](https://aws.amazon.com/redshift/redshift-serverless/)。Amazon Aurora PostgreSQL 仍是运营侧的记录系统，一条复制路径（[AWS Database Migration Service](https://aws.amazon.com/dms/) 或 [Amazon Aurora 到 Amazon Redshift 的 zero-ETL](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/zero-etl.html)）让分析副本保持最新。agent 查询的是映射到 Amazon Redshift 表的单个 AtScale 模型。

Amazon Redshift 中的 schema：

| **表** | **关键列** |
| --- | --- |
| customer | cid (PK), first_name, last_name, email, ssn, phone, location |
| address | id (PK), city, state, zip, street_name |
| credit_card | id (PK), cid, card_num, card_type |
| rewards_account | id (PK), cid, account_id, create_date |
| purchase | id (PK), pid, purchase_date, quantity, price, cid, card |
| product | id (PK), name, brand, price, dept |
| category | id (PK), dept_name, parent |
| vendor | id (PK), vendor_name, industry |

八张表中九个值得关注的列。`cid` 把客户记录与购买关联起来。`pid` 把购买关联到产品。`dept` 把产品关联到类别。所有分析型数据都在 Amazon Redshift 中，因此连接会下推为原生 SQL，而不在语义层或抽取、转换、加载（ETL）流水线中解析。

一个能跑通整个模型的代表性问题是：*按生命周期消费额排名前 20 的客户中，哪些还没有加入奖励计划？* 这就是 Denodo 那篇中的自动注册问题，保留下来是为了让跟随本系列的读者看到同一个请求由不同的语义层作答。它涉及客户档案、地址、购买历史和注册状态：每个客户跨四个逻辑实体一行。

## 本文用到的 AtScale 术语

AtScale 把语义层实现为数据仓库之上的维度模型。AtScale 文档和 SML 规范使用一组特定的原语，它们会在本文中反复出现。在我们进入演练之前，一份简短的参考会很有用。

- **语义建模语言（SML）–** 一种用于描述语义模型的、基于 YAML 的开放规范。每个 SML 对象（模型、数据集、维度、层次结构、度量、计算、perspective、行安全）都是一个 YAML 文件。规范位于 [github.com/semanticdatalayer/SML](https://github.com/semanticdatalayer/SML)。
- **模型（Model）–** 顶层产物。模型引用数据集、维度、事实和度量，并通过 AtScale 查询引擎暴露它们。
- **维度与层次结构 –** 维度对相关属性（customer、product、date）分组。维度内部的层次结构把这些属性组织成级别（product → category → department，或 year → quarter → month → day）。
- **事实与度量 –** 事实是一个数据集，保存可度量的事件，并按键列与维度连接。度量是从事实列聚合出来的量，例如收入用 `SUM(price * quantity)`。
- **计算（Calculation）–** 以针对其他度量的公式表达的派生度量。
- **[Perspective](https://documentation.atscale.com/container/creating-and-sharing-cubes/creating-cubes/modeling-perspectives/working-with-perspectives)** – 模型中可发布、暴露给特定角色或组的子集。AtScale 通过 perspective 控制调用者能看到哪些维度和度量。
- **[行安全（Row security）](https://documentation.atscale.com/container/creating-and-sharing-cubes/creating-cubes/modeling-row-security-objects)** – 一种模型对象，根据调用者的身份或属性筛选返回给调用者的行。
- **[自主聚合管理](https://documentation.atscale.com/container/managing-atscale/managing-aggregates) –** AtScale 观察各个消费者之间的查询模式，当某种模式的成本高到值得物化时，就在仓库中物化汇总表。后续命中该模式的查询会被透明地路由到聚合。
- **Design Center –** AtScale 的创作界面。建模者通过可视化画布或文本编辑器编辑 SML。无论哪种方式，磁盘上的产物都是 Git 中的 SML YAML。
- **[AtScale MCP server](https://documentation.atscale.com/container/connect-integrate/connecting-with-ai)** – 产品内置的 MCP 端点，位于 `<atscale-host>/mcp`，把语义模型暴露给任何 MCP 客户端。

在需要更多细节的地方，[AtScale 文档](https://documentation.atscale.com/container/atscale)和 [SML 规范](https://github.com/semanticdatalayer/SML)是权威参考。

## 参考架构

运行时分为入站路径和出站路径，形态与 Stardog 和 Denodo 那两篇一致。

**入站。** 客户端通过 AgentCore Gateway 把用户的问题发送给 Strands agent。Gateway 针对企业身份提供商（IdP）校验标识人类用户的 JSON Web Token（JWT），然后把请求路由到 [AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html)（Amazon Bedrock AgentCore 的一项能力），由后者托管 agent 进程。agent 调用 Amazon Bedrock 上的 Claude Sonnet 4.6 来解释 prompt 并规划查询。

**出站。** 当 agent 决定查询语义模型时，它向 AtScale MCP server 发起一次工具调用。AgentCore Gateway 充当出站代理：AtScale MCP server 在 Gateway 上注册为一个 MCP target，因此工具调用经由 Gateway 路由，并由 AgentCore Identity 在这一跳注入凭证。AtScale 的 MCP 端点接受两种凭证：bearer token（用于开发和单一身份场景），或由 AtScale 内置 Keycloak 实例签发的 OAuth 2.0 访问令牌（生产路径）。AtScale 引擎校验令牌，把调用者解析为某个 AtScale 角色，并针对已部署的 C360 模型规划查询。

查询请求向下穿过 AtScale 引擎，结果再向上返回。没有预先物化跨数据库连接的 ETL 作业。Amazon Redshift 中的分析副本是语义模型的事实来源，由上游复制路径从 Aurora 保持新鲜。

图 1：客户端、Amazon Bedrock AgentCore 各组件、AtScale MCP server、AtScale 引擎与 Amazon Redshift Serverless 之间的入站认证路径和出站查询路径

这套架构在身份处理上是刻意有主张的。Gateway 和 Identity 在运行时的边缘持有令牌。agent 看不到它们，只负责编排对话和工具调用。

## 构建语义层

AtScale 的语义模型是一组在 Git 中做版本控制的 SML 对象（数据集、维度、事实、度量、计算、perspective、行安全）。一个可用模型具有数据工程师能从星型 schema 认出来的形状，但每个对象都以 YAML 表达而不是数据定义语言（DDL），并且每个对象都是单独的文件。构建 C360 模型分三遍进行：在 Amazon Redshift 表之上的数据集、维度与层次结构及其间的连接，以及表达业务逻辑的度量与计算。

**数据集。** 每张 Amazon Redshift 表都变成一个 SML 数据集。数据集声明物理连接、schema、表，以及 AtScale 要暴露的列。数据集可以在 Design Center 中可视化创作，也可以直接作为 YAML 编辑。两种界面写入的是同一个 SML 文件到 Git。

**维度与层次结构。** C360 模型有七个维度。`dim_customer` 保存客户档案属性，并通过 location 键连接到 `dim_address`，通过 `cid` 连接到 `dim_rewards`。`dim_product` 保存产品属性，并通过 `dim_category` 把它们组织成一个层次结构。`dim_date` 支持基于日期的分析。`dim_vendor` 按供应商对产品分组。`dim_rewards` 为每个已注册客户保存一行，包含 `account_id` 和 `create_date`，并从 `dim_customer` 雪花开出，因此从未注册的客户在注册属性上呈现为空。

AtScale 的层次结构原语是产品到类别关系的简洁表达。针对模型的查询可以在没有递归 SQL 公共表表达式的情况下遍历 `product → category → parent category`，大语言模型（LLM）看到的是单条维度路径，而不是一张连接图。

产品层次结构的一个代表性 SML 片段：

```
# dim_product.yml
unique_name: dim_product
object_type: dimension
label: Product
hierarchies:
  - unique_name: product_category
    label: Product Category
    levels:
      - unique_name: department
        dataset: category
        key_columns: [dept_name]
      - unique_name: category
        dataset: category
        key_columns: [id]
      - unique_name: product
        dataset: product
        key_columns: [id]
secondary_attributes:
  - unique_name: brand
  - unique_name: product_name
    key_column: name
```

**事实与度量。** C360 的事实表是 `fact_purchase`，映射到 Amazon Redshift 的 purchase 表。它在 `cid` 上连接到 `dim_customer`，在 `pid` 上连接到 `dim_product`，在 `purchase_date` 上连接到 `dim_date`。度量来自事实：`total_revenue` 为 `SUM(price * quantity)`，`order_count` 为 `COUNT(id)`，`units_sold` 为 `SUM(quantity)`。

**计算度量。** 业务逻辑存在于模型中，而不是查询里。`customer_lifetime_value` 是在客户粒度上求值的 `total_revenue`，即同一个公式应用于事实的更粗切片。像 `big_spender` 和 `spend_tier` 这样的分段是带条件表达式的计算度量：

```
# big_spender.yml
unique_name: big_spender
object_type: metric
expression: |
  CASE WHEN SUM(price * quantity) > 10000
  THEN 'Yes' ELSE 'No' END
```

表达式在查询时求值。一个列只能在一个粒度上保存一个答案。表达式会针对查询所问的任何切片重新计算：按客户、按客户和年份，或按地区。当定义变化时（阈值从 $10,000 变为 $15,000），更新发生在一个 YAML 文件里，作为 pull request 接受评审，并通过 AtScale CI hook 部署。每个消费者在下一次查询时都会取到新定义，无论是 agent、走 XMLA 的 Excel，还是走多维表达式（MDX）的 Tableau。

部署之后，模型可以同时通过 SQL（面向基于 JDBC 的 BI 工具和 notebook）、XMLA（面向 Excel 和 Power BI）以及 MCP（面向 agent）访问。`total_revenue` 计算对 Claude Sonnet 4.6 返回的数字，与指向同一个 XMLA 端点的 Excel 数据透视表得到的数字相同。我们在验证一节确认了这一致性。

## AtScale 如何规划并下推查询

当 agent 针对语义模型提问时，由 AtScale 的 AI Computation Engine（ACE）负责规划。无论是来自 MCP `run_query` 工具的维度 SQL 请求，还是来自 Excel 的 XMLA 请求，查询经过的步骤都相同。只有前端的解析器不同。

以自动注册问题为例：*按生命周期消费额排名前 20 的客户中，哪些还没有加入奖励计划？* agent 在 `describe_model` 返回的模型上下文提示下，针对 C360 模型组合出一条维度 SQL 查询。ACE 把该查询解析为逻辑计划，把维度引用解析到底层的 `fact_purchase`、`dim_customer`、`dim_address` 和 `dim_rewards` 数据集，应用调用者所受的任何行安全策略，然后针对 Amazon Redshift 规划物理查询。

在物理规划阶段有两件事发生，使 AtScale 区别于手写流水线。第一，连接作为原生 SQL 连接下推到 Amazon Redshift，而不是在语义层中物化。Amazon Redshift 优化器看到的是一条带筛选和聚合的 SQL 语句，并据此执行。第二，AtScale 的聚合管理器在其注册表中检查是否存在匹配该查询模式的预构建聚合。如果存在按正确粒度以客户分组的购买的汇总表，AtScale 会重写查询去命中该聚合，而不是扫描 `fact_purchase`。查询返回所需的时间只是针对原始事实表的一小部分，而 agent 和建模者都不需要做任何手工路由工作。

![AtScale 规划器检查其聚合注册表，并把 agent 的查询重写为命中 Amazon Redshift 中的汇总表](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/14/ML-21303-4.png)

图 4：agent 的维度查询进入 AtScale 规划器。规划器检查其聚合注册表，找到与该查询模式匹配的聚合，重写查询以命中 Amazon Redshift 中的汇总表，并返回结果。下方路径展示同一个查询在没有匹配聚合时直接命中 fact_purchase

聚合管理器是让 agent 驱动的工作负载在经济上可行的关键。LLM 驱动的分析发出的查询比人类分析师更多，而像 *告诉我一些关于我们销售的有趣发现* 这样的开放式 prompt 可能催生十几条查询。AtScale 观察查询模式，在仓库本身（而不是独立的缓存）中物化聚合，并透明地路由匹配的查询。聚合的创建由需求定义，依据的是跨消费者的实际观察流量，而不只是 agent。

查询的审计记录同时捕获 LLM 写出的维度 SQL 和 AtScale 重写后的仓库原生 SQL，以及是否由聚合服务了该查询。操作者可以通过 Design Center 中的 [AtScale Queries 页面](https://documentation.atscale.com/container/managing-atscale/monitoring-queries/using-the-queries-tab)查看该记录，后面的治理一节正是建立在其之上。

## 关于多源与互操作性的一点说明

AtScale 通过 JDBC 连接数据仓库。C360 演练针对 Amazon Redshift Serverless。同一个 SML 模型在 Snowflake、Databricks 和 Google BigQuery 上同样可用，AtScale 为每一种都记录了连接方式。换连接时改变的是 AtScale 生成的 SQL 方言，而不是 Git 中的 SML。

有一个架构特性值得明确说明，因为它与本系列前两篇不同。单条 AtScale 查询只在一个仓库引擎内解析。如果 C360 模型跨两个仓库（比如维度在 Snowflake、事实在 Amazon Redshift），那么一条同时触及两者的查询必须以两种方式之一来调和。第一种是在上游，通过复制路径把分析副本整合到一个仓库中。第二种是借助仓库自身，使用引擎级的联邦能力，例如用 [Amazon Redshift Spectrum](https://docs.aws.amazon.com/redshift/latest/dg/c-using-spectrum.html) 查询 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/)，或者使用两个引擎都能读取的 [Apache Iceberg](https://iceberg.apache.org/) 表。AtScale 规划维度查询并把它下推到一个引擎。跨引擎的故事在更下一层。

这个选择有利有弊。它排除了 Stardog 和 Denodo 在查询时所做的实时跨引擎联邦，但让 AtScale 的规划器和聚合管理器得以在单引擎执行模型上工作，而这正是聚合这套能力在大规模下承载关键作用的原因。已经采用以仓库为中心、通过变更数据捕获（CDC）流水线从运营系统同步数据的企业，可以直接复用那套架构。而那些答案需要跨引擎实时联邦的企业，更适合前两篇文章中的语义层。

## 受治理访问：身份传播与运行时强制执行

Customer 360 数据是受监管的。部分用户（HR、反欺诈）需要看到社会保障号和卡号这类个人可识别信息。大多数用户（市场、数据分析）则不能。行级筛选按地理区域限制分析师，而按用户的审计轨迹必须从人类的浏览器一直保留到仓库。

AtScale 在语义层强制执行这些要求，在任何查询抵达仓库之前。无论调用者是经由 MCP 的 Strands agent、经由 XMLA 用 Excel 的分析师，还是经由 JDBC 的 notebook，强制执行都完全相同。SML 中的一个行安全对象、一个 perspective、一组角色绑定，应用于模型的每个消费者。

### 从用户到 AtScale 的身份传播

这条链的形状与 Denodo 那篇中的一致，只是最后一跳落在 AtScale 引擎而不是继续到仓库。

- 人类用户针对企业 IdP 向应用完成认证，并获得一个 JWT。
- 应用把该 JWT 作为 bearer token，经 AgentCore Gateway 转发给 Strands agent；Gateway 校验它（签发者、受众、签名）并把请求路由到 AgentCore runtime。
- 当 agent 向 AtScale MCP server 发起工具调用时，AgentCore Identity 提供由 AtScale 内置 Keycloak 签发的 OAuth 2.0 访问令牌，并映射到人类用户的身份。AtScale 的凭证不会进入 agent 代码。
- AtScale MCP server 接受该 OAuth token。AtScale 引擎针对 Keycloak 校验它，把调用者解析为某个 AtScale 角色，并在应用调用者的行安全约束和 perspective 绑定的情况下规划查询。访问仓库时使用来自 AWS Secrets Manager 的 AtScale 连接身份。

![从人类用户经 AgentCore Gateway、Runtime 和 Identity 到 AtScale MCP server 与引擎的身份链](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/14/ML-21303-5.png)

图 5：从人类用户经 AgentCore Gateway、AgentCore runtime、AgentCore Identity、AtScale MCP server 到 AtScale 引擎的身份链，终止于语义层的强制执行点。到仓库的一跳是使用 AtScale 凭证的服务账号连接

### RBAC、行安全与 perspective

AtScale 把访问控制表达为三个可组合的原语。RBAC 根据 Keycloak 声明为调用者分配角色。行安全是一个模型对象，根据调用者的身份或属性筛选返回给调用者的行。perspective 是模型中可发布、暴露给特定角色或组的子集。

对于 C360 演练，我们定义两个角色。

- `hr_user`：可以看到完整的 C360 模型，包括 `ssn` 和 `card_num`。
- `marketing_user`：可以看到 Marketing perspective，它在模型层隐藏了 `ssn` 和 `card_num`。

当 `marketing_user` 提出一个引用 `ssn` 的问题时，agent 的 `describe_model` 调用返回 Marketing perspective，其中不包含 `ssn`。agent 没有可投影的属性。行级筛选以同样的方式组合：一个按州限定客户范围的 SML 行安全对象，即可把调用者限制在特定的行集合内，而 agent 的 prompt 完全不需要改动。

### 审计保真度

通过 AtScale 引擎的查询会连同以下信息一起记录：调用者身份、模型、LLM 生成的维度 SQL、Amazon Redshift 实际看到的 AtScale 翻译后的下推 SQL、所应用的安全策略、是否由聚合服务了该查询，以及返回的行数。由于记录同时捕获了模型写出的查询和仓库执行的查询，审计者可以把一个答案从人类的问题一直追溯到产出该数字的 SQL。本系列的第一篇和第二篇都无法在一条记录中同时捕获两种形态的查询。

一条受治理查询的审计记录大致如下：

```
{
  "timestamp": "2026-08-31T10:34:56Z",
  "user_identity": "mary_major@example.com",
  "user_role": "marketing_user",
  "semantic_model": "Customer_360",
  "question": "Top 10 customers by revenue in California",
  "generated_sql": "SELECT full_name, total_revenue FROM ...",
  "translated_pushdown_sql": "SELECT ... FROM redshift ...",
  "security_policies_applied": ["regional_row_security"],
  "served_from": "aggregate",
  "execution_time_ms": 850,
  "rows_returned": 10
}
```

`generated_sql` 和 `translated_pushdown_sql` 这两个字段是让轨迹完整的关键：审计者既能看到 LLM 针对语义模型组合的查询，也能看到仓库实际执行的查询。

## 通过 AtScale MCP server 暴露该层

[AtScale MCP server](https://documentation.atscale.com/container/connect-integrate/connecting-with-ai)是 AtScale 发行版的一个组件，暴露在 `<atscale-host>/mcp`。它在 [AtScale C2026.7 版本](https://documentation.atscale.com/container/release-notes/C2026.7/new-features-and-improvements)中正式可用，并遵循标准的 [Model Context Protocol](https://modelcontextprotocol.io/)。任何兼容 MCP 的客户端（AgentCore runtime 中的 Strands agent、Claude、ChatGPT、Cursor、VS Code）都可以连接到同一个端点、访问同一个已部署模型。

server 暴露一组限定于查询语义模型的工具。AtScale 文档按版本发布工具参考。对 agent 驱动的工作负载最重要的工具是：

- `list_models`：枚举调用者可见的模型，并列出描述维度如何映射到事实的列组。
- `describe_model`：返回所选模型的维度、层次结构、度量、计算和业务描述。这就是 agent 系统提示词在开始组合查询之前所加载的负载。
- `search_columns`：对模型列做关键词搜索。当完整的 `describe_model` 负载会占用 LLM 上下文窗口过多时很有用。
- `validate_query`：在不针对仓库执行的情况下，检查一条维度 SQL 语句是否与模型兼容。这让 agent 可以在发出任何会被 Amazon Redshift 计费的东西之前，低成本地迭代查询。
- `run_query`：针对模型执行一条维度 SQL 语句并返回行。
- `run_queries`：批量执行多条语句，适用于 agent 并行发出若干探索性查询的开放式 prompt。
- `get_version`：报告 MCP server 版本，使客户端可以决定是否缓存模型 schema。

AtScale MCP 端点接受两种认证模式。**bearer-token** 路径使用从 Design Center 铸造的 API token。每个请求都以 token 所有者的身份运行，这条路径适合概念验证或单一身份的服务。**OAuth 2.0** 路径使用 AtScale 内置的 Keycloak，客户端预先配置，其 ID 恰为 `atscale-mcp`，记载在 AtScale 的 [Connecting with Claude](https://documentation.atscale.com/container/connect-integrate/connecting-with-ai/connect-ai-applications/claude) 页面。AgentCore Gateway 代表 agent 出示访问令牌，AtScale 引擎针对 Keycloak 校验它，下游的策略评估使用人类用户的身份。

把 AtScale MCP server 注册为 AgentCore Gateway target 遵循标准的 Gateway MCP target 流程。前面列出的工具对 agent 来说就是普通工具，由 AgentCore Identity 在 Gateway 这一跳处理凭证。

## 侧栏：用 AI 辅助建模扩展模型

AtScale MCP server 暴露的是限定于查询的工具，而 AtScale 一直在用创作侧工具扩展 MCP 面，让 agent 能探查仓库 schema、从源元数据生成候选 SML 模型、按规范校验 SML，并把结果提交到 Git。这种模式——agent 塑造语义模型而不仅仅是读取它——天然适合 Claude Code 和 Cursor 的工作流。在这些工作流中，数据工程师与 LLM 协作，在一个新数据集上引导出模型。

AtScale 把这一方向归为三项能力。**Semantic Discovery Engine** 扫描仓库 schema、查询历史和血缘，推断候选的连接、层次结构和度量定义。**Model Recommendation System** 根据观察到的查询模式建议维度、度量和关系。**Governed Feedback Loop** 把对 AI 建议的人工评审保留在 `SML-and-Git` 工作流中，使变更可版本化、可审计。

发布时点可用的具体工具有 AtScale MCP 工具参考文档记载。请查看[当前版本的 release notes](https://documentation.atscale.com/container/release-notes/C2026.7/new-features-and-improvements)以了解哪些已正式可用、哪些仍在预览。本文剩余部分讨论消费侧路径，即 agent 查询已部署的模型，这也是如今生产环境 C360 工作流所依赖的部分。

## 部署并运行 agent

[Strands Agents](https://docs.aws.amazon.com/prescriptive-guidance/latest/agentic-ai-frameworks/strands-agents.html)是一个用于构建 agent 的小型框架。一个简短的 Python 入口把 Amazon Bedrock 上的 Claude Sonnet 4.6 接到 AtScale MCP server 作为工具源。AgentCore runtime 托管该进程。AgentCore Gateway 终止入站请求，并通过 AgentCore Identity 持有出站的 AtScale 凭证。Amazon Bedrock 上基础模型的可用性因 AWS Region 而异。当前列表见[各模型的区域可用性](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。

系统提示词很重要。AtScale 文档和 AtScale 语料中的参考 demo 一致推荐 agent 采用三步调用模式：先 `list_models` 看有什么可用，再对目标模型调用 `describe_model` 把维度和度量加载进上下文，然后才 `run_query`（如果查询迭代成本高，先 `validate_query`）。理由在于 LLM 不应编造列名或度量名，而只应引用 `describe_model` 返回过的内容。系统提示词应明确说明这一点，并加入一小节关于目标模型业务术语的说明（`total_revenue` 指销售金额，不是件数），以便 agent 把用户问题映射到正确的度量。

为系统提示词中被复用的部分启用 [Amazon Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)。`describe_model` 的负载达数千 token，且在同一模型版本内不会变化，因此缓存它可降低重复调用时每次查询的 input token 成本。缓存点配置是 `BedrockModel` 对象上的一个请求参数。当前参数名请参见 Strands 文档。

## 验证

为确认语义层、agent 和身份流按预期工作，我们通过 agent 运行了三个查询，然后在另一个角色下对其中一个做了治理复跑。以下行为应当能在可用的部署中复现。

### 查询 1，单维度

*列出我们在威斯康星州的客户及其所在城市。*

agent 针对 C360 模型生成一条维度 SQL 查询，从 `dim_customer` 和 `dim_address` 中选择 `first_name`、`last_name` 和 `city`，条件为 `state = 'WI'`。AtScale 的规划器把维度路径解析到 Amazon Redshift 中的 `customer` 和 `address` 表，下推一条 SQL 语句并返回行。

### 查询 2，带聚合命中的聚合

*按销量计算，我们的前 10 个产品是什么？*

agent 按产品聚合 `units_sold` 并按降序排序。AtScale 的聚合管理器找到一个匹配的[需求定义聚合](https://documentation.atscale.com/container/managing-atscale/managing-aggregates/about-aggregates/when-the-atscale-engine-creates-demand-defined-aggregates)，把查询重写为命中 Amazon Redshift 中的汇总表，而不是扫描 `fact_purchase`。Queries 页面并排显示 LLM 生成的维度 SQL 和聚合路由后的仓库 SQL。

### 查询 3，跨域

*按生命周期消费额排名前 20 的客户中，哪些还没有加入奖励计划？*

agent 生成一条连接 `dim_customer`、`dim_address`、`dim_rewards` 和 `fact_purchase` 的查询，并按客户聚合 `customer_lifetime_value`。查询限定 `dim_rewards.account_id` 为空的客户。在 `cid` 上对 `dim_customer` 的左连接保留了从未注册的客户，他们在注册记录上呈现为空。agent 返回按生命周期消费额排序的前 20 名。AtScale 的规划器把这些连接解析为针对 Amazon Redshift 的原生 SQL，并返回排名列表。`customer_lifetime_value` 的公式不是 LLM 需要自己发明的。它是在 `customer_lifetime_value.yml` 中定义一次、并在查询中按名称引用的计算度量。

### 治理复跑

我们以两个不同的调用者身份运行查询 1 的一个变体，在投影中加入 `ssn`（*给我看看我们在威斯康星州的客户及其 SSN*）。作为 `hr_user`，`describe_model` 返回完整的 C360 模型，agent 组合查询，结果集包含 SSN 值。作为 `marketing_user`，`describe_model` 返回 Marketing perspective，其中不暴露 `ssn`。agent 没有可投影的属性，因此返回一个不含 SSN 的答案。两次运行之间除了调用者身份之外没有任何变化。查询文本、agent 代码、MCP server、AtScale 引擎和 Amazon Redshift 都未被改动。

### 跨消费者确认

我们通过 AtScale XMLA 端点在 Excel 中打开同一个 C360 模型，把 `Customer.State` 和 `Total Revenue` 拖到数据透视表上。州级总计与 agent 针对等价问题返回的结果完全一致，精确到数字。

## 扩展到更多数据源

为 C360 模型新增一个数据源是建模工作，而不是集成工作。假设客户支持团队要求模型包含工单量，以便 agent 能回答 *我们的哪些高消费客户在过去 30 天内提交了支持工单？* 步骤是：

- 使用与运营表相同的复制模式，把支持工单数据落到 Amazon Redshift，与其他 C360 表放在一起。
- 新增一个 SML 数据集，把新表映射到一个逻辑对象。
- 新增或扩展一个维度（`dim_ticket`），并在 `cid` 上加入与 `dim_customer` 的连接。
- 加入模型需要的任何新度量（`open_ticket_count`、`avg_resolution_time`）。
- 提交 SML 变更，作为 pull request 评审，并通过 AtScale CI hook 部署。

agent 代码和 AgentCore 配置都不需要改动。agent 下一次调用 `describe_model` 时，就会看到新的维度和度量，并能针对它们组合问题。同样的模式适用于不同的仓库。如果数据源落在 Snowflake 或 Databricks 而不是 Amazon Redshift，连接就是一个带 Snowflake 或 Databricks 连接的新 SML 数据集，查询会按前面多源说明所述的在该引擎内解析。

## 部署：Amazon EKS 上的 AtScale

AtScale 运行在 Kubernetes 上，AWS 上的参考部署是 [Amazon EKS](https://aws.amazon.com/eks/)。AtScale 在 `oci://docker.io/atscaleinc/atscale` 提供[官方 Helm chart](https://documentation.atscale.com/container/installation-guides/kubernetes/installing-atscale)，[AtScale K8S Blueprints](https://github.com/AtScaleInc/atscale-k8s-blueprints) 仓库则提供基础设施即代码（IaC）脚手架，用于搭起一个包含 AtScale 所需组件的 EKS 集群：一个 ingress controller、一个用于 AtScale 元数据库的持久存储、一个用于查询缓存的 Redis 实例，以及一个为身份联邦配置好的 AtScale Keycloak 实例。

EKS 上的 AtScale 部署运行在一小组 Kubernetes pod 上。`atscale-engine` 是核心的查询规划器与执行器。`atscale-mcp-server` 是 agent 对话的 MCP 端点。`atscale-keycloak` 是内置的身份提供商，联邦到 Amazon Cognito、Okta、Azure Active Directory 以及其他符合 OpenID Connect（OIDC）的 IdP。辅助 pod 负责 SML API 与 Design Center UI（`atscale-sml-api`、`atscale-sml-web`）、PostgreSQL 元数据存储（`atscale-db`）、查询缓存（`atscale-redis`）以及 ingress（`atscale-ingress`，通常前置一个 AWS Network Load Balancer）。

C360 应用（一个聊天 UI，或调用 agent 的客户端库）可以在同一个 EKS 集群中以自己的 namespace 运行。它使用 [IAM role for service account（IRSA）](https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html)访问 Bedrock 和 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/)，而无需内嵌凭证。

网络是标准做法：AtScale 通过虚拟私有云（VPC）端点或一条允许 AtScale namespace 出站到 Amazon Redshift 的安全组规则访问 Amazon Redshift，人类用户则通过 ingress 负载均衡器访问应用。

除自管理的 EKS 之外，AtScale 还提供云部署选项。当前的产品与 AWS 可用性请查看 [AtScale 网站](https://www.atscale.com/)。本文剩余部分假定采用前面描述的自管理模式。

## 结论

agentic 访问企业数据需要三样东西协同工作：一个能规划并生成查询的基础模型、一个在实时仓库之上计算受治理且具业务含义答案的语义层，以及一个托管 agent 并管理身份流的运行时。Amazon Bedrock、AtScale 和 Amazon Bedrock AgentCore 各自承担其中一个角色。

agent 与语义层对话，而不直接与仓库对话。维度、层次结构、度量、perspective 和行安全都以 SML 存在 Git 中。当 schema 漂移或治理规则变化时，更新发生在一个文件里，每个消费者（agent、Excel、Tableau、Power BI）在下一次查询时就会取到。

### 从哪里入手

大多数把这件事做成的团队都是从小处开始，然后扩展。

- 挑一个横跨两到三个数据源、如今回答起来比应有的时间更长的流程。
- 写下该流程需要回答的 3–5 个问题。这些就是语义层在第一天上必须支持的查询。
- 使用 [AWS Database Migration Service](https://aws.amazon.com/dms/) 或 [Amazon Aurora zero-ETL](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/zero-etl.html) 把运营数据整合进 Amazon Redshift（或你选择的仓库）。
- 在 Design Center 中从仓库 schema 引导出 SML，再针对能力问题（competency questions）精炼它。
- 用 AtScale Helm chart 和 AtScale K8S Blueprints 在 Amazon EKS 上部署 AtScale，把 AtScale MCP server 注册为 AgentCore Gateway target，并通过它接入一个 Strands agent。
