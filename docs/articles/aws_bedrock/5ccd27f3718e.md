# 使用 AtScale 和 Amazon Bedrock AgentCore 在 AWS 上构建代理 AI 语义层

在[本系列的第一篇文章](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/)中，我们使用Stardog的知识图在[Amazon Aurora](https://aws.amazon.com/rds/aurora/)和[Amazon]上构建了一个语义层。 Redshift](https://aws.amazon.com/redshift/)。我们针对该层在 [Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/) 上运行了 [Strands](https://docs.aws.amazon.com/prescriptive-guidance/latest/agentic-ai-frameworks/strands-agents.html) 代理。 [第二篇文章](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-denodo-and-amazon-bedrock-agentcore/) 保留了相同的客户 360 (C360) 模式并交换到 Denodo 的数据虚拟化平台中，扩展了源组合以包含本地 PostgreSQL 集群。这篇文章再次使用相同的 C360 模式，以 [AtScale](https://www.atscale.com/) 作为语义层。

AtScale 的形状与前两者不同。语义模型是维度的（维度、层次结构和度量），而不是三元组图或一组视图。 AtScale 使用 [语义建模语言](https://github.com/semanticdatalayer/SML) 创建模型，这是一种在 Git 中版本化的基于 YAML 的开放规范，并通过单个部署的模型通过三种协议同时公开它：SQL、XML for Analysis (XMLA) 和模型上下文协议 (MCP)。企业已经使用的 Strands 代理和商业智能 (BI) 工具根据相同的定义获得相同的计算答案。

该模式的其余部分继承了之前的帖子。 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的基础模型（用于演练的 Anthropic Claude Sonnet 4.6）计划并编写查询。 Amazon Bedrock AgentCore 托管 Strands 代理并管理代理向 AtScale 提供的出站凭证。应用于调用者的连接、度量定义以及行和列过滤器位于语义层而不是提示内。

我们假设您熟悉本系列第一篇文章中的语义层架构：什么是语义层、它的用途以及为什么模型在不拥有连接的情况下计划查询。如果其中有任何新内容，第一篇文章将介绍基础知识。

读完这篇文章后，您将了解：

- 如何使用语义建模语言 (SML) 对 C360 域进行建模：数据集、维度和层次结构、事实、度量、计算度量和视角，在 Git 中进行版本控制。
- AtScale 如何针对 Amazon Redshift 规划维度查询，以及 AtScale 的自主聚合管理如何加速代理生成的查询模式。
- 如何通过 AtScale MCP 服务器向 AgentCore 托管的 Strands 代理公开模型，以及如何使用 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)（Amazon Bedrock AgentCore 的一项功能）注册该 MCP 服务器。
- 人类用户的身份如何通过 [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) Amazon Bedrock AgentCore 的功能从企业身份提供商传播到 AtScale，以及 AtScale 如何在查询时实施基于角色的访问控制 (RBAC)、行安全性和视角。
- 如何使用 AtScale Helm 图表和 [AtScale K8S 蓝图](https://github.com/AtScaleInc/atscale-k8s-blueprints) 存储库在 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/) 上部署 AtScale。

本演练的事实来源是 [AtScale C2026.7 版本](https://documentation.atscale.com/container/release-notes/C2026.7)。在适用特定工具名称或端点的情况下，我们引用 [AtScale 文档](https://documentation.atscale.com/container/atscale)。

## 示例：Amazon Redshift 上的 Customer 360

前两篇文章中的客户 360 度模式保持不变。零售企业的客户记录、订单、产品和奖励登记分布在各个系统中，业务用户希望在不知道哪个系统保存哪个事实的情况下提出交叉问题。我们为该系列第一篇文章改编的 [Stardog C360 知识工具包](https://github.com/stardog-union/knowledge-kits/tree/main/examples/c360) 对该场景进行了建模，其中客户、订单、产品和地址实体连接在整数“cid”上，该整数在客户表中显示为主键，在购买表中显示为普通列。

这篇文章与前两篇文章的不同之处在于数据的物理位置。 Stardog 和 Denodo 在查询时跨两个引擎进行联合。 AtScale 将维度查询规划为原生仓库 SQL，并将每个查询推送到一个引擎，因此跨引擎数据在上游得到整合。在本演练中，所有分析 C360 数据都位于 [Amazon Redshift Serverless](https://aws.amazon.com/redshift/redshift-serverless/) 中。 Amazon Aurora PostgreSQL 仍然是记录操作系统，复制路径（[AWS Database Migration Service](https://aws.amazon.com/dms/) 或 [Amazon Aurora 零 ETL 到 Amazon Redshift](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/zero-etl.html)）使分析副本保持最新状态。该代理查询映射到 Amazon Redshift 表的单个 AtScale 模型。

Amazon Redshift 中的架构：

| **表** | **关键栏目** |
| --- | --- |
|客户| cid (PK)、名字、姓氏、电子邮件、ssn、电话、位置 |
|地址 | id (PK)、城市、州、邮政编码、街道名称 |
|信用卡 | id (PK)、cid、card_num、card_type |
|奖励帐户 | id (PK)、cid、account_id、create_date |
|购买| id (PK)、pid、购买日期、数量、价格、cid、卡 |
|产品 | id (PK)、名称、品牌、价格、部门 |
|类别 | id (PK)、部门名称、父级 |
|供应商 | id (PK)、供应商名称、行业 |

八个表中的九个感兴趣的列。 “cid”将客户记录与购买联系起来。 `pid` 将购买链接到产品。 “dept”将产品链接到类别。所有分析都在 Amazon Redshift 中进行，因此连接会下推到本机 SQL，而不是在语义层或提取、转换和加载 (ETL) 管道中解析。

运用整个模型的一个代表性问题：*按终身支出计算，我们的前 20 位客户中哪些尚未注册奖励计划？*这是 Denodo 帖子中的自动注册问题，保留下来，以便关注该系列的读者可以看到不同语义层回答的相同请求。它涉及客户资料、地址、购买历史记录和注册状态：每个客户跨四个逻辑实体一行。

## 本文中使用的 AtScale 术语

AtScale 将语义层实现为仓库上的维度模型。 AtScale 文档和 SML 规范使用本文中出现的一组特定原语。在我们开始演练之前，简短的参考很有用。

- **语义建模语言 (SML) –** 一种基于 YAML 的开放规范，用于描述语义模型。每个 SML 对象（模型、数据集、维度、层次结构、指标、计算、透视图、行安全性）都是一个 YAML 文件。该规范位于 [github.com/semanticdatalayer/SML](https://github.com/semanticdatalayer/SML)。
- **模型 –** 顶级工件。模型引用数据集、维度、事实和指标，并通过 AtScale 查询引擎公开它们。
- **维度和层次结构 –** 维度对相关属性（客户、产品、日期）进行分组。维度内的层次结构将这些属性组织为级别（产品 → 类别 → 部门，或年 → 季度 → 月 → 日）。
- **事实和度量 –** 事实是一个数据集，其中包含连接到关键列上的维度的可度量事件。度量是从事实列聚合的数量，例如收入的“SUM(价格 * 数量)”。
- **计算 –** 相对于其他度量以公式表示的派生度量。
- **[Perspective](https://documentation.atscale.com/container/creating-and-sharing-cubes/creating-cubes/modeling-perspectives/working-with-perspectives)** – 向特定角色或组公开的模型的可发布子集。视角是 AtScale 如何控制调用者可以看到哪些维度和度量的方式。
- **[Row security](https://documentation.atscale.com/container/creating-and-sharing-cubes/creating-cubes/modeling-row-security-objects)** – 根据调用者的身份或属性过滤返回给调用者的行的模型对象。
- **[自主聚合管理](https://documentation.atscale.com/container/managing-atscale/managing-aggregates) –** AtScale 会监视消费者之间的查询模式，并在某个模式的成本足以证明其合理性时在仓库中具体化汇总表。与模式匹配的后续查询透明地路由到聚合。
- **设计中心 –** AtScale 创作界面。建模者通过可视画布或文本编辑器编辑 SML。无论哪种方式，磁盘上的工件都是 Git 中的 SML YAML。
- **[AtScale MCP 服务器](https://documentation.atscale.com/container/connect-integrate/connecting-with-ai)** – “<atscale-host>/mcp”处的产品内 MCP 端点，可向任何 MCP 客户端公开语义模型。

如果需要更多详细信息，[AtScale 文档](https://documentation.atscale.com/container/atscale) 和 [SML 规范](https://github.com/semanticdatalayer/SML) 是权威参考。

## 参考架构

运行时分为入站路径和出站路径，遵循与 Stardog 和 Denodo 帖子相同的形状。

**入站。** 客户端通过 AgentCore Gateway 将用户的问题发送到 Strands 代理。 Gateway 根据企业身份提供商 (IdP) 验证用于识别人类用户的 JSON Web 令牌 (JWT)，然后将请求路由到托管代理进程的 [AgentCore 运行时](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html)（Amazon Bedrock AgentCore 的一项功能）。该代理在 Amazon Bedrock 上调用 Claude Sonnet 4.6 来解释提示并规划查询。

**出站。** 当代理决定查询语义模型时，它会调用 AtScale MCP 服务器的工具。 AgentCore Gateway 充当出站代理：AtScale MCP 服务器在 Gateway 上注册为 MCP 目标，因此工具调用通过 Gateway 的路由，AgentCore Identity 会在该跃点注入凭证。 AtScale 的 MCP 端点接受不记名令牌（用于开发和单一身份场景）或由 AtScale 的捆绑 Keycloak 实例（生产路径）颁发的 OAuth 2.0 访问令牌。 AtScale 引擎验证令牌，将调用者解析为 AtScale 角色，并针对已部署的 C360 模型规划查询。

查询请求通过 AtScale 引擎向下传输，结果向上传输。没有预先具体化跨数据库连接的 ETL 作业。 Amazon Redshift 中的分析副本是语义模型的真实来源，通过上游复制路径从 Aurora 保持最新状态。

该建筑刻意强调身份。网关和身份在运行时边缘保存令牌。代理看不到它们，只会协调对话和工具调用。

## 构建语义层

AtScale 的语义模型是在 Git 中版本化的 SML 对象（数据集、维度、事实、度量、计算、视角、行安全性）的集合。工作模型具有数据工程师可以从星型模式中识别的形状，但每个对象都表示为 YAML 而不是数据定义语言 (DDL)，并且每个对象都是一个单独的文件。构建 C360 模型分三遍：Amazon Redshift 表上的数据集、维度和层次结构以及它们之间的联接，以及表达业务逻辑的度量和计算。

**数据集。** 每个 Amazon Redshift 表都会成为一个 SML 数据集。数据集声明 AtScale 将显示的物理连接、架构、表和列。数据集可以在设计中心直观地创作，也可以直接作为 YAML 进行编辑。任一表面都将相同的 SML 文件写入 Git。

**维度和层次结构。** C360 模型有七个维度。 `dim_customer` 保存客户个人资料属性，并通过位置键连接到 `dim_address` 并通过 `cid` 连接到 `dim_rewards`。 `dim_product` 保存产品属性并通过 `dim_category` 将它们组织成层次结构。 `dim_date` 支持基于日期的分析。 `dim_vendor` 按供应商对产品进行分组。 “dim_rewards”为每个注册客户保留一行“account_id”和“create_date”，并从“dim_customer”中雪花化，以便从未注册的客户在注册属性中显示为空。

AtScale 的层次结构原语是产品与类别关系的简洁表达。针对模型的查询可以导航“产品 → 类别 → 父类别”，无需递归 SQL 公共表表达式，并且大型语言模型 (LLM) 看到的是单维路径而不是连接图。

产品层次结构的代表性 SML 片段：
```
# dim_product.yml
unique_name: dim_product
object_type: dimension
label: Product
hierarchies:
  - unique_name: product_category
    label: Product Category
    levels:
      - unique_name: department
        dataset: category
        key_columns: [dept_name]
      - unique_name: category
        dataset: category
        key_columns: [id]
      - unique_name: product
        dataset: product
        key_columns: [id]
secondary_attributes:
  - unique_name: brand
  - unique_name: product_name
    key_column: name
```
**事实和度量。** C360 的事实表是“fact_purchase”，映射到 Amazon Redshift 购买表。它连接到“cid”上的“dim_customer”、“pid”上的“dim_product”以及“purchase_date”上的“dim_date”。衡量标准基于以下事实：“total_revenue”为“SUM(price *Quantity)”，“order_count”为“COUNT(id)”，“units_sold”为“SUM(quantity)”。

**计算的度量。** 业务逻辑存在于模型中而不是查询中。 “customer_lifetime_value”是根据客户粒度评估的“total_revenue”，相同的公式适用于更粗略的事实。像“big_spender”和“spend_tier”这样的分段是使用条件表达式计算的度量：
```
# big_spender.yml
unique_name: big_spender
object_type: metric
expression: |
  CASE WHEN SUM(price * quantity) > 10000
  THEN 'Yes' ELSE 'No' END
```
该表达式在查询时计算。一列可以容纳一粒的一个答案。该表达式会针对查询询问的任何切片（按客户、按客户和年份或按地区）重新计算。当定义发生更改（阈值从 10,000 美元变为 15,000 美元）时，更新会在一个 YAML 文件中进行，作为拉取请求进行审核，并通过 AtScale CI 挂钩进行部署。每个使用者都会在下一个查询中选择新的定义，无论是代理、基于 XMLA 的 Excel，还是基于多维表达式 (MDX) 的 Tableau。

## AtScale 如何规划和下推查询

当代理针对语义模型提出问题时，AtScale 的人工智能计算引擎 (ACE) 会进行规划。对于来自 MCP“run_query”工具的维度 SQL 请求和来自 Excel 的 XMLA 请求，查询所经历的步骤是相同的​​。只有前面的解析器不同。

以自动注册问题为例：*按终身支出计算，前 20 位客户中哪些尚未注册奖励计划？* 代理根据“describe_model”返回的模型上下文进行提示，针对 C360 模型编写维度 SQL 查询。 ACE 将该查询解析为逻辑计划，解析对底层“fact_purchase”、“dim_customer”、“dim_address”和“dim_rewards”数据集的维度引用，应用调用者须遵守的任何行安全性，然后计划针对 Amazon Redshift 的物理查询。

在物理规划阶段发生的两件事将 AtScale 与手写管道分开。首先，连接作为本机 SQL 连接推送到 Amazon Redshift，而不是在语义层中具体化。 Amazon Redshift 优化器会看到带有过滤器和聚合的单个 SQL 语句，并相应地执行它。其次，AtScale 的聚合管理器检查其注册表中是否有与查询模式匹配的预构建聚合。如果存在按正确粒度对客户购买进行分组的汇总表，则 AtScale 会重写查询以进行聚合，而不是扫描“fact_purchase”。查询返回的时间只是原始事实表所需时间的一小部分，而无需代理或建模者执行任何手动工作来路由它。

![AtScale 规划器检查其聚合注册表并重写代理的查询以命中 Amazon Redshift 中的汇总表](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/14/ML-21303-4.png)

图 4：代理的维度查询进入 AtScale 规划器。规划器检查其聚合注册表，找到查询模式的匹配聚合，重写查询以命中 Amazon Redshift 中的汇总表，然后返回结果。下面的路径显示相同的查询，但没有匹配的聚合直接命中fact_purchase

聚合管理器使代理驱动的工作负载在经济上可行。 LLM 驱动的分析比人类分析师会引发更多的查询，而像“告诉我一些关于我们销售的有趣的事情”这样的开放式提示可能会产生十几个。 AtScale 监视查询模式，在仓库本身（而不是单独的缓存）中具体化聚合，并透明地路由匹配的查询。聚合创建是根据消费者（而不仅仅是代理）观察到的流量按需定义的。

查询的审计记录捕获 LLM 编写的维度 SQL 和 AtScale 重写的仓库本机 SQL，以及聚合是否为查询提供服务。操作员可以通过设计中心的 [AtScale 查询页面](https://documentation.atscale.com/container/managing-atscale/monitoring-queries/using-the-queries-tab) 获取该记录，这也是以下治理部分的基础。

## 关于多源和互操作性的说明

AtScale 通过 JDBC 连接到仓库。 C360 演练针对的是 Amazon Redshift Serverless。相同的 SML 模型适用于 Snowflake、Databricks 和 Google BigQuery，并且 AtScale 记录了每种模型的连接模式。交换连接时发生的变化是 AtScale 发出的 SQL 方言，而不是 Git 中的 SML。

有一个架构属性值得明确说明，因为它与本系列的前两篇文章不同。单个 AtScale 查询在一个仓库引擎中解析。如果 C360 模型跨越两个仓库（例如 Snowflake 上的维度、Amazon Redshift 上的事实），则必须通过两种方式之一协调涉及这两个仓库的查询。第一个是上游，通过复制路径将分析副本合并到一个仓库中。第二种是由仓库本身使用引擎级联合，例如 [Amazon Redshift Spectrum](https://docs.aws.amazon.com/redshift/latest/dg/c-using-spectrum.html) 来查询两个引擎都可以读取的 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 或 [Apache Iceberg](https://iceberg.apache.org/) 表。 AtScale 规划维度查询并将其推送到一个引擎。跨引擎的故事存在于下一层。

这个选择是双向的。它排除了 Stardog 和 Denodo 在查询时执行的实时跨引擎联合，但它让 AtScale 的规划器和聚合管理器针对单引擎执行模型工作，这使得聚合故事能够大规模承载。已经运行以仓库为中心的分析架构以及来自操作系统的变更数据捕获 (CDC) 管道的企业可以重用该架构。前两篇文章中的语义层可以更好地为那些答案需要跨引擎实时联合的企业提供服务。

## 受控访问：身份传播和运行时强制

Customer 360 数据受到监管。某些用户（人力资源、欺诈）需要查看个人身份信息，例如社会安全号码和卡号。大多数用户（营销、分析）不得这样做。行级过滤器按地理位置限制分析师，并且每个用户的审计跟踪必须保留从人类浏览器一直到仓库的过程。

在任何查询到达仓库之前，AtScale 在语义层强制执行这些要求。无论调用者是通过 MCP 的 Strands 代理、通过 XMLA 的 Excel 中的分析师，还是通过 JDBC 的笔记本，执行过程都是相同的。 SML 中的一个行安全对象、一个视角、一组角色绑定，应用于模型的每个使用者。

### 从用户到 AtScale 的身份传播

该链条的形状与 Denodo 邮局的形状相同，终点站降落在 AtScale 引擎上，而不是继续到达仓库。

- 人员根据企业 IdP 对应用程序进行身份验证并接收 JWT。
- 应用程序通过 AgentCore Gateway 将 JWT 作为不记名令牌转发到 Strands 代理，后者验证它（颁发者、受众、签名）并将请求路由到 AgentCore 运行时。
- 当代理对 AtScale MCP 服务器进行工具调用时，AgentCore Identity 提供由 AtScale 捆绑的 Keycloak 颁发的 OAuth 2.0 访问令牌，映射到人类用户的身份。 AtScale 凭证不输入代理代码。
- AtScale MCP 服务器接受 OAuth 令牌。 AtScale 引擎根据 Keycloak 对其进行验证，将调用者解析为 AtScale 角色，并使用调用者的行安全约束和应用的透视绑定来规划查询。使用来自 AWS Secrets Manager 的 AtScale 连接身份访问仓库。

![从人类用户通过 AgentCore 网关、运行时和身份到 AtScale MCP 服务器和引擎的身份链](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/14/ML-21303-5.png)

图 5：从人类用户到 AgentCore 网关、AgentCore 运行时、AgentCore 身份、AtScale MCP 服务器和 AtScale 引擎的身份链，终止于语义层执行点。仓库跃点是具有 AtScale 凭证的服务帐户连接

### RBAC、行安全性和视角

AtScale 将访问控制表示为三个可组合原语。 RBAC 根据 Keycloak 声明为调用者分配角色。行安全性是一个模型对象，它根据调用者的身份或属性过滤返回给调用者的行。透视图是向特定角色或组公开的模型的可发布子集。

对于 C360 演练，我们定义了两个角色。

- `hr_user`：查看完整的 C360 模型，包括 `ssn` 和 `card_num`。
- `marketing_user`：查看 Marketing 视角，在模型层隐藏了 `ssn` 和 `card_num`。

当“marketing_user”询问引用“ssn”的问题时，代理的“describe_model”调用将返回“营销”视角，该视角不包含“ssn”。代理没有项目属性。行级过滤器的组成方式相同：按状态划分客户范围的 SML 行安全对象将调用者限制为特定的行集，而不会对代理的提示进行任何更改。

### 审计保真度

通过 AtScale 引擎进行的查询会记录调用者的身份、模型、LLM 生成的维度 SQL、Amazon Redshift 看到的 AtScale 翻译的下推 SQL、应用的安全策略、聚合是否为查询提供服务以及返回的行数。由于记录捕获了模型编写的查询和仓库执行的查询，因此审核员可以跟踪从人类问题到生成数字的 SQL 的答案。本系列的第一篇文章和第二篇文章都没有在一条记录中捕获这两种形式的查询。

受管查询的审核记录如下所示：
```
{
  "timestamp": "2026-08-31T10:34:56Z",
  "user_identity": "mary_major@example.com",
  "user_role": "marketing_user",
  "semantic_model": "Customer_360",
  "question": "Top 10 customers by revenue in California",
  "generated_sql": "SELECT full_name, total_revenue FROM ...",
  "translated_pushdown_sql": "SELECT ... FROM redshift ...",
  "security_policies_applied": ["regional_row_security"],
  "served_from": "aggregate",
  "execution_time_ms": 850,
  "rows_returned": 10
}
```
` generated_sql` 和 `translated_pushdown_sql` 字段是使跟踪完整的字段：审核员可以看到 LLM 根据语义模型编写的查询和仓库实际运行的查询。

## 通过 AtScale MCP 服务器公开该层

[AtScale MCP 服务器](https://documentation.atscale.com/container/connect-integrate/connecting-with-ai) 是 AtScale 发行版的一个组件，在“<atscale-host>/mcp”中公开。它通常在 [AtScale C2026.7 版本](https://documentation.atscale.com/container/release-notes/C2026.7/new-features-and-improvements) 中提供，并采用标准 [模型上下文协议](https://modelcontextprotocol.io/)。任何 MCP 兼容客户端（AgentCore 运行时中的 Strands 代理、Claude、ChatGPT、Cursor、VS Code）都可以针对同一部署模型连接到同一端点。

服务器公开了一组用于查询语义模型的工具。 AtScale 文档针对每个版本发布了工具参考。对于代理驱动的工作负载而言，重要的工具包括：

- `list_models`：枚举调用者可以看到的模型，以及描述维度如何映射到事实的列组。
- `describe_model`：返回所选模型的维度、层次结构、度量、计算和业务描述。这是代理的系统提示在开始编写查询之前加载的有效负载。
- `search_columns`：对模型列进行关键字搜索。当完整的“describe_model”有效负载会使用过多的 LLM 上下文窗口时很有用。
- `validate_query`：检查维度 SQL 语句是否与模型兼容，而不针对仓库执行它。这使得代理可以在触发任何 Amazon Redshift 计费之前以较低的成本迭代其查询。
- `run_query`：针对模型执行维度 SQL 语句并返回行。
- `run_queries`：批量运行多个语句，对于代理并行触发多个探索性查询的开放式提示很有用。
- `get_version`：报告 MCP 服务器版本，以便客户端可以决定是否缓存模型架构。

AtScale MCP 端点接受两种身份验证模式。 **不记名令牌**路径使用从设计中心铸造的 API 令牌。每个请求都以令牌所有者的身份运行，并且此路径适合概念验证或单一身份服务。 **OAuth 2.0** 路径使用 AtScale 的捆绑 Keycloak 和预配置客户端，其 ID 正是“atscale-mcp”，记录在 AtScale [与 Claude 连接](https://documentation.atscale.com/container/connect-integrate/connecting-with-ai/connect-ai-applications/claude) 页面上。 AgentCore Gateway 代表代理提供访问令牌，AtScale 引擎根据 Keycloak 对其进行验证，下游策略评估使用人类用户的身份。

将 AtScale MCP 服务器注册为 AgentCore 网关目标遵循标准网关 MCP 目标流程。前面列出的工具对于代理来说就像普通工具，AgentCore Identity 在网关跃点处理凭证。

## 侧边栏：通过 AI 辅助建模扩展模型

AtScale MCP 服务器公开了查询范围内的工具，AtScale 一直在使用作者端工具扩展 MCP 表面，这些工具让代理能够内省仓库模式、从源元数据生成候选 SML 模型、根据规范验证 SML，并将结果提交到 Git。在这种模式中，代理塑造语义模型而不仅仅是从中读取，非常适合 Claude Code 和 Cursor 工作流程。在这些工作流程中，数据工程师与法学硕士合作，在新数据集上引导模型。

AtScale 将此方向分为三个功能。 **语义发现引擎**扫描仓库架构、查询历史记录和沿袭，以推断候选连接、层次结构和指标定义。 **模型推荐系统** 根据观察到的查询模式建议维度、度量和关系。 **受控反馈循环**在“SML-and-Git”工作流程中对人工智能建议进行人工审查，因此更改是版本化且可审核的。

发布时可用的特定工具记录在 AtScale MCP 工具参考中。检查[当前发行说明](https://documentation.atscale.com/container/release-notes/C2026.7/new-features-and-improvements)，了解一般可用的内容和仍处于预览状态的内容。本文的其余部分将介绍消费者路径，即代理查询已部署的模型，这是当今生产 C360 工作流程所依赖的。

## 部署并运行代理

[Strands Agents](https://docs.aws.amazon.com/prescriptive-guidance/latest/agentic-ai-frameworks/strands-agents.html) 是一个用于构建代理的小型框架。一个简短的 Python 入口点将 Amazon Bedrock 上的 Claude Sonnet 4.6 连接到 AtScale MCP 服务器作为工具源。 AgentCore 运行时托管该进程。 AgentCore Gateway 终止入站请求并通过 AgentCore Identity 保存出站 AtScale 凭证。 Amazon Bedrock 上的基础模型可用性因 AWS 区域而异。有关当前列表，请参阅[按型号划分的区域可用性](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。

系统提示很重要。 AtScale 文档和 AtScale 语料库中的参考演示一致推荐代理采用三步调用模式：“list_models”以查看可用内容，然后在目标模型上使用“describe_model”将维度和度量加载到上下文中，然后只有“run_query”（或首先“validate_query”，如果查询迭代成本较高）。原因是法学硕士不应该伪造列名称或指标名称。它应该仅引用 `describe_model` 返回的内容。系统提示应明确说明，并且应包含有关目标模型中业务术语的一小部分（“total_revenue”表示销售额，而不是单位），以便代理将用户问题映射到正确的度量。

为系统提示的重用部分启用 [Amazon Bedrock 提示缓存](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)。 “describe_model”有效负载运行数千个令牌，并且在模型版本内不会更改，因此对其进行缓存会降低重复调用时每个查询的输入令牌成本。缓存点配置是“BedrockModel”对象上的请求参数。有关当前参数名称，请参阅 Strands 文档。

## 验证

为了确认语义层、代理和身份流按预期工作，我们通过代理运行了三个查询，然后在不同的角色下重新运行其中一个查询。以下行为是在工作部署中应该重现的行为。

### 查询1，单一维度

*列出我们在威斯康星州的客户及其城市。*

该代理针对 C360 模型生成维度 SQL 查询，从“dim_customer”和“dim_address”中选择“first_name”、“last_name”和“city”，其中“state = 'WI'”。 AtScale 的规划器解析 Amazon Redshift 中“客户”和“地址”表的维度路径，向下推送单个 SQL 语句，然后返回行。

### 查询2，聚合命中

*按销量排名前 10 位的产品是什么？*

代理按产品和订单降序聚合“units_sold”。 AtScale 的聚合管理器会找到匹配的[需求定义聚合](https://documentation.atscale.com/container/managing-atscale/managing-aggregates/about-aggregates/when-the-atscale-engine-creates-demand-defined-aggregates)，并重写查询以命中 Amazon Redshift 中的汇总表，而不是扫描“fact_purchase”。 “查询”页面并排显示 LLM 生成的维度 SQL 和聚合路由的仓库 SQL。

###查询3，跨域

*按终身支出排名前 20 位的客户中，哪些尚未加入奖励计划？*

该代理生成一个连接“dim_customer”、“dim_address”、“dim_rewards”和“fact_purchase”的查询，并按客户聚合“customer_lifetime_value”。该查询仅限于“dim_rewards.account_id”为空的客户。 “cid”上“dim_customer”的左连接保留从未注册的客户，这些客户的注册记录为空。代理返回按生命周期支出排名前 20 名的产品。 AtScale 的规划器根据 Amazon Redshift 解析与本机 SQL 的连接并返回排名列表。 “customer_lifetime_value”公式不是法学硕士必须发明的东西。它是在“customer_lifetime_value.yml”中定义一次并在查询中按名称引用的计算度量。

### 治理重演

我们运行查询 1 的一个变体，将“ssn”添加到投影中（*向我显示我们在威斯康星州的客户及其 SSN*）作为两个不同的呼叫者。作为“hr_user”，“describe_model”返回完整的 C360 模型，代理组成查询，结果集包括 SSN 值。作为“marketing_user”，“describe_model”返回营销视角，该视角不公开“ssn”。代理没有项目属性，因此它返回没有 SSN 的答案。除了调用者的身份之外，两次运行之间没有任何变化。查询文本、代理代码、MCP 服务器、AtScale 引擎和 Amazon Redshift 均未受影响。

### 跨消费者确认

我们通过 AtScale XMLA 端点在 Excel 中打开相同的 C360 模型，并将“Customer.State”和“Total Revenue”拖到数据透视表上。州级总数与代理针对同等问题返回的总数精确匹配。

## 跨数据源扩展

向 C360 模型添加新数据源是一项建模练习，而不是集成练习。假设客户支持团队要求模型包含票证数量，以便客服人员可以回答“我们的哪些支出最高的用户在过去 30 天内打开了支持票证？”步骤如下：

- 使用与操作表相同的复制模式，将支持票证数据与其他 C360 表一起存放在 Amazon Redshift 中。
- 添加将新表映射到逻辑对象的 SML 数据集。
- 添加或扩展维度 (`dim_ticket`) 并将连接添加到 `cid` 上的 `dim_customer`。
- 添加模型需要的任何新度量（`open_ticket_count`、`avg_resolution_time`）。
- 提交 SML 更改，将其作为拉取请求进行审查，并通过 AtScale CI 挂钩进行部署。

代理代码或 AgentCore 配置没有任何变化。下次代理调用“describe_model”时，它会看到新的维度和度量，并且可以针对它们提出问题。相同的模式适用于不同的仓库。如果源位于 Snowflake 或 Databricks 而不是 Amazon Redshift，则连接是具有 Snowflake 或 Databricks 连接的新 SML 数据集，并且根据之前的多源注释在该引擎中解析查询。

## 部署：Amazon EKS 上的 AtScale

AtScale 在 Kubernetes 上运行，AWS 上的参考部署是 [Amazon EKS](https://aws.amazon.com/eks/)。 AtScale 在 `oci://docker.io/atscaleinc/atscale` 上发布了 [官方 Helm 图表](https://documentation.atscale.com/container/installation-guides/kubernetes/installing-atscale)，并且 [AtScale K8S 蓝图](https://github.com/AtScaleInc/atscale-k8s-blueprints) 存储库提供了基础设施即代码 (IaC) 脚手架，用于使用组件建立 EKS 集群AtScale 需要：入口控制器、AtScale 元数据数据库的持久存储、用于查询缓存的 Redis 实例以及用于身份联合的 AtScale 配置的 Keycloak 实例。

EKS 上的 AtScale 部署跨一小组 Kubernetes Pod 运行。 `atscale-engine` 是核心查询规划器和执行器。 `atscale-mcp-server` 是代理与之通信的 MCP 端点。 `atscale-keycloak` 是与 Amazon Cognito、Okta、Azure Active Directory 和其他符合 OpenID Connect (OIDC) 的 IdP 联合的捆绑身份提供商。支持 Pod 处理 SML API 和设计中心 UI（“atscale-sml-api”、“atscale-sml-web”）、PostgreSQL 元数据存储（“atscale-db”）、查询缓存（“atscale-redis”）和入口（“atscale-ingress”，通常由 AWS 网络负载均衡器前置）。

C360 应用程序（聊天 UI 或调用代理的客户端库）可以在其自己的命名空间中的同一 EKS 集群中运行。它使用 [服务账户的 IAM 角色 (IRSA)](https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html) 来访问 Bedrock 和 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/)，而无需嵌入凭证。

网络是标准的：AtScale 通过虚拟私有云 (VPC) 终端节点或允许 AtScale 命名空间出口到 Amazon Redshift 的安全组规则到达 Amazon Redshift，并且人类用户通过入口负载均衡器到达应用程序。

AtScale 提供超越自我管理 EKS 的云部署选项。检查 [AtScale 网站](https://www.atscale.com/) 了解当前产品和 AWS 可用性。本文的其余部分假设前面描述的自我管理模式。

## 结论

对企业数据的代理访问需要三件事协同工作：可以规划和生成查询的基础模型、通过实时仓库计算受治理的、对业务有意义的答案的语义层，以及托管代理和管理身份流的运行时。 Amazon Bedrock、AtScale 和 Amazon Bedrock AgentCore 各自扮演其中一个角色。

代理与语义层对话，而不是直接与仓库对话。维度、层次结构、度量、视角和行安全性存在于 Git 的 SML 中。当架构发生变化或治理规则发生变化时，更新会发生在一个文件中，每个使用者（代理、Excel、Tableau、Power BI）都会在下一个查询中选取它。

### 从哪里开始

大多数完成这项工作的团队都是从缩小范围开始并进行扩展的。

- 选择一个跨越两个或三个数据源且需要比当前应有的时间更长的工作流程。
- 写出工作流程需要回答的 3-5 个问题。这些是语义层在第一天必须支持的查询。
- 使用 [AWS Database Migration Service](https://aws.amazon.com/dms/) 或 [Amazon Aurora Zero-ETL](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/zero-etl.html) 将分析数据整合到 Amazon Redshift（或您选择的仓库）中以获取运营数据。
- 从设计中心的仓库模式引导 SML，然后根据能力问题对其进行细化。
- 使用 AtScale Helm 图表和 AtScale K8S 蓝图在 Amazon EKS 上部署 AtScale，将 AtScale MCP 服务器注册为 AgentCore 网关目标，并通过它连接 Strands 代理。
