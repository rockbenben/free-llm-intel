# 使用 Denodo 和 Amazon Bedrock AgentCore 在 AWS 上为 agentic AI 构建语义层

Agentic AI 应用需要对实时企业数据进行受治理的访问，而这些数据可能位于运营系统、分析数仓、SaaS 应用、其他云或本地机房。在本系列的[上一篇文章](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/)中，我们使用 Stardog 的知识图谱在 Amazon Aurora 和 Amazon Redshift 之上构建了一个 AWS 上的语义层，并由 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上的 Strands agent 查询该层。Amazon Bedrock AgentCore 是一个可以用任意框架或模型大规模构建、连接和优化 agent 的平台。本文沿用同样的 customer 360 模式，但换了一种语义层实现，并扩展了数据源组合。

这里有两处变化。第一，语义层是 Denodo Platform：一个 AI 数据层，提供活动上下文（active context），并以实时、零拷贝的方式访问分布式企业数据。agent 用 Denodo 的 SQL 方言 [VQL](https://community.denodo.com/docs/html/browse/latest/en/vdp/vql/introduction/introduction) 与它对话。第二，数据源组合在 Amazon Aurora 和 Amazon Redshift 之外，还包含一个本地 PostgreSQL 数据库，因此联邦查询问题不再受 Amazon Virtual Private Cloud（Amazon VPC）的边界限制。

其余模式照旧。Amazon Bedrock 上的基础模型负责规划和编写查询。[Denodo MCP Server](https://community.denodo.com/docs/html/document/denodoconnects/latest/en/Denodo%20MCP%20Server%20-%20User%20Manual) 通过 Model Context Protocol（MCP）向 agent 暴露受治理的视图。[Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html) 托管 agent、终止入站身份验证，并管理 agent 向 Denodo 出示的出站凭证。模型推理所依据的一切都不在 prompt 里，而在语义层内：join、指标定义，以及适用于调用者的行级与列级过滤器。

读完之后，你将了解：

- 如何在 Denodo 中把 Amazon Aurora、Amazon Redshift 和一个本地 PostgreSQL 数据库联邦成一个 agent 可以查询的 customer 360 视图。
- 如何通过 Denodo MCP Server 把这个语义视图暴露给 AgentCore 托管的 agent，以及如何把 MCP Server 注册为 AgentCore Gateway 的 target。
- 最终用户的身份如何从企业身份提供商（IdP）经 AgentCore Identity 的 On-Behalf-Of token 交换流转到 Denodo。
- [Global Security Policies](https://community.denodo.com/docs/html/browse/latest/en/vdp/administration/databases_users_and_access_rights_in_virtual_dataport/global_security_policies/global_security_policies) 如何在查询时应用行过滤与列过滤。
- Denodo 在 AWS 上的两种部署方式：[Agora](https://www.denodo.com/en/denodo-platform/denodo-agora)，完全托管的云服务；以及在 Amazon Elastic Compute Cloud（Amazon EC2）或 Amazon Elastic Kubernetes Service（Amazon EKS）上自管理安装。

我们假定你已熟悉[上一篇文章](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/)中的语义层架构：它是什么、用途是什么、以及为什么模型在不拥有 join 的情况下也能规划查询。如果这些对你来说是新的，上一篇文章已经覆盖了这些内容。

## 示例：数据源位于 AWS 之外的 Customer 360

我们沿用上一篇文章里的 customer 360 模式。上一篇文章使用的 [Stardog C360 Knowledge Kit](https://github.com/stardog-union/knowledge-kits/tree/main/examples/c360) 为一个电商零售商建模，围绕两个有说服力的用例：理解流失，以及找出可自动加入奖励计划的客户。本文的 schema 不变。变的是某张表的位置：`rewards_account` 位于一个本地 PostgreSQL 集群，而不再是和其他客户档案数据一起放在 Amazon Aurora 中。

这个位置安排并不是特例。企业数据源可能位于 AWS 之外：本地机房、CRM 之类的 SaaS 工具，或另一个云。语义层必须能够到达相应位置。我们用本地 PostgreSQL 来做这次演练，用它代表来自第三方应用的数据。当数据源是 SaaS 工具、CRM 或大型机时会有哪些变化，见 **扩展到其他数据源** 一节。那一节也涵盖了 [Denodo 默认支持的数百种其他数据源](https://www.denodo.com/system/files/document-attachments/DS-DenodoPlatform-9.5-final.pdf)。

### Amazon Aurora（兼容 PostgreSQL）：客户档案

| **表** | **关键列** |
| --- | --- |
| customer | cid (PK), first_name, last_name, email, ssn, phone, location |
| address | id (PK), city, state, zip, street_name |
| credit_card | id (PK), cid, card_num, card_type |

### Amazon Redshift：订单历史

| **表** | **关键列** |
| --- | --- |
| order | id (PK), cid, pid, order_date, quantity, price, card |
| product | id (PK), name, brand, price, dept |

### 本地 PostgreSQL：奖励计划

| **表** | **关键列** |
| --- | --- |
| rewards_account | id (PK), cid, account_id, create_date |

共享标识符是 `cid`，一个普通整数，在 Aurora 的 customer 表中作为主键出现。在 Amazon Redshift 的 order 表和本地的 `rewards_account` 中，它以非外键列的形式出现。在 Aurora 内部，`customer.location` 列是指向 `address.id` 的整数外键，客户档案正是借此关联到地址记录。没有任何外键跨越两个引擎，也没有 ETL 任务去建立这样的外键。凡是需要把客户与其购买记录、及其奖励计划加入状态关联起来的回答，都必须在查询时对 `cid` 做核对与关联。

这套配置能回答的一个典型问题是：“在我们按终身消费额排名前 20 的客户中，有哪些还没有加入奖励计划？”这就是 Stardog kit 里的自动加入场景，回答它需要来自 Aurora 的档案数据、来自 Amazon Redshift 的终身消费额，以及来自本地集群的加入状态。

Denodo 在执行时规划这条联邦查询，决定哪些下推到 Aurora、哪些下推到 Amazon Redshift、哪些从本地集群拉取，以及如何合并结果。数据不会在数据源之间移动，语义层只声明一次，供所有消费者复用。

## 本文使用的 Denodo 术语

Denodo 以数据虚拟化平台的形式实现语义层。**Denodo Virtual DataPort（VDP）** 是核心的查询引擎：语义层对象存放在这里，VQL 在这里执行，访问策略也在这里评估。**Design Studio** 是 VDP 基于浏览器的建模界面。本文建模的每一个对象都在那里定义。

有三种对象类型会反复出现。

- **base view（基础视图）** 是源系统中物理表、API 或文件与 VDP 中逻辑视图之间的映射。一张 Aurora 表对应一个 base view。
- **derived view（派生视图）** 是对一个或多个 base view 或其他 derived view 的 VQL 查询。本文中的 `customer_360` 视图就是一个 derived view。
- **metric view（指标视图）** 只定义一次业务度量（例如 `lifetime_customer_value`），让其他 derived view 引用它。metric view 把度量的定义与任何使用它的具体查询分离开。

**VQL** 是 Denodo 的 SQL 方言。它是与 ANSI 对齐的 SQL 再加上一组 Denodo 特有的构造，特别是用于表示数据源的 DDL 构造，以及语义 metric view 的语法。在 agentic 场景中，[VQL 的具体语法由一个 skill 提供](https://github.com/denodo/denodo-skills)，LLM 在使用 Denodo 工具时会用到它，以确保正确使用 Denodo 的语法。

**Global Security Policy（GSP，全局安全策略）** 是一条运行时访问控制规则，作用于带有特定 tag 的视图或列。行过滤器和列掩码正是通过 GSP 在查询时按调用者逐个评估并执行的。

更完整的参考见 [Denodo Platform 文档](https://community.denodo.com/docs/)。

## 参考架构

运行时包含两条流程。入站：客户端通过 Amazon Bedrock AgentCore Gateway 把用户请求发送给 agent。Gateway 用企业身份提供商（IdP）校验标识该人类用户的 JSON Web Token（JWT），然后把请求路由到 Amazon Bedrock AgentCore runtime，后者托管 [Strands](https://github.com/strands-agents/sdk-python) agent 进程。agent 调用 Amazon Bedrock 上的基础模型（本次演练中是 Anthropic Claude Sonnet 4.6）来解释 prompt 并规划查询。

出站：AgentCore Gateway 同时充当 agent 工具调用的出站代理。Denodo MCP Server 在 Gateway 上注册为 [MCP target](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-add-target-cli.html)，因此 agent 为获取企业数据而发起的工具调用会经 Gateway 路由到 MCP Server。在请求到达 Denodo 之前，AgentCore Identity 执行一次 [On-Behalf-Of token 交换](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/on-behalf-of-token-exchange.html)，把人类用户的入站 token 换成一个作用域受限、以 Denodo 为受众、代表同一用户的访问 token。Denodo MCP Server 把这个交换后的 token 当作 bearer 凭证接收，并通过 JDBC 把 VQL 请求转发给 Denodo Virtual DataPort（VDP）。VDP 独立校验该 token、把调用者解析为一个 Denodo 角色、应用访问策略，并针对 Amazon Aurora、Amazon Redshift 和本地 PostgreSQL 集群规划联邦查询。

只有 VQL 请求向下传到 VDP，也只有结果集向上返回。任何源数据都不会在引擎之间移动。Aurora、Amazon Redshift 和本地集群响应的是由 VDP 联邦优化器重写后的原生 SQL。后续章节会详细介绍身份传播与策略执行，另外还有章节介绍 MCP Server 注册和 agent 部署步骤。

## 构建语义层

Denodo 中的语义模型并不是单一产物。它是一组 VDP 中的 base view、derived view、metric view 和 tag，共同向消费者呈现具有业务含义的数据。在本文中构建语义模型，意味着把这些部件逐个创建出来。

我们分三轮构建：为每张源表建 base view；建一个 derived view（`customer_360`），在客户粒度上按 `cid` 关联这些 base view；再建一个 metric view（`lifetime_customer_value`），定义可复用的消费额聚合，供查询在需要时关联使用。

在实践中，这些建模工作是在 Denodo Design Studio 中以可视化方式完成的。你把 Aurora、Amazon Redshift 和本地 PostgreSQL 数据源拖到画布上，在它们之间画出 join，并通过表单（而不是手写 DDL）重命名字段或修改字段类型（例如把 `cust_ref` 映射为 `customer_id`）。本文后面介绍的安全策略附加，也是在同一个界面里完成的。

metric view 与其引用的 derived view 放在一起，定义一次、多处复用。如果两个团队在同一份基础数据之上各自构建客户级视图，两者呈现的度量定义是相同的。

## Base view

每张源表都会成为 VDP 中的一个 base view。以 Aurora 的 customer 表为例，这意味着在 Design Studio 中用专门的连接器引入 Aurora、指向相应 schema，并让 VDP 内省列。Design Studio 负责内省。得到的 base view 是物理列与其 VDP 对应物之间的一对一映射，不对源数据做任何转换。

创建过程中还有两项额外的配置：

- **用于治理的列 tag。** customer 的 base view 上的 `ssn` 会被打上 `pii_sensitive` tag。`credit_card` 的 base view 上的 `card_num` 也会被打上同一个 tag。**受治理的访问** 一节中定义的 Global Security Policy 正是绑定到这些 tag 上。
- **主键与 join 字段。** `cid` 在 `aurora_customer` 上被标记为主键，在 `redshift_order` 和 `postgres_rewards_account` 上被标记为 join 字段。Design Studio 会在源元数据可用时推断主键，否则你在 base view 定义中设置一次即可。

对前面介绍的源表重复这一过程。最终得到六个 base view：Amazon Aurora 上的 `aurora_customer`、`aurora_address` 和 `aurora_credit_card`；Amazon Redshift 上的 `redshift_order` 和 `redshift_product`；以及本地 PostgreSQL 上的 `postgres_rewards_account`。

Design Studio 还通过 [Denodo Assistant](https://www.denodo.com/en/solutions/by-capability/denodo-assistant) 支持自然语言建模。开发者可以用平实的英语描述一个视图（例如“把 Aurora 的客户档案与 Amazon Redshift 的订单总额按 `cid` 关联起来”），拿回一份候选 VQL 定义，然后在同一个画布上审阅、细化，再保存。细化是迭代的：后续 prompt 会在定义定稿前调整过滤器、join 或字段映射。本节所述的治理与类型规则同样适用于以这种方式创建的对象。

## Derived view：Customer 360

`customer_360` 是跨三个数据源的客户级视图，每个客户一行。订单明细与聚合单独放在我们接下来定义的 metric view 中。

```
CREATE OR REPLACE VIEW customer_360 AS
SELECT aurora_customer.cid,
aurora_customer.first_name,
aurora_customer.last_name,
aurora_customer.email,
aurora_customer.ssn,
aurora_address.city,
aurora_address.state,
aurora_credit_card.card_num,
aurora_credit_card.card_type,
postgres_rewards_account.account_id,
postgres_rewards_account.create_date AS rewards_since
FROM (
(
aurora_customer AS aurora_customer
LEFT OUTER JOIN aurora_address AS aurora_address
ON aurora_customer.location = aurora_address.id
)
LEFT OUTER JOIN aurora_credit_card AS aurora_credit_card
ON aurora_customer.cid = aurora_credit_card.cid
)
LEFT OUTER JOIN postgres_rewards_account AS postgres_rewards_account
ON aurora_customer.cid = postgres_rewards_account.cid;
```

这个定义有两个特性对后面的架构很重要。第一，join 位于 Denodo Platform 中，而不是在一条流水线里。没有任何 ETL 任务去维护一张物化的 `customer_360` 表。VDP 在执行时解析 join：Aurora 返回档案加上信用卡，本地集群返回奖励计划加入记录，VDP 按 `cid` 把它们合并。第二，这个 derived view 承载了每一列，包括 `ssn` 和 `card_num`。

为了治理和 AI，我们还添加了元数据：针对个人可识别信息（PII）字段的列 tag，以及记录这个视图和每个字段的说明。Denodo 的 Assistant 可以借助 LLM 来建议这些内容。后面的章节会说明这些元数据为何重要。

## Metric view：客户终身价值

metric view 用特定的 SOURCES/DIMENSIONS/METRICS 结构定义可复用的业务度量。完整语法见 VQL 指南中的 [Defining a Metric View](https://community.denodo.com/docs/html/browse/latest/en/vdp/vql/defining_a_derived_view/defining_a_metric_view/defining_a_metric_view) 参考。`lifetime_customer_value` 并不放在 `customer_360` 里面，而是与它并列，作为独立对象存在：

```
CREATE OR REPLACE METRIC VIEW lifetime_customer_value
(
first_name, last_name, state, rewards_since, lifetime_spend, order_count, product_id,product_name, product_brand,product_dept, units_sold
)
SOURCES (
customer_360 AS customer_360,
redshift_order AS redshift_order,
redshift_product AS redshift_product
)
ASSOCIATIONS (
customer_360 redshift_order assoc_customer360_orders,
redshift_product redshift_order assoc_product_orders
)
DIMENSIONS (
customer_360(
first_name AS customer_360.first_name,
last_name AS customer_360.last_name,
state AS customer_360.state,
rewards_since AS customer_360.rewards_since
),
product(
product_id AS redshift_product.id,
product_name AS redshift_product.name,
product_brand AS redshift_product.brand,
product_dept AS redshift_product.dept
)
)
METRICS (
lifetime_spend AS sum((redshift_order.price*redshift_order.quantity)),
order_count AS count(redshift_order.id),
units_sold AS sum(redshift_order.quantity)
);
```

其他视图和外部报表工具可以引用 `lifetime_customer_value`，方式与它引用其他视图相同。当业务规则变化时（比如 `lifetime_spend` 应当排除已取消的订单），更新只发生在度量定义这一处。每个消费者在下一次查询时就会采用这一变化，无需改动 derived view 或下游应用。不同团队可以搭建各自的 derived view，表达其业务线看待世界的方式。基础数据保持共享，而语义解释保持独立，因此任一团队的改动都不会打扰另一个团队。

## VDP 如何执行联邦查询

当 agent 执行 **示例** 一节中的自动加入问题时（*“在我们按终身消费额排名前 20 的客户中，有哪些还没有加入奖励计划？”*），对应的 VQL 会使用 metric view 计算结果集并求出所需度量：

```
SELECT first_name, last_name, state, EVALUATE_METRIC(lifetime_spend) AS lifetime_spend
FROM lifetime_customer_value
WHERE rewards_since IS NULL
GROUP BY first_name, last_name, state
ORDER BY EVALUATE_METRIC(lifetime_spend) DESC
LIMIT 20;
```

尽管这条查询只引用了 metric view，VDP 的基于代价的优化器仍会针对相应数据所在的三个引擎规划联邦执行。得到的执行计划大致如下：

- **下推到 Amazon Aurora**：Denodo 把 customer、address 和 `credit_card` 的 join 下推到 Aurora，返回客户档案字段，包括 `first_name`、`last_name`、state 和 `cid`。
- **下推到本地 PostgreSQL**：Denodo 把 `rewards_account` 的投影下推，返回 `cid` 和 `create_date`。
- **下推到 Amazon Redshift**：Denodo 把消费额聚合以 `SUM(price * quantity)` 按 `cid` 分组的形式下推到 Amazon Redshift。
- **在 Denodo 内部合并**：Denodo 把 Aurora 的档案结果与 PostgreSQL 的奖励计划结果按 `cid` 做左连接，再把该结果与 Amazon Redshift 的聚合消费额按 `cid` 做右外连接。Denodo 过滤出 `rewards_since` IS NULL 的行，按 `first_name`、`last_name` 和 state 分组，把度量按外层分组聚合（`sum(sum) AS lifetime_spend`）求出，按 `lifetime_spend` 降序排序，最多返回 20 行。

这个计划体现了各数据源的优势。Amazon Redshift 负责聚合，Aurora 负责客户档案 join（因为三张档案表都在那里），本地集群返回一小批奖励计划记录。VDP 处理最后的跨引擎 join 和 top-N 过滤，所操作的是三个紧凑的中间结果集，每个客户一行而不是每个订单一行。手写流水线通常也大致是这个形态，然后必须永远让它保持同步。

VDP 还会在最划算的地方处理类型对齐。如果同一个标识符在某个源中是整数、在另一个源中是字符串，VDP 会把类型转换下推到那个仍然能基于转换后谓词做过滤的源，而不是跨引擎拉数据、事后再统一类型。

## 受治理的访问：身份传播与运行时执行

广泛触达各数据源是企业级语义层的核心特征之一，但如果没有运行时访问控制，这种触达就会带来真实风险。如果按用户过滤的逻辑写在 agent 代码里，那么一次 prompt 注入就可能绕过它。如果它写在 LLM 里，那它其实哪儿都不在。如果只在各个源系统中执行，策略可能不一致，也可能无法顾及跨数据源形成的业务含义。Aurora 不知道语义层里“*消费冠军*”是什么意思，堡垒机后面的本地 PostgreSQL 集群也不知道。而且很多时候，尤其是在混合了本地与云系统的场景中，让所有系统共享同一批身份提供商甚至都不是一个选项。

本架构的做法是在语义层执行访问控制，使用发起请求的人类用户的身份，并让该身份从 IdP 一路经 Amazon Bedrock AgentCore 传播到 Denodo Virtual DataPort。

## 身份传播链

![图 6. 从用户登录经 Amazon Bedrock AgentCore 到 Denodo（MCP Server 和 VDP）及底层数据源的身份传播与查询流程。黑色箭头表示出站身份与查询路径。绿色虚线箭头表示带过滤结果集的返回路径。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/06/ML-21332-6-1.png)

图 6：从用户登录经 Amazon Bedrock AgentCore 到 Denodo（MCP Server 和 VDP）及底层数据源的身份传播与查询流程。黑色箭头表示出站身份与查询路径。绿色虚线箭头表示带过滤结果集的返回路径

- 用户在应用上向企业 IdP 完成身份验证。IdP 返回一个 JWT，携带用户身份与属性声明——角色、区域、部门，以及 IdP 配置要发出的其他任何内容。
- 应用以用户的 JWT 作为 bearer token，通过 AgentCore Gateway 调用 agent。
- Gateway 把请求路由到 AgentCore runtime，后者托管 Strands agent 进程。
- 当 agent 发起出站工具调用时，AgentCore Identity 执行一次 On-Behalf-Of token 交换，返回一个新的访问 token，其 sub 声明是人类用户，aud 声明是 Denodo。
- agent 在 MCP 请求上以 `Authorization: Bearer <access_token>` 的形式，把新的访问 token 出示给 Denodo MCP Server。
- Denodo VDP 用配置的 JWKS URL 校验该 JWT、检查签发者与受众、提取 scope 声明，并把调用者映射为一个 Denodo 角色。
- VDP 在查询时评估 Global Security Policies，并把过滤后的结果集返回给 agent。
- VDP 查询数据源以满足请求，合并结果后再返回。

第 2 步的 Gateway JWT 校验是可选的，因为 VDP 会在第 6 步重新校验 token。开启 Gateway 校验后，格式错误的 token 会在请求路径中更早地失败。

第 4 步的 token 交换根据凭证提供方的配置，使用 RFC 8693 的 token-exchange grant 或 RFC 7523 的 JWT-bearer grant。凭证本身不会进入 agent 代码。AgentCore Identity 在调用时注入它。

第 8 步的调用者身份透传选项按数据源启用，并要求 Denodo 与该数据源共享同一 IdP。适用时，调用者的身份会被端到端转发，从而在源端获得完整的审计能力。

## 在 Denodo 中应用访问策略

Customer 360 数据是受监管的。例如，某些用户（HR、欺诈分析师）可能需要看到 Social Security number（SSN）和完整信用卡号这样的 PII，但大多数用户（市场、分析）绝不能看到。

Denodo 对此的机制是 [Global Security Policies](https://community.denodo.com/docs/html/browse/latest/en/vdp/administration/databases_users_and_access_rights_in_virtual_dataport/global_security_policies/global_security_policies)，配合基于属性和角色的访问控制。Global Security Policy 是一条作用于带特定 tag 的视图或列的规则，在查询时根据调用者的角色和会话属性评估。底层视图的结构不会被改动。

为了说明这一点，我们在 Aurora 之上的 base view 中把两列（`ssn` 和 `card_num`）标记为 PII。我们创建一个 Global Security Policy `mask_pii_columns`。

- 适用对象：调用者的角色不是 `hr_user`。
- 作用元素：作用于带 `pii_sensitive` tag 的列。
- 动作：用星号（`****`）掩码。

然后我们定义两个 Denodo 角色。

- `hr_user`：对 `customer_360` 拥有 Execute 权限。可以看到所有列。
- `marketing_user`：对 `customer_360` 拥有 Execute 权限。因为策略生效，看到的 `ssn` 和 `card_num` 会是 `****`。

当 `marketing_user` 执行下面这条 VQL 查询时：

```
SELECT cid, first_name, last_name, state, ssn
FROM customer_360
WHERE state = 'WI';
```

VDP 在规划查询之前评估 Global Security Policy。它发现 `ssn` 带有 `pii_sensitive` tag，而调用者的角色不是 `hr_user`，于是把投影改写为对 `ssn` 返回 `***`。

对于行级过滤（例如一个只应看到东海岸客户的 US-East 分析师），同样的机制可以扩展适用。策略条件甚至可以依赖从 JWT token 映射来的会话属性，或动态地从外部表拉取。

### 关于 Responsible AI 的一点说明

Denodo 的 Global Security Policies 在语义层过滤 PII，因此对于那些不该看到 `ssn` 或 `card_num` 的调用者，模型根本看不到这些值。即便如此，agent 的响应仍可能用自然语言复述客户标识符、位置或消费模式。请用你对待底层受监管数据时相同的方式和留存策略来处理 agent 输出：限定日志与对话记录的记录范围，应用 Amazon Bedrock Guardrails 做内容与敏感话题控制，并限制谁可以读取这些响应。更全面的指导见 [Amazon Bedrock 中的 Responsible AI](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html)。

## 跨层审计与可观测性

请求路径上的每一层都独立记日志。AgentCore runtime 把调用记录发到 [Amazon CloudWatch](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/WhatIsCloudWatchLogs.html)。AgentCore Gateway 记录入站 MCP 请求，包括调用者的 JWT sub 声明。Denodo MCP Server 把工具调用记录到自己的日志中。Denodo VDP 的审计日志会捕获完整的 VQL 请求、映射到的 Denodo 角色、解析出的联邦计划，以及策略评估结果。

这些日志也可以[接入 Amazon CloudWatch](https://community.denodo.com/kb/en/view/document/Monitoring%20Denodo%20with%20Amazon%20CloudWatch)。当需要按数据源追溯到具体人类用户的审计时（例如出于 HIPAA 或 SOX 合规要求），请为这些数据源的 base view 配置透传会话凭证，让 Denodo 在源系统支持的情况下把调用者身份转发到源系统，而不是依赖服务账号。

## 通过 Denodo MCP Server 暴露语义层

[Denodo MCP Server](https://community.denodo.com/docs/html/document/denodoconnects/latest/en/Denodo%20MCP%20Server%20-%20User%20Manual) 是一个附加组件，位于 MCP 客户端与 VDP 之间：下载分发包、解压、编辑 `config/application.properties`，然后启动。该服务器在 `http://<mcp-host>:8080/<database>/mcp` 上监听 streamable HTTP 的 MCP 请求，并通过 JDBC 转发给 VDP。

本次演练中有三个配置值很重要。

- `mcp.security.oauth2.enabled=true`：在入站 MCP 请求上接受 OAuth 2.0 bearer token。配合 VDP 的 OAuth 认证器配置，token 会被转发给 VDP 做校验和角色解析（另见 **受治理的访问** 一节）。
- `vdp.datasource.jdbcUrl=jdbc:vdb://<vdp-host>:9999/`：访问 VDP 所用的 JDBC URL。每次请求具体针对哪个数据库，来自 MCP 端点路径。
- `mcp.visibility.tags=mcp` 控制 MCP Server 上哪些视图可见。如果定义了，只有带至少一个这些 tag 的视图才可见。

该服务器实现了 [MCP OAuth 2.0 授权](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization#authorization-flow)流程，包括 RFC 9728 Protected Resource Metadata 和 RFC 7591 Dynamic Client Registration。

### 关于 IdP 兼容性的一点说明

Denodo MCP Server 文档中说明支持与 Okta、Ping Identity 和 Keycloak 的自动 Dynamic Client Registration 流程。对于其他身份提供商，MCP Server 也接受手动客户端配置：在带外获取 OAuth token，并把它作为静态 `Authorization` 头附加在 MCP 请求上，具体做法见 [Denodo MCP Server 用户手册](https://community.denodo.com/docs/html/document/denodoconnects/latest/en/Denodo%20MCP%20Server%20-%20User%20Manual#h.hs7cb89txbqj)。

## 用 Application Load Balancer 前置该服务器

如果 Denodo MCP Server 运行在与 VDP 同一 VPC 的 Amazon EC2 或 Amazon EKS 上，请通过 [Application Load Balancer](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html) 暴露它，配置 HTTPS 监听器和来自 [AWS Certificate Manager](https://docs.aws.amazon.com/acm/latest/userguide/acm-overview.html) 的证书。这样 AgentCore Gateway 就有了稳定的 HTTPS 端点，也把 TLS 终止从 MCP Server 进程中卸载出去。目标组：HTTP，端口 8080。健康检查路径应同时接受 200 和 404 为健康响应，因为根路径返回 404，而当服务器已启动并连接到 VDP 时 `/health` 返回 200。

## 验证

为了确认语义层、agent 和身份流转都按预期工作，我们通过 agent 运行了三类查询，另外还做了一次治理重跑，用来演示 **受治理的访问** 一节中“同一查询、两个用户”的特性。我们可以使用 Denodo 的 Data Marketplace assistant——它背后依赖的是等价的工具——来对我们的场景做一次快速验证。

### 查询 1：仅 Aurora

*“列出我们在 Wisconsin 的客户，以及他们所在的城市。”*

agent 生成并执行：

```
/* The query needs to retrieve first_name, last_name, and city from the customer_360 view where state = 'WI', ordered by last_name. The output will be multiple rows with 3 columns. The table is at customer granularity (one row per customer). No obligatory columns are present, so a simple WHERE filter on state suffices. */
SELECT "first_name",
"last_name",
"city"
FROM "customer_360"."customer_360"
WHERE "state" = 'WI'
ORDER BY "last_name"
```

VDP 的优化器判断这次投影和过滤只需要 Aurora 侧的数据，于是把一条查询下推到 Amazon Aurora。基于一次探测查询，agent 可以把“Wisconsin”这个过滤条件翻译成谓词 `state = 'WI'`。Amazon Redshift 和本地集群都不被触及。

### 查询 2：仅 Redshift

*“按销量排名的前 10 个产品是什么？”*

agent 生成：

```
/* The user wants top 10 products by total units sold from a metric view. I need to use EVALUATE_METRIC for units_sold, GROUP BY product_name, ORDER BY the metric descending, LIMIT 10. The output will be multiple rows (up to 10) with two columns: product_name and total_units_sold. */
SELECT "product_name",
EVALUATE_METRIC("units_sold") AS "total_units_sold"
FROM "customer_360"."lifetime_customer_value"
GROUP BY "product_name"
ORDER BY "total_units_sold" DESC
LIMIT 10
```

图 7：VDP 把整条查询（join、聚合、排序和 limit）下推到 Amazon Redshift，因为产品数据和订单数据都在那里。Aurora 和本地集群不被触及

### 查询 3：三方联邦

*“在我们按终身价值排名前 20 的客户中，有哪些还没有加入奖励计划？”*

agent 生成：

```
/* This is a metric view, so I need to use EVALUATE_METRIC for lifetime_spend and order_count. The query needs to: 1. Aggregate by first_name, last_name, state, rewards_since to get total lifetime_spend and order_count 2. Rank top 20 by total lifetime_spend 3. Filter those top 20 where rewards_since IS NULL I'll use a CTE with ROW_NUMBER() to get top 20, then filter for NULL rewards_since in outer query. */
WITH "ranked_customers" AS (
SELECT "first_name",
"last_name",
"state",
"rewards_since",
EVALUATE_METRIC("lifetime_spend") AS "total_lifetime_spend",
EVALUATE_METRIC("order_count") AS "total_order_count"
FROM "customer_360"."lifetime_customer_value"
GROUP BY "first_name",
"last_name",
"state",
"rewards_since"
ORDER BY "total_lifetime_spend" DESC
LIMIT 20
)
SELECT "first_name",
"last_name",
"state",
"rewards_since",
"total_lifetime_spend",
"total_order_count"
FROM "ranked_customers"
WHERE "rewards_since" IS NULL
ORDER BY "total_lifetime_spend" DESC
```

![agent 输出，列出按终身价值排名前 20 且尚未加入奖励计划的客户](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/06/ML-21332-8.png)

图 8：三方联邦查询的 agent 结果，列出按终身价值排名前列、尚未加入奖励计划的客户

VDP 按 **构建语义层** 一节所述跨三个引擎规划：来自 Aurora 的档案、来自 Amazon Redshift 的聚合消费额、来自本地集群的加入记录，以及在 VDP 内部完成的最终 join 和 top-N。POC 数据中排名第一的结果是来自 Wisconsin 州 Milwaukee 的 Marcus Chen，终身消费额 47,832 美元，一个高消费却未加入奖励计划的客户，正是 **示例** 一节那个示例问题中的自动加入目标。请注意，LLM 无需自己给出 `lifetime_spend` 的定义，因为该公式作为 metric view 中定义的语义模型的一部分已经存在。

### 治理重跑

我们在投影中加上 `ssn`，以两个不同的调用者身份运行查询 1：

```
SELECT cid, first_name, last_name, state, ssn
FROM customer_360
WHERE state = 'WI';
```

以 `hr_user` 身份运行时，结果包含 `ssn` 的值。以 `marketing_user` 身份运行时，返回相同的行，但 `ssn` 是被星号掩码的值。两次运行之间，查询文本、agent 代码、MCP Server、VDP 和 Aurora 都没有任何改动。**受治理的访问** 一节中的 Global Security Policy `mask_pii_columns` 在查询时按调用者角色评估，VDP 相应地改写投影。同样的行为也适用于 `card_num`。

## 扩展到其他数据源

把 AWS 之外的数据源加入 `customer_360`，无论是用于 CRM 记录的 Salesforce、用于客户服务数据的 ServiceNow，还是用于 ERP 表的 SAP，其建模工作与 Aurora、Amazon Redshift 和本地集群完全相同。创建一个 base view，按 `cid` 把它 join 进 derived view，并给敏感列打 tag。metric view、Global Security Policy 和 agent 的 VQL 都不变。变的是 VDP 用来访问该数据源的包装器。例如：

- **Salesforce** 通过 [Denodo Salesforce 连接器](https://community.denodo.com/docs/html/browse/latest/en/vdp/administration/creating_data_sources_and_base_views/salesforce_sources/salesforce_sources)连接，使用 OAuth 2.0 认证，并在 REST 或 Bulk API 上做 `VQL-to-SOQL` 转换。
- **ServiceNow、Microsoft Dynamics 365 和其他 SaaS 工具**使用 Denodo 的 [SaaS 向导模板](https://community.denodo.com/docs/html/browse/latest/en/vdp/administration/creating_data_sources_and_base_views/software_as_a_service_wizards/software_as_a_service_wizards)，针对常见 API 做了预配置。
- **SAP ERP** 通过 [BAPI 数据源](https://community.denodo.com/docs/html/browse/latest/en/vdp/administration/creating_data_sources_and_base_views/bapi_sources/bapi_sources)使用 SAP Java Connector 连接。VDP 调用 SAP RFC 并把响应塑造成行。

agent 并不知道底下是其中哪一种。它用 VQL 查询 `customer_360`。Denodo 的包装器处理源生语法转换，而无论数据行来自 JDBC 引擎、REST API 还是 RFC 调用，Denodo 的 Global Security Policy 都会统一生效。

有一个部署期的决定会因数据源而异：是把调用者身份透传到数据源，还是以服务账号连接。透传在数据源支持时（例如到 SAP 的 Kerberos 或到 Salesforce 的 OAuth）能在源端提供端到端审计。服务账号连接更简单，而源端的审计只会显示查询来自 Denodo。

## 部署：Denodo Agora 与自管理

Denodo 在 AWS 上有两种形态。两者使用相同的 Virtual DataPort、相同的 VQL、相同的 Global Security Policies、相同的 MCP Server。选择取决于运维方式。

### Agora：完全托管

[Denodo Agora](https://www.denodo.com/en/denodo-platform/denodo-agora) 是 Denodo 的完全托管云服务，可在 [AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-ze2asxcox56o2?sr=0-3&ref_=beagle&applicationId=AWSMPContessa) 上获取。Agora 采用分离平面的架构。**控制平面**（Solution Manager、Design Studio、Scheduler 管理、监控/诊断）运行在 Denodo 的云账号中，**执行平面**（VDP、Scheduler、Data Catalog）运行在客户的 AWS 账号内。接触数据的算力位于客户的 VPC 中。管理界面由 Denodo 运营。

当你不想自己运维应用、而 Denodo 发布的更新节奏适用于你的组织时，选择 Agora。

### 在 Amazon EC2 或 Amazon EKS 上自管理

自管理部署把 Denodo Platform 完全安装在客户的 AWS 账号中。Denodo 在 AWS Marketplace 上发布 VM 镜像，并为 Amazon EKS 提供带 Helm chart 的容器镜像。集群、升级和备份由你负责。

当合规要求特定的部署姿态、当你希望控制版本节奏，或当参考架构要求在某个特定 VPC 内部署 Denodo 集群时，选择自管理。

## 访问 AWS 之外的数据源

两种部署形态都把 VDP 放在客户的 AWS 账号中。访问本地数据源在两种情况下是同一个问题：从托管 VDP 的 VPC 到本地集群之间需要一条网络路径，通过组织已经在用的某种混合连接方案打通。对于 Salesforce 或 ServiceNow 这类 SaaS 数据源，无需额外配置，因为执行平面默认具备出站互联网访问能力，足以完成 OAuth 2.0 认证和 REST API 调用。

## 结论与从哪里开始

可靠的 agentic 企业数据访问需要三样东西协同工作：一个能规划和生成查询的基础模型、一个在实时源系统之上呈现业务含义数据的语义层，以及一个托管 agent 并管理身份流转的 runtime。Amazon Bedrock、Denodo Platform 和 Amazon Bedrock AgentCore 各自承担其中一个角色。

agent 与语义层对话，而不是直接与底层数据库对话。base view、derived view、metric view、tag 和 Global Security Policies 都位于 VDP 中。当源 schema 发生漂移、新数据源上线，或治理规则变化时，更新发生在语义层，每个消费者在下一次查询时就会采用它。语义层携带的额外元数据（文档、说明、度量公式和 360 graph）为模型提供了更多有依据的业务上下文可供推理，而不只是原始 schema。

### 从哪里开始

试用 [AWS 上的 Agora](https://aws.amazon.com/marketplace/pp/prodview-ze2asxcox56o2) 并按说明部署。Agora 是 Denodo 的完全托管云服务，用于在 AWS 上部署 AI 数据层，提供对分布式企业数据的实时、受治理访问。

大多数团队都是从小范围起步、再逐步扩展，从而把这套东西跑起来的。

- 选择**一个跨两三个不同源系统的 agentic 工作流**，它今天回答起来花的时间过长。
- 写下该工作流需要回答的**三到五个具体问题**。这些就是语义层第一天就必须支持的查询。
- **连接数据源并创建 base view**，覆盖该工作流涉及的源表。创建时给 PII 列打 tag。
- **构建**这些问题所需的 **derived view** 和 **metric view**。
- **实施 Global Security Policy**，帮助保护 PII、受保护健康信息（PHI）、支付卡行业（PCI）或其他敏感信息。
- **把 Denodo MCP Server 注册为 AgentCore Gateway target**，并按前面章节的模式把 Strands agent 接到它上面。用 `agentcore deploy` 部署。
