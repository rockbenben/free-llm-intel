# 使用 Denodo 和 Amazon Bedrock AgentCore 在 AWS 上构建代理 AI 语义层

代理人工智能应用程序需要对实时企业数据进行受管控的访问。这些数据可以存在于操作系统、分析仓库、SaaS 应用程序、其他云或本地。在本系列的上一篇文章中，我们使用 Stardog 的知识图谱、Amazon Aurora 和 Amazon Redshift 在 AWS 上构建了一个语义层。 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上的 Strands 代理查询该层。 Amazon Bedrock AgentCore 是一个使用任何框架或模型大规模构建、连接和优化代理的平台。这篇文章使用相同的客户 360 度模式，但交换了不同的语义层实现并扩展了源组合。

这里有两件事发生了变化。首先，语义层是 Denodo 平台：一个 AI 数据层，提供活动上下文以及对分布式企业数据的实时、零复制访问。代理使用 Denodo 的 SQL 方言 [VQL](https://community.denodo.com/docs/html/browse/latest/en/vdp/vql/introduction/introduction) 与其进行对话。其次，源组合包括本地 PostgreSQL 数据库以及 Amazon Aurora 和 Amazon Redshift，因此联合问题不再受 Amazon Virtual Private Cloud (Amazon VPC) 的限制。

该模式的其余部分继续存在。 Amazon Bedrock 上的基础模型负责规划和编写查询。 [Denodo MCP 服务器](https://community.denodo.com/docs/html/document/denodoconnects/latest/en/Denodo%20MCP%20Server%20-%20User%20Manual) 通过模型上下文协议 (MCP) 向代理公开受管视图。 [Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html) 托管代理、终止入站身份验证并管理代理向 Denodo 提供的出站凭证。模型推理的所有内容都位于语义层而不是提示中：连接、度量定义以及适用于调用者的行和列过滤器。

读完这篇文章后，您将了解：

- 如何将 Amazon Aurora、Amazon Redshift 和 Denodo 中的本地 PostgreSQL 数据库联合到代理可以查询的单个客户 360 度视图中。
- 如何通过 Denodo MCP 服务器向 AgentCore 托管的代理公开该语义视图，以及如何将 MCP 服务器注册为 AgentCore 网关目标。
- 最终用户的身份如何从企业身份提供商通过 AgentCore Identity On-Behalf-Of 令牌交换流向 Denodo。
- [全局安全策略](https://community.denodo.com/docs/html/browse/latest/en/vdp/administration/databases_users_and_access_rights_in_virtual_dataport/global_security_policies/global_security_policies) 如何在查询时应用行和列过滤器。
- AWS 上 Denodo 的两个部署选项：[Agora](https://www.denodo.com/en/denodo-platform/denodo-agora)、完全托管的云服务以及 Amazon Elastic Compute Cloud (Amazon EC2) 或 Amazon Elastic Kubernetes Service (Amazon EKS) 上的自我管理安装。

我们假设您熟悉[上一篇文章：](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/)中的语义层架构，它是什么、它的用途以及为什么模型计划在不拥有连接的情况下进行查询。如果其中有任何新内容，上一篇文章将介绍相关内容。

## 示例：具有 AWS 外部来源的 Customer 360

我们仍然采用与上一篇文章相同的客户 360 度模式。上一篇文章中使用的 [Stardog C360 知识套件](https://github.com/stardog-union/knowledge-kits/tree/main/examples/c360) 通过两个激励用例对电子商务零售商进行了建模：了解客户流失情况和识别客户以自动注册奖励计划。本文中的架构没有改变。发生变化的是一张表所在的位置：“rewards_account”位于本地 PostgreSQL 集群上，而不是与其余客户资料数据一起位于 Amazon Aurora 中。

这个位置并不是一个特例。企业数据源可能位于 AWS 之外：本地、CRM 等 SaaS 工具中或其他云中。语义层必须达到任何适用的程度。我们使用本地 PostgreSQL 来演示来自第三方应用程序的数据。 **扩展到其他源**部分介绍了当源是 SaaS 工具、CRM 或大型机时发生的变化。它还涵盖了[Denodo默认支持的其他数百个数据源](https://www.denodo.com/system/files/document-attachments/DS-DenodoPlatform-9.5-final.pdf)。

### Amazon Aurora（与 PostgreSQL 兼容）：客户资料

| **表** | **关键栏目** |
| --- | --- |
|客户| cid (PK)、名字、姓氏、电子邮件、ssn、电话、位置 |
|地址 | id (PK)、城市、州、邮政编码、街道名称 |
|信用卡 | id (PK)、cid、card_num、card_type |

### Amazon Redshift：订单历史记录

| **表** | **关键栏目** |
| --- | --- |
|订单| id (PK)、cid、pid、订单日期、数量、价格、卡 |
|产品 | id (PK)、名称、品牌、价格、部门 |

### 本地 PostgreSQL：奖励计划

| **表** | **关键栏目** |
| --- | --- |
|奖励帐户 | id (PK)、cid、account_id、create_date |

共享标识符是“cid”，一个纯整数，在 Aurora 客户表中显示为主键。它在 Amazon Redshift 订单表和本地“rewards_account”中显示为非外键列。在 Aurora 本身内，“customer.location”列是“address.id”的整数外键，这是配置文件连接到地址记录的方式。没有跨两个引擎的外键，也没有构建一个引擎的 ETL 作业。将客户加入购买和奖励注册的答案必须在查询时协调“cid”。

此设置回答的一个代表性问题是：“按终身支出计算，我们的前 20 位客户中哪些尚未加入奖励计划？”这是 Stardog 套件的自动注册场景，它需要来自 Aurora 的配置文件数据、来自 Amazon Redshift 的生命周期支出以及来自本地集群的注册状态来回答。

Denodo 在执行时规划联合查询，决定将什么推送到 Aurora、将什么推送到 Amazon Redshift、从本地集群获取什么以及如何组合结果。数据源之间没有数据移动，并且语义层保持声明一次，以便每个消费者重用。

## 本文中使用的 Denodo 术语

Denodo 将语义层实现为数据虚拟化平台。 **Denodo Virtual DataPort (VDP)** 是核心查询引擎：它是语义层对象所在的位置、VQL 执行的位置以及访问策略评估的位置。 **Design Studio** 是基于浏览器的 VDP 创作界面。本文中建模的每个对象都在那里定义。

三种对象类型反复出现。

- **基本视图**是源系统中的物理表、API 或文件与 VDP 中的逻辑视图之间的映射。一张 Aurora 表映射到一张基本视图。
- **派生视图**是对一个或多个基本或其他派生视图的 VQL 查询。本文中的“customer_360”视图是派生视图。
- **指标视图**定义一次业务度量（例如，`lifetime_customer_value`）并让其他派生视图引用它。指标视图将度量的定义与使用该度量的任何特定查询分开。

**VQL** 是 Denodo 的 SQL 方言。它是 ANSI 对齐的 SQL 加上一组 Denodo 特定的构造，特别是表示数据源的 DDL 构造和语义度量视图的语法。在代理场景中，[VQL的特定语法由技能](https://github.com/denodo/denodo-skills)提供，LLM在使用Denodo工具时将使用该技能来促进正确使用Denodo的语法。

**全局安全策略 (GSP)** 是一种运行时访问控制规则，适用于带有特定标记的视图或列。 GSP 是在查询时强制执行行过滤器和列掩码的方式，并根据调用者进行评估。

有关更完整的参考，请参阅 [Denodo 平台文档](https://community.denodo.com/docs/)。

## 参考架构

运行时有两个流程。入站：客户端通过 Amazon Bedrock AgentCore Gateway 将用户的请求发送到代理。 Gateway 根据企业身份提供商 (IdP) 验证用于识别人类用户的 JSON Web 令牌 (JWT)，然后将请求路由到托管 [Strands](https://github.com/strands-agents/sdk-python) 代理进程的 Amazon Bedrock AgentCore 运行时。该代理调用 Amazon Bedrock 上的基础模型（本演练中为 Anthropic Claude Sonnet 4.6）来解释提示并规划查询。

出站：AgentCore Gateway 还充当代理工具调用的出站代理。 Denodo MCP 服务器在网关上注册为 [MCP 目标](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-add-target-cli.html)，因此工具调用代理使企业数据通过网关路由到 MCP 服务器。在请求到达 Denodo 之前，AgentCore Identity 会执行[代表令牌交换](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/on-behalf-of-token-exchange.html)，将人类用户的入站令牌转换为范围访问令牌，该令牌代表与 Denodo 相同的用户。 Denodo MCP 服务器接受交换的令牌作为承载凭证，并通过 JDBC 将 VQL 请求转发到 Denodo Virtual DataPort (VDP)。 VDP 独立验证令牌，将调用者解析为 Denodo 角色，应用访问策略，并规划针对 Amazon Aurora、Amazon Redshift 和本地 PostgreSQL 集群的联合查询。

只有 VQL 请求会向下传输到 VDP，结果集会向上传输。引擎之间没有源数据移动。 Aurora、Amazon Redshift 和本地集群响应由 VDP 联合优化器重写的本机 SQL。以下部分详细介绍了身份传播和策略实施。其他部分介绍了 MCP 服务器注册和代理部署步骤。

## 构建语义层

Denodo 中的语义模型不是一个单一的工件。它是 VDP 中基本视图、派生视图、指标视图和标签的集合，共同向消费者呈现具有业务意义的数据。在这篇文章中构建语义模型意味着创建每个部分。

我们构建了三遍：每个源表的基本视图、在客户级别连接“cid”上的基本视图的派生视图（“customer_360”）以及定义可在需要时加入的可重用支出聚合查询的指标视图（“lifetime_customer_value”）。

实际上，这种建模是在 Denodo Design Studio 中直观完成的。您将 Aurora、Amazon Redshift 和本地 PostgreSQL 源拖到画布上，在它们之间绘制联接，并通过表单而不是手写 DDL 重命名或重新键入字段（例如，将“cust_ref”映射到“customer_id”）。附加本文稍后介绍的安全策略也发生在同一 UI 中。

指标视图位于引用它们的派生视图旁边，定义一次并重复使用。如果两个团队针对相同的基础数据构建两个不同的客户级视图，则两者都会显示相同的指标定义。

## 基本视图

每个源表都成为 VDP 中的基本视图。对于 Aurora 客户表，这意味着使用 Design Studio 中的特定连接器引入 Aurora，指向架构，并让 VDP 自省列。设计工作室负责内省。生成的基本视图是物理列与其 VDP 对应项之间的一对一映射，并且它不会转换源数据。

创建过程中会发生两个额外的配置：

- **用于治理的列标签。** 客户基础视图上的“ssn”获取标签“pii_sensitive”。 “credit_card” 基础视图上的“card_num” 具有相同的标签。这些标签是 **受控访问** 部分中定义的全局安全策略所绑定的内容。
- **主键和连接字段。** `cid` 被标记为 `aurora_customer` 上的主键，以及 `redshift_order` 和 `postgres_rewards_account` 上的连接字段。 Design Studio 会在源元数据可用时从源元数据推断主键。否则，您可以在基本视图定义中设置它们一次。

对之前介绍的源表重复此操作。结果有六个基本视图：Amazon Aurora 上的“aurora_customer”、“aurora_address”和“aurora_credit_card”； Amazon Redshift 上的“redshift_order”和“redshift_product”；以及本地 PostgreSQL 上的“postgres_rewards_account”。

Design Studio 还通过 [Denodo Assistant](https://www.denodo.com/en/solutions/by-capability/denodo-assistant) 支持自然语言创作。开发人员可以用简单的英语描述视图（例如，“将 Aurora 的客户资料与‘cid’上的 Amazon Redshift 的订单总计结合起来”）并获取候选 VQL 定义，以便在保存之前在同一画布中进行审查和优化。细化是迭代的：后续提示在定义最终确定之前调整过滤器、联接或字段映射。本节中描述的治理和类型规则仍然适用于以这种方式创建的对象。

## 派生视图：客户 360

“customer_360”是跨三个源的客户级别视图，每个客户一行。订单详细信息和聚合单独存在，在我们接下来定义的指标视图中。
```
CREATE OR REPLACE VIEW customer_360 AS
SELECT aurora_customer.cid,
aurora_customer.first_name,
aurora_customer.last_name,
aurora_customer.email,
aurora_customer.ssn,
aurora_address.city,
aurora_address.state,
aurora_credit_card.card_num,
aurora_credit_card.card_type,
postgres_rewards_account.account_id,
postgres_rewards_account.create_date AS rewards_since
FROM (
(
aurora_customer AS aurora_customer
LEFT OUTER JOIN aurora_address AS aurora_address
ON aurora_customer.location = aurora_address.id
)
LEFT OUTER JOIN aurora_credit_card AS aurora_credit_card
ON aurora_customer.cid = aurora_credit_card.cid
)
LEFT OUTER JOIN postgres_rewards_account AS postgres_rewards_account
ON aurora_customer.cid = postgres_rewards_account.cid;
```
该定义的两个属性对于架构的其余部分很重要。首先，连接存在于 Denodo 平台中而不是管道中。没有 ETL 作业维护具体化的“customer_360”表。 VDP 在执行时解析连接：Aurora 返回配置文件和卡，本地集群返回奖励注册记录，VDP 将它们合并到“cid”上。其次，派生视图包含每一列，包括“ssn”和“card_num”。

对于治理和人工智能，我们还添加元数据：个人身份信息 (PII) 字段的列标签，以及记录视图和每个字段的描述。 Denodo 的助理可以使用法学硕士来提出这些建议。后面的部分将说明为什么此元数据很重要。

## 指标视图：终身客户价值

指标视图使用特定的 SOURCES/DIMENSIONS/METRICS 结构定义可重用的业务指标。有关完整语法，请参阅 VQL 指南中的[定义指标视图](https://community.denodo.com/docs/html/browse/latest/en/vdp/vql/defining_a_derived_view/defining_a_metric_view/defining_a_metric_view)参考。 `lifetime_customer_value` 并不存在于 `customer_360` 中。它生活在它旁边，作为它自己的对象：
```
CREATE OR REPLACE METRIC VIEW lifetime_customer_value
(
first_name, last_name, state, rewards_since, lifetime_spend, order_count, product_id,product_name, product_brand,product_dept, units_sold
)
SOURCES (
customer_360 AS customer_360,
redshift_order AS redshift_order,
redshift_product AS redshift_product
)
ASSOCIATIONS (
customer_360 redshift_order assoc_customer360_orders,
redshift_product redshift_order assoc_product_orders
)
DIMENSIONS (
customer_360(
first_name AS customer_360.first_name,
last_name AS customer_360.last_name,
state AS customer_360.state,
rewards_since AS customer_360.rewards_since
),
product(
product_id AS redshift_product.id,
product_name AS redshift_product.name,
product_brand AS redshift_product.brand,
product_dept AS redshift_product.dept
)
)
METRICS (
lifetime_spend AS sum((redshift_order.price*redshift_order.quantity)),
order_count AS count(redshift_order.id),
units_sold AS sum(redshift_order.quantity)
);
```
其他视图和外部报告工具可以像引用其他视图一样引用“lifetime_customer_value”。当业务规则更改时（例如，“lifetime_spend”应排除已取消的订单），更新会在指标定义中发生一次。每个消费者都会在下一个查询时获取更改，而无需触及派生视图或下游应用程序。不同的团队可以提出自己的衍生观点来传达其业务线看待世界的方式。基础数据保持共享，而语义解释保持独立，因此两个团队的编辑都不会干扰对方。

## VDP 如何执行联合查询

当代理运行 **示例** 中的自动注册问题（*“按生命周期支出计算，我们的前 20 位客户中哪些尚未注册奖励计划？”*）时，相应的 VQL 使用指标视图来计算结果集并评估所需的指标：
```
SELECT first_name, last_name, state, EVALUATE_METRIC(lifetime_spend) AS lifetime_spend
FROM lifetime_customer_value
WHERE rewards_since IS NULL
GROUP BY first_name, last_name, state
ORDER BY EVALUATE_METRIC(lifetime_spend) DESC
LIMIT 20;
```
尽管此查询仅引用指标视图，但 VDP 基于成本的优化器会计划跨相应数据来源的三个引擎的联合执行。最终的计划看起来大约是这样的：

- **下推到 Amazon Aurora**：Denodo 将客户、地址和“信用卡”的联接推送到 Aurora，返回客户配置文件字段，包括“first_name”、“last_name”、state 和“cid”。
- **下推到本地 PostgreSQL**：Denodo 推送“rewards_account”的投影，返回“cid”和“create_date”。
- **下推到 Amazon Redshift**：Denodo 将支出聚合推送到 Amazon Redshift，作为按“cid”分组的“SUM(价格 * 数量)”。
- **在 Denodo 内部组合**：Denodo 将 Aurora 配置文件结果与“cid”上的 PostgreSQL 奖励结果进行左连接，然后将所得结果与“cid”上的 Amazon Redshift 聚合支出进行右外连接。 Denodo 过滤“rewards_since”为 NULL 的行，将指标评估为按“first_name”、“last_name”和状态分组的外部分组聚合（“sum(sum) AS Lifetime_spend”），按“lifetime_spend”降序排序，最多返回 20 行。

该计划反映了每个来源的优势。 Amazon Redshift 执行聚合，Aurora 执行客户配置文件联接，因为所有三个配置文件表都位于其中，并且本地集群返回一小组奖励记录。 VDP 处理最终的跨引擎连接和 top-N 过滤器，使用三个紧凑的中间结果集，每个客户携带一行，而不是每个订单携带一行。手写的管道通常近似相同的形状，然后必须永远保持同步。

VDP 还以最便宜的方式处理类型协调。如果相同的标识符在一个源中存储为整数，在另一个源中存储为字符串，VDP 会将转换推入仍可对结果谓词进行过滤的源，而不是跨引擎拉取数据并随后协调类型。

## 受控访问：身份传播和运行时强制

跨数据源的广泛覆盖范围是企业范围语义层的核心特征之一，但当缺少运行时访问控制时，同样的覆盖范围会产生真正的风险。如果针对每个用户的过滤存在于代理的代码中，那么只需一次注入就能避免被绕过。如果它存在于法学硕士中，那么它实际上并不存在于任何地方。如果仅在各个源系统中强制执行，策略可能会不一致，并且可能无法解释跨源创建的业务含义。 Aurora 不知道“*最高支出者*”在语义层中的含义，堡垒主机后面的本地 PostgreSQL 集群也不知道。很多时候，尤其是在混合本地和云系统的混合场景中，跨所有系统的身份提供商甚至不是一种选择。

此架构中的方法是使用发起请求的人类用户的身份在语义层强制执行访问，并通过 Amazon Bedrock AgentCore 从 IdP 端到端传播到 Denodo Virtual DataPort。

图 6：从用户登录通过 Amazon Bedrock AgentCore 到 Denodo（MCP 服务器和 VDP）以及底层数据源的身份传播和查询流程。黑色箭头显示出站身份和查询路径。绿色虚线箭头显示过滤结果集的返回路径

- 用户根据企业 IdP 对应用程序进行身份验证。 IdP 返回一个 JWT，其中包含用户的身份和属性声明 - 角色、区域、部门以及 IdP 配置为发出的任何其他内容。
- 应用程序通过 AgentCore Gateway 使用用户的 JWT 作为不记名令牌调用代理。
- 网关将请求路由到托管 Strands 代理进程的 AgentCore 运行时。
- 当代理调用出站工具调用时，AgentCore Identity 执行代表令牌交换并返回一个新的访问令牌，其子声明是人类用户，其 aud 声明是 Denodo。
- 代理在 MCP 请求上将新的访问令牌作为“授权：承载 <access_token>”提供给 Denodo MCP 服务器。
- Denodo VDP 根据配置的 JWKS URL 验证 JWT，检查颁发者和受众，提取范围声明，并将调用者映射到 Denodo 角色。
- VDP 在查询时评估全局安全策略并向代理返回过滤后的结果集。
- VDP 查询数据源以满足请求并在返回结果之前合并结果。

步骤 2 中的网关 JWT 验证是可选的，因为 VDP 会在步骤 6 中重新验证令牌。启用网关验证后，格式错误的令牌会在请求路径中较早失败。

根据凭证提供程序配置，步骤 4 中的令牌交换使用 RFC 8693 令牌交换授予或 RFC 7523 JWT 不记名授予。凭证本身不输入代理代码。 AgentCore Identity 在调用时注入它。

步骤 8 中的呼叫者身份直通选项针对每个数据源启用，并要求 Denodo 和源共享相同的 IdP。当它适用时，呼叫者的身份会被端到端转发，从而在源头进行全面审核。

## 在 Denodo 中应用访问策略

Customer 360 数据受到监管。例如，某些用户（HR、欺诈分析师）可能需要查看 PII，例如社会安全号码 (SSN) 和完整的信用卡号码。但大多数用户（营销、分析）不得这样做。

Denodo 的机制是具有基于属性和角色的访问控制的全局安全策略。全局安全策略是适用于带有特定标记的视图或列的规则，在查询时根据调用者的角色和会话属性进行评估。底层视图未重构。

为了说明这一点，我们在 Aurora 的基本视图上将两列（“ssn”和“card_num”）标记为 PII。我们创建一个全局安全策略“mask_pii_columns”。

- 受众：调用者的角色不是“hr_user”。
- 元素：适用于带有“pii_sensitive”标签的列。
- 操作：带星号的掩码 (`****`)。

然后我们定义两个 Denodo 角色。

- `hr_user`：已在`customer_360`上执行。查看每一列。
- `marketing_user`：已在`customer_360`上执行。将看到 `ssn` 和 `card_num` 为 `****`，因为该策略适用。

当“marketing_user”运行 VQL 查询时：
```
SELECT cid, first_name, last_name, state, ssn
FROM customer_360
WHERE state = 'WI';
```
VDP 在规划查询之前评估全局安全策略。它发现“ssn”带有“pii_sensitive”标签，并且调用者的角色不是“hr_user”，因此它重写了投影，为“ssn”返回“***”。

对于行级过滤（例如，美国东部分析师应该只看到东海岸客户），可以使用相同的机制进行扩展。策略条件甚至可以取决于从 JWT 令牌映射的会话属性，或从外部表动态提取的会话属性。

### 关于负责任的人工智能的说明

Denodo 的全局安全策略在语义层过滤 PII，因此该模型永远不会看到不应看到的调用者的“ssn”或“card_num”。即便如此，客服人员的响应也可以用自然语言回显客户标识符、位置或消费模式。使用与底层监管数据相同的处理和保留策略来处理代理输出：范围日志记录和转录本存储，对内容和敏感主题控制应用 Amazon Bedrock Guardrails，并限制可以读取响应的人员。如需更广泛的指导，请参阅 [Amazon Bedrock 中的负责任的 AI](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html)。

## 跨层审计和可观察性

请求路径的每一层独立记录。 AgentCore 运行时将调用记录发送到 [Amazon CloudWatch](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/WhatIsCloudWatchLogs.html)。 AgentCore Gateway 记录入站 MCP 请求，包括调用者的 JWT 子声明。 Denodo MCP 服务器将工具调用记录到其自己的日志中。 Denodo VDP 的审核日志捕获完整的 VQL 请求、映射的 Denodo 角色、已解决的联合计划和策略评估结果。

这些日志也可以[合并到 Amazon CloudWatch](https://community.denodo.com/kb/en/view/document/Monitoring%20Denodo%20with%20Amazon%20CloudWatch)。当需要与人类用户关联的每个源审计时（例如，为了 HIPAA 或 SOX 合规性），请在这些源的基本视图上配置直通会话凭据，以便 Denodo 将调用者的身份转发到源支持的源系统，而不是依赖服务帐户。

## 通过 Denodo MCP 服务器公开该层

[Denodo MCP 服务器](https://community.denodo.com/docs/html/document/denodoconnects/latest/en/Denodo%20MCP%20Server%20-%20User%20Manual) 是位于 MCP 客户端和 VDP 之间的附加组件：下载发行版，解压它，编辑 `config/application.properties`，然后启动它。服务器在“http://<mcp-host>:8080/<database>/mcp”处侦听可流式传输的 HTTP MCP 请求，并通过 JDBC 将它们转发到 VDP。

三个配置值对于本演练很重要。

- `mcp.security.oauth2.enabled=true`：接受入站 MCP 请求上的 OAuth 2.0 不记名令牌。与 VDP 的 OAuth 身份验证器配置配合使用，令牌转发到 VDP 进行验证和角色解析（另请参阅**受控访问**部分）。
- `vdp.datasource.jdbcUrl=jdbc:vdb://<vdp-host>:9999/`：到达 VDP 的 JDBC URL。每个请求的目标特定数据库来自 MCP 端点路径。
- `mcp.visibility.tags=mcp` 控制哪些视图对 MCP 服务器可见。如果已定义，则只有至少标记有这些标签之一的视图才是可见的。

服务器实现 [MCP OAuth 2.0 授权](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization) 流程，包括 RFC 9728 受保护资源元数据和 RFC 7591 动态客户端注册。

### 关于 IdP 兼容性的说明

Denodo MCP 服务器记录了对 Okta、Ping Identity 和 Keycloak 的自动动态客户端注册流程的支持。对于其他身份提供商，MCP 服务器还接受手动客户端配置，其中 OAuth 令牌在带外获取并作为 MCP 请求上的静态“授权”标头转发，如 [Denodo MCP 服务器用户手册](https://community.denodo.com/docs/html/document/denodoconnects/latest/en/Denodo%20MCP%20Server%20-%20User%20Manual#h.hs7cb89txbqj)。

## 在服务器前面放置一个应用程序负载均衡器

如果 Denodo MCP 服务器在与 VDP 相同的 VPC 中的 Amazon EC2 或 Amazon EKS 上运行，请通过 [Application Load Balancer](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html) 公开它，并使用 HTTPS 侦听器和来自 [AWS 证书管理器](https://docs.aws.amazon.com/acm/latest/userguide/acm-overview.html) 的证书。这为 AgentCore Gateway 提供了稳定的 HTTPS 端点，并从 MCP 服务器进程中卸载了 TLS 终止。目标组：HTTP，端口 8080。运行状况检查路径应接受 200 和 404 作为运行状况响应，因为当服务器启动并连接到 VDP 时，根路径返回 404，而“/health”返回 200。

## 验证

为了确认语义层、代理和身份流按预期工作，我们通过代理运行三个查询类别，再加上一次治理重新运行，该治理重新运行演示了 **受控访问** 部分中的相同查询两个用户属性。我们可以使用 Denodo 的数据市场助手（它依赖于幕后的等效工具）来快速验证我们的场景。

### 查询 1，仅限 Aurora

*“列出我们在威斯康星州的客户及其所在城市。”*

代理生成并运行：
```
/* The query needs to retrieve first_name, last_name, and city from the customer_360 view where state = 'WI', ordered by last_name. The output will be multiple rows with 3 columns. The table is at customer granularity (one row per customer). No obligatory columns are present, so a simple WHERE filter on state suffices. */
SELECT "first_name",
"last_name",
"city"
FROM "customer_360"."customer_360"
WHERE "state" = 'WI'
ORDER BY "last_name"
```
VDP 的优化器确定投影和过滤只需要 Aurora 端数据，并将单个查询下推到 Amazon Aurora。基于探测查询，代理可以将过滤器从威斯康星州转换为谓词“state = 'WI'”。 Amazon Redshift 和本地集群不受影响。

### 查询 2，仅限 Redshift

*“按销量计算，我们排名前 10 的产品是什么？”*

代理生成：
```
/* The user wants top 10 products by total units sold from a metric view. I need to use EVALUATE_METRIC for units_sold, GROUP BY product_name, ORDER BY the metric descending, LIMIT 10. The output will be multiple rows (up to 10) with two columns: product_name and total_units_sold. */
SELECT "product_name",
EVALUATE_METRIC("units_sold") AS "total_units_sold"
FROM "customer_360"."lifetime_customer_value"
GROUP BY "product_name"
ORDER BY "total_units_sold" DESC
LIMIT 10
```

图 7：VDP 将整个查询（联接、聚合、排序和限制）推送到 Amazon Redshift，因为产品和订单数据都驻留在其中。 Aurora 和本地集群未受影响

### 查询3，三向联合

*“按终身价值排名前 20 位的客户中，哪些尚未加入奖励计划？”*

代理生成：
```
/* This is a metric view, so I need to use EVALUATE_METRIC for lifetime_spend and order_count. The query needs to: 1. Aggregate by first_name, last_name, state, rewards_since to get total lifetime_spend and order_count 2. Rank top 20 by total lifetime_spend 3. Filter those top 20 where rewards_since IS NULL I'll use a CTE with ROW_NUMBER() to get top 20, then filter for NULL rewards_since in outer query. */
WITH "ranked_customers" AS (
SELECT "first_name",
"last_name",
"state",
"rewards_since",
EVALUATE_METRIC("lifetime_spend") AS "total_lifetime_spend",
EVALUATE_METRIC("order_count") AS "total_order_count"
FROM "customer_360"."lifetime_customer_value"
GROUP BY "first_name",
"last_name",
"state",
"rewards_since"
ORDER BY "total_lifetime_spend" DESC
LIMIT 20
)
SELECT "first_name",
"last_name",
"state",
"rewards_since",
"total_lifetime_spend",
"total_order_count"
FROM "ranked_customers"
WHERE "rewards_since" IS NULL
ORDER BY "total_lifetime_spend" DESC
```
![代理输出列出了未加入奖励计划的按终身价值排名前 20 位的客户](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/06/ML-21332-8.png)

图 8：三向联合查询的代理结果，按生命周期价值列出了尚未加入奖励计划的顶级客户

VDP 计划跨三个引擎，如 **构建语义层** 部分中所述：来自 Aurora 的配置文件、来自 Amazon Redshift 的汇总支出、来自本地集群的注册记录以及 VDP 内的最终加入和前 N 个。 POC 数据中的最高结果是来自威斯康星州密尔沃基的 Marcus Chen，其终生支出为 47,832 美元，是一位支出较高且没有奖励注册的客户，正是**示例**中的示例问题中的自动注册目标。请注意，法学硕士不需要提出“lifetime_spend”的定义，因为该公式是度量视图中定义的语义模型的一部分。

### 治理重演

我们运行查询 1，并将“ssn”添加到投影中，作为两个不同的调用者：
```
SELECT cid, first_name, last_name, state, ssn
FROM customer_360
WHERE state = 'WI';
```

作为“hr_user”，结果包括“ssn”值。作为“marketing_user”，结果返回与“ssn”相同的行，并以星号作为屏蔽值。两次运行之间的查询文本、代理代码、MCP 服务器、VDP 或 Aurora 没有更改。 **受控访问**部分中的全局安全策略“mask_pii_columns”在查询时根据调用者的角色进行评估，VDP 相应地重写投影。同样的行为也适用于“card_num”。

## 扩展到其他来源

将 AWS 外部的源添加到“customer_360”，无论是用于 CRM 记录的 Salesforce、用于客户服务数据的 ServiceNow 还是用于 ERP 表的 SAP，与 Aurora、Amazon Redshift 和本地集群的建模练习相同。创建一个基本视图，将其加入到“cid”上的派生视图中，并标记敏感列。指标视图、全局安全策略和代理的 VQL 不会更改。变化的是 VDP 用于到达源的包装器。例如：

- **Salesforce** 通过 [Denodo Salesforce 连接器](https://community.denodo.com/docs/html/browse/latest/en/vdp/administration/creating_data_sources_and_base_views/salesforce_sources/salesforce_sources) 连接，并通过 REST 或批量 API 进行 OAuth 2.0 身份验证和“VQL 到 SOQL”转换。
- **ServiceNow、Microsoft Dynamics 365 和其他 SaaS 工具** 使用 Denodo 的 [SaaS 向导模板](https://community.denodo.com/docs/html/browse/latest/en/vdp/administration/creating_data_sources_and_base_views/software_as_a_service_wizards/software_as_a_service_wizards)，针对常见 API 进行了预配置。
- **SAP ERP** 使用 SAP Java 连接器通过 [BAPI 源](https://community.denodo.com/docs/html/browse/latest/en/vdp/administration/creating_data_sources_and_base_views/bapi_sources/bapi_sources) 连接。 VDP 调用 SAP RFC 并将响应整理为行。

特工不知道其中哪一个位于下面。它在 VQL 中查询“customer_360”。 Denodo 的包装器处理源本地转换，并且无论行来自 JDBC 引擎、REST API 还是 RFC 调用，Denodo 的全局安全策略都统一应用。

一项部署时决策因来源而异：是将调用者的身份传递给来源还是作为服务帐户进行连接。当源支持时，传递可在源处提供端到端审核（例如，Kerberos 到 SAP 或 OAuth 到 Salesforce）。服务帐户连接更简单，并且源的审核显示查询来自 Denodo。

## 部署：Denodo Agora 与自我管理

AWS 上的 Denodo 以两种形式之一运行。两者都使用相同的虚拟数据端口、相同的 VQL、相同的全局安全策略、相同的 MCP 服务器。该选择是可操作的。

### Agora：完全托管

[Denodo Agora](https://www.denodo.com/en/denodo-platform/denodo-agora) 是 Denodo 的完全托管云服务，可在 [AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-ze2asxcox56o2?sr=0-3&ref_=beagle&applicationId=AWSMPContessa) 上使用。 Agora 运行在分面架构上。 **控制平面**（解决方案管理器、设计工作室、调度程序管理、监控/诊断）在 Denodo 的云帐户中运行，而**执行平面**（VDP、调度程序、数据目录）在客户的 AWS 帐户中运行。涉及数据的计算位于客户的 VPC 中。管理界面由 Denodo 运营。

当您不想运行该应用程序并且 Denodo 发布的更新节奏适合您的组织时，请选择 Agora。

### 在 Amazon EC2 或 Amazon EKS 上自行管理

自我管理部署将 Denodo 平台完全安装在客户的 AWS 账户中。 Denodo 在 AWS Marketplace 上发布 VM 映像，并为 Amazon EKS 提供带有 Helm 图表的容器映像。您负责处理集群、升级和备份。

当合规性需要特定的部署状态时、当您想要控制版本节奏时、或者当参考架构需要特定 VPC 内的 Denodo 集群时，请选择自我管理。

## 获取 AWS 之外的资源

两种部署形式都将 VDP 放置在客户的 AWS 账户中。在这两种情况下，到达本地源都会遇到相同的问题：从托管 VDP 的 VPC 到本地集群的网络路径，通过组织已使用的任何混合连接选项进行配置。对于 Salesforce 或 ServiceNow 等 SaaS 源，无需额外设置，因为执行平面默认具有出站 Internet 访问权限，这足以进行 OAuth 2.0 身份验证和 REST API 调用。

## 结论和从哪里开始

对企业数据的可靠代理访问需要三个要素协同工作：可以规划和生成查询的基础模型、通过实时源系统呈现对业务有意义的数据的语义层，以及托管代理和管理身份流的运行时。 Amazon Bedrock、Denodo Platform 和 Amazon Bedrock AgentCore 各自扮演其中一个角色。

代理与语义层对话，而不是直接与底层数据库对话。基本视图、派生视图、指标视图、标签和全局安全策略位于 VDP 中。当源模式发生变化时，当新源上线时，或者当治理规则发生变化时，更新会发生在语义层中，并且每个消费者都会在下一个查询时拾取它。语义层携带的附加元数据（文档、描述、度量公式和 360 图）为模型提供了更基础的业务上下文来进行推理，而不仅仅是原始模式。

### 从哪里开始

尝试 [Agora on AWS](https://aws.amazon.com/marketplace/pp/prodview-ze2asxcox56o2) 并按照说明进行部署。 Agora 是 Denodo 的完全托管云服务，用于在 AWS 上部署人工智能数据层，提供对分布式企业数据的实时、受管控的访问。

大多数团队通过缩小范围和扩展来实现这一目标。

- **选择一个代理工作流程**，该工作流程跨越两个或三个不同的源系统，其响应时间比今天应有的时间要长。
- **写出三到五个具体问题**工作流程需要回答。这些是语义层第一天必须支持的查询。
- **连接数据源并在工作流程涉及的源表上创建基本视图**。在创建过程中标记 PII 列。
- **构建问题所需的派生视图**和**指标视图**。
- **实施全球安全政策**，帮助保护 PII、受保护的健康信息 (PHI)、支付卡行业 (PCI) 或其他敏感信息。
- **将 Denodo MCP 服务器注册为 AgentCore 网关目标**并使用前面部分中的模式将 Strands 代理连接到它。使用“agentcore部署”进行部署。
