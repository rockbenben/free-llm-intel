# 用 Amazon Bedrock 上的 Grok 4.7 构建长程任务智能体

SpaceXAI 的 Grok 4.7 现已在 Amazon Bedrock 上可用，Amazon Bedrock 提供来自多家提供商的基础模型（FM）供选择。据 SpaceXAI 介绍，Grok 4.7 经过训练，能在更难的任务上工作更长时间，并且知道什么时候该检查自己的工作。这一点对智能体最为关键：智能体要把一个任务一步步推进到底，还必须沿途验证自己找到的东西。

这样工作的智能体要做的远不止查资料。它得先形成一个候选答案，拿已经掌握的信息去核对，再不断修正直到对得上。Grok 4.7 提供了一个推理强度（reasoning effort）设置，控制每次生成回答前投入多少斟酌；对智能体负载来说，一个实际的问题是要跑哪一档。

在本文里，我们基于 Grok 4.7 构建了一个工具调用（tool-calling）智能体，并在三个需要搜索而非查找的任务上评估它。这三个任务是：从告警中诊断一次涉及两个服务的故障、在相互牵连的约束下排定维护计划、在预算内选出一组最优迁移。每个任务有且只有一个正确答案，并用穷举法验证过。我们在每一档推理强度下都跑了这三个任务，每个任务各跑六次，合计 72 次智能体运行。

72 次运行里智能体答对了 67 次。`xhigh` 档 18 次全对；`low` 档 18 次里对了 15 次，输出 token 只用了 `xhigh` 的大约八分之一。这中间有一条清晰的取舍线，你可以按请求逐个调整。本文会说明怎么在自己的任务上测量这条线，以及怎么在生产环境监控它。

全文都用 token 数而不是金额来报告。token 单价会变，而你自己的成本正是从用量数推算出来的，所以以 token 表述的度量结果不会过期。

SpaceXAI 公布的基准测试结果与这一侧重相符。相对 Grok 4.6 提升幅度最大的，正是衡量持续工作能力而非单轮作答的那些类别。

基准测试显示的是模型在标准任务上的表现。对你自己的工作负载，有用的下一步是在同你的任务形状相近的任务上做测量，这正是本文后半部分要一步步走一遍的内容。

SpaceXAI 给出的 Grok 4.7 上下文窗口是 500K token，输入支持文本和图像，输出为文本。在 Amazon Bedrock 上，该模型支持可配置的推理强度、工具调用和结构化输出。

## 如何在 Amazon Bedrock 上访问 Grok 4.7

Grok 4.7 运行在 `bedrock-runtime` 端点上，通过[跨区域推理](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)配置文件（profile）访问。可用的配置文件有两个：

| **推理配置文件** | **路由范围** | **适用场景** |
| --- | --- | --- |
| **us.xai.grok-4.7** | 在美国地理范围内 | 你有美国的数据驻留要求 |
| **global.xai.grok-4.7** | 商用 AWS 区域 | 你没有驻留限制，想要最大的容量 |

跨区域推理会把请求路由到多个 AWS 区域，因此你不必逐个区域管理容量就能拿到更高吞吐。请求里填写的是推理配置文件，而不是裸的模型 ID。

该模型支持兼容 OpenAI 的 Chat Completions 与 Responses API，也支持 Amazon Bedrock Converse API。在 Converse 上，推理内容以 `reasoningContent` 块返回，与 `text` 块并列。`inferenceConfig` 里只设 `maxTokens`，模型专属参数（比如推理强度）放进 `additionalModelRequestFields`。

至于当前支持的区域、服务层级和 token 单价，请参见 Amazon Bedrock 用户指南中的 Grok 4.7 模型卡，以及 Amazon Bedrock 定价页（[https://aws.amazon.com/bedrock/pricing/](https://aws.amazon.com/bedrock/pricing/)）。

## 前提条件

- 一个可访问 Amazon Bedrock 的 AWS 账户，并已为 Grok 4.7 开通模型访问。
- Python 3.9 或更高版本，并安装了 `openai`、`boto3` 和 `aws-bedrock-token-generator`。
- 环境中已配置好 AWS 凭证。

你的 AWS Identity and Access Management（IAM）身份需要同时对你所用的推理配置文件和你账户的默认 project 拥有 `bedrock:InvokeModel` 权限：

- `arn:aws:bedrock:{region}::inference-profile/us.xai.grok-4.7`，或对应的 `global.` 版本。
- `arn:aws:bedrock:{region}:{account-id}:project/default`。

这两项资源都要写进策略语句里。除推理配置文件之外，默认 project 的权限同样是必需的。

## 连接模型

生产环境中，我们建议用现有的 AWS 凭证生成短期 bearer token，这样认证始终绑定在你的 IAM 身份上，也不必存放任何长期机密：

```
from aws_bedrock_token_generator import provide_token
from openai import OpenAI

REGION = "us-west-2"
MODEL_ID = "us.xai.grok-4.7"

client = OpenAI(
    api_key=provide_token(region=REGION),
    base_url=f"https://bedrock-runtime.{REGION}.amazonaws.com/openai/v1",
    timeout=360,
    max_retries=0,  # retries are handled explicitly, see "Build in retries" below
)
```

推理 token 计入输出 token，会在答案文本生成之前就把 `max_completion_tokens` 消耗掉，所以设上限时要给两部分都留出空间。如果推理阶段就把上限用完，返回的响应里就没有答案文本，因此要在智能体代码里检查内容为空的情况，一旦发现就调高上限。我们的运行把上限设为 32,768 个 token，在每一档推理强度下都留有余量。

Grok 4.7 支持四档强度：`low`、`medium`、`high` 和 `xhigh`。不同模型版本之间强度档位可能变化，所以值得向服务端确认，而不是把清单写死在代码里：

```
def supported_effort_levels(candidates=("none", "low", "medium", "high", "xhigh", "max")):
    supported = []
    for level in candidates:
        try:
            client.responses.create(model=MODEL_ID, input="Say OK.",
                reasoning={"effort": level}, max_output_tokens=2048)
            supported.append(level)
        except Exception as exc:
            if "unsupported_value" not in str(exc) and "invalid_value" not in str(exc):
                raise
    return supported


print(supported_effort_levels())  # ['low', 'medium', 'high', 'xhigh']
```

## 设计需要推理的任务

许多智能体评测考的是细致程度：读一条记录、筛选、求和。这类任务自有价值，但要看出推理强度带来了什么，任务就必须需要搜索：答案不能直接从数据里读出来，得先提出来、再加以验证。

我们搭建了一个包含 20 个服务的合成环境，通过七个工具暴露出来，并在它之上设计了三个任务。每个任务有且只有一个正确答案，而且每个任务的设计都保证靠快捷启发式方法找不到答案。

| **任务** | **智能体要做什么** | **为什么算推理任务** |
| --- | --- | --- |
| **two_fault_diagnosis** | 两个服务在 03:00 静默失败，另有 12 个服务发出告警。找出失败的那两个 | 失败的服务不发出告警，所以答案不在告警的服务里。可能的配对有 190 对，只有一对能恰好解释观察到的全部告警 |
| **maintenance_schedule** | 四个夜里给八个服务打补丁，每晚两个，受十条约束，另有一条规则：同一团队的两个服务绝不能排在同一夜 | 可能的排法有 2,520 种，合法的只有一种。团队规则依赖智能体必须去查的数据 |
| **migration_budget** | 在预算内挑选要迁移的候选，使风险削减最大化，其中包含传递性的前置依赖 | 可行集合有 53 个，最优的只有一个。先挑单项比例最优的那些，得到的集合比最优解少 9 分 |

有四条做法能让这样的度量站得住脚，它们同样适用于大多数智能体评测。

**评分器依赖的规则要全部写明。** 如果 prompt 留下边界情况没有交代，一个合理的回答就可能被判错，评测最后量出来的就成了规格说明而不是模型。例如诊断任务的 prompt 就明确写出：失败的服务不会发出属于自己的告警。

**证明每个任务只有一个答案。** 每个环境都小到可以穷举，因此在正式运行之前我们把所有候选答案都核对了一遍。就排期任务而言，只需几行：

```
import itertools

ALL_SLOTS = sorted(set(itertools.permutations([1, 1, 2, 2, 3, 3, 4, 4])))

def valid_schedules(services, constraints):
    return [s for slots in ALL_SLOTS
        if satisfies(s := dict(zip(services, slots)), constraints)]

assert len(valid_schedules(SERVICES, CONSTRAINTS)) == 1  # exactly one answer
assert len(valid_schedules(SERVICES, CONSTRAINTS_WITHOUT_TEAM_RULE)) > 1  # the rule matters
```

**只评那一行必须给出的最终答案，不评整段回答。** 每个 prompt 都要求智能体以 `FINAL: auth, checkout` 这样的行收尾。评分器只读这一行，于是即便回答在陈述推理过程时讨论了其他候选，评的仍然是它给出的结论：

```
def final_line(answer):
    lines = [l for l in (answer or "").splitlines() if "FINAL" in l.upper()]
    return lines[-1] if lines else None
```

**格式与正确性分开统计。** 最终答案行缺失和最终答案写错是两种不同的信号。在我们的运行里，72 次回答全部包含可评分的最终答案行。

在合法取值已知时，用 `enum` 约束工具参数，这样每次工具调用针对的都是真实存在的资源：

```
TOOLS = [
    {"type": "function", "function": {
        "name": "get_dependencies",
        "description": "Services that one service directly depends on.",
        "parameters": {
            "type": "object",
            "properties": {"service": {"type": "string", "enum": SERVICE_NAMES}},
            "required": ["service"],
        }}},
    # The remaining six tools follow the same shape.
]
```

system prompt 刻意写得很短，只要求智能体在给出答案前先检查一遍自己的答案：

```
AGENT_SYSTEM = (
    "You are an infrastructure analyst agent. Use the tools to gather facts and never guess "
    "a value you can look up. Before answering, check your answer against every rule in the "
    "task. End with the FINAL line exactly as the task specifies."
)
```

智能体循环就是标准的工具调用循环：带着设置好的 `reasoning_effort` 调用模型，执行返回的每一个工具调用，把结果按 `tool_call_id` 追加回去，如此重复直到模型不再请求工具。在整个循环里累计 `prompt_tokens` 和 `completion_tokens`，就得到下一节报告的 token 数。

## 结果

每档强度下每个任务跑六次，合计 72 次运行。智能体答对了 67 次。

| **任务** | **low** | **medium** | **high** | **xhigh** |
| --- | --- | --- | --- | --- |
| **two_fault_diagnosis** | 6 次中 5 次 | 6 次中 6 次 | 6 次中 6 次 | 6 次中 6 次 |
| **maintenance_schedule** | 6 次中 5 次 | 6 次中 5 次 | 6 次中 5 次 | 6 次中 6 次 |
| **migration_budget** | 6 次中 5 次 | 6 次中 6 次 | 6 次中 6 次 | 6 次中 6 次 |
| **三项任务合计** | **18 次中 15 次** | **18 次中 17 次** | **18 次中 17 次** | **18 次中 18 次** |

| **单次运行** | **low** | **medium** | **high** | **xhigh** |
| --- | --- | --- | --- | --- |
| **平均输出 token** | 1,184 | 6,430 | 6,778 | 9,147 |
| **输出 token 相对 low 的倍数** | 1.0x | 5.4x | 5.7x | 7.7x |
| **平均工具调用次数** | 17.2 | 18.7 | 17.8 | 18.1 |
| **耗时中位数** | 18 秒 | 98 秒 | 89 秒 | 106 秒 |

图 1：每一档推理强度下答对的运行占比（左），以及单次运行平均输出 token 数，并叠加了单次运行耗时中位数（右）

三点观察。

**`xhigh` 每次运行都答对。** 三个任务的 18 次运行在 `xhigh` 下全部正确，`medium` 和 `high` 各自 18 次里对了 17 次。每个任务每档只有六次运行，档位之间的差距只能算方向性参考，还称不上统计定论；不过这个方向在三个任务上是一致的。

**强度改变的是智能体推理多少，而不是探索多少。** 工具调用次数基本持平，每一档都在每次 17.2 到 18.7 之间。不管哪档强度，智能体收集到的事实都一样，变化的是它在这些事实上投入多少推理：输出 token 从 `low` 档的 1,184 涨到 `xhigh` 档的 9,147。

**`low` 的性价比很高。** 在 `low` 档，智能体 18 次里答对 15 次，输出 token 只有 `xhigh` 的大约八分之一，单次运行耗时中位数 18 秒。如果可以接受略低一点的完成率，或者答案在下游还会被复核，`low` 是一个高效的选择。如果要求每个答案一次就对，更高的档位是更稳妥的默认值。

## 强度档位如何塑造答案

这些任务各自围绕一类特定的难度设计，观察各档强度如何处理它们，就能看清额外的推理什么时候值得。

**最优化。** 迁移任务奖励的是考察组合，而不是逐个给候选排序。只挑单项比例最优的那些候选，会得到一个看起来合理、但比最优解少 9 分的答案。`medium` 及以上，智能体在 18 次运行里全部找到了最优集合。

**假设检验。** 诊断任务要求双向核对一组候选：每一条告警都要能被解释，每一个保持静默的服务也都要与答案相符。`medium` 及以上，智能体在 18 次运行里全部识别出了正确的那一对。

**约束满足。** 排期任务把列出的十条约束和一条团队规则叠在一起，而团队规则依赖需要查出来的归属数据。`xhigh` 在每次运行里都产出了合法排期，这也是最高档带来差别最明显的任务。

三个任务合起来的规律是：当智能体必须把几个候选答案放在一起相互权衡，而不是沿单一路径走到结果时，额外的推理强度最有价值。

## 在生产环境监控推理

生产环境里没有已知答案可供评分，但你知道每次运行用了多少输出 token、调了多少次工具。这些数字能给出有用的运维信号。

各档答对的运行，推理量都保持在一条明确的底线之上。`medium` 及以上每一次答对的运行至少用了 1,739 个输出 token，典型运行是几千个。一次运行如果完全没有工具调用，或者输出量明显低于该档的正常水平，就值得标记出来复核：

```
def flag_for_review(run, baseline):
    """baseline: output tokens of graded, correct runs at the same effort level."""
    reasons = []
    if run["tool_calls"] == 0:
        reasons.append("made no tool calls")
    if run["output_tokens"] < 0.2 * min(baseline):
        reasons.append(f"used {run['output_tokens']} output tokens, "
            f"under a fifth of the lowest correct run ({min(baseline)})")
    return reasons
```

基线要从你已经评过分的运行里标定，按任务、按强度档位分别计算，再套用到没评过分的运行上。一次运行被标记，就等于提示你去检查或者重跑。`low` 档每次运行都很短，输出量的信号意义更弱，所以要配合抽查使用。

在 system prompt 里要求智能体核查自己的答案，这个做法值得保留，因为复核一次运行时，它的推理更容易跟着走一遍。凡是存在已知答案的地方，都把它和自动评分配合起来，这样质量的度量就独立于运行记录本身。

## 如何选择推理强度

这些结果可以归纳出几条实用规则。

**按任务类型配强度。** 涉及搜索、最优化或假设检验的任务，从 `medium` 及以上获益最大。沿单一路径完成、或答案在下游会被复核的任务，用 `low` 就能高效跑完。

**按请求设强度，而不是按智能体设。** 强度是请求级参数，所以同一个智能体可以在规划和验证步骤上用更高的档位，在机械步骤（比如给工具结果排版）上用 `low`。这样既拿到高档位的大部分可靠性，又压低了 token 成本。

**在自己的任务上量，并且重复。** 每种配置只跑一次，就只有一个观测点。每种配置重复跑几次，才能看出它有多一致。

**监控推理量。** 按强度档位分别追踪每次运行的输出 token 和工具调用次数，能在结果被使用之前给你一个复核信号。

## 这次度量的局限

**每个任务、每档强度只有六次运行。** 这足够在三个任务上显示出一致的方向，但不足以给出置信区间。档位之间的差距只能当方向性参考。

**合成环境。** 工具读的是代码生成的数据，正因如此才能证明每个任务有且只有一个答案，并实现自动评分。真实工具会带来延迟、部分结果和错误，这些这里都没有测。

**是分钟，不是小时。** 单次运行耗时中位数从 `low` 档的 18 秒到 `xhigh` 档的 106 秒。这是长程任务缩小后的替身。方法可以照搬，绝对数字不行。

**一个模型版本、一个区域、每个任务一种 prompt。** 同一个任务换个说法，结果可能就变，这也是为什么把每条规则都写明确很重要。

**是 token 数，不是成本。** 要换算成金额，请按 Amazon Bedrock 定价页上你所用推理配置文件和服务层级的当前费率计算。Global 与美国 Geo 的配置文件定价不同，Flex 和 Priority 服务层级还会乘上相应倍率。

## 智能体负载的运维控制

**把重试做进设计。** 调用量大的智能体应当把重试视为设计的一部分。设好请求超时，只对可重试的错误重试，采用带抖动的指数退避，并在响应带回 `Retry-After` 头时遵守它：

```
import random, time

RETRYABLE = {408, 429, 500, 502, 503, 504}

def call_with_backoff(fn, attempts=7, base=4.0, cap=180.0):
    for attempt in range(1, attempts + 1):
        try:
            return fn()
        except Exception as exc:
            status = getattr(exc, "status_code", None)
            retryable = status in RETRYABLE or "timed out" in str(exc).lower()
            if not retryable or attempt == attempts:
                raise
            time.sleep(random.uniform(base, min(cap, base * 2 ** attempt)))
```

按需吞吐是随时间逐步扩上去的，所以新上线的高调用量负载要慢慢加压，不要一上来就按全速发。

**运行审计。** 模型调用日志会把请求和响应数据写入 Amazon Simple Storage Service（Amazon S3）或 Amazon CloudWatch Logs。这样你就能拿到某次运行完整的记录，供事后复核。

**规模化监控推理量。** Amazon CloudWatch 指标提供 token 用量的汇总视图，前面说的按档位标定的基线在这里就能变成可告警的东西。

**把开销归属到各个智能体。** AWS Cost Explorer 的成本明细和 AWS Cost and Usage Report 能按模型拆分用量，再配上按任务统计的 token 数，单位经济性和总账单一并都能看清。

**让成本对上紧迫程度。** 服务层级是按请求设定的，所以同一个部署可以把夜间的分析任务走 Flex 层级，把交互式请求走 Priority。对于跑在更高强度档位的负载，层级选择是又一根成本杠杆。

**选择路由配置文件。** 跨区域推理拓宽了一次长运行可取用的容量池。Global 配置文件从商用的 AWS 区域中按需取用提供服务，每个 token 的价格通常低于按地理范围路由。US 配置文件把处理留在美国境内。选择时既要考虑你的数据驻留要求，也要考虑成本。

## 清理

本文的示例除按请求产生的 token 用量之外，不会创建任何计费的 AWS 资源。如果你生成了长期 Amazon Bedrock API key，用完请到 Amazon Bedrock 控制台把它删除，因为它在被撤销之前一直有效。由 IAM 凭证生成的短期 token 会自行过期。

如果测试时开启过向 Amazon S3 写模型调用日志，请检查那个存储桶并移除不再需要的对象。

## 结语

SpaceXAI 把 Grok 4.7 训练成能在更难的任务上工作更久，并且知道什么时候该核查自己的工作。在这三个需要搜索而非查找的任务上，智能体 72 次运行答对了 67 次，而 `xhigh` 档每次都答对。由于推理强度是按请求设定的，你可以自己决定智能体的每一步落在「彻底程度」与 token 成本这条取舍线的哪个位置。

有三件事值得带进你自己的评测里。设计只有一个可证明答案的任务，并把评分器依赖的每条规则都写明。重复运行，这样你能看出每种配置有多一致。按强度档位监控输出 token 和工具调用次数，让你在质量度量之外还有一条运维信号。
