# 构建自助式 AWS Health 分析，借助由 Amazon Bedrock 驱动的 AI agent 发现可执行的运行状况洞察

在一个典型的周一上午，某企业运维团队会收到多条 AWS Health 通知，内容涉及 Amazon Linux 2 生命周期终止、RDS 版本弃用，以及分布在 50 多个账号中的 EC2 实例退役。没有自助式分析，团队就无法快速识别哪些事件会影响生产系统、哪些事件需要立即处理、哪些可以纳入长期规划，也无法判断每一类事件的业务影响。

运维团队还要花时间等待技术客户经理（Technical Account Manager，TAM）解读运行状况事件，这让关键运维决策进一步延后。最终，时间都花在被动救火上，而不是创新上。

本文介绍如何构建 **Chaplin**（Customer Health and Planned Lifecycle Intelligence Nexus），这是一个开源解决方案，它通过 Model Context Protocol（MCP）暴露的 AI agent 提供自助式运行状况事件分析。借助 Chaplin，团队可以直接在兼容 MCP 的 AI 助手中用自然语言提问，并获得精确、结合上下文的回答，无需为日常分析依赖 AWS Support。详细的部署说明见 [Chaplin AWS Health Agentic Assistant GitHub 仓库](https://github.com/aws-samples/sample-aws-health-agentic-assistant)。

## 挑战：被动的运行状况事件管理

在 AWS 上运行生产工作负载的企业，需要在数十到数百个账号之间处理持续不断的运行状况事件——服务变更、维护窗口、安全补丁和运维通知。AWS Health 通过 AWS Health API 和 Amazon EventBridge 提供全面的事件数据，但被动的管理方式仍会留下空白。

- 团队依赖 TAM 解读运行状况事件并做影响分析，在决策链上形成瓶颈。采用预定义 schema 的商业智能看板无法适应动态问题，也无法提供运维团队在当下需要的上下文洞察。
- DevOps 与云运维团队要花大量时间，手工对数以千计、分散在多个账号和区域的运行状况事件进行分类和排定优先级。没有集中的分析位置，就很难评估整体影响、协调跨团队响应，也很难发现可主动作为的机会——比如在问题演变为严重故障之前规划迁移或安排维护。

符合条件的运行状况事件很快会直接关联到 AWS Transform 模板，让客户能够直接针对事件采取行动。Chaplin 可以为你的环境呈现这些可执行事件并为其排定优先级。

## 方案概览：使用 Chaplin 的自助式分析

Chaplin 使用由 Amazon Bedrock 驱动的 agentic AI 实现自助式运行状况事件分析，并通过 Model Context Protocol（MCP）对外提供。与预定义的看板 schema 不同，Chaplin 暴露的是兼容 MCP 的客户端可以直接消费的 AI 工具。团队可以直接在自己的 AI 助手中（例如 Claude Code 或 Kiro CLI）与 Chaplin 交互，用自然语言提问。例如，团队成员可以询问未来 60 天内即将发生的 RDS 生命周期事件，要求按紧急程度汇总未关闭的 EC2 事件，查询影响生产环境的安全补丁，或者查看哪些维护窗口可能影响高优先级应用。

你的团队可以不断追问，直到拿到做出知情决策、拟定补救方案所需的全部信息。这种做法让 DevOps、安全和运维团队能够独立分析运行状况事件、规划迁移并评估运维影响，而不会造成瓶颈。由于 Chaplin 使用 MCP，团队还可以在工作流中把它与其他支持 MCP 的工具（如 JIRA、GitHub 或 ServiceNow）组合使用，以 agentic 的方式执行操作。

此外，MCP 让 AWS 数据与元数据可以直接与业务或应用层上下文关联——例如资源标签、环境分类和归属信息——从而为运行状况事件分析补充组织维度的相关性。

## agentic AI 如何统一结构化与非结构化数据

Chaplin 采用多 agent 架构，解决企业数据分析中的一个根本性挑战：有效地把结构化数据与非结构化数据的处理结合起来。传统的检索增强生成（Retrieval-Augmented Generation，RAG）系统和生成式 AI 方法存在一个关键局限：在处理数值运算和聚合时，它们本质上是非确定性的。作为 RAG 的基础，向量相似度检索能召回语义相近的内容，却无法保证数学上的准确性。当被要求计数、求和或聚合数据时，基于 RAG 的系统可能产生幻觉（例如，报告 190 个与生命周期终止相关的运行状况事件，而实际数量是 958）。这种非确定性源于检索机制（按语义相似度而非精确匹配对文档排序）和语言模型生成过程（预测可能的 token 而非计算精确数值）两方面的概率性。

AWS Health 事件恰好呈现了这一挑战。每个事件都包含结构化元数据——事件类型、服务名称、受影响的资源、时间戳、严重级别和账号 ID——需要精确的过滤与聚合。每个事件还包含非结构化描述，其中用自然语言说明问题、评估影响并给出建议操作，需要语义理解和上下文分析。

### 智能查询处理

当你向 Chaplin 提问时，三个专门的组件会协同工作。Natural Language to Structured Query Agent 把自然语言问题转换成针对运行状况事件元数据的精确结构化数据查询。它了解你的运行状况事件 schema——有哪些字段，例如 event_type、affected_accounts 和 start_time——并构造符合你意图的过滤条件。像“显示生产账号中的 EC2 退役事件”这样的问题，会变成带精确字段过滤的结构化查询，而不是关键词匹配。

- Contextual Impact Analysis Agent 负责处理非结构化的运行状况事件描述，把它们与你的客户元数据结合起来——生产环境与非生产环境、业务单元、应用层级和归属信息。这个 agent 会做系统级推理，不仅解读事件说了什么，还解读它对你这套特定基础设施和组织上下文意味着什么。
- Pattern-Based Classification Engine 使用基于规则的模式匹配对运行状况事件分类，对例行分类不产生 AI 处理成本，同时保持较高准确率。这一成本优化层让方案在大规模下依然可行。

### 成本优化的 AI 架构

Chaplin 通过有选择地使用 AI 增强来实现智能成本优化。系统采用模式优先的处理方式，由基于规则的分类处理大多数事件，不产生 AI 成本。为 30 天、60 天和 120 天窗口预置的、带过滤条件的汇总视图，帮助团队快速识别关键告警。在当前实现中，带 Claude 的 Amazon Bedrock 只处理需要上下文分析的非结构化数据。但该方案也与 LLM 无关，支持多种模型提供商，例如 Amazon Bedrock、OpenAI、Anthropic，或 Ollama 这样的本地模型，从而根据你的需求和成本约束保持灵活性。智能缓存减少冗余的 AI 处理，而结构化查询则借助 AWS Health API schema 完成精确的数值分析，不产生 AI 推理成本。

## 架构概览

下图展示了 Chaplin 的完整架构。它说明运行状况事件如何从多个 AWS 账号经过集中式数据管道，流入由基于 Amazon Bedrock 构建的 AI agent 支撑的 MCP 服务器，最终到达兼容 MCP 的 AI 助手，团队在那里通过自然语言与数据交互。图中每一层都会在下文详细描述。

图 1：Chaplin 架构，展示由多账号数据采集、搭载 Amazon Bedrock agent 的 AI 驱动 MCP 服务器以及 MCP 客户端集成组成的三层系统”

该架构由三个主要层次组成，它们协同工作以提供智能的运行状况事件分析。

#### 1. 数据层——采集层（多账号）

数据层从整个 AWS Organization 采集运行状况事件，并集中起来用于分析。在每个成员账号中，AWS Health API 是运行状况事件的来源。Amazon EventBridge 提供事件驱动的触发器以实现实时捕获，AWS Lambda 采集函数则使用按最小权限原则配置的跨账号 IAM 角色来获取事件。

这些事件流入一个集中式的管理账号，其中的 Amazon Simple Storage Service（Amazon S3）数据湖按账号、日期和事件类型智能分区，存储采集到的运行状况事件。新事件到达时，S3 事件通知会触发一个 AWS Lambda 函数，由它处理 JSON 格式的运行状况事件并将其加载到 Amazon DynamoDB，以便快速查询。

这种多账号架构支持两种部署模式：

- **选项 1**：使用 AWS Organizations API，在你的各个账号之间进行集中、自动化的部署。
- **选项 2**：针对有安全限制的组织，逐账号单独部署。

#### 2. 中间层——MCP 服务器与智能层

中间层负责把原始运行状况事件数据转化为可执行的智能，并通过 MCP 服务器暴露出来。Amazon DynamoDB 作为结构化运行状况事件元数据的主要数据存储，针对事件类型、严重级别、日期和账号建有索引，为快速查询做了优化。这让基于模式的分类和 AI 分析都能实时访问数据。

基于模式的事件分类器提供第一层智能。这个基于规则的分类引擎对事件类型使用正则表达式模式，把事件映射到五个业务类别：迁移需求（Migration Requirements）、安全与合规（Security & Compliance）、维护与更新（Maintenance & Updates）、成本影响事件（Cost Impact Events）和运维通知（Operational Notifications）。由于大多数事件都遵循可预测的模式，这种做法通过高效的模式匹配处理了绝大多数事件，不产生 AI 成本。

对于需要更深入分析的事件，则由基于 Amazon Bedrock 构建的 AI 分析引擎接手。该引擎使用 Strands Agents 框架——AWS 开发的开源 agentic 框架——并以 Claude 4.5 Sonnet 作为大语言模型。你可以把它换成自己偏好的 LLM。三个专门的 agent 分别处理分析的不同方面：SQL Query Agent 把自然语言查询转换为结构化的 DynamoDB 查询，用于精确的数值分析；Impact Analysis Agent 结合环境、业务单元和归属等客户元数据评估非结构化的事件描述；DBQueryBuilder Agent 为多维聚合生成经过优化的数据库查询。所有这些能力都以 MCP 工具的形式暴露，兼容的客户端可以调用。

#### 3. 表现层——MCP 客户端——AI 助手集成

表现层由一个兼容 MCP 的 AI 助手构成，例如 Claude Code 或 Kiro CLI。Chaplin 没有自定义前端，而是把自身能力以 MCP 工具的形式暴露，由这些客户端原生消费。用户在自己现有的开发环境中用自然语言交互，AI 助手负责编排对 Chaplin MCP 服务器的调用，以获取运行状况事件数据、执行 AI 驱动的分析并呈现结合上下文的结果——全部在团队已用于开发任务的同一个对话界面内完成。

安全方面依靠 AWS Identity and Access Management（AWS IAM）进行身份验证和授权。MCP 客户端以只读方式挂载 AWS 凭证，访问权限通过遵循最小权限原则的 IAM 角色来控制。数据在传输中采用 TLS 1.2+ 加密，静态存储时采用 AES-256 加密，AWS CloudTrail 为 API 调用提供审计日志。

## 关键能力

Chaplin 提供三项核心能力，填补组织当前管理 AWS Health 事件方式的空白。

Chaplin 提供动态的对话式分析。它根据你的具体问题按需生成可执行的洞察，给出包含精确计数、受影响账号和上下文分析的准确细分——这些都在你的 AI 助手内部动态生成，无需预置报表或看板。Chaplin 通过三项集成能力实现这一点：

### MCP 驱动的运行状况智能工具

Chaplin 暴露一套完整的 MCP 工具，分为三类。摘要类工具直接查询 DynamoDB 并即时返回，提供服务、状态、类别和区域维度的高层计数。明细类工具让你下钻到特定事件类别、事件类型或经过过滤的事件列表。AI 分析类工具使用 Strands Agents 与 Amazon Bedrock，解读你的自然语言查询、获取相关数据并生成上下文洞察。

### 多账号数据管道

Chaplin 从你的 AWS 账号采集运行状况事件，并把数据集中到 Amazon S3，支持根据你的安全态势选择灵活的部署模式。该数据管道由以下部分组成：用于自动摄取运行状况事件的 AWS Lambda 函数，采集频率可配置（每日或每小时）的 Amazon EventBridge 调度器，遵循最小权限原则、用于安全的多账号数据采集的跨账号 IAM 角色，带分区以实现高效查询的 Amazon S3 数据湖，以及保留策略可配置的自动化生命周期管理。

### 精确的分析处理

Chaplin 把结构化与非结构化数据处理结合起来以进行全面分析。对结构化数据，它给出精确的数值结果，包括事件计数与分布、带趋势识别的时间线分析、跨账号/服务/严重级别维度的多维聚合，以及带精确百分比的分类细分。对非结构化数据，它提供上下文洞察，例如基于事件描述的影响评估、架构缺陷识别、相关事件之间的风险关联，以及基于事件上下文的建议操作。

主要事件模式

- **ElastiCache UPDATE_AVAILABLE**——2,100 多个事件，全部逾期（截止日期从 2024 年 9 月起）。这是补丁积压，不是新发生的故障。
- **VPN REDUNDANCY_LOSS**——14 个账号共 647 个事件。反复出现的单隧道故障。
- **EC2 INSTANCE_STOP_SCHEDULED / RETIREMENT**——351 个事件。属于实例生命周期维护。
- **维护更新（Maintenance Updates）**占主导，共 2,447 个事件（占全部事件的 52%）。

减少反复事件的架构改造

#### 1. ElastiCache：自动化补丁（可消除约 2,100 个事件）

这是最大的单项收益。几乎所有的 ElastiCache 事件都是 `UPDATE_AVAILABLE`，截止日期从 2024 年 9 月起，已逾期超过 19 个月。

- 在所有 ElastiCache 集群上启用 auto-minor-version-upgrade
- 在低流量时段设置维护窗口
- 使用 IaC（Terraform/CloudFormation）在所有账号上把 auto_minor_version_upgrade = true 强制为默认值
- 实施 AWS Config 规则，检测禁用了自动升级的集群

#### 2. VPN：修复单隧道架构（可消除约 647 个事件）

所有 VPN 事件都是 REDUNDANCY_LOSS——意味着连接只跑在一条隧道而不是两条上。单是账号 456303994757 就有 327 个事件。

- 确认每条 AWS Site-to-Site VPN 连接的两条隧道都处于活动状态。
- 迁移到 AWS Transit Gateway，以获得集中、冗余的连接性，替代按 VPC 单独建立的 VPN 连接
- 在两条隧道上实施带自动故障转移的运行状况检查
- 对关键账号考虑采用带 VPN 备份的 AWS Direct Connect

#### 3. EC2：转向托管/容器化计算（可减少约 351 个事件）

EC2 事件主要是实例退役、计划内停止和维护重启——这些都是管理单台实例本身所固有的。

- 把无状态工作负载迁移到 AWS Fargate 上的 ECS 或 EKS。AWS 会透明地处理主机维护。
- 对剩余的 EC2 工作负载使用带实例刷新的 Auto Scaling 组，让退役被自动处理
- 用采用混合实例策略、对 Spot 友好的架构替代长期运行的实例
- 启用 EC2 自动恢复，并确认在各处都已开启。

#### 4. 横切事项：运维卫生

- 为所有账号打标签——100 多个账号显示为“N/A”且没有标签，导致无法分诊
- 用 EventBridge 规则自动化运行状况事件的响应，对常见事件类型触发 Lambda 函数
- 整合账号——ElastiCache 补丁积压横跨 140 个账号，说明开发/沙箱环境中存在过度配置或孤立的集群。审计并下线未使用的资源。

优先级顺序

- **ElastiCache 自动补丁**——投入最少，事件减少最多（2,100 多个事件）
- **VPN 隧道冗余**——修复真实的可用性风险。
- **账号打标签**——使正确的分诊和归属成为可能
- **EC2 → 托管计算迁移**——周期更长，但可消除一整类维护事件

## 部署演练

Chaplin 提供两种部署选项以匹配你团队的需求。两者都完全脚本化——克隆仓库并按照 README 中的引导式设置操作即可。

**选项 A**：本地安装——在你自己的机器上运行 MCP 服务器，使用本地 AWS 凭证直接连接 DynamoDB 和 Bedrock。最适合个人开发者或快速评估。仓库中为 Kiro IDE、Cursor 和 VS Code 提供了一键安装按钮。
**选项 B**：远程部署（Lambda）——把 MCP 服务器作为 Lambda 函数部署到你的 AWS 账号中。团队成员通过轻量的本地代理连接——无需本地依赖，服务器只有单个实例托管在中心位置。最适合全团队推广。

两种选项都会部署后端基础设施（DynamoDB 表、S3 到 DynamoDB 的 Lambda，以及 S3 事件通知），并自动配置你的 MCP 客户端。

部署完成后，打开你兼容 MCP 的 AI 助手，确认 Chaplin 的运行状况工具可用。试着问一个简单的问题，例如“计划内变更事件有哪些——计划内维护与变更？”，以确认连接正常工作。

### 数据管道

Chaplin 需要 AWS Health Events 数据。你可以在搭建数据管道之前或之后部署 Chaplin。数据管道支持两种部署模式：

**选项 1**：AWS Organizations——跨多个账号批量部署（推荐）
**选项 2**：单个账号——手动部署到指定账号

关于分步部署说明和数据管道设置，见 [Chaplin GitHub 仓库](https://github.com/aws-samples/sample-aws-health-agentic-assistant)。

## 收益与影响

实施 Chaplin 的组织在 AWS Health 事件管理的三个方面获得可衡量的改善：运维效率、成本优化和风险缓解。

从运维效率看，Chaplin 提前 60 到 90 天识别即将到来的迁移和弃用，从而实现主动的技术生命周期管理，减少紧急救火。自动化的事件分类减轻了运维团队的手工分诊负担。自助式分析消除了日常分析对 TAM 的依赖，使当天完成补救规划成为可能。团队还能及早发现已弃用的服务和配置，避免技术债累积。

成本优化来自多个方面。跟上生命周期变化可以避免代价高昂的紧急迁移和延长支持费用。模式优先的处理方式让大多数事件走基于规则的分类而不是 LLM 调用，从而把 AI 推理成本降到最低。自助能力减少了针对日常询问的 TAM 介入，而对影响成本的事件有更好的可见性，有助于主动识别预留实例到期和容量变化。可配置的 Amazon S3 保留策略有助于长期管理存储成本。

在风险缓解方面，Chaplin 通过在安全补丁和漏洞被利用之前主动识别它们，提供早期的安全可见性。对与合规相关的运行状况事件进行带审计轨迹的自动监控，支持合规跟踪。对生产系统所受事件影响的上下文分析有助于防止中断，而对配置问题和架构缺陷的检测能在其引发故障之前发现问题。

## 展望：从自助式分析走向借助 AWS DevOps Agent 的自主运维

当前版本聚焦于对话式分析和自助能力，而 Chaplin 的长期愿景则朝向自主运维。由于 Chaplin 构建在 MCP 之上，它能与 AWS DevOps Agent 自然集成——后者是一个前沿 agent，可自主调查故障、定位根因并给出详细的缓解方案。把 Chaplin 的 MCP 服务器注册为 AWS DevOps Agent Space 中的能力提供方后，运维团队就能在事件响应工作流中直接获得运行状况事件智能。AWS DevOps Agent 可以把 Chaplin 的运行状况事件数据与应用拓扑、遥测和部署历史关联起来，从而呈现影响范围、排定补救优先级，并通过 Slack 和 ServiceNow 等渠道协调响应。

这种集成形成了强大的反馈回路。当 AWS DevOps Agent 调查某个故障时，它可以查询 Chaplin，判断是否有关联的运行状况事件——例如即将到来的实例退役或服务弃用——正在促成该问题。Chaplin 的影响范围分析提供业务上下文，显示哪些账号和工作负载面临风险及其相关支出，而 AWS DevOps Agent 则通过其拓扑图把这些映射到具体的应用资源及其依赖关系。两者结合，可实现自动分诊：运行状况事件不仅被分类，还与实时基础设施状态关联，帮助团队从被动救火转向主动预防故障。随着 AWS Health 引入原生的优先级能力，这条管道会变得更加丰富，让客户可以定义自己的优先级规则，并由运行状况事件元数据和运维遥测共同丰富。

未来的增强将在此基础上构建，包括通过事件模式分析实现的预测性维护，以及带回滚能力的引导式补救工作流——把运维团队从被动的响应者转变为策略性的编排者。
