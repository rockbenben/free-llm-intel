# Amazon Quick 中的 agentic 原语分类

在过去一年构建 Amazon Quick 的过程中，我们的 agent 经历了从“回答问题”到“采取行动”的转变：安排会议、开展研究、生成报告。随着系统的演进，一个问题反复浮现：对于构成 agentic 工作的核心原语（primitives），业内一直缺乏统一的定义。有几种相同的核心构件不断被冠以不同的名称反复构建：执行工作的行动实体（actor）、启动工作的信号、打包好的规程（procedure），以及承载经验教训的记忆。这种重复性不仅渗透到了产品设计中，也直接影响了终端用户的使用体验。

例如，当用户提出“*监控我的 Slack 频道并每天向我发送摘要*”时：这到底是一个全新的 agent、还是对已有 agent 的定时指令、亦或是一个工作流（workflow）还是一项技能（skill）？这些本是截然不同的问题，但由于缺乏统一的语汇，它们最终被压缩成了一个令人困惑的选项。

本文分享了我们最终收敛出的分类体系：通过将 agentic 工作拆解为四个朴素的问题——*何时（When?）*、*何事（What?）*、*何人（Who?）*和*如何做（How?）*，提炼出一套统一的原语。按照设计初衷，该框架的大部分细节对终端用户是不可见的，但一套通用的语汇能够让底层构建者更容易对系统进行推理和设计。

**触发器（trigger）**启动工作并承载任务（*何时*与*何事*），**agent** 承接任务（*何人*），并运用自身的**能力（capabilities）**（工具、技能与工作流）来执行任务（*如何做*）。本文将详细介绍这些原语以及它们之间的相互关系。这是该系列的第一篇文章，后续文章还将涵盖我们的 agentic 操作系统、后台学习、主动推送流（proactive feeds）等更多内容。

## 触发器：什么促使工作开始

触发器是启动工作完成的激活机制，但它们同时也承载着指令：人类发送的一条消息，既是激活的时刻，也是对具体执行内容的描述。它们同时构成了任务的*何时（When?）*与*何事（What?）*。

- **人类发起（Human-initiated）：** 用户开启对话并要求 agent 执行某些操作。具备交互性、同步性和对话性。
- **Agent 委托（Agent-delegated）：** 一个 agent 在执行任务途中调用另一个 agent 来处理子问题。具备可编程性、可组合性，并可能具有递归性。
- **定时调度（Scheduled）：** 基于时间的激活，例如“每周一上午 9 点运行财务调研”。具备确定性，在多次运行中应用相同的固定指令。
- **事件驱动（Event-driven）：** 来自外部系统的信号，例如新邮件、Slack @提及、文件变更或 webhook。

触发器的类型决定了执行的方式：计划好的后台任务可能会保持保守策略（例如在不确定时不执行任何操作），而由人类发起的任务则更具响应性（例如倾向于提问而非直接停止）。

## Agent

我们将 agent 定义为*具备持久性与学习能力的行动实体（persistent, learning actor）*。它是任何执行过程中的*何人（Who?）*，也是积累学习成果的锚点。即使输入完全相同，两个 agent 的表现也可能截然不同，因为它们承载着不同的指令、能力与历史。Agent 本身并不等同于它所遵循的指令，而是解释这些指令的实体。它由三部分构成：

- **指令（Instructions）：** 定义人设、角色、上下文文件及运行原则的固定指导。财务 Agent 之所以表现得与通用助手不同，主要就源于这一点。
- **能力（Capabilities）：** 可供使用的工具、技能、工作流以及 sub-agent，支持动态更新。例如可以在某个会话中添加图表库，在下个会话中将其移除。
- **学到的上下文（Learned context）：** 随着使用不断积累的记忆：对某个工具最有效的查询方式、用户偏好的排版格式、用户关注的边界用例。正是凭借这一点，在没有任何人手动修改指令的情况下，第十次执行的效果也能显著优于第一次。

除此以外的一切都是外部要素：Agent 底层的大型语言模型（LLM）是可替换的模型参数，对话历史是基于单次会话的状态，而触发器则属于平台层。

这一定义带来的一个直接推论是：当用户提出“*我想要一个能监控我的 Slack 并在每天早晨发送摘要的 agent*”时，这通常只是*向现有 agent 添加了一个触发器*，而不是去创建一个全新的 agent 或工作流。在这种框架下，我们可以将对话型 agent、定时型 agent 以及“自主型” agent 合并为同一个行动实体——你既可以与它对话、对它进行定时调度，它还能够编排并审查自己过去的各项工作。

## 能力

能力决定了 agent*如何做（How）*，涵盖从完全 agentic 自主决策到完全确定性的整个光谱。这个光谱轴本质上是一份*置信契约（confidence contract）*：即 agent 保留多大的自主权，与用户预先固定多少流程之间的权衡。

**工具（Tools）**是具备类型化 schema 的原子操作：发送邮件、查询数据库、读取文件。无论是本地函数、Model Context Protocol (MCP) 服务器，还是位于协议边界背后的另一个 agent，调用方看到的都是相同的统一接口：名称、描述、参数和返回结果。

**技能（Skills）**是带有裁量空间的结构化指导：将指令与配套资源（模板、脚本、示例）打包在一起，描述的是一种解决思路而非死板固定的步骤序列。技能通过*渐进式呈现（progressive disclosure）*加载，因此 agent 最初只能看到技能名称和简短描述，直到某项技能变得相关时，才会完整读入其全部指令。这样一来，技能便可以在不带来持续上下文开销的前提下，封装任意深度的专业知识。

**工作流（Workflows）**是确定性的协作协调：声明好的步骤、控制流、分支和错误处理均以固定顺序执行，决策逻辑由代码而非模型推理来掌控。例如采购审批流程：预算检查、经理审批、财务入账，每一步均有记录。整个流转路线是固定的，但某个步骤*内部*的具体裁量依然由 agent 做出。

## 为什么技能与工作流能够经受住模型能力演进的考验

一个很自然的问题是：如果模型不断进步，技能和工作流未来是否会变得多余？我们认为并不会，因为它们各自具备独立于模型能力的独特价值。技能是沉淀、版本化管理以及共享组织内部专业知识的基本单元；而工作流则提供了可审计性、逐步可见性以及跨多个服务的确定性协同。此外，它们也并非一成不变：一项被深入理解的技能可以沉淀收紧为工作流（*结晶，crystallization*），而一个频繁遇到边界用例的工作流也可以放宽松绑还原为技能（*消解，dissolution*）。在 Quick 中，这通过我们的持续学习框架来实现，我们将在后续文章中对此展开讨论。

## 这在实践中意味着什么

回到“*监控我的 Slack 频道并每天向我发送摘要*”这个场景。由于这些原语具备可组合性，同一个需求可以通过多种合理的方式来实现：

- 带有单行指令的定时任务，剩下的具体执行完全交给 agent 自行摸索。
- 借助具备明确排版规则和频道优先级的技能来支撑同一任务。
- 调用具备确定性步骤和错误处理机制的工作流来执行同一任务。

这三种方式都能按计划生成每日摘要。它们的不同之处在于置信契约。充分信任 agent 的用户会选择第一种；曾吃过输出不一致亏的用户倾向于第二种；而在合规敏感场景下运行流程的用户则需要第三种。

随着时间的推移，学习机制会改变这一轨迹。一个最初仅有一句话的任务（“*检查我的邮件中是否有紧急事项*”）会逐步积累领域内的学习成果：更有效的查询语句、偏好的格式、以及哪些发件人更为重要。在无需任何人手动编码调整的情况下，第十次运行的效果就会显著提升。最佳的设计方案应当是满足用户置信要求的极简选择，同时保留随着需求增长通过自主学习机制逐步演进升级的路径。

## 结语

这套 agentic 原语分类体系的价值在于：仅需*何时（When）*、*何事（What）*、*何人（Who）*和*如何做（How）*这四个朴素的问题，就足以定位任何 agentic 工作，无论是单行对话请求，还是按计划执行的合规级流程。共享同一套语汇让构建者能够清晰推理系统架构，同时也让产品得以隐藏底层的复杂性。最棒的是，用户完全不需要学习这些概念。他们只需表达自己的诉求，系统便会自动组装相应的原语来完成工作。
