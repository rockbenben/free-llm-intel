# 使用 Amazon Bedrock AgentCore 构建多租户 agent

构建多租户 agent 应用的软件即服务（SaaS）提供商，除了安全、治理与响应准确性这些常规关注点之外，还必须应对额外的架构挑战。这些挑战包括租户隔离、租户身份、租户可观测性、数据隔离、成本归集以及噪声邻居（noisy neighbor）缓解。要把可用的 demo 与生产部署之间的差距补上，需要为多租户环境专门构建的基础设施。Amazon Bedrock AgentCore 是一项托管、无服务器（serverless）服务，用于在 AWS 上构建、部署并安全运营 agent 应用。它提供了用于部署 agent 和托管 MCP server 的构造（constructs），并内置对身份管理、memory、可观测性与评估（evaluations）的支持，这些设计都是为了让多租户 agent 架构搭起来有章可循。

本文是这一博客系列的第 1 部分，探讨为多租户 agent 应用做架构设计时的考量，以及借助 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 应对 SaaS 架构挑战所需的框架。

## 构建多租户 agent 的设计考量

构建具备强隔离的安全多租户 agent 应用，需要在若干关键组件上做出细致的架构决策，如图 1 所示。每个组件都必须在保持安全与合规标准的同时，平衡租户隔离、运营效率与成本优化。这些设计考量围绕三种租户隔离模式展开：[Silo、Pool 与 Bridge](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html)，而分层（tiering）策略是三者之间做选择时的一项关键考量。

### 1. Agent Runtime 部署：专用制与共享制的比较

多租户 agent 架构中的一个关键决策是：agent runtime 相对租户如何供给。为每个租户配置一个*专用* runtime，会为每个租户实例化独立的执行环境，各自拥有容器镜像、进程空间与生命周期。这种 silo 方式提供最强的噪声邻居防护，并简化合规审计。*共享* runtime 则在同一容器镜像与进程池中托管所有租户的 agent，降低基础设施成本与运营开销，但需要严格的进程内租户上下文传递。

Amazon Bedrock AgentCore Runtime 通过基于 microVM 的会话隔离计算化解这一矛盾。AgentCore Runtime 按会话启动轻量级 microVM，无需为每个租户付出启动整台虚拟机的成本或延迟。每个会话都带有自己的持久文件系统，因此 agent 可以读写会话范围内的文件、保留中间计算产物，并在多步交互中保持状态，降低跨会话数据泄漏的风险。该架构很适合托管多租户 MCP server、agent 与 AG-UI server。租户上下文通过自定义 HTTP header 流入隔离的执行环境。当 SaaS 平台把请求转发到某个 AgentCore Runtime 会话时，会在标准授权 token 之外附加携带租户专属元数据的 header，例如租户标识、层级、区域偏好、功能开关（feature flags）或权益（entitlements）。agent 在调用时读取这些 header 以建立完整的租户认知，从而可以运行按该租户业务逻辑调优的 workflow、只调用已授权的工具，并在不硬编码路由逻辑的情况下调用租户专属的 API endpoint。

### 2. 共享模型、按层级模型与微调模型的比较

共享基础模型（FM）是大多数多租户部署的推荐起点，运维简化，模型只需维护一份。租户通常能从自动模型更新中获益，无需按租户做定制。按租户层级选择模型（层级专属模型）这一选项提供了灵活性，可在各租户层级之间平衡成本、性能与准确性。对于需要租户专属术语、法规遵从或性能 SLA 的特殊用例，租户专属的微调模型就变得必要，尽管它们带来更高的运营复杂度与按租户的 pipeline。一种混合做法——标准层级使用能力较弱的模型，高级企业客户使用微调模型或能力更强的模型——在成本效率与定制需求之间取得平衡。Amazon Bedrock 提供来自领先提供商的大语言模型（LLM）选择，使 SaaS 提供商可以挑选适合租户与层级特定需求的模型。Amazon Bedrock 微调支持使用你自己的标注数据集定制 FM，以提升领域特定任务的表现。借助 Amazon Bedrock Custom Model Import，你可以导入自己微调好的模型，并用 Amazon Bedrock 的托管基础设施部署它们。

### 3. Workflow：Silo、Pool 与 Bridge 模式

多租户 agent 应用需要灵活的工作流管理，每个 agent 依据租户要求与业务逻辑执行不同的步骤序列。工作流可以通过多种机制实现：作为封装分步流程的 MCP 工具、作为定义业务逻辑流程的 API endpoint，或作为内嵌领域特定 workflow 模式的 agent skill。

有三种主要模式用于管理租户专属 workflow。silo 模式使用租户专属的专用 skill，每个租户的完整 workflow——包括所有业务逻辑、校验规则与集成步骤——都内嵌在隔离的 agent skill 中。这带来最大程度的定制与完全独立，但需要按租户分别维护 skill。pool 模式使用共享的 agent skill。bridge 模式把认证、日志、错误处理等通用 workflow 步骤内嵌到共享 agent skill 中，并在运行时为业务关键逻辑调用租户专属 skill。其结果是可与租户专属定制共存的可复用基础设施。

### 4. 多租户 RAG

检索增强生成（RAG）系统需要做出数据隔离决策。silo 模式为每个租户使用专用向量数据库，提供最高安全性与完全的数据分离。对于需要专用基础设施的受监管行业与企业客户，这是推荐做法。pool 模式使用共享向量数据库，配合基于元数据的租户过滤与基于 namespace 的访问控制，为服务大量中小租户的 SaaS 平台提供成本高效的运营方式。检索操作应包含自动租户过滤注入与结果清洗，以帮助防止跨租户数据泄漏。

Amazon Bedrock Knowledge Bases 提供全托管的 RAG 能力，把 FM 连接到你的数据源，自动处理数据摄取、分块（chunking）、embedding 生成与向量存储。它支持多种向量数据库，并支持创建隔离的或共享的向量数据库（使用元数据过滤）。

关于使用 Amazon Bedrock Knowledge Bases 实现多租户 RAG 架构的详细指导，请参阅[使用 Amazon Bedrock Knowledge Bases 的多租户 RAG](https://aws.amazon.com/blogs/machine-learning/multi-tenant-rag-with-amazon-bedrock-knowledge-bases/) 了解 silo、pool 与 bridge 部署模式，以及[在单个 Amazon Bedrock 知识库中通过元数据过滤实现 RAG 应用的多租户](https://aws.amazon.com/blogs/machine-learning/multi-tenancy-in-rag-applications-in-a-single-amazon-bedrock-knowledge-base-with-metadata-filtering/) 了解共享知识库内基于元数据的租户隔离。

### 5. 租户上下文、act-on-behalf 模式与 token 传递

多租户身份管理需要在整条服务链上谨慎处理租户上下文。租户上下文代表完整的身份，它与请求专属状态必须通过可靠且安全的机制流经每一个架构层。与执行路径可预测的确定性软件 API 不同，AI agent 是非确定性的，且可能具备自主性，因此安全考量在若干重要方面有所不同。失控或被攻陷的 agent 可能对下游服务发起未授权调用，导致凭据被窃、权限提升与混淆代理（Confused Deputy）问题。当 agent 以完整用户凭据运行（impersonation，即冒充）时，单个被攻陷的 agent 就获得了跨所有下游系统的全部用户权限。随着 agent 变得更自主、能独立决定调用哪些工具、何时调用、用哪些参数，这一风险会增大。act-on-behalf 模式之所以重要，是因为它在用户与 agent 之间建立了清晰区分：agent 代表用户发起调用，但每个具体操作都被限定在明确受限的范围内。

把租户上下文编码在 JSON Web Token（JWT）中，涵盖三个维度：安全上下文（标准 claim：iss、sub、exp、aud）、租户上下文（tenant_id 与租户专属 scope）与请求上下文（用于业务逻辑的领域专属属性）。以这种方式编码租户上下文，为多租户运营提供了强健而灵活的基础。

在两种安全含义不同的模式之间做选择：impersonation 允许 agent 以完整的用户身份与权限运行，实现简单，但违反最小权限原则并带来安全风险。Act-on-Behalf（委派）是推荐做法，它实现真正的委派：token 在每个服务边界被转换，携带范围受限的凭据，以及标识 agent 的 act claim（依据 OAuth 2.0 RFC 8693）。使用 AgentCore Identity 中的 On-behalf-of token 交换，agent 与其他工作负载（例如 MCP server）可以把入站的用户访问 token 换成面向下游资源服务器的新范围化访问 token。由于该交换把一个为某个受众签发的 token 直接转换为面向另一个下游受众的 token，你的 agent 就能代表已认证用户访问受保护资源，而无需触发额外的授权同意流程。交换后的 token 同时携带 agent 自身的身份与原始调用方的身份，为资源服务器提供在每个跳点执行细粒度零信任授权所需的信号。

### 6. MCP 工具与 API 的细粒度访问控制

多租户 agent 应用需要用策略限制 MCP server 访问、在工具调用层做细粒度访问控制，并在数据访问层做租户隔离。在授权层，策略在运行时评估租户上下文，以做出允许/拒绝的授权决策，并在允许工具调用之前，依据租户当前状态评估租户配额、基于层级的权限与用量限制，而不是只依赖内嵌在 token 中的静态权限。解耦且集中的策略存储允许在不重新部署的情况下动态更新，策略版本化则支持审计轨迹与回滚能力。AgentCore Policy 会在允许工具访问之前拦截并依据既定策略评估所有 agent 请求，基于用户身份与工具输入参数提供细粒度控制，策略可用自然语言或直接用 Cedar 编写。

在调用层，MCP server 通过在 agent 调用工具之前按租户层级、feature flag 与配额限制过滤可用工具，来执行细粒度访问控制。工具拦截器校验 JWT claim，确认发起请求的主体对该具体操作具有相应权限。schema translation 能力会依据租户配置与权益适配工具接口。AgentCore Gateway 通过把 API 与 AWS Lambda function 转换为 agent 兼容的工具、并连接到既有 MCP server，让 agent 安全地访问工具，支持 Amazon API Gateway、OpenAPI schema、Smithy 模型、Lambda function 与 MCP server。你可以通过 gateway 拦截器实现自定义逻辑的访问控制，或使用基于资源的策略实现标准 AWS 风格的访问控制。在数据访问层，基于属性的访问控制（ABAC）策略对数据访问执行租户隔离，租户识别通过 JWT claim 完成。ABAC 策略使用 AWS Identity and Access Management（IAM）条件，基于主体标签与属性限制数据访问，因此 agent 只能通过行级安全或存储策略查询与其租户上下文匹配的资源。

### 7. Memory：分层 namespace 隔离

多租户 memory 管理需要细致的架构设计，使 agent 既能保持上下文与已学到的信息，又能防止跨租户数据泄漏。memory 系统应实现五个逻辑层级：

- Global（跨租户共享的知识）
- Strategy（agent 类型专属的模式与行为）
- Tenant（租户范围内的对话历史与偏好）
- User（租户内的单个用户上下文）
- Session（活跃会话的短暂短期记忆）

访问控制通过基于属性的策略强制隔离，这些策略会校验主体身份与请求的 namespace 路径是否匹配，因此 agent 只能在其允许的范围内读写 memory。pool 模式用共享基础设施配合基于分层 namespace 的逻辑隔离来实现运营与成本效率，把所有租户数据存放在同一数据存储中，并基于 namespace 前缀做严格过滤。silo 模式按租户部署专用 memory 存储以获得最大隔离，以更高的运营成本降低跨租户访问风险。实现方式包括：用租户与用户信息构造复合标识符（例如 tenant_123:user_456），以携带租户上下文（作为 claim 或标签）的范围化凭据进行认证，并给所有 memory 操作加上合适的 namespace 路径前缀。

AgentCore Memory 在全局、strategy、租户、用户与 session 层级上提供分层 namespace 隔离，同时支持多轮会话的短期记忆与跨会话保留的长期记忆，从而实现上下文感知的 agent 体验。它支持[基于资源的策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/resource-based-policies.html)与[基于属性的访问控制](https://builder.aws.com/content/3C1SCSoe15VaBnmsiMIfGcZfhxM/secure-shared-multi-tenant-agent-memory-namespaces-using-agentcore-memory)以实现细粒度访问。

### 8. Agent 身份、信任与发现

随着 agent 应用跨组织边界与外部 agent 交互，浮现出三个基础性问题：agent 身份、agent 信任与 agent 发现。它们虽然相关，但各自解决一个不同的问题。

**Agent Identity（身份）** 回答*“这个 agent 是谁，它能证明吗？”*——建立一个与组织绑定的、可验证的唯一身份。

**Agent Trust（信任）** 回答*“我应该信任这个 agent 吗？”*——基于多种信号的组合而非单一凭据来评估可信度。

**Agent Discovery（发现）** 回答*“我如何找到合适的 agent？”*——在没有事先掌握 endpoint 的情况下，按能力或隶属关系定位 agent。

#### **使用 AgentCore Identity 的 agent 身份**

Amazon Bedrock AgentCore Identity 把 agent 身份实现为工作负载身份（workload identity），这是云原生安全中已经确立的模式。每个 agent 都会获得锚定在组织 AWS 账户与 IAM 基础设施上的、可加密验证的身份。agent 可以使用 OAuth 2.0 流程代表用户安全访问 AWS 资源与第三方工具，AgentCore Identity 可与 Okta、Microsoft Entra ID、Amazon Cognito 等既有企业身份提供商集成，无需迁移用户。

#### **Agent 信任**

单靠身份并不能回答某个 agent 是否应当被信任。业界正在积极解决这个问题。[Agent Naming Service (ANS) v2](https://datatracker.ietf.org/doc/html/draft-narajala-courtney-ansv2) 目前是一份 IETF Internet-Draft（进行中的工作），它把每个 agent 身份锚定到一个 DNS 域名。客户端可以选择与其交易风险相称的保证级别，共有三个验证层级：Bronze（PKI）、Silver（PKI + DANE）与 Gold（PKI + DANE + 透明日志）。

#### **使用 AWS Agent Registry 的 agent 发现**

AWS Agent Registry 通过 Amazon Bedrock AgentCore 提供，是一个集中式目录，用于发现组织内的 agent、skill、MCP server 与自定义资源。团队可以发布、版本化并共享可复用的 agent 能力。使用方可以通过自然语言或结构化搜索发现 agent，无需事先知道标识符或 endpoint。内置治理控制决定使用方如何访问 registry，以及记录在被发现之前是否需要审批。总之，AgentCore Identity 提供基础性的身份证明，Agent Registry 解决发现，而像 ANS 这样的新兴信任框架旨在补齐多信号信任评估的差距。

### 9. 按租户的成本追踪与可观测性

准确的多租户成本归集需要在应用层埋点，为每次 agent 调用向日志方案输出带租户标签的指标，捕获 I/O token、工具调用与执行时长。带租户上下文的结构化日志可支持对使用模式、性能瓶颈与容量规划的细致分析。AgentCore Observability 借助由 Amazon CloudWatch 驱动的、与 OpenTelemetry 兼容的集成，提供对 agent workflow 的实时可见性，并对 agent 执行的每一步提供详细可视化。

### 10. Guardrail：内容安全

多租户 guardrail 在三个执行点强制安全与合规。预处理阶段的输入 guardrail 在 agent 处理之前校验用户输入，阻断恶意 prompt、prompt 注入，并依据租户特定的合规要求（例如医疗行业的 HIPAA、金融行业的 PCI-DSS）清洗 PII。后处理阶段的输出 guardrail 校验 agent 响应的真实性、检测幻觉、确认格式合规，并扫描跨租户边界的敏感数据泄漏。你可以按租户或层级应用 guardrail，配置毒性检测、内容过滤与自定义屏蔽词，并通过可观测性指标跟踪触发率、按类别统计的阻断请求数与误报率，以持续改进。Amazon Bedrock Guardrails 提供内容过滤与安全控制，可配置拒绝话题、内容过滤器、词过滤器与敏感信息脱敏策略，支持在所有模型交互中负责任地部署 AI。

这十个组件为设计多租户 agent 提供了完整框架。在接下来的章节中，我们会带着这些核心组件，探讨在 AgentCore 中实现 silo、pool 与 bridge 三种模型的方式。

## 使用 AgentCore 实现 Silo 模型

如下图所示，*silo 模型*让每个租户在完全隔离的栈中运行，拥有自己的专用 Bedrock AgentCore Runtime、Bedrock AgentCore Gateway 与 Bedrock AgentCore Memory，全部置于各自独立的 AWS IAM 边界之后。memory 支持多种分类，例如长期、短期与情景（episodic），需要按租户要求进行配置。

### **关键架构组件**

- **隔离的 Agent 层** —— 专用 AgentCore Runtime，各自以独立的 IAM 执行角色部署，用于租户专属权限。
- **隔离的 Gateway** —— 专用 AgentCore Gateway，用 MCP 编排工具，并依据执行角色限制对数据层的访问。
- **隔离的 Agent Memory —— ** 专用 AgentCore Memory，具备分层 namespace 隔离，无需在每个 namespace 路径中都包含租户 ID。agent 通过 IAM 角色访问租户专属 memory。
- **隔离的数据层** —— 专用工具、知识库、数据库与后端资源，实现最大程度的数据隔离。

### **请求流程**

- **认证** —— 用户使用身份提供商完成认证，获得包含租户上下文（租户 ID 与订阅层级）的 JWT token。
- **SaaS 应用代理路由** —— SaaS 应用代理依据租户上下文决定调用哪个 agent。这需要在租户与 agent 部署之间建立映射配置，该功能通常属于 SaaS 控制平面。代理把应用层请求转换为 AgentCore Runtime API 调用（InvokeAgent），并附上租户 JWT token。
- **Agent 执行** —— AgentCore Runtime 使用 AgentCore Identity 校验 JWT，创建隔离的 microVM 会话，并开始 agent 推理。此外，它还通过在 AgentCore Identity 的 JWT Authorizer 中配置自定义 claim，校验该租户 id 是否有权调用此 agent（例如“仅当 tenant_id = Tenant A 时允许”）。agent 使用 runtime 的 IAM 执行角色访问租户专属的 AgentCore Memory。
- **使用 AgentCore Gateway 访问工具** —— 当 agent 必须调用工具时，它调用*专用 AgentCore Gateway*，该 gateway 的作用域专门限定为访问某个特定租户的 MCP 工具。Gateway 会：使用 AgentCore Identity 校验 JWT。从校验过的 token 中提取租户上下文，并通过自定义拦截器验证该 Gateway 在上下文中已映射到该租户。与隔离的租户专属后端资源（API、数据库、知识库）集成。
- **响应流程** —— 工具响应经 Gateway 返回给 agent，agent 完成推理。隔离的 agent 应用租户专属格式化后返回给 SaaS 应用代理。代理把响应返回给用户。

Silo 模式的设计使每个客户的 agent 会话、工具访问与 memory 都完全封闭，成本也直接归集到其告警触发这项工作的那位客户。代价是更高的运营开销，因为每个客户运行的是专用资源而非共享资源。但对于安全关键、合规敏感的工作流，潜在影响范围有限使其成为正确选择。

## 使用 AgentCore 实现 Pool 模型

如下图所示，*pool 模型*实现跨多个租户的资源共享，因此你可以设计出最大化资源利用率并带来运营效率的架构。

### **关键架构组件**

- **池化的 Agent 层** —— 多个租户共享同一 AgentCore Runtime 与 agent 逻辑。
- **池化的 Gateway** —— 集中式 AgentCore Gateway，用 MCP 编排工具。
- **池化的 Agent Memory —— ** 共享的 AgentCore Memory，按租户上下文分区。
- **池化的数据层** —— 共享的工具、知识库、数据库与后端资源。
- **池化的身份管理** —— 池化的身份提供商，基于 JWT 传播租户上下文。

### **请求流程**

- **认证**—— 用户使用身份提供商完成认证，获得包含租户上下文（租户 ID 与订阅层级）的 JWT token。
- **SaaS 应用代理路由** —— SaaS 应用充当直通（pass through），把带租户上下文的输入请求路由到运行在池化 AgentCore Runtime 中的 agent。SaaS 应用代理把应用层请求转换为 AgentCore Runtime API 调用（InvokeAgent），并附上租户 JWT token。
- **Agent 执行** —— AgentCore Runtime 使用 AgentCore Identity 校验 JWT，创建隔离的 microVM 会话，从 JWT 中提取租户上下文并开始 agent 推理。agent 使用基于 namespace 的分区（例如 actor_id: “tenant-a:user-123”）访问租户范围内的 AgentCore Memory。
- **使用 AgentCore Gateway 访问工具** —— 当 agent 必须调用工具时，它调用*池化 AgentCore Gateway*，它专为 MCP 工具编排而设计，而不是通用路由。Gateway 会：使用 AgentCore Identity 校验 JWT。从校验过的 token 中提取租户上下文。把工具调用路由到池化的后端资源（API、数据库、知识库）。通过租户范围内的凭据与配置强制工具级隔离。为横切关注点应用策略执行与拦截器。
- **响应流程** —— 工具响应经 Gateway 返回给 agent，agent 完成推理。agent 响应经 Runtime 返回到 Seller 代理，代理应用租户专属格式化后再返回给用户。

pool 模型效率很高，当你拥有大量小租户时，它可能也是唯一选择。代价是需要在测试细粒度访问控制上更加严格，并且需要更多埋点来把成本归集到租户。

## 使用 AgentCore 实现 Bridge 模型

*bridge 模型*（混合模型）代表 silo 与 pool 两种部署模式之间的战略性折中位置。这种做法把共享基础设施的成本效率与隔离数据资源的安全收益结合起来。

依据你的需求，可以选择用多种方式实现 bridge 模式：

- 为高级层级租户使用隔离的 AgentCore Runtime/gateway/tool/memory，为标准层级使用池化共享的 AgentCore Runtime/gateway/tool/memory
- 隔离的 Runtime 搭配池化的 gateway/tool 与 memory
- 其他

其思想是能够在每一层、每个组件上选择 tenancy 方式，而不是被绑定到某一种租户隔离模式。依据你的实现方式，这种做法会结合两种方式的优势。例如在 SOC 分析师用例中，gateway 可以做成隔离的，以处理 email API 交互与其他下游租户资源，而池化的 agent runtime 托管 agent 并执行推理，因为每次调查都运行在自己的隔离 microVM 中。

## 结论

构建生产就绪的多租户 agent 应用，需要的不仅仅是能跑的 AI agent。它要求一套全面的架构方法，在每一层处理租户隔离、身份管理、成本归集与安全。Amazon Bedrock AgentCore 提供了应对这些挑战所需的基础原语，通过 silo、pool 与 bridge 模型提供灵活的部署模式，可针对你的具体分层策略与合规要求进行裁剪。无论你是服务需要专用基础设施的企业客户，还是在数以百计的较小租户之间优化成本，都可以使用 AgentCore 集成的 Runtime、Gateway、Memory、Identity 与 Observability 组件，构建安全、可扩展的多租户 agent workflow，而不必重复造轮子。这些原语协同工作，帮助保持租户数据隔离、受作用域限制的工具访问、准确的成本归集与安全边界，把多租户 agent 架构的复杂性转化为与你的 SaaS 业务一同扩展的、可管理且生产就绪的方案。
