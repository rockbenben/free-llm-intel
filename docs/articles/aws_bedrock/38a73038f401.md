# MoEngage 如何基于 Amazon Bedrock AgentCore 构建智能体化客户互动

*本文由 MoEngage 的 Ashwin Srinivasan、Nishan Das 和 Karthik Baile 共同撰写。*

市场或产品团队的成员在策划一场周末闪促时，往往在写下一行文案之前就已经打开了三个工具。先是打开分析 dashboard 看上次什么有效，然后打开内容库找到合适的语气，再打开 campaign builder 把 campaign 本身搭出来。把这套流程在 email、push、SMS 和 WhatsApp 上重复一遍，市场团队一周里的大部分时间就都花在切换工具上，而不是做决策。

MoEngage Model Context Protocol (MCP) Connector 让 Claude 或 ChatGPT 这类兼容 MCP 的助手能够以安全、限定在租户范围内的方式访问品牌的 segment、campaign 历史与内容库。

这项能力指向软件平台的一轮更广泛的转变。除了面向业务用户的用户界面和面向工程团队的 API，第三层正在浮现：用户用自然语言描述想要的结果，agent 在平台内把各个步骤执行完。对客户互动平台来说，这意味着一个已经以 API 形式暴露出来的能力可以变成 agent 调用的工具，而过去要在多个工具之间流转的 campaign，如今可以通过一次对话完成。

MoEngage 是一个 agentic 客户互动平台，有超过 1,350 个消费品牌在 push、email、应用内、SMS、WhatsApp 和 Rich Communication Services (RCS) 等渠道上使用它。它着手构建的正是这一层能力。MoEngage 打造了 Merlin AI——一组直接与平台实时数据协作的 AI agent。市场与产品团队现在可以在一次对话中起草、分析并调整 campaign，同时由 agent 决定向每位客户发送什么内容。其中一家客户 Glance 因此把 push 通知的点击率提升了 38%。

MoEngage 把这件事当成一个架构问题来处理。核心问题是：如何在不重建数百个现有 API 的前提下，让 agent 以安全、限定在租户范围内的方式访问实时数据。本文介绍 MoEngage 如何借助 Amazon Bedrock 与 Amazon Bedrock AgentCore 解决该问题——后者是一个可以用任意框架或模型大规模构建、连接和优化 AI agent 的平台。文章涵盖 Merlin AI 中的四种 agent 模式、MoEngage 如何把现有 API 暴露为 MCP 工具，以及该架构如何隔离每个租户的数据。最后给出 MoEngage 客户已经看到的结果，以及其它软件提供商可以复用的模式。

## 方案概览：Merlin AI 中的四种 agent 模式

Merlin AI 运行四种 agent。四者共享同一套基础：用于推理与生成的 Amazon Bedrock 基础模型、用于托管的 AgentCore runtime（Amazon Bedrock AgentCore 的一项能力），以及用于以标准化方式访问数据的 MCP。在四种模式下，Merlin AI 都在 Amazon Bedrock 上使用 Anthropic Claude Sonnet 4.6、Claude Sonnet 5 和 Claude Sonnet 5.5 进行推理、工具调用规划与内容生成。完整模型列表见 [Amazon Bedrock 支持的基础模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)。

### Merlin AI Studio 中的嵌入式 agent

Merlin AI Studio 把专门构建的 agent 放到市场与产品团队完成对应工作的那个确切工作流环节上：

- **Copywriter** 生成个性化的 push 与事务性文案，并保持与品牌语气一致。
- **Designer** 根据文本描述生成营销 banner 或图片。
- **Segment Assist** 把一段自然语言的受众描述转换成正确的属性与筛选条件组合。例如，市场或产品团队成员可以要求找出过去 2 小时内放弃购物车的用户。
- **Jinja Assist** 把自然语言请求转换成可用于动态内容的 Jinja 与 Liquid 标记。
- **In-app Template Builder** 为应用内消息创建响应式、无障碍的 HTML 模板，包括游戏化形式、线索收集弹窗和问卷。
- **Flow Assist** 把一个高层想法变成可直接部署的客户旅程。在后台，一系列专门步骤会解读请求、提出路径、构建 flow 结构、用历史数据加以打磨，并打包好以便部署。

### 对话式 agent

对话式 agent 横跨 campaign、分析、segment 和 flow 工作。用户可以用自然语言提出一个问题，agent 调用合适的工具来回答或执行。嵌入在分析页面上的 Campaign Insights Agent 会把工作委派给专门的子 agent。其中一个子 agent 会同时跨多个指标做分析，第二个诊断某个指标为何表现不佳，第三个则跨时间段或 segment 对比表现。最后一步把发现整理成一个清晰的答案。

### 自定义 agent

自定义 agent 让生命周期与客户关系管理（CRM）团队设计出能够持续运行在 MoEngage 数据与工具之上的 agent，并受产品与市场团队定义的规则约束。每个 agent 都会通过活动日志展示自己的工作过程：拉取了哪些数据、做了哪些决策、触及了哪些渠道、发送了什么内容。团队可以让 agent 完全自主运行，也可以要求在任何操作执行前经过人工审核。

### 决策 agent

决策 agent 为每一位客户单独行动。每个 agent 决定说什么、何时说、说多频繁、通过哪个渠道说，并从每一次结果中学习。产品与市场团队设定内容、目标和 guardrails，其余交给 agent 处理，且每一项决策都可见。Offer Decisioning 在 web 与 app 界面上挑选最佳 offer。Campaign Decisioning 在 email、push、SMS 和 WhatsApp 上交付 1:1 的决策。再配合 workflow agent，agentic 营销的两半就被放进了同一个系统。

## 架构概览

该架构分为四层。每一层只承担单一职责，并且可以在不影响其它层的情况下变更。

- **客户端。** MoEngage 产品内部的 Merlin AI agent，以及 Claude、ChatGPT 等外部 MCP client，都通过 MoEngage MCP Connector 连接到 MoEngage MCP server。任何支持 MCP 的 client 都可以连接。
- **AgentCore runtime 上的 MCP server。** MoEngage 把 MCP server 托管在 AgentCore runtime 上。该 server 把 MoEngage 平台能力暴露为 MCP 工具。它自己不运行模型，推理发生在调用它的 agent 中。
- **MoEngage 平台 API。** MCP server 调用的就是 MoEngage 客户已经在用的那套兼容 OpenAPI 3.0 的 API。这些 API 会执行现有的权限与数据驻留规则。
- **Amazon Bedrock 中的基础模型。** agent 使用 Amazon Bedrock 中的基础模型来规划工具调用、生成内容并总结结果。各区（Region）的模型可用情况见 [Amazon Bedrock 中各 AWS Region 支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

在一个典型请求中，用户登录 MoEngage 并提出问题。client 携带用户现有的 JSON Web Token (JWT) 发送请求。AgentCore runtime 校验该 token，并为这个用户启动一个隔离的会话。agent 向 Amazon Bedrock 中的模型询问该调用哪些工具。MCP server 带着用户的租户上下文调用 MoEngage API 并返回结果。随后 agent 组织出答案。

### 把现有 API 变成 MCP 工具

MoEngage 通过一个 MCP server 和可被 agent 调用的 API，把平台开放给 agent。它用于 campaign、分析、segment、内容和 flow 的平台 API 本来就兼容 OpenAPI 3.0，因此 MoEngage 用 FastMCP 框架从这些规范生成 MCP 工具。每个操作都会成为一个工具，带有结构化的 schema、一段描述和参数校验。

下面这个简化示例展示了该模式：

```
import httpx
from fastmcp import FastMCP

spec = httpx.get(MOENGAGE_OPENAPI_URL).json()
client = httpx.AsyncClient(base_url=MOENGAGE_API_BASE)
mcp = FastMCP.from_openapi(openapi_spec=spec, client=client, name='moengage')

if __name__ == '__main__':
    mcp.run(transport='streamable-http', host='0.0.0.0', port=8000)
```

这些工具分为五组：

- **Campaign 工具** 跨渠道创建、编辑、排期并发送 campaign。
- **分析工具** 查询投递漏斗、点击率、转化和 cohort 表现。
- **分群工具** 列出、查看并基于行为与属性筛选条件创建 segment。
- **内容工具** 管理内容块、模板和动态内容规则。
- **Flow 工具** 查看、暂停或修改自动化旅程。

这些工具来自规范本身，因此与 API 保持同步。当团队更新规范时，工具定义也会随之更新。

### 保持租户隔离，让身份信息不落入模型可及范围

多租户系统不能让模型自己决定它在读谁的数据。MoEngage 通过三项设计来帮助避免这一点。第一，MCP server 复用现有认证模型，接受与 MoEngage API 相同的基于 JWT 的认证方式，并且 AgentCore runtime 会在请求到达 server 之前校验每个 token。第二，workspace 与用户上下文通过请求 header 传递，由 AgentCore runtime 转发给 server，而不是作为工具参数传入，因此模型看不到这些值，也无法改动它们。第三，AgentCore runtime 在各自隔离的环境中运行每个用户会话，因此一个用户的对话无法读取另一个用户的会话状态。

在此之上，Amazon Bedrock Guardrails 对 agent 的响应施加内容安全与个人可识别信息（PII）过滤。随后，一个 backend-for-frontend 层会在 MoEngage 界面渲染之前校验生成内容的结构。

**把 agent 的控制权交给用户。** 用户可以设置每个 agent 能做什么的 guardrails，在活动日志中查看每一项操作，并在自主执行与人工审核执行之间做出选择。

### MoEngage 为什么选择 AgentCore runtime

AgentCore runtime 提供了多租户 MCP server 所需的生产级能力，而每一项能力都对应 MoEngage 工作负载的一项具体需求。AgentCore runtime 会随需求变化伸缩会话，因此 MoEngage 不必为跨客户 workspace 的流量峰值预留容量。默认情况下每个会话都运行在自己隔离的环境中，从而让一个品牌的对话与数据同另一个品牌隔开。内置的 JWT authorizer 会依据 MoEngage 现有的 identity provider 校验 token，因此 MCP server 使用的认证模型与 API 相同。

托管在 AgentCore runtime 上还与框架无关。MoEngage 可以更换模型或 agent 框架而无需改动 MCP server，这在 agent 层不断演进时很重要。通过 Amazon CloudWatch 提供的内置指标、日志与 trace，让 MoEngage 工程师对每个会话都具备可见性。这些能力合在一起，使团队能够专注于 agent 逻辑与营销智能，而不是托管基础设施。

通过 Amazon Bedrock 进行推理，还为 MoEngage 带来两项额外收益。Merlin AI 的 agent 运行在 Amazon Bedrock 上的 Anthropic Claude Sonnet 4.6、Claude Sonnet 5 和 Claude Sonnet 5.5 上，MoEngage 通过同一套 Amazon Bedrock API 在这些版本之间切换。MoEngage 也改为按 token 计费，而不再自己运营 GPU 基础设施。Amazon Bedrock 不会使用客户的 prompt 或响应训练基础模型，这对一个大规模处理客户互动数据的系统来说很重要。

## 一个 campaign，一次对话

下面的示例展示用户如何在不离开对话的情况下搭完一个 campaign。

- 请求初稿。用户输入：
  为我们高价值分群起草一条周末闪促的 push，语气与我们表现最好的 12 月 campaign 保持一致。 agent 会调用分析工具找出表现最好的 12 月 campaign，调用分群工具确认高价值 segment，并调用内容工具取来品牌语气。它返回一份包含多个文案变体的初稿。
- 检查哪些表现不佳。用户提问：
  上个月哪些 push 通知的点击率（CTR）低于 2%，它们有什么共同点？ Campaign Insights Agent 会对比这些 campaign 并报告共同的模式，例如发送时间或受众重叠。
- 调整旅程。用户提问：
  展示我们 onboarding flow 第 3 步的流失情况，如果 SMS 分支的转化率低于 5% 就暂停它。 agent 通过 flow 工具读取 flow 状态，并在用户确认后暂停该分支。这就是实际运用中的人工审核模式。

每一步使用的都是驱动 MoEngage 界面的那些工具。用户不需要打开另一个 dashboard。

## 成果

这套架构上的 Merlin AI agent 已在生产环境运行超过 6 个月。其中一家客户 Glance 让 campaign 上线速度提升了 50%，push 通知点击率提升了 38%。借助 Merlin AI Copywriter，Glance 的团队在每个 campaign 上生产的内容变体数量也达到原来的约三倍。

在整个平台上，MoEngage 报告称，市场与产品团队在渠道、时机和频率决策上的手工工作量减少了 60–70%，基于目标的决策带来的转化率提升了 20–30%。与自托管模型相比，Amazon Bedrock 中托管式、按 token 计费的推理把 AI 基础设施成本降低了 50% 以上。

AgentCore 的功能可用性因 AWS Region 而异。受支持的 Region 见 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/)。

## 结论

MoEngage 让平台为 agent 做好准备，而没有重建它。现有的 OpenAPI 规范变成了 MCP 工具。AgentCore runtime 提供了托管、认证与会话隔离。Amazon Bedrock 中的基础模型提供了推理与生成。最终得到的平台让市场与产品团队在一次对话中从提问走向行动，让 MoEngage 工程师把时间花在营销智能而不是基础设施上，并让 agent 为团队处理工作流、为每位客户做决策，同时让用户始终握有控制权。

同样的模式适用于其它拥有成熟 API 表面的软件提供商。从现有规范出发，把身份信息留在模型之外，并让托管式 runtime 处理生产层面的问题。

要在同一套基础上构建你自己的 MCP server，请从 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/) 开始，并按 AgentCore runtime 指南来托管它。要为你的 agent 挑选基础模型，并了解安全与数据处理控制，请参阅 [Amazon Bedrock 用户指南](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html)。要从现有 OpenAPI 规范生成 MCP 工具，请查阅 [FastMCP 文档](https://gofastmcp.com/)。想看 Merlin AI 的实际效果，请访问 [MoEngage Merlin AI](https://www.moengage.com/merlin-ai/)。要规划类似的架构，请联系你的 AWS 客户团队或 Solutions Architect。
