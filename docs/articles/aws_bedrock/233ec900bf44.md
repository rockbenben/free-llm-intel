# 大规模评估你的 Amazon Nova Sonic voice agent，无需麦克风

语音 agent 正在改变企业与客户互动的方式，它通过自然的口语对话处理预约、订单查询、账户管理等任务。但随着这些 agent 能力越来越强，一个根本性的挑战浮现出来：你该如何测试它们？

基于文本的聊天机器人可以脚本化输入并断言输出，语音 agent 则在一种根本不同的范式下运作。它们双向流式传输音频、以非确定性的方式响应、在多轮对话中维持上下文，并实时使用工具。如今大多数团队唯一的测试办法，是让人真的对着系统说话，再听听系统回什么。这又慢、又不一致，而且无法扩展。

这一测试缺口给构建语音应用的团队带来两个关键问题：

- **迭代 system prompt 与工具配置痛苦而缓慢。** 每次为了提升准确率而微调 prompt 或调整工具定义，你都得手动重测几十个对话场景，看看事情变好了还是变坏了。没有自动化的反馈，prompt 工程就变成了猜谜。
- **没有可靠的评估框架来衡量语音 agent 的质量。** 你无法在部署变更前跑一套回归测试。你无法度量 agent 在数百个场景中是否正确处理了边界情况。你也无法在真实客户撞上之前，捕捉到那些细微的回归——比如 agent 突然忘了确认预约。

如果你有 3 种用户人设下的 50 个对话场景，那就是 150 次手动测试，每次都要花上几分钟的实时交互。每改一次 prompt 就跑一遍，你的 QA 时间会成天成天地烧掉。

在本文中，我们带你了解 [Nova Sonic Test Harness](https://github.com/aws-samples/sample-amazon-nova-sonic-eval-harness)——我们为同时解决这两个问题而构建的开源框架。它既是一个用于调优 system prompt 与工具配置的快速迭代工具（跑一段对话、看结果、调整、再来一遍），也是一个用于大规模验证语音 agent 质量的综合评估框架。它会用 [Amazon Nova Sonic](https://docs.aws.amazon.com/nova/latest/userguide/speech.html) 自动跑完整的多轮对话，用 LLM-as-judge 技术对它们进行评估，甚至能检测出模型音频输出与文本输出不一致的情况（音频幻觉）。无需麦克风。

## 为什么 speech-to-speech 测试不一样

如果你以前测试过基于文本的大语言模型（LLM），你可能会想：为什么不直接把那些工具改造过来用？下面是语音 agent 测试在根本上更难的原因：

**双向流式传输。** Speech-to-speech 模型不使用请求-响应模式。它们维持一条持久的全双工连接，音频与文本同时在两个方向上流动。标准的 HTTP 测试工具无法与这种协议交互。

**非确定性响应。** 同一个问题问两次，你会得到不同的措辞、不同的音频时序，甚至不同的工具调用顺序。你没法写出“期望精确字符串 X”这样的断言。

**多轮上下文。** 单看一轮几乎说明不了什么。有意思的行为发生在跨轮之间：模型记得来电者之前说过什么吗？它会恰当地追问吗？它知道对话何时结束吗？

**音频与文本背离。** Speech-to-speech 模型同时产出文本与音频，而两者可能说的不是一回事。文本里写着“3:00 PM”，音频里说的却是“3:30 PM”。光读转写文本抓不到这种问题。

**会话上限。** 连接大约 8 分钟后就会超时。如果你的测试对话更长，就必须处理重连与历史重放。

测试 harness 把这些问题全都处理掉了。我们来看看它是怎么工作的。

## 测试 harness 如何工作

从高层看，harness 做四件事：配置一个测试场景、与 Nova Sonic 跑完一段完整对话、评估结果并生成报告。整条 pipeline 无人值守地运行。你在一个 JSON 文件里定义场景，然后回来取结果。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/26/ML-21086-1.png)

*图 1：架构总览。测试 harness 协调用户模拟器、Nova Sonic 与 LLM 评判器，跨多个 AWS 服务运行。*

我们逐个阶段来看。

### 定义测试场景

每个测试都始于一个 JSON 配置文件。可以把它看作对一段对话场景的描述：Nova Sonic 扮演谁、来电者是谁、有哪些工具可用，以及“成功”长什么样？

下面是一个真实示例，用于测试预约挂号 agent：

```
{
    "test_name": "healthcare_appointment_booking",
    "sonic_system_prompt": "You are the receptionist at Dr. Smith's office...",
    "sonic_voice_id": "tiffany",
    "sonic_tool_config": {
        "tools": [{"toolSpec": {"name": "checkAvailability", "..."}}]
    },
    "user_model_id": "claude-haiku",
    "user_system_prompt": "You are a patient calling to book an appointment...",
    "max_turns": 8,
    "auto_evaluate": true,
    "evaluation_criteria": {
        "user_goal": "Book an appointment for next Tuesday",
        "evaluation_aspects": ["Goal Achievement", "Response Accuracy", "Tool Usage", "Conversation Flow"],
        "rubrics": {
            "Goal Achievement": [
                "Did the agent confirm a specific date and time?",
                "Did the agent collect the patient name?"
            ]
        }
    }
}
```

关键洞见在于：你定义的是*目标*与*评估标准*，而不是期望输出。因为 Nova Sonic 每次的响应都不一样，我们按评分细则（rubric）来评估，而不是检查精确字符串。

模型注册表（`models.yaml`）把 `claude-haiku` 这样的简短别名映射到完整的 Amazon Bedrock 模型 ID，这样当模型版本变化时，配置不会失效。

### 运行对话

拿到配置文件之后，harness 会自动运行对话。每一轮会发生这些事：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/26/ML-21086-2.png)

*图 2：从配置到结果的四阶段测试 pipeline。*

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/26/ML-21086-3.png)

*图 3：单轮对话内的数据流。*

- **用户模拟器生成一条消息。** 一个 LLM（例如 Amazon Bedrock 上的 Claude Haiku）读取到目前为止的对话，决定来电者接下来会说什么。它会保持角色。如果人设是“不耐烦的客户”，它就表现得不耐烦。
- **这条消息发给 Nova Sonic。** 要么以文本形式（快，适合大多数测试），要么用 Amazon Polly 合成音频（用于测试完整的语音识别 pipeline）。
- **Nova Sonic 流式返回响应。** 文本、音频，可能还有工具调用，都异步到达。harness 使用响应式流实时处理这些内容。
- **harness 判断这一轮何时结束。** Nova Sonic 分两个阶段产出文本（先推测，再最终）。当所有推测块都定稿后，这一轮就完成了。这比等待静音或使用超时更可靠。
- **工具调用在流内处理。** 如果 Nova Sonic 请求调用某个工具（比如查询预约可约时段），注册的 handler 会执行并返回结果，且不中断连接。
- **一切都被记录。** 最终文本、音频 WAV、工具调用与时序元数据全部保存下来。

然后循环重复。

### 长对话怎么办？

Nova Sonic 的连接大约 8 分钟后超时。`SessionContinuationManager` 透明地处理这件事：它监控连接的存活时长，在超时之前（默认 6 分钟）创建新会话，并把对话历史重放进新会话。你的测试场景不需要知道这些，它自己就能跑通。

### 评估质量

对话结束后，harness 把完整转写文本交给一个独立的 LLM 评判器（例如 Claude Opus）。评判器对测试设置一无所知，它只看到对话与评估标准。这样可以避免偏见。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/26/ML-21086-4.png)

*图 4：LLM 评判器独立评估每一项指标，以 YES/NO 的评分细则给出判定。*

评判器评估六项内置指标，分为三个层级：

| **指标** | **层级** | **检查内容** |
| --- | --- | --- |
| Goal Achievement | Critical | 对话是否完成了用户想要的结果？ |
| Response Accuracy | Critical | 事实、数字与陈述是否正确？ |
| Tool Usage | Important | 是否以正确的参数调用了正确的工具？ |
| Conversation Flow | Important | 听起来像自然的对话吗？ |
| System Prompt Compliance | Important | agent 是否保持了角色？ |
| Voice Formatting | Advisory | 这段响应朗读出来会自然吗？ |

层级系统决定通过/失败的逻辑：两项 Critical 指标都必须通过，整体才算 **PASS**。Important 指标计入通过率得分。Advisory 指标只做报告，不影响最终判定。

每项指标都通过多个评分细则问题来评估，这些问题只接受严格的 YES/NO 回答。只有当某项指标的**所有**评分细则问题都通过时，该项指标才算通过。这意味着当某处失败时，你能确切知道是哪个问题失败，并可以阅读评判器的推理过程来理解原因。

你也可以为自己的领域定义自定义评分细则问题。对医疗 agent，你可能会加一条：“agent 在预约之前是否核实了保险信息？”对银行 agent：“agent 在执行转账之前是否确认了金额？”

### 查看结果

结果会以多种格式呈现，取决于你的工作流：

- **交互式看板。** 通过一个 Streamlit 应用，你可以可视化浏览批量结果、对比多次运行、下钻到失败项，并跨转写文本搜索。
- **结构化 JSON/CSV。** 每个会话都会在一个组织好的目录里产出交互日志、评估结果与音频文件。批量汇总会把所有会话的通过率聚合起来。
- **对持续集成与持续交付（CI/CD）友好的判定。** 二值的 PASS/FAIL 输出与数值化的通过率，被设计为可以直接接入自动化质量门禁。

## 捕捉音频幻觉

Speech-to-speech 模型同时产出文本与音频。多数时候两者一致。但偶尔 Nova Sonic 会写一套、说另一套。想象一个语音 agent 在音频里告诉客户订单“下周一”到，而文本流里写的是“下周二”。如果你只检查文本日志，你永远抓不到这种问题。

- 把每一轮的音频上传到 Amazon Simple Storage Service（Amazon S3）。
- 用 Amazon Transcribe 转写它（记录实际说出的内容）。
- 用一个 LLM 把转写结果与文本输出做比对。
- 对每一处差异进行分类：填充词、措辞变体，还是事实性错误。

每一轮都会得到一个判定：

- **CONSISTENT。** 只有填充词（“um”“uh”），或者根本没有差异。
- **MINOR_DIFFERENCES。** 意思相同的措辞变体（“I can help you”与“Let me help”）。
- **HALLUCINATION。** 事实性不符。文本与音频在数字、日期、名称或陈述上不一致。

这对传递具体事实的语音 agent 最为重要：预约时间、价格、电话号码、药品名称、确认码。其中任何一项出现幻觉，都可能直接伤害用户。

## 规模化测试

测试单个场景对开发很有用。但在部署前要建立信心，你必须测试几十个场景，覆盖不同人设、边界情况与对话路径，而且必须反复运行，以应对非确定性。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/26/ML-21086-5.png)

*图 5：批量执行并行跑多个测试会话，并汇总质量报告。*

批量运行器让这件事变得可行：

```
# Run 12 healthcare scenarios in parallel
python -m cli.main --scenarios-dir scenarios/healthcare --parallel 4

# Run the same scenario 10 times to measure variance
python -m cli.main --config configs/order_status.json --repeat 10 --parallel 5

# Run a 100-entry evaluation dataset
python -m cli.main --dataset datasets/healthcare_eval.jsonl --parallel 8
```

harness 自带开箱即用的场景包：12 个医疗场景（预约挂号、保险理赔、转诊）、8 个银行场景（转账、余额查询、争议处理），以及 5 个客户服务变体（愤怒、平静、困惑的来电者，搭配不同的订单状态）。

批量运行之后，看板会展示所有场景的通过率、各指标的分解、共同失败相关性（哪些指标倾向于一起失败），以及多次运行之间的并排对比。你可以确切看到改动 prompt 之后什么变好了、什么退步了。

## 选择合适的输入模式

不同的测试需求需要不同的做法。harness 支持四种输入模式：

| **模式** | **工作方式** | **适用场景** |
| --- | --- | --- |
| Text（默认） | LLM 生成的消息以文本事件发送 | 日常测试、prompt 迭代、工具验证 |
| Amazon Polly TTS | 用户文本用 Amazon Polly 合成为音频 | 测试完整的自动语音识别（ASR）pipeline、接近生产的条件 |
| Scripted | 预定义消息，不涉及 LLM | 回归测试、多次运行之间精确可复现 |
| Dataset-driven | 场景从 JSONL 或 Hugging Face 加载 | 基准评估、大规模测试套件 |

Text 模式最快，支持最高的并行度。当你确实需要测试 Nova Sonic 如何处理真实音频输入时（包括 ASR 可能出现的误识别），使用 Amazon Polly 模式。当回归测试需要每次输入完全一致时，使用 Scripted 模式。

## 用到的 AWS 服务

| **服务** | **在 harness 中的作用** | **是否必需？** |
| --- | --- | --- |
| [Amazon Bedrock](https://aws.amazon.com/bedrock) | 托管 Nova Sonic、用户模拟器 LLM 与评判 LLM | 是 |
| [Amazon Polly](https://aws.amazon.com/pm/polly/) | 在音频输入测试中把用户文本转为语音 | 可选 |

| [Amazon Transcribe](https://aws.amazon.com/pm/transcribe) | 在幻觉检测中把音频转为文本 | 可选 |

## 清理

Amazon Bedrock 的模型调用按使用量付费，没有空闲费用。如果你使用了可选服务，请删除为音频评估创建的任何 Amazon S3 存储桶（其中的对象会被自动清理，但存储桶本身会保留）。如有需要，你可以在 AWS Management Console 中移除 Amazon Transcribe 任务。

## 结论

在这个工具出现之前，测试 Nova Sonic voice agent 只意味着两种选择：让人去和它说话（慢、不一致、无法扩展），或者干脆不测（有风险，尤其是在迭代 prompt 或部署到新场景时）。

Nova Sonic Test Harness 给了你第三个选项：自动化、可重复、可扩展的测试，覆盖完整的对话生命周期——从第一轮到评估，再到幻觉检测。它处理了那些难啃的部分（双向流式传输、会话超时、非确定性评估），让你可以专注于构建更好的语音体验。

## 关键要点

- **不需要音频硬件。** 测试 Nova Sonic 就像测试任何 API 一样简单。
- **LLM 驱动的评估。** 用基于评分细则的评估应对非确定性，而不是脆弱的断言。
- **音频幻觉检测。** 捕捉文本与音频的背离。
- **可水平扩展。** 用一条命令并行运行数百个场景。
- **开源且可扩展。** 添加你自己的工具、指标、评分细则与场景。

克隆[仓库](https://github.com/aws-samples/sample-amazon-nova-sonic-eval-harness)，今天就跑起你的第一个测试。随着你的 Nova Sonic 应用成长，测试也一起成长。
