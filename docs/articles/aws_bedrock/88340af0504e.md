# 使用 Amazon Bedrock 创建异步 AI agent

随着各类组织认识到这些技术尚未开发的潜力，将生成式 AI agent 集成到业务流程中的进程势必加速。多模态人工智能（AI）的进步——agent 不仅能理解和生成文本，还能理解并生成图像、音频和视频——将进一步拓宽其应用范围。本文将讨论由 agentic AI 驱动的架构以及实现方式。

近年来生成式 AI agent 的出现推动了 AI 格局的转变，其动力来自大语言模型（LLM）和自然语言处理（NLP）的进步。Anthropic、Cohere 和 Amazon 等公司在开发强大的语言模型方面取得了重大进展，这些模型能够跨多种模态理解并生成类人内容，正在彻底改变企业在其流程中集成和使用人工智能的方式。

这些 AI agent 展现出非凡的多面性，能够执行从创意写作、代码生成到数据分析、决策支持等各类任务。它们进行智能对话、给出具备上下文感知的响应以及适应不同领域的能力，已经彻底改变了企业处理问题解决、客户服务和知识传播的方式。

生成式 AI agent 最重大的影响之一，在于它们能够通过同步与异步两种模式增强人的能力。在同步编排（orchestration）中，与传统流程自动化一样，由一个 supervisor agent 编排多 agent 协作，在保持对整个流程高层视图的同时，主动引导信息和任务的流动。这种方式让企业能够以可控、可预测的方式卸载重复且耗时的任务。

另一种方式是异步协同（choreography），它遵循事件驱动模式：agent 自主运行，由系统中的事件或状态变化触发。在这种模式下，agent 发布事件或消息，其他 agent 可以订阅这些事件或消息，从而形成一个由它们的集体行为涌现出的 workflow。在提升客户体验方面，这些模式尤其有价值：agent 可以通过编排式或事件驱动的交互提供全天候支持、快速解决问题并给出个性化推荐，从而提升客户满意度与忠诚度。

## agentic AI 架构

agentic AI 架构代表了流程自动化从借助自主 agent 向 AI 能力的一次转变，其目的是模仿认知能力，并增强传统自主 agent 的行动能力。这种架构能够帮助企业精简运营、改进决策流程，并以新的方式自动化复杂任务。

与借助技术的传统业务流程自动化十分相似，**agentic AI 架构是对 AI 系统的设计，这类系统旨在以有限或间接的人工干预解决复杂问题**。这些系统由多个 AI agent 组成，它们彼此对话，或通过一系列协同或编排的流程执行复杂任务。这种方式让 AI 系统能够表现出目标导向的行为、从经验中学习，并适应不断变化的环境。

单次 agent 调用与多 agent 协作之间的区别，在于流程的复杂程度以及参与其中的 agent 数量。

当你与 Alexa 这样的数字助理交互时，通常是在与单个 agent（也称为对话 agent）打交道。这个 agent 处理你的请求（例如设置定时器或查询天气），并在无需咨询其他 agent 的情况下给出响应。

现在，设想把这种交互扩展为多个 agent 协同工作。我们先从一个简单的旅行预订场景开始：

你的交互从向一个旅行规划 agent 说明心仪的行程开始。在第一步中，AI 模型（这里是一个 LLM）充当解释器和用户体验界面，在你输入的自然语言与旅行规划系统所需的结构化信息之间做转换。它处理你的请求——可能是像“我想下个月带四口之家去夏威夷度一周的海滩假期”这样复杂的表述——并提取目的地、时长、出行人数和大致日期等关键细节。

LLM 还可能推断出未被明确提到的其他相关信息，例如需要适合家庭的住宿或活动。它可能会追问以澄清含糊之处，或收集更具体的偏好。实质上，LLM 正在把你随口说出的对话式输入转化为一组结构化的旅行需求，供 workflow 后续步骤中的专业预订 agent 使用。

这次初始交互为整个多 agent workflow 奠定了基础，确保旅行规划 agent 在调用其他专业 agent 之前已清楚理解你的需求。

再增加一个 agent——航班预订 agent——旅行规划 agent 就可以调用它来查找合适的航班。旅行规划 agent 需要向航班预订 agent 提供相关信息（日期、目的地），并等待、处理航班预订 agent 的响应，从而把航班选项纳入整体方案

现在，我们再向 workflow 中加入一个 agent：负责寻找住宿的酒店预订 agent。有了这个新增角色，旅行规划 agent 还必须与酒店预订 agent 沟通，后者需要确保酒店日期与航班日期一致，并把信息回传给整体方案，以同时包含航班和酒店选项。

当我们继续添加 agent，例如租车 agent 或本地活动 agent 时，每个新成员都会从旅行规划 agent 那里收到相关信息，执行自己的特定任务，并返回结果以并入整体方案。旅行规划 agent 不仅充当用户体验界面，还充当协调者，决定何时引入各个专业 agent，以及如何把它们的输入整合为一份连贯的旅行方案。

这种多 agent workflow 通过利用每个 agent 的特定能力，能够完成更复杂的任务。系统保持灵活，因为可以根据每个请求的具体需求增删 agent，既不需要对现有 agent 做重大改动，对整体 workflow 的改动也很小。

关于把任务拆解给 agent 的好处，参见[任务拆解与更小的 LLM 如何让 AI 更可负担](https://www.amazon.science/blog/how-task-decomposition-and-smaller-llms-can-make-ai-more-affordable)。

## 使用 agentic AI 架构实现流程自动化

前面的场景与传统流程自动化一样，是一种常见的编排模式：多 agent 协作由一个 supervisor agent 编排。supervisor agent 就像指挥一支管弦乐队的指挥，告诉每件乐器何时演奏、如何与其他乐器协调。对于这种方式，[Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 让生成式 AI 应用能够执行由某个 agent 编排的多步任务，并借助 Amazon Bedrock Agents 创建多 agent 协作来解决复杂任务。具体做法是把一个 Amazon Bedrock agent 指定为 supervisor agent，并为该 supervisor 关联一个或多个协作 agent。更多细节请阅读[创建和配置 Amazon Bedrock Agents](https://aws.amazon.com/blogs/aws/agents-for-amazon-bedrock-introducing-a-simplified-creation-and-configuration-experience/)以及[在 Amazon Bedrock Agents 中使用多 agent 协作](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-multi-agent-collaboration.html)。

沿用传统流程自动化的模式，与同步编排相对的另一端是异步协同：一种异步、事件驱动的多 agent workflow。在这种方式中，不存在中心的编排 agent（supervisor）。agent 自主运行，动作由事件或系统状态的变化触发，agent 发布事件或消息，其他 agent 可以订阅。在这种方式中，workflow 从 agent 异步响应事件的集体行为中涌现出来。它更像爵士乐的即兴演奏，每位乐手回应其他人正在演奏的内容，而没有指挥。下图展示了这种事件驱动的 workflow。

事件驱动 workflow 方法

异步系统中的事件驱动模式在没有预定义 workflow 的情况下运行，从而营造出一个动态、甚至可能混乱的处理环境。虽然 agent 通过中心事件枢纽订阅和发布消息，但处理流程是由消息需求与可用的订阅 agent 有机决定的。尽管结果模式在可视化时可能看起来像一个结构化 workflow，但重要的是要理解：这是涌现行为，而非编排式的设计。缺少集中式 workflow 定义意味着消息处理会基于发布时机和 agent 可用性自然发生，从而形成一个流畅且可适应的系统，能够随需求变化而演进。

在同步编排与异步事件驱动模式之间做选择，从根本上决定了 agentic AI 系统如何运行和扩展。同步编排及其 supervisor agent 方式提供了精确的控制与可预测性，使其非常适合需要严格监督和顺序执行的复杂流程。这种模式在 workflow 需要被紧密管理、审计和调试的场景中表现出色。不过，由于所有操作都必须经过 supervisor agent，它也可能造成瓶颈。相反，异步事件驱动系统凭借其分布式特性提供了更大的灵活性和可扩展性。通过让 agent 独立运行并实时响应事件，这类系统能够处理动态场景，并更从容地适应变化的需求。虽然这种方式可能会让 workflow 的跟踪和调试变得更复杂，但在需要高可扩展性、容错性和自适应行为的场景中它表现出色。在这两种模式之间做决定，往往取决于系统的具体需求，需要在控制性与可预测性的需要，与灵活性和可扩展性带来的好处之间取得平衡。

## 兼取两种模式之长

你可以用单个 agent 在运行时根据事件数据（消息）的上下文把消息路由给其他 agent，事先无需了解下游 agent，也不必依赖每个 agent 都订阅某个事件枢纽。这在传统上称为消息代理（message broker）或事件代理（event broker）模式；为本文起见，我们称之为 agent broker 模式，以表示把消息代理给 AI agent。agent broker 模式是一种混合方式，融合了集中式同步编排与分布式异步事件驱动系统的要素。

这种模式的关键在于：单个 agent 充当消息分发的中心枢纽，但并不控制整个 workflow。broker agent 根据消息的内容或元数据决定把每条消息发往何处，在运行时做出路由决策。处理 agent 彼此解耦，也与消息来源解耦，只与 broker 交互以接收消息。agent broker 模式与 supervisor 模式不同：它把消息路由给某个 agent 后并不等待响应，而 supervisor 模式会等待协作 agent 的响应。下图展示了 agent broker 方法。

Agent broker 方法

采用 agent broker 模式时，系统从根本上仍然是事件驱动的，动作由消息到达触发。可以添加新的 agent 来处理特定类型的消息，而无需改变整体系统架构。关于如何实现这类模式，本文后面会进一步说明。

这种模式常用于企业消息系统、微服务架构和复杂事件处理系统。它在编排式 workflow 的结构性与纯事件驱动系统的灵活性之间取得了平衡。

## 基于 Amazon Bedrock Converse API 的 agentic 架构

传统上，当我们向架构中添加额外的流程（agent）时，可能不得不同时更新 broker 中的路由逻辑，从而牺牲 broker 模式的部分灵活性。然而，使用 Amazon Bedrock Converse API 时情况并非如此。借助 [Converse API，我们可以调用工具](https://docs.aws.amazon.com/bedrock/latest/userguide/tool-use-inference-call.html)来完成 Amazon Bedrock 模型的响应。唯一的改动，就是以配置形式存放在 broker 之外、加入协作的那个额外 agent。

要让模型使用工具来完成对某条消息的响应，需要把该消息以及一个或多个工具（agent）的定义发送给模型。如果模型判断其中某个工具有助于生成响应，它就会返回一个使用该工具的请求。

作为 AWS Systems Manager 的一项能力，[AWS AppConfig](https://docs.aws.amazon.com/appconfig/latest/userguide/what-is-appconfig.html#appconfig-when-to-use) 用于把每个 agent 的工具上下文数据作为一份配置存放在托管数据存储中，以便发送给 Converse API 的 tool 请求。以 [AWS Lambda](https://docs.aws.amazon.com/lambda/latest/dg/welcome.html) 作为消息 broker 来接收所有消息，并把 AWS AppConfig 中存储的工具上下文随请求发送给 Converse API，这种架构就允许在不更新路由逻辑的情况下向系统添加额外 agent：只需把 agent 作为“工具上下文”注册到 AWS AppConfig 中保存的配置里，由 Lambda 在运行时（收到事件消息时）读取。关于何时使用 AWS Config 的更多信息，参见 AWS 的 [AppConfig 使用场景](https://docs.aws.amazon.com/appconfig/latest/userguide/what-is-appconfig.html#appconfig-when-to-use)。

### 实现 agent broker 模式

下图展示了 [Amazon EventBridge](https://aws.amazon.com/eventbridge/) 与 Lambda 如何充当中心消息 broker，并通过 Amazon Bedrock Converse API 让模型在对话中使用工具，把消息动态路由到合适的 AI agent。

Agent broker 架构

发送到 EventBridge 的消息会经由一条 EventBridge 规则路由到 Lambda。作为 agent broker，这个 EventBridge Lambda 函数执行三项任务：

- 查询 AWS AppConfig，获取所有 agent 的工具上下文。agent 工具上下文是对该 agent 能力的描述，以及该 agent 消息入口的 Amazon Resource Name（ARN）或 URL。
- 通过 Converse API 把 agent 工具上下文与入站事件消息一起提供给 Amazon Bedrock LLM；在本例中使用的是一个兼容工具的 Amazon Bedrock LLM。该 LLM 使用 Converse API，把事件消息的上下文与 agent 工具上下文相对比，从而把响应返回给发起请求的 Lambda 函数，其中包含处理该消息建议使用的一个或多个工具。
- 接收 Converse API 请求返回的响应，其中包含处理该事件消息应调用的一个或多个工具，并把事件消息交给推荐工具的入口。

在这个示例中，该架构演示了如何从同一个 agent broker 异步地把消息代理给一个基于 [Amazon SageMaker](https://aws.amazon.com/sagemaker/) 的 agent、一个 Amazon Bedrock agent，以及一个外部的第三方 agent。

尽管代理用的 Lambda 函数可以直接连接 SageMaker 或 Amazon Bedrock agent 的 API，但该架构在消息吞吐上提供了适应性与可扩展性：从 agent broker 发出的消息可以先进入队列（本例中使用 [Amazon Simple Queue Service](https://aws.amazon.com/sqs/)（Amazon SQS）），再按接收 agent 的能力进行处理。为了获得适应性，订阅 agent 入口队列的 Lambda 函数会提供额外的系统 prompt（针对特定工具上下文对 LLM 进行 pre-prompting）、格式化后的消息，以及该 agent 请求预期输入输出所需的函数。

要往系统中添加新的 agent，集成要求只有两项：用新 agent 的工具上下文（agent 能力描述与入口端点）更新 AWS AppConfig，并确保代理用的 Lambda 函数具有写入该 agent 入口端点的权限。

添加 agent 无需重写 Lambda 函数，也不需要会造成停机的集成改动，新 agent 会在代理用 Lambda 函数下一次实例化时即可使用。

### 借助 agent broker 实现 supervisor 模式

在 agent broker 模式的基础上，架构可以进一步扩展，以处理更复杂、有状态的交互。尽管 broker 模式有效地利用 AWS AppConfig 和 Amazon Bedrock Converse API 的工具使用能力实现了动态路由，但其单向特性存在局限。事件流入并分发给各个 agent，但像旅行预订这样的复杂场景需要跨多次 agent 交互维持上下文。这正是 supervisor 模式发挥作用之处：它提供额外能力，同时不损害我们通过 broker 模式获得的灵活路由。

以旅行预订 agent 为例：该示例包含一个 broker agent，以及若干会被推送事件的任务型 agent。在处理“为 2 人预订 9 月第一周从墨尔本到悉尼的 3 晚行程”这样的请求时，我们会遇到几个挑战。尽管这句话表达了明确的意图，但它缺少 agent 可能需要的关键细节，例如：

- 具体的出行日期
- 住宿偏好与房间配置

仅靠 broker 模式无法在维持 agent 交互上下文的同时有效管理这些信息缺口。这正是给 broker agent 增加 supervisor 能力所能提供的：

- 事件与 agent 调用之间的上下文感知
- 双向信息流能力

Supervisor 模式架构

当新事件进入系统时，该 workflow 会启动以下步骤：

- 为该事件分配一个唯一标识符以便跟踪
- supervisor 执行以下动作：评估要调用哪些 agent（brokering）；用该标识符与时间戳创建新的状态记录；把这份上下文信息连同调用参数一起提供给选中的 agent
- 各个 agent 处理自己的任务，并向 EventBridge 回发“任务完成”事件
- supervisor 执行以下动作：收集并处理已完成的事件；评估合并后的结果与上下文；判断是否需要额外的 agent 调用；持续这一循环，直到所有必要的动作都已完成

这种模式能够处理 agent 可能返回不同结果或请求补充信息的场景。supervisor 可以：

- 从其他 agent 的响应中推导缺失的信息
- 向来源请求补充信息
- 与其他 agent 协调以弥补信息缺口

为了在不改动架构的情况下处理信息缺口，我们可以向现有系统引入一个 answers agent。该 agent 与其他 agent 在同一框架内运行，但专门负责上下文消解。当 agent 报告信息不完整或需要澄清时，answers agent 可以：

- 处理关于缺失信息的查询
- 发出带有增强上下文的任务完成事件
- 让 supervisor 能利用新获得的信息恢复 workflow 执行，就如同在另一个 agent 发出任务完成事件后那样。

这一增强使得复杂的多步 workflow 成为可能，同时保持系统的可扩展性与灵活性。supervisor 可以管理 agent 之间的依赖关系、处理部分完成的情况，并确保在最终完成任务之前收集到必要的信息。

### **实现注意事项：**

在现有 broker agent 架构之上实现 supervisor 模式，可以同时获得 broker 模式的优势与编排带来的复杂状态管理能力。状态管理可以通过 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 处理，同时继续使用 EventBridge 进行事件路由、使用 AWS AppConfig 进行 agent 配置。Amazon Bedrock Converse API 在 agent 选择上继续发挥关键作用，只是现在多了来自 supervisor 状态管理的上下文。这样既能保留我们用 broker 模式建立的动态路由能力，又能增加复杂多步流程所需的精细 workflow 管理。

## 结语

由 Amazon Bedrock 和 AWS 服务驱动的 agentic AI 架构，代表着自动化 AI 系统演进中的一次飞跃。通过把事件驱动系统的灵活性与生成式 AI 的强大能力结合起来，这种架构使企业能够构建更具适应性、可扩展性和智能性的自动化流程。agent broker 模式为把复杂任务动态路由到专业 AI agent 提供了稳健的解决方案，而 agent supervisor 模式则扩展了这些能力，以处理精细的、具备上下文感知的 workflow。

这些模式利用 Amazon Bedrock Converse API、Lambda、EventBridge 和 AWS AppConfig 的优势，构建出一个灵活且可扩展的系统。broker 模式擅长动态路由与无缝的 agent 集成，supervisor 模式则为复杂多步流程增加了至关重要的状态管理与上下文感知。两者结合，为构建既能处理简单路由又能处理复杂有状态交互的精细 AI 系统提供了全面的框架。

这种架构不仅精简了运营，还为各行各业的创新与效率打开了新的可能。无论是实现简单的任务路由，还是编排需要维持上下文的复杂 workflow，组织都可以构建可扩展、易维护、能随自身需求演进的 AI 系统，同时保持运营稳定。

- **为你的 agent broker 做原型** —— 以本文概述的架构为起点，构建一个符合组织需求的概念验证 agent broker 系统。先从少数几个专业 agent 小规模开始，再逐步扩展。
- **识别用例** —— 分析当前的业务流程，找出 agentic AI 架构能够带来显著改进的环节。关注那些能从 AI 辅助中受益的复杂多步任务。

- **协作与分享** —— [加入 AI 与云计算社区](https://community.aws/generative-ai)，分享你的经验并向他人学习。可以考虑为开源项目做贡献，或撰写关于你实现方案的文章，帮助推动该领域发展。
- **投入培训** —— 确保团队具备[使用这些先进 AI 技术所需的技能](https://aws.amazon.com/training/learn-about/generative-ai/)。可以考虑 AWS 的培训与认证项目，在组织中培养专业能力。
