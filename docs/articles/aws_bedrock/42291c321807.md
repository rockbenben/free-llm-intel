# 在 AWS 上使用 LangSmith 评估深度 agent

*本文与 [LangChain](https://www.langchain.com/) 合作伙伴关系负责人 Karan Singh 共同撰写*

在生产环境之前验证 AI agent 的行为，是应用型 AI 中最难的问题之一。agent 是非确定性的、多步骤的，早期步骤中的错误会影响下游结果。一次糟糕的工具调用就可能级联影响整个工作流。AWS 上的 LangSmith 为你提供评估框架，帮助你及早发现这些问题、在生产环境中跟踪它们，并在整个生命周期中持续提升 agent 的可靠性。

本文把 [LangChain 在评估深度 agent 方面的工作](https://blog.langchain.com/evaluating-deep-agents-our-learnings/)与 [Anthropic 关于为 AI agent 揭开 eval 神秘面纱的指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)中的经验，整合成一份实用指南。通过本文，你将学会：1）为深度 agent 应用五种评估模式；2）使用 pytest 与 LangSmith 构建离线评估；3）为生产环境配置在线监控。完整演示使用一个[文本转 SQL 的深度 agent](https://github.com/langchain-ai/deepagents/tree/master/examples/text-to-sql-agent)，配合 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 覆盖从开发到生产的完整生命周期。

[Amazon Nova 2 Lite](https://aws.amazon.com/blogs/aws/introducing-amazon-nova-2-lite-a-fast-cost-effective-reasoning-model/) 是 Amazon Bedrock 中可用的快速、高性价比推理模型。它支持可配置预算档位（低、中、高）的扩展思考，可接受文本、图像、视频与文档输入，上下文窗口为 100 万 token。Nova 2 Lite 在指令遵循、函数调用与代码生成方面表现良好，因此很适合像本文中文本转 SQL agent 这样的 agentic 工作负载。

## agent 评估的结构

评估是对 AI 系统的一种测试：给 AI 一个输入，对其输出应用评分逻辑，并度量成功与否。对于大语言模型（LLM）调用，这很直接。对于 agent，每个组成部分都变得更复杂。

### 关键术语

在深入模式之前，先说明本文通篇使用的术语：

- **任务（task）**：一项带有既定输入与成功标准的单一测试。例如「有多少客户来自加拿大？」，期望答案是八。
- **试验（trial）**：对任务的一次尝试。由于模型输出是非确定性的，每个任务运行多次试验可以得到更可靠的结果。
- **评分器（grader）**：对 agent 表现的某个方面打分的逻辑。一个任务可以有多个评分器，各自评估不同的维度。
- **记录（transcript）**：一次试验的完整记录，包括工具调用、推理步骤、中间结果与交互。在 LangSmith 中，这就是你可以检查以进行调试的完整 trace。
- **结果状态（outcome）**：试验结束时环境的最终状态。agent 可能*说*「答案是八」，但结果状态指的是它是否真的对数据库执行了正确的 SQL 查询。
- **评估执行框架（evaluation harness）**：端到端运行评估的基础设施。它提供指令与工具、并发运行任务、记录步骤、对输出打分并汇总结果。
- **评估套件（evaluation suite）**：为度量特定能力或行为而设计的一组任务。

### 为什么 agent 评估更难

有三种特性使 agent 评估与评估简单的 LLM 输出存在本质区别：

- **非确定性——**agent 行为在多次运行之间会有变化。同一个任务可能 90% 成功、10% 失败。单次通过/失败的结果说明不了太多。你需要多次试验来估计真实表现。有两个指标有帮助：*pass@k* 度量在 k 次尝试中至少有一次成功的可能性，而 *pass^k* 度量全部 k 次试验都成功的概率。当一次成功就足够时使用 pass@k；当一致性很重要时使用 pass^k。
- **错误传播——**在多步骤 agent 中，第 3 步的错误会级联影响后续步骤。一个早期误判 schema 的文本转 SQL agent 会构造出错误的 JOIN，从而在最终答案中产出错误结果。只评估最终输出，就会错过问题出在哪里。
- **创造性解法——**前沿模型有时会找到评估设计者没有预料到的有效做法。

### 你可以评估什么

对于一次 agent 运行，你可以测试三类内容：

- **轨迹（trajectory）——**调用的工具序列以及 agent 生成的具体参数。它是否探查了 schema？它在执行前是否使用了 sql_db_query_checker？
- **最终响应（final response）——**返回给用户的最终输出。答案是否正确？格式是否良好？
- **其他状态：**agent 产出的其他产物，例如写入的文件、创建的 TODO 计划以及保存的中间结果。

## AI agent 的评估模式

agent 评估通常组合三类评分器，而有效评估设计的关键是为你的用例选择正确的组合。

### 基于代码的评分器

基于代码的评分器使用确定性逻辑来验证特定条件：字符串匹配、正则表达式模式、二元通过/失败测试、静态分析、工具调用验证以及记录分析（轮次数、token 使用量）。

**优势——**快速、便宜、客观、可复现，且易于调试。当你能把成功标准表达为代码时，就这么做。

**劣势——**对于与预期模式不完全匹配的变体，验证会很脆弱。查询结果格式化为「eight customers」与「There are eight」相比，即使两者都正确，也可能无法通过严格的字符串匹配。

**示例**：验证某个工具被调用：

```
# Assert the agent executed a SQL query
tool_names = [tc["name"] for tc in tool_calls]
assert "sql_db_query" in tool_names, "Agent must execute sql_db_query"
```

### 基于模型的评分器（LLM-as-judge）

基于模型的评分器使用另一个 LLM 来评估 agent 的输出。方法包括基于评分细则（rubric）的打分、自然语言断言、两两比较以及多评分器共识。

**优势——**灵活、可扩展、能捕捉细微差别，可处理开放式任务，以及答案可能有多种有效形式的自由格式输出。

**劣势——**非确定性、比代码更贵，并且需要与人工评分器校准以验证准确性。给评审 LLM 一条退路（例如「如果信息不足，请返回 Unknown」），以避免幻觉出的分数。

**示例**：为一个复杂的分析型答案打分：

```
rubric = """Score the agent's answer on these dimensions (0.0 to 1.0):
1. correctness: Does it identify the right top employee? (Jane Peacock)
2. completeness: Does it include revenue broken down by country?
3. clarity: Is the answer well-formatted and easy to understand?
Return JSON: {"correctness": float, "completeness": float, "clarity": float}"""
 
judge_response = model.invoke(rubric.format(answer=answer))
scores = json.loads(judge_response.content)
```

LangSmith 的 Align Evaluator 功能会引导你通过一系列步骤，用人类专家反馈来校准你的 LLM-as-a-judge 评估器。你可以用此功能调优在数据集上运行的评估器，用于[离线评估](https://docs.langchain.com/langsmith/evaluation-concepts#offline-evaluation)或[在线评估](https://docs.langchain.com/langsmith/evaluation-concepts#online-evaluation)。

### 人工评分器

*人工评分器*（领域专家评审、众包判断、抽样抽查）通常被视为主观质量评估的黄金标准。与程序化评估方案相比，人工评分器昂贵且缓慢，但对校准基于模型的评分器必不可少。请审慎使用：初期用专家人工判断来校准 LLM-as-judge 的评分细则，之后定期用人工评审验证自动评分器没有漂移。

### 组合评分器：实用建议

尽可能使用确定性评分器，在需要捕捉细微差别时使用 LLM 评分器，并用人工评分器做校准。对于文本转 SQL agent，这可能看起来像：

- **基于代码——**agent 是否调用了 sql_db_query？答案中是否包含「eight」？是否执行了 DML 语句（INSERT、DELETE）？
- **LLM-as-judge——**用于输出格式各异的复杂查询。分析是否正确、完整且结构良好？
- **人工——**定期抽查，以验证 LLM 评分与专家判断一致。

### 能力评估与回归评估

并非所有评估都服务于同一目的：

- **能力评估（capability evaluation）**追问「这个 agent 擅长做什么？」它们应针对 agent 当前吃力的任务，给团队一个可以攀登的目标。从较低的通过率开始，逐步提升。
- **回归评估（regression evaluation）**追问「agent 是否仍能处理它以前处理的事？」它们的通过率应接近 100%。一旦下降，就说明某处坏了。

随着 agent 成熟，达到高通过率的能力评估可以*毕业*进入你的回归套件。曾经度量「它到底能不能做这件事？」的任务，转而度量「它是否仍能可靠地做这件事？」

## 评估深度 agent

*深度 agent*（使用规划、工具使用、文件系统后端与渐进式上下文加载来处理复杂多步骤任务的系统）打破了传统假设——即每个测试用例都能通过相同的应用逻辑运行、并由相同的评估器打分。过去几个月里，[LangChain 在深度 agent 架构之上发布了四个应用](https://blog.langchain.com/evaluating-deep-agents-our-learnings/)，并总结出四种可广泛适用的模式。

### 模式 1：为每个数据点定制测试逻辑

传统 LLM 评估对每个数据点一视同仁：通过同一个应用运行，用同一个评估器打分。深度 agent 打破了这一假设。每个测试用例都可能拥有自己的成功标准，而这些标准可能涉及针对 agent 轨迹与状态的具体断言，而不只是最终消息。

以文本转 SQL agent 为例。「有多少客户来自加拿大？」只有一个正确答案（八），你可以用字符串匹配来检查。但「哪位员工带来的收入最多，来自哪些国家？」需要 LLM 评审来评估正确性、完整性与清晰度，因为有效答案的格式差异很大。

LangSmith 的 [Pytest 集成](https://docs.smith.langchain.com/)支持这种模式。你可以针对每个测试用例，对 agent 的轨迹、最终消息与状态做出不同的断言：

```
@pytest.mark.langsmith
def test_canada_customer_count(sql_agent):
    """Custom logic: this test checks for a specific number."""
    result = sql_agent.invoke({
        "messages": [{"role": "user", "content": "How many customers are from Canada?"}]
    })
    answer = result["messages"][-1].content
    assert "8" in answer  # Simple code-based grader for this specific datapoint
 
@pytest.mark.langsmith
def test_revenue_by_employee(sql_agent, model):
    """Custom logic: this test needs an LLM judge — the answer format varies."""
    result = sql_agent.invoke({
        "messages": [{"role": "user", "content": "Which employee generated the most revenue?"}]
    })
    scores = llm_judge(model, result["messages"][-1].content)
    assert scores["correctness"] >= 0.5
```

### 模式 2：单步评估

LangChain 针对深度 agent 的测试用例中约有一半是单步评估：在特定输入之后，agent 立即决定做什么？这特别适用于验证单个决策点。它是否用正确的参数调用了正确的工具？

回归往往发生在单个决策点，而不是整个执行序列上。对于文本转 SQL agent，单步评估可以验证 agent 的第一个动作是探查数据库 schema（调用 `sql_db_list_tables` 或 `sql_db_schema`），而不是直接跳到编写查询。

```
@pytest.mark.langsmith
def test_agent_calls_sql_tools_first(sql_agent):
    """Single-step eval: Verify the agent uses SQL tools, not guessing."""
    result = sql_agent.invoke({
        "messages": [{"role": "user", "content": "How many customers are from Canada?"}]
    })
 
    tool_calls = extract_tool_calls(result["messages"])
    tool_names = [tc["name"] for tc in tool_calls]
 
    sql_tools = {"sql_db_list_tables", "sql_db_schema", "sql_db_query", "sql_db_query_checker"}
    assert sql_tools & set(tool_names), "Agent must use SQL tools"
```

单步评估就是你的单元测试。快速、聚焦，且 token 使用高效。

### 模式 3：完整的 agent 轮次

单步评估检验单个决策，而完整的 agent 轮次能让你看到全貌。在单个输入上端到端运行 agent 并进行评估：

```
@pytest.mark.langsmith
def test_full_turn_simple_query(sql_agent):
    """Full turn eval: Run end-to-end, check trajectory and answer."""
    result = sql_agent.invoke({
        "messages": [{"role": "user", "content": "How many customers are from Canada?"}]
    })
 
    # Check trajectory
    tool_names = extract_tool_names(result["messages"])
    assert "sql_db_query" in tool_names, "Agent must execute a query"
 
    # Check final answer (code-based grader — Canada has 8 customers in Chinook)
    answer = result["messages"][-1].content
    assert "8" in answer, "Answer must contain the correct count"
```

**关键洞见：**这个测试断言轨迹中出现了某些工具，但并不断言确切的顺序。agent 可能先列出数据表再获取 schema，也可能直接获取 schema。两者都有效。评估*agent 产出了什么*，而不是它走的确切*路径*。

LangSmith 会为完整的 agent 轮次展示完整 trace。你可以看到规划步骤（write_todos）、每次 SQL 工具调用、实际执行的查询，以及最终格式化的答案。

### 模式 4：多轮评估

有些场景需要跨多轮对话测试 agent。用户先问「最畅销的前 5 位艺人是谁？」，接着追问「对于排名第一的艺人，他们有多少张专辑？」挑战在于：如果你硬编码一串输入，而 agent 偏离了预期路径，后续输入可能就不合理了。解决方案是在测试中加入条件逻辑：

```
@pytest.mark.langsmith
def test_multi_turn_followup(sql_agent):
    """Multi-turn: Initial query, then a follow-up that builds on it."""
    # Turn 1
    result1 = sql_agent.invoke({
        "messages": [{"role": "user", "content": "What are the top 5 best-selling artists?"}]
    })
    answer1 = result1["messages"][-1].content
 
    # Conditional: if turn 1 failed, fail early
    if not answer1 or len(answer1) < 20:
        t.log_feedback(key="turn1_success", score=0.0)
        pytest.fail("Turn 1 produced no meaningful answer — skipping turn 2")
 
    # Turn 2: follow-up with conversation history
    result2 = sql_agent.invoke({
        "messages": [
            {"role": "user", "content": "What are the top 5 best-selling artists?"},
            {"role": "assistant", "content": answer1},
            {"role": "user", "content": "For the top artist, how many albums do they have?"},
        ]
    })
    answer2 = result2["messages"][-1].content
    assert answer2 and len(answer2) > 20, "Follow-up must produce a meaningful answer"
```

如果你想单独测试第 2 轮，可以从该点开始搭建一个测试，并把预期的第 1 轮输出作为初始状态。

## 端到端示例：在 AWS 上评估文本转 SQL 深度 agent

现在把这些模式付诸实践。本示例使用 LangChain 的[文本转 SQL 深度 agent](https://github.com/langchain-ai/deepagents/tree/master/examples/text-to-sql-agent)示例，将其配置为在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上运行，并使用 [LangSmith](https://smith.langchain.com/) 构建评估。

### 架构概览

### 构建评估套件

现在应用所有评估模式。以下示例使用 LangSmith 的 Pytest 集成，它会自动把每个测试用例记录为一次带完整 trace 的实验。

### 评估 1：单步——agent 是否使用了 SQL 工具？

```
@pytest.mark.langsmith
def test_simple_query_calls_correct_tool(sql_agent):
    """Single-step eval: Agent should use SQL tools, not guess."""
    question = "How many customers are from Canada?"
    t.log_inputs({"question": question})
 
    result = sql_agent.invoke({
        "messages": [{"role": "user", "content": question}]
    })
 
    tool_names = [tc["name"] for tc in extract_tool_calls(result["messages"])]
 
    sql_tools = {"sql_db_list_tables", "sql_db_schema", "sql_db_query"}
    assert sql_tools & set(tool_names), f"Agent must use SQL tools; got: {tool_names}"
    t.log_feedback(key="used_sql_tools", score=1.0)
```

### 评估 2：带确定性评分的完整轮次

```
@pytest.mark.langsmith
def test_full_turn_simple_query(sql_agent):
    """Full turn: End-to-end, check trajectory and correct answer."""
    question = "How many customers are from Canada?"
    t.log_inputs({"question": question})
 
    result = sql_agent.invoke({
        "messages": [{"role": "user", "content": question}]
    })
 
    answer = result["messages"][-1].content
 
    # Trajectory check
    assert "sql_db_query" in extract_tool_names(result["messages"])
    t.log_feedback(key="executed_query", score=1.0)
 
    # Deterministic answer check (Chinook has 8 Canadian customers)
    assert "8" in answer, "Answer must contain the correct count"
    t.log_feedback(key="correct_answer", score=1.0)
```

### 评估 3：使用 LLM-as-judge 的复杂查询

```
@pytest.mark.langsmith
def test_complex_query_llm_judge(sql_agent, model):
    """LLM-as-judge: Grade a complex analytical answer for quality."""
    question = "Which employee generated the most revenue and from which countries?"
    t.log_inputs({"question": question})
 
    result = sql_agent.invoke({
        "messages": [{"role": "user", "content": question}]
    })
    answer = result["messages"][-1].content
 
    rubric = """Score each dimension 0.0 to 1.0. Return ONLY valid JSON.
    1. correctness: Does it identify Jane Peacock as the top employee?
    2. completeness: Does it include revenue broken down by country?
    3. clarity: Is the answer well-formatted and easy to understand?
    Answer: {answer}
    Return: {{"correctness": float, "completeness": float, "clarity": float}}"""
 
    scores = json.loads(model.invoke(rubric.format(answer=answer)).content)
    for key, value in scores.items():
        t.log_feedback(key=key, score=float(value))
 
    assert scores["correctness"] >= 0.5, "Must identify the correct top employee"
```

### 评估 4：多轮追问

```
@pytest.mark.langsmith
def test_multi_turn_followup(sql_agent):
    """Multi-turn: Initial question, then a follow-up that builds on it."""
    result1 = sql_agent.invoke({
        "messages": [{"role": "user", "content": "What are the top 5 best-selling artists?"}]
    })
    answer1 = result1["messages"][-1].content
 
    if not answer1 or len(answer1) < 20:
        pytest.fail("Turn 1 failed — skipping turn 2")
 
    t.log_feedback(key="turn1_success", score=1.0)
 
    result2 = sql_agent.invoke({
        "messages": [
            {"role": "user", "content": "What are the top 5 best-selling artists?"},
            {"role": "assistant", "content": answer1},
            {"role": "user", "content": "For the top artist, how many albums do they have?"},
        ]
    })
    assert result2["messages"][-1].content, "Follow-up must produce an answer"
    t.log_feedback(key="turn2_success", score=1.0)
```

### 评估 5：安全与状态检查

```
@pytest.mark.langsmith
def test_safe_sql_and_planning(sql_agent):
    """State check: Complex query uses planning; SQL must be safe (no DML)."""
    result = sql_agent.invoke({
        "messages": [{"role": "user", "content":
                      "What is the total revenue per genre, and which has the most tracks?"}]
    })
 
    # Extract executed SQL queries
    sql_queries = [tc["args"]["query"] for tc in extract_tool_calls(result["messages"])
                   if tc["name"] == "sql_db_query"]
 
    # Safety: no DML statements
    dangerous = ["INSERT", "UPDATE", "DELETE", "DROP", "ALTER", "TRUNCATE"]
    for query in sql_queries:
        for kw in dangerous:
            assert kw not in query.upper().split(), f"SAFETY VIOLATION: {kw} in {query}"
    t.log_feedback(key="sql_safety", score=1.0)
 
    # Substantive answer
    assert len(result["messages"][-1].content) > 50
    t.log_feedback(key="substantive_answer", score=1.0)
```

## 从离线到在线：使用 LangSmith 在线评估器进行生产监控

到目前为止构建的所有内容（五个基于 pytest 的评估）都在部署之前离线运行。你精选测试用例、让 agent 针对它们运行，并检查分数。这对开发与回归测试必不可少。下一步是在生产环境中监控 agent。在生产环境中，你没有参考输出。真实用户会提出你从未预料的问题，数据库可能发生变化，也会出现任何精选数据集都无法覆盖的边界情况。这正是在线评估器的用武之地。LangSmith 支持两种评估模式，它们在 agent 生命周期中协同工作：

|  | **离线评估** | **在线评估** |
| --- | --- | --- |
| **运行位置** | 带参考输出的精选数据集 | 生产环境的实时 trace |
| **时机** | 部署前（开发、持续集成与交付（CI/CD）） | 部署后（生产环境） |
| **目的** | 基准测试、回归测试、单元测试 | 实时监控、异常检测 |
| **数据** | 输入 + 输出 + 参考答案 | 仅输入 + 输出（无参考） |
| **设置** | SDK（pytest）或 LangSmith UI | LangSmith UI → Tracing Project → Evaluators 标签页 |

在线评估器在生产 trace 上自动运行，无需部署代码。你在 LangSmith UI 中配置它们，它们会实时为每条 trace（或抽样）打分。在线评估器有三种类型。

### 在线评估器 1：代码评估器，SQL 安全检查

代码评估器是在 LangSmith 中内联运行的确定性 Python 或 JavaScript 函数。它们非常适合必须检查每条生产 trace 的安全护栏。对于文本转 SQL agent，最关键的在线检查是 SQL 安全。验证 agent 在生产环境中不会执行 DML 语句（INSERT、UPDATE、DELETE、DROP）：

```
# Code evaluator function — paste into LangSmith UI
def sql_safety_check(run) -> dict:
    """Check that no DML statements were executed in this trace."""
    dangerous_keywords = {"INSERT", "UPDATE", "DELETE", "DROP", "ALTER", "TRUNCATE"}
 
    if not hasattr(run, "child_runs") or not run.child_runs:
        return {"sql_safety": 1}
 
    for child in run.child_runs:
        if child.name == "sql_db_query" and child.inputs:
            query = child.inputs.get("query", "")
            tokens = query.upper().split()
            for keyword in dangerous_keywords:
                if keyword in tokens:
                    return {"sql_safety": 0}  # VIOLATION
 
    return {"sql_safety": 1}
```

### 在线评估器 2：LLM-as-judge，答案质量

LLM-as-judge 在线评估器使用 LLM 按评分细则为每条生产 trace 打分。由于生产环境中没有参考输出，这是一种无参考评估。评审者评估答案的内部一致性、清晰度与表面完整性。在 LangSmith UI 中配置：

- **名称：**answer-quality
- **采样率：**0.5（评估 50% 的 trace 以控制成本）
- **模型：**选择一个成本高效的模型（例如 Amazon Bedrock 上的 Amazon Nova 2 Lite）
- **Prompt：**

> 你正在评估一个 text-to-SQL agent，它回答关于数据库的自然语言问题。你会得到用户的问题和 agent 的最终答案。你无法访问实际数据库。请基于答案的内部一致性、清晰度和表面完整性进行评估。
>
> 用户问题：{{question}}
>
> agent 的答案：{{answer}}
>
> 为每个维度打 0.0 到 1.0 的分：
>
> 1. correctness_confidence：你对答案在事实上正确的信心有多高？留意具体数字、数据点，以及答案是否直接回应了问题。
>
> 2. clarity：答案格式是否良好、易于阅读？
>
> 3. completeness：答案是否完整覆盖了用户问题的所有部分？

- **变量映射：**把 {{question}} 映射到 run.inputs，把 {{answer}} 映射到 run.outputs
- **反馈配置：**三个连续分数（0.0–1.0）：correctness_confidence、clarity、completeness

### 在线评估器 3：复合型，整体质量分数

复合评估器把多个评估器的分数合并为单个指标。这对看板与告警很有用。在 LangSmith UI 中配置：

- **名称：**overall-quality
- **聚合方式：**加权平均
- **组成部分与权重：**sql_safety：权重 0.4（安全是最高优先级）correctness_confidence：权重 0.3 clarity：权重 0.15 completeness：权重 0.15

复合分数会在每个拥有全部组成分数的运行上作为反馈出现。然后你可以：

- **筛选 trace**：overall_quality < 0.7 的运行，以找出有问题的运行
- **创建看板图表**，跟踪质量随时间的变化趋势
- **设置告警**，在质量跌破阈值时触发

## 结论

AI agent 需要一套根本不同的评估策略。[LangChain](https://docs.smith.langchain.com/evaluation) 提供的五种模式（自定义测试逻辑、单步评估、完整 agent 轮次、多轮对话与环境设置）为你提供了这一框架。

文本转 SQL 深度 agent 示例表明，这些模式在 agent 的整个生命周期中都有效。在开发期间，你通过 [LangSmith 的](https://docs.langchain.com/langsmith/pytest) Pytest 集成运行离线评估（基于代码的安全检查、基于模型的质量打分与人工评审）。在生产环境中，你运行[在线评估](https://docs.smith.langchain.com/evaluation/how_to_guides/online_evaluations)（基于代码的安全检查、基于 LLM 的质量打分及其组合），在无参考输出的情况下监控每条 trace。两者之间的闭环是改进 agent 行为的关键：生产中的失败变成测试用例，测试用例帮助预防未来的失败，指标取代猜测。

要开始实践，请浏览[配套仓库](https://github.com/aws-samples/sample-text2sql-deep-agent-evalulation)获取完整可运行的示例。如需进一步了解本文用到的服务，请访问 [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html) 了解托管的基础模型访问能力，访问 [Amazon Nova](https://docs.aws.amazon.com/nova/latest/userguide/what-is-nova.html) 了解 AWS 的模型系列，并访问 [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 了解如何为你的 agent 添加安全控制。
