# 利用 Accenture 的排序方法优化 Amazon Bedrock 上的 AI 经济效益

企业在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上扩展 AI 规模时，即便每 token 的单价持续下降，token 支出往往仍在上涨。在尚未部署成本分配标签的情况下，你的云账单只会把 AI 支出显示成单独一行费用，而不会按团队、工作负载、agent 或模型拆分开来。更便宜的 token 会扩大使用面，而 agentic 工作负载又成倍放大调用次数。随着成功的 AI 用例不断放量，消耗的增长完全可能快过单价的下降。真正的经济问题在于：所产生的业务价值，是否比产出这份智能所需的成本增长得更快。Linux 基金会已经发起 [Tokenomics Foundation](https://www.linuxfoundation.org/press/linux-foundation-launches-the-tokenomics-foundation-to-define-the-economics-and-roi-of-ai-value)，为 AI 成本经济学制定开放标准——这件事本身就说明，管理 AI 的经济性已经成为一门行业性课题。

本文会介绍优化 token 支出的六个杠杆，说明 Accenture 如何在生产环境中落地这些杠杆，以及在 Amazon Bedrock 上该如何应用它们。

Accenture 在四个客户项目中应用了这些杠杆，覆盖电信、保险、采矿，以及一次大型企业部署。如本文所述，Amazon Bedrock 原生就提供同样的杠杆。在做过测量的项目里，token 支出下降了约 40% 到 85%。结果取决于各客户自身的工作负载，可能存在差异。为保护客户机密，Accenture 未披露客户名称。

## 归因优先：在业务层面衡量成本

在优化任何东西之前，你需要先看清消耗发生在哪里、由谁负责，以及它产出了什么业务价值。团队、工作负载与 agent 级别的成本分配标签，是把消耗对应到责任主体、并最终对应到业务成果的前提。你可以通过 [Amazon Bedrock 应用推理配置文件](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-application-inference-profiles.html) 来应用这些标签：每个应用或工作负载一个 profile，按团队、成本中心和环境打标。在 [AWS Billing and Cost Management 控制台](https://aws.amazon.com/aws-cost-management/billing-and-cost-management-console-home/) 中把它们激活为成本分配标签之后，你就能用这些标签追踪哪些团队、应用和 agent 在推高支出，也能衡量你引入的每一项改动带来的影响。

底层的遥测数据由三项 AWS 服务提供。[AWS Cost and Usage Reports](https://aws.amazon.com/aws-cost-management/aws-cost-and-usage-reporting/)（CUR 2.0）通过 [AWS Data Exports](https://docs.aws.amazon.com/cur/latest/userguide/what-is-data-exports.html) 交付，负责财务归属：成本分配标签生效后，它把计费的推理成本按工作负载和团队拆开。[Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 负责采集调用次数、延迟这类运行信号。[Amazon Bedrock 模型调用日志](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html) 记录请求级的细节，包括每次调用用的是哪个模型，以及输入和输出的 token 数量。

只有遥测还不够。工程师能在看板上读到每次调用的成本，但产品负责人和项目管理者需要的是用业务语言表达的指标。Accenture 的每笔业务交易成本（Cost per Business Transaction，CpBT）框架正好补上这一层。CpBT 把为产出一个成功业务结果而发生的所有模型调用、重试、工具调用和 agent 交接，汇总成一个把各项成本都算进去的完整数字，从而暴露出产出结果的真实代价，包括原始 token 定价所掩盖的那些失败尝试。再对照每个工作流交付的业务价值来看，CpBT 能区分出账单增长究竟反映了规模化成功，还是反映了浪费。

## 六个优化杠杆

这六个杠杆的目标，并不是不惜代价把 token 压到最低。它真正的目标，是针对每一项业务结果，用恰当的数量和恰当的智能水平，在可接受的成本、质量和风险下把它交付出来。按改动复杂度和所需投入，这些杠杆被分成三个阶段。AWS 与 Accenture 建议按阶段顺序推进，同时每个阶段都可以独立应用到收益最大的那些工作负载上。

### 阶段一：仅改配置，不动基础设施

借助 [Amazon Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)，模型可以复用那些在多个请求之间反复出现的提示内容，例如系统指令、工具定义和参考文档，于是你不再需要为重复处理同样的内容支付全价。Amazon Bedrock 会保存此前已计算过的提示前缀的键值状态，并在后续请求中跳过重算。对于受支持的模型，这套机制可将缓存输入 token 的成本降低最多 90%（参见 [Amazon Bedrock Prompt Caching](https://aws.amazon.com/bedrock/prompt-caching/)）。

[Amazon Bedrock 批量推理](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference.html) 以批处理方式异步处理非紧急工作负载，对部分模型而言，成本比按需定价低 50%（参见 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)）。你把推理请求作为批处理作业提交，处理完成后结果会写入 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/)。批量推理适合夜间报表、文档处理流水线，以及不需要即时返回结果的评测任务。

这两个杠杆都只是在现有配置上增加设置。prompt caching 需要在提示中加入缓存检查点标记，批量推理则需要把符合条件的请求作为批处理作业提交，而不是调用按需 API。交互式、按需的流量用缓存，异步的工作用批量推理。两者都不需要新增基础设施，也不需要改动架构。

### 阶段二：架构调整

[Amazon Bedrock 智能提示路由](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.html) 在同一个模型家族内部把请求分发出去，把每项任务匹配到它的业务价值、复杂度和风险所要求的智能水平上，而不是把所有请求都默认交给最强的模型。智能提示路由可以在不牺牲准确率的前提下把成本降低最多 30%（[参见 Amazon Bedrock 智能提示路由](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.html)）。路由是否产生费用，请查阅 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)。在下面的客户项目中，Accenture 的模型分层与分级路由用的就是这个路由杠杆。

[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）优化针对的是 RAG 流程里的检索环节，目的是让进入模型的无关上下文 token 更少。分层分块、基于元数据的过滤和重排序这些做法，会把检索到的上下文收窄到最相关的片段，于是你付费的主要就是那些真正改善答案的内容。

Accenture 还有两种互补的做法，与上述 AWS 原生杠杆配合使用。上下文范围控制把每个 agent 收到的数据限制在与其所处流程步骤相关的文档切片上，而不是在每次交接时都传递完整的案例上下文。上下文压缩则在文档进入模型之前先做摘要或过滤。两者都能减少输入 token 的体量，在多 agent 链路中尤其明显。

### 阶段三：基础设施与训练投入

语义缓存会保存响应，当新请求与已经回答过的问题语义相近时直接复用，即使措辞并不相同。这样就能避免重复的模型调用，同时把成本和延迟一起降下来。在 AWS 上，可以在模型前面加一层向量存储来实现，例如 [Amazon ElastiCache](https://aws.amazon.com/elasticache/)。AWS 曾针对 63,796 条真实聊天机器人查询做过基准测试，相似度阈值取 0.90 时，缓存命中率为 74.5%，准确率为 92.3%，成本节省为 72.5%（[参见 ElastiCache 语义缓存基准测试](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/semantic-caching-benchmarks.html)）。在应用路由和语义缓存时，请让每条路由上都保留 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/)，并为语义缓存设置过期时间，免得用户拿到过时的答案。

[模型蒸馏](https://aws.amazon.com/bedrock/model-distillation/) 把知识从大的教师模型迁移到更小、更快的学生模型。与原始模型相比，Amazon Bedrock 中的蒸馏模型[速度最高提升 500%，成本最高降低 75%](https://aws.amazon.com/bedrock/model-distillation/)，在 RAG 这类用例上准确率损失不到 2%。蒸馏最适合稳定、高并发的工作负载，也就是交易量足以摊平训练投入的那些场景。

## 生产实践：四个客户项目

Accenture 在四个客户项目中应用了这些杠杆，每个项目针对的都是不同的成本模式。其中两个项目同时应用了多项改动，因此那些结果反映的是叠加起来的效果，而不是某个单一杠杆的作用。

第一个项目是一次大型企业部署，所有请求都流向前沿模型，既没有缓存，也没有模型分层或批处理。Accenture 同时做了三件事：按任务做模型分层，把每类任务交给能够胜任的最小模型；对重复出现的上下文启用 prompt caching；把夜间作业和非紧急作业改为批处理。三者合计把月度 token 成本削减了 85%，而且这笔节省没有按单项改动拆分。约 15% 的任务仍然需要顶级模型来处理困难的开放式推理，其余任务则跑在更轻量的模型上。你的这个比例会取决于自身工作负载的构成。

第二个项目是一家电信运营商，年度 token 支出为 1,200 万美元。其中大部分支出来自两处：agent 不加限制地扇出请求，以及无论任务复杂与否、每个请求都被送往前沿模型。Accenture 把分级路由、语义缓存和上下文压缩一起用上。输入 token 下降了 70%，年度 token 支出从 1,200 万美元降到 380 万美元，降幅 68%。Accenture 以该运营商变更前的性能基准验证了输出质量。

第三、第四个项目各自只加了一层缓存。一家保险公司使用模型层的前缀缓存，在多次调用之间复用提示中静态的部分。一家采矿运营商使用应用层的语义缓存，对重复查询在它们到达模型之前就返回已存储的响应。两个项目合计，在没有更换模型路由、也没有训练投入的情况下，token 支出下降了约 40%。

## 结果

结果从约 40% 到约 85% 不等，取决于各客户自己的起点。那次大型企业部署起步时没有任何优化，最终达到 85%。电信运营商在 1,200 万美元的年度 token 支出上达到了 68% 的降幅；保险公司与采矿运营商各用一个缓存杠杆，合计约 40%。结果取决于各客户自身的工作负载，可能存在差异。

这些节省并不是终点。它们带来的是扩展 AI 工作负载的容量，是向高价值用例再投资的空间，也是让每一美元 AI 消耗产生更高回报的可能。其中两个项目同时应用了多项改动。当你一次只上一个杠杆时，就能把每个结果归因到具体改动上。AWS 与 Accenture 建议在自己的工作负载上按这个顺序推进：先把消耗对应到责任人和业务结果，一次只上一个杠杆，衡量成本、质量和业务价值，然后在已经奏效的做法上继续叠加。

## 生产治理：四条运营准则

在生产环境中优化 AI 经济性，需要的是一套持续运转的治理循环，覆盖成本、质量、风险和业务价值，而不是一次性的技术改动。在应用任何一个杠杆之前，先为成本和质量建立量化基线，这样每一项改动的影响都能对照一个已知的起点来衡量。验证输出质量时，请使用从真实生产流量中抽取的留出评测集，而不是合成的基准集。每个工作负载一次只上一个杠杆，这样才能把结果归因到具体改动上，并在质量跌破可接受阈值时干净地回滚。如果你处在金融服务、保险、医疗这类受监管行业，请把质量测试结果和回滚流程一并写入标准变更管理记录。

无论你用的是哪几个杠杆、处在排序的哪个阶段，这四条准则都适用。[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 是一个可以用任意框架、任意模型大规模构建、连接和优化 agent 的环境。它包含 [AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html)，这是 Amazon Bedrock AgentCore 的一项能力，提供批量评测，在你逐步采用更高级的杠杆时支撑你的质量验证循环。

## 上手步骤

你可以从三步开始。第一，为 Amazon Bedrock 打开成本归因：在团队和工作负载级别应用成本分配标签，让支出从第一天起就可追溯。第二，在 AWS Billing and Cost Management 控制台中激活这些标签，然后用 CUR 2.0 和模型调用日志找出高消耗工作负载，并按支出、业务价值、质量要求、风险、体量和优化空间逐项评估。第三，把 Amazon Bedrock prompt caching 应用到该工作负载的交互式流量上，把 Amazon Bedrock 批量推理应用到它的异步作业上，这两项都只是配置改动，请在进入阶段二的架构调整之前先测量效果。

[AWS Well-Architected Agentic AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentic-ai-lens.html) 中包含[模型调用与 token 成本优化](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentcost02.html)（AGENTCOST02），它是 agentic 工作负载成本优化支柱下的一个重点领域。这个重点领域提供的结构化框架，可用于在整个组织内大规模落地这些杠杆。
