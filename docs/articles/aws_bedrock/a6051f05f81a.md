## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 利用 Accenture 的排序方法优化 Amazon Bedrock 上的 AI 经济性

随着企业在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上扩展人工智能，即使每个代币价格下降，代币支出也往往会增长。如果没有成本分配标签，您的云发票将 AI 支出显示为单个行项目，而不是按团队、工作负载、代理或模型显示。更便宜的代币扩大了采用范围，代理工作负载增加了调用次数。随着成功的人工智能用例规模的扩大，消费的增长速度可能快于单价的下降速度。经济问题是所产生的商业价值的增长是否快于产生商业价值所需的情报成本。 Linux 基金会推出了 [Tokenomics 基金会](https://www.linuxfoundation.org/press/linux-foundation-launches-the-tokenomics-foundation-to-define-the-economics-and-roi-of-ai-value) 来开发 AI 成本经济学的开放标准，这标志着管理 AI 经济学现已成为一门行业学科。

在这篇文章中，您将了解优化代币支出的六个杠杆、埃森哲如何在生产中应用它们，以及如何使用 Amazon Bedrock 来应用它们。

埃森哲将这些杠杆应用于电信、保险、采矿和大型企业部署的四个客户项目中。正如本文所述，Amazon Bedrock 上也提供了相同的杠杆。在衡量储蓄情况时，代币支出下降了约 40-85%。结果因每个客户的工作负载而异，可能会有所不同。埃森哲保留客户姓名以保护客户机密。

## 归因优先：在业务层面衡量成本

在优化任何内容之前，您需要了解消费发生在哪里、谁拥有它以及它产生什么商业价值。团队、工作负载和代理级别的成本分配标签是将消费与负责任的所有者联系起来并最终与业务成果联系起来的先决条件。您可以通过 [Amazon Bedrock 应用程序推理配置文件](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-application-inference-profiles.html) 应用它们，每个应用程序或工作负载一个配置文件，按团队、成本中心和环境标记。在 [AWS 账单和成本管理控制台](https://aws.amazon.com/aws-cost-management/billing-and-cost-management-console-home/) 中将它们激活为成本分配标签后，您可以使用这些标签来跟踪哪些团队、应用程序和代理在推动支出。它们还可以衡量您引入的每个更改的影响。

三个 AWS 服务提供底层遥测。 [AWS 成本和使用情况报告](https://aws.amazon.com/aws-cost-management/aws-cost-and-usage-reporting/) (CUR 2.0) 通过 [AWS Data Exports](https://docs.aws.amazon.com/cur/latest/userguide/what-is-data-exports.html) 交付，用于处理财务归属，在成本分配标签处于活动状态后按工作负载和团队细分计费推理成本。 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 捕获调用计数和延迟等操作信号。 [Amazon Bedrock 模型调用日志记录](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html) 记录请求级别的详细信息，包括使用的模型以及每次调用的输入和输出令牌计数。

仅遥测是不够的。工程师可以在仪表板上读取每次调用的成本，但产品所有者和项目负责人需要以业务术语表示的指标。埃森哲的每笔业务交易成本 (CpBT) 框架弥补了这一差距。 CpBT 将有助于成功实现业务输出的所有模型调用、重试、工具调用和代理切换聚合为一个满载成本数据。它揭示了产生结果的真实成本，包括原始代币定价隐藏的失败尝试。 CpBT 根据每个工作流程提供的业务价值进行跟踪，区分反映扩展成功的不断增长的账单和反映浪费的账单。

## 六个优化杠杆

这六个杠杆的目标并不是不惜一切代价最小化代币。它是使用适当数量和水平的情报以适当的成本、质量和风险交付每项业务成果。根据变革的复杂性及其所需的投资，杠杆分为三个阶段。 AWS 和 Accenture 建议按顺序完成各个阶段，并且您可以将每个阶段独立应用于影响最大的工作负载。

### 第 1 阶段：仅配置，不更改基础架构

通过 [Amazon Bedrock 提示缓存](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)，该模型可以重复使用跨请求重复的提示部分，例如系统指令、工具定义和参考文档，因此您无需支付全价即可再次处理相同的内容。 Amazon Bedrock 存储先前计算的提示前缀的键值状态，并旨在跳过后续请求的重新计算。这样做的目的是为了将受支持模型的缓存输入令牌成本降低高达 90%（请参阅 [Amazon Bedrock 提示缓存](https://aws.amazon.com/bedrock/prompt-caching/)）。

[Amazon Bedrock 批量推理](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference.html) 将非紧急工作负载作为一个组进行异步处理，其成本比特定模型的按需定价低 50%（请参阅 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)）。您以批处理作业形式提交推理请求，处理完成后结果将写入 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/)。批量推理适合夜间报告、文档处理管道和不需要立即响应的评估运行。

两个杠杆都可以为您现有的设置添加配置。提示缓存需要在提示中缓存检查点标记，批量推理需要将符合条件的请求作为批处理作业提交，而不是调用按需 API。将缓存应用于交互式按需流量，将批量推理应用于异步工作。两者都不需要新的基础设施或架构变化。

### 第 2 阶段：架构变更

[Amazon Bedrock 智能提示路由](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.html) 跨同一系列内的模型定向请求，将每个任务与其业务价值、复杂性和风险所需的智能级别相匹配，而不是将每个请求默认为最强大的模型。智能提示路由可在不影响准确性的情况下将成本降低高达 30%（[请参阅 Amazon Bedrock 智能提示路由](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.html)）。检查 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/) 了解任何路由费用。在以下活动中，埃森哲的模型分层和分类路由应用了相同的路由杠杆。

[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/) (RAG) 优化调整 RAG 过程中的检索步骤，以便更少不必要的上下文标记到达模型。分层分块、基于元数据的过滤和重新排名等技术将检索到的上下文缩小到最相关的块，因此您主要为改进答案的内容付费。

两种互补的 Accenture 模式与这些 AWS 原生杠杆一起工作。上下文范围将每个代理接收的数据限制为与其工作流程步骤相关的文档切片，而不是在每次切换时传递完整的案例上下文。上下文压缩在文档到达模型之前对其进行总结或过滤。两者都减少了输入代币量，尤其是跨多代理链。

### 第三阶段：基础设施和培训投资

当新请求在语义上与已答复的请求相似时，语义缓存会存储响应并重用它们，即使措辞不同。这避免了冗余模型调用并降低了成本和延迟。在 AWS 上，您可以在模型前面使用矢量存储（例如 [Amazon ElastiCache](https://aws.amazon.com/elasticache/)）来实现它。在针对 63,796 个真实聊天机器人查询的 AWS 基准测试中，0.90 的相似性阈值可产生 74.5% 的缓存命中率、92.3% 的准确率和 72.5% 的成本节省（[请参阅 ElastiCache 语义缓存基准测试](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/semantic-caching-benchmarks.html)）。当您应用路由和语义缓存时，请在每条路由上保留 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/)，并设置语义缓存过期时间，以便用户不会收到过时的答案。

[模型蒸馏](https://aws.amazon.com/bedrock/model-distillation/) 将知识从大型教师模型转移到更小、更快的学生模型。 Amazon Bedrock 中的蒸馏模型比原始模型[速度提高了 500%，成本降低了 75%](https://aws.amazon.com/bedrock/model-distillation/)，对于 RAG 等用例，精度损失不到 2%。蒸馏最适合稳定、大容量的工作负载，其中交易量证明培训投资是合理的。

## 生产中：四个客户参与

埃森哲在四个客户项目中应用了这些杠杆。每次参与都针对不同的成本模式。在其中两个项目中，埃森哲同时应用了多项变革，因此这些结果反映了综合效果，而不是任何单一杠杆的效果。

第一次合作是大型企业部署，其中每个请求都发送到前沿模型，没有缓存、模型分层或批处理。埃森哲一起应用了三项更改：模型分层，将每个任务与能够很好处理该任务的最小模型相匹配，提示重复上下文的缓存，以及对夜间和非紧急作业的批处理。他们共同将每月的代币成本降低了 85%，而且节省的费用并没有因为零钱而被削减。大约 15% 的任务仍然需要顶级模型来进行硬性、开放式推理，其余任务则在较轻的模型上运行。您的分配将取决于您的工作负载构成。

第二个项目是一家电信运营商，每年的代币支出为 1200 万美元。大部分支出来自代理无限制地散布请求，以及来自无论复杂程度如何都进入前沿模型的每个请求。埃森哲将分类路由、语义缓存和上下文压缩结合在一起应用。输入代币下降了 70%，年度代币支出从 1200 万美元下降到 380 万美元，减少了 68%。埃森哲根据操作员变更前的绩效基准验证了输出质量。

第三次和第四次约定均应用了单个缓存层。一家保险公司使用模型层前缀缓存，在调用中重复使用其提示的静态部分。挖掘操作员使用应用程序层语义缓存，在重复查询到达模型之前返回存储的响应。在这两次合作中，在没有模型路由更改或培训投资的情况下，代币支出总计下降了约 40%。

## 结果

结果范围从大约 40% 到大约 85%，反映了每个客户的起点。大型企业部署开始时没有进行任何优化，但达到了 85%。电信运营商的年度代币支出为 1200 万美元，占比达到 68%；保险公司和挖矿运营商各自使用一个缓存杠杆，占比达到约 40%。结果因每个客户的工作负载而异，可能会有所不同。

这些节省并不是最终目标。它们创造了扩展人工智能工作负载的能力，对更高价值的用例进行再投资，并提高每一美元人工智能消耗所产生的回报。其中两次约定同时应用了多项更改。当您一次应用一个杠杆时，您可以将每个结果归因于特定的更改。 AWS 和 Accenture 建议您为自己的工作负载采用此顺序：将消费与所有者和结果联系起来，一次应用一个杠杆，衡量成本、质量和业务价值，并在有效的基础上进行构建。

## 生产治理：四大经营原则

优化生产中的人工智能经济性需要一个涵盖成本、质量、风险和商业价值的持续治理周期，而不是一次性的技术变革。在应用任何杠杆之前，请建立成本和质量的定量基线，以便您可以根据已知的起点衡量每个变更的影响。当您验证输出质量时，请使用从实际生产流量中提取的保留评估集，而不是综合基准。每个工作负载一次应用一个杠杆，以便您可以将结果归因于特定更改，并在质量低于可接受的阈值时干净地回滚。如果您从事金融服务、保险或医疗保健等受监管行业，请将质量测试结果和回滚程序记录为标准变更管理记录的一部分。

无论您使用哪种杠杆或处于排序的哪个阶段，这四个原则都适用。[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 是一个您可以使用任何框架或模型大规模构建、连接和优化代理的环境。它包括 [AgentCore 评估](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html)，这是 Amazon Bedrock AgentCore 的一项功能，可提供批量评估，以在您逐步采用更高级的杠杆时支持您的质量验证周期。

## 开始使用

您可以从三个步骤开始。首先，通过在团队和工作负载级别应用成本分配标签来启用 Amazon Bedrock 的成本归因，以便从第一天起就可以跟踪您的支出。其次，在 AWS Billing and Cost Management 控制台中激活这些标签。然后使用 CUR 2.0 和模型调用日志记录来识别高消耗工作负载，并根据支出、业务价值、质量要求、风险、数量和优化潜力评估每一项工作负载。第三，将 Amazon Bedrock 提示缓存应用于该工作负载的交互式流量，并将 Amazon Bedrock 批量推理应用于其异步作业（仅作为配置更改），并在进入第 2 阶段的架构更改之前测量结果。

[AWS Well-Architected Agentic AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentic-ai-lens.html) 包括[模型调用和令牌成本优化](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentcost02.html) (AGENTCOST02)，这是代理工作负载成本优化支柱中的一个重点领域。此重点领域提供了一个结构化框架，您可以使用它在整个组织中大规模应用这些杠杆。
