# Airbnb 如何用每任务成本在 Amazon Bedrock 上运营编码 agent

Amazon Bedrock 通过统一 API 提供来自多个提供商的基础模型，模型基础设施由 AWS 管理。它与 AWS 的访问控制和监控体系集成，prompt、代码和模型响应都在 AWS 内部处理。

随着编码 agent 进入生产环境，模型与用量的变化会同时影响延迟、容量和成本。CloudWatch 中的 Amazon Bedrock 运行时指标能帮团队排查延迟上升、限流和 token 消耗变化。评估（evals）则在一组固定的代表性任务上考察 agent 的工作质量，补上这些运营指标看不到的部分。

本文将介绍 Airbnb 如何为编码 agent 评估模型，以及如何监控它们在 Amazon Bedrock 上的使用情况。我们会说明每任务成本如何指导模型选择，生产数据如何在使用情况变化时帮助我们重新审视这些选择，以及用于排查延迟、限流和支出的运行时信号。

在 Airbnb，每周有数千名工程师以及工程周边岗位的同事使用 AirChat——这是我们运行编码 agent 的内部工具。agent 把模型请求发给我们的大语言模型（LLM）网关，网关运行在 Amazon Bedrock 上。Bedrock 在 AWS 内处理 Airbnb 的代码、prompt 和模型响应。大约五周之内出了八款新模型。到 10 月中旬，工程师通过编码 agent 发出的请求中，约有三分之二流向了这些新模型。

每次发布都可能一次性改变输出 token、成本、延迟和容量，而发布时随附的基准图表并不能说明模型如何应对我们工程师的活儿。所以我们并行跑两套系统。上线之前，我们用自己的任务跑评估，测出每个模型的得分和每任务成本。每任务成本，是指 agent 完成一个任务所用全部 token 按目录价折算的成本。

上线之后，可观测性告诉我们生产端变了什么。当生产用量与评估结果对不上，我们会去查原因。

## 解决方案概览

CloudWatch 中 `AWS/Bedrock` 命名空间里的几个信号，足以诊断大多数生产问题：

- 延迟：`InvocationLatency`、`TimeToFirstToken`、`OutputTokenCount`，以及自行推导的每秒输出 token 数（OTPS）。
- 限流：`InvocationThrottles`，再加上每个请求针对你的配额预留的 token 数（这一项由你自己发布）。Bedrock 还会发布 `EstimatedTPMQuotaUsage`，它衡量你估算的每分钟 token（TPM）配额消耗，计入缓存写入 token 与输出消耗倍率，覆盖全部推理 API（`Converse`、`InvokeModel`、`ConverseStream` 和 `InvokeModelWithResponseStream`）。你可以用这个指标在触达配额上限之前设置主动告警，跟踪各模型的配额消耗，并在被限流之前申请更多配额。
- 成本：`InputTokenCount`（未缓存输入）、`CacheReadInputTokenCount`、`CacheWriteInputTokenCount` 和 `OutputTokenCount`，各按自身费率计价。缓存读取比未缓存输入便宜，缓存写入则可能更贵，取决于模型。缓存命中率下降会推高每请求成本。

在这些指标之上，我们再加入每任务成本。对我们允许的每一个模型、每一档推理强度（reasoning effort），评估都会给出一个得分和一个每任务成本。推理强度是一项设置，控制模型在回答前思考多少。我们据此选定每个默认值——即工程师未另行选择时编码工具使用的模型与强度——以及每个强度上限，也就是我们为某个模型允许的最高强度。

## 架构

工程师在自己的 AirDev 工作区上运行 AirChat，这些工作区是云端的个人开发机。他们也可以把任务交给 AirChat Remote，由它在独立的云工作区里运行云端 agent，工程师则腾出手去做别的事。两条路径都经由我们的 LLM 网关抵达 Amazon Bedrock。

图 1 展示了 AirChat 与 AirChat Remote 如何经由我们的网关抵达 Amazon Bedrock，也展示了评估与生产监控如何指导模型默认值和强度上限。

![AirChat 与 AirChat Remote 通过 Airbnb 的网关抵达 Amazon Bedrock，CloudWatch 指标与评估结果共同设定模型默认值和强度上限](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/18/ML-22452-1.png)

图 1：编码 agent 和云端 agent 通过我们的 LLM 网关调用 Amazon Bedrock。使用记录与 CloudWatch 指标反映真实使用情况，我们用评估结果设定默认值和强度上限

网关记录每个请求的模型、客户端、团队和用户。这些记录我们只做聚合使用，用于成本和容量规划。CloudWatch 提供 token 计数、延迟、错误和限流。我们把生产信号与评估得分、每任务成本对照，判断默认值或强度上限何时需要调整。

## 先决条件

在 AWS 一侧，你需要：

- 对你计划运行和评估的 Amazon Bedrock 模型有访问权限。各 AWS 区域的模型可用性，请见 Amazon Bedrock 用户指南中的[按模型划分的区域可用性](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。
- 通过 `ConverseStream` 或 `InvokeModelWithResponseStream` 发起流式调用。Bedrock 只为流式 API 发布 `TimeToFirstToken`。
- 在你调用的每个 AWS 区域开启模型调用日志记录。该功能默认关闭。日志可能保存完整的 prompt 与响应以及调用者身份，所以要限制谁能读取，并设置保留期限。

为调用者使用带标签的 IAM 角色，并启用成本分配标签。要在开始收集之前启用，因为启用不会回溯此前产生的成本。

你还需要自己准备三样东西：

- 一组来自你自己工程工作的任务。为每个任务给出起始仓库状态、工程师会写的那段 prompt，以及一个你信得过的评分器。评分器是给 agent 的工作打分的程序或模型。我们的任务取自真实代码变更、这些变更上的评审意见，以及原始工单里没有写明的决策。第 2 步会展示一个例子。
- 一台位于 Bedrock 之前的网关或转发组件，记录每个请求的模型、客户端、团队、用户和 token 计数。
- 一张你运行的每个模型的公开目录价表，每条都带日期，以便用同一基准为评估 token 和生产 token 定价。

上线之前，先界定 agent 能访问什么、哪些操作需要人工复核。在隔离的工作区里运行代码，合并前先测试生成的改动。[Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 可以帮助过滤 prompt 与响应中的有害内容和敏感信息。对于基于所给参考材料的响应，[上下文基础检查](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-contextual-grounding-check.html)可以标出缺乏依据的说法。在你自己的任务上测试这些控制措施，并把它们的延迟和成本计入你的测量。

## 演练

先测出一个完整任务要花多少钱，再用这些结果来选定模型默认值、检查生产行为、管理容量、归集支出。

### 第 1 步：完成一个任务要花你多少钱？

编码 agent 要发很多次请求才能完成一个任务，而每一次请求，模型都会把到此为止的 context 重新读一遍。所以我们为整个任务定价。

Bedrock 对每个请求报告四类 token：未缓存输入、缓存读取、缓存写入和输出。在一次评估运行中，我们为每个请求的这四类都定价，再把任务内所有请求加起来。本文中每一项成本都使用该次运行对应日期的公开目录价。我们把平均成本记在每个模型、每档推理强度、每个 agent 客户端的得分旁边，而平均值里包含得分较低的尝试。

推理强度会同时改变得分和成本。在我们测试的某个模型上，从低强度提到高强度，得分提高 0.8 分，每任务成本却高出 2.5 倍。我们用这些结果来设定强度上限，由网关强制执行。

### 第 2 步：你能多快评估一个新模型？

新模型发布那天下午，向我们的 agent 发一个请求就启动了一轮评估活动，让新模型跑遍我们全部任务套件。一个套件是同一类型任务的固定集合，我们共有七个。agent 把数百个任务分散到各个套件和多个云工作区，评分器一打分，结果就立刻出现。首批结果几小时内就到了。到第二天早上，每个套件都有了得分和每任务成本，整个组织做部署决策所需的信息就齐了。

这种速度靠的是已经写下来的任务。每个任务是一个文件夹，装着一次运行所需的一切。下面是我们机器学习工作中一个精简过的任务：

```
honest-holdout-bakeoff/
  instruction.md     what the agent is told
  task.toml          time limit, CPUs and memory
  environment/       Dockerfile for the sandbox
  tests/test.sh      runs the grader and writes the reward
  tests/grader.py    the checks
  solution/          a reference solution that must pass the grader

instruction.md (excerpt):
  We have two candidate models for a prediction task, and we need to
  know which one to ship.
  ...
  Then answer the question we actually have to decide: is either
  candidate worth rolling out over the system already in production?
```

评分器每次运行都会用冻结数据重算正确答案，只有每一项检查都通过，agent 才能拿到 1 的奖励。要测一个模型在每一档强度下的表现，就在作业配置里把每档强度列成独立的 agent：

```
job_name: model-a-effort-sweep
n_attempts: 1                # one attempt per task at each effort
datasets:
  - path: tasks/ml           # each task brings its own grader
agents:
  - name: model-a-low
    model_name: vendor/model-a
    kwargs: {reasoning_effort: low}
  - name: model-a-medium
    model_name: vendor/model-a
    kwargs: {reasoning_effort: medium}
  - name: model-a-high
    model_name: vendor/model-a
    kwargs: {reasoning_effort: high}
```

两个示例用的都是 [Harbor](https://github.com/harbor-framework/harbor) 的格式，这是一个在沙箱里运行 agent 评估的开源框架。如果你刚起步，它是一个可选方案。

跑评估这件事本身可以优化。最难的是写评分细则，也就是评分器遵循的那份打分指南。我们的长任务会运行好几轮，每轮之间由一位模拟评审者提出质疑。模型评分器按八个加权维度给每次运行打分，每个维度 0 到 3 分。

```
Correctness of delivery   25     Judgment                 10
Verification quality      15     Evidence and reporting   10
Autonomy                  15     Readability              10
Design and workload fit   10     Operational discipline    5

Ceiling: if the reviewer had to rescue the agent repeatedly
(autonomy 0 or 0.5), the total is capped at 25 of 100.
```

正因为有这类上限，需要人反复救场的 agent，没法光靠表面功夫拿高分。

### 第 3 步：上线之后要盯什么？

延迟上升时，先看三张图再决定要不要提支持工单：`TimeToFirstToken` 看生成开始前的等待，`OutputTokenCount` 看响应长度，OTPS 看生成速度。Bedrock 没有原生的 OTPS 指标，需要用指标数学推导，具体做法 Amazon [Bedrock 用户指南](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-runtime-otps.html)里有说明：

```
OTPS = OutputTokenCount / (InvocationLatency - TimeToFirstToken) * 1000
```

在我们那次会话的例子里，延迟上升了 40%，而首 token 时间和 OTPS 都没动。原因是有人改了系统 prompt，要求回答更详尽，每请求的输出 token 因此涨了 50%。模型的速度没变，只是写得更长了。要把 prompt 改动和模型升级当成一次部署，并在仪表板上标出来。

每周我们都会把 CloudWatch 运行时指标和网关的使用记录按模型并排放在一起看。做成本和容量规划时，我们还会看聚合用量：每请求成本，以及每周每用户的平均请求数。新模型可能把这两项都推动。每次上线之后，我们都拿它们和评估得出的每任务成本预期作对比。

### 第 4 步：评估看着不错，生产上又如何？

有一个模型，我们叫它模型 A，在评估里表现很好。在我们的编码任务上，它比此前最好的模型高出 3 分以上。每任务成本大致持平，而且所有模型用的是同一个评分器。我们把它推上线，把强度上限设在高，并请大多数工作在低或中等强度下完成。

上线几周后，我们按目录价给模型 A 的生产用量算了账，并做聚合查看。模型 A 上每用户的平均周支出，是上一个模型的数倍。模型 A 每个请求贵约三倍，而模型 A 的用户平均发出的请求数也约是三倍。

输出 token 只占一个请求成本的一成。大头花在缓存 context 上，模型每次请求都要把它重读一遍。模型 A 能独自长时间工作，于是人们开始用它开很长、很自主的会话。

评估衡量的是模型在一个任务上的表现。生产衡量的是人们选择怎样和它一起干活。

后来，一个更新的模型在同样的任务和评分器上得分超过模型 A，每任务成本约为它的六分之一。我们改了一次配置，就把模型 A 的用户迁了过去。

随后我们在同一批用户上做了聚合对比，也就是模型 A 的重度用户。换到新模型的第一个完整周，这群人发给主模型的请求数基本持平，而他们在这个模型上的支出降到了约七分之一。

### 第 5 步：为什么会被限流，流量又往哪里去

在 `bedrock-runtime` 端点上，请求一到达，Bedrock 就在模型写出任何内容之前核对你的每分钟 token 配额。它会预留你的未缓存输入 token 和缓存写入，再加上 `max_tokens`，也就是这个请求允许产出的最大量。随着模型生成，预留量会调整，请求结算时未用掉的部分会退回。缓存读取从不计入配额，所以一个请求可能在配额上很便宜，在账单上却很贵。输出 token 按消耗倍率结算，多数模型是 1:1，某些当前模型则是数倍，所以要查[你的模型费率](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-token-burndown.html)。

一块只统计计费 token 的仪表板，可能在请求正被限流时仍显示有余量。在我们那次会话的例子里，配额是每分钟 100 万 token，流量是每分钟 300 个请求。仪表板显示用掉约 30% 的配额。套用 5:1 的输出 token 消耗倍率之后，已完成的请求实际消耗约 77%。

准入走的是另一套算法。每个请求最初预留 600 个未缓存输入 token，加上 4,096 的 `max_tokens`，合计 4,696 个 token。而响应的 p99 约为 800 个 token。

把 `max_tokens` 降到 1,024，初始预留就降到 1,624 个 token，缩小约 65%。这个上限仍然高于 p99。输入和输出不变时，最终配额消耗也不变，但更小的预留留出了更多准入空间。要盯 `stopReason`，以便发现被截断的响应。使用退避加抖动，并给重试次数设上限。

需求也可能超出你在任何单一模型上的余量。你希望在有需要之前就知道活儿能去哪儿，我们的评估回答的正是这个问题。答案可以是另一个模型系列里的模型。对我们使用的每个主要模型，我们都至少保留一个在评估中表现相当、且可以负载均衡过去的等效模型。没有这些评估，判断工作往哪儿去就只能靠猜。

如果某个模型的余量一直很紧，我们可以改配置里的默认值来重新平衡。先确认等效模型有容量承接额外负载，你的配额也覆盖得住。同时要在它上面留够流量以保住访问权限：模型进入 Legacy 期之后，现有客户若 15 天不活动就可能失去访问。Legacy 模型在生命周期结束前一直可用，此后 Bedrock 会把它从每个区域移除，发往它的请求会失败，而 Bedrock 不会自动迁移你的流量。当 `LegacyModelInvocations` 升到零以上时就报警。

### 第 6 步：这笔支出算谁的？

Bedrock 运行时指标按 `ModelId` 划分维度，所以你能看出是哪个模型服务了请求，但看不出是哪个团队发的。Bedrock 发布这些指标时带 `ModelId` 维度，也发布不带该维度的版本；如果请求在 Bedrock 解析出模型之前就失败了，它只会出现在不带维度的序列里，因此按 `ModelId` 过滤会少算错误。Bedrock 提供三种归集支出的方式：

- 哪个团队或哪个用户？Bedrock 在每个请求上记录调用者的 IAM 身份。给你的角色打标签，或传递会话标签，就能在 AWS Cost Explorer 和 AWS 成本与使用报告（CUR 2.0）中按标签查看成本。
- 哪个应用？应用推理配置文件是与模型绑定的，所以为每个应用和模型的组合建一个带标签的配置文件，并调用对应配置文件的 ARN。
- 哪个功能或哪段 prompt？在 `Converse` 的 `requestMetadata` 里传键值对。Bedrock 会把它们写进模型调用日志，但不放进账单。要给它定价，就把日志里的 token 计数乘以公布费率。经典 CUR 和 CUR 2.0 都不带逐请求 ID，所以只能按模型、用量类型和时间段比对总计来对账。

放在网关后面时，Bedrock 看到的是网关的角色，所以要由网关为每个用户代入一个角色，并带上各自的 `RoleSessionName` 或会话标签。要把这些凭证按会话缓存起来，因为每个请求都代入角色可能超出 AWS Security Token Service（AWS STS）的速率配额。归因断了，请求照样成功，所以要为 Bedrock 未能投递调用日志设置告警。

我们的使用记录可以按模型、客户端、团队和用户归集用量，这些只用于成本和容量规划的聚合分析。每任务成本也是用同样的四类 token 计数算出来的，因此我们能在评估与生产之间比较 token 构成和成本。

## 结果

我们能在一夜之间从模型发布走到部署决策。某次上线之后，模型 A 上每用户的平均周支出是上一个模型的数倍。我们把它的大用量用户迁到了更新的模型。在第一个完整周里，这群人在主模型上的支出降到约七分之一，请求数基本不变。对我们使用的每个主要模型，评估都能找到一个可以重新平衡过去的等效模型。

## 清理

测试结束后，停掉你启动的评估作业和 agent 进程。如果你只是为这次演练启用了模型调用日志记录，请在每个区域用 [DeleteModelInvocationLoggingConfiguration](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_DeleteModelInvocationLoggingConfiguration.html) 关掉。

调用方不再使用之后，用 [DeleteInferenceProfile](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_DeleteInferenceProfile.html) 删除你创建的应用推理配置文件。删除只为这次演练创建的 IAM 角色、策略和资源标签。停用只用于这些测试的成本分配标签。删除不再需要的测试用 CloudWatch 日志组和 S3 日志对象。

## 结论

每次模型发布，我们都会跑四项检查：

- 发布当天：在自己的任务上把新模型的每一档强度都跑一遍，同时记下得分和每任务成本。
- 上线之前：根据这些数字选默认值、定强度上限。凡是比更低一档更贵、得分又更低的强度，一律禁用。
- 头几周：把每请求成本和每用户平均请求数，与评估得到的每任务成本作对比，两边都按同样的四类 token 计数定价。
- 在需要之前：弄清来自任何模型系列的哪些模型在你的评估里得分相同，并在重新平衡前核实它们的容量和你的配额。

我们选择 Amazon Bedrock，是为了通过一个 API 触达多个模型系列。它让我们能沿用现有的 AWS 访问控制和日志能力，模型基础设施则交给 AWS 管理。我们用评估为工作挑选模型，用可观测性判断这些选择何时需要重新看一眼。
