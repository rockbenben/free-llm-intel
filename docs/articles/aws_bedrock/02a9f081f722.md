# Airbnb 如何用每任务成本（cost per task）在 Amazon Bedrock 上运营编码代理

Amazon Bedrock 通过统一 API 提供来自多个提供商的基础模型，并由 AWS 管理模型基础设施。它与 AWS 的访问控制和监控集成，并在 AWS 内处理提示词、代码和模型响应。

随着编码代理进入生产环境，模型和使用情况的变化可能影响延迟、容量和成本。Amazon CloudWatch 中的 Amazon Bedrock 运行时指标可帮助团队调查延迟上升、限流和 token 消耗变化。评估（evals）则通过在一组固定的代表性任务上衡量代理工作质量，补充这些运营指标。

本文介绍 Airbnb 如何为编码代理评估模型，并监控它们在 Amazon Bedrock 上的使用情况。我们解释每任务成本如何指导模型选择，以及生产数据如何帮助我们在使用情况变化时重新审视这些选择。我们还会描述用于调查延迟、限流和支出的运行时信号。

在 Airbnb，每周有数千名工程师及工程相关人员使用 AirChat——我们用于运行编码代理的内部工具。代理通过我们的大语言模型（LLM）网关发送模型请求，该网关运行在 Amazon Bedrock 上。Bedrock 在 AWS 内处理 Airbnb 的代码、提示词和模型响应。大约五周内发布了八款新模型。到 10 月中旬，我们的工程师通过编码代理发送的请求中，约三分之二流向了这些新模型。

每次发布都可能同时改变输出 token、成本、延迟和容量，而发布时公布的基准图表并不能展示模型如何处理我们工程师的工作。因此我们并行运行两套系统。在推广之前，我们用自己的任务运行评估，衡量每个模型的得分和每任务成本。每任务成本是指代理完成一个任务所使用的所有 token 按目录价计算的成本。

推广之后，可观测性向我们展示生产环境中发生了什么变化。当生产使用情况与评估结果不一致时，我们会找出原因。

## 解决方案概览

你可以利用 CloudWatch 中 `AWS/Bedrock` 命名空间的几个信号诊断大多数生产问题：

- 延迟：`InvocationLatency`、`TimeToFirstToken`、`OutputTokenCount`，以及你自行推导的每秒输出 token 数（OTPS）。
- 限流：`InvocationThrottles`，加上每个请求针对你的配额预留的 token 数（由你自行发布）。Bedrock 还会发布 `EstimatedTPMQuotaUsage`，该指标衡量你估算的每分钟 token（TPM）配额消耗，包括缓存写入 token 和输出消耗倍率，覆盖所有推理 API（`Converse`、`InvokeModel`、`ConverseStream` 和 `InvokeModelWithResponseStream`）。你可以使用该指标在达到配额限制前设置主动告警，跟踪各模型的配额消耗，并在使用被限流前申请进一步提高配额。
- 成本：`InputTokenCount`（未缓存输入）、`CacheReadInputTokenCount`、`CacheWriteInputTokenCount` 和 `OutputTokenCount`，每种都按其各自费率计价。缓存读取的成本低于未缓存输入，而缓存写入可能因模型不同而成本更高。较低的缓存命中率会增加每请求成本。

在这些指标之上，我们还加入每任务成本。我们的评估会为我们允许的每个模型和每种推理强度衡量得分和每任务成本。推理强度（reasoning effort）是一种设置，用于控制模型在响应前进行多少推理。我们使用结果来选择每个默认设置——即除非工程师另选，否则我们的编码工具使用的模型和推理强度——以及每个推理强度上限，即我们为某个模型允许的最高推理强度。

## 架构

工程师在他们的 AirDev 工作区上运行 AirChat，这些工作区是云端的个人开发机器。他们也可以把任务交给 AirChat Remote，后者在独立的云工作区中运行云端代理，而工程师可以去做其他事情。两条路径都通过我们的 LLM 网关到达 Amazon Bedrock。

网关记录每个请求的模型、客户端、团队和用户。我们仅以聚合方式使用这些记录，用于成本和容量规划。CloudWatch 提供 token 计数、延迟、错误和限流。我们将这些生产信号与评估得分和每任务成本进行比较，以决定何时需要更改默认值或推理强度上限。

## 先决条件

在 AWS 侧，你需要：

- 有权访问你计划运行和评估的 Amazon Bedrock 中的模型。有关按 AWS 区域划分的模型可用性，请参阅 Amazon Bedrock 用户指南中的[按模型划分的区域可用性](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。
- 通过 `ConverseStream` 或 `InvokeModelWithResponseStream` 进行流式调用。Bedrock 仅为流式 API 发布 `TimeToFirstToken`。
- 在你调用的每个 AWS 区域启用模型调用日志记录。该功能默认关闭。日志可能包含完整提示词和响应以及调用者身份，因此请限制谁可以读取日志，并设置保留期限。

为你的调用者使用带标签的 IAM 角色，并激活成本分配标签。在开始收集之前激活它们，因为激活不会回溯此前成本。

你还需要自己准备三样东西：

- 一组来自你自己工程工作的任务。为每个任务提供起始仓库状态、工程师会编写的提示词，以及你信任的评分器。评分器是给代理工作打分的程序或模型。我们根据真实代码变更、这些变更上的评审评论，以及原始工单未明确说明的决策来构建任务。第 2 步展示了一个示例。
- 位于 Bedrock 前面的网关或代理，用于记录每个请求的模型、客户端、团队、用户和 token 计数。
- 一张你运行的每个模型的公开目录价格表，每条记录都带有日期，以便你能以相同基准为评估 token 和生产 token 定价。

在推广之前，定义代理可以访问什么，以及哪些操作需要人工审核。在隔离的工作区中运行代码，并在合并前测试生成的变更。[Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 可帮助过滤提示词和响应中的有害内容和敏感信息。对于基于所提供参考材料的响应，[上下文 grounding 检查](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-contextual-grounding-check.html)可以标记没有依据的说法。在你自己的任务上测试这些控制措施，并将其延迟和成本纳入你的衡量。

## 演练

首先衡量完成一个完整任务需要多少成本。然后使用这些结果来选择模型默认值、检查生产行为、管理容量并归因支出。

### 第 1 步：完成一个任务需要多少成本？

编码代理需要多次请求才能完成一个任务，而且在每次请求时，模型都会重新读取到目前为止的上下文。因此我们为整个任务定价。

Bedrock 会为每个请求报告四类 token：未缓存输入、缓存读取、缓存写入和输出。在一次评估运行中，我们为每个请求的这四类 token 定价，并把任务中的请求加起来。本文中的每项成本都使用该次运行对应日期的公开目录价格。我们在得分旁边记录每个模型、每种推理强度和每个代理客户端的平均成本，且平均值包含低分尝试。

推理强度会同时改变得分和成本。在我们测试的一个模型上，从低推理强度提高到高推理强度使得分提高了 0.8 分。每任务成本则高出 2.5 倍。我们使用这些结果来设置推理强度上限，由网关强制执行。

### 第 2 步：你能多快评估一个新模型？

在新模型发布当天下午，向我们的代理发送一个请求就启动了一次评估活动，使新模型跑遍我们所有任务套件。一个套件是一组固定类型的任务，我们共有七个套件。代理将数百个任务分散到各个套件和多个云工作区中，每个结果在评分器打分后立即出现。首批结果在数小时内到达。到第二天早上，每个套件都有了得分和每任务成本，我们便掌握了为整个组织做出部署决策所需的信息。

这种速度依赖于已经写下来的任务。每个任务都是一个文件夹，包含一次运行所需的一切。以下是我们机器学习工作中一个精简后的任务：

```
honest-holdout-bakeoff/
  instruction.md     what the agent is told
  task.toml          time limit, CPUs and memory
  environment/       Dockerfile for the sandbox
  tests/test.sh      runs the grader and writes the reward
  tests/grader.py    the checks
  solution/          a reference solution that must pass the grader

instruction.md (excerpt):
  We have two candidate models for a prediction task, and we need to
  know which one to ship.
  ...
  Then answer the question we actually have to decide: is either
  candidate worth rolling out over the system already in production?
```

评分器每次运行都会根据冻结数据重新计算正确答案，只有当所有检查都通过时，代理才能获得 1 的奖励。要测试一个模型在每种推理强度下的表现，可在作业配置中将每种推理强度列为单独的代理：

```
job_name: model-a-effort-sweep
n_attempts: 1                # one attempt per task at each effort
datasets:
  - path: tasks/ml           # each task brings its own grader
agents:
  - name: model-a-low
    model_name: vendor/model-a
    kwargs: {reasoning_effort: low}
  - name: model-a-medium
    model_name: vendor/model-a
    kwargs: {reasoning_effort: medium}
  - name: model-a-high
    model_name: vendor/model-a
    kwargs: {reasoning_effort: high}
```

两个示例都使用 [Harbor](https://github.com/harbor-framework/harbor) 的格式，这是一个用于在沙箱中运行代理评估的开源框架。如果你刚开始，它是一个选择。

运行评估可以优化。编写评分标准——评分器遵循的评分指南——是最困难的部分。我们的长任务会运行多轮，并在轮次之间由模拟评审者提出质疑。模型评分器会按八个加权维度为每次运行打分。每个维度的得分为 0 到 3。

```
Correctness of delivery   25     Judgment                 10
Verification quality      15     Evidence and reporting   10
Autonomy                  15     Readability              10
Design and workload fit   10     Operational discipline    5

Ceiling: if the reviewer had to rescue the agent repeatedly
(autonomy 0 or 0.5), the total is capped at 25 of 100.
```

由于存在这样的上限，一个需要被反复挽救的代理不能仅靠表面打磨获得高分。

### 第 3 步：推广后你要观察什么？

当延迟上升时，在提交支持案例之前先绘制三个信号：`TimeToFirstToken` 表示生成开始前的等待时间，`OutputTokenCount` 表示响应长度，OTPS 表示生成速度。Bedrock 没有原生 OTPS 指标。你可以按照 Amazon [Bedrock 用户指南](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-runtime-otps.html)所述，通过指标数学推导：

```
OTPS = OutputTokenCount / (InvocationLatency - TimeToFirstToken) * 1000
```

在我们会话的示例中，延迟上升了 40%，而首 token 时间和 OTPS 保持不变。有人修改了系统提示词，要求更详尽的回答，导致每请求输出 token 增加了 50%。模型以相同速度生成，但写出了更长的响应。把提示词更改和模型升级当作部署来对待，并在仪表板上标记它们。

每周，我们会把 CloudWatch 运行时指标与网关中每个模型的使用记录放在一起看。对于成本和容量规划，我们还会查看聚合使用情况：每请求成本，以及每周每用户的平均请求数。新模型可能同时改变这两者。每次推广后，我们会将它们与评估中每任务成本的预期进行比较。

### 第 4 步：评估看起来不错。生产显示了什么？

有一个模型，我们称它为模型 A，在我们的评估中表现良好。在我们的编码任务上，它比此前最佳模型高出 3 分以上。每任务成本大致相同，而且所有模型都由同一个评分器打分。我们推广了它，将推理强度上限设为高，并要求人们在大多数工作中使用低或中等推理强度。

上线几周后，我们按目录价格为模型 A 的生产使用定价，并进行聚合查看。模型 A 上每用户平均每周支出比前一个模型高出数倍。模型 A 的每个请求成本约为三倍，而模型 A 的平均用户发送的请求数也约为三倍。

输出 token 只占一个请求成本的十分之一。大部分成本流向了缓存上下文，模型在每次请求时都会重新读取它。模型 A 可以长时间自主工作，因此人们开始用它进行长时间、自主导向的会话。

评估衡量的是模型在一个任务上的表现。生产衡量的是人们选择如何与它协作。

后来，一个更新的模型在相同任务和评分器上得分高于模型 A，每任务成本约为其六分之一。我们通过一次配置更改将模型 A 的用户迁移到了它上面。

随后，我们在同一用户群体——模型 A 的重度用户——上聚合检查了这一变化。在他们使用更新模型后的第一个完整周，该群体向其主模型发送的请求数大致相同，而该群体在该模型上的支出降至约七分之一。

### 第 5 步：为什么会被限流，以及流量接下来去哪里

在 `bedrock-runtime` 端点上，Bedrock 会在请求到达时、模型写出任何内容之前检查你的每分钟 token 配额。它会预留你的未缓存输入 token 和缓存写入，再加上 `max_tokens`，即该请求允许的最大输出量。随着模型生成，它会调整该预留量，并在请求结算时返还未使用部分。缓存读取永远不会计入配额，因此一个请求在配额上可能很便宜，但在账单上可能很贵。输出 token 按消耗倍率结算，在大多数模型上为 1:1，在一些当前模型上则为数倍，因此请检查[你的模型费率](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-token-burndown.html)。

一个显示计费 token 的仪表板可能在请求被限流时仍显示有余量。在我们会话的示例中，配额为每分钟 100 万 token，流量为每分钟 300 个请求。仪表板显示约 30% 的配额。在应用 5:1 的输出 token 消耗倍率后，已完成的请求消耗了约 77%。

准入使用不同的计算方式。每个请求最初预留 600 个未缓存输入 token，加上 `max_tokens` 为 4,096，总计 4,696 个 token。响应的 p99 约为 800 个 token。

将 `max_tokens` 降至 1,024，会把初始预留量削减到 1,624 个 token，约缩小 65%。该限制仍高于 p99。对于未变化的输入和输出，最终配额消耗保持不变。更小的预留为准入请求留下了更多空间。监控 `stopReason` 以捕获被截断的响应。使用退避和抖动，并限制重试次数。

需求也可能超出你在任何单一模型上的余量。你希望在有需要之前就知道工作可以去哪里，而我们的评估回答了这个问题。答案可以是来自另一个模型系列的模型。对于我们使用的每个主要模型，我们至少保留一个在我们的评估中表现同样好、且可以负载均衡过去的等效模型。没有这些评估，选择工作去向就会是猜测。

如果某个模型上的余量持续紧张，我们可以通过更改配置中的默认值来重新平衡。首先要检查等效模型是否有容量承受额外负载，以及你的配额是否覆盖它。也要在其上保留足够流量以保住你的访问权限：模型进入 Legacy 期后，现有客户在 15 天不活动后可能失去访问权限。Legacy 模型在生命周期结束前仍然可用，之后 Bedrock 会将其从每个区域移除，对其的请求会失败，并且 Bedrock 不会自动迁移你的流量。当 `LegacyModelInvocations` 升至零以上时发出告警。

### 第 6 步：这是谁的支出？

Bedrock 运行时指标按 `ModelId` 划分维度，因此你可以看到是哪个模型服务了请求，但看不到是哪个团队发送的。Bedrock 发布这些指标时，既有带 `ModelId` 维度的，也有不带该维度的；如果请求在 Bedrock 解析模型之前失败，则只会出现在不带该维度的序列中，因此按 `ModelId` 过滤会少计错误。Bedrock 提供三种归因支出的方式：

- 哪个团队或用户？Bedrock 会在每个请求上记录调用者的 IAM 身份。为你的角色打标签，或传递会话标签，以便在 AWS Cost Explorer 和 AWS 成本与使用报告（CUR 2.0）中按标签查看成本。
- 哪个应用程序？应用程序推理配置文件是模型特定的，因此为每个应用程序和模型创建一个带标签的配置文件，并调用匹配配置文件的 ARN。
- 哪个功能或提示词？在 `Converse` 上通过 `requestMetadata` 传递键值对。Bedrock 会将它们写入模型调用日志，并且不会放入账单。要为其定价，请将日志中的 token 计数乘以公布的费率。经典 CUR 和 CUR 2.0 都不包含每请求 ID，因此请通过比较按模型、使用类型和时间段的总计来对账。

在网关后面，Bedrock 看到的是网关的角色，因此让网关为每个用户代入一个角色，并使用各自的 `RoleSessionName` 或会话标签。为会话缓存这些凭证，因为每个请求都代入角色可能超出你的 AWS Security Token Service（AWS STS）速率配额。归因失效时请求仍会继续成功，因此请为 Bedrock 未能交付调用日志设置告警。

我们的使用记录让我们可以按模型、客户端、团队和用户归因使用情况，我们仅以聚合方式将其用于成本和容量规划。我们根据同样的四类 token 计数计算每任务成本，因此可以比较评估与生产之间的 token 构成和成本。

## 结果

我们可以在一夜之间从模型发布走到部署决策。在一次推广后，模型 A 上每用户平均每周支出是前一个模型的数倍。我们将其重度用户迁移到了一个更新的模型。在他们使用后的第一个完整周，该群体在其主模型上的支出降至约七分之一，而请求数大致相同。对于我们使用的每个主要模型，我们的评估都会识别出一个可以重新平衡过去的等效模型。

## 清理

测试后，停止你启动的评估作业和代理进程。如果你仅为本次演练启用了模型调用日志记录，请使用 [DeleteModelInvocationLoggingConfiguration](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_DeleteModelInvocationLoggingConfiguration.html) 在每个区域禁用它。

在调用者不再使用它们后，使用 [DeleteInferenceProfile](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_DeleteInferenceProfile.html) 删除你创建的应用程序推理配置文件。删除仅为本次演练创建的 IAM 角色、策略和资源标签。停用仅用于这些测试的成本分配标签。删除你不再需要的测试 CloudWatch 日志组和 S3 日志对象。

## 结论

每次模型发布时，我们都会运行四项检查：

- 发布日：在你自己的任务上以每种推理强度运行新模型，并同时记录得分和每任务成本。
- 推广前：根据这些数字选择默认值和推理强度上限。阻止任何成本更高且得分低于更低推理强度的推理强度。
- 最初几周：将每请求成本和每用户平均请求数与评估中的每任务成本进行比较，两者都根据同样的四类 token 计数定价。
- 在有需要之前：了解来自任何模型系列的哪些模型在你的评估中得分相同，并在重新平衡之前检查它们的容量和你的配额。

我们选择 Amazon Bedrock，是为了通过一个 API 访问多个模型系列。它让我们可以使用现有的 AWS 访问控制和日志记录，同时由 AWS 管理模型基础设施。我们使用评估为我们的工作选择模型，并使用可观测性了解这些选择何时需要重新审视。
