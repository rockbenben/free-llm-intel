# MoEngage 如何用 AgentCore Gateway 把 400 个 API 变成 agent 工具

*本文由 MoEngage 的 Nikhil Kumar 和 Shakir Khan 合写。*

当工程团队开始构建 AI agent 时，这些 agent 所需要的能力通常已经以内部 API 的形式存在了：活动创建、人群分段查询、送达统计。难点不在于造新功能。难点在于如何让 agent 安全地触达数百个私有 API——既不把它们暴露到公网，又不把身份的控制权交给模型，也不让上百条工具定义把 context window 撑爆。

MoEngage 就是这个问题的当事人。它是一个 agentic 客户互动平台，1,350 多个消费品牌用它通过 push、邮件、in-app、SMS、WhatsApp 和 RCS 交付个性化体验。在产品背后，是约 400 个内部 REST API，由 25 个工程团队构建，运行在横跨七个 AWS Region 的私有虚拟私有云（VPC）里。MoEngage 按 Region 隔离这些 API 以履行数据驻留承诺，并且不把它们暴露到公网。agent 需要的能力本来就在生产环境里跑着，难的是让它安全可达。

在这篇文章里，我们会讲清楚 MoEngage 如何用 AgentCore Gateway——Amazon Bedrock AgentCore 的一项能力——把这些私有 API 变成按权限收口的 agent 工具。这套做法为 MoEngage 省下估计约六个月的平台工程工作量，如今接入一个新 API 花的是小时而不是天。没有任何产品团队写过 Model Context Protocol（MCP）server 代码，没有为每次集成单独 provision 网络，整条路径上也不存在任何一个公网 endpoint。

## 为什么 20 个 MCP server 是错误答案

Model Context Protocol（MCP）给 agent 提供了一套标准的工具发现与调用方式。采用它的最直白路径，是每个团队各自暴露一个自己的 MCP server。MoEngage 把这条路的成本算了一遍，然后否掉了它。

20 多个 MCP server 就意味着 20 多个部署要监控、打补丁，并在 MCP 不断演进时持续保持协议兼容。而跨域的 agent——那些真正有用的、会读一个活动、查它的人群分段、再检查送达统计的 agent——得连上好几台 server 并把它们对齐。再加上每个团队都得具备与实际产品工作无关的 MCP 专业知识。

于是 MoEngage 定下了一条塑造后续一切的原则：各个工程团队不实现 MCP。团队只构建 REST API，并声明哪些操作应该成为工具。MCP 这一层由 AI Platform 团队端到端负责。一个团队的责任边界，止于一份描述良好的 OpenAPI spec。

这条原则立刻带来三项需求：一个集中的工具面，agent 只需连接一次而不是每个服务连一次；按 agent 收口的授权，在服务端强制而不是靠约定；以及私有连通性，且不必为每个新 API 重建一遍。

全部从零自建也是一种选项。一个自研的中央 MCP server 能解决 20 个 server 的问题，但会留下 MoEngage 自己去建一条工具生成流水线、一套策略文件格式、一个用于重命名的工具别名注册表，以及熔断器。全是自定义代码，全由一个团队拥有，全都是无差异化的工作——既不会让 MoEngage 的 agent 更聪明，也不会让客户的活动做得更好。

## 塑造架构的四条约束

在评估任何方案之前，MoEngage 定下四条约束，四条必须同时满足。一个解决了前两条、却在第三条和第四条上崩掉的方案并不可行。

**任何东西都不许有公网 endpoint。** MoEngage 的内部 API 按策略都是 VPC 私有的。任何要求把它们暴露出去的方案——哪怕前面还叠一层额外认证——都直接没戏。常规的绕法是按集成逐个建网络：这儿一个 NAT gateway，那儿一个反向代理，第三个再来一条 VPN 隧道。把这个乘以七个 Region，运维面的增长就比 agent 数量的增长还快。每接入一个新 API，就意味着又一次网络变更申请、又一轮安全评审、又一块要维护的基础设施。

**身份不能由 agent 来决定。** 每一次内部 API 调用都带着租户、用户、角色和数据库上下文。如果这份上下文是一个大语言模型（LLM）可见的工具参数，模型就可能把它填错，或者被话哄着改掉。MoEngage 需要身份在结构上就超出模型的触及范围——由调用方服务注入，而不是作为模型可以设置或覆盖的东西暴露出来。

**400 个工具的目录装不进一个 context window。** 按每个工具约 50 token 的 JSON schema 估算，一次覆盖全部资产的 `tools/list` 就是超过 20,000 token，而且每次连接都要传输一遍。这点 token 预算在 agent 干任何有用之事之前就已经花光，还把 agent 真正需要用来推理任务的 context 挤掉了。客户端过滤（ADK 或 MCP SDK 里的 `tool_filter`）解决不了这个问题：完整目录已经过了线路，而靠客户端约定来过滤并不是一条授权边界。一个本不该看到写操作的 agent，一开始就不该收到它们。

最后这条约束，正是让那些显而易见的替代方案出局的原因。自研的中央 MCP server 能解决 20 个 server 的问题，但仍然会让 MoEngage 得自己去建一条工具生成流水线、一套策略文件格式、一个用于重命名的工具别名注册表和熔断器。全是自定义代码，全由一个团队拥有，没有一样能让 MoEngage 的产品更好。

## AgentCore Gateway 如何对上这些约束

Amazon Bedrock AgentCore Gateway 是一个全托管的 MCP server。你把 OpenAPI spec 注册为 target，网关就从它们生成 MCP 工具，再把调用路由到背后的服务。四条特性直接对上 MoEngage 的约束。

**OpenAPI 进，MCP 工具出。** 没有要构建或运维的 MCP server，也没有一份需要与 API 保持同步的独立产物。团队本来就在维护的那份 spec 就是工具定义。每个 operation 变成一个名为 `Target___operationId` 形式的工具，例如 `CampaignsAPI___searchCampaigns`。spec 一改，工具就跟着改。某个团队加一个 endpoint，工具就出现。某个团队去掉一个，工具就消失。不用部署，不用协议专业知识，不用和 AI Platform 团队协调。

**Cedar 策略，在目录被序列化之前就完成求值。** AgentCore 策略引擎用部分求值（partial evaluation）按 principal 过滤 `tools/list`。每个 agent 用自己的 IAM role 认证，而它的 Cedar 策略决定它能看到和调用哪些工具。这正是让 400 个工具变得可行的原因。它不是事后在客户端过滤，而是在构造响应之前就在服务端收口。

举个例子，一个活动 QA bot 拿到活动与人群分段工具的读权限，但不能调用写操作：

```
permit(
    principal == Agent::"campaign-qa-bot-v1",
    action == Action::"tools/call",
    resource in ToolGroup::"campaigns-read"
);

forbid(
    principal == Agent::"campaign-qa-bot-v1",
    action == Action::"tools/call",
    resource in ToolGroup::"write-actions"
);
```

这个 bot 的 `tools/list` 响应里根本看不到写工具。客户端那边没什么可过滤的，因为那些工具压根没被发过来。

**经由 Amazon VPC Lattice 的托管出口。** 网关通过 AgentCore 的 managed egress 触达 MoEngage 的内部服务，而不是通过 MoEngage 自建自运维的网络。入站方向，网关只能通过带私有 DNS 的 VPC interface endpoint 访问，没有任何公网路径通向它。接入一个新 API 增加的是一个 target，不是一次网络拓扑变更。这正是打破*乘以七个 Region*那道难题的属性：网络只需要存在一次，每个 API 都复用它。

**语义搜索作为网关的内建能力。** 有了 `x_amz_bedrock_agentcore_search` 能力，agent 可以通过描述任务来找工具，而不必点名叫出工具。它省掉了自建一层发现机制的需要，还顺带消掉了重命名带来的脆弱性：如果 `get_segment_user_count` 改名为 `get_segment_size`，一个搜索 *segment user count* 的 agent 依然能找到它，因为匹配发生在描述上而不是标识符上。

## 实际运行中的架构

从 agent 到内部 API 的请求链路很短，每一层各管一件具体的事。agent 服务通过 VPC interface endpoint 连到 AgentCore Gateway，网关求值 Cedar 策略，再通过基于 Amazon VPC Lattice 的 managed egress 把工具调用路由到内部 API。

图 1：MoEngage AgentCore Gateway 架构

运行在 Amazon Elastic Compute Cloud（Amazon EC2）上或容器里的 agent 服务调用 MCP client。这个 client 可以是官方 MCP SDK、LangChain、Google ADK，或 MoEngage 自己的 agent runner。client 用该服务本来就持有的 AWS Identity and Access Management（IAM）角色以 SigV4 给请求签名。请求经 HTTPS 走到一个带私有 DNS 的 VPC interface endpoint，中间没有公网跳点。AgentCore Gateway 收到请求后求值 Cedar 策略，判定这个 principal 能看到或调用什么，随后通过基于 Amazon VPC Lattice 的 managed egress 把工具调用路由到内部 API。

MoEngage 做了两个值得点出的认证决策。

第一，内部网关他们选了 SigV4 而不是 JWT。这里的 agent 是本来就拥有 IAM 角色的服务。用 SigV4，它们可以直接拿手里已有的凭证签名，没有新东西要签发、轮换或存储。MoEngage 另有一个对外的公共 MCP server，服务来自 Claude 等客户端的、由人认证的会话，它用的是 AgentCore runtime 上的 OIDC JWT。那是另一个面，有不同的需求。

第二，身份作为 header 传递，而不是作为工具参数。租户、用户、角色与数据库上下文由客户端库从一个小的 `Identity` 对象转换成 `X-MOE-*` header。模型看不到它们，也无法设置。有一个细节对所有想做类似东西的人很关键：由于 SigV4 签名占用了 Authorization header，调用方转发的 bearer token 必须挪到别处。MoEngage 把它作为一个带 MoEngage 前缀的专用 header 传播下去。header 传播也有上限，所以这一组 header 是刻意选定的，而不是攒出来的。

发现和执行有着不同的身份需求。列出工具和搜索工具不携带租户身份，只有 `tools/call` 携带。这一划分让发现保持廉价，也让审计链路清晰无歧义——每一个带身份的请求都是一次真实的数据访问。

即便用 Cedar 把 agent 收口到目录的一个子集，这个子集也可能很大。MoEngage 的客户端库向模型只暴露一个 meta 工具 `search_tools`。模型描述它需要什么，网关的语义搜索返回候选，而只有这些候选在这一轮剩余过程里可调用。完整目录不会进入 context。agent 的 context 在开始时只有一条工具定义，搜索之后是一小把相关的工具，而不是几百条它永远用不到的定义。

## 接入一个新 API

一个团队要把 API 作为 agent 工具暴露出去，只需在它现有的 OpenAPI spec 里加一个块：

```
paths:
  /campaigns:
    get:
      operationId: listCampaigns
      description: |
        Returns a paginated list of campaigns. Supports filtering by
        status, channel, date range, and tags.
      x-moe-mcp:
        expose:
          external: false
          internal: true
        tool_description: |
          Find campaigns by status or channel. Returns campaign ID, name,
          status, and channel. Use the returned campaign_id with
          get_campaign for full details, or send_campaign to launch it.
        param_overrides:
          status:
            description: |
              Filter by campaign status. Use 'active' for running
              campaigns, 'scheduled' for upcoming. Omit for all.
```

这个块里有四个值得解释的设计选择。

**暴露是显式 opt-in**。没有 `x-moe-mcp` 块的 endpoint 就不是工具。持续集成（CI）不会为它的缺失告警，因为对大多数 endpoint 来说，缺失才是正确的状态。缓存预热路由和迁移触发器不是 agent 工具，也不该有任何东西推着团队把它们变成工具。有了 `internal` 和 `external` 这两个标志，一个团队可以把某个 operation 独立地暴露给内部 agent、暴露给公共 MCP server，或者两者都暴露。

**工具描述不是 API 描述**。API 描述是告诉一个正在读文档的开发者这个 endpoint 返回什么；工具描述是告诉一个模型什么时候该取用这个工具、该传什么进去。MoEngage 发现，把 API 描述原样复用会导致很差的选择工具效果：模型会基于实现细节（“Returns a paginated list”）而不是意图（“Find campaigns by status or channel”）来挑工具。`tool_description` 和 `param_overrides` 字段的存在，就是专门给团队一个写面向模型的文案的地方，而不必改动面向开发者的文档。

**CI 流水线负责从 spec 到运行中工具的一切**。当一个团队推送 spec 变更，流水线会校验 `x-moe-mcp` 块、把 target 注册到 AgentCore Gateway，并应用 Cedar 策略。没有手工步骤，也不用给 AI Platform 团队提工单。一个从未考虑过 MCP 的团队，在流水线跑完的时间里就能让一个 operation 成为可用的 agent 工具。

**客户端库有两种模式**。一种是插件模式，把 AgentCore Gateway 这个 MCP server 作为 tool provider 包进 LangChain、Google ADK 或某个 MCP 兼容的框架里。另一种是 agent runner 模式，为那些想要一个独立 agent、又不想引入框架的团队跑完整的 agent loop。

## MoEngage 今天跑着什么

MoEngage 的 AgentCore Gateway 部署今天在七个 AWS Region 上运行。网关向 10 个内部 agent 提供约 400 个已注册 API operation 的服务。没有产品团队写过 MCP server 代码，没有产品团队为一次 agent 集成开通过网络，也没有产品团队实现过 Cedar 策略。这些全部由 AI Platform 团队拥有，而接入一个新 API 的成本是一条 spec 注解加一次 CI 运行。AgentCore 的功能可用性因 Region 而异。支持的 Region 请见 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/)。

这套系统已在生产环境运行三个月。这些 agent 覆盖了一位市场团队成员每天会碰到的整条工作流。一个活动 QA agent 在上线前校验定向规则和内容。一个送达健康 agent 跨渠道监控发送率和退信模式。一个人群分段构建 agent 把自然语言的受众描述翻译成人群分段查询。每个 agent 用自己的 IAM role 认证，只看到它的 Cedar 策略允许的工具，并通过描述任务而不是记住工具名来发现工具。通过省掉构建和运维 20 个独立 MCP server、以及在七个 Region 上按 API 逐个 provision 网络的需要，MoEngage 估计这套做法省下了约六个月的工程工作量。接入一个新 API 现在花的是几小时的 spec 注解，而不是几天的网络铺设与安全评审。

search-first 这个模式改变了 MoEngage 思考 agent 设计的方式。新 agent 一开始不硬编码任何工具引用：它们描述意图、收到候选，然后调用找到的东西。当一个团队重命名一个 operation 或上线一个新 operation，现有 agent 无需改代码就能用上它。

## 结论

MoEngage 这套做法背后的关键洞见，是一种与工程组织的实际运作方式对得上的关注点分离。产品团队拥有 API 并把它描述清楚。平台团队拥有协议层、策略层和连通层。AgentCore Gateway 让这种分工变得可行，因为它清掉了中间那些无差异化的工作：不用写 MCP server 代码，不用按 API 铺网络，也没有一套假装自己是授权的客户端过滤。

结果是这样一个 agent 系统：加一个新工具是一次 spec 变更，收紧一次访问是一次策略变更，而两者都不需要另一个团队参与。

要开始使用 AgentCore Gateway，请见 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/)。关于编写 Cedar 策略，请见 [Cedar 策略语言参考](https://docs.cedarpolicy.com/)。关于私有连通性模式，请见 [Amazon VPC Lattice 文档](https://docs.aws.amazon.com/vpc-lattice/)。
