# MoEngage 如何使用 AgentCore Gateway 将 400 个 API 转变为代理工具

*这篇文章是与 MoEngage 的 Nikhil Kumar 和 Shakir Khan 共同撰写的。*

当工程团队开始构建 AI 代理时，这些代理所需的功能通常已经作为内部 API 存在。活动创建、细分查询、交付统计。挑战不在于构建新功能。面临的挑战是如何让代理安全地访问数百个私有 API，而不将它们暴露于公共互联网，不让模型控制身份，也不用数百个工具定义淹没上下文窗口。

MoEngage 是一个代理客户参与平台，超过 1,350 个消费品牌使用该平台通过推送、电子邮件、应用内、短信、WhatsApp 和 RCS 提供个性化体验，它就面临着这个问题。该产品背后有大约 400 个内部 REST API，由 25 个工程团队构建，在七个 AWS 区域的私有虚拟私有云 (VPC) 中运行。 MoEngage 在区域内隔离这些 API，以满足数据驻留承诺，并且不会将它们暴露于公共互联网。代理所需的功能已经在生产中运行。让它安全地到达是最困难的部分。

在这篇文章中，我们将介绍 MoEngage 如何使用 AgentCore Gateway（Amazon Bedrock AgentCore 的一项功能）将这些私有 API 转变为权限范围内的代理工具。该方法为 MoEngage 节省了大约六个月的平台工程工作量，并且现在使用新 API 需要几个小时而不是几天。没有产品团队编写模型上下文协议 (MCP) 服务器代码，没有为每个集成配置网络，并且路径中的任何位置都不存在公共端点。

## 为什么 20 个 MCP 服务器是错误的答案

模型上下文协议 (MCP) 为代理提供了一种发现和调用工具的标准方法。采用它的直接途径是每个团队公开自己的 MCP 服务器。 MoEngage 考虑到了这一点并拒绝了它。

超过 20 台 MCP 服务器意味着随着 MCP 的发展，需要进行 20 多个部署来监控、修补和保持协议兼容。跨域代理是读取活动、检查其分段并检查交付统计信息的有用代理，需要连接到多个服务器并协调它们。每个团队都需要与其实际产品工作无关的 MCP 专业知识。

因此，MoEngage 确立了影响后续一切的原则：单个工程团队不实施 MCP。团队构建 REST API 并声明哪些操作应该是工具。 AI Platform 团队端到端地拥有 MCP 层。团队的责任以明确描述的 OpenAPI 规范结束。

该原则立即产生了三个要求：代理连接一次而不是每个服务的中央工具界面、每个代理授权在服务器端而不是按照惯例强制执行、以及不需要为每个新 API 重建的私有连接。

从头开始构建这一切是一种选择。定制的中央 MCP 服务器可以解决 20 台服务器的问题，但需要 MoEngage 构建工具生成管道、策略文件格式、用于重命名的工具别名注册表和断路器。所有自定义代码都归一个团队所有，所有这些工作都是无差异的，不会让 MoEngage 的代理变得更聪明，也不会让客户的活动变得更好。

## 塑造架构的四个约束

在评估任何解决方案之前，MoEngage 定义了四个约束。所有四个人都必须同时满足。解决两个问题但破坏第三个和第四个的解决方案是不可行的。

**没有任何东西可以获得公共端点。** MoEngage 的内部 API 根据策略是 VPC 私有的。任何需要暴露它们的解决方案，即使是在额外的身份验证之后，都是行不通的。传统的解决方法是按集成网络进行：这里一个 NAT 网关，那里一个反向代理，第三个网关使用 VPN 隧道。将其乘以七个区域，操作面的增长速度将快于代理组的增长速度。每个新的 API 都意味着另一个网络变更请求、另一组安全审查、另一部分需要维护的基础设施。

**身份不能由代理决定。**每个内部 API 调用都携带租户、用户、角色和数据库上下文。如果该上下文是大型语言模型 (LLM) 可见的工具参数，则模型可能会出错或被要求更改它。 MoEngage 需要身份在结构上超出模型的范围，由调用服务注入，并且不能作为模型可以设置或覆盖的内容出现。

**包含 400 个工具的目录不适合上下文窗口。** 每个工具大约有 50 个 JSON 模式令牌，整个资产中的完整“工具/列表”在每个连接上传输超过 20,000 个令牌。该代币预算是在代理执行任何有用的操作之前花费的，并且它挤出了代理推理任务实际需要的上下文。客户端过滤（ADK 或 MCP SDK 中的“tool_filter”）无法解决此问题。完整的目录已经通过网络，并且按客户端约定进行过滤并不是授权边界。不应看到写入操作的代理一开始就不应该接收它们。

最后一个限制是避免明显替代方案的限制。定制的中央 MCP 服务器解决了 20 台服务器的问题，但仍然让 MoEngage 构建工具生成管道、策略文件格式、用于重命名的工具别名注册表和断路器。所有自定义代码都由一个团队拥有，它们都没有使 MoEngage 的产品变得更好。

## AgentCore Gateway 如何映射到这些约束

Amazon Bedrock AgentCore Gateway 是完全托管的 MCP 服务器。您将 OpenAPI 规范注册为目标，网关根据它们生成 MCP 工具，然后将调用路由到支持服务。四个属性直接映射到 MoEngage 的约束。

**输入 OpenAPI，输出 MCP 工具。** 无需构建或操作 MCP 服务器，也无需单独的工件与 API 保持同步。规范团队已经维护了工具定义。每个操作都会成为一个名为“Target___operationId”的工具，例如“CampaignsAPI___searchCampaigns”。当规范发生变化时，工具也会发生变化。当团队添加端点时，该工具就会出现。当团队删除一个工具时，该工具就会消失。没有部署，没有协议专业知识，没有与 AI 平台团队协调。

**Cedar 策略，在序列化目录之前进行评估。** AgentCore 策略引擎使用部分评估来过滤每个主体的“工具/列表”。每个代理都以其自己的 IAM 角色进行身份验证，其 Cedar 策略决定它可以查看和调用哪些工具。这就是 400 工具易于使用的原因。它不是事后的客户端过滤，而是构建响应之前的服务器端范围界定。

例如，活动 QA 机器人可以读取活动和分段工具，但无法调用写入操作：
```
permit(
    principal == Agent::"campaign-qa-bot-v1",
    action == Action::"tools/call",
    resource in ToolGroup::"campaigns-read"
);

forbid(
    principal == Agent::"campaign-qa-bot-v1",
    action == Action::"tools/call",
    resource in ToolGroup::"write-actions"
);
```
机器人在其“tools/list”响应中看不到写入工具。由于未发送工具，因此客户端无需过滤任何内容。

**通过 Amazon VPC Lattice 托管出口。** 网关通过 AgentCore 托管出口而不是通过 MoEngage 构建和运营的网络到达 MoEngage 的内部服务。入站，只能通过具有私有 DNS 的 VPC 接口终端节点访问网关。没有公共路径可以到达它。加入新的 API 会添加目标，而不是网络拓扑更改。这是解决“乘以七个区域”问题的属性。网络一旦存在，每个 API 都会使用它。

**语义搜索作为网关功能。** 通过“x_amz_bedrock_agentcore_search”功能，代理可以通过描述任务而不是命名工具来查找工具。它消除了对自定义发现层的需要。它还消除了重命名脆弱性的副作用：如果“get_segment_user_count”变为“get_segment_size”，搜索*分段用户计数*的代理仍然会找到它，因为匹配发生在描述而不是标识符上。

## 实践中的架构

从代理到内部API的请求流程很短，并且每一层都有特定的工作。代理服务通过 VPC 接口终端节点连接到 AgentCore Gateway，后者评估 Cedar 策略并通过 Amazon VPC Lattice 上的托管出口将工具调用路由到内部 API。

在 Amazon Elastic Compute Cloud (Amazon EC2) 或容器中运行的代理服务调用 MCP 客户端。客户端可以是官方的MCP SDK、LangChain、Google ADK或MoEngage自己的代理运行器。客户端使用服务已有的 AWS Identity and Access Management (IAM) 角色通过 SigV4 签署请求。请求通过 HTTPS 传输到具有私有 DNS 的 VPC 接口终端节点。没有公共跳跃。 AgentCore Gateway 接收请求并评估 Cedar 策略以确定该主体可以看到或调用什么。然后，它通过 Amazon VPC Lattice 上的托管出口将工具调用路由到内部 API。

MoEngage 做出了两个值得关注的身份验证决定。

首先，他们选择 SigV4 而不是 JWT 作为内部网关。这里的代理是已经具有 IAM 角色的服务。借助 SigV4，他们可以使用已有的凭据进行签名。没有任何新内容可供发布、轮换或存储。 MoEngage 的独立公共 MCP 服务器为来自 Claude 和其他客户端的人工验证会话提供服务，在 AgentCore 运行时上使用 OIDC JWT。这是具有不同要求的不同表面。

其次，身份作为标头而不是工具参数进行传输。客户端库将租户、用户、角色和数据库上下文从小型“Identity”对象转换为“X-MOE-*”标头。模型看不到它们，也无法设置它们。对于任何构建类似内容的人来说，一个细节很重要：由于 SigV4 签名占用了授权标头，因此调用者转发的不记名令牌必须移至其他地方。 MoEngage 将其作为专用的 MoEngage 前缀标头进行传播。标头传播也受到限制，因此标头集是经过深思熟虑的而不是累积的。

发现和执行有不同的身份要求。列表和搜索工具不带有租户身份。只有“工具/调用”可以。这种分离可以降低发现成本，并使审计追踪变得明确。每个身份承载请求都是实际的数据访问。

即使 Cedar 将代理范围限定为目录的子集，该子集也可能很大。 MoEngage 的客户端库向模型公开了一个元工具“search_tools”。该模型描述了它需要什么，网关的语义搜索返回候选者，并且只有这些候选者在接下来的回合中才可调用。完整的目录不进入上下文。代理的上下文在开始时包含一个工具定义，在搜索后包含一些相关的定义，而不是它永远不会使用的数百个定义。

## 加入新的 API

将 API 作为代理工具公开的团队在其现有的 OpenAPI 规范中添加了一个块：
```
paths:
  /campaigns:
    get:
      operationId: listCampaigns
      description: |
        Returns a paginated list of campaigns. Supports filtering by
        status, channel, date range, and tags.
      x-moe-mcp:
        expose:
          external: false
          internal: true
        tool_description: |
          Find campaigns by status or channel. Returns campaign ID, name,
          status, and channel. Use the returned campaign_id with
          get_campaign for full details, or send_campaign to launch it.
        param_overrides:
          status:
            description: |
              Filter by campaign status. Use 'active' for running
              campaigns, 'scheduled' for upcoming. Omit for all.
```
该块中的四个设计选择值得解释。

**曝光是明确的选择加入**。没有“x-moe-mcp”块的端点不是工具。持续集成 (CI) 不会警告其不存在，因为对于大多数端点来说，不存在是正确的状态。缓存预热路由和迁移触发器不是代理工具，没有任何东西可以推动团队将它们变成一种工具。通过“internal”和“external”标志，团队可以独立地将操作公开给内部代理、公共 MCP 服务器或两者。

**工具描述不是 API 描述**。 API 描述告诉开发人员阅读文档端点返回什么。工具描述告诉模型何时使用该工具以及传递什么。 MoEngage 发现逐字重复使用 API 描述会导致工具选择不当。模型根据实施细节（“返回分页列表”）而不是意图（“按状态或渠道查找活动”）来选择工具。 “tool_description”和“param_overrides”字段的存在专门是为了让团队可以编写面向模型的文本，而无需更改面向开发人员的文档。

**CI 管道处理从规范到运行工具的所有事情**。当团队推送规范更改时，管道会验证“x-moe-mcp”块，向 AgentCore Gateway 注册目标，并应用 Cedar 策略。无需手动步骤，无需向 AI Platform 团队提供门票。从未考虑过 MCP 的团队可以在管道运行期间将操作用作代理工具。

**客户端库有两种模式**。插件模式将 AgentCore Gateway MCP 服务器封装在 LangChain、Google ADK 或 MCP 兼容框架内作为工具提供者。代理运行器模式为需要独立代理而不采用框架的团队运行完整的代理循环。

## MoEngage 今天运行什么

MoEngage 的 AgentCore Gateway 部署目前在七个 AWS 区域运行。该网关为 10 个内部代理提供大约 400 个注册 API 操作。没有产品团队编写过 MCP 服务器代码。没有产品团队为代理集成配置网络。没有产品团队实施 Cedar 政策。 AI Platform 团队拥有所有这些，而启用新 API 的成本是规范注释和 CI 运行。 AgentCore 功能的可用性因区域而异。有关受支持的区域，请参阅 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/)。

该系统已在生产环境中运行了三个月。这些代理涵盖了营销团队成员日常接触的工作流程。活动 QA 代理在启动前验证定位规则和内容。交付运行状况代理监控跨渠道的发送速率和跳出模式。细分生成器代理将自然语言受众描述转换为细分查询。每个代理都使用自己的 IAM 角色进行身份验证，仅查看其 Cedar 策略允许的工具，并通过描述任务而不是记住工具名称来发现工具。 MoEngage 估计，通过消除在七个区域构建和运营 20 个独立的 MCP 服务器以及按 API 网络配置的需要，该方法节省了大约六个月的工程工作量。现在，加入新的 API 需要花费数小时的规范注释，而不是花费数天的网络配置和安全审查。

搜索优先的模式改变了 MoEngage 对代理设计的看法。新代理从零硬编码工具引用开始。他们描述意图，接待候选人，并对他们发现的内容进行称呼。当团队重命名一项操作或发布新操作时，现有代理会直接选择该操作，而无需更改代码。

＃＃ 结论

MoEngage 方法背后的关键见解是关注点分离，映射到工程组织的实际工作方式。产品团队拥有 API 并对其进行了很好的描述。平台团队拥有协议层、策略层和连接层。 AgentCore Gateway 通过消除两者之间无差异的工作使这种分割变得实用：没有 MCP 服务器代码、没有每个 API 网络、没有假装授权的客户端过滤。

结果是一个代理系统，其中添加新工具是规范更改，限制访问是策略更改，并且不需要其他团队参与。

要开始使用 AgentCore Gateway，请参阅 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/)。有关 Cedar 策略编写的信息，请参阅 [Cedar 策略语言参考](https://docs.cedarpolicy.com/)。有关私有连接模式，请参阅 [Amazon VPC Lattice 文档](https://docs.aws.amazon.com/vpc-lattice/)。
