# 加速 AI 创新：借助 Amazon Bedrock 为企业工作负载扩展 MCP server

生成式 AI 一直在快速演进，新工具、新产品和新模型频繁发布。根据 Gartner 的说法，[agentic AI 是 2025 年最重要的技术趋势之一](https://www.gartner.com/en/articles/top-technology-trends-2025)，各类组织正在围绕如何在企业环境中使用 agent 开展原型验证。agent 依赖工具，而每种工具都可能有自己的信息收发机制。Anthropic 的 [Model Context Protocol (MCP)](https://modelcontextprotocol.io/introduction) 是一个开源协议，试图解决这一难题。它提供了一套可与不同工具交叉兼容的协议与通信标准，agentic 应用程序的大语言模型（LLM）可以用标准机制连接企业 API 或外部工具。不过，像金融服务这样的大型企业组织往往拥有复杂的数据治理与运营模式，这使得让 agent 与 MCP 协同工作颇具挑战。

一个主要挑战是各自为政的孤岛式做法：各个团队自行构建自己的工具，导致重复劳动和资源浪费。这种做法拖慢创新，并在集成与企业设计上造成不一致。此外，跨团队管理多个彼此割裂的 MCP 工具，使 AI 举措难以有效扩展。这些低效问题阻碍企业充分借助生成式 AI 处理交易后处理、客户服务自动化和监管合规等任务。

本文介绍一种使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 的集中式 MCP server 实现，它通过提供对工具与资源的共享访问带来一种创新做法。采用这种做法，团队可以专注于构建 AI 能力，而不是把时间花在开发或维护工具上。通过 MCP 标准化对资源与工具的访问，组织可以加速 AI agent 的开发，让团队更快进入生产。此外，集中式做法带来一致性与标准化，并降低运维开销，因为工具由专门团队统一管理，而不是分散在各团队手中。它还支持集中式治理，强制对 MCP server 的受控访问，从而降低数据外泄风险，并防止组织内出现未授权或不安全的工具使用。

## 解决方案概述

下图展示了一个基于金融服务用例的提议方案，该用例在合规、交易、运营和风险管理等多个业务线（LoB）中使用 MCP server。每个 LoB 都执行针对其特定业务定制的不同职能。例如，交易 LoB 专注于交易执行，而风险 LoB 执行风险限额检查。为履行这些职能，每个部门都提供一组 MCP server，用于支撑相应 LoB 内的操作并访问相关数据。这些 server 可供各 LoB 内部开发的 agent 访问，也可以开放给 LoB 之外的 agent。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/24/ML-18728-image-1.png)

MCP server 的开发是去中心化的。每个 LoB 负责开发支撑其特定职能的 server。某个 server 开发完成后会被集中托管，并可跨 LoB 访问。它以注册表或 marketplace 的形式存在，既促进 AI 驱动方案在各部门间的集成，又对共享资源保持控制与治理。

在接下来的章节中，我们从概念层面探讨该方案的整体形态。

## agentic 应用程序与中央 MCP server hub 的交互

以下流程图展示了使用 Amazon Bedrock 构建的 agentic 应用程序如何与 MCP server hub 中的某个 MCP server 交互。![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/24/ML-18728-image-2.png)

该流程包含以下步骤：

- 应用程序通过负载均衡器连接到中央 MCP hub，并向特定的 MCP server 请求可用工具列表。这一过程可以按 agentic 应用程序有权访问的 server 做细粒度控制。
- 交易 server 返回可用工具列表，其中包含工具名称、描述和所需输入参数等细节。
- agentic 应用程序调用 Amazon Bedrock agent，并提供可用工具列表。
- agent 利用这些信息，根据给定任务和自身可用的工具列表决定下一步做什么。
- agent 选择最合适的工具，并返回工具名称与输入参数。控制权交回 agentic 应用程序。
- agentic 应用程序使用工具名称与输入参数，通过 MCP server 请求执行该工具。
- 交易 MCP server 执行该工具，并把执行结果返回给应用程序。
- 应用程序把工具执行结果返回给 Amazon Bedrock agent。
- agent 查看工具执行结果并决定下一步。

接下来我们深入该方案的技术架构。

## 架构概述

下图展示了为某个 LoB 托管集中式 MCP server 集群的架构。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/24/ML-18728-image-3.png)

该架构可以分为五个部分：

- MCP server 发现 API
- agentic 应用程序
- 中央 MCP server hub
- 工具与资源

下面我们逐一详述各部分：

- **MCP server 发现 API** – 该 API 是一个用于发现各类 MCP server 的专用端点。不同团队可以调用它来查找注册表中可用的 MCP server、阅读其描述以及工具与资源详情，并判断哪个 MCP server 适合自己的 agentic 应用程序。新的 MCP server 发布后会被加入 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 数据库。MCP server 的所有者负责保持注册表信息的最新状态。
- **agentic 应用程序** – agentic 应用程序托管在 [Amazon Elastic Container Service](https://aws.amazon.com/ecs)（Amazon ECS）的 [AWS Fargate](https://aws.amazon.com/fargate) 上，并使用 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 构建。团队也可以使用新发布的开源 [AWS Strands Agents SDK](https://strandsagents.com/)，或自选的其他 agentic 框架来构建 agentic 应用程序，并用自有的容器化方案来托管它。agentic 应用程序通过安全的私有[虚拟私有云（VPC）端点](https://docs.aws.amazon.com/vpc/latest/privatelink/concepts.html)访问 Amazon Bedrock，并使用私有 VPC 端点访问 MCP server。
- **中央 MCP server hub** – 这里托管着 MCP server。对 server 的访问通过 [AWS Network Load Balancer](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/introduction.html) 实现。从技术上说，每个 server 都是一个可托管在 Amazon ECS 上的 [Docker 容器](https://www.docker.com/resources/what-container/)，但你也可以选择自己的容器部署方案。这些 server 可以独立扩展，互不影响。它们再通过私有 VPC 端点连接到一个或多个工具。
- **工具与资源** – 该组件承载工具，例如数据库、另一个应用程序、[Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）或其他工具。对企业而言，对工具与资源的访问仅通过私有 VPC 端点提供。

## 方案的优势

该方案带来以下关键优势：

- **可扩展性与韧性** – 由于使用了 Fargate 上的 Amazon ECS，你开箱即得可扩展性，无需管理基础设施或处理扩缩容问题。Amazon ECS 会自动检测故障并从中恢复：在本地重启失败的 MCP server 任务，或重新预置容器，从而把停机时间降到最低。它还能把流量从不健康的可用区转移走，并在健康的可用区之间重新平衡任务，以提供不间断的 server 访问。
- **安全性** – 对 MCP server 的访问在网络层面通过 PrivateLink 等网络控制手段加以保护。这确保 agentic 应用程序只连接组织托管的可信 MCP server，反之亦然。每个 Fargate 工作负载都在隔离环境中运行，从而防止任务之间共享资源。对于应用程序的身份认证与授权，我们建议使用 MCP Auth Server（参见下面的 [GitHub repo](https://github.com/aws-solutions-library-samples/guidance-for-deploying-model-context-protocol-servers-on-aws/)），把这类任务交给一个可独立扩展的专用组件。

截至本文撰写时，MCP 协议并不提供用户级访问控制或授权的内置机制。需要按用户进行访问限制的组织，必须在 MCP 协议之上实现额外的安全层。参考实现请参见下面的 [GitHub repo](https://github.com/aws-solutions-library-samples/guidance-for-deploying-model-context-protocol-servers-on-aws)。

## 用例

本实现基于一个以交易后执行为核心的金融服务用例。交易后执行指的是客户下达股票买入/卖出订单之后发生的流程与步骤。它涉及许多步骤，包括核实交易明细、实际划转资产、提供执行详情报告、运行欺诈检查等。为简化演示，我们聚焦于订单执行这一步。

尽管该用例是为金融行业量身定制的，你也可以把这套架构与方法应用到其他企业工作负载。本实现的全部代码可在 [GitHub](https://github.com/aws-samples/sample-deploy-mcp-servers-at-scale-on-aws) 上获取。我们使用 [AWS Cloud Development Kit](https://aws.amazon.com/cdk/)（AWS CDK）的 Python 版本部署该方案，它会创建一个通过 MCP server 连接工具的 agentic 应用程序，还会创建一个 [Streamlit](https://streamlit.io/) UI 来与 agentic 应用程序交互。

以下代码片段提供了对 MCP 发现 API 的访问：

```
def get_server_registry():
    # Initialize DynamoDB client
    dynamodb = boto3.resource('dynamodb')
    table = dynamodb.Table(DDBTBL_MCP_SERVER_REGISTRY)
    
    try:
        # Scan the table to get all items
        response = table.scan()
        items = response.get('Items', [])
        
        # Format the items to include only id, description, server
        formatted_items = []
        for item in items:
            formatted_item = {
                'id': item.get('id', ''),
                'description': item.get('description', ''),
                'server': item.get('server', ''),
            }
            formatted_items.append(formatted_item)
        
        # Return the formatted items as JSON
        return {
            'statusCode': 200,
            'headers': cors_headers,
            'body': json.dumps(formatted_items)
        }
    except Exception as e:
        # Handle any errors
        return {
            'statusCode': 500,
            'headers': cors_headers,
            'body': json.dumps({'error': str(e)})
        }
```

上述代码通过 [AWS Lambda](https://aws.amazon.com/lambda) 函数调用。完整代码见 [GitHub 仓库](https://github.com/aws-samples/sample-deploy-mcp-servers-at-scale-on-aws/tree/main/lambda/mcp-server-discovery/index.py)。下图展示了发现 API 的响应。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/06/24/ML-18728-image-4-1.gif)

我们来看一个场景：用户提交一个问题：“以 USD 186 买入 100 股 AMZN，在账户 A31 与 B12 之间平均分配。”为执行该任务，agentic 应用程序调用交易执行 MCP server。以下代码是该 MCP server 实现交易执行的示例：

```
from fastmcp import FastMCP
from starlette.requests import Request
from starlette.responses import PlainTextResponse
mcp = FastMCP("server")

@mcp.custom_route("/", methods=["GET"])
async def health_check(request: Request) -> PlainTextResponse:
    return PlainTextResponse("OK")

@mcp.tool()
async def executeTrade(ticker, quantity, price):
    """
    Execute a trade for the given ticker, quantity, and price.
    
    Sample input:
    {
        "ticker": "AMZN",
        "quantity": 1000,
        "price": 150.25
    }
    """
    # Simulate trade execution
    return {
        "tradeId": "T12345",
        "status": "Executed",
        "timestamp": "2025-04-09T22:58:00"
    }
    
@mcp.tool()
async def sendTradeDetails(tradeId):
    """
    Send trade details for the given tradeId.
    Sample input:
    {
        "tradeId": "T12345"
    }
    """
    return {
        "status": "Details Sent",
        "recipientSystem": "MiddleOffice",
        "timestamp": "2025-04-09T22:59:00"
    }
if __name__ == "__main__":
    mcp.run(host="0.0.0.0", transport="streamable-http")
```

完整代码可在以下 [GitHub repo](https://github.com/aws-samples/sample-deploy-mcp-servers-at-scale-on-aws/blob/main/mcp_servers/trading/trade-execution/index.py)中获取。
