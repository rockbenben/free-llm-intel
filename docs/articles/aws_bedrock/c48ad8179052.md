# Care Access 如何借助 Amazon Bedrock prompt caching 将数据处理成本降低 86%、处理速度提升 66%

*本文与 Care Access 的 Michelle Tat、Christopher Penrose、Rasmus Buchmann 和 Daniel Hansen 合写。*

医疗行业的组织在处理大量病历文件时面临一个关键挑战：如何在维持严格的安全与合规标准的同时，每天高效分析数千份病历。基于 LLM 的病历分析是强有力的方案，但它针对每个独立的分析问题都要重新处理大块医疗数据，导致运营成本高、响应变慢。

正面应对这一挑战的组织之一是 [Care Access](https://careaccess.com/)——全球健康服务与临床研究领域的领军者，它在扩大健康筛查项目规模时遇到了完全相同的问题。每天处理 300-500+ 份病历，意味着每项分析都需要多个独立的 prompt，而每个 prompt 都要重新处理病历中的大块内容。随着每天有数百名新参与者选择分享自己的病历，Care Access 需要一套能高效扩展、同时满足严格医疗合规与隐私标准的方案。

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 中的 [prompt caching](https://aws.amazon.com/bedrock/prompt-caching/) 功能带来了突破。通过缓存静态的病历内容、只让分析问题变化，Care Access 显著降低了成本、缩短了处理时间。这一优化把病历处理从潜在的制约因素，转变为支撑项目增长的助力。

本文演示医疗行业的组织如何安全地实施 prompt caching 技术，在满足合规要求的前提下简化病历处理。

## 背景

[Care Access](https://careaccess.com/) 致力于让未来的健康服务对所有人更好。Care Access 拥有数百个临床研究点、移动诊所和遍布全球的临床医生，把世界一流的健康研究与医疗服务直接带到那些常常面临就医障碍的社区。

其使命的核心是一个健康筛查项目：为参与者提供先进血液检测的结果，同时帮助其对接相关的健康资源，包括具有突破性的临床试验。Care Access 目前每月在全球为近 15,000 名新参与者提供健康筛查，并预计在未来数月至数年内快速增长。

参与者常常选择分享自己的病历，这让 Care Access 能提供更个性化的医疗照护，并识别与参与者健康状况相匹配的潜在健康资源，包括临床研究机会。这一创新做法与参与者产生强烈共鸣，每天都有数百人申请向 Care Access 分享病历。

然而，快速增长和成功也会给那些为迅速满足上升需求而扩张运营的组织带来后勤挑战。对 Care Access 而言，既要处理海量、格式多样的医疗数据，又要维持严格的合规、隐私与安全标准，就需要一套创新方案。公司实施了一套基于 Amazon Bedrock 的大语言模型（LLM）方案来分析这些记录。尽管电子病历可能遵循某些规范化的数据标准，但由于患者每次就诊时信息记录方式不同，每份病历的内容可能千差万别。虽然已存在传统的基于规则系统和基于 OCR 的提取方法，但 LLM 在这一挑战上尤为有效：它们能理解上下文，并解读不同医疗服务提供方之间病历记录方式的差异，而无需为每种数据源格式做大量规则定制。

最初的实现要求每项分析都使用多个独立的 prompt，而每个 prompt 都需要重新处理病历中的大块内容。随着项目规模扩大，这种做法因大量输入 token 被反复处理，导致每日运营成本高企。

## prompt caching 概览

在深入 Care Access 的实施之前，先理解 Amazon Bedrock 的 prompt caching 能力，以及它为何对病历处理格外有效，这很重要。

prompt caching 允许复用 prompt 中的某些部分，而这些部分原本在每次推理时都要为每条记录重新计算。使用 prompt caching 功能时，Amazon Bedrock 会存储（缓存）初始 prompt（称为 prefix），并为其分配唯一的 `promptId`。处理后续记录时，prompt prefix 会通过 `promptId` 从缓存中取出，用于每条后续记录的推理。

### 何时使用 prompt caching 而非其他优化技术

prompt caching 是可用于大幅提升性能的多种优化技术之一。带标签的组件式 prompt caching 可以缓存请求之间保持静态的 prompt 部分，同时仍允许 prompt 的其他部分变化。对 Care Access 来说，带标签的组件式 prompt caching 恰好契合其用例。其他优化技术（例如问题打包）也可以叠加使用，进一步提升效果。

#### 展示已缓存与未缓存组件的示例 prompt 结构

参与者的病历在请求之间保持不变，而针对该病历提出的具体医疗问题会变化。这种做法可以缓存绝大多数 token，同时允许 prompt 的最后一部分变化。例如：

```
{ 
 	"content": [ 
		{ 
			"cache-control": { 
				"type": "ephemeral" 
			}, 
			"text": [  
				  
			], 
			"type": "text"  
		},  
		{  
			"text": "The question is: ", 
			"type": "text"  
		}  
	]
}  
```

在这里，缓存参与者的病历使得快速遍历大量医疗问题成为可能，而无需重新处理大部分 token。

## 方案架构

Care Access 选择 Amazon Bedrock，源于其与 AWS 的长期合作——这段合作支持 Care Access 从初创公司成长为跨国企业。患者隐私与安全合规始终是 Care Access 的最高优先级，因此只采用和实施方案中能保障患者数据安全的那些，这一点至关重要。在与 Care Access 的合作历程中，AWS 方案持续证明其严格遵守 Care Access 的高安全标准，以及确保病历数据安全的隐私措施。Amazon Bedrock 中的 prompt caching 功能，则为 Care Access 提供了一条同时优化通过 LLM 处理数千份病历所需速度与成本的路径。

Care Access 推理 pipeline 的整体架构按以下编号阶段展开：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/21/image-1-15.png)

**阶段 1：病历检索**

单份电子健康记录（EHR）从 Amazon S3 存储桶中检索出来，做处理前的规范化，并在移除不必要数据后为推理做好准备。

**阶段 2：prompt 缓存管理**

病历内容成为静态的缓存 prefix，而具体的分析问题构成随每次查询变化的动态部分。

**阶段 3：LLM 推理**

每份已缓存的健康记录都通过 Amazon Bedrock 接受多个分析问题。当 prefix 与现有缓存匹配且超过 1,000 个 token 的最低要求时，缓存检查点（cache checkpointing）即被激活。

**阶段 4：输出处理**

结果按参与者合并为单个 JSON 并存入 Amazon S3，供后续通过 Amazon Athena 做下游分析。随后参与者会被匹配到相关的临床试验。

## 数据安全与隐私

**安全与隐私要求：**

Care Access 在处理病历时须满足严格要求：

- 所有 PHI 处理都须符合高隐私与安全标准（HIPAA 或类 HIPAA 标准）
- 最小必要信息原则
- 所有数据访问都需留审计轨迹
- 安全的数据传输与存储

**如何满足这些要求：**

通过推理 pipeline 处理的每份 EHR 都包含个人健康信息（PHI）和个人身份信息（PII）。Care Access 通过以下方式满足这些要求：

- **AWS Lake Formation：** 为所有服务（Amazon S3、Amazon Bedrock、Amazon Athena）管理特权 IAM 权限
- **数据最小化：** 遵循基于 HIPAA 合规的准则，只使用最小必要的 PHI（医疗状况），丢弃不必要的 PHI
- **移除 PII：** 所有 PII（姓名、地址、电话号码）都被移除，仅保留用于记录索引的唯一标识符
- **审计日志：** 通过 Amazon CloudWatch 提供所有数据与服务访问的完整审计轨迹

## 收益与影响

在 Amazon Bedrock 中实施 prompt caching 带来了变革性成果：

**成本优化：**

- Amazon Bedrock 成本降低 86%（降至原来的 1/7）

**性能提升：**

- 每条记录的处理时间减少 66%（速度提升 3 倍）
- 每天节省 4-8+ 小时处理时间

**运营收益：**

- 通过上下文复用降低 token 消耗
- 改善连续查询的响应时间
- 在所有病历处理操作中保持上下文完整性
- 尽管时间表雄心勃勃，仍按期达成所有实施里程碑

“在我们推出第一代基于 LLM 的解决方案时，AWS 是极佳的合作伙伴，”Care Access 应用机器学习与分析负责人 Josh Brandoff 说。“Amazon Bedrock 快速集成了我们现有的数据湖架构，让我们在六周内（而不是数月）就上线了病史审阅方案，并为健康筛查参与者识别和匹配了更多健康资源机会，包括临床试验。当我们的记录摄入量比预期更早激增时，Bedrock 的 prompt caching 能力让我们只需极少技术改动就能控制成本。”

## 最佳实践与技术考量

**实施建议：**

Care Access 的团队认为 prompt caching 功能对其用例高度灵活。关键经验包括：

- **token 阈值策略：** 大多数 EHR 包含数千到数万个 token。利用 1,000 token 的最低阈值，只要记录足够大，其 pipeline 就会自动启用缓存。
- **默认缓存策略：** 当预期 prompt 大小不一，尤其是偏向较大的 token 数时，默认启用缓存。
- **缓存优化：** 让 prompt 的组织方式使病历内容（静态、体量大）成为缓存 prefix，而分析问题（动态、体量小）保持不缓存。
