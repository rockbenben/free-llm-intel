# 在 AWS 上优化生成式 AI 应用的成本

McKinsey & Company 发布的报告[《生成式 AI 的经济潜力：下一个生产力前沿》](https://www.mckinsey.com/capabilities/mckinsey-digital/our-insights/the-economic-potential-of-generative-ai-the-next-productivity-frontier#introduction)估计，[生成式 AI](https://aws.amazon.com/generative-ai/) 可为全球经济带来相当于 2.6 万亿至 4.4 万亿美元的价值。最大的价值将来自四个领域：客户运营、市场营销与销售、软件工程以及研发。

如此巨大商业价值的潜力，正激励着数以万计的企业在 AWS 上构建自己的生成式 AI 应用。然而，许多产品经理和企业架构负责人希望更深入地理解成本、成本优化杠杆以及敏感性分析。

本文讨论这些成本考量，帮助你优化在 AWS 上的生成式 AI 成本。

本文假定你对基础模型（FM）与大语言模型（LLM）、token、向量嵌入以及 AWS 中的向量数据库有基本了解。由于检索增强生成（RAG）是生成式 AI 解决方案中最常用的框架之一，本文将在 RAG 解决方案的语境下解释成本，以及在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上相应的优化支柱。

在本系列的第二部分中，我们将介绍如何估算商业价值及其影响因素。

## 成本与性能优化支柱

设计性能出色且成本高效的生成式 AI 应用，对于充分释放这项变革性技术的潜力、推动其在组织内广泛采用至关重要。

生成式 AI 应用中的成本与性能预测和管理由以下优化支柱驱动：

- 模型选择、模型选定与模型定制 —— 我们的定义如下：  模型选择（model selection）—— 该过程包括识别能满足多种用例的最优模型，随后进行模型验证，即在高品质数据集和 prompt 上做基准测试，以找出胜出的模型候选。模型选定（model choice）—— 指选择恰当的模型，因为不同模型的定价和性能属性各不相同。模型定制（model customization）—— 指选择恰当的技术，用训练数据定制 FM，以根据业务特定用例优化性能与成本效益。
- token 使用 —— 分析 token 使用包括以下内容：  token 计数 —— 使用生成式 AI 模型的成本取决于所处理的 token 数量，这会直接影响一次操作的成本。token 限制 —— 理解 token 限制以及是什么驱动 token 数量，并设置护栏来限制 token 数量，可以帮助你优化 token 成本与性能。token 缓存 —— 在应用层或 LLM 层对常见用户问题进行缓存，有助于减少 token 数量并提升性能。
- 推理定价方案与使用模式 —— 我们考虑两种定价选项：  On-Demand —— 适合大多数模型，按输入/输出 token 数量计费，不保证 token 吞吐量。Provisioned Throughput —— 适合要求有保障吞吐量的工作负载，但成本相对更高。
- 其他因素 —— 额外因素还包括：  安全护栏 —— 针对个人可识别信息（PII）、有害内容、不当话题应用内容过滤器，并检测幻觉，可提升生成式 AI 应用的安全性。这些过滤器可以独立于 LLM 运行与扩展，其成本与过滤器数量以及所检查的 token 数量成正比。向量数据库 —— 向量数据库是大多数生成式 AI 应用的关键组件。随着生成式 AI 应用中的数据用量增长，向量数据库成本也会增长。分块策略 —— 固定大小分块、分层分块或语义分块等分块策略，会影响生成式 AI 应用的准确性与成本。

下面我们深入考察这些因素以及相关的成本优化建议。

## 检索增强生成

RAG 帮助 LLM 回答针对你企业数据的问题，即使该 LLM 从未在你的数据上训练过。

如以下示意图所示，生成式 AI 应用读取你受信任的企业数据源，对其进行分块，生成向量嵌入，并把嵌入存储到向量数据库中。存储在向量数据库中的向量和数据通常被称为*知识库*。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/16/ML-17334-RAG.png)

生成式 AI 应用使用向量嵌入来搜索并检索与用户问题最相关的数据块，并据此增强问题以生成 LLM 响应。以下示意图展示了这一工作流。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/16/ML-17334-workflow.png)

该工作流包括以下步骤：

- 用户通过生成式 AI 应用提出一个问题。
- 向 LLM 发送生成嵌入的请求。
- LLM 把嵌入返回给应用。
- 这些嵌入会与存储在向量数据库（知识库）中的向量嵌入进行检索比对。
- 应用从知识库中接收与用户问题相关的上下文。
- 应用把用户问题和上下文发送给 LLM。
- LLM 使用上下文生成准确且有依据的响应。
- 应用把最终响应发回给用户。

Amazon Bedrock 是一项全托管服务，通过统一的 API 提供来自领先 AI 提供商的高性能 FM。它提供范围广泛的 LLM 可供选择。

在上述工作流中，生成式 AI 应用调用 Amazon Bedrock API，把文本发送给 Amazon Titan Embeddings V2 这类 LLM 以生成文本嵌入，并把 prompt 发送给 Anthropic 的 Claude Haiku 或 Meta Llama 这类 LLM 以生成响应。

生成的文本嵌入存储在向量数据库中，例如 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/)、[Amazon Relational Database Service](https://aws.amazon.com/rds/)（Amazon RDS）、[Amazon Aurora](https://aws.amazon.com/rds/aurora/) 或 [Amazon MemoryDB](https://aws.amazon.com/memorydb/)。

虚拟助手或支持聊天机器人这类生成式 AI 应用可能需要与用户进行对话。多轮对话要求应用保存每个用户的问题-回答历史，并把它发送给 LLM 作为额外上下文。该问题-回答历史可以存储在 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 这类数据库中。

生成式 AI 应用还可以使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 来检测离题问题、把响应锚定到知识库、检测并脱敏 PII 信息，以及检测并阻止与仇恨或暴力相关的问题和回答。

现在我们已经较好地理解了基于 RAG 的生成式 AI 应用中的各个组件，接下来看看在 AWS 上用 RAG 运行应用时，这些因素如何影响成本。

## 小、中、大与超大场景的方向性成本

假设某组织希望借助一个虚拟助手帮助其客户，该助手能够随时以高准确度、高性能、一致性和安全性回答客户的问题。生成式 AI 应用的性能与成本直接取决于环境中的几个主要因素，例如每分钟的问题速率、每天的问题量（考虑高峰与非高峰时段）、知识库数据量，以及所使用的 LLM。

尽管本文解释的是影响成本的因素，但了解基于某些假设的方向性成本也可能有帮助，这能让你对小型、中型、大型和超大型环境等几个场景的各类成本构成形成相对的理解。

## Amazon Bedrock 成本

Amazon Bedrock 有两种定价模式：On-Demand（用于前述示例场景）和 Provisioned Throughput。

在 On-Demand 模式下，每个 LLM 都有每分钟最大请求数（问题数，RPM）和每分钟 token 数（TPM）限制。RPM 和 TPM 通常因 LLM 而异。更多信息，请参阅 [Amazon Bedrock 的配额](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas.html)。

在超大型用例中，每月 700 万个问题，假设每天 10 小时、每月 22 个工作日，折算为每分钟 532 个问题（532 RPM）。这远低于 Anthropic 的 Claude 3 Haiku 的 1,000 RPM 上限。

以每个问题平均 2,720 个 token、每分钟 532 个请求计算，TPM 为 2,720 x 532 = 1,447,040，远低于 Anthropic 的 Claude 3 Haiku 的 2,000,000 TPM 上限。

然而，假设用户问题增长 50%。RPM、TPM 或两者可能越过阈值。在生成式 AI 应用需要越过 On-Demand 的 RPM 和 TPM 阈值的情况下，你应考虑 Amazon Bedrock Provisioned Throughput 模式。

使用 Amazon Bedrock Provisioned Throughput 时，成本按每个模型单元计算。模型单元在你计划使用的整个期间专用，例如按小时、1 个月或 6 个月的承诺。

每个模型单元提供一定的每分钟最大 token 容量。因此，模型单元的数量（以及成本）由输入和输出 TPM 决定。

使用 Amazon Bedrock Provisioned Throughput 时，无论是否使用，你都要为每个模型单元付费。因此，Provisioned Throughput 模式相对比 On-Demand 模式更贵。

请考虑以下成本优化建议：

- 从 On-Demand 模式开始，用你选定的 LLM 测试其性能与延迟。这会带来最低的成本。
- 如果 On-Demand 无法满足所需的 RPM 或 TPM 量，可以在生成式 AI 应用测试期先采用 1 个月订阅的 Provisioned Throughput。不过，对于稳态生产，可考虑 6 个月订阅以降低 Provisioned Throughput 成本。
- 如果高峰时段较短而非高峰时段较长，可以考虑在高峰时段使用 Provisioned Throughput 的按小时模式，在非高峰时段使用 On-Demand。这可以尽量减少 Provisioned Throughput 成本。

## 影响成本的因素

本节我们讨论可能影响成本的各种因素。

### 问题数量

在 On-Demand 模式下，随着问题数量增长，成本也会增长，从下图的年成本可以看出（基于前面讨论的表格）。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/16/ML-17334-costs.png)

### 输入 token

发送给 LLM 的输入 token 主要来源是 system prompt、user prompt、来自向量数据库（知识库）的上下文，以及来自问答历史的上下文，如下图所示。

随着每个组成部分的规模增长，发送给 LLM 的输入 token 数量会增长，成本也随之增长。

一般而言，user prompt 相对较小。例如，在 user prompt“Amazon DynamoDB 的性能与成本优化策略有哪些？”中，假设每个 token 四个字符，大约有 20 个 token。

system prompt 可能很大（因此成本更高），尤其是 multi-shot prompt，其中会提供多个示例，以获得语气和风格更好的 LLM 响应。如果 system prompt 中的每个示例使用 100 个 token，且有 3 个示例，那就是 300 个 token，比实际的 user prompt 大不少。

来自知识库的上下文往往是最大的一块。例如，当文档被分块并为每个块生成文本嵌入时，假设块大小为 2,000 个字符。假设生成式 AI 应用把三个与 user prompt 相关的块发送给 LLM，那就是 6,000 个字符。按每个 token 四个字符计算，折合 1,500 个 token。与典型的 user prompt 或 system prompt 相比，这要高得多。

来自问答历史的上下文也可能很高。假设 user prompt 平均 20 个 token，LLM 响应 100 个 token。假设生成式 AI 应用在每次提问时都附带三个问答对的历史，折合为（每个问题 20 个 token + 每个响应 100 个 token）x 3 个问答对 = 360 个 token。

请考虑以下成本优化建议：

- 限制每个 user prompt 的字符数
- 在最终确定取值之前，测试来自向量数据库的不同块数量和块大小下的响应准确性
- 对于需要与用户进行对话的生成式 AI 应用，用两个、三个、四个或五个问答对的历史做测试，然后选出最优值

### 输出 token

LLM 的响应取决于 user prompt。总体而言，输出 token 的定价是输入 token 定价的三到五倍。

请考虑以下成本优化建议：

- 由于输出 token 较贵，可考虑在 system prompt 中指定最大响应长度
- 如果部分用户属于需要对 user prompt 或 LLM 响应设置更高 token 上限的群组或部门，可考虑使用多个 system prompt，让生成式 AI 应用根据用户选择正确的 system prompt

### 向量嵌入成本

如前所述，在 RAG 应用中，数据被分块，文本嵌入被生成并存储到向量数据库（知识库）中。文本嵌入通过调用带有 LLM（例如 Amazon Titan Text Embeddings V2）的 Amazon Bedrock API 来生成。这与你为推理选择的 Amazon Bedrock 模型（例如 Anthropic 的 Claude Haiku 或其他 LLM）无关。

生成文本嵌入的定价基于输入 token 数量。数据越多，输入 token 越多，成本也就越高。

例如，25 GB 数据，按每个 token 四个字符计算，输入 token 总计 67.11 亿个。Amazon Titan Text Embeddings V2 的 Amazon Bedrock On-Demand 价格为每百万 token 0.02 美元，则生成嵌入的成本为 134.22 美元。

不过，Amazon Titan Text Embeddings V2 的 On-Demand 有 [2,000 RPM 的限制](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas.html)。在 2,000 RPM 下，嵌入 25 GB 数据需要 112 小时。由于嵌入数据是一次性任务，这在大多数场景下或许可以接受。

对于每月 5% 的变更率和新增数据（每月 1.25 GB），所需时间为 6 小时。

在少数情况下，实际文本数据高达数 TB，此时需要 Provisioned Throughput 来生成文本嵌入。例如，要在 3 天、6 天和 9 天内为 500 GB 数据生成文本嵌入，使用 Provisioned Throughput 的一次性成本分别约为 60,000 美元、33,000 美元或 24,000 美元。

通常，文件中的实际文本比 Amazon S3 或文件系统报告的文件大小小 5–10 倍。因此，当你看到所有需要向量化的文件大小为 100 GB 时，文件中的实际文本很可能只有 2–20 GB。

估算文件内文本大小的一种方法是按以下步骤操作：

- 挑选 5–10 个有代表性的文件样本。
- 打开文件，复制内容，并粘贴到 Word 文档中。
- 使用字数统计功能确定文本大小。
- 计算该大小与文件系统报告大小的比率。
- 把该比率应用到整个文件系统，得到所有文件内实际文本大小的方向性估计。

### 向量数据库成本

AWS 提供许多向量数据库，例如 OpenSearch Service、Aurora、Amazon RDS 和 MemoryDB。如本文前面所述，向量数据库在把响应锚定到企业数据方面起着关键作用，这些数据的向量嵌入就存储在向量数据库中。

以下是影响向量数据库成本的一些因素。为简洁起见，我们把 OpenSearch Service 预置集群作为向量数据库。

- 用作知识库的数据量 —— 成本与数据规模成正比。数据越多意味着向量越多。向量越多意味着向量数据库中的索引越多，这反过来需要更多内存，因而成本更高。为获得最佳性能，建议为向量数据库设定足够容量，使所有向量都存储在内存中。
- 索引压缩 —— 向量嵌入可以用 HNSW 或 IVF 算法建立索引。索引也可以压缩。虽然压缩索引可以减少内存需求和成本，但可能损失准确性。因此，在决定使用 HNSW 或 IVF 的压缩变体之前，应考虑做大量准确性测试。例如，对于 100 GB 的大文本数据，假设块大小为 2,000 字节、重叠 15%、向量维度数为 512、无预付的 3 年 Reserved Instance，并使用 HNSW 算法，粗略成本为每年 37,000 美元。使用 hnsw-fp16 和 hnsw-pq 压缩的对应成本分别为每年 21,000 美元和 10,000 美元。
- Reserved Instances —— 成本与为存储向量数据库的集群实例预留的年数成反比。例如，在前述场景中，On-Demand 实例每年约需 75,000 美元，无预付 1 年 Reserved Instance 每年 52,000 美元，无预付 3 年 Reserved Instance 每年 37,000 美元。

其他因素，例如你从向量数据库检索并作为上下文传给 LLM 的次数，会影响输入 token，从而影响成本。但总体而言，上述因素是最重要的成本驱动因素。

### Amazon Bedrock Guardrails

假设你的生成式 AI 虚拟助手要在网站上为客户回答与你产品相关的问题。你如何避免用户提出科学、宗教、地理、政治或谜题这类离题问题？你如何避免回答关于仇恨、暴力或种族的用户问题？又如何在问题和响应中检测并脱敏 PII？

Amazon Bedrock 的 [ApplyGuardrail API](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-use-independent-api.html) 可以帮助你解决这些问题。Guardrails 提供多种策略，例如内容过滤器、拒绝主题、上下文锚定检查和敏感信息过滤器（PII）。你可以选择性地把这些过滤器应用到全部数据或特定部分数据，例如 user prompt、system prompt、知识库上下文和 LLM 响应。

对所有数据应用所有过滤器会增加成本。因此，你应仔细评估要在哪部分数据上应用哪个过滤器。例如，如果你希望从 LLM 响应中检测或脱敏 PII，对于每月 200 万个问题，粗略成本（基于本文前面提到的输出 token）为每月 200 美元。此外，如果你的安全团队还希望对用户问题进行 PII 检测或脱敏，Amazon Bedrock Guardrails 的总成本将是每月 400 美元。

### 分块策略

如前面介绍 RAG 工作原理时所述，你的数据被分块，为这些块生成嵌入，块和嵌入都存储在向量数据库中。这些数据块随后被检索出来，与用户问题一起作为上下文传给 LLM，以生成有依据且相关的响应。

以下是不同的分块策略，每一种都可能影响成本：

- 标准分块 —— 在这种情况下，你可以指定默认分块（约 300 个 token），或使用固定大小分块，即你为每个块指定 token 大小（例如 300 个 token）。块越大，输入 token 越多，成本也就越高。
- 分层分块 —— 当你希望以较小的尺寸分块（例如 300 个 token），但把更大的块片段（例如 1,500 个 token）发送给 LLM，让 LLM 在生成响应时有更大的上下文可用时，这种策略很有用。虽然这在某些情况下能提高准确性，但也可能因为发送给 LLM 的数据块更大而增加成本。
- 语义分块 —— 当你希望按语义而非仅按 token 分块时，这种策略很有用。在这种情况下，会为一个或三个句子生成向量嵌入。使用滑动窗口考虑下一个句子并重新计算嵌入，以判断下一个句子在语义上是否相似。该过程持续进行，直到达到 token 上限（例如 300 个 token）或遇到语义不相似的句子。这个边界就定义了一个块。发送给 LLM 的输入 token 成本与标准分块相似（基于最大 token 大小），但由于块内的句子语义相似，准确性可能更好。不过，这会增加生成向量嵌入的成本，因为既要为每个句子生成嵌入，之后还要为每个块生成嵌入。但与此同时，这些是一次性成本（以及针对新增或变更数据的成本），如果你的数据在准确性上相对更好，这或许是值得的。
- 高级解析 —— 这是分块策略的可选前置步骤。它用于识别块的边界，当你处理的文档包含表格、图像和文本等大量复杂数据时尤其有用。因此，成本将是你要用于向量嵌入的整个数据的输入和输出 token 成本。这些成本会很高。可考虑只对包含大量表格和图像的文件使用高级解析。
