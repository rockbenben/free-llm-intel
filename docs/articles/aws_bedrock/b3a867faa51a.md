# 通过 Amazon Bedrock Managed Knowledge Base 中的 tabular search 从表格中获取答案

[Amazon Bedrock Managed Knowledge Base](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-build-managed.html) 现已支持 tabular search，因此你可以通过 agentic retrieval 从表格中获取答案。当问题需要来自 CSV、XLSX 或 XLS 文件的数据时，tabular search 会在一张或多张表、一个或多个 sheet 的每一相关行上查找值并执行计算，然后把结果与相关文档中的事实结合起来，回答需要多步完成的分析性问题。

一个正在做季度结账的财务团队需要知道：“哪些部门必须撰写差异说明？”没有任何一个文件能给出答案。它取决于差异政策的阈值、季度结账备忘录中的预算修订，以及对损益（P&L）工作簿中每个部门所做的计算。

像这个财务团队一样，大多数团队都把叙述和数据放在同一个地方。例如，一个 Microsoft SharePoint 站点会把工作簿和政策放在一起，一个 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/) 存储桶会把 CSV 导出文件和 PDF 放在一起。tabular search 通过你已经在用的同一个 `AgenticRetrieveStream` 请求，跨这些文件回答问题。它在隔离的 sandbox 中对原始文件运行代码，因此答案使用整张表，而不只是检索返回的那些行。对这个财务团队来说，一次请求就能返回必须撰写差异说明的部门。答案会引用政策和备忘录，trace 则会指明代码读取的是哪个工作簿。

在本文中，你会了解 tabular search 如何回答既需要表格数据、又需要文档事实的问题，以及什么时候换另一个工具更合适。你还会用示例财务文件构建一个知识库，并通过 trace 查看代码读取了哪个文件。

## 为什么表格难做检索

检索增强生成（RAG）返回与问题最匹配的固定数量的段落，这对散文类文本很有效。表格在被切分成段落时会丢失信息，丢失方式取决于表格的形状：

- **长表——** 一张有数千行的表会横跨许多段落，而检索只返回与问题最匹配的少数几段。用它们构建的答案只会用到少量行，因此一个总计、一次比较或一次阈值检查可能并不完整。
- **宽表——** 在一张有数百列的表里，单独一行所包含的文本就可能超过一个段落或一个搜索模型一次能处理的内容。因此，靠后列中的值更难被匹配。来自宽表的长段落还可能匹配到许多不相关的问题，把更相关的段落挤出结果。

检索还必须把问题匹配到正确的表。问题用的是业务术语，比如“可控支出”，而表里存的却是成本中心代码、科目名称和数字。草稿工作簿和最终工作簿在搜索看来几乎一样。赋予这些数字含义的规则，往往在另一份文档里，比如一份政策。

因此 tabular search 把工作拆开：检索只需返回来自正确表格文件的一个段落，然后由代码读取整张表。由于检索仍须先找到那个文件，在问题里点出文件名会有帮助。

表 1 展示了普通检索和 tabular search 分别如何处理财务团队的问题“哪些部门必须撰写差异说明？”

| **对比项** | **仅检索** | **带 tabular search 的 agentic retrieval** |
| --- | --- | --- |
| 得到的结果 | 来自政策、备忘录、业务复盘和工作簿的段落，但没有完整答案 | 一个点名 Sales、Engineering 和 Operations 部门，并给出每个部门相对修订后预算差异的答案 |
| 修订后的差异百分比 | 不可得。没有任何文件存着这些数字，所以也不可能有段落包含它们 | 根据最终工作簿中每个部门的行计算得出 |
| 来源 | 每个段落链接到各自的文件，但没有一个包含答案 | 对财务政策和结账备忘录的引用。trace 指明代码读取的工作簿 |

*表 1：同一个问题分别用普通检索和 tabular search 处理。*

## tabular search 在 agentic retrieval 中如何工作

在 [agentic retrieval](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html) 中，agent 用检索来决定哪些文档重要，然后撰写答案。tabular search 是这条流程的一部分，因此不需要打开什么开关。

当问题需要表格中的数据时，请求会经过这些阶段：

- **Retrieve（检索）——** 返回段落，其中包括来自某个表格文件的段落。
- **Plan（规划）——** agent 用问题和表格结构来判断是否要对一张或多张检索到的表运行代码。
- **Stage（准备）——** tabular search 把原始文件复制到一个没有网络访问的隔离 sandbox 中。
- **Compute（计算）——** 模型编写的代码在整张表或整个 sheet 上运行。
- **Return（返回）——** agent 只拿回代码打印出来的内容，比如总计或匹配的行。
- **Answer（作答）——** agent 基于结果和段落作答，并附上引用。

当检索到的段落来自 CSV、XLSX 或 XLS 文件，且问题需要跨行计算或查找特定值时，tabular search 就会启动。

### 知识库、connector 与 API

一个 `AgenticRetrieveStream` 请求可以搜索一个或多个知识库。`Retrieve` API 则继续只返回段落，不运行代码。

无论用哪个 [connector](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-create.html#kb-managed-connectors) 把文件带进知识库——包括 Amazon S3、Microsoft SharePoint、Atlassian Confluence 等——tabular search 的工作方式都相同。

### 范围与权衡

tabular search 是为那些需要针对其检索到的表格文件做计算或查找的问题而构建的。运行代码至少会增加一个 agent 轮次，所以使用表格数据的答案会比纯文本答案慢。受治理的指标、周期性仪表盘、仓库规模的 join 和报表控制仍应交给你的商业智能（BI）工具。tabular search 处理与文档存放在一起的表格文件，而且你无需定义 schema。

## 先决条件

你需要以下条件：

- 创建 AWS Identity and Access Management（IAM）角色、S3 存储桶和 Amazon Bedrock 知识库的权限。
- 对于调用 `AgenticRetrieveStream` 的身份，需要 [agentic retrieval 所需权限](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html)，包括 `bedrock:GetDocumentContent`。agent 用调用者的凭证读取原始表格文件。
- 在 tabular search 可用的 AWS Region 中使用 Amazon Bedrock。关于 Region 可用性，参见[支持的 AWS Region](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-regions.html)。
- 你自己的 CSV、XLSX 或 XLS 文件及相关文档。
- 如果想跟着走一遍：Python 3.10 或更高版本，以及 AWS SDK for Python（Boto3）1.43.123 或更高版本。你也可以在 Amazon Bedrock 控制台的知识库测试窗口里提问，或使用 AWS Command Line Interface（AWS CLI）。

## 把文件上传到 Amazon S3

把表格文件和相关文档放在同一个前缀下。

- 打开 Amazon S3 控制台，选择 **Create bucket**。
- 输入一个全局唯一的存储桶名称（本文使用 `amzn-s3-demo-bucket`），保持 **Block all public access** 选中，然后选择 **Create bucket**。
- 选择该存储桶，选择 **Create folder**，输入 `finance`。
- 打开 `finance` 文件夹，选择 **Upload**。
- 选择 **Add files**，选中你的表格文件和文档，然后选择 **Upload**。

## 创建知识库和数据源

知识库需要一个 Amazon Bedrock 可以代入的 IAM 角色。这个信任策略只允许 `bedrock.amazonaws.com` 服务主体，且仅限你账户中的知识库。

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BedrockKnowledgeBaseAssume",
      "Effect": "Allow",
      "Principal": {"Service": "bedrock.amazonaws.com"},
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {"aws:SourceAccount": "111122223333"},
        "ArnLike": {
          "aws:SourceArn": "arn:aws:bedrock:<region>:111122223333:knowledge-base/*"
        }
      }
    }
  ]
}
```

接下来，设置其余资源：

- 用该信任策略创建一个名为 `kb-finance-role` 的角色。
- 附加一条内联策略，允许对存储桶执行 `s3:ListBucket`，对其中的对象执行 `s3:GetObject`。
- 用托管 embedding 模型创建一个类型为 `MANAGED` 的知识库。
- 为该存储桶创建一个 `MANAGED_KNOWLEDGE_BASE_CONNECTOR` 数据源，限定在 `finance/` 前缀。
- 把 `maxFileSizeInMegaBytes` 设为大于你最大的文件。

第 2 步的内联策略只允许读取这个存储桶：

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::amzn-s3-demo-bucket",
      "Condition": {"StringEquals": {"aws:ResourceAccount": "111122223333"}}
    },
    {
      "Sid": "ReadObjects",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::amzn-s3-demo-bucket/*",
      "Condition": {"StringEquals": {"aws:ResourceAccount": "111122223333"}}
    }
  ]
}
```

这个脚本执行第 3 到第 5 步并打印 ID：

```
import time
import boto3

agent = boto3.client("bedrock-agent")

kb = agent.create_knowledge_base(
    name="finance-kb",
    roleArn="arn:aws:iam::111122223333:role/kb-finance-role",
    knowledgeBaseConfiguration={
        "type": "MANAGED",
        "managedKnowledgeBaseConfiguration": {"embeddingModelType": "MANAGED"},
    },
)
kb_id = kb["knowledgeBase"]["knowledgeBaseId"]

# Wait until the knowledge base is ACTIVE before adding a data source.
status = "CREATING"
while status in ("CREATING", "UPDATING"):
    time.sleep(10)
    status = agent.get_knowledge_base(knowledgeBaseId=kb_id)["knowledgeBase"]["status"]
if status != "ACTIVE":
    raise RuntimeError(f"Knowledge base status is {status}")

ds = agent.create_data_source(
    knowledgeBaseId=kb_id,
    name="finance-s3",
    dataSourceConfiguration={
        "type": "MANAGED_KNOWLEDGE_BASE_CONNECTOR",
        "managedKnowledgeBaseConnectorConfiguration": {
            "connectorParameters": {
                "type": "S3",
                "version": "1",
                "connectionConfiguration": {
                    "bucketName": "amzn-s3-demo-bucket",
                    "bucketOwnerAccountId": "111122223333",
                },
                "filterConfiguration": {
                    # In MB. Set this above your largest table.
                    "maxFileSizeInMegaBytes": "200",
                    "inclusionPrefixes": ["finance/"],
                },
                "aclEnabled": False,
            }
        },
    },
    vectorIngestionConfiguration={
        "parsingConfiguration": {"parsingStrategy": "SMART_PARSING"}
    },
)
print("knowledge base:", kb_id, "data source:", ds["dataSource"]["dataSourceId"])
```

## 同步数据源并检查文件类型

只有当知识库分配了正确的文件类型，tabular search 才能启动，所以在第一次同步后检查文件类型。

- 为该数据源启动一个摄取任务。
- 轮询该任务，直到其状态为 `COMPLETE`。
- 查看任务统计中失败的文档。
- 用你的问题运行一次 `Retrieve` 调用。
- 确认表格段落的 `_file_type` 显示为 `CSV`（CSV 文件）或 `MS_EXCEL`（XLSX 和 XLS 文件）。

第一个脚本执行第 1 到第 3 步：

```
import time
import boto3

agent = boto3.client("bedrock-agent")
KB_ID, DS_ID = "<your-knowledge-base-id>", "<your-data-source-id>"

job_id = agent.start_ingestion_job(knowledgeBaseId=KB_ID, dataSourceId=DS_ID)[
    "ingestionJob"]["ingestionJobId"]
while True:
    job = agent.get_ingestion_job(
        knowledgeBaseId=KB_ID, dataSourceId=DS_ID, ingestionJobId=job_id
    )["ingestionJob"]
    if job["status"] in ("COMPLETE", "FAILED", "STOPPED"):
        break
    time.sleep(15)
print(job["status"], job.get("statistics"), job.get("failureReasons"))
```

第二个脚本执行第 4 和第 5 步，让你在用 agentic retrieval 提问之前检查表格文件类型。用你自己的文件时，问一个把某份文档中的规则与对你表格的计算配对起来的问题，并把两者都点名。

```
import boto3

runtime = boto3.client("bedrock-agent-runtime")
question = (
    "In fiscal Q2 of FY2026, which cost center had the largest overspend in "
    "controllable spend, as the finance policy defines it? Compare the Actuals "
    "and Budget sheets of the FY2026 P&L workbook and give the cost center and "
    "the overspend in US dollars."
)
response = runtime.retrieve(
    knowledgeBaseId="1234567890",
    retrievalQuery={"text": question},
    retrievalConfiguration={"managedSearchConfiguration": {"numberOfResults": 10}},
)
for result in response["retrievalResults"]:
    print(result["metadata"].get("_file_type"), result.get("documentId"))
```

## 跨表格和文档提问

通过 `AgenticRetrieveStream` 发送同一个问题。脚本会打印答案、每个 `CodeExecution` 状态，以及代码读取的文件。

```
import boto3

runtime = boto3.client("bedrock-agent-runtime")
question = (
    "In fiscal Q2 of FY2026, which cost center had the largest overspend in "
    "controllable spend, as the finance policy defines it? Compare the Actuals "
    "and Budget sheets of the FY2026 P&L workbook and give the cost center and "
    "the overspend in US dollars."
)

response = runtime.agentic_retrieve_stream(
    messages=[{"role": "user", "content": {"text": question}}],
    retrievers=[{"configuration": {"knowledgeBase": {"knowledgeBaseId": "1234567890"}}}],
    agenticRetrieveConfiguration={
        "foundationModelType": "MANAGED",
        "rerankingModelType": "MANAGED",
    },
)

for event in response["stream"]:
    if "traceEvent" in event:
        attributes = event["traceEvent"]["attributes"]
        # CodeExecution steps report IN_PROGRESS, then SUCCEEDED or FAILED.
        if attributes.get("step") == "CodeExecution":
            print(attributes["status"], attributes.get("message"))
        # A Planning event lists the files the code will read.
        for action in attributes.get("actions", []):
            for doc in action.get("codeExecution", {}).get("documents", []):
                print("code read:", doc["documentId"])
    elif "responseEvent" in event:
        print(event["responseEvent"]["text"], end="")
```

对这些文件来说，答案把两张工作簿表格和两份文档结合了起来：

- **来自文档。** 财务政策把可控支出定义为 Contractors、Travel、Software 和 Marketing Programs 四个科目，因而不包括薪资和设施。业务复盘解释了主要的差异。
- **来自表格。** 代码使用 Actuals 和 Budget sheet 中的每一行，把两者都过滤到财季 Q2 和这四个科目，然后比较成本中心。
- **答案。** CC-3010（Platform）超支 124,559.90 美元，实际支出 394,859.90，预算为 270,300.00。业务复盘把这笔差异归因于为数据平台迁移而引入的承包商。如果把所有运营费用科目都算上，结果则是 133,434.05。

## 解读 trace

trace 事件按以下顺序到达：

- **Planning。** 一个状态为 `SUCCEEDED` 的 `Planning` 事件包含一个 `codeExecution` action，其中点名代码将要读取的文档。
- **代码步骤。** 先是一个状态为 `IN_PROGRESS` 的 `CodeExecution` 事件（“Running code over 1 document(s)”），然后是一个状态为 `SUCCEEDED` 的事件。`SUCCEEDED` 消息会点名代码读取的每个文件及其大小。
- **答案。** 第二轮规划与响应文本之后，是一个包含引用的最终 `result` 事件。引用指向答案用到的段落，所以代码读取的某个表格文件并不总在其中。

在这个例子中，`Planning` 事件只点名了那个最终工作簿，因为政策和业务复盘是作为检索到的段落到达的。

```
{
  "traceEvent": {
    "attributes": {
      "step": "Planning",
      "status": "SUCCEEDED",
      "message": "Agent planning completed",
      "actions": [
        {
          "retrieve": {},
          "codeExecution": {
            "documents": [
              {
                "documentId": "s3://amzn-s3-demo-bucket/finance/anycompany-pnl-fy2026.xlsx",
                "sourceRetriever": {"identifier": "1234567890"}
              }
            ]
          }
        }
      ]
    }
  }
}
```

在更长的调用中，流每 10 秒重复一次 `IN_PROGRESS` 事件，这样读超时就不会触发。无法完成的代码步骤会报告 `FAILED`，agent 通常会重试或回退。

tabular search 作为响应生成的一部分运行，而响应生成默认开启，所以脚本没有设置 `generateResponse`。如果你把 `generateResponse` 设为 false，agent 会返回检索结果而不运行代码。详情参见 [agentic retrieval](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html)。

## 尝试更多问题

下面每个问题也都把一份文档与工作簿配对起来。

### 把备忘录中的修订应用到季度总计

这个问题需要一个只有在备忘录修订之后才存在的预算：

```
Did total operating expense for fiscal Q3 of FY2026 stay within the Q3 budget
as revised in the Q3 close memo? Give the actual Q3 operating expense, the
revised Q3 budget and the difference, in US dollars.
```

答案使用备忘录中的修订，以及工作簿中的 Q3 实际值和原始预算。支出比修订后的预算低了 49,572.40 美元，所以答案是肯定的，尽管同一笔支出超出了原始预算。普通的 `Retrieve` 会返回备忘录和工作簿的段落，但其中没有任何一段包含这些数字。

### 在预算修订之后应用政策阈值

以下是开头那个财务团队问题的完整版本。它需要政策的阈值、备忘录的修订以及工作簿：

```
Applying the budget revisions approved in the Q3 close memo, which
departments must write variance commentary for fiscal Q3 of FY2026 under
the finance policy?
```

政策要求：当差异超过已批准预算（包含已批准的修订）的 5% 时就必须撰写说明，而备忘录批准了一笔 Marketing 的增加和一笔 Engineering 的削减。答案是 Sales（-6.50%）、Engineering（+5.79%）和 Operations（+6.20%）。Engineering 之所以越过阈值，只是因为获批的削减压低了它的预算。

### 继续对话

tabular search 也能在多轮对话中工作。把先前的轮次放进 `messages`，它就会在需要表格的那一轮运行。第一个问题要求从工作簿做一次计算：

```
Calculate the Customer Support department's actual operating expense and its
budget for fiscal Q2 of FY2026 from the Actuals and Budget sheets of the final
FY2026 P&L workbook, in US dollars.
```

对于追问，把第一个问题、它的答案（`"role": "assistant"`）和新问题都放进 `messages`：

```
Under the finance policy, does that variance need written commentary, and does
anyone besides the Controller have to review it?
```

差异为超预算 12.40%，因此需要书面说明。因为它超过 10%，政策还要求由 CFO Nikki Wolf 评审。在这里，第一轮通常会在工作簿上运行代码，第二轮则根据历史记录回答政策问题。

对于更长的会话，你可以通过在请求上设置 `memoryConfiguration`，把对话历史保存在一个 Amazon Bedrock AgentCore memory 资源中，而不必重新发送先前的轮次。详情参见 [agentic retrieval](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html)。

## 面向表格提问的最佳实践

提问时要斟酌措辞，因为检索决定了代码读哪张表。点名来源的聚焦问题有助于检索选对表。

- **一条规则配一张表。** 点名承载该规则的文档，比如“按 Q3 结账备忘录中的修订”。
- **存在多个版本时点名文件。** 例如“使用最终的 FY2026 P&L 工作簿，anycompany-pnl-fy2026.xlsx”。
- **需要计算时就明确要求计算。** 如果某个汇总 sheet 存着某个数字，agent 可以直接从它作答。要说“从 Actuals 和 Budget sheet 计算每个部门的差异”，才会从明细行计算。
- **提聚焦的问题。** 把更大的分析拆到多轮里完成。

一些数据和应用层面的选择也有帮助：

- **把表格保留在 CSV、XLSX 或 XLS 文件中。** 先从 PDF 或 Word 文档中导出表格。
- **把文件大小过滤器设得高于你最大的表。** 大于 `maxFileSizeInMegaBytes` 的文件不会被摄取，因此代码无法读取它们。
- **让 Excel sheet 保持在 200 MB 以内。** 截至本文写作时，tabular search 对 CSV 文件最多可对 500 MB 运行代码（即摄取上限），但对 Excel sheet 最多只支持 200 MB。你仍然可以摄取更大的 Excel 文件，所以在依赖整表计算之前，先检查 sheet 大小。
- **用 tabular search 做分析。** 运行代码会增加一个 agent 轮次，所以文本里的快速查找继续用普通的 `Retrieve`。
- **用元数据过滤器限定文件范围。** `retrievalOverrides` 下的过滤器（例如针对 `_document_title`）控制代码可以读取哪些文件。
- **用 trace 审计。** 生成的代码按设计不会返回，因为它可能会回显单元格里的值。trace 会显示代码读取了哪些文件。

## 清理

为避免持续产生费用，请按顺序删除这些资源：

- 在 Amazon Bedrock 控制台中，选择 **Knowledge Bases**，然后选择 `finance-kb`。
- 选中 `finance-s3` 数据源，选择 **Delete**。
- 删除 `finance-kb` 知识库。
- 在 Amazon S3 控制台中，选中该存储桶，选择 **Empty**，然后选择 **Delete**，除非还有其他工作负载在用它。
- 在 IAM 控制台中，选择 **Roles**，选中 `kb-finance-role`，然后选择 **Delete**。

如果你是用仓库中的 AWS CDK 应用部署的，请在其 `infra` 文件夹中运行 `npx cdk destroy`，来代替这些步骤。它会删除该 stack 创建的所有内容。

## 结论

财务团队的成员需要知道“哪些部门必须撰写差异说明？”借助 Amazon Bedrock Managed Knowledge Base 中的 tabular search，你可以用一个 agentic retrieval 请求回答这个问题，把工作簿、政策和备忘录一起用上。

在本文中，你了解了 tabular search 如何回答既需要表格数据、又需要文档事实的问题，以及什么时候换另一个工具更合适。你还用示例财务文件构建了一个知识库，并通过 trace 查看代码读取了哪个文件。

要开始使用，请参阅 Amazon Bedrock 用户指南中的[构建托管知识库](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-build-managed.html)和 [agentic retrieval](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html)，以及 Amazon Bedrock API Reference 中的 [AgenticRetrieveStream](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_AgenticRetrieveStream.html)。想了解更多，请阅读 AWS Artificial Intelligence 博客上的[用 Amazon Bedrock Managed Knowledge Base 为 agents 构建企业搜索](https://aws.amazon.com/blogs/machine-learning/build-enterprise-search-for-agents-with-amazon-bedrock-managed-knowledge-base/)。
