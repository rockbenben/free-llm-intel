# 在 AWS 上使用 A2A 构建可组合、可互操作的多代理系统

跨越组织边界的多代理系统中的代理通常需要以可组合、可互操作的方式与其他组织构建和运行的代理进行协作。他们需要一种方式来发现对方、沟通和交换任务，而不暴露内部结构或要求双方使用相同的框架。

代理到代理 (A2A) 协议解决了这一限制。如果没有 A2A，跨组织边界构建可组合的多代理系统需要为每个客户和框架定制集成代码。独立软件供应商 (ISV) 可以构建可组合、可互操作的代理，与客户已经使用的 A2A 兼容框架配合使用。

虽然我们围绕 ISV 用例构建这篇文章，但该模式也适用于跨边界公开代理的组织，无论是向合作伙伴、客户还是使用不同框架的内部团队。随着系统的发展，您可以通过向协调器注册代理卡来添加技能，而无需更改已运行的代理。

在这篇文章中，我们将介绍在 AWS 上部署的参考架构。基于 LangChain 的企业协调器使用 A2A 与基于 Strands Agents 的软件即服务 (SaaS) 代理跨组织边界进行通信，企业和 SaaS 提供商位于不同的 AWS 账户中。双方都不依赖对方的框架或 SDK，双方没有秘密。我们介绍架构和实现模式，然后从三个 Jupyter 笔记本部署系统并运行端到端测试。

[A2A 协议现在是 Linux 基金会项目](https://www.linuxfoundation.org/press/linux-foundation-launches-the-agent2agent-protocol-project-to-enable-secure-intelligent-communication- Between-ai-agents)，AWS 是支持它的组织之一。借助 A2A，代理可以通过标准化协议发现彼此、协商任务并跨组织边界进行协作。该协议使用 OAuth 2.0 和 OpenID Connect (OIDC) 等现有身份验证标准来实现跨界安全，并且旨在跨 A2A 兼容框架工作。

在[代理互操作性开放协议第 4 部分：A2A 上的代理间通信](https://aws.amazon.com/blogs/opensource/open-protocols-for-agent-interoperability-part-4-inter-agent-communication-on-a2a/) 中，我们介绍了 A2A 概念并演示了两个在 AWS 上使用该协议进行通信的 Strands 代理。这篇文章为代理卡发现、结构化任务执行和 A2A 服务器模式奠定了基础。这篇文章建立在跨框架互操作性、跨组织信任边界和双向 OAuth 的基础上。

## 解决方案概述

三个代理在两个 AWS 账户中运行，一个用于企业，另一个用于 SaaS 提供商。 A2A 协议将它们连接起来，并在两个方向上进行 OAuth 身份验证。每个账户都有自己的 [Amazon Cognito](https://aws.amazon.com/cognito/) 用户池，因此每一方都使用自己的身份提供商进行身份验证。

在加入期间，企业和 SaaS 提供商仅交换公共值，例如身份提供商 URL、客户端 ID、范围和端点 URL。然后，每一方都信任对方用户池中的令牌，并且不会共享任何秘密。

入职后，每个请求都遵循以下步骤：

- 企业应用程序从企业的 Amazon Cognito 用户池获取访问令牌。
- 应用程序通过 HTTPS 向 Amazon API Gateway 中的用户 API 发送问题，然后轮询答案。
- [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 通过 VPC 链接和内部网络负载均衡器私下将请求转发到 Enterprise Orchestrator（LangChain 代理）。
- 当其模型确定问题需要合规性扫描时，编排器会使用存储在 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 中的客户端密钥从企业用户池获取自己的令牌。
- 协调器使用在启动时从代理的代理卡中读取的技能，向 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 运行时上的合规 SaaS 代理发送 A2A 请求。
- 合规代理在入职时注册的回调 URL 处检查企业上下文代理的代理卡，然后从 SaaS 提供商自己的池中获取令牌。
- 合规代理回调企业上下文代理以获取帐户元数据，完成扫描，并将答案返回到协调器，然后返回到应用程序。

在企业端，两个代理在 [Amazon Elastic Container Service](https://aws.amazon.com/ecs/) (Amazon ECS) 和 [AWS Fargate](https://aws.amazon.com/fargate/) 上运行。 Enterprise Orchestrator 是用户的入口点。 LangChain 提供代理框架和工具调用抽象，而 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 提供支持每个代理推理的基础模型 (FM)。编排器使用 LangChain 和 Amazon Bedrock (Anthropic Claude Sonnet 4.6)。启动时，编排器从众所周知的 URL 获取 SaaS 代理的代理卡，并为卡上描述的每项技能创建一个 LangChain 工具。然后，模型根据用户的问题决定调用哪个工具，因此编排器不需要硬编码的路由逻辑。它使用 OAuth 不记名令牌通过 A2A 发送合规性扫描请求，并为领导层总结结果。用户通过 Amazon API Gateway HTTPS 终端节点访问编排器，该终端节点仅接受来自企业自己的池的令牌。

第二个企业代理提供内部上下文。 Enterprise Context Agent 使用 LangChain 和 Amazon Bedrock (Amazon Nova Lite) 构建。它提供内部帐户元数据，例如内部策略规则、数据分类、业务关键性和升级联系人（团队待命轮换）。部署的代理使用官方 a2a-sdk（AgentCard、AgentExecutor 和符合规范的 JSON-RPC 路由），固定到 a2a-sdk[http-server]==1.2.2。 SaaS 代理通过仅接受 SaaS 提供商的回调令牌的 API 网关合作伙伴 API 到达上下文代理。

两个企业代理都在 [Amazon Virtual Private Cloud](https://aws.amazon.com/vpc/) (Amazon VPC) 的私有子网中运行，没有公共 IP 地址。

在 SaaS 提供商方面，Compliance SaaS Agent 在 SaaS 提供商自己的 AWS 账户中的 Amazon Bedrock AgentCore 上运行。它使用 [Strands Agents SDK](https://strandsagents.com/) 构建，根据企业自己的内部策略检查 AWS 账户，例如生产中不存在公共存储以及机密数据的静态加密。在生产中，扫描工具将连接到 [AWS Config](https://aws.amazon.com/config/)、[AWS Security Hub](https://aws.amazon.com/security-hub/) 或 [Amazon GuardDuty](https://aws.amazon.com/guardduty/) 等服务。在此演示中，代理使用合成数据来模拟多个帐户的合规性结果。

在扫描之前，SaaS 代理会回调企业上下文代理以了解企业上下文，例如哪些帐户是生产帐户、应用哪些内部策略以及要升级到谁。这种双向模式使代理成为真正的对等体，而不是客户端和服务器。回调仅发送至客户在入职时注册的地址。

关键的设计决策是使用 A2A 进行所有跨界通信。企业无法访问SaaS代理的内部工具、系统提示或模型选择。这种分离意味着 ISV 可以在不改变客户集成的情况下改变其内部架构，只要其代理卡和 A2A 接口保持兼容。 SaaS 卡发布一项精选技能，而不是其内部工具名称。

Amazon Bedrock 提供对多个基础模型的 API 访问，因此每个代理都可以使用适合其工作负载的模型。在此解决方案中，编排器和 SaaS 代理使用 Anthropic Claude Sonnet 4.6 进行复杂推理，而上下文代理使用 Amazon Nova Lite 进行元数据查找。您可以根据自己的需求选择不同的型号。

A2A 和模型上下文协议 (MCP) 解决了该架构中的不同问题。 MCP 在客户端-服务器模型中将代理连接到其自己的工具和数据源。 A2A 将代理与其他代理作为对等体连接，双方都不会暴露其内部结构。在生产中，SaaS 代理可以在内部使用 MCP 连接到其合规性扫描工具，同时通过 A2A 将自身暴露在外部。无论代理如何连接到其内部工具，外部接口都保持不变。

## 实施解决方案

使用三个笔记本部署系统，使用 Jupyter 按顺序运行，一次运行一个单元。笔记本 1（企业帐户，大约 3 分钟）创建企业身份并编写入职请求。笔记本 2（SaaS 提供商帐户，大约 5 分钟）部署合规代理并编写加入响应。笔记本 3（企业帐户，大约 20 分钟）部署企业代理并运行测试。入职文件仅包含公共值。

- 克隆 [GitHub 存储库](https://github.com/aws-samples/sample-a2a-cross-org-agents)，并设置两个用于本地运行的 AWS 配置文件，或每个帐户一个笔记本实例，并将存储库克隆到每个帐户。
- 在企业帐户中运行笔记本1。
- 将“onboarding-request.json”提供给 SaaS 提供商。
- 在 SaaS 提供商帐户中运行笔记本 2。
- 将“onboarding-response.json”返还给企业。
- 在企业帐户中运行笔记本3。
- 测试后，运行笔记本 3 的 Clean up，然后运行笔记本 2 的。

以下部分解释了部署背后的关键实现模式。它们共同展示了三种功能：

- **跨框架的互操作性 –** LangChain 编排器使用 A2A 调用 Strands 代理，双方都不依赖于对方的 SDK。
- **跨组织边界的可组合性 –** ISV 的合规代理和企业的上下文代理组成一个工作流程，这两个团队都不是单独构建的。
- **与 OAuth 双向协作 –** 代理充当对等方，通过基于令牌的身份验证跨信任边界相互调用。

借助 A2A，此场景中的 ISV 用单个基于协议的接口取代了多个自定义集成路径。

## 构建 SaaS 合规代理

使用 Strands Agents SDK 构建 ISV 的合规代理并将其部署到 Amazon Bedrock AgentCore。对于此演示，扫描工具返回综合合规性结果。

该代理使用 Strands @tool 装饰器公开三个合规性工具（列出可用帐户、运行合规性扫描和检索补救步骤），以及第四个回调企业的合规性工具，这将在下一节中介绍。代理卡没有列出这些工具。它发布了一项精心策划的技能，因此呼叫者的模型可以看到产品的功能，而不是它的构建方式。这个简化的示例显示了扫描工具：
```
from strands import Agent, ToolContext, tool
from strands.models.bedrock import BedrockModel
from strands.multiagent.a2a import A2AServer

@tool
def run_compliance_scan(account_id: str) -> dict:
    """Run a compliance scan on a specific AWS account.

    Args:
        account_id: The AWS account ID to scan (e.g., acc-12345)
    """
    if account_id not in ACCOUNTS:
        return {"error": f"Account {account_id} not found."}
    findings = COMPLIANCE_FINDINGS.get(account_id, [])
    non_compliant = [f for f in findings if f["status"] == "NON_COMPLIANT"]
    return {
        "account_id": account_id,
        "account_name": ACCOUNTS[account_id]["name"],
        "scan_summary": {
            "total_rules_checked": len(findings),
            "compliant": len(findings) - len(non_compliant),
            "non_compliant": len(non_compliant),
            "critical_findings": len([f for f in non_compliant if f["severity"] == "CRITICAL"]),
            "high_findings": len([f for f in non_compliant if f["severity"] == "HIGH"]),
        },
        "findings": findings,
    }
```
### 启用双向回调

这就是该解决方案超越典型代理集成的地方。大多数代理到代理演示都显示单向请求和响应，其中客户端代理调用服务器代理并等待结果。当被叫座席需要只有呼叫者拥有的信息时，这种模式就会崩溃。在生产中，代理需要是可以互相调用的对等体。

SaaS 合规代理需要企业环境。示例包括哪些账户是生产账户、适用哪些内部政策以及要升级给谁。这是只有企业拥有的信息。

SaaS 代理通过 A2A 进行回调，但仅限于客户在入职时注册的回调 URL。它首先验证客户的公共上下文卡，然后从 SaaS 提供商自己的 Cognito 池获取令牌，并将消息/发送到企业合作伙伴 API：
```
def _call_enterprise_context(message_text: str, inbound_task_id: str = "-") -> str:
    if not CALLBACK_URL_VALID: # checked once at import
        raise CallbackUnavailable("CALLBACK_URL is not a registered callback URL")
    cfg = _load_callback_config() # this SaaS provider's own client, from Secrets Manager
    _verify_context_card(cfg) # anonymous GET of the card at CALLBACK_URL, no redirects
    rpc_id = f"req-{uuid4().hex}"
    payload = {
        "jsonrpc": "2.0",
        "id": rpc_id,
        "method": "message/send",
        "params": {
            "message": {
                "role": "user",
                "parts": [{"kind": "text", "text": message_text}],
                "messageId": uuid4().hex,
            }
        },
    }

    for attempt in (1, 2):
        token = _fetch_token(cfg, force=attempt > 1) # from the SaaS provider's own Cognito pool
        try:
            resp = _post_callback(CALLBACK_URL, payload, token)
            ...
```
每次失败，从未经验证的卡到被拒绝的令牌，都会向模型发出一条消息“企业上下文不可用”，并且详细信息保留在 SaaS 提供商的日志中。

### 在 AgentCore 上通过 A2A 公开代理

Strands SDK 中的 A2AServer 类处理 A2A 协议、代理卡生成和 JSON-RPC 消息处理。服务器发布一项策划的技能，并在卡片上声明调用者如何获取令牌：
```
a2a_server = SecuredA2AServer( # A2AServer plus the card's securitySchemes
    agent_factory=create_compliance_agent,
    http_url=AGENT_URL,
    serve_at_root=True,
    skills=[COMPLIANCE_SCAN_SKILL], # one curated skill, not the internal tools
    enable_a2a_compliant_streaming=True,
)
```
部署到 AgentCore 时，会自动在“/.well-known/agent-card.json”处生成一个代理卡。代理卡是一个 JSON 文档，描述代理的姓名、能力和技能。 A2A 兼容的客户端可以获取此卡并了解代理可以做什么，而无需文档或 SDK 集成。

## 使用LangChain构建企业编排器

这就是互操作性证明。企业编排器使用LangChain，故意与基于Strands的SaaS代理不同。它使用带有 A2A JSON-RPC 的原始 httpx HTTP 调用，并且不依赖于 Strands SDK。如果 ISV 从 Strands 切换到另一个 A2A 兼容框架，只要 SaaS 代理仍然使用 A2A 并发布兼容的代理卡，企业协调器将继续工作而无需更改。这就是协议级互操作性在实践中的含义。

编排器从企业自己的 Cognito 池获取令牌，并通过 HTTPS 将 JSON-RPC 有效负载仅发送到固定到从中获取代理卡的地址的代理 URL。此精简代码显示了核心 A2A 客户端：
```
from langchain_aws import ChatBedrock
from langchain_core.tools import tool as langchain_tool
from langchain.agents import create_agent

llm = ChatBedrock(
    model_id="us.anthropic.claude-sonnet-4-6",
    region_name=AWS_REGION,
    max_tokens=4096,
    config=BEDROCK_CLIENT_CONFIG, # timeouts and standard retries
    guardrails=GUARDRAIL_CONFIG, # this account's guardrail on every model call
)

def send_a2a_message(agent_url: str, message_text: str) -> str:
    # agent_url is the pinned agent URL from discovery: the address the Agent Card
    # was fetched from, never a value from a caller or a message.
    rpc_id = f"lc-{uuid4().hex}"
    payload = {
        "jsonrpc": "2.0",
        "id": rpc_id,
        "method": "message/send",
        "params": {
            "message": {
                "role": "user",
                "parts": [{"kind": "text", "text": message_text}],
                "messageId": uuid4().hex,
            }
        },
    }
    def _post(token: str, attempt: int) -> httpx.Response:
        headers = {"Content-Type": "application/json", "Authorization": f"Bearer {token}"}
        with httpx.Client(timeout=_A2A_TIMEOUT) as client: # Timeout(300.0, connect=5.0); httpx doesn't follow redirects by default
            resp = client.post(agent_url, json=payload, headers=headers)
            resp.raise_for_status()
            return resp

    # get_bearer_token() raises when there is no valid client config and never returns
    # an empty token, so no request goes out without one (fail closed).
    token = get_bearer_token()
    try:
        resp = _post(token, 1)
    except httpx.HTTPStatusError as e:
        # On a 401, force one token refresh and retry once.
        if e.response.status_code == 401:
            resp = _post(_fetch_token(force=True), 2)
        else:
            raise
    ...
```
### 通过LLM发现代理并路由请求

启动时，协调器从配置的 ISV URL 获取代理卡。它读取每张卡牌的技能描述，并为每项技能创建一个LangChain工具。然后，编排器的大型语言模型 (LLM) Anthropic Claude Sonnet 4.6 根据用户的问题决定调用哪个工具。这个简化的代码显示了该模式：
```
def _tool_name_part(text: str) -> str:
    """Reduce card text to the characters Bedrock allows in a tool name (letters, digits, _)."""
    return re.sub(r"[^A-Za-z0-9_]+", "_", str(text)).strip("_") or "agent"

def build_langchain_tools(agents: list[dict]) -> list:
    """Create a LangChain tool for each skill in each discovered agent."""
    tools = []

    for agent in agents:
        agent_url = agent["url"]
        agent_name = _tool_name_part(agent["name"])

        for skill in agent["skills"]:
            skill_name = _tool_name_part(skill["name"])
            skill_description = skill.get("description", "")
            examples = skill.get("examples", [])

            # Build a descriptive tool name and description
            tool_name = f"{agent_name}__{skill_name}"[:64]
            tool_description = (
                f"{skill_description} "
                f"(External agent: {agent['name']})"
            )
            if examples:
                tool_description += f" Examples: {'; '.join(examples[:3])}"

            # Create a closure to capture agent_url for this specific tool
            def make_tool(name: str, desc: str, url: str):
                def call_external_agent(question: str) -> str:
                    """Send a natural language question to an external agent via A2A protocol."""
                    return send_a2a_message(url, question)
                call_external_agent.__name__ = name
                call_external_agent.__doc__ = desc
                return langchain_tool(call_external_agent)

            tools.append(make_tool(tool_name, tool_description, agent_url))

    # (A catch-all tool for an agent whose card lists no skills is omitted here.)
    return tools

agent_tools = build_langchain_tools(discovered_agents) # from the Agent Cards fetched at startup
agent_executor = create_agent(llm, agent_tools, system_prompt=SYSTEM_PROMPT)
```
因此，当 ISV 添加或更改功能时，其代理卡也会随之更改，并且协调器会在下次重新启动时采用新技能。两个团队不需要协调变更。

## 构建企业上下文代理

企业上下文代理使用 LangChain 和 Amazon Nova Lite 进行企业元数据查找，并使用官方 a2a-sdk 通过 A2A 公开其功能。 SDK 处理代理卡服务、JSON-RPC 路由和协议一致性。由于 A2A 是基于 HTTP 的 JSON-RPC，因此标准 Web 框架可以为其提供服务。编排器显示客户端：它使用纯 httpx 发送 A2A 请求，没有 A2A SDK。

代理还在“/.well-known/agent-card.json”中发布了自己的代理卡，SaaS 代理在回调之前会检查该代理卡。这与另一个方向使用的发现机制相同。 A2A 规范定义了代理卡，因此它们不依赖于构建代理的框架。

## 使用 Amazon Cognito 设置跨境 OAuth

对于大多数企业来说，未经身份验证的跨组织边界的代理间通信是不可接受的。此解决方案中的每个 A2A 任务请求（消息/发送）都带有 JSON Web 令牌 (JWT)。每一方都使用来自其自己的身份提供商的令牌进行身份验证，接收方仅接受该提供商、一个客户端和一个范围。唯一未经身份验证的端点是企业上下文代理的代理卡，它发布描述性元数据，以便调用者可以发现代理。

该解决方案使用 [Amazon Cognito](https://aws.amazon.com/cognito/) 作为 OAuth 提供商。在更新示例的特定于 Cognito 的检查后，相同的模式可以使用另一个 OpenID Connect (OIDC) 身份提供商来颁发签名的 JWT 访问令牌。

身份验证流程涉及四个组件：

Amazon Cognito：每个账户一个用户池。企业池向编排器和企业应用程序颁发令牌，SaaS 池向 SaaS 代理颁发令牌以供其回调。您可以在 [Amazon Cognito](https://console.aws.amazon.com/cognito/) 控制台中查看它们。

Amazon Bedrock AgentCore 配置有企业池的发现 URL、编排器的客户端 ID 和一个范围。它会验证每个传入 A2A 请求的 JWT：
```
{"customJWTAuthorizer": {
    "discoveryUrl": "https://cognito-idp.us-east-1.amazonaws.com/<enterprise pool ID>/.well-known/openid-configuration",
    "allowedClients": ["<a2a-enterprise-orchestrator-saas client ID>"],
    "allowedScopes": ["a2a-enterprise-compliance-saas/invoke"]
}}
```
Amazon API Gateway 使用 JWT 授权者。合作伙伴 API 仅接受 SaaS 提供商的回调令牌，用户 API 仅接受企业应用程序的令牌。在 [Amazon API Gateway 控制台](https://console.aws.amazon.com/apigateway/) 中查看配置。

每个账户中的 AWS Secrets Manager 存储该账户的客户端密钥，并且 IAM 授权和拒绝所有其他委托人的资源策略将每个密钥限制为使用它的一个工作负载。没有秘密被硬编码或与其他帐户共享。您可以在 [AWS Secrets Manager 控制台](https://console.aws.amazon.com/secretsmanager/) 中管理密钥。

此 AWS CloudFormation 代码段显示了合作伙伴 API 的 JWT 授权者：
```
# Trusts only the SaaS provider's pool, its callback client, and its callback scope.
ContextApiAuthorizer:
  Type: AWS::ApiGatewayV2::Authorizer
  Properties:
    ApiId: !ImportValue
      Fn::Sub: '${IdentityStackName}-PartnerApiId'
    AuthorizerType: JWT
    Name: saas-jwt
    IdentitySource:
      - '$request.header.Authorization'
    JwtConfiguration:
      Audience: [!Ref SaasCallbackClientId]
      Issuer: !Ref SaasIssuer
ContextApiRoute:
  Type: AWS::ApiGatewayV2::Route
  Properties:
    RouteKey: 'POST /'
    AuthorizationType: JWT
    AuthorizerId: !Ref ContextApiAuthorizer
    AuthorizationScopes: [!Ref SaasCallbackScope]
    # ApiId and Target omitted
```
当您在 API Gateway 和 AgentCore 之间连接 OAuth 时，机器对机器身份验证的一个细节是常见的错误来源。 Amazon Cognito 客户端凭证访问令牌包含 client_id 和范围，但没有 aud 声明。当 aud 不存在时，API Gateway JWT 授权者会根据受众列表检查 client_id。在 AgentCore 端，配置 allowedClients 并保留 allowedAudience 未设置。

## 了解特工卡和发现

代理卡使发现成为可能，无需事先就工具定义达成一致。如果没有它们，企业将需要文档、SDK 或与 ISV 工程团队的会议来了解合规代理可以做什么。通过代理卡，企业协调器可以获取单个 JSON 文档。它在运行时以编程方式立即知道代理的名称、能力和技能。这是合规代理为一位客户发布的卡片，已删节：

## 生产注意事项

为了清楚起见，该演示简化了几个区域。对于生产，请考虑以下更改：

- 每个客户一个运行时，或接受多个客户身份提供商的前门，以及每个客户的回调客户端。
- 基于密钥的客户端身份验证（private_key_jwt 或双向 TLS）而不是客户端机密。
- 用于私有连接的 AWS PrivateLink，以及用于端到端加密的 VPC 内的 TLS。
- 客户管理的 Amazon Simple Storage Service (Amazon S3)、Amazon ECR、AWS Secrets Manager、Amazon CloudWatch Logs 和 Amazon Bedrock Guardrails 的 AWS Key Management Service (AWS KMS) 密钥。
- VPC 流日志和网络负载均衡器访问日志。两个 API Gateway 阶段都已写入访问日志。
- 用于 Cognito 客户端凭据的 Secrets Manager 轮换功能。
- 经过身份验证的入职门户或 API，而不是文件。

如果通过 API Gateway 的调用间歇性返回 HTTP 503，请检查内部网络负载均衡器是否启用了跨区域负载均衡。每个 ECS 服务运行一个可以在任一可用区中启动的任务。

该存储库的自述文件涵盖了安全控制和生产注意事项的完整列表。

## 安全考虑

仅在没有客户或业务数据的沙盒帐户中部署此解决方案，并在测试后删除堆栈。该样本仅使用合成数据，没有个人数据。其合规代理检查内部政策示例。它不评估或证明对任何法律、法规或标准的遵守情况。该示例包括以下控件。在生产中使用此模式之前，您负责检查和调整它们：

- 传输加密。每个跨账户调用都使用 HTTPS 发送至 Amazon API Gateway 或 Amazon Bedrock AgentCore，并且除上下文代理的公共代理卡之外的每个路由都需要 Cognito JWT。
- 护栏。在此示例中，每个模型调用都使用带有提示攻击和有害内容过滤器的 Amazon Bedrock 护栏，并且在模型使用该护栏之前，会根据同一护栏检查来自其他组织的文本。
- 最低权限 IAM。每个工作负载都有自己的角色，可以命名确切的 ARN。只有协调器和合规代理才能读取秘密，每个秘密都有自己的秘密。
- 容器硬化。 ECS 容器使用只读根文件系统运行，并且删除了所有 Linux 功能。基本图像由摘要固定。
- 帐户隔离。这两个账户不共享任何秘密、密钥或 IAM 权限。他们只交换公共价值观。

## 结论

这篇文章展示了如何构建一个多代理系统，其中来自不同组织、基于不同框架构建的代理通过 AWS 上的 A2A 进行协作。

Amazon ECS 上的 LangChain 编排器与 Amazon Bedrock AgentCore 上的 Strands 代理进行通信。双方都不需要对方的框架或 SDK。 SaaS 代理回调企业上下文代理以获取帐户元数据，并且每一方都使用自己的身份提供商进行身份验证。来自同一 ISV 的新技能无需更改代码。添加第二个 ISV 需要一次扩展，因为编排器现在拥有一个 OAuth 客户端：为每个 ISV 提供一个客户端和范围，如 README 的生产注意事项所述。然后运行相同的入职交换，添加其代理卡 URL，然后重新启动协调器。
