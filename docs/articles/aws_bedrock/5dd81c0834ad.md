# 在 AWS 上使用 A2A 构建可组合、可互操作的多 agent 系统

跨越组织边界的多 agent 系统里，agent 常常需要与其他组织构建和运行的 agent 以可组合、可互操作的方式协作。它们需要一种方式来发现彼此、通信、交换任务，而不暴露内部实现，也不要求两侧使用同一框架。

Agent-to-Agent (A2A) 协议正是为解决这一限制而来。没有 A2A，跨组织边界构建可组合的多 agent 系统，就得为每个客户、每个框架编写定制集成代码。独立软件供应商 (ISV) 则可以构建可组合、可互操作的 agent，与客户已经在用的 A2A 兼容框架直接配合。

虽然本文围绕 ISV 场景展开，但这一模式同样适用于跨边界对外提供 agent 的组织——无论对象是合作伙伴、客户，还是使用不同框架的内部团队。随着系统扩展，你只需向编排器注册 Agent Card 就能增加 skill，无需改动已在运行的 agent。

在本文中，我们走一遍部署在 AWS 上的参考架构。一个基于 LangChain 的企业编排器，通过 A2A 与一个基于 Strands Agents 的软件即服务 (SaaS) agent 跨组织边界通信，企业与 SaaS 提供商分处两个 AWS 账户。双方都不依赖对方的框架或 SDK，也不共享任何机密。我们先讲架构与实现模式，再用三个 Jupyter notebook 部署这套系统，并跑一次端到端测试。

[A2A 协议现已成为 Linux Foundation 项目](https://www.linuxfoundation.org/press/linux-foundation-launches-the-agent2agent-protocol-project-to-enable-secure-intelligent-communication-between-ai-agents)，AWS 是支持它的组织之一。借助 A2A，agent 可以通过标准化协议发现彼此、协商任务、跨组织边界协作。该协议沿用 OAuth 2.0、OpenID Connect (OIDC) 等现有认证标准来保障跨边界安全，并设计为可跨 A2A 兼容框架工作。

在[agent 互操作性开放协议第 4 部分：A2A 上的 agent 间通信](https://aws.amazon.com/blogs/opensource/open-protocols-for-agent-interoperability-part-4-inter-agent-communication-on-a2a/) 中，我们介绍了 A2A 的概念，并演示两个 Strands agent 在 AWS 上用该协议通信。那篇文章奠定了 Agent Card 发现、结构化任务执行和 A2A server 模式的基础。本文在此基础上进一步引入跨框架互操作、跨组织信任边界以及双向 OAuth。

## 解决方案概述

三个 agent 跑在两个 AWS 账户里，一个属于企业，一个属于 SaaS 提供商。A2A 协议把它们连起来，并在两个方向上都做 OAuth 认证。每个账户都有自己的 [Amazon Cognito](https://aws.amazon.com/cognito/) 用户池，因此每一方都用自己的身份提供商完成认证。

![架构图。一个企业 AWS 账户在两个 Amazon API Gateway API 之后，于 AWS Fargate 上运行编排器和上下文 agent；一个 SaaS 提供商账户在 Amazon Bedrock AgentCore runtime 上运行合规 agent。每个账户都有自己的 Amazon Cognito 用户池，并使用 Amazon Bedrock 与 Amazon Bedrock Guardrails。两个账户在接入时只交换公共值，agent 之间则携带 OAuth token 通过 A2A 相互调用。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/10/ML-21127-1.png)

图 1：跨企业账户与 SaaS 提供商账户的 A2A agent

接入时，企业与 SaaS 提供商只交换公共值，例如身份提供商 URL、客户端 ID、scope 和 endpoint URL。之后每一方都信任来自对方用户池的 token，不共享任何机密。

接入完成后，每个请求按以下步骤进行：

- 企业应用从企业的 Amazon Cognito 用户池获取访问 token。
- 应用通过 HTTPS 把问题发到 Amazon API Gateway 中的 user API，然后轮询答案。
- [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 通过 VPC link 和内部 Network Load Balancer，把请求私密转发给 Enterprise Orchestrator（一个 LangChain agent）。
- 当模型判定问题需要合规扫描时，编排器会用存储在 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 中的客户端密钥，从企业用户池获取自己的 token。
- 编排器用启动时从该 agent 的 Agent Card 读到的 skill，向 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) runtime 上的合规 SaaS agent 发送 A2A 请求。
- 合规 agent 先到接入时注册的回调 URL 查看企业上下文 agent 的 Agent Card，再从 SaaS 提供商自己的用户池获取 token。
- 合规 agent 回调企业上下文 agent 取账户元数据，完成扫描，把答案返回给编排器，再交回应用。

在企业侧，两个 agent 跑在 [Amazon Elastic Container Service](https://aws.amazon.com/ecs/) (Amazon ECS) 与 [AWS Fargate](https://aws.amazon.com/fargate/) 上。Enterprise Orchestrator 是用户的入口。LangChain 提供 agent 框架和工具调用抽象，[Amazon Bedrock](https://aws.amazon.com/bedrock/) 提供支撑每个 agent 推理的基础模型 (FM)。编排器使用 LangChain 和 Amazon Bedrock (Anthropic Claude Sonnet 4.6)。启动时，编排器从 SaaS agent 的 well-known URL 拉取 Agent Card，并为卡上描述的每个 skill 创建一个 LangChain 工具。随后模型根据用户的问题决定调用哪个工具，因此编排器不需要硬编码的路由逻辑。它携带 OAuth bearer token 通过 A2A 发送合规扫描请求，并把结果汇总给管理层。用户通过 Amazon API Gateway 的 HTTPS endpoint 访问编排器，该 endpoint 只接受来自企业自己用户池的 token。

第二个企业 agent 提供内部上下文。Enterprise Context Agent 用 LangChain 和 Amazon Bedrock (Amazon Nova Lite) 构建，提供内部账户元数据，例如内部策略规则、数据分类、业务关键性，以及升级联系人（团队值班轮换）。部署的 agent 使用官方 a2a-sdk（AgentCard、AgentExecutor 和符合规范的 JSON-RPC 路由），固定为 a2a-sdk[http-server]==1.2.2。SaaS agent 通过一个只接受 SaaS 提供商回调 token 的 API Gateway partner API 访问上下文 agent。

两个企业 agent 都跑在 [Amazon Virtual Private Cloud](https://aws.amazon.com/vpc/) (Amazon VPC) 的私有子网里，没有公网 IP 地址。

在 SaaS 提供商侧，Compliance SaaS Agent 跑在 SaaS 提供商自己 AWS 账户中的 Amazon Bedrock AgentCore 上。它用 [Strands Agents SDK](https://strandsagents.com/) 构建，按企业自己的内部策略检查 AWS 账户，例如生产环境不得有公共存储、机密数据须静态加密。在生产中，扫描工具会连到 [AWS Config](https://aws.amazon.com/config/)、[AWS Security Hub](https://aws.amazon.com/security-hub/) 或 [Amazon GuardDuty](https://aws.amazon.com/guardduty/) 等服务。本演示里，agent 使用合成数据来模拟跨多个账户的合规发现。

扫描之前，SaaS agent 会回调 Enterprise Context Agent 获取企业上下文，例如哪些账户是生产账户、适用哪些内部策略、该向谁升级。这种双向模式让 agent 成为真正的对等方，而不是客户端与服务器。回调只会发往客户在接入时注册的地址。

关键的设计决策是：所有跨边界通信都用 A2A。企业看不到 SaaS agent 的内部工具、system prompt 或模型选择。这种分离意味着，只要 Agent Card 和 A2A 接口保持兼容，ISV 就能改动内部架构而不必改动客户侧的集成。SaaS 卡只发布一个精选 skill，而不是它的内部工具名。

Amazon Bedrock 提供对多个基础模型的 API 访问，因此每个 agent 都能选用适合自身工作负载的模型。在这套方案里，编排器和 SaaS agent 用 Anthropic Claude Sonnet 4.6 做复杂推理，上下文 agent 用 Amazon Nova Lite 做元数据查找。你也可以按自己的需求选择不同的模型。

在这套架构里，A2A 和 Model Context Protocol (MCP) 解决的是不同问题。MCP 以客户端—服务器模型把 agent 连到它自己的工具和数据源；A2A 则把 agent 与 agent 作为对等方连起来，任何一方都不暴露内部实现。在生产中，SaaS agent 可以在内部用 MCP 连到它的合规扫描工具，同时对外通过 A2A 暴露自己。无论 agent 怎样连接内部工具，外部接口都保持不变。

- 在 SaaS 提供商账户里运行 notebook 2。
- 把 `onboarding-response.json` 交还企业。
- 在企业账户里运行 notebook 3。

以下几节解释部署背后的关键实现模式。它们共同展示三种能力：

- **跨框架的互操作性 –** 一个 LangChain 编排器通过 A2A 调用 Strands agent，双方都不依赖对方的 SDK。
- **跨组织边界的可组合性 –** ISV 的合规 agent 与企业的上下文 agent 组合成一个工作流，两个团队谁都没有单独把它建出来。
- **基于 OAuth 的双向协作 –** agent 作为对等方，用基于 token 的认证跨信任边界相互调用。

有了 A2A，这个场景里的 ISV 用单个基于协议的接口，取代了多条定制集成路径。

## 构建 SaaS 合规 agent

用 Strands Agents SDK 构建 ISV 的合规 agent，并部署到 Amazon Bedrock AgentCore。本演示里，扫描工具返回的是合成的合规发现。

该 agent 用 Strands @tool 装饰器暴露三个合规工具（列出可用账户、运行合规扫描、检索补救步骤），外加第四个回调企业的工具，下一节会讲到。Agent Card 并不列出这些工具，它只发布一个精选 skill，让调用方的模型看到产品能做什么，而不是它怎么实现的。下面是扫描工具的简化示例：

```
from strands import Agent, ToolContext, tool
from strands.models.bedrock import BedrockModel
from strands.multiagent.a2a import A2AServer

@tool
def run_compliance_scan(account_id: str) -> dict:
    """Run a compliance scan on a specific AWS account.

    Args:
        account_id: The AWS account ID to scan (e.g., acc-12345)
    """
    if account_id not in ACCOUNTS:
        return {"error": f"Account {account_id} not found."}
    findings = COMPLIANCE_FINDINGS.get(account_id, [])
    non_compliant = [f for f in findings if f["status"] == "NON_COMPLIANT"]
    return {
        "account_id": account_id,
        "account_name": ACCOUNTS[account_id]["name"],
        "scan_summary": {
            "total_rules_checked": len(findings),
            "compliant": len(findings) - len(non_compliant),
            "non_compliant": len(non_compliant),
            "critical_findings": len([f for f in non_compliant if f["severity"] == "CRITICAL"]),
            "high_findings": len([f for f in non_compliant if f["severity"] == "HIGH"]),
        },
        "findings": findings,
    }
```

### 启用双向回调

这正是这套方案超越常见 agent 集成的地方。大多数 agent 到 agent 的演示只展示单向的请求—响应：客户端 agent 调用服务端 agent，然后等结果。一旦被调用的 agent 需要只有调用方才有的信息，这个模式就不管用了。在生产中，agent 需要成为能互相调用的对等方。

SaaS 合规 agent 需要企业上下文，例如哪些账户是生产账户、适用哪些内部策略、该向谁升级。这些信息只有企业才有。

SaaS agent 通过 A2A 回调，但只发往客户在接入时注册的回调 URL。它先在那里校验客户的公开上下文卡，再从 SaaS 提供商自己的 Cognito 池获取 token，然后向企业 partner API 发送 message/send：

```
def _call_enterprise_context(message_text: str, inbound_task_id: str = "-") -> str:

        raise CallbackUnavailable("CALLBACK_URL is not a registered callback URL")
    cfg = _load_callback_config() # this SaaS provider's own client, from Secrets Manager
    _verify_context_card(cfg) # anonymous GET of the card at CALLBACK_URL, no redirects
    rpc_id = f"req-{uuid4().hex}"
    payload = {
        "jsonrpc": "2.0",
        "id": rpc_id,
        "method": "message/send",
        "params": {
            "message": {
                "role": "user",
                "parts": [{"kind": "text", "text": message_text}],
                "messageId": uuid4().hex,
            }
        },
    }

    for attempt in (1, 2):
        token = _fetch_token(cfg, force=attempt > 1) # from the SaaS provider's own Cognito pool
        try:
            resp = _post_callback(CALLBACK_URL, payload, token)
            ...
```

从卡未通过校验到 token 被拒，任何一次失败都只给模型一条消息 "Enterprise context unavailable"，细节留在 SaaS 提供商的日志里。

### 在 AgentCore 上通过 A2A 暴露 agent

Strands SDK 里的 A2AServer 类负责 A2A 协议、Agent Card 生成和 JSON-RPC 消息处理。服务器发布一个精选 skill，并在卡上声明调用方如何获取 token：

```
a2a_server = SecuredA2AServer( # A2AServer plus the card's securitySchemes
    agent_factory=create_compliance_agent,
    http_url=AGENT_URL,
    serve_at_root=True,
    skills=[COMPLIANCE_SCAN_SKILL], # one curated skill, not the internal tools
    enable_a2a_compliant_streaming=True,
)
```

部署到 AgentCore 后，会在 `/.well-known/agent-card.json` 自动生成一张 Agent Card。Agent Card 是一份 JSON 文档，描述 agent 的名称、能力和 skill。A2A 兼容的客户端可以拉取这张卡，无需文档或 SDK 集成就能了解 agent 能做什么。

## 用 LangChain 构建企业编排器

这就是互操作性的证明。企业编排器刻意选用 LangChain，与基于 Strands 的 SaaS agent 不同。它用原始 httpx HTTP 调用承载 A2A JSON-RPC，不依赖 Strands SDK。如果 ISV 从 Strands 换到另一个 A2A 兼容框架，只要 SaaS agent 仍讲 A2A 并发布兼容的 Agent Card，企业编排器就无需改动、照常工作。这正是协议级互操作性在实践中的含义。

编排器从企业自己的 Cognito 池获取 token，并且只通过 HTTPS 把 JSON-RPC 负载发到固定地址上的 agent URL——也就是拉取 Agent Card 的那个地址。下面这段节选代码展示核心的 A2A 客户端：

```
from langchain_aws import ChatBedrock
from langchain_core.tools import tool as langchain_tool
from langchain.agents import create_agent

llm = ChatBedrock(
    model_id="us.anthropic.claude-sonnet-4-6",
    region_name=AWS_REGION,
    max_tokens=4096,
    config=BEDROCK_CLIENT_CONFIG, # timeouts and standard retries
    guardrails=GUARDRAIL_CONFIG, # this account's guardrail on every model call
)

def send_a2a_message(agent_url: str, message_text: str) -> str:
    # agent_url is the pinned agent URL from discovery: the address the Agent Card
    # was fetched from, never a value from a caller or a message.
    rpc_id = f"lc-{uuid4().hex}"
    payload = {
        "jsonrpc": "2.0",
        "id": rpc_id,
        "method": "message/send",
        "params": {
            "message": {
                "role": "user",
                "parts": [{"kind": "text", "text": message_text}],
                "messageId": uuid4().hex,
            }
        },
    }
    def _post(token: str, attempt: int) -> httpx.Response:
        headers = {"Content-Type": "application/json", "Authorization": f"Bearer {token}"}
        with httpx.Client(timeout=_A2A_TIMEOUT) as client: # Timeout(300.0, connect=5.0); httpx doesn't follow redirects by default
            resp = client.post(agent_url, json=payload, headers=headers)
            resp.raise_for_status()
            return resp

    # get_bearer_token() raises when there is no valid client config and never returns
    # an empty token, so no request goes out without one (fail closed).
    token = get_bearer_token()
    try:
        resp = _post(token, 1)
    except httpx.HTTPStatusError as e:
        # On a 401, force one token refresh and retry once.
        if e.response.status_code == 401:
            resp = _post(_fetch_token(force=True), 2)
        else:
            raise
    ...
```

### 用 LLM 发现 agent 并路由请求

启动时，编排器从配置好的 ISV URL 拉取 Agent Card，读取每张卡上的 skill 描述，并为每个 skill 创建一个 LangChain 工具。随后编排器的大语言模型 (LLM) Anthropic Claude Sonnet 4.6 根据用户的问题决定调用哪个工具。下面这段简化代码展示这个模式：

```
def _tool_name_part(text: str) -> str:
    """Reduce card text to the characters Bedrock allows in a tool name (letters, digits, _)."""
    return re.sub(r"[^A-Za-z0-9_]+", "_", str(text)).strip("_") or "agent"

def build_langchain_tools(agents: list[dict]) -> list:
    """Create a LangChain tool for each skill in each discovered agent."""
    tools = []

    for agent in agents:
        agent_url = agent["url"]
        agent_name = _tool_name_part(agent["name"])

        for skill in agent["skills"]:
            skill_name = _tool_name_part(skill["name"])
            skill_description = skill.get("description", "")
            examples = skill.get("examples", [])

            # Build a descriptive tool name and description
            tool_name = f"{agent_name}__{skill_name}"[:64]
            tool_description = (
                f"{skill_description} "
                f"(External agent: {agent['name']})"
            )
            if examples:
                tool_description += f" Examples: {'; '.join(examples[:3])}"

            # Create a closure to capture agent_url for this specific tool
            def make_tool(name: str, desc: str, url: str):
                def call_external_agent(question: str) -> str:
                    """Send a natural language question to an external agent via A2A protocol."""
                    return send_a2a_message(url, question)
                call_external_agent.__name__ = name
                call_external_agent.__doc__ = desc
                return langchain_tool(call_external_agent)

            tools.append(make_tool(tool_name, tool_description, agent_url))

    # (A catch-all tool for an agent whose card lists no skills is omitted here.)
    return tools

agent_tools = build_langchain_tools(discovered_agents) # from the Agent Cards fetched at startup
agent_executor = create_agent(llm, agent_tools, system_prompt=SYSTEM_PROMPT)
```

如此一来，当 ISV 增加或改动某项能力时，它的 Agent Card 随之变化，编排器下次重启就会纳入新的 skill。两个团队无需协调这次变更。

## 构建企业上下文 agent

企业上下文 agent 用 LangChain 和 Amazon Nova Lite 做企业元数据查找，并通过官方 a2a-sdk 以 A2A 暴露自身能力。SDK 负责 Agent Card 的提供、JSON-RPC 路由和协议一致性。由于 A2A 就是基于 HTTP 的 JSON-RPC，标准 Web 框架就能承载它。编排器展示了客户端一侧：它用纯 httpx 发送 A2A 请求，不用任何 A2A SDK。

该 agent 也在 `/.well-known/agent-card.json` 发布自己的 Agent Card，SaaS agent 回调前会先查看它。这与另一个方向用的是同一套发现机制。A2A 规范定义了 Agent Card，因此它们不依赖构建 agent 所用的框架。

## 用 Amazon Cognito 设置跨边界 OAuth

对大多数企业来说，跨组织边界却不做认证的 agent 间通信无法接受。这套方案里每个 A2A 任务请求 (message/send) 都携带 JSON Web Token (JWT)。每一方都用自己身份提供商签发的 token 认证，接收方只接受该提供商、一个 client 和一个 scope。唯一不做认证的 endpoint 是企业上下文 agent 的 Agent Card，它发布描述性元数据，供调用方发现这个 agent。

方案用 [Amazon Cognito](https://aws.amazon.com/cognito/) 作为 OAuth 提供商。在更新示例中针对 Cognito 的检查之后，同一模式也可以换用另一个能签发带签名 JWT 访问 token 的 OpenID Connect (OIDC) 身份提供商。

认证流程涉及四个组件：

Amazon Cognito：每个账户一个用户池。企业池向编排器和企业应用签发 token，SaaS 池向 SaaS agent 签发 token 供其回调。你可以在 [Amazon Cognito](https://console.aws.amazon.com/cognito/) 控制台查看。

Amazon Bedrock AgentCore 配置了企业池的 discovery URL、编排器的客户端 ID 和一个 scope。它会校验每个传入 A2A 请求的 JWT：

```
{"customJWTAuthorizer": {
    "discoveryUrl": "https://cognito-idp.us-east-1.amazonaws.com/<enterprise pool ID>/.well-known/openid-configuration",
    "allowedClients": ["<a2a-enterprise-orchestrator-saas client ID>"],
    "allowedScopes": ["a2a-enterprise-compliance-saas/invoke"]
}}
```

Amazon API Gateway 使用 JWT authorizer。partner API 只接受 SaaS 提供商的回调 token，user API 只接受企业应用的 token。配置可在 [Amazon API Gateway 控制台](https://console.aws.amazon.com/apigateway/) 查看。

每个账户里的 AWS Secrets Manager 保存该账户的客户端密钥，IAM 授权和一条拒绝其他所有 principal 的资源策略，把每个密钥限定给使用它的那一个工作负载。没有密钥被硬编码，也没有密钥与另一个账户共享。你可以在 [AWS Secrets Manager 控制台](https://console.aws.amazon.com/secretsmanager/) 管理密钥。

下面这段 AWS CloudFormation 片段展示 partner API 的 JWT authorizer：

```
# Trusts only the SaaS provider's pool, its callback client, and its callback scope.
ContextApiAuthorizer:
  Type: AWS::ApiGatewayV2::Authorizer
  Properties:
    ApiId: !ImportValue
      Fn::Sub: '${IdentityStackName}-PartnerApiId'
    AuthorizerType: JWT
    Name: saas-jwt
    IdentitySource:
      - '$request.header.Authorization'
    JwtConfiguration:
      Audience: [!Ref SaasCallbackClientId]
      Issuer: !Ref SaasIssuer
ContextApiRoute:
  Type: AWS::ApiGatewayV2::Route
  Properties:
    RouteKey: 'POST /'
    AuthorizationType: JWT
    AuthorizerId: !Ref ContextApiAuthorizer
    AuthorizationScopes: [!Ref SaasCallbackScope]
    # ApiId and Target omitted
```

在 API Gateway 和 AgentCore 之间接 OAuth 时，机器到机器认证有一个细节常引发错误。Amazon Cognito 的 client-credentials 访问 token 带 client_id 和 scope，却没有 aud claim。aud 缺失时，API Gateway JWT authorizer 会拿 client_id 去比对 audience 列表。在 AgentCore 一侧，配置 allowedClients，并把 allowedAudience 留空不设。

## 理解 Agent Card 与发现

有了 Agent Card，发现就不必事先约定工具定义。没有它，企业就得靠文档、SDK，或者与 ISV 工程团队开会，才能弄清合规 agent 能做什么。有了 Agent Card，企业编排器只需拉取一份 JSON 文档，就能在运行时以编程方式立刻知道 agent 的名称、能力和 skill。下面是合规 agent 为某一位客户发布的卡片（已节选）：

```
{
    "name": "Compliance SaaS Agent",
    "description": "Scans AWS accounts for compliance with your organization's policies and returns findings by severity with remediation steps.",
    "url": "https://bedrock-agentcore.us-east-1.amazonaws.com/runtimes/.../invocations/",
    "protocolVersion": "0.3.0",
    "capabilities": { "streaming": true },
    "skills": [
        {
            "id": "compliance-scan",
            "name": "Compliance scan",
            "description": "Scans your AWS accounts against your organization's policies and returns findings by severity, remediation steps with estimated effort, and your escalation contacts when available."
        }
    ],
    "securitySchemes": {
        "cognito": {
            "type": "oauth2",
            "description": "OAuth 2.0 client credentials from the customer's identity provider, registered at onboarding.",
            "flows": { "clientCredentials": {
                "tokenUrl": "https://a2a-enterprise-<account-id>.auth.us-east-1.amazoncognito.com/oauth2/token",
                "scopes": { "a2a-enterprise-compliance-saas/invoke": "Invoke the compliance agent" }
            } }
        }
    },
    "security": [ { "cognito": ["a2a-enterprise-compliance-saas/invoke"] } ]
}
```

每个 skill 的描述都会变成一个工具 docstring，因此编排器的模型把每个请求路由到正确的 agent。两个团队从不需要约定工具定义，也不需要共享 SDK。这张卡还声明调用方如何认证。编排器是核对这份声明，而不是照它执行：只有当卡里写明的 token endpoint 和 scope 正是接入时登记的那些，它才保留这张卡。

## 生产注意事项

为便于说明，本演示简化了若干地方。上生产时，建议考虑这些改动：

- 每个客户一个 runtime，或者用一个能接纳多个客户身份提供商的前置入口，并为每个客户配回调 client。
- 改用基于密钥的客户端认证（private_key_jwt 或双向 TLS），而不是客户端密钥。
- 用 AWS PrivateLink 做私有连接，并在 VPC 内用 TLS 实现端到端加密。
- 为 Amazon Simple Storage Service (Amazon S3)、Amazon ECR、AWS Secrets Manager、Amazon CloudWatch Logs 和 Amazon Bedrock Guardrails 使用客户自管的 AWS Key Management Service (AWS KMS) 密钥。
- VPC Flow Logs 和 Network Load Balancer 访问日志。两个 API Gateway stage 都已经写访问日志。
- 为 Cognito 客户端凭证配一个 Secrets Manager 轮换函数。
- 用带认证的接入门户或 API 取代文件交换。

如果经 API Gateway 的调用间歇性返回 HTTP 503，请检查内部 Network Load Balancer 是否开启了跨可用区负载均衡。每个 ECS 服务只跑一个任务，而它可能在任一可用区启动。

仓库 README 的 Security controls 和 Considerations for production 小节有完整清单。

## 安全注意事项

只在没有客户或业务数据的沙盒账户里部署这套方案，并在测试后删除堆栈。示例只用合成数据，不含个人数据；其合规 agent 检查的是示例性的内部策略，不评估、也不认证对任何法律、法规或标准的合规情况。示例包含以下控制。在生产中使用这一模式之前，你有责任审阅并调整它们：

- 传输加密。每次跨账户调用都用 HTTPS 发往 Amazon API Gateway 或 Amazon Bedrock AgentCore，除上下文 agent 的公开 Agent Card 外，每条路由都要求 Cognito JWT。
- 护栏。本示例里，每次模型调用都使用带 prompt 攻击和有害内容过滤器的 Amazon Bedrock guardrail，来自另一组织的文本在模型使用之前也会先经过同一 guardrail 检查。
- 最小权限 IAM。每个工作负载都有自己的角色，明确列出确切的 ARN。只有编排器和合规 agent 能读取机密，且各自只能读自己的。
- 容器加固。ECS 容器以只读根文件系统运行，并丢弃所有 Linux capabilities。基础镜像按 digest 固定。
- 账户隔离。两个账户不共享任何机密、密钥或 IAM 权限，只交换公共值。

## 结论

本文展示了如何构建这样一套多 agent 系统：来自不同组织、基于不同框架的 agent，通过 AWS 上的 A2A 协作。

Amazon ECS 上的 LangChain 编排器与 Amazon Bedrock AgentCore 上的 Strands agent 通信。双方都不需要对方的框架或 SDK。SaaS agent 回调企业上下文 agent 取账户元数据，每一方都用自己的身份提供商认证。同一 ISV 增加一个 skill 无需改动代码。接入第二个 ISV 只需一次扩展，因为编排器目前只持有一个 OAuth client：按 README 的 Considerations for production 所述，给每个 ISV 各配一个 client 和 scope，然后跑一遍相同的接入交换、加入它的 Agent Card URL，重启编排器即可。
