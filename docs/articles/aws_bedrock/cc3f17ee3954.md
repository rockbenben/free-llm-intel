# 使用 Kiro 构建可重复的 PHP 到 Java 迁移引擎

当你的团队把一个成熟的 PHP 应用迁移到 Java 时，你会获得更强的类型安全、更广的库支持和更可预测的扩缩容。一个多年积累、基于 Laravel、Symfony 或 Doctrine 的 PHP 代码库，把业务规则藏在不起眼的地方——从 Eloquent trait 到 XML 映射文件——因此一个结构上相似的 Java 移植可能编译干净、行为却不同。

本文演示如何用 [Kiro](https://kiro.dev/) 把 PHP 到 Java 的迁移从一次靠胆量的飞跃，变成一个可度量、可重复的过程。Kiro 是一个 AI 集成开发环境（IDE），它把 AI agent 与你的代码库配对，在人在环的情况下执行多步工程任务。这套方法的核心是一个可复用的引擎：一套共享方法论、一个机械式的发现扫描器和一个八阶段工作流。这个引擎把原始 PHP 应用当作规格说明，在 parity harness 验证通过之前，它拒绝宣布 Java 移植是正确的。

## 先决条件

开始之前，你需要：

- 熟悉 PHP（Laravel/Eloquent 或 Symfony/Doctrine）。Java 知识（Spring Boot、JPA）有助于你审阅生成产物，但引擎会替你产出地道的 Java，你不需要自己用 Java 重写应用。
- 一个可访问 [Skills](https://kiro.dev/docs/skills/) 和 [Steering](https://kiro.dev/docs/steering/) 文件的 Kiro 工作区。
- 运行发现扫描器的机器上有 PHP 8.0 或更新版本，生成出的 Spring Boot 项目需要 Java 21 和 Maven。
- 对迁移规划（发现、转换、验证）的基本理解。

## 你在本文中能学到什么

你从一个完整开放的仓库开始，所以你可以亲自运行这个引擎，而不只是读它。引擎所知道的一切都存放在一小组 skill 文件里，有了这些文件，你可以用不止一种方式运行同一套方法论。

## 运行引擎的两种方式：Kiro 和 AWS Transform

这里的一切都被打包成 skill 文件：带版本管理的 Markdown 能力包，编码了迁移方法论（php-to-java-migration）和发现扫描器工作流（php-model-discovery）。因为这些知识存在于文件里而不是某个工具里，你可以用两种方式运行同一套方法论。

### 方式一：Kiro，交互式、开发者在环

Kiro 把 AI agent 带进你的编辑器，一步步推进迁移。把仓库根目录作为 Kiro 工作区打开，当你要求 Kiro 迁移一个 PHP 应用时，skills 会自动激活。Kiro 随后带着明确的审批关卡走完八阶段工作流：你审阅发现清单（manifest）、批准规则手册，并在下一阶段开始前逐阶段签字确认。本文的每个示例用的都是这个模式。

### 方式二：AWS Transform，agentic、应用组合级规模

[AWS Transform](https://aws.amazon.com/transform/) 是 AWS 面向大规模迁移与现代化的 agentic AI 服务，它现在与 Kiro 原生集成。通过该集成，你可以把管理交互式 Kiro 会话的同一批 skill 文件交给 AWS Transform，于是「先发现再转换」、以 parity harness 为裁判，以及'*修复的是循环，不是代码*'同样适用于一次自治运行。

### 两条路径各自的适用场景

- **控制与自主：** 用 Kiro 先把一个应用的代码走通：对一个应用运行该 skill，阅读生成的 Java，跑测试。当你想迁移更多应用时，AWS Transform 以 agentic 方式运行同一套方法论，并在 skill 定义的关卡处交由人审阅。
- **规模与新意：** Kiro 一次处理一个应用，适合首个此类框架的迁移。AWS Transform 把许多应用作为并行作业运行。
- **共享的反馈循环：** 两条路径读取同一批 skill 文件，因此在 Kiro 中对规则手册做的每一次修正都会改进下一次 AWS Transform 运行，反之亦然。

## 方案概览：一个共享大脑，多个项目

## 先发现，后转换

最重要的一条规则最先触发：在扫描器跑完之前，不要阅读、猜测或手工翻译任何 model 或 entity 文件。

扫描器单遍完成、无依赖，如下图所示。它对源 token 应用三种发现策略，只输出一份 JSON manifest，任何有歧义的内容都被路由到 review-flag 队列，交由人来裁决。

![php-model-discovery：三种策略，一份 manifest。发现扫描器 discover-models.php 的示意图。左侧 PHP 代码库流入扫描器，扫描器依次运行三种策略：Eloquent 模型发现、Doctrine 属性检测、ORM XML 映射。随后箭头把结果带到右侧的 model-manifest.json，其中包含一个由字段、cast 和关系组成的 models 数组，外加一个充当人工审阅队列的 flags 数组。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/28/ML-21579-3.png)

图 3：扫描器对源 token 运行三种发现策略，输出一份带 review-flag 队列的单一 JSON manifest

扫描器就是 discover-models.php，一个单文件、零依赖的 PHP 命令行工具，它不会执行目标代码。它只把源码当 token 来读，因此无论目标应用的依赖是否安装完毕，它都能针对你选定的应用运行。它每次扫描都会运行三种策略：Eloquent 模型发现（沿类继承链一直走到 Illuminate\Database\Eloquent\Model）、Doctrine 属性检测（#[ORM\Entity] 属性）以及 ORM XML 映射（外部的 `*.orm.xml` 文件）。输出是一份单一的 JSON manifest。`models[]` 数组承载每个字段、cast、关系和可见性规则，每个条目上都带一个 `flags[]` 数组。扫描器对歧义只打 flag，不猜。例如，一个由运行时表达式构建的 `$fillable` 列表会变成一条用通俗英文写成的 flag，而这些 flag 的列表就是人工审阅队列。

## Parity 优先的流水线

Phase 0 是准备阶段：运行扫描器并汇编清单。前三个阶段集中人的专业判断。Phase 1 在写 Java 之前先搭好 parity harness，把请求/响应对同时回放到 PHP 原件和 Java 移植版上。这个 harness 必须在正常工作的 PHP 上通过、在你故意破坏它时报失败，因为一个漏检了注入故障的 harness 不值得信任。Phase 2 建立规则手册和差距清单（RULEBOOK.md、GAP_INVENTORY.md），Phase 3 先在代表性文件上对其做压力测试，再把它推行到整个应用。

![Parity 优先的迁移流水线（8 个阶段）。八阶段 parity 优先迁移流水线示意图。Phase 0 到 3 是人主导的判断步骤，Phase 4 到 8 是自动驾驶循环，两组共同喂给充当裁判的 parity harness，由它比对 PHP 原件与 Java 移植版。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/28/ML-21579-4.png)

图 4：人的判断被前置到准备性 Phase 0 与 Phase 1–3；Phase 4–8 大多是自动驾驶循环，由 parity harness 执法裁判

前四个阶段集中人的专业判断。Phase 0 运行扫描器并汇编清单。Phase 1 在写 Java 之前先搭好 parity harness，把请求/响应对同时回放到 PHP 原件和 Java 移植版上。这个 harness 必须在正常工作的 PHP 上通过、在你故意破坏它时报失败，因为一个漏检了注入故障的 harness 不值得信任。Phase 2 建立规则手册和差距清单（RULEBOOK.md、GAP_INVENTORY.md），Phase 3 先在代表性文件上对其做压力测试，再把它推行到整个应用。

| **阶段** | **名称** | **交付物** |
| --- | --- | --- |
| **0** | 评估与发现 | 模型 manifest + 清单 + 切换方式选择 |
| **1** | 构建裁判 | 可同时针对 PHP 和 Java 运行的 parity harness |
| **2** | 规则手册 + 差距清单 | RULEBOOK.md、GAP_INVENTORY.md |
| **3** | 压力测试规则手册 | 强化后的规则手册，已在代表性文件上验证 |
| **4** | 脚手架 | 可编译的 Spring Boot 项目 |
| **5** | 转换数据模型 | JPA 实体 + schema 基线 |
| **6** | 转换 I/O 层 | controller、安全、模板可响应 |
| **7** | 转换业务逻辑 | 逻辑完成转换，测试全绿 |
| **8** | 证明 parity 并切换 | parity 报告 + 切换清单 |

Phase 4–8 大多是自动驾驶循环：Phase 4 搭建项目脚手架，Phase 5 依据 manifest 转换数据模型，Phase 6 转换 I/O 层（路由变成 controller，中间件变成 filter，校验变成带注解的数据传输对象），Phase 7 分批转换业务逻辑，Phase 8 依据 harness 证明 parity 并完成切换。两条原则统御这个循环。第一，PHP 代码就是规格说明：裁判点头，移植才算完成，否则每处不一致都要记录为已批准的变更。第二，修复的是循环，不是代码——修订规则手册并重新生成，而不是手工打补丁。

## 演练：从 Eloquent 到 Spring Boot

laravel-eloquent-sample 项目是一个可运行、有边界的示例：一个开源 Laravel 应用的只读切片，其中 Book、Chapter、Page 和 User 模型已迁移到 Spring Boot 3.4.1，运行于 Java 21 + Maven 和内存 H2 数据库之上。

从 PHP 到 Spring Boot 的映射是机械的、可追溯的，如下图所示。左侧的每条 manifest 条目都映射到右侧的一个 Java 构造，产出这个生成应用切片的分层运行时架构。

![从 Eloquent 到 Spring Boot：映射与生成的切片。两部分示意图。左侧把 PHP 与 Laravel Eloquent 构造映射到对应的 Java 与 Spring Boot 等价物，用箭头连接每一对，例如 model 对应 JPA 实体、查询 scope 对应 Spring Data repository 方法。右侧展示生成的 book-stack 切片的分层架构：HTTP 客户端调用 controller 层，controller 层调用 repository 层，再到 entity 层，最后是 H2 内存数据库。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/28/ML-21579-5.png)

图 5：左侧是 manifest 驱动的映射；右侧是生成应用切片的分层运行时架构

这些映射是机械的、可追溯到 manifest 的：PHP namespace 变成 Java 包，Eloquent model 变成 JPA @Entity，has Many 和 belongs to 关系变成 @OneToMany 和 @ManyToOne，Eloquent 查询 scope 变成 Spring Data repository 方法。这套纪律在序列化上也有体现：html、markdown 和 text 带 @JsonIgnore，因为 manifest 记录了它们在 Page 的 `$hidden` 列表里，而 Book 的 description 则刻意不在其中。

spec 坦白地写道，37 个模型只移植了 4 个，而最重要的是，这个切片的 parity harness 从未建成——它称之为「最大的单一缺口」。把自己不足之处写进文档，本身就是设计的一部分。

## 开始使用

完整的迁移引擎可在[示例 PHP 到 Java 迁移仓库](https://github.com/aws-samples/sample-php-to-java-migration)中获得。

使用方法：

- 克隆仓库并把其根目录作为你的 Kiro 工作区打开（打开文件夹并选择包含 .kiro/ 的那个文件夹）。除了扫描器所需的 PHP 8.0+ 和 Java 21 + Maven 之外，无需安装任何东西。
- 把 PHP 源码拉取到项目的 source-php/ 文件夹。README 钉住了用于 parity 的确切上游 commit，任何人都能复现基线。
- 要求 Kiro 迁移该应用。php-to-java-migration skill 会自动激活，先运行扫描器，在 .kiro/specs/ 下生成一份全新的 spec，并带你走完各道审批关卡。
- 若要 agentic 运行，把 AWS Transform 指向同一批 skill 文件，让它的 agents 在你的整个应用组合上执行完全相同的方法论。

该方法论能自动检测 Laravel、Symfony、CodeIgniter 和原生 PHP，而扩展是增量式的：为新框架加一行检测规则和一份 `references/<framework>-to-spring.md` 指南即可。由于 Kiro 和 AWS Transform 读取同样的文件，改进一次就能同时升级两个引擎。

## 清理

如果你在演练中部署了示例 Spring Boot 应用：

- 停止正在运行的 Spring Boot 应用（内存 H2 数据库是临时的，无需单独清理）。
- 若不再需要，从工作区移除生成的 Java 项目文件夹。
- 发现扫描器只产出一份 JSON manifest 文件。若不打算再引用它，把工作目录里的扫描器 JSON manifest 删掉即可。
- 迁移引擎本身不开通任何 AWS 资源，因此也没有云资源需要释放。

## 总结

我们展示了如何用 Kiro 构建一个可重复的 PHP 到 Java 迁移引擎，把大规模重写变成可度量、可复利的过程。关键原则是：

- **先发现，后转换：** 机械式扫描器盘点每个模型、字段和关系，你不必猜测结构。
- **先建裁判，再写代码：** parity harness 在第一行 Java 写下之前就定义了*完成*。
- **修复的是循环，不是代码：** 当同一个错误跨文件重复出现时，修订规则手册并重新生成，而不是手工打补丁。
- **一个共享大脑：** 方法论只写一次，跨项目共享，并在每次迁移中改进。

这一切都不是 PHP 或 Java 特有的。凡是旧系统是唯一完整规格说明的迁移，同样的形态都适用。克隆[示例 PHP 到 Java 迁移仓库](https://github.com/aws-samples/sample-php-to-java-migration)，将其作为 Kiro 工作区打开，探索支撑它的 Skills 与 Steering 能力，或者把同一批 skill 文件带到 AWS Transform。了解更多 AWS 上的语言迁移模式，请看 [AWS Prescriptive Guidance](https://aws.amazon.com/prescriptive-guidance/) 文档。
