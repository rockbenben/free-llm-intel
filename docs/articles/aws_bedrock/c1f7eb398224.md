# 从孤立告警到上下文智能：用生成式 AI 实现 agentic 海上异常分析

*本文由 Windward 的 Arad Ben Haim 和 Hannah Danan Moise 共同撰写。*

[Windward](https://windward.ai/) 是一家领先的海事 AI 公司，为海上作业提供达到任务级标准的多源情报。通过融合船舶自动识别系统（AIS）数据、遥感信号、专有 AI 模型和生成式 AI，Windward 给出全球海上活动的 360° 视图，使国防与情报机构、执法部门以及商业决策者能够预判威胁、保护关键资产，并在海上保持掌控。

这篇博文展示了 Windward 如何通过把地理空间情报与生成式 AI 结合，帮助增强并加速告警调查流程，让分析人员可以专注于决策而不是数据收集。在使用 Windward 之前，海事分析人员要花数小时手工收集并关联复杂数据，才能理解船舶行为的异常：异常的活动高峰、意外的移动、偏离已知模式。这需要大量时间和深厚的领域专业知识。Windward 的 Maritime AI™ 自动完成这一过程，把上下文与影响呈现出来，使分析人员和公司能够快速、精准地对海上风险与机会做出知情决策。

## 挑战

海事分析人员依靠 Windward 的系统来领先于复杂的全球威胁。作为 Windward 持续打造“任务就绪”用户体验承诺的一部分，公司不断演进用户从发现到决策的路径。虽然 [Windward Early Detection](https://windward.ai/solutions/early-detection/) 能成功识别可疑模式，Windward 仍通过让调查过程更顺畅、更自动化，进一步加快了态势感知。

为了优化分析工作流，Windward 从三个关键战略改进入手，加强对外部上下文的关联：

**统一工作流：** 尽量减少查阅外部数据源的需要，营造连续、专注的分析环境。

**专业能力优化：** 自动收集天气、新闻和告警数据，让领域专家把更多时间投入战略性解读。

**全面覆盖：** 简化信息综合过程，以便同时、更快、更深入地调查多个告警。

作为 MAI Expert™（首个生成式 AI 海事 agent）的核心组件，Windward 与 AWS Generative AI Innovation Center 合作交付了一套能自动为海上异常补全上下文的解决方案。这次合作把告警与相关的公开数据和专有数据关联起来，把这些发现与 Windward 的内部模型无缝集成，并利用生成式 AI 帮助产出全面、可执行的风险评估，从而提升了用户体验。

## 方案概述

与 AWS 合作，Windward 开发了一套多步骤、由 AI 驱动的解决方案：它自动从各类内部与外部数据源获取相关数据，再用这些信息生成一段文本描述，为海上异常事件补全上下文。图 1 展示了该方案部署到 AWS 后的端到端架构。

![windward aws 博客的架构图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/03/24/ML-18948-image-1.png)

图 1. 方案架构

给定 [Windward Early Detection](https://windward.ai/solutions/early-detection/) 系统识别出的一个异常，方案会用 Windward 的内部数据库从该异常事件中提取相关元数据。元数据包括异常时间戳、区域坐标、异常类型、船舶类别以及其他相关信息。

接着，异常元数据被传给由 Amazon Bedrock 上大语言模型（LLM）驱动的 agentic 分析系统。多步骤的异常分析 pipeline 使用 [AWS Step Functions](https://aws.amazon.com/step-functions/) 编排。在第一步中，系统查询多个不同来源的外部数据源，为异常提供相关背景——这是为客户创造新价值的关键部分。这些数据源包括：

- **实时新闻流：** 抓取从公开数据中发现的告警与事件信号，并按海上异常的时间与位置进行过滤。
- **智能网络搜索：** 系统使用大语言模型生成精确的搜索查询，检索实时网络搜索结果，为异常提供最新的上下文。
- **天气数据：** 用一个外部 API 检索异常所在位置与时间的相关天气数据，例如温度、风速和降水量。

每个数据源都通过独立的 [AWS Lambda 函数](https://aws.amazon.com/lambda/) 查询。从三个数据源取回数据后，pipeline 进入第二步。在第二步中，另一个 LLM——通过 Amazon Bedrock 调用 Anthropic 的 Claude——检查这些数据条目，并判断是否需要再抓取额外的网络搜索结果。该 LLM 被要求先把异常数据与已检索到的数据条目做交叉核对，判断目前检索到的数据是否足以解释该异常，或者该事件的某些方面仍然缺失，然后才做出决定。LLM 要么生成新的搜索查询，要么输出一条指令以进入 pipeline 的下一步。Lambda 函数解析 LLM 的输出，并在需要时再次触发网络搜索功能，抓取可能为异常提供重要上下文的更多新闻，追加到先前的搜索结果中。如果没有新的搜索查询，Step Functions 就继续执行 pipeline 中的下一个 Lambda 函数。

![经过自我反思的流程示意图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/03/24/ML-18948-image-2.png)

图 2. 自我反思逻辑

在完成自我反思与额外数据检索之后，系统执行两个过滤与排序步骤，剔除与所讨论异常无关的新闻条目。首先，它使用一个重排 AI 模型 Amazon Rerank，按与异常的相关性对数据条目排序。这一步骤着眼于保持高召回率，重点是剔除最不相关的数据条目，以缩减下一阶段需要处理的候选条目集合。其次，每个排名靠前的条目还会由 LLM 从多个维度进一步打分，包括时间、位置、船舶类型是否匹配等等。系统给出 0 到 100 之间的相关性分数，只保留分数高于方案开发者所设定阈值的条目。这一步更精确，着眼于高精度，确保只保留最相关的新闻条目。排名靠前的数据与新闻条目被送入方案 pipeline 的下一步。最后，pipeline 使用另一个 LLM，以排名靠前的数据条目为依据，生成关于该异常的上下文报告，概述其潜在原因、风险与影响。这份简明的报告为 Windward 的客户而写，并直接引用所使用的数据源，使用户可以顺着链接核实信息、了解额外细节。图 3 给出了针对某个船舶活动异常所生成报告的示例。

## 评估

端到端系统在一组过去发生的真实海上异常上进行评估。评估由几个阶段组成。首先，用 LLM-as-a-judge 方法自动评估摘要，该方法包含针对 LLM 评判者的人类对齐工作。评判者使用六项预定义标准，包括可信度、数据质量、来源多样性、连贯性和伦理偏见。评判者对每个维度按 1 到 100 打分，并把分数分配给每份报告。图 4 描绘了 LLM 评判者给某份生成报告打分的示例。其次，我们计算若干关于报告质量的确定性指标，包括报告的字符长度，以及正文中明确引用的数据源数量。这些指标有助于判断所生成解释的规模与可信度。最后，选定的摘要还要由人类专家评估，他们会把生成的摘要与检索到的数据源，同自己的搜索结果和领域理解做交叉核对。

## 结论

本文介绍的初步 agentic 方案，是 Windward MAI Expert™ 发展过程中的一个重要里程碑。在 Windward 本已强大的系统之上，这一增强加速了海上告警调查，让分析人员能更专注于决策而不是数据收集。该方案把地理空间情报与生成式 AI 结合，简化了此前手工完成、耗时密集的流程。系统生成的高质量异常摘要帮助分析人员更好地理解海上事件的背景——异常的活动高峰、意外的移动、偏离已知模式——并对相应的风险与机会做出知情决策。这些能力扩展了 Windward 在各类用户群体中的价值主张。对于具备深厚海事专业知识的现有用户，它们进一步简化了工作流，缩短了获取相关上下文所需的时间。对于海事专业知识有限的用户，它们开辟了新的可能：无需手工关联复杂数据集，就能获得关键洞察。
