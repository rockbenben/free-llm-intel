# 使用 Datadog LLM Observability 监控构建在 Amazon Bedrock 上的 agent

*本文由来自 Datadog 的 Mohammad Jama、Yun Kim 与 Barry Eom 共同撰写。*

近年来生成式 AI agent 的出现改变了 AI 的格局，其驱动力来自大语言模型（LLM）与自然语言处理（NLP）的进步。关注点正在从简单的 AI 助手转向能够思考、迭代并采取行动以解决复杂任务的 Agentic AI 系统。这些 Agentic AI 系统可能使用多个 agent，与组织边界内外的工具交互以做出决策，并连接知识源来了解流程。虽然这些自主系统帮助组织提升工作场所生产力、精简业务工作流并改变研究等领域，但它们也带来了额外的运营要求。为确保可靠性、性能与负责任的 AI 使用，团队需要专为跟踪 agent 行为、协同与执行流而构建的可观测性方案。

[Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 的多 agent 系统协作能力让构建这类系统变得简单而快速。开发者可以把复杂的用户请求拆解为多个步骤、调用内部 API、访问知识库，并维持具备上下文的对话，从而配置一组协同工作的 agent——这一切都无需自己管理其中的逻辑。

组织要扩展 Agentic AI 系统，就需要健壮的可观测性方案，以确保 AI 技术的可靠性、性能与负责任使用。

[Datadog LLM Observability](https://www.datadoghq.com/product/llm-observability/) 通过监控性能、质量与安全问题——例如延迟飙升、幻觉、工具选择或 prompt 注入尝试——帮助团队自信地运营生产级 LLM 应用。凭借对模型行为与应用上下文的完整可见性，开发者可以更快地识别、排查并解决问题。

我们很高兴宣布 Datadog LLM Observability 与 Amazon Bedrock Agents 之间的一项新集成，它有助于监控构建在 Amazon Bedrock 上的 agentic 应用。除了跟踪 agentic 应用的整体健康状况，开发者还可以跟踪复杂工作流中 agent 的逐步执行，并监控基础模型调用、工具调用与知识库交互。

本文中，我们将探讨 Datadog 的 LLM Observability 如何提供必要的可见性与控制能力，以成功监控、运营并调试构建在 Amazon Bedrock Agents 上的生产级 agentic 应用。

## 方案概览

Datadog 与 Amazon Bedrock Agents 的集成为 agentic 生成式 AI 应用提供了全面的可观测性，这类应用通过 InvokeAgent API 以编程方式调用 agent。该集成会从每次 agent 执行中捕获详细的遥测数据，使团队能够有效地监控、排查并优化其 LLM 应用。

### 优化性能并控制成本

随着团队扩展其 agentic 应用，每一次 agent 交互——无论是检索知识、调用工具还是调用模型——都可能影响延迟与成本。如果无法看清这些资源是如何被使用的，那么随着工作流变得更复杂，就很难定位低效之处或控制开支。对于构建在 Bedrock Agents 上的应用，Datadog 会自动捕获并提供：

- **延迟监控**：跟踪每一步与整体执行所花费的时间，以识别瓶颈
- **错误率跟踪**：观察遇到的错误的频率与类型，以提升可靠性并调试问题
- **token 用量分析**：监控处理过程中消耗的 token 数量，以管理成本
- **工具调用详情**：洞察 agent 发起的外部 API 调用，例如 Lambda 函数或知识库查询

这张 LLM Observability 仪表盘详细呈现了一个 AI 驱动的支持聊天机器人的性能与使用模式。

### 监控复杂的 agentic 工作流

Agent 可以执行特定任务、调用工具、访问知识库并维持具备上下文的对话。Datadog 通过从 Amazon Bedrock Agents 捕获详细的遥测数据，提供对 agent 工作流的全面可见性，使团队能够有效地监控、排查并优化其 LLM 应用，并提供：

- **端到端执行可见性**：可视化 agent 工作流的每一项操作，从预处理到后处理，包括编排与 guardrail 评估
- **高效的故障排查**：借助详细的执行洞见进行调试，快速定位故障点并理解错误上下文

这条 LLM Observability trace 详细展示了使用 Amazon Bedrock 的旅行 agent 机器人的执行过程。

### 评估输出、工具选择与整体质量

在 agentic 应用中，仅知道任务完成了是不够的，你还需要知道它完成得有多好。例如，生成的摘要是否准确且切题？面向用户的回答是否清晰、有帮助且不含有害内容？agent 是否选择了正确的工具？如果无法看清这些问题，静默失败就可能悄然而过，削弱预期的成果——例如减少向人工 agent 的交接，或自动化重复性决策。

Datadog LLM Observability 通过评估模型调用的输入与输出，帮助团队评估其 LLM 应用的质量与安全性——既包括根层级，也包括工作流中嵌套的步骤。借助这一集成，你可以：

- **运行内置评估：** 用 [Datadog LLM Observability Evaluations](https://docs.datadoghq.com/llm_observability/terms/#evaluations) 检测质量、安全与安全性问题，例如 prompt 注入、偏题的补全或有毒内容
- **提交自定义评估**：可视化领域特定的质量指标，例如输出是否符合预期格式或遵循策略准则
- **监控 guardrail**：检查执行过程中内容过滤器在何时、因何被触发。

这些洞见直接与延迟、成本和 trace 数据并列呈现——帮助团队不仅了解 agent 的表现如何，还能判断它是否产出了正确的结果。

## 如何开始

Datadog Bedrock Agent Observability 目前首先面向 Python 应用提供，更多语言支持已在路线图中。跟踪 Bedrock Agent 调用是通过把 Datadog 的 [ddtrace](https://ddtrace.readthedocs.io/en/stable/) 库集成进你的应用来实现的。

**前提条件**

- 一个已启用 [Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/getting-started.html) 访问权限的 [AWS 账户](https://signin.aws.amazon.com/signup?request_type=register)。
- 一个基于 Python、使用 Amazon Bedrock 的应用。如有需要，请参阅 [amazon-bedrock-samples](https://github.com/aws-samples/amazon-bedrock-samples) 中的示例。
- 一个 Datadog 账户与 [api key](https://docs.datadoghq.com/cloudcraft/getting-started/generate-api-key/)。

只需几个步骤即可完成埋点，完整细节请参阅最新的 [LLM Observability Python SDK 参考](https://docs.datadoghq.com/llm_observability/setup/sdk/python/)。大多数情况下，只需 2 行代码就能把 ddtrace 加入你的应用：

```
from ddtrace.llmobs import LLMObs
LLMObs.enable()
```

ddtrace 库可以通过环境变量配置，也可以在运行时把值传给 enable 函数来配置。更多细节与定制选项，请参阅上面的 SDK 参考以及[安装文档](https://docs.datadoghq.com/llm_observability/setup/auto_instrumentation?tab=python#amazon-bedrock)。

最后，完成后务必停止或移除相关应用，以管理成本。
