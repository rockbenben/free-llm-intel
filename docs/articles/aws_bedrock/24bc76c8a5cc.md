# 检测并从 Amazon SageMaker HyperPod 上的静默数据损坏中恢复

当 GPU 之类的硬件返回一个错误但看起来合理的数字、却又不报任何错误时，就发生了静默数据损坏（silent data corruption，SDC）。在分布式训练里，这个错误数字可能流进每一个 replica 的梯度和权重。loss 可能一连几个小时看着都正常，等团队察觉到一次无法解释的发散或一个变弱的模型时，算力已经花掉了。它会在规模化时发生：在最多 16K 块 H100 GPU 上进行的为期 54 天的 [Llama 3 405B 预训练](https://arxiv.org/abs/2407.21783)里，Meta 把 419 次意外作业中断中的 6 次归因于静默数据损坏，而这还只算了那些中断了作业、且被追溯到 SDC 的情形。

Amazon SageMaker HyperPod 已经会替换报告故障的节点：health-monitoring agent 盯着 GPU 错误、deep health checks 对节点做压力测试，automatic node recovery 换掉坏硬件。SDC 从这些功能底下全都溜过去了，因为硬件根本不报任何东西。检测必须来自训练作业本身。

本文里，我们往一个 PyTorch DistributedDataParallel（DDP）训练循环里加三项检查来检测 SDC。检查触发时，我们把可疑 rank 映射到它所在的节点、遏制住损坏，并让 SageMaker HyperPod 替换该节点。每项检查覆盖一处故障可能落下的不同位置：

- **非有限梯度检查** 在 GPU 的 forward 或 backward pass 里，于发生的那一步抓住 NaN、Inf 和溢出，也抓住 gradient all-reduce 引入的 NaN 或 Inf。
- **ring replay audit** 抓住有限的错误值。在 audit 步上，每块 GPU 重算来自另一个节点的一个 micro-batch，逐位比较 loss，并按 fingerprint 比较梯度。
- **权重 fingerprint 比较** 在更新之后比较每个 replica 的权重，抓住 optimizer step 和已存权重里的损坏。

我们在一个由 4 个 ml.p5.48xlarge 实例（32 块 NVIDIA H100 GPU）组成的 SageMaker HyperPod 集群上，用软件注入的故障测了这些检查，并在 3 个实例上重复了每一项测试——3 个是这些检查所需的最少数量。本方案的完整代码见[配套 GitHub repository](https://github.com/awslabs/awsome-distributed-ai/tree/main/examples/use-cases/pytorch-ddp-sdc-detection)。

## 静默数据损坏是怎么发生的，以及常规检查为什么漏掉它

SDC 源自制造缺陷（躲过供应商筛选的临界晶体管），以及某个具体计算单元——最常见是 tensor core 里的一条 multiply-accumulate lane，正是模型训练反复猛砸的硬件——的硅老化。那条临界电路大多数时候算得对，只在受压时才算错：高温、电压跌落，或特定的 operand 模式。由于算术逻辑路径没有 ECC 或 parity（不像内存），错误结果（比如本该 4.0000 却给出 4.0001）永远不会被标记，于是它穿过 activations 和梯度，流进每个 replica 的权重。

它之所以这么难抓，是因为 **SDC 在计算路径上，而你已有的每一项完整性检查守的都是另一道边界**：

| **检查** | **它守什么** | **为什么漏掉 SDC** |
| --- | --- | --- |
| ECC | 内存 | 抓内存里的 bit flip，不抓算错的数学。tensor-core 结果上没有 ECC。 |
| Xid errors（NVRM） | GPU driver/硬件故障 | GPU 检测到故障才抛 Xid。SDC 按定义不抛，因此 `/aws/sagemaker/Clusters/` 的 HMA 日志里什么都没有。 |
| DCGM deep health check | 硬件故障 | 漏掉那些需要你工作负载的 operand、热状态或时序才暴露的缺陷。它在空闲节点上、在你的作业之外跑。 |
| NVLink / PCIe / EFA checksums | 传输 | 校验字节按发送原样抵达，不校验它们是否被正确算出来。 |
| Checkpoint checksums | 存储往返 | 一份被污染但内部一致的 checkpoint 照样能通过校验和。 |

抓住 SDC 的办法，是检查计算本身的结果。

## 方案概览

这个循环有四步。前两步由你的训练作业做，后两步用 Kubernetes 和 SageMaker HyperPod 的功能：

第 1 步。**检测：** 训练循环里的三项检查，通过比较 data-parallel replicas 指名一块可疑 GPU。

第 2 步。**定位：** 在由 Amazon Elastic Kubernetes Service（Amazon EKS）编排的 SageMaker HyperPod 集群上，Kubernetes node name 里含着 instance ID，因此把可疑 rank 映射到节点只是一次查表。

第 3 步。**遏制与关联：** 停掉作业、cordon 该节点，并在 SageMaker HyperPod observability dashboards 里看它的 GPU 指标。

第 4 步。**确认与恢复：** 告警含糊时先确认，评审后替换节点，再从可疑窗口之前保存的 checkpoint 续跑。

把这个循环看成分层会有帮助，每层各添一点不同的东西：

| **层** | **来源** | **它添了什么** | **能抓到真正静默的 SDC 吗？** |
| --- | --- | --- | --- |
| 1. 非有限梯度检查 | 你的训练脚本 | 在 all-reduce 之前指名本地梯度为 NaN 或 Inf 的 GPU；若 reduced gradient 是 NaN 或 Inf 就停掉这一步 | 只能抓变成 NaN、Inf 或溢出的故障 |
| 2. Ring replay audit | 你的训练脚本 | 每块 GPU 重算另一节点的一个 micro-batch，比较 loss 的位与梯度 fingerprint | 能，针对在 audit 步上改变 loss 或某个梯度的有限计算路径故障 |
| 3. 权重 fingerprint 比较 | 你的训练脚本 | 更新后指名权重与严格多数不一致的那个 replica | 能，针对单份副本上的 optimizer-step 与已存权重故障。对计算路径故障和分片权重无效 |
| 4. 定位 | 你的训练脚本，用 SageMaker HyperPod node names | 把可疑 rank 映射成 Kubernetes node name 里的 instance ID | 不适用：它只做定位 |
| 5. DCGM 关联 | HyperPod observability add-on | 告警前后该可疑 GPU 的 DCGM 指标 | 只在故障同时出现在硬件计数器里时才确认它。干净的 telemetry 并不能洗清一个节点。 |
| 6. Deep health check | `StartClusterHealthCheck`（DCGM L4） | 对可疑节点做一次按需硬件诊断 | 抓它自己的测试模式能触发的硬件缺陷。是分诊，不是证明 |
| 7. 惯犯历史 | 你在留存告警与 telemetry 之上建的一条查询 | 反复告警的节点 | 部分能：它把值得早点查的节点浮出来 |

第 1–3 层是唯一能检测静默 SDC 的层，它们都住在你的训练代码里。第 4 层把它们的告警变成一个 instance ID，HyperPod 那几层则为告警提供佐证并闭合循环。

## 前置条件

跟着做，你需要：

- 一个由 Amazon EKS 编排、至少有三个 GPU 节点的 SageMaker HyperPod 集群。ring audit 每次要定案的比较都需要三个不同节点，权重比较也需要每份权重的三个副本才能指名落单的那个。见 [Orchestrating SageMaker HyperPod clusters with Amazon EKS](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks.html)。
- 一个 PyTorch DDP 训练作业，其中每个 replica 各跑自己的 optimizer step，并有一条数据流水线能为给定步骤重建任意 rank 的 micro-batch，例如带种子的 sampler。
- Checkpoint 放在共享存储上：Amazon FSx for Lustre 或 Amazon Simple Storage Service（Amazon S3）。替换节点会销毁它的 root 与 secondary volumes，包括本地 NVMe 上的一切。
- 为关联步骤装上 [SageMaker HyperPod observability add-on](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-observability-addon.html)。想要 ECC、NVLink 和 throttling 计数器，就打开 advanced DCGM metrics。
- 能通过 `kubectl` 访问集群，并具备 `sagemaker:StartClusterHealthCheck` 和 `sagemaker:BatchReplaceClusterNodes` 的 AWS Identity and Access Management（IAM）权限。见 [Manually quarantine, replace, or reboot a node](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-resiliency-manual.html)。

## 第 1 步：用训练循环里的三项检查做检测

数据并行同时训练模型的若干份拷贝，称为 replicas。每个 replica 在 batch 的不同切片上训练。每次 backward pass 之后，一次 all-reduce 把各 replica 的梯度取平均，每个 replica 在 `optimizer.step()` 里施加同一份平均值。下面是跨三个 replicas 的一个权重，学习率 0.1：

|  | **replica 0** | **replica 1** | **replica 2** |  |
| --- | --- | --- | --- | --- |
| 起始权重 | 0.500 | 0.500 | 0.500 | 相同 |
| 本地梯度 | 0.20 | 0.40 | 0.30 | 不同（数据不同） |
| 平均后梯度 | 0.30 | 0.30 | 0.30 | 相同，all-reduce 之后 |
| 一步之后权重 | 0.470 | 0.470 | 0.470 | 相同 |

本地梯度不同，是因为每个 replica 看到的数据不同。而 optimizer step 之后，权重必须逐位完全相同。

故障落在哪儿，决定哪顶检查能看见它。若 replica 1 把本地梯度算成 4.00 而非 0.40，all-reduce 会把这个错误摊给每个 replica：三者施加同一份错误更新，权重仍然对得上。只有 replica 1 的本地梯度看着不同，而且只在 all-reduce 之前。反过来，若 replica 1 在 optimizer step 期间或之后弄坏了一个权重，它的权重就与其余对不上了。有一个例外：某个 replica 权重里的 NaN 或 Inf 会经下一次 all-reduce 抵达每个 replica，之后各 replica 又一致了。all-reduce 内部的一次故障（比如某块 GPU 把部分和加错）同样会一模一样地抵达每个 replica。

因此，计算路径故障必须在 optimizer step 之前抓——那时坏梯度还能丢掉；而更新中或其后已存权重里的故障，得在更新之后抓。有限的错误值需要重算：跨 replica 比较梯度范数只能抓到 NaN 和 Inf（见 [Why not compare local gradient norms?](https://aws.amazon.com/cn/blogs/machine-learning/detecting-and-recovering-from-silent-data-corruption-on-amazon-sagemaker-hyperpod/#why-not-compare-local-gradient-norms)）。于是每个 DP rank 上、在每个训练步内按固定顺序有了三项检查：

- **非有限梯度检查 –** all-reduce 之前，标记本地梯度为 NaN 或 Inf 的 rank。它抓 GPU 的 forward 或 backward pass 里在发生那一步就膨胀的值，并指名该 GPU。all-reduce 之后，更新之前，也要检查 reduced gradient 是否为 NaN 或 Inf。
- **Ring replay audit –** 在 audit 步、optimizer step 之前，每个 rank 重算另一节点上某个 rank 的 micro-batch。它逐位比较 loss，并在确定性 kernel 下比较每个参数梯度的 fingerprint。这抓计算路径里的有限错误值。
- **权重 fingerprint 比较 –** optimizer step 之后，每 N 步以及每次 checkpoint 之前，比较每个 replica 的权重 fingerprint。这抓 optimizer step 和已存权重里的故障。

本步的代码针对 PyTorch DDP。tensor、pipeline 或 context parallelism 见 [Beyond DDP](https://aws.amazon.com/cn/blogs/machine-learning/detecting-and-recovering-from-silent-data-corruption-on-amazon-sagemaker-hyperpod/#beyond-ddp)。

### 为什么不比较本地梯度范数？

一个很自然、也是我们最初采用的初版设计，是当某 rank 的本地梯度范数偏离该步中位数超过 k 个 median absolute deviations（MADs）时标记它。我们在 4 个实例上三次无故障运行的每一步都记下每个 rank 的本地梯度范数（22,800 步，见 [Fault-free runs](https://aws.amazon.com/cn/blogs/machine-learning/detecting-and-recovering-from-silent-data-corruption-on-amazon-sagemaker-hyperpod/#fault-free-runs)），跑的是 32 块 H100 上训练一个 953-million-parameter 模型，结果这个测试不成立：

- **健康分布本身就太宽 –** 每个 rank 看到的数据不同，因此健康的本地范数在前 800 步就到了 224 MADs，在所有健康步上到了 1,240 MADs。
- **安静的阈值对有限故障一无所见 –** 取 k = 336（前 800 个健康步里最高分数的 1.5 倍），它在余下 22,000 个健康步里报了 11 次误警；而没有哪个有限故障接近过：即便把一处 activation 乘上 10,000，故障 rank 的分数也从没超过 6.9。

### 按 fingerprint 比较

检查 2 和 3 跨 GPU 比较 tensor。把整个 tensor 发过去代价太大，因此每个 tensor 被压成一个 fingerprint：对其原始位模式做两个 64 位求和，一个 plain、一个按位置加权。对元素少于 2³² 个、每个至多 4 字节的 tensor，改动其中一两个元素就会改变 fingerprint。这覆盖了我们注入的每一种权重故障。更大的改动原则上可能相互抵消，因此 fingerprint 相等是「tensor 相等」的强证据，不是证明。按位置加权那一重求和很要紧：在我们的测试里，交换两个权重值、再对两个值做补偿性改动，plain 和保持不变，只有加权和抓住了它们。

```
_INT_VIEW = {1: torch.uint8, 2: torch.int16, 4: torch.int32, 8: torch.int64}

@torch.no_grad()
def fingerprints(tensors, chunk=1 << 24):
    # ... picks the device and allocates out: one row of two int64 per tensor
    for k, t in enumerate(tensors):
        if t is None:
            continue
        bits = t.detach().contiguous().view(-1).view(_INT_VIEW[t.element_size()])
        for i in range(0, bits.numel(), chunk):  # chunked to bound temporary memory
            b = bits[i:i + chunk].to(torch.int64)
            pos = torch.arange(i + 1, i + 1 + b.numel(), dtype=torch.int64, device=dev)
            out[k, 0] += b.sum()
            out[k, 1] += (b * pos).sum()
    return out
```

### 检查 1：NaN/Inf 梯度，在 all-reduce 前后

一个 DDP communication hook 在梯度被平均之前记下每个 rank 的本地梯度。它存下每个 gradient bucket 的平方范数，并在确定性的 audit 步上存下每个参数梯度的 fingerprint（供检查 2 用）。随后它把这个 bucket 交给 PyTorch 标准的 all-reduce。

backward 之后，`nonfinite_ranks` 从每个 rank 收一个标量，返回本地梯度范数为 NaN 或 Inf 的 ranks。第一个被标记的 rank 就是出故障的那个。若施加了这一步，NaN 会在下一步抵达每个 rank。

```
def local_stats_hook(stats, bucket):
    stats.sq.append(bucket.buffer().float().pow(2).sum())
    if stats.record_fingerprints:  # per parameter, before allreduce_hook divides in place
        rows = [stats.row[p.data_ptr()] for p in bucket.parameters()]
        stats.fp[rows] = fingerprints(bucket.gradients())
    return allreduce_hook(stats.dp_group, bucket)

def attach(ddp_model, dp_group):
    stats = LocalStats(dp_group, list(ddp_model.module.parameters()))
    ddp_model.register_comm_hook(state=stats, hook=local_stats_hook)
    return stats

def nonfinite_ranks(stats):
    """After backward: global ranks whose local gradient norm is NaN or Inf."""
    local = torch.stack(stats.sq).sum().sqrt().reshape(1)
    n = dist.get_world_size(stats.dp_group)
    gathered = [torch.empty_like(local) for _ in range(n)]
    dist.all_gather(gathered, local, group=stats.dp_group)
    bad = ~torch.isfinite(torch.cat(gathered).cpu())
    return [dist.get_global_rank(stats.dp_group, r) for r in bad.nonzero().flatten().tolist()]
```

`train()` 还在 all-reduce 之后检查梯度。reduction 内部产生的 NaN 或 Inf 会以同样方式抵达每个 replica，因此各副本仍然一致、检查 3 会放过它们。没有这项检查，NaN 就会变成每个 replica 上的 NaN 权重，而该步该存的 checkpoint 会带着它们存下、还被打上「通过」的标签。`clip_grad_norm_` 本来就算 reduced gradient 的范数，因此这项检查每步只多一次单元素 all-reduce。reduction 里的一处有限错误仍会通过所有检查。

如果你用 fp16 配 gradient scaler，把 scaler 已经跳过的 overflow 步排除掉。bf16 没有这些步。

### 检查 2：Ring replay，在 optimizer step 之前

直到 `optimizer.step()` 为止，每个 replica 都持有相同的权重。因此在 backward pass 与 optimizer step 之间，任意 rank 都能重算任意其它 rank 的 micro-batch，而在确定性 kernel 下它必须拿到相同的位。

在一个 audit 步上，每个 rank *r* 重算 rank *r + 8* 的 micro-batch：往前 8 个位置，在 p5 实例上正好隔一个节点。它用未包装的 module，因此什么都不做 all-reduce，事后恢复梯度、module 的 buffers 和随机数状态。一次 replay 不论有多少 rank 做，阻塞作业的程度都一样，所以审计每个 rank 与审计一个 rank 的墙钟时间相同。

于是每个 rank 出现在两次比较里：它自己的 micro-batch（由某个 peer 重放），以及它为别人重放的那个 micro-batch。

- **两次比较都不匹配：** 该 rank 在两处都算错了，所以它是元凶。
- **只有一次不匹配：** 任意一侧都可能错。`confirm` 就地裁决：目标之后 8 个位置、位于第三个节点上的 GPU，与目标本身，再各重放一次目标的 micro-batch。这也能区分「持续性故障」（目标会重现）与「瞬态故障」（目标不会重现）。

```
def ring_audit(module, compute_loss, rebuild_batch, step, stats, local_loss, offset, with_grads):
    # ... g is the DP group, n its size, and me this rank's position in it
    target = dist.get_global_rank(g, (me + offset) % n)
    replay = _replay(module, compute_loss, rebuild_batch(step, target), with_grads)
    # ... v = [this rank's own loss bits and gradient fingerprints, its replay of target]
    dist.all_gather_into_tensor(out, v, group=g)
    table = out.view(n, 2, -1).cpu()  # per DP rank: [own result, its replay of its target]
    pairs = [(dist.get_global_rank(g, (r + offset) % n), dist.get_global_rank(g, r))
             for r in range(n) if not torch.equal(table[(r + offset) % n, 0], table[r, 1])]
    return pairs, table

def localize(pairs):
    hits = Counter(r for p in pairs for r in p)
    culprits = sorted(r for r, c in hits.items() if c >= 2)
    ambiguous = [p for p in pairs if not set(p) & set(culprits)]
    return culprits, ambiguous

def confirm(module, compute_loss, rebuild_batch, step, pair, table, stats, offset, with_grads):
    # ... the third GPU (target + offset) and the target replay the target's micro-batch again
    third_r, self_r = v.cpu()
    orig, peer = table[ti, 0], table[ri, 1]
    if torch.equal(third_r, orig):
        return {"pair": pair, "third": third, "suspect": replayer, "kind": "replayer computed wrong"}
    if torch.equal(third_r, peer):
        kind = ("persistent" if torch.equal(self_r, orig) else
                "transient" if torch.equal(self_r, third_r) else "unclear")
        return {"pair": pair, "third": third, "suspect": target, "kind": kind}
    return {"pair": pair, "third": third, "suspect": None, "kind": "unattributable"}
```

只有当三块 GPU 分处三个不同节点时，这次确认才真正独立。`check_topology` 在训练开始前、依据每个 pod 的 `NODE_NAME` 为每一对核验这一点，否则抛错。

挑 audit 模式：

- **默认 kernel：** 只比较 loss。这需要一个 loss 可按位复现的 forward pass，我们的测试里成立：健康的 replay 与原 loss 逐位吻合。梯度没法这样比，因为 attention 默认的 backward pass 不是确定性的。此模式抓改变 loss 的 forward-pass 故障。
- **确定性 kernel**（`deterministic_audits=True`）：整个 audit 步用确定性算法和 math attention kernel 跑。梯度 fingerprint 于是也对得上，因此审计还能抓 backward-only 故障。一个没有确定性实现的 op 会抛错，而不是制造误警。在我们的模型上，一个确定性 audit 步的代价是默认步的 2.4 倍。

绝不要只在可疑者自己身上重放可疑者的工作。一块有持续性缺陷的 GPU 能重现自己的错误答案。

### 检查 3：权重 fingerprint，在 optimizer step 之后

`optimizer.step()` 之后，每个 replica 的权重必须完全相同，因此没有容差可调。每个 rank 给每个权重 tensor 算 fingerprint，并 gather 所有人的 fingerprint。

只有当某个 rank 的某份 tensor 与「严格多数」（超过一半的副本）不同时，才指名它。只有两份副本、或出现没有严格多数的分裂时，比较只报出分歧、不指名任何 rank。

```
def find_divergent_ranks(params, dp_group):
    local = fingerprints(params).flatten()
    # ... all-gathers every rank's fingerprints into table: [dp_size, num_tensors, 2]
    differs = (table != table[0]).any(dim=2).any(dim=0)
    if not differs.any():
        return {"diverged": False, "suspects": []}
    suspects = set()
    for k in differs.nonzero().flatten().tolist():
        copies = [tuple(row) for row in table[:, k].tolist()]
        value, count = Counter(copies).most_common(1)[0]
        if 2 * count <= n:
            return {"diverged": True, "suspects": None}  # no strict majority for tensor k
        suspects.update(r for r, c in enumerate(copies) if c != value)
    return {"diverged": True,
            "suspects": sorted(dist.get_global_rank(dp_group, r) for r in suspects)}
```

每 N 步以及每个 checkpoint 步都跑一次。它是唯一在更新之后跑的检查，因此也是唯一能拦住「从被污染的副本写出 checkpoint」的检查。在我们的测试里，一次更新之后立刻被弄坏的权重，在下一个 checkpoint 步被抓住，save 没有发生。没有这次强制检查，save 就会从被污染的副本照常进行，而 ring audit 要到五次之后的下一轮审计才察觉。

在 953-million-parameter 模型上，每次检查耗 31.1 ms：每 10 步跑一次时，占一步的 2%。

### 把检查放进训练循环

`train` 按图 2 的顺序跑每一步，并在第一个告警处停下。它在 forward pass 之前就决定某步是不是 audit 步，因为确定性比较要求原本那次计算也是确定性的。检查 1 或 2 触发时，它把梯度清零、直接返回，不做 clipping 也不施加更新，于是坏梯度永远到不了权重或 optimizer state，而确切的状态还留在那里供确认。clipping 之后，它检查 reduced gradient 是否为 NaN 或 Inf，是就在更新前返回。只有什么都没触发时才存 checkpoint。

```
def train(ddp_model, stats, optimizer, batches, compute_loss, rebuild_batch, save_checkpoint,
          sched, start_step=0):
    # ... setup, including check_topology(dp_group, sched.peer_offset)
    for step, batch in enumerate(batches, start_step):
        audit = step % sched.audit_every == 0  # 0. decide first
        det = audit and sched.deterministic_audits
        # ... resets the hook's per-step state
        with deterministic() if det else nullcontext():
            loss = compute_loss(ddp_model, batch)  # 1. forward, backward
            loss.backward()
        nonfinite = nonfinite_ranks(stats)  # 2. non-finite check
        pairs, table = [], None
        if audit or nonfinite:  # 3. ring replay
            pairs, table = ring_audit(module, compute_loss, rebuild_batch, step, stats,
                                      loss, sched.peer_offset, with_grads=det)
        if nonfinite or pairs:  # 4. gate
            optimizer.zero_grad(set_to_none=True)  # step not applied
            culprits, ambiguous = localize(pairs)
            verdicts = [confirm(module, compute_loss, rebuild_batch, step, p, table, stats,
                                sched.peer_offset, with_grads=det) for p in ambiguous]
            return {"step": step, "check": "compute", "nonfinite": nonfinite,
                    "mismatched_pairs": pairs, "culprits": culprits, "verdicts": verdicts,
                    "suspect_window": _window(last_audit, step, start_step),
                    "last_audit_pass": last_audit, "last_weight_check_pass": last_weights}
        if audit:
            last_audit = step
        grad_norm = torch.nn.utils.clip_grad_norm_(params, sched.max_grad_norm)
        bad = (~torch.isfinite(grad_norm)).to(torch.int32).reshape(1)  # reduced gradient
        dist.all_reduce(bad, op=dist.ReduceOp.MAX, group=dp_group)
        if bad.item():
            optimizer.zero_grad(set_to_none=True)  # step not applied
            return {"step": step, "check": "reduced gradient", "suspect_window": [step, step],
                    "last_audit_pass": last_audit, "last_weight_check_pass": last_weights}
        optimizer.step()
        optimizer.zero_grad(set_to_none=True)
        ckpt = step % sched.ckpt_every == 0
        if step % sched.check_every == 0 or (ckpt and sched.check_on_checkpoint):
            wc = find_divergent_ranks(params, dp_group)  # 5. weight check
            if wc["diverged"]:
                return {"step": step, "check": "weights", "suspects": wc["suspects"],
                        "suspect_window": _window(last_weights, step, start_step),
                        "last_audit_pass": last_audit, "last_weight_check_pass": last_weights}
            last_weights = step
        if ckpt:  # 6. checkpoint
            save_checkpoint(step, tags={"last_audit_pass": last_audit,
                                        "last_weight_check_pass": last_weights})
    return None
```

告警的 `suspect_window` 是「自触发的那项检查上次通过以来的步数范围」。一个从起始那步起每步都活跃的故障，就发生在这个窗口之内；间歇性故障可能更老，而没有哪项检查看见的故障可能落在任何 checkpoint 里，所以请把那些 tag 当作「检查在该步通过了」的记录，而不是「已存状态干净」的证明。

训练脚本这样调它：

```
# ... imports, and the model, optimizer, and dataset setup
import sdc_order as S

stats = S.attach(ddp_model, dp_group)  # registers the comm hook, once
sched = S.Schedule(audit_every=10, deterministic_audits=True, check_every=10,
                   ckpt_every=100, peer_offset=8)  # 8 = GPUs per node

def compute_loss(model, batch):  # used for training AND replay
    x, y = batch
    with torch.autocast("cuda", dtype=torch.bfloat16):
        logits = model(x)
    return F.cross_entropy(logits.float().flatten(0, 1), y.flatten())

def rebuild_batch(step, rank):  # exactly the micro-batch `rank` trained on
    return dataset.micro_batch(step, rank)

# ... batches(start) yields this rank's micro-batches and sets the learning rate
alarm = S.train(ddp_model, stats, optimizer, batches(start), compute_loss, rebuild_batch,
                save_checkpoint, sched, start_step=start)
if alarm is not None:
    report_sdc(alarm)  # metric + log line; Step 2 maps the rank to a node
    sys.exit(3)
```

replay 依赖这些：

- **精确的 micro-batch：** `rebuild_batch(step, rank)` 必须返回该 rank 训练时用的那个 micro-batch，例如来自带种子的 sampler。
- **同一个 loss 函数：** `compute_loss` 在训练和 replay 里必须是同一个函数，包括 autocast；它内部的任何随机性（如 dropout）都必须按步、按 rank 设种子。
- **模型里没有 collective 或影响输出的状态：** 确认用的 replay 只在两个 rank（目标与第三块 GPU）上跑，因此一个在 forward 或 backward pass 里调 collective 的模型（例如 SyncBatchNorm）会在含糊告警时挂住。一个被 forward pass 既读又更新的 buffer，会让健康的 replay 出现差异。
- **确定性设置：** 在训练进程启动前设好 `CUBLAS_WORKSPACE_CONFIG=:4096:8`，并确认模型里每个 op 都有确定性实现。
- **Peer offset：** 按节点给 DP ranks 编号，使等于「每节点 GPU 数」的 `peer_offset` 把每个 replayer 放到另一个节点上。`check_topology` 会拒绝做不到的排布。
- **此处未测：** 未使用的参数、梯度累积、BatchNorm，以及带副作用的 forward hooks。有未使用参数时设 `deterministic_audits=False`，只比较 loss。

`audit_every` 是成本与鲁棒性之间的主要旋钮：

- **检测延迟：** 一个持续性的有限故障，若它也出现在审计所跑的 kernel 里，就会在 `audit_every` 步之内被抓到。确定性审计跑的是确定性 kernel 和 math attention kernel，因此只落在其余步所用默认 kernel 里的故障永远不会被审计到。
- **被污染的更新：** 审计抓到之前，最多可能已施加 `audit_every` − 1 次被污染的更新。它们都在告警的 `suspect_window` 里。
- **一次性故障：** 只发生在某个非 audit 步、且不再复现的有限故障，完全抓不到。

让 `ckpt_every` 同时是 `audit_every` 和 `check_every` 的倍数，这样每个 checkpoint 步都在更新前被审计、更新后被算 fingerprint。

我们在 953M 模型、32 块 H100 上，按每种 schedule 连续 1,000 步测了端到端平均步时。每种带检查的 schedule 也都每 10 步跑一次权重检查：

| **Schedule** | **平均步时** | **相对纯 DDP** |
| --- | --- | --- |
| 纯 DDP，无检查 | 157.4 ms | — |
| 有检查，无审计 | 169.0 ms | +7.4% |
| 每 10 步确定性审计 | 211.9 ms | +34.7% |
| 每 10 步默认 kernel 审计 | 177.0 ms | +12.5% |
| 每 100 步确定性审计 | 173.3 ms | +10.1% |
| 每 100 步默认 kernel 审计 | 169.3 ms | +7.6% |

每种 schedule 成本里约 7 个百分点与审计无关：每步的 gradient hook 和两次 NaN/Inf 检查，加上每 10 步的权重检查。生产里一个合理起点是每 100 步确定性审计，这里代价 10%。它仍能在 100 步内抓到持续性故障（包括 backward-only 的），代价是最多要回滚 99 次被污染的更新。需要更快检测时——比如在新容量上做 burn-in、或盯着一个可疑节点时——就每 10 步审计一次。成本请在自己的模型上量：确定性 attention 用 math kernel，其代价随序列长度平方增长。

在[无故障运行](https://aws.amazon.com/cn/blogs/machine-learning/detecting-and-recovering-from-silent-data-corruption-on-amazon-sagemaker-hyperpod/#fault-free-runs)里，15,320 个 audit 步和 3,080 次权重检查没有触发告警，这把每 audit 步的误警率上界按 95% 置信度约束在约 1/5,100。

## 第 2 步：把可疑 rank 定位到节点

rank 是逻辑 ID。要对它采取行动，你需要 instance 和那块物理 GPU。在 HyperPod EKS 上，Kubernetes node name 就是带 `hyperpod-` 前缀的 instance ID。用 Kubernetes downward API 把它传进你的 pod：

```
env:
- name: NODE_NAME  # on HyperPod EKS, spec.nodeName is "hyperpod-<instance-id>"
  valueFrom:
    fieldRef:
      fieldPath: spec.nodeName
```

作业启动时，打一张把每个 rank 映射到其节点、instance 和 GPU UUID 的表：

```
import os
import torch
import torch.distributed as dist

node = os.environ["NODE_NAME"]  # "hyperpod-i-0123456789abcdef0"
instance_id = node.removeprefix("hyperpod-")  # "i-0123456789abcdef0", what the Replace API takes
gpu_uuid = "GPU-" + str(torch.cuda.get_device_properties(torch.cuda.current_device()).uuid)
info = {"rank": dist.get_rank(), "node": node,
        "instance_id": instance_id, "gpu_uuid": gpu_uuid}
table = [None] * dist.get_world_size()
dist.all_gather_object(table, info)
if dist.get_rank() == 0:
    print("rank_map", table)  # log at every job start
```

若某个作业已经在跑、却没配 downward API，你可以从外部用 `kubectl get pod <pod> -o jsonpath='{.spec.nodeName}'` 把 pod 映射到它的节点。

## 第 3 步：遏制损害并查看 GPU 指标

告警触发时，先停作业。随后在调查期间 cordon 该节点，阻止新工作落到可疑节点上：

```
kubectl cordon <node-name>  # marks the node unschedulable; existing pods keep running
```

然后在 SageMaker HyperPod observability add-on 里打开 GPU health dashboard，筛到可疑节点和 GPU，看告警触发的时刻。那块 GPU 上 correctable ECC errors、PCIe replays、throttling 或温度的上升，会提高「硬件有故障」的置信度。干净的面板并不能洗清节点：纯 SDC 常常在硬件 telemetry 里不留痕迹。

## 第 4 步：确认，然后替换节点

第 1 步的检查跑着时，告警本身已经指名一块可疑 GPU。当你看到症状却没有告警（比如 loss 尖峰），或想在替换任何东西之前先排除软件问题，就从便宜的解释查起。多数 loss 尖峰不是 SDC，把 SDC 追到一个数据 bug 上会白白耗掉几天：

```
Loss anomaly / suspected corruption
- Reproduces with the same seed on DIFFERENT nodes? -> deterministic bug, not SDC
- Goes away, or follows one node, when you move the job? -> strong SDC candidate
- DP replicas that must be bitwise identical disagree? -> strong SDC signal
- One rank's step replayed on another node gives different bits? -> strong SDC signal
- One rank's pre-all-reduce gradient is NaN or Inf? -> SDC candidate (use the first step it fired)
- Fleet-wide and gradual? -> likely recipe or optimizer
- Started at a data, config, or library change? -> usually software, but not proof
```

把 SDC 与软件区分开的检验，是问题是否跟着硬件走：

- **可复现的失败并不排除 SDC –** [Meta 把一个失败的工作负载](https://arxiv.org/abs/2102.11245) 钉到某一个 core 上，对特定输入每次都拿到同一个错误答案。
- **在软件改动处开始出现的失败也不排除 –** [Google 把一次事故](https://research.google/pubs/cores-that-dont-count/) 追到一次正确的库更新：它开始在有缺陷的 core 上使用极少用到的指令。
- **别指望全局 loss 会指向哪儿 –** 一次 forward 故障先改变故障 rank 自己的 loss，随后 all-reduce 把它的梯度摊给每个 replica。逐 rank 的检查与 replay 才给你 locality。

### 判断告警意味着什么

| **告警** | **含义** | **建议动作** |
| --- | --- | --- |
| `check == "weights"`, `suspects == [r]` | 更新后 rank r 的副本与严格多数不同 | 保持 r 的节点 cordon。评审后替换它 |
| `check == "weights"`, `suspects is None` | 副本有分歧，但没有严格多数 | 含糊：保持涉及到的节点 cordon。查 DCGM 并跑 deep health checks |
| `culprits == [r]` | r 的两次 ring 比较都不匹配。这假定互相重放的那几块 GPU（local index 相同的那些）里至多一块有故障 GPU。有两块时，一块健康的 GPU 可能被指名 | 保持 cordon。评审后替换，或等故障重现后再替换 |
| Verdict persistent | 目标重现了自己的错误答案，且第三块 GPU 与 replayer 一致 | 保持 cordon。评审后替换 |
| Verdict transient | 目标重试算对了，并与第三块 GPU 一致。间歇性故障可能长得一样 | 保持 cordon，直到一次以该节点为目标的审计、或一次 deep health check 通过。再发生就替换它 |
| Verdict replayer computed wrong | 是重放的那块 GPU 错了，不是目标 | 把 replayer 当作可疑者，再确认一次 |
| nonfinite 集非空，无不匹配的 pair | backward pass 里的 NaN 或 Inf，loss 没显出来；或梯度范数大到 float32 装不下（约 1.8 × 10¹⁹ 以上） | 含糊：以可疑者为目标做审计，或查 DCGM 并跑一次 deep health check |
| `check == "reduced gradient"` | all-reduce 之后梯度为 NaN 或 Inf，尽管每个 rank 的本地梯度都有限。不指名任何 rank | 含糊：保持作业停止，查 DCGM、对作业里每个节点跑 deep health checks，并从告警步之前保存的 checkpoint 续跑 |
| Verdict unattributable 或 unclear | 三块 GPU 对不齐 | 含糊：查 DCGM 并对涉及到的节点跑 deep health checks |

在生产里，在你拿到「这些检查在你自己工作负载上的精确率」的证据之前，每一次替换都保留人工批准。像我们这样的合成测试并不能确立它。

### 确认含糊的告警

[deep health check](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-resiliency-deep-health-checks.html) 是处理含糊告警的主要工具。它的压力测试抓硬件会报告的故障，而微妙的、依赖数据的故障往往通过。要在可疑 instance group 上跑一次：

```
aws sagemaker start-cluster-health-check \
    --cluster-name <cluster-name> \
    --deep-health-check-configurations '[{"InstanceGroupName":"<instance-group>","InstanceIds":["i-0123456789abcdef0"],"DeepHealthChecks":["InstanceStress"]}]'
```

### 替换节点

准备替换节点时，你有两个选项。两者触发的是同一套 SageMaker HyperPod 恢复流程，见 [Manually quarantine, replace, or reboot a node](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-resiliency-manual.html)。

若打开了 automatic node recovery，你可以给节点打标签、让 SageMaker HyperPod 替换它，这对自动化很方便：

```
kubectl label node <node-name> \
    sagemaker.amazonaws.com/node-health-status=UnschedulablePendingReplacement --overwrite
```

要改用 API，跑：

```
aws sagemaker batch-replace-cluster-nodes --cluster-name <cluster-name> --node-ids <instance-id>
```

在用 Karpenter 做自动扩缩的集群上，`BatchReplaceClusterNodes` 会终止该节点，但只有在有 pending pods 需要时才创建替代节点。替代节点加入后，训练作业经 SageMaker HyperPod training operator 或作业的 restart policy 重启，训练脚本从告警的 `suspect_window` 开始之前保存的最新 checkpoint 续跑。加载完它之后、第一步之前，立刻调 `find_divergent_ranks`。替换会销毁该节点的 root 与 secondary volumes，所以把 checkpoint 留在共享存储上。

## 把工作流自动化

手动步骤是为了理解。生产里，把它们包进一个跑在你自己集群和账户里的小 controller：

- **触发：** 训练作业把告警报成一个 Kubernetes event、一个小的 custom resource（例如 SDCReport{rank, job, step, check}），或一个挂在 `sdc_nonfinite_grad`、`sdc_replay_mismatch`、`sdc_divergent_tensors` 等指标上的 Amazon CloudWatch alarm。
- **解析：** controller 经 Kubernetes API 映射 rank → pod → node，再剥掉 `hyperpod-` 前缀把 node → instance ID。
- **遏制：** 它 cordon 该节点。
- **决策：** 它套用第 4 步那张表。ring audit 已经就地确认过含糊的 pair，因此告警里带着 verdicts。对含糊结果，它跑一次 node-scoped deep health check。
- **恢复：** 要替换时，它请人批准，然后调 `BatchReplaceClusterNodes`；若打开了 automatic node recovery，就设 node-health label。随后它依托 training operator 与你的 checkpoint reload，并把每一步记进 CloudWatch。

可以把它做成一个轻量 Kubernetes operator，或做成一条挂在 CloudWatch alarm 上、调用 AWS Lambda function 的 Amazon EventBridge rule。

## 用例：在 SageMaker HyperPod 上测试这些检查

我们在一个由 Amazon EKS 编排的 SageMaker HyperPod 集群上把测试跑了两遍，先用 4 个、再用 3 个 ml.p5.48xlarge 实例，每个带 8 块 NVIDIA H100 80GB HBM3 GPU，用 AWS Deep Learning Containers training image 里的 PyTorch 2.9.0（CUDA 13.0）。模型是一个 953-million-parameter 的 Llama 式 decoder，16 层、hidden size 2,048、16 个 attention heads、32,000-token 词表、2,048-token 序列。每块 GPU 每步处理 2 条序列（32 块 GPU 上每步 131,072 tokens），权重、梯度和 optimizer state 用 fp32，计算用 bf16 autocast。我们用 AdamW 训练，100 步 linear warm-up 后学习率 3 × 10⁻⁴，betas (0.9, 0.95)，weight decay 0.1，gradient clipping 1.0。数据是合成的：一个带 Zipf 分布 token 的复制任务，前半段重复，按 rank 和步设种子，因此任何 micro-batch 都能重建。

### 故障场景

故障注入在一层里——16 个 decoder blocks 中第 8 个的 MLP down-projection——在选定的 rank 和步上：

- **Forward 故障** 改变该层的输出，但保留其梯度路径，像 forward pass 里一次错误的乘法。
- **Backward-only 故障** 改变该层输入或权重的梯度。
- **权重故障** 在 optimizer step 之后立刻改动某块 GPU 上已存权重的副本：一次 bit flip、交换两个值，或对两个值做补偿性改动。
- **持续性** 故障在故障 GPU 计算的一切里反复出现，包括它为别的 ranks 跑的 replay；**瞬态** 故障只触发一次。

每个场景都从 400 个 warm-up 步之后取的快照重启，步数从那里算起。除特别注明，审计每 10 步跑一次、用确定性 kernel，权重检查每 10 步一次，每 20 步一次 checkpoint。下表是 4 实例结果。在 3 实例上，每个场景都触发同样的告警、在同样的步、由同样的检查、指名同样的 ranks，只有 peer ranks 变了。

| **注入的故障** | **结果** | **由谁抓住** |
| --- | --- | --- |
| 只在第 25 步（非 audit 步）把 rank 13 forward 输出的一个元素设为 NaN | 第 25 步触发并指名 rank 13。ring replay 也跑了。由 rank 21 与 rank 13 确认：*rank 13 上瞬态*。第 25 步未施加。可疑窗口：第 21–25 步 | 检查 1 |
| 从第 23 步起每步把 rank 13 forward 输出的一个元素 ×1,000 | 第 23–29 步通过检查 1 并被施加。第 30 步的审计在 (13, 5) 和 (21, 13) 上不匹配并指名 rank 13。第 30 步未施加。可疑窗口：第 21–30 步 | 检查 2 |
| 只在 audit 步第 30 步做同样一次 ×1,000 | 一对不匹配，(13, 5)。由第三节点上的 rank 21 与 rank 13 确认：*rank 13 上瞬态* | 检查 2 |
| 在 rank 5（它重放 rank 13 的 micro-batch）上做持续 ×1,000 | (13, 5) 与 (5, 29) 两对不匹配，指名 rank 5。若只由 rank 5 重放一次 rank 13，反而会错怪健康的 rank 13 | 检查 2 |
| rank 13 上其它 forward 故障，从第 23 步起每步：一个元素 ×10,000、整个输出加 10% 乘性噪声、一个 bf16 元素翻第 3 位、某一输出列 ×1.1 | 每个都在第 30 步指名 rank 13。bit flip 与 ×1.1 列也被默认 kernel 审计抓到 | 检查 2 |
| 从第 23 步起每步把流入 rank 13 那一层的梯度、或其权重梯度的一个元素 ×1,000（仅 backward） | 每个都仅凭梯度 fingerprint 在第 30 步指名 rank 13 | 检查 2 |
| 上面那个权重梯度故障，改用默认 kernel 审计 | **50 步内无告警。** 第 20 和 40 步的 checkpoint 被打上「审计与权重检查通过」的标签，因为 loss 没受影响、每个副本都施加了同样被污染的更新 | 未抓到 |
| 同时在 ranks 13 和 22 上做持续 forward ×1,000 | (13, 5)、(21, 13)、(22, 14) 和 (30, 22) 四对不匹配，指名 ranks 13 和 22 | 检查 2 |
| 第 31 步更新后，把 rank 0 上一个 fp32 权重元素的第 22 位翻转，每 5 步一次 checkpoint | 第 35 步 checkpoint 的强制权重检查指名 rank 0，save 未发生。可疑窗口：第 31–35 步 | 检查 3 |
| 同样情形，但 `check_on_checkpoint=False` | **第 35 步的 save 从 rank 0 被污染的副本照常进行了。** 它的 tag 显示上一次通过的权重检查在第 30 步。ring audit 在第 40 步由 (8, 0) 和 (0, 24) 两对指名 rank 0 | 检查 2 |
| 第 31 步更新后，在 rank 0 某个权重 tensor 里交换两个值，或对两个值的位模式分别加 +4,096 与 −4,096，不审计、权重检查每 10 步 | 每个都在第 40 步的权重检查指名 rank 0，尽管该 tensor 的 plain 位和没变 | 检查 3 |
| 恢复快照后（作为加载 checkpoint 的替身），把 rank 7 上一个 attention 权重的第 22 位翻转 | 第一步之前跑的 `find_divergent_ranks` 指名 rank 7 | 检查 3 |

### 无故障运行

为测误警，我们在两种集群规模上都不注入故障训练，各跑三种 schedule。每种 schedule 都每 10 步跑一次权重检查、不存 checkpoint；每次运行的时长按分钟固定，因此「每步都审计」的那两种 schedule 贡献了最多的 audit 步：

| **实例数** | **审计** | **分钟** | **步数** | **Audit 步** | **权重检查** | **告警** |
| --- | --- | --- | --- | --- | --- | --- |
| 4 | 确定性，每步 | 45 | 4,600 | 4,600 | 460 | 0 |
| 4 | 默认 kernel，每步 | 22.5 | 5,400 | 5,400 | 540 | 0 |
| 4 | 确定性，每 10 步 | 45 | 12,800 | 1,280 | 1,280 | 0 |
| 3 | 确定性，每步 | 15 | 1,600 | 1,600 | 160 | 0 |
| 3 | 默认 kernel，每步 | 7.5 | 2,000 | 2,000 | 200 | 0 |
| 3 | 确定性，每 10 步 | 15 | 4,400 | 440 | 440 | 0 |
| 合计 |  | 150 | 30,800 | 15,320 | 3,080 | 0 |

15,320 个 audit 步里 0 告警，按 rule of three，每 audit 步误警率的 95% 上界是 3 / 15,320，约 1/5,100。NaN/Inf 检查在任何无故障步上也没触发。[Why not compare local gradient norms?](https://aws.amazon.com/cn/blogs/machine-learning/detecting-and-recovering-from-silent-data-corruption-on-amazon-sagemaker-hyperpod/#why-not-compare-local-gradient-norms) 里的梯度范数分析只用 4 实例那几次运行。

## 超越 DDP

权重比较并不限于 DDP。`find_divergent_ranks` 接受任意 data-parallel group，因此也适用于 tensor、pipeline 和 context parallelism、HSDP 以及 mixture of experts——这些都是为每份权重保留独立副本的布局。在 ZeRO-1 或全量 FSDP sharding 下它帮不上忙，因为每个 shard 的更新只在一个 rank 上算。本文里的检查和训练循环我们只用 DDP 测过。

要在另一种布局里用它，就拿「持有同一 shard 副本的那个 group」去调 `find_divergent_ranks`。只有两份副本时，它能检测出分歧，但指名不了出错的那份。

如果你更想让服务替你检查节点，SageMaker HyperPod 还提供 MultiNodeTraining deep health check。它在一批 GPU 节点上跑一段短的、固定的分布式训练作业，无需改代码，并替换那些训练 loss 变成 NaN 或 Inf、发散、或没按时跑完的节点。创建 instance group 时把它和 InstanceStress、InstanceConnectivity 一起选上，或用 `StartClusterHealthCheck` 按需跑。它是本文这些检查的补充：用它筛新节点和替代节点、赶在作业落上去之前，用 in-job 检查去抓你自己训练里那些永远不会变成 NaN 或 Inf 的错误值。详情见 [SageMaker HyperPod Deep Health Checks](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-resiliency-deep-health-checks.html#sagemaker-hyperpod-eks-resiliency-deep-health-checks-types)。

## 清理

为避免持续产生费用，把为测试建的东西删掉。若建过 HyperPod 集群，用 `aws sagemaker delete-cluster --cluster-name <cluster-name>` 删除它——这只移除 HyperPod 资源。EKS 集群、它的 add-ons 以及任何 Amazon FSx volumes，要在 HyperPod 集群之后分别删除。见 [Deleting a SageMaker HyperPod cluster](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-operate-cli-command-delete-cluster.html)。

## 结语

本文里，我们展示了如何检测数据并行训练中的静默数据损坏，以及如何把一个可疑节点交给 SageMaker HyperPod 去替换。三项检查覆盖故障可能落下的三处：对每个 rank 的梯度以及 reduced gradient 做一次 NaN/Inf 检查、一次把每块 GPU 的活与另一节点上一块 GPU 比较的 ring replay，以及更新之后的一次权重 fingerprint 比较。前两项在 optimizer step 之前跑，别施加未通过检查的那一步，并在每次 checkpoint 前比较权重。SageMaker HyperPod EKS 集群上的 node names 把可疑 rank 变成 instance ID。随后隔离该节点、回滚到可疑窗口之前的 checkpoint，并让 node-health label 或 Replace API 完成恢复。

要上手，先过一遍 [SageMaker HyperPod resiliency features for Amazon EKS](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-resiliency.html)，再试[配套 repository](https://github.com/awslabs/awsome-distributed-ai/tree/main/examples/use-cases/pytorch-ddp-sdc-detection)。想深入，见 [deep health checks](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-resiliency-deep-health-checks.html) 和 [observability add-on](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-observability-addon.html)。
