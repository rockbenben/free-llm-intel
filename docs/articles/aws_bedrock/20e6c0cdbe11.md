# 为业务需求定制基础模型：RAG、微调与混合方法的全面指南

基础模型（foundation model，FM）已经革新了 AI 能力，但要把它们用于特定的业务需求可能颇具挑战。组织常常难以在模型性能、成本效益与领域特定知识的需求之间取得平衡。本文探讨三种强大的技术，帮助你针对自身独特需求定制 FM：检索增强生成（RAG）、微调（fine-tuning），以及结合两者的混合方法。我们深入分析每种策略的优势、局限与理想用例。

AWS 提供了一整套服务与功能来简化这些技术的实现。[Amazon Bedrock](https://aws.amazon.com/bedrock) 是一项全托管服务，通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、Meta、Stability AI 和 Amazon 等领先 AI 公司的高性能 FM 选择，并提供构建生成式 AI 应用所需的一系列能力，覆盖安全、隐私与负责任的 AI。[Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 原生支持 RAG，简化了用领域特定信息增强模型输出的流程。Amazon Bedrock 还通过持续预训练（continued pre-training）和微调提供[模型定制](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-models.html)的原生功能。此外，你可以使用 [Amazon Bedrock Custom Model Import](https://aws.amazon.com/bedrock/custom-model-import/)，通过单一的无服务器统一 API，把自定义模型与现有 FM 一并引入并使用。使用 [Amazon Bedrock Model Distillation](https://aws.amazon.com/bedrock/model-distillation/) 可以获得更小、更快、更具成本效益的模型，并交付与 Amazon Bedrock 中最先进模型相当的特定用例准确度。

在本文中，我们使用 [Amazon SageMaker AI](https://aws.amazon.com/pm/sagemaker/) 来实现微调与混合方法，以便对微调脚本保留更多控制权并尝试不同的微调方法。此外，如图 1 所示，我们在 RAG 方法中使用了 Amazon Bedrock Knowledge Bases。

为帮助你做出明智决策，我们在 [Github 仓库](https://github.com/aws-samples/tailoring-foundation-models-for-business-needs-guide-to-rag-fine-tuning-hybrid-approaches)中提供了即用型代码，用这些 AWS 服务来试验 RAG、微调与混合方法。你可以基于自身的具体用例与数据集评估它们的表现，并选用最契合的模型，从而有效地为业务需求定制 FM。

## 检索增强生成

RAG 是一种成本效益良好的方式，通过把现有模型连接到外部知识源来增强 AI 能力。例如，一个使用 RAG 的 AI 客服 chatbot 可以先查阅产品文档知识库，来回答关于当前产品功能的问题。当客户提问时，系统会先从产品知识库中检索具体细节，再组织回答，从而帮助保证信息准确且最新。

RAG 方法让 AI 模型能够访问外部知识源以获得更好的回答，它包含两个主要步骤：*检索*（retrieval），从已连接的数据源中找到相关信息；以及*生成*（generation），使用 FM 基于检索到的信息生成答案。

## 微调

微调是一种强大的方式，可以使用额外的训练数据针对特定任务或领域定制 FM。在微调中，你使用与目标领域相关的、规模较小的标注数据集来调整模型参数。

例如，要构建一个 AI 客服 chatbot，你可以用自己的数据集微调现有 FM，让它能够处理关于公司产品功能的问题。通过在历史客户交互与产品规格上训练模型，微调后的模型会习得上下文与公司的表达语气，从而给出更准确的回答。

如果公司发布了新产品，模型就需要用新数据再次微调，以更新其知识并保持相关性。微调有助于确保模型能够给出精确、具备上下文意识的回答。不过，与 RAG 相比，它需要更多的计算资源和时间，因为模型本身需要用新数据重新训练。

## 混合方法

混合方法结合 RAG 与微调的优势，交付高度准确、具备上下文意识的回答。让我们看一个例子：一家公司经常更新其产品功能。他们希望用内部数据定制自己的 FM，但让模型跟上产品目录的变化却很困难。由于产品功能每月都在变化，保持模型最新既昂贵又耗时。

通过采用混合方法，公司可以降低成本并提升效率。他们可以每隔几个月微调一次模型，使其与公司整体语气保持一致。同时，RAG 可以从公司知识库中检索最新的产品信息，帮助确保回答是最新的。微调模型还能增强 RAG 在生成阶段的表现，带来更连贯、更贴合上下文的回答。如果你想进一步改进检索阶段，可以定制 embedding 模型、使用不同的搜索算法，或探索其他检索优化技术。

## 实现

我们实现了三种不同的方法：RAG、微调和混合。关于部署整个解决方案的说明，请参阅 [Readme 文件](https://github.com/aws-samples/tailoring-foundation-models-for-business-needs-guide-to-rag-fine-tuning-hybrid-approaches/blob/main/README.md)。

### RAG

RAG 方法使用 Amazon Bedrock Knowledge Bases，由两个主要部分组成。

**搭建基础设施：**

- 用你所需的数据更新配置文件（详情见 [Readme](https://github.com/aws-samples/tailoring-foundation-models-for-business-needs-guide-to-rag-fine-tuning-hybrid-approaches/blob/main/README.md)）
- 在 infrastructure 文件夹中运行以下命令：

```
cd infrastructure
./prepare.sh
cdk bootstrap aws://<<ACCOUNT_ID>>/<<REGION>>
cdk synth
cdk deploy --all
```

**上下文检索与响应生成：**

- 系统通过用用户的问题搜索知识库来找到相关信息
- 然后它把用户的问题和检索到的信息一起发送给 Amazon Bedrock 上的 Meta LLama 3.1 8b LLM
- LLM 随后基于用户的问题和检索到的信息生成回答

### 微调

我们使用 [Amazon SageMaker AI JumpStart](https://aws.amazon.com/sagemaker-ai/jumpstart/) 采用领域自适应方法对 Meta Llama 3.1 8b Instruct 模型微调了 5 个 epoch。你可以在 `config.py` 文件中调整以下参数：

- **微调方法：**你可以在配置文件中更改微调方法，默认为 `domain_adaptation`。
- **训练轮数（epoch）：**根据你的数据规模在配置文件中调整 epoch 数量。
- **微调模板：**根据你的用例更改模板。当前模板会提示 LLM 回答客户问题。

### 混合

混合方法结合 RAG 与微调，采用以下高层步骤：

- 根据用户的问题从 Knowledge Base 中检索最相关的上下文
- 微调后的模型使用检索到的上下文生成答案

你可以在 `config.py` 文件中定制 prompt 模板。

## 评估

在本示例中，我们使用三项评估指标来衡量表现。你可以修改 `src/evaluation.py` 来实现你自己的评估指标。

每项指标都能帮助你了解各方法在不同方面的表现：

- **BERTScore：**BERTScore 使用余弦相似度衡量生成的回答与正确答案的相似程度。它会计算精确率、召回率和 F1 值。我们用 F1 值作为评估得分。
- **LLM 评估器评分（LLM evaluator score）：**我们使用 Amazon Bedrock 中不同的语言模型为 RAG、微调和混合方法的回答打分。每次评估都会同时收到正确答案和生成的回答，并为每个生成的回答给出 0 到 1 之间的分数（越接近 1 表示相似度越高）。然后我们对所有评估分数取平均，得出最终得分。该流程如下图所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/07/ML-17329-image2.png)

图 2：LLM 评估器方法

- **推理延迟（inference latency）：**响应时间在 chatbot 这类应用中很重要，因此根据你的用例，这项指标可能对你的决策很重要。对每种方法，我们取每个样本获得完整响应所需时间的平均值。
- **成本分析（cost analysis）：**为做完整的成本分析，我们做了以下假设：在 RAG 中，我们使用一个 OpenSearch 计算单元（OCU）用于索引，另一个用于与文档索引相关的搜索。详情请参阅 [OpenSearch Serverless 定价](https://aws.amazon.com/opensearch-service/pricing/)。我们假设一个应用有 1,000 名用户，每人每天发起 10 次请求，平均每次使用 2,000 个输入 token 和 1,000 个输出 token。详情请参阅 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)。我们使用 `ml.g5.12xlarge` 实例进行微调并托管微调后的模型。微调作业耗时 15 分钟完成。详情请参阅 [SageMaker AI 定价](https://aws.amazon.com/sagemaker-ai/pricing/)。对于微调和混合方法，我们假设模型实例 7×24 小时运行，实际情况可能因你的用例而异。成本按一个月计算。

基于这些假设，三种方法各自的成本计算如下：

- **RAG：**  OpenSearch Serverless 月度成本 = 每小时 1 个 OCU 的成本 * 2 个 OCU * 24 小时 * 30 天   Meta Llama 3.1 8b 的总调用成本 = 1000 用户 * 10 次请求 * （每个输入 token 的价格 * 2,000 + 每个输出 token 的价格 * 1,000）* 30 天
- **微调：**  （微调作业使用的分钟数 / 60）* ml.g5.12xlarge 实例的小时成本   托管 ml.g5.12xlarge 实例的小时成本 * 24 小时 * 30 天
- **混合：**  OpenSearch Serverless 月度成本 = 每小时 1 个 OCU 的成本 * 2 个 OCU * 24 小时 * 30 天   （微调作业使用的分钟数 / 60）* ml.g5.12xlarge 实例的成本   托管 ml.g5.12xlarge 实例的小时成本 * 24 小时 * 30 天
