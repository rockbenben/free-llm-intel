# 使用 Ray LLM Deep Learning Containers 运行多节点推理工作负载

本文演示如何用多节点 [Ray LLM Deep Learning Containers](https://aws.github.io/deep-learning-containers/ray-llm/)，把一个大语言模型（LLM）部署到 Amazon Elastic Kubernetes Service (Amazon EKS) 的两个 GPU 节点上。prefill 节点和 decode 节点各自独立，共同藏在一个兼容 OpenAI 的端点后面。这种多节点布局在张量并行、流水线并行、数据并行，以及 prefill/decode 分离这类推理工作负载中都很常见。在[上一篇文章](https://aws.amazon.com/blogs/machine-learning/simplify-and-support-your-torchserve-workloads-using-ray-serve-deep-learning-containers/)中，我们介绍了 [Ray Serve DLC](https://aws.github.io/deep-learning-containers/ray/)，并用它在单个 GPU 节点上把一个小模型挂到一个 HTTP 端点后面。那样你就有了一个可用的推理端点，而容器会保证 GPU 技术栈（包括 CUDA 库）彼此兼容，你不需要写任何样板代码。

[Ray](https://docs.ray.io/en/latest/ray-overview/index.html) 是一个分布式计算框架，因此 Ray Serve 的部署可以横跨多个节点。客户使用多节点 Ray Serve 有几种不同的原因。有人要跑 foundation model 或开放权重模型，而单张 GPU 装不下；有人需要的吞吐超过一个副本能给出的量；还有人想把推理的两个阶段拆开来提升性能。每一种情况下，客户都得自己把依赖链搭起来：为 GPU 技术栈挑选彼此兼容的库，并在某个组件偏离对齐时排查问题。这些都是没有差异化的工作，把本该用来交付模型的时间和精力占走了。

[AWS Deep Learning Containers](https://aws.amazon.com/ai/machine-learning/containers/)（DLC）长期就在解决训练和推理负载中的这类问题。DLC 是预构建、经过性能优化的 Docker 镜像，把一个框架、它的依赖以及 GPU 技术栈打包成一套经过测试、打过补丁的组合，你拉下来就能直接用。随着面向多节点部署的 [Ray LLM DLC](https://aws.github.io/deep-learning-containers/ray-llm/) 发布，同样的思路现在延伸到了多节点推理。你拿到的是一个专为在 HTTP 端点后面服务模型而构建的容器，由 AWS 维护和测试，完整的推理技术栈已经组装到位。

本文走一遍如何用多节点 Ray LLM DLC 实现多节点分离式推理：在 [Amazon EKS](https://aws.amazon.com/eks/) 上把单个大语言模型部署到两个 GPU 节点，让它们在同一个端点后面协同工作。其中一个 GPU 节点处理 prefill 阶段，另一个 GPU 节点处理 decode 阶段。把两个阶段分开，就能避免计算密集的长 prompt 拖慢已经在进行的请求的 token 生成。这种方式很适合 Retrieval Augmented Generation (RAG)、文档摘要、智能体应用这类工作负载。我们使用的多节点 Ray LLM DLC 自带 [Ray Serve LLM](https://docs.ray.io/en/latest/serve/llm/index.html)、[NVIDIA Inference Transfer Library (NIXL)](https://github.com/ai-dynamo/nixl) 和 [Elastic Fabric Adapter (EFA)](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html) 技术栈，并且直接暴露一个兼容 OpenAI 的 API，不需要应用代码。完整代码在[配套仓库](https://github.com/aws-samples/sample-aws-deep-learning-containers/tree/main/inference/ray-serve/ray-serve-multi-node)中。

## 为什么需要 prefill/decode（PD）分离

LLM 推理有两个性质不同的阶段。**Prefill** 并行处理整个输入 prompt，并构建 key-value（KV）缓存。**Decode** 随后一次生成一个 token，读取并延展这份缓存。Prefill 受算力约束，decode 受内存带宽约束。两个阶段共用一张 GPU 时，它们争抢同一批资源，突发而计算密集的 prefill 会干扰平稳、对延迟敏感的 decode。把 prefill 阶段与 decode 阶段分开，你就能为每个阶段分别选择硬件和服务属性，从而在规模化时改善整体性能。

PD 分离把这两个阶段放到不同节点上，于是每个阶段都在不干扰另一个的前提下运行，并且可以各自独立扩缩。代价是，prefill 期间构建的 KV 缓存必须交接给 decode 节点，而这次交接要足够快，快到不至于把收益抵掉。这也正是节点之间的互联重要的原因。

## Ray LLM DLC 提供了什么

AWS DLC 是预构建、经过性能优化的 Docker 镜像，把一个框架、它的依赖以及 GPU 技术栈打包成一套经过测试、打过补丁的组合，你拉下来就能直接用。每次发布前，所有组件都会放在一起验证，所以 CUDA 运行时、框架和服务层之间不会出现版本漂移。安全补丁在构建时就已打上。

[Ray LLM DLC](https://aws.github.io/deep-learning-containers/ray-llm/) 把这一点延伸到了分布式 LLM 服务。它自带 [vLLM](https://github.com/vllm-project/vllm) 作为推理引擎、Ray Serve 的 HTTP 作为服务层、NIXL 用于节点之间的 KV 缓存传输，以及 EFA 技术栈（[libfabric](https://aws.amazon.com/hpc/efa/) 和 [aws-ofi-nccl](https://github.com/aws/aws-ofi-nccl)）用于节点间高带宽通信。由于 [Ray Serve LLM 库](https://docs.ray.io/en/latest/serve/llm/index.html) 内置了应用构建器，整个服务应用就是一段 YAML。没有 handler 类，没有模型归档工具，也不需要自己构建镜像。只有一个辅助函数 `build_pd_openai_app`，它接收一份 prefill 配置和一份 decode 配置，在两者之间把 KV 缓存传输接好，对外呈现为一个兼容 OpenAI 的端点。

## 架构

下图展示了这套部署在 Amazon EKS 上的布局。用户请求到达 CPU 系统节点上的 Ray head，两个 GPU worker 节点分别运行模型的 prefill 和 decode 阶段。

![架构图：用户请求到达 CPU 系统节点上的 Ray head，两个 GPU worker 节点在 Amazon EKS 上运行 prefill 和 decode 阶段](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/09/ML-22045-1.png)

图 1：Amazon EKS 上的多节点推理架构，Ray head 位于 CPU 系统节点，prefill 和 decode 阶段位于两个 GPU worker 节点

这套部署是一个位于 virtual private cloud（VPC）内的 EKS 集群。节点运行在私有子网中，出网流量经过 NAT Gateway。一个 CPU **系统节点**（m7i.xlarge）承载系统工作负载、[KubeRay](https://docs.ray.io/en/latest/cluster/kubernetes/index.html) operator，以及纯 CPU 的 Ray head pod。两个 GPU **worker 节点**（g6.8xlarge）运行 Ray worker：一个服务 prefill 阶段，另一个服务 decode 阶段。两个节点都从 [Amazon Elastic Container Registry (Amazon ECR)](https://aws.amazon.com/ecr/) 拉取 Ray LLM DLC。

KubeRay 监听你 apply 的 RayService，并自动完成 head 到 worker 的组网。Ray Serve 把 prefill 和 decode 这两个部署放到两个 GPU worker 上。KV 缓存经 NIXL 从 prefill worker 流向 decode worker，并通过 NIXL 的 libfabric 后端使用 EFA。GPU 节点组固定在单个可用区（AZ），因为 EFA 无法跨 AZ。

## 前提条件

要跟着本文操作，你需要：

- 一个已开通计费的 AWS 账户。
- 目标 Region 中有足够的服务配额，用于运行两台 g6.8xlarge 实例（至少 64 vCPU）。
- 已配置好凭证的 AWS [Command Line Interface (AWS CLI)](https://aws.amazon.com/cli/)。
- 用于与 Kubernetes 集群控制面通信的 kubectl CLI。
- 用于在 EKS 上创建和管理集群的 eksctl CLI。
- 用于安装 KubeRay operator 的 helm（Kubernetes 的包管理器）。
- 用于渲染 manifest 的 envsubst 工具（GNU gettext 的一部分）。

用以下命令确认你的 AWS 凭证处于活动状态：

```
aws sts get-caller-identity
```

## 使用预构建的应用对外提供推理

应用就是 `manifest/rayservice.yaml` 里的 `serveConfigV2` 代码块。它使用 `build_pd_openai_app`，该函数接收一份 `prefill_config` 和一份 `decode_config`，并把两者之间的 KV 缓存传输连起来：

```
applications:
- name: qwen
  import_path: ray.serve.llm:build_pd_openai_app # OpenAI-compatible PD app, built in
  route_prefix: /
  args:
    prefill_config:
      model_loading_config: { model_id: qwen3.5-9b, model_source: Qwen/Qwen3.5-9B }
      engine_kwargs:
        max_model_len: 4096
        dtype: bfloat16
        gpu_memory_utilization: 0.90
        enforce_eager: true # Skip CUDA graph capture to reduce peak GPU memory
      kv_transfer_config:
        kv_connector: NixlConnector
        kv_role: kv_both
        engine_id: prefill
        kv_connector_extra_config: { backends: ["LIBFABRIC"] }
      deployment_config: { num_replicas: 1 }
    decode_config:
      model_loading_config: { model_id: qwen3.5-9b, model_source: Qwen/Qwen3.5-9B }
      engine_kwargs:
        max_model_len: 4096
        dtype: bfloat16
        gpu_memory_utilization: 0.90
        enforce_eager: true
      kv_transfer_config:
        kv_connector: NixlConnector
        kv_role: kv_both
        engine_id: decode
        kv_connector_extra_config: { backends: ["LIBFABRIC"] }
      deployment_config: { num_replicas: 1 }
```

有几个设置承担了大部分工作。`max_model_len: 4096` 把上下文长度定成能让实测的 KV 缓存装进 GPU 的规模。`dtype: bfloat16` 和 `gpu_memory_utilization: 0.90` 分别设定精度，以及 vLLM 可以占走多少 VRAM。`enforce_eager: true` 跳过 CUDA graph 捕获，以降低 GPU 显存峰值（效果取决于模型和输入）。真正让分离生效的是 `kv_transfer_config`：两个阶段都用 `NixlConnector`、`kv_role: kv_both`，并各自用不同的 `engine_id`（一个是 prefill，另一个是 decode）。最关键的是 `kv_connector_extra_config: { backends: ["LIBFABRIC"] }` 这一行。少了它，NIXL 会退回 UCX，而 UCX 即便跑在 EFA 上也只有 TCP 的速度。

manifest 剩下的部分在 `rayClusterConfig` 里，描述各个 pod。head pod 是纯 CPU 的（`num-gpus: "0"`），固定在系统节点组上。每个 worker pod 请求一张 GPU 和一个 EFA 接口（`nvidia.com/gpu: "1", vpc.amazonaws.com/efa: "1"`），并通过 `nodeSelector: { role: gpu-worker }` 指向 GPU 节点。它以 `privileged: true` 运行，因为 NIXL 要把 CUDA 显存注册到 EFA 网卡上，光有 `IPC_LOCK` 能力并不够。worker 设置 `FI_PROVIDER=efa`，从 pod IP 读取 `VLLM_HOST_IP`，并挂载一块共享内存卷。内存上限设在远高于约 18 GiB checkpoint 的位置，这样操作系统的 page cache 就能把它留住。在 g6.8xlarge 上、采用上述缓存配置加载 Qwen3.5-9B 模型时，模型权重加载时间从大约 145 秒降到重启后的约 2 秒。

## 部署到 Amazon EKS

所有脚本共用同一个配置文件 `scripts/env.sh`。脚本里给出了 `CLUSTER_NAME`、`REGION`、`K8S_VERSION` 和 `NAMESPACE` 的默认值，其他默认值覆盖系统节点组与 GPU 节点组、KubeRay 版本以及模型。要在运行脚本前覆盖任何变量，先把该变量导出即可。

从项目根目录出发，先设定一个基础目录，然后加载变量：

```
CURRENT_DIR=$(pwd)
cd $CURRENT_DIR/ray-serve-multi-node/scripts
source ./env.sh
```

### 第 1 步：创建 EKS 集群

```
./deploy_cluster.sh
```

这会创建 EKS 集群（VPC、OIDC provider、核心 add-on），以及一个运行系统工作负载、KubeRay operator 和 Ray head 的 CPU 系统节点组。节点运行在私有子网中，出网流量经过 NAT Gateway，集群子网放在提供该 GPU 实例类型的 AZ 里。脚本是幂等的，在全新环境上跑一次需要 15–20 分钟。

### 第 2 步：添加 GPU worker 节点

```
./deploy_node_group.sh
```

这会创建 GPU 节点组：两台启用 EFA 的 g6.8xlarge 实例，固定在单个 AZ，并打上 `role=gpu-worker` 标签，好让 Ray worker 指向它们。启用 EFA 的同时也会安装 EFA device plugin，它在每个节点上通告 `vpc.amazonaws.com/efa`。这一步大约需要 5-20 分钟，首次运行通常更久。

### 第 3 步：安装 KubeRay operator

```
./install_kuberay.sh
```

这会用 Helm 安装 KubeRay operator，并把它固定在系统节点组上，以便把 GPU 节点留给推理。KubeRay 会监听你接下来 apply 的 RayService，并自动完成 head 到 worker 的组网。这一步大约需要 1–2 分钟。

### 第 4 步：部署 RayService

```
./deploy_ray_service.sh
```

这会先用 envsubst 按你的镜像、模型和命名变量渲染 `manifest/rayservice.yaml`，然后把它 apply 上去。KubeRay 创建 head 和两个 worker pod，Ray Serve LLM 接着拉起 prefill 和 decode 两个部署。脚本会等待 head 变为 Ready、两个 worker 都进入 Running，最后等待 Serve 应用报告 RUNNING。由于每个节点都要加载模型，这一步预计要几分钟。

随时可以查看状态，包括每个 pod 落在了哪个节点上，以及可用的 GPU 容量：

```
./deploy_ray_service.sh status
```

## 调用模型

Serve 应用健康之后，KubeRay 会创建一个稳定的 `<rayservice-name>-serve-svc` Service。向它做端口转发：

```
kubectl port-forward -n inference svc/ray-llm-serve-svc 8000:8000
```

由于 DLC 暴露的是兼容 OpenAI 的 API，你可以直接列出模型、发送标准的 chat-completion 请求，不需要自定义 schema：

```
curl --silent http://127.0.0.1:8000/v1/models
curl --fail --silent --show-error \
  --request POST "http://127.0.0.1:8000/v1/chat/completions" \
  --header "Content-Type: application/json" \
  --data '{
    "model": "qwen3.5-9b",
    "messages": [
      {"role": "user", "content": "Explain the benefits of prefill/decode disaggregation."}
    ],
    "max_tokens": 200,
    "temperature": 0.7
  }'
```

## 确认 EFA 确实在被使用

如果 NIXL 用不上 libfabric，它会退回 TCP 速度的传输方式，而且不会报错，所以值得确认它实际选了哪个后端。grep 一下 worker 日志：

```
for POD in $(kubectl get pods -n inference -l ray.io/node-type=worker \
  -o jsonpath='{.items[*].metadata.name}'); do
  kubectl exec -n inference "$POD" -c ray-worker -- \
    grep -rhoE "Backend (LIBFABRIC|UCX) was instantiated" /tmp/ray/session_latest/logs/ 2>/dev/null
done | sort | uniq -c
```

`deploy_node_group.sh` 在创建节点组时本来就会打印每个节点上的 `vpc.amazonaws.com/efa` 数量。要拿到一个跨节点带宽数字，DLC 自带一个预构建的 NVIDIA Collective Communications Library (NCCL) 基准程序，位于 `/usr/local/bin/all_reduce_perf`。

## 清理

为避免持续产生费用，请按相反的顺序拆除资源：

```
./delete_ray_service.sh # Remove the RayService
./install_kuberay.sh cleanup # Uninstall the KubeRay operator
./delete_node_group.sh # Remove the GPU node group
./delete_cluster.sh # Delete the EKS cluster
```

## 结论与后续步骤

你在两个 GPU 节点上用 prefill/decode 分离服务了同一个模型，而整个应用就是一段 YAML：没有 handler 代码，没有模型归档工具，也不用手工拼装 GPU 和 EFA 技术栈。多节点 Ray LLM DLC 提供了经过测试的推理技术栈，KubeRay 编排 Ray 集群，NIXL over EFA 在节点之间搬运 KV 缓存。你要做的是配置它，而不是构建它。

运行多节点推理的常见模式包括张量并行和流水线并行（切分一个单台实例装不下的模型）、数据并行（复制模型以提高吞吐），以及 prefill/decode 分离（把推理的两个阶段拆到不同节点上）。

接下来，你可以增加 decode 副本换取更高吞吐，改用更大的 GPU 实例配合张量或流水线并行来承载更大的模型，或者在同一套经过测试的基础镜像上为需要它的模型叠加额外的库。完整代码、当前的镜像 tag 列表，以及底层机制，请参见[配套仓库](https://github.com/aws-samples/sample-aws-deep-learning-containers/tree/main/inference/ray-serve/ray-serve-multi-node)、[Ray LLM DLC available images 页面](https://aws.github.io/deep-learning-containers/reference/available_images/#ray-llm)、[Ray Serve LLM prefill/decode 文档](https://docs.ray.io/en/latest/serve/llm/user-guides/prefill-decode.html)和 [EFA 文档](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html)。
