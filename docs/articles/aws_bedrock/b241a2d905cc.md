# 使用 Ray LLM 深度学习容器运行多节点推理工作负载

本文介绍如何使用多节点 [Ray LLM 深度学习容器](https://aws.github.io/deep-learning-containers/ray-llm/) 在 Amazon Elastic Kubernetes Service (Amazon EKS) 上的两个 GPU 节点上部署一个大型语言模型 (LLM)。它在一个 OpenAI 兼容端点后面使用单独的预填充和解码节点。这种多节点设置对于张量、管道和数据并行性以及预填充/解码分解推理工作负载很常见。在[上一篇文章](https://aws.amazon.com/blogs/machine-learning/simplify-and-support-your-torchserve-workloads-using-ray-serve-deep-learning-containers/)中，我们介绍了[Ray Serve DLC](https://aws.github.io/deep-learning-containers/ray/)，并用它在单个 GPU 节点上的 HTTP 端点后面建立了一个小模型。您有一个工作推理端点，并且容器保持 GPU 堆栈兼容，包括 CUDA 库，因此您不需要编写样板代码。

[Ray](https://docs.ray.io/en/latest/ray-overview/index.html) 是一个分布式计算框架，因此 Ray Serve 部署可以跨多个节点。客户使用多节点 Ray Serve 有多种原因。有些人想要运行对于单个 GPU 来说太大的基础模型或开放权重模型。其他人需要比一个副本所能提供的更多的吞吐量。还有一些人希望将推理的两个阶段分开以提高性能。在每种情况下，客户都必须自行构建依赖链：为 GPU 堆栈选择兼容的库，并在组件偏离对齐时调试问题。这是一项无差别的工作，需要花费时间和精力来交付模型。

[AWS 深度学习容器](https://aws.amazon.com/ai/machine-learning/containers/) (DLC) 早已解决了此类训练和推理工作负载的问题。 DLC 是预构建的、性能优化的 Docker 映像，它将框架、其依赖项和 GPU 堆栈捆绑到经过测试、修补的组合中，您可以立即拉取和使用。随着用于多节点部署的 [Ray LLM DLC](https://aws.github.io/deep-learning-containers/ray-llm/) 的推出，同样的方法现在扩展到多节点推理。您将获得一个专门为 HTTP 端点后面的模型提供服务而构建的容器，由 AWS 维护和测试，并且已经组装了完整的推理堆栈。

本文将介绍如何使用多节点 Ray LLM DLC 实现多节点分类推理：在 [Amazon EKS](https://aws.amazon.com/eks/) 上的两个 GPU 驱动的节点上部署单个大型语言模型，并在单个端点后面进行协作。当其中一个 GPU 节点处理预填充阶段时，另一个 GPU 节点处理解码阶段。分离阶段可以防止计算量大的长提示阻碍已在进行的请求的令牌生成。这种方法非常适合检索增强生成 (RAG)、文档摘要和代理应用程序等工作负载。我们使用多节点 Ray LLM DLC，它附带 [Ray Serve LLM](https://docs.ray.io/en/latest/serve/llm/index.html)、[NVIDIA 推理传输库 (NIXL)](https://github.com/ai-dynamo/nixl) 和 [Elastic Fabric Adapter (EFA)](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html)堆栈，并公开 OpenAI 兼容的 API，无需应用程序代码。完整的代码可在[附带存储库](https://github.com/aws-samples/sample-aws-deep-learning-containers/tree/main/inference/ray-serve/ray-serve-multi-node)中找到。

## 为什么要进行预填充/解码 (PD) 分解

LLM 推理有两个不同的阶段。 **Prefill** 并行处理整个输入提示并构建键值 (KV) 缓存。 **解码** 然后每次生成一个令牌的响应，读取并扩展该缓存。预填充受计算限制，解码受内存带宽限制。当两个阶段共享一个 GPU 时，它们会争夺相同的资源，并且突发性、计算量大的预填充工作会干扰稳定、对延迟敏感的解码工作。将预填充阶段与解码阶段分开意味着您可以为每个阶段选择硬件和服务属性，从而大规模提高整体性能。

PD 分解将两个阶段置于不同的节点上，因此每个阶段的运行不会相互干扰，并且可以独立扩展。权衡是，预填充期间构建的 KV 缓存必须交给解码节点，并且传输应该足够快，以免抹去好处。这正是节点之间的互连很重要的原因。

## Ray LLM DLC 提供什么

AWS DLC 是预构建的、性能优化的 Docker 映像，它将框架、其依赖项和 GPU 堆栈捆绑到经过测试、修补的组合中，您可以立即拉取和使用。所有组件在每次发布之前都会一起进行验证，因此 CUDA 运行时、框架和服务层之间不存在版本漂移。安全补丁在构建时应用。

[Ray LLM DLC](https://aws.github.io/deep-learning-containers/ray-llm/) 将其扩展到分布式 LLM 服务。它提供 [vLLM](https://github.com/vllm-project/vllm) 作为推理引擎，Ray Serve 的 HTTP 作为服务层，NIXL 用于节点之间的 KV 缓存传输，以及 EFA 堆栈 ([libfabric](https://aws.amazon.com/hpc/efa/) 和 [aws-ofi-nccl](https://github.com/aws/aws-ofi-nccl))高带宽节点到节点通信。由于 [Ray Serve LLM 库](https://docs.ray.io/en/latest/serve/llm/index.html) 包含内置应用程序构建器，因此整个服务应用程序是一个 YAML 块。没有处理程序类，没有模型存档器，也没有要构建的自定义图像。单个助手“build_pd_openai_app”采用预填充配置和解码配置，并在一个 OpenAI 兼容端点后面连接它们之间的 KV 缓存传输。

图 1：Amazon EKS 上的多节点推理架构，其中 Ray 头位于 CPU 系统节点上，预填充和解码阶段位于两个 GPU 工作节点上

该部署是 Virtual Private Cloud (VPC) 内的 EKS 集群。节点在私有子网中运行，并通过 NAT 网关进行出站访问。 CPU **系统节点** (m7i.xlarge) 托管系统工作负载、[KubeRay](https://docs.ray.io/en/latest/cluster/kubernetes/index.html) 运算符和仅包含 CPU 的 Ray head pod。两个 GPU **工作节点** (g​​6.8xlarge) 运行 Ray 工作节点：一个服务于预填充阶段，另一个服务于解码阶段。两个节点都从 [Amazon Elastic Container Registry (Amazon ECR)](https://aws.amazon.com/ecr/) 提取 Ray LLM DLC。

KubeRay 监视您应用的 RayService 并自动连接 head-to-worker 连接。 Ray Serve 将预填充和解码部署放在两个 GPU 工作线程上。 KV 缓存通过 NIXL 从预填充工作器流向解码工作器，通过 NIXL 的 libfabric 后端使用 EFA。 GPU 节点组固定到单个可用区 (AZ)，因为 EFA 无法跨 AZ。

## 使用预构建的应用程序进行推理

该应用程序是“manifest/rayservice.yaml”中的“serveConfigV2”块。它使用“build_pd_openai_app”，它采用“prefill_config”和“decode_config”并连接它们之间的 KV 缓存传输：
```
applications:
- name: qwen
  import_path: ray.serve.llm:build_pd_openai_app # OpenAI-compatible PD app, built in
  route_prefix: /
  args:
    prefill_config:
      model_loading_config: { model_id: qwen3.5-9b, model_source: Qwen/Qwen3.5-9B }
      engine_kwargs:
        max_model_len: 4096
        dtype: bfloat16
        gpu_memory_utilization: 0.90
        enforce_eager: true # Skip CUDA graph capture to reduce peak GPU memory
      kv_transfer_config:
        kv_connector: NixlConnector
        kv_role: kv_both
        engine_id: prefill
        kv_connector_extra_config: { backends: ["LIBFABRIC"] }
      deployment_config: { num_replicas: 1 }
    decode_config:
      model_loading_config: { model_id: qwen3.5-9b, model_source: Qwen/Qwen3.5-9B }
      engine_kwargs:
        max_model_len: 4096
        dtype: bfloat16
        gpu_memory_utilization: 0.90
        enforce_eager: true
      kv_transfer_config:
        kv_connector: NixlConnector
        kv_role: kv_both
        engine_id: decode
        kv_connector_extra_config: { backends: ["LIBFABRIC"] }
      deployment_config: { num_replicas: 1 }
```
少数设置承担着大部分的重任。 `max_model_len: 4096` 调整上下文大小以适应 GPU 上测量的 KV 缓存。 `dtype: bfloat16` 和 `gpu_memory_utilization: 0.90` 设置精度以及 vLLM 可以声明多少 VRAM。 `enforce_eager: true` 跳过 CUDA 图形捕获以减少峰值 GPU 内存（取决于模型和输入）。 `kv_transfer_config` 设置是分解工作的关键：两个阶段都使用 `NixlConnector` 和 `kv_role: kv_both` 以及不同的 `engine_id`（一个阶段预填充，另一个阶段解码）。关键设置是`kv_connector_extra_config: { backends: ["LIBFABRIC"] }`。如果没有该行，NIXL 默认为 UCX，即使在 EFA 上也以 TCP 速度运行。

清单的其余部分在“rayClusterConfig”中描述了 Pod。 head pod 仅包含 CPU（`num-gpus: "0"`）并固定到系统节点组。每个工作 Pod 请求一个 GPU 和一个 EFA 接口（`nvidia.com/gpu: "1", vpc.amazonaws.com/efa: "1"`），并通过 `nodeSelector: { role: gpu-worker }` 定位 GPU 节点。它运行“privileged: true”，因为 NIXL 将 CUDA VRAM 注册到 EFA NIC。仅“IPC_LOCK”功能是不够的。工作人员设置“FI_PROVIDER=efa”，从 Pod IP 读取“VLLM_HOST_IP”，并挂载共享内存卷。内存限制远高于大约 18 GiB 检查点，因此操作系统页面缓存可以容纳它。对于采用上述缓存配置的 g6.8xlarge 上的 Qwen3.5-9B 模型加载，重新启动后模型权重加载从约 145 秒降至约 2 秒。

## 在 Amazon EKS 上部署

所有脚本共享一个配置文件“scripts/env.sh”。该脚本包含“CLUSTER_NAME”、“REGION”、“K8S_VERSION”和“NAMESPACE”的默认值。其他默认值包括系统和 GPU 节点组、KubeRay 版本和模型。在运行脚本之前通过导出来覆盖任何变量。

从项目根目录，设置基目录，然后加载变量：
```
CURRENT_DIR=$(pwd)
cd $CURRENT_DIR/ray-serve-multi-node/scripts
source ./env.sh
```

### Step 1: Create the EKS cluster

```
./deploy_cluster.sh
```
这会配置 EKS 集群（VPC、OIDC 提供商、核心附加组件）以及运行系统工作负载、KubeRay 运算符和 Ray head 的 CPU 系统节点组。节点在私有子网中运行，出口通过 NAT 网关，集群子网位于提供 GPU 实例类型的可用区中。该脚本是幂等的，重新运行需要 15-20 分钟。

### 步骤2：添加GPU工作节点
```
./deploy_node_group.sh
```
这将创建 GPU 节点组：两个启用了 EFA 的 g6.8xlarge 实例，固定到单个 AZ 并标记为“role=gpu-worker”，以便 Ray Worker 瞄准它们。启用 EFA 还会安装 EFA 设备插件，该插件会在每个节点上通告“vpc.amazonaws.com/efa”。此步骤大约需要 5-20 分钟，第一次运行时通常会更长。

### 步骤 3：安装 KubeRay Operator
```
./install_kuberay.sh
```
这将使用 Helm 安装 KubeRay 运算符，固定到系统节点组以保持 GPU 节点可用于推理。 KubeRay 监视您接下来应用的 RayService 并自动连接 head-to-worker 连接。此步骤大约需要 1-2 分钟。

### 步骤4：部署RayService
```
./deploy_ray_service.sh
```
这将使用 envsubst 渲染包含图像、模型和命名变量的“manifest/rayservice.yaml”并应用它。 KubeRay 创建头部和两个工作 Pod，Ray Serve LLM 启动预填充和解码部署。该脚本等待头部就绪、两个工作线程运行，最后等待服务应用程序报告“正在运行”。由于每个节点都会加载模型，因此预计此步骤需要几分钟时间。

随时查看状态，包括每个 Pod 落在哪个节点以及可用的 GPU 容量：
```
./deploy_ray_service.sh status
```
## 调用模型

Serve 应用程序正常运行后，KubeRay 创建稳定的 `<rayservice-name>-serve-svc` 服务。端口转发到它：
```
kubectl port-forward -n inference svc/ray-llm-serve-svc 8000:8000
```
由于 DLC 公开了兼容 OpenAI 的 API，因此您可以列出模型并发送标准聊天完成请求，无需自定义架构：
```
curl --silent http://127.0.0.1:8000/v1/models
curl --fail --silent --show-error \
  --request POST "http://127.0.0.1:8000/v1/chat/completions" \
  --header "Content-Type: application/json" \
  --data '{
    "model": "qwen3.5-9b",
    "messages": [
      {"role": "user", "content": "Explain the benefits of prefill/decode disaggregation."}
    ],
    "max_tokens": 200,
    "temperature": 0.7
  }'
```
## 验证是否正在使用 EFA

如果 NIXL 无法使用 libfabric，则它会回退到 TCP 速度传输，并且这样做不会引发错误，因此值得确认它选择的后端。 Grep 工作日志：
```
for POD in $(kubectl get pods -n inference -l ray.io/node-type=worker \
  -o jsonpath='{.items[*].metadata.name}'); do
  kubectl exec -n inference "$POD" -c ray-worker -- \
    grep -rhoE "Backend (LIBFABRIC|UCX) was instantiated" /tmp/ray/session_latest/logs/ 2>/dev/null
done | sort | uniq -c
```
创建组时，“deploy_node_group.sh”已打印每个节点的“vpc.amazonaws.com/efa”计数。对于跨节点带宽数，DLC 在“/usr/local/bin/all_reduce_perf”处提供了预构建的 NVIDIA Collective Communications Library (NCCL) 基准测试。

## 清理

为了避免持续产生费用，请按相反顺序拆除资源：
```
./delete_ray_service.sh # Remove the RayService
./install_kuberay.sh cleanup # Uninstall the KubeRay operator
./delete_node_group.sh # Remove the GPU node group
./delete_cluster.sh # Delete the EKS cluster
```
## 结论和后续步骤

您通过预填充/解码分解在两个 GPU 节点上提供单个模型，整个应用程序是一个 YAML 块，没有处理程序代码，没有模型存档器，也没有手工组装的 GPU 和 EFA 堆栈。多节点 Ray LLM DLC 提供经过测试的推理堆栈，KubeRay 编排 Ray 集群，NIXL over EFA 在节点之间承载 KV 缓存。您的工作是配置它，而不是构建它。

运行多节点推理的常见模式包括张量和管道并行（对一个实例来说太大的模型进行分片）、数据并行（复制模型以提高吞吐量）和预填充/解码分解（将推理的两个阶段分离到不同的节点上）。

从这里，您可以扩展解码副本以获得更高的吞吐量，在更大的 GPU 实例上迁移到具有张量或管道并行性的更大模型，或者将额外的库分层到需要它们的模型的相同测试基础上。有关完整代码、当前图像标签列表以及底层机制，请参阅[随附存储库](https://github.com/aws-samples/sample-aws-deep-learning-containers/tree/main/inference/ray-serve/ray-serve-multi-node)、[Ray LLM DLC 可用图像页](https://aws.github.io/deep-learning-containers/reference/available_images/#ray-llm)、[Ray Serve LLM 预填充/解码文档](https://docs.ray.io/en/latest/serve/llm/user-guides/prefill-decode.html) 和 [EFA文档](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html)。
