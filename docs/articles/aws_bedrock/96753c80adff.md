# 用 Amazon Bedrock Custom Model Import 的 log probability 支持解锁模型洞察

你可以使用 [Amazon Bedrock Custom Model Import](https://aws.amazon.com/bedrock/custom-model-import/)，把已在别处微调好的定制模型（例如 Llama、Mistral 和 Qwen）无缝集成到 Amazon Bedrock 中。整个体验完全无服务器（serverless），将基础设施管理工作降到最低，同时让你导入的模型获得与 Amazon Bedrock 原生模型相同的统一 API 访问能力。你的定制模型可受益于自动扩缩容、企业级安全性，以及与 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails) 和 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases) 等 Amazon Bedrock 功能的原生集成。

了解模型对自己的预测有多大把握，对于构建可靠的 AI 应用至关重要，尤其是在处理可能遇到特定领域问题的专用定制模型时。

如今 Custom Model Import 已加入 log probability 支持，你可以在 token 级别获取模型对其预测的置信度信息。这一增强能力让你对模型行为有更强的可见性，并为模型评估、置信度评分和高级过滤技术带来新的可能。

本文探讨 log probability 在 Amazon Bedrock 中如何与导入的模型配合工作。你将了解什么是 log probability、如何在 API 调用中启用它，以及如何解读返回的数据。我们还会重点介绍一些实际应用——从检测潜在的幻觉，到优化 RAG 系统、评估微调模型——展示这些洞察如何改进你的 AI 应用，帮助你用定制模型构建更值得信赖的解决方案。

## 理解 log probability

在语言模型中，log probability 表示模型为序列中某个 token 赋予的概率的对数。这些数值表明模型对它所生成或处理的每个 token 有多大把握。log probability 以负数表示，数值越接近零表示置信度越高。例如，log probability 为 -0.1 大致对应 90% 的置信度，而 -3.0 则对应约 5% 的置信度。通过查看这些数值，你可以分辨出模型何时高度确定、何时把握不足。log probability 提供了一种量化度量，反映模型认为每个生成的 token 有多大概率，从而让你对输出的置信程度获得有价值的洞察。通过分析它们，你可以：

- **衡量整段回答的置信度**：评估模型对其输出不同部分的把握程度，帮助你识别哪些地方它很确定、哪些地方不确定。
- **为输出打分并比较**：通过把 log probability 相加或取平均来比较整体序列的似然，从而对多个模型输出排序或过滤。
- **检测潜在的幻觉**：识别 token 级别置信度的骤降，从而标出可能需要核实或复核的片段。
- **通过提前剪枝降低 RAG 成本**：基于检索到的上下文运行简短、低成本的草稿生成，计算这些草稿的 log probability，并尽早丢弃得分低的候选，避免不必要的全长生成或昂贵的重排序，同时只在 pipeline 中保留最有希望的上下文。
- **构建能感知置信度的应用**：依据确定程度调整系统行为——例如触发澄清式 prompt、提供回退回答，或标记出来交由人工复核。

总体而言，log probability 是解读和调试模型回答的有力工具，并附带可度量的确定性——对于这样一类应用尤其有价值：理解模型为何以某种方式回答，可能与回答本身同样重要。

## 前提条件

要在 Amazon Bedrock 的 custom model import 中使用 log probability 支持，你需要：

- 一个可用的 [AWS 账户](https://signin.aws.amazon.com/signup?request_type=builderId)，且具备访问 Amazon Bedrock 的权限
- 一个在 2025 年 7 月 31 日（log probability 支持发布之日）之后通过 Custom Model Import 功能在 Amazon Bedrock 中创建的定制模型
- 通过 Amazon Bedrock Runtime 调用模型所需的适当 [AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 权限

## Amazon Bedrock 中的 log probability 支持

借助本次发布，Amazon Bedrock 现在允许通过 Custom Model Import 功能导入的模型在推理响应中返回 token 级别的 log probability。

通过 Amazon Bedrock [InvokeModel API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_InvokeModel.html) 调用模型时，你可以在 JSON 请求体中设置 `"return_logprobs": true` 来获取 token 的 log probability。启用该标志后，模型的响应会包含额外字段，为 prompt token 和生成的 token 都提供 log probability，以便客户分析模型对其预测的置信度。这些 log probability 让你可以定量评估定制模型在处理输入和生成响应时的把握程度。这种细粒度指标有助于更好地评估响应质量、排查意外输出，以及优化 prompt 或模型配置。

我们通过一个示例来演示如何在启用 log probability 的情况下调用 Amazon Bedrock 上的定制模型，并查看输出格式。假设你已将某个定制模型（例如一个微调过的 Llama 3.2 1B 模型）导入 Amazon Bedrock，并已取得该模型的 Amazon Resource Name (ARN)。你可以使用 Amazon Bedrock Runtime SDK（本例中为 Python 的 Boto3）调用该模型，如下例所示：

```
import boto3, json

bedrock_runtime = boto3.client('bedrock-runtime')  
model_arn = "arn:aws:bedrock:<<aws-region>>:<<account-id>>:imported-model/your-model-id"

# Define the request payload with log probabilties enabled
request_payload = {
    "prompt": "The quick brown fox jumps",
    "max_gen_len": 50,
    "temperature": 0.5,
    "stop": [".", "\n"],
    "return_logprobs": True   # Request log probabilities
}

response = bedrock_runtime.invoke_model(
    modelId=model_arn,
    body=json.dumps(request_payload),
    contentType="application/json",
    accept="application/json"
)

# Parse the JSON response
result = json.loads(response["body"].read())
print(json.dumps(result, indent=2))
```

在上面的代码中，我们向自定义导入的模型发送了一个 prompt——`"The quick brown fox jumps"`。我们配置了标准推理参数：最大生成长度为 50 个 token、适中的 temperature 0.5 以获得适度的随机性，以及一个停止条件（句号或换行符）。`"return_logprobs":True` 参数告诉 Amazon Bedrock 在响应中返回 log probability。

`InvokeModel` API 返回的 JSON 响应包含三个主要组成部分：标准的生成文本输出、关于生成过程的元数据，以及如今针对 prompt token 和生成 token 的 log probability。这些数值揭示了模型对每个 token 预测的内部置信度，因此你不仅能知道产生了什么文本，还能知道模型在过程的每一步有多确定。下面是针对 `"quick brown fox jumps"` 这个 prompt 的示例响应，其中展示了 log probability（以负数形式出现）：

下面逐一拆解这些信息告诉了我们模型内部处理的哪些情况：

- `generation`：这是模型实际生成的文本（在我们的示例中，它是我们发送给模型的 prompt 的续写）。这是任何模型调用通常都会返回的同一个字段。
- `prompt_token_count` 和 `generation_token_count`：分别表示输入 prompt 和输出中的 token 数量。在我们的示例中，prompt 被分词为六个 token，模型在补全中生成了五个 token。
- `stop_reason`：生成停止的原因（`"stop"` 表示模型在某个停止序列或文本结束处自然停止，`"length"` 表示达到了最大 token 上限，等等）。在我们的例子中它显示为 `"stop"`，表示模型自行停止，或因为我们提供的停止条件而停止。
- `prompt_logprobs`：该数组为 prompt 中的每个 token 提供 log probability。模型处理你的输入时，会基于目前为止看到的内容不断预测接下来应该是什么。这些数值衡量你的 prompt 中哪些 token 是模型预料之中的、哪些是出乎意料的。第一个条目是 `None`，因为最初的 token 没有任何前置上下文。没有先前信息，模型无法预测任何东西。后续每个条目包含映射到对应 log probability 的 token ID。我们已将这些 ID 转换为可读文本，并把 log probability 转换为百分比以便理解。你可以观察到模型在处理熟悉的序列时置信度逐步上升。例如，在看到 *The quick brown,* 之后，模型以 95.1% 的置信度预测出 *fox*。在看到截至 *fox* 的完整上下文之后，它以 81.1% 的置信度预测出 *jumps*。许多位置会显示多个 token 及其概率，揭示出模型考虑过的其他备选。例如在第二个位置，模型既评估了 *The*（2.7%）也评估了 *Question*（30.6%），这意味着模型认为两个 token 在该位置都可行。这种额外的可见性帮助你了解模型在哪里权衡了备选，也能揭示它在何处更不确定、或难以在多个选项之间做出选择。某些 token 的概率明显偏低——*quick* 只得到 0.01%——表明模型认为这些词在其上下文中出乎意料。整体模式讲出了一个清晰的故事：单个词最初获得的概率较低，但当完整的 *quick brown fox jumps* 短语逐步成形后，模型的置信度大幅上升，说明它认出了这是一个熟悉的表达。当你的 prompt 中多个 token 持续获得低概率时，你的措辞对模型来说可能比较少见。这种不确定性会影响补全的质量。利用这些洞察，你可以重新组织 prompt，使其更好地贴合模型在训练数据中遇到的模式。
- `logprobs`：该数组包含模型生成输出中每个 token 的 log probability。格式类似：一个把 token ID 映射到对应 log probability 的字典。解码这些数值后，我们可以看到 *over*、*the*、*lazy* 和 *dog* 这些 token 的概率都很高。这表明模型意识到自己正在补全那个著名的短语 *the quick brown fox jumps over the lazy dog*——这是一个常见的全字母句（pangram），模型显然对它相当熟悉。相比之下，最后那个句号（换行）token 的概率要低得多（30.3%），揭示出模型对如何结束这句话并不确定。这很合理，因为模型有多个有效选项：用句号结束句子、继续补充更多内容，或者干脆改用另一种标点。

## log probability 的实际用例

Custom Model Import 功能提供的 token 级 log probability，为了解模型的决策过程提供了有价值的洞察。这些指标通过揭示模型对每个生成 token 的置信水平，改变了你与定制模型交互的方式。以下是一些有影响力的用法：

### 对多个补全结果排序

你可以用 log probability 对同一 prompt 的多个生成输出进行定量排序。当你的应用需要在不同的可能补全之间做选择时——无论是摘要、翻译还是创意写作——你可以通过对其所有 token 的 log probability 取平均或求和，计算出每个补全的整体似然。

**示例：**

**Prompt**：`Translate the phrase "Battre le fer pendant qu'il est chaud"`

- **补全 A：**`"Strike while the iron is hot"`（平均 log probability：-0.39）
- **补全 B：**`"Beat the iron while it is hot."`（平均 log probability：-0.46）

在这个例子中，*补全 A* 获得更高的 log probability 分数（更接近零），表明模型认为这个意译版本比更直译的*补全 B* 更自然。这种数值化的方法让你的应用可以自动选出最可能的输出，或按模型的置信水平对多个候选排序后呈现。

这种排序能力不止适用于翻译，还适用于许多存在多个有效输出的场景——包括内容生成、代码补全和创意写作——它提供了一种基于模型置信度的客观质量指标，而不必只依赖主观的人工判断。

### 检测幻觉与低置信度回答

在处理模糊的 prompt、复杂的查询或超出其专长的话题时，模型可能会产生幻觉——听起来合理但事实上不正确的陈述。log probability 提供了一种实用的方法来检测这类情况：它揭示模型内部的不确定性，帮助你在输出看起来很有把握时也能识别出可能不准确的信息。

通过分析 token 级的 log probability，你可以识别出回答中模型可能不确定的部分，即使文本表面上显得很有把握。在检索增强生成（RAG）系统中，这项能力尤其有价值，因为这类系统要求回答立足于检索到的上下文。当模型有相关信息可用时，它通常以更高的置信度生成答案。反之，如果多个 token 的置信度都偏低，就说明模型可能在没有足够支撑信息的情况下生成内容。

**示例：**

- **Prompt**：`"Explain how the Portfolio Synergy Quotient (PSQ) is applied in multi-asset investment strategies?"`
- **模型输出**：`"The PSQ is a measure of the diversification benefits of combining different asset classes in a portfolio."`

在这个例子中，我们故意询问了一个虚构的指标——Portfolio Synergy Quotient (PSQ)——以演示 log probability 如何揭示模型回答中的不确定性。尽管模型为这个并不存在的金融概念给出了听起来很专业的定义，但 token 级的置信度分数却道出了实情。下面显示的置信度分数是通过对模型返回的 log probability 应用指数函数得出的。

- *PSQ* 显示中等置信度（63.8%），表明模型识别出了缩写形式，但对这个具体术语并不十分确定。
- 像 *classes*（98.2%）和 *portfolio*（92.8%）这样的常见金融术语表现出高置信度，很可能是因为它们是金融语境中广泛使用的标准概念。
- 关键的连接性概念置信度明显偏低：*measure*（14.0%）和 *diversification*（31.8%），揭示出模型在试图解释 PSQ 的含义或作用时的不确定性。
- 像 *is*（45.9%）和 *of*（56.6%）这样的功能词处于中等置信度水平，说明模型对整个解释的结构并不确定。

通过识别这些低置信度片段，你可以在应用中实施有针对性的防护措施——例如把内容标记出来以待核实、检索额外上下文、生成澄清性问题，或对敏感信息应用置信度阈值。这种方法有助于构建更可靠的 AI 系统，使其能够区分高置信度的知识和不确定的回答。

### 监控 prompt 质量

在为你的应用设计 prompt 时，log probability 能揭示模型对你的指令理解得有多好。如果最初几个生成的 token 概率异常低，通常说明模型难以理解你在问什么。

通过跟踪最初若干 token（通常是前 5–10 个生成的 token）的平均 log probability，你可以定量衡量 prompt 的清晰度。上下文清晰、结构良好的 prompt 通常会产生更高的概率，因为模型立刻就知道该做什么。含糊或描述不足的 prompt 往往在初始 token 上给出更低的似然，因为模型在犹豫或寻找方向。

**示例：**

客户服务回复的 prompt 对比：

- **基础 prompt：**`"Write a response to this customer complaint: I ordered a laptop 2 weeks ago and it still hasn't arrived."` 前五个 token 的平均 log probability：-1.215（置信度较低）
- **优化后的 prompt：**`"You are a senior customer service manager with expertise in conflict resolution and customer retention. You work for a reputable electronics retailer that values customer satisfaction above all else. Your task is to respond to the following customer complaint with professionalism and empathy. Customer Complaint: I ordered a laptop 2 weeks ago and it still hasn't arrived."` 前五个 token 的平均 log probability：-0.333（置信度较高）

优化后的 prompt 产生更高的 log probability，说明精确的指令和清晰的上下文降低了模型的不确定性。这种方法不对 prompt 质量作绝对判断，而是让你衡量不同版本之间的相对改进。你可以直接观察到具体要素——角色定义、上下文细节和明确的期望——如何提升模型置信度。通过系统地衡量不同 prompt 迭代的这些置信度分数，你建立起一套用于 prompt engineering 的定量框架，它精确地揭示你的指令在何时、以何种方式变得不够清晰，从而实现持续的数据驱动优化。

### 通过提前剪枝降低 RAG 成本

在传统的 RAG 实现中，系统会检索 5–20 篇文档，并用这些检索到的上下文生成完整回答。这种做法推高了推理成本，因为每段检索到的上下文无论实际是否有用都会消耗 token。

log probability 通过提前剪枝（early pruning）实现了一种更具成本效益的替代方案。与其立即完整处理检索到的文档，不如：

- 基于每段检索到的上下文生成草稿回答
- 计算这些简短草稿的平均 log probability
- 按平均 log probability 分数对上下文排序
- 丢弃低于置信度阈值的低分上下文
- 只使用置信度最高的上下文生成完整回答

这种做法之所以有效，是因为包含相关信息的上下文在草稿生成阶段会产生更高的 log probability。当模型遇到有用的上下文时，它生成文本时更有把握，体现为 log probability 更接近零。反之，无关或枝节的上下文会产生更不确定的输出，log probability 更低。

通过在完整生成之前过滤上下文，你可以在减少 token 消耗的同时保持甚至提升答案质量。这把过程从蛮力式做法转变为有针对性的 pipeline，只把完整生成导向那些模型在其中表现出真实把握的上下文。

### 微调评估

当你针对特定领域微调了模型后，log probability 提供了一种定量评估训练效果的方法。通过分析回答中的置信度模式，你可以判断模型是否形成了恰当的校准（calibration）——在领域相关的正确答案上表现出高置信度，而在其他方面表现出适当的不确定性。

一个校准良好的微调模型，应当在其专长领域内为准确的信息赋予更高的概率，而在其训练领域之外保持较低的置信度。校准问题主要出现在两种形式上。过度自信（overconfidence）出现在模型为不正确的回答赋予高概率时，说明它没有正确学到自身知识的边界。信心不足（under confidence）表现为尽管给出了准确答案但概率持续偏低，说明训练可能没有充分强化正确的模式。

通过在不同场景下系统地测试模型并分析 log probability，你可以找出需要额外训练的地方，或发现当前方法中的潜在偏差。这形成了一个数据驱动的反馈回路，支撑迭代改进，确保模型在其预期范围内可靠运行，同时在其专长边界上保持适当的分寸。

## 开始使用

以下是开始对通过 Amazon Bedrock Custom Model Import 功能导入的模型使用 log probability 的方法：

- **在 API 调用中启用 log probability：**在调用自定义导入的模型时，把 `"return_logprobs": true` 加入请求载荷。该参数同时适用于 `InvokeModel` 和 `InvokeModelWithResponseStream` API。从熟悉的 prompt 入手，观察模型对哪些 token 预测的置信度高、对哪些感到意外。
- **分析定制模型中的置信度模式：**考察你微调过或做过领域适配的模型如何回应不同输入。log probability 揭示你的模型是否针对具体领域得到了恰当的校准——在该确定的地方表现出高置信度。
- **开发能感知置信度的应用：**落地幻觉检测、回答排序和内容核实等实际用例，让你的应用更稳健。例如，你可以把回答中置信度低的片段标记出来交由人工复核，或从多次生成中挑选置信度最高的回答。
