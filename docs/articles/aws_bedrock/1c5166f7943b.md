# 在单个 Amazon Bedrock 知识库中通过元数据过滤实现 RAG 应用的多租户

[Amazon Bedrock](https://aws.amazon.com/bedrock/knowledge-bases/) 是一项全托管服务，可从领先的 AI 公司和 AWS 提供多种高性能基础模型（FM）。[Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 提供全托管的端到端[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）工作流，通过引入贵公司数据源中的上下文信息，构建高度准确、低延迟、安全且可定制的生成式 AI 应用。

组织需要跨不同业务单元（包括公司、部门甚至个人）控制对自身数据的访问，同时保持可扩展性。当组织试图手动拆分数据源时，往往会制造不必要的复杂性，并撞上服务限制。本文演示 Amazon Bedrock Knowledge Bases 如何帮助您有效扩展数据管理，同时在不同管理级别上维持恰当的访问控制。

其中一种策略是使用 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）文件夹结构配合 Amazon Bedrock Knowledge Bases 元数据过滤，在单个知识库内实现高效的数据切分。此外，我们还会深入探讨如何集成 Amazon Bedrock Knowledge Bases 可用的常见向量数据库方案，以及这些集成如何带来高级的元数据过滤与查询能力。

## 为可扩展的知识库组织 S3 文件夹结构

服务多个客户的组织需要一种安全且可扩展的方式，在保持高效访问控制的同时把每个客户的数据隔离开。缺乏恰当的数据隔离，企业就有可能在客户之间泄露敏感信息，或者搭出复杂且难以维护的系统。本文聚焦于在同一管理级别内跨多个业务单元维持访问控制。

一项关键策略是使用 S3 文件夹结构配合 Amazon Bedrock Knowledge Bases 元数据过滤，在单个知识库内实现高效的数据隔离。与其为每个客户单独创建知识库，不如使用一个结构良好的 S3 文件夹层级来组织统一的知识库。例如，设想一家为多家医疗机构管理文档的咨询公司——每个客户的敏感病历与运营文档必须严格隔离。Amazon S3 结构可能如下所示：

`s3://amzn-s3-demo-my-knowledge-base-bucket/customer-data/`

` s3://amzn-s3-demo-my-knowledge-base-bucket/customer-data/customerA/`

` s3://amzn-s3-demo-my-knowledge-base-bucket/customer-data/customerA/policies/`

` s3://amzn-s3-demo-my-knowledge-base-bucket/customer-data/customerA/procedures/`

` s3://amzn-s3-demo-my-knowledge-base-bucket/customer-data/customerB/`

` s3://amzn-s3-demo-my-knowledge-base-bucket/customer-data/customerB/policies/`

` s3://amzn-s3-demo-my-knowledge-base-bucket/customer-data/customerB/procedures/`

这种结构确保客户 A 的医疗文档与客户 B 的数据完全隔离。当与 Amazon Bedrock Knowledge Bases 元数据过滤结合使用时，您可以验证与客户 A 关联的用户只能访问本组织的文档，而客户 B 的用户只能看到自己的数据——从而在单一、高效的知识库基础设施上维持严格的数据边界。

Amazon Bedrock Knowledge Bases 的元数据过滤能力进一步强化了这种隔离：它允许您为文档打上客户专属标识符和其他相关属性。这些元数据过滤器提供了额外的安全与组织层次，确保查询只返回来自相应客户数据集的结果。

## 解决方案概览

下图通过一个示例用例，提供 AWS 服务与功能的高层概览。尽管示例使用客户 A 和客户 B 进行说明，它们也可以代表具有不同合规要求的不同业务单元（例如部门、公司或团队），而不只是单个客户。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/26/ML-16728-arch-diagram.png)

工作流包含以下步骤：

- 客户数据连同标明数据归属及其他属性的元数据，一起上传到 S3 桶中的特定文件夹。
- 包含客户数据与元数据的 S3 桶被配置为知识库数据源。Amazon Bedrock Knowledge Bases 从源存储库摄取数据及其元数据，并执行知识库同步。
- 客户通过前端应用，带着元数据过滤器向 Amazon Bedrock 知识库发起查询。必须设置访问控制元数据过滤器，确保客户只能访问属于自己的数据；客户还可以应用额外过滤器以进一步细化查询结果。该组合查询与过滤器被传给 `RetrieveAndGenerate` API。
- `RetrieveAndGenerate` API 处理核心 RAG 工作流。它包含若干子步骤：用户查询被转换为向量表示（embedding）。利用查询 embedding 与元数据过滤器，从知识库中检索相关文档。原始查询用检索到的文档进行增强，为大语言模型（LLM）提供上下文。LLM 基于增强后的查询与检索到的上下文生成回答。
- 最后，生成的回答被送回给用户。

在涉及敏感信息或需要访问控制的场景中实现 Amazon Bedrock Knowledge Bases 时，开发者必须在应用代码中实现恰当的元数据过滤。未能强制执行适当的基于元数据的过滤，可能导致对知识库内敏感文档的未授权访问。元数据过滤是一道关键的安全边界，应在所有查询中一致地应用。有关实现安全元数据过滤实践的全面指引，请参阅 [Amazon Bedrock 知识库安全文档。](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html)

## 实现元数据过滤

对于本用例，两个具体示例客户——客户 A 与客户 B——分别对应不同的专有合规文档。客户与文件夹数量可以按客户规模扩展到 N。我们将使用以下公开文档，它们将存放在各自客户的 S3 文件夹中。客户 A 需要 [Architecting for HIPAA Security and Compliance on AWS](https://docs.aws.amazon.com/pdfs/whitepapers/latest/architecting-hipaa-security-and-compliance-on-aws/architecting-hipaa-security-and-compliance-on-aws.pdf) 文档。客户 B 需要访问 [Using AWS in the Context of NHS Cloud Security Guidance ](https://docs.aws.amazon.com/pdfs/whitepapers/latest/nhs-cloud-security-guidance-using-aws/nhs-cloud-security-guidance-using-aws.pdf) 文档。

- 创建一个 JSON 文件，表示客户 A 与客户 B 对应的元数据：

以下是客户 A 数据的 JSON 元数据：

`{ "metadataAttributes": { "customer": "CustomerA", "documentType": "HIPAA Compliance Guide", "focus": "HIPAA Compliance", "publicationYear": 2022, "region": "North America" }}`

以下是客户 B 数据的 JSON 元数据：

`{ "metadataAttributes": { "customer": "CustomerB", "documentType": "NHS Compliance Guidance", "focus": "UK Healthcare Compliance", "publicationYear": 2023, "region": "Europe" }}`

- 单独保存这些文件，命名约定为 *<filename>.pdf.metadata.JSON*，并将它们存放在存放源文档的同一个 S3 文件夹或前缀中。对于客户 A，将元数据文件命名为 *architecting-hipaa-compliance-on-aws.pdf.metadata.json* 并上传到客户 A 文档对应的文件夹。对客户 B 重复这些步骤。![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/26/ML-16728-second.png)
- 创建 Amazon Bedrock 知识库。相关说明见[在 Amazon Bedrock Knowledge Bases 中连接数据源创建知识库](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-create.html)
- 创建知识库后，您可以同步数据源。更多细节见[将数据与您的 Amazon Bedrock 知识库同步](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-data-source-sync-ingest.html)。

## 实现按字段分块

Amazon Bedrock Knowledge Bases 支持多种用于 Amazon S3 元数据过滤的文档类型。支持的文件格式包括：

- 纯文本（.txt）
- Markdown（.md）
- HTML（.html）
- Microsoft Word 文档（.doc 和 .docx）
- CSV 文件（.csv）
- Microsoft Excel 电子表格（.xls 和 .xlsx）

处理 CSV 数据时，客户常常希望按 CSV 文档中的特定字段进行分块，以便对数据检索获得更细粒度的控制，并提升查询的效率与准确性。通过基于字段建立逻辑划分，用户无需处理整个数据集即可快速访问相关的数据子集。

此外，按字段分块有助于组织与维护大型数据集，便于更新或修改特定部分而不影响整体。这种细粒度支持更好的版本控制与数据血缘追踪，而这些对数据完整性与合规至关重要。聚焦相关分块可以提升 LLM 的表现，最终在组织内带来更准确的洞见与更好的决策流程。更多信息见[Amazon Bedrock Knowledge Bases 现已支持高级解析、分块与查询重构，让基于 RAG 的应用对准确性拥有更强的控制。](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-knowledge-bases-now-supports-advanced-parsing-chunking-and-query-reformulation-giving-greater-control-of-accuracy-in-rag-based-applications/)

## 为 Amazon Bedrock API 应用元数据过滤

您可以调用 Amazon Bedrock API `RetrieveAndGenerate` 查询知识库，并使用指定的 FM 或推理配置文件（inference profile）基于检索结果生成回答。响应只引用与查询相关的来源。

以下 Python Boto3 示例 API 调用应用元数据过滤来检索客户 B 的数据，并在 `RetrieveAndGenerate` 中使用指定的 FM（Anthropic 的 Claude 3 Sonnet）基于检索结果生成回答：

```
response = bedrock_client.retrieve_and_generate(
    input={
    "text": "Summarize NHS compliance guidance."
},
    retrieveAndGenerateConfiguration={
    "type": "KNOWLEDGE_BASE",
    "knowledgeBaseConfiguration": {
            'knowledgeBaseId': 'example_knowledge_base_id’,
        "modelArn": "arn:aws:bedrock:{}::foundation-model/anthropic.claude-3-sonnet-20240229-v1:0".format(region),
        "retrievalConfiguration": {
            "vectorSearchConfiguration": {
                "numberOfResults": 5,
                "filter": {
                    "equals": {
                        "key": "customer",
                        "value": ‘CustomerB’
                    }
                }
            }
        }
    }
})
```

以下 [GitHub 仓库](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/rag/knowledge-bases/use-case-examples/metadata-filter-access-control) 提供了一个 notebook，您可以照着它在自己 AWS 账户中部署一个通过元数据过滤实现访问控制的 Amazon Bedrock 知识库。

## 将现有向量数据库与 Amazon Bedrock Knowledge Bases 集成并校验元数据

构建可扩展解决方案时，可以通过多种方式利用 AWS 服务与合作伙伴产品创建向量数据库。如果尚无向量数据库，您可以使用 Amazon Bedrock Knowledge Bases，借助 [Amazon OpenSearch Serverless Service](https://aws.amazon.com/opensearch-service/features/serverless/)、[Amazon Aurora PostgreSQL Serverless](https://aws.amazon.com/rds/aurora/serverless/) 或 [Amazon Neptune Analytics](https://aws.amazon.com/neptune/) 创建向量存储 embedding，也可以指定受 [Redis Enterprise Cloud](https://aws.amazon.com/marketplace/pp/prodview-mwscixe4ujhkq?sr=0-1&ref_=beagle&applicationId=AWSMPContessa)、[带 pgvector 扩展的 Amazon Aurora PostgreSQL](https://aws.amazon.com/about-aws/whats-new/2023/07/amazon-aurora-postgresql-pgvector-vector-storage-similarity-search/)、[MongoDB Atlas](https://www.mongodb.com/products/platform/atlas-database) 或 [Pinecone](https://www.pinecone.io/?utm_term=pinecone%20db&utm_campaign=Brand+-+US/Canada&utm_source=adwords&utm_medium=ppc&hsa_acc=3111363649&hsa_cam=16223687665&hsa_grp=133738612775&hsa_ad=582256510975&hsa_src=g&hsa_tgt=kwd-1628011569784&hsa_kw=pinecone%20db&hsa_mt=p&hsa_net=adwords&hsa_ver=3&gad_source=1&gclid=Cj0KCQjwrp-3BhDgARIsAEWJ6SwGphaGtJGKo3NssrldzymnBOhpsOymBJ39HCgibOjj9qHaVjtewdsaAsH8EALw_wcB) 支持的现有向量数据库。创建知识库并摄取或同步数据后，附加在数据上的元数据将被摄取，并自动填充到向量数据库中。

本节回顾如何使用 OpenSearch Serverless、带 pgvector 扩展的 Aurora PostgreSQL 以及 Pinecone，把元数据过滤纳入现有向量数据库并加以校验。要了解如何设置各个向量数据库，请按照[为您自己的知识库向量存储准备前提条件](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-setup.html)中的说明操作。

### 使用 OpenSearch Serverless 作为知识库向量存储

借助 OpenSearch Serverless 的向量数据库能力，您可以实现语义搜索、基于 LLM 的 RAG 以及推荐引擎。要在每个使用 OpenSearch Serverless 向量数据库的 Amazon Bedrock 知识库中处理业务段之间的数据隔离，请使用元数据过滤。元数据过滤让您可以在 OpenSearch Serverless 向量数据库内部切分数据。当您希望为文档添加描述性数据，以便在搜索中获得更强控制与更细粒度时，这很有用。

每个 OpenSearch Serverless 仪表板都有一个可用于添加文档和查询数据库的 URL；该 URL 的结构为 `domain-endpoint/_dashboard`。

创建向量数据库索引后，您可以在请求体中使用 JSON 查询选项，通过元数据过滤有选择地检索条目。例如，要返回属于客户 A 的记录，可以使用以下请求：

```
GET <index_name>/_search
{
  "query": {
    "match": {
      "customer": "CustomerA"
    }
  }
}
```

该查询将返回一个 JSON 响应，其中包含标记为属于客户 A 的文档索引。

### 使用带 pgvector 扩展的 Aurora PostgreSQL 作为知识库向量存储

Pgvector 是 PostgreSQL 的一个扩展，允许您把关系数据库扩展为高维向量数据库。它把每个文档的向量存储在数据库表中的单独一行。有关创建 Aurora PostgreSQL 表以用作知识库向量存储的详情，请参阅[将 Aurora PostgreSQL 用作 Amazon Bedrock 的知识库](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraPostgreSQL.VectorDB.html)。

当把知识库的向量索引存储在 Aurora 数据库集群中时，请确保在开始数据摄取之前，索引表已为元数据文件中的每个元数据属性包含一列。

继续客户 A 的示例，该客户需要 [Architecting for HIPAA Security and Compliance on AWS](https://docs.aws.amazon.com/pdfs/whitepapers/latest/architecting-hipaa-security-and-compliance-on-aws/architecting-hipaa-security-and-compliance-on-aws.pdf) 文档。

以下是客户 A 数据的 JSON 元数据：

`{ "metadataAttributes": { "customer": "CustomerA", "documentType": "HIPAA Compliance Guide", "focus": "HIPAA Compliance", "publicationYear": 2022, "region": "North America" }}`

您创建的 PostgreSQL 表 schema 必须包含四个基本列，分别用于 ID、文本内容、向量值和服务托管元数据；还必须为对应元数据文件中的每个元数据属性包含额外的元数据列（`customer`、`documentType`、`focus`、`publicationYear`、`region`）。这样 pgvector 就能直接在数据库表上运行查询，执行高效的向量搜索与相似度比较。下表汇总了这些列。

| **列名** | **数据类型** | **说明** |
| --- | --- | --- |
| id | UUID 主键 | 包含每条记录的唯一标识符 |
| chunks | 文本 | 包含数据源原始文本的分块 |
| embedding | 向量 | 包含数据源的向量 embedding |
| metadata | JSON | 包含执行来源归属以及支持数据摄取与查询所需的 Amazon Bedrock 托管元数据。 |
| customer | 文本 | 包含客户 ID |
| documentType | 文本 | 包含文档类型 |
| focus | 文本 | 包含文档重点 |
| publicationYear | 整数 | 包含文档发布的年份 |
| region | 文本 | 包含文档相关的 AWS 区域 |

在 [Amazon Bedrock 知识库数据摄取](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-data-source-sync-ingest.html)期间，这些列将被填充为相应的属性值。分块可以把单个文档拆分为多条独立记录（每条记录关联不同的 ID）。

这种 PostgreSQL 表结构可以高效存储与检索文档向量，利用 PostgreSQL 的稳健性和 pgvector 专门的向量处理能力，服务于推荐系统、搜索引擎或其他需要在高维空间做相似度搜索的系统。

采用这种方法，您可以通过为每个数据段创建数据库表，在表级别实现访问控制。表中还可以加入额外的元数据列，用于特定文档所有者（`user_id`）、标签等属性，从而在您把每个用户限制为只能查询包含其用户 ID（文档所有者）的行时，进一步启用并强制执行细粒度（行级）访问控制与结果过滤。

创建向量数据库表后，您可以使用 PostgreSQL 查询，通过元数据过滤有选择地检索条目。例如，要返回属于客户 A 的表记录，可以使用以下查询：

```
SELECT *
FROM bedrock_integration.bedrock_kb
WHERE customer = 'CustomerA';
```

该查询将返回包含标记为属于客户 A 的数据库记录的响应。

### 使用 Pinecone 作为知识库向量存储

Pinecone 是一个全托管的向量数据库，支持语义搜索、高性能搜索与相似度匹配。Pinecone 数据库可以以 Amazon Bedrock 知识库的形式集成到您的 AWS 环境，但需要先通过 Pinecone 控制台创建。有关在 Pinecone 中设置向量存储的详细文档，请参阅[Pinecone as a Knowledge Base for Amazon Bedrock](https://docs.pinecone.io/docs/amazon-bedrock)。之后，您可以使用 Amazon Bedrock 控制台集成这些数据库。有关 Pinecone 与 Amazon Bedrock 集成的更多信息，请参阅[Bring reliable GenAI applications to market with Amazon Bedrock and Pinecone](https://www.pinecone.io/amazon-bedrock/)。

您可以通过为每个索引添加描述性元数据，并利用这些元数据影响查询结果，来切分 Pinecone 数据库。Pinecone 支持字符串和字符串列表，用于按客户名称、客户行业等过滤向量搜索。Pinecone 还支持数字和布尔值。

使用元数据查询语言过滤输出（`$eq`、`$ne`、`$in`、`$nin`、`$and` 与 `$or`）。以下示例展示了一段元数据和将返回该索引的查询。示例中的 Python 查询演示如何从 Pinecone 数据库检索与客户 A 关联的记录列表。

```
pc = Pinecone(api_key="xxxxxxxxxxx")

index = pc.Index(<index_name>)

index.query(
    namespace="",
    vector=[0.17,0.96, …, 0.44],
    filter={
        "customer": {"$eq": "CustomerA"}
    },
    top_k=10,
    include_metadata=True # Include metadata in the response.
)
```

该查询将返回包含标记为属于客户 A 的数据库记录的响应。

## 通过多个数据源增强扩展能力

Amazon Bedrock Knowledge Bases 现支持跨 AWS 账户的多个数据源。Amazon Bedrock Knowledge Bases 最多可从五个数据源摄取数据，提升知识库的全面性与相关性。该功能让拥有复杂 IT 系统的客户能够把数据纳入生成式 AI 应用，而无需重构或迁移数据源。当数据位于不同 AWS 账户时，它也为您扩展 Amazon Bedrock 知识库提供了灵活性。

这些功能包括跨账户数据访问，支持跨不同账户将 S3 桶配置为数据源，以及在移除数据源时保留或删除数据的高效数据管理选项。这些增强减少了创建多个知识库或冗余数据副本的需求。

## 清理

完成本文中的步骤后，请务必清理资源，以免产生不必要的费用。要删除 Amazon Bedrock 知识库，请导航到 Amazon Bedrock 控制台，选择您的知识库，然后从“Actions”下拉菜单中选择“Delete”。如果您为测试创建了向量数据库，请记得删除 OpenSearch Serverless 集合、停止或删除 Aurora PostgreSQL 实例，并删除创建的 Pinecone 索引。此外，考虑删除专为本文示例上传到 S3 桶的测试文档，以避免存储费用。检查并清理为此演示创建的任何 IAM 角色或策略（如果不再需要）。

Amazon Bedrock Knowledge Bases 会对数据索引和查询收费，但 S3 与向量数据库的底层存储在这些资源被删除之前会持续产生费用。具体定价详情请参阅 [Amazon Bedrock 定价页面](https://aws.amazon.com/bedrock/pricing/)。

## 结论

本文介绍了构建可扩展、安全且分段化的 Amazon Bedrock 知识库的若干关键策略，包括使用 S3 文件夹结构、元数据来组织数据源，以及在单个知识库内进行数据切分。使用元数据过滤创建针对特定数据段的自定义查询，有助于提升检索准确性并维护数据隐私。我们还探讨了为包括 OpenSearch Serverless、带 pgvector 扩展的 Aurora PostgreSQL 以及 Pinecone 在内的向量数据库集成并校验元数据。

通过在单个 Amazon Bedrock 知识库中整合多个业务段或客户数据，组织与分别创建和管理相比可以实现成本优化。改进的数据切分与访问控制措施有助于确保每个团队或客户只能访问与其领域相关的信息。增强的可扩展性有助于满足组织多样化的需求，同时维持必要的数据隔离与访问控制。

试试在 Amazon Bedrock Knowledge Bases 中使用元数据过滤，并与作者或在评论中分享您的想法与疑问。
