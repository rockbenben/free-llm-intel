# 使用 Amazon Bedrock AgentCore Observability 调试生产环境中的 agent

生产环境中的人工智能（AI）agent 可能无声无息地失败。它们可能返回看似合理却错误的答案、陷入无限的推理循环，或者选错工具却不触发任何错误告警。这些失败让调试生产环境中的 agent 行为变得困难，因为标准日志与指标并不能记录决策是如何做出的。

Amazon [Bedrock AgentCore Observability](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/AgentCore-Agents.html) 通过让你在指标、追踪与结构化日志这三个层面上洞察 agent 的执行过程，来应对这些调试难题。你可以跟踪每一步推理、检查工具调用，并准确定位执行从何处开始偏离预期。这种可见性让你从「发现出现了失败」进阶到「理解为什么失败」。即使没有抛出明确的错误，你也能追溯 agent 是如何推理的、选择了哪些工具、工作流在哪里断掉。在本文中，你将学习如何利用内置的可观测性能力调试生产环境中的 agent 失败。我们会逐一分析常见的失败模式，展示如何借助追踪与指标分析 agent 行为，并提供结构化的处理流程来解决问题，例如无限循环与工具调用失败。本文是两篇系列文章中的第 1 篇，第 2 篇将介绍性能优化与内存管理。

## 前提条件

在按本文中的演练步骤操作之前，请确认你已经具备所需的访问权限与工具。

你需要一个已开启 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 访问权限的 AWS 账户，熟悉 [Amazon CloudWatch 控制面板](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch_Dashboards.html)与基本的日志查询，并对 AWS [Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色与策略有可用的理解。你还需要为账户开启 [CloudWatch Transaction Search](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Transaction-Search.html)（参见「启用可观测性」一节），以及一个已部署的 Amazon Bedrock AgentCore agent，或者部署一个 agent 的权限。

## 理解 agent 的失败模式

AI agent 的失败方式与传统应用不同。你可能会看到执行成功、却仍返回错误答案、工作流不完整或工具使用异常的记录。这类问题常常出现在生产环境中却不触发标准错误告警，因而更难发现和诊断。多数生产问题可归入三类：质量、可靠性与效率。理解这些模式有助于你迅速收窄排查范围。

### 质量类失败

质量类失败发生在 agent 完成任务但返回错误结果的时候。监控系统常常显示执行成功，而用户收到的却是不准确的响应。幻觉与事实性错误频繁出现：agent 可能引用并不存在的政策，或者凭空生成数据来填补空白。在多 agent 系统中，当一个 agent 的输出成为另一个 agent 的输入时，这类错误会扩散。推理层面的问题也会浮现，agent 可能重复同样的错误计算，或者选择一个不合适的工具。遇到这种情况时，审查执行追踪有助于定位逻辑在哪里出错。

### 可靠性问题

可靠性问题会阻止 agent 完成其工作流。

工具调用失败是常见原因。agent 可能因凭证缺失而收到 401 错误，因角色缺少权限而收到 403 错误，或因输入无效而收到 400 错误。每种错误指向不同的根本原因。

你也可能遇到上下文丢失：agent 未能保留会话状态，把后续请求当作新对话处理。这通常说明会话管理或内存配置存在问题。

### 效率问题

效率问题影响的是成本与性能，而非正确性。高延迟会拖慢响应时间并降低用户参与度。当响应耗时过长时，用户会放弃交互或反复重试。过多的 token 消耗会增加成本却不改善结果。当 agent 生成过于冗长的响应、不必要地检索整份文档，或者重复调用工具而不是缓存结果时，你可能会看到这种情况。

## 你的调试工具箱

你可以通过三个可观测性层面来监控、追踪和分析 agent 行为：控制面板提供系统级可见性，追踪提供执行级的细节，指标则用于告警与趋势分析。这些能力协同工作，帮助你从「发现问题」走到「定位根本原因」。

### Amazon CloudWatch 控制面板

通过 Amazon CloudWatch 指标实时监控 agent 性能，包括会话量、延迟、token 使用量与错误率。这些指标让你在 agent、内存系统与工具集成之间获得可见性。

GenAI Observability 控制面板在一个统一视图中展示会话量、调用延迟、token 使用量与错误率。你可以按 agent ID、会话 ID 或时间范围筛选这些指标，聚焦于特定的性能模式。

当你发现异常时，如果延迟超出可接受的阈值，或者错误率飙升到正常水平之上，CloudWatch 告警会自动通知你。

### OpenTelemetry 追踪

控制面板在较高层次上展示系统行为，追踪则展示每个请求如何一步步执行。

Amazon Bedrock AgentCore 在 bedrock-agentcore 的 CloudWatch 命名空间下发出分布式追踪、结构化的 span 级日志与指标。这些遥测数据遵循 [OpenTelemetry](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-OpenTelemetry-Sections.html)（OTEL）协议，默认路由到 Amazon CloudWatch。如果你的组织使用 Datadog、Grafana Cloud 或 Elastic Observability，你可以把同样的遥测数据导出到这些后端，无需额外的埋点。

每条追踪都捕获完整的执行流程：推理步骤、工具调用、内存检索与最终输出。这种细粒度的可见性能精准定位执行从何处偏离预期行为，并展示导致该问题的决策顺序。

### 需要监控的关键指标

请关注三类指标：性能、资源使用与可靠性。

#### 性能指标

跟踪第 50、95 与 99 百分位的延迟。更高的延迟往往意味着下游存在瓶颈。请分别测量内存检索时间与工具响应时间，这有助于隔离出是哪个组件拖慢了执行。

#### 资源指标

会话时长揭示了使用模式。短会话可能说明用户受挫，长会话则可能暗示循环或复杂工作流。并发会话显示你的系统支持多少个活跃交互。token 使用量直接影响成本，请分别监控输入与输出 token 以找出低效之处。

#### 可靠性指标

错误率显示执行失败的频率。

请按类型细分：

- 身份验证错误。
- 授权错误。
- 校验错误。
- 超时错误。

任何一类出现飙升，都指向一个具体的排查方向。

### 启用可观测性

在开始调试之前，请为你的账户启用 CloudWatch Transaction Search。这使 Amazon Bedrock AgentCore 能够把追踪与指标数据发送到 CloudWatch。启用该设置后，服务会开始在你的 agent、内存系统与工具集成中收集可观测性数据。随后你可以通过 CloudWatch 控制面板与 Logs Insights 查询访问这些数据。

## 分步排查工作流

以下场景带你逐步诊断并解决两种最常见的生产失败。每个场景都会说明你观察到的症状、你运行的 Amazon CloudWatch Logs Insights 查询（每个通常耗时 2-3 分钟），以及你实施的修复。CloudWatch Logs Insights 是一项完全托管的查询服务，让你实时搜索和分析来自 Bedrock AgentCore 的结构化日志数据。你可以通过 CloudWatch 控制台的 Logs 菜单访问它。

### 场景 1：调试 agent 的无限循环

无限循环发生在 agent 缺少恰当的终止条件，或者未能识别自己已经犯错的时候。在深入日志之前，先理解三种最常见的根本原因可以加快你的诊断。

#### 无限循环的常见原因

prompt 设计不佳，是指 system prompt 没有确立清晰的终止条件。prompt 可能没有说明多少次尝试是合理的、何时应宣布任务无法完成，或何时应升级给人工处理。缺少循环检测，是指 agent 的推理框架无法识别重复动作。如果没有显式逻辑来跟踪先前的尝试，agent 就无从察觉「我已经试了三次，还是不行」这种模式。工具选择错误，是指 agent 持续选错工具，例如用 web search 工具而不是计算器去解一道数学题。

#### 需要留意的症状

当 agent 进入循环时，token 使用量会显著上升，会话时长也会超出正常范围。在某些情况下，agent 会在没有用户输入时生成多条响应。值得注意的是，错误率依然很低，因为 agent 并没有崩溃，它只是无法完成任务。

CloudWatch GenAI Observability 控制面板显示总共消耗了 266.9K token，而错误率为 0%。高 token 使用量加上零错误，正是无限循环的关键信号——agent 在运行，却无法完成它的任务。

#### 诊断 prompt 设计不佳

首先找出有问题的会话。在 CloudWatch Logs Insights 中运行以下查询，查找 token 使用量异常高的会话：

```
fields @timestamp, SessionId, TokenUsage
| filter TokenUsage > 10000
| sort TokenUsage desc
| limit 20
```

挑选消耗最高的那个，记下它的 SessionId。然后检查该会话内 agent 的推理模式：

```
fields @timestamp, @message, RequestId
| filter SessionId = "<SessionId>"
| filter Operation like /InvokeAgent/
| sort @timestamp asc
| limit 1000
```

会话详情显示单条追踪包含 177 个 span，平均延迟为 85,590 毫秒（约 85 秒）。正常的 agent 响应在 1–5 秒内完成。span 数量与执行时间共同证实 agent 进入了循环。

查找 agent 推理中重复出现的模式。下面这段日志序列是循环的明确迹象：

```
"Try using calculator tool with input 25"
"Result: 24.95"
"This is incorrect, try again"
"Try using calculator tool with input 25"
"Result: 24.95"
"This is incorrect, try again"
```

OpenTelemetry 追踪瀑布图揭示了根本原因：一个 system prompt 要求 agent「永不放弃」并且「一直尝试直到得到确切答案」，却没有终止条件。这一 prompt 设计缺陷直接导致了图 2 中那个包含 177 个 span 的循环。

要修复 prompt 设计问题，请在 agent 的 system prompt 中加入显式的终止条件。加入类似这样的指令：「如果你三次尝试同一操作都未成功，请停止，并向用户解释你为何无法完成任务。」为每个会话设置最大 token 限制（对话型 agent 通常是 5,000 到 10,000 个 token），并实现 10 到 15 步的推理步数上限作为硬性停止条件，不论内部逻辑如何。

#### 诊断循环检测失效

运行以下查询来检查工具调用序列：

```
fields @timestamp, ToolName, ToolInput, ToolOutput
| filter SessionId = "<SessionId>"
| filter Operation like /InvokeTool/
| sort @timestamp asc
```

结果中出现以下模式，即可确认循环检测失效：

```
2026-02-02 22:02:39 | calculate_percentage | {"value": 25, "total": 100} | 25.0
2026-02-02 22:02:45 | calculate_percentage | {"value": 25, "total": 100} | 25.0
2026-02-02 22:02:51 | calculate_percentage | {"value": 25, "total": 100} | 25.0
[repeated 40 more times]
```

CloudWatch Logs Insights 的结果显示，calculate_percentage 被重复调用了 86 次，输入几乎完全相同，返回的值类似 24.954% 与 25.049%——始终不是 prompt 所要求的精确 25.00%。整列中反复出现的「差一点」数值确认了循环检测失效。

要修复循环检测失效，请在 agent 框架中加入循环检测。跟踪工具调用与推理步骤，在三次完全相同的重复动作后强制终止。设置 CloudWatch 告警，在每会话平均 token 使用量显著上升时通知你。这样能及早发现循环问题，帮助避免成本失控。

#### 诊断工具选择错误

在追踪事件中审查 agent 的工具选择推理。下面的日志模式表明 agent 选错了工具：

```
"User wants to calculate 25% of 100"
"I should use the web_search tool to find the answer"
[web_search returns irrelevant results]
"Let me try web_search again with different terms"
```

要修复工具选择问题，请在 agent 的配置中提供更清晰的工具描述以及明确的使用示例：

```
{
  "tools": [
    {
      "name": "calculator",
      "description": "Use this tool for mathematical calculations, including
      percentages, arithmetic, and numerical operations.
      Example: calculating 25% of 100."
    },
    {
      "name": "web_search",
      "description": "Use this tool to find information on the internet.
      Do NOT use for mathematical calculations."
    }
  ]
}
```

### 场景 2：工具调用失败

工具调用失败会在你的 CloudWatch 控制面板中产生明确的错误以及升高的错误率。与无限循环不同，用户会收到清晰的失败消息。挑战在于迅速找出根本原因。

#### 工具调用失败的常见类型

五种错误类型涵盖了大多数工具调用失败，每种指向不同的修复方式。身份验证错误（401）在凭证过期、缺失或使用了错误的验证方法时发生。授权错误（403）在附加到 agent 的 IAM 角色缺少必需策略时出现。校验错误（400）发生在 agent 的输入与工具期望的 schema 不匹配时。资源未找到错误（404）表示工具名称不对、资源 ID 无效，或工具已被删除。工具执行错误（500）意味着工具自身因内部错误、超时或速率限制而失败。

#### 需要留意的症状

工具调用失败会产生明确的错误。你的 CloudWatch 控制面板显示错误率升高，agent 会话无法完成，用户反馈 agent 无法访问信息或执行操作。

#### 诊断身份验证与授权错误

先找出哪个工具最常失败。在 CloudWatch Logs Insights 中运行以下查询：

```
fields @timestamp, ToolName, StatusCode, ErrorMessage
| filter Operation like /InvokeTool/
| filter StatusCode like /4[0-9][0-9]|5[0-9][0-9]/
| stats count(*) by ToolName, StatusCode
| sort count desc
```

一个 CloudWatch Logs Insights 查询按类型拆解了工具调用错误：Exception（45 次）、PermissionError（6 次）与 RuntimeError（6 次）。Exception 错误占主导，说明校验失败是应当优先调查的主要根本原因。

对于身份验证与授权错误，请检查附加到 agent 网关的 Gateway 服务角色。在 Amazon Bedrock AgentCore 中，工具通过 Gateway 访问，而 Gateway 服务角色必须具有调用下游资源的权限：

```
fields @timestamp, AgentId, ExecutionRoleArn, ErrorMessage
| filter StatusCode = 401 or StatusCode = 403
| limit 100
```

把 Gateway 服务角色的策略与失败工具所需的权限做对比。例如，如果你的 agent 通过网关调用某个 AWS Lambda 函数工具并收到 403 错误，请更新 Gateway 服务角色以包含以下权限：

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowGatewayToInvokeLambdaTool",
      "Effect": "Allow",
      "Action": [
        "lambda:InvokeFunction"
      ],
      "Resource": [
        "arn:aws:lambda:us-east-1:123456789012:function:my-tool-function"
      ]
    }
  ]
}
```

对于凭证问题，请使用 AWS Secrets Manager 自动存储与轮换凭证。为工具错误率设置 CloudWatch 告警；任何工具的错误率超过 5% 时就应立即调查。

#### 诊断校验错误

对于校验错误，请检查 agent 所提供的工具输入：

```
fields @timestamp, ToolName, ToolInput, ErrorMessage
| filter StatusCode = 400
| limit 50
```

把 agent 的输入与工具期望的 schema 做对比。查找缺失的必填字段、错误的数据类型或格式不正确的值：

```
Tool expected: {"customer_id": "string", "amount": number}
Agent provided: {"customer_id": 12345, "amount": "100.00"}
```

要修复校验错误，请更新工具 schema 使其与工具的当前 API 一致。在部署到生产环境之前独立测试工具调用。创建集成测试，用各种输入（包括边界情况）调用每个工具。

#### 诊断资源与执行错误

对于资源未找到错误（404）与工具执行错误（500），请先检查工具自身的日志与指标。问题可能并不在你的 agent 里。按具体错误模式查询：

```
fields @timestamp, ToolName, ToolInput, ErrorMessage
| filter StatusCode = 404 or StatusCode = 500
| limit 50
```

当工具失败时，你的 agent 应记录带有完整上下文的错误，包括工具名称、输入载荷与错误消息。对于暂时性失败，它应使用指数退避重试；当工具不可用时，它应通过尝试替代方案来优雅降级；当工具无法访问时，它应清晰告知用户。

## 从调试走向主动监控

前面场景中的查询帮助你**在问题发生之后**进行诊断。若要在用户反馈之前捕捉问题，请把你的诊断查询转化为常驻的控制面板与告警，并使用 [AgentCore Evaluators](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluators.html) 进行持续的工具评估。

### [从 Logs Insights 创建 CloudWatch 告警](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/cloudwatch-metrics-insights-alarms.html)

指标筛选器可以持续监控 agent 的日志组，寻找指示失败的模式；再附加一个 CloudWatch 告警，你的团队就能自动收到通知。

这为你提供了一套针对无限循环的预警系统，而无需任何人手动运行 Logs Insights 查询。

### [构建 CloudWatch 控制面板](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/CWL_ExportQueryResults.html)

把关键诊断查询作为 CloudWatch 控制面板的 widget 添加进去，以保持持续可见性。这让你的运维团队无需手动重跑查询，就能在一个视图中掌握 agent 健康状况。可视化还能帮助发现更多异常值。

### [使用 AgentCore Evaluators 实现工具准确性的自动化](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html)

若要在规模上监控工具准确性，Amazon Bedrock AgentCore Evaluators 可以对 agent 行为进行持续、自动化的评估。Evaluators 不必在出问题时手动审查追踪，而是实时检查 agent 会话，并依据质量准则为其打分，从而在规模上评估 agent 表现。

## 清理资源

完成演练后，请删除或停用你创建的资源，以避免持续产生费用。

要停用 CloudWatch 查询与告警，请打开 Amazon CloudWatch 控制台，进入 Logs -> Log Insights 并删除你创建的已保存查询，然后进入 Alarms > All Alarms 并删除你为 token 使用量或错误率阈值创建的告警。如果你仅为本次演练开启了 CloudWatch Transaction Search，请在 CloudWatch 控制台的 Settings 中将其关闭。

**注意：**关闭 CloudWatch Transaction Search 会停止此后所有的追踪收集。在关闭之前，请确认你不再需要可观测性数据。你可以自行决定何时重新开启。

如果你为本次演练部署了测试用 agent，请进入 Amazon Bedrock 控制台，选择你的 agent，然后选择 Delete 以移除它及其关联资源。

## 结语
