# 使用 Amazon Bedrock AgentCore Evaluations 构建可靠的 AI agent

你的 AI agent 在演示中表现良好，打动了相关方，通过了测试场景，看起来已为生产做好准备。然后你把它部署上线，情况就变了。真实用户遭遇了错误的工具调用、前后不一致的响应，以及测试期间没人预料到的故障模式。

结果是预期中的 agent 行为与生产环境中实际用户体验之间出现了落差。agent 评估带来了传统软件测试并未设计去应对的挑战。由于大语言模型（LLM）是非确定性的，同一个用户查询在多次运行中可能产生不同的工具选择、推理路径和输出。这意味着你必须对每个场景反复测试，才能了解 agent 的真实行为模式。一次测试通过只能说明可能发生什么，而不能说明通常会发生什么。若没有跨这些差异的系统化度量，团队就会陷入人工测试与被动调试的循环：这会消耗大量 API 成本，却无法清楚判断改动是否提升了 agent 表现。这种不确定性让每次 prompt 修改都带有风险，并留下一个根本性问题没有答案：“这个 agent 现在真的更好了吗？”

本文将介绍 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) Evaluations，这是一项完全托管的服务，用于在整个开发生命周期中评估 AI agent 的表现。我们会说明该服务如何在多个质量维度上度量 agent 的准确性，解释面向开发与生产的两类评估方式，并分享如何构建可放心上线的 agent 的实用建议。

## 为什么 agent 评估需要新方法

当用户向 agent 发送请求时，会依次发生多个决策。agent 判断要调用哪些工具（如果有的话），执行这些调用，并基于结果生成响应。每个环节都引入潜在的失败点：选错工具、用错误的参数调用正确的工具，或把工具输出综合成不准确的最终答案。传统应用只需测试单个函数的输出，而 agent 评估需要度量整个交互流程上的质量。

这给 agent 开发者带来了具体挑战，可以通过以下做法来应对：

- 定义评估标准，明确什么算正确的工具选择、有效的工具参数、准确的响应，以及有帮助的用户体验。
- 构建能代表真实用户请求与预期行为的测试数据集。
- 选择能够在反复运行中一致评估质量的打分方法。

上述每项定义都直接决定你的评估系统度量什么，定义错了就意味着在优化错误的目标。缺少这项基础工作，团队所期望 agent 做到的事与能够证明 agent 做到的事之间的落差，就会变成真实的业务风险。弥合这一落差需要一个持续评估循环，如*图 1* 所示。团队构建测试用例、对 agent 运行这些用例、为结果打分、分析失败并实施改进。每一次失败都会成为新的测试用例，这个循环在 agent 的每次迭代中持续运转。

*图 1：agent 评估流程遵循一个持续循环：测试用例、agent 执行、打分、分析和改进。失败会变成新的测试用例。*

然而，把这个循环端到端跑起来，需要评估逻辑之外的大量基础设施。团队必须整理数据集、选择并托管打分模型、管理推理容量与 API 速率限制、构建把 agent 追踪数据转换为可评估格式的数据管道，还要创建可视化趋势的仪表板。对运行多个 agent 的组织而言，这些开销会随每个 agent 成倍放大。结果是，agent 开发者团队最终花在维护评估工具上的时间，比用在根据工具结论采取行动上的时间还多。这正是 Amazon Bedrock AgentCore Evaluations 要解决的问题。

## 认识 Amazon Bedrock AgentCore Evaluations

该服务最初在 [AWS re:Invent 2025](https://www.youtube.com/watch?v=Gcje6pRGr1g) 上以公开预览形式发布，现已正式可用。它负责评估模型、推理基础设施、数据管道与扩缩容，让团队可以专注于改进 agent 质量，而不必自行构建和维护评估系统。对于内置评估器，模型配额与推理容量完全托管。这意味着要评估许多 agent 的组织不会占用自身配额，也无需为评估工作负载单独配置基础设施。

AgentCore Evaluations 使用[带生成式 AI 语义约定的 OpenTelemetry（OTEL）追踪](https://opentelemetry.io/docs/specs/semconv/gen-ai/)端到端考察 agent 行为。OTEL 是一项开源可观测性标准，用于从应用收集分布式追踪数据。生成式 AI 语义约定在此基础上扩展出语言模型交互专用的字段，包括 prompt、completion、工具调用和模型参数。基于这一标准构建，使该服务对用任意 [Strands Agents](https://strandsagents.com/) 或 [LangGraph](https://www.langchain.com/langgraph) 构建、并以 [OpenTelemetry](https://opentelemetry.io/) 与 OpenInference 埋点的 agent 都能一致工作，从而捕获有意义评估所需的完整上下文。

评估可以用不同方式配置：

- [LLM-as-a-Judge](https://arxiv.org/abs/2306.05685)：由 LLM 依据带明确定义标准的结构化评分规则（rubric）评估每一次 agent 交互。
- 基于 Ground Truth 的评估，可用于把 agent 响应与预定义数据集或模拟数据集进行比较。
- 自定义代码评估器，可以引入一个 Lambda 作为评估器，运行你自己的自定义代码。

在 LLM-as-a-Judge 方式中，裁判模型会考察完整的交互上下文，包括对话历史、可用工具、实际使用的工具、传入的参数与系统指令，然后在给出分数之前提供详细的推理过程。每个分数都附带解释。团队可以用这些分数核实判断、准确理解某次交互为何得到特定评分，并识别本应有何不同。这种方式超越了简单的通过/失败判定，提供了结构化评估与透明的推理，使质量评估能达到人工审阅无法企及的规模。

有三条原则指导该服务的评估方式。**证据驱动的开发**用可量化的指标取代直觉，让团队能度量改动的真实影响，而不是争论某次 prompt 修改是否“感觉更好”。**多维度评估**独立评估 agent 行为的各个方面，从而能精确定位需要改进之处，而不依赖单一的汇总分数。**持续度量**把开发期建立的性能基线与生产监控直接对接，确保质量在真实条件演变时依然稳固。这些原则贯穿 agent 生命周期的始终，从第一轮开发测试一直到持续的生产监控。

### 面向生产监控的在线评估

在线评估通过持续采样可配置比例的追踪数据，并按你所选的评估器打分，来监控实时 agent 交互。你定义要应用哪些评估器、设置控制多大比例生产流量被评估的采样规则，并配置合适的过滤条件。该服务负责读取追踪数据、运行评估，并把结果呈现在由 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 提供支持的 **AgentCore Observability 仪表板**中。如果你已经在为可观测性收集追踪数据，在线评估无需改代码或重新部署，就能在现有运维指标之外附加带解释的质量分数。*图 4* 展示了这一过程如何运作。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/03/31/evals_gt_figure_4.png)

生产环境中的质量问题，其暴露方式往往被传统监控忽略。运维仪表板上延迟与错误率可能一片绿，而用户体验却在悄悄退化，因为 agent 开始选错工具或给出帮助不大的响应。通过把评估指标与运维指标一起跟踪，持续质量打分能捕捉到这类静默失败。由于 AgentCore Observability 运行在 CloudWatch 上，你可以创建自定义仪表板并设置告警，在分数跌破阈值的那一刻收到通知。

### 面向开发的按需评估

按需评估是为开发与 CI/CD 工作流设计的实时 API。团队用它在上线前测试改动、把评估套件作为 CI/CD 流水线的一部分运行、跨构建做回归测试，并以质量阈值作为部署门禁。开发者选择一个完整会话，并指定确切的 span（追踪中的单个操作）或追踪（通过提供其 ID）。该服务会考虑整个会话对话，并用与生产相同的评估器为单个 span/追踪打分。常见用例包括验证 prompt 改动、比较不同候选方案下的模型表现，以及防止质量回退。

由于两种模式使用相同的评估器，你在 CI/CD 中测试的内容就是你在生产中监控的内容，从而在整个开发生命周期中保持一致的质量标准。按需评估提供了架构决策与系统性改进所需的受控环境，而在线评估确保 agent 上线后质量监控持续进行。两种模式合起来，在开发与生产之间形成持续的反馈闭环，并且都使用同一套评估器与打分基础设施。

## AgentCore 如何评估你的 agent

AgentCore Evaluations 把 agent 交互组织成三级层次结构，由此决定可以评估什么、以何种粒度评估。**session** 表示用户与你的 agent 之间的一次完整对话，把来自单个用户或单个工作流的所有相关交互归为一组。在每个 session 内，**trace** 捕获单次往返中发生的一切。当用户发送一条消息并收到响应，这一趟往返就产生一条 trace，其中包含 agent 为生成答案所采取的每一个步骤。每条 trace 又包含称为 **span** 的单个操作，代表 agent 执行的具体动作，例如调用工具、从知识库检索信息或生成文本。

不同的评估器在这一层次结构的不同层级上工作，某一层级的问题在另一层级看来可能非常不同。该服务提供 13 个预配置的内置评估器，分布在这三个层级上，各自度量 agent 行为的某个不同方面*（图 6）*。你可以使用 LLM-as-a-Judge 定义自定义评估器，也可以使用能在 session、trace 与 span 层级工作的自定义代码评估器。

| 层级 | 评估器 | 用途 | Ground Truth 用法 |
| --- | --- | --- | --- |
| Session | Goal Success Rate | 评估一次对话中是否完成了用户的全部目标 | 用户提供关于目标完成的自由文本断言，系统将其与系统行为比较，并通过 Goal Success Rate 度量 |
| Trace | Helpfulness、Correctness、Coherence、Conciseness、Faithfulness、Harmfulness、Instruction Following、Response Relevance、Context Relevance、Refusal、Stereotyping | 评估响应质量、准确性、安全性与沟通有效性 | 轮级 ground truth（例如每轮的预期答案或属性）支撑对 Correctness 的评估 |
| Tool | Tool Selection Accuracy、Tool Parameter Accuracy | 评估工具选择决策与参数抽取的精确度 | 工具调用 ground truth 指定正确的工具序列，从而支持 Trajectory Exact Order Match、Trajectory In-Order Match 和 Trajectory Any Order Match |

*图 6：内置评估器在 session、trace 和 tool 层级工作。每个层级度量 agent 行为的不同方面。Ground Truth 可以以断言、预期响应和预期轨迹的形式提供，用于 session、trace 和 tool 层级的评估。*

独立评估每个层级，有助于团队诊断问题究竟源自工具选择、响应生成，还是会话级规划。一个 agent 可能选对了工具、参数也准确，却在最终响应里把工具输出综合得很差。只有单独考察每个层级，这种模式才会显现。agent 的首要用途决定了应优先考虑哪些评估器。客户服务 agent 应聚焦 *Helpfulness*、*Goal Success Rate* 和 *Instruction Following*，因为在既定护栏内解决用户问题会直接影响满意度；带检索增强生成（RAG）组件的 agent 最能从 *Correctness* 和 *Faithfulness* 中受益，以确保响应基于所提供的上下文；重度使用工具的 agent 则需要较高的 *Tool Selection Accuracy* 与 *Tool Parameter Accuracy* 分数。建议从三到四个与 agent 用途相符的评估器起步，随着理解加深再扩大覆盖范围。

### **理解评估器之间的差异**

有些评估器天生会相互影响，因此分数应当结合着看，而不是孤立地看。听起来相似的评估器，往往度量的是根本不同的东西，理解这些差异对诊断很重要。

- *Correctness* 检查响应在事实上是否准确，而 *Faithfulness* 检查它是否与对话历史一致。例如，agent 可以忠实于有缺陷的原始材料，却依然是错的。
- *Helpfulness* 追问响应是否推动用户朝其目标前进，而 *Response Relevance* 追问它是否回答了最初提出的问题。例如，agent 可以把一个错误的问题回答得很详尽。
- *Coherence* 检查推理中是否存在内部矛盾，而 *Context Relevance* 检查 agent 当时是否掌握了正确的信息。例如，前者暴露的是生成问题，后者暴露的是检索问题。

有些评估器还会相互依赖或相互权衡。例如：

- *Tool Parameter Accuracy* 只有在 agent 选对了工具时才有意义，因此应优先解决偏低的 *Tool Selection Accuracy*。
- *Correctness* 往往依赖 *Context Relevance*，因为 agent 若没有正确的信息就无法生成准确的答案。
- *Conciseness* 与 *Helpfulness* 常常相互冲突，因为简短的回答可能省略用户所需的上下文。

内置评估器自带预定义的 prompt 模板、选定的评估器模型和标准化的评分标准，其配置固定不变，以在多次评估之间保持一致。它们使用跨区域推理，自动从你所在地理范围内的 AWS 区域选择算力，在提高模型可用性与吞吐量的同时，把数据保存在发起请求的区域。自定义评估器在此基础上进一步支持你自己的评估器模型、评估指令、评估标准和评分 schema。它们对行业特定的评估尤其有价值，例如医疗健康或金融服务领域的合规检查、品牌语调一致性验证，或组织质量标准的强制执行。自定义代码评估器让你可以引入一个 AWS Lambda 函数来执行评估，从而也能为你的 agent 建立确定性的打分。

对于要求所有处理都在单一区域内完成的用例，自定义评估器还可以让你完全控制推理配置。构建自定义评估器时，你定义的指令中包含占位符，这些占位符在发送给裁判模型之前会被替换为真实的追踪信息。可用信息的范围取决于评估器的层级：session 级评估器可以访问完整的对话上下文与可用工具，trace 级评估器看到此前的轮次加上当前的助手响应，而 tool 级评估器则聚焦于其周边上下文中的特定工具调用。AWS 控制台提供了加载任意既有内置评估器的 prompt 模板作为起点的选项，让创建自定义变体变得简单直接*（图 7）*。

构建多个自定义评估器时，用 **MECE**（Mutually Exclusive, Collectively Exhaustive，相互独立、完全穷尽）原则来设计你的评估套件。每个评估器都应有清晰、互不重叠的考察范围，同时合起来覆盖你关心的全部质量维度。例如，与其创建两个都部分评估“响应质量”的评估器，不如把它们拆成一个评估事实依据、另一个评估表达清晰度。此外，在编写评估器指令时，要把裁判模型的角色设定为性能评估者，以避免评估与任务执行之间的混淆。使用清晰、按顺序排列的指令和精确的语言，并考虑加入一到三个相关示例，其输入/输出对能代表你期望的标准。至于打分，可在二值量表（0/1，适用于通过/失败场景）与序数量表（例如 1–5，适用于更细致的评估）之间选择，不确定时先用二值打分。该服务会把输出标准化为 reason 字段后跟 score 字段，因此裁判模型总是先给出推理再给出数字。避免加入你自己的输出格式指令，因为它们可能让裁判模型困惑。

### 基于自定义代码的评估器

内置评估器与自定义评估器都使用 LLM-as-a-Judge。AgentCore Evaluations 还支持第三种方式：基于代码的评估器，即用一个 AWS Lambda 函数配合你的自定义代码充当评估器。

当你有无需语言理解即可验证的启发式打分方法时，基于代码的评估器是理想选择。LLM 评估器可以判断一个响应“听起来是否对”，但它无法可靠地确认某个具体的工资单数字 $8,333.33 是否逐字出现在响应中，也无法确认生成的请求 ID 是否符合 PTO-2026-NNN 的格式。对于这类确定性检查，自定义代码更快、更便宜也更可靠。有四种情况特别适合用基于代码的评估器：

- **精确数据校验**：agent 需要从数据源返回特定值，例如账户余额、交易 ID 或价格。
- **格式合规**：响应必须符合结构性约束，例如长度限制、必需短语或输出 schema。
- **业务规则执行**：需要精确解释的策略，例如响应是否正确应用了阶梯折扣规则，或是否引用了正确的监管条款。
- **高频生产监控**：Lambda 调用的成本只是 LLM 推理的一小部分，当每个生产会话都需要在大规模下持续打分时，基于代码的评估器就是正确选择。

#### 创建基于代码的评估器

基于代码的评估器配置为一个承载你自定义逻辑的 AWS Lambda 函数。AgentCore 会把 agent 的 OTel span 作为结构化事件传给函数，并期望返回一个结果。你的函数从 span 中抽取所需信息，返回分数、标签和解释。

一旦 Lambda 部署完成并被授予由 AgentCore 服务主体调用的权限，你就可以把它注册为 AgentCore 的评估器。注册之后，该评估器 ID 即可用于按需评估。

## 设置 AgentCore Evaluations

配置该服务包含三个步骤：选择你的 agent、选择你的评估器、设置采样规则。开始之前，请先用 AgentCore Runtime 部署你的 agent，并通过 OpenTelemetry 或 OpenInference 埋点建立可观测性。GitHub 上的 [AgentCore 示例仓库](https://github.com/awslabs/amazon-bedrock-agentcore-samples/tree/main/01-tutorials/07-AgentCore-evaluations)提供了可运行的示例。

### 使用按需评估

在开发与测试阶段，你可以用按需评估分析特定交互：选择想要检查的 trace 或 span，应用所选评估器，获得带解释的详细分数。结果直接在 API 响应中返回，每次调用最多 10 项评估，每项结果包含 span 上下文、分数和推理。如果某次评估部分失败，响应会同时包含成功与失败的结果，并附带错误码与消息。按需评估很适合测试自定义评估器、排查特定的质量问题，以及在上线前验证修复。

### 用 ground truth 评估 agent

LLM-as-judge 打分告诉你响应在通用语言模型看来是否显得正确和有帮助。ground truth 评估则更进一步，让你指定答案、本应调用的工具以及会话本应达成的结果。这有助于度量 agent 的实际行为与你的参考输入有多接近。这在开发阶段尤其有价值——此时你掌握着关于正确行为的领域知识，并希望针对特定场景进行测试。

AgentCore Evaluations 支持三类 ground truth 参考输入，每类由一组特定的评估器使用：

| 参考输入 | 评估器 | 度量的内容 |
| --- | --- | --- |
| `expected_response` | `Builtin.Correctness` | agent 的响应与已知正确答案之间的相似度 |
| `expected_trajectory` | `Builtin.TrajectoryExactOrderMatch`、`Builtin.TrajectoryInOrderMatch`、`Builtin.TrajectoryAnyOrderMatch` | agent 是否按正确顺序调用了正确的工具 |
| `assertions` | `Builtin.GoalSuccessRate` | 该 session 是否满足了一组关于预期结果的自然语言陈述 |

这些输入是可选的，彼此独立。不需要 ground truth 的评估器（例如 `Builtin.Helpfulness` 和 `Builtin.ResponseRelevance`）可以与使用 ground truth 的评估器放在同一次调用中，每个评估器只读取它需要的字段。你可以同时提供全部三类参考输入以获得全面评估，也可以只提供与特定场景相关的那一部分。

`bedrock-agentcore` Python SDK 提供两个用于 ground truth 评估的接口：`EvaluationClient` 用于评估已有会话，`OnDemandEvaluationRunner` 用于自动化数据集评估。

### Evaluation Client：评估已有会话

当你已经在 CloudWatch 中记录了 agent 会话，并希望评估特定交互时，Evaluation Client 就是合适的选择。你需要提供 session ID、agent ID、所选评估器、用于检索 CloudWatch span 的回看窗口，以及可选的 Reference Inputs。该客户端会拉取该 session 的 span 并提交评估。它很适合开发期分析、调试特定的 agent 故障，以及在 prompt 或模型变更后验证已知的交互。

Evaluation Client 对多轮会话同样好用。当你传入一段多轮对话的 session ID 时，客户端会拉取该 session 的全部 span 并评估完整对话。轨迹评估器跨所有轮次验证工具使用情况，目标成功断言作用于整个 session，正确性评估器则针对每轮的预期答案逐个为响应打分。

### On-Demand Evaluation Dataset Runner：自动化数据集评估

当你希望在一个整理好的数据集上系统化评估 agent——对每个场景调用 agent、收集 CloudWatch span，并在单一自动化工作流中为结果打分——On-Demand Evaluation Dataset Runner 就是合适的选择。你定义一个 Dataset，其中包含带每轮和每场景 ground truth 的多轮场景，并提供一个 `agent_invoker` 函数供 runner 在每一轮调用。runner 负责管理 session ID，并协调调用、span 收集与评估之间的所有环节。

On-Demand Evaluation Dataset Runner 很适合 CI/CD 流水线（同一数据集对每次构建运行）、prompt 或模型变更后的回归测试，以及发布前对大规模测试用例语料做批量化评估。

这两个接口共用相同的评估器与 Reference Inputs schema，因此你可以先用 Evaluation Client 对既有生产会话交互式地开发和验证 ground truth 测试用例，再把同样的场景提升到 Evaluation Runner 的数据集中做系统化回归测试。[AgentCore 示例仓库](https://github.com/awslabs/agentcore-samples/tree/main/01-tutorials/07-AgentCore-evaluations)中的动手教程以一个示例 agent 端到端演示了这两个接口，覆盖单轮与多轮场景，并用到全部三类 ground truth 参考输入。

## 最佳实践

agent 的成功标准通常由三个维度构成：响应的质量、用户获得响应的延迟，以及推理的成本。AgentCore Evaluations 聚焦质量维度，而延迟、成本等运维指标可通过 CloudWatch 中的 AgentCore Observability 获取。以下最佳实践围绕前面介绍的三条评估原则组织，反映了在大规模实践中涌现出的模式。

**证据驱动的开发**

- 用合成数据和真实数据为 agent 的表现建立基线，并严格地做实验。在每次改动前后都进行度量，让改进建立在证据而非直觉之上。尽早用你手上已有的测试用例开始测试，并持续积累语料。*图 1* 中描述的评估循环确保失败会随时间转化为新的测试用例。
- 对每次改动都以统计严谨性运行 A/B 测试。无论你是在更新 system prompt、更换模型还是新增工具，都要在部署前后用同一套评估器比较表现。
- 按类别组织重复试验（每个问题至少 10 次），以基准化可靠性并识别可专门优化的机会。多次运行之间的方差揭示了 agent 在哪里表现稳定、在哪里仍需打磨。

**多维度评估**

- 尽早定义何谓成功，使用能反映 agent 真实用途的多维度标准。考虑哪些评估层级最重要（session、trace 或 tool），并选择与你的业务目标对应的评估器。
- 评估 agent 工作流中的每一步，而不仅是最终结果。分别度量工具选择、参数准确性与响应质量，能带来诊断精度，让你在问题实际发生的位置修复它。
- 让领域专家参与设计指标、定义任务覆盖范围，并开展人在回路的质量保证评审。领域专家的输入让评估器贴近真实预期，并能发现单靠自动打分可能遗漏的盲区。
- 先用内置评估器建立基线度量，随着需求成熟再创建自定义评估器。与领域专家一起校准自定义评估器的打分，使自动判断与你这行的真人预期一致。

**持续度量**

- 通过把生产行为与测试基线比较来发现漂移。在关键指标上设置 CloudWatch 告警，以便在回归影响到大量用户之前就捕捉到它。
- 记住你的测试数据集会随 agent、用户以及你遇到的对抗性场景而演变。当生产中浮现边缘情况、需求发生变化时，要定期更新它。

## 排查常见的评估问题模式

- 前面描述的评估器之间的关系能帮助你以诊断的方式解读分数。以下模式针对你在扩展应用时可能遇到的具体场景，并给出解决步骤。
- 如果你发现所有评估器的分数都偏低，问题通常是基础性的。先检查 Context Relevance 分数，判断 agent 是否能获取所需信息；检查 agent 的 system prompt 是否清晰完整，含糊或自相矛盾的指令会影响所有下游行为；核实工具描述是否准确说明了每个工具的适用时机与用法。
- 如果你发现相似交互的分数忽高忽低，这通常指向评估配置问题而非 agent 问题。如果你在用自定义评估器，检查指令是否足够具体，每个分数档位是否有清晰可区分的定义。可以考虑调低自定义评估器模型配置中的 temperature 参数，以获得更确定性的打分。
- 如果你看到 Tool Selection Accuracy 很高但 Goal Success Rate 很低，说明 agent 选对了工具却未能完成用户目标。这一模式意味着你可能需要更多工具来应对某些用户请求，或者你的 agent 在需要多次串行工具调用的任务上表现吃力。同时检查 Helpfulness 分数；agent 可能正确使用了工具，但结果解释得很差。
- 如果评估很慢或因为限流而失败，降低采样率以评估更小比例的会话，减少评估器数量。对自定义评估器，为你所选的模型申请配额提升，或换用默认配额更高的模型。

## 结论

本文展示了 Amazon Bedrock AgentCore Evaluations 如何帮助团队从被动调试走向对 AI agent 的系统化质量管理。作为一项完全托管的服务，它承担了团队原本需要为每个 agent 自行构建和维护的评估模型、推理基础设施与数据管道。按需评估锚定开发工作流，在线评估提供持续的生产洞察，质量因此在 agent 生命周期的每个阶段都成为可度量、可改进的属性。评估器之间的关系与诊断模式提供了一个框架，不仅用于给 agent 打分，也用于理解质量问题在何处、因何发生，以及应把改进精力投向哪里。
