# 面向医疗与生命科学 agentic 工作流的人机协同机制

在医疗与生命科学领域，AI agent 帮助组织处理临床数据、提交监管申报、自动化医疗编码，并加速药物研发与商业化。然而，医疗数据的敏感性，以及良好规范（Good Practice，GxP）合规等监管要求，都要求在关键决策点保留人工监督。这正是人机协同（human-in-the-loop，HITL）机制变得不可或缺的地方。本文中，你将学习使用 AWS 服务实现人机协同机制的四种实践方式。

## 为什么人机协同在医疗领域很重要

部署 AI agent 时，医疗与生命科学组织面临独特的挑战：

**监管合规——**GxP 法规要求对敏感操作进行人工监督。例如，删除患者记录或修改临床试验方案，在没有书面授权的情况下不能进行。

**患者安全——**影响患者诊疗的医疗决策在执行前必须经过临床验证。

**审计要求——**医疗系统需要完整追溯谁在何时批准了哪些操作。

**数据敏感性——**受保护健康信息（Protected Health Information，PHI）在访问或修改前需要明确授权。

HITL 机制在满足这些要求的同时，提供了必要的控制点，并保留了 agentic 自动化带来的效率提升。

## 方案概览

我们提出四种互补的方法，用于在 agentic 工作流中实现 HITL。每种工作流适合不同的场景与风险画像，正如我们在[在 GxP 环境中构建 AI agent 的指南](https://aws.amazon.com/blogs/machine-learning/a-guide-to-building-ai-agents-in-gxp-environments/)中所述。我们使用 [Strands Agents](https://strandsagents.com/) 框架、[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) Runtime 和 Model Context Protocol（MCP）构建这些模式，并附上你可为自己的用例调整的代码示例。

- **Agentic 循环中断（agent 框架 hook 系统）——** 我们使用 Strands Agent 框架的 Hooks 来强制执行人机协同策略。借助 hook，我们可以在工具调用执行之前拦截它们。
- **工具上下文中断——** 人机协同的审批逻辑也可以直接实现在工具逻辑内部，以获得细粒度、针对具体工具的控制与灵活性。会话上下文可用于自定义审批逻辑。
- **远程工具中断（AWS Step Functions）——** 在某些情况下，人们希望把审批请求异步发送给第三方系统或人员。我们通过使用 Amazon Simple Notification Service（Amazon SNS）向外部审批者发送通知来演示这一模式。审批在后台进行，agent 会话继续推进而不阻塞。
- **MCP Elicitation——** MCP 协议最近引入了 elicitation，服务端用它来在交互过程中通过客户端向用户请求补充信息。MCP 原生的 elicitation 协议借助服务器发送事件（SSE）实现实时、交互式的审批，支持有状态的双向通信。

## 架构

该方案架构使用 Strands Agents Framework 进行 agent 生命周期管理和中断处理，部署在 Amazon Bedrock AgentCore Runtime 上以获得无服务器可扩展性和会话隔离。AWS Step Functions 借助 Amazon SNS 编排异步审批工作流，而 MCP 服务器则通过 MCP 向 agent 暴露工具——这些 MCP 服务器同样部署在 AgentCore Runtime 上。

## 实现细节

这些架构模式的所有代码都公开在 [GitHub 仓库](https://github.com/aws-samples/sample-human-in-the-loop-patterns)中。

下面每种方法都演示一种自成一体的做法。agent 部署在 Amazon Bedrock AgentCore Runtime 上，并可访问不同敏感级别的医疗工具。低风险操作，例如查询患者姓名，无需审批即可执行；而高风险操作，例如获取生命体征或病情，则需要人工授权。患者出院这类操作则要求通过邮件通知获得外部主管的审批。

**方法 1：agentic 循环 hook 本地工具中断**

Strands Agent 框架提供了 **hook 系统**，可以在 agent 循环层面于工具执行**之前**拦截工具调用。这样无需修改工具本身，就能对敏感工具统一强制执行一条 HITL 策略。

`HookProvider` 在 `BeforeToolCallEvent` 上注册回调。当调用敏感工具时，hook 触发 `interrupt`，暂停 agent 循环，直到人工响应。用户可以回复“y”（本次批准）、“n”（拒绝）或“t”（信任——在本次会话余下时间内批准该工具）：

```
class ApprovalHook(HookProvider):
    SENSITIVE_TOOLS = ["get_patient_condition", "get_patient_vitals"]

    def register_hooks(self, registry: HookRegistry, **kwargs: Any) -> None:
        registry.add_callback(BeforeToolCallEvent, self.approve)

    def approve(self, event: BeforeToolCallEvent) -> None:
        tool_name = event.tool_use["name"]
        if tool_name not in self.SENSITIVE_TOOLS:
            return

        # Skip if user previously chose "trust always" for this tool
        approval_key = f"{tool_name}-approval"
        if event.agent.state.get(approval_key) == "t":
            return

        approval = event.interrupt(
            approval_key,
            reason={"reason": f"Authorize {tool_name} with args: {event.tool_use.get('input', {})}"},
        )
        if approval.lower() not in ["y", "yes", "t"]:
            event.cancel_tool = f"User denied permission to run {tool_name}"
            return

        if approval.lower() == "t":
            event.agent.state.set(approval_key, "t")  # trust tool for the rest of the session
```

hook 在构造时挂到 agent 上——工具完全不知道审批逻辑的存在：

```
agent = Agent(
    hooks=[ApprovalHook()],
    tools=[get_patient_name, get_patient_condition, get_patient_vitals],
)
```

**方法 2：工具上下文中断**

审批逻辑不放在集中式的 hook 中，而是使用 `tool_context.interrupt()` 直接嵌入每个工具内部。这带来细粒度的、按工具的控制：每个工具可以根据会话上下文实现自己的访问规则。在这个示例中，agent 会话携带一个 `user_role`。一个共享的 `check_access` 函数强制执行基于角色的访问：在我们的代码示例中，非医师会被直接拒绝，而医师会被提示审批：与方法 1 一样，trust 选项会为整个会话缓存审批结果：

```
def check_access(tool_context, patient_id: str, action: str):
    user_role = tool_context.agent.state.get("user_role") or "Non-Physician"

    if user_role != "Physician":
        return f"Access denied: {action} requires Physician role (current: {user_role})"

    approval_key = f"{action}-{patient_id}-approval"
    if tool_context.agent.state.get(approval_key) == "t":
        return None  # previously trusted

    approval = tool_context.interrupt(
        approval_key,
        reason={"reason": f"[{user_role}] Authorize {action} for patient {patient_id}"},
    )
    if approval.lower() not in ["y", "yes", "t"]:
        return f"Physician denied access to {action} for patient {patient_id}"

    if approval.lower() == "t":
        tool_context.agent.state.set(approval_key, "t")
    return None  # approved
```

**方法 3：使用 AWS Step Functions 的异步工具审批**

在许多企业场景中，审批流程需要由第三方审批者授权，而该审批者并非调用 agent 的人。这就需要一套能够独立于 agent 会话运行的异步审批工作流。一种有效的方式是使用 **AWS Step Functions** 来编排这些外部审批流程。

在这个模式中，agent 工具会触发一个 Step Functions 工作流，该工作流通过 Amazon SNS 以邮件通知的形式向外部审批者发送审批请求。工具轮询审批结果，并相应地更新 agent 会话状态。用户之后还可以用另一个 `check_discharge_status` 工具查看审批状态。`discharge_patient` 工具启动 Step Functions 执行并轮询结果：

```
@tool(context=True)
def discharge_patient(tool_context, patient_id: str, reason: str) -> str:
    # Skip workflow if already approved in this session
    if tool_context.agent.state.get("external-approver-state") == "approved":
        return f"Patient {patient_id} discharged (pre-approved). Reason: {reason}"

    response = sfn_client.start_execution(
        stateMachineArn=state_machine_arn,
        input=json.dumps({"patient_id": patient_id, "action": "discharge", "reason": reason}),
    )
    return f"Waiting for approval. Execution ARN: {response['executionArn']}"
```

这种异步方式支持非阻塞运行：用户不必被迫等待可能耗时数小时甚至数天的审批，agent 执行可以独立继续。Step Functions 通过完整的执行历史维护详尽的审计追踪，并提供跨会话超时的持久状态管理，以及与邮件、Slack 或 Microsoft Teams 等现有企业沟通渠道的集成。启动敏感工作流的用户会触发一个 State Function：agent 向用户返回工作流已启动的确认。任何时候，用户都可以查看状态更新，以确认工作流已完成。

**方法 4：MCP elicitation**

MCP 协议最近引入了 elicitation 协议，允许 MCP 服务器在工具执行期间向用户请求补充信息或审批。这种做法遵循协议标准，并提供一种在运行时提示用户的动态机制，无需提前把参数硬编码。它可以用来授权一次工具调用，并附带一些业务理由。

当调用敏感工具时，MCP 服务器暂停执行，并通过 MCP 客户端把审批提示回传给终端用户。用户看到提示、做出决定，服务器随后恢复——要么继续执行操作，要么拒绝访问。这种双向通信由 MCP 的可流式 HTTP 传输（streamable HTTP transport）支持，它在客户端与服务器之间维持有状态连接。

在 MCP 服务器端，审批逻辑就是每个敏感工具内部的一次 `ctx.elicit()` 调用：

```
@server.tool
async def get_patient_condition(patient_id: str, ctx: Context) -> str:
    """Get patient condition. Sensitive — requires approval via MCP elicitation."""
    result = await ctx.elicit(
        f"⚠️ Approve access to SENSITIVE condition data for patient {patient_id}?"
    )
    if result.action != "accept":
        return f"Access to condition data for patient {patient_id} DENIED."
    return f"Patient {patient_id} condition: Hypertension Stage 2, Type 2 Diabetes"
```

在 agent 一侧，向 MCP 客户端注册一个 `elicitation_callback`。当服务器调用 `ctx.elicit(),` 时，该回调触发，把审批提示转达给用户，并把用户决定回传给服务器。对于本地 agent，这是一个终端提示。对于部署在 AgentCore Runtime 上的 agent，我们使用 WebSocket 连接把 elicitation 实时转达给远端终端用户：

这种方法把审批逻辑完全保留在 MCP 服务器的工具定义之内。agent 本身并不知道哪些工具需要审批，因此你可以独立地添加或修改审批要求。

## 结论

你可以使用这些人机协同（HITL）机制，在医疗与生命科学领域构建安全、合规的 AI agent 部署。通过为你的用例实施合适的 HITL 模式，你可以部署从试点项目扩展到全企业范围的生产级工作流。先从识别工作流中哪些操作需要人工监督开始，然后选择与你的审批需求相匹配的 HITL 模式——集中式（方法 1）、工具专属（方法 2）、异步（方法 3）或实时（方法 4）。

关于 Amazon Bedrock AgentCore 的更多信息，请访问 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/)。
