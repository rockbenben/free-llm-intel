# 用 Amazon Nova 创建旅行规划 agentic 工作流

旅行本身令人愉快，但规划行程往往繁杂又费心。旅行者必须预订住宿、安排活动、解决当地交通，所有这些决定都可能让人应接不暇。尽管旅行专业人士长期以来一直在帮助应对这些复杂事务，但[生成式 AI](https://aws.amazon.com/what-is/generative-ai/) 最近的突破带来了全新的可能——智能助手能够理解自然语言对话、访问实时数据，并直接与预订系统和旅行工具对接。[Agentic workflows](https://aws.amazon.com/what-is/ai-agents/) 使用大型语言模型（LLM）并让其能够访问外部工具，在简化旅行规划这类动态、多步骤流程方面尤其有前景。

本文探讨如何用 AI agent 构建一个旅行规划解决方案。该 agent 使用 [Amazon Nova](https://aws.amazon.com/ai/generative-ai/nova/)，与其他商用 LLM 相比，它在性能和成本之间取得了最佳平衡。通过将准确且经济高效的 Amazon Nova 模型与 [LangGraph](https://www.langchain.com/langgraph) 的编排能力相结合，我们打造了一个实用的旅行助手，既能处理复杂的规划任务，又能让生产部署的运营成本保持在可控范围内。

## 解决方案概览

我们的解决方案建立在无服务器 [AWS Lambda](https://aws.amazon.com/lambda) 架构之上，使用 [Docker](https://www.docker.com/) 容器，并采用完整的三层设计：前端交互、核心处理和集成服务。在核心处理层，我们使用 LangGraph 这一有状态编排框架，构建出一个既精密又灵活的基于 agent 的系统，负责管理旅行规划所需的复杂交互。

系统的核心是一种图架构：各个组件（节点）分别处理旅行规划的不同方面，由 router 节点编排它们之间的信息流。我们使用 Amazon Nova，这是新一代先进的基础模型（FM），仅在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上提供，具备前沿的智能水平与行业领先的价格性能比。router 节点使用 LLM 分析每条用户查询，并结合我们 14 个 action 节点的描述，决定需要执行哪些节点。每个 action 节点都有自己的 LLM chain，由 Amazon Nova Pro 或 Amazon Nova Lite 模型驱动，负责各种功能，包括网络调研、个性化推荐、天气查询、产品搜索和购物车管理。

我们在 router 和较简单的 action 节点上使用 Amazon Nova Lite。它处理速度极快，能以低成本完成查询分析和基础内容生成，同时保持较高的准确性。五个较复杂的节点使用 Amazon Nova Pro，处理需要高级指令遵循和多步骤操作的任务，例如详细的旅行规划和推荐。两个模型都支持 30 万 token 的上下文窗口，可以处理文本、图像和视频输入。模型支持 200 多种语言的文本处理，帮助我们的旅行助手服务全球用户。集成层通过一个接口整合了多个数据源和服务：

- [Amazon Product Advertising API](https://webservices.amazon.com/paapi5/documentation/) 用于旅行相关产品推荐
- Google Custom Search API 用于获取实时旅行信息
- OpenWeather API 用于获取准确的天气预报
- [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 用于提供旅行目的地洞察
- [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 用于持久化存储用户画像和聊天记录

这些集成只是示例，该架构被设计为可扩展的，因此组织可以根据具体需求快速接入自己的 API 和数据源。

该 agent 使用 AgentState（[TypedDict](https://mypy.readthedocs.io/en/stable/typed_dict.html)）来跟踪对话状态。AgentState 是一种特殊的 Python 字典，通过强制特定数据类型来帮助防止数据错误。它存储我们需要了解的每个用户会话信息：对话历史、画像信息、处理状态和最终输出。这确保不同的 action 节点能够可靠地访问和更新信息。

旅行助手端到端地处理用户交互：

- 用户通过聊天界面与 React.js Web 应用交互。
- 其请求通过 [Amazon Cognito](https://aws.amazon.com/cognito/) 进行身份验证，并经 [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 路由转发。
- 通过身份验证的请求被发送到后端 [Lambda functions](https://aws.amazon.com/lambda/)，后者承载核心的 agent 工作流。
- API 凭据使用 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 安全存储，遵循最佳实践，确保这些敏感密钥不会出现在代码或配置文件中，并实施适当的访问控制和轮换策略。
- Travel Assistant Agent 本身由多个相互连接的组件构成。位于中心位置的 agent router 负责分析传入的查询并编排工作流。
- agent 通过三张 DynamoDB 表维护状态，分别存储对话历史、购物清单和用户画像，确保上下文在多次交互之间得以保留。
- 对于旅行相关知识，系统结合了 Amazon Bedrock Knowledge Bases、[Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/) 以及 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）中的文档存储。这些组件协同工作，在需要时提供准确、相关的旅行信息。
- agent 的 action 节点通过将 LLM chain 与外部 API 结合来处理专门任务。当用户需要产品推荐时，系统连接到 Amazon Product Advertising API；对于一般旅行信息，使用 Google Custom Search API；对于天气相关查询，则查询 OpenWeather API。API 凭据通过 Secrets Manager 进行安全管理。
- 系统根据收集到的信息生成完整的回答，最终通过聊天界面返回给用户。

该架构既支持可由单个节点处理的简单查询，也支持需要多个组件协同的复杂多步骤交互。系统可以横向扩展，通过引入更多 action 节点和 API 集成即可添加新能力。

你可以使用 [AWS Cloud Development Kit](https://aws.amazon.com/cdk/)（AWS CDK）部署该解决方案，它会生成一个 [AWS CloudFormation](https://aws.amazon.com/cloudformation) 模板，自动处理所需资源，包括 Lambda 函数、DynamoDB 表和 API 配置。部署过程会创建必要的 AWS 资源，并为你的前端应用输出 API endpoint URL。

## 前提条件

完成本演练需要满足以下前提条件：

- 一个有效的 [AWS 账户](https://signin.aws.amazon.com/signup?request_type=builderId)，并熟悉 FM、Amazon Bedrock 和 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/)
- 拥有 Amazon Bedrock 上 Amazon Nova FM 的[访问权限](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access-modify.html)
- [Node.js](https://nodejs.org/en) v16.x 或更高版本
- Python 3.9 或更高版本
- 拥有 Product Advertising API（PAAPI）的访问权限

## 克隆代码仓库

首先克隆包含解决方案文件的 GitHub 仓库：

```
git clone https://github.com/aws-samples/sample-travel-assistant-agent.git
```

## 获取 API 密钥

该解决方案需要三个服务的 API 密钥来启用其核心功能：

- **OpenWeather API**——在 [OpenWeather](https://openweathermap.org/) 上创建 Free Access 账户以获取 API 密钥。免费套餐（每分钟 60 次调用）足以用于测试和开发。
- **Google Custom Search API**——通过 [Google Cloud Console](https://console.cloud.google.com/) 设置搜索功能。创建或选择一个项目，并启用 Custom Search API。然后，在凭据部分生成 API 密钥。在 [Programmable Search](https://programmablesearch.google.com/controlpanel/all) 上创建一个搜索引擎，并记下你的 Search Engine ID。免费套餐每天包含 100 次查询。
- **（可选）Amazon Product Advertising API（PAAPI）**——如果你想启用产品推荐，请访问 [PAAPI 文档门户](https://webservices.amazon.com/paapi5/documentation/)生成 API 密钥。你将获得一个公钥和一个私钥。必须拥有 Amazon Associates 账户才能访问这些凭据。如果你刚接触 Amazon Associates Program，请先完成申请流程。如果不想使用 PAAPI 功能，可以跳过这一步。

## 将 API 密钥添加到 Secrets Manager

在部署解决方案之前，必须将 API 密钥安全地存储在 Secrets Manager 中。下表列出了需要创建的密钥及其 JSON 结构。有关创建密钥的说明，请参阅[创建 AWS Secrets Manager 密钥](https://docs.aws.amazon.com/secretsmanager/latest/userguide/create_secret.html)。

| **密钥名称** | **JSON 结构** |
| --- | --- |
| `openweather_maps_keys` | `{" openweather_key": "YOUR_API_KEY"}` |
| `google_search_keys` | `{"cse_id": "YOUR_SEARCH_ENGINE_ID", "google_api_key": "YOUR_API_KEY"}` |
| `paapi_keys` | `{"paapi_public": "YOUR_PUBLIC_KEY", "paapi_secret": "YOUR_SECRET_KEY"}` |

## 配置环境变量

在项目根目录创建一个包含你的配置的 .env 文件：

```
STACK_NAME=TravelAssistantAgent

# Optional: Create Bedrock Knowledge Base with documents
KB_DOCS_PATH = Path/to/your/documents/folder
# Optional: Enable/disable Product Search features with PAAPI
USE_PAAPI=false
```

## 部署堆栈

如果这是你在 AWS 账户和 AWS 区域中首次使用 AWS CDK，请先引导（bootstrap）你的环境：

```
cdk bootstrap
```

使用提供的脚本部署解决方案，该脚本会创建所需的 AWS 资源，包括 Lambda 函数、DynamoDB 表和 API 配置：

```
sh deploy.sh
```

## 访问你的应用

部署完成后，打开 AWS CloudFormation 控制台并打开你的堆栈。在 **Outputs** 选项卡上，记下以下值：

- **WebAppDomain**——你的应用 URL
- **UserPoolId**——用户管理所需
- **UserPoolClientId**——用于身份验证

## 创建 Amazon Cognito 用户

完成以下步骤以创建 Amazon Cognito 用户：

- 在 Amazon Cognito 控制台上，在导航窗格中选择 **User pools**。
- 选择你的用户池。
- 在导航窗格中选择 **Users**，然后选择 **Create user**。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/31/ML-18031-IMAGE-2-1024x567.png)

- 对于 **Email address**，输入一个电子邮件地址，并选中 **Mark email address as verified**。
- 对于 **Password**，输入一个临时密码。
- 选择 **Create user**。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/31/ML-18031-IMAGE-3-1024x728.png)

你可以使用这些凭据，通过 WebAppDomain URL 访问你的应用。

## 结论

我们的旅行规划助手 agent 展示了一个由 Amazon Nova 和 LangGraph 构建的实用应用，可用于解决真实的业务挑战。该系统简化了复杂的旅行规划，同时通过专用处理节点和实时数据集成自然地融入了产品推荐。Amazon Nova Lite 模型在任务编排方面表现尚可，Amazon Nova Pro 在更复杂的函数调用操作上表现出色。展望未来，这一框架可以结合 ReAct 等更动态的编排系统来实现。要构建你自己的实现，请查看 [GitHub repository](https://github.com/aws-samples/sample-travel-assistant-agent/tree/main) 中的代码示例。

对于希望深入了解 LLM 驱动 agent 的读者，AWS 提供了大量关于构建智能系统的资源。[Amazon Bedrock Agents 文档](https://aws.amazon.com/bedrock/agents/?utm_source=chatgpt.com)介绍了如何用 FM 实现多步骤任务自动化，[AWS Bedrock Agent Samples GitHub repo](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/agents-and-function-calling) 则提供了使用 Amazon Bedrock 实现多种 agent 应用的指导。
