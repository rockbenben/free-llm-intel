# 借助 Amazon Bedrock Guardrails 新增的防护层级定制负责任的 AI

[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 提供可配置的防护措施，帮助你大规模构建可信的生成式 AI 应用。它为企业提供集成的安全与隐私防护，可跨多个[基础模型（FM）](https://aws.amazon.com/what-is/foundation-models/)工作，既包括 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 中可用的模型，也包括由其他模型厂商与云厂商托管在 Amazon Bedrock 之外的模型。借助独立的 [ApplyGuardrail](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-use-independent-api.html) API，Amazon Bedrock Guardrails 提供了一种与模型无关、可扩展的方式，为你的生成式 AI 应用实施负责任的 AI 策略。Guardrails 目前提供[六项关键防护](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-components.html)：内容过滤器、拒绝主题、词过滤器、敏感信息过滤器、上下文落地检查（contextual grounding check）与自动推理检查（Automated Reasoning checks，预览），用于帮助阻止不受欢迎的内容，并让 AI 交互与组织的负责任 AI 策略保持一致。

当组织力求在多样化用例中落实负责任的 AI 实践时，会面临一项挑战：在安全控制与各应用不同的性能、语言要求之间取得平衡，使得一刀切的做法收效甚微。为此，我们推出了 [Amazon Bedrock Guardrails 的防护层级（safeguard tier）](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-tiers.html)，让你可以依据具体需求选择合适的防护。例如，一家金融服务公司可以为面向客户的 AI 助手实施全面的多语言防护，而为内部分析工具使用更聚焦、更低延迟的防护，确保每个应用都以恰当的保护级别遵循负责任 AI 原则，同时不牺牲性能或功能。

在本文中，我们介绍 Amazon Bedrock Guardrails 中新增的防护层级，说明它们的优势与用例，并就如何在你的 AI 应用中实施与评估它们给出指引。

## 方案概述

在此之前，使用 Amazon Bedrock Guardrails 时，你能得到的只有一套与特定 AWS Region 关联的防护，且支持语言有限。引入 [Amazon Bedrock Guardrails 的防护层级](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-tiers.html) 为实施 AI 安全控制带来三项关键优势：

- 以层级为基础的方法，让你掌控内容过滤器与拒绝主题要使用哪种 guardrail 实现，从而为每个用例选择合适的保护级别。我们会在后续章节展开细节。
- 为 Amazon Bedrock Guardrails 提供的[跨区域推理支持（CRIS）](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-cross-region.html)，让你可以使用多个 Region 的计算容量，为 guardrail 获得更好的扩展性与可用性。这样一来，在评估 guardrail 策略时，你的请求会被自动路由到你所在地理范围内的最优 Region，最大化可用算力与模型可用性。这有助于在需求上升时维持 guardrail 的性能与可靠性。将 CRIS 与 Amazon Bedrock Guardrails 一起使用不产生额外费用，你还可以从特定的 [guardrail 配置文件](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-cross-region-support.html)中选择，以控制模型版本与后续升级。
- 将高级能力作为可配置的层级选项，适用于更稳健的保护或更广泛的语言支持属于首要考量、且能够接受适度延迟增加的用例。

防护层级在 guardrail 策略级别生效，具体针对内容过滤器与拒绝主题。你可以为 AI 应用的不同方面量身定制保护策略。下面我们来了解两个可用层级：

- Classic 层级（默认）： 维持 Amazon Bedrock Guardrails 的既有行为 语言支持有限：英语、法语与西班牙语 无需为 Amazon Bedrock Guardrails 使用 CRIS 面向低延迟应用优化
- Standard 层级： 作为一项新能力提供，你可以为现有或新建的 guardrail 启用 支持[超过 60 种语言的多语言](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-supported-languages.html) 对 prompt 拼写错误与被操纵输入的鲁棒性更强 增强的 prompt 攻击防护，覆盖现代 jailbreak 与 prompt 注入技术，包括 token 走私、AutoDAN 与 many-shot 等 增强的主题检测，对复杂主题的理解与处理更佳 要求为 Amazon Bedrock Guardrails 使用 CRIS，与 Classic 层级选项相比延迟特征可能略有上升

你可以为内容过滤器与拒绝主题策略分别独立选择层级，从而在同一个 guardrail 内形成混合配置，如下面的层级结构所示。有了这种灵活性，公司可以为每个具体应用实施恰当级别的保护。

- **Policy：**内容过滤器  **Tier：**Classic 或 Standard
- **Policy：**拒绝主题  **Tier：**Classic 或 Standard
- **其他策略：**词过滤器、敏感信息过滤器、上下文落地检查与自动推理检查（预览）

为说明这些层级如何应用，设想一家在全球运营的金融服务公司，在面向客户的应用与内部应用中同时部署 AI：

- 对于他们的客户服务 AI 助手，可以为内容过滤器与拒绝主题都选择 Standard 层级，以在多种语言上提供全面防护。
- 对于内部分析工具，他们可以为内容过滤器使用 Classic 层级以优先保证低延迟，同时为拒绝主题实施 Standard 层级，以针对敏感财务信息披露提供稳健防护。

你可以通过 [AWS 管理控制台](https://aws.amazon.com/console)，或以编程方式通过 Amazon Bedrock SDK 与 API，在每个 guardrail 中为内容过滤器与拒绝主题配置防护层级。你可以使用新建或现有的 guardrail。关于如何创建或修改 guardrail，请参阅[创建你的 guardrail](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-components.html)。

你现有的 guardrail 会自动默认设为 Classic 层级，以确保其行为不受影响。

## Standard 层级带来的质量提升

根据我们的测试，与 Classic 层级相比，新的 Standard 层级将有害内容过滤的召回率提升超过 15%，平衡准确率提升超过 7%。新 Standard 层级的一个关键差异化特性是多语言支持：在最常见的 14 种语言上，它保持强劲表现，召回率超过 78%，平衡准确率超过 88%。防护能力的增强还延伸到其他多个方面。例如，Standard 层级中针对 prompt 攻击的内容过滤器，与 Classic 层级相比召回率提升 30%、平衡准确率提升 16%，同时保持更低的误报率。在拒绝主题检测上，新的 Standard 层级召回率提升 32%，平衡准确率因此改善 18%。这些针对 Amazon Bedrock Guardrails 检测能力的大幅演进，加上始终较低的误报率与稳健的多语言表现，也意味着内容保护技术相较其他常见方案取得了显著进步。多语言方面的改进尤其值得注意：与其他竞品方案相比，Amazon Bedrock Guardrails 的新 Standard 层级在不同语言的评测中召回率稳定提升 33–49%。

## 防护层级的优势

不同 AI 应用根据其受众、内容领域与地理覆盖范围，有着各自不同的安全要求。例如：

- 面向客户的应用，通常比内部应用需要更强的防护来抵御潜在滥用
- 服务全球客户的应用，需要防护措施能在多种语言上有效工作
- 内部企业工具可能更看重用少数几种主要语言控制特定主题

防护层级与 Amazon Bedrock Guardrails 的 CRIS 相结合，还能满足多种运营需求，带来超越功能差异的实际好处：

- **策略独立演进** – 每个策略（内容过滤器或拒绝主题）都能按自己的节奏演进，而不打乱整个 guardrail 体系。你可以在 CRIS 中通过特定的 guardrail 配置文件来配置这些策略，以控制驱动 guardrail 策略的模型的版本。
- **受控采用** – 由你决定何时、以何种方式采用新能力，为生产应用保持稳定。你可以不改动地继续按之前的配置使用 Amazon Bedrock Guardrails，只在你认为合适时才迁移到新层级与 CRIS 配置。
- **资源效率** – 你可以只在需要的地方实施增强防护，在安全需求与性能考量之间取得平衡。
- **简化的迁移路径** – 新能力推出时，你可以按策略领域逐步评估与集成，而不必面对全有或全无的选择。这也简化了 A/B 测试或蓝绿部署等针对 guardrail 的测试与比较机制。

这一方法帮助组织以比单选项体系更细腻的方式，在具体保护需求与运营考量之间取得平衡。

## 使用 AWS SDK 配置防护层级

你也可以使用 AWS SDK 配置 guardrail 的层级。下面是一个用 Python SDK 入门的示例：

```
import boto3
import json

bedrock = boto3.client(
    "bedrock",
    region_name="us-east-1"
)

# Create a guardrail with Standard tier for both Content Filters and Denied Topics
response = bedrock.create_guardrail(
    name="enhanced-safety-guardrail",
    # cross-Region is required for STANDARD tier
    crossRegionConfig={
        'guardrailProfileIdentifier': 'us.guardrail.v1:0'
    },
    # Configure Denied Topics with Standard tier
    topicPolicyConfig={
        "topicsConfig": [
            {
                "name": "Financial Advice",
                "definition": "Providing specific investment advice or financial recommendations",
                "type": "DENY",
                "inputEnabled": True,
                "inputAction": "BLOCK",
                "outputEnabled": True,
                "outputAction": "BLOCK"
            }
        ],
        "tierConfig": {
            "tierName": "STANDARD"
        }
    },
    # Configure Content Filters with Standard tier
    contentPolicyConfig={
        "filtersConfig": [
            {
                "inputStrength": "HIGH",
                "outputStrength": "HIGH",
                "type": "SEXUAL"
            },
            {
                "inputStrength": "HIGH",
                "outputStrength": "HIGH",
                "type": "VIOLENCE"
            }
        ],
        "tierConfig": {
            "tierName": "STANDARD"
        }
    },
    blockedInputMessaging="I cannot respond to that request.",
    blockedOutputsMessaging="I cannot provide that information."
)
```

在同一个 guardrail 内，内容过滤器与拒绝主题策略可以各自独立地配置层级，让你对 guardrail 的行为拥有细粒度控制。例如，你可以根据具体需求为内容过滤选择 Standard 层级，同时把拒绝主题保持在 Classic 层级。

要将现有 guardrail 的配置迁移到 Standard 层级，请把上例中高亮标出的 `crossRegionConfig` 与 `tierConfig` 部分加入到你当前的 guardrail 定义中。你可以使用 [UpdateGuardrail](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_UpdateGuardrail.html) API 完成，或用 [CreateGuardrail](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_CreateGuardrail.html) API 新建一个 guardrail。

## 评估你的 guardrail

为全面评估 guardrail 的表现，建议创建一个包含以下内容的测试数据集：

- **安全示例** – 应当通过 guardrail 的内容
- **有害示例** – 应当被拦截的内容
- **边界用例** – 用于测试策略边界的内容
- **多语言示例** – 使用 Standard 层级时尤为重要

你也可以为此依赖公开可用的数据集。理想情况下，你的数据集应为每个样本标注预期结果，以便评估 guardrail 的准确率与召回率。

数据集准备好后，你可以像下面的示例那样使用 Amazon Bedrock [ApplyGuardrail](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-use-independent-api.html) API，在不调用 FM 的情况下高效测试 guardrail 对用户输入的行为。这样可以省去与大语言模型（LLM）响应生成相关的成本。

```
import boto3
import json

bedrock_runtime = boto3.client(
    "bedrock-runtime",
    region_name="us-east-1"
)

# Test the guardrail with potentially problematic content
content = [
    {
        "text": {
            "text": "Your test prompt here"
        }
    }
]

response = bedrock_runtime.apply_guardrail(
    content=content,
    source="INPUT",
    guardrailIdentifier="your-guardrail-id",
    guardrailVersion="DRAFT"
)

print(json.dumps(response, indent=2, default=str))
```

之后如有需要，你可以对 LLM 的输出重复这一过程。为此，如果你想对 AWS 内或其他云厂商的模型做独立评估，可以使用 ApplyGuardrail API；如果你打算使用 Amazon Bedrock 中的模型，也可以直接使用 [Converse](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html) API。使用 Converse API 时，输入与输出在同一次调用请求中完成评估，从而优化延迟并减少编码开销。

由于数据集带有标注，你可以直接借助 SKLearn Metrics 之类的库，实现一套评估准确率、召回率以及潜在假阴性或假阳性的机制：

```
# scoring script
# labels and preds store list of ground truth label and guardrails predictions

from sklearn.metrics import confusion_matrix

tn, fp, fn, tp = confusion_matrix(labels, preds, labels=[0, 1]).ravel()

recall = tp / (tp + fn) if (tp + fn) != 0 else 0
fpr = fp / (fp + tn) if (fp + tn) != 0 else 0
balanced_accuracy = 0.5 * (recall + 1 - fpr)
```

另外，如果你没有标注数据，或者用例的响应带有主观性，你也可以依赖 LLM-as-a-judge 之类的机制：把输入与 guardrail 的评估输出交给 LLM，让它依据你自己预定义的标准打分。更多信息请参阅[使用测试驱动开发自动化构建 Amazon Bedrock guardrail](https://aws.amazon.com/blogs/machine-learning/automate-building-guardrails-for-amazon-bedrock-using-test-driven-development/)。

## 实施层级的最佳实践

在为 Amazon Bedrock Guardrails 配置层级时，我们建议考虑以下几个方面：

- **从分阶段测试开始** – 在做出大规模部署决定之前，先用具有代表性的预期输入与响应样本测试两个层级。
- **考虑你的语言需求** – 如果你的应用服务于多种语言的用户，Standard 层级扩展的语言支持可能必不可少。
- **平衡安全与性能** – 同时评估准确率提升与延迟差异，以做出知情决策。考虑你能否为 Standard 层级更强的鲁棒性接受几毫秒的额外延迟，还是更倾向于为更直白的评估场景选择延迟优化的 Classic 层级。
- **使用策略级层级选择** – 利用为不同策略选择不同层级的能力来优化你的 guardrail。你可以为内容过滤器与拒绝主题选择不同的层级，同时与 Amazon Bedrock Guardrails 中其余策略与功能组合使用。
- **记住跨区域要求** – Standard 层级要求跨区域推理，因此请确认你的架构与合规要求能够容纳这一点。使用 CRIS 时，你的请求发起于 guardrail 部署所在的 Region，但为了优化延迟与可用性，它可能由 guardrail 推理配置文件中包含的其他 Region 来提供服务。

## 结语

Amazon Bedrock Guardrails 引入防护层级，是我们践行负责任 AI 承诺的重要一步。通过为生成式 AI 应用提供灵活、强大且持续演进的安全工具，我们让组织能够实施不仅创新、而且合乎伦理且值得信赖的 AI 解决方案。这种基于能力的方法让你可以针对每个具体用例调整负责任 AI 实践。你现在可以为不同应用实施恰当级别的保护，同时为 AI 安全与伦理的持续改进开辟路径。新的 Standard 层级在多语言支持与检测准确率上带来显著提升，使其成为许多应用的理想选择，尤其是那些服务多元化全球受众或需要更强防护的应用。这符合负责任 AI 原则——确保 AI 系统在不同语言与文化之间保持公平与包容。同时，Classic 层级仍可供优先考虑低延迟或语言要求更简单的用例使用，让组织按需在性能与保护之间取得平衡。

通过提供这些可定制的保护级别，我们支持组织负责任地开发与部署 AI 的旅程。这一方法有助于确保 AI 应用不仅强大高效，也契合组织价值观、遵守法规并维系用户信任。

想进一步了解 Amazon Bedrock Guardrails 中的防护层级，请参阅[使用 Amazon Bedrock Guardrails 检测并过滤有害内容](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html)，或访问 Amazon Bedrock 控制台创建你的第一个分级 guardrail。
