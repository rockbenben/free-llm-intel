# 使用 Amazon Bedrock 和 LLM 网关实现韧性模式

随着生成式 AI 工作负载从实验走向大规模生产，为[大语言模型（LLM）](https://aws.amazon.com/what-is/large-language-model/)推理实现韧性模式至关重要。随着 LLM 驱动的应用投入生产，组织需要各种方法，使 LLM 推理在大规模下保持高可用、响应迅速且经济高效。现有的韧性最佳实践（如静态稳定性和实施退避与重试）仍然适用。然而，生成式 AI 带来了新的考量，包括模型可用性、快速变化的配额、跨多个提供商的 token 限制，以及与新发布模型保持一致。[Amazon Bedrock](https://aws.amazon.com/bedrock/) 提供完全托管的基础模型，并内置跨区域推理等功能，以提高吞吐量并减少限流。

在为生产环境设计推理时，通常有四个维度指导架构决策：**可用性**、**响应时间**、**成本**和**吞吐量**。可用性指在模型、区域或提供商发生故障时仍能维持推理。响应时间指用户多快收到输出，通常以首个 token 时间（Time to First Token，TTFT）和末个 token 时间（Time to Last Token，TTLT）衡量。成本涵盖每个 token 和每次请求的支出，以及路由决策对其的影响。吞吐量反映系统在负载下能支撑的并发请求数和每秒 token 数。

这些维度相互关联。例如，跨区域路由会提高吞吐量，但可能增加响应时间。本文中的模式主要聚焦于**可用性**：通过故障转移、地域分布和配额隔离，使推理保持运行。后续文章将深入探讨响应时间优化和成本感知路由。

在本文中，你将学习五种实用模式，用于在 AWS 上构建具备韧性的生成式 AI 应用，从 Amazon Bedrock 原生功能逐步推进到使用 LLM 网关的多模型编排。这些模式应对现实世界中的挑战，例如意外流量激增时的配额耗尽、通过推理的地域分布最大化可用性，以及帮助防止多租户环境中的“吵闹邻居”问题。它们还支持通过智能请求路由进行成本优化，并让你根据具体需求灵活使用多个模型和提供商。

这种“爬、走、跑”的方式使你可以根据应用的成熟度和需求逐步采用这些模式。配套的 [GitHub 仓库](https://github.com/aws-samples/sample-resilient-llm-inference) 提供了演示每种模式的代码示例。

### 模式 1：使用 Amazon Bedrock 跨区域推理

Amazon Bedrock 跨区域推理（CRIS）是一项原生功能，可提高应用可用的吞吐量，并帮助在负载下保持一致的性能。你可以使用[跨区域推理配置](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)，将总吞吐量提升到超出单个区域的配额，降低在 AWS 区域内被限流的可能性，并分散模型流量。路由行为因模型而异：有些模型根据实时容量在区域之间动态路由，另一些则在固定的推理区域运行。CRIS 是一种容量机制，而不是故障转移或灾难恢复机制，无法防范模型或提供商的故障。它会基于可用性、延迟和当前需求等实时因素，自动将请求从源区域路由到最佳目标区域。这能应对高峰使用时段意外的流量突发，并降低服务配额影响推理的可能性。

CRIS 配置通常绑定到特定地域（如美国或欧盟）内的商业区域，为推理请求提供性能与延迟之间的适当平衡。这种方式将总吞吐量提升到超出单区域配额，同时在地理边界内保持数据驻留。

Amazon Bedrock 跨区域推理

对于能够承受较高推理请求延迟的某些用例，可以选择使用 [Global Cross-Region Inference profiles](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-support.html#:~:text=Global%20Claude%20Sonnet%204)。使用 Global 配置时，请求可以路由到模型可用于全局推理的任何商业区域，而不像标准跨区域推理配置那样仅限某个地域内的区域。

例如，在我们的演示中，当使用跨区域推理配置向 Amazon Bedrock 发送 10 个请求时，命令输出显示了 CRIS 如何自动将模型推理分布到 3 个 AWS 区域：

| **区域** | **调用次数** | **占比** |
| --- | --- | --- |
| us-east-1 | 1 | 10% |
| us-east-2 | 7 | 70% |
| us-west-2 | 2 | 20% |

*Amazon Bedrock 跨区域推理将 10 个请求分布到三个 AWS 区域*

### 模式 2：使用多个 AWS 账户

虽然 CRIS 可以在单个 AWS 账户内成倍提升吞吐量，你还可以从额外的扩展与隔离策略中受益。AWS 账户分片将请求分散到多个 AWS 账户，每个账户都有独立的配额和 CRIS 配置。

账户分片会形成天然的[故障隔离边界](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/use-fault-isolation-to-protect-your-workload.html)，一个账户中的问题不会影响其他账户，这对于需要在工作负载之间严格隔离的多团队和多租户架构尤其有价值。

结合 Amazon Bedrock 跨区域推理的 AWS 账户分片

运行账户分片演示时，我们使用跨区域推理配置，向两个已配置的 AWS 账户各发送 10 个请求。输出显示了每个账户如何独立地将推理分布到各个 AWS 区域：

| **账户 1** |  |  |
| --- | --- | --- |
| **区域** | **调用次数** | **占比** |
| us-east-2 | 7 | 70% |
| us-west-2 | 3 | 30% |

| **账户 2** |  |  |
| --- | --- | --- |
| **区域** | **调用次数** | **占比** |
| us-east-1 | 2 | 20% |
| us-east-2 | 3 | 30% |
| us-west-2 | 5 | 50% |

*两个 AWS 账户通过 CRIS 独立地将请求分布到各个区域*

### 使用 LLM 网关

对于复杂的生产场景，LLM 网关提供的路由、故障转移和治理能力，超出了直接 API 调用所能实现的范围。网关充当应用与 LLM 提供商之间的智能中介，提供统一的抽象层，使你可通过单一 API 接口访问来自不同提供商的多个模型。这种标准化简化了集成，同时嵌入了负责任 AI 防护措施、审计日志、自动重试与回退逻辑、配额管理等多种能力，帮助你的应用即使在单个模型不可用时也能保持韧性。

LLM 网关跨 AWS 账户和外部提供商编排请求

该网关支持跨多个模型和账户的智能请求路由与负载均衡，在按消费者隔离实施速率限制和配额管理的同时，最大化吞吐量。这有助于防止多租户环境中的“吵闹邻居”问题，同时通过用量分析提供全面的成本跟踪与优化。集中式的可观测性和监控让你全面洞察 LLM 使用模式，并获得细粒度的按应用洞察，帮助快速发现优化机会和排查问题。

如今有许多开源和商业 LLM 网关可用。在我们的演示中，我们使用 [LiteLLM](https://www.litellm.ai/) 作为轻量级的开源方案，在本地运行以演示这些模式。在大规模部署时，[面向多提供商生成式 AI 网关的 AWS 解决方案](https://aws.amazon.com/solutions/guidance/multi-provider-generative-ai-gateway-on-aws/) 提供参考实现和架构，它同样使用 LiteLLM，但增加了企业级能力，包括在 [Amazon Elastic Container Service](https://aws.amazon.com/pm/ecs/)（Amazon ECS）或 [Amazon Elastic Kubernetes Service](https://aws.amazon.com/pm/eks/)（Amazon EKS）上的容器化部署、自动扩缩、[AWS WAF](https://aws.amazon.com/waf/) 防护、密钥管理，以及通过 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 实现的完整可观测性。

### 模式 3：模型回退

即使在主模型触及速率限制或遭遇服务中断时，模型之间的自动故障转移也能提供更高的可用性。该模式旨在在客户定义的主模型和备用模型之间自动路由请求。如果你的回退策略侧重于优化质量和成本，而非应对配额耗尽，[Amazon Bedrock Intelligent Prompt Routing](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.html) 提供了原生选项。它无需外部网关，即可为每个请求动态选择最合适的模型。如果对主模型的调用失败，网关会自动使用备用模型重试请求，即使在流量意外激增时也能支持高可用性。回退策略还兼顾成本优化和性能考量，例如限制较高成本模型的用量，并在适当时回退到更具成本效益的替代方案。

以受限主模型和高容量备用模型进行的回退演示

在我们的演示中，LiteLLM 配置定义了一个主模型，其速率限制为每分钟 3 个请求（RPM），以及一个容量为 25 RPM 的备用模型。当客户端通过网关发送 10 个并发请求时，前三个请求路由到 Amazon Bedrock 中的主模型。随着主模型达到速率限制，LiteLLM 会自动将剩余七个请求转移到备用模型。这 10 个请求无需人工干预或应用层的重试逻辑，便全部成功完成。

演示输出证实了该模式的有效性：尽管主模型存在速率限制，10 个请求仍全部成功完成，显示出很高的可靠性。分布结果显示，在达到配额之前，恰好有 3 个请求由主模型处理。其余 7 个请求故障转移到备用模型，展示了网关通过智能路由维持服务可用性的能力。

显示模型分布的回退演示输出

### 模式 4：跨模型负载均衡

负载均衡模式将请求分散到多个模型实例，以优化资源利用率并帮助防止瓶颈。这种方式不仅最大化利用率，还允许你按需添加或移除模型实例，从而快速扩展。例如，在全面部署前评估新模型时，你可以实施加权路由或 A/B 测试策略，只将一小部分请求导向新模型，而大多数请求继续使用经过验证的模型。

跨主模型负载均衡并由回退承接溢出流量

在我们的负载均衡演示中，网关使用 shuffle 策略成功将 10 个并发请求分布到两个模型。负载均衡器最初向两个已配置的主模型各路由 3 个请求，当达到速率限制时，剩余 4 个请求会自动重定向到备用模型。结果是 100% 的成功率，展示了负载均衡如何与回退策略协同工作。

负载均衡演示输出

### 模式 5：多租户配额隔离

多租户配额隔离模式创建逻辑隔离的环境，每个环境都配备自己的配额和速率限制，以管理多租户环境中的请求。通过为每个消费者实施独立的速率限制桶，该模式有助于防止“吵闹邻居”问题——即一个消费者的请求对其他消费者的性能产生负面影响。无论其他租户的使用模式如何，每个租户都获得专用配额，从而支持公平的资源分配，并在各消费者之间保持一致的服务质量。

按消费者独立速率限制的多租户配额隔离

该模式非常适合这样的环境：多个应用共享模型资源，同时要求可预测的性能和可靠的隔离。

在我们的演示中，三个速率限制不同的消费者同时尝试访问同一模型。消费者 A 被配置为每分钟仅允许 3 个请求（RPM），而消费者 B 和 C 各有 10 RPM。当三个消费者各发送 5 个并发请求时，网关强制执行各自的配额。消费者 A 遭遇速率限制，只有 3 个请求成功，2 个被拒绝。消费者 B 和消费者 C 达到 100% 成功率，5 个请求全部得到处理。

| **配额隔离分析** |  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- | --- |
| **消费者** | **类型** | **成功率** | **总数** | **成功** | **失败** | **被限流** |
| A | Noisy | 60% | 5 | 3 | 2 | 2 |
| B | Normal | 100% | 5 | 5 | 0 | 0 |
| C | Normal | 100% | 5 | 5 | 0 | 0 |

*多租户隔离演示输出*

### 重要考量

上述指导对工作负载需求、数据安全与合规义务以及性能需求做了某些假设。与大多数事情一样，“我什么时候应该使用这些模式？”的答案是“视情况而定！”。以下是一些适合应用这些模式的用例。

#### 适用场景与用例

**高可用要求**：当你的应用无法容忍停机时，多个模型可提供自动故障转移。如果主模型触及速率限制或发生中断，请求将路由到备用模型，从而维持 100% 的可用性。

**突破单模型配额进行扩展**：单个模型都有吞吐上限。使用多个模型（即使是跨不同账户/区域的同一模型类型）也能成倍增加总可用容量。对于请求量可能超出单模型配额的高容量应用，这一点至关重要。

**多租户隔离**：在软件即服务（SaaS）应用中，不同客户可以使用不同的模型或模型实例，从而避免某个客户的使用影响其他客户。

**开发与生产**：为测试（更便宜、更快的模型）和生产（更高质量的模型）分别配置模型，无需改动代码。
