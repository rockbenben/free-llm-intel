# 在 Amazon Bedrock 上超越 Chain-of-Thought：用 Chain-of-Draft 思考

随着各组织扩大生成式 AI 的落地规模，在质量、成本和延迟之间取得平衡这一关键挑战变得越来越复杂。当[推理成本](https://aws.amazon.com/blogs/machine-learning/reduce-ml-inference-costs-on-amazon-sagemaker-with-hardware-and-software-acceleration/)占大语言模型（LLM）[运营支出](https://docs.aws.amazon.com/wellarchitected/latest/machine-learning-lens/machine-learning-lens.html)的 70–90%，而冗长的 prompt 策略又把 token 数量膨胀 3–5 倍时，各组织都在积极寻找更高效的模型交互方式。传统 prompting 方法虽然有效，但往往带来不必要的开销，既影响成本效率，也影响响应时间。

本文探讨 Chain-of-Draft（CoD）——Zoom AI Research 论文 [Chain of Draft: Thinking Faster by Writing Less](https://arxiv.org/abs/2502.18600) 中提出的一种创新 prompting 技术，它改变了模型处理推理任务的方式。Chain-of-Thought（CoT）prompting 一直是增强模型推理能力的首选方法，而 CoD 提供了一种更高效的替代方案，它更贴近人类解决问题的模式——用简洁、高信号量的思考步骤取代冗长的解释。

我们使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 和 [AWS Lambda,](https://aws.amazon.com/lambda/) 演示了 CoD 的一个实际实现，它可带来显著的效率提升：token 用量最多减少 75%，延迟下降超过 78%，同时保持传统 CoT 方法的准确率水平。通过详细示例、代码示例和性能指标，我们演示了如何在 AWS 环境中部署 CoD，并衡量它对 AI 实现的影响。这种方法不仅优化了成本，还通过更快的响应时间提升了整体用户体验。

## 理解 Chain-of-Thought prompting

Chain-of-Thought（CoT）prompting 是一种引导大语言模型逐步推理问题、而不是直接跳到答案的技术。对于逻辑谜题、数学问题和常识推理场景等复杂任务，这一方法被证明尤为有效。通过模仿人类解决问题的模式，CoT 帮助模型把复杂问题拆解为可处理的步骤，从而同时提升准确率与透明度。

CoT prompting 示例：

**问题**：如果有 5 个苹果，你吃掉了 2 个，还剩多少个苹果？

**CoT 回复**：从 5 个苹果开始。我吃掉 2 个苹果。用 5 减去 2。5 – 2 = 3，还剩 3 个苹果。

然而，如上例所示，这种方法在生产环境中存在一些缺点。CoT 回复的冗长特性导致 token 用量增加、成本上升。生成详细解释所需的额外处理时间会带来更高的延迟，在某些情况下使它不太适合实时应用。此外，详细的输出可能使下游处理以及与其他系统的集成变得复杂。

## 引入 Chain-of-Draft prompting

Chain-of-Draft（CoD）是一种新颖的 prompting 技术，它通过限制每个推理步骤所用的词数来减少冗长，只关注推进推理所必需的关键计算或变换，同时显著降低 token 用量与推理延迟。CoD 的灵感来自人类如何用简短的脑内笔记而不是冗长解释来解决问题——它鼓励 LLM 生成紧凑、高信号量的推理步骤。

CoD 的关键创新在于它的约束：每个推理步骤被限制在 5 个词以内。这一限制迫使模型专注于关键的逻辑要素，同时尽量减少不必要的冗长。例如，在求解数学应用题时，CoD 不会生成解释每一步的完整句子，而是产出简洁的数值运算和关键逻辑标记。

请看这个例子：

**问题**：Jason 有 20 根棒棒糖。他给了 Denny 一些棒棒糖。现在 Jason 有 12 根棒棒糖。Jason 给了 Denny 多少根棒棒糖？

CoT 回复可能包含若干句子来解释推理过程，例如：“Jason 有 20 根棒棒糖。他给了 Denny 一些，现在还剩 12 根。所以他一共给出了 8 根。”

相比之下，CoD 回复只会写：“Start: 20, End: 12, 20 – 12 = 8.”

这种极简方法在只使用少得多 token 的情况下实现了同样的逻辑推理。

### **CoD 为何有效**

CoD 背后的核心思想是：大多数推理链都包含高度冗余。通过把步骤提炼到语义核心，CoD 帮助模型专注于任务的逻辑结构而非语言流畅度。由此带来的是更低的推理延迟（因为输出更短）、token 成本下降（因为生成量最小化），以及更干净的输出便于下游解析或自动化。

这种极简并没有牺牲准确率。事实上，根据[Zoom AI 原始论文](https://arxiv.org/html/2502.18600v1)，CoD“在 GSM8K 上达到 91.4% 的准确率（CoT 为 95.3%），同时把输出 token 最多减少 92.1%，并在测试的若干模型上把延迟几乎减半”。

在底层，CoD 技术使用自然语言 prompt，指示模型“逐步思考”，同时显式限制每个推理步骤的长度：“Only keep a minimum draft for each thinking step, with 5 words at most.”（每个思考步骤只保留最小草稿，最多 5 个词。）

研究人员发现，GPT-4、Claude 和 Cohere Command R+ 等模型在这些约束下表现尤其出色，特别是在使用 few-shot 示例来演示简洁推理模式时。

[![流程图：展示 Chain-of-Draft prompting 技术，三个连续步骤导向最终答案，突出效率优势。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/15/ML-19022-image-2.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/15/ML-19022-image-2.png)

除算术任务之外，CoD 在常识推理任务中也表现出强劲性能。在[Zoom AI 原始论文](https://arxiv.org/html/2502.18600v1)中，作者使用 big-bench 基准评估 CoD，具体聚焦日期理解和体育理解任务。评估使用了与算术评估相同的 system prompt，以保持实验之间的一致性。结果显示，CoD 不仅显著减少了 token 生成和延迟，而且在若干情况下准确率超过 CoT——尤其是在不需要冗长输出的时候。

一个值得注意的发现来自某个大语言模型在体育理解任务上的表现：CoT 产出了冗长的回复，平均 172.5 个输出 token，而 CoD 将其降至 31.3 个 token，实现了约 82% 的减少。有意思的是，准确率还略有提升，说明 CoD 用更少的词可以更有效。

以下是[原始论文](https://arxiv.org/html/2502.18600v1)中的一张快照，展示了在两个 LLM 上的评估结果：

| --- | --- | --- | --- | --- |
| LLM-1 | Standard | 72.60% | 5.2 | 0.6s |
|  | Chain-of-Thought | 90.20% | 75.7 | 1.7s |
|  | Chain-of-Draft | 88.10% | 30.2 | 1.3s |

|  | Chain-of-Thought | 87% | 172.5 | 3.2s |

这些结果进一步验证了 CoD 在真实推理场景中的价值，表明模型可以用更少、更聪明的 token 进行有效推理。对生产使用的启示很明确：更快的响应和更低的成本，而不必在质量上做出权衡。

## 在 AWS 上实现与评估

为了评估 CoD prompting 技术的效率，我们在 Amazon Bedrock 中运行了一次测试，使用 LLM 求解“红球、蓝球和绿球”谜题。

**谜题：** 你有三个盒子。每个盒子里有三个球，球可以是红色、蓝色或绿色。1 号盒标签为“仅红球”。2 号盒标签为“仅蓝球”。3 号盒标签为“仅红球和蓝球”。所有盒子上的标签都是错误的。任务是在已知所有标签都错误的前提下，判定每个盒子的内容。你只能从一个盒子中取出一个球并观察它的颜色。然后你必须推断出三个盒子的内容。

我们选择这个谜题，是因为求解它所需的 token 数量可以被度量：该问题需要拆解为若干逻辑步骤，每一步都要求 LLM 处理并保留信息。LLM 需要处理“如果—那么”语句，并考虑导致逻辑推理的多种可能性。LLM 还需要在整个推理过程中保持谜题的上下文；最后，LLM 需要理解符号以及颜色、标签与球之间的关系。

### **前置条件**

要在 Amazon Bedrock 中测试并比较这些 prompting 技术，请确认你满足以下前置条件：

- 拥有可创建并执行 Lambda 函数的 AWS 账户
- 在你所在的 AWS 区域（例如 us-east-1）已启用 Amazon Bedrock 访问权限，并具备 Model Access（例如 Model-1 和 Model-2）；可选择你想要的任意模型
- 用于 Lambda 函数执行的 [AWS IAM](https://aws.amazon.com/iam/) 角色
- 调用 Amazon Bedrock 模型的权限（[bedrock:Converse](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html)）
- 向 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 写入自定义指标的权限（[cloudwatch:PutMetricData](https://docs.aws.amazon.com/AmazonCloudWatch/latest/APIReference/API_PutMetricData.html)）
- （可选）用于日志记录的 [CloudWatch Logs](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/WhatIsCloudWatchLogs.html) 权限
- 必要的 Python 库（[boto3](https://boto3.amazonaws.com/v1/documentation/api/latest/index.html)），已包含在 Python 3.9 或更高版本的 AWS Lambda 运行时环境中

### **使用 Amazon Bedrock Converse API 进行评估**

我们首先创建一个 Python Lambda 函数，用于通过 Amazon Bedrock 与模型交互来求解谜题。该 AWS Lambda 函数使用 [Amazon Bedrock Converse API](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html)，它提供统一、一致的接口来与各种基础模型交互。Converse API 简化了向模型发送对话消息并接收回复的过程，支持多轮对话和高级功能，同时负责处理 AWS 认证与基础设施。该 Lambda 函数初始化 Amazon Bedrock Runtime 和 CloudWatch 的客户端，将静态谜题 prompt 作为用户消息发送给 Converse API，获取响应文本，并计算延迟以及输入和输出的 token 用量。这些指标被发布到 CloudWatch，并记录相关日志。最后，函数返回模型的答案以及输入/输出 token 数。错误会被记录，并以正确的 HTTP 错误码返回。
[![架构图：展示 AWS Lambda 在 AWS 区域内调用 Amazon Bedrock。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/15/ML-19022-image-4.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/15/ML-19022-image-4.png)

**Lambda 函数**

```
import json
import boto3
import time
import logging
from botocore.exceptions import ClientError

logger = logging.getLogger()
logger.setLevel(logging.INFO)

bedrock = boto3.client('bedrock-runtime', region_name='us-east-1')
cloudwatch = boto3.client('cloudwatch')
MODEL_ID = "model1-id" # Replace with actual Model 1 ID
PROMPT = (
 "You have three boxes. Each box contains three balls, but the balls can be red, blue, or green. "
 "Box 1 is labeled as 'Red Balls Only'. Box 2 is labeled 'Blue Balls Only'. "
 "Box 3 is labeled 'Red and Blue Balls Only'. The labels on the boxes are all incorrect. "
 "The Task: You must determine the contents of each box, knowing that all labels are incorrect. "
 "You can only take a single ball from one box and observe its color. "
 "Then you must deduce the contents of all three boxes. "
 "Think step by step to answer the question, but only keep a minimum draft for each thinking step, with 5 words at most. "
 "Return the answer at the end of the response after separator ###."
)

def lambda_handler(event, context):
 conversation = [{"role": "user", "content": [{"text": PROMPT}]}]
 start_time = time.time()
 try:
 response = bedrock.converse(
 modelId=MODEL_ID,
 messages=conversation,
 inferenceConfig={"maxTokens": 2000, "temperature": 0.7}
 )
 response_text = response["output"]["message"]["content"][0]["text"]
 latency = time.time() - start_time
 input_tokens = len(PROMPT.split())
 output_tokens = len(response_text.split())

 cloudwatch.put_metric_data(
 Namespace='ChainOfDraft',
 MetricData=[
 {"MetricName": "Latency", "Value": latency, "Unit": "Seconds"},
 {"MetricName": "TokensUsed", "Value": input_tokens + output_tokens, "Unit": "Count"},
 ]
 )

 logger.info({
 "request_id": context.aws_request_id,
 "latency_seconds": round(latency, 2),
 "total_tokens": input_tokens + output_tokens
 })

 return {
 "statuscode": 200,
 "body": json.dumps({
 "response": response_text,
 "input_tokens": input_tokens,
 "output_tokens": output_tokens,
 "metrics": {
 "latency_seconds": round(latency, 2),
 "total_tokens": input_tokens + output_tokens,
 },
 }),
 }

 except ClientError as e:
 logger.error(f"AWS service error: {e}")
 return {"statuscode": 500, "body": json.dumps("Service error occurred")}

 except Exception as e:
 logger.error(f"Unexpected error: {e}")
 return {"statusCode": 500, "body": json.dumps(f"Internal error occurred: {e}")}
```

如果你使用的是 Model 2，请把上述代码中的 MODEL_ID 改为 Model 2 的 id。其余代码保持不变。

## 何时应避免使用 CoD

虽然 CoD prompting 在效率和性能方面提供了很有吸引力的优势，但它并不普遍适用。有些场景下传统 CoT 甚至更冗长的推理可能更有效或更合适。基于我们的实验和原始研究的发现，以下是一些关键考量：

- **Zero-shot 或仅靠 prompt 的用例**：CoD 在与强 few-shot 示例配合时表现最佳。在没有提供任何推理模式的 zero-shot 场景中，模型往往难以自行采用极简草稿风格。这可能导致准确率下降或推理步骤不完整。
- **需要高可解释性的任务**：对于法律或医疗文档审查、审计轨迹或受监管环境等用例，冗长推理可能是必需的。在这种情况下，CoT 更透明、逐步的解释提供了更好的可追溯性和可信度。
- **小型语言模型**：CoD 在参数量少于 30 亿的模型上表现不佳。这类模型缺乏有效执行 CoD 风格 prompt 所需的指令遵循保真度和推理能力。在这些情况下 CoT 可能取得更好的结果。
- **创意或开放式任务：** 从展开阐述中获益的任务——例如写作、构思或面向用户的对话——如果过度压缩可能会失去价值。CoD 最适合结构化推理、逻辑和确定性任务，在这类任务中简洁能提升性能。

简而言之，当目标是以最小开销实现高效推理时，CoD 表现出色——但精心的 prompt 设计、模型选择和任务匹配是成功的关键。

## 结论与要点

CoD prompting 正成为希望优化生成式 AI 实现的组织的有效技术。通过鼓励语言模型以简洁、聚焦的步骤推理，CoD 在性能和资源利用两方面都实现了显著改进。我们基于 Amazon Bedrock 和 AWS Lambda 的实现表明，与传统的 CoT prompting 相比，它在 token 用量和延迟方面都有明显收益，同时在各类基础模型和复杂推理任务上保持了相当的准确率。随着 AI 不断演进，CoD 代表着迈向更高效、更高性能语言模型的重要一步。对于速度与 token 效率至关重要的结构化推理任务，它尤其有价值，不过它并不是一刀切的解决方案。我们鼓励从业者在自己的 AI 工作流中探索 CoD，利用它降低成本、改善响应时间、提升可扩展性的潜力。AI 的未来在于更聪明、更高效的推理方法，而 CoD prompting 正处于这场变革的前沿。
