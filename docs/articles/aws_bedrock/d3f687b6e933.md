# Amazon Bedrock tokenomics 数据湖

如果你需要为 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 工作负载建一个可观测性数据湖，有这想法的不止你一个。当每天跨多个账户发起数千次模型调用时，请求发出去之后你可能会纳闷：到底发生了什么？你能看到汇总账单，却看不到每次调用内部发生了什么。

你可能会开始追问：发出去的 prompt 是什么，模型返回了什么，用了多少 token，是哪个模型处理的，响应质量到底怎么样！如果你是平台工程师或机器学习 (ML) 工程师，要照看跨团队的一大批 Amazon Bedrock 工作负载，这就是个实打实的问题：用量突增没法排查，浪费的 prompt 找不出来，也分不清哪个团队用了多少。

我们做了一套东西来帮忙：一个集中式的 Amazon Bedrock 调用可观测性数据湖。本文会讲你手头有哪些原生数据、我们是怎么设计这个数据湖的，也会演示怎么用它查看 prompt、算出每次调用的成本。[AWS CloudFormation](https://docs.aws.amazon.com/cloudformation/) 模板、[AWS Lambda](https://aws.amazon.com/lambda/) 代码和 SQL 查询都放在 [AWS Sample Bedrock Invocation Data Lake GitHub 仓库](https://github.com/aws-samples/sample-bedrock-token-cost-allocation) 里。本文梳理架构和部署步骤，仓库里则有部署所需的全部内容。

## 目前 Amazon Bedrock 能提供哪些可见性？

Amazon Bedrock 提供[模型调用日志记录](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html)，功能确实强大。你在[每个使用 Bedrock 的 AWS 账户的设置](https://us-east-1.console.aws.amazon.com/bedrock/home?region=us-east-1#/settings) 里打开调用日志，它就会把请求和响应的完整记录投递到 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/pm/serv-s3/) 或 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)。

数据是在，只是被锁在各自的账户里。你真正想要的是整个组织里每次调用的一个统一、快速、可查询的视图。这正是数据湖能给的。

## 什么是 Amazon Bedrock 可观测性数据湖？

集中式 [Amazon Bedrock 调用日志](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html) 数据湖把各关联账户里的原始模型调用日志汇聚到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)，再由订阅日志过滤器把这些记录转发到中央账户。中央账户通过 [Amazon Data Firehose](https://aws.amazon.com/firehose/) 处理数据，并借助 [Amazon Athena](https://aws.amazon.com/athena/) 把它们呈现为一张干净的表，供你在整个组织范围内查询。

图 1：跨中央账户与关联账户的 Amazon Bedrock 调用可观测性数据湖架构

所有组件都用两个 [AWS CloudFormation](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/Welcome.html) 模板以基础设施即代码的方式部署，因此可以在组织里的每个账户中反复铺开。这些内容可在 [AWS Sample Bedrock Invocation Data Lake GitHub 仓库](https://github.com/aws-samples/sample-bedrock-token-cost-allocation) 找到。

## 每条 Amazon Bedrock 调用日志会捕获什么？

部署并运行这套方案后，你会在所部署的关联账户里得到一份汇总数据，可以用 Athena 查询。日志被展平进处理后的表之后，每次调用你能拿到：

- 用户或应用发出的 **prompt**。
- 返回的**模型响应**。
- **输入与输出 token 数**，用来衡量每次调用的真实分量。
- **所用的模型**，用来了解各团队对模型的使用情况。
- **停止原因**（例如 `max_tokens`），它告诉你响应是在哪里被截断的。
- **账户和时间戳**，用来对一切做归属划分和时间切片。
- **该** [AWS Identity and Access Management (IAM) 角色](https://aws.amazon.com/iam/?trk=40032cd2-744c-4b2c-ad0c-cf60894e0921&sc_channel=ps&ef_id=CjwKCAjws_DTBhB_EiwAXZknGfru2_JWQb1nqidRQ4APsbkaGf1W2ywetPh_unJq1IEvVAlNJfLWzRoCpg4QAvD_BwE&gads_camp=23528572748&gads_ag=198422384371&gads_ad=795811958070&gads_kw=iam&gads_matchtype=e&gads_network=g&gads_device=c&gads_geo=9198785&gad_campaignid=23528572748&gbraid=0AAAAADjHtp-pAfh6ucw0EYbg13-jUO8NM&gclid=CjwKCAjws_DTBhB_EiwAXZknGfru2_JWQb1nqidRQ4APsbkaGf1W2ywetPh_unJq1IEvVAlNJfLWzRoCpg4QAvD_BwE)，用来查看是谁发出了 prompt。

像这样把每次调用都记录下来之后，你的认知会从"我们在 Amazon Bedrock 上用了 X 个 token"变成"每次模型调用里到底是什么内容、效率有多高，一清二楚"。这正是平台团队和 ML 团队一直缺的可见性。

## Amazon Bedrock 数据湖是怎么设计的？

数据湖让每次调用走五个阶段：从 Amazon Bedrock 写出日志，到你能用 Athena 查询为止。

### 1. Amazon Bedrock 写出调用日志

应用每次调用 Amazon Bedrock 模型时，Amazon Bedrock 都能记录下发生的事：用了哪个模型、哪个账户、哪个 IAM 身份发起调用、消耗了多少输入和输出 token，以及 prompt 和响应文本。这个功能每个账户通过一次 API 调用就能开启：把 Amazon Bedrock 指向一个 CloudWatch 日志组，并给它一个能在其中写入的角色。

### 2. CloudWatch 把日志转发到中央账户

每个源账户会在自己的 Amazon Bedrock 日志组上挂一个订阅过滤器。可以把它理解成一条常驻的转发规则：把每条新事件都发到这个地址。这个地址就是中央账户里的一个 Amazon CloudWatch Logs 目标。源账户拿不到中央管道的权限，它们只管把事件交给目标，之后由中央账户自己的角色接手。

### 3. 一个小型 Lambda 整理每条记录

CloudWatch 交出来的不是干净的 JSON。它把事件打成批次，压缩并编码包起来，所以到达时看着像一堆乱码，拆开才看得懂。一个小型 Lambda 函数做三件事：

- 把批次拆回一条条独立的日志记录。
- 丢掉噪音。CloudWatch 偶尔会发一些内务消息和英文提示，比如"Amazon Bedrock 日志的权限已设置妥当"。这些不是调用数据，放它们过去会打断下一阶段。
- 展平一个别扭的字段。调用方的身份原本嵌在下一层，Lambda 把它提到顶层，之后查询就直观了。

### 4. Amazon Data Firehose 转成 Parquet 并写入 S3

Amazon Data Firehose 先缓冲记录，再把它们写入 Amazon S3 存储桶，途中把 JSON 转成 Parquet。Firehose 还会按日期路径归档每个对象（`year=2026/month=08/day=27/`）。

### 5. 用 Athena 查询数据并关联成本数据

[AWS Glue](https://aws.amazon.com/glue/) 表告诉 Athena 怎么读这些文件，于是用普通 SQL 就能查询数据湖。你能看到哪些用户用的 token 最多、哪些模型最常被选中、大家都在 prompt 些什么。需要的话，还可以把它接到 [AWS Cost and Usage Report](https://aws.amazon.com/aws-cost-management/aws-cost-and-usage-reporting/) (CUR) 上，按天算出用户 prompt 的花费。

## 开始前需要准备什么？

部署前需要备好几样东西：

- 为 [AWS Command Line Interface (AWS CLI)](https://aws.amazon.com/cli/) 配好每个账户的凭证。
- **CloudFormation** 的 `CAPABILITY_IAM` 和 `CAPABILITY_NAMED_IAM` 权限。
- **至少一个关联账户**（运行 Amazon Bedrock 工作负载的账户）和**一个中央账户**，用来接收复制过来的日志（两者可以是同一个账户）。
- **Python 3 与 Boto3**（`pip install boto3`），用于端到端测试脚本。
- [克隆好的仓库](https://github.com/aws-samples/sample-bedrock-token-cost-allocation)，里面包含全部资源。

## 怎么部署？

**这里的顺序很关键。** 中央账户的堆栈必须先存在，关联账户的堆栈才能引用它。

### 阶段 1：部署中央数据湖堆栈

先把中央 CloudFormation 堆栈部署到将要承载管道的账户里。继续之前，记下堆栈输出中的两个值：CloudWatch Logs 目标 ARN（每个源账户都要用），以及 [AWS Quick Sight](https://aws.amazon.com/quick/?trk=cb69a790-31b4-4f3f-ab38-8c131506ae2b&sc_channel=ps&ef_id=Cj0KCQjw2OnUBhC2ARIsACKyfaHOyrI2BSqC3eo7DZbbj0Ks030dwANVC-ITwsJaw_YzyJqknqgei6IaAm3WEALw_wcB:G:s&gads_camp=23528573981&gads_ag=191423962694&gads_ad=806967564154&gads_kw=amazon%20quick&gads_matchtype=e&gads_network=g&gads_device=c&gads_geo=1006993&gad_campaignid=23528573981&gbraid=0AAAAADjHtp_o1ijSErUcY81biixQPaoFW&gclid=Cj0KCQjw2OnUBhC2ARIsACKyfaHOyrI2BSqC3eo7DZbbj0Ks030dwANVC-ITwsJaw_YzyJqknqgei6IaAm3WEALw_wcB) 角色 ARN（如果之后要部署仪表板会用到）。

### 阶段 2：在每个源账户部署日志记录堆栈

部署关联账户的 CloudFormation。每个运行 Amazon Bedrock 工作负载的账户都要来一遍。源堆栈很小，只接收一个输入：阶段 1 里的目标 ARN。

### 阶段 3：开启 Amazon Bedrock 模型调用日志记录

部署堆栈并不会启动日志记录。Amazon Bedrock 的日志记录是账户级设置，不是 CloudFormation 资源。每个源账户激活一次，把 Amazon Bedrock 指向阶段 2 里的日志组和日志记录角色，并且只开启 CloudWatch 投递。

### 阶段 4：确认数据已到达

在源账户里跑一次测试调用，等 Amazon Data Firehose 把缓冲区刷出去（[大约一分钟，有时更久](https://docs.aws.amazon.com/firehose/latest/dev/basic-deliver.html#frequency)），再确认数据湖的 `data/` 前缀下已经出现 Parquet 对象。最后到 S3 存储桶里看看数据。

### 阶段 5：创建 Athena 视图并查询数据

中央堆栈把视图定义存成一条具名的 Athena 查询，但不会执行它。手动跑一次这条保存的查询，就生成了展平视图。查询都在专用的 Athena 工作组里跑，可以针对原始表，也可以针对展平视图。视图很直白：token 数、缓存 token、停止原因，以及 prompt/响应预览，都已经是平铺的列。

## 怎么看 Amazon Bedrock 的 token 成本？

想给这一切算出美元金额时，把处理后的表与 CUR 2.0 数据做关联，关联键是 IAM ARN。可用的示例查询在 [Bedrock Data Lake SQL](https://github.com/aws-samples/sample-bedrock-token-cost-allocation/blob/main/Bedrock%20Data%20Lake%20SQL.md) 文件里。

就这一次关联，把可观测性数据湖也变成了成本归因工具：哪些 prompt 最花钱、各团队或账户每天的成本、效率最低的那些调用究竟在烧掉多少钱。这是很棒的补充，但早在你走到这一步之前，数据湖本身就已经值回票价了。

## 什么是 tokenomics，这个数据湖为什么对它重要？

tokenomics 指的是管理人工智能 (AI) token 消耗经济性的实践，在 2026 年 FinOps Foundation 大会上被宣布为一个正式的 FinOps 领域。它建立在与 Cloud Financial Management 相同的 See、Save、Run、Plan 四大支柱之上，只是把对象从基础设施换成了 token。难点在于，无法衡量的东西就没法优化。如今大多数组织都缺少回答基本 tokenomics 问题所需的细粒度数据：哪些团队消耗的 token 最多，哪些 prompt 在浪费。有了每次调用的 token 与成本可见性，团队就能把每个工作负载配到合适的模型上——这正是这个数据湖给你的东西。对每次调用的 prompt、响应、token 数、模型和 IAM 身份都能看见，你就有了开展 tokenomics 实践的基础，而不只是盯着一张 Amazon Bedrock 账单。

## 有了 Amazon Bedrock 调用日志，现在能做什么？

每次调用都落在一张快速可查询的表里，过去那些让人头疼的问题终于能回答了：

- **调试与审计调用 –** 在某个账户里调出指定调用的确切 prompt 和响应，不必翻原始日志文件。
- **衡量 token 效率 –** 把 `input_tokens` 与 `output_tokens` 对比，再结合各团队的模型选择，找出白白烧 token 的地方。
- **发现 prompt 优化机会 –** 找出响应被截断的请求（`stop_reason = max_tokens`），这往往说明 prompt 或配置需要调整。
- **审视模型系列 –** 数据能显示每种模式由哪个模型承接，团队可据此确认模型与工作负载是否匹配。
- **管理跨团队用量 –** 每次调用都关联到一个账户，谁在跑什么一目了然。

## 数据治理

这套方案把各团队完整的 prompt 和补全结果集中到单个 Amazon S3 存储桶里，因此安全与治理从一开始就内建在架构中。存储桶由 AWS Key Management Service (AWS KMS) 的服务器端加密保护，数据默认静态加密。对存储桶和 Amazon Athena 查询结果的访问，由 AWS Identity and Access Management (IAM) 策略控制，你可以把权限收窄到确实需要的团队和角色。prompt 里可能带有个人身份信息 (PII)，取决于用户怎么与 Amazon Bedrock 交互。建议检查一下 IAM 策略和 Amazon S3 存储桶策略，确认只有获得授权的主体能接触到这些数据。

## 清理

想删掉创建的资源，先清空存储桶里的对象，再删除 CloudFormation 模板。注意删除前要把 S3 存储桶清空，Athena Workgroup 需要手动删除。

## 总结

现在你有办法把 Amazon Bedrock 的原始调用日志，变成一层统一、快速、覆盖整个组织的可观测能力。不再是封闭的系统，各账户里每次 prompt、响应、token 数和模型选择都看得清清楚楚；想看成本时，还能直接对上每一笔。

和所有系统项目一样，别想着一口吃成胖子。先从一两个关联账户开始，把查询调用表练熟，再推广到整个组织。你的 Amazon Bedrock 用量只会越来越大，越早建好这层可见性，日后每次谈调试、效率和成本就越省事。

如果有疑问，或者想分享你怎么在自己的工作负载里做可观测性，欢迎到 [AWS Sample Bedrock Invocation Data Lake GitHub 仓库](https://github.com/aws-samples/sample-bedrock-token-cost-allocation) 看看。
