# 文档智能演进：构建并评估可扩展的 KIE 解决方案

智能文档处理（IDP）指的是从各种文档格式——无论结构化还是非结构化——中自动抽取、分类并处理数据。在 IDP 的整体版图中，关键信息抽取（KIE）是一项基础组件，让系统能够在尽可能少的人工干预下识别并抽取文档中的关键数据点。横跨金融服务、医疗健康、法律和供应链管理等不同行业的组织，正越来越多地采用 IDP 解决方案来精简运营、减少人工录入并加速业务流程。随着文档数量呈指数级增长，IDP 解决方案不仅在实现处理自动化，还支撑起复杂的 agentic 工作流——AI 系统可以在其中分析抽取出的数据，并在尽可能少的人工干预下发起恰当的后续动作。能否准确处理发票、合同、病历和监管文件，已经不只是一种竞争优势，而是业务上的必需能力。重要的是，要开发有效的 IDP 解决方案，不仅需要稳健的抽取能力，还需要与特定行业需求以及各组织自身用例相匹配的定制化评估框架。

在本文中，我们演示一套端到端方法，用于构建并评估基于 [Amazon Nova](https://aws.amazon.com/ai/generative-ai/nova/) 模型的 KIE 解决方案，这些模型可通过 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 使用。这套端到端方法涵盖三个关键阶段：数据就绪（理解并准备你的文档）、方案开发（用合适的模型实现抽取逻辑），以及性能度量（评估准确率、效率与成本效益）。我们使用 [FATURA](https://arxiv.org/abs/2311.11856) 数据集来演示这套完整方法——该数据集汇集了多样化的发票文档，可作为真实企业数据的一个有代表性的替代样本。通过走完这个实践示例，我们展示如何为文档处理任务选择、实现并评估基础模型，同时把抽取准确率、处理速度和运营成本等关键因素纳入考量。

无论你是正在探索[生成式 AI](https://aws.amazon.com/generative-ai/) 能力的数据科学家、正在实现文档处理 pipeline 的开发者，还是希望了解自动化可能性的业务分析师，本指南都能为你的用例提供有价值的洞见。读完本文，你将实际掌握如何使用大语言模型完成文档抽取任务、为你的具体用例建立有意义的评估指标，并基于性能与业务两方面的考量做出有理有据的模型选择。这些技能可以帮助你的组织摆脱人工处理文档的方式，转向更高效、更准确、更可扩展的文档处理解决方案。

## 数据集

要演示我们的 KIE 解决方案并对其性能做基准测试，需要一个既能提供贴近真实的文档处理场景、又能给出可靠 ground truth 以便准确衡量性能的数据集。FATURA 就是这样一个数据集，它包含 10,000 张发票、50 种不同的版式（每种版式 200 张发票）。这些发票均为单页文档，以 JPEG 图像形式存储，每份文档标注了 24 个字段。高质量的标注是评估工作的基础，它们充当 ground truth，我们据此衡量抽取准确率。在检查 FATURA 数据集时，我们发现 ground truth 标注中存在若干需要标准化的差异。其中包括结构上的不一致（例如嵌套式与扁平式的字段表示）以及取值格式的不一致（例如 `INVOICE DATE: 01/15/2023` 这类带前缀的字段，或数值以字符串而非浮点数存储）。

为确保研究中的评估公平且准确，我们对这些差异做了归一化：去掉不一致的前缀，并让标注格式与我们的（大语言模型）LLM 解决方案所期望的输出结构保持一致。本文中，我们从 49 种不同版式各抽取 40 份文档，共得到 1,960 个样本，下图展示了标签的分布；我们省略了一种版式，因为其 ground truth 标注存在若干不一致之处。如图所示，各字段在各样本间的分布明显不均衡，18 个不同字段的出现次数大致在 250 到 1,800 次之间。这种稀疏性反映了文档的真实情况：并非每份文档都包含所有字段——这是信息抽取系统面临的一项关键挑战，系统必须学会处理缺失字段，而不是在数据不存在时强行给出预测。

![FATURA 数据集字段频次可视化：DATE 字段以 1900 条记录占据主导，其余 16 个字段的数量各不相同](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/07/ML-18379_data_distribution.jpg)

从业者还经常遇到其他数据挑战：单个字段存在多个取值（例如为联系人列出多个电话号码）、缺失信息的表示不一致（空字符串、*N/A*、短横线或其他占位符）、字段既可能包含结构化文本也可能包含非结构化文本（地址），以及处理取值之间的层级依赖，即某个字段在上下文上可能依赖另一个字段（税额基于小计）。

## Amazon Bedrock 中的 KIE

[Amazon Bedrock](https://aws.amazon.com/bedrock) 通过提供对 LLM 的访问来精简文档处理，让你无需复杂的基于规则的系统即可抽取结构化信息。

### Converse API 方法

[Amazon Bedrock Converse API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html) 提供了一个精简、统一的接口，用于与 Amazon Bedrock 中的基础模型交互，显著简化了在文档处理任务上跨不同模型做实验的过程。该 API 消除了管理各模型专有格式要求的复杂性，使文档抽取工作流能够更快迭代并比较模型。

要通过 Converse API 调用语言模型，必需参数包括用于指定使用哪个基础模型的 `model_id`，以及包含 prompt 与对话上下文的 `messages`。下面的示例演示如何组织这次 API 调用，下一节将详述正确的 `messages` 格式化技巧。

```
import boto3

bedrock_runtime = boto3.client("bedrock-runtime")


response = bedrock_runtime.converse(
                modelId=model_id, # Here the model ID can be changed to any model on Amazon Bedrock
                messages=messages,
                system=[{"text": system_prompt}],
                inferenceConfig=inference_config
            )
```

关于更多参数、响应处理与最佳实践的完整细节，请参阅 [Amazon Bedrock Converse API 文档](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html)。

### 标准化的 prompt 工程

有效的信息抽取需要一致且与模型无关的 prompt 策略，能够在不同 LLM 上都奏效。使用 [Jinja2](https://jinja.palletsprojects.com/en/stable/) 这类模板框架，可以在维护单一 prompt 结构的同时纳入基于规则的逻辑。这种方法在各类抽取场景中既提供了灵活性，又保持了一致性。

为 KIE 设计模板时，请考虑这些逻辑要素：输入的变化（文本上下文的类型与格式）、针对不同模态（图像、文本或两者组合）的指令调整，以及包含属性与别名的字段规格。下面是一个为 KIE 设计的 Jinja2 模板示例：

```
<background>
An invoice is a formal document issued by a seller to a buyer that records a 
transaction.
</background>

{% if docs %}
<document_ocr_data>
Docs: {{ docs }}
</document_ocr_data>
{% endif %}

<task>
Your task is to take the unstructured text provided and convert it into a well 
organized format using JSON. Only extract these fields, and nothing else. 

<fields>
{{ fields }}
</fields>

{% if use_images %}
Carefully examine the entire image to identify all relevant invoice fields.
{% endif %}
{% if docs %}
Carefully examine the document text to identify all relevant invoice fields.
{% endif %}
</task>
 
```

要在实践中使用这个模板，你需要在把它发送给 LLM 之前用相关数据填充它。下面的代码演示如何加载模板、插入文档相关的数据并生成最终的 prompt 文本。LangChain 的 PromptTemplate 加载你的 Jinja2 文件，随后一个键值对字典提供所需变量，例如文档中的光学字符识别（OCR）文本与字段描述。当 `format` 方法运行时，Jinja2 会处理条件语句与变量替换，为你的具体抽取任务生成贴合需要的指令：

```
from langchain_core.prompts.prompt import PromptTemplate

# Load the template
prompt_template = PromptTemplate.from_file(template_file=<path to .txt file>, template_format="jinja2")

# Prepare arguments based on available data (here is an example)
prompt_kwargs = {
    'docs': "Invoice #12345\nDate: 2023-10-15\nVendor: ABC Corp\nAmount: \$1,250.00",
    'fields': {
        'invoice_number': 'The unique identifier for the invoice',
        'date': 'The invoice issuance date',
        'vendor_name': 'Name of the company issuing the invoice',
        'total_amount': 'The total amount due on the invoice'
    },
    'use_images': True
}

# Generate the formatted prompt text
text_content = prompt_template.format(**prompt_kwargs)
```

要在单个请求中处理多种输入模态，可构造一个包含可用信息来源的 content 数组。对每张图像，创建一个带正确编码的格式化条目并加入数组。同样地，把文本 prompt 作为另一个条目加入。这种统一做法可容纳各种输入组合——纯文本、纯图像或多模态——而无需为每种情况编写单独的处理逻辑。下面的示例演示如何创建这种复合输入结构：

```
content = []

if images:
    for image in images:
        image_content = {
            "image": {
                "format": "jpeg",
                "source": {"bytes": image_to_bytes(image)}, # This function resizes the image to the model constraints if applicable
            }
        } 
        content.append(image_content)  
content.append({"text": text_content})

messages = [{"role": "user", "content": content}]
```

            image.convert("RGB").save(buffer, format="JPEG", quality=85, optimize=True)

## 度量性能

在构建智能文档处理解决方案时，建立稳健的评估框架对于满足技术要求与业务目标都至关重要。对 KIE 而言，评估必须超越基础准确率指标，以应对文档处理的多维特性。有效的评估策略应包含精确率与召回率的度量，并考虑不同字段重要性的差异：正确抽取总金额可能比抓到某个备注字段更为关键。处理延迟与单文档成本等实际考量也必须纳入你的评估矩阵。我们将使用 FATURA 数据集演示如何构建既平衡技术性能又体现业务价值的指标，这样你不仅能量化抽取准确率，还能量化你的解决方案对所在组织具体文档处理需求的满足程度。

### F1 分数

对我们的 KIE 解决方案，我们用 F1 分数评估性能，它平衡了系统的精确率（抽取取值的正确性）与召回率（找到相关字段的能力），从而对抽取准确率给出全面评估。要计算 F1 分数，我们需要把每一次抽取尝试准确归类为真阳性、假阳性或假阴性。这种归类取决于一个关键问题：抽取出的取值是否与 ground truth 匹配？在文档处理中，这一看似简单的比较会因抽取信息的多样性而变得复杂——日期的格式可能不同却表示同一天，货币金额可能带有不同的货币符号而在数值上完全相同。

这一挑战要求使用按字段定制的比较器，由它们智能地判定一次抽取何时算作匹配。以下是几种：

- **数值字段**：允许格式差异，但匹配实际数值
- **文本字段**：对空格或标点差异采用模糊匹配
- **结构化字段**：在比较前对日期、地址及其他表示形式多变的结构化数据做格式归一化

有了这些比较器，我们把每一次抽取尝试归入以下四类之一：

- **真阳性（TP）**：字段存在于 ground truth 中，且我们的系统按该字段的比较器正确抽取了它的取值
- **假阳性（FP）**：系统为某个字段抽取了取值，但该字段在 ground truth 中并不存在，或抽取出的取值不匹配期望值
- **假阴性（FN）**：字段存在于 ground truth 中，但系统未能抽取到它
- **真阴性（TN）**：字段不存在于 ground truth 中，且系统正确地没有抽取它

这些数值用于计算精确率 `(TP/(TP+FP))` 与召回率 `(TP/(TP+FN))`，并将二者合成 F1 分数：`2 × (precision × recall)/(precision + recall)`。这种方法给出了全面评估，在系统找到相关信息的能力与避免错误抽取的能力之间取得平衡。

### 延迟与成本

在实现 IDP 解决方案时，延迟与成本的考量与抽取准确率同样关键。这些运营指标直接影响用户体验，也直接影响你的文档处理 pipeline 在经济上是否可行。Amazon Bedrock 在每次模型响应中都附带关键指标，从而简化了性能监控。每次调用基础模型时，响应中都包含输入 token、输出 token 以及以毫秒计的处理延迟等元数据。借助这套内置的度量能力，团队无需搭建额外的监控基础设施即可跟踪性能。以下是响应语法模板的一个子集（更多信息见 [Converse](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html)）：

```
{
    "modelOutput": [ "string" ],
    "metrics": { 
      "latencyMs": number
   },
    "usage": { 
      "inputTokens": number,
      "outputTokens": number,
      "totalTokens": number
   }   
 }
```

Amazon Bedrock 中的延迟表示模型的响应时间——即它处理你的文档并生成抽取结果的速度。同一模型家族中较小的模型通常比更大的变体处理文档更快，不过这也会因文档复杂度而异。这一处理时间直接影响抽取出的信息多快能提供给下游业务流程使用。

Amazon Bedrock 中的成本由 token 用量决定，遵循一个简单的公式：![（输入 token 数 /1000）× 每 1000 个输入 token 的价格 +（输出 token 数 /1000）× 每 1000 个输出 token 的价格](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/28/Screenshot-2025-08-27-at-9.16.07 PM.png)

每个模型使用自己的 tokenizer，因此即便文档完全相同，不同模型的 token 计数也会不同。Amazon Bedrock 各模型的价格信息见 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)。

由于文档长度在不同业务场景中差异巨大——从单页收据到上百页的合同——在文档层面比较性能指标可能产生误导。把延迟与成本归一化到标准单位（例如每 1,000 页），可以建立一致的评估基准。这种标准化做法使不同模型、不同文档类型与不同处理策略之间能够做有意义的比较。例如，知道某个解决方案以每 1,000 页 15 美元的成本、每页平均 2.3 秒的延迟处理文档，就能对运营成本与性能影响形成可扩展的理解，而不受单份文档长度的影响。

通过在不同文档类型上系统地跟踪这些指标，组织可以基于自身具体的业务需求，做出在抽取质量、处理速度与运营成本之间取得平衡的明智决策。

## 性能分析：F1 分数、延迟与成本的权衡

我们在 FATURA 数据集上，从三个维度对智能文档处理的性能做了全面评估：抽取准确率（F1 分数）、处理速度（延迟）与运营开销（成本）。我们的分析比较了 Nova 家族中的两个模型，分别代表更轻更小的模型与更大更强的模型。我们从每个家族中选择具体模型，是因为它们具备多模态能力，使我们能够评估文本、图像以及两者组合等不同模态下的表现。

### 准确率表现

如预期那样，较大的模型取得了比较小模型更高的抽取准确率。在同时使用文本与图像输入时，Amazon Nova Pro 取得了最高的总体 F1 分数（0.9793）。在本次评估的两个模型中，纯文本处理通常带来最高的抽取准确率，文本与图像组合的表现与之相近或略低。在我们的测试中，纯图像处理始终取得最低的 F1 分数。按具体字段拆解准确率，可以更深入地了解模型表现。字段级分析常常揭示出：某些信息类型——例如日期、发票号或明细行——即便在同一个模型内，抽取成功率也可能差异显著。这种细粒度评估有助于识别哪些字段需要优化 prompt 或进一步调整模型。例如，某个模型可能擅长抽取总金额，却在供应商地址上表现吃力。这类按字段的误差分析使得能够有针对性地改进 prompt 策略与抽取技术，最终提升系统的整体表现。

### 延迟考量

符合预期的是，较小的模型 Amazon Nova Lite 处理速度更快。图像处理通常需要额外的处理时间，对较大的模型尤其如此，这反映了 Amazon Nova Pro 在视觉信息抽取上的额外复杂性。

### 成本效率

这两个模型的成本差异巨大，每 1,000 页最贵与最便宜的选项之间相差 20 倍以上：

- Nova Lite 最经济，成本远低于每 1,000 页 0.50 美元
- 加入图像处理通常会因输入 token 数增加而提高成本

### 最优配置分析

我们的评估说明了为什么组织在为文档处理选择基础模型时，应把准确率、速度与成本指标放在一起权衡。尽管这些发现提供了有价值的洞见，但它们只针对 FATURA 数据集——组织应针对自己的文档类型开展类似评估，以确定符合自身业务需求的最优模型与模态组合。
