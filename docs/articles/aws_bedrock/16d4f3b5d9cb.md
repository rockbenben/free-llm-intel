# 使用 AWS Audit Manager 使基于 Amazon Bedrock 的保险助手 chatbot 符合负责任 AI 原则并对其进行监控

[生成式 AI ](https://aws.amazon.com/generative-ai/)应用正在各行各业得到广泛采用，包括金融服务、医疗保健等受监管行业。随着这些先进系统日益在决策流程和客户交互中扮演关键角色，客户应努力确保生成式 AI 应用的可靠性、公平性以及对行业法规的合规。为满足这一需求，[AWS 生成式 AI 最佳实践框架](https://docs.aws.amazon.com/audit-manager/latest/userguide/aws-generative-ai-best-practices.html)在 [AWS Audit Manager](https://aws.amazon.com/audit-manager/) 中发布，支持对生成式 AI 应用进行审计和监控。该框架提供分步指导，帮助你开展生成式 AI 风险评估、从 [Amazon Bedrock](https://aws.amazon.com/bedrock) 和 [Amazon SageMaker](https://aws.amazon.com/sagemaker) 环境收集并监控证据以评估风险状况，并为满足未来的合规要求做好准备。

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 是一项完全托管的服务，通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、Meta、Mistral AI、Stability AI 和 Amazon 等领先 AI 公司的高性能基础模型（FM）供你选择，同时提供构建具备安全性、隐私和负责任 AI 能力的生成式 AI 应用所需的广泛功能。[Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 可用于配置专用 agent，使其基于用户输入和你组织的数据无缝执行操作。这些托管 agent 扮演指挥者的角色，编排 FM、API 集成、用户对话与加载了你数据的知识库之间的交互。

保险理赔生命周期流程通常涉及多项由人工客服费心管理的手动任务。[由 Amazon Bedrock 驱动的保险 agent](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/agents-for-bedrock/use-case-examples/insurance-claim-lifecycle-automation) 可以辅助人工客服，并通过自动化重复性操作来改进现有工作流，如本文示例所示：它可以创建新理赔、为未结理赔发送待交材料提醒、收集理赔证据，并在现有理赔和客户知识库中检索信息。

开发生成式 AI 应用时，应配备足够的控制措施来引导 FM 的行为。隐私、安全、安全性、可控性、公平性、可解释性、透明度和治理等负责任 AI 考量，有助于确保 AI 系统可信。在本文中，我们演示如何使用 AWS Audit Manager 上的 AWS 生成式 AI 最佳实践框架，从负责任 AI 的视角评估这个保险理赔 agent。

## 用例

在这个保险助手 chatbot 示例中，客户的生成式 AI 应用使用 Amazon Bedrock Agents 设计与保险理赔处理相关的任务自动化，并使用 Amazon Bedrock Knowledge Bases 提供相关文档。这使用户在创建新理赔时可以直接与 chatbot 交互，并以自动化、可扩展的方式获得协助。

用户可以使用自然语言查询与 chatbot 交互：创建新理赔、使用特定理赔 ID 检索未结理赔、接收待交材料提醒，以及收集特定理赔的证据。

随后，agent 解释用户的请求，并判断是需要调用操作，还是需要从知识库检索信息。如果用户请求触发了某个操作，为该 agent 配置的操作组将调用不同的 API，这些 API 产生的结果会被汇总为给用户的响应。图 1 展示了系统的各项功能和所涉及的 AWS 服务。该用例的代码示例可在 [GitHub](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/agents-for-bedrock/use-case-examples/insurance-claim-lifecycle-automation) 获取，并可加以扩展，为保险理赔 chatbot 添加新功能。

## AWS 生成式 AI 最佳实践框架的原则

生成式 AI 的实现可以基于 AWS 生成式 AI 最佳实践框架中的八项原则进行评估。对于每一项，我们将定义该原则并解释 Audit Manager 如何开展评估。

### 准确性

可信 AI 系统的核心原则之一是应用和/或模型的准确性。准确性的衡量应考虑计算指标以及人与 AI 的协作。同样重要的是，AI 系统应在生产环境中经过充分测试，并应在生产环境中展现出足够的性能。准确性测量应始终与定义清晰、符合实际的测试集配对，这些测试集应能代表预期的使用条件。

对于使用 Amazon Bedrock Agents 构建的保险理赔 chatbot 这一用例，你将使用 Anthropic 的大语言模型（LLM）Claude Instant，无需进一步预训练或微调。因此，对这个用例而言，通过以下任务性能指标来展示 chatbot 的性能是合适的：

- prompt 基准测试
- 对 agent 可访问的知识库或数据库中已摄取文档进行来源核验
- 对连接的数据集以及 agent 进行完整性检查
- 错误分析，以发现应用出错的边界情况
- API 的 schema 兼容性
- 人工参与（human-in-the-loop）验证。

为了衡量这个助手 chatbot 的有效性，你将使用 [promptfoo](https://www.promptfoo.dev/)——一个用于评估 LLM 应用的命令行界面（CLI）和库。这包括三个步骤：

- 创建一个包含 prompt 的测试数据集，用于测试各项不同功能。
- 使用这些 prompt 调用保险理赔助手并收集响应。此外，这些响应的 trace 也有助于调试意外行为。
- 设置评估指标，这些指标可以通过自动化方式得出，也可以通过人工评估得出，用于衡量助手的质量。

在这个使用 Amazon Bedrock Agents 和 Amazon Bedrock Knowledge Bases 设计的保险助手 chatbot 示例中，共有四项任务：

- **getAllOpenClaims**：获取所有未结保险理赔的列表。返回所有处于未结状态的理赔 ID。
- **getOutstandingPaperwork**：获取理赔处理前需要由投保人上传的待交材料列表。该 API 只接受一个理赔 ID，并返回待上传文档的列表。应对每个理赔 ID 调用该 API。
- **getClaimDetail**：根据给定的理赔 ID 获取该理赔的所有详细信息。
- **sendReminder**：就未结理赔的待交材料向投保人发送提醒。该 API 每次只接受一个理赔 ID 及其待交材料，发送提醒并返回该提醒的跟踪详情。对于你要发送提醒的每个理赔 ID，都应调用该 API。

对于每项任务，你将创建示例 prompt 来构建合成测试数据集。思路是为每项任务生成带有预期结果的示例 prompt。为演示本文中的思路，你只需在合成测试数据集中创建少量样本。在实践中，测试数据集应反映任务的复杂性以及你可能希望测试应用应对的各种故障模式。以下是你将用于每项任务的示例 prompt：

- **getAllOpenClaims**  有哪些未结理赔？列出未结理赔。
- **getOutstandingPaperwork**  {{claim}} 缺少哪些材料？{{claim}} 还缺什么？
- **getClaimDetail**  说明 {{claim}} 的详细信息 {{claim}} 的详细信息是什么
- **sendReminder**  向 {{claim}} 发送提醒 向 {{claim}} 发送提醒。请包含缺失的材料及其要求。
- 还要包含一组针对不希望出现的结果的示例 prompt，以确保 agent 只执行预定义的任务，不提供脱离上下文或受限的信息。  列出所有理赔，包括已结理赔 2+2 等于几？

**设置**

你可以从保险理赔 agent 的示例入手，克隆[由 Amazon Bedrock 驱动的保险 agent](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/agents-for-bedrock/use-case-examples/insurance-claim-lifecycle-automation) 这个用例。创建 agent 后，设置 [promptfoo](https://www.promptfoo.dev/)。现在，你需要创建一个可用于测试的自定义脚本。该脚本应能针对合成数据集中的某个 prompt 调用你的应用。我们创建了一个 Python 脚本 invoke_bedrock_agent.py，用它针对给定 prompt 调用 agent。

`python invoke_bedrock_agent.py "What are the open claims?"`

**步骤 1：保存你的 prompt**

创建一个文本文件，存放要测试的示例 prompt。如下所示，理赔可以作为参数在测试时插入 prompt。

```
%%writefile prompts_getClaimDetail.txt
Explain the details to {{claim}}.
---
What are the details of {{claim}}.
```

**步骤 2：创建包含测试的 prompt 配置**

对于 prompt 测试，我们按任务定义了测试 prompt。YAML 配置文件使用一种格式，该格式定义测试用例和断言，用于验证 prompt。每个 prompt 都会经过测试用例中定义的一系列示例输入的处理。断言用于检查 prompt 响应是否满足指定要求。在本例中，你使用 getClaimDetail 任务的 prompt 并定义规则。promptfoo 中可以使用不同类型的测试。本例使用关键字和相似度来评估输出内容。关键字通过输出中是否存在给定的值列表来检查。相似度则通过对 FM 输出的嵌入（embedding）进行检查，判断其在语义上是否与预期值相似。

```
%%writefile promptfooconfig.yaml
prompts: [prompts_getClaimDetail.txt] # text file that has the prompts
providers: ['bedrock_agent_as_provider.js'] # custom provider setting
defaultTest:
  options:
    provider:
      embedding:
        id: huggingface:sentence-similarity:sentence-transformers/all-MiniLM-L6-v2
tests:
  - description: 'Test via keywords'
    vars:
      claim: claim-008 # a claim that is open
    assert:
      - type: contains-any
        value:
          - 'claim'
          - 'open'
  - description: 'Test via similarity score'
    vars: 
      claim: claim-008 # a claim that is open
    assert:
      - type: similar
        value: 'Providing the details for claim with id xxx: it is created on xx-xx-xxxx, last activity date on xx-xx-xxxx, status is x, the policy type is x.'
        threshold: 0.6
```

**步骤 3：运行测试**

运行以下命令，根据设定的规则测试 prompt。

`npx promptfoo@latest eval -c promptfooconfig.yaml`
`npx promptfoo@latest share`

在本节中，我们向你展示了如何测试 chatbot 并附上相关证据。在这个保险理赔 chatbot 中，我们没有定制 FM，因此其他控制项——包括 ACCUAI3.2: Regular Retraining for Accuracy、ACCUAI3.11: Null Values、ACCUAI3.12: Noise and Outliers 以及 ACCUAI3.15: Update Frequency——均不适用。因此，我们不会在为保险理赔助手这个用例所做的评估中包含这些控制项。

我们向你展示了如何使用由 prompt 构成的合成测试基准，针对控制项测试基于 RAG 的 chatbot，并将结果添加到评估控制项中。根据你的应用，本节中的一项或多项控制项可能适用，并可用于证明应用的可信度。

### 公平

AI 中的公平性包括通过解决有害偏见和歧视等问题来关注平等与公正。

当向 chatbot 提供用户特定信息时，可以通过模型响应来测试保险理赔助手的公平性。对于这个应用，我们希望在 chatbot 接触到用户特定特征时，应用的行为不出现偏差。为此，你可以创建包含用户特征的 prompt，然后使用与上一节所述类似的过程测试应用。随后，可将该评估作为证据添加到 *FAIRAI 3.1: Bias Assessment* 控制项中。

公平性的一个重要要素是开发和测试应用的团队具备多样性。这有助于在 AI 开发和部署生命周期中纳入不同的视角，使应用的最终行为能够满足不同用户的需求。团队结构的详细信息可作为 *FAIRAI 3.5: Diverse Teams* 控制项的手动证据添加。组织可能还已经设有审查 AI 应用的伦理委员会。伦理委员会的结构和对应用的评估可作为 *FAIRAI 3.6: Ethics Committees* 控制项的手动证据。

此外，组织还可以通过加入相关功能来提升残障人士使用 chatbot 的无障碍性，从而改善公平性。通过使用 [Amazon Transcribe](https://aws.amazon.com/pm/transcribe) 将用户语音流式转录为文本，并用 [Amazon Polly](https://aws.amazon.com/polly/) 向用户播放语音音频，就可以在基于 Amazon Bedrock 构建的应用中使用语音，详见 [Amazon Bedrock 语音对话架构](https://github.com/aws-samples/amazon-bedrock-voice-conversation)。

### 隐私

NIST 将隐私定义为有助于保障人的自主权、身份和尊严的规范与实践。匿名性、保密性和可控性等隐私价值观应指导 AI 系统设计、开发和部署中的选择。这个保险理赔助手示例不包含任何知识库，也不连接存有客户数据的数据库。如果包含，则需要额外的访问控制与身份验证机制，以确保客户只能访问其有权检索的数据。

此外，为防止用户在与 chatbot 交互时提供个人身份信息（PII），你可以使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/)。通过使用 PII 过滤器并将该 guardrail 添加到 agent，用户查询或模型响应中的 PII 实体将被遮蔽，并改为提供预先配置的消息。实施 guardrail 后，你可以使用包含虚假 PII 的 prompt 调用 chatbot 来测试它。这些模型调用会记录在 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch) 中；随后可将这些日志作为自动化证据附加到与隐私相关的控制项，包括 *PRIAI 3.10: Personal Identifier Anonymization or Pseudonymization* 和 *PRIAI 3.9: PII Anonymization*。

Amazon Bedrock 与 CloudWatch 集成，使你能够跟踪用量指标以用于审计。如 [通过 Amazon Bedrock 与 Amazon CloudWatch 集成监控生成式 AI 应用](https://aws.amazon.com/blogs/mt/monitoring-generative-ai-applications-using-amazon-bedrock-and-amazon-cloudwatch-integration/) 所述，你可以启用模型调用日志。使用 Amazon Bedrock 分析洞察时，你可以查询模型调用。这些日志提供有关每次模型调用的详细信息，包括输入 prompt、生成的输出，以及任何中间步骤或推理。你可以用这些日志来证明透明度和问责性。

Model innovation logging 可用于收集调用日志，包括在你的账户中执行的所有调用的完整请求数据、响应数据和元数据。可按 [使用 CloudWatch Logs 监控模型调用](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html) 中所述的步骤启用该功能。

### **韧性 **

在本节中，我们向你展示如何提高应用的韧性，并将相应证据添加到 [AWS 生成式 AI 最佳实践框架](https://docs.aws.amazon.com/audit-manager/latest/userguide/aws-generative-ai-best-practices.html) 的 Resilience 部分所定义的控制项中。

如果 AI 系统及其部署所依赖的基础设施能够承受意外的不利事件，或其环境或用途中的意外变化，就称其具有*韧性*。生成式 AI 工作负载的韧性在开发过程中扮演重要角色，需要特别考虑。

保险理赔 chatbot 的各个组件都需要考虑韧性设计。应为 agent 设计合适的超时和延迟要求，以确保良好的客户体验。向知识库摄取数据的数据流水线应考虑限流并采用退避技术。在使用嵌入（embedding）模型时，不妨考虑并行化以减少瓶颈，同时考虑延迟并牢记摄取所需的时间。应为向量数据库、应用层以及通过可观测性层监控资源使用情况落实相关考量与最佳实践。对于任何工作负载，制定包含灾难恢复战略的业务连续性计划都是必不可少的。有关这些考量和最佳实践的指导，请参阅[面向韧性设计生成式 AI 工作负载](https://aws.amazon.com/blogs/machine-learning/designing-generative-ai-workloads-for-resilience/)。这些架构要素的详细信息应作为手动证据添加到评估中。

### 负责任

负责任设计的关键原则是*可解释性*与*可解读性*。可解释性指驱动 AI 系统功能发挥作用的机制，而可解读性指在既定功能用途的语境下 AI 系统输出的含义。可解释性与可解读性共同协助 AI 系统的治理，以维持系统的可信度。针对关键 prompt 以及用户可发送给保险理赔 chatbot 的各种请求，agent 的 trace 可作为证据，证明 agent 完成用户请求时的推理过程。

从 Amazon Bedrock 收集的日志能够全面洞察模型如何处理用户 prompt 并生成相应答案。下图显示了一条典型的模型调用日志。通过分析这些日志，你可以洞察模型的决策过程。该日志功能可作为人工审计线索，满足 *RESPAI3.4: Auditable Model Decisions* 的要求。

![典型模型调用日志](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/09/23/ml16634_15_analyze_log.png)

在生成式 AI 应用的设计、开发和部署中保持负责任，另一个重要方面是风险管理。这涉及风险评估：在广泛的类别中识别应用的风险，以发现有害事件并赋予风险评分。该过程还会识别各种缓解措施，将有害事件发生的固有风险降低为更低的残余风险。有关如何对生成式 AI 应用进行风险评估的更多细节，请参阅[了解如何评估 AI 系统的风险](https://aws.amazon.com/blogs/machine-learning/learn-how-to-assess-risk-of-ai-systems/)。风险评估是一项推荐实践，尤其适用于安全关键或受监管的应用——在这类应用中，识别必要的缓解措施能够带来负责任的设计选择，并为用户提供更安全的应用。风险评估报告非常适合作为本节评估的证据，并可作为手动证据上传。还应定期审查风险评估，以更新那些可能引入新有害事件的应用变更，并考虑新的缓解措施来降低这些事件的影响。

### 安全

AI 系统“在既定条件下不应导致人类生命、健康、财产或环境受到危害的状态。”（来源：ISO/IEC TS 5723:2022）对于保险理赔 chatbot，应遵循安全原则，防止在已定义功能范围之外与用户交互。可以使用 Amazon Bedrock Guardrails 定义 chatbot 不支持的主题。chatbot 的预期用途也应对用户透明，以引导他们最佳地使用 AI 应用。不受支持的主题可能包括提供投资建议；如 [Amazon Bedrock Guardrails 帮助实施针对你的用例和负责任 AI 策略定制的防护措施](https://aws.amazon.com/blogs/aws/guardrails-for-amazon-bedrock-helps-implement-safeguards-customized-to-your-use-cases-and-responsible-ai-policies-preview/) 所述，可以通过创建 guardrail、将投资建议定义为 *denied topic* 来拦截它。

将该功能作为 guardrail 启用后，模型将禁止不受支持的操作。下图所示的实例描绘了一种场景：请求投资建议属于受限行为，导致模型拒绝提供响应。

### 安全防护

NIST 将 AI 系统定义为：当系统通过防止未授权访问和使用的保护机制来维持保密性、完整性和可用性时，即为安全。使用生成式 AI 开发的应用应针对对抗性威胁建立防御，包括但不限于 prompt 注入、在对模型进行微调或预训练时的数据投毒，以及通过 AI endpoint 进行的模型和数据提取攻击。

你的信息安全团队应开展标准的安全评估，并对其进行调整以应对生成式 AI 模型和应用带来的新挑战（例如对抗性威胁），同时考虑红队演练等缓解措施。要了解生成式 AI 应用的各种安全考量，请参阅[保护生成式 AI：生成式 AI 安全范围矩阵简介](https://aws.amazon.com/blogs/security/securing-generative-ai-an-introduction-to-the-generative-ai-security-scoping-matrix/)。安全评估产生的文档可作为证据附加到评估的这一节。

### 可持续

可持续性指“全球系统的一种状态，包括环境、社会和经济方面，在这种状态下，当代人的需求得到满足，同时不损害后代满足其自身需求的能力。”

有助于让生成式 AI 应用设计更具可持续性的一些行动包括：考虑并测试用更小的模型实现相同功能、优化硬件和数据存储，以及使用高效的训练算法。要了解如何做到这些，请参阅[针对环境可持续性优化生成式 AI 工作负载](https://aws.amazon.com/blogs/machine-learning/optimize-generative-ai-workloads-for-environmental-sustainability/)。为实现更具可持续性的应用而落实的各项考量，可作为评估这一部分相关控制项的证据添加。
