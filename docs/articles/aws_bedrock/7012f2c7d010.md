# 借助 Amazon Bedrock 上的 CreditAI 变革财务分析：Octus 与 AWS 同行之旅

投资专业人士面临着越来越大的挑战：要处理海量数据，才能及时做出有依据的决策。传统做法是人工翻阅无数研究文档、行业报告和财务报表，这不仅耗时，还可能导致错失机会和分析不完整。这一挑战在信用市场尤为突出，因为信息的复杂性以及对快速、准确洞见的需求会直接影响投资结果。金融机构需要一种解决方案，它不仅能聚合并处理海量数据，还能以对话式、易用的形式交付可付诸行动的智能。AI 与财务分析的交叉，为变革投资专业人士获取和使用信用智能的方式提供了极具吸引力的机会，从而带来更高效的决策流程和更好的风险管理结果。

Octus（前身为 Reorg）成立于 2013 年，是全球领先的买方机构、投资银行、律师事务所和咨询公司不可或缺的信用智能与数据提供商。Octus 以经过验证的技术、数据和 AI 工具赋能无与伦比的人类专业能力，揭示出推动金融市场果断行动的有力真相。访问 [octus.com](http://octus.com/) 了解我们如何快速交付经过严格核验的智能，并为贯穿整个信用周期的专业人士构建完整图景。在 [LinkedIn](https://www.linkedin.com/company/octus-credit1) 和 [X](https://x.com/OctusCredit) 上关注 Octus。

借助先进的 GenAI，[CreditAI](https://octus.com/products/credit-ai/)[ by Octus™](https://octus.com/products/credit-ai/) 是一款旗舰级对话式聊天机器人，支持自然语言查询和带来源归因的实时数据访问，显著缩短分析时间并简化研究工作流。它让用户即时获取来自数十万篇专有情报文章的、覆盖超过 10,000 家公司的洞见，帮助金融机构在有效管理风险的同时做出有依据的信用决策。关键特性包括聊天历史管理、可以提出针对特定公司的定向问题或更宽泛地针对某个行业的问题，以及获取后续问题的建议。

本文演示 Octus 如何将其旗舰产品 CreditAI 迁移到 [Amazon Bedrock](https://aws.amazon.com/bedrock/)，从而改变投资专业人士获取和分析信用智能的方式。我们完整梳理 Octus 的这段旅程：从管理多个云提供商和昂贵的 GPU 实例，到采用 Amazon Bedrock、[AWS Fargate](https://aws.amazon.com/fargate) 和 [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 等 AWS 服务实现精简且具成本效益的解决方案。我们详细分享其中的架构决策、实施策略、安全最佳实践以及关键经验，正是这些让 Octus 在显著提升应用性能与可扩展性的同时保持了零停机。

## 创新机会

[CreditAI](https://octus.com/products/credit-ai/)[ by Octus™](https://octus.com/products/credit-ai/) 1.x 版本使用[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）。它由多种内部与外部云服务组合构建：在 Microsoft Azure 上运行大语言模型（LLM），用 Pinecone 作为向量化数据库，用 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2)（Amazon EC2）做 embedding。基于我们的运维经验，随着开始扩大规模，我们意识到存在若干运维效率问题以及改进机会：

- 我们自建的 embedding 服务（部署在 EC2 实例上）在可扩展性和可靠性上达不到需要。它们还需要团队投入比可支配更多的时间来做运维维护。
- 整体解决方案的运营成本很高，尤其是因为使用了按需 GPU 实例。我们应用的实时特性意味着 Spot Instances 不是一个选项。此外，我们对成本更低的基于 CPU 的实例所做的调研显示，它们无法满足我们的延迟要求。
- 使用多个外部云提供商让 DevOps、技术支持和预算编制变得复杂。

这些运维效率问题意味着我们必须重新审视解决方案架构。显而易见，我们需要一个能满足生成式 AI 需求且具成本效益的解决方案。于是 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 登场了。它支持可简化 RAG 操作的知识库，在与 OpenSearch Service 的集成中提供向量化搜索，具备多租户 embedding，并且提供 [Anthropic 的 Claude](https://www.anthropic.com/claude) 系列 LLM——这些都让它成为 Octus 迁移解决方案架构的有力选择。在此过程中，它还简化了运维，因为 Octus 总体而言是一家以 AWS 为主的公司。不过，我们仍然好奇该如何推进这次迁移，以及迁移过程中是否会出现停机。

## 战略需求

为了有条不紊地推进，Octus 确定了以下关键需求来指导向 Amazon Bedrock 的迁移：

- **可扩展性** – 一项关键需求是把运营规模从处理数十万份文档扩展到数百万份文档。此前系统的一大挑战是把新文档 embedding 到向量数据库的过程缓慢（而且相对不可靠），这成为扩展运营的瓶颈。
- **成本效益与基础设施优化** – CreditAI 1.x 虽然性能不错，但由于 embedding 和 reranking 使用基于 GPU 的单租户服务，基础设施成本很高。我们需要便宜得多、同时又能提供弹性和规模的多租户替代方案。
- **响应性能与延迟** – 基于生成式 AI 的应用能否成功，取决于响应的质量和速度。考虑到我们的用户群体，响应必须准确，同时也要珍惜用户的时间（低延迟）。当数据规模和复杂度增长时，这是一项挑战。我们希望平衡空间检索与时间检索，以便给出在答案与上下文相关性上都最优的响应，尤其是在每天都有大量数据更新的情况下。
- **零停机** – CreditAI 已投入生产，我们在这次迁移中无法承受任何停机。
- **技术敏捷性与创新** – 在快速演进的 AI 格局中，Octus 认识到保持技术竞争力的重要性。我们希望摆脱 embeddings 服务、reranker、guardrails 和 RAG evaluator 等自研开发与功能维护工作。这能让 Octus 专注于产品创新并更快地部署新功能。
- **运维整合与可靠性** – Octus 的目标是整合云提供商，并降低支持开销和运维复杂性。

## 迁移到 Amazon Bedrock 并满足我们的需求

迁移到 Amazon Bedrock 以如下方式满足了前述需求：

- **可扩展性** – Amazon Bedrock 的架构，结合 [AWS Fargate for Amazon ECS](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html)、[Amazon Textract](https://aws.amazon.com/textract/) 和 [AWS Lambda](https://aws.amazon.com/lambda/)，提供了此次扩展所需的弹性且可扩展的基础设施，同时维持了性能、数据完整性、合规与安全标准。该解决方案高效的文档处理与 embedding 能力解决了此前系统的局限，使知识库更新更快、更高效。
- **成本效益与基础设施优化** – 通过迁移到 Amazon Bedrock 的多租户 embedding，Octus 在借助 Anthropic 的 Claude Sonnet 和改进后的 embedding 能力维持性能标准的同时实现了显著的成本下降。此举免除了对基于 GPU 实例的服务的需求，转而采用更具成本效益的无服务器 Amazon ECS 与 Fargate 解决方案。
- **响应性能与延迟** – Octus 验证了 Anthropic 的 Claude Sonnet 所产出响应的质量与延迟，确认在此次迁移中响应的准确性和延迟都得以保持（甚至有所超出）。借助这一 LLM，CreditAI 现在能够比以往更好地回答更宽泛的、行业层面的问题。
- **零停机** – 借助我们内部的集中式基础设施框架，我们为应用实现了向 Amazon Bedrock 的零停机迁移。我们的框架包括通过 Terraform 实现的基础设施即代码（IaC）、持续集成与交付（CI/CD）、SOC2 安全，以及针对基础设施和应用的监控、可观测性与告警。
- **技术敏捷性与创新** – Amazon Bedrock 成为一个理想的合作伙伴，提供专为 AI 应用开发设计的解决方案。Amazon Bedrock 的内置特性（如 embeddings 服务、reranking、guardrails 以及即将推出的 RAG evaluator）免除了自行开发这些组件的需要，让 Octus 能够专注于产品创新并更快地部署功能。
- **运维整合与可靠性** – AWS 全面的服务套件提供了一个精简的框架，在简化运维的同时提供高可用性和可靠性。这种整合把管理多个云提供商的复杂性降到最低，并营造出更具凝聚力的技术生态。考虑到 Octus 已有超过 75 名工程师使用 AWS 服务进行应用开发，此番整合也在开发速度上带来了规模经济。

此外，Amazon Bedrock Knowledge Bases 团队与我们紧密合作，处理了若干关键事项，包括扩展 embedding 上限、管理元数据长度限制（250 个字符）、测试不同的分块方法，以及调整向知识库同步的吞吐量。

在接下来的几节中，我们介绍我们的解决方案，以及我们如何处理迁移到 Amazon Bedrock 和 Fargate 的各项细节。

## 解决方案概览

下图展示了我们在 AWS 上运行 CreditAI 的系统架构，其中有两条关键路径：文档摄取与内容提取工作流，以及用于实时响应用户查询的问答工作流。

[![解决方案架构](https://d2908q01vomqb2.cloudfront.net/887309d048beef83ad3eabf2a79a64a389ab1c9f/2025/02/26/Architecture.png)](https://d2908q01vomqb2.cloudfront.net/887309d048beef83ad3eabf2a79a64a389ab1c9f/2025/02/26/Architecture.png)

在接下来的几节中，我们深入介绍解决方案各关键组件中的重要细节。为便于理解，每一种情况下我们都会把它们与前面讨论过的需求对应起来。

文档摄取工作流（在上述架构图中以蓝色编号标示）分五个不同阶段处理内容：

- 上传到 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）的文档会通过 S3 Event Notifications 自动调用 Lambda 函数。这种事件驱动架构让新文档得到即时处理。
- Lambda 函数处理包含文档位置的事件 payload，执行格式校验，并为内容提取做准备。这包括在路由到 Amazon Textract 之前进行文件类型核验、大小校验和元数据提取。
- Amazon Textract 处理文档，同时提取文本和结构信息。该服务可处理 PDF、图像和表单等多种格式，并保留文档版式以及内容元素之间的关系。
- 提取出的内容存储在专用的 S3 前缀下，与源文档分开存放，从而保持清晰的数据血缘。每份已处理的文档都保留对源文件、提取时间戳和处理元数据的引用。
- 提取出的内容流入 Amazon Bedrock Knowledge Bases，在这里我们实施语义分块策略，把内容切分为最优的片段。系统随后为每个分块生成 embedding，并将这些向量存储在 OpenSearch Service 中以便高效检索。在整个过程中，系统维护全面的元数据，以支撑下游的过滤和来源归因需求。

问答工作流（在上述架构图中以黄色编号标示）分六个相互衔接的阶段处理用户交互：

- 托管在 AWS Fargate 上的 Web 应用处理用户交互和查询输入，在把查询路由到相应处理服务之前完成初始请求校验。
- [Amazon Managed Streaming for Kafka](https://aws.amazon.com/msk/)（Amazon MSK）作为流式服务，在查询处理中提供可靠的服务间通信，同时维持消息顺序和高吞吐处理。
- 运行在 AWS Fargate 上的问答处理器通过协调各服务之间的工作并让响应经过 LLM 管道处理，来编排完整的查询响应周期。
- 该管道通过以下组件与 Amazon Bedrock 基础模型集成：Cohere Embeddings 模型对输入执行向量变换。Amazon OpenSearch Service 管理向量 embedding 并执行相似性搜索。Amazon Bedrock Knowledge Bases 提供对文档库的高效访问。
- [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 作为查询处理管道的一部分，实施内容过滤与安全检查。
- Anthropic Claude LLM 执行自然语言处理，生成响应后再返回给 Web 应用。

这一集成工作流在提供高效查询处理的同时维持了响应质量和系统可靠性。

## 可扩展性：使用 OpenSearch Service 作为向量数据库

[Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/) 成为满足 CreditAI 不断演进需求的最优方案，在提供高级能力的同时保持在 AWS 生态内的无缝集成：

- **向量搜索能力** – OpenSearch Serverless 提供我们所需的稳健内置向量搜索能力。该服务支持混合搜索，让我们无需修改 embedding 模型，就能把向量 embedding 与原始文本搜索结合起来。这一能力对于在 CreditAI 2.x 中支持更宽泛的问题至关重要，提升了其整体可用性和灵活性。
- **无服务器架构的优势** – 无服务器设计免除了预置、配置或调优基础设施的需要，显著降低了运维复杂性。这一转变让我们团队能把更多时间和资源投入到功能开发与应用改进上，而不是管理底层基础设施。
- **AWS 集成优势** – 与其他 AWS 服务（尤其是 Amazon S3 和 Amazon Bedrock）的紧密集成简化了我们的内容摄取流程。这种内置的兼容性为未来的增强提供了连贯且可扩展的格局，同时维持最佳性能。

OpenSearch Serverless 使我们能够高效扩展向量搜索能力，同时把运维开销降到最低并维持高性能标准。

## 可扩展性与安全：把数据拆分到多个向量数据库，并自建对复杂权限的支持

为了提升可扩展性和安全性，我们为每个客户的数据实施了彼此隔离的知识库（对应向量数据库）。这种方法虽然会略微增加成本，但带来多项显著好处。首先，它保持客户数据的完全隔离，提供更强的隐私与安全性。得益于 Amazon Bedrock Knowledge Bases，这一解决方案不会牺牲性能。Amazon Bedrock Knowledge Bases 支持跨多个知识库并发执行 embedding 和同步，使我们能够无延迟地维持实时更新——这在过去基于 GPU 的架构下是无法实现的。

此外，我们在 Octus 内部引入了两个自建服务来强化这一系统：

- **AuthZ 访问管理服务** – 该服务实施细粒度的访问控制，确保用户和应用只能与其被授权访问的数据交互。我们必须把 AuthZ 后端从 Airbyte 迁移到原生 SQL 复制，以便在大规模下近乎实时地支持访问管理。
- **全局标识符服务** – 该服务提供一个统一框架，用于跨多个域关联标识符，实现跨多个数据集的标识符无缝集成与交叉引用。

这些增强共同构建了一个稳健、安全且高效的环境，用于管理和访问客户数据。

## 成本效益：采用多租户 embedding 服务

在迁移到 Amazon Bedrock Knowledge Bases 的过程中，Octus 做了一个战略转变：从在 EC2 实例上使用开源 embedding 服务，转为通过 Cohere 的多语言模型使用 Amazon Bedrock 的托管 embedding 能力。这一转变是在基于若干关键因素审慎评估后做出的。

我们选择 Cohere 的多语言模型有两个主要优势驱动。第一，它在我们的对比测试中展现出更优的检索性能。第二，它提供稳健的多语言支持能力，这对我们的全球业务至关重要。

此次迁移的技术收益体现在两个不同方面：文档 embedding 与消息 embedding。在文档 embedding 方面，我们从基于 CPU 的系统迁移到 Amazon Bedrock Knowledge Bases，其多租户架构带来了更快、更高吞吐的文档处理。在消息 embedding 方面，我们摆脱了对专用 GPU 实例的依赖，同时以 20–30 毫秒的 embedding 时间维持了最佳性能。Amazon Bedrock Knowledge Bases API 还把 embedding 与检索功能合并到单次 API 调用中，从而简化了我们的运维。

迁移到 Amazon Bedrock Knowledge Bases 的托管 embedding 带来两项显著优势：它消除了维护自有开源方案的运维开销，同时通过 Cohere 的模型提供对业界领先 embedding 能力的访问。这帮助我们在不做妥协的情况下同时实现了成本效益与性能目标。

## 成本效益与响应性能：分块策略的选择

我们的首要目标是改善 CreditAI 响应的三个关键方面：质量（信息的准确性）、有据可依（能够把响应追溯到源文档）以及相关性（提供直接回答用户查询的信息）。为此，我们测试了三种把文档拆分为更小片段（chunk）的不同方法：

- **固定分块** – 把文本切分为固定长度的片段
- **语义分块** – 依据段落、章节或完整思想等自然语义边界来切分文本
- **分层分块** – 创建两级结构：较小的子分块用于精确匹配，较大的父分块用于上下文理解

我们的测试显示，在检索相关信息方面，语义分块和分层分块都明显优于固定分块。不过，每种方法都有各自的技术考量。

分层分块需要更大的分块尺寸，以便在检索时维持完整的上下文。这种方法创建两级结构：较小的子分块用于精确匹配，较大的父分块用于上下文理解。检索时，系统先识别相关的子分块，然后自动包含其父分块以提供更宽泛的上下文。尽管这种方法同时优化了搜索精度和上下文保持，但我们无法用更偏好的 Cohere embedding 来实施它，因为后者只支持最多 512 个 token 的分块，这对维持有效层级关系所需的父分块来说不够大。

语义分块使用 LLM，通过分析语义相似度和自然语言结构来智能地切分文本。系统不是任意切分，而是通过计算句子与段落之间基于 embedding 的相似度分数来识别逻辑断点，确保语义相关的内容保持在一起。由此得到的分块兼顾语言特征（如句子和段落边界）与语义连贯性，从而维持上下文完整性；不过这种精度是以额外的计算资源为代价的，用于 LLM 分析和 embedding 计算。

在评估各选项之后，我们选择了语义分块，尽管它有两个取舍：

- 它需要我们的 LLM 做额外处理，从而增加成本
- 它每个文档处理批次有 1,000,000 个 token 的上限

我们做出这一选择，是因为语义分块在实施简便性与检索性能之间提供了最佳平衡。虽然分层分块展现出潜力，但实施起来更复杂，也更难扩展。这一决定帮助我们在维持高质量、有据可依且相关的响应的同时，让系统保持易管理且高效。

## 响应性能与技术敏捷性：将 Amazon Bedrock Guardrails 与 Amazon Bedrock Knowledge Bases 结合使用

我们实施 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 时聚焦三个关键目标：提升响应安全性、优化性能，以及简化 guardrail 管理。该服务在确保我们的响应既安全又高效方面发挥着关键作用。

Amazon Bedrock Guardrails 提供内容过滤与响应审核的综合框架。该系统的工作方式是在 LLM 处理内容之前，按预定义规则评估内容，帮助阻止不当内容并维持响应质量。通过 Amazon Bedrock Guardrails 与 Amazon Bedrock Knowledge Bases 的集成，我们无需编写复杂代码就能配置、测试并迭代我们的 guardrails。

我们在三个方面取得了显著的技术改进：

- **简化的审核框架** – 我们不再管理多个彼此独立的禁止主题，而是把内容过滤整合到一个统一的 guardrail 服务中。这种方法让我们能够为内容审核规则维持单一事实来源，并支持可自定义的示例短语，以帮助微调过滤准确性。
- **性能优化** – 我们把 guardrail 检查直接集成到主 prompt 中，而不是作为独立操作运行，从而提升了系统性能。这一优化减少了 token 用量并把不必要的 API 调用降到最少，使每次查询的延迟更低。
- **增强的内容控制** – 该服务为过滤潜在有害内容提供可配置阈值，并内置检测幻觉和评估响应相关性的能力。这减轻了我们对 TruLens 等外部服务的依赖，同时维持稳健的内容质量控制。

这些改进帮助我们在维持高响应质量的同时降低了运维复杂性和处理开销。与 Amazon Bedrock 的集成让我们有了更精简、更高效的内容审核方式。

## 实现零停机：基础设施迁移

我们向 Amazon Bedrock 的迁移需要周密规划，既要为 CreditAI 提供不间断的服务，又要显著降低基础设施成本。我们通过覆盖部署、安全和监控需求的全面基础设施框架实现了这一点：

- **IaC 实施** – 我们使用可复用的 Terraform 模块，在各环境间一致地管理基础设施。这些模块让我们能在服务与项目之间高效共享配置。我们的方法支持以最少的配置改动进行多 Region 部署，同时把基础设施版本控制与应用代码放在一起维护。
- **自动化部署策略** – 我们嵌入 GitOps 的框架通过为不同环境实施清晰的分支策略来简化部署流程。这套自动化通过 CI/CD 管道处理 CreditAI 各组件的部署，借助自动化校验与测试减少人为错误。系统在需要时还支持快速回滚。
- **安全与合规** – 为维持 SOC2 合规性和稳健的安全性，我们的框架纳入了全面的访问管理控制以及静态与传输中数据的加密。我们遵循网络安全最佳实践，定期开展安全审计与监控，并在部署管道中运行自动化合规检查。

在整个迁移过程中我们保持了零停机，同时通过消除 GPU 实例把基础设施成本降低了 70%。从 Amazon EC2 上的 Amazon ECS 成功迁移到使用 Fargate 的 Amazon ECS，简化了我们的基础设施管理与监控。

## 达致卓越

CreditAI 向 Amazon Bedrock 的迁移为 Octus 带来了显著成果：

- **可扩展性** – 我们在几天而非几周内，就把三个环境中可用于问答的文档数量几乎翻了一倍。基于 Fargate 的 Amazon ECS 配合自动扩缩规则与控制，让我们在用量高峰时段获得服务的弹性可扩展性。
- **成本效益与基础设施优化** – 通过从基于 GPU 的集群转向 Fargate，我们的月度基础设施成本现在降低了 78.47%，每个问题的成本下降了 87.6%。
- **响应性能与延迟** – 延迟没有出现下降，同时成功回答的问题数量增加了 27%。我们还看到用户参与度提升了 250%。用户尤其喜欢我们由 Anthropic 的 Claude Sonnet 支持的、针对宽泛行业问题的解答能力。
- **零停机** – 我们在迁移期间实现了零停机，整个应用的整体可用性达到 99%。
- **技术敏捷性与创新** – 我们新增文档数据源所需的时间只有迁移前的四分之一。此外，我们免费获得了增强的 guardrails 支持，不再需要从知识库中检索文档并把分块传给 Anthropic 的 Claude Sonnet 来触发 guardrail。
- **运维整合与可靠性** – 迁移之后，我们 DevOps 与 SRE 团队的维护负担和开销减少了 20%。由于我们只用一家云提供商，支持 SOC2 合规也变得简单直接。
