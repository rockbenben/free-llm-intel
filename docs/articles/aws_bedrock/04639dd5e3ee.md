# 以聊天机器人助手为例解密 Amazon Bedrock 定价

“在 Amazon Bedrock 上运行我们的聊天机器人要花多少钱？”这是我们听到客户在探索 AI 解决方案时最常问的问题之一。这也难怪——计算 AI 应用的成本就像穿行于由 token、embedding 和各种定价模式构成的复杂迷宫。无论你是解决方案架构师、技术负责人还是业务决策者，理解这些成本对项目规划和预算都至关重要。在本文中，我们将通过一个实用的真实案例来审视 Amazon Bedrock 定价：构建一个客服聊天机器人。我们会拆解核心成本构成，走一遍中型呼叫中心实施方案的容量规划，并对不同基础模型给出详细的定价计算。读完本文，你将拥有一个清晰的框架，用于估算自己的 Amazon Bedrock 实施成本，并理解影响它们的关键因素。

对于不熟悉的人，[Amazon Bedrock](https://aws.amazon.com/bedrock/?gclid=Cj0KCQjwkdO0BhDxARIsANkNcrfsk7wZwVk72KFs24tdNtnl2w_YUEz2-_CPOoOwGcqW_kXsbWqevfcaArKMEALw_wcB&trk=36201f68-a9b0-45cc-849b-8ab260660e1c&sc_channel=ps&ef_id=Cj0KCQjwkdO0BhDxARIsANkNcrfsk7wZwVk72KFs24tdNtnl2w_YUEz2-_CPOoOwGcqW_kXsbWqevfcaArKMEALw_wcB:G:s&s_kwcid=AL!4422!3!692006004850!e!!g!!amazon%20bedrock!21048268689!159639953975) 是一项完全托管的服务，通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、Meta、Stability AI 和 Amazon 等领先人工智能（artificial intelligence，AI）公司的多种高性能基础模型（foundation model，FM），并附带广泛的构建能力，可用于以安全、隐私和负责任的 AI 方式构建生成式 AI 应用。

Amazon Bedrock 提供了一套全面的工具包来支撑 AI 应用，包括预训练的大语言模型（large language model，LLM）、检索增强生成（Retrieval Augmented Generation，RAG）能力，以及与现有 Knowledge Base 的无缝集成。这一强大的组合使构建聊天机器人成为可能，它们能够高准确度、贴合上下文地理解并响应客户查询。

## 解决方案概览

在本例中，我们的 Amazon Bedrock 聊天机器人将使用一组经过整理的数据源，并通过检索增强生成（Retrieval-Augmented Generation，RAG）实时检索相关信息。借助 RAG，聊天机器人的输出会因为来自数据源的上下文信息而更加丰富，从而为用户带来更好的客户体验。要理解 Amazon Bedrock 定价，关键是要熟悉几个会显著影响预期成本的核心术语。这些组件不仅构成了聊天机器人运行的基础，也直接影响你的定价计算。让我们来看看这些关键组件。

### 关键组件

- 数据源（Data Sources） – 构成聊天机器人 Knowledge Base 的文档、手册、FAQ 及其他信息载体。
- 检索增强生成（Retrieval-Augmented Generation，RAG） – 指在生成响应之前，引用训练数据源之外的权威 Knowledge Base，以优化大语言模型输出的过程。RAG 将 LLM 已有的强大能力扩展到特定领域或组织的内部 Knowledge Base，而无需重新训练模型。这是一种经济高效的方法，可改进 LLM 输出，使其在各种情境下保持相关性、准确性和实用性。
- Token – 模型可以作为单一意义单元解释或预测的字符序列。例如，对于文本模型，token 不仅可以对应一个词，还可以对应具有语法意义的部分词（如 “-ed”）、标点符号（如 “?”）或常见短语（如 “a lot”）。Amazon Bedrock 的定价基于处理的输入和输出 token 数量。
- Context Window（上下文窗口） – LLM 在单次请求中能处理的最大文本量（以 token 衡量）。这包括输入文本以及生成响应所需的额外上下文。更大的上下文窗口让模型在生成响应时能考虑更多信息，从而产生更全面、更贴合上下文的输出。
- Embedding – 捕获语义含义的文本稠密向量表示。在 RAG 系统中，Knowledge Base 文档和用户查询都会生成 embedding，从而支持语义相似度搜索，从 Knowledge Base 中检索最相关的信息来增强 LLM 的响应。
- Vector Store（向量存储）：Vector Store 包含你数据源的 embedding，充当你的 Knowledge Base。
- Embeddings Model（Embedding 模型）：Embedding 模型是机器学习模型，将数据（文本、图像、代码等）转换为固定大小的数字向量。这些向量以可用于相似度搜索、聚类、分类、推荐系统和检索增强生成（retrieval-augmented generation，RAG）的格式捕获输入的语义含义。
- 大语言模型（Large Language Model，LLM） – 在海量数据上训练的模型，使用数十亿参数生成原创输出，用于回答问题、语言翻译和补全句子等任务。Amazon Bedrock 提供多种多样的基础模型（foundation model，FM）供选择，每种都有不同的能力和专长。

## 估算定价

实施 AI 解决方案最具挑战性的方面之一，是准确预测容量需求。如果容量估算不当，你可能过度配置（导致不必要的成本）或配置不足（导致性能问题）。让我们通过一个真实场景来看看如何处理这一关键的规划步骤。在深入数字之前，先来了解影响容量和成本的关键因素：

- Embedding：文本的向量表示，支持语义搜索能力。Knowledge Base 中的每个文档都需要转换为 embedding，这会影响处理成本和存储需求。
- User Queries（用户查询）：来自用户的传入问题或请求。理解预期的查询量和复杂度至关重要，因为每次查询都会消耗 token 并需要处理能力。
- LLM Responses（LLM 响应）：针对用户查询由 AI 生成的答案。这些响应的长度和复杂度直接影响 token 用量和处理成本。
- Concurrency（并发）：系统需要处理的并发用户数。更高的并发要求可能需要额外的基础设施，并会影响你对定价模式的选择。

为了让这一切更具体，我们来看一个典型的呼叫中心实施方案。假设你正计划为一家中型组织部署客服聊天机器人，处理产品咨询和支持请求。下面是我们的容量规划分解方式：首先，考虑你的 Knowledge Base。在我们的场景中，我们有 10,000 份支持文档，平均每份长度为 500 个 token。这些文档需要被切成更小的片段以便有效检索，通常每份文档拆成 5 个 chunk。这样我们的 Knowledge Base 总共有 500 万个 token。在 embedding 过程中，考虑到分块和重叠内容，这 10,000 份文档将产生大约 50,000 个 embedding。这一点很重要，因为 embedding 会同时影响初始配置成本和持续的存储需求。

现在，我们来看看运营需求。基于典型的呼叫中心业务量，我们按以下规划：

- 每月 10,000 次客户查询
- 查询长度从 50 到 200 个 token 不等（取决于复杂度）
- 每次交互的平均响应长度为 100 个 token
- 峰值用量为 100 个并发用户

汇总这些数字后，我们的月度容量需求如下：

- 500 万个 token，用于处理 Knowledge Base
- 50,000 个 embedding，用于语义搜索
- 500,000 个 token，用于处理用户查询
- 100 万个 token，用于生成响应

理解这些数字至关重要，因为它们会在几个方面直接影响你的成本：

- 处理和 embedding Knowledge Base 的初始配置成本
- 维护向量数据库和文档存储的持续存储成本
- 处理用户交互的月度处理成本
- 支持并发需求的基础设施成本

这为成本计算奠定了坚实基础，我们将在下一节详细探讨。

## 计算总体拥有成本（total cost of ownership，TCO）

Amazon Bedrock 提供灵活的[定价模式](https://aws.amazon.com/bedrock/pricing/)。使用 Amazon Bedrock 时，你需要为模型推理和定制付费。推理有两种定价方案可供选择：1. 按需和 Batch：此模式让你可以按量付费使用 FM，无需做出基于时长的期限承诺。2. Provisioned Throughput：此模式允许你预置足够的吞吐量以满足应用的性能要求，作为交换，你需要做出基于时长的期限承诺。

- 按需 – 适合不频繁或不可预测的使用
- Batch – 专为在一次操作中处理大量数据而设计
- Provisioned Throughput – 适合具有稳定且可预测工作负载的应用

要将此场景的 TCO 作为一次性成本来计算，我们会考虑基础模型、Knowledge Base 中的数据量、预估的查询和响应次数，以及上面提到的并发级别。在本场景中，我们将使用按需定价模式，并展示 Amazon Bedrock 上部分基础模型的定价情况。

## 按需定价公式如下：

该配置的成本将是 LLM 推理成本与向量存储成本之和。要估算推理成本，你可以从 LLM 返回的响应元数据中获取输入 token 数、上下文大小和输出 token 数。产生的总成本 = ((Input Tokens + Context Size) * Price per 1000 Input Tokens + Output tokens * Price per 1000 Output Tokens) + Embeddings。对于输入 token，我们将为 User Queries 额外增加约 150 个 token 的上下文大小。因此，按照我们 10,000 次 User Queries 的假设，总 Context Size 将为 1,500,000 个 token。

以下是基于我们的示例用例、使用按需定价公式，对 Amazon Bedrock 上各模型估算月度成本的比较：

**Embedding 成本：**

对于 Amazon Bedrock 上的文本 embedding，我们可以选择 Amazon Titan Embeddings V2 模型或 Cohere Embeddings Model。在本例中，我们计算 embedding 的一次性成本。

- Amazon Titan Text Embeddings V2:  每 1,000 个输入 token 的价格 – $0.00002 Embedding 成本 – (Data Sources + User Queries) * 每 1000 token 的 Embedding 成本  (5,000,000 +500,000) * 0.00002/1000 = $0.11
- Cohere Embeddings:  每 1,000 个输入 token 的价格 – $0.0001 Embedding 成本 – (5,000,000+500,000) * 0.0001/1000 =$0.55

向量存储的常见成本包含两个组成部分：向量数据大小 + 向存储发起的请求数。你可以选择让 Amazon Bedrock 控制台为你自动在 Amazon OpenSearch Serverless 中设置向量存储，也可以使用自己在受支持服务中创建并配置了相应字段的向量存储。如果你在配置中使用 OpenSearch Serverless，就需要考虑其成本。定价详情请参阅：[OpenSearch Service Pricing ](https://aws.amazon.com/opensearch-service/pricing/?nc1=h_ls#Amazon_OpenSearch_Serverless)。

- Claude 4 Sonnet: ((500,000 +1,500,000) tokens/1000 * $0.003 + 1,000,000 tokens/1000* $0.015 = $21+0.11= $21.11

- Amazon Nova Pro: ((500,000 +1,500,000) tokens/1000 * $0.0008 + 1,000,000 tokens/1000* $0.0032= $4.8+0.11= $4.91

## 结语

理解和估算 Amazon Bedrock 成本不必让人不知所措。正如我们通过客服聊天机器人示例所展示的，将定价拆解为核心组成部分——token 用量、embedding 和模型选择——就能让它变得可控且可预测。

规划 Bedrock 实施成本的关键要点：

- 首先清晰评估 Knowledge Base 的规模和预期查询量
- 同时考虑一次性成本（初始 embedding）和持续运营成本
- 根据性能和定价比较不同的基础模型
- 在按需、Batch 或 Provisioned Throughput 定价之间做选择时，将并发需求考虑在内

按照这种系统化的成本估算方法，你可以自信地规划 Amazon Bedrock 实施，并为特定用例选择最具成本效益的配置。请记住，最便宜的选项并不总是最好的——在做最终决定时，要考虑成本、性能与你的特定需求之间的平衡。
