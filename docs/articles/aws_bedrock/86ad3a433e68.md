# 从 SageMaker Studio 直接管理 Amazon SageMaker HyperPod Spaces

我们最近推出了新功能：可以直接从 Amazon SageMaker Studio UI 在 Amazon SageMaker HyperPod EKS 集群上创建和管理 Amazon SageMaker Spaces。数据科学家和机器学习 (ML) 工程师现在可以在 HyperPod 集群上启动 JupyterLab 和 Code Editor 环境，无需离开浏览器或使用命令行工具，把从获取集群访问到进入高效开发的时间缩短到几次点击。

## 背景

[Amazon SageMaker HyperPod](https://aws.amazon.com/sagemaker/ai/hyperpod/?trk=48c755df-3170-4fc9-bb40-e7f04d88494d&sc_channel=ps) 为 foundation model (FM) 的大规模训练与推理提供专用基础设施。借助 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/) 编排，团队可以在数百个加速器上运行分布式训练作业，并享有内置的容错能力和自动故障恢复。除了训练，HyperPod 还把这套 EKS 编排的基础设施延伸到推理侧，为数百亿参数的 foundation model 提供低延迟、可扩展的推理服务。

今年早些时候，我们推出了 [面向 HyperPod 的 Amazon SageMaker Spaces](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-cluster-ide.html)，这是一个 ML 开发者可以用来在 HyperPod EKS 集群上直接创建交互式开发环境的 add-on。组织随后可以在同一基础设施上，让交互式负载与训练作业和模型部署并行运行，从而最大化 GPU 投资，并支持 fractional GPU 分配。

此前，创建和管理 Spaces 主要依赖 [HyperPod CLI](https://github.com/aws/sagemaker-hyperpod-cli) 或 `kubectl` 命令。虽然这种方式为基础设施管理员提供了强大而细粒度的控制，但偏好可视化界面的数据科学家现在可以使用这一新的 SageMaker Studio 能力，绕过命令行工具，全心投入模型开发。

## 新增内容

借助这一新能力，数据科学家现在可以直接在 SageMaker Studio 中创建、配置、启动、停止和打开 Spaces。HyperPod 集群详情页上新增的 IDE and Notebooks 标签页提供了完整的 Space 管理用户界面，日常的 Space 操作不再需要 CLI 工具。

通过 Studio 可用的关键能力包括：

- 通过向导式表单创建 Spaces，可配置计算、命名空间、存储、用于计算配额管理的 [HyperPod Task Governance](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-operate-console-ui-governance.html) 以及镜像设置。
- 在可搜索的表格中查看所有 Spaces，展示名称、应用类型、状态、访问类型、存储、GPU 和 vCPU 分配。
- 单次选择即可启动和停止 Spaces，在 Spaces 不使用时释放计算资源。
- 直接在浏览器中打开 Spaces（JupyterLab 或 Code Editor），或通过你选择的远程 IDE（例如 VS Code）连接。

图 1：HyperPod 集群详情页上的 IDE and Notebooks 标签页，展示所有 Spaces 及其状态、计算分配，以及停止、打开或在远程 IDE 中打开的快捷操作

## 开始使用

设置涉及两个角色：*管理员*负责准备集群，*数据科学家*负责创建并打开 Spaces。以下各小节分别说明。

### 面向管理员

管理员从其 SageMaker HyperPod EKS 集群的 IDE and Notebooks 标签页，使用 **Quick install**（一键安装、优化默认配置）或 **Custom install** 选项（配置 web UI 访问时必需），在其 HyperPod EKS 集群上[安装 SageMaker Spaces add-on](https://docs.aws.amazon.com/sagemaker/latest/dg/operator-install.html)。安装完成后，管理员可以配置命名空间、创建 Space 模板，并通过 EKS access entries 管理访问权限。

以下是管理员必须完成的一次性设置：

- **安装 Spaces add-on：** 从 Amazon SageMaker AI 控制台打开你的 HyperPod 集群，进入 **IDE and Notebooks** 标签页，选择 **Quick install** 或 **Custom install**（启用 web 浏览器访问必须使用 Custom install）。完整说明见 [AWS 文档](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-cluster-ide.html)。
- **配置 EKS access entries：** 将三个托管策略 `AmazonSagemakerHyperpodSpacePolicy`、`AmazonSagemakerHyperpodUserClusterPolicy` 和 `AmazonSagemakerHyperpodSpaceTemplatePolicy` 附加到你的数据科学家使用的 AWS Identity and Access Management (IAM) 角色上。
- **在 Studio domain 上启用按用户身份传播：** 如果你的 Studio domain 创建于 SageMaker Studio 与 HyperPod Spaces 集成推出之前，你必须启用向 HyperPod EKS 集群的按用户身份传播。这样可以确保每个 Studio 用户在集群上的操作（创建、停止或删除 Space）在 EKS access entries 和 AWS CloudTrail 中都归因到其用户 profile。此外，这一身份映射会强制实施严格的 Space 归属：它记录哪个用户创建了该环境，并决定该 Space 是私有的还是在整个 SageMaker Studio domain 内共享。

> 对每个 Studio domain 运行一次以下命令：

```
aws sagemaker update-domain \
    --domain-id $DOMAIN_ID \
    --default-user-settings '{
  "StudioWebPortalSettings": {
    "ExecutionRoleSessionNameMode": "USER_IDENTITY"
  }
}'
```

更新 domain 之后，验证以下命令返回 “USER_IDENTITY”：

```
aws sagemaker describe-domain --domain-id $DOMAIN_ID \
    --query 'DefaultUserSettings.StudioWebPortalSettings.ExecutionRoleSessionNameMode'
```

*现有正在运行的应用不受影响。用户会在下次登录时采用新设置。*

- **可选：开启额外能力：** 从下方的 Optional capabilities（可选能力）表中启用任意能力。

### 面向数据科学家

add-on 安装完成且访问配置就绪后，数据科学家在 SageMaker Studio 中通过 Compute **→** HyperPod 导航到其 HyperPod 集群，选择 IDE and Notebooks 标签页，即可看到 Spaces 管理界面（见图 1）。关于创建和管理 Spaces 的更多说明：[在 HyperPod 上创建和管理 Spaces](https://docs.aws.amazon.com/sagemaker/latest/dg/create-manage-spaces.html)。

当 Space 状态显示为 **Running**（在未预热的集群上通常需要几分钟，启用 over-provisioning 后约 30–40 秒）后，选择 **Open** 即可在浏览器中启动 JupyterLab 或 Code Editor（图 2 和图 3），或选择 **Open in VS Code**，通过 SSH-over-SSM 从本地编辑器连接（图 4）。

图 2：通过 web 浏览器访问的 JupyterLab Space，展示带有可用 notebook kernels、控制台和终端访问的 Launcher

#### 在 JupyterLab Space 中工作

打开 JupyterLab Space 后，你会获得一个完全配置好的开发环境，可以使用：

- 配备 ipykernel 的 Python 3 notebooks。
- Glue PySpark 和 Glue Spark 控制台。
- SparkMagic 的 PySpark 和 Spark kernels。
- 用于运行命令的终端访问。
- 带持久化存储的文件浏览器。
- 内置聊天与上下文帮助。

你的工作会持久保存在挂载的 Amazon Elastic Block Store (Amazon EBS) 卷上，因此可以停止并重启 Spaces 而不会丢失进度。

图 3：运行在 HyperPod 上的 Code Editor Space，展示带有文件资源管理器、编辑器和集成终端的 VS Code 风格 web 界面

#### 在 Code Editor Space 中工作

对于偏好浏览器中 VS Code 风格体验的开发者，Code Editor Spaces 提供了一个轻量的 web IDE，具备：

- 支持语法高亮和 IntelliSense 的完整文件编辑。
- 集成终端，可运行 shell 命令、提交训练作业或与集群资源交互。
- 对语言服务器、linter 和 formatter 的扩展支持。
- 用于版本控制工作流的 Git 集成。
- 直接访问集群文件系统和挂载的 Amazon FSx 卷。

Code Editor Spaces 非常适合编写和调试训练脚本、管理实验配置以及处理代码仓库——全程无需离开浏览器。

图 4：远程连接到 HyperPod Space 的本地 VS Code 实例，展示远程连接指示器以及运行在集群算力上的完整 IDE 能力

#### 远程 IDE 连接（VS Code）

在 Spaces 表格中选择 Open in VS Code，即可把你本地的 Visual Studio Code 连接到运行在 HyperPod 上的 Space。其内部使用 SSH-over-SSM 隧道，提供安全连接，无需你管理 SSH 密钥或暴露 22 端口。

你可以在 HyperPod 集群算力上执行代码，同时拥有本地 VS Code 环境的全部能力，包括扩展、主题和快捷键绑定。

你也可以使用 AWS Toolkit for Visual Studio Code 进行连接，它会在 SageMaker AI > HyperPod 下列出你的 Spaces，你可以直接从该工具面板启动、停止和连接 Spaces。

### 可选能力

以下每一项能力都是可选且可组合的。选择开启适合团队需求的任意组合即可。

| **能力** | **说明** |
| --- | --- |
| Web 浏览器访问 | 通过 AWS Application Load Balancer 和基于 Amazon Route 53 的自定义 DNS，把浏览器流量路由到 Spaces。远程 IDE（经 SSM 的 VS Code）访问不需要此项。 |
| Space 模板 | 由管理员定义的模板，预先配置计算、镜像、存储和生命周期脚本，保证各团队的 Space 配置一致。 |
| Task Governance | 面向多租户集群，通过 Kueue 提供命名空间级计算配额、队列和基于优先级的准入。 |
| Karpenter autoscaling | 根据 Space 需求动态扩缩节点。 |
| Karpenter over-provisioning | 预先预热节点并预拉取镜像，把 Space 启动时间从 5–7 分钟降到约 30–40 秒。见下文的 Pro tip 小节。 |
| 持久卷（EFS / FSx） | 跨 Spaces 持久保留的共享用户目录和团队数据集。 |
| 自定义镜像（ECR） | 团队专属的运行时和库，封装进托管在 Amazon Elastic Container Registry (Amazon ECR) 的容器镜像中。 |
| 闲置自动关机 | 自动终止不活跃的 Spaces，防止计算成本失控。 |
| NVIDIA MIG | 在 A100/H100 硬件上进行 fractional GPU 分配，实现低成本的交互式负载。 |

### Pro tip：用节点 over-provisioning 缩短 Space 启动时间

默认情况下，在使用 Karpenter autoscaling 的 HyperPod EKS 集群上，SageMaker Spaces 在 scale-to-zero 集群上首次创建 Space 时会带来 **5–7 分钟的冷启动延迟**，主要耗时在：

- Amazon Elastic Compute cloud (Amazon EC2) 实例启动。
- Kubernetes 节点注册。
- SageMaker Distribution (SMD) 镜像拉取。

对于延迟敏感的交互式负载（JupyterLab、Code Editor），你可以使用标准的 Kubernetes over-provisioning 模式维持一池**预热、镜像已缓存的节点**。这可把 Space 启动时间从几分钟降到约 **30–40 秒**。

#### 工作原理

- 一个低优先级（`-1000`）的占位 Deployment 在每个预热节点上保留一个 Kubernetes pod。这些 pod 申请的 CPU/内存与真实 Space 相同。
- 每个占位 pod 上的 `initContainer` 会在 Karpenter 供给节点时，把 SageMaker Distribution 镜像预拉取到该节点上。
- 当用户创建 Space（默认优先级 `0`）时，Kubernetes 调度器会抢占占位 pod（优先级 `-1000`）。随后 Space 在几秒内落到已经预热且镜像已缓存的节点上，无需拉取镜像，也无需等待节点启动。
- Karpenter 在后台为被抢占的占位 pod 供给替换节点。

了解更多 Pro tip 部署信息：[面向 HyperPod Spaces 的 Overprovisioning](https://awslabs.github.io/ai-on-sagemaker-hyperpod/docs/category/node-overprovisioning-for-spaces)。

**已验证的启动延迟**，基于 `ml.m5.12xlarge`（24 vCPU 可分配、2 vCPU 占位、8 GiB 占位内存），使用约 3.5 GB 的 `sagemaker-distribution:latest-cpu` SMD 镜像：

| **路径** | **延迟** |
| --- | --- |
| Space 与占位 pod 共存（coexist） | ~14 s |
| Space 抢占占位 pod | ~35 s |
| 冷启动（无预热池） | 5-7 min |

**注意：** 以上数字仅为 CPU 场景。GPU Spaces 需要各自申请 `nvidia.com/gpu` 并预拉取 GPU 镜像的占位 Deployment。否则 GPU 节点会保持冷态，而 GPU 镜像约 10 GB，拉取成本远高于 3.5 GB 的 CPU 镜像。

**注意：** 每个预热节点都会持有一台处于 Running 状态的 EC2 实例。对于按需实例，这意味着保持预热节点持续运行的额外成本。

关于安装 HyperPod Spaces add-on 和入门的更多信息，请参见 [AWS 文档](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-cluster-ide.html)。

## 定价

配置 SageMaker Spaces add-on 本身不会产生额外费用。你只需为 Spaces 消耗的底层 HyperPod 集群算力付费，以及为用于 SSH-over-SSM 远程连接的 AWS Systems Manager Advanced On-Premises Instance 按小时付费。详情见 [AWS Systems Manager 定价](https://aws.amazon.com/systems-manager/pricing/)。

如果你使用上文所述的 over-provisioning，请注意预热节点会带来额外成本。视实例类型和规格而定，这些节点会保持运行状态，等待为 Spaces 供给资源。

## 结论

用 SageMaker Studio 管理 HyperPod Spaces，弥合了数据科学家与高性能计算基础设施之间的鸿沟。团队现在可以在几分钟内从获取集群访问走到运行中的 JupyterLab 或 Code Editor 环境，无需学习 CLI 工具或 Kubernetes 概念。结合 HyperPod Task Governance、fractional GPU 支持和闲置自动关机等特性，组织可以在保持成本控制和资源公平的同时，为共享集群提供自助式访问。

要开始使用，请在 SageMaker AI 控制台导航到你的 HyperPod EKS 集群并选择 IDE and Notebooks 标签页。更多信息请参见 SageMaker HyperPod Spaces 文档。
