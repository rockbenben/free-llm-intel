# Twitch 如何在 Amazon Bedrock 上使用带 RAG 的 agentic 工作流为广告销售提速

[Twitch](https://www.twitch.tv/) 是全球领先的直播平台，月均访客超过 1.05 亿。作为 Amazon 的一部分，Twitch 的广告业务由 Amazon 的广告销售组织负责。面向不同市场的新广告产品涉及由公告、培训和文档构成的复杂网络，使销售团队难以快速找到精确信息。2024 年初，Amazon 发起了一项重大行动，要在全球范围内为广告主发挥 Twitch 的力量。这就要求向 Amazon 所有广告销售团队普及 Twitch 知识。对内部销售支持团队而言，这项任务尤为艰巨。在每位专家平均对接 30 多名销售人员的情况下，在公开渠道提出的问题平均需要 2 小时才能获得首次回复，且有 20% 的问题完全得不到回答。总而言之，从广告主提出需求到首次投放活动上线，整个流程最长可能拖到 7 天。

在本文中，我们演示了如何创新性地构建一个带 agentic 工作流的[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）应用，并在 [Amazon Bedrock](https://aws.amazon.com/bedrock) 上建立知识库。我们将该 RAG pipeline 实现在一个基于 Slack 聊天的助手中，帮助 Amazon Twitch 广告销售团队快速把握新的销售机会。我们讨论构建多模态知识库、驱动 agentic 工作流、利用元数据应对幻觉等方案组件，也分享在使用多个[大型语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）和 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 开发该方案过程中的经验教训。

## 解决方案概览

RAG 应用将 LLM 与专用知识库结合，帮助回答特定领域的问题。我们开发的带 RAG 的 agentic 工作流方案围绕一个集中式知识库展开，该知识库汇集了 Twitch 内部营销文档。这些内容随后被转换为针对高效信息检索优化的向量数据库。在 RAG pipeline 中，检索器访问该向量数据库以呈现相关信息，LLM 则针对用户通过 Slack 助手提交的 Twitch 查询生成定制响应。解决方案架构如下图所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/12/12/ML-16730_architecture_diagram.jpg)

驱动该解决方案的关键架构组件包括：

- **数据源** – 一个集中式存储库，包含通过网页爬虫和定期刷新，从 wiki、幻灯片等各种来源汇集的营销数据
- **向量数据库** – 营销内容首先使用 Amazon Bedrock 上的 [Amazon Titan Multimodal Embeddings G1](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-multiemb-models.html) 嵌入为向量表示，该模型能够处理文本和图像数据。这些嵌入随后存储在一个 Amazon Bedrock knowledge bases 中。
- **Agentic 工作流** – agent 充当智能调度器。它会评估每个用户查询以确定合适的处理方式：拒绝回答偏题查询、调用 LLM，还是调用 API 和向量数据库等数据源。agent 使用思维链（CoT）推理，将复杂任务拆解为一系列更小的步骤，然后为每个子任务动态生成 prompt，合并结果，并综合出最终连贯的响应。
- **Slack 集成** – 我们实现了一个消息处理器，使用 [AWS Lambda](https://aws.amazon.com/lambda/) 函数通过 Slack 助手与用户交互，提供无缝的对话体验。

## 经验教训与最佳实践

在 Amazon Bedrock 上设计、实现并迭代带 agentic 工作流和知识库的 RAG 应用的过程，带来了若干宝贵的经验。

### 在知识库中处理多模态源文档

我们早期面临的一个问题是，Twitch 文档分散在 Amazon 内部网络上。不仅没有集中式数据存储，数据格式也不一致。内部 wiki 中混杂着图片和文字，面向销售人员的培训材料常常是 PowerPoint 演示文稿。为了让我们的聊天助手发挥最大效用，我们需要把所有这些信息整合到一个 LLM 能够理解的单一存储库中。

第一步是编写一个 wiki 爬虫，将所有相关的 Twitch wiki 和 PowerPoint 幻灯片上传到 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/)。我们以此为源，在 Amazon Bedrock 上创建知识库。为了处理数据源中图片与文本的组合，我们使用了 [Amazon Titan Multimodal Embeddings G1](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-multiemb-models.html) 模型。对于包含人口统计背景等特定信息的文档，我们对多张幻灯片做了摘要，以确保这些信息被包含在面向 LLM 的最终上下文中。

我们的知识库总共包含 200 多份文档。Amazon Bedrock knowledge bases 易于修订，我们会根据 wiki 或幻灯片的变化例行添加和删除文档。我们的知识库每天都会被不时查询，而指标、仪表板和告警通过 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 在 [Amazon Web Services（AWS）](https://aws.amazon.com/) 中天然得到支持。这些工具提供了对系统健康状况的完全透明，并支持完全无人值守的运行。

### 面向各类用户查询的 agentic 工作流

在观察用户与我们的聊天助手互动的过程中，我们注意到有些问题是标准 RAG 应用无法回答的。其中一些问题过于复杂，把多个问题合在了一起；有些要求深入洞察 Twitch 受众的人口统计；还有一些与 Twitch 完全无关。

由于标准 RAG 方案只能回答简单问题，无法优雅地处理所有这些场景，我们投入建设了带 RAG 的 agentic 工作流方案。在该方案中，agent 把回答问题的过程拆解为多个步骤，并使用不同的工具回答不同类型的问题。我们在 [LangChain](https://www.langchain.com/) 中实现了一个 XML agent，选择 XML 是因为 Amazon Bedrock 中可用的 Anthropic Claude 模型在 XML 数据上经过大量训练。此外，我们精心设计了 prompt，指示 agent 采用具备广告与 Twitch 业务领域专长的专门角色。agent 会拆解查询、收集相关信息、分析上下文，并权衡潜在方案。我们的聊天 agent 的流程如下图所示。在下图中，当 agent 读取用户问题时，第一步是判断该问题是否与 Twitch 相关——如果不相关，agent 会礼貌地拒绝回答。如果问题与 Twitch 相关，agent 会“思考”哪个工具最适合回答该问题。例如，如果问题与受众预测相关，agent 会调用 Amazon 内部的 Audience Forecasting API。如果问题与 Twitch 广告产品相关，agent 会调用其广告知识库。一旦 agent 从合适的工具获取结果，它会考虑这些结果，并思考现在是否有足够信息回答问题。如果不够，agent 会再次调用其工具集（最多 3 次尝试）以获取更多上下文。一旦完成信息收集，agent 会生成最终响应并发送给用户。

agentic AI 的主要好处之一是能够与多个数据源集成。在我们的场景中，我们使用内部预测 API 获取与可用 Amazon 和 Twitch 受众供给相关的数据。我们还使用 Amazon Bedrock Knowledge Bases 帮助回答关于静态数据的问题，例如 Twitch 广告产品的特性。这极大扩展了聊天机器人可回答问题的范围，而最初的 RAG 无法支持这些。agent 足够智能，能够根据查询知道该使用哪个工具。你只需就工具用途提供高层指令，它就会调用 LLM 做出决策。例如，

```
tools = [
  Tool(
    name="twitch_ad_product_tool",
    func=self.product_search,
    description="Use when you need to find information about Twitch ad products.",
   ),
  Tool(
    name="twitch_audience_forecasting_tool",
    func=self.forecasting_api_search,
    description="Use when you need to find forecasting information about the Amazon and Twitch audiences.",
   )
]
```

更好的是，LangChain 会在 CloudWatch 中记录 agent 的思考过程。当 agent 决定使用哪个工具时，日志语句如下所示：

```
Thought: I need to use the twitch_ad_product_tool to find information about Twitch Premium Video. 

3 documents returned from the retrievers: [Overview: Twitch Premium Video ....]

Thought: The documents provide relevant information about the ad product Twitch Premium Video. I have enough context to provide a final answer. 

<final_answer> Twitch Premium Video is a premier Twitch ad product in which .... </final answer>
```

agent 帮助我们的 RAG 保持灵活。展望未来，我们计划接入更多 API、构建新的向量存储，并与其他 Amazon 组织的聊天助手集成。这对于帮助我们扩展产品、最大化其覆盖范围与影响力至关重要。

### 面向 LLM 调用的上下文压缩

在文档检索过程中，我们发现内部 wiki 的体量差异很大。这意味着一个 wiki 常常包含数百甚至数千行文本，但只有一小段与回答问题相关。为了减小上下文规模和输入到 LLM 的 token 数，我们使用另一个 LLM 执行上下文压缩，以提取返回文档中的相关部分。最初我们使用 Anthropic Claude Haiku，因为它的速度更优。然而我们发现，Anthropic Claude Sonnet 提升了结果准确性，而速度只比 Haiku 慢 20%（从 8 秒变为 10 秒）。因此，我们为自身用例选择了 Sonnet，因为为用户提供最高质量的答案是最重要的因素。相比传统人工流程 2 天的周转时间，我们愿意多承担 2 秒延迟。

### 借助文档元数据应对幻觉

与任何 RAG 方案一样，我们的聊天助手偶尔会幻觉出错误答案。虽然这是 LLM 公认的问题，但在我们的系统中尤为明显，因为 Twitch 广告领域十分复杂。由于用户依赖聊天机器人的回复与客户互动，即便大多数回答是正确的，他们也不愿信任其中哪怕正确的答案。

我们通过向用户展示 LLM 针对每一条陈述的信息来源来提升信任。这样，如果用户对某条陈述存疑，可以查看 LLM 使用的参考文献，并亲自阅读权威文档。我们实现这一点的方式是将检索到的文档的源 URL 作为元数据加入知识库，Amazon Bedrock 直接支持这一做法。随后我们指示 LLM 读取元数据，并在响应中把源 URL 作为可点击链接附加在后。

以下是一个带引用的问答示例：

```
What are the supported ad lengths for the Twitch Premium Video ad product?

Twitch offers the following ad lengths for Premium Video ads:

- Pre-roll (before stream): Up to 30 seconds, full-screen, non-skippable [1]
- Mid-roll (during stream):
- Up to 30 seconds when purchased through Amazon Demand-Side-Platform (DSP) [1]
- Up to 60 seconds when purchased directly [2]

Sources:
[1] US - Twitch + OLV Core Narrative (slide 8) - https://ads.amazon.com/cms/contents/9f24a95e
[2] Twitch Premium Video - https://w.amazon.com/TwitchAds/Products/PremiumVideo
```

请注意，LLM 回复了两个来源。第一个来自一份销售培训 PowerPoint 幻灯片，第二个来自一份内部 wiki。对于幻灯片，LLM 能够提供它获取信息的确切幻灯片编号。这尤其有用，因为有些演示文稿包含 100 多张幻灯片。

添加引用后，我们的用户反馈评分显著提升。正面反馈率提升了 40%，助手整体使用量提升了 20%，这表明由于能够核实答案，用户对助手回复的信任有所增强。

### 人在回路中的反馈收集

当我们在 Slack 中上线聊天助手时，我们设置了一个用户可填写的反馈表单。其中包含若干问题，以 1–5 分评价聊天助手的各个方面。尽管数据非常丰富，但几乎没人使用。在改为简单得多的点赞/点踩按钮、用户可以不费力地选择之后（按钮附加在每个聊天机器人回答之后），我们的反馈率提升了八倍。

## 结论

在 AI 领域快速行动很重要，尤其是因为技术变化如此之快。工程师常常对 AI 中的某项新技术有了想法，就想快速验证。使用 AWS 服务帮助我们快速了解哪些技术有效、哪些无效。我们使用 Amazon Bedrock 测试了多个基础模型（FM），包括 Anthropic Claude Haiku 和 Sonnet、Meta Llama 3、Cohere embedding 模型，以及 Amazon Titan Multimodal Embeddings。Amazon Bedrock Knowledge Bases 帮助我们高效实现带 agentic 工作流的 RAG，而无需为各种多模态数据源和数据流构建定制集成。使用动态分块和元数据过滤让我们能够更准确地检索所需内容。所有这些让我们在几天内而非数月内就搭建出一个可用的原型。在将改动部署给客户之后，我们继续在应用中采用 Amazon Bedrock 和其他 AWS 服务。

自 2024 年 2 月 Twitch Sales Bot 上线以来，我们已回答了超过 11,000 个有关 Twitch 销售流程的问题。此外，年初至今，使用我们生成式 AI 方案的 Amazon 销售人员相比未使用的销售人员带来的 Twitch 收入高出 25%，相比自助服务账户高出 120%。我们将继续扩展聊天助手的 agentic 能力——使用 Amazon Bedrock 以及其他 AWS 服务——为用户解决新问题并提升 Twitch 的利润。我们计划把针对 Prime Video、Alexa 和 IMDb 等 Amazon 1P Publishers 组合的独立 Knowledge Bases 纳入进来，作为一种快速、准确且全面的生成式 AI 方案，为广告销售提速。

就你自己的项目而言，可以沿用我们的架构，采用类似方案构建 AI 助手，以应对你自己的业务挑战。
