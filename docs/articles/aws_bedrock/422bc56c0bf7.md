# 使用 AWS DLC、Amazon EKS 和 Amazon Bedrock 微调并部署 Meta Llama 3.2 Vision，实现由生成式 AI 驱动的 Web 自动化

对大语言模型（LLM）进行微调，已经成为组织把强大的基础模型（FM）适配到自身特定需求的一项关键技术。组织不必从零开始训练模型——那个过程可能耗资数百万美元、需要大量计算资源——而是可以用领域特定数据，以很低的成本定制现有模型。随着医疗、金融、技术等行业的组织希望把 AI 用于专门任务、同时保持成本效率，这种做法变得尤其有价值。然而，落地一套生产级微调方案会带来若干重大挑战。组织必须应对复杂的基础设施搭建要求、落实稳健的安全措施、优化性能，并建立可靠的模型托管方案。

本文给出了一套完整方案，用于微调并部署 [Llama-3.2-11B-Vision-Instruct](https://huggingface.co/meta-llama/Llama-3.2-11B-Vision-Instruct) 模型以完成 Web 自动化任务。我们演示如何在 [Amazon Elastic Kubernetes Service（Amazon EKS）](https://aws.amazon.com/eks/) 上使用 [AWS Deep Learning Containers（DLC）](https://aws.amazon.com/ai/machine-learning/containers/) 搭建安全、可扩展且高效的基础设施。使用 AWS DLC，你可以获得经过充分测试的环境，这些环境自带增强的安全特性和预装软件包，能显著简化微调流程的优化工作。这种做法不仅加快开发速度，也能在生产环境中提供稳健的安全性与性能。

## 方案概览

本节介绍我们的架构中用于微调 Meta Llama 模型并将其用于 Web 任务自动化的关键组件。我们讨论各组件的优势、它们之间如何交互，以及如何借助它们构建生产级微调 pipeline。

### 用于训练和托管 AI/ML 负载的 AWS DLC

方案的核心是 AWS DLC，它为机器学习（ML）负载提供经过优化的环境。这些容器预配置了必要的依赖，包括 NVIDIA 驱动、CUDA 工具包和 [Elastic Fabric Adapter](https://aws.amazon.com/hpc/efa/)（EFA）支持，以及预装的 [PyTorch](https://pytorch.org/) 等框架，用于模型训练与托管。AWS DLC 解决了把各种软件组件打包、使其与训练脚本协调工作的复杂难题，让你开箱即可用上经过优化的硬件能力。此外，AWS DLC 采用独特的补丁算法与流程，持续监控、识别并处理安全漏洞，确保容器保持安全且始终更新。其预先验证过的配置显著缩短搭建时间，并减少 ML 基础设施搭建中常见的兼容性问题。

### 借助 AWS DLC、Amazon EKS 与 Amazon EC2 实现无缝的基础设施管理

我们在 Amazon EKS 上部署这些 DLC，为模型微调构建稳健且可扩展的基础设施。组织可以用这一组合，以前所未有的灵活性搭建和管理训练基础设施。Amazon EKS 负责复杂的容器编排，你可以在所需的 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2)（Amazon EC2）实例上启动运行于 DLC 内的训练任务，从而得到一个可随训练需求伸缩、同时保持稳定性能的生产级环境。

### 以 AWS DLC 与 EFA 支持实现高性能网络

AWS DLC 预配置了对 EFA 的支持，可在 EC2 节点之间实现高吞吐、低延迟的通信。EFA 是一种可挂载到 EC2 实例上的网络设备，用于加速 AI、ML 和高性能计算应用。DLC 预装了经过测试且与底层 EC2 实例兼容的 EFA 软件，因此你无需自己费劲搭建底层组件。本文使用安装脚本创建 EKS 集群和 EC2 实例，它们开箱即支持 EFA。

### 以 AWS DLC 配合 FSDP 提升内存效率

我们的方案使用 PyTorch 内置的 Fully Sharded Data Parallel（FSDP）训练支持，这是一种能大幅降低训练期内存需求的前沿技术。与每个 GPU 都必须持有一份完整模型副本的传统分布式训练方式不同，FSDP 把模型参数、优化器状态和梯度分片到各个 worker 上。AWS DLC 中对 FSDP 的优化实现，使得在有限的 GPU 资源下训练更大的模型成为可能，同时保持训练效率。

更多信息，请参阅 [Scale LLMs with PyTorch 2.0 FSDP on Amazon EKS – Part 2](https://aws.amazon.com/blogs/machine-learning/scale-llms-with-pytorch-2-0-fsdp-on-amazon-eks-part-2/)。

### 在 Amazon Bedrock 上部署模型

模型部署方面，我们使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/)，这是一个面向 FM 的全托管服务。虽然也可以用 AWS DLC 托管模型，但本文选择 Amazon Bedrock，以展示服务使用上的多样性。

### Web 自动化集成

最后，我们实现 SeeAct agent——一个精密的 Web 自动化工具——并演示它与我们在 Amazon Bedrock 上托管的模型的集成。这一组合构建出强大的系统，能够理解视觉输入并自主执行复杂的 Web 任务，展示了我们微调模型的实际应用场景。下文演示如何：

- 为 AI 负载搭建 EKS 集群。
- 使用 AWS DLC，通过 PyTorch FSDP 微调 Meta Llama 3.2 Vision。
- 在 Amazon Bedrock 上部署微调后的模型。
- 结合 SeeAct 使用该模型完成 Web 任务自动化。

## 搭建 EKS 集群

本节逐步介绍创建 EKS 集群，以及安装所需插件、operator 和其他依赖的步骤。

### 创建 EKS 集群

创建 EKS 集群最简单的方式是使用集群配置 YAML 文件。你可以把下面的示例配置文件作为基础，按需定制。请提供前置步骤中创建的 EC2 密钥对。更多配置选项，请参阅 [使用配置文件](https://eksctl.io/usage/creating-and-managing-clusters/"%20\l%20"using-config-files)。

```
---
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: MyCluster
  region: us-west-2

managedNodeGroups: 
  - name: p5
    instanceType: p5.48xlarge
    minSize: 0
    maxSize: 2
    desiredCapacity: 2
    availabilityZones: ["us-west-2a"]
    volumeSize: 1024
    ssh:
      publicKeyName: <your-ec2-key-pair>
    efaEnabled: true
    privateNetworking: true
    ## In case you have an On Demand Capacity Reservation (ODCR) and want to use it, uncomment the lines below.
    # capacityReservation:
    #   capacityReservationTarget:
    #     capacityReservationResourceGroupARN: arn:aws:resource-groups:us-west-2:897880167187:group/eks_blog_post_capacity_reservation_resource_group_p5
```

运行以下命令创建 EKS 集群：

`eksctl create cluster --config-file cluster.yaml`以下是一个输出示例：

```
YYYY-MM-DD HH:mm:SS [ℹ] eksctl version x.yyy.z
YYYY-MM-DD HH:mm:SS [ℹ] using region <region_name>
...
YYYY-MM-DD HH:mm:SS [✔] EKS cluster "<cluster_name>" in "<region_name>" region is ready
```

集群创建可能需要 15–30 分钟。创建完成后，你本地的 `~/.kube/config` 文件会更新为指向该集群的连接信息。

运行以下命令行，验证集群可访问：

`kubectl get nodes`

## 在 Amazon EKS 上使用 DLC 微调 Meta Llama 3.2 Vision

本节概述在 Amazon EKS 上使用 PyTorch FSDP 微调 Meta Llama 3.2 Vision 模型的流程。我们以 DLC 作为基础镜像来运行训练任务。

### 配置微调所需的设置

按以下步骤配置微调环境：

- 创建一个 Hugging Face 账户，并获取 [Hugging Face 安全 token](https://huggingface.co/docs/hub/en/security-tokens)。
- 进入 `fsdp` 文件夹：

```
cd Container-Root/eks/deployment/distributed-training/pytorch/pytorchjob/fsdp
```

- 创建一个 Persistent Volume Claim（PVC），它将使用你先前安装的底层 FSx CSI 驱动：

```
kubectl apply -f pvc.yaml
```

监控 `kubectl get pvc fsx-claim`，确认它达到 `BOUND` 状态。之后你可以到 Amazon EKS 控制台，看到一个未命名的卷已被创建。这一步可以让它在后台进行，但在后续步骤中运行 `./run.sh` 启动微调任务之前，请确保已达到 `BOUND` 状态。

- 要配置环境，打开 .env 文件并修改以下变量：`HF_TOKEN`：填入你先前生成的 Hugging Face token。`S3_LOCATION`：填入 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）位置，即训练完成后你希望存放微调模型的地址。
- 创建所需的资源 YAML：

```
./deploy.sh
```

这一行会使用 .env 文件中的值生成新的 YAML 文件，这些文件最终将用于模型部署。

- 构建并推送容器镜像：

```
./login-dlc.sh
./build.sh
./push.sh
```

### 运行微调任务

这一步我们使用上游 DLC，并把训练脚本加入镜像中以运行训练。

请确认你已在 Hugging Face 上申请 [Meta Llama 3.2 Vision 模型](https://huggingface.co/meta-llama/Llama-3.2-11B-Vision-Instruct) 的访问权限。获得许可后再继续下一步。

执行微调任务：

```
./run.sh
```

### 运行模型处理，并将输出保存到 Amazon S3

任务完成后，微调后的模型会存在于 FSx 文件系统中。下一步是把模型转换为 Hugging Face 格式并保存到 Amazon S3，以便你在后续步骤中访问和部署该模型：`kubectl apply -f model-processor.yaml`

上述命令会在你的实例上部署一个 pod，它会从 FSx 读取模型、转换为 Hugging Face 类型，并推送到 Amazon S3。该 pod 运行大约需要 8–10 分钟。你可以用 `./logs.sh` 或 `kubectl logs -l app=model-processor` 监控其日志。

获取模型在 Amazon S3 中的存储位置。这就是先前步骤中 .env 文件提到的同一个 Amazon S3 位置。运行以下命令（提供该 Amazon S3 位置）：`aws s3 cp tokenizer_config.json <S3_LOCATION>://tokenizer_config.json`

这是 Amazon Bedrock 导入 Meta Llama 模型所需的 tokenizer 配置，只有提供它，模型才能与 Amazon Bedrock Converse API 配合工作。更多细节请参阅 [自定义模型导入的 Converse API 代码示例](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-model-import-code-samples-converse.html)。

本文使用 [Mind2Web](https://github.com/OSU-NLP-Group/Mind2Web) 数据集。我们实现了从 [Mind2Web 代码](https://github.com/OSU-NLP-Group/Mind2Web/blob/main/src/action_prediction/dataloader.py) 改编而来的微调代码。改编后的代码如下：

## 在 Amazon Bedrock 上部署微调后的模型

微调完 Meta Llama 3.2 Vision 模型之后，你有多种部署选择。本节介绍其中一种部署方式：使用 Amazon Bedrock。借助 Amazon Bedrock，你可以无缝导入并使用自己定制的训练模型。请确保微调后的模型已上传到 S3 桶，并已转换为 Hugging Face 格式。按以下步骤导入你微调后的 Meta Llama 3.2 Vision 模型：

- 在 Amazon Bedrock 控制台的导航窗格中，于 **Foundation models ** 下选择 **Imported models**。
- 选择 **Import model**。
- 在 **Model name** 中，输入该模型的名称。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/29/image-ML-179103.jpeg)

- 在 **Model import source** 中，选择 **Amazon S3 bucket**。
- 在 **S3 location** 中，输入包含你微调模型的 S3 桶位置。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/29/image-ML-179104.jpeg)

- 按需配置其他模型设置，然后导入模型。

视模型大小而定，该过程可能需要 10–15 分钟才能完成。

导入自定义模型后，你可以用与默认 Meta Llama 3.2 Vision 模型相同的 Amazon Bedrock API 来调用它。只需把模型名称替换为你导入模型的 Amazon Resource Name（ARN）。详细说明请参阅 [Amazon Bedrock 自定义模型导入](https://aws.amazon.com/bedrock/custom-model-import/)。

你可以遵循以下 [GitHub repo](https://github.com/meta-llama/llama-models/blob/main/models/llama3_2/text_prompt_format.md) 中提到的 prompt 格式。例如：

`What are the steps to build a docker image?<|eot_id|><|start_header_id|>assistant<|end_header_id|>`

## 清理

使用以下代码清理你在本文中创建的资源：

```
cd Container-Root/eks/deployment/distributed-training/pytorch/pytorchjob/fsdp
kubectl delete -f ./fsdp.yaml ## Deletes the training fsdp job
kubectl delete -f ./etcd.yaml ## Deletes etcd
kubectl delete -f ./model-processor.yaml ## Deletes model processing YAML

cd aws-do-eks/Container-Root/eks/deployment/kubeflow/mpi-operator/
./remove.sh

cd aws-do-eks/Container-Root/eks/deployment/kubeflow/training-operator/
./remove.sh

## [VOLUME GETS DELETED] - If you want to delete the FSX volume
kubectl delete -f ./pvc.yaml ## Deletes persistent volume claim, persistent volume and actual volume
```

要停止并释放 P5 节点，请完成以下步骤：

- 在 Amazon EKS 控制台的导航窗格中选择 **Clusters**。
- 选择包含你节点组的集群。
- 在集群详情页选择 **Compute** 选项卡。
- 在 **Node groups** 区域中选择你的节点组，然后选择 **Edit**。
- 把期望大小设为 0。

## 结论
