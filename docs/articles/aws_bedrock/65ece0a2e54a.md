# HERE Technologies 借助全新的生成式 AI 编码助手提升开发者生产力

*本文与 HERE Technologies 的 Jonas Neuman 合写。*

[HERE Technologies](https://www.here.com/) 是地图与位置技术领域 40 年的先行者，它与 [AWS 生成式 AI 创新中心（GenAIIC）](https://aws.amazon.com/ai/generative-ai/innovation-center/)合作，借助一款由生成式 AI 驱动的编码助手提升开发者生产力。这一创新工具旨在改善 HERE 自助式 Maps API for JavaScript 的上手体验。HERE 对生成式 AI 的运用，使其全球开发者社区能够快速把自然语言查询转化为可交互的地图可视化，从而简化对 HERE 地图服务的评估与适配。

初次试用这些 API 的新开发者，往往从「我怎样才能生成从 A 点到 B 点的步行路线？」或「我怎样在地图上围绕某个点显示一个圆？」这类问题开始。尽管 HERE 的 API 文档十分详尽，HERE 仍意识到，加快上手过程可以显著提升开发者参与度。他们的目标是通过个性化体验提高留存率，并培养出熟练的产品拥护者。

为打造这一方案，HERE 与 GenAIIC 展开合作。我们的共同使命是创建一个智能的 AI 编码助手，能够针对用户的自然语言查询给出解释和可执行的代码方案。需求是构建一个可扩展的系统，能够把自然语言问题转换为内嵌 JavaScript 的 HTML 代码，可直接渲染为交互式地图供用户在屏幕上查看。

团队需要构建一套能满足以下目标的方案：

- 提供价值与可靠性：交付与用户问题相关、正确且可渲染的代码
- 促成自然、高效的开发者交互：以低延迟（撰写本文时约为 60 秒）提供代码和解释，同时保持对后续问题的上下文感知
- 通过在 HERE 的系统与品牌内实施针对无关或不可行查询的健壮过滤器，保持该功能的完整性与实用性
- 使系统成本保持合理，以便在整个 API 系统中扩展时维持正向 ROI

HERE 与 GenAIIC 共同构建了一套基于 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 的方案，在目标与固有取舍之间取得平衡。Amazon Bedrock 是一项全托管服务，通过单一 API 提供来自领先 AI 公司的基础模型（FM）访问，并提供一整套广泛的能力，使你能够构建具备内置安全性、隐私保护和负责任 AI 特性的生成式 AI 应用。该服务让你可以借助微调和 [Retrieval Augmented Generation](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）等技术，试验并私有化定制不同的 FM，还可以构建执行任务的 agent。Amazon Bedrock 是 serverless 的，免去基础设施管理负担，并能与现有 AWS 服务无缝集成。

该方案构建在一整套全面的 AWS 托管与 serverless 服务之上，包括 Amazon Bedrock FM、用于实现 RAG 的 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)、用于内容过滤的 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 以及用于会话管理的 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/)，从而在不承担基础设施管理开销的情况下交付一个健壮、可扩展的编码助手。其成果是一个实用、易用的工具，能够提升开发者体验，并为 API 探索与位置导航体验的快速方案构建提供一种新颖方式。

本文介绍这项工作是如何完成的。

## 数据集

我们在本方案中使用了以下资源：

- **领域文档** – 我们使用了两个公开可用的资源：[HERE Maps API for JavaScript Developer Guide](https://www.here.com/docs/bundle/maps-api-for-javascript-developer-guide/page/README.html) 和 [HERE Maps API for JavaScript API Reference](https://www.here.com/docs/bundle/maps-api-for-javascript-api-reference/page/index.html)。Developer Guide 提供概念性解释，API Reference 提供详细的 API 函数信息。
- **示例样例** – HERE 提供了 60 个案例，每个案例包含一个用户查询、HTML/JavaScript 代码方案和简要说明。这些示例横跨多个类别，包括 [geodata](https://www.here.com/docs/bundle/maps-api-for-javascript-developer-guide/page/topics/map-types.html)、[markers](https://www.here.com/docs/bundle/maps-api-for-javascript-developer-guide/page/topics/marker-objects.html) 和 [geoshapes](https://www.here.com/docs/bundle/maps-api-for-javascript-developer-guide/page/topics/geo-shapes.html)，并被划分为训练集与测试集。
- **范围外查询** – HERE 提供了超出 HERE Maps API for JavaScript 范围的查询样例，大型语言模型（LLM）不应对其作出回应。

## 方案概览

为开发这一编码助手，我们设计并实现了一条 RAG 工作流。尽管标准 LLM 能够生成代码，但它们往往基于过时的知识工作，无法适应 HERE Maps API for JavaScript 的最新变更或最佳实践。HERE Maps API for JavaScript 文档通过提供准确、最新的上下文，可以显著增强编码助手的能力。将 HERE Maps API for JavaScript 文档存放在向量数据库中，可让编码助手针对用户查询检索相关片段。这使得 LLM 能把自己的回复扎根于官方文档，而不是可能过时的训练数据，从而产生更准确的代码建议。

该方案架构由四个关键模块组成：

- **后续问题模块** – 该模块通过上下文会话处理实现后续问题的回答。聊天历史存储在 DynamoDB 中，并在用户提出新问题时检索出来。如果存在聊天历史，就将其与新问题合并。随后 LLM 对其进行处理，把后续问题改写为独立查询以供下游处理。该模块在保持上下文感知的同时能识别话题变化——当新问题偏离之前的对话上下文时，保留原始问题。
- **范围过滤与防护模块** – 该模块评估查询是否落在 HERE Maps API for JavaScript 的范围之内，并判断其可行性。我们在 Amazon Bedrock 上应用了 Amazon Bedrock Guardrails 和 [Anthropic 的 Claude 3 Haiku](https://www.anthropic.com/news/claude-3-haiku) 来过滤范围外问题。借助简短的自然语言描述，Amazon Bedrock Guardrails 可以帮助为编码助手定义一组要拦截的范围外话题，例如涉及其他 HERE 产品的话题。Amazon Bedrock Guardrails 还有助于过滤包含仇恨言论、侮辱、性、暴力以及不当行为（包括犯罪活动）等话题的有害内容，并帮助防御 prompt 攻击。这确保编码助手遵循负责任 AI 政策。对于范围内的查询，我们使用 Anthropic 的 Claude 3 Haiku 模型，通过同时分析用户查询和检索到的领域文档来评估可行性。我们选择 Anthropic 的 Claude Haiku 3，是因为它在性能与速度之间达到最佳平衡。系统对范围外或不可行的查询生成标准回复，可行的问题则进入回复生成环节。
- **知识库模块** – 该模块使用 Amazon Bedrock Knowledge Bases 执行文档索引和检索操作。Amazon Bedrock Knowledge Bases 是一项全面的托管服务，端到端简化了 RAG 流程。它自动处理从数据摄取到索引、检索与生成的各个环节，免去了构建和维护自定义集成以及管理数据流的复杂性。对于这个编码助手，我们使用 Amazon Bedrock Knowledge Bases 进行文档索引与检索。Amazon Bedrock Knowledge Bases 提供的多种文档分块、embedding 生成和检索方法选项使其适应性很强，让我们可以测试并找出最优配置。我们创建了两个独立的索引，每个领域文档一个。这种双索引方式确保回复生成时能从两个文档来源检索到内容。索引过程在 Amazon Bedrock 上使用 [Cohere embedding English V3](https://cohere.com/blog/introducing-embed-v3) 模型实现分层分块，文档检索则采用语义检索。
- **回复生成模块** – 回复生成模块使用 Amazon Bedrock 上 [Anthropic 的 Claude 3.5 Sonnet](https://www.anthropic.com/news/claude-3-5-sonnet) 模型处理范围内且可行的查询。它把用户查询与检索到的文档结合起来，生成内嵌 JavaScript 代码的 HTML 代码，能够渲染交互式地图。此外，该模块还会对方案要点给出简要说明。我们选择 Anthropic 的 Claude 3.5 Sonnet，是因为它具备出色的代码生成能力。

## 方案编排

上一节讨论的每个模块都被拆解为更小的子任务。这使我们得以使用 [LangGraph](https://www.langchain.com/langgraph) 把系统中的功能与各个决策点建模为有向无环图（DAG）。DAG 是一种节点（顶点）之间通过表示关系的定向边（箭头）相连的图，关键在于图中没有环（循环）。DAG 可以表示具有确定顺序的依赖关系，有助于实现安全、高效的任务执行。LangGraph 编排有多项好处，例如并行任务执行、代码可读性，以及通过状态管理和流式支持带来的可维护性。

下图展示了编码助手的工作流。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/04/24/ml-17998-here-langchain.jpg)

当用户提交问题时，会触发一条工作流，从 Reformulate Question 节点开始。该节点实现后续问题模块（模块 1）的功能。Apply Guardrail、Retrieve Documents 和 Review Question 三个节点使用改写后的输入问题并行执行。Apply Guardrail 节点使用 Amazon Bedrock Guardrails 的拒绝话题来划定边界并施加防护，抵御有害输入；Review Question 节点则使用 Anthropic 的 Claude 3 Haiku 过滤范围外询问（模块 2）。Retrieve Documents 节点从 Amazon Bedrock 知识库检索相关文档，为语言模型提供必要信息（模块 3）。

Apply Guardrail 和 Review Question 节点的输出决定下一个被调用的节点。如果输入通过了两项检查，Review Documents 节点会通过分析该问题能否用检索到的文档回答来评估其可行性（模块 2）。如果可行，Generate Response 节点便会回答问题，代码和描述以流式方式推送到 UI，用户可以在数秒内开始获得系统的反馈（模块 4）。否则，Block Response 节点返回预定义的答复。最后，Update Chat History 节点持久保存会话历史以备后续参考（模块 1）。

这条 pipeline 支撑着代码助手 chatbot 的能力，为寻求 HERE Maps API for JavaScript 实现指导的开发者提供高效、易用的体验。下面的代码和截图是针对查询「如何在点击 marker 时打开 infobubble？」由模型生成的代码以及代码渲染出的地图示例。

## Prompt 工程

为提升最终代码生成的准确性，我们针对回复生成模块做了大量的 prompt 工程。最终的 prompt 融合了以下组成部分：

- **结合思维链的任务拆解** – 我们把代码生成任务分解为连续的步骤，为 LLM 在回复生成过程中提供结构化的指引。
- **Few-shot learning** – 我们从 LLM 起初表现欠佳的问题类别中精选了三个训练示例来增强 prompt。这些示例包含检索到的文档和预期回复，展示了期望的输出格式。
- **代码模板集成** – 针对领域专家（SME）反馈的地图交互问题，我们引入了一个用于生成的代码模板。该模板包含 HERE 地图初始化与设置的样板代码，从而提升准确性，并让生成的代码保持一致的地图交互能力。

下面列出 prompt 的核心结构及其涉及的组成部分：

- 任务指令
- 示例
- 用户查询
- Developer Guide 内容
- API Reference 内容
- 代码模板

## 评估

我们针对测试集中的每个问题人工评估了代码生成的准确性。评估聚焦两个关键标准：

- 生成的代码能否渲染出可交互的 HERE 地图
- 渲染出的地图是否解决了用户的查询——例如，若用户要求添加一个圆，则检查生成的代码是否成功在地图上添加了圆

同时满足这两项标准的代码样本被判为正确。除准确性外，我们还评估了延迟，包括整体延迟和首 token 时延。整体延迟指生成完整回复所花费的总时间。为改善用户体验、避免用户干等而没有可见输出，我们采用了响应流式输出。首 token 时延衡量系统生成回复第一个 token 所需的时间。基于测试数据集中 20 个样本的评估结果如下：

- 代码生成准确性：87.5%
- 整体延迟：23.5 秒
- 首 token 时延：8 秒以内

高准确性确保代码助手能生成正确的代码来回答用户问题。较低的整体延迟和快速的首 token 时延显著减少了用户等待时间，提升了整体用户体验。

## 安全考量

在 AWS，安全是我们的首要任务。就本文的范围而言，我们分享了如何使用 Amazon Bedrock Guardrails 构建负责任的 AI 应用。安全与保障对每一个应用都至关重要。有关 AWS 在安全、负责任的 AI 开发方面做法的深入指引，请参阅 [Securing generative AI](https://aws.amazon.com/ai/generative-ai/security/) 以及 AWS 白皮书 [Navigating the security landscape of generative AI](https://docs.aws.amazon.com/pdfs/whitepapers/latest/navigating-security-landscape-genai/navigating-security-landscape-genai.pdf)。

## 可改进之处

以下两个方面值得探索，以提升系统整体准确性并改进当前评估 LLM 回复的机制：

- **改进自动化评估** – 我们建议探索把评估自动化。例如，可以采用 LLM-as-a-judge 的方式对比基准真值与生成的代码，同时借助 [Playwright](https://playwright.dev/) 这类工具做自动化的地图渲染检查。这一组合策略可以为评估 LLM 生成的地图代码的质量与功能性提供可扩展、准确且高效的框架。
- **带自我纠正反馈的 prompt 链** – 未来的实现可以考虑一条 pipeline：执行生成的代码、与地图交互，并把错误反馈回 LLM 以提升准确性。取舍在于这一反馈回路会增加系统整体延迟。

## 结论

本方案的成果是一个快速、实用、易用的编码助手，提升了 HERE Maps API for JavaScript 的开发者体验。通过对 RAG 方法与 prompt 工程技术的迭代演进，团队在未依赖微调的情况下超越了目标准确率与延迟指标。这意味着该方案可以扩展到 HERE Maps API for JavaScript 之外的其他 HERE 产品。此外，随着 Amazon Bedrock 上出现性能更强的 FM，支撑该助手的 LLM 也可以升级。

该方案的亮点包括：在 prompt 中使用地图初始化代码模板、由 LangGraph 编排的模块化且可维护的架构，以及能在 8 秒内开始显示生成代码的响应流式能力。针对特定任务优化的语言模型经过精心挑选与组合，进一步提升了方案的整体性能与成本效益。

总体而言，这一概念验证的成果得益于 GenAIIC 与 HERE Technologies 的合作。该编码助手为 HERE Technologies 显著提升开发者生产力、加快 API 采用并推动其开发者生态增长奠定了坚实基础。

了解 Amazon Bedrock 如何凭借模型选择以及 Amazon Bedrock Knowledge Bases 和 Amazon Bedrock Guardrails 等功能，让构建生成式 AI 应用变得轻而易举。从 Amazon Bedrock Knowledge Bases 入手，实现基于 RAG 的方案，从而转变你的开发者体验并提升生产力。
