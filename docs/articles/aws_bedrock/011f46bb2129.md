# 使用 AgentCore Gateway 与 MCP 客户端构建安全的 auth code flow 配置

在现代开发 workflow 中，开发者越来越依赖 [Kiro Integrated Development Environment（IDE）](https://kiro.dev/)等 agentic 编码助手来与远程工具和服务交互。然而，组织需要强大的身份验证机制，在这些 agentic 编码助手与企业级[模型上下文协议（Model Context Protocol，MCP）](https://modelcontextprotocol.io/docs/getting-started/intro)服务器之间提供安全、经过身份验证的访问。

[Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html) 是一项全托管服务，可帮助你在生产环境中部署、管理和扩展 AI agent。其关键组件之一 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 提供集中入口，用于对 agent 与工具之间的通信进行路由和保护。当 AI 助手通过 Gateway 向 MCP 服务器发起请求时，该请求在处理之前必须经过验证。这就是所谓的*入站身份验证*。只有经过授权的用户和 agent 才能访问 MCP 服务器暴露的工具和服务。组织通常通过身份提供商（identity provider，IdP，例如 Okta、Microsoft Entra ID 或 [Amazon Cognito](https://aws.amazon.com/cognito/)）管理用户身份，由其对用户进行身份验证并签发用于确认其身份的安全 token。

本文演示如何实现开放授权（Open Authorization，OAuth）Code flow，将其作为托管在 [Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 上 MCP 服务器的入站授权机制。读完本指南，你将获得一套可用于生产环境的配置，其中每个 AI 助手请求都会使用由组织身份提供商签发的有效用户身份 token 进行身份验证。

#### 你将学到什么

- auth code flow 如何与作为 MCP 资源服务器的 AgentCore Gateway 协同工作。
- 分步配置你组织的身份提供商。
- AgentCore Gateway 的入站身份验证设置。
- 与 Kiro IDE 客户端的集成。

## 解决方案概览

在入站 authorization code flow 的 OAuth 配置中，AgentCore Gateway 充当 *MCP 资源服务器*，在允许 AI 客户端访问任何工具之前都要求提供有效的身份 token。

下图展示了使用 AgentCore Gateway 的 authorization code flow 端到端架构，包括身份提供商、AI 客户端和 MCP 服务器之间的交互。

*图 1：authorization code flow 架构图。*

### 关键组件

该解决方案涉及以下组件协同工作，以完成身份验证 flow：

- **身份提供商（IdP）：** 管理用户身份验证并签发 token。上图以 Amazon Cognito 为例，但它也可以是你的组织所使用的 IdP。
- **用户：** 向 IdP 进行身份验证的最终用户，其身份会在每次请求时得到验证。
- **Amazon Bedrock AgentCore Gateway：** 充当 OAuth 资源服务器，验证 token 并将请求转发到 MCP 服务器。
- **Agentic 编码助手：** Kiro IDE，充当 OAuth 客户端并管理身份验证 flow。
- **MCP 服务器：** AI 助手需要访问的后端工具和服务。
- **MCP OAuth proxy（可选）：** 帮助弥合 agentic 编码助手、IdP 和 MCP 服务器之间规范标准化的差距。MCP OAuth proxy 带来支持 authorization code flow 的标准化能力。

### 入站 authorization code flow

这一 flow 确保 AI 助手发送给 MCP 服务器的每个请求都使用属于该用户的有效身份 token 进行身份验证。

- **MCP 客户端连接** – agentic 编码助手（例如 Kiro IDE）发起与 AgentCore Gateway 的 MCP endpoint 的连接。
- **身份验证质询** – Gateway 检测到请求缺少有效 token，返回 HTTP 401，其中包含指向 Gateway 的 OAuth Protected Resource Metadata endpoint（`.well-known/oauth-protected-resource`）的 `www-authenticate` 标头。这遵循 MCP 规范的 [Protected Resource Metadata（PRM）模式](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)。
- **发现** – MCP 客户端从 Gateway 获取 Protected Resource Metadata，后者返回 IdP 的授权服务器 discovery URL（例如 `https://{yourIdPDomain}/oauth2/default/.well-known/openid-configuration`）。
- **用户重定向** – MCP 客户端打开用户的系统浏览器，带着 PKCE challenge 重定向到 IdP 的授权 endpoint，请求已配置的 scopes（例如 `openid profile email offline_access`）。
- **用户身份验证与授权同意** – 用户在 IdP 登录页面输入凭据。IdP 验证用户身份，并提示用户同意授权该应用。
- **授权码授予** – 批准之后，IdP 将用户的浏览器连同授权码一起重定向到客户端的本地回调 URL（由客户端的本地监听器管理）。
- **token 交换请求** – MCP 客户端将授权码连同 PKCE code verifier 一起发送到 IdP 的 token endpoint。
- **token 签发** – IdP 验证授权码和 PKCE verifier，然后向 MCP 客户端返回 access token（以及可选的 refresh token）。
- **经过身份验证的 MCP 请求与验证** – MCP 客户端在所有后续请求的 `Authorization` 标头中携带 access token。Gateway 验证 token 的签名、过期时间、签发者以及 audience 或自定义 claims，然后将请求转发到目标 MCP 服务器执行。

![展示 MCP 客户端、AgentCore Gateway、IdP 和 MCP 服务器之间交换 discovery、授权、token 与验证请求的 authorization code flow 时序图。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/26/ML-20412-2.jpg)

*图 2：authorization code flow 请求时序。*

### 配置概览

下表汇总了 authorization code flow 配置中各组件所需的配置。详细分步说明见「技术实现」一节。

|  | **组件** | **所需配置** |
| --- | --- | --- |
| 1 | **身份提供商** | 创建一个 OpenID Connect（OIDC）Web 应用，并启用 Authorization Code 和 Refresh Token 授予类型。 |
| 2 | **AgentCore Gateway** | 将入站授权设置为 JWT。将 discovery URL 配置为你的 IdP 签发者（例如 `https://{yourIdPDomain}/oauth2/default/.well-known/openid-configuration`）。 |
| 3 | **Kiro IDE** | 在 Settings > Connectors 中添加 Gateway URL（或通过 CLI 添加）。如果 Gateway 返回带有正确身份验证标头的 401 Unauthorized，客户端会自动触发 OAuth flow。 |

## 技术实现

在明确架构和 flow 之后，配置各个组件。本节为配置概览表中提到的三个组件提供分步说明：

- **身份提供商**：注册 OIDC 应用，并配置授予类型、重定向 URI 和 token 设置。
- **AgentCore Gateway**：启用基于 JWT 的入站授权，并将其指向你的 IdP discovery endpoint。
- **MCP 客户端（Kiro IDE）**：将客户端连接到 Gateway URL，并验证端到端 OAuth flow。

### 前提条件

要跟随本文操作，你必须具备以下前提条件。

- 一个已部署 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-building.html) 的 AWS 账户。
- 一个有权限配置应用的身份提供商（IdP，例如 Amazon Cognito、Okta、Auth0 或其他企业级身份提供商）。
- MCP OAuth proxy。
- 本地安装 Kiro IDE。
- 对 [OAuth 2.0](https://oauth.net/2/) flow 有基本了解。

### 步骤 1：配置组织的身份提供商

在此步骤中，你要在组织的身份提供商处注册一个 OIDC 应用，并将其配置为支持带 PKCE 的 authorization code flow。

#### 1.1 创建 OIDC 应用

登录 IdP 管理控制台，创建一个新的 OIDC/OAuth 2.0 应用集成：

- **登录方式：** OIDC。
- **应用类型：** Web 应用。
- **名称：** AgentCore Gateway client（或你偏好的名称）。

#### 1.2 配置授予类型

启用以下授予类型：

- Authorization Code。
- Refresh Token。

#### 1.3 设置重定向 URI

添加你的 AI 客户端将使用的回调 URL：

```
http://localhost:PORT/callback
```

将 `PORT` 替换为你的[客户端使用的](https://kiro.dev/docs/enterprise/identity-provider/okta/#create-new-app-integration)端口。

#### 1.4 配置 token 设置

在 IdP 应用设置中，执行以下操作。

**token 有效期：**

- **access token 有效期：** 1 小时（推荐）。
- **refresh token 有效期：** 90 天（根据安全要求调整）。
- **ID token 有效期：** 1 小时。

#### 1.5 记录你的配置

保存以下值。配置 Gateway 时会用到它们：

- **Client ID：** 在应用的 General 选项卡中找到（Kiro IDE 客户端配置需要）。
- **Issuer URL：** 你的 IdP 签发者 URL（例如 `https://{yourIdPDomain}/oauth2/default`）。
- **Discovery URL：** 你的 IdP 的 OpenID Connect discovery endpoint（例如 `https://{yourIdPDomain}/oauth2/default/.well-known/openid-configuration`）。

对于此配置：

- **无需 client secret** – 此 flow 使用 PKCE（Proof Key for Code Exchange），它专为桌面应用等公共客户端设计。Kiro IDE 不需要也不会使用 client secret。
- **客户端配置中无需 IdP endpoint** – Kiro IDE 会从 Gateway 自动发现 OAuth endpoint，Gateway 会返回 discovery URL。你无需在客户端中直接配置 IdP URL。

### 步骤 2：配置 AgentCore Gateway

配置好身份提供商后，下一步是将 AgentCore Gateway 连接到你的 IdP，以便验证传入的 token。

#### 2.1 设置入站授权模式

将 Gateway 配置为使用基于 JWT 的身份验证，并指向你的 IdP discovery endpoint：

```
# Example Gateway configuration (adjust based on your deployment method)
aws agentcore update-gateway \
  --gateway-id <your-gateway-id> \
  --inbound-auth-type JWT \
  --jwt-discovery-url "https://{yourIdPDomain}/oauth2/default/.well-known/openid-configuration" \
  --region <your-region>
```

#### 2.2 自定义 claim 验证

AgentCore Gateway 基于标准 OAuth 2.0 claims 验证 JWT token，并支持自定义 claim 验证，以适配不同的 IdP 实现。Gateway 期望 token 包含：

- **标准 claims：** `iss`（签发者）、`aud`（audience）、`exp`（过期时间）、`iat`（签发时间）、`client_id`（客户端标识）和 `scopes`（允许的 scopes）。
- **客户端标识：** Gateway 可以根据你的 IdP，通过各种 claim 验证客户端身份。

其他 IdP 可能使用不同的 claim 名称来表示客户端标识、scopes 等（例如 `cid`、`azp`、`scp`）。你可以在 Gateway 中配置自定义 claim 验证，以匹配你的 IdP token 结构：

- **自定义 claim：** `<claim-name> EQUALS <expected-value>`（参见 [AgentCore Gateway: Set up a JWT](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-inbound-auth.html)）。
- 示例：`cid EQUALS 0oaz7147z771FZmdQ697`（适用于使用 `cid` 的 IdP，如 Okta）。
- 这会验证 token 是否为你的特定应用签发。

**注意：** 使用自定义 claim 验证时，Gateway 的 **Allowed audience** 字段可以留空。自定义 claim 检查已提供必要的客户端身份验证。

#### 2.3 理解 Gateway 的 token 验证

Gateway 现已配置好你的 IdP discovery URL 和 claim 规则，接下来看看它在运行时如何验证传入的 token。

AgentCore Gateway 的设计不关心用户如何获取 OAuth token。Gateway 不区分通过以下方式获取的 token：

- **Client credentials flow**，即应用直接进行身份验证。
- **Authorization code flow**，即用户显式进行身份验证并授予同意。

Gateway 只要求请求中提供的 OAuth token 根据 Gateway 设置时配置的参数是有效的：

- **token 签名：** 使用 IdP discovery URL 提供的公钥进行验证。
- **token 过期时间：** 验证 token 尚未过期。
- **签发者（`iss` claim）：** 与预期的 IdP 签发者匹配。
- **Audience 或自定义 claims：** 验证 token 是为该 Gateway 或应用签发的。
- **标准 OAuth claims：** 检查 `iat`、`exp` 等必需 claims。

无论用户通过 client credentials flow、authorization code flow 还是其他 OAuth 授予类型获取 token，Gateway 都一视同仁。只要 token 通过 Gateway 设置中配置的验证检查，请求就会获得授权。凭借这种灵活性，你可以选择适合自己用例的身份验证 flow，同时在 Gateway 层面保持一致的安全性。

#### 2.4 验证 Gateway 配置

测试 Gateway endpoint 是否可访问且需要身份验证：

```
# Test authentication with an actual MCP request (POST without auth token)
curl -i -X POST https://<your-gateway-url>/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"initialize","params":{},"id":1}'
```

以下响应确认身份验证配置正确（对未经身份验证的 MCP 请求返回 401 响应）：

```
# Expected response showing authentication is required:
HTTP/2 401
www-authenticate: Bearer resource_metadata="https://<your-gateway-url>/.well-known/oauth-protected-resource"
{"jsonrpc":"2.0","id":0,"error":{"code":-32001,"message":"Missing Bearer token"}}
```

### 步骤 3：MCP OAuth proxy

在本文中，使用 `mcp-remote` 来标准化 MCP 客户端接口并完成 authorization code flow。

#### 3.1 安装 mcp-remote 包

使用 [mcp-remote](https://www.npmjs.com/package/mcp-remote) 将 Kiro IDE 的 MCP 客户端与 Gateway 受 OAuth 保护的 endpoint 桥接起来。

**注意：** `mcp-remote` 是一个可行的概念验证，应视为实验性工具。

```
npm install -g mcp-remote
```

### 步骤 4：配置 AI 客户端（Kiro IDE）

配置好 Gateway 和 MCP OAuth proxy 后，最后一步配置是将 AI 客户端连接到 Gateway endpoint。Kiro IDE 会自动处理 OAuth flow。当它收到来自 Gateway 的 401 质询时，会与你的 IdP 启动 authorization code flow。

#### 4.1 配置 Kiro IDE

在 `~/.kiro/settings/mcp.json` 的 MCP 配置文件中添加 Gateway：

```
{
  "mcpServers": {
    "gateway-tools": {
      "command": "mcp-remote",
      "args": [
        "https://<your-gateway-url>/mcp",
        "<PORT>",
        "--static-oauth-client-info",
        "{\"client_id\": \"<your-idp-client-id>\", \"redirect_uris\": [\"http://localhost:<PORT>/oauth/callback\"], \"scope\": \"openid profile email offline_access\"}"
      ]
    }
  }
}
```

**配置参数：**

- `command`：使用 `mcp-remote` 连接远程 MCP 服务器（[mcp-remote](https://www.npmjs.com/package/mcp-remote)）。
- 第一个参数：带 `/mcp` 路径的 Gateway URL。
- 第二个参数：OAuth 回调的本地端口（例如 `3334`）。
- `--static-oauth-client-info`：包含以下内容的 JSON 字符串：  `client_id`：你的 IdP 应用 client ID。 `redirect_uris`：必须与第二个参数指定的端口匹配。 `scope`：包含 `openid profile email offline_access` 以实现基本身份验证。

#### 4.2 测试身份验证 flow

添加 Gateway 连接后，验证身份验证 flow 是否成功完成：

- 重启 AI 客户端。
- 尝试使用 Gateway 中的一个工具。
- 你会被重定向到浏览器进行 IdP 登录。
- 身份验证成功后，工具运行。

### 步骤 5：验证端到端 flow

所有组件配置完毕且初次身份验证成功后，验证整个 flow 是否能够端到端工作：从 AI 客户端发送工具请求，到 Gateway 进行 token 验证，再到接收 MCP 服务器的响应。

#### 5.1 检查 token 验证

监控 Gateway 日志以确认 token 验证情况：

```
# Example log entry showing successful validation
[INFO] Token validated successfully for user: user@example.com
[INFO] Executing tool: list_files
```

有关以 Okta 作为 IdP 的分步演练，请参阅这个 [GitHub 仓库](https://github.com/awslabs/agentcore-samples/tree/main/06-workshops/02-AgentCore-gateway/17-inbound-auth-code-flow-okta)。

## 清理

如果你跟随本文操作并想撤销所创建的资源，请完成以下步骤。这些步骤按创建的相反顺序排列，以便先移除依赖资源，再移除其所依赖的组件。

### 撤销 OAuth token

在移除任何配置之前，先撤销测试期间签发的任何有效 token。请查阅 IdP 文档，了解撤销 endpoint 的准确 URL 及支持的参数。

```
curl -X POST "<your-idp-revocation-endpoint>" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "token=<your-refresh-token>&client_id=<your-client-id>"
```

因 IdP 而异的关键注意事项：

- **撤销 endpoint URL：** 查看 IdP 的 OpenID Connect discovery 文档（`revocation_endpoint` 字段）。
- **接受的 token 类型：** 某些 IdP 只接受 refresh token，另一些则同时接受 access token 和 refresh token。
- **客户端身份验证：** 公共客户端通常在请求体中传递 `client_id`。机密客户端可能需要带有编码凭据的 Basic Authorization 标头。
- **级联行为：** 撤销 refresh token 通常会使关联的 access token 失效，但请与你的 IdP 确认。

你还可以通过移除 `mcp-remote` 身份验证缓存来清除本地缓存的 token。在 macOS 或 Linux 上：

```
rm -rf ~/.mcp-auth
```

### 移除 AI 客户端配置（Kiro IDE）

从 `~/.kiro/settings/mcp.json` 的 Kiro IDE MCP 配置中移除 Gateway 条目。删除你在步骤 4 中添加的 `gateway-tools` 服务器块。

### 移除 MCP OAuth proxy

卸载你在步骤 3 中安装的 `mcp-remote` 包：

```
npm uninstall -g mcp-remote
```

### 删除 AgentCore Gateway 配置

移除你在步骤 2 中设置的入站身份验证配置；如果该 Gateway 仅为本演练创建，也可以将其整个删除：

**选项 A：移除入站身份验证（保留 Gateway）**

```
aws agentcore update-gateway \
  --gateway-id <your-gateway-id> \
  --inbound-auth-type NONE \
  --region <your-region>
```

**选项 B：删除 Gateway**

```
aws agentcore delete-gateway \
  --gateway-id <your-gateway-id> \
  --region <your-region>
```

### 移除组织的身份提供商配置

删除你在步骤 1 中创建的 OIDC 应用集成：

- 登录 IdP 管理控制台。
- 导航到 **Applications** > **Applications**。
- 选择你创建的应用（例如“AgentCore Gateway client”）。
- 先停用该应用（如果 IdP 要求），然后删除它。

这会撤销所有客户端凭据，并阻止今后为该应用签发任何 token。

## 结论

在本文中，你学习了如何使用入站 authorization code flow，实现对托管在 Amazon Bedrock AgentCore Gateway 上的 MCP 服务器的安全、经过身份验证的访问。借助这套配置，每个 AI 助手请求都会使用来自组织身份提供商的有效用户 token 进行身份验证。

#### 关键要点

- authorization code flow 通过要求用户同意和身份验证，提供强大的身份验证能力。
- AgentCore Gateway 充当 OAuth 资源服务器，在允许请求调用目标之前验证 token。
- 该 flow 对最终用户是透明的。他们只需身份验证一次，token 便会自动刷新。
- 该架构可扩展，支持多个 AI 客户端和身份提供商。
