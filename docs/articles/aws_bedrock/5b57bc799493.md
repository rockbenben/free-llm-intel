# 使用 Amazon Bedrock AgentCore 构建多 agent 站点可靠性工程助手

站点可靠性工程师（SRE）在现代分布式系统中面临日益复杂的挑战。在生产事故期间，他们必须快速关联来自多个来源的数据——日志、指标、Kubernetes 事件和运维手册——以定位根本原因并实施解决方案。传统监控工具提供原始数据，但缺乏跨这些异构系统综合信息的智能，往往只能让 SRE 手工拼凑系统故障背后的来龙去脉。

借助生成式 AI 方案，SRE 可以用自然语言向自己的基础设施提问。例如，他们可以问“payment-service 的 pod 为什么在反复崩溃重启？”或“是什么导致 API 延迟飙升？”，并获得结合了基础设施状态、日志分析、性能指标和逐步修复流程的全面、可执行的洞察。这项能力把事故响应从人工的、耗时密集的流程，转变为高效的协作式排查。

本文演示如何使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)、[LangGraph](https://langchain-ai.github.io/langgraph/) 和 [Model Context Protocol (MCP)](https://modelcontextprotocol.io/) 构建多 agent SRE 助手。该系统部署专业化的 AI agent，它们协同工作，提供现代 SRE 团队进行有效事故响应和基础设施管理所需的深度上下文智能。我们将带你走完完整的实现过程，从搭建演示环境到在生产环境的 Amazon Bedrock AgentCore Runtime 上部署。

## 方案概览

该方案采用全面的多 agent 架构，通过智能自动化应对现代 SRE 运营的挑战。方案由四个专业化的 AI agent 组成，它们在 supervisor agent 之下协同工作，提供全面的基础设施分析和事故响应协助。

本文中的示例使用来自我们演示环境的合成生成数据。后端服务器模拟真实的 Kubernetes 集群、应用日志、性能指标和运维手册。在生产部署中，这些打桩服务器会被替换为与你实际的基础设施系统、监控服务和文档仓库的连接。

该架构展示了多项关键能力：

- **自然语言基础设施查询** – 你可以用平实的语言对基础设施提出复杂问题，并获得结合多来源数据的详细分析
- **多 agent 协作** – 面向 Kubernetes、日志、指标和运维流程的专业化 agent 协同工作，提供全面的洞察
- **实时数据综合** – agent 通过标准化 API 访问实时基础设施数据，并呈现关联后的发现
- **自动化手册执行** – agent 针对常见事故场景检索并展示逐步的操作流程
- **来源标注** – 每条发现都包含明确的来源标注，便于核实和审计

该架构展示了 SRE 支持 agent 如何与 Amazon Bedrock AgentCore 的各个组件无缝集成：

- **客户接口** – 接收关于 API 响应时间下降的告警，并返回全面的 agent 响应
- **Amazon Bedrock AgentCore Runtime** – 管理多 agent SRE 方案的执行环境
- **SRE 支持 agent** – 处理事故并编排响应的多 agent 协作系统
- **Amazon Bedrock AgentCore Gateway** – 通过 OpenAPI 接口把请求路由到专业化工具：用于获取集群事件的 Kubernetes API、用于分析日志模式的 Logs API、用于分析性能趋势的 Metrics API、用于检索操作流程的 Runbooks API
- **Amazon Bedrock AgentCore Memory** – 存储和检索会话上下文与先前交互，以保持连续性
- **Amazon Bedrock AgentCore Identity** – 使用 [Amazon Cognito](https://aws.amazon.com/cognito) 集成来处理工具访问的认证
- **Amazon Bedrock AgentCore Observability** – 收集并可视化 agent 追踪数据，用于监控和调试
- **Amazon Bedrock LLM** – 通过 Anthropic 的 Claude 大语言模型（LLM）为 agent 提供智能

该多 agent 方案采用 supervisor-agent 模式，由一个中央编排器协调五个专业化 agent：

- **Supervisor agent** – 分析传入查询并制定排查计划，把工作路由给合适的专家，并将结果汇总为全面报告
- **Kubernetes 基础设施 agent** – 处理容器编排和集群运维，排查 pod 故障、部署问题、资源约束和集群事件
- **应用日志 agent** – 处理日志数据以找到相关信息，识别模式与异常，并跨多个服务关联事件
- **性能指标 agent** – 监控系统指标并识别性能问题，提供实时分析和历史趋势
- **运维手册 agent** – 根据当前情况提供有文档记录的流程、故障排查指南和升级流程

## 使用 Amazon Bedrock AgentCore 基础原语

该方案通过使用多个核心原语，展示了 Amazon Bedrock AgentCore 的强大能力。方案支持 Anthropic LLM 的两种提供方。Amazon Bedrock 为 AWS 集成部署支持 Anthropic 的 Claude 3.7 Sonnet，Anthropic API 则为直接 API 访问支持 Anthropic 的 Claude 4 Sonnet。

Amazon Bedrock AgentCore Gateway 组件把 SRE agent 的后端 API（Kubernetes、应用日志、性能指标和运维手册）转换为 Model Context Protocol（MCP）工具。这使使用支持 MCP 的开源框架（如本文中的 LangGraph）构建的 agent 能够无缝访问基础设施 API。

整个方案的安全性由 Amazon Bedrock AgentCore Identity 提供。它支持入站认证，为连接网关的 agent 提供安全的访问控制；也支持出站认证，管理与后端服务器的认证，从而在无需硬编码凭证的情况下提供安全的 API 访问。

用于在生产环境部署 SRE agent 的无服务器执行环境由 Amazon Bedrock AgentCore Runtime 提供。它可以从零自动扩展以应对并发的故障排查，同时保持完整的会话隔离。Amazon Bedrock AgentCore Runtime 同时支持 OAuth 和 [AWS Identity and Access Management](https://aws.amazon.com/iam)（IAM）用于 agent 认证。调用 agent 的应用必须具备适当的 IAM 权限和信任策略。更多信息请参阅 [Amazon Bedrock AgentCore 的身份与访问管理](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/security-iam.html)。

Amazon Bedrock AgentCore Memory 把 SRE agent 从无状态系统转变为智能的学习型助手，可依据用户偏好和历史上下文对排查进行个性化。memory 组件提供三种不同的策略：

- **用户偏好策略（/sre/users/{user_id}/preferences）** – 存储个人用户在排查风格、沟通渠道、升级流程和报告格式方面的偏好。例如，Alice（技术型 SRE）会收到带有故障排查步骤的详细系统分析，而 Carol（高管）会收到聚焦业务影响的摘要与影响分析。
- **基础设施知识策略（/sre/infrastructure/{user_id}/{session_id}）** – 在多次排查之间累积领域专业知识，使 agent 能够从过去的发现中学习。当 Kubernetes agent 识别出内存泄漏模式时，这一知识可供后续排查使用，从而更快定位根本原因。
- **排查记忆策略（/sre/investigations/{user_id}/{session_id}）** – 维护过往事故及其处置的历史上下文。这使方案能够建议经过验证的修复方法，并避免此前失败过的反模式。

memory 组件通过个性化排查体现其价值。当 Alice 和 Carol 都在排查“过去一小时内 API 响应时间下降了 3 倍”时，她们会收到相同的技术发现，但呈现方式完全不同。

Alice 收到技术分析：

```
memory_client.retrieve_user_preferences(user_id="Alice")
# Returns: {"investigation_style": "detailed_systematic_analysis", "reports": "technical_exposition_with_troubleshooting_steps"}
```

Carol 收到执行摘要：

```
memory_client.retrieve_user_preferences(user_id="Carol") 
# Returns: {"investigation_style": "business_impact_focused","reports": "executive_summary_without_technical_details"}
```

## 为 SRE agent 添加可观测性

为部署在 Amazon Bedrock AgentCore Runtime 上的 SRE agent 添加可观测性，使用 Amazon Bedrock AgentCore Observability 原语即可轻松完成。这可以通过 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch) 提供指标、追踪和日志的全面监控。设置可观测性需要三个步骤：

- 在你的 pyproject.toml 中添加 OpenTelemetry 包：`dependencies = [ # ... other dependencies ... "opentelemetry-instrumentation-langchain", "aws-opentelemetry-distro~=0.10.1", ]`
- [为你的 agent 配置可观测性](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-configure.html)，以在 CloudWatch 中启用指标。
- 使用 opentelemetry-instrument 工具启动容器，以自动为你的应用注入监测。

以下命令被添加到 SRE agent 的 Dockerfile 中：

```
# Run application with OpenTelemetry instrumentation 
CMD ["uv", "run", "opentelemetry-instrument", "uvicorn", "sre_agent.agent_runtime:app", "--host", "0.0.0.0", "--port", "8080"]
```

如下图所示，启用可观测性后，你可以获得对以下方面的可见性：

- LLM 调用指标 – 各 agent 的 token 用量、延迟和模型表现
- 工具执行追踪 – 每次 MCP 工具调用的耗时和成功率
- Memory 操作 – 检索模式和存储效率
- 端到端请求追踪 – 从用户查询到最终响应的完整请求流

## 使用 Amazon Bedrock AgentCore Gateway 将 API 转换为 MCP 工具

Amazon Bedrock AgentCore Gateway 通过把现有后端 API 转换为 agent 框架可消费的 MCP 工具，展示了协议标准化的威力。这一转换无缝完成，只需要 OpenAPI 规范。

### 上传 OpenAPI 规范

网关流程从把你的现有 API 规范上传到 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）开始。[create_gateway.sh](https://github.com/awslabs/agentcore-samples/blob/main/02-use-cases/01-conversational-agents/SRE-agent/gateway/create_gateway.sh) 脚本会自动把四份 API 规范（Kubernetes、Logs、Metrics 和 Runbooks）上传到你配置的 S3 存储桶，并带有适当的元数据和内容类型。这些规范将用于在网关中创建 API 端点目标。

### 创建身份提供程序和网关

认证通过 Amazon Bedrock AgentCore Identity 无缝处理。[main.py](https://github.com/awslabs/agentcore-samples/blob/main/02-use-cases/01-conversational-agents/SRE-agent/gateway/main.py) 脚本同时创建凭证提供程序和网关：

```
# Create AgentCore Gateway with JWT authorization
def create_gateway(
    client: Any,
    gateway_name: str,
    role_arn: str,
    discovery_url: str,
    allowed_clients: list = None,
    description: str = "AgentCore Gateway created via SDK",
    search_type: str = "SEMANTIC",
    protocol_version: str = "2025-03-26",
) -> Dict[str, Any]:
    
    # Build auth config for Cognito
    auth_config = {"customJWTAuthorizer": {"discoveryUrl": discovery_url}}
    if allowed_clients:
        auth_config["customJWTAuthorizer"]["allowedClients"] = allowed_clients
    
    protocol_configuration = {
        "mcp": {"searchType": search_type, "supportedVersions": [protocol_version]}
    }

    response = client.create_gateway(
        name=gateway_name,
        roleArn=role_arn,
        protocolType="MCP",
        authorizerType="CUSTOM_JWT",
        authorizerConfiguration=auth_config,
        protocolConfiguration=protocol_configuration,
        description=description,
        exceptionLevel='DEBUG'
    )
    return response
```

### 使用凭证提供程序部署 API 端点目标

每个 API 都通过网关成为一个 MCP 目标。方案自动处理凭证管理：

```
def create_api_endpoint_target(
    client: Any,
    gateway_id: str,
    s3_uri: str,
    provider_arn: str,
    target_name_prefix: str = "open",
    description: str = "API Endpoint Target for OpenAPI schema",
) -> Dict[str, Any]:
    
    api_target_config = {"mcp": {"openApiSchema": {"s3": {"uri": s3_uri}}}}

    # API key credential provider configuration
    credential_config = {
        "credentialProviderType": "API_KEY",
        "credentialProvider": {
            "apiKeyCredentialProvider": {
                "providerArn": provider_arn,
                "credentialLocation": "HEADER",
                "credentialParameterName": "X-API-KEY",
            }
        },
    }
    
    response = client.create_gateway_target(
        gatewayIdentifier=gateway_id,
        name=target_name_prefix,
        description=description,
        targetConfiguration=api_target_config,
        credentialProviderConfigurations=[credential_config],
    )
    return response
```

### 通用 agent 框架兼容性

这个符合 MCP 标准的网关现在可以配置为 MCP client 的 Streamable-HTTP server，包括 AWS Strands（Amazon 的 agent 开发框架）、LangGraph（我们 SRE agent 实现中使用的框架）以及 CrewAI（一个多 agent 协作框架）。

这种方式的优势在于现有 API 无需修改，只需要 OpenAPI 规范。Amazon Bedrock AgentCore Gateway 负责以下事项：

- **协议转换** – 在 REST API 与 MCP 之间
- **认证** – JWT token 校验与凭证注入
- **安全** – TLS 终止与访问控制
- **标准化** – 统一工具命名与参数处理

这意味着你可以拿现有的基础设施 API（Kubernetes、监控、日志、文档），通过单一、安全、标准化的接口，立刻让支持 MCP 的 AI agent 框架使用它们。

## 使用 Amazon Bedrock AgentCore Memory 实现持久智能

Amazon Bedrock AgentCore Gateway 提供无缝的 API 访问，而 Amazon Bedrock AgentCore Memory 则把 SRE agent 从无状态系统转变为智能的学习型助手。memory 的实现展示了如何用寥寥几行代码实现复杂的个性化和跨会话知识留存。

### 初始化 memory 策略

SRE agent 的 memory 组件构建在 Amazon Bedrock AgentCore Memory 基于事件的模型之上，并带有自动命名空间路由。在初始化期间，方案会以特定的命名空间模式创建三种 memory 策略：

```
from sre_agent.memory.client import SREMemoryClient
from sre_agent.memory.strategies import create_memory_strategies

# Initialize memory client
memory_client = SREMemoryClient(
    memory_name="sre_agent_memory",
    region="us-east-1"
)

# Create three specialized memory strategies
strategies = create_memory_strategies()
for strategy in strategies:
    memory_client.create_strategy(strategy)
```

这三种策略各自服务于不同的目的：

- **用户偏好（/sre/users/{user_id}/preferences）** – 个人排查风格与沟通偏好
- **基础设施知识：/sre/infrastructure/{user_id}/{session_id}** – 跨多次排查累积的领域专业知识
- **排查摘要：/sre/investigations/{user_id}/{session_id}** – 历史事故模式与处置方式

### 加载用户 persona 与偏好

该方案预配置了若干用户 persona，用于演示个性化排查。[manage_memories.py](https://github.com/awslabs/agentcore-samples/blob/main/02-use-cases/01-conversational-agents/SRE-agent/scripts/manage_memories.py) 脚本负责加载这些 persona：

```
# Load Alice - Technical SRE Engineer
alice_preferences = {
    "investigation_style": "detailed_systematic_analysis",
    "communication": ["#alice-alerts", "#sre-team"],
    "escalation": {"contact": "alice.manager@company.com", "threshold": "15min"},
    "reports": "technical_exposition_with_troubleshooting_steps",
    "timezone": "UTC"
}

# Load Carol - Executive/Director
carol_preferences = {
    "investigation_style": "business_impact_focused",
    "communication": ["#carol-executive", "#strategic-alerts"],
    "escalation": {"contact": "carol.director@company.com", "threshold": "5min"},
    "reports": "executive_summary_without_technical_details",
    "timezone": "EST"
}

# Store preferences using memory client
memory_client.store_user_preference("Alice", alice_preferences)
memory_client.store_user_preference("Carol", carol_preferences)
```

### 自动命名空间路由的实战

Amazon Bedrock AgentCore Memory 的威力在于其自动命名空间路由。当 SRE agent 创建事件时，它只需提供 actor_id，Amazon Bedrock AgentCore Memory 会自动判断该事件属于哪些命名空间：

```
# During investigation, the supervisor agent stores context
memory_client.create_event(
    memory_id="sre_agent_memory-abc123",
```

## 使用 Amazon Bedrock AgentCore Runtime 部署到生产环境

Amazon Bedrock AgentCore 让把现有 agent 部署到生产环境变得简单。该过程包含三个关键步骤：把 agent 容器化、部署到 Amazon Bedrock AgentCore Runtime，以及调用已部署的 agent。

### 将 agent 容器化

Amazon Bedrock AgentCore Runtime 要求 ARM64 容器。以下代码展示了完整的 [Dockerfile](https://github.com/awslabs/agentcore-samples/blob/main/02-use-cases/01-conversational-agents/SRE-agent/Dockerfile)：

```
# Use uv's ARM64 Python base image
FROM --platform=linux/arm64 ghcr.io/astral-sh/uv:python3.12-bookworm-slim

WORKDIR /app

# Copy uv files
COPY pyproject.toml uv.lock ./

# Install dependencies
RUN uv sync --frozen --no-dev

# Copy SRE agent module
COPY sre_agent/ ./sre_agent/

# Set environment variables
# Note: Set DEBUG=true to enable debug logging and traces
ENV PYTHONPATH="/app" \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

# Expose port
EXPOSE 8080

# Run application with OpenTelemetry instrumentation
CMD ["uv", "run", "opentelemetry-instrument", "uvicorn", "sre_agent.agent_runtime:app", "--host", "0.0.0.0", "--port", "8080"]
```

现有 agent 只需一个 FastAPI 包装器（agent_runtime:app）即可与 Amazon Bedrock AgentCore 兼容，我们再添加 opentelemetry-instrument 以通过 Amazon Bedrock AgentCore 启用可观测性。

### 部署到 Amazon Bedrock AgentCore Runtime

使用 [deploy_agent_runtime.py](https://github.com/awslabs/agentcore-samples/blob/main/02-use-cases/01-conversational-agents/SRE-agent/deployment/deploy_agent_runtime.py) 脚本，部署到 Amazon Bedrock AgentCore Runtime 非常简单：

```
import boto3

# Create AgentCore client
client = boto3.client('bedrock-agentcore', region_name=region)

# Environment variables for your agent
env_vars = {
    'GATEWAY_ACCESS_TOKEN': gateway_access_token,
    'LLM_PROVIDER': llm_provider,
    'ANTHROPIC_API_KEY': anthropic_api_key  # if using Anthropic
}

# Deploy container to AgentCore Runtime
response = client.create_agent_runtime(
    agentRuntimeName=runtime_name,
    agentRuntimeArtifact={
        'containerConfiguration': {
            'containerUri': container_uri  # Your ECR container URI
        }
    },
    networkConfiguration={"networkMode": "PUBLIC"},
    roleArn=role_arn,
    environmentVariables=env_vars
)

print(f"Agent Runtime ARN: {response['agentRuntimeArn']}")
```

Amazon Bedrock AgentCore 会自动处理基础设施、扩缩容和会话管理。

### 调用已部署的 agent

使用 [invoke_agent_runtime.py](https://github.com/awslabs/agentcore-samples/blob/main/02-use-cases/01-conversational-agents/SRE-agent/deployment/invoke_agent_runtime.py) 调用已部署的 agent 同样简单：

```
# Prepare your query with user_id and session_id for memory personalization
payload = json.dumps({
    "input": {
        "prompt": "API response times have degraded 3x in the last hour",
        "user_id": "Alice",  # User for personalized investigation
        "session_id": "investigation-20250127-123456"  # Session for context
    }
})

# Invoke the deployed agent
response = agent_core_client.invoke_agent_runtime(
    agentRuntimeArn=runtime_arn,
    runtimeSessionId=session_id,
    payload=payload,
    qualifier="DEFAULT"
)

# Get the response
response_data = json.loads(response['response'].read())
print(response_data)  # Full response includes output with agent's investigation
```

### Amazon Bedrock AgentCore Runtime 的关键优势

Amazon Bedrock AgentCore Runtime 提供以下关键优势：

- **零基础设施管理** – 无需配置服务器、负载均衡器或扩缩容
- **内置会话隔离** – 每个对话都完全隔离
- **AWS IAM 集成** – 无需自定义认证即可实现安全访问控制
- **自动扩缩容** – 可从零扩展到数千个并发会话

完整的部署流程，包括构建容器和处理 AWS 权限，记录在[部署指南](https://github.com/awslabs/agentcore-samples/blob/main/02-use-cases/01-conversational-agents/SRE-agent/docs/deployment-guide.md)中。

## 真实用例

我们来看 SRE agent 如何在一次真实排查中处理常见的事故响应场景。

面对生产问题时，你可以用自然语言查询系统。方案使用 Amazon Bedrock AgentCore Memory 根据你的角色和偏好对排查进行个性化：

```
export USER_ID=Alice
sre-agent --prompt "API response times have degraded 3x in the last hour"
```

supervisor 从 memory 中检索 Alice 的偏好（详细的系统分析风格），并针对她作为技术型 SRE 的角色制定排查计划：

```
Investigation Plan
1. Use metrics_agent to analyze API performance metrics including response times, error rates, and resource utilization to identify the extent and pattern of slowdown
2. Use logs_agent to examine application logs for errors related to slow API responses, focusing on database connection issues and memory errors
3. Use kubernetes_agent to check pod status and resource constraints, especially for web-service and database pods, looking for CrashLoopBackOff states and missing ConfigMaps
Complexity: Simple
Auto-execute: Yes
Agents involved: Metrics Agent, Logs Agent, Kubernetes Agent
```

各 agent 按照计划依次排查，各自贡献其专业化分析。方案随后把这些发现汇总为一份全面的执行摘要：

```
Executive Summary
Key Insights
- Root Cause: Database service failure due to missing ConfigMap 'database-config' in production namespace, causing database pod to crash repeatedly
- Impact: Severe performance degradation with API response times increased from 150ms to 5000ms (33x slower)
- Severity: High - Database unavailability, memory exhaustion (100%), and CPU saturation (95%) causing 75% error rate
Next Steps
1. Immediate (< 1 hour): Create/update ConfigMap 'database-config' in production namespace and restart database pod
2. Short-term (< 24 hours): 
   - Fix permissions on '/var/lib/postgresql/data' directory
   - Increase Java heap space for web-service to address OutOfMemoryErrors
   - Optimize UserService.loadAllUsers method causing memory issues
3. Long-term (< 1 week): 
   - Implement resource monitoring with alerts for CPU (>80%), memory (>90%)
   - Optimize slow database queries, particularly "SELECT * FROM users WHERE status='active'"
   - Scale up resources or implement autoscaling for web-service
Critical Alerts
- Database pod (database-pod-7b9c4d8f2a-x5m1q) in CrashLoopBackOff state
- Web-service experiencing OutOfMemoryErrors in UserService.loadAllUsers(UserService.java:45)
- Node-3 experiencing memory pressure (>85% usage)
- Web-app-deployment showing readiness probe failures with 503 errors
Troubleshooting Steps
1. Verify ConfigMap status: `kubectl get configmap database-config -n production`
2. Check database pod logs: `kubectl logs database-pod-7b9c4d8f2a-x5m1q -n production`
3. Create/update ConfigMap: `kubectl create configmap database-config --from-file=database.conf -n production`
4. Fix data directory permissions: `kubectl exec database-pod-7b9c4d8f2a-x5m1q -n production -- chmod -R 700 /var/lib/postgresql/data`
5. Restart database pod: `kubectl delete pod database-pod-7b9c4d8f2a-x5m1q -n production`
```

这次排查展示了 Amazon Bedrock AgentCore 各原语如何协同工作：

- **Amazon Bedrock AgentCore Gateway** – 通过 MCP 工具提供对基础设施 API 的安全访问
- **Amazon Bedrock AgentCore Identity** – 处理入站和出站认证
- **Amazon Bedrock AgentCore Runtime** – 承载多 agent 方案并自动扩缩容
- **Amazon Bedrock AgentCore Memory** – 个性化 Alice 的体验，并为未来事故存储排查知识
- **Amazon Bedrock AgentCore Observability** – 在 CloudWatch 中捕获详细的指标和追踪，用于监控和调试

SRE agent 展示了智能的 agent 编排：supervisor 依据排查计划把工作路由给专家。方案的 memory 能力确保每次排查都积累组织知识，并依据用户角色和偏好提供个性化体验。

这次排查体现了多项关键能力：

- **多来源关联** – 它把数据库配置问题与 API 性能下降联系起来
- **顺序排查** – agent 按照排查计划系统性地推进，同时提供实时更新
- **来源标注** – 发现中附带具体的工具和数据来源
- **可执行洞察** – 它提供清晰的事件时间线和按优先级排序的恢复步骤
- **级联故障检测** – 它可以帮助展示一次故障如何在整个系统中传播

## 业务影响

实施 AI 驱动 SRE 协助的组织报告称关键运营指标有显著改善。此前需要 30–45 分钟的初步排查，现在可以在 5–10 分钟内完成，使 SRE 在深入细致分析之前就获得全面的上下文。排查时间的这一大幅缩短直接转化为更快的事故解决和更短的停机时间。该方案改善了 SRE 与基础设施交互的方式。工程师不再需要在多个仪表板和工具之间穿梭，而是可以用自然语言提问，并从相关数据源获得汇总后的洞察。这种上下文切换的减少使团队在关键事故期间能够保持专注，也降低了排查过程中的认知负担。也许最重要的是，该方案在团队内部普及了知识。所有团队成员都能获得同样全面的排查方法，减少了对口口相传的部落知识和值班负担的依赖。方案提供的一致方法论确保排查方式在团队成员和事故类型之间保持统一，从而提升整体可靠性，并降低遗漏证据的可能性。

自动生成的排查报告为事故后复盘提供了有价值的文档，帮助团队从每次事故中学习，随着时间推移积累组织知识。此外，该方案还延伸了现有的 AWS 基础设施投资，与 Amazon CloudWatch、[AWS Systems Manager](https://aws.amazon.com/systems-manager/) 和其他 AWS 运营工具协同工作，提供统一的运营智能系统。
