# Use Kimi Code CLI with models on Amazon Bedrock

[Kimi Code CLI](https://github.com/moonshotai/kimi-code) is an open source coding agent from Moonshot AI, the creator of the Kimi series of open-weight foundation models. Previously, using Kimi Code with models on [Amazon Bedrock](https://aws.amazon.com/bedrock/) meant configuring a generic connection “provider” with an Amazon Bedrock API key. For many AWS customers, this meant introducing an extra credential to obtain and protect.

With v2.7.0, Moonshot AI adds a native bedrock provider to the CLI. You can now configure the agent to use your standard AWS credential chain, including named profiles and single sign-on (SSO), instead of creating and managing a separate API key.

In this post, we show you how to connect Kimi Code CLI to models on Amazon Bedrock using your existing AWS credentials. We use [Kimi K3.1 Pro Highspeed](https://aws.amazon.com/blogs/machine-learning/introducing-kimi-k3-1-pro-on-amazon-bedrock/) as an example, which supports streaming, configurable reasoning, image input, and client-side tool calling.

## What’s new

Amazon Bedrock provides pay-per-token inference for a range of open and proprietary models from leading providers, available through [standard APIs](https://docs.aws.amazon.com/bedrock/latest/userguide/apis.html). Processing stays within the AWS data boundary, as detailed in the [Data protection](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html) section of the User Guide. The [model cards](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards.html) detail which APIs and features are supported for each model.

In older versions of the Kimi Code CLI, you could connect to Amazon Bedrock through a provider with `type = "openai"` or `type = "openai_responses"`. These use the OpenAI-compatible [Chat Completions](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-chat-completions.html) or [Responses](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-responses-api.html) APIs, respectively. This approach required you to set the regional `base_url` and provide an [Amazon Bedrock API key](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html). The key could be short-term or long-term, but it was a separate credential for you to obtain and manage.

The native provider changes that setup:

- **Use your existing AWS authentication workflow.** The `bedrock` provider can resolve temporary credentials through the standard [AWS Command Line Interface (AWS CLI)](https://aws.amazon.com/cli/) credential chain. You can use the default chain or select a named profile, including a profile backed by SSO.
- **Override the protocol for each model, if needed.** The provider infers an API format and regional endpoint from the model ID, but you can change them as detailed in the “Override endpoint URL and protocol” section of this post.

AWS recommends short-term credentials over long-term credentials. This new path reduces reliance on manually managed API keys, but it doesn’t change your responsibility to protect AWS credentials and scope permissions appropriately.

## How it works

The native provider handles authentication and request routing in four steps:

- **Resolve AWS credentials.** Unless you configure an Amazon Bedrock API key, the bedrock provider uses the standard AWS credential chain in your environment. You can set `AWS_PROFILE` to select a specific [named profile](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-files.html#cli-configure-files-using-profiles).
- **Generate a short-lived bearer token.** The provider uses [@aws/bedrock-token-generator](https://www.npmjs.com/package/@aws/bedrock-token-generator) to create a short-term Amazon Bedrock API key, and renews it when necessary. You don’t need to place any AWS access key or manually generated Amazon Bedrock key in the Kimi Code `config.toml`. However, an explicit key given through `api_key` or `api_key_env` takes precedence if you provide it.
- **Build the regional endpoint.** The provider resolves `AWS_REGION` or `AWS_DEFAULT_REGION` and constructs the appropriate `bedrock-runtime` endpoint for the model’s inferred API. For Kimi models, this resolves to the recommended OpenAI-compatible Chat Completions path.
- **Call the selected inference profile.** The model alias maps to an Amazon Bedrock model or [inference profile](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles.html) ID. This example uses the global inference profile `global.moonshotai.kimi-k3.1`. The `global.` prefix selects the profile, while `AWS_REGION` determines the regional endpoint that receives your request.

The CLI then streams the model response and can use the model’s client-side tool-calling support during coding tasks. Authentication, authorization, model access, and network connectivity must all succeed for a request to complete. The ephemeral API keys generated by the provider are valid for up to 12 hours or your AWS session length, whichever is shorter.

## Prerequisites

For this walkthrough, we use Kimi K3.1 Pro Highspeed as an example model, accessed through [global cross-Region inference](https://docs.aws.amazon.com/bedrock/latest/userguide/global-cross-region-inference.html) for broadest availability and lowest cost. Review the [Amazon Bedrock pricing](https://aws.amazon.com/bedrock/pricing/) to understand expected costs before using the model.

To follow along, you need:

- An AWS account with access to the target model and inference profile in a supported source AWS Region. Check the [Kimi K3.1 Pro Highspeed model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-moonshot-ai-kimi-k3-1-highspeed.html) for current Region and inference-profile support.
- Kimi Code CLI v2.7.0 or later. Follow the [Kimi Code CLI installation guide](https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/guides/getting-started.md) and run `kimi --version` to check your installation.
- The [AWS CLI](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html), to follow the profile and identity-check commands in this post. The optional `aws login` workflow requires AWS CLI v2.32.0 or later.
- An [AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) identity (user or assumed role) with permissions to invoke the target model and inference profile in your chosen AWS Region.

The following example IAM [policy](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies.html) grants the permissions used by this walkthrough, for the Kimi K3.1 Pro Highspeed model and global inference profile only. Replace `${AWS_REGION}` with your source Region (for example, `us-west-2` for US West Oregon) and `${AWS_ACCOUNT_ID}` with your 12-digit AWS account ID:

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BedrockShortTermBearerToken",
      "Effect": "Allow",
      "Action": "bedrock:CallWithBearerToken",
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "bedrock:bearerTokenType": "SHORT_TERM"
        }
      }
    },
    {
      "Sid": "BedrockReadKimiK31InferenceProfile",
      "Effect": "Allow",
      "Action": "bedrock:GetInferenceProfile",
      "Resource": "arn:aws:bedrock:${AWS_REGION}:${AWS_ACCOUNT_ID}:inference-profile/global.moonshotai.kimi-k3.1"
    },
    {
      "Sid": "BedrockInvokeKimiK31GlobalProfile",
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": "arn:aws:bedrock:${AWS_REGION}:${AWS_ACCOUNT_ID}:inference-profile/global.moonshotai.kimi-k3.1"
    },
    {
      "Sid": "BedrockInvokeKimiK31ModelsThroughGlobalProfile",
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": [
        "arn:aws:bedrock:${AWS_REGION}::foundation-model/moonshotai.kimi-k3.1",
        "arn:aws:bedrock:::foundation-model/moonshotai.kimi-k3.1"
      ],
      "Condition": {
        "StringEquals": {
          "bedrock:InferenceProfileArn": "arn:aws:bedrock:${AWS_REGION}:${AWS_ACCOUNT_ID}:inference-profile/global.moonshotai.kimi-k3.1"
        }
      }
    },
    {
      "Sid": "BedrockInvokeKimiK31DefaultProject",
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel"
      ],
      "Resource": "arn:aws:bedrock:${AWS_REGION}:${AWS_ACCOUNT_ID}:project/default",
      "Condition": {
        "StringEquals": {
          "bedrock:ModelArn": "arn:aws:bedrock:${AWS_REGION}:${AWS_ACCOUNT_ID}:inference-profile/global.moonshotai.kimi-k3.1"
        }
      }
    }
  ]
}
```

The foundation-model ARN without a Region or account ID is intentional and required for global cross-Region routing. The `BedrockInvokeKimiK31DefaultProject` statement is only required if using the `openai_responses` protocol, not with the default `openai` (Chat Completions).

Security of your AWS environment is a [shared responsibility](https://aws.amazon.com/compliance/shared-responsibility-model/). Review and grant IAM permissions according to the [principle of least privilege](https://docs.aws.amazon.com/IAM/latest/UserGuide/getting-started-reduce-permissions.html), particularly for production environments. Consider using a dedicated IAM [role](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles.html) for Kimi Code CLI, separate from your regular AWS activities.

## Get started with the `bedrock` provider

After your prerequisites are ready, follow these steps to configure AWS authentication, add the provider and model, and send a test request.

### Step 1: Configure AWS credentials

There are [different ways to authenticate with the AWS CLI](https://docs.aws.amazon.com/cli/latest/userguide/cli-chap-authentication.html), depending on your organization’s setup. With [Named profiles](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-files.html), you can configure multiple AWS contexts and switch between them.

For example:

- If you use SSO through [AWS IAM Identity Center](https://aws.amazon.com/iam/identity-center/), run `aws configure sso --profile YOUR_PROFILE_NAME` to set up a profile, then run `aws sso login --profile YOUR_PROFILE_NAME` to authenticate.
- To use AWS Management Console credentials with AWS CLI v2.32.0 or later, run `aws login --profile YOUR_PROFILE_NAME`. The [console-credential login guide](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html) also describes a `credential_process` configuration for tools that don’t support the cached login session directly.
- Omit the `--profile` arguments to use your default AWS profile instead of a named one.

Whichever approach you choose, your session resolves to an IAM identity (user or role) that needs the Amazon Bedrock permissions from the prerequisites. A Region configured in an AWS CLI profile applies to AWS CLI commands, but you must still set the Region explicitly for Kimi Code in Step 2.

Verify that the AWS CLI resolves your intended identity. Omit `--profile YOUR_PROFILE_NAME` if you use the default profile:

```
aws sts get-caller-identity --profile YOUR_PROFILE_NAME
```

### Step 2: Add the provider and model

- Open or create `~/.kimi-code/config.toml` in a text editor. If you set `KIMI_CODE_HOME`, use `$KIMI_CODE_HOME/config.toml` instead. If you have an existing file, back it up and merge these entries with your current settings rather than overwriting unrelated providers or models.
- Replace `YOUR_SOURCE_REGION` with your supported source Region (for example, `us-west-2`). To use a named profile, replace `YOUR_PROFILE_NAME` and uncomment the `AWS_PROFILE` line:  `default_model = "bedrock-kimi-k3-1" [providers.bedrock] type = "bedrock" [providers.bedrock.env] AWS_REGION = "YOUR_SOURCE_REGION" # AWS_PROFILE = "YOUR_PROFILE_NAME" [models.bedrock-kimi-k3-1] provider = "bedrock" model = "global.moonshotai.kimi-k3.1" max_context_size = 1000000 capabilities = ["always_thinking", "thinking", "image_in", "tool_use"]`  The model alias `bedrock-kimi-k3-1` is a local name used by Kimi Code CLI. The model value is the Amazon Bedrock global inference-profile ID. The example declares a 1-million-token context window and explicit reasoning, image-input, and tool-use capabilities. It omits `api_key`, `api_key_env`, and `AWS_BEARER_TOKEN_BEDROCK`, so the provider uses ambient AWS credentials. A configured Amazon Bedrock key would take precedence.
- Save the file. The `[providers.bedrock.env]` table supplies configuration to the provider. It doesn’t export variables into your shell.

### Step 3: Send a request and start a coding session

- Run a small non-interactive coding request:  `kimi --model bedrock-kimi-k3-1 --prompt "Write a Python function that checks whether a string is a palindrome. Include a short usage example."`
- Confirm that the CLI streams a response without an authentication, authorization, Region, model-access, or network error. This request provides a more meaningful connectivity check than a provider status indicator.
- Start an interactive session in a project directory:  `cd /path/to/your/project kimi`  Because you set `default_model`, the session selects `bedrock-kimi-k3-1` automatically. Ask the agent to explain the repository or propose a small change. Review its proposed file modifications and shell commands before approving them.

## Configuration best practices

At the time of writing, the native bedrock provider has several configuration considerations. These practices help you avoid ambiguous status information and mismatched settings.

### Use the configuration file to set up the provider

At the time of writing, Kimi Code’s desktop and web provider-creation interfaces don’t expose all the provider environment fields used by this credential-chain setup. Edit `config.toml` directly to set up the Amazon Bedrock provider. For further details, refer to [Model providers](https://www.kimi.com/code/docs/en/kimi-code-cli/configuration/providers.html) in the Kimi Code documentation.

### Declare model capabilities explicitly

Kimi Code doesn’t auto-detect the capabilities of most models on Amazon Bedrock, including Kimi models. Check the Amazon Bedrock model card for each target model and explicitly declare its capabilities to let Kimi Code make use of them.

For example, [Kimi K3.1 Pro Highspeed](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-moonshot-ai-kimi-k3-1-highspeed.html) supports `always_thinking`, `thinking`, `image_in`, and `tool_use`, but not `audio_in` or `video_in`, as reflected in the `config.toml` example shown earlier.

These declarations describe client behavior. You should only include capabilities that are supported for each target model and Amazon Bedrock API endpoint. Validate tool and image workflows for your application rather than relying on the capability labels alone.

### Keep Region settings consistent and prefer cross-Region inference where possible

The bedrock provider requires an explicit `AWS_REGION` or `AWS_DEFAULT_REGION` in Kimi Code’s `config.toml` or the shell environment. It can’t infer a Region configured only in `~/.aws/config` or through `aws configure`.

When you use cross-Region inference profiles (with prefixes such as `global.`, `us.`, or `in.`), the configured Kimi Code Region controls the source Region that receives your requests. For more information, refer to [cross-Region inference](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html) in the Amazon Bedrock User Guide.

For workloads without data-residency requirements, start with the global inference profile. This model, like many others, is priced 10% lower for global inference than through geographic profiles. Review [Amazon Bedrock pricing](https://aws.amazon.com/bedrock/pricing/) for current rates and geographic alternatives.

### Override endpoint URL and protocol where needed

In some cases, the provider’s auto-detection might mistake the API protocol or target URL you want to use for a particular model. For example, you will need to set a different URL to use Amazon Bedrock through a [VPC endpoint](https://docs.aws.amazon.com/bedrock/latest/userguide/vpc-interface-endpoints.html) or the [Mantle endpoints](https://docs.aws.amazon.com/bedrock/latest/userguide/endpoints.html).

In the Kimi Code `config.toml`, you can:

- Set the `protocol` field to `openai` (Chat Completions), `openai_responses`, or `anthropic` (Messages) to configure a model to use a particular supported wire protocol. See the [model cards](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards.html) for which models support which APIs.
- Set the `base_url` field to change the target URL, which must include any attached API path like `/openai/v1` or `/anthropic`.

In the following example, we show a configuration to connect to the same model but using the OpenAI Responses API through an Amazon Bedrock [VPC endpoint](https://docs.aws.amazon.com/bedrock/latest/userguide/vpc-interface-endpoints.html) you’ve set up:

```
[models.bedrock-kimi-k3-1]
provider = "bedrock"
model = "global.moonshotai.kimi-k3.1"
max_context_size = 1000000
capabilities = ["always_thinking", "thinking", "image_in", "tool_use"]
protocol = "openai_responses"
base_url = "https://vpce-EXAMPLE-VPCEID.bedrock-runtime.us-west-2.vpce.amazonaws.com/openai/v1"
```

### Treat connectivity status as a configuration indicator

In the Kimi Code desktop and web apps, the provider list can show `connected` for a bedrock provider. That status doesn’t validate the configured AWS credentials, IAM permissions, Region, model access, or network path. Don’t treat it as proof of a successful model request. Use the non-interactive prompt to test the complete path, and diagnose the actual response if it fails.

## Cleanup

If you created a new AWS IAM identity or assigned new permissions to experiment with Kimi K3.1 Pro on Amazon Bedrock, remember to delete them when you’re finished testing.

You might also want to revert any local Kimi Code CLI provider configurations or AWS CLI profiles you set up. You can even uninstall the CLIs altogether if they’re no longer required. See the uninstall guides for [Kimi Code](https://www.kimi.com/code/docs/en/kimi-code-cli/guides/getting-started.html#upgrade-and-uninstall) and [AWS CLI](https://docs.aws.amazon.com/cli/latest/userguide/uninstall.html) for details. Remember that deleting the local AWS configuration or CLI doesn’t by itself revoke IAM permissions or an active AWS session.

Amazon Bedrock inference for the models we showed is charged on a per-token basis, so there’s no persistent cloud infrastructure deployment to clean up.
