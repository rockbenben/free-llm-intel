# AWS DevOps Agent 调查后自动修复

对于在 AWS 上运行生产工作负载的组织来说，缩短事件检测、调查和修复之间的时间是一个关键优先事项。当出现问题时，值班工程师通常需要快速诊断跨应用程序组件的问题，找出根本原因，并应用修复程序，通常是在半夜。

[AWS DevOps Agent](https://aws.amazon.com/devops-agent/) 是一种人工智能驱动的代理，可根据相关指标、日志和应用程序拓扑全天自动对事件进行分类，通过提供根本原因分析 (RCA) 和建议的解决措施来解决此优先级的第一部分。然而，为了保持控制并帮助防止意外更改，组织通常将其可观测代理（包括 AWS DevOps Agent）保持在观察和报告模式下，在该模式下，代理会诊断问题，但不会直接修改生产资源。在本文中，我们演示如何使用 [AWS Lambda Durable Functions](https://aws.amazon.com/lambda/lambda-durable-functions/)（AWS Lambda 的一项功能）、[Amazon EventBridge](https://aws.amazon.com/eventbridge/) 和 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 创建自动修复工作流程，以补充 AWS DevOps Agent 来完成问题解决步骤。此工作流程将调查摘要转换为预先验证的修复程序，准备进行单次批准操作，帮助您缩短解决问题的平均时间 (MTTR)，并将值班工程师从重复的诊断工作中解放出来。

## 解决方案概述

借助 [AWS Lambda Durable Functions](https://aws.amazon.com/lambda/lambda-durable-functions/)，您可以构建可运行长达一年的弹性多步骤应用程序和 AI 工作流程，而无需管理额外的基础设施或编写自定义状态管理和错误处理代码。这些功能会自动检查进度，在长时间运行的任务期间暂停执行，并从故障中恢复，同时在中断的情况下保持可靠的进度。

下图展示了该解决方案的架构。

图 1：AWS DevOps Agent 通过 Amazon EventBridge、AWS Lambda 和 Amazon Bedrock 进行调查的自动修复工作流程，在更改到达基础设施之前可选择人工批准

工作流程包括以下步骤：

- AWS DevOps Agent 完成事件调查并发出包含症状、发现结果和根本原因分析的事件。
- Amazon EventBridge 接收调查完成事件并使用调查内容触发“devops-agent-trigger”函数。
- Lambda 函数打包调查摘要并调用“devops-agent-remediation-durable”持久函数。
- 持久功能将调查上下文发送到 Amazon Bedrock，后者分析调查结果并寻找适用的补救措施。
- Amazon Bedrock 从经批准的 Lambda 函数的允许列表中识别并列出可用的修复工具：“devops-agent-lambda-tool”。
- Amazon Bedrock 根据调查结果和可用工具提出具体的补救措施。
- 对于只读操作，持久功能会自主运行修复工具。对于基础设施更改，工作流程将暂停并等待[人工批准](https://docs.aws.amazon.com/lambda/latest/dg/durable-examples.html#durable-examples-long-running)，然后再继续。
- 批准后，持久功能使用所选工具将修复操作应用于基础设施。

持久函数作为代理循环运行，迭代调用 Amazon Bedrock，执行批准的工具，并将结果反馈到对话中，直到修复完成。为了保持自动化操作的安全性和可审计性，编排器强制执行精心策划的修复工具白名单。每个工具都是专门构建的 Lambda 函数，用于执行特定的、范围明确的操作，例如读取 Lambda 函数配置或更新 AWS Identity and Access Management (IAM) 策略语句。 Amazon Bedrock 只能从该批准的集合中选择和调用工具，从而保持自动化操作的范围受到控制。该工作流程进一步区分只读操作和变异操作。只读工具自主运行，无需人工干预。会修改基础设施状态的突变操作会导致持久功能暂停执行并等待人工批准。这就是 AWS Lambda Durable Functions 提供的关键优势。函数 [checkpoints](https://docs.aws.amazon.com/durable-execution/#key-features) 会在不消耗计算资源的情况下暂停几分钟、几小时甚至几天，然后在收到批准信号后从停止的位置准确恢复。当值班工程师参与时，系统已经收集了相关配置，将根本原因与可用的补救措施相关联，并准备了一组预先验证的更改，以供一键批准。当前的实现使用批准或拒绝信号。由于回调接受任意 JSON 负载，因此您可以扩展批准以携带参数覆盖或审阅者观察结果。这些可以反馈到基岩对话中，以便在执行之前完善建议的补救措施。

在以下部分中，我们将逐步介绍实施细节，包括 Amazon EventBridge 规则配置和持久函数编排逻辑。然后，我们使用 [AWS 云开发套件](https://aws.amazon.com/cdk/) (AWS CDK) 部署解决方案。

## 先决条件

在部署此解决方案之前，请验证您是否满足以下先决条件：

- 安装并配置了 [AWS 命令行界面](https://aws.amazon.com/cli) (AWS CLI)。
- Python 3.14 或更高版本。
- 已安装 [AWS CDK](https://aws.amazon.com/cdk/)。
- 活跃的 [AWS DevOps Agent 空间](https://docs.aws.amazon.com/devopsagent/latest/userguide/getting-started-with-aws-devops-agent-creating-an-agent-space.html)。
- （可选）[Kiro](https://kiro.dev) 与 [Agent Toolkit for AWS](https://aws.amazon.com/products/developer-tools/agent-toolkit-for-aws/)。 Agent Toolkit 让 Kiro 通过具有基于 IAM 访问控制的托管 MCP 服务器安全地访问 AWS API。如果您使用 Kiro，则可以使用自然语言提示完成本文中的事件模拟、部署和清理步骤，而无需手动运行 CLI 命令。要进行设置，请将 AWS MCP 服务器添加到 `~/.kiro/settings/mcp.json` （[设置说明](https://aws.amazon.com/products/developer-tools/agent-toolkit-for-aws/#getting-started)）。该存储库包含一个 Kiro 规则和代理文件，可自动为 Kiro 提供项目上下文、部署顺序和安全约定。

### 模拟事件

为了演示端到端工作流程，我们模拟了一个常见场景：超过其配置超时的 Lambda 函数。这为 AWS DevOps Agent 提供了一个真实的事件来调查并启动修复工作流程。

为了将重点放在修复解决方案本身上，创建和调用此测试函数的步骤保留在[存储库](https://github.com/aws-samples/sample-automate-remediation-post-devops-agent-investigation.git)中。它包括一个即用型“devops-agent-timeout”函数以及用于部署该函数、调用该函数以及在 Amazon CloudWatch Logs 中确认超时错误的分步说明。有关完整演练，请参阅自述文件的[“模拟事件”部分](https://github.com/aws-samples/sample-automate-remediation-post-devops-agent-investigation#simulate-the-incident)。

该函数部署并至少产生一个超时错误后，您就可以开始使用 AWS DevOps Agent 进行调查了。

## 使用 AWS CDK 部署解决方案

完成以下步骤来部署剩余的解决方案资源：

**Kiro：** 如果您的 Kiro 已配置了 Agent Toolkit for AWS（请参阅先决条件），请在 Kiro 中打开克隆存储库并询问：“*设置 Python 环境并部署 CDK 堆栈。显示部署前将创建哪些资源。*”Kiro 从存储库中读取项目规则，设置虚拟环境，安装依赖项，并在部署前向您显示计划的资源。它在执行之前确认每个基础设施更改，遵循修复解决方案本身使用的相同人机循环模式。要手动部署，请按照以下步骤操作。

- 克隆 GitHub 上托管的 AWS CDK 代码：“$ git clone https://github.com/aws-samples/sample-automate-remediation-post-devops-agent-investigation.git”
- 导航到目录“sample-automate-remediation-post-devops-agent-investigation”：“$ cd Sample-automate-remediation-post-devops-agent-investigation”
- 引导AWS CDK。首次在特定 AWS [环境](https://docs.aws.amazon.com/cdk/v2/guide/environments.html)（AWS 账户和 AWS 区域的组合）中使用 AWS CDK 时需要执行此操作。  `$ cdk 引导程序`
- 部署堆栈：`$ cdk deploy`

AWS CDK 自动预置和配置以下资源：

- 三个 Lambda 函数：“devops-agent-trigger”。 `devops-agent-remediation-durable`。 `devops-agent-lambda-tool`。
- Amazon EventBridge 规则。

AWS CDK 使用最小权限原则和 AWS 安全最佳实践自动处理 IAM 权限。例如，Amazon EventBridge 被授予“devops-agent-trigger”函数的“lambda:InvokeFunction”权限。该堆栈向“devops-agent-trigger”函数授予“aidevops:ListJournalRecords”权限，以便它可以从 AWS DevOps Agent 日志中获取调查摘要。它还向“devops-agent-remediation-durable”函数授予“bedrock:InvokeModel”权限，以便它可以调用 Amazon Bedrock。

## 验证解决方案

部署修复堆栈并且“devops-agent-timeout”函数因超时错误而失败后，我们现在可以完成端到端工作流程。

### 使用 AWS DevOps Agent 开始调查

打开 [AWS DevOps Agent 控制台](https://console.aws.amazon.com/aidevops/)，导航到您的代理空间，然后询问：“*devops-agent-timeout 函数发生了什么？*”

图 2：从 AWS DevOps Agent 控制台开始调查

调查开始并需要几分钟才能完成。在此期间，AWS DevOps Agent 会自动关联 CloudWatch 指标、日志和函数的配置，以确定根本原因。

图 3：AWS DevOps Agent 在调查期间关联信号

调查完成后，AWS DevOps Agent 会提供根本原因分析，确定函数超时不足以满足工作负载的需要。

图 4：识别函数超时不足的根本原因分析

### 验证触发器Lambda执行

调查完成会向 Amazon EventBridge 发出*调查已完成*事件。

该规则会触发“devops-agent-trigger”Lambda 函数，该函数从 AWS DevOps Agent 日志中获取调查摘要。在“/aws/lambda/devops-agent-trigger”CloudWatch 日志组中，您可以看到发送到“devops-agent-remediation-durable”持久功能的解析摘要，包括症状、根本原因、促成原因和调查差距。

图 5：触发函数 CloudWatch 日志组中解析的调查摘要

### 监控持久函数的执行

导航到 [Lambda 控制台](https://console.aws.amazon.com/lambda/)，打开 `devops-agent-remediation-durable` 函数，然后选择 **持久执行** 选项卡。选择新的执行来检查其检查点步骤。

图 6：Lambda 控制台中的持久函数执行及其检查点步骤

持久协调器通过将调查上下文发送到 Amazon Bedrock 来开始其代理循环。在第一次 Bedrock 调用中，模型分析调查摘要并确定需要在提出修复之前检查当前的功能配置。它从白名单中选择“lambda_get_function_configuration”工具。由于这是只读操作，因此它可以自主运行，无需人工批准。步骤结果显示了“devops-agent-timeout”函数的当前配置，确认超时值为 3 秒。

图 7：返回当前 3 秒超时配置的只读工具调用

### Amazon Bedrock 提出补救措施

确认当前配置后，Amazon Bedrock 将进入下一个迭代。它认为 3 秒超时是失败的根本原因，并建议将其增加到 30 秒。 Amazon Bedrock 响应包含推理和工具调用：

由于“lambda_update_function_configuration”是一个变异操作，因此持久函数会暂停执行并等待人工批准。

## 清理

通过完成以下步骤清理您创建的资源：

**Kiro：** 如果您将 Kiro 与 Agent Toolkit for AWS 结合使用，请询问：*“从 DevOps Agent 修复演示中清理所有资源：销毁 CDK 堆栈，删除 devops-agent-timeout 测试函数、其 IAM 角色及其 CloudWatch 日志组。”* Kiro 按正确的顺序删除资源，在继续之前确认每个破坏性操作。要手动清理，请按照以下步骤操作。

- 删除AWS CDK资源：`$ cdk destroy`
- 手动删除模拟事件的 `devops-agent-timeout` 函数：`$ aws lambda delete-function --function-name devops-agent-timeout`
- 手动删除 `devops-agent-timeout` 函数的 IAM 角色和 CloudWatch 日志组： `$ aws iam detach-role-policy \ --role-name devops-agent-timeout-role \ --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole $ aws iam delete-role --role-name devops-agent-timeout-role $ aws 日志删除日志组 --log-group-name /aws/lambda/devops-agent-timeout`

## 结论

本文演示了如何通过将 Lambda Durable Functions、Amazon EventBridge 和 Bedrock 与 DevOps Agent 结合使用来自动执行问题修复。该解决方案继承了 AWS DevOps Agent 的不足，将调查摘要转化为可操作的修复步骤，并在人工参与的批准下运行。这种方法缩短了解决问题的平均时间，因为当值班工程师介入时，系统已经诊断出问题、收集当前配置并准备好可供批准的修复。安全仍然是设计的核心：许可名单限制 Amazon Bedrock 仅调用预先批准的工具，而人工审批门有助于防止未经明确授权的意外更改进入生产。该架构本质上也是可扩展的。添加新的修复功能仅需要对工具注册表进行配置更新，而不需要对协调器进行代码更改。而且，由于 AWS Lambda Durable Functions 在审批等待期间会暂停而不消耗计算资源，因此即使审批周期长达数小时或数天，该解决方案仍然具有成本效益。
