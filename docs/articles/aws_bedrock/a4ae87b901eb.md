# 在 AWS DevOps Agent 调查之后自动执行修复

对在 AWS 上运行生产工作负载的组织来说，缩短故障从检测、调查到修复之间的时间是一项关键的优先事项。一旦出问题，值班工程师往往需要快速横跨各个应用组件诊断问题、找到根因并实施修复，而且常常是在半夜。

[AWS DevOps Agent](https://aws.amazon.com/devops-agent/) 是一个 AI 驱动的智能体，全天基于关联起来的指标、日志和应用拓扑自主对故障做分诊，它解决了这项优先事项的前半部分：给出根因分析（RCA）以及用于解决问题的建议动作。但为了保住控制权、帮助防止意料之外的改动，组织通常会把可观测性智能体（包括 AWS DevOps Agent）保持在只观测、只报告的模式下——智能体诊断问题，但不直接改动生产资源。本文中我们演示如何组合使用 [AWS Lambda Durable Functions](https://aws.amazon.com/lambda/lambda-durable-functions/)（AWS Lambda 的一项能力）、[Amazon EventBridge](https://aws.amazon.com/eventbridge/) 和 [Amazon Bedrock](https://aws.amazon.com/bedrock/)，搭出一条与 AWS DevOps Agent 互补的自动修复工作流，把问题解决的这一步走完。这条工作流把调查摘要转成经过预校验、只等一次批准的修复方案，帮你缩短平均解决时间（MTTR），把值班工程师从重复的诊断工作中释放出来。

## 方案概览

借助 [AWS Lambda Durable Functions](https://aws.amazon.com/lambda/lambda-durable-functions/)，你可以构建有韧性的多步骤应用和 AI 工作流，它们能运行长达一年，而不需要你管理额外基础设施，也不用自己编写状态管理和错误处理代码。这类函数会自动为进度打检查点、在长时间运行的任务期间挂起执行，并在遭遇中断后从故障中恢复，同时保持进度可靠。

下图展示了方案架构。

图 1：从 AWS DevOps Agent 的调查出发，经 Amazon EventBridge、AWS Lambda 和 Amazon Bedrock 的自动修复工作流，在改动落到基础设施之前可选择是否经过人工审批

工作流由以下步骤组成：

- AWS DevOps Agent 完成一次故障调查，发出一个包含症状、发现和根因分析的事件。
- Amazon EventBridge 收到调查完成事件，用调查内容触发 `devops-agent-trigger` 函数。
- 该 Lambda 函数把调查摘要打包，调用 `devops-agent-remediation-durable` 这个 durable 函数。
- durable 函数把调查上下文发给 Amazon Bedrock，由 Amazon Bedrock 分析这些发现并寻找适用的修复手段。
- Amazon Bedrock 从一个经过筛选的允许列表（其中都是已批准的 Lambda 函数）中识别并列出可用的修复工具：`devops-agent-lambda-tool`。
- Amazon Bedrock 基于调查发现与可用工具提出具体的修复动作。
- 对于只读动作，durable 函数自主运行这些修复工具；对于基础设施改动，工作流会挂起并等待[人工审批](https://docs.aws.amazon.com/lambda/latest/dg/durable-examples.html#durable-examples-long-running)后再继续。
- 审批通过后，durable 函数用选定的工具把修复动作应用到基础设施上。

这个 durable 函数以一个[智能体循环](https://docs.aws.amazon.com/prescriptive-guidance/latest/agentic-ai-patterns/prompt-chaining-saga-patterns.html#agent-choreography)的形式运行：反复调用 Amazon Bedrock、执行已批准的工具，并把结果喂回对话，直到修复完成。为了让自动动作既安全又可审计，编排器强制执行一份经过筛选的修复工具允许列表。每个工具都是为特定用途构建的 Lambda 函数，只做一个具体、范围明确的动作，比如读取某个 Lambda 函数的配置，或更新一条 AWS Identity and Access Management (IAM) 策略语句。Amazon Bedrock 只能在这套已批准的集合里选择和调用工具，自动动作的范围因此始终受到控制。工作流还进一步区分只读操作和改动型操作：只读工具无需人工介入即可自主运行；会修改基础设施状态的改动型动作会让 durable 函数挂起执行，等待人工审批。这正是 AWS Lambda Durable Functions 提供关键优势的地方——函数为进度[打检查点](https://docs.aws.amazon.com/durable-execution/#key-features)，可以几分钟、几小时甚至几天地暂停而不消耗算力，收到审批信号后再从它停下的地方原样继续。等到值班工程师介入时，系统已经收集好相关配置、把根因和可用的修复动作对应起来，并准备出一批经过预校验、可以一键批准的改动。当前实现用的是批准或拒绝信号。由于回调接受任意 JSON 负载，你可以扩展批准所携带的内容，比如参数覆盖值或审阅者的意见，再把这些内容喂回 Bedrock 的对话，在执行之前进一步完善它提出的修复方案。

下面几节我们逐一走查实现细节，包括 Amazon EventBridge 规则配置和 durable 函数的编排逻辑，然后用 [AWS Cloud Development Kit](https://aws.amazon.com/cdk/) (AWS CDK) 部署这套方案。

## 前提条件

部署这套方案之前，请确认已满足以下前提条件：

- 已安装并配置好 [AWS Command Line Interface](https://aws.amazon.com/cli) (AWS CLI)。
- Python 3.14 或更高版本。
- 已安装 [AWS CDK](https://aws.amazon.com/cdk/)。
- 一个处于活动状态的 [AWS DevOps Agent 智能体空间](https://docs.aws.amazon.com/devopsagent/latest/userguide/getting-started-with-aws-devops-agent-creating-an-agent-space.html)。
- （可选）[Kiro](https://kiro.dev) 和 [Agent Toolkit for AWS](https://aws.amazon.com/products/developer-tools/agent-toolkit-for-aws/)。Agent Toolkit 通过一个托管的 MCP Server 和基于 IAM 的访问控制，让 Kiro 安全地访问 AWS API。如果你用 Kiro，本文中故障模拟、部署和清理这几步都可以用自然语言提示完成，不必手动执行 CLI 命令。配置方式是把 AWS MCP Server 加到 `~/.kiro/settings/mcp.json`（[设置说明](https://aws.amazon.com/products/developer-tools/agent-toolkit-for-aws/#getting-started)）。仓库里带有一个 Kiro 规则与 agents 文件，会自动把项目上下文、部署顺序和安全约定提供给 Kiro。

### 模拟故障

为了演示端到端的工作流，我们模拟一个常见场景：一个 Lambda 函数超出了它配置的超时时间。这样 AWS DevOps Agent 就有了一次真实的故障可供调查，修复工作流也随之启动。

为了把重点放在修复方案本身，创建和调用这个测试函数的步骤放在[仓库](https://github.com/aws-samples/sample-automate-remediation-post-devops-agent-investigation.git)里。仓库包含一个开箱即用的 `devops-agent-timeout` 函数，以及部署它、调用它、并在 Amazon CloudWatch Logs 中确认超时错误的分步说明。完整走查见 [README 中「模拟故障」一节](https://github.com/aws-samples/sample-automate-remediation-post-devops-agent-investigation#simulate-the-incident)。

函数部署完成并至少产生一次超时错误之后，你就可以用 AWS DevOps Agent 发起一次调查。

## 用 AWS CDK 部署方案

完成以下步骤来部署其余的方案资源：

**Kiro：** 如果你已经配置好带 Agent Toolkit for AWS 的 Kiro（见前提条件），在 Kiro 里打开克隆下来的仓库并提问：「*配置 Python 环境并部署 CDK stack。部署之前先把将要创建的资源展示给我看。*」Kiro 会读取仓库里的项目规则、搭建虚拟环境、安装依赖，并在部署之前把计划创建的资源展示给你。每执行一处基础设施改动之前它都会先确认，遵循的正是这套修复方案自身所用的人在回路模式。要手动部署，请按以下步骤操作。

- 克隆托管在 GitHub 上的 AWS CDK 代码：  `$ git clone https://github.com/aws-samples/sample-automate-remediation-post-devops-agent-investigation.git`
- 进入 `sample-automate-remediation-post-devops-agent-investigation` 目录：  `$ cd sample-automate-remediation-post-devops-agent-investigation`
- 为 AWS CDK 做 bootstrap。第一次在某个 AWS [环境](https://docs.aws.amazon.com/cdk/v2/guide/environments.html)（一个 AWS 账户与 AWS Region 的组合）中使用 AWS CDK 时这一步是必需的。  `$ cdk bootstrap`
- 部署 stack：  `$ cdk deploy`

AWS CDK 会自动预置并配置以下资源：

- 三个 Lambda 函数：  `devops-agent-trigger`. `devops-agent-remediation-durable`. `devops-agent-lambda-tool`.
- Amazon EventBridge 规则。

AWS CDK 会按照最小权限原则和 AWS 安全最佳实践自动处理 IAM 权限。例如，为 Amazon EventBridge 授予针对 `devops-agent-trigger` 函数的 `lambda:InvokeFunction` 权限。stack 把 `aidevops:ListJournalRecords` 权限授予 `devops-agent-trigger` 函数，让它能从 AWS DevOps Agent 的 journal 取回调查摘要；还把 `bedrock:InvokeModel` 权限授予 `devops-agent-remediation-durable` 函数，让它能调用 Amazon Bedrock。

## 验证方案

修复 stack 已经部署，`devops-agent-timeout` 函数正在因超时报错，现在我们可以走一遍端到端的工作流。

### 用 AWS DevOps Agent 发起一次调查

打开 [AWS DevOps Agent 控制台](https://console.aws.amazon.com/aidevops/)，进入你的智能体空间，然后提问：「*devops-agent-timeout 函数出什么问题了？*」

图 2：在 AWS DevOps Agent 控制台发起一次调查

调查随即开始，需要几分钟完成。这段时间里，AWS DevOps Agent 自主地把 CloudWatch 指标、日志和函数配置关联起来，以确定根因。

图 3：AWS DevOps Agent 在调查过程中关联各种信号

调查结束后，AWS DevOps Agent 给出根因分析，指出函数超时设置对该工作负载来说不够。

图 4：根因分析指出函数超时设置不足

### 确认触发函数的 Lambda 执行

调查完成时会向 Amazon EventBridge 发出一个 *Investigation Completed* 事件。

该规则触发 `devops-agent-trigger` Lambda 函数，由它从 AWS DevOps Agent 的 journal 取回调查摘要。在 `/aws/lambda/devops-agent-trigger` 这个 CloudWatch 日志组里，你可以看到发往 `devops-agent-remediation-durable` durable 函数的、已解析好的摘要，内容包括症状、根因、促成原因以及调查缺口。

图 5：触发函数 CloudWatch 日志组中已解析的调查摘要

### 监控 durable 函数的执行

进入 [Lambda 控制台](https://console.aws.amazon.com/lambda/)，打开 `devops-agent-remediation-durable` 函数，选择 **Durable executions** 标签页。再选择那条新的执行，查看它已打检查点的各个步骤。

图 6：Lambda 控制台中的 durable 函数执行及其已打检查点的步骤

durable 编排器把调查上下文发给 Amazon Bedrock，由此开启它的智能体循环。第一次调用 Bedrock 时，模型分析调查摘要，判断出在提出修复方案之前需要先查看当前的函数配置。它从允许列表里选择了 `lambda_get_function_configuration` 工具；由于这是只读操作，它自主运行，不需要人工审批。该步骤的结果显示 `devops-agent-timeout` 函数的当前配置，确认超时值为 3 秒。

图 7：只读工具调用返回当前 3 秒超时的配置

### Amazon Bedrock 提出修复方案

确认当前配置后，Amazon Bedrock 进入下一轮迭代。它推断 3 秒超时正是这些失败的根因，并提出把它提高到 30 秒。Amazon Bedrock 的响应同时包含推理过程和工具调用：

## 清理

按以下步骤清理你创建的资源：

**Kiro：** 如果你用的是带 Agent Toolkit for AWS 的 Kiro，可以这样要求：「*清理 DevOps Agent 修复演示产生的所有资源：销毁 CDK stack，删除 devops-agent-timeout 测试函数、它的 IAM 角色和它的 CloudWatch 日志组。*」Kiro 会按正确的顺序移除资源，每执行一个破坏性动作之前都先确认。要手动清理，请按以下步骤操作。

- 删除 AWS CDK 资源：  `$ cdk destroy`
- 手动删除用于模拟故障的 `devops-agent-timeout` 函数：  `$ aws lambda delete-function --function-name devops-agent-timeout`
- 手动删除 `devops-agent-timeout` 函数的 IAM 角色和 CloudWatch 日志组：  `$ aws iam detach-role-policy \ --role-name devops-agent-timeout-role \ --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole $ aws iam delete-role --role-name devops-agent-timeout-role $ aws logs delete-log-group --log-group-name /aws/lambda/devops-agent-timeout`

## 结论

本文演示了如何把 Lambda Durable Functions、Amazon EventBridge 和 Bedrock 与 DevOps Agent 配合起来，自动完成问题修复。这套方案接在 AWS DevOps Agent 停下的地方继续往下做，把调查摘要转成可执行的修复步骤，在人在回路的批准下运行。它之所以能缩短平均解决时间，是因为等值班工程师介入时，系统已经诊断出问题、收集了当前配置，并准备好一个可以直接批准的修复方案。安全性始终是设计的核心：允许列表把 Amazon Bedrock 限制为只能调用预先批准的工具，人工审批闸门则有助于防止未经明确授权的意外改动进入生产环境。这套架构本身也具有可扩展性——新增修复能力只需要更新工具注册表的配置，不需要改动编排器的代码。而由于 AWS Lambda Durable Functions 在等待审批期间挂起且不消耗算力，即使审批周期长达几小时或几天，方案在成本上依然划算。

要开始使用这套方案，请从 [GitHub 仓库](https://github.com/aws-samples/sample-automate-remediation-post-devops-agent-investigation.git)下载完整的 AWS CDK 模板，并按本文步骤在你的环境中部署。
