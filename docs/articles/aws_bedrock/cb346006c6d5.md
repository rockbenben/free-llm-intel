# 在 Amazon Bedrock AgentCore Runtime 上以无服务器方式运行自定义 MCP 代理

当 AI agent 通过 [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro)（MCP）连接工具时，它们就能获得从数据库查询、API 调用到文件操作与第三方服务集成等各类能力。在生产环境中，这些交互需要与组织安全策略相一致的治理、控制和可观测性。这包括在工具输入到达后端系统之前对其进行清洗、以特定格式生成审计轨迹，或在协议层脱敏敏感数据。这些要求由内部治理标准、行业法规以及每个生产环境的具体情况所决定。本文演示如何在 [Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 上部署一个无服务器 MCP 代理，为你提供一个可编程层来实现这些控制。

[Amazon Bedrock AgentCore Gateway](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-bedrock-agentcore-gateway-transforming-enterprise-ai-agent-tool-development/) 为 agent 与工具的集成提供集中化治理和控制，包括语义化工具发现、托管凭证和策略执行。对于需要在 Gateway 请求路径中嵌入自定义逻辑的组织，Gateway 支持 [Lambda 拦截器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-interceptors.html)。这些拦截器让你可以在每次工具调用时，以 [AWS Lambda](https://aws.amazon.com/lambda/) 函数的形式运行校验、转换或过滤代码。这样你的自定义逻辑就能保持自包含，并与 Gateway 配置一同管理。

然而，有些组织已经投入建设了与内部库或本地合规系统紧密耦合的自定义 MCP 过滤逻辑。他们希望直接在 AgentCore Runtime 上复用这套逻辑，而不必把它重构为 Lambda 函数。另一些组织跨多个系统或混合环境运行，此时把控制逻辑作为独立的 MCP 服务器运行，比系统特定的拦截器具有更好的可移植性。在这些情况下，运行在 AgentCore Runtime 上的无服务器 MCP 代理可以提供一种互补的模式。

AgentCore Runtime 是一个完全托管的计算环境，用于部署 AI agent 和 MCP 服务器。它提供无服务器基础设施，具备自动扩缩容、通过 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 和 [OpenTelemetry](https://opentelemetry.io/) 实现的内置可观测性，以及用于身份验证和授权的 [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html)。由于 Runtime 原生支持 MCP 协议，你可以用它托管 MCP 服务器，包括为 MCP 流量添加自定义控制的 MCP 代理。

我们演示如何构建并部署一个无状态 MCP 代理到 AgentCore Runtime，让你可以为 MCP 流量添加可编程控制。该代理作为无服务器工作负载运行在 Runtime 上，在启动时从上游 MCP 服务器发现工具，应用你的自定义逻辑后重新暴露这些工具，并透明地转发请求。上游 MCP 服务器可以是你选择的任何 MCP 兼容端点，包括运行在 AgentCore Runtime 上的 MCP 服务器、自托管的 MCP 服务器或第三方 MCP 服务。你也可以把这个代理连接到 Amazon Bedrock AgentCore Gateway。这样你就能利用 Gateway 跨 MCP 服务器、Lambda 函数和 SaaS 集成的托管工具发现、凭证管理和策略执行能力。

以一个开源 [GitHub](https://github.com/aws-samples/sample-mcp-proxy-agentcore-runtime) 实现为基础，我们带你走过架构、解释各层的授权如何工作、用自动化脚本部署代理，并用示例 agent 测试端到端流程。读完本文，你就拥有了一个使用 AgentCore Runtime 为 MCP 流量添加自定义控制的可用部署模式。

## 解决方案概览

自定义 MCP 代理运行在 AgentCore Runtime 上，充当 MCP 客户端与上游 MCP 服务器之间的中介。MCP 客户端与代理交互的方式，与它们与其他 MCP 服务器交互的方式相同；代理应用你专门的逻辑并把请求转发给上游服务器。这种分离让你可以在协议层引入自定义控制，而无需修改上游 MCP 服务器或客户端。

### 架构组件

该方案包含三个逻辑层，它们通过 MCP 协同工作：MCP 客户端、AgentCore Runtime 上的 MCP 代理，以及上游 MCP 服务器。请求流依次穿过这些层：客户端向代理发送 MCP 请求，代理应用你的自定义逻辑并把请求转发给上游 MCP 服务器，上游服务器处理请求并把响应沿同一路径返回。

上游 MCP 服务器可以托管在任何地方，包括 AgentCore Runtime 上、你自己的基础设施上，或作为第三方服务提供。在本文中，我们使用一个 AgentCore Gateway 作为上游 MCP 服务器，因为它提供了一个现成的、MCP 兼容的工具端点且已注册目标，让你无需另外搭建一个独立的 MCP 服务器就能完成整个演练。该代理模式同样适用于其他 MCP 兼容的上游端点，我们在文中也会讨论其他可选方案，包括运行在 AgentCore Runtime 上的上游 MCP 服务器。

Runtime 中的 MCP 客户端把自定义 MCP 代理当作它的工具服务器，向它发送标准 MCP 请求来发现和调用工具。从客户端的视角看，该代理与其他 MCP 服务器无从区分。AgentCore Runtime 为客户端工作负载提供托管计算、自动扩缩容和内置可观测性。

MCP 代理充当客户端与上游 MCP 服务器之间的中介。它接收来自客户端的 MCP 请求，应用你的自定义逻辑，并把请求转发给上游服务器。代理在 Runtime 中作为独立的 MCP 服务器运行，使用与客户端本身相同的无服务器托管基础设施。

代理以标准 MCP 客户端的身份连接上游 MCP 服务器。上游服务器把代理视为已通过身份验证的 MCP 客户端，与其他获授权的调用方没有区别。上游服务器负责处理对下游服务和 MCP 工具的访问。

工具本身，无论是以 [MCP 服务器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-mcp.html)、[AWS Lambda 函数](https://aws.amazon.com/lambda/) 还是第三方 SaaS 集成的形式托管，都在上游服务器上注册并由其管理。对于寻求全托管工具集成路径的组织，AgentCore Gateway 为开发者提供了一种直接而安全的方式，用于大规模构建、部署、发现和连接工具。

### MCP 代理如何工作

我们使用 [FastMCP](https://gofastmcp.com/getting-started/welcome) 实现该代理，在启动时从上游 MCP 服务器发现工具，并在运行时转发每个客户端请求。代理不定义自己的工具，也不预先知道上游服务器暴露了哪些内容。

当代理进程启动时，它向“上游服务器”发送标准的 MCP `tools/list` 请求。服务器返回完整的可用工具目录。对于每个工具，代理动态注册一个同名的 FastMCP 本地工具，描述也相同。每个工具由一个处理函数支撑，该函数把 `tools/call` 请求转发给上游服务器并返回响应。连接到代理的 MCP 客户端看到的工具目录和得到的结果，与它们直接连接上游服务器时完全相同。

由于代理是你自己拥有并部署的标准 Python MCP 服务器，你可以在转发工具调用之前或收到响应之后插入自定义逻辑。上游服务器负责工具执行，而代理在其前面增加了一个可编程层，并不取代上游服务器的原生能力。

### 各组件之间的授权

授权在架构的每一层独立执行，从而在整个流程中形成彼此分离的信任边界。

- **Agent 到 MCP 代理：** 当 agent 连接 MCP 代理时，它使用 [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) 进行身份验证和授权。代理使用 AgentCore Identity 提供的能力，包括 agent 身份的集中管理和安全凭证存储。你可以使用为 AgentCore Runtime 中其他工作负载所用的同一套身份框架，控制哪些 agent 和主体可以调用该代理。
- **代理到上游 MCP 服务器：** 代理必须向它所连接的上游 MCP 服务器进行身份验证。身份验证方式取决于上游服务器的要求。AgentCore Identity 为托管在 AgentCore Runtime 上的工作负载提供入站授权，既支持通过 [AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 使用 [AWS Signature Version 4 (SigV4](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv.html))，也支持基于 JSON Web Token (JWT) 的 OAuth 2.0 客户端凭证授权。使用基于 JWT 的授权时，你需要为上游服务器配置发现 URL、允许的 audience 和允许的客户端。AgentCore Identity 会在每个请求上校验 bearer token。代理通过 OAuth 2.0 客户端凭证授予获取 token，并以 `Authorization: Bearer ` 请求头的形式携带。

对于基于 IAM 的授权，代理使用它从 AgentCore Runtime 继承的 IAM 执行角色，通过 AWS SigV4 对请求签名。具体权限因上游服务器类型而异。如果上游 MCP 服务器托管在 AgentCore Runtime 上，你可以把 `bedrock-agentcore:InvokeAgentRuntime` 权限限定在范围内，以控制哪些调用方可以访问它。或者，如果上游服务器是 AgentCore Gateway（如本演练所示），你可以把 `bedrock-agentcore:InvokeGateway` 权限限定到特定的 Gateway 和调用方身份。这可确保只有受信任的代理才能访问工具目录。

配套的 [GitHub](https://github.com/aws-samples/sample-mcp-proxy-agentcore-runtime) 项目默认使用基于 IAM 的授权方式。部署脚本也为该集成支持基于 JWT 的授权。

- **上游服务器到工具：** 上游 MCP 服务器使用 AgentCore Identity 凭证提供方对下游工具进行身份验证，这些提供方透明地管理 OAuth 2.0 token、API key 和凭证轮换。无论请求源自代理还是直接来自客户端，出站授权的工作方式都相同。

该架构中的每一层都独立进行身份验证。你通过代理在 MCP 协议层注入自定义逻辑，而上游服务器继续负责工具执行和它自己的授权。最终形成这样一种架构：自定义控制与上游能力在彼此分离、边界清晰的层中运作。

## 前提条件

要实现该方案，你需要具备以下条件：

- 一个安装了 Python 3.12 或更高版本的 Linux 或 macOS 开发环境。它可以是本地机器或云实例。
- 已安装并配置好凭证的 [AWS Command Line Interface (AWS CLI)](https://aws.amazon.com/cli/)，凭证需属于一个 [AWS Identity and Access Management (AWS IAM)](https://aws.amazon.com/iam/) 主体，该主体具有创建 IAM 角色、与 [Amazon Elastic Container Registry (Amazon ECR)](https://aws.amazon.com/ecr/) 交互以及调用 Amazon Bedrock AgentCore API 的权限。如果你没有 AWS 账户，请参阅 [如何创建并激活一个新的 Amazon Web Services 账户？](https://repost.aws/knowledge-center/create-and-activate-aws-account)
- 在开发环境中安装的 [AgentCore starter toolkit](https://pypi.org/project/bedrock-agentcore-starter-toolkit/)。该工具用于把 agent 打包并部署到 AgentCore Runtime。如果你还没有 AgentCore starter toolkit，请参阅 [在 Python 中开始使用 Amazon Bedrock AgentCore starter toolkit](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-toolkit.html)。
- 在开发环境中安装的 [Docker](https://www.docker.com/)。AgentCore CLI 使用 Docker 构建运行在 AgentCore Runtime 上的容器镜像。
- 代理将要连接的上游 MCP 服务器端点。在本演练中，我们使用已注册至少一个目标的 Amazon Bedrock AgentCore Gateway。如果你还没有 AgentCore Gateway，请参阅 [创建 Amazon Bedrock AgentCore gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-create.html)。创建后请记下 Gateway 的 MCP 端点 URL。你将用该 URL 配置代理。
- （如果你的上游服务器使用 OAuth 入站授权）一个 [Amazon Cognito](https://aws.amazon.com/cognito/) 用户池，需配置好域名，并有一个使用带客户端密钥的客户端凭证授予的应用客户端。如果你使用 AgentCore starter toolkit 以 OAuth 授权创建了 Gateway，这些资源会在创建 Gateway 时自动预置。

## 如何配置代理的身份验证方式

MCP 代理与上游服务器之间的身份验证模式取决于上游服务器入站授权的配置方式。对于托管在 AgentCore 上的工作负载，AgentCore Identity 同时支持 IAM 和 JWT 入站身份验证。[GitHub](https://github.com/aws-samples/sample-mcp-proxy-agentcore-runtime) 上的代理代码在单一函数 `_send_gateway_request` 中实现了这两种模式，对上游服务器的出站 HTTP 调用就在该函数中进行。

### IAM 授权

代理使用 AWS SigV4 对发往上游服务器的每个出站请求签名。由于代理运行在 AgentCore Runtime 上，它继承了你在部署时指定的 IAM 执行角色。部署脚本为该角色授予 `bedrock-agentcore:InvokeGateway` 权限，并把 `Resource` 字段限定到该 Gateway。不需要额外的凭证或 token。代理使用 runtime 的 [boto3](https://pypi.org/project/boto3/) 会话自动为请求签名。

### OAuth 授权

如果你的上游服务器使用 JWT authorizer，代理会用通过 OAuth 2.0 客户端凭证授予获得的 bearer token 替代 SigV4 签名。该模式内置于代理中，无需改动代码。你只需在部署配置中把 `auth_mode` 设为 `jwt`，并提供 Cognito 用户池的详细信息。

当你选择 `JWT` 时，脚本会收集 Cognito 用户池 ID、应用客户端 ID、应用客户端密钥和域名前缀。这些值会在 `agentcore launch` 步骤中作为环境变量传给 AgentCore Runtime 容器。你也可以直接在 `deploy_config.json` 中设置这些值，从而跳过交互式提示。

启动时，代理读取 `AUTH_MODE` 环境变量。当它被设为 `jwt` 时，代理使用带客户端凭证的 HTTP 身份验证请求访问 token。该 token 缓存在内存中，并在接近过期时自动刷新。发往上游 MCP 服务器的每个出站请求都携带该 token 作为 `Authorization: Bearer` 请求头，而不再是 SigV4 签名头。

代理的其余部分（工具发现、工具转发和 FastMCP 服务器）无论采用哪种身份验证模式，运行方式都完全相同。唯一的区别在于 `_send_gateway_request` 如何对其出站调用进行身份验证。

## 定制机会

该代理架构让你可以拦截并转换客户端与上游 MCP 服务器之间的 MCP 流量。以下示例演示两种常见的定制模式：

### 令牌化（Tokenization）

工具调用参数中可能包含个人可识别信息（PII），这些信息不应以明文形式进入后端系统。代理的转发流程为你提供了一个自然的拦截点，可用于加入令牌化处理。

流程是这样运作的：当客户端调用某个工具时，代理 `main.py` 中的 `_make_tool_handler` 函数会以 `kwargs` 字典的形式接收参数，把它们传给 `_send_gateway_request`；后者把参数包装进 JSON-RPC 载荷并（以 SigV4 签名）发送到上游 MCP 服务器，然后把响应格式化后返回给客户端。相关代码路径如下：

```
def _make_tool_handler(tool_name: str):
    """Create a tool handler function that forwards calls to the gateway."""
    def handler(**kwargs) -> str:
        # --- Tokenize: scan kwargs for PII and replace with tokens ---
        result = _send_gateway_request(
            "tools/call", {"name": tool_name, "arguments": kwargs}
        )
        content = result.get("content", [])
        # --- Detokenize: reverse tokens in content before returning ---
        if content and isinstance(content, list):
            texts = [c.get("text", str(c)) for c in content if isinstance(c, dict)]
            return "\n".join(texts) if texts else json.dumps(result)
        return json.dumps(result)
    return handler
```

你可以在 handler 闭包内的两个位置加入令牌化。在调用 `_send_gateway_request` 之前，你会扫描 `kwargs ` 中的值以查找 PII 模式，并用可逆的 token 替换它们（参见 [在 AWS 上通过令牌化提升数据安全并缩小审计范围的指南](https://aws.amazon.com/solutions/guidance/tokenization-to-improve-data-security-and-reduce-audit-scope-on-aws/)）。在 `_send_gateway_request` 返回之后，你会把响应内容中的 token 还原，再把结果返回给客户端。这样既能让 PII 不进入后端目标，又能为 agent 保留端到端的数据流。

### 工具级访问控制

你可能希望限制某个调用方可以调用哪些工具，尽管上游服务器暴露了完整的工具目录。你可以在由 `_make_tool_handler` 创建的处理函数开头加入策略检查来实现这一点。代理在构建处理函数时已经把工具名作为参数接收。在把 `tools/call` 请求转发给上游服务器之前，处理函数会根据访问策略评估调用方的身份。身份可以从入站请求头或 MCP 会话上下文中提取。如果调用方未获该工具的授权，处理函数会直接返回错误响应，而不联系上游服务器。你也可以在 `register_gateway_tools` 函数中过滤 `tools/list` 的响应，只暴露符合给定策略的工具。这样，未授权的工具就永远不会出现在客户端的工具目录中。

## 清理

为避免持续产生费用，如果你在测试本方案之后不再需要所创建的资源，请将其删除。AgentCore CLI 提供了 `destroy` 命令，用于移除 agent 及其关联资源。请在项目根目录下运行以下命令：

- 删除 AgentCore Runtime agent 及其 ECR 镜像：
`agentcore destroy --agent <agent-name> --delete-ecr-repo --force`
- 删除内联 IAM 策略和执行角色：  `aws iam delete-role-policy --role-name <your-MCPProxy-Server-Role> --policy-name <your-Gateway-Access-Policy> aws iam delete-role --role-name <your-MCPProxy-Server-Role>`
- 如果你专门为本演练创建了 AgentCore Gateway 且不再需要它，请删除该 Gateway 及其目标：  `agentcore gateway delete-mcp-gateway --name <your-Gateway> --force`  把 agent 名称、角色名称和 Gateway 名称替换为你在部署期间使用的值。

## 结论

本文演示了如何在 Amazon Bedrock AgentCore Runtime 上构建并部署一个无服务器 MCP 代理，为 MCP 流量添加自定义控制。该代理在启动时从上游 MCP 服务器动态发现工具，把它们作为标准 MCP 服务器重新暴露，并在运行时转发工具调用。这为你提供了一个可编程层，你可以在其中应用输入校验、日志记录、速率限制或响应增强等自定义逻辑。

我们以 AgentCore Gateway 作为上游服务器走完了端到端工作流，并介绍了如何让代理适配采用 IAM 或 JWT 入站授权的 Gateway。该代理是无状态的，作为标准容器运行在 AgentCore Runtime 上。你可以把它连接到其他 MCP 兼容的上游服务器、串联多个上游端点，或添加针对你工作负载的中间件逻辑。完整的源代码、部署脚本和测试 agent 可在 [GitHub](https://github.com/aws-samples/sample-mcp-proxy-agentcore-runtime) 上获取。

要开始使用，请克隆仓库、配置你的上游 MCP 服务器端点，然后运行自动化部署脚本。如需进一步了解如何在 AgentCore 上构建和部署 agent 以及使用 Strands Agents 框架，请参阅 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/agentcore.html) 和 [Strands Agents SDK](https://github.com/strands-agents/sdk-python)。
