# 使用 Amazon Nova Multimodal Embeddings 和 Amazon Bedrock AgentCore 实现代理工程智能

当合格的航空航天组件过时或交付周期较长时，工程师会花费数天时间在供应商数据表、接口控制文档 (ICD) 和资格记录中交叉引用规范，然后记录替代理由以供审查。飞行关键组件的错误替换可能会导致任务失败，但每个决定背后的证据线索通常分布在电子邮件和未记录的机构知识中，因此没有正式的、可重复的包供审核人员检查。

之前的文章[使用 Amazon Nova 多模态嵌入制造智能](https://aws.amazon.com/blogs/machine-learning/manufacturing-intelligence-with-amazon-nova-multimodal-embeddings/) 展示了该模型如何检索锁定在纯文本管道错过的工程图、热图和数据表图表中的答案。这篇文章将从检索工作停止的地方开始，将这些功能放入一个多代理系统中，该系统会收集从检索到起草的评估的替代证据。

在这篇文章中，我们展示了如何构建一个多代理工程助手，使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)、[Amazon Nova Multimodal Embeddings](https://docs.aws.amazon.com/nova/latest/nova2-userguide/embeddings.html) 和开源 [Strands Agents] 来减少零件替换评估背后的手动交叉引用SDK](https://strandsagents.com/)。规划人员将工作分配给三个专业代理，这些代理搜索多模式知识库、根据确定性公差规则对候选者进行评分、比较零件照片以及实时网络数据中的地面生命周期声明。工程师始终是决策者，因为系统会收集证据并起草文件，而不会自行批准替换。

## 解决方案概述

该助手是围绕一个设计规则构建的，即工程师做出每一个决定，系统为其收集证据。该规则决定了我们在哪里使用大型语言模型 (LLM) 以及在哪里使用确定性代码。

该架构由三大支柱定义：

- **确定性规格适合度评估** – 用 Python 编写的公差规则代码根据参考零件和工程师规定的要求对每个候选零件进行评分。由于相同的输入始终会产生相同的通过/标志判决，因此结果可以进入正式的工程审查。
- **多代理编排** – 轻量级规划器将每个查询路由到三个专家代理（目录、评估、知识）中的一个或多个，并且仅当超过一名专家做出贡献时，主管才会综合他们的发现。复杂的问题，例如“检查这个轮子是否即将报废，找到替代品，并对其进行评分”，将所有三位专家依次联系起来。
- **人机交互决策** – 系统起草理由备忘录和集成影响评估以供工程审查，但不建议或批准替代。每次评估还会编写与 AS9100 第 8.4 节和 8.5.6 节一致的审核跟踪条目。

Amazon Bedrock AgentCore 是一个使用任何框架或模型大规模构建、连接和优化代理的平台。在此解决方案中，来自工程师应用程序的聊天请求流入 AgentCore 运行时托管的多代理图：规划器 (Claude Haiku 5.5) 生成路由计划，专家 (Claude Sonnet 5.5) 执行他们的工具，而主管 (Claude Opus 5.5) 在多个专家运行时综合其结果。专家们使用 Amazon Nova 多模式嵌入从我们通过 [Amazon Bedrock 托管知识库](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-management-kb.html) 创建的托管知识库进行检索，并通过 AgentCore 网关（Amazon Bedrock AgentCore 的一项功能）以及用于实时 Web 数据的 Web 搜索连接器进行路由。对于图像即查询（上传图表来识别零件），代理直接调用本机 Amazon S3 Vectors 索引，因为托管知识库检索 API 不接受图像输入。 Amazon S3 Vectors 是 Amazon Simple Storage Service (Amazon S3) 的一项功能。一个单独的固定链（知识，然后是评估，然后是主管）生成正式的集成影响评估（IIA）文件。

Amazon Nova 多模式嵌入有两个不同的角色：

- **多模态检索** – 数据表、ICD 和性能图表嵌入 Nova 多模态嵌入，因此文本和视觉内容共享一个语义空间。工程师可以输入“0.06 Nms车轮的扭矩曲线”或上传图表图像，检索将返回带有来源归属的匹配图表。
- **视觉相似性评分** – 当比较两个候选部件时，Nova Multimodal Embeddings 会生成它们照片之间的定量余弦相似性，Claude 会分析具体的物理差异（安装模式、连接器放置、外壳几何形状）。该分数为确定性规格比较添加了支持证据，这是适合性判断的基础。

### 使用范围工具定义专家

每个专家都是 Strands 代理，其提示范围很窄，只提供其所需的工具。 Scoping tools per specialist keeps behavior predictable, because the Knowledge specialist has no access to the catalog discovery tools and the Catalog specialist has no access to the evaluation tools.以下代码创建评估专家。
```
from strands import Agent

def create_evaluation_specialist() -> Agent:
    """Evaluation Specialist: deterministic spec-by-spec comparison and scoring."""
    return Agent(
        name="evaluation_specialist",
        system_prompt="""You are the Evaluation Specialist. Your job is to run
deterministic, spec-driven comparisons between parts.
...
RULES:
- Your comparisons are deterministic (code, not opinion)
- NEVER recommend or approve --- present evidence and flags; the engineer decides
- Always include the disclaimer that this is evidence only""",
        tools=[score_substitution_fit, compare_parts, visual_similarity_score,
               check_qualification_status, generate_substitution_memo],
        model="us.anthropic.claude-sonnet-5-5",
    )
```

### 使用小模型进行布线，使用大模型进行综合

路由是一个分类任务，没有工具调用，因此不需要大型推理模型。基于Haiku的规划器会在几秒钟内返回编号的路由规划。 Opus 管理器仅在两个或更多专家贡献时运行，因为综合单个专家已经完成的答案会增加大约 8 秒的延迟，并且不会提高质量。
```
# Step 1: Planner (fast model) plans the routing (may be multi-step).
plan_response = planner(planning_prompt)
ordered_specialists = _parse_specialist_plan(str(plan_response))

# Step 2: Execute specialists in sequence, passing context forward
accumulated_context = ""
for spec_name in ordered_specialists:
    specialist = specialists[spec_name]
    specialist_response = specialist(spec_prompt)
    accumulated_context += f"\n[{spec_name.upper()}]: {specialist_response}\n"

# Step 3: Synthesize only when 2+ specialists ran.
if len(ordered_specialists) == 1:
    final_text = steps[0]["response"]
else:
    final_text = str(supervisor(synthesis_prompt))
```
将工作拆分到三个模型层可以匹配每个阶段的成本和延迟。 Haiku 对查询进行分类，Sonnet 运行工具，Opus 编写组合答案，这是响应质量最重要的步骤。

### 保持评分的确定性

规范适合度评估作为普通 Python 代码针对手写的需求模式运行。该模式定义了每个组件类别的关键规格和容差规则，“score_substitution_fit”会比较每个规格，计算通过和标志，并显示生命周期风险。由于工程审查包的结论必须是可重现的，因此此步骤不涉及LLM。
```
{
  "categories": {
    "reaction_wheel": {
      "critical_specs": [
        {"field": "voltage_v", "label": "Bus voltage (V)",
         "rule": "match", "required_from_user": true},
        {"field": "mass_g", "label": "Mass (g)",
         "rule": "candidate_lte_reference_within_pct", "tolerance_pct": 20,
         "required_from_user": false}
      ]
    }
  }
}
```
该工具返回带有明确免责声明的结构化判决：
```
return {
    "spec_results": results,  # per-spec pass/flag/review status
    "counts": counts,
    "out_of_tolerance": out_of_tolerance,
    "lifecycle": {...},  # obsolescence and lead-time flags
    "summary": summary,
    "disclaimer": "Evidence only. This tool does not recommend or approve "

```
专家展示了这个表格并解释了标志，但它不能改变结论。审计跟踪遵循相同的工作分工。每次评估后，编排层都会读取专家的工具调用历史记录并自行写入审核条目，因此日志记录并不依赖于模型记得执行此操作。

### 使用 Amazon Nova Multimodal Embeddings 评分视觉相似度

当替代品必须适合现有支架时，外形因素很重要。 “visual_similarity_score”工具使用 Nova Multimodal Embeddings 嵌入两个零件照片并计算余弦相似度，然后要求 Claude 描述具体的可观察到的差异。
```
def embed_image(image_bytes):
    """Embed one image with Nova MME (IMAGE_RETRIEVAL) -> 1024-d vector."""
    b64 = base64.b64encode(image_bytes).decode('utf-8')
    fmt = 'png' if image_bytes[:8] == b'\x89PNG\r\n\x1a\n' else 'jpeg'
    body = {
        'taskType': 'SINGLE_EMBEDDING',
        'singleEmbeddingParams': {
            'embeddingPurpose': 'IMAGE_RETRIEVAL',
            'embeddingDimension': 1024,
            'image': {'detailLevel': 'STANDARD_IMAGE', 'format': fmt,
                      'source': {'bytes': b64}},
        },
    }
    resp = bedrock.invoke_model(
        modelId='amazon.nova-2-multimodal-embeddings-v1:0',
        body=json.dumps(body), accept='application/json',
        contentType='application/json',
    )
    result = json.loads(resp['body'].read())
    return np.array(result['embeddings'][0]['embedding'])

# cosine similarity of the two photo embeddings
emb_a, emb_b = embed_image(photo_a_bytes), embed_image(photo_b_bytes)
similarity = float(np.dot(emb_a, emb_b) /
                   (np.linalg.norm(emb_a) * np.linalg.norm(emb_b)))
```
嵌入相似性是确定性的且可重复的，对于同一产品系列的两个车轮，返回约 0.84，对于不同类别的车轮，返回 0.40 左右。然后，Claude的视觉分析解释了造成差异的原因，例如注意到一个外壳的直径大约是另一个外壳的两倍，并且具有六孔安装模式，而另一个外壳有四个。

### 使用两个检索路径检索图表和图表

文本和文档查询通过由 Amazon Nova 多模式嵌入支持的托管知识库，并通过 AgentCore 网关进行路由。图像即查询（上传图表或照片以查找匹配内容）使用直接从代理调用的本机 Amazon S3 Vectors 索引，因为托管知识库检索 API 不接受图像输入。

知识专家的“retrieve_visual_content”工具为这两种路径提供了一个界面。工程师可以将需求文档中的性能曲线粘贴到聊天中，并询问哪个部分与其匹配，或者改为在文本查询中描述图表。
```
# Image-as-query: embed the uploaded image with Nova MME, exactly as the
# datasheet crops and photos were embedded at indexing time.
def embed_query_image(image_bytes):
    b64 = base64.b64encode(image_bytes).decode('utf-8')
    fmt = 'png' if image_bytes[:8] == b'\x89PNG\r\n\x1a\n' else 'jpeg'
    body = {'taskType': 'SINGLE_EMBEDDING', 'singleEmbeddingParams': {
        'embeddingPurpose': 'IMAGE_RETRIEVAL', 'embeddingDimension': 1024,
        'image': {'detailLevel': 'STANDARD_IMAGE', 'format': fmt,
                  'source': {'bytes': b64}}}}
    r = bedrock.invoke_model(modelId=NOVA_MME_MODEL_ID, body=json.dumps(body),
                             accept='application/json', contentType='application/json')
    return json.loads(r['body'].read())['embeddings'][0]['embedding']
```
在图像路径上，使用“IMAGE_RETRIEVAL”目的使用 Nova Multimodal Embeddings 嵌入 1,024 维的上传内容，然后与 S3 矢量索引进行匹配：
```
# Query the native S3 Vectors index and collapse to the best vector per part.
emb = embed_query_image(image_bytes)
s3v = boto3.client('s3vectors', region_name=REGION)
fetch_k = max(top_k * 6, 12)  # each part has several vectors; dedupe below
resp = s3v.query_vectors(
    vectorBucketName=S3_VECTOR_BUCKET, indexName=S3_VECTOR_INDEX,
    queryVector={'float32': emb}, topK=fetch_k,
    returnDistance=True, returnMetadata=True,
)

best = {}
for v in resp.get('vectors', []):
    meta = v.get('metadata', {}) or {}
    pid = meta.get('part_id', '')
    if not pid:
        continue
    sim = 1.0 - v.get('distance', 1.0)  # cosine distance -> similarity
    if pid not in best or sim > best[pid]['score']:
        best[pid] = {'part_id': pid, 'score': sim}
ranked = sorted(best.values(), key=lambda r: r["score"], reverse=True)[:top_k]
```
由于一个零件会贡献多个向量（其照片、整个数据表页面和每个裁剪的图表区域），因此结果在到达模型之前会被删除为每个零件的最佳得分向量。

我们在构建检索路径时学到了三个实践经验：

- **在索引图表之前裁剪图表** – 整个数据表页面的索引条目很差，因为页面的大约 90%（页眉、规格表、页脚）是每个部分共享的样板文件，并且共享内容主导了嵌入。在整页旁边索引裁剪的图表区域解决了这个问题。在我们的测试中，图表上传匹配从整页索引的 7 个部分中的 3 个正确到图表带裁剪的 7 个部分中的 7 个正确。我们将裁剪区域定义为页面的一部分，这使它们在数据表分辨率下保持正确。
- **当工程师命名零件时过滤结果** – 跨模式文本到图像的相似性本身并不能可靠地返回正确的零件图表，因为扭矩曲线图像不包含可见的零件名称。当工程师命名特定部件时，该工具仅保留该部件索引内容的结果，它通过从每个结果的 S3 URI 中解析部件文件夹来识别该内容。由于过滤器在工具中运行，因此它无需索引中的自定义元数据即可工作。
- **记录图像路径上的每个回退** – 图像路径在出现错误时返回“None”并进行文本检索。这种回退是合理的，但这意味着 AgentCore 运行时执行角色缺少“s3vectors:QueryVectors”权限不会引发错误。图像即查询会在没有警告的情况下停止工作，然后模型会以很高的明显置信度命名错误的部分。这个问题在开发过程中很容易被忽视，因为本地开发人员凭据通常比运行时角色具有更广泛的权限。现在，只要该路径回退，该工具就会记录一个明确的“S3 Vectors 图像查询失败”警告，其中包含存储桶、索引和区域。检测检索路径中的每一个无声回退，因为硬故障比无声故障更容易诊断。

### 通过固定的专家链制作正式文件

聊天使用动态路由，因为无法提前知道解决自由形式问题的合适专家。集成影响评估的工作方式有所不同。当工程师请求对参考和候选对进行影响评估时，所需的序列已经已知，因此该服务会按照固定顺序使用专门构建的综合提示来组成相同的专业工厂功能。
```
# 1. Knowledge Specialist --- ICD/datasheet interface detail for both parts
knowledge_text = str(knowledge(knowledge_prompt))

# 2. Evaluation Specialist --- structured field delta + qualification check
evaluation_text = str(evaluation(evaluation_prompt))

# Deterministic structured delta for exact summary stats
comparison = compare_parts(reference_id, candidate_id)

# 3. Supervisor --- synthesize into the six-section IIA document
markdown = str(supervisor(synthesis_prompt))
```
生成的文档涵盖了接口变更、机械集成、电气集成、热集成、资格增量和供应链影响。叙述部分需要 LLM 综合，因为引脚排列和协议详细信息必须从 ICD 散文中提取。摘要统计数据（匹配、差异、总字段）是直接从“compare_parts”输出计算的，因此与叙述一起显示的数字是准确的。

### 通过 AgentCore Gateway 在实时 Web 数据中地面生命周期声明

目录数据已过时，因此知识专家的“web_search_eol”工具通过具有 Web 搜索连接器的 AgentCore 网关检查当前的生命周期终止通知、供应商公告和交付时间。网关将连接器公开为受管理的模型上下文协议 (MCP) 端点。由于网关还处理托管知识库检索，因此您可以将策略和可观察性附加到一处的外部和内部数据访问。

## 评估助手

我们通过两种方式衡量质量，通过 AgentCore 评估（Amazon Bedrock AgentCore 的一项功能）进行持续在线评分，以及针对策划的查询集进行离线验证。

### AgentCore在线评测

[Amazon Bedrock AgentCore 评估](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html)，[自 2026 年 3 月起全面推出](https://aws.amazon.com/about-aws/whats-new/2026/03/agentcore-evaluations-generally-available/)，使用“LLM-as-a-judge”技术对代理跟踪进行评分。它读取 Strands 代理已经发出的 OpenTelemetry 跟踪，因此检测代理不需要评估应用程序更改。该服务提供两种模式。在线评估不断对实时生产会话进行采样，按需评估运行适合持续集成和持续交付 (CI/CD) 管道的程序化测试。

我们使用在线评估，并将结果发布到 Amazon CloudWatch 以用于仪表板和警报。 GitHub 存储库中的 Notebook 05 创建在线评估配置，并将测试查询发送到已部署的运行时以生成用于评分的会话。
```
config = eval_client.create_online_config(
    config_name=CONFIG_NAME,
    agent_id=RUNTIME_ID,
    sampling_rate=SAMPLING_RATE,
    evaluator_list=[
        "Builtin.GoalSuccessRate",
        "Builtin.Correctness",
        "Builtin.Helpfulness",
        "Builtin.Faithfulness",
        "Builtin.ResponseRelevance",
        "Builtin.ToolSelectionAccuracy",
        "Builtin.ToolParameterAccuracy",
    ],
    auto_create_execution_role=True,
    enable_on_create=True,
)
```
该服务附带 13 个内置评估器，同时支持由提示定义或作为 AWS Lambda 函数托管的自定义评估器。我们启用了七个，涵盖所有三个评分级别：

| **级别** | **评估者** | **得分多少** |
| --- | --- | --- |
|会议|目标成功率|对话是否端到端地实现了用户的目标？ |
|追踪|正确性|信息是否真实准确？ |
|追踪|乐于助人 |回应有用且有价值吗？ |
|追踪|诚信|响应是否忠实于检索到的上下文？ |
|追踪|响应相关性 |响应是否解决了用户的实际查询？ |
|工具调用 |刀具选择精度|代理是否选择了正确的工具？ |
|工具调用 |刀具参数精度|代理提取参数是否正确？ |

**策划的查询集**包含 6 个类别的 36 个查询：目录发现 (8)、知识和 ICD 检索 (8)、多专家链 (6)、确定性评估 (5)、文本到视觉检索 (5) 以及断言代理拒绝推荐或批准的人机循环安全拒绝 (4)。每个查询都带有其预期的目录部件 ID，但安全查询除外，其预期结果是拒绝。
```
export AGENTCORE_RUNTIME_ARN=arn:aws:bedrock-agentcore:us-east-1:ACCOUNT:runtime/YOUR_RUNTIME

```
### 结果

AgentCore 会持续对实时会话进行采样，因此每个评估者的分数都是一个不断变化的总分，会随着流量的积累和代理的变化而变化。以下数字是合成数据集运行的快照。使用它们作为设置 CloudWatch 警报阈值的基准，并预计您自己运行的数字会有所不同。

| **级别** | **评估者** | **分数（30 天平均）** |
| --- | --- | --- |
|会议|目标成功率| 0.892 | 0.892
|追踪|正确性| 0.968 | 0.968
|追踪|乐于助人 | 0.956 | 0.956
|追踪|诚信| 0.981 | 0.981
|追踪|响应相关性 | 0.968 | 0.968
|工具调用 |刀具选择精度| 0.861 | 0.861
|工具调用 |刀具参数精度| 0.980 |

所有跟踪级别质量指标的得分均达到或高于 0.95，工具参数提取的得分接近完美，为 0.980。评估运行之间最显着的改进是工具选择准确性，从 0.809 上升到 0.861。三个变化推动了这一成果：整合到单个托管知识库、修复图像查询路径上缺少的权限（该权限导致无提示地回退到文本搜索）以及收紧规划器的路由以避免链接不必要的专家。

由于查询集的设计方式，目标成功率较低，为 0.892。查询集包括要求代理推荐或批准替代的安全类别提示。代理正确地拒绝，但评估者将正确的拒绝评分为未实现的目标。我们期望这个结果，因为在人机循环系统中，代理不得自行批准替换。

## 使模式适应您自己的目录

该代码是一种可重用的模式，适用于反作用轮之外的其他零件类别。交换域需要三项更改：替换零件数据（“specs.json”、描述、ICD、数据表页面和每个零件的照片），编辑需求架构以定义类别的关键规格和容差规则，并将知识库指向您的 S3 语料库。代理、工具和评分引擎保持不变。由于“mei_core”中的确定性工具是普通的 Python 函数，因此 PLM 或 ERP 集成可以直接调用“score_substitution_fit”，而循环中没有代理。

＃＃ 结论

在这篇文章中，我们展示了如何构建一个多智能体工程助手，用自动证据组装取代手动零件替换研究。该架构将 Amazon Nova Multimodal Embeddings（处理纯文本系统错过的视觉相似性评分和图表检索）与 Amazon Bedrock AgentCore（提供运行时托管、网关管理的检索和 Web 搜索以及质量评估的生产支架）配对。三种设计选择最重要。确定性代码会生成每个通过/失败判定，每个任务都在能够很好处理该任务的三个模型层中最小的一个上运行，并且只有工程师才能批准替换。
