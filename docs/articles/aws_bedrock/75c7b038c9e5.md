# 编写你自己的训练循环——不用管理 GPU——用 Amazon SageMaker 训练会话 API

今天微调一个大语言模型（LLM），通常要在训练循环的控制力和运维简便性之间做取舍。用全托管服务时，你选一个基础模型、提供数据和超参数，其余的一切都由服务负责——当一套标准的、预打包的配方正好适配你的问题时，这很好用。托管程度较低的服务给你更多控制，但你也要自己管理更多底层基础设施和训练框架。有时候标准配方就是不够：你需要为监督微调（SFT）定制的损失或数据课程，需要自己做偏好优化，需要一个强化学习（RL）奖励函数，或者需要上周才发表的对齐算法。一旦你要亲自塑造训练过程，你就得承担那部分基础设施工作，以换取算法上的自由。

今天，Amazon SageMaker AI 中的无服务器模型定制能力通过训练会话 API 得到扩展，它把抽象边界下移一层，从而消除了这种取舍。它抽象掉的不是算法，而是算力。`forward_backward()`、`optim_step()`、`sample()` 这些操作变成 SageMaker API 调用，你可以把它们组合成你的技术所需的任何流程：SFT、偏好优化、RL，或者某种全新的东西。这些调用面向一个活动的、有状态的会话，因此模型在各步之间一直驻留在 GPU 上，你可以对它发起任意多次调用。服务负责运行时准备、分布式执行、梯度同步、故障恢复、租户隔离，以及规模化运行 GPU 的运维。你写训练循环，SageMaker AI 跑基础设施。

与服务一起，我们还发布了 [SageMaker training sessions cookbook](https://github.com/aws/sagemaker-training-sessions-cookbook)，其中是一组可直接运行的 SFT 与 RL 配方，可以作为你自己训练循环的蓝图。

本文将介绍这套编程模型和三个 SDK 客户端，并说明训练会话 API 在 SageMaker AI 的模型训练与定制选项中处于什么位置。然后我们会拆解一个在小学数学题（GSM8K）上的最小 RL 循环，展示各个操作如何咬合，最后以 cookbook 中的一个真实工作负载收尾：在竞赛编程题上做强化学习，由单元测试运行生成的代码来评分。

## 什么是 SageMaker AI 训练会话 API？

有了 SageMaker AI 训练会话 API，你可以从本地机器上的 Python 进程驱动一个活动的、由 GPU 支撑的会话。你调用操作，SageMaker AI 在托管加速器上运行它们，这些加速器已加载你选定的基础模型以及你的低秩适配（LoRA）适配器。没有描述整个作业的配置文件，也没有创建集群的步骤。你在代码里以交互方式控制每一步发生什么，所以可以快速迭代和调试。

职责划分大致如下：

| **你关注** | **你编写** | **SageMaker AI 负责** |
| --- | --- | --- |
| 你的数据、RL 环境、agent 和算法 | 一个 Python 训练循环，对需要 GPU 的步骤调用 `forward_backward()`、`optim_step()` 和 `sample()` 等操作 | GPU 分配、模型与 LoRA 加载、分布式执行、故障恢复、检查点存储、安全 |

这套 API 围绕 [SageMaker Python SDK](https://github.com/aws/sagemaker-python-sdk) 中的三个客户端组织，按顺序创建。`ServiceClient` 持有平台级设置（执行角色、模型包组、Amazon Simple Storage Service (Amazon S3) 输出位置，以及可选的 AWS Key Management Service (AWS KMS) 密钥和虚拟私有云（VPC）配置，这些也可以按会话覆盖），并启动一个会话。`ServiceClient` 实例化 `TrainingClient`（训练与检查点操作，如 `forward`、`forward_backward`、`optim_step` 和 `save_weights_for_sampler`），后者又实例化 `SamplingClient`（`sample` 和 `compute_logprobs`，用于 rollout 与评估期间的生成和打分）。每次 API 调用对应你循环中的一个操作。活动会话还提供一个 OpenAI 兼容的 chat completions 端点，因此现有的 OpenAI 客户端代码可以直接从它采样。

每一步加载一批提示词，(1) 在 GPU 上从当前模型采样。然后你的 Python 代码 (2) 为这些输出打分：一个验证器、一次奖励模型调用、一个测试框架，任何你能用代码表达的东西。(3) `forward_backward` 和 `optim_step` 把分数变成 GPU 上的梯度更新，(4) `save_weights_and_get_sampling_client()` 刷新采样器，让下一步从更新后的模型取样本。

你拥有数据、循环控制和奖励；SageMaker AI 运行受 GPU 约束的采样、梯度和检查点操作。同样的原语也覆盖**监督微调（SFT）和其他 LLM 训练技术**。对 SFT，去掉采样和奖励两步，改用在带标签样本上以 `cross_entropy` 损失调用 `forward_backward`。

### 这套 API 面向谁，在 Amazon SageMaker AI 中处于什么位置？

当你需要快速迭代周期和算法自由（比如自定义损失、新的 RL 奖励信号或多阶段流水线），但又不想自己准备或运维 GPU 基础设施时，训练会话 API 就是合适的起点。

用量按处理的 token 计费，所以你只为循环消耗的算力付费。如果你的奖励函数在你机器上给一批数据打分需要 10 秒，这期间不计 GPU 时间。相比按小时计费的 GPU，这有两个实际优势。第一，没有空闲 GPU 成本：奖励计算、数据加载、日志和调试都在计时之外发生，只有当你调用受 GPU 约束的操作时才计费。第二，成本随数据集和生成量增长，而不是随墙钟时间或集群规模增长，这让支出更容易预估，实验之间也更容易比较。对于本地计算很重的工作负载——复杂奖励模型、多工具 agentic rollout 或人在环评估——相比为整个会话预留 GPU，节省可能相当可观。

训练会话 API 是为那些工作由训练算法而非仅由数据集定义的团队打造的。因为循环由你自己组合，同样的原语可以支撑用 `cross_entropy` 损失在带标签数据上做监督微调（SFT）、用 `ppo`、`importance_sampling` 或 `cispo` 做**强化学习**（GRPO、PPO 及其他 group-relative 方法），以及用同样零件搭起的**自定义目标**，比如偏好优化或蒸馏。它们适合：

- 实现 RL 方法（GRPO、PPO、importance-sampling 变体）、自定义优势估计器或新目标函数的后训练与对齐研究者。
- 做监督微调或偏好优化、需要非标准损失、数据课程或多阶段流水线（而配置驱动的配方表达不出来）的团队。
- 需要自定义 rollout 逻辑、奖励塑形和课程的 agentic 与多轮 RL 构建者。
- 已经超出配置驱动微调、但不想承担 GPU 集群运维负担的机器学习（ML）工程师。
- 迁移现有训练循环代码的研究者，因为基于操作的编程模型能直接对上按底层 `forward_backward`、`optim_step` 和 `sample` API 写的循环。

受支持的基础模型以及各自可用的 AWS Region 列在[训练会话 API 文档](https://docs.aws.amazon.com/sagemaker/latest/dg/customizing-models-training-sessions.html)中。

#### 训练会话 API 在 Amazon SageMaker AI 中的位置

训练会话 API 位于 SageMaker AI 各模型定制选项中的一个独特位置：对训练算法的控制远多于完全托管的 [Serverless Model Customization](https://docs.aws.amazon.com/sagemaker/latest/dg/customize-model.html)，而运维负担远少于在 [Amazon SageMaker Training Jobs](https://docs.aws.amazon.com/sagemaker/latest/dg/how-it-works-training.html) 或 [Amazon SageMaker HyperPod](https://aws.amazon.com/sagemaker/ai/hyperpod/) 上训练。

## 训练循环剖析：在数学题上做 GRPO

本节拆解一个最小强化学习循环，展示这些操作如何咬合。任务是 [GSM8K](https://github.com/openai/grade-school-math)，一个约 8,500 道小学数学应用题的基准，每题一个数字答案，例如：

> Natalia 四月份把发卡卖给了 48 位朋友，五月份卖出的发卡数量是四月的一半。Natalia 在四月和五月一共卖了多少个发卡？→ 72

我们用分组相对策略优化（GRPO）为 OpenAI 的 **GPT-OSS 20B** 训练一个 LoRA 适配器：对每个问题，模型生成若干回答，每个回答按正确性打分，超过组内平均的回答被强化。完整可运行的示例在 [Amazon SageMaker 示例仓库](https://github.com/aws/amazon-sagemaker-examples/tree/default/%20%20%20%20%20model_customization/sm-training_sessions_grpo_gsm8k)中。

打开会话之前，请先完成文档中的[先决条件](https://docs.aws.amazon.com/sagemaker/latest/dg/training-sessions-prereqs.html)。

### 打开会话

创建一个会话，然后从中取得 tokenizer 和一个 `SamplingClient`：

```
from sagemaker.train.training_session import ServiceClient, SamplingParams, AdamParams

svc = ServiceClient(role_arn=role, region=REGION)

training_client = svc.create_lora_training_client(
    "openai/gpt-oss-20b",                        # a name from svc.list_base_models()
    training_session_name=SESSION_NAME,
    rank=32, alpha=64,                           # LoRA rank and scaling factor
    model_package_group_arn=MODEL_PACKAGE_GROUP_ARN,
    s3_output_path=OUTPUT_S3_PATH,
)
tokenizer = training_client.get_tokenizer()
sampling_client = training_client.create_sampling_client()
```

### 定义奖励和优势

任务相关的逻辑是两个跑在你机器上的短函数：

```
def compute_reward(response_text, ground_truth):
    predicted = extract_answer(response_text)      # parse the number after "#### "
    return 1.0 if predicted == ground_truth else 0.0

def compute_advantages(rewards):
    rewards = np.array(rewards)
    advantages = rewards - rewards.mean()          # center within the group (the GRPO baseline)
    return advantages / (rewards.std() + 1e-8)     # normalize
```

### 循环

每一步都遵循图 2 中的四个阶段。`draw`、`build_prompt` 和 `build_training_datum` 是示例里的短辅助函数：

```
for step in range(NUM_STEPS):
    datums, pending = [], []
    # (1) sample K responses per question in one request each (GPU); returns a future right away
    for question, ground_truth in draw(PROMPTS_PER_STEP):          # data loading is local
        prompt = tokenizer.encode(build_prompt(question), add_special_tokens=False)
        pending.append((prompt, ground_truth, sampling_client.sample(
            prompt, num_samples=K,
            sampling_params=SamplingParams(max_tokens=512, temperature=0.7, top_p=0.9))))

    for prompt, ground_truth, future in pending:
        result = future.result()                                    # wait once the batch is in flight
        # (2) score each response, then center the rewards within the group (local)
        rewards = [compute_reward(tokenizer.decode(s.tokens), ground_truth) for s in result.sequences]
        advantages = compute_advantages(rewards)
        datums += [build_training_datum(prompt, s, a) for s, a in zip(result.sequences, advantages)]

    # (3) one gradient step over the batch (GPU); the optimizer step is sequenced behind it
    fwd_bwd_op = training_client.forward_backward(datums, loss_fn="ppo")
    optim_op = training_client.optim_step(AdamParams(learning_rate=1e-5))
    fwd_bwd_op.result(), optim_op.result()

    # (4) refresh the sampler so the next step's rollouts come from the updated policy (GPU)
    sampling_client = training_client.save_weights_and_get_sampling_client()

training_client.stop()
```

有三个细节让这个循环成立：

操作返回 future。每一次受 GPU 约束的调用都会立刻返回一个 `APIFuture`：请求被排队，由后台提交器发出，`.result()` 等待取值。循环会在等待任何一个之前先提交一步里全部的采样请求，所以整批数据并发生成。训练操作按你调用的顺序执行，因此 `optim_step` 可以在 `forward_backward` 完成之前就被提交。

datum 携带损失所需的一切。`build_training_datum` 打包提示词与回答 token、来自 `sample()` 的逐 token logprob、优势值，以及一个把提示词排除在损失之外的 `weights` 掩码。

检查点就是模型包。每次保存都会在你的模型包组里注册一个版本，包括上面循环里每一步的采样器刷新。训练结束后，再两次保存会加上一个用于部署的合并模型，以及一份带权重和优化器、可恢复的状态。

```
training_client.save_weights_for_sampler(merge_weights=True).result()   # merged, deployable model
training_client.save_state().result()                                   # resumable state (weights + optimizer)
```

要恢复，就用 `create_training_client_from_state_with_optimizer` 从最新检查点启动一个新会话。

运行中的会话会占用你的并发会话配额，直到你调用 `stop()` 或它过期，所以做完就停掉它——出错路径里也一样——或者把客户端放在 `with` 块中打开。合并后的检查点可以部署到实时端点。如果想改为把检查点作为 LoRA 适配器提供，请见 cookbook 的[部署 notebook](https://github.com/aws/sagemaker-training-sessions-cookbook/blob/main/notebooks/deploy_to_sagemaker_inference.ipynb)。

在我们这次示例运行中，40 道题上跑 10 个训练步骤，把留出集准确率从 56% 提升到 75%。

## 真实工作负载：在竞赛编程上做 RL

GSM8K 让机制保持可见，但生产级 RL 工作负载还要加上：更长的生成、多轮交互、外部评分器，以及足以让 GPU 保持忙碌的吞吐量。[SageMaker training sessions cookbook](https://github.com/aws/sagemaker-training-sessions-cookbook) 把这套工程打包成建立在同样操作之上的可复用训练循环。对一个新 RL 任务，你写一个环境：模型看到什么、它的答案如何被打分、以及它能否再获得一轮机会。cookbook 负责批处理、chat 模板、优势估计、采样与训练重叠、验证、带恢复的检查点以及逐步指标，并记录每次运行的配置以便复现。`code_rl` 配方用它来训练一个模型做竞赛编程题。

任务。题目来自 DeepCoder 数据集（训练用 PrimeIntellect、TACO 和 LiveCodeBench；测试用 Codeforces 和 LiveCodeBench）。模型写一个 Python 解法，在你机器上的 [SandboxFusion](https://github.com/bytedance/SandboxFusion) 容器里针对题目的单元测试运行。全部测试通过时奖励为 1，否则为 0；若回答中不含代码块，再扣 0.1。

多轮工具使用。有两轮时，模型可以调用 `check_solution` 工具，读取测试结果，并在最终评分前修改答案。工具调用和结果按模型原生 chat 格式呈现，因此模型训练时用的 token 格式与推理时一致。

这个配方在最小循环之上增加了什么：

- **采样与训练重叠：** rollout worker 在训练器跑一步时继续生成。从较旧策略采样的回答组，如果最多只旧 k 步就继续使用，否则重新排队，`cispo` 损失会修正策略差异。
- **流式梯度计算：** `forward_backward` 在一组组数据完成时按子批次提交，而不是每步提交一次。
- **留出集验证、检查点恢复和逐步指标**，可选发布到 [SageMaker managed MLflow](https://docs.aws.amazon.com/sagemaker/latest/dg/mlflow.html)。

我们为 GPT-OSS 20B 训练了一个 LoRA 适配器（rank 32），跑 50 步，每步 128 道题、每题 8 个回答，使用两轮交互和 k=3 的陈旧度上界。训练奖励从 0.46 升到 0.60，在 200 道留出测试题上的准确率从 40% 升到 50.5%。

## 结论

SageMaker AI 训练会话 API 把抽象边界下移到训练操作：你在自己机器上用 Python 写训练循环，服务在托管 GPU 上运行它，负责模型与 LoRA 加载、分布式执行、故障恢复和检查点。一个完整的 GRPO 循环归结为四个操作——`sample`、`forward_backward`、`optim_step` 和 `save_weights_and_get_sampling_client`——奖励和优势逻辑留在你自己的代码里。同样的操作可以扩展到带沙箱评分的多轮、使用工具的 RL，正如 Code RL 配方所示。

自定义奖励、agentic rollout、逐步调试和刚发表的新技术都用同一套编程模型：算法留在你的循环里，SageMaker AI 运行 GPU。

上手：

- 从 [SageMaker training sessions cookbook](https://github.com/aws/sagemaker-training-sessions-cookbook) 里挑一个配方，比如 [Code RL](https://github.com/aws/sagemaker-training-sessions-cookbook/tree/main/training_sessions_cookbook/recipes/code_rl)。
- 运行 Amazon SageMaker 示例仓库中的 [GSM8K 示例](https://github.com/aws/amazon-sagemaker-examples/tree/default/%20%20%20%20%20model_customization/sm-training_sessions_grpo_gsm8k)，换成你自己的奖励函数。
- 阅读[训练会话 API 文档](https://docs.aws.amazon.com/sagemaker/latest/dg/customizing-models-training-sessions.html)，了解先决条件、配额、Region、受支持的模型和 API 参考。
