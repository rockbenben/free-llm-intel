# 使用 Arize AI 实现 Amazon Bedrock Agents 可观测性

*本文与来自 Arize AI 的 John Gilhuly 合写。*

借助 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/)，你可以在应用中构建并配置自主 agent。agent 帮助最终用户基于组织数据和用户输入完成各项操作。agent 编排 foundation model（FM）、数据源、软件应用与用户对话之间的交互。此外，agent 会自动调用 API 以执行操作，并调用 knowledge base 为这些操作补充信息。通过集成 agent，你可以加速开发工作，交付生成式 AI 应用。借助 agent，你可以为客户自动执行任务，并为他们解答问题。例如，你可以创建一个 agent，帮助客户处理保险理赔或进行旅行预订。你无需预置容量、管理基础设施或编写自定义代码。[Amazon Bedrock](https://aws.amazon.com/bedrock/) 负责 prompt engineering、memory、监控、加密、用户权限与 API 调用。

AI agent 代表了应用做决策以及与用户交互方式的根本转变。与传统软件系统遵循预设路径不同，AI agent 采用常常以“黑箱”方式运作的复杂推理。对于希望在 AI 落地中保持可靠性、效率和最佳性能的组织而言，监控 AI agent 带来了独特的挑战。

今天，我们很高兴宣布 [Arize AI](https://arize.com/) 与 Amazon Bedrock Agents 之间的一项全新集成，它解决了 AI 开发中最重大的挑战之一：可观测性。agent 可观测性是 AI 运营的关键方面，它能深入揭示你的 Amazon Bedrock agent 如何执行、交互和完成任务。它涉及跟踪和分析 agent 活动的层级化 trace，从高层用户请求一直到单个 API 调用与工具调用。这些 trace 构成结构化的事件树，帮助开发者理解用户交互在 agent 决策过程中的完整旅程。需要重点关注的指标包括响应延迟、token 用量、运行时异常，以及检查 function calling。随着组织将 AI 落地从概念验证扩展到生产环境，理解和监控 AI agent 行为变得日益关键。

Arize AI 与 Amazon Bedrock Agents 的集成为开发者提供了全面的可观测性工具，用于追踪、评估和监控 AI agent 应用。该方案带来三项主要收益：

- **全面的可追溯性** – 洞察 agent 执行路径的每一步，从最初的用户查询一直到知识检索与操作执行
- **系统化评估框架** – 套用一致的评估方法，衡量并理解 agent 性能
- **数据驱动的优化** – 运行结构化实验，比较不同的 agent 配置并找出最优设置

Arize AI 服务提供两个版本：

- [Arize AX](https://arize.com/generative-ai/) – 企业级解决方案，提供高级监控能力
- [Arize Phoenix](https://docs.arize.com/phoenix) – 开源服务，让开发者也能使用追踪与评估

在本文中，我们演示用于追踪与评估的 [Arize Phoenix](https://docs.arize.com/phoenix) 系统。Phoenix 可以运行在你的本地机器、Jupyter notebook、容器化部署或云端。我们探讨这项集成如何工作、它有哪些关键特性，以及你如何在自己的 Amazon Bedrock Agents 应用中实施它，以增强可观测性并保持生产级可靠性。

## 方案概述

大语言模型（LLM）追踪记录请求在 LLM 应用的多个步骤或组件之间传播时所经过的路径。它提升了应用或系统健康度的可见性，并让调试那些难以在本地复现的行为成为可能。例如，当用户与 LLM 应用交互时，追踪可以捕获一系列操作，如文档检索、embedding 生成、语言模型调用和响应生成，从而提供请求执行的详细时间线。

为了让应用能够发出供分析的 trace，应用必须被插桩（instrumented）。你的应用可以手动插桩，也可以自动插桩。Arize Phoenix 提供了一组插件（instrumentor），你可以把它们加入应用的启动流程来执行自动插桩。这些插件为你的应用收集 trace，并（通过 exporter）导出，供采集与可视化使用。Phoenix 服务器是一个采集器和 UI，帮助你实时排查应用问题。当你运行 Phoenix 时（例如 px.launch_app() 容器），Phoenix 就开始从向其导出 trace 的应用接收 trace。对 Phoenix 而言，instrumentor 通过一个名为 [OpenInference](https://github.com/Arize-ai/openinference) 的单一仓库管理。OpenInference 为多种语言的主流机器学习（ML）SDK 与框架提供一套插桩。它是一套约定与插件，与 [OpenTelemetry](https://opentelemetry.io/) 和 online transaction processing（OLTP）互补，使 AI 应用可被追踪。Phoenix 目前支持基于 HTTP 的 OTLP。

对 AWS 而言，Boto3 提供 AWS 服务的 Python 绑定，其中包括 Amazon Bedrock，后者可访问多种 FM。你可以使用 OpenInference 对这些模型的调用进行插桩，从而为基于这些模型构建的应用提供与 OpenTelemetry 对齐的可观测性。你也可以使用 OpenInference 捕获对 Amazon Bedrock agent 调用的 trace，并在 Phoenix 中查看。下面的高层架构图展示了一个使用 Amazon Bedrock Agents 创建的 LLM 应用，它已被插桩以将 trace 发送到 Phoenix 服务器。

在以下章节中，我们演示如何通过安装 `openinference-instrumentation-bedrock` 库，自动为与 Amazon Bedrock 或 Amazon Bedrock agent 的交互插桩，以便在 Phoenix 中进行可观测性分析、评估与故障排查。

## 在启用追踪的情况下运行 agent

创建一个函数来运行 agent 并捕获其输出：

```
@using_metadata(metadata)
def run(input_text):
    session_id = f"default-session1_{int(time.time())}"

    attributes = dict(
        inputText=input_text,
        agentId=agent_id,
        agentAliasId=agent_alias_id,
        sessionId=session_id,
        enableTrace=True,
    )
    response = bedrock_agent_runtime.invoke_agent(**attributes)

    # Stream the response
    for _, event in enumerate(response["completion"]):
        if "chunk" in event:
            print(event)
            chunk_data = event["chunk"]
            if "bytes" in chunk_data:
                output_text = chunk_data["bytes"].decode("utf8")
                print(output_text)
        elif "trace" in event:
            print(event["trace"])
```

用几个示例查询测试你的 agent：

```
run ("What are the total leaves for Employee 1?")
run ("If Employee 1 takes 4 vacation days off, What are the total leaves left for Employee 1?")
```

你应当把这些查询替换为你的应用所面向的查询。执行这些命令后，你应该能在 notebook 输出中看到 agent 的响应。Phoenix 插桩会自动捕获这些交互的详细 trace，包括 knowledge base 查询、编排步骤和工具调用。

## 在 Phoenix 中查看捕获的 trace

- 完整的对话上下文
- knowledge base 查询与结果
- 工具或 action group 调用与响应
- agent 推理与决策步骤

Phoenix 的追踪与 span 分析能力在原型和调试阶段很有用。通过用 Phoenix 为应用代码插桩，团队可以深入洞察执行流程，从而轻松定位并解决问题。开发者可以下钻到特定 span、分析性能指标，并访问相关日志与 metadata，以简化调试工作。借助 Phoenix 的追踪能力，你可以监控以下内容：

- **应用延迟** – 找出延迟瓶颈，处理 LLM、retriever 及其他组件中缓慢的调用，从而优化性能与响应速度。
- **token 用量** – 详细拆解 LLM 调用的 token 用量，从而找出并优化最昂贵的 LLM 调用。
- **运行时异常** – 捕获并检查关键运行时异常，例如限流事件，帮助你主动应对并缓解潜在问题。
- **检索到的文档** – 检查 retriever 调用期间检索到的文档，包括分数与返回顺序，从而洞悉检索过程。
- **embedding** – 检查用于检索的 embedding 文本及其底层 embedding 模型，从而验证并改进你的 embedding 策略。
- **LLM 参数** – 检查调用 LLM 时使用的参数，例如 temperature 与 system prompt，以便实现最优配置并便于调试。
- **prompt 模板** – 理解 prompting 步骤中使用的 prompt 模板及其所套用的变量，从而微调并改进你的 prompting 策略。
- **工具描述** – 查看 LLM 被赋予访问权限的工具的描述与函数签名，以便更好地理解和控制 LLM 的能力。
- **LLM function call** – 对于具备 function call 能力的 LLM（例如 Anthropic 的 Claude、[Amazon Nova](https://aws.amazon.com/ai/generative-ai/nova/) 或 Meta 的 Llama），你可以检查 LLM 输入中的函数选择与函数消息。这能进一步帮助你调试并优化应用。

## 在 Phoenix 中评估 agent

评估任何 AI 应用都是挑战。评估 agent 则更难。agent 会带来一组独特的评估陷阱需要应对。agent 的一项常见评估指标是它们的 function calling 准确率，换言之，即它们为任务选择正确工具的表现如何。例如，agent 可能走低效路径却仍然得到正确解。你怎么知道它是否走了最优路径？此外，上游的错误响应可能导致下游出现奇怪的响应。你如何定位问题的源头？Phoenix 还包含内置的 LLM 评估与基于代码的实验测试。agent 的特征在于它对世界的认知、它能执行的动作集合，以及它抵达目标所走的路径。要评估 agent，你必须评估每个组件。Phoenix 为每个步骤都准备了评估模板，例如：

- [agent 函数调用](https://docs.arize.com/phoenix/evaluation/how-to-evals/running-pre-tested-evals/tool-calling-eval)
- [agent 路径收敛](https://docs.arize.com/phoenix/evaluation/how-to-evals/running-pre-tested-evals/agent-path-convergence)
- [agent 规划](https://docs.arize.com/phoenix/evaluation/how-to-evals/running-pre-tested-evals/agent-planning)
- [agent 反思](https://docs.arize.com/phoenix/evaluation/how-to-evals/running-pre-tested-evals/agent-reflection)

你可以使用常规的 LLM 评估策略来评估单项技能与响应，例如检索评估、用 LLM 作为评判者的分类、幻觉检测或问答正确性。在本文中，我们演示 agent function calling 的评估。你可以使用 Agent Function Call 评估来判断模型选择所用工具的准确度、从用户查询中提取正确参数的程度，以及生成工具调用代码的质量。既然你在上一步已为 agent 完成追踪，下一步就是添加评估来衡量其性能。agent 的一项常见评估指标是它们的 function calling 准确率（它们为任务选择正确工具的表现如何）。请完成以下步骤：

- 到目前为止，你只用了较轻量的 Phoenix OTEL 追踪库。要运行评估，你必须安装完整库：

`!pip install -q arize-phoenix — quiet`

- 导入必要的评估组件：

```
import re
import json
import phoenix as px
from phoenix.evals import (
TOOL_CALLING_PROMPT_RAILS_MAP,
TOOL_CALLING_PROMPT_TEMPLATE,
BedrockModel,
llm_classify,
)
from phoenix.trace import SpanEvaluations
from phoenix.trace.dsl import SpanQuery
```

以下是我们用于 agent function calling 的 prompt 模板：

```
TOOL_CALLING_PROMPT_TEMPLATE = """

You are an evaluation assistant evaluating questions and tool calls to
determine whether the tool called would answer the question. The tool
calls have been generated by a separate agent, and chosen from the list of
tools provided below. It is your job to decide whether that agent chose
the right tool to call.

    [BEGIN DATA]
    ************
    [Question]: {question}
    ************
    [Tool Called]: {tool_call}
    [END DATA]

Your response must be single word, either "correct" or "incorrect",
and should not contain any text or characters aside from that word.
"incorrect" means that the chosen tool would not answer the question,
the tool includes information that is not presented in the question,
or that the tool signature includes parameter values that don't match
the formats specified in the tool signatures below.

"correct" means the correct tool call was chosen, the correct parameters
were extracted from the question, the tool call generated is runnable and correct,
and that no outside information not present in the question was used
in the generated question.

    [Tool Definitions]: {tool_definitions}
"""
```

- 由于我们只评估输入、输出和 function call 列，先把它们提取到一个更易用的 dataframe。Phoenix 提供了一种方法，可查询你的 span 数据并直接导出你关心的值：

```
query = (
SpanQuery()
.where(
# Filter for the `LLM` span kind.
# The filter condition is a string of valid Python boolean expression.
"span_kind == 'LLM' and 'evaluation' not in input.value"
)
.select(
question="input.value",
outputs="output.value",
)
)
trace_df = px.Client().query_spans(query, project_name=project_name)
```

- 下一步是把这些 trace 准备成一个 dataframe，包含输入、tool call 和 tool definition 三列。解析 JSON 输入与输出数据来创建这些列：

```
def extract_tool_calls(output_value):
try:
tool_calls = []
# Look for tool calls within <function_calls> tags
if "<function_calls>" in output_value:
# Find all tool_name tags
tool_name_pattern = r"<tool_name>(.*?)</tool_name>"
tool_names = re.findall(tool_name_pattern, output_value)

# Add each found tool name to the list
for tool_name in tool_names:
if tool_name:
tool_calls.append(tool_name)
except Exception as e:
print(f"Error extracting tool calls: {e}")
pass

return tool_calls
```

- 把该函数应用到 `trace_df.output.value` 的每一行：

```
trace_df["tool_call"] = trace_df["outputs"].apply(
lambda x: extract_tool_calls(x) if isinstance(x, str) else []
)

# Display the tool calls found
print("Tool calls found in traces:", trace_df["tool_call"].sum())
```

- 添加用于评估的工具定义：

```
trace_df["tool_definitions"] = (
"phoenix-traces retrieves the latest trace information from Phoenix, phoenix-experiments retrieves the latest experiment information from Phoenix, phoenix-datasets retrieves the latest dataset information from Phoenix"
)
```

现在 dataframe 已准备好，你可以使用 Phoenix 内置的 LLM-as-a-Judge 模板进行工具调用评估。下面的方法接收待评估的 trace dataframe、我们的内置评估 prompt、所用评估模型，以及一个 rails 对象，用于把模型响应归置到一组二分类响应上。我们还指示模型为其响应提供解释。

- 运行工具调用评估：

```
rails = list(TOOL_CALLING_PROMPT_RAILS_MAP.values())

eval_model = BedrockModel(session=session, model_id="us.anthropic.claude-3-5-haiku-20241022-v1:0")

response_classifications = llm_classify(
    data=trace_df,
    template=TOOL_CALLING_PROMPT_TEMPLATE,
    model=eval_model,
    rails=rails,
    provide_explanation=True,
)
response_classifications["score"] = response_classifications.apply(
    lambda x: 1 if x["label"] == "correct" else 0, axis=1
)
```

我们使用以下参数：

- **df** – 待评估案例的 dataframe。该 dataframe 必须有与默认模板匹配的列。
- **question** – 向模型发出的查询。如果你[从 Phoenix 导出 span](https://docs.arize.com/phoenix/tracing/how-to-tracing/importing-and-exporting-traces/extract-data-from-spans) 来评估，这就是导出数据中的 `llm.input_messages` 列。
- **tool_call** – 关于所调用工具及所含参数的信息。如果你从 Phoenix 导出 span 来评估，这就是导出数据中的 `llm.function_call` 列。

- 最后，把评估结果记录到 Phoenix：

```
px.Client().log_evaluations(
SpanEvaluations(eval_name="Tool Calling Eval", dataframe=response_classifications),
)
```

运行这些命令后，你会在 Phoenix 仪表板看到评估结果，从而洞察 agent 使用其可用工具的有效程度。
