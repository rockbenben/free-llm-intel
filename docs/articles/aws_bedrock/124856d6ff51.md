# Natera 基于 Amazon Bedrock AgentCore 的智能预约调度

对于已经在应对治疗过程的肿瘤患者来说，预约抽血本不该是一件麻烦事。Natera 的服务由 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 提供支持，让抽血师可以上门为患者服务，帮助 Natera 提供更便捷的体验。

[Natera](https://www.natera.com/) 是一家专注于游离 DNA 检测的全球诊断公司，希望用更好的方式取代人工调度电话，从而改善患者体验。借助 Amazon Bedrock AgentCore，他们构建了一个自动化语音 agent，让患者通过对话即可预约，同时满足医疗保健领域所需的准确性和合规标准。

本文分享构建于 Bedrock AgentCore 之上的 Natera 语音调度 agent 背后的架构模式与设计决策。你将了解 Natera 和 AWS 如何设计一个实时语音 agent，通过三项核心架构原则将电话通信、基础模型和后端服务连接起来：双 WebSocket 桥接模式、事件驱动的延迟掩盖技术，以及用于对话途中身份认证的渐进式信任模型。本文解释了每一项设计选择背后的理由，也展示了该架构如何在 500 次端到端通话模拟的验证中达成 100% 的工具调用准确率，在每次完成通话成本低于 USD 0.01 的情况下，感知延迟低于 7 秒。本文呈现的系统设计展示了每个 AWS 服务如何连接，以及 Natera 为何在实施中做出特定的集成选择。

我们将带你了解 Natera 如何从 [Amazon Elastic Container Service (Amazon ECS)](https://aws.amazon.com/ecs/) 迁移到 [Amazon Bedrock AgentCore runtime](https://aws.amazon.com/bedrock/agentcore/)，包括团队在此过程中如何解决 WebSocket 生命周期和会话状态的挑战。

## 挑战：大规模下的调度复杂性

Natera 目前的移动抽血服务帮助患者预约上门抽血，而无需前往诊所。调度系统支撑着这一工作流。

患者打电话、完成身份验证，并提供三个期望的预约日期以及他们的服务地点。随后，人工调度团队与抽血师和供应商协调，确认所提议的时段之一。

这一工作流需要使用个人标识符和短信服务（Short Message Service，SMS）验证码进行患者身份验证，需要与多个第三方供应商系统集成以获取预约可用时间窗口，还需要为复杂场景提供优雅的回退选项。现有系统使用第三方人工智能（artificial intelligence，AI）提供商处理语音交互和编排，通过 Twilio 实现电话连接，并运行在 Amazon ECS 容器上。虽然可用，但团队发现了提升准确性、可扩展性和对话参与度的机会。

对于使用 Epic 或 Cerner 并采用标准预约工作流的组织，[Amazon Connect Health](https://aws.amazon.com/health/connect-health/) 提供预置的患者互动 agent，开箱即用地处理验证和调度。Natera 的用例需要定制化的供应商协调和预置方案目前无法支持的电话灵活性，这使 AgentCore 成为合适的架构基础。

## 为何选择 Amazon Bedrock AgentCore

Natera 选择在 Amazon Bedrock AgentCore 上重建其调度 agent。这是一项可使用任意框架或模型大规模构建、连接和优化 agent 的服务。他们是在评估了该服务如何应对其核心运营挑战后做出这一选择的。团队需要借助自主 AI agent 大规模满足客户请求，同时不承担管理容器基础设施或扩展配置的负担。AgentCore 的全托管架构消除了这类运营开销。

同样重要的是在处理延迟期间维持较高的客户参与度，他们通过 Amazon Bedrock 使用快速基础模型生成情境感知的中间响应来实现这一点，使对话保持自然。内置的记忆管理系统会存储患者先前的活动，让 agent 能够提供个性化、主动的支持。

Natera 还因为 AgentCore 内置的可观测性而采用它。每当 agent 处理一个请求，AgentCore 都会捕获每一步所发生事情的详细追踪。团队可以查看调用了哪些工具、每一步耗时多久，以及模型做出了什么决定。他们可以端到端地跟踪单个会话，精准定位延迟发生在何处，无论是在模型推理、工具执行还是记忆检索中。对于准确性和性能不容妥协的医疗环境，这种可见性使团队能够快速识别和修复问题，而无需猜测。

## 解决方案概览

本节描述 Natera 语音调度 agent 的端到端架构。该设计遵循三项核心原则，使其能够适配其他实时语音 AI 用例：

- 双 WebSocket 桥接模式通过在电话流式传输和模型推理之间放置一个编排层，将二者分离。这意味着系统维持一个到电话提供商的 WebSocket 连接和另一个到基础模型的连接，由编排器管理两者之间的流转。这种分离让团队可以独立替换任意一侧，例如用 Amazon Connect Health 替换 Twilio，或用 Amazon Nova 替换 OpenAI，而无需重新设计整个系统。
- 事件驱动的延迟掩盖将感知延迟视为一等的设计关注点，而不是试图优化每个单独组件的原始速度。当 agent 需要调用工具（例如检查预约可用性）时，该架构会并行生成情境化的填充响应，这样患者听到的是自然的回应而非沉默。即使后端操作需要数秒才能完成，这种方法也能让对话保持流畅。
- 渐进式信任模型随着对话展开逐步提升身份验证和记忆访问权限。系统不要求患者在任何事情发生之前就预先验证身份，而是以低信任交互开始，随着患者通过身份验证，逐步授予对更敏感信息的访问。这形成了自然的对话流程，而非那种让人感觉像走流程的"先设卡再继续"式体验。

该架构的取舍点在于编排复杂度的增加。管理两个并发 WebSocket 连接、并行的填充生成以及渐进式记忆会话，需要仔细的状态管理。对于更简单的用例（例如单轮问答或纯文本 agent），不采用桥接模式的直接集成会降低开销。

### 从 Amazon ECS 到 AgentCore runtime 的迁移方法

Natera 将其工作负载从 Amazon ECS 迁移到 Bedrock AgentCore runtime。这是一个全托管 serverless 环境，在隔离的 microVM 中托管 AI agent，每个 microVM 拥有专用的 CPU、内存和文件系统资源。

为开始迁移，团队将语音编排逻辑与容器特定的基础设施代码（如健康检查端点、扩展策略和部署清单）解耦。完成分离后，他们重构了 agent 的入口点，使其符合 AgentCore runtime 的调用接口，用 AgentCore handler 模式取代了 HTTP 服务器初始化。最后一步是将会话状态从容器本地存储迁移到 Bedrock AgentCore memory，后者提供了持久的跨会话存储能力，而无需管理单独的状态存储。

团队在迁移中遇到两个主要挑战。一是让长生命周期的 WebSocket 连接适配 AgentCore runtime 的执行模型。与可以无限期运行的 Amazon ECS 任务不同，AgentCore 的 microVM 作用域限定在一次调用内。团队通过在 agent 的运行时上下文中实现连接池来解决这一问题，使 WebSocket 会话能够在单次通话期间持续存在，同时由 AgentCore 管理底层计算生命周期。会话状态的连续性是另一个挑战。在 Amazon ECS 上，对话状态保存在容器本地内存中，重启后即丢失。迁移到 AgentCore memory 需要重新设计状态模型，使其外部化并以 actor ID 为键，这最终提升了可靠性，但需要重构所有状态读写路径。

这消除了管理容器扩展、健康检查和部署流水线的运营开销。

### 请求流程详解

以下各节描述请求流程，从患者拨入的那一刻到他们收到确认的预约。

#### 呼叫发起与语音流式传输

当患者拨打调度线路时，Twilio 与运行在 AgentCore runtime 上的 agent 建立双向 WebSocket 连接。同时，agent 打开第二个到实时语音处理 API 的 WebSocket 连接。这形成了一个实时音频桥。

在入站路径上，Twilio 将原始通话媒体（患者语音）流式传输到语音处理服务以进行意图识别。在出站路径上，语音处理服务生成音频响应，并通过 agent 将其流式传回 Twilio，将合成语音传送到患者手机。

运行在 AgentCore runtime 上的 agent 充当这两个 WebSocket 通道之间的编排层。它拦截来自语音处理服务的工具调用请求，执行业务逻辑，并将结果注入回对话上下文。

#### 情境感知的填充生成（延迟掩盖）

当 agent 处理工具调用时（第 3-5 步），一个并行的填充循环会激活以维持对话流畅。该技术的运作方式如下：

agent 监控来自语音处理服务 WebSocket 流的工具调用事件。当工具调用开始时，填充循环会以一个根据该特定工具预期持续时间校准的计时器启动（例如，身份验证 API 平均 2.5 秒，调度 API 平均 4 秒）。

这些校准值来自团队在可观测性阶段执行的一套结构化测量流程。首先，他们使用 AgentCore runtime 内置的追踪导出功能，在两周的代表性通话流量窗口内，将每个工具的延迟事件路由到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) Logs。其次，他们查询日志以构建每个工具调用的延迟分布，提取 P50（中位数）响应时间作为基线。第三，他们从每个工具的 P50 中减去一秒来设定填充触发点，让 Claude Haiku 的填充请求有时间完成，并在大多数通话者察觉到沉默之前注入。

结果是一张按工具查询的表（例如，身份验证在 1.5 秒触发，调度在 3.0 秒触发），当新的工具调用开始时，填充循环会参考这张表。采用这一模式的团队可以通过使用支持百分位的日志分析工具，针对自己的工具延迟分布重复相同的三个步骤，来重新推导出自己的表。

在校准的时间点（通常是工具调用开始后 1.5 秒），agent 通过 Amazon Bedrock 发送请求以生成情境化响应。prompt 遵循以下模板结构：

> 你是一名调度助手。系统当前正在执行 [TOOL_NAME]。患者最后说："[LAST_UTTERANCE]" 当前工作流步骤：[STEP_NAME] 生成恰好一个短句（少于 15 个词），要求：– 自然地承认短暂等待 – 不承诺具体结果 – 与当前步骤的情境相匹配

系统生成一句填充语句（例如"让我调出你的可用时段"或"我正在向当地服务商确认可用性"）。生成的填充内容作为中间音频响应注入对话上下文。如果工具调用在填充间隔之前完成，填充内容会被抑制。这种事件驱动的方法避免了对快速操作产生不必要的填充，同时掩盖了较慢操作的延迟。

#### 患者身份验证与记忆转移

agent 通过分层验证流程对患者进行身份验证，该流程使用 AgentCore memory 的会话管理能力。

流程从电话号码识别开始。agent 使用 SHA-256 对来电号码进行哈希，并在通过 AgentCore memory 的 [session management API](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-memory.html) 创建新会话时，将该哈希值用作 actor ID。这会创建一个未经过身份验证的会话，agent 在其中存储早期的对话上下文，例如问候语和初始意图，而不暴露敏感的患者数据。

随着对话推进，agent 通过收集患者的个人标识符执行完整的身份验证。在针对 Natera 身份验证服务成功验证后，agent 使用已验证的患者 ID 作为 actor ID 创建一个新的已认证会话，建立对患者完整历史记录的访问权限。

两个会话都建立后，agent 迁移对话历史。它从未认证会话中检索对话轮次，并通过 AgentCore memory 的会话历史 API 将它们注入已认证会话（参见 [AgentCore memory documentation](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-memory.html)）。这提供了连续性，而无需患者重复信息。随后，未认证会话被标记为已合并，并从未来的检索中排除。

这种转换模式支持渐进式信任。回答一般问题等基本交互以电话号码级别的识别进行。而确认预约或访问健康记录等敏感操作则需要完整验证。

#### 个性化上下文检索

在完成身份验证后，agent 从两个来源检索患者的历史上下文。从 Bedrock AgentCore memory 中，agent 检索先前的对话历史、预约偏好以及来自以往交互的活动数据。AgentCore memory 同时提供短期存储（当前会话对话）和长期存储（跨会话的患者模式）。底层数据持久化在 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 中，以大规模提供持久、低延迟的读写访问。

从 [Amazon Managed Streaming for Apache Kafka (Amazon MSK)](https://aws.amazon.com/msk/) 和 [AWS Lambda](https://aws.amazon.com/lambda/) 事件流水线中，agent 接收来自其他渠道的患者活动事件（Web 门户上的活动、先前的 SMS、电子邮件和通话流量）。一个 Lambda 函数使用来自 Amazon MSK 的事件，并将相关活动摘要写入 AgentCore memory。这使语音 agent 即使对于首次使用 AI 的患者也能拥有全面的上下文。

#### 知识检索增强生成（RAG）

患者在调度通话期间经常会询问有关抽血流程、预期情况、准备事项或保险覆盖的问题。这些问题往往超出 agent 预定义的 prompt 范围。

系统使用 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)（全托管的检索能力）实时扩展 agent 的知识。Natera 将常见问题文档、流程指南和策略信息存储在 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 中，无需维护专用的向量数据库基础设施。[Amazon Titan Text Embeddings V2](https://aws.amazon.com/bedrock/titan/) 将文档和查询转换为向量表示以进行语义搜索。定制的分层分块策略在多个细节层级（章节、段落、句子）对文档进行切分。这支持与患者问题的具体程度相匹配的精准检索。

基于开发阶段使用包含 200 个代表性患者查询的数据集进行的内部测试，该配置对一般患者查询实现了超过 90% 的回答准确率。这使得对话能够持续进行，而无需转接人工客服。

#### 预约调度与确认

在患者通过身份验证并加载其偏好后，agent 执行核心调度工作流。agent 首先检索产品类型和订单信息，以便在继续之前播报重要的产品特定提醒。然后，它根据患者的订单信息评估可用的预约时间窗口，并收集三个期望的预约日期以及患者的服务地点。agent 与其他 Natera 服务交互，提交移动抽血预约请求，并将预约详情告知患者。最后，它将已确认的预约存储到患者的记忆档案中，以供将来参考。

有关各区域的模型可用性，请参阅 [Amazon Bedrock 中各 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

## 合规与安全

系统实现了 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 以维持对话安全和输出质量，并在 Business Associate Agreement (BAA) 下作为符合 HIPAA 资格的 AWS 服务运行。这些配置分为三个方面：数据隐私、对话安全和输出完整性。

数据隐私与访问控制是系统设计的基础。系统在 BAA 下，于符合 HIPAA 资格的 AWS 服务中处理并存储受保护的健康信息（protected health information，PHI）。Guardrails 提供输出级别的控制，阻止 agent 在语音交互中读出敏感标识符，例如 SSN、信用卡号或保险 ID，即使底层基础设施安全地处理这些数据，也有助于防止口头泄露。对处理个人信息的工具的访问受到身份验证的门槛限制。在患者通过身份验证之前，这些工具不会对 agent 开放。即使在验证之后，工具访问也严格限定在已验证患者的会话范围内。agent 没有任何技术手段去查找其他患者的数据，或为未验证的来电者获取个人信息。

语音处理架构在带有加密要求的数据处理协议下运行。Natera 正在探索全托管的 AWS 服务，以将所有音频处理保持在 BAA 边界之内。对数据驻留有更严格要求的组织可以立即采用这一路径。

对话安全 guardrails 定义了 agent 在与患者互动期间能做和不能做的边界。agent 不提供超出已验证工具调用返回内容的医疗建议、诊断或结果解读。当系统检测到脏话、痛苦信号、紧急用语或某些被标记的关键词时，会将对话升级给人工 agent。系统还会阻止 SMS 通信，直到它验证了患者的通信偏好并获得口头同意。

输出质量与 RAG 完整性 guardrails 确保 agent 的回答准确且有据可依。确定性判定会阻止重复、检测脱离上下文的响应，并在可疑内容到达患者之前对其进行标记。当 agent 与知识库交互时，幻觉检测与缓解会在 RAG 响应生成之前运行。相似度评分和相关性评估会在 RAG 响应呈现给患者之前进一步加以验证。

## 成果

经过四个月的迭代开发以及跨 500 次端到端通话模拟的测试，该解决方案在准确性和延迟方面都展现出强劲的性能。

编排器在所有 500 个测试场景的验证中实现了 100% 的工具调用准确率，正确地将每个请求路由到相应的专用 agent。参数提取同样精准：在模拟测试中，每一次工具调用都收到了结构正确的参数。这些准确性指标通过 AgentCore 内置的追踪分析得到验证，该分析记录每一次 agent 循环迭代，并将调用的工具和参数与预期输出进行比较。

感知延迟的中位数为 6.8 秒，这是从患者输入到第一个有意义响应（包括语音处理）的端到端测量值。仅 Bedrock 部分的测量值为 6.2 秒。这些数字是根据通过 AgentCore 的延迟分解检测手段，在一批有代表性的真实患者交互样本中捕获的会话时间戳计算得出。

每次通话成本保持在每次完成通话 USD 0.01 以下（按完整的端到端患者交互的总成本衡量，包括模型推理、工具执行和记忆操作，而非按单个对话轮次计算）。

语音 agent 处理从患者验证到确认的完整预约流程，包括身份验证、调度偏好和确认详情。回答准确率超过 90%，评估方式是将 agent 的回答与人工审核的调度结果基准数据集进行比较，并按预约详情、资格验证和患者特定上下文检索的正确性进行评分。

## 团队的经验教训

将该系统投入生产暴露出以下挑战：

延迟感知比原始速度更重要。早期演示显示，在用户输入与 agent 响应之间存在 3-5 秒的沉默，造成尴尬的停顿，有可能让患者放弃 AI 而转投人工 agent。团队发现瓶颈并非大语言模型（large language model，LLM）推理，而是 API 和身份验证检查等外部服务调用。突破来自这样一个观察：人工 agent 完成相同任务比 AI 耗时更长，却能自然地管理等待时间，会说"让我帮你查一下"之类的话。患者并不将此视为延迟。通过与工具执行并行生成情境化填充响应，团队将同样的原则应用于语音 agent，在不加快后端调用速度的情况下消除了通话静默。

多样化的输入测试及早暴露了盲点。语音识别对常见姓名处理良好，但会误识别不常见的族裔姓名，给患者身份验证带来挑战。团队构建了一个姓名拼写辅助工具，当置信度较低时激活，要求患者逐个字母拼写姓名。这类边缘案例只有通过对代表性患者群体进行测试才会浮现，强化了在生产部署前构建多样化测试套件的重要性。

逐步的可观测性暴露了真正的瓶颈。Bedrock AgentCore 内置的追踪分析捕获每一次 agent 循环迭代，包括工具调用延迟、LLM 推理时间和记忆检索时长。这一检测手段揭示出 70% 的感知延迟来自单一供应商 API，而非 LLM。如果没有逐步追踪，团队会优化错误的组件。端到端指标对 agentic 系统来说并不充分。每一次工具调用都需要独立的检测手段，以暴露真正的制约因素。

渐进式身份验证需要前置设计。从哈希电话号码到已认证患者 ID 的记忆交接模式运作良好，但需要从一开始就仔细规划。将渐进式信任改造到一个假定单一身份模型的 agent 中要困难得多。我们建议在编写 agent 逻辑之前，规划好你的 actor ID 策略和记忆交接流程。AgentCore memory 原生支持这一模式，但你必须显式地设计它，而不是事后添加。

## 结论

Natera 的语音 agent 已完成验证测试，现已投入生产，用于呼入移动抽血调度，并正在扩展为支持呼入和呼出通话处理的全渠道支持。移动抽血调度用例证明，AI 驱动的语音 agent 能够提供医疗级别的准确性，同时降低运营成本和患者摩擦。

早期生产数据印证了这些成果。在一个为期四周的报告窗口内，基于 AgentCore 构建的系统处理了 4,744 通电话，比先前系统增长 5.5%。它还减少了过早挂断：短通话率（30 秒以下的通话）从 22% 降至 12%，表明患者保持参与的时间更长，而不是放弃并转接人工 agent。调研回收量也显著扩大，Net Promoter Score (NPS) 的回收率攀升了 47%（从 1.09% 升至 1.60%），让团队得以更广泛地了解患者情绪。满意度得分总体保持稳定，尽管样本更大，推荐者和贬损者的占比基本未变。验证完成率略有提升（66%，此前为 64%），已解决交互的平均通话时长从 79 秒增加到 101 秒。这与让患者在流程中停留更久、而非过早升级的设计目标相一致。

展望未来，Natera 计划将这一基础扩展至运营、客户成功和实验室团队，使用 Amazon Bedrock AgentCore 作为多 agent 协调的骨干。目标是让非技术团队能够通过自然语言构建和部署 AI agent，将曾经需要工程资源的工作变成团队几分钟内即可创建的事情。随着 Natera 扩展这些能力，AgentCore runtime、AgentCore memory 和 Amazon Bedrock 的基础模型框架等服务，将继续支撑其让患者就医互动更简单、让服务团队更高效的方法。

## 后续步骤

如果你正在为医疗保健、生命科学或其他受监管行业构建语音 agent 或对话式 AI，以下是使用本文所涵盖服务入门的几种方式：

- **在 AgentCore runtime 上部署你的第一个 agent。** 如果你目前在容器上运行 agent 工作负载，并希望消除基础设施管理负担，请遵循 [AgentCore runtime getting started guide](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)，在 30 分钟内部署一个 serverless agent。
- **为现有 agent 添加会话记忆。** 如果你的 agent 在交互之间丢失上下文，或要求用户重复信息，请集成 [AgentCore memory session management APIs](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-memory.html)，以跨会话持久化对话状态，而无需管理自己的状态存储。
- **用事件驱动的填充生成降低感知延迟。** 如果你的语音 agent 在工具调用期间有明显停顿，请使用 [AgentCore streaming invocation mode](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 实现本文描述的填充生成模式，与后端操作并行生成情境化响应。
- **构建渐进式身份验证流程。** 如果你的应用处理敏感数据，且希望避免前置身份验证关卡，请使用 [AgentCore memory actor-based session model](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-memory.html)，在用户于对话途中验证身份时逐步提升信任。
