## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# U Mobile 如何使用 Amazon Bedrock AgentCore 构建代理电信运营

U Mobile 是马来西亚最新的 5G 网络提供商，始终精益运营其电信运营，通过持续自动化，以更少的资源做更多的事情。当新的人工智能功能可用时，U Mobile 探索了如何在基本生产力提升之外提高运营效率。真正的机会在更上游的地方，即运营团队如何首先诊断和解决问题。同样的精益运营准则为 AiDaH 奠定了基础：这不是一次性的技术举措，而是在不增加复杂性的情况下简化运营和扩展能力的长期旅程的下一步。

当订户无法购买数据附加组件时，解决它就不是一个简单的问题。这是一个协调问题。客户服务代理需要提取接口日志以获取错误代码。然后，同一代理必须查询业务支持系统 API 以了解订户资格，并交叉引用内部知识库以获取适用的业务策略。所有这一切都发生在多个系统中，然后才起草一个回复。当失败时，问题会升级到后端 IT 团队，订阅者的等待时间会更长。

传统的自动化工具可以帮助客服人员写出更好的回复。他们无法做的是浏览多个系统、分析结果并提出纠正措施。缩小这一差距需要基于 Amazon Bedrock AgentCore 构建的代理架构。

U Mobile 的信息系统部门 (ISD) 正是这样做的。他们与 AWS 和 AWS 合作伙伴 Axrail 合作，在 Amazon Bedrock AgentCore 上创建了 AiDaH（人工智能驱动的代理帮助台），这是一个使用任何框架或模型大规模构建、连接和优化代理的平台。两种能力决定了这个选择。托管代理运行时意味着无需运行代理基础设施。内置内存可以跨轮传送对话上下文，而无需建立单独的状态存储。在开始这一旅程的一年内，AiDaH 处理了六个业务部门的 150 多个记录的运营场景。 U Mobile 的内部测量显示，关键类别的故障单数量下降了 84.5%。

在这篇文章中，我们将介绍 AiDaH 背后的六层架构。然后，我们描述该平台下的安全基础，并以团队用于构建该平台的规范驱动方法的简短说明作为结尾。

## 问题：系统太多，摩擦太多

U Mobile 的 IT 格局反映了现代电信的典型复杂性：业务支持和客户关系管理系统、手机号码可移植平台、大数据分析和基础设施监控工具，在本地和云端混合运行。

在 AiDaH 出现之前，这种碎片化意味着即使是常规诊断也需要跨不同的系统和门户手动检查日志、查询订阅者资格以及咨询业务策略知识库。每次查找都是一次上下文切换，每次上下文切换都会浪费时间，并且每个未解决的查询都会升级到后端 IT 团队。将覆盖范围扩大到其他操作领域会使问题变得更加复杂，因为每个新系统通常都需要定制集成。

ISD 团队的战略基于三个支柱。

- **Reach**：跨后端系统实时协调的代理。
- **深度**：多步骤根本原因分析的思想链推理。
- **社区**：一个安全的多租户框架，具有基于角色的访问控制和内置护栏，可供每个部门使用。

## 旅程：从知识库到代理平台

AiDaH 的起步原则是：大处着眼，小处着手。 U Mobile 于 2025 年底通过两个试点代理和 Amazon Bedrock 知识库（一种完全托管的检索增强生成 (RAG) 功能）开始概念化。 2026 年第一季度的试点使内部 IT 服务台上线，包含 4 个代理和 20 个操作场景。到 2026 年，该平台将得到强化和扩展，增加三层路由，并在年中达到 6 个代理。 AiDaH 于 2026 年第三季度向 50 个 L2 呼叫中心和分支机构用户以及 8 名客服人员上线，目前涵盖 150 多个记录的操作场景。

## 代理在实践中意味着什么

传统人工智能辅助和代理人工智能之间的区别可以通过一个真实的例子得到最好的说明。

使用传统的人工智能助手，处理“移动数据在海外无法使用”的支持代理可以帮助起草响应和一些建议的故障排除步骤，但仍然手动检查漫游状态、验证资格、提出请求并发送最终答复。

通过AiDaH，系统可以独立检查用户的漫游配置，验证国际数据资格，并识别具体的故障点。然后，它会制定一个补救计划：重置哪些服务、推送哪些配置以及是否需要网络票证。支持代理进行审查和确认，然后执行操作。过去耗费特工时间的调查现在发生在他们阅读第一行之前。人类决策点被保留在重要的地方：此时，实时订阅者帐户上发生了一些变化。

在一个生产案例中，一位订阅者报告无法购买附加组件。 AiDaH 将故障追溯到错误代码“订阅者有挂单”。它还显示，该客户在三天内通过多个渠道尝试同一购买超过 30 次，每次尝试都被相同的基础挂单阻止。 AiDaH 在一次响应中揭示了根本原因和补救步骤。以前，这需要跨多个系统进行手动调查。

## 架构：六层，一个接口

AiDaH 在基于 Amazon Bedrock AgentCore 构建的分层架构上运行，部署在亚太地区（新加坡）区域。员工通过 Microsoft Teams 进行交互，这是一个经过深思熟虑的选择，可以满足大多数用户已经工作的情况，无需学习新的应用程序，也无需切换门户。

图1：AiDaH的分层架构

如图 1 所示，该平台分为六层。

**第一层：员工界面**

员工通过 Microsoft Teams 和由 Amazon CloudFront 提供服务并受 AWS WAF 保护的 Web 门户（具有 AWS Lambda 后端和用于编程触发器的 REST API）联系 AiDaH。

**第二层：编排**

Amazon Bedrock AgentCore 上的路由大脑。每个请求都会通过飞行前的安全检查，包括基于角色的访问控制、身份验证和护栏，然后进入成本优化的路由层。大约 70% 的请求通过确定性关键字匹配进行解析，无需模型调用，20% 通过轻量级模型进行分类，只有 10% 需要完整的编排器。能够自信地处理请求的最便宜的路径就是正在运行的路径。

**第 3 层：专业代理**

八位专家涵盖客户关系管理、客户问题管理、号码可携性、订单和 SIM 运营、基础设施监控、大数据分析、云成本管理和财务运营。它们通过 Agent2Agent (A2A) 协议进行通信，这使它们能够委派子任务并完成单个代理无法单独处理的跨系统工作流程。

**第 4 层：网关和后端 API**

AgentCore Gateway 是 Amazon Bedrock AgentCore 的一项功能，通过统一的模型上下文协议 (MCP) 接口向代理公开 U Mobile 的后端。每个网关后面都有 AWS Lambda 函数和 MCP 服务器，它们将代理意图转换为针对特定系统的调用。

**第五层：数据和知识**

Amazon Bedrock 知识库是完全托管的 RAG 功能，使用 Amazon OpenSearch Serverless 矢量存储将代理响应置于受管内容中。内容涵盖共享的企业知识库和单独的金融语料库。 AgentCore 内存是 Amazon Bedrock AgentCore 的一项功能，可跨轮维护对话上下文，Amazon DynamoDB 保存基于六层角色的访问控制模型和会话元数据。

**第 6 层：操作系统**

U Mobile 的本地和云操作系统可通过 AWS Transit Gateway 和 AWS Site-to-Site VPN（一种 IPsec 加密隧道，不暴露于公共互联网）进行访问。

### 请求如何流经各层

跟踪单个请求使各层之间的交互变得具体。假设一名支持代理在 Microsoft Teams 的 AiDaH 频道中输入了移植状态问题。

- **接口：** Teams 消息到达 AWS Lambda 函数，该函数将请求和调用者的联合身份转发给协调器。
- **飞行前检查：** 编排器根据 Amazon DynamoDB 中保存的六层基于角色的访问控制模型解析调用者，验证 AgentCore Identity（Amazon Bedrock AgentCore 的一项功能）颁发的令牌，并将 Amazon Bedrock Guardrails 应用于传入提示。未通过任何这些检查的请求将在此处停止。
- **路由：** 编排器选择可以处理请求的最便宜的层。诸如“port-in status”之类的可识别短语会确定性匹配并完全跳过模型调用。轻量级分类器的措辞含糊不清。一个新颖的或多部分的问题将交给完整的协调器。
- **代理实例化：** 选定的专业代理在 AgentCore 运行时中作为会话运行，这是 Amazon Bedrock AgentCore 的一项功能。 AgentCore 内存会对对话进行重新水化，以便代理继承订阅者号码以及先前轮次中的任何先前发现，而不是要求用户重复它们。
- **工具发现和调用：** 代理查询 AgentCore Gateway 以获取其有权使用的工具。每个网关将其后端发布为具有类型化输入和输出的 MCP 工具，因此代理可以通过名称和模式而不是通过手动编码的集成逻辑来选择工具。 Amazon Cognito 代理调用的 OAuth 授权。
- **后端调用：** 网关的 Lambda 函数或 MCP 服务器将工具调用转换为针对目标系统的请求，遍历 AWS Transit Gateway 和 Site-to-Site VPN 隧道到达本地号码可携平台。在响应到达模型之前，敏感字段在返回过程中被屏蔽。
- **推理与协作：** 如果答案跨域，代理将通过 Agent2Agent 协议进行委托。例如，一个转入查询最终会成为一个计费块，然后将其交给业务支持系统代理，并将结果合并到一个叙述中。
- **响应和审核：** 代理根据 Amazon Bedrock 知识库做出解释，然后将调查结果和建议的补救措施返回给 Teams 供人工确认。 AgentCore 可观察性是 Amazon Bedrock AgentCore 的一项功能，它将提示、工具调用、令牌计数和延迟的完整跟踪写入 Amazon CloudWatch，而 AWS CloudTrail 记录相应的 API 活动。

加入新的操作域会在步骤 5 中添加网关及其 MCP 工具定义。步骤 1-4 以及步骤 7 和 8 保持不变。稳定的核心使每个新领域的边际成本保持较低。

### Amazon Bedrock Agent 生产中的核心功能

下表将每个 AgentCore 功能映射到它在 AiDaH 中执行的工作。

| **能力** | **《AiDaH》中的角色** |
| ---| ---|
|运行时|将 AiDaH 及其子代理托管为可自动扩展的托管容器，无需配置服务器 |
|内存|维护对话上下文，例如订阅者编号、订单 ID 和先前的发现结果 |

## 巩固基础

部署可访问订户数据、计费系统和网络基础设施的代理人工智能平台需要的不仅仅是应用程序级安全性。它需要一个安全的云基础。 U Mobile 采用了双管齐下的方法：验证和增强底层 AWS Landing Zone，以及构建 Amazon Bedrock AgentCore 中的安全功能。

**登陆区安全 –** 在将 AiDaH 扩展到生产环境之前，U Mobile 聘请 AWS 对托管该平台的登陆区进行架构完善的安全审查。该审查根据 AWS 安全最佳实践验证了环境。通过 AWS Control Tower 护栏和 AWS Organizations 服务控制策略，基础设施保护是第一位的。然后，审查检查了集中式身份联合和入口和出口的网络安全控制。综合 AWS Security Hub 中的安全发现和每个架构层的加密标准完成了评估。结果是双重的：相信每个 AiDaH 组件都在独立验证的基础上运行，以及持续改进的优先路线图。

**应用程序层安全性 –** 每个代理操作都会追踪到特定的经过身份验证的用户。员工通过 Microsoft Entra ID 进行联合，AgentCore Identity 颁发授权代理调用的短期令牌。 Amazon Cognito 在网关处代理 OAuth 授权。因此，代理只能访问其调用用户有权查看的系统。基于角色的六层访问控制模型强制执行每个代理、每个工具和每个数据源的权限。敏感订阅者数据在到达模型之前会在网关处被屏蔽，并由 Amazon Bedrock Guardrails 强制执行内容策略。

每个提示、工具调用和响应都会通过 AgentCore Observability 流式传输到 Amazon CloudWatch Logs，并且 AWS CloudTrail 记录底层 API 活动。审计跟踪很重要：AiDaH 现已写入 U Mobile 的 L2 支持标准操作程序，并接受操作审计。所有计算都在私有 VPC 子网中运行，本地连接仅通过加密 VPN 进行，AWS Key Management Service (AWS KMS) 管理静态和传输中数据的加密密钥。

## 推动采用：从工具到队友

部署 AiDaH 是一项挑战。让人们信任并使用它是另一回事。

ISD 很早就认识到，采用不是技术问题，而是行为改变的挑战。员工习惯于既定的工作流程、值得信赖的工具和熟悉的升级路径。引入 AiDaH 意味着要求他们改变根深蒂固的习惯。这还意味着信任人工智能能够代表他们检索信息、诊断问题并提出后续步骤。

该团队依靠定向提示。 ISD 并没有期待开放式探索，而是为常见场景提供了结构化提示模板。这些模板将“向 AiDaH 询问任何事情”变成了“这里就是询问账单检查或转入状态的具体方法”。这减少了犹豫并产生了立竿见影的成果。当响应被证明是快速、准确且可行时，消息就会传播开来。一项内部调查对该平台的易用性评分为 4.6 分（满分 5 分），目前一线团队的日常使用已成为常态。

当AiDaH正式纳入U Mobile的L2支持标准操作程序时，发出了最明确的信号。从可选工具到可审核的 SOP 的转变标志着从实验到运营的转变。

ISD 的做法从来不是购买成品解决方案。这是关于掌控整个旅程：建立内部人工智能能力，鼓励负责任的实验，并将实用的人工智能流畅性融入日常运营节奏中。除了 AiDaH 本身之外，ISD 还维护一个专门的内部 AI 渠道，团队可以在其中分享用例、技术和早期实验。我们的目标不是将人工智能专业知识集中在一个团队中，而是将其分配出去，以便每个部门都可以在受监管的范围内自信地使用人工智能。进展不是线性的。这条道路充满了挫折和重新调整，每一次挫折都让平台和团队变得更加强大。

## 结果

根据 U Mobile 的内部测量，2026 年 1 月至 9 月期间，三个主要类别的每月故障单数量有所下降：

- 供应和网络票据下降了 84.5%。
- 一般查询下降了 81.6%。
- 计费和收费减少了 48.7%。

## 团队如何构建它：使用 Kiro 进行规范驱动开发

U Mobile 使用 Kiro（围绕规范驱动开发构建的 AWS 代理 IDE）加速了 AiDaH 的开发。在 Kiro 中，新功能从规范开始，而不是提示：首先写下并审查需求、设计和任务分解，然后根据商定的工件生成代码。对于 AiDaH 来说，这在代理和工具边界最为重要。每个新的操作域都意味着一个新的网关、一组 MCP 工具定义以及决定谁可以调用它们的基于角色的访问控制条目。首先把这些写下来，使每个新领域成为一个可重复的工作单元，而不是一个新的设计练习。

支持工具链是常规的。该团队使用 Kiro IDE 进行本地开发，并使用代理挂钩和 MCP 集成，以及用于管道自动化的 Kiro CLI。源代码控制在 GitLab 上运行，AWS CodePipeline 和 AWS CodeBuild 推动持续集成，容器映像发布到 Amazon Elastic Container Registry (Amazon ECR)，SonarQube 提供持续代码质量扫描。规范推动了代码生成。该规则让一个小团队在 12 周的冲刺节奏中从两个用例的概念验证发展到超过 150 个记录的用例。

## 关键架构决策

几个选择决定了 AiDaH 如何从概念验证扩展到生产平台。其中有四个突出，每个都降低了添加下一个操作域的成本或在平台增长时保持平台的可管理性。

**AgentCore 作为托管基础设施 –** 该团队没有构建自定义代理框架，而是使用 Amazon Bedrock AgentCore 中的内置扩展、身份、内存和可观察性功能。 AWS 管理底层的配置、扩展和修补，从而消除了整个基础设施工程层。

**用于通用工具连接的 MCP –** 模型上下文协议的标准化意味着 AiDaH 可以装载新的后端系统，而无需重建代理逻辑。每个新的操作域都需要一个新的网关，而不是一个新的集成架构。

**A2A 用于专家协作 –** Agent2Agent 协议允许领域专家相互委派子任务。涵盖客户记录、界面日志和计费数据的查询自然会跨越相关代理。

**安全基础第一 –** 在扩展到生产之前在着陆区运行架构完善的安全审查意味着每个新代理和网关都会继承安全控制，而不是事后附加。

## 下一步是什么

U Mobile 的路线图侧重于扩展广度和深度：加入额外的操作域和后端集成，同时将平台的功能从单系统查询发展到多系统相关诊断。能力模型的 8 级长期目标是从通知支持代理转向自主解决问题。

安全治理同时成熟。该团队正在根据 NIST SP 800-53、LLM 应用程序的 OWASP Top 10、CSA AI 信任框架和 MITRE ATLAS 调整实践。同时继续遵守马来西亚的个人数据保护法和马来西亚通信和多媒体委员会的法规。

## 结论

AiDaH 展示了当人工智能停止协助并开始行动时会发生什么变化。在不到一年的时间里，U Mobile 从两个代理的概念验证发展到八个专业代理，为 150 多个记录的操作场景提供服务。根据U Mobile的内部测量，关键类别的故障单下降了高达84.5%，U Mobile现已将该平台写入其正式的L2支持程序。

我们遍历了六个层，跟踪了 Teams 到本地系统的请求并返回，并描述了生产规模扩大之前的架构完善的安全审查。技术基础很重要，但不那么光鲜亮丽的工作也很重要。这意味着在扩展之前验证登陆区，编写结构化提示以便员工知道如何开始，并将采用视为行为改变问题而不是部署里程碑。面临类似系统碎片化的团队可能会发现相同的模式很有用。从托管代理运行时开始，在集成边界添加标准工具协议，并在扩展之前而不是之后运行安全审查。

方向仍然明确：安全扩展、负责任地实现自动化，并稳步迈向自主、自我修复的运营，一步一个深思熟虑、受监管的步骤。
