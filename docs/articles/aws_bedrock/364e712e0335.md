# 使用 Amazon Nova Act 构建意图驱动的 UI 测试

为了在其产品团队中规模化推广意图驱动的 UI 测试，[Epsilon](https://www.epsilon.com/)——一家隶属 [Publicis Groupe](https://www.publicisgroupe.com/) 的数据、技术与营销服务公司——选择了 [Amazon Nova Act](https://aws.amazon.com/nova/act/)。Epsilon 拥有数亿消费者档案和数千个品牌合作关系，需要能与应用的快速变更保持同步的 UI 测试，而且这套方案不能给每个产品团队都带来维护负担。

在 Epsilon 内部，Agentic Platform 团队（50 名工程师）构建共享基础设施，让其他产品团队能安全地构建、部署、治理和运行 AI agent。有了这个共享平台，各团队可以拿到一个基于 skills 的 agent 构建器，还能拿到联合身份与预检授权、模型上下文协议（MCP）集成以及跨账号开通。当某个产品团队想采用 AI 工具时，他们无需额外配置，也不必再自行解决身份、安全、浏览器基础设施或模型集成问题，就直接获得这些能力。

其中一个受管能力就是 *UI 测试*。借助 [Amazon Nova Act](https://aws.amazon.com/nova/act/) 和 [Amazon Bedrock AgentCore Browser](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html)（Amazon Bedrock AgentCore 的一项能力），Epsilon 的平台团队能够以服务的形式，为平台上的团队交付有韧性、意图驱动的测试。

在本文中，我们将梳理 Epsilon 把 UI 测试作为受管平台服务交付的架构，展示 Nova Act 与 Amazon Bedrock AgentCore Browser Tool 集成的核心代码，剖析一个具体的 18 步测试工作流，并分享最佳实践与实测结果。

## 挑战：扩大覆盖面，而不是替代行之有效之物

Epsilon 现有的 UI 测试实践并没有坏。团队维护着一套 *基于 Playwright 的回归测试套件*，用于验证其各个 Web 应用的功能，而且效果很好。直到今天，Playwright 仍是他们的回归测试脊梁。

Epsilon 看到的机会是做加法，不是纠错：

- **脚本化的 Playwright 测试**适合做确定性的回归检查。但它们与选择器和页面结构强耦合。即使底层功能完好，纯外观的 UI 变更也可能把它们弄坏。
- **多个产品团队**都需要针对各自应用的完整测试覆盖。逐团队搭建浏览器基础设施、管理依赖、对接身份系统，产生了重复劳动。
- 平台团队希望 UI 测试是一项契合其现有 agent 模型的**受管能力**，而不是一个每个接入团队都得自己运维的定制 CLI。

目标是：在现有 Playwright 回归套件之上叠加**意图驱动的测试**，并以多租户平台服务的形式交付，让每个 Epsilon 产品团队都能通过他们使用其他所有 agent 能力的同一个 API 界面来消费它。

## Epsilon 为何选择 Amazon Nova Act 与 Amazon Bedrock AgentCore Browser Tool

Epsilon 按两条要求评估了各种选项：自然语言编写测试步骤（用来补充基于选择器的 Playwright 测试），以及托管的浏览器基础设施（以契合其多租户平台模型）。Amazon Nova Act 与 Amazon Bedrock AgentCore Browser Tool 相结合，两点都能满足。

- **自然语言步骤。** 测试步骤就是由 Nova Act 执行的通俗英文指令。它们对纯外观的 UI 变更有韧性，非工程人员也能读懂。像 *“确认奖励余额可见”* 这样的步骤，比脆弱的 CSS 选择器耐用得多。
- **AWS 托管的临时浏览器会话。** 借助 Amazon Bedrock AgentCore Browser Tool，各团队获得隔离的浏览器实例，无需分发任何二进制文件，也没有显示服务器要维护。Amazon Bedrock AgentCore Browser Tool 还提供供人观察或接管（应对 CAPTCHA 或多因素认证很有用）的实时视图、到 Amazon Simple Storage Service (Amazon S3) 的会话录制，以及 AWS CloudTrail 审计，且全部无需额外配置。
- **基于 AWS Identity and Access Management (AWS IAM) 的认证。** 使用 Nova Act，你可以通过标准 AWS 凭证链（任务角色）进行认证。这契合 Epsilon 现有的安全模型，不必分发单独管理的 API key。
- **对跨账号友好。** Nova Act 与 Amazon Bedrock AgentCore Browser Tool 可以直接接入你现有的 AWS Security Token Service (AWS STS) AssumeRole 开通流程。每个接入的团队都能在自己的 AWS 账号内、在受作用域约束的角色下运行测试，从而保持隔离性与可审计性。

Epsilon 专门选择 Amazon Bedrock AgentCore Browser Tool，正是因为它消除了管理浏览器二进制文件、显示服务器和会话生命周期的运维负担。Agentic Platform 团队完全无意自己持有那套基础设施。

## 方案：架构与实现

Epsilon 的方案有三个主要组件：用于创建工作流的平台 API、用于执行工作流的后台任务运行器，以及驱动浏览器的 Nova Act 与 Amazon Bedrock AgentCore Browser Tool 集成。

### 平台架构

Epsilon 的 UI 测试能力遵循一条清晰的流水线：

- 用户通过平台 API 创建工作流，指定一个 `target_url` 和一串自然语言步骤。
- 创建时，平台在 AWS 上注册一个 Nova Act 工作流定义。
- 执行时，后台任务运行器（[Celery](https://docs.celeryq.dev/)，一个用于异步作业处理的 Python 框架）开启一个 Amazon Bedrock AgentCore Browser Tool 浏览器会话，通过 [Chrome DevTools Protocol (CDP)](https://chromedevtools.github.io/devtools-protocol/) WebSocket（以编程方式控制 Chromium 浏览器的标准接口）用 Nova Act 逐步执行，包括条件逻辑（例如 *“如果出现导览框，跳过它”*）。
- 系统对每一步截图、逐步跟踪通过/失败、计算总体通过率，并存储全部内容（结果 JSON、存放在 Amazon S3 的截图、会话 ID）。
- 触发完成钩子，把结果回写到平台中。

图 1 展示了 Epsilon UI Testing Service 的分层架构。用户请求从 Agent Cloud Frontend 出发，流经带认证与权限检查的 API Gateway。API 层（Django REST）暴露用于工作流、执行、自动化套件和统计的端点。业务逻辑层包括 Workflow Manager、Execution Orchestrator 和 Suite Coordinator。测试作业排入 Amazon Simple Queue Service (Amazon SQS)，由运行在 Amazon Elastic Container Service (Amazon ECS) 上的 Runner Service 取出执行，该服务内嵌 Nova Act 引擎与无头 Chromium 浏览器。结果、截图、轨迹和 HTML 报告存储在 Amazon S3 中。

该能力以一个标准 agent（`ui-test-agent`）的形式暴露，带两个 skills：

- **ui-test-recorder**：交互式地探索一个场景并记录自然语言步骤。
- **ui-test-executor**：运行已记录的步骤并返回结构化结果。

接入的团队消费 UI 测试能力的方式，与他们消费平台上任何其他 agent 的方式完全相同，没有额外的基础设施要管理。接入流程很直接：平台团队为新团队开通一个跨账号 IAM 角色，登记其目标应用的 URL，并通过现有平台 API 授予对 `ui-test-agent` 的访问权限。从那一刻起，团队就用他们操作其他平台能力的同一个界面来创建工作流、触发执行、获取结果。

### 核心集成

Nova Act + Amazon Bedrock AgentCore Browser Tool 的集成非常简洁：

```
import boto3
from bedrock_agentcore.tools.browser_client import browser_session
from nova_act import NovaAct

boto_session = boto3.Session(region_name=region)

with browser_session(region) as client:
    ws_url, headers = client.generate_ws_headers()
    with NovaAct(
        cdp_endpoint_url=ws_url,
        cdp_headers=headers,
        boto_session=boto_session,
        starting_page=url
    ) as nova_act:
        result = nova_act.act(instruction)
```

这个模式——开启托管浏览器会话、经由 CDP WebSocket 连接、用自然语言驱动操作——就是地基。Epsilon 在外层包装了自己平台的多租户编排、结果捕获和可观测性层。

### 示例：自动化「Create an agent」流程

为说明意图驱动的测试，这里是 Epsilon 平台中的一个代表性工作流。它覆盖了登录、表单填写、条件处理、滚动和验证。下列步骤凸显了 Nova Act 的差异化模式：

| **步骤** | **指令** |
| --- | --- |
| 1 | 输入用户名并选择 **Next** |
| 2 | 输入密码并选择 **Verify** |
| 3 | 导航到 **Create Agent**，选择 **Design a new specification** 卡片 |
| 4 | 如果出现新手引导框，选择 **Skip Tour**，然后验证加载了正确的页面 |
| 5 | 填写 agent 名称和描述字段 |
| 6 | 向下滚动直到 **Goal Statement** 字段可见，然后填写它 |
| 7 | 如果技能搜索框不可见，滚动直到它出现，然后搜索并添加一个技能 |
| 8 | 选择 **Save**，确认成功提示，返回上一页，并验证新 agent 出现在列表中 |

步骤 4 和 7 演示了*条件逻辑*：「如果某个元素出现，就处理它」和「如果目标不可见，就滚动直到它可见」。这些模式在传统框架里需要显式的分支代码，Nova Act 则通过语言理解自然地处理它们。

### 运行时隔离

Epsilon 在一个*专用 runner 服务*（FastAPI sidecar）中运行 UI 测试，该服务锁定 `nova-act` 3.x（带 Workflow 和 IAM 认证支持），外加 Amazon Bedrock AgentCore Browser Tool 客户端。这让依赖与主后端相互隔离，不会与 Strands agent 栈冲突。当 runner 被禁用时，worker 会退回到进程内执行，为部署期间提供韧性。

## 最佳实践

基于把 UI 测试建成平台能力的经验，Epsilon 团队建议：

### 1. 按意图而非机械操作编写步骤

```
GOOD: "Confirm the rewards balance is visible"
BAD: await page.locator('#rewards-balance-container > span.amount').toBeVisible()
```

意图驱动的步骤挺得过 UI 重设计。可能不写代码的产品经理和质量保证（QA）负责人可以直接审阅它们。

### 2. 隔离 Nova Act 运行时

把 Nova Act 和 Amazon Bedrock AgentCore Browser Tool 的依赖锁定在一个专用服务或容器里。Epsilon 学到的教训是：Nova Act 的签名端点无论浏览器会话在哪个区域，都指向 `us-east-1`。把它跑在一个有自己依赖锁文件的独立服务里，可以避免难以调试的冲突。

### 3. 复用录制的轨迹以削减成本

Epsilon 在 **draft 状态**下使用轨迹重试，保存成功的轨迹，再在 **active 状态**下回放它。重复运行会跳过冗余的大语言模型（LLM）「思考」，为回归式的重复执行同时降低延迟和成本。

### 4. 从第一天起就为多租户设计

使用带作用域 IAM 策略的跨账号 AssumeRole。每个租户的测试都在其自己账号里、以自己的角色运行。这在不为每个团队定制基础设施的前提下，提供了隔离性、可审计性和故障范围控制。

### 5. 依托托管可观测性

借助 Amazon Bedrock AgentCore Browser Tool，团队获得实时视图、会话录制和 AWS CloudTrail 集成。Epsilon 使用这些内置能力而不是自建可观测性，减少了维护量，并给合规团队提供了熟悉的审计界面。

### 6. 顾及 Amazon Bedrock AgentCore Browser Tool 的视口行为

在编写 Nova Act 步骤的指令时，要考虑 Amazon Bedrock AgentCore Browser Tool 的浏览器视口默认值。涉及滚动的步骤（例如「向下滚动直到 Goal Statement 文本框可见」）可以验证 Nova Act 是否正确处理了页面下半部分的内容。

## 结果与影响

Epsilon 的 UI 测试能力已在多个团队投入运行，多租户架构在生产环境中得到验证。

| **维度** | **Amazon Nova Act** | **Playwright（等效实现）** |
| --- | --- | --- |
| 编写行数 | 18 条自然语言步骤 | 约 80–150 行代码 |
| 选择器/DOM 检查 | 无 | 每个交互步骤都需要 |
| 编写时间（每工作流） | 约 5–10 分钟 | 约 30–90 分钟 |
| 工作量比 | 基线 | **多花 4–6 倍精力** |

以下是实测结果：

- **测试编写快 4–6 倍（基于 Epsilon 内部基准）。** 一个代表性的 18 步工作流用 Nova Act 编写只需 5–10 分钟，而等效的 Playwright 脚本（80–150 行代码）需要 30–90 分钟。Playwright 脚本中每个交互步骤都要求检查 DOM、挑选稳定选择器，并为条件情形编写显式的等待、断言和分支。Nova Act 用 18 条自然语言指令和零选择器/DOM 检查取代了这些逐步开销，条件逻辑（如导览框和滚动至可见等步骤）用通俗英文表达即可。
- **轨迹重放 100% 通过率（基于 Epsilon 内部** **基准）。** 工作流通过最初的探索阶段（通常 4–5 轮 prompt 迭代）后，Epsilon 保存成功轨迹并确定性地回放。已保存的轨迹在重复运行中达到 100% 的通过率。
- **测试编写门槛更低。** 步骤读起来就是通俗英文。核心测试工程师之外的团队成员也能阅读、审阅并提出测试，让质量的所有权更广泛。
- **内建审计线索。** AWS CloudTrail 集成与 Amazon Bedrock AgentCore Browser Tool 会话录制，让调试和合规沟通变得更轻松。这是团队最初并未刻意追求的一项收益。
- **每团队零基础设施开销。** 接入的团队通过与其他平台 agent 相同的 API 界面获得 UI 测试。没有浏览器二进制文件，没有 Selenium grid，没有显示服务器要管理。
- **逐步的通过/失败可见性。** 每一步的截图捕获提供了细粒度的调试上下文，缩短了定位故障的平均时间。

> “Nova Act 让我们把 UI 测试从一项脆弱、追着选择器跑的苦差，变成了一项受管的平台能力。我们的测试现在用通俗英文描述意图，运行在 AWS 托管的浏览器上，我们接入的每个产品团队都能在不做任何额外配置的情况下获得可靠的测试。”
>         — Epsilon Agentic Platform 团队
