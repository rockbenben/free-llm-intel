# 使用 Amazon Bedrock Data Automation 构建 serverless 的 PII 抹除 pipeline

每天处理数千份扫描文档（包括医疗表格、保险理赔单和财务记录）的组织，面临一项反复出现的合规需求：在文档共享给第三方或被下游处理之前，对个人可识别信息（PII）进行抹除（redaction）。

人工抹除无法规模化：它消耗员工工时、引入人为错误，并造成合规风险敞口。除了是一个*检测*问题，抹除还是一个*精度*问题。单页文档中可能包含多个姓名、日期和地址，而其中只有一部分对该用例是敏感的。传统抹除做法把光学字符识别（OCR）与模式匹配或自定义机器学习（ML）模型搭配使用。然而，当文本质量退化时这些做法存在局限，难以表达字段级的业务逻辑，且随着文档格式变化，需要 ML 专业知识来构建和重新训练自定义模型。

本文将演示如何在 AWS 上大规模地自动完成文档与图片中 PII 的端到端检测与抹除。我们为 PII 抹除设计了一个自定义 blueprint，并展示了一套使用 Amazon Bedrock Data Automation（BDA）、AWS Step Functions 和 AWS Lambda 进行处理的 serverless 批处理架构。流程如图 1 所示。

图 1：端到端的 serverless PII 抹除 workflow

生成式 AI 的文档理解能力有助于打破传统抹除的约束。基础模型可以整体地理解一个文档页面，包括其版式、字段标签与上下文，并能使用自然语言指令而不是训练好的实体模型，区分某个字段中的信息属于谁。Amazon Bedrock Data Automation 是 Amazon Bedrock 提供的一项服务，可从非结构化文档、图片、音频和视频中智能提取结构化信息。

使用 BDA 的*自定义 blueprint*（custom blueprint）功能，你可以用自然语言指令声明希望精确提取的具名文档字段。借助 BDA，你能得到所需的字段内容、置信度分数，以及每个实例的边界框坐标，供下游后处理使用。针对批量 PII 抹除用例定制一个自定义 blueprint，你就可以把 BDA 当作专用的 PII 检测引擎，实现规模化抹除。

想进一步了解 Amazon Bedrock Data Automation 的 blueprint 与自定义输出 schema，请参阅 [Amazon Bedrock Data Automation 文档](https://aws.amazon.com/bedrock/bda/)。关于在生成式 AI 应用中更广泛地管理 PII 的指导，请参阅 [生成式 AI 安全范围矩阵](https://aws.amazon.com/blogs/security/securing-generative-ai-an-introduction-to-the-generative-ai-security-scoping-matrix/)。

## 解决方案概览

该方案包含两部分：一个定义“抹除什么”的自定义 BDA blueprint，以及一条在批处理规模上应用它的 serverless pipeline（采用本文概述的最佳实践）。同一条 serverless pipeline 可以通过不同的 blueprint 满足多种用例。

### 设计 PII 抹除 blueprint

为某个文档处理用例设计专用的抹除 blueprint，需要回答四个范围界定问题：哪些*是*敏感信息，哪些*不是*敏感信息，它在页面上的哪里，以及如何把它移除？本文以“在下游理赔处理之前对主治医师声明（Attending Physician Statement）执行 PII 抹除”这一用例来演示该过程。

基于该用例的上下文，我们在表 1 中确立了抹除需求。

| ***范围界定问题*** | ***用例需求*** |
| --- | --- |
| *什么是敏感信息？* | 患者姓名、出生日期、家庭住址、联系方式 |
| *什么不是敏感信息？* | 医师姓名、检查日期、诊所地址、诊所联系方式、症状与医疗记录 |
| *它在页面上的哪里？* | 分布于结构化表单字段、非结构化手写内容，以及文档中的多处实例 |
| *如何把它移除？* | 确定合格字段的边界框坐标，把 PDF 转换为 PNG，并在后处理中于坐标位置施加黑框抹除 |

*表 1：专用抹除 blueprint 的需求*

根据收集到的需求，可通过 AWS 管理控制台、AWS 命令行界面（AWS CLI）或开发 SDK 创建 BDA blueprint，并指定目标 blueprint schema。控制台提供一个向导选项，可基于样本文档生成 blueprint schema。最终的 schema 必须逐一列出可抹除的字段、其数据类型、简短的自然语言描述，以及适用的转换（例如在使用*推断*（inferred）推理类型时的日期格式）。*显式*（explicit）推理类型则不进行预期转换，直接提取。

以患者出生日期字段为例。它是一个日期类型字段，但文档中并非所有日期都应被抹除，例如预约日期和签名日期。blueprint 的 `instruction` 告诉 BDA 应提取哪些日期信息子类型，从而把提取聚焦在目标字段上。

该 `instruction` 把字段限定到患者身上，使 BDA 即使在同页出现不同格式时，也能区分出生日期与预约日期、签名日期。同样的设计过程也把主治医师的打印姓名与签名排除在抹除集合之外。图 2 展示了使用这条 PII 抹除 pipeline 前后的一份示例声明。图 3 展示了在控制台上呈现的 blueprint。

以下片段展示了 blueprint schema 中一个有代表性的字段组。该主治医师声明 PII 抹除用例的完整 blueprint schema 定义了 9 个字段组、共 37 个字段。字段组（field group）是一种结构，用于把相关结果组织到你抽取结果中的同一位置。

```
{
  "PatientIdentity": {
    "type": "object",
    "properties": {
      "patient_first_name": {
        "type": "string",
        "inferenceType": "explicit",
        "instruction": "The patient's given or first name."
      },
      "patient_last_name": {
        "type": "string",
        "inferenceType": "explicit",
        "instruction": "The patient's surname or family name. Look carefully in all sections including signature areas."
      },
      "patient_date_of_birth": {
        "type": "string",
        "inferenceType": "explicit",
        "instruction": "The patient's date of birth in any format (dd-mm-yyyy, mm/dd/yyyy, etc.)."
      },
      "patient_mrn": {
        "type": "string",
        "inferenceType": "explicit",
        "instruction": "The patient's Medical Record Number (MRN)."
      }
    }
  }
}
```

每个字段都使用 `inferenceType: "explicit"` 进行不做转换的提取，并用自然语言的 `instruction` 限定检测范围。字段组是一种结构，把相关结果组织到你抽取结果中的同一位置。

我们建议针对每个文档处理用例的抹除需求，设计专用的 BDA blueprint。用例层面的 blueprint 定制依赖于持续迭代的实验结果，而进一步的自动化实验属于未来工作。

在最终部署中，所需 blueprint 的 Amazon Resource Name（ARN）作为输入参数传入，使同一套批处理 pipeline 基础设施能够被编排并部署，以支撑多个抹除用例的规模扩展。在这条 pipeline 中，我们每次 API 调用只向 BDA 发送一个文档页面，从而把生成式 AI 请求的范围聚焦在一次一页上下文上。

在单次请求中，BDA 会处理完整的文档页面，以理解版式、字段标签和上下文，而不依赖字符级 OCR。因此，BDA 能够定位 OCR 引擎可能难以转录的手写患者姓名，也能更有效地处理输入文档质量较差的边界情况。

### 评估 blueprint

设计好 blueprint 之后，以人工作为真值（ground truth）的抹除文档为准，计算被抹除 PII 实例的精确率与召回率，以评估其抹除表现。在我们的用例中，我们测试了覆盖六个文档质量等级的文档样本，从干净的打印表单一直到 100 点每英寸（DPI）的低分辨率扫描件（表 2）。

| **等级 ID** | **文档质量** | **挑战** |
| --- | --- | --- |
| 1 | 干净的打印表单 | 基线情况：结构化字段、清晰印刷 |
| 2 | 打印后传真 | 压缩伪影、旋转、模糊 |
| 3 | 打印机质量差的传真件 | 噪点、字符残缺 |
| 4 | 手写表单 | 字迹潦草、间距不均 |
| 5 | 手写、打印后重新扫描 | 印刷与扫描退化叠加 |
| 6 | 低分辨率扫描件（100 DPI） | 像素密度降低、文字出现锯齿 |

*表 2：文档质量测试等级*

对样本测试用例的初步测试显示，该 blueprint 在我们 12 份文档（47 页）的样本集中，至少识别出了每个 PII 实例一次，但偶尔会漏掉叙述性文本和医师手写记录中重复出现的实例。为了在最小影响精确率的前提下提升召回率，我们引入了使用 BDA standard output 的第二遍检测，并通过图 4 所示的后处理 token 匹配步骤合并结果。

一次 API 调用，BDA 会返回两种输出：

- **自定义输出（custom output）：** 由 blueprint 检测出的 PII 字段及其边界框。
- **标准输出（standard output）：** 完整抽取结果，包含每个单词的边界框。

```
response = self._runtime.invoke_data_automation_async(
    inputConfiguration={"s3Uri": input_s3_uri},
    outputConfiguration={"s3Uri": output_s3_uri},
    dataAutomationProfileArn=profile_arn,
    dataAutomationConfiguration={
        "dataAutomationProjectArn": project_arn,
        "stage": stage,
    },
)
```

token 匹配会把每个检测到的 PII 值归一化为词级 token，然后扫描页面的词级 standard output，找出归一化形式与某个 PII token 匹配的词。新的、不重叠的匹配会被加入最终的待抹除坐标集合。这样，重复出现的 PII 实例无论在页面何处再次出现，包括自由文本段落和手写内容，都能被捕获。

![token 匹配质量检查示意图：把 custom output 与 standard output 合并为最终的 PII 字段集合](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/11/ML-20554-4-1.png)

图 4：质量检查流程。一次 BDA API 调用产生 custom output 和 standard output，二者输入匹配器，由匹配器产出最终的 PII 字段集合

### Pipeline 架构

这里我们演示如何构建一条 serverless pipeline，把已验证的 PII 抹除 blueprint 投入批量文档处理。主治医师声明抹除的生产文档量每晚可达约 25,000 页。在保持成本效率的同时最大化抹除工作负载的并发度，是一项重要的设计考量。

这条 pipeline 以 serverless workflow 的形式运行，由一台 AWS Step Functions 状态机编排五个 AWS Lambda 函数。多个 AWS Step Functions 分布式 map 状态在页面级别扇出并发的 BDA API 调用。文档 PDF 通过一个 Amazon Simple Storage Service（Amazon S3）前缀输入。如果限流失败影响你的 workflow，可以使用 Step Functions 原生的 redrive 能力继续处理。

图 6 概述了生产 pipeline 的架构。

![由 AWS Step Functions 编排的 serverless PII 抹除 pipeline 架构图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/11/ML-20554-6-1.png)

图 6：Serverless PII 抹除 pipeline 架构

该架构图显示一台 AWS Step Functions 状态机编排五个顺序执行的 Lambda 函数：Initialize、Preprocessing、Redaction、Reassembly 和 Reporting。两层嵌套的分布式 map 负责并行：外层 map 遍历文档，内层 map 遍历每份文档内的页面。Amazon S3 提供输入与输出存储，Amazon Bedrock Data Automation 处理每个页面图像以进行 PII 检测。

该 Step Function 有三个输入：

- **一个 S3 输入前缀**，包含一组未抹除的 PDF 输入。
- **一个 S3 输出前缀**，配置结果写入的位置。
- **blueprint ARN**，即为该抹除用例开发并验证过的 BDA blueprint ID。

该抹除 workflow 包含以下步骤：

- **Initialize** – 校验输入、解析 blueprint、列出 Amazon S3 中的源文档，并为文档级分布式 map 写入清单（manifest）。
- **Preprocess** – 把每个 PDF 转换为逐页 PNG 图像。图片类文档则作为单页 PNG 直接通过。
- **Detect and redact** – 把每个页面图像发送到 Amazon Bedrock Data Automation 进行 PII 检测，然后在每个检测到的区域坐标上施加黑色矩形。
- **Reassemble** – 把抹除后的页面图像按文档合并为单个抹除后的 PDF，并构建文档级元数据。
- **Report** – 把各文档摘要聚合为作业级报告，并运行对账检查（reconciliation）。

Step Functions 运行两层嵌套的分布式 map：外层 map 遍历文档，内层 map 遍历每份文档内的页面。你在文档级与页面级的并发设置必须匹配账户级针对 `InvokeDataAutomationAsync` 的服务配额。请根据工作负载特性优化并发，并按用例需要申请必要的配额提升。

#### 执行抹除

**Preprocessing** Lambda 函数把每个输入文档转换为逐页 PNG 图像。它从 Amazon S3 下载文档、检测文件类型、把每个 PDF 页面渲染为 PNG，并写回 S3。

**Redaction** Lambda 函数对每个页面执行四项操作：调用 BDA、解析结果、抹除图像，并上传到 S3。

BDA 返回每个检测到的字段及其值、置信度分数和归一化坐标下的边界框（left、top、width、height 为 0 到 1 之间的小数）。该函数把这些坐标转换为像素坐标，略微扩张每个框以容纳偏差，并在该区域上绘制实心黑色矩形（图 7）。抹除会覆盖图像本身的像素数据，因此被遮盖的内容并不存在于输出文件中。这与基于注释（annotation）的做法不同：后者的原始文本在覆盖层之下仍可还原。

#### 从失败中恢复

该 pipeline 采用分层方式处理失败恢复。第一层使用 Step Functions 原生的指数退避重试与 jitter 应对限流尖峰。第二层暴露损坏输入文档的错误，同时让成功的同级任务继续执行。如果出现持续性故障，运维人员可以使用 Step Functions 的 redrive 能力，而无需重新处理已完成的工作。

适用两种隔离策略：

- **文档级失败** *（即损坏的 PDF 或重组错误）*。pipeline 会在作业报告中记录失败，同时其他文档继续处理。输出包含成功执行的抹除后 PDF，以及逐条列出的失败记录。
- **页面级失败** *（即持续限流导致重试耗尽）*。恢复使用 Step Functions 内置的 redrive。运维人员可以看到哪些页面失败，然后再决定是否恢复。

#### 报告

最终的作业报告聚合了各文档的明细、耗时数据和对账摘要。当 `fully_reconciled` 为 true 时，每一份提交的文档都产出了抹除后的 PDF。如果所有文档都失败，执行会以专门的 `PipelineNoOutput` 失败结束。

#### 安全

该 pipeline 建立在其所用 AWS 服务的安全控制之上：

- **受 IAM 限定的访问：** 每个 Lambda 函数都有专用的最小权限 AWS Identity and Access Management（IAM）角色，范围限定在 pipeline 存储桶及其所需操作。
- **静态与传输加密：** Amazon S3 默认加密使用 AES-256 帮助保护每份文档和 Lambda 制品。pipeline 通过传输层安全（TLS）访问 Amazon S3、AWS Step Functions 和 Amazon Bedrock。
- **私有网络：** Lambda 函数通过基础设施即代码（IaC）变量支持虚拟私有云（VPC）部署。启用后，到这些服务的流量通过 VPC 端点而不经过公共互联网。
- **可审计性：** AWS CloudTrail 记录整条 pipeline 的 API 活动，可用于支撑你的合规审查。

### 选择合适的 PII 抹除方案

这种 BDA blueprint 做法非常适合以下情况：文档质量退化或格式混杂；需要应用字段级业务逻辑（例如抹除患者姓名但不抹除医师姓名）；或者图像抹除需要像素级边界框坐标。

## 结论

本文展示了如何使用 Amazon Bedrock Data Automation、AWS Step Functions 和 AWS Lambda，设计并构建一条从扫描文档中检测并抹除 PII 的 serverless pipeline。借助自定义 BDA blueprint，你可以用自然语言指令声明要抹除的特定字段（例如患者姓名），而不会过度抹除医师姓名或临床内容。

在相对于人工抹除真值的评估中，blueprint 抹除达到 97.0% 的精确率；而把 BDA standard output 作为 token 匹配质量检查加入后，仅凭单次 API 调用，就在数字 PDF、手写表单和低分辨率传真件上把召回率从 89.3% 提升到 95.2%。

把你的 BDA blueprint 当作配置来看待。只需更改 blueprint schema 和 S3 输入前缀，就能让同一条生产 pipeline 指向新的文档类型，使这次部署成为一个可复用的模式，帮助在医疗记录、金融开户表单、政府申请，以及其他文档密集、对 PII 敏感的工作负载中批量完成 PII 抹除。

我们鼓励你在 Amazon Bedrock Data Automation 控制台中构建第一个 blueprint，并今天就着手把 PII 抹除自动化。要开始使用，请参阅 Amazon Bedrock Data Automation 文档中的[创建 blueprint](https://docs.aws.amazon.com/bedrock/latest/userguide/bda-idp.html)，并进一步阅读使用 BDA 进行智能文档处理的内容，以及 [BDA 如何与 Bedrock Guardrails 协同工作](https://aws.amazon.com/blogs/machine-learning/detect-and-redact-personally-identifiable-information-using-amazon-bedrock-data-automation-and-guardrails/)。
