# 在 AWS Quick 中运营您的整个销售业务

大多数卖家并不需要再去学一款新的 AI 产品。他们真正需要的，是把手上已经在用的那些工具和信息汇集到一起，于是就能看清自己的生意里正在发生什么，并且据此采取行动。

AWS Quick 与 Amazon Selling Partner 插件联手来做这件事。Quick 把亚马逊卖家的销售数据、库存信号与市场情报汇集到同一处，让问题变成答案，答案变成行动。它能理解卖家完整的业务上下文，卖家不必在每一次对话里重新交代自己的商品目录、利润率水平或竞争格局。它构建在 AWS 之上——那也是亚马逊运营自家商城所用的同一套基础设施。

在 2026 年 9 月 23 日的 Amazon Accelerate 上，亚马逊发布了 Selling Partner 插件，并在 AWS Quick 中以 beta 形式上线。本文介绍这次发布的内容、如何领取免费的 AWS Quick 优惠，以及日常使用是什么体验；也会说明卖家真正上手时，skills 与 connectors 如何协同工作。

# 1. 为什么 Quick 适合亚马逊卖家

有四点让 Quick 贴合亚马逊卖家如今已经成型的工作方式：它会自己去学这门生意、触角伸得到亚马逊店铺之外、把数据变成决策，并且在卖家本就信任的基础设施上把卖家数据保护好。

## Quick 懂你的业务，而不只是你的 prompt

Quick 与 Selling Partner 插件接入卖家的库存数据流、销售数据和运营文档。基于这些输入，Quick 会对商品目录结构、利润阈值、季节性和竞争位置形成一份持续更新、活的理解。让 Quick 针对 Q4 审查你的 ASIN，它会返回一份排好序的建议，依据是卖家真实的利润数据、历史转化率和库存可用量。卖家与它配合得越多，建议就越精准。

## Quick 不止步于你的亚马逊店铺

卖家的生意横跨许多工具：另一个渠道的店面、邮箱、会计系统、电子表格、供应商门户。Quick 接入卖家本来就在用的地方，从整个经营流程中提取上下文。它是一个恰好深谙亚马逊的业务助手，因此卖家获得的是整体增长，而不是只在单一渠道上增长。

## 它把数据变成可执行的决策

卖家并不缺数据：Brand Analytics、Search Query Performance、广告报告、库存健康度和 listing 质量数据都摆在那里。难的地方在于把这些信号收敛成一个明确的动作。综合归纳由 Quick 完成：它盯住变化、标出要紧的事、把分析做出来，并把决策连同支撑证据一起呈现。

## 数据在你已在卖货的基础设施上受保护

Quick 运行在 AWS 上，不用卖家数据训练模型——既不用于通用改进，也不用于任何其他用途。卖家数据留在卖家自己的环境中，永远不会影响别人的模型。对已经在亚马逊商城经营的卖家来说，没有新的安全姿态需要评估：这套基础设施就是当下保护卖家账户的那一套，数据留在哪里，由卖家自己选定的 AWS Region 决定。

# Amazon Selling Partner 插件

Selling Partner 插件把 AWS Quick 直接接到实时的 Seller Central 数据上。用 Seller Central 账户登录一次之后，插件就能以对话方式访问商品 listing、库存和销售数据——这些数据都是实时拉取来的，不需要先手工导出、再重新拼装。它像装一个 app 那样安装，无需写代码。它自带一组精选的亚马逊 skills，并与 Amazon Ads MCP 搭配，让广告活动的表现和花费就摆在销售数据旁边。该插件目前处于 beta 阶段，面向美国店铺提供。

图 1：Selling Partner 插件的授权同意页，卖家按数据类别分别授予 None、View 或 Edit 权限

这个权限页值得多看一眼。卖家按数据类别逐项授权，每一类都可以单独选 None、View 或 Edit，并且在授权之前先看一遍协议。没有哪一项是全有或全无的，访问范围之后可以收窄，也可以撤销。

# 3. 用起来是什么样

插件接好之后，工作就在对话里完成。你用日常语言提问，Quick 就去拉取相关的实时数据，然后带着一个答案和一条推荐的下一步回来。你不必再走查仪表板、导出报表、拿到电子表格里核对这一圈，而是在同一个地方就能从一个问题走到一个答案，再走到一个行动。在任何内容真正发出去之前，你都会先过一遍 Quick 给出的提议。

# 4. 卖家可以搭出的两个用例

在 Accelerate 的研讨会上，我们让卖家现场从一段日常语言描述出发，在几分钟内搭出真正能跑的 agent。Quick 把描述变成一个可用的 agent，卖家随后在对话中把它打磨到位。

## 用例 A：库存上线准备

卖家正在把一款新品铺进亚马逊，希望总到岸成本最低。agent 读取供应商数据，按入库成本、仓储和可售速度逐 SKU 权衡履约方案。它会把各种铺货方案逐个走一遍，然后返回卖家指定的那种产出：一份发货计划、一份成本对比，或者把两者合并成一个材料包。它会解释自己的推理，并在真正动手创建任何东西之前先做确认。

图 4：Inventory Launch Prep agent 逐项比较 FBA 与 AWD 履约，并推荐混合方案

## 用例 B：上线后的商品健康度

上线之后，agent 通过 Selling Partner 插件读取四类信号：listing 健康度、库存、销售和流量。它把这些信号串起来，去找出背后的原因，而不是只把数字报给你。销量走平但流量健康，说明问题出在转化上；销量走平而流量在下滑，说明问题出在可发现性上；转化率不错但销量在下滑，说明问题出在供货上。它会返回每个 ASIN 的健康度摘要、带证据的诊断，以及一份排好序的修复清单，并对任何置信度低的判断明确标注。

图 5：Post-Launch Product Health agent 的每周摘要，附周环比销售证据

有一个诚实的边界，也照实处理：销售数据里不含商品成本，所以 agent 报的是扣除亚马逊费用后的利润率，并如实标注。卖家若要看真正的毛利率，agent 会请他们把成本数字带进对话。它从不把扣费后利润率当成毛利率来呈现。

# 5. skills 与 connectors 实战

Selling Partner 插件与 Amazon Ads MCP 把亚马逊的销售与广告数据带进 Quick。AWS Quick 的其他 connectors 则按角色把业务运转的其余部分接进来：第二个店面（来自另一渠道的订单与商品）、邮件与日历（起草一封给供应商的说明、跟踪哪些事项到期）、团队消息（同步一条进展），以及会计与库存系统（销售数据不携带的成本与库存上下文）。正因为这些部件摆在一起，卖家才可以用同一个问题，同时触达亚马逊的数据和它周边的那些工具。
