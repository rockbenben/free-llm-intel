# 使用 Amazon Bedrock 上的 Automated Reasoning 构建可靠的 AI 系统 – 第 1 部分

受监管行业的企业往往需要数学上的确定性，确保每一条 AI 响应都符合既定策略与领域知识。受监管行业无法采用传统的质量保证方法——那类方法只对 AI 输出做统计抽样测试，并对合规性做出概率性断言。当我们在 AWS re:Invent 2024 上以预览形式推出 [Amazon Bedrock Guardrails 中的 Automated Reasoning checks](https://aws.amazon.com/bedrock/guardrails/) 时，它提供了一种新颖的解决方案：应用形式化验证技术，依据编码后的业务规则与领域知识系统性地验证 AI 输出。这些技术让验证结果变得透明且可解释。

Automated Reasoning checks 正被用于各行各业的 workflow。金融机构以数学确定性验证 AI 生成的投资建议是否符合监管要求。医疗机构确保面向患者的指导与临床规范一致。制药公司确认营销宣传有 AI 批准的证据支撑。公用事业公司在灾害期间验证应急响应协议，法务部门则验证 AI 工具是否捕捉到强制性的合同条款。

随着 Automated Reasoning [正式可用](https://aws.amazon.com/blogs/aws/minimize-ai-hallucinations-and-deliver-up-to-99-verification-accuracy-with-automated-reasoning-checks-now-available/)，我们提升了文档处理能力，并新增了 scenario generation 等功能，它可以自动生成示例，演示你的 policy 规则如何在实际中生效。借助增强后的测试管理系统，领域专家可以构建、保存并自动执行完整的测试套件，从而在模型与应用的不同版本之间保持一致的政策执行效果。

在这篇分为两部分的技术深度解析的第一部分中，我们将探讨 Amazon Bedrock Guardrails 中 Automated Reasoning checks 的技术基础，并演示如何实现这一能力，为生成式 AI 应用建立数学上严格的 guardrails。

**在本文中，你将学到：**

- 理解使 AI 输出的数学验证成为可能的形式化验证技术
- 从自然语言文档创建并迭代优化 Automated Reasoning policy
- 设计并实现有效的测试用例，依据业务规则验证 AI 响应
- 通过 annotation 精修 policy，提升 policy 的准确性
- 使用 Bedrock Guardrails 将 Automated Reasoning checks 集成到你的 AI 应用 workflow 中，并遵循 AWS 最佳实践，以对生成内容保持高置信度

遵循这份实现指南，你可以系统性地帮助防止事实性错误与 policy 违规在触达最终用户之前发生——对于要求高保证与数学确定性的受监管行业企业而言，这是一项关键能力。

## Automated Reasoning checks 的核心能力

本节我们将探讨 Automated Reasoning checks 的各项能力，包括用于 policy 开发的控制台体验、文档处理架构、逻辑验证机制、测试管理框架以及集成模式。理解这些核心组件，将为实现面向生成式 AI 应用的有效验证系统奠定基础。

### 控制台体验

Amazon Bedrock Automated Reasoning checks 控制台把 policy 开发组织成若干逻辑分区，引导你走完创建、精修与测试的流程。界面中包含以唯一 ID 清晰标识的规则，并允许在规则中直接使用变量名，使复杂的 policy 结构变得易于理解和管理。

### 文档处理容量

文档处理最多支持 120K token（约 100 页），因此你可以把体量可观的知识库和复杂的 policy 文档编码进 Automated Reasoning policy。组织可以把完整的 policy 手册、详细的流程文档以及篇幅庞大的监管指南一并纳入。凭借这一容量，你可以在单个 policy 中处理完整的文档。

### 验证能力

验证 API 包含歧义检测，用于识别需要澄清的陈述；为 INVALID 的结论提供反例，说明验证为何失败；为 SATISFIABLE 的结论同时给出有效与无效示例，帮助理解边界条件。这些功能为验证结果提供上下文，帮助你理解特定响应为何被标记，以及可以如何改进。系统还能给出自然语言与逻辑结构之间翻译的置信度，以便为特定用例设置合适的阈值。

### 迭代反馈与精修流程

Automated Reasoning checks 会给出详细且可审计的 finding，解释某条响应为何未通过验证，从而支持迭代式精修，而不是简单地拦截不合规内容。这些信息可以回传给 foundation model，让它依据具体反馈调整响应，直到符合 policy 规则。这种方法在受监管行业尤其有价值——在这些行业里，事实准确性与合规性必须被数学验证，而不能靠估算。

### 通过一个 policy 示例了解 finding 类型

以一个用于判定休假日期的 policy 为例。在实现 Automated Reasoning checks 时，policy 由两部分组成：变量 schema（定义员工类型、服务年限、可用休假天数等概念）以及一组建立这些变量之间关系的逻辑规则（例如不同类型休假的资格条件）。在验证过程中，系统会使用这套 schema 与规则结构来评估 foundation model 的响应是否符合你定义的 policy 约束。

我们要验证下面这条用户向由 foundation model（FM）驱动的应用提出的输入，以及生成的输出。

```
Input:
"Is Thursday a day off if it's a public holiday?"

Output:
"Yes, Thursday would be a day off if it's a public holiday, since all public holidays are considered days off regardless of the day of the week."
```

premise 是据此得出结论的陈述，claim 则是对真实性的断言。在这个例子中，推断出的 premise 是 `day` 等于“Thursday”、`is_public_holiday` 为 true，而 claim 主张 `is_day_off` 为 true。

这一推理遵循如下 automated reasoning policy：

```
Days Off Policy:
- All weekend days (Saturday and Sunday) are days off
- All public holidays are days off
- A day is considered a day off if it is either a weekend day or a public holiday
```

正式可用后，Automated Reasoning checks 现在会产出七种不同的 finding 类型，为 FM 生成响应的验证过程提供精确洞察：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-2.png)

**VALID**：确认 *Input* 与 *Output* 完全符合 policy 规则，让你确信生成响应中的信息依据你定义的 policy 是正确的。这些 claim 由 premise 推断而来，并经 AR policy 验证为真，且不存在与这些 claim 相矛盾的其他答案。

```
Input:
Today is Sunday, do I have the day off? 

Output:
Yes, Sunday is a weekend day, you have the day off.

Premises:
day: Sunday
is_weekend: true

Claim:
is_day_off: true

Explanation:
Given the assigned variables and policy rules that weekends are days off, the only possible answer is that it is a day off.
```

**SATISFIABLE**：识别出 *Input* 与 *Output* 可能为真也可能为假，取决于具体假设。这类 finding 帮助你理解边界条件——响应只在某些条件下成立，从而使你能够判断这些假设在你的场景中是否合理。如果所需的假设不成立，则可能存在与 premise 一致的其他 claim。

```
Input:
Today is Tuesday, do I have the day off?

Output:
Yes
Premises:
day: Tuesday

Claim:
is_day_off: true

Explanation: 
If we assume is_public_holiday=true, this is correct, but if we assume is_public_holiday=false, the answer would be incorrect since Tuesday is not a weekend.
```

**INVALID**：识别出 *Input* 与 *Output* 存在 policy 不准确或事实性错误，并附上明确展示验证为何失败的反例。这些 claim 并不由 premise 与 AR policy 蕴含，且存在与 premise 和 AR policy 一致的不同 claim。

```
Input:
Today is Sunday, do I have the day off?

Output:
No you do not have the day off.

Premises:
day: Sunday

Claim:
is_day_off: false

Explanation:
This is invalid because the policy states weekends are days off. The correct claim would be is_day_off = true since Sunday is a weekend day
```

**IMPOSSIBLE**：表示无法生成任何有效的 *Claims*，因为 premise 与 AR policy 冲突，或 policy 本身存在内部矛盾。当 policy 中定义的约束造成逻辑上的不可能时，就会出现这种 finding。

```
Input: 
Today is Sunday and not a weekend day, do I have the day off?

Output:
Yes

Premises:
day: Sunday
is_weekend: false

Claim:
is_day_off: true

Explanation: 
Sunday is always a weekend day, so the premises contain a contradiction. No valid claim can exist given these contradictory premises.
```

**NO_TRANSLATIONS**：当 *Input* 与 *Output* 中不包含可翻译为 AR policy 评估所需相关数据的信息时出现。这通常发生在文本与 policy 领域完全无关，或其中没有任何可操作信息的时候。

```
Input: 
How many legs does the average cat have?

Output:
Less than 4

Explanation:
The AR policy is about days off, so there is no relevant translation for content about cats. The input has no connection to the policy domain.
```

**TRANSLATION_AMBIGUOUS**：当 *Input* 与 *Output* 中的歧义导致无法确定性地翻译成逻辑结构时出现。这类 finding 表明可能需要补充上下文或追问，才能继续验证。

```
Input: 
I won! Today is Winsday, do I get the day off?

Output:
Yes, you get the day off!

Explanation: 
"Winsday" is not a recognized day in the AR policy, creating ambiguity. Automated reasoning cannot proceed without clarification of what day is being referenced.
```

**TOO_COMPLEX**：表明 *Input* 与 *Output* 包含的信息过多，无法在延迟限制内处理完。当输入极其庞大或复杂、超出系统当前处理能力时，就会出现这种 finding。

```
Input:
Can you tell me which days are off for all 50 states plus territories for the next 3 years, accounting for federal, state, and local holidays? Include exceptions for floating holidays and special observances.

Output:
I have analyzed the holiday calendars for all 50 states. In Alabama, days off include...

Explanation: 
This use case contains too many variables and conditions for AR checks to process while maintaining accuracy and response time requirements.
```

### Scenario 生成

你现在可以直接从 policy 生成 scenario，它会创建符合你 policy 规则的测试样本，帮助识别边界情况，并支持验证 policy 业务逻辑的实现是否正确。借助这一能力，policy 作者可以在部署之前看到规则在实践中如何生效的具体示例，减少对大量人工测试的依赖。scenario 生成还会凸显 policy 覆盖范围中潜在的冲突或空白——这些仅靠逐条查看单个规则可能无法发现。

### 测试管理系统

新的测试管理系统让你可以保存并注解 policy 测试、构建用于一致性验证的测试库、自动执行测试以验证 policy 变更，并在 policy 各版本之间维持质量保证。该系统包含版本管理能力，可跨 policy 迭代追踪测试结果，使你更容易发现某些改动何时可能带来意外后果。你现在还可以导出测试结果，集成到既有的质量保证流程与文档流程中。

### 通过直接集成 guardrail 扩展的选项

Automated Reasoning checks 现在与 Amazon Bedrock API 集成，可在复杂的交互过程中依据既定 policy 验证 AI 生成的响应。这一集成同时覆盖 `Converse` 与 `RetrieveAndGenerate` 操作，使 policy 执行可跨越不同的交互模态。组织可以根据自身领域要求配置验证置信度阈值：在受监管行业选择更严格的执行，在探索性场景中采用更灵活的应用方式。

### 用例与 policy 数据集概览

本示例中使用的完整 policy 文档可从 [Automated Reasoning GitHub repository](https://github.com/aws-samples/amazon-bedrock-samples/blob/main/responsible_ai/bedrock-automated-reasoning-checks/uploads/sample_medical_policy.pdf) 获取。要验证 Automated Reasoning checks 的结果，熟悉该 policy 会很有帮助。此外，对 Automated Reasoning 生成的 policy 进行精修，是达到 99% 以上 soundness 的关键。

我们先回顾一下本文所用示例医疗 policy 的主要细节。在开始验证响应时，对照源文档进行核对会很有帮助。

- **风险评估与分层：** 医疗机构必须实施标准化的风险评分体系，依据人口学、临床、医疗资源使用、实验室与社会因素进行评分，把患者分为 Low（0-3 分）、Intermediate（4-7 分）或 High Risk（8 分及以上）三类。
- **强制干预：** 每个风险等级都要求特定的干预措施，较高风险等级在包含较低等级干预的基础上再叠加额外措施；同时某些条件会触发自动的 High Risk 分类，与分数无关。
- **质量指标与合规：** 机构必须达到特定的完成率，包括入院 24 小时内完成 95% 以上的风险评估、出院前完成 100%，且 High Risk 患者需要有记录在案的出院计划。
- **临床监督：** 评分体系虽然是标准化的，但主治医师保留覆盖权限，并需有完整记录以及出院计划协调员的批准。

### 探究 Automated Reasoning checks 的定义

在面向 policy 文档的 automated reasoning 中，**Variable** 是一个具名容器，用于存放特定类型的信息（如 Integer、Real Number 或 Boolean），并代表 policy 中的某个独立概念或度量。变量是规则的构建单元，可用于追踪、度量与评估 policy 要求。从下图中可以看到一些示例，例如 `admissionsWithin30Days`（用于追踪既往住院次数的 Integer 变量）、`ageRiskPoints`（保存基于年龄的风险分数的 Integer 变量）以及 `conductingMonthlyHighRiskReview`（指示是否正在执行月度评审的 Boolean 变量）。每个变量都有清晰的描述，说明其用途以及它所代表的特定 policy 概念，因此可以在规则中使用这些变量来落实 policy 要求并度量合规情况。Issues 中还会提示某些变量未被使用。核实这些变量代表哪些概念、并确认是否缺少规则，尤为重要。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-16.jpeg)

在 **Definitions** 中，我们可以看到 ‘Rules’、‘Variables’ 和 ‘Types’。**rule** 是 Automated Reasoning 从你的源文档中提取出的无歧义逻辑陈述。看这条已创建好的简单规则：`followupAppointmentsScheduledRate is at least 90.0` – 该规则来自 [Section III A Process Measures](https://github.com/aws-samples/amazon-bedrock-samples/blob/main/responsible_ai/bedrock-automated-reasoning-checks/uploads/sample_medical_policy.pdf)，其中指出医疗机构应监控多项过程指标，要求出院前安排的随访预约比例应达到 90% 或更高。

我们再看一条更复杂的规则：

```
comorbidityRiskPoints is equal to(ite hasDiabetesMellitus 1 0) + (ite hasHeartFailure 2 0) + (ite hasCOPD 1 0) + (ite hasChronicKidneyDisease 1 0)
```

```
Where “ite” is “If then else”
```

该规则依据 policy 文档的规定，根据患者既有的医疗状况（合并症）计算其风险分。评估患者时，系统会检查四种特定状况：任何类型的糖尿病（计 1 分）、任何分级的心力衰竭（计 2 分）、慢性阻塞性肺疾病（计 1 分）以及慢性肾病 3-5 期（计 1 分）。该规则通过布尔逻辑把这些分数相加——即把每个状况（以 true=1 或 false=0 表示）乘以分配给它的分值，再把所有数值求和，得到合并症风险总分。例如，若患者同时有心力衰竭和糖尿病，则共得 3 分（心力衰竭 2 分加糖尿病 1 分）。这个合并症分数随后成为更大风险评估框架的一部分，用于判定患者的整体再入院风险等级。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-18.jpeg)

Definitions 中还包含自定义变量类型。**自定义变量类型**又称枚举（ENUM），是一种专门的数据结构，为特定 policy 概念定义一组合法取值的固定集合。这些自定义类型通过把取值限定在与 policy 要求一致的一组预定义选项中，保持数据采集与规则执行的一致性与准确性。在示例 policy 中，我们可以看到识别出了四种自定义变量类型：

- `AdmissionType`：定义可能的住院类型（MEDICAL、SURGICAL、MIXED_MEDICAL_SURGICAL、PSYCHIATRIC），用于判定患者是否符合再入院风险评估协议的纳入条件。
- `HealthcareFacilityType`：指定可实施再入院风险评估协议的医疗机构类型（ACUTE_CARE_HOSPITAL_25PLUS、CRITICAL_ACCESS_HOSPITAL）。
- `LivingSituation`：对患者的居住安排进行分类（LIVES_ALONE_NO_CAREGIVER、LIVES_ALONE_WITH_CAREGIVER），这是判定社会支持与风险等级的关键因素。
- `RiskCategory`：定义可依据患者总风险分指派的三档风险分层（LOW_RISK、INTERMEDIATE_RISK、HIGH_RISK）。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-20.jpeg)

提升 soundness（即 Automated Reasoning checks 判定为 VALID 时的准确率）的一个重要步骤是 policy 精修：确保所捕获的规则、变量与类型最大程度地反映事实来源。为此，我们将前往测试套件，探索如何添加测试、生成测试，并利用测试结果来应用 annotation，进而更新规则。

## 测试 Automated Reasoning policy 与 policy 精修

Automated Reasoning 中的测试套件提供两类测试能力：第一，我们要运行不同 scenario，测试 Automated Reasoning policy 中的各项规则与变量，并对它们进行精修，使其准确反映事实基准（ground truth）。这一 policy 精修步骤对提升 Automated Reasoning checks 的 soundness 十分重要。第二，我们需要指标来了解 Automated Reasoning checks 在所定义 policy 与该用例下的表现。为此，我们可以在 Automated Reasoning 控制台打开 **Tests** 标签页。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-22.jpeg)

测试样本可以通过 **Add** 按钮手动添加。为了扩大测试规模，我们可以根据 policy 规则生成测试。这种测试方法既能验证 policy 的语义正确性（确保规则准确表达预期的 policy 约束），也能验证自然语言翻译能力（确认系统能够正确理解用户在与你的应用交互时会使用的语言）。在下图中，我们看到一个已生成的测试样本；在把它加入测试套件之前，SME 应标明该测试样本是否可能成立（thumbs up）或不可能（thumbs up）。随后该测试样本即可保存到测试套件中。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-25.png)

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-26.jpeg)

测试样本创建好后，可以单独运行该样本，也可以通过 **Validate all tests** 运行测试套件中的所有样本。执行后，我们看到该测试成功通过。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-28.jpeg)

你也可以手动创建测试，提供输入（可选）与输出。这些内容会在验证发生之前被翻译成逻辑表示。

**翻译如何工作**：

翻译会把你的自然语言测试转换成可对你 policy 规则进行数学验证的逻辑表示：

- Automated Reasoning Checks 使用多个 LLM 把你的 input/output 翻译成逻辑 finding
- 每次翻译都会得到一票置信度，表示翻译质量
- 你可以设置置信度阈值，控制哪些 finding 会被验证并返回

**置信度阈值的行为：**

置信度阈值控制哪些翻译被认为足够可靠、可以进入验证，从而在严格程度与覆盖范围之间取得平衡：

- **较高阈值**：翻译准确性的确定性更强，但没有任何 finding 通过验证的可能性也更高。
- **较低阈值**：返回已通过验证的 finding 的机会更大，但翻译的确定性可能较低。
- **阈值 = 0**：所有 finding 无论置信度高低都会被验证并返回。

**歧义结果：**

当没有任何 finding 达到你的置信度阈值时，Automated Reasoning Checks 会返回“Translation Ambiguous”，表示对该内容逻辑解释存在不确定性。我们将创建并验证的测试用例如下：

```
Input:
Patient A
Age: 82
Length of stay: 16 days
Diabetes Mellitus: Yes
Heart Failure: Yes
Chronic Kidney Disease: Yes
Hemoglobin: 9.2 g/dL
eGFR: 28 ml/min/1.73m^2
Sodium: 146 mEq/L
Living Situation: Lives alone without caregiver
Has established PCP: No
Insurance Status: Medicaid
Admissions within 30 days: 1

Output:
Final Classification: INTERMEDIATE RISK
```

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-30.jpeg)

我们看到这条测试在运行时通过了，结果 ‘INVALID’ 与我们预期的结果一致。此外，Automated Reasoning checks 还显示有 12 条规则与 premise 和 claim 相矛盾，这正是该测试样本输出为 ‘INVALID’ 的原因

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-32.png)

我们来看其中一些可见的矛盾规则：

- **年龄风险**：患者 82 岁  规则触发条件：“if patientAge is at least 80, then ageRiskPoints is equal to 3”
- **住院时长风险**：患者住院 16 天  规则触发条件：“if lengthOfStay is greater than 14, then lengthOfStayRiskPoints is equal to 3”
- **合并症风险**：患者有多种状况  规则计算：“comorbidityRiskPoints = (hasDiabetesMellitus × 1) + (hasHeartFailure × 2) + (hasCOPD × 1) + (hasChronicKidneyDisease × 1)”
- **医疗资源使用风险**：患者在 30 天内住院 1 次  规则触发条件：“if admissionsWithin30Days is at least 1, then utilizationRiskPoints is at least 3”
- **实验室指标风险**：患者的 eGFR 为 28  规则触发条件：“if eGFR is less than 30.0, then laboratoryRiskPoints is at least 2”

这些规则很可能产生了相互冲突的风险评分，使系统无法确定有效的最终风险等级。这些矛盾向我们展示了哪些规则被用来判定该测试的输入文本为 INVALID。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-34.jpeg)

我们再往测试套件中添加一个测试，如下图所示：

执行该测试时，我们看到患者的每一项信息都被提取为 premise，用于验证“再入院风险为高风险”这一 claim。我们看到共有 8 条规则被用于验证该 claim。关键的规则及其验证包括：

- **年龄风险**：验证患者年龄 ≥ 80 会贡献 3 个风险分
- **住院时长风险**：确认住院 >14 天会追加 3 个风险分
- **合并症风险：** 依据糖尿病、心力衰竭、慢性肾病的有无计算
- **医疗资源使用风险：** 评估住院史
- **实验室指标风险：** 依据血红蛋白 9.2 与 eGFR 28 评估风险

每一项 premise 都被评估为真，且存在多个风险因素（高龄、住院时间长、多种合并症、实验室指标异常、独居无照护者、无固定 PCP），共同支持该 HIGH RISK 评估整体的 **Valid** 结论。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-40.jpeg)

此外，Automated Reasoning 引擎使用 93 种不同赋值对该测试样本进行了大量验证，以提升 HIGH RISK 分类正确的 soundness。Automated Reasoning policy 中的各项相关规则被用于针对 93 种不同场景与变量组合验证该样本。通过这种方式，Automated Reasoning checks 确认不存在使该患者的 HIGH RISK 分类失效的可能情形。这一严谨的验证过程印证了针对这位患有多种慢性疾病、照护需求复杂的老年患者所做风险评估的可靠性。若测试样本失败，这 93 种赋值将成为重要的诊断工具，可精确定位与预期结果冲突的具体变量及其相互作用，从而使主题专家（SME）能够分析相关规则及其关系，判断是临床逻辑还是风险评估标准需要调整。在下一节中，我们将介绍 policy 精修，以及 SME 如何应用 annotation 来改进和修正 Automated Reasoning policy 的规则、变量与自定义类型。

## 通过 annotation 精修 policy

当测试未能产生预期结果时，annotation 为 Automated Reasoning policy 提供了一种强大的改进机制。通过 annotation，SME 可以系统性地精修 policy：

- 通过修改有问题规则的逻辑或条件来修正它们
- 补充 policy 定义所必需的缺失变量
- 更新变量描述，使其更精确、更清晰
- 解决原始 policy 表述存在歧义所导致的翻译问题
- 从 policy 中删除冗余或冲突的元素

这种测试、注解、更新的迭代过程会打造出越来越稳健的 policy，能够准确编码领域专业知识。如下图所述，annotation 可用于修改各类 policy 元素，之后精修后的 policy 可以导出为 JSON 文件用于部署。

在下图中，我们可以看到 annotation 是如何被应用的，以及 policy 中的规则是如何被删除的。同样地，对规则、变量或自定义类型也可以进行新增与更新。

## 在推理时使用 Automated Reasoning checks

要使用已创建的 policy 配合 Automated Reasoning checks，我们可以前往 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/)，并新建一个 guardrail，填写名称、描述，以及在 guardrail 介入并拦截 AI 系统的 prompt 或输出时显示的消息。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/30/19626-51.jpeg)

现在，我们可以通过 **Enable Automated Reasoning policy** 开关来挂载 Automated Reasoning check。我们可以设置置信度阈值，它决定该 policy 应被执行得多严格。该阈值范围为 0.00 到 1.00，其中 1.00 是默认值也是最严格的设置。每个 guardrail 最多可以容纳两个独立的 automated reasoning policy，以提供更强的验证灵活性。在下图中，我们挂载的是与患者医院再入院风险评估相关的医疗 policy 的草稿版本。
