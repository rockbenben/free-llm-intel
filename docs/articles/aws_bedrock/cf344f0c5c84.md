# AutoScout24 如何构建 Bot Factory，用 Amazon Bedrock 标准化 AI agent 开发

[AutoScout24](https://www.autoscout24.com/) 是欧洲领先的汽车市场平台，在多个欧洲国家连接新车与二手车、摩托车及商用车的买家和卖家。他们的长期愿景是构建一个 Bot Factory——一个用于创建和部署人工智能（AI）agent 的集中式框架，这些 agent 能在工作流中执行任务并做出决策，从而显著提升整个组织的运营效率。

## 从零散的试验走向标准化框架

随着生成式 AI agent（能够推理、规划并行动的系统）能力日益强大，为 AutoScout24 提升内部生产力的机会已然明确。于是各工程团队开始试验这项技术。随着 AI 创新在 AutoScout24 内部加速，他们意识到有机会率先探索出一条标准化的 AI 开发路径。尽管 AutoScout24 已在 Amazon Web Services（AWS）上成功试验过多种工具与框架，他们仍设想创建一个统一的企业级框架，以支持更快的创新。他们的目标是为整个组织中的团队铺就一条坦途，使其更容易构建安全、可扩缩且易于维护的 AI agent。AutoScout24 的 AI 平台工程团队与 AWS Prototype and Cloud Engineering（PACE）团队合作，开展了为期三周的 AI 训练营。目标是通过创建一个可复用的蓝图——Bot Factory——从碎片化的试验走向统一的策略，把公司未来 AI agent 的构建与运营方式标准化。

## 挑战：找出高影响的用例

为了让 Bot Factory 蓝图建立在切实的业务场景之上，团队锁定了一项显著运营成本：内部开发者支持。问题是明确界定的。AutoScout24 的 AI 平台工程师最多会把 30% 的时间花在重复性任务上，比如回答问题、授予工具访问权限以及查找文档。这项支持税削减了整体生产力，使资深工程师无法专注于高优先级的功能开发，并迫使其他开发者等待常规请求被处理完。一个自动化支持 bot 是理想的首个用例，因为它需要执行两项核心 agent 功能：

- **知识检索：** 通过检索内部文档回答「如何做」类问题，这一能力被称为检索增强生成（Retrieval Augmented Generation，RAG）。
- **动作执行：** 在其他系统中执行任务，例如分配 **GitHub Copilot** 许可证，这需要安全的 API 集成，也就是「工具调用」（tool use）。

通过构建一个能同时做到这两点的 bot，团队既能验证蓝图，又能立即交付业务价值。

## 架构概览

本文中，我们探讨 AutoScout24 用于构建其标准化 AI 开发框架的架构，该框架使安全且可扩缩的 AI agent 得以快速部署。

![架构图展示 AgentCore Runtime 系统的工作流：从 Slack 用户交互出发，经 AWS 服务，到访问 GitHub 与 Amazon Bedrock KnowledgeBase 的专用工作 agent。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/01/06/image-ML195901.png)

该架构采用简单、解耦的流程设计，以确保系统既具韧性又易于维护。图中提供了一个聚焦核心生成式 AI 工作流的简化视图。在生产环境中，还可以集成 [AWS Identity and Access Management（IAM）](https://aws.amazon.com/iam/)、[Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)、[AWS X-Ray](https://aws.amazon.com/xray/)、[AWS CloudTrail](https://aws.amazon.com/cloudtrail/)、[AWS Web Application Firewall（WAF）](https://aws.amazon.com/waf/) 和 [AWS Key Management Service（KMS）](https://aws.amazon.com/kms/) 等额外 AWS 服务，以增强安全性、可观测性与运营治理。

下面是一个请求流经该系统的过程：

- **通过 Slack 的用户交互：** 开发者在支持频道中发布消息，例如「@SupportBot，我可以申请一个 GitHub Copilot 许可证吗？」
- **经由 **[**Amazon API Gateway**](https://aws.amazon.com/api-gateway/)** 与 **[**AWS Lambda**](https://aws.amazon.com/lambda/)** 的安全入口：** Slack 将事件发送到 Amazon API Gateway 端点，该端点触发一个 AWS Lambda 函数。此函数执行一项必要的安全检查，验证请求的密码学签名，以确认它确实来自 Slack。
- **经由 **[**Amazon Simple Queue Service (SQS**](https://aws.amazon.com/sqs/))** 解耦：** 经过验证的请求被放入 Amazon SQS 先进先出（FIFO）队列。这将前端与 agent 解耦，提升韧性。使用 FIFO 队列并以消息的线程时间戳作为 MessageGroupId，可确保单次会话内的回复按顺序处理，这对保持对话连贯很重要。
- **经由 **[**Amazon Bedrock AgentCore**](https://aws.amazon.com/bedrock/agentcore/)** 的 agent 执行：** 消息到达时，SQS 队列触发一个 Lambda 函数，从而激活运行在 AgentCore Runtime 中的 agent。AgentCore 负责运营性任务，包括编排对基础模型以及 agent 工具的调用。Orchestrator Agent 的逻辑使用 [Strands Agents](https://aws.amazon.com/blogs/opensource/introducing-strands-agents-an-open-source-ai-agents-sdk/) 构建，它会分析用户的 prompt，并确定应调用哪个专用 agent——若是一个问题，则调用 Knowledge Base Agent；若是一个动作请求，则调用 GitHub Agent。

一个关键的实现细节是系统如何利用 AgentCore 完整的会话隔离能力。为保持对话上下文，系统通过组合频道 ID 与线程时间戳，为每个 Slack 线程生成唯一的、确定性的 sessionId。该 sessionId 会随该线程内的每一次 agent 调用一并传递。同一线程内的交互共享同一个 sessionId，因此 agent 会将其视为一次连续的对话。同时，其他线程中的交互会得到不同的 sessionId，从而保持各自上下文相互独立。实际上，每个对话都在一个隔离的会话中运行：AgentCore 会为每个 sessionId 启动独立资源，因此上下文与状态不会在线程之间泄漏。在实践中，这意味着如果开发者在同一个 Slack 线程中发送多条消息，agent 会记住该对话此前的部分。每个线程的历史都由 AgentCore 自动保留。

这一会话管理策略对可观测性同样至关重要。基于唯一的 sessionId，可以使用 [AWS X-Ray](https://aws.amazon.com/xray/) 追踪整个交互，从而洞察流程——从 Slack 消息到达 API Gateway，到消息被放入 SQS 队列。它还会跟踪 orchestrator 的处理、对基础模型的调用、随后的工具调用（例如知识库查询或 GitHub API 调用），以及最终返回 Slack 的响应。

元数据与耗时有助于标示每一步的流转，从而了解时间花在哪里。如果某一步失败或变慢（例如外部 API 调用超时），X-Ray 能精确定位是哪一步导致了问题。这对快速诊断问题、建立对系统行为的信心非常有价值。

## 解决方案：由 AWS 驱动的可复用蓝图

由 AutoScout24 与 AWS 团队设计的 Bot Factory 架构是事件驱动的、无服务器的，并构建在托管 AWS 服务的基础之上。这种方式提供了一个具韧性且可扩缩的模式，可适配新的用例。

该解决方案构建在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 及其集成能力之上：

- **Amazon Bedrock** 提供对高性能基础模型（FM）的访问，这些模型充当 agent 的推理引擎。
- [**Amazon Bedrock Knowledge Bases**](https://aws.amazon.com/bedrock/knowledge-bases/) 提供 RAG 能力，使 agent 能够连接 AutoScout24 的内部文档并检索信息，以准确回答问题。
- **Amazon Bedrock AgentCore** 是蓝图运营侧的关键组件。它提供全托管、无服务器的运行时环境，用于部署、运行和扩缩 agent。

这一解决方案为 AutoScout24 带来了显著优势。他们无需自行构建用于会话管理、安全与可观测性的基础基础设施，而是使用 AgentCore 专为此构建的服务。这使团队能够专注于 agent 的业务逻辑，而非底层基础设施。AgentCore 还提供内置的安全与隔离特性。每次 agent 调用都在其自身隔离的容器中运行，有助于防止会话之间的数据泄漏。agent 会被分配特定的 IAM 角色以限制其 AWS 权限（遵循最小权限原则）。agent 工具所需的凭证或 token（例如 GitHub API 密钥）安全地存储在 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 中，并在运行时访问。这些特性为团队提供了一个以最少自定义基础设施运行 agent 的安全环境。

agent 本身使用 Strands Agents SDK 构建，这是一个开源框架，可简化用 Python 定义 agent 的逻辑、工具与行为。这一组合被证明有效：用 Strands 构建 agent，用 AgentCore 安全地大规模运行它。团队采用了成熟的「agents-as-tools」设计模式，由一个中心 orchestrator Agent 充当主控制器。该 orchestrator 并不包含所有可能任务的逻辑，而是智能地把请求委派给专用的单一用途 agent。对于这个支持 bot，这包括一个处理信息查询的 Knowledge Base agent，以及一个执行诸如分配许可证等动作的 GitHub agent。这种模块化设计使系统可以轻松扩展新能力，例如新增一个 PR 审查 agent，而无需重新架构整条 pipeline。在 Amazon Bedrock 上运行这些 agent 进一步增强了灵活性，因为团队可以从广泛的基础模型中选择。更强大的模型可应用于复杂推理任务，而更轻量、成本更低的模型则很适合诸如 GitHub 许可证请求或运营工作流这类常规工作 agent。这种混搭模型的能力使 AutoScout24 能够在其 agent 架构中平衡成本、性能与准确性。

### Orchestrator agent：使用 Strands SDK 构建

使用 Strands Agents SDK 帮助团队以简洁的声明式代码定义 orchestrator agent。该框架采用模型驱动的方式：开发者专注于定义 agent 的指令与工具，而由基础模型负责推理与规划。orchestrator agent 只需几十行 Python 即可表达。下面的示例片段（为清晰起见做了简化，不适用于直接使用）展示了如何为 agent 配置模型、系统 prompt 以及工具列表（在此架构中，工具即代表各个专用 agent）：

```
# A simplified, representative example of the orchestrator agent logic
# built with the Strands Agents SDK and deployed on Amazon Bedrock AgentCore.
from bedrock_agentcore.runtime import BedrockAgentCoreApp
from strands import Agent
from strands.models import BedrockModel
from tools import knowledge_base_query_tool, github_copilot_seat_agent
# Initialize the AgentCore application, which acts as the serverless container
app = BedrockAgentCoreApp()
class OrchestratorAgent:
    def __init__(self):
        # 1. Define the Model: Point to a foundation model in Amazon Bedrock.
        self.model = BedrockModel(model_id="anthropic.claude-3-sonnet-20240229-v1:0")
        
        # 2. Define the Prompt: Give the agent its core instructions.
        self.system_prompt = """
        You are a helpful and friendly support bot for the AutoScout24 Platform Engineering team.
        Your goal is to answer developer questions and automate common requests.
        Use your tools to answer questions or perform actions.
        If you cannot handle a request, politely say so.
        """
        
        # 3. Define the Tools: Provide the agent with its capabilities.
        # These tools are entry points to other specialized Strands agents.
        self.tools = [
            knowledge_base_query_tool, 
            github_copilot_seat_agent
        ]
        
        # Create the agent instance
        self.agent = Agent(
            model=self.model, 
            system_prompt=self.system_prompt, 
            tools=self.tools
        )
    def __call__(self, user_input: str):
        # Run the agent to get a response for the user's input
        return self.agent(user_input)
# Define the entry point that AgentCore will invoke when a new event arrives from SQS
@app.entrypoint
def main(event):
    # Extract the user's query from the incoming event
    user_query = event.get("prompt")
    
    # Instantiate and run the orchestrator agent
    return OrchestratorAgent()(user_query)
```

另一个例子是 GitHub Copilot 许可证 agent。它以 Strands 工具函数的形式实现。下面的片段展示了团队如何使用 @tool 装饰器定义它。该函数创建一个 GitHubCopilotSeatAgent，把用户的请求（一个 GitHub 用户名）传给它，并返回结果：

```
from strands import Agent, tool
class GitHubCopilotSeatAgent:
def __call__(self, query: str):
agent = Agent(model=self.model, system_prompt=self.system_prompt, tools=self.tools)
return agent(query)

@tool
def github_copilot_seat_agent(github_username: str) -> str:
agent = GitHubCopilotSeatAgent() response = agent(f"Request GitHub Copilot license for user: {github_username}")
return str(response)
```

这种方式的关键优势包括清晰的关注点分离。开发者编写聚焦于 agent 目的的声明式代码，而包括扩缩、会话管理与安全执行在内的复杂基础设施逻辑由 Amazon Bedrock AgentCore 处理。这种抽象实现了快速开发，使 AutoScout24 能更快地从原型走向生产。工具列表实际上把其他 agent 变成了可调用函数，使 orchestrator 无需了解其内部实现即可委派任务。

### 影响：一个经过验证的企业 AI 蓝图

Bot Factory 项目交付的成果超越了最初的原型。它创造了即时业务价值，并为 AutoScout24 未来的 AI 创新奠定了战略基础。关键成果包括：

- **一个可用于生产的支持 bot：** 团队部署了一个功能完整的 Slack bot，它正在积极减轻 AutoScout24 AI 平台工程团队的人工支持负担，解决此前花在重复性任务上的 30% 时间。
- **一个可复用的 Bot Factory 蓝图：** 该项目产出了一个经过验证、可复用的架构模式。现在，AutoScout24 的各团队可以基于这一经过验证的模板（Slack -> API Gateway -> SQS -> AgentCore）着手构建新 agent。这使团队能够专注于其独特的业务逻辑，而不必重新发明基础设施，从而显著加速创新。这种模块化设计还为他们准备了更高级的多 agent 协作能力——随着需求演进，可能会采用 [Agent-to-Agent（A2A）协议](https://github.com/a2aproject/A2A) 等标准。
- **赋能更广泛的 AI 开发：** 通过抽象掉基础设施的复杂性，Bot Factory 让更多人能够构建 AI 解决方案。安全或数据分析领域的领域专家现在可以创建新工具或专用 agent，并把它「接入」工厂，而无需成为分布式系统专家。

### 结论：企业 agent 的新范式

AutoScout24 与 AWS 的合作把零散的生成式 AI 试验转变为一个可扩缩的标准化框架。通过采用 Amazon Bedrock AgentCore，团队把支持 bot 从原型推进到生产，同时专注于他们的 Bot Factory 愿景。AgentCore 负责管理会话状态与扩缩，因此工程师可以专注于高价值的业务逻辑，而非基础设施。其成果不只是一个支持 bot：它是一块用于构建企业 agent 的可复用基石。借助 AgentCore，AutoScout24 能够高效地从原型走向生产，为组织如何在 AWS 上标准化生成式 AI 开发树立了范式。要开始使用 Amazon Bedrock 构建企业 agent，请查阅以下资源：
