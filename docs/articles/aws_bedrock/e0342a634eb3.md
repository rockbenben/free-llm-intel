# Exa 将嵌入吞吐量提升 50%，在 AWS AI 芯片上索引数十亿文档

在 [Exa](https://exa.ai/)，我们正在构建为数不多的真正 Web 索引之一：把来自整个 Web 以及私有来源、合成来源的知识聚合起来并对外提供服务。我们针对语义搜索优化这个索引，让 agent 和人类都落在真实、高质量的数据上。我们用多塔语义机器学习（ML）模型，把 Web 数据和查询数据嵌入同一个向量空间，用户因此可以在传统关键词搜索之外，用自然语言表达复杂查询。支撑这一切的基石技术是自研的向量数据库：它必须尽可能多地摄入高质量 Web 数据，并把这些数据全部嵌入。于是，嵌入的单位经济性成为我们一切工作的底层约束。在数百亿乃至数千亿文档的规模上，找到每美元性能最好的硬件不是调优细节——任何单文档成本的改善，都会复利成可观的数字。

本文介绍我们如何在 AWS Neuron 硬件（[AWS Inferentia2](https://aws.amazon.com/ai/machine-learning/inferentia/) 和 [AWS Trainium2](https://aws.amazon.com/ai/machine-learning/trainium/)）上为更便宜、更灵活的推理负载优化嵌入基础设施，以及一条 agentic 开发工作流如何推动了这次优化。

推理跑在异步流水线上，但必须高吞吐、足够快，才能及时服务最新数据，缩短从发现到对外提供之间的间隔。

## 大规模嵌入文档

我们与 Neuron 硬件系列的结缘始于一次回填。要迁到更好的文档模型，就得把现有语料重新嵌入一遍。我们挑出 300 亿份高优先级文档做重新嵌入。这类迁移会让嵌入负载暂时翻倍，也正因如此，它成了重新审视硬件选型的最佳时机。

## 优化历程

AWS Inferentia2 的数据指最小实例类型 [Inferentia2 xlarge 实例](https://aws.amazon.com/ec2/instance-types/inf2/)（`inf2.xlarge`）上的表现，该实例包含一个芯片和两个 [NeuronCores](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/about-neuron/arch/neuron-hardware/neuron-core-v2.html)。我们的负载只跑在单个 NeuronCore 上，因此我们把 Kubernetes Pod 打包到更大的实例上，不留下空闲核心，从而在整个嵌入机群中保持容器同构。同一套流程也能跑在 Trainium2 NeuronCore 上，并以相同的数据并行方式扩展。最初的 Inferentia2 实现，是对模型做直白的数据并行 FP16 表示。从这个基线出发，我们借助 Neuron SDK 和 AWS Trainium 团队的支持，一路把吞吐（docs/sec）往高推。下图展示了各里程碑处的吞吐提升。

![展示各优化里程碑吞吐量提升的图表，最终升至约为基线的 1.5 倍](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/13/ML-22138-3-1.png)

图 3：各优化里程碑的吞吐提升

从最朴素的编译起步，一系列递进的优化最终带来约 1.5× 的吞吐提升。第一步是权重布局优化：让权重布局与整体模型的调度和布局对齐，去掉不必要的转置。我们还启用了 autocast，让编译器把矩阵乘法降精度到更低精度，同时保住动态范围。降精度后的输出达到了我们的正确性门槛——相对参考结果 0.999 的余弦相似度（见 [Agentic methodology](https://aws.amazon.com/blogs/machine-learning/exa-boosts-embedding-throughput-by-50-to-index-billions-of-documents-on-aws-ai-chips/#agentic-methodology)）——因此精度影响落在可接受阈值之内。

### NKI kernel

[Neuron Kernel Interface](https://awsdocs-neuron.readthedocs-hosted.com/en/v2.33.0/nki/index.html)（NKI）库为常见模型层和算子提供优化好的 kernel。这些预构建 kernel 在常见特性上即时见效，我们用它们迅速清掉了最直接的效率损耗。一个可直接替换的注意力 kernel 带来了下一波性能提升。

### 内存布局优化：融合 SwiGLU MLP kernel

下一个瓶颈是内存溢出。[Neuron Explorer](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/tools/neuron-explorer/index.html) 的剖析结果持续显示，大量数据从高带宽内存（HBM）溢出后又被重新加载，导致 Tensor Engine 在整个前向传播过程中都无法被吃满。我们先把一个可直接替换的 MLP kernel 当作跳板，剖析预构建实现的短板，随后写了一个自定义的权重驻留式融合 SwiGLU MLP kernel，消除了 HBM 停顿。

布局操作、循环和内存操作，我们用较高层的 NKI 语言编写，只有特定张量算子才下沉到更低层的 NKI ISA。让 kernel 的大部分停留在高层语言里，工程师更容易理解，也更容易调试。

### 减少 FLOPS

到这里我们撞上了墙。另一个片上核心空闲时测得的单加速器吞吐，明显高于两个核心同时运行的吞吐。这个差距意味着，理论上的数据并行吞吐本应远高于实际达到的总体性能——问题指向核心之间的争用。

剖析和实验表明，我们的负载还没有把 Tensor Engine 吃满。剩下的余量，只能靠把计算做得更精简来拿。最清晰的路子是消除浪费，减少产出结果所需的 FLOPS 总量。我们围绕模型里的确切形状重写了注意力 kernel，砍掉花在填充上的 FLOPS。kernel 定制的价值正体现在这里：通用 kernel 为了应付任意形状而构建，因此用不上某个具体架构里的特定形状。我们按模型注意力头架构的真实形状来定制实现，从注意力里又榨出一截性能。在通用 kernel 要用多条指令步骤的地方，我们还把注意力算子折叠进单个 matmul。这减少了算出同样数值所需的内层循环操作，也减少了 HBM 往返，最终换来显著的提速。

总计，相比最初的基线，我们的最终版本在每嵌入 100 万份文档的性能和成本上改善了 47%。

## agentic 方法论

所有这些优化，都是 agent 在一个简单的三段式 harness 里完成的：这套 harness 让它们验证正确性、测量性能、剖析负载，从而找到下一个方向。借助 ML ops 工作流平台 [Flyte](https://flyte.org/)，每个 agent 运行属于自己的工作流。工作流会编译一个 [NEFF](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/compiler/neuronx-cc/how-to-generate-neff.html#neuronx-cc-generate-neff-how-to) Neuron 可执行文件，并针对基线数据集检查一次前向传播，结果必须达到与规范模型 0.999 的余弦相似度；随后剖析一次前向传播，并在真实硬件上跑一场 30 分钟的饱和基准测试。

这套 harness 支持不同成本的 agent。轻量模型负责繁琐的活，例如网格搜索编译器参数，正确性检查则防止跑偏；推理型 agent 验证复杂假设、定位瓶颈，最强的代码生成器编写自定义 kernel 来把它们修掉。让每个 agent 匹配自己的任务可以压住成本，验证则让能力强的 agent 不至于漂移。由于许多 agent 并不了解最新的特性和语法，[neuron agentic development skills](https://github.com/aws-neuron/neuron-agentic-development/tree/main) 也帮上了忙。

## 灵活算力的好处

到目前为止，我们只在美国西部（俄勒冈）区域（[us-west-2](https://aws.amazon.com/about-aws/global-infrastructure/regions_az/)）优化了 Inferentia2，但在单一区域调优单一硬件系列是有硬上限的。Spot 和 On-Demand 的可用性因区域而异，使用方众多的组织还会跟自己抢资源。锁定一个区域或一种实例类型，几乎必然导致算力短缺，甚至服务降级。

Exa 从单一 Kubernetes 控制平面跨多个区域调度算力。调度器比较各实例类型的每美元性能，把 Pod 打包到最便宜的节点上，并在嵌入需求变化时重新调度。我们每优化一种硬件类型，就离全局最优更近一步——这也是 Inferentia2 上的工作能直接沿用到 Trainium2 的原因。切换硬件配置，让我们可以腾出别的团队需要的节点，或吸收他们闲置的预留算力。对一个长期存活的模型来说，跨硬件优化回报巨大。

## 结论

在 Exa 的运营规模上，真正重要的是从一个灵活的硬件池里榨出最大的性价比。把 Neuron 硬件加进这个池子，并用 NKI 对它做优化，已被证明是长期成本节约的重要来源。
