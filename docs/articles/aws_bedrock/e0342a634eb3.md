# Exa 在 AWS AI 芯片上将嵌入吞吐量提升 50%，为数十亿文档建立索引

在 [Exa](https://exa.ai/)，我们正在构建少数真正的 Web 索引之一，通过聚合并提供来自整个 Web 以及私有和合成来源的知识。我们针对语义搜索优化该索引，让智能体和人类基于真实、高质量的数据。我们使用多塔语义机器学习（ML）模型，将 Web 数据和查询数据嵌入同一向量空间，因此用户可以在传统关键词搜索之外，用自然语言表达复杂查询。其背后的基石技术是自研向量数据库。它必须尽可能多地摄取高质量 Web 数据，并对其全部完成嵌入。因此，嵌入的单位经济性构成了我们一切工作的基础。在数百亿乃至数千亿文档的规模下，找到每美元性能最佳的硬件并不是一个调优细节。任何单文档成本的改善都会复利成可观的数字。

本文详细介绍了我们如何在 AWS Neuron 硬件（[AWS Inferentia2](https://aws.amazon.com/ai/machine-learning/inferentia/) 和 [AWS Trainium2](https://aws.amazon.com/ai/machine-learning/trainium/)）上为更便宜、更灵活的推理工作负载优化嵌入基础设施，以及智能体式开发工作流如何推动这一优化。

推理运行在异步流水线上，但必须高吞吐且快速，以便快速服务最新数据，并缩短从发现到提供服务之间的时间。

我们对 Neuron 硬件系列的经验始于一次回填。迁移到更优的文档模型意味着要重新嵌入现有语料库。我们选择了 300 亿份高优先级文档进行重新嵌入。这样的迁移会暂时使嵌入负载翻倍，这正是重新评估硬件选择的合适时机。

## 优化历程

AWS Inferentia2 的数据指最小实例类型 [Inferentia2 xlarge 实例](https://aws.amazon.com/ec2/instance-types/inf2/)（`inf2.xlarge`）上的性能，该实例包含一个芯片和两个 [NeuronCores](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/about-neuron/arch/neuron-hardware/neuron-core-v2.html)。我们的工作负载运行在单个 NeuronCore 上，因此我们运行 Kubernetes Pod，将它们打包到更大的实例上而不让任何核心空闲，从而在嵌入集群中实现容器同质性。同一进程可在 Trainium2 NeuronCore 上运行，并以相同方式通过数据并行扩展。我们最初的 Inferentia2 实现是直接采用数据并行、FP16 表示的模型。从该基线开始，我们借助 Neuron SDK 和 AWS Trainium 团队的支持，尽可能推高吞吐量（docs/sec）。下图展示了每个里程碑处的吞吐量提升。

![展示各优化里程碑吞吐量提升的图表，最终升至约为基线的 1.5 倍](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/13/ML-22138-3-1.png)

图 3：各优化里程碑的吞吐量提升

从朴素编译开始，一系列逐步推进的优化最终带来了约 1.5× 的吞吐量提升。首先是权重布局优化，它通过让权重布局与更大模型的调度和布局对齐，消除不必要的转置。我们还启用了 autocast，让编译器将矩阵乘法降精度到更低精度，同时保持动态范围。降精度后的输出达到了我们的正确性门槛：相对参考结果的 0.999 余弦相似度（参见[智能体式方法](https://aws.amazon.com/blogs/machine-learning/exa-boosts-embedding-throughput-by-50-to-index-billions-of-documents-on-aws-ai-chips/#agentic-methodology)），因此准确率影响在我们的可接受阈值内。

### NKI kernel

[Neuron Kernel Interface](https://awsdocs-neuron.readthedocs-hosted.com/en/v2.33.0/nki/index.html)（NKI）库为常见模型层和操作提供优化后的 kernel。这些预构建 kernel 在常见功能上带来即时收益，我们使用它们快速消除了最直接的效率低下来源。一个可直接替换的注意力 kernel 为我们带来了下一轮性能提升。

### 内存布局优化：融合 SwiGLU MLP kernel

下一个瓶颈是内存溢出。[Neuron Explorer](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/tools/neuron-explorer/index.html) 的性能分析持续显示，大量数据从高带宽内存（HBM）溢出并重新加载，这使得 Tensor Engine 在整个前向传播过程中无法被充分利用。我们使用可直接替换的 MLP kernel 作为跳板，分析预构建实现的不足，然后编写了自定义的权重驻留式融合 SwiGLU MLP kernel，消除了 HBM 停顿。

我们使用更高层级的 NKI 语言进行布局操作、循环和内存操作，仅在特定张量操作中下探到更低层级的 NKI ISA。将大部分 kernel 保持在更高层级的语言中，使工程师更容易理解，也更容易调试。

### 减少 FLOPS

此时我们遇到了瓶颈。在另一个片上核心空闲时测得的单加速器吞吐量，显著高于两个核心同时运行时的吞吐量。这一差距意味着，我们的理论数据并行吞吐量本应远高于实际达到的总性能，这表明核心之间存在争用。

性能分析和实验表明，我们的工作负载尚未使 Tensor Engine 饱和。剩余的性能空间可以通过让计算更精简来争取。最清晰的路径是消除浪费，减少产生结果所需的总体 FLOPS。我们围绕模型中的确切形状重写了注意力 kernel，以减少花在填充上的 FLOPS。这正是 kernel 定制真正见效的地方。通用 kernel 为处理任意形状而构建，因此无法利用特定架构中的具体形状。我们根据模型注意力头架构的真实形状定制实现，从注意力中榨取了更多性能。在通用 kernel 使用多个指令步骤的地方，我们还将注意力操作折叠进单个 matmul。这减少了计算相同值所需的内层循环操作，从而降低了 HBM 往返次数，并带来了最终显著的加速。

总体而言，与最初的基线相比，我们的最终版本在每嵌入 100 万份文档的性能和成本上改善了 47%。

## 智能体式方法

智能体在一个简单的三部分测试框架内开发了所有这些优化，该框架让它们验证正确性、测量性能并分析工作负载，以找到下一个方向。使用 ML ops 工作流平台 [Flyte](https://flyte.org/)，每个智能体运行自己的工作流。该工作流编译一个 [NEFF](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/compiler/neuronx-cc/how-to-generate-neff.html#neuronx-cc-generate-neff-how-to) Neuron 可执行文件，并针对基线数据集检查一次前向传播，其结果必须达到与规范模型 0.999 的余弦相似度。然后，它会分析一次前向传播，并在真实硬件上运行 30 分钟的饱和基准测试。

该测试框架支持不同成本的智能体。轻量级模型处理繁琐工作，例如网格搜索编译器参数，正确性检查可防止漂移。推理智能体测试复杂假设并发现瓶颈，而最强的代码生成器编写自定义 kernel 来修复问题。让每个智能体匹配其任务可以控制成本，验证则可以防止能力强的智能体漂移。由于许多智能体不了解最新功能和语法，[neuron agentic development skills](https://github.com/aws-neuron/neuron-agentic-development/tree/main) 也提供了帮助。

## 灵活计算的优势

到目前为止，我们已针对美国西部（俄勒冈）区域（[us-west-2](https://aws.amazon.com/about-aws/global-infrastructure/regions_az/)）优化了 Inferentia2，但在单一区域调优单一硬件系列存在硬性限制。Spot 和 On-Demand 可用性因区域而异，拥有多个使用方的组织会与自己竞争。锁定一个区域或实例类型几乎必然导致计算资源短缺，并可能造成服务降级。

Exa 通过一个 Kubernetes 控制平面跨多个区域调度计算。我们的调度器比较不同实例类型的每美元性能，并将 Pod 打包到最便宜的节点上，在嵌入需求变化时重新调度。我们优化的每种硬件类型都会让我们更接近全局最优。这就是为什么我们的 Inferentia2 工作可以直接沿用到 Trainium2。切换硬件配置让我们可以释放其他团队需要的节点，或吸收他们未使用的预留计算资源。对于长期使用的模型，跨硬件优化会带来巨大回报。

## 结论

在 Exa 运营的规模下，从灵活硬件池中提取最大成本性能才是关键。将 Neuron 硬件加入该硬件池并使用 NKI 对其进行优化，已被证明是长期成本节约的重要来源。
