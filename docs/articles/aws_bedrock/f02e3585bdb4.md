理赔答案散落在查勘员的日记记录、维修估价、警方报告、支付账本和扫描附件中，而非一个可搜索的字段。保单持有人可能问一笔理赔是否获批，而查勘员可能需要上个月所有金额超过 10,000 美元的未结车险理赔。两项任务都需要快速、准确地查找并合并证据。

检索增强生成（RAG）用检索到的文档为模型响应提供接地。[Amazon Bedrock Knowledge Bases](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html) 是用于文档的完全托管 RAG 能力。Amazon Bedrock 处理解析、分块、嵌入和向量存储，于是你可以构建一个从理赔文件中返回带引用答案的对话式界面。

这篇技术 how-to 使用合成的理赔记录，并不描述某个生产客户部署。你构建一个理赔助手，它通过完成以下步骤用引用回答自然语言问题：

- 从 Amazon Simple Storage Service (Amazon S3) 摄入理赔文档及其元数据。
- 用 `AgenticRetrieveStream` API 以大白话查询它们。
- 提出多轮追问。
- 用对理赔 ID 和理赔类型等属性的元数据过滤器限定检索范围。
- 加一道上下文接地护栏，让答案与记录保持绑定。

## 理赔查找的挑战

保单持有人、联络中心客服和查勘员问不同的问题：

- 保单持有人要一个大白话的状态更新：“CLM-100482 这笔理赔的估价获批了吗？支票什么时候开出？”
- 联络中心客服需要在客户等待时快速、准确地回答，而无需转接电话。
- 查勘员问跨多笔理赔的多部分问题，比如上月提交的、金额超过 10,000 美元、哪些未结车险理赔，以及每笔上还剩哪些工作。

答案存放在 PDF 查勘员报告、Word 往来函件和文本笔记里，而非一致的数据库字段。

记录可能相互冲突或取代早期版本。一份修订后的估价可能替换较早的一份，或一笔临时支付后来被撤销。助手必须确定哪份估价、支付或状态起决定作用。

因为理赔受监管，每个答案都必须接地位于源文档并含引用。联络中心客服在复述一个答案之前可以核实来源，而主管可以审计助手是如何得出它的。

## 方案概览

该方案用 [Amazon Bedrock Knowledge Bases](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html) 为检索索引来自 Amazon S3 的理赔文档。

通过 `AgenticRetrieveStream` 的[智能体检索](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html)规划一个答案、把一个多部分问题拆成子查询，并运行一次或多次检索。它在生成响应之前检查证据是否充分。

该 API 流式传输 trace 事件、答案文本和引用。Trace 事件暴露检索计划，而每个引用把答案的一部分映射到一份源理赔文档。

下图展示两条路径。摄入道把理赔文档和元数据加载进一个知识库。检索道把每个问题经 `AgenticRetrieveStream` 和一个 Amazon Bedrock Guardrails 接地检查，然后返回一个带引用的答案。

图 1：带 Amazon Bedrock Knowledge Bases 的对话式理赔助手

摄入道随文档到达而运行：

- PDF、Word 或文本格式的理赔文档落到 Amazon S3，并带上匹配的元数据边车（sidecar）文件。
- 一个摄入作业在文档变化时把 S3 数据源与知识库同步。
- 知识库解析、分块、嵌入并在托管向量存储中索引这些文档及其元数据。

检索道对每个问题运行：

- 应用带着问题、会话历史和可选的限定搜索范围的元数据过滤器调用 `AgenticRetrieveStream`。
- 一个基础模型创建子查询并重复检索，直到它有足够证据，最多 maxAgentIteration 轮。
- 一个上下文接地检查阻止那些不被检索到记录支撑的答案。
- Amazon Bedrock 流式输出答案、trace 事件和引用，因此应用可以在输出到达时显示。

## 前提条件

开始前，确认你具备以下内容：

- 一个 AWS 账户，具备用于 Amazon Bedrock 和 Amazon S3 的 AWS Identity and Access Management (IAM) 权限。
- 通过 [Amazon Bedrock 模型访问](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html) 启用的一个基础模型（FM）的访问权限。
- 一个支持所选基础模型和 Amazon Bedrock Knowledge Bases 的 AWS 区域。本演练使用美国西部（俄勒冈）us-west-2。部署前查看 [Amazon Bedrock 中按 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。
- [AWS SDK for Python (Boto3)](https://aws.amazon.com/sdk-for-python/)，配置好凭证和一个支持本文所用 API 的版本。
- 一个用于合成理赔文档和元数据的 S3 桶。
- 熟悉 Python 和基本的 RAG 概念。

## 准备理赔文档和元数据

在 Amazon S3 中每笔理赔存一份文档。知识库直接读取 PDF 查勘员报告、Word 往来函件和文本笔记，因此你可以把文档保持在其原生格式。

图 2 展示一条合成理赔记录。当前敞口是估计的总理赔成本。其证据索引识别出一份被取代的传真草稿，即一条被更新版本替换的记录。元数据边车重复了助手可以过滤的字段。

图 2：一条合成理赔记录，带其文件控制字段和证据索引

为了过滤，添加一个带同名加 `.metadata.json` 的伴随元数据文件。对 `CLM-100482.pdf`，用 `CLM-100482.pdf.metadata.json`。代位求偿是保险人向责任第三方追回成本的努力。下面的例子描述一笔车险理赔：

```
{
    "metadataAttributes": {
        "claim_id": "CLM-100482",
        "claim_type": "auto",
        "status": "open",
        "date_filed": 20260709,
        "amount": 14250,
        "region": "us-west",
        "adjuster": "Martha Rivera",
        "policyholder": "Mary Major",
        "policy_number": "POL-AUTO-78432",
        "customer_id": "CUST-MM-1042",
        "household_id": "HHD-MM-1042",
        "document_type": "adjuster_report",
        "carrier": "Example Insurance",
        "has_subrogation": true,
        "has_litigation": false,
        "complexity_tier": "high"
    }
}
```

边车含标量的字符串、数字和布尔值。值类型决定可用的过滤器。下表列出后续查询用到的字段。

本文使用合成数据。在没有必要的控制和批准之前，不要把真实的可识别个人身份信息（PII）或受保护的医疗信息放进这些资源。

| 属性 | 类型 | 示例 | 过滤用途 |
| --- | --- | --- | --- |
| claim_id | String | CLM-100482 | equals，用于单笔理赔查找 |
| claim_type | String | auto | equals 或 in，用于一条业务线 |
| status | String | open | in，用于活跃工作队列 |
| amount | Number | 14250 | 数字范围比较 |
| date_filed | Number | 20260709 | 以 `YYYYMMDD` 整数表示的日期范围 |
| region | String | us-west | 来自会话的租户范围界定 |
| customer_id | String | CUST-MM-1042 | 来自会话的客户范围界定 |
| has_subrogation | Boolean | true | equals，用于追偿工作 |

把日期存为 `YYYYMMDD` 整数，因为元数据过滤器比较数字而非日期字符串。这种格式支持像“上月提交”这样的范围。

在 `amount` 中只存一个可比较的金额值。准备金（reserve）是为估计理赔成本预留的钱，而暂扣款（hold）是暂时扣留的。把准备金、支付和暂扣款留在文档文本中，使它们的标签保持清晰。

边车文件限制为 10 KB。完整格式参见[为你的知识库连接到 Amazon S3](https://docs.aws.amazon.com/bedrock/latest/userguide/s3-data-source-connector.html)。

## 创建托管知识库并摄入理赔

用 bedrock-agent 客户端创建知识库。把 knowledgeBaseConfiguration.type 和 embeddingModelType 设为 MANAGED。

Amazon Bedrock 选择并运营嵌入模型。无需向量存储配置。所有参数见 [CreateKnowledgeBase](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent_CreateKnowledgeBase.html)。下面的代码创建知识库：

```
import boto3

bedrock_agent = boto3.client("bedrock-agent", region_name="us-west-2")

kb = bedrock_agent.create_knowledge_base(
    name="insurance-claims-kb",
    description="Synthetic insurance claims for the claims assistant",
    roleArn="arn:aws:iam::111122223333:role/InsuranceClaimsKnowledgeBaseRole",
    knowledgeBaseConfiguration={
        "type": "MANAGED",
        "managedKnowledgeBaseConfiguration": {
            "embeddingModelType": "MANAGED"
        },
    },
)
kb_id = kb["knowledgeBase"]["knowledgeBaseId"]
```

roleArn 服务角色授予知识库读取 S3 桶和使用托管嵌入模型的权限。参见[为 Amazon Bedrock Knowledge Bases 创建一个服务角色](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-permissions.html)。要用客户托管的 [AWS Key Management Service (AWS KMS)](https://docs.aws.amazon.com/kms/latest/developerguide/overview.html) 密钥加密托管向量存储，在 serverSideEncryptionConfiguration 中传入其 ARN。

接下来，把 S3 桶连接为一个数据源。inclusionPrefixes 设置把摄入限定到 claims/：

```
data_source = bedrock_agent.create_data_source(
    knowledgeBaseId=kb_id,
    name="claims-s3",
    dataSourceConfiguration={
        "type": "S3",
        "s3Configuration": {
            "bucketArn": "arn:aws:s3:::amzn-s3-demo-insurance-claims",
            "inclusionPrefixes": ["claims/"],
        },
    },
)
data_source_id = data_source["dataSource"]["dataSourceId"]
```

启动一个摄入作业来解析、分块、嵌入并索引文档。每当理赔文档被添加或更新时重新运行它，以保持索引同步：

```
bedrock_agent.start_ingestion_job(
    knowledgeBaseId=kb_id,
    dataSourceId=data_source_id,
)
```

用 get_ingestion_job 或 Amazon Bedrock 控制台检查状态。当作业完成时，理赔就可搜索了。细节参见 [StartIngestionJob](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent_StartIngestionJob.html)。

## 用 AgenticRetrieveStream API 查询理赔

理赔摄入后，用 bedrock-agent-runtime 客户端调用 [AgenticRetrieveStream](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_AgenticRetrieveStream.html)。完整的请求和响应语法见 API 参考。请求有三个部分：

- messages：会话回合。每条消息有一个 user 或 assistant 角色和一个 content.text 值。
- retrievers：最多五个知识库。每个含一个知识库 ID，并可指定一个元数据过滤器和 maxNumberOfResults（1–100）。对跨多笔理赔的问题提高上限。
- agenticRetrieveConfiguration：规划模型和迭代上限。服务模型用 MANAGED。要用一个特定模型，用一个 model ARN 配 CUSTOM。maxAgentIteration 给规划和检索轮数封顶。

这个请求问一笔理赔的状态。把 generateResponse 设为 True 返回一个自然语言答案：

```
bedrock_agent_runtime = boto3.client("bedrock-agent-runtime", region_name="us-west-2")

response = bedrock_agent_runtime.agentic_retrieve_stream(
    messages=[
        {"role": "user", "content": {"text": "What is the status of claim CLM-100482?"}}
    ],
    retrievers=[
        {
            "configuration": {"knowledgeBase": {"knowledgeBaseId": kb_id}},
            "description": "Synthetic insurance claim records",
        }
    ],
    agenticRetrieveConfiguration={
        "foundationModelType": "MANAGED",
        "maxAgentIteration": 5,
    },
    generateResponse=True,
)
```

遍历 response[“stream”] 并处理这三种事件类型：

- traceEvent：报告每一步的规划、检索、全文档展开、护栏动作、状态，以及生成的子查询。
- responseEvent：提供你可以流式给用户的增量答案文本。
- result：含去重后的检索结果，且当 generateResponse 为 True 时含完整的生成答案及其引用。

下面的循环在答案块到达时流式它们，并为引用渲染保留最终结果：

```
answer = ""
final_result = None

for event in response["stream"]:
    if "traceEvent" in event:
        attributes = event["traceEvent"]["attributes"]
        print(f"[trace] {attributes.get('step')}: {attributes.get('status')}")
    elif "responseEvent" in event:
        chunk = event["responseEvent"]["text"]
        answer += chunk
        print(chunk, end="", flush=True)
    elif "result" in event:
        final_result = event["result"]
```

### 读 trace 以看清计划

基本的循环打印每一步和状态。这个辅助函数还打印子查询、全文档取回和护栏动作：

```
def report_trace(trace_event):
    attributes = trace_event.get("attributes", {})
    print(f"[trace] {attributes.get('step')}: {attributes.get('status')}")

    for action in attributes.get("actions", []):
        if "retrieve" in action:
            sub_query = action["retrieve"].get("inputQuery", {}).get("text", "")
            print(f"    sub-query: {sub_query}")
        elif "fullDocumentExpansion" in action:
            document = action["fullDocumentExpansion"].get("documentId", "")
            print(f"    full document: {document}")

    for warning in attributes.get("warnings", []):
        if "guardrail" in warning:
            print(f"    guardrail: {warning['guardrail'].get('action')}")
```

图 3 展示智能体循环。服务规划一个策略、创建子查询、检索证据，并检查它是否足够。如有需要，它在生成一个带引用的答案之前再运行一遍。

图 3：从问题到带引用答案的智能体检索循环

### 渲染引用

每个引用识别答案中的一个字符区间，并引用 result 事件的 results 数组中的支撑条目。应用用这些索引把显示的文本与其源文档关联。

下面的代码在每段被引用的文本旁，打印其源文档的内建 x-amz-bedrock-kb-source-uri 值：

```
generated = final_result["generatedResponse"]
results = final_result["results"]

for citation in generated.get("citations", []):
    span = generated["answer"][citation["startIndex"]:citation["endIndex"]]
    for reference in citation["references"]:
        source = results[reference["resultIndex"]]
        source_uri = source.get("metadata", {}).get("x-amz-bedrock-kb-source-uri")
        print(f'"{span}"\n  -> {source_uri}')
```

## 在多轮对话中提追问

追问依赖于先前的回合。在一个状态答案之后，保单持有人可能问“分配给它的是哪位查勘员？”这个词 *it* 从传入 messages 的会话历史中解析。

把会话保持在应用里。每回合之后，追加用户的问题和助手的答案，然后在下次调用时发送完整的列表：

```
messages = [
    {"role": "user", "content": {"text": "What is the status of claim CLM-100482?"}},
    {"role": "assistant", "content": {"text": answer}},
    {"role": "user", "content": {"text": "Who is the adjuster assigned to it?"}},
]

response = bedrock_agent_runtime.agentic_retrieve_stream(
    messages=messages,
    retrievers=[
        {"configuration": {"knowledgeBase": {"knowledgeBaseId": kb_id}}}
    ],
    agenticRetrieveConfiguration={"foundationModelType": "MANAGED"},
    generateResponse=True,
)
```

服务用较早的回合把 it 解析为理赔 `CLM-100482` 并检索那笔理赔的查勘员。像之前一样处理响应流。

## 用元数据过滤器限定检索范围

元数据过滤器在语义搜索之前限制文档。把它们加在 retriever 的 retrievalOverrides 下。用查询过滤器做相关性，并从服务器上经认证的会话派生授权过滤器。

对于按理赔 ID 的直接查找，用一个 equals 过滤器：

```
retrievers = [
    {
        "configuration": {
            "knowledgeBase": {
                "knowledgeBaseId": kb_id,
                "retrievalOverrides": {
                    "filter": {"equals": {"key": "claim_id", "value": "CLM-100482"}}
                },
            }
        }
    }
]
```

对于 2026 年 7 月提交、金额超过 10,000 美元的未结车险理赔，用 andAll 组合理赔类型、状态、金额和日期条件：

```
claims_filter = {
    "andAll": [
        {"equals": {"key": "claim_type", "value": "auto"}},
        {"equals": {"key": "status", "value": "open"}},
        {"greaterThan": {"key": "amount", "value": 10000}},
        {"greaterThanOrEquals": {"key": "date_filed", "value": 20260701}},
        {"lessThanOrEquals": {"key": "date_filed", "value": 20260731}},
    ]
}

response = bedrock_agent_runtime.agentic_retrieve_stream(
    messages=[
        {
            "role": "user",
            "content": {
                "text": "Summarize the outstanding items on the open auto "
                        "claims over $10,000 filed in July."
            },
        }
    ],
    retrievers=[
        {
            "configuration": {
                "knowledgeBase": {
                    "knowledgeBaseId": kb_id,
                    "retrievalOverrides": {
                        "filter": claims_filter,
                        "maxNumberOfResults": 50,
                    },
                }
            }
        }
    ],
    agenticRetrieveConfiguration={"foundationModelType": "MANAGED"},
    generateResponse=True,
)
```

这个查询可能匹配很多理赔，所以 maxNumberOfResults 是 50。更小的上限可能在摘要中遗漏匹配的理赔。

支持的操作符包括 equals、notEquals、数字比较、in、notIn、stringContains、listContains，以及逻辑 andAll/orAll。startsWith 仅限于 Amazon OpenSearch Serverless 向量存储。参见[元数据与过滤](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-metadata.html) 并确认操作符支持。

如果某个过滤器没有返回文档，检查是否有空结果并返回一条清晰的消息（如“没有理赔符合那些条件”），而非生成一个答案。

## 我们测量了什么

我们用 Retrieve 和 RetrieveAndGenerate 测量了这个 30 文档的合成语料，而非 AgenticRetrieveStream。把这些结果当作语料和元数据 schema 的基线，而非一个智能体检索基准。

这个 40 问题套件包括直接查找、比较、别名、被取代的记录、被撤销的支付，以及类指令的文档文本。自动化的基础模型评分使事实层面的结果只是方向性的。

期望来源检索召回衡量所需的文档被找到。引用召回衡量所需的文档被引用。两者都在文档级逐问平均，且不衡量块精确度。

下表展示总体结果。

| 指标 | 结果 |
| --- | --- |
| 回答的问题 | 40 of 40 |
| 带引用的答案 | 40 of 40 |
| 每答案平均引用数 | 3.9 |
| 期望来源检索召回 | 90.5% |
| 期望来源引用召回 | 81.2% |
| 与所请求过滤器相矛盾的块 | 0 |

来源：本文描述的 40 问题评估套件和基础模型评分器。

在 20 道对抗性问题上，检索召回为 96.7%，引用召回为 90.2%。模型把名称相似的公司分开、把一个指控保留为一个指控，并忽略附件内类指令的文本。

引用覆盖并不保证答案完整性，因此在完整性重要时要单独衡量它。

这些结果使用合成文档和自动化评分。在向保单持有人暴露一个助手之前，对你自己的语料做人工审阅。

## 添加安全与治理

一个理赔助手需要访问控制和接地的响应。

### 把过滤器限定到经认证的用户

把元数据过滤器当作一道访问边界。从经认证的会话派生 `region` 或 `customer_id`，用 andAll 把它与查询过滤器组合，且永不从用户文本接受这道边界。userContext 字段也支持访问控制过滤。

### IAM 权限

只授予智能体检索、知识库访问、模型流式传输和护栏动作所需的权限：

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": "bedrock:AgenticRetrieveStream",
            "Resource": "*"
        },
        {
            "Effect": "Allow",
            "Action": [
                "bedrock:Retrieve",
                "bedrock:GetDocumentContent"
            ],
            "Resource": "arn:aws:bedrock:us-west-2:111122223333:knowledge-base/*"
        },
        {
            "Effect": "Allow",
            "Action": "bedrock:InvokeModelWithResponseStream",
            "Resource": "*"
        },
        {
            "Effect": "Allow",
            "Action": [
                "bedrock:GetGuardrail",
                "bedrock:ApplyGuardrail"
            ],
            "Resource": "*"
        }
    ]
}
```

[AWS CloudTrail](https://docs.aws.amazon.com/bedrock/latest/userguide/logging-using-cloudtrail.html) 为审计记录对 Amazon Bedrock 的调用。

### 加密

Amazon S3 默认在静态加密对象。参见[配置默认加密](https://docs.aws.amazon.com/AmazonS3/latest/userguide/default-bucket-encryption.html)。你可以对桶和托管向量存储使用客户托管的 AWS KMS 密钥。API 流量使用传输层安全（TLS）。

### 用 Amazon Bedrock Guardrails 做上下文接地

添加一个 Amazon Bedrock Guardrails [上下文接地检查](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-contextual-grounding-check.html)，以阻止低于配置接地或相关性阈值响应的内容：

- Grounding（接地）：与检索到的理赔文档的一致性。
- Relevance（相关性）：与用户问题的对齐。

用 bedrock 客户端创建一个护栏。所有策略类型见 [CreateGuardrail](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_CreateGuardrail.html)，并为理赔选择一个高的接地阈值：

```
bedrock = boto3.client("bedrock", region_name="us-west-2")

guardrail = bedrock.create_guardrail(
    name="claims-assistant-guardrail",
    description="Contextual grounding for the claims assistant",
    contextualGroundingPolicyConfig={
        "filtersConfig": [
            {"type": "GROUNDING", "threshold": 0.85},
            {"type": "RELEVANCE", "threshold": 0.75},
        ]
    },
    blockedInputMessaging="I can't help with that request.",
    blockedOutputsMessaging="I can only answer questions using the claim records.",
)
guardrail_id = guardrail["guardrailId"]
guardrail_version = bedrock.create_guardrail_version(
    guardrailIdentifier=guardrail_id
)["version"]
```

更高的阈值阻止更多响应。在理赔工作流中，拒答比生成无支撑的内容更安全。在 policyConfiguration 中传入护栏 ID 和版本：

```
response = bedrock_agent_runtime.agentic_retrieve_stream(
    messages=[
        {"role": "user", "content": {"text": "What is the status of claim CLM-100482?"}}
    ],
    retrievers=[
        {"configuration": {"knowledgeBase": {"knowledgeBaseId": kb_id}}}
    ],
    agenticRetrieveConfiguration={"foundationModelType": "MANAGED"},
    policyConfiguration={
        "bedrockGuardrailConfiguration": {
            "guardrailId": guardrail_id,
            "guardrailVersion": guardrail_version,
        }
    },
    generateResponse=True,
)
```

智能体检索支持 BLOCK 动作。一次失败的接地检查会阻止响应，而 trace 事件记录这次干预。

保留一个人在环，以审阅被引用的证据并做出最终的理赔决定。

## 清理

完成时删除资源以避免未来产生费用：

- 删除知识库。这也会移除托管向量存储：  `bedrock_agent.delete_knowledge_base(knowledgeBaseId=kb_id)`
- 删除数据源：  `bedrock_agent.delete_data_source(knowledgeBaseId=kb_id, dataSourceId=data_source_id)`
- 删除护栏，删除 S3 桶内容，并在不再需要时移除 IAM 角色。
