# 借助 Amazon Bedrock AgentCore Observability 构建可信的 AI agent

AI agent 正在改变各行各业的企业应用，从客户服务到复杂的决策工作流。随着组织扩大这些部署的规模，他们面临一个根本性问题：如何提高对 AI 应用的信任？挑战在于透明度。AI agent 可以代表用户做出决策、动态调用工具，并沿着推理路径行进，而这些都会造成问责缺口。洞察影响用户交互和结果的因素，有助于你构建透明、可靠的 agent。可观测性常常沦为事后考虑。这种做法在 AI agent 上行不通。可观测性必须从第一天起就成为基础，因为这些系统会学习、适应，并做出直接影响用户信任的决策。尽早实施可观测性，有助于把透明度、可靠性和卓越的用户体验打造为核心特性。

在 2025 年纽约市 AWS Summit 上，我们推出了 [Amazon Bedrock AgentCore Observability](https://aws.amazon.com/bedrock/agentcore/)，这是一套面向 AI agent 的全面监控方案，可跨不同的 agent 框架和基础模型（FM）工作。Amazon Bedrock AgentCore Observability 通过最大限度减少复杂的可观测性基础设施搭建，同时提供对 agent 运行的完整可见性，让开发者能够轻松地监控、分析和审计 AI agent 的交互。它提供了强大的能力，用于跟踪 agent 交互、分析性能指标，以及跨不同部署环境调试问题，使开发者从第一天起就能构建可信的 AI 系统。

在本文中，我们将带你了解两类 agent 的实现方案：一类托管在 [Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 上，另一类托管在其他服务上，例如 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2)（Amazon EC2）、[Amazon Elastic Kubernetes Service](https://aws.amazon.com/eks/)（Amazon EKS）、[AWS Lambda](https://aws.amazon.com/lambda)，或其他云提供商。我们还会分享在整个开发生命周期中融入可观测性的最佳实践。

下面的视频概述了各项能力，展示了控制面板界面，并重点介绍了这些特性如何融入你的 agent 开发工作流。要快速上手，请访问我们的 [GitHub 仓库](https://github.com/awslabs/agentcore-samples/tree/main/01-features/06-observe-evaluate-optimize-your-agent/01-observe)，查看代码讲解并了解更多信息。

## 方案概览

Amazon Bedrock AgentCore Observability 被设计为一款开发加速器，可从第一天起就带来直接价值，具备以下关键优势：

- 易于设置和使用
- 借助开箱即用的控制面板实现完整的端到端可追溯性与可视化
- 基于 [OpenTelemetry](https://opentelemetry.io/docs/what-is-opentelemetry/) 和生成式 AI [语义约定](https://opentelemetry.io/docs/concepts/semantic-conventions/) 的标准化能力
- 可用于所有 AI agent 框架和大语言模型（LLM）

这种统一的监控方式减少了对特定框架的可观测性方案的需求，简化了跨多样化 agent 架构的实现。无论你选择何种技术，这种灵活性都有助于让你的可观测性投入物有所值。Amazon Bedrock AgentCore Observability 提供两种监控配置方式，以满足不同的基础设施需求：

- **托管在 Amazon Bedrock AgentCore Runtime 上的 agent** – 这些 agent 直接在 Amazon Bedrock AgentCore 环境中部署和执行，只需极少配置即可提供自动插桩。这种方式提供了最快的部署路径，非常适合快速开发和测试。
- **非 Runtime 托管的 agent** – 这些 agent 为部署在你自有基础设施上的 agent 提供相同的监控能力，无论 agent 在哪里运行，都能获得一致的可观测性。

两种方案都能捕获传统监控会遗漏的关键指标，包括 token 使用量、工具选择模式、推理过程，以及跨 agent 工作流的端到端延迟。数据会自动路由到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)，并可通过 GenAI Observability 控制面板的 **Bedrock AgentCore** 标签页访问，让识别模式和排查问题变得轻而易举。团队通常会看到调试时间缩短、生产事故率降低，以及跨 AI agent 部署的资源利用率更加高效。

## 前置条件

要为你的 AI agent 启用 Amazon Bedrock AgentCore Observability，必须具备以下前置条件：

- 一个有效的 [AWS 账户](https://signin.aws.amazon.com/signup?request_type=builderId)，已对要使用的 FM 开通模型访问权限，并已配置凭证。
- 在 CloudWatch 上[启用事务搜索](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Enable-TransactionSearch.html)。首次使用的用户必须启用 CloudWatch 事务搜索，才能查看 Amazon Bedrock AgentCore 的 span 和 trace。
- [OpenTelemetry 库](https://.org/project/aws-opentelemetry-distro/)。要添加它，请在你的 `requirements.txt` 文件中加入 `aws-opentelemetry-distro`（ADOT）。

对于托管在 Amazon Bedrock AgentCore Runtime 上的 agent，可观测性会自动启用，无需额外配置。对于未托管在 Amazon Bedrock AgentCore Runtime 上的 agent，你必须在 CloudWatch 中为 agent 创建日志组和日志流，并据此配置以下环境变量：

- `AGENT_OBSERVABILITY_ENABLED=true` – 激活 ADOT 管道
- `OTEL_PYTHON_DISTRO=aws_distro` – 使用 AWS Distro for OpenTelemetry
- `OTEL_PYTHON_CONFIGURATOR=aws_configurator` – 为 ADOT SDK 设置 AWS 配置器
- `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf` – 配置导出协议
- `OTEL_EXPORTER_OTLP_LOGS_HEADERS=x-aws-log-group=`<YOUR-LOG-GROUP>、`x-aws-log-stream=`<YOUR-LOG-STREAM> 和 `x-aws-metric-namespace=`<YOUR-NAMESPACE> – 将日志导向 CloudWatch 日志组
- `OTEL_RESOURCE_ATTRIBUTES=service.name=<YOUR-AGENT-NAME>` – 在可观测性数据中标识你的 agent

你可以使用 .env 文件管理这些环境变量，使 AWS 凭证与代码分离。有关示例模板，请参阅以下 [env.example 文件](https://github.com/awslabs/agentcore-samples/tree/main/03-integrations/agents-hosted-outside-runtime)。

## 安装依赖

实现过程需要在你的 AWS 账户中启用事务搜索（一次性设置），并在你的 `requirements.txt` 文件中加入必要的依赖：

```
bedrock-agentcore   # if you are using AgentCore SDK to deploy on Runtime
aws-opentelemetry-distro # MUST be included to get traces, logs, and metrics
<your-agent-framework> # e.g., strands-agents[otel], crewai, langgraph
<your-agent-framework-auto-instrumentor>  # e.g., opentelemetry-instrumentation-langchain
```

安装好这些依赖并启用 CloudWatch 事务搜索后，你就可以为 AI agent 实施可观测性了。实施过程会随 agent 的托管位置而异，但两种方式都能通过 CloudWatch GenAI Observability 控制面板提供同样全面的监控能力。

## 为 Amazon Bedrock AgentCore Runtime 上的 agent 配置可观测性

Amazon Bedrock AgentCore Runtime 通过在你的环境中内置自动插桩，提供了通往全面可观测性的最快路径。你现有的 agent 代码无需任何改动——只需用 Amazon Bedrock AgentCore Runtime SDK 将其包装起来，即可获得完整的可观测性。Amazon Bedrock AgentCore Runtime 会自动捕获会话指标、性能数据、错误跟踪，以及包含所有工具调用的完整执行 trace。以下代码展示了只需增加四行 Amazon Bedrock AgentCore Runtime SDK 代码，一个普通 agent 就能具备生产级的自动可观测性：

```
# Example: Strands Agent with Automatic Observability
from strands import Agent, tool
from strands.models import BedrockModel
from bedrock_agentcore.runtime import BedrockAgentCoreApp

# Your existing agent code - no changes needed
model = BedrockModel(model_id="anthropic.claude-3-5-sonnet")
agent = Agent(
    model=model,
    tools=[your_tools],
    system_prompt="Your agent instructions"
)

# Add these four lines to enable full observability
app = BedrockAgentCoreApp()

@app.entrypoint
def agent_handler(payload):
    """Your existing handler - automatically instrumented"""
    user_input = payload.get("prompt")
    response = agent(user_input)
    return response.message['content'][0]['text']

if __name__ == "__main__":
    app.run()  # Launch with automatic observability
```

无需编写插桩代码、手动创建 span 或做进一步配置。Runtime 会自动传播 trace 上下文、关联会话，并捕获 agent 工作流中 LLM 调用、工具调用和决策点的详细遥测数据。

## 为 Amazon Bedrock AgentCore Runtime 之外的 agent 配置可观测性

对于运行在 Amazon EC2、Amazon EKS、Lambda 或其他平台上的 agent，Amazon Bedrock AgentCore Observability 提供完全相同的监控能力——与 Runtime 托管的 agent 一样的指标、trace、span 和控制面板可视化。唯一的区别在于初始设置：你需要配置环境变量，将遥测数据导向 CloudWatch，并使用 OpenTelemetry 插桩运行 agent。首先，配置环境变量以启用可观测性：

```
# .env configuration for external agents
AGENT_OBSERVABILITY_ENABLED=true
OTEL_PYTHON_DISTRO=aws_distro
OTEL_PYTHON_CONFIGURATOR=aws_configurator
OTEL_RESOURCE_ATTRIBUTES=service.name=my-agent,aws.log.group.names=/aws/bedrock-agentcore/runtimes/my-agent-id
OTEL_EXPORTER_OTLP_LOGS_HEADERS=x-aws-log-group=/aws/bedrock-agentcore/runtimes/my-agent-id,x-aws-log-stream=runtime-logs,x-aws-metric-namespace=bedrock-agentcore
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_TRACES_EXPORTER=otlp
```

然后使用 OpenTelemetry 插桩运行你现有的 agent 代码：

```
# agent.py - Your existing Strands agent
from strands import Agent, tool
from strands.models import BedrockModel

# Define your custom tools
@tool
def custom_tool(input_parameter: str):
    """Your tool description"""
    # Tool implementation
    return result

# Configure your agent with model and tools
model = BedrockModel(model_id="<your-selected-model-id>")
agent = Agent(
    model=model,
    tools=[<your-tools>],  # Add your tools here
    system_prompt="<your-system-prompt>",
    trace_attributes={  # These attributes enhance your observability data
        "use_case": "<your-use-case>",
        "environment": "development"
    }  
)

# Run with automatic instrumentation
# Command: opentelemetry-instrument python agent.py
```

OpenTelemetry 插桩会自动捕获与 Runtime 方式相同的遥测数据——框架操作、LLM 调用、工具调用和执行流——而无需额外改动代码。无论 agent 部署在哪里，都能获得完整的可观测性。

## 添加会话跟踪和自定义属性

虽然两种实现路径都开箱即用地提供全面可观测性，但你仍可以通过自定义属性增强遥测数据，实现更细粒度的分析。Amazon Bedrock AgentCore Runtime 通过 `runtimeSessionId` 参数自动处理会话跟踪，但对于 Runtime 和非 Runtime 的 agent，你都可以使用 OpenTelemetry baggage 添加自定义元数据。

要添加有助于过滤、分析和调试的自定义属性，请使用以下代码：

```
from opentelemetry import baggage, context

# Add custom metadata for analysis
ctx = baggage.set_baggage("user.type", "premium")
ctx = baggage.set_baggage("experiment.id", "travel-agent-v2")
ctx = baggage.set_baggage("conversation.topic", "business-travel")

# For non-runtime agents, you can also add session tracking
ctx = baggage.set_baggage("session.id", "user-session-123")

# Attach context to make it active for all subsequent operations
attach(ctx)

# Run your agent with enhanced observability
# Command: opentelemetry-instrument python your_agent.py
```

这些自定义属性会贯穿整条 trace，使你能够在 CloudWatch 中执行强大的查询，例如“显示所有延迟超过 2 秒的高级用户会话”或“比较不同实验版本之间的性能”。这些元数据对于离线评估、A/B 测试和性能优化非常有价值。

## 使用自定义请求头实现高级追踪

为了获得更深入的可观测性和跨服务关联，你可以通过自定义请求头增强 agent 调用。当 agent 与其他服务交互，或需要在不同组件之间保持 trace 连续性时，这尤其有用。请看以下代码：

```
import boto3

client = boto3.client("bedrock-agentcore")

response = client.invoke_agent_runtime(
    agentRuntimeArn="arn:aws:bedrock-agentcore:region:account:runtime/agent-id",
    runtimeSessionId="unique-session-id",
    payload='{"query": "Your request"}',
    headers={
        "X-Amzn-Trace-Id": "Root=1-5759e988-bd862e3fe1be46a994272793",
        "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
        "X-Amzn-Bedrock-AgentCore-Runtime-Session-Id": "session-123",
        "baggage": "userId=alice,environment=production"
    }
)
```

通过这种配置，你的可观测性数据会流入 CloudWatch，你可以通过 GenAI Observability 控制面板查看，从宏观指标到单条 trace 细节，全面洞察 agent 的行为。

## 最佳实践

从第一天起实施可观测性，需要深思熟虑地将其融入开发工作流，而不是把它当作一个独立的关注点。最成功的 AI agent 实现将可观测性作为核心开发实践，同时提升开发者的生产效率和运营可靠性。为 AI agent 实施可观测性时，请考虑以下关键实践，以在最小化复杂度的同时最大化价值：

- **从简单开始，再逐步扩展** – 在添加自定义 span 或属性之前，先使用基础的自动插桩。Amazon Bedrock AgentCore 提供的默认可观测性会自动捕获大多数关键指标，包括模型调用、token 使用量和工具执行。随着你发现需要更多可见性的特定业务指标或操作，再逐步添加自定义插桩。
- **按开发阶段配置** – 让可观测性配置与当前开发阶段相匹配。在早期开发阶段，设置较高的详细程度并捕获所有 trace，以最大化对 agent 行为的可见性。对于测试环境，降低日志详细程度并采用部分采样，在可见性与性能之间取得平衡。在生产环境中，以效率为先，采用最少的日志记录和聚焦关键路径的策略性采样。这种渐进式调整能在每个阶段提供恰当的详细程度，而不会带来不必要的开销。
- **使用一致的命名** – 从一开始就为服务、span 和属性建立命名约定。用前缀对相关属性分组，例如用 `agent.` 表示 agent 属性，用 `business.` 表示用例信息。这种一致性会形成可查询的结构，使你在实现不断扩展时仍能轻松分析可观测性数据，并确保监控模式在不同团队和项目之间保持连贯。
- **过滤敏感数据** – 从可观测性属性和载荷中过滤掉敏感数据，以帮助降低泄露此类数据的风险。要特别留意用户输入、个人身份信息，以及可能出现在 agent 交互中的敏感业务数据。
- **定期审查可观测性数据** – 将分析监控数据作为开发流程的常规环节，而不是只在出现问题时才去查看。定期审查有助于发现优化机会和可为 agent 设计提供参考的行为模式。

## 结论

从第一天起实施 Amazon Bedrock AgentCore Observability，会改变团队开发、调试和部署 AI agent 的方式。通过将全面监控融入整个开发生命周期，而不是把它当作生产环境的事后补充，组织能够实现更快的开发周期、更可靠的 agent 行为，以及更好的运营可见性。这种与框架无关的方式，有助于让可观测性投入在你为 agent 选择的任何技术上保持价值，在 Strands、CrewAI、LangGraph 或自定义实现之间提供一致的监控能力。
