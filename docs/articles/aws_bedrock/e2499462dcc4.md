# 用 Agent-EvalKit 系统化地评估 AI agent

构建 AI agent 的团队评估 agent 的方式，通常和他们评估其他软件一样：检查输出是否符合预期。但那些会自主选择工具、跨多个数据源编排操作的 agent，其行为无法靠输出层面的测试完整刻画。

一个 agent 可能给出结构良好、可执行的回答，同时却在幻觉——因为工具返回空结果，它就编造事实。它也可能得出正确结论，却跳过了可靠流程所要求的校验步骤。由于这些故障藏在最终回答的表面之下，要发现它们，评估必须追踪 agent 的完整执行路径：agent 调用了哪些工具、这些工具返回了什么数据、回答是否忠实反映了这些数据。

要补上这个缺口，需要大多数 agent 团队没有人力从零搭建的基础设施：带基准真值（ground truth）结果的测试用例、用于捕获工具调用与中间状态的可观测性埋点，以及在表层准确度之外评估忠实度和工具使用情况的指标。

Agent-EvalKit 是一个开源工具包（Apache 2.0），它通过与 AI 编码助手集成，把这套评估基础设施变得可用，支持的助手包括 [Claude Code](https://claude.com/product/claude-code)、[Kiro CLI](https://kiro.dev/cli/) 和 [Kilo Code](https://kilo.ai/)。它把整个工作流带进你的开发环境，而不是把评估当成部署之后另做的一件事。你用自然语言描述评估目标，工具包就会处理每个阶段：从读取 agent 源码、生成有针对性的测试用例，到运行评估并产出一份改进建议报告，这些建议会引用你代码库中的具体位置。接下来的章节会以一个用 [Strands Agents SDK](https://strandsagents.com/) 和 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 构建的旅行研究 agent 为例，逐一说明 Agent-EvalKit 的六个评估阶段如何工作。

## agent 评估需要什么

除了基础设施本身，选择衡量什么同样费神。agent 的质量横跨多个维度，没有单一指标能覆盖：回答是否以工具实际返回的内容为依据、agent 是否用正确的参数调用了正确的工具、最终输出对提问者是否连贯有用。一份回答可以读起来很顺畅，却在空工具结果之上悄悄幻觉；一个 agent 也可能通过一连串错误的工具调用得出看似合理的答案。因此每个维度都必须单独检查，而不能从相邻维度推断。

没有哪一种评估器风格能把这三者都处理好。基于代码的评估器给出快速、可复现的结果，但会惩罚合理的实现差异。以大语言模型（LLM）作为评判者的评估器（LLM-as-judge）能提供更细致的评估，代价是额外的推理开销和精心的 prompt 设计。多数有效的评估策略会把两种方法结合起来。把评估分数转化为具体的代码改动，正是很多工作最终卡住的地方，这也是为什么评估工作流必须落在具体的、代码级建议上，而不是一堆数字仪表盘。

## Agent-EvalKit 如何工作

Agent-EvalKit 通过你现有的 AI 编码助手来工作，而不是作为一个独立的评估平台运行。你的助手——无论是 Claude Code、Kiro CLI 还是 Kilo Code——凭借它阅读代码、推理 agent 行为的能力，在评估过程的每个阶段充当评估引擎。你通过 `/evalkit.plan`、`/evalkit.data` 这样的斜杠命令驱动这套工作流，并在命令后附加自然语言指引，告诉助手哪些质量维度对你的 agent 最重要。这种设计让评估留在你的开发环境内，于是帮你构建 agent 的同一个助手也帮你评估它。

流程从 agent 的源代码开始：助手读取工具定义、系统 prompt 和框架配置，据此构建一个详细模型，弄清你的 agent 做什么、可以调用哪些工具、行为可能在哪些地方出问题。工具包在后续阶段产出的每一份工件——从评估计划到最终报告——都建立在这份代码级理解之上。

在这个基础上，助手设计一份个性化的评估计划，其中的指标针对你的 agent 的能力与风险区域，然后推进后续阶段：生成测试用例、用兼容 OpenTelemetry 的追踪为 agent 埋点、逐个运行测试用例并收集结构化追踪，最后按你的标准评估结果。整个过程最终汇成一份报告，其中按优先级排列的建议会引用你代码中的具体位置，把评估发现直接连接到可执行的修复。举例来说，如果你指示系统重点关注由空工具结果触发的幻觉，这条指引会影响测试用例的生成、指标的选择，以及报告最终突出哪些模式。

下图展示了从测试用例到指标评估的这一流程。

![示意图：Agent-EvalKit 从生成的测试用例，经追踪、agent 执行与指标评估，直到最终报告的流程](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/18/ML-20590-1.png)

工具包把这些工作组织成六个阶段，每个阶段都会在 `eval/` 目录中产出工件，供给下一阶段使用。你通过 AI 助手以斜杠命令的方式调用每个阶段，命令之后的文字就是该阶段的自然语言指引。初始工件就位后，你可以换一份指引重新调用任何阶段，以调整重点或加深分析，而无需从头重建。

![Agent-EvalKit 六个阶段的示意图：Plan、Data、Trace、Run agent、Eval 和 Report，展示它们在 eval 目录中相互传递的工件](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/18/ML-20590-2.png)

这六个阶段覆盖完整的评估生命周期，从理解 agent 的能力一直到给出具体的代码改进建议。

- **Plan**（`/evalkit.plan`）读取你的 agent 代码以理解其工具和框架，然后产出一份评估计划，为每个指标配上具体的评估方法。你的指引决定计划优先关注哪些质量维度，而这些优先级会延续到后续阶段真正可运行的评估代码中。
- **Data**（`/evalkit.data`）在评估计划的基础上生成测试用例，每条用例都带有输入和预期结果，针对你的 agent 需要处理的具体行为与失败模式。如果你已经有来自生产日志或手工测试的测试数据，也可以让这一阶段改用你现有的数据集。
- **Trace**（`/evalkit.trace`）通过给 agent 加上兼容 OpenTelemetry 的追踪，让完整执行路径变得可见。对于受支持的框架（包括 Strands、LangGraph 和 CrewAI），它会识别框架并施加相应的埋点。当前支持矩阵见 Agent-EvalKit 仓库。
- **Run agent**（`/evalkit.run_agent`）针对每条测试用例运行你的 agent，为每次运行产出一个结构化追踪文件，记录工具调用、模型响应和中间状态的完整历史。
- **Eval**（`/evalkit.eval`）把计划中的指标实现为可执行的评估代码，对收集到的追踪运行它，并保存结构化结果。它支持 DeepEval 和 Strands Evals SDK 等评估库，会选择最适合你的 agent 和指标的做法。
- **Report**（`/evalkit.report`）分析跨测试用例的模式，生成按优先级排列的建议，并引用 agent 代码中的具体位置；每条建议都附带预期影响，便于你把改进投入放在收益最大的地方。

贯穿这些阶段，模糊的质量担忧会变成一套结构化的证据：测试用例、执行追踪、指标分数，以及都能回溯到代码具体位置的按优先级排列的建议。

## 演示研究：评估一个旅行研究 agent

在用 Strands Agents SDK 和 Amazon Bedrock 构建一个旅行研究 agent 的过程中，我们注意到该 agent 有时会在回答里给出精确得可疑的数字。这个 agent 借助网页搜索、航班信息、气候数据、货币换算和预算计算等工具帮用户规划行程，但我们无法确定这个精度问题的范围有多大，也无法确定是哪些查询触发了它。

Agent-EvalKit 分析了 agent 的代码，并在 Plan 阶段围绕三个指标设计了一套聚焦的评估：Faithfulness 衡量回答是否以工具实际返回的数据为依据；Tool Parameter Accuracy 检查 agent 是否用正确的输入调用工具；Response Quality 评估输出的连贯性和有用程度。Data 阶段随后生成了 100 个多轮测试会话，覆盖目的地调研、季节性时机、行程安排、对比类问题和预算计算，后续阶段运行每个会话并捕获详细的执行追踪。

![柱状图展示旅行研究 agent 的三项评估指标分数：Response Quality 83.9%、Tool Parameter Accuracy 64.5%、Faithfulness 32.3%](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/18/ML-20590-3.png)

结果暴露出质量与可靠性之间存在明显分化。Response Quality 得分为 83.9%，说明 agent 确实给出了清晰、可执行的旅行建议；Tool Parameter Accuracy 达到 64.5%，说明 agent 总体上选对了工具，但有时传入了不精确的参数。Faithfulness 只有 32.3%，暴露出 agent 在网页搜索工具返回空结果或不完整结果时，会编造汇率、气温和景点细节，并把这些虚构内容当作来自工具的结果呈现。

下图展示了这种幻觉模式在一次执行内部是什么样子：agent 收到空的工具响应，却把编造的数据当作来自工具的结果呈现。

![单次 agent 执行的追踪示意图：网页搜索工具返回空结果，而 agent 把编造的汇率和气温数据当作来自该工具的结果呈现](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/18/ML-20590-4.png)

报告把幻觉防护（hallucination guardrails）列为最高优先级的修复项，建议在系统 prompt 中指示：当工具返回空结果时要如实说明；并改进所有代码路径上的工具错误处理。在运行 Agent-EvalKit 之前，我们知道这个 agent 有时显得不可靠；之后我们知道根因是空的工具输出触发了幻觉，并且有了具体的代码改动来应对它。

## 上手演练

以下各节会带你走完 Agent-EvalKit 的前置条件、安装工具包，以及对你的 agent 跑一次端到端评估。

### 前置条件

运行 Agent-EvalKit 评估需要用于基础模型推理的云端访问权限，以及用于评估工作流的本地工具。

- 一个有效的 AWS 账号，并在 Amazon Bedrock 控制台中启用了基础模型。Agent-EvalKit 使用 LLM-as-judge 指标，评分需要基础模型，因此在继续之前请先在 Model access 页面确认你的模型可用。
- Python 3.11 或更高版本，以及 Git。
- uv 包管理器。在 macOS 和 Linux 上，用 `curl -LsSf https://astral.sh/uv/install.sh | sh` 安装。
- 在你的机器上安装并配置好一个受支持的 AI 编码助手（Claude Code、Kiro CLI 或 Kilo Code）。本文示例使用 Claude Code，但这套工作流对三者都适用。安装说明请参考各助手自己的文档。

### 开始使用

用 uv 安装工具包，它会直接从 Agent-EvalKit 的 GitHub 仓库拉取。

```
uv tool install evalkit --from git+https://github.com/awslabs/Agent-EvalKit.git
```

初始化一个评估项目，并把你的 agent 代码复制到项目目录中。你的 agent 目录应当包含源代码、工具定义，以及运行该 agent 所需的任何配置。有关受支持的 agent 框架和项目结构的细节，请参阅 Agent-EvalKit 仓库。

```
evalkit init my-agent-evaluation
cd my-agent-evaluation
cp -r /path/to/your/agent .
```

在评估项目内启动你的 AI 助手。对于 Claude Code，运行 `claude` 命令。

```
claude
```

如果希望第一次评估有引导，quick 命令会带你逐步走完六个阶段，并解释每个阶段做什么、接下来该运行哪个命令。

```
/evalkit.quick <your natural language guidance>
/evalkit.quick Evaluate my agent at ./my_agent for response quality and tool accuracy
```

如果需要更多控制，可以逐个运行各阶段。

```
/evalkit.plan <your natural language guidance>
/evalkit.plan Evaluate my agent at ./my_agent for response quality and tool accuracy
/evalkit.data
/evalkit.trace
/evalkit.run_agent
/evalkit.eval
/evalkit.report
```

下面的视频完整走过这套工作流，其中 Agent-EvalKit 对一个配备了网页搜索和规划工具的旅行研究 agent，跨全部六个阶段——从代码分析到最终评估报告——进行评估。

## 最佳实践

评估在每次有意义的改动上运行、而不是只当成发布前的检查点时，收益最大。下面的做法反映了我们在把 Agent-EvalKit 融入持续开发周期时觉得最有用的经验。

- **从小处开始**，聚焦两三个针对 agent 最关键质量维度的指标，在解决初步发现并对基线建立信心之后，再在后续评估中扩大范围。
- **用领域知识做指引**，在每个阶段描述你观察到的具体输入、边界情况和失败模式。你的自然语言指令越有针对性，生成的测试用例、指标和建议就越相关。
- **在执行前先审阅测试用例**，因为 Data 阶段是根据评估计划合成用例的，而你对真实用户行为的理解无法替代。请补充反映你在生产中观察到的模式的场景。
- **每次重大改动之后都做评估**，以便尽早发现回归，并衡量每项改进的影响。对比不同 agent 版本之间的报告，能让进展可见，也让开发聚焦在价值最高的修复上。
- **增量地处理建议**，从报告中影响最大的条目入手。实现修复、重新评估以确认改进，然后再处理下一条发现。
- **在以往评估的基础上继续**，通过重新调用单个阶段来探索新的质量维度，同时复用已有的测试用例和埋点。一次聚焦忠实度的初始评估之后，可以紧接着对工具准确度做一轮更深入的分析，而无需重新生成数据或给 agent 重新埋点。
- **在生产中持续监控 agent**，用 Amazon Bedrock AgentCore Observability 捕获真实流量的追踪，再用 AgentCore Evaluation 对这些追踪运行质量指标。生产监控能暴露部署前评估无法预料的回归和新失败模式。
- **让评估器与人类专家保持一致**，定期把 LLM-as-judge 的评分与你的领域专家或人工标注者的判断做比较。当两者出现分歧时就更新评估器 prompt，好让你的自动指标持续反映用户真正在意的质量维度。

## 清理

如果你为跟随本文而创建了评估项目，完成后请删除该项目目录。如果你的评估通过 Amazon Bedrock 使用了基础模型，请在 AWS Management Console 的 Amazon Bedrock 定价页面上查看用量，以了解相关费用。

## 结论

Agent-EvalKit 让 AI agent 评估有了系统化的形态：它把评估设计、指标计算到报告的每一步，都交给那个你已经在用来写代码的 AI 助手。旅行研究 agent 的案例研究展示了这在实践中是什么样子：把一个发散的质量担忧，变成在具体某一行的具体修复，并附带预期影响。

随着 agent 承担的任务风险更高、影响范围更广，超越输出检查的评估已成为上生产的前提。Agent-EvalKit 的设计目标，就是让这种评估成为你写代码、审查 agent 代码所用的同一套开发工作流的一部分。

访问 Agent-EvalKit 的 GitHub 仓库可获取完整文档和示例评估，也可以通过 GitHub discussions 联系团队提出问题、反馈或贡献。想进一步了解这套方案，可参阅 [An Empirical Study of Automating Agent Evaluation](https://arxiv.org/pdf/2605.11378)。
