# 放心支付：Solv Labs 如何在 Amazon Bedrock AgentCore payments 上构建可验证、可审计的 agent 支付

*本文由 Solv Labs 的 Patrick Duffy 与 ICME Labs 的 Houman Shadab 共同撰写*

Solv Labs 使用 Amazon Bedrock AgentCore payments（Amazon Bedrock AgentCore 的一项能力）构建了一套 AI agent 支付 workflow，由两层治理：ORACLE（Solv 的策略引擎）与用于合规校验的 ICME PreFlight。AgentCore payments 提供支付处理基础设施。ORACLE 在每笔交易之前强制执行授权策略。ICME 的验证层扩展了 AWS Automated Reasoning Checks，使其具备隐私保护、可移植、可独立验证的特性，且每一个决策都可被检查。

因此，每一笔 agent 支付都要经过三个核心治理组件：用于预授权决策的 ORACLE、运行在 AWS Nitro Enclave 中的完整性服务，以及用于逐笔交易定价的风险引擎。每笔交易都能在四秒内完成，覆盖预授权、治理以及通过 Coinbase 进行的链上结算。每笔交易都会生成完整的审计轨迹，这完全处于 agent 工作负载的延迟预算之内。

当一个自主 agent 第一次代表企业转移真实资金时，问题就不再是“它跑通了吗？”，而是“我们能证明刚才发生了什么吗？”。仅仅在一个季度之内，四块让这个问题变得可回答的基础设施同时到位：Amazon Bedrock AgentCore payments、AWS Automated Reasoning Checks、用作逐笔交易见证者的 AWS Nitro Enclaves，以及面向 agent 向服务付费的 x402 支付标准。

Amazon 于 2026 年 5 月推出 Amazon Bedrock AgentCore payments，它与 Coinbase 和 Stripe 合作构建。它让 AI agent 能够即时获取并为其使用的内容付费，包括网页内容、API、MCP server 和其他 agent。支出由开发者已经在使用的、用来运营其 agent 的同一套控制来治理。

在本文中，Solv Labs 与策略验证伙伴 ICME 一起详解我们如何在 AgentCore payments 上构建一套 agent 支付 workflow：每笔交易都在执行时受到治理、在 AWS Nitro Enclave 内被见证、单独进行风险定价，并且完全可审计。我们还会说明这种模式为在受监管环境中运行 agent 的企业解锁了什么。

## 企业面临的挑战

当一个自主系统转移资金时，运营方必须向审计人员、交易对手和法律部门证明：每笔支付都经过了授权、都按其承担的风险定了价，并且以经得起审视的方式被记录下来。一个配置错误或被操纵的 agent 不只是返回一个糟糕的答案，它会转移资金。而困难之处并不在于执行支付，而在于事后证明这笔支付当初是被许可的。

企业团队始终在同一个缺口上挣扎：当一笔 agent 交易完成时，没有任何持久记录把这一个具体动作与授权它的策略、它满足的约束或它承担的风险绑定起来。模型卡、SOC 2 报告和事后审查描述的是系统周围的*组织*，它们并不描述单个决策的*执行*。缺少这种交易级别的绑定，运营方就没有干净的办法来化解争议、满足审计人员，或者把常规的 agent 动作与被入侵的动作区分开来。

Solv Labs 需要让每一个 agent 动作都可以被验证、被风险定价，并且能按需审计，同时又不拖慢 agent，也不在他们已经运行的系统之外硬加一套基础设施。

## 愿景

这个愿景很直接：在执行时治理每一笔 agent 支付，并生成一份记录，让各方（审计人员、交易对手、监管机构）都能独立验证，而不必依赖运营方的口头说法。

这只在最近才变得可行：AgentCore payments 作为支付编排层，Automated Reasoning Checks（ARc）用于形式化策略评估，Nitro Enclaves 用于硬件见证，而 x402 在 agent 支付领域获得了广泛采用。它们共同使“受治理的 agent 支付”成为一个实现选择，而不是一个研究项目。

## 架构

这套 workflow 由一组专门化的组件构成：运行在 Solv 运营环境中的 AgentCore payments、带有 Nitro Enclave 见证者的 ORACLE 引擎，以及作为外部服务由 ICME 提供的策略检查。组件之间只通过已签名、以哈希绑定的工件跨越信任边界，因此无论服务如何部署，证据流都成立。该 workflow 附加到基于 Amazon Bedrock AgentCore 构建的 agent 上，并兼容运行在 AgentCore runtime 或自定义 AgentCore 实现上的 agent。

图 1：系统架构。每一笔 agent 支付在结算之前都要经过预授权、约束校验、完整性见证和风险定价，全部原生运行于 AgentCore

每一笔支付都要经过五个专门化的组件，每个组件解决治理问题中一个不同的部分。

- **ORACLE——预授权。** ORACLE 根据适用的策略评估拟执行的动作，并在资金流动之前返回 ALLOW 或 REVIEW 判定，因此策略失败不会产生一笔已经结算、还要由运营方撤销的交易。
- **PreFlight——可独立验证的策略检查。** ICME 的 PreFlight 提供 ORACLE 决策所依据的策略检查。它会为这项检查生成一份小巧、具备隐私保护的证明，第三方无需访问策略或交易参数即可验证。
- **AWS Nitro Enclave——完整性见证。** 运行在 Nitro Enclave 中的完整性服务在硬件隔离环境内对执行记录签名。由 Nitro Security Module 生成的见证文档把签名密钥绑定到具体的 enclave 镜像度量值（PCR0，同时也包含 PCR1 与 PCR2）。因此，验证者不只能确认记录是在某个 enclave 内签名的，还能确认它是在 Solv Labs 已发布的那个具体 enclave 镜像内签名的。于是每个动作都以密码学方式被见证并绑定到产生它的 enclave，记录无法在事后被悄悄改写。
- **风险引擎——逐笔交易定价。** 风险引擎为每笔交易附加一个风险乘数，它由评估出的违规信号确定性计算得出，因此治理记录携带的是一个风险价格，而不是一刀切的通过。该乘数为下游的复核优先级提供依据，并在适用时用于为转移给第三方的风险定价。
- **支付处理与结算。** AgentCore payments 在处理每笔支付的同时强制执行每会话支出限额，使交易保持在最终用户已授权的预算之内。随后结算通过 Coinbase 完成链上路由。

这些组件按固定顺序运行：ORACLE 的判定、其可独立验证的证明、硬件见证以及逐笔交易的风险价格，都在结算发起之前生成。这道闸门是绝对的：没有判定，就没有结算。

图 2：交易时序。步骤 1–3 在结算发起之前生成治理记录，闸门强制执行“没有判定，就没有结算”。端到端延迟低于每笔交易四秒，治理开销低于一秒

## 治理层见证了什么

每一笔受治理的支付都会生成一份已签名的证据记录，绑定五样东西：被评估的策略、策略检查的结果及其可独立验证的证明、经硬件见证的执行记录、逐笔交易的风险价格，以及来自 AgentCore payments 的结算工件。

它并不见证 agent 的底层决策是否明智、交易对手是否有偿付能力，或者策略本身是否正确。这些仍属于运营方的责任，与其他支付一样。它*确实*以各方都能验证的方式见证了：这笔特定的支付是在这些特定约束下、以这个特定风险价格、依据这项特定策略被评估的，而且正是该评估的结果授权了结算。

图 3：逐笔交易的证据记录，包含执行与策略哈希、约束结果、零知识证明引用、硬件见证摘要、风险乘数以及链上锚点。哈希和标识符仅为示意性占位符。完整记录会被规范化、在 Nitro Enclave 内以 Ed25519 签名，并锚定到链上

## AgentCore payments 如何弥合治理缺口

这项服务的三个特性让这套 workflow 在运维上保持干净：

- **原生属于 agent 系统。** 治理 workflow 与 agent 运行在同一个 AgentCore 环境中，因此继承了 agent 的身份、网关和可观测性界面。运营方不必运行两个并行的控制平面——而在实践中，大多数治理缺口恰恰出现在这种配置里。
- **基础设施级别的支出限额。** AgentCore payments 独立于 agent 或策略引擎做出的任何决定来强制执行每会话支出限额。纵深防御是内建的，而不是拼装出来的。
- **单一的可观测性界面。** 每一个决策、见证、风险价格和结算，都与其他 agent 行为一起，通过标准的 AgentCore Observability（Amazon Bedrock AgentCore 的一项能力）在 Amazon CloudWatch 的日志、指标和追踪中可见。

## 成果

这套 workflow 在 agent 的一笔支付交易结算之前，生成一份逐笔交易、经硬件见证、可独立验证的治理记录。在 Amazon Bedrock AgentCore payments 上采用这一模式的企业，会以机器速度、按每一笔支付交易获得以下收益：

- **交易层面的可验证执行：** 每个 agent 动作都以密码学方式签名，并可对照 Base 网络上的公开锚点独立验证。受治理的支付在 ALLOW 和 REVIEW 两条决策路径上都会被处理，两者携带同样的证据保证。DENY 路径已在 ORACLE 引擎中完整实现并通过单元测试，在违反已配置的约束时会生成一份已签名的拒绝记录。
- **风险定价：** 每笔交易都携带一个确定性计算出的风险乘数，因此治理记录为它承担的风险定了价，而不是把每笔支付都当作相同的东西。风险乘数反映了引擎的工作点，随着观察到的执行不断累积，结果校准也会逐步到位。
- **独立可审计性：** 每个治理决策都锚定在公开区块链上，设计上可由第三方使用 Solv Labs 与 ICME 提供的参考验证工具进行验证，而不暴露策略细节、交易参数或私钥。
- **机器速度的治理：** 交易在四秒内完成，覆盖预授权、治理、支付处理以及通过 Coinbase 进行的链上结算。治理调用的延迟保持在整笔交易的延迟预算之内。
- **单一、可观测的界面：** 每个决策、见证和风险价格，都通过运营方用于其余 agent 行为的同一套 AgentCore Observability、在 Amazon CloudWatch 的日志、指标和追踪中可见。记录的结构是为其使用者设计的：风险与合规部门、内部审计，以及外部审计人员和交易对手，每一方都能验证。

图 4：逐笔交易的证据栈。全部四类工件都在结算触发之前生成并一起记录，审计人员、交易对手和监管机构可以独立验证每一个要素，而无需访问运营方的策略细节、交易参数或私钥

## 这为企业解锁了什么

- **每笔交易一条干净的审计轨迹**，在执行的那一刻产生，而不是事后重建：授权了什么、依据哪项策略、对照哪些约束、以什么风险价格、由哪个 enclave 签名、锚定在哪里。
- **经得起争议的证据。** 当交易对手、审计人员或监管机构询问某笔支付为何被许可时，答案是一份可验证的工件，而不是一句组织层面的断言。这在受监管环境中最为重要——在那里，证据留存义务附着于每一笔交易。
- **agent 速度的治理。** 亚秒级的治理开销意味着企业既能获得控制，也能获得 agent 工作负载所需的吞吐。
- **复核工作量随异常而增长，而非随交易量增长。** 因为每笔交易都自带证据，并在结算前通过一道策略闸门，复核工作从“每隔 N 笔抽样一次”转变为“调查证据本身标记出的异常”。监督工作量随异常率增长，而非随交易率增长。
- **符合你已有预算项的控制成本。** 运行在 AgentCore 的原生界面上，无需为并行的控制平面采购许可、做集成或配备人员。多治理一笔支付的边际成本主要由 AgentCore 调用本身构成，证明与锚定则是在企业已经支付的那条预算项之上叠加的边际成本，而不是一个新的预算条目。
- **面向未来工作负载的基础。** 同一套逐笔交易的证据模型，可以扩展到 agent 工作负载在生产环境中产生的支付动作的规模与多样性。

## 结论

Solv Labs 将 Amazon Bedrock AgentCore payments 与 ORACLE、PreFlight 和 AWS Nitro Enclave 见证者结合使用，构建了一套受治理的 agent 支付 workflow：每笔交易都依据策略被评估、在硬件中被见证、按风险定价，并锚定到公开区块链，而这一切都发生在结算触发之前。对企业而言，这意味着复核工作量随异常而非交易量增长、控制成本落在已有的预算项之内，以及一份风险、合规和审计部门都能各自验证的审计轨迹，且无需访问运营方的策略细节、交易参数或私钥。这就是在受监管环境中部署 agent 支付、又不必用速度换控制所需要的条件。
