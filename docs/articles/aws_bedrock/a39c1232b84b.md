# Eon 如何在 Amazon Bedrock AgentCore 上使用 MCP 网关构建多云调查

*这是与 Eon 的 Roei Zavida 共同撰写的客座帖子。*

构建人工智能产品的独立软件供应商 (ISV) 需要将代理和人员连接到数十个跨云的操作工具，每个工具都有不同的身份验证模型、网络边界和访问策略。当这些工具同时跨越 AWS、GCP 和 Azure 时，集成面就会成倍增加。

本文介绍了 Eon 如何使用 Amazon Bedrock AgentCore（一个使用任何框架或模型大规模构建、连接和优化代理的平台）。 Eon 使用它用单个经过身份验证的网关替换每个工具的凭据和本地模型上下文协议 (MCP) 进程。结果使开发人员和自主代理能够跨三个云统一访问调查工具。新工程师现在只需大约两分钟即可使用所有调查工具，而不是以前配置凭据和本地 MCP 服务器需要两天的时间。

## 关于亿昂

Eon 为人工智能时代提供自主数据基础。该平台跨 AWS、Azure 和 GCP 发现云资源并对其进行分类。它提供持续的重复数据删除备份，根据 Eon 的内部测量，可将存储成本降低高达 50%。它还可以检测勒索软件和流氓代理的损坏，并为人工智能代理提供实时的接地上下文。所有这些都通过单个只读 AWS Identity and Access Management (IAM) 角色运行，以 Apache Parquet 和 Apache Iceberg 格式存储数据。 Eon 由前 AWS 工程师创立，在 AWS 上运行其软件即服务 (SaaS) 基础设施。

## 挑战

Eon 的内部工程团队调查多个云和数十个操作系统的生产事件。崩溃的 Kubernetes Pod 需要在同一会话中检查容器日志、Grafana 指标、部署的 GitHub 拉取请求 (PR) 以及云提供商的运行状况。

Eon 需要满足几个关键要求：

- **凭证整合** — 每个新工具都添加了另一个集成来配置、保护和轮换，随着工具集的增长，保持一致变得越来越困难。
- **消除本地 MCP 流程** - 每个开发人员在本地运行多个 MCP 服务器，这很难标准化并保持最新。
- **身份分离** - 工程师使用基于角色的权限访问每个系统，但没有一个地方可以决定每个人或代理可以调用​​哪些工具。
- **跨账户访问，无需网络开销** — 跨多个 AWS 账户托管 MCP 服务器需要虚拟私有云 (VPC) 对等互连或每个账户的 AWS PrivateLink，从而增加了运营成本和设置时间。
- **开发人员入职** — 新工程师在调查他们的第一个事件之前花了大约 2 天的时间配置凭据和本地 MCP 服务器。
- **代理访问** — Eon 的自主站点可靠性工程 (SRE) 代理（在 Amazon Bedrock 上运行 Claude）需要与人类相同的工具访问权限，但具有不同的权限。

不断增长的工程人员数量加上快速扩展的 AI 工具和 MCP，使得维护凭证和本地 MCP 服务器的成本越来越高。这推动 Eon 走向集中式解决方案。

## 考虑的方法

在构建 AgentCore 之前，Eon 评估了替代方案：

### 选项 1：具有自定义身份验证的集中代理

每个线束都有自己的代理配置和所有目标。单个反向代理聚合了所有工具，并具有自定义身份验证层。这处理了凭证整合，但仅支持远程 MCP，并且需要从头开始构建和维护工具协议转换、会话管理和授权逻辑。实施和维护负担很大。

### 选项 2：Amazon Bedrock AgentCore 网关

[Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 是 Amazon Bedrock AgentCore 的一项功能，是一个托管网关，具有内置身份联合、基于 Cedar 的授权策略和运行时托管，可将本地 MCP 服务器转换为远程 HTTP 终端节点。这无需定制基础设施即可满足所有要求。

Eon 选择选项 2，因为它提供身份分离、跨账户连接和策略实施作为托管功能，而不是他们需要构建和维护的代码。这是摆在桌面上的仅有的两个选择。

## 解决方案概述

Eon 部署了完整的 Amazon Bedrock AgentCore 堆栈：AgentCore Gateway、Amazon Bedrock AgentCore 中的策略、AgentCore 运行时和 AgentCore Identity，以及 Amazon Bedrock AgentCore 的所有功能。下图显示了客户端请求如何通过身份验证层流向单个网关。网关将授权工具调用路由到跨多个 AWS 账户的 AgentCore 运行时上托管的目标。

图 1：Eon 在 Amazon Bedrock AgentCore 上的集中式网关架构

该架构有五层：

### 客户

使用 Claude Code、Cursor 或 OpenAI Codex 的开发人员连接到单个 MCP URL。在 Amazon Bedrock 上运行 Claude 的自治 SRE 代理使用不同的身份连接到同一网关。

### 身份平面

企业单点登录 (SSO) 通过 Amazon Cognito 进行联合，Amazon Cognito 会生成 JSON Web 令牌 (JWT) 并将其传递给网关。 Amazon API Gateway 位于前面，作为人类的 OAuth 入口点，代理 MCP 会话。代理直接针对网关使用 Cognito“client_credentials”授权进行身份验证。

### 一个网关，最低权限访问

单个 AgentCore MCP 网关充当公司范围内的前门。 ENFORCE 模式下的 Cedar 策略控制哪些主体可以调用哪些工具。读取操作适用于选定的组，而不是每个经过身份验证的用户。写入操作仅限于影响较小的协作操作，例如评论 PR 或票证，并且生产工具是只读的。

### Amazon Bedrock AgentCore 中的策略

Cedar 策略将每个主体映射到允许的工具。写入操作仅限于影响较小的协作操作，例如评论 PR 或票证，并且生产工具是只读的。网关会在转发到目标之前针对 Cedar 评估每个“工具/调用”请求。

### 目标

数十台目标 MCP 服务器在一个网关上公开数百种工具，由分布在多个 AWS 账户的 AgentCore 运行时提供服务。每个运行时将本地基于 stdio 的 MCP 服务器转换为可通过网关访问的 Streamable HTTP 端点。

开发人员打开其集成开发环境 (IDE)，配置一个 MCP URL，通过公司 SSO 进行身份验证，然后网关将数百个工具聚合到单个“工具/列表”响应中。没有本地设置，也没有每个工具的令牌。

## 身份和访问分离

核心安全决策是通过网关级别的 Cedar 策略强制执行读写边界。

**单一网关，策略强制分离：**

网关接受 JWT 令牌（人员通过公司 SSO 和 Cognito）和“client_credentials”令牌（代理）。 Cedar 政策决定了每个校长可以做什么。批准组中的人员可以获得读取权限。写入操作需要仅授予特定代理身份的显式 Cedar 许可。

**Cedar 增强了每个工具的粒度：**
```
// Agent "sre-bot" can add comments on GitHub PRs
permit(
    principal == Agent::"sre-bot",
    action == Action::"tools/call",
    resource == Tool::"github_add_pr_comment"
);

// No human principal can invoke mutation tools
forbid(
    principal in Group::"humans",
    action == Action::"tools/call",
    resource in ResourceGroup::"write-tools"
);
```
Cedar 策略通过 GitHub PR 以代码形式进行管理，并附有审核评论，为团队提供版本控制和每次权限更改的审计跟踪。

在网关内，Cedar 策略范围按 SSO 组访问工具，并且组映射到工作角色。默认情况下，工程师可以访问开发和测试环境。生产访问遵循 Eon 的安全性和合规性控制：它是只读的，通过审批流程及时授予并经过审核。新团队成员的组范围以相同的方式确定，按角色而不是按他们碰巧拥有的服务。由于每个代理操作都会在 ENFORCE 模式下针对 Cedar 进行检查，并且范围仅限于最低权限工具集，因此自主代理会在安全、有限的范围内运行。它只能调用其身份明确允许调用的特定工具。

> “之前，我们的内部代理无法访问开发人员使用的相同调查工具。之后，它使用具有自己身份的相同网关和更严格的工具集。”

— Roei Zavida，Eon 高级 DevOps 工程师

## 跨账户连接

Eon 跨多个 AWS 账户运行运行时，按环境或服务边界组织。 AgentCore Gateway 通过 IAM 跨账户角色承担到达每个运行时。账户 B 中的运行时通过标准 IAM 信任策略信任账户 A 中的 AgentCore 网关执行角色。

这消除了什么：

- 跨多个 AWS 账户的 VPC 对等配置和路由表管理。
- 每个帐户的 PrivateLink 端点成本。
- 帐户之间的安全组协调。
- 每个新账户的设置天数（由一项 IAM 信任策略取代，可在几分钟内完成部署）。

**目标附着模式：**

根据每个工具的身份验证和托管模型，Eon 使用两种主要附件模式。下表总结了何时使用每种模式并给出了示例。

| **图案** | **何时使用** | **示例** |
| --- | --- | --- |
|运行时 + IAM |工具需要通过 IAM 凭证进行云跳跃 | Grafana 查询、Kubernetes API 调用 |
|运行时包装远程 MCP |工具表面需要过滤或凭证翻译 |线性|

大多数目标使用运行时 + IAM。 Eon 仅包装远程 MCP，以缩小网关无法提供的凭证中的目录或插槽。

## 调查会话流程

以下流程跟踪开发人员调查生产事件：

- **身份验证。** 开发人员打开 Claude Code（或 Cursor/Codex）并连接到网关 MCP URL。 IDE 通过公司 SSO 启动 OAuth。 Cognito 发布一个包含开发人员身份和组成员身份的 JWT。
- **工具发现。** 网关聚合来自数十个连接目标的“工具/列表”，并向 IDE 返回数百个工具的统一清单。开发人员可以在一个列表中看到所有可用的调查工具。
- **工具调用。** 开发人员询问：“显示过去一小时支付服务的错误率峰值。” IDE 的代理选择 Grafana 查询工具并发送“tools/call”请求。
- **策略评估。** 网关根据 Cedar 评估请求。开发人员的组成员资格授予对 Grafana 工具的访问权限。请求通过。
- **运行时执行。** 网关将请求转发到托管 Grafana MCP 服务器的运行时（在单独的 AWS 账户中运行）。运行时使用 AgentCore Identity Vault 中存储的服务凭证向 Grafana 进行身份验证，执行查询并返回结果。
- **跨工具关联。** 代理通过检查 Kubernetes 部署状态和相关的 GitHub PR 进行跟进，每个路由到不同的运行时。开发人员无需切换工具或重新验证即可看到相关结果。

## 大规模的经验教训

向 100 多名开发人员和大约 10,000 个会话进行部署时，出现了生产挑战：

### 管理 Cedar 保单规模

网关预索引的每个工具模式都会影响 Cedar 策略的大小。由于数十个目标暴露了广泛的工具清单，Eon 的政策朝着规模配额的方向发展。修复：针对高工具数量目标的动态列表模式。在动态模式下，网关在请求时将“工具/列表”调用转发到 MCP 服务器，而不是预索引架构，从而向策略添加零字节。

代价是语义工具搜索对于 DYNAMIC 目标不可用。 Eon 运行混合配置：默认模式适用于需要每用户 OAuth 的目标（工具数量较少，需要预索引模式用于同意流程），动态模式适用于大型目录目标。

### 标准 MCP 客户端的 OAuth 会话绑定

Claude Code、Cursor 和 Codex 需要 OAuth“state”参数来实现跨站点请求伪造 (CSRF) 保护。 AgentCore 使用会话 URI 绑定。 Eon 构建了一个 Amazon API Gateway shim，可以在两种协议之间进行转换，以便标准 MCP 客户端无需修改即可完成 OAuth 流程。

### 过滤工具表面

一些 MCP 服务器公开了数百种工具。个人开发者只需要他们的服务的一个子集。 Eon 构建了一个运行时包装器，可在运行时层过滤工具清单，减少“工具/列表”响应中的噪音并防止意外调用不相关的操作。这种方法还将这些目标保持在默认模式，保留动态模式牺牲的语义搜索和嵌入功能。

单网关架构已在 Eon 内部工程团队的生产环境中运行了几个月。最明显的结果是开发人员入职。设置对完整工具集的访问权限从配置凭据和本地 MCP 服务器的大约两天减少到大约两分钟。新工程师连接一个网关 URL，通过公司 SSO 进行身份验证，并立即看到其角色允许使用的工具。

内部代理占据了节省的大部分时间，因为它可以通过网关访问更多上下文，从而提高调查准确性。工程师节省了之前花在AI工具设置上的时间，因为他们只需要连接到网关URL。

Eon 正在探索相同的模式如何在自己的产品中支持人工智能功能。

## 结论

本文介绍了 Eon 如何使用单个 Amazon Bedrock AgentCore MCP 网关替换每个工具凭证和本地 MCP 进程。结果是基于 Cedar 的身份分离、无需 VPC 对等的跨账户连接，以及跨三个云的 100 多名开发人员和自治代理的统一工具访问。单网关架构、Cedar 最低权限执行以及混合默认和动态策略模式是 ISV 将代理和开发人员连接到跨多个云的工具的可重用模式。
