# Eon 如何借助 Amazon Bedrock AgentCore 上的 MCP Gateway 构建多云调查能力

*本文是与 Eon 的 Roei Zavida 合写的客座文章。*

构建 AI 驱动产品的独立软件供应商（ISV）需要把智能体和人员连接到数十个跨云运营工具，而每个工具都有不同的身份认证模型、网络边界和访问策略。当这些工具同时横跨 AWS、GCP 和 Azure 时，集成面会成倍扩大。

本文介绍 Eon 如何使用 Amazon Bedrock AgentCore——一个可以配合任意框架或模型、大规模构建、连接和优化智能体的平台。Eon 用它把每工具一份的凭证和本地 Model Context Protocol（MCP）进程替换为一个经过身份认证的单一网关。结果是，开发者和自主智能体能够统一访问横跨三个云的调查工具。新工程师现在大约两分钟就能接入全部调查工具，而此前配置凭证和本地 MCP 服务器需要两天。

## 关于 Eon

Eon 为 AI 时代提供 Autonomous Data Foundation。该平台发现并分类横跨 AWS、Azure 和 GCP 的云资源。它提供持续的、去重的备份，按 Eon 的内部测量可将存储成本降低最多 50%。它还能检测勒索软件和失控智能体造成的损害，并为 AI 智能体提供实时、有依据的上下文。所有这些都运行在单个只读的 AWS Identity and Access Management（IAM）角色下，数据以 Apache Parquet 和 Apache Iceberg 格式存储。Eon 由前 AWS 工程师创立，其软件即服务（SaaS）基础设施运行在 AWS 上。

## 挑战

Eon 的内部工程团队要在多个云和数十个运营系统中调查生产事故。一个崩溃的 Kubernetes pod，需要在同一次会话中检查容器日志、Grafana 指标、该部署的 GitHub pull request（PR）以及云服务商的健康状态。

Eon 需要解决几个关键需求：

- **凭证整合** —— 每新增一个工具就多一个需要配置、保护和轮换的集成；随着工具集增长，保持一致变得越来越难。
- **消除本地 MCP 进程** —— 每位开发者都在本地运行多个 MCP 服务器，难以标准化并保持最新。
- **身份隔离** —— 工程师基于角色的权限访问各个系统，但没有一个统一的地方来决定每个人或每个智能体可以调用哪些工具。
- **无需网络开销的跨账户访问** —— 在多个 AWS 账户中托管 MCP 服务器，需要为每个账户配置虚拟私有云（VPC）对等连接或 AWS PrivateLink，使运营成本和搭建时间成倍增加。
- **开发者上手** —— 新工程师在调查第一个事故之前，要花大约 2 天配置凭证和本地 MCP 服务器。
- **智能体访问** —— Eon 的自主站点可靠性工程（SRE）智能体（在 Amazon Bedrock 上运行 Claude）需要与人类相同的工具访问权限，但权限要不同。

工程人员规模不断增长，加上快速扩张的 AI 工具和 MCP 集合，使得维护凭证和本地 MCP 服务器变得越来越昂贵。这推动 Eon 走向集中式方案。

## 考虑过的方案

在基于 AgentCore 构建之前，Eon 评估了几种替代方案：

### 方案 1：带自定义认证的集中式代理

每个执行框架（harness）都有一套包含所有目标的代理配置。也就是用一个反向代理聚合所有工具，并配一层自定义认证。这能解决凭证整合，但只支持远程 MCP，而且需要从零构建和维护工具协议转换、会话管理和授权逻辑。实现和维护负担很重。

### 方案 2：Amazon Bedrock AgentCore Gateway

[Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 是 Amazon Bedrock AgentCore 的一项能力，它是一个托管网关，内置身份联合、基于 Cedar 的授权策略，以及能把本地 MCP 服务器转换为远程 HTTP 端点的 Runtime 托管能力。它在无需自定义基础设施的情况下满足了全部需求。

Eon 选择了方案 2，因为它把身份隔离、跨账户连接和策略执行作为托管能力提供，而不是他们需要自行构建和维护的代码。这两种是当时仅有的备选方案。

## 解决方案概述

Eon 部署了完整的 Amazon Bedrock AgentCore 技术栈：AgentCore Gateway、Policy in Amazon Bedrock AgentCore、AgentCore Runtime 和 AgentCore Identity，它们都是 Amazon Bedrock AgentCore 的能力。下图展示了客户端请求如何经过认证层到达单一网关。网关把获授权的工具调用路由到托管在多个 AWS 账户中 AgentCore Runtime 上的目标。

该架构分为五层：

### 客户端

使用 Claude Code、Cursor 或 OpenAI Codex 的开发者连接同一个 MCP URL。一个在 Amazon Bedrock 上运行 Claude 的自主 SRE 智能体以不同身份连接到同一个网关。

### 身份平面

企业单点登录（SSO）通过 Amazon Cognito 进行联合，由 Cognito 签发 JSON Web Token（JWT）并交给网关。Amazon API Gateway 前置作为面向人类的 OAuth 入口点，代理 MCP 会话。智能体则使用 Cognito 的 `client_credentials` 授权，直接向网关进行身份认证。

### 单一网关，最小权限访问

单个 AgentCore MCP Gateway 充当公司范围的前门。ENFORCE 模式下的 Cedar 策略控制哪些主体可以调用哪些工具。读操作仅对选定组开放，而不是对每个已认证用户开放。写操作仅限于低影响的协作动作，例如在 PR 或工单上评论，而生产工具是只读的。

### Policy in Amazon Bedrock AgentCore

Cedar 策略把每个主体映射到允许使用的工具。写操作仅限于低影响的协作动作，例如在 PR 或工单上评论，而生产工具是只读的。网关在转发到目标之前，会用 Cedar 评估每一个 `tools/call` 请求。

### 目标

数十个目标 MCP 服务器在一个网关上暴露数百个工具，由分布在多个 AWS 账户中的 AgentCore Runtime 提供服务。每个 Runtime 把基于本地 stdio 的 MCP 服务器转换为可通过网关访问的 Streamable HTTP 端点。

开发者打开自己的集成开发环境（IDE），配置一个 MCP URL，通过企业 SSO 完成认证，网关就会把数百个工具聚合到一个 `tools/list` 响应中。无需本地设置，也没有按工具区分的 token。

## 身份与访问隔离

核心的安全决策是在网关层面通过 Cedar 策略强制实施读、写边界。

**单一网关，策略强制的隔离：**

网关同时接受 JWT token（人类通过企业 SSO 和 Cognito）和 `client_credentials` token（智能体）。Cedar 策略决定每个主体可以做什么。获批组中的人类获得读访问权限。写操作需要显式的 Cedar 许可，且仅授予特定的智能体身份。

**Cedar 强化了逐工具的粒度：**

```
// Agent "sre-bot" can add comments on GitHub PRs
permit(
    principal == Agent::"sre-bot",
    action == Action::"tools/call",
    resource == Tool::"github_add_pr_comment"
);

// No human principal can invoke mutation tools
forbid(
    principal in Group::"humans",
    action == Action::"tools/call",
    resource in ResourceGroup::"write-tools"
);
```

Cedar 策略通过带评审评论的 GitHub PR 以代码方式管理，使团队对每一次权限变更都拥有版本控制和审计轨迹。

在网关内部，Cedar 策略按 SSO 组限定工具访问范围，而组与岗位角色相对应。工程师默认可以访问开发和测试环境。生产环境访问遵循 Eon 的安全与合规控制：它是只读的，通过审批流程即时授予，并接受审计。新团队成员的组也以同样方式按角色来限定，而不是按他恰好负责哪个服务。由于每个智能体动作都会在 ENFORCE 模式下对照 Cedar 检查，并被限定在最小权限的工具集内，自主智能体在安全、受限的范围内运行。它只能调用其身份被明确允许调用的那些工具。

> “以前，我们的内部智能体无法访问开发者使用的那些调查工具。现在，它使用同一个 Gateway，但拥有自己的身份和更严格的工具集。”

— Roei Zavida，Eon 高级 DevOps 工程师

## 跨账户连接

Eon 在多个 AWS 账户中运行 Runtime，按环境或服务边界组织。AgentCore Gateway 通过 IAM 跨账户角色代入访问每个 Runtime。账户 B 中的 Runtime 通过标准 IAM 信任策略信任账户 A 中的 AgentCore Gateway 执行角色。

这消除了什么：

- 跨多个 AWS 账户的 VPC 对等连接配置和路由表管理。
- 每个账户的 PrivateLink 端点成本。
- 账户之间的安全组协调。
- 每新增一个账户要花数天的配置工作（现在被一份 IAM 信任策略取代，几分钟即可部署）。

**目标挂载模式：**

根据每个工具的身份认证和托管模型，Eon 使用两种主要的挂载模式。下表总结了何时使用每种模式，并给出示例。

| **模式** | **何时使用** | **示例** |
| --- | --- | --- |
| Runtime + IAM | 工具需要通过 IAM 凭证走一次云内跳转 | Grafana 查询、Kubernetes API 调用 |
| Runtime 包装远程 MCP | 需要对工具面进行过滤或做凭证转换 | Linear |

大多数目标使用 Runtime + IAM。Eon 只在需要精简工具目录、或需要填入网关无法提供的凭证时，才包装远程 MCP。

## 调查会话流程

下面的流程跟踪一位开发者调查生产事故的过程：

- **身份认证。** 开发者打开 Claude Code（或 Cursor/Codex），连接到网关的 MCP URL。IDE 通过企业 SSO 发起 OAuth。Cognito 签发携带该开发者身份和组成员关系的 JWT。
- **工具发现。** 网关聚合来自数十个已连接目标的 `tools/list`，并向 IDE 返回包含数百个工具的统一清单。开发者在同一个列表中就能看到所有可用的调查工具。
- **工具调用。** 开发者提出：“给我看看过去一小时支付服务的错误率峰值。” IDE 的智能体选择 Grafana 查询工具，并发送一个 `tools/call` 请求。
- **策略评估。** 网关用 Cedar 评估该请求。开发者的组成员关系授予了对 Grafana 工具的访问权限。请求通过。
- **Runtime 执行。** 网关把请求转发给托管 Grafana MCP 服务器的 Runtime（运行在另一个 AWS 账户中）。Runtime 使用存储在 AgentCore Identity 保管库中的服务凭证向 Grafana 认证，执行查询并返回结果。
- **跨工具关联。** 智能体接着检查 Kubernetes 部署状态和相关的 GitHub PR，它们分别被路由到不同的 Runtime。开发者无需切换工具或重新认证，就能看到相互关联的结果。

## 规模化之后的经验教训

部署给 100 多名开发者、约 10,000 次会话，暴露了一些生产环境中的挑战：

### 管理 Cedar 策略大小

网关预先索引的每一个工具 schema 都会计入 Cedar 策略大小。当数十个目标暴露大量工具清单时，Eon 的策略增长到了接近大小配额。解决办法是：对工具数量多的目标使用 DYNAMIC 列表模式。在 DYNAMIC 模式下，网关在请求时把 `tools/list` 调用转发给 MCP 服务器，而不是预先索引 schema，因此对策略大小的贡献为零字节。

代价是 DYNAMIC 目标无法使用语义工具搜索。Eon 采用混合配置：对需要按用户 OAuth 的目标（工具数量较少、需要预先索引的 schema 来支撑同意流程）使用 DEFAULT 模式，对大型目录目标使用 DYNAMIC 模式。

### 标准 MCP 客户端的 OAuth 会话绑定

Claude Code、Cursor 和 Codex 期望使用 OAuth 的 `state` 参数来防护跨站请求伪造（CSRF）。AgentCore 使用 session-URI 绑定。Eon 构建了一个 Amazon API Gateway 中间层（shim），在两种协议之间做转换，使标准 MCP 客户端无需修改即可完成 OAuth 流程。

### 过滤工具面

有些 MCP 服务器会暴露数百个工具。单个开发者只用到其中与其服务相关的一小部分。Eon 构建了一个 Runtime 包装器，在 Runtime 层过滤工具清单，减少 `tools/list` 响应中的噪音，并防止意外调用无关操作。这种做法还让这些目标保持在 DEFAULT 模式，从而保留语义搜索和嵌入式特性，而这些正是 DYNAMIC 模式所牺牲的。

## 成果

| **指标** | **使用 AgentCore 之前** | **使用 AgentCore 之后** |
| --- | --- | --- |
| 每位开发者的凭证集 | 每个系统/MCP 服务器一份（GitHub、Grafana、云账户等） | 0（一次 SSO 登录） |
| 每台机器的本地 MCP 进程 | 10 | 0 |
| 开发者上手时间 | 2 天 | 2 分钟 |
| 跨账户网络配置 | 每个账户的 VPC 对等连接 | 0（仅 IAM） |
| 工具授权 | 按工具分别配置 | 一套面向人类和智能体的 Cedar 策略 |
| 平台上的开发者 | — | 100 多名 |
| 通过一个 URL 可访问的工具 | — | 数百个（横跨数十个目标） |
| 已处理会话数 | — | 约 10,000 |

这种单网关架构已经在 Eon 内部工程团队的生产环境中运行了数月。最明显的结果是开发者上手。接入完整工具集的设置时间，从大约两天配置凭证和本地 MCP 服务器，降到约两分钟。新工程师连接一个网关 URL，通过企业 SSO 认证，立刻就能看到其角色允许的工具。

节省下来的时间大部分归功于内部智能体，因为它通过网关获得了更多上下文，从而提高了调查的准确性。工程师则省下了此前花在 AI 工具设置上的时间，因为他们只需要连接到网关 URL。

Eon 正在探索如何用同样的模式支撑其自有产品中的 AI 能力。

> “AgentCore 给了我们一个经过认证的 MCP Gateway，取代了按工具区分的 token 和本地 MCP 进程。开发者和我们的内部智能体现在都能从一个 URL 访问 Kubernetes、Grafana、GitHub 和我们的云账户。”

— Roei Zavida，Eon 高级 DevOps 工程师

## 结论

本文介绍了 Eon 如何用单一 Amazon Bedrock AgentCore MCP Gateway 取代按工具区分的凭证和本地 MCP 进程。结果是基于 Cedar 的身份隔离、无需 VPC 对等连接的跨账户连接，以及面向 100 多名开发者和跨三个云的自主智能体的统一工具访问。单网关架构、Cedar 最小权限执行，以及 DEFAULT 与 DYNAMIC 混合策略模式，都是 ISV 把智能体和开发者连接到跨多云工具时可以复用的模式。
