# 借助 Amazon Bedrock 与 MCP，用生成式 AI 精简 GitHub 工作流

客户越来越希望借助大语言模型（LLM）的能力解决现实世界的问题。然而，在这些 LLM 与实际应用之间架起桥梁一直是个难题。AI agent 作为一种填补这一空白的新兴技术而出现。

通过 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 提供的基础模型（FM）充当 AI agent 的认知引擎，提供解读用户请求并生成恰当响应所必需的推理与自然语言理解能力。你可以把这些模型与各类 agent 框架和编排层集成，构建能理解上下文、做出决策并采取行动的 AI 应用。你可以基于 Amazon Bedrock Agents 构建，也可以使用 [LangGraph](https://www.langchain.com/langgraph) 与近期发布的 [Strands Agent SDK](https://strandsagents.com/0.1.x/) 等其他框架。

本篇博客探讨如何使用 Amazon Bedrock 的 FM、LangGraph 与 [Model Context Protocol](https://modelcontextprotocol.io/introduction)（MCP）构建强大的 agentic 应用，并给出一个处理 GitHub 工作流的实际场景：issue 分析、代码修复与 pull request 生成。

对于希望用托管方案精简 GitHub 工作流的团队，[GitHub 中的 Amazon Q Developer](https://aws.amazon.com/blogs/aws/amazon-q-developer-in-github-now-in-preview-with-code-generation-review-and-legacy-transformation-capabilities/) 提供了与 GitHub 仓库的原生集成。它内置代码生成、代码审阅与代码转换能力，无需自行开发 agent。Amazon Q Developer 为常见开发工作流提供了开箱即用的功能，而有特定需求或独特用例的组织，则可能更适合用 Amazon Bedrock 与 agent 框架构建定制方案。这种灵活性让团队可以按自身具体需求、技术要求以及希望对实现细节的掌控程度，在 Amazon Q Developer 的即用方案与基于 Amazon Bedrock 的定制方案之间做选择。

## 当前 AI agent 状态带来的挑战

尽管 AI agent 技术取得了显著进步，但 agent 的开发与部署现状仍面临重大挑战，制约着其有效性、可靠性与更广泛的采用。这些挑战横跨技术、运营与概念三个层面，形成了开发者与组织在落地 agentic 方案时必须跨越的障碍。

其中一个重大挑战是工具集成。尽管 Amazon Bedrock Agents、LangGraph 与 Strands Agent SDK 等框架为 agent 与外部工具和服务交互提供了机制，但现有做法往往缺乏标准化与灵活性。开发者必须为每个工具各自编写定制集成、定义精确的 schema，并在工具调用与响应处理中应对大量边界情况。此外，许多工具集成框架的僵化特性意味着 agent 难以适应工具接口的变化，也难以动态发现并使用新能力。

## MCP 如何帮助构建 agent

MCP 正是针对当前 agent 架构的局限与挑战而生，它提供了一个标准化框架，从根本上重新定义了 FM、上下文管理与工具集成之间的关系。该协议解决了此前阻碍 AI agent 更广泛采用与发挥效用的诸多核心挑战，尤其是在企业环境与复杂用例中。

借助 MCP 的 Tool Registry 与标准化调用模式，工具集成被大幅简化。开发者可以用一致的格式在注册表中登记工具，而工具选择、参数准备与响应处理这些复杂环节由协议来管理。这不仅降低了集成新工具所需的开发投入，还使更复杂的工具使用模式成为可能，例如工具链式调用与并行工具调用，而这些在现有框架中都难以实现。

这种组合发挥了各项技术的长处——Amazon Bedrock 中的高质量 FM、MCP 的上下文管理能力，以及 LangGraph 的编排框架——从而构建出能以更高可靠性和有效性应对日益复杂任务的 agent。

想象一下，你的开发团队早上一觉醒来，发现昨天的 GitHub issue 已经分析完毕、修复完成，并以 pull request 的形式等着审阅——这一切都是在夜间自主完成的。

AI 的近期进展，尤其是具备代码生成能力的 LLM，为开发工作流带来了颇具影响力的新思路。借助 agent，开发团队可以把简单改动自动化，例如依赖更新或直截了当的 bug 修复。

## 方案概览

Amazon Bedrock 是一项全托管服务，通过统一的 API 提供来自领先 AI 公司和 Amazon 自身的高性能 FM。Amazon Bedrock 还提供一整套广泛的能力，帮助你以兼顾安全、隐私与负责任 AI 的方式构建生成式 AI 应用。

LangGraph 通过基于图的架构编排 agentic 工作流，该架构能处理复杂流程，并在 agent 交互之间保持上下文。它使用监督控制模式与记忆系统进行协调。更多细节请参阅 [使用 LangGraph 与 Amazon Bedrock 构建多 agent 系统](https://aws.amazon.com/blogs/machine-learning/build-multi-agent-systems-with-langgraph-and-amazon-bedrock/)。

Model Context Protocol（MCP）是一项开放标准，让开发者能在自己的数据源与 AI 驱动的工具之间建立安全、双向的连接。[GitHub MCP Server](https://github.com/github/github-mcp-server) 是一个提供与 GitHub API 无缝集成的 MCP server。它为 AI 工具提供了一种标准方式来操作 GitHub 的仓库。开发者可以用它自动化任务、分析代码并改进工作流，而无需处理复杂的 API 调用。

本文以互补的方式使用这三种技术。Amazon Bedrock 提供理解 issue 并生成代码修复的 AI 能力。LangGraph 编排端到端工作流，在整个过程中管理状态与决策。GitHub MCP Server 与 GitHub 仓库交互，为 FM 提供上下文并落地生成的改动。三者结合，构成了一套自动化系统：它能够理解并分析 GitHub issue、提取相关代码上下文、生成代码修复、创建文档齐全的 pull request，并与现有 GitHub 工作流无缝衔接。

### 前置条件

在部署该方案之前，你必须具备以下前置条件。本文使用 `us-west-2` AWS 区域。有关可用区域的详情，请参阅 [Amazon Bedrock 端点与配额](https://docs.aws.amazon.com/general/latest/gr/bedrock.html)。

- 一个有效的 AWS 账户。
- 该账户中有一个具备调用 Amazon Bedrock 模型[足够权限](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-prereq.html)的 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色。如果你打算在 [Amazon SageMaker](https://aws.amazon.com/sagemaker/) Jupyter notebook 实例上运行代码（而非本地），还需要具备设置并管理 SageMaker 资源的[权限](https://docs.aws.amazon.com/sagemaker/latest/dg/security-iam-awsmanpol.html)。如果你拥有管理员权限，这一步无需额外操作。
- 在 Amazon Bedrock 上拥有 Anthropic 的 Claude 3.5 Haiku 访问权限。操作说明请参阅 [Access Amazon Bedrock foundation models](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)。
- [Docker](https://www.docker.com/) 或 [Finch](https://github.com/runfinch/finch)，用于以容器方式运行 GitHub MCP server。
- 一个细粒度 [personal access token](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)。GitHub MCP server 可以使用受支持的 GitHub API，因此只启用本文所需的最小权限。为 [contents](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens?apiVersion=2022-11-28#repository-permissions-for-contents)、[issues](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens?apiVersion=2022-11-28#repository-permissions-for-issues) 与 [pull requests](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens?apiVersion=2022-11-28#repository-permissions-for-pull-requests) 分配仓库权限。

### 环境配置与搭建

MCP server 充当我们的 LangGraph agent 与 GitHub API 之间的桥梁。我们没有直接调用 GitHub API，而是使用以容器方式运行的 GitHub MCP Server，它提供了标准化的工具接口。

你需要用前置条件中定义的 personal access token 来定义 MCP 配置。该配置将使用 Docker 或 Finch 启动 GitHub MCP Server。

```
mcp_config = {
    "mcp": {
        "inputs": [
            {
                "type": "promptString",
                "id": "github_token",
                "description": "GitHub Personal Access Token",
                "password": "true",
            }
        ],
        "servers": {
            "github": {
                "command": "/usr/local/bin/docker",
                "args": [
                    "run",
                    "-i",
                    "--rm",
                    "-e",
                    "GITHUB_PERSONAL_ACCESS_TOKEN",
                    "ghcr.io/github/github-mcp-server",
                ],
                "env": {
                    "GITHUB_PERSONAL_ACCESS_TOKEN": os.environ.get("GITHUB_TOKEN")
                },
            }
        },
    }
}
```

### Agent 状态

LangGraph 需要一个在工作流各节点之间流转的共享状态对象。该状态充当记忆，使每一步都能访问先前步骤的数据，并把结果传给后续步骤。

```
class AgentState(TypedDict):
    issues: List[Dict[str, Any]] 
    current_issue_index: int 
    analysis_result: Optional[Dict[str, Any]] 
    action_required: Optional[str]
```

### 结构化输出

我们不解析自由形式的 LLM 响应，而是用 Pydantic 模型强制输出保持一致、机器可读。这减少了分析错误，并确保下游节点以预期格式接收数据。Field 描述会引导 LLM 恰好提供我们所需的内容。

```
class IssueAnalysis(BaseModel):
    """Analysis of the GitHub issue."""
    analysis: str = Field(
        description="Brief summary of the issue's core problem or request."
    )
    action_required: str = Field(
        description="Decision on next step. Must be one of: 'code_change_required', 'no_change_needed', 'needs_clarification'."
    )
```

### MCP 工具集成

LangChain 的 MCP 适配器中的 `load_mcp_tools` 函数会自动把 MCP server 的能力转换为 LangChain 兼容的工具。这层抽象使得 GitHub 操作（列出 issue、创建分支、更新文件）可以像内置 LangChain 工具一样使用。

```
async def get_mcp_tools(session: ClientSession) -> List[Any]:
     """Loads tools from the connected MCP session."""
     tools = await load_mcp_tools(session)
     return tools 
```

### 工作流结构

每个节点都是无状态的——它接收当前状态，执行一项特定任务，并返回状态更新。这使工作流可预测、可测试，也便于调试。这些节点通过边（edge）或条件边连接起来。并非每个 GitHub issue 都需要改动代码：有些可能是文档请求、重复项，或需要进一步澄清。路由函数利用结构化的 LLM 输出动态决定下一步，使工作流具备适应性而不是僵化固定。

## 注意事项

为实现自动化工作流，[Amazon EventBridge](https://aws.amazon.com/eventbridge/) 通过其 [SaaS 合作伙伴事件源](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-saas-furls.html)提供了与 GitHub 的集成。配置完成后，EventBridge 会近乎实时地接收这些 GitHub 事件。你可以创建规则来匹配特定的 issue 模式，并把它们路由到各类 AWS 服务，例如 [AWS Lambda](https://aws.amazon.com/lambda/) 函数、[AWS Step Functions 状态机](https://aws.amazon.com/step-functions/)，或 [Amazon Simple Notification Service（Amazon SNS）](https://aws.amazon.com/sns/)主题做进一步处理。该集成使自动化工作流成为可能，当出现相关的 GitHub issue 活动时即可触发你的分析 pipeline 或代码生成流程。

部署该系统时，考虑采用分阶段铺开策略。先在两三个非关键仓库中进行试点，确认效果并发现问题。在试点阶段，务必在一组多样化的代码文件上充分评估该方案。这项测试应覆盖不同的编程语言、框架、文件格式（例如 Jupyter notebook），以及代码文件数量与规模上的不同复杂度。之后再逐步扩展到更多仓库，优先选择维护负担重或代码模式标准化的仓库。

基础设施方面的最佳实践包括容器化、面向可扩展性的设计、提供高可用性，以及针对应用、系统与业务指标实施全面监控。安全考量至关重要，包括以最小权限运行、妥善管理密钥、做输入校验，以及通过定期更新与安全扫描进行漏洞管理。

与公司的生成式 AI 运营与治理框架保持一致至关重要。部署前，请核实与组织的 AI 安全协议、数据处理政策以及模型部署准则相符。尽管这一架构模式带来显著收益，你仍应调整实现方式，使其契合贵组织的具体 AI 治理结构与风险管理框架。

## 结论

Amazon Bedrock 的 FM 与 MCP、LangGraph 的集成是 AI agent 领域的一次重要进步。通过解决上下文管理与工具集成这两项根本挑战，这一组合使开发更精巧、更可靠、更强大的 agentic 应用成为可能。

GitHub issue 工作流场景展现了多重收益，包括生产力提升、一致性改善、响应更快、可扩展的维护以及知识放大。重要的洞察包括：FM 作为开发伙伴的角色、工作流编排的必要性、仓库上下文的重要性、置信度评估的需求，以及反馈闭环对持续改进的价值。

AI 驱动的开发自动化未来将呈现多 agent 协作系统、主动式代码维护、上下文感知的代码生成、更强的开发者协作以及负责任的 AI 开发等趋势。挑战包括技能演进、治理复杂度、质量保障与集成复杂度；机会则包括开发者体验的转型、创新的加速、知识的普及以及可访问性的改善。组织可以通过小处着手、投入知识沉淀、建立反馈闭环、培养 AI 素养并试验新能力来做好准备。目标是增强开发者的能力而非取代他们，从而营造一个 AI 与人类开发者携手构建更好软件的协作未来。
