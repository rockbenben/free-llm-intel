# 优化 Amazon Bedrock Data Automation 中的 blueprint 抽取准确率

从发票、合同、税务表单、入学申请等非结构化文档中抽取结构化数据，是各类组织常见的自动化目标。而实现高抽取精度始终是一项关键挑战。当文档偏离预期模板、格式因供应商而异，或者扫描质量不佳时，准确率就会下降。借助 [Amazon Bedrock Data Automation](https://aws.amazon.com/bedrock/bda/)（BDA），你可以通过单一 API 对文档中的数据进行分类、抽取、规范化与校验。你使用可定制的 blueprint 来生成针对特定文档格式与业务需求量身定制的输出。不过，要让 blueprint 抽取准确率足以应对生产文档的全部多样性，仍然需要迭代调优。

**Blueprint instruction optimization（blueprint 指令优化）** 是一项 BDA 功能，它自动精炼你的抽取指令，直接应对这一挑战。你提供三到十份带期望值的示例文档，BDA 就会精炼你的 blueprint 指令，在几分钟而不是几周内提升准确率。无需单独做模型微调。

读完本文，你将能够优化自己的 blueprint 以提升准确率、通过 Amazon Bedrock 控制台或 API 运行优化工作流，并在选择示例与 ground truth 时应用最佳实践。

## 文档字段抽取的挑战

当你用 Amazon Bedrock Data Automation 构建智能文档处理（IDP）pipeline 时，你会创建 [blueprint](https://docs.aws.amazon.com/bedrock/latest/userguide/bda-bp.html) 来定义从文档中抽取哪些字段。每个字段都包含一条自然语言指令来引导抽取。例如：

- 字段：`invoice_number` → 指令：“The invoice number”。
- 字段：`total_amount` → 指令：“The total amount due”。

这些初始指令在简单直白的情况下效果不错。但真实世界的文档会带来额外的复杂度：

- 字段标签在不同文档变体之间会变化。
- 外观相似的标签会造成混淆（例如“subtotal”与“total”）。
- 不同供应商或不同时期的文档版式不同。
- 边界情况需要更具体的抽取指引。

下面是一个简化的示例，展示采购订单 blueprint schema 长什么样。每个字段都有一个 `type`、一个 `inferenceType`（`explicit` 表示值直接出现在文档中，`inferred` 表示值需要推理得出），以及一条引导抽取的 `instruction`：

```
{
  "class": "Purchase Order",
  "type": "object",
  "properties": {
    "po_number": {
      "type": "string",
      "inferenceType": "explicit",
      "instruction": "The unique identifier for the purchase order"
    },
    "order_date": {
      "type": "string",
      "inferenceType": "explicit",
      "instruction": "The date when the order was placed"
    },
    "order_total": {
      "type": "number",
      "inferenceType": "explicit",
      "instruction": "The total amount for the order"
    },
    "special_requests": {
      "type": "string",
      "inferenceType": "inferred",
      "instruction": "Any special requests or notes included in the order"
    }
  }
}
```

Blueprint 指令优化会精炼每个字段的 `instruction` 值。`type` 与 `inferenceType` 保持不变。你可以在 [GitHub 仓库](https://github.com/aws-samples/sample-blueprint-optimizer-for-data-automation) 中查看完整的采购订单 schema。

你已经了解自己的文档和数据。Blueprint 指令优化为你提供了一条更快缩小准确率差距的路径。

### 传统做法：手动迭代

为了提升抽取准确率，你通常会手动迭代字段指令：尝试不同措辞、补充上下文，通过反复试错来打磨描述。每一轮都意味着跑抽取、把结果与期望值比对、调整指令、再重复。对于要处理来自数百家供应商的文档的组织来说，这个过程可能每种文档类型要花上数周。

### 优化后的做法：自动精炼

借助 blueprint 指令优化，你可以在一个工作流中把整个精炼循环自动化。BDA 分析其抽取结果与你的 ground truth 之间的差异，然后精炼每个字段的自然语言指令，在几分钟而不是几周内交付优化后的指令。

## 用 blueprint 指令优化提升准确率

按照以下步骤，用你工作负载中的真实文档来精炼抽取指令。

- **提供示例文档**——上传三到十份来自生产工作负载的代表性文档，包括那些抽取一直很棘手的边界情况。此外，尽可能覆盖生产文档分布的多样性，以避免过拟合。
- **提供 ground truth**——为每份示例文档中的每个字段给出正确的期望值。Ground truth 是经过核实、准确的数据，用作衡量抽取质量的基准。它告诉 BDA 正确答案应该是什么。
- **运行优化**——启动优化过程。BDA 会把其初始抽取结果与你的 ground truth 比对，并精炼每个字段的自然语言指令。
- **评审结果**——查看详细的准确率指标与优化后的指令。优化通常几分钟内完成。指标包括 F1 分数（精确率与召回率的综合度量）与精确匹配率（抽取值与 ground truth 完全一致的字段占比）。

优化后的指令会吸收从你的示例中学到的模式，并补充更多细节与具体性。例如，一条初始指令“The invoice number”可能变成“The invoice number, typically found in the upper right corner of the document header, formatted as a numeric or alphanumeric code following ‘Invoice #’ or ‘Invoice No.’”。

## 示例场景：采购订单抽取

为了说明优化工作流，我们用一家虚构的自行车制造公司的文档，走一遍采购订单抽取场景。

你创建一个 blueprint，用于从采购订单中抽取字段，包括订单号、物料描述、数量、单价与总额。

在上传四份代表性采购订单（来自 Cycle Central 与 Bike World 等零售商）及其对应的 ground truth 文件并运行优化之后，准确率得到提升：

| **指标** | **优化前** | **优化后** |
| --- | --- | --- |
| 单文件精确匹配（最佳情况） | 92% | 100% |
| 聚合精确匹配 | 90% | 92% |

BDA 自动精炼指令，以应对这批采购订单中供应商特有的格式、字段标签差异与版式差异，把聚合精确匹配率从 90% 提升到 92%。

如果你在处理大批量文档，哪怕几个百分点的准确率提升，也会直接转化为人工复核队列的缩短与处理吞吐的加快。

## 解读结果

结果页按每个示例文件与聚合两种维度展示三项指标。理解每项指标在说明什么，有助于你判断是保存优化后的 blueprint，还是补充更多示例重新运行。

**Exact Match Rate（精确匹配率）** 是指抽取值与你的 ground truth 逐字符完全一致的字段占比。这是最严格的准确率度量。在上面的示例中，Cycle Central 文件的精确匹配率从 92.4% 提升到 100%，意味着 BDA 抽取的每个字段都与期望值精确匹配。

**Overall F1 Score（总体 F1 分数）** 把精确率（BDA 抽取出来的内容里有多少是对的）与召回率（正确数据里 BDA 找回了多少）合成一个分数。对于行项目描述这类取值长度可变的字段，F1 特别有用：这时精确匹配可能过于严格，而部分得分是有意义的。在这个示例中，F1 分数同样从 92.4% 提升到 100%，说明优化后的指令既抓到了正确的值，也抓到了适当的内容量。

**Confidence Score（置信度分数）** 反映 BDA 对每个抽取值的确定程度。置信度分数越高，意味着 BDA 在文档中为该字段找到了更清晰的信号。这个文件的置信度从 57.8% 提升到 60.1%，涨幅较小——当文档版式含糊时这是意料之中的。更高的置信度分数会减少 human-in-the-loop 工作流中被转给人工复核的字段量。

用 **Metrics by file** 标签页找出优化后分数仍然偏低的文档。这些文档适合补充更有针对性的示例。切换到 **Aggregated metrics**，在整套样例上评估 blueprint 的整体健康度，然后再选择 **Save optimized blueprint**。

## API 实操演示

以下示例展示了使用 AWS SDK for Python（Boto3）完成优化工作流的关键 API 调用。完整可运行的 notebook 见 [GitHub 仓库](https://github.com/aws-samples/sample-blueprint-optimizer-for-data-automation)。

**1. 创建 blueprint**

把你的 JSON schema 传给 `CreateBlueprint`。把 `DEVELOPMENT` 阶段当作沙箱使用：在你显式提升之前，它不会影响 `LIVE` 的 blueprint。

```
import boto3, json

bda_client = boto3.client('bedrock-data-automation')

response = bda_client.create_blueprint(
    blueprintName='acme-bikes-purchase-order',
    type='DOCUMENT',
    blueprintStage='DEVELOPMENT',
    schema=json.dumps(blueprint_schema)
)
blueprint_arn = response['blueprint']['blueprintArn']
```

**2. 启动优化**

用你的示例文档与 ground truth 文件调用 `InvokeBlueprintOptimizationAsync`。每个样本把文档的 S3 URI 与其 ground truth JSON 的 S3 URI 配成一对。

```
response = bda_client.invoke_blueprint_optimization_async(
    blueprint={
        'blueprintArn': blueprint_arn,
        'stage': 'DEVELOPMENT'
    },
    samples=[
        {
            'assetS3Object':       {'s3Uri': 's3://my-bucket/samples/PO_001.pdf'},
            'groundTruthS3Object': {'s3Uri': 's3://my-bucket/ground-truth/PO_001.json'}
        },
        # ... additional samples
    ],
    outputConfiguration={
        's3Object': {'s3Uri': 's3://my-bucket/optimization-output/'}
    },
    dataAutomationProfileArn=profile_arn
)
invocation_arn = response['invocationArn']
```

**3. 轮询完成状态**

该任务异步运行。轮询 `GetBlueprintOptimizationStatus`，直到状态变为 `Success`。

```
import time

while True:
    status = bda_client.get_blueprint_optimization_status(
        invocationArn=invocation_arn
    )['status']
    if status == 'Success':
        break
    elif status in ('ServiceError', 'ClientError'):
        raise RuntimeError(f'Optimization failed: {status}')
    time.sleep(15)
```

**4. 取回优化后的 blueprint**

任务完成后，`GetBlueprint` 会返回更新后的 schema，其中每个字段的 `instruction` 值都已精炼。

```
bp = bda_client.get_blueprint(
    blueprintArn=blueprint_arn,
    blueprintStage='DEVELOPMENT'
)
optimized_schema = json.loads(bp['blueprint']['schema'])
```

**5. 提升到 LIVE（可选）**

当指标满足你的要求时，把优化后的 blueprint 提升到生产环境。

```
bda_client.copy_blueprint_stage(
    blueprintArn=blueprint_arn,
    sourceStage='DEVELOPMENT',
    targetStage='LIVE'
)
```

## 与其他 Amazon Bedrock 功能的集成

优化后的 blueprint 提升了抽取层的准确率，这有助于强化你在 Amazon Bedrock Data Automation 之上构建的下游工作流：

- [**Amazon Bedrock Knowledge Bases**](https://aws.amazon.com/bedrock/knowledge-bases/) 是一项全托管的检索增强生成（RAG）能力，它能从质量更高的抽取数据中获益——语义搜索的向量嵌入更好，从而提升 RAG 工作流的准确率。
- [**Amazon Bedrock Agents**](https://aws.amazon.com/bedrock/agents/)——依赖抽取出的文档数据的 agentic 工作流（例如[自主房贷处理](https://aws.amazon.com/blogs/machine-learning/autonomous-mortgage-processing-using-amazon-bedrock-data-automation-and-amazon-bedrock-agents/)）会因输入更可靠而受益，从而降低错误处理的复杂度。
- [**Amazon Bedrock Guardrails**](https://aws.amazon.com/bedrock/guardrails/)——通过[自动推理检查（Automated Reasoning checks）](https://aws.amazon.com/blogs/aws/minimize-ai-hallucinations-and-deliver-up-to-99-verification-accuracy-with-automated-reasoning-checks-now-available/)校验的抽取数据，会因输入更干净而受益，从而提升验证准确率。

借助抽取字段的置信度分数与视觉依据（边界框），你可以在需要的地方实施 human-in-the-loop 校验。Blueprint 指令优化同时改善抽取值与相应的置信度分数，让你在自动化处理路径中获得更高的确定性。

## 最佳实践

基于早期客户反馈，我们建议如下：

- **选择有代表性的示例**——挑选能代表你生产工作负载多样性的文档，既包括常见格式，也包括抽取一直很棘手的边界情况。
- **核实 ground truth 的准确性**——在运行优化之前再检查一遍期望值是否正确，因为 ground truth 的质量直接影响结果。
- **从三到五个示例开始**——只用少数几个精心挑选的示例就能获得显著改善；如果初始结果没有达到你的准确率目标，再增加示例。
- **纳入有挑战的案例**——加入此前抽取失败的示例，帮助优化过程学会准确抽取边界情况。
- **需要时重新优化**——如果你发现准确率随时间下降（例如工作负载中出现了新的文档格式），就再跑一次优化。

- 删除你创建的 blueprint：在 Amazon Bedrock 控制台中进入 **Amazon Bedrock Data Automation**，选中该 blueprint，然后选择 **Delete**。
- 从你在该 stack 之外创建的 S3 存储桶中移除示例文档与 ground truth 文件。

有关管理 Amazon Bedrock Data Automation 资源的更多信息，请参阅 [Amazon Bedrock Data Automation 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/bda-bp.html)。

## 结论

Blueprint 指令优化可以显著减少达到高抽取准确率所需的人工投入。只需提供少量带 ground truth 值的示例文档，你就能自动精炼抽取指令，在几分钟而不是几周内提升准确率。

再加上 Amazon Bedrock Data Automation 的置信度分数、视觉依据，以及与 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 和 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 的集成，这项功能可以加速从原型走向生产 IDP 工作流的路径。

- 在你自己的文档上运行优化，度量针对你具体用例的准确率提升。
