# 使用 Amazon Bedrock Knowledge Bases、Amazon Transcribe 与用心的 UX 设计加速视频问答工作流

组织常常被包含宝贵洞见的视频和音频内容淹没。然而，既要高效、又要高准确率地提取这些洞见仍然是一大挑战。本文探讨一套创新方案，通过精心设计的用户体验加速视频与音频的审阅工作流，促成人与 AI 的协作。从用户的视角出发思考问题，我们就能打造一个强大的工具，让人们在长时间的录音中快速找到相关信息，同时不必承担 AI 幻觉的风险。

从律师、记者到内容创作者和医生，许多专业人士都需要定期审阅数小时的录制内容，以提取可验证的准确洞见。传统的人工审阅或对转录文本做简单关键词搜索的方法既耗时，又常常漏掉重要的上下文。确实存在更先进的 AI 摘要工具，但它们有产生幻觉或不准确信息的风险，而在医疗或法律诉讼这类高风险环境中，这可能十分危险。

我们的方案 Recorded Voice Insight Extraction Webapp（ReVIEW）通过为人类与 AI 协作提供无缝的方式，来应对这些挑战：在保持结果准确可信的同时加速审阅流程。该应用构建在 [Amazon Transcribe](https://aws.amazon.com/pm/transcribe/) 和 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 之上。Amazon Bedrock 是一项全托管服务，通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、Meta、Mistral AI、Stability AI 和 Amazon 等领先 AI 公司的高性能基座模型（FM）供你选择，并提供构建安全、注重隐私且负责任的生成式 AI 应用的广泛能力。

## 用户体验

为了在加速用户审阅长时音频或视频的同时降低幻觉风险，我们引入了带时间戳的引证这一概念。大语言模型（LLM）不仅能根据文件的转录文本回答用户的问题，还能指出该答案在转录文本中被讨论的时间戳（可能是一个或多个）。通过结合转录文本预处理、prompt 工程和结构化的 LLM 输出，我们实现了以下截图所示的用户体验：LLM 生成的时间戳引证被转换为可点击的按钮（图中以红色下划线标示），点击即可跳转到源视频的对应位置。

![ReVIEW 应用截图，展示可跳转到视频中特定时间戳的引证](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/28/ML-17810-image001.png)

这个例子中的用户上传了多个视频，包括一些 [AWS re:Invent](https://reinvent.awsevents.com/) 演讲的录像。你会注意到，上面那条回答其实包含一处源于转录错误的幻觉：AI 助手回答说发布了“Hyperpaths”，而实际上该服务叫 [Amazon SageMaker HyperPod](https://aws.amazon.com/sagemaker/hyperpod/)。

上图中的用户经历了如下过程：

- 用户向 AI 助手提问“SageMaker 有什么新东西？”。助手会搜索已上传的 re:Invent 视频的带时间戳转录文本。
- 助手给出带引证的答案。这些引证既包含视频名称，也包含时间戳，前端会显示与引证对应的按钮。每条引证可以指向不同的视频，也可以指向同一视频中的不同时间戳。
- 用户读到的内容是 SageMaker“Hyperpaths”被发布。他们随后通过点击按钮来核实生成答案的准确性，按钮会从该时间戳开始自动播放源视频。
- 用户看到该产品实际上叫 Amazon SageMaker HyperPod，从而可以确信在 re:Invent 上发布的产品就是 SageMaker HyperPod。

这一体验正是 ReVIEW 应用的核心：它让用户能够基于上传的音频或视频文件高效地获得问题答案，并通过亲自回看源媒体来核实答案的准确性。

## 方案概览

该应用的完整代码可在 [GitHub 仓库](https://github.com/aws-samples/recorded-voice-insight-extraction-webapp) 中获取。

下图展示了该方案的架构，呈现了数据在应用中的流转过程。

![ReVIEW 应用的架构图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/28/ML-17810-image002.png)

该工作流包含以下步骤：

- 用户通过 [Amazon CloudFront](https://aws.amazon.com/cloudfront/) 分配访问该应用；该分配会添加自定义请求头，并把 HTTPS 流量转发到 Elastic Load Balancing 的应用负载均衡器。负载均衡器后面是一个运行在 [Amazon Elastic Container Service](https://aws.amazon.com/ecs/)（Amazon ECS）上的容器化 [Streamlit](https://streamlit.io/) 应用。
- [Amazon Cognito](https://aws.amazon.com/pm/cognito/) 负责处理用户登录前端应用与 [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 的认证。
- 当用户通过前端上传媒体文件时，系统会生成一个预签名 URL，供前端把文件上传到 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）。
- 前端把文件提交到应用的 S3 存储桶，此时通过触发 [AWS Lambda](https://aws.amazon.com/pm/lambda/) 启动文件处理流程。文件被送至 Amazon Transcribe，生成的转录文本存储在 Amazon S3 中。转录文本会被后处理为更适合 LLM 使用的文本形式，并由 [AWS Step Functions](https://aws.amazon.com/step-functions/) 状态机把该转录文本同步到 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 中配置的知识库。知识库同步过程负责转录文本的分块与 embedding，并把 embedding 向量和文件元数据存储到 [Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/) 向量数据库中。
- 如果用户针对某一特定转录文本提问（通过在 UI 中的“选择媒体文件”下拉菜单指定），则会使用整份转录文本生成回答，因此不需要通过知识库执行检索步骤，而是直接通过 Amazon Bedrock 调用 LLM。
- 如果用户所提问题的答案可能出现在任意多个源视频中（通过在 UI 下拉菜单中选择 **Chat with all media files**），则会使用 Amazon Bedrock Knowledge Bases 的 [RetrieveAndGenerate](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_RetrieveAndGenerate.html) API 对用户查询做 embedding，在向量数据库中找出语义相似的分块，把这些分块输入 LLM 的 prompt，并生成格式特殊的回答。
- 在整个过程中，跟踪转录与摄取状态、把用户名映射到已上传文件以及缓存回答等应用数据，都通过 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 实现。

该架构的一个重要特点是：通过由 API Gateway 部署的 REST API，把前端与后端逻辑清晰分离。这是一项设计决策，目的是让该应用的使用者能够用自定义前端替换 Streamlit 前端。替换前端的说明见 [GitHub 仓库的 README](https://github.com/aws-samples/recorded-voice-insight-extraction-webapp?tab=readme-ov-file)。

### 带时间戳的引证

该方案的关键在于 prompt 工程与结构化的输出格式。在针对用户问题生成回答时，LLM 会被要求不仅（在可能的情况下）给出问题答案，还要以特定方式标注来源引用。

完整 prompt 可以[在 GitHub 仓库中](https://github.com/aws-samples/recorded-voice-insight-extraction-webapp/blob/main/infra/lambdas/kb/kb_qa_prompt.py)查看，这里仅展示一个为简洁而缩短的伪 prompt：

> 你是一个智能 AI，基于自动生成转录文本的检索分块来回答问题。
>         以下是检索到的转录文本分块及其元数据，元数据中包含文件名。每个分块都包含一个 <media_name> 和多行转录文本，每行以一个时间戳开头。
>         $$ retrieved transcript chunks $$
>         你的回答应采用 json 格式，包含一个部分答案列表，每个部分答案都带有一条引证。引证应包含源文件名和时间戳。以下是用户的问题：
>         $$ user question $$

随后，前端会把 LLM 的响应解析到一个固定的 schema 数据模型中，该模型用 [Pydantic](https://docs.pydantic.dev/latest/) 的 [BaseModels](https://docs.pydantic.dev/latest/api/base_model/) 描述：

```
from pydantic import BaseModel

class Citation(BaseModel):
    """A single citation from a transcript"""
    media_name: str
    timestamp: int

class PartialQAnswer(BaseModel):
    """Part of a complete answer, to be concatenated with other partial answers"""
    partial_answer: str
    citations: List[Citation]

class FullQAnswer(BaseModel):
    """Full user query response including citations and one or more partial answers"""
    answer: List[PartialQAnswer]
```

这种格式让前端能够解析响应，并为每条引证显示按钮，把相关的媒体片段定位出来供用户查看。

### 部署细节

该方案以一个 [AWS Cloud Development Kit](https://aws.amazon.com/cdk/)（AWS CDK）[stack](https://docs.aws.amazon.com/cdk/v2/guide/stacks.html) 的形式部署，其中包含四个嵌套 stack：

- 一个后端，负责转录已上传的媒体并跟踪作业状态
- 一个检索增强生成（RAG）stack，负责搭建 OpenSearch Serverless 和 Amazon Bedrock Knowledge Bases
- 一个 API stack，搭建由 Amazon Cognito 授权的 REST API 以及多个 Lambda 函数，在逻辑上把前端与后端分离
- 一个前端 stack，由在 ECS 集群中作为负载均衡服务运行的容器化 Streamlit 应用构成，并有一个 CloudFront 分配连接到该负载均衡器

## 先决条件

该方案需要以下先决条件：

- 你需要拥有 AWS 账户，以及一个具备创建和管理该应用所需资源与组件权限的 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色和用户。如果你还没有 AWS 账户，请参阅[如何创建并激活新的 Amazon Web Services 账户？](https://aws.amazon.com/premiumsupport/knowledge-center/create-and-activate-aws-account/)
- 你还需要申请至少一个 Amazon Bedrock LLM（用于生成问题答案）和一个 embedding 模型（用于找出与用户问题语义相似的转录分块）的访问权限。以下 Amazon Bedrock 模型是默认配置，但在部署应用时可以通过配置文件更改（后文会说明）：Amazon Titan Embeddings V2 – Text、Amazon 的 Nova Pro
- 你需要一个已安装 AWS CDK 依赖的 Python 环境。操作说明请参阅[在 Python 中使用 AWS CDK](https://docs.aws.amazon.com/cdk/v2/guide/work-with-cdk-python.html)。
- 部署时需要 [Docker](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/create-container-image.html#create-container-image-install-docker) 来构建 Streamlit 前端容器。
- 引导和部署 AWS CDK 所需的最小 IAM 权限，在 GitHub 仓库的 ReVIEW/infra/minimal-iam-policy.json 文件中有说明。请确保部署各 stack 的 IAM 用户或角色具备这些权限。

## 克隆仓库

先 fork 该仓库，然后把它克隆到你选择的位置。例如：

```
$ git clone https://github.com/aws-samples/recorded-voice-insight-extraction-webapp.git
```

## 编辑部署配置文件

你还可以选择编辑 `infra/config.yaml` 文件，为你的 stack 提供一个具描述性的基础名称。该文件也是你选择用于语义检索的特定 Amazon Bedrock embedding 模型、以及用于生成回答的 LLM，并为将要摄取已上传媒体文件转录文本的知识库定义分块策略的地方。如果你想用已有的用户基础来引导应用，也可以在该文件中复用现有的 Amazon Cognito 用户池。

## 部署 AWS CDK stack

使用以下代码部署 AWS CDK stack：

```
$ cd infra
$ cdk bootstrap
$ cdk deploy –-all
```

每个 AWS 账户只需使用一次上述命令。deploy 命令会部署父 stack 和四个嵌套 stack。该过程大约需要 20 分钟完成。

部署完成后，控制台屏幕上会打印一个形如 `xxx.cloudfront.net` 的 CloudFront 分配 URL，用于访问该应用。你也可以在 [AWS CloudFormation](https://aws.amazon.com/cloudformation) 控制台中找到该 URL：定位名称与配置文件中取值相匹配的 stack，选择 **Outputs** 标签页，然后找到与键 `ReVIEWFrontendURL` 关联的值。该 URL 会带你进入如下截图所示的登录页面。

![ReVIEW 应用登录页面的截图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/28/ML-17810-image003.png)

## 创建 Amazon Cognito 用户以访问应用

要登录正在运行的 Web 应用，你必须创建一个 Amazon Cognito 用户。请完成以下步骤：

- 在 Amazon Cognito 控制台中，进入刚刚创建的用户池。
- 在 **User Management** 下的 **Users** 部分，选择 **Create user**。
- 创建用户名和密码，用于登录部署在该账户中的 ReVIEW 应用。

当应用部署被销毁时（如清理一节所述），Amazon Cognito 用户池会保留下来以保留用户基础。你可以使用 Amazon Cognito 控制台手动彻底删除该用户池。

## **测试应用**

在 **File Upload** 标签页上传一个或多个音频或视频文件即可测试该应用。该应用支持 [Amazon Transcribe 支持的媒体格式](https://docs.aws.amazon.com/transcribe/latest/dg/how-input.html#how-input-audio)。如果你想找示例视频，可以考虑[下载一段 TED 演讲](https://www.ted.com/talks)。上传后，你会看到文件出现在 **Job Status** 标签页上。你可以在这个标签页跟踪转录、后处理和知识库同步各步骤的处理进度。在至少一个文件被标记为 **Complete** 之后，你就可以在 **Chat With Your Media** 标签页与它对话了。

**Analyze Your Media** 标签页让你可以为单个已上传文件创建并应用自定义的 LLM 模板 prompt。例如，你可以创建一个基础摘要模板或一个“提取关键信息”模板，并在这里把它应用到已上传的文件上。本文未对该功能做详细介绍。

## 清理

即使不使用，已部署的应用也会持续产生费用，例如来自 OpenSearch Serverless 索引与搜索的 [OCU 最低用量](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-scaling.html)。要删除部署该应用时创建的所有资源，请运行以下命令：

```
$ cdk destroy –-all
```
