# 用 Amazon Bedrock AgentCore 驱动 agentic AI 销售战略

随着 agent 的采用规模不断扩大，我们看到一个共同模式在各企业（包括我们自己的销售组织）中出现：专用 agent 能创造价值，但如果没有编排，用户就要承担在它们之间做选择的认知负担。在 AWS Sales，这意味着全球组织内部署了 20 多个领域专属 agent，销售代表要在系统之间来回切换上下文，而不是专注于与客户的对话。在本文中，我们介绍如何基于 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore) 构建 Field Advisor 来解决这个问题、我们做出的架构决策，以及我们看到的可量化成果。

## **挑战：agent 泛滥却缺少编排**

随着 AWS 扩大 AI 的采用范围，AWS 销售代表面临一个不小的挑战。有 20 多个领域专属 agent 分别处理客户关系管理（CRM）操作、会议排期、客户洞察、产品推荐和合规检查，代表们必须知道每项任务该调用哪个 agent。他们还要在碎片化的对话之间维护上下文，并手工合并来自不同系统的输出。这些额外开销占用了本可以用来理解客户需求、交付解决方案的时间。

## **为什么选 Bedrock AgentCore：为企业规模的编排而生**

AWS Sales 团队选择 Amazon Bedrock AgentCore，是因为它提供了在生产环境中大规模运行 agentic AI 所需的能力：

- 隔离的执行环境，支持安全的多租户运营
- 统一网关，跨 AWS 账户访问工具与 agent
- 持久记忆，覆盖会话与长期上下文
- 一致的标识传播，集成 OAuth
- 内置可观测性，覆盖复杂的请求流
- 集成评估，用于持续的质量监控。

这些能力消除了对自建基础设施的需求，工程团队因此可以专注于能改善客户成果的领域智能，而不必去搭建基础服务。Field Advisor 通过充当一个中心层来应对编排难题：它把请求路由给专用 agent，同时保持单一对话界面。销售代表用自然语言提问，Field Advisor 把请求路由到正确的 agent 或工具、在多次交互之间保持对话上下文、为敏感操作协调审批，并交付统一的答复。这最终使全球销售需求能得到更快、更有依据的响应。

## **Field Advisor 为销售团队带来了什么**

Field Advisor 是一个内部对话式助手，覆盖 AWS 销售团队的六项关键工作流，每一项都旨在把时间尽可能多地用在面向客户的活动上：

- **多 agent 编排**消除了“要知道哪个专用 agent 负责合规检查、产品推荐或技术分析”这一认知负担。销售代表只与单一对话界面交互，Field Advisor 在后台完成请求路由，因此他们可以专注于客户对话，而不是系统导航。
- **嵌入式访问**把 AI 能力直接带入销售团队日常使用的工具。Field Advisor 可以工作在 CRM 系统、Slack 和自研应用中，从而消除工作流中断，让代表专注于客户交互。
- **人在环路中的工作流**在加速日常任务的同时，对关键业务操作保持控制。当 Field Advisor 需要更新 CRM 数据时，它会展示拟议的变更，并等待明确批准后才做修改。这有助于保持数据准确性、防止非预期或有害的改动，并通过让销售代表掌控关键更新来维持问责。

- **主动推荐**通过 Slack 的推送式提醒来补充对话能力。销售代表会收到由 AI 驱动的洞察，涉及客户服务使用情况、业务数据趋势，以及 CRM 数据整洁度（hygiene）提醒。这些洞察让团队主动触达客户，而不是被动响应。

## **Amazon Bedrock AgentCore 如何提供底座**

要支撑全球销售团队中的数千名 AWS 人员，方案必须能处理复杂的多 agent 编排、对内部系统的安全访问，以及高并发下可预测的执行。Amazon Bedrock AgentCore 为 agent 提供隔离的执行环境、用于工具与 agent 访问的统一网关、覆盖会话与长期上下文的持久记忆、一致的标识传播、跨请求流的内置可观测性，以及用于持续质量监控的集成评估。

当销售代表通过受支持的渠道（CRM 系统、Slack 或独立 Web 门户）提问时，请求会先经过一个身份认证服务，由它验证身份并签发 OAuth token。AgentCore Runtime 接收通过认证的请求，初始化一个用 Strands Agents 构建的 supervisor agent，并管理完整的执行生命周期。

supervisor agent 分析查询并决定如何处理。它可以调用本地工具做 CRM 查询与知识库检索，调用为通过 MCP 集成的系统准备的远程 MCP 工具，或者委派给运行在其他 AgentCore Runtime 中的专用领域 agent。AgentCore Identity 把已认证的身份传播到每一个下游工具和 agent。结果被综合成统一答复，通过 AgentCore Runtime 的原生流式支持回传。

### **关键架构组件**

该架构使用多项协同工作的 Amazon Bedrock AgentCore 能力来交付 Field Advisor 的各项功能：

- **AgentCore Runtime** 在安全、隔离的 MicroVM 环境中托管 supervisor agent。每个用户会话运行在自己的执行上下文中。运行时负责模型访问、guardrails 和 agent 生命周期，包括把答复以流式方式回传给用户。
- **Strands Agents** 驱动运行时内部的推理循环。它处理编排周期：接收模型响应、分派工具调用（尽可能并行）、管理对话上下文，并协调多 agent 流程。Strands Agents 中可扩展的 hook 系统允许在不改动核心推理循环的前提下定制 agent 行为，例如错误处理、授权检查和响应处理。
- **AgentCore Memory** 同时存储短期对话历史与长期用户上下文。实现中使用了一个自定义会话管理器，它扩展了 Strands Agents 的 AgentCoreMemorySessionManager 以优化写入模式。它在每次调用之后同步状态，而不是每条消息之后同步，这在不为耐久性妥协的前提下减少了 API 调用。
- **AgentCore Identity** 负责整个方案中的标识传播。销售代表用 OAuth 认证一次，token 便在系统中传播。对于跨账户的 agent 调用，系统通过 AgentCore Identity 的资源凭证提供方（resource credential provider）支持机器对机器的 OAuth token 交换。
- **AgentCore Gateway** 为远程 MCP 工具提供集中式访问入口。工具无需逐个管理与每个 MCP 服务器的连接，而是注册到单一的 Gateway 实例，由它处理认证与可用性。启动时，supervisor 从 Gateway 获取工具定义并创建对应的本地 Strands 工具，因此新的 MCP 工具可以在不改动运行时部署的情况下接入。
- **AgentCore Observability** 为每次执行捕获 traces、logs 和 metrics。Strands 原生集成 OpenTelemetry，后者为跨多 agent、多工具的流程提供分布式追踪。当单个用户问题可能并行扇出到多个远程 agent 和 MCP 工具时，这对排障至关重要。
- **AgentCore Evaluations** 支持对生产环境中 agent 行为的持续质量监控。AWS 使用通过 AgentCore Observability traces 捕获的评估数据，衡量答案相关性、上下文精确度、操作正确性和忠实度。这提供了一个反馈回路，帮助识别回归并随时间提升编排质量。

### **核心架构能力**

Field Advisor 的架构建立在前面介绍的 AgentCore 组件之上，这些组件构成一组相互咬合的能力，共同交付可靠、安全且可扩展的多 agent 编排。以下几节将走查团队如何实现每一项能力。

### **编排与模型配置**

supervisor agent 是一个 Strands Agent，用 system prompt、一组工具、会话管理器、对话管理器和模型提供方初始化。实现中使用 Amazon Bedrock 上可用的最新 Anthropic Claude 模型作为基础模型（FM），并通过 Amazon Bedrock 的跨区域推理配置文件（cross-Region inference profile）访问，以获得更高吞吐。

为了降低多轮对话的延迟，团队构建了自定义的 PromptCachingBedrockModel，它扩展 Strands 的 BedrockModel 以加入增量式 [prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)。在每次模型调用之前，实现会从对话历史中移除先前所有的缓存点，并给最新一条消息加上新的缓存点。这样，直到最近一轮为止的内容都被缓存，模型在每一轮只需处理新内容。

```
CACHE_POINT = {"cachePoint": {"type": "default", "ttl": "1h"}}


class PromptCachingBedrockModel(BedrockModel):
    """Add a rolling cache point to the latest message so the model reuses
    cached prefixes instead of re-processing the full history."""

    def _format_request(self, messages, **kwargs):
        # Remove stale cache points from older messages
        for msg in messages:
            msg["content"] = [
                b for b in msg["content"] if "cachePoint" not in b
            ]
        # Add a cache point to the latest message
        messages[-1]["content"].append(CACHE_POINT)
        return super()._format_request(messages=messages, **kwargs)
```

由于 Amazon Bedrock 限制每个请求的缓存点数量，并要求请求中（工具、system prompt，然后是消息）的 TTL 取值非递减，实现会谨慎管理缓存点的位置。结果是每个新的用户轮次都增量地延长已缓存的 prefix，而不是重新处理整段对话。

Strands Agents 的 [hook](https://strandsagents.com/docs/user-guide/concepts/agents/hooks/) 系统是核心机制，它让 agent 行为可以在不改动核心推理循环的前提下被定制。注册的 hook 分别用于：错误熔断，即自动跳过在单次调用中反复失败的工具；条件式授权，即拦截访问敏感 CRM 数据的工具调用，用 Strands Interrupts 暂停执行以请求用户同意，并且只有批准之后才继续；写操作确认，即对会修改数据的工具展示拟议变更，要求执行前获得明确批准；引用提取，即处理知识库检索结果，提取来源引用并附加到最终答复；工具调用流式推送，即把工具调用状态流式发送到前端，让用户在 agent 工作时看到实时进度。

这种基于 hook 的做法意味着授权、错误处理这类横切关注点与工具实现解耦。拥有远程 agent 的团队不必实现熔断或流式推送，supervisor 会统一处理。对于设计类似系统的构建者来说，hook 是一个自然的扩展点，可以避开中间件链或装饰器栈带来的复杂度。

### **多 agent 协调**

Field Advisor 采用 supervisor-subagent 模式。supervisor agent 充当主编排者，负责合规、产品推荐、会议排期等的专用领域 agent 则以工具形式集成。每个远程 agent 由名称、描述和单个 query 参数定义。当 supervisor 判断某个问题应由某个领域 agent 处理时，它就调用对应的工具。包装层负责完整的调用生命周期：构造 payload、通过 OAuth 认证、把请求发送到远程 AgentCore Runtime，并把响应流式回传。

```
def create_remote_agent_tool(config: RemoteAgentConfig) -> AgentTool:
    """Create a Strands tool that wraps a remote agent."""

    async def remote_agent_tool(query: str, tool_context: ToolContext):
        invoker = RemoteAgentInvoker(config)
        params = InvocationParams(
            query=query, session_id=session_id, alias=alias, ...
        )
        async for event in invoker.stream(params):
            if is_final_response(event):
                payload = parse_response_payload(event)
                # Surface any interrupts from the remote agent
                if payload.interrupts:
                    tool_context.interrupt(payload.interrupts)
                yield payload.response
            else:
                yield event  # stream tool-call progress to the UI

    return tool(context=True)(remote_agent_tool)
```

supervisor 看到的是一份扁平的工具目录，其余由 Strands 推理循环处理。这意味着新增一个 agent 只需一条配置项，无需改动编排逻辑。Field Advisor 还支持直通（pass-through）模式，销售代表可以显式指定某个 agent 处理其请求。在这种模式下，请求完全绕过 supervisor。运行时把查询直接转发给目标远程 agent，并把它的响应流式回传，保留子 agent 的格式与引用。用户可以在同一段对话中在 supervisor 模式与直通模式之间切换。

### **人在环路中的工作流**

实现使用了 Strands Agents 原生的 [Interrupt](https://strandsagents.com/docs/user-guide/concepts/interrupts/) 特性，来支持需要用户明确确认的工作流。当某个工具或远程 agent 需要用户输入时（例如在查询 CRM 记录之前确认某项数据访问协议），执行会暂停，interrupt 被返回给客户端。用户通过 Slack 或 CRM 界面作答，agent 带着其输入继续执行。

这一模式被扩展为可跨 agent 边界工作。当远程 agent 在其响应 payload 中返回 interrupt 时，本地工具包装层会检测到它，并代表该远程 agent 抛出一个 Strands Interrupt。这意味着方案中的每个 agent 无论运行在哪里都能请求用户输入，而用户通过单一一致的界面交互。这一设计是有意为之的选择，而不是另建一个带消息队列与轮询的人在环路服务。由于 Strands Interrupts 把状态持久化在会话管理器中，这个模式完全基于代码——不需要额外的基础设施组件。关键洞见在于本地工具包装层充当桥梁：它把远程 agent 的 interrupt 响应翻译成原生 Strands Interrupt，于是暂停与恢复的机制全部由框架处理。

### **记忆与上下文管理**

AgentCore Memory 同时提供短期与长期持久化。短期记忆维护单个会话内的完整对话历史。长期记忆使用语义策略跨会话存储摘要与重要事实，因此 agent 即使在新对话中也能记住用户偏好与既往交互。

在上下文管理方面，实现使用 Strands Agents 的 [SummarizingConversationManager](https://strandsagents.com/docs/user-guide/concepts/agents/conversation-management/#summarizingconversationmanager) 来处理接近模型 token 上下文窗口的对话。较早的消息会被摘要，以腾出上下文空间，同时保留关键信息。用户输入也会受 token 上限约束，过大的工具响应在回传给模型之前会被截断，从而防止单一来源造成上下文溢出。

### **文件上传**

销售代表可以直接在对话中上传文档与图像。Strands 接受文件字节作为 ContentBlock 输入，支持文本格式与图像。文件上传后，其内容成为对话历史的一部分，可供 agent 分析、摘要或回答后续问题。对于 JSON 这类不受支持的文件类型，系统会提取文本内容并把它前置到用户消息中。这比之前的方案有所改进——过去每次聊天最多 5 个文件，合计大小上限 10 MB。

### **通过 MCP 统一工具集成**

Field Advisor 通过统一界面支持三类工具。本地工具直接运行在 AgentCore Runtime 内部，用于 CRM 查询、知识库检索和数据查找。远程 MCP 工具通过 Model Context Protocol 连接外部系统。启动时，运行时通过 AgentCore Gateway 与已注册的 MCP 服务器建立连接，获取其工具定义并创建对应的本地 Strands 工具。已有 20 多个 MCP 工具以这种方式接入，每个只需几分钟即可完成集成，而不是几天。接入流程很直接：在 Registry 服务中注册 MCP 配置，supervisor 会在下次启动时自动发现它；无需改代码，也无需重新部署运行时。其他 AgentCore Runtime 中的远程 agent 以相同接口被包装为工具，使工具与 agent 之间的区别对模型透明。这种统一做法意味着新增一项能力（无论是本地函数、MCP 服务器，还是完整的 agent）都不需要改动编排逻辑。supervisor 看到的是一份扁平的工具目录，其余由 Strands 推理循环处理。

### **可观测性与评估**

Strands 原生集成 OpenTelemetry。AgentCore Observability 捕获由此产生的 traces、logs 和 metrics。每一次 agent 调用、工具调用和模型交互都被端到端追踪，包括扇出到其他账户中远程 agent 的调用。这些数据既用于运营监控，也用于通过 AgentCore Evaluations 做持续评估。团队既对实时生产流量跑在线评估，也针对精心整理的测试集跑离线评估。Amazon Bedrock AgentCore 中内置的评估器持续衡量 agent 质量，并在用户受到影响之前捕捉回归。对于刚开始做 agent 评估的构建者，AWS 建议先从针对生产流量的在线评估入手，而不是先构建精心整理的测试集。真实的用户查询会暴露合成测试漏掉的边缘情况，而 AgentCore Evaluations 中内置的评估器无需开发自定义指标就能提供一个有用的基线。

### **安全与合规**

安全性在整个方案中分层实现。AgentCore Runtime 的 MicroVM 隔离为每个用户会话提供各自的安全执行上下文。Amazon Bedrock Guardrails 过滤用户输入与模型响应，拦截有害或超出范围的内容。AgentCore Identity 把已认证的用户标识传播到每一个下游系统。工具与远程 agent 一致地执行访问控制，包括在访问敏感 CRM 数据前要求用户明确同意的条件式授权检查。

## **结论**

本文展示了 AWS Sales 如何把 Field Advisor 从一个独立的对话式助手演进为由 Amazon Bedrock AgentCore 驱动的完整 AI agentic 编排方案。通过使用 Amazon Bedrock AgentCore 中可组合的服务（Runtime、Gateway、Memory、Identity 和 Observability），并搭配 Strands Agents，我们取得了可量化的改进，直接影响全球销售组织，并最终影响他们所服务的客户。销售代表花在系统导航上的时间更少，用在理解客户需求上的时间更多，从而交付更快、更有依据的答复。要了解 AI 如何改变你的销售职能，请联系你的 AWS 客户团队。他们可以与你讨论 Amazon Bedrock AgentCore 这类服务如何帮助你的组织构建类似方案。

要了解更多关于 Amazon Bedrock AgentCore 的信息，请访问 Amazon [Bedrock 文档](https://docs.aws.amazon.com/bedrock-agentcore/)。对于希望构建类似多 agent 编排方案的团队，AWS 建议先从 AgentCore Runtime 上的单个 supervisor agent 开始，通过 AgentCore Gateway 逐步增加工具，并使用 Strands hooks 分层加入授权与错误处理这类横切关注点。这种渐进式做法让你可以在增加复杂度之前，在生产环境中逐一验证每个组件。
