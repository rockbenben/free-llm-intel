## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# Postman 如何在 Amazon Bedrock 上为 4000 万开发者运行 Agent Mode

给演示做一个 AI 智能体，和为 [4000 万开发者](https://www.postman.com/company/about-postman/)持续运维一个智能体，是两个不同的工程问题。Postman 着手构建 [Agent Mode](https://learning.postman.com/docs/postman-ai-developer-tools/agent-mode/)，让 [API 测试](https://learning.postman.com/docs/sending-requests/response-data/test-responses/)、[文档](https://learning.postman.com/docs/publishing-your-api/documenting-your-api/)、发现与实现这几件事都有一种 AI 原生的做法。团队原本预计最难的是模型质量和提示设计，而更深的挑战来自把一个智能体接进一个成熟产品——它带着多年积累的界面驱动假设，产品覆盖面很广，还有大量专门概念。

本文里，Postman 和 AWS 共同描述了在让成熟产品对 AI 智能体「可读」的过程中逐渐成形的几个架构模式：控制工具泛滥、开放基于 schema 的读取，以及把瓶颈看作上下文而不是能力。

我们还会说明 [Agent Mode](https://learning.postman.com/docs/getting-started/basics/about-agent-mode/)如何使用 [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html)来获得模型灵活性、按地理范围划定的跨区域推理、依模型而定的零数据保留，以及多层级提示缓存。这些经验合在一起，能帮助团队把生产环境的智能体真正推过原型阶段。

## Postman 为什么要构建 Agent Mode

[Agent Mode](https://learning.postman.com/docs/getting-started/basics/about-agent-mode/)是 Postman 提供的入口，让使用者以 AI 原生的方式在产品中完成测试、文档、发现与实现。Postman 已经演进了 11 年，开发者和用户早已习惯通过界面定位信息：展开侧边栏、切换标签页、打开请求。把这套认知方式为智能体重做一遍，就把产品的 API、用户体验以及产品知识分布里的结构性假设暴露了出来。智能体是对数据推理，而不是在屏幕上找路。图 1 说明 Agent Mode 如何直接作用于应用本身。

![Postman Agent Mode 直接在应用里打开 pull request 并提出后续步骤](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/06/ML-21683-1.png)

图 1：Agent Mode 直接作用于 Postman 应用。这个例子里，它打开了一个 pull request 并提出后续步骤，用户不需要再在界面里逐层导航

[Agent Mode](https://learning.postman.com/docs/getting-started/basics/about-agent-mode/)运行在 [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html)上，由后者为智能体背后的基础模型提供托管访问。服务 Postman 的全球开发者社区，意味着需求波动大、对延迟敏感，还会突然出现流量尖峰。借助 Amazon Bedrock，Postman 不必自己运维模型服务基础设施就能扩展这一生产负载，同时在模型选择上保留灵活性，并对吞吐量、地理处理范围和成本保持控制。图 2 先给出生产架构的整体视图，后续几节再逐一检视其中的组件。

![Postman Agent Mode 架构：客户端工具、智能体编排、按需构建的上下文与 Amazon Bedrock 推理组合在一起](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/06/ML-21683-2.png)

图 2：Postman Agent Mode 把客户端工具、智能体编排、按需构建的上下文与 Amazon Bedrock 模型推理组合在一起。工具按任务划定范围，修改应用状态的操作仍然需要用户批准

人工监督本身就是生产设计的一部分。执行会修改应用状态的操作之前，Agent Mode 要求用户先批准。Postman 还会按任务收窄可用工具的范围、挑选按需构建的上下文，并应用依模型而定的数据保留设置。这些控制减少了误操作和不必要的数据暴露，但生产环境的测试与监控依然少不了。作为一项负责任 AI 控制措施，Postman 使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/)，在个人身份信息进入底层大语言模型（LLM）之前把它脱敏。企业管理员可以在 Agent Mode 的 Guardrails 设置里开启这一功能。

## 应对工具泛滥

在 Agent Mode 里，工具定义了智能体在 Postman 内部如何行动。早期团队倾向于高度原子化的工具：打开一个请求、改一个字段、取某一条元数据这类小而精确的动作。这套做法在早期迭代中保证了正确性和可控性，但也暴露出几个问题。

现实中许多工作流都需要一长串工具调用。即使每一步都很快，整体感受仍然慢，因为每个动作都要先返回给模型，下一个才能开始。用户眼看着智能体一步步做完他们在心里当作同一件事的操作。

按 Postman 的测试，可见工具集一旦超过约 40 个工具，工具选择错误就开始增多。智能体会去调用并不存在的工具、在 schema 有效的情况下传错参数，或者选中看起来语义合理、放到上下文里却错了的工具。更大或更新的模型能减少这类行为，但没能消除。

工具集超过某个规模之后，继续暴露更多工具反而会削弱智能体的表现。现有架构按需要和上下文来挑选工具，并把各个执行线程隔离开，模型只看到与当前任务相关的工具。图 3 展示了这个动态选择过程。

![根智能体查询工具嵌入的向量库，把 170 多个工具收窄到约 15 个，再交给一个上下文隔离的子智能体](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/06/ML-21683-3.png)

图 3：根智能体查询工具嵌入的向量库，把 170 多个工具收窄到与该请求相关的约 15 个，随后把这些工具交给一个上下文隔离的子智能体，模型因此只看到任务所需的工具

一个更隐蔽的问题是，许多客户端 API 与界面状态存在隐式耦合：修改请求的工具需要某些元素处于打开状态，而另一些工具又会顺带打开新标签页。智能体要读一个请求，就得先打开它所在的标签页，这是在模仿界面交互，而不是对数据推理。Postman 正在主动把工具与标签页解耦，它的 [Native Git](https://www.postman.com/product/native-git/)功能大量用上了这套做法。例如 [Agent Mode](https://learning.postman.com/docs/postman-ai-developer-tools/agent-mode/)现在已经能在后台发送请求，不需要打开标签页，只是仍然要用户批准。

**构建者要点：**把工具目录当作上下文预算的一部分。按任务动态划定暴露给模型的工具范围，并把「智能体能做什么」和「界面恰好开着什么」解耦。

## 开放基于 schema 的读取

对 API Catalog 这类产品，Postman 把多个窄视图合并成一个查询工具。这些产品暴露的是结构化数据，例如服务可用时长、测试结果，以及众多服务的端点响应时间。

拿到底层 ClickHouse 表的 schema 后，智能体可以自行生成带 join 和 WHERE 子句的复杂查询。这大幅降低了回答一个分析问题所需的工具种类数：

```
SELECT toString(service_id) AS service_id,
    countMerge(total_events_state) AS total_requests,
    countMerge(error_events_state) AS total_errors,
    round(countMerge(error_events_state) * 100.0
        / countMerge(total_events_state), 4) AS error_rate_pct,
    avgMerge(avg_latency_state) AS avg_latency_ms,
    quantileMerge(0.95)(p95_latency_state) AS p95_latency_ms
FROM http_events_summary_1d
WHERE service_id IN ('...list of service IDs')
    AND bucket_1d >= today() - 7
GROUP BY service_id
HAVING p95_latency_ms < 100
    AND total_requests > 0
ORDER BY error_rate_pct DESC;
```

采用这种方式，工程重心就从*为每个问题写一个工具*转成了*把数据模型一次做好*。智能体能生成的查询种类，远比团队当初能一条条列成独立工具的要多。

**构建者要点：**在有结构化良好的数据处，把带 schema 感知的查询引擎读取权限交给智能体，而不是铺一堆单一用途的读取工具。这是用数据建模换工具数量，换来的是更好的扩展曲线。

## 上下文才是真正的瓶颈

Postman 一开始以为最大的阻碍是*工具*不够。实际跑下来，*上下文*缺失或不完全，比能力缺失造成的失败更多。

上下文，是智能体对用户当前在 Postman 中的位置、哪些实体处于活动状态、已经确立了哪些状态的理解。上下文一旦有误或缺失，工具再对也不管用。图 4 区分了供给智能体的两类上下文。

![自动收集的背景上下文，与经按实体处理器转发的用户所选上下文，两者共同供给智能体](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/06/ML-21683-4.png)

图 4：两类上下文共同供给智能体。宽而浅的背景上下文由系统自动收集，压缩后写入提示；深而聚焦的所选上下文由用户指定，再经由每种实体类型对应的专用处理器转发。每个处理器把这个实体提炼成智能体需要的信息

这是结构性的难题。11 年里，开发者和用户都学会了通过界面去找信息。要把这套认知为智能体重做一遍，就得反复迭代，判断每种工作流里什么是有用的、什么是噪声。直接把现有的界面数据模型序列化，并不能得到可用的上下文，因为那些对象是为渲染和数据传输设计的，不是为了推理。Postman 因此构建了专门的上下文处理器，把每个实体提炼成智能体需要知道的内容。

随着更多对象有了处理器，截断成了下一个问题。很多字段装的是长度不定的用户生成数据，包括请求描述、OpenAPI 规范和请求体。这些数据会把上下文窗口挤满。在规模化之下，精细管理上下文预算是必须的，它也支撑了团队正在探索的、由文件系统承接的方案：在那个方案里，每个处理器都不必再自带一套截断和展开逻辑。

**构建者要点：**别把用于渲染的数据模型直接喂给模型。按用途去做上下文处理器，并把上下文窗口当作一份稀缺、需要主动管理的预算。往往远未到模型上限，噪声就已经把信号挤了出去。

## 把各部分组装起来

Agent Mode 演进到后来，越来越清楚的一点是：系统必须聚合三个不同的组件，它们各自解决不同的问题。

- 客户端工具位于 Postman 应用内，代表智能体最终能执行的动作，例如打开请求、修改设置、运行 collection、查看认证配置。Agent Mode 也会用服务端工具来实现网页搜索、智能体循环管理等功能，但多数工具作用于 Postman 应用本身。
- 通用智能体指令定义系统层面的行为，包括 Agent Mode 应该多主动、如何表达不确定性，以及它自带哪些基础产品知识。
- 知识库采用检索增强生成（RAG）方案。Postman 的产品面很广，涵盖多种请求协议、mock server、monitor、文档、API Network、工作区治理、变量、helper、代码生成、请求设置，以及 collection 运行。

把这些内容都编码进静态提示并不可行，而且对某一次查询来说，其中大部分并不相关。初始填充时，团队用 Postman 的 Learning Center 生成了针对各个功能的简短文章。运行时，Agent Mode 依据进来的查询和可用上下文挑选知识文章。例如用户选中一个 mock server，Agent Mode 就自动注入相关文章。这样智能体默认保持轻量，需要时才给出深度。知识库与应用一起演进，团队可以在交付新功能的同时把 Agent Mode 的文档一起发出去。

## 在 Amazon Bedrock 上运行 Agent Mode

前面描述的三个组件，最终都归结为同一个运行时动作：向基础模型（FM）发起一次推理调用。在 Postman 的规模上，流量是突发式的、由开发者驱动的。路由、缓存和地理处理控制，帮助 Postman 承接流量尖峰、管理推理成本，并满足不同负载各自的处理要求。Amazon Bedrock 在其中提供了四项最关键的能力。

### Claude 系列内的模型灵活性

Agent Mode 并不绑死在某一个模型上。通过 [Amazon Bedrock 模型推理 API](https://docs.aws.amazon.com/bedrock/latest/APIReference/welcome.html)，Postman 可以访问受支持的 Anthropic Claude 模型，并把每种负载路由到合适的模型：较快的模型服务量大、对延迟敏感的交互，较大的模型处理质量比成本更要紧的复杂推理。在受支持的 Claude 模型之间切换，主要是改配置，而不是做一次新的集成。这份灵活性直接支撑了前文的工具泛滥和上下文两个难题。在 Postman 的测试里，更新、更大的模型减少了工具幻觉，而 Postman 采用受支持的模型时不必重建集成。参见 [Amazon Bedrock 按 AWS 区域划分的受支持模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

### 跨区域推理带来高吞吐量

开发者的流量起伏很大，只在一个 AWS 区域按峰值需求备容量代价高昂。Agent Mode 使用 [Amazon Bedrock 跨区域推理](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)，在推理配置文件所定义的目标区域之间自动路由请求。运行时，应用把选定的推理配置文件 ID 或 Amazon Resource Name（ARN）作为 modelId 传给 Converse 或 InvokeModel。配置文件、适用的 AWS Identity and Access Management（IAM）与服务控制策略，以及配额，都必须放行 Bedrock 可能选中的每一个目标区域。

- [地理推理配置文件](https://docs.aws.amazon.com/bedrock/latest/userguide/geographic-cross-region-inference.html)只在某个既定地理范围内受支持的区域之间路由请求，例如美国或欧盟。这一选项既提高了吞吐量，又把处理限定在设定好的地理边界内。
- 全球推理配置文件可以在全球受支持的目标区域之间路由请求，在流量尖峰时提供更多吞吐量。只有在负载不要求把处理限制在特定地理边界内时，它才合适。

Postman 按负载选择推理配置文件：要最大可用吞吐量就用全球配置文件，处理必须留在某个地理范围内就用地理配置文件。这个选择显式体现在每次 Bedrock 推理请求所用的 modelId 上。

```
# Schematic Converse request
response = bedrock_runtime.converse(
    modelId="<geographic-inference-profile-id-or-arn>",
    messages=messages,
    system=system_blocks,
)
```

### 数据驻留与企业级控制

对企业客户来说，允许处理的地理范围可能和吞吐量同样重要。地理推理配置文件把 Bedrock 的路由限制在所选地理范围内该配置文件支持的目标区域。但这并不意味着推理跑在 Postman 自己的 AWS 环境里。Amazon Bedrock 在该配置文件符合条件的 AWS 区域中处理请求，数据在传输和静态存储时都加密。AWS 说明 Bedrock 不会用提示和补全内容训练 AWS 的模型，也不会把它们分发给第三方。Postman 已为受支持的 Agent Mode 模型配置了零数据保留，把 data_retention_mode 设为 none。可用性与行为依模型而定，所以每个生产模型都要对照现行的 [Amazon Bedrock 数据保护与保留文档](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html)核实一遍。

### 用提示缓存控制成本

生产环境的智能体每一轮都会重发大量稳定不变的上下文，包括系统指令、通用智能体行为、核心工具集、选中的知识内容，以及对话上下文。每次请求都重新处理这段没有变化的前缀，带来的是本可避免的延迟和成本。

Agent Mode 使用 [Amazon Bedrock 提示缓存](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)来复用稳定的提示前缀。几乎不变的核心部分——系统提示、智能体指令和核心工具定义——用一小时的缓存检查点；变化较多的上下文用五分钟检查点，命中缓存时刷新。Bedrock 要求生命周期更长的检查点出现在更短的那个之前。短的一档适合交互式会话，因为闲置的上下文会到期；一小时那一档则可以把较高的缓存写入价格摊到很多次读取上。缓存收益与支持的 TTL 取决于所选模型。团队可以通过 cacheReadInputTokens 和 cacheWriteInputTokens 这两个用量字段验证行为，并针对自己的负载测量首个 token 的耗时。

```
# Schematic cache checkpoints in Converse content blocks
{"cachePoint": {"type": "default", "ttl": "1h"}}  # stable core
{"cachePoint": {"type": "default", "ttl": "5m"}}  # variable layer
```

**构建者要点：**把推理看成路由加缓存的问题，而不只是选模型的决定。按负载选 Claude 模型，挑合适的跨区域推理配置文件，再按每一层上下文的变化频率用相应的 TTL 缓存稳定的提示前缀。

## 在生产环境扩展智能体的最佳实践

从 Postman 的历程中提炼，供在 Amazon Bedrock 上构建的团队参考：

- **像管 token 一样管工具的预算。**按任务动态选择暴露出去的工具。Postman 的测试显示，可见工具集变大后，工具选择的错误随之增多。
- **优先用带 schema 感知的读取，而不是堆工具。**把数据建模做好，让智能体自己去查询。
- **把智能体动作与界面状态解耦。**如果一个工具需要某个标签页开着，那智能体是在界面里找路，而不是直接对数据推理。
- **认真做上下文工程。**专门构建的上下文处理器，胜过每次都去序列化渲染模型。
- **把上下文窗口当作稀缺资源来管理。**截断与展开策略是头等的设计问题，不是事后补的环节。
- **文档和功能一起发布。**RAG 知识库只有跟产品同步演进才有用。
- **在 Bedrock 上做好路由和缓存。**让每种负载对上合适的 Claude 模型，按吞吐量和地理要求选择跨区域推理，并对稳定的提示前缀做分层缓存。

## 结论

构建 Agent Mode 让 Postman 直面大语言模型能力与成熟产品结构之间的落差：界面假设、紧耦合的客户端、不断膨胀的工具目录，以及散落在文档和团队里的知识。动态工具选择、基于 schema 的读取，以及刻意为之的上下文工程，在 [Postman 开发者社区](https://www.postman.com/company/about-postman/)这样的规模上成了可复用的模式。[Amazon Bedrock](https://aws.amazon.com/bedrock/)提供了托管的模型访问、[跨区域推理](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)、依模型而定的[保留控制](https://docs.aws.amazon.com/bedrock/latest/userguide/data-retention.html)以及[提示缓存](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)，支撑起这套生产架构。

无论你是在做第一个智能体，还是在给已有的智能体扩容，这些模式都能帮团队避开智能体集成与扩展上的常见问题。

想深入了解，请看 [Amazon Bedrock 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html)，其中包含[跨区域推理](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)、[提示缓存](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)与[数据保护和保留](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html)的指南。相关的实现指南可在 AWS Machine Learning Blog 上读到：[在 Amazon Bedrock 上有效使用提示缓存](https://aws.amazon.com/blogs/machine-learning/effectively-use-prompt-caching-on-amazon-bedrock/)和 [Amazon Bedrock 宣布推出全球跨区域推理以提升吞吐量](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-announces-global-cross-region-inference-for-increased-throughput/)。要了解产品本身，见 [Postman Agent Mode 文档](https://learning.postman.com/docs/getting-started/basics/about-agent-mode/)。
