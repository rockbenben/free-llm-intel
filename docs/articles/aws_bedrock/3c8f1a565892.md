## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# Postman 如何在 Amazon Bedrock 上为 4000 万开发者运行代理模式

为演示构建 AI 代理和为 [4000 万开发人员](https://www.postman.com/company/about-postman/) 运行一个 AI 代理是不同的工程问题。 Postman 着手构建 [代理模式](https://learning.postman.com/docs/postman-ai-developer-tools/agent-mode/)，这是一种跨 [API 测试](https://learning.postman.com/docs/sending-requests/response-data/test-responses/) 工作的 AI 原生方式， [文档](https://learning.postman.com/docs/publishing-your-api/documenting-your-api/)、发现和实施。该团队预计模型质量和及时设计是最难的问题。更深层次的挑战来自于将代理集成到成熟的产品中，该产品具有多年的界面驱动假设、广泛的表面积和专门的概念。

在这篇文章中，Postman 和 AWS 描述了在使成熟的产品对 AI 代理来说易于理解时出现的架构模式。这些模式包括控制工具蔓延、公开基于模式的读取以及将上下文而不是功能视为主要瓶颈。

我们还解释了[代理模式](https://learning.postman.com/docs/getting-started/basics/about-agent-mode/)如何使用[Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html)来实现模型灵活性、地理范围的跨区域推理、模型相关的零数据保留和多层提示缓存。总之，这些经验教训可以帮助团队将生产代理转移到原型之外。

## 为什么Postman建立代理模式

[代理模式](https://learning.postman.com/docs/getting-started/basics/about-agent-mode/) 是 Postman 的门户，用于以 AI 原生方式跨测试、文档、发现和实施使用产品。 Postman 已经发展了 11 年，开发人员和用户学会了通过扩展侧边栏、检查选项卡和打开请求来通过界面定位信息。重新设计代理的意识，在产品的 API、用户体验和产品知识的分布中提出了结构性假设。座席通过数据进行推理，而不是在屏幕上导航。图 1 说明了代理模式如何直接针对应用程序工作。

图 1：代理模式直接针对 Postman 应用程序工作。在此示例中，它打开拉取请求并建议后续步骤，而无需用户浏览界面

[代理模式](https://learning.postman.com/docs/getting-started/basics/about-agent-mode/) 在 [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html) 上运行，它提供对代理背后的基础模型的托管访问。支持 Postman 的全球开发者社区会产生可变的、对延迟敏感的需求以及急剧的流量爆发。借助 Amazon Bedrock，Postman 可以扩展此生产工作负载，而无需运行自己的模型服务基础设施，同时保留模型选择的灵活性以及对吞吐量、地理处理和成本的控制。在下面的部分检查其组件之前，图 2 提供了生产架构的高级视图。

![结合了客户端工具、代理编排、专用上下文和 Amazon Bedrock 推理的 Postman 代理模式架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/06/ML-21683-2.png)

图 2：Postman 代理模式结合了客户端工具、代理编排、专用上下文和 Amazon Bedrock 模型推理。工具的范围适用于每个任务，用户批准仍然是修改应用程序状态的操作的一部分

人工监督是生产设计的一部分。代理模式需要用户批准才能执行修改应用程序状态的操作。 Postman 还会根据任务确定可用工具的范围，选择专门构建的上下文，并应用依赖于模型的数据保留设置。这些控制措施减少了意外操作和不必要的数据暴露，同时生产测试和监控仍然是必要的。作为负责任的 AI 控件，Postman 使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 在个人身份信息到达底层大语言模型 (LLM) 之前对其进行编辑。企业管理员可以在代理模式的护栏设置中打开此功能。

## 处理工具蔓延

在代理模式下，工具定义代理在 Postman 内的行为方式。早期，团队倾向于高度原子化的工具：小而精确的操作，例如打开请求、更新一个字段或获取特定的元数据。这种方法支持早期迭代的正确性和控制，但也暴露了一些问题。

许多现实世界的工作流程需要长序列的工具调用。即使每一步都很快，整体体验也会感觉很慢，因为每一个动作都必须返回模型才能开始下一个动作。用户观看代理逐步执行他们在心里分组为单个操作的操作。

在 Postman 的测试中，一旦可见工具集超过大约 40 个工具，工具选择错误就会增加。代理可以调用​​不存在的工具，尽管模式有效但传递错误的参数，或者选择语义上看似合理但在上下文中错误的工具。更大或更新的型号减少了这种行为，但没有消除它。

超过一定的工具集大小后，暴露更多工具可能会降低代理效率。当前的架构根据需要和上下文选择工具并隔离各个执行线程。该模型仅看到与当前任务相关的工具。图 3 说明了这个动态选择过程。

![根代理通过查询工具嵌入的向量数据库，将 170 多个工具缩小到大约 15 个，然后将它们交给上下文隔离的工具子代理](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/06/ML-21683-3.png)

图 3：根代理查询工具嵌入的向量数据库，并将 170 多个工具缩小到与请求相关的大约 15 个。然后，它将这些工具交给上下文隔离的子代理，因此模型只能看到任务所需的工具

一个更微妙的问题是许多客户端 API 隐式耦合到接口状态。修改请求的工具需要打开某些元素，而其他工具会打开新选项卡作为副作用。代理必须打开请求选项卡才能读取它，模仿界面交互而不是推理数据。 Postman 正在积极地将工具与选项卡解耦，其 [Native Git](https://www.postman.com/product/native-git/) 功能广泛使用了这种方法。例如，[代理模式](https://learning.postman.com/docs/postman-ai-developer-tools/agent-mode/)现在可以在后台发送请求，而无需打开选项卡，但仍需要用户批准。

**构建者要点：** 将您的工具目录视为上下文预算的一部分。动态调整每个任务向模型公开的工具的范围，并将“代理可以做什么”与“UI 碰巧打开了什么”分离。

## 公开基于模式的读取

对于 API Catalog 等产品，Postman 将多个窄视图合并到一个查询工具中。这些产品公开结构化数据，例如跨许多服务的服务正常运行时间、测试结果和端点响应时间。

给定基础 ClickHouse 表的架构，代理可以使用联接和 WHERE 子句生成复杂的查询。这大大减少了回答分析问题所需的不同工具的数量：
```
SELECT toString(service_id) AS service_id,
    countMerge(total_events_state) AS total_requests,
    countMerge(error_events_state) AS total_errors,
    round(countMerge(error_events_state) * 100.0
        / countMerge(total_events_state), 4) AS error_rate_pct,
    avgMerge(avg_latency_state) AS avg_latency_ms,
    quantileMerge(0.95)(p95_latency_state) AS p95_latency_ms
FROM http_events_summary_1d
WHERE service_id IN ('...list of service IDs')
    AND bucket_1d >= today() - 7
GROUP BY service_id
HAVING p95_latency_ms < 100
    AND total_requests > 0
ORDER BY error_rate_pct DESC;
```
通过这种方法，工程工作从“为每个问题构建一个工具”转变为“一次很好地对数据进行建模”。然后，代理可以生成比团队作为单独工具列举的要广泛得多的查询。

**构建器要点：** 如果您拥有结构良好的数据，请为代理提供对查询引擎的模式感知读取访问权限，而不是使用大量单一用途的读取工具。您可以用工具数量换取数据建模，从而产生更好的缩放曲线。

## 上下文是真正的瓶颈

邮递员最初认为缺少“工具”将是最大的障碍。在实践中，缺失或不完整的“上下文”导致的失败比缺失功能更多。

上下文是代理对用户在 Postman 中的位置、哪些实体处于活动状态以及已经建立的状态的理解。当上下文错误或不存在时，即使是正确的工具也会变得无效。图 4 区分了提供给代理的两种形式的上下文。

![自动收集的后台上下文和通过每个实体处理程序路由的用户选择的上下文，两者都提供给代理](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/06/ML-21683-4.png)

图 4：代理提供两种上下文。广泛、浅层的背景上下文会自动收集并缩小以供提示。深度、集中的选定上下文由用户选择，并通过每个实体类型的专用处理程序进行路由。每个处理程序将实体提取为代理所需的信息

挑战是结构性的。 11 年来，开发人员和用户学会了通过界面查找信息。重新设计代理的意识需要多次迭代才能确定对每个工作流程来说什么是重要的以及什么是噪音。序列化现有的接口数据模型不会产生有用的上下文，因为这些对象是为渲染和数据传输而设计的，而不是推理。因此，Postman 构建了专用的上下文处理程序，将每个实体提炼为代理需要知道的内容。

随着越来越多的对象获得处理程序，截断成为下一个问题。许多字段包含开放式用户生成的数据，包括请求描述、OpenAPI 规范和请求负载。这些数据可能会挤满上下文窗口。仔细管理上下文预算对于规模来说至关重要，并且支持团队正在探索的文件系统支持的方法，其中每个处理程序不需要自定义截断和扩展逻辑。

**构建器要点：** 不要向模型提供渲染数据模型。构建有目的的上下文处理程序，并将上下文窗口视为稀缺的、主动管理的预算。早在模型达到极限之前，噪声就挤占了信号。

## 将它们放在一起

随着代理模式的发展，很明显系统必须聚合三个不同的组件，每个组件解决不同的问题。

- 客户端工具位于 Postman 应用程序中，代表代理可以采取的最终操作，例如打开请求、修改设置、运行集合和检查身份验证。代理模式还使用服务器端工具来实现 Web 搜索和代理循环管理等功能，但大多数工具在 Postman 应用程序上运行。
- 通用代理指令定义系统级行为，包括代理模式应该如何主动、如何传达不确定性以及它携带哪些基线产品知识。
- 知识库使用检索增强生成（RAG）方法。 Postman 拥有庞大的产品面，其中包括多个请求协议、模拟服务器、监视器、文档、API 网络、工作区治理、变量、帮助程序、代码生成、请求设置和收集运行。

在静态提示中对所有这些进行编码是不可行的，并且其中大部分与给定的查询无关。对于初始播种，该团队使用 Postman 的学习中心来生成简洁的特定功能文章。在运行时，代理模式根据传入查询和可用上下文选择知识文章。例如，当用户选择模拟服务器时，代理模式会自动注入相关文章。默认情况下，这使代理保持轻量级，同时在需要时提供深度。知识库随着应用程序的发展而发展，因此团队可以发布具有新功能的代理模式文档。

## 在 Amazon Bedrock 上运行代理模式

前面描述的三个组件解析为相同的运行时操作：对基础模型 (FM) 的推理调用。以 Postman 的规模来看，流量是突发性的并且是由开发人员驱动的。路由、缓存和地理处理控制可帮助 Postman 适应流量突发、管理推理成本并满足特定于工作负载的处理要求。 Amazon Bedrock 提供了四种最重要的功能。

### 克劳德家族的模型灵活性

代理模式不依赖于一种模型。通过 [Amazon Bedrock 模型推理 API](https://docs.aws.amazon.com/bedrock/latest/APIReference/welcome.html)，Postman 可以访问支持的 Anthropic Claude 模型并将每个工作负载路由到适当的模型。更快的模型可以服务于大容量、延迟敏感的交互，而更大的模型可以处理复杂的推理，其中质量比成本更重要。在受支持的 Claude 模型之间移动主要是配置更改，而不是新的集成。这种灵活性直接支持前面描述的工具蔓延和环境挑战。在Postman的测试中，更新和更大的模型减少了工具幻觉，并且Postman可以采用支持的模型而无需重建集成。请参阅 [Amazon Bedrock 中 AWS 区域支持的型号](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

### 高吞吐量的跨区域推理

开发人员流量激增，在一个 AWS 区域中针对峰值需求进行预置可能成本高昂。代理模式使用 [Amazon Bedrock 跨区域推理](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html) 在推理配置文件定义的目标区域之间自动路由请求。在运行时，应用程序将选定的推理配置文件 ID 或 Amazon 资源名称 (ARN) 作为 Converse 或 InvokeModel 中的 modelId 传递。配置文件、适用的 AWS Identity and Access Management (IAM) 和服务控制策略以及配额必须允许 Bedrock 可能选择的每个目标区域。

- [地理推理配置文件](https://docs.aws.amazon.com/bedrock/latest/userguide/geographic-cross-region-inference.html) 仅在定义的地理范围内的受支持区域（例如美国或欧盟）之间路由请求。此选项将增加的吞吐量与配置的地理处理边界相结合。
- 全局推理配置文件可以在全球受支持的目标区域之间路由请求，以在流量爆发期间提供额外的吞吐量。仅当工作负载不需要地理限制的处理边界时，它们才适用。

Postman 可以为每个工作负载选择推理配置文件：最大可用吞吐量的全局配置文件或当处理必须保留在配置文件定义的地理范围内时的地理配置文件。此选择在用于每个 Bedrock 推理请求的 modelId 中是明确的。
```
# Schematic Converse request
response = bedrock_runtime.converse(
    modelId="<geographic-inference-profile-id-or-arn>",
    messages=messages,
    system=system_blocks,
)
```
### 数据驻留和企业控制

对于企业客户来说，允许的处理地理位置与吞吐量一样重要。地理推理配置文件将 Bedrock 路由限制到所选地理位置内配置文件支持的目标区域。这并不意味着推理在 Postman 自己的 AWS 环境中运行。 Amazon Bedrock 在符合条件的 AWS 区域中处理该配置文件的请求，并在传输过程中和静态时对数据进行加密。 AWS 声明 Bedrock 不会使用提示和补全来训练 AWS 模型或将其分发给第三方。对于支持的代理模式模型，Postman 已配置零数据保留，并将 data_retention_mode 设置为 none。可用性和行为取决于模型，因此必须根据当前的 [Amazon Bedrock 数据保护和保留文档](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html) 检查每个生产模型。

### 提示缓存以控制成本

生产代理在每一回合重新发送大量稳定的上下文，包括系统指令、通用代理行为、核心工具集、选定的知识和对话上下文。对每个请求重新处理未更改的前缀会增加可避免的延迟和成本。

代理模式使用 [Amazon Bedrock 提示缓存](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html) 来重用稳定的提示前缀。近乎不可变的核心，包括系统提示、代理指令和核心工具定义，使用一小时的缓存检查点。更多变量上下文使用五分钟检查点，在缓存命中时刷新。基岩要求寿命较长的检查点出现在寿命较短的检查点之前。较短的层适合交互式会话，因为空闲上下文会过期，而一小时层可以在多次读取中分摊其较高的缓存写入价格。缓存优势和支持的 TTL 取决于所选型号。团队可以通过cacheReadInputTokens和cacheWriteInputTokens使用字段验证行为，并测量自己的工作负载的第一个令牌的时间。
```
# Schematic cache checkpoints in Converse content blocks
{"cachePoint": {"type": "default", "ttl": "1h"}}  # stable core
{"cachePoint": {"type": "default", "ttl": "5m"}}  # variable layer
```
**构建器要点：** 将推理视为路由和缓存问题，而不仅仅是模型选择决策。根据工作负载选择 Claude 模型，选择适当的跨区域推理配置文件，并缓存稳定的提示前缀，其 TTL 与每层更改的频率相匹配。

## 生产中阻垢剂的最佳实践

对于在 Amazon Bedrock 上工作的构建者来说，从 Postman 的旅程中提炼出来：

- **像令牌一样仔细地预算工具。**动态选择每个任务公开的工具。在 Postman 的测试中，随着可见工具集变大，工具选择错误也会增加。
- **优先选择模式感知读取而不是工具扩散。** 对数据进行良好建模并让代理对其进行查询。
- **将代理操作与界面状态解耦。** 如果工具需要打开选项卡，则代理将在界面中导航，而不是直接通过数据进行推理。
- **故意设计上下文。** 专门构建的上下文处理程序每​​次都胜过序列化渲染模型。
- **将上下文窗口作为稀缺资源进行管理。** 截断和扩展策略是一流的设计问题，而不是事后的想法。
- **发布具有功能的文档。** RAG 知识库只有在与产品同步发展时才保持有用。
- **在 Bedrock 上进行路由和缓存。** 将每个工作负载与适当的 Claude 模型相匹配，根据吞吐量和地理要求选择跨区域推理，并将分层缓存应用于稳定的提示前缀。

＃＃ 结论

构建代理模式要求 Postman 面对大型语言模型功能与成熟产品结构之间的差距：接口假设、耦合的客户端、庞大的工具目录以及分布在文档和团队中的知识。动态工具选择、基于模式的读取和深思熟虑的上下文工程在 [Postman 开发者社区](https://www.postman.com/company/about-postman/) 范围内作为可重复的模式出现。 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 提供托管模型访问、[跨区域推理](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)、模型相关的[保留控制](https://docs.aws.amazon.com/bedrock/latest/userguide/data-retention.html) 和 [提示支持生产架构的缓存](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)。

无论您是构建第一个代理还是扩展现有代理，这些模式都可以帮助团队避免常见的代理集成和扩展挑战。
