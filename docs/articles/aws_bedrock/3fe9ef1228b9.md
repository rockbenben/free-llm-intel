# TP ICAP 如何借助 Amazon Bedrock 把 CRM 数据转化为实时洞察

*本文与 TP ICAP 的 Ross Ashworth 合写。*

能否从客户关系管理（CRM）系统以及海量会议记录中快速提炼洞察，可能决定了是抓住机会还是彻底错失。[TP ICAP](https://tpicap.com/tpicap/) 就面临这一挑战，其 CRM 中存有数千条供应商会议记录。借助 [Amazon Bedrock](https://aws.amazon.com/bedrock/)，其 Innovation Lab 构建了一套可投产的解决方案，结合检索增强生成（RAG）与 text-to-SQL 方法提供 AI 驱动的洞察，把数小时的人工分析压缩到数秒。

本文介绍 TP ICAP 如何使用 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 和 [Amazon Bedrock Evaluations](https://aws.amazon.com/bedrock/evaluations/) 构建 ClientIQ——一套具备增强安全特性的企业级解决方案，用 AI 提炼 CRM 洞察，立即交付业务价值。

## 挑战

多年来，TP ICAP 在其 CRM 系统中积累了数万条供应商会议记录。这些记录包含丰富的定性信息，以及关于产品供给、集成讨论、关系洞察和战略方向的细节。然而，这些数据并未被充分利用，业务用户要花数小时在记录中人工检索，他们知道信息存在，却无法高效定位。TP ICAP Innovation Lab 着手让这些信息对内部相关方更易获取、更可行动、更快得到摘要。他们的方案需要快速呈现相关信息、保持准确，并维持恰当的上下文。

## ClientIQ：TP ICAP 的自定义 CRM 助手

借助 ClientIQ，用户可以通过自然语言查询与其 Salesforce 会议数据交互。例如：

- 用平实的自然语言就会议数据提问，例如“我们怎样才能改善与客户的关系？”、“客户如何看待我们的解决方案？”或“客户受到了英国脱欧怎样的影响？”
- 通过追问来细化查询。
- 应用过滤器，把模型回答限定在特定时间段。
- 通过指向具体 Salesforce 记录的链接直接访问源文档。

ClientIQ 提供全面的回答，同时通过引用源数据和指向原始 Salesforce 记录的直接链接来保持完全可追溯。会话式界面支持自然的对话流，用户可以细化并探索查询而无需从头开始。下面的截图展示了交互示例（本文中的示例使用虚构数据和虚构公司 AnyCompany 进行演示）。

![带问答的 Client IQ 界面](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/30/image-1-26.png)

为完成用户请求，ClientIQ 会执行多项任务：

- 它使用大语言模型（LLM）分析每个用户查询，以确定最优处理路径。
- 它把请求路由到两条工作流之一：RAG 工作流，用于从非结构化会议记录中获取洞察。例如“过去 14 天内是否与 AnyCompany 讨论过话题 A？”SQL 生成工作流，用于通过查询结构化数据来回答分析型问题。例如“给我一份过去 4 周各区域会议数量的报告”。
- 随后它以自然语言生成回答。
- ClientIQ 遵守既有的权限边界和访问控制，帮助确保用户只能访问其获授权的数据。例如，如果某用户在 CRM 系统中只能访问其所属区域的客户账户，ClientIQ 就只返回这些账户的信息。

## 解决方案概述

尽管团队考虑过使用其 CRM 内置的 AI 助手，但他们最终选择开发一套更定制化、更具成本效益的解决方案，以精确匹配自身需求。他们与 AWS 合作，构建了一套由 Amazon Bedrock 驱动的企业级解决方案。借助 Amazon Bedrock，TP ICAP 评估并为本用例选出了最佳模型，并在数周而非数月内构建出可投产的 RAG 方案，无需管理底层基础设施。他们具体使用了以下 Amazon Bedrock 托管能力：

- **Amazon Bedrock 基础模型** – Amazon Bedrock 提供来自 Anthropic、Meta、Mistral AI 和 Amazon 等提供商的一系列基础模型（FM），并可通过单一 API 访问。TP ICAP 针对不同任务试验了不同模型，并在延迟、性能和成本之间权衡，为每项任务选出最佳模型。例如，他们使用 [Anthropic 的 Claude 3.5 Sonnet](https://aws.amazon.com/bedrock/anthropic/) 完成分类任务，使用 [Amazon Nova Pro](https://aws.amazon.com/ai/generative-ai/nova) 完成 text-to-SQL 生成。由于 Amazon Bedrock 是全托管的，他们无需花时间搭建用于托管这些模型的基础设施，从而缩短了交付时间。
- **Amazon Bedrock Knowledge Bases** – 这些基础模型需要访问 TP ICAP 的 Salesforce 系统中的信息，才能给出准确、相关的回答。TP ICAP 使用 Amazon Bedrock Knowledge Bases 实现 RAG——一种通过引入组织知识源中的相关数据来增强生成式 AI 回答的技术。Amazon Bedrock Knowledge Bases 是一项全托管的 RAG 能力，内置会话上下文管理和来源归属（source attribution）。最终实现既能给出精确、与上下文相关的回答，又能保持对源文档的可追溯性。
- **Amazon Bedrock Evaluations** – 为保证质量与性能的一致性，团队希望实现自动化评估。通过在开发环境和 CI/CD pipeline 中使用 Amazon Bedrock Evaluations 以及面向 Amazon Bedrock Knowledge Bases 的 [RAG 评估](https://aws.amazon.com/blogs/aws/new-rag-evaluation-and-llm-as-a-judge-capabilities-in-amazon-bedrock/)工具，他们得以以接近人工的水准评估和比较基础模型。他们评估了多个维度，包括回答的准确性、相关性和完整性，以及 RAG 检索的质量。

自上线以来，该方案可高效扩展到分析数千条回答，并促进围绕模型与推理参数选择、RAG 配置的数据驱动决策。下图展示了该解决方案的架构。

![结合 Lambda、DynamoDB、S3 与 Bedrock 的 CRM 解决方案 AWS 架构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/30/image-2-22.png)

用户查询工作流包含以下步骤：

- 用户通过一个前端 React 应用登录，该应用托管在 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）存储桶中，且仅能通过内网专用的 [Application Load Balancer](https://aws.amazon.com/elasticloadbalancing/application-load-balancer/) 在组织网络内访问。
- 登录后，客户端与 [Amazon API Gateway](https://aws.amazon.com/api-gateway) 之间建立 WebSocket 连接，以实现实时双向通信。
- 连接建立后，会调用一个 [AWS Lambda](https://aws.amazon.com/lambda) 函数（连接处理器），它处理 payload、把追踪数据记录到 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/)，并把请求数据发布到 [Amazon Simple Notification Service](https://aws.amazon.com/sns)（Amazon SNS）主题以供下游处理。
- 面向不同任务类型的 Lambda 函数从 [Amazon Simple Queue Service](https://aws.amazon.com/sqs/)（Amazon SQS）消费消息，以实现可扩展、事件驱动的处理。
- 这些 Lambda 函数使用 Amazon Bedrock 基础模型判断某个问题是通过查询 [Amazon Athena](https://aws.amazon.com/athena) 中的结构化数据来回答更好，还是从 Amazon Bedrock 知识库中检索信息来回答更好。
- 处理完成后，答案通过 API Gateway 复用既有 WebSocket 连接实时返回给用户。

## 数据摄取

ClientIQ 需要定期更新最新的 Salesforce 数据。TP ICAP 没有采用现成的方案，而是开发了一个自定义连接器，用以对接其高度定制的 Salesforce 实现，并把最新数据摄取到 Amazon S3。这种定制方式提供了处理其特定数据结构所需的灵活性，同时配置和维护仍然简单。该连接器使用 Salesforce Object Query Language（SOQL）查询来获取数据，每天运行，已被证明快速可靠。为在 RAG 检索工作流中优化结果质量，TP ICAP 在其 Amazon Bedrock 知识库中选择了自定义分块（chunking）方式。自定义分块发生在摄取过程中：连接器把数据拆成一个个独立的 CSV 文件，每次会议一个。这些文件还会使用 Amazon Nova Pro，按预定义列表自动打上相关话题标签，以进一步提升检索结果的质量。Amazon S3 中的最终输出包含每次会议一个 CSV 文件，以及一个对应的 JSON 元数据文件，其中包含日期、事业部、品牌和区域等标签。以下是相关元数据文件的示例：

```
{
"metadataAttributes": {
   "Tier": "Bronze",
   "Number_Date_of_Visit": 20171130,
   "Author_Region_C": "AMER",
   "Brand_C": "Credit",
   "Division_C": "Credit",
   "Visiting_City_C": "Chicago",
   "Client_Name": "AnyCompany”
   }
}
```

一旦数据在 Amazon S3 中可用，就会触发一个 [AWS Glue](https://aws.amazon.com/glue) 作业来填充 AWS Glue Data Catalog。之后 Athena 在查询 Amazon S3 数据时就会用到它。

Amazon Bedrock 知识库也与 Amazon S3 同步。在此过程中，每个 CSV 文件使用 [Amazon Titan v1](https://aws.amazon.com/bedrock/amazon-models/titan/) 转换为 embedding，并在向量存储 [Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/) 中建立索引。元数据同样被摄取，可用于在检索时过滤向量存储结果，如下一节所述。

## 提升 RAG 检索质量

在 RAG 查询工作流中，第一步是从向量存储中检索与用户查询相关的文档，并把它们作为上下文附加到查询上。查找相关文档的常见方式包括语义搜索、关键词搜索，或两者结合——称为混合搜索（hybrid search）。ClientIQ 使用混合搜索，先根据元数据过滤文档，再在过滤后的结果内做语义搜索。这种预过滤对被检索的文档提供了更多控制，并有助于消解查询歧义。例如，“找出在芝加哥与 AnyCompany 高管会议的记录”这样的问题，既可能指在芝加哥举行的、与 AnyCompany 任一事业部的会议，也可能指与总部位于芝加哥的 AnyCompany 事业部的会议。

TP ICAP 使用 Amazon Bedrock Knowledge Bases 中的[手动元数据过滤能力](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)，在其向量存储 OpenSearch Serverless 中实现混合搜索。采用这种方法，在上面的例子中，文档会先按 `Visiting_City_C` 预过滤为“Chicago”。随后执行语义搜索，找出包含 AnyCompany 高管会议记录的那些文档。最终输出包含在芝加哥举行的会议记录，这正是本例所期望的结果。团队还进一步借助 Amazon Bedrock Knowledge Bases 的[隐式元数据过滤](https://aws.amazon.com/about-aws/whats-new/2024/12/amazon-bedrock-knowledge-bases-auto-generated-query-filters-improved-retrieval/)增强了这一功能。该能力依靠 Amazon Bedrock 基础模型自动分析查询，理解哪些值可映射到元数据字段，并在执行检索前相应地重写查询。

最后，为进一步提升精度，用户可以在应用界面中手动指定过滤器，从而对搜索结果有更强的控制。这种多层过滤方式在保持快速检索的同时，显著改善了上下文和最终回答的准确性。

## 安全与访问控制

为在 ClientIQ 方案中延续 Salesforce 的细粒度权限模型，TP ICAP 实现了一套安全框架，把 Okta 的组声明（group claims）映射到具体的事业部和区域。用户登录时，其组声明会被附加到会话上。用户提问时，这些声明会根据所走的路径，自动与 Athena 或 OpenSearch Serverless 中的元数据字段匹配。

例如，如果某用户只有 EMEA 的信息访问权限，那么文档会自动按 EMEA 区域过滤。在 Athena 中，这是通过自动调整查询以加入该过滤器实现的。在 Amazon Bedrock Knowledge Bases 中，这是通过在混合搜索中引入额外的元数据字段过滤器 `region=EMEA` 实现的。下图对此做了标注。

![通过 Okta 实现 CRM 数据访问控制的简要工作流图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/30/image-3-26.png)

与用户权限标签不匹配的结果会被过滤掉，因此用户只能访问其获授权查看的数据。这一统一的安全模型保持 Salesforce 权限与 ClientIQ 访问控制之间的一致性，在多个解决方案之间维护数据治理。

该团队还为管理 Salesforce 权限的管理员开发了一个自定义管理界面，使其可以使用 Okta 的 API 在组中添加或移除用户。

## 自动化评估

Innovation Lab 团队在构建 RAG 应用时面临一个常见挑战：如何科学地度量和改进其性能。为此，他们制定了一套基于 Amazon Bedrock Evaluations 的评估策略，包含三个阶段：

- **构建 ground truth** – 他们与相关方和测试团队紧密合作，构建了一套 100 组具有代表性的问答对，模拟真实世界的交互。
- **RAG 评估** – 在开发环境中，他们通过程序在 Amazon Bedrock Evaluations 中触发 RAG 评估，处理 Amazon S3 中的 ground truth 数据并运行全面评估。他们评估了不同的分块策略（包括默认分块和自定义分块），测试了不同的 embedding 模型用于检索，并使用一系列推理参数比较了不同基础模型用于生成的表现。
- **指标驱动的优化** – 评估作业完成后，Amazon Bedrock 会生成包含指标、分数和洞察的评估报告。团队跟踪了检索侧的内容相关性与内容覆盖度，以及生成侧的责任 AI 指标，如回答相关性、事实准确性、检索精度和上下文理解能力。他们用评估报告做优化，直到达到性能目标。

下图展示了这一方式。

![使用 Amazon Bedrock 与 S3 的 AI 模型评估工作流](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/30/image-4-15.png)

此外，他们把 RAG 评估直接集成到持续集成与持续交付（CI/CD）pipeline 中，这样每次部署都会自动验证改动不会降低回答质量。这种自动化测试方式让团队有信心快速迭代，同时为生产方案维持一贯的高标准。

## 业务成果

ClientIQ 改变了 TP ICAP 从其 CRM 数据中提取价值的方式。在 20 名用户的初期上线之后，结果显示该方案使研究任务所花时间减少了 75%。相关方还反馈洞察质量有所提升，呈现出更全面、更有上下文的信息。在此成功的基础上，TP ICAP Innovation Lab 计划把 ClientIQ 演进为更智能的虚拟助手，能够跨多个企业系统处理更广泛、更复杂的任务。他们的使命始终如一：帮助业务中的技术与非技术团队借助生成式 AI 释放业务价值。

在本文中，我们探讨了 TP ICAP Innovation Lab 团队如何使用 Amazon Bedrock 基础模型、Amazon Bedrock Knowledge Bases 和 Amazon Bedrock Evaluations，把数千条会议记录从一项未被充分利用的资源转变为有价值的资产，在保持企业级安全与治理的同时加快洞察的产出速度。他们的成功表明，只要方法得当，企业可以在数周内落地可投产的 AI 方案并交付业务价值。要了解如何用 Amazon Bedrock 构建类似方案，请访问 [Amazon Bedrock 文档](https://aws.amazon.com/bedrock/)，或在 [AWS Financial Services Blog](https://aws.amazon.com/blogs/industries/category/industries/financial-services/) 上了解真实世界的成功案例与实现。
