# 使用 Amazon Bedrock 和 AWS Step Functions 编排生成式 AI 工作流

各行各业的公司都在借助[生成式 AI](https://aws.amazon.com/ai/generative-ai/) 的力量来应对各种用例。云服务提供商已经认识到，需要通过一次 API 调用来提供模型推理，从而显著简化 AI 在应用中的实现。尽管单次 API 调用可以处理简单的用例，但更复杂的用例可能需要多次调用并与其他服务集成。

本文讨论如何使用 [AWS Step Functions](https://aws.amazon.com/step-functions/) 高效协调多步生成式 AI 工作流，例如将对 [Amazon Bedrock](https://aws.amazon.com/bedrock) 的 API 调用并行化，以快速收集所提交问题清单的答案。我们还会谈及使用[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）来优化输出、提供额外一层精确度，以及通过 Step Functions 实现的其他可能集成。

## Amazon Bedrock 与 Step Functions 简介

Amazon Bedrock 是一项完全托管服务，通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、Meta、Mistral AI、Stability AI 和 Amazon 等领先 AI 公司的高性能基础模型（FM）供你选择，并附有一整套构建安全、隐私和负责任 AI 的生成式 AI 应用所需的能力。使用 Amazon Bedrock，你可以轻松试验和评估适合自己用例的顶级 FM，使用微调和检索增强生成（RAG）等技术借助自己的数据私下定制这些模型，并构建使用企业系统和数据源执行任务的 agent。由于 Amazon Bedrock 是无服务器的，你无需管理任何基础设施，并且可以使用你已熟悉的 AWS 服务，安全地将生成式 AI 能力集成并部署到应用中。

AWS Step Functions 是一项完全托管服务，让你可以更轻松地使用可视化工作流来协调分布式应用和微服务的各个组件。用各自执行独立功能的单个组件构建应用，有助于更轻松地扩展并更快地修改应用。Step Functions 是协调组件并按步骤执行应用各项功能的可靠方式。Step Functions 提供图形化控制台，可将应用的组件以一系列步骤的形式排列并可视化。这让构建和运行多步骤应用更加容易。Step Functions 会自动触发并跟踪每个步骤，并在出现错误时重试，因此你的应用会按顺序并如期执行。Step Functions 会记录每个步骤的状态，因此当确实出现问题时，你可以[更快地诊断和调试问题](https://aws.amazon.com/step-functions/features/)。你甚至无需编写代码就能更改和添加步骤，因此可以更轻松地演进应用并更快地创新。

## 使用 Map 功能编排并行任务

数组是编程中的基础数据结构，由有序的元素集合构成。在 Step Functions 的语境中，数组在实现并行处理和高效任务编排方面起着关键作用。Step Functions 中的 Map 功能使用数组来并发执行多个任务，显著提升涉及重复操作的工作流的性能和可扩展性。Step Functions 提供两种不同的映射策略来遍历数组：内联映射（inline mapping）和分布式映射（distributed mapping），各自有其优势和适用场景。

### 内联映射

内联 Map 功能允许你在单次 Step Functions 状态机执行中并行处理数组元素。当你需要处理的条目数量相对较少，且每个条目的处理都与其他条目相互独立时，这种方式很适合。
 具体做法如下：

- 你在 Step Functions 状态机中定义一个 Map 状态。
- Step Functions 遍历数组，并为每个元素并发运行指定的任务。
- 每次迭代的结果都会被收集起来，并可供状态机中的后续步骤使用。

内联映射对轻量级任务很高效，并有助于避免启动多次 Step Functions 执行，因为后者可能成本更高、更消耗资源。但也存在限制。使用内联映射时，输入只接受 JSON 载荷，工作流的执行历史不能超过 25,000 条，并发运行的 Map 迭代不能超过 40 个。

### 分布式映射

分布式 Map 功能面向这样的场景：需要处理很多条目，或者每个条目的处理都资源密集或耗时较长。Step Functions 不是在一次执行中处理所有条目，而是为数组中的每个条目启动一次单独的执行，让你可以并发处理存储在 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）中的大规模数据源，例如包含大量数据的单个 JSON 或 CSV 文件，甚至一大组 Amazon S3 对象。这种方式具有以下优势：

- **可扩展性** – 通过将处理分散到多次执行中，你可以更高效地扩展，并利用 Step Functions 内置的并行能力
- **故障隔离** – 如果某次执行失败，不会影响其他执行，从而提供更好的容错性和可靠性
- **资源管理** – 每次执行都可以分配各自的资源，有助于防止资源争用并提供一致的性能

不过，由于启动多次 Step Functions 执行存在额外开销，分布式映射可能带来额外成本。

### 如何选择映射方式

总而言之，内联映射适合条目数量相对较少的轻量级任务，而分布式映射更适合资源密集的任务，或需要更好的可扩展性和故障隔离的大型数据集。两种映射策略之间的选择取决于你应用的具体需求，例如条目数量、处理复杂度，以及期望的并行度和容错水平。

在结合使用 Amazon Bedrock 与 Step Functions Map 状态构建生成式 AI 应用时，另一个重要考量是 [Amazon Bedrock 运行时配额](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas.html#quotas-runtime)。一般来说，这些模型配额允许每分钟数百甚至数千次请求。不过，如果在每分钟请求处理量配额较低的模型（例如图像生成模型）上运行大型 Map，你可能会遇到问题。在这种情况下，你可以在 [Map 状态的错误处理中加入重试器](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html#error-handling-retrying-after-an-error)。

## 解决方案概览

在接下来的几节中，我们将动手实践，看看这个解决方案如何运作。Amazon Bedrock 提供多种模型选择，以满足各个用例的具体需求。就本次练习而言，我们使用 Amazon Bedrock 对 Anthropic 的 Claude 3.5 Haiku 模型运行推理，以获取一组问题的答案，因为它是一个性能出色、速度快且成本高效的选项。

我们的目标是在 Step Functions 中创建一个 Express 状态机，使用内联 Map 状态解析应用通过 API 调用发送的问题 JSON 数组。对于每个问题，Step Functions 都会横向扩展，发起对 Amazon Bedrock 的同步调用。所有答案返回后，Step Functions 会将它们拼接成一个响应，我们最初发起调用的应用随后可以将其用于进一步处理或向最终用户展示。

### 先决条件

要跟随本解决方案的实施，你需要以下先决条件：

- 一个 AWS 账户
- 一个有权访问 Amazon Bedrock 和 Step Functions 的 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）用户
- 在[受支持的 AWS 区域](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)中，拥有对 Amazon Bedrock 上 Anthropic Claude 3.5 Haiku 的[模型访问权限](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html?icmpid=docs_bedrock_help_panel_model_access)（我们将使用 `us-west-2`）

通过添加一个条目取自 JSON 载荷的内联 Map 状态来编辑状态机。

### 调用 Amazon Bedrock 模型

接下来，在 Map 状态内添加一个 `Bedrock: InvokeModel` 动作任务作为下一个状态。

### 构建载荷

你构建的 prompt 使用 [Amazon State Language](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-amazon-states-language.html) 内建函数 [States.Format 来进行字符串插值](https://docs.aws.amazon.com/step-functions/latest/dg/amazon-states-language-intrinsic-functions.html#asl-intrsc-func-generic)，用 `{}` 替换字符串之后声明的变量。我们还必须在 `text` 键之后加上 `.$`，以引用此状态 JSON 输入中的某个节点。

在构建这个 prompt 时，你应当非常明确地要求模型做到以下几点：

- 使用以下描述彻底回答问题
- 不要重复问题
- 只回复问题的答案

我们将 `max_tokens` 设为 `800`，以允许 Amazon Bedrock 返回更长的响应。此外，你还可以加入[其他推理参数](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters-anthropic-claude-messages.html)，例如 temperature、`top_p`、`top_k` 和 `stop_sequences`。调整这些参数有助于限制长度，或影响模型响应的随机性或多样性。就本示例而言，我们将所有其他可选参数保持为默认值。

```
{
  "anthropic_version": "bedrock-2023-05-31",
  "max_tokens": 800,
  "messages": [
    {
      "role": "user",
      "content": [
        {
          "type": "text",
          "text.$": "States.Format('Answer following question thoroughly, using the following description. Do not repeat the question. Only respond with the answer to the question. Question: {} Description: {}', $.questions.question, $.description)"
        }
      ]
    }
  ]
}
```

## RAG 及其他可能的集成

RAG 是一种策略，通过让大型语言模型（LLM）引用权威的外部知识库来增强其输出，从而生成更准确或更安全的响应。这个强大的工具可以将 LLM 的能力扩展到特定领域或组织的内部知识库，而无需重新训练甚至微调模型。

将 RAG 集成到前面 RFP 示例中的一种直接方式，是在调用模型之前向你的 Map 状态添加一个 Bedrock Runtime Agents: Retrieve 动作任务。这使得可以查询 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)，它支持多种向量存储数据库，包括 [Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/) 向量引擎、Pinecone、Redis Enterprise Cloud，以及即将支持的 [Amazon Aurora](https://aws.amazon.com/rds/aurora/) 和 MongoDB。使用 Knowledge Bases 摄取并向量化存储在 Amazon S3 中的示例 RFP 和文档，就无需在问题数组中附带描述。此外，由于向量存储能够容纳的信息范围比单个 prompt 更广，RAG 可以极大提升响应的具体程度。

除了 Amazon Bedrock Knowledge Bases，根据你现有的技术栈，还有其他可用于 RAG 的集成选项，例如直接使用 [Amazon Kendra](https://aws.amazon.com/kendra/) Task 状态，或通过 [HTTP Task 状态使用第三方 API](https://docs.aws.amazon.com/step-functions/latest/dg/connect-third-party-apis.html) 接入你自行选择的向量数据库。

Step Functions 提供可组合性，让你可以[将来自 200 多个服务的 9,000 多个 AWS API 操作无缝集成](https://docs.aws.amazon.com/step-functions/latest/dg/supported-services-awssdk.html)到你的工作流中。这些经过优化的服务集成简化了 [AWS Lambda](https://aws.amazon.com/lambda/)、[Amazon Elastic Container Service](https://aws.amazon.com/ecs/)（Amazon ECS）、[AWS Glue](https://aws.amazon.com/glue/) 和 [Amazon EMR](https://aws.amazon.com/emr/) 等常用服务的使用，并提供 IAM 策略生成和 Run A Job (.sync) 模式等功能，后者会自动等待异步任务完成。生成式 AI 应用中另一个常见模式是将模型串联起来完成次要任务，例如在主要的摘要任务完成后进行语言翻译。这可以通过像我们前面那样再添加一个 `Bedrock: InvokeModel` 动作任务来实现。

## 结论

在本文中，我们展示了 Step Functions 在编排对 Amazon Bedrock 的并行调用方面的强大能力和灵活性。我们探讨了两种映射策略——内联映射和分布式映射——分别用于处理小型和大型数据集。此外，我们深入分析了一个回答 RFP 问题清单的实际用例，展示了 Step Functions 如何高效地横向扩展并管理多个 Amazon Bedrock 调用。

我们引入了 RAG 的概念，即通过引用外部知识库来增强 LLM 输出的一种策略，并演示了将 RAG 纳入 Step Functions 状态机的多种方式。我们还强调了 Step Functions 的集成能力，特别是可以直接从工作流中调用来自 200 多个服务的 9,000 多个 AWS API 操作。
