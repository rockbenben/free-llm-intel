# 从 PDF 到洞察：用 AWS 生成式 AI 服务构建智能文档处理 pipeline

组织每天要处理数百万份文档，从保险理赔单、发票到法律合同和病历。传统的光学字符识别（OCR）方案虽然能抽取文本，却无法理解复杂文档中蕴含的上下文、关系或含义。这一局限造成瓶颈，只能靠人工介入，既拉长了处理时间、推高了成本，也引入了潜在错误。

[Amazon Bedrock Data Automation](https://aws.amazon.com/bedrock/bda/)（BDA）提供统一的 API 体验，可从多模态内容（包括文档、图像、视频和音频文件）中抽取有意义的洞察。与传统只专注文本抽取的方案不同，BDA 理解文档上下文、校验抽取出的事实数据，并给出用于衡量准确度的置信度分数。BDA 通过一条 pipeline 处理文档，自动完成文档分类、抽取、规范化与校验等复杂任务。文档提交后，BDA 会自动按逻辑边界切分，把每个片段归入相应的文档类型，并匹配到正确的处理蓝图（blueprint）。这种智能路由免去了人工分拣文档、以及编排多个 AI 模型的麻烦。该服务支持多种文件格式，单次 API 请求最多支持 3,000 页和 500 MB，因此适合大规模处理各类文档。

本文介绍如何在 AWS 上构建一条成本可控、可扩展的智能文档处理 pipeline，由 Amazon Bedrock 及其各项能力驱动。BDA 是 Amazon Bedrock 内的一项托管服务，自动完成从文档中抽取洞察的工作。我们会演示 BDA 如何抽取并分析文档内容，托管在 Amazon Bedrock AgentCore Runtime 上的 Strands Agent 如何协调各项专门的处理任务，以及 Amazon Bedrock Knowledge Base 如何实现对多份文档的上下文理解。把这些能力组合进统一的架构，组织只需极少的开发投入就能改造自己的文档处理流程。

## 方案概览

我们的智能文档处理 pipeline 把生成式 AI 与编排好的工作流结合起来，自动抽取、分析文档中的可视化图表、图形和数据曲线，并从中提炼洞察，同时保持跨多个数据源的上下文与关系。该方案通过四个相互集成的层来处理文档：

- **输入处理层**：文档上传会触发处理编排和状态机协调。
- **抽取与存储层**：原始文本与表格抽取、图像与视觉元素分析，以及可扩展的数据集成。
- **智能层**：知识库摄取与语义搜索、多模态基础模型（FM）分析，以及由大语言模型（LLM）驱动的解读。
- **Agent 协调层**：协调器 agent 与各专门任务 agent。

### 输入处理层

输入处理层是本方案的基础。这一层负责接收新到的文档并决定其路由。当文档到达指定的 Amazon Simple Storage Service（Amazon S3）存储桶时，文档上传（Document Upload）会触发处理工作流，支持包括 PDF 以及扫描件（PDF 格式）在内的多种格式。

![AWS Step Functions 工作流图，展示使用 Amazon Bedrock Data Automation、DynamoDB 和 Lambda 自动处理 PDF 文档的流程。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/12/ML-18003-image-2-773x1024.png)

BDA 是输入处理层的核心抽取引擎，通过统一的 API 完成文档切分、分类和内容抽取。AWS Step Functions 负责编排工作流，以在抽取与存储层充分发挥 BDA 的能力，并在整个过程中提供运维可见性与控制力。下面是详细的编排流程：

- **文档摄取**：文件以各种格式到达 S3 存储桶。每种格式都通过统一的 API 处理，无需针对格式做预处理。
- **元数据记录**：工作流把文档元数据记录到 Amazon DynamoDB，用于跟踪、审计追溯和报表。记录内容包括文件类型、大小、提交时间和处理状态。  **页数分析**：工作流会检查页数以优化处理策略。BDA 会自动处理文档切分，可处理多达 3,000 页的文档。Step Functions 中的页数检查有助于为异步任务设置合适的超时值，并对异常大的文档做监控和告警。
- **BDA 处理调用**：工作流使用 InvokeDataAutomationAsync API 启动异步 BDA 任务。随后 BDA 会自动：按逻辑边界切分文档（每次切分最多 20 页）。把每个片段归类到文档类型。把文档匹配到合适的蓝图（如果使用自定义输出）。蓝图是事先配置好的工件，定义了抽取逻辑，必须在 BDA 处理之前完成设置。抽取包括文本、表格、表单和视觉元素在内的全部内容。
- **基于任务令牌的异步处理**：工作流保存一个任务令牌（task token），等待 BDA 任务完成。这种模式提高了资源利用率，并允许并发处理数千份文档。
- **错误处理与路由**：完善的错误处理覆盖成功处理、校验错误、超时和不支持的文件类型等不同场景，确保没有文档被丢弃，所有问题都被记录以便复查。

这种编排方式提供了一条高度可扩展的无服务器 pipeline，用于自动化文档分析，并在每个处理阶段都有恰当的分支逻辑和异常管理。

### 抽取与存储层

这一层是本方案的核心，BDA 在这里充当把原始内容转换为结构化、可操作数据的核心引擎。下一节会给出更多细节。

**Amazon Bedrock Data Automation** 是主要的处理引擎，提供两种灵活的输出选项：

- **标准输出** —— 按数据类型提供常用的信息，包括文档摘要、按阅读顺序抽取的文本、表格与图片的说明文字，以及生成式洞察。标准输出可以通过项目（project）定制，按处理需要开启或关闭表头、页脚、标题和示意图等特定抽取功能。
- **带蓝图的自定义输出** —— 思路是每种文档类型创建一个蓝图，因为同一类型文档要用同一套指令抽取相同的信息。而不同类型的文档需要不同的蓝图来抽取不同的信息。举例来说，你希望从护照中抽取的信息与从银行对账单中抽取的不同，所以这两种文档类型需要各自独立的蓝图。所有银行对账单都应当只用一份蓝图来处理，因为无论来自哪家银行、采用什么格式，你想从银行对账单中抽取的信息类型都应当是一致的。蓝图通过定义具体字段、数据格式和抽取指令，让你精确控制所抽取的信息。一个项目最多可以包含 40 份文档蓝图，BDA 会自动把每份文档匹配到合适的蓝图。这样一来，发票、合同和表单等不同类型的文档就能在同一个统一的工作流中处理。

此外，BDA 还提供：

- 通过单一接口处理多模态内容的统一 API 体验
- 跨多个区域的跨区域推理能力，以提升处理效率
- 内置防护措施，包括视觉定位（visual grounding）和用于保证准确度的置信度分数
- 支持自定义蓝图，为特定文档类型统一输出格式

**视觉分析处理** 借助 BDA 的能力，从传统光学字符识别（OCR）方案无法解读的图表、示意图和数据曲线中抽取洞察。在做图片说明时，BDA 会把图像裁剪区域作为输出的一部分提供，还会从这些视觉元素生成详细的文字描述和结构化数据，一并纳入下游工作流。例如，BDA 处理一张图表时会产出：

- 描述图表内容与用途的生成式说明文字
- 从图形中抽取的数据点和趋势
- 从示意图和流程图中抽取的结构关系
- 把视觉元素与其在文档中位置关联起来的边界框（bounding box）坐标

**下游处理中的全部文档格式**：所有受支持的文档格式（PDF、PNG、JPG、TIFF、DOC、DOCX）都通过统一的 API 处理。BDA 抽取出的内容（包括视觉元素描述）随后可以被手工配置到 Amazon Bedrock Knowledge Bases 中做索引和向量化，从而在多种文档类型上实现语义搜索。需要注意，BDA 还与 Knowledge Bases 内置集成：在把文档摄取进知识库的过程中，它可以作为解析器，使用 BDA 的标准输出（无需蓝图）。这条下游工作流接收 BDA 输出的结构化 JSON（包含全部抽取信息），因此无论原始文件格式如何，处理方式都能保持一致。

**文档数据抽取** 包括：

- 按阅读顺序抽取文本，并保留版式
- 识别表格结构，并保持单元格之间的关系
- 检测表单字段并抽取键值对
- 分析视觉元素，包括图表、图形和示意图，并生成说明文字
- 用边界框坐标为抽取出的元素精确定位
- 生成文档级和页面级的摘要，并保留上下文

### 智能层

这一层是本方案的认知引擎。Amazon Bedrock Knowledge Bases 需要配置为与 Amazon OpenSearch Serverless 配合工作，才能通过语义搜索和检索增强生成（RAG）能力把原始内容转化为可操作的洞察。下一节给出更多细节。

Amazon Bedrock Knowledge Bases 与 Amazon OpenSearch Serverless 结合，通过以下方式支撑语义搜索与 RAG 工作流：

- 为处理后的文档内容建索引，以便智能查询
- 维护向量嵌入，用于跨文档集合的相似度搜索
- 支持跨多份文档和多个数据源的复杂查询

**Amazon Bedrock FM** 分析视觉内容，包括图表解读、文档版式理解，以及文本与视觉组件之间的跨模态关系检测。

### Agent 协调层

这一层组织起本方案的智能。托管在 Amazon Bedrock AgentCore Runtime 上的 Strands Agents 负责管理整体处理工作流：按请求类型把请求路由到合适的专门 agent，并在复杂文档分析中协调 agent 之间的通信。

![架构图：一个构建在 AWS AgentCore Runtime 上的多 agent AI 系统，由协调器 agent 编排市场分析师、投资顾问和外部 API 三类 agent，它们经 Amazon API Gateway 连接，并由使用 Amazon Titan Embeddings 的向量数据库支撑。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/12/ML-18003-image-3.png)

**专门任务 agent** 负责特定的文档处理职能：

- 市场分析师 agent，处理金融市场报告和投资文档。
- 投资顾问 agent，处理投资组合分析和顾问类文档。
- 外部 API agent，通过到金融数据提供商、监管数据库和市场情报平台的安全 API 连接，集成实时第三方数据。
- 协调器 agent，通过把外部 API agent 提供的实时市场数据与 Amazon Bedrock 知识库中存储的历史数据做对比，完成交叉引用校验。

## 实现架构

这条处理 pipeline 采用事件驱动的方式处理文档，把多个专门层集成到一个内聚的工作流中。它遵循一条逻辑递进的路径，每一步都建立在前一步之上。流程从文档上传开始，触发 Amazon S3 事件，进而启动状态机，然后进入多模态处理，从多种内容类型中抽取含义。pipeline 接着进入 agent 协调，根据文档特征决定处理方式，随后是用于智能检索的知识库索引。这条有条不紊的流程最终落在洞察的生成以及与企业系统的集成上，形成一段从原始文档到可操作智能的完整处理旅程。

### 文档处理流程

AWS Step Functions 编排文档处理 pipeline，负责文档分类、多模态抽取、数据校验和知识库集成。

### Agent 交互流程

面向用户的这一层提供智能查询处理：用自然语言与处理后的文档语料交互，由协调 agent 监督各专门 agent，并把查询智能地分发到正确的处理 agent。

### 用例：商业地产物业分析

一家商业地产投资公司每月收到 200 多份物业评估报告。这些报告包含：

- **物业概览文档**，含位置图、分区信息和物业描述。
- **财务分析表格**，以图片形式嵌入 PDF，展示现金流预测、资本化率（cap rate）和 ROI 计算。
- **市场对比图表**，展示可比物业的成交价、租金水平和市场趋势。
- **物业照片和平面图**，带有标注和尺寸。
- **法律文件**，包括产权报告、环境评估和分区合规文件。
- **历史业绩曲线**，展示入住率、租金清册和维护成本随时间的变化。

**多模态内容抽取**：

- 市场分析师 agent 处理嵌入的财务图表，抽取净营业收入（NOI）预测和资本化率趋势。

## 成本优化策略

以下是一些在保持本方案处理效果的同时管理运营开支的务实做法。

### 智能路由

按复杂程度把文档路由到合适的处理层级。简单的纯文本文档采用基础抽取，而含表格和图像的复杂文档则采用更高级的处理技术。

### 批处理

在合适的情况下把多份文档合并到一个 Amazon Bedrock Data Automation 请求中，以改善成本，同时遵守服务限额。

### 存储生命周期管理

实施 [Amazon S3 生命周期策略](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html)，根据访问模式自动把处理后的文档转入成本更低的存储层级。

## 安全与合规

该架构通过多种方式实现企业级安全：用 AWS KMS 密钥加密文档和处理结果，用 AWS PrivateLink 连接在 VPC 边界内提供安全的 API 访问，并在所有组件上采用遵循最小权限原则的 IAM 角色。
