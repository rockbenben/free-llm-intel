# 用 Amazon Bedrock 和 Amazon Lex 提升客户的全渠道体验

AI 的兴起为跨多个渠道提升客户体验开辟了新途径。natural language understanding（NLU）等技术被用于识别客户意图，从而实现高效的自助操作。automatic speech recognition（ASR）把口述的词转为文本，实现无缝的语音交互。借助 [Amazon Lex](https://aws.amazon.com/lex/) bot，企业可以使用[对话式 AI](https://aws.amazon.com/lex/)把这些能力集成到呼叫中心。Amazon Lex 使用 ASR 和 NLU 理解客户需求，并引导他们走完整个流程。这些 AI 技术显著缩短了坐席处理时长、提高了净推荐值（NPS），并简化了预约排程等自助任务。

[生成式 AI](https://aws.amazon.com/generative-ai/) 的出现进一步拓展了提升全渠道客户体验的潜力。然而，对安全性、合规性和 AI 幻觉的担忧，常常使企业不愿通过其全渠道解决方案让客户直接接触 large language model（LLM）。这正是集成 Amazon Lex 与 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 的价值所在。在这种设置中，Amazon Lex 作为初始触点，负责意图分类、slot 收集和 fulfillment。同时，Amazon Bedrock 作为二级校验层，当 Amazon Lex 在理解客户输入时遇到不确定情况就介入。

在本文中，我们演示如何使用 Amazon Lex 和 Amazon Bedrock 把 LLM 集成到你的全渠道体验中。

## 用 LLM 增强客户交互

以下三个场景说明了 LLM 如何增强客户交互：

- **意图分类** – 这类场景发生在客户清楚地表达意图，但缺乏话语（utterance）训练数据导致传统模型表现不佳时。例如，客户来电说：“我家地下室淹水了，至少有一英尺深，我完全不知道该怎么办。”传统 NLU 模型可能缺乏处理这种超出既有范式的响应的训练数据，因为它们通常是在“我要报案”“我有洪水理赔”“打开理赔”等示例话语上训练的，这些话语被映射到假设的 `StartClaim` 意图。然而，当 LLM 获得每个意图的上下文（包括描述和示例话语）时，它可以准确判断客户正在处理被淹的地下室，并希望发起理赔。
- **辅助 slot 解析（内置）与自定义 slot 辅助（自定义）** – 这类场景发生在客户对 slot 收集给出超出既有范式的响应时。对于 `AMAZON.Date`、`AMAZON.Country` 和 `AMAZON.Confirmation` 等部分内置 slot 类型，Amazon Lex 目前具备[为部分内置 slot 类型处理 slot 解析的内置能力](https://docs.aws.amazon.com/lexv2/latest/dg/assisted-slot.html)。对于自定义 slot 类型，你需要使用 [AWS Lambda](https://aws.amazon.com/lambda) 实现自定义逻辑来进行 slot 解析和额外校验。本解决方案使用 LLM 澄清这些输入并将其映射到正确的 slot，从而实现自定义 slot 解析。例如，把“Toyota Tundra”理解为“truck”，或把“the whole dang top of my house is gone”理解为“roof”。这让你可以集成生成式 AI，对预置 slot 和自定义 slot 都进行校验。
- **背景噪声缓解** – 许多客户在致电呼叫中心时无法控制背景噪声。噪声可能包括电视声响、旁人的对话，或被转写成语音的非人类声音（例如一辆车驶过被转写成“uhhh”）。此类情况下，NLU 模型视其训练数据而定，可能误判来电者意图，或要求来电者重复。然而，借助 LLM，你可以提供带有适当上下文的转写文本，以区分噪声与客户实际说的话。例如，如果背景中正在播放电视节目，而客户在被问及保单时说的是“my car”，转写文本可能读作“Tune in this evening for my car.”。LLM 可以忽略转写中不相关的部分，专注于相关部分“my car”，从而准确理解客户的意图。

如这些场景所示，LLM 并不控制对话。相反，它在 Amazon Lex 的意图、意图描述、slot、示例 slot 和话语所界定的边界内运作。这种方法帮助引导客户走上正确的路径，降低幻觉和面客应用被操纵的风险。此外，这种方法还能降低成本，因为凡是能用 NLU 的地方就用 NLU，LLM 只在再次提示客户之前作为二次校验。

你还可以把它与你自己的联络中心解决方案（例如 [Amazon Connect](https://aws.amazon.com/connect/)）集成，进一步增强这种 AI 驱动的体验。通过结合 Amazon Lex、Amazon Bedrock 和 Amazon Connect 的能力，你可以在各个渠道上交付无缝、智能的客户体验。

当客户通过语音或聊天联系时，这一集成解决方案会提供强大、AI 驱动的交互：

- Amazon Connect 管理最初的客户联系，处理呼叫路由和渠道选择。
- Amazon Lex 处理客户输入，使用 NLU 识别意图并提取相关信息。
- 在 Amazon Lex 可能无法完全理解客户意图，或需要更细致解读的情况下，可以调用 Amazon Bedrock 中的先进语言模型来做更深入的分析与理解。
- 来自 Amazon Lex 和 Amazon Bedrock 的综合洞见会引导 Amazon Connect 中的对话流程，决定是提供自动响应、请求更多信息，还是把客户转接给人工坐席。

## 解决方案概述

在本解决方案中，Amazon Lex 将通过 Lambda 连接 Amazon Bedrock，并在对话过程中需要意图分类和 slot 解析方面的协助时，调用你在 Amazon Bedrock 上选择的 LLM。例如，如果 `ElicitIntent` 调用落入 `FallbackIntent`，Lambda 函数会运行，让 Amazon Bedrock 判断用户是否可能使用了应当被正确映射的超范式短语。此外，我们还可以用业务上下文来增强发送给模型的、用于意图分类和 slot 解析的 prompt，以取得更准确的结果。用于意图分类和 slot 解析的示例 prompt 可在 [GitHub 仓库](https://github.com/aws-samples/omnichannel-experience-bot-with-bedrock-and-lex)中找到。

下图展示了解决方案架构：

![architecture diagram](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/10/diagram.png)

该 workflow 包含以下步骤：

- 消息通过 Amazon Connect（文本和语音）、消息应用（文本）和第三方联络中心（文本和语音）发送到 Amazon Lex 全渠道。Amazon Lex NLU 把用户话语映射到特定意图。
- 在 Amazon Lex NLU 未能识别用户话语的对话阶段（例如 fallback 意图或 slot fulfillment 期间），会调用 Lambda 函数。
- Lambda 通过 Amazon Bedrock 调用从 [AWS CloudFormation](https://aws.amazon.com/cloudformation) 模板中选择的基座模型（FM），以识别意图、识别 slot，或判断转写消息中是否包含背景噪声。
- Amazon Bedrock 返回识别出的意图或 slot，或回复无法把该话语归类为相关意图或 slot。
- Lambda 设置 Amazon Lex 的状态，使其要么在选定的意图上继续推进，要么重新提示用户输入。
- Amazon Lex 要么再次提示用户，要么继续完成该意图，从而继续对话。

## 先决条件

你需要满足以下先决条件：

- 一个具有创建 [AWS Identity and Access Management](https://aws.amazon.com/iam)（IAM）角色与策略权限的 [AWS 账户](https://signin.aws.amazon.com/signup?request_type=builderId)。更多信息请参阅[访问管理概述：权限与策略](https://docs.aws.amazon.com/IAM/latest/UserGuide/introduction_access-management.html)。
- 熟悉 Amazon Lex、AWS Lambda 和 Amazon Bedrock 等 AWS 服务。
- 已在 Amazon Bedrock 上启用对 FM 的访问。有关操作说明，请参阅[访问 Amazon Bedrock 基座模型](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)。在本解决方案中，你可以选择使用 Anthropic 的 Claude 3 Haiku、Anthropic 的 Claude 3.5 Haiku 或 Anthropic 的 Claude 3.5 Sonnet。

## 部署全渠道 Amazon Lex bot

要部署本解决方案，请完成以下步骤：

- 选择 **Launch Stack**，在 `us-east-1` 中启动 CloudFormation 堆栈：
[![启动堆栈按钮](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/07/image2.jpg)](https://us-east-1.console.aws.amazon.com/cloudformation/home?region=us-east-1#/stacks/create/review?templateURL=https://aws-blogs-artifacts-public.s3.us-east-1.amazonaws.com/ML-17242/omnichannel_bot.yaml)
- 在 **Stack name** 中，为你的堆栈输入一个名称。本文使用名称 `FNOLBot`。
- 在 **Parameters** 部分，选择你要使用的模型。
- 检查 IAM 资源创建情况并选择 **Create stack**。

几分钟后，你的堆栈应该就绪。核心资源如下：

- **Amazon Lex bot** – `FNOLBot`
- **Lambda 函数** – `ai-assist-lambda-{Stack-Name}`
- **IAM 角色** – `{Stack-Name}-AIAssistLambdaRole` 和 `{Stack-Name}-BotRuntimeRole`

## 测试全渠道 bot

要测试该 bot，请在 Amazon Lex 控制台上导航到 `FNOLBot` 并打开测试窗口。更多细节请参阅[使用控制台测试 bot](https://docs.aws.amazon.com/lexv2/latest/dg/test-bot.html)。

### 意图分类

我们来测试这样的场景：客户不说“我想报案”，而是提出更复杂的问题：

- 在测试窗口中输入“My neighbor’s tree fell on my garage. What steps should I take with my insurance company?”
- 选择 **Inspect**。

在响应中，意图被识别为 `GatherFNOLInfo`。

### Slot 辅助

我们来测试这样的场景：客户不说出明确的 slot 值，而是由生成式 AI 帮助填充 slot：

- 通过选择刷新图标来刷新 bot。
- 输入“I need to make a claim.”

Amazon Lex bot 随后会问“What portion of the home was damaged?”

- 输入“the whole dang top of my house was gone.”

bot 随后会问“Please describe any injuries that occurred during the incident.”

- 输入“I got a pretty bad cut from the shingles.”
- 选择 **Inspect**。

你会看到 `Damage` slot 已被填入“roof”，`PersonalInjury` slot 已被填入“laceration”。

现在我们模拟 Amazon Lex 使用 ASR 转写背景噪声的情况。第一个场景是用户在与 Amazon Lex bot 对话的同时还与其他人交谈。第二个场景是背景中电视声音太大，被 ASR 转写进来。

## 结论

在本文中，我们展示了如何把 Amazon Lex 配置为全渠道 chatbot 体验，并把 Amazon Bedrock 作为你的二级校验层。这让你的客户有可能在意图层面和 slot 收集层面都给出超范式响应，而无需被反复提示，从而实现无缝的客户体验。正如我们所演示的，无论用户给出对其意图和 slot 的详细描述，还是使用超出 Amazon Lex NLU 训练数据的短语，LLM 都能正确识别出正确的意图和 slot。

如果你已经部署了 Amazon Lex bot，你可以编辑 Lambda 代码来进一步增强该 bot。试试 CloudFormation 堆栈中的解决方案或 [GitHub 仓库](https://github.com/aws-samples/omnichannel-experience-bot-with-bedrock-and-lex)中的代码，如有任何问题，请在评论区告诉我们。
