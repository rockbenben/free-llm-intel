# HCLTech 由 AWS 驱动的 AutoWise Companion：以数据驱动设计，为汽车买家带来明智决策的无缝体验

本文介绍 HCLTech 的 AutoWise Companion，这是一个变革性的生成式 AI 解决方案，旨在优化客户的购车旅程。该解决方案根据个人偏好定制推荐，引导客户找到最适合自己的车型。同时，它利用真实的客户反馈来推动战略决策，帮助整车制造商（原始设备制造商，OEM）提升销量与公司利润。HCLTech 的 AutoWise Companion 由 AWS 上的[生成式 AI](https://aws.amazon.com/generative-ai/) 服务和[大型语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）的多模态能力驱动，提供无缝且有影响力的体验。

在本文中，我们分析当前的行业挑战，并借助内置的 AWS 服务和开源工具，带读者了解 AutoWise Companion 解决方案的功能流程与架构设计。此外，我们还从安全和负责任 AI 的角度讨论该设计，展示如何把这一解决方案应用到更广泛的行业场景中。

## 机遇

购车是一项关键决策，可能给客户带来压力与不确定性。以下是客户和制造商在现实中面临的一些挑战：

- **选对品牌与车型** – 即便已经缩小了品牌范围，客户仍需在众多车型和配置之间做出选择。每个车型的特性、价位和性能指标各不相同，要做出既符合需求又符合预算的自信选择并不容易。
- **分析客户反馈** – OEM 面临着从大量质量报告工具（QRT）报告中筛选信息的艰巨任务。这些报告包含海量数据，分析起来既令人不知所措又耗时。
- **与客户情绪保持一致** – OEM 必须把 QRT 报告中的发现与客户的实际情绪对齐。从原始数据中理解客户满意度和需要改进的方面十分复杂，往往需要先进的分析工具。

HCLTech 的 AutoWise Companion 解决方案针对这些痛点，既让客户受益，也惠及制造商：它简化了客户的决策过程，同时增强了制造商的数据分析和客户情绪对齐能力。

该解决方案从多种数据源中提取有价值的洞察，包括 OEM 交易数据、车辆规格、社交媒体评论以及 OEM 的 QRT 报告。通过采用多模态方法，解决方案把各个数据库中的相关数据要素连接起来。根据客户查询和上下文，系统动态生成 text-to-SQL 查询，使用[语义搜索](https://en.wikipedia.org/wiki/Semantic_search)概括知识库结果，并基于客户的偏好生成个性化的车辆宣传册。这一无缝流程由[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）和 [text-to-SQL](https://aws.amazon.com/blogs/machine-learning/build-a-robust-text-to-sql-solution-generating-complex-queries-self-correcting-and-querying-diverse-data-sources/) 框架支撑。

## 解决方案概览

整个解决方案按面向客户和面向 OEM 划分为不同的功能模块。

### 客户助手

即使考虑的是同一个汽车品牌和车型，每位客户也都有独特的偏好。该解决方案旨在为客户提供关于其偏好特性的详尽、个性化解释，帮助他们做出明智决策。解决方案提供以下能力：

- **自然语言查询** – 客户可以用平实的语言询问车辆特性，例如总体评分、价格等。系统能够理解并有效回应这些询问。
- **定制化交互** – 解决方案允许客户从可用列表中挑选特定特性，从而更深入地探索自己偏好的选项。这有助于客户全面理解最符合自身需求的特性。
- **个性化宣传册生成** – 解决方案会考虑客户的功能偏好，生成定制的特性说明宣传册（并附带具体的特性图片）。这份个性化文档帮助客户更深入地了解车辆，并支持他们的决策过程。

### OEM 助手

汽车行业的 OEM 必须主动处理客户针对各类汽车零部件的投诉和反馈。这一综合解决方案使 OEM 管理者能够分析和概括不同类别下的客户投诉与已上报的质量问题，从而高效地制定数据驱动的策略。这提升了在动态变化的汽车行业中的决策能力和竞争力。解决方案支持以下能力：

- **洞察摘要** – 系统让 OEM 能够更好地理解通过集成和汇聚多源数据（例如 QRT 报告、车辆交易销售数据和社交媒体评论）而呈现的洞察摘要。
- **明细视图** – OEM 可以用自然语言无缝获取问题、报告、投诉或数据点的具体细节，系统会从所引用的评论数据、交易数据或非结构化 QRT 报告中提供相关信息。

为了更好地理解该解决方案，我们用下图所示的七个步骤来说明整体功能流程。

[![flow map explaning the overall function flow](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/20/AutoWise_Overallflow.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/20/AutoWise_Overallflow.png)

整体功能流程包含以下步骤：

- 用户（客户或 OEM 管理者）通过自然语言界面与系统交互，提出各种问题。
- 系统的自然语言解释器由生成式 AI 引擎驱动，分析查询的上下文、意图和相关人物角色，以确定合适的数据源。
- 基于识别出的数据源，由生成式 AI 引擎生成相应的多源查询执行计划。
- 查询 agent 解析执行计划，并向相应的查询执行器发送查询。
- 系统从多个来源（例如公司产品元数据、销售交易、OEM 报告等）智能地获取所需信息，以生成有意义的回答。
- 系统把从各个来源收集到的信息无缝整合，运用上下文理解和领域特定知识，为用户生成精心组织、全面且相关的回答。
- 系统针对原始查询生成回答，并让用户能够继续交互——既可以在同一上下文内提出后续问题，也可以探索新的兴趣领域，同时受益于系统保持上下文感知、持续提供相关且有信息量回答的能力。

## 技术架构

整个解决方案使用 AWS 服务和 [LangChain](https://www.langchain.com/) 实现。多个 LangChain 函数（例如 CharacterTextSplitter 和 embedding 向量）用于文本处理和调用嵌入模型。在应用层，解决方案的 GUI 使用 Python 语言的 [Streamlit](https://streamlit.io/) 构建。该应用容器采用基于 AWS 微服务、成本最优的架构部署，使用 [Amazon Elastic Container Service (Amazon ECS)](https://aws.amazon.com/ecs/) 集群和 [AWS Fargate](https://aws.amazon.com/fargate/)。

该解决方案包含以下处理层：

- **数据管道** – 各类数据源，例如销售交易数据、非结构化 QRT 报告、JSON 格式的社交媒体评论和车辆元数据，会经过处理、转换并存储在相应的数据库中。
- **向量嵌入与数据编目** – 为支持自然语言查询的相似度匹配，相应数据会被向量化并存储为向量嵌入。此外，为启用自然语言转 SQL（text-to-SQL）功能，会为交易数据生成相应的数据目录。
- **LLM（请求与响应构建）** – 系统在不同阶段调用 LLM，以理解请求、构建上下文，并基于查询和上下文生成回答。
- **前端应用** – 客户或 OEM 通过一个助手应用与解决方案交互，该应用旨在支持与系统进行自然语言交互。

该解决方案使用以下 AWS 数据存储和分析服务：

- **非结构化数据** – [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/pm/serv-s3/?gclid=Cj0KCQjw3ZayBhDRARIsAPWzx8q7_PkEW0seFvhdcNzGRlgrhgP2RaiElAOfMHfwIzhWgESBnmf3frIaAkxZEALw_wcB&trk=55ffcfa3-95d3-4418-9a79-62a64040b867&sc_channel=ps&ef_id=Cj0KCQjw3ZayBhDRARIsAPWzx8q7_PkEW0seFvhdcNzGRlgrhgP2RaiElAOfMHfwIzhWgESBnmf3frIaAkxZEALw_wcB:G:s&s_kwcid=AL!4422!3!536452732958!e!!g!!amazon%20s3!11543056249!112002966709) 存储桶用于保存基于 JSON 的社交媒体反馈数据、质量报告 PDF（OEM 专用）以及车辆及其特性图片。
- **交易销售数据** – [Amazon Relational Database Service (Amazon RDS) for PostgreSQL](https://aws.amazon.com/rds/postgresql/) 用于按季度或月度保存车辆的交易报告。
- **车辆规格数据** – [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 用于存储车辆元数据（其特性和规格）。
- **Amazon Athena** – [Amazon Athena](https://aws.amazon.com/athena/) 用于查询存储在 S3 存储桶中基于 JSON 的社交媒体反馈数据。
- **AWS Glue** – [AWS Glue](https://aws.amazon.com/glue/) 用于数据编目。

[![details architecture design on aws](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/20/AutoWise_Architectdesign.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/20/AutoWise_Architectdesign.png)

该工作流包含以下步骤：

- 用户以自然语言表述的查询，由经过编排的 [AWS Lambda](https://aws.amazon.com/lambda/) 处理
- Lambda 函数尝试从 LLM 缓存中查找查询匹配。若找到匹配，则从 LLM 缓存返回回答。若未找到匹配，该函数会通过 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 调用相应的 LLM。本解决方案使用 Amazon Bedrock 上的 LLM（Anthropic 的 [Claude 2](https://www.anthropic.com/news/claude-2) 和 [Claude 3 Haiku](https://aws.amazon.com/marketplace/pp/prodview-5iaka6xethmle)）来生成回答。[Amazon Titan Embeddings G1 – Text](https://aws.amazon.com/bedrock/amazon-models/titan/) LLM 用于把知识文档和用户查询转换为向量嵌入。
- 基于查询的上下文和可用目录，LLM 识别出相关数据源：交易销售数据、社交媒体评论、车辆元数据等会经过转换，用于客户和 OEM 交互。此步骤中的数据受到限制，只有 OEM 角色可以访问，以帮助诊断质量相关问题并就 QRT 报告提供洞察。本解决方案使用 [Amazon Textract](https://aws.amazon.com/textract/) 作为数据提取工具，从 PDF（例如质量报告）中提取文本。
- LLM 生成查询（text-to-SQL），以便根据识别出的数据源从相应数据通道获取数据。
- 来自各数据通道的回答被汇总起来，生成整体上下文。
- 此外，为生成个性化宣传册，系统会基于查询上下文获取相关图片（以文本形式的嵌入来描述）。[Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/) 被用作向量数据库，存储从质量报告 PDF 和图片描述中提取的文本块嵌入。
- 随后，整体上下文被传给负责生成回答的 LLM，以生成给用户的最终答复。缓存也会同步更新。

## 负责任的生成式 AI 与安全考量

采用 LLM 实施生成式 AI 项目的客户，越来越重视安全和负责任 AI 的实践。这种关注源于保护敏感数据、维护模型完整性以及确保 AI 技术合乎伦理使用的需要。AutoWise Companion 解决方案使用 AWS 服务，使客户能够专注于创新，同时保持最高标准的数据保护和合乎伦理的 AI 使用。

### Amazon Bedrock Guardrails

[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 提供可配置的防护措施，可作为安全和隐私控制施加于用户输入和基础模型输出。通过引入 guardrails，解决方案可主动引导用户远离潜在风险或错误，促进更好的结果并遵循既定标准。在汽车行业，OEM 厂商通常会针对车辆规格施加安全过滤器。例如，他们希望校验输入，确保查询针对的是合法存在的车型。Amazon Bedrock Guardrails 提供[拒绝主题](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-denied-topics.html)和[上下文 grounding 检查](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-contextual-grounding-check.html)，确保关于不存在的汽车车型的查询会被识别出来，并用自定义回复予以拒绝。

### 安全考量

该系统采用依赖客户数据的 RAG 框架，因此数据安全是首要事项。在设计上，Amazon Bedrock 提供一层数据安全保障，确保客户数据保持加密和受保护状态，既不会被用于训练底层 LLM，也不会与模型提供商共享。Amazon Bedrock 在 ISO、SOC、CSA STAR Level 2 等通用合规标准范围内，符合 HIPAA 要求，客户也可以在符合 GDPR 的前提下使用 Amazon Bedrock。

对于 Amazon S3 上的原始文档存储，以及交易数据的存储与检索，这些数据源均已加密，并部署了相应的访问控制机制，以维持受限制的数据访问。

## 关键经验

该解决方案带来了以下关键经验：

- **LLM 成本优化** – 在解决方案的初期阶段，根据用户查询需要进行多次独立的 LLM 调用，导致成本和执行时间增加。通过使用 [AWS Glue Data Catalog](https://docs.aws.amazon.com/glue/latest/dg/catalog-and-crawler.html)，我们改进了解法，用单次 LLM 调用即可找到相关的最佳信息来源。
- **LLM 缓存** – 我们观察到收到的查询中有相当大的比例是重复的。为优化性能和成本，我们实现了一套缓存机制，存储此前 LLM 模型调用的请求-响应数据。通过这次缓存查找，我们可以从缓存数据中获取回答，从而减少对底层 LLM 的调用次数。这种缓存方式帮助降低了成本并改善了响应时间。
- **图像转文本** – 基于客户偏好生成个性化宣传册颇具挑战。不过，最新的具备视觉能力的多模态 LLM，例如 Anthropic 的 Claude 3 模型（Haiku 和 Sonnet），已显著提升了准确率。
