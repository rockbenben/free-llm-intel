# 用 Amazon Bedrock 为货运物流构建双语 NER

[IBS Software](https://www.ibsplc.com/) 的 Cargo 系统每天处理数千封双语货运物流电子邮件。系统需要从英文和日文两种语言中抽取运单号（AWB）、航班详情、重量和交付指示等关键信息。这增加了构建稳健的命名实体识别（NER）解决方案的复杂度。挑战包括拖慢运营的人工干预，以及准确率与成本之间的权衡。IBS Software 需要一个能够跨两种语言准确识别 23 种不同实体类型、同时在规模化时仍具成本效益的 AI 解决方案。

在探索了多种方法之后，IBS Software 使用 Amazon Bedrock 的托管蒸馏能力打造出一个生产就绪的解决方案。通过把知识从 Amazon Nova Pro 蒸馏到更高效的 [Amazon Nova Lite](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-amazon-nova-lite.html) 模型中，IBS Software 取得 95.085% 的 F1-Score 准确率，同时把运营成本降低 14 倍。本案例研究详述了他们从面对复杂的开源实现，到在 AWS 上成功部署、如今实时处理货运电子邮件的历程。

在本文中，我们分享基于 token 的蒸馏技术路线、经验教训以及部署架构。如果你也面临类似的双语 NER 挑战，可以从 IBS Software 使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/model-distillation/) 知识蒸馏能力的经验中获益。

## 解决方案概览

目标是构建一个双语 NER 系统，能够从用英文和日文写成的货运物流电子邮件中抽取 23 种实体类型。关键实体包括：

- AWB（Air Waybill）运单号。
- 航班号与航线。
- 重量（毛重、计费重量、体积重量）。
- 尺寸与体积。
- 品名描述。
- 发货人与收货人信息。
- 特殊操作代码。
- 交付指示。

主要风险包括在两种语言上同时维持高准确率、在规模化下管理推理成本，以及为实时处理实现低延迟。借助 Amazon Bedrock 的模型蒸馏能力，你可以使用更小、更快、更具成本效益的模型。这些模型为你的用例提供的准确率可与 Amazon Bedrock 中最先进的模型相当。

## 解决方案

IBS 由九名研究员和工程师组成的团队花了大约 4 个月开发和部署该解决方案。项目时间线包括：

- **第 1 个月：** 数据集准备与 500 封双语电子邮件的标注。
- **第 2 个月：** 在开源框架（PyTorch、TextBrewer）上遇到挑战。
- **第 3 个月：** 使用 Amazon Bedrock 成功蒸馏（Nova Pro → Nova Lite）。
- **第 4 个月：** 生产部署与优化。

完成的关键任务：

- 为 500 封货运电子邮件（350 封英文、150 封日文）标注 23 种实体类型。
- 使用自定义超参数配置 Amazon Bedrock 蒸馏。
- 在 70 个 step 上训练学生模型 4 个 epoch。
- 把 loss 从 0.05 降到 0.008。
- 部署了带 .eml 文件处理 pipeline 的推理端点。
- 在测试集上验证了 95.085% 的 F1-Score。

IBS Software 使用 Amazon Bedrock 托管服务部署了全部基础设施，从而无需自建模型托管基础设施。

### 开源方案的挑战

起初，团队尝试使用开源框架进行知识蒸馏，包括基于 PyTorch 的实现和 TextBrewer 库。这些方法失败的原因是：

- 为双语数据配置蒸馏 pipeline 的复杂度高。
- 缺少用于训练和部署的托管基础设施。
- 为 token 级蒸馏调优超参数困难。
- 与我们生产环境的电子邮件处理工作流不兼容。

有关知识蒸馏基础知识的更多细节，参见 [AWS Machine Learning Best Practices](https://docs.aws.amazon.com/machine-learning/)。

### Amazon Bedrock 蒸馏方案

我们转向 Amazon Bedrock Model Distillation，使用 Amazon Nova Pro 作为教师模型、Nova Lite 作为学生模型。主要优势包括：

- 托管训练基础设施，支持自动超参数优化。
- 原生支持 token 级蒸馏。
- 易于与我们电子邮件处理 pipeline 集成。
- 内置监控与评估指标。

**训练配置：**

```
distillation_config = {
    "teacher_model": "amazon.nova-pro-v1:0",
    "student_model": "amazon.nova-lite-v1:0",
    "max_sequence_length": 2048,
    "epochs": 4,
    "training_steps": 70,
    "loss_function": "token_level_kl_divergence"
}
```

训练过程在 70 个 step 内把 loss 从 0.05 降到 0.008，表明从教师到学生的知识迁移效果很强。

关于 Amazon Bedrock 蒸馏文档，参见[在 Amazon Bedrock 中使用蒸馏自定义模型](https://docs.aws.amazon.com/bedrock/latest/userguide/model-distillation.html)。

### 数据集准备

我们的数据集包含 500 封真实的货运物流电子邮件：

- **350 封英文电子邮件：** 包含运单号、航班详情、重量和操作指示的标准货运单据。
- **150 封日文电子邮件：** 内容类似，但采用日文特有的格式与术语。

每封电子邮件都由熟悉货运物流术语的领域专家针对 23 种实体类型进行人工标注。标注过程大约耗时 3 周，为两种语言提供了高质量的训练数据。

### 模型评估

我们用 F1-Score（precision 与 recall 的调和平均数）评估了教师模型和学生模型：

**结果：**

基础 Nova Lite 模型的总体 F1-Score 约为 84%，而教师模型与定制后的 Nova Lite 模型的准确率提升了约 10%。下表展示了 F1-Score 结果。

| **模型** | **总体 F1-Score** | **英文 F1-Score** | **日文 F1-Score** |
| --- | --- | --- | --- |
| Nova Pro（教师） | 97.0% | 97.8% | 96.2% |
| Nova Lite（学生） | 95.085% | 96.535% | 93.635% |

蒸馏后的 Nova Lite 模型保留了教师模型 98% 的性能，同时在生产推理中把成本降低 14 倍。

### 错误分析与挑战

我们观察到，学生模型在日文文本上的 F1-Score 比英文文本低 2.565%。这一差距主要来自品名描述中复杂的汉字组合、无空格日文文本中模糊的实体边界，以及日文训练数据量较小（150 封对 350 封电子邮件）。包含内嵌实体的多行交付指示偶尔也会导致边界检测错误。

为克服这些挑战，我们用合成样本扩充了日文训练数据。我们还针对已知实体模式（AWB 格式、航班号正则）应用了后处理规则，并实现了置信度阈值处理，把低置信度的预测标记出来供人工复核。

### 部署工作流

**注意：** 下面的部署会创建产生费用的 AWS 资源。Amazon Simple Storage Service（Amazon S3）存储、AWS Lambda 调用、Amazon Bedrock 模型推理和 Amazon DynamoDB 存储都有相关成本。不再需要这些资源时请将其删除，以避免持续计费。

我们的生产部署通过以下工作流处理 .eml 文件：

- **邮件摄取：** 货运电子邮件以 .eml 文件形式到达 Amazon S3。
- **预处理：** AWS Lambda 抽取邮件正文与元数据。
- **推理：** Amazon Bedrock 端点用蒸馏后的 Nova Lite 模型处理文本。
- **实体抽取：** 模型返回 23 种实体类型及其置信度分数。
- **后处理：** 应用校验规则与置信度过滤。
- **输出：** 包含抽取实体的结构化 JSON，存储在 Amazon DynamoDB 中。

```
import boto3
import json

bedrock_runtime = boto3.client('bedrock-runtime')

def extract_entities(email_text):
    response = bedrock_runtime.invoke_model(
        modelId='<custom model arn>',
        body=json.dumps({
            "inputText": email_text,
            "taskType": "NER",
            "entityTypes": [
                "AWB_NUMBER", "FLIGHT_NUMBER", "WEIGHT_GROSS",
                "WEIGHT_CHARGEABLE", "DIMENSIONS", "COMMODITY",
                "SHIPPER", "CONSIGNEE", "HANDLING_CODE",
                # ... 14 more entity types
            ]
        })
    )

    result = json.loads(response['body'].read())
    return result['entities']
```

关于 Lambda 集成模式，参见 [AWS Lambda with Amazon Bedrock](https://docs.aws.amazon.com/lambda/latest/dg/services-bedrock.html)。

整个 pipeline 处理电子邮件的时间不到 2 秒，准确率为 95.085%，满足我们的实时处理要求。

## 结论

本文展示了 IBS Software 如何利用 Amazon Bedrock 的托管蒸馏能力，为货运物流构建一个具有成本效益的双语 NER 系统。该系统取得 95.085% 的 F1-Score，同时把运营成本降低 14 倍。蒸馏后的 Nova Lite 模型保留了教师模型 98% 的性能，非常适合高吞吐量的生产工作负载。

我们的核心收获是，Amazon Bedrock 的托管蒸馏能力减轻了开源框架带来的复杂度。token 级知识蒸馏在英文和日文两种语言上都保住了准确率，2048 token 的序列长度足以容纳典型的货运邮件长度。生产部署通过与 AWS Lambda 和 Amazon S3 集成完成，所需的定制基础设施极少。
