# 使用 Strands Agents 与 Amazon Nova 的多 Agent 协作模式

多 Agent 生成式 AI 系统使用多个专门的 AI agent 协同工作，处理超出任何单一模型能力的复杂、多面向任务。通过组合具备不同技能或模态（例如语言、视觉、音频、视频）的 agent，这些系统能够以并行或顺序方式处理任务，产出更稳健的结果。[近期研究表明，多 Agent 协作能显著提升复杂目标的成功率](https://arxiv.org/html/2412.05449v1)（相比单 Agent 方法最高可高出 70%）。这类多 Agent 协作存在几种不同的模式。无论是把专门任务委派出去的 manager agent（Agent as tools）、一群头脑风暴者（Swarms）、精心连线的专家 agent 图（Agent Graph），还是结构化的 pipeline（agent workflow），正确的设计模式配合正确的工具，都会显著提升系统的有效性。

然而，多 Agent 系统的挑战在于其算力需求**。** 现代多 Agent 应用在用户的一次请求中可能发出数千条 prompt，因为 agent 会彼此头脑风暴、批评并改进答案。这种高强度的工作流带来两项关键要求：高吞吐（tokens-per-second）与成本效率（dollars-per-million-tokens）。这正是 Amazon Nova 成为多 Agent 架构非常合适的基础模型（FM）选择的原因：

- **极速吞吐：** Nova Micro 的流式输出超过每秒 200 个 token，首 token 延迟低于一秒，即便是大规模 agent 集群也能对终端用户保持响应。
- **稳定的结构化输出：** 借助最新的受限解码（constrained decoding）实现，Amazon Nova 模型可以产出一致的结构化输出，并提升工具调用的准确率。
- **极低成本：** 凭借 Nova Micro 与 Nova Lite 的低价，团队能够负担多 Agent 推理所需的 token 量。

由于每一次 agent 调用都很便宜，开发者可以放手让开放式 Strands Agents SDK 这类编排框架按任务创建 Nova agent、重试或交叉验证答案，并持续迭代直到收敛到最佳结果——全程无需担心推理账单失控。反过来，多 Agent 生成式 AI 系统也通过以下方式释放 Amazon Nova 的全部潜力：

- **迭代式自我改进：** agent 可以让 Nova 反思自己的答案、批评其中的弱点并重新生成，往往能在不做任何微调的情况下把成功率提升两位数的百分比。
- **冗余与故障转移：** 并行运行多个 Nova agent（例如 *consensus* 或 *swarm* 模式）可提升答案质量与韧性——一个较弱的回答会被投票否决或自动重试。

本文探讨多 Agent、多模态 AI 系统的四种关键协作模式——Agents as Tools、Swarms Agents、Agent Graphs 与 Agent Workflows——并讨论在何种场景、如何用开源的 AWS Strands Agents SDK 搭配 Amazon Nova 模型来应用它们。作为 agent 编排框架，Strands 的设计目标是轻量、易学——它只用到少量概念，并依赖 Python 原生结构来组合 agent。另一个优势是它的模型驱动方式：Strands 鼓励让 FM 自行决定步骤顺序（agent loop 向 FM 咨询下一步做什么，而不是把流程硬编码）。这能利用 FM 强大的推理能力来做编排决策，减少固定的代码逻辑。下面每个模式章节都会给出概念概述与示意图、真实场景用例、优缺点，以及说明实现方式的代码示例。

## Agents as Tools 模式

Agents as Tools 模式把专门的 AI agent 包装成可调用的工具，由主编排（orchestrator）agent 调用。这形成一种分层的团队结构：顶层 agent 扮演 manager，把具体查询委派给专家子 agent，然后整合它们的输出。每个工具 agent 专注于某个特定领域或模态，而编排器决定用户请求的每一部分该调用哪个工具。这种设置模拟了人类场景：团队负责人咨询各位专家，而不是试图独自完成所有事情。通过把工作交给专家 agent，编排器能比单体 agent 提供更准确、更多面的回答。

### 用例、优点与缺点

当一个用户查询自然拆分成需要不同专长的独立子任务时，这一模式最为理想。例如：

- 一个多领域助手回答涉及诸如旅行规划、产品推荐与研究的问题——编排器可以把不同部分分别路由给 Trip Planner、Product Recommender 或 Researcher agent。
- 多模态任务，其中一个 agent 处理图像或语音输入，另一个处理文本（编排器把合适的模态专属 agent 选作工具）。
- 任何需要专门技能或工具的系统（例如，教学辅导 agent 在处理编程问题时调用代码执行 agent，或客户服务机器人调用数据库查询 agent）。

**优点：**

- **关注点分离：** 每个 agent 都有聚焦的角色与专长，使整个系统更容易理解和扩展。
- **模块化：** 专家（工具）可以独立新增或更新而不影响其他部分，只要编排器与它们之间的接口保持一致。
- **分层决策：** 编排器提供清晰的指挥链，为每项任务决定使用哪位专家，这能提升可靠性。
- **性能优化：** 每个 agent 都可以为其特定任务定制 prompt、模型或工具，可能比通才 agent 获得更好的准确率或效率。

**缺点：**

- **编排器复杂度：** 顶层 agent 必须正确识别要调用哪个工具 agent、以及如何整合结果。这需要细致的 prompt 工程或路由逻辑（如果编排器误解了查询，就有出错的风险）。
- **单点故障：** 编排器 agent 成为关键组件；一旦它失败或做出糟糕的决策，整个系统的输出都可能受损。
- **上下文共享与整合：** 专家 agent 通常只收到其具体查询中显式包含的信息，这限制了它们获取更广上下文的能力。因此，编排器必须汇总来自不同 agent 的输出。如果各位专家各自孤立工作，要保证最终答案连贯（避免矛盾或缺口）可能很困难。

### Strands SDK 示例

Strands Agents SDK 让 Agents as Tools 的实现变得容易：用 @tool 装饰器把 python 函数变成可调用的工具。每个工具 agent 本质上就是一个 LLM（或其他服务），拥有自己的 prompt 或指令，并以可调用函数的形式暴露。被调用时，专家 agent 只收到编排器传入的信息（通常就是具体的子任务 prompt），然后返回其输出。编排器再结合上下文使用该输出，可能继续调用其他工具，或产出最终答案。在下面的代码中，我们定义一个专门的研究助理 agent 作为工具，然后创建一个编排器，让它（连同其他领域专属 agent）用索引知识库或网络搜索到的信息来回答问题：

```
from strands import Agent
from strands_tools import retrieve, http_request

# Define a specialized Research Assistant agent as a tool
RESEARCH_ASSISTANT_PROMPT = (
    "You are a specialized research assistant. Provide factual, cited answers."
)

@tool
def research_assistant(query: str) -> str:
    """Provide well-sourced research answers for a given query."""
    try:
        # Create an agent with a research-focused prompt and tools
        research_agent = Agent(
            system_prompt=RESEARCH_ASSISTANT_PROMPT,
            tools=[retrieve, http_request]  # e.g. multimodal knowledge base retrieval, web retrieval tools
        )
        response = research_agent(query)
        return str(response)
    except Exception as e:
        return f"Error in research assistant: {e}"
```

以类似方式，你还可以定义其他工具 agent，例如 `editor_assistant` 或 `image_creation_assistant`，各自拥有面向自身领域的 system prompt 与工具。专家 agent 定义好之后，编排器 agent 就可以把它们加入自己的工具列表：

```
# Define the orchestrator agent with all specialized tools
MAIN_SYSTEM_PROMPT = "You are an orchestrator coordinating multiple domain experts."

orchestrator = Agent(
    system_prompt=MAIN_SYSTEM_PROMPT,
    tools=[research_assistant, editor_assistant, image_creation_assistant]
)

# Process a complex user query through the orchestrator
query = "I'm planning a hiking trip to Patagonia and need the right gear."
response = orchestrator(query)
print(response)
```

在这个示例中，编排器会把查询的不同部分委派给相关专家——例如先使用研究助理，再把该上下文传给编辑助理，以基于所提供上下文产出内容，最后为用户综合出一个合并答案。Agents as Tools 模式实现了强大的专家组合，而这一切都通过 Strands 中的简单函数调用来管理。

## Swarm 模式

*Swarm* 模式由一组同级 agent 就同一任务协同工作，彼此直接、迭代地交换信息。其灵感来自自然界中的群体智能（如蚁群或蜂群）：大量简单单元相互作用，产生复杂的涌现行为。在 AI swarm 中，每个 agent 可能从不同视角（或使用不同数据、不同模态）切入问题，并共享自己的发现，使其他 agent 得以改进各自的结果。没有中心控制器对过程事无巨细地管理；相反，协调是去中心化的，往往通过共享记忆或消息空间发生。于是 swarm 集体探索解空间，并通过多轮沟通收敛到一个答案。

![Swarm 模式下的多 Agent 协作](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/17/multi-agent-nova-image-3.jpg)

***图 3：**** Swarms Agents——一个去中心化的 agent 网状结构（例如 Research、Creative、Critical、Summarizer），彼此通信以协作解决问题。没有单一的编排器；智能从 agent 们共同分享与改进想法的过程中涌现。*

swarm 的关键特征包括信息共享、agent 专长化、冗余，以及超越各 agent 个体之和的涌现智能潜力。重要的是，控制是去中心化的——不存在某个 agent 为其他 agent 分配角色。agent 遵循相对简单的局部规则（“把我的结果分享给别人，看到别人的结果后再修改自己的答案”），复杂的全局行为就从这些交互中涌现。例如，一个 agent 专注于创意头脑风暴，另一个负责事实准确性，再一个负责批评解决方案，最后一个负责总结；通过两轮或更多轮的交换想法，它们共同产出均衡且经过充分检验的结果。

### 用例、优点与缺点

当问题受益于多元视角或并行探索时，swarm 模式很有用：

- **头脑风暴与构思：** 多个生成式 agent 可以并行提出想法或方案（有些大胆有创意，有些更保守），然后集体加以改进。相比单个 agent 的答案，这可能带来更具创新性的结果。
- **复杂推理任务：** agent 可以通过结构化的交接在彼此的工作之上继续推进。例如，一个 agent 分析问题，交给另一个设计解决方案，再交给第三个进行验证与改进。这种顺序协作往往比并行方式产出更高质量的结果。
- **多阶段工作流：** 不同 agent 可以处理复杂任务的不同阶段。在金融分析中，研究 agent 收集数据，交给分析 agent 提炼洞察，再交给报告 agent 做最终呈现。每次交接都包含上下文与中间结果。
- **迭代改进：** 通过多轮迭代与交接，swarm 可以逐步改进方案。一个 agent 的初稿会被后续 agent 增强，每次迭代都在可配置的时间窗口内基于之前的工作继续推进。
- **容错处理：** 借助超时控制与交接机制，swarm 可以从容应对 agent 失败。如果某个 agent 超时，swarm 可以用已有结果继续，或换其他 agent 重试。

**优点：**

- **思维多样性：** 每个 agent 可以采取独特的策略或视角，产出更丰富的想法集合。通过吸纳所有 agent 的输入，最终结果可能更全面、更均衡。
- **涌现式改进：** 通过迭代沟通，swarm 往往能比单趟方式更好地改进方案。agent 可以纠正彼此的错误，或在彼此的部分方案上继续构建，从而得到高质量的结果。
- **没有单点故障：** 由于没有中心编排器，系统可能更具容错性——如果一个 agent 表现不佳，其他 agent 可以弥补（也不存在某个 agent 一旦失败就使整个流程崩溃的情况）。

**缺点：**

- **对超时敏感：** 过于激进的超时设置可能中断有产出的工作，而宽松的超时又可能在 agent 卡住时造成资源利用低效。
- **迭代开销：** 多轮迭代会累积成本与延迟，尤其是使用大语言模型时，需要在质量与效率之间小心权衡。

### Strands SDK 示例

在下面的示例中，swarm 包含三个协作 agent：

- `research_agent`：查找事实性信息
- `analysis_agent`：通过 API 分析实时市场数据
- `writer_agent`：汇编最终答案

```
from strands import Agent
from strands.models import BedrockModel
from strands.multiagent import Swarm

# Create specialized agents for different tasks
research_agent = Agent(
    name="researcher",
    system_prompt="Research and gather information, then hand off to analyst.",
    model=BedrockModel(model_id="us.amazon.nova-pro-v1:0", region="us-east-1"),
    tools=[web_search, knowledge_base]
)

analysis_agent = Agent(
    name="analyst", 
    system_prompt="Analyze research data and hand off to writer.",
    model=BedrockModel(model_id="us.amazon.nova-pro-v1:0", region="us-east-1"),
    tools=[data_analysis, financial_metrics]
)

writer_agent = Agent(
    name="writer",
    system_prompt="Create final report based on research and analysis.",
    model=BedrockModel(model_id="us.amazon.nova-pro-v1:0", region="us-east-1"),
    tools=[editor, formatter]
)

# Configure swarm with handoff and timeout controls
swarm = Swarm(
    agents=[research_agent, analysis_agent, writer_agent],
    max_handoffs=2,           # Allow up to 2 handoffs between agents
    max_iterations=3,         # Up to 3 rounds of refinement
    execution_timeout=300.0,  # Total swarm timeout (5 minutes)
    node_timeout=60.0        # Individual agent timeout (1 minute)
)

# Execute collaborative workflow
result = swarm("Analyze Q3 financial performance and create executive summary")
print(f"Final result: {result.final_response}")
print(f"Collaboration path: {[node.node_id for node in result.node_history]}")
```

这种做法免去了手写协调代码的需要，并能对协作模式进行细粒度控制。swarm 会自动管理 agent 之间的交接、记录会话历史，并确认执行在指定超时内完成。agent 可以专注于自己的专门任务，而由 swarm 框架处理复杂的编排、共享记忆管理与容错机制。关键优势在于：复杂的多 Agent 工作流变得只需配置几个参数，同时仍通过交接与迭代机制支持复杂的协作模式。

## Graph 模式

agent graph 定义了一个结构化的 agent 网络，其有向连接决定信息如何在它们之间流动。与 swarm 的自由网状结构不同，agent graph 通常由开发者针对特定工作流或组织层级来设计。图中的每个节点都是一个具有明确定义角色的 agent，每条边代表一条通信或交接通道（可能是单向，也可能是双向）。这一模式有助于对 agent 间交互的顺序与方向实施精确控制。例如，你可以把 agent 排成多级层次：顶层主管 agent 把任务拆成若干部分，把子任务交给中层 manager agent，后者再委派给低层专家 agent，结果沿链条逐级回流。你也可以定义星形拓扑，由一个中心 agent 协调一组外围 agent（类似 Agents as Tools，但可能带有反馈回路），或任何适合问题领域的自定义图拓扑（树、无环图）。

![Graph agent 模式示意图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/17/multi-agent-nova-image-5.jpg)

***图 5：**** Graph agent 模式示意。*

agent graph 如下图所示。（拓扑示例——层级式）：agent 以多级图相连。planner agent 把查询交给一个强力的 supervisor agent，再委派给中层 agent Agent 1、Agent 2、Agent 3 与 Agent 4；每个中层 agent 各自管理一支专家 agent 团队。信息沿有向边流动。分支可以结合业务逻辑，依据条件边决定使用哪个 agent。agent graph 的关键好处是可预测性与控制力。通过在图中显式连接 agent，开发者可以核实事实核查 agent 始终在输出到达最终报告 agent 之前验证生成 agent 的产出，或信息只以获准的方式流动（这对安全很有用，可避免某些 agent 在不需要时看到敏感数据）。当你需要自定义通信模式、明确的专门角色以及细粒度的信息流管理时，这一模式最为出色。

### 用例、优点与缺点

agent graph 模式在以下情形尤其出彩：

- **你拥有复杂的多阶段决策流程**，例如企业工作流中，牵头 agent 把任务委派给各自独立的分析 agent（财务、技术、社会影响分析），而每个分析 agent 还可能进一步委派给子 agent。图结构可以映照组织架构图或决策树，使每一步的输出都在更高层级被评审与整合。
- **你需要受控的工具访问与数据流**：假设某些 agent 可以调用外部工具或 API，而另一些（出于安全或成本原因）不应如此。通过构造图结构，你可以把使用工具的 agent 隔离出来，让其他 agent 通过它们转发请求。
- **为了避免放任自流的通信**：如果任务需要紧密协调与清晰的角色，agent graph 优于 swarm。例如，在多 agent 的客户支持系统（计费、技术支持、销售）中，你可能不希望它们彼此任意通信。图可以强制所有通信都经过中心协调者，或遵循既定的升级路径（如星形或树形拓扑）。

**优点：**

- **细粒度控制：** 开发者显式定义谁与谁通信。这可以避免非预期的交互，也让系统行为更容易推理，例如你确切知道 Report Aggregator Agent 只从 Fact-Checker 与 Analysis agent 接收输入，别无其他。
- **上下文与状态管理：** 图的边可以看作持久通道——可能维护状态或使用消息队列。这对长时间运行的上下文很有用。
- **可预测的执行流程：** 与 swarm（交换的时机与顺序是涌现出来的）不同，agent graph 遵循更确定性的流程。这对需要确定性输出或逐步追踪的工作流有利。借助图的通路，更容易追踪某个输入如何流经系统。

**缺点：**

- **设计成本：** 确定合适的图拓扑可能很有挑战。你必须充分理解问题领域，才能有效划分任务并安排 agent。过度设计图可能导致僵化；设计不足则可能享受不到这一模式的好处。
- **动态适应性较弱：** 固定的图不如 swarm 那样能自发适应。如果来了稍偏离预期模式的查询，编排好的通路可能无法从容处理（除非你内置大量路由逻辑）。相比之下，swarm 或工具方式只要尝试不同工具或 agent 就能动态调整。
- **深层图的延迟：** 如果图有很多层级（如高耸的层级结构），信息必须依次经过多个 agent，这会增加延迟。每一跳都会带来开销。例如在三级层次中，一条消息可能向下经过两个中间 agent 再向上返回——这比扁平架构有更多的往返。

### Strands SDK 示例

Strands SDK 中的 GraphBuilder 类提供了一种精简的方式来实现 agent graph 模式。它处理 agent 通信与网络拓扑管理的复杂性，帮助开发者专注于 agent 行为。它内置支持定义图拓扑、消息处理（传输数据的机制）以及 agent 之间的方向（单向或双向信息流）。对每个 agent，开发者都可以实现业务逻辑来处理回退机制与 agent 响应评估。

```
from strands import Agent
from strands_tools import agent_graph

builder = GraphBuilder()

# Add nodes
builder.add_node(coord_agent, "research")
builder.add_node(get_stock_prices_agent, "stock_price_search")
builder.add_node(fin_web_searcher_agent, "fin_web_searcher")
builder.add_node(report_writer_agent, "report")
builder.add_node(image_generator_agent, "create_display_img")

# Add edges (dependencies) - star topology with coordinator at center
builder.add_edge("research", "stock_price_search")
builder.add_edge("research", "fin_web_searcher")
builder.add_edge("research", "report")
builder.add_edge("research", "create_display_img")

# Set entry point
builder.set_entry_point("research")

# Build the graph
graph = builder.build()

# Run the graph
result = graph("Analyze Q3 financial performance and create executive summary")
```

使用 GraphBuilder 为多 Agent 工作流定义节点、边与入口点。在此基础上，你可以通过各种组合构建复杂模式：

- **动态工作流**：为边添加条件逻辑，依据运行时决策进行路由
- **嵌套架构**：把整张图或 swarm 作为节点嵌入更大的图结构

这些示例只展现了用 Strands SDK 构建图时无穷架构可能性的一小部分。

这张 agent graph 可运行、可部署的完整代码示例见 [该 Github 仓库](https://github.com/aws-samples/amazon-nova-samples/tree/main/multimodal-understanding/repeatable-patterns/27-multi-agent-orchastration-with-strands)。

更多信息请参阅 [graphs 文档](https://strandsagents.com/latest/documentation/docs/user-guide/concepts/multi-agent/graph/)。

## Workflow 模式

workflow 模式按照预定义的任务顺序或依赖图来编排多个 agent——很像经典工作流或 pipeline，只是由 AI agent 执行各个步骤。这一模式强调任务排序与依赖管理：你把复杂工作显式拆成一系列离散任务，分配给不同 agent，并定义这些任务之间的依赖关系（有些任务可以并行，另一些必须等待特定输出）。在 workflow 模式中，每个 agent 都在正确的时间完成自己那一份，并把输出作为输入传给链条中下一个相关 agent。

![Workflow 模式下的多 Agent 协作](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/17/multi-agent-nova-image-6.jpg)

***图 6：**** workflow agent 模式。一个执行多步过程的 agent 有向无环图。在此示例中，A0（入口点）把查询分给三个 agent（Agent 1、2、3），它们再汇入后续步骤（Agent 4、5、6、7），最终汇聚到产出响应的 Agent 8。这展示了显式的任务依赖与执行顺序如何构成一个工作流。*

你可以把 agent workflow 看作任务的有向无环图（DAG），其中每个任务由一个 agent 执行。这与 agent graph 类似，但 workflow 通常更强调一个流程从开始到结束的一次性执行（像一次 pipeline 运行），而 agent graph 可能是持续处理任务的持久 agent 网络。workflow 非常适合具有清晰阶段结构的过程——例如数据处理 pipeline、带检查点的多步推理，或任何某些步骤（任务）必须严格按序、或必须在满足某些前置条件后才能发生的情形。workflow 模式也很契合需要在复杂作业的每一步进行监控、日志记录或错误恢复的系统（因为每个任务的执行都可以独立追踪）。

### 用例、优点与缺点

在处理具有明确定义阶段的复杂多步任务时使用 agent workflow：

- **带评审的内容生成：** 一个 agent 起草文章，另一个 agent（或工具）核查事实，再一个 agent 做风格编辑，还有一个 agent 批准或发布。这些步骤按顺序执行（可能带一些并行检查），失败时可能会重复。
- **需要协调与依赖处理的情形：** 如果某些任务可以并行，workflow 可以分支；如果某些任务必须汇聚，workflow 可以汇合。例如，职位申请筛选可以让一个 AI agent 给简历打分，同时让另一个 agent 进行技能测试，最后由一个 agent 用两个结果做出决定。
- **长时间运行或受监控的过程：** 借助 workflow，你可以在任务级别暂停、恢复或重试。如果某个 agent 失败或某一步需要重做，你可以重置那一步而不必重跑整个工作流——这对健壮的生产 pipeline 很有用。

**优点：**

- **结构清晰且可靠：** 顺序与依赖的显式定义意味着执行路径可预测、可重复。对于正确性与可审计性重要的过程，这一点至关重要（你可以记录每一步的输入与输出）。
- **并行效率：** workflow 可以为独立任务指定并行分支，更好地利用资源（不同于单个 agent 顺序完成一切）。当分支需要汇合时，框架会做同步。
- **错误处理与恢复：** 由于任务是离散的，workflow 控制器可以捕获某个 agent 在某一步的失败，并只针对那一步实施重试或回退。无需重启整个流程。这种局部化的错误处理提升了健壮性。
- **每一步使用专门的 agent：** 与 Agents as Tools 类似，每一步都可以使用最适合该子任务的 agent（例如先翻译 agent、再总结 agent）。workflow 确保这些专门 agent 以正确的顺序、配合正确的数据运行。
- **状态管理：** workflow 可以显式地在各步骤之间维护状态上下文（例如携带任务 ID 或收集输出）。Strands 的 workflow 工具支持进度追踪、暂停，甚至恢复跨越单次会话持久存在的工作流。

**缺点：**

- **对新颖情形的灵活性较差：** workflow 能很好地处理预期内的序列，但如果用户查询不符合预定义流程，系统可能无法适应。它不如 swarm 那样有探索性，也不如 agent graph 那样能动态路由。本质上，workflow 的智能程度只取决于预定义的流程。
- **前期投入：** 你需要分解任务并定义依赖。如果这项分析有误或不完整，workflow 可能失败或产出次优结果。设计好的 workflow 可能需要领域专业知识来确定正确的拆分。
- **潜在利用不足：** 如果 workflow 有很多顺序步骤，它可能比能并行执行部分步骤的 agent 更慢。例如，单个大语言模型可能在阅读文本的同时在内部做总结，而严格顺序的 workflow 会在阅读与总结 agent 之间强制一次完整交接，可能带来额外开销。
- **编排开销：** 管理多个 agent 的执行（尤其是使用通用 workflow 引擎时）会带来开销。在简单场景中，单个 agent 通过 prompt 工程就能达成目标。workflow 在复杂场景中大放异彩，但对琐碎任务而言，编排开销是不必要的。

### Strands SDK 示例

Strands Agent SDK 并不强制所有 agent 之间进行严格的会话——流程需要你自己编写——但它极简的抽象让并行或顺序编排变得直接（如前面示例用普通 Python async 代码并行运行三个诗人 agent 那样）。使用 Strands Agent SDK 的另一个优势是分层 agent 概念：借助 @tool 装饰器，你可以像前面展示的那样自然地构建 agent 层次，从而使 manager/sub-agent 模式的实现变得直观。下面展示一个简单的手动工作流：三个 agent（researcher、analyst、writer）执行一系列步骤。

```
from strands import Agent
from strands.models import BedrockModel

# Create specialized agents for each step
researcher = Agent(
    system_prompt="You are a research specialist. Find key information.",
    model=BedrockModel(model_id="us.amazon.nova-pro-v1:0", region="us-east-1")
)

analyst = Agent(
    system_prompt="You analyze research data and extract insights.",
    model=BedrockModel(model_id="us.amazon.nova-pro-v1:0", region="us-east-1")
)

writer = Agent(
    system_prompt="You create polished reports based on analysis.",
    model=BedrockModel(model_id="us.amazon.nova-pro-v1:0", region="us-east-1")
)

# Define the workflow function
def process_workflow(topic: str):
    # Step 1: Research
    research_results = researcher(f"Research the latest developments in {topic}")
    
    # Step 2: Analysis
    analysis = analyst(f"Analyze these findings: {research_results}")
    
    # Step 3: Reporting
    final_report = writer(f"Write a report based on this analysis: {analysis}")
    
    return final_report

# Execute the workflow
result = process_workflow("artificial intelligence in healthcare")
print(result)
```

在这段代码中，我们依次显式调用每个 agent，把前一个的输出作为下一个的输入。`process_workflow` 函数编排这个序列。如果研究者 agent 返回大量数据，我们可能先精简或截断再传给分析 agent，依此类推，但模式很清晰：线性交接。

智能文档处理（IDP）工作流是 agentic workflow 的一个很好的实战范例。IDP 工作流之所以是 agentic workflow 的典型例子，是因为它天然涉及多个离散却相互依赖的步骤，能受益于任务专门化的 agent、动态协调与自适应决策。典型 IDP 工作流的代码示例见这份[解决方案指南](https://aws.amazon.com/solutions/guidance/agentic-workflow-assistants-on-aws/)。

更多信息请参阅 [workflows 文档](https://strandsagents.com/latest/documentation/docs/user-guide/concepts/multi-agent/workflow/)。

## 结论

多 Agent 协作释放出单一模型无法匹敌的生成式 AI 能力——尤其当每个 agent 都能借助 Amazon Nova 的低延迟、低成本 token 生成，并通过开源的 Strands Agents SDK 无缝协作时。Nova 每千 token 低至零点几分钱的超低定价，加上超过每秒 200 token 的高吞吐，意味着团队可以自由地试验更深的推理循环、冗余与工具使用，而不必担心成本失控。Strands 提供恰到好处的编排：一套 Python 风格的 API 覆盖 Agents as Tools、swarms、graphs 与 workflow 模式，集成的 Bedrock 模型封装、用于上下文交换的共享记忆，以及内置遥测。无论你是在构建多模态问答系统、自主文档处理 pipeline，还是创意头脑风暴助手，Amazon Nova 与 Strands 的组合都能帮你从单个原型 agent 扩展到生产级多 Agent 架构——同时保持现代企业负载所需的速度、准确性与成本画像。现在正是应用这些模式的最佳时机，让你的生成式 AI 应用取得真正超越各 Nova 驱动部分之和的成果。
