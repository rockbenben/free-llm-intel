# 为企业工作负载部署 Anthropic Claude apps gateway for AWS

在整个组织内部署 [Claude Code](https://claude.com/product/claude-code) 与 [Claude Desktop](https://claude.com/product/overview) 的 AI 管理员，需要对身份认证、模型访问、成本归因与支出管控进行集中管理。这些控制措施能降低运维开销，并在规模化时一致地落实治理。

[Claude apps gateway](https://code.claude.com/docs/en/claude-apps-gateway) 在这些应用与 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 或 [Claude Platform on AWS](https://aws.amazon.com/claude-platform/) 之间提供自托管的治理层。

在[发布文章](https://aws.amazon.com/blogs/machine-learning/introducing-claude-apps-gateway-for-aws/)的基础上，本文给出一个生产参考部署，涵盖端到端架构、企业部署模式、成本与实现资源。

## 架构

本节介绍参考部署拓扑，以及请求如何流经 gateway。

### 部署拓扑

Claude apps gateway 就打包在开发者已经在用的那个 [Claude Code CLI](https://code.claude.com/docs/en/quickstart) 二进制里。用 `claude gateway --config gateway.yaml` 启动后，它以服务器模式运行，并在启动时加载 YAML 配置。在这个参考部署中，容器运行在你[虚拟私有云](https://aws.amazon.com/vpc/)（VPC）内的 [AWS Fargate](https://aws.amazon.com/fargate/) 上。同一个镜像也可以运行在 [Amazon Elastic Kubernetes Service](https://aws.amazon.com/eks/)（Amazon EKS）或 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2/)（Amazon EC2）上，前提是其中之一更贴合你现有的环境。

参考架构使用以下组件：

- **计算与状态：** 每个 AWS Fargate 任务运行一个无状态 gateway 容器。用于 PostgreSQL 的 [Amazon Relational Database Service](https://aws.amazon.com/rds/)（Amazon RDS）存储短生命周期的登录状态，包括设备码与会话。启用支出限额后，它还会存储按用户划分的支出计数器与审计记录。认证状态存放在数据库中而不是任务里，这意味着任何任务都能处理任何请求，负载均衡器上不需要粘性会话。
- **入口与私有 DNS：** 内部 [Application Load Balancer](https://aws.amazon.com/elasticloadbalancing/application-load-balancer/) 使用 [AWS Certificate Manager](https://aws.amazon.com/certificate-manager/) 证书终止 TLS。[Amazon Route 53](https://aws.amazon.com/route53/) 私有托管区把 gateway 解析为可通过 VPN、[AWS Direct Connect](https://aws.amazon.com/directconnect/) 或等效私有连接访问的私有 IP 地址。
- **服务连通性：** VPC 端点让受支持的 AWS 服务流量保持私有，[NAT gateway](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-nat-gateway.html) 则提供其他必要的出网能力。
- **上游凭证：** gateway 使用分配给 gateway 任务的 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色向 Amazon Bedrock 认证。Claude Platform on AWS 的 API key 与其他静态凭证仍保存在 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 中。没有任何上游凭证被分发到开发者机器上。

**运维提示：** 请把负载均衡器的空闲超时配置为大于预期中最长的无数据间隔。默认值是 60 秒。负载均衡器会终止空闲时间超过所配置超时的连接。请同时检查延迟返回的非流式响应与流式块之间的停顿。

### 请求流

**登录（每个会话一次）。** 平台团队分发[受管设置](https://code.claude.com/docs/en/claude-apps-gateway#connect-developers)，把 Claude Code 与 Claude Desktop 指向 gateway 的私有 URL。当开发者执行 `/login` 时，客户端启动 OAuth 2.0 设备授权流程，并打开浏览器通过你的 [OpenID Connect](https://openid.net/developers/how-connect-works/)（OIDC）身份提供方完成认证。浏览器也必须能访问 gateway 的私有端点，因为设备验证页面由 gateway 提供。认证完成后，gateway 签发一个短生命周期 bearer token，默认有效期为 1 小时。此后会话在后台静默刷新。

**推理（每次请求）。** 每个推理请求都会携带 bearer token。gateway 校验它、解析开发者身份与组成员关系、应用匹配的策略、评估适用的支出上限，然后把请求路由到 Amazon Bedrock 或 Claude Platform on AWS。响应流式返回客户端。客户端发出用量指标，gateway 通过 OpenTelemetry Protocol（OTLP）把这些指标转发到你配置的 collector。指标归属于用于策略评估的那个已认证身份。

部署脚本与配置模板见[配套仓库](https://github.com/aws-samples/anthropic-on-aws/tree/main/claude-apps-gateway)。运维指引见[部署指南](https://code.claude.com/docs/en/claude-apps-gateway-deploy)。设备码验证与 token 生命周期细节见 [Claude apps gateway 文档](https://code.claude.com/docs/en/claude-apps-gateway)。

## 它解决了什么

gateway 应对五项治理需求，下文逐项说明。

### 1. 身份：SSO 认证

gateway 把认证委托给你的 OIDC 身份提供方。开发者通过浏览器 SSO 登录一次。gateway 签发短生命周期 token，并在后台处理静默刷新。gateway 支持符合 OIDC 的提供方，例如 [Okta](https://www.okta.com/)、[Microsoft Entra ID](https://www.microsoft.com/en-us/security/business/identity-access/microsoft-entra-id)、[Auth0](https://auth0.com/)、[Keycloak](https://www.keycloak.org/) 或 [Amazon Cognito](https://aws.amazon.com/pm/cognito/?trk=4cc82392-4dab-406f-91c8-96680bbf531f&sc_channel=ps&ef_id=CjwKCAjwpqHTBhAcEiwAj2Afui4ZVRj0ExkCug9kd9UjQQiWUUzkm7uaDb_Fe4c7-G0YsZHzj2eKgBoCAvIQAvD_BwE&gads_camp=23528572748&gads_ag=198422384291&gads_ad=795811958064&gads_kw=amazon%20cognito&gads_matchtype=e&gads_network=g&gads_device=c&gads_geo=9042989&gad_campaignid=23528572748&gbraid=0AAAAADjHtp8i14OymISrCSMhtAjqFD58j&gclid=CjwKCAjwpqHTBhAcEiwAj2Afui4ZVRj0ExkCug9kd9UjQQiWUUzkm7uaDb_Fe4c7-G0YsZHzj2eKgBoCAvIQAvD_BwE)。

这为你带来集中式的 OIDC 认证，开发者机器上无需任何上游凭证；通过从身份提供方移除用户即可即时完成离职下线；并且无需自定义插桩，就能在请求之间保持一致的按用户归因。

gateway 自身不维护任何用户目录。没有需要预先创建的账户，也没有需要配置的 SCIM 同步。你的身份提供方为用户分配什么组，gateway 就用这些组做策略匹配，一对一，没有转换层。用户与组完全在你的身份提供方中管理，gateway 会在下一次会话刷新时读取变更。离职下线就是从身份提供方移除该用户；其会话会在配置的存活时间（默认 1 小时）内过期，无需轮换凭证。

下面的示例展示一个使用 Microsoft Entra ID 配置的 gateway：

```
oidc:
  issuer: https://login.microsoftonline.com/<tenant-id>/v2.0
  client_id: ${OIDC_CLIENT_ID}
  client_secret: ${OIDC_CLIENT_SECRET}
  allowed_email_domains: [company.com]
  groups_claim: roles
```

**注意：** Microsoft Entra ID 默认不包含组或角色声明（claim）。如果你的策略要配合 Entra 应用角色使用 `match: {groups: [...]}`，请在 OIDC 配置中加入 `groups_claim: roles`。没有这一步，gateway 无法解析组成员关系，所有用户都只会匹配兜底策略。

各身份提供方的具体设置说明见[身份提供方设置指南](https://code.claude.com/docs/en/claude-apps-gateway-deploy#identity-provider-setup)。下面的图片从开发者视角展示了 Claude Code 与 Claude Desktop 的登录体验。

### 2. 策略：集中化的模型访问与权限

gateway 在服务端强制模型访问，并以受管设置的形式分发工具权限，按身份提供方中的组划分范围。你在一个 YAML 块里定义每个团队能用哪些模型与能力。策略按声明顺序求值：选中第一个匹配项，然后合并到 `match: {}` 兜底基础上。请以一条 `match: {}` 策略结束列表，它作为兜底，适用于组未匹配到列表中更靠前的具体策略的用户。若没有这一条，未匹配的用户将获得完整目录访问权限。变更会在一小时内传播到已连接的客户端，开发者无需任何操作。

```
Managed:
  policies:
    # Contractors: Haiku only, no web access
    - match: { groups: [contractors] }
      cli:
        availableModels: [claude-sonnet-5, claude-haiku-4-5]
        enforceAvailableModels: true
      permissions:
        deny: ["WebFetch", "WebSearch"]
    # Engineers: full model access with guardrails
    - match: { groups: [engineers] }
      cli:
        availableModels: [claude-opus-4-8, claude-sonnet-5, claude-haiku-4-5]
      permissions:
        allow: [Read, Grep, Bash, Edit]
        deny: ["Read(./.env)", "Read(./secrets/**)"]
    # Catch-all: every other authenticated user. Must be last.
    - match: {}
      cli:
        availableModels: [claude-haiku-4-5, claude-sonnet-5]
```

**注意：** 请在每个策略条目中加入 `desktop: {}` 以启用 Claude Desktop 客户端。没有这一项，gateway 会拒绝匹配该策略的用户的 Desktop 推理请求，即使登录是成功的。

模型访问在服务端强制执行。组内只被授予 Claude Haiku 的开发者，即使改用修改过的客户端也无法绕过限制。Claude Code 与 Claude Desktop 中的模型选择器只显示被允许的模型。包含工具权限与受管设置下发的完整策略 schema，请参阅[配置参考](https://code.claude.com/docs/en/claude-apps-gateway-config#managed)。

### 3. 遥测：按用户归因用量

客户端发出用量指标（`claude_code.token.usage`、`claude_code.cost.usage` 与 `claude_code.active_time.total`），并归属于已认证开发者的身份：用户 ID、邮箱与组成员关系。

图 8：来自 Claude Code 会话的 OpenTelemetry 指标，经 gateway 中继，并由 collector 导出到 Amazon CloudWatch

gateway 通过 [OpenTelemetry Protocol](https://opentelemetry.io/docs/specs/otel/protocol/)（OTLP）把这些遥测数据中继到你配置的 collector。受支持、兼容 OTLP 的后端包括 [Datadog](https://www.datadoghq.com/)、[Splunk](https://www.splunk.com/)、[Grafana](https://grafana.com/)，以及通过 [AWS Distro for OpenTelemetry](https://aws.amazon.com/otel/)（ADOT）collector 接入的 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)。

```
telemetry:
  forward_to:
    - url: https://otel-collector.internal.example.com
      metrics: true
      logs: false
      traces: false
```

日志与 trace 需要显式开启，因为它们可能包含源代码与 prompt 内容。大多数部署从只启用指标开始——指标可提供按用户的成本与用量明细，而不暴露敏感数据。更多信息请参阅 Claude apps gateway 的[配置](https://code.claude.com/docs/en/claude-apps-gateway-config)页面。

### 4. 路由：带故障转移的推理

gateway 按声明顺序把推理路由到一个或多个上游，并在上游不可用、被限流或超时时自动故障转移。跨提供方的故障转移可能改变适用的服务条款与数据处理地域。

你可以用以下上游类型配置各种组合：

```
upstreams:
  # Amazon Bedrock (uses ECS task role, no static keys)
  - name: bedrock-east
    provider: bedrock
    region: us-east-1
    auth: {}
  # Amazon Bedrock in a second region for failover
  - name: bedrock-west
    provider: bedrock
    region: us-west-2
    auth: {}
  # Claude Platform on AWS (cross-provider fallback)
  - name: claude-platform
    provider: anthropicAws
    region: us-east-1
    workspace_id: wrkspc_01ABCDEFGHIJKLMN
    auth:
      api_key: ${ANTHROPIC_AWS_API_KEY}
```

**部署模式**一节展示了如何针对常见场景组合这些构件。完整的上游配置与各提供方特定的认证选项，请参阅[上游参考](https://code.claude.com/docs/en/claude-apps-gateway-config#upstreams)。

### 5. 支出上限：按用户执行预算

AWS Budgets 与 AWS Cost Explorer 提供账户级可见性，但按周期聚合，因此很适合组织级成本治理。gateway 与这些工具互补：除了提供按开发者的用量可见性，它还会在推理发生之前就地强制执行限制。

上限分三个层级设置：组织级默认、按组、以及按用户的覆盖。每个上限都按开发者个人分别适用，而不是共享池。gateway 为每个请求解析生效限额：按用户覆盖优先，其次是适用的组上限中最严格的那个，最后是组织默认值。如果任何层级都没有上限，支出即不受限制。当开发者触达其上限时，gateway 会立即返回 HTTP 429。计数器在每个周期（每日、每周或每月）开始时自动重置。

```
# Org-wide default: $500/month per developer (amounts in USD cents)
curl -X POST https://<gateway>/v1/organizations/spend_limits \
  -H "x-api-key: $ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"scope":{"type":"organization"},"amount":"50000","period":"monthly"}'

# Tighter cap for a specific group: $10/day for contractors
curl -X POST https://<gateway>/v1/organizations/spend_limits \
  -H "x-api-key: $ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"scope":{"type":"rbac_group","rbac_group_id":"contractors"},"amount":"1000","period":"daily"}'

# Instant shutoff for one user: set cap to zero
curl -X POST https://<gateway>/v1/organizations/spend_limits \
  -H "x-api-key: $ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"scope":{"type":"user","user_id":"<oidc-sub>"},"amount":"0","period":"daily"}'
```

支出上限与模型访问控制是分开的。一个组可能拥有 Opus、Sonnet 与 Haiku 的访问权。上限管的是这份访问要花多少钱，而不是哪些模型可用。

管理流程：上限完全通过 Admin API 管理，没有管理界面。平台团队通常用一个脚本把它自动化——在部署流水线中从纳入版本控制的配置文件同步限额，或者通过 Terraform 调用该 API。`GET /v1/organizations/spend_limits/effective` 端点会显示每位开发者解析后的上限与本周期至今的支出，便于报表使用。

**需要注意的限制：** 支出是按 token 数量并按标价估算的。它是实时的熔断器，而不是账单。承诺使用量折扣与协议价不会体现在其中。如果数据库不可用，支出强制默认「失败开放」，允许推理继续。需要严格预算执行的组织可以设置 `fail_closed_on_error: true`，改为阻断请求。要以权威计费为准，请与 Amazon Bedrock 调用日志或 AWS 成本和使用情况报告对账。完整的 Admin API 参考与强制机制，请参阅[支出限额文档](https://code.claude.com/docs/en/claude-apps-gateway-spend-limits)。

## 部署模式

如何部署 gateway，取决于你的组织结构、流量模式与治理要求。没有唯一正确的架构。

把全部 Claude 用量集中到 gateway，可以简化配额管理，并为成本归因与策略执行提供单一位置。新成员上线通常是即时的：新开发者加入身份提供方中的组即获得访问权。代价是 gateway 变成由你平台团队运营的共享基础设施，而需要 Amazon Bedrock 原生特性的工作负载无法经由它路由。

在专用账户中直接运行 Amazon Bedrock，能给每个团队隔离的配额、无共享依赖，并可访问完整的 Amazon Bedrock 特性集。直接部署 Amazon Bedrock 可以使用 IAM 角色，并保留集中计费与审计数据。代价是失去 gateway 的按开发者认证、策略、遥测与支出控制。

大多数组织会以某种形式组合这两种做法。下面的模式展示了从单团队部署到多账户架构的常见配置。请从最接近你当前环境的模式开始，并随用量增长逐步演进。

### 模式 A：单团队、单一 AWS 区域

**推荐用于：** 正在评估 gateway 的团队，或在一个区域内只有一个开发组的组织。

最小化部署：在 `us-east-1` 配置一个 Amazon Bedrock 上游、一个组织级每日支出上限，所有开发者获得相同的模型访问权。从这里开始，等用例需要时再增加复杂度。

图 10：单一账户、单一区域中的单个团队，配组织级每日、每周与每月上限

### 模式 B：多团队与分层访问

**最适合：** 有多个团队、且各团队需要不同模型访问级别与支出限额的组织。身份提供方中的组驱动差异化的策略：

- **平台工程：** Opus + Sonnet + Haiku，每天 50 美元。
- **应用开发：** Sonnet + Haiku，每天 20 美元。
- **外包人员：** 仅 Haiku，每天 5 美元，禁用 Web 工具。

组限额由每位开发者各自继承，而不是作为一个团队预算共享。Admin API 按开发者报告支出并附带组元数据，因此团队总额需要另行聚合。平台团队可以在部署流水线中从纳入版本控制的配置文件同步限额。

图 11：单一账户、单一区域中的多个团队，配团队级每日、每周与每月上限

### 模式 C：Amazon Bedrock + Claude Platform on AWS 混合

**最适合：** 希望以 Amazon Bedrock 为首选上游、以 Claude Platform on AWS 作为溢出容量的组织。请注意，跨提供方的故障转移可能改变适用的服务条款与数据处理地域。

```
upstreams:
  - name: claude-platform
    provider: anthropicAws
    region: us-east-1
    workspace_id: wrkspc_01ABCDEFGHIJKLMN
    auth:
      api_key: ${ANTHROPIC_AWS_API_KEY}
  - name: bedrock
    provider: bedrock
    region: us-east-1
    auth: {}
```

请求优先发往 Amazon Bedrock。只有在被限流或发生故障时，gateway 才回退到 Claude Platform on AWS。

图 12：单账户多上游，使用 Amazon Bedrock 与 Claude Platform on AWS 做故障转移

### 模式 D：开发者工具走 gateway，应用直连 Amazon Bedrock

**推荐用于：** 开发者工具需要治理（SSO、支出上限、遥测），但生产应用以隔离配额与原生特性直连 Amazon Bedrock 的组织。

图 13：生产工作负载留在专用的 Amazon Bedrock 账户中，使用 Amazon Bedrock Knowledge Bases、Agents 与 Flows 等 gateway 不代理的原生特性

### 模式 E：多账户（共享服务）

**推荐用于：** 由中央平台团队运营 gateway、各业务单元在独立账户中拥有自己的 Amazon Bedrock 访问权的组织。

```
upstreams:
  - name: team-alpha
    provider: bedrock
    region: us-east-1
    auth:
      aws_access_key_id: ${TEAM_ALPHA_AKID}
      aws_secret_access_key: ${TEAM_ALPHA_SK}
  - name: team-beta
    provider: bedrock
    region: us-east-1
    auth:
      aws_access_key_id: ${TEAM_BETA_AKID}
      aws_secret_access_key: ${TEAM_BETA_SK}
```

账单落在各团队自己的账户中。gateway 依据模型配置路由到正确的上游。

图 14：多个团队跨多个账户，Bedrock 消耗按账户分别计费

gateway 位于共享服务账户中，每个业务单元的 Amazon Bedrock 用量计入各自的 AWS 账户。gateway 本身并不支持为每个上游承担不同的 IAM 角色，多账户路由需要在上游配置中显式提供凭证。请把这些凭证存入 AWS Secrets Manager 并定期轮换。长期有效的访问密钥是一项重大的安全与运维权衡。可以考虑用一个外部进程，定期把短生命周期的 [AWS Security Token Service](https://docs.aws.amazon.com/STS/latest/APIReference/Welcome.html)（AWS STS）凭证刷新进 gateway 的环境，以减小暴露面。

## 结论

Claude apps gateway 为平台团队提供了在 AWS 上管理 Claude Code 与 Claude Desktop 的单一控制点。一个容器、一个 YAML 配置文件、五项能力：SSO 认证、按组的模型策略、按用户的遥测、带故障转移的多区域路由，以及支出上限。

它不收取按席位计的许可费。以 Amazon Bedrock 作为上游时，没有任何开发者数据离开你的 AWS 账户。开发者运行的仍是他们早已熟悉的那个 `claude` 二进制。在首次登录之后，gateway 对他们而言是透明的。

要开始上手，请克隆[配套 GitHub 仓库](https://github.com/aws-samples/anthropic-on-aws/tree/main/claude-apps-gateway)并选择两种方式之一。两者都会预置同样的 Amazon ECS Fargate 部署：内部 ALB、用于 PostgreSQL 的 Amazon RDS、ECR、Secrets Manager、IAM 任务角色，以及 ADOT 遥测 collector。选择幂等的 `setup.sh` 脚本，可以完全看清每一次 AWS 调用；或选择 [AWS Cloud Development Kit](https://aws.amazon.com/cdk/)（AWS CDK）堆栈，获得受管生命周期。配置细节请参阅 [Claude apps gateway 文档](https://code.claude.com/docs/en/claude-apps-gateway)。
