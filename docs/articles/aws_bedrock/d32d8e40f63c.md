# 将决策模型与 Amazon Bedrock AgentCore 评估结合使用

您在评估代理人时提出的一些问题范围狭窄且可重复。这一回应是否符合政策？此工具调用可以安全批准吗？该答案与检索到的上下文匹配吗？决策模型正好回答了这类问题。它们采用结构化状态和一组固定的允许答案，并返回它们的校准概率，而不是自由格式的文本，其置信度会随着运行而变化。这使得它们非常适合代理评估中的评分步骤，您需要一个可以阈值和信任的标签和数字。

[Amazon Bedrock AgentCore 评估](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 是 Amazon Bedrock AgentCore 的一项功能，可在开发期间按需、针对存储会话的批处理作业以及针对生产流量的在线评估代理的整个生命周期。除了 15 个内置评估器之外，AgentCore 评估还支持自定义评估器，您可以将其定义为 LLM-as-a-judge 或基于代码的评估器。自定义 LLM 法官评估员将您的说明和评级量表应用到 Amazon Bedrock 中的模型中。基于代码的评估器在 AWS Lambda 函数中运行您自己的逻辑，并且该逻辑可以调用您选择的外部系统、模型或 API，包括决策模型。

决策模型适用于具有一组固定答案的问题，知情者一眼就能决定，例如代理是否拒绝请求或响应是否紧扣主题。在您针对自己的流量验证问题后，决策模型足以做出该决策或​​评分，并且您可以将相同的方法扩展到策略中的特定危害或刻板印象类别。由于两个后端都可以在单个请求中回答有关同一状态的多个问题，因此您可以将它们用作筛选层而不是替代层，在指标中运行通过或失败信号来选择需要内置评估器进行更深入评估的轮次，其解释可以帮助您调查出了什么问题。

这篇文章展示了如何通过基于代码的评估器将两个决策模型后端连接到 AgentCore 评估。第一个是 [Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev)，这是 TypeSafe 的托管决策模型。第二个是 [Strands Decider 2B](https://strandsagents.com/blog/introducing-strands-decider/)，一个您自己运行的开源决策模型。在本文结束时，您将了解如何将 AgentCore 评估器输入转换为决策模型请求，并将模型的概率转换回 AgentCore 评估结果。不过，首先，您什么时候应该寻求定制的LLM作为法官评估员，以及决策模型什么时候更适合？下一节将详细介绍什么是决策模型以及所涉及的权衡。

## 决策模型

决策模型是一种小型的专门模型，经过训练可以从一组固定的选项中进行选择并返回校准的置信度分数，而不是生成自由格式的文本。通用大语言模型 (LLM) 评估器会生成带有理由的分数。相反，决策模型会生成预定义答案的概率分布。这为您提供了直接的置信度衡量标准，您可以通过编程方式进行阈值、聚合和操作。这使得决策模型非常适合评估任务，其中判断可以表述为在一组固定选项中的选择：“这个响应是否有根据？”或“代理完成了用户的目标吗？”

当您想要在标签旁边获得经过良好校准的置信度分数而不仅仅是二元判断时，决策模型最有用。当您想要一致地执行特定的规则而不依赖通用的LLM来解释它时，它们也很合适。

Jev（来自 TypeSafe 的托管决策模型）和 [Strands Decider](https://strandsagents.com/blog/introducing-strands-decider/)（来自 Strands Agents 团队的开源 20 亿参数决策模型）都支持三种类型的问题。 “noul”问题提出是/否问题，并返回 0（否）和 1（是）之间的概率。 “选择”问题询问最多 255 个选项中的哪一个适用，返回最可能的选项以及完整的分布和置信度。 “分数”问题询问 2 到 10 个有序级别中的哪一个适用，返回概率加权分数、级别分布和置信度。许多评估标准都符合其中一种类型。 “该响应中的每个事实都得到工具结果的支持吗？”是/否问题，“这个回答在四级标题上有多大帮助？”是一个分数。

## 决策模型与LLM法官

如今，AgentCore 中的内置评估器使用通用 LLM 来评估代理针对某个标准的响应并解释其判断。当评估需要连接证据、识别缺失信息或在任务中深入回答（其中解释与分数一样有用）时，这是很有价值的。决策模型不能替代 LLM 评估器。它们是基于代码的评估器框架使之成为可能的补充。将它们与内置评估器进行更广泛的评估一起用于狭窄的、明确定义的检查。

## 解决方案概述

为了展示这些评估器类型如何协同工作，本文构建了一个 HR Assistant 代理的端到端示例，该示例由基于代码的确定性检查、内置 LLM-as-a-judge 评估器以及由 Jev 或 Strands Decider 2B 支持的决策模型评估器进行评估。

该代理是使用 Strands Agent 构建的，并部署到 AgentCore 运行时，这是 Amazon Bedrock AgentCore 的一项功能。它使用五种工具回答员工问题，这些工具返回固定的模拟数据，例如带薪休假 (PTO) 余额、PTO 请求、人力资源政策、福利和工资单。我们在此代码示例中使用固定数据，以便从LLM法官和决策模型中直接验证评估者的行为。当您还掌握了基本事实时，您可以确定每个评估者是否发现了正确的错误。此代码示例可帮助您建立用于测试决策模型的框架，并将其与您自己的用例的LLM作为法官进行比较。

要部署示例，您需要以下内容：

- 账户中的[已启用 Amazon CloudWatch Transaction Search](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-get-started.html#enabling-transaction-search)。
- [访问 Amazon Bedrock 中的基础模型](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)。
- Python 3.12 或更高版本、AWS 命令​​行界面 (AWS CLI) 和 Docker。
- Jev 需要 TypeSafe API 密钥。请访问 [typesafe.ai](https://typesafe.ai/) 了解访问详情。
- Strands Decider 需要运行 Strands Decider 服务器的主机。您可以在本地运行它进行测试，也可以在 Virtual Private Cloud (VPC) 内的 Amazon Elastic Compute Cloud (Amazon EC2) 上运行，以便 Lambda 函数可以访问它。

### 看到它的实际效果

您可以在 [AgentCore 示例 GitHub 存储库](https://github.com/awslabs/agentcore-samples/tree/main/01-features/06-observe-evaluate-optimize-your-agent/02-evaluate/custom-code-based-evaluation) 中找到完整的代码示例。两个 Python 脚本处理所有事情：

- `../utils/deploy.py` 将 HR Assistant 部署到 AgentCore 运行时。
- `evaluate.py` 部署评估器、调用代理并运行评估模式。

运行不带标志的“evaluate.py”会执行五个步骤：

- 创建 Lambda 执行角色 (`AgentCoreLambdaEvaluatorRole`)。
- 打包并部署两个确定性 Lambda 评估器：“hr-response-length”（跟踪级别评估器，用于检查代理的响应是否保持在长度范围内）和“hr-fact-checker”（会话级评估器，根据已知模拟数据进行正则表达式验证 HR 事实）。
- 通过控制平面将两者注册为 AgentCore 基于代码的评估器。
- 使用“EvaluationClient”和“OnDemandEvaluationDatasetRunner”在五个标记场景中运行按需评估，将基于代码的评估器与“Builtin.Correctness”、“Builtin.Helpativity”和“Builtin.ResponseRelevance”相结合。
- 创建在线评估配置，以 100% 采样持续对实时会话进行评分。

此时，您已经有了一个具有确定性检查和LLM法官评分的工作评估流程。决策模型评估者可以选择加入。您可以使用标志添加它们，它们与基本评估器一起运行，而不会对现有流程进行任何更改。使用标志 `--with-jev --jev-secret-arn <ARN>` 部署 `jev-evaluator` 并注册三个评估器：`JevGroundedness`、`JevHelpativity` 和 `JevGoalCompletion`。使用标志 `--with-decider` 部署 `strands-decider-evaluator` 并注册由 Strands Decider 2B 支持的相同的三个评估器。添加“--decider-ec2”以自动配置 Amazon EC2 实例、安全组、IAM 角色和 Lambda VPC 配置，无需手动控制台步骤。

## 使用决策模型构建评估器

使用标志 `--with-jev` 和 `--with-decider` 创建一个基于自定义代码的评估器，您可以完全控制要作为评估器运行的代码。我们创建 AWS Lambda 函数，其中在 AWS Lambda 函数内调用决策模型并返回标签或数值。此 Lambda 函数在 AgentCore 评估中注册为基于代码的评估器。

注册为评估器的 Lambda 接收代理的 OpenTelemetry 跨度。 `spans.py` 模块规范 OpenTelemetry 内容可以到达的形状，然后对其进行适当的格式化以调用决策模型。对于跟踪级别评估，仅发送目标回合和简短的先前历史记录，而会话级别则包含完整的对话。

![基于代码的评估器 Lambda 将 OpenTelemetry 跨度转换为决策模型请求，并将概率映射回 AgentCore结果](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22136-3.png)

适配器将模型的概率分布转换为 AgentCore 评估期望的结果。对于“noul”问题，“true”的概率成为值，最可能的答案成为标签。对于“分数”问题，该值是缩放到“[0, 1]”的概率加权预期水平。对于“选择”问题，它是预定义选项值的加权平均值。

### 根据您自己的流量验证决策模型评估器

当您将评分标准重写为决策模型问题时，您创建了一个新的衡量标准，而不是旧衡量标准的副本。重新构建的标题通常比最初的预期更严格或更宽松，除非您将其与实际会话进行检查，否则您不会看到这种变化。在决策模型评估器上发布版本之前，请以与验证任何新测量相同的方式针对您自己的流量的标记样本进行验证。本部分的目标是引导您端到端地完成验证，以便您可以放心地使用评估器来完成验证。

该过程有五个步骤。

**步骤 1.** 构建标记样本。从代理的流量中提取一组存储的会话，充分覆盖您关心的故障和边缘情况。仅涵盖快乐路径的样本无法告诉您评估器在哪里中断。

**步骤 2.** 获取人类参考标签。让三个独立的贴标机对您的问题测量的属性进行每轮评分，并以多数票作为参考标签。记录哪些回合是一致的，哪些回合是分裂的。虽然一致投票是明确的情况，但分票投票才是有价值的，因为它们在模型看到之前就揭示了标题本身的模糊性。

**步骤 3.** 在相同的输入上运行两个评估器。在单批评估中的相同会话上运行决策模型评估器和匹配的内置评估器。对相同的输入进行评分是使比较具有同等性的原因。

**步骤 4.** 通过三个镜头读取结果。有了多数票标签以及简单和困难的划分，您现在可以回答三个问题，告诉您评估器是否准备好。

- 同意率：它与你的人类匹配吗？衡量每个评估者同意多数票标签的频率，并针对每个问题进行测量，因为一个问题的准确性与另一个问题的准确性无关。然后将数字分为简单（一致）和困难（分裂投票）的情况。只在困难情况下犯错的评估者的行为很像人类贴标签者的行为，这正是您想要的。
- 校准：置信度分数有什么意义吗？根据评估者报告的概率进行分组，并将每个组的一致性与标签进行比较。较高的置信度应该跟踪较高的准确性。然后检查简单的案例是否始终比困难的案例获得更高的置信度。如果确实如此，则模型的不确定性正在跟踪真正的模糊性，您可以使用这些组为每个评估者选择决策阈值，而不是默认为 0.5。
- 分歧分析：差异在哪里以及为何？找到两个评估者意见不一致的回合，并检查这些回合是否与人类认为模棱两可的回合相同。阅读它们。大多数分歧都可以追溯到问题的措辞，修改后的问题可以消除这些分歧。当错误集中在困难情况中时，问题就是标题而不是模型。

**步骤 5**。当发生任何变化时重新运行检查。将此视为可重复的检查而不是一次性的门。每当您改写问题或转移到新的模型版本时，请再次运行它。每个结果的解释都会记录生成它的模型版本，因此您知道给定分数来自哪个版本。

## 为您的代理人选择最好的评估者集

内置评估器仍然是 AgentCore 评估中广泛评估策略的基础。他们根据标题及其支持背景评估响应，并解释判断，以便开发人员可以调查出了什么问题。对于人力资源助理来说，忠诚度评估可以识别与工具结果相矛盾的主张，而有用性评估可以指出代理回答了平衡问题，但未完成所请求的操作。

忠诚、乐于助人和正确性可能需要连接证据、识别缺失的信息或找到解决方案。预印本*JEV-as-a-Judge：有信心时接受，不确定时升级*将相关区别描述为“阅读与推导”。狭隘的决策模型检查可以标记注意力的转向，而内置评估器提供审查它所需的更广泛的评估和推理。当您将决策模型视为大门而不是替代品时，它们就会发挥最大的作用。级联模式的工作原理如下。首先，在每个会话的每个回合运行快速、校准的决策模型，以获得廉价的通过/失败信号。然后仅在信号低于阈值的会话上调用完整的 LLM 评估器。

![级联模式，决策模型筛选每个回合并将低置信度升级为完整的 LLM 评估器](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22136-4.png)

图 4：级联模式，其中校准决策模型会筛选每个回合，只有低置信度回合才会升级到内置评估器

| **标准** | **LLM作为法官** | **作为法官的决策模型** |
| ---| ---| ---|
| **输出** |评分+说明|校准概率 |
| **延迟** | 2–10 秒 | 〜数百毫秒（网络）|
| **可定制** |有限（固定提示模板）|问题定义 |
| **最适合** |定性的细微差别，解释 |校准判断|

我们推荐以下设置：

- 使用您依赖的内置评估器配置在线评估，作为整个座席质量的标准衡量标准。
- 将针对特定领域的是/否和选择问题的决策模型评估器添加到同一配置中，以及针对您可以精确计算的任何内容的基于确定性代码的评估器。
- 每周或按照适合您的发布周期的任何时间表，查询决策模型检查失败或得分接近其阈值的会话的在线结果，并使用内置评估器对这些会话运行批量评估以获取解释。
- 在内置评估器和您根据标记数据验证的决策模型评估器上进行控制发布，并跟踪两者一致的频率。

## 清理

为了避免持续产生费用，请运行“cleanup.py”，以删除 AgentCore 运行时上托管的代理、评估器和评估配置、注册为评估器的 AWS Lambda 函数、托管 Strands Decider 模型的 EC2 实例、AWS Secrets Manager 密钥以及 CloudWatch 上的关联日志组。

＃＃ 结论

在这篇文章中，您使用基于代码的评估器将两个决策模型 Jev 和 Strands Decider 连接到 AgentCore 评估，随附的代码示例为您提供了一个框架，用于测试这些模型并查看它们作为评估器在哪里增加价值。内置评估器仍然是您的基准。决策模型添加了狭窄的、经过验证的检查，这些检查附带了您可以设定阈值并采取行动的确定性措施。实际的前进道路是在您已经运行的内置评估器旁边添加决策模型检查，测量它们与您自己的流量上的参考标签一致的频率，并仅在您信任它们后才扩大覆盖范围。

要开始使用，请查看 [Amazon Bedrock AgentCore 评估](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 文档，使用 [基于代码的评估器](https://aws.amazon.com/blogs/machine-learning/build-custom-code-based-evaluators-in-amazon-bedrock-agentcore/) 集成自定义评估器，并深入了解 [Strands]决策者](https://strandsagents.com/blog/introducing-strands-decider/)模型。通过部署 [Amazon Bedrock AgentCore 示例存储库](https://github.com/awslabs/agentcore-samples) 中的示例评估器来开始使用代码示例。
