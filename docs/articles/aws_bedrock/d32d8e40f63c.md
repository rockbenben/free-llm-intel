# 在 Amazon Bedrock AgentCore Evaluations 中使用决策模型

你评估一个 agent 时，有些问题是窄而可重复的。这条回答守住了 policy 吗？这次 tool call 批准安全吗？这个回答和检索到的上下文相符吗？决策模型回答的正是这类问题。它们接收一个结构化状态和一组固定的可选答案，返回的是这些答案上的校准概率，而不是置信度会随每次运行漂移的自由文本。这让它们很适合 agent 评估里的打分那一步——你要的是一个标签，以及一个能设阈值、能信任的数值。

[Amazon Bedrock AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 是 Amazon Bedrock AgentCore 的一项能力，会在 agent 的整个生命周期里为它打分：开发时按需评估、对存量 session 跑批量任务、对生产流量做在线评估。除了 15 个内置 evaluator，AgentCore Evaluations 还支持你自己定义的 custom evaluator，形式要么是 LLM-as-a-judge，要么是 code-based evaluator。Custom LLM-as-a-judge evaluator 会用 Amazon Bedrock 中的一个模型来执行你的指令和评分量表。Code-based evaluator 则在 AWS Lambda function 里跑你自己的逻辑，而这段逻辑可以调用你任选的外部系统、模型或 API，其中就包括决策模型。

决策模型适合这样一类问题：答案集合是固定的，而且一个知情的人扫一眼就能定，比如 agent 是否拒绝了某个请求、某条回答是否没有跑题。在你自己的流量上验证过一个问题之后，对这个决策或这个分数，一个决策模型可能就够用了，你还能把同样的做法延伸到你 policy 里具体的 harmfulness 或 stereotyping 类别。因为这两个后端都能在一次请求里就同一个状态回答多个问题，你可以把它们当作筛查层而不是替代品：在你的各项指标上跑一个 pass/fail 信号，挑出那些值得由内置 evaluator 做更深评估的 turn——内置 evaluator 给出的解释能帮你排查到底哪里出了问题。

本文演示如何通过 code-based evaluator，把两个决策模型后端接到 AgentCore Evaluations 上。第一个是 [Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev)，TypeSafe 提供的托管决策模型。第二个是 [Strands Decider 2B](https://strandsagents.com/blog/introducing-strands-decider/)，一个需要你自己运行的开源决策模型。读完本文，你会知道如何把 AgentCore evaluator 的输入转换成决策模型的请求，以及如何把模型输出的概率转换回 AgentCore 的评估结果。不过先回答一个问题：什么时候该用 custom LLM-as-a-judge evaluator，什么时候决策模型更合适？下一节会拆解决策模型是什么，以及其中的取舍。

## 决策模型

决策模型是一个小而专的模型，训练目标是从一个固定的选项集合中做选择，并返回校准过的置信分数，而不是生成自由文本。通用大语言模型（LLM）evaluator 给出的是一次打分加上理由；决策模型给出的则是预定义答案上的概率分布。这让你直接拿到一个置信度量，可以用程序去设阈值、聚合并据此行动。因此决策模型很适合这样一类评估任务：判断可以被表述成在一组固定选项里做选择，比如「这条回答是 grounded 的吗？」或「agent 完成了用户的目标吗？」

决策模型最有用的场景，是你想要的不是一个二元判断，而是在标签之外还有一个校准良好的置信分数。当你希望稳定一致地执行某份特定的 rubric、又不想依赖通用 LLM 去解读它时，也适合用它。

TypeSafe 的托管决策模型 Jev，以及 [Strands Decider](https://strandsagents.com/blog/introducing-strands-decider/)——Strands Agents 团队出品的开源、20 亿参数决策模型——都支持三类问题。`noul` 问题提出一个是/否问题，返回 0（否）到 1（是）之间的一个概率。`choice` 问题问的是最多 255 个选项里哪一个成立，返回最可能的选项，外加完整分布和一个置信度。`score` 问题问的是 2 到 10 个有序档位里哪一档成立，返回概率加权的得分、各档上的分布和一个置信度。很多评估 rubric 都能落进这几类之一。「这条回答里的每一条事实都被 tool results 支持吗？」是一个是/否问题，而「按四档 rubric，这条回答有多大帮助？」是一个 score 问题。

## 决策模型 versus LLM-as-a-judge

AgentCore 目前的内置 evaluator 用通用 LLM 对照 rubric 评估 agent 的回答，并解释它的判断。当评估需要串联证据、找出缺失信息，或逐条深入推敲一段回答时——在这类任务里解释和分数一样有用——这是很有价值的。决策模型不是 LLM evaluator 的替代品，它们是 code-based evaluator 这套框架带来的新增项。把它们用在窄而界定清楚的检查上，与内置 evaluator 更宽泛的评估并行。

## 方案概览

为了说明这几类 evaluator 怎么配合，本文搭了一个端到端的例子：一个 HR Assistant agent，由确定性的 code-based 检查、内置 LLM-as-a-judge evaluator，以及由 Jev 或 Strands Decider 2B 支撑的决策模型 evaluator 来评估。

这个 agent 用 Strands Agents 构建，部署到 AgentCore runtime，这是 Amazon Bedrock AgentCore 的一项能力。它靠五个工具回答员工的问题，这些工具返回固定的 mock 数据，例如带薪休假（PTO）余额、PTO 申请、HR policy、福利和工资单。这段代码示例之所以用固定数据，是为了让验证 LLM-as-a-judge 与决策模型的 evaluator 行为变得直接。当你另外还握有 ground truth 时，就能确认每个 evaluator 是否抓到了它该抓的那些失败。这段代码示例帮你把框架搭起来，在你自己的场景里对比测试决策模型与 LLM-as-a-judge。

### 前提条件

要部署这个示例，你需要以下内容：

- 一个 AWS 账户，且处于 AgentCore Evaluations 可用的某个 [Region](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-regions.html) 中。该示例默认使用 US West (Oregon)。
- 账户中已[启用 Amazon CloudWatch Transaction Search](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-get-started.html#enabling-transaction-search)。
- [可访问 Amazon Bedrock 中的某个基础模型](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)。
- Python 3.12 或更高版本、AWS Command Line Interface (AWS CLI) 以及 Docker。
- Jev 需要一个 TypeSafe API key。访问方式详见 [typesafe.ai](https://typesafe.ai/)。
- Strands Decider 需要一台运行 Strands Decider server 的主机。你可以在本地跑它做测试，也可以跑在虚拟私有云（VPC）内的 Amazon Elastic Compute Cloud (Amazon EC2) 上，好让 Lambda function 能访问到它。

### 看它跑起来

完整代码示例在 [AgentCore samples GitHub 仓库](https://github.com/awslabs/agentcore-samples/tree/main/01-features/06-observe-evaluate-optimize-your-agent/02-evaluate/custom-code-based-evaluation) 里。两个 Python 脚本包办一切：

- `../utils/deploy.py` 把 HR Assistant 部署到 AgentCore runtime。
- `evaluate.py` 部署 evaluator、调用 agent，并运行各种评估模式。

不带任何旗标运行 `evaluate.py`，会执行五个步骤：

- 创建 Lambda 执行角色（`AgentCoreLambdaEvaluatorRole`）。
- 打包并部署两个确定性的 Lambda evaluator：`hr-response-length`（一个 trace 级 evaluator，检查 agent 的回答是否保持在长度限制之内）和 `hr-fact-checker`（一个 session 级 evaluator，用 regex 对照已知的 mock 数据校验 HR 事实）。
- 通过控制面把这两个都注册为 AgentCore 的 code-based evaluator。
- 用 `EvaluationClient` 和 `OnDemandEvaluationDatasetRunner` 在五个带标注的场景上跑按需评估，把 code-based evaluator 与 `Builtin.Correctness`、`Builtin.Helpfulness`、`Builtin.ResponseRelevance` 组合在一起。
- 创建一个在线评估配置，以 100% 采样持续为在线 session 打分。

到这里，你已经有一条能跑的评估流水线：确定性检查加上 LLM-as-a-judge 打分。决策模型 evaluator 是需要显式开启的。你可以用一个旗标把它们加上，它们会与基础 evaluator 并行运行，现有流程不用改。使用旗标 `--with-jev --jev-secret-arn <ARN>` 会部署 `jev-evaluator`，并注册三个 evaluator：`JevGroundedness`、`JevHelpfulness` 和 `JevGoalCompletion`。使用旗标 `--with-decider` 会部署 `strands-decider-evaluator`，注册同样这三个 evaluator，但后端换成 Strands Decider 2B。再加上 `--decider-ec2`，就会自动开好 Amazon EC2 实例、security group、IAM role 和 Lambda 的 VPC 配置，不必在控制台手工操作。

![evaluate.py 部署的评估流水线，把确定性、内置与决策模型 evaluator 组合在按需与在线两种模式中](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22136-2.png)

## 用决策模型构建 evaluator

使用 `--with-jev` 和 `--with-decider` 这两个旗标会创建一个 custom code-based evaluator，你可以完全掌控自己想拿来当 evaluator 运行的代码。我们创建 AWS Lambda function：决策模型在 AWS Lambda function 内部被调用，返回一个标签或一个数值。这个 Lambda function 就注册为 AgentCore Evaluations 中的 code-based evaluator。

注册为 evaluator 的这个 Lambda 收到的是 agent 的 OpenTelemetry span。`spans.py` 模块先把 OpenTelemetry 内容可能呈现的各种形态归一化，再按合适的方式格式化，以便向决策模型发起调用。做 trace 级评估时，只发送目标 turn 和简短的先前历史；session 级则会带上完整对话。

![作为 code-based evaluator 的 Lambda 把 OpenTelemetry span 转换成决策模型请求，并把概率映射回 AgentCore 结果](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22136-3.png)

图 3：作为 code-based evaluator 的 Lambda 如何为决策模型改写 OpenTelemetry span，又如何把结果映射回 AgentCore

这个适配层把模型的概率分布转换成 AgentCore 评估期望的结果。对 `noul` 问题，`true` 的概率成为取值，最可能的答案成为标签。对 `score` 问题，取值是按概率加权的期望档位，并缩放到 `[0, 1]`。对 `choice` 问题，取值是预定义选项值的加权平均。

### 在你自己的流量上验证决策模型 evaluator

当你把一份 rubric 改写成一个决策模型问题，你造出来的是一个新的度量，而不是旧度量的副本。被重新表述的 rubric 往往会比原意更严或更松，而不去拿真实 session 核对，你看不到这种漂移。在拿决策模型 evaluator 去做发布卡点之前，先按你验证任何新度量的方式验证它：拿你自己流量的一个带标注样本来对。这一节的目标是带你把这条验证走通一遍，结束时你手上是一个可以放心设阈值的 evaluator。

这个流程有五个步骤。

**步骤 1.** 构建一个带标注的样本。从你 agent 的流量里拉出一批存量 session，对你关心的那些失败和边界情况要有足够的覆盖。只覆盖 happy path 的样本，告诉不了你 evaluator 会在哪里崩。

**步骤 2.** 拿到人工参考标签。请三个独立标注者，就你的问题所衡量的那个属性为每一个 turn 打分，取多数票作为参考标签。记下哪些 turn 是全票一致、哪些是分成了几派。全票一致的 turn 是那些明确的案例，但分歧票的 turn 才是值钱的那些，因为它们会在模型看到 rubric 之前，先暴露出 rubric 本身的含糊。

**步骤 3.** 让两个 evaluator 跑同样的输入。把这些相同的 session 放进一次批量评估里，同时跑决策模型 evaluator 和对应的那个内置 evaluator。只有在打分对象完全一致时，这个比较才是公平的。

**步骤 4.** 用三个视角读结果。手上有多数票标签、以及难易两组的划分，你现在可以回答那三个能告诉你 evaluator 是否就绪的问题。

- 一致率：它和你们的人类标注一致吗？量一量每个 evaluator 与多数票标签一致的比例，而且要按问题分别量，因为一个问题的准确率说明不了另一个问题。然后把数字按简单（全票一致）和困难（分歧票）两类拆开。一个只在困难案例上打滑的 evaluator，表现得就和你们的人类标注者很像，这正是你想要的。
- 校准度：那些置信分数说明了什么吗？按 evaluator 报告的概率把 turn 分组，再比较每组与标签的一致程度。更高的置信应当对应更高的准确率。然后检查简单案例是否确实拿到比困难案例更高的置信。如果是，模型的 uncertainty 就在追踪真实的含糊，你就可以用这些分组为每个 evaluator 各选一个决策阈值，而不是一律默认 0.5。
- 分歧分析：它们在何处、因何而不同？找出两个 evaluator 彼此不一致的那些 turn，看看它们是不是你们的人类标注者也觉得含糊的那批。把它们读一遍。大多数分歧都能追溯到问题的措辞，改一版问题就理顺了。当错误聚在困难案例上时，有问题的是 rubric 而不是模型。

**步骤 5**。任何改动之后重新跑一次检查。把它当成一个可重复的检查，而不是一次性的卡点。每当你改写一个问题或换到新的模型版本，就再跑一遍。每条结果的 explanation 都会记下产出它的那个模型版本，所以你能知道某个分数出自哪个版本。

## 为你的 agent 挑选最合适的一组 evaluator

内置 evaluator 仍然是 AgentCore Evaluations 里覆盖面更广的评估策略的地基。它们对照 rubric 及其支撑上下文来评估回答，并解释判断的依据，让开发者能去排查哪里出了问题。对 HR Assistant 来说，一次 faithfulness 评估能找出某个与 tool result 矛盾的说法，而一次 helpfulness 评估能指出 agent 回答了余额问题、却没做完用户要求的那个操作。

Faithfulness、helpfulness 和 correctness 可能需要串联证据、找出缺失信息，或者把解法推演一遍。预印本 *JEV-as-a-Judge: Accept When Confident, Escalate When Unsure* 把这一相关区分描述为「reading 与 deriving」。一个窄口径的决策模型检查可以把某个 turn 标记为需要留意，而内置 evaluator 提供复查它所需的更宽评估和推理。当你把决策模型当作一道闸门而不是替代品时，它最能发挥作用。cascade 模式是这样运作的。先在每个 session 的每个 turn 上跑一个快速、校准过的决策模型，拿到一个廉价的 pass/fail 信号。然后只在信号低于你阈值的 session 上调用完整的 LLM evaluator。

![cascade 模式：决策模型筛查每一个 turn，并把低置信的 turn 上报给完整的 LLM evaluator](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/04/ML-22136-4.png)

图 4：cascade 模式，校准过的决策模型筛查每一个 turn，只有低置信的 turn 才上报给内置 evaluator

| **判据** | **LLM as Judge** | **Decision Models as Judge** |
| --- | --- | --- |
| **输出** | 分数 + 解释 | 校准过的概率 |
| **延迟** | 2–10 秒 | 约几百毫秒（网络） |
| **可定制性** | 有限（固定的 prompt 模板） | 问题定义 |
| **最适合** | 定性的细微差别、解释 | 校准过的判断 |

我们推荐这样配置：

- 用你依赖的那些内置 evaluator 配置好在线评估，作为跨你所有 agent 的标准质量度量。
- 在同一个配置里，为领域特定的是/否和 choice 问题加上决策模型 evaluator，再为你能精确算出来的一切都加上确定性的 code-based evaluator。
- 每周一次，或按你发布节奏合适的任意周期，去查询在线结果里那些决策模型检查失败、或分数贴近其阈值的 session，然后用内置 evaluator 对这些 session 跑批量评估，拿到解释。
- 把发布卡点设在内置 evaluator、以及你已经用带标注数据验证过的决策模型 evaluator 上，并跟踪两者的一致频率。

## 清理

为避免持续产生费用，请运行 `cleanup.py`，它会删除托管在 AgentCore runtime 上的 agent、evaluator 与评估配置、注册为 evaluator 的那些 AWS Lambda function、托管 Strands Decider 模型的 EC2 实例、AWS Secrets Manager 密钥，以及 CloudWatch 上关联的 log group。

## 结论

本文中，你把 Jev 和 Strands Decider 这两个决策模型通过 code-based evaluator 接到了 AgentCore Evaluations 上，配套的代码示例给了你一个测试这些模型的框架，让你看到它们作为 evaluator 在哪些地方加分。内置 evaluator 仍然是你的基线。决策模型带来的是窄口径、经过验证的检查，并且附带一个你可以设阈值、可以据此行动的确定性度量。实际可行的推进路径是：在你已经在跑的内置 evaluator 旁边加上决策模型检查，在你自己的流量上度量它们与你参考标签的一致频率，只有当你信任它们之后再扩大覆盖面。

要开始上手，请先看 [Amazon Bedrock AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 文档，用 [code-based evaluator](https://aws.amazon.com/blogs/machine-learning/build-custom-code-based-evaluators-in-amazon-bedrock-agentcore/) 集成 custom evaluator，并深入了解 [Strands Decider](https://strandsagents.com/blog/introducing-strands-decider/) 模型。要拿代码示例起步，可以从 [Amazon Bedrock AgentCore 示例仓库](https://github.com/awslabs/agentcore-samples) 部署这些示例 evaluator。
