# 使用 Amazon Bedrock 模型生成 Gremlin 查询

图数据库彻底改变了组织管理复杂、相互关联数据的方式。然而，Gremlin 这类专用查询语言往往给希望高效提取洞察的团队带来障碍。与传统关系数据库拥有明确定义的 schema 不同，图数据库缺少集中式 schema，要高效查询就需要深厚的技术专长。

为应对这一挑战，我们探索一种把自然语言转换为 Gremlin 查询的方法，使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的 [Amazon Nova Pro](https://aws.amazon.com/ai/generative-ai/nova/) 等模型。该方法帮助业务分析师、数据科学家以及其他非技术用户无缝访问和操作图数据库。

本文介绍我们从自然语言生成 Gremlin 查询的方法论，比较不同技术，并演示如何以大语言模型（LLM）作为评判者来评估这些生成查询的有效性。

## 方案概述

把自然语言查询转换为 Gremlin 查询，需要深入理解图结构以及图数据库中蕴含的领域知识。为此，我们把方法分为三个关键步骤：

- 理解并提取图知识
- 参照 text-to-SQL 的处理方式对图进行结构化
- 生成并执行 Gremlin 查询

下图展示了这一工作流。

### 第 1 步：提取图知识

一个成功的查询生成框架必须同时整合图知识和领域知识，才能准确地翻译自然语言查询。图知识涵盖直接从图数据库中提取的结构信息和语义信息。具体包括：

- **顶点标签与属性** —— 顶点类型、名称及其关联属性的清单
- **边标签与属性** —— 关于边类型及其属性的信息
- **每个顶点的一跳邻居** —— 捕获局部连通性信息，例如顶点之间的直接关系

借助这些图特有的知识，框架可以有效地对图数据库固有的异构属性和复杂连接进行推理。

领域知识捕获的是对图知识形成补充、并专门针对应用领域的额外上下文。它的来源有两种：

- **客户提供的领域知识** —— 例如，客户 kscope.ai 帮助指定了那些表示元数据、不应被查询的顶点。这类约束被编码进系统，用于引导查询生成过程。
- **LLM 生成的描述** —— 为了增强系统对顶点标签及其与具体问题相关性的理解，我们使用 LLM 生成关于顶点名称、属性和边的详细语义描述。这些描述存储在领域知识库中，提供额外的上下文以提升所生成查询的相关性。

### 第 2 步：把图结构化为 text-to-SQL 式的 schema

为了提升模型对图结构的理解，我们采用类似 text-to-SQL 处理的方式，构建一个表示顶点类型、边和属性的 schema。这种结构化表示增强了模型解读并生成有意义查询的能力。

问题处理组件把自然语言输入转换为用于查询生成的结构化元素。它分三个阶段工作：

- **实体识别与分类** —— 识别输入问题中的关键数据库元素（如顶点、边和属性），并根据意图对问题进行分类
- **上下文增强** —— 用知识组件中的相关信息丰富问题，使图特有的上下文和领域特有的上下文都能被恰当捕获
- **查询规划** —— 把增强后的问题映射到查询执行所需的具体数据库元素

上下文生成组件通过汇集以下内容，确保生成的查询准确反映底层图结构：

- **元素属性** —— 获取顶点和边的属性及其数据类型
- **图结构** —— 便于与数据库的拓扑结构对齐
- **领域规则** —— 应用业务约束和逻辑

### 第 3 步：生成并执行 Gremlin 查询

最后一步是查询生成，LLM 基于提取的上下文构造 Gremlin 查询。流程如下：

- LLM 生成初始的 Gremlin 查询。
- 该查询在 Gremlin 引擎中执行。
- 如果执行成功，则返回结果。
- 如果执行失败，错误消息解析机制会分析返回的错误，并借助基于 LLM 的反馈来修正查询。

这种迭代修正确保生成的查询符合数据库的结构和约束，从而提升整体准确性和可用性。

### Prompt 模板

我们最终的 prompt 模板如下：

```
## Request
Please write a gremlin query to answer the given question:
{{question}}
You will be provided with couple relevant vertices, together with their 
schema and other information.
Please choose the most relevant vertex according to its schema and other 
information to make the gremlin query correct.


## Instructions
1. Here are related vertices and their details:
{{schema}}
2. Don't rename properties.
3. Don't change lines (using slash n) in the generated query.


## IMPORTANT
Return the results in the following XML format:

<Results>
    <Query>INSERT YOUR QUERY HERE</Query>
    <Explanation>
        PROVIDE YOUR EXPLANATION ON HOW THIS QUERY WAS GENERATED 
        AND HOW THE PROVIDED SCHEMA WAS LEVERAGED
    </Explanation>
</Results>
```

## 将 LLM 生成的查询与标准答案对比

我们实现了一套基于 LLM 的评估系统，使用 Amazon Bedrock 上 Anthropic 的 Claude 3.5 Sonnet 作为评判者，对 Amazon Nova Pro 和某个基准模型的查询生成与执行结果进行评估。该系统在两个关键领域工作：

- **查询评估** —— 评估正确性、效率以及与标准答案查询的相似度；计算精确匹配组件的百分比；并根据与领域专家共同制定的预定义规则给出总体评分
- **执行评估** —— 最初采用单阶段方式比较生成结果与标准答案，后来升级为两阶段评估流程： 逐项对照标准答案核验；计算整体匹配百分比

在 120 个问题上的测试表明，该框架能够有效区分正确与错误的查询。两阶段方式通过在评分前进行彻底比较，尤其提升了执行结果评估的可靠性。

## 实验与结果

本节讨论我们开展的实验及其结果。

### 查询相似度

在查询评估这一环节，我们提出两个指标：查询精确匹配度和查询总体评分。精确匹配分数通过识别生成查询与标准答案查询之间匹配与不匹配的组件来计算。下表汇总了查询精确匹配的分数。

|  | **简单** | **中等** | **困难** | **总体** |
| --- | --- | --- | --- | --- |
| **Amazon Nova Pro** | 82.70% | 61% | 46.60% | 70.36% |
| **Benchmark Model** | 92.60% | 68.70% | 56.20% | 78.93% |

总体评分是在考虑查询正确性、效率和完整性等因素后给出的，评判依据是 prompt 中的指示。总体评分采用 1–10 分制。下表汇总了查询总体评分的分数。

|  | **简单** | **中等** | **困难** | **总体** |
| --- | --- | --- | --- | --- |
| **Amazon Nova Pro** | 8.7 | 7 | 5.3 | 7.6 |
| **Benchmark Model** | 9.7 | 8 | 6.1 | 8.5 |

当前查询评估设置的一个局限在于，我们完全依赖 LLM 比较标准答案与 LLM 生成的查询并给出最终分数的能力。因此，LLM 可能无法与人类偏好对齐，对生成查询的扣分过重或过轻。为解决这一问题，我们建议与领域专家合作，把领域特有的规则加入评估 prompt。

### 执行准确率

为计算准确率，我们把 LLM 生成的 Gremlin 查询的结果与标准答案查询的结果进行比较。如果两个查询的结果完全一致，就把该实例计为正确；否则视为不正确。准确率随后按正确执行的查询数占所测试查询总数的比例计算。该指标直截了当地评估了模型生成的查询从图数据库中检索预期信息的效果，有助于与预期的查询逻辑对齐。

下表汇总了执行结果数量匹配的分数。

|  | **简单** | **中等** | **困难** | **总体** |
| --- | --- | --- | --- | --- |
| **Amazon Nova Pro** | 80% | 50% | 10% | 60.42% |
| **Benchmark Model** | 90% | 70% | 30% | 74.83% |

### 查询执行延迟

除准确率外，我们还通过测量生成查询的运行时并与标准答案查询比较来评估其效率。对每个查询，我们记录以毫秒计的运行时间，并分析生成查询与对应标准答案查询之间的差异。运行时间越低表示查询越优化，而显著偏差可能意味着查询结构或执行规划存在低效之处。综合考虑准确率和运行时间，我们就能对查询质量做出更全面的评估，确保生成的查询在图数据库中既正确又高效。下面的箱线图展示了标准答案查询与 Amazon Nova Pro 生成查询的查询执行延迟随时间的变化。如图所示，三类查询的运行时相当，中位延迟相近，四分位区间也有重叠。尽管标准答案查询的分布范围略宽、存在一个更高的离群值，但三组的中位值仍然接近。这表明模型生成的查询在执行效率上与人类编写的查询处于同一水平，支持了 AI 生成的查询质量相当且不会带来额外延迟开销这一结论。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/19/Picture2-3.jpg)

### 查询生成延迟与成本

最后，我们比较生成每个查询所花的时间，并根据 token 消耗计算成本。更具体地说，我们测量查询生成时间并跟踪所用的 token 数量，因为大多数基于 LLM 的 API 都按 token 用量计费。通过分析生成速度和 token 成本，我们可以判断该模型是否高效且经济。这些结果为选择在查询准确性、执行效率和经济可行性之间取得平衡的最优模型提供了见解。

如下图所示，Amazon Nova Pro 在生成延迟和成本两方面都持续优于基准模型。左图描绘查询生成延迟：Amazon Nova Pro 的中位生成时间明显更低，多数取值集中在 1.8–4 秒之间，而基准模型的范围更宽，约为 5–11 秒。右图展示查询生成成本：Amazon Nova Pro 的单次查询成本要低得多，中心位置远低于 $0.005，而基准模型的成本更高且波动更大，某些情况下可达 $0.025。这些结果表明 Amazon Nova Pro 在速度和成本两方面都具备优势，使其成为部署在对时间敏感或大规模系统中的有力候选。

## 结语

我们对 kscope.ai 提供给我们的全部 120 条标准答案查询进行了实验，在生成正确结果方面取得了 74.17% 的总体准确率。所提出的框架通过有效应对图查询生成的特有挑战展示了其潜力，这些挑战包括处理异构的顶点与边属性、在复杂图结构上进行推理，以及融入领域知识。框架的关键组件，如图知识与领域知识的整合、使用检索增强生成（RAG）来创建查询计划，以及用于修正查询的迭代错误处理机制，都对取得这一性能起到了关键作用。

除提升准确率外，我们还在积极开展若干改进工作。其中包括完善评估方法以更有效地处理深度嵌套的查询结果，以及进一步优化 LLM 在查询生成中的使用。此外，我们正在使用 RAGAS-faithfulness 指标来改进查询结果的自动化评估，从而在评估该框架输出时获得更高的可靠性和一致性。
