# 使用 Amazon Bedrock 和 LangChain 在可扩展的多账户部署中实现安全分布式日志

对于在数据管理领域提供服务的软件公司而言，数据隐私是一个关键问题。如果希望客户放心把数据托付给自己，软件公司就需要展示并证明客户的数据将保持机密，并且始终处于受控环境中。有些公司为维护机密性而不遗余力，有时会采用多账户架构，让每个客户的数据都存放在单独的 AWS 账户中。通过在账户层面隔离数据，软件公司可以落实严格的安全边界、帮助防止跨客户的数据泄露，并以最小的风险支持符合 HIPAA 或 GDPR 等行业法规的要求。

多账户部署是云数据隐私的黄金标准，它使软件公司即使在超大规模式下也能确保客户数据保持隔离，其中 AWS 账户提供了安全隔离边界，这一点在 [AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/security-pillar/sec_securely_operate_multi_accounts.html#:~:text=AWS%20accounts%20provide%20a%20security,to%20leverage%20this%20isolation%20boundary.) 中有所强调。软件公司越来越多地采用 [Amazon Bedrock](https://aws.amazon.com/bedrock/?trk=36201f68-a9b0-45cc-849b-8ab260660e1c&sc_channel=ps&ef_id=EAIaIQobChMIjcXZpPetjAMV3c_CBB2CrxmaEAAYASAAEgL3rPD_BwE:G:s&s_kwcid=AL!4422!3!692006004850!e!!g!!amazon%20bedrock!21048268689!159639953975&gclid=EAIaIQobChMIjcXZpPetjAMV3c_CBB2CrxmaEAAYASAAEgL3rPD_BwE) 等生成式 AI 能力，它提供具备全面安全功能的完全托管基础模型。然而，管理由 Amazon Bedrock 驱动的多账户部署会带来访问控制、[配额管理](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas.html)和运维可见性方面的独特挑战，可能使其大规模实施变得复杂。当 AWS 账户数量达到两位数时，不断申请和监控在 Amazon Bedrock 上调用基础模型的配额就成了一件难事。简化运维的一种方法是配置一个专用的运维账户来集中管理，同时让客户数据经由托管服务传输，并只在各自客户账户中静态存储。通过把运维集中在一个账户中、同时把数据保留在不同账户中，软件公司可以简化模型访问和配额的管理，同时维持严格的数据边界和安全隔离。

在本文中，我们介绍一个使用 Amazon Bedrock 和 LangChain 为多账户部署的分布式日志提供安全保护的解决方案。

## 使用 Amazon Bedrock 记录日志的挑战

可观测性对有效的 AI 实现至关重要——组织无法优化自己不去度量的东西。可观测性有助于性能优化、成本管理和模型质量保障。Amazon Bedrock 通过 [AWS Management Console](https://aws.amazon.com/console) 上的[配置](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html)，提供内置的调用日志记录到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 或 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）的能力，并且可以通过[跨账户共享](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Unified-Cross-Account.html)把单个日志路由到不同的 CloudWatch 账户，如下图所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/15/ML-18659-not-private-new.png)

把日志路由到各个客户账户会带来两个挑战：包含客户数据的日志会在运维账户中按用户定义的保留期限（至少 1 天）存储，这可能不符合严格的隐私要求；并且 CloudWatch 最多支持五个监控账户（客户账户）。面对这些限制，组织如何构建一个能够跨多个租户和客户扩展的安全日志解决方案？

在本文中，我们介绍一个为多账户部署中的 Amazon Bedrock 启用分布式日志的解决方案。这一设计的目标是提供健壮的 AI 可观测性，同时通过把日志完全保留在客户账户内，为静态数据维持严格的隐私边界。实现方式是：把日志记录移到客户账户中，而不是从运维账户发起。通过在每个客户账户中配置日志记录指令，软件公司可以集中 AI 运维，同时落实数据隐私——具体做法是把客户数据和日志保留在每个客户账户内严格的数据边界之中。该架构使用 [AWS Security Token Service](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp.html)（AWS STS），使客户账户在调用 Amazon Bedrock 时能够扮演运维账户中 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）的专用角色。在日志方面，该解决方案使用 [LangChain callback](https://python.langchain.com/docs/concepts/callbacks/) 直接在每个客户账户中捕获调用元数据，使运维账户中的整个流程不保留任何记忆。Callback 可用于记录 token 用量、性能指标，以及模型针对客户查询的整体质量。所提出的解决方案在集中式 AI 服务管理与强数据隐私之间取得平衡，确保客户交互始终留在其专属环境中。

## 解决方案概述

下图展示了在 Amazon Bedrock 上调用模型的完整流程。运维账户是这样一个账户：Amazon Bedrock 权限将在此通过[基于身份的策略](https://docs.aws.amazon.com/bedrock/latest/userguide/security_iam_service-with-iam.html)进行管理，[Amazon Bedrock client](https://boto3.amazonaws.com/v1/documentation/api/latest/reference/services/bedrock-runtime.html) 将在此创建，具备正确权限的 IAM 角色也将在此存在。每个客户账户都会在运维账户中扮演一个不同的 IAM 角色。客户账户是客户访问软件或应用的地方。该账户会包含一个 IAM 角色，用于扮演运维账户中对应的角色，以便允许调用 Amazon Bedrock。需要注意的是，这两个账户不必存在于同一个 AWS organization 中。在本解决方案中，我们使用 [AWS Lambda](https://aws.amazon.com/lambda) 函数从 Amazon Bedrock 调用模型，并使用 LangChain callback 把调用数据写入 CloudWatch。不失一般性，同样的原则可以应用于其他形式的计算，例如 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2)（Amazon EC2）实例中的服务器，或 [Amazon Elastic Container Service](https://aws.amazon.com/ecs)（Amazon ECS）上的托管容器。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/05/12/ML-18659-proposed-architecture.png)

一次模型调用的步骤顺序如下：

- 过程开始于客户账户中的 IAM 角色扮演运维账户中的角色，从而获得访问 Amazon Bedrock 服务的权限。这通过 AWS STS 的 [AssumeRole API 操作](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html)完成，该操作建立起所需的跨账户关系。
- 运维账户验证来自客户账户的请求主体（IAM 角色）是否被授权扮演其目标角色。这一验证基于附加在运维账户中 IAM 角色上的[信任策略](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-custom.html#roles-creatingrole-custom-trust-policy-console)。这一步确保只有获得授权的客户账户和角色才能访问集中化的 Amazon Bedrock 资源。
- 信任关系验证通过后，带有指定权限的临时凭证（access key ID、secret access key 和 session token）会返回给客户账户的 IAM 执行角色。
- 客户账户中的 Lambda 函数调用运维账户中的 Amazon Bedrock client。客户账户的 IAM 角色使用临时凭证，通过运维账户向 Amazon Bedrock 发送 prompt，消耗运维账户的模型配额。
- Amazon Bedrock client 的响应返回到客户账户后，LangChain callback 会把响应指标直接记录到客户账户中的 CloudWatch。

## 使用 IAM 角色启用跨账户访问

这一解决方案的核心思路是：在运维账户中为每个客户设置一个 IAM 角色。软件公司将管理这个角色并分配权限，以定义诸如可以调用哪些模型、在哪些 AWS Region、以及受哪些配额约束等方面。这种集中式方法显著简化了模型访问和权限的管理，尤其是在扩展到数百或数千个客户时。对于拥有多个 AWS 账户的企业客户，这一模式尤其有价值，因为它允许软件公司配置一个角色，供客户的多个账户扮演，从而提供一致的访问策略，并简化权限管理和成本追踪。通过精心设计的信任关系，运维账户可以保持对谁可以访问什么内容的控制，同时仍保留复杂多账户环境所需的灵活性。

该 IAM 角色可以附加一个或多个策略。例如，以下策略允许某个客户调用部分模型：

```
{
    "Version": "2012-10-17",
    "Statement": {
        "Sid": "AllowInference",
        "Effect": "Allow",
        "Action": [
            "bedrock:Converse",
            "bedrock:ConverseStream",
            "bedrock:GetAsyncInvoke",
            "bedrock:InvokeModel",
            "bedrock:InvokeModelWithResponseStream",
            "bedrock:StartAsyncInvoke"
        ],
        "Resource": "arn:aws:bedrock:*::foundation-model/<model-id>"
    }
}
```

控制将在信任关系层面实现，我们只允许某些账户扮演该角色。例如，在以下脚本中，信任关系允许客户 1 的角色仅在 `ExternalId` 匹配指定值时被获准的 AWS 账户扮演，目的是防止[混淆代理人问题](https://docs.aws.amazon.com/IAM/latest/UserGuide/confused-deputy.html)：

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AmazonBedrockModelInvocationCustomer1",
            "Effect": "Allow",
            "Principal": {
                "Service": "bedrock.amazonaws.com"
                },
            "Action": "sts:AssumeRole",
            "Condition": {
                "StringEquals": {
                    "aws:SourceAccount": "<account-customer-1>",
                    "sts:ExternalId": "<external-id>"
                },
                "ArnLike": {
                    "aws:SourceArn": "arn:aws:bedrock::<account-customer-1>:*"
                }
            }
        }
    ]
}
```

AWS STS `AssumeRole` 操作构成多租户 AWS 环境中安全跨账户访问的基石。通过实施这一身份认证机制，组织建立起健壮的安全框架，使运维账户与各个客户账户之间能够进行受控的交互。运维团队授予跨客户账户资源的精确范围访问权限，权限严格由所扮演角色的信任策略和附加的 IAM 权限管控。这种细粒度控制确保运维团队和客户只能对特定资源执行获授权的操作，从而在租户之间维持强安全边界。

随着组织把多租户架构扩展到涵盖数千个账户，这些跨账户身份认证操作的性能特征和可靠性成为越来越关键的考量。工程团队必须审慎设计其跨账户访问模式，以在安全与运维效率两方面同时优化，确保即使环境在复杂度和规模上不断增长，身份认证过程仍保持响应及时且可靠。

在考虑管控这些操作的服务配额时，需要注意：使用 AWS 凭证发起的 AWS STS 请求受默认配额限制，即每个账户、每个 Region 每秒 600 个请求——其中包括 `AssumeRole` 操作。跨账户场景中会出现一个关键的架构优势：只有发起 `AssumeRole` 请求的账户（客户账户）会计入其 AWS STS 配额；目标账户（运维账户）的配额不受影响。这种非对称的配额消耗意味着运维账户在响应来自客户账户的 API 请求时，不会耗尽自身的 AWS STS 服务配额。对大多数多租户实现而言，每秒 600 个请求的标准配额提供了充足容量，不过 AWS 也为有特殊需求的环境提供配额调整选项。这一配额设计支持可扩展的运维模式：单个运维账户可以高效服务数千个租户账户，而不会触及服务限制。

## 使用 LangChain callback 写入私有日志

LangChain 是一个流行的开源编排框架，它使开发者能够通过 *chain* 连接各种组件来构建强大的应用；chain 是按顺序执行的一系列操作，负责处理和转换数据。LangChain 可扩展性的核心是 `BaseCallbackHandler` 类，这是一个基础抽象，它提供接入 chain 执行生命周期的挂钩，使开发者能够在处理的不同阶段实现自定义逻辑。该类可以被扩展，以精确地定义在 chain 调用完成时应当发生的行为，从而支持精密的监控、日志记录或对下游流程的触发。通过实现自定义 callback handler，开发者可以捕获指标、把结果持久化到外部系统，或根据中间输出动态改变执行流程，这使 LangChain 对生产级语言模型应用既灵活又强大。

在 LangChain 中实现自定义的 CloudWatch 日志 callback，为在多账户部署中维护数据隐私提供了健壮的解决方案。通过扩展 BaseCallbackHandler 类，我们可以创建一个专门的 handler，建立到客户账户 CloudWatch Logs 的直接连接，确保模型交互数据始终留在账户边界之内。实现的第一步是使用客户账户（而非运维账户）的凭证初始化一个 Boto3 CloudWatch Logs client。该 client 配置了适当的日志组和日志流名称，这些名称可以根据客户标识符或应用上下文动态生成。在模型调用期间，该 callback 捕获 token 用量、延迟、prompt 细节和响应特征等关键指标。以下 Python 脚本是本实现的一个示例：

```
class CustomCallbackHandler(BaseCallbackHandler):

    def log_to_cloudwatch(self, message: str):
        """Function to write extracted metrics to CloudWatch"""

    def on_llm_end(self, response, **kwargs):
        print("\nChat model finished processing.")
        # Extract model_id and token usage from the response
        input_token_count = response.llm_output.get("usage", {}).get("prompt_tokens", None)
        output_token_count = response.llm_output.get("usage", {}).get("completion_tokens", None)
        model_id=response.llm_output.get("model_id", None)

        # Here we invoke the callback
        self.log_to_cloudwatch(
              f"User ID: {self.user_id}\nApplication ID: {self.application_id}\n Input tokens: {input_token_count}\n Output tokens: {output_token_count}\n Invoked model: {model_id}"
             )

    def on_llm_error(self, error: Exception, **kwargs):
        print(f"Chat model encountered an error: {error}")
```

on_llm_start、on_llm_end 和 on_llm_error 方法被重写，以拦截这些生命周期事件并持久化相关数据。例如，on_llm_end 方法可以抽取 token 数量、执行时间和模型专属的元数据，把这些信息格式化为结构化日志条目，然后再写入 CloudWatch。通过在 callback 内实现恰当的差错处理和重试逻辑，即使遇到间歇性的连接问题，我们也能提供可靠的日志记录。这种方法在客户账户中维持严格数据隔离的同时，创建了 AI 交互的全面审计轨迹，因为日志不会经过运维账户，也不会在其中驻留。

## 多账户日志中的 AWS 责任共担模型

在多账户架构中为 Amazon Bedrock 实施分布式日志时，理解 [AWS 责任共担模型](https://aws.amazon.com/compliance/shared-responsibility-model/)变得至关重要。尽管 AWS 负责保护底层基础设施以及 Amazon Bedrock 和 CloudWatch 等服务，客户仍需负责保护自身数据、配置访问控制并实施恰当的日志策略。正如我们的 IAM 角色配置所示，客户必须精心设计信任关系和权限边界，以帮助防止未经授权的跨账户访问。所概述的 LangChain callback 实现把责任放在客户身上：落实对静态日志的恰当加密、定义符合合规要求的保留期限，并为谁可以查看敏感的 AI 交互数据实施访问控制。这与多账户设计原则一致，即客户数据保持隔离在其各自账户内。通过在保持运维效率的同时尊重这些安全边界，软件公司可以在共享安全模型中履行自身责任，同时为整个客户群交付可扩展的 AI 能力。

## 结语

使用 Amazon Bedrock 实施安全、可扩展的多租户架构，需要在账户结构、访问模式和运维管理方面做审慎规划。我们概述的分布式日志方法展示了组织如何在保持严格数据隔离的同时，仍从集中式 AI 运维中获益。通过使用具备精确信任关系的 IAM 角色、用于安全跨账户身份认证的 AWS STS，以及用于私有日志的 LangChain callback，企业可以建立一个健壮的基础，扩展到数千个客户而不在安全或运维效率上妥协。

这一架构解决了在多账户部署中维护数据隐私的同时仍能实现全面可观测性的关键挑战。组织应从起步阶段就把自动化、监控和治理放在优先位置，以避免随系统扩展产生技术债务。为角色管理实施基础设施即代码、对跨账户访问模式进行自动化监控、以及定期开展安全评审，将确保架构保持韧性，并有助于在业务需求演进时维持对合规标准的遵循。随着生成式 AI 在软件提供商的产品中日益居于核心地位，这些架构模式提供了一份蓝图，用于在维持最高数据隐私标准的同时，向处于不同监管和安全要求的客户交付创新的 AI 能力。
