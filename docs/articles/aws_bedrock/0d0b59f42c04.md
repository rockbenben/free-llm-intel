# Swann 借助 Amazon Bedrock 为数百万台 IoT 设备提供生成式 AI

如果你在大规模管理物联网（IoT）设备，告警疲劳可能正在削弱系统的有效性。这篇文章将向你展示如何使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 及其生成式 AI 能力实现智能通知过滤。你将了解模型选择策略、成本优化技巧，以及面向 IoT 规模部署生成式 AI 的架构模式，这些都基于 [Swann Communications](https://us.swann.com/) 在数百万台设备上的部署实践。

智能家居安防客户如今期望系统能够区分快递员和潜在的入侵者——而不只是检测到移动。客户被大量每日通知或误报淹没，其中许多告警由与客户无关的事件触发，例如路过的车辆、四处走动的宠物等等。用户对持续不断的误报感到沮丧，开始完全忽略通知，包括真正的安全威胁。

作为自助式（DIY）安防解决方案的先驱，[Swann Communications](https://us.swann.com/) 已建成一个覆盖超过 1,174 万台联网设备的全球网络，为多个大洲的房主和企业提供服务。Swann 与 [Amazon Web Services (AWS)](https://aws.amazon.com/) 合作开发了一套多模型生成式 AI 通知系统，将其通知系统从基础的被动告警机制演进为智能的、具备上下文感知能力的安全助手。

## 推动解决方案的业务挑战

在实施新解决方案之前，Swann 面临若干关键挑战，这些挑战需要一种根本不同的安全通知方法。

Swann 之前的系统只具备基础检测能力，只能识别*人*或*宠物*事件，没有上下文感知——把快递员和潜在入侵者一视同仁——同时也不提供任何自定义选项，让用户根据自己独特的安全需求定义什么才算有意义的告警。这些技术限制，再加上在数千万台设备上经济高效地管理通知所面临的可扩展性挑战，清楚地表明渐进式改进远远不够——Swann 需要一种从根本上更智能的方法。

每台摄像头每天大约 20 条通知——其中大多数无关紧要——导致客户错过关键的安全事件，许多用户在最初几个月内就关闭了通知。这大大降低了系统的有效性，表明需要一种只提供有意义的告警的智能过滤机制。Swann 没有去管理多个供应商和定制集成，而是采用了可以协同工作的多种 AWS 云服务。借助 AWS 集成服务，Swann 的工程团队可以专注于创造新的安全功能。

## 为何选择 AWS 和 Amazon Bedrock

在评估 AI 合作伙伴时，Swann 优先考虑能够可靠扩展的企业级能力。AWS 在几个关键方面脱颖而出：

### 企业级 AI 能力

Swann 选择 AWS，是因为它以全面、集成的方式来大规模部署生成式 AI。Amazon Bedrock 是一项全托管服务，通过单一 API 提供对多个基础模型的访问，自动处理 GPU 供给、模型部署和扩展，使 Swann 无需更改基础设施即可测试和比较不同的模型家族（例如 Claude 和 Nova），并根据每种场景优化速度或准确性，例如大批量例行筛查、需要详细分析的威胁验证、时间敏感型告警以及复杂的行为评估。凭借每月约 2.75 亿次推理，AWS 的按使用付费定价模式，以及使用 Nova Lite 等高性价比模型进行例行分析的能力，实现了成本优化。AWS 服务在北美、欧洲和亚太地区提供低延迟推理，同时为关键任务安全应用提供数据驻留合规性和高可用性。

Swann 使用的 AWS 环境包括用于设备连接的 [AWS IoT Core](https://aws.amazon.com/iot-core/)、用于可扩展存储和存储视频源的 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/)，以及用于响应事件运行代码而无需管理服务器的 [AWS Lambda](https://aws.amazon.com/pm/lambda/)，它可从零扩展到数千次执行，并且只对使用的计算时间计费。[Amazon Cognito](https://aws.amazon.com/pm/cognito/) 用于管理用户身份验证和授权，提供安全登录、多因素身份验证、社交身份集成和临时 AWS 凭证。[Amazon Simple Query Service (Amazon SQS)](https://aws.amazon.com/sqs/) 用于管理消息队列，在流量高峰时缓冲请求，并帮助确保即使数千台摄像头同时触发也能可靠处理。

借助这些能力省去管理多个供应商和定制集成的精力，Swann 得以专注于创新而非基础设施。这种以云为中心的集成使上市时间缩短了 2 个月，同时降低了运营开销，并使得在数百万台设备上经济高效地部署复杂的 AI 能力成为可能。

### 可扩展性与性能要求

Swann 的解决方案需要处理数百万台并发设备（超过 1,174 万台摄像头 24/7 持续生成画面）、在晚间和周末出现活动高峰的波动工作负载模式、为关键安全事件提供亚秒级延迟的实时处理、在多个地理区域保持一致性能的全球分发，以及通过随使用量线性增长的透明定价实现成本可预测性。Swann 发现，Amazon Bedrock 和 AWS 服务让他们两全其美：一个能够处理其庞大规模的全球网络，加上智能成本控制，让他们可以为每种情况精确选择合适的模型。

## 解决方案架构概述与实施

Swann 的动态通知系统使用 Amazon Bedrock，在两个关键功能中策略性地使用四个基础模型（Nova Lite、Nova Pro、Claude Haiku 和 Claude Sonnet），以平衡性能、成本和准确性。如下图所示的架构展示了如何组合 AWS 服务，创建利用生成式 AI 能力的可扩展智能视频分析解决方案，同时兼顾性能和成本优化：

**![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/01/25/image-1-7.png)**

- **边缘设备集成：** 智能摄像头和门铃通过 AWS IoT Device Gateway 连接，提供实时视频源用于分析。
- **数据管道：** 视频内容流经 [Amazon EventBridge](https://aws.amazon.com/eventbridge)、Amazon S3 和 Amazon SQS，从而实现可靠的存储和消息队列处理。
- **智能画面处理：** [Amazon Elastic Compute Cloud (Amazon EC2)](https://aws.amazon.com/ec2) 实例（[G3 和 G4 系列](https://docs.aws.amazon.com/dlami/latest/devguide/gpu.html)）使用计算机视觉库将视频切分为帧，并处理帧的选择和过滤，以优化处理效率。G3 和 G4 实例是专为视频分析和 AI 推理等并行处理工作负载设计的 [GPU 驱动的虚拟服务器](https://aws.amazon.com/ec2/instance-types/g4/)。与按顺序处理任务的传统 CPU 不同，GPU 包含数千个核心，可以同时分析多个视频帧。这意味着 Swann 可以并发处理来自数千台摄像头的画面，而不会产生延迟瓶颈，从而实现近乎实时的安全监控。
- **无服务器处理：** Lambda 函数调用 Amazon Bedrock，并根据用例需求实现模型选择逻辑。
- **分层模型策略：** 一种使用多种不同能力模型的高性价比方案。Amazon Nova Lite 用于例行大批量筛查中的速度和成本效率，Nova Pro 用于威胁验证中均衡的性能，Claude Haiku 用于时间敏感型告警的超低延迟，Claude Sonnet 用于需要细致推理的复杂行为分析中的高级推理。
- **动态通知：** 自定义通知服务根据检测结果向移动应用发送实时告警。

## 生成式 AI 实施的最佳实践

以下最佳实践可以帮助组织在大规模实施类似的生成式 AI 解决方案时优化成本、性能和准确性：

- **理解 RPM 和 token 限制：** 每分钟请求数（RPM）限制定义了每分钟允许的 API 调用次数，要求应用程序实现排队或重试逻辑来处理大批量工作负载。token 是 AI 模型处理文本和图像的基本单位，成本按每千个 token 计算，因此简洁的 prompt 对于大规模降低成本至关重要。
- **业务逻辑优化：** Swann 通过在调用 AI 模型之前实施智能预过滤（移动检测、基于区域的分析以及重复帧消除），将 API 调用减少了 88%（从 17,000 降到 2,000 RPM）。
- **Prompt 工程与 token 优化：** Swann 通过三项关键策略实现了 88% 的 token 削减（从每个请求 150 个降到 18 个）：优化图像分辨率以在保持视觉质量的同时减少输入 token。在基于 GPU 的 EC2 实例上部署自定义预过滤模型，在到达 Amazon Bedrock 之前消除 65% 的误检（摇晃的树枝、路过的车辆）。设计超简洁的 prompt，采用结构化响应格式，用机器可解析的键值对取代冗长的自然语言（例如 `threat:LOW|type:person|action:delivery`）。Swann 的客户调查显示，这些优化不仅降低了延迟和成本，还将威胁检测准确率从 89% 提高到 95%。
- **Prompt 版本管理、优化与测试：** Swann 为 prompt 添加性能元数据（准确性、成本和延迟）进行版本管理，并在上线前对 5%–10% 的流量进行 A/B 测试。Swann 还使用 Amazon Bedrock 的 [prompt 优化](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-management-optimize.html)。
- **模型选择与分层策略**：Swann 根据活动类型选择模型。**Nova Lite（占请求的 87%）：** 处理例行活动的快速筛查，例如路过的车辆、宠物和快递人员。其低成本、高吞吐量和亚毫秒级延迟使其成为大批量实时分析的关键选择，在这些场景中速度和效率比精确性更重要。**Nova Pro（占请求的 8%）：** 当潜在威胁需要更高准确性的验证时，从 Nova Lite 升级而来。可区分快递人员与入侵者，并识别可疑行为模式。**Claude Haiku（占请求的 2%）：** 支撑 *Notify Me When* 功能，在用户定义的条件满足时立即通知。为时间敏感型自定义告警提供超低延迟。**Claude Sonnet（占请求的 3%）：** 处理需要复杂推理的边缘案例。分析多人交互、模糊场景，并提供细致的行为评估。**结果**：这种智能路由实现了 95% 的整体准确率，同时相比对所有请求都使用 Claude Sonnet 的方案，成本降低了 99.7%，从预计每月 210 万美元降至 6 千美元。关键洞察在于，将模型能力与任务复杂度相匹配，能够实现经济高效的大规模生成式 AI 部署，其中业务逻辑预过滤和分层模型选择带来的节省远超单纯的模型选择。
- **模型蒸馏策略：** Swann 教会更小、更快的 AI 模型去模仿更大模型的智能——就像创建一个几乎同样聪明、但运行快得多且比大模型成本更低的轻量版本。对于新功能，Swann 正在探索 [Nova 模型蒸馏](https://docs.aws.amazon.com/nova/latest/userguide/customize-distill.html) 技术。它支持从更大、更先进的模型向更小、更高效的模型迁移知识。还有助于针对特定用例优化模型性能，而无需大量带标注的训练数据。
- **实施全面监控**：使用 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 跟踪关键性能指标，包括延迟百分位——p50（响应时间中位数）、p95（第 95 百分位，反映大多数用户的最差情况）和 p99（第 99 百分位，识别异常值和系统压力）——以及 token 消耗、每次推理成本、准确率和限流事件。这些百分位指标至关重要，因为平均延迟可能掩盖性能问题；例如，200 毫秒的平均值可能掩盖 5% 的请求耗时超过 2 秒的情况，直接影响客户体验。

## 结论

在实施 Amazon Bedrock 之后，Swann 立即看到了改善——客户收到的告警更少，但更相关。告警量下降了 25%，通知相关性提高了 89%，客户满意度提升了 3%。该系统可扩展至 1,174 万台设备，p95 延迟低于 300 毫秒，表明复杂的生成式 AI 能力可以在消费级 IoT 产品中以经济高效的方式部署。动态通知（如下图所示）提供具备上下文感知的安全告警。

### **后续步骤**

考虑大规模采用生成式 AI 的组织，应从清晰、可衡量的业务问题入手，在全面部署前先用部分设备进行试点，并从第一天起就通过智能业务逻辑和分层模型选择进行成本优化。投资于全面监控以实现持续优化，并设计支持优雅降级的架构，以验证即使服务中断期间也能保持可靠性。尽早关注 prompt 工程和 token 优化，以帮助实现性能和成本的改善。使用 Amazon Bedrock 这样的托管服务来处理基础设施的复杂性，并构建灵活的架构，以支持未来的模型改进和不断演进的 AI 能力。
