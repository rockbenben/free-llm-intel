# 在 Amazon EKS 上使用 NVIDIA Run:ai GPU 分段

GPU 共享并不是新话题：Multi-Instance GPU（MIG）、时间切片与 Multi-Process Service（MPS）分别应对不同的隔离与利用率诉求。NVIDIA Run:ai GPU Fractioning 在 MPS 之上叠加了与 Kubernetes 集成的调度、按 Pod 的内存契约、强制执行与指标。

[NVIDIA Run:ai](https://github.com/dsx-ai-factory/run-ai) 是面向 Kubernetes 的 AI 工作负载编排软件。其 GPU Fractioning Operator 可以帮助多个团队共用 [Amazon Elastic Kubernetes Service（Amazon EKS）](https://aws.amazon.com/eks/) 上的一两块 GPU。Notebook、模型评估和规模不大的推理服务经常让团队排队等待，而 GPU 显存其实还有富余。本演练的基线状态是：NVIDIA 设备插件把单块 GPU 暴露为一个 `nvidia.com/gpu` 资源，且未开启 GPU 共享。两个各自请求 `nvidia.com/gpu: 1` 的 Pod 无法在该节点上同时运行，哪怕两者的显存需求之和完全装得下。

[NVIDIA Run:ai GPU Fractioning](https://github.com/kai-scheduler/gpu-fractioning/) 为基于软件的共享补上了 Kubernetes 调度集成、强制生效的显存上限和按 Pod 的指标。这一方案适用于满足 GPU Fractioning Operator 软硬件要求的 NVIDIA GPU，包括本身不支持 MIG 的型号。本文用一台搭载 NVIDIA A10G Tensor Core GPU 的 [Amazon Elastic Compute Cloud（Amazon EC2）](https://aws.amazon.com/ec2/) g5.xlarge 实例作为验证过的示例。其他配置需要自行做兼容性检查与验证。

NVIDIA 于 2026 年 10 月 13 日[宣布](https://developer.nvidia.com/blog/nvidia-runai-is-now-open-source-as-part-of-nvidia-dsx-ai-factory-platform/) [开源 NVIDIA Run:ai](https://github.com/dsx-ai-factory/run-ai)。本示例用到其四个模块化组件中的两个：[KAI Scheduler](https://github.com/kai-scheduler/KAI-Scheduler) 与 [GPU Fractioning Operator](https://github.com/kai-scheduler/gpu-fractioning/)。KAI Resource Management 和 Workload Map 负责组织级治理与更多工作负载类型，不在本演练范围内。

本文介绍如何构建自定义 [Amazon Linux 2023（AL2023）](https://aws.amazon.com/linux/amazon-linux-2023/) 镜像，并在 Amazon EKS 上配置显存共享。在验证过的 G5/A10G 示例中，你先建立整卡 GPU 基线，再为每个 Pod 配一份 8 GiB 内存契约，并验证 6 GiB 的分配；随后查看按 Pod 的指标、测试 9 GiB 分配会被拒绝，最后清理这套一次性环境。

## 选择 GPU 共享方式

MIG 在[受支持的 GPU](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/supported-gpus.html) 上提供硬件分区。[设备插件的时间切片](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/gpu-sharing.html) 能共享一块 GPU，但既不复制显存，也不做故障隔离。MPS 允许多个 CUDA 进程并发运行，故障是否会限制在单进程内取决于配置。NVIDIA Run:ai GPU Fractioning 增加了按容器强制生效的显存上限，并支持时间切片（默认）与 sm-sharing 两种计算模式。[NVIDIA 的文档](https://developer.nvidia.com/blog/memory-enforced-gpu-sharing-in-kubernetes-with-nvidia-cuda-13-4/) 说明其默认模式下各工作负载的错误域彼此独立，而 sm-sharing 下共用一个错误域。这些都不构成安全保证。本演练只测显存上限，不测故障隔离，也不测计算性能。显存上限并不会按比例预留算力。

Amazon EKS 文档列出了几种 GPU 共享方案：[MIG](https://docs.aws.amazon.com/eks/latest/userguide/device-management-nvidia-mig.html)、基于 [NVIDIA 设备插件](https://docs.aws.amazon.com/eks/latest/userguide/device-management-nvidia-time-slicing.html#eks-time-slicing-device-plugin-al2023) 的时间切片，以及基于 [NVIDIA DRA 驱动与 Karpenter](https://docs.aws.amazon.com/eks/latest/userguide/device-management-nvidia-time-slicing.html#eks-time-slicing-karpenter-consumable-capacity) 的时间切片。要在这些方案之间做选择，可参考 Amazon EKS 最佳实践指南里的 [GPU 共享指引](https://docs.aws.amazon.com/eks/latest/best-practices/aiml-compute.html#_optimize_gpu_resource_allocation_with_time_slicing_mig_and_fractional_gpu_allocation)。如果你需要在没有 MIG 的 GPU 上强制实施按 Pod 的显存上限，并且可以运行固定规模的 GPU 节点组，那就选 GPU 分段。

[Dynamic Resource Allocation（DRA）](https://docs.aws.amazon.com/eks/latest/userguide/device-management.html) 提供了用于申请和分配设备的 Kubernetes API。GPU 共享与隔离的效果取决于设备驱动的实现和已启用的特性。KAI Scheduler 与 GPU Operator 都支持 DRA。本演练用的是 NvFractions annotation，不是 DRA。

GPU 分段适合有闲置时段的交互式 notebook、短时评估作业、GPU 兼容性测试和小型推理服务。每个 GPU 显存请求量应按实测峰值用量加上额外开销来确定，然后在并发负载下测延迟。本文展示的密度提升并不能证明吞吐量有提升，也不代表成本普降。

## 实施演练

本演练基于 AWS Samples 仓库。先确认前置条件和经过验证的组件版本，然后完成步骤 1 到 10。

### 前置条件

需要一个具备 Amazon EKS、[AWS CloudFormation](https://aws.amazon.com/cloudformation/)、Amazon VPC、Amazon EC2、[Amazon Elastic Block Store（Amazon EBS）](https://aws.amazon.com/ebs/)、[AWS Identity and Access Management（IAM）](https://aws.amazon.com/iam/) 和 [AWS Systems Manager](https://aws.amazon.com/systems-manager/) 权限的 AWS 账户，其中 Systems Manager 权限用于发现 Amazon Machine Image（AMI）。确认 g5.xlarge、系统节点以及临时 m5.xlarge 镜像构建机的配额与容量。安装 AWS CLI v2、eksctl、kubectl、Helm、Packer、Git、jq 和 curl。

凭证走你平时用的 AWS 凭证提供方：命名 profile、[AWS IAM Identity Center](https://aws.amazon.com/iam/identity-center/)、代入角色，或访问密钥环境变量。优先使用临时凭证；使用临时访问密钥时必须设置 `AWS_SESSION_TOKEN`。示例使用 us-east-2，换到其他区域时，该区域必须支持所选的 Amazon EKS 版本和实例类型。

在换用其他 GPU 之前，先查 NVIDIA 的 [GPU Operator 硬件清单](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/platform-support.html#supported-nvidia-data-center-gpus-and-systems)、所选 [驱动的硬件支持](https://docs.nvidia.com/datacenter/tesla/tesla-release-notes-615-71-10/index.html) 和 [GPU Fractioning Operator 的前置条件](https://github.com/kai-scheduler/gpu-fractioning/blob/v0.1.7/README.md#prerequisites)。仅有硬件支持并不代表分段可用。本演练只验证 G5/A10G 配置，AMI 构建目标是 `x86_64`。还要检查 CUDA 兼容性与显存余量：两份 8 GiB 契约需要同时容纳两份契约加上运行时开销，显存更小的卡就得配更小的契约并相应调整探测程序。

本演练会创建计费资源，包括 Amazon EKS 控制平面、NAT 网关、实例、卷和 AMI 快照。请使用一次性环境，验证结束后彻底清理。

### 使用验证过的 AL2023 栈

验证时，EKS 优化的 AL2023 NVIDIA 镜像提供 R580 与 R595 驱动分支，而 GPU Fractioning Operator v0.1.7 要求 R615 或更新版本。R615 属于短周期分支，也不是 GPU Operator 的默认版本。本示例构建了一个自定义的标准 Amazon EKS 1.36 AL2023 镜像，驱动与工具链由 AMI 自带，没有采用在其他操作系统上由 operator 管理驱动容器的方式。表中记录的是实验室验证结果，不是厂商的支持认证。

| **组件** | **验证过的版本** |
| --- | --- |
| Amazon EKS | 1.36 |
| GPU | NVIDIA A10G，23,028 MiB |
| NVIDIA 驱动 / Container Toolkit | 615.71.10 / 1.20.1-1 |
| containerd | 2.3.5，启用 NRI |
| GPU Operator / 设备插件 | 26.7.1 / 0.20.1 |
| KAI Scheduler / Fractioning Operator | 0.18.5 / 0.1.7 |

我们在 2026 年 10 月 22 日用 NVIDIA 驱动 615.71.10 验证了本演练。2026 年 11 月 18 日更新 GPU 节点污点之后，我们用同一驱动的镜像重跑了除步骤 3 镜像构建之外的每一步，结果一致。表中列出的是实测的组件版本，不是长期支持矩阵。改动任何组件之前，请重新核对 Amazon EKS AMI 文档和 NVIDIA 的前置条件。

### 步骤 1：克隆并配置

克隆仓库，然后基于随附的示例创建本地配置文件并收紧其权限：

```
git clone https://github.com/aws-samples/sample-code-for-gpu-fractioning-on-eks.git
cd sample-code-for-gpu-fractioning-on-eks
cp walkthrough.env.example walkthrough.env
chmod 600 walkthrough.env
```

克隆完成后，用 `walkthrough.env` 做配置，用 `run.sh` 执行各个阶段。生成的文件和 kubeconfig 都留在被忽略的 `.state` 目录里。`GPU_INSTANCE_TYPE` 决定实例类型，但只改它并不代表配置兼容。

walkthrough.env 中的默认值与可选身份验证设置

```
AWS_REGION=us-east-2
CLUSTER_NAME=runai-fractioning-blog
EKS_VERSION=1.36
GPU_INSTANCE_TYPE=g5.xlarge
NVIDIA_DRIVER_VERSION=615.71.10

# Choose a profile or access-key variables, not both.
# AWS_PROFILE=my-profile
# AWS_ACCESS_KEY_ID=YOUR_ACCESS_KEY_ID
# AWS_SECRET_ACCESS_KEY=YOUR_SECRET_ACCESS_KEY
# AWS_SESSION_TOKEN=YOUR_SESSION_TOKEN
```

切勿提交凭证，该本地配置文件已被 Git 忽略。在开始置备之前，先确认当前生效的身份：

```
./run.sh check
```

分阶段单独执行便于逐项检查结果，也可以用 `./run.sh walkthrough` 一路跑到显存上限测试。清理始终是单独的操作。

### 步骤 2：创建一次性集群

执行以下命令创建一次性 Amazon EKS 集群及其系统节点：

```
./run.sh create-cluster
```

该命令会置备一个运行 Kubernetes 1.36 的 Amazon EKS 集群、一个只带单个 NAT 网关的专用 VPC、OpenID Connect（OIDC）集成，以及一个私有的 m7i.large 托管节点。

config/eksctl-cluster.yaml.tpl 中的部分字段

```
iam:
  withOIDC: true
vpc:
  nat:
    gateway: Single
managedNodeGroups:
  - name: system-ondemand
    instanceType: m7i.large
    desiredCapacity: 1
    privateNetworking: true
```

### 步骤 3：构建自定义 AL2023 镜像

执行以下命令，用 R615 驱动分支构建自定义 AL2023 镜像：

```
./run.sh build-ami
```

脚本会自动发现一个公共构建子网，以及适用于 AL2023 上 Kubernetes 1.36 的[推荐标准 Amazon EKS AMI](https://docs.aws.amazon.com/eks/latest/userguide/retrieve-ami-id.html)。Packer 从 R615 驱动分支安装当前补丁版本与工具链，配置 NVIDIA runtime，检查软件包状态，并生成加密镜像。区域相关的 AMI ID 存放在 `.state/ami-id`。

`NVIDIA_DRIVER_VERSION` 选择的是 R615 分支，并不锁定到具体补丁号。工作流会把实际发现的驱动版本连同 AMI ID 一起记录下来，并把该版本写进 AMI 标签和节点组标签。构建中实际观察到的版本见 `.state/installed-driver-version`。生产环境中，请在你自己的构建里锁定确切的软件包与基础镜像，并验证一条受支持的驱动分支升级路径。

之所以需要这一步，只是因为验证时 EKS 优化的 AL2023 NVIDIA AMI 还没带上 R615 驱动分支。一旦该 AMI 为你的 GPU 选定的驱动、以及其余主机前置条件都满足 GPU Fractioning Operator 的要求，就应优先使用 EKS 优化的 NVIDIA AMI。各驱动版本可查 GitHub 上的 [Amazon EKS AMI 发布记录](https://github.com/awslabs/amazon-eks-ami/releases)。目前示例脚本依赖 R615 驱动和镜像构建阶段产生的元数据，因此改用官方现成 AMI 也需要同步修改脚本。

ami/eks-al2023-r615.pkr.hcl 中的相关 Packer 配置

```
source "amazon-ebs" "eks_al2023_r615" {
  source_ami = var.source_ami_id
  region = var.aws_region
  encrypt_boot = true
  metadata_options {
    http_tokens = "required"
  }
}
```

`SOURCE_AMI_ID` 与 `PACKER_SUBNET_ID` 是可选覆盖项，用于指定已批准的基础镜像或构建子网。操作系统或 GPU 栈发生变化时，需要重建镜像并重新测试。

### 步骤 4：添加 GPU 工作节点

执行以下命令，添加一个使用自定义镜像的 GPU 托管节点组：

```
./run.sh add-gpu-node
```

默认情况下，该托管节点组使用自定义镜像，保持一台 On-Demand g5.xlarge，也就是验证过的 GPU 工作节点。一条 GPU 污点会把普通工作负载挡在外面。脚本关闭了 [eksctl 的 NVIDIA 设备插件安装](https://docs.aws.amazon.com/eks/latest/eksctl/gpu-support.html)，因为该组件由 GPU Operator 负责。

config/eksctl-gpu-nodegroup.yaml.tpl 中的部分字段

```
managedNodeGroups:
  - name: gpu-g5-r615-ondemand
    instanceType: g5.xlarge
    ami: <generated-ami-id>
    amiFamily: AmazonLinux2023
    desiredCapacity: 1
    minSize: 1
    maxSize: 1
    privateNetworking: true
    taints:
      - key: nvidia.com/gpu
        effect: NoSchedule
```

### 步骤 5：安装 GPU Operator 并检查主机

执行以下命令安装 GPU Operator，并检查 GPU 工作节点的主机配置：

```
./run.sh install-gpu-operator
```

GPU Operator 26.7.1 提供设备插件和 Kubernetes 集成能力，其配置保留镜像自带的驱动与工具链：

```
driver:
  enabled: false
toolkit:
  enabled: false
```

同一条命令还会在 GPU 工作节点上运行一个临时特权检查 Pod，打印主机配置后删除该 Pod。验证过的节点报告如下：

实际观察到的主机配置

```
GPU: NVIDIA A10G, 23028 MiB
Driver: 615.71.10
NVIDIA Container Toolkit: 1.20.1-1
containerd: 2.3.5
cgroup filesystem: cgroup2fs
NRI socket paths:
  /var/run/nri/nri.sock
  /run/nri/nri.sock
```

在这台 AL2023 节点上，`/var/run` 是指向 `/run` 的符号链接，两个路径指向同一个 socket。特权检查只应放在一次性环境里做，并确认 Pod 已被删除。

### 步骤 6：建立整卡 GPU 基线

在安装分段组件之前，先执行以下命令测试整卡 GPU 的调度行为：

```
./run.sh baseline
```

基线中每个 Pod 都把 `nvidia.com/gpu` 的 request 和 limit 设为 1。该测试假定只有一块可用物理 GPU 且未开启共享：一个 Pod 进入运行状态，另一个停留在 `Pending`。这就演示了安装分段之前的整卡调度约束。在多 GPU 节点上，需要相应调整该基线，并确认两个分段工作负载确实落在同一块 GPU 上。

实测基线结果

```
NAME          READY   STATUS    NODE
whole-gpu-a   1/1     Running   <gpu-node>
whole-gpu-b   0/1     Pending   <none>
```

脚本会校验这一状态，然后删除两个基线 Pod。

### 步骤 7：安装 KAI Scheduler 与 GPU Fractioning Operator

执行以下命令安装 KAI Scheduler，其中已包含 GPU Fractioning Operator：

```
./run.sh install-kai
```

锁定版本的 [KAI Scheduler 0.18.5](https://github.com/kai-scheduler/KAI-Scheduler/tree/v0.18.5) chart 内含 GPU Fractioning Operator 0.1.7。这些 values 打开 `NvFractions` 与按 Pod 指标，同时保留 GPU 栈版本检查。可选的 `nvidia.com/container.<name>.gpu-compute.mode` annotation 用于选择计算模式。本演练中的工作负载不改动该默认值。

helm/kai-values.yaml 中的相关字段

```
global:
  gpuSharingMode: NvFractions
  nvFractions:
    set: true
gpu-fractioning:
  metricsAgent:
    enabled: true
  skipGpuStackVersionChecks: false
```

验证中，`FractiondReady`、`MpsdReady` 和 Ready 均为 True；`DriverUpgradeInProgress` 为 False，原因是 `NoDriverUpgrade`，这与驱动仍由 AMI 持有的事实相符。

### 步骤 8：执行正向共享测试

执行以下命令部署两个带 8 GiB 显存契约的 Pod：

```
./run.sh share
```

每个 Pod 都把内存 request 与 limit 设为 8 GiB，并选择 `kai-scheduler`。两者都不申请整块 `nvidia.com/gpu` 资源。仓库会应用这些调度字段，并运行一个分配 6 GiB 的 CUDA 探测程序：

kubernetes/fraction-8gi-pods.yaml 中的关键字段

```
metadata:
  annotations:
    nvidia.com/container.gpu-workload.gpu-memory.request: 8Gi
    nvidia.com/container.gpu-workload.gpu-memory.limit: 8Gi
spec:
  schedulerName: kai-scheduler
  runtimeClassName: nvidia
```

实测正向结果

```
NAME             READY   STATUS    NODE
fraction-8gi-a   1/1     Running   <same-gpu-node>
fraction-8gi-b   1/1     Running   <same-gpu-node>
```

脚本会校验节点名与 GPU UUID 是否一致。验证中两个 Pod 都看到 8,192 MiB，并报告 `allocation_succeeded_mib=6144`。这几项检查确认了三件事：两个 Pod 落在同一块物理 GPU 上、设备视图被限定在该契约内、各自的契约内分配都成功。

每个 Pod 的实测分配输出

```
NVIDIA_GPU_MEMORY_LIMIT=8192
requested_allocation_mib=6144
allocation_succeeded_mib=6144
```

两个 Pod 保持运行期间观察显存

```
./run.sh metrics
```

`gpu_fractioning_gpu_memory_used_bytes` 指标按 Pod 和 GPU UUID 归属显存。观测到每个 Pod 为 6,394 MiB（约 6.24 GiB），比探测程序申请的 6,144 MiB 多出 250 MiB。指标里可能包含 CUDA 上下文和运行时开销，本次实验没有拆分这部分。监控共享设备时，应把工作负载标识与 request、limit、usage 数值放在一起看。

实测按 Pod 指标序列

```
gpu_fractioning_gpu_memory_used_bytes{
  gpu_uuid="<same-gpu-uuid>",
  namespace="runai-fractioning-test",
  pod="fraction-8gi-a"} 6.704594944e+09

gpu_fractioning_gpu_memory_used_bytes{
  gpu_uuid="<same-gpu-uuid>",
  namespace="runai-fractioning-test",
  pod="fraction-8gi-b"} 6.704594944e+09
```

### 步骤 9：验证超限分配被拒绝

执行以下命令，测试一个超过 8 GiB 契约的分配：

```
./run.sh limit
```

该命令会删除正向测试的 Pod，并新建一个带 8 GiB 契约、试图分配 9 GiB 的 Pod。探测程序报告如下：

实测超限结果

```
NVIDIA_GPU_MEMORY_LIMIT=8192
requested_allocation_mib=9216
allocation_failed=out of memory
```

实测负向测试 Pod 状态

```
NAME                      READY   STATUS      NODE
fraction-8gi-over-limit   0/1     Completed   <gpu-node>
```

这里 `cudaMalloc` 返回 out-of-memory 错误，探测程序捕获该错误后以退出码 0 结束，因此状态是 `Completed` 而不是 `OOMKilled`，属于预期行为。这演示的是分配被拒绝，不代表容器会被终止，也不构成通用意义上的故障隔离。

### 步骤 10：清理

删除集群之前先记下 VPC ID。后面的独立校验使用默认集群名与区域；如果你改过配置，请替换为实际值。

记录 VPC ID

```
VPC_ID=$(aws eks describe-cluster \
  --name runai-fractioning-blog --region us-east-2 \
  --query cluster.resourcesVpcConfig.vpcId --output text)
```

移除一次性环境

```
./run.sh cleanup
```

标准清理会删除测试命名空间、Helm release 和一次性集群，但保留自定义 AMI 及其 Amazon EBS 快照。

校验资源已删除

```
aws eks describe-cluster \
  --name runai-fractioning-blog --region us-east-2
aws cloudformation describe-stacks \
  --stack-name eksctl-runai-fractioning-blog-cluster \
  --region us-east-2
aws ec2 describe-vpcs --vpc-ids "$VPC_ID" --region us-east-2
```

对已删除的资源，应看到明确的 resource-not-found 响应。身份验证或权限错误不能说明资源已删除。还应检查残留的节点组和带集群标签的实例。清理失败时，先查看 CloudFormation 事件，把归属依赖处理干净再重试。Amazon EKS 端点不存在，并不证明它的 VPC 已经消失。

只有当自定义 AMI 及其 Amazon EBS 快照确实不再需要时，才使用 `./run.sh cleanup-all`。如果镜像删除被拒绝，请核对 AMI ID 与 sample 归属标签，不要绕过这道保护。

## 生产环境注意事项

请把本文当作一次行为验证。使用可信工作负载，并针对分段请求施加最小权限 IAM、命名空间管控、已批准的镜像和准入规则。需要更强隔离时，应在受支持的硬件上改用整卡 GPU 或 MIG。

锁定版本的分段守护进程使用特权容器、主机 PID 访问以及 NRI/MPS 主机挂载。其部署与配置应仅限受信任的管理员操作。

要为 CUDA 上下文、缓存、批处理和运行时开销留出余量。在并发负载下测量延迟与吞吐量。监控分配失败、MPS 健康状况、NRI 连通性和 GPU 错误。把基础 AMI、驱动、工具链、设备插件、operator、调度器和工作负载镜像作为一个经过测试的整体组合来锁定版本；上线前重建镜像并演练回滚。

本演练要求 GPU 容量已预先置备，既没有配置、也没有验证能感知 GPU 分段的自动扩缩容。分段 Pod 选择 `kai-scheduler`，不申请 `nvidia.com/gpu` 资源，并用 `nodeSelector` 指向一个固定为单节点的节点组。Karpenter 对第二调度器的支持仍是未实现的功能请求（GitHub 上的 [issue #742](https://github.com/kubernetes-sigs/karpenter/issues/742)）。自定义镜像无法运行在 Amazon EKS Auto Mode 管理的节点上，因为 Auto Mode 会[自行选择并管理这些节点的 AMI](https://docs.aws.amazon.com/eks/latest/userguide/automode.html)。一个集群可以[把 Auto Mode 管理的节点与托管节点组混用](https://docs.aws.amazon.com/eks/latest/userguide/eks-compute.html)，但我们没有在这样的集群里验证本演练。

使用 Karpenter 的团队可以在 `EC2NodeClass` 中按 ID 引用同一个自定义 AMI，自动扩缩容的限制依然适用。这条路径我们未做验证。

KAI Scheduler 是第二调度器，负责为选择它的 Pod 做排队和放置。如果你已经在用 [Kueue](https://kueue.sigs.k8s.io/)，先确定由哪个组件负责 GPU 工作负载的排队，再决定是否引入 KAI Scheduler。

建议在 GPU 节点上运行 [Amazon EKS 节点监控 agent](https://docs.aws.amazon.com/eks/latest/userguide/node-health-nma.html)。在 2026 年 11 月 18 日的一次回归运行中，该 agent 在开启 MPS 共享的自定义 R615 镜像上运行，整个共享测试与上限测试期间都报告 GPU 状态健康；那次运行没有测试故障检测。由于 GPU Operator 已经运行了 Data Center GPU Manager（DCGM）host engine，应把该 agent 配置为[复用这个 host engine](https://docs.aws.amazon.com/eks/latest/userguide/node-monitoring-agent-configure.html#nma-configure-byo-dcgm)，而不是使用它自带的那个。

## 结论

本文以 G5/A10G 为验证示例，介绍了如何用自定义 AL2023 镜像在 Amazon EKS 上配置显存分段。核对前置条件并验证所选配置之后，该方案可以推广到兼容的 NVIDIA GPU。你建立了整卡 GPU 基线，在同一块 GPU 上跑了两个有界工作负载，查看了按 Pod 的显存用量，并验证了超过上限的分配会被拒绝。当工作负载的显存需求装得下时，分段能改善对现有容量的利用。生产落地还需要隔离控制和性能测试。

要复现实验，请克隆 [AWS Samples 仓库](https://github.com/aws-samples/sample-code-for-gpu-fractioning-on-eks)，并把你的结果与其中的验证证据对照。把示例适配到自己的工作负载之前，先看看 [GPU Fractioning Operator 文档](https://github.com/kai-scheduler/gpu-fractioning/) 和 [Amazon EKS 加速 AMI 指南](https://docs.aws.amazon.com/eks/latest/userguide/ml-eks-optimized-ami.html)。
