# 在 Amazon EKS 上使用 NVIDIA Run:ai GPU 分段

GPU 共享并不是什么新鲜事：多实例 GPU (MIG)、时间切片和多进程服务 (MPS) 可以满足不同的隔离和利用需求。 NVIDIA Run:ai GPU Fractioning 基于 MPS 构建，具有 Kubernetes 集成调度、per-Pod 内存合约、执行和指标。

[NVIDIA Run:ai](https://github.com/dsx-ai-factory/run-ai) 是适用于 Kubernetes 的 AI 工作负载编排软件。其 GPU Fractioning Operator 可以帮助多个团队在 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/) 上共享一两个 GPU。即使 GPU 内存仍然可用，笔记本、模型评估和小型推理服务也会让团队等待。在本演练的基准中，NVIDIA 设备插件将单个 GPU 公开为一个 `nvidia.com/gpu` 资源，并禁用 GPU 共享。每个请求 `nvidia.com/gpu: 1` 的两个 Pod 无法在该节点上同时运行，即使它们的 GPU 内存组合需求满足。

[NVIDIA Run:ai GPU Fractioning](https://github.com/kai-scheduler/gpu-fractioning/) 在基于软件的共享中添加了 Kubernetes 调度集成、强制 GPU 内存限制和每个 Pod 指标。该方法适用于满足 GPU Fractioning Operator 硬件和软件要求的 NVIDIA GPU，包括不带 MIG 的 GPU。我们使用一个带有 NVIDIA A10G Tensor Core GPU 的 [Amazon Elastic Compute Cloud (Amazon EC2)](https://aws.amazon.com/ec2/) g5.xlarge 实例作为经过验证的示例。其他配置需要兼容性检查和验证。

NVIDIA [宣布](https://developer.nvidia.com/blog/nvidia-runai-is-now-open-source-as-part-of-nvidia-dsx-ai-factory-platform/) 于 2026 年 10 月 13 日发布 [NVIDIA Run:ai 开源版本](https://github.com/dsx-ai-factory/run-ai)。此示例使用其四个模块化组件中的两个：[KAI Scheduler](https://github.com/kai-scheduler/KAI-Scheduler) 和 [GPU Fractioning Operator](https://github.com/kai-scheduler/gpu-fractioning/)。 KAI 资源管理和工作负载图解决了本演练范围之外的组织治理和其他工作负载类型。

在本文中，我们将展示如何构建自定义 [Amazon Linux 2023 (AL2023)](https://aws.amazon.com/linux/amazon-linux-2023/) 映像并在 Amazon EKS 上配置 GPU 内存共享。在经过验证的 G5/A10G 示例中，您建立了整个 GPU 基线，为每个 Pod 提供 8 GiB 内存合同，并验证 6 GiB 分配。然后，您检查每个 Pod 指标，测试拒绝 9 GiB 分配，并清理一次性环境。

## 选择GPU共享方式

MIG 在[支持的 GPU](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/supported-gpus.html) 上提供硬件分区。 [设备插件时间切片](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/gpu-sharing.html) 共享一个 GPU，没有副本内存或故障隔离。 MPS 允许并发 CUDA 进程。故障遏制取决于配置。 NVIDIA Run:ai GPU Fractioning 添加了强制的每个容器内存限制，并支持时间切片（默认）或 sm 共享计算模式。 [NVIDIA 文档](https://developer.nvidia.com/blog/memory-enforced-gpu-sharing-in-kubernetes-with-nvidia-cuda-13-4/) 其默认模式的独立工作负载错误域和 sm 共享的共享错误域。这些都不是安全保证。本演练测试内存限制，而不是故障遏制或计算性能。内存限制不保留比例计算。

Amazon EKS 记录了多个 GPU 共享选项：[MIG](https://docs.aws.amazon.com/eks/latest/userguide/device-management-nvidia-mig.html)、使用 [NVIDIA 设备插件](https://docs.aws.amazon.com/eks/latest/userguide/device-management-nvidia-time-slicing.html#eks-time-slicing-device-plugin-al2023) 进行时间切片以及使用 [NVIDIA DRA 驱动程序和 Karpenter](https://docs.aws.amazon.com/eks/latest/userguide/device-management-nvidia-time-slicing.html#eks-time-slicing-karpenter-consumable-capacity) 进行时间切片。有关在其中进行选择的指南，请参阅 Amazon EKS 最佳实践指南中的[GPU 共享指南](https://docs.aws.amazon.com/eks/latest/best-practices/aiml-compute.html#_optimize_gpu_resource_allocation_with_time_slicing_mig_and_fractional_gpu_allocation)。当您需要在没有 MIG 的 GPU 上强制执行每个 Pod GPU 内存限制并且可以运行固定大小的 GPU 节点组时，请选择 GPU 分段。

[动态资源分配（DRA）](https://docs.aws.amazon.com/eks/latest/userguide/device-management.html) 提供用于请求和分配设备的 Kubernetes API。 GPU 共享和隔离取决于设备驱动程序的实现和启用的功能。 KAI Scheduler 和 GPU Operator 支持 DRA。本演练使用 NvFractions 注释，而不是 DRA。

GPU 分数划分可以帮助交互式笔记本实现空闲期、短评估作业、GPU 兼容性测试和小型推理服务。从测量的峰值使用量加上开销中选择每个 GPU 内存请求，然后测试并发负载下的延迟。所展示的密度改进并没有建立吞吐量增益或普遍成本降低。

## 实施演练

本演练使用 AWS Samples 存储库。确认先决条件和经过验证的组件版本，然后完成步骤 1 到 10。

### 先决条件

使用具有 Amazon EKS、[AWS CloudFormation](https://aws.amazon.com/cloudformation/)、Amazon VPC、Amazon EC2、[Amazon Elastic Block Store (Amazon EBS)](https://aws.amazon.com/ebs/)、[AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 和 [AWS Systems Manager](https://aws.amazon.com/systems-manager/) 权限的 AWS 账户进行 Amazon 系统映像 (AMI) 发现。确认 g5.xlarge、系统节点和临时 m5.xlarge 映像生成器的配额和容量。安装 AWS CLI v2、eksctl、kubectl、Helm、Packer、Git、jq 和 curl。

使用普通的 AWS 凭证提供程序：命名配置文件、[AWS IAM Identity Center](https://aws.amazon.com/iam/identity-center/)、代入角色或访问密钥环境变量。更喜欢临时凭证。使用临时访问密钥时需要 `AWS_SESSION_TOKEN`。这些示例使用 us-east-2。另一个区域必须支持所选的 Amazon EKS 版本和实例类型。

在选择其他 GPU 之前，请检查 NVIDIA 的 [GPU Operator 硬件列表](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/platform-support.html#supported-nvidia-data-center-gpus-and-systems)、所选的 [驱动程序的硬件支持](https://docs.nvidia.com/datacenter/tesla/tesla-release-notes-615-71-10/index.html) 以及 [GPU Fractioning Operator 先决条件](https://github.com/kai-scheduler/gpu-fractioning/blob/v0.1.7/README.md#prerequisites)。仅硬件支持并不能建立分数兼容性。本演练仅验证 G5/A10G 配置。 AMI 构建目标为 `x86_64`。检查 CUDA 兼容性和内存空间：两个 8 GiB 合约都需要空间来容纳合约和运行时开销。较小的设备需要较小的合同和调整后的探头。

本演练创建可计费资源，包括 Amazon EKS 控制平面、NAT 网关、实例、卷和 AMI 快照。使用一次性环境并在验证完成后进行彻底清理。

### 使用经过验证的 AL2023 堆栈

在验证时，EKS 优化的 AL2023 NVIDIA 映像提供了 R580 和 R595 驱动程序分支。 GPU Fractioning Operator v0.1.7 需要 R615 或更高版本。 R615 是短暂的，不是 GPU Operator 默认值。此示例使用 AMI 拥有的驱动程序和工具包构建自定义标准 Amazon EKS 1.36 AL2023 映像。它不使用另一个操作系统上的操作员管理的驱动程序容器。该表记录实验室验证，而不是供应商支持认证。

| **组件** | **验证版本** |
| --- | --- |
|亚马逊 EKS | 1.36 | 1.36
|图形处理器 | NVIDIA A10G，23,028 MiB |
| NVIDIA 驱动程序/容器工具包 | 615.71.10 / 1.20.1-1 |
|容器 | 2.3.5 与 NRI |
| GPU 操作员/设备插件 | 26.7.1 / 0.20.1 |
| KAI 调度程序/分式运算符 | 0.18.5 / 0.1.7 | 0.18.5 / 0.1.7

我们于 2026 年 10 月 22 日使用 NVIDIA 驱动程序 615.71.10 验证了本演练。 2026 年 11 月 18 日，更新 GPU 节点污点后，我们使用具有相同驱动程序的映像重复了除步骤 3 映像构建之外的所有步骤。结果匹配。该表列出了经过测试的组件版本，而不是永久支持矩阵。在更改任何组件之前，请重新检查 Amazon EKS AMI 文档和 NVIDIA 先决条件。

### 第 1 步：克隆并配置

克隆存储库，然后从提供的示例创建本地配置文件并限制其权限：
```
git clone https://github.com/aws-samples/sample-code-for-gpu-fractioning-on-eks.git
cd sample-code-for-gpu-fractioning-on-eks
cp walkthrough.env.example walkthrough.env
chmod 600 walkthrough.env
```
克隆后，使用 `walkthrough.env` 进行配置，并使用 `run.sh` 进行每个阶段。生成的文件和 kubeconfig 保留在被忽略的 `.state` 目录中。 `GPU_INSTANCE_TYPE` 选择实例类型。单独更改它并不能建立兼容性。

walkthrough.env 中的默认值和可选身份验证设置
```
AWS_REGION=us-east-2
CLUSTER_NAME=runai-fractioning-blog
EKS_VERSION=1.36
GPU_INSTANCE_TYPE=g5.xlarge
NVIDIA_DRIVER_VERSION=615.71.10

# Choose a profile or access-key variables, not both.
# AWS_PROFILE=my-profile
# AWS_ACCESS_KEY_ID=YOUR_ACCESS_KEY_ID
# AWS_SECRET_ACCESS_KEY=YOUR_SECRET_ACCESS_KEY
# AWS_SESSION_TOKEN=YOUR_SESSION_TOKEN
```
切勿提交凭证。 Git 会忽略本地配置文件。在配置之前确认活动身份：
```
./run.sh check
```
单独运行阶段来检查结果，或使用 `./run.sh walkthrough` 来运行内存限制测试。清理始终是一个单独的操作。

### 步骤 2：创建一次性集群

运行以下命令创建一次性 Amazon EKS 集群及其系统节点：
```
./run.sh create-cluster
```
该命令配置一个运行 Kubernetes 版本 1.36 的 Amazon EKS 集群、一个带有一个 NAT 网关的专用 VPC、OpenID Connect (OIDC) 集成以及一个私有 m7i.large 托管节点。

从 config/eksctl-cluster.yaml.tpl 中选择的字段
```
iam:
  withOIDC: true
vpc:
  nat:
    gateway: Single
managedNodeGroups:
  - name: system-ondemand
    instanceType: m7i.large
    desiredCapacity: 1
    privateNetworking: true
```
### 第 3 步：构建自定义 AL2023 映像

运行以下命令以使用 R615 驱动程序分支构建自定义 AL2023 映像：
```
./run.sh build-ami
```
该脚本会发现 AL2023 上 Kubernetes 1.36 的公共构建器子网和[推荐的标准 Amazon EKS AMI](https://docs.aws.amazon.com/eks/latest/userguide/retrieve-ami-id.html)。 Packer 从 R615 驱动程序分支和工具包安装当前补丁版本，配置 NVIDIA 运行时，检查包状态并创建加密映像。区域特定的 AMI ID 存储在 `.state/ami-id` 中。

`NVIDIA_DRIVER_VERSION`选择R615支路。它不是一个精确的贴片引脚。该工作流程使用 AMI ID 记录发现的驱动程序版本，并在 AMI 和节点组标签中使用该版本。请阅读 `.state/installed-driver-version` 以了解在您的构建中观察到的版本。对于生产，在您自己的构建中固定确切的包和基础映像，并验证支持的驱动程序分支升级。

您需要执行此步骤只是因为 EKS 优化的 AL2023 NVIDIA AMI 在验证时不包含 R615 驱动程序分支。一旦为您的 GPU 选择的驱动程序和其余主机先决条件满足 GPU Fractioning Operator 要求，请首选 EKS 优化的 NVIDIA AMI。检查 GitHub 上的 [Amazon EKS AMI 版本](https://github.com/awslabs/amazon-eks-ami/releases) 中的驱动程序版本。该示例的脚本当前需要来自映像构建的 R615 驱动程序和元数据，因此使用库存 AMI 还需要更改脚本。

来自 ami/eks-al2023-r615.pkr.hcl 的相关加壳器设置
```
source "amazon-ebs" "eks_al2023_r615" {
  source_ami = var.source_ami_id
  region = var.aws_region
  encrypt_boot = true
  metadata_options {
    http_tokens = "required"
  }
}
```
`SOURCE_AMI_ID` 和 `PACKER_SUBNET_ID` 是批准的基础映像或构建器子网的可选覆盖。当操作系统或 GPU 堆栈发生变化时重建并测试图像。

### 步骤 4：添加 GPU 工作线程

运行以下命令添加使用自定义镜像的GPU托管节点组：
```
./run.sh add-gpu-node
```
默认情况下，托管节点组使用自定义映像并保留一个 On-Demand g5.xlarge（经过验证的 GPU 工作线程）。 GPU 污点排除了普通工作负载。该脚本禁用 [eksctl 的 NVIDIA 设备插件安装](https://docs.aws.amazon.com/eks/latest/eksctl/gpu-support.html)，因为 GPU Operator 管理该组件。

从 config/eksctl-gpu-nodegroup.yaml.tpl 中选择的字段
```
managedNodeGroups:
  - name: gpu-g5-r615-ondemand
    instanceType: g5.xlarge
    ami: <generated-ami-id>
    amiFamily: AmazonLinux2023
    desiredCapacity: 1
    minSize: 1
    maxSize: 1
    privateNetworking: true
    taints:
      - key: nvidia.com/gpu
        effect: NoSchedule
```
### 步骤 5：安装 GPU Operator 并检查主机

运行以下命令安装 GPU Operator 并检查 GPU Worker 的主机配置：
```
./run.sh install-gpu-operator
```
GPU Operator 26.7.1 提供设备插件和 Kubernetes 集成。它的配置保留了映像拥有的驱动程序和工具包：
```
driver:
  enabled: false
toolkit:
  enabled: false
```
同一命令在 GPU Worker 上运行临时特权检查 Pod，打印主机配置，然后删除该 Pod。经过验证的节点报告：

观察主机配置
```
GPU: NVIDIA A10G, 23028 MiB
Driver: 615.71.10
NVIDIA Container Toolkit: 1.20.1-1
containerd: 2.3.5
cgroup filesystem: cgroup2fs
NRI socket paths:
  /var/run/nri/nri.sock
  /run/nri/nri.sock
```
在此 AL2023 节点上，`/var/run` 是指向 `/run` 的符号链接。两条路径都标识相同的套接字。将特权检查限制在一次性环境中，并确认 Pod 已被移除。

### 步骤 6：建立整体 GPU 基线

在安装 Fractioning 之前，运行以下命令来测试整个 GPU 调度：
```
./run.sh baseline
```
每个基线 Pod 请求并将 `nvidia.com/gpu` 限制为 1。测试假设一个可用的物理 GPU 禁用共享：一个 Pod 运行，另一个保持 `Pending`。这演示了安装分段之前的整个设备调度约束。在多 GPU 节点上，调整此基准并验证两个部分工作负载是否使用相同的 GPU。

测量基线结果
```
NAME          READY   STATUS    NODE
whole-gpu-a   1/1     Running   <gpu-node>
whole-gpu-b   0/1     Pending   <none>
```
该脚本检查此状态并删除两个基线 Pod。

### 步骤 7：安装 KAI Scheduler 和 GPU Fractioning Operator

运行以下命令安装 KAI Scheduler，其中包括 GPU Fractioning Operator：
```
./run.sh install-kai
```
固定的 [KAI Scheduler 0.18.5](https://github.com/kai-scheduler/KAI-Scheduler/tree/v0.18.5) 图表包括 GPU Fractioning Operator 0.1.7。这些值打开 `NvFractions` 和每个 Pod 指标，同时保留 GPU 堆栈版本检查。可选的 `nvidia.com/container.<name>.gpu-compute.mode` 注释选择计算模式。这些工作负载保持默认值不变。

helm/kai-values.yaml 中的相关字段
```
global:
  gpuSharingMode: NvFractions
  nvFractions:
    set: true
gpu-fractioning:
  metricsAgent:
    enabled: true
  skipGpuStackVersionChecks: false
```
验证中，`FractiondReady`、`MpsdReady` 和 Ready 为 True。 `DriverUpgradeInProgress` 为 False，原因为 `NoDriverUpgrade`，与 AMI 保留驱动程序所有权一致。

### 第 8 步：运行积极分享测试

运行以下命令部署两个具有 8 GiB GPU 内存合约的 Pod：
```
./run.sh share
```
每个 Pod 请求内存并将其限制为 8 GiB，并选择 `kai-scheduler`。两者都不会请求整个 `nvidia.com/gpu` 资源。存储库应用这些调度字段并运行分配 6 GiB 的 CUDA 探测器：

kubernetes/fraction-8gi-pods.yaml 中的基本字段
```
metadata:
  annotations:
    nvidia.com/container.gpu-workload.gpu-memory.request: 8Gi
    nvidia.com/container.gpu-workload.gpu-memory.limit: 8Gi
spec:
  schedulerName: kai-scheduler
  runtimeClassName: nvidia
```
测量呈阳性结果
```
NAME             READY   STATUS    NODE
fraction-8gi-a   1/1     Running   <same-gpu-node>
fraction-8gi-b   1/1     Running   <same-gpu-node>
```
该脚本验证匹配的节点名称和 GPU UUID。在验证中，两个 Pod 都看到 8,192 MiB 并报告 `allocation_succeeded_mib=6144`。这些检查确定一个物理 GPU 上的放置、有界设备视图以及每个合约内的成功分配。

每个 Pod 的测量分配输出
```
NVIDIA_GPU_MEMORY_LIMIT=8192
requested_allocation_mib=6144
allocation_succeeded_mib=6144
```
在两个 Pod 保持活动状态时观察内存
```
./run.sh metrics
```
`gpu_fractioning_gpu_memory_used_bytes` 指标通过 Pod 和 GPU UUID 来属性内存。观察到的每个 Pod 为 6,394 MiB（约 6.24 GiB），比探测器的 6,144 MiB 分配多了 250 MiB。指标可以包括 CUDA 上下文和运行时开销。该实验不测量这种故障。监控共享设备时，将工作负载标识以及请求、限制和使用值保留在一起。

按 Pod 度量的度量系列
```
gpu_fractioning_gpu_memory_used_bytes{
  gpu_uuid="<same-gpu-uuid>",
  namespace="runai-fractioning-test",
  pod="fraction-8gi-a"} 6.704594944e+09

gpu_fractioning_gpu_memory_used_bytes{
  gpu_uuid="<same-gpu-uuid>",
  namespace="runai-fractioning-test",
  pod="fraction-8gi-b"} 6.704594944e+09
```
### 步骤 9：验证拒绝是否超出限制

运行以下命令来测试超过 8 GiB 合同的分配：
```
./run.sh limit
```
此命令删除正测试 Pod，并创建一个具有 8 GiB 合约的 Pod，尝试分配 9 GiB。调查报告称：

测量超限结果
```
NVIDIA_GPU_MEMORY_LIMIT=8192
requested_allocation_mib=9216
allocation_failed=out of memory
```
测量的阴性测试 Pod 状态
```
NAME                      READY   STATUS      NODE
fraction-8gi-over-limit   0/1     Completed   <gpu-node>
```
此处，`cudaMalloc` 返回内存不足错误，探测器会在以代码 0 退出之前处理该错误。需要 `Completed`，而不是 `OOMKilled`。这表明分配拒绝，而不是容器终止或一般故障隔离。

### 第 10 步：清理

在删除集群之前捕获 VPC ID。接下来的独立检查使用默认集群名称和区域。如果您更改了配置值，请替换它们。

捕获 VPC ID
```
VPC_ID=$(aws eks describe-cluster \
  --name runai-fractioning-blog --region us-east-2 \
  --query cluster.resourcesVpcConfig.vpcId --output text)
```
去除一次性环境
```
./run.sh cleanup
```
标准清理会删除测试命名空间、Helm 版本和一次性集群，同时保留自定义 AMI 及其 Amazon EBS 快照。

验证资源删除
```
aws eks describe-cluster \
  --name runai-fractioning-blog --region us-east-2
aws cloudformation describe-stacks \
  --stack-name eksctl-runai-fractioning-blog-cluster \
  --region us-east-2
aws ec2 describe-vpcs --vpc-ids "$VPC_ID" --region us-east-2
```
对于已删除的资源，预计会出现明确的资源未找到响应。身份验证或权限错误不会建立删除。还要检查剩余的节点组和集群标记的实例。如果清理失败，请在重试之前检查 CloudFormation 事件并解决拥有的依赖项。缺失的 Amazon EKS 终端节点并不能证明其 VPC 已消失。

仅当不再需要自定义 AMI 及其 Amazon EBS 快照时才使用 `./run.sh cleanup-all`。如果图像删除被拒绝，请确认 AMI ID 和样本所有权标签。请勿绕过防护装置。

## 生产注意事项

将其视为行为验证。使用可信工作负载并针对分数请求应用最低权限 IAM、命名空间控制、批准的映像和准入规则。当需要更强的隔离时，请在支持的硬件上选择整个 GPU 或 MIG。

固定的分段守护进程使用特权容器、主机 PID 访问和 NRI/MPS 主机挂载。将其部署和配置限制为受信任的管理员。

为 CUDA 上下文、缓存、批处理和运行时开销留出空间。测量并发负载下的延迟和吞吐量。监控分配失败、MPS 运行状况、NRI 连接和 GPU 错误。将基础 AMI、驱动程序、工具包、设备插件、操作员、调度程序和工作负载映像固定为一个经过测试的组合。在推出之前重建映像并测试回滚。

本演练需要预先配置的 GPU 容量。它不会配置或验证 GPU 分数感知自动缩放。部分 Pod 选择 `kai-scheduler`，不请求 `nvidia.com/gpu` 资源，并使用以固定在一个节点的节点组为目标的 `nodeSelector`。 Karpenter 对辅助调度程序的支持是一个开放的功能请求（GitHub 上的[问题 #742](https://github.com/kubernetes-sigs/karpenter/issues/742)）。自定义映像无法在 Amazon EKS 自动模式管理的节点上运行，因为自动模式[选择并管理其 AMI](https://docs.aws.amazon.com/eks/latest/userguide/automode.html)。群集可以[将自动模式托管节点与托管节点组混合](https://docs.aws.amazon.com/eks/latest/userguide/eks-compute.html)，但我们没有在此类群集中验证此演练。

使用 Karpenter 的团队可以通过 `EC2NodeClass` 中的 ID 引用相同的自定义 AMI。自动缩放限制仍然适用。我们没有验证这条路径。

KAI Scheduler 是第二个调度程序。它处理选择它的 Pod 的排队和放置。如果您已经使用 [Kueue](https://kueue.sigs.k8s.io/)，请在采用 KAI Scheduler 之前确定哪个组件拥有 GPU 工作负载队列。

我们建议在 GPU 节点上运行 [Amazon EKS 节点监控代理](https://docs.aws.amazon.com/eks/latest/userguide/node-health-nma.html)。在 2026 年 11 月 18 日的回归运行中，代理在具有 MPS 共享活动的自定义 R615 映像上运行，并在整个共享和限制测试中报告健康的 GPU 状况。该运行没有测试故障检测。由于 GPU Operator 已运行数据中心 GPU 管理器 (DCGM) 主机引擎，因此请将代理配置为 [使用该主机引擎](https://docs.aws.amazon.com/eks/latest/userguide/node-monitoring-agent-configure.html#nma-configure-byo-dcgm)，而不是其捆绑的引擎。

## 结论

在这篇文章中，我们使用 G5/A10G 作为经过验证的示例，展示了如何使用自定义 AL2023 映像在 Amazon EKS 上配置 GPU 内存分段。在检查先决条件并验证所选配置后，该方法扩展到兼容的 NVIDIA GPU。您建立了整个 GPU 基准，在同一 GPU 上运行两个有界工作负载，检查每个 Pod 内存使用情况，并验证拒绝超出限制的分配。当工作负载内存适合时，分段可以改善对现有容量的访问。生产采用还需要隔离控制和性能测试。

要重复实验，请克隆 [AWS 示例存储库](https://github.com/aws-samples/sample-code-for-gpu-fractioning-on-eks) 并将您的结果与其经过验证的证据进行比较。在根据您的工作负载调整示例之前，请先浏览 [GPU Fractioning Operator 文档](https://github.com/kai-scheduler/gpu-fractioning/) 和 [Amazon EKS 加速 AMI 指南](https://docs.aws.amazon.com/eks/latest/userguide/ml-eks-optimized-ami.html)。
