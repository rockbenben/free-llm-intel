# 从代码到图表：用 Amazon Bedrock AgentCore 实现 agentic 架构文档

随着代码库快速演进，架构文档始终是软件开发中最持久未解的难题之一。开发团队常常要花数小时手工绘制架构图，结果部署后短短几周它们就已过时。这种文档缺口会造成知识孤岛、拖慢开发者上手速度，并让合规审计变得复杂。

[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 是一个可以用任意框架或模型大规模构建、连接并优化 agent 的平台。它通过自主 agent 提供解决方案：这些 agent 可以分析代码库、生成架构图，并自动维护可搜索的文档。这种 agentic 方式利用迭代式改进与自我纠正，通过 AWS 服务统筹代码分析、图表生成与自动发布。

本文将介绍一家全球跨交易商经纪商（interdealer broker）如何构建自动化的架构文档 pipeline，并与既有的持续集成与持续交付（CI/CD）工作流集成。该方案结合 [AgentCore](https://aws.amazon.com/bedrock/agentcore/) 做代码分析、[Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 提供语义搜索能力、[AWS CodePipeline](https://aws.amazon.com/codepipeline/) 负责持续部署。我们与一家在全球主要金融市场从事跨交易商经纪业务的全球性金融服务公司共同开发并验证了这一做法；该方案自 2026 年第一季度起在生产环境运行，用于维护其电子交易平台的架构文档。

## 架构文档的挑战

开发团队在架构文档方面面临若干关键痛点：

- **耗时的手工流程** – 以统一建模语言（UML）或 Mermaid 等格式编制完整的架构图极为费工。对大型代码库而言，这种方式不可持续。
- **迅速过时** – 代码每天都在变化，而文档更新滞后。几周之内，图表就不再反映现实，使其在决策中不可靠。
- **知识孤岛** – 团队成员离开后，部落知识随之消失。遗留系统变成「黑盒」，迫使新开发者逆向工程代码，拖慢上手并削弱组织知识。
- **合规缺口** – 安全评审与审计要求提供当前的架构图。过时的文档会带来合规风险并延误认证。

这些挑战在微服务架构中会叠加放大——在微服务架构中，理解服务依赖与消息流对防止级联故障至关重要。

## 解决方案概览

我们的方案使用 AgentCore 创建一个自主 agent，用于分析 .NET 代码库并生成完整的架构图。该 agent 运行在 AWS CodePipeline 内，由向 [AWS CodeCommit](https://aws.amazon.com/codecommit/) 仓库提交代码触发。随后生成的图表及其元数据被摄取到 Amazon Bedrock Knowledge Bases，以支持对全部架构文档语料的语义搜索与自然语言查询。这让你能更清楚地了解架构的当前状态，并从这种可见性中释放业务价值。

### 关键组件

该方案集成多项 AWS 服务，以实现一条精简的工作流：

| **服务名称** | **职责** |
| --- | --- |
| Amazon Bedrock AgentCore | 为我们的自主文档 agent 提供无服务器运行时环境。AgentCore 负责 agent 生命周期管理、自动扩缩容与工具编排，无需管理基础设施。 |
| AWS CodePipeline | 统筹从代码提交到发布文档的端到端工作流。该 pipeline 直接与 AWS CodeCommit 集成，在每次向主分支 push 时触发文档生成。 |
| [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/) | 存储生成的图表并托管文档站点，提供持久存储与全球可访问性。专用的 Architecture Diagrams 存储桶存放可缩放矢量图形（SVG）文件、Mermaid 源文件与图表元数据。[Amazon S3](https://aws.amazon.com/s3/) 同时充当 Amazon Bedrock Knowledge Bases 的向量存储后端。 |
| [AWS CodeBuild](https://aws.amazon.com/codebuild/) | 执行 pipeline 的各个阶段，包括依赖安装、agent 调用与产物准备。 |
| Amazon Bedrock Knowledge Bases | 作为生成式架构文档的检索与呈现层。存放在 Amazon S3 中的图表元数据、Mermaid 源文件与描述会使用 Amazon Titan Text Embeddings 模型摄取到 Knowledge Base。以 Amazon S3 作为向量存储，它支持语义搜索与自然语言查询。 |

该工作流包含以下步骤：

- 开发者把代码变更推送到 AWS CodeCommit。
- AWS CodeCommit 触发 AWS CodePipeline 执行。
- AWS CodePipeline 启动构建流程。
- AWS CodeBuild 从 AWS CodeCommit 仓库获取代码，然后把源代码打包并上传到 [Amazon S3](https://aws.amazon.com/s3/) 源代码存储桶。
- AWS CodeBuild 调用 AgentCore：它准备调用载荷并调用由 AgentCore 托管的 Strands agent。该 agent 使用通过 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 可用的大语言模型作为推理引擎，分析代码模式、生成图表语法，并自我纠正校验错误。按区域查看模型可用性，请参阅 [Amazon Bedrock 中按 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。
- Strands agent 从 Amazon S3 获取源代码。
- Strands agent 扫描代码库、生成图表、校验语法，并把图表转换为 SVG 文件以进行迭代式改进。
- Strands agent 把产物上传到 Amazon S3 的 Architecture Diagrams 存储桶，包括渲染后的 SVG 文件、Mermaid 源文件与图表描述元数据（JSON）。
- Amazon Bedrock Knowledge Bases 从 Amazon S3 的 Architecture Diagrams 存储桶摄取图表产物。摄取 pipeline 使用 Amazon Titan Text Embeddings v2 模型生成向量 embedding，对图表描述与 Mermaid 源码做分块、切成语义上有意义的单元，并把生成的向量存入 Amazon S3 向量存储。这支持对完整架构文档的语义搜索与检索增强生成（RAG）。
- 开发者与相关方通过自然语言查询知识库，以发现、探索并检索相关架构图及其上下文说明：例如询问「重连活动的流程是什么样的？」或「列出基础设施组件的所有类图」。

### 代码分析与优先级排序

agent 先分析代码库结构。它不会处理每一个文件，而是聚焦生产代码，排除测试文件、构建产物与生成代码。这种优先级排序减少了处理时间并提升了图表的相关性。

```
def scan_codebase(source_path: str) -> str:
    """Scan .NET codebase and return structured analysis."""
    cs_files = []
    for root, dirs, files in os.walk(source_path):
        dirs[:] = [d for d in dirs if d not in ['bin', 'obj', 'packages', '.git']]
        for file in files:
            if file.endswith('.cs'):
                analysis = analyze_csharp_file(os.path.join(root, file))
                cs_files.append(analysis)
    return json.dumps({
        "files_found": len(cs_files),
        "summary": generate_summary(cs_files),
        "files": cs_files
    })
```

扫描会识别关键架构元素，包括接口、抽象类、具体实现及其依赖关系。这种结构化分析为 agent 提供了生成准确图表所需的上下文。

### 使用 Amazon Bedrock AgentCore 部署文档 agent

你可以用 AgentCore 托管一个自主文档 agent，该 agent 使用 Strands agent 进行迭代式改进与自我纠正。

```
from bedrock_agentcore.runtime import BedrockAgentCoreApp
from strands import Agent
from strands.models.bedrock import BedrockModel

app = BedrockAgentCoreApp()

def create_uml_agent():
    model = BedrockModel(
        model_id="your-selected-model-id",
        region_name="us-east-1",
        temperature=0.3,
        max_tokens=4096
    )
    agent = Agent(
        model=model,
        system_prompt=UML_GENERATION_PROMPT,
        tools=[fetch_source_from_s3, scan_codebase, save_mermaid_diagram,
               validate_mermaid_syntax, convert_to_svg, upload_to_s3]
    )
    return agent

@app.entrypoint
async def invoke(payload: Dict[str, Any], context: Any) -> AsyncGenerator[Dict[str, Any], None]:
    """AgentCore entrypoint for UML generation."""
    # Extract parameters from payload
    source_s3_bucket = payload.get("source_s3_bucket")
    source_s3_key = payload.get("source_s3_key")
    project_name = payload.get("project_name", "Project")
    diagrams_bucket = payload.get("diagrams_bucket", "")

    # Create UML agent instance
    agent = create_uml_agent()

    # Construct generation prompt
    generation_prompt = f"""Generate complete UML documentation for {project_name}.

Steps:
1. Fetch source code from Amazon S3 bucket: {source_s3_bucket}, key: {source_s3_key}
2. Scan and analyze the codebase
3. Generate all required diagrams
4. Validate and convert each diagram to SVG
5. Upload all artifacts to Amazon S3

Begin now by fetching the source code."""

    # Stream async response
    stream = agent.stream_async(generation_prompt)

    # Process stream events
    async for event in stream:
        if "data" in event and isinstance(event["data"], str):
            yield {"content": event["data"]}
```

agent 依据其对代码库的分析以及图表生成的当前状态来做出工具使用决策。这种 agentic 方式在出现校验错误时允许自我纠正，相比单次 API 调用显著提升了可靠性。

### Agentic 工作流

该 agent 遵循一套迭代式工作流，其方式与人类架构师处理文档的思路相似：

![跨理解、生成、校验、转换与发布各阶段的迭代式 agent 工作流](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/28/ML-20745-2.png)

图 2：跨理解、生成、校验、转换与发布各阶段的迭代式 agent 工作流

**阶段 1 – 理解**：agent 从 Amazon S3 获取源代码并扫描代码库，以理解整体结构，识别关键组件、接口与关系。

**阶段 2 – 生成**：对于每一种架构图类型，agent 使用通过 Amazon Bedrock 可用的基础模型，基于其分析生成 Mermaid 形式的 UML。图表类型包括类图、序列图、状态图、组件图与活动图。

**阶段 3 – 校验：** 生成每张图之后，agent 会校验 Mermaid 语法。如果检测到错误，agent 会分析错误信息并带着修正重新生成图表。

**阶段 4 – 转换**：校验通过后，agent 把图表转换为 SVG 格式，以便在 Web 浏览器中高质量渲染。

**阶段 5 – 发布：** agent 把产物、SVG 文件、Mermaid 源文件与图表元数据上传到 Amazon S3 的 Architecture Diagrams 存储桶。

这种迭代方式达到 95% 的可靠性，而单次 API 调用为 65%，因为 agent 可以自主发现并纠正错误。

### AWS CodePipeline 集成

该 pipeline 统筹从代码提交到发布文档与 Knowledge Base 摄取的整个工作流：

```
version: 0.2

env:
  variables:
    SOURCE_BUCKET: "amzn-s3-demo-source-bucket1"
    DOCS_BUCKET: "amzn-s3-demo-source-bucket2"
    VECTOR_STORE_BUCKET: "amzn-s3-demo-destination-bucket"
    AGENT_ID: "agentcore-uml-agent"
    PROJECT_NAME: "MyDotNetService"
    KB_ID: "architecture-diagrams-kb"
    DATA_SOURCE_ID: "architecture-diagrams-source"
    AWS_REGION: "us-east-1"

phases:
  install:
    runtime-versions:
      python: 3.11
    commands:
      - pip install boto3 awscli
  pre_build:
    commands:
      # Package source code
      - zip -r source_code.zip src/
      # Upload to S3 for agent access
      - aws s3 cp source_code.zip s3://${SOURCE_BUCKET}/source_code.zip
  build:
    commands:
      # Invoke AgentCore agent - generates SVG, Mermaid, and metadata JSON
      - |
        python invoke_agentcore.py \
          --agent-id ${AGENT_ID} \
          --project-name ${PROJECT_NAME} \
          --s3-bucket ${SOURCE_BUCKET} \
          --s3-key source_code.zip \
          --output-dir uml_output \
          --region ${AWS_REGION}
      # Verify expected output structure before publishing
      - |
        echo "Verifying output structure..."
        ls -R uml_output/
        test -d uml_output/svg && echo "SVG directory found"
        test -d uml_output/mermaid && echo "Mermaid directory found"
        test -d uml_output/metadata && echo "Metadata directory found"
  post_build:
    commands:
      # Sync each artifact type independently to preserve structure
      # Using --size-only to avoid unnecessary overwrites on unchanged files
      - aws s3 sync uml_output/svg/ s3://${DOCS_BUCKET}/svg/ --size-only
      - aws s3 sync uml_output/mermaid/ s3://${DOCS_BUCKET}/mermaid/ --size-only
      - aws s3 sync uml_output/metadata/ s3://${DOCS_BUCKET}/metadata/ --size-only
      # Wait for S3 eventual consistency before triggering ingestion
      - sleep 5
      # Trigger Amazon Bedrock Knowledge Bases ingestion after all files are uploaded
      - |
        python trigger_kb_sync.py \
          --knowledge-base-id ${KB_ID} \
          --data-source-id ${DATA_SOURCE_ID} \
          --region ${AWS_REGION}

artifacts:
  files:
    - uml_output/**/*
```

该 pipeline 使用 AWS CodeBuild 执行，提供具有所需依赖的一致环境。[AWS Identity and Access Management（IAM）](https://aws.amazon.com/iam/) 角色授予 pipeline 访问 AWS CodeCommit、调用 AgentCore、发布到 Amazon S3 以及触发 Amazon Bedrock Knowledge Bases 摄取的权限。在发布步骤之后，一个摄取作业会把更新后的产物摄取到知识库中，使语义搜索索引随每一次代码变更保持最新。

### 输出格式

该方案生成多种输出格式。SVG 图表提供高质量、可缩放的矢量图形。Mermaid 源文件提供可版本控制、可编辑的图表定义。元数据 JSON 文件为 Amazon Bedrock Knowledge Bases 的语义搜索层提供支撑，以支持用自然语言发现图表。

### 知识库配置与呈现层

该方案集成 Amazon Bedrock Knowledge Bases——全托管的 RAG 能力——作为语义检索层，把静态图表转变为可查询的知识系统，并与代码库保持同步。

对于每一张生成的图表，agent 还会创建一个配套的元数据文件，与 SVG、Mermaid 文件一起存放在 Architecture Diagrams 存储桶中。

```
{
  "diagram_type": "sequence",
  "title": "Message Publishing Flow",
  "description": "End-to-end message publishing sequence including connection establishment, channel creation, and broker confirmation.",
```

#### 知识库设置

该知识库配置了三个组件：

**数据源：** Amazon S3 的 Architecture Diagrams 存储桶，范围限定为 metadata/ 与 mermaid/ 前缀，只索引图表描述与源码定义等语义丰富的内容，而不索引原始 SVG 二进制数据。

**Embedding 模型：** Amazon Titan Text Embeddings v2 生成 1,024 维向量，每块最多支持 8,192 token，为图表内容提供高质量的语义表示。

**向量存储：** Amazon S3 作为向量存储后端，无需单独的向量数据库，与该方案的无服务器思路一致。

**分块策略：** 采用层级分块，1,500 token 的父块用于承载图表的完整上下文，300 token 的子块用于实体级的细粒度检索。借助这一策略，知识库可根据查询返回完整的图表描述，或返回围绕某个具体实体的聚焦回答。

#### 查询知识库

摄取完成后，开发者可以通过 Amazon Bedrock 控制台、Amazon Bedrock AgentCore，或使用 RetrieveAndGenerate API 的自定义应用，以自然语言查询知识库。例如，查询「系统采用什么重连策略？」会给出带有指数退避描述的活动图。

知识库在每次 pipeline 运行时刷新，使结果与代码库的变更保持同步。

- 创建 Amazon CloudWatch Logs。
- [AWS Cloud Development Kit（AWS CDK）](https://aws.amazon.com/cdk/) bootstrap 命令：`cdk bootstrap aws://ACCOUNT_ID/us-east-1`。

**技术能力**（300–400 级别要求）：

- **.NET 代码库：** 需要熟悉标准 .NET 项目结构与常见编码模式。
- **CI/CD pipeline：** 需要对自动化构建与部署 pipeline 有基本理解（最好是 AWS CodePipeline）。
- **AWS CDK：** 需要有使用 AWS CDK 以基础设施即代码方式部署的经验。
- **架构可视化：** 需要能够自如地解读技术图表与架构模式。

**仓库结构**：该方案最适合遵循标准 .NET 项目约定的代码库：源代码位于 `src/` 目录，生产代码与测试代码清晰分离。

### 部署步骤

前置条件就绪后，按以下步骤部署端到端 pipeline。每一步都建立在前一步之上，因此请按顺序完成。

- 部署 AgentCore agent：使用 AgentCore CLI 打包 agent 代码并部署到 AWS。  `# Package the agent agentcore package \ --agent-name architecture-diagram-agent \ --entry-point agent/main.py \ --requirements requirements.txt \ --output-dir ./build # Deploy the agent to AgentCore agentcore deploy \ --agent-name architecture-diagram-agent \ --package ./build/agent.zip \ --role-arn arn:aws:iam::<ACCOUNT_ID>:role/AgentCoreExecutionRole \ --region us-east-1`
- 创建 AWS CodePipeline：配置一条包含来源、构建与部署阶段的 pipeline，并与你的 AWS CodeCommit 仓库连接。  `# Create the CodeCommit repository (if not already created) aws codecommit create-repository \ --repository-name architecture-diagram-repo \ --repository-description "Source repo for architecture diagram pipeline" # Create the CodePipeline (using a JSON input file) aws codepipeline create-pipeline --cli-input-json file://pipeline-definition.json # The pipeline-definition.json should define Source (CodeCommit), # Build (CodeBuild), and Deploy (S3) stages. For the full JSON # structure, see the AWS CodePipeline documentation.`
- 配置 Amazon S3 存储桶：为源代码暂存与文档托管创建存储桶，并设置合适的生命周期策略。  `# Create the source code staging bucket aws s3api create-bucket \ --bucket amzn-s3-demo-source-bucket1 \ --region us-east-1 # Create the documentation/diagrams hosting bucket aws s3api create-bucket \ --bucket amzn-s3-demo-source-bucket2 \ --region us-east-1 # Enable versioning aws s3api put-bucket-versioning \ --bucket amzn-s3-demo-source-bucket1 \ --versioning-configuration Status=Enabled # Add lifecycle policy to expire old versions after 90 days aws s3api put-bucket-lifecycle-configuration \ --bucket amzn-s3-demo-source-bucket1 \ --lifecycle-configuration '{ "Rules": [{ "ID": "ExpireOldVersions", "Status": "Enabled", "NoncurrentVersionExpiration": {"NoncurrentDays": 90}, "Filter": {"Prefix": ""} }] }'`
- 创建 Amazon Bedrock Knowledge Bases：把 Amazon S3 的 Architecture Diagrams 存储桶配置为数据源（范围限定为 metadata/ 与 mermaid/ 前缀），Amazon Titan Text Embeddings v2 作为 embedding 模型，Amazon S3 作为向量存储。设置层级分块：1,500 token 的父块与 300 token 的子块。  `# Create the Knowledge Base aws bedrock-agent create-knowledge-base \ --name architecture-diagrams-kb \ --role-arn arn:aws:iam::<ACCOUNT_ID>:role/BedrockKnowledgeBaseRole \ --knowledge-base-configuration '{ "type": "VECTOR", "vectorKnowledgeBaseConfiguration": { "embeddingModelArn": "arn:aws:bedrock:us-east-1::foundation-model/amazon.titan-embed-text-v2:0" } }' \ --storage-configuration '{ "type": "S3", "s3Configuration": { "bucketArn": "arn:aws:s3:::amzn-s3-demo-source-bucket1-<ACCOUNT_ID>" } }' # Create the data source with hierarchical chunking aws bedrock-agent create-data-source \ --knowledge-base-id <KNOWLEDGE_BASE_ID> \ --name diagrams-s3-source \ --data-source-configuration '{ "type": "S3", "s3Configuration": { "bucketArn": "arn:aws:s3:::amzn-s3-demo-source-bucket1-<ACCOUNT_ID>", "inclusionPrefixes": ["metadata/", "mermaid/"] } }' \ --vector-ingestion-configuration '{ "chunkingConfiguration": { "chunkingStrategy": "HIERARCHICAL", "hierarchicalChunkingConfiguration": { "levelConfigurations": [ {"maxTokens": 1500}, {"maxTokens": 300} ], "overlapTokens": 60 } } }'`
- 设置监控：为 pipeline 失败与 AgentCore 调用错误配置 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 告警。  `# Create an SNS topic for alerts aws sns create-topic --name pipeline-alerts # Subscribe your email to the alerts topic aws sns subscribe \ --topic-arn arn:aws:sns:us-east-1:<ACCOUNT_ID>:pipeline-alerts \ --protocol email \ --notification-endpoint your-team@example.com # CloudWatch alarm for pipeline execution failures aws cloudwatch put-metric-alarm \ --alarm-name pipeline-execution-failure \ --namespace AWS/CodePipeline \ --metric-name PipelineExecutionFailure \ --dimensions Name=PipelineName,Value=architecture-diagram-pipeline \ --statistic Sum --period 300 --threshold 1 \ --comparison-operator GreaterThanOrEqualToThreshold \ --evaluation-periods 1 \ --alarm-actions arn:aws:sns:us-east-1:<ACCOUNT_ID>:pipeline-alerts # CloudWatch alarm for AgentCore invocation errors aws cloudwatch put-metric-alarm \ --alarm-name agentcore-invocation-errors \ --namespace AWS/BedrockAgentCore \ --metric-name InvocationErrors \ --dimensions Name=AgentName,Value=architecture-diagram-agent \ --statistic Sum --period 300 --threshold 5 \ --comparison-operator GreaterThanOrEqualToThreshold \ --evaluation-periods 1 \ --alarm-actions arn:aws:sns:us-east-1:<ACCOUNT_ID>:pipeline-alerts`
- 测试 pipeline：在启用自动触发之前，先手动触发一次执行，以验证端到端功能，包括 Knowledge Base 摄取与查询结果。  `# Trigger a manual pipeline execution aws codepipeline start-pipeline-execution \ --name architecture-diagram-pipeline # Check pipeline execution status aws codepipeline get-pipeline-execution \ --pipeline-name architecture-diagram-pipeline \ --pipeline-execution-id <EXECUTION_ID> # Trigger Knowledge Base ingestion aws bedrock-agent start-ingestion-job \ --knowledge-base-id <KNOWLEDGE_BASE_ID> \ --data-source-id <DATA_SOURCE_ID> # Check ingestion job status aws bedrock-agent get-ingestion-job \ --knowledge-base-id <KNOWLEDGE_BASE_ID> \ --data-source-id <DATA_SOURCE_ID> \ --ingestion-job-id <INGESTION_JOB_ID> # Test a query against the Knowledge Base aws bedrock-agent-runtime retrieve \ --knowledge-base-id <KNOWLEDGE_BASE_ID> \ --retrieval-query '{"text": "What reconnection strategy does the system use?"}'`
- 清理：为避免产生持续费用，在不再需要时删除本次实践创建的资源：  `# Delete Codepipeline aws codepipeline delete-pipeline --name architecture-diagram-pipeline # Delete CodeBuild Project aws codebuild delete-project --name architecture-diagram-build # Delete the Amazon Bedrock knowledge base and data source: aws bedrock-agent delete-data-source \ --knowledge-base-id <KNOWLEDGE_BASE_ID> \ --data-source-id <DATA_SOURCE_ID> aws bedrock-agent delete-knowledge-base \ --knowledge-base-id <KNOWLEDGE_BASE_ID> # Empty and delete the Amazon S3 buckets: aws s3 rm s3://amzn-s3-demo-source-bucket1 --recursive aws s3api delete-bucket --bucket amzn-s3-demo-source-bucket1 aws s3 rm s3://amzn-s3-demo-source-bucket2 --recursive aws s3api delete-bucket --bucket amzn-s3-demo-source-bucket2 # Delete the AgentCore agent: agentcore delete --agent-name architecture-diagram-agent --region us-east-1 # Delete the CloudWatch alarms and SNS topics: aws cloudwatch delete-alarms \ --alarm-names pipeline-execution-failure agentcore-invocation-errors aws sns delete-topic \ --topic-arn arn:aws:sns:us-east-1:<ACCOUNT_ID>:pipeline-alerts`

## 真实用例

Amazon Bedrock Knowledge Bases 可加速开发者上手、支持安全的遗留系统现代化、支撑可供审计的合规，并通过把静态图表转变为可搜索的自然语言查询来提升可发现性。它还促进围绕微服务的跨团队协作，并通过生成的图表把系统复杂度与依赖关系可视化，帮助识别技术债。

对一家全球跨交易商经纪商而言，该方案每周为 20 个仓库与服务生成七类图表，为其电子交易平台维护当前的架构文档。这支撑了合规审计、开发者上手，以及围绕实时交易流的服务依赖的跨团队可见性。

## 收益

该方案自 2025 年 12 月起在一家大型金融服务公司投入生产；该公司是 AWS 的战略客户，运营 20 个仓库，每周生成 140 多张架构图，且零手工开销。

基于六个月持续生产使用的内部度量，可量化的业务影响相当可观。交付时间从 10 天压缩到 3 天。消息吞吐量翻倍，平均恢复时间缩短 20%。生产事故减少 30%。审计准备与架构决策记录过去需要 2 周的工作量，现在 2 天即可完成。开发者上手周期从 4 周加速到 1 周。

过去每个仓库要花 2 到 4 小时的文档工作，现在只需 5 分钟。这种 agentic 方式相比单次 API 调用节省 40% 成本；横跨 AgentCore、Amazon S3 与 Amazon Bedrock Knowledge Bases 的无服务器架构可在无需管理基础设施的情况下自动扩展到整个资产范围。

这不是概念验证。它是一个大规模、多 agent 的生产系统，解决的是一个真实且反复出现的客户问题：在企业规模上维护完整、可搜索且始终最新的架构文档。

## 结论

用 AgentCore 与 AWS CodePipeline 自动化架构文档，把手工、耗时的流程转变为顺畅且可扩展的工作流。这种 agentic 方式通过自我纠正带来可靠性，通过聚焦的模型交互带来成本效率，并通过无服务器设计带来基础设施独立性。Amazon Bedrock Knowledge Bases 通过让生成的文档可被自然语言立即发现，进一步延伸了这一价值：架构知识不仅是最新的，而且对每一位相关方都可访问。

一家全球跨交易商经纪商今天已把这一方案用于生产，每周在 20 个仓库上生成 140 多张图，且零手工开销，把过去每周数小时的任务变成了自动化、可查询的知识系统。采用该方案后，团队无需传统开销即可维护完整、最新且可搜索的架构文档，从而支撑更快上手、合规就绪与更明智的架构决策。
