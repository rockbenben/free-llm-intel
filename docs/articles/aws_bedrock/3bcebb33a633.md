# AvioBook 如何借助 Amazon Bedrock AgentCore 从运行数据中构建过站周转洞察

*本文由 AvioBook（Thales 集团旗下公司）产品经理 Petra Lafond 与 Tech Lead Maarten Cardinaels 共同撰写。*

航空公司的运行依赖紧密且层层级联的时刻表，能否访问运行数据则决定了它们能否守住这份时刻表。在过站周转（turnaround）期间，某一个登机口几分钟的延误，就可能波及其他一整天的中转衔接。航空公司的成败正取决于此：从飞机落地到下一次起飞之间的这段时间。[登机口损失的时间](https://www.iata.org/en/iata-repository/publications/economic-reports/air-traffic-control-delays-in-europe/) 单是这一项，每分钟就让航空公司损失约 20 美元。燃油消耗、机组成本、登机口费用、错失的中转，以及对当天剩余时刻表的连锁影响，都会叠加在这笔账上。对一家每天执飞 200 个航班、且过站周转是起飞环节硬性约束的中型航空公司来说，把平均过站周转缩短 2 分钟，每月约值 240,000 美元。

[AvioBook](https://www.thalesgroup.com/en/solutions-catalogue/civil-aviation/aviobook-suite) 是 [Thales](https://www.thalesgroup.com/en) 集团旗下公司，为航班运行与地面运行构建软件。其通信平台 [AvioBook Connect](https://aviobook.aero/products/connect) 自 2018 年起在航空公司投入服务，当前的 API 平台于 2025 年上线。飞行机组、客舱机组、签派与站点运行团队正是在这里协同完成过站周转。AvioBook Connect 以 flightroom 为单位组织工作，每个航班一个实时聊天室。在每个房间里，平台的 API 会向参与者通知飞机变更、延误、新飞行计划、登机进度，以及航空公司选择配置的其他任何内容。AvioBook Connect 既保留这些自动消息背后的 *硬* 数据，也保留围绕它们的 *软* 的对话数据。机组消息完全在该航空公司自己的数据环境内处理，由其自行掌控。

把这些数据收集起来只是一半的工作。一个满是带时间戳事件与消息的 flightroom 仍只是一份档案：有人索取时才有用，而其价值取决于对方有多大耐心去翻查数周的历史、并手动与延误代码交叉比对。把这份档案变成人们当下就能用的东西，是另一个挑战。

这正是 AvioBook 构思 Connected Analytics 的起点，随后它在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上做了原型验证——后者是一个 agentic 平台，可用任意框架与基础模型，安全地大规模构建、部署与运营高效的 agent。它架设在 AvioBook Connect 的数据之上，设计目标是让航空公司经理与运行控制中心签派员用自然语言提问，而不必自己去翻档案。两个 agent（每个角色一个）负责挖掘：拉取相关航班事件，与 flightroom 中实际记录的内容比对，然后给出直接答案以及支撑该答案的证据。

本文介绍 AvioBook Connected Analytics 旨在解决的那个运行难题，概述 AvioBook 在 AWS 上用 Amazon Bedrock AgentCore 验证过的多 agent 概念验证架构，并分享 AvioBook Connect 客户已经在把过站周转数据用起来之后看到的成果。

## 挑战：数据很丰富，但只有被追问时才作答

AvioBook Connect 把每个航班组织成一个 flightroom。在那里记录的每一次过站周转都会留下持久、带时间戳的记录，涵盖通过 Connect 的 API 推送的自动事件（如飞机变更、延误、新飞行计划与登机进度），以及运行团队围绕这些事件交换的消息。

但收集数据与使用数据并不是一回事，这个差距以三种反复出现的方式显现出来。

**运行实际上是个黑箱。** 同一次过站周转上的团队很少共享一致的实时图景，对同一次延误的描述也常常各不相同。事后审计时，记录只存在于口口相传之中，机组得回忆数周前执行的那个航班上事件的先后顺序。机组的叙述与纸质流程能否经得起审查，则是另一个问题——航空公司可能难以回答。

**延误代码只讲了一半故事。** 编码是在时间压力下完成的，通常由一个人做，并且主要归因于主导性延误。即便允许填多个代码，导致主导延误的上游事件也常常根本没有被编码。一个延误代码可以按规则填得完全正确，却仍然误导人们对实际发生了什么的理解。由于延误代码会同时进入内部与外部报告，一个把某个代码标为错误的系统就不只是分析脚注，而是航空公司的合规问题。

**答案需要一个航司可能并不具备的数据团队。** 超出短时间窗口的历史数据并不易于访问，每个问题都意味着一次手动查询或一次数据提取请求。在利润微薄的情况下，很少有航空公司承担得起专职分析团队来做这项工作。

在航空公司内部，这类分析工作通常落到两个需求不同的具体角色身上：

**负责准点率（OTP）的航空公司经理**需要知道延误为何发生、地面流程是否被遵循，以及审计提问时如何解释。他们处理历史数据与长期走势，会问这样的问题：*“航班 X 可能的延误来源有哪些？”*、*“最常见的非天气类延误来源是什么？”*、*“流程 X 的规程是否在被遵循？”*

**运行控制中心（OCC）签派员**承担着同一问题在网络层面的版本：一个登机口正在累积的延误，可能蔓延到一整天的中转衔接。他们处理实时数据，需要在扰动刚开始时就看到它，并理解其全机队范围的影响。他们会问这样的问题：*“X 机场的扰动会带来哪些下游影响？”*、*“目前有载客超过 250 人且处于风险中的航班吗？”*、*“今天执飞且风险价值（VaR）指数最高的航班是哪些？”*

两个角色需要的都是一个快速、人类可读、基于证据的答案，同时留有深入追查的空间，以及一种检验某个延误代码是否站得住的方式——它不是自动裁决，而是航空公司经理可以有信心据以行动的决策支持。这正是 AvioBook Connected Analytics 旨在弥合的差距。

## 方法：构建在 Amazon Bedrock AgentCore 上的多 agent 架构

AvioBook Connected Analytics 旨在提供两种能力：与运行数据的自然语言对话，以及 agentic 的延误代码校验。它不是单一的通用助手，而是运行两个面向特定角色的 agent。面向航空公司经理的 agent 负责历史分析与延误代码校验。面向 OCC 签派员的 agent 负责实时运行查询与扰动影响分析。每个 agent 都限定在自己的角色范围内，因此用户只会与为其角色授权的 agent 交互。

Amazon Bedrock AgentCore 提供了托管的基础，让你无需从零搭建 agent 基础设施就能部署与编排这些 agent。这些 agent 运行在 [AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 上，那是 Amazon Bedrock AgentCore 的一项能力，为部署 AI agent 与 Model Context Protocol（MCP）服务器提供全托管的计算环境。它们使用 [AgentCore memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html)，那是 Amazon Bedrock AgentCore 的一项能力，让 AI agent 能够记住过往交互，并在用户会话之间保持对话上下文。工具访问通过 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 代理，那是 Amazon Bedrock AgentCore 的一项能力，为 agentic 流量提供单一、安全的入口。AgentCore Gateway 暴露 MCP target，从而为 agent 提供一致、受治理的方式来调用访问 AvioBook 数据的函数。

AgentCore runtime 配置为使用 JSON Web Token（JWT）做入站身份验证。在 AvioBook Connect 前端，[Amazon API Gateway](https://aws.amazon.com/api-gateway/) 配置为以 [AWS Lambda](https://aws.amazon.com/lambda/) 函数为目标。该 Lambda 函数在请求头中携带有效的 JWT 访问令牌来调用 runtime，runtime 在 agent 运行前会校验该令牌。令牌携带用户身份，因此每个请求都与某个具体的航空公司账户和某个 AWS 区域绑定。这一身份验证与范围界定本身值得单列出来讲。agent 回答的每个问题都绑定到一家航空公司的身份与一家航空公司的数据，而这正是评估这类工具的航空公司安全与 IT 团队想看到的。

下面这些编号步骤描摹了从用户提问到答案的路径：

- AvioBook Connect 用户（航空公司经理或 OCC 签派员）用自然语言提问，经 Amazon API Gateway 的 [WebSocket API](https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-websocket-api.html) 进入。
- WebSocket API 中的 Lambda Authorizer 函数依据 [Amazon Cognito](https://aws.amazon.com/pm/cognito) 校验请求的 JWT，由 Cognito 为每个请求签发 JWT。
- 通过验证的请求触发一个 AWS Lambda 目标，后者在 AgentCore runtime 上调用相应的 agent。
- 该 agent 在 AgentCore memory 中更新会话上下文。
- 该 agent 通过 AgentCore Gateway 使用 MCP 调用工具。
- 网关调用相应的工具函数，该函数实现为 AWS Lambda 函数。
- 工具函数向 [Amazon Athena](https://aws.amazon.com/athena/) 发出相关的数据查询。
- Amazon Athena 从 [AWS Glue Data Catalog](https://docs.aws.amazon.com/glue/latest/dg/catalog-and-crawler.html) 解析表 schema，并扫描 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/) 桶中按航空公司分区的 Parquet 数据。
- 在后台，一个 AWS Glue crawler 与抽取、转换、加载（ETL）作业把传入的 JSON 转换为 Amazon S3 中的 Parquet，并在 Glue Data Catalog 中注册 schema，使数据保持可查询状态。
- 有依据的答案沿同一条路径返回给用户，并附带其背后的支撑证据。

延误代码校验复用同一条数据访问路径。agent 把记录的延误代码与底层事件的序列做比较，并暴露出代码看起来不一致、或本该适用多个代码的情形，其定位是供航空公司经理审阅的第二意见，而不是自动更正。由于延误代码会进入合规报告，agent 的角色是支持这一判断，而不是替人做判断。

## 设计决策与考量

决意构建在 Amazon Bedrock AgentCore 之上，是经过一段研究之后做出的：AvioBook 在确定方向之前，评估了它在 agent 编排、会话管理与工具访问方面的多种选择。这项研究指向 AgentCore runtime、AgentCore memory 与 AgentCore Gateway，把它们视为团队无需自行构建的托管积木。随后与 AWS 进行了集中一周的共同开发，让团队搭起一个多 agent 概念验证并确认了方案：架构、数据访问模式与 agent 设计。能如此迅速地验证概念，正是 AvioBook 有底气把 Connected Analytics 产品化、交付给航空公司客户的原因——而且这个基础可以继续扩展新的 agent 与数据源，无需重新架构。

有几个设计选择值得单独说明。按角色构建不同的 agent，使每个 agent 的范围保持狭窄、工具保持相关，行为因而比单一的全能助手更容易推理。通过 AgentCore Gateway 把数据访问暴露为 MCP 工具，使 agent 与数据层解耦，因此之后新增工具与数据源无需重构 agent。把数据保存在 Amazon S3 中并使用 Athena 与 Glue Data Catalog，意味着这个概念验证可以建立在 AvioBook 已在使用的同一套 AWS 数据服务之上，而不必另建一套分析栈。

由于 agent 的建议会为运行决策提供依据，负责任 AI 实践从一开始就被纳入设计，作为要带入生产的控制措施。每个答案都以 agent 检索到的运行数据为依据，证据与回答一并呈现，因此用户可以把结论追溯回底层事件，而不是凭空相信。agent 的输出被当作航空公司经理或 OCC 签派员的起点，而不是自动执行的动作：由人来审阅建议，并对运行决策保持负责。Connected Analytics 还处在飞机经认证、与适航性绑定的系统之外：它是咨询性软件，旨在为做决定的人提供信息，而不是自行行动。

## 结果与业务影响

AvioBook Connect 的运行成果构成了 Connected Analytics 所要依托的基线。在单个夏季航季里，一家欧洲中型航空公司避免了超过 4,000 小时的延误，其中 124 小时直接来自减少了 Connect 所替代的电话沟通与手动来回确认。

Connected Analytics 旨在进一步放大这份收益。为签派员提供一个支持思考过程、而不仅是更快答案的工具，才是带来额外节省的关键：围绕空中交通容量限制做改航决策，需要态势感知以及几分钟不被打断的时间，而当一个人正在打电话追状态更新时，这两者都很稀缺。

在一个保守的示例基线上——每天 200 个航班、登机口损失时间按每分钟约 20 美元计——平均过站周转缩短两分钟，每月约值 240,000 美元，与前面的估算一致。随着流程合规性变得更稳定，还可再回收 2 到 4 分钟，对同一家航空公司而言每月最高约值 495,000 美元，此外还有把不正常运行处理得更好所带来的收益。

## 接下来

AvioBook Connected Analytics 旨在提供两种能力：针对 Connect 运行数据的自然语言问答，以及依据底层事件校验延误代码。同一套基础也开出了自然的向前路径。

AvioBook 正在研究的一个方向是主动异常告警。与其由用户索取洞察，不如由他们定义自己关心的条件——例如某个流程运行过久、某个站点正在形成延误模式，或某个航班的特征值得关注——然后由 agent 监视传入数据，并在匹配发生时立即呈现。这把 AvioBook Connected Analytics 的角色从“回答问题”扩展为“在任何人想到要问之前提出正确的问题”。由于数据已经可以通过 AgentCore Gateway 中的模块化工具访问，告警可以复用查询 agent 所依赖的同一数据层，而不需要单独的 pipeline。

模块化设计也为新增面向新角色的 agent、以及连接新数据源留出了空间，随着航空公司把更多过站周转活动推进 Connect，这些都能建立在今天已经运行的东西之上。

## 结论

过站周转一直在决定航空公司的时刻表完整性，而在此之前，它是航空公司运行中最不透明、最隐蔽的部分之一。AvioBook Connect 把事件数据与围绕它的对话汇集到一处。在 Amazon Bedrock AgentCore 上做出原型的 Connected Analytics，旨在把同一份数据变成航空公司经理与签派员能够直接追问的东西：是什么延误了某个航班、某个流程是否真的被遵循、某个机场的扰动对其余网络意味着什么。

这一切都不取代运行过站周转的人的判断。AvioBook 构建它是为了给他们一个更快、更可靠的起点，并为这份判断的价值积累越来越多的证据——而这个基础，AvioBook 已经在朝着“在任何人不得不提问之前就捕捉到值得处理的问题”的方向扩展。
