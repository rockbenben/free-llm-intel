# 在 AWS 上以现代化的 data mesh 策略构建 agentic AI 应用

当客服 agent 自主查询订单数据库、检索退货政策并综合出答案时，它需要在你的组织内以受治理的方式访问多个数据源。在现代化 data mesh 上构建 agentic AI 应用，要求在数据交互链的每一层都实施细粒度访问控制。那些能自主发现数据库 schema、构造 SQL 查询并综合多个数据源的 AI agent，会暴露出为检索增强生成（RAG）而设计的单点管控模型无法应对的治理缺口。组织需要的控制措施要覆盖从工具发现、查询执行一直到响应综合的全过程。

在早前的一篇文章[《用 AWS 无服务器数据湖构建安全的 RAG 应用》](https://aws.amazon.com/blogs/machine-learning/build-secure-rag-applications-with-aws-serverless-data-lakes/)中，我们展示了如何通过使用业务域与安全分级等元数据过滤向量搜索结果，对 RAG 实施细粒度访问控制（FGAC）。那种做法之所以有效，是因为 RAG 的数据交互很简单：从预先构建的向量索引中检索文本块、按元数据过滤，然后呈现结果。

本文展示如何在 AWS 上构建一个受治理、无服务器的 data mesh，为生产级 agentic AI 提供所需的安全、可扩展的数据基础。该架构在原有方案基础上做了三项关键改动：

- 用 [Amazon S3 Vectors](https://aws.amazon.com/s3/features/vectors/) 取代 Amazon OpenSearch Serverless 来承载成本优化的知识库；在中等查询频率的工作负载下，相比专用向量数据库方案，它可将向量存储与查询成本降低最多 90%。
- 用 [Amazon S3 Tables](https://aws.amazon.com/s3/features/tables/)（内置 Apache Iceberg 支持）取代通用的 Amazon Simple Storage Service（Amazon S3），并由 [AWS Lake Formation](https://aws.amazon.com/lake-formation/) 治理；相比自管理的 Iceberg 表，每秒事务数最高提升 10 倍，并具备行、列与单元格级的细粒度安全控制。
- 通过 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 把 data mesh 以 Model Context Protocol（MCP）工具的形式对外暴露，并用由 AWS Lambda 支撑的 interceptor 在每个 agent 到工具的调用上实施确定性的访问控制。

## 前提条件

要实施这套架构，你需要具备以下条件：

- 一个具有管理员访问权限的 [AWS 账户](https://aws.amazon.com/premiumsupport/knowledge-center/create-and-activate-aws-account/)。
- 具备创建角色、策略、Lambda 函数、S3 Tables 表存储桶、Amazon Athena 工作组与 Lake Formation 配置的 [AWS Identity and Access Management（IAM）](https://docs.aws.amazon.com/IAM/latest/UserGuide/introduction.html) 权限。
- 熟悉 [AWS Lake Formation](https://docs.aws.amazon.com/lake-formation/latest/dg/what-is-lake-formation.html) 的概念（数据湖管理员、LF-Tag、数据过滤器）。
- 一个已启用 [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html) 并配置好模型访问权限的账户。
- 已在你账户中配置好 [Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-agentcore.html) 访问权限。
- 已安装并配置 [AWS Command Line Interface（AWS CLI）](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html) v2。

- Agent Layer —— 客户与 AgentCore Runtime 交互，后者是一个安全、无服务器的托管环境，在相互隔离的 microVM 环境中以会话隔离的方式部署 agent。agent 运行在 LangGraph 框架内，通过 MCPClient 类与 MCP 工具集成。
- Gateway Layer —— Gateway 包含一个执行 JSON Web Token（JWT）校验与 scope 强制的请求 interceptor，一个负责工具过滤、数据脱敏与审计日志的响应 interceptor，以及带 Bedrock Guardrails 的 AgentCore Policy，后者会实时评估每次工具调用的输入与输出，检查 prompt injection、有害内容与敏感信息泄露。
- Tools Layer —— 四个由 Lambda 支撑的 MCP 工具（`get_user_tables`、`get_schema`、`run_query` 与 `kb_search`）提供受治理的数据访问。
- Governed Data Mesh —— 注册在 [AWS Glue Data Catalog](https://docs.aws.amazon.com/glue/latest/dg/catalog-and-crawler.html)（s3tablescatalog）中的 S3 Tables（Iceberg）、带工作组成本控制的 Amazon Athena、执行行/列/单元格级安全的 Lake Formation，以及为 Amazon Bedrock Knowledge Bases 提供向量能力的 S3 Vectors。

## 为什么 agentic AI 需要新的治理模型

RAG 架构在单一检查点实施治理：经元数据过滤的向量检索。这种做法很好地服务了 RAG 工作负载。agentic 模式引入了更多步骤，形成一条多步链条，其中每一步都需要各自的授权决策。在 RAG 中，系统在检索时用元数据过滤器查询一个预先构建的向量索引。在 agentic AI 中，系统要发现存在哪些表、理解 schema、构造 SQL、从向量存储中检索，然后综合结果。

位于单一检索边界的元数据过滤器无法治理这条五步链条。向量数据库会定期同步权限，这意味着权限撤销不会立即生效。当 agent 正在自主操作数据时，这是不可接受的缺口。角色层级、基于属性的访问、行级过滤器这类复杂的身份权限，无法表达为向量文本块上直白的元数据键值对。

这些局限促使我们转向受治理的 data mesh 架构，在每一个数据访问层以原生方式实施授权。

## 构建受治理的无服务器 data mesh

[data mesh](https://aws.amazon.com/what-is/data-mesh/) 把数据所有权下放给各领域团队，同时集中治理与可发现性。在 AWS 上，领域团队端到端地拥有自己的数据产品，AWS Glue Data Catalog 提供集中的元数据发现，而 [Lake Formation](https://docs.aws.amazon.com/lake-formation/latest/dg/what-is-lake-formation.html) 以授权/撤销语义在数据库、表、列、行与单元格各级实施权限。

每个生产者领域都位于自己的 AWS 账户中。生产者在中央治理账户中注册数据产品，该账户是一个专门承载整个组织权威 AWS Glue Data Catalog 与 Lake Formation 权限策略的 AWS 账户。数据通过 [Lake Formation 跨账户共享](https://docs.aws.amazon.com/lake-formation/latest/dg/cross-account-permissions.html) 共享。数据不会被复制，只有元数据通过使用者目录中的资源链接进行关联。查询时，Lake Formation 校验权限并向查询引擎签发临时凭证。[基于标签的访问控制（LF-TBAC）](https://docs.aws.amazon.com/lake-formation/latest/dg/tag-based-access-control.html) 让这种模式得以动态扩展。管理员为资源分配 `classification=PII` 或 `department=customer_service` 这类 LF-Tag，并基于这些标签授予权限。

下面几小节介绍我们如何实现这个 mesh 的两个数据层。首先介绍用于结构化数据（订单记录、客户档案）、由 Lake Formation 行与列安全治理的事务型 Iceberg 表。然后介绍用于非结构化知识（政策、FAQ）、为语义搜索提供支持的向量存储。

### 用 Apache Iceberg 的 S3 Tables 承载事务型数据

对本文的客服 agent 而言，Order Management 领域团队使用 [Amazon S3 Tables](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-tables.html) 发布订单与客户数据。S3 Tables 是首个内置 Apache Iceberg 支持的云对象存储，相比通用 S3 存储桶上自管理的 Iceberg 表，每秒事务数最高提升 10 倍。它会自动处理 compaction、快照管理以及无引用文件清理。

S3 Tables 与 [Amazon SageMaker Lakehouse](https://docs.aws.amazon.com/sagemaker-lakehouse-architecture/latest/userguide/what-is-smlh.html) 集成，后者会填充 AWS Glue Data Catalog，并通过 Lake Formation 联合访问。三个数据产品（`customer_orders`、`customer_profiles` 与 `interaction_history`）可从 Amazon Athena 查询、受 Lake Formation 权限治理，并由 S3 Tables 自动 compaction。

Lake Formation 的[数据过滤器](https://docs.aws.amazon.com/lake-formation/latest/dg/data-filtering.html) 实施行级安全，使 agent 只能访问属于已认证客户的记录。对 `customer_orders` 施加行过滤表达式 `customer_id = :customer_id` 的数据过滤器后，无论 agent 如何构造 SQL，每个查询都会被限制在当前客户的记录范围内。`run_query` Lambda 函数在向 Athena 提交查询之前，会把已认证客户的身份作为会话参数注入。列级安全则把 `payment_method`、`billing_address` 这类敏感字段完全从查询结果中隐藏。

### 用 Amazon S3 Vectors 构建知识库

只有结构化数据还不够。客户需要从非结构化知识（产品手册、退货政策、常见问题（FAQ）与故障排查指南）中获得答案，而这需要语义搜索能力。

[Amazon S3 Vectors](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors.html) 以完全无服务器的服务形态提供原生向量存储与查询支持。它支持每个索引最多 20 亿个向量，并提供强写一致性，也就是说新增的向量可立即被查询到。

### S3 Vectors 的成本优势

使用 [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html) 知识库功能的客户可以选择 S3 Vectors 作为向量存储；在中等查询频率的工作负载下，相比专用向量数据库方案可将成本降低最多 90%。对于需要个位数毫秒延迟的高每秒查询数（QPS）工作负载，Amazon OpenSearch Serverless 仍是更合适的选择。对于超出 S3 Vectors 性能画像的工作负载，AWS 提供从 S3 Vectors 到 Amazon OpenSearch Serverless collection 的一步式导出。

S3 Vectors 支持[可过滤元数据](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-metadata-filtering.html)（字符串、数字、布尔与列表类型，支持 `$eq`、`$ne`、`$gt`、`$in`、`$and`、`$or` 等运算符），也支持不可过滤元数据，用于随结果返回的较大上下文数据。在我们的用例中，文档会带上 `product_category`、`document_type` 这类可过滤元数据键，从而支持有针对性的语义搜索。下面的示例展示了一个只检索电子产品退货政策的元数据过滤器：

```
{"$and": [{"product_category": {"$eq": "electronics"}}, {"document_type": {"$eq": "return_policy"}}]}
```

## 通过 AgentCore Gateway 暴露 data mesh

受治理的 data mesh 与知识库就位之后，下一个挑战是以安全、可发现且标准化的方式把这些能力暴露给 AI agent。本节介绍实现这一目标的工具、interceptor 与身份传播模式。

[AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 提供了一个集中层，用于管理 AI agent 如何连接工具。它把身份验证、可观测性与策略执行整合到单一端点中。Gateway 通过协议转换、入站 OAuth 授权与出站凭证管理，把 Lambda 函数、API 与现有 MCP server 转换为 MCP 兼容的工具。agent 通过带 OAuth Bearer token 的流式 HTTP 传输连接。

### 四个核心数据工具

四个由 Lambda 支撑的 MCP 工具通过 Gateway 提供受治理的数据访问。`get_user_tables` 查询经 Lake Formation 权限过滤的 AWS Glue Data Catalog，返回已授权的表。`get_schema` 检索指定表的列名、类型与描述。`run_query` 依据只读白名单校验 SQL、为行级过滤注入客户身份，并通过 Athena 执行，同时施加字节扫描成本上限。`kb_search` 针对 Amazon Bedrock 中的 Knowledge Bases 执行带元数据过滤的语义搜索。

随着 Amazon Bedrock Managed Knowledge Base 的发布，知识库现在可以作为 AgentCore Gateway 中原生的预构建 target 类型使用。这意味着你无需自定义 Lambda 函数即可通过 Gateway 暴露知识库——Gateway 会自动生成 IAM 角色、提供内置的可观测性与评估指标，并通过 AgentCore Policy 执行策略。在本架构中，我们使用自定义的 `Lambda-backed kb_search` 工具，演示 Gateway interceptor 如何在工具调用边界实施细粒度授权与元数据过滤。对于不需要自定义 interceptor 逻辑的生产工作负载，原生 Managed KB target 类型可以完全省掉 Lambda 函数，从而降低运维开销，同时保留 MCP 兼容性与 AgentCore Policy 执行。

下面的 JSON 展示了 `run_query` 的工具 schema 注册。

```
{
  "name": "run_query",
  "description": "Executes a read-only SQL query against governed Iceberg tables via Amazon Athena with byte-scan limits and Lake Formation row-level security.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "sql": {"type": "string", "description": "A read-only SQL SELECT statement."},
      "database": {"type": "string", "description": "The Glue Data Catalog database name."}
    },
    "required": ["sql", "database"]
  }
}
```

部署 MCP 工具与 interceptor：

- 克隆 AgentCore Gateway interceptor 示例仓库。
- 对每个 Lambda 函数（`get_user_tables`、`get_schema`、`run_query`、`kb_search`、请求 interceptor、响应 interceptor），使用 AWS CLI 创建函数：  `aws lambda create-function --function-name get_user_tables \ --runtime python3.12 --handler lambda_function.lambda_handler \ --role arn:aws:iam::ACCOUNT_ID:role/mcp-tool-role \ --zip-file fileb://function.zip`
- 把仓库 policies/ 目录中定义的 IAM 策略附加到每个函数的执行角色。
- 在 AgentCore Gateway 中把 Lambda 函数注册为 MCP 工具 target。操作说明见 Registering tool targets。
- 把请求与响应 interceptor 附加到 gateway。操作说明见 [AgentCore Gateway interceptor 示例](https://github.com/awslabs/agentcore-samples)。

注意：四个 MCP 工具与两个 interceptor 的完整 Lambda 函数源代码、IAM 策略与部署说明，见 [AgentCore Gateway interceptor 示例](https://github.com/awslabs/agentcore-samples)。

### 用 interceptor 实现确定性的访问控制

[AgentCore Gateway interceptor](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-interceptors.html) 是自定义 Lambda 函数，在请求-响应生命周期的两个阶段实施授权。interceptor 充当中间件，检查、转换或阻断流经 Gateway 的请求与响应。请求 interceptor 在 Gateway 调用目标 Lambda 之前执行，响应 interceptor 在目标返回之后、结果送达调用方之前执行。

interceptor 模式在每个阶段解决不同的安全问题：

| **模式** | **解决的问题** | **如何实现** |
| --- | --- | --- |
| 基于 JWT scope 的工具调用控制 | 未授权的工具访问 | 请求 interceptor 解码 JWT 的 scope 声明，并阻断未授权的 `tools/call` 调用 |
| 动态工具过滤 | 工具发现泄漏 | 响应 interceptor 依据每个用户的 scope，从 `tools/list` 中移除未授权的工具 |
| 代为操作的身份传播 | 权限提升 / [混淆代理](https://docs.aws.amazon.com/IAM/latest/UserGuide/confused-deputy.html) | 每一跳都收到单独的、权限收窄的 token（例如 Order 工具只拿到 `order:read`；KB 工具只拿到 `kb:search`） |

授权检查被有意做得极简：

```
def check_tool_authorization(scopes, tool, target):
    if target in scopes:
        return True
    return f"{target}:{tool}" in scopes
```

对于动态工具过滤，响应 interceptor 会过滤 `tools/list` 的响应：

```
def lambda_handler(event, context):
    gateway_response = event['mcp']['gatewayResponse']
    auth_header = gateway_response['headers'].get('Authorization', '')
    token = auth_header.replace('Bearer ', '')
    claims = decode_jwt_payload(token)
    scopes = claims.get('scope', '').split()
    tools = gateway_response['body']['result'].get('tools', [])
    filtered_tools = [t for t in tools if check_tool_authorization(
        scopes, t['name'].split('___')[1], t['name'].split('___')[0])]
    return {
        "interceptorOutputVersion": "1.0",
        "mcp": {
            "transformedGatewayResponse": {
                "statusCode": 200,
                "headers": {"Authorization": auth_header},
                "body": {"result": {"tools": filtered_tools}}
            }
        }
    }
```

对于代为操作的 token，每个 token 都包含一个 `Act: Agent` 字段，从而建立清晰的责任链。未授权的下游工具无法复用权限过大的 token 去访问其它工具。

Gateway interceptor 在模型看到或执行工具之前，就在工具调用边界确定性地实施授权。不过，agent 对 SQL 的构造仍取决于模型行为。Athena 的字节扫描上限、只读 IAM 策略与 Lake Formation 行过滤器作为补偿性控制，限定了模型可能生成的不合格查询的影响范围。

## agent 请求流程：客服场景实战

贯穿本文，我们用一个客服场景演示这套架构的实际运作。一位客户联系支持并问道：“我的订单 #12345 到哪了？我上周买的耳机还能退吗？”该 agent 需要从受治理的 Iceberg 表中查询订单状态、从向量知识库中检索退货政策，并在遵守成本护栏与监管约束的前提下综合出完整回答。行级安全至关重要，因为 `customer_orders` 表中的每一行都代表某个特定客户的订单。如果没有行级过滤，代表客户 A 行动的 agent 就可能无意间访问客户 B 的订单历史、配送详情或购买模式。

以下步骤按下图所示，追踪贯穿每个治理层的完整交互过程：

![请求流程图展示从工具发现到响应综合的六个步骤，并在每个治理层实施授权](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/16/ML-20469-2.png)

- Tool Discovery —— agent 调用 Gateway 的 `tools/list` 端点。响应 interceptor 依据客服代表的 JWT scope 过滤工具列表，返回四个已授权的工具。
- Table Discovery —— 接下来调用 `get_user_tables`。请求 interceptor 校验 JWT 并确认 `order:read` scope。Lambda 返回三个表：`customer_orders`、`customer_profiles` 与 `interaction_history`。
- Schema Discovery —— 对 `customer_orders` 调用 `get_schema`，返回列 `order_id`、status、`ship_date`、`estimated_delivery` 与 `product_name`。Lake Formation 的列级安全排除了 `payment_method` 与 `billing_address`，使这些列对 agent 不可见。
- Query Execution —— 构造出的查询 SELECT `order_id`, status, `ship_date`, `estimated_delivery` FROM `customer_orders` WHERE `order_id` = ‘12345’ 通过 `run_query` 提交，后者注入已认证客户的身份以解析 Lake Formation 行过滤器。Athena 工作组执行 `BytesScannedCutoffPerQuery` 上限（例如 100 MB），只读 IAM 策略拒绝会修改数据的 AWS Glue 操作。结果是：订单 #12345 已于 3 月 20 日发货，预计 3 月 25 日送达。
- Knowledge Base Retrieval —— 同时，`kb_search` 以查询“return policy for electronics”和元数据过滤器 {“`product_category`”: {“$eq”: “electronics”}} 运行。返回的政策写道：“电子产品可在购买后 30 天内以原包装退货并全额退款。”
- Response Synthesis —— 最终回答合并了两部分结果：“你的订单 #12345 已于 3 月 20 日发货，预计 3 月 25 日送达。关于耳机，我们的电子产品退货政策允许在购买后 30 天内以原包装退货。我可以为你发起退货。需要我继续吗？”

每一步的授权都在不同层次执行：第 1–2 步用 Gateway interceptor，第 3–4 步用 Lake Formation，第 4 步用 Athena 工作组限额，第 5 步用 S3 Vectors 元数据过滤。这种纵深防御做法降低了单一控制失效就泄漏未授权数据的风险。

## 查询治理与安全护栏

对于自主构造 SQL 的 agent，稳健的治理必不可少。本节介绍五个相互重叠的防护层，它们共同约束 agent 能查询什么、能扫描多少数据，以及哪些信息会到达模型。

第一层是 Athena 工作组成本控制。每个 agent 查询都在一个配置了 `BytesScannedCutoffPerQuery` 上限的专用 [Athena 工作组](https://docs.aws.amazon.com/athena/latest/ug/workgroups-create-update-delete.html) 中执行。如果查询超过该阈值，Athena 会自动取消它。`EnforceWorkGroupConfiguration` 设置有助于防止 agent 绕过这些限制。按工作组汇总的数据用量告警会在总扫描数据超过阈值时触发 Amazon Simple Notification Service（Amazon SNS）通知。

第二层是通过只读 IAM 策略阻止数据定义语言（DDL）操作。Lambda 执行角色带有显式拒绝，禁止修改 Glue Data Catalog 的操作（`glue:CreateTable`、`glue:DeleteTable`、`glue:UpdateTable` 以及分区级的对应操作）。Lake Formation 还额外加了一道 DDL 关卡：除非显式授予相应权限，否则主体无法创建数据库或表。

第三层是 Lake Formation 的细粒度访问。五个粒度层级（数据库、表、列、行与单元格）的安全策略在 Amazon Athena、Amazon Redshift Spectrum、AWS Glue 抽取、转换与加载（ETL）以及 Amazon EMR 上原生实施，且不额外收费。更多信息见 [Lake Formation 数据过滤](https://docs.aws.amazon.com/lake-formation/latest/dg/data-filtering.html)。

第四层是 Gateway interceptor。请求 interceptor 在工具执行前实施基于 JWT scope 的授权。响应 interceptor 过滤工具列表，并从查询结果中脱敏敏感数据。

第五层是通过 Gateway 处 AgentCore Policy 执行的 [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) Guardrails。Guardrails 不再只在模型推理边界施加内容安全控制，而是直接集成进 AgentCore Policy Engine，在那里实时评估每个已授权的 agent 动作的输入与输出，以及每一次对 gateway target（包括工具、agent 与模型）的调用。这意味着 prompt injection 攻击、有害内容与敏感信息泄露会在到达下游系统之前就被检测并阻断，而不仅仅是在模型返回的路上被抓住。Policy Engine 在 gateway 层确定性地执行这些护栏，与前文描述的基于 interceptor 的访问控制并行，形成同时覆盖授权与内容安全的统一执行点。对于需要额外模型层控制的工作负载，仍可在模型推理边界施加 Amazon Bedrock Guardrails 作为补充防护。

**为什么对 agentic 工作负载而言，Gateway 级护栏更可取**

在传统 RAG 架构中，只在模型推理边界施加护栏就够了，因为数据交互遵循单一的“先检索、再生成”模式。模型是唯一负责综合信息的组件，所以过滤它的输出就能抓住所有策略违规。然而在 agentic 架构中，agent 会在生成任何模型响应之前自主调用多个工具、构造查询，并跨多个环节综合结果。只评估最终模型输出的护栏无法阻止恶意或被操纵的输入到达某个工具调用——例如，工具响应中嵌入的 prompt injection 可能在模型给出最终答案之前就影响后续的工具调用。通过在 Gateway 处经由 AgentCore Policy 实施护栏，每一次 agent 到工具的交互都会实时被评估，从而在行动发生处、而不仅仅在输出处提供防护。

**与替代方案的权衡**

只在模型推理处施加护栏带来了简单性：单一集成点，无需改动工具基础设施。然而对 agentic 模式而言，这种做法留下三处缺口。第一，它造成时间上的盲区——有害内容可能在到达模型输出边界之前就已通过中间工具调用传播。第二，它无法执行工具专属策略（例如，对 run_query 工具阻断某些查询模式，而对 kb_search 放行）。第三，它完全依赖模型的配合才能把工具输出呈现出来以供评估，而这在多步推理链中并无保证。基于 Gateway 的做法在工具调用边界评估每个请求与响应，从而消除这些缺口，实现按工具定制策略、实时阻断工具输入中的 prompt injection，以及与模型行为无关的确定性执行。

没有任何单一层能独自负责。纵深防御跨越从网络到应用再到模型的不同层次，其设计目的就是帮助防止单一控制失效时泄漏未授权数据。

- AgentCore Gateway —— 删除 gateway 及其已注册的 target。操作说明见[删除 gateway](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_DeleteGateway.html)。
- Amazon Athena 工作组 —— 删除专用的 agent 工作组（这不会删除存储在 S3 中的查询结果）。操作说明见[删除工作组](https://docs.aws.amazon.com/athena/latest/ug/deleting-workgroups.html)。
- Amazon S3 Tables 表存储桶 —— 警告：这会永久删除 Iceberg 表中的所有数据（客户订单、档案、交互历史）。请删除包含这些 Iceberg 表的表存储桶。操作说明见[删除表存储桶](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-tables-buckets-delete.html)。
- Amazon S3 Vectors 索引 —— 这会永久删除所有知识库内容（产品手册、政策、FAQ）。请删除向量索引及其关联的 S3 存储桶。操作说明见[删除向量索引](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-index-delete.html)。
- Amazon Bedrock Knowledge Bases —— 删除知识库配置。操作说明见[删除知识库](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-delete.html)。
- Lake Formation 权限 —— 撤销 Lake Formation 授权。操作说明见[撤销权限](https://docs.aws.amazon.com/lake-formation/latest/APIReference/API_RevokePermissions.html)。
- Lake Formation 数据过滤器 —— 移除为行级安全创建的数据过滤器。操作说明见[管理数据过滤器](https://docs.aws.amazon.com/lake-formation/latest/dg/managing-filters.html)。
- AWS Glue Data Catalog —— 删除 s3tablescatalog 数据库、已注册的表，以及为跨账户共享创建的任何资源链接。操作说明见[删除数据库与表](https://docs.aws.amazon.com/athena/latest/ug/drop-database.html)。
- IAM 角色与策略 —— 删除为本架构创建的执行角色与策略。操作说明见[删除 IAM 角色](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_manage_delete.html)。

## 结论

从 RAG 转向 agentic AI 扩大了治理面。RAG 只需一个经元数据过滤的检索检查点。agentic AI 引入了自主的 schema 发现、SQL 构造、多源综合与工具调用，每一项都需要各自的授权控制。本文演示了如何用 AWS 上受治理的 data mesh 应对这一扩大的治理面：以 Amazon S3 Tables 承载事务型存储并配合 Lake Formation 安全、以 Amazon S3 Vectors 提供成本优化的语义搜索、以 AgentCore Gateway interceptor 实现确定性的工具级授权、以 Athena 工作组控制查询成本，并以 Amazon Bedrock Guardrails 在模型推理处保障内容安全。这些层次共同支撑生产部署，尤其适用于合规上要求在每一个数据访问决策点都做到纵深防御的高监管行业。
