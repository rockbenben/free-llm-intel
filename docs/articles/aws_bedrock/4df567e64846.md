# 在 Amazon SageMaker HyperPod Inference 上管理 NVIDIA Dynamo

高效地服务大型语言模型 (LLM) 需要足够的 GPU 内存以及仔细协调提示处理和令牌生成。例如，在考虑 KV 缓存和运行时开销之前，GLM-5.3 的 FP8 权重超过单个 `ml.p5.48xlarge` 实例上的 640 GB GPU 内存。当两者共享相同的 GPU 时，长提示也会减慢令牌生成速度。

Amazon SageMaker HyperPod Inference 现在支持 [NVIDIA Dynamo](https://github.com/ai-dynamo/dynamo)，将 Dynamo 的分布式推理功能与 HyperPod 的基础设施管理相结合来应对这些挑战。 Dynamo 是一个开源分布式推理框架，支持多节点部署、分解预填充和解码以及使用 vLLM、SGLang 和 TensorRT-LLM 等引擎的 KV 感知路由。 HyperPod 通过高性能 Elastic Fabric Adapter (EFA) 网络、协调的 GPU 调度以及节点运行状况监控和恢复来支持这些部署。在这篇文章中，我们通过部署示例说明多节点和分类服务，分享基准测试结果，并概述优化 HyperPod 推理的最佳实践。

## 集成如何运作

HyperPod Inference 附加组件安装 Dynamo 自定义资源定义以及这些服务和调度组件：

- *HyperPod Inference Operator *通过 InferenceEndpointConfig (IEC) 自定义资源管理端点部署。其 `dynamoSpec` 部分提供 Dynamo 配置。
- *Dynamo 运算符 *管理 [DynamoGraphDeployment (DGD)](https://docs.nvidia.com/dynamo/dev/kubernetes/model-deployment/deploy-with-dgd) 中定义的资源，包括前端、模型工作线程、副本计数和资源需求。
- *[Grove](https://github.com/ai-dynamo/grove) *协调相关的 pod 组，包括多节点工作线程及其扩展关系。
- *[Kubernetes AI (KAI) Scheduler](https://github.com/kai-scheduler/KAI-Scheduler) *将 Pod 放置在 GPU 资源上，使用群组调度将多节点工作所需的 Pod 一起调度。

AWS 深度学习容器 (DLC) 提供 Dynamo 运行时，而该插件则管理集成组件版本。要采用受支持的 Dynamo 版本，请更新该附加组件。

### 部署架构

下图显示了 SageMaker HyperPod 上分类推理的部署路径、服务组件和基础设施管理。 Dynamo 前端将请求路由到预填充工作人员（处理提示）和解码工作人员（生成令牌）。这些单独的池允许独立的扩展和调整。两个池都加载完整的模型权重，并且 KV 缓存通过 EFA 在它们之间传输。

Dynamo 还支持聚合服务，其中预填充和解码在同一工作线程中运行。在任一拓扑中，工作线程都可以在一个实例上运行，也可以使用张量和管道并行性跨多个实例。 Dynamo 的 [KV 感知路由器](https://docs.nvidia.com/dynamo/dev/knowledge-base/concepts/system-architecture/kv-aware-routing) 考虑了两种拓扑中可重用的前缀 KV 缓存和活动工作负载。前缀重用可以减少提示重新计算并缩短第一个令牌的时间，而负载感知有助于避免工作人员过载。有关 Dynamo 架构的更多详细信息，请参阅[Dynamo 知识库概述](https://docs.nvidia.com/dynamo/knowledge-base/overview)。

HyperPod 提供节点、GPU 和 EFA 运行状况监控并管理节点更换，同时编排组件重新创建受影响的工作线程。通过 InferenceEndpointConfig 和 `dynamoSpec` 配置的部署支持通过 SageMaker 端点进行调用。

## 配置部署的两种方法

无论您是 HyperPod 新手、Dynamo 新手，还是两者兼而有之，该附加组件都提供了两种部署路径来适合您的工作流程：

*自带 DynamoGraphDeployment (DGD)* 允许现有 Dynamo 用户继续使用上游文档、配方和清单，并由 Dynamo 操作员管理部署。要将现有 DGD 引入 HyperPod，请使用受支持的容器映像并为集群配置存储、网络和 Pod 放置。

*InferenceEndpointConfig 与 dynamoSpec* 允许现有 HyperPod Inference 用户使用他们已知的相同配置格式和 OpenAI 兼容接口部署新的 Dynamo 端点。对于推理引擎，您可以选择vLLM、SGLang或TensorRT-LLM，默认使用vLLM。该操作员还提供 KV 感知路由和副本计数的默认值。

两种路径都支持单实例和多节点部署。无论哪种情况，HyperPod 都会管理节点的运行状况和更换。该表总结了每条路径的职责。

|  | **自带 DGD** | **InferenceEndpointConfig 与 dynamoSpec** |
| --- | --- | --- |
|你写|完整的 DGD 清单 | IEC 包含 dynamoSpec |
|最适合 |希望直接控制服务图或重用现有 DGD 的团队 |希望通过 IEC 设置托管端点的团队 |
|模型重量 |您可以配置下载或安装权重 |操作员从 Amazon Simple Storage Service (Amazon S3) 或 Amazon FSx 暂存权重 |
|端点、TLS、注册 |您配置和管理这些资源|通过 HyperPod Inference Operator 进行管理 |
|自动缩放|您配置和管理扩展 |通过 `autoScalingSpec` 进行聚合和分解部署的 Kubernetes 事件驱动自动扩展 (KEDA) |

## 部署示例：GLM-5.3

以下摘录在 `ml.p5.48xlarge` 实例上使用带有 vLLM 的 InferenceEndpointConfig (IEC) 部署路径。 Dynamo 特定设置属于 `spec.dynamoSpec`。模型源和端点设置包含在完整的清单中。

### 多节点聚合服务

此配置跨两个实例（16 个 GPU）运行一个模型工作线程副本，并使用两个前端副本进行请求处理。将 `dynamoSpec.frontend.routingMode` 设置为 `kv-aware` 会打开 KV 感知路由。
```
spec:
  replicas: 1
  dynamoSpec:
    modelServer: vllm
    frontend:
      replicas: 2
      routingMode: kv-aware
    aggregation:
      nodesPerReplica: 2
      tensorParallelism: 16
```
在这里，`spec.replicas` 控制模型工作人员副本的数量，而 `frontend.replicas` 控制前端副本的数量。

### 多节点分解服务

将 `spec.dynamoSpec` 下的 `aggregation` 替换为以下 `disaggregation` 块，保持前面的前端配置。预填充和解码的副本计数是单独设置的。此示例运行一个预填充副本和两个解码副本，每个副本跨越两个实例，总共六个实例。
```
disaggregation:
  prefill:
    nodesPerReplica: 2
    tensorParallelism: 16
    replicas: 1
  decode:
    nodesPerReplica: 2
    tensorParallelism: 16
    replicas: 2
```
### 应用部署

使用 `kubectl apply` 应用完整的清单。 HyperPod Inference Operator 使工作人员可以使用配置的模型权重并生成 DGD。 Grove 和 KAI Scheduler 协调放置，以便将每个多节点工作线程所需的 Pod 一起调度。

SageMaker 端点准备就绪并配置为完成聊天后，客户端可以通过 SageMaker 运行时 API 发送与 OpenAI 兼容的请求负载：
```
aws sagemaker-runtime invoke-endpoint \
--endpoint-name glm53 \
--content-type application/json \
--body '{"model":"zai-org/GLM-5.3","messages":[{"role":"user","content":"Hello"}],"max_tokens":128}' \
--cli-binary-format raw-in-base64-out \
out.json
```
## 基准测试

我们在 SageMaker HyperPod 上对两种模型的 Dynamo 进行了基准测试，以比较服务配置。

### Qwen3-235B 的分解预填充和解码

我们使用 [AIPerf](https://github.com/ai-dynamo/aiperf) 在两个 p5en.48xlarge 实例（16 个 H200 GPU）上使用 Dynamo 和 TensorRT-LLM 来比较 `Qwen3-235B-A22B-FP8` 的聚合和分解服务。请求包含 4,000 个输入令牌和 200 个输出令牌。我们保留了满足两个目标的测量点：第一个令牌的 P90 时间低于一秒，以及每个用户每秒至少 50 个令牌的中位生成速度。其中，分类服务实现了最高聚合吞吐量的 2.05 倍：每个 GPU 每秒分别输出 207 个和 101 个令牌，并发数分别为 80 和 32。

![Qwen3-235B 的吞吐量比较：每 GPU 每秒 207 个输出令牌的分解服务与每秒 101 个输出令牌的聚合](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/14/ML-22230-2.png)

图 2：Qwen3-235B-A22B-FP8 的聚合服务吞吐量与分解服务吞吐量的比较

### Qwen3.5-397B多节点聚合服务

对于超出单个实例 GPU 内存的模型，Dynamo 支持以聚合和分解模式提供多节点服务。为了评估跨节点的工作器，我们使用 AIPerf 对带有 Dynamo 和 vLLM 的 Qwen3.5-397B-A17B-FP8 的多节点聚合服务进行基准测试，使用 TP4 × PP2 和八个活动 H200 GPU。该模型适合一个实例，因此实际上您不会拆分它。它在这里用作受控基线。我们使用相同的模型、并行性和工作负载配置，将一个 p5en.48xlarge 上的 8 个 GPU 与两个实例中每个实例上的 4 个 GPU 进行了比较。通过在并发数为 32 时具有高前缀重用的代理工作负载，双节点配置为每个 GPU 每秒提供 126.4 个输出令牌，保留了 99.1% 的单节点吞吐量。这表明 SageMaker HyperPod 上的 Dynamo 可以为需要多个跨节点实例的模型提供服务。节点边界本身不会造成显着的吞吐量损失。

![Qwen3.5-397B 的吞吐量比较：双节点服务，每 GPU 每秒 126.4 个输出令牌，单节点吞吐量的 99.1%](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/14/ML-22230-3.png)

## 优化推理的最佳实践

NVIDIA Dynamo 提供配方和工具来帮助您选择服务配置、基准性能并调整 SageMaker HyperPod 上的部署。

- **从匹配的配方开始 –** 为您的模型、推理引擎和 GPU 类型选择 [Dynamo 配方](https://docs.nvidia.com/dynamo/dev/recipes/browse)。在调整工作线程大小时考虑模型权重、KV 缓存和运行时内存。对于受支持的配置，[AISimulate](https://github.com/ai-dynamo/aisimulate) 可以在 GPU 上进行测试之前帮助比较聚合和分解服务、选择并行性以及预填充和解码工作池的大小。
- **在基准测试之前验证通信 –** 对于跨实例的部署，确认通信使用预期的 EFA 传输，包括预填充和解码工作器之间的 KV 缓存传输。请参阅 [Dynamo EFA 指南](https://docs.nvidia.com/dynamo/dev/kubernetes/installation/rdma-setup/efa-on-aws)。
- **对代表性流量进行基准测试 –** 使用 [AIPerf](https://docs.nvidia.com/aiperf/welcome-to-ai-perf-documentation) 重播您的流量，或使用具有代表性提示长度、输出长度和前缀重用的 [生成的代理跟踪](https://github.com/ai-dynamo/aiperf/blob/main/docs/tutorials/agentic-code-generator.md)。清除每个配置的并发性，保留满足 SLA 的点，并根据成本和延迟优先级进行选择。
- **根据测得的瓶颈进行调整 –** 在引擎设置之前调整拓扑和工作分配，一次更改一个变量。遵循[性能调优指南](https://docs.nvidia.com/dynamo/dev/kubernetes/operations/performance-tuning)，或使用[Dynamo优化代理技能](https://docs.nvidia.com/dynamo/dev/agent-skills/optimization)协助进行基准测试和调优。验证目标 HyperPod 部署上的每个候选者。

## 结论

SageMaker HyperPod Inference 上的 NVIDIA Dynamo 通过多节点服务、分解预填充和解码以及 KV 感知路由，简化了大型模型的部署和操作。托管附加组件安装服务组件，默认配置简化了端点设置。 HyperPod 管理模型权重、根据 GPU 和推理指标自动扩展集群、监控节点运行状况并替换故障节点。这些功能共同减少了无差异的基础设施工作，因此团队可以专注于他们的模型和应用程序。开始使用链接存储库中的设置说明并完成部署示例。
