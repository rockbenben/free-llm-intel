# 使用 Amazon Bedrock 和 AWS HealthLake 构建 agentic AI 医疗理赔 pipeline

在医疗行业，手工处理纸质表单仍然是一项可观的成本。尽管在扫描文档与图像的数据提取方面已有进展，通常仍然需要人工监督。填表人造成的录入错误，或数字化过程中置信度较低的提取结果，依然必须得到纠正。

在本文中，我们展示如何使用 Amazon Bedrock 的两项关键能力构建一条自动化理赔处理 pipeline：[Amazon Bedrock Data Automation](https://aws.amazon.com/bedrock/bda/) 用于从医疗理赔表单中进行智能文档提取，[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 用于托管一个 AI agent，由它校验提取出的数据并将其转换为 [AWS HealthLake](https://aws.amazon.com/healthlake/) 中的 FHIR（Fast Healthcare Interoperable Resources）资源。你将了解如何组合这些服务，构建一套端到端的 workflow，在通过自动校验检查保持准确性的同时减少人工处理。

## 解决方案概览

该解决方案演示了一套使用 AI 驱动服务处理医疗理赔表单的自动化 workflow。当医疗服务提供方将 CMS-1500 理赔表单（PDF 格式）上传到 Amazon Simple Storage Service（Amazon S3）桶时，会触发一条以 [AWS Lambda](https://aws.amazon.com/pm/lambda/) 开始的处理 pipeline，它执行三项主要功能：

- Amazon Bedrock Data Automation 使用智能文档处理从表单中提取结构化数据。
- 一个使用 [Strands Agents](https://strandsagents.com/) 的 AI agent 运行在 Amazon Bedrock AgentCore 上，它会将这些数据与 AWS HealthLake 中已有的患者和提供方记录进行校验，检查完整性与一致性。
- 如果所有校验都通过，agent 会在 HealthLake 中创建标准化的 FHIR 理赔资源。它还会为理赔处理人员生成一份技术摘要，并为患者生成一份通俗易懂的理赔状态说明。两者都以 Amazon Simple Notification Service（Amazon SNS）[通知](https://aws.amazon.com/sns/)的形式发出。

这套自动化 workflow 有助于缩短人工处理时间，同时通过 AI 辅助的校验保持准确性。

*图 1：该解决方案的架构视图。*

上图展示了以下步骤：

- 提交者将理赔文档上传到 Amazon S3。
- 文件到达时触发 AWS Lambda。
- Amazon Bedrock Data Automation 从文档中提取信息，并以 JSON 格式输出结果。
- AWS Lambda 随后调用 AgentCore，并把文档传递过去进行处理。
- AgentCore 查询 AWS HealthLake、创建理赔，并生成一份摘要 JSON 响应。
- AWS Lambda 调用 Amazon SNS，投递错误响应或成功响应。

在 S3 中创建文档时，Lambda 被用作事件触发器，并充当 agentic workflow 之上的确定性监督者。它会校验每份文档都被处理，或被送入死信队列进行异常处理。

Bedrock Data Automation 简化了生成式 AI 的开发，并自动化涉及文档、图像、音频和视频的 workflow。在文档处理方面，Bedrock Data Automation 结合传统的光学字符识别（OCR）、机器学习（ML）模型和生成式 AI，以准确提取数据。你可以使用 Blueprint（artifact）来指定从文档中提取哪些数据以及如何提取。你可以使用预置模板，也可以构建针对自身用例定制的配置。输出包含所提取字段和表格的置信度分数与边界框数据。这里的自定义输出为 CMS-1500 理赔表单在各类格式变体下生成可预测的 JSON 表示。

AgentCore 托管 Strands agent。该 agent 使用两个工具与 HealthLake 交互：`create_fhir_claim` 和 `search_fhir_resources`。

该 agent 使用以下 workflow：

- 在 AWS HealthLake 中查找 Insured、Patient、Practitioner 和 Coverage 信息，用作理赔表单中的参考。首次尝试使用[直接方法调用](https://strandsagents.com/docs/user-guide/concepts/tools/#direct-method-calls)和默认搜索参数。在此之后，agent 会运行以下 prompt 来检查工具调用，并在必要时重新尝试搜索：
  识别 insured 资源，首先查看先前的工具调用。如果没有匹配项，再从理赔 JSON 中使用不同的搜索参数进行两次尝试以寻找匹配。重点关注置信度分数高的属性，并报告你是如何找到该匹配的。
- 如果找到这些参考，则创建理赔的 FHIR 表示，并将其发送到 AWS HealthLake。
- 创建一个 JSON 对象，记录已完成的工作。该对象包括理赔 ID（如果已创建）、给人工处理人员的响应，以及给患者的响应。处理人员响应充当告警或观察记录。当需要纠正错误时，患者响应会向提交者发出信号。

## 先决条件

在部署该解决方案之前，请确保你具备以下条件：

- 具有管理员权限的 AWS 账户。
- 在 Amazon Bedrock 上访问 Anthropic Claude Sonnet 4.6 的权限。更多细节请参阅[访问 Amazon Bedrock 基础模型](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)。
- NodeJS 24 或更高版本。
- Node Package Manager（npm）11.5 或更高版本。
- Python 3.13 或更高版本。
- AWS Cloud Development Kit（AWS CDK）2.1025 或更高版本。

## 部署解决方案

部署使用 AWS Cloud Development Kit（CDK）和 AgentCore 命令行界面，步骤如下：

- 克隆代码仓库：  `git clone https://github.com/aws-samples/sample-agenticidptohealthlake.git`
- 在代码仓库根目录运行以下命令：  `npm install python -m venv .venv source .venv/bin/activate pip install -r requirements.txt pip install -r requirements.txt --python-version 3.12 --platform manylinux2014_aarch64 --target ./packaging/_dependencies --only-binary=:all: cd agentcore agentcore configure --entrypoint claimsprocessor.py agentcore launch python ./bin/package_for_lambda.py npx cdk bootstrap npx cdk deploy`

## 订阅 SNS 主题以接收通知

- 访问 [Amazon SNS 控制台](https://console.aws.amazon.com/sns/)。
- 选择 **Topics**。
- 选择 **Agent-Notifications**。
- 选择 **Create subscription**。
- 对于 protocol，选择 **email**。
- 输入你的电子邮件地址。
- 选择 **Create subscription**。
- 打开电子邮件中确认通知里的链接，以确认你的订阅。

## 使用解决方案

以下各节将演练两种场景：失败场景和成功场景。

1. 失败场景：通过故意不加载 AWS HealthLake 中所需的某个参考资源来模拟失败。

项目代码中包含一个 `sampledata` 文件夹。使用 `load_sampledata.py` 装载一些数据，其中 `<data_store_id>` 是 `cdk deploy` 输出中的 `HealthLakeDatastoreArn`：

```
python load_sampledata.py <data_store_id> bda_output_insuredid_error.json Patient,Insured,Practitioner
```

将 `sample1_cms-1500-P.pdf` 上传到 S3 桶中名为 `/input` 的文件夹。我们故意不加载其中一个必需的资源。

这应会通过 SNS 生成类似如下的消息：

***我们无法处理你的理赔，因为我们在系统中找不到你的保险保障信息。请联系你的保险提供方，核实你在 AnyHealth Plus Medicare 计划下的保单号 G4683A，或致电我们的办公室更新你的保障信息。***

这模拟了 agent 如何识别问题，并针对理赔失败生成一段对用户友好的响应。

2. 成功场景：通过确保所需的 HealthLake 资源存在来模拟成功处理。在这个场景中，我们植入了一处数据不一致，让 agent 帮我们克服。在下面的示例数据中，Insured 的 ID 号已被改动。

在 HealthLake 中创建缺失的参考资源：

```
python load_sampledata.py <data_store_id> bda_output_insuredid_error.json Coverage
```

按前面的步骤重新处理该 PDF。你会通过 SNS 收到类似如下的消息：

*已成功处理患者 John Doe 的 CMS 1500 理赔表单，诊断为背痛 M54.9。患者通过出生日期（1960-10-10）识别。投保方 Jane Doe 因 ID 搜索失败而通过姓名搜索识别，失败原因是理赔 ID（11-2234-10190）与数据库 ID（11-2234-1019O）不一致——最后一个字符不同。Jane Smith 医生通过 ID 123456 被确认为转诊医师。保障已依据 AnyHealth Plus 签发的 Medicare 保单 G4683A 完成核验。该理赔包含 4 项操作：2005-10-15 的 CPT 97810（$170）、2005-10-20 的 CPT 73521（$120）、2005-10-30 的 CPT 98940（$250）以及 2005-10-30 的 CPT 97124（$120），合计 $660。*

这条消息可以向人工审核者传达一份可快速扫读的摘要，涵盖该笔成功理赔以及 agent 做出的任何其他观察。

## 最佳实践

**设计期的 AI 优于运行期的 AI。** 在这个解决方案中，编排逻辑是预先已知的。文档处理步骤是可预测的，对 HealthLake 的初始查询遵循一致的模式。由于这些需求在设计阶段就已明确，我们显式编码了逻辑，而不是依赖 Model Context Protocol（MCP）服务器在运行时推断操作顺序。结果是更可靠、更易维护的解决方案。为了构建它，我们使用了 Kiro——一个能把自然语言规格说明转成可运行代码的 agentic IDE。Kiro 在 Lambda 内生成对 Bedrock Data Automation 的 API 调用，并在 agent 内部构建工具。通过在设计阶段产出精确、有针对性的代码，而不是在运行时发出宽泛的探索性 prompt，Kiro 减少了对 Bedrock 的调用次数。这有助于降低运营成本并缩短开发生命周期。

**确定性地监督 agent。** 在这个架构中使用 S3 和 Lambda 是有意为之。该 agent 做两件基本的事：观察显式的工具调用，以及生成要载入 HealthLake 的 FHIR 资源。随后它向 Lambda 函数回报，由后者充当该笔理赔成功与否的最终裁决者。

## 成本

下面列出所用各项服务的成本考虑。

**注意：** 以下成本考虑基于发布之时的 AWS 定价，仅供参考。实际成本可能有所不同。有关最新定价，请参阅各服务的定价页面。

- [AgentCore Runtime](https://aws.amazon.com/bedrock/agentcore/pricing/) 按每 vCPU 小时 $0.0895、内存按每 GB 小时 $0.00945 计费，会形成每份文档的一项名义成本。
- Amazon Bedrock Data Automation 对于字段数不超过 30 个的 Blueprint，按每页 $0.04 计费，超过 30 个的每个额外字段 $0.0005。
- 使用 [Anthropic Claude Sonnet 3.7 V1](https://aws.amazon.com/bedrock/pricing/) 的 agent 的模型费用。在我们的测试文档中，token 约为 76 千输入和 6 千输出。按按需定价计算，即 $0.23/in 与 $0.09 out，合每份文档 $0.32。
- [AWS HealthLake](https://aws.amazon.com/healthlake/pricing/) 按每小时存储计费，前 10 GB 为每小时 $0.27。
- 在此架构中，[Lambda](https://aws.amazon.com/lambda/pricing/)、[S3](https://aws.amazon.com/s3/pricing/) 和 [SNS](https://aws.amazon.com/sns/pricing/) 的每份文档费用可以忽略不计。

## 结论

虽然生产环境的医疗理赔处理通常还涉及本方案之外的更多步骤，但这一模式展示了把 AI agent 集成到文档 workflow 中的威力。通过让 AI agent 直接访问处理工具，它能在多个方面提供有价值的洞察：识别潜在的理赔问题、指出需要人工审核的地方，以及生成对患者友好的状态消息。这种 AI 辅助的方法可以帮助理赔处理人员更高效地工作，并在保持准确性的同时缩短处理时间。前面的示例展示了一个很可能出现的场景：字母 *o* 与数字零之间的数据不一致。在这种情况下，agent 绕过了这处不一致，准确处理了该笔理赔。
