# Amazon SageMaker HyperPod 管理与治理最佳实践

[Amazon SageMaker HyperPod](https://aws.amazon.com/sagemaker/hyperpod/) 让机器学习（ML）团队能够使用大规模加速计算资源池来训练和 fine-tuning 模型。当多个团队共用一个集群时，技术搭建通常不难，真正有挑战性的是治理：你必须决定哪些团队可以使用该集群、每个团队获得多少容量、当一个团队的工作负载与另一个团队竞争时怎么办，以及当使用偏离策略时由谁负责。[Amazon SageMaker Unified Studio](https://aws.amazon.com/sagemaker/unified-studio/) 又带来另一层考虑：你可以把 SageMaker HyperPod 集群连接到项目，让团队成员从自己的项目工作区启动工作负载。这种便利很有价值，但在多个团队共享同一集群的可见性之后，管控「谁能做什么」的机制就变得更加重要。在本文中，我们展示如何通过 SageMaker Unified Studio 来管理 SageMaker HyperPod，同时保留底层的治理控制。我们覆盖四个控制层：组织（organization）、项目（project）、集群（cluster）与工作负载（workload），并说明如何在这四层之上设计身份、容量与可观测性策略。读完后，你将获得一个可复用的模型：在 ML 团队的项目上下文中提供经批准的 SageMaker HyperPod 计算资源，同时把集群运维保留在基础设施团队手中。

Amazon SageMaker HyperPod 是 [Amazon SageMaker AI](https://aws.amazon.com/sagemaker/ai/) 的一项能力。Amazon SageMaker Unified Studio 是数据与 AI 开发环境，团队在其中基于自己的数据和工具进行构建。借助 SageMaker Unified Studio，你可以把一个项目连接到现有的 SageMaker HyperPod 集群。成员随即可启动机器学习工作负载、查看集群和任务信息，并打开 JupyterLab 工作流。你继续通过 Amazon SageMaker AI 的界面和 API 管理集群。

这种职责分离为基础设施团队提供了一个实用的运行模式。你可以通过既有的云运维流程管理集群基础设施，同时在 ML 团队的项目上下文中呈现经批准的算力。在本文中，我们描述如何设计基础设施边界、管控访问、分配共享容量，并通过 SageMaker Unified Studio 一致地运行 SageMaker HyperPod。

## 理解管理边界

治理良好的环境会把组织管理、项目访问和集群运维分离开来。每一层回答不同的问题，并使用不同的控制手段。下表总结了各边界、其主要控制手段及管理用途。

| **边界** | **主要控制手段** | **管理用途** |
| --- | --- | --- |
| 组织 | SageMaker Unified Studio domains、domain units、关联账户、project profiles 与授权策略 | 决定谁可以创建项目、项目可以使用哪些账户和 Region、哪些工具可用 |
| 项目 | 项目成员、项目角色与 SageMaker HyperPod 连接 | 定义协作上下文以及项目成员可访问的 AWS 资源 |
| 集群 | SageMaker HyperPod 集群管理员角色、Amazon EKS access entries、基于角色的访问控制（RBAC）与 EKS Pod Identity，或 Slurm 控制 | 治理集群配置、调度器访问、namespaces、任务与基础设施运维 |
| 工作负载 | 计算分配、priority classes、借贷（lending and borrowing）策略与任务权限 | 控制谁可以提交作业，以及共享容量如何分配 |

把这些控制手段视为分层。SageMaker HyperPod 连接只是把一个经批准的集群加入项目，它并不取代该集群的 AWS Identity and Access Management（IAM）、Amazon Elastic Kubernetes Service（Amazon EKS）或 Slurm 控制。应当整体审视项目角色、连接访问角色、EKS access entries 与 RBAC 或 Slurm 控制、工作负载身份、数据与 [AWS Key Management Service（AWS KMS）密钥](https://aws.amazon.com/kms/)策略、网络策略、task-view 限制以及调度器策略，只有这些控制对齐之后才让集群可用。

这些控制构成四个层级，如下图所示。

图 1：四个控制层——组织、项目、集群与工作负载。每一层回答不同的问题并使用不同的控制手段，因此应在各自的边界上逐层审视。

SageMaker Unified Studio 的项目是协作边界，而不是强运行时安全边界。把 SageMaker HyperPod 集群、调度器和稀缺的加速器容量保留在一个指定的容量账户（capacity account）下。经批准的用户和数据集可以留在同一账户，也可以放在独立的消费账户或数据账户中。AWS 文档描述了 SageMaker HyperPod 任务治理在 Amazon EKS 集群上的多账户支持。尽管 On-Demand Capacity Reservations 可以跨账户共享，仍应将 SageMaker HyperPod 集群的所有权和容量管理集中到容量账户，使用经批准的跨账户访问方式，而不是让每个消费账户都成为独立的容量管理员。

- 对于 Amazon EKS，为每个租户使用独立 namespace，配合 RBAC、每租户的 service accounts 与 EKS Pod Identity 角色、default-deny network policies，以及租户专属的存储和 AWS KMS 权限。对于 Slurm，使用带层级账户与关联（associations）的 Slurm accounting、quality of service（QoS）、优先级与 fair-share 策略以及 partitions；同时使用操作系统级身份与文件权限、网络控制以及租户专属的数据路径。
- 使用 IAM 角色和资源策略（而不是仅凭项目成员身份）来控制对 Amazon Simple Storage Service（Amazon S3）buckets、AWS KMS 密钥、secrets、容器镜像仓库及其他数据服务的访问。项目与 domain-unit 策略则用于协作与委派。
- 对于 Amazon EKS 集群，使用 SageMaker HyperPod 任务治理——包括配额、priority classes、借贷与抢占（preemption）——来公平共享中央加速器池。对于 Slurm 集群，使用原生 partitions、quality of service（QoS）、优先级、fair-share 与抢占控制；Slurm 不提供同样的借贷模式。这些调度控制决定经授权的工作负载何时获得算力，并不授予 namespace 或数据访问权限。

若需要在集群内实现更强隔离，可在适当场合使用专属节点或节点组以及准入控制（admission controls）。当法律、监管或安全要求硬性规定基础设施隔离时，使用独立集群或独立账户。跨账户的消费访问可以保留账户级所有权，而无需复制中央 SageMaker HyperPod 集群。在容量账户内部，使用 [project profiles](https://docs.aws.amazon.com/sagemaker-unified-studio/latest/adminguide/custom.html) 和 [domain units](https://docs.aws.amazon.com/sagemaker-unified-studio/latest/adminguide/domain-units.html) 配合项目授权策略，来委派项目的创建与所有权。

## 判断 SageMaker Unified Studio 何时是合适的管理体验

借助 SageMaker Unified Studio，已经在项目中工作的机器学习团队可以沿一条经批准的路径使用共享的 SageMaker HyperPod 算力。成员可以找到已连接的集群、查看状态与元数据、检视受支持的任务与指标，并直接进入 JupyterLab 工作流，而不必再维护单独的基础设施清单。

这种体验并不取代集群管理。下表说明各角色应如何把 SageMaker Unified Studio 与面向具体服务的界面配合使用。

| **角色** | **用 SageMaker Unified Studio 做什么** | **继续使用专用工具做什么** |
| --- | --- | --- |
| Domain/基础设施管理员 | domain units、项目创建策略、project profiles、成员策略与账户放置 | 组织级控制、账户开通与基础设施自动化 |
| SageMaker HyperPod 集群管理员 | 呈现经批准的集群连接，查看集群、任务、设置与元数据视图 | 集群创建、更新、resiliency 配置、add-ons、EKS 或 Slurm 管理以及事故响应 |
| 项目所有者 | 管理项目成员，为用户提供商定的项目上下文以使用经批准的算力 | 提出基础设施变更请求，审批业务专属的访问需求 |
| ML 工程师或数据科学家 | 查找经批准的算力、查看工作负载状态、打开 JupyterLab 工作流 | 按需通过 SageMaker [HyperPod CLI](https://docs.aws.amazon.com/sagemaker/latest/dg/getting-started-hyperpod-training-deploying-models.html)、`kubectl` 或 Slurm 工具提交和管理细粒度工作负载 |

当项目成员、数据访问、开发工具和算力需要一个共同上下文时，使用 SageMaker Unified Studio。对于集群变更与可复用自动化，继续使用 SageMaker AI API、infrastructure as code 与编排工具。参考实现与集成请参阅 [AI on SageMaker HyperPod](https://awslabs.github.io/ai-on-sagemaker-hyperpod) 站点。

## 在连接集群之前先做基础设施决策

在批准一个连接之前，先书面明确容量账户、任何消费账户或数据账户、AWS Region、网络路径、身份、负责人、工作负载边界与隔离要求。如果你需要创建集群的指引，请参阅 [Amazon SageMaker HyperPod 文档](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-quickstart.html)或 [AI on SageMaker HyperPod 站点](https://awslabs.github.io/ai-on-sagemaker-hyperpod)。

将管理身份与工作负载身份分离。在创建项目和访问角色时，保留 SageMaker HyperPod 对集群管理员与数据科学家用户的区分。面向项目的角色不应仅因其用户运行工作负载就获得集群生命周期权限。受支持的权限模型请参阅 [SageMaker HyperPod 的 AWS Identity and Access Management](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-prerequisites-iam.html)。

把网络当作端到端控制来对待。将 Amazon EKS Kubernetes API endpoint 的访问限制在经批准的管理网络路径上，控制 pod 的 ingress 与 egress，并确认项目、连接角色、工作负载角色与集群网络只支持预期的数据路径。编排器专属配置请参阅[使用 Amazon EKS 编排 SageMaker HyperPod 集群](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks.html)。

例如，为 Amazon EKS API endpoint 配置私有访问，只允许来自经批准的管理员或工作负载子网的连接；应用 default-deny 的 Kubernetes `NetworkPolicy`，并显式放行所需的服务间通信与 egress 路径；在适当场景下为 Amazon S3、Amazon Elastic Container Registry（Amazon ECR）、Amazon CloudWatch 等服务使用 virtual private cloud（VPC）endpoints，并为每个租户配备专属的工作负载角色用于数据访问。

建立连接契约（connection contract）。连接契约是客户自管的治理记录，例如 wiki 页面、工单、service-catalog 记录，或记录在 infrastructure-as-code 仓库中的文件；它不是平台功能。为每一个经批准的项目到集群的连接记录以下信息：

- 业务负责人、运维负责人与成本负责人。
- SageMaker Unified Studio 的 domain unit 与项目。
- 集群所在账户、Region、名称与编排器。
- 项目角色以及连接所使用的访问角色 Amazon Resource Name（ARN）。
- 经批准的工作负载类型与数据分级。
- EKS namespaces 或 Slurm 访问范围。
- 调度策略与例外情况的负责人。
- 监控、支持与退役（decommissioning）的预期。

这份契约让评审者可以依据一条记录来评估并批准完整的访问路径。

## 治理身份与任务可见性

同时控制「操作」与「可见性」。任务名称、namespaces、资源请求与使用模式若配置不当，可能泄露其他团队的工作信息。

在项目成员与集群访问上尽量使用组（groups）而非逐个授权。在每个边界上分别审视每个角色，而不是创建一个横跨 domain、项目、集群与工作负载策略的宽泛角色。

下面的工作流展示如何把「用户能看到什么」与「用户能做什么」分离开。

图 4：治理身份与任务可见性。通过组来分配访问，把每个角色限定在其边界内，限制 task visibility，并把「看见工作」与「对工作采取行动」分离。

在为用户开通之前先审视默认的任务可见性。[SageMaker AI Studio 中的 SageMaker HyperPod 文档](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-studio-tabs.html)说明：默认情况下，SageMaker AI Studio 用户可以看见所有 Amazon EKS 集群任务；对于 Slurm 集群，每个 SageMaker AI Studio 用户都可以查看、管理并与可用任务交互。在接入多个团队之前先配置 task-view 限制：Amazon EKS 参见[为 EKS 集群在 Studio 中限制 task view](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-studio-setup-eks.html#sagemaker-hyperpod-studio-setup-eks-restrict-tasks-view)，Slurm 参见[为 Slurm 集群在 Studio 中限制 task view](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-studio-setup-slurm.html#sagemaker-hyperpod-studio-setup-slurm-restrict-tasks-view)。项目成员身份不是集群级的安全边界。

对于 Amazon EKS 集群，把每个团队映射到经批准的 namespace 与 RBAC 权限，并把每个工作负载的 service account 映射到租户专属的 IAM 角色。对于跨账户数据访问，将 service account 与容量（集群）账户中的一个 EKS Pod Identity 角色关联，并在该关联上设置目标 IAM 角色（`targetRoleArn`）。随后 EKS Pod Identity 会自动完成跨账户的角色代入，应用代码无需调用 `AssumeRole`。目标角色位于消费账户或数据账户中。把只读可见性与创建、更新或删除工作负载的权限分开。对于 Slurm 集群，定义等价的用户、账户、partition、文件系统与任务可见性控制。

例如，下面的 Kubernetes RBAC Role 只授予某团队对自己 namespace 内 jobs 的只读访问。创建或删除工作负载需要另一个独立角色，从而把「看见」与「行动」分离。

```
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: team-research
  name: research-job-viewer
rules:
  - apiGroups: ["batch"]
    resources: ["jobs"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["kubeflow.org"]
    resources: ["pytorchjobs"]
    verbs: ["get", "list", "watch"]
```

## 把业务优先级转化为调度策略

对于 Amazon EKS 集群，只有在身份与工作负载访问控制就位之后，才应用任务治理。

下图把其中的两个决策分离开来。

图 5：把授权与调度策略分开。EKS RBAC 或 Slurm ACL 决定用户能否提交工作负载；针对 Amazon EKS 的 SageMaker HyperPod 任务治理或 Slurm 原生调度控制决定其何时获得算力。

书面明确保障容量与共享容量、priority classes，以及某团队能否使用另一团队闲置的配额，并为每一条例外指派负责人。任务治理同样适用于 [SageMaker HyperPod spaces](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-studio-tabs.html)（直接运行在集群上的自包含 JupyterLab 或 Code Editor 环境），因此把这些交互式开发工作负载也纳入分配策略。

例如，在一个 Amazon EKS 集群上，你可以给生产训练团队 60% 的保障配额并配高 priority class，让研究团队以较低优先级借用闲置容量，并在生产团队提交作业时允许抢占这部分借来的容量。指派一位负责人审批对该策略的任何例外，避免一次性请求悄然变成常态。

把授权与调度策略保持分离。EKS RBAC 或 Slurm ACL 决定用户能否提交工作负载；针对 Amazon EKS 的 SageMaker HyperPod 任务治理，或 Slurm 原生调度控制，决定这个已授权的工作负载何时获得算力。把调度器配额当访问控制用，或把授权控制当调度策略用，都会导致行为不清晰，并让事故更难诊断。

博文[《Amazon SageMaker HyperPod 任务治理最佳实践》](https://aws.amazon.com/blogs/machine-learning/best-practices-for-amazon-sagemaker-hyperpod-task-governance/)讲解了 fair-share 权重、配额、借贷、priority classes 以及常见的分配场景。对于 Amazon EKS 集群，在定义分配策略时采用这些模式；对于 Slurm 集群，使用前文描述的原生调度控制。

## 把可观测性作为治理反馈环

借助 SageMaker Unified Studio，你可以查看 SageMaker HyperPod 集群的任务、指标、设置与元数据详情。对于 Amazon EKS 集群，任务治理指标包括硬件、团队与任务视图。这些视图帮助你对照策略意图与实际消耗。

把可观测性当作一个循环，如下图所示。

图 6：作为治理反馈环的可观测性。监控信号、将其与策略意图对比、决定响应、调整策略与分配，并为每个信号指派负责人和响应方式。

为你监控的每个信号定义负责人和响应动作。下面的示例把看板数据转化为管理决策。

| **信号** | **管理决策** |
| --- | --- |
| 集群容量与加速器利用率 | 判断低利用率是暂时的、策略导致的，还是工作负载约束造成的 |
| 团队配额与利用率 | 复审预留与共享容量是否仍反映业务需求 |
| 任务运行时长与排队时长 | 排查优先级策略、工作负载规模或容量争用 |
| Pending 与被抢占的任务 | 确认调度器结果与已批准的优先级模型一致 |
| 节点健康与恢复事件 | 启动集群事故流程并验证恢复目标 |

对于 Amazon EKS 集群，任务表格展示 Kubeflow 任务（PyTorch、MPI 与 TensorFlow），默认显示 PyTorch 任务；通过其他机制提交的工作负载可能不出现在其中。对于 Slurm 集群，任务表格展示当前调度队列中的作业，而 Slurm accounting 通过 `sacct` 等工具提供历史作业数据。明确你从哪里获取历史任务数据、审计证据与事故详情。

文档中的指标视图需要 Amazon CloudWatch Observability EKS add-on。该 add-on 有自身的前提条件：版本 2.4.0 或更高，并且把 `CloudWatchAgentServerPolicy` IAM 策略附加到 Kubernetes worker 节点角色。提供任务治理视图的 Kueue 指标在免费层之后可能产生 CloudWatch 指标费用。当前的配置与定价注意事项请参阅 [SageMaker HyperPod dashboard 文档](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-operate-console-ui-governance-metrics.html)。

## 在连接的整个生命周期内持续复审

为每个连接设定复审计划，并针对以下变化定义事件驱动的复审：项目所有权、访问角色、账户或 Region、集群容量、编排器版本、数据分级或监控覆盖的变更。用连接契约记录每一次决策。

## 结论

借助 Amazon SageMaker Unified Studio，机器学习团队可以沿着以项目为中心的路径使用经批准的 SageMaker HyperPod 算力，同时基础设施团队保留对集中集群的控制。从一个非生产集群和一个测试项目开始。在添加成员之前，先配置工作负载身份、namespace 或 Slurm 范围、数据权限、网络策略、task-view 限制，以及针对 Amazon EKS 的任务治理或针对 Slurm 的原生调度控制。安装 Amazon CloudWatch Observability EKS add-on，让指标视图有数据呈现，并在连接契约中记录完整的审批。为经批准的消费账户使用跨账户角色，在需要硬性隔离时使用专属基础设施。实施步骤请遵循 [SageMaker HyperPod 连接流程](https://docs.aws.amazon.com/sagemaker-unified-studio/latest/userguide/sagemaker-hyperpods.html)。
