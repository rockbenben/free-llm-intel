# 为 Amazon Bedrock 推出细粒度成本归因

随着 AI 推理在云支出中所占比例不断增大，弄清是谁、是什么在驱动成本，对于成本分摊、成本优化和财务规划至关重要。今天，我们宣布为 Amazon Bedrock 推理推出细粒度成本归因。

Amazon Bedrock 现在会自动将推理成本归因到发起调用的 IAM principal。[IAM principal](https://docs.aws.amazon.com/IAM/latest/UserGuide/intro-structure.html) 可以是 IAM 用户、应用程序所担任的角色，或来自 Okta、Entra ID 等提供方的联合身份。归因结果会流入你的 AWS Billing 并跨模型生效，无需管理任何资源，也无需改动你现有的工作流。借助可选的 cost allocation tags，你可以在 AWS Cost Explorer 和 AWS Cost and Usage Reports（CUR 2.0）中按团队、项目或自定义维度汇总成本。

本文将介绍 Amazon Bedrock 细粒度成本归因的工作原理，并逐一走过几个成本跟踪示例场景。

## **细粒度成本归因的工作原理**

在你的 [CUR 2.0](https://docs.aws.amazon.com/cur/latest/userguide/table-dictionary-cur2.html) 中，当你在数据导出配置里启用 IAM principal 数据后，就能看到哪些 AWS Identity and Access Management（IAM）principal 在调用 Amazon Bedrock，以及各自花多少钱，如下例所示：

| **line_item_iam_principal** | **line_item_usage_type** | **line_item_unblended_cost** |
| --- | --- | --- |
| arn:aws:iam::123456789012:user/alice | USE1-Claude4.6Sonnet-input-tokens | $0.069 |
| arn:aws:iam::123456789012:user/alice | USE1-Claude4.6Sonnet-output-tokens | $0.214 |
| arn:aws:iam::123456789012:user/bob | USE1-Claude4.6Opus-input-tokens | $0.198 |
| arn:aws:iam::123456789012:user/bob | USE1-Claude4.6Opus-output-tokens | $0.990 |

在这里你可以看到，Alice 使用的是 Claude 4.6 Sonnet，Bob 使用的是 Claude 4.6 Opus，以及各自在输入和输出 token 上的花费。下表显示了每种身份类型在 `line_item_iam_principal` 列中包含的内容：

| **你如何调用 Amazon Bedrock 推理** | **line_item_iam_principal** |
| --- | --- |
| AWS IAM 用户 | …user/alice |
| Bedrock key（映射到 IAM 用户） | …user/BedrockAPIKey-234s |
| AWS IAM 角色（例如 AWS Lambda 函数） | …assumed-role/AppRole/session |
| 联合用户（例如来自身份提供方） | …assumed-role/Role/user@acme.org |

### 添加标签以进行聚合和在 Cost Explorer 中使用

要按团队、项目或成本中心汇总成本，请为你的 IAM principals 添加标签。标签会以两种方式流入你的账单数据：

- **Principal tags** 直接附加在 IAM 用户或角色上。只需设置一次，该 principal 的每个请求都会带上它们。
- **Session tags** 在用户或应用程序担任 IAM 角色以获取临时凭证时动态传入，或嵌入在身份提供方的断言中。了解更多信息，请参阅 [Passing session tags in AWS STS](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_session-tags.html)。

在 AWS Billing 中将其激活为 [cost allocation tags](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-alloc-tags.html) 之后，两种标签类型都会以 `iamPrincipal/` 前缀出现在 CUR 2.0 的 tags 列中，如下例所示：

| **你如何调用 Bedrock** | **line_item_iam_principal** | **tags** |
| --- | --- | --- |
| AWS IAM 用户 | …user/alice | {“iamPrincipal/team”:”ds”} |
| AWS IAM 角色 | …assumed-role/AppRole/session | {“iamPrincipal/project”:”chatbot”} |
| 联合用户 | …assumed-role/Role/user@acme.org | {“iamPrincipal/team”:”eng”} |

有关制定成本分摊策略的更多指导，请参阅 [Best Practices for Tagging AWS Resources](https://docs.aws.amazon.com/whitepapers/latest/tagging-best-practices/building-a-cost-allocation-strategy.html)。

## **按场景快速上手**

你的配置方式取决于用户和应用程序如何调用 Amazon Bedrock。下表汇总了每种访问模式在 CUR 2.0 中可获得的归因信息，以及为基于标签的聚合需要配置的内容：

| **你的配置** | **CUR 2.0 归因** | **如何为聚合 + Cost Explorer 添加标签** | **场景** |
| --- | --- | --- | --- |
| 使用 IAM 用户或 API key 的开发者 | 每个用户的 ARN 都会出现在 CUR 2.0 中 | 为 IAM 用户附加标签 | 1 |
| 使用 IAM 角色的应用程序 | 每个角色的 ARN 都会出现在 CUR 2.0 中 | 为 IAM 角色附加标签 | 2 |
| 用户通过 IdP 进行身份验证 | ARN 中的 session name 标识用户 | 从你的 IdP 传入 session name 和标签 | 3 |
| 代理到 Bedrock 的 LLM 网关 | 只显示网关的角色（所有用户共用一个身份） | 增加按用户的 AssumeRole，并带上 session name 和标签 | 4 |

**注意：**对于场景 1–3，CUR 2.0 中的 `line_item_iam_principal` 列会为你提供按调用方的身份归因。只有当你希望按自定义维度（团队、成本中心、租户）聚合，或使用 Cost Explorer 进行可视化分析和告警时，才需要标签。对于场景 4，必须实施按用户的会话管理才能获得用户级归因。否则，流量会被归因到网关的单一角色。

添加标签后，请在 AWS Billing 控制台中或通过 `UpdateCostAllocationTagsStatus` API [激活你的 cost allocation tags](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/activating-tags.html)。标签会在 24–48 小时内出现在 Cost Explorer 和 CUR 2.0 中。

以下各节将逐一介绍几种常见场景。

## 场景 1：使用 IAM 用户和 API key 进行按用户跟踪

**使用场景：**小型团队、开发环境或快速原型验证，其中各个开发者使用 IAM 用户凭证或 Amazon Bedrock API keys。

### **工作原理：**

每个团队成员都有一个带长期凭证的专用 IAM 用户。例如，当 user-1 或 user-2 调用 Amazon Bedrock 时，Amazon Bedrock 会在身份验证过程中自动捕获其 IAM 用户 Amazon Resource Name（ARN）。你的 CUR 2.0 会显示谁花了多少钱。

如果你希望按团队、成本中心或其他维度汇总成本——例如查看数据科学团队成员的总体支出——请为你的 IAM 用户附加标签。你可以在 IAM 控制台、AWS Command Line Interface（AWS CLI）或 AWS API 中添加标签。以下示例使用 AWS CLI：

```
# Tag the data science team's users
aws iam tag-user \
  --user-name user-1 \
  --tags Key=team,Value="BedrockDataScience" Key=cost-center,Value="12345"

aws iam tag-user \
  --user-name user-2 \
  --tags Key=team,Value="BedrockDataScience" Key=cost-center,Value="12345"
```

**CUR 2.0 中会显示什么：**

Cost and Usage Report 会同时记录单个用户的身份及其标签，为你提供两个分析维度，如下例所示：

| **line_item_iam_principal** | **line_item_usage_type** | **line_item_unblended_cost** | **tags** |
| --- | --- | --- | --- |
| arn:aws:iam::123456789012:user/user-1 | USE1-Claude4.6Sonnet-input-tokens | $0.0693 | {“iamPrincipal/team”:”BedrockDataScience”,”iamPrincipal/cost-center”:”12345″} |
| arn:aws:iam::123456789012:user/user-1 | USE1-Claude4.6Sonnet-output-tokens | $0.2145 | {“iamPrincipal/team”:”BedrockDataScience”,”iamPrincipal/cost-center”:”12345″} |
| arn:aws:iam::123456789012:user/user-2 | USE1-Claude4.6Opus-input-tokens | $0.1980 | {“iamPrincipal/team”:”BedrockDataScience”,”iamPrincipal/cost-center”:”12345″} |
| arn:aws:iam::123456789012:user/user-2 | USE1-Claude4.6Opus-output-tokens | $0.9900 | {“iamPrincipal/team”:”BedrockDataScience”,”iamPrincipal/cost-center”:”12345″} |

`line_item_usage_type` 列编码了区域、模型和 token 方向（输入还是输出），因此你可以回答诸如“user-1 在 Sonnet 输入 token 和输出 token 上各花了多少？”或“谁在用 Opus、谁在用 Sonnet？”这样的问题。

基于这些数据，你可以通过多种方式分析成本：

- **按用户：**按 `line_item_iam_principal` 筛选，即可准确查看每个人的花费。这有助于识别重度用户或跟踪个人实验成本。
- **按模型：**按 `line_item_usage_type` 筛选，比较各模型的支出，例如谁在推高 Opus 成本、谁在使用 Sonnet。
- **按团队：**按 `iamPrincipal/team` 分组，查看数据科学团队成员的总体支出。这适用于部门成本分摊。

当用户数量可控、且你希望采用尽可能简单的配置时，这种方式最为理想。每个用户的凭证会直接在其账单中标识出他们，而标签让你可以把成本汇总到更高层级的维度。

**使用 Amazon Bedrock API keys：**Amazon Bedrock 还支持 [API keys](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html)，提供与其他 AI 提供方类似的简化身份验证体验。API keys 与 IAM principals 关联。使用 API keys 发出的请求会被归因到相应的 IAM 身份，因此同样适用于 `line_item_iam_principal` 和基于标签的归因。这意味着，组织无论是把 API keys 分发给开发者，还是将其嵌入应用程序，仍然可以把成本追溯到最初的 IAM 用户或角色。

## 场景 2：使用 IAM 角色进行按应用跟踪

**使用场景：**由应用程序（而非人工）调用 Amazon Bedrock 的生产工作负载，并且你希望按项目或服务跟踪成本。

**工作原理：**

你有两个后端应用程序，例如一个文档处理服务（app-1）和一个聊天服务（app-2）。每个应用程序运行在计算基础设施上（Amazon EC2、AWS Lambda、Amazon Elastic Container Service（Amazon ECS）等），并担任一个专用 IAM 角色来调用 Amazon Bedrock。当任一应用程序调用 Amazon Bedrock 时，其 assumed-role ARN 会被自动捕获。该归因会流入你的 CUR 2.0 报告，为你提供按应用的成本可见性。

你可以按包含角色名称的 `line_item_iam_principal` 筛选，查看每个应用的总体支出，或按 `line_item_usage_type` 比较各服务的模型用量。标签是可选的。如果你的应用程序为每个请求或批处理作业生成唯一的 session name，你还可以在更细的粒度上跟踪成本。

如果你希望按项目、成本中心或其他维度汇总成本——例如比较 DocFlow 与 ChatBackend 的总体支出——请为 IAM 角色附加标签：

```
# Tag the document processing role
aws iam tag-role \
  --role-name Role-1 \
  --tags Key=project,Value="DocFlow" Key=cost-center,Value="12345"

# Tag the chat service role
aws iam tag-role \
  --role-name Role-2 \
  --tags Key=project,Value="ChatBackend" Key=cost-center,Value="12345"
```

当 app-1 担任 Role-1 并调用 Amazon Bedrock 时，该请求会被归因到 assumed-role 会话。角色的标签会自动流入账单。

**CUR 2.0 中会显示什么：**

`line_item_iam_principal` 会显示完整的 assumed-role ARN，包括 session name，如下例所示：

| **line_item_iam_principal** | **line_item_usage_type** | **line_item_unblended_cost** | **tags** |
| --- | --- | --- | --- |
| arn:aws:sts::123456789012:assumed-role/Role-1/session-123 | USE1-Claude4.6Sonnet-input-tokens | $0.0330 | {“iamPrincipal/project”:”DocFlow”,”iamPrincipal/cost-center”:”12345″} |
| arn:aws:sts::123456789012:assumed-role/Role-1/session-123 | USE1-Claude4.6Opus-output-tokens | $0.1650 | {“iamPrincipal/project”:”DocFlow”,”iamPrincipal/cost-center”:”12345″} |
| arn:aws:sts::123456789012:assumed-role/Role-2/session-456 | USE1-NovaLite-input-tokens | $0.0810 | {{“iamPrincipal/project”:”ChatBackend”,”iamPrincipal/cost-center”:”12345″} |
| arn:aws:sts::123456789012:assumed-role/Role-2/session-456 | USE1-NovaLite-output-tokens | $0.0500 | {“iamPrincipal/project”:”ChatBackend”,”iamPrincipal/cost-center”:”12345″} |

这为你提供了多种分析选项：

- **按角色筛选：**使用 ARN 中的角色名称部分查看每个应用的总体支出。
- **按会话筛选：**使用 session name 按请求或批处理作业跟踪成本。
- **按项目聚合：**按 `iamPrincipal/project` 分组，比较 DocFlow 与 ChatBackend 的成本。
- **按成本中心聚合：**按 `iamPrincipal/cost-center` 分组，查看同一团队拥有的各应用的总体支出。

对于每个服务拥有自己 IAM 角色的微服务架构，这种方式最为理想——这一安全最佳实践现在也兼作成本归因机制。

## 场景 3：使用联合身份验证进行按用户跟踪

**使用场景：**用户通过企业身份提供方（Auth0、Okta、Azure AD、Amazon Cognito）进行身份验证，并通过 OpenID Connect（OIDC）或 Security Assertion Markup Language（SAML）联合身份访问 AWS 的企业环境。

**工作原理：**

用户通过你的身份提供方（IdP）进行身份验证，并担任一个共享的 IAM 角色。按用户的归因来自两种机制：**session name**（嵌入在 assumed-role ARN 中的用户身份）和 **session tags**（从 IdP 传入的团队、成本中心等）。一个 IAM 角色即可服务这些用户，因此无需管理按用户的 IAM 资源。

session name（以绿色高亮显示）就是出现在 `line_item_iam_principal` 中的内容：
 arn:aws:sts::123456789012:assumed-role/BedrockRole/user-1@acme.org

![架构图，展示使用 AWS Security Token Service（STS）和 OpenID Connect（OIDC）以临时凭证访问 Amazon Bedrock 的六步联合身份验证流程。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/17/ML-20614-1.png)

**图 1. 联合身份验证场景中的身份流程**

**对于 OIDC 联合身份**（Auth0、Cognito、Okta OIDC）：将你的 IdP 注册为 IAM OIDC 提供方，创建一个带有信任策略的角色，允许 `sts:AssumeRoleWithWebIdentity` 和 `sts:TagSession`，并配置你的 IdP 将 `https://aws.amazon.com/tags` 声明注入 ID token。AWS Security Token Service（AWS STS）会自动从该声明中提取 session tags。调用方应用程序在调用 `AssumeRoleWithWebIdentity` 时将 –role-session-name 设置为用户的 email（或其他标识符）。

**对于 SAML 联合身份**（Okta、Azure AD、Ping、ADFS）：在你的 IdP 中配置 SAML 属性映射，在断言中传递 `RoleSessionName`（例如用户 email）和 `PrincipalTag:*` 属性（团队、成本中心）。session name 和标签都嵌入在已签名的断言中——调用方应用程序无需单独设置它们。IAM 角色需要 `sts:AssumeRoleWithSAML` 和 `sts:TagSession`。

在这两种情况下，标签都在断言或 token 内部以密码学方式签名，因此用户无法篡改自己的成本归因。

**CUR 2.0 中会显示什么：**

| **line_item_iam_principal** | **line_item_usage_type** | **line_item_unblended_cost** | **tags** |
| --- | --- | --- | --- |
| …assumed-role/Role-1/user-1@acme.org | USE1-Claude4.6Opus-input-tokens | $0.283 | {“iamPrincipal/team”:”data-science”,”iamPrincipal/cost-center”:”12345″} |
| …assumed-role/Role-1/user-1@acme.org | USE1-Claude4.6Opus-output-tokens | $0.990 | {“iamPrincipal/team”:”data-science”,”iamPrincipal/cost-center”:”12345″} |
| …assumed-role/Role-1/user-2@acme.org | USE1-Claude4.6Sonnet-input-tokens | $0.165 | {“iamPrincipal/team”:”engineering”,”iamPrincipal/cost-center”:”67890″} |
| …assumed-role/Role-1/user-2@acme.org | USE1-Claude4.6Sonnet-output-tokens | $0.264 | {“iamPrincipal/team”:”engineering”,”iamPrincipal/cost-center”:”67890″} |

在此示例中，user-1 使用的是 Opus，user-2 使用的是 Sonnet。两者共用同一个 IAM 角色，但各自都可单独看到。按 `iamPrincipal/team` 分组可进行部门成本分摊，或解析 session name 进行按用户分析。

## 场景 4：通过 LLM 网关进行按用户跟踪

**使用场景：**组织在用户与 Amazon Bedrock 之间运行一个大型语言模型（LLM）网关或代理（LiteLLM、自定义 API 网关、Kong、Envoy 或自研服务）。

**问题所在：**网关在自己的层面完成用户身份验证，然后使用附加在网关计算资源上的单一 IAM 角色调用 Amazon Bedrock。如果不做额外工作，每次 Amazon Bedrock 调用在 CUR 2.0 中都会显示为同一个身份，没有按用户或按租户的可见性。

**解决方案：按用户的会话管理**

网关为每个用户调用一个限定于 Amazon Bedrock 的角色上的 `AssumeRole`，将用户身份作为 `--role-session-name` 传入，并将其属性（团队、租户、成本中心）作为 `--tags` 传入。由此产生的按用户凭证会被缓存（有效期最长 1 小时），并在同一用户的后续请求中复用。这需要两个 IAM 角色。第一个是网关执行角色，具有 `sts:AssumeRole` 和 `sts:TagSession` 权限。第二个是 Amazon Bedrock 调用角色，由网关角色信任，并限定于 Amazon Bedrock API。

![架构图，展示 LLM Gateway 为 User-1、User-2 和 Tenant-acme 管理按用户的 STS 凭证会话，以实现对 Amazon Bedrock 的隔离式多租户访问。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/04/17/ML-20614-2.png)
**图 2. LLM Gateway 场景中的身份流程**

关键的实现考量：

- **缓存会话**：`AssumeRole` 增加的延迟极小。在 1 小时的 time to live（TTL）下，你每小时每个用户只调用一次 STS，而不是每次请求都调用。
- **缓存大小随并发用户数增长**，而不是随用户总数（500 并发 = 约 500 个缓存会话）。
- **STS 速率限制**默认是每账户每秒 500 次 `AssumeRole` 调用。对于高吞吐网关，请申请提高配额。
- **session tags 在单个会话内不可变**。标签变更会在下次创建会话时生效。

**CUR 2.0 中会显示什么：**

| **line_item_iam_principal** | **line_item_usage_type** | **line_item_unblended_cost** | **tags** |
| --- | --- | --- | --- |
| …assumed-role/BedrockRole/gw-user-1 | USE1-Claude4.6Sonnet-input-tokens | $0.081 | {“iamPrincipal/team”:”data-science”} |
| …assumed-role/BedrockRole/gw-user-1 | USE1-Claude4.6Sonnet-output-tokens | $0.163 | {“iamPrincipal/team”:”data-science”} |
| …assumed-role/BedrockRole/gw-tenant-acme | USE1-Claude4.6Opus-input-tokens | $0.526 | {“iamPrincipal/tenant”:”acme-corp”} |
| …assumed-role/BedrockRole/gw-tenant-acme | USE1-Claude4.6Opus-output-tokens | $0.925 | {“iamPrincipal/tenant”:”acme-corp”} |

如果没有按用户的会话管理，网关流量会被归因到网关的单一角色。增加会话管理是解锁按用户和按租户归因的关键。

## **选择合适的场景**

- 使用 IAM 用户或 Amazon Bedrock API keys 的开发者 → **场景 1**
- 运行在 AWS 计算资源上、使用 IAM 角色的应用程序/服务 → **场景 2**
- 用户通过 IdP（Auth0、Okta、Azure AD）进行身份验证 → **场景 3**
- 位于 Amazon Bedrock 之前的 LLM 网关或代理 → **场景 4**
- 构建多租户 SaaS → 采用 **场景 4**，以 tenant ID 作为 session name + session tags
- Claude Code 工作负载 → **场景 3**

## **在 AWS Billing 中激活标签**

- 打开 [AWS Billing console](https://console.aws.amazon.com/billing/)
- 导航到 **Cost allocation tags**
- 在你的标签出现在至少一次 Amazon Bedrock 请求中之后（最多需等待 24 小时），它们会出现在 AWS 管理控制台的 **IAM** 类别下
- 选择要激活的标签，然后选择 **Activate**

对于 CUR 2.0，你还需要在创建或更新数据导出配置时启用 IAM principal。

## **在 Cost Explorer 中查看成本**

激活之后，你的 IAM 标签会出现在 Cost Explorer 的 **Tags **下拉菜单中，位于 **IAM** 类别下。你可以：

- 按 team = data-science 筛选，查看该团队的 Amazon Bedrock 总支出
- 按 tenant 分组，比较各客户的成本

## **开始使用**

Amazon Bedrock 的新成本归因功能现已在商业区域推出，且不额外收费。要开始使用：

- **确定你的访问模式**。开发者是直接用 IAM 用户或 API keys 调用 Amazon Bedrock 吗（场景 1）？应用程序使用的是 IAM 角色吗（场景 2）？用户通过身份提供方进行身份验证吗（场景 3）？还是流量经过 LLM 网关（场景 4）？
- **在你的 CUR 2.0 中启用 IAM principal 数据。**更新你的数据导出配置，使其包含 IAM principal 数据。
- **如果需要聚合或想在 Cost Explorer 中筛选，请添加标签。**为 IAM 用户或角色附加标签、配置你的 IdP 传入 session name 和标签，或为网关增加按用户的会话管理。然后在 AWS Billing 控制台中激活你的 cost allocation tags。
- **分析。**激活后 24–48 小时内，你的标签会出现在 Cost Explorer 和 CUR 2.0 中。按团队筛选、按项目分组，或组合多个维度，回答“engineering 团队这个月在 Claude Sonnet 上花了多少？”之类的问题。

## **结论**

弄清谁在推理上花了多少钱，是实现成本分摊、预测和优化的第一步。借助 Amazon Bedrock 的细粒度成本归因，你可以使用已有的 IAM 身份和标签机制，把推理请求追溯到具体的用户、应用程序或租户。无论你的团队是直接用 IAM 凭证调用 Amazon Bedrock，还是通过联合身份验证，抑或经由 LLM 网关，AWS CUR 2.0 和 AWS Cost Explorer 都能在不额外收费的前提下提供你所需的可见性。
