## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 使用 LangGraph 和 Amazon Bedrock AgentCore 网络搜索构建每日依赖性观察器

人工智能代理越来越多地处理取决于当前变化的工作，例如安全建议、产品发布、价格和法规。模型的训练数据无法回答这些问题，因此代理需要网络搜索。对于生产用途，团队还需要可以引用的结果，并控制哪些来源重要。他们希望搜索查询保留在云环境中，因为这些查询通常会泄露内部工作。

[Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/web-search-api.html) 中的 Web 搜索 API 现已推出。它通过单个 API 调用为代理和应用程序提供当前的 Web 结果，并使用他们已使用的 AWS 凭证进行签名。 AWS 为来自 Amazon 运营的网络索引的每个查询提供服务，并且不会将其发送到第三方搜索引擎。

每个结果都包括页面标题、URL、发布日期以及与查询相关的摘录。请求可以包含或排除域，并将结果限制在发布日期范围内。在 [AWS Lambda](https://aws.amazon.com/lambda/)、[Amazon Elastic Container Service (Amazon ECS)](https://aws.amazon.com/ecs/) 或 [Amazon Bedrock AgentCore 运行时](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 上，您的代理使用其执行角色调用 API。没有可存储或轮换的搜索 API 密钥。 [Amazon Bedrock AgentCore 上的 Web 搜索](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-web-search-tool.html) 也可通过 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 进行，这是 Amazon Bedrock AgentCore 的一项功能。在那里，一个管理员源策略涵盖每个代理和[模型上下文协议（MCP）]（https://modelcontextprotocol.io/）客户端。

对于LangChain开发者来说，LangChain的AWS集成中的AgentCore Web搜索工具现在调用Web搜索API。一个函数调用可为代理提供当前引用的搜索结果。该工具还可以保存模型无法更改的规则，例如日期窗口、源阻止列表和搜索预算。它将结果作为您的代码可以检查的数据返回。它可与 LangChain 代理、运行它们的编排框架 [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) 以及 [Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview) 配合使用，后者添加了子代理、虚拟文件系统和上下文压缩。

在这篇文章中，您将在 Web Search API 上为安全团队构建一个每日依赖性监视作为 LangGraph 图。每天早上，手表都会检查是否有任何新内容影响团队发布的开源包和容器基础镜像。它并行研究三个包生态系统，而您的代码使日期窗口、阻止列表和搜索预算不受模型的控制。它会根据其引用的来源检查每项发现，并记住其已报告的内容。然后，您在 AgentCore 运行时上运行手表，并通过 AgentCore Gateway 跨团队提供它。在我们的测试中，三个分支的完成时间为 36 秒，而之前的分支则为 99 秒。

## 解决方案概述

模型决定搜索内容并记录结果。无论模型做什么，必须遵守的每条规则都保留在代码中：日期窗口、阻止列表、搜索预算以及对每个发现的检查。图 1 显示了当您从笔记本电脑运行手表时这些部件如何组合在一起。

![依赖观察架构：一次运行分散到三个并行的研究分支，每个分支调用 Claude 模型和 Web 搜索 API，然后合并到引用的报告](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/06/ML-22037-1.png)

图 1：使用 LangGraph 和 Web 搜索 API 进行的日常依赖性观察，从笔记本运行

编号步骤：

- 运行以监视列表和监视窗口开始图形。
- `fan_out` 为每个生态系统启动一个研究分支：npm、PyPI 和容器基础镜像。 LangGraph 并行运行三个分支。
- 在每个分支内，代理调用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 中的 [Anthropic Claude](https://aws.amazon.com/bedrock/anthropic/) 模型。该模型决定要搜索什么，并最终产生结构化的结果。
- 分支机构的搜索工具将日期窗口和阻止列表添加到每个查询中。它使用使用 [AWS 签名版本 4 (SigV4)](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv.html) 签名的请求调用 Web Search API。重复步骤 3 和 4，每个分支最多同时在每个分支中进行四次搜索。
- 每个分支仅保留其来源支持且属于窗口范围内的发现。当所有三个分支完成后，LangGraph 会合并他们的发现并运行一次“keep_new”。
- `keep_new` 检查 [LangGraph 存储](https://docs.langchain.com/oss/python/langgraph/persistence) 并记录新的发现，因此不会报告两次。
- 报告为安全团队建立了新发现的引用表。

## 先决条件

在开始之前，您需要满足以下条件：

- 在提供 Web 搜索 API 的 AWS 区域中工作的 AWS 账户。这些示例使用美国东部（弗吉尼亚北部）区域 (us-east-1)。对于其他区域，请参阅[支持的 AWS 区域](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-regions.html)。
- Python 3.10 或更高版本。
- 运行笔记本的身份的 AWS 凭证，来自环境变量或 [AWS 命令​​行界面 (AWS CLI)](https://aws.amazon.com/cli/) 配置文件。该身份需要步骤 1 中的 [AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 权限以及对 Amazon Bedrock 中的 Anthropic Claude 模型的访问权限。
- 以下 Python 软件包：boto3 1.43.127 或更高版本、AgentCore Python SDK (bedrock-agentcore) 1.26.0 或更高版本以及 langchain-aws 1.9.3 或更高版本。使用以下`pip`命令安装它们：`pip install -U "boto3>=1.43.127" "bedrock-agentcore>=1.26.0" "langchain-aws[tools]>=1.9.3" langchain langgraph`

网络搜索和模型调用按使用次数计费。有关详细信息，请参阅 [Amazon Bedrock AgentCore 定价](https://aws.amazon.com/bedrock/agentcore/pricing/)。手表运行一次最多进行 12 次搜索。

完整的代码在此[笔记本](https://github.com/langchain-ai/langchain-aws/blob/main/samples/agents/agentcore_web_search_supply_chain_watch.ipynb)中。笔记本运行每个单元，包括设置。以下步骤涵盖了与搜索相关的部分。

## 第 1 步：授予权限

首先，授予您运行的身份作为搜索权限。 Web 搜索 API 需要对 AWS 拥有的一项资源执行一项 IAM 操作，因此每个账户中的语句都是相同的。 （有关完整设置，请参阅[授予调用 API 的权限](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/web-search-api-get-started.html#web-search-api-permissions)。）这使用与网关服务角色用于 Web 搜索的相同权限：
```
{
  "Effect": "Allow",
  "Action": "bedrock-agentcore:InvokeWebSearch",
  "Resource": "arn:aws:bedrock-agentcore:us-east-1:aws:tool/web-search.v1"
}
```
## 第二步：构建一个有固定规则的搜索工具

现在构建每个研究分支使用的搜索工具。手表无法让模型选择日期窗口、可信来源或搜索次数。该图还需要返回的源作为数据，以便稍后检查结果。 [langchain-aws 包](https://github.com/langchain-ai/langchain-aws) 中的网络搜索工具包涵盖了所有这些及其选项：
```
toolkit, tools = create_web_search_toolkit(
    region="us-east-1",
    exclude_domains=BLOCKLIST,
    published_after=window_start.strftime("%Y-%m-%dT%H:%M:%SZ"),
    model_filters=False,
    max_searches=4,
    return_sources=True,
)
```
如果没有网关参数，该工具将调用 Web 搜索 API。每次搜索都带有阻止列表和日期层，而模型自己的论点只能缩小它们的范围。使用 model_filters=False 时，模型仅看到查询参数。该工具在四次搜索后停止，并返回两次结果：作为模型的文本，以及作为图形的工件。每个分支都会创建自己的工具包，因此分支可以并行搜索。您可以为 Deep Agents 子代理提供相同的工具。

## 步骤 3：定义结果模式

使用搜索工具后，定义每个分支返回的内容。每个分支都是一个 [create_agent](https://docs.langchain.com/oss/python/langchain/agents) 代理，其响应格式为 Pydantic 模式，因此它返回结果而不是散文。调查结果包含包、单行标题以及 CVE 或咨询 ID（如果来源提供）。它还具有消息来源声明的严重性、消息来源是否表示它已被利用、建议的操作以及源 URL。该笔记本具有完整的架构和提示。

## 步骤 4：构建图表及其证据检查

现在组装图表。 “fan_out”使用 LangGraph 中的 Send API 向每个生态系统发送一个分支，因此这些分支是并行运行的。

在分支返回之前，代码会对每个发现运行四次检查。检查将结果与该分支自己的搜索返回的结果进行比较：

- 所引用的 URL 来自该分支机构的一项搜索。
- 来源的标题或文本将包命名为整个单词。
- 结果中的任何 CVE 或咨询 ID 都会出现在该文本中。
- 来源的发布日期位于观察窗口内。该工件包含已解析的每个日期，并且丢失的日期被视为外部日期。

所有分支完成后，“keep_new”将幸存的结果与 LangGraph 存储进行比较，并报告构建表。这些检查会捕获不受支持的 URL、未命名包的源、发明的 ID 和窗口外源。他们不确认严重性、利用状态、受影响的版本或建议的操作。他们也无法证明问题首次披露的时间：索引日期为本周的页面可以描述较早的事件。对于生产安全工作流程，根据权威漏洞源验证结果。在任何人采取行动之前，让某人审查发现的结果。

## 步骤 5：运行手表

您已准备好在 7 天的窗口内运行手表。在我们的运行中，三个分支机构进行了 12 次搜索并返回了 80 个来源。他们用了 36 秒的墙时间完成了比赛，而树枝加起来的时间为 99 秒。证据检查发现了两项结果：一项的来源未命名该软件包，另一项的 CVE ID 未出现在其来源中。没有任何来源来自被阻止的域。

有四个结果通过了检查，“keep_new”报告了其中两个。早些时候的测试已经报告了另外两个，所以商店阻止了它们。图 2 显示了在 LangGraph 的可视化调试器 [LangGraph Studio](https://docs.langchain.com/langsmith/quick-start-studio) 中的运行情况。报告的每一行都链接到其源，这是 [Web 搜索可接受使用条款](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/web-search-api.html#web-search-api-acceptable-use) 向用户显示的任何输出所要求的。

![LangGraph Studio 运行显示了三个并行研究分支和一份仅新的、经过证据检查的发现的报告，每个发现都与其来源相关联](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/06/ML-22037-2.png)

图 2：LangGraph Studio 中依赖关系监视的运行。右边的三个研究条目是三个生态系统分支，LangGraph 并行运行。该报告仅列出了通过证据检查且之前未报告过的发现，每项都与其来源相关联

## 步骤 6：再次运行手表以仅查看新发现

最后，第二次运行手表以查看商店的工作情况。计划的监视每天都会运行，团队不应该两次看到相同的建议。在我们的第二次调查中，分支机构再次进行了搜索，并保留了两项结果，并且商店之前已经报告过这两项结果。因此该报告没有什么新内容，如图 3 所示。

![LangGraph Studio 第二次运行，keep_new 发现存储中已有所有结果，因此报告没有显示新的发现](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/06/ML-22037-3.png)

对于计划作业，将“InMemoryStore”交换为具有精确键查找的持久存储，例如来自 [langgraph-checkpoint-aws](https://github.com/langchain-ai/langchain-aws/tree/main/libs/langgraph-checkpoint-aws) 的“DynamoDBStore”。

## 将网络搜索添加到现有的 LangChain 或 Deep Agents 应用程序中

如果您已经有 LangChain 代理，添加网络搜索需要进行一些更改。在部署之前检查这些：

- 权限：将步骤 1 语句添加到您的应用程序已运行的身份或执行角色。不需要创建其他任何东西。
- 区域：工具包的区域必须提供 Web 搜索 API，它可以与您的模型或应用程序的其余部分的区域不同。
- 工具名称：该工具名为“web_search”。如果您的代理已经有同名的工具（例如另一个搜索提供程序），请在添加该工具之前设置不同的名称。
- 规则和预算：每个工具包都有自己的过滤器和搜索预算。为需要单独规则或自己预算的每个代理或分支机构创建一个工具包。
- 吞吐量：帐户中的所有代理共享其 Web 搜索配额，因此并行分支会增加。默认情况下，一个账户在每个区域每秒可以发送 10 个请求。有关详细信息，请参阅 [Amazon Bedrock AgentCore 配额](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html#web-search-service-limits)。

使用 Deep Agents，您可以使用“create_deep_agent”定义代理：模型、工具、系统提示和子代理。将工具包的工具传递到子代理的工具列表中。将规则设置为工具包选项，因为无论模型要求什么，该工具都会将它们应用于每次搜索。要根据来源检查结果，如步骤 4 所示，请对代理的输出运行该检查或将其添加为中间件。在我们的测试中，深度代理协调员将这些工具委托给研究人员子代理，并在大约一分钟内返回引用的答案。

## 在 AgentCore 运行时上将其投入生产

当您准备好每天在没有笔记本的情况下运行手表时，请将其托管在 AgentCore 运行时上。运行时运行使用任何框架（包括 LangGraph）构建的代理，无需重写。它在相同的 API 背后提供两种计算类型。默认情况下，MicroVM 为每个会话提供自己独立的 microVM，因此一次运行无法看到另一次运行的数据。实例在您自己的账户中 AWS 托管的 [Amazon Elastic Compute Cloud (Amazon EC2)](https://aws.amazon.com/ec2/) 实例上运行您的代理。它们适合多天会话、GPU 工作负载或共享一个实例的多个代理。

有关各自的限制，请参阅[对代理使用隔离会话](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html) 和[运行时实例和容量提供程序](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-instances.html)。笔记本旁边的 [运行时示例](https://github.com/langchain-ai/langchain-aws/tree/main/samples/agents/agentcore_web_search_supply_chain_runtime) 包含与运行时入口点相同的图表。其策略授予运行时执行角色步骤 1 权限，但没有更广泛的访问权限。其自述文件逐步介绍了在任一计算类型上使用 [AgentCore CLI](https://github.com/aws/agentcore-cli) 创建、部署和调用项目。

![AgentCore 运行时上的依赖关系监视架构，每个 Web 搜索均由运行时执行角色签名，运行时返回报告](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/06/ML-22037-4.png)

图 4：AgentCore 运行时上托管的相同依赖项监视。步骤 2 到 7 与图 1 匹配，每个搜索均由运行时执行角色签名。在步骤 1，调用者调用运行时，例如使用 agentcore invoke。在第8步，运行时返回报告

运行时会话状态是短暂的，因此内存中的存储仅持续与会话一样长的时间。日常工作需要按计划调用第 6 步中的持久存储。

## 使用 AgentCore Gateway 跨团队扩展监视

AgentCore Gateway 上的 Web 搜索 API 和 [Web 搜索工具](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-web-search-tool.html) 搜索相同的索引，并且相同的图表适用于两者。选择谁执行规则以及谁调用搜索：

- 当您自己的应用程序调用搜索并强制执行其自己的规则时，请使用 Web 搜索 API，如步骤 1 至 6 中所示。它只需要一个 IAM 权限。
- 当平台团队向许多代理或团队提供搜索并希望 AWS 对每次搜索应用一个管理员源策略时，请使用 AgentCore Gateway。该策略位于网关目标上，对代理隐藏，代理无法解除它。
- 当 Claude 等 MCP 客户端需要搜索时，或者当您希望在一个 MCP 端点后面的其他工具旁边进行 Web 搜索时，请使用 AgentCore Gateway。

笔记本电脑的可选 Step 7 通过网关运行手表。它创建一个将阻止列表作为管理员策略的 Web 搜索目标，因此搜索客户端不再添加它。此路由需要针对两个不同主体的两个 IAM 授权。网关的服务角色需要Web搜索工具上的bedrock-agentcore:InvokeWebSearch。您的代理签署的凭据需要网关上的 bedrock-agentcore:InvokeGateway 。图 5 显示了流程。

![使用 SigV4 通过 MCP 调用 AgentCore Gateway 的依赖关系监视架构，其中 Web 搜索目标在调用 AgentCore Web 之前应用阻止列表搜索](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/06/ML-22037-5.png)

图 5：通过 AgentCore Gateway 进行相同的依赖关系监视。该图与图 1 相同。在步骤 4 中，搜索工具通过 MCP 调用使用 SigV4 签名的 AgentCore Gateway。在步骤 5 中，Web 搜索目标应用管理员阻止列表并调用 AgentCore Web 搜索

要为每个团队提供自己的策略，请为每个团队添加一个 Web 搜索目标，每个目标都有自己的阻止列表。此[演练笔记本](https://github.com/langchain-ai/langchain-aws/blob/main/samples/agents/agentcore_web_search_langgraph_walkthrough.ipynb) 显示了该模式。有关此路线的更多信息，请参阅 [Web 搜索工具](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-web-search-tool.html)。

## 清理

步骤 1–6 不创建 AWS 资源。如果您仅为此帖子添加了第 1 步权限，请将其从您附加的身份中删除。如果您运行了步骤 7，请删除目标和网关以避免持续产生费用。当您设置“DELETE_GATEWAY = True”时，笔记本的最后一个单元格会执行此操作：
```
target = gateway_client.get_gateway_target_by_name(GATEWAY_ID, "security-sources")
gateway_client.delete_gateway_target_and_wait(gatewayIdentifier=GATEWAY_ID, targetId=target["targetId"])
gateway_client.delete_gateway_and_wait(gatewayIdentifier=GATEWAY_ID)
```
笔记本保留网关的服务角色，以便其他网关可以使用它。当您不再需要它时，请在 IAM 控制台中将其删除。如果部署到运行时，请从项目文件夹运行“agentcore remove all”，然后运行“agentcore deploy -y”。
