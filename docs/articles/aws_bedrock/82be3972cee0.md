## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 使用 LangGraph 和 Amazon Bedrock AgentCore Web 搜索构建每日依赖项监视器

AI agent 越来越多地承担这类工作：结果取决于当天发生了什么变化，比如安全公告、产品发布、价格和法规。模型的训练数据回答不了这些问题，所以 agent 需要网页搜索。用于生产时，团队还需要能引用的结果，以及决定哪些来源算数的控制权。他们希望搜索查询留在自己的云环境里，因为这些查询往往会暴露内部工作。

[Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/web-search-api.html) 中的 Web Search API 现已可用。它通过一次 API 调用，为 agent 和应用程序提供最新的网页结果，请求用它们已在使用的 AWS 凭证签名。AWS 用 Amazon 自己运营的网页索引来响应每次查询，不会把查询转给第三方搜索引擎。

每条结果都包含页面标题、URL、发布日期，以及与查询相关的摘录。请求可以指定包含或排除某些域名，也能把结果限定在某个发布日期范围内。在 [AWS Lambda](https://aws.amazon.com/lambda/)、[Amazon Elastic Container Service (Amazon ECS)](https://aws.amazon.com/ecs/) 或 [Amazon Bedrock AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 上，agent 用自己的执行角色调用该 API，不需要存储或轮换搜索 API 密钥。[Amazon Bedrock AgentCore 上的 Web Search](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-web-search-tool.html) 也可通过 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 使用，后者是 Amazon Bedrock AgentCore 的一项能力。在那里，一条管理员来源策略就能覆盖所有 agent 和 [Model Context Protocol (MCP)](https://modelcontextprotocol.io/) 客户端。

对 [LangChain](https://docs.langchain.com/oss/python/langchain/overview) 开发者来说，[LangChain 的 AWS 集成](https://docs.langchain.com/oss/python/integrations/tools/bedrock_agentcore_web_search) 里的 AgentCore 网页搜索工具现在会调用 Web Search API。一次函数调用就能给 agent 最新的、带引用的搜索结果。这个工具还能固化一些模型改不了的规则，比如时间窗口、来源屏蔽列表和搜索预算。它把结果作为数据返回，方便代码核验。它既能配合 LangChain agent 使用，也能配合 [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview)（运行这些 agent 的编排框架）和 [Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview)（增加了子 agent、虚拟文件系统和上下文压缩）使用。

本文会把 Web Search API 上的一张 LangGraph 图，做成供安全团队使用的每日依赖项监视。每天早上，这套监视会检查团队交付的开源包和容器基础镜像有没有受到新情况影响。它并行调研三个包生态系统，而时间窗口、屏蔽列表和搜索预算都由代码掌管，不交给模型控制。它拿每条发现项对照其引用的来源核验，并记住已经报告过的内容。随后你在 AgentCore runtime 上运行这套监视，再通过 AgentCore Gateway 提供给多个团队。在我们的测试里，三个分支 36 秒就跑完了，逐个串行执行则要 99 秒。

## 方案概览

模型决定搜索什么、撰写发现项。无论模型怎么做，都必须成立的规则一律留在代码里：时间窗口、屏蔽列表、搜索预算，以及对每条发现项的检查。图 1 展示了从 notebook 运行这套监视时，这些部分如何配合。

![依赖项监视架构：一次运行分出三个并行调研分支，各分支分别调用 Claude 模型和 Web Search API，最后汇总成一份带引用的报告](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/06/ML-22037-1.png)

图 1：用 LangGraph 和 Web Search API 实现的每日依赖项监视，从 notebook 运行

编号步骤如下：

- 一次运行以监视清单和监视窗口启动这张图。
- `fan_out` 为每个生态系统启动一个调研分支：npm、PyPI 和容器基础镜像。LangGraph 并行运行这三个分支。
- 每个分支内，agent 调用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 中的 [Anthropic Claude](https://aws.amazon.com/bedrock/anthropic/) 模型。模型决定搜索内容，最后产出结构化的发现项。
- 分支的搜索工具把时间窗口和屏蔽列表加到每次查询上，再用经 [AWS Signature Version 4 (SigV4)](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv.html) 签名的请求调用 Web Search API。步骤 3 和步骤 4 会重复，每个分支最多搜索四次，各分支同时进行。
- 每个分支只保留有来源支撑、且落在窗口内的发现项。三个分支全部完成后，LangGraph 合并它们的发现项，并运行一次 `keep_new`。
- `keep_new` 检查 [LangGraph 存储](https://docs.langchain.com/oss/python/langgraph/persistence)，记录新的发现项，保证同一内容不会报告两次。
- report 为安全团队生成新发现项的带引用表格。

## 前提条件

开始前，需要准备好以下几项：

- 一个 AWS 账户，且所用 AWS 区域提供 Web Search API。示例使用美国东部（弗吉尼亚北部）区域 (us-east-1)。其他区域见[支持的 AWS 区域](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-regions.html)。
- Python 3.10 或更高版本。
- 运行 notebook 的身份所用的 AWS 凭证，来自环境变量或 [AWS Command Line Interface (AWS CLI)](https://aws.amazon.com/cli/) 配置文件。该身份需要第 1 步中的 [AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 权限，以及访问 Amazon Bedrock 中某个 Anthropic Claude 模型的权限。
- 以下 Python 包：boto3 1.43.127 或更高版本、AgentCore Python SDK (bedrock-agentcore) 1.26.0 或更高版本、langchain-aws 1.9.3 或更高版本。用下面这条 `pip` 命令安装：  `pip install -U "boto3>=1.43.127" "bedrock-agentcore>=1.26.0" "langchain-aws[tools]>=1.9.3" langchain langgraph`

Web Search 和模型调用按次计费。详情见 [Amazon Bedrock AgentCore 定价](https://aws.amazon.com/bedrock/agentcore/pricing/)。这套监视运行一次最多发起 12 次搜索。

完整代码在这个 [notebook](https://github.com/langchain-ai/langchain-aws/blob/main/samples/agents/agentcore_web_search_supply_chain_watch.ipynb) 里。notebook 会运行每一个单元格，包括设置部分。下面的步骤只讲与搜索相关的部分。

## 第 1 步：授予权限

首先，给你运行任务时所用的身份授予搜索权限。Web Search API 只需要对 AWS 自有的一项资源执行一个 IAM 操作，因此每个账户里的这条语句都一样。（完整设置见[授予调用 API 的权限](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/web-search-api-get-started.html#web-search-api-permissions)。）这里用的权限，与网关服务角色做网页搜索时所用的是同一个：

```
{
  "Effect": "Allow",
  "Action": "bedrock-agentcore:InvokeWebSearch",
  "Resource": "arn:aws:bedrock-agentcore:us-east-1:aws:tool/web-search.v1"
}
```

## 第 2 步：构建一个带固定规则的搜索工具

接下来构建各调研分支使用的搜索工具。这套监视不能让模型自行决定时间窗口、可信来源或搜索次数；图还需要把返回的来源当作数据留存，以便稍后据此核验发现项。[langchain-aws 包](https://github.com/langchain-ai/langchain-aws) 里的网页搜索工具包用一组选项覆盖了这些需求：

```
toolkit, tools = create_web_search_toolkit(
    region="us-east-1",
    exclude_domains=BLOCKLIST,
    published_after=window_start.strftime("%Y-%m-%dT%H:%M:%SZ"),
    model_filters=False,
    max_searches=4,
    return_sources=True,
)
```

不传网关参数时，工具会调用 Web Search API。每次搜索都带上屏蔽列表和起始日期，模型自带的参数只能把它们收得更窄。设置 `model_filters=False` 后，模型只看得到一个查询参数。工具在四次搜索后停止，并把结果返回两份：一份作为给模型的文本，一份作为给图的工件。每个分支都创建自己的工具包，因此各分支可以并行搜索。你也可以把同一套工具交给 Deep Agents 的子 agent。

## 第 3 步：定义发现项的结构

搜索工具就位后，定义每个分支返回什么。每个分支都是一个 [create_agent](https://docs.langchain.com/oss/python/langchain/agents) agent，以 Pydantic schema 作为响应格式，因此返回的是发现项，而不是一段散文。一条发现项包含包名、一行标题，以及来源若给出就一并带上的 CVE 或公告 ID；还包含来源标明的严重级别、来源是否称其已被利用、建议的处置措施，以及来源 URL。notebook 里有完整的 schema 和 prompt。

## 第 4 步：构建图与证据核验

现在把图组装起来。`fan_out` 用 LangGraph 的 Send API 为每个生态系统发出一个分支，让它们并行运行。

分支返回前，代码会对每条发现项做四项检查，把发现项与该分支自己搜索返回的内容逐一比对：

- 所引用的 URL 确实来自该分支的某次搜索。
- 来源的标题或正文以完整单词的形式提到该包。
- 发现项里的任何 CVE 或公告 ID 都出现在该正文中。
- 来源的发布日期落在监视窗口内。工件里带着已解析好的各个日期，缺日期一律视为窗口外。

所有分支完成后，`keep_new` 把通过检查的发现项与 LangGraph 存储比对，report 则生成表格。这些检查能拦下没有来源支撑的 URL、没提到包名的来源、编造的 ID，以及落在窗口外的来源。它们不核实严重级别、利用状态、受影响版本或建议的处置措施；也不能证明问题最初是何时披露的——索引把某个页面标为本周，它讲的却可能是更早的事件。用于生产安全流程时，请拿权威漏洞源再核验一遍发现项；任何人据此采取行动前，先让人审一遍。

## 第 5 步：运行监视

现在可以用 7 天窗口跑这套监视了。在我们的这次运行里，三个分支发起了 12 次搜索，取回 80 个来源，实际耗时 36 秒，而各分支耗时相加是 99 秒。证据核验剔除了两条发现项：一条的来源没提到包名，另一条的 CVE ID 没出现在它的来源里。没有任何来源来自被屏蔽的域名。

有四条发现项通过了检查，`keep_new` 只报告了其中两条。另外两条在更早的测试运行里已经报过，所以被存储拦下了。图 2 展示的是在 [LangGraph Studio](https://docs.langchain.com/langsmith/quick-start-studio)（LangGraph 的可视化调试器）中的这次运行。报告每一行都链向它的来源——[Web Search 可接受使用条款](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/web-search-api.html#web-search-api-acceptable-use) 要求，凡展示给用户的内容都必须做到这一点。

![LangGraph Studio 中的一次运行，显示三个并行调研分支，以及一份只含新增、经过证据核验且各自链接到来源的发现项的报告](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/06/ML-22037-2.png)

图 2：LangGraph Studio 里一次依赖项监视的运行。右侧三条调研记录就是三个生态系统分支，由 LangGraph 并行执行。报告只列出通过证据核验、且此前未报告过的发现项，每条都链接到它的来源

## 第 6 步：再跑一次，只看新增发现项

最后再跑一次，看看存储是怎么起作用的。定时监视每天运行，团队不该把同一条公告看两遍。第二次运行时，各分支重新搜索并留下两条发现项，而存储此前已经报过这两条，于是报告里没有新内容，如图 3 所示。

![LangGraph Studio 的第二次运行：keep_new 发现所有结果都已在存储中，因此报告没有新增发现项](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/06/ML-22037-3.png)

图 3：用相同输入再跑一次。各分支重新搜索，但 keep_new 发现每个结果都已在 LangGraph 存储中，因此报告没有新内容

对于定时任务，把 `InMemoryStore` 换成支持精确键查找的持久存储，比如 [langgraph-checkpoint-aws](https://github.com/langchain-ai/langchain-aws/tree/main/libs/langgraph-checkpoint-aws) 里的 `DynamoDBStore`。

## 为现有的 LangChain 或 Deep Agents 应用添加网页搜索

如果你已经有 LangChain agent，加上网页搜索只需改几处。部署前先核对这几项：

- 权限：把第 1 步的语句加到应用当前所用的身份或执行角色上，无需另建任何东西。
- 区域：工具包所在的区域必须提供 Web Search API，它可以与模型或应用其他部分所在的区域不同。
- 工具名称：该工具名为 `web_search`。如果 agent 里已有同名工具（比如另一家搜索服务），添加前先给它换个名字。
- 规则与预算：每个工具包都带自己的过滤器和搜索预算。凡是规则或预算需要独立的 agent 或分支，就各配一个工具包。
- 吞吐量：一个账户里的所有 agent 共用该账户的 Web Search 配额，并行分支会累加。默认情况下，账户在每个区域每秒可发 10 个请求。详情见 [Amazon Bedrock AgentCore 配额](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html#web-search-service-limits)。

用 Deep Agents 时，你通过 `create_deep_agent` 定义 agent：一个模型、一组工具、一段 system prompt 和若干子 agent。把工具包里的工具放进某个子 agent 的工具列表。规则要设在工具包选项上，因为无论模型怎么要求，工具每次搜索都会套用这些规则。要像第 4 步那样拿来源核验发现项，可以在 agent 的输出上跑这道检查，或者把它加成中间件。在我们的测试里，Deep Agents 的协调 agent 把这些工具交给一个负责调研的子 agent，大约一分钟后返回了带引用的答案。

## 在 AgentCore runtime 上投入生产

当你不想依赖 notebook、打算每天运行这套监视时，就把它托管到 AgentCore runtime 上。Runtime 能运行用任意框架构建的 agent，包括 LangGraph，无需重写。它在同一套 API 背后提供两种计算类型。默认的 MicroVM 给每个会话分配一台独立的 microVM，一次运行看不到另一次的数据。Instances 则在自己账户里由 AWS 托管的 [Amazon Elastic Compute Cloud (Amazon EC2)](https://aws.amazon.com/ec2/) 实例上运行 agent，适合持续数天的会话、GPU 工作负载，或多个 agent 共用一台实例。

两者的限制分别见[为 agent 使用隔离会话](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html) 和 [Runtime Instances 与容量提供程序](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-instances.html)。notebook 旁边的 [Runtime 示例](https://github.com/langchain-ai/langchain-aws/tree/main/samples/agents/agentcore_web_search_supply_chain_runtime) 把同一张图作为 Runtime 入口。它的策略只授予 Runtime 执行角色第 1 步的权限，没有更宽的访问权限。README 逐步演示如何用 [AgentCore CLI](https://github.com/aws/agentcore-cli) 在任一种计算类型上创建、部署和调用这个项目。

![AgentCore runtime 上的依赖项监视架构：每次网页搜索都由 Runtime 执行角色签名，Runtime 返回报告](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/06/ML-22037-4.png)

图 4：托管在 AgentCore runtime 上的同一套依赖项监视。步骤 2 到 7 与图 1 一致，只是每次搜索都由 Runtime 执行角色签名。步骤 1 由调用方发起调用，例如用 agentcore invoke；步骤 8 由 Runtime 返回报告

Runtime 的会话状态是临时的，内存存储只在会话期间存在。每日任务需要第 6 步里的持久存储，并按计划定时调用。

## 用 AgentCore Gateway 把监视扩展到多个团队

Web Search API 和 AgentCore Gateway 上的 [Web Search Tool](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-web-search-tool.html) 搜的是同一个索引，同一张图在两边都能跑。按谁来执行规则、谁来发起搜索来选：

- 自己的应用发起搜索、自己执行规则时（如第 1 到 6 步），用 Web Search API，它只需要一条 IAM 权限。
- 平台团队要把搜索提供给许多 agent 或团队，并希望由 AWS 对每次搜索套用同一条管理员来源策略时，用 AgentCore Gateway。这条策略挂在网关目标上，对 agent 不可见，agent 也无法解除。
- Claude 之类的 MCP 客户端需要搜索，或者想让网页搜索与其他工具一起挂在同一个 MCP endpoint 后面时，用 AgentCore Gateway。

notebook 里可选的第 7 步会经网关运行这套监视。它创建一个网页搜索目标，把屏蔽列表作为管理员策略带上去，于是搜索客户端不再自己添加。这条路径需要给两个不同的主体各授一条 IAM 权限：网关的服务角色需要在网页搜索工具上有 bedrock-agentcore:InvokeWebSearch；agent 签名所用的凭证需要在网关上有 bedrock-agentcore:InvokeGateway。图 5 展示了这一流程。

![依赖项监视经 MCP、用 SigV4 调用 AgentCore Gateway 的架构：网页搜索目标先套用屏蔽列表，再调用 AgentCore Web Search](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/06/ML-22037-5.png)

图 5：经 AgentCore Gateway 运行的同一套依赖项监视。图与图 1 相同。步骤 4 中，搜索工具通过 MCP 调用经 SigV4 签名的 AgentCore Gateway；步骤 5 中，网页搜索目标套用管理员屏蔽列表并调用 AgentCore Web Search

要让每个团队各有自己的策略，就给每个团队加一个网页搜索目标，各带自己的屏蔽列表。这个[演练 notebook](https://github.com/langchain-ai/langchain-aws/blob/main/samples/agents/agentcore_web_search_langgraph_walkthrough.ipynb) 演示了这种模式。想进一步了解这条路径，见 [Web Search Tool](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-web-search-tool.html)。

## 清理

第 1 到 6 步不创建任何 AWS 资源。如果第 1 步的权限只是为本文加的，就把它从所挂的身份上移除。如果跑了第 7 步，删掉目标和网关，以免持续计费。把 `DELETE_GATEWAY = True` 设好，notebook 的最后一个单元格就会做这件事：

```
target = gateway_client.get_gateway_target_by_name(GATEWAY_ID, "security-sources")
gateway_client.delete_gateway_target_and_wait(gatewayIdentifier=GATEWAY_ID, targetId=target["targetId"])
gateway_client.delete_gateway_and_wait(gatewayIdentifier=GATEWAY_ID)
```

notebook 会保留网关的服务角色，供其他网关复用；不再需要时，到 IAM 控制台删掉它。如果部署到了 Runtime，在项目目录里先运行 `agentcore remove all`，再运行 `agentcore deploy -y`。

## 结语

Amazon Bedrock AgentCore 中的 Web Search API 用现成的 AWS 凭证，为 LangChain agent 提供最新、带引用的网页结果。这套依赖项监视展示了如何不止于一次工具调用：把模型不能改的规则留在代码里，把返回的来源作为数据留在模型上下文之外；能核验的都核验，用户看到的每处内容都保留引用。当更多团队需要同一套搜索时，AgentCore Gateway 用一条策略覆盖所有团队。
