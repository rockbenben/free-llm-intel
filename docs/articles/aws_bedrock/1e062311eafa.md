# 面向金融合规的生产级 AI agent：来自 Stripe 的经验

*本文由 Stripe 的 Christopher Phillippi 与 Chrissie Cui 合著。*

[Stripe](https://stripe.com/) 每年在 50 个国家处理 1.4 万亿美元的支付量，合规团队每天需要审查数千笔交易。本文探讨 Stripe 如何用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 在 AWS 上构建一套生产级 AI agent 系统，把审查处理时间缩短 26%，同时保留人工监督。文章涵盖技术架构、基础设施决策，以及部署这套 agentic AI 的经验——它获得了超过 96% 的有用性评分，而最终决策权牢牢掌握在人类专家手中。

在本文中，你将了解 Stripe 如何为金融合规构建一套生产级 AI agent 系统。我们介绍 Stripe 的 ReAct agent 框架的技术架构，以及专用 agent 服务背后的基础设施决策。我们还会讨论人工监督在维持问责性方面的作用，以及关于任务分解、编排模式和通过 prompt caching 优化成本的关键经验。读到最后，你将理解如何设计 agentic 系统，使其在扩展合规运营的同时不牺牲质量或可审计性。

## Stripe 的规模与合规挑战

Stripe 的根本使命是提升互联网的国内生产总值（GDP）。这一追求需要可编程的金融基础设施，其设计要能为各种规模的企业支撑顺畅的交易与运营管理。截至 2026 年初，Stripe 已从其起源于开发者导向支付 API 的形态，成长为全球经济的系统性支柱。公司服务 50 个国家的数百万家企业——从早期初创公司到《财富》500 强中的 62%——每年处理约 1.4 万亿美元的支付量。这一规模约占全球 GDP 总量的 1.3%，使 Stripe 处于技术创新与强监管框架的关键交汇点。

## 合规的规模化难题

随着 Stripe 的全球布局扩展到 50 个国家，组织面临一个关键挑战：如何在不按比例增加人力的前提下扩展合规运营，同时维持监管质量标准。每天，合规团队都要做细致的审查，以识别并缓解金融犯罪风险。然而，熟练的分析师把多达 80% 的时间花在穿梭于碎片化系统去收集材料上，而不是做高价值的风险评估。Stripe 的解决方案把 AI agent 与自动化编排结合起来，将合规从一项资源密集型流程转变为可扩展的引擎。这一做法应对了 2060 亿美元的全球合规负担：它帮助组织实时识别 95% 的卡测试攻击，并把不必要的客户摩擦降低 20%。这一做法同时保持了监管机构所要求的可审计性与精确性。

### 为什么合规工作要用 agentic AI？

传统自动化在处理复杂的、依赖判断的合规工作时有局限，因此需要 AI agent 来以规模化、一致的质量和完整的可审计性处理辅助调查，同时把控制权留在人手里。

### 三大支柱

- **监督与问责** – 以人为中心的校验，配有可配置的审批 workflow 和多层决策检查点。人类始终掌握主导权，由 agent 提供支持。
- **透明性** – 完整的审计轨迹，对每一项操作、决策和理由都有不可篡改的记录。
- **效率** – 预调查与动态分析让更深入的审查能以更快的节奏完成。

## 技术架构

Stripe 的 agentic 合规系统在技术实现上由三个关键组件构成：任务分解与编排、ReAct agent 框架，以及配套的基础设施服务。每个组件都在实现可扩展、可审计的合规自动化中发挥关键作用。

### 任务分解与审查编排

只派一个 agent 一次性地处理这段漫长而复杂的审查是行不通的。一个不受约束的单一 agent 会把注意力过多地放在错误的事情上，而对真正需要的东西关注不足。于是 Stripe 把这段复杂的审查拆成可组合的、小块的子任务，使方案变得可处理。每个子任务都可以按有向无环图（directed acyclic graph，DAG）依赖其他子任务的结果。这些 *rails* 有助于确保每个 agentic 流程只跑在经过验证的问题上——这些问题的质量已通过质量测试衡量。它们还有助于确认调查覆盖了必需的各个方面，并为 agent 提供足够的上下文与聚焦，以产出高质量结果。

尽管对每个子任务中的 agent 响应都做了严格的质量测试，Stripe 的实现并没有完全依赖 agent 的回答。相反，这些回答作为补充信息提供给人工审查者，而审查者最终必须回答审查中的每个子任务。这在解决监督与问责问题的同时，仍然收获了效率收益。下图展示了高层的审查流程。

![示意图：审查编排流程，人工审查者与审查工具交互，该工具将有向无环图形式的问题编排起来，agent 的回答作为补充信息提供](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/24/ML-20542-1-1.png)

审查者与审查工具交互，该工具知道当前是哪个问题，以及哪些后续问题需要把该答案作为上下文。工具充当编排器，把经人工审查的答案作为上下文输送给后续问题。

### ReAct agent 框架的实现

为了给每个子问题获取调研材料，Stripe 用 ReAct（reasoning and acting，推理与行动）agent 框架的一种形式构建了一个合规 agent。除了使用大语言模型（large language model，LLM）——Amazon Bedrock 上的一类基础模型（foundation model，FM）——来做推理之外，agentic 的一面还会通过工具调用动态收集相关信号。Stripe 选择这一 agent 框架，是为了解决这样一个问题：信号数量近乎无限，而对某个特定对象而言，它们可能相关也可能不相关。Agent 自行判断哪些信号相关并提出后续追问，直到有足够信心给出最终答案。下图展示了 agent 的高层逻辑。

![示意图：ReAct agent 框架的循环，展示 Thought、Action（工具调用）和 Observation 步骤的迭代过程，直至得出最终答案](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/24/ML-20542-2-1.png)

为了走一遍这个流程，设想有人问你这样一个 query：“10 除以数字 π 的答案是什么？”

如果你是 ReAct agent，你的第一个 thought 会是考虑自己是否已经知道答案。你不知道，于是会提出一个 action：拿出计算器并输入 `10/π`。计算器随后返回一个 observation。你的下一个 thought 是判断自己是否已有答案，然后把这个计算结果作为最终答案给出。你可以想象更难的请求，例如“产出一份预测公司明年营收的分析”，它需要许多轮数据库查询（Tool）与解读（Thought）的迭代。

在 ReAct 循环中，只要 Thought 块里请求了某个工具，agent 框架就会停止 LLM 的执行，改为以程序方式运行该工具。然后它把该输出作为 observation 强制回注给 agent，之后才允许其继续。这种注入模式实现了一种*闭环控制机制*，它：

- **让 agent 的推理扎根于真实数据** – 通过强制每个工具输出都必须被当作 observation 处理，防止 agent 幻觉或编造工具结果。
- **维持上下文连贯** – 强制 agent 在继续之前显式确认并推理每一份检索到的信息。
- **防止推理漂移** – observation 步骤充当检查点，帮助确认 agent 的思考过程始终锚定在事实性的工具输出上，而不是猜测性推理上。
- **支持可审计性** – 创建一条明确的追踪链：工具调用 → observation → 推理，可记录日志以供合规审查。

这类似于工程学中的*反馈控制系统*。agent 必须先处理上一次动作的反馈（observation），才能进入下一个动作，从而避免可能引发幻觉或推理跑偏的开环行为。

这种做法的一个挑战是：当任务复杂到需要很多轮对话和 observation 时，prompt 在后期轮次会变得非常长，尤其是 observation 冗长的时候。子任务分解限制了每个问题的范围，从而把轮次数量压得更少。Prompt caching 也有助于降低输入 token 的成本——这是这里最主要的成本驱动因素。借助 prompt caching，你只需为每一轮追加到既有消息之后的新 observation 和 thought 付费。Amazon Bedrock 提供了这项能力。

### 构建专用的 agent 服务

在这个项目之前，Stripe 并没有 agent 服务，是这个项目让 Stripe 提出了这一需求。起初，Stripe 尝试把一个 agent 塞进传统的 ML 推理引擎。这个做法很快被否决，原因如下：

- **计算画像 –** 传统 ML 是算力密集型，需要 GPU、多线程高性能 CPU 或大块内存分配这类昂贵硬件。相比之下，agentic 应用大多是网络密集型，在等基础模型算完或等工具调用执行完。
- **延迟 –** 回到前面描述的 ReAct 流程，一个 agent 完成所需的时间是不确定的，取决于它需要多少轮工具调用。一次长时间的 agent query 或一次数据库工具调用，可能让一个线程空等数分钟；而一个 XGBoost 模型在毫秒级就能跑完。
- **API 不同 –** 传统 ML 倾向于输出基本类型（float、Boolean 等），与之不同，agent 需要更灵活的 schema 来标注其结果。有些 agent 需要维护有状态的对话状态。

于是，Stripe 搭起了自己的 agent 服务，最初形似一个无状态、同步的推理端点。如今它也能处理有状态的多轮对话 agent。它在不到一年里从发布时的少数几个 agent，增长到远超 100 个 agent。

### LLM proxy 架构

Stripe 的 ReAct agent 并不直接调用 Amazon Bedrock。相反，Stripe 用一个 LLM Proxy 微服务作为访问 LLM 的标准方式。下图展示了 LLM Proxy 的架构。

![示意图：LLM Proxy 微服务架构，提供单一 API 端点以访问多个基础模型，具备噪声邻居防护、模型回退和监控等特性](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/24/ML-20542-4-1.png)

Stripe 使用 LLM Proxy 服务的原因如下：

- **噪声邻居 –** Stripe 内部有许多团队把 LLM 用于各种应用。LLM Proxy 提供了防护，避免其他团队把某个模型的 LLM 带宽占满，防止资源争用。
- **一个 API，多种模型 –** 单一端点让跨 Amazon 与领先 AI 公司的基础模型指定 prompt caching、工具调用等能力变得简单。切换模型只需把 model type 作为参数改掉，而不必让每个用例各自管理许多不同的客户端。
- **模型回退 –** 这提供了在资源受限或彻底失败时自动指定默认模型的能力。
- **监控 –** 通过要求认证，服务可以跟踪模型用量，帮助预测未来的资源需求，并确认根据应用的隐私级别选用了合适的模型。

### 架构组件如何协同工作

人工审查者主导审查，把 agentic 回答当作预先取得的调研材料。随着他们作答，这些回答可以用在同一次审查中更深层问题的 prompt 里，从而把审查问题按有向无环图（DAG）编排起来。

对某个给定问题，agent 可以调用工具，按需动态访问内部数据或服务。之所以采用这种做法，是因为可检查的潜在相关信号通常远多于能塞进 prompt 的量。agent 的工具调用能力意味着 thought log 只包含回答当前问题所需的相关数据，没有额外无关信息，从而形成聚焦。

agent 本身由来自 Amazon 与领先 AI 公司的基础模型驱动，这些模型负责思考并决定需要哪些工具调用。agent 应用通过 LLM Client 访问 LLM，该客户端把 prompt caching 和模型回退等特性抽象掉了。

### Amazon Bedrock 集成带来的收益

Stripe 在其 LLM Proxy 中使用 Amazon Bedrock。Amazon Bedrock 还带来以下收益：

- **标准化的隐私与安全 –** 作为支付处理商，Stripe 在隐私与安全上必须格外谨慎。Amazon Bedrock 有助于确认来自 Amazon 与领先 AI 公司的基础模型符合既有的安全与隐私约束，而无需为每个模型单独增加一轮审查。
- **功能丰富 –** 如前所述，Amazon Bedrock 允许在受支持的模型上使用 prompt caching。此外，Amazon Bedrock 还支持微调并托管自定义模型，Stripe 预计未来一年会重点投入这方面。
- **一个 API，多种模型 –** 集成很直接，因为模型都落在同一个 API 里。切换模型只需改用不同的模型名称。Amazon Bedrock 还支持来自 Amazon 与领先 AI 公司的许多不同基础模型，为 Stripe 提供行业标准的性能。

### 为满足监管合规的审计轨迹实现

尽管 Stripe 最终由人工审查者做判断和决策，系统仍然必须证明自己能经得起监管审视。因此，Stripe 实现了日志记录，使每一次历史运行的完整 agent 日志都可检索。每一项 agent 操作、决策和理由都有记录。

## 结果与影响：审查提速 26%，有用性超过 96%

通过 agentic 自动化，Stripe 把审查处理时间的中位数缩短了 26%，同时审查者给出的有用性评分保持在 96% 以上，决策仍由人工审查者掌控。这一切是在提供满足检查标准的完整审计轨迹的同时实现的。

随着 Stripe 持续增长，组织将能够跟上风险管理方面相应增长的需求。人工审查者可以把时间集中在更棘手的问题或新的调查机会上，从而让合规项目不断改进。

## 生产部署中的关键经验

在构建和部署这套生产级 agentic AI 系统的过程中，Stripe 提炼出若干洞见，它们塑造了项目的成功，也可为类似实现提供参考。

**小块任务 –** 让 agent 任务小到能放进工作记忆。逐步测试质量，而不是直接一头扎进全自动化。

**编排 –** 支持 DAG 的异步 workflow 架构对于复杂的 agent 交互至关重要，同时还能在大规模下维持可审计性与人工监督。

**基础设施 –** 专用微服务架构之所以重要，是因为 agent 的资源画像与传统 ML 模型根本不同。传统推理系统是算力密集型的，针对昂贵 GPU 硬件上的毫秒级响应做了优化。agent 则是网络密集型的，会把数分钟花在等待 LLM 调用和工具执行上，且延迟模式不可预测。专用 agent 服务通过异步执行模式处理这些长时间运行、有状态的交互。这让线程能高效管理多个并发的 agent 会话，而不会阻塞在外部调用上。Token caching 通过在各 agent 轮次间复用公共 prompt 前缀，而不是每一步都重新处理整段对话历史，把成本降低 60%。成本度量会跟踪每次 agent 调用的 token 用量，帮助团队在工作负载扩展时预测开销，并在影响预算之前识别优化机会。这种基础设施优先的做法，把 agent 从实验性原型转变为支撑 Stripe 内 100 多个 agent 的生产服务。

**让人保持控制 –** agent 提供协助，但专家审查者保有最终决策权。用 rail 约束 agent，以界定上下文边界。

## 下一步

起初，Stripe 聚焦于那些在审查开始之前就能回答的问题。剩下的问题很可能需要审查过程中才已知并经验证的上游上下文。这将带来更复杂、多步的调查——在审查过程中把实时回答编排为上下文，从而支撑更深入的效率改进。当前的 26% 缩短只是早期进展。

由于 Stripe 不愿因使用这项技术而接受风险容忍度的上升，团队会用人类质量标准来检验 agentic 调查组件。在允许该组件于生产环境中为审查者提供信息之前，团队会与真人一起做验证。团队还在探索用 LLM 快速判断并淘汰不合格做法的方式。

Amazon Bedrock 提供的定制能力正被 Stripe 探索用于进一步增强其合规系统。目前，Stripe 使用检索增强生成（RAG）通过工具调用动态注入知识，让 agent 能访问实时的合规数据。展望未来，Stripe 正考虑用 Amazon Bedrock 的微调能力，专门为金融合规任务调整模型行为。这将有助于锁定模型质量，并在模型演进时减少重复评估的开销。此外，Amazon Bedrock 还提供 continued pre-training（持续预训练）选项，用于纳入领域特定知识，这可能有助于把更专业的合规经验构建进 agent 的推理中。Amazon Bedrock 的模型版本管理与 6 个月弃用通知窗口，有助于有策略地规划这些定制工作，使模型升级只发生在确实能提升调查能力的时候。随着合规运营扩展，这些互补的技术共同在性能、稳定性与适应性之间取得平衡。

## 结语

Stripe 已经证明，agent 能够加速人工审查流程：在把决策权保留在人类手中、而非全自动化的前提下，仍把审查处理时间缩短了 26%，并保持 96% 以上的有用性评分。Stripe 并没有单靠 agent 的能力，而是通过构建 rail 把 agent 约束在它能胜任的小块审查范围内来达成。为此，Stripe 需要新的 agentic 服务基础设施——它受历史上已有的机器学习推理系统启发，但与之不同。

这在 Amazon Bedrock 上成为可能：它为 Stripe 提供了支撑这次审查效率跃升的隐私保护与模型选择能力，而这些能力有望延伸到许多其他领域。
