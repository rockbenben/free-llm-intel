# 使用 AWS Agent Registry 大规模管理 agent、工具与技能

大多数组织在扩大 agent 与工具的使用规模时，都会遇到同样的挑战。各团队各自孤立地建设，没有共享记录说明存在什么、由谁负责，或是否已经过评审。问题已经从「构建 agent 与工具」转变为「发现与治理它们」。AWS Agent Registry 正是为解决这一问题而专门构建的。它现已正式可用（generally available），为环境中的 agent、工具、技能与自定义资源提供一个统一、可搜索、可治理的目录。

在本文中，我们将介绍 Registry 是什么，逐步讲解其核心的发布、策展与发现工作流，探讨企业级考量，并展望后续发展。

## 企业为什么需要一个 registry

随着组织扩大其 agentic AI 系统的规模，三个关键挑战随之浮现。

### 缺乏权威清单

当每个团队都孤立地维护自己的 agent 与工具集合时，就没有统一记录说明存在什么、由谁负责，或它是否仍在积极维护。结果是重复劳动、版本漂移，以及散落在整个组织中的未跟踪能力不断膨胀。

### 缺乏跨团队发现能力

即便存在优秀的工具、agent 与技能，它们也会被闲置，因为其他团队的开发者找不到它们。没有可搜索的目录，默认做法就是重建已有的东西。这浪费了工程投入，带来需要维护的冗余基础设施，以及随每个孤立建设的团队而不断增长的持续运营成本。

### 缺乏治理与审计轨迹

没有中心化的 registry，就无法跟踪谁有权访问哪些 agent、工具与技能、它们是否通过了安全评审，也无法把故障追溯回具体版本与负责人。在企业规模下，每个已注册的 agent、工具或技能都需要一个负责人、清晰的来源链路和审计轨迹。

AWS Agent Registry 同时解决这三点：它提供一个中心化、可搜索的目录，团队可以在其中注册 agent、工具与技能，发现整个组织中已有的资源，并通过访问控制、生命周期跟踪和审批工作流实施治理。

## 什么是 AWS Agent Registry

当 agentic 系统从少数几个工具增长到数百个时，找到已有的资源并信任你所找到的东西就成了瓶颈。AWS Agent Registry 缓解了这一瓶颈。它为团队提供一个统一、可治理的目录，内置语义搜索与访问控制，用于注册、发现和管理 AI agent、工具与能力。

在内部，Registry 由两个互补的平面构成：

- **治理平面（The Governance Plane）**。

治理平面即已注册的全部 agent、工具与技能。它被设计为其定义范围内的资源的权威存储，无论这些资源处于何种生命周期状态。

管理员在此配置决定资源如何被管理的规则，例如：

- **合规与安全信号** – 用于跟踪资源是否通过安全评审、是否满足监管要求，或是否带有已知风险的元数据。
- **发现策略** – 基于授权的搜索规则，根据使用者的角色或团队控制他们能看到哪些资源。
- **自定义元数据 schema** – 组织特有的字段（例如成本中心、数据分类、SLA 层级），用于统一团队描述其资源的方式。

随着时间推移，治理平面将呈现更丰富的治理信号，让管理员能在单一视图中了解其整个 agentic 生态的合规与安全态势。

- **发现平面（The Discovery Plane）**。

发现平面是消费者日常交互的界面。它只呈现已通过组织审批门槛的资源，是一个经过策展的高性能视图。

关键特征：

- **经过策展，而非全量** – 此处只出现经管理员或策展人批准的记录。草稿、被拒绝或影子资源对消费者不可见。
- **为规模而构建** – 支持高吞吐查询，使 agent 与开发者可以以编程方式搜索而不触发速率限制。
- **语义与词法搜索** – 消费者可以按意图（“帮我找一个用于工单路由的工具”）或按精确名称，在全部已批准的目录中查找资源。
- **信任信号而非治理细节** – 呈现的是经过汇总的合规与安全指标，其表达方式服务于「是否使用它」的决策，而不是原始治理数据。

两个平面合在一起清晰地分离了关注点：管理员通过治理平面获得全面的可见性与策略控制，而消费者通过发现平面获得快速、受治理的搜索体验，且只显示可供使用的资源。前文描述的部分功能属于前瞻性规划，将在后文详细说明。

### Registry 中可以编目哪些内容

Registry 支持四种记录类型：

- **MCP** – Model Context Protocol 服务器及其工具、资源与 prompt。
- **Agent** – 定义 agent 及其技能的 Agent2Agent（A2A）agent card。
- **Skill** – markdown 文件中的 agent 技能定义，以及相关代码与包。
- **Custom** – 自定义描述符，必须是有效的 JSON。

## 为 agentic 治理与协作专门构建

registry 为参与组织 agentic 战略的每一类角色提供专门构建的能力。这些角色包括建立防护栏的管理员、创建并发布资源的构建者，以及为多 agent 协作和复杂任务与工作流完成而使用这些资源的用户与自主 agent。

Registry 围绕四类用户设计：

- **管理员（Admins）** – 中心管理员负责搭建 registry、配置防护栏，并为 agentic 发现与治理建立流程。
- **发布者（Publishers）** – 构建 agent、工具与技能的开发者或非技术角色，他们允许自己的资源被更广泛地发现。
- **消费者（Consumers）** – 在组织内发现并使用已可用且已批准使用的 agentic 能力的开发者、业务用户或自主 agent。
- **策展人（Curators）** – 通过依据是否符合内部业务需求（例如财务、安全、合规 PoC）来批准或拒绝资源，策展 registry 中可供发现的 agent、工具与技能。

### 管理员与策展人的工作流

Registry 的核心是为企业规模现实而构建的治理模型。管理员可以在整个企业内创建并管理一个 registry，或管理多个 registry 实例，从而可以按业务部门、环境或合规要求轻松划出逻辑边界。每个实例都带有自己的访问策略、审批工作流与生命周期规则，因此各团队可以独立运作。每个 registry 实例都可以为发布能力的团队和使用能力的团队分别独立配置基于 OAuth 或基于 IAM 的认证。

管理员治理 registry 中一切内容的完整生命周期。这意味着配置带基于角色的审批人分配的审批工作流，由它管理从草稿到批准的各个状态转换。策展人充当人工在环的评审者，为每个 agent、工具或技能管理生命周期决策。当某项能力需要退役时，策展人可以在其生命周期的任何时点把记录转为 deprecated 状态。AWS CloudTrail 会捕获对 Registry 执行的每一个操作的完整审计轨迹。安全与合规评估可以作为审批工作流的一部分进行配置。

图 2：记录发布到 Registry 后由管理员执行的审批工作流

**步骤 1：CRUD Registry：** **管理员**通过访问 registry 管理界面（可通过 AWS Command Line Interface（AWS CLI）、SDK 或 AWS Console 使用）发起流程，执行**创建、读取、更新与删除（CRUD）**操作。这是搭建与维护 registry 本身的基础步骤。

**步骤 2：创建并管理审批工作流：** 与此同时，管理员**设计并配置审批工作流**，由它治理 agent 与工具提交的验证方式。其中可以包括设置安全扫描、去重以及其他验证检查。

**步骤 3：发布记录：** 记录被发布到 registry 中。管理员也可以直接添加记录，方式是显式指定活跃端点（registry 可以从这些端点获取元数据），或把完整记录直接发布到 registry。

**步骤 4：Amazon EventBridge 触发：** 记录提交并进入待审批状态后，registry 通过 **Amazon EventBridge** 发出一个事件，由 EventBridge 充当事件代理。该事件可以被路由到步骤 2 中设置的审批工作流。

**步骤 5：审批工作流：** 审批工作流应包含制衡检查，用于判定这些记录是否应开放给整个组织更广泛地发现。具体的制衡检查由管理员根据组织内部要求确定。

**步骤 6：批准与发现：** 在做出最终批准决定后（通过 API 或 Console 传达给 registry），registry 会把记录状态更新为 approved，并把它发布到 registry 的发现平面。

**步骤 7：消费者发现：** 浏览 registry 的消费者现在可以在 registry 的发现平面中找到该记录，该平面支持浏览以及语义或词法（混合）搜索。

#### 组织级自动检测

组织级自动检测解决了围绕影子 AI（Shadow AI）的担忧。管理员在 AWS Organization 层级启用一次端点检测，Registry 便会自动检测在 [AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)（Amazon Bedrock AgentCore 的一项能力）与 [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 上运行的 agent 与 MCP 服务器，检测范围覆盖组织中的每个账户。检测到的资源会出现在一个集中的「Detected Endpoints」视图中，并带有其标识符、端点与描述符元数据。管理员随后把特定账户（或整个组织单元）连接到一个中心 Agent Registry，检测到的资源便以草稿记录的形式流入，并遵循标准治理生命周期：评审、批准，然后发布到发现平面。这种关系是持续的：当某个已连接账户中部署了新 agent 时，它会自动出现在 Registry 中，无需发布团队采取任何操作。这避免了影子 agent，并为中央 AI 管理员提供了在规模化下执行治理所需的全面可见性。

### 发布

Registry 支持通过 Console、CLI 和 API 进行注册，因此团队可以选择适合自身开发流程的方式来发布 MCP 服务器、A2A agent、技能与自定义资源元数据。发布者可以把 registry 记录的更新直接集成到现有的持续集成与持续交付（CI/CD）pipeline 中，避免每次发布都要手工改动。提交之后，记录会随着评审人授予批准而走过已配置的生命周期状态（从草稿到待审批，再到 approved、rejected 或 deprecated）。

Registry 还可以使用**同步**功能直接从外部 MCP 或 A2A 服务器拉取元数据。它根据服务器的配置，使用 OAuth、IAM 或未认证访问进行连接，并自动同步记录元数据。

**步骤 1：发现 Registry** – 开发者使用自己的 **IDE 与 SDK** 构建 agent 或工具。他们首先与 **Registry** 交互，以发现已经注册了什么。

**步骤 2：开发者自控的 CI/CD pipeline** – 假设开发者的代码流入他们自己的 **CI/CD pipeline**，由它自动完成 agent 或工具的打包与注册准备工作。

**步骤 3：生成 agent card 与 MCP 定义 –** 可以把 CI/CD pipeline 设置为产出包含 agent 元数据、能力与规格的 **agent card**，或产出定义工具接口及其可达位置的**带端点 URL 的 MCP 服务器**。

**步骤 4：提交并创建 Registry 记录** – pipeline 在 **Registry** 中创建一条记录，然后提交以待审批。

**步骤 5-8：审批工作流过程 –** 如前一张图所述。

### 发现与使用

对消费者而言，发现建立在一个覆盖全部目录的语义搜索体验之上，通过 Search API 即可访问。对于自动化 pipeline 和 agentic 工作流，Search API 同时以 MCP 服务器的形式暴露，因此 agent 可以以编程方式查找并选择工具与技能。认证遵循与 Registry 其他部分相同的模式：OAuth 或 IAM，由管理员按实例配置。对于在封闭网络环境中运作的团队，则使用 [AWS PrivateLink](https://aws.amazon.com/privatelink/)，使 Registry 在不牺牲安全态势的前提下保持可达。

#### 从 IDE 中发现

Registry 把每个 registry 实例都暴露为一个 MCP 服务器。兼容 MCP 的 IDE（包括 Kiro 与 Claude Code）可以原生连接到它。这意味着开发者可以直接在自己的 IDE 中输入自然语言请求，例如*「帮我找一个用于问题工单的 MCP 服务器」*。IDE 会查询 Registry 中的特定 registry 实例，返回匹配的工具及其元数据与连接详情；如果开发者有访问权限，他们可以立即开始使用该工具，无需离开编辑器。

连接设置很轻量：IDE 使用动态客户端注册（DCR）在运行时与 Registry 建立信任关系。无需管理员预先配置 OAuth 凭证。开发者通过组织的身份提供方（例如 [AWS IAM Identity Center](https://aws.amazon.com/iam/identity-center/)）认证一次，IDE 便获得一个限定范围的访问 token。此后，搜索 registry、浏览元数据以及获取连接详情都在原地完成。

#### 从 Amazon Quick 中发现

正如开发者可以从 IDE 中发现 Registry 资源，业务用户与知识工作者现在可以直接从 [Amazon Quick](https://aws.amazon.com/quick) 中发现并调用这些资源。Quick 管理员把其租户连接到一个或多个 Agent Registry 之后，已批准的 agent 以及暴露 MCP 连接器的 MCP 服务器会出现在 Quick 的 Integrations 页面上。企业许可证用户可以浏览并搜索全部目录、查看工具描述与能力、为租户启用特定 agent，并把它们分享给相应的团队。终端用户随后通过 Quick Chat、Automations、Flows 和 Deep Research 访问这些 agent。这意味着组织不再需要在 Quick 内部重建已在别处存在的能力，一个受治理的目录同时支撑开发者和业务用户的体验。

## 状态转换

registry 中的记录会经历一个受治理的生命周期，其中包含多次状态转换，如下图所示。

![记录生命周期的状态转换：草稿、待审批、已批准、被拒绝与已弃用](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/31/ML-20739-5.png)

图 5：Registry 中记录生命周期的状态转换

- **发布者创建/更新 Registry 记录** – 发布者通过创建新的 registry 记录（或更新已有记录）发起流程，使其进入 **DRAFT** 状态。
- **发布者提交审批** – 发布者把草稿记录提交评审，使其转入 **PENDING_APPROVAL** 状态。
- **审批人更新状态** – 审批人审阅工作流结果并采取两种操作之一：**批准** – 记录进入 **APPROVED** 状态。**拒绝** – 记录进入 **REJECTED** 状态。或者，当 `auto_approve` 标记设为 `true` 时，记录会直接进入 **APPROVED** 状态。
- **发布者更新记录** *（可选循环）* – 当记录处于 **PENDING_APPROVAL** 或 **APPROVED** 状态时，发布者可以对其进行更新，这会把它送回 **DRAFT** 状态，重新开始提交流程。
- **策展人弃用记录** – 当记录不再需要时，策展人可以将其弃用，使其转入 **DEPRECATED** 状态。

## 企业级考量

当你在整个组织中推广 Registry 时，有几个决策会影响你如何搭建并规模化运营它。

### 单一 registry 与多个 registry

大多数团队首先面对的问题是：运行一个 registry 还是多个。单一 registry 提供最广的可见性：一个搜索入口，以及在构建新东西之前只需检查一处。但如果组织在 dev、staging 与 production 之间已有严格的隔离需求（多数受监管行业的公司都有），那么在 registry 层面映射这一边界才是正确做法。也有团队选择按业务部门拆分，尤其在涉及数据驻留（data residency）时。

需要权衡的几个因素：

- 如果合规要求强制物理隔离，就使用独立的 registry 实例。
- 每增加一个 registry，就多一份需要维护的东西，带着自己的 IAM 策略、标准执行与工作流。运营负担随实例数量增长。
- 如果没有良好的元数据与过滤机制，单个大型 registry 会变得嘈杂。按领域限定范围的多个 registry 更易于管理。
- 如果不同团队使用不同的授权模型，例如一个用 OAuth、另一个用 IAM，那么就必须设置多个 registry。

这里没有普遍正确的答案。它是可见性与隔离、可发现性与噪音、简单性与合规性之间的权衡。一个好的经验法则是：从满足隔离要求的最少 registry 数量开始，只有在出现具体需求时才进一步拆分。

### 治理工作流

Registry 并不附带内置审批工作流，而是提供 hook 来搭建组织专属的工作流。至少应做到：发布前检查重复，在任何工具、agent 或技能获批前运行安全扫描，并由人类审批人签字确认。策展人可以核实元数据是否完整、描述对编写团队之外的人是否说得通，以及该条目是否确实应归入 registry。起步阶段，在发布 CI/CD pipeline 中放一份检查清单，或使用基于 Slack 的审批流，都可以正常工作。

### 安全

并非所有能发现工具的人都应该能注册新工具。工具元数据可能包含对威胁行为者有用的内部端点或架构细节。要评估这些信息应放在一个广泛可读的 registry 条目中，还是应置于更严格的访问边界之后。审计是谁在查询 registry，以及查询频率。

## 后续规划

AWS Agent Registry 今天已正式可用，具备核心的发布、治理与发现工作流。展望未来，路线图围绕四个主题组织，每个主题都针对企业在 agentic 版图从数十个资源增长到数千个资源时面临的一类问题。

### 治理、安全与合规

批准某个 agent 或工具供组织使用是一个高风险的决策。但今天，可用于做决策的信息仅限于发布者提供的内容。组织必须投入并在内部构建用于治理的评估工作流，这是一笔可观的投入。策展人缺乏批准所需的信号，例如安全态势、合规状况，或是否已经存在近乎相同的资源。随着治理需求成熟，组织需要其 registry 主动参与治理过程，而不只是充当守门人。

Registry 将在审批工作流中呈现安全与漏洞评估、合规评估以及去重分析。这些能力由深度参与此类评估的 AWS 服务驱动，让策展人无需自建工具即可获得所需证据。带完整审计轨迹的资源版本管理，旨在让组织把每个资源的每次变更追溯回具体版本与负责人。对 agent 调用的集中策略执行，意在把 registry 的治理决策与运行时行为连接起来，闭合「已批准使用」与「按批准方式使用」之间的环路。

### 丰富的清单与元数据

registry 的价值取决于其中的内容。最难的问题之一并不是管理你所知晓的东西，而是管理团队部署却从未注册的 agent 与工具。影子 agent 孤立地构建、在缺乏监督的情况下运行，构成了企业治理中快速增长的盲区。

无论部署在 AWS 何处、跨哪些 AWS 服务，agentic 资源——无论是在 Amazon Bedrock AgentCore 上，还是在 [Amazon Quick](https://aws.amazon.com/quick)，以及 Amazon Elastic Compute Cloud（Amazon EC2）、Amazon Elastic Kubernetes Service（Amazon EKS）或 Amazon Elastic Container Service（Amazon ECS）这类服务上——都将被 Registry 自动检测到。我们计划通过联合（federation）合作把这一可见性扩展到运行在非 AWS 服务上的资源——无论是本地托管，还是基于云或 SaaS——从而使 registry 无论团队选择在哪里构建都能反映现实。除了完整性，我们还在投入提升元数据的丰富度：允许组织通过*自定义 schema*精确指定哪些信息对他们最重要，并在各记录中强制这一结构。最终状态是这样一个 registry：组织中的每一项 agentic 资源都被纳入、被充分描述，并被持续丰富，从而消除盲区，并为治理工作流提供所需的上下文。

### 搜索、发现与可观测性

今天的发现是二元的。如果你在某个 registry 上有搜索权限，你就能看到所有已批准的内容。这在规模较小时行得通，但当组织拥有数百条记录、横跨不同业务部门、团队与个人（以及 agent）、且各自具有不同的敏感级别、合规要求与受众时，就会失效。

我们将构建一种发现体验，让消费者在希望发现的地方，恰好找到与自己相关的内容，而不多不少。策略驱动的可见性意在控制哪些消费者身份可以看到哪些记录。除了过滤，我们还在扩展可发现的内容范围，依据客户最关注的资产类型——例如 prompt、模型与知识库等等。按 agent 与工具呈现的可观测性指标，结合用于影响分析的依赖图，将让团队不仅能发现资源，还能理解资源之间如何关联、表现如何，以及某个资源宕掉会破坏什么。对于希望不仅在组织内部、也向外部客户与合作伙伴展示其 agentic 能力的企业，我们还将支持跨组织的资源发现。

### 在客户所在之处满足他们

只存在于 AWS Console 中的 registry，只能触及需要它的人中的一小部分。构建者生活在 IDE 里。业务用户生活在生产力工具里。团队通过基础设施即代码（IaC）pipeline 工作。如果发现资源需要切换到 console 这个上下文，采用就会停滞。

我们正朝着这样的模型构建：registry 可以从客户已经在用的任何界面访问。这意味着与流行的 agentic IDE、生产力系统进行原生集成，并提供从 registry 记录到 AgentCore Gateway 与 AgentCore runtime 的直接部署路径。一个带 OAuth/SSO 认证的独立 Web 应用（无需 AWS Console）将服务更广泛的构建者社区。而对于正在构建网络的企业，公有 registry 将为其 agentic 能力提供一个店面，客户与合作伙伴无需任何 AWS 账户即可浏览。最终状态是：registry 成为发现骨干，为所有能发现与使用 agent 和工具的界面提供支撑，而不是一个你必须前往的目的地。

AWS Agent Registry 是为 agentic 时代构建可扩展且安全的基础设施的基础。我们从客户需求出发倒推，为未来而构建。

## 结语

在企业规模下，生产环境的 agent 与工具横跨团队、区域与业务部门。agent 与工具的治理和可发现性成为一等关注点。Registry 为组织提供一个统一、受治理的事实来源，配有语义搜索与可扩展的治理 hook，用于接入审批工作流、安全扫描以及与你的治理态势相匹配的生命周期策略。

无论你是注册第一个 agent/工具的开发者，还是设计 agentic 系统的架构师，AWS Agent Registry 都提供了扩展你的 agentic 版图所需的受治理基础。
