# Amazon 如何用 AI agent 支撑每天数十亿笔交易的合规筛查

在 Amazon，我们对全球业务及其子公司的客户和交易进行筛查，以遵守制裁规定和其他全球法律。未能遵守这些法律可能导致巨额罚款和声誉损失。Amazon 的 Compliance 团队开发了一套 AI 驱动的筛查与调查系统，把 Amazon 的合规流程转变为业界领先的解决方案：Amazon Compliance Screening，它每天在 160 多家全球业务中筛查约 20 亿笔交易，以防止被禁止的交易。我们执行多个司法辖区的制裁名单，包括但不限于美国财政部外国资产控制办公室（OFAC）的特别指定国民和被封锁人员名单（SDN 名单）以及英国的 His Majesty Treasury 名单（HMT 名单）。制裁执法持续加码，仅美国监管机构自 2023 年以来就开出了 20 亿美元罚单。在这一规模上管理合规，需要数千名人类专家按照行业标准/最佳实践审核被标记的交易并开展调查。然而，这种人力密集型方式造成了严重的瓶颈——人工审核周期可能需要数天，直接通过交易延迟、账户冻结和订单履约中断影响客户体验。在规模不断扩大的情况下，Amazon 必须在保持高准确率、降低合规成本并加速复杂调查的同时，应对复杂且不断演变的监管要求。

## 解决方案概述：三层智能合规系统

Amazon Compliance Screening 系统采用精细的三层方案，在速度、准确率与彻底性之间取得平衡：

**第 1 层 – 筛查引擎**：作为基础层，它使用先进的模糊匹配算法和借助 Amazon SageMaker 开发并部署的自定义向量嵌入模型，把每个输入实体的数据与制裁名单及其他政府名单上的实体进行比对。这一层针对高召回率做了优化，即使付出误报的代价也要捕获所有潜在匹配。

**第 2 层 – 智能自动化引擎**：使用传统机器学习模型滤除低质量匹配，大幅降低噪声。这一层通过分析匹配置信度信号来减少误报，让合规团队可以专注于真正的风险。

**第 3 层 – AI 驱动的调查系统**：使用部署在 Amazon Bedrock AgentCore Runtime 上的专用 AI agent，对剩余的高质量匹配进行综合评估。概括来说，这些 agent 系统性地收集相关信息，按照 Amazon Compliance 团队整理的标准调查作业程序（SOP）对其做整体分析，并生成附有建议的详细案件摘要。只有在少数情况下才需要人工介入：当 agent 因证据不足或出现超出标准调查参数的例外情形而无法得出结论时。

本篇博客聚焦第 3 层，探讨 Amazon Compliance 团队如何通过一系列基于 AWS 构建的 AI agent 打造其 AI 驱动的调查系统。

### 系统架构

当某个潜在匹配通过第 1 层和第 2 层后，系统会创建一个案件并将其路由到我们的 AI 驱动调查系统。随后由 agent 收集和分析信息，并产出包含风险评估和最终结论的完整调查报告。我们的调查员 AI agent 构建在 [Strands](https://strandsagents.com/) agent 框架之上，由托管在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的大语言模型驱动，并部署在 [Amazon Bedrock AgentCore Runtime](https://aws.amazon.com/bedrock/agentcore/) 上。系统使用多个 AI agent 协同工作，每个 agent 都使用专用工具与外部系统交互、访问数据并执行各自指定的功能。

### Agent 架构

我们的系统由多个 AI agent 组成，每个 agent 负责调查流程中特定的方面。

- **Name matching agent：** 分析跨多种语言和文字系统的姓名变体、音译以及文化命名习惯。该 agent 能识别“Abel Hernandez, Jr.”与“Hernandez Abel”可能指同一个人，并处理涉及昵称、婚前姓和别名等的复杂情形。它会处理包括阿拉伯文、中文、日文和西里尔文在内的非拉丁文字，同时理解不同文化中名与姓的顺序等命名习惯。例如，在调查“李明”（Li Ming）与“Ming Li”之间的匹配时，该 agent 能同时识别出音译差异以及中文与西方格式在姓名顺序上的不同约定。
- **Address matching agent：** 专注于地理数据，理解地址变体、缩写以及各国格式差异。它能识别“123 Main St., New York, NY”与“123 Main Street, New York City, New York”指的是同一地点。该 agent 处理各国地址格式与本地缩写，用地理空间数据校验地址，并检测可能的地址混淆手法。看这个例子：该 agent 可以判定“Flat No. 502, Sai Kripa Apartments, Plot No. 23, Linking Road, Bandra West, Mumbai – 400050, Maharashtra, India”与“Sai Kripa Apts., 5th Floor, Flat 502, 23 Linking Rd., Bandra (W), Mumbai, MH 400050″尽管格式不同，指向的是同一个地址。
- **Entity type inference agent：** 先通过数据聚合工具查看 Amazon 内部系统的数据，来判断输入实体的类型（个人或组织）。当在 Amazon 内部系统中找不到证据时，它会利用多种语言中的命名模式和企业标识（LLC、Inc.、Ministry）来判断该条目对应的实体类型（例如个人还是组织）。
- **Verified customer information (VCI) agent：** 检查客户（或其他当事方）提供的信息，例如身份证明文件、企业注册资料和账户验证记录。
- **Recommendation agent：** 综合所有 AI agent 的发现，进行风险加权分析，并基于所收集的证据生成附有详细论证的最终建议。它汇总所有调查 agent 的证据，依据多个因素做风险评分，并为建议生成详细论证。该 agent 以置信度把案件判定为误报或真实命中，产出包含全部收集到的证据、各 agent 的分析、风险评估以及带支持理由的明确建议的综合案件摘要。
- **Orchestration agent：** 协调所有 agent 之间的工作流。它位于这些 agent 之上，管理 agent 之间的依赖关系，根据案件复杂度优化调查顺序，在合适处处理并行执行，并在处理异常的同时监控 agent 进度。编排 agent 使用 Strands Graph Multi-Agent Pattern 实现，可依据图结构实现确定性的执行顺序。

### 工具

工具是扩展 agent 能力的主要机制，使 agent 能够与外部系统交互、访问数据并操作其环境。我们的 agent 使用多种工具——有些内置于 Strands（例如 ThinkTool），另一些则为特定需求而开发。Amazon Compliance Screening 系统使用以下自建工具：

- **Data aggregator tool：** 数据聚合工具充当数据聚合器，是连接我们 AI agent 与 Amazon 庞大数据生态的关键桥梁。这个数据聚合微服务从多个内部来源检索并整合信息，包括 Know Your Customer（KYC）系统、交易历史系统、账户验证记录、当事方档案信息和历史合规数据。
- **Maps tool：** 地图工具提供地理空间情报和地址校验能力。它执行地址校验与标准化、地理编码与反向地理编码、管辖区分析以及位置之间的距离计算。该工具集成了多个地理 API，帮助 agent 核实基于位置的信息并发现地址不一致。这项功能对地址匹配 agent 至关重要——它需要核实基于位置的信息、发现可疑的地址模式并理解实体之间的地理关系。
- **Open source data tool：** 开源数据工具聚合来自多个第三方数据提供方的公开信息，使调查过程中能够开展全面的开源情报收集。该工具连接各类专业数据源，包括企业注册数据库。

### 合规优先的设计

所有 agent 都被要求遵循严格指引以及 Amazon Compliance 团队整理的调查标准作业程序（SOP）。我们遵循这些准则，以确保 AI 的推理符合监管要求和公司政策。每一个决策和推理步骤都会被记录并保持可追溯，使我们能够审计完整的调查轨迹，并准确理解 AI 是如何得出结论的。我们实施了严格的检查，验证 agent 严格遵循其被分配的 SOP，从而让所有调查保持一致，不受案件量或复杂度影响。例如，建议 agent 在收到所有 AI agent（姓名匹配、地址匹配、实体类型推断 agent 以及 VCI agent）的结果之前无法执行；当 agent 的置信度分数低于我们设定的阈值时，案件会自动升级给人类调查员，并生成一个 human-in-the-loop 任务。

### 为什么选择 Strands 和 Amazon Bedrock AgentCore Runtime？

我们的 AI agent 使用 [Strands](https://aws.amazon.com/blogs/opensource/introducing-strands-agents-an-open-source-ai-agents-sdk/) 构建并部署在 Amazon Bedrock AgentCore Runtime 上。Strands 与 AgentCore Runtime 组合起来，提供了 agent 开发、会话管理、安全隔离和基础设施管理的强大能力，让我们的构建者能够专注于解决核心问题和多 agent 编排，而不必纠缠于复杂的实现细节。Strands 通过标准化的 Model Communication Protocol（MCP）和 Agent-to-Agent（A2A）构造，与 AWS 服务和外部工具实现无缝集成，同时整个 Bedrock 模型选择都可供我们使用。

AgentCore Runtime 的无服务器架构对我们难以预测的工作负载至关重要——制裁名单每天更新时，案件量会急剧飙升。AgentCore Runtime 会在流量高峰时自动扩容、在正常运行期间缩容，提供高效的计算资源利用，无需人工干预。

**结果与性能**

我们的 agentic AI 驱动调查系统通过显著改进改变了调查流程。AI agent 会同时分析数百个数据点，并遵循复杂流程。它们在历史决策上实现了 96% 的整体准确率，精确率 96%、召回率 100%，表现优于人类，并为超过 60% 的业务量自动完成决策。

## 可供借鉴的经验

基于我们构建 Amazon Compliance Screening 系统的经验，我们建议如下：

**从清晰的 SOP 开始：** 我们 AI agent 的成功在很大程度上取决于是否有定义良好的调查标准作业程序。在实现 AI agent 之前，我们投入了大量时间与合规团队合作，把调查流程文档化并规范化。这项前期投入后来被证明至关重要，因为 agent 的效果上限就是其所遵循流程的效果上限。

**迭代式 agent 开发：** 我们并没有同时部署所有 agent。我们先从姓名匹配 agent 开始，验证其性能，然后通过增加更多 agent 逐步提升复杂度。这种迭代方式让我们能够及早发现并解决问题，与相关方建立信任，并在扩展到更复杂的多 agent 场景之前，从 agent 设计中获得宝贵经验。

**平衡自主性与控制：** 在自主性与控制之间找到合适的平衡点至关重要。自主性过强会带来不可预测的行为——在早期迭代中，当姓名相似度看起来较低时，agent 会跳过地址核验，认为没有必要。控制过强则会限制效果。我们根据职能和风险采用不同方式。对于编排 agent，我们实现了 Strands Graph Multi-Agent Pattern 来强制确定性的执行顺序（先做实体类型推断，再做姓名匹配），保证了调查的 SOP 合规性与审计轨迹。对于姓名匹配 agent 这类 AI agent，模型驱动的方式提供了推理自主性，以处理复杂场景——阿拉伯语到英语的音译、西里尔文变体或中文罗马化——这些都需要通过语言模式进行动态推理，僵化规则无法做到。

**工具设计至关重要**：工具的质量与可靠性直接影响 agent 的表现。我们学会了以清晰的接口、完善的错误处理和详细的文档来设计工具，使 agent 能有效使用它们。一个设计良好的工具，决定了一个 agent 是持续产出有价值的洞察，还是在基础任务上挣扎。

**从第一天就做可观测性：** 从一开始就构建完善的日志、监控和调试能力至关重要。理解 agent 为何做出特定决策，对合规和持续改进都是必需的。我们可以追踪每一个 agent 动作、每一次工具调用和每一个推理步骤，这在故障排查、审计和优化 agent 行为方面被证明极具价值。

## 结论

Amazon 的 AI 驱动 Amazon Compliance Screening 系统通过自主 agent 精确地分析、推理并解决案件，应对复杂的合规挑战。只有在 agent 因证据不足或出现超出标准调查参数的例外情形而无法得出结论时，才需要人工介入。这种自动化优先的方式在保持准确性与可审计性的同时最大化效率——把人工调查完全留给需要细致判断的边缘案例。随着监管环境不断演变，我们的 agentic 方式提供了可扩展性，能够维持高合规标准，同时持续扩大自主案件处理的范围。
