## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 优化每任务成本，证明 Amazon Bedrock 上 agent 的 ROI

本系列的[第 1 部分](https://aws.amazon.com/blogs/machine-learning/managing-amazon-bedrock-costs-end-to-end-a-playbook-for-finops-and-platform-teams/) 搭起了控制 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 支出的运营模型：用 AWS Identity and Access Management (IAM) 主体标签和 Cost and Usage Report 2.0 做归因，用模型调用日志做可观测性，在三个层级强制执行，再配上定期复盘节奏。这一层回答“钱是谁花的”，也让你能拦住他们；但它回答不了这笔钱花得值不值。

本文回答第 1 部分有意留白的两个问题。第一：这个工作流为什么贵？要回答它，得按每任务成本而不是每 token 成本来思考。第二：agent 比原来的人类做得更好吗？要回答它，需要基线、受控实验，以及一张与决策挂钩的记分卡。

本文你会学到：一套计算模型真实成本的框架（含定价页看不到的四个隐性成本驱动因素）、通过缓存、路由和输出约束压低每任务成本的手法，以及用人类基线、留出实验和五维记分卡衡量 agent ROI 的一套方法。本文面向两类读者：掌握优化杠杆的应用与平台工程师，以及需要向管理层论证 agent 支出合理性的产品负责人和 FinOps 伙伴。

## 每任务成本，而非每 token 成本

每 token 单价便于快速比价，却反映不了你实际付的钱。公开费率算的是一个 token 的成本，账单算的是完成一项任务的成本。任务，是应用交给模型去做的一个完整工作单元：处理一封支持邮件、从一张发票里抽取字段，或回答用户的一个问题。任务从发起请求一直走到拿到可用结果，中间不管要调用多少次模型。

标价更低的模型，跑起来未必更省钱。便宜的模型可能把文本切出更多 token、在回复里塞满废话、误读你的 tool schema 而反复纠错，或者在作答前先烧掉几千个推理 token。这些成本，[Bedrock 定价页](https://aws.amazon.com/bedrock/pricing/) 上一个都不会列。

### 四个隐性成本驱动因素

有四个模型特性，决定了那个公开费率落到你的工作负载上到底要花多少钱。

#### 分词器效率

token 不是单词，各模型之间也不等价。每个模型系列用的分词器和词表都不同，同一段文本、代码或 JSON 载荷切出来的 token 数也不一样。假如 Model A 的标价低 15%，但它的分词器对你的数据要多切 40% 的 token（结构化 schema 和数值数组里很常见），那反倒是 Model B 更便宜。非英文文本上差距更大：许多分词器会把非拉丁文字切成的 token 数，膨胀到同等英文内容的两到三倍。

#### 输出对齐与冗余度

输出 token 的单价通常比输入 token 贵 3–5 倍（比例因模型系列而异，见 [Bedrock 定价页](https://aws.amazon.com/bedrock/pricing/)）。无视“return only raw JSON”这类格式约束的模型，会让你为填充词付这笔输出溢价；严格照格式指令走的模型，少生成一些这类更贵的输出 token，就把钱省下来了。

#### agentic 循环效率

agentic 工作流把成本算法整个改写。[Tool use (function calling)](https://docs.aws.amazon.com/bedrock/latest/userguide/tool-use.html) 让模型调用外部函数，于是需要多轮循环：分析 prompt、决定调用工具、等待观察结果、生成答案。每一轮都会把完整对话历史和工具结果当作输入 token 重新发一遍。走四轮的模型（每轮重发的上下文载荷还更大），成本远高于一次就完成的模型。

#### 推理开销

很多模型支持 [extended thinking](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-reasoning.html)，在给出可见答案前先走一遍思维链。推理 token 按输出 token 计费，所以在一段 200 token 的回答前先想掉 2,000 token 的模型，会按 2,200 收费。有些模型把推理过程隐去，钱照收。先把推理关掉，只有当基准测试显示出值得这份开销的质量差距时，再打开它。

### 每任务成本：一个具体算例

![五个成本维度的雷达图：Model A 仅在价格优势上领先，Model B 在其余四项领先](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/02/ML-21540-1.png)

图 1：在五个成本维度上比较两个模型。标价只是决定实际成本的五个因素之一

设想一个 agentic 工作流：读取一封 750 词的客户邮件、抽取实体、调 API 核验账户状态，再输出严格 JSON。下面的对比用的是示意价格（务必拿自己的数据和当前的 [Bedrock 定价](https://aws.amazon.com/bedrock/pricing/) 做基准）：

| **指标** | **Model A（标价较低）** | **Model B（标价较高）** |
| --- | --- | --- |
| 输入标价 | $0.50 / 1M tokens | $1.00 / 1M tokens |
| 输出标价 | $1.50 / 1M tokens | $3.00 / 1M tokens |
| 分词器效率（第 1 轮输入） | 1,500 tokens | 1,000 tokens |
| 输出冗余度（最终回复） | 450 tokens | 150 tokens |
| 所需 agentic 循环 | 3 轮（纠错） | 1 轮（zero-shot） |
| 各轮累计输入 token | 6,150 | 1,000 |
| 各轮累计输出 token | 750 | 150 |
| 总任务成本 | $0.0042 | $0.00145 |

Model A: (6,150 x $0.50 + 750 x $1.50) / 1,000,000 = $0.0042

Model B: (1,000 x $1.00 + 150 x $3.00) / 1,000,000 = $0.00145

![流程图：Model A 需要三轮纠错、反复重发上下文（$0.0042）；Model B 一轮完成（$0.00145）](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/02/ML-21540-2.png)

图 2：为什么标价更高的模型反而便宜 65%。每多一轮都要重发不断变大的上下文载荷，账单随之叠加

**为什么价格翻倍的模型反而便宜 65%：** 三个因素叠加。Model A 的分词器把这封邮件多切出 50% 的 token，把每一次输入载荷都撑大；它往 JSON 里塞填充词，输出 token 翻了三倍；还跟 tool schema 对不上，得多走两轮纠错，每轮都把越来越长的历史重发一遍。

### 每个成功任务的成本

上面的例子假定两个模型最终都能成功。生产环境里不会这么理想，而失败很少是免费的。公式如下：

对于重试直到成功的工作流：

`cost per successful task = cost per attempt / success rate`

对于失败即升级的工作流：

`cost per successful task = cost per attempt + (1 - success rate) x escalation cost`

启用 [prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html) 后，输入还会再分成三档：按基础费率计费的未缓存输入、低于基础费率的缓存读取、高于基础费率的缓存写入。

### 在自己的工作负载上实测

到底哪个模型更便宜，只有拿自己的数据跑基准才看得出来。[Amazon Bedrock model evaluation](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html) 负责这件事里“质量”那一半：定义准则、上传 prompt 数据集，拿到带自动指标、可选人工复核的评分结果，而且不需要自建基础设施。

不过光有质量分数算不出账单。另有三个 Bedrock 功能，提供你据以计价的 token 数与轮次数：

- [CountTokens](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_CountTokens.html) 返回给定模型对给定载荷会计费的输入 token 数，且不必真跑推理。在往生成上花钱之前，这是比较各候选模型分词器效率（驱动因素 #1）最省钱的法子。
- 模型调用响应里带一个 `usage` 块，含 `inputTokens`、`outputTokens`、`cacheReadInputTokens` 和 `cacheWriteInputTokens`。把单个任务各轮次里的这些值累加起来，就得到前面“每次尝试成本”公式的四项。有个坑：启用缓存后，`inputTokens` 只统计未缓存的 token，所以总输入量是 `inputTokens + cacheReadInputTokens + cacheWriteInputTokens`。把它们加总能看清体量，但计价要分开算，因为三者的费率不同。在整个使用过程中要多次复核这一点，并按当前实际负载来设缓存检查点。随着应用推进、工具逐渐过时，缓存检查点会发生漂移；这意味着三个月后漂移发生时，你往缓存里写的内容会更多。持续评估数据、把缓存用到最优，就成了降低成本的主要杠杆。
- [Model invocation logging](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html) 把每次调用的 token 数写入 Amazon Simple Storage Service (Amazon S3) 或 Amazon CloudWatch Logs，于是你能拿真实生产流量、而非抽样，来度量“到完成用了几轮”。用 [request metadata](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-request-metadata.html) 给调用打标，就能按团队、功能或实验切分这些日志里的 token 数。但要注意，这些是日志字段，不是成本分配标签，永远不会出现在 AWS Cost Explorer 或你的 Cost and Usage Report 里。[Application inference profiles](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-application-inference-profiles.html) 倒能进入这两处，粒度是每天一种用量类型——这个粒度做费用分摊刚好，算每任务成本就太粗了。把日志里的 token 数乘以公开费率，得到的是近实时的估算，不是发票；除非你另行建模，它不会反映承诺折扣、批量定价或预配置吞吐量。在把它当账单之前，先跟你的 Cost and Usage Report 对账。

### 降低每任务成本：四个杠杆

四个驱动因素各对应一个杠杆，也都有详细文档。[Prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html) 砍掉让 Model A 变贵的重发上下文，因此是 agentic 路径上收益最大的一处。[Intelligent prompt routing](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-routing.html) 把简单请求送到同一系列里更便宜的模型。一个 [tool schema](https://docs.aws.amazon.com/bedrock/latest/userguide/tool-use.html) 配上 maxTokens 上限，比自然语言指令更稳地压住冗余；extended thinking 则一直关着，直到基准测试证明它值回票价。[Batch inference](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference.html) 让批量单轮任务的费率减半，代价是不能用工具调用和多轮交互。

## 证明 agent ROI：先刻画人类基线

高效不等于有价值。一个 agent 可以优化到极致，却依然不值得跑。决定预算的那个问题是：agent 比原来的人类做得更好吗？

### 先记录人工流程

做 agent ROI 最容易犯的错，就是还没描述人工工作流就急着证明价值。在构建或放大 agent 之前，先用运营语言把当前流程写下来：什么触发了工作、涉及哪些人工角色、交接点在哪、怎样算完成。这听着像走流程，其实是度量设计。下游每一个埋点决策——什么算一次运行、什么算成功、人的时间花在哪里——都从这份描述里推导出来。

### 在 agent 上线前测好基线

流程写清楚后，在一个有代表性的时间窗里测人类基线：完成时长、排队时长、实际投入工时、重开率、升级率、每任务成本、结果质量。基线必须在 agent 上线之前测，不能事后凭记忆倒推。回溯出来的基线会系统性地偏向 agent：人只记得平均情况，忘了那些处理得飞快的案例。

### 把工作流当实验来埋点

基线有了之后，从第一天起就把 agent 工作流当实验来埋点。每次运行都拿到一个 trace ID，每个关键步骤都可观测。一条工作流运行记录把模型调用之上的一切汇总成一个可分析的单元：

```
{
  "runId": "run-8f3a2c",
  "workflow": "renewal-risk-summary",
  "agent": "renewal-agent",
  "principalArn": "arn:aws:sts::123456789012:assumed-role/BedrockRuntimeRole/gw-alex",
  "team": "sales-ai",
  "costCenter": "CC-2041",
  "experiment": {
    "variant": "treatment",
    "holdout": False,
    "promptVersion": "v14",
    "policyVersion": "2026-07"
  },
  "ops": {
    "latencyMs": 41200,
    "retries": 1,
    "toolCalls": 6,
    "humanApprovals": 1,
    "humanMinutes": 35,
    "escalations": 0
  },
  "econ": {
    "inputTokens": 48210,
    "outputTokens": 3105,
    "cacheReadTokens": 31500,
    "estCostUsd": 0.87
  },
  "outcome": {
    "status": "success",
    "accepted": True,
    "reopened": False,
    "revenueEventId": "opp-44121"
  }
}
```

有三个字段值得特别说明：

**experiment 块：** 在运行时创建时盖上，并传递到 Bedrock [request metadata](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html#bedrock-runtime_Converse-request-requestMetadata)，这样模型级与工作流级的记录就能干净地对上。

**humanMinutes：** 多数团队会漏掉、却也最需要的一个字段。没有它，“活是 agent 干的”这种说法，就悄悄抹去了人类花在复核上的那 35 分钟。

**revenueEventId：** 让日后做收入归因成为可能的挂钩。记下来几乎不花成本，事后却补不回来。

一条准则：如果工作流遥测答不出业务问题，埋点就不完整。

### 把成本与结果关联起来

把 [invocation logs](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html) 落到 Amazon S3（见第 1 部分）、工作流运行记录存进分析库之后，一次 join 就能产出真正要紧的指标。Amazon Bedrock 日志记录的是 token 而不是美元，所以先按 token 数和你的模型费率表给每次调用定价，建一张按 run ID 聚合的视图，再用 [Amazon Athena](https://aws.amazon.com/athena/) 查询：

```
SELECT
  w.workflow,
  w.variant,
  COUNT(*) AS runs,
  SUM(IF(w.outcome_status = 'success', 1, 0)) AS successes,
  ROUND(SUM(c.est_cost_usd) /
    NULLIF(SUM(IF(w.outcome_status = 'success', 1, 0)), 0), 2)
    AS cost_per_success,
  ROUND(SUM(w.retries) * 1.0 /
    NULLIF(SUM(IF(w.outcome_status = 'success', 1, 0)), 0), 2)
    AS retries_per_success,
  ROUND(SUM(w.human_minutes) /
    NULLIF(SUM(IF(w.outcome_status = 'success', 1, 0)), 0), 1)
    AS human_min_per_success
FROM workflow_runs w
JOIN invocation_costs_by_run c ON c.run_id = w.run_id
GROUP BY w.workflow, w.variant
ORDER BY cost_per_success DESC
```

> 注意：上面查询里的列名和关联键只是示意。请对照你的调用日志 schema 和工作流遥测存储核实，具体实现可能有差异。

每个成功结果的成本、每次成功的重试数、每次成功的人力分钟数——这三个数字，才经得起一位持怀疑态度的 CFO 追问。按每次调用算成本，会便宜了那些爱打转的 agent；按每次成功算就不会。注意按 variant 分组：同一条查询按实验组拆开，就是 ROI 对比。

### 正确地比较 agent 与人类

最可信的评估是 A/B 测试或留出测试。受控的实验组与对照组，把 agent 辅助的工作流拿来和人类基线比，且不会把市场、季节或组织变动混进结果里。

面向客户或与收入挂钩的工作流，就在访客、线索、客户或案例这一层做随机化；内部工作流（支持运营、编码助手）则用匹配队列：团队、仓库组或 pod。

比较覆盖四个维度：

**效率：** 完成时长、省下的工时、排队时长降幅。

**质量：** 错误率、批准率、重开率、升级率。

**成本：** 每任务成本、每个成功结果的成本、总服务成本。

**业务价值：** 转化率提升、留存率提升、扩张率、每名销售或每个工作流的收入。

如果 agent 改善了一个维度，却明显拖累另一个，结果就含糊了，部署还得再调。

## 收入：最难衡量的指标

效率提升是 ROI 故事里最好证明的部分，收入影响就难多了，而管理层恰恰是照着这个指标拨预算的。在贴近收入的工作流里，要衡量 agent 是否改善了转化率、响应时长、交易推进或每名销售的收入。要把归因于 agent 的增量收入，和整体业务增长势头分开，留出测试是最可靠的办法。

当收入提升确实成立，话题就变了：组织不再问 Bedrock 账单是不是涨了，而是问多出来的这笔支出，有没有换来业务产出的实质增长。

### 记分卡

从我们与客户合作的观察看，一套扎实的运营模型并不需要五十个指标。真正管用的，是一张与决策挂钩的小记分卡，按固定节奏为每个生产 agent 复盘。

下面的阈值是起点，不是定规。请拿自己的机群数据和组织情况去校准。

| **维度** | **指标** | **绿色** | **黄色** | **红色** |
| --- | --- | --- | --- | --- |
| 采用率 | 活跃用户 / 目标用户 | >70% | 40-70% | <40% |
| 质量 | 无需返工即完成的任务 | >90% | 75-90% | <75% |
| 效率 | 每周省下的工时 | >目标 | 目标的 50-100% | <目标的 50% |
| 成本 | 每个成功结果的成本 | ≤预算 | 预算的 1-1.5 倍 | >预算的 1.5 倍 |
| 业务影响 | 相对基线的 KPI 提升 | 显著 | 轻微 | 无或为负 |

绿色代表扩量：agent 跑赢基线，同时满足成本与质量阈值。黄色代表调优：有苗头，但还得打磨。红色代表下线或重做：agent 在烧钱，却拿不出足够可衡量的价值。肯真的把一个红色 agent 下线，才让记分卡其余部分站得住脚。

## 结论

本文讲了：怎样把四个隐性成本驱动因素（分词器效率、输出对齐、agentic 循环效率、推理开销）算进去，得出模型的真实成本；怎样通过提示缓存、模型路由、输出约束和批量推理压低每任务成本；以及怎样靠测人类基线、把工作流当实验埋点、把成本与结果关联、跑留出对照，来证明 agent ROI。

成本优化那一半回答“为什么这么贵、怎么修”，ROI 那一半回答“agent 是不是比原来的人类更好”。再加上第 1 部分的运营模型（归因、观测、执行、优化、运营），三者合成一套完整框架：看得见谁花了钱，讲得清为什么，减得掉浪费，也说得明剩下那些为什么该留。

想上手，先用 [Amazon Bedrock model evaluation](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html) 拿自己的 prompt 给头部候选模型跑基准；再从 `usage` 块或你的 [invocation logs](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html) 里取到 token 数和轮次数，按当前 [Bedrock 定价](https://aws.amazon.com/bedrock/pricing/) 计价，最后除以成功率。做 ROI 度量，可查阅 [Well-Architected Agentic AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentcost07.html) 里的 agent 成本治理最佳实践。

如果你还发现了别的降低每任务成本、或衡量 Amazon Bedrock 上 agent ROI 的手法，欢迎在评论里告诉我们。
