# 在 AWS 上使用 AI 缩短医疗理赔审核时间：EXL Medical IDP 解决方案

保险理赔审核员在每个案件上要花费超过 100 分钟来人工审核医疗记录。构建在 AWS 上的 EXL AI 驱动的医疗智能文档处理（IDP）解决方案改变了这一流程。它将 IDP 与领域特定的大语言模型（LLM）相结合，以企业级规模提取、总结和查询医疗信息。

## 挑战：医疗记录复杂、体量庞大且至关重要

在保险理赔裁定和人寿核保中，医疗记录是每一项决策的基础。理赔审核员和核保人员必须审核这些往往长达数百页的记录，以评估有效性、确定赔付金额或做出核保决策。

挑战不仅在于体量。医疗记录是非结构化的，充满专业临床术语，需要审核人员把关于患者病情及其随时间演变的零散数据点连接起来。这些文档本身涵盖数十种类型：脊椎按摩治疗记录、诊断检查、急诊就诊记录、手术报告、医生会诊记录、处方药报告、精神科评估、化验结果、独立医疗检查（IME）报告和同行评审等等。

这类审核需要深厚的医疗领域专业知识、持续的专注和解释性判断。鉴于这种复杂性，该过程缓慢、依赖人工且容易出现不一致。不同的专业人员会以不同方式解读相同的医疗数据。其后果是真实的：理赔结算延迟、评估中的准确性问题、赔付成本增加、客户体验变差，以及监管审查加剧。

## 解决方案：两个 AI 应用，一条智能 pipeline

EXL 通过将两个互补的 AI 应用组合成一个端到端解决方案来应对这一挑战，该方案托管在 AWS 上：

- **Xtrakto.AI** 负责文档摄取、拆分、分类、提取、富化和后处理。它是一个与模板无关的 IDP 应用，使用计算机视觉、自然语言处理（NLP）和 agentic AI 工作流，从各类文档中提取结构化数据，而无需预先配置模板。
- **EXL Insurance LLM** 提供领域智能层：医疗摘要、自然语言查询、带可追溯性的深度推理，以及结构化输出生成。它基于保险和医疗领域数据进行了微调，理解临床术语、ICD（International Classification of Diseases）和 CPT（Current Procedural Terminology）代码、诊断-治疗关系，以及理赔和核保工作流的具体需求。

这两个应用共同构成一条自动化、可扩展的 pipeline，将原始医疗文档转化为供理赔审核员、核保人员和护理协调员使用的可执行情报。

EXL 在 AWS 上构建该解决方案，以便将模型开发和生产推理置于同一屋檐下，并保持一致的安全控制。[Amazon SageMaker AI](https://aws.amazon.com/sagemaker/ai/) 为领域特定的 EXL Insurance LLM 提供全托管训练和推理环境：多 GPU 微调、与生产隔离的实验环境，以及随理赔量伸缩的实时推理端点。[Amazon Bedrock](https://aws.amazon.com/bedrock/) 则通过单一 API 按需访问通用基础模型来形成互补。借助这一访问能力，EXL 可以为每项任务应用合适的模型：用微调后的 Insurance LLM 进行领域推理，用通用模型处理更广泛的语言任务，而无需管理额外的基础设施。这两项服务都在由 AWS Identity and Access Management（IAM）划定范围的访问控制内运行，这对处理受保护健康信息的工作流至关重要。

## 架构概览

该解决方案完全运行在一个 AWS 区域内，上游和下游客户端应用通过安全的 API 连接。架构遵循 11 步流程，从文档摄取一直到输出交付，并有一个独立的模型开发环境用于持续改进。

该 pipeline 构建在以下 AWS 服务之上：

- [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 用于安全的摄取和结果交付 API（步骤 1 和 11）。
- [Amazon Cognito](https://aws.amazon.com/cognito/) 用于请求身份验证和授权（步骤 2）。
- [AWS Step Functions](https://aws.amazon.com/step-functions/) 作为编排引擎，协调子请求、路由和提取工作流（步骤 3）。
- [Amazon Textract](https://aws.amazon.com/textract/) 和 [AWS Lambda](https://aws.amazon.com/lambda/) 用于文档预处理：机器可读性检查、OCR、文件类型转换和文本嵌入生成（步骤 4）。
- [Amazon SageMaker AI](https://aws.amazon.com/sagemaker/ai/) 用于机器学习（ML）模型推理，以及基于训练好的领域模型进行数据检索（步骤 5）。
- [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 和 [Amazon Relational Database Service (Amazon RDS)](https://aws.amazon.com/rds/) 用于使用内部和外部参考数据库进行数据富化（步骤 6）。
- Amazon SageMaker AI 实时推理端点为 EXL Insurance LLM 提供服务，用于验证、摘要、查询和 agentic 推理（步骤 7）。
- [Amazon Bedrock](https://aws.amazon.com/bedrock/) 提供对通用基础模型的按需访问，这些模型在通用推理任务上补充领域特定的 EXL Insurance LLM。有关各 AWS 区域支持的模型，请参阅 [Amazon Bedrock 中各 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。
- AWS Lambda 用于生成多种格式的输出（步骤 8）。
- [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 用于应用和模型监控仪表板（步骤 9）。
- [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 作为用于文档存储和处理输出的中央数据湖（步骤 10）。
- Amazon SageMaker AI（在隔离的模型开发环境中）用于[模型训练、微调](https://docs.aws.amazon.com/sagemaker/latest/dg/jumpstart-fine-tune.html)和实验（步骤 0）。

## 在 Amazon SageMaker AI 上构建 EXL Insurance LLM

该解决方案的一个关键差异化优势是 EXL Insurance LLM：一个领域特定的大语言模型，专门针对涉及医疗记录的保险理赔工作流进行了微调。EXL 没有依赖缺乏保险和医疗领域专业知识的通用 LLM，而是在 Amazon SageMaker AI 上构建了一个专门训练的模型，并在保险特定的 NLP 任务上与通用模型进行了基准对比。

### 为什么微调而不是 prompt？

像 GPT-4 或 Claude 这样的通用模型具备广泛的语言理解能力，但缺乏保险理赔裁定所需的专业词汇、推理模式和工作流意识。保险理赔涉及用于医疗记录标注的多种不同标记类型、领域特定的摘要格式（经济性和非经济性损害赔偿），以及谈判指导生成。这些任务需要深度的领域适配，仅靠 prompt 无法在大规模下稳定实现。

### 训练数据与准备

EXL 从九年的保险理赔运营中整理了训练数据，包含超过 13,500 条记录，涵盖结构化数据库记录和非结构化医疗文档。AWS 上的数据准备 pipeline 包括：

- **使用 Amazon Textract 进行光学字符识别（OCR）：** 从扫描的医疗 PDF 中提取文本，同时在行和词级别保留位置上下文，这对维持医疗发现之间的关联至关重要。
- **垃圾页检测：** 一个自动化分类器，用于识别并移除无关或扫描质量差、会降低训练质量的页面。
- **数据去标识化：** 符合 HIPAA 要求的去标识化流程，在训练前移除受保护健康信息，使模型不会学到敏感的患者数据。
- **多标记合并：** 将每页的多个标记引用分组为统一的训练样本，有助于防止模型在单个页面包含多项医疗发现时产生不一致的输出。

### SageMaker AI 上的微调方法

EXL 在 Amazon SageMaker AI 上采用了[参数高效微调](https://huggingface.co/docs/peft/en/index)（PEFT）与[低秩适配](https://arxiv.org/abs/2106.09685)（LoRA）。该方法在不修改基础模型全部参数的情况下高效地适配模型，在保持性能的同时降低计算成本。训练使用了：

- 采用 NVIDIA GPU 的 SageMaker AI 训练实例上的多 GPU 配置。
- 高级并行（数据并行和模型并行），以优化大规模训练吞吐。
- NVIDIA [NeMo](https://developer.nvidia.com/nemo-framework) 框架，用于构建和管理训练 pipeline。
- 与生产推理隔离的 SageMaker AI 环境（架构中的步骤 0），使模型实验不会影响线上工作负载。

### 性能结果

在 EXL 的内部基准测试中，微调后的 EXL Insurance LLM 在关键理赔工作流任务（标注、摘要、问答和推理）上表现出强劲性能，评估使用了自动化指标（BLEU、ROUGE、BERTScore、METEOR）以及由三位保险领域主题专家进行的盲审。

有关方法和详细结果，请参阅 [EXL 关于 Insurance LLM 的白皮书](https://www.exlservice.com/insights/white-paper/ai-powered-insurance-workflows-operationalizing-llms-with-exl-insurance-llm)。

借助这条 pipeline，EXL 将医疗记录审核时间从数天缩短到数小时，并在关键阶段进行 human-in-the-loop 验证，帮助在缩短周转时间的同时保持质量。

## 工作原理：从文档到决策

该 pipeline 使每份文档经过七个阶段，从摄取一直到结构化输出交付。以下各节逐一介绍每个阶段。

### 阶段 1：文档拆分与分类

当上游应用通过基于 Amazon API Gateway 构建的 Ingestion API 提交提取请求时，pipeline 便开始了。文档通过多种渠道、以多种格式到达。AWS Lambda 函数使用 Apache Tika 进行解析和 OCR 后规范化来完成初始文件处理，并将原始文档存储在 Amazon S3 中。

在通过 Amazon Cognito 完成身份验证后，编排引擎（AWS Step Functions）接管，根据输入创建子请求并将内容路由到适当的处理模块。

Xtrakto.AI 的分类引擎与模板无关，并基于推理。它不依赖文档布局或预定义模板，而是使用少样本和迁移学习方法，根据含义和上下文对内容进行分类。因此，系统可以用有限的训练样本对新文档类型进行分类。打包文件（包含多个附件的电子邮件）会被拆分为单独的子文档，每个子文档都被路由到相应的下游提取模块。

### 阶段 2：带置信度评分和可追溯性的数据提取

这是 pipeline 的核心，Xtrakto.AI 的提取能力在此汇聚，涵盖预处理、计算机视觉和领域特定提取。

#### 预处理

文档会经历机器可读性检查、使用 Amazon Textract 的 OCR、文件类型转换和文本嵌入生成。这些步骤作为 Lambda 函数运行，由 Step Functions 协调。部署在 Amazon SageMaker AI 上的计算机视觉模型（CNN、RCNN）处理像素级图像数据，以解决扫描医疗记录中常见的质量问题：分辨率低、褶皱或污渍带来的噪点、倾斜，以及手写与印刷内容混杂。这些模型可以识别重复页面、检测有界和无界表格、识别提取区域、检测签名，并解读条形码和二维码。

约 25–30% 的文档包含手写内容，从结构化的表单填写（复杂度低，约占手写体量的 50–60%）到半结构化注释（约 15–20%），再到完全自由形式的医生笔记（约 15–20%）。每种类型都需要专门的处理。

#### 基于上下文的提取

Xtrakto.AI 不会配置输入模板来在特定位置查找信息。提取是基于上下文的：

- 对于结构化和半结构化文档，计算机视觉（CV）模型识别区域并提取键值对。内置的领域本体结合语义相似度 NLP 模型，将提取的键映射到业务特定字段。
- 对于高度非结构化的内容（医生笔记、手术报告），提取通过基于 LangGraph 的 agentic 工作流进行编排。该工作流将提取分解为结构化的推理步骤，使用机器阅读理解和问答模型进行有针对性的字段级提取，同时由 transformer 模型为模糊情况提供上下文理解。

Amazon SageMaker AI 承载用于提取的推理模型家族。传统方法（SVM、梯度提升）处理结构化分类任务，而使用领域特定医疗和保险数据增强的 transformer 架构（BERT、GPT、BART 变体）负责上下文提取。

#### 置信度评分与 human-in-the-loop

每个提取的字段都会获得 0-100 的置信度评分。低于可配置阈值的字段会通过 EXL Xtrakto.AI 验证界面路由给人工验证员进行核验。这些反馈会随着时间持续提升模型准确率。

### 阶段 3：数据富化与集成

提取的数据会使用存储在 Amazon DynamoDB 和 Amazon RDS 中的内部和外部参考数据库进行增强。这一富化步骤会根据 ICD-10、CPT 和 Healthcare Common Procedure Coding System（HCPCS）库验证提取的代码，规范化日期和术语，并解决跨字段一致性问题。富化后的数据会被存回 Amazon S3 数据湖，供下游消费。

### 阶段 4：智能摘要

EXL Insurance LLM 在此接管，由 Amazon SageMaker AI 上的推理端点提供服务。跨越数百页的复杂医疗记录会被浓缩为针对用户需求量身定制的结构化摘要。

摘要引擎提供了灵活性：用户可以根据自己的工作流选择短、中或长摘要。Insurance LLM 会提取、标注、总结并呈现最相关的临床信息，同时保留文档的原始上下文和叙事流。

通过反馈机制，用户可以对摘要进行评分和纠正。这些纠正会进入 Amazon SageMaker AI 上的模型微调，持续提升摘要质量。

### 阶段 5：自然语言查询

除了摘要之外，用户还需要针对医疗记录提出具体问题，并获得精确、有来源的答案。该查询能力由 Amazon SageMaker AI 上的 Insurance LLM 驱动，支持三种模式：

- **预定义 FAQ**，用于各类理赔中的常见问题。
- **捆绑问题**，将相关查询分组并一起触发以进行批处理。
- **开放查询**，使用日常语言，让用户无需复杂的搜索语法即可检索特定信息。

Insurance LLM 理解每个查询背后的意图，并基于底层文档数据提供准确的答案。它可以同时处理多个查询，因此在体量大的运维场景中也很实用。

### 阶段 6：带可追溯性的深度推理

对于需要临床判断支持的复杂病例，该解决方案提供了具备完整可追溯性的深度推理能力：

- **来源级可追溯性：** 每个问答响应和摘要都会链接回确切的源数据或文档片段，使审核人员能够对照原始记录验证 AI 生成的洞察。
- **覆写与反馈：** 用户可以通过编辑生成的摘要或答案来纠正不准确之处，并对输出质量进行评分。这些纠正会进入持续的模型改进，形成一个良性循环：系统越用越准确。

> 在决策必须可审计且有据可依的受监管环境中，这种可追溯性至关重要。

#### 负责任 AI 与生产防护措施

由于该工作流处理受保护健康信息并产生 AI 生成的临床和理赔洞察，负责任 AI 控制是内置于部署中的，而不是事后添加的。生成式输出在到达审核人员之前会经过内容过滤和 grounding 检查，因此摘要和答案始终锚定在源记录上并保持在政策范围内。来源级可追溯性使每个输出都能审计回原始文档，human-in-the-loop 验证为低置信度结果把关，符合 HIPAA 要求的去标识化流程在整个 pipeline 中保护患者数据。这些控制共同帮助该解决方案在受监管的医疗健康环境中安全交付。

### 阶段 7：结构化输出与可视化

最后阶段通过 AWS Lambda 函数生成输出，并通过 Results API（Amazon API Gateway）交付结果。下游应用以其所需的格式检索处理后的数据：

- **可导出的 PDF 报告：** 结合提取结果、摘要和问答输出的统一 AI 驱动报告。
- **有序的文档索引：** 结构化、无需滚动的导航，可即时访问大型医疗记录中的关键章节。
- **带超链接的时间线图表：** 按年份组织的可视化诊断历史，并附有用于查看详细临床洞察的链接。
- **多种导出格式：** JSON、XML、CSV、平面文件，并可配置输出 schema 以匹配下游系统要求。
- 输出数据存储在 Amazon S3 数据湖中，Amazon CloudWatch 提供端到端监控仪表板，覆盖模型性能、提取准确率、处理吞吐量和系统健康状况。

## 真实世界影响：大规模临床病例管理

一家大型医疗健康支付方在临床病例管理上面临重大运营挑战。与前面描述的理赔审核员类似，该支付方的护士和护理协调员在每个病例上也要花费超过 100 分钟，这里花的是手动数据检索、验证和临床摘要准备的时间。信息分散在多个系统中：电子健康记录、护理管理系统、理赔系统和扫描的医疗文档。

该组织实施了 EXL Medical IDP 解决方案，用统一的智能 pipeline 取代这些碎片化的手动工作流。

**部署内容：**

- 跨多个临床系统（EPIC、CarePort、Predictal、文档管理系统）的单一 API 主导编排（通过 Amazon API Gateway 和 AWS Step Functions）。
- 智能提取 agent 处理来自不同临床来源的多种格式数据（JSON 和 Fast Healthcare Interoperability Resources（FHIR）包、扫描的 PDF）。
- 使用 Amazon SageMaker AI 上的 Insurance LLM，对药物、既往病史、诊断、手术、化验和护理记录进行 LLM 驱动的提取和分类。
- 使用行业标准医疗代码进行自动验证，在保持可追溯性的同时解决跨来源的数据冲突。
- 自动生成临床摘要，并进行 human-in-the-loop 验证。

**结果：**

- **减少人工投入：** 自动化的数据摄取、提取、验证和摘要减少了每个病例所花费的时间，让护理团队能够专注于患者护理。
- **缓解运营瓶颈：** 标准化、AI 生成的临床摘要消除了在多个系统间手动导航造成的延迟。
- **加快成员外联：** 完整、经过验证的病例摘要更快可用，支持更快速的外联和更主动的护理管理。
- **在不增加人员编制的情况下提升临床带宽：** 生产力提升直接转化为护士和护理协调员更高的病例处理能力。
- **提升准确率与合规性：** 依据行业标准代码进行验证、来源级可追溯性和 human-in-the-loop 复核，帮助在受监管的医疗健康环境中维持数据完整性。

## 结论

医疗记录处于关键保险和医疗健康决策的中心，然而从中提取情报的过程几十年来在很大程度上仍是手工的。EXL Medical IDP 解决方案表明，情况不再需要如此。

通过将 Xtrakto.AI 与模板无关的文档处理与 EXL Insurance LLM 的领域智能相结合，EXL 打造了一个覆盖完整生命周期的解决方案，从原始文档摄取到智能提取、摘要、查询和结构化输出交付。该 pipeline 运行在包括 Amazon API Gateway、Amazon Cognito、AWS Step Functions、[Amazon Textract](https://aws.amazon.com/textract/)、[Amazon SageMaker AI](https://aws.amazon.com/sagemaker/ai/)、[Amazon Bedrock](https://aws.amazon.com/bedrock/)、Amazon S3、Amazon CloudWatch 和 Amazon DynamoDB 在内的 AWS 服务上。

该解决方案背后的关键原则是增强而非取代。通过基于置信度的路由、human-in-the-loop 验证和持续反馈闭环，人类专业知识始终处于核心位置。AI 负责体量和重复性的模式识别。人类负责判断和例外情况。
