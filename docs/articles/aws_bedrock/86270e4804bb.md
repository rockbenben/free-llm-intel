# 在 Amazon Quick 中下调用户角色

高效地管理访问权限，是在 Amazon Quick 中维持安全且协作顺畅的环境的重要一环。Quick 支持灵活多样的用户管理选项，以适应不同的身份类型和组织需求。你可以通过 Quick Identity 原生地开通用户，也可以通过 AWS IAM Identity Center 或 Active Directory 这类企业身份提供方来管理用户。这些系统允许按职能和安全要求分配并分组 Admin、Author、Reader 等用户角色。当团队成员加入、转岗或离开组织时，管理员必须确保过渡平滑，既不干扰业务工作流，也不留下安全缺口。

定期的访问审查对维护 Quick 环境的安全很重要。计划每月或每季度审计一次用户角色，确认每个人都拥有恰当的权限。当团队成员的职责发生变化时，主动把他们 dashboard 和分析资源的所有权转移出去，避免出现无主资源。这一做法是 [AWS Well-Architected Framework](https://aws.amazon.com/architecture/well-architected/) 推荐的做法，有助于为业务关键的可视化保持连续性。

在这篇文章中，我们聚焦一项具体但重要的用户生命周期任务：下调用户角色。

## 为什么要下调？

最小权限原则在 Quick 管理中尤为适用。用户只应拥有其具体职能所需的访问权限。下调用户角色是落实最小权限的关键一环。当一个用户的职责不再需要创作或管理能力时，就应相应地降低其角色，以缩小安全暴露面。

Quick 的定价也是按角色划分的：Author 和 Admin 按每用户固定月费计费，而 Reader 采用按会话计费。对于把只消费 dashboard 的用户开通成 Author 的组织，把这些用户调整为 Reader 角色可以显著降低成本。当前定价详情参见 [Amazon Quick 定价页](https://aws.amazon.com/quicksight/pricing/)。

如果需要在 Amazon Quick 内置角色之外做更细粒度的控制，可以考虑用 [Custom Permissions](https://docs.aws.amazon.com/quicksight/latest/user/custom-permissions-profiles.html) 来补充角色分配，它在某个角色层级内限制特定能力。Amazon Quick 与 [AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 的集成提供了额外的权限边界，与基础角色体系互为补充。

## 本文的范围

虽然具体步骤取决于用户身份类型，但本文主要面向 Amazon Quick Identity 用户（也称为 Quick 托管用户）。通过 IAM Identity Center 或 Active Directory 认证的用户，其角色变更通常由外部身份提供方的组映射来管理。如果你的环境使用 IAM Identity Center，下调角色只要把用户从一个 IdC 组移到另一个组（例如从 Quick-Admins 组移到 Quick-Readers 组），不需要逐级下降的序列。

尽管 Amazon Quick 控制台并没有为所有角色转换提供直接的下调路径（具体来说，你无法通过控制台界面直接从 Admin 降到 Reader，或从 Author 降到 Reader），但存在两种可靠的解决方案：一种是手工删除并重建的方法，另一种是使用 AWS Command Line Interface（AWS CLI）的方法。我们会逐一介绍这两种技术，帮助你在团队演变过程中维持恰当的访问管理。

## 前提条件

开始之前，请确认你有一个活跃的 AWS 账户，并且对 Amazon Quick 具有管理员访问权限。如果你打算使用 CLI 方法，需要在你的机器上[安装并配置 AWS CLI](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html)。另外，先准备一份需要变更角色的用户清单会更有帮助。

## 了解 Amazon Quick 的角色

Amazon Quick 提供两个订阅层级，各自有不同的一套角色：

| **订阅** | **角色** | **能力** |
| --- | --- | --- |
| **Amazon Quick Enterprise** | Admin Pro、Author Pro、Reader Pro | 完整 BI + AI 功能（agents、topics、Q&A、stories、生成式摘要） |
| **Amazon Quick Sight**（仅 BI） | Admin、Author、Reader | 传统 BI 创作与消费 |

控制台不提供从任何 Author 层级下调到任何 Reader 层级的直接方式。`update-user` API 也强制同样的约束，会拒绝直接下调并返回 “You cannot downgrade a user role” 错误。

下面的截图展示了 Amazon Quick Suite 的用户管理页面，控制台中没有提供把用户从 Author 层级降到 Reader 层级的直接操作。这也说明了为什么需要本文介绍的几种方法。

图 1：Amazon Quick Suite 用户管理页面

CLI 逐级下降的方法对**传统的仅 BI 角色**（Admin、Author、Reader）稳定有效，遵循如下序列：

Admin > Author > Restricted Reader > Reader

同样的序列对 Pro 用户也适用，只要中间步骤使用传统角色。例如，Author Pro > Author > Restricted Reader > Reader Pro 可以成功完成。

## 变更前的重要注意事项

无论用哪种方式实施角色变更，都有几个重要因素需要记住。首先，在做出变更前，确认清单中的所有用户当前都是 Admin 或 Author 用户。尝试下调权限本就更低的用户可能导致错误。即使使用 CLI 方法，资源所有权的问题依然适用。被下调的用户将无法再编辑他们此前拥有的资源。对于使用 CLI 方法的较大组织，考虑从 CSV 文件读取用户邮箱地址，而不是硬编码。如果你使用 [AWS CloudShell](https://aws.amazon.com/cloudshell/) 而不是本地 CLI 安装，可以省略 AWS Region 的指定，因为 AWS CloudShell 会自动使用你当前控制台的 Region 上下文。

## 转移资产所有权（先做这一步）

在删除用户之前，必须确保他们拥有的资产（例如 dashboard、数据集和分析）已被妥善重新指派。这能防止中断，避免留下无主资源。如果该用户是 Author，请核实其是否拥有数据集或 dashboard，并按照此处所述的资产重新指派步骤操作。在 Amazon Quick 中处理资产所有权转移主要有三种方式。

### 选项 1：主动把所有权转移给另一位管理员

控制力最强的做法是在删除用户之前手动重新指派所有权。为此，进入 Quick 中的每一项资产，选择 **Share**，并把另一位管理员指为共同所有者。用这种方式，你可以精确决定由谁接手每一项资源，对于影响面大的 dashboard 或数据集尤其有用。虽然在大型环境中这会比较耗时，但它让你能按照团队的结构与职责灵活地分配资产。

下面的截图展示了某项资产的 **Share** 对话框，在其中你把另一位管理员添加为共同所有者，从而在原用户被移除之前完成所有权转移。

图 2：把资产所有权转移给另一位用户

### 选项 2：使用 Admin 页面上的 Amazon Quick 批量资产转移

如果该用户拥有大量资产，手动方式就会效率低下。这时你可以使用 Quick 管理（Admin）区域中的 **Manage assets** 功能。通过该工具，管理员可以批量转移所有权，或一次更新多项资产的共享权限。它极大地简化了重新指派流程，尤其是在用户离职或组织调整时。关于如何使用该功能的更多细节，参见官方文档 [Managing assets in Amazon Quick](https://docs.aws.amazon.com/quicksight/latest/user/manage-qs-assets.html)。

### 选项 3：把资产共享给一个 Quick 用户组

另一种有效策略是把资产共享给用户组。对于 Quick Identity 用户，你可以创建一个 Quick 组，把相关团队成员加入，然后把 dashboard 或数据集共享给该组而不是单个用户。如果你的账户与 IAM Identity Center 或 Active Directory 集成，等价的组会在这些系统中创建和管理，Quick 会使用那些外部组来做访问控制，而不是 Quick 托管的组。这样，即使某个具体用户被删除，对共享资源的访问依然保持不变。这是一种有韧性的做法，减少了将来重新指派所有权的需要，也有助于在动态变化的团队中保持一致的访问。

## 手动方法：删除并重建用户

虽然手动删除并重建不是最高效的做法，但它是在无法使用 CLI 的环境中的一个选择。这种方法要完全移除该 admin 用户，然后以 reader 权限重建。把 Author 下调为 Reader 时同样适用这种手动方法，只不过通常不像资产所有权那么麻烦。

因为这种方法要求先删除用户账户再以较低角色重建，所以充分的准备至关重要，以避免丢失有价值的资源、打断工作流。在继续之前，请确认你已完成上一节所述的资产所有权转移。

### 步骤 1：删除 admin 用户

转移完所有资源的归属后，登录 AWS Management Console 并进入 Amazon Quick 服务。在那里选择你的头像图标，然后依次选择 **Manage Quick** 和 **Manage users**。找到你要下调的 admin 用户后，点击其名字旁的删除图标，并在提示时确认删除。这会彻底移除他们当前对系统的访问。

如果你此前没有转移全部资源，Quick 会弹出一个所有权转移对话框，提示你选择另一位管理员来接收该用户所有资源的所有权。从列表中选择合适的管理员，然后选择 **Delete and transfer** 确认转移。这个内置的转移机制有助于避免产生无主资源，但它会把所有内容转移给单一管理员。若要更细粒度的控制，请使用前面提到的主动方式，把资源有策略地分配给不同团队成员。

如果你跳过了主动转移，下图所示的删除对话框允许你在账户被移除之前，把该用户的全部资源重新指派给某一位管理员。

图 3：删除用户时内置的资源转移

### 步骤 2：以 Reader 角色重建用户

成功删除用户后，留在 Users 页面并选择 **Invite users**。输入该用户的邮箱地址，并从可选角色中选择 **Reader**。发出邀请，让用户以新的、更受限的权限重新加入 Quick。

### 步骤 3：验证角色变更

用户接受邀请之后：

- 确认其权限已更新为 **Reader**。
- 验证他们只能查看 dashboard 和报表。
- 确认他们无法修改或创建内容。

## CLI 方法：逐级下降的角色转换（推荐）

如果你更倾向使用 AWS CLI 或 AWS CloudShell，可以用编程方式改变用户的角色。由于 Quick 要求角色变更必须按特定顺序进行，你无法从任何 Admin 直接转换到任何 Reader。你必须逐级经过中间角色。

### 重要说明

- 把 `<your-account-id>` 替换为你的 AWS 账户 ID。
- 把 `<user-name>` 替换为该用户的用户名。
- 把 `<user-email>` 替换为该用户的邮箱地址。
- 如果你在 CloudShell 之外使用 AWS CLI，请指定 `--region` 参数。
- `--role` 的取值必须与 API 角色名完全一致（见前表）。

### 示例：传统路径（Admin 到 Reader）

**步骤 1：** 把角色从 Admin 改为 Author：

```
aws quicksight update-user \
  --aws-account-id <your-account-id> \
  --user-name <user-name> \
  --namespace default \
  --email <user-email> \
  --role AUTHOR
```

**步骤 2：** 把角色从 Author 更新为 Restricted Reader：

```
aws quicksight update-user \
  --aws-account-id <your-account-id> \
  --user-name <user-name> \
  --namespace default \
  --email <user-email> \
  --role RESTRICTED_READER
```

**步骤 3：** 把角色从 Restricted Reader 改为 Reader：

```
aws quicksight update-user \
  --aws-account-id <your-account-id> \
  --user-name <user-name> \
  --namespace default \
  --email <user-email> \
  --role READER
```

## 下调之后：复查 Limit Profiles 和 Custom Permissions

角色变更不会自动调整 Limit Profiles 或 Custom Permissions 配置。两者都独立于用户角色而存在，你在任何一次下调之后都应当复查。

- **Limit Profiles** 控制每个用户在索引存储、agent 小时数等资源上的上限。如果被下调的用户此前被分配了适配其 Admin 或 Author 角色的配置，请重新指派一个适合 Reader 的 limit profile，以免过度分配资源。细节参见 [Limit Profiles 文档](https://docs.aws.amazon.com/quicksight/latest/user/limit-profiles.html)。
- **Custom Permissions** 在某个角色层级内限制特定能力。一个分配给 Author 的配置在 Reader 上可能不会按预期生效。要么在最后一步 CLI 操作中取消应用（使用 `--unapply-custom-permissions`），要么分配一个为 Reader 层级设计的配置。

## 批量更新多个用户的脚本

使用下面的脚本来更新多个用户。

```
#!/bin/bash

# Define AWS account details
AWS_ACCOUNT_ID="<your-account-id>"
REGION="<your-region>"

# Load users from file (format: username,email per line)
# Lines starting with # are treated as comments
INPUT_FILE="users_to_downgrade.txt"

while IFS=',' read -r username email; do
  # Skip comments and empty lines
  [[ "$username" =~ ^#.*$ || -z "$username" ]] && continue

  echo "Processing user: $username"

  # Role transition stages
  for ROLE in AUTHOR RESTRICTED_READER READER; do
    RESULT=$(aws quicksight update-user \
      --aws-account-id "$AWS_ACCOUNT_ID" \
      --user-name "$username" \
      --namespace default \
      --email "$email" \
      --role "$ROLE" \
      --region "$REGION" 2>&1)

    if [ $? -ne 0 ]; then
      echo " ERROR at $ROLE: $RESULT"
      break
    fi

    echo " Transitioned to $ROLE"
    sleep 3
  done

  echo "Role update completed for $username."
done < "$INPUT_FILE"

echo "All user role updates processed!"
```

### 脚本功能

该脚本完成以下事情：

- 从外部文件读取用户名和邮箱地址（支持以 # 开头的注释）。
- 分三个阶段更新角色：Admin > Author > Restricted Reader > Reader。
- 错误处理：某一步失败就停止该用户的后续转换。
- sleep 命令为变更生效留出时间。

运行脚本时有几点需要注意：

- 运行前确认用户当前是 Admin 或 Author 用户。
- 使用真实的 Quick 用户名，在联合身份（federated）环境中它可能与邮箱前缀不同。
- 在 AWS CloudShell 中无需指定 Region。
- 你可以修改脚本，从 `list-users` 导出的 CSV 文件加载用户。

## 用户访问管理的最佳实践

为了让你的 Quick 环境保持安全且井井有条，请遵循以下最佳实践：

- 定期审查用户角色（每月或每季度审计）。
- 在变更角色之前转移资源所有权。
- 遵循最小权限原则。
- 使用 Custom Permissions 配置在角色层级内做细粒度控制。
- 为增强韧性，把资源共享给组而不是个人。
- 使用 AWS Identity and Access Management 提供额外的权限边界。

## 清理

完成用户角色变更后：

- 移除所有测试用户。
- 确认没有遗留意料之外的资源。
- 删除临时 CLI 脚本或用户清单文件。
- 再次核对最终的用户权限。

## 结语

在这篇文章中，我们探讨了两种在 Amazon Quick 中下调用户角色的方法：手动删除并重建，以及灵活的 AWS CLI 方式。这些策略能帮助你高效且安全地管理团队访问权限。

对于使用 IAM Identity Center 的环境，角色变更通过 IdC 组重新指派来管理，不需要本文所述的逐级下降序列。若要更多治理控制，可以了解用于功能级限制的 [Custom Permissions](https://docs.aws.amazon.com/quicksight/latest/user/custom-permissions-profiles.html) 和用于内容级隔离的 [Restricted Folders](https://docs.aws.amazon.com/quicksight/latest/user/restricted-folders.html)。
