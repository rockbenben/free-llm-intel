# 用 SageMaker SDK v3 实现边缘侧覆盖全设备群的计算机视觉生命周期

全设备群的计算机视觉模型生命周期管理，这个问题在质量检测的概念验证一成功就冒出来了。一台相机配一个模型没问题。接着工厂要求在 40 条产线上得到同样的结果，每条产线上有好几台相机，而每台相机看到的世界都不一样：角度不同，同一块不锈钢表面的反光不同，开着哪扇厂房的门也决定了环境光有多少。在我们参与过的生产部署中，用汇总素材训练出来的单个模型在足够多的单台相机上表现不佳，最后每台相机都配上了自己微调过的模型。于是真正的问题不再是「把一个模型训好」，而是「训练、评估、版本化并交付成千上万个模型，而且每一个都不需要有人类介入」。

本文更新了 2023 年系列文章[在边缘构建用于视觉质量检测的端到端 MLOps 流水线](https://aws.amazon.com/blogs/machine-learning/build-an-end-to-end-mlops-pipeline-for-visual-quality-inspection-at-the-edge-part-1/)中提出的模式，以适配当前的 [Amazon SageMaker](https://aws.amazon.com/sagemaker/) Python SDK v3。它用 Amazon SageMaker Neo 取代了此后被弃用的 Amazon SageMaker Edge Manager 来做边缘优化。我会讲解一条双分支的 Amazon SageMaker Pipeline：它为每台相机训练一个异常检测器和一个缺陷分类器，并设有质量门禁来拦下表现不佳的模型。流水线中的 SageMaker Neo 编译步骤确保每个注册的模型都随附一份针对设备优化的产物；AWS Step Functions 编排层则负责控制设备群训练的节奏。所有东西都用 AWS Cloud Development Kit (AWS CDK) 部署，在合成数据上跑完一次完整流水线大约花费 $0.07 的计算费用。

完整示例可在 [aws-samples GitHub 仓库](https://github.com/aws-samples/sample-sagemaker-fleet-cv-pipeline)中找到。

## 方案概览

下面的示意图展示了示例中覆盖全设备群的模型生命周期。编排层对再训练请求排队并限制并发量。每台相机各自有一条训练流水线，负责准备数据、训练并评估一个异常检测器和一个分类器，并产出带版本的模型产物供边缘设备使用。

![方案架构：SQS FIFO 队列触发 AWS Lambda，后者启动一个带 Amazon DynamoDB 信号量做并发控制的 Step Functions 状态机。该状态机启动一条 13 步的 SageMaker Pipeline，包含并行的入口步骤（Preprocess、Fetch Latest Anomaly、Fetch Latest Classifier）、带 ONNX 评估的双训练分支、质量门禁、Neo 编译以及 Model Registry 注册。编译后的产物落到 S3。完成与失败都汇入同一个 SNS 主题。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/19/ML-20483-1-1.png)

图 1：方案架构

训练这半边是一条按相机参数化的 SageMaker Pipeline，每次执行跑 13 个步骤。三个入口步骤并行运行：Preprocess、Fetch Latest Anomaly 和 Fetch Latest Classifier。流水线先预处理该相机的图像，并为每条分支取回该相机最近一次获批的模型，然后训练两个模型。第一个是一个小型卷积自编码器，学习正常产品长什么样，并通过重建误差标记异常。第二个是微调过的 ResNet18 分类器，用来确认缺陷。每条分支都把自己的模型导出为 ONNX，用留出数据评估导出的产物，再通过质量门禁。过了门禁之后，模型会用 SageMaker Neo 针对配置的边缘目标编译，然后才注册进 SageMaker Model Registry。结果是，每个获批的模型包都带有一份设备就绪的编译产物。模型包把相机 ID 作为元数据携带，各分支的 warm-start 取回会按它过滤，因此再训练总是从该相机自己的历史继续。

编排这半边负责控制设备群的节奏。再训练请求进入 Amazon Simple Queue Service (Amazon SQS) FIFO 队列，AWS Lambda 函数为每个请求启动一次 Step Functions 执行。每次执行在启动自己的流水线之前，先通过 DynamoDB 信号量取一个名额，这样一拥而上的请求就会以稳定的速率排空，而不是一齐启动。完成情况发布到 Amazon Simple Notification Service (Amazon SNS)，运维层面的失败则经由一条 Amazon EventBridge 规则进入同一个主题，并保留原始错误信息。

系统的产出是带版本、经过质量门禁、按相机划分的模型产物。Model Registry 保存可移植的 ONNX，S3 保存该模型经 Neo 编译的构建结果——那是一个针对设备优化的共享库，由 DLR runtime 加载，而不是 ONNX。两者都可以直接配合工厂使用的任何交付方式。

## 前置条件

部署这个示例需要具备以下条件：

- 一个有权创建 AWS Identity and Access Management (IAM) 角色的 AWS 账户。
- 一个 Amazon Simple Storage Service (Amazon S3) 存储桶。
- 一个 Amazon Elastic Container Registry (Amazon ECR) 仓库。
- 栈中用到的 SageMaker AI、AWS Step Functions、AWS Lambda、Amazon Simple Queue Service (Amazon SQS)、Amazon Simple Notification Service (Amazon SNS)、Amazon EventBridge 和 Amazon DynamoDB 资源。
- Python 3.10、3.11 或 3.12，以及 Docker。
- AWS CDK CLI 2.1131.0 或更高版本。

更早的 CLI 版本在与较新 `aws-cdk-lib` 交互时会因云组装 schema 不匹配而失败。无需申请提升服务配额。编排层默认最多同时放行 5 次流水线执行，这能让并发的 SageMaker 训练作业保持在账户的标准配额之内。

如果你要部署到 CLI 默认区域以外的 AWS 区域，请把 `AWS_REGION`、`AWS_DEFAULT_REGION` 和 `CDK_DEFAULT_REGION` 三个变量都写在部署命令本身上，而不是写进 shell 配置文件，例如 `AWS_REGION=us-east-2 AWS_DEFAULT_REGION=us-east-2 CDK_DEFAULT_REGION=us-east-2 cdk deploy --all`。CDK CLI、Boto3 和 AWS Command Line Interface (AWS CLI) 各自从有重叠但并不完全相同的变量集合里解析区域，一旦不一致就会产生令人困惑的半成品部署。给命令加前缀只会为这一次调用设置这三个变量，你自己默认的区域不受影响。

## 用 SDK v3 定义训练流水线

本节的代码摘自仓库里的 CDK 应用，而不是独立脚本；它在 `cdk deploy` 期间运行——那时栈会合成出流水线定义。环境准备和部署命令稍后见「部署并运行示例」一节。SDK v3 把 SageMaker Python SDK 重组为若干模块化包，下面这些 import 展示了新的库结构：

```
from sagemaker.train import ModelTrainer
from sagemaker.train.configs import InputData, Compute, OutputDataConfig
from sagemaker.core.training.configs import MetricDefinition
from sagemaker.serve.model_builder import ModelBuilder
from sagemaker.mlops.workflow.pipeline import Pipeline
from sagemaker.mlops.workflow.steps import ProcessingStep, TrainingStep
from sagemaker.mlops.workflow.model_step import ModelStep
from sagemaker.mlops.workflow.condition_step import ConditionStep
from sagemaker.core.workflow.conditions import ConditionGreaterThanOrEqualTo
from sagemaker.core.workflow.functions import JsonGet
```

安装 `sagemaker>=3.0.0,<4` 会把 `sagemaker-core`、`sagemaker-train`、`sagemaker-serve` 和 `sagemaker-mlops` 作为独立包一并拉取。v2 中分散在 `Estimator` 构造函数参数里的训练配置，如今变成传给 `ModelTrainer` 的强类型配置对象。下面是异常分支的 trainer，原样摘自示例：

```
anomalib_trainer = ModelTrainer(
    training_image=custom_training_image_uri,
    compute=Compute(
        instance_type=training_instance_type.to_string(),
        instance_count=1,
    ),
    base_job_name="cv-pipeline-anomalib-train",
    sagemaker_session=pipeline_session,
    role=role_arn,
    hyperparameters={
        "program": "train_anomalib.py",
        "model_name": "autoencoder",
        "image_size": "256",
        "num_epochs": "3",
        "batch_size": "16",
        "learning_rate": "0.001",
    },
    input_data_config=anomalib_input_data,
    output_data_config=OutputDataConfig(
        s3_output_path=run_prefix("anomalib-training")
    ),
).with_metric_definitions(
    [
        MetricDefinition(
            name="image_auroc",
            regex=r"validation:image_auroc=([0-9]*\.?[0-9]+)",
        ),
    ]
)
```

`anomalib_input_data` 从上游步骤属性接入四个通道（`train`、`validation`、`test`、`pretrained_model`），`run_prefix` 则把每条 S3 路径限定到流水线执行 ID 上，使并发的设备群运行不会互相冲突。两者都在仓库里。

当流水线活在一个 CDK 应用里时，有两个 v3 的行为很关键，而它们都没有在更新日志里以破坏性变更的形式出现。第一，SDK v3 在构建流水线定义时，会拿真实的 IAM 去校验流水线的执行角色。这项校验发生在合成阶段，而不是执行阶段。CDK 应用无法在一次部署里同时创建角色和流水线，因为 SDK 校验时角色还不存在。这与 `cdk bootstrap` 是两回事——后者为每个账户和区域一次性准备 CDK 工具链资源，你的账户里可能早就做过了。示例自身采用的两阶段部署由一个上下文开关驱动，而这个开关恰好同名。第一轮带上 `-c bootstrap=true` 会创建角色、存储桶和 ECR 仓库，第二轮则基于已经存在的角色来合成流水线。嵌在流水线定义里的角色 Amazon Resource Name (ARN) 也必须是一个具体的字符串，而不是未解析的 CDK token。

第二，v3 的角色校验器在模拟 ECR 拉取权限时并不带上资源 ARN，因此一个限定到单个 ECR 仓库的执行角色会校验失败，即便它在运行时完全可用。出于这个原因，示例中的角色带了一个范围更宽的 ECR 授权。

最后是示例采用的一个 v3 习惯：用 `PipelineSession(default_bucket=your_bucket)` 构造流水线，会把 SDK 管理的上传（比如步骤代码）导向流水线自己的存储桶，这样所有产物都集中在一处，执行角色的权限也只需要覆盖一个存储桶。（给角色授予访问 SDK 默认存储桶的权限同样可行，但这种做法更整洁。）

## 与缺陷数据特性相匹配的质量门禁

每个训练好的模型在注册之前都要评估，而且评估针对的是导出的 ONNX 产物，而不是内存中的 PyTorch 模型。这个区别很关键：你把关的产物就是你交付的产物，因此导出环节的问题绝不可能让一个坏模型混过一场看起来一切正常的训练。

异常分支的门禁是 AUROC 不低于 0.8。分类分支的门禁同时看两个指标，而指标的选择由缺陷数据的决定性特征决定：严重的类别不平衡。在这个示例里大约 90% 的图像是良品，这对产线来说是现实的。在这种分布下，单看准确率毫无意义——一个对每张图都预测「良品」的模型能拿到约 0.9 的分数，却一个缺陷都抓不到。平衡准确率（各类别召回率的平均值）修正了这一点，但它也有自己的盲区：一个对良品召回率完美、对缺陷召回率只有 20% 的模型，得分依然是 (1.0 + 0.2) / 2 = 0.6。所以门禁要求同时满足：平衡准确率不低于 0.6，且缺陷召回率不低于 0.5。

```
step_check_classifier = ConditionStep(
    name="CheckClassifierQuality",
    conditions=[
        ConditionGreaterThanOrEqualTo(
            left=JsonGet(
                step_name=step_eval_classifier.name,
                property_file="evaluation",
                json_path="balanced_accuracy",
            ),
            right=min_accuracy,
        ),
        ConditionGreaterThanOrEqualTo(
            left=JsonGet(
                step_name=step_eval_classifier.name,
                property_file="evaluation",
                json_path="defect_recall",
            ),
            right=min_defect_recall,
        ),
    ],
    if_steps=[step_compile_classifier, step_register_classifier],
    else_steps=[step_fail_classifier],
    depends_on=[step_eval_classifier],
)
```

一个 `ConditionStep` 会把它的条件取「与」，因此两个条件都必须通过。阈值是流水线参数，每次执行都能调整，无需重新部署。如果某个门禁没过，`FailStep` 会把这次执行标记为失败，该分支的模型也就永远不会进入 registry（两条分支各自独立设门禁，所以另一条分支的模型仍可能注册成功）。设备群会继续为该相机提供上一个获批的模型。

训练代码从另一侧处理同一个不平衡问题。分类器是一个带 ImageNet 权重和二分类头的微调 `resnet18`。在每台相机各自的数据集规模下，微调预训练权重正是防止模型塌陷到多数类的原因。训练代码用 `WeightedRandomSampler` 按类别频率的倒数来平衡训练批次，而损失函数保持不加权。把加权损失和加权采样叠加使用，会朝少数类过度校正。

## 在流水线内部用 SageMaker Neo 做边缘编译

注意前面代码里门禁的 `if_steps`：过了门禁之后先执行编译，注册则依赖编译结果。两个训练脚本都导出带动态批次轴的 ONNX。质量门禁在 ONNX Runtime 下给这些导出的产物打分，然后由 `CompileAnomalibNeo` 或 `CompileClassifierNeo` 步骤把通过门禁的产物交给 [SageMaker Neo](https://docs.aws.amazon.com/sagemaker/latest/dg/neo.html)。不变式是：先设门禁，再编译，最后注册。只有同时为设备群的边缘目标编译成功的模型，才会成为 Approved 状态的模型包，因此 registry 绝不会登记一个设备跑不起来的模型。

编译步骤把三个容易出错的细节封装了起来。Neo 要求输入 tar 包里只含模型文件，但训练作业产出的 `model.tar.gz` 里在 ONNX 模型旁边还带着 checkpoint 和指标文件，所以该步骤会先重新打包成只含 ONNX 的 tar 包。Neo 还要求具体的输入形状，而导出时声明的是动态批次轴，因此编译请求里把批大小固定为 1。再者，由于流水线步骤可能会重试，编译作业名由执行 ID 确定性地派生而来，这样重试时会继续轮询它已经启动的那个作业，而不会把它变成孤儿。

目标是一个流水线参数：`NeoTargetDevice` 选择某个具名设备，比如 `jetson_xavier` 或 `rasp4b`；它的默认值则针对 `NeoTargetOs`/`NeoTargetArch` 平台编译，默认是 LINUX/X86_64。编译后的包包含优化过的 `compiled.so`，以及用于加载它的 [DLR runtime](https://github.com/neo-ai/neo-ai-dlr)。默认产物可以运行在任何 x86_64 Linux 主机上，因此你可以先验证，再决定是否绑定到特定设备目标。编译本身不收费，你要付的是驱动它的那台处理实例，以及产物在 S3 上的存储费用。如果之后想为已注册的模型再编译出其他设备类型、而不重新训练，仓库里还提供一个临时脚本，对 Model Registry 跑同样的流程。

## Model Registry 中按相机划分的模型

每条分支注册到各自的模型包组，每个模型包都带着相机 ID 和它的评估指标。下面摘自示例，略去了指标部分：

```
classifier_model_builder = ModelBuilder(
    s3_model_data_url=classifier_model_data,
    image_uri=custom_training_image_uri,
    sagemaker_session=pipeline_session,
    role_arn=role_arn,
)
step_register_classifier = ModelStep(
    name="RegisterClassifierModel",
    depends_on=[step_compile_classifier],
    step_args=classifier_model_builder.register(
        model_package_group_name="sm1k-classifier-model-group",
        approval_status="Approved",
        model_metrics=classifier_metrics,
        customer_metadata_properties={"CameraId": camera_id},
    ),
)
```

写进 `customer_metadata_properties` 的相机标识，把两个共享的模型包组变成了一份设备群目录。所有相机的模型包都放在同一批组里，按相机划分的历史则通过过滤该元数据来还原。每条分支都有一个取回步骤，按从新到旧逐页翻找获批的模型包，直到找到发起请求的那台相机最新的模型，因为 `ListModelPackages` 无法在服务端按客户元数据过滤。某台相机首次运行时取回不到任何东西，训练便退回冷启动初始化（分类器用 ImageNet 权重，自编码器用随机初始化）。之后的每一次运行都从该相机自己上一个模型继续，这正是让跨整个设备群的频繁、低成本增量再训练成为可能的关键。

注意这些 registry 条目是什么、又不是什么：它们登记的是带版本、经过质量门禁的产物，但它们的容器引用指向训练镜像，而训练镜像不承载任何推理端点。它们是为这样一条设备群流程而存在的——由下游系统拉取产物并下发到设备——而不是用来配合 `CreateEndpoint` 的。

## 编排设备群训练请求

每个 AWS 账户对并发的 SageMaker 训练作业都有服务配额，而这里每次流水线执行都会启动若干作业，所以设备群再训练需要控节奏。必须得有某种机制，阻止一波 500 个请求变成 500 次同时启动的流水线。示例用的是信号量——一个可用名额的计数器，像一个只有五个车位的停车场。在 Step Functions 状态机启动流水线之前，它通过原子递增 DynamoDB 中的计数器来取一个名额，并用条件表达式在达到上限后拒绝继续递增：

```
acquire_semaphore = tasks.DynamoUpdateItem(
    self, "AcquireSemaphore",
    table=semaphore_table,
    key={"LockName": tasks.DynamoAttributeValue.from_string("pipeline-concurrency")},
    update_expression="SET ActiveCount = if_not_exists(ActiveCount, :zero) + :one",
    condition_expression="attribute_not_exists(ActiveCount) OR ActiveCount < :limit",
)
```

如果名额已满，这次执行就等待并重试；当它的流水线结束，计数减一，释放名额。有个细节值得借鉴到你自己的设计里：DynamoDB 的条件表达式在单次原子操作中施加上限，而不是由状态机先读计数器再判断——后者会在读与写之间留下竞争窗口。仓库实现了其余的运维加固，包括在每条失败路径上释放名额，以及通过 Amazon EventBridge 把失败执行转发到 Amazon SNS。其 README 讨论了等待边界的设定。

上限 5 是一个栈参数，设得较低，好让这个示例在任何标准账户里都能部署并运行，而不必申请提升配额。你可以按账户的训练作业配额把它调到合适的值。超出单个账户的配额之后，如何扩展设备群训练就是另一个话题了。常规手段包括提升服务配额、把训练分散到不同实例类型或不同 Region，以及把设备群分布到多个账户。你也可以把积压的任务留在 SQS 里，等容量释放出来再放行。这些选择取决于你设备群的规模与构成。示例给你的是一份可以直接扩展的骨架。

## 部署并运行示例

仓库 README 中的操作指南是权威版本。下面这个精简版从全新检出开始，在第一次部署前先准备好环境：

```
git clone https://github.com/aws-samples/sample-sagemaker-fleet-cv-pipeline
cd sample-sagemaker-fleet-cv-pipeline && python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cdk bootstrap                                           # once per account/region
cdk deploy SageMakerCVPipelineStack -c bootstrap=true   # roles, bucket, ECR
cdk deploy --all                                        # pipeline + orchestration
./scripts/push_ecr_image.sh                             # build and push training image
```

默认情况下流水线会生成合成的产线图像，因此你不用数据集、也不需要任何数据审批，就能端到端验证整套系统。完整跑一次会执行全部 13 个步骤，包含两次 Neo 编译，大约 15 分钟，按计费的 `ml.m5.xlarge` 机时计算花费约 $0.07（US East (Ohio) 区域 (us-east-2)，2026 年 7 月，按需价格）。在示例规模下，编排资源合计每月远低于 $0.10。

要在真实图像上跑通这条流水线，仓库提供了一个 [BCCD 数据集](https://github.com/Shenggan/BCCD_Dataset)的下载脚本。该数据集是 364 张标注过的血涂片显微图像，最初在 GitHub 上开源，后来按 MIT 许可重新整理为 Pascal VOC 格式。同一数据集也由 [Roboflow](https://public.roboflow.com/object-detection/bccd) 以公有领域方式发布。该脚本把血小板的有无映射为缺陷类别，可以选择按相机切分图像以模拟设备群，并把训练用 tar 包上传到流水线存储桶。配套的 notebook 会在真实数据上跑完整条流水线，并对一个正常样本和一个异常样本做并排的 ONNX 推理。把血小板当作缺陷，只是用制造缺陷分布来举例说明，并非临床结论。

## 清理

模型包是在流水线运行时创建的，因此 AWS CloudFormation 无法删除它们。请先用 AWS CLI 移除这些模型包，再用 `cdk destroy --all -c bootstrap=true --force` 销毁各个栈。确切的命令列在 [README](https://github.com/aws-samples/sample-sagemaker-fleet-cv-pipeline)中。

## 结语

本文展示了一套可运行的 SageMaker SDK v3 参考架构，用于设备群规模的计算机视觉生命周期管理。这套架构包含一条双分支训练流水线：每个模型都要在导出的 ONNX 产物上通过质量门禁，用 SageMaker Neo 编译，然后才注册。一套 Model Registry 结构利用相机元数据，把共享的模型包组变成按相机划分、可用于 warm start 的历史；一层 Step Functions 编排则在账户配额内为设备群训练控制节奏。如果你的需求能被 Amazon Lookout for Vision 之类的托管选项满足，那是一条更简单的路。这套模式针对的正是托管选项覆盖不到的「按相机划分、面向设备群规模」这一约束。它的设计原则也能迁移到计算机视觉之外：用平衡准确率加少数类召回率而不是准确率设门禁，评估并编译你真正要交付的那个产物，以及让运维失败发出通知而不是悄无声息地终止。

这个示例几分钟就能部署完，一次完整验证运行大约花七美分的计算费用，所以一个低门槛的下一步就是克隆[仓库](https://github.com/aws-samples/sample-sagemaker-fleet-cv-pipeline)并跑起来。接下来，你可以把 BCCD 下载脚本指向一个真实的存储桶，为你的硬件设置 `NeoTargetDevice`，或者按设备群的规模调整编排的等待边界。至于 SDK v3 迁移本身，[SageMaker Python SDK 文档](https://sagemaker.readthedocs.io/)以及宣布新 SDK 的那个两篇系列文章，是我全程放在手边的参考。

如果你需要帮助把这套模式适配到你的生产环境，请联系你的 AWS 客户团队。
