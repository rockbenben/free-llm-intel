# 规模化 agent 管理的未来：AWS Agent Registry 现已推出预览版

*现可通过 Amazon Bedrock AgentCore 使用。借助 AWS Agent Registry，你可以在整个组织内发现、共享并复用 agent、工具与 agent skill。*

当企业扩展到数百或数千个 agent 时，平台团队面临三个关键挑战：可见性（了解整个组织中存在哪些 agent）、控制（治理谁能发布、什么能在全组织范围内被发现）和复用（防止团队重复重建已有的能力）。没有集中式系统，agent 泛滥会加速、合规风险上升，开发精力被浪费在重复工作上。现实情况让这些挑战更加棘手：没有任何组织的 agent 版图完全存在于单一提供商之内。agent 会被构建在 AWS 服务、其他云平台和本地环境中。只覆盖部分技术栈的注册中心会让其余部分不可见，而不可见的 agent 无法被发现、治理或复用。要解决这个问题，需要的不仅仅是一个罗列现有资产的地方。平台团队需要构建 agent，以审批工作流发布它们，帮助团队发现并复用已有资产，治理谁能发布和消费，监控生产环境中正在运行的内容，并退役不再需要的东西。今天，我们宣布在 AgentCore 中推出 AWS Agent Registry（预览版），这是在整个企业内发现、共享并复用 AI agent、工具和 agent skill 的单一位置。

[AgentCore](https://aws.amazon.com/bedrock/agentcore/) 是一个用于大规模构建、连接和优化 agent 的平台，从底层就是为 agent 设计的：对任何模型、任何框架、任何企业架构开放。无论你是在交付第一个 agent 还是第千个，你都有同一个平台随你一起扩展。注册中心把同样的灵活性延伸到你对已构建资产的组织与治理方式上。无论 agent 构建或托管在哪里——AWS、其他云提供商或本地环境——它都会为 agent 建立索引。

## **预览版目前提供什么**

注册中心把每个 agent、工具、MCP 服务器、agent skill 和自定义资源的元数据存储为结构化记录。它记录谁发布了每条记录、实现了哪些协议、暴露了什么，以及如何调用它。注册中心原生支持 MCP 和 A2A 等成熟标准，同时保留为你的组织定义自定义 schema 的灵活性。注册记录有两种方式。你可以通过控制台、AWS SDK 或 API 手动提供元数据，说明能力描述、归属、合规状态和使用文档。或者你指向一个 MCP 或 A2A 端点，注册中心会自动拉取详细信息。你的注册中心从第一天起就能反映完整的 agent 版图，而不只是恰好运行在 AWS 上的那部分。

注册中心可通过 AgentCore [控制台](https://us-east-1.console.aws.amazon.com/bedrock-agentcore/registry?region=us-east-1)、API，以及作为 MCP 服务器访问。任何兼容 MCP 的客户端都可以直接查询它，包括 Kiro 和 Claude Code。对于使用自定义身份提供商的组织，基于 OAuth 的访问意味着团队可以构建自己的发现 UI，而无需 IAM 凭证。

### ***找到已经存在的东西***

没有中央注册中心时，开发者会到外部寻找第三方工具，或者重复隔壁团队已经交付的工作。你失去了对以下情况的可见性：已经构建了什么、谁拥有它、它是否获准使用。注册中心用结合关键词匹配与语义匹配的混合搜索解决这个问题：所有查询都使用关键词匹配，但较长的自然语言查询还会使用语义理解来浮现概念上相关的结果。这意味着搜索“payment processing”会浮现被标记为“billing”或“invoicing”的工具，即使它们命名不同。发现因此成为阻力最小的路径。团队可以按名称、描述和资源类型搜索，在构建新东西之前找到已有资产。开发者先搜索注册中心。如果有经过审核的能力，就直接使用。如果没有，就构建它、注册它，并提供给其他人使用。你可以看到整个组织中存在什么。

> 对 Zuora 而言——一个 AI 优先的变现与收入管理平台，在销售、财务、产品和开发者团队中部署了 50 个 agent——AgentCore 中的 AWS Agent Registry 为主架构师提供了一个统一视图，用来发现、管理和编目正在使用的每个 agent、工具和 skill。这种集中式做法使团队能够找到并复用现有资产，而不是从零重建。标准化元数据确保每个 agent 和工具都包含一致的归属与能力细节，让团队在整个 agent 生态中获得端到端的可见性与问责。

### ***治理什么可以被发布***

没有治理，任何人都能注册任何东西。你会失去对什么能被发现的控制，无法强制执行标准，无法追踪归属，也无法管理 agent 从开发到退役的全过程。当只有几个 agent 时，你可以用电子表格管理。当有数百或数千个时，你需要一个自动强制执行标准的系统。

注册中心让你控制什么可以被发布、谁可以访问。管理员使用 IAM 策略定义谁可以注册 agent、工具和 agent skill，以及谁可以发现它们。每条记录都遵循审批工作流：从草稿开始，进入待审批状态，获批后即对更广泛的组织可见。注册中心追踪 agent 的整个生命周期，从初始开发到部署，直至最终退役。记录带版本号以追踪随时间的变化，组织可以弃用不再使用的记录。注册中心提供 hook 以集成你现有的审批工作流。你可以通过记录为每个条目添加自定义元数据，记录团队归属、合规状态或部署环境等信息。

## **我们前进的方向**

我们正在构建这样一个未来：注册中心覆盖构建 agent 的每一项 AWS 服务，包括 Amazon Quick 和 Kiro。agent 一经部署就会被自动编入索引。开发者从 IDE 中搜索，业务用户在工作空间中发现 agent，管理员从控制台进行治理，全部由同一个事实来源支撑。跨注册中心联邦（cross-registry federation）让你可以连接多个注册中心并把它们当作一个来搜索。你将能够定义符合你组织对 agent 思考方式的分类与分类法，并由结构化元数据 schema 支撑，涵盖归属、合规状态、成本中心以及你的治理模型所需的任何其他内容。随着时间推移，来自 AgentCore Observability 的运营智能将与注册记录一同呈现：调用次数、延迟、运行时间和使用模式，帮助你不仅了解存在什么，还了解什么在生产中真正在运行。

除了 AWS Agent Registry，我们还在朝着连接外部合作伙伴目录的方向努力。早期合作伙伴对跨技术版图的集中式发现与治理表现出兴趣，我们对此感到兴奋。

## **开始使用**

今天的预览版只是起跑线。不必再重建已经存在的东西。不必再让 agent 在没有可见性的情况下部署。AWS Agent Registry 为你提供一个位置，来发现、治理并复用企业内的每一个 agent。

AWS Agent Registry 今天通过 AgentCore 在五个 [AWS 区域](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-regions.html)以预览形式提供：美国东部（弗吉尼亚北部）、美国西部（俄勒冈）、亚太地区（悉尼）、亚太地区（东京）和欧洲（爱尔兰）。

通过 AgentCore [控制台](https://us-east-1.console.aws.amazon.com/bedrock-agentcore/registry?region=us-east-1)开始使用 AWS Agent Registry。阅读[文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry.html)了解更多。
