# 为 Amazon Bedrock 构建主动式 AI 成本管理系统 – 第 1 部分

随着组织采用由 [Amazon Bedrock](https://www.google.com/url?sa=t&source=web&rct=j&opi=89978449&url=https://aws.amazon.com/bedrock/&ved=2ahUKEwjCr6_Mk5yLAxWj8MkDHX4bKycQFnoECAkQAQ&usg=AOvVaw2O2p3pxtk9s114vQ58fVAy) 驱动的生成式 AI，他们面临着管理与基于 token 的定价模型相关成本的挑战。Amazon Bedrock 提供按量付费的定价结构，如果用量未经仔细监控，可能会导致意外且过高的账单。传统的成本监控方法（如预算告警和成本异常检测）可以帮助发现异常高企的用量，但本质上是被动的。要主动管控成本，同时使用先行指标和滞后指标至关重要。

*先行指标*是预测性信号，可帮助你在未来趋势或潜在问题完全显现之前加以预判。这些指标提供主动的洞察，使人能够及时干预。相比之下，*滞后指标*是回顾性度量，用于确认已经发生的情况。通过理解并跟踪这两类指标，组织可以建立更具战略性、响应更快的决策流程。

在这个分为两部分的系列中，我们介绍一个主动管理 Amazon Bedrock 推理成本的综合方案。我们的方法采用 cost sentry 机制，旨在建立并执行 token 用量限制，为组织提供一个控制生成式 AI 支出的稳健框架。本文重点讨论核心架构、cost sentry 设计、token 用量跟踪和初步预算执行策略。在[第 2 部分](https://aws.amazon.com/blogs/machine-learning/build-a-proactive-ai-cost-management-system-for-amazon-bedrock-part-2/)中，我们将探讨高级监控技术、自定义标签、报告和长期成本优化最佳实践。目标是提供一种可预测、高性价比的 Amazon Bedrock 部署方式，使之与组织的财务约束相一致。

## 解决方案概述

Amazon Bedrock 采用基于 token 用量的计费策略，根据所使用的输入和输出 token 收费。费率取决于所用的模型和执行推理的 AWS Region。开发者必须在应用中实施稳健的 token 管理策略，以帮助防止成本失控，确保生成式 AI 应用包含与预算约束相匹配的熔断机制和用量限制。

为此，你可以配置 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 告警，或通过账单告警和预算来监控成本，但这些机制都是事后查看已产生的成本或用量。另一种选择是 AWS Solutions Library 中的 [Generative AI Gateway Solution](https://aws.amazon.com/solutions/guidance/multi-provider-generative-ai-gateway-on-aws/)，它使用 LiteLLM 为 Amazon Bedrock 和其他模型提供程序强制执行预算限制。

本方案旨在找到一种主动、集中的机制，将生成式 AI 用量限制在可调整的具体预算内。该方法使用 serverless 工作流和原生 Amazon Bedrock 集成，在提供大规模性能和扩展能力的同时，降低运维复杂度。

使用 Amazon Bedrock 构建应用时，通常的做法是通过开发好的 API 访问该服务：要么通过 REST API 同步访问，要么通过队列系统异步访问。下图对比了这些架构。

![AWS 架构图，对比通过 API Gateway 实现的直接式与事件驱动式 Bedrock 集成模式](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/24/ML-17734-figure-1-api-architecture-diagram.jpg)

对于同步交互，客户端直接向 Amazon Bedrock 发起 REST API 调用，并传入必要的参数。在异步架构中，客户端将推理请求提交到队列或消息 broker（如 [Amazon Simple Queue Service](https://aws.amazon.com/sqs/)（Amazon SQS））。后端处理系统通常实现为 serverless 函数或容器化应用，持续监控队列并处理传入的请求。这种方式将客户端与推理处理解耦，从而在处理请求突发时具备可扩展性和韧性。

本方案是一个集中式机制，可用于与 Amazon Bedrock 交互，充当主动的 cost sentry。它采用 serverless 架构设计，使用 [AWS Step Functions](https://aws.amazon.com/step-functions/) 编排工作流：在放行 Amazon Bedrock 推理请求之前，先根据配置的限制校验 token 用量。该方案确保生成式 AI 应用保持在预定义的预算边界内，提供成本可预测性和控制能力。

下图展示了我们在本文中构建的架构。

![AWS Cost Sentry 架构，包含 API Gateway、Step Functions 以及用于 Bedrock 监控的 CloudWatch 集成](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/24/ML-17734-figure-2-cost-sentry-architecture-diagram.jpg)

本方案的核心组件包括：

- **速率限制工作流** – 一个 Step Functions 工作流，从 CloudWatch 获取当前 token 用量指标，将其与存储在 [Amazon DynamoDB](https://aws.amazon.com/pm/dynamodb) 中的预定义限制进行比较，并决定是放行还是拒绝 Amazon Bedrock 推理请求。
- **Amazon Bedrock 模型路由器** – 一个独立的 Step Functions 状态机，充当调用各种 Amazon Bedrock 模型的集中式网关。该组件抽象了处理各模型所需不同 I/O 参数的复杂性。
- **Token 用量跟踪** – 利用 CloudWatch 与 Amazon Bedrock 的指标集成，获取所有模型或特定模型的输入和输出 token 的当前用量数据。
- **预算配置** – 通过将所需预算值存储在 DynamoDB 中，可以按模型设置 token 用量限制。也可以设置默认限制，适用于未定义具体预算的模型。
- **成本与用量可见性 **– 通过 CloudWatch 仪表板提供 AI 用量的可见性，并通过 [AWS Cost Explorer](https://aws.amazon.com/aws-cost-management/aws-cost-explorer/) 提供随时间变化的成本报告。

该方案采用 serverless 架构方法，使用 Step Functions、[AWS Lambda](https://aws.amazon.com/pm/lambda)、DynamoDB 和 CloudWatch 等托管 AWS 服务，提供可扩展、可拓展且高性价比的实现。

目标是提供一种主动设置生成式 AI 用量限制的方法，作为先行指标来限制用量：

- **主动预算** – 在放行推理请求之前强制执行 token 用量限制，帮助防止意外超支
- **按模型定制预算** – 支持根据不同 Amazon Bedrock 模型的定价和使用模式设置单独的预算
- **默认预算兜底** – 如果未为模型定义具体预算，可以应用默认限制以实现成本控制
- **监控** – 使用 CloudWatch 指标集成跟踪 token 用量，实现精准的预算执行
- **Serverless 架构** – 使用 Step Functions、Lambda、DynamoDB 和 CloudWatch，提供可扩展且高性价比的方案
- **可扩展性** – 模块化设计支持无缝集成更多 Amazon Bedrock 模型或其他推理方式

## Step Functions 工作流

本节探讨该方案如何使用 Step Functions 实现速率限制和模型路由工作流。

### 速率限制工作流

速率限制工作流设计为接受一个最小的 JSON 文档作为输入，格式如下：

```
{
  "modelId": "string",       // e.g. "anthropic.claude-3-sonnet-20240229-v1:0"
  "prompt": {
    "messages": [
      {
        "role": "string",    // "system", "user", or "assistant"
        "content": "string"
      }
    ]
  }
}
```

该工作流是执行预算控制的核心组件。关键步骤如下：

- Lambda 函数获取当月的开始和结束日期，用于查询相应时间范围内的 token 用量指标。
- 工作流查询 CloudWatch，获取指定 Amazon Bedrock 模型当月的 token 用量指标。
- 工作流从 DynamoDB 获取指定 Amazon Bedrock 模型配置的 token 用量限制。如果未找到具体限制，则回退到获取默认限制。
- 工作流将当前 token 用量与配置的限制进行比较，判断是否已超出预算。
- 如果 token 用量在预算内，该步骤将调用 Amazon Bedrock 模型路由器状态机来执行实际的推理请求。
- 根据预算检查的结果，工作流返回格式化后的推理结果，或返回指示预算已超出的错误。

### Amazon Bedrock 模型路由器工作流

Amazon Bedrock 模型路由器工作流是一个独立的 Step Functions 状态机，负责根据请求参数调用相应的 Amazon Bedrock 模型。它抽象了处理各种 Amazon Bedrock 模型所需不同 I/O 格式的复杂性，并将结果合并为标准化格式。

工作流中的关键步骤包括：

- 根据提供的模型 ID，工作流确定要调用的具体 Amazon Bedrock 模型。
- 工作流使用所需的输入参数调用相应的 Amazon Bedrock 模型。
- 工作流将 Amazon Bedrock 模型的输出规范化为一致格式，以便进一步处理或返回给客户端。
- 工作流将转换后的推理结果返回给调用方工作流（cost sentry 工作流）。

下图展示了 Step Functions 工作流。

![ 详细的状态机工作流，展示 Bedrock 模型类型判定和调用过程](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/24/ML-17734-figure-4-bedrock-router-workflow.jpg)

你可以实现额外的步骤来处理错误情况并适当格式化输出。在本例中，Anthropic flow 包含错误处理。

该 CloudWatch 指标查询可获取指定时间范围内的输入和输出 token 总数，使速率限制工作流能够基于实时用量数据精准执行预算。

## 使用 DynamoDB 配置预算

Amazon Bedrock cost sentry 将 token 用量限制存储在 DynamoDB 表中，可无缝配置和更新单个模型预算或默认限制。例如，参见以下代码：

```
{
    "modelId": "anthropic.claude-3-sonnet-20240229-v1:0",
    "limit": {
        "input": 1000000,
        "output": 3000000
    }
}
```

在本例中，指定 Amazon Bedrock 模型（`anthropic.claude-3-sonnet-20240229-v1:0`）的 token 用量限制设置为 1,000,000 个输入 token 和 3,000,000 个输出 token。

管理员可以通过修改相应的 DynamoDB 记录快速更新这些限制，从而灵活地按需调整预算。

## 速率限制工作流的性能分析

为评估引入该工作流对性能的影响，我们使用了一组推理请求。测试用例包含各种 prompt，旨在生成从简洁答案到超过 500 字的详细说明等不同响应，有效测试了工作流在不同输出 token 规模下的性能。在 501 次成功执行中，该工作流展现出优异的性能特征，处理了从简短响应到大量内容生成的各类推理请求。

在处理总时长从 6.76 秒到 32.24 秒不等的请求时，该工作流保持一致的执行模式，差异主要反映了每个请求对输出 token 的不同要求：

- **快速响应（10 秒以内）** – 通常处理简洁答案和简单查询
- **中等长度内容（11–22 秒）** – 常见于详细说明和多段响应
- **较长生成（最长 32 秒）** – 处理需要超过 500 字的全面响应

下图展示了我们的时间分布发现。

![性能分析，显示 98.26% 的时间花费在 Bedrock 模型处理上，开销极小](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/24/ML-17734-figure-5-cost-sentry-processing-time.jpg)

时间分布分析揭示了高度优化的资源利用率：

- **Amazon Bedrock 模型路由器** – 5.80–31.99 秒（占运行时间的 98.26%）
- **其他工作流步骤** – 0.11–4.74 秒（占运行时间的 1.65%）
- **系统开销** – 平均 0.02 秒（占运行时间的 0.09%）

这一性能特征符合工作流编排的最佳实践，即最小化开销和保持一致的执行模式对可靠性至关重要。该工作流的效率体现在其极低的 system overhead（仅 0.09%）上，无论生成的响应大小如何，都能有效利用 Step Functions 的内置控制和状态管理能力。

执行一致性尤其值得关注：无论推理请求的复杂度或输出大小如何，每次执行的事件数都稳定在 47–49 个，模式可预测。这种可预测性对工作负载管理和资源规划至关重要，尤其是在处理各不相同的请求复杂度和 token 输出量时。

这些指标表明，该工作流架构良好，有效利用 [Step Functions Express workflow](https://docs.aws.amazon.com/wellarchitected/latest/serverless-applications-lens/step-functions-workflows.html) 能力处理大批量事件，同时在简单查询和复杂的 token 密集型推理请求之间都保持极低开销和一致的性能特征。

## 结论

在本方案中，我们使用 Step Functions 构建了一个充当先行指标的系统：它跟踪速率限制和 token 用量，在接近用量限制时立即发出警告。在[第 2 部分](https://aws.amazon.com/blogs/machine-learning/build-a-proactive-ai-cost-management-system-for-amazon-bedrock-part-2/)中，我们将讨论如何将其与滞后指标结合，以持续掌握用量和成本情况。
