# 优化 AI 响应性：Amazon Bedrock 延迟优化推理实用指南

在生产环境的[生成式 AI](https://aws.amazon.com/ai/generative-ai/)应用中，响应速度与模型本身的智能程度同等重要。无论是处理时效性咨询的客服团队，还是需要即时代码建议的开发者，每一秒的延迟（即 latency）都可能带来显著影响。随着企业越来越多地把[大语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）用于这些关键任务和流程，它们面临一个根本性挑战：如何在交付这些精密模型所承诺的高质量输出的同时，保持用户所期待的快速、灵敏的性能。

延迟对用户体验的影响远不止于不便。在交互式 AI 应用中，延迟的响应会打断对话的自然流畅感，削弱用户参与度，最终影响 AI 驱动方案的采用。现代 LLM 应用日益复杂，往往需要多次 LLM 调用才能解决单个问题，这会显著拉长总处理时间，使这一挑战进一步加剧。

在 re:Invent 2024 期间，我们为 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 中的[基础模型](https://aws.amazon.com/what-is/foundation-models/)（FM）推出了[延迟优化推理](https://docs.aws.amazon.com/bedrock/latest/userguide/latency-optimized-inference.html)。与标准版本相比，这一新的推理功能可降低 [Anthropic 的 Claude 3.5 Haiku 模型](https://aws.amazon.com/bedrock/claude/)以及 [Meta 的 Llama 3.1 405B 和 70B 模型](https://aws.amazon.com/bedrock/llama/)的延迟。该功能对快速响应关乎业务成败的时效敏感型工作负载尤其有帮助。

在本文中，我们探讨 Amazon Bedrock 延迟优化推理如何帮助应对在 LLM 应用中保持响应性的挑战。我们将深入介绍优化应用性能、改善用户体验的策略。无论你是在构建新的 AI 应用还是优化现有应用，都能找到关于延迟优化技术细节与实际落地方法的实用指引。我们先从解释 LLM 应用中的延迟开始。

## 理解 LLM 应用中的延迟

LLM 应用中的延迟是一个多维度的概念，并不局限于简单的响应时间。与 LLM 交互时，你可以通过两种方式之一接收回答：流式（streaming）或非流式（nonstreaming）模式。在非流式模式下，你要等到回答全部生成完毕才能收到任何输出——就像等别人把信写完。在流式模式下，回答在生成过程中就会陆续到达——就像看着别人实时打字。

要为响应性有效优化 AI 应用，我们需要理解定义延迟的关键指标，以及它们如何影响用户体验。这些指标在流式与非流式模式下有所不同，理解它们对于构建响应灵敏的 AI 应用至关重要。

首 token 时间（Time to first token，TTFT）表示你的流式应用开始响应的快慢。它指从用户提交请求到收到回答开头（第一个词、token 或 chunk）所经历的时间。可以把它理解为 AI 应用的初始反应时间。

TTFT 受以下几个因素影响：

- 输入 prompt 的长度（prompt 越长，TTFT 通常越高）
- 网络状况与地理位置（如果 prompt 在其他区域处理，耗时会更长）

计算：TTFT = 首个 chunk/token 的时间 – 请求提交的时间
 解读：越低越好

每秒输出 token 数（Output tokens per second，OTPS）表示模型在开始响应后生成新 token 的速度。该指标对于理解模型的实际吞吐量，以及它在较长生成过程中如何维持响应速度至关重要。

OTPS 受以下因素影响：

- 模型的规模与复杂度
- 生成回答的长度
- 任务与 prompt 的复杂度
- 系统负载与资源可用性

计算：OTPS = 输出 token 总数 / 总生成时间
 解读：越高越好

端到端延迟（End-to-end latency，E2E）衡量从发起请求到获得完整回答的总时间。如上图所示，它涵盖整个交互过程。

影响该指标的关键因素包括：

- 输入 prompt 的长度
- 请求的输出长度
- 模型处理速度
- 网络状况
- 任务与 prompt 的复杂度
- 后处理需求（例如使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 或其他质量检查）

计算：E2E 延迟 = 请求完成的时间 – 请求提交的时间
 解读：越低越好

### tokenization 的作用

延迟中一个常被忽视的方面，是不同模型对文本做 tokenization 的方式不同。每个模型的 tokenization 策略由其提供方在训练时确定，无法修改。例如，同一段 prompt 在某个模型上生成 100 个 token，在另一个模型上可能生成 150 个。在比较模型性能时请记住，即使各模型效率相当，这种固有的 tokenization 差异也会影响被感知到的响应时间。了解这一差异有助于你更好地解读模型之间的延迟差别，并在为应用选择模型时做出更明智的决定。

### 理解用户体验

AI 应用中的等待心理揭示了关于用户期望与满意度的有趣规律。用户往往会根据请求的上下文和复杂度，对响应时间产生不同的感知。生成复杂分析时稍微延迟可能可以接受，而在对话交流中即便很小的卡顿也会让人觉得不顺畅。这一认识有助于我们为不同类型的应用设定合适的优化优先级。

### 一致性优先于速度

稳定的响应时间（即使稍慢一些）往往比波动很大、只是偶尔快速的响应时间带来更高的用户满意度。这对流式响应和实施优化策略都至关重要。

### 保持用户参与

当处理时间较长时，“正在处理你的请求”或“加载动画”之类的简单提示有助于维持用户的参与感，在初始响应阶段尤其如此。在这类场景中，你应当针对 TTFT 做优化。

### 平衡速度、质量与成本

输出质量往往比速度更重要。相比快速但不太可靠的回答，用户更偏好准确的回答。可以考虑对你的用户体验做基准测试，以找到适合你用例的最佳延迟，同时考虑到大多数人阅读速度不会超过每分钟 225 词，因此过快的响应反而可能损害用户体验。

通过理解这些细微之处，你可以做出更明智的决定，优化 AI 应用以获得更好的用户体验。

## 延迟优化推理：深入解析

Amazon Bedrock 延迟优化推理能力旨在提供更高的 OTPS 和更快的 TTFT，使应用能更可靠地处理工作负载。该优化已在美国东部（俄亥俄）[AWS 区域](https://docs.aws.amazon.com/glossary/latest/reference/glos-chap.html#region)对部分 FM 提供，包括 Anthropic 的 Claude 3.5 Haiku 以及 Meta 的 Llama 3.1 模型（405B 和 70B 两个版本）。该优化支持以下模型：

- **更高的 OTPS** – 模型开始响应后更快的 token 生成速度
- **更快的 TTFT** – 更快的初始响应时间

### 实现

要启用延迟优化，你需要在 API 调用中把 `latency` 参数设置为 optimized：

```
# Using converse api without streaming
response = bedrock_runtime.converse(
    modelId='us.anthropic.claude-3-5-haiku-20241022-v1:0',
    messages=[{
            'role': 'user',
            'content': [{
                'text':'Write a story about music generating AI models'
                }]
              }],
    performanceConfig={'latency': 'optimized'}
)

For streaming responses:

# using converse API with streaming
response = bedrock_runtime.converse_stream(
       modelId='us.anthropic.claude-3-5-haiku-20241022-v1:0',
       messages=[{
            'role': 'user',
            'content': [{
                'text':'Write a story about music generating AI models'
                }]
              }],
        performanceConfig={'latency': 'optimized'}
    )
```

### 基准测试方法与结果

为了解 TTFT 和 OTPS 两方面的性能提升，我们做了一次离线实验，在一天中的不同时段、跨多天共发起约 1,600 次 API 调用。我们使用了一份包含不同任务类型的虚拟数据集：序列计数、故事写作、摘要和翻译。输入 prompt 的长度从 100 个 token 到 100,000 个 token，输出 token 数从 100 到 1,000。选择这些任务是为了代表不同的复杂度水平和不同的模型输出长度。我们的测试环境托管在美国西部（俄勒冈）`us-west-2` 区域，而优化版和标准版模型都托管在美国东部（俄亥俄）`us-east-2` 区域。这种跨区域配置引入了真实的网络波动，有助于我们在接近真实应用的条件下测量性能。

在分析结果时，我们聚焦于前面讨论过的关键延迟指标：TTFT 和 OTPS。简单回顾一下：TTFT 越低表示初始响应越快，OTPS 越高表示 token 生成速度越快。我们还考察了第 50 百分位（P50）和第 90 百分位（P90）的数值，以同时了解典型性能，以及困难或上界条件下的性能边界。依据中心极限定理，我们观察到在样本充足时结果会收敛到稳定的数值，从而提供可靠的性能指标。

需要说明的是，这些结果来自我们特定的测试环境和数据集。你的实际结果可能因具体用例、prompt 长度、预期的模型回答长度、网络状况、客户端位置以及其他实现组件而异。在自行做基准测试时，请确保测试数据集能代表你真实生产工作负载的特征，包括典型的输入长度和预期的输出模式。

### 基准测试结果

我们对延迟优化模型的实验显示，TTFT 与 OTPS 两项指标都有显著提升。下表中的结果对比了 Anthropic 的 Claude 3.5 Haiku 和 Meta 的 Llama 3.1 70B 模型标准版与优化版的表现。对每个模型，我们都对测试场景做了多轮迭代，以确保性能数据可靠。提升在高百分位测量中尤为明显，说明即使在困难条件下性能也更加稳定。

Meta 的 Llama 3.1 70B 模型的收益更为可观：优化版在 TTFT P50 上最多降低 51.65%，在 TTFT P90 上最多降低 97.10%，提供了持续快速的初始响应。更进一步，OTPS 大幅提升，P50 水平上最多提升 353.84%，P90 水平上最多提升 529.33%，在某些场景下使 token 生成速度提升最多 5 倍。

## LLM 延迟优化综合指南

尽管 Amazon Bedrock 延迟优化推理从一开始就能带来可观改善，但要获得最佳性能，仍需要以周全的方式设计和实现你的应用。下一节我们探讨其他一些策略与考量，让你的应用尽可能响应灵敏。

### 面向延迟优化的 prompt engineering

在为降低延迟而优化 LLM 应用时，你撰写 prompt 的方式会同时影响输入处理和输出生成。

要优化输入 prompt，请遵循以下建议：

- **保持 prompt 简洁** – 长的输入 prompt 处理耗时更久，会提高 TTFT。请编写简短、聚焦的 prompt，优先包含必要的上下文和信息。
- **拆解复杂任务** – 不要用单个请求处理大型任务，而应把它们拆成更小、更易处理的片段。这种做法有助于在任务复杂度不同的情况下都保持响应性。
- **智能上下文管理** – 对聊天机器人等交互式应用，只包含相关上下文，而不是整段对话历史。
- **Token 管理** – 不同模型对文本的 tokenization 方式不同，同一输入可能产生不同数量的 token。请监控并优化 token 用量，以保持性能稳定。使用 token 预算来平衡上下文保留与性能需求。

要为简短输出做设计，请遵循以下建议：

- **为简洁而设计** – 在 prompt 中加入明确的长度约束（例如“用 50 词以内回答”）
- **使用 system message** – 通过 system message 设定回答长度约束
- **平衡质量与长度** – 确保回答约束不会损害输出质量

让 AI 应用“感觉更快”的最佳方式之一是使用流式。流式不必等到回答完整生成，而是边生成边展示——就像看着别人实时打字。对回答采用流式，是提升 LLM 应用被感知性能、维持用户参与度最有效的方法之一。

这些技巧可以显著减少 token 用量和生成时间，同时改善延迟与成本效率。

## 构建可上生产的 AI 应用

尽管单项优化很重要，生产级应用仍需要对延迟做整体管理。本节探讨不同系统组件和架构决策如何影响应用的整体响应性。

### 系统架构与端到端延迟考量

在生产环境中，系统整体延迟远超模型推理时间。AI 应用栈中的每个组件都会累加到用户所体验的总延迟中。例如，在通过 Amazon Bedrock Guardrails 落地负责任的 AI 实践时，你可能会注意到小幅的额外延迟开销。集成内容过滤、用户认证或输入校验层时也有类似考量。尽管每个组件都承担着关键作用，但它们对延迟的累积影响需要在系统设计阶段仔细权衡。

地理分布对应用性能影响很大。模型调用延迟会因调用来自不同区域、本地机器还是不同云服务商而差异明显。这种差异源于数据穿越网络和地理距离所需的时间。在设计应用架构时，请考虑应用与模型端点之间的物理距离、跨区域数据传输时间，以及不同区域的网络可靠性等因素。数据驻留要求也可能影响这些架构选择，可能需要在特定区域部署。

集成方式会显著影响用户对应用性能的感知。同步处理虽然实现更简单，但未必总能提供最佳用户体验。请在适当之处考虑异步模式，例如根据用户行为模式预取可能的回答，或在后台处理非关键组件。对批量操作使用请求批处理也有助于优化系统整体吞吐量，不过需要与响应时间要求仔细平衡。

随着应用规模扩大，会需要更多基础设施组件，而这些组件可能影响延迟。负载均衡器、队列系统、缓存层和监控系统都会占用整体延迟预算。理解这些组件的影响，有助于在基础设施设计和优化策略上做出明智决定。

复杂任务往往需要编排多次模型调用，或把问题拆成子任务。设想一个内容生成系统：先用一个快速模型生成大纲，再并行处理各个章节，最后用另一个模型做连贯性检查和润色。这种编排方式要求在保持输出质量的同时，认真关注延迟的累积影响。每一步都需要合适的超时与回退机制，以在各种条件下提供可靠性能。

### 用 prompt caching 提升性能

尽管我们的重点是延迟优化推理，但值得一提的是，Amazon Bedrock 还提供 [prompt caching](https://aws.amazon.com/bedrock/prompt-caching/)（预览版），可同时优化成本与延迟。该功能对频繁复用上下文的场景尤其有价值，例如基于文档的聊天助手，或查询模式重复的应用。

### 用 prompt routing 智能选择模型

与 prompt caching 类似，[Amazon Bedrock Intelligent Prompt Routing](https://aws.amazon.com/bedrock/intelligent-prompt-routing/)（预览版）是另一个强大的优化功能。该能力会根据每个 prompt 的复杂度，自动把请求路由到同一模型系列中的不同模型。例如，简单查询可以路由到更快、更具成本效益的模型，而需要更深理解的复杂请求则交给更精密的模型处理。这种自动路由无需人工干预，即可同时优化性能与成本。

### 架构考量与缓存

应用架构对整体延迟优化起着关键作用。可以考虑实施多层缓存策略，包括对高频请求信息的响应缓存，以及对历史信息的智能上下文管理。这不只是存储完全匹配的内容——可以考虑实施语义缓存，识别并返回针对相似查询的响应。

### 平衡模型精密程度、延迟与成本

在 AI 应用中，模型的精密程度、延迟与成本之间始终存在权衡，如图所示。更先进的模型往往能提供更高质量的输出，但它们未必总能满足严格的延迟要求。在这种情况下，使用精密程度较低但更快的模型可能是更好的选择。例如，在需要近乎瞬时响应的应用中，为了达成延迟目标，可能必须选择更小、更高效的模型，即便这会在输出质量上做出少许让步。这一做法契合在 AI 系统中优化成本、速度与质量之间关系的更广泛需求。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/23/ML-18072-image003.jpg)

Amazon Bedrock Intelligent Prompt Routing 等功能有助于有效管理这种平衡。通过根据请求复杂度自动完成模型选择，你可以同时优化质量、速度与成本这三个因素，而无需让开发者为所有请求固定使用同一个模型。

正如本文通篇所探讨的，优化 LLM 应用延迟涉及多种策略，从使用延迟优化推理和 prompt caching，到实施智能路由和细致的 prompt engineering。关键在于以最适合你具体用例和需求的方式组合这些方法。

## 结论

让 AI 应用快速且响应灵敏不是一次性任务，而是一个持续测试与改进的过程。Amazon Bedrock 延迟优化推理为你提供了很好的起点，与本文讨论的策略结合使用时，你会看到显著的改善。

- 在应用代码中启用[延迟优化](https://docs.aws.amazon.com/bedrock/latest/userguide/latency-optimized-inference.html)推理
- [设置](https://docs.aws.amazon.com/AmazonS3/latest/userguide/configure-request-metrics-bucket.html) [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 指标，以监控应用性能
