# t54 如何借助 Amazon Bedrock AgentCore payments 构建信任层

agentic 系统可以研究、推理并编排多步骤工作流，但一旦撞上付费墙就停住了：它没有钱包、没有卡，也没有消费限额。t54 解决了这个问题。[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 是一个用于构建、连接并大规模优化 agent 的平台，支持任意框架与模型。他们基于 Amazon Bedrock AgentCore payments（Amazon Bedrock AgentCore 的一项能力）构建的信任层，已处理超过 [2,000 万笔由 agent 发起的交易](https://www.x402scan.com/server/655c6f59-88df-4bf2-99c5-42e392322c84)，期间没有任何一笔经过人工批准。每笔交易都是金额在 0.001 至 0.01 美元之间的小额支付：快速、高频的调用，这个频率下没有人能逐笔审核。

## 问题所在：给 agent 一个钱包很简单，大规模治理它却不然

t54 的客户部署的 agentic 系统需要自主为第三方服务付费。以一个金融服务团队为例：他们运行一套 agentic 系统，监控股票组合，并在持仓变化时提醒分析师。系统需要来自付费 API 的实时行情数据。给 agent 开通钱包访问权限很简单，难的是围绕它的一切：执行消费限额，避免某个配置错误的循环把账户掏空；隔离凭证，让 agent 永远接触不到原始密钥；为合规审计每一笔交易；并且要在数十个 agent 调用数百个端点的规模上完成所有这些事。

缺少这层治理，团队就只能在两者之间选择：逐笔人工审核批准，或者接受无人管理的风险。在低流量下，人工审批可行；但在机器速度下、每小时数千次 API 调用时，它就会失效。团队需要的是自带管控的自主支付。

t54 构建的是面向 agent 支付的信任基础设施。他们的客户反复提出同样的诉求：让 agent 能够付款，既安全、可扩展，又不绑定特定支付提供商，而且不必从零搭建定制的支付编排。为满足这一点，t54 需要一条把会话级消费限额、凭证保管和多提供商支持都内建好的支付骨干。

Amazon Bedrock AgentCore payments 提供消费基础设施：会话限额、凭证隔离和支付执行。t54 的 x402-secure 提供信任智能：实时端点评分，判定向谁付款是安全的。两者结合，让团队无需定制集成工作就能获得受治理的 agent 支付。

## t54 构建了什么

[![t54 标志](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/28/ML-21104-1-1.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/28/ML-21104-1-1.png)

t54 构建的信任基础设施负责治理 AI agent 可以安全地向哪些服务付款。其产品 x402-secure 是一个信任层，会实时为端点和链上支付地址打分。在 agent 向某个服务付款之前，x402-secure 会告诉它该服务是否安全可付。

其底层的协议是 x402——一个开放支付标准，利用 HTTP 402 状态码让客户端直接通过 HTTP 为 API 付费。当 agent 调用一个付费端点并收到 402 响应时，由 Amazon Bedrock AgentCore payments 处理签名与结算。agent 不直接接触私钥。

x402-secure 背后的评分引擎 Trustline 会在支付结算前评估五个相互独立的信号：支付地址的区块链历史、目标网页的合法性、服务的社交媒体足迹、API 的实时健康状态，以及综合前四项得出的总体风险评分。每个信号捕获不同类别的不可信端点。t54 在风险模型上做了这样的设计：任何单一弱信号都无法单独授权一笔交易。

产品套件还包括 ClawCredit，一项 agent 原生的信用额度。Amazon Bedrock AgentCore payments 执行每个会话的消费上限，而 ClawCredit 提供在该上限内运作的、由信用支持的资金来源。两层各自独立地管控支出。

> “AgentCore 上已经有很多优秀的开发者，我们认为最好的体验就是在那里直接服务他们，把 Trustline 内建到平台里，而不是让他们自己去接支付编排。开发者真正担心的是 agent 做出会带来真实财务后果的事情。我们的工作就是让他们安心。”

— Chandler Fang，t54 创始人

## 架构：信任与支付如何协同

![x402 支付流程：agent 先为端点评分，再由一个失败即关闭的信任门控批准，之后 Amazon Bedrock AgentCore payments 才结算该交易](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/28/ML-21104-2-1.png)

图 1：受信任门控的 x402 支付流程，信任检查必须先通过，Amazon Bedrock AgentCore payments 才会结算交易

该图展示跨五条泳道的端到端流程：应用后端、Amazon Bedrock AgentCore runtime（Amazon Bedrock AgentCore 的一项能力）、带有确定性信任门控的 Strands agent、外部付费服务，以及 Amazon Bedrock AgentCore payments。支付必须先通过信任检查才能继续。关于 Amazon Bedrock AgentCore payments 的完整架构，包括 AWS Identity and Access Management（IAM）认证、AWS Secrets Manager 凭证存储和 Amazon CloudWatch 可观测性，请参阅[技术深入解析：AgentCore Payments 与 agentic 商务的创新](https://aws.amazon.com/blogs/machine-learning/technical-deep-dive-agentcore-payments-and-innovation-in-agentic-commerce/)。

核心设计原则是职责分离：花钱的东西永远不该同时是制定花钱规则的东西。t54 通过 IAM 的严格角色分离来落实这一点。他们把系统拆成四个角色，使 agent runtime 可以执行支付，却无法修改自身的限额、开通新钱包或直接访问凭证。

在实践中，这意味着 agent 在调用时只会拿到一个 session ID 和一个 instrument ID，别的什么都没有。开发者凭证通过 Amazon Bedrock AgentCore Identity（Amazon Bedrock AgentCore 的一项能力）加密存放在 AWS Secrets Manager 中，不会从 API 返回。终端用户钱包的签名密钥留在钱包提供商（Coinbase）一侧。agent 只拿到一个会话级 token。一旦 agent 用尽消费限额，它就停下。agent 内部没有任何途径去充值或重建该会话。

> “最难的决策是把风险检查做成每次 ProcessPayment 之前必须经过的门控，而不是在旁边跑的东西。为每个端点内联打分要付出一点延迟，但另一种做法是让支付在我们还没确认对面是谁之前就结算。对于调动真实资金的 agent，这不是我们愿意做的取舍。所以我们接受多一点延迟，换取一个保证：没有新的风险判定，任何交易都不会结算。”

— Frank He（博士），t54 该集成的负责人

## 信任门控：为什么重要

Frank 所说的那个保证，就是关键的架构选择。信任检查是一个确定性的门控，而不是由模型给出的建议。agentic 系统在每次支付前调用 x402-secure API。如果端点未能达到评分阈值、被标记为诈骗，或出现 URL 不匹配，支付会在代码层被阻断。模型无法推翻它。

在大规模下，agent 在未做付款前授权的情况下调用未知 API，会造成无人管理的风险。确定性的信任门控封住了这一风险面。

在生产环境中，这一设计经受住了考验。

## 结果

自上线以来，x402-secure 已处理超过 [2,000 万笔由 AI agent 发起的交易](https://www.x402scan.com/server/655c6f59-88df-4bf2-99c5-42e392322c84)。确定性信任门控、IAM 角色分离和会话消费限额，让每一笔交易都处于治理之下，无需任何人工介入。

> “两千万笔交易告诉我们，agent 之间的支付已经在真实规模上发生，而不只是演示。每一笔都是 0.001 至 0.01 美元的小额支付，这种为数据或 API 发起的快速小额调用，没有人能实时审核。在这个过程中，我们阻断了对被判定为高风险的端点的支付，因此会话保住了它的消费限额，agent 也被导向更安全的地方。”

— Chandler Fang，t54 创始人

面向自主 AI 的金融原语已经进入生产环境。更难的问题不是 agent 将来是否需要为东西付费，而是：在本不该结算的事情结算之前，治理层是否已经就位。

## 内部机制：控制面与数据面

对于想实现类似集成的开发者，下面是 t54 如何把他们的系统映射到 Amazon Bedrock AgentCore payments 的两个层上。

### 配置阶段（控制面）

三个资源即可创建支付基础设施，无需为每个提供商编写定制集成代码：

- Credential Provider 把凭证存放在 token 保管库中。凭证不会以明文形式出现在 agent runtime 面前。
- Payment Manager 把授权、身份与支付连接器串联起来。t54 为它配置了一个 `CUSTOM_JWT` 授权器，背后是 OpenID Connect（OIDC）发现端点。
- Payment Connector 指定支付提供商类型（`CoinbaseCDP`）并引用 Credential Provider，把 Payment Manager 与外部提供商连接起来。

### 运行阶段（数据面）

三个操作处理实时交易：

- `CreatePaymentSession` 开启一个会话，带有消费限额、有效期窗口（15 至 480 分钟）和一个 `userId`。Amazon Bedrock AgentCore payments 实时跟踪可用额度。
- `CreatePaymentInstrument` 按指定网络开通一个 Embedded Crypto Wallet。响应返回钱包地址和一个用于接入流程的重定向 URL。
- `ProcessPayment` 执行支付。在结算之前，Trustline 会为该端点评分。通过后，Amazon Bedrock AgentCore payments 返回 `processPaymentId`、状态和完整审计轨迹。若被标记，x402-secure 会阻断支付并保持消费限额不变。

### 与 MCP 市场的集成

t54 还把同一套集成放到 Coinbase x402 Bazaar 上做了测试——这是一个付费 AI 工具服务器（Model Context Protocol，即 MCP，server）的市场。agentic 系统通过 Amazon Bedrock AgentCore Gateway（Amazon Bedrock AgentCore 的一项能力）连接、发现付费工具并调用它们。当某个工具返回 x402 支付要求时，由 `ProcessPayment` 对交易签名。一套 Amazon Bedrock AgentCore payments 配置即可同时覆盖直连 API 端点和市场上架的工具，无需额外配置。

## 可观测性与审计

每次 `ProcessPayment` 调用都会向 Amazon CloudWatch 输出结构化日志（会话、instrument、金额、状态）。AWS CloudTrail 记录完整的 API 历史以供合规审查。信任判定与支付结果在 Amazon CloudWatch Application Signals 中按会话关联。对于受监管的工作负载，这为合规团队提供了连续的审计轨迹，涵盖 agent 花出的每一美元以及与之对应的信任信号。

## 开始使用

**如果你正在构建会调用付费 API 的 agent：**

文中的完整实现见 [t54 x402-secure 用例](https://github.com/awslabs/agentcore-samples/tree/main/01-features/08-agents-that-transact/02-use-cases/pay-for-x402-secure-data)。[入门教程](https://github.com/awslabs/agentcore-samples/tree/main/01-features/08-agents-that-transact/00-getting-started)会带你端到端走完第一笔 agentic 支付。用开源 SDK 为已有的 AgentCore agent 加上带信任评分的支付：

```
pip install x402-secure
```

**如果你是提供付费端点的 API 提供商：**

把 x402 facilitator URL 换成 t54 代理，即可获得信任保护。同一套 x402 API，只改一处配置：

```
Before: https://x402.org/facilitator
After: https://x402-proxy.t54.ai
```
