# 评估 AI agent：在 Amazon 构建 agentic 系统的真实世界经验

生成式 AI 行业经历了从使用由 [大语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）驱动的应用，到采用 [agentic AI 系统](https://aws.amazon.com/ai/agentic-ai/) 的重大转变，这标志着 AI 能力的架构方式与部署方式发生了根本性变化。早期的 [生成式 AI](https://aws.amazon.com/ai/generative-ai/) 应用主要依赖 LLM 直接生成文本并回应 prompt，而行业已经从那种静态的 prompt-响应范式，演进到自主 agent 框架，以构建能够在生产环境中进行工具编排、迭代式问题求解和自适应任务执行的动态、目标导向系统。

我们在 Amazon 亲眼见证了这种演进：自 2025 年以来，Amazon 各组织内已经构建了数千个 agent。虽然单模型基准测试是评估单个 LLM 在 LLM 驱动应用中表现的重要基础，但 agentic AI 系统要求评估方法发生根本转变。新范式不仅评估底层模型的表现，还评估整个系统涌现出的行为，包括工具选择决策的准确性、多步推理过程的一致性、记忆检索操作的效率，以及生产环境中任务完成的整体成功率。

在本文中，我们介绍一个面向 Amazon agentic AI 系统的综合评估框架，它通过两个核心组件来应对 Amazon 内部 agentic AI 应用的复杂性：一个是通用评估工作流，用于在各类 agent 实现之间统一评估流程；另一个是 agent 评估库，在 [Amazon Bedrock AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 中提供系统化的度量与指标，此外还包括针对 Amazon 特定用例的评估方法和指标。我们还会分享在与多个 Amazon 团队合作过程中总结的最佳实践与经验，为面临类似评估与部署 agentic AI 系统挑战的 AWS 开发者社区提供可落地的洞察。

## Amazon 的 AI agent 评估框架

构建者在设计、开发和评估 AI agent 时会面临重大挑战。与只针对孤立 prompt 生成响应的传统 LLM 驱动应用不同，AI agent 通过多步推理、工具使用和跨多轮交互的自适应决策来自主追求目标。传统 LLM 评估方法把 agent 系统当作黑盒，只评估最终结果，无法提供足够的洞察来判断 AI agent 为何失败或定位根因。尽管业内已有多种专门的评估工具，构建者仍不得不在它们之间来回切换，并投入大量人工来汇总结果。此外，虽然 [Strands Agents](https://aws.amazon.com/blogs/opensource/introducing-strands-agents-an-open-source-ai-agents-sdk/)、[LangChain](https://docs.langchain.com/oss/javascript/langchain/agents) 和 [LangGraph](https://www.langchain.com/langgraph) 等 agent 开发框架内置了评估模块，但构建者想要的是与框架无关的评估方式，而不是被锁定在某个框架内置的方法里。

另外，AI agent 中健壮的自省与错误处理能力，要求系统性地评估 agent 如何在推理、工具使用、记忆处理和行动执行的整个生命周期中检测、分类并从失败中恢复。例如，评估框架必须衡量 agent 识别各类失败场景的能力，例如推理模型给出的不当规划、无效的工具调用、格式错误的参数、非预期的工具响应格式、身份验证失败以及记忆检索错误。生产级 agent 必须表现出一致的错误恢复模式，并在遇到异常后仍能保持用户交互的连贯性。

为满足这些需求，大规模部署在生产环境中的 AI agent 需要持续监控和系统化评估，以便及时发现并缓解 agent 衰退与性能下降。这要求 agent 评估框架简化端到端流程，并提供接近实时的问题检测、通知与问题解决能力。最后，引入 [human-in-the-loop](https://en.wikipedia.org/wiki/Human-in-the-loop)（HITL）流程对于审计评估结果至关重要，有助于确保系统输出的可靠性。

为应对这些挑战，我们提出一个整体性的 agentic AI 评估框架，如下图所示。该框架包含两个关键组件：自动化的 AI agent 评估工作流和 AI agent 评估库。

[![ML-20173_image_1](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/11/ML-20173_image_1.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/11/ML-20173_image_1.jpg)

自动化的 AI agent 评估工作流通过四个步骤驱动这一整体评估方法。

**步骤 1**：用户定义用于评估的输入，通常是 agent 执行产生的 trace 文件。这些输入可以是 agent 完成任务后采集、并通过统一 API 访问点上传到框架的离线 trace，也可以是用户可自行定义评估维度和指标的在线 trace。

**步骤 2**：使用 AI agent 评估库自动生成默认的和用户自定义的评估指标。该库中的方法在下文列表中说明。

**步骤 3**：评估结果通过 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/pm/serv-s3/) 存储桶共享，或通过一个可视化展示 agent trace 可观测性与评估结果的仪表板共享。

**步骤 4**：通过 agent 性能审计与监控来分析结果。构建者可以定义自己的规则，在 agent 性能下降时发送通知，并采取措施解决问题。构建者还可以借助 HITL 机制，安排对 agent trace 子集和评估结果的定期人工审计，从而持续提升 agent 质量与性能的一致性。

AI agent 评估库跨三层运作：计算并生成针对 agent 最终输出的评估指标、评估 agent 的各个组件，以及衡量为 agent 提供支持的底层 LLM 的表现。

- **底层**：对多个基础模型进行基准测试，以选出为 AI agent 提供支持的合适模型，并确定不同模型如何影响 agent 的整体质量与延迟。
- **中层**：评估 agent 各组件的表现，包括意图检测、多轮对话、记忆、LLM 推理与规划、工具使用等。例如，中层判断 agent 是否正确理解用户意图、LLM 如何通过[思维链](https://www.promptingguide.ai/techniques/cot)（CoT）推理驱动 agentic 工作流规划、工具选择与执行是否与 agentic 规划一致，以及规划是否成功完成。
- **上层**：评估 agent 的最终响应、任务完成情况，以及 agent 是否达成用例中定义的目标。它还覆盖整体的责任与安全、成本以及客户体验影响。

[Amazon Bedrock AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 提供自动化评估工具，用于衡量你的 agent 或工具在某项特定任务上表现如何、能否处理边缘情况，以及在不同输入和上下文中能否保持一致。在 agent 评估库中，我们基于 AgentCore Evaluations 的内置配置、评估器和指标，为 agent 的最终响应及其各组件提供了一组预定义评估指标。我们还进一步扩展了该评估库，加入针对 Amazon 异构场景复杂度和应用特定需求的专门指标。库中的主要指标包括

- **最终响应质量：**  **Correctness**：AI 助手对给定任务的响应在事实层面的准确性与正确性。**Faithfulness**：AI 助手的响应是否与对话历史保持一致。**Helpfulness**：AI 助手的响应在帮助用户恰当处理查询并朝目标推进方面有多有效。**Response relevance**：AI 助手的响应在多大程度上针对了具体问题或请求。**Conciseness**：AI 助手传达信息的效率，例如响应是否在不遗漏关键信息的前提下足够简短。
- **任务完成：**  **Goal success**：AI 助手是否在一个对话会话内成功完成所有用户目标。**Goal accuracy**：将输出与 ground truth 进行比较。
- **工具使用：**  **Tool selection accuracy**：AI 助手是否为给定情境选择了合适的工具。**Tool parameter accuracy**：AI 助手在发起工具调用时是否正确使用了上下文信息。**Tool call error rate**：AI 助手发起工具调用时出现失败的频率。**Multi-turn function calling accuracy**：是否在调用多个工具，以及这些工具按正确顺序被调用的频率有多高。
- **记忆：**  **Context retrieval**：评估检索结果的准确性，从记忆中为给定查询找出最相关的上下文，依据相似度或排序优先处理相关信息，并在精确率与召回率之间取得平衡。
- **多轮对话：**  **Topic adherence classification**：如果多轮对话涉及多个主题，评估对话在交互过程中是否保持在预定义的领域与主题内。**Topic adherence refusal**：判断 AI agent 是否拒绝对某个主题的问题作出回答。
- **推理：**  **Grounding accuracy**：模型是否理解任务、是否恰当选择工具，以及 CoT 是否与所提供的上下文和外部工具返回的数据一致。**Faithfulness score**：衡量整个推理过程中的逻辑一致性。**Context score**：agent 采取的每一步是否有上下文依据。
- **责任与安全：**  **Hallucination**：输出是否与既有知识、可验证数据、逻辑推理相符，或是否包含任何不合情理、误导性或完全虚构的元素。**Toxicity**：输出是否包含有害、冒犯、不尊重或助长负面情绪的语言、建议或态度。这包括可能具有攻击性、贬低他人、带有偏见，或在缺乏建设性目的的情况下过度批判的内容。**Harmfulness**：AI 助手的响应中是否存在潜在有害内容，包括侮辱、仇恨言论、暴力、不当性内容和刻板印象。

有关其他 agent 输出质量指标，或如何创建适合你特定用例与评估要求的自定义评估器，请参阅 [AgentCore evaluation templates](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/prompt-templates-builtin.html#correctness)。

## 评估 Amazon 实际使用的真实 agent 系统

过去几年，Amazon 一直在推进构建 agentic AI 应用的方式，以应对复杂的业务挑战，简化业务流程、提升运营效率并优化业务成果——从早期实验走向跨多个业务部门的生产级部署。这些 agentic AI 应用以企业级规模运行，部署在 AWS 基础设施之上，改变了 Amazon 全球运营中完成工作的方式。本节我们介绍几个 Amazon 的真实 agentic AI 用例，以展示 Amazon 团队如何利用上一节讨论的框架，通过整体性评估提升 AI agent 的性能。

### 评估 Amazon 购物助手 AI agent 中的工具使用

为向 Amazon 消费者提供顺畅的购物体验，Amazon 购物助手需要与来自 Amazon 底层系统的众多 API 和 Web 服务无缝交互，如下图所示。该 AI agent 需要接入来自 Amazon 底层系统的数百个、有时是数千个工具，以便与消费者进行长时间的多轮对话。agent 使用这些工具提供个性化体验，包括客户画像、商品与库存发现以及下单。然而，手工为 AI agent 接入这么多企业 API 和 Web 服务是一个繁琐的过程，通常需要数月才能完成。

[![ML-20173_image_2](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/11/ML-20173_image_2.jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/11/ML-20173_image_2.jpg)

把遗留 API 和 Web 服务转化为与 agent 兼容的工具，需要为 API 和 Web 服务的端点系统地定义结构化 schema 与语义描述，从而使 agent 的推理与规划机制能够在任务执行过程中准确识别并选择与上下文相符的工具。定义不佳的工具 schema 和不精确的语义描述会导致 agent 运行时出现错误的工具选择，进而调用无关的 API，不必要地扩大上下文窗口、增加推理延迟，并通过冗余的 LLM 调用推高计算成本。为应对这些挑战，Amazon 制定了跨组织的工具 schema 与描述规范化标准，建立了一套治理框架，对参与工具开发和 agent 集成的所有构建者团队规定了强制性合规要求。这一标准化举措为工具接口、参数定义、能力描述和使用约束确立了统一规范，有助于确保跨不同组织单元开发的工具保持结构模式一致、语义清晰，从而产生可靠的 agent-工具交互。所有参与工具开发和 agent 集成的构建者团队都必须遵守这些架构规范，这些规范规定了工具签名、输入校验 schema、输出契约和人类可读文档的标准化格式。这有助于确保企业级 agentic 系统中工具表示的一致性。此外，手工为数百或数千个工具定义 schema 和描述是一项沉重的工程负担，而当多个 API 需要协同编排才能完成复合任务时，复杂性会大幅上升。Amazon 构建者实现了一套 API 自接入系统，使用 LLM 自动生成标准化的工具 schema 和描述。这显著提升了把大量 API 和服务接入为 agent 兼容工具的效率，加快了集成周期并减少了手工工程开销。为在 API 集成完成后评估工具选择和工具使用情况，Amazon 团队为回归测试创建了 golden 数据集。这些数据集使用 LLM 从历史 API 调用日志中针对用户查询合成生成。借助预定义的工具选择和工具使用指标（如 tool selection accuracy、tool parameter accuracy 和 multi-turn function call accuracy），Amazon 构建者可以系统地评估购物助手 AI agent 的能力：是否正确识别合适的工具、是否用准确的值填充参数，以及在多轮对话中是否保持连贯的工具调用序列。随着 agent 持续演进，快速可靠地把新 API 作为工具集成到 agent 中并评估其工具使用表现的能力变得愈发关键。对 agent 在生产环境中功能可靠性的客观评估，有效降低了开发开销，同时在 agentic AI 应用中保持稳健的性能。

### 评估 Amazon 客服 AI agent 中的用户意图检测

在 Amazon 客服领域，AI agent 在受理客户咨询和解决问题方面发挥着关键作用。这些系统的核心是一项关键能力：由一个编排 AI agent 使用其推理模型准确检测客户意图，这决定了客户的查询是否被正确理解，并被路由到由 agent 工具或子 agent 实现的相应专门解决器，如下图所示。意图检测准确性的影响很大。当客服 agent 误解客户意图时，会引发一连串问题：查询被路由到错误的专门解决器、客户收到不相关的响应，挫败感不断累积。这既影响客户体验，也会导致运营成本上升，因为会有更多客户寻求人工 agent 介入。

[![ML-20173_image3.](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/11/ML-20173_image3..jpg)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/02/11/ML-20173_image3..jpg)

为评估 agent 在意图检测上的推理能力，Amazon 团队开发了一个 LLM 模拟器，使用由 LLM 驱动的虚拟客户画像来模拟多样化的用户场景与交互。评估主要聚焦于编排 agent 生成的意图是否正确，以及是否路由到正确的子 agent。仿真数据集包含一组从匿名化历史客户交互中收集的用户查询与 ground truth 意图配对。使用该模拟器，编排 agent 会针对仿真数据集中的用户查询生成意图。通过将 agent 响应的意图与 ground truth 意图比较，我们可以验证 agent 生成的意图是否符合 ground truth。

除了意图正确性，评估还覆盖任务完成情况——agent 的最终响应与意图解决——这是客服任务的最终目标。对于多轮对话，我们还纳入 topic adherence classification 和 topic adherence refusal 指标，以帮助确保对话连贯性和用户体验质量。随着 AI 客服系统持续演进，针对用户意图检测的 agent 推理评估只会越来越重要，其影响也超出即时的客户满意度。它还能优化客服运营效率和服务交付成本，从而最大化 AI 投资的回报。

### 评估 Amazon 的多 agent 系统

随着企业在复杂业务环境中越来越多地面对多方面挑战，从跨职能工作流编排到不确定性下的实时决策，Amazon 团队正逐步采用多 agent 系统架构，把单体式 AI 解决方案拆解为专门化、可协作的 agent，使其能够进行分布式推理、动态任务分配和大规模自适应问题求解。一个例子是涵盖多个 AI agent 协作的 Amazon 卖家助手 AI agent，如下图所示。

该 agentic 工作流以 LLM 规划器和任务编排器开始，接收用户请求，把复杂任务拆解为专门化的子任务，并根据各底层 agent 的能力和当前负载，智能地把每个子任务分配给最合适的 agent。随后，底层 agent 自主运行，利用各自的专门工具、推理能力和领域专长执行所分配的任务以完成目标，无需编排器持续监督。任务完成后，这些专门 agent 会把结果回传给编排 agent，报告任务状态更新、完成确认、中间结果，或在遇到超出其职责边界的场景时提出升级请求。编排 agent 汇总这些响应，监控整体进度，处理子任务之间的依赖关系，并把各方的输出综合为一个连贯的最终结果，以应对原始用户请求。为评估这种多 agent 协作过程，评估工作流同时考虑单个 agent 的表现和整体的系统协同动态。除了评估专门 agent 在任务完成、推理、工具使用和记忆检索方面的整体任务执行质量与表现，我们还需要衡量 agent 间通信模式、协调效率和任务交接准确性。为此，Amazon 团队使用规划得分（子任务成功分配给子 agent 的比例）、通信得分（用于完成子任务的 agent 间通信消息）和协作成功率（成功完成子任务的百分比）等指标。在多 agent 系统评估中，HITL 变得至关重要，因为复杂性提升、意外涌现行为的可能性增加，而自动化指标可能无法捕捉这些情况。在评估工作流中引入人工介入，为以下方面提供了必要的监督：评估 agent 间通信以识别特定边缘情况下的协调失败、评估 agent 专门化是否恰当以及任务拆解是否与 agent 能力匹配，并验证当 agent 给出相互矛盾的建议时可能采用的冲突解决策略。它还有助于确保多个 agent 共同参与同一决策时的逻辑一致性，以及整体 agent 行为服务于既定的业务目标。这些维度难以仅靠自动化指标量化，但对生产部署的成功至关重要。

## 经验教训与最佳实践

通过与在生产环境中部署 agentic AI 系统的 Amazon 产品和工程团队的广泛合作，我们总结出了关键的经验教训，并确立了最佳实践，以应对大规模评估自主 agent 架构的独特挑战。

- **跨多个维度的整体评估**：agentic 应用评估必须超越传统的准确性指标，覆盖一个包含 agent 质量、性能、责任与成本的综合评估框架。质量评估包括衡量推理一致性、工具选择准确性和多样化场景下的任务完成成功率。性能评估捕捉生产工作负载下的延迟、吞吐和资源利用率。责任评估涉及安全性、毒性、偏见缓解、幻觉检测和护栏，以符合组织策略与监管要求。成本分析既量化直接费用（包括模型推理、工具调用、数据处理），也量化间接成本（如人力投入和错误补救）。这种多维度方法有助于确保在平衡各种权衡的前提下实现整体优化。
- **用例与应用特定的评估：** 除前面各节讨论的标准化指标外，应用特定的评估指标也有助于整体的应用评估。例如，客服应用需要客户满意度分数、首次接触解决率和情感分析分数等指标来衡量最终的业务成果。这种方式要求与领域专家紧密协作，定义有意义的成功标准、确定合适的指标，并创建能反映真实运营复杂度的评估数据集，从而完成整个评估过程。
- **把 human-in-the-loop（HITL）作为关键评估环节：** 正如多 agent 系统评估案例所讨论的，HITL 不可或缺，尤其对高风险决策场景而言。它提供对 agent 推理链、多步工作流一致性，以及 agent 行为与业务要求是否对齐的必要评估。HITL 还有助于为构建 golden 测试数据集提供 ground truth 标签，并校准自动评估器中 LLM-as-a-judge 的输出，使其与人类偏好对齐。
- **生产环境中的持续评估：** 维持质量至关重要，因为部署前评估可能无法完整刻画性能特征。同时，生产评估会监控真实世界的表现，覆盖上线前未曾体现的多样化用户行为、使用模式和边缘情况，以识别随时间推移的性能下降。你可以通过运营仪表板跟踪关键指标、设置告警阈值、自动化异常检测流程，并建立反馈闭环。一旦发现问题，就可以启动模型再训练、优化上下文工程，并与最终业务目标保持一致。

## 结论

随着 AI 系统日益复杂，彻底的 AI agent 评估方法的重要性怎么强调都不为过。通过覆盖质量、性能、责任和成本维度的整体评估，再加上持续的生产监控和 human-in-the-loop 验证，就可以覆盖 agentic AI 从开发到生产的完整部署生命周期。你可以借鉴本文给出的示例、最佳实践和经验教训——其中许多已在 Amazon Bedrock AgentCore Evaluations 中提供——来加速自己的 agentic AI 计划，同时避开评估设计与实施中的常见陷阱。
