# Wood Mackenzie 在 Amazon Bedrock AgentCore 上的共享 agentic 平台

构建一个可用的 agentic 原型只需要一个下午，而把它推向生产才是工作量爆炸的地方。一旦 agent 需要服务多个用户，就会浮现出一层新的工程问题，而能否判断 agent 在真实流量下是否做对了事也变得至关重要。并发、会话隔离、身份、持久状态、扩缩容和护栏，这些都是大多数团队每次都要从零重建的层次，尽管为每个 agent 提供一套标准化平台是更可复用的做法。

结果是实验与生产之间存在巨大的鸿沟。截至 2026 年初的行业调研显示，企业级 AI 实验几乎已经普及，但只有约四分之一的组织哪怕在单一职能中把 agent 扩展到生产环境。在 Wood Mackenzie 内部，我们发现 88% 的 AI 概念验证从未进入大规模部署。各家分析机构给出的原因相当一致，而且大多是架构层面的，而非模型层面的。Forrester 把 agent 的失败主要归因于歧义、协调不当和不可预测的系统行为，而不是普通 bug。被提及最多的单一阻碍因素是评估与可观测性：团队无法提前可靠地判断一个非确定性 agent 何时会出错，标准回归测试也抓不住这类问题。治理与身份紧随其后，很大一部分高管表示他们无法立即关停一个行为异常的 agent。而在这一切之下，是重复建设的基础设施：每个团队都重新实现认证、护栏、记忆和追踪，并把模型硬编码，以至于更换提供商就意味着重写代码。

这正是共享 agentic 平台要解决的问题。与其让每个团队重建相同的基础，不如由一个 runtime 统一处理编排、安全、可观测性、身份和连接性，团队则把精力放在让产品形成差异化的业务逻辑上。

在本文中，我们将展示我们如何构建 APEX（Agentic Platform for Energy eXperience），这是一个共享平台，让每个团队都能交付 agent 而无需重复造基础设施。APEX 构建在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 之上，后者是一个用于大规模构建、连接和优化 agent 的平台，支持任何框架和模型。我们将介绍为什么我们选择 AgentCore 而不是自托管方案、架构是如何组成的、APEX Studio 如何为团队提供统一的控制平面来运维它，以及我们如何把交互式 AI 带入真实应用——既服务像 Woody 这样的内部用户，也服务像 Lens 这样的外部消费者。我们还会深入探讨同一套基础设施如何在身份感知的权益（entitlements）机制下同时服务这两类用户、我们如何弥合让大多数 agent 计划停滞的评估与治理缺口，以及随着多 agent 系统成为默认形态，这个平台将走向何方。

## 为什么需要共享平台，为什么选择 AgentCore

在 APEX 之前，有三个应用各自走在构建自己 agent 技术栈的路上：Woody、Lens AI 和 ST Trading App。如果放任不管，每一个都会搭起自己的 runtime、接上自己的身份、外挂自己的可观测性，并把模型硬编码。我们就会把同一笔基础设施成本付三遍，最终得到三个无法共享记忆、工具或评估的栈。

AgentCore 通过提供一个能够满足企业级 agentic 部署需求的平台解决了这个问题。我们按生产平台的要求评估了 AgentCore：托管模式、成本模式、是否与模型无关、可扩展性、治理和企业支持。

| **框架** | **托管方式** | **成本模式** | **模型无关** | **可扩展性** | **治理** | **企业支持** |
| --- | --- | --- | --- | --- | --- | --- |
| LangChain | 自托管 | 免费/企业版 | 是 | 手动 | 自行实现 | 社区 |
| LangChain | 自托管/ LangSmith | 免费 + LangSmith | 是 | 手动 | LangSmith | 社区 |
| CrewAI | 自托管/ CrewAI-Cloud | 免费/ 云版 | 是 | 有限 | 基础 | 社区 |
| n8n | 自托管/ 云版 | 免费/ 专业版 | 否 | 中等 | 工作流 | 社区 + 专业版 |
| Frontier Model Direct | 提供商托管 | 按 token 计费 | 否 | 提供商管理 | 无 | 提供商 SLA |
| Bedrock AgentCore | AWS 托管 | 按使用量付费 | 是 | 自动扩缩容 | 原生 Amazon Bedrock Guardrails 与 Policy | AWS 企业级 SLA |

AgentCore 为我们提供的是一个托管平台，而不是一个需要我们自己运维的库。它可与任何开源框架配合使用，包括 Strands Agents、LangGraph、LangChain、LlamaIndex、CrewAI、Google ADK、OpenAI Agents SDK，并且可与任何模型配合，无论该模型是否运行在 Amazon Bedrock 上。它同时支持 Model Context Protocol（MCP）和 Agent-to-Agent（A2A）协议。这意味着我们不必在开源灵活性与 AWS 服务安全性之间做选择。这让我们得以标准化平台层，同时让每个团队自由选择自己的框架和模型。

有五个能力让我们下定了决心：

- **托管基础设施。** 没有集群需要运维。AWS 负责扩缩容、打补丁和可用性，因此我们的平台团队专注于 agent 能力，而不是后端管道。AgentCore 于 2025 年 10 月正式可用（GA），在 GA 时所有服务都增加了对 Amazon Virtual Private Cloud（VPC）、AWS PrivateLink、AWS CloudFormation 和资源标签的支持。
- **真正的模型无关。** Claude、GPT-4.1、Amazon Nova、Mistral 和 Llama 都可以通过单一平台访问。团队可以用一个模型做规划、用另一个模型执行，可以通过更换提供商来做性价比测试，或者摆脱某个发布后出现回归的模型，而不会丢失对话上下文，也不必触碰业务逻辑。
- **自动扩缩容。** AgentCore runtime（Amazon Bedrock AgentCore 的一项能力）可以从零扩展到数千个并发 agent 调用，无需容量规划，并具备完整的会话隔离和最长 8 小时执行窗口。
- **原生护栏与身份。** 内容过滤、个人身份信息（PII）检测和策略执行都是托管能力，而不是每个团队都要重新实现的东西。Amazon Bedrock AgentCore 中的 [Policy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html) 与 Gateway 集成，实时拦截每一次工具调用，并把自然语言规则转换为 Cedar——AWS 的开源策略语言——因此开发、合规和安全团队无需编写自定义代码就能编写和审计规则。AgentCore Identity（Amazon Bedrock AgentCore 的一项能力）增加了 AWS Identity and Access Management（IAM）集成、VPC 隔离和加密，因此 agent 能够满足你的合规要求，并可在已定义的访问控制下代表用户行事或自主行事。
- **AWS 企业支持。** AWS Enterprise Support 提供 7×24 支持，以及技术客户经理（TAM）和客户团队关系，帮助客户根据自身需求影响 AgentCore 这类产品的路线图。

AgentCore 采用[按使用量计费](https://aws.amazon.com/bedrock/agentcore/pricing/)，没有预付承诺或最低费用。每项服务独立计费，因此团队可以只采用单一能力，例如 AgentCore memory（Amazon Bedrock AgentCore 的一项能力），而不必迁移整个 agent。runtime 的计费基于按秒计算的活跃 CPU 和内存消耗，且在 I/O 等待期间不计 CPU 费用。这对 agentic 工作负载很重要——它们通常有 30–70% 的时间在等待模型响应、工具调用或数据库查询。如果使用预分配算力，你就要为这些空闲时间付费；使用 AgentCore 则不必。

## 解决方案概览

APEX 按层次组织，如图 1 所示。最上层是最终用户与三个应用交互：Woody、Lens AI 和 ST Trading App。这些应用与 APEX 前端通信，前端对外提供一个框架，让产品团队可以把 agentic 能力放入用户界面，而无需每次都重建与后端的连接。APEX 后端则是 AgentCore 发挥作用的地方。

后端旁边还有两条基础设施轨道。WM 基础设施即代码（IaC）框架使用 AWS Cloud Development Kit（AWS CDK）和 GitHub 来预置平台资源并做版本管理，护栏也在代码中定义。MCP 层通过标准协议（而非定制的点对点集成）把平台连接到第三方和外部访问，包括 AWS Marketplace 和合作伙伴系统。

用户通过 APEX 前端 SDK 访问这三个应用。APEX 后端运行在 AgentCore 上（Runtime、Identity、Gateway、Memory、Observability），并配有 Orchestrator、用于检索的向量数据库、通过 Amazon Bedrock 模型目录获得的模型访问，以及 Amazon Bedrock Guardrails。WM IaC 框架通过 AWS CDK 和 GitHub 预置资源，MCP 层则连接外部系统。

![APEX 分层架构：三个应用调用 APEX 前端 SDK、AgentCore 后端，以及 WM IaC 与 MCP 两条轨道](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/16/ML-21057-1.png)

图 1：APEX 参考架构

在后端内部，一个请求会流经以下组件。

**用户认证与 AgentCore Identity** 确定调用者是谁、以及被授予了哪些操作权限。身份与权益贯穿每一次 agent 调用，而不是在边缘检查一次，因此代表用户行事的 agent 会在每一次下游工具调用和数据调用中携带该用户的权限。与自选身份提供方的联邦也是重要的一环。我们把 Okta 作为唯一可信源（source of truth）。

**Orchestrator** 负责路由请求，并查询 Woodmac Agent Registry——这是一个在组织范围内发现、共享和复用 agent、工具与技能的单一场所，内置治理和审批工作流。一个团队的 agent 就是这样在不复制代码的情况下提供给另一个团队使用。

**AgentCore runtime** 在无服务器、会话隔离的环境中托管 agent 代码。在 runtime 内部，我们运行 AI Agents Studio（基于 Amazon Quick 构建，支持 Strands Agents、LangGraph、CrewAI、n8n、Vertex 和 OpenAI），因此每个团队都能保留自己偏好的框架。runtime 通过 Amazon Bedrock 模型目录调用模型，模型无关在这里变得具体：agent 按名称指向某个模型，我们更换提供商时无需重写 agent。

**工具** 以可组合的构建块形式暴露给 agent。架构图展示了 Wood Mackenzie 如何使用 Code Interpreter 工具进行安全代码执行，以及使用 Amazon Nova Act web 工具执行浏览器操作。这些工具通过 **AgentCore Gateway**（Amazon Bedrock AgentCore 的一项能力）访问，它把 API、AWS Lambda 函数和现有 MCP 服务器转换为 agent 兼容的工具，并提供用于发现和调用的单一安全端点。Gateway 从 Tools Repository 拉取信息用于发现和调用，并支持 IAM、OAuth 2.1 和 API key 认证。

**基于向量数据库的检索增强生成（RAG）** 让 agent 以我们自己的内容（包括非结构化文档）为依据，因此回复基于检索到的事实，而不是仅依赖模型的参数化记忆。我们使用 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 以无服务器、托管的方式为 agent 提供 RAG。

**AgentCore memory** 为 agent 提供短期和长期上下文，因此对话可以跨会话持续，agent 之间也能共享状态，而不必各自维护一个存储。

**Amazon Bedrock Guardrails 与 Policy** 治理允许的 prompt 并拦截工具调用，执行内容过滤、PII 检测以及前面介绍的基于 Cedar 的规则。

**可观测性与评估** 决定一个 agent 能否在生产中存活。agent 的输出是非确定性的，因此难回答的问题不是 *它能不能工作*，而是 *我们能否察觉它什么时候不再工作*。AgentCore Observability（Amazon Bedrock AgentCore 的一项能力）以兼容 OpenTelemetry 的格式向 Amazon CloudWatch 发送遥测数据，覆盖会话数、延迟、时长、token 用量和错误率。Wood Mackenzie 随后可以把单个请求从一个会话追踪到具体的 span，并在正确的步骤呈现各组件日志，而不是让它们散落在各个日志组中。在此之上，AgentCore Evaluations（Amazon Bedrock AgentCore 的一项能力）为有用性、工具选择、准确性等质量维度提供了内置评估器，并支持基于模型的自定义打分，因此我们可以针对真实流量给 agent 打分。

## APEX Studio：控制平面

前面描述的架构是 runtime。APEX Studio 是运维它的后台，是一个统一界面，团队可以在其中构建、部署和监控 agent，而无需触碰底层基础设施。它是位于 AgentCore 之上、面向人类的控制平面，也是团队从一个想法走到一个上线 agent 的方式——不必为每一步提工单。

图 2 所示的 Studio 仪表盘让人一眼看清平台的运行状态：活跃的 agent、工作流和连接器，以及最近的部署及其状态，运维人员因此可以看到哪些在生产中运行、哪些仍在预发布环境。六项能力覆盖了 agent 的生命周期。

**Agent Builder** 是模板驱动的 agent 创建，团队配置 agent 的人格、工具和护栏，而不是手工接线。这是实践中的黄金路径（Golden Path）：新的 agent 从一个铺好的模板开始，而不是从一个空白仓库开始。

**Workflow Designer** 是可视化的多步骤编排，支持分支、循环和人在回路（human-in-the-loop）步骤，因此多步骤流程可以在一处组合和审阅，而不必分散编码在各个服务里。

**Connector Registry** 让团队浏览、配置和发布兼容 MCP 的数据连接器。它是运维人员对前面所述同一套 gateway 和工具层的视图，使工具发布保持受治理并可跨团队复用。

**Live Chat Testing** 提供实时 agent 交互，用于在生产部署前进行验证。评估纪律正是从这里开始。运维人员在 agent 触达用户之前用真实输入演练它，这是抵御那些让大多数 agent 计划停滞的非确定性故障的第一道防线。

**App Deployment** 覆盖从构建到生产上线的完整应用生命周期，**Monitoring Dashboard** 则在一处呈现 agent 的健康状况、成本、延迟和准确性指标，数据来自 AgentCore Observability 和 Evaluations。两者合在一起，闭合了从交付 agent 到观察它上线后行为的回路。

在 Studio 之下是我们称为 vibe coding 的内嵌软件开发生命周期（SDLC）集成：团队可以通过自然语言创建一个 agent，并配有自动化测试、预览和一键生产部署。这与贯穿整个平台的理念一致：运维人员表达意图，平台负责构建、测试脚手架和部署，因此从一个想法到一个受治理的生产 agent，所需时间以小时计。

图 2：APEX Studio 控制平面

该仪表盘展示活跃的 agent、工作流和连接器及其最近的部署状态，并在 AgentCore 之上提供 Agent Builder、Workflow Designer、Connector Registry、Live Chat Testing、App Deployment 以及 Monitoring Dashboard。

APEX 中承担最多工作的单一集成模式，是我们在 AgentCore Gateway 上构建的轴辐式（hub-and-spoke）模型，如图 3 所示。没有它，每个消费者都要为每个数据服务维护一条定制连接。当有 N 个消费者和 M 个服务时，这就是一个 N×M 的集成问题：每新增一个应用或 agent，都会让我们必须构建、加固和维护的点对点连接数量成倍增加，而且每条连接都会重复实现相同的横切关注点。

轴辐式模型避免了这一点。每个应用和 agent 都通过一个 gateway 连接，而不是各自持有到每个数据服务的连接。在消费者侧，内部分析师、客户聊天机器人和交易 agent 都与同一个枢纽通信。在数据侧，gateway 扇出到 Lens Direct（分析与曲线）、Short Term Trading（实时执行）、Digital Content（上游模型）以及 P&R Dataset 计算器。新增一个消费者或一个数据服务，意味着把一根辐条接到枢纽上，而不是重建整张网状结构。

![轴辐式示意图：消费者通过一个 AgentCore Gateway 连接，再由它扇出到 Lens Direct、Short Term Trading、Digital Content 和 P&R Dataset](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/16/ML-21057-3.png)

图 3：统一 MCP Gateway

消费者（内部分析师、客户聊天机器人、交易 agent）通过一个使用 MCP 协议的单一 Amazon Bedrock AgentCore Gateway 连接，再由它扇出到数据服务（Lens Direct、Short Term Trading、Digital Content、P&R Dataset）。横切关注点在枢纽处统一执行一次。

该 gateway 使用 Model Context Protocol（MCP），因此无论每根辐条后面是什么，它都呈现一致的工具接口。AgentCore Gateway 把现有 API、AWS Lambda 函数和现有 MCP 服务器转换为 agent 兼容的工具，并作为单一安全端点，让 agent 无需自定义集成代码即可发现和调用这些工具。它支持 IAM、OAuth 2.1 和 API key 认证，通过 AWS Marketplace 采购的 AWS 合作伙伴工具也可以直接导入该 gateway。

由于流量汇集到一个枢纽，这些横切关注点在 gateway 处统一执行一次，而不是在每个消费者或辐条中重新实现：身份、可观测性、评估与护栏、技能与工具、限流、数据保护和合规。策略一旦落到枢纽，就会立即在所有地方生效；每一次工具调用都会继承相同的身份上下文、相同的遥测和相同的护栏。MCP 服务器选项对外部访问的重要性也体现在这里：通过受治理的 MCP 端点暴露我们的数据服务，意味着合作伙伴可以通过单一受控接口直接进行 AI 驱动的数据访问，而不是通过蔓延的点对点集成。

## 生成式 UI：用 AG-UI、A2UI 和 Strands 实现动态组件

只有当 agent 能把它的工作呈现给用户时，平台才有用；而为每个 agent 重建流式、有状态的界面，会重新引入 APEX 本要消除的那种重复。我们用解决连接性的同样方式来解决表现层：共享协议。APEX 前端 SDK 构建在两个互补协议之上，由 CopilotKit 提供 Web 组件和工具链。

AG-UI 是传输层。它是 agentic 后端与面向用户的应用之间的双向、事件驱动的 runtime 连接，通过标准 HTTP 或 Server-Sent Events 承载一连串类型化事件，例如 token 流式输出、工具调用和状态更新。它可跨技术栈工作，从 Web 到移动端再到命令行。

A2UI 是载荷。它是一份由 Google 发起的声明式生成式 UI 规范，agent 用它把 UI 作为组件的 JSON 蓝图返回，而不是返回文本或可执行代码。客户端从自己受信任的原生 widget 目录中渲染每个组件，这既让 UI 与宿主应用的样式保持一致，也避免了任意代码执行。AG-UI 把 A2UI 蓝图传送到前端，CopilotKit 作为发布合作伙伴支持 A2UI。简而言之：A2UI 描述 agent 想要显示什么，AG-UI 负责传送，客户端负责渲染。

agent 本身是运行在 AgentCore runtime 中的 Strands agent。Strands 直接与 AG-UI 集成，这一组合为我们带来三项能力，ST Trading App、Lens AI 和 Woody 都在复用它们而不是重建。

**流式聊天。** AG-UI 处理用户与 agent 之间的消息流式传输，因此对话界面只是一个配置好的组件，而不是手工搭建的传输层。

**基于工具的生成式 UI。** 动态组件正是来自这里。agent 不只是返回文本。AG-UI 与客户端共享工具信息，客户端把一次工具调用映射到某个已渲染的组件。当 agent 调用工具时，前端用该工具的参数渲染匹配的组件，因此来自 Lens Direct 的曲线分析请求或来自 Short Term Trading 的实时执行结果，会以活的 widget 形式返回，而不是一大段文字。对于更复杂的场景，agent 会发出 A2UI 蓝图，客户端从自己受信任的组件目录中渲染它，因此 agent 可以组合出一个界面、一张图表、一个表单、一张结果卡片，而无需前端事先硬编码。agent 已经暴露的工具，只要在客户端加一个小小的渲染绑定，就变成了一个 UI 元素——这就是把可组合构建块原则应用到了界面上：单个 widget 或完整工作流，都由同样的部件组装而成。

**共享状态。** Strands agent 是有状态的，AG-UI 会双向同步该状态。agent 能够看到用户在界面中做出的变更，界面也会反映 agent 更新的状态，因此用户修改参数与 agent 修订计算结果可以保持同步，而无需定制接线。

部署沿用标准的 AgentCore 路径。Strands agent 配置完成后被启动到 AgentCore runtime 上，后者暴露 `POST /invocations` 交互端点和 `GET /ping` 健康检查。认证通过 [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) 处理，使用由 Amazon Cognito 支撑的 OAuth 授权器，因此在 gateway 处治理工具调用的同一套身份模型也治理 UI 会话。随后前端用 bearer token 连接到已部署的 runtime 端点，生成式 UI 就在生产中上线了。

结果是：团队只需编写 agent 逻辑、绑定工具和组件蓝图，就能新增一个由 agent 支撑的功能，而流式传输、状态同步、身份和生产 runtime 都来自平台。

### Lens 中的 AG-UI：实时仪表盘上的交互式 AI

最清晰的例子是 Synapse AI，即嵌入在我们 Lens 应用中的生成式 AI 助手。正在查看 Lens Power Summary 仪表盘的用户可以在侧面板中打开该助手，用自然语言提问，例如哪些国家的可再生能源装机容量最多。该 agent 不会用通用网络搜索来回答。它会调用 `extractWidgetConfig` 工具，读取用户正在查看的仪表盘上已有的排行 widget 的配置和数据，然后返回一张按国家排列的太阳能和风能装机容量表格，并内联渲染在对话中。

这正是 AG-UI 发挥其本来作用的地方。agent 的推理步骤和工具调用在发生时即以类型化事件流式进入面板，因此用户能看到 agent 先思考、再行动，而不是对着转圈的加载指示器等待。结果不是以段落形式返回，而是以 agent 组合出的结构化表格返回，并由客户端从其组件目录中渲染。而且由于助手读取的是仪表盘自身的 widget 状态，回复基于用户已经信任的数据，而不是一次毫无关联的查询。这个交互式助手是 Strands agent 之上的一个配置化界面，因此 Lens 无需自行构建传输层、状态同步机制或渲染流水线，就得到了一个基于真实数据、可流式、贴合上下文的分析师。

### Woody 中的 agentic 流程：把工具编排成可交付成果

Woody 是我们内部的 Wood Mackenzie 应用，它展示了同一套协议如何承载一个运行更久的流程——把多个工具串联成一份成品交付物。在某一个流程中，分析师给 Woody 一条指令：同时使用网络来源和 Lens Direct 数据集研究伊朗冲突对油价的影响，生成图表，并制作一份 PowerPoint 演示文稿。

接下来是 agent 规划并跨多个工具执行。它先对任务进行推理，检查自己有哪些可用工具，然后按顺序使用它们：用于开源研究的 web 搜索 agent 工具、用于我们专有数据的 Lens Direct MCP 服务器、用于生成可视化的 Vega-Lite 图表工具，以及用于组装输出的 PowerPoint 生成器。agent 会随时流式输出推理过程和访问状态——网络研究完成、Lens Direct 数据已取回——然后交付一个研究包：四张交互式图表（分别覆盖油价走势、供应中断与缓冲机制、价格情景对比以及霍尔木兹海峡流量），外加一份可下载的 15 页演示文稿。一个自然语言请求变成了一条协同的多工具工作流，最终产出分析师可以直接使用的成果物。

这个流程中有两点对「平台」这个论点很重要。第一，agent 在一次运行中混合了公共 web 工具、专有 MCP 数据连接器、图表工具和文档生成器，而它们每一个都是通过 gateway 访问的独立构建块。更换图表库、新增数据连接器，或把同一套工作流指向另一个模型，都不会改变 agent 的逻辑，因为工具是组合出来的，而不是硬编码的。第二，agent 通过 Lens Direct MCP 服务器访问了我们的专有数据，这与外部消费者会使用的连接器模式相同，而这正好引出了下一点。

Woody 还会在人在回路的情况下处理风险更高的操作。在另一个独立流程中，分析师要求 Woody 创建并训练一个内部天然气需求模型。agent 在模型的 GitHub 分支上工作，然后在一个明确的检查点暂停，提示需要审阅 `GUIDANCE.md` 文件，并列出在训练开始前需要在 `train.py` 或 `inference.py` 中完成的具体修改，且在分析师确认之前不会继续。Task Tracker 侧面板渲染实时运行状态、模型参数（例如采暖度日和制冷度日、天然气价格、储气水平、可再生能源发电量）以及结构化的结果载荷，并通过 AG-UI 共享状态与 agent 保持同步。这就是 Workflow Designer 的人在回路模式在 runtime 中强制执行：agent 未经批准不会采取任何有后果的操作，正是这一控制让我们可以把模型流水线的真实职责交给它。

### 一个平台，内外兼用，由权益机制治理

Lens 和 Woody 的例子运行在同一套基础设施上。Woody 服务内部用户——Wood Mackenzie 内的分析师和研究员；Lens 中的 Synapse 服务外部消费者；而 MCP 连接器把我们的数据暴露给合作伙伴系统。这三者都是同一个 AgentCore runtime、同一个 gateway、同一个模型目录，以及同一套可观测性和护栏。不同的不是技术栈，而是在枢纽处施加的访问与权益控制。身份贯穿每一次 agent 调用，因此治理「内部分析师能训练和部署什么」的权益，与治理「外部消费者能查询什么、合作伙伴的 MCP 客户端能访问什么」的权益，是同一套机制。我们不会为员工跑一个平台、为客户再跑第二个平台。我们跑一个平台，让身份感知的授权决定每个调用者能看到什么、做什么。

正是这个单一基础，让工作流能够以团队本来就熟悉的常规方式实现可组合。由于 agent 注册在 Woodmac Agent Registry 中、工具和连接器通过 gateway 发布、模型从目录中选择，团队只需挑选所需的 agent、工具和连接器并把它们拼装起来，就能组装出一条工作流——无论消费者是内部研究员还是外部客户，都是同一套乐高积木模型。伊朗冲突研究流程和模型训练流程，就是用同一货架的部件以不同组合搭建的。新增一个连接器、更换一个工具，或把两个 agent 组合成一条工作流，都是 APEX Studio 中的配置变更，而不是一次重新平台化，而且每种组合都会继承在枢纽处执行的身份、护栏和追踪。

## 平台工程原则

APEX 不只是一张架构图。它由六条原则治理，这些原则决定了我们如何构建和运维它。

**可组合的构建块。** 每个能力都是独立的积木，既可以单独使用，也可以叠加成更大的工作流。团队可以只取 AgentCore memory，或只取 Gateway，也可以把整套能力组装成一个自主工作流。按需选取，拼装起来，交付产品。

**为飞轮加速。** 为一个团队解决一个问题，就会为所有团队产生一个通用解决方案。当我们为 Lens AI 构建身份感知的工具访问能力时，ST Trading App 直接继承了它。

**抽象掉无差别的繁重工作。** 安全、合规、基础设施、数据和 AI 都集中在平台中，因此产品团队把时间花在让产品形成差异化的地方，而不是无差别的管道上。统一的 MCP Gateway 是最清晰的例子：身份、限流和合规在枢纽处统一执行一次，而不是在每个消费者中重建。

**为复用而组件化。** 黄金路径和可复用 SDK 可以减轻样板代码负担。前端 SDK 和 agent 注册表，让新团队从一条铺好的路径开始，而不是从一张白纸开始。

**解耦演进。** 我们严格分离平台代码和业务逻辑。由于 AgentCore 的各项服务是托管且独立版本化的，我们可以在团队脚下升级平台而不打扰它的 agent。

**价值复利。** 更多采用会降低下一次创新的边际成本。这个平台是价值放大器：每加入一个团队，都会让下一个团队更快。

## 下一步走向：多 agent 系统

单个 agent 是起点，而不是终点。贯穿 2026 年的明确行业方向是多 agent 系统——由不同团队、最终是不同组织所拥有的 agent 相互协调，完成任何单个 agent 无法完成的工作。这一转变取决于位于不同层次的两个开放协议。MCP 是纵向层，把 agent 连接到工具和数据，这正是我们的 gateway 已经标准化的部分。Agent-to-Agent（A2A）协议是横向层，让 agent 彼此发现、委派和协作。这个两层栈——工具用 MCP、agent 用 A2A——正在成为企业 agent 部署的默认架构；A2A 已在广泛的厂商支持下转到 Linux Foundation 治理，而 AgentCore runtime 已经支持 A2A。

APEX 的构建方式是为了生长到这个形态，而不是为此重建。由于每个 agent 都注册在 Woodmac Agent Registry 中并通过受治理的端点访问，一个 Lens 分析 agent、一个 Short Term Trading 执行 agent 和一个研究 agent 可以组合成单一工作流，其中一个 agent 把子任务委派给另一个，而每一跳仍然携带在枢纽处执行的相同身份上下文、护栏和追踪。今天让我们把工具组装成一个 agent 的可组合构建块原则，正是明天让我们把 agent 组装成一个团队的同一条原则。

基于现有的架构，可以自然延伸出三项具体扩展。第一，跨我们自身各领域的 agent 对 agent 工作流，这样一个交易问题可以从分析 agent 取一条曲线、从 P&R agent 取一项计算，而无需人工把这些步骤串起来。第二，受治理的外部协作——同一个为合作伙伴提供直接数据访问的 MCP 服务器端点，可以在我们已执行的权益和审计轨迹下，暴露选定的 agent，用于跨组织的 A2A 协调。第三，有控制的更深自主性——把针对实时流量的 AgentCore Evaluations 与针对每次工具调用的 Policy 执行配成一对，这样当 agent 承担运行更久、风险更高的任务时，护栏也随之扩展。平台层把上述每一项都作为新能力来吸收，而不是重写，这正是「一次建好」的意义所在。

## 结论

大多数 agent 计划停滞，不是因为模型不够好，而是因为围绕它的基础设施缺失：没有共享的 runtime、没有一致的评估、没有受治理的身份，而且每个用例都要重建重复的管道。通过在 Amazon Bedrock AgentCore 上做标准化，我们把三个并行的 agent 构建工作变成了一整套共享平台。现在团队可以在数小时内而不是数月内构建一个 agent，在不触碰业务逻辑的情况下更换模型，并在第一次调用时就带着护栏、追踪、身份和评估交付到生产。平台层是托管的、与模型无关的、可自动扩缩容的，并且只按每个 agent 实际消耗的资源计费。

结果是，我们的团队把时间花在让客户使用的能源产品形成差异化的业务逻辑上，而不是第四次重建认证、记忆和可观测性。随着更多团队采用 APEX，下一个 agent 的边际成本持续下降；又因为平台构建在开放的 MCP 和 A2A 协议之上，今天运行单个 agent 的同一套基础可以延伸到即将到来的多 agent 系统。要了解更多，请查阅 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 文档、了解 [AgentCore 定价](https://aws.amazon.com/bedrock/agentcore/pricing/)，或留下评论。
