# 使用 Terraform 为基于 RAG 的生成式 AI 应用部署 Amazon Bedrock Knowledge Bases

检索增强生成（RAG）是一种强大的方法，它通过为基座模型（FM）提供额外且相关的数据来构建[生成式 AI 应用](https://aws.amazon.com/generative-ai/)。该方法提升了响应的准确性与透明度，同时避免了 FM 训练或微调可能带来的成本与复杂度。

许多客户使用 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 来帮助实现 RAG 工作流。你可以在 AWS 管理控制台中通过几次点击，为初始开发部署一个 Amazon Bedrock 知识库并建立与数据源的连接。当需要把开发环境迁移到用于生产部署的基础设施即代码（IaC）模板时，从现有的 IaC 项目模板起步会很有帮助，因为还有一些额外的配置细节需要指定，而这些细节在控制台中被抽象掉了。虽然已有基于 CDK 的模板可用于搭建 Bedrock 知识库，但许多组织仍把 [Terraform](https://www.terraform.io/) 作为他们首选的基础设施即代码框架。

在本文中，我们提供一套 Terraform IaC 解决方案，用于部署 Amazon Bedrock 知识库并建立数据源连接，帮助你快速上手用 Terraform 部署 RAG 工作流。你可以在我们的 [AWS Samples GitHub 仓库](https://github.com/aws-samples/sample-bedrock-knowledge-base-terraform) 中找到该解决方案。

## 解决方案概述

该解决方案使用 Terraform 自动化创建并配置以下 AWS 服务组件：

- [AWS Identity and Access Management（IAM）role](https://aws.amazon.com/iam/)：在各服务之间建立安全的访问与执行策略。
- [Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/)：配置索引集合，以高效地管理与查询大规模数据集。
- Amazon Bedrock Knowledge Bases：为 FM 与 agent 提供来自你的数据源的上下文信息，从而给出相关、准确、定制化的响应。

## 前提条件

要成功部署该解决方案，请确保具备以下前提条件：

- **AWS 账户**：需要一个有效的 AWS 账户。如果你还没有，可以使用 [AWS 管理控制台](https://aws.amazon.com/console/) 创建一个账户。
- **IAM role 与权限**：确保你拥有一个具备创建与管理 AWS 资源所需权限的 [AWS Identity and Access Management（IAM）](https://aws.amazon.com/iam/) role 与用户。该配置应包含处理 Amazon S3、Amazon OpenSearch Service 与 Amazon Bedrock 等 AWS 服务的权限。
- **Terraform**：确保本地机器上已安装 Terraform。详细说明请参阅 [AWS Modernization Workshop with Hashicorp Terraform Cloud](https://hashicorp-terraform.awsworkshop.io/) 中提供的安装指南。
- **AWS CLI**：使用适当的凭证配置 [AWS Command Line Interface（AWS CLI）](https://aws.amazon.com/cli)，以便与你的 AWS 资源交互。设置说明请参阅[为 AWS CLI 配置设置](https://docs.aws.amazon.com/cli/v1/userguide/cli-chap-configure.html)。
- **文档存储**：创建一个 [Amazon S3](https://aws.amazon.com/pm/serv-s3/?gclid=Cj0KCQjwyL24BhCtARIsALo0fSAIX2UV4qimf9YmL0HzdkLldRWjGh0R0zyPngHpcRHfKcKPCATBQNoaArRZEALw_wcB&trk=b8b87cd7-09b8-4229-a529-91943319b8f5&sc_channel=ps&ef_id=Cj0KCQjwyL24BhCtARIsALo0fSAIX2UV4qimf9YmL0HzdkLldRWjGh0R0zyPngHpcRHfKcKPCATBQNoaArRZEALw_wcB:G:s&s_kwcid=AL!4422!3!536324516040!e!!g!!amazon%20s3!11539706604!115473954714) 存储桶，并以受支持的格式上传文档，例如 TXT、MD HTML、DOC、DOCX、CSL、XLS、XLSX 或 PDF。确保你的 S3 存储桶已正确配置，以便与部署所涉及的其他 AWS 服务协同工作。

如果你需要用于测试的示例文档，我们建议使用 AWS Well-Architected Framework 指南，你可以[下载其 PDF](https://docs.aws.amazon.com/pdfs/wellarchitected/latest/framework/wellarchitected-framework.pdf)。

## Amazon Bedrock 模型访问权限

请确保你已在 Amazon Bedrock 中启用对某个基座模型（FM）的访问权限，用于生成嵌入。该解决方案默认使用 Titan Text Embeddings V2 模型。你可以按以下步骤在 Amazon Bedrock 中启用模型访问权限：

- 导航到 **Amazon Bedrock 控制台**。
- 在导航窗格的 **Bedrock Configurations** 下选择 **Model access**。
- 选择 **Enable specific models**。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/15/ML-17524-model-access.png)

- 选择 **Titan Text Embeddings V2** 模型。
- 选择 **Next** 并填写访问申请表单以启用该模型。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/15/ML-17524-Embedding-Model-Selection.png)

## 搭建项目

- **克隆仓库：**  决定你想把仓库克隆到哪里。这可以是：    **本地机器：**如果你直接在笔记本或台式机上工作。**EC2 实例：**如果你从远程服务器部署该配置。**AWS CloudShell：**如果你更愿意使用 AWS 基于浏览器的命令行界面。   使用[受支持的方法](https://registry.terraform.io/providers/hashicorp/aws/latest/docs#authentication-and-configuration)之一为 Terraform 配置你的 AWS 凭证。切换到你所选环境中的相应目录，运行以下命令克隆仓库：  `git clone https://github.com/aws-samples/sample-bedrock-knowledge-base-terraform`  确保环境中已安装 Git，且你的 SSH 密钥已配置为可访问该仓库。

- **进入克隆后的目录：**  `cd sample-bedrock-knowledge-base-terraform`
- **更新 AWS Region：**  **用途**：在 Terraform 配置中设置 AWS Region，以确保使用正确的区域。**默认值**：无默认值。必须由用户提供。**更新位置**：  **文件**：main.tf **行**：查找 `"aws"` provider 块。  `provider "aws" { region = "us-east-1" # Update this to your desired AWS region}`
- **提供 S3 存储桶名称：**  **用途**：指定用于存储知识库数据的 S3 存储桶。**默认值**：无默认值。必须由用户提供。**更新位置**：  **文件**：`main.tf` **行**：在 `"knowledge_base"` module 块中查找 `"kb_s3_bucket_name_prefix"` 变量。  `module "knowledge_base" { source = "./modules" kb_s3_bucket_name_prefix = "your-s3-bucket-name" # Replace with your bucket name }`
- **为知识库 module 设置额外的配置项（可选）：
**
`knowledge_base` module 还接受其他可选输入，用于自定义 chunking 策略、所使用的嵌入模型以及所创建知识库资源的名称等设置。   `module "knowledge_base" { ... chunking_strategy = "FIXED_SIZE" kb_model_id = “amazon.titan-embed-text-v2:0” kb_name = “myKnowledgeBase” ... }`  关于可用于控制嵌入维度与其他 chunking 行为等细粒度设置的更多 module 输入变量，请参阅 `modules/variables.tf` 文件。
- **验证并部署 stack：**

## 知识库部署的进阶自定义选项：

Terraform module 为用户提供了根据具体使用场景自定义各项参数的灵活性。这些配置可以在 `variables.tf` 文件中快速调整。本节说明如何调整 chunking 策略与 OpenSearch 向量维度以满足你的需求。

### 自定义 chunking 策略与 token 上限

*chunking 策略*决定了知识库如何把内容切分为更小、更易管理的 chunk 以便高效处理。该 module 支持以下策略：

- **DEFAULT**：标准 chunking，无额外自定义。
- **FIXED_SIZE**：把内容切分为固定 token 大小的 chunk，可选重叠。
- **HIERARCHICAL**：创建具有父子结构的层级 chunk。
- **SEMANTIC**：根据语义含义切分内容，以改善上下文分组。

**修改固定大小 chunking（可选）**

如果你选择 `FIXED_SIZE` 作为 chunking 策略，还可以进一步自定义：

- **每个 chunk 的最大 token 数**：调整 `fixed_size_max_tokens` 变量。
- **chunk 之间的重叠**：配置 `fixed_size_overlap_percentage` 变量。

```
variable "fixed_size_max_tokens" {
  type        = number
  description = "Maximum number of tokens for fixed-size chunking"
  default     = 512
}
variable "fixed_size_overlap_percentage" {
  type        = number
  description = "Percentage of overlap between chunks"
  default     = 20
}
```

**修改层级 chunking（可选）**

对于 `HIERARCHICAL` chunking，你可以调整：

- **父 chunk 与子 chunk 的 token 上限**：使用 `hierarchical_parent_max_tokens` 与 `hierarchical_child_max_tokens`。
- **重叠 token：** 配置 `hierarchical_overlap_tokens` 变量。

```
variable "hierarchical_parent_max_tokens" {
  type        = number
  description = "Maximum tokens for parent chunks"
  default     = 1000
}
variable "hierarchical_child_max_tokens" {
  type        = number
  description = "Maximum tokens for child chunks"
  default     = 500
}
variable "hierarchical_overlap_tokens" {
  type        = number
  description = "Number of tokens to overlap in hierarchical chunking"
  default     = 70
}
```

**修改语义 chunking（可选）**

对于 `SEMANTIC` chunking，你可以自定义：

- **最大 token 数**：使用 `semantic_max_tokens` 变量。
- **缓冲区大小**：调整 `semantic_buffer_size`。
- **断点百分位阈值**：修改 `semantic_breakpoint_percentile_threshold`。

```
variable "semantic_max_tokens" {
  type        = number
  description = "Maximum tokens for semantic chunking"
  default     = 512
}
variable "semantic_buffer_size" {
  type        = number
  description = "Buffer size for semantic chunking"
  default     = 1
}
variable "semantic_breakpoint_percentile_threshold" {
  type        = number
  description = "Breakpoint percentile threshold for semantic chunking"
  default     = 75
}
```

### 自定义 OpenSearch 集合的向量维度

向量维度定义了所选模型生成的嵌入大小，并影响 OpenSearch 集合内搜索的精度。你可以在 `variables.tf` 文件中调整 `vector_dimension` 变量：

```
variable "vector_dimension" {
  description = "The dimension of the vectors produced by the model."
  type        = number
  default     = 1024
}
```

视你的使用场景与嵌入模型支持的向量维度取值而定，你可以考虑增大向量维度设置以提升检索精度；若为优化存储与查询性能，你可以考虑减小向量维度设置。

## 在 Amazon Bedrock 中测试知识库：

按以下步骤测试知识库与所选 FM 模型的交互，确认其表现符合预期。

- 导航到 **Amazon Bedrock** 控制台，并在导航窗格中选择 **Knowledge Bases**。
- 选择你创建的知识库。
- 选择 **Sync**，以更新存储在 S3 存储桶中的数据。
- 选择 **Select Model**。
- 在模型选择窗口中，选择你想要的 FM。
- 提交你的问答查询来测试知识库，观察模型的响应情况。

## 清理

为避免产生额外费用，请在测试或使用 Terraform 部署完成后清理你的环境：

**移除基础设施资源**

- 打开终端，切换到包含你的 Terraform 文件的目录。
- 执行以下命令，移除 Terraform 配置中定义的资源：

`terraform destroy`

- 该命令会提示你确认销毁资源。输入 `yes` 继续。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/15/ML-17524-terraform-destoyed-yes.png)

- 以下截图是确认资源已被移除的预期输出。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/15/ML-17524-terraform-destroyed-info.png)

**删除 S3 存储桶内容：**

- 确保删除 S3 存储桶中的所有文件，以避免后续产生费用。

**手动清理状态文件（可选）：**

- 如果你想彻底清理项目目录，执行以下命令移除 Terraform 状态文件：

```
rm -rf .terraform/ 
rm .terraform.lock.hcl
rm terraform.tfstate
rm terraform.tfstate.backup
```

这一过程有助于彻底清理你的环境，并避免与闲置资源相关的潜在费用。
