# 我们如何构建 MCP bridge，让托管在 AgentCore 上的 AI agent 访问本地 MCP 工具

我们的 agent 运行在云端，但用户的电子表格却躺在他们的笔记本电脑上。如何跨越这道鸿沟？

[Model Context Protocol（MCP）](https://modelcontextprotocol.io/) 是 Anthropic 于 2024 年 11 月推出的开源标准，用于统一 AI 模型连接外部数据与工具的方式。MCP 遵循客户端—服务器架构：MCP host（即 [Amazon Quick](https://aws.amazon.com/quick/) 或 Claude Code 这样的 AI 应用）建立到一个或多个 MCP server 的连接。MCP 协议支持两种传输机制：stdio（同一台机器上本地进程之间通信所用的标准 I/O）和可流式 HTTP 传输（远端服务器与客户端之间基于 HTTP 的通信）。缺失的一环是：当 MCP server 位于本地、而 MCP client 位于远端时该怎么办。

这种模式对主要使用 Excel 和本地文件的财务经理与分析人员很重要。他们可以使用集中部署的 AI agent 来操作这些文件，同时还能从浏览器中获取上下文。支撑 [Claude Cowork](https://www.anthropic.com/product/claude-cowork) 这类产品的正是同一种模式——云端 agent 通过 MCP 调用本地工具——只不过我们把它完全自托管在 AWS 上，使用自己的模型和自定义工具服务器。在内网，我们为财务部门构建了一个生产级 AI 助手，上线一年内已承载超过 41,000 次对话。

在本文中，我们以简化形式复现内部构建的成果。我们的 agent 部署在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上，使用运行在用户本机的 MCP server。我们通过 WebSocket 与原生消息传递（native messaging）为 MCP 消息建立隧道，从而在远端 MCP client 与本地 MCP server 之间架起桥梁。我们在“What's Next”一节中讨论更多的生产环境加固措施。完整源代码见 [GitHub](https://github.com/aws-samples/sample-mcp-bridge-agentcore)。

MCP Bridge Demo 扩展正在总结一份本地 Excel 工作簿。托管在云端的 agent 通过 MCP bridge 直接从用户机器读取该文件，并把结构化摘要流式回传到侧边面板

## 架构概览

AgentCore runtime 是 Amazon Bedrock AgentCore 的一项能力，它支撑起一套包含四个组件的架构：

- **AgentCore runtime：** 在云端托管 [Strands agent](https://strandsagents.com/)。该 agent 充当 MCP client，发出工具发现与工具调用请求。
- **浏览器扩展（browser extension）：** 提供聊天界面，并充当双向中继，在 AgentCore runtime（通过 WebSocket）与 MCP Bridge（通过原生消息传递）之间转发 MCP 消息。
- **MCP Bridge：** 一个运行在用户本机的 [FastMCP proxy](https://gofastmcp.com/v2/servers/proxy)，由浏览器通过原生消息传递宿主注册启动。它在原生消息传递信封格式与原始 MCP JSON-RPC 之间做转换。
- **MCP Server：** 一个在本地运行的标准 MCP server。由于 bridge 与它同处一地，二者通信使用 stdio 传输。

下图展示了端到端的消息流。用户通过扩展发送消息，扩展则通过预签名 WebSocket 连接到 AgentCore runtime。当 Strands agent 需要调用工具时，它把一个 MCP JSON-RPC 请求封装在 JSON 信封中，经由 WebSocket 发回扩展。扩展通过原生消息传递把消息原样中继给 bridge。bridge 拆开信封、取出 JSON-RPC 内容，并通过 stdio 转发给 MCP server。响应沿相反路径返回。bridge 把未经修改的 MCP server 响应重新包进信封，经扩展中继到 AgentCore runtime，在那里 agent 消费工具结果并继续生成。

高层次架构图，展示所有组件。浏览器扩展与 MCP Bridge 充当中继，对来自 AgentCore runtime 的 JSON 消息和来自 MCP server 的 JSON-RPC 消息进行封装与拆封

下表展示一次工具调用从 agent 到 MCP server 的传播过程，每一跳都会剥掉一层封装：

| **跳** | **发送方 → 接收方** | **消息** |
| --- | --- | --- |
| 1 | Agent -> 扩展（WebSocket） | {“type”: “mcpbridge”, “content”: {“type”: “mcp”, “payload”: “”}, “session_id”: “session_123”} |
| 2 | 扩展 -> Bridge（原生消息传递） | {“type”: “mcp”, “payload”: “”} |
| 3 | Bridge → MCP Server（stdio） | {“jsonrpc”: “2.0”, “id”: 1, “method”: “tools/call”, “params”: {“name”: “read_sheet”, “arguments”: {“file_path”: “budget.xlsx”}}} |

## Strands agent 在 AgentCore runtime 中如何工作

**WebSocket 连接：** 浏览器扩展通过预签名 WebSocket URL 连接到 AgentCore runtime。启动时，侧边面板经由后台脚本向本地 bridge 发送预签名请求，bridge 使用用户的本地 AWS 凭证和 [bedrock-agentcore 软件开发工具包（SDK）](https://github.com/aws/bedrock-agentcore-sdk-python) 生成一个 SigV4 签名、限定到已部署 runtime ARN 的 `wss://` URL（有效期 5 分钟）。侧边面板向该 URL 打开 WebSocket。凭证从不离开用户机器，也不会进入浏览器。如果连接因 URL 过期或网络中断而断开，侧边面板会在 2 秒后自动请求新的预签名 URL 并重新连接，从而让过期窗口在正常使用中对用户不可见。

**MCP 初始化：** 在发现工具之前，agent 会执行标准的 [MCP 初始化握手](https://modelcontextprotocol.io/specification/2025-03-26/basic/lifecycle#initialization)。它发送带协议版本的 `initialize` 请求，等待服务器的能力响应，然后发送 `notifications/initialized` 通知。只有该握手完成后，服务器才会接受 `tools/list` 和 `tools/call` 请求。

**工具发现：** 每收到一条用户消息，agent 就调用 `tools/list` 并收到一组工具 schema。它把每个 schema 包装成一个 [Strands AgentTool](https://strandsagents.com/docs/api/python/strands.types.tools/#agenttool)，其 `stream()` 方法会通过 bridge 发送 `tools/call` 请求。添加到 MCP server 的工具会在下一次请求时自动可用，无需改动 agent 代码。

**请求—响应关联：** agent 发出的每个 JSON-RPC 请求都会被分配唯一 ID，并以 `(session_id, jsonrpc_id)` 为键注册到 `asyncio.Future` 上。当响应经 WebSocket 返回时，会被匹配到等待中的 Future 并完成解析。这让多个工具调用可以并发进行而不产生歧义。

## 原生消息传递如何工作

我们需要扩展能够与一个长期运行的本地进程通信，且不需要网络权限，也不需要为每条消息弹出用户提示。原生消息传递正好提供了这一点。[Chrome](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging) 与 [Firefox](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging) 都为其扩展支持原生消息传递。浏览器会在用户机器上一个固定位置查找清单文件，其中指定要启动哪个可执行文件。macOS 上 Chrome 的原生消息传递清单文件如下：

```
# Stored at ~/Library/Application\ Support/Google/Chrome/NativeMessagingHosts/com.example.mcp_bridge.json
{
  "name": "com.example.mcp_bridge",
  "description": "MCP Bridge - Routes MCP messages to local servers",
  "path": "/path/to/mcp-bridge-demo/bridge/run_bridge.sh",
  "type": "stdio",
  "allowed_origins": [
    "chrome-extension://<extension_id>/"
  ]
}
```

扩展启动时，后台脚本调用 `chrome.runtime.connectNative("com.example.mcp_bridge")` 在本地启动原生应用。清单中引用的 `run_bridge.sh` 脚本会激活 Python 环境并启动 bridge：

```
#!/bin/bash
cd "/path/to/mcp-bridge-demo/bridge"
source .venv/bin/activate
exec python3 bridge.py
```

原生消息传递宿主进程会在连接存续期间一直存活。每条消息都被序列化为 JSON、以 UTF-8 编码，并在前面加上 32 位的小端字节序消息长度。来自原生消息传递宿主的单条消息最大为 1 MB（以保护浏览器免受行为异常的原生应用影响）。发送给原生消息传递宿主的消息最大为 64 MiB。

## MCP Bridge 如何工作

MCP Bridge 充当两个世界之间的协议翻译器：一边是 Chrome 的原生消息传递协议，另一边是 MCP 标准（基于 stdio 的 JSON-RPC 2.0）。在入站路径上，它从 stdin 剥掉 4 字节长度头，解析 JSON 正文，并拆开信封以取出原始的 JSON-RPC 消息。在出站路径上，它做相反的事：把 JSON-RPC 响应重新包进信封，并带上长度头写回。JSON-RPC 内容本身原样穿过。

在内部，bridge 运行两个并发循环，并通过 FastMCP proxy 相连。主循环从浏览器读取消息、拆开信封，并把 JSON-RPC 内容放入一个输入队列。FastMCP proxy 只启动一次并在 bridge 生命周期内常驻，它从该队列取出消息、经其 stdin 转发给 MCP server 子进程，并把来自服务器 stdout 的响应放入输出队列。第二个后台循环从输出队列读取，把每个响应重新包进信封，并写入 stdout 供浏览器接收。这种双循环设计把浏览器的请求时序与 MCP server 的处理速度解耦，因此 bridge 不会在等待一个缓慢工具完成时阻塞、无法接受下一个请求。

MCP server 本身是 bridge 在启动时派生的子进程，通过 `mcp.json` 文件配置。它会在 bridge 生命周期内持续运行，不存在每次请求的进程开销。新增一个 MCP server 只需一行配置改动。管道工作由 bridge 负责。

```
# mcp.json
{
  "mcpServers": {
    "excel": {
      "command": "python3",
      "args": ["excel_server.py"]
    }
  }
}
```

MCP Bridge 的内部架构。MCP Bridge 把来自浏览器扩展的消息转换为面向 MCP server 的 MCP 协议。I/O 队列与 FastMCP proxy server 协作，把消息转发给本地运行的 MCP server，并把消息中继回浏览器扩展

## 前置条件

部署和测试该 MCP bridge 解决方案需要以下前置条件。它们涵盖浏览器扩展、部署在 AgentCore 上的 agent、MCP Bridge 以及一个示例 Excel MCP server。

### AWS 账户与权限

- 已启用 Bedrock 模型访问权限的 AWS 账户（代码使用 Claude Opus 4.7）。模型可用性因 Region 而异。当前列表请参见 [Amazon Bedrock 模型可用性](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html) 文档。
- 针对 Bedrock AgentCore（`bedrock-agentcore:*`）、AWS CloudFormation、IAM 角色创建和 S3 的 AWS Identity and Access Management（IAM）权限。
- 已配置凭证的 AWS Command Line Interface（AWS CLI）（可用 `aws sts get-caller-identity` 验证）。
- 在目标 Region 中已完成引导（`cdk bootstrap`）的 AWS Cloud Development Kit（AWS CDK）。

### 工具与软件

- Python 3.10+。
- Node.js 20+（用于 AgentCore 命令行接口（CLI））。
- Google Chrome（支持 Manifest V3 侧边面板）。
- Git。

### 安装

- AgentCore CLI：`npm install -g @aws/agentcore`。
- AWS CDK：`npm install -g aws-cdk`。

### 预计时间与成本

- 环境搭建：约 15 分钟（部署、安装扩展并注册 bridge）。
- AgentCore runtime：按调用付费（无空闲成本）。
- Bedrock 模型用量：Claude 的标准按 token 计费。
- 其他组件在本地运行，不产生额外成本。

## 部署解决方案

- **克隆仓库。**  `git clone https://github.com/aws-samples/sample-mcp-bridge-agentcore.git cd mcp-bridge-demo`
- **安装 Python 依赖。**  `chmod +x scripts/setup.sh manifests/install.sh ./scripts/setup.sh`
- **创建 agent 并部署到 AgentCore。**  `npm install -g @aws/agentcore cd agent agentcore create --name McpBridgeAgent --defaults cd McpBridgeAgent cp ../agent.py app/McpBridgeAgent/main.py cp ../mcp_bridge_transport.py app/McpBridgeAgent/ agentcore deploy`  请记下输出中的 runtime Amazon Resource Name（ARN）（或运行 `agentcore status`）。
- **配置 bridge。**用你的 runtime ARN 编辑 `bridge/bridge_config.json`：  `{ "runtime_arn": "arn:aws:bedrock-agentcore:<region>:<account-id>:runtime/<your-runtime>", "region": "us-east-1", "presign_expires": 300 }`  bridge 会使用你的本地 AWS 凭证自动生成预签名 WebSocket URL，无需手动管理 token。
- **加载 Chrome 扩展。**  打开 `chrome://extensions`。开启**开发者模式（Developer mode）**。选择**加载已解压的扩展程序（Load unpacked）**，然后选中 `extension/` 目录。记下卡片上显示的扩展 ID。
- **注册原生消息传递 bridge。**  `./manifests/install.sh <your-extension-id>`  这会创建一个启动脚本并将其注册到 Chrome，以便浏览器可以派生 bridge 进程。

## 安全考量

本文优先展示 MCP bridge 的功能，因此把安全措施限定为以下几项：

- **原生消息传递来源限制：** Chrome 会把调用方扩展的 ID 与原生消息传递清单中的 `allowed_origins` 列表比对，并拒绝未显式列出的扩展的连接。
- **预签名 URL 过期：** WebSocket URL 经 SigV4 签名，5 分钟后过期。凭证保留在用户机器上，不会发送到浏览器。
- **进程隔离：** 扩展、bridge 和 MCP server 各自运行在独立的操作系统进程中，不共享内存。

这一架构特有的主要暴露面就是 bridge 本身。它接受来自云端 agent 的指令，并以用户的文件系统权限在本地执行。关键原则是：agent 不应拥有超出用户显式授予范围的访问权限，而用户始终能看到调用了哪些工具、带了哪些参数。

对于生产系统，除了实现用于内容过滤的 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 之外，我们建议采取以下额外的安全措施：

| **层面** | **需要添加什么** | **为什么** |
| --- | --- | --- |
| 认证 | 要求把 JSON Web Token（JWT）握手作为第一个 WebSocket 帧。在接受消息之前验证该 token（例如通过 Amazon Cognito 和 AWS Systems Manager 中的 HMAC secret）。 | 即使预签名 URL 泄露，也有助于防止未授权使用。 |
| 载荷签名 | 用 Ed25519 对每条 MCP 消息签名（私钥放在 agent 上，公钥放在 bridge 上）。拒绝未签名或被篡改的载荷。 | 确保消息在云端与本地机器之间的传输过程中未被修改。 |
| 文件系统范围限定 | 为 MCP server 可访问的目录配置显式允许列表。拒绝边界之外的路径。 | 有助于防止 prompt injection 诱使 agent 读取敏感文件（SSH 密钥、凭证）。 |
| 审计日志 | 把每次工具调用（工具名、参数、时间戳、结果状态）记录到本地文件。 | 为 agent 在用户机器上做了什么提供可追溯性。 |

## 清理

试验完成后，请移除已部署的资源以避免持续产生费用。

- **移除 AgentCore 部署。** 拆除 CloudFormation 堆栈、IAM 角色和 runtime 资源。  `cd agent/McpBridgeAgent agentcore remove all agentcore deploy`
- **注销原生消息传递 bridge。**  `rm ~/Library/Application\ Support/Google/Chrome/NativeMessagingHosts/com.example.mcp_bridge.json`
- **移除 Chrome 扩展。**  打开 `chrome://extensions`。在 MCP Bridge Demo 卡片上选择**移除**。
- **删除本地文件（可选）。**  `rm -rf mcp-bridge-demo/`

## 下一步

我们的内部生产解决方案包含以下能力。MCP Bridge 充当托管在 AgentCore 上的 agent 观察用户本地系统的窗口。结合浏览器扩展，当前架构还可以扩展以支持更多用例。

### 浏览器操作

浏览器扩展可以仿照 [Playwright MCP 的工具定义](https://github.com/microsoft/playwright/tree/main/packages/playwright-core/src/tools/backend) 实现自己的浏览器工具，并把它们暴露给 agent，以执行点击元素、填写表单、页面导航和截屏等操作。

由于扩展位于 AgentCore agent 与 MCP Bridge 之间充当消息中继，它可以拦截 `tools/list` 和 `tools/call` 这两类 MCP 消息，把浏览器工具注入工具列表，并在本地处理它们的执行。

### 本地工具自动化

bridge 通过 stdio 使用标准 MCP JSON-RPC，因此采用 stdio 传输的 MCP server 无需修改即可兼容。只需在 `mcp.json` 中增加一条条目。示例包括：用于沙箱化文件读写的[文件系统访问](https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem)、用于仓库操作的 [Git](https://github.com/modelcontextprotocol/servers/tree/main/src/git)、用于持久化本地知识图谱的 [memory](https://github.com/modelcontextprotocol/servers/tree/main/src/memory)。可用的 server 目录请参见 [awesome-mcp-servers](https://github.com/punkpeye/awesome-mcp-servers)。

### 把 bridge 打包为独立可执行文件

为便于生产分发，我们使用 PyInstaller 把 bridge 打包成一个独立可执行文件，将 Python 运行时、依赖与配置捆绑进单一可执行文件。原生消息传递清单直接指向该文件，因此用户不必安装 Python 或管理虚拟环境。bridge 在扩展首次启动时即可工作，无需额外设置。

## 结论

在本文中，我们构建了一个 MCP bridge，把 Amazon Bedrock AgentCore 上托管的云端 Strands agent 与运行在用户机器上的本地 MCP 工具服务器连接起来。我们以浏览器扩展作为中继层、以 Chrome 的原生消息传递作为本地传输，在云端与用户的文件系统之间为标准的 MCP JSON-RPC 消息建立隧道，既不向浏览器暴露凭证，也不修改 MCP 协议本身。

借助这一模式，你可以让 agent 保持集中部署与管理，同时赋予它访问必须本地运行的工具的能力，例如 Excel 文件、Git 仓库或其他本地运行的 MCP server。该架构可扩展。你可以用一行配置改动添加新工具，通过扩展叠加浏览器操作，或把 bridge 打包成独立可执行文件以实现无摩擦分发。

要开始实践，请部署[示例仓库](https://github.com/aws-samples/sample-mcp-bridge-agentcore) 并用你自己的 MCP server 做实验。想进一步了解本文用到的服务，请参阅 [Amazon Bedrock AgentCore 文档](https://docs.aws.amazon.com/bedrock-agentcore/)、[Strands Agents SDK](https://github.com/strands-agents/sdk-python) 和 [Model Context Protocol 规范](https://modelcontextprotocol.io/)。
