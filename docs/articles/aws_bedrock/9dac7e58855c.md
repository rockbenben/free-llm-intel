# Hapag-Lloyd 如何借助 Amazon Bedrock 将客户反馈转化为可执行的洞察

[Hapag-Lloyd](https://www.hapag-lloyd.com/en/home.html) 是全球领先的班轮运输公司之一，运营着一支由 313 艘集装箱船组成的现代化船队，总运输能力达 250 万 TEU（Twenty-foot Equivalent Unit，二十英尺等效单位——集装箱运输中衡量载货能力的标准计量单位）。公司维持着 370 万 TEU 的集装箱运力，其中包括业界规模最大、最现代化的冷藏集装箱（reefer）船队之一。班轮运输板块（Liner Shipping Segment）拥有约 14,000 名员工，并在 140 个国家设有 400 多个办事处，Hapag-Lloyd 由此保持着强大的全球布局。通过遍布全球的 133 条班轮航线，我们为各大洲 600 多个港口之间提供可靠的连接。

公司的数字客户体验与工程团队（Digital Customer Experience and Engineering）分布在海堡（Hamburg）和格但斯克（Gdańsk）两地，通过开发和维护面向客户的 Web 与移动产品来推动数字化创新。

过去几年，数字客户体验与工程团队已从一个以交付为导向的渠道，演变为真正的数字产品驱动者，兼具强烈的客户导向、卓越的工程能力与可衡量的业务影响。我们对数字产品承担端到端的所有权，把客户至上的创新与工程技艺相结合，直接支撑增长与业务成果。依托现代化的、自主掌控的技术栈和高水平的工程成熟度，我们致力于始终站在技术前沿。如今，我们正迈出下一步：走向 AI 原生（AI-native），大力投资人工智能这一核心能力。这段旅程的意义在于用 AI 放大强大的工程能力，打造更智能的产品、更快的创新和更大的客户价值。

## **理解用户影响。**

到目前为止，我们的客户反馈分析流程在很大程度上仍是人工和被动响应的。特别是在评审会（review ceremonies）之前，当需要审阅数百条评分和评论时，人工分析客户反馈可能要花上数小时、有时甚至数天。每两周，产品经理会把客户反馈数据导出为 CSV 文件，通读大量评论，并手动归类情感倾向和主题。虽然这项工作很有价值、与产品决策紧密相关，但它重复、耗时且难以规模化，每当需要更快或更深入的洞察时就缺乏灵活性。

借助我们的生成式 AI 解决方案，我们从根本上改变了这一方式。不再手动汇总和解读反馈，我们现在把整个工作流自动化：收集客户评论、提取情感、识别主题，并呈现可执行的洞察。产品经理和团队可以把更少的精力放在操作性分析上，更多投入战略、创新和打造卓越的用户体验。

在这篇文章中，我们将带你了解这套由生成式 AI 驱动的反馈分析解决方案，它基于 [Amazon Bedrock、](https://aws.amazon.com/bedrock/?nc1=h_ls) [Elasticsearch](https://aws.amazon.com/what-is/elasticsearch/?nc1=h_ls)，以及 [LangChain](https://python.langchain.com/docs/introduction/) 和 [LangGraph](https://www.langchain.com/langgraph) 等开源框架构建。Amazon Bedrock 是一项完全托管的服务，通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、DeepSeek、Luma、Meta、Mistral AI 和 Amazon 等领先 AI 公司的高性能基础模型，并提供构建生成式 AI 应用所需的广泛能力，涵盖安全、隐私和负责任的 AI。借助该解决方案，你可以自动摄取客户评论、生成丰富的摘要，并交付有针对性的洞察。这使我们的产品团队能够做出更快、更明智的决策，并持续改进。

我们将带你了解该解决方案的架构与实现，展示如何利用编排、数据管理、安全与隐私等生成式 AI 基础，快速构建一条可扩展、可用于生产的反馈处理流水线（pipeline）。

## **解决方案概览**

用于自动化反馈处理与分析的 AWS 架构：使用 Lambda 函数从 Amazon S3 摄取数据，使用 Amazon Bedrock 提供由 AI 驱动的洞察并由相关方通过 Amazon ECS 访问，使用 Elasticsearch 对反馈数据进行索引和查询，并通过 SES 发送电子邮件通知。

该解决方案构建在 AWS 架构之上，旨在通过可扩展性、可维护性和安全性来应对这些挑战。它使用 [AWS CloudFormation](https://aws.amazon.com/cloudformation/) 进行部署。

- **持续与季度反馈收集**  我们的 Web 和移动应用每月服务数十万名客户。用户可以留下评分和文字评论，帮助我们了解用户体验并改进服务。
- **每日反馈摄取与处理**  一个 [AWS Lambda](https://aws.amazon.com/lambda/) 函数每天运行一次，获取新的反馈条目。我们使用 Amazon Bedrock 对每条开放评论进行**情感分类**（正面、负面、混合或中性），以简化下游分析。处理后的记录会索引到 Amazon OpenSearch Service，它同时充当我们的全文检索引擎和向量数据库。
- **通过 OpenSearch Service 进行交互式反馈探索**  相关方可以通过 OpenSearch Dashboards 获取实时反馈洞察，对用户情感、评分和随时间变化的趋势形成鸟瞰式视图。从情感分布、评分和反馈量等高层级可视化开始，用户可以下钻到具体的应用、功能甚至单条评论。仪表板支持按时间段、评论情感、产品版本等条件筛选，从而实现有针对性的根因分析。例如，产品经理可以可视化某次近期应用更新前后的情感如何逐周变化，或放大查看提到某个具体功能的负面评论。
- **AI 驱动的内部聊天机器人**  我们面向相关方的聊天机器人以 OpenSearch 索引作为知识库进行查询。我们使用 [Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 来保障安全性和可靠性，并确保回答符合我们的品牌与合规标准。产品经理和支持团队可以用自然语言提问，例如“客户最常提到哪些痛点？”，并即时获得上下文丰富的回答。
- **双周洞察报告**  每两周，第二个 Lambda 函数会汇总并分析最新的反馈趋势。它生成一份简洁的报告，包含关键指标、亮点和情感细分。报告会自动发送给我们的产品经理和产品负责人（Product Owner），直接服务于冲刺规划（sprint planning）和路线图讨论。

### **生成式 AI 编排**

编排是我们解决方案的核心基础，因为生成式 AI 工作流通常涉及多个需要协调的步骤。在我们的流水线中，情感分析、生成嵌入（embedding）和索引等数据摄取与处理步骤由 LangChain 编排，它提供了模块化、可复用的组件，用于调用模型、转换数据，以及与 Amazon OpenSearch Service 这类外部系统集成。对于内部聊天机器人，我们依赖 LangGraph 实现多 agent 架构。每个助手都在 LangGraph 中以声明式方式定义，封装各自的逻辑和工具。这种设计让助手灵活且可组合：我们不是采用僵化的分步流程，而是使用基于 agent 的方式，由 LLM 动态选择合适的工具和动作来回答用户查询。这为产品经理和支持团队提供了一种自然、交互式的方式，去探索反馈和相关的运营洞察。

借助 LangChain 的原生支持，与 Amazon Bedrock 模型的集成非常直接。例如，我们的 AI 驱动内部聊天机器人通过 Amazon Bedrock 使用 Claude Sonnet 4.6 模型。我们选择 Claude Sonnet 4.6，是因为它在编码和 agentic 工作流方面具备前沿性能。该模型在多轮对话交流和 agentic 工作流中表现出色，非常适合我们的内部聊天机器人——它需要在与相关方的单轮和多轮交互中保持可靠性能。凭借精确的工作流管理能力，以及同时担任主 agent（lead agent）和子 agent（subagent）角色的能力，Claude Sonnet 4.6 提供了产品经理和支持团队在规模化探索反馈洞察时所需的一致的对话质量。此外，我们利用地理 [Cross-Region Inference Service](https://docs.aws.amazon.com/bedrock/latest/userguide/geographic-cross-region-inference.html)（CRIS）端点，将计算分布到多个 EU AWS 区域，从而无缝应对计划外的流量高峰。这种跨区域能力确保我们的反馈处理流水线在用量高峰期依然保持弹性，同时为全球相关方群体维持一致的性能。该模型通过 LangChain 配置直接应用护栏：

```
from langchain_aws import ChatBedrockConverse

def get_chatbot_model():
    return ChatBedrockConverse(
        client=session.client("bedrock-runtime", region_name="eu-central-1", config=config),
        model="eu.anthropic.claude-sonnet-4-6",         guardrail_config={
            "guardrailIdentifier": settings.GUARDRAIL_ID,
            "guardrailVersion": "DRAFT",
            "trace": "enabled"
        }
    )
```

### **数据管理**

一个 [AWS Lambda](https://aws.amazon.com/lambda/) 函数每天运行一次，将新的反馈条目从反馈仓库抓取到 [Amazon S3](https://aws.amazon.com/s3/)，随后通过 Amazon Bedrock 的语义检测对数据进行归类。数据之后会索引到 Amazon OpenSearch Service，它同时充当我们的全文检索引擎和向量数据库。

### **负责任的 AI**

为了负责任地使用该解决方案，我们使用 Amazon Bedrock Guardrails 实施防护措施。这让我们能够把 **Amazon Bedrock Guardrails** 附加到 AI 交互上，执行内容审核策略，并确保回答符合我们的品牌与合规标准。

借助 AWS CloudFormation，我们将护栏策略定义为基础设施即代码（infrastructure-as-code），并提供了有助于拦截有害内容的配置示例。

### **护栏即代码：CloudFormation**

### **编程式输入校验**

我们还独立使用 Amazon Bedrock Guardrails，在把原始用户输入传给 LLM 之前进行校验，帮助防止 prompt 注入和其他滥用行为：

```
def validate_question_with_guardrail(question: str, user_data: UserData) -> bool:
    client = boto3.client('bedrock-runtime')
    response = client.apply_guardrail(
        guardrailIdentifier=settings.GUARDRAIL_ID,
        guardrailVersion='DRAFT',
        source='INPUT',
        content=[{'text': {'text': question}}]
    )

    if response.get("action") == "GUARDRAIL_INTERVENED":
        print(json.dumps(response, indent=4))
        print(
            f"Prompt was blocked. user_id=[{user_data.user_id}] question=[{question}]"
        )
        return False
    return True
```

通过这套设置，我们构建了一条更安全、可扩展且可解释的流水线，让生成式 AI 在我们的产品反馈全生命周期中负责任且高效地发挥作用。

## **监控**

我们使用 Amazon CloudWatch 监控应用的各个部分，它收集原始数据并将其处理为可读的近实时指标。我们启用了模型调用日志（model invocation logging），用于收集调用日志、模型输入数据和模型输出数据，从而能够采集完整的请求数据、响应数据以及与该调用相关的元数据。Amazon Bedrock 还与 AWS CloudTrail 集成，后者会把针对 Amazon Bedrock 的 API 调用捕获为事件。这会产生可用于进一步优化应用的洞察，例如改善响应延迟或降低成本。

## **后续步骤**

该解决方案每月处理超过 15,000 条反馈，在标注测试数据集上的情感分类准确率达到 95%。团队不再需要花数小时审阅原始反馈，现在几秒内就能收到清晰、结构化的摘要，突出最重要的主题和反复出现的信号。这帮助他们从信息更快地走向行动，把决策周期从数周缩短到数天。随着时间推移，这些报告不仅让我们了解情感何时改善，也让我们明白为何没有改善。通过持续监控客户反馈，我们可以对早期信号迅速反应、调整决策，并在需要时纠正方向。在若干领域，基于这些洞察采取的行动已经带来了更多正面评论和负面反馈的明显减少。一个有力的例子是 Shipping Instructions 中的“Preview”功能。该功能之所以被优先安排，正是为了回应对预览能力缺失的大量负面用户反馈。在发布之后，AI 驱动的报告让我们能够详细追踪用户的反应。专门针对该功能的反馈显示，此前频繁出现的预览能力请求已被有效解决，表明核心用户需求得到了成功满足。与此同时，更广泛的反馈继续揭示应用其他方面可改进之处。AI 洞察也指导了未来的功能规划与优先级排序。基于用户评论，我们创建了新的基于 OpenSearch Service 的仪表板，帮助团队快速核实和分析用户报告的问题。另一个例子是通过 Excel 文件上传货物数据的能力，这是一项被反复要求的功能，AI 建议也对它予以了突出。该功能现已完全可用，预计将显著减少人工工作量，尤其是对大批量货物而言。在评审会上，相关方现在可以实时看到最正面和最负面的评论，以及 AI 生成的建议，从而开展信息更充分、更富成效的讨论。

这套反馈分析解决方案只是我们在各项流程中应用生成式 AI 的一个例子，它标志着我们 AI 原生之旅的开始，而非终点。在我们的 **AI-Native Umbrella Program** 之下——该计划是 AI 采用的单一事实来源——我们的下一个重点是与 Amazon Bedrock 一起建立一个共享且稳健的 AI 基础。通过提供标准化的基础设施、安全与护栏，我们力求让部门内的每个角色——工程、产品与交付（PM、PO、SM）、UX/设计以及运营/支持——都能安全、独立地创建自己的 AI“空间”，同时可以使用一流的基础模型。这样的设置旨在降低实验门槛、简化探索流程，并鼓励在日常工作中动手探索生成式 AI 用例。由此，我们帮助团队更快地把想法转化为影响，同时在各项 AI 举措之间保持一致、负责任和可扩展。
