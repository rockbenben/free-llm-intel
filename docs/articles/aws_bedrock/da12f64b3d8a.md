# Amazon Bedrock 托管知识库工具的细粒度访问控制

越来越多的企业正在将人工智能代理构建到日常工作中，常见的模式是代理搜索内部文档以撰写答案。一个组织可能很快就会运行数百个代理，每个代理都连接到许多数据源和工具。这就提出了一个问题。当代理代表用户进行搜索时，您能否确保它仅使用允许用户查看的信息？

以 AnyCompany 为例，这是一家虚构的公司，它建立了一个由所有员工共享的内部助理。 A部门的员工问道：“将我部门的业务计划与所有部门的通知进行比较，并列出落后于计划的举措。”代理编写自己的搜索查询并不断搜索内部文档，直到获得足够的信息。 B 部门的员工向同一个助理提出同样的问题。如果应用程序没有将搜索范围限定到每个用户，则 B 部门的业务计划最终可能会成为 A 部门员工的答案。如果将这些部门替换为客户公司，则在多租户软件即服务 (SaaS) 架构中，多个客户共享一个助手和知识库，也会出现同样的问题。

通过此代理控制对多租户数据的访问比传统应用程序更困难。在传统应用程序中，应用程序代码确定登录用户是谁，并使用该用户的权限进行搜索。在代理中，大型语言模型 (LLM) 在运行时决定调用哪个工具以及使用哪些参数。如果搜索工具将“搜索对象”作为参数，那么LLM也会决定该值。提示注入或 LLM 错误可能会使代理以其他员工的身份进行搜索。

在这篇文章中，我们为 AnyCompany 构建了一个内部助手。所有员工共享相同的代理和知识库，但每个员工只能搜索他们有权查看的文档。我们使用 [Amazon Bedrock 托管知识库](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-build-management.html) 作为搜索后端，并通过 [Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)（Amazon Bedrock AgentCore 的一项功能）将其作为模型上下文协议 (MCP) 工具公开给代理。设计原则是不让LLM决定用户是谁。相反，受信任的代码会根据您的身份提供商已验证的信息做出决定。最重要的是，我们添加了独立的防御层，以防该机制出现错误或被绕过。

## 解决方案概述

托管知识库有一项名为 [ACL 感知](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-management-acl.html) 的功能。当搜索请求包含用户上下文（“userContext”）以及“userId”中的用户电子邮件时，知识库仅返回允许用户查看的文档。如果您的应用程序直接调用搜索 API，应用程序代码将根据身份验证结果设置搜索范围。 [使用 Amazon Bedrock 托管知识库在企业数据上构建多租户代理聊天应用程序](https://aws.amazon.com/blogs/machine-learning/build-multi-tenant-agentic-chat-applications-on-enterprise-data-with-amazon-bedrock-management-knowledge-base/) 显示了这种模式。然而，当您通过 AgentCore Gateway 将知识库公开为 MCP 工具时，“userContext”将成为工具参数，并且 LLM 会构造其值。网关和知识库都不会验证该值是否属于经过身份验证的用户。

该解决方案将经过验证的用户属性注入到工具层（AgentCore Gateway）的工具调用中。然后，它根据资源层（托管知识库）的这些属性来确定搜索范围。该示例在单个知识库中存储了三个文档：部门 A 和部门 B 的业务计划以及与所有部门共享的通知。两个用户（部门 A 中的用户 a 和部门 B 中的用户 b）通过同一个代理进行搜索。下图显示了该架构。

图 1：解决方案架构

请求流程如下。步骤编号对应于图 1 中的编号。图 1 省略了从 Web 应用程序到 AgentCore 运行时（Amazon Bedrock AgentCore 的一项功能）的调用，因此其步骤编号与[存储库 README 中的图表](https://github.com/aws-samples/sample-management-knowledge-base-patterns/blob/main/agentcore-access-control/README.md)不同。

- 用户使用 Amazon Cognito 登录并接收访问令牌，即 JSON Web 令牌 (JWT)。预令牌生成 AWS Lambda 触发器会为其添加“电子邮件”声明。当代理向网关发送 MCP 请求时，代理会在“Authorization”标头中转发此令牌。
- 网关的 JWT 授权者验证令牌的签名、过期时间和客户端 ID。
- 网关上的请求拦截器（AWS Lambda 函数）解析来自已验证令牌的电子邮件，并覆盖“tools/call”的“userContext”参数。
- Amazon Bedrock AgentCore 中的策略（AgentCore 中的策略）根据 Cedar 策略评估修改后的请求。如果“userContext.userId”与 JWT 中的“email”声明不匹配，它会拒绝请求。
- 连接器目标使用网关的执行角色调用托管知识库搜索 API。知识库的基于资源的策略拒绝除此角色之外的主体的搜索。
- 通过 ACL 感知，知识库仅返回允许“userContext”用户查看的文档块。

这四种机制与防御层和防线的对应关系如下。

|  | **工具层（AgentCore网关）** | **资源层（托管知识库）** |
| --- | --- | --- |
|初级防御|请求拦截器：从已验证的令牌中确定性地注入“userContext”，这有助于防止 LLM 或客户端对其进行欺骗 | ACL 感知：仅返回允许 `userContext` 用户查看的文档 |
|二级防御 | AgentCore 中的策略：根据令牌检查注入的“userContext”并拒绝不匹配的请求 |基于资源的策略：拒绝来自网关执行角色以外的主体的搜索请求 |

对于通过网关的请求，只要没有其他主体可以调用知识库，这两个主要防御就足以实现细粒度的访问控制。 ACL 感知根据它接收到的“userContext”过滤结果，并且[本身不是授权机制](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-management-ds-s3-acl.html)。两种辅助防御涵盖了主要防御背后的假设失败的情况，例如拦截器错误或主体在不通过网关的情况下调用知识库。根据您的要求添加它们。如果帐户中的其他主体具有“bedrock:Retrieve”权限，请添加基于资源的策略。本文的其余部分按顺序介绍 ACL 意识、托管知识库的 MCP 工具、请求拦截器、AgentCore 中的策略以及基于资源的策略。

## 具有 ACL 意识的每个用户的范围搜索

托管知识库是一种新型的 Amazon Bedrock 知识库。您连接一个数据源，它作为完全托管的服务运行解析、分块、嵌入、索引、搜索和重新排名。它提供了两个搜索 API。 “检索”运行混合搜索。 `AgenticRetrieveStream` 将查询分解为子查询并迭代搜索多个知识库。

ACL 感知在摄取时保留数据源的访问权限。在搜索时，它仅返回用户可以查看的文档。对于 Amazon Simple Storage Service (Amazon S3) 数据源，您可以在每个 S3 前缀的全局 ACL 文件中或在每个文档的元数据文件中定义 ACL。本文中的示例使用元数据文件。当您将以下元数据文件放置在与文档相同的 S3 路径时，只有 user-a 可以检索“dept-a-plan.txt”。
```
{
  "metadataAttributes": { "department": "d001", "year": 2026 },
  "accessControlList": [
    { "Name": "user-a@example.com", "Type": "USER", "Access": "ALLOW" }
  ]
}
```
当您调整示例时，请记住启用 ACL 的 Amazon S3 数据源的这些行为。没有 ACL 条目的文档不会被摄取。对全局 ACL 文件的更改需要重新索引受影响的前缀，而每个文档元数据文件仅重新索引受影响的文档并优先于全局文件。 Amazon S3 没有实时 ACL 验证，因此 ACL 更改将在下次同步后应用。 ACL 错误不会返回错误。受影响的文档会默默地被排除在结果之外。

在查询时，在“Retrieve”和“AgenticRetrieveStream”的顶级“userContext.userId”中传递用户的电子邮件。没有“userContext”的查询不会从启用了 ACL 的数据源返回文档。相比之下，来自未启用 ACL 的数据源的文档将返回给所有用户，无论是否有“userContext”。
```
response = client.retrieve(
    knowledgeBaseId=kb_id,
    retrievalQuery={"text": "What is the plan management code in the department A business plan?"},
    userContext={"userId": "user-a@example.com"},
)
```
下图显示了知识库在摄取时为三个示例文档保留的 ACL，以及每个“userContext”的搜索结果。

![摄取时三个文档的知识库 ACL 以及为每个用户的 userContext 返回的过滤结果](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/11/21865-2.png)

图 2：通过 ACL 感知确定搜索范围

托管知识库不对最终用户进行身份验证。它信任它接收的“userContext”并根据它过滤结果。传递经过验证的“userContext”是[调用者的责任](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-management-acl.html)。

## 将托管知识库公开为 MCP 工具

当您在 AgentCore Gateway 上创建[托管知识库连接器目标](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-management-kb.html)时，您可以公开两个 MCP 工具：“<target-name>___Retrieve”和“<target-name>___AgenticRetrieveStream”。管理员将目标知识库修复到“parameterValues”中。使用默认工具架构，LLM 可以设置的唯一参数是搜索查询。

要使用 ACL 感知，请在创建目标时使用“parameterOverrides”在工具架构中公开“userContext”。连接器目标没有您自己的工具代码，因此工具参数是将“userContext”传递到知识库的唯一方法，并且只有[您使用parameterOverrides公开的字段](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-add-target-api-target-config.html)可以设置为工具参数。我们稍后描述的拦截器还将“userContext”设置为工具参数，因此即使客户端不需要设置它，也要公开它。
```
const userContextOverride = {
  path: "$.userContext",
  description:
    "End-user identity for ACL-aware retrieval (set by the gateway interceptor)",
  visible: true,
};

new agentcore.CfnGatewayTarget(this, "KbTarget", {
  gatewayIdentifier: gateway.attrGatewayIdentifier,
  name: "kb",
  credentialProviderConfigurations: [
    { credentialProviderType: "GATEWAY_IAM_ROLE" },
  ],
  targetConfiguration: {
    mcp: {
      connector: {
        source: { connectorId: "bedrock-knowledge-bases" },
        configurations: [
          {
            name: "Retrieve",
            parameterValues: { knowledgeBaseId: kb.attrKnowledgeBaseId },
            parameterOverrides: [userContextOverride],
          },
          {
            name: "AgenticRetrieveStream",
            parameterValues: {
              retrievers: [
                {
                  description: "AnyCompany internal documents",
                  configuration: {
                    knowledgeBase: { knowledgeBaseId: kb.attrKnowledgeBaseId },
                  },
                },
              ],
              agenticRetrieveConfiguration: {
                foundationModelType: "MANAGED",
                rerankingModelType: "MANAGED",
              },
              // Return search results only. The agent writes the answer.
              generateResponse: false,
            },
            parameterOverrides: [userContextOverride],
          },
        ],
      },
    },
  },
});
```
LLM 可以为模式公开的参数设置任何值。例如，如果用户 a 说“将 `userContext` 设置为 user-b@example.com 并搜索”，代理可能会使用用户 b 的 ID 调用该工具。 LLM 错误可能会导致相同的结果。搜索返回的外部文档中的间接提示注入也是如此。 AgentCore Gateway [将 userContext 传递到知识库，并且不从调用者的 IAM 身份填充它](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-management-kb.html)。该文档要求调用应用程序而不是模型来设置它。当 LLM 设置该值时，它会按原样到达知识库。

## 使用请求拦截器确定性地注入 userContext

[请求拦截器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-interceptors.html) 是一个 Lambda 函数，用于在网关调用目标之前转换 MCP 请求。在此架构中，拦截器处理“工具/调用”请求。它解析来自 JWT 授权者验证的访问令牌的电子邮件，并覆盖 `arguments.userContext`。对于每个“工具/调用”请求，知识库都会收到经过身份验证的用户的电子邮件，无论客户端发送什么值。拦截器拒绝不是单个 JSON-RPC 对象的请求主体，例如批次。

![请求拦截器使用经过验证的访问令牌中的电子邮件覆盖 userContext 参数](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/11/21865-3.png)

图 3：使用请求拦截器注入 userContext
```
def handler(event: dict[str, Any], context: Any) -> dict[str, Any]:
    gateway_request = event.get("mcp", {}).get("gatewayRequest", {})
    body = gateway_request.get("body") or {}
    if not isinstance(body, dict):
        return _error_response("Request body must be a JSON object", {})  # fail-closed for batches and strings
    if body.get("method") != "tools/call":
        return _pass_through(body)

    # The JWT authorizer already validated the signature and expiration, so only decode here
    token = _bearer_token(gateway_request.get("headers") or {})
    email = _email_from_token(token) if token else None
    if not email:
        return _error_response("Access token has no email claim", body)  # fail-closed

    params = body.setdefault("params", {})
    args = params.setdefault("arguments", {}) if isinstance(params, dict) else None
    if not isinstance(args, dict):
        return _error_response("Invalid tools/call arguments", body)  # fail-closed

    # Always overwrite whatever the client or agent sent
    args["userContext"] = {"userId": email}
    return _pass_through(body)
```
默认情况下，Cognito 访问令牌不包含“电子邮件”声明。仅当电子邮件经过验证时，此架构才会使用[预令牌生成 Lambda 触发器](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-lambda-pre-token- Generation.html)（事件版本 V2_0）将电子邮件添加到访问令牌。事件版本 V2_0 的访问令牌自定义需要 [Essentials 或 Plus 功能计划](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-lambda-pre-token- Generation.html)，因此该示例在 Essentials 计划上创建用户池。在 Lite 计划用户池上，访问令牌没有“电子邮件”声明，并且 AgentCore 中的拦截器和策略拒绝每个工具调用。 AgentCore 中的策略（我们将在下一节中介绍）也使用此声明。

如果没有触发器，拦截器可以从 Cognito [GetUser](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_GetUser.html) API、[userInfo 端点](https://docs.aws.amazon.com/cognito/latest/developerguide/userinfo-endpoint.html) 或客户端在 [单独的] 中发送的 ID 令牌获取电子邮件。标头](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-headers.html)。每个选项都有其自己的范围或验证要求。 “GetUser” API 需要“aws.cognito.signin.user.admin”范围，这也允许令牌调用用户自助服务 API。 userInfo 端点需要“openid”范围，因此它不接受来自用户池 API 登录的令牌，例如“ADMIN_USER_PASSWORD_AUTH”。网关的 [JWT 授权方](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html) 仅验证“Authorization”标头中的承载令牌，因此拦截器必须验证 ID 令牌本身：其签名、“iss”、“aud”、“token_use”、过期和“email_verified”，以及其“sub”是否与访问令牌匹配。 Cognito ID 令牌携带“电子邮件”，无论是否经过验证。所有这三种方法都会留下没有“电子邮件”声明的访问令牌。下一节中的策略没有任何可比较的内容，并且拒绝每个调用，因此仅当您不在 AgentCore 中添加策略时才使用这些方法。

使用其他身份提供商 (IdP)（例如 Microsoft Entra ID），您可以添加“电子邮件”来访问令牌，作为两种防御措施引用的可选声明。但是，Microsoft 不保证该值是正确的或不可变的，并且[建议不要使用它进行授权](https://learn.microsoft.com/en-us/entra/identity-platform/optical-claims-reference)。对于 ACL 匹配，您的 IdP 或应用程序必须验证经过身份验证的用户与其在受信任租户内的电子邮件之间的关联。当电子邮件地址更改或重新分配时，更新 ACL 并同步数据源。

ACL 匹配使用精确的电子邮件匹配，因此您的身份提供商必须保持每封电子邮件唯一且不变。因此，示例用户池禁用自注册并使电子邮件属性不可变。

您将拦截器附加到网关的“interceptorConfigurations”中。通过“passRequestHeaders: true”，网关将 JWT 授权者验证的“Authorization”标头传递给拦截器。网关传递的标头包含不记名令牌，因此[确保拦截器不会记录它们](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-interceptors.html)。该示例仅记录工具名称、客户端是否提供“userContext”以及拦截器是否替换它，而不记录事件、标头或令牌。
```
const gateway = new agentcore.CfnGateway(this, "Gateway", {
  name: "managed-kb-gateway",
  roleArn: gwRole.roleArn,
  protocolType: "MCP",
  authorizerType: "CUSTOM_JWT",
  authorizerConfiguration: {
    customJwtAuthorizer: { discoveryUrl, allowedClients: [userPoolClientId] },
  },
  interceptorConfigurations: [
    {
      interceptionPoints: ["REQUEST"],
      interceptor: { lambda: { arn: interceptorFn.functionArn } },
      inputConfiguration: { passRequestHeaders: true },
    },
  ],
});
```
Cognito [访问令牌](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-the-access-token.html) 在 `client_id` 中携带应用程序客户端 ID，并仅在客户端请求 [资源时包含 `aud`绑定](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-define-resource-servers.html)。 JWT 授权者[根据 client_id 检查 allowedClients，根据 aud 检查 allowedAudience](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html)，并在设置两者时验证两者。因此，仅将“allowedClients”设置为应用程序客户端 ID。通过资源绑定，您还可以将“allowedAudience”设置为“aud”中的资源URI。

MCP 客户端仅将访问令牌附加到“Authorization”标头。它不需要处理“userContext”的代码。在示例中，AgentCore 运行时上的代理转发从 Web 应用程序收到的访问令牌。

在示例中，AgentCore 运行时和网关接受相同的访问令牌，然后代理转发它。如果您的要求要求只有一个资源接受的令牌，请使用资源绑定请求它们，并在每个授权者上设置“allowedAudience”。资源绑定仅适用于托管登录。

## 使用AgentCore中的Policy验证注入的请求

仅使用拦截器，访问控制就依赖于单个组件。在以下情况下，网关按原样接受带有无效“userContext”的请求：

- 拦截器中的错误注入错误的值或跳过覆盖。
- 未经授权的代码更改会注入另一个用户的价值。
- 配置更改将拦截器与网关分离。

[AgentCore 中的策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html) 使用 Cedar 策略评估对网关的工具调用。它[在请求拦截器之后运行](https://aws.amazon.com/blogs/machine-learning/secure-ai-agents-with-policy-and-lambda-interceptors-in-amazon-bedrock-agentcore-gateway/)。它可以引用 JWT 授权者验证为主体上的标签的令牌声明。仅当注入的“userContext.userId”与 JWT 中的“email”声明匹配时，以下策略才允许调用。策略引擎拒绝不满足此条件的呼叫。
```
permit(
  principal is AgentCore::OAuthUser,
  action == AgentCore::Action::"kb___Retrieve",
  resource == AgentCore::Gateway::"<GATEWAY_ARN>"
) when {
  principal.hasTag("email") &&
  context has input && context.input has userContext &&
  context.input.userContext has userId &&
  context.input.userContext.userId == principal.getTag("email")
};
```
在此策略中，“principal”代表经过身份验证的用户，“resource”指定网关 ARN。操作“kb___Retrieve”指的是名为“kb”的网关目标上的“Retrieve”工具。 “when”子句需要工具参数“userContext.userId”来匹配 JWT 的“email”声明。该代码片段显示了“kb___Retrieve”的策略。该示例为“kb___AgenticRetrieveStream”创建具有相同条件的第二个策略，因为每个策略都命名一个操作，并且[策略引擎拒绝任何没有许可策略匹配的请求](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/example-policies-action-resource.html)。

下图显示了当拦截器未正确覆盖“userContext”时，AgentCore 中的策略如何拒绝工具调用。

![当注入的 userContext 与令牌的电子邮件声明不匹配时，AgentCore 中的策略拒绝工具调用](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/11/21865-4.png)

图 4：使用 AgentCore 中的策略验证注入的请求

拦截器和策略都使用来自同一令牌的电子邮件，但它们从不同的来源读取它。该策略从签名验证的令牌中获取预期值，并从拦截器构建的请求正文中获取实际值。这可以让它检测到缺少的拦截器或错误的注入。 IdP、预令牌生成触发器和策略配置本身仍然是两者的共享依赖项。仅凭策略，LLM 就会返回到构造“userContext”，因此我们建议您将注入和验证结合起来。

您可以在网关的“policyEngineConfiguration”中附加保存 Cedar 策略的策略引擎。当“mode”设置为“ENFORCE”时，网关根据评估结果拒绝请求。当您将策略添加到已在使用的网关时，您可以从“LOG_ONLY”开始，检查跟踪中的决策，然后切换到“ENFORCE”。
```
const gateway = new agentcore.CfnGateway(this, "Gateway", {
  // Authorizer and interceptor settings are the same as in the earlier example
  policyEngineConfiguration: {
    arn: policyEngine.attrPolicyEngineArn,
    mode: "ENFORCE",
  },
});
```
在创建 Cedar 策略之前创建网关目标。创建目标会向策略引擎注册其工具架构。如果策略引用尚未注册的工具，无论 [validationMode](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-validation-overview.html) 如何，策略创建都会失败。

## 使用基于资源的策略限制对知识库的访问

AgentCore 中的策略仅评估通过附加策略引擎的网关的请求。有两条路径绕过工具层控件。一种是没有拦截器和指向相同知识库的策略的另一个网关。另一种是从开发工具包或 AWS 命令​​行界面 (AWS CLI) 直接调用“检索”API。

![基于资源的策略，拒绝检索来自网关执行角色以外的主体的调用](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/11/21865-5.png)

图 5：使用基于资源的策略限制调用者

托管知识库支持[基于资源的策略](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-management-cross-account.html)。当您将以下策略附加到知识库时，它会显式拒绝网关执行角色以外的主体的“Retrieve”和“GetDocumentContent”。代理检索可以调用“GetDocumentContent”将结果扩展到完整文档。在同一账户中基于身份的策略中，显式拒绝优先于允许，因此拒绝也适用于管理员和知识库的其他使用者，例如控制台上的测试窗口。如果其他角色需要搜索知识库，请将其 Amazon 资源名称 (ARN) 添加到 `ArnNotEquals`。
```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyRetrieveExceptGatewayRole",
      "Effect": "Deny",
      "Principal": "*",
      "Action": ["bedrock:Retrieve", "bedrock:GetDocumentContent"],
      "Resource": "arn:aws:bedrock:<REGION>:<ACCOUNT_ID>:knowledge-base/<KB_ID>",
      "Condition": {
        "ArnNotEquals": {
          "aws:PrincipalArn": "arn:aws:iam::<ACCOUNT_ID>:role/<GATEWAY_EXECUTION_ROLE>"
        }
      }
    }
  ]
}
```
借助 AWS CDK，您可以将此策略文档附加到“CfnKnowledgeBasePolicy”，该策略映射到“AWS::Bedrock::KnowledgeBasePolicy”资源类型。将 `aws:PrincipalArn` 设置为网关执行角色的 ARN，例如 `gwRole.roleArn`。

您不能在策略的“Action”元素中列出“bedrock:AgenticRetrieveStream”。但是，[AgenticRetrieveStream 内的搜索为每个知识库上的调用者授权 bedrock:Retrieve](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html)。因此，此策略中的拒绝也会阻止通过“AgenticRetrieveStream”进行搜索。

基于资源的策略限制哪些 IAM 委托人可以搜索知识库。它不能拒绝另一个重用相同执行角色的网关。不要与其他工作负载共享执行角色。限制哪些用户可以传递角色 (iam:PassRole) 并管理基于资源的策略（bedrock:PutResourcePolicy、bedrock:GetResourcePolicy 和 bedrock:DeleteResourcePolicy），因为任何可以更改或删除策略的人都可以删除此控制。该策略也不涵盖“GetKnowledgeBase”等控制平面操作，因此请使用基于身份的策略保护知识库配置。

## 测试解决方案

存储库中的 [scripts/verify_defenses.py](https://github.com/aws-samples/sample-management-knowledge-base-patterns/blob/main/agentcore-access-control/scripts/verify_defenses.py) 脚本以两个用户身份登录，并确认每种机制阻止其目标路径。每个示例文档都包含一个唯一的代码，因此脚本可以从响应中判断文档是否被无意中泄露。该脚本使用“ADMIN_USER_PASSWORD_AUTH”以演示用户身份登录。有关其所需的 AWS 权限，请参阅 [docs/verification.md](https://github.com/aws-samples/sample-management-knowledge-base-patterns/blob/main/agentcore-access-control/docs/verification.md)。代理场景取决于模型，因此如果代理在三轮内没有发送欺骗性的“userContext”，脚本会将其报告为不确定（“SKIP”）。

要单独检查 AgentCore 中的策略和基于资源的策略，请使用“-c enableBypassSimulation=true”部署堆栈。此标志为同一知识库添加两个测试网关。一个没有拦截器，另一个既没有拦截器也没有策略引擎。两者都作为基于资源的策略不豁免的测试角色运行。测试后重新部署，不带标志以删除它们。下表显示了结果。

| **场景** | **结果** | **被**阻止 |
| --- | --- | --- |
|用户 a 和用户 b 发送相同的查询 |每个用户只能获取其 ACL 中的文档 | ACL 意识 |
|用户 a 使用用户 b 的“userContext”调用“kb___Retrieve”或“kb___AgenticRetrieveStream” |只有user-a的文档可以查看 return |请求拦截器|
| user-a 提示代理设置 user-b 的 `userContext` |代理可能会设置它。如果是，则只有 user-a 的文档可以查看 return |请求拦截器|
|客户端在没有拦截器的情况下将另一个用户的“userContext”发送到网关 |网关拒绝工具调用，并显示“工具执行被拒绝”错误 | AgentCore 中的策略 |
|没有拦截器、没有策略、有自己的执行角色的独立网关搜索知识库 |该工具返回错误，因为知识库拒绝搜索 |基于资源的政策|
|具有管理员权限的用户直接从 SDK 调用“Retrieve” |基于资源的策略中具有显式拒绝的“AccessDeniedException” |基于资源的政策|
|具有管理员权限的用户直接从 SDK 调用 `AgenticRetrieveStream` |流失败并出现“dependencyFailedException”，该异常包装了“bedrock:Retrieve”上的显式拒绝 |基于资源的政策|

当用户a和用户b发送开场问题时，用户a的答案借鉴A部门的业务计划和通知，用户b的答案借鉴B部门的业务计划和通知。

Web 应用程序在返回的文档旁边显示了 LLM 生成的工具参数。当用户 a 要求代理以用户 b 的身份进行搜索时，应用程序会显示欺骗性的“userContext”，但只显示用户 a 的文档。

## 清理

为了避免将来产生费用，请在完成测试后删除堆栈。在模式的“infra”目录中运行“npx cdk destroy”。这将删除知识库、S3 存储桶及其对象、用户池、AWS Secrets Manager 中的演示用户密码以及每个 Lambda 函数和代理运行时的 Amazon CloudWatch Logs 日志组。

＃＃ 结论

在这篇文章中，我们展示了如何在整个公司共享代理和知识库，同时仍将每个用户的搜索限制为他们允许查看的文档。作为主要防御措施，请求拦截器从已验证的令牌中注入“userContext”，并且托管知识库中的 ACL 感知会确定搜索范围。根据您的要求，AgentCore 中的策略会独立验证注入的值，并且基于资源的策略会拒绝绕过网关的搜索。

底层设计原则是不让LLM生成影响授权的值。此原则也适用于多个客户共享知识库的多租户 SaaS 架构。它还适用于除托管知识库之外接受影响访问控制的参数的 MCP 工具。从 [GitHub 存储库](https://github.com/aws-samples/sample-management-knowledge-base-patterns/tree/main/agentcore-access-control) 部署 CDK 堆栈，并使用您自己的数据源和 IdP 进行尝试。要了解何时使用拦截器以及何时使用策略，请参阅[在 Amazon Bedrock AgentCore 网关中使用策略和 Lambda 拦截器保护 AI 代理](https://aws.amazon.com/blogs/machine-learning/secure-ai-agents-with-policy-and-lambda-interceptors-in-amazon-bedrock-agentcore-gateway)。

本文中的架构使用托管知识库的内置 AgentCore Gateway 连接器。如果您正在考虑从[客户管理的知识库](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-build-management.html#kb-management-vs-custom)迁移到托管知识库，[Agent Toolkit for AWS](https://aws.amazon.com/products/developer-tools/agent-toolkit-for-aws/)中的“amazon-bedrock”技能包括[迁移过程](https://github.com/aws/agent-toolkit-for-aws/blob/main/skills/core-skills/amazon-bedrock/references/migrate-knowledge-base-to-driven.md) 可帮助您评估和规划过渡。它适用于您已经使用的编码代理，例如 Kiro、Claude Code 和 Cursor。代理通过只读调用读取您当前的配置并编写迁移计划，还可以选择根据您测量的使用情况进行成本比较。批准计划后，它会在原始知识库旁边创建新的知识库，并且不会更改或删除原始知识库。有关托管知识库的优势和分步迁移演练，请参阅[使用编码代理迁移到 Amazon Bedrock 托管知识库](https://aws.amazon.com/blogs/machine-learning/migrate-to-amazon-bedrock-driven-knowledge-base-with-your-coding-agent/)。
