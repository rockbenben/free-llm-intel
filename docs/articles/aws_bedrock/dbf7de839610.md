# 在 Amazon Bedrock AgentCore Runtime 上安全地启动并扩展你的 agent 与工具

组织对 AI agent 潜力的热情日益高涨，但许多组织发现自己困在我们所称的“概念验证炼狱”之中——前景看好的 agent 原型难以跃升到生产部署。在与客户的交流中，我们反复听到一些阻碍从试验走向企业级部署的挑战：

“我们的开发者希望针对不同用例使用不同的框架和模型——强制统一会拖慢创新。”

“agent 的随机性使安全性比传统应用更为复杂——我们需要用户会话之间更强的隔离。”

“对于需要代表用户行事或访问敏感系统的 agent，我们在身份与访问控制上颇感吃力。”

“我们的 agent 需要处理各种输入类型——文本、图像、文档——而且常常带有超出典型无服务器计算限制的大负载。”

“我们无法预测每个 agent 需要多少计算资源，而为峰值需求过度预置时成本会失控攀升。”

“为可能混合了短时与长时运行的 agent 管理基础设施，需要专业知识，这会分散我们构建真正 agent 功能的精力。”

[Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 通过一个专为 AI agent 和工具设计的安全无服务器托管环境来应对这些挑战。传统应用托管系统并非为 agent 工作负载的独特特性——可变的执行时间、有状态交互和复杂的安全要求——而构建，而 AgentCore Runtime 则是为这些需求量身打造。

该服务缓解了一直阻碍优秀 agent 原型走向生产的基础设施复杂性。它承担容器编排、会话管理、可扩展性和安全隔离这些无差异的重体力活，帮助开发者专注于打造智能体验，而不是管理基础设施。本文讨论如何实现以下目标：

- 使用不同的 agent 框架和不同的模型
- 用四行代码部署、扩展并流式返回 agent 响应
- 通过会话隔离与内嵌身份保障 agent 执行安全
- 结合 [Amazon Bedrock AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-getting-started.html) 为有状态 agent 使用状态持久化
- 处理带有大负载的不同模态
- 运行持续数小时的异步 agent
- 只为使用的资源付费

## 使用不同的 agent 框架和模型

AgentCore Runtime 的一个优势在于其 agent 部署的框架无关、模型无关方式。无论你的团队是为复杂推理工作流投入了 LangGraph、为多 agent 协作采用了 CrewAI，还是用 Strands 构建了自定义 agent，AgentCore Runtime 都可以直接使用你现有的代码库，无需架构变更，也无需任何框架迁移。示例请参阅这些 [GitHub 上的样例](https://github.com/awslabs/amazon-bedrock-agentcore-samples/tree/main/03-integrations/agentic-frameworks)。

## 通过会话隔离与内嵌身份保障 agent 执行安全

AgentCore Runtime 引入的持久执行环境可以在多次调用之间维持 agent 的状态，从根本上改变了我们对 agentic 应用无服务器计算的看法。典型无服务器模型是函数启动、执行、随即终止，而 AgentCore Runtime 则预置专用 microVM，可持续存在最长 8 小时。这使得复杂的多步 agentic 工作流成为可能：在同一会话中，每次后续调用都能在前序交互积累的上下文与状态之上构建。其实际意义在于，你现在可以实现此前需要外部状态管理方案或繁琐变通做法才能在函数执行之间维持上下文的复杂有状态逻辑模式。这并不排除对外部状态管理的需要（参见下一节关于结合 AgentCore Memory 使用 AgentCore Runtime 的内容），但它是在会话上下文内临时维护本地状态与文件的常见需求。

### 理解会话生命周期

会话生命周期通过三个不同状态运作，这些状态决定资源分配与可用性（关于该会话生命周期的高层视图，参见下图）。当你首次以唯一会话标识符调用 runtime 时，AgentCore 会预置一个专用执行环境，并在请求处理期间或后台任务运行时将其转换为 `Active` 状态。

系统会自动跟踪同步调用活动，而后台进程可以通过对服务健康检查 ping 返回 `HealthyBusy` 响应来表明其状态（参见后文关于异步工作负载的章节）。会话在不处理请求时会转入 `Idle` 状态，但仍保持预置并随时可用，从而降低后续调用的冷启动开销。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/12/ML-19422-image-1-kosti.png)

最后，当会话超过 15 分钟的不活动阈值、达到 8 小时的最长持续时间限制或健康检查失败时，就会进入 `Terminated` 状态。理解这些状态转换对于设计能够优雅处理会话边界与资源清理的弹性工作流至关重要。关于会话生命周期相关配额的更多细节，请参阅 [AgentCore Runtime 服务配额](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html#runtime-service-limits)。

AgentCore 会话的短暂性意味着运行时状态仅存在于活动会话生命周期的边界之内。agent 在执行期间积累的数据——例如对话上下文、用户偏好映射、中间计算结果或瞬态工作流状态——只在会话存续期间可访问，并在会话终止时被彻底清除。

对于超出单个会话边界的持久数据需求，AgentCore Memory 提供了持久状态管理的架构方案。这项专为 agent 工作负载打造的服务同时提供短期与长期记忆抽象，可以跨会话边界维持用户对话历史、习得的行为模式和关键洞察。关于 AgentCore Memory 入门，请参阅[文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-getting-started.html)。

### 真正的会话隔离

AI agent 工作负载中的会话隔离，应对的是传统应用架构中并不存在的基础性安全与运营挑战。与独立处理单个请求的无状态函数不同，AI agent 在长时间推理过程中维护复杂的上下文状态，使用敏感凭证和文件执行特权操作，并表现出非确定性的行为模式。这会带来独特的风险：一个用户的 agent 有可能访问另一个用户的数据——会话专属信息可能被跨多个会话使用，凭证可能在会话之间泄露，或者不可预测的 agent 行为可能突破系统边界。传统的容器化或进程隔离并不充分，因为 agent 既需要持久的状态管理，又需要在用户之间保持绝对隔离。

让我们看一个案例：2025 年 5 月，Asana 部署了一个新的 MCP 服务器，为其企业软件即服务（SaaS）产品线中的 agentic AI 功能（与 ChatGPT、Anthropic 的 Claude、Microsoft Copilot 的集成）提供支持。由于 MCP 租户隔离中的一处逻辑缺陷，以及只依赖用户身份而未依赖 agent 身份，来自某一家组织用户的请求可能意外检索到包含另一家组织数据的缓存结果。这次跨租户污染并非由针对性的利用触发，而是跨 agentic AI 驱动会话处理上下文与缓存隔离时的一处内在安全缺陷。

该暴露悄无声息地持续了 34 天，影响约 1,000 家组织，其中包括大型企业。被发现后，Asana 停止了该服务、修复了缺陷、通知了受影响的客户，并发布了补丁。

AgentCore Runtime 通过超越简单资源隔离的完整 microVM 隔离来解决这些挑战。每个会话都获得自己的专用虚拟机，具备隔离的计算、内存和文件系统资源，确保 agent 状态、工具操作和凭证访问保持完全分隔。会话结束时，整个 microVM 被终止、内存被清理，将数据残留或交叉污染的风险降到最低。这种架构提供了企业部署所需的确定性安全边界——即便面对 AI agent 固有的概率性与非确定性本质也是如此——同时仍能实现让 agent 具有价值的有状态、个性化体验。尽管其他方案可能提供沙箱化内核，并允许你自己管理会话状态、持久化和隔离，但这不应被视为严格的安全边界。无论 agent 的执行模式如何，AgentCore Runtime 都提供一致、确定性的隔离边界，交付企业部署所需可预期的安全属性。下图展示了两个独立会话如何在隔离的 microVM 内核中运行。

### AgentCore Runtime 的内嵌身份

传统的 agent 部署常常在身份与访问管理上捉襟见肘，尤其是当 agent 需要代表用户行事或安全地访问外部服务时。在多租户环境中，这一挑战更为复杂——例如，你需要确保代表用户 1 访问 Google Drive 的 agent A 绝不会意外检索到属于用户 2 的数据。

AgentCore Runtime 通过其内嵌身份系统来应对这些挑战，该系统把身份验证与授权无缝集成到 agent 执行环境中。首先，每个 runtime 都关联一个唯一的工作负载身份（你可以将其视为唯一的 agent 身份）。对于使用这一唯一 agent 身份的 agent，该服务支持两种主要身份验证机制：适用于在 AWS 安全边界内运行的 agent 的 IAM SigV4 身份验证，以及基于 OAuth（JWT Bearer Token 身份验证）与现有企业身份提供商（如 [Amazon Cognito](https://aws.amazon.com/cognito/)、Okta 或 Microsoft Entra ID）的集成。

以 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）身份验证部署 agent 时，用户无需加入其他 [Amazon Bedrock AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-overview.html) 的特定设置或配置——只需以 IAM 授权进行配置、启动，并使用正确的用户凭证调用。

使用 JWT 身份验证时，你在 `CreateAgentRuntime` 操作期间配置授权器，指定身份提供商（IdP）专属的发现 URL 和允许的客户端。现有 agent 代码无需修改——只需在 runtime 部署中加入授权器配置。当调用实体或用户调用你的 agent 时，他们在 `Authorization` 请求头中以 bearer token 的形式传入其 IdP 专属访问 token。AgentCore Runtime 使用 AgentCore Identity 自动依据你配置的授权器验证该 token，并拒绝未授权的请求。下图展示了 AgentCore runtime、你的 IdP、AgentCore Identity、其他 AgentCore 服务、其他 AWS 服务（橙色）以及其他外部 API 或资源（紫色）之间的信息流。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/12/ML-19422-image-3.jpg)

在幕后，AgentCore Runtime 会自动将已验证的用户 token 换为工作负载访问 token（通过 `bedrock-agentcore:GetWorkloadAccessTokenForJWT` API）。这通过 AgentCore 凭证提供商系统为外部服务提供安全的出站访问，其中 token 以 agent 工作负载身份与用户 ID 的组合作为绑定键进行缓存。这种密码学绑定确保——例如——在处理用户 2 的请求时，绝不可能访问到用户 1 的 Google token，无论应用逻辑是否存在错误。请注意，在上图中，连接到 AWS 资源只需编辑 AgentCore Runtime 执行角色即可实现，但连接到 [Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 或另一个 runtime 则需要用新的访问 token 重新授权。

## 结合 AgentCore Memory 使用 AgentCore Runtime 状态持久化

AgentCore Runtime 提供短暂的、会话专属的状态管理，在活跃对话期间维持上下文，但不会超出会话生命周期而持久存在。每个用户会话都在隔离的执行环境中保留对话状态、内存中的对象和本地临时文件。对于短时运行的 agent，你可以使用 AgentCore Runtime 提供的状态持久化，而无需在外部保存这些信息。然而，在会话生命周期结束时，这些短暂状态会被永久销毁，因此这种方式只适用于不需要跨独立对话保留知识的交互。

AgentCore Memory 通过提供可存活于单个会话之外的持久存储来应对这一挑战。短期记忆使用 `create_event` 把原始交互捕获为事件，保存完整的对话历史；即使 runtime 会话重启，也能通过 `get_last_k_turns` 检索回来。长期记忆使用可配置的策略从这些原始交互中提取并整合关键洞察，例如用户偏好、重要事实或对话摘要。通过 `retrieve_memories`，agent 可以跨完全不同的会话访问这些持久知识，从而实现个性化体验。下图展示了 AgentCore Runtime 如何调用特定 API 与 AgentCore Memory 中的短期记忆和长期记忆交互。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/12/ML-19422-image-6.jpg)

这种基础架构——用一个 runtime 托管 agent，并配合短期与长期记忆的组合——在如今大多数 agentic AI 应用中已颇为常见。以相同会话 ID 调用 AgentCore Runtime，让你可以像本地运行一样访问 agent 状态（例如在对话流中），而无需承担外部存储操作的开销；同时 AgentCore Memory 会选择性地捕获并结构化那些值得在会话生命周期之后保留的有价值信息。这种混合方式意味着 agent 可以在活跃会话期间保持快速、贴合上下文的响应，同时随时间积累智能。AgentCore Memory 按各策略对长期记忆进行的自动异步处理，确保洞察的提取与整合不影响实时性能，营造出一种无缝体验：agent 在保持交互响应性的同时变得越来越有用。这种架构避免了对话速度与长期学习之间的传统权衡，让 agent 既能即时可用，又能持续改进。

## 处理带有大负载的不同模态

大多数 AI agent 系统因严格的负载大小限制而在大文件处理上吃力，通常把请求上限压在几 MB。这迫使开发者实现复杂的文件分块、多次 API 调用或外部存储方案，从而增加延迟与复杂度。AgentCore Runtime 通过支持最大 100 MB 的负载消除了这些限制，使 agent 能在单次调用中处理大规模数据集、高分辨率图像、音频和完整的文档集合。

设想一个财务审计场景：你需要通过把详细的交易数据与来自分析系统的仪表板截图进行比对，来核对季度销售表现。传统做法需要使用 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）或 Google Drive 等外部存储，把 Excel 文件和图像下载到运行 agent 逻辑的容器中。而使用 AgentCore Runtime，你可以从客户端以单一负载同时发送完整的销售数据和仪表板图像：

```
large_payload = {
"prompt": "Compare the Q4 sales data with the dashboard metrics and identify any discrepancies",
"sales_data": base64.b64encode(excel_sales_data).decode('utf-8'),
"dashboard_image": base64.b64encode(dashboard_screenshot).decode('utf-8')
}
```

可以对 agent 的 entrypoint 函数进行修改，以同时处理两个数据源，从而实现这种交叉验证分析：

```
@app.entrypoint
def audit_analyzer(payload, context):
    inputs = [
        {"text": payload.get("prompt", "Analyze the sales data and dashboard")},
        {"document": {"format": "xlsx", "name": "sales_data", 
                     "source": {"bytes": base64.b64decode(payload["sales_data"])}}},
        {"image": {"format": "png", 
                  "source": {"bytes": base64.b64decode(payload["dashboard_image"])}}}
    ]
    
    response = agent(inputs)
    return response.message['content'][0]['text']
```

如需测试使用大负载的示例，请参阅以下 [GitHub 仓库](https://github.com/awslabs/amazon-bedrock-agentcore-samples/blob/main/01-tutorials/01-AgentCore-runtime/03-advanced-concepts/03-handling-large-payloads/handling_large_payloads.ipynb)。

## 运行持续数小时的异步 agent

随着 AI agent 演进以处理日益复杂的任务——从处理大规模数据集到生成全面报告——它们往往需要耗时可观的多步处理。然而，大多数 agent 实现是同步的（配合响应流式输出），会一直阻塞到完成为止。虽然同步的流式 agent 是向用户暴露 agentic 聊天应用的常见方式，但当某个任务或工具仍在运行时，用户无法与 agent 交互、无法查看状态、无法取消后台操作，也无法在其他任务尚未完成时启动更多并发任务。

构建异步 agent 迫使开发者实现复杂的分布式任务管理系统，其中包含状态持久化、作业队列、worker 协调、故障恢复和跨调用状态管理，同时还要应对无服务器系统的限制，例如执行超时（数十分钟）、负载大小限制，以及长时间运行计算操作的冷启动开销——这是一项相当繁重的工程，会分散对核心功能的关注。

AgentCore Runtime 通过跨调用维持上下文的有状态执行会话缓解了这种复杂性，使开发者可以增量地在前序工作之上构建，而无需实现复杂的任务管理逻辑。AgentCore SDK 提供开箱即用的构造来跟踪异步任务并无缝管理计算生命周期，AgentCore Runtime 支持最长 8 小时的执行时间以及 100 MB 的请求/响应负载大小，适用于大多数异步 agent 任务。

### 异步 agent 入门

只需进行少量代码改动即可开始：

```
pip install bedrock-agentcore
```

要构建执行异步任务的交互式 agent，只需在任务开始时调用 `add_async_task`、在完成时调用 `complete_async_task`。SDK 会自动为你处理任务跟踪并管理计算生命周期。

```
# Start tracking a task
task_id = app.add_async_task("data_processing")

# Do your work...
# (your business logic here)

# Mark task as complete
app.complete_async_task(task_id)
```

这两次方法调用即可把你的同步 agent 转变为完全异步的交互式系统。更多细节请参阅这个[样例](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-long-run.html#runtime-long-run-complete-example)。

以下示例展示了两者的区别：一个是立即向用户流式返回响应的同步 agent，另一个是更复杂的多 agent 场景——在其中，运行时间更长的异步后台购物 agent 使用 [Amazon Bedrock AgentCore Browser](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html) 代表用户在 [amazon.com](http://amazon.com) 上自动化购物体验。

## 只为使用的资源付费

Amazon Bedrock AgentCore Runtime 引入了基于用量的定价模型，从根本上改变了你为 AI agent 基础设施付费的方式。传统的计算模型无论利用率如何都会对已分配资源计费，而 AgentCore Runtime 只对你实际使用的内容计费，无论你使用多久；换个说法，你无需预先分配 CPU 或 GB 内存等资源，也不会在 I/O 等待期间为 CPU 资源付费。这一区别对 AI agent 尤其有价值，因为它们通常要花大量时间等待 LLM 响应或外部 API 调用完成。下面是一个典型的 Agent 事件循环，其中我们预期只有紫色方框会在 Runtime 内处理：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/08/12/ML-19422-image-7.png)

LLM 调用（浅蓝色）和工具调用（绿色）方框需要时间，但运行在 AgentCore Runtime 的上下文之外；用户只需为 Runtime 内部发生的处理（紫色方框）付费。让我们通过一些真实示例来理解其影响：

### 客户支持 agent 示例

设想一个每天处理 10,000 次用户咨询的客户支持 agent。每次交互都包括初始查询处理、从检索增强生成（RAG）系统中检索知识、为组织回复而进行的 LLM 推理、调用订单系统的 API，以及最终生成回复。在一个持续 60 秒的典型会话中，agent 可能只有 18 秒在主动使用 CPU（30%），其余 42 秒（70%）则在等待 LLM 响应或 API 调用完成。内存使用量可能在 1.5 GB 到 2.5 GB 之间波动，取决于客户查询的复杂度和所需上下文的数量。使用传统计算模型，你需要为完整的 60 秒 CPU 时间和峰值内存分配付费。而使用 AgentCore Runtime，你只需为 18 秒的活跃 CPU 处理以及逐刻实际消耗的内存付费：

```
CPU cost: 18 seconds × 1 vCPU × ($0.0895/3600) = $0.0004475
 Memory cost: 60 seconds × 2GB average × ($0.00945/3600) = $0.000315
 Total per session: $0.0007625
```

对于每天 10,000 次会话，相比按完整 60 秒计费的传统模型，这意味着 CPU 成本降低 70%。

### 数据分析 agent 示例

对于处理复杂工作流的数据处理 agent，节省更为显著。一个处理季度报告的财务分析 agent 可能运行三个小时，但资源需求高度波动。在数据加载和初始解析阶段，它可能只使用极少的资源（0.5 vCPU、2 GB 内存）。在执行复杂计算或运行统计模型时，它可能在整个运行时中仅有 15 分钟飙升至 2 vCPU 和 8 GB 内存，其余时间则以低得多的资源利用率等待批处理操作或模型推理。由于只对实际资源消耗计费，同时在 I/O 等待期间维持你的会话状态，AgentCore Runtime 让成本与价值创造直接对齐，使复杂的 agent 部署在规模化时具备经济可行性。
