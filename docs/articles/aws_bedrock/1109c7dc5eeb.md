# 无服务器 MCP 服务器，用于 Amazon ECS Fargate 上的 AI 代理数据湖访问

构建由人工智能 (AI) 驱动的应用程序的组织面临着一个反复出现的挑战：让大型语言模型 (LLM) 代理能够访问企业数据湖，而无需在每个代理和应用程序之间重复集成逻辑。大多数团队首先将代理直接连接到数据库和 API，中间没有共享网关，例如模型上下文协议 (MCP) 服务器。每个新数据集都需要自定义代码，每个代理都重新实现自己的访问控制。随着数据集或代理数量的增长，权限执行会发生变化，并且加入新的数据源成为一项需要数天的工程工作。

我们的团队支持亚马逊的北美分拣中心 (NASC) 网络，其中规划团队依靠运营数据来管理产能、劳动力和包裹流。为了让这些团队能够以对话方式访问这些数据，我们使用 AWS Fargate 在 [Amazon Elastic Container Service (Amazon ECS)](https://aws.amazon.com/fargate/) 上构建了一个无服务器 [Model Context Protocol (MCP)](https://modelcontextprotocol.io/) 服务器，以解决 NASC 规划团队的此问题。该服务器充当人工智能代理和我们的企业数据湖之间的集中式、与代理无关的网关。公开新数据集仅需要服务器在下一次管道同步时自动发现的 JSON 元数据文件。

在这篇文章中，我们描述了该架构，展示了元数据驱动的方法如何消除对每个数据集集成代码的需求，并解释无服务器基础设施如何支持多租户环境中的多个代理和应用程序。

## 问题陈述和设计目标

两个相互关联的挑战决定了我们如何设计这个系统：碎片化的数据访问模式和不可持续的入职模型。

### 大规模集成挑战

我们的数据湖包含数千个数据集，涵盖运营指标、业务分析和特定领域的数据。多个团队希望人工智能助手能够以对话方式查询这些数据，但每个团队都从头开始构建自己的集成。每个代理都嵌入了自己的 SQL 生成逻辑、模式知识和连接处理，因此模式更改意味着单独修补每个代理。访问控制是分散的，没有针对数据访问决策的单一审核点。加入新的数据集需要自定义工具代码、查询验证和重新部署，通常每个表需要花费数天的时间。

### 设计目标

我们制定了四项要求：

- 配置驱动的数据湖访问。添加数据集仅需要元数据文件，而不需要代码。
- 与代理无关的工具界面。任何与 MCP 兼容的客户端都可以调用相同的工具。
- 集中执行许可。访问控制在 MCP 服务器层实施。
- 弹性基础设施。该系统可根据突发的人工智能工作负载模式进行扩展。

## 解决方案概述

该架构将关注点分为四层（客户端、MCP 服务器、工具和知识库刷新），每层都独立可扩展和可部署。元数据目录支撑着工具层，存储 AI 代理在生成 SQL 时引用的架构描述、列级语义和表关系。由于代理在查询时从目录中获取模式知识，因此无需在模式更改时对表结构进行硬编码或重新部署。知识库刷新层使该目录保持最新状态，并在新数据集元数据到达时对其进行索引。以下部分详细描述了每一层。

## 架构演练

下图显示了从用户查询到跨所有四个层的数据层的请求流程。用户从客户端应用程序（网络聊天、Slack、IDE 插件或外部代理）提交查询。该请求通过 Amazon Route 53 for DNS 进行解析，并到达公有子网中配置了 HTTPS 和 AWS WAF 的 Application Load Balancer。负载均衡器路由到 Amazon Cognito，后者对用户进行身份验证并丰富请求。然后，经过身份验证的流量进入私有子网，其中客户端层在 Amazon ECS Fargate 上运行。该层处理 Amazon DynamoDB 中的会话状态，并通过内部应用程序负载均衡器将请求转发到同样位于 Amazon ECS Fargate 上的 MCP 服务器层。在 MCP 服务器层，由 Amazon Bedrock 提供支持的 AI 代理协调使用 FastMCP（用于构建 MCP 服务器的 Python 框架）构建的工具。 Amazon Bedrock Guardrails 应用于每个模型交互。右侧，数据层包含工具后端。 Amazon Athena 和 Amazon Redshift 针对数据湖运行 SQL 查询，而 Amazon Bedrock 知识库（完全托管的检索增强生成 (RAG) 功能）则处理语义搜索。将数据引入 Amazon Simple Storage Service (Amazon S3) 和知识库由 AWS Lambda 处理。下面的部分详细描述了每一层。

### MCP 客户端层：身份验证和会话管理

请求从客户端应用程序流经 Amazon Route 53 以进行 DNS 解析，到达配置了 HTTPS 和 [AWS WAF](https://aws.amazon.com/waf/) 的 Application Load Balancer。负载均衡器将流量转发到 Amazon ECS Fargate 客户端服务，该服务与 Amazon Cognito 集成以进行 JSON Web 令牌 (JWT) 身份验证，并与 Amazon DynamoDB 集成以进行会话存储。

上下文映射配置驱动了这种丰富，将每个查询的范围仅限于相关表。在我们的测试中，此范围将端到端交互延迟保持在 15-20 秒范围内。以下示例显示了上下文映射配置：
```
{
  "package_data": {
    "description": "Package tracking and delivery information",
    "tables": ["analytics_db.regional_order_summary", "operations_gold.load_summary"],
    "sources": {"wiki": [], "quip": []}
  },
  "labor_planning": {
    "description": "Workforce management and capacity planning",
    "tables": ["workforce.capacity_details"],
    "sources": {"wiki": [], "quip": []}
  }
}
```
当上下文指定表时，MCP 服务器会将元数据目录的搜索范围缩小到这些表，从而减少噪音并提高 SQL 生成的准确性。添加新的业务域只需要向该映射添加一个条目。

### MCP 服务器层：具有会话状态的无状态执行

MCP 服务器在其自己的 ECS Fargate 集群上运行，与客户端层隔离。请求通过 Amazon Route 53 和私有子网中的内部应用程序负载均衡器到达它。服务器处理完整的编排，包括查询分析、工具选择、执行和响应生成。通过 MCP 协议终端节点 (`/mcp`)（FastMCP 支持的 JSON-RPC 接口），外部 MCP 兼容客户端（例如 Amazon Q Developer 或 IDE 扩展）可以直接发现和调用工具。

Fargate 任务是无状态的，会话状态保留在 DynamoDB 中，因此可以替换或扩展任务而不会丢失数据。当请求到达时，代理会检索会话历史记录，使用 Amazon Bedrock 分析用户意图，发现并调用适当的工具，并将结果流式传输回用户。

### 工具层和元数据驱动的数据湖访问

每个工具都在 FastMCP 中注册并在运行时可发现：

| **老先生** | **工具** | **后端** | **目的** |
| --- | --- | --- | --- |
| 1 | SQL查询工具|亚马逊 Athena 亚马逊 Redshift |针对数据湖和 Redshift 中任何已配置数据集的 SQL 查询 |
| 2 |文档和元数据搜索 |Amazon Bedrock知识库 |对内部文档、表格元数据和团队 wiki 进行语义搜索 |
| 3 |政策搜索|Amazon Bedrock知识库 |搜索运营政策和标准程序 |

Athena 查询工具是数据湖的主要接口。该代理首先查询元数据目录以了解可用架构，通过 Amazon Bedrock 生成优化的 SQL 查询，验证并自动更正 SQL 以实现 Athena 兼容性，然后执行它。结果流回编排代理进行自然语言合成。

### 负责任的人工智能控制

Amazon Bedrock Guardrails 适用于所有 LLM 交互，旨在过滤有害内容、执行接地检查并帮助阻止提示注入尝试。这些护栏在 MCP 服务器层充当生产控制，因此每个连接的代理都受益于相同的内容安全策略，无论其如何连接。 Athena 查询工具强制执行仅“SELECT”查询，在工具级别拒绝写入操作到达数据湖。

### 知识库刷新层：使用单个 JSON 文件加载数据集

整个系统是围绕配置驱动的可扩展性构建的。添加新数据集需要一个描述表的元数据 JSON 文件和一个可选的上下文映射条目。该文件捕获表的架构、业务上下文和列级语义。它是人工智能代理用来理解和查询数据集的单一事实来源：
```
{
  "database_service_name": "athena",
  "database_name": "analytics_db",
  "table_name": "regional_order_summary",
  "business_description_for_the_table": "Regional order history with shipping status and delivery performance. Contains completed orders with delivery data. Refreshes daily. In Athena SQL, always use date() to wrap string literals when comparing against timestamp columns.",
  "column_details": {
    "order_id [varchar]": {
      "description": "Unique order identifier assigned at checkout.",
      "sample_values": ["ORD-20250115-001234", "ORD-20250116-005678"]
    },
    "order_date [timestamp(3)]": {
      "description": "Date and time the order was placed. Use this column for time-range filtering.",
      "sample_values": ["2025-01-15 08:00:00.000", "2025-01-16 12:30:00.000"]
    },
    "warehouse_id [varchar]": {
      "description": "Fulfillment center that processed the order.",
      "sample_values": ["FC-EAST-07", "FC-WEST-03", "FC-SOUTH-12"]
    }
  },
  "load_type": "Incremental (refreshes last 7 days)",
  "refresh_frequency": "Daily at 6:00 AM UTC",
  "table_size": "~2.1B rows",
  "creation_time": "2024-03-15",
  "last_refresh_time": "2025-05-20T06:00:00Z"
}
```
“business_description_for_the_table”字段携带特定于引擎的查询提示，例如“始终使用“date()”来包装字符串文字”，以减少 SQL 验证失败。 “column_details”字段将每个“column_name [type]”与自然语言描述和示例值配对，为代理提供模式感知和业务语义。 “sample_values”字段对于准确生成“WHERE”子句很重要，因为代理会学习真实的数据模式，例如“warehouse_id”保存“FC-EAST-07”等代码，而不是“East Region Facilities”等拼写出来的名称。

该管道拾取元数据文件，使用 Amazon Titan Text Embeddings 生成矢量嵌入，并将其索引到 Amazon Bedrock 知识库中。一旦建立索引，所有连接的代理都可以发现该表，而无需手动重新索引或服务器重新启动。

为了提高特定应用程序的准确性，工程师可以选择将数据集与业务上下文相关联。这缩小了搜索范围，因此代理会优先考虑正确的表。以下示例显示了上下文映射条目：
```
{
  "delivery_metrics": {
    "description": "Delivery accuracy and defect attribution data",
    "tables": ["analytics_db.customer_orders_summary"],
    "sources": {"wiki": [], "quip": []}
  }
}
```
如果未指定上下文，代理将搜索所有索引表。上下文映射通过限制搜索空间来减少延迟并提高 SQL 准确性。此范围是可选的，可以随时添加，而无需修改元数据文件本身。

### 将其放在一起：正在执行的查询

当用户询问“上个月价值最高的 10 个订单是什么？”时，客户会根据业务背景丰富请求以缩小范围。代理将问题转换为向量嵌入，搜索元数据目录以查找匹配模式，并通过轻量级 LLM 调用选择最相关的表。

使用选定的架构、列描述和特定于引擎的查询提示，代理生成 SQL 语句，例如：
```
SELECT order_id, customer_id, total_amount, order_date
FROM analytics_db.regional_order_summary
WHERE order_date >= date_add('month', -1, current_date)
ORDER BY total_amount DESC
LIMIT 10
```
SQL 经过验证并自动更正引擎兼容性，然后针对 Amazon Athena 执行。代理将结果格式化为自然语言响应并将其流式传输回用户。在我们的测试中，此端到端流程在 15-20 秒内完成。

相同的编排超出了纯 SQL 的范围。由于文档搜索被注册为同一服务器上的另一个工具，因此代理可以一次性回答跨越结构化和非结构化来源的问题，例如“我们第四季度的退货率是多少，产品团队的分析对根本原因有何看法？”对于该请求，代理运行 Athena 查询以获取回报率数据，并运行知识库文档搜索以进行分析，然后将两者合并为一个响应。

## 安全性和多租户访问

这种单轮编排之所以有效，只是因为每个工具调用都经过相同的受控网关。该架构使用分层安全性而不是单个执行点。 MCP 服务器在内部应用程序负载均衡器后面的私有子网中运行，无法从 Internet 访问。只有位于具有 AWS WAF 的面向公众的应用程序负载均衡器后面的客户端层可以将请求路由到它。 Amazon Cognito 在客户端层验证用户身份，并且仅将经过身份验证的带有令牌的请求转发到下游。在工具级别，Athena 查询工具强制执行仅“SELECT”查询，在写入操作到达数据湖之前拒绝写入操作。所有工具调用都使用结构化 JSON 记录到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)，这为安全团队提供了跨每个代理和应用程序的数据访问的单一审核点。此架构在提供 Amazon Bedrock 和 Amazon Bedrock 知识库的 AWS 区域中可用。

这种集中式设计也是服务器多租户的原因。由于标准化的“/mcp”端点接受任何与 MCP 兼容的客户端，无论其使用哪种 LLM 或编排框架，因此多个代理共享相同的工具和相同的访问控制。添加新代理只需将其指向服务器端点，因此加入另一个团队可以扩展系统，而不会削弱或重复安全模型。

## 无服务器基础设施和扩展

每层通过适合其工作负载模式的机制进行扩展：

| **层** | **缩放机制** | **触发** |
| --- | --- | --- |
|客户端（ECS Fargate）| ECS服务弹性伸缩 | CPU 利用率（50% 阈值）|
| MCP 服务器（ECS Fargate）| ECS服务弹性伸缩 | CPU/内存利用率 |
|雅典娜 |无服务器（自动）|查询并发 |
|Amazon Bedrock |托管服务扩展|推理请求 |

Amazon ECS Fargate 提供无服务器计算，无需管理 EC2 实例。下游服务（Athena、Bedrock）会自动扩展，因此系统无需更改配置即可处理单个查询或数百个并发查询。

## 用例和扩展

该架构支持除基本问答之外的多种模式。企业知识助手可以将数据湖查询与文档搜索结合起来，回答涵盖结构化数据和非结构化知识的复杂问题，例如“我们第四季度的回报率是多少，产品团队的分析对根本原因有何看法？”内部分析副驾驶让业务用户能够以对话方式查询数据湖，而无需编写 SQL，依靠元数据描述和查询提示来引导代理实现准确、高性能的查询模式。

标准化的“/mcp”端点还支持多代理工作流程。用于数据分析、文档检索和操作警报的多个专用代理可以共享同一个 MCP 服务器，每个代理都通过通用协议访问完整的工具套件。新团队的数据加入遵循相同的配置驱动模式。他们添加一个元数据 JSON 文件，并且在一个管道同步周期内，每个连接的代理和应用程序都可以发现其数据集。

## 结论

Amazon ECS Fargate 上的集中式 MCP 服务器在 AI 代理和企业数据湖之间提供可扩展的安全网关。元数据驱动的方法消除了对每个数据集集成代码的需要，并且模型上下文协议标准意味着任何 MCP 兼容的客户端都可以在没有自定义适配器的情况下进行连接。

关键的架构决策是将工具层与代理层分开。代理发展迅速，但数据访问模式应该比任何单一代理实现更长久。将可扩展性视为配置问题而不是代码问题可以加快入门速度。

要了解更多信息，请参阅 [AWS Fargate 上的 Amazon ECS](https://aws.amazon.com/fargate/)、[Amazon Bedrock](https://aws.amazon.com/bedrock/)、[Amazon Bedrock 知识库](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html) 用户指南、[Amazon Athena](https://aws.amazon.com/athena/) 和[模型上下文协议规范](https://modelcontextprotocol.io/docs/2026-07-28/getting-started/intro)。

## 后续步骤

我们正在两个方向扩展这个架构。首先，更细粒度的访问控制，其中表所有者可以将敏感列标记为每个权限组的限制，并且代理会自动从生成的 SQL 中排除这些列，而无需进行提示级更改。

其次，关闭反馈循环，以便当查询失败或产生低置信度结果时，系统捕获失败模式并提出有针对性的建议，以改进列描述、添加查询提示。
