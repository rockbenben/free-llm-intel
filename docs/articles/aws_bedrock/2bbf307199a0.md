# Amazon Bedrock Guardrails 宣布基于 IAM 策略的强制实施，以交付安全的 AI 交互

随着[生成式 AI](https://aws.amazon.com/ai/generative-ai/)在企业中的采用不断加速，保持安全、负责任且合规的 AI 交互变得前所未有的关键。[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 提供可配置的防护措施，帮助组织构建具备行业领先安全保护的生成式 AI 应用。借助 Amazon Bedrock Guardrails，您可以在生成式 AI 应用中实施针对自身用例和负责任 AI 政策定制的防护措施。您可以创建多套针对不同用例量身定制的 guardrail，并将它们应用到多个基础模型（FM），从而改善用户体验并统一生成式 AI 应用的安全控制。除 Amazon Bedrock 模型之外，该服务还提供灵活的 [ApplyGuardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-use-independent-api.html) API，让您无需调用 FM 即可使用预配置的 guardrail 评估文本，从而在由 Amazon Bedrock 或其他系统承载的生成式 AI 应用中，于输入和输出两个层面实施安全控制。

今天，我们宣布 Amazon Bedrock Guardrails 的一项重要增强：[AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）基于策略的强制实施。这项强大的能力让安全与合规团队可以为每一次模型推理调用设定强制的 guardrail，确保组织安全政策在 AI 交互中被一致地执行。该功能通过实现对 guardrail 实施的集中控制，增强了 AI 治理。

## 构建生成式 AI 应用面临的挑战

部署生成式 AI 的组织面临关键的治理挑战：内容适当性——模型可能对问题 prompt 产生不良回答；安全顾虑——即使是无害 prompt 也可能生成有害内容；处理敏感信息时的隐私保护要求；以及跨 AI 部署的一致政策执行。

或许最具挑战性的是，确保在组织内的 AI 交互中一致地应用恰当的防护措施，无论应用由哪个团队或个人开发或部署。

## Amazon Bedrock Guardrails 的能力

Amazon Bedrock Guardrails 让您可以在按具体用例和负责任 AI 政策定制的生成式 AI 应用中实施防护措施。Guardrails 目前支持六类策略：

- **内容过滤器** – 跨六类有害内容的可配置阈值：仇恨、侮辱、色情、暴力、不当行为和 prompt 注入
- **被拒主题** – 定义在应用语境中应避免的特定主题
- **敏感信息过滤器** – 检测并移除个人可识别信息（PII）和自定义 regex 实体，以保护用户隐私
- **词语过滤器** – 在生成式 AI 应用中屏蔽特定词语，例如有害词、脏话，或竞争对手的名称与产品
- **上下文 grounding 检查** – 通过验证回答是否恰当基于所提供的参考来源且与用户查询相关，检测并过滤模型回答中的幻觉
- **自动推理** – 使用严谨的数学、基于逻辑的算法验证与推理过程来核验模型生成的信息，防止幻觉导致的事实错误，使输出符合已知事实，而不是基于编造或不一致的数据

## guardrails 的基于策略的强制实施

安全团队常有组织要求：对 Amazon Bedrock 的每一次推理调用都必须使用 Amazon Bedrock Guardrails。为支持这一要求，Amazon Bedrock Guardrails 提供了新的 IAM 条件键 `bedrock:GuardrailIdentifier`，可在 IAM 策略中用于强制模型推理使用某个特定 guardrail。IAM 策略中的该条件键可应用于以下 API：

- [InvokeModel](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_InvokeModel.html)
- [InvokeModelWithResponseStream](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_InvokeModelWithResponseStream.html)
- [Converse](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html)
- [ConverseStream](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ConverseStream.html)

如果 IAM 策略中配置的 guardrail 与请求中指定的 guardrail 不匹配，请求将被拒绝并抛出 access denied 异常，从而强制遵循组织政策。

## 策略示例

本节给出若干策略示例，演示如何为模型推理强制实施 guardrails。

### 示例 1：强制使用特定 guardrail 及其数字版本

以下示例说明在模型推理期间强制使用 `exampleguardrail` 及其数字版本 1：

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "InvokeFoundationModelStatement1",
            "Effect": "Allow",
            "Action": [
                "bedrock:InvokeModel",
                "bedrock:InvokeModelWithResponseStream"
            ],
            "Resource": [
                "arn:aws:bedrock:region::foundation-model/*"
            ],
            "Condition": {
                "StringEquals": {
                    "bedrock:GuardrailIdentifier": "arn:aws:bedrock:<region>:<account-id>:guardrail/exampleguardrail:1"
                }
            }
        },
        {
            "Sid": "InvokeFoundationModelStatement2",
            "Effect": "Deny",
            "Action": [
                "bedrock:InvokeModel",
                "bedrock:InvokeModelWithResponseStream"
            ],
            "Resource": [
                "arn:aws:bedrock:region::foundation-model/*"
            ],
            "Condition": {
                "StringNotEquals": {
                    "bedrock:GuardrailIdentifier": "arn:aws:bedrock:<region>:<account-id>:guardrail/exampleguardrail:1"
                }
            }
        },
        {
            "Sid": "ApplyGuardrail",
            "Effect": "Allow",
            "Action": [
                "bedrock:ApplyGuardrail"
            ],
            "Resource": [
                "arn:aws:bedrock:<region>:<account-id>:guardrail/exampleguardrail"
            ]
        }
    ]
}
```

新增的显式 deny 会拒绝用户使用其他 `GuardrailIdentifier` 和 `GuardrailVersion` 值调用所列操作的请求，即使用户还拥有其他权限。

## 已知限制

实施基于策略的 guardrail 强制时，请注意以下限制：

- 截至本文撰写时，Amazon Bedrock Guardrails 不支持用于跨账户访问的基于资源的策略。
- 如果用户代入的角色使用 `bedrock:GuardrailIdentifier` 条件键配置了特定 guardrail，该用户就可以策略性地使用[输入标签](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-tagging.html)来帮助规避 guardrail 检查作用于其 prompt 的某些部分。输入标签允许用户标记应由 guardrails 处理的特定文本区段，而其他区段不被处理。例如，用户可以故意把敏感或可能有害的内容留在被标记区段之外，使这些部分不被按 guardrail 策略评估。然而，无论 prompt 如何组织或标记，guardrail 仍会完整作用于模型的回答。
- 如果用户的角色配置了特定 guardrail 要求（使用 `bedrock:GuardrailIdentifier` 条件），该用户就不应使用同一角色访问 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) `RetrieveAndGenerate` 或 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) `InvokeAgent` 等服务。这些更高层级的服务会在幕后代表用户发起多次 `InvokeModel` 调用。尽管其中一些调用可能包含所需的 guardrail，另一些则不含。当系统尝试使用要求 guardrails 的角色发起这些不带 guardrail 的调用时，就会产生 `AccessDenied` 错误，破坏这些服务的功能。为帮助避免此问题，组织应分离权限——对带 guardrails 的直接模型访问与对这些复合型 Amazon Bedrock 服务的访问使用不同角色。

## 结论

随着生成式 AI 融入业务运营，Amazon Bedrock 新增的基于 IAM 策略的 guardrail 强制实施代表了 AI 治理方面的一项重要进展。通过实现集中式策略执行，安全团队可以跨 AI 应用维持一致的安全控制，无论由谁开发或部署，从而有效降低与有害内容、隐私侵犯和偏见相关的风险。这种方法带来显著优势：它能随组织 AI 举措的扩展而高效扩展，不产生管理瓶颈；通过标准化安全实现帮助避免技术债；并让团队专注于创新而非合规机制，从而提升开发者体验。

该能力通过全面的监控与审计机制，体现了组织对负责任 AI 实践的承诺。组织可以使用 Amazon Bedrock 中的模型调用日志，在 [Amazon CloudWatch Logs](https://aws.amazon.com/cloudwatch) 或 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）桶中捕获完整的请求与响应数据，包括具体的 guardrail trace 记录，显示内容在何时、以何种方式被过滤。结合记录 guardrail 配置与策略执行操作的 [AWS CloudTrail](https://aws.amazon.com/cloudtrail) 集成，企业可以放心扩展其生成式 AI 举措，以恰当的安全机制保护品牌、客户与数据——在创新与伦理责任之间取得必要平衡，从而建立对 AI 系统的信任。

今天就通过 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 上手，在整个组织中实施兼顾创新与负责任 AI 治理的可配置防护措施。
