# 标准银行集团如何自动化生成式 AI 风险评估

*本文由 AWS 的 Tala Qraitem 与 Standard Bank Group 的 Jörg Fischer 共同撰写*

有一套 AI 政策是一回事，逐个用例证明 AI 系统确实遵守这套政策则是另一回事。每新增一个生成式 AI 应用，就多出一个需要证明的系统。如今团队几天就能做出一个应用，但它在触达客户或员工之前，仍要拿到风险委员会的批准。一旦批准取决于评审人员读文档、手工测试系统，治理就成了整条流水线上最慢的一环。

Standard Bank Group 选择把这套证明自动化。该银行与 AWS Professional Services 合作，部署了一套自动化评估，按国际 AI 标准及其自身政策为每个生成式 AI 用例打分。评估产出报告和仪表板，说明哪些措施已经就位、哪些运转良好、哪些仍待缓解。本文介绍这套评估如何在 AWS 上运行，以及 Standard Bank Group 从最初几轮运行中学到了什么。

## 用你已有的框架治理 AI

Standard Bank Group 不需要一套新的 AI 政策。和多数大型银行一样，它早已有成熟的模型风险实践，覆盖可解释性、公平性等事项，也有一套变更风险流程，在上线前依风险高低评估每个新用例。

生成式 AI 抬高了复杂度：模型和工具每三到六个月就换一轮，而每个用例仍要达到同样高的安全与合规门槛。

> “在 Standard Bank，这项评估展示了我们如何与 AWS 合作，把智能、自动化的风险管理嵌入我们的 AI 旅程，让我们能够加快创造有意义的业务价值，同时守住银行业所要求的信任与管控。我们相信，负责任的 AI 不是把创新放慢，而是让创新能够带着信心去构建和扩展。”

— Jörg Fischer，Standard Bank Group 集团首席信息与 AI 官

目标是把证据收集和测试自动化，再把结果送入 Standard Bank Group 已有的审批关卡。评审与批准仍归风险委员会，但委员会如今依据的是一致证据——各处用例以同一方式收集来的证据。

## 评估如何运作

![在 Standard Bank Group 的 AWS 账户中运行的自动化 AI 风险评估架构图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/19/ML-22493-1.png)

图 1：Standard Bank Group AWS 账户中的评估流水线，从受理、评估到报告

评估完全跑在 Standard Bank Group 自己的 AWS 账户里。文档、代码和测试结果都存放在该账户的 Amazon Simple Storage Service（Amazon S3）存储桶中。AWS Well-Architected Tool 负责受理，AWS Step Functions 编排流水线，Amazon Bedrock 上的基础模型负责评估证据。它用的是一种叫 LLM-as-a-judge 的方法，即由大语言模型对照既定标准核查证据。

有了 Amazon Bedrock，Standard Bank Group 无需跳出它在 AWS 上已有的管控就能用上基础模型。银行通过 AWS Identity and Access Management（IAM）控制模型访问，与其他 AWS 工作负载的做法一致。Amazon Bedrock 不会把银行的 prompt 或模型输出分享给模型提供商，也不会用它们训练模型。由于 Amazon Bedrock 通过单一 API 提供多种基础模型，团队只要改一项配置，就能换用更新的评判模型，无需重建流水线。

每次评估走四步。前两步，一个预评估 agent 收集用例证据，随后流水线检查这些证据并直接测试应用；第三步对照控制项评估证据；第四步以标准的预定义格式汇总结果，交付给据此行动的人。

### 步骤 1：预评估 agent 收集证据

Well-Architected Tool 中的自定义 lens 约有 40 个问题，每个问题对应一类风险事件，例如技术文档不完整或人工监督不足。交付团队不必再从零填写。运行在 AWS Fargate 上的预评估 agent 会扫描用例的代码仓库和文档，把相关文件映射到每个问题，并用答案和证据链接预填 lens。交付团队随后复核这些答案、纠正错误，并补上 agent 没能找到的证据。

### 步骤 2：流水线检查产物并测试应用

流水线依据四类证据工作。

- 系统文档，说明应用如何设计、构建与评估。
- 政策文档，规定角色、职责以及事件处理等流程。
- 源代码和系统 prompt，体现控制项如何落实。
- 对应用的实时调用，反映它在实际运行中的行为。

对文档和代码，流水线检查每份产物是否包含其所映射控制项要求的内容。每个控制项都来自某项国际 AI 标准或框架，或来自 Standard Bank Group 自身的政策。例如，事件处理流程必须说明事件如何上报。

实时测试时，流水线通过应用的 AWS Lambda 函数或 API 调用应用。交付团队提供典型用户会问的问题。流水线另外加入一组内置的越狱尝试和跑题问题，期望应用拒绝作答；它还会把同一个 prompt 以原始形式和改写形式发送多次，并用 Amazon Bedrock 上的嵌入模型检查答案在语义上是否保持一致。在团队给出预期答案的场合，流水线会衡量响应与预期答案的贴近程度。所有响应都存入 Amazon S3，评审人员可以看到应用究竟生成了什么。

### 步骤 3：基于标准的 LLM-as-a-judge 评估

这一步由 Amazon Bedrock 上的基础模型担任评判者。评估按模型原样使用，不做任何微调或定制。（模型可用性因 AWS 区域而异，部署前请查阅[各区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。）对每个问题，模型判断特定证据是否出现在产物和应用响应中，返回是或否。

每项检查都对应 AI 管理、AI 风险或 AI 安全方面某项国际标准或框架中的一个控制项。Standard Bank Group 还用自身标准构建评判问题来定制 lens，使问题总数超过 300 个。这些检查覆盖下表中 AWS 负责任 AI 的八个维度：

| **维度** | **评估关注的内容** |
| --- | --- |
| 真实性与稳健性 | 即使面对意外或对抗性输入，输出仍然正确 |
| 隐私与安全 | 对数据和模型进行恰当的收集、使用与保护 |
| 透明度 | 帮助利益相关方就其对 AI 系统的使用做出知情选择的信息 |
| 公平性 | 考虑对不同利益相关群体的影响 |
| 安全性 | 防止有害输出与滥用 |
| 可控性 | 监控和引导系统行为的机制 |
| 治理 | 贯穿 AI 供应链（含提供商与部署方）的最佳实践 |
| 可解释性 | 理解和评估系统输出的方式 |

每项风险得到一个可能性评分——模型未能找到的必需证据所占比例——以及一个固定的严重性等级，银行的风险团队可以调整。两者合成从 Very low 到 Critical 的评级。每一处缺失证据都对应一项具体缓解措施，以及它所出自的标准条款或政策条款。风险官向监管机构解释决策时，可以把任何发现追溯回来源。图 2 以一处缺失证据为例，走完从证据请求到建议修复的整个过程。

图 2：一项发现如何从证据追溯到修复

Standard Bank Group 用两种方式保护和校验评估输出。每一次 AI 模型交互都由 Amazon Bedrock Guardrails 保护，确保符合银行既有的安全与负责任 AI 标准；评估的模型调用要经过银行在其各 AWS 账户中为 AI 工作负载统一实施的同一套防护。这些护栏筛查有害内容，也筛查操纵模型的企图。

评估的设计还保证输出可以被校验。流水线不让模型给开放式意见，而是提出范围很窄的是/否问题，每个问题的措辞都对应一个具体控制项。一套风险团队可以查看的固定公式把这些回答换算成分数。每次评估运行多遍，以衡量答案的一致程度，不一致的发现会在评审界面中被标出。每条判断都与支撑它的证据一起存储，评审人员和审计人员可以追溯结论的形成过程。

### 步骤 4：面向不同受众的报告

流水线以标准格式汇总结果，交付形式包括高管演示文稿、缓解清单、详细技术报告，以及一个随时间跟踪各用例评分的 Amazon CloudWatch 仪表板。关卡决策之前，评审人员在带单点登录的自定义评审界面中确认发现。他们可以在那里添加用例、审阅问题、附上业务理由修改答案，并重写输出。

评估产出的是针对各控制项的证据。它不对任何法规做合规认证，Standard Bank Group 仍对自身的监管判断负责。

## 依据 Standard Bank Group 自身的规则测试

国际标准为每个用例提供共同基线，但银行的风险委员会是按其自身政策批准用例的。为此，「问题工厂」（question factory）从内部文档生成额外的评判问题。Standard Bank Group 的风险团队借此把内部政策转成在每个用例上运行的检查。

由于这些检查直接源自政策条文，政策一变，测试就跟着变。之后每次评估都会自动套用更新后的规则，风险团队几乎不需要手工返工。

> “多数组织把政策当成拿来读的东西。Standard Bank Group 把政策当成拿来跑的东西。当每条规则都变成对着实时系统运行的检查，政策更新就不再是一份备忘录，而变成了一项测试。这从根本上改变了银行以负责任的方式扩展 AI 的速度。”

— Sri Elaprolu，AWS 前沿 AI 科学与工程总监

## 融入用例生命周期

评估对应了用例生命周期的三个阶段。概念验证阶段它是可选项，让团队尽早看到潜在缺口；进入构建阶段它成为必选项，审批关卡把它的结果当作正式证据。目前该评估已在 Standard Bank Group 的生产环境中运行，在上线前评估用例。接入线上工作负载后，评估将按计划重跑，或在代码、配置变更时重跑，让证据在发布之后长期保持最新。银行的团队已经通过一个中央系统自行触发评估，用例在单一工作流中从受理流转到评估。

## 这对金融机构意味着什么

在 Standard Bank Group，这套评估把历来需要人工两周的评审压缩成约两小时生成的一份完整风险报告，并已在六次评估中得到验证。整改之后，用例风险评分还提升了 14%。这强化了负责任 AI 治理，减少了合规瓶颈，也缩短了从评估到生产的路径。

这一做法能惠及参与 AI 用例审批的三类人：

- 风险与合规负责人拿到的是每个用例格式一致的证据，可追溯到已发布标准或内部政策条款。从你已经在跑的框架起步，正如 Standard Bank Group 依托其现有风险流程和审批关卡所做的那样。
- 交付团队在概念验证阶段就知道要改什么，那时改动成本最低，不必等到审批关卡被拒。
- 高管可以扩大 AI 组合，而评审工作量不必同比例增长。

> “要在整个企业大规模采用 AI，需要信任，既包括内部的信任，也包括客户的信任。事实证明，这项评估对于让所有产品团队都能证明自己构建的是符合我们自身及行业最佳实践的企业级解决方案，至关重要。”

— Duncan Macdonald，Standard Bank Group 首席技术官

## 从审批关卡到持续保障

银行设计审批关卡时，面对的是每年只变动几次的系统。生成式 AI 应用会随每次 prompt 更新、每个模型版本、每个新数据源而变。当它们承担更多自主任务，需要证据支撑的决策数量持续增长，靠增加评审人员跟不上这个变化速度。

Standard Bank Group 的做法指向另一种运营模式。当政策变成测试、证据自动收集，治理就从交付末端的检查点移进系统本身。组合中的每个 AI 应用都能随身带一份最新、可审计的记录，说明自己如何满足银行标准，并在代码或配置变更时刷新。风险团队把时间用在判断和政策设计上，银行也能向监管机构出示与自身决策所用的同一套证据。

这个基础还能继续外延。持续重评让证据在上线后始终与变化的代码库对齐。新的监管要求可以一次性编码成检查，套用到每个用例。汇总后的评分让董事会看到企业范围的 AI 风险全貌，而不是一堆零散评审。
