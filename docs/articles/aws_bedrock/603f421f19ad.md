# 从理论到交付：Atos 如何让 400 名工程师掌握 agentic AI

当 Atos 着手让 400 名工程师在 agentic AI 上从理论走向交付时，团队面对的是一个熟悉的挑战：如何构建真实世界的能力，而不只是理论知识。在线课程和课堂授课能打下基础，但它们并不总能给团队带来把 AI 有效应用于业务问题所需的信心或实践经验。

通过 [Atos 与 AWS 的合作](https://aws.amazon.com/partners/atos/)，我们已经看到动手实践是有效 AI 赋能中缺失的那一环。此前我们已通过 AWS DeepRacer 交付过强化学习的实践赋能，并在 2025 年通过 AI League 交付过模型微调的实践赋能。

2026 年，Atos 与 AWS 合作，为 400 名工程师举办了一场 agentic AI League 活动。在三天时间里，工程师们从有限的动手经验，进阶到构建具备寻路、护栏、记忆和微调模型的多 agent 系统。他们在一个实时排行榜上竞争，评分同时考察性能与效率。

参与者的技能水平差异很大。有些是已有 AWS 经验的开发者。另一些则是第一次使用 AWS，或者担任产品负责人、项目经理这类技术性较弱的角色。

- 5% 对 agentic AI 毫无先前了解。
- 25% 对该主题有基本认知。
- 50% 理解该主题但没有动手经验。
- 20% 对 agentic AI 服务有实践经验。

本文解释我们为什么选择 AI League 这种形式、工程师们构建并学到了什么、涉及了哪些 AWS 服务，以及其他企业在举办类似活动时应当考虑什么。

## 为什么选择 AWS AI League？

Atos 对 agentic AI 有战略承诺，包括在全球多个地点建设 [Sovereign Agentic AI Studios](https://atos.net/en/services/ai-atos-sovereign-agentic-studios)。我们需要一种方式，让工程团队快速掌握 agentic AI 模式，不是通过被动的培训，而是通过动手交付。传统工作坊传授概念。AI League 则通过更贴近真实交付条件的实际工作来构建能力。

相比常规培训，AI League 这种形式有几项优势：

- 即时的实际应用——工程师构建出能跑起来的 agentic 系统，而不是仅仅阅读相关资料。
- 竞争带来的动力——排行榜制造了紧迫感和参与度，这是被动学习很少能达到的。
- 真实的 AWS 服务——活动中构建的一切都使用原生 AWS 服务，工程师可以直接应用于客户交付，包括 [Amazon Bedrock](https://aws.amazon.com/bedrock/)、[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)、[AWS Lambda](https://aws.amazon.com/lambda/)、[Kiro](https://kiro.dev/) 和 [Amazon SageMaker](https://aws.amazon.com/sagemaker/)。
- 可衡量的结果——AI League 排行榜分数反映了功能完整性和方案效率。

## 时间投入与形式

AWS AI League 是交钥匙方案，所以准备工作很直接。准备过程只需要与 AWS 开几次会，就后勤和活动细节达成一致，另外再加一套宣传活动并收集参与者信息的机制。

由于 AWS AI League 通过 [AWS Workshop Studio](https://workshops.aws/) 交付，活动可以在一天到三天内举办。为了让工程师有最大的灵活性，我们选择三天的形式。参与者的时间投入如下：

- 启动工作坊（2 小时）——介绍 AI League、所用的 AWS 服务以及挑战的形式。
- 每日 office hours 通话（1 小时）——为需要帮助或想分享想法的工程师提供支持。
- 前三名总决赛（1 小时）——我们在此加冕 2026 年的冠军。

在这些排定的场次之外，工程师可以在不影响本职工作的前提下自由迭代自己的 agentic AI 方案。

评分模型奖励以下行为：

- 成功完成挑战——答对得分，答错则损失生命。
- 收集金币——与挑战不同，金币不带来风险，也不需要额外花时间去收集。
- 完成地图——在规定时间内抵达宝藏的工程师会获得宝藏奖励分。
- 保留生命——挑战结束时每剩余一条生命都会获得额外分数。
- 效率——简洁的 agent 响应比啰嗦的响应得分更高。
- 微调——开发专门的小语言模型可获得奖励分。

### Amazon Bedrock

借助 Amazon Bedrock，工程师可以访问为 agent 推理提供动力的模型。按区域划分的模型可用性，请参阅 [Amazon Bedrock 中按 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)：

- 为不同任务选择合适的模型，先从一个熟悉的模型开始，再对自己的微调模型执行推理。
- 设计有效的 system prompt，以高效回答问题或委派给子 agent 和工具。
- 管理 token 用量和成本。

### Amazon Bedrock AgentCore

借助 Amazon Bedrock AgentCore——一个可以用任意框架或模型大规模构建、连接和优化 agent 的平台——工程师编排了多 agent 系统。在 AI League 期间，工程师使用了以下 AgentCore 能力：

- AgentCore runtime（Amazon Bedrock AgentCore 的一项能力）——工程师用它托管 agent 容器，容器处理挑战格子并在时限内返回被评分的响应。
- AgentCore Gateway（Amazon Bedrock AgentCore 的一项能力）——工程师通过 Model Context Protocol（MCP）把 agent 的工具调用路由到 Lambda 函数，用于寻路、web 抓取和代码执行。
- AgentCore memory（Amazon Bedrock AgentCore 的一项能力）——工程师跨交互持久化上下文，使 agent 能回忆起之前的事件，例如已收集的钥匙和已解开的挑战。
- AgentCore Code Interpreter（Amazon Bedrock AgentCore 的一项能力）——工程师在隔离沙箱中安全执行代码，以应对计算类挑战。

### Amazon Bedrock Guardrails

借助 Amazon Bedrock Guardrails，你可以过滤内容，以防范有害的输入和输出。工程师配置了：

- 拒绝主题——必须被屏蔽的特定内容。
- 内容过滤器——针对仇恨、暴力和不当行为的阈值。
- 带自定义消息的输入与输出阻断。

### AWS Lambda

借助 AWS Lambda，你可以为模型无法自行可靠处理的任务构建自定义工具函数：

- 寻路——使用广度优先搜索（BFS）等算法在地图上导航。
- Code Interpreter——为计算类挑战执行代码。
- Web 抓取——抓取并解析网页以检索信息。

### Amazon SageMaker

借助 Amazon SageMaker，你可以搭建开发环境并微调模型。工程师使用了可验证奖励强化学习（RLVR）：

- Amazon SageMaker Studio 提供开发环境，包括一个内置 AI 开发工具的集成开发环境（IDE）。
- 无服务器微调在参与者创建的数据集上训练自定义模型。
- 微调后的模型随后部署到推理端点以承载流量。

## 工程师们学到了什么

AWS AI League 呈现出若干可以直接应用于生产级 agentic AI 工作的实践工程经验。

### 约束条件下的 prompt engineering

最清晰的教训之一是：成功并不来自单纯地写 prompt，而来自写出在真实约束下仍然有效的 prompt。每一个多余的 token 都会扣分。每一次不必要的工具调用都会消耗时间并扣分。工程师很快发现，让方案跑通只是第一步。让它变得高效，才是这场比赛与真实客户场景最贴近的地方。

### 多 agent 架构决策

工程师必须决定架构中要包含多少个 agent，从带专用工具的单一用途 agent，到功能更综合的 agent。每种做法在 token 用量、延迟和可靠性上都有取舍。这与生产环境中关于 agent 设计的真实决策高度一致。

### 护栏配置

Violent Violet 挑战凸显了一个重要教训：护栏必须足够精确，既能屏蔽不受欢迎的内容，又不会过度屏蔽合法查询。如果过于激进，工程师会在其他挑战中失败。如果过于宽松，他们就会在护栏挑战中失败。这可以直接转化为生产环境 AI 安全的一堂实践课。

### 寻路算法设计

构建寻路工具要求工程师思考：

- 针对不同场景的多种策略（速度优先还是分数最大化）。
- 风险评估（尖刺损失生命，而撞墙则直接结束游戏）。
- 时间预算（是走遍每个挑战，还是直奔宝藏？）
- 依赖顺序（例如，先收集钥匙再尝试开门）。

### 可观测性的价值

在两次运行之间查看 Amazon CloudWatch Logs 的工程师，进步似乎更快。而那些只是猜测哪里出了问题的工程师，进展往往更慢。这强化了一条核心工程原则：先给方案做好埋点，观察之后再动手。

### 用 AI 构建 agentic AI 方案

使用 Kiro 这类 AI 开发工具的工程师往往进步迅速。那些把自己所面对挑战的完整上下文交给 AI 工具的工程师，通常能更快取得更好的结果。这印证了一个更广泛的道理：当 AI 工具扎根于正在解决的具体问题时，它能带来更大的价值。
