# 使用查询感知压缩降低 Amazon Bedrock 上的 RAG 成本

每次调用时发送给基础模型（foundation model，FM）的输入 token，往往是在规模化运行[检索增强生成（RAG）](https://aws.amazon.com/what-is/retrieval-augmented-generation/)时成本的重要部分。查询感知压缩（query-aware compression）提供了一种减少进入模型的 token 数量的途径。[Amazon Bedrock](https://aws.amazon.com/bedrock/?trk=7ecf60df-6136-414c-a7c3-6aa4d2d6019f&sc_channel=ps&ef_id=EAIaIQobChMIypH5r4fBlQMVqEx_AB1OvwmNEAAYASAAEgIGTfD_BwE&gads_camp=23532472972&gads_ag=194311072004&gads_ad=795877020842&gads_kw=amazon%20bedrock&gads_matchtype=e&gads_network=g&gads_device=c&gads_geo=9026933&gad_campaignid=23532472972&gbraid=0AAAAADjHtp8ByFw1VLhJ9bdURylYSJ7dd&gclid=EAIaIQobChMIypH5r4fBlQMVqEx_AB1OvwmNEAAYASAAEgIGTfD_BwE) 提供了构建 RAG 应用所需的[基础模型](https://aws.amazon.com/what-is/foundation-models/)与相关功能。RAG 检索通常会针对高召回率进行调优，返回一大批可能相关的 chunk，使主模型有充分的源材料可用。这种设计让构建者确信在推理时正确的信息是可得可用的。随着工作负载扩展，构建者常常希望通过减少主模型处理的输入 token 数量来优化成本与性能的权衡，同时保持答案质量。Amazon Bedrock 开放、可组合的架构支持自定义的检索后处理步骤，用来精炼最终进入主模型的内容。

本文介绍一种检索后定制模式，它在大幅减少输入 token（并因此节省成本）的同时保持答案质量。该模式兼容 Amazon Bedrock 上的各类 RAG 检索器，包括 Amazon Bedrock [知识库](https://aws.amazon.com/bedrock/knowledge-bases/)。一个附加收益是，移除无关上下文也缩小了幻觉的滋生面。在检索之后、最终答案调用之前，Amazon Bedrock 上一个更小、成本更低的模型会依据用户查询对检索到的 chunk 进行过滤。主模型随后接收过滤后的上下文并生成答案。

我们会从整体上介绍该模式的架构，展示在一个 [AWS Lambda](https://aws.amazon.com/pm/lambda/?trk=2abe6167-e3db-40c4-a9fa-b283e7b4d7c8&sc_channel=ps&ef_id=EAIaIQobChMI0eez9oXBlQMVVTfUAR2_2xb9EAAYASAAEgI-OvD_BwE&gads_camp=23527793912&gads_ag=191938386622&gads_ad=802094701896&gads_kw=amazon%20lambda&gads_matchtype=e&gads_network=g&gads_device=c&gads_geo=9026933&gad_campaignid=23527793912&gbraid=0AAAAADjHtp8GsQ-cK5F5U0jJWeu2our88&gclid=EAIaIQobChMI0eez9oXBlQMVVTfUAR2_2xb9EAAYASAAEgI-OvD_BwE) 函数中的核心 Amazon Bedrock 实现，梳理成本模型与延迟上的权衡，并说明我们如何评估答案质量。我们还会探讨该模式如何叠加在 Amazon Bedrock 现有能力之上，例如 [prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)、Amazon Bedrock [Intelligent Prompt Routing](https://aws.amazon.com/bedrock/intelligent-prompt-routing/) 以及 Rerank API，以实现叠加式的成本节省。

## 前置条件

要实施该方案，请完成以下前置步骤：

- 拥有一个有效的 [AWS 账户](https://signin.aws.amazon.com/signup?request_type=builderId)。
- 为 Lambda 函数创建一个 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色，以便它访问 Amazon Bedrock。相关说明请参阅[创建角色以将权限委派给 AWS 服务](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-service.html)。
- 为该 IAM 角色添加策略权限。
- 在你的 AWS 区域中为级联架构里的两个模型开通 Amazon Bedrock 模型访问权限：一个较小的压缩模型（本文使用 Anthropic Claude Haiku）和一个主模型（Anthropic Claude Sonnet）。请在 Amazon Bedrock 控制台的 Model access 下[申请访问权限](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)。

## 查询感知压缩如何降低 Amazon Bedrock 上的 RAG 成本

使用传统 RAG 基础设施或框架的 RAG 流程大致如下：

- 应用对用户查询做向量化（embedding）。
- 向量索引返回 top-k 个 chunk（通常为 5–20 个）。
- 可选地，由 reranker 按相关性对这些 chunk 重新排序。
- 所有检索到的 chunk 被拼接进 prompt。
- 主模型生成答案。

检索到的上下文规模随 top-k 与 chunk 大小而扩展：在典型的 chunk 大小下检索 5–20 个 chunk，会让许多技术文档与法律类 RAG 工作负载落在每次查询数千个输入 token 的区间。降低单次查询的 token 数可以带来可观的成本节省。

## 架构概览

一个较小的模型会同时读取检索到的 chunk 与查询，只输出与问题相关的原文片段（verbatim span）。本文使用 Claude Haiku，但该模式也适用于 Amazon Bedrock 上同一模型家族内的其他「较小模型/主模型」组合。压缩调用与主模型的答案调用都运行在同一个 AWS Lambda 函数内。在上游，检索器对查询做向量化并返回 top-k 个 chunk。Amazon Bedrock 知识库——由 Amazon OpenSearch Serverless 支撑的全托管 RAG 能力——就是这样的检索器之一。Lambda 函数把这些 chunk 作为输入接收，并返回最终答案。压缩调用是标准 RAG 流程中唯一新增的步骤。

由于较小模型每 token 的成本低于主模型，节省正来自于在昂贵的答案调用之前裁剪上下文。而节省幅度有多大，取决于两件事。

下图展示了该方案的架构。

图 1：Amazon Bedrock 上的查询感知上下文压缩架构

**流程按以下步骤推进：**

- 用户向应用提交查询。
- 应用把查询发送给检索器，检索器在已向量化的知识源中执行搜索。
- 检索器把 top-k 个 chunk（完整的检索上下文）返回给应用。
- 应用把查询与全部检索到的 chunk 传给一个 AWS Lambda 函数，该函数通过 Amazon Bedrock Converse API 把它们发送给较小的模型（Claude Haiku）。这就是压缩调用。
- 较小模型只输出与查询相关的原文片段（即压缩后的上下文）。
- Lambda 函数通过 Converse API 把查询与压缩后的上下文发送给主模型（Claude Sonnet）。这就是答案调用。
- 主模型生成最终答案，应用将其返回给用户。

### 为什么这在经济上成立

经济性取决于两个因素：Amazon Bedrock 上小模型与主模型之间的价格比，以及较小模型所达到的压缩比。

对于一次 RAG 查询，设检索到的输入 token 为 `R`，压缩比为 `c`（其中 `c` > 1），最终答案输出为 `A` 个 token，每 token 价格为 `P_small_in` / `P_small_out`（较小模型的输入与输出价格）以及 `P_large_in` / `P_large_out`（主模型的输入与输出价格）：

| **阶段** | **基线** | **使用压缩** | **实际发生什么** |
| --- | --- | --- | --- |
| 较小模型读取 chunk | — | `R` × `P_small_in` | 较小模型接收查询和全部检索到的 chunk 作为输入 |
| 较小模型写出压缩输出 | — | `(R/c)` × `P_small_out` | 较小模型只输出与查询相关的原文片段 |
| 主模型读取上下文 | `R` × `P_large_in` | `(R/c)` × `P_large_in` | 主模型接收上下文作为输入以生成答案 |
| 主模型写出答案 | `A` × `P_large_out` | `A` × `P_large_out` | 主模型为用户生成最终答案 |
| 合计 | `R·P_large_in + A·P_large_out` | `R·P_small_in + (R/c)·P_small_out + (R/c)·P_large_in + A·P_large_out` |  |

压缩调用增加了较小模型的输入与输出成本。节省则来自向主模型发送 `R/c` 而非 `R` 个 token。当以下条件成立时，经济性更倾向于压缩：

- 检索到的上下文很大（花在较大模型上的节省占主导）。
- 大模型与小模型之间的价格比很高（Sonnet/Opus 搭配 Haiku）。
- 对于给定查询，检索内容中有相当一部分可以被裁剪掉而不影响答案质量。

## 在 Amazon Bedrock 上实现

该模式位于检索与最终答案调用之间。我们把它实现为一个单独的 AWS Lambda 函数，由它用 Converse API 编排两次 Amazon Bedrock 模型调用。该函数以用户查询和检索到的 chunk 作为输入事件接收。

### 压缩用的 prompt

压缩用的 prompt 是实现中最重要的部分。它必须指示较小模型去抽取片段而不是做摘要，禁止改写与重写，并保留足够的周边上下文，使引用仍然准确。

```
COMPRESSION_SYSTEM_PROMPT = """You extract evidence from retrieved documents.
You will receive a user QUESTION and a list of CHUNKS.

Your job:
1. For each chunk, identify the spans (verbatim sentences or short paragraphs)
that contain evidence directly relevant to answering the QUESTION.
2. Output ONLY those spans, copied verbatim from the source. Do not paraphrase,
summarize, or rewrite.
3. Preserve chunk identifiers so the downstream system can cite sources.
4. If a chunk contains no relevant evidence, output the chunk identifier
followed by NO_RELEVANT_EVIDENCE.

Output format (strict):
[CHUNK_ID: <id>]
<verbatim span 1>
<verbatim span 2>
[CHUNK_ID: <id>]
NO_RELEVANT_EVIDENCE

Do not add commentary, headings, conclusions, or your own words. Only verbatim
spans from the source chunks, grouped by chunk identifier."""
```

### Lambda 函数

该函数接收用户查询与检索到的 chunk，从环境变量中读取两个模型 ID，并初始化一个配置了自适应重试的 Amazon Bedrock Runtime 客户端。随后它通过 Bedrock Converse API 发起两次调用：第一次调用较小模型来压缩 chunk，第二次调用主模型来基于压缩后的证据生成答案。压缩调用以 temperature 0.0 运行，这使抽取过程保持确定性，从而让较小模型按片段在源文中的原样抄录：

步骤 1：压缩。较小模型对检索到的 chunk 进行过滤。

```
compressed = bedrock.converse(
    modelId=COMPRESSION_MODEL_ID,
    system=[{"text": COMPRESSION_SYSTEM_PROMPT}],
    messages=[{"role": "user",
               "content": [{"text": f"QUESTION:\n{query}\n\nCHUNKS:\n{chunks}"}]}],
    inferenceConfig={"temperature": 0.0},
)
```

步骤 2：回答。主模型基于过滤后的证据进行推理。

```
answer = bedrock.converse(
    modelId=ANSWER_MODEL_ID,
    system=[{"text": "Answer using only the evidence provided. Cite sources."}],
    messages=[{"role": "user",
               "content": [{"text": f"QUESTION:\n{query}\n\nEVIDENCE:\n{compressed}"}]}],
)
```

**注意：** 这些 prompt 只是示例，应根据你的文档与问题类型做调整。

## 方法

在推荐该模式之前，我们对其做了实证评估。基准测试覆盖：

- 一个超过 500,000 份文档的语料库，横跨 9 种企业源类型，包括聊天消息、电子邮件、issue tracker 工单、共享盘文档、CRM 记录、会议转录、代码仓库和 wiki 页面。
- 一组 500 个问题，分布在 10 个类别，从窄口径的事实查找到范围更广的多部分问题，既有措辞精确的查询，也有更口语化的查询。
- 多种压缩条件：不压缩（基线）、压缩，以及 rerank 加压缩。
- 每个查询都跑过基线与优化后的 pipeline，答案由一个[大型语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）评判器打分。
- 对照参考答案，从四个维度（正确性、完整性、引用准确性、简洁性）对质量打分。忠实性单独跟踪，用主模型收到的证据逐条核对每个答案中的主张。

这些数字描述的是某一个语料库、某一个领域和某一种查询分布。在你自己的文档与查询上，结果会有所不同。

## 生产环境使用的考量

在采用该模式之前必须权衡三件事：新增压缩调用的延迟、对答案质量的影响，以及该工作负载是否适配。以下各节分别讨论。

### 延迟

增加一次较小模型的调用会在路径中引入一个额外步骤。Claude Haiku 针对速度做了优化；而且由于主模型随后处理的是更小、更聚焦的上下文，这部分新增时间会在答案调用中部分收回。端到端的总延迟等于压缩调用加上在聚焦上下文上的答案调用。净影响取决于主模型在原始上下文规模下受计算约束的程度。

对于延迟敏感的场景（亚秒级聊天），请在部署前用你自己的上下文规模做测量。

### 质量

压缩涉及几个值得刻意设计的因素。

| **维度** | **设计考量** | **该模式如何处理** |
| --- | --- | --- |
| 事实一致性 | 主模型应当收到它所需的全部证据 | prompt 指示忠实、逐字地抽取所有与查询相关的证据 |
| 引用保留 | 片段始终与来源 chunk 绑定 | `[CHUNK_ID: <id>]` 标记随 prompt 一起传递 |
| 忠实抽取 | 输出与源文保持逐字一致 | `temperature=0.0`、「只做逐字抽取」的指令，以及可选的抽取后片段校验 |
| 多步推理 | 分析型问题的证据链保持完整 | 当问题涉及多个来源时，压缩模型会保留更多片段 |
| 数值推理 | 具体数字被保留 | 「只做逐字抽取」的指令按源文原样保留数字与计算 |

### 如何选择较小模型

以下几点考量可以协助你选择较小模型：

- **相对定价。** 该模式的节省取决于较小模型与主模型之间的价格比。一旦把压缩调用的成本计入，较小模型相对价格越低，留给净节省的空间就越大。Amazon Bedrock 的模型家族覆盖一系列价位，当前费率可在 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/) 页面查看。
- **推理速度。** 压缩调用被加到请求路径上，因此针对快速推理优化的较小模型能限制额外延迟。
- **模型家族一致性。** 从同一家族中选择较小模型与主模型，可以让两次调用在格式、chunk 标记和指令处理上保持一致。Claude Haiku 搭配 Claude Sonnet、Amazon Nova Micro 搭配 Amazon Nova Pro，就是 Amazon Bedrock 上这类配对的例子。有关按区域划分的模型可用性，请参阅 [Amazon Bedrock 中按 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

### 部署前推荐的评估方法

- 从你的应用日志（已去标识化）中汇集一组有代表性的查询作为评估集，覆盖窄口径查找与范围更广的多事实问题，并按它们在生产中出现的比例分配。
- 在相同的检索结果上分别运行基线与压缩 pipeline，使对比只反映压缩本身的效果。
- 对照参考答案，在你这个工作负载真正重要的维度上为两组答案打分，例如正确性、完整性和引用准确性；同时对照主模型收到的证据评估忠实性，从而暴露那些不被该证据支持的主张。
- 设定适合该工作负载的验收阈值，达标之后再推广该配置。

对于生产部署，[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 可以提供额外的内容过滤与事实性校验（grounding validation），作为与压缩模式并行的补充控制。

### 该模式适用的场景

当三个条件同时成立时，该模式才有价值：检索到的上下文很大、主模型是调用中昂贵的一环、问题相对于检索范围而言较窄。以下场景都具备这些特征。

- **受监管行业的合规与政策助手。** 公用事业、金融服务、保险和医疗健康行业保存着冗长的公告、费率表和政策文档，其中往往一个章节就能回答大部分问题。检索会拉回整份公告（8,000–15,000 个 token），而分析师只需要其中一个条款。逐字抽取既保留了监管措辞的原文，也保留了来源 ID，这在答案必须能在审计中站得住脚时尤为重要。
- **基于大型产品知识库的客户支持 copilot。** top-k 被设得较高，以便助手不太可能漏掉边缘情况，这意味着大多数工单检索到的内容远超所需。「如何重置 X」或「Y 的费用是多少」这类工单，通常靠长文中某一两段就能解决。压缩在不触动支持工程师已经信任的检索策略的前提下，降低了单个工单的推理成本。在支持量很大时（每月数十万工单），每次查询的少量节省会迅速累积。
- **面向 runbook 与 wiki 的内部工程与运维助手。** 针对 Confluence、SharePoint 和 runbook 的 RAG 会检索到大块内容，因为内部文档冗长且结构松散。问题通常很具体（「服务 Z 会代入哪个 IAM 角色」、「迁移 N 的回滚步骤是什么」）。答案只有几行，周边的策略与背景信息对回答并不需要。
- **金融研究与财报电话会分析。** 检索到的 chunk 信息密集（10-K 章节、电话会转录段落），而问题往往很尖锐（「CFO 在第三季度对汇率敞口说了什么」）。压缩既保留了分析师逐字引用来源的能力，又降低了在大模型上每次查询的成本。

如果你的工作负载满足其中大部分条件，该模式很可能值得做个原型：

- 每次查询平均检索到的上下文大致超过 5,000 个 token。
- 主模型的输入 token 足够昂贵，以至于上下文缩减 3–10× 会带来实质影响。
- 多数问题相对于检索到的内容量而言较窄，而不是宽泛的「把所有内容都总结一遍」请求。
- 你的延迟预算能容纳一次额外的模型调用（几百毫秒到约 1 秒）。
- 你已有或能够构建一个评估集，用来对比改动前后的质量。

如果你的工作负载是检索上下文很小的亚秒级对话式聊天，这个模式可能并不合适。可以考虑 Amazon Bedrock 的 prompt caching 与 Intelligent Prompt Routing 等能力，它们能以更少的额外延迟提供更多价值。

## 结论

该模式可以嵌入基于 Amazon Bedrock 构建的 RAG pipeline：在检索与最终模型调用之间放一个 Lambda 函数，即可压缩上下文，并针对你的具体工作负载微调成本与质量。

压缩用的 prompt 既能处理简单查找，也能处理复杂的多来源问题，无需另设路由逻辑。再结合 prompt caching、Intelligent Prompt Routing 和 Rerank API 等现有能力，这一方法能在整条 RAG pipeline 上带来叠加式的优化。

你可以把这个模式放在功能开关之后使用，在你真实的查询分布上度量它，并调整压缩 prompt 以匹配你的领域。

要开始使用，请参阅 [Amazon Bedrock 文档](https://docs.aws.amazon.com/bedrock/) 和 [Amazon Bedrock 定价页面](https://aws.amazon.com/bedrock/pricing/) 了解当前的模型费用。
