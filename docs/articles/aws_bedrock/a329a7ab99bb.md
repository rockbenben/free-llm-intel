# 用 Amazon Nova Multimodal Embeddings 打造制造业情报能力

如果你在航空航天、汽车或重工业制造领域工作，你的组织很可能维护着规模庞大的技术文档库。这些文档把书面规格与工程图、CAD 图纸、检验照片、热分析图和疲劳曲线混在一起。一个关于喷嘴喉部最高壁温的文本查询，答案可能锁在热力等值线图里，而不是写在文字中。纯文本检索系统无法把这些信息检索出来，因为它们看不到图像内容。

[Amazon Nova Multimodal Embeddings](https://aws.amazon.com/blogs/aws/amazon-nova-multimodal-embeddings-now-available-in-amazon-bedrock/) 通过把文本、图像和文档页面映射到同一个共享向量空间来填补这一空白。文本查询可以检索到工程图，图像查询也可以检索到书面规格，因为两种模态共享同一套坐标体系。

本文将基于 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的 Amazon Nova Multimodal Embeddings 与 [Amazon S3 Vectors](https://aws.amazon.com/s3/features/vectors/)，为航空航天制造文档构建一套多模态检索系统。我们在 26 条制造领域查询上评估该系统，并比较纯文本 pipeline 与多模态 pipeline 的生成质量。

## 为什么制造业需要多模态检索

大多数制造文档都是文本、图表和图像的混合体。一份工单里可能既有书面的装配步骤，也有标注过的完成步骤照片。一份检验报告会把合格/不合格的测量结果与焊缝射线图像并列。一份材料合格证既包含表格形式的力学性能，也包含 S-N 疲劳曲线，工程师在设计评审时必须查阅。

举几个本文所用数据集里视觉信息的具体例子：一张扭矩规格表被画在工程图内部，而不是以独立文本形式存储。一张用颜色编码的热力等值线图用来可视化火箭发动机喷管各处的峰值温度。一张制造工艺流程图用判断菱形和颜色编码的门格在视觉上标出质量停检点，相关周期时间则以标注形式直接出现在图本身。

纯文本检索系统处理这类文档的方式是：先用 OCR 提取文本，再对提取出的字符串做嵌入和索引。当答案出现在文档的文字部分时，这样可行；但纯文本系统会漏掉图中的空间关系、检验图像中的视觉模式，以及图表中编码的定量信息。当你搜索涡轮泵所用的轴承类型时，答案可能出现在某张剖视图的标注引线里，而 OCR 要么读错，要么把它剥离了原有的空间语境。

多模态嵌入走了另一条路。它不把图像转成文本再嵌入文本，而是让模型直接处理图像，并在与文本嵌入相同的空间里生成向量。关于涡轮泵轴承的文本查询可以基于视觉理解去匹配我们数据集中的那张剖视图，而不只是依赖 OCR 侥幸抽到的那点文字。

## Amazon Nova Multimodal Embeddings 概览

[Amazon Nova Multimodal Embeddings](https://docs.aws.amazon.com/nova/latest/nova2-userguide/embeddings.html) 已在 Amazon Bedrock 中提供，可为文本、图像和多页文档生成嵌入。文本、图像和文档三种模态都投射到单一的共享向量空间，这意味着你可以直接计算文本嵌入与图像嵌入之间的余弦相似度。

嵌入维度可以配置为 256、384、1024 或 3072。维度越高，捕捉的语义细节越多，但相似度检索所需的存储与算力也越大。本文的评估使用 1024 维，作为检索质量与成本之间的实用折中。模型还支持 `DOCUMENT_IMAGE` detail level，这是一种为包含图表、表格和带标注图纸等混合内容的页面设计的处理模式。

对于检索类负载，模型接受一个 `purpose` 参数，可取 `GENERIC_INDEX`（用于被索引的文档）或 `GENERIC_RETRIEVAL`（用于查询）。这种非对称嵌入方式改善了检索用的向量空间，而无需手动构造查询格式。

## 方案概览

我们在同一份数据集上构建了两条并行的检索 pipeline，以比较它们在下游生成质量上的差异。

**数据集——** 15 张独立技术图像（CAD 图纸、检验报告、测试图、材料规格、工艺流程图表）和 5 份多页 PDF（装配步骤、热试车报告、工程变更通知、材料合格证、不合格报告）。这些文档包含合成的航空航天制造数据。

**Pipeline A，多模态——** 使用 Amazon Nova Multimodal Embeddings 直接嵌入每张图像，并把每个 PDF 页面作为文档图像嵌入，然后写入 Amazon Simple Storage Service（Amazon S3）Vectors 索引。

**Pipeline B，纯文本基线——** 把每张图像和每个 PDF 页面送给 Amazon Nova 2 Lite 做 OCR 文本提取，再用 Amazon Nova Multimodal Embeddings（纯文本输入）嵌入提取出的文本，然后写入另一个独立的 Amazon S3 Vectors 索引。OCR 步骤使用以下 prompt：

```
Note: OCR prompt for text extraction
"Extract ALL visible text from this image exactly as it appears. Include all numbers, labels, annotations, table contents, headers, and footnotes. Preserve the structure (tables, lists, sections) as much as possible. Return only the extracted text, no commentary."
```

**评估——** 针对多模态索引运行 26 条制造领域查询，计算检索指标（Recall@K、Mean Reciprocal Rank（MRR）、NDCG@K）。随后对两条 pipeline 都先用 Amazon Nova 2 Lite 检索上下文并生成答案，再用一个大语言模型（LLM）评判者对照标准答案对每个答案打分。

下图展示了端到端的 pipeline 架构。源文档流经两条并行路径：Pipeline A 用 Amazon Nova Multimodal Embeddings 直接嵌入图像，Pipeline B 则先通过 OCR 提取文本再嵌入。两条 pipeline 都把向量存放在 Amazon S3 Vectors 中。查询时，检索到的上下文送入 Amazon Nova 2 Lite 生成答案，再由 LLM 评判者对照标准答案给每个答案打分。

### 生成多模态嵌入

为一张制造图像生成嵌入，只需向 Amazon Bedrock 发起一次 `InvokeModel` 调用。请求中指定图像字节、期望的嵌入维度和 detail level。对于 CAD 图纸这类独立图像，我们使用 `STANDARD_IMAGE`。对于文字与图形混杂的 PDF 页面，`DOCUMENT_IMAGE` 效果更好，因为模型会对表格和图表内容做额外处理。

```
import base64, json, boto3

bedrock_runtime = boto3.client("bedrock-runtime", region_name="us-east-1")
MODEL_ID = "amazon.nova-2-multimodal-embeddings-v1:0"

with open("dataset/nozzle_assembly_diagram.png", "rb") as f:
    b64_data = base64.b64encode(f.read()).decode("utf-8")

request_body = {
    "taskType": "SINGLE_EMBEDDING",
    "singleEmbeddingParams": {
        "embeddingPurpose": "GENERIC_INDEX",
        "embeddingDimension": 1024,
        "image": {
            "format": "png",
            "detailLevel": "STANDARD_IMAGE",
            "source": {"bytes": b64_data},
        },
    },
}

response = bedrock_runtime.invoke_model(
    modelId=MODEL_ID,
    body=json.dumps(request_body),
    accept="application/json",
    contentType="application/json",
)
embedding = json.loads(response["body"].read())["embeddings"][0]["embedding"]
print(f"Embedding dimension: {len(embedding)}")  # 1024
```

### 构建 Amazon S3 Vectors 索引

Amazon S3 Vectors 提供托管的向量存储与查询层。我们先创建一个 vector bucket 和一个按余弦相似度配置的索引，再以每批 50 条的规模写入嵌入。

```
s3vectors = boto3.client("s3vectors", region_name="us-east-1")

# Create vector bucket and index
s3vectors.create_vector_bucket(vectorBucketName="manufacturing-vectors")
s3vectors.create_index(
    vectorBucketName="manufacturing-vectors",
    indexName="manufacturing-multimodal",
    dataType="float32",
    dimension=1024,
    distanceMetric="cosine",
)

# Ingest a batch of embeddings with metadata
vectors = [
    {
        "key": "img-nozzle_assembly_diagram",
        "data": {"float32": embedding},
        "metadata": {
            "source_file": "nozzle_assembly_diagram.png",
            "type": "image",
        },
    }
]
s3vectors.put_vectors(
    vectorBucketName="manufacturing-vectors",
    indexName="manufacturing-multimodal",
    vectors=vectors,
)
```

### 查询索引

查询时，我们用 `GENERIC_RETRIEVAL` purpose 生成文本嵌入，然后调用 `query_vectors` 检索最相似的文档。`GENERIC_RETRIEVAL` purpose 告诉模型要针对查询与文档的匹配来优化嵌入。

```
query = "What is the torque specification for the chamber flange bolts?"

request_body = {
    "taskType": "SINGLE_EMBEDDING",
    "singleEmbeddingParams": {
        "embeddingPurpose": "GENERIC_RETRIEVAL",
        "embeddingDimension": 1024,
        "text": {"truncationMode": "END", "value": query},
    },
}
response = bedrock_runtime.invoke_model(
    modelId=MODEL_ID, body=json.dumps(request_body),
    accept="application/json", contentType="application/json",
)
query_embedding = json.loads(response["body"].read())["embeddings"][0]["embedding"]

results = s3vectors.query_vectors(
    vectorBucketName="manufacturing-vectors",
    indexName="manufacturing-multimodal",
    queryVector={"float32": query_embedding},
    topK=5,
    returnDistance=True,
    returnMetadata=True,
)
for v in results["vectors"]:
    print(f"  {v['key']}  (distance: {v['distance']:.4f})")
```

该查询把扭矩规格图和法兰螺栓布局图检索为最前面的结果，这两者都包含答案。纯文本系统则要依赖 OCR 正确地从工程图中捕获扭矩数值，而对复杂技术图纸来说这并不总是可靠。

## 评估方法

我们分两个阶段评估该系统：检索质量（系统能否找到正确的文档？）和生成质量（语言模型能否根据检索到的上下文给出正确答案？）。评估数据集包含 26 条查询，均源自那批航空航天制造文档，每条都配有标准答案的相关文档 ID 和一个参考答案。以下小节说明每个阶段的做法。

### 检索评估

对每条查询，我们用 `GENERIC_RETRIEVAL` purpose 生成文本嵌入，查询多模态 S3 Vectors 索引，并把返回的文档与标准答案的相关文档 ID 做比对。

```
query = "What is the torque specification for the chamber flange bolts?"
query_embed = generate_text_embedding(
    query, dim=1024, purpose="GENERIC_RETRIEVAL"
)

results = s3vectors.query_vectors(
    vectorBucketName="manufacturing-vectors",
    indexName="manufacturing-multimodal",
    queryVector={"float32": query_embed},
    topK=10,
    returnDistance=True,
    returnMetadata=True,
)
retrieved_ids = [v["key"] for v in results["vectors"]]
```

我们在 K=3、5、10 上计算三个指标：**Recall@K**（前 K 条结果中找到的相关文档占比）、**MRR**（衡量第一个相关结果出现得有多靠前）和 **NDCG@K**（归一化折损累计增益，相关文档排名越靠前得分越高）。

### 用 LLM-as-Judge 做生成评估

生成评估时，两条 pipeline 都为每条查询检索前五条结果。多模态 pipeline 把检索到的图像直接作为多模态上下文传给 Amazon Nova 2 Lite。纯文本 pipeline 则把 OCR 提取的文本作为字符串上下文传入。

```
def generate_answer_multimodal(query, retrieved_keys):
    """Pass retrieved images directly as multimodal context."""
    content_blocks = []
    for key in retrieved_keys[:5]:
        img_path = vector_key_to_image_path(key)
        with open(img_path, "rb") as f:
            img_bytes = f.read()
        content_blocks.append({"text": f"Retrieved document:"})
        content_blocks.append({
            "image": {"format": "png", "source": {"bytes": img_bytes}}
        })
    content_blocks.append({
        "text": (
            f"Review each image above carefully. "
            f"Answer the following question concisely and precisely.\n\n"
            f"Question: {query}\n\nAnswer:"
        )
    })
    response = bedrock_runtime.converse(
        modelId="us.amazon.nova-2-lite-v1:0",
        messages=[{"role": "user", "content": content_blocks}],
        inferenceConfig={"maxTokens": 500, "temperature": 0.1},
    )
    return response["output"]["message"]["content"][0]["text"]
```

每个生成的答案都用 Anthropic Claude Sonnet 4.5 作为 LLM 评判者，对照标准答案打分。评判者接收查询、标准答案和生成的答案，然后给出 1–5 分并附简短说明。

```
def judge_correctness(query, generated_answer, ground_truth):
    prompt = (
        "You are an evaluation judge. Score the generated answer compared "
        "to the ground truth on a scale of 1-5.\n\n"
        "1 = Completely wrong or irrelevant\n"
        "2 = Partially relevant but mostly incorrect\n"
        "3 = Somewhat correct but missing key information\n"
        "4 = Mostly correct with minor omissions\n"
        "5 = Fully correct and complete\n\n"
        f"Question: {query}\n"
        f"Ground Truth: {ground_truth}\n"
        f"Generated Answer: {generated_answer}\n\n"
        'Respond with ONLY a JSON object: '
        '{"score": <1-5>, "reason": "<brief explanation>"}'
    )
    response = bedrock_runtime.converse(
        modelId="us.anthropic.claude-sonnet-4-5-20250929-v1:0",
        messages=[{"role": "user", "content": [{"text": prompt}]}],
        inferenceConfig={"maxTokens": 200, "temperature": 0.0},
    )
    return response["output"]["message"]["content"][0]["text"]
```

把检索与生成分开评估，你就能定位每条 pipeline 在何处成功、何处失败。某条 pipeline 可能检索到了正确的文档，但如果生成器无法从所提供的上下文格式中提取信息，仍然会给出错误答案。

## 评估结果

我们在源自航空航天制造数据集的 26 条查询上评估了多模态 pipeline。每条查询都有一个或多个标准答案的相关文档 ID。检索指标衡量系统在不同 K 值（返回结果条数）下把正确文档呈现出来的能力。

### 多模态检索指标

多模态 pipeline 在 K=5 时达到 90% 的召回率，即大多数相关文档都出现在前五条结果中，K=10 时升至 96%。MRR 为 0.92，说明第一个相关结果通常就出现在第 1 位。K=10 时召回率仍低于 1.0 的那两条查询，涉及的相关信息分散在一个 PDF 和一张独立图像中，其中两个相关来源之一落在了前 10 名之外。

下图为多模态检索在 K=3、5、10 时的指标。MRR 衡量第一个相关结果出现得有多靠前。Recall@K 衡量前 K 条结果中找到的相关文档占比。NDCG@K 衡量排序质量，相关文档在列表中越靠前得分越高。

### 生成质量：纯文本 vs. 多模态

*检索指标*衡量系统是否找到了正确的文档。*生成指标*衡量下游语言模型能否根据检索到的上下文给出正确答案。我们把两条 pipeline 各自的检索前五条结果传给 Amazon Nova 2 Lite 生成答案，再用 Anthropic Claude Sonnet 4.5 作为 LLM 评判者，按 1–5 分为每个答案对照标准答案打分。

| Pipeline | 平均评判分数 | 归一化（0–1） |
| --- | --- | --- |
| 多模态（MME） | **4.88 / 5** | **0.977** |
| 纯文本（OCR） | 2.00 / 5 | 0.400 |

*表 2：由 LLM-as-Judge 打分的生成质量。多模态 pipeline 直接检索图像并传给生成器，而纯文本 pipeline 传的是 OCR 提取的文本。*

多模态 pipeline 在 88% 的查询上（26 条中的 23 条）得分更高，平均 4.88 分（满分 5 分）。纯文本 pipeline 平均 2.00 分，其中 26 条查询里有 17 条得 1 分（完全错误）。热分析等值线图、疲劳曲线、工艺流程图和 CAD 标注引线这类视觉内容提升最为明显。在两条 pipeline 都得分较高（4 或 5）的少数查询里，答案恰好以格式清晰的文本出现，OCR 能可靠捕获，例如表格布局中的材料名称或数值。

下图展示了两条 pipeline 的 LLM 评判分数（1–5）分布。多模态 pipeline 集中在 5 分，而纯文本 pipeline 在需要理解视觉内容的查询上集中在 1 分。

[![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/06/ML-20830-image-4.png)](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/06/ML-20830-image-4.png)

这些结果表明检索质量直接影响答案质量。当系统检索到了正确的文档，却只把 OCR 文本传给生成器时，它丢掉了答案所依赖的视觉信息。多模态 pipeline 通过把原始图像传给多模态生成器，避开了这种有损转换。

### 实现复杂度与成本

除准确性之外，多模态 pipeline 也更易构建、运行成本更低。纯文本 pipeline 每份文档需要两次模型调用（一次 OCR 文本提取、一次文本嵌入），还要做 prompt 工程来应对各种文档版式。多模态 pipeline 每份文档只需一次嵌入调用，没有中间的提取步骤，使实现复杂度和单文档写入成本都降低约一半。

## 清理

为避免持续产生费用，请在完成评估后删除 S3 Vectors 的索引和 bucket。[GitHub 上的配套 notebook](https://github.com/aws-samples/amazon-nova-samples/tree/main/multimodal-embeddings/repeatable-patterns/manufacturing-intelligence-nova-mme) 中包含这些清理命令（出于安全考虑已注释掉）。下面的代码片段展示如何删除索引和 vector bucket：

```
# Delete indexes
s3vectors.delete_index(vectorBucketName=S3_VECTOR_BUCKET, indexName=MME_INDEX)
s3vectors.delete_index(vectorBucketName=S3_VECTOR_BUCKET, indexName=TEXT_ONLY_INDEX)

# Delete vector bucket
s3vectors.delete_vector_bucket(vectorBucketName=S3_VECTOR_BUCKET)
```

Amazon Bedrock 的嵌入推理按请求计费，没有需要管理的常驻基础设施。

## 结论

对于视觉内容占比高的文档集合，多模态嵌入弥合了纯文本系统无法解决的检索缺口。在本文的航空航天制造数据集上，多模态 pipeline 在 K=5 时达到 90% 的召回率（K=10 时为 96%），生成质量接近完美（4.88/5）；而纯文本 pipeline 只得 2.00/5，因为 OCR 无法可靠地从工程图、热力图和流程图中捕获信息。

借助 Amazon Bedrock 上的 Amazon Nova Multimodal Embeddings，你无需管理嵌入模型基础设施就能构建这一能力。Amazon S3 Vectors 提供的向量存储与查询层不需要集群管理或容量规划。
