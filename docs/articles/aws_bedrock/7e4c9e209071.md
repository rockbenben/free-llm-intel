# Cornerstone OnDemand 如何用 Amazon Bedrock 把数据库诊断时间削减 78%

[Cornerstone OnDemand, Inc.](https://www.cornerstoneondemand.com/)（Cornerstone）是劳动力准备解决方案领域的全球领导者，服务 186 个国家的 1.4 亿用户。公司构建了一套多智能体 AI 系统，把数据库运维从被动救火变成主动、自我编排的工作流。这套系统名为 Orion AI，用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 和 [Strands Agents](https://strandsagents.com/)（AWS 的开源智能体编排框架）来协调各个专业智能体。

在 Orion AI 之前，Cornerstone 的企业 DataOps 团队处理一次数据库事故要投入最多 45 分钟，手工查询系统视图、交叉比对日志，然后才能在团队之间交接。有了 Orion AI，数据库诊断从 45 分钟降到 10 分钟，降幅 78%。一个三人的团队在六个月内交付了这套系统。

本文会梳理 Cornerstone 遇到的运维问题、他们如何设计 Orion AI、实测到的成果，以及其他团队可以复用的设计决策。

## 运维挑战

在 Orion AI 之前，Cornerstone 的企业 DataOps 团队一直处于被动响应状态，有四个反复出现的痛点：

- 数据库性能排查每次约需 45 分钟，散落在多个工具和系统视图之间。
- 数据库生命周期流程需要 10 步以上的手工操作，从建立连接一直到通报状态更新。
- 站点可靠性工程（site reliability engineering，SRE）团队与数据团队之间的汇报有 15 分钟延迟。
- 重复、交叉的告警制造噪声，把真正重要的信号埋了起来。

这些加在一起，意味着工程师的时间花在手工协调上，而不是解决问题上。

## 解决方案：Orion AI

Orion AI 是一套多智能体系统，一个协调智能体（元编排器）把工作分派给按中心辐射式（hub-and-spoke）拓扑组织的专业子智能体。工程师通过一个 Web 应用与它交互，在原本协调运维工作的同一个地方提问、批准动作。这些智能体覆盖基础设施监控、数据库诊断、数据库生命周期操作、客户分析，以及知识驱动的支持。

构建过程遵循两条准则：在[责任共担模型](https://aws.amazon.com/compliance/shared-responsibility-model/)之下用 AWS 的控制项保障数据隐私；与现有运维工具深度集成。Amazon Bedrock 提供托管的基础模型接入，Strands Agents 提供编排层。

## 成果

Orion AI 在诊断速度和准确性上都带来了可度量的改善，也把团队从手工协调中解放出来。通过自动化手工瓶颈、精简跨团队工作流，Cornerstone 取得了以下成果。

| **指标** | **之前** | **之后** | **改善** |
| --- | --- | --- | --- |
| 数据库诊断时间 | 45 分钟 | 10 分钟 | 快 78% |
| 手工生命周期步骤 | 10 步以上 | 1 次交互 | 减少 70% |
| `SRE-to-data-team` 汇报延迟 | 15 分钟 | 即时 | 实时 |
| 重复告警 | 基线告警量高 | 已过滤 | 减少 65%（中位数） |

### 更快的性能排查

压缩数据库诊断时间是 Orion AI 迄今最大的一项效率提升。原先，工程师要手工连上出问题的 SQL Server 实例，查询系统视图找阻塞链和等待类型，再交叉比对日志定位长时间运行的查询，然后把这些证据关联起来形成根因假设。平均每次事故约 45 分钟。

在 Orion AI 里，三个专业智能体分担排查，各自负责一个明确的阶段。除了诊断，Orion AI 还会把问题一路推进到修复：识别根因、给出修复建议，并创建一张内容填好的 Jira 工单，指派给对应的值班工程师。原本四步的手工交接收敛为一次交互。

### 自动化的数据库生命周期管理

过去需要 10 步以上手工操作的任务，从建立数据库连接、跨系统运行查询到通报状态更新，现在一次自然语言交互就能完成。Orion AI 会找出合适的工具和数据源，跨系统执行查询，校验结果，返回一份统一的答复。从工程师的视角看，工作只剩下向 Orion AI 提问，以及验证它反馈回来的结论。

### 实时监控与更少的告警疲劳

Orion AI 消除了 15 分钟的 `SRE-to-data-team` 汇报延迟，用持续的跨系统可见性取代定时的手工检查。

通过去重、阈值过滤和跨信号关联，Orion AI 把重复告警减少了 65%（中位数）。原先每产生 10 条告警，如今只有 3–4 条会到达工程师。告警直接路由到负责的团队，中间不再有一层告警转发。

## 关键设计原则

三个决策塑造了 Orion AI，你可以把它们用到自己的多智能体项目上：

- **按领域拆分智能体，而不是按任务复杂度拆分**：每个智能体只针对一个运维领域，携带范围很窄的工具集成。这让模型的上下文保持聚焦，也提高了工具选择的准确率，而不是让一个通用智能体去做所有事。
- **默认关键词路由，语义检索兜底**：可预期的请求用关键词匹配，图的是快；有歧义的请求退回到语义检索，图的是准。这样延迟保持很低，难一些的问题也不牺牲正确性。
- **对话记忆限定在会话范围内，实时指标一律绕过它**：持久化记忆支撑多轮对话，但运维问题读到的永远是系统当前状态。实时指标绕过记忆，可以避免过期数据污染实时诊断。

## 架构详解

前面的设计原则在架构里都有具体的落点。本节余下的部分逐一走查 Orion AI 的核心组件。

### 用 Strands Agents 搭出中心辐射式结构

Orion AI 用少量 Strands Agents 原语来表达它的拓扑。`Agent` 类是专业智能体和元编排器共用的积木。每个智能体的工具就是带 `@tool` 装饰器的普通 Python 函数，工具规格由函数的类型标注和 docstring 推导出来，因此不需要另外维护一份 schema。`BedrockModel` 封装每个智能体所运行的 Amazon Bedrock 模型，`MCPClient` 把智能体连到外部工具服务器。

拓扑结构：

- 中心是一个 Strands Agent，充当元编排器（TaskExecutor）。它不持有任何领域工具，只有路由工具（`find_relevant_agents`、`call_agent`）和控制流工具（`emit_plan_step`、`emit_confirmation_gate`），因此能够一步步推理如何处理一个请求。
- 辐条是各自独立的 `Agent` 实例，通过基于装饰器的注册表懒加载。每个实例带着自己的模型、领域工具和本地化的 system prompt。

运行时，中心通过注册好的 `call_agent` 工具按名字调用某个专业智能体。每个专业智能体运行自己的工具调用循环，把综合后的文本返回给中心，由中心组装出最终响应。

### 混合路由

Orion AI 采用关键词优先路由，语义检索兜底。约 80% 的查询走内存中的关键词快速通道，在 1 毫秒内完成匹配。当关键词不足以判定意图时，系统退回到由 [Amazon Titan Text Embeddings V2](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html) 驱动的语义检索，按含义路由。各 AWS 区域的模型可用性见 [Amazon Bedrock 中按 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

不适合直接调用工具时，会启用一条兜底链：[Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 是全托管的检索增强生成（RAG）能力，由它取回运维文档，让回答建立在已获认可的流程之上，而不是脱离上下文生成。

### 领域专用智能体及其边界

Orion AI 使用 13 个领域专用智能体。其中三个 SQL Server 智能体能说明按领域拆分如何对应到一次真实排查的各个阶段：

- **数据库诊断智能体**呈现阻塞链、等待类型和长时间运行的查询，再把技术性发现翻译成业务影响，并给出修复建议。它回答的是「正在发生什么，这意味着什么」。
- **会话阻塞分析智能体**用推理模型执行多步排查，把阻塞链追溯到一个根源阻塞方。它回答的是「为什么会发生，根因是什么」，并给出按优先级排序的建议，从立即终止会话到更长周期的架构修复。
- **实时 SQL 诊断智能体**通过 Cornerstone 的 DATAOPS API 直接查询 SQL Server 实例，获取实时阻塞数据并做高 CPU 会话分析。它回答的是「此刻的真实情况是什么」。

其余智能体遵循同样的窄职责原则：基础设施监控、运维分析、数据库生命周期管理、客户分析、从 runbook 检索知识、通知路由、复合查询拆解、Availability Group 监听器解析，以及模型连接预热。

### 工具集成与服务连接

Orion AI 用两种模式访问数据源：

- **[Model Context Protocol](https://modelcontextprotocol.io/)（MCP）**，用于多个智能体共享的工具（例如实时 SQL 诊断）。一个 Strands `@tool` 函数通过可流式传输的 HTTP 调用 `MCPClient`，连到 Portal-Tools MCP server，再由它访问 SQL Server 和 DATAOPS API。Jira 集成走同样的路子，通过外部 Atlassian MCP 工具实现。
- **直接 SDK 或 REST API 调用**，用于不需要共享 MCP 接口的数据源。包括指标与仪表盘、值班排班表，以及通过 [AWS SDK for Python (Boto3)](https://aws.amazon.com/sdk-for-python/) 访问 Amazon Bedrock Knowledge Bases。

这样拆分的结果是，每个智能体都用最贴合其数据源的轻量机制，而 MCP server 把多个智能体共享的工具集中托管。这些连接走 TLS 运行，MCP token、REST API 授权这类凭证按请求提供，不写进智能体代码。

### 对话记忆

[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 是一个用任意框架或模型大规模构建、连接和优化智能体的平台，由它提供跨会话的记忆层。Orion AI 通过一个中央记忆管理器协调上下文，该管理器并行读取三层记忆，每层各有自己的超时时间和 token 配额。

Orion AI 分三层协调上下文。短期记忆把同一会话的上下文存放在 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 里，默认静态加密，并配一份滚动更新的对话摘要，由 [Amazon Nova 2 Lite](https://aws.amazon.com/ai/generative-ai/nova/) 异步生成。长期记忆通过 AgentCore memory 提供跨会话回忆，它是 Amazon Bedrock AgentCore 的一项能力，按用户 ID 划分命名空间。任务完成时，Orion AI 调用 `create_event` 触发自动的抽取、摘要和归并。第三层是智能体之间的记忆，一份临时的内存便签，在同一个任务里跨子智能体的各个步骤传递发现。

记忆管理器跨层检索的硬超时为 500 毫秒，token 预算为 4,000，背后由最近最少使用缓存支撑。请求涉及系统当前状态时，智能体完全绕过记忆，直接读取实时数据，以免过期上下文污染实时诊断。

### 负责任的 AI 与护栏

DataOps 的安全性取决于领域特定的规则，比如哪些数据库操作具有破坏性，因此团队构建了自研的护栏逻辑，而不是依赖通用的内容过滤。Orion AI 的控制分四层：

- **Prompt 层面的安全约束**，注入每个智能体的 system prompt，阻止危险建议（例如终止关键数据库进程），强制使用非破坏性的做法。
- **人在回路的确认闸门**，破坏性操作会被暂停，等待用户在 5 分钟窗口内确认，超时默认拒绝。
- **用于输入校验的自研护栏模块**（长度限制、prompt 注入与 SQL 注入拦截），以及输出脱敏（遮蔽机密信息和个人身份信息）、限流、基于角色的访问控制、按请求的成本追踪。
- **路由层面的保护**，禁止从记忆里回答运维查询，涉及当前状态的问题必须实时执行工具。

### 可观测性

Orion AI 用标准的 AWS 可观测服务做监控和调试。[Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 为路由置信度、延迟和智能体调用活动提供指标与结构化日志。[AWS X-Ray](https://aws.amazon.com/xray/) 追踪跨智能体执行的分布式调用，让请求链路端到端可见。

## 经验教训

让 Orion AI 得以落地的这些设计决策，你都可以复用。按领域拆分智能体，让每个智能体只带范围很窄的工具集成，又不会把单个模型的上下文撑爆。默认关键词路由、语义检索兜底，使延迟保持很低，遇到有歧义的请求也不牺牲准确性。对话记忆限定在会话范围内、实时指标绕过记忆，让实时诊断值得信任。

团队在基础设施上也做了务实的取舍。他们把计算部署在 Amazon ECS 上，因为项目启动时 [Amazon Bedrock AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)（Amazon Bedrock AgentCore 的一项能力）还不可用，如今他们正在评估把它作为未来的迁移选项。如果你今天开始构建，同样的权衡要放到你自己的技术栈上做一次：先用当下稳定可用的东西，等托管能力成熟后再回头评估。

## 总结

Orion AI 把数据库诊断从 45 分钟降到 10 分钟，省掉 70% 的手工生命周期步骤，告警噪声降低 65%。一个三人团队在 Amazon Bedrock 上用六个月交付了它。这些结果背后的模式，其他运维团队同样可以采纳：按领域划分的智能体、混合路由，以及限定在会话范围并绕过实时指标的记忆。
