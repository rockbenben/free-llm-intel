# Cornerstone OnDemand 如何利用 Amazon Bedrock 将数据库诊断减少 78%

[Cornerstone OnDemand, Inc.](https://www.cornerstoneondemand.com/) (Cornerstone) 是劳动力准备解决方案的全球领导者，为 186 个国家/地区的 1.4 亿用户提供服务。该公司构建了一个多代理人工智能系统，将数据库操作从被动的消防转变为主动、自我编排的工作流程。该系统名为 Orion AI，使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 和 [Strands Agents](https://strandsagents.com/)（AWS 的开源代理编排框架）来协调专业代理。

在 Orion AI 之前，Cornerstone 的企业 DataOps 团队在每个数据库事件上花费长达 45 分钟的时间手动查询系统视图和交叉引用日志，然后再跨团队移交。借助 Orion AI，数据库诊断时间从 45 分钟缩短至 10 分钟，缩短了 78%。三人团队在六个月内交付了该系统。

在这篇文章中，我们将介绍 Cornerstone 面临的运营问题、他们如何设计 Orion AI、他们测量的结果以及其他团队可以重用的设计决策。

## 运营挑战

在 Orion AI 出现之前，Cornerstone 的企业数据运营团队采取被动操作，存在四个反复出现的痛点：

- 每个事件的数据库性能调查大约需要 45 分钟，分布在多个工具和系统视图中。
- 数据库生命周期工作流程需要 10 个或更多手动步骤，从建立连接到传达状态更新。
- 站点可靠性工程 (SRE) 团队和数据团队之间的报告存在 15 分钟的延迟。
- 冗余和重叠的警报会产生噪音，掩盖重要的信号。

总之，这些意味着工程师将时间花在手动协调上，而不是解决问题上。

## 解决方案：Orion AI

Orion AI 是一个多代理系统，其中协调代理（元协调器）将工作委托给以中心辐射型拓扑排列的专门子代理。工程师通过网络应用程序与其进行交互，在他们已经协调运营工作的同一位置提出问题并批准行动。这些代理涵盖基础设施监控、数据库诊断、数据库生命周期操作、客户分析和知识驱动的支持。

指导构建的两个原则是：在[共享责任模型](https://aws.amazon.com/compliance/shared-responsibility-model/)下使用 AWS 控制来实现数据隐私，以及与现有操作工具的深度集成。 Amazon Bedrock 提供对基础模型的托管访问，Strands Agents 提供编排层。

＃＃ 结果

Orion AI 在诊断速度和准确性方面都取得了显着的进步，并将团队从手动协调中解放出来。通过自动化手动瓶颈和简化跨团队工作流程，Cornerstone 取得了以下成果。

| **公制** | **之前** | **之后** | **改进** |
| ---| ---| ---| ---|
|数据库诊断时间| 45 分钟 | 10 分钟 |速度提高 78% |
|手动生命周期步骤 | 10 步以上 | 1 次互动 |减少 70% |
| “SRE 到数据团队”报告滞后 | 15 分钟 |瞬时|实时|
|冗余警报|高基线量 |过滤|减少 65%（中位数）|

### 更快的性能故障排除

减少数据库诊断时间是 Orion AI 迄今为止最大的单一效率提升。此前，工程师手动连接到受影响的 SQL Server 实例，查询系统视图以了解阻塞链和等待类型，交叉引用日志以隔离长时间运行的查询，并关联证据以形成根本原因假设。每个事件平均大约需要 45 分钟。

在 Orion AI 中，三名专业特工共同参与调查，每名特工都有一个不同的阶段。除了诊断之外，Orion AI 还通过修复来解决问题：确定根本原因、建议修复方案以及创建分配给正确的待命工程师的填充 Jira 票证。四步手动切换分解为一次交互。

### 自动化数据库生命周期管理

以前需要 10 多个手动步骤的任务（从建立数据库连接到运行跨系统查询再到通信状态更新）现在作为单一自然语言交互运行。 Orion AI 识别正确的工具和数据源，跨系统运行查询，验证结果并返回统一的响应。从工程师的角度来看，工作被简化为提示 Orion AI 并验证其报告的结果。

### 实时监控并减少警报疲劳

Orion AI 消除了“SRE 到数据团队”15 分钟的报告延迟，用持续的跨系统可见性取代了定期的手动检查。

Orion AI 通过重复数据删除、阈值过滤和跨信号关联，将冗余警报平均减少了 65%。对于之前生成的每 10 个警报，现在只有 3-4 个到达工程师手中。警报直接发送至负责团队，无需中间警报层。

## 关键设计原则

三个决定塑造了 Orion AI，您可以将它们应用到您自己的多代理项目中：

- **按领域而不是按任务复杂性划分代理**：每个代理都针对一个操作域携带一组狭窄的工具集成。这可以保持模型的上下文集中，并提高工具选择的准确性，而不是要求一个通用代理完成所有事情。
- **默认关键字路由，回退到语义搜索**：可预测的请求通过关键字匹配以提高速度。不明确的请求会退回到语义搜索以确保准确性。这可以在不牺牲较难查询的正确性的情况下保持较低的延迟。
- **将会话内存范围扩展到会话并绕过它以获取实时指标**：持久内存支持多轮对话，但操作问题始终读取当前系统状态。绕过实时指标的内存有助于防止陈旧数据污染实时诊断。

## 架构深入探讨

上述设计原则具体体现在架构中。本节的其余部分将介绍 Orion AI 的核心组件。

### 使用 Strands Agent 构建中心辐射模式

Orion AI 使用一些 Strands Agent 原语来表达其拓扑。 “Agent”类是专业代理和元编排器的构建块。每个代理的工具都是用“@tool”装饰器标记的普通 Python 函数。这从函数的类型提示和文档字符串中派生出工具的规范，这意味着不需要维护单独的模式。 “BedrockModel”包装每个代理运行的 Amazon Bedrock 模型，“MCPClient”将代理连接到外部工具服务器。

拓扑结构：

- 中心是一个充当元协调器（任务执行器）的 Strands 代理。它没有域工具——只有路由工具（“find_relevant_agents”、“call_agent”）和控制流工具（“emit_plan_step”、“emit_confirmation_gate”），因此它可以逐步推理请求。
- 辐条是独立的“代理”实例，通过基于装饰器的注册表延迟加载。每个都有自己的模型、领域工具和本地化系统提示。

在运行时，中心通过注册的“call_agent”工具按名称调用专家。每个专家都会运行自己的工具调用循环，并将合成文本返回到集线器，集线器组装最终响应。

### 混合路由

Orion AI 使用关键字优先路由和语义搜索回退。大约 80% 的查询可在一毫秒内通过内存中关键字快速路径进行解析。当关键字不足以确定意图时，系统会退回到由 [Amazon Titan Text Embeddings V2](https://docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html) 支持的语义搜索来按含义进行路由。有关 AWS 区域的模型可用性，请参阅 [Amazon Bedrock 中 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

当直接工具调用不合适时，后备链将激活：[Amazon Bedrock 知识库](https://aws.amazon.com/bedrock/knowledge-bases/)，这是完全托管的检索增强生成 (RAG) 功能，可检索操作文档，以便响应基于批准的程序，而不是在没有上下文的情况下生成。

### 特定领域的代理及其边界

Orion AI 使用 13 个特定领域代理。三个 SQL Server 代理说明了域分割如何映射到实际调查的阶段：

- **数据库诊断代理**显示阻塞链、等待类型和长时间运行的查询，然后将技术发现转化为业务影响和补救建议。它回答：“正在发生什么以及这意味着什么。”
- **会话阻塞分析代理** 使用推理模型运行多步骤调查，将阻塞链映射到根阻塞者。它回答“为什么会发生这种情况以及根本原因是什么”，提供从立即会话终止到长期架构修复的优先建议。
- **实时 SQL 诊断代理** 通过 Cornerstone 的 DATAOPS API 直接查询 SQL Server 实例，以进行实时阻塞数据和高 CPU 会话分析。它回答说：“现在什么是真实的。”

其余代理遵循相同的狭义所有权原则：基础设施监控、操作分析、数据库生命周期管理、客户分析、从操作手册检索知识、通知路由、复合查询分解、可用性组侦听器解析和模型连接预热。

### 工具集成和服务连接

Orion AI 通过两种模式到达数据源：

- **[模型上下文协议](https://modelcontextprotocol.io/) (MCP)** 用于多个代理共享的工具（例如，实时 SQL 诊断）。 Strands `@tool` 函数通过可流传输的 HTTP 向 Portal-Tools MCP 服务器调用 `MCPClient`，从而到达 SQL Server 和 DATAOPS API。 Jira 集成通过外部 Atlassian MCP 工具遵循相同的方法。
- **直接 SDK 或 REST API 调用**，适用于不需要共享 MCP 接口的源。这包括指标和仪表板、待命计划以及通过 [AWS SDK for Python (Boto3)](https://aws.amazon.com/sdk-for-python/) 提供的 Amazon Bedrock 知识库。

这种拆分意味着每个代理都使用适合其源的最轻量机制，而 MCP 服务器集中了多个代理共享的工具。这些连接通过 TLS 运行，并且 MCP 令牌和 REST API 授权等凭据是根据请求提供的，而不是嵌入到代理代码中。

### 对话记忆

[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 是一个使用任何框架或模型大规模构建、连接和优化代理的平台，提供跨会话内存层。 Orion AI 通过中央内存管理器协调上下文，该管理器并行读取三层，每层都有自己的超时和令牌分配。

Orion AI 跨三个层协调上下文。短期记忆在 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 中保留相同会话上下文，默认情况下静态加密，并与 [Amazon Nova 2 Lite](https://aws.amazon.com/ai/generative-ai/nova/) 异步生成的滚动对话摘要配对。长期内存通过 AgentCore 内存提供跨会话调用，这是 Amazon Bedrock AgentCore 的一项功能，按用户 ID 命名。任务完成后，Orion AI 调用“create_event”来触发自动提取、汇总和合并。第三层，代理间内存，是一个临时的内存暂存器，它在单个任务中跨子代理步骤携带发现结果。

内存管理器在 500 毫秒硬超时内针对 4,000 个令牌预算跨层进行检索，并由最近最少使用的缓存提供支持。当请求涉及当前系统状态时，代理完全绕过内存并读取实时数据，因此陈旧的上下文不会污染实时诊断。

### 负责任的人工智能和护栏

由于 DataOps 安全性取决于特定于域的规则，例如哪些数据库操作具有破坏性，因此团队构建了自定义护栏逻辑，而不是依赖于通用内容过滤器。 Orion AI 跨四个层应用控制：

- **提示级安全约束**注入每个代理的系统提示中，阻止危险建议（例如，终止关键数据库进程）并强制执行非破坏性方法。
- **人机交互确认门**，暂停破坏性操作，直到用户在五分钟窗口内确认，默认超时拒绝。
- **用于输入验证的自定义护栏模块**（长度限制、提示和 SQL 注入阻止）、输出清理（编辑机密和个人身份信息）、速率限制、基于角色的访问控制和每个请求成本跟踪。
- **路由级保护**，阻止从内存中回答操作查询，强制执行当前状态问题的实时工具。

### 可观察性

Orion AI 使用标准 AWS 可观测性服务进行监控和调试。 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 提供路由置信度、延迟和代理调用活动的指标和结构化日志记录。 [AWS X-Ray](https://aws.amazon.com/xray/) 跟踪跨代理执行的分布式调用，以实现端到端请求路径可见性。

## 经验教训

使 Orion AI 成为可能的设计决策是您可以重复使用的。按领域拆分代理可以让每个代理进行狭窄的工具集成，而不会导致单个模型的上下文膨胀。默认情况下使用关键字路由和语义搜索作为后备，可以保持较低的延迟，而不会牺牲模糊请求的准确性。将会话内存范围限定为会话，同时绕过实时指标以保持实时诊断的可信度。

该团队还做出了务实的基础设施选择。他们在 Amazon ECS 上部署计算，因为 [Amazon Bedrock AgentCore 运行时](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)（Amazon Bedrock AgentCore 的一项功能）在项目开始时不可用，他们现在正在将其评估为未来的迁移选项。如果您今天正在构建，请为您自己的堆栈权衡相同的权衡：从现在稳定且可用的内容开始，并在托管功能成熟时重新审视。

## 结论

Orion AI 将数据库诊断时间从 45 分钟减少到 10 分钟，避免了 70% 的手动生命周期步骤，并将警报噪音降低了 65%。一个三人团队在六个月内在 Amazon Bedrock 上交付了它。这些结果背后的模式是其他运营团队可以采用的模式：域范围代理、混合路由和具有实时指标旁路的会话范围内存。
