## [人工智能](https://aws.amazon.com/blogs/machine-learning/)

# 用 Anchor Browser 与 AgentCore payments 构建能完成交易的智能体

AI 智能体越来越需要访问按请求计价的 web 资源。例如，付费数据集按查询次数收费，研究类 API 按调用计量，设有付费墙的出版商把内容挡在支付之后。当 AI 智能体遇到这类资源时，服务器返回 HTTP 402 Payment Required。智能体没有内置的支付机制，会话上没有绑定预算，也没有任何以编程方式满足这个请求的办法。任务因此停滞，需要人工介入。

[支持智能体支付的 Anchor Browser](https://aws.amazon.com/marketplace/pp/prodview-ujbrqwp274l6g)代表智能体处理机器对机器的支付工作流。它与 [AWS Generative AI Innovation Center 的 Partner Agent Factory](https://aws.amazon.com/blogs/awsmarketplace/aws-genaiic-partner-agent-factory-new-ai-agents-now-in-aws-marketplace/)合作开发，现已上架 [AWS Marketplace](https://aws.amazon.com/marketplace/)。本文介绍 [Anchor Browser](https://anchorbrowser.io/)如何与 [Amazon Bedrock AgentCore payments](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments.html)集成，让 AI 智能体能够自主为受 x402 保护的页面和 API 付费。x402 协议是一项基于 HTTP 的机器对机器支付开放标准。服务器以 402 Payment Required 响应，同时给出金额、可接受的支付方式，以及智能体用来完成交易所需的支付地址。

Anchor Browser 是为 AI 智能体专门打造的云端浏览器自动化方案。每个智能体会话都运行在一个托管浏览器环境内，该环境维护认证状态、处理导航、捕获网络请求，并提供页面交互的实时视图。

Amazon Bedrock AgentCore 提供规模化构建、连接和优化智能体所需的能力。Amazon Bedrock AgentCore payments 是 AgentCore 中的一项完全托管能力，AI 智能体可以用它自主发现、访问 API、Model Context Protocol（MCP）服务器和 web 内容并为之付费。AgentCore payments 管理钱包连接，在基础设施层强制执行可配置的支出上限，并通过 x402 协议处理支付。它还通过 Amazon CloudWatch 提供对支付尝试、批准、拒绝和结算的可观测性。

当运行在 Anchor Browser 中的智能体遇到 402 响应时，AgentCore payments 会在配置好的预算内授权并完成交易。工作流不中断地继续下去。

## 挑战

自主智能体遇到受 x402 保护的资源时，工作流会停滞。智能体发出一个请求，比如获取一份付费研究报告，或调用一个付费数据增强 API，服务器返回 HTTP 402 Payment Required。没有可支付的机制，本来应当自主运行的任务就转而需要人工介入。

如今开发者必须自己搭建整套支付栈。这部分工作量横跨四类复杂性：

**支付协议处理**

- 从 HTTP 响应中检出并解析 402 支付挑战，把需要支付的响应与其他 4xx 错误区分开。
- 按商户期望的确切格式，构造出携带密码学证明的正确支付头。
- 支持多种[支付方案](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments-process-payment.html)（exact、upto 以及各种协议变体），而不把厂商专属逻辑硬编码进智能体。
- 在不同 x402 商户实现之间保持兼容，它们的挑战格式、支持的稳定币、结算时点都可能不一样。

**安全与密钥管理**

- 保存用于给支付签名的私钥，就得在一个会接触不可信输入的环境里做到安全的密钥存储。
- 管理钱包的生命周期操作，包括密钥轮换、凭证刷新和提供商故障切换。

**运行韧性**

- 带着支付头重新提交原始请求，同时保住会话状态、cookie 和请求上下文。
- 提供幂等性，这对钱包操作必不可少。
- 强制执行按会话、按交易的支出上限，并在并发的智能体执行之间做实时预算跟踪。

**可观测性与合规**

- 把每一次支付尝试、批准、拒绝和结算都记进审计日志，用于合规和对账。

没有托管的支付服务，智能体就得把整套支付栈内化。每一次访问受 x402 保护的资源，只要返回 402，智能体都要在内部编排完整的支付流程，包括：

- 签署证明。
- 附上正确的头。
- 重试请求。
- 结算交易。
- 记录结果。

这些步骤中的每一步都需要开发者自己编写、加固并维护的自定义代码。图 1 展示了这种架构。智能体内含八个紧耦合的组件（钱包、私钥、预算控制、签署证明、附加头、重试逻辑、结算支付和日志）。智能体连接到一个 x402 API，回流的是 402 挑战，发出的是重试请求。

安全方面的顾虑还不止于工程工作量本身。

**支出失控。** 如果基础设施层没有强制的硬性支出上限，一个 bug、一个重试循环、一次提示注入或一次意外访问都可能触发计划外的支付。一个反复重试某个付费端点的智能体会不断授权支付，直到有人工介入为止。

**密钥暴露。** 私钥存放在智能体运行时内部时，它就和不可信网页、第三方工具、外部依赖共享同一个执行环境。这些途径都可能无意间泄露那些控制真实资金的凭证。

**签名链路暴露。** 如果运行时能够访问签名基础设施，攻击者就可能试图取得密钥，或把支付重定向到不受授权控制的地址。真正有效的缓解措施，是从一开始就不让密钥进入运行时。

基于浏览器的智能体还多出一条约束：支付必须发生在同一个浏览器会话内。否则会话录制和实时视图就不再与实际执行的内容相符。

## 方案

Anchor Browser 和 AgentCore payments 的做法是把整套支付栈搬进托管基础设施，从而消化这些复杂性。

与无状态的工具调用不同，Anchor Browser 提供的是一个真正的云端浏览器：身份持久、工作流可重复且确定，并且具备可靠地完成登录、导航和把任务做完所需的会话上下文。认证、导航、网络请求、录制和实时视图都发生在同一个浏览器会话内。需要支付时，交易也在那个会话内完成。录制会捕获从请求到 402、从支付到内容交付的完整过程。Anchor 智能体内置一个 x402 工具，在浏览器上下文中原生处理付费 API 调用。这个内置工具不需要改动现有的 Playwright、Puppeteer 或基于 Chrome DevTools Protocol 的工作流。

AgentCore payments 充当支付层。这项服务的中心是 Payment Manager，它是协调该 AWS 账户支付操作的顶层资源。创建 Payment Manager 需要指定一种 authorizer 类型和一个 IAM 角色，随后 AgentCore 会在 Amazon Bedrock AgentCore Identity 中配置一个对应的工作负载身份。

其余组件把 Payment Manager 连接到外部钱包基础设施：

- **PaymentConnector** 把 Payment Manager 与外部钱包提供商集成，可以是 Coinbase Developer Platform（Coinbase CDP）或 Stripe Privy。
- **PaymentCredentialProvider** 把钱包提供商的凭证安全地存放在 AgentCore Identity 中。
- **PaymentInstrument** 指明实际扣款的具体钱包地址。

Anchor Browser 通过 AgentCore payments、使用受支持的钱包提供商来设置钱包，而不把钱包机密或私钥放进智能体运行时。钱包操作由 AgentCore payments 通过配置好的提供商处理。在端点发现方面，AgentCore 通过 [Amazon Bedrock AgentCore Gateway 提供经过筛选的 Coinbase x402 Bazaar MCP 服务器](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments-connect-bazaar.html)，因此智能体可以用编程方式发现可用的按次付费 x402 端点。

AgentCore payments 重构了支付架构。敏感操作从智能体运行时移出，进入托管服务层。Anchor Agent 只保留两个与支付相关的组件：一个预算会话和 x402 工具。基础设施，包括认证、钱包机密、支付限额、可观测性和支付证明签名，都留在 AgentCore payments 层。图 2 展示了 Anchor Agent 连向 AgentCore payments 托管层，由该层负责与 Coinbase CDP 或 Stripe Privy 的钱包提供商集成。

### 支付流程如何运转

下面这些步骤描述端到端发生的事情，从浏览器会话遇到受 x402 保护的资源那一刻，到智能体收到响应、继续任务那一刻。

- **Anchor Browser 为浏览器会话创建一个专属的 AgentCore PaymentSession。** 会话在开启 x402 的情况下启动时，Anchor Browser 会通过 AgentCore payments 建立一个 PaymentSession，把浏览器会话与配置好的支付工具和预算关联起来。
- **浏览器收到 HTTP 402 Payment Required 响应。** 智能体导航到某个 URL，或发出 fetch 或 XMLHttpRequest（XHR）请求。商户返回一个 402 挑战，指明金额、可接受的支付方式和支付地址。
- **浏览器选出一种兼容的支付方式。** Anchor Browser 读取 402 挑战的载荷，把所要求的支付方式与 PaymentSession 关联的支付工具做匹配。
- **AgentCore 校验会话预算并生成密码学支付证明。** AgentCore payments 先验证支付金额落在会话支出上限之内。随后该服务用配置好的钱包提供商（Coinbase CDP 或 Stripe Privy）为交易签名，并返回密码学证明。任何密钥材料都不会进入浏览器或智能体运行时。
- **浏览器带着支付头重试原始请求。** 浏览器把签好的证明作为 x402 v2 的 `PAYMENT-SIGNATURE` 或 x402 v1 的 `X-PAYMENT` 附加上去，然后对原始请求恰好重试一次。
- **商户验证并结算支付，然后返回受保护的资源。** 商户校验密码学证明，在链上结算交易，并提供内容。智能体继续任务。

在整个流程中，钱包凭证始终留在 AgentCore 和配置好的钱包提供商那里。

## 前提条件

开始之前，先确认你有一个有效的 Anchor Browser API key（`ANCHOR_API_KEY`）。要创建它，参见 Anchor Browser 的[快速上手](https://docs.anchorbrowser.io/quickstart/use-via-api)指南。

## 配置自动 x402 支付

为 Anchor Browser 配置智能体支付只需要一个会话属性：把 `session.x402` 设为 `true`。该属性默认为 `false`。开启后，浏览器会话就能自动访问受 x402 保护的网站，支付由 AgentCore payments 签名，并在同一个浏览器会话内重试。开启 `session.x402` 等于授权浏览器用配置好的支付工具进行真实支付。

下面的示例展示如何用 cURL 和 JavaScript 为 Anchor Browser 创建一个可支付的会话：

**cURL**

```
curl --request POST
--url https://api.anchorbrowser.io/v1/sessions
--header "anchor-api-key: $ANCHOR_API_KEY"
--header "content-type: application/json"
--data '{"session":{"x402":true}}'
```

**JavaScript**

```
const response = await fetch('https://api.anchorbrowser.io/v1/sessions', {
  method: 'POST',
  headers: {
    'anchor-api-key': process.env.ANCHOR_API_KEY,
    'content-type': 'application/json',
  },
  body: JSON.stringify({ session: { x402: true } }),
});
const { data: session } = await response.json();
console.log(session.cdp_url);
```

通过 Chrome DevTools Protocol 连上之后，智能体照常导航即可。你的自动化代码里不需要放钱包密钥或支付头。对于文档导航、fetch 和 XHR 请求，浏览器会透明地处理 402 挑战、支付签名和重试。

## 支付会话的限制与行为

通过 AgentCore payments 集成，Anchor Browser 在会话层面强制下面这些护栏。每个具备支付能力的浏览器会话都在配置好的支出和时间约束内运行。具体限额参见 [Anchor Browser 技术文档](https://docs.anchorbrowser.io/advanced/automatic-x402-payments)。

如果商户响应格式不对、没有提供兼容的网络、预算已经耗尽，或者 AgentCore payments 拒绝了这笔支付，浏览器会把原始的 402 响应原样返回给页面。你的自动化代码随后可以把这个 402 当作标准 HTTP 错误来处理。

x402 会话属性只控制对第三方资源的支付。该属性不会取代 Anchor credits，也不用于支付浏览器会话本身的费用。

## Anchor Browser 的自动化代码

你为 Anchor Browser 写的自动化代码保持不变。下面的示例说明并不需要任何支付专用的代码：

```
const { chromium } = require('playwright');
// Connect to the x402-enabled session via CDP
const browser = await chromium.connectOverCDP(session.cdp_url);
const page = await browser.newPage();
// Navigate to an x402-protected resource exactly as with a free page
await page.goto('https://premium-research.example.com/market-report');
// The page loaded, the payment was handled automatically
// Extract content as normal
const content = await page.textContent('article');
```

没有钱包逻辑，没有支付头构造，也没有重试代码。智能体导航到那个 URL。如果服务器返回 402，Anchor Browser 会与 AgentCore payments 协同签署支付证明，带上合适的支付头重试请求，并把内容交付给页面。你的自动化代码收到的就是最终渲染好的页面，看不出发生过一次支付。

这一模式统一适用于付费墙新闻、授权金融数据、受限访问的 API 文档、按量计费的研究数据库，以及其他把内容挡在 402 挑战之后的资源。

## 用内置的 x402 工具调用 API

付费资源不限于网页。很多付费资源是 API，它们期望的是 POST、PUT 或其他 HTTP 方法。常见例子包括数据增强服务、高级推理端点和授权内容 API。针对这些用例，Anchor Browser 的智能体内置了一个 x402 工具，你可以像调用标准 HTTPS API 那样在浏览器上下文里调用它。

你的智能体通过 fetch 或 XHR 发起 API 调用。如果服务器返回 402 挑战，浏览器会通过 AgentCore payments 协调支付签名，并带上签好的支付头重试请求。你的代码收到的响应，就好像那个端点是免费的一样。这个工具不绑定特定厂商、模型或框架。支付是位于你现有工具之下的一种会话级能力，不需要对智能体代码做任何改动。

```
// Fetch call to a paid API endpoint within the x402-enabled session
const response = await page.evaluate(async () => {
  const res = await fetch('https://data-enrichment.example.com/api/v1/enrich', {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ company_domain: 'example.com' }),
  });
  return res.json();
});
// If the API returned 402, AgentCore handled payment automatically
// The response contains the enriched data
console.log(response);
```

你的自动化代码不会拿到钱包凭证。自动支付只在 `session.x402` 设为 `true` 时可用，并且始终受上一节所述的支出上限和有效期限制约束。

## 主要收益

这套集成把支付从应用代码移到了基础设施层：

**没有支付基础设施要自建。** 没有钱包 SDK 要集成，没有 402 响应解析器要写，没有重试循环要实现，没有头构造逻辑要维护，也没有自定义审计日志要搭建。整套支付栈由 AgentCore payments 管理。

**现有工具无需改动。** Playwright 脚本、Puppeteer 自动化、Chrome DevTools Protocol 命令，以及 Anchor Browser 里的智能体流程，都照旧运行。支付是挂在浏览器上的一种会话能力，而不是对智能体逻辑、prompt 或工具定义的修改。

**私钥不进入运行时。** 签名和结算都发生在 AgentCore payments 内部。该服务通过 AgentCore Identity 中的安全凭证存储与 Coinbase CDP 或 Stripe Privy 通信。智能体运行时接触不到任何能调动资金的密钥材料。

**预算在基础设施层强制执行。** 每个会话都在设定好的支出上限内运行，AgentCore 在授权支付之前先做校验。Amazon Bedrock AgentCore Observability 通过 Amazon CloudWatch 提供完整的支付审计轨迹。会话达到支出上限时，AgentCore payments 会拒绝这笔支付。

**付费任务能顺利完成。** 付费的 GET 页面能加载，付费的 API 调用能返回响应。智能体走完整条工作流，而不是停在一个 402 响应上等待人工介入。

**账单合并。** Anchor Browser 用 credits 结算第三方 x402 费用，和浏览器会话时长开在同一张账单上。没有需要单独管理的加密货币托管，没有需要盯的 USDC 余额，也没有需要财务团队去对账的链上结算。

## 结语

Anchor Browser 与 AgentCore payments 集成后，AI 智能体就能自主处理 x402 支付挑战，无论是付费墙网页还是付费 API 端点。钱包凭证不会进入智能体代码，也不需要自建支付基础设施。

随着越来越多的 web 资源转向按请求计价，缺少支付机制的智能体无法完成涉及付费资源的任务。这套集成补上了这个缺口：智能体端到端跑完付费工作流，在设定好的预算内运行，通过 AgentCore Observability 获得完整的可观测性，而运行时里没有密码学密钥材料。
