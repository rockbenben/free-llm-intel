# 使用 Amazon Bedrock LLM 与 RAG，靠生成式 AI 生成合成交易对手（CR）风险数据

数据是现代应用的命脉，驱动着从应用测试到 [机器学习](https://aws.amazon.com/ai/machine-learning/)（ML）模型训练与评估的一切。随着数据需求持续攀升，[生成式 AI](https://aws.amazon.com/ai/generative-ai/) 模型的出现提供了一种创新解法。这些 [大语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）在海量语料上训练，具备惊人的能力：可依据给定的 prompt 与输入，跨越文本、音频、视频等多种媒体形态，并跨越不同业务领域生成新内容。

本文探讨如何将这类 LLM 与先进的 [检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）结合，为金融领域的用例生成高质量的合成数据。你同样可以用这套技术为其他业务领域的用例生成合成数据。本文演示如何生成交易对手风险（CR）数据，这对直接在双方之间交易、不经过正式交易所的场外（OTC）衍生品会很有用。

## 解决方案概述

OTC 衍生品通常是交易对手之间定制的合约，包含多种金融工具，如远期、期权、互换以及其他结构性产品。交易对手是金融交易中涉及的另一方。在 OTC 衍生品的语境下，交易对手指与之订立衍生品合约的实体（例如银行、金融机构、公司或个人）。

例如，在一份 OTC 互换或期权合约中，一个实体与另一方就条款达成一致，双方互为对方的交易对手。责任、义务与风险（例如信用风险）按合约在这两个实体之间分担。

随着金融机构持续应对 CR 的复杂格局，对准确可靠的风险评估模型的需求变得至关重要。在我们的用例中，一家虚构的金融服务机构 ABC Bank 接下了这个挑战：开发一个 ML 模型，依据给定交易对手的 OTC 衍生品敞口数据来评估其风险。

构建这样的模型会面临诸多挑战。尽管 ABC Bank 已从各种来源收集了不同格式的大型数据集，但数据可能存在偏差、倾斜，或缺乏训练高准确度模型所需的多样性。主要挑战在于收集并预处理数据，使其适合训练 ML 模型。部署一个不适配的模型可能导致决策失据和重大财务损失。

我们提出一个采用 RAG 方法的生成式 AI 方案。RAG 是一种被广泛使用的方法，它通过从原始训练未包含的外部数据源补充额外信息来增强 LLM。整个方案大致可分为三步：索引、数据生成与验证。

### 数据索引

在索引步骤中，我们解析、切分具有代表性的 CR 数据，并使用 [Amazon Titan Text Embeddings V2](https://aws.amazon.com/bedrock/amazon-models/titan/) 模型将其转换为向量格式，再把这些信息存入 Chroma 向量数据库。Chroma 是一个开源向量数据库，以易用、高效的相似度搜索以及对多模态数据与元数据的支持而著称。它同时提供内存与持久化存储选项，能与主流 ML 框架良好集成，适用于各类 AI 应用。它对中小型数据集以及需要本地部署或低资源占用的项目尤其有益。下图说明了这一架构。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/22/Image1.jpg)

数据索引的步骤如下：

- 样本 CR 数据被分割成更小、更易处理的块，以便为生成 embedding 做优化。
- 这些分割后的数据块随后被传给一个方法，由它负责生成 embedding 并高效存储。
- 调用 Amazon Titan Text Embeddings V2 API，从准备好的数据块生成高质量 embedding。
- 生成的 embedding 随后存入 Chroma 向量数据库，为后续使用提供高效检索与相似度搜索。

### 数据生成

当用户请求某个场景的数据时，该请求会被转换为向量格式，然后在 Chroma 数据库中查找与已存数据的匹配项。检索到的数据会与用户请求以及附加的 prompt 一起，送往 [Anthropic's Claude Haiku](https://aws.amazon.com/bedrock/claude/)（运行在 [Amazon Bedrock](https://aws.amazon.com/bedrock/claude/) 上）。选择 Anthropic's Claude Haiku 主要因其速度，它每秒可处理超过 21,000 个 token，明显快于同类模型。此外，Anthropic's Claude Haiku 在数据生成上的效率也很突出，其[输入与输出 token 比为 1:5](https://www.anthropic.com/news/claude-3-haiku)。这意味着它可以从相对少量的输入或上下文生成大量数据。这一能力不仅提升了模型的有效性，也使我们的应用更具成本效益——我们需要从有限的示例生成大量数据样本。Anthropic's Claude Haiku LLM 会被迭代调用，以便高效管理 token 消耗并帮助避免触及最大 token 上限。下图说明了这一工作流。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/22/Image2-data-generation.jpg)

数据生成的步骤如下：

- 用户发起请求，要求基于特定条件生成新的合成交易对手风险数据。
- 使用 Amazon Titan Text Embeddings V2 LLM 为用户请求的 prompt 创建 embedding，将其转换为机器可解读的格式。
- 这些新生成的 embedding 随后被送往一个专门模块，用于找出匹配的已存数据。
- 查询存放着先前已存 embedding 的 Chroma 向量数据库，找出与用户请求高度匹配的数据。
- 找到的匹配数据与原始用户 prompt 随后被传给一个负责生成新合成数据的模块。
- 调用 Anthropic's Claude Haiku 3.0 模型，以匹配的 embedding 与用户 prompt 作为输入来创建高质量的合成数据。
- 生成的合成数据随后用 Pydantic 库解析并格式化为 .csv 文件，提供结构化且经过校验的输出。
- 为确认生成数据的质量，会应用若干统计方法，包括分位数-分位数（Q-Q）图与关键属性的相关性热力图，构成一套全面的验证流程。

### 数据验证

验证 LLM 生成的合成 CR 数据时，我们采用了 Q-Q 图与相关性热力图，重点关注 `cp_exposure`、`cp_replacement_cost` 和 `cp_settlement_risk` 等关键属性。这些统计工具在提升合成数据的质量与代表性方面起着关键作用。借助 Q-Q 图，我们可以评估这些属性是否服从正态分布——这在许多临床与金融变量中往往是预期之中的。通过把合成数据的分位数与理论正态分布对比，我们可以识别出可能意味着偏差或不真实数据生成的显著偏离。

与此同时，相关性热力图以可视化方式呈现这些属性与数据集中其他属性之间的关系。这一点尤其重要，因为它有助于验证 LLM 是否保持了真实 CR 数据中通常可见的复杂相互依赖关系。例如，我们预期敞口与重置成本之间、或重置成本与结算风险之间存在特定相关性。通过确保这些相关性在合成数据中得以保留，我们对基于该数据所做的分析或模型能产出适用于真实场景的洞见会更有信心。这一严格的验证流程有助于降低引入人为模式或偏差的风险，从而提升我们合成 CR 数据集在后续研究或建模任务中的可靠性与实用性。

def get_context(scenario):
    region_name = 'us-east-1'
    credential_profile_name = "default"
    titan_model_id = "amazon.titan-embed-text-v2:0"
    kb_context = []
    be = BedrockEmbeddings(region_name=region_name,
                           credentials_profile_name=credential_profile_name,
                           model_id=titan_model_id)

    vector_store = Chroma(collection_name="test_124", persist_directory="../data/chroma_index",
                      embedding_function=be)
    search_results = vector_store.similarity_search(scenario, k=3)
    for doc in search_results:
        kb_context.append(doc.page_content)
    return json.dumps(kb_context)
```

解析 LLM 生成的输出并以 CSV 表示颇具挑战。我们使用 Pydantic 解析器来解析 LLM 生成的 JSON 输出，如下方代码片段所示：

```
class CustomPydanticOutputParser(PydanticOutputParser):
    def parse(self, text: str) -> BaseModel:
        # Extract JSON from the text
        try:
            # Find the first occurrence of '{'
            start = text.index('{')
            # Find the last occurrence of '}'
            end = text.rindex('}') + 1
            json_str = text[start:end]

            # Parse the JSON string
            parsed_json = json.loads(json_str)

            # Use the parent class to convert to Pydantic object
            return super().parse_with_cls(parsed_json)
        except (ValueError, json.JSONDecodeError) as e:
            raise ValueError(f"Failed to parse output: {e}")
```

以下代码片段展示了如何以迭代方式生成记录，每次调用 LLM 生成 10 条记录：

```
def generate_full_dataset(total_records, batch_size, scenario, context):
    dataset = []
    total_generated = 0
    last_record = ""
    batch: DataSet = generate_records(total_generated,
                                      min(batch_size, total_records - total_generated),
                                      scenario, context, last_record)
    # print(f"batch: {type(batch)}")
    total_generated = len(batch.records)
    dataset.extend(batch.records)
    while total_generated < total_records:
        try:
            batch = generate_records(total_generated,
                                     min(batch_size, total_records - total_generated),
                                     scenario, context, batch.records[-1].json())
            processed_batch = batch.records

            if processed_batch:
                dataset.extend(processed_batch)
                total_generated += len(processed_batch)
                last_record = processed_batch[-1].start_index
                print(f"Generated {total_generated} records.")
            else:
                print("Generated an empty or invalid batch. Retrying...")
                time.sleep(10)
        except Exception as e:
            print(f"Error occurred: {e}. Retrying...")
            time.sleep(5)

    return dataset[:total_records]  # Ensure exactly the requested number of records
