# 基于 LLM-as-a-judge 的强化微调

大型语言模型（LLM）如今驱动着最先进的对话 agent、创作工具和决策支持系统。然而，它们的原始输出常常包含不准确、与策略不一致或措辞无益的内容——这些问题会损害信任，并限制其实际价值。*强化微调（Reinforcement Fine‑Tuning，RFT）* 已成为高效对齐这些模型的首选方法，它用*自动化的奖励信号*取代昂贵的人工标注。

现代 RFT 的核心是奖励函数。它们针对每个领域构建：可以用一段代码为 LLM 的生成结果打分（Reinforcement Learning with Verifiable Rewards，即 RLVR），也可以用 LLM-as-a-judge——由另一个语言模型评估候选回答来指导对齐（Reinforcement Learning with AI Feedback，即 RLAIF）。这两种方法都会把分数交给 RL 算法，推动模型解决当前问题。在本文中，我们将深入探讨 RLAIF 或基于 LLM-as-a-judge 的 RL 如何与 Amazon Nova 模型有效配合。

## **相比通用 RFT，为什么要用基于 LLM‑as‑a‑judge 的 RFT？**

强化微调可以使用任意奖励信号：直接手工构造的规则（RLVR），或者一个评估模型输出的 LLM（LLM-as-a-judge 或 RLAIF）。RLAIF 让对齐变得灵活得多、也强大得多，尤其是在奖励信号模糊、难以手工构造的时候。通用 RFT 奖励依赖子串匹配这类简单粗暴的数值打分，而 LLM 判官不同：它会跨多个维度——正确性、语气、安全性、相关性——进行推理，给出能感知上下文的反馈，捕捉细微差别和领域特有的微妙之处，而无需针对任务重新训练。此外，LLM 判官通过理由说明内置了可解释性（例如“回答 A 引用了同行评审的研究”），提供的诊断信息可以加速迭代、直接定位失败模式、减少隐性错位，这是静态奖励函数做不到的。

## **实现 LLM-as-a-judge：六个关键步骤**

本节介绍设计和部署 LLM-as-a-judge 奖励函数涉及的关键步骤。

### **选择判官架构**

第一个关键决策是选择判官架构。LLM-as-a-judge 提供两种主要评估模式：*基于评分标准（按分打分）的判定* 与 *基于偏好的判定*，各自适用于不同的对齐场景。

| **对比项** | **基于评分标准的判定** | **基于偏好的判定** |
| --- | --- | --- |
| 评估方式 | 依据预定义标准为单个回答给出数值分数 | 并排比较两个候选回答并选出更优者 |
| 质量度量 | 绝对质量度量 | 通过直接比较得到相对质量 |
| 优先使用的场景 | 存在清晰、可量化的评估维度（准确性、完整性、安全性合规） | 希望策略模型自由探索、不受参考数据限制 |
| 数据要求 | 只需细致的 prompt 工程，把模型对齐到奖励规范 | 至少需要一个回答样本用于偏好比较 |
| 泛化能力 | 更适合分布外数据，可避免数据偏差 | 取决于参考回答的质量 |
| 评估风格 | 类似绝对评分体系 | 类似人类通过比较作出的自然评估 |
| 推荐的起点 | 若没有偏好数据且 RLVR 不适用，从这里起步 | 有对比数据时使用 |

### **定义评估标准**

选定判官类型之后，要明确你想改进的具体维度。清晰的评估标准是有效 RLAIF 训练的基础。

**对于基于偏好的判官：**

编写清晰的 prompt，说明一个回答为什么优于另一个。用具体例子明确表达质量偏好。示例：*“优先选择引用权威来源、使用易懂语言、并直接回应用户问题的回答。”*

**对于基于评分标准的判官：**

对于基于评分标准的判官，我们建议使用布尔（通过/不通过）打分。与 1–10 的细粒度量表相比，布尔打分更可靠，也能减少判官的波动。要为每个评估维度定义清晰的通过/不通过标准，并给出具体、可观察的特征。

### **选择并配置判官模型**

选择一个推理能力足以评估目标领域的 LLM，通过 Amazon Bedrock 配置，并用奖励 AWS Lambda 函数调用。对于数学、编码和对话能力这类常见领域，只要 prompt 工程做得细致，较小的模型也能胜任。

| **模型档位** | **优先用于** | **成本** | **可靠性** | **Amazon Bedrock 模型** |
| --- | --- | --- | --- | --- |
| 大型/重量级 | 复杂推理、细致评估、多维打分 | 高 | 很高 | Amazon Nova Pro、Claude Opus、Claude Sonnet |
| 中型/轻量级 | 数学或编码这类通用领域，成本与性能均衡 | 低—中 | 中—高 | Amazon Nova 2 Lite、Claude Haiku |

### **打磨判官模型的 prompt**

判官 prompt 是对齐质量的基础。设计时要让它产出结构化、可解析的输出，并带有清晰的打分维度：

- **结构化输出格式** – 指定 JSON 或其他可解析格式，便于直接提取
- **清晰的打分规则** – 明确定义每个维度应如何计算
- **边界情况处理** – 处理含义模糊的场景（例如“若回答为空，则记 0 分”）
- **期望的行为** – 明确写出要鼓励或抑制的行为

### **让判官标准与生产评估指标对齐**

你的奖励函数应当映射你在生产环境中评估最终模型时所用的指标。让奖励函数与生产成功标准对齐，模型才会朝着正确的目标去设计。

**对齐工作流：**

- **定义**生产成功标准（例如准确性、安全性）以及可接受的阈值
- **映射**每一条标准到具体的判官打分维度
- **验证**判官分数与你的评估指标之间存在相关性
- **测试**判官在代表性样本和边界情况上的表现

### **构建**一个健壮的奖励 Lambda 函数

生产级 RFT 系统每个训练步骤要处理数千次奖励评估。构建一个健壮的奖励 Lambda 函数，有助于提供训练稳定性、高效的计算使用和可靠的模型行为。本节介绍如何构建一个健壮、高效且可直接用于生产的奖励 Lambda 函数。

**复合奖励分数的组织方式**

不要只依赖 LLM 判官。把它们与快速、确定性的奖励组件结合起来，在昂贵的判官评估之前先拦住明显的失败：

**核心组件**

| **组件** | **用途** | **何时使用** |
| --- | --- | --- |
| 格式正确性 | 校验 JSON 结构、必需字段、schema 合规性 | 始终使用——可立即拦住格式错误的输出，反馈便宜且即时 |
| 长度惩罚 | 抑制过于冗长或过于简略的回答 | 输出长度重要时（例如摘要） |
| 语言一致性 | 校验回答与输入语言一致 | 多语言应用的关键 |
| 安全过滤 | 基于规则检查违禁内容 | 始终使用——阻止不安全内容进入生产环境 |

**基础设施就绪度**

- **实现指数退避：** 优雅地处理 Amazon Bedrock API 的速率限制和瞬时故障
- **并行化策略**：使用 ThreadPoolExecutor 或异步模式，把多次 rollout 的判官调用并行化以降低延迟
- **避免 Lambda 冷启动延迟：** 设置合适的 Lambda 超时（建议 15 分钟）和预置并发（典型配置约 100）
- **错误处理：** 加入完善的错误处理，在失败时返回中性/带噪的奖励（0.5），而不是让整个训练步骤失败

**测试奖励 Lambda 函数的健壮性**

验证判官的一致性和校准情况：

- **一致性**：在同一批样本上多次测试判官，测量分数方差（确定性评估下应当很低）
- **跨判官比较：** 对比不同判官模型给出的分数，找出评估盲区
- **人工校准：** 定期抽样 rollout 交由人工复核，以发现判官漂移或系统性错误
- **回归测试：** 构建一个包含已知好/坏示例的“判官测试集”，对判官行为做回归测试

## **真实案例：自动化法律合同审查**

本节介绍一个与法律行业领先合作伙伴合作的真实用例。任务是针对法律文档，参照政策与既往合同等参考文件，生成关于风险、评估和处置动作的评论。

### **挑战**

该合作伙伴希望解决法律合同文档中风险审查、评估与标记流程的自动化问题。具体来说，他们想依据内部准则与法规、既往合同，以及合同所属国家的法律，来评估潜在的新合同。

### **解决方案**

我们把这个问题形式化为：给定一份目标文档（需要评估的“合同”）和一份参考文档（作为依据的文档与上下文），期望 LLM 生成一个 JSON，其中包含多条评论、评论类型，以及基于评估给出的建议动作。该用例最初可用的数据集规模较小，包含完整合同以及法律专家给出的标注和评论。在 RFT 过程中，我们用 LLM 作为判官，判官模型选用 GPT OSS 120b，并配了一份自定义 system prompt。

#### **用于 LLM-as-a-judge 的奖励 Lambda 函数**

以下代码片段展示了奖励 Lambda 函数的关键组成部分。

**注意**：Lambda 函数的名称中应当包含 “SageMaker”，例如 `"arn:aws:lambda:us-east-1:123456789012:function:MyRewardFunction**SageMaker**"`

**a) 从定义高层次目标开始**

```
# Contract Review Evaluation - Unweighted Scoring
You are an expert contract reviewer evaluating AI-generated comments. Your PRIMARY objective is to assess how well each predicted comment identifies issues in the TargetDocument contract clauses and whether those issues are justified by the Reference guidelines.
```

**b) 定义评估方法**

```
## Evaluation Approach
For each sample, you receive:
- **TargetDocument**: The contract text being reviewed (the document under evaluation)
- **Reference**: Reference guidelines/standards used for the review (the evaluation criteria)
- **Prediction**: One or more comments from the AI model
**Important**: The SystemPrompt shows what instructions the model received. Consider whether the model followed these instructions when evaluating the prediction quality.
**CRITICAL**: Each comment must identify a specific issue, gap, or concern IN THE TARGETDOCUMENT CONTRACT TEXT ITSELF. The comment's text_excerpt field should quote problematic contract language from the TargetDocument, NOT quote text from the Reference guidelines. The Reference justifies WHY the contract clause is problematic, but the issue must exist IN the contract.
Evaluate EACH predicted comment independently. Comments should flag problems in the contract clauses, not merely cite Reference requirements.
```

**c) 描述打分维度，并明确说明某个分数应当如何计算**

```
## Scoring Dimensions (Per Comment)
**EVALUATION ORDER**: Evaluate in this sequence: (1) TargetDocument_Grounding, (2) Reference_Consistency, (3) Actionability
### 1. TargetDocument_Grounding
**Evaluates**: (a) Whether text_excerpt quotes from TargetDocument contract text, and (b) Whether the comment is relevant to the quoted text_excerpt
**MANDATORY**: text_excerpt must quote from TargetDocument contract text. If text_excerpt quotes from Reference instead, score MUST be 1.
- **5**: text_excerpt correctly quotes TargetDocument contract text AND comment identifies a highly relevant, valid, and notable issue in that quoted text
- **4**: text_excerpt correctly quotes TargetDocument contract text AND comment identifies a valid and relevant issue in that quoted text
- **3**: text_excerpt correctly quotes TargetDocument contract text AND comment is somewhat relevant to that quoted text, but concern has moderate validity
- **2**: text_excerpt correctly quotes TargetDocument contract text BUT comment has weak relevance to that quoted text, or concern is questionable
- **1**: text_excerpt does NOT quote TargetDocument contract text (quotes Reference instead, or no actual quote), OR comment is irrelevant to the quoted text
### 2. Reference_Consistency
...
...
```

**d) 明确定义最终需要解析的输出格式**

```
## Scoring Calculation
**Comment_Score** = Simple average of the three dimensions:
- Comment_Score = (TargetDocument_Grounding + Reference_Consistency + Actionability) / 3
**Aggregate_Score** = Average of all Comment_Score values for the sample
## Output Format
For each sample, evaluate ALL predicted comments and provide:
```json
{ "comments": [ 
        { "comment_id": "...",
          "TargetDocument_Grounding": {"score": X, "justification": "...", "supporting_evidence": "Verify text_excerpt quotes actual TargetDocument contract text and comment is relevant to it"},
          "Reference_Consistency": {"score": X, "justification": "...", "supporting_reference": "Quote from Reference that justifies the concern OR explain meaningful reasoning"},                   
          "Actionability": {"score": X, "justification": "Assess if action is clear, grounded in TargetDocument and Reference, and relevant to comment"},
          "Comment_Score": X.XX 
        } ],
  "Aggregate_Score": {
          "score": X.XX,
          "total_comments": N,
          "rationale": "..." 
   }
}
```

**e) 编写高层次的 Lambda handler，并提供足够的多线程以加快推理**

```
def lambda_handler(event, context): 
        scores: List[RewardOutput] = []
        samples = event
        max_workers = len(samples)
        print(f"Evaluating {len(samples)} items with {max_workers} threads...")
        with ThreadPoolExecutor(max_workers=max_workers) as executor:
                futures = [executor.submit(judge_answer, sample) for sample in samples]
                scores = [future.result() for future in futures]
        print(f"Completed {len(scores)} evaluations")
        return [asdict(score) for score in scores]
```

#### **定制训练配置**

我们发布了 Nova Forge SDK，它为模型定制生命周期的每个阶段都提供模块化组件：用于训练的 `ForgeTrainer`、用于评估的 `ForgeEvaluator`、用于部署的 `ForgeDeployer`，以及用于推理的 `ForgeInference`。Nova Forge SDK 让你不必再为特定技术去找合适的 recipe 或容器 URI。

你可以用 Nova Forge SDK 中的 `ForgeTrainer` 以两种方式定制训练参数：通过 recipe_path 提供完整的 recipe YAML，或通过 overrides 传入特定字段做选择性修改。在本用例中，我们使用 overrides 调整 rollout 和 trainer 设置，如下一节所示。

```

from amzn_nova_forge.core import ForgeConfig

trainer = ForgeTrainer(
    model=Model.NOVA_LITE_2,
    method=TrainingMethod.RFT_LORA,
    infra=SMTJRuntimeManager(instance_type="ml.p5.48xlarge", instance_count=2),
    training_data_s3_path="s3://...",

)

result = trainer.train(
        job_name="my-rft-run",

采用 RFT 的 Amazon Nova 2 Lite 取得了 **4.33 的总分**，超过 Claude Sonnet 4.5 和 Claude Haiku 4.5，同时还实现了完美的 **JSON schema 校验**。

- **消除了不必要的训练副产物**

在 SFT 迭代过程中，我们观察到一些有问题的行为，包括重复生成评论以及预测出不自然的 Unicode 字符。这些问题很可能由过拟合或数据集不平衡导致，但在 RFT 的检查点中没有出现。RFT 基于奖励的改进会自然地抑制这类副产物，**产出更健壮、更可靠的输出**。

- **对新的判官标准有很强的泛化能力**

当我们用修改过的判官 prompt（与训练时的奖励函数对齐但不完全相同）评估 RFT 模型时，性能依然很强。这说明 RFT 学到的是可泛化的质量模式，而不是过拟合到特定的评估标准。对于需求会不断变化的生产部署来说，这是一个关键优势。

- **算力方面的考量**

RFT 每个训练样本需要 4–8 次 rollout，因此相比 SFT 增加了算力成本。使用非零 reasoning effort 设置时，这种开销会进一步放大。但对于对齐质量直接影响业务成果的关键任务应用——例如法律合同审查、金融合规或医疗文档——性能提升足以证明额外的算力成本是值得的。

## **结论**

基于 LLM-as-a-judge 的强化微调（RFT）是将 LLM 对齐到特定领域应用的一条强大路径。正如我们的法律合同审查案例所示，这套方法相比基础模型和传统的监督微调（SFT）方法都有显著提升，RFT 在所有评估维度上都取得了最高的总分。对于正在构建关键任务 AI 系统、且对齐质量直接影响业务成果的团队来说，基于 LLM-as-a-judge 的 RFT 提供了一条有说服力的前进路径。该方法在可解释性、灵活性和性能上的优势，使其在需要把握细微差别的复杂领域（如法律审查、金融服务或医疗）格外有价值。

考虑采用这一方法的组织应当从小规模开始——在精心构建的基准上验证判官设计，确认基础设施的健壮性，然后逐步扩大规模，同时监控是否出现奖励劫持。只要实施得当，RFT 就能把有能力的基础模型转化为高度专用、可直接用于生产的系统，稳定输出对齐、可信的结果。
