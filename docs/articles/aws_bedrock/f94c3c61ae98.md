# 在 Anthropic 中借助 Amazon Bedrock Knowledge Bases 实现上下文检索

AI 模型要在专业领域有效发挥作用，就需要访问相关的背景知识。例如，客服聊天助手需要关于其所服务业务的详细信息，而法律分析工具则必须依托一个涵盖过往案例的全面数据库。

为了让[大语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）具备这些知识，开发者通常使用[检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）。这项技术从知识库中检索相关信息，并将其融入用户的 prompt，从而显著改善模型的回答。然而，传统 RAG 系统的一个关键局限在于，它们在编码数据时往往会丢失上下文细节，导致从知识库中检索到不相关或不完整的内容。

## **传统 RAG 的挑战**

在传统 RAG 中，文档通常被切分为更小的 chunk 以优化检索效率。尽管这种方法在许多情况下表现良好，但当单个 chunk 缺少必要的上下文时，就会带来挑战。例如，某份政策规定远程办公需要“6 months of tenure”（chunk 1）以及“HR approval for exceptions”（chunk 3），却遗漏了把例外与经理审批联系起来的中间 chunk；此时用户询问一名任职 3 个月的员工是否符合条件，可能得到一个误导性的“No”，而不是正确的“Only with HR approval.”。这是因为孤立的 chunk 无法保留条款之间的依赖关系，凸显了 RAG 系统中基础分块策略的一项关键局限。

上下文检索通过在生成 embedding 之前为每个 chunk 添加针对该 chunk 的解释性上下文，来增强传统 RAG。这种方法用相关的上下文信息丰富向量表示，使得在回应用户查询时能够更准确地检索语义相关的内容。例如，当被问及远程办公资格时，它会同时取回任职时长要求和 HR 例外条款，使 LLM 能够给出诸如“Normally no, but HR may approve exceptions.”这样准确的回答。通过智能地拼接碎片化信息，上下文检索缓解了僵化分块带来的问题，交付更可靠、更细致的回答。

在本文中，我们演示如何在 Anthropic 与 Amazon Bedrock [Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 上使用上下文检索。

## 解决方案概览

本方案使用 Amazon Bedrock Knowledge Bases，并引入一个自定义 Lambda 函数，在知识库摄入过程中转换数据。该 Lambda 函数处理来自 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）的文档，将其切分为更小的片段，使用 Amazon Bedrock 中的 Anthropic Claude 为每个片段补充上下文信息，然后把结果保存回一个中间 S3 桶。以下是分步说明：

- 从事件中指定的 S3 桶读取输入文件。
- 把输入数据切分为更小的 chunk。
- 使用 Anthropic 的 Claude 3 Haiku 为每个 chunk 生成上下文信息
- 把处理后的 chunk 及其元数据写回中间 S3 桶

要实施该方案，请完成以下前提步骤：

## 性能基准测试

为了评估所提出的上下文检索方法的性能，[我们使用 AWS Decision Guide: Choosing a generative AI service](https://docs.aws.amazon.com/decision-guides/latest/generative-ai-on-aws-how-to-choose/guide.html) 作为 RAG 测试的文档。我们为评估搭建了两个 Amazon Bedrock 知识库：

- 一个采用默认分块策略的知识库，每个 chunk 使用 300 个 token，重叠比例为 20%
- 另一个采用自定义上下文检索分块方法的知识库，它在固定分块策略之外还配置了一个自定义的上下文检索 Lambda 转换器，该固定分块策略同样每个 chunk 使用 300 个 token、重叠 20%

我们使用 RAGAS 框架和较小的数据集来评估这两种方法的性能。具体来说，我们关注以下指标：

- `context_recall` – 上下文召回率衡量有多少相关文档（或信息片段）被成功检索到
- `context_precision` – 上下文精确率是一项衡量 `retrieved_contexts` 中相关 chunk 比例的指标
- `answer_correctness` – 答案正确性评估是通过与标准答案（ground truth）比较来衡量生成答案的准确度

## 实施注意事项

在使用 Amazon Bedrock 实施上下文检索时，有几个因素需要仔细考虑。首先，自定义分块策略必须同时针对性能和准确度进行优化，这需要在不同类型的文档和不同大小上做充分测试。Lambda 函数的内存分配和超时设置应根据预期的文档复杂度和处理需求进行校准，初始建议以 1024 MB 内存和 900 秒超时作为基线配置。组织还必须按照最小权限原则配置 IAM 角色，同时保持足够的权限让 Lambda 与 Amazon S3 和 Amazon Bedrock 服务交互。此外，向量化过程和知识库配置应经过微调，以在检索准确度与计算效率之间取得平衡，尤其是在扩展到更大数据集时。

基础设施可扩展性和监控方面的考量对成功实施同样关键。组织应在 Lambda 函数内实现健壮的错误处理机制，以从容应对各种文档格式和潜在的处理失败。应建立监控系统来跟踪分块性能、检索准确度和系统延迟等关键指标，从而支持主动优化和维护。

将 Langfuse 与 Amazon Bedrock 配合使用，是为该方案引入可观测性的一个不错选择。源存储与中间存储的 S3 桶结构应设计清晰的生命周期策略和访问控制，并考虑区域可用性和数据驻留要求。此外，采用分阶段部署的方式——先用一部分数据，再扩展到完整的生产工作负载——有助于在实施过程的早期发现并处理潜在的瓶颈或优化机会。
