# 使用 Amazon SageMaker HyperPod Data Capture 构建模型改进飞轮

Amazon SageMaker HyperPod 上部署的基础模型满足任何预先策划的数据集都无法涵盖的输入：特定领域的术语、意外的格式、新产品和不断变化的用户行为。如果没有生产推理数据的记录，团队就无法检测偏差、找到故障模式或使用真实的交互来改进模型。

Amazon SageMaker HyperPod 现在提供数据捕获，这是一种内置功能，可在三个独立层将实时推理输入和输出记录到 Amazon Simple Storage Service (Amazon S3)，将延迟影响降至最低，对模型可用性的影响为零。

在这篇文章中，我们将演练单个 SageMaker HyperPod 集群上的一个完整示例。家用电器支持路由器捕获其生产流量，Amazon Athena 查询显示新产品盲点，SQL 策略标记捕获的记录，并对数据进行微调，向路由器通报新产品。我们在部署模型之前和之后测量模型部署之前不可能存在的数据的准确性。推理算子在一个节点上为模型提供服务，训练算子在另一节点上运行微调。

我们在演练中使用合成数据。脚本、清单、SQL、合成数据集和预期输出可在[随附的 GitHub 存储库](https://github.com/awslabs/awsome-distributed-ai/tree/main/examples/use-cases/sagemaker-hyperpod-data-capture-flywheel)中获取。

## 三层数据采集架构

HyperPod Data Capture 提供三个独立的层，每个层位于请求路径中的不同点。您可以在同一个“dataCapture”块中打开任意组合。

|  | **第 1 层：SageMaker 端点** | **第 2 层：负载均衡器** | **第 3 层：模型吊舱** |
| --- | --- | --- | --- |
|捕获了什么 |完整的请求/响应有效负载 |应用程序负载均衡器 (ALB) 访问日志字段：请求行、状态代码、计时、客户端 IP、用户代理 |完整的请求/响应有效负载以及事件元数据 |
|管理人 | SageMaker 本机数据捕获 | ALB 访问日志 | HyperPod 推理运算符（NGINX + OTel 收集器 + S3 上传边车）|
|最适合 |合规性、模型监控、审计 |低成本流量和错误率监控|调试、分析、培训数据收集 |
|配置| `sagemakerEndpoint:` — 采样 %、输入/输出、AWS KMS | `loadBalancer: { 启用: true }` | `modelPod:` — 采样百分比、输入/输出、缓冲区、最大负载大小、AWS KMS、内容类型 |

第 1 层和第 3 层都存储完整的有效负载，因此这两个层都可以将每个记录存储两次。使用第 1 层来实现合规性和模型监控，当您只需要流量元数据时使用第 2 层，当您打算“使用”有效负载时使用第 3 层。这篇文章仅使用第 3 层。由于第 3 层记录了完整的有效负载（其中可能包括名称、地址和订单号），因此请在数据成为训练数据之前对其进行保护。使用采样、AWS Key Management Service (AWS KMS) 加密（`kmsKeyId`）、S3 生命周期规则和个人身份信息 (PII) 编辑（例如，使用 Amazon Comprehend）。

## 先决条件

- 由 Amazon Elastic Kubernetes Service (Amazon EKS) 编排的 SageMaker HyperPod 集群，安装了推理运算符（[设置 HyperPod 集群以进行模型部署](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-model-deployment-setup.html)）并安装了训练运算符 EKS 插件“amazon-sagemaker-hyperpod-training-operator” （[安装训练运算符](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-eks-operator-install.html)）。
- **两个可用的 NVIDIA GPU**，一个用于服务，一个用于训练。我们使用“ml.g6e.8xlarge”进行服务，使用“ml.g6e.xlarge”进行训练（每个 48 GB NVIDIA L40S）。服务 Pod 在端点的生命周期内保留其 GPU，因此只有一个 GPU 时，训练 Pod 会保持“待处理”状态。
- 为集群配置的“kubectl”。
- 同一区域中的 S3 存储桶。

确认两个操作员均已安装。该命令返回两行：
```
kubectl get crd | grep -E 'inferenceendpointconfigs|hyperpodpytorchjobs'
hyperpodpytorchjobs.sagemaker.amazonaws.com                         2026-09-21T10:57:14Z
inferenceendpointconfigs.inference.sagemaker.aws.amazon.com         2026-08-06T11:58:53Z
```
## 解决方案概述

推理运算符将三个 sidecar 添加到模型容器中。通过 NGINX 代理的每个请求都会被复制到 OpenTelemetry 收集器、批处理并通过 Mountpoint-S3 卷写入 S3。 Athena 就地读取这些文件。训练操作员在第二个 GPU 上作为“HyperPodPyTorchJob”运行微调，新模型由也启用捕获的第二个端点提供服务。

### 步骤 1：在 S3 中暂存基础模型

我们使用“Qwen2.5-3B-Instruct”，因为它足够小，可以在大约一分钟内进行微调，并且适合单个 L40S。
```
pip install -q huggingface_hub
python3 -c "from huggingface_hub import snapshot_download; \
  snapshot_download('Qwen/Qwen2.5-3B-Instruct', local_dir='qwen2.5-3b-instruct')"
aws s3 sync qwen2.5-3b-instruct "s3://${BUCKET}/${MODEL_LOCATION}/" --exclude ".cache/*"
```
### 步骤 2：IAM 权限

四个身份需要访问。有关策略声明，请参阅[HyperPod 上的推理数据捕获](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-model-deployment-data-capture.html)。

- **Mountpoint-S3 CSI 驱动程序角色。** 第 3 层捕获通过 Mountpoint-S3 卷进行写入，并且驱动程序作为其自己的服务帐户 (IRSA) 角色的 IAM 角色（而不是 Pod 的服务帐户）进行身份验证。它需要捕获存储桶上的“s3:PutObject”、“s3:AbortMultipartUpload”和“s3:DeleteObject”，如果设置“kmsKeyId”，还需要“kms:Decrypt”、“kms:GenerateDataKey”和“kms:DescribeKey”。如果缺少此项，端点将保持健康并且请求成功，但不会出现任何捕获。请参阅 [Amazon S3 CSI 驱动程序的挂载点](https://docs.aws.amazon.com/eks/latest/userguide/s3-csi.html)。
- **推理运算符执行角色。** 如果您设置了“kmsKeyId”，它需要捕获存储桶上的“s3:PutObject”，以及“kms:Decrypt”和“kms:GenerateDataKey”。捕获文件本身是通过 CSI 驱动程序角色写入的，因此当没有捕获出现时，请首先检查该角色。
- **训练 Pod 的服务帐户 (**`$TRAIN_SA`**)。** 通过 [EKS Pod Identity](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html) 读取基本模型和训练数据的访问权限，以及写入合并模型的访问权限。
- **Athena.** 对捕获前缀以及查询结果位置的读取访问权限。

## 启用数据捕获

接下来的三个步骤在启用第 3 层捕获的情况下部署路由器，检查 Pod 是否运行捕获边车，并确认记录到达 Amazon S3。

### 步骤 3：在启用第 3 层捕获的情况下部署模型

这就是整个功能：“dataCapture.modelPod.enabled: true”块。其他一切都是普通的 vLLM 部署。
```
cat > endpoint.yaml <<'YAML'
apiVersion: inference.sagemaker.aws.amazon.com/v1
kind: InferenceEndpointConfig
metadata:
  name: ${ENDPOINT_NAME}
  namespace: default
spec:
  replicas: 1
  modelName: ${ENDPOINT_NAME}
  endpointName: ${ENDPOINT_NAME}
  instanceType: ${SERVE_INSTANCE_TYPE}
  invocationEndpoint: v1/chat/completions
  modelSourceConfig:
    modelSourceType: s3
    modelLocation: ${MODEL_LOCATION}
    s3Storage:
      bucketName: ${BUCKET}
      region: ${AWS_REGION}

  # >>> This is all you need to turn on Tier 3 data capture <<<
  dataCapture:
    s3Uri: "s3://${BUCKET}/capture/"
    modelPod:
      enabled: true
      initialSamplingPercentage: 100
      bufferConfig:
        batchSize: 50
        flushIntervalSeconds: 60
      payloadConfig:
        maxPayloadSizeKB: 1024

  worker:
    image: vllm/vllm-openai:v0.10.0
    modelInvocationPort:
      containerPort: 8000
      name: http
    modelVolumeMount:
      mountPath: /opt/ml/model
      name: model-weights
    args: ["--model", "/opt/ml/model", "--served-model-name", "${ENDPOINT_NAME}",
           "--port", "8000", "--max-model-len", "2048", "--gpu-memory-utilization", "0.90"]
    resources:
      requests: { cpu: "2", memory: 16Gi, nvidia.com/gpu: 1 }
      limits:   { nvidia.com/gpu: 1 }
YAML
render < endpoint.yaml | kubectl apply -f -
```
前面的“modelPod”块设置 100% 采样并捕获输入和输出，这是默认值。要调整它，请在“modelPod”下添加以下任意可选字段：
```
modelPod:
  enabled: true
  initialSamplingPercentage: 50          # capture 50% of requests (default 100)
  bufferConfig:
    batchSize: 100                       # records buffered per upload batch (default 10)
    flushIntervalSeconds: 60             # max seconds before a flush (default 60)
  payloadConfig:
    maxPayloadSizeKB: 1024               # truncate payloads larger than this (default: no limit)
  kmsKeyId: "arn:aws:kms:...:key/..."    # encrypt captures at rest
```
### 第 4 步：等待 Pod

启用捕获功能的 Pod 运行 **四个容器**：模型、“sidecar-reverse-proxy”（NGINX）、“otel-collector”和“s3-uploader”。模型容器和 pod 的 app 标签均以 modelName 命名。
```
kubectl get pods -l app=$ENDPOINT_NAME -o custom-columns=\
'NAME:.metadata.name,READY:.status.containerStatuses[*].ready,CONTAINERS:.spec.containers[*].name,NODE:.spec.nodeName'
NAME                            READY                 CONTAINERS                                                              NODE
appliance-router-849f466476-4f5v8   true,true,true,true   appliance-router,s3-uploader,sidecar-reverse-proxy,otel-collector   hyperpod-i-0f3fe2684afd6a583
```
在我们的运行中，pod 在“kubectl apply”后大约五分钟就准备好了，其中大部分时间都花在下载权重上。

### 步骤 5：发送请求并确认占领 S3 中的土地

通过端口 **8081** 上的捕获代理发送推理请求，然后在刷新间隔后列出捕获前缀。模型本身侦听端口 8000。发送到那里的请求绕过代理并且不会被捕获。
```
POD=$(kubectl get pod -l app=$ENDPOINT_NAME -o jsonpath='{.items[0].metadata.name}')
kubectl port-forward "pod/$POD" 18081:8081 >/dev/null 2>&1 &
sleep 5

curl -s http://localhost:18081/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"'"$ENDPOINT_NAME"'","messages":[{"role":"user","content":"my fridge is not cooling"}],"max_tokens":24}'

echo "Waiting for the capture buffer to flush..."; sleep 75
aws s3 ls "s3://${BUCKET}/capture/" --recursive | grep '\.jsonl$' | head
2026-09-28 15:47:14     634356 capture/20e4425092f90c7f/pod/AllTraffic/2026/09/28/15/28-15-47-12-999-ac31d31b-5156-46ad-9ccc-e8a040ab9ab2.jsonl
```
您会在“{s3Uri}/{uniqueID}/pod/{variant}/{YYYY}/{MM}/{DD}/{HH}/”下看到一个或多个“.jsonl”对象。每个端点都会生成“uniqueID”。每一行都是 SageMaker 数据捕获格式中的一个推论，如下所示。

### 捕获的记录格式

请求和响应主体以 **base64 编码** 的方式存储，如“encoding”字段所示，因此读回它们需要进行 base64 解码，然后解析 JSON：
```
{
  "captureData": {
    "endpointInput":  { "observedContentType": "application/json", "mode": "INPUT",
                        "data": "eyJtb2RlbCI6ICJyb3V0ZXItZnJlc2giLCAidGVtcGVyYXR1cmUiOiAwLCAi...", "encoding": "BASE64" },
    "endpointOutput": { "observedContentType": "application/json", "mode": "OUTPUT",
                        "data": "eyJpZCI6ImNoYXRjbXBsLTctMTc5MDYxMDM2OS4wMDUtMjMxMiIsIm9iamVj...", "encoding": "BASE64" }
  },
  "eventMetadata": { "eventId": "26859f07-d60b-4683-94aa-d21e7f19e746", "inferenceTime": "2026-09-28T15:46:09Z" },
  "eventVersion": "0"
}
```
解码后，“endpointInput.data”是客户端发送的请求正文，“endpointOutput.data”是模型返回的响应。

## 场景：支持票证路由器满足产品发布要求

部署的模型是家电零售商的支持票据路由器。它使用 vLLM 引导的 JSON 解码将每张票据分为六个类别之一：“ProductFridge”、“ProductWasher”、“ProductOven”、“ProductDishwasher”、“ProductMicrowave”或包罗万象的“Other”。引导解码意味着它只能返回带有以下标签之一的有效对象：
```
{"category": "ProductWasher", "confidence": 1}
```
该型号部署后，零售商推出了自己的空调系列，即 **Arctis** 系列（Arctis 9K、12K、Mini 等）。路由器没有它们的类别。它不能说“这是新的”。它只能选择它所知道的最接近的标签。除非记录每个请求和响应，否则证据在返回响应后就消失了。

### 合成流量

我们生成了两个合成数据集：

- **生产流量：** 900 张票据，通过捕获代理在 15 分钟内按顺序重播，使用路由器的原始六标签提示。前 400 个是在发布之前发布的，并且没有提到空调。在剩下的 500 个中，Arctis 门票的份额从 15% 上升到 55%。
- **评估集：** 280 张标签票，每个类别 40 张，包括新的“ProductAC”。它*按内容*提供：它使用从未出现在流量中的症状、句子模板和 Arctis 模型名称。

每个生产请求如下所示（系统提示缩写）：
```
{"model": "appliance-router", "temperature": 0, "max_tokens": 40,
 "messages": [{"role": "system", "content": "You are a support-ticket router for a home-appliance retailer. ... category is one of: ProductFridge, ProductWasher, ProductOven, ProductDishwasher, ProductMicrowave, Other. ..."},
              {"role": "user", "content": "Hi, our Arctis 12K blows warm air since last week. Order #66759."}],
 "guided_json": {"type": "object", "required": ["category", "confidence"],
                 "properties": {"category": {"enum": ["ProductFridge", "ProductWasher", "ProductOven",
                                                      "ProductDishwasher", "ProductMicrowave", "Other"]},
                                "confidence": {"type": "number"}}}}
```
要重放流量，请克隆随附的存储库，生成数据集，然后通过捕获代理发送它们。 `scripts/pod.sh` 在模型容器内运行客户端，因此不需要负载均衡器或 DNS。客户端打印 Athena 步骤使用的三个时间戳：“RUN_START”、“LAUNCH_TS”（第一个启动后票证）和“RUN_END”。
```

cd awsome-distributed-ai/examples/use-cases/sagemaker-hyperpod-data-capture-flywheel
(cd data && python3 ../scripts/gen_dataset.py)
scripts/pod.sh $ENDPOINT_NAME drive /tmp/tickets_traffic.jsonl --seconds 900
RUN_START=2026-09-28 15:52:40
  sent 100/900
...
LAUNCH_TS=2026-09-28 15:59:20
...
RUN_END=2026-09-28 16:07:40
```
导出运行打印的三个值，然后等待一个刷新间隔：
```

sleep 75    # one flush interval
```
## 使用 Amazon Athena 解决问题

离线基准测试在发布后看起来仍然没有变化，因为它们已被冻结在过去。这种转变仅在捕获的生产流量中可见。本部分展示了数据科学家如何在不配置任何基础设施的情况下使用 Athena 找到它。

### 步骤 6：设置变量并配置 Athena 辅助函数
```
export ATHENA_DB="flywheel_demo"
export ATHENA_OUTPUT="s3://${BUCKET}/athena-results/"
# Each endpoint writes under its own uniqueID. Pick the prefix whose captured requests name this
# endpoint, not whichever prefix sorts first (the Step 15 endpoint adds a second one).
for id in $(aws s3 ls "s3://${BUCKET}/capture/" | awk '/PRE/{print $2}'); do
  key=$(aws s3 ls "s3://${BUCKET}/capture/${id}pod/AllTraffic/" --recursive | awk '/\.jsonl$/{print $4; exit}')
  [ -n "$key" ] || continue
  model=$(aws s3 cp "s3://${BUCKET}/${key}" - 2>/dev/null | head -n 1 | python3 -c 'import sys, json, base64; r = json.loads(sys.stdin.readline()); print(json.loads(base64.b64decode(r["captureData"]["endpointInput"]["data"]))["model"])')
  if [ "$model" = "$ENDPOINT_NAME" ]; then export CAPTURE_LOCATION="s3://${BUCKET}/capture/${id}pod/AllTraffic/"; break; fi
done
echo "$CAPTURE_LOCATION"     # s3://<bucket>/capture/<uniqueID>/pod/AllTraffic/

# run_athena "<SQL>": runs one statement, prints tab-separated rows, and sets LAST_QID
run_athena() {
  local qid st
  qid=$(aws athena start-query-execution --query-string "$1" \
        --query-execution-context "Database=$ATHENA_DB" \
        --result-configuration "OutputLocation=$ATHENA_OUTPUT" \
        --output text --query 'QueryExecutionId') || return 1
  while :; do
    st=$(aws athena get-query-execution --query-execution-id "$qid" \
         --output text --query 'QueryExecution.Status.State')
    case "$st" in
      SUCCEEDED) break ;;
      FAILED|CANCELLED) aws athena get-query-execution --query-execution-id "$qid" \
          --output text --query 'QueryExecution.Status.StateChangeReason' >&2; return 1 ;;
    esac
    sleep 2
  done
  LAST_QID=$qid
  aws athena get-query-results --query-execution-id "$qid" \
    --output text --query 'ResultSet.Rows[*].Data[*].VarCharValue'
}
run_athena "CREATE DATABASE IF NOT EXISTS ${ATHENA_DB}"
```
### 步骤 7：向 Athena 声明捕获（两层）

第一层是信封。外部表描述了每条记录的外部 JSON，“年/月/日/小时”上的分区投影将每小时的 S3 前缀映射到分区，而无需爬虫或“ADD PARTITION”。 “data”字段被声明为纯字符串，因为它们是 base64 文本。
```
run_athena "
CREATE EXTERNAL TABLE IF NOT EXISTS inference_captures (
  captureData struct<
    endpointInput:  struct<observedContentType: string, mode: string, data: string, encoding: string>,
    endpointOutput: struct<observedContentType: string, mode: string, data: string, encoding: string>
  >,
  eventMetadata struct<eventId: string, inferenceTime: string>,
  eventVersion string
)
PARTITIONED BY (year string, month string, day string, hour string)
ROW FORMAT SERDE 'org.openx.data.jsonserde.JsonSerDe'
LOCATION '${CAPTURE_LOCATION}'
TBLPROPERTIES (
  'projection.enabled'='true',
  'projection.year.type'='integer',  'projection.year.range'='2026,2035',
  'projection.month.type'='integer', 'projection.month.range'='1,12', 'projection.month.digits'='2',

第二层是对每条记录解码一次的视图。 `from_utf8(from_base64(...))` 将有效负载重新转换为 JSON。如果没有它，每次提取都会返回“NULL”。票证是用户消息（“messages[1]”，因为“messages[0]”是系统提示符）。该模型的答案是响应 JSON 中的 JSON 字符串，因此需要进行第二次提取。
```

- **始终在分区上进行过滤。** Athena 读取原始 JSON，因此没有分区过滤器的查询会扫描您捕获的每个对象。视图过滤到一天，并且时间限制将其限制为我们的流量运行：相同的前缀还保存来自步骤 5 的请求。

## 从诊断到标记训练数据

数据科学家不会手工标记数百张票证。相反，他们将 Athena 的发现写下来作为**标签策略**：一个 SQL 视图，为每个捕获的记录分配正确的标签。我们将错误路由的空调票重新标记为新类别。

### 第 11 步：标签政策
```
run_athena "
CREATE OR REPLACE VIEW labeled_training_data AS
WITH t AS (SELECT ticket_text, predicted_category, lower(ticket_text) AS txt FROM preds)
SELECT ticket_text, predicted_category,
  CASE
    -- 1. The new class, identified by keyword evidence, not by what the model predicted
    WHEN regexp_like(txt, '\\barctis\\b|air condition|\\bac unit\\b|mini split')
     AND NOT regexp_like(txt, 'fridge|refrigerat|freezer|washer|\\boven\\b|\\brange\\b|dishwasher|microwave')
      THEN 'ProductAC'
    -- 2. Keep the production decision when nothing hints at the new product
    WHEN NOT regexp_like(txt, '\\barctis\\b|air condition|\\bac\\b|mini split')
      THEN predicted_category
    -- 3. Mixed signals: send to human review (Amazon SageMaker Ground Truth)
    ELSE NULL
  END AS corrected_category
FROM t"
```
双反斜杠 (`\\b`) 是双引号字符串内的 shell 转义。 Athena 接收“\b”，即正则表达式字边界。

检查政策产生了什么：

## 使用 HyperPod 训练算子对捕获的数据进行微调

我们使用第二个 GPU 上的 HyperPod 训练算子对服务模型的同一集群进行微调。第一个端点始终保持服务。

### 第 13 步：训练脚本

该脚本从 S3 下载基本模型和训练数据，并训练低阶自适应 (LoRA) 适配器。损失仅在辅助回合中计算，因此模型学习生成标签而不是重复提示。然后，该脚本将适配器合并回基本权重，以便 vLLM 可以保持不变地提供结果，并将合并的模型上传到 S3。该作业将脚本从 ConfigMap 安装到训练 Pod 中。
```
cat > train.py <<'PY'
import os, boto3, torch
from datasets import load_dataset
from peft import LoraConfig, get_peft_model
from transformers import AutoModelForCausalLM, AutoTokenizer, Trainer, TrainingArguments

s3 = boto3.client("s3")
def split(uri): b, _, k = uri[5:].partition("/"); return b, k

# 1. Stage base model + training data from S3
bucket, prefix = split(os.environ["BASE_MODEL_S3"])
for page in s3.get_paginator("list_objects_v2").paginate(Bucket=bucket, Prefix=prefix):
    for o in page.get("Contents", []):
        dst = os.path.join("/work/base", os.path.relpath(o["Key"], prefix))
        os.makedirs(os.path.dirname(dst), exist_ok=True); s3.download_file(bucket, o["Key"], dst)
s3.download_file(*split(os.environ["TRAIN_FILE_S3"]), "/work/train.jsonl")
print("[stage] base model and training data downloaded", flush=True)

# 2. LoRA SFT, loss only on the assistant turn (the label), not the prompt
tok = AutoTokenizer.from_pretrained("/work/base")
def encode(ex):
    full = tok.apply_chat_template(ex["messages"], tokenize=False)
    prompt = tok.apply_chat_template(ex["messages"][:-1], tokenize=False, add_generation_prompt=True)
    ids = tok(full, add_special_tokens=False)["input_ids"]
    n = len(tok(prompt, add_special_tokens=False)["input_ids"])
    return {"input_ids": ids, "labels": [-100] * n + ids[n:]}
ds = load_dataset("json", data_files="/work/train.jsonl", split="train")
print(f"[data] {len(ds)} examples", flush=True)
ds = ds.map(encode, remove_columns=ds.column_names)

def collate(batch):
    m = max(len(b["input_ids"]) for b in batch)
    pad = lambda xs, v: [x + [v] * (m - len(x)) for x in xs]
    return {"input_ids": torch.tensor(pad([b["input_ids"] for b in batch], tok.pad_token_id)),
            "labels": torch.tensor(pad([b["labels"] for b in batch], -100)),
            "attention_mask": torch.tensor(pad([[1] * len(b["input_ids"]) for b in batch], 0))}

model = AutoModelForCausalLM.from_pretrained("/work/base", torch_dtype=torch.bfloat16, device_map="cuda:0")
model = get_peft_model(model, LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05, task_type="CAUSAL_LM",
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj", "gate_proj", "up_proj", "down_proj"]))
model.print_trainable_parameters()
Trainer(model=model, train_dataset=ds, data_collator=collate, args=TrainingArguments(
    output_dir="/tmp/ckpt", num_train_epochs=float(os.getenv("EPOCHS", "2")), learning_rate=1e-4,
    per_device_train_batch_size=8, bf16=True, logging_steps=10, save_strategy="no", report_to=[],
    warmup_ratio=0.1, lr_scheduler_type="cosine")).train()

# 3. Merge the adapter into the base weights (a plain model vLLM can serve) and upload it
model.merge_and_unload().save_pretrained("/work/out", safe_serialization=True)
tok.save_pretrained("/work/out")
bucket, prefix = split(os.environ["OUTPUT_S3"])
for f in os.listdir("/work/out"):
    s3.upload_file(os.path.join("/work/out", f), bucket, f"{prefix.rstrip('/')}/{f}")
print(f"[done] merged model uploaded to {os.environ['OUTPUT_S3']}", flush=True)
PY

  ProductWasher      40/40
  ProductOven        40/40
  ProductDishwasher  40/40
  ProductMicrowave   40/40
  ProductAC          40/40
  Other              40/40
```
| **公制** | **微调之前（启动时）** | **微调后** |
| --- | --- | --- |
|保留精度 (280) | 235 (83.9%) | **280 (100%)** |
| `产品AC` (40) | 0/40 — 全部路由到“其他” | **40/40** |
| `其他` (40) | 35/40 | 35/40 **40/40** |
|五个既定产品类别 (200) | 200/200 | 200/200 200/200 | 200/200
|手写探针（24，接下来介绍）| 16/24 | 20/24 | 20/24

微调教会了路由器新的类别，并且不会导致五个已建立的类别回归。它还修复了启动前路由器发送到“ProductFridge”的五个“其他”错误。

因为我们的评估集与训练数据来自同一个生成器，所以我们还手工编写了 24 个探测单，其样式是生成器从未生成的。微调后的模型得分为 20/24：
```
  MISS ProductFridge -> ProductAC: The cooling fan in my fridge is squealing.
  MISS Other -> ProductAC: When will the Arctis 12K be back in stock?
  MISS Other -> ProductAC: Can I get a quote to install central air in my house?
  MISS Other -> ProductAC: Do you price match the Arctis at other stores?
overall 20/24 = 83.33%
```
它正确路由所有八个空调探针，但它学到了两个快捷方式：“冷却”意味着空调，任何提及 Arctis 的意思都是“ProductAC”，包括库存和价格匹配问题。两者都来自训练数据：标签策略将每张 Arctis 票证发送到“ProductAC”，并且捕获的流量不包含售前问题。启用新端点的捕获后，这些票证正是下一轮捕获收集的内容。

## 捕获会增加多少延迟？

我们直接测量了这一点：相同的 400 个路由请求，从 Pod 内部发送到端口 8000（无捕获）或端口 8081（通过捕获代理）。我们在 8 个并发请求下运行了三轮，再加上一轮串行请求：

| **路径** | **并发** | **第50页** | **第99页** | **吞吐量** |
| --- | --- | --- | --- | --- |
|直接进入 vLLM (8000)，无需捕获 | 8 | 200.7 毫秒 | 249.4 毫秒 | 39.1 请求/秒 |
|通过捕获代理（8081）| 8 | 200.0 毫秒 | 249.8 毫秒 | 39.1 请求/秒 |
|直接进入 vLLM (8000)，无需捕获 | 1 | 164.4 毫秒 | 206.9 毫秒 | 6.0 请求/秒 |
|通过捕获代理（8081）| 1 | 164.4 毫秒 | 207.0 毫秒 | 6.0 请求/秒 |

*并发8时的行数是三轮的平均值。逐轮变化（p50 时 ±1 毫秒）大于两条路径之间的差异。*

## 捕获数据的其他用途

推理数据到达 S3 后，相同的记录会提供给许多工作流程：

- **改进模型：** 使用监督微调（此处所示），将大型模型的输出提炼为较小的模型，或构建偏好对以进行直接偏好优化 (DPO)。
- **了解模型：** 运行 Athena 分析（如图所示），根据真实提示构建黄金回归集，设置漂移警报，发现新出现的意图，并检测格式错误的输出和拒绝。
- **操作和治理：** 将不明确的样本路由到 Ground Truth 进行标记，保留审核跟踪（建议使用第 1 层），重放事件背后的确切输入，并分析流量和有效负载以进行成本归因。

## 成本考虑

| **等级** | **大概的成本影响** |
| --- | --- |
|第 1 层（SageMaker 端点）|由 SageMaker 在端点捕获。您支付 S3 存储费用并请求有效负载 |
|第 2 层（ALB 访问日志）|仅用于日志文件的 S3 存储 |
|第 3 层（模型吊舱）|三个 sidecar 总共请求每个 pod **250m CPU + 640 MiB**（NGINX 代理 100m/128Mi、OTel 收集器 100m/256Mi、`s3-uploader` 50m/256Mi），加上 S3 存储和有效负载请求 |

两种成本随使用情况而变化：

- **S3.** 我们的记录平均每条约为 2.3 KB（9.0 MB 中有 3,955 条记录）。较长的提示和响应成本相应更高。上传者在每个 Pod 的每个刷新间隔写入一个对象，每个 Pod 每天大约 1,440 个 PUT，时间为 60 秒。
- **Athena** 按扫描的数据收费，因此始终过滤分区列，并使用“CREATE TABLE AS SELECT”(CTAS) 查询将原始 JSON 转换为 Parquet 以进行重复分析。

有关当前价格，请参阅 [Amazon S3 定价](https://aws.amazon.com/s3/pricing/) 和 [Amazon Athena 定价](https://aws.amazon.com/athena/pricing/)。

## 结论

在这篇文章中，我们展示了如何使用 SageMaker HyperPod Data Capture 记录实时推理数据并将其转换为训练数据。通过三个独立层的捕获，您可以：

- 收集真实世界的训练数据，对服务延迟没有可测量的影响。
- 使用 Amazon Athena 大规模查询推理模式，无需管理基础设施。
- 将 Athena 诊断转化为可重现的 SQL 标签策略。
- 对捕获的生产数据进行微调并测量硬前/后提升。
- 与 HyperPod 训练操作员和 SageMaker Ground Truth 集成以完成循环的其余部分。

我们在家用电器支持路由器上运行了一整圈循环。捕获的流量揭示了新产品的盲点，SQL 标签策略将这些捕获转化为训练数据。使用 HyperPod 训练操作员进行 60 秒的 LoRA 微调在为模型提供服务的同一集群上运行。它将新类别的召回率从 0% 提高到完全召回，而没有对任何现有类别进行回归。在部署模型之前，这些训练数据都不存在。

数据捕获现已在带有推理运算符的 SageMaker HyperPod 集群上可用。首先，将“dataCapture”部分添加到“InferenceEndpointConfig”或“JumpStartModel”资源中并进行部署。要关闭同一集群上的循环，请添加“amazon-sagemaker-hyperpod-training-operator”EKS 插件。本演练的完整代码位于[随附的 GitHub 存储库](https://github.com/awslabs/awsome-distributed-ai/tree/main/examples/use-cases/sagemaker-hyperpod-data-capture-flywheel)。

有关更多信息，请参阅 [SageMaker HyperPod 推理文档](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-model-deployment.html) 和 [HyperPod 训练操作员文档](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-eks-operator.html)。
