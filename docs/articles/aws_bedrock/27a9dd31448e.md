# 从数据到决策：用 Amazon Quick 和 Amazon Bedrock AgentCore 构建对话式供应链智能

*让供应链团队直接访问支撑其决策的系统。*

每条供应链都在持续产生信号：待审批的订单、不断变化的交货周期、放缓的港口、漂移的价格、各类中断。问题不在于数据稀缺，而在于数据与决策者之间的距离。

要回答"哪些营收最高的 SKU 受到当前港口关闭的影响，代价会是多少？"，过去意味着要先知道每部分数据在哪个系统里，然后在领域专家等待的同时手工拼接起来。

那位经理能不能改用自然语言提问，几秒钟内就得到一个可执行、跨系统的答案？Amazon Bedrock AgentCore 是智能层，把企业级的 Model Context Protocol (MCP) 服务器暴露为一个可组合的工具层。Amazon Quick 则把它转化为无需任何配置、面向各类角色人员的行动力。答案来自实时的记录系统和有依据的文档，而不是模型的记忆；每一处变更都要等待一位具名的真人确认。本文端到端地讲解这一模式：从 Amazon Quick 中的对话式走查，到其背后的 AgentCore 工具层，并向你展示如何自行部署。

### 一天的工作实况

一位经理的早晨，传统上要横跨 ERP（库存异常）、监控工具（告警）、采购（替代方案）、电子邮件（RFQ）以及一张追踪表：在五个系统之间花 45–60 分钟，切换十几次以上上下文。

改用对话方式，就只是一个工具里的三段提示词，"有没有影响我营收最高 SKU 的严重中断？" → "评估 TechComp 停产事件，并向已批准的替代供应商发出紧急 RFQ" → "看起来不错。发出去。"，几分钟内完成。

## 深入探讨：供应链场景走查

以下五个步骤跟踪一次中断，从发现到一份获批的紧急 RFQ，全程都在同一个 Amazon Quick 对话中完成。

### 第 1 步：发现 —— "我有哪些工具？"

用户问"我有哪些供应链工具？"，Amazon Quick 会列出发布在 AWS Agent Registry 中的供应链 MCP 服务器。因为管理员已开启注册表集成，四个业务 MCP 服务器已经以连接器卡片的形式出现，连接详情已预先填好，无需手工输入 URL。编排智能体则作为它自己的 MCP 连接器添加。

### 第 2 步：查询 —— "给我看活跃的中断"

"检查活跃的供应中断"会调用 Disruption Alerts MCP（`assess_disruption_impact`）：返回三起中断，包含严重程度、地区和 SKU 数量。*我们如何解决：Quick 通过 AgentCore 把请求路由到 MCP 服务器，后者查询后端监控并返回结构化结果，无需仪表盘或导出。*

### 第 3 步：下钻 —— "评估那起严重中断"

用户打开 TechComp Production Halt。`assess_disruption_impact(disruption_id="DISR-002")` 关联订单、客户和库存数据：75 万美元面临风险、23 个订单、三天的供应量。*我们如何解决：一次 MCP 工具调用就扇出到多个记录系统，因此经理无需碰 ERP 就能获得一份合并的影响评估。*

### 第 4 步：行动 —— "给出缓解建议"

用户请求缓解方案。`recommend_mitigation(disruption_id="DISR-002")` 串联 Governance MCP（核实已批准的替代供应商）和 Quoting MCP（与合同对齐的报价），由一个请求驱动一条完整流程。*我们如何解决：智能体规划并排序这些调用，因此一次请求就能横跨中断、治理和报价，无需人工交接。*

### 第 5 步：自动化跟进

用户随后设置主动监控（"每天早上如果有新的严重中断就提醒我"）。同样的流程也可以从一封入站供应商邮件出发无人值守地运行。*我们如何解决：同一个智能体和工具集按计划或邮件触发器运行，把可供审核的卡片发布到 Activity Feed，由人来批准。*

## Amazon Bedrock AgentCore：智能层

Amazon Bedrock AgentCore 是一个模块化的智能体平台，用于安全地大规模构建、部署和运维智能体。它提供的能力超出我们在此使用的范围。其中四项服务与本模式相关：

- Runtime —— 面向 MCP 服务器和智能体的无服务器托管，具备会话隔离和内置身份。
- Gateway —— 把 API、AWS Lambda 函数和服务转换为 MCP 兼容的工具，置于一个安全托管端点之后，从而标准化工具访问。推理由发起调用的智能体负责。
- Identity —— 身份验证与凭证管理，兼容已有的身份提供方。
- Policy —— 用自然语言或 Cedar 编写的确定性授权规则，在执行前拦截每一次工具调用，让智能体在采购和财务数据上守好本分。

### MCP 协议：工具之间如何通信

MCP 是一个开放标准，规定了 AI 模型如何与外部工具交互。每个服务器暴露的工具都带有类型化参数：

```
{
  "server_name": "sc-disruption-alert-gateway",
  "tools": [{
    "name": "assess_disruption_impact",
    "parameters": {
      "disruption_id": {"type": "string"},
      "context": {"type": "object"} // order, inventory, revenue data
    }
  }] // plus classify_severity, recommend_mitigation, get_escalation_chain
}
```

这意味着：

- AI 客户端（Quick、自定义智能体、其他 MCP 应用）可以消费同样的服务器。
- 后端（SAP、Oracle、自定义微服务）可以被封装为一个 MCP 服务器。
- 工具发现是自动的。客户端在运行时向注册表查询 schema。

### AWS Agent Registry：发现层

注册表是受治理的发现层：发布者提交一条记录，策展人批准它，只有到那时它才能通过混合搜索、浏览或注册表的 MCP 端点被发现。有一点规模化方面的现实值得注意：由于 schema 是在运行时发现的，应把每一个都当作契约，在发生破坏性变更时让新旧版本并存。

### 多步编排

推理层是运行在 AgentCore Runtime 上的一个智能体，通过 Custom MCP 连接器在其直接调用 URL 上有一条智能体记录，不用 Lambda 也不用网关。在这里，它就是 Order Fulfillment Agent。接到一个请求后，它规划要调用哪些工具以及调用顺序：

```
User: "A supplier just went down. Find alternatives, verify compliance, issue an emergency RFQ."
Disruption Alerts MCP -> identify the disruption
Governance MCP -> approved alternatives + compliance + budget authority
Quoting MCP -> contract-aligned quote
-> one consolidated recommendation
```

## Amazon Quick：企业级 AI 助手

Amazon Quick 通过聊天、智能体、Activity Feed 和自动化工作流，把 AgentCore 工具呈现在业务用户面前，无需任何技术配置。

### 使用的关键组件

| **组件** | **在本模式中的角色** | **工作方式** |
| --- | --- | --- |
| Agent Registry 连接 | 把 MCP 服务器呈现为连接器 | 管理员关联一次注册表。记录即成为连接器卡片 |
| Quick Agent | 一个可适应角色的 SC 智能体 | 针对角色（经理、采购、分析师）定制 |
| MCP 连接器 | 在聊天中暴露 MCP 工具 | 一张卡片连接器即可在 Chat、智能体、计划任务中暴露工具 |
| Activity Feed | 主动提醒与操作 | 智能体发布卡片。用户据此行动 |
| Schedules | 基于自然语言的周期性自动化 | 例如“每天早上” |
| Outlook 集成 | 把邮件带入信息流 | 供应商回复会被解析并校验 |
| 结构化数据连接器 | 查询运营记录 | Quick 查询 Space 数据集（订单、库存、供应商、合同）以执行 MCP 规则检查 |
| Amazon Simple Storage Service (Amazon S3) 知识库 | 在文档上做检索 | 发票、合同、策略放在 S3 知识库中，通过 Retrieval Augmented Generation (RAG) 为答案提供依据 |
| CRM 连接器（可选） | 读取客户记录（可选） | CRM（例如 Salesforce）的账户、商机、联系人。也可以加载到数据集中 |

## 自动化的 Activity Feed 与主动监控

*Activity Feed* 是 Amazon Quick 的主动式界面，一个统一的收件箱，智能体在其中发布结果、告警和建议。信息流中的条目是：

- 可执行的，每一条都带有上下文和下一步操作。
- 经 AI 分诊的，带有优先级指示（需要回复、待跟进、截止日期）。
- 跨来源的，横跨电子邮件、计划任务、智能体运行和外部系统。
- 人在环中的，智能体提建议，人来决定。

### 自动监控如何工作

AgentCore 工具加上 Amazon Quick 的主动能力，提供两条路径——基于时间和由邮件驱动——它们共用同一条“触发器 → 智能体 → 输出”的管道。

![Three-stage pipeline from a schedule or email trigger to an autonomous agent to a review-ready card](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/14/ML-22042-7-1.png)

图 7：从触发器（计划任务或邮件）到自主智能体（assess_disruption_impact、check_supplier_approval、apply_approval_rules、validate_quote）再到可供审核卡片的三阶段管道

### 用例：校验来自邮件的供应商回复

供应商通过电子邮件回复紧急 RFQ，附上报价。智能体逐一校验（是否为已批准供应商？是否在指引范围内？）并暂存结果。它不会起草报价、不挑选赢家，也不开采购订单（PO）。

**阶段 1：配置（一次性，约 5 分钟）**

- **连接 Outlook**：在 Amazon Quick 中，选择 **Settings** → **Connections** → **Add Outlook**。
- **配置 Activity Feed**：在信息流偏好设置中开启邮件监控。
- **创建 SC Agent**：用以下指令构建一个智能体：

```
Supply chain procurement assistant. On a supplier RFQ reply with pricing: 1) extract SKU(s), quantities, pricing; 2) validate approved vendor (Governance MCP); 3) check pricing within guidelines (Quoting MCP); 4) post a review-ready card (approved-supplier, within-guidelines); do NOT draft a PO or select a supplier.
```

- **创建计划任务**：“在工作时间内每 2 小时检查一次新的供应商回复并加以校验。”

**阶段 2：运行时（完全自动化）**

```
Schedule -> email from "TechSupply Co" (MCU-7200, 10,000 units @ $2.45/unit) -> Governance MCP: approved? | Quoting MCP: within guidelines? -> "Supplier Response - Ready for Review" card
```

信息流卡片带有校验结果和决策相关的事实：

| **供应商回复：可供审核** | **详情** |
| --- | --- |
| **供应商** | TechSupply Co，✅ 已批准供应商 |
| **SKU / 数量 / 价格** | MCU-7200 · 10,000 units · $2.45/unit |
| **价格检查** | ✅ 在采购指引范围内 |
| **操作** | 选择用于 PO · 比较回复 · 拒绝 |

**阶段 3：人在环中**

审核人比较已校验的回复，要么选定一家供应商并开出 PO，要么拒绝并记录原因。选定供应商和开 PO 始终由人来完成。

### 用例：主动式中断监控

由计划任务触发，同样的模式也适用：每天早上 8:30 运行的智能体会检查是否有新的严重或高严重度中断，评估影响，把供应量不足七天的项目标记为 URGENT，并发布一张带“发起紧急 RFQ”操作的告警卡片。

## 这与传统 BI 如何共存

| **维度** | **传统商业智能（BI）/仪表盘** | **AgentCore + Amazon Quick** |
| --- | --- | --- |
| **访问方式** | 导航、登录、找到仪表盘/报表 | 用自然语言提问。系统自己找到数据源 |
| **洞察耗时** | 数分钟到数小时（查找 → 筛选 → 导出 → 关联） | 数秒（提问 → 带跨系统上下文的答案） |
| **多系统关联** | 手工：3-4 个标签页、复制粘贴 | 自动：智能体从一次查询出发跨 MCP 服务器编排 |
| **行动断层** | 在一个工具里获得洞察 → 切到另一个工具行动 | 洞察 → 在同一段对话中行动 |
| **搭建成本** | 数周/数月（仪表盘设计、ETL、权限、培训） | 分钟级连接，前提是 MCP 服务器已存在 |
| **运行成本** | 固定：不管有没有人问，管道都要花同样的钱 | 按用量计费：无服务器可缩容到零，成本跟随问题数量（Lambda + 智能体 token） |
| **可信度与准确性** | 与上一次 ETL 加载同样新 | 从记录系统和有依据的文档实时计算，每次写入都有人工把关 |

这并非“取代一切”的论调。仪表盘在趋势可视化、协作分析、监管报告和探索性分析方面仍然更优。用对话式 AI 做实时运营决策，用 BI 做战略分析。它们互补，而非竞争。

## 角色与用例

一个 Quick Agent 服务全部三类角色：经理维持连续性，采购以合规意识寻找货源，分析师关联各类信号。角色同时界定触达范围，通过行/列级安全和按角色的 MCP 工具范围限定，使采购看不到财务数据。

| **角色** | **用例** | **调用的工具** | **结果** |
| --- | --- | --- | --- |
| **SC Manager** | 每日中断检查 | Disruption Alerts MCP | 中断情况、风险营收、供应天数 |
| **SC Manager** | 紧急采购 | Governance → Quoting MCP | 经核实的替代方案 + RFQ，一条流程 |
| **采购** | 供应商核实、预算权限 | Governance MCP | 审批、合规、限额 |
| **采购** | RFQ 生成与回复校验 | Quoting MCP | RFQ 已发出 + 回复已校验 |
| **Ops Analyst** | 跨系统关联 | SC Operations Agent | 多 MCP 推理，一次查询 |
| **Ops Analyst** | 付款队列、审计、中断趋势 | Invoice / Governance MCP | 应付账龄、审计日志、模式 |

## 开始使用

部署这个模式分三个阶段：预配基础设施，把 Amazon Quick 连接到你的数据和注册表，然后开启监控。

### 先决条件

开始之前：

- 一个具备 Amazon Bedrock AgentCore 和 AWS Agent Registry 的 AWS 账户。
- AWS Command Line Interface (AWS CLI) v2、AWS Serverless Application Model (AWS SAM) CLI 和 Docker（智能体以 arm64 容器运行）。
- Python 3.12 或更高版本，以及用于注册表步骤的 Boto3 1.43.94 或更高版本。
- 有效的凭证，具备部署和注册所需的 AWS Identity and Access Management (IAM) 权限（`aws sts get-caller-identity` 返回目标账户）。
- 数据层：一个数据库（Snowflake、PostgreSQL/RDS 或 SQLAlchemy 引擎）、一个 Amazon S3 存储桶，可选一个 Salesforce 组织。
- 为你的组织配置好 Amazon Quick。
- （可选）一个用于邮件自动化的 Outlook 账户。

配置涉及两个界面，因此下面每一步都会说明它在何处进行：浏览器中的 **Amazon Quick Web 控制台**（Amazon Quick Sight 权限、Agent Registry 关联、连接器与智能体设置）以及 **Quick Desktop App**（连接 Outlook 以支持邮件自动化）。Desktop App 中的对话体验放在最后，等配置完成后再说。

### 部署基础设施

一切都是开源的、脚本化的：克隆 aws-samples/sample-amazon-quick-suite-knowledge-hub 仓库中的 [quick-for-supply-chain](https://github.com/aws-samples/sample-amazon-quick-suite-knowledge-hub/tree/main/examples/quick-for-supply-chain) 示例并遵循其 `README.md`，或者让类似 Kiro 的编码智能体照着做。

`README.md` 涵盖三个阶段。阶段 1 部署 AgentCore 堆栈：身份层（一个 Amazon Cognito 用户池和应用客户端、授权码 OAuth 流程，外加一个测试用户）、四个业务规则 MCP 服务器（每个都是一个 AWS Lambda 函数，前面各有一个 AgentCore Gateway——Amazon Bedrock AgentCore 的一项能力——使用 `CUSTOM_JWT` 授权）、映射每个 Lambda 函数工具的网关目标，以及在 AgentCore Runtime 上以容器形式运行的 `sc-order-fulfillment-agent`，并配以最小权限的 IAM 角色。阶段 2 把合成数据集上传到 Amazon S3。阶段 3 验证各网关和运行时处于 Ready 状态。六条 Agent Registry 记录获批。

### 关联注册表并创建连接器

关联注册表是一次性的管理员级操作。创建连接器是按用户进行的。两者都在 Amazon Quick 控制台中完成。参见 AWS Agent Registry 集成指南。

#### 关联注册表（管理员，一次性）

管理员把一个 Agent Registry 关联到 Quick 账户。**在 Amazon Quick Web 控制台（管理员）中：**前往 Manage account → Permissions → AWS Agent Registry，并开启该注册表（`sc-supply-chain-registry`，每个账户一个）。只有位于你所在账户和区域、agent-registry 命名空间、AWS_IAM (SigV4) 授权且状态为 READY 的注册表才会出现。由 Quick 托管的服务角色完成关联。

#### 创建连接器

注册表关联后，已批准的 MCP 服务器记录会变成连接器卡片：四个业务 MCP 作为卡片，订单履约智能体则手动添加。规模化时，可通过你的身份提供方联合连接器身份验证，并按组预配连接器，以 Cognito 用户池作为接缝。

**在 Amazon Quick Web 控制台（按用户）中：**四张卡片会出现在 Connectors 页面上（`sc-quoting-mcp`、`sc-governance-mcp`、`sc-invoice-processing-mcp`、`sc-disruption-alert-mcp`）。通过 OAuth 授权码流程（`OAUTH2_AUTHORIZATION_CODE`）完成身份验证，使用部署脚本提供的客户端 ID、密钥以及 token、授权和重定向 URL。以测试用户身份登录，开启工具，创建并共享。

### 把连接器挂到你的智能体上

部署过程会创建 Supply Chain 智能体：一个 Quick Space、导入的数据集和 S3 知识库，以及带有指令、起始提示词和欢迎语的智能体。剩下的就是把连接器挂上去。

**在 Amazon Quick Web 控制台（智能体设置）中：**打开部署创建的 Supply Chain 智能体（默认 id 为 `sc-supply-chain-agent`），挂上全部五个连接器（四个业务 MCP 加上 `sc-order-fulfillment-agent`），或者把五个连接器 ID 传给安装脚本。

### 配置主动监控

要让它主动起来，Quick 会按计划或在收到邮件时运行同一个智能体，并把结果发布到 Activity Feed。两条路径都复用你配置好的智能体和工具。

**在 Quick Desktop App 中（Settings → Connections）：**连接 Outlook 并开启邮件监控。然后在 Quick Chat 中创建两条自然语言计划任务，一条基于时间（“每天早上检查是否有新的严重中断”），一条由邮件驱动（“工作时间内每两小时检查供应商回复并校验”）。智能体会提取报价、执行检查并发布一张卡片。

### 在 Amazon Quick 中试用

智能体和连接器就绪后，在 Amazon Quick Chat 中用自然语言提问。每条提示词都体现了“先取数据、再套规则”的模式。

| **向 Amazon Quick 提问** | **你会得到什么** |
| --- | --- |
| “What supply chain tools do I have?” | 五个 MCP 连接器（报价、治理、发票、中断告警、订单履约智能体）及其状态。 |
| “Show me active supply disruptions.” | 活跃中断及其严重程度、地区、SKU 数量（Disruption Alerts MCP）。 |
| “Assess the impact of the TechComp production halt.” | 来自你数据集的面临风险的营收、受影响订单、供应天数。 |
| “Is this supplier an approved vendor, and do we have budget authority for a $72,000 PO?” | Governance MCP 给出的审批结论（供应商状态、预算权限、合规）。 |
| “Generate a contract-aligned quote for 1,000 units for this customer.” | Quoting MCP 给出的与合同对齐的报价，以品牌化文档形式呈现。 |
| “A supplier just went down. Find alternatives, verify compliance, and issue an emergency RFQ.” | Order Fulfillment Agent 把中断、治理和报价 MCP 串成一份建议。 |

## 结论

AgentCore 与 Amazon Quick 构成一个可复用的企业 AI 模式：把智能与界面分离。AgentCore 通过标准 MCP 接口，把碎片化的后端变成一个可组合、受治理、AI 可访问的层。Amazon Quick 用自然语言实现了访问的普及化。

收益在于被压缩的决策链：发现、调研、决策、行动、记录，过去横跨五个工具，如今只需一段对话。AI 负责调研、关联、校验。人负责决策。每一次调用都经过身份验证、授权、策略检查和审计，原本横跨五个系统、耗时 45-60 分钟的例行工作可以压缩到几分钟。

这就是从“数据丰富、洞察贫乏”到“数据丰富、决策就绪”的转变。从一个 MCP 服务器和一个角色开始。注册表会成长，而体验保持不变。
