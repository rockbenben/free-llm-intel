# 从数据到决策：使用 Amazon Quick 和 Amazon Bedrock AgentCore 实现对话式供应链智能

*让供应链团队能够直接访问其决策背后的系统。*

每个供应链都会产生持续的信号：批准的订单、交货时间的变化、港口放缓、价格波动、中断。问题不在于数据稀缺。这是数据和决策者之间的距离。

回答“哪些收入最高的 SKU 会受到当前端口关闭的影响，其成本是多少？”过去意味着知道哪个系统保存每个部分并在领域专家等待时手工将它们缝合在一起。

该经理是否可以用简单的语言提问并在几秒钟内得到可操作的跨系统答案？ Amazon Bedrock AgentCore 是智能层，将企业模型上下文协议 (MCP) 服务器公开为可组合工具层。 Amazon Quick 将其转化为角色的行动，无需任何设置。答案来自实时记录系统和基础文档，而不是模型回忆，每一个变化都等待指定的人。在这篇文章中，我们从 Amazon Quick 中的对话演练到其背后的 AgentCore 工具层，从头到尾地演练此模式，并向您展示如何自行部署它。

## 深入探讨：供应链场景演练

以下五个步骤遵循从检测到批准的紧急询价的一次中断，所有这些都在一个 Amazon Quick 对话中完成。

### 第 1 步：发现 – “我有什么工具？”

用户问“我有什么供应链工具？” Amazon Quick 列出了 AWS Agent Registry 中发布的供应链 MCP 服务器。由于管理员已打开注册表集成，因此四个业务 MCP 服务器已显示为连接器卡，其中已预先填充连接详细信息，并且无需手动输入 URL。编排代理作为其自己的 MCP 连接器添加。

### 步骤 2：查询 – “显示活跃的中断”

“检查主动供应中断”调用中断警报 MCP (`assess_disruption_impact`)：三种中断，包括严重程度、区域和 SKU 计数。 *我们如何解决：通过AgentCore将请求快速路由到MCP服务器，该服务器查询后端监控并返回结构化结果，无需仪表板或导出。*

### 步骤 3：深入分析 – “评估关键问题”

用户打开 TechComp 生产暂停。 `assess_disruption_impact(disruption_id="DISR-002")` 关联订单、客户和库存数据：75 万美元的风险、23 个订单、三天的供应。 *我们如何解决这个问题：一个 MCP 工具呼叫在记录系统中分散，因此经理无需接触 ERP 即可获得综合影响读取。*

### 步骤 4：行动 – “获取缓解建议”

用户请求缓解。 `recommend_mitigation(disruption_id="DISR-002")` 链接治理 MCP（验证批准的替代方案）和引用 MCP（合同一致的报价），一个请求的一个流程。 *我们如何解决这个问题：座席对呼叫进行计划和排序，因此一次询问即可涵盖中断、治理和报价，无需手动交接。*

### 第 5 步：自动跟进

然后，用户设置主动监控（“如果出现新的严重中断，每天早上提醒我”）。相同的流程可以在无人值守的情况下从入站供应商电子邮件运行。 *我们如何解决这个问题：相同的代理和工具按计划或电子邮件触发器运行，将审核就绪卡发布到活动源以供人员批准。*

## Amazon Bedrock AgentCore：智能层

Amazon Bedrock AgentCore 是一个模块化代理平台，用于大规模安全地构建、部署和操作代理。它提供的比我们在这里使用的更多。它的四个服务与此模式相关：

- 运行时 – MCP 服务器和代理的无服务器托管，具有会话隔离和内置身份。
- 网关 – 将 API、AWS Lambda 函数和服务转变为安全托管端点后面与 MCP 兼容的工具，从而标准化工具访问。推理是呼叫代理的。
- 身份 – 身份验证和凭证管理，与现有身份提供商兼容。
- 策略——确定性授权规则，以自然语言或 Cedar 编写，在执行前拦截每个工具调用，使代理保持在采购和财务数据的轨道上。

### MCP 协议：工具如何通信

MCP 是关于 AI 模型如何与外部工具交互的开放标准。每个服务器都公开带有类型参数的工具：
```
{
  "server_name": "sc-disruption-alert-gateway",
  "tools": [{
    "name": "assess_disruption_impact",
    "parameters": {
      "disruption_id": {"type": "string"},
      "context": {"type": "object"} // order, inventory, revenue data
    }
  }] // plus classify_severity, recommend_mitigation, get_escalation_chain
}
```
这意味着：

- AI 客户端（快速、自定义代理、其他 MCP 应用程序）可以使用相同的服务器。
- 后端（SAP、Oracle、自定义微服务）可以包装为 MCP 服务器。
- 工具发现是自动的。客户端在运行时查询注册表以获取模式。

### AWS 代理注册表：发现层

注册表是受管理的发现层：发布者提交记录，管理者批准它，然后才能通过混合搜索、浏览或注册表的 MCP 端点来发现它。值得注意的是一个规模的现实：因为模式是在运行时发现的，所以将每个模式视为契约，将新版本与旧版本一起进行重大更改。

### 多步骤编排

推理层是 AgentCore Runtime 上的代理，是通过自定义 MCP 连接器直接调用 URL 的代理记录，没有 Lambda 或网关。在这里，它是订单履行代理。给定一个请求，它会计划调用哪些工具以及以什么顺序：
```
User: "A supplier just went down. Find alternatives, verify compliance, issue an emergency RFQ."
Disruption Alerts MCP -> identify the disruption
Governance MCP -> approved alternatives + compliance + budget authority
Quoting MCP -> contract-aligned quote
-> one consolidated recommendation
```

## 自动活动源和主动监控

* 活动源* 是 Amazon Quick 的主动界面，这是一个统一的收件箱，客服人员可以在其中发布结果、警报和建议。饲料项目有：

- 可操作的，每项都包含上下文和下一步行动。
- 人工智能分类，带有优先级指标（需要回复、跟进、截止日期）。
- 跨源、跨电子邮件、时间表、代理运行和外部系统。
- 人机交互，由代理提出建议并由人类决定。

### 自动监控的工作原理

AgentCore 工具加上 Amazon Quick 的主动功能，通过通用触发器 → 代理 → 输出管道，提供了两种路径：基于时间的路径和电子邮件驱动的路径。

### 用例：验证供应商的电子邮件回复

供应商通过电子邮件回复紧急询价并附上价格。代理验证每个（批准的供应商？符合指南？）并暂存结果。它不会撰写报价、挑选获胜者或发出采购订单 (PO)。

**第 1 阶段：设置（一次性，大约 5 分钟）**

- **连接 Outlook**：在 Amazon Quick 中，选择 **设置** → **连接** → **添加 Outlook**。
- **配置活动源**：在源首选项中打开电子邮件监控。
- **创建 SC 代理**：使用以下说明构建代理：
```
Supply chain procurement assistant. On a supplier RFQ reply with pricing: 1) extract SKU(s), quantities, pricing; 2) validate approved vendor (Governance MCP); 3) check pricing within guidelines (Quoting MCP); 4) post a review-ready card (approved-supplier, within-guidelines); do NOT draft a PO or select a supplier.
```
- **创建时间表**：“工作时间内每 2 小时检查一次新的供应商回复并验证它们。”

**阶段 2：运行时（完全自动化）**
```
Schedule -> email from "TechSupply Co" (MCU-7200, 10,000 units @ $2.45/unit) -> Governance MCP: approved? | Quoting MCP: within guidelines? -> "Supplier Response - Ready for Review" card
```
Feed 卡包含验证结果和决策相关事实：

| **供应商回应：准备审核** | **详情** |
| --- | --- |
| **供应商** | TechSupply Co, ✅ 批准的供应商 |
| **SKU/数量/价格** | MCU-7200 · 10,000 件 · 2.45 美元/件 |
| **价格检查** | ✅ 符合购买指南 |
| **行动** |选择采购订单 · 比较回复 · 拒绝 |

**阶段 3：人机交互**

审核者比较经过验证的响应，然后选择供应商并发出采购订单，或者拒绝并记录原因。选择和 PO 留在一个人身边。

### 使用案例：主动中断监控

由计划触发，同样的模式适用：每天上午 8:30 代理检查是否有新的严重或高严重性中断，评估影响，将供应不足 7 天内的任何情况标记为“紧急”，并发布带有“发出紧急询价”操作的警报卡。

## 开始使用

部署该模式需要三个阶段：配置基础设施、将 Amazon Quick 连接到您的数据和注册表，以及打开监控。

### 先决条件

开始之前：

- 具有 Amazon Bedrock AgentCore 和 AWS Agent Registry 的 AWS 账户。
- AWS 命令​​行界面 (AWS CLI) v2、AWS 无服务器应用程序模型 (AWS SAM) CLI 和 Docker（代理作为 arm64 容器运行）。
- Python 3.12 或更高版本，Boto3 1.43.94 或更高版本用于注册表步骤。
- 具有 AWS Identity and Access Management (IAM) 部署和注册权限的活动凭证（“aws sts get-caller-identity”返回目标账户）。
- 数据层：数据库（Snowflake、PostgreSQL/RDS 或 SQLAlchemy 引擎）、Amazon S3 存储桶、可选的 Salesforce 组织。
- 为您的组织快速设置亚马逊。
- （可选）用于电子邮件自动化的 Outlook 帐户。

安装程序使用两个界面，因此以下每个步骤都会在其发生位置进行命名：浏览器中的 **Amazon Quick Web 控制台**（Amazon Quick Sight 权限、代理注册表链接、连接器和代理设置）和 **Quick Desktop App**（连接 Outlook 以实现电子邮件自动化）。设置完成后，桌面应用程序中的对话体验排在最后。

### 部署基础设施

一切都是开源和脚本化的：克隆 aws-samples/sample-amazon-quick-suite-knowledge-hub 存储库中的 [quick-for-supply-chain](https://github.com/aws-samples/sample-amazon-quick-suite-knowledge-hub/tree/main/examples/quick-for-supply-chain) 示例并遵循其“README.md”，或将像 Kiro 这样的编码代理指向它。

`README.md` 涵盖三个阶段。第 1 阶段部署 AgentCore 堆栈：身份层（一个 Amazon Cognito 用户池和应用程序客户端、授权代码 OAuth 流以及一个测试用户）、四个业务规则 MCP 服务器（每个服务器都有一个 AWS Lambda 函数，由自己的 AgentCore 网关、Amazon Bedrock AgentCore 的功能、使用“CUSTOM_JWT”授权）、网关目标映射每个 Lambda 函数的工具以及 AgentCore Runtime 上的“sc-order-fulfillment-agent”作为容器，权限最小的 IAM 角色。第 2 阶段将合成数据集上传到 Amazon S3。第 3 阶段验证网关和运行时是否就绪。六项代理登记记录已获得批准。

![AWS Agent Registration 控制台显示六项已批准的记录：四台 MCP 服务器、一台代理和一项技能记录](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/14/ML-22042-8-1.png)

### 链接注册表并创建连接器

链接注册表是一次性的且是管理员级别的。创建连接器是针对每个用户的。两者都发生在 Amazon Quick 控制台中。请参阅 AWS Agent Registry 集成指南。

#### 链接注册表（管理员，一次性）

管理员将一个代理注册表链接到 Quick 帐户。 **在 Amazon Quick Web 控制台（管理员）中：** 转至管理账户 → 权限 → AWS 代理注册表并打开注册表（“sc-supply-chain-registry”，每个账户一个）。仅显示您的账户和区域中的注册表、代理注册表命名空间、AWS_IAM (SigV4) 授权和 READY 状态。快速管理服务角色将其链接起来。

![注册表链接屏幕仅显示 READY、AWS_IAM 注册表可供选择](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/14/ML-22042-10-1.png)

图 10：链接注册表，其中仅可选择 READY、AWS_IAM 注册表

#### 创建连接器

链接注册表后，批准的 MCP 服务器记录将成为连接器卡：四个业务 MCP 作为卡，由订单履行代理手动添加。大规模地，通过您的身份提供商联合连接器身份验证，并将连接器配置到组，并以 Cognito 用户池作为接缝。

**在 Amazon Quick Web 控制台中（每个用户）：** 四张卡显示在连接器页面上（`sc-quoting-mcp`、`sc-governance-mcp`、`sc-invoice-processing-mcp`、`sc-disruption-alert-mcp`）。使用客户端 ID、机密和令牌、授权以及来自部署脚本的重定向 URL 通过 OAuth 授权代码流 (`OAUTH2_AUTHORIZATION_CODE`) 进行身份验证。以测试用户身份登录，打开工具，创建和共享。

**在 Amazon Quick Web 控制台中：**因为它是代理记录，所以手动创建其连接器（连接器 → 为您的团队创建 → 模型上下文协议 → 新建）：将其命名为 `sc-order-fulfillment-agent`，将其指向部署脚本中的 AgentCore 运行时直接调用 URL，完成相同的 OAuth 登录、创建和共享。

### 将连接器连接到您的代理

部署将创建供应链代理：Quick Space、导入的数据集和 S3 知识库，以及带有说明、入门提示和欢迎消息的代理。剩下的就是连接连接器。

**在 Amazon Quick Web 控制台（代理设置）中：** 打开部署创建的供应链代理（默认 ID `sc-supply-chain-agent`）并附加所有五个连接器（四个业务 MCP 加上 `sc-order-fulfillment-agent`），或将五个连接器 ID 传递给设置脚本。

### 设置主动监控

为了使其主动，Quick 按计划或传入电子邮件运行相同的代理，并将结果发布到活动源。两条路径都会重复使用您配置的代理和工具。

**在快速桌面应用程序中（设置 → 连接）：** 连接 Outlook 并打开电子邮件监控。然后，在“快速聊天”中，创建两个自然语言时间表，基于时间的（“每天早上，检查新的严重中断”）和电子邮件驱动的（“工作时间内每两个小时，检查供应商回复并验证”）。代理提取定价、运行检查并发布卡片。

### 在 Amazon Quick 中尝试一下

代理和连接器准备就绪后，可以在 Amazon Quick Chat 中用自然语言提问。每个提示都显示数据然后规则模式。

| **快速询问亚马逊** | **你得到什么** |
| --- | --- |
| “我有哪些供应链工具？” |五个 MCP 连接器（报价、治理、发票、中断警报、订单履行代理）以及状态。 |
| “让我看看活跃的供应中断情况。” |主动中断的严重程度、区域、SKU 计数（中断警报 MCP）。 |

## 结论

AgentCore 和 Amazon Quick 是一种可重复的企业人工智能模式：将智能与界面分开。 AgentCore 通过标准 MCP 接口将分散的后端转变为可组合、受治理、AI 可访问的层。 Amazon Quick 实现了自然语言访问的民主化。

收益是崩溃的决策链：检测、研究、决策、行动和日志曾经跨越五种工具，现在跨越一种对话。人工智能进行研究、关联、验证。人决定。每个呼叫都经过身份验证、授权、策略检查和审核，跨五个系统的 45-60 分钟例程可以缩短到几分钟。

这就是从数据丰富、洞察力匮乏到数据丰富、决策就绪的转变。从一台 MCP 服务器和一个角色开始。注册表不断增长，但体验保持不变。
