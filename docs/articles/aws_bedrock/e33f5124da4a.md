# Tamnoon 如何基于 Amazon Bedrock 构建 AI 驱动的云安全修复

关键的云暴露（exposure）堆积得比安全团队能关闭它们的速度更快。云原生应用保护平台（CNAPP）、云服务商以及安全态势扫描器产生的发现项（finding），数量超出任何团队所能分诊的上限，而风险就积累在「已检出」与「已修复」之间的那道缝隙里。绝大多数发现项无人问津，并不是因为它们难以修复。得有人去调查上下文、找出资源负责人、确认这个修复不会把生产环境搞挂，然后还要以超出人力规模的数量把它们做完。

在这篇文章里，我们会分享 [Tamnoon](https://www.tamnoon.io/) 如何在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 之上构建 Tami——一个 agentic 的云修复编排器——来弥合这道缝隙。Tami 会自主调查从 CNAPP 和云原生来源摄入的发现项，并评估修复是否安全。随后，在变更触及客户云的地方，它会带着护栏与治理来生成并编排这个修复。这一做法[把关键云暴露降低了 90% 以上](https://tamnoon.io/blog/how-tamnoon-rebuilt-cloud-remediation/)，用时 90 天，且零生产事故。

## 关于 Tamnoon

Tamnoon 是一个 AI 驱动的云安全修复平台，与 CNAPP 协同工作。它的 AI 助手 Tami 帮助人类云安全专家在客户环境——AWS、Azure、Google Cloud 以及其他云服务商——中调查、排出优先级，并安全地修复错误配置和问题。

Tamnoon 与团队已经在用的 CNAPP 和云原生工具集成，并把它们的发现项转化为经过校验、生产安全的修复。包括调查、优先级排序和修复规划在内的大部分工作，都发生在任何东西触达线上环境之前，这正是自动化修复能在规模化前提下值得信赖的原因。

## 云安全修复的挑战

一名安全工程师可能花上几个小时来调查一个发现项。而很多时候，它和另外几十个告警追溯到的其实是同一个根因。

- 告警数量压过人力：CNAPP 和扫描器会产生数千条发现项。团队无法把它们全部分诊，于是关键暴露悬而未决，风险持续累积数月。
- 调查靠人工且高度重复：每一条发现项都需要收集上下文——谁拥有这个资源、什么依赖它、修复是否安全。这会消耗资深工程师数小时，并且要对积压队列里的每一项重复一遍。
- 对生产影响的恐惧阻碍了自动化：团队不敢把修复自动化，因为他们拿不起「把生产环境搞挂」这个风险。没有「这个修复是安全的」这种信心，任何事情都不会推进。
- 被动式的优先级排序：没有办法把相关发现项聚类、也没有办法给修复置信度打分，团队只能线性地一条条处理告警，而不是去解决那个能一次消解很多问题的根因。

Tamnoon 的方案覆盖从发现项摄入到经过校验的修复这整条管线。平台把这些挑战视为相互关联的问题，而不是彼此孤立的问题。

## 方案总览

Tamnoon 带你从最初的发现项一路走到执行修复。平台从 CNAPP、云安全态势管理（CSPM）服务商和其他安全工具摄入发现项，把它们归一化成统一的 schema。接着用资产和暴露上下文对它们做富化，并排出优先级。此后由 agentic 层接管，使用一组各司其职的专用 AI agent，每个 agent 都运行在 AWS 上事件驱动、serverless 的架构中，因此每个阶段都能独立扩缩、并且安全地失败。

### Amazon Bedrock 上的 agentic 架构

平台把工作分派给四个专用 agent，每个 agent 负责修复管线中一个独立的阶段：

- 调查 agent 借助从数百万真实客户云环境中学到的训练来确定上下文，并通过一层大语言模型（LLM）as-a-judge 的校验层来过滤这些上下文。它会就修复目标、运维范围以及云服务商特定的验证方式进行推理，产出只读的调查步骤和一份完整的调查计划。
- 安全评分 agent 为每个资产构建一条证据链，把自动化验证结果和分析师的结论结合起来。它会把每条发现项的修复归类为 SAFE、RISKY 或 AWAITING DATA，并带有刻意保守的倾向。拿不准时，它就降级。
- 修复 agent 只对安全 agent 判定为安全的发现项启动。它会对顺序、依赖关系和条件进行推理，然后产出一份修复计划，其中每一步都遵循「备份、修复、验证」的结构，并包含回滚指引。
- 代码生成 agent 把计划步骤转化为可执行的修复动作，但前提是输入护栏先筛查过相关性与 prompt injection。每一件产物都要过一个自动化的生成—复核循环，其中必须由另一个独立的 reviewer agent 批准输出。

### 为什么选择 Amazon Bedrock

当 Tamnoon 团队着手构建 Tami 时，基础模型（FM）平台的选择会决定之后的一切。Tamnoon 的修复 agent 做的并不是同一类工作。有些要做深度调查推理，以理解一条安全发现项的根因；另一些处理高吞吐量的校验，快速而廉价地检查待执行的修复；还有一些要审阅生成的代码，在每一项任务上权衡质量与成本。把这些工作各自匹配到合适的模型，同时不为每一个模型单独拼一套集成——这是一条核心要求。

正是这条要求让 Amazon Bedrock 成为自然之选。通过单一 API，每个 agent 都能调用最适合其任务的基础模型。能力最强的模型承担最难的推理；更经济的模型接手重复性高、吞吐量大的工作；面向复核的模型则优化输出质量与成本之间的取舍。因为是一套集成而不是很多套，模型可以随技术版图演进而替换或升级，不必每次都重新铺设架构。

规模化之下的运维开销是决策中的另一个因素。随着请求量增长，Tamnoon 希望避免自己构建并维护一套在区域容量之间分配流量的逻辑。Amazon Bedrock 跨区域推理（Cross-Region inference）自动处理了这件事。它会把推理请求自动路由到所定义的地理边界内的最优 AWS Region，在无需任何自定义路由代码运行的情况下维持吞吐量。

安全性是最后一条考量，而对一家云安全公司来说它没有商量余地。用 Bedrock 时，推理运行在 Tamnoon 自己的 AWS 环境之内，受 AWS Identity and Access Management（IAM）范围化权限的约束。敏感客户数据从不离开信任边界。这让团队有底气相信，支撑 Tami 的这套平台达到了 Tamnoon 对自己服务所要求的同一标准。

### Tamnoon 如何与 CNAPP 和云安全工具集成

Tamnoon 位于安全团队已经在运行的检测工具的下游。Wiz、CrowdStrike、Palo Alto Cortex、Upwind、SentinelOne、Orca、Cyera 这样的 CNAPP，以及 AWS Security Hub、Amazon GuardDuty 这样的云原生服务，才是「环境里哪里有问题」的事实来源。Tamnoon 通过基于 API 的集成连接它们，并把发现项归一化成统一的格式，于是一处错误配置不管来自 Wiz 还是 GuardDuty 看起来都一样。检测工具仍然是地基，Tamnoon 交付的是紧随其后的端到端修复。

对每一条它处理的发现项，Tami 都会给出一个修复置信度指标（Remediation Confidence Indicator，RCI）：SAFE、RISKY 或 AWAITING DATA。这个评级告诉团队哪些可以自动执行、哪些需要先由人工复核。

### Tamnoon 的 AWS 架构

Tamnoon 完全运行在它自己的 AWS 账户内，按环境相互隔离。用户通过构建在 Amazon API Gateway 之上的单一安全入口访问平台，加密由 AWS Certificate Manager 管理，登录由 Amazon Cognito 处理。入口之后的一切都在横跨多个可用区（Availability Zone）的私有网络中运行，因此核心平台从不直接暴露到公网上。

在这套环境内部，Tamnoon 结合了两种计算形态。Amazon Elastic Kubernetes Service（Amazon EKS）运行 dashboard 背后的常驻服务，而 AWS Lambda 承担收集发现项、分析发现项、执行修复这些事件驱动的工作。一组 AWS 消息与工作流服务，包括 Amazon EventBridge、Amazon Simple Queue Service（Amazon SQS）和 AWS Step Functions，把这些步骤协调起来，从而可靠地并行处理大量发现项，不会让某一条坏记录把其余的都卡住。

AI 层运行在 Amazon Bedrock 上。[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)——一个可用任意框架或模型大规模构建、连接并优化 agent 的平台——给 Tamnoon 的 agent 提供了一种受治理的方式来采取行动，而不是开放式的访问权限。随后 Amazon Bedrock Guardrails 会在任何东西向前推进之前，同时审查请求和生成的代码。支撑服务处理平台的其余部分：托管数据库与缓存负责状态，Amazon Simple Storage Service（Amazon S3）存放 playbook 与产物，AWS Secrets Manager 存放凭证，因此敏感的 key 从不驻留在应用代码里。

在客户这一侧，AWS Cloud 边界左边的一切，都是客户接入 Tamnoon 的东西。他们可以关联自己的 AWS、Azure 和 Google Cloud 账户，插上他们的发现项所来自的安全工具，并连上他们希望交付结果的目的地，例如 Slack、Jira、ServiceNow 和 GitHub。

### Tamnoon 如何做到零生产事故

零生产事故对 Tamnoon 的客户来说是现实，而且这不是偶然。在 Tamnoon，自主性被安置在一套纵深防御（defense-in-depth）的安全架构之内，其中每一层都假设它前面那一层可能漏掉些什么。

这一切在任何修复被起草之前就开始了。在一道独立的、聚焦于范围并刻意偏向谨慎的安全评估得出「这个改动可以安全地进行」的结论之前，不会写任何修复。此后，平台在「读」与「写」之间划出一条硬线。调查步骤会被校验为严格只读，因此「理解一个问题」这件事永远不会改动这个问题。只有修复路径被允许更改任何东西，而它做出的每一处更改都自带备份、验证和回滚步骤。

这种纪律由持续的自我批判来加固。每一个生成步骤都配一个反思步骤，检查输出并把自己的批评反馈回再生成，因此系统始终在复核自己的工作，而不是直接相信它。这些建议也被牢牢锚在现实之上。agent 的输出会对照自动化执行结果、用户反馈，以及从真实已修复告警中提炼的训练数据来校验；当模型自己无法得出准确结果时，就把人拉进这个闭环。

最后一道防线在执行的那一刻。AI 从不持有云凭证。相反，执行是由短时效、按租户范围限定的凭证居间代理的，这些凭证处于客户控制的信任之下，并运行在与规划这些工作的 agent 相互隔离、独立分开的隔离环境中。包裹这一切的是人类治理：修复走一条带完整审计轨迹的审批流程，而每一项 AI 能力在触达客户之前都在内部被验证过。

## 数据安全与合规

Tami 会对敏感的客户数据做推理：告警 payload、资源标识符、错误配置以及修复上下文。这些数据必须留在 AWS 信任边界之内、以最小权限运行、并保持可审计。统一到 Amazon Bedrock 上让这件事成为可能。

### 敏感内容留在 AWS 内部

每一个 Tami 工作负载都通过 `ChatBedrockConverse` 接口在 Amazon Bedrock 上调用 Anthropic Claude，而不是调用第三方的 LLM 端点。这一个选择就把整条 AI 供应链放进了单个 AWS 原生服务之下，这对客户数据的处理方式有实实在在的影响。推理完全运行在 Tamnoon 自己位于美国商用 Region 的 AWS 账户内，因此数据从不离开 AWS。有关各 Region 模型可用性的信息，参见 [Amazon Bedrock 按 AWS Region 划分的受支持模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。因为 Bedrock 不会保留 prompt 或补全内容、也不用它们做训练，客户数据从一开始就不会到达任何外部供应商。

即便工作负载扩容，这道边界依然成立。Bedrock 的跨区域推理会自动把请求路由到美国地理边界内的各个 Region，提升应用可用的吞吐量。它背后的计算同样保持私有。每个服务都作为挂到虚拟私有云（VPC）上的 AWS Lambda 函数运行，位于私有子网中，配有明确的安全组、没有公网入站、出站受到严格控制。

### 守住进入模型的内容

payload 可能携带敏感细节，因此 Tami 对每一个请求和响应都施加 Amazon Bedrock Guardrails。这套策略在 Bedrock 层强制执行，意味着它统一覆盖全部三个服务，而任何一个函数自己的 prompt 逻辑都无法绕过它。这单一的强制点同时做好几件事。

首先，它保护敏感数据。PII 和类似 secret 的内容在被持久化或被呈现出来之前就会被遮蔽，因此没有敏感信息会滞留在不该在的地方。它同时防范 prompt injection——这很重要，因为 Tami 推理的对象是不可信的发现项，未经授权的用户有可能对它施加影响。在护栏层做过滤，能阻止一个精心构造的 payload 劫持模型或外泄上下文。最后，denied topics 与内容过滤器把模型的输出限定在安全修复这一件事上，其他一概不做。每一次干预都会与 AWS CloudTrail 一并记录，给企业客户提供一条清晰的治理证据链。

### 最小权限访问

整个平台的访问都经由一个每服务专属的 IAM 执行角色，因此每个函数只能触达它需要的东西，多一点都不行。这一原则在 Tami 触碰 Amazon Bedrock 的方式上最容易看清。它唯一的 Bedrock 权限是 `bedrock:InvokeModel`，范围限定到具体的 inference-profile 和基础模型 ARN。它没有任何管理、训练或导出模型的能力。

同样的纪律延伸到每一个其他依赖。对 AWS Secrets Manager 的访问仅限于某个函数实际使用的那两个 secret，SQS 访问被限制在它自己的输入队列，Amazon CloudWatch 写入按命名空间受限。整个设计里没有任何宽泛的、包打天下的角色。函数只挂载受管策略 `AWSLambdaBasicExecutionRole` 和 `AWSLambdaVPCAccessExecutionRole`，绝不比这更宽。

### 多租户隔离与治理

把租户彼此分开是一项基础性要求，它从第一次调用起就被强制执行。服务之间的调用使用经由 Cognito 的 OAuth2 client credentials，按应用限定范围，并且工作是一次一条 SQS 消息地处理，消息上带着它的租户上下文。结果就是，一次调用永远只触达一个租户的数据。

这种保证有很大一部分来自把整个平台当作代码来对待。IAM 策略、网络位置、模型 ID 和告警都存在于带版本管理的 AWS CloudFormation 和 SAM 模板里，因此每一项权限和模型版本都能在源代码管理中被审阅，没有会漂移出同步状态的手工控制台改动。模型版本尤其被钉死到带日期的标识符上，例如 `claude-sonnet-4-5-20250929`，这意味着换模型永远是一次显式、经过审阅的代码改动，而不是一次悄无声息的升级。

这种透明度一直贯穿到运行时。每一次推理调用都落在 AWS CloudTrail 里，可归因到发起调用的角色；而把 temperature 设为零的确定性解码，让打分和规划在一次运行与下一次运行之间保持一致。失败处理以同样的严苛被治理。每个服务都有一条带 redrive 的输入队列、一个错误处理函数、一条死信队列，以及针对超时和 DLQ 深度并连到 on-call 的 CloudWatch 告警。故障是被收敛且可观测的，绝不会悄无声息地被丢弃。

## 成果与影响

Tami 已经在 Tamnoon 的客户群里分析过 1400 多万条云告警，这个数字记录在 Tamnoon 的 [2026 云修复状况报告](https://tamnoon.io/state-of-cloud-remediation/)中。Tami 做出的决策反映的是从这些真实世界环境中习得的模式。

对一个典型客户而言，结果出现得很快，通常在 90 天之内。

## 结论

构建一个能对云发现项进行推理的 agent，是直截了当的那部分。构建一个你敢让它对生产环境采取行动的 agent，才是难的那部分。Amazon Bedrock 是一项完全托管的服务，它提供对高性能基础模型的访问，以及构建 agentic 应用所需的工具：编排、工具使用和护栏，全部通过单一 API。这个组合在这里之所以重要，有一个很具体的原因：对生产云基础设施采取行动，同时需要强推理和硬的安全边界。

有四件事让这成为可能：

- 你的暴露真的被关闭：Tamnoon 作用在真实运行的云基础设施上，不是作用在工单或工作流自动化上。积压队列是在往下走，而不是往旁边挪。
- 自主性扩容而不带来生产风险：每一个待执行的动作都带着一个置信度评级。SAFE 的动作可以自动执行，而 AWAITING DATA 或 RISKY 的动作会引入 Tamnoon 内置的云工程师。
- 跑在你已经买下的技术栈上：Tamnoon 构建在主流 CNAPP 和云安全工具之上。你已经在付钱的每一个检测工具都开始回本，因为它们的发现项终于被关闭了。
- 团队产能扩张而不用扩人：快速、安全地采用前沿 AI，意味着每位分析师能关闭更多暴露，不需要新增人手。

- 探索 [Amazon Bedrock](https://aws.amazon.com/bedrock) 以及通过它可用的模型。
- 查阅 [Amazon Bedrock 文档](https://docs.aws.amazon.com/bedrock/) 来规划你的架构。
- 与 Tamnoon [预约一次演示](https://tamnoon.io/demo/)，看看你的关键云暴露中未来 90 天内能关闭多少。
