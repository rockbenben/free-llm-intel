# 使用 LLM 加固网络防御：Sophos 关于将 LLM 与 Amazon Bedrock、Amazon SageMaker 结合使用的策略洞见

*本文由 Sophos 的 Adarsh Kyadige 和 Salma Taoufiq 共同撰写。*

作为前沿网络安全领域的领导者，[Sophos](https://www.sophos.com/en-us/company) 致力于保护 150 多个国家/地区的 500,000 多家组织和数百万客户。Sophos 借助威胁情报、machine learning（ML）和 artificial intelligence（AI）的力量，提供全面的先进产品与服务。这些解决方案旨在保护用户、网络和终端，抵御包括钓鱼、勒索软件和恶意软件在内的各类网络威胁。[Sophos Artificial Intelligence (AI) group](https://ai.sophos.com/)（SophosAI）负责 Sophos 主要 ML 安全技术的开发与维护。

Large language models（LLM）在跨领域的自然语言理解与生成上展现出了令人印象深刻的能力，众多排行榜（例如 [HELM](https://crfm.stanford.edu/helm/lite/latest/)、[Hugging Face Open LLM leaderboard](https://huggingface.co/open-llm-leaderboard)）用大量通用任务对它们进行评估，也印证了这一点。然而，它们在网络安全这类专业领域的有效性高度依赖领域特定知识。在此背景下，fine-tuning 成为让这些通用模型适应网络安全复杂性的关键技术。例如，我们可以使用 [Instruction fine-tuning](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-models.html) 来提升模型在事件分类或摘要上的表现。不过，在 fine-tuning 之前，重要的是先通过一组基于该领域的任务，判断开箱即用的模型有多大潜力。我们定义了三个专门任务，稍后会在本文中介绍。这些相同的任务也可以用来衡量通过 fine-tuning、[Retrieval-Augmented Generation](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）或 knowledge distillation 获得的性能提升。

在本文中，SophosAI 分享了使用与评估开箱即用 LLM 的洞见，以借助 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 和 [Amazon SageMaker](https://aws.amazon.com/sagemaker/) 提升安全运营中心（SOC）的生产力。我们使用 Amazon Bedrock 上的 Anthropic Claude 3 Sonnet 来说明这些用例。

Amazon Bedrock 是一项全托管服务，通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、Meta、Mistral AI、Stability AI 和 Amazon 等领先 AI 公司的高性能基座模型（FM）供你选择，并提供构建生成式 AI 应用所需的广泛能力，同时在安全、隐私和负责任 AI 方面提供保障。

## 任务

我们将展示三个示例任务，以深入探讨在 SOC 场景中使用 LLM 的方式。SOC 是负责监控、检测、分析和响应网络安全威胁与事件的组织单元。它结合技术、流程和熟练人员，来维护信息系统与数据的机密性、完整性和可用性。SOC 分析师持续监控安全事件、调查潜在威胁，并采取适当措施来降低风险。SOC 已知的挑战是检测工具产生的大量告警，以及分析师随之而来的告警疲劳。这些挑战往往还伴随着人员短缺。为应对这些挑战并提升运营效率与可扩展性，许多 SOC 正越来越多地转向自动化技术，以简化重复性任务、对告警排定优先级并加速事件响应。考虑到分析师需要执行的任务性质，LLM 是提升 SOC 自动化水平、赋能安全团队的良好工具。

在本项工作中，我们聚焦 SOC 的三个关键用例，在这些用例中 LLM 有潜力为分析师提供极大帮助，即：

- 从自然语言生成 SQL 查询，以简化数据提取
- 事件严重性预测，以确定分析师应优先关注哪些事件
- 基于构成事件的告警数据生成事件摘要，以提升分析师生产力

根据这些任务的 token 消耗，尤其是摘要部分，我们需要一个上下文窗口至少为 4000 token 的模型。虽然这些任务是用英文测试的，但 Anthropic 的 Claude 3 Sonnet 模型也能在其他语言下表现良好。不过，我们建议在你关注的具体语言下评估性能。

下面我们深入每个任务的细节。

### 任务 1：从自然语言生成查询

该任务的目标是评估模型利用底层数据 schema 的上下文知识，将自然语言问题转换为 SQL 查询的能力。这项技能简化了数据提取过程，让安全分析师无需深厚的技术知识就能更高效地开展调查。我们使用 [prompt engineering guidelines](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-engineering-guidelines.html) 来调整 prompt，以便从 LLM 获得更好的回复。

该任务采用 three-shot prompting 策略。给定一个数据库 schema，模型会拿到三个示例，每个示例把一个自然语言问题与其对应的 SQL 查询配对。在这些示例之后，再提示模型为关注的问题生成 SQL 查询。

下面的 prompt 是一个从自然语言生成查询的 three-shot prompt 示例。根据经验，我们使用 few-shot prompting 得到的结果优于 one-shot（在实际关注的问题之前，只给模型提供一个示例问题及对应查询）或 zero-shot（直接提示模型生成所需查询，不提供任何示例）。

```
Translate the following request into SQL
Schema for alert_table table
   <Table schema>
Schema for process_table table
   <Table schema>
Schema for network_table table
   <Table schema>

Here are some examples
<examples>
Request:tell me a list of processes that were executed between 2021/10/19 and 2021/11/30
   SQL:select * from process_table where timestamp between '2021-10-19' and '2021-11-30';

Request:show me any low severity security alerts for the 23 days ago
   SQL:select * from alert_table where severity='low' and timestamp>=DATEADD('day', -23, CURRENT_TIMESTAMP());

Request:show me the count of msword.exe processes that ran between Dec/01 and Dec/11
   SQL:select count(*) from process_table where process='msword.exe' and timestamp>='2022-12-01' and timestamp<='2022-12-11';
</examples>

Request:"Any Ubuntu processes that was run by the user ""admin"" from host ""db-server"""
SQL:
```

为了评估模型在该任务上的表现，我们使用一个专有数据集，其中包含约 100 条基于测试数据库 schema 的目标查询。为判断模型生成的查询是否准确，我们采用多步评估。首先，我们核验模型的输出是否与预期 SQL 语句完全匹配。完全匹配的记录为成功结果。如果存在不匹配，我们就用模型的查询和预期查询分别对 mock 数据库执行，并比较结果。不过，这种方法容易产生误报和漏报。为缓解这一点，我们进一步用另一个更强的 LLM 对该任务做查询等价性评估。这种方法被称为 [LLM-as-a-judge](https://huggingface.co/learn/cookbook/en/llm_judge)。

Anthropic 的 Claude 3 Sonnet 模型在所选数据集上取得了 88% 的良好准确率，说明这项自然语言转 SQL 的任务对 LLM 来说相当简单。因此，借助基础的 few-shot prompting，安全分析师无需 fine-tuning 就能开箱即用地使用 LLM，在调查威胁时帮助他们获取关键信息。上述模型表现基于我们的数据集和我们的实验。这意味着你可以用上面说明的策略做你自己的测试。

### 任务 2：事件严重性预测

对于第二个任务，我们评估模型把观察到的事件识别为事件指标并判断其严重性的能力。具体而言，我们试图判断 LLM 能否审查一起安全事件并准确衡量其重要性。具备这种能力后，模型可以帮助分析师确定哪些事件最为紧迫，从而让他们按严重性级别组织工作队列，更高效地工作，穿透噪声并节省时间与精力。

该用例的输入数据是半结构化告警数据，也就是各类检测系统在事件期间产生的典型数据。我们明确界定了严重性类别——critical、high、medium、low 和 informational——模型要据此对事件的严重性进行分类。因此这是一个分类问题，用来检验 LLM 固有的网络安全知识。

Sophos Managed Detection and Response（MDR）平台中的每起安全事件都由多个检测构成，这些检测指出用户环境中正在发生的可疑活动。一项检测可能涉及识别潜在有害的模式，例如异常的命令执行、不寻常的文件访问、异常的 network 流量或可疑的脚本使用。我们在下面附上了一个示例输入数据。

“detection” 部分提供关于每个已识别具体可疑活动的详细信息。它包含安全事件的类型，例如 “Execution”，以及说明威胁性质的描述，例如使用可疑的 PowerShell 命令。该检测关联一个唯一标识符，用于追踪和引用。此外，它还包含来自 [MITRE ATT&CK framework](https://attack.mitre.org/) 的细节，该框架对威胁涉及的 tactics 和 techniques 进行分类。这一部分也可能引用相关的 Sigma 规则，这些规则是社区驱动的签名，用于在各类系统上检测威胁。通过包含这些要素，detection 部分构成了对潜在威胁的全面概述，帮助分析师不仅理解检测到了什么，也理解它为何重要。

“machine_data” 部分包含关于发生检测的机器的重要信息。它可以提供该机器的更多元数据，帮助精确定位可疑活动在环境中的确切位置。

即使在多种设置下，例如使用最近邻事件的 few-shot prompting，模型的表现也无法可靠地超过随机猜测。作为参考，测试集上的基线准确率约为 71%，基线平衡准确率为 20%。

### 任务 3：事件摘要

第三个任务关注对传入事件的摘要。它评估模型在安全事件到来时，通过提供触发该事件活动的简洁摘要，帮助威胁分析师进行分诊和调查的潜力。

安全事件通常由发生在用户终端或网络上的一系列事件组成，并与已检测到的可疑活动相关联。调查该事件的分析师会看到在检测到可疑活动时该终端上发生的一系列事件。然而，分析这一事件序列可能困难且耗时，导致难以识别值得关注的事件。这正是 LLM 可以发挥作用的地方：按照特定模板帮助整理和归类事件数据，从而协助理解，并帮助分析师快速确定合适的后续操作。

我们使用 Sophos MDR 的真实事件数据来做事件摘要。该任务的输入是一组 JSON 事件，每个事件根据采集传感器的不同而具有不同的 schema 与属性。这些数据与指令以及一个预定义模板一起提供给模型，以生成摘要。下面的 prompt 是从 SOC 数据生成事件摘要的模板 prompt 示例。

```
As a cybersecurity assistant, your task is to:
    1. Analyze the provided cybersecurity detections data.
    2. Create a report of the events using the information from the '### Detections' section, which may include security artifacts such as command lines and file paths.
    3. [Any other additional general requirements for formatting, etc.]
The report outline should look like this:
Summary:
    <Few sentence description of the activity. [Any additional requirements for the summary: what to  include, etc.]>
Observed MITRE Techniques:
    <List only the registered MITRE Technique or Tactic ID and name pairs if available. The ID should start with 'T'.>
Impacted Hosts:
    <List of all hostname observed in the detections, provide corresponding IPs if available>
Active Users:
    <List of all usernames observed in the detections. There could be multiple, list all of them>
Events:
    <One sentence description for top three detection events. Start the list with \n1. >
IPs/URLs:
    <List available IPs and URLs.>
    <Enumerate only up to ten artifacts under each report category, and summarize any remaining events beyond that.>
Files: 
    <List the files found in the incident as follows:>
    <TEMPLATE FOR FILES WITH DETAILS>
Command Lines: 
    <List the command lines found in the detections as follows:>
    <TEMPLATE FOR COMMAND LINES WITH DETAILS>

### Detections:
```

评估这些生成的事件摘要并不简单，因为必须考虑多个因素。例如，提取出的信息不仅要正确，还必须相关，这一点至关重要。为了总体了解模型事件摘要的质量，我们使用一组五项不同的指标，并依赖一个由 N 起事件组成的数据集。我们把生成的描述与根据 Sophos 分析师反馈编写的对应黄金标准描述进行比较。

我们计算两类指标。第一类指标评估事实准确性，用于评估模型正确识别并摘要了多少 artifact，例如命令行、文件路径、用户名等。这里的计算很直接：我们计算生成描述与目标之间在提取出的 artifact 上的平均距离。我们使用两种距离指标，Levenshtein distance 与 longest common subsequence（LCS）。

第二类指标用于对生成的描述做更语义化的评估，使用三种不同的指标：

- **BERTScore metric**：该指标使用预训练 BERT 模型的上下文 embedding 来评估生成的摘要。它通过 cosine similarity 判断生成摘要与参考摘要之间的相似度。
- **ADA2 embeddings cosine similarity**：该指标评估生成摘要中 token 的 ADA2 embeddings 与参考摘要中对应 token 的 cosine similarity。
- **METEOR score**：METEOR 是一种基于 unigram 精确率与召回率调和平均的评估指标。

也可以使用更先进的评估方法，例如在人类偏好上训练 reward model 并将其用作评估器，但为简便与成本效益考虑，我们把范围限定在这些指标上。

下面是我们在这个任务上的结果摘要：

| **模型** | **基于 Levenshtein 的事实准确性** | **基于 LCS 的事实准确性** | **BERTScore** | **ADA2 embeddings 的 cosine similarity** | **METEOR 分数** |
| --- | --- | --- | --- | --- | --- |
| Anthropic 的 Claude 3 Sonnet | 0.810 | 0.721 | 0.886 | 0.951 | 0.4165 |

基于这些发现，我们对模型在生成事件摘要方面的表现有了总体了解，尤其关注事实准确性与检索率。Anthropic 的 Claude 3 Sonnet 模型能够捕捉事件中正在发生的活动并良好地加以摘要。然而，它会忽略某些指令，例如对所有 IP 和 URL 做 defanging。返回的报告在 token 层面也未与目标响应完全对齐，这一点从 METEOR 分数可以看出。Anthropic 的 Claude 3 Sonnet 模型在报告中略过了一些细节和解释。

## 使用 Amazon Bedrock 和 Amazon SageMaker 的实验设置

本节概述使用 Amazon Bedrock 和 Amazon SageMaker 评估多种 large language model（LLM）的实验设置。这些服务让我们能够高效地与多个 LLM 交互并部署它们，从而快速、低成本地开展实验。

### Amazon Bedrock

Amazon Bedrock 是一项托管服务，可以按需快速试验多种 LLM。它的优势在于无需自行托管 LLM 就能与之交互和实验，并且只需按消耗的 token 付费。我们使用 [InvokeModel API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_InvokeModel.html) 以最小延迟与模型交互。我们编写了下面的函数，通过向 API 传入必要的推理参数来调用不同模型。关于各提供商的推理参数详情，建议你阅读 [Amazon Bedrock 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-bedrock.html)中的 [Inference request parameters and response fields for foundation models](https://docs.aws.amazon.com/bedrock/latest/userguide/model-parameters.html) 一节。下面的示例使用基于 Anthropic 的 Claude 3 Sonnet 模型的函数。注意我们通过 [system prompt](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/system-prompts) 给模型设定了角色，并且[预填充了它的响应](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/prefill-claudes-response)。

```

messages = [

             "content": 
" Respond strictly with this JSON format:{"severity_pred": "xxx"} where xxx should only be either:
- Critical,
<Criteria for a critical incident>
- High,
<Criteria for a high severity incident>
- Medium,
<Criteria for a medium severity incident>
- Low,
<Criteria for a low severity incident>
- Informational

def generate_message(bedrock_runtime, model_id, system_prompt, messages, max_tokens):
    body=json.dumps(
        {
            "anthropic_version": " bedrock-2023-05-31",
            "max_tokens": max_tokens,
            "system": system_prompt,
            "messages": messages
        }  
    )   
    response = bedrock_runtime.invoke_model(body=body, modelId=model_id)
    response_body = json.loads(response.get('body').read())
    return response_body
```

以上示例基于我们的用例。*model_id* 参数指定你希望通过 Bedrock runtime 调用的具体模型标识符。我们使用的 model id 是 *anthropic.claude-3-sonnet-20240229-v1:0*。其他 model id 请参考 [bedrock 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)。关于该 API 的更多细节，我们建议你阅读 [API 文档](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_InvokeModel.html)。我们建议你根据自身需求把它适配到你的用例。

本文的分析聚焦 Anthropic 的 Claude 3 Sonnet 模型和三个具体用例。这些洞见可以适配到其他 SOC 的具体需求和期望的模型。例如，可以访问 Meta 的 Llama 模型、Mistral 模型、Amazon Titan 模型等其他模型。对于更多模型，我们使用了 Amazon SageMaker Jumpstart。

### Amazon SageMaker

[Amazon SageMaker](https://aws.amazon.com/sagemaker/) 是一项全托管的机器学习（ML）服务。借助 SageMaker，数据科学家和开发者可以快速、自信地构建、训练和部署 ML 模型到可用于生产的托管环境。[Amazon SageMaker JumpStart](https://aws.amazon.com/sagemaker/jumpstart/) 是 SageMaker 机器学习（ML）环境中的一项强大功能，为从业者提供一个公开可用和专有基座模型（FM）的综合枢纽。它提供广泛的公开可用和专有 LLM，你可以用低代码方式快速调优和部署。为了以低成本方式在 SageMaker 中快速部署并试验开箱即用的模型，我们使用[异步推理](https://docs.aws.amazon.com/sagemaker/latest/dg/async-inference.html)端点部署了 SageMaker JumpStart 中的 LLM。

推理端点对我们来说是一种省力的方式，可以直接从各个 Hugging Face 仓库下载这些模型，并用几行代码和预制的 [Text Generation Inference (TGI)](https://aws.amazon.com/blogs/machine-learning/announcing-the-launch-of-new-hugging-face-llm-inference-containers-on-amazon-sagemaker/) 容器完成部署（参见 GitHub 上的[示例 notebook](https://github.com/awslabs/llm-hosting-container/blob/main/examples/huggingface/huggingface-large-model-inference.ipynb)）。此外，我们使用了带 autoscaling 的[异步推理](https://docs.aws.amazon.com/sagemaker/latest/dg/async-inference.html)端点，这帮助我们在不再使用推理端点时自动将其缩容到零，从而管理成本。考虑到我们要创建的端点数量，异步推理让我们可以轻松管理端点：需要时端点随时可用，不使用时缩容，而且在定义好扩缩容策略后，我们这一侧无需额外管理。

## 后续步骤

在本文中，我们在单个模型上应用这些任务，只是为了把它作为示例展示；在现实中，你会根据自身需求挑选几个 LLM，让它们走一遍本文中的实验。在此基础上，如果开箱即用的模型对该任务还不够好，你会选出最合适的 LLM，再针对具体任务对它做 fine-tuning。

例如，基于我们三个实验任务的结果，我们发现事件信息摘要任务的结果未达到预期。因此，我们将对最符合我们需求的开箱即用模型做 fine-tuning。这一 fine-tuning 过程可以通过 [Amazon Bedrock Custom Models](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-models.html) 或 [SageMaker fine tuning](https://docs.aws.amazon.com/sagemaker/latest/dg/jumpstart-fine-tune.html) 完成，然后可以通过[使用定制模型](https://docs.aws.amazon.com/bedrock/latest/userguide/model-customization-use.html)来部署 fine-tuned 模型，方式是把模型[导入到 Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/model-customization-import-model.html)，或把模型部署到 SageMaker 端点。

本文我们覆盖了实验阶段。一旦你找到满足性能要求的 LLM，重要的是开始考虑如何将其生产化。在生产化 LLM 时，重要的是考虑 guardrails 和 LLM 的可扩展性等方面。实施 guardrails 有助于你把模型被误用或安全被破坏的风险降到最低。[Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 让你可以基于自己的用例和负责任 AI 政策，为生成式 AI 应用实施防护措施。这篇[博客](https://aws.amazon.com/blogs/machine-learning/build-safe-and-responsible-generative-ai-applications-with-guardrails/)介绍了如何在生成式 AI 应用中构建 guardrails。将 LLM 投入生产时，你还需要根据请求流量验证 LLM 的可扩展性。在 Amazon Bedrock 中，可以考虑[提高配额](https://docs.aws.amazon.com/servicequotas/latest/userguide/request-quota-increase.html)、[批处理推理](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference.html)、对请求排队，甚至把请求分散到提供相同模型的不同 Region。请根据你的用例和流量选择合适的技术。

## 结论

在本文中，SophosAI 分享了借助 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 和 [Amazon SageMaker](https://aws.amazon.com/sagemaker/)，按照一组专门任务来使用与评估开箱即用 LLM 的洞见，以提升安全运营中心（SOC）的生产力。我们使用 Amazon Bedrock 上的 Anthropic Claude 3 Sonnet 模型说明了三个用例。

Amazon Bedrock 和 SageMaker 是使我们能够运行这些实验的关键。Amazon Bedrock 通过一次 API 调用，让我们便捷地访问来自领先 AI 公司的高性能基座模型（FM），因此我们无需自行部署就能测试多种 LLM。此外，按需定价模式让我们只需按 token 消耗为实际使用付费。

要灵活掌控地访问更多模型，SageMaker 是一个很好的替代方案，它提供广泛的、可直接部署的 LLM。虽然这些模型需要你自己部署，但你仍然可以通过使用带扩缩容策略的异步端点获得很好的成本优化，该策略会在不使用时把实例缩容到零。

关于像 Anthropic 的 Claude 3 Sonnet 这类 LLM 在网络安全中的适用性，总体结论可以归纳如下：

- 开箱即用的 LLM 可以成为威胁狩猎和事件调查的得力助手。不过，它仍然需要一些 guardrails 和引导。我们相信，通过仔细的 prompt engineering，这种潜在应用可以用现有的强大模型（例如 Anthropic 的 Claude 3 Sonnet 模型）来实现。
- 在从原始数据摘要事件信息方面，Anthropic 的 Claude 3 Sonnet 模型表现尚可，但仍有通过 fine-tuning 改进的空间。
- 评估单个 artifact 或 artifact 组对于预训练 LLM 仍是一项有挑战性的任务。要解决这个问题，可能需要一个专门在网络安全数据上训练的专用 LLM。

同样值得注意的是，虽然我们使用了 Amazon Bedrock 的 InvokeModel API，但访问 Amazon Bedrock 模型还有另一种更简单的方式，即使用 [Converse API](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html)。Converse API 提供一致的 API 调用，可与支持 messages 的 Amazon Bedrock 模型配合使用。这意味着你可以只写一次代码，就能用于不同模型。如果模型有独特的推理参数，Converse API 也允许你在模型专属结构中传入这些独特参数。
