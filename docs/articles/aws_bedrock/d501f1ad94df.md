# 弥合开发与生产之间的鸿沟：用 Amazon Bedrock 实现无缝的模型生命周期管理

在[生成式 AI](https://aws.amazon.com/ai/generative-ai/) 的版图中，各组织越来越多地采用结构化的方式来部署其 AI 应用，效仿传统的软件开发实践。这种做法通常涉及彼此独立的开发环境和生产环境，各自拥有自己的 AWS 账户，以实现逻辑隔离、增强安全性并简化工作流。

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 是一项全托管服务，通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、Meta、Mistral AI、Stability AI 和 Amazon 等领先 AI 公司的高性能基础模型（FM）供你选择，并提供构建生成式 AI 应用所需的一系列广泛能力，涵盖安全、隐私和负责任 AI。随着组织扩大其 AI 举措，它们常常在跨不同开发阶段、跨地理区域高效管理和部署自定义模型方面遇到挑战。

为应对这些挑战，Amazon Bedrock 推出了两项关键特性：[Model Share](https://docs.aws.amazon.com/bedrock/latest/userguide/share-model.html) 和 [Model Copy](https://docs.aws.amazon.com/bedrock/latest/userguide/copy-model.html)。这些特性旨在简化 AI 开发生命周期，从最初的实验一直到全球生产部署。它们让开发团队与生产团队之间实现无缝协作，促进资源的高效利用，并帮助组织在整个自定义模型生命周期中保持控制与安全。

在这篇内容详尽的博文中，我们将深入介绍 Model Share 和 Model Copy 特性，探讨它们的功能、优势，以及在典型的“从开发到生产”场景中的实际应用。

## Model Copy 与 Model Share 的前提条件

在开始使用 Model Copy 和 Model Share 之前，必须满足以下前提条件：

- [AWS Organizations](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_introduction.html)** 设置**：源账户（共享模型的账户）和目标账户（接收模型的账户）必须属于同一个组织。如果你还没有组织，需要先创建一个，启用资源共享，并邀请相关账户。
- **IAM 权限**：**对 Model Share**：为共享账户设置 [AWS Identity and Access Management（IAM）](https://aws.amazon.com/iam)权限，以允许通过 [AWS Resource Access Manager（AWS RAM）](https://aws.amazon.com/ram)进行共享。**对 Model Copy**：在源和目标 AWS 区域都配置 IAM 权限，以允许复制操作。将必要的 IAM 策略附加到两个账户中的角色上，以启用模型共享。
- **KMS 密钥策略（可选）**：如果你的模型使用客户管理的 KMS 密钥加密，则需要设置密钥策略，允许目标账户解密共享模型，或者用指定的 KMS 密钥加密复制后的模型。
- **网络配置**：确保所需的网络配置已经就位，尤其是在你使用 VPC 端点或有特定网络安全要求的情况下。
- **服务配额**：检查并在必要时申请提高源和目标区域、账户中每个账户的自定义模型数量[服务配额](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas.html)。
- **预置吞吐量支持**：确认目标区域支持你打算复制的模型所需的预置吞吐量。这一点很关键，因为如果目标区域不支持预置吞吐量，复制作业会被拒绝。

### Model Share：简化从开发到生产的工作流

下图展示了 Model Share 与 Model Copy 的架构。它包含一个对模型进行微调的源账户。接下来，Amazon Bedrock 把它共享给接收账户，该账户在 [AWS Resource Access Manager](https://aws.amazon.com/ram/)（RAM）中接受共享模型。之后，共享模型可以被复制到所需的 AWS 区域。

![Model Share 与 Model Copy 的架构图。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/20/ML-17607-1.png)

在“从开发到生产”的流水线中管理 Amazon Bedrock 自定义模型时，安全地跨 AWS 账户共享这些模型对于简化向更高环境的晋升流程至关重要。Amazon Bedrock 的 Model Share 特性正是为此需求而生，可在开发环境与生产环境之间实现顺畅共享。Model Share 支持在同一区域、同一组织内的不同 AWS 账户之间，共享在 Amazon Bedrock 上微调的自定义模型。该特性对于那些把开发环境和生产环境分开维护的组织尤其有用。

**重要注意事项：**

- 源和目标 AWS 账户必须属于同一个组织。
- 只有已在 Amazon Bedrock 内完成微调的模型才能被共享。
- 基础模型以及通过[自定义模型导入](https://aws.amazon.com/bedrock/custom-model-import/)（CMI）导入的自定义模型不能直接共享。对于这些模型，请在每个 AWS 账户中使用标准的模型导入流程。
- 共享加密模型时，请使用客户管理的 KMS 密钥，并附加一份[密钥策略](https://docs.aws.amazon.com/bedrock/latest/userguide/encryption-custom-job.html#encryption-copy)，允许接收账户解密共享模型。在密钥策略的 Principal 字段中指定接收账户。

**主要优势：**

- **简化从开发到生产的过渡**：将 Amazon Bedrock 上的微调模型快速从开发环境迁移到生产环境。
- **增强团队协作**：在不同部门或项目团队之间共享模型。
- **资源优化**：减少组织内重复的模型定制工作。

**工作原理：**

- 在源 AWS 账户中使用 Amazon Bedrock 完成模型微调后，源 AWS 账户可以通过面向 Amazon Bedrock 的 AWS 管理控制台共享该模型。
- 目标 AWS 账户在 AWS RAM 中接受共享模型。
- 目标 AWS 账户中的共享模型需要复制到所需区域。
- 复制完成后，目标 AWS 账户可以购买预置吞吐量并使用该模型。
- 如果使用 KMS 加密，请确保为接收账户正确设置密钥策略。

### Model Copy：优化跨区域的模型部署

Amazon Bedrock 的 Model Copy 特性让你能够在自己的账户内跨不同区域复制自定义模型。这项能力有两个主要用途：它可以独立用于单账户部署，也可以在多账户场景中与 Model Share 配合，即先跨账户共享模型，然后再复制。该特性对于需要全球模型部署、区域负载均衡和健壮灾难恢复方案的组织尤其有价值。通过允许跨区域灵活分发模型，Model Copy 帮助你在性能与可靠性两方面优化 AI 基础设施。

**重要注意事项：**

- 确认目标区域支持要复制的模型所需的预置吞吐量。如果不支持预置吞吐量，复制作业会被拒绝。
- 注意在多个区域存储和使用复制模型所涉及的成本。详情请查阅 [Amazon Bedrock 定价页面](https://aws.amazon.com/bedrock/pricing/)。
- 在跨账户场景中于 Model Share 之后使用时，请先接受共享模型，再在你的账户内发起跨区域复制。
- 定期审查并优化你的多区域部署策略，在性能需求与成本考量之间取得平衡。
- 复制加密模型时，请使用客户管理的 KMS 密钥，并附加一份允许执行复制的角色加密模型的密钥策略。在密钥策略的 Principal 字段中指定该角色。

**Model Copy 的主要优势：**

- **降低延迟**：把模型部署到更接近不同地理位置最终用户的地方，以缩短响应时间。
- **提升可用性**：通过在多个区域提供模型访问，增强 AI 应用的整体可用性与可靠性。
- **改进灾难恢复**：通过在不同区域保留模型副本，更轻松地实施灾难恢复策略。
- **支持区域合规**：按需在特定区域部署模型，以满足数据驻留要求。

**工作原理：**

- 确定你希望部署模型的目标区域。
- 使用 Amazon Bedrock 控制台从源区域向目标区域发起 Model Copy 流程。
- 模型复制完成后，在你希望使用该模型的每个区域购买预置吞吐量。
- 如果使用 KMS 加密，请确保为执行复制操作的角色正确设置密钥策略。

**用例：**

- **单账户部署**：使用 Model Copy 在同一 AWS 账户内跨区域复制模型，以提升全球性能。
- **多账户部署**：在使用 Model Share 把模型从开发账户转移到生产账户之后，使用 Model Copy 在生产账户内跨区域分发该模型。

通过单独使用 Model Copy，或将其与 Model Share 配合使用，你可以构建健壮、全球分布的 AI 基础设施。这种灵活性让你在不同地理位置都能低延迟地访问自定义模型，无论你的账户结构如何，都能提升 AI 驱动应用的性能与可靠性。

### 让 Model Share 与 Model Copy 符合 AWS 最佳实践

实施 Model Share 和 Model Copy 时，让这些特性符合 [AWS 多账户环境最佳实践](https://aws.amazon.com/organizations/getting-started/best-practices/)至关重要。AWS 建议为开发和生产分别设置独立账户，这使 Model Share 在环境之间的模型迁移上尤其有价值。请思考这些特性与你的组织结构如何互动，尤其是在你为安全、基础设施和工作负载设置了独立组织单元（OU）的情况下。关键考量包括：

- 遵守在 OU 层级设定的策略。
- 在组织的持续集成与持续交付（CI/CD）流水线中使用 Model Share 和 Model Copy。
- 使用 AWS 计费特性进行跨账户成本管理。
- 在同一 AWS 账户内做灾难恢复时使用 Model Copy；跨多个 AWS 账户实施灾难恢复时，同时使用 Model Share 和 Model Copy。

通过让 Model Share 和 Model Copy 符合这些最佳实践，你可以在 AI 模型生命周期管理中提升安全性、合规性和运营效率。更详细的指导请参阅 [AWS Organizations 文档](https://aws.amazon.com/organizations/getting-started/best-practices/)。

## 从开发到生产：一个实际用例

让我们走一遍典型场景，看看如何用 Model Copy 和 Model Share 简化把自定义模型从开发环境迁移到生产环境的过程。

![Amazon Bedrock Copy 与 Model Share 的工作流。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/20/ML-17607-2-1024x357.png)

### 步骤 1：模型开发（开发账户）

在开发账户中，数据科学家在 Amazon Bedrock 上微调模型。该过程通常包括：

- 试验不同的 FM
- 进行 prompt 工程
- 用领域特定数据微调选定的模型
- 在特定任务上评估模型性能
- 应用 Amazon Bedrock Guardrails，确保模型符合伦理与监管标准

下面的示例在美国东部（弗吉尼亚北部）区域（us-east-1）微调一个 [Amazon Titan](https://aws.amazon.com/titan) Text Express 模型。

```
# Example: Fine-tuning a model in the development account
import boto3
bedrock = boto3.client(service_name='bedrock')
    
# Set parameters
customizationType = "FINE_TUNING"
baseModelIdentifier = "arn:aws:bedrock:us-east-1::foundation-model/amazon.titan-text-express-v1"
roleArn = "${your-customization-role-arn}"
jobName = "MyFineTuningJob"
customModelName = "MyCustomModel"
hyperParameters = {
        "epochCount": "1",
        "batchSize": "1",
        "learningRate": ".0005",
        "learningRateWarmupSteps": "0"
    }
trainingDataConfig = {"s3Uri": "s3://${training-bucket}/myInputData/train.jsonl"}
outputDataConfig = {"s3Uri": "s3://${output-bucket}/myOutputData"}

# Create job
response = bedrock.create_model_customization_job(
    jobName=jobName, 
    customModelName=customModelName,
    roleArn=roleArn,
    baseModelIdentifier=baseModelIdentifier,
    hyperParameters=hyperParameters,
    trainingDataConfig=trainingDataConfig,
    outputDataConfig=outputDataConfig
)
 
job_arn = response['jobArn']
print(f"Model customization job created: {job_arn}")
```

### 步骤 2：模型评估与选择

模型微调完成后，开发团队评估其性能，并判断它是否已准备好投入生产使用。

```
# Example: Evaluating the fine-tuned model
bedrock_runtime = boto3.client('bedrock-runtime')
 
response = bedrock_runtime.invoke_model(
    modelId=customModelName,
    contentType="application/json",
    accept="application/json",
    body=json.dumps({
        "prompt": "Your LLM as judge prompt go here",
        "max_tokens_to_sample": 500
    })
)
 
result = json.loads(response['body'].read())
print(f"Model output: {result['completion']}")
```

### 步骤 3：模型共享（开发账户到生产账户）

模型获批用于生产后，开发团队使用 Model Share 把它提供给生产账户。请记住，这一步仅适用于在 Amazon Bedrock 内创建的微调模型，不适用于通过自定义模型导入进来的自定义模型。

```
# Example: Sharing the model with the production account
ram = boto3.client('ram')

response = ram.create_resource_share(
    name='financial-analyst-model-share',
    resourceArns=['arn:aws:bedrock:us-east-1:{dev-account-id}:model/custom-financial-analyst-model'],
    principals=['production-account-id'],
    allowExternalPrincipals=False
)
 
share_arn = response['resourceShare']['resourceShareArn']
print(f"Resource share created: {share_arn}"
```

### 步骤 4：模型复制（生产账户）

生产团队现在已能访问共享模型，但在使用前必须先把模型复制到他们想要的区域。即便是共享模型，这一步也是必需的，因为仅仅共享并不能让模型在目标账户中可用。

```
# Example: Copying the model to the production account's desired region
bedrock = boto3.client('bedrock', region_name='us-west-2')
 
# Check if the target region supports provisioned throughput for this model
# This check is not provided by the API and would need to be implemented separately
 
response = bedrock.create_model_copy_job(
    sourceModelArn='arn:aws:bedrock:us-east-1:{dev-account-id}:model/custom-financial-analyst-model',
    targetModelName='financial-analyst-model-us-west-2',
    targetRegion='us-west-2'
)
 
job_arn = response['jobArn']
print(f"Model copy job created: {job_arn}"
```

### 步骤 5：生产部署

最后，在模型成功复制后，生产团队可以购买预置吞吐量，并搭建推理所需的基础设施。

```
# Example: Setting up provisioned throughput and inference endpoint in production
bedrock = boto3.client('bedrock', region_name='us-west-2')
 
# Purchase provisioned throughput
response = bedrock.create_provisioned_model_throughput(
    modelId='financial-analyst-model-us-west-2',
    provisionedUnits=1
)
 
# Set up inference endpoint
response = bedrock.create_model_invocation_endpoint(
    modelId='financial-analyst-model-us-west-2',
    endpointName='financial-analyst-endpoint',
    instanceCount=2
)
 
endpoint_arn = response['endpointArn']
print(f"Inference endpoint created: {endpoint_arn}" 
```

## 结论

Amazon Bedrock 的 Model Copy 和 Model Share 特性为管理 AI 应用从开发到生产的生命周期提供了强大的选项。这些特性让组织能够：

- 简化从实验到部署的过渡
- 增强开发团队与生产团队之间的协作
- 在全球范围内优化模型性能与可用性
- 在整个模型生命周期中保持安全与合规

随着 AI 领域不断演进，这些工具对于组织保持敏捷、高效和竞争力至关重要。请记住，从开发到生产的旅程是迭代式的，需要持续监控、评估和改进模型，以维持长期有效性并与业务需求保持一致。

通过实施本文所述的最佳实践与考量，你可以为跨不同环境和区域管理 AI 模型建立起健壮、安全且高效的工作流。这种做法将加速你的 AI 开发过程，并最大化你在模型定制与微调上的投入价值。借助 Amazon Bedrock 提供的特性，你已具备充分条件，能够成功应对 AI 模型管理与部署的复杂性。
