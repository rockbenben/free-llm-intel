# 修复评估偏差，在 Amazon Bedrock 上解锁更好的模型

*本文与来自 Property Finder 的 Khaled Thabit、Meriem Boughrara 和 Mohamed Desouky 合著。*

数字房地产应用 [Property Finder](https://www.propertyfinder.ae/) 的工程团队发现，他们 96.8% 的评估标签直接继承自某一个模型的预测，而非由人类专家核验。他们的 ground truth 被系统性地偏向现有模型，使每一个替代方案都显得表现更差。标签本身也有错误，但真正阻碍客观模型比较的是这种偏差。他们是在把视觉 AI 工作负载迁移到 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上更具成本效益的方案时发现这一点的。

Property Finder 每天在中东和北非（MENA）地区处理数万张房源图片。他们的系统对每张图片评估 11 项质量属性，覆盖水印检测、房间分类、装修状态、照片质量和施工迹象。这意味着每天有数千条新房源，每条平均 15 张图片。所有这些都需在上线前完成质量评估。

Property Finder 需要一个更具成本效益的方案。但以那些标签为标尺来衡量，任何替代方案都处于劣势。

最难的部分不是找到一个更好的模型，而是发现他们的评估方法本身就是障碍。

本文分享 Property Finder 如何识别评估偏差、构建无偏的 ground truth，并应用进化式 prompt 优化在 Amazon Bedrock 上选出合适的模型，以低 86% 的成本获得更高的准确率。我们会逐一介绍方法论和迭代示例，其中的经验你可以应用到自己的工作负载上。

该图展示了迭代式的 prompt 优化循环。一张房源图片由 Amazon Bedrock 处理，并以 JSON 格式输出预测属性。优化期间，这些预测会与 256 张图片的专家标注开发集对比，用 Micro F1 评分。随后错误分析会检查失败的图片并识别视觉模式，用以指导下一版 prompt。这个循环从 v0 跑到 v27。AI 助手帮助完善 prompt，后期版本则使用了自动优化。

## 你的评估可能在说谎

许多团队都会遇到这种情形。你想比较视觉模型，于是构建一个评估数据集。获取标签最常见的方式是跑你当前的模型，把它的输出当作 ground truth。这个模型已经在生产环境跑了很久，也没人抱怨，所以标签应该够好了。

但这会造成循环评估：任何替代方案得到的评判标准是它与现有模型行为有多接近，而不是它是否真的正确。

Property Finder 的评估数据集恰恰有这个问题。在他们的已标注样本中，96.8% 直接来自现有视觉语言模型（VLM）的预测，而非独立的人工核验。任何替代模型在一张图片都还没处理之前，就已结构性处于劣势。

隐藏的错误印证了问题的严重性。水印文本提取中，字符级错误被标为正确，包括凭空生成的品牌名和漏掉的字符。照片分类则把单一标签强加给包含多种房间类型的图片。

在其余 3.2% 的人工标注样本中，标注者引入了原始规范之外的类别，比如出现了 *Office*，而 prompt 里并不存在这个标签。当标准答案是由你要替换的那个模型写的，模型比较就失去了效力。

## 构建可信的 ground truth

要打破这个循环，你需要具备真实领域知识的人类专家独立进行全新标注。不参考以往的模型输出，也看不到现有模型预测了什么。

### 数据集范围

Property Finder 团队手工标注了 356 张阿联酋图片，另有一组埃及图片。这些图片选自各代表性行业类目中未标注的生产房源。本文报告的是阿联酋图片上的结果。埃及图片用于一项覆盖 230 张图片的跨区域校验，本文不作报告。最先完成标注的 256 张阿联酋图片构成用于调优的开发集。最终模型比较的评估集使用全部 356 张，其中包含开发阶段之后标注的 100 张。356 张的规模大致足以检出模型之间的中等差异。单个属性内的稀有类别样本更少，因此这些属性上较小的差异可能无法检出。

### 专家标注

由一位战略与分析专家标注了所有图片，其带来了房源刊登质量标准方面的专业知识。AWS Generative AI Innovation Center 团队通过专门的澄清会议进行系统性质量复核。这些复核解决了模糊案例，并使整个数据集的标注保持一致。

### 转向多标签

房地产图片经常通过门洞展示多个房间，或呈现相互重叠的质量特征。从单标签分类切换到多标签分类，缓解了一个主要的人为歧义来源。

一张透过门洞拍到卧室的走廊照片，确实两者都是。允许使用多个标签后，你衡量的是模型判断正确的部分，而不是因为它给出了合理的次要预测就惩罚它。

一种混合方式可以补充这套方法论：来自不同模型族的模型给出候选标签和分歧，由人类专家对每个案例作出裁决，这样就不会有任何模型输出被直接用作标签。这将减轻未来扩展数据集的标注负担。

### 指标选择

Micro F1 作为主指标，因为它对每个预测等权，契合「整体标签正确性」这一业务目标。同时报告 Macro F1，因为 Micro F1 被高频类别主导，可能掩盖稀有属性上的薄弱表现。按标签统计的 precision 和 recall 有助于定位具体的失败模式。按样本计算的 intersection over union（IoU）衡量每张图片的预测标签与专家标签的重合程度。九个单标签属性（例如旋转或水印检测）每张图片只有一个正确答案。AWS 团队还用 exact-match accuracy 为它们评分，即答案与专家标签一致的图片占比。

## 把 prompt 优化当作强化学习

有了无偏的评估，你才能开始改进。你无法改进自己无法正确衡量的东西。

这一优化遵循一个类似强化学习的循环。把每一版 prompt 看作一个 agent，把 Micro F1 分数看作奖励信号，把错误分析看作改进的梯度。这一思路类似于 [GEPA（Genetic-Pareto reflective prompt evolution）](https://arxiv.org/abs/2507.19457)：变异 prompt 的各个组成部分、评估适应度、选出幸存者、不断迭代。在本次合作中，AWS 团队主要通过错误分析来完善大多数版本，由 AI 助手检查失败的图片并提出修改。

来自 [DSPy](https://dspy.ai/current/) 库的自动 prompt 优化框架 [MIPROv2](https://dspy.ai/current/api/optimizers/MIPROv2/)，在 v27 中为照片分类任务补充了这一人工流程。

### 起点

第一个 prompt（v0）使用通用的分类指令，此处为便于说明做了简化：

> “把这张图片归入以下类别之一：Living Room、Kitchen、Bedroom、Bathroom……”

专有模型 A 是 Property Finder 的生产基线，在 256 张图片的开发集上 Micro F1 为 0.55。它使用的是 v22，即为该模型族调优过的 prompt。v21 之前的分数来自更早的单标签设置，不能直接比较。

### 逐版迭代

AWS 团队在多个候选模型上测试了早期版本，并加入了结构化输出格式和属性专属定义。

最有启发的修正来自图片级错误分析。在早期的单标签版本中，模型总是把透过门洞看到的房间归类为次要房间类型。AWS Generative AI Innovation Center 团队加入了明确指令：以占据画面主体的房间为准进行分类。后来转向多标签输出，则保留主房间作为标签，并允许透过门洞看到的房间作为附加标签。

区域化定制带来了下一项提升。在某些地区，房源照片会带有装饰性的阿拉伯文叠字，而它们并不是水印。针对这类文字制定规则，消除了一整类误报。

v21 版 prompt 把照片分类和房间类别切换为多标签输出，并成为每个模型共享的起始 prompt。用它时，来自 Meta 的 [Llama 4 Maverick 17B Instruct](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html) 在开发集上取得 0.75 的 Micro F1。此后，AWS 团队分别针对每个模型调优其 prompt。对这个模型，v24 针对房间面积高估、多标签处理和输出格式；接着 v25 这一自动优化版本把关键任务前置。在 v27 中，MIPROv2 重构了照片分类任务，该模型在这一任务上的 Micro F1 达到 0.76。

### 终点

最终的 prompt 是 v27_PF，即 v27 加上 Property Finder 为效果图、带边框或画框的图片以及走廊补充的规则。与 v27 一样，它保留阿拉伯文规则和输出格式指令。每次模型调用之后都有一个归一化步骤，处理剩余的格式差异。

使用 v27_PF 时，Llama 4 Maverick 17B Instruct 在 356 张图片的评估集上取得 0.80 的 Micro F1，而专有模型 A 用 v22 为 0.56。评估集包含那 256 张开发图片，且两个模型的 prompt 都在这些图片上调优过。因此这些分数偏乐观。

从专有模型 A 切换到 Llama 4 Maverick 17B Instruct（各自使用自己调优过的 prompt），使开发集上的 Micro F1 从 0.55 提升到 0.81，相对提升 47%。仅就 Llama 4 Maverick 17B Instruct 的 prompt 调优而言，则把分数从共享 v21 prompt 时的 0.75 提升到 v27 时的 0.81。

## 失败方案的教训

并非所有尝试都成功。*2-bucket* 方案把水印属性和其他属性放在两次独立的 API 调用中，没有带来多少有意义的准确率提升。带边框图片检测还大幅下降。由于同一 prompt 中没有水印属性，模型把水印叠字误认为图片边框。

通用 prompt 无论用在哪个模型上也都失败了。房地产图像领域特异性太强，不适合一刀切的指令。

## 结果：成本、准确率与速度

AWS Generative AI Innovation Center 团队用这套无偏评估框架在 Amazon Bedrock 上评估了多个模型。所有模型都从共享的 v21 prompt 出发，然后在开发集上针对各自的模型族调优。专有模型 A 只做了一轮调优（v22）。Llama 4 Maverick 17B Instruct 做了多轮（v24 到 v27），再加上 Property Finder 的边缘案例规则，因此背后投入的调优更多。最终与专有模型 A 的对比使用的是 356 张图片的评估集。Property Finder 基于全部 11 项属性的准确率和成本效益，为生产工作负载选择了 Llama 4 Maverick 17B Instruct。各区域的模型可用情况，请参阅 [Amazon Bedrock 中各 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

下表展示 Llama 4 Maverick 17B Instruct（v27_PF）在 356 张图片评估集上各单标签属性达到的 exact-match accuracy。九个属性中有六个达到 90% 或更高，并在全部 11 项属性上达到或超过专有模型 A。在每张图片可能有多个标签的照片分类上，两者得分相同。

### 每 1,000 张图片的成本

Property Finder 每天要为数万张图片评分，因此单张图片的成本很重要。Llama 4 Maverick 17B Instruct 是一个高性价比的 open-weight 模型，而且流水线在一次调用中就能获取一张图片的全部属性。

| **结果** | **数值** |
| --- | --- |
| 每 1,000 张图片的估计成本 | **$2.35** |
| 相比 Property Finder 原方案的成本降幅 | **86%** |

这些数字是截至 2025 年 12 月在美国东部（俄亥俄）区域的估算。Llama 4 Maverick 17B Instruct 的数字假设每张图片 9,000 个输入 token 和 200 个输出 token，来自最初的双调用成本分析。使用生产 prompt 的单次调用携带约 7,500–8,000 个输入 token，因此这是一个偏高的估算。86% 是与 Property Finder 原方案（使用 v21 prompt）的成本分析估算相比得出的。准确率对比使用的是由 v21 调优而来的 v22，其成本可能不同。当前价格请参阅 [Amazon Bedrock pricing](https://aws.amazon.com/bedrock/pricing/)。

### 推理速度

Property Finder 已在生产中运行这条优化后的流水线，每天在 Amazon Bedrock 上用 Llama 4 Maverick 17B Instruct 处理数万张图片。据其自身的监控，相比原方案，推理延迟下降了 40–60%。

## 把它用在你自己的工作负载上

先从审计你的评估标签开始。如果它们来自模型预测而非人类专家，那你就存在与 Property Finder 相同的偏差问题。

为几百个有代表性的样本构建由领域专家给出的 ground truth，并保留一个绝不用于调优的独立测试划分。当你的分类任务涉及相互重叠的属性时，采用多标签指标。然后用图片错误分析迭代 prompt，把每一轮迭代视为进化优化循环中的一代。

部署这样的流水线时，要加入负责任 AI 的控制措施。例如，你可以用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 强制执行内容策略并过滤不当的模型输出。这条流水线中的属性预测并不附带经过校准的置信度分数，因此要用一个实用的信号来挑选需要人工复核的图片。模型分歧就是这样一个信号：当两个模型对某个属性给出不同答案时，这张图片往往确实存在歧义。对每张图片都跑第二个模型会增加成本，所以可以先从抽样开始。在依赖这一信号之前，先在你的开发集上检查它抓出真实错误的频率。

## 结论

本文介绍了 Property Finder 如何识别评估偏差、构建无偏的 ground truth，并应用进化式 prompt 优化，通过在 Amazon Bedrock 上进行模型选择，以更低的成本获得更好的准确率。

要取得这样的结果，需要三个要素共同到位：能诚实衡量的无偏评估；无需重建平台即可在模型族之间评估和切换的灵活性；以及针对领域精心演化出的 prompt。Amazon Bedrock 提供了基础：它让 Property Finder 通过单一 API 访问多个模型族，继承 AWS 的治理与安全控制，并且能够在新模型可用时加以采用而无需改动基础设施。

要开始在 Amazon Bedrock 上做模型评估与选择，请访问 [Amazon Bedrock 文档](https://docs.aws.amazon.com/bedrock/)。如果你需要大规模处理视觉工作负载，并希望获得构建无偏评估框架的帮助，请联系 [AWS Generative AI Innovation Center](https://aws.amazon.com/ai/generative-ai/innovation-center/)。
