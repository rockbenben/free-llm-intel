# 免手动操作的首次损失通知：用 Strands Agents 与 Amazon Bedrock AgentCore Browser Tool 实现智能理赔受理

把多模态的首次损失通知（FNOL）证据转化为已打标签、可直接决策的受理数据，让理赔员从上下文出发，而不是从原始材料开始。

人工 FNOL 处理会把大量专家时间消耗在重复性任务上，因为非结构化、多模态的证据必须经由为人类交互而设计的门户来解读。现场拍摄的照片、环车检查（walkaround）视频、扫描文档，以及口述或录制的笔记，全都在受理环节进入系统，而这一环节的决策会直接影响理赔周期时长、下游准确性与客户体验。

在各类保险业务线中，这一时刻的复杂度极具迷惑性。FNOL 受理常被描述成“只是开个案件”，但实际上，正是在这里，海量非结构化数据必须先被解读、校验并相互关联，任何有意义的决策才有可能开始。

挑战相当可观：理赔专业人员把过多时间花在重复性的受理校验上。在把专业能力用于更高价值决策之前，他们必须先操作门户、核验证据是否完整、解读各类材料，这要耗费大量时间。行业观察显示，在初次理赔处理期间，受理校验可能占用理赔员相当大比例的时间，典型提交件在评估开始前都需要大量屏幕上的操作。当巨灾事件或季节性高峰带来业务量激增时，这些延迟会叠加放大，形成积压，拖慢理赔结案并影响客户体验。

在本文中，我们演示一套免手动操作的 FNOL 受理系统如何把用 Strands Agents SDK 构建、负责领域推理的 agent，与负责实时门户交互的 Amazon Bedrock AgentCore Browser Tool 结合起来。这种做法在去掉重复性屏幕操作的同时，保留了人的专业判断。

该方案组合了两项互补能力：

[Strands Agents](https://strandsagents.com/latest/) 是一个开源 SDK，采用模型驱动（model-driven）的方式来构建生成式 AI agent。在这一架构中，这些 agent（用 Strands Agents 构建）会应用保险业特有的业务规则，例如证据解读、跨模态关联，以及基于通过 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 提供的基础模型（FM）做理赔复杂度评估。

浏览器推理由 [Amazon Nova Act](https://docs.aws.amazon.com/nova-act/latest/userguide/what-is-nova-act.html) 完成，这是一个客户端 SDK，它解释自然语言指令（例如“打开下一个未处理的理赔案件”或“触发图像分析”），并把这些指令转化为有据可依的 UI 操作。[Amazon Bedrock AgentCore Browser tool](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-bedrock-agentcore-browser-tool/) 则提供受管、隔离的 Chrome 会话，Nova Act 连接到该会话以执行这些操作。AgentCore Browser Tool 还提供会话录制与实时查看（live view）能力，用于可观测性。

在这一工作流中，Nova Act 通过 AgentCore Browser 会话对屏幕上可见的内容进行推理，从而驱动受理流程；与此同时，基于 Strands 的 agent 在后台执行领域推理。Nova Act 判断证据何时必须被分析，并编排门户交互；领域 agent 则应用与人类审核员相同的领域逻辑，判断证据意味着什么。

结果是把手动的屏幕操作自动化，同时保留人的监督与可审计性。理赔专业人员收到的提交件内容上下文丰富、已完成预分析，可以直接进入判断环节，而不再需要先做校验。打过标签的证据成为一项持久的运营资产，支持更好的路由、模式分析，以及贯穿理赔生命周期的持续工作流优化。

本文用直接从运行中的系统捕获的真实浏览器自动化录制来展示这一工作流。

## 机会所在：优化理赔受理，放大人的专业能力

在各类保险业务线（车险、财产与责任险、寿险、健康险和特种险）中，理赔受理标志着非结构化信息首次进入系统的时刻。照片、视频、扫描文档和录制笔记一起抵达，往往并不完整，标注不一致，也极少标准化。

理赔专业人员在这一刻带入的是深厚的领域知识。他们知道可用的证据长什么样、通常缺什么、各类材料之间如何相互关联，以及哪些信号对承保范围、严重程度和后续步骤至关重要。然而在今天，这些专业能力有很大一部分都要通过缓慢的手工门户操作来施展：在屏幕上逐页点击，逐一目视检查材料。在有意义的评估开始之前，审核员必须回答一些高度依赖经验的根本性问题，包括：必需的材料是否齐全，照片和视频是否可用、是否相关，音频笔记中是否含有实质性陈述，以及这次提交是否足以不再拖延地继续推进。

回答这些问题需要费力的屏幕操作。一份典型的 FNOL 提交件可能包含几十份分散在多个视图中的材料，审核员要定位证据、打开并解读每一项、跨模态关联信号、把发现与保单阈值比对，并为审计的连续性记录摘要。

这些步骤必不可少，但同样重复而机械。它们需要的是注意力，而不是判断力。结果是，熟练的理赔员和审核员在能把专业能力用于更高价值决策之前，不得不把不成比例的时间花在核验受理完整性上。

这一挑战在日常理赔处理中就已存在，而在巨灾事件、季节性车险理赔或健康险与寿险索赔活动激增带来的业务量高峰期间会更加突出。随着工作量上升，积压增多，证据审核变得仓促或前后不一致，人的判断被推迟到本不该那么晚的时刻才介入。

问题不在于缺少专业能力或技术，而在于领域知识在流程中被使用得太晚：时间已经先花在重复性的受理校验上了。

### 为什么把领域知识编码化会改变局面

当关键决策逻辑被写入结构化规则，并在摄入（ingestion）阶段一致地应用，而不是只依赖个人经验与直觉，理赔受理就会提速。

有经验的审核员凭直觉就知道：不同理赔类型需要哪些拍摄角度，什么时候视频可以替代缺失的照片，哪些材料组合意味着更高的复杂度，以及哪些缺口可能会卡住下游处理。

agentic 生成式 AI 让这种实践经验有可能被编码进业务规则和推理工具，并在证据进入系统的过程中被一致地应用。

把 Strands Agents 与 Nova Act、AgentCore Browser Tool 组合起来，就能把操作门户、打开理赔案件、触发分析这类机械性受理工作与领域推理分离开。Nova Act 通过 Browser Tool 会话推进工作流，Strands Agents 则应用专家逻辑来解读、打标签并关联证据。

当证据在摄入阶段就被打上标签，缺失或不充足的材料会被尽早发现，相关性从隐含变为显式，理赔案件可以依据实际已有的内容来做分诊。人类审核员从上下文出发，而不是从零开始。

## 为什么自动证据打标签很重要——现在与将来

自动打标签会在下游步骤开始之前确保受理的完整与清晰，从而加速当前这笔理赔。审核员花在核对基本信息上的时间更少，用在关键处做判断的时间更多。

随着时间推移，被一致打标签的证据会成为持久的数据资产。由于标签由编码化的领域推理生成，而不是一次性的解读，保险公司可以做到以下几点：

- 改进路由与优先级排序
- 减少因提交件不完整导致的返工
- 识别会导致延迟或升级的模式
- 在新场景出现时优化受理规则，同时不改变合规边界或决策权限

随着打标签的证据不断累积，非结构化材料不再是孤立的文件。图像、视频和音频变成可搜索、可分析的信号，支撑新的工作流，例如在检测到常见缺口时主动联系客户、为专业团队预先准备理赔案件，以及缩短未来同类理赔的处理周期。

最重要的是，打标签让领域专业能力只需在摄入时应用一次，就能在整个生命周期内复用，而不必在不同阶段反复重新摸索。

这正是 agentic 自动化带来的转变：把专业能力前移，用结构化信号丰富下游系统，实现更快、更一致的结案处理，同时不把人从环路中移除。

为展示这一转变如何在不需要改动现有门户的情况下落地，下一节将完整走查一套 agentic FNOL 受理架构，它把浏览器层面的自动化与推理驱动的 agent 结合起来。

## 方案概览：不改门户的 agentic 受理

这个原型演示了如何用 agentic 推理与浏览器层面的交互把 FNOL 受理端到端自动化。在生产环境中，同一套浏览器自动化方法可以直接作用于现有门户而无需修改，因为 Nova Act 客户端 SDK 是像人一样与 UI 交互的。

这个原型在构建上尽量贴近真实的生产环境。FNOL 门户与后端服务作为容器化应用运行在 AWS 上，agent 驱动的浏览器自动化则像人类审核员一样与实时门户交互。这种分离让领域推理与 UI 控制可以各自独立演进，同时保留可审计性与运营安全。

从高层面看，本方案假定你大致熟悉现代 agentic 系统在 AWS 上的部署方式，包括使用 FM 做推理、用容器化服务承载应用运行时，以及用事件驱动的存储保存状态与证据。你不需要有传统机器人流程自动化（RPA）工具的经验。这里描述的自动化依赖对 UI 状态的推理，而不是回放预录脚本或硬编码流程。

### AWS 账户与权限

你需要访问一个 AWS 账户，并具备部署和管理本方案所用资源的权限，这些资源包括 [AWS Cloud Development Kit](https://aws.amazon.com/cdk/)（AWS CDK）、[Amazon Elastic Container Service (Amazon ECS) on AWS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/create-cluster-console-v2.html)、[Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/)、[Amazon DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Introduction.html)、[Elastic Load Balancing (Application Load Balancer)](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html)、[Amazon CloudFront](https://aws.amazon.com/cloudfront/getting-started/)，以及 [AWS Identity and Access Management (IAM)](https://aws.amazon.com/iam/) 角色与策略。

部署假定本地已使用 [AWS Command Line Interface (AWS CLI)](https://aws.amazon.com/cli/) 的标准开发配置设好了 AWS 凭证。

### 运行时环境与部署模型

FNOL 受理的用户界面与后端服务（包括用 Strands Agents 实现的证据分析和理赔复杂度评估）被封装为 Docker 容器，部署在采用 AWS Fargate 的 Amazon ECS 上。基础设施通过 AWS CDK 预置，它会在同一个部署工作流中构建容器镜像，并创建所需的计算、存储与网络资源。

图像、视频和转写文本这类非结构化证据材料存放在 Amazon S3 中。理赔元数据、证据引用以及 agent 生成的分析输出持久化在 Amazon DynamoDB 中。这使 agent 能在整个受理过程中检索、关联并推理证据。

### 浏览器自动化的实际运作

agent 驱动的浏览器自动化从独立的控制环境（例如工作站或自动化主机）执行，并通过 AgentCore Browser 会话连接到已部署的 FNOL 应用。这反映了浏览器自动化在真实环境中的常见运行方式。负责浏览器推理的客户端 SDK Nova Act，通过基于 WebSocket 的 Chrome DevTools Protocol（CDP）连接到 AgentCore Browser Tool 提供的受管 Chrome 会话。自动化层通过这个受管浏览器观察实时门户并与之交互，而后端服务仍然独立托管、彼此隔离。

把浏览器控制保持在应用运行时之外，系统得以维持清晰的运营边界。agent 看到的内容与人类审核员在屏幕上看到的完全一致，基于当前 UI 状态做决策，并在不需要直接访问门户内部或应用代码的情况下有意识地采取行动。

### 部署工作流与配置

完整的部署工作流——包括基础设施预置、容器部署、可选的数据生成和浏览器自动化配置——都已通过随附的 [GitHub 仓库](https://github.com/aws-samples/sample-browser-automation-with-agentcore-for-insurance-fnol-claims-queue) 中提供的脚本与配置文件实现自动化。

### 架构概览

从高层面看，该架构由以下互补的层次构成：

- 浏览器交互。Nova Act 通过基于 WebSocket 的 Chrome DevTools Protocol（CDP）连接到 AgentCore Browser Tool 会话，对 FNOL 门户的 UI 状态进行推理，并针对可见内容有意识地执行操作。
- 领域推理。两个 agent 用 Strands Agents SDK 构建：一个是解读并给多模态证据打标签的 *Evidence Analyzer agent*，另一个是评估理赔复杂度的 *Claims Complexity Analyzer agent*。
- 执行可观测性。截图、prompt、推理过程与 UI 状态变迁在每一步都会被自动捕获，无需额外埋点即可产生可复核的审计轨迹。
- 基础设施与持久化。采用 AWS Fargate 的 Amazon ECS 运行应用，Amazon S3 存放证据材料，Amazon DynamoDB 维护理赔状态与分析输出，Amazon CloudWatch 提供运营可见性。

该架构有意分层，以分离门户交互、领域推理、执行可观测性与基础设施关注点，同时保持单一、端到端的 FNOL 受理工作流。agent 驱动的浏览器自动化位于技术栈的顶层，像人类审核员一样与 FNOL 门户交互。领域专属推理由 Strands Agents 独立应用，AWS 基础设施则为执行、持久化与运营可见性提供受管底座。

### 用 Nova Act 与 AgentCore Browser Tool 完成浏览器交互

Nova Act 负责观察 FNOL 门户的用户界面并与之交互，自身不内嵌任何领域逻辑或决策。Nova Act 运行在 AgentCore Browser Tool 会话内，通过 Chrome DevTools Protocol（CDP）连接浏览器，实时对当前 UI 状态进行推理。它在理赔队列中导航、识别尚未处理的证据区块、调用 **Analyze Images**、**Analyze Videos** 和 **Analyze Audio** 操作、与模态对话框交互，并且只在必要时滚动页面，以避免产生非预期的 UI 变化。这种方法让自动化表现得像一位谨慎的人类审核员：观察屏幕上可见的内容，判断哪一项操作合适，并根据当前状态有意识地行动，而不是回放预定义步骤或脆弱的脚本。

### 执行可观测性与可审计性

由于 AgentCore Browser 通过受管浏览器会话执行操作，每一次交互在设计上都是可观测、可追溯的。自动化运行期间，操作可以通过 Chrome DevTools Protocol（CDP）会话实时查看，从而实时掌握 agent 与 FNOL 门户交互的过程。

在每个决策点，系统都会自动截图，同时把 prompt、决策和 UI 状态变迁记录为结构化元数据。这些材料共同构成完整的执行轨迹，使 agent 的行为透明、可复核。你随时都能确定 agent 在屏幕上看到了什么、为什么采取某个具体操作、处理了哪些证据，以及由此得出了什么结论。

这在不引入额外埋点或自定义日志的情况下自然产生了审计轨迹。在受监管的保险环境中，可解释性、可追溯性与运营问责与自动化本身同样重要，因此这是一项不可或缺的能力。

### 在 agent 执行期间捕获截图

在这个原型中，浏览器自动化配置了一个按会话区分的日志目录。当 agent 执行每个 act() 步骤时，Nova Act 会捕获可见的浏览器状态，并把截图与步骤元数据（例如 prompt、时间戳和操作标识符）一并持久化。

这些材料既支持运营排障（它们能揭示 agent 在遇到非预期 UI 状态时究竟观察到了什么），也支持审计或运行后复核，而且不依赖连续的屏幕录制。每次执行都会产生一个独立、带时间戳的文件夹，其中包含截图与日志。这使得每次运行都可复现、可检查，并且能清楚地归属到某个特定会话。

## AWS 上的下游处理与存储

在证据完成分析和打标签之后，AWS 服务提供持久化的底座，用于在整个受理工作流中保存结果、维护理赔状态并支持运营可见性。

两个基于 Strands 的 agent 独立于用户界面处理所有推理驱动的任务。Evidence Analyzer agent 对图像、视频和转写文本执行多模态证据分析，并用结构化元数据打标签；Claims Complexity Analyzer agent 使用专门工具评估理赔复杂度。分析后的材料、摘要和打标签输出存放在 Amazon S3 中，理赔状态、证据引用与 agent 生成的结果则保存在 Amazon DynamoDB 中，以保留一份完整、可查询的记录，说明观察到什么、推断出什么。

运营日志、指标与执行轨迹通过 Amazon CloudWatch 捕获，提供对系统行为的可见性，并满足监控、排障与审计需求。这些组件共同把原始的 FNOL 提交件在摄入阶段就转化为结构化、可直接决策的输入，而这一步发生在理赔被路由或升级去做追加审核之前。这确保下游流程从一开始就拿到一致、上下文丰富且可追溯的信息。

架构就位之后，本文余下部分将跟随系统在实际运行中的表现。接下来几节会走查一个完整的 FNOL 受理序列在实时门户中的展开过程，从 FNOL 队列开始，依次经过证据分析和复杂度分类。每一步都用执行期间捕获的真实浏览器自动化录制与截图来说明，展示 agentic 自动化与领域推理如何实时协同工作。

## 从 FNOL 队列到选择理赔案件

工作流从 FNOL 队列开始。Nova Act 通过 AgentCore Browser Tool 会话观察实时门户状态，依据可见的状态指示器识别下一个可处理的理赔案件，并进入案件详情视图。由于决策基于当前 UI 状态而非预录脚本或硬编码选择器，同一套逻辑可以无需修改地应对新的队列布局、列顺序调整或行数变化。

选定案件并加载其详情视图后，工作流从队列管理进入受理处理。此时详情视图已完成渲染，可用的证据区块也已被识别，为结构化的证据分析下一阶段做好准备。

## 证据分析：跨模态的结构化审核

证据审核通常是 FNOL 受理变慢的地方。执行录制通过展示三个相互独立的操作——**Analyze Images**、**Analyze Videos** 和 **Analyze Audio**——突出了这一点，每个操作对应一条独立的审核路径。这反映了人类审核员逐一模态评估证据的方式，而不是对所有材料做统一对待。

![实际运行中的证据分析按钮](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/01/ML-19303-4.png)

在这一阶段，职责划分得很干净。Nova Act 管理 UI 控制流：判断证据何时就绪、调用合适的分析操作、等待其完成。Strands Agents 运行在服务端，应用保险业特有的推理，其业务规则经过编码化，反映了人类审核员会如何解读每一份材料。这种分离是有意为之：UI 编排决定分析应在*何时*、*何处*发生，领域推理决定*证据意味着什么*。结果与人类审核员的工作方式一致——先识别可用证据，再解读它——同时让每一步都以机器速度执行，并且完全可追溯。

下面的截图展示了分析开始前 Nova Act 观察到的证据区块。Analyze Images、Analyze Videos 和 Analyze Audio 这些控件是依据当前 UI 状态被检测到的，而不是靠硬编码选择器。

![agent 检测到的证据分析操作](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/01/ML-19303-5.png)

### 分析图像：给视觉证据打标签

调用 Analyze Images 时，每一张提交的图像都会被独立评估。Strands Agents 应用保险业特有的业务规则，这些规则反映了有经验的审核员如何解读视觉证据，包括：识别图像描绘的内容（例如车辆损伤、屋顶表面、外墙板、室内或医疗文书）、评估拍摄视角是否适合该理赔类型、确认清晰度与可用性，并标记损伤迹象。这种做法不把解读留在隐含状态，而是给每张图像打上结构化属性标签，使人的判断变得显式、一致，并可在整个理赔生命周期中复用。

下面的截图捕获了图像分析启动时的 UI 状态，图像集合与分析控件对自动化可见，并作为执行轨迹的一部分被记录。分析触发后，模态框打开并展示已提交的图像，Strands Agents 在后台逐一评估。截图展示了这一进行中的状态：评估正在进行，图像证据在屏幕上可见。

![图像分析的启动](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/01/ML-19303-6.png)

### 分析视频：把运动画面当作一等证据

调用 Analyze Videos 时，提交的视频会被当作证据来评估，而不是不透明的附件。Strands Agents 评估每个视频捕捉到了什么：它是否提供了静态图像之外的信息、是否补上了缺失的照片，还是印证或反驳了其他材料。随后，视频衍生出的信号会被打上标签并归一化，与图像和文档一起直接参与下游推理，而不是被当作次要的或需人工处理的审核步骤。

下面的截图捕获了视频分析触发时的门户状态，保留 UI 上下文，使视频评估完全可追溯、可审计。

![视频证据分析状态](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/01/ML-19303-7.png)

### 分析音频：从口头叙述中提取信号

调用 Analyze Audio 时，系统通过对应的通话转写文本来处理音频证据，而不是直接处理原始音频。对每一段录音，都会取回对应的文字转写。随后 Evidence Analyzer Strands Agent 分析转写文本，提取实质性观察与事实陈述、所报告的损伤或状况，以及可补充视觉证据或文档证据的上下文细节。

随后，转写得到的信号会与图像标签和视频标签相互关联，这与人类审核员在受理时把口头上下文与视觉证据相互对照的方式一致。下面的截图捕获了音频分析触发时的门户状态，转写文本对自动化可见。

![音频证据处理状态](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/01/ML-19303-8.png)

综合来看，Analyze Images、Analyze Videos 和 Analyze Audio 这三步产生了一份分层次、可复核的受理记录。AgentCore Browser Tool 在每一步捕获截图与会话活动。Nova Act 记录针对当前 UI 状态所收到的 prompt、所做的推理以及所采取的操作。Strands Agents 则把为每份材料生成的结构化标签与分类推理持久化。

结果是形成一条完整的审计轨迹：屏幕上当时有什么、agent 为什么这样操作、证据是如何被解读的；而所有这些都作为执行过程的副产品产生，而不是靠额外的埋点。

### 为什么这一步重要

到证据分析结束时，每一份图像、视频和音频材料都已被评估并打上标签。没有证据处于未分类状态，质量、相关性与完整性都变为显式信息，而不再靠推断。

这就在下游路由、升级或人工复核发生之前，把原始的 FNOL 提交件转化为结构化、可直接决策的输入，并为下一步对所提交理赔案件做复杂度评估铺好基础。

## 复杂度分析：从已打标签的证据到分诊决策

证据全部打上标签后，agent 会整体评估每个理赔案件。Strands Agents 不只依赖静态的受理字段，而是把理赔元数据与受理过程中观察到的证据衍生信号结合起来，用保险运营团队本就熟悉的规则评估复杂度。这些规则包括跨模态的严重程度指标、证据完整性与内部一致性，以及决定升级或路由的保单阈值。

由于这项评估基于实际提交和观察到的内容，复杂度分类反映的是理赔案件的真实状态，而不是提交时的假设。案件被分为 *Simple* 或 *Complex*。Simple 案件自动结案，Complex 案件则被置为“Needs Review”状态，并自动生成结构化备注，说明案件为何被标记。这些备注为下游使用者提供即时、可执行的上下文。

![带推理备注的理赔复杂度分类](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/01/ML-19303-9.png)

这些截图捕获了复杂度分析完成后的门户状态。证据衍生信号与结构化备注并列展示，使分类依据透明、可复核、可审计。

### 为什么这对保险公司很重要

把人的介入推迟到复杂度评估完成之后，专业能力就会用在恰当的时点——用于解读、判断和结案，而不是受理校验。简单的理赔案件在没有多余摩擦的情况下推进，复杂案件则被尽早暴露出来，且上下文已经就位。这减少了队列污染，避免后期才升级，并在稳定运营与业务量高峰两种情形下都提升了可预测性。

## 人留在环路中，而不是陷在琐事里

这套系统并没有把人从流程中移除，而是改变了人介入的位置。证据已被分析并打上标签，理赔员带着上下文开始工作，而不是面对原始材料。复核取代了重复处理。纠正成为反馈，而不是返工。

随着时间推移，当跨案件出现规律时，这些反馈会渐进地改进业务规则。FNOL 受理从一个瓶颈演化为一个学习系统，持续优化证据如何被解读、如何被路由、如何被处理，而不增加运营负担。

## 为什么这对保险公司很重要

这种方法从根本上改变了专业能力在理赔生命周期中被应用的位置与时机。通过在摄入阶段就结构化多模态证据，保险公司可以自动评估完整性与相关性，从而缩短受理处理时间。理赔推进得更快，在业务量激增时尤其如此，因为更少的提交件会滞留在下游等待校验。

证据解读变得更一致，也更少依赖个别审核员的经验。缺口被尽早识别，减少了下游的更正与返工。同样重要的是，理赔员的认知疲劳更轻，可以把精力放在决策而非校验上。这些能力不需要替换现有系统，也不会打乱既有工作流。自动化所配合的，正是保险公司已经在用的那些门户。

## 超越 FNOL：已打标签的非结构化证据的价值

虽然 FNOL 是入口，但结构化、已打标签的证据的价值延伸到整个理赔生命周期。当非结构化材料在摄入阶段被一致地解读并打上标签后，它们就不再像静态附件那样存在，而是开始作为运营信号发挥作用。

理赔可以依据证据实际显示的内容来路由，而不依赖粗粒度的受理字段或人工分诊。下游工作流在到达时就已预填上下文，包括损伤指标、完整性信号和印证性证据。这减少了每次交接处的摩擦，也把重复校验的需求降到最低。随着跨案件的规律浮现，证据收集指引会自然地改进，帮助保险公司识别常见缺口，并在这些缺口造成下游延迟之前调整受理预期。

随着时间推移，历史理赔可以基于真正提交和观察到的内容来分析，而不只是依据受理时的标注。这使得更深入的运营洞察成为可能：跨地区、跨承保风险（peril）和跨理赔类型的周期时长驱动因素、升级模式与证据质量。已打标签的证据把非结构化文件变成可复用、可查询的数据，在不改变合规边界、决策权限或核心系统的前提下支持更好的决策。

最终结果不只是更快的 FNOL 处理，而是为一个更具适应性、证据驱动的理赔运营打下基础。

## 结论

在本文中，我们展示了免手动操作的 FNOL 受理系统如何把 Strands Agents 与 Amazon Bedrock AgentCore Browser Tool、Amazon Nova Act 结合起来，在证据进入系统的那一刻就把它结构化。FNOL 从一个校验瓶颈转变为一个加速点。理赔推进时上下文已经就位。路由决策由实际提交的内容来支撑。升级发生得更早、更可预测。简单案件无需多余处理即可推进。

这一转变不依赖替换门户、重写现有系统或改变决策权限。它来自把受理中的解读显式化——证据如何被评估、哪些信号有意义、缺口如何影响下游处理——并在摄入阶段一致地应用这种解读。过去需要通过反复人工复核重新推导的东西，变得结构化、持久且可复用。

其成果不是为自动化而自动化，而是更有效地使用判断力。解读只发生一次。证据以可持续的方式被打上标签。这些信号随理赔一起流转，而不是在每个阶段被重新发现。FNOL 受理通过更清晰的信号与更顺畅的流转得到改善，让下游流程从上下文出发，而不是从不确定性出发。
