# 用分布式 KV 缓存 agent skill 降低自托管 LLM 的成本与延迟

越来越多客户在 GPU 上自托管大语言模型（LLM），以便掌控成本、准确性和延迟。然而，自托管往往意味着为重复的 GPU 计算付费，因为每台服务器上小而隔离的缓存无法保存或共享 AI agent 与聊天应用不断重发的、持续增长的上下文。以法律 AI 助手为例，它在每次对话中可能积累数十万 token 的案情历史。当律师午餐后回到某个会话线程时，LLM 的响应可能要花上几分钟。接手该请求的 GPU 服务器内存中没有任何这段历史。因此，GPU 在写出第一个字之前，要重新计算所有这些 token 的键值（KV）注意力状态，这一步称为 prefill。同样的模式也会拖慢恢复运行的编程 agent、agentic AI 助手以及文档问答助手。使用 Amazon ElastiCache 的分布式 KV 缓存，可将自托管 LLM 推理成本降低多达 40%，并将首 token 延迟（TTFT）降低多达 80%。分布式 KV 缓存通过在 GPU 集群旁增设共享层来扩展 GPU 本地缓存，使任何服务器都能在数天内跨会话、路由变化和服务器故障复用 KV 状态。[“Announcing distributed KV caching for self-hosted LLMs with Amazon ElastiCache”](https://aws.amazon.com/blogs/database/announcing-distributed-kv-caching-for-self-hosted-llms-with-amazon-elasticache/)一文深入介绍了技术细节和性能基准测试。

本文详细介绍 Agent Toolkit for AWS 中的[分布式 KV 缓存 skill](https://github.com/aws/agent-toolkit-for-aws/tree/main/skills/specialized-skills/database-skills/distributed-kv-caching)。借助该 skill，你可以在编码 agent 中通过几个提示词完成分布式 KV 缓存的评估与设置。该 skill 引导 agent 检查你的工作负载是否能从分布式 KV 缓存中获益、为测试或生产工作负载搭建缓存集群，以及排查 LLM 推理缓存的问题。该 skill 适用于 [Kiro](https://kiro.dev/)、Claude Code、OpenAI Codex 以及其他支持 Agent Skills 的编码 agent。我们通过四段对话演示该 skill 的工作方式：诊断首 token 缓慢、确定缓存容量与价格、完成设置，以及修复失败的传输。

## 为什么需要 KV 缓存的 skill，它能做什么？

你的工作负载能获得多少收益，取决于所用 LLM 模型、用户流量模式和提示词路由选择等特征，估算起来可能很复杂。我们创建了 [KVTrace 工具](https://github.com/aws-samples/amazon-elasticache-samples/tree/main/kvtrace)，让你在部署任何基础设施之前，基于自己的模型和流量，以不额外收费的方式近似估算工作负载可获得的收益。该 skill 简化了这项评估与设置流程，并在做出任何改动之前引导编码 agent 遵循以下最佳实践：

- **先做适配检查，再花钱。** agent 通过只读的 `describe-instances` 调用读取你的 GPU 集群，并统计 Elastic Fabric Adapter（EFA）接口数量。它只询问自己看不到的信息：推理引擎、模型、张量并行（TP）规模、KV 数据类型、服务器价格，以及提示词的重复频率。当某些条件不匹配时，它会停下来并说明原因。
- **数据来自你的工作负载。** 对于较短的提示词，加载 KV 状态可能比重新计算更耗时。当提示词长度超过某个阈值（切换点）时，读取更划算。该切换点以及提示词的重复频率，决定了缓存是否值这个价钱。agent 使用 KVTrace 基于你自己的流量估算节省额，且不额外收费；如果节省额无法覆盖缓存成本，它就会停止。每个数字都会注明来源。
- **用你现有的技术栈统一管理各推理服务器的配置。** agent 将 LMCache connector 添加到现有的 vLLM 或 SGLang 引擎中，包括 llm-d、Ray Serve 等服务框架下的 vLLM worker。它保留你的路由配置和引擎设置，并把推理集群中的服务器统一为同一套 KV ID 机制（hash 与 seed）和明确的 KV 数据类型。设置一致可避免 key 不匹配——即各服务器写入的 KV 状态彼此找不到。
- **落实最佳实践。** 在承载生产流量之前，agent 会清空本地各层，并检查两次从缓存加载的运行是否给出相同输出，因为布局不匹配可能产生看似正常的命中计数，却给出错误答案。对于创建、修改或删除资源等高影响操作，该 skill 会引导 agent 先取得明确批准。

## 前提条件

从收益估算到设置的这些流程需要以下条件：

- 一个支持 Agent Skills 的编码 agent，例如 Kiro 或 Claude Code。
- 支持 EFA RDMA write 的 GPU 实例，例如 p5。
- LMCache 0.5.8rc1 或更高版本，以及 vLLM 0.11.1 或更高版本（SGLang 0.5.13 或更高版本）。
- ElastiCache for Valkey 9.1 或更高版本，运行在 cache.i8ge.48xlarge 节点上（如果要搭建缓存）。

## 流程 1：分布式 KV 缓存能帮上忙吗？

我们给 agent 这样的提示词：*“我的 vLLM 集群在 p5 实例上为法律助手提供服务，上下文长度为 64K token。返回既有对话时，首 token 需要 13 秒，因为 GPU 每一轮都要重算完整的对话历史。我该如何解决？”*

agent 将请求匹配到该 skill，并在 Kiro 中先请求批准再加载它。回答指出延迟源于冷 prefill，其中有三点对真实部署很重要。第一，它先检查无需新增基础设施的修复方式。如果你关闭了 prefix caching，重新开启可以加快连续多轮对话。如果在会话亲和（session affinity）下 GPU prefix 缓存命中率已高于 90%，你可能并不需要共享 KV 缓存。第二，它识别出法律 AI 助手特有的约束。共享 KV 缓存可能让一个租户通过响应时间判断另一个租户是否发送了相同文本。必须隔离的案例使用独立缓存；共享同一缓存的租户则在 KV hash 中加入各自 ID。第三，它不猜测容量。它会询问模型与 TP 规模、KV 数据类型、副本数量和路由方式，以及用户在轮次之间等待多久。

## 流程 2：估算节省额

为确定节省规模，我们给 agent 一个示例集群：8 台 p5 实例，为一个多轮检索增强生成（RAG）助手处理 64,000 token 的提示词。agent 查询了 GPU 和缓存节点的价格，并从基准测试中推导出 prefill 速率和 KV 大小。最后，agent 建议使用两个 cache.i8ge.48xlarge 节点做分布式 KV 缓存。下图展示了 agent 的汇总及其使用的输入。

![agent 的成本汇总，展示了它查询到的 GPU 与缓存节点价格，以及建议使用的两个 cache.i8ge.48xlarge 节点](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22449-2.png)

图 2：agent 的汇总与输入。它在 AWS 价格清单中查询了两类价格，并说明如何得出重算成本数字

我们没有提供缓存命中率，即缓存可承接的重算 token 占比。因此 agent 给出了几种情景，并建议运行 KVTrace 以确定缓存命中率。KVTrace [记录 KV 缓存事件](https://aws.amazon.com/blogs/database/announcing-distributed-kv-caching-for-self-hosted-llms-with-amazon-elasticache/#savings-for-your-workload)，来源为 vLLM 或 SGLang。然后离线地把这些事件在每个候选容量的共享 KV 缓存上重放。记录器从不写入 token ID 或提示词文本。trace 中保存的是 block hash 和 token 数量。block hash 由 token 内容生成，因此当提示词敏感时请传入 `--anonymize-key-file`。该 skill 会在每台 GPU 服务器上记录一个有代表性的时间窗口，例如一个完整工作日。agent 还指出，只有当你减少服务器数量，或在同样的服务器上承载更多流量时，释放出的 GPU 时间才会转化为实际的金钱节省。

![KVTrace 报告，展示四种缓存命中占比下的净节省、TTFT 基准测试和建议的分片数量](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22449-3.png)

图 3：来自合成演示流量的 KVTrace 报告顶部。它建议采用能达到节省上限 90% 的最小容量。

## 流程 3：搭建分布式 KV 缓存

我们给 agent 的提示词是：“从零开始为 LLM 推理搭建共享 L2 KV 缓存。”在创建任何资源之前，agent 会请求你确认：在预估价格下，在你的可用区中按建议的缓存节点数量进行搭建。确认后，它会创建带 EFA 权限的安全组，以及一个使用含缓存淘汰策略的自定义参数组的 Valkey 9.1 集群。LMCache 会获得[独立的缓存用户](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/distributed-kv-caching-security.html#distributed-kv-caching-security.lmcache-user)，密码存放在 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 中。agent 准备 GPU 服务器，并在每台 GPU 服务器上启动一个 LMCache 服务器。然后用一个小测试对象检查集群，确认重复的提示词可通过远程直接内存访问（RDMA）从缓存加载其 KV 状态。在 GPU 集群上，该 skill 会将实测的 L2 占比与 KVTrace 的预测值进行比对。包含全部命令的完整设置步骤，请参阅 Amazon ElastiCache 文档中的[分布式 KV 缓存入门](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/distributed-kv-caching-getting-started.html)。

## 流程 4：故障排查

> 提示词：“我的 LMCache 服务器能连接 ElastiCache 集群，BLOB.RDMA_HELLO 也成功了，但实际数据传输失败。INFO largeobj 显示 rdma_write_errors 持续上升。哪里出问题了？”

按照该 skill 的故障排查指南，agent 从症状模式进行推理，判断最可能的原因是一个阻止自身成员之间 EFA 流量的安全组。它为你提供了检查和修复该规则的命令。

## 开始使用

你可以从 [Agent Toolkit for AWS](https://aws.amazon.com/products/developer-tools/agent-toolkit-for-aws/) 获取[分布式 KV 缓存](https://github.com/aws/agent-toolkit-for-aws/tree/main/skills/specialized-skills/database-skills/distributed-kv-caching) skill 或 AWS MCP Server。然后描述你遇到的问题，或让你的 AI agent 降低 GPU 集群的成本与延迟，即可开始。想进一步了解 ElastiCache 分布式 KV 缓存及性能基准测试，请参阅 [AWS 博客](https://aws.amazon.com/blogs/database/announcing-distributed-kv-caching-for-self-hosted-llms-with-amazon-elasticache/)。你可以在 [Amazon ElastiCache 文档](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/distributed-kv-caching-getting-started.html)中查看使用 AWS Command Line Interface（AWS CLI）的入门指南，并在 [GitHub repo](https://github.com/aws-samples/amazon-elasticache-samples/tree/main/kvtrace) 了解更多关于 KVTrace 的内容。
