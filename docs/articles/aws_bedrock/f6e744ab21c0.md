# 用分布式 KV 缓存 agent skill 降低自托管 LLM 的成本与延迟

越来越多客户把大语言模型（LLM）自托管在 GPU 上，以便掌控成本、准确性和延迟。但自托管往往意味着为重复的 GPU 计算付费：每台服务器上小而孤立的缓存，既存不下 AI agent 和聊天应用反复发送的不断增长的 context，也无法在服务器之间共享。以一个法律 AI 助手为例，它每次对话可能积累数十万 token 的案情历史。律师午饭后回到某个会话线程时，LLM 的响应可能要等上几分钟。接手这个请求的 GPU 服务器，内存里并没有这段历史。于是 GPU 在写出第一个字之前，要重新计算所有这些 token 的键值（KV）注意力状态——这一步称为 prefill。恢复执行的编码 agent、agentic AI 助手和文档问答助手，也会被同样的模式拖慢。借助 Amazon ElastiCache 的分布式 KV 缓存，自托管 LLM 的推理成本最多可降低 40%，首 token 延迟（TTFT）最多可降低 80%。分布式 KV 缓存会在 GPU 集群旁增设一个共享层，扩展 GPU 本地缓存，让任何服务器都能跨会话、跨路由变化和服务器故障，连续数天复用 KV 状态。[“宣布面向自托管 LLM 的 Amazon ElastiCache 分布式 KV 缓存”](https://aws.amazon.com/blogs/database/announcing-distributed-kv-caching-for-self-hosted-llms-with-amazon-elasticache/)一文深入介绍了技术细节和性能基准。

本文详细介绍 Agent Toolkit for AWS 中的[分布式 KV 缓存 skill](https://github.com/aws/agent-toolkit-for-aws/tree/main/skills/specialized-skills/database-skills/distributed-kv-caching)。借助这个 skill，你可以在编码 agent 里通过几轮 prompt 完成分布式 KV 缓存的评估和搭建。该 skill 会引导 agent 判断你的工作负载能否从分布式 KV 缓存中获益、为测试或生产工作负载搭建缓存集群，以及排查 LLM 推理缓存的问题。该 skill 可用于 [Kiro](https://kiro.dev/)、Claude Code、OpenAI Codex 以及其他支持 Agent Skills 的编码 agent。我们通过四段对话演示该 skill 的工作方式：诊断首 token 缓慢、为缓存定容定价、完成搭建，以及修复一次失败的传输。

## 为什么为 KV 缓存做一个 skill，它能做什么？

你的工作负载能获得多少收益，取决于所用 LLM 模型、用户流量模式和 prompt 路由选择等特征，估算起来可能很复杂。我们开发了 [KVTrace 工具](https://github.com/aws-samples/amazon-elasticache-samples/tree/main/kvtrace)，让你在部署任何基础设施之前，就能基于自己的模型和流量，近似估算工作负载的收益，且不额外收费。该 skill 简化了这项评估和搭建工作，并在改动任何东西之前，引导编码 agent 遵循以下最佳实践：

- **先做适配检查，再花钱。** agent 通过只读的 `describe-instances` 调用读取你的 GPU 集群，统计 Elastic Fabric Adapter（EFA）接口数量。它只询问自己看不到的信息：推理引擎、模型、张量并行（TP）规模、KV 数据类型、服务器价格，以及 prompt 的重复频率。遇到不适用的情况，它会停下来并说明原因。
- **数字来自你的工作负载。** prompt 较短时，加载 KV 状态可能比重新计算更耗时。prompt 长度超过某个阈值（切换点）后，读取更划算。这个切换点和 prompt 的重复频率，决定了缓存是否对得起它的价格。agent 会用 KVTrace 基于你自己的流量估算节省额，不额外收费；如果节省额覆盖不了缓存成本，它就会停下。每个数字都会注明来源。
- **沿用你现有的技术栈，统一管理各推理服务器的配置。** agent 把 LMCache connector 加到你现有的 vLLM 或 SGLang 引擎上，也包括 llm-d、Ray Serve 这类服务框架下的 vLLM worker。它保留你的路由和引擎设置，并把推理集群中的服务器统一到同一套 KV ID 机制（hash 与 seed）和明确的 KV 数据类型上。设置一致可以避免 key 不匹配，也就是各服务器写入的 KV 状态彼此找不到。
- **落实最佳实践。** 在承载生产流量之前，agent 会清空本地各层，并检查两次从缓存加载的运行是否给出相同输出，因为布局不匹配可能让命中计数看起来正常，答案却是错的。对于创建、更改或删除资源这类高影响操作，该 skill 会引导 agent 先取得明确批准。

## 前提条件

从收益估算到搭建的这些 flow，需要满足以下条件：

- 一个支持 Agent Skills 的编码 agent，例如 Kiro 或 Claude Code。
- 支持 EFA RDMA write 的 GPU 实例，例如 p5。
- LMCache 0.5.8rc1 或更高版本，以及 vLLM 0.11.1 或更高版本（SGLang 0.5.13 或更高版本）。
- ElastiCache for Valkey 9.1 或更高版本，运行在 cache.i8ge.48xlarge 节点上（如果是要搭建缓存）。

## Flow 1：分布式 KV 缓存能帮上忙吗？

我们给 agent 这样一段 prompt：*“我的 vLLM 集群在 p5 实例上为法律助手提供服务，context 长度为 64K token。用户回到既有对话时，首 token 要 13 秒，因为 GPU 每一轮都重算完整的对话历史。我该怎么解决？”*

agent 把请求匹配到该 skill，并在 Kiro 中先请求批准，然后才加载它。回答指出延迟来自冷 prefill，其中有三点对真实部署很关键。第一，它先检查无需新增基础设施就能做的修复。如果你关掉了 prefix caching，重新打开可以加快连续多轮对话。如果开启会话亲和（session affinity）后，GPU prefix 缓存命中率已经高于 90%，你可能不需要共享 KV 缓存。第二，它指出法律 AI 助手特有的约束。共享 KV 缓存可能让一个租户根据响应时间判断另一个租户是否发送了相同的文本。必须隔离的案例使用独立缓存；共用缓存的租户则把各自的 ID 加进 KV hash。第三，它不猜容量。它会询问模型和 TP 规模、KV 数据类型、副本数量和路由方式，以及用户在轮次之间等待多久。

## Flow 2：估算节省额

为节省额定量，我们给 agent 一个示例集群：8 台 p5 实例，为一个多轮检索增强生成（RAG）助手处理 64,000 token 的 prompt。agent 查询了 GPU 和缓存节点的价格，又从基准测试推导出 prefill 速率和 KV 大小。最后，agent 建议用两个 cache.i8ge.48xlarge 节点做分布式 KV 缓存。下图展示了 agent 的汇总和它使用的输入。

![agent 的成本汇总，展示了它查询到的 GPU 与缓存节点价格，以及建议使用的两个 cache.i8ge.48xlarge 节点](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22449-2.png)

图 2：agent 的汇总和输入。它在 AWS 价格清单中查了这两类价格，并说明了重算数字是怎么算出来的

我们没有提供缓存命中率，也就是缓存能承接的重算 token 占比。因此 agent 给出了几种情景，并建议运行 KVTrace 来确定命中率。KVTrace 会从 vLLM 或 SGLang [记录 KV 缓存事件](https://aws.amazon.com/blogs/database/announcing-distributed-kv-caching-for-self-hosted-llms-with-amazon-elasticache/#savings-for-your-workload)。然后它把这些事件离线重放到各个候选容量的共享 KV 缓存上。记录器从不写入 token ID 或 prompt 文本。trace 里保存的是 block hash 和 token 数量。block hash 由 token 内容生成，所以 prompt 敏感时请传入 `--anonymize-key-file`。该 skill 会在每台 GPU 服务器上记录一个有代表性的时间窗口，例如一个完整工作日。agent 还指出，只有当你减少服务器数量，或在同样的服务器上承载更多流量时，省下来的 GPU 时间才会变成真金白银。

![KVTrace 报告，展示四种缓存命中占比下的净节省、TTFT 基准测试和建议的分片数量](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/20/ML-22449-3.png)

图 3：一份来自合成演示流量的 KVTrace 报告顶部。它建议采用能达到节省上限 90% 的最小容量。

## Flow 3：搭建分布式 KV 缓存

我们给 agent 的 prompt 是：“从零开始，为 LLM 推理搭建一个共享 L2 KV 缓存。”在创建任何东西之前，agent 会请求你确认：按建议的缓存节点数、在预估价格下，在你的可用区中搭建。确认之后，它会创建带 EFA 权限的安全组，以及一个使用自定义参数组（含缓存淘汰策略）的 Valkey 9.1 集群。LMCache 会拿到[自己的缓存用户](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/distributed-kv-caching-security.html#distributed-kv-caching-security.lmcache-user)，密码存放在 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 中。agent 准备好 GPU 服务器，并在每台 GPU 服务器上启动一个 LMCache 服务器。然后用一个小测试对象检查集群，确认重复的 prompt 能通过远程直接内存访问（RDMA）从缓存加载 KV 状态。在 GPU 集群上，该 skill 会把实测的 L2 占比与 KVTrace 的预测值做比对。包含全部命令的完整搭建步骤，请参阅 Amazon ElastiCache 文档中的[分布式 KV 缓存入门](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/distributed-kv-caching-getting-started.html)。

## Flow 4：故障排查

> Prompt：“我的 LMCache 服务器能连上 ElastiCache 集群，BLOB.RDMA_HELLO 也成功了，但实际数据传输一直失败。INFO largeobj 显示 rdma_write_errors 不断上升。哪里出了问题？”

按照该 skill 的故障排查指南，agent 从症状模式出发推理，判断最可能的原因是一个安全组挡住了自身成员之间的 EFA 流量。它会给你检查和修复该规则的命令。

## 开始使用

你可以从 [Agent Toolkit for AWS](https://aws.amazon.com/products/developer-tools/agent-toolkit-for-aws/) 获取[分布式 KV 缓存](https://github.com/aws/agent-toolkit-for-aws/tree/main/skills/specialized-skills/database-skills/distributed-kv-caching) skill 或 AWS MCP Server。然后描述你遇到的问题，或者让你的 AI agent 去降低 GPU 集群的成本与延迟，就可以开始了。想进一步了解 ElastiCache 分布式 KV 缓存和性能基准，请参阅 [AWS 博客](https://aws.amazon.com/blogs/database/announcing-distributed-kv-caching-for-self-hosted-llms-with-amazon-elasticache/)。使用 AWS Command Line Interface（AWS CLI）的入门步骤见 [Amazon ElastiCache 文档](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/distributed-kv-caching-getting-started.html)，KVTrace 的更多信息见 [GitHub repo](https://github.com/aws-samples/amazon-elasticache-samples/tree/main/kvtrace)。
