# 使用 Amazon Bedrock 生成训练数据并以低成本训练分类模型

本文探讨如何使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 生成高质量的类别型真实基准数据（ground truth），这对在成本敏感的环境中训练机器学习（ML）模型至关重要。[生成式 AI](https://aws.amazon.com/ai/generative-ai/) 方案可以在模型开发阶段发挥不可替代的作用，为多分类监督学习用例简化训练与测试数据的构建。我们会深入这一过程：如何用 XML 标签组织 prompt，引导 Amazon Bedrock 生成类别均衡且准确率高的标签数据集。我们还会展示一个真实示例，用于预测支持工单的根本原因类别。这一可用 ML 解决的用例，能帮助支持团队更好地理解客户需求并优化应对策略。

## 业务挑战

本文描述的探索与方法论针对两个关键挑战：为多分类用例生成真实基准数据集的相关成本可能高得让人却步；而用于生成真实基准数据的传统做法与合成数据集构建策略，在生成均衡类别、以及满足真实用例所需性能参数方面都不够。

### 真实基准数据的生成既昂贵又耗时

真实基准（ground truth）标注必须准确且一致，往往需要投入大量时间与专业能力，才能确保数据集均衡、多样，并且规模足以支撑模型训练与测试。对于支持工单根本原因归类这样的多分类问题，这一挑战会成倍放大。

假设手头的任务是为客户支持工单预测根本原因类别（Customer Education、Feature Request、Software Defect、Documentation Improvement、Security Awareness 与 Billing Inquiry）。基于我们使用 [AutoGluon](https://auto.gluon.ai/) 中可用的最佳监督学习算法所做的实验，我们得出：要让准确率达到 90%，每个类别的训练数据集需要 3,000 个样本的规模。这一要求意味着要投入受过训练的人员（可能是支持工程师或其他技术人员）的时间与精力，去审阅数万条支持工单，才能得到每类 3,000 条的均匀分布。假设每条支持工单及相关往来邮件平均需要人工标注者 5 分钟来审阅和评估，这就相当于 1,500 小时（5 分钟 × 18,000 条支持工单）的工作量；按 8 小时工作日计算约为 188 天。除了审阅与标注的时间，前期还需要投入培训标注者的成本，好让拆分给 10 名或更多标注者的工作保持一致。再进一步拆解：如果把一场真实基准标注活动拆分给 10 名标注者，在每人每周投入 40 小时的情况下，标注 18,000 条工单需要接近 4 周。

这样一场周期长、投入大的活动不仅昂贵，而且每当标注者把任务搁下、过一阵再回来继续时，各分类的标注都可能变得不一致。这项活动也不能保证得到类别均衡的标注真实基准数据集，因为像 Customer Education 这样的根本原因类别可能远比 Feature Request 或 Software Defect 常见，从而进一步拉长活动周期。

### 获得均衡类别的常规手段或合成数据生成方式存在不足

对多分类用例而言，均衡的标注数据集至关重要，它可以减轻偏差，确保模型学会准确分类所有类别，而不是偏向多数类。如果数据集不均衡，一个或多个类别的实例数明显少于其他类别，模型可能难以学到少数类相关的模式与特征，导致表现不佳、预测有偏差。在少数类的准确分类至关重要的应用中——例如医学诊断、欺诈检测或根本原因归类——这一问题尤其突出。在为支持工单的根本原因类别打标签这一用例中，为 Software Defect、Feature Request 与 Documentation Improvement 等类别找到可标注的样本，通常比 Customer Education 更困难。这就造成训练集与测试集的类别分布不均衡。

为应对这一挑战，可以采用多种技术，包括对少数类过采样、对多数类欠采样、使用集成方法把在不同数据子集上训练出的多个分类器组合起来，或通过合成数据生成来扩充少数类。不过，要获得最佳性能，理想的做法是从一份均衡且高度准确的标注数据集出发，用于真实基准的训练。

对少数类过采样意味着要由人工审阅支持工单，标注周期长、成本高；而用合成数据生成来扩充少数类也有自身的难题。对于为支持工单数据打标签这一多分类问题，合成数据生成很快就会导致[过拟合](https://aws.amazon.com/what-is/overfitting/#:~:text=Overfitting%20is%20an%20undesirable%20machine,all%20types%20of%20new%20data)。这是因为，要合成出真实世界中技术工单往来邮件的例子相当困难，这些内容涉及软件配置、实施指导、文档引用、技术排查等复杂信息。

由于真实基准标注成本高昂，而合成数据生成对根本原因预测这类用例又不可行，训练模型的努力常被搁置。这就错失了审视根本原因趋势的机会——而这些趋势本可以指导资源投入到正确的方向，例如客户教育、文档改进，或其他能减少工单量、改善客户体验的举措。

## 方案概览

上一节讨论了为什么传统的真实基准数据生成技术对某些监督学习用例并不可行，以及在我们的示例中，它们在训练一个能高准确率预测支持工单根本原因的模型方面为何不够。下面看看生成式 AI 如何帮助解决这一问题。

生成式 AI 支持内容创作、摘要、代码生成、创意应用、数据增强、自然语言处理、科学研究等众多关键用例。Amazon Bedrock 非常适合承担这项数据增强工作，用来生成高质量的真实基准数据。借助经过高度调优、量身定制的 prompt，配合下面几节讨论的示例与技巧，支持团队可以把匿名化后的支持工单往来邮件传给 [Amazon Bedrock 上的 Anthropic Claude 3.5 Sonnet](https://aws.amazon.com/bedrock/claude/) 或其他可用的大语言模型（LLM），从众多类别（Customer Education、Feature Request、Software Defect、Documentation Improvement、Security Awareness 与 Billing Inquiry）中预测一条支持工单的根本原因标签。达到期望的准确率之后，你就可以在 ML pipeline 中使用这些真实基准数据，配合 AutoGluon 这类自动化机器学习（AutoML）工具训练模型，并对支持工单做推理。

### 检查 LLM 在真实基准数据上的准确率

要用 LLM 完成类别标注任务并对其进行评估，流程的第一步是判断是否有可用的标注数据。如果有标注数据，下一步要检查该模型的用例是否产生离散结果。在既有标注数据、又有离散结果的情况下，可以使用精确率、召回率等标准 ML 方法或其他经典 ML 指标。这些指标精度高，但受限于可用的真实基准数据有限，只适用于特定用例。

如果用例不产生离散输出，那么任务专属的指标更合适。这包括用于文本相似度的 ROUGE 或余弦相似度等指标，以及评估有害性（Detoxify）、prompt 刻板印象（交叉熵损失）或事实知识（HELM、LAMA）的专门基准。

如果没有标注数据，下一个问题是测试流程是否应当自动化。这一决策取决于成本与准确率的权衡，因为更高的准确率意味着更高的成本。对于不需要自动化的场景，可以采用 human-in-the-Loop（HIL）方式。这涉及依据预定义的评估规则（例如 ground truth）做人工评估，评估精度高，但往往耗时且成本高。

如果倾向于自动化，用另一个 LLM 来评估输出可能是有效做法。这里可以指示一个可靠的 LLM 给生成的输出打分，并提供自动化的分数与解释。不过，这种方法的精度取决于所选 LLM 的可靠性。每条路径都是依据标注数据的可获得性与自动化需求而定制的做法，使得评估各类 FM 应用时具有灵活性。

就本用例而言，如果已有 1 万条或更多支持工单借助 [Amazon SageMaker Ground Truth](https://aws.amazon.com/sagemaker/groundtruth/)、以 HIL 方式标注好的历史集合，就可以用它来评估 LLM 预测的准确率。使用 Amazon Bedrock 生成新真实基准数据的关键目标应当是扩充它，以增加多样性、增大 AutoGluon 训练的数据规模，从而得到一个性能良好、可用于最终推理或根本原因预测的模型。在下面几节中，我们说明如何通过 prompt engineering，采取循序渐进、有分寸的方式来提升 Anthropic Claude 3.5 Sonnet 的预测准确率。

### 为提升 FM 准确率与一致性而做 prompt engineering

[Prompt engineering](https://docs.aws.amazon.com/bedrock/latest/userguide/what-is-prompt-engineering.html) 是一门设计与打磨 prompt、让 LLM 产出期望输出的艺术与科学。做实验时，我们建议参考 LLM prompt engineering 的相关文档，例如 [Anthropic prompt engineering](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)。基于在未做精细调优与优化的 prompt 上进行的实验，我们观察到准确率偏低，低于 60%。下面几节中，我们会详细说明如何构建你的第一个 prompt，然后逐步改进它，以稳定达到 90% 以上的准确率。

### 设计 prompt

在开始任何规模化的生成式 AI 使用之前，你应当先具备以下条件：

- 对你试图解决的问题以及最终目标有清晰的定义。
- 一种测试模型输出准确性的方法。用[点赞/点踩](https://docs.aws.amazon.com/sagemaker/latest/dg/clarify-foundation-model-evaluate-overview.html#clarify-foundation-model-evaluate-overview-types)的方式判断准确性，并与通过 SageMaker Ground Truth 得到的 1 万条标注数据集做对比，很适合这项练习。
- 一条明确界定的成功标准，说明模型需要达到多高的准确率。

把 LLM 想象成一位新员工会很有帮助：他读过很多书，但对你的文化、你的规范、你正在做什么、为什么这样做一无所知。LLM 的表现取决于你能多精确地说明你想要什么。一位有经验的管理者会如何对待一位非常聪明、但新来且缺乏经验的员工？管理者会提供背景信息、解释问题、说明分析问题时应当遵循的规则，并给出一些“好的样子”的示例以及为什么好。之后，如果他看到员工犯错，可能会试图简化问题，并通过给出反面示例及其原因来提供建设性反馈。有一处不同：员工会理解自己被聘用要做的这份工作，所以我们需要明确告诉 LLM 去扮演一名支持人员的角色。

## 使用 Anthropic Claude 的原生推理 API 测试代码

下面的代码使用原生推理 API 向 Anthropic Claude 发送一条文本消息。这段 Python 代码调用 Amazon Bedrock Runtime 服务：

```
import boto3
import json
from datetime import datetime
import time

# Create an Amazon Bedrock Runtime client in the AWS Region of your choice.
client = boto3.client("bedrock-runtime", region_name="us-east-1")

# Set the model ID, e.g., Claude 3 Haiku.
model_id = "anthropic.claude-3-5-sonnet-20240620-v1:0"

# Load the prompt from a file (showed and explained later in the blog)
with open('prompt.txt', 'r') as file:
data = file.read()


def callBedrock(body):
# Format the request payload using the model's native structure.

prompt = data + body;

# The prompt is then truncated to the max input window size of Sonnet 3.5
prompt = prompt[:180000]

# Define parametres passed to the model. 
native_request = {
"anthropic_version": "bedrock-2023-05-31",
"max_tokens": 512,
"temperature": 0.2,
"messages": [
{
"role": "user",
"content": [{"type": "text", "text": prompt}],
}
],
}

# Convert the native request to JSON.
request = json.dumps(native_request)

try:
# Invoke the model with the request.
response = client.invoke_model(modelId=model_id, body=request)

except (Exception) as e:
print(f"ERROR: Can't invoke '{model_id}'. Reason: {e}")

# Load the response returned from Amazon Bedrock into a json object
model_response = json.loads(response["body"].read())

# Extract and print the response text.
response_text = model_response["content"][0]["text"]
return response_text;
```

## 分析结果

我们建议取一小批随机工单样本（例如 150 条），用初始 prompt 让 Anthropic Claude 3.5 Sonnet 跑一遍，并人工检查初始结果。你可以把输入数据与模型输出导入 Excel，并添加以下列用于分析：

- **Claude Label** – 一个计算列，填入 Anthropic Claude 给出的类别
- **Label** – 审阅每条工单并选定具体根本原因类别后的真实类别，用于与模型预测对比、得出准确率度量
- **Close Call** – 填 1 或 0，便于做数值平均
- **Notes** – 用于记录工单中有值得注意之处、或归类不准确的工单
- **Claude Correct** – 一个计算列（0 或 1），取决于我们的类别是否与模型输出的类别一致

尽管第一次运行预期准确率偏低、不足以用该 prompt 生成真实基准数据，但其中的推理会帮你理解 Anthropic Claude 为何把这些工单标错。在该示例中，许多错误落在以下几类情形，准确率只有 61%：

- Anthropic Claude 把 Customer Education 类工单归为 Software Defect，因为它把支持人员要求重新配置某物的说明理解成了 Software Defect 的临时绕行方案。
- 用户提出计费相关问题时，Anthropic Claude 把它们归为 Customer Education。虽然计费问题也可以算 Customer Education 工单，但我们希望将其归为更具体的 Billing Inquiry。同样，虽然 Security Awareness 工单也属于 Customer Education，但我们希望把它们归入更具体的 Security Awareness 类别。

## 迭代 prompt 并做出调整

就如何纠正这些错误向 LLM 提供明确指令，应当能带来准确率的显著提升。我们用 Anthropic Claude 测试了以下调整：

- 我们为 LLM 定义并赋予了一个带背景信息的人设：“你是一名支持人员，是企业应用软件方面的专家。你将把客户工单分类到各个类别中……”
- 我们按从更确定、定义更清晰到更不具体的顺序排列类别，并指示 Anthropic Claude 按 prompt 中出现的顺序评估各类别。
- 我们建议采用 Anthropic 文档中的建议，[使用 XML 标签](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/use-xml-tags)，把根本原因类别包裹在轻量 XML（而非正式的 XML 文档）中，各元素用标签分隔。理想做法是把类别建成节点，每个类别各有自己的子节点。类别节点应当包含类别名称、描述以及输出大致长什么样。各类别应当由起止标签界定。

```
You are a Support Agent and an expert on the enterprise application software. You will be classifying the customer support cases into categories, based on the given interaction between an agent and a customer. You can only choose ONE Category from the list below. You follow instructions well, step by step, and evaluate the categories in the order they appear in the prompt when making a decision.

The categories are defined as:

<categories>
<category>
<name>
"Software Defect"
</name>
<description>
“Software Defect” are cases where the application software does not work as expected. The agent confirms the application is not working as expected and may refer to internal team working on a fix or patch to address the bug or defect. The category includes common errors or failures related to performance, software version, functional defect, unexpected exception or usability bug when the customer is following the documented steps.
</description>
</category>
...
</categories>
```

以下是解析输出的代码：

```
# This python script parses LLM output into a comma separated list with the SupportID, Category, Reason
# Command line is python parse_llm_putput.py PathToLLMOutput.txt PathToParsedOutput.csv
# Note:  It will overwrite the output file without confirming
# it will write completion status and any error messages to stdout
 
import re
import sys
 
# these tokens are based on the format of the claude output.
# This will create three inputs CaseID, RootCause and Reasoning.  We will to extract them using re.match.
pattern = re.compile(
    "^([0-9]*).*<classification>(.*)</classification><explanation>(.*)</explanation>"
)
 
endToken = "</response>"
checkToken = "<classification>"
 
acceptableClassifications = [
    "Billing Inquiry",
    "Documentation Improvement",
    "Feature Request",
    "Security Awareness",
    "Software Defect",
    "Customer Education",
]
 
def parseResponse(response):
    # parsing is trivial withe regular expression groups
    m = pattern.match(response)
    return m
 
# get the input and output files
if len(sys.argv) != 3:
    print("Command line error parse_llm_output.py inputfile outputfile")
    exit(1)
 
# open the file
input = open(sys.argv[1], encoding="utf8")
output = open(sys.argv[2], "w")
 
# read the entire file in.  This works well with 30,000 responses, but would need to be adjusted for say 3,000,000 responses
responses = input.read()
 
# get rid of the double quotes and newlines to avoid incorrect excel parsing and these are unnecessary
responses = responses.replace('"', "")
responses = responses.replace("\n", "")
 
# initialize our placeholder, and counters
parsedChars = 0
skipped = 0
invalid = 0
responseCount = 0
 
# write the header
output.write("CaseID,RootCause,Reason\n")
 
# find the first response
index = responses.find(endToken, parsedChars)
 
while index > 0:
    # extract the response
    response = responses[parsedChars : index + len(endToken)]
    # parse it
    parsedResponse = parseResponse(response)
 
    # is the response valid
    if parsedResponse is None or len(response.split(checkToken)) != 2:
        # this happens when there is a missing /response delimiter or some other formatting problem, it clutters up and the next response
        skipped = skipped + 2
    else:
        # if we have a valid response write it to the file, enclose the reason in double quotes because it uses commas
        if parsedResponse.group(2).lower() not in acceptableClassifications:
            # make sure the classification is one we expect
            print("Invalid Classification: {0}".format(parsedResponse.group(2)))
            invalid = invalid + 1
        else:
            # write a valid line to the output file
            output.write(
                '{0},{1},"{2}"\n'.format(
                    parsedResponse.group(1),
                    parsedResponse.group(2),
                    parsedResponse.group(3),
                )
            )
 
    # move the pointer past where we parsed and update the counter
    parsedChars = index + len(endToken)
    responseCount = responseCount + 1
 
    # find the next response
    index = responses.find(endToken, parsedChars)
 
print("skipped {0} of {1} responses".format(skipped, responseCount))
print("{0} of these were invalid".format(invalid)) 
```

大多数被标错的工单都属于难以判定的情形，或具有非常相似的特征。例如，客户描述了一个问题，支持人员给出可能的解决方案并要求提供日志以便排查；但客户自行解决了该工单，因此解决细节并不具有决定性。对这类场景，根本原因预测就不准确。在我们的实验中，Anthropic Claude 把这些工单标为 Software Defect，但最可能的情形是客户自己想明白了，从此没有再跟进。

持续微调 prompt 以调整示例、逐步纳入这类场景，有助于把预测准确率提升到 90% 以上，这一点我们已通过实验确认。下面的代码展示了如何调整 prompt 并再添加几个 bad examples：
