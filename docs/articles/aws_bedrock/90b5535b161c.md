# 在 Amazon Bedrock AgentCore 中构建自定义的基于代码的 evaluator

*特别感谢为本次发布做出贡献的所有人：Stephanie Yuan、Lefan Zhang、Ritvika Pillai、Irene Wang、Carter Williams、T.J Ariyawansa、Gitika Jha、Shoaib Javed，以及来自产品领导团队的 Vivek Singh。*

要把原型阶段的 agent 推向生产，需要从多个维度衡量质量。[Amazon Bedrock AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 提供大语言模型（LLM）作为评判者（LLM-as-a-Judge）的检查，以及可扩展的基于代码的 evaluator，用来覆盖评估 agentic 应用时所需的领域特定要求。

在金融服务和专业化领域，关键的质量维度往往超出语言层面。一个市场情报 agent 必须把股票报价限制在可配置的实时区间内，在访问财务档案之前遵循强制的经纪人身份识别工作流，返回符合严格 JSON schema 的工具输出，并且不泄露个人可识别信息（PII）。这些检查需要确定性的代码，对相同输入产生相同结果。而在客观的一段代码就是最直接选择的情况下，用 LLM-as-a-Judge 来跑这些检查也可能很昂贵。

借助[自定义的基于代码的 evaluator](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/code-based-evaluators.html)，你可以把 [AWS Lambda](https://aws.amazon.com/pm/lambda/) 函数作为评估引擎。使用自定义的基于代码的 evaluator 时，评分逻辑由你掌控：正则与结构校验、外部数据查询、调用其他服务，或业务规则。同一个 evaluator 可以多种方式复用，而无需为每次请求消耗 foundation model（FM）的 token。在按需评估（on-demand evaluation）中，它充当开发工作流和持续集成与交付（CI/CD）pipeline 中的一道关卡。在在线评估（online evaluation）设置中，它可以为线上生产流量打分。通过 AWS Lambda 完全掌控评估逻辑，你可以按需定制自定义的基于代码的 evaluator。即便 trace 来自不同的 agent 框架，你也可以用这种做法，按自己的逻辑一致地评估 agent 质量。

本文将为一个金融市场情报 agent 实现四个基于 Lambda 的自定义代码 evaluator，把它们逐一注册到 AgentCore，并以按需和在线两种模式运行。你还会看到如何把自定义的基于代码的 evaluator 与内置 evaluator 组合使用，以及如何调用其他 AWS 服务来做有依据的事实核查、PII 检测和实时告警。

## 适合用代码评估的质量维度

agent 依赖来自搜索、检索或业务 API 的结构化工具输出，例如 JSON。契约变更、解析 bug 或上游故障都可能产生畸形数据，再被 agent 编织进错误答案。工具响应的 schema 校验能在工具边界截住结构性问题，非常适合作为基于代码的检查；而 LLM-as-a-Judge evaluator 则可以补上对有用性和清晰度的评判。

agent 会引用价格、指标、阈值和配额，而小至 0.1% 的偏差就可能改变一笔金融交易决策。LLM 容易出现算术错误，而基于代码的 evaluator 会调用参考系统、计算容差，并逐项标记差异。对照参考源的数值准确性，用确定性方式验证最为有效。

在顺序与策略约束下工作的 agent，应当在读取敏感数据前识别用户身份，在执行操作前取得批准，并遵循特定的工具调用顺序以维持数据完整性。验证工作流契约的合规性，需要检查一个会话内工具调用的先后顺序。基于代码的 evaluator 检查 agent 是否遵循了流程，LLM-as-a-Judge 则衡量它对结果的表达是否到位。

在处理档案、文档或日志时，agent 必须隐藏姓名、账户 ID、联系方式与密钥。泄露这些数据的响应属于合规或安全失败。基于代码的 evaluator 会调用 PII 检测或密钥扫描服务，对响应内容执行硬性规则，与语言质量和有用性评分形成互补。

与 LLM-as-a-Judge evaluator 配合使用时，基于代码的检查既能验证 agent 的表达方式，也能验证它是否遵守了契约、数值、工作流和数据处理规则。这一组合把 agent 的可靠性从“听起来对”推进到“契约已验证”。

## evaluator 生命周期：从 span 到评分结果

基于代码的 evaluator 就是注册到 AgentCore 控制面的一个 Lambda 函数。评估运行时，AgentCore 会代入你账户中的 AWS Identity and Access Management（IAM）角色，用包含该 agent 的 OpenTelemetry（OTel）span 的 payload 调用该 Lambda，并把 Lambda 的响应作为评估结果写入 Amazon CloudWatch Logs。payload 包含 schema 版本、evaluator ID、evaluator 名称、评估层级，以及一个持有该会话 OTel span 数组的评估输入对象。对于 trace 级 evaluator，另有一个评估目标字段指明要打分的具体 trace。对于 session 级 evaluator，AgentCore 会省略该目标，由 Lambda 对整段对话打分。

Lambda 的响应遵循固定契约。成功时，它返回一个字典，其中包含 label（例如 PASS 或 FAIL）、一个可选的 0.0–1.0 之间的数值分数，以及一个可选的说明字符串。失败时，它返回包含错误码和错误消息的字典。每个成功响应都必须包含 label。score 和 explanation 字段是可选的，但它们会直接进入 CloudWatch 指标和 AgentCore Observability 仪表板，在你分数偏低时帮助你排查。每个 evaluator 都在注册时设定的三种层级之一上运行：TRACE、TOOL_CALL 或 SESSION，如下图所示。若想用同一个 Lambda 在多个层级上打分，需要在每个层级分别注册，并指向同一个函数。

## 自定义基于代码的 evaluator 的按需与在线模式

AgentCore Evaluations 在按需和在线两种模式下都支持基于代码的 evaluator。同一个 evaluator ID 可用于开发、测试、持续集成与交付（CI/CD）关卡，以及持续的生产监控。Lambda 契约——包括 payload、响应格式和 IAM 配置——在两种模式下都保持不变。下图展示了在线评估的流程；按需评估走同一条路径，只是用 Evaluate API 调用替代了定时采样步骤。

## **用于开发与 CI/CD 的按需评估**

按需评估适用于三种场景：

- 开发迭代。捕获一个会话，运行 evaluator 套件，查看每个 evaluator 的分数与说明，并用这些反馈指导下一步对 prompt、工具定义或 memory 工作流的修改。
- 回归测试。维护一个代表性会话库，其中包括此前暴露出失败的会话，然后在你的测试套件中对它们运行 evaluator 套件。得分低于阈值的 evaluator 就表示出现了回归。
- CI/CD 部署关卡。在把新的 agent 版本推上生产之前，对一组冒烟测试会话运行 evaluator 套件，若有基于代码的 evaluator 失败就阻止部署。

一次按需调用最多可以引用 10 个 evaluator，涵盖基于代码的类型和内置类型。对于 Market Trends Agent，部署前的一轮检查会同时运行 Helpfulness 和 Correctness 两个内置 evaluator 与四个基于代码的 evaluator。合并后的结果一次性确认了语言质量、工具契约完整性、价格准确性、工作流顺序和 PII 安全性。

## **用于持续生产监控的在线评估**

在线评估会持续采样线上的 agent 流量，并按固定周期用已配置的 evaluator 为其打分。要设置在线评估，你需要通过 AgentCore 控制面创建一次在线评估配置，并指定以下内容：

- Evaluators：最多 10 个 evaluator ID，可混用基于代码与内置类型
- 数据源：存放该 agent span 的 CloudWatch 日志组与 OTel service name
- 采样：要评估的会话百分比（0.01–100%）

在线评估通过两种方式挂到 agent 上：直接指向 AgentCore Runtime 上的该 agent，或引用该 agent 使用的 CloudWatch 日志组。随后 AgentCore 会利用这些数据源设置，把代表该 agent 完整对话的 span 分组，从而找到已完成的会话，并对它们运行评估。

你可以在 0.01–100% 之间设置采样百分比，精确控制有多少流量会被评估。你还可以设置会话超时，告诉 AgentCore 在最后一个 span 之后等待多久才把会话视为完成。该超时应与 agent 的典型会话时长匹配，以免给仍在进行中的会话打分。

配置启用后，AgentCore 会替你管理周期性调度。对每个被采样的会话，它从 CloudWatch 读取 span，调用你配置的每个 evaluator，并把评估结果写入专用的评估结果 CloudWatch 日志组。执行这些操作时，AgentCore 会代入配置中定义的评估执行 IAM 角色，因此 Lambda 和 CloudWatch 权限挂在该角色上，而不是挂在 agent 的 runtime 角色上。

每个 evaluator 的分数还会以 Embedded Metric Format 形式出现在 CloudWatch 指标中，位于 Bedrock-AgentCore/Evaluations 命名空间下，以 evaluator 名称和配置 ID 为键。由此，你可以构建 CloudWatch 仪表板，把 schema 有效性、工作流合规性和 PII 干净度与 Helpfulness、Correctness 一并绘制出来，从而统一查看语言质量与结构质量。在此基础上，你还可以在这些指标上配置 CloudWatch Alarms，在某个质量维度跌破重要阈值时通知运维人员。

## 方案概览

在本方案中，我们以 Market Trends Agent 为例。Market Trends Agent 是一个基于 LangGraph 构建的投资情报助手，部署在 [Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 上。完整示例位于 AgentCore 示例仓库的 [02-use-cases/market-trends-agent](https://github.com/aws-samples/amazon-bedrock-agentcore-samples/tree/main/02-use-cases/market-trends-agent)。该 agent 为金融经纪人提供股票数据、多源新闻分析，以及存放在 [AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html) 中的经纪人档案，并针对每位经纪人的策略、兴趣和风险承受能力定制分析。

该 agent 暴露的工具涵盖股票价格获取、金融新闻、搜索、经纪人身份提取、档案读写和市场简报生成。LangGraph 的 OTel 埋点会通过 [AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html) 把 span 发布到 Amazon CloudWatch，使这个 agent 成为基于代码和 LLM-as-a-Judge evaluator 的试验台。我们用它来演示如何在在线和按需模式下搭建自定义的基于代码的评估。

![agent 架构图](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/13/ML-207993.png)

图 3：Market Trends Agent 的架构

该示例包含四个 evaluator，分别覆盖 schema 校验、数值准确性、工作流合规性和 PII 检测。

- ToolResponseSchemaValidator（trace 级）——该 evaluator 把 span 过滤到目标 trace，识别工具调用 span，并检查每个工具的响应是否符合预期模式：股票数据要有 ticker 和价格，新闻摘要要有长度与格式。
- StockPriceDriftChecker（trace 级）——在可配置的容差（默认 2%）内，对照外部可信源核验 agent 响应中引用的价格。该 evaluator 从响应文本中提取“ticker+价格”对，从行情数据端点获取参考价，并计算每一对的百分比偏差。
- WorkflowContractGSR（session 级）——在整个会话范围内强制执行三步工作流契约：识别经纪人、操作经纪人档案，然后调用行情数据与新闻工具。该 evaluator 从会话 span 重建工具调用的有序列表，并验证每一步是否按顺序发生。
- BrokerPIILeakChecker（session 级）——使用 [Amazon Comprehend DetectPiiEntities API](https://docs.aws.amazon.com/comprehend/latest/APIReference/API_DetectPiiEntities.html) 扫描会话中 agent 的每一次响应以查找 PII。该 Lambda 把检测到的实体分为高风险类型（SSN、支付卡、银行账户、政府 ID、凭据）和较低风险的联系方式（姓名、邮箱、电话、地址），并对两者应用不同阈值。出现高风险 PII 返回 FAIL；低风险 PII 过度出现则返回带计数的部分分数。示例还提供了一个基于正则的变体，供无法依赖 Comprehend 的环境使用。

### 前置条件

本演练需要 45 分钟的手动操作时间，在默认采样率下的 AWS 费用低于 5 美元。跟着做，你需要：

- 一个 [AWS 账户](https://signin.aws.amazon.com/signup?request_type=register)，以及一个[授予访问权限的 IAM 角色](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create.html)，可访问 Amazon Bedrock AgentCore Runtime、Memory 和 Evaluations，以及 AWS Lambda、Amazon CloudWatch。
- 已安装并配置好的 [AWS Command Line Interface（AWS CLI）](https://aws.amazon.com/cli/)，具备部署 AgentCore 资源、Lambda 函数、CloudWatch 日志以及（可选）Amazon Comprehend 的权限。
- 已启用 [AgentCore Observability 与 CloudWatch Transaction Search](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Enable-TransactionSearch.html)，这样 OTel span 才会同时落到 runtime 日志组和共享的 aws/spans 日志组。Transaction Search 是账户级的一次性开通项。没有它，AgentCore Evaluations 无法采样 span。没有它，评估也无法采样 span。
- 已克隆 [agentcore-samples](https://github.com/awslabs/agentcore-samples) 仓库。

### 实现步骤

完整示例（包含 agent 代码、全部四个 evaluator Lambda 以及部署脚本）位于 [market trend agent 目录](https://github.com/awslabs/agentcore-samples/tree/main/02-use-cases/market-trends-agent)。按该目录中的 README 完成以下步骤：

- 部署 Market Trends Agent——一条 uv run python `deploy.py` 命令即可创建 AgentCore Runtime、Memory、IAM 角色和 Amazon Elastic Container Registry（Amazon ECR）容器。
- 部署 evaluator——`uv run python evaluators/scripts/deploy.py` 会打包这四个 Lambda 函数、创建 IAM 角色、把每个 evaluator 注册到 AgentCore 控制面，并创建一个 100% 采样的在线评估配置。
- 生成测试流量——uv run python `evaluators/scripts/invoke.py` 运行四个内置场景（顺利路径的经纪人工作流、回头客经纪人、用伪造 SSN 做 PII 诱饵、匿名闲聊），生成能覆盖通过、失败和边界行为的会话。
- 运行按需评估——使用 AgentCore CLI 或 SDK 同步评估指定会话，查看每个 evaluator 的 label 和说明，并在推上生产之前验证行为。
- 查看在线评估结果——uv run python `evaluators/scripts/results.py` 从 CloudWatch 拉取已评分结果，并按 evaluator 分组。结果也会以 CloudWatch 指标形式出现在 Bedrock-AgentCore/Evaluations 命名空间下，供仪表板和告警使用。

完成 [README](https://github.com/awslabs/agentcore-samples/blob/main/02-use-cases/market-trends-agent/README.md) 中的说明后，你就可以像下图那样在 AgentCore Observability 控制台里开始监控评估指标。如果你的 AgentCore Evaluation 配置没有产出结果，或者出现错误、评估分数为空，可以用 [AgentCore Evaluation Diagnostic Skill](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/diagnose-evaluation-issues.html) 来排查问题。

## 使用自定义基于代码的 evaluator 的最佳实践

当你在生产环境中开始评估 agent 时，很快会发现有些质量问题带有主观性，另一些则是刚性的、基于规则的。AgentCore 中自定义的基于代码的 evaluator 就是为后一类设计的，让你可以用自己的逻辑执行确定性检查。添加这类 evaluator 的流程每次都一样，无论你是写第一个，还是在铺开一整套评估套件。

### 决定哪些检查交给代码

先找出那些你希望零歧义的确定性质量维度。这类地方仅靠人工判断或 LLM 推理是不够的。例如，必须匹配特定格式或取值的 ID、金额等精确数据约束；必需的工具调用顺序或工作流步骤等结构性约束；以及 PII 策略或监管规则等需要可证明执行的合规要求。

有用性、语气、连贯性、推理能力以及整体对话质量等主观维度，继续交给内置或自定义的 LLM-as-a-Judge evaluator。基于代码的 evaluator 负责覆盖那些你想要确定性保证的硬性、二值化边界。

要把每个问题映射到交互中的正确位置，请选择评估层级：

| 层级 | 粒度 | 调用模式 | 典型用途 |
| --- | --- | --- | --- |
| TRACE | 单轮用户输入 | 每个 trace 一次 Lambda 调用，并行扇出 | 逐响应的 schema 校验、数值准确性检查、逐响应的 PII 扫描 |
| TOOL_CALL | 单次工具调用 | 每个匹配的 span 一次 Lambda 调用，由评估目标标识 | 校验工具参数、检查检索新鲜度 |
| SESSION | 整段对话 | 每个会话一次 Lambda 调用，无评估目标 | 工作流顺序检查、会话级 PII 扫描、目标达成评估 |

这种映射可以避免你为了把每条业务规则塞进 agent 生命周期而把检查做得过于复杂。

### 在按需模式下针对真实失败场景做测试

通常，在一个新 evaluator 对部署决策或值班告警有任何发言权之前，你希望先拿到基于真实流量的证据，而按需评估恰好适合这一步。不要直接大范围启用，而是先拿一小批已知会话来跑该 evaluator，确认它能可靠地捕捉你关心的具体问题，并且它给出的说明能清楚地指出导致失败的 span 或工具调用。如果该 evaluator 需要访问外部系统（例如 PII 检测器或策略引擎），这也是验证权限、超时和其他集成细节是否按预期工作的时机。

随后，同一套机制可以作为部署关卡接入 CI/CD pipeline。当你对 evaluator 在精选测试集上的表现感到放心后，就可以从 pipeline 调用按需评估 API，在它标记出关键问题时让构建失败。这样你就有办法在变更上线之前，对 schema 有效性、数值正确性、PII 卫生等做出硬性保证，同时让在线评估专注于捕捉漂移和长尾失败，而不是明显的回归。

### 接入持续监控

当你确信某个自定义 evaluator 的行为符合预期后，就可以把它提升到在线评估，让它为实时流量打分，而不仅限于测试运行。实践中，这意味着定义一个在线评估配置：把该 evaluator ID 与你已经依赖的内置 evaluator 放在一起，并把数据源接到 agent 的 CloudWatch 日志组和 OTel service name 上。此后，采样百分比就成了你在覆盖度和成本之间权衡的主要旋钮：低流量 agent 通常适合 100%，这样每个会话都被检查；高流量 agent 一般落在 10–20% 区间，既能保住信号又不会让预算爆掉。

这一切就位后，结果会流入专用的结果日志组，每个 evaluator 的分数也会以 CloudWatch 指标的形式出现。这些指标为你提供了原料：可以构建仪表板来呈现自定义评估信号，也可以接上 CloudWatch Alarms，在某个指标跌破你最在意的阈值时通知团队。到那时，你的 evaluator 不再是隐藏的实现细节，而是可见、可追踪的信号——当你需要弄清质量是否已经漂移、系统是否仍满足某个用例的合规标准时，可以指着它们说话。

## 结论

基于代码的 evaluator 把 AgentCore 的覆盖范围扩展到需要确定性逻辑的质量维度。在按需模式下，它们充当开发检查和 CI/CD 部署关卡，返回同步分数与 span 级说明。在在线模式下，同一个已注册的 evaluator 与内置的 LLM-as-a-Judge evaluator 一起为线上生产会话打分，并把结果以 CloudWatch 指标形式发出。与内置 evaluator 配合时，自定义的基于代码的 evaluator 把 agent 可靠性从“听起来对”推进到契约已验证的范式。由于逻辑就放在你自己的 Lambda 里，你可以随业务规则变化而演进这些检查。一次 evaluator 注册即可服务本地开发、CI/CD 关卡和持续生产监控，让团队从原型到规模化都拥有同一个一致的质量信号。

要开始使用，请查阅 [Amazon Bedrock AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html) 文档，找出你的 agent 中需要确定性检查的结构性与合规属性，并从 [amazon-bedrock-agentcore-samples](https://github.com/aws-samples/amazon-bedrock-agentcore-samples) 仓库部署示例 evaluator。
