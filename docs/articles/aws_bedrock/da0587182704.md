# 使用 Amazon Quick 在符合 HIPAA 要求的环境中部署 AI

医疗保健组织希望从人工智能中获得与其他企业相同的东西：更快的答案、更少的手动工作以及及时传达给决策者并采取行动的见解。然而，医疗保健行业的不同之处在于，数据极其复杂、与背景密切相关且受到严格监管。因此，这篇文章首先给出了一些定义，为接下来的一切奠定了基础。

受保护的健康信息 (PHI) 是指识别个人身份并与其健康、护理或护理付款相关的任何信息，例如医疗记录、索赔或会员 ID。当软件涉及 PHI 时，它受《健康保险流通与责任法案》(HIPAA) 的约束，该法案是一项管理 PHI 数据访问、保护和审计方式的联邦法律。

Agentic AI 改变了软件“接触 PHI”的含义。传统的分析工具读取数据并返回响应。像[亚马逊快速](https://aws.amazon.com/quick/?trk=0ea79374-057c-4897-84f0-5fe792905a8f&sc_channel=ps&ef_id=Cj0KCQjwh4TVBhCWARIsAG0czmpo54 zJn-WvYCuM5cs0LyHLwwhCnMDagTibEwL0NQcei0e-YQr-36QaAnmREALw_wcB:G:s&gads_camp=23532473728&gads_ag=195603221991&gads_ad=8069675426 17&gads_kw=amazon%20quick&gads_matchtype=e&gads_network=g&gads_device=c&gads_geo=9033253&gad_campaignid=23532473728&gbraid=0AAAA ADjHtp8O4mvy6Ui9bVNOkaBiEk9zr&gclid=Cj0KCQjwh4TVBhCWARIsAG0czmpo54zJn-WvYCuM5cs0LyHLwwhCnMDagTibEwL0NQcei0e-YQr-36QaAnmREALw_wcB)可能会走得更远。例如，其聊天代理既可以处理非结构化内容（例如临床记录和上诉信），也可以处理结构化数据（例如索赔和会员记录）。代理可以从非结构化和结构化源检索数据，通过连接器调用其他系统，并代表用户完成多步骤任务。 [连接器](https://docs.aws.amazon.com/quick/latest/userguide/action-integrations.html) 是预构建的集成，可让 Amazon Quick 安全地读取外部系统并在其中执行操作，例如 [Slack](https://slack.com/)、Microsoft [Outlook](https://www.microsoft.com/en-us/microsoft-365/outlook/email-and-calendar-software-microsoft-outlook)、 [Salesforce](https://www.salesforce.com/)、[Atlassian Jira](https://www.atlassian.com/software/jira?campaign=18440774103&adgroup=205067403288&targetid=kwd-855725 830&matchtype=e&network=g&device=c&device_model=&creative=821687169116&keyword=jira&placement=&target=&ds_e id=700000001558501&ds_e1=GOOGLE&gad_source=1&gad_campaignid=18440774103&gbraid=0AAAAAD_uzhDBLBtUXFuk3eQBeJP YfuhAL&gclid=Cj0KCQjwh4TVBhCWARIsAG0czmo2Qtlpne3MKJgjXeGJRy_C78qQ5oMVYE5BIkJ3M4PerbYN0ZBwgsIaAtUJEALw_wcB),和 [Microsoft SharePoint](https://support.microsoft.com/en-us/sharepoint/platform/what-is-sharepoint)。您还可以通过模型上下文协议 (MCP) 添加自己的自定义工具。只有在您的组织内授权的连接器才是可见的。当聊天代理可以读取 PHI 并对其进行操作时，您需要充分的治理：确定性护栏、对代理所做操作的行为审计跟踪，以及对无人参与的情况下所采取的操作的明确责任。为了支持这种治理，Amazon Quick 公开了 ACL 感知检索、聊天和反馈日志记录，并控制允许每个聊天代理执行的操作。

Amazon Quick 是一项符合 [HIPAA](https://docs.aws.amazon.com/quick/latest/userguide/sec-compliance.html) 资格的服务。此资格适用于 Amazon Quick Web、桌面和移动客户端，具体取决于责任共担模型和您的配置。不过，本文重点介绍 Amazon Quick 网络版本的功能，您可以通过浏览器访问该版本。

在这篇文章中，我们从基础开始：HIPAA 适用于谁以及符合 HIPAA 资格和符合 HIPAA 要求之间的区别。然后，我们介绍 Amazon Quick 作为平台以及 PHI 的两种数据流（非结构化和结构化）。在此基础上，我们将介绍 Amazon Quick 为受监管环境提供的功能和不提供的功能，演练一个虚构的健康计划 (AnyCompany) 部署，并提炼出您应该预先做出的最佳实践和不可逆转的决策。最后，我们提供了分步实施指南、结论以及供深入阅读的资源。

## HIPAA 适用于谁？

HIPAA 的影响范围不仅仅限于医院和诊所。根据法律，两类组织承担义务，大多数人工智能项目都涉及这两类组织。

### 涵盖实体 (CE)

- **健康计划** – 健康保险公司、HMO、雇主资助计划、医疗保险和医疗补助。
- **医疗保健信息交换所** – 将非标准健康信息处理为标准电子格式的组织。
- **医疗保健提供者** – 医生、诊所、医院、药房、疗养院以及任何以电子方式传输健康信息的提供者。

### 商业伙伴 (BA)

- 业务伙伴是指所涵盖实体的员工队伍之外、代表所涵盖实体创建、接收、维护或传输受保护的健康信息 (PHI) 的任何个人或实体。
- 常见示例包括云服务提供商、IT 供应商、计费公司、数据分析公司、索赔处理者、律师事务所和咨询公司。
- 代表其他业务伙伴处理 PHI 的分包商本身就是业务伙伴。

在 PHI 易手之前，所涉及的实体和业务伙伴都必须签署业务伙伴附录 (BAA)。在您通过 AWS Artifact 接受 AWS BAA 后，AWS 充当该特定 AWS 账户的业务伙伴，并且仅当您使用 Amazon Quick 等符合 HIPAA 要求的服务来处理其中的 PHI 时。本附录不涉及您的其他帐户、不符合 HIPAA 资格的服务中的 PHI 或您配置服务的方式。这些仍然是你的责任。请务必与您自己的法律和合规团队一起审查并确认当前的 AWS BAA 条款以及您的义务。

## 符合 HIPAA 要求与符合 HIPAA 要求不同

虽然符合 HIPAA 要求是 AWS 的一项指定，但符合 HIPAA 要求是您整个环境的财产。符合 HIPAA 条件意味着 AWS 已评估该服务并允许您根据签署的 AWS BAA 使用该服务来处理、存储和传输 PHI。 Amazon Quick 是一项符合 HIPAA 要求的服务，第三方审计员根据 AWS 合规性计划（包括 HIPAA、FedRAMP、PCI DSS、SOC 和 ISO）对其进行评估。作为云服务的 AWS 不存在官方 HIPAA 认证，而且 AWS 本身也不“符合 HIPAA 要求”。

Amazon Quick 资格仅作为构建块。仅此一点并不能使您的应用程序和环境符合 HIPAA。您仍然需要签署 BAA、对数据进行分类、正确配置控制措施，并拥有 HIPAA 要求的管理和物理保护措施，包括员工培训、风险分析和 AWS 不会为您执行的违规程序。 Amazon Quick 等符合条件的服务、已签署的 BAA、正确的配置、治理和您自己的保护措施才能实现符合 HIPAA 的部署。 Amazon Quick 符合资格意味着您可以在其上构建合规的工作流程。这并不意味着打开它会让您自动合规。

## 什么是亚马逊快速

Amazon Quick 通常是通过其聊天代理引入的，但 HIPAA 资格适用于整个工作区，而不是单个功能，因此平台级视图对于合规性至关重要。 Amazon Quick 中的所有功能均由以下构建块组装而成：

- **聊天**是主要界面。用户可以用自然语言提出问题或提供说明，然后 Amazon Quick 决定如何回应。
- **聊天代理**处理每个请求。这是您在控制台“聊天代理”菜单下看到的内容。每个聊天代理都可以配置指令，以知识源为基础，并提供采取行动的工具。 Amazon Quick 附带默认聊天代理 (My Assistant)，您可以为特定域创建自定义聊天代理。
- **空间** 组织聊天代理所需的资源，例如文档、仪表板、数据集、知识库和操作连接器。空间可以与团队共享。

## Amazon Quick 为受监管环境提供了什么

Amazon Quick 符合 HIPAA 要求，我们概述了这在实践中意味着什么。

### 托管基础设施

Amazon Quick 是一项完全托管的服务。 AWS 运营底层基础设施并负责云的安全性，并由第三方审计员按照 [AWS 责任共担模型](https://aws.amazon.com/compliance/shared-responsibility-model/) 中的规定进行验证。

### 加密

Amazon Quick 默认对静态数据进行加密，并支持对传输中的数据进行加密。

- 默认情况下，使用 AWS 自有或 AWS 管理的密钥启用静态[加密](https://docs.aws.amazon.com/quick/latest/userguide/data-encryption.html)。注册客户管理密钥是可选的，不是 HIPAA 要求。如果您需要直接控制加密密钥，您可以为参与的资源类型（包括 SPICE 数据集、数据源凭证、OAuth 令牌和报告工件）注册客户管理的 AWS KMS 密钥（需要企业订阅）。如果不适用客户管理的密钥，AWS 将使用 AWS 自有或 AWS 管理的密钥加密数据。
- 需要注意的一个细微差别：用户对聊天响应的反馈（包括可选的自由文本评论）未使用您的客户管理密钥或保护 Amazon Quick 的 AI 索引数据的密钥进行加密。用户反馈应被视为潜在的 PHI 表面并进行相应的管理。
- 对于传输中的数据，Amazon Quick 通过传输层安全性 (TLS) 保护加密传输。对于某些数据库连接，您可以选择传输是否加密，因此您应该在这些数据源连接上显式启用 TLS/SSL，而不是假设它始终处于启用状态。

### 您的数据不会训练模型

Amazon Quick 不会使用您的客户数据来训练或改进底层大语言模型 (LLM)。

### 访问控制和身份联合

Amazon Quick 通过 AWS IAM Identity Center、Microsoft Active Directory 和 SAML 2.0 身份提供商支持基于角色的访问控制 (RBAC) 和单点登录 (SSO)。对于商业智能 (BI) 工作负载，您可以通过行级和列级安全性以及运行角色来补充这一点，以限制查询时的数据访问。借助这些功能，您可以强制执行唯一的用户标识和最低权限。

### 审计和监控信号

Amazon Quick 发出几个不同的信号。它们不可互换，混淆它们是常见的审计漏洞。

- [AWS CloudTrail](https://aws.amazon.com/cloudtrail/) 记录支持的 API 操作和一组记录的非 API 事件，例如仪表板视图和用户管理操作。它捕获谁在何时做了什么，但不捕获聊天消息正文或响应内容。
- [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 出售的日志将特定于 AI 的记录传送到您控制的目的地（CloudWatch Logs、Amazon S3 或 Firehose）。有五种日志类型：聊天对话 (CHAT_LOGS)、用户反馈 (FEEDBACK_LOGS)、代理和研究时间 (AGENT_HOURS_LOGS)、索引存储使用情况 (INDEX_USAGE_LOGS) 和知识库文件同步 (KB_FILE_SYNC_LOGS)。这是“用户提出的问题和 Amazon Quick 回答的内容”所在的位置，而不是 CloudTrail 中。
- CloudWatch 指标和警报还提供近乎实时的操作监控。
- 分析仪表板向管理员展示使用情况和采用情况。请注意，它可以在负面反馈审核范围内公开详细的查询文本和完整的对话上下文，因此仅向授权管理员授予访问权限。

由于聊天日志和反馈可能包含 PHI，因此请应用 CloudWatch Logs 数据保护屏蔽，并在依赖给定信号来确保合规性之前确认给定信号实际上涵盖了您想要跟踪的事件。

### 将功能转化为 HIPAA 控制

Amazon Quick 是一项符合条件的服务非常有用，因为它将每项功能都映射到特定的 HIPAA 保障措施，如下表所示：

| **亚马逊快速功能** | **如何使用它** | **它支持 HIPAA 控制** |
| --- | --- | --- |
|联合 SSO + RBAC | IAM 身份中心/AD，最低权限角色 | 164.312(a)(1) 访问控制。唯一的用户ID |
|知识库上的文档级 ACL |支持 ACL 的 KB。查询时失败关闭 | 164.312(a)(1) 访问控制。最低限度的必要|
|静态和传输中的加密 |默认情况下，使用 AWS 托管密钥打开。 （可选）客户管理的密钥以实现密钥所有权 | 164.312(a)(2)(iv) / (e)(2)(ii) 加密 |
| CloudTrail + CloudWatch 出售日志 |捕获API事件和聊天/反馈记录 | 164.312(b) 审计控制 |
|日志保留+屏蔽|保留策略、S3 对象锁定、PII 屏蔽 | 164.316(b) 文件保留 |
| AI护栏+内置屏蔽|阻止的单词/短语、内容安全检查 |支持最低限度的必要目标和诚信目标 |

### Amazon Quick 不做什么

虽然 Amazon Quick 提供了上述控件，但本节介绍了 Amazon Quick 不提供的功能以及如何弥补这一差距。 Amazon Quick 管理访问、检索和交互。它不是数据工程或数据湖治理平台。在 HIPAA 环境中，一些需求不在 Amazon Quick 范围内，而是由其上游的其他 AWS 服务满足。

- **去标识化和转换。** Amazon Quick 不会去标识化 PHI 或重塑源数据。当您的用例需要有限数据集或去识别化数据提取时，请在数据到达 Amazon Quick 之前使用适当的 AWS 服务进行准备，例如，使用 AWS Glue DataBrew（AWS Glue 的一项功能）进行可视化数据准备和编辑，或使用 AWS Glue DataBrew 进行提取、转换和加载 (ETL)管道。
- **数据湖治理和细粒度表权限。** 对于 Amazon Quick Sight 通过数据湖查询的结构化数据，数据湖本身的列级和行级治理是 [AWS Lake Formation](https://aws.amazon.com/lake-formation/) 的角色，而不是 Amazon Quick。 Amazon Quick Sight 在分析层强制实施自己的行级和列级安全性，但权威的湖级授权存在于 Lake Formation 和 AWS Glue 数据目录中。
- **管理和物理保障措施。** 无论使用何种工具，员工培训、风险分析和违规程序仍然属于您。

一般的最佳实践是划分职责并允许上游服务决定存在哪些数据以及谁可以在源处查询数据。让 Amazon Quick 决定谁可以向其提出问题以及代理可以如何处理数据。

## AnyCompany 健康计划：示例用例

AnyCompany Health Plan 是一个虚构的健康计划，它说明了一个用例和模式。 AnyCompany Health Plan 是一个受覆盖的实体，它想要两件事：让其护理管理团队以自然语言询问政策和会员申诉文件的问题，并为运营领导者提供有关索赔数据的自助仪表板。两者都涉及 PHI，因此 AnyCompany 需要确认解决方案符合 HIPAA 要求。 AnyCompany 的环境有两个数据路径，每个路径都由不同的解决方案进行架构和管理，然后 Amazon Quick 才能访问数据。

**非结构化路径（保单和医疗记录文档）**

→ Amazon S3 存储桶（ACL 感知知识库源）

→ Amazon Quick Knowledge Base（文档级 ACL、查询时失败关闭）

**结构化路径（声明）**

目前，所有索赔数据都驻留在湖中 (Amazon S3)。

→ Glue ETL（策划）→ Glue DataBrew（去识别）

→ Lake Formation（行/列拨款和 [AWS Glue 数据目录](https://docs.aws.amazon.com/glue/latest/dg/catalog-and-crawler.html)）

→ Amazon Quick Sight 数据集 ([Amazon Athena](https://aws.amazon.com/athena/))（行级和列级安全性、运行角色）

上述结构化和非结构化数据的数据流均汇聚到具有联合 SSO、最低权限空间、护栏和 CloudWatch 发布日志的 Amazon Quick 聊天代理中。

以下是 AnyCompany 管理员实施该解决方案的方式：

- **通过 [AWS 管理控制台](https://docs.aws.amazon.com/signin/latest/userguide/how-to-sign-in.html) 签署 BAA 并进行配置。** 管理员根据 AWS 账户接受 AWS Artifact 中的 AWS BAA，然后通过 IAM Identity Center 从 AWS 管理控制台配置 Amazon Quick。 AnyCompany 在其合规登记册中记录协议 ID、时间戳和帐户。只有通过 AWS 管理控制台配置的 Amazon Quick Web 版本才能通过 AWS Artifact 纳入已签署的 BAA 之下，对于构建涉及 PHI 且符合 HIPAA 要求的工作流程的客户来说，AWS Artifact 是必要的组件，但须遵守正确的配置并承担客户自己的合规责任。
- **在第 0 天设置不可逆转的控制。** 由于 AnyCompany 的安全策略要求控制其自己的加密密钥，因此管理员选择在创建任何 Amazon Quick AI 数据之前将客户管理的密钥注册为账户默认值。数据密钥一旦设置，以后就无法更改。 （默认的 AWS 托管加密也符合 HIPAA 要求。使用客户托管密钥并不是服务符合 HIPAA 要求的先决条件。）管理员还在 IAM Identity Center 上确定身份模型，以便应用非活动用户检测。 Amazon Quick 数据密钥在首次创建数据时设置一次，并且永远无法更改。如果密钥被删除，唯一的恢复方法是取消订阅并重新订阅，这将永久删除所有 Amazon Quick 数据。
- **在 Amazon Quick 外部准备结构化路径。** 在 Amazon Quick Sight 接触索赔之前，AnyCompany 的数据团队使用 AWS Glue 构建精选索赔表，并使用 Glue DataBrew 为操作仪表板生成去识别化的提取内容。 AWS Lake Formation 通过 AWS Glue 数据目录授予对这些表的行级和列级访问权限。因此，Amazon Quick 永远不会看到它不需要的原始 PHI。
- **为文档创建 ACL 感知知识库。** 管理员将策略和申诉 S3 存储桶连接为知识库，并在创建时启用文档级 ACL。由于 ACL 以后无法打开，因此需要在创建 S3 存储桶时进行配置。 Amazon Quick 在查询时评估每个用户的身份，并且在无法确认访问时不返回任何文档。
- **构建专用空间和自定义聊天代理。** AnyCompany 创建一个具有受限成员资格的 PHI 空间，与一般生产力空间分开。护理管理聊天代理的范围仅限于 ACL 感知的知识库，禁用开放网络搜索并配置护栏。只读连接器是为任何与 PHI 相邻的东西实现的。
- **通过查询时安全性连接仪表板。** 操作仪表板通过 Athena 读取去识别化的 Amazon Quick Sight 数据集，并具有 Amazon Quick Sight 行级和列级安全性以及位于 Lake Formation 授权之上的运行身份角色。
- **在用户加入之前打开审核信号。** 管理员创建 CloudTrail 跟踪并将 CloudWatch 提供的日志传送（CHAT_LOGS、FEEDBACK_LOGS、KB_FILE_SYNC_LOGS 等）配置到保留的屏蔽目标。反馈被视为 PHI 表面。
- **验证，然后从非 PHI 扩展到 PHI。** AnyCompany 从非 PHI 工作流程（例如政策问答和文档搜索）开始，以确认治理，使用对抗性提示进行测试以验证失败关闭的 ACL 行为，检查日志以确认事件已捕获，然后才将护理管理团队扩展到与 PHI 相邻的工作。 Amazon Quick 强制实施身份、检索、护栏和审计跟踪。但去标识化、ETL 和湖级拨款发生在 Glue、Glue DataBrew 和 Lake Formation 的上游。这种划分是推荐的模式，也是在联合环境中增强 Amazon Quick 的实用答案。

## 如何使其合规：最佳实践

资格为您提供了一个*可以*处理 PHI 的平台。您仍然必须对其进行配置，以便它*可以。*

本节帮助您了解所涉及的共同责任决策。由于其中一些决定是不可逆转的，因此请在创建资源或加入用户之前做出决定。

### 从代理 AI 的安全模型开始

Amazon Quick 代理不会在每一步都等待指示。他们自行调用工具、修改数据并与外部系统交互。这会改变您保护环境的方式。 AWS 于 2026 年 4 月发布了代理 AI 的四项安全原则，它们直接适用于此处。

**原则 1 —** 层代理保护您现有的安全框架。不要为 Amazon Quick 采取并行的安全态势。在您已实施的 IAM、网络和加密策略之上添加特定于代理的措施（护栏、主题阻止和 PII 编辑）。

**原则 2 — 信任基于提示的确定性控制。** 精心设计的对抗性输入可以绕过提示指令。 AWS Identity and Access Management (IAM) 策略、文档级 ACL、网络边界和管理员配置的护栏无法讨论。将它们用作您的主要执行措施。代理指令是您的第二层，而不是唯一的一层。

**原则 3 — 在感知、推理和行动中应用深度防御。** 将每个代理能力映射到三个层之一：

- **感知：**知识库、上传的文件、网络搜索、连接器输入、MCP 工具输出。
- **原因：** LLM 处理上下文，由护栏和主题控件控制。
- **行动：** 连接器、快速流程、快速自动化、计划任务、MCP 工具调用。

在每一层独立应用控制。一个方面的差距不应该蔓延到其他方面。

请注意，HIPAA BAA 义务延伸至 MCP 工具等支持服务和解决方案。

**原则 4 — 逐步扩大自主权。** 针对非 PHI 数据以只读模式启动代理。一次添加一项功能。在进行下一步之前，在每一步中测试数据泄漏、即时注入弹性和权限边界遵守情况。

### 部署前决定

因为这三个选择是永久性的，所以在实施之前做出这些决定。

**首先注册您的 KMS 密钥。** 如果您的组织需要控制自己的加密密钥，请在创建任何 Amazon Quick AI 资源之前将客户管理的密钥注册为账户默认值。数据密钥是在账户中首次创建 Quick AI 数据时设置的。之后，就无法更改。客户管理的密钥支持需要企业订阅。请注意，客户管理的密钥会禁用聊天记忆。配置了客户管理密钥的账户[不支持](https://docs.aws.amazon.com/quick/latest/userguide/customer-managed-keys.html)此功能。

**谨慎选择您的身份模型。** 您有四个选项：IAM 身份中心、Active Directory、IAM 联合和快速本地用户。它们在配置、卸载和治理行为方面有所不同。例如，非活动用户检测仅适用于 IAM Identity Center 或 Active Directory。部署后切换身份提供商意味着重新配置每个用户的权限和空间成员身份。选一次。

**在创建时使 PHI 知识库支持 ACL。** 对于受支持的源（Amazon S3、Google Drive、SharePoint、Confluence Cloud 和 OneDrive），您可以在创建时决定知识库是否强制执行文档级 ACL。该设置是永久的。您无法在没有 ACL 的情况下创建的知识库上启用 ACL。对于任何与 PHI 相邻的内容，从一开始就将其创建为 ACL 感知型。

**警告：** 配置错误的用户存储映射可能会默默地将受限文档暴露给错误的用户，而不会出现错误或警报。在提取 PHI 内容之前验证您的身份到 ACL 的映射至关重要。

### AWS 区域、网络和账户边界

根据以下因素规划部署区域：

- **数据驻留：** Amazon Quick 在您配置数据的区域中处理和存储数据，并且您需要确认该区域满足您组织的数据本地化要求。请注意，Amazon Quick 是一项单区域服务：它受益于区域内*内的多可用区弹性，但它不会跨区域进行故障转移。如果您支持需要跨区域弹性的关键业务工作流程，请在第二个区域中配置单独的 Amazon Quick 部署及其支持数据，例如，跨区域复制基于 S3 的知识库源。
- **服务可用性。** 功能有时会在不同区域的不同时间推出。验证您的代理所需的一切（例如知识库、连接器和 Amazon Quick Sight 功能）是否在您计划部署的位置可用。
- **多账户策略。** 将 Amazon Quick 置于 AWS Organizations 中的专用工作负载账户中。使用服务控制策略 (SCP) 强制执行区域限制并阻止范围外区域中的意外配置。

对于网络边界：Amazon Quick 是通过 HTTPS 访问的托管服务。您无需将其部署到 Virtual Private Cloud (VPC) 中。但您的数据源（S3 存储桶、数据库、本地系统）可能位于 VPC 边界后面。使用 VPC 终端节点和 AWS PrivateLink（如果可用）。确保 DNS 解析和防火墙规则允许 Amazon Quick 的连接器访问您的授权数据源，而不会打开超出必要范围的网络。

### 最小化代理的攻击面

Amazon Quick 自己的文档将对抗性风险描述为两个条件问题：当 (1) 代理可以从您的信任边界之外读取内容，*和* (2) 它可以采取相应的行动时，就会存在风险。缩小任一条件的范围即可减少暴露。

**限制代理可以读取的内容（感知层）。** 了解为代理提供上下文的每个来源：知识库、上传的文件、网络搜索、第三方研究提供商、连接器响应、MCP 工具输出和保留的对话记忆。对于 PHI 工作流程：

- 将代理范围扩展到受信任的、ACL 感知的知识库。
- 关闭不需要的开放网络搜索。
- 如果代理不需要，请关闭文件上传。
- 将对话历史记录保留限制在最小的有用窗口内。

**限制代理可以执行的操作（操作层）。** 清点每个出站路径：连接器、MCP 工具、Web 查询、快速流程、快速自动化工作流程、计划的代理运行。对于 PHI 相邻代理：

- 首选只读连接器访问。
- 对自动化和预定的工作流程保持谨慎，因为它们在没有任何人监视的情况下运行。
- 阻止写入操作，除非您的安全团队明确证明合理并批准。
- 使用连接器级权限范围来限制代理可以调用​​的操作。

**了解操作运行的身份。** 按需操作以调用用户身份进行身份验证，受该用户的连接器权限限制。自动化工作流程无需交互式会话即可运行。将自主级别与操作的敏感性相匹配，并记录哪些代理在哪种身份模式下操作。

### 强制执行最小权限和数据隔离

- 将包含 PHI 的知识库和空间与一般生产力知识库和空间分开。限制会员资格。
- 在需要知道的基础上授予空间和代理访问权限。查看共享权限（谁可以使用知识库）和源文档 ACL（授权用户可以实际检索的索引文档）。
- 默认知识库刷新周期为24小时。当您的访问更改要求需要更快的传播时，请缩短它。在重新分配或回收电子邮件地址之前刷新 ACL。
- PHI 代理不应与通用生产力工具共享空间。这意味着您需要在空间级别隔离用例。
- 定期检查连接器权限。按照与您的凭证管理策略相匹配的计划轮换存储在 AWS Secrets Manager 中的凭证。

### 练习数据最小化

AWS 建议不要在资源名称或标签中输入机密数据，以避免在计费或诊断日志中意外提及。

- 在用例允许的情况下，首选去识别化数据。
- 从数据库或 API 提取结构化数据时，在索引之前在源处过滤列和行。
- 配置代理护栏，使用内置 PII 检测过滤器编辑响应中的 PII，隐藏社会安全号码 (SSN)、医疗记录号码 (MRN) 和出生日期。

### 配置审核日志记录和保留

Amazon Quick 提供了多种不同的审计信号。默认情况下它们都不流动，您可能需要将它们打开。

| **信号** | **来源** | **它捕获了什么** |
| --- | --- | --- |
| API操作|云踪 |管理员操作、配置更改 |
|聊天互动 |云观察 | CHAT_LOGS — 完整的对话记录 |
|用户反馈|云观察| FEEDBACK_LOGS — 根据上下文表示同意/反对 |
|知识库同步事件 |云观察 | KB_FILE_SYNC_LOGS — 摄取状态 |
|运营指标|云观察|延迟、错误率、调用次数 |
|使用情况分析 |快捷控制台|采用率、热门查询、用户活动 |

以下是如何设置它们：

- 为范围内的账户和区域创建 CloudTrail 跟踪。
- 在打开 Amazon Quick 的 AI 功能后不久配置 CloudWatch 提供的日志传输（CHAT_LOGS、FEEDBACK_LOGS、KB_FILE_SYNC_LOGS）。
- 将 CloudWatch Logs 数据保护屏蔽应用于聊天日志，以便 PHI 不会以明文形式存储。
- 设置至少六年的保留期限。考虑日志存档上的 S3 对象锁定。
- 添加针对异常活动的 CloudWatch 警报。
- 启用 AWS Security Hub 进行持续合规性检查。
- 将关键警报发送至安全信息和事件管理 (SIEM) 或事件响应平台。

### 在扩展之前进行验证

在扩大范围之前，请检查以下内容：

- BAA 接受记录在您的合规登记册中。
- 记录数据分类：哪些知识库和空间包含 PHI，哪些代理可以访问它们。
- 对抗性查询和提示注入场景已经过测试。
- 正在捕获日志并且屏蔽工作正常。
- 桌面突破演习已经完成。
- InfoSec 已签署。

### 已知限制

以下是 Amazon Quick 的一些已知限制。

- **免费或增强路径上没有 BAA。** 您必须使用通过 AWS 管理控制台配置的路径才能获得 BAA 覆盖范围。
- **无跨区域复制。** 灾难恢复 (DR) 仅限于单个区域。
- **护栏是概率性的，而不是确定性的。**它们可以降低风险。他们不会消除它。补充前面描述的基础设施级控制。
- **第三方连接器扩展了您的 BAA 义务。** 当连接器将数据发送到外部系统时，您的合规责任将遵循数据。
- **对话内存可能包含回显的 PHI。** 设置保留策略并应用屏蔽。

## 实施指南

AnyCompany Health Plan 示例展示了如何推出 Amazon Quick。本部分将该模式转变为您可以交给平台团队的分步项目计划。

**第 1 步：执行 BAA（第一天）**

- 使用 AWS Artifact 权限登录并接受 BAA。
- 记录协议 ID、时间戳、主体 ARN 和账户 ID。
- 通知您的法律和合规团队。

**第 2 步：设置基本的、不可逆转的控制（第 1-2 天）**

- 将客户管理的密钥注册为帐户默认值。
- 验证密钥策略授予所需的权限：加密、解密、生成数据密钥、描述密钥。
- 配置您的身份模型（建议使用 IAM Identity Center）。
- 确认帐户位于具有区域限制 SCP 的专用工作负载组织单位 (OU) 中。

**步骤 3：创建 ACL 感知知识库（第 3-7 天）**

- 对数据源进行分类：PHI、PHI 相邻和非 PHI。
- 创建知识库，并为 PHI 和 PHI 相邻源启用 ACL 感知。
- 将身份存储映射到源权限并使用多个测试用户进行验证。
- 验证同步日志以确认摄取成功。将 PHI 知识库与一般内容分开。

**第 4 步：创建空间（第 5-8 天）**

- 将 PHI 相邻空间与一般生产力空间分开。
- 附加知识库、仪表板和操作连接器。限制会员资格。
- 确认未经授权的用户被阻止。

**第 5 步：创建带有护栏的自定义代理（第 7-12 天）**

- 狭隘地定义每个代理人的目的。仅附加所需的知识来源。
- 配置 PII 编辑、阻止的主题、内容过滤器和接地控制。
- 使用普通查询、边界查询和对抗性提示进行测试。
- 记录结果和补救步骤。

**第 6 步：配置操作连接器（第 10-14 天）**

- 从 PHI 相邻数据的只读模式开始。将每个连接器的范围限定到特定资源。
- 在启用轮换的情况下将凭证存储在 AWS Secrets Manager 中。
- 记录任何写访问的理由。在打开之前获得安全签字。
- 测试范围限制，以确认连接器无法访问超出其预期范围的资源。

**步骤 7：配置审核、保留和监控（第 12-16 天）**

- 启用 CloudTrail 和 CloudWatch 发布的日志。
- 应用数据保护屏蔽。将保留时间设置为至少六年。启用 S3 对象锁定。
- 配置警报、启用 Security Hub 并与您的 SIEM 集成。

**第 8 步：通过 InfoSec 进行验证（第 14-21 天）**

- 编译证据包：BAA确认、KMS配置、身份设置、数据分类、测试结果和日志样本。
- 进行桌面突破练习。
- 向您的信息安全团队展示。纠正发现的问题。获得签核。

**扩展阶段（第 4-8 周）**

从非 PHI 工作流程开始：政策问答、文档搜索、会议准备、工作流程自动化。这些可以让您的团队在 PHI 参与之前建立对该平台的信心。

然后扩展到与 PHI 相关的工作流程：临床文档协助、索赔处理、事先授权、监管问答、患者沟通起草以及人工审核。

密切监控：每周查看聊天日志，跟踪护栏触发率，并在每个新工作流程上线后 30 天内观察访问模式。

## 结论

Amazon Quick 为受监管的医疗保健组织以及为其服务的业务伙伴提供了一个托管 AI 工作区，该工作区的全部功能均符合 HIPAA 要求：代理 AI、知识检索、商业智能、自动化和研究。

合规部署的路径遵循明确的顺序：

- 了解合格和合规之间的区别，并承担自己的共同责任。
- 在通过 AWS 管理控制台配置的账户上执行 BAA。
- 首先设置不可逆控制：KMS 密钥、身份模型、ACL 感知知识库。
- 最小化代理的读取和操作界面，强制执行最低权限，并屏蔽日志中的 PHI。
- 与您的 InfoSec 团队进行验证，然后从非 PHI 扩展到与 PHI 相邻的工作流程。

合规性期望与技术一样快速发展。 AWS 于 2026 年 4 月发布了针对代理 AI 的[四项安全原则](https://aws.amazon.com/blogs/security/four-security-principles-for-agentic-ai-systems/)，并于 2026 年 6 月发布了[架构完善的代理 AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentic-ai-lens.html)。随着监管期望赶上代理人工智能的能力，当今建立在确定性基础设施级控制之上的技术可能会处于有利地位。

### 接下来做什么

**如果您正在评估 Amazon Quick：** 向您的 AWS 客户团队索取以合规性为重点的简报。询问 BAA 范围、代理 AI 的共同责任以及最新的符合 HIPAA 要求的服务附加内容。

**如果您准备好部署：** 使用实施指南作为您的项目计划。在开始创建资源之前，需要对第 2 步中的不可逆转决策进行专门的架构审查。

**如果您已经在运行 Amazon Quick：** 根据本文中的最佳实践审核您的部署，尤其是代理安全原则和已知限制列表。

如需架构指导，请联系您的 AWS 解决方案架构师或 AWS 医疗保健和生命科学团队。
