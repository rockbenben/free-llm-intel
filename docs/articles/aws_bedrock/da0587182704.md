# 在符合 HIPAA 资格要求的环境中用 Amazon Quick 部署 AI

医疗健康组织对 AI 的期待，与其他任何企业并无不同：更快的答案、更少的人工操作，以及能及时送到决策者手中、供其据以行动的洞察。但医疗健康行业的特殊之处在于，其数据格外复杂、高度依赖上下文，并受到严格监管。因此本文先给出几个定义，为后文的一切奠定基础。

受保护健康信息（PHI）是任何能够识别个人身份、并与其健康、照护或照护付费相关的信息，例如病历记录、理赔单或会员 ID。当软件触及 PHI 时，就落入《健康保险流通与责任法案》（HIPAA）的管辖范围——这是规定 PHI 数据如何被访问、保护与审计的联邦法律。

Agentic AI 改变了「软件触及 PHI」这件事的含义。传统分析工具读取数据并返回结果。而像 [Amazon Quick](https://aws.amazon.com/quick/?trk=0ea79374-057c-4897-84f0-5fe792905a8f&sc_channel=ps&ef_id=Cj0KCQjwh4TVBhCWARIsAG0czmpo54zJn-WvYCuM5cs0LyHLwwhCnMDagTibEwL0NQcei0e-YQr-36QaAnmREALw_wcB:G:s&gads_camp=23532473728&gads_ag=195603221991&gads_ad=806967542617&gads_kw=amazon%20quick&gads_matchtype=e&gads_network=g&gads_device=c&gads_geo=9033253&gad_campaignid=23532473728&gbraid=0AAAAADjHtp8O4mvy6Ui9bVNOkaBiEk9zr&gclid=Cj0KCQjwh4TVBhCWARIsAG0czmpo54zJn-WvYCuM5cs0LyHLwwhCnMDagTibEwL0NQcei0e-YQr-36QaAnmREALw_wcB) 这样的 agentic 工作区可能走得更远。例如，它的 chat agent 既能在非结构化内容（如临床记录和申诉信）上工作，也能处理结构化数据（如理赔和会员记录）。Agent 可以从非结构化和结构化源中检索数据、通过连接器调用其他系统，并代表用户完成多步骤任务。[连接器](https://docs.aws.amazon.com/quick/latest/userguide/action-integrations.html) 是预构建的集成，让 Amazon Quick 能安全地读取你的外部系统并在其中执行操作，例如 [Slack](https://slack.com/)、Microsoft [Outlook](https://www.microsoft.com/en-us/microsoft-365/outlook/email-and-calendar-software-microsoft-outlook)、[Salesforce](https://www.salesforce.com/)、[Atlassian Jira](https://www.atlassian.com/software/jira?campaign=18440774103&adgroup=205067403288&targetid=kwd-855725830&matchtype=e&network=g&device=c&device_model=&creative=821687169116&keyword=jira&placement=&target=&ds_eid=700000001558501&ds_e1=GOOGLE&gad_source=1&gad_campaignid=18440774103&gbraid=0AAAAAD_uzhDBLBtUXFuk3eQBeJPYfuhAL&gclid=Cj0KCQjwh4TVBhCWARIsAG0czmo2Qtlpne3MKJgjXeGJRy_C78qQ5oMVYE5BIkJ3M4PerbYN0ZBwgsIaAtUJEALw_wcB) 和 [Microsoft SharePoint](https://support.microsoft.com/en-us/sharepoint/platform/what-is-sharepoint)。你也可以通过 Model Context Protocol（MCP）添加自己的自定义工具。只有在你组织内获得授权的连接器才可见。当一个 chat agent 既能读取 PHI 又能对 PHI 执行操作时，你需要足够的治理能力：确定性的护栏、对 agent 所做行为的审计跟踪，以及对无人介入时所执行操作的明确问责。为支撑这种治理，Amazon Quick 提供 ACL 感知的检索、聊天与反馈日志记录，以及对每个 chat agent 允许执行哪些操作的控制。

Amazon Quick 是一项符合 [HIPAA](https://docs.aws.amazon.com/quick/latest/userguide/sec-compliance.html) 资格的服务。这一资格适用于 Amazon Quick 的 Web、桌面和移动客户端，但须遵循责任共担模型以及你的配置。不过本文聚焦于 Amazon Quick Web 版的能力，也就是你通过浏览器访问的那个版本。

在本文中，我们先讲基础：HIPAA 适用于谁，以及「符合 HIPAA 资格」与「满足 HIPAA 合规要求」之间的区别。随后我们把 Amazon Quick 作为一个平台来介绍，以及 PHI 的两条数据流（非结构化与结构化）。在此基础上，我们说明 Amazon Quick 为受监管环境提供了什么、没有提供什么，演练一个虚构健康计划（AnyCompany）的部署，并提炼出你应当提前做好的最佳实践和不可逆决策。最后给出分步实施指南、结论，以及用于深入阅读的资源。

## HIPAA 适用于谁？

HIPAA 的适用范围远不止医院和诊所。按照该法律，有两类组织承担义务，而大多数 AI 项目会同时涉及这两类。

### 受涵盖实体（CE）

- **健康计划** – 健康保险公司、HMO、雇主发起的计划、Medicare 和 Medicaid。
- **医疗健康信息交换所** – 把非标准健康信息处理为标准电子格式的组织。
- **医疗健康服务提供方** – 医生、诊所、医院、药房、养老院，以及任何以电子方式传输健康信息的提供方。

### 业务伙伴（BA）

- 业务伙伴是指受涵盖实体员工队伍之外、代表受涵盖实体创建、接收、维护或传输受保护健康信息（PHI）的任何个人或实体。
- 常见例子包括云服务提供商、IT 供应商、账单公司、数据分析公司、理赔处理机构、律师事务所和咨询公司。
- 代表另一个业务伙伴处理 PHI 的分包商，本身也是业务伙伴。

受涵盖实体和业务伙伴在 PHI 交接之前都必须签署业务伙伴附录（BAA）。你通过 AWS Artifact 接受 AWS BAA 之后，AWS 就会针对那个特定的 AWS 账户充当你的业务伙伴，而且仅当你使用 Amazon Quick 之类符合 HIPAA 资格的服务在该账户中处理 PHI 时才成立。该附录不会延伸到你的其他账户、不会延伸到放入不符合 HIPAA 资格的服务中的 PHI，也不涵盖你对该服务的配置方式。这些仍然是你自己的责任。请务必与你们自己的法律与合规团队一起审阅并确认当前的 AWS BAA 条款以及你的义务。

## 符合 HIPAA 资格不等于满足 HIPAA 合规要求

「符合 HIPAA 资格」是 AWS 给出的一种认定，而「满足 HIPAA 合规要求」则是你整个环境的一种属性。符合 HIPAA 资格意味着 AWS 已对该服务完成评估，并允许你在签署 AWS BAA 的前提下用它处理、存储和传输 PHI。Amazon Quick 是一项符合 HIPAA 资格的服务，第三方审计机构依据包括 HIPAA、FedRAMP、PCI DSS、SOC 和 ISO 在内的 AWS 合规计划对其进行了评估。AWS 作为云服务并不存在官方的 HIPAA 认证，AWS 本身也不「符合 HIPAA 资格」。

Amazon Quick 的资格只是一个构建块，单凭它并不能让你的应用和环境满足 HIPAA 合规要求。你仍然需要签署 BAA、对数据分类、正确配置各项控制措施，并自行承担 HIPAA 要求的管理性保障与物理性保障——包括员工培训、风险分析和违规处置流程，这些 AWS 不会替你做。一项像 Amazon Quick 这样符合资格的服务、一份已签署的 BAA、正确的配置、治理，加上你自己的保障措施，这些合在一起才能产出满足 HIPAA 合规要求的部署。Amazon Quick 符合资格，意味着你可以在它之上构建合规的工作流；它并不意味着只要开启就自动合规。

## Amazon Quick 是什么

Amazon Quick 常常是通过它的 chat agent 被介绍的，但 HIPAA 资格适用于整个工作区，而不适用于某个单一功能，因此从平台层面来看待它对合规很重要。Amazon Quick 中的所有能力都由以下构建块组装而成：

- **Chat** 是主要界面。用户可以用自然语言提出问题或给出指令，由 Amazon Quick 决定如何回应。
- **Chat agent** 处理每一个请求。这就是你在控制台 Chat agents 菜单下看到的内容。每个 chat agent 都可以配置指令、以知识源作为依据，并被赋予执行操作的工具。Amazon Quick 自带一个默认 chat agent（My Assistant），你也可以为特定领域创建自定义 chat agent。
- **Spaces** 组织 chat agent 所需的资源，例如文档、仪表板、数据集、知识库和操作连接器。一个 Space 可以与团队共享。
- **集成**把 Amazon Quick 连接到你的环境：用于 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/pm/serv-s3/?trk=50b671a1-06f5-4224-9505-fa45ee881c08&sc_channel=ps&ef_id=Cj0KCQjwh4TVBhCWARIsAG0czmqPmwab7uk1SoV93N1u2zfC-eOot4lM4VBRMC5LhngcDqaPOjZVcKUaAiIQEALw_wcB:G:s&gads_camp=23522747487&gads_ag=196433733807&gads_ad=795876995201&gads_kw=amazon%20s3&gads_matchtype=e&gads_network=g&gads_device=c&gads_geo=9033253&gad_campaignid=23522747487&gbraid=0AAAAADjHtp_hv3L7XtwtQ4-z22halx2fq&gclid=Cj0KCQjwh4TVBhCWARIsAG0czmqPmwab7uk1SoV93N1u2zfC-eOot4lM4VBRMC5LhngcDqaPOjZVcKUaAiIQEALw_wcB)、[Microsoft SharePoint](https://www.microsoft.com/en-us/microsoft-365/sharepoint/collaboration)、[Atlassian Confluence](https://www.atlassian.com/software/confluence?gclsrc=aw.ds&&campaign=18312196222&adgroup=195508706140&targetid=kwd-22737151&matchtype=e&network=g&device=c&device_model=&creative=802289199964&keyword=confluence&placement=&target=&ds_eid=700000001542923&ds_e1=GOOGLE&gad_source=1&gad_campaignid=18312196222&gbraid=0AAAAAD2bkRdeXStJlCsztIv1MjIoP2ZPI&gclid=Cj0KCQjwh4TVBhCWARIsAG0czmqkFB6vY1Y2LtqDXSAlErEjRferpQciVAzBiz6YrqOsM0KPP-H0QukaAsdFEALw_wcB) 等非结构化内容的[知识库](https://docs.aws.amazon.com/quick/latest/userguide/knowledge-base-integrations.html)；把 Amazon Quick Sight 连接到你的结构化数据库、数据仓库和数据湖的结构化数据连接；操作连接器（基于 OpenAPI 规范或 Model Context Protocol server 构建）；以及扩展（Chrome、Slack、Microsoft Teams 和 Microsoft 365）。在这些构建块之上才是各项功能。**依赖哪些构建块**一列对合规很重要，因为它显示了每个功能依赖哪些构建块，从而依赖哪些数据路径。

| **功能** | **它的作用** | **它所依赖的构建块** |
| --- | --- | --- |
| Amazon Quick Sight | 交互式仪表板与分析（BI） | 结构化数据连接、SPICE、数据集 |
| Amazon Quick Flows | 任务自动化 | 操作连接器、Spaces、agent 逻辑 |

**注意：**SPICE 是 Amazon Quick Sight 的内存查询引擎。SPICE 数据集在创建时使用账户默认的客户托管密钥；要把已有数据集迁移到新的默认密钥上，你必须执行一次完整的[刷新](https://docs.aws.amazon.com/quick/latest/userguide/customer-managed-keys.html)。如果你的数据包含 PHI，请把 SPICE 纳入你的加密策略（如果你使用客户托管的 [AWS Key Management Service](https://aws.amazon.com/kms/)（KMS）密钥，就用它保护 SPICE），也纳入关于导入什么的数据最小化决策，例如改为实时查询，或改为加载去标识化的抽取数据。

同样的资格、BAA、加密、访问控制和审计态势延伸到每一项功能。但正如开头所指出的，PHI 通过两条路径到达 Amazon Quick，而每条路径的安全方式不同。非结构化路径经由知识库，其中的文档受文档级 ACL 控制，并在查询时被评估。结构化路径经由 [Amazon Quick Sight](https://aws.amazon.com/quick/quicksight/) 读取你的数据库和数据湖，其中的行与列访问由行级安全和列级安全控制。这两条数据流承载 PHI 的方式不同，而且如下一节所示，两条路径中控制措施的落地方式也不同。

## Amazon Quick 为受监管环境提供了什么

Amazon Quick 符合 HIPAA 资格，下面我们说明这在实践中意味着什么。

### 托管基础设施

Amazon Quick 是一项完全托管的服务。AWS 运营底层基础设施，并对「云本身的安全」负责，这一点已由第三方审计机构按照 [AWS 责任共担模型](https://aws.amazon.com/compliance/shared-responsibility-model/) 的界定完成验证。

### 加密

Amazon Quick 默认对静态数据加密，并支持传输中数据的加密。

- 静态[加密](https://docs.aws.amazon.com/quick/latest/userguide/data-encryption.html)默认开启，使用 AWS 自有密钥或 AWS 托管密钥。注册客户托管密钥是可选项，并不是 HIPAA 的要求。如果你需要直接控制加密密钥，可以为参与的资源类型（包括 SPICE 数据集、数据源凭证、OAuth token 和报告产物）注册一个客户托管的 AWS KMS 密钥（需要 Enterprise 订阅）。在不适用客户托管密钥的地方，AWS 使用 AWS 自有密钥或 AWS 托管密钥加密数据。
- 有一个细节需要注意：用户对聊天回复的反馈（包括可选的自由文本评论）不会用你的客户托管密钥、也不会用保护 Amazon Quick 的 AI 索引数据的密钥加密。用户反馈应被视为潜在的 PHI 暴露面，并据此治理。
- 对于传输中的数据，Amazon Quick 使用 Transport Layer Security（TLS）保护加密传输。对某些数据库连接，你可以选择传输是否加密，因此在这些数据源连接上你应当显式启用 TLS/SSL，而不是假定它一直开启。

### 你的数据不会用于训练模型

Amazon Quick 不会使用你的客户数据来训练或改进底层大语言模型（LLM）。

### 访问控制与身份联合

Amazon Quick 通过 AWS IAM Identity Center、Microsoft Active Directory 和 SAML 2.0 身份提供商支持基于角色的访问控制（RBAC）和单点登录（SSO）。对于商业智能（BI）工作负载，你还可以用行级安全、列级安全和 run-as 角色来补充，在查询时限制数据访问。借助这些能力，你可以落实唯一的用户标识和最小权限。

### 审计与监控信号

Amazon Quick 会发出几种不同的信号。它们不可互换，把它们混为一谈是常见的审计遗漏。

- [AWS CloudTrail](https://aws.amazon.com/cloudtrail/) 记录受支持的 API 操作，以及一组已有文档说明的非 API 事件，例如仪表板查看和用户管理操作。它捕获谁在何时做了什么，但不记录聊天消息正文或回复内容。
- [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) vended logs 会把你指定、由你控制的 AI 相关记录投递到目标位置（CloudWatch Logs、Amazon S3 或 Firehose）。共有五种日志类型：聊天会话（CHAT_LOGS）、用户反馈（FEEDBACK_LOGS）、agent 与 research 时长（AGENT_HOURS_LOGS）、索引存储用量（INDEX_USAGE_LOGS）以及知识库文件同步（KB_FILE_SYNC_LOGS）。「用户问了什么、Amazon Quick 答了什么」就在这里，而不在 CloudTrail 里。
- CloudWatch 指标和告警还提供近实时的运维监控。
- 分析仪表板向管理员呈现使用情况与采用情况。注意，在负面反馈审核的范围内，它可能暴露详细的查询文本和完整的对话上下文，因此只应授予经授权的管理员访问权限。

由于聊天日志和反馈可能包含 PHI，请应用 CloudWatch Logs 的数据保护脱敏，并在依赖某个信号满足合规之前，确认该信号确实覆盖了你打算追踪的事件。

### 把功能映射到 HIPAA 控制要求

Amazon Quick 符合资格之所以有用，是因为它把每项功能映射到具体的 HIPAA 保障措施，如下表所示：

| **Amazon Quick 能力** | **你如何使用它** | **它支撑的 HIPAA 控制要求** |
| --- | --- | --- |
| 联合 SSO + RBAC | IAM Identity Center / AD，最小权限角色 | 164.312(a)(1) 访问控制。唯一用户 ID |
| 知识库上的文档级 ACL | ACL 感知的知识库。查询时 fail-closed | 164.312(a)(1) 访问控制。最小必要 |
| 静态与传输中加密 | 默认开启，使用 AWS 托管密钥。可选使用客户托管密钥以实现密钥所有权 | 164.312(a)(2)(iv) / (e)(2)(ii) 加密 |
| CloudTrail + CloudWatch vended logs | 捕获 API 事件和聊天/反馈记录 | 164.312(b) 审计控制 |
| 日志保留 + 脱敏 | 保留策略、S3 Object Lock、PII 脱敏 | 164.316(b) 文档保留 |
| AI 护栏 + 内置筛查 | 屏蔽词/短语、内容安全检查 | 支撑最小必要与完整性目标 |

### Amazon Quick 不做什么

虽然 Amazon Quick 提供了上述控制，但本节要说明它没有提供什么，以及如何弥合这一差距。Amazon Quick 治理的是访问、检索和交互，它不是数据工程或数据湖治理平台。在 HIPAA 语境下，有些需求落在 Amazon Quick 之外，要由位于其上游的其他 AWS 服务来满足。

- **去标识化与数据转换。**Amazon Quick 不会对 PHI 去标识化，也不会重塑源数据。当你的用例需要有限数据集或去标识化的抽取数据时，请在数据到达 Amazon Quick 之前用合适的 AWS 服务准备好，例如用 [AWS Glue DataBrew](https://aws.amazon.com/glue/features/databrew/)（AWS Glue 的一项能力）进行可视化数据准备与脱敏，或用 [AWS Glue](https://aws.amazon.com/glue/) 构建抽取、转换与加载（ETL）管道。
- **数据湖治理与细粒度表权限。**对于 Amazon Quick Sight 经数据湖查询的结构化数据，湖本身的列级与行级治理属于 [AWS Lake Formation](https://aws.amazon.com/lake-formation/) 的职责，而不是 Amazon Quick。Amazon Quick Sight 在分析层实施自己的行级安全和列级安全，但权威的湖级授权存在于 Lake Formation 和 AWS Glue Data Catalog 中。
- **管理性保障与物理性保障。**无论用什么工具，员工培训、风险分析和违规处置流程仍然由你负责。

一条通用的最佳实践是：划清职责边界，让上游服务决定存在哪些数据、以及谁可以在源头查询这些数据。让 Amazon Quick 决定谁能向它提问，以及 agent 可以对数据做什么。

## AnyCompany 健康计划：一个示例用例

AnyCompany Health Plan 是一个虚构的健康计划，用于说明一个用例和一种模式。AnyCompany Health Plan 是一家受涵盖实体，它想要两件事：让护理管理团队用自然语言询问政策文件和会员申诉文件，以及为运营负责人提供基于理赔数据的自助式仪表板。两者都涉及 PHI，因此 AnyCompany 需要确认该方案满足 HIPAA 合规要求。AnyCompany 的环境有两条数据路径，每条都由不同的方案来构建和治理，之后 Amazon Quick 才能访问数据。

**非结构化路径（政策与医疗记录文档）**

→ Amazon S3 存储桶（ACL 感知的知识库源）

→ Amazon Quick Knowledge Base（文档级 ACL，查询时 fail-closed）

**结构化路径（理赔数据）**

目前所有理赔数据都存放在一个数据湖中（Amazon S3）。

→ Glue ETL（整理）→ Glue DataBrew（去标识化）

→ Lake Formation（行/列授权与 [AWS Glue Data Catalog](https://docs.aws.amazon.com/glue/latest/dg/catalog-and-crawler.html)）

→ Amazon Quick Sight 数据集（[Amazon Athena](https://aws.amazon.com/athena/)）（行级与列级安全、run-as 角色）

上述面向结构化与非结构化数据的两条数据流，都汇聚到一个配置了联合 SSO、最小权限 Space、护栏和 CloudWatch vended logs 的 Amazon Quick chat agent 中。

下面是 AnyCompany 的管理员实施该方案的方式：

- **签署 BAA，并通过 [AWS Management Console](https://docs.aws.amazon.com/signin/latest/userguide/how-to-sign-in.html) 完成供给。**管理员在 AWS Artifact 中针对该 AWS 账户接受 AWS BAA，然后用 IAM Identity Center 从 AWS Management Console 供给 Amazon Quick。AnyCompany 在其合规登记册中记录协议 ID、时间戳和账户。只有通过 AWS Management Console 供给的 Amazon Quick Web 版，才能通过 AWS Artifact 纳入已签署 BAA 的覆盖范围；对于构建触及 PHI、满足 HIPAA 合规要求的工作流的客户来说，这是必要的组成部分，但须以正确配置和客户自身的合规责任为前提。
- **在第 0 天设定不可逆的控制。**由于 AnyCompany 的安全策略要求控制自己的加密密钥，管理员选择在创建任何 Amazon Quick AI 数据之前，就把一个客户托管密钥注册为账户默认密钥。数据密钥一旦设定，之后就无法更改。（默认的 AWS 托管加密同样符合 HIPAA 资格。使用客户托管密钥并不是该服务符合 HIPAA 资格的前提。）管理员还在 IAM Identity Center 上确定了身份模型，以便启用非活跃用户检测。Amazon Quick 的数据密钥在首次创建数据时[设定一次](https://docs.aws.amazon.com/quick/latest/userguide/customer-managed-keys.html)，此后永远无法更改。如果该密钥被删除，唯一的恢复方式就是取消订阅再重新订阅，而这会永久删除所有 Amazon Quick 数据。
- **在 Amazon Quick 之外准备结构化路径。**在 Amazon Quick Sight 触及理赔数据之前，AnyCompany 的数据团队使用 AWS Glue 构建整理后的理赔表，并使用 Glue DataBrew 为运营仪表板产出经过去标识化的抽取数据。AWS Lake Formation 通过 AWS Glue Data Catalog 在这些表上授予行级和列级访问权限。因此，Amazon Quick 永远不会看到它并不需要的原始 PHI。
- **为文档创建一个 ACL 感知的知识库。**管理员把存放政策与申诉文件的 S3 存储桶连接为知识库，并在创建时启用文档级 ACL。由于 ACL 之后无法再开启，这一步必须在创建 S3 存储桶时就配置好。Amazon Quick 在查询时评估每个用户的身份，在无法确认访问权限时不返回任何文档。
- **构建专用的 Space 和一个自定义 chat agent。**AnyCompany 创建一个成员受限的 PHI Space，与通用生产力 Space 分开。护理管理 chat agent 的范围仅限定到那个 ACL 感知的知识库，并关闭开放 Web 搜索、配置好护栏。凡是与 PHI 相邻的集成，都实现为只读连接器。
- **以查询时安全的方式接入仪表板。**运营仪表板经 Athena 读取去标识化的 Amazon Quick Sight 数据集，并在 Lake Formation 授权之上叠加 Amazon Quick Sight 的行级安全、列级安全以及一个 run-as 角色。
- **在让用户入驻之前开启审计信号。**管理员创建一条 CloudTrail trail，并把 CloudWatch vended log 投递（CHAT_LOGS、FEEDBACK_LOGS、KB_FILE_SYNC_LOGS 等）配置到一个带保留策略、已脱敏的目标。反馈被视为一个 PHI 暴露面。
- **先验证，再从非 PHI 扩展到 PHI。**AnyCompany 从政策问答、文档搜索等非 PHI 工作流起步，以确认治理有效；再用对抗性 prompt 测试，验证 ACL 的 fail-closed 行为；然后检查日志，确认事件确实被捕获；只有这些都通过之后，才把护理管理团队扩展到与 PHI 相邻的工作。Amazon Quick 负责落实身份、检索、护栏和审计跟踪；而去标识化、ETL 和湖级授权发生在上游的 Glue、Glue DataBrew 和 Lake Formation 中。这种划分是推荐模式，也是在联邦环境中增强 Amazon Quick 的务实答案。

## 如何做到合规：最佳实践

资格给你的是一个*能够*处理 PHI 的平台。你仍然必须把它配置成*确实*处理 PHI 的样子。

本节帮你理解其中涉及的责任共担决策。由于其中少数决策是不可逆的，请在创建资源或让用户入驻之前就把它们定下来。

### 从 agentic AI 的安全模型开始

Amazon Quick 的 agent 不会在每一步都等待指令。它们会自行调用工具、修改数据、与外部系统交互。这改变了你保护环境的方式。AWS 在 2026 年 4 月[发布](https://aws.amazon.com/blogs/security/four-security-principles-for-agentic-ai-systems/)了 agentic AI 的四项安全原则，它们直接适用于这里。

**原则 1 ——**把 agent 相关的保障措施叠加到你现有的安全框架之上。不要为 Amazon Quick 另立一套平行的安全态势。在你已经在执行的 IAM、网络和加密策略之上，增加 agent 专属的措施（护栏、主题屏蔽和 PII 脱敏）。

**原则 2 ——信任确定性控制，而不是基于 prompt 的控制。**一个精心构造的对抗性输入可以绕过 prompt 指令。AWS Identity and Access Management（IAM）策略、文档级 ACL、网络边界和管理员配置的护栏是「说」不动的。请把它们作为你的主要执行手段。Agent 指令是你的第二层，而不是唯一一层。

**原则 3 ——在感知、推理和行动三个环节上实施纵深防御。**把每一项 agent 能力映射到三个层次之一：

- **感知（Perceive）：**知识库、上传的文件、Web 搜索、连接器输入、MCP 工具输出。
- **推理（Reason）：**LLM 处理的上下文，由护栏和主题控制来约束。
- **行动（Act）：**连接器、Quick Flows、Quick Automate、计划任务、MCP 工具调用。

在每一层独立地施加控制。某一层的缺口不应级联到其他层。

注意，HIPAA BAA 义务延伸到支撑性服务与方案，例如 MCP 工具。

**原则 4 ——逐步扩大自主性。**先让 agent 以只读模式面向非 PHI 数据运行。一次只增加一项能力。每一步都要测试数据泄漏、prompt injection 抗性和权限边界遵守情况，通过之后再进入下一步。

### 部署之前就要定下的决策

由于以下三个选择是永久性的，请在实施之前就把它们决定好。

**先注册你的 KMS 密钥。**如果你的组织要求控制自己的加密密钥，请在创建任何 Amazon Quick AI 资源之前，先把一个客户托管密钥注册为账户默认密钥。数据密钥在账户中首次创建 Quick AI 数据时设定，此后就无法更改。客户托管密钥支持需要 Enterprise 订阅。注意，客户托管密钥会禁用聊天记忆。配置了客户托管密钥的账户[不支持](https://docs.aws.amazon.com/quick/latest/userguide/customer-managed-keys.html)该功能。

**审慎选择你的身份模型。**你有四个选项：IAM Identity Center、Active Directory、IAM 联合和 Quick 本地用户。它们在供给、离职处理和治理行为上各不相同。例如，非活跃用户检测只在 IAM Identity Center 或 Active Directory 下有效。部署之后再更换身份提供商，意味着要重新为每个用户配置权限和 Space 成员关系。所以只选一次。

**在创建时就让 PHI 知识库具备 ACL 感知。**对于受支持的源（Amazon S3、Google Drive、SharePoint、Confluence Cloud 和 OneDrive），知识库是否强制执行文档级 ACL 在创建时决定，而该设置是永久的。你无法为一个创建时未启用 ACL 的知识库再开启 ACL。凡是与 PHI 相邻的内容，从最开始就以 ACL 感知的方式创建。

**警告：**配置错误的用户存储映射可能会把受限文档静默地暴露给错误的用户，既不报错也不告警。在导入 PHI 内容之前，验证身份到 ACL 的映射至关重要。

### AWS Region、网络与账户边界

根据以下因素规划你的部署 Region：

- **数据驻留：**Amazon Quick 在你供给它的 Region 中处理和存储数据，你需要确认该 Region 满足你组织的数据本地化要求。注意，Amazon Quick 是单 Region 服务：它能获得 Region *内部*的多可用区韧性，但不会跨 Region 故障转移。如果你要支撑需要跨 Region 韧性的业务关键工作流，请在第二个 Region 中再供给一套 Amazon Quick 部署及其配套数据，例如跨 Region 复制基于 S3 的知识库源。
- **服务可用性。**各项功能有时会在不同 Region 分不同时间上线。请核实你的 agent 所需的一切，例如知识库、连接器和 Amazon Quick Sight 能力，在你计划部署的地方是否可用。
- **多账户策略。**把 Amazon Quick 放在 AWS Organizations 中一个专用的工作负载账户里。使用服务控制策略（SCP）强制 Region 限制，并阻止在范围之外的 Region 中意外供给资源。

关于网络边界：Amazon Quick 是一项通过 HTTPS 访问的托管服务，你不需要把它部署进虚拟私有云（VPC）。但你的数据源（S3 存储桶、数据库、本地系统）可能位于 VPC 边界之后。在可用的地方使用 VPC 终端节点和 AWS PrivateLink。确保 DNS 解析和防火墙规则能让 Amazon Quick 的连接器到达你授权的数据源，而不会把网络开放得超出必要范围。

### 尽量缩小 agent 的攻击面

Amazon Quick 自己的文档把对抗性风险描述为一个双条件问题：当（1）agent 能从你的信任边界之外读取内容，*且*（2）它能采取有后果的行动时，风险才存在。缩小任一条件，你就能降低暴露。

**约束 agent 能读什么（感知层）。**弄清每一个为 agent 上下文提供输入的源：知识库、上传的文件、Web 搜索、第三方研究提供商、连接器响应、MCP 工具输出，以及保留的对话记忆。对于 PHI 工作流：

- 把 agent 限定到可信的、ACL 感知的知识库。
- 在不需要的地方关闭开放 Web 搜索。
- 如果 agent 不需要文件上传，就关闭它。
- 把对话历史保留期限限制到最短的有用窗口。

**约束 agent 能做什么（行动层）。**清点每一条出站路径：连接器、MCP 工具、Web 查询、Quick Flows、Quick Automate 工作流、计划性的 agent 运行。对于与 PHI 相邻的 agent：

- 优先使用只读的连接器访问。
- 对自动化和计划性工作流保持谨慎，因为它们在无人监看的情况下运行。
- 除非有明确理由并获得你的安全团队批准，否则阻止写操作。
- 使用连接器级权限范围来限制 agent 能调用哪些操作。

**弄清一次操作以什么身份运行。**按需操作以发起用户的身份进行身份验证，并受该用户的连接器权限约束。自动化工作流在没有交互式会话的情况下运行。让自主程度与操作的敏感度相匹配，并记录哪些 agent 以哪种身份模式运行。

### 落实最小权限与数据隔离

- 把包含 PHI 的知识库和 Space 与通用生产力类的分开。限制成员范围。
- 按知悉必要原则授予 Space 和 agent 访问权限。既要检查共享权限（谁能使用某个知识库），也要检查源文档 ACL（经授权的用户实际能检索到哪些已索引文档）。
- 知识库的默认刷新周期是 24 小时。当你的访问变更要求需要更快传播时，请缩短它。在重新分配或回收邮箱地址之前，先刷新 ACL。
- PHI agent 不应与通用生产力工具共享同一个 Space。这意味着你需要在 Space 层面隔离用例。
- 定期复查连接器权限。按照与你凭证管理策略相匹配的周期，轮换存放在 AWS Secrets Manager 中的凭证。

### 践行数据最小化

AWS 建议不要在资源名称或标签中输入机密数据，以免在账单日志或诊断日志中被意外提及。

- 在用例允许的地方，优先使用去标识化的数据。
- 从数据库或 API 摄取结构化数据时，在索引之前先在源端过滤列与行。
- 配置 agent 护栏，使用内置的 PII 检测过滤器在回复中对 PII 脱敏，隐藏社会安全号码（SSN）、病历号（MRN）和出生日期。

### 配置审计日志与保留

Amazon Quick 提供几种不同的审计信号。它们默认都不会流转，你可能需要手动开启。

| **信号** | **来源** | **捕获的内容** |
| --- | --- | --- |
| API 操作 | CloudTrail | 管理员操作、配置变更 |
| 聊天交互 | CloudWatch | CHAT_LOGS——完整的会话记录 |
| 用户反馈 | CloudWatch | FEEDBACK_LOGS——带上下文的点赞/点踩 |
| 知识库同步事件 | CloudWatch | KB_FILE_SYNC_LOGS——摄取状态 |
| 运维指标 | CloudWatch | 延迟、错误率、调用次数 |
| 使用分析 | Quick 控制台 | 采用情况、热门查询、用户活动 |

下面是设置方法：

- 为范围内的账户和 Region 创建一条 CloudTrail trail。
- 在开启 Amazon Quick 的 AI 功能之后不久，配置 CloudWatch vended log 投递（CHAT_LOGS、FEEDBACK_LOGS、KB_FILE_SYNC_LOGS）。
- 对聊天日志应用 CloudWatch Logs 数据保护脱敏，使 PHI 不以明文形式存储。
- 设置至少六年的保留期。考虑对日志存档启用 S3 Object Lock。
- 为异常活动添加 CloudWatch 告警。
- 启用 AWS Security Hub 进行持续性合规检查。
- 把关键告警路由到你的安全信息与事件管理（SIEM）平台或事件响应平台。

### 扩展之前先验证

在扩大范围之前，检查以下几点：

- BAA 的接受情况已记录在你的合规登记册中。
- 数据分类已有文档：哪些知识库和 Space 包含 PHI，哪些 agent 能访问它们。
- 对抗性查询和 prompt injection 场景已经测试过。
- 日志正在被捕获，脱敏工作正常。
- 已完成一次桌面推演的违规演练。
- InfoSec 已经签字确认。

### 已知限制

以下是 Amazon Quick 的一些已知限制。

- **Free 或 Plus 路径上没有 BAA。**你必须使用通过 AWS Management Console 供给的那条路径，才能获得 BAA 覆盖。
- **没有跨 Region 复制。**灾难恢复（DR）被限制在单个 Region 内。
- **护栏是概率性的，而不是确定性的。**它们能降低风险，但不能消除风险。请用前面描述的基础设施级控制来补充。
- **第三方连接器会扩展你的 BAA 义务。**当连接器把数据发送到外部系统时，你的合规责任会随数据一起延伸。
- **对话记忆可能包含被回显的 PHI。**请设置保留策略并应用脱敏。

## 实施指南

AnyCompany 健康计划的例子展示了如何铺开 Amazon Quick。本节把这一模式转化为一份可以交给平台团队的分步项目计划。

**第 1 步：执行 BAA（第 1 天）**

- 使用具备 AWS Artifact 权限的身份登录并接受 BAA。
- 记录协议 ID、时间戳、principal ARN 和账户 ID。
- 通知你的法律与合规团队。

**第 2 步：设定基础性的不可逆控制（第 1–2 天）**

- 把一个客户托管密钥注册为账户默认密钥。
- 验证密钥策略授予了所需权限：Encrypt、Decrypt、GenerateDataKey、DescribeKey。
- 配置你的身份模型（推荐 IAM Identity Center）。
- 确认该账户位于一个专用的工作负载组织单元（OU）中，并应用了限制 Region 的 SCP。

**第 3 步：创建 ACL 感知的知识库（第 3–7 天）**

- 对数据源分类：PHI、与 PHI 相邻、非 PHI。
- 为 PHI 和与 PHI 相邻的源创建知识库，并开启 ACL 感知。
- 把身份存储映射到源权限，并用多个测试用户验证。
- 核实同步日志确认摄取成功。让 PHI 知识库与通用内容保持分离。

**第 4 步：创建 Spaces（第 5–8 天）**

- 把与 PHI 相邻的 Space 与通用生产力 Space 分开。
- 挂载知识库、仪表板和操作连接器。限制成员范围。
- 确认未授权用户会被拦截。

**第 5 步：创建带护栏的自定义 agent（第 7–12 天）**

- 把每个 agent 的用途定义得很窄。只挂载它需要的知识源。
- 配置 PII 脱敏、屏蔽主题、内容过滤器和 grounding 控制。
- 用常规查询、边界查询和对抗性 prompt 进行测试。
- 记录测试结果与整改步骤。

**第 6 步：配置操作连接器（第 10–14 天）**

- 对与 PHI 相邻的数据先从只读模式开始。把每个连接器的范围限定到具体资源。
- 把凭证存放在 AWS Secrets Manager 中，并开启轮换。
- 为任何写访问记录理由。在开启之前取得安全团队的签字确认。
- 测试范围限制，确认连接器无法触及超出其预期范围的资源。

**第 7 步：配置审计、保留与监控（第 12–16 天）**

- 启用 CloudTrail 和 CloudWatch vended logs。
- 应用数据保护脱敏。把保留期设为至少六年。启用 S3 Object Lock。
- 配置告警，启用 Security Hub，并与你的 SIEM 集成。

**第 8 步：与 InfoSec 一起验证（第 14–21 天）**

- 汇总证据包：BAA 确认、KMS 配置、身份设置、数据分类、测试结果和日志样本。
- 进行一次桌面推演的违规演练。
- 向你的 InfoSec 团队汇报。整改发现的问题。取得签字确认。

**扩展阶段（第 4–8 周）**

从非 PHI 工作流开始：政策问答、文档搜索、会议准备、工作流自动化。这些能让你的团队在 PHI 登场之前先建立对平台的信心。

然后扩展到与 PHI 相邻的工作流：临床文档辅助、理赔处理、事先授权、监管问答、带人工审核的患者沟通起草。

密切监控：每周复查聊天日志、跟踪护栏触发率，并在每个新工作流上线后的 30 天内观察访问模式。

## 结论

Amazon Quick 为受监管的医疗健康组织以及为其服务的业务伙伴提供了一个托管的 AI 工作区，其全套能力都符合 HIPAA 资格：agentic AI、知识检索、商业智能、自动化和研究。

通往合规部署的路径遵循一个清晰的顺序：

- 理解「符合资格」与「满足合规要求」的区别，并承担起责任共担中属于你的那一部分。
- 在通过 AWS Management Console 供给的账户上执行 BAA。
- 先设定不可逆的控制：KMS 密钥、身份模型、ACL 感知的知识库。
- 尽量缩小 agent 的读取面和行动面，落实最小权限，并对日志中的 PHI 脱敏。
- 与你的 InfoSec 团队一起验证，然后从非 PHI 工作流扩展到与 PHI 相邻的工作流。

合规预期的演进速度与技术一样快。AWS 于 2026 年 4 月发布了 agentic AI 的[四项安全原则](https://aws.amazon.com/blogs/security/four-security-principles-for-agentic-ai-systems/)，并于 2026 年 6 月发布了 [Well-Architected Agentic AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentic-ai-lens.html)。那些今天就建立在确定性、基础设施级控制之上的组织，在监管预期追平 agentic AI 能力的过程中，很可能会处于有利位置。
