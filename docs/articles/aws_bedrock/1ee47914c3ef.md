# 使用 Strategy Mosaic 和 Amazon Bedrock AgentCore 在 AWS 上为 agentic AI 构建语义层

*本文与 Strategy 首席产品经理 Zhili Cheng、AI 工程总监 George Earle 以及销售工程师 Kyler K 合写。*

在[本系列的第一篇文章](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/)中，我们使用 Stardog 的知识图，在 [Amazon Aurora](https://aws.amazon.com/rds/aurora/) 和 [Amazon Redshift](https://aws.amazon.com/redshift/) 之上于 AWS 构建了一个语义层，并在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上针对该层运行了一个 Strands agent。[第二篇文章](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-denodo-and-amazon-bedrock-agentcore/)保留了相同的 customer 360（C360）模式，换成 Denodo 的数据虚拟化平台，并把数据源组合扩展到包含一个本地 PostgreSQL 集群。本文再次沿用相同的 C360 模式，语义层则换成 Strategy Mosaic。

Stardog 的语义层是基于本体的：概念和关系建模为 RDF，以 IRI 作为联邦的单位，以 SPARQL 作为查询语言。Denodo 的是数据虚拟化：基础视图和派生视图用 VQL 组合。Mosaic 的则是维度式的：属性、层次结构、事实和度量通过 Strategy 的度量表达式语法组合，以链接模型作为联邦的单位。该模型从一份定义出发，同时对外提供四种原生协议：面向 AI agent 的 Model Context Protocol（MCP）、面向 SQL 客户端的基于 Trino 的 JDBC/ODBC、面向 Power BI 和 Excel 的 XMLA，以及面向自定义应用的 REST。这些协议背后是[一长串经过认证的数据源](https://software.strategy.com/support/drivers-and-connectors)。受支持的系统包括 Snowflake、Databricks 等云数据仓库。运营数据库包括 [Amazon Relational Database Service（Amazon RDS）](https://aws.amazon.com/rds/)、Oracle 和 SQL Server。分析引擎包括 [Amazon Athena](https://aws.amazon.com/athena/)、Trino 和 SAP HANA，软件即服务（SaaS）数据源则包括 Salesforce。链接模型这套模式并不局限于本演练使用的 Amazon Redshift 与 Amazon Aurora 组合。在本演练中，托管在 AgentCore runtime（[Amazon Bedrock](https://aws.amazon.com/bedrock/) AgentCore 的一项能力）上的 Strands agent 通过 MCP 端点访问 Mosaic。连接、度量定义以及按调用者区分的行与列筛选都位于 Mosaic 内部，而不在 agent 的 prompt 里。

我们假设你已经熟悉本系列第一篇文章中的语义层架构。如果有任何内容对你是新的，[Stardog 那篇](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/)已经覆盖了这些基础。

读完本文，你将了解：

- 如何在 Strategy Mosaic 中跨 Amazon Redshift 和 Amazon Aurora 对 C360 域建模，使用两个链接模型，且不需要 ETL。
- Mosaic 的度量语法（基础度量、带具名筛选对象的高级度量、级别限定符和复合度量）如何承载 agent 必须据以推理的业务定义。
- 如何通过 Mosaic MCP server 把模型暴露给由 AgentCore 托管的 Strands agent，以及用户身份如何传播，使按用户生效的行级安全（RLS）和对象级安全（OLS）端到端成立。
- 针对 agent 流量，如何在实时下推和内存内执行之间做选择。
- 如何把同一套受治理的定义发布到 Power BI、Tableau、notebook 和自定义应用，以及如何以 Apache Ossie 格式导出，供 Mosaic 之外的工具使用。

本演练的事实来源是 [Strategy One（2026 年 3 月）](https://www2.microstrategy.com/producthelp/Current/NextGenAI/en-us/Content/agent_MCPServerIntegration.htm)，也就是通过 MCP server 访问 Mosaic 默认可用的那个版本。

## 本文用到的 Strategy Mosaic 术语

在进入模型之前，先给一份简短的参考。

- **[Mosaic Schema 与 Mosaic Models](https://software.strategy.com/blog/strategy-mosaic-unlock-decades-of-business-context)。** 同一个通用语义层内的两条建模路径。Mosaic Schema 是集中治理的企业模型。Mosaic Models 是 Mosaic Studio 中自助式、AI 辅助的建模路径。模型可以映射到 Schema 的属性，并继承维度、对象 ACL 和 RLS。本演练使用 Mosaic Models。
- **[模型（Model）](https://www2.microstrategy.com/producthelp/Current/Mosaic/en-us/Content/mosaic_logical_modeling.htm)。** 两条建模路径中的顶层产物。它在物理表之上发布属性、度量、层次结构和安全规则。本演练使用两个 Mosaic Model，一个建在 Amazon Redshift 上，一个建在 Aurora 上，并将二者链接起来。
- **[属性（Attribute）](https://www2.microstrategy.com/producthelp/Current/Mosaic/en-us/Content/attributes_in_model.htm)。** 诸如 Customer 这样的业务实体。它携带多种形式：用于连接的 ID 形式和用于展示的显示形式。Mosaic 用这些形式把 “Carolyn Inworth” 这样的名字解析到底层的 `cid`。
- **[层次结构（Hierarchy）](https://www2.microstrategy.com/producthelp/Current/Mosaic/en-us/Content/Hierarchy_Editor_in_model.htm)。** 属性之间的父子关系。Category 经 parent 上卷到 Department。Address 上卷到 City，再上卷到 State。
- **[事实与度量](https://www2.microstrategy.com/producthelp/Current/Mosaic/en-us/Content/advanced_metrics_in_model.htm)。** 事实是一个数值列。度量对事实做聚合。`Purchase Amount = price * quantity` 是一个基础度量。度量也可以是高级度量（由具名条件限定的聚合）或复合度量（对其他度量的公式）。
- **[筛选对象](https://www2.microstrategy.com/producthelp/Current/FunctionsRef/Content/FuncRef/Filter_expressions.htm)。** 一个具名条件，由度量以尖括号引用。`[Large Orders]` 是一个筛选，其限定条件为 `Purchase Amount > 500`。度量引用 `<[Large Orders]>`，而不内联该谓词。
- **[级别限定符](https://www2.strategy.com/producthelp/Current/AdvancedReportingGuide/WebHelp/Lang_1033/Content/Level_metrics__Modifying_the_context_of_data_calcu.htm)。** 一种把聚合粒度钉住的度量表达式语法。`{~+, !Customer+}` 把粒度设为 Customer，无论查询如何切片。
- **[模型链接（Model linking）](https://www2.microstrategy.com/producthelp/Current/Mosaic/en-us/Content/mosaic_time_analytics.htm)。** 在共享属性（Customer、Time）上跨模型组合。Mosaic 把聚合下推到每个数据源，再在链接属性上连接中间结果。
- **[认证模型](https://www2.microstrategy.com/producthelp/Current/NextGenAI/en-us/Content/agent_MCPServerIntegration.htm)。** 只有认证模型才能通过 MCP server 访问。
- **[实时或内存内](https://www2.microstrategy.com/producthelp/current/workstation/en-us/Content/manage_intelligent_cubes.htm)。** 两种按模型设置的执行模式：实时下推到数据源，或从 Mosaic 驻留的 cube 返回答案。细节见本文后文。

## 示例：跨 Amazon Redshift 与 Amazon Aurora 的 Customer 360

前两篇文章中的 C360 模式保持不变。该 schema 改编自 [Stardog 的 C360 Knowledge Kit](https://www.stardog.com/blog/stardog-knowledge-kits-your-path-to-mastery-in-knowledge-graphs/)，因此跟随本系列的读者看到的仍是相同的实体、相同的键，以及由另一个语义层回答的同一个锚点问题。一家零售企业的客户记录、地址、信用卡和奖励计划登记位于运营侧，订单、产品和产品类别位于数据仓库中。业务用户希望获得跨越两侧的答案，而无需知道哪个系统持有哪个事实。

本文的不同之处在于 Mosaic 如何触达这两个数据源。Mosaic 不在查询时跨引擎联邦行数据。它为每个数据源规划一条查询，把原生 SQL 下推，再在 Mosaic 引擎中按模型链接所声明的共享属性连接中间结果集。C360 演练把分析侧建模为建在 Amazon Redshift 上的 Purchase 模型，把运营侧建模为建在 Amazon Aurora PostgreSQL 兼容版上的 Customer 模型。

两个数据库中的 schema 如下：

**Amazon Aurora PostgreSQL 兼容版（运营）**

| **表** | **关键列** |
| --- | --- |
| `customer` | `cid` (PK), `first_name`, `last_name`, `email`, `ssn`, `phone`, `location` |
| `address` | `id` (PK), `city`, `state`, `zip`, `street_name` |
| `credit_card` | `id` (PK), `cid`, `card_num`, `card_type` |
| `rewards_account` | `id` (PK), `cid`, `account_id`, `create_date` |

**Amazon Redshift（分析）**

| **表** | **关键列** |
| --- | --- |
| `purchase` | `id` (PK), `cid`, `pid`, `date`, `quantity`, `price`, `card` |
| `product` | `id` (PK), `name`, `brand`, `price`, `dept` |
| `category` | `id` (PK), `dept_name`, `parent` |
| `vendor` | `id` (PK), `vendor_name`, `industry` |

共享的 ID 是 `cid`，一个整数：它在 Aurora 的 `customer` 中是主键，在 Amazon Redshift 的 `purchase` 中则是一个普通列。两者之间没有 SQL 约束，也不可能有，因为它们位于不同的引擎中。任何把客户与其订单连接起来的问题，都必须在某处对齐这个整数。Mosaic 通过模型链接吸收它，而不是靠一个物化的跨引擎连接。

一个能跑通整个模型的代表性问题是：*按生命周期消费额排名前 20 的客户中，哪些还没有加入奖励计划？* 这就是 [Denodo 那篇](https://aws.amazon.com/blogs/machine-learning/build-semantic-layer-denodo-amazon-bedrock-agentcore/)中的自动注册问题。它需要来自 Aurora 的客户档案、来自 Amazon Redshift 的聚合消费额，以及来自 Aurora 的注册状态，并按语义层中的定义进行排名和筛选。

图 1：参考架构。客户端、Amazon Bedrock AgentCore 各组件、Strategy Mosaic MCP 端点、Mosaic 引擎以及 Amazon Redshift 与 Amazon Aurora 之间的入站认证路径和出站查询路径。

运行时分为入站路径和出站路径。

**入站。** 客户端通过 Amazon Bedrock AgentCore Gateway 发送用户的问题。Gateway 针对企业身份提供商（IdP）校验标识人类用户的 JSON Web Token（JWT），然后把请求路由到 Amazon Bedrock AgentCore runtime，由后者托管 Strands agent。agent 调用 Amazon Bedrock 上的 Anthropic Claude Sonnet 4.6 来解释 prompt 并规划查询。

**出站。** 当 agent 决定查询语义模型时，它的 MCP 工具通过 HTTPS 直接连接 `https://<env-domain>/collaboration/mcp/mosaic` 处的 Mosaic MCP 端点。agent 在 `Authorization: Bearer` 头中出示 OAuth 2.0 访问令牌。Mosaic 针对其内置的 OAuth 授权服务器校验该令牌，并把调用者解析为某个 Strategy 用户。随后它应用 `Use MCP Server` 权限和认证模型闸门，评估该用户的行级与列级安全，并跨链接的 Purchase 和 Customer 模型规划查询。Amazon Redshift 和 Amazon Aurora 响应 Mosaic 引擎按数据源生成的原生 SQL。

有两个特性对本文后续内容很重要。跨源连接之所以发生，是因为建模者声明了链接，而不是因为两个数据源恰好可达。agent 只能沿模型中存在的链接行走。抵达 Mosaic 的令牌代表人类用户，而不是服务账号，因此 RLS 和 OLS 端到端地按调用者身份评估。[AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 在两次调用之间保存调用者的 refresh token，Governed access 一节会完整走一遍身份链路。

## 构建语义层

本演练使用两个 Mosaic Model，即 Mosaic Studio 中自助式、AI 辅助的建模路径，并在共享属性上链接。Mosaic Studio 是创作套件，本文的截图来自其 Design Center 建模工作区。共三遍：每侧的 dataset 与连接、属性与层次结构，然后是承载业务逻辑的度量。团队如果已有集中治理的 [Mosaic Schema](https://software.strategy.com/blog/strategy-mosaic-unlock-decades-of-business-context)，可以把模型的属性映射到它，并从企业 schema 继承维度、对象 ACL 和 RLS，无需再做一轮平行的安全评审。如果你的数据架构师已经在维护受治理的 schema，这件事要早点做。

### 两个链接模型

每个 Mosaic 模型连接一个实时数据源。模型链接把它们组合起来。

- **Purchase**：实时连接 Amazon Redshift。事实位于 `purchase` 表（`price * quantity`），维度位于 `product`、`category`、`vendor` 以及购买日期。
- **Customer**：实时连接 Amazon Aurora PostgreSQL 兼容版。维度位于 `customer`、`address`、`credit_card`、`rewards_account`。

在每个模型内部，物理连接只针对源 schema 声明一次。Purchase 模型解析 `purchase.pid = product.id`、`product.dept = category.id` 和 `product.brand = vendor.id`，另外还有 `category.parent = category.id` 的自引用，用于部门上卷。Customer 模型解析 `customer.location = address.id`、`customer.cid = credit_card.cid` 和 `customer.cid = rewards_account.cid`。这些就是 Mosaic 用来规划并下推原生 SQL 的关系。Purchase 与 Customer 之间没有任何物理对象跨越。

两个模型在 Customer 和 Time 上链接。当一个问题同时需要两侧时（例如 *威斯康星州消费最高的人*，从 `address` 取州、从 `purchase` 取消费额），Mosaic 把相应的聚合分别下推到各数据源，并在链接属性上合并结果。没有 ETL，也没有第三份副本。

领域归属跟随模型边界。CRM 团队拥有 Customer，数据系统团队拥有 Purchase。双方都不交出各自的数据源。他们就链接属性达成一致，安全策略会自动从底层模型传播下来。Amazon Redshift 和 Amazon Aurora 之间没有物化的跨引擎连接，也没有共享的物理 schema。连接就是那组链接属性约定。

### 属性与层次结构

属性携带多种形式。Customer 以 `cid` 作为 ID 形式，以 `first_name + last_name` 作为显示形式，因此 agent 可以问 “Carolyn Inworth”，而 Mosaic 会在链接的两侧把它解析为正确的键。图 2 展示了在 Mosaic Studio 中创作的 Customer 属性，cid 为 ID 形式，Full Name、First Name 和 Last Name 为显示形式。

![Design Center 中的 Customer 属性定义。cid 是用于连接底层键的 ID 形式。Full Name、First Name 和 Last Name 是显示形式。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/05/ML-21332-2-1.png)

图 2：Design Center 中的 Customer 属性定义。cid 是用于连接底层键的 ID 形式。Full Name、First Name 和 Last Name 是显示形式。

对 C360 而言有两个重要的层次结构：

- **Category 层次结构经 parent 上卷到 Department。** `category.parent` 自引用意味着部门级问题能得到一致的聚合结果。
- **Address 以同样的模式经 City 上卷到 State。** 这使得 `State = 'WI'` 成为单个属性限定条件，而不是 agent 必须自己构造的连接。

图 3 展示了在 Design Center 中创作的地理层次结构，把 State 经 City 和 ZIP Code 串联到 Customer。

![Design Center 中的地理层次结构。属性从 State 经 City、ZIP Code 和 Location 串联到 Customer，Rewards 和电话属性挂在 customer 节点下。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/05/ML-21332-3-1.png)

图 3：Customer 模型在 Design Center 中的地理层次结构。State 经 City 和 ZIP Code 上卷到 Location，Location 链接到 Customer。

agent 请求的是 `State = 'WI'`，而不是 `address.state`。物理列名不会离开模型。语义层的每个消费者看到的都是属性形式及其显示形式，而层次结构会自动承载上卷。

### 度量：基础、高级、复合、时间智能

基础度量把分组函数应用于某个事实。`Purchase Amount` 是 `purchase` 表上的 `Sum(price * quantity)`。

图 4 展示了在 Mosaic Studio 中创作的 Purchase Amount 基础度量：公式为 Price * Quantity，另有一个描述字段，用来告诉 agent 该度量在业务上意味着什么。

![Design Center 中创作的 Purchase Amount 度量。公式为 Price * Quantity。描述告诉 agent 该度量在业务上的含义。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/05/ML-21332-4-1.png)

图 4：Design Center 中创作的 Purchase Amount 度量。公式把价格与数量相乘，描述告诉 agent 该度量在业务上的含义。

C360 里有意思的概念是高级度量：由具名条件限定的聚合。在 Strategy 中，条件是对尖括号内筛选对象的引用，而不是内联谓词。筛选对象是拥有自己的名称、描述和权限的模型对象，因此在共享同一组定义的度量之间可复用、可审计。

把这些筛选定义一次：

| **筛选对象** | **限定条件** |
| --- | --- |
| `[Large Orders]` | `Purchase Amount > 500` |
| `[Sports Category]` | `Category = "Sports"` |
| `[Rewards Members]` | `Rewards Account is not null` |
| `[Card Present]` | `Purchase Card is not null` |
| `[Big Spender]` | `Customer Lifetime Spend > 10000` |

每个筛选对象都带有名称、描述、限定条件和访问权限。建模者为 `[Large Orders]` 创作或导出的形态大致如下：

```
name:          [Large Orders]
description:   Purchases whose net line amount exceeds $500.
               Referenced by Large Order Spend and any metric that
               scopes to high-value transactions.
qualification: Purchase Amount > 500
permissions:   read:   Everyone
               modify: Data Modelers
```

然后在度量表达式中引用这些筛选。下面每一个都是高级度量：由具名筛选限定的基础聚合。

```
Large Order Spend    Sum([Purchase Amount]) {~+} <[Large Orders]>
Sports Spend         Sum([Purchase Amount]) {~+} <[Sports Category]>
Rewards Spend        Sum([Purchase Amount]) {~+} <[Rewards Members]>
```

图 5 展示了应用了筛选条件的高级度量在 Design Center 中的视图。它使用的是与前面 `Large Order Spend` 相同的创作模式。

![Design Center 中的高级度量创作，基础公式和筛选条件显示在 Breakdown 标签页上。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/05/ML-21332-5-1.png)

图 5：Design Center 中的高级度量创作，展示了基础公式以及从 Large Orders 筛选对象引用的筛选条件。

`Customer Lifetime Spend` 还需要一个级别限定符，因为“生命周期”意味着全部历史，无论当前问题如何切片：

```
Customer Lifetime Spend    Sum([Purchase Amount]) {~+, !Customer+}
```

`Customer` 前面的 `!` 把分组设为无，因此该度量在每一行上都返回每个客户的完整总额，而不是折叠成每个客户一行。完整语法见 [Strategy Metric Level Symbols](https://www2.strategy.com/producthelp/Current/AdvancedReportingGuide/WebHelp/Lang_1033/Content/Level_metrics__Modifying_the_context_of_data_calcu.htm)。

注意，筛选表中的 `[Big Spender]` 是按度量表达式而非属性谓词限定的。筛选对象可以基于二者之一。钱包份额是一个复合度量，由其他度量构建：

```
Sports Share of Wallet    [Sports Spend] / [Customer Lifetime Spend]
```

级别和条件从组件中原样传递下来。钱包份额是一个比率，因此不能做加法也不能求平均。一个 AWS Region 上的份额并不是每个客户份额的平均值，度量的描述会把这一点告诉 agent。参见 [Strategy Conditional Metrics](https://www2.strategy.com/producthelp/Current/AdvancedReportingGuide/WebHelp/Lang_1033/Content/Conditional_metrics.htm)。

除基础、高级和复合度量之外，Mosaic 还提供受治理的时间智能度量，作为一等表达式。`Previous Year`、`Previous Quarter`、`Year-to-Date` 和 `Quarter-to-Date` 在模型上声明一次，并在切片过程中保留，因此像 *今年 Sports 消费与去年相比如何* 这样的问题，变成一次属性挑选和两次度量引用，而不是手写 SQL 日期筛选。自定义日历在模型层挂接，因此同一个同比表达式既能适用于 9 月结束的财年，也能适用于 12 月结束的自然年。参见 [Governed Time-Intelligence Metrics in Mosaic](https://software.strategy.com/blog/time-intelligence-metrics-in-mosaic-year-over-year-and-period-to-date-without-the-sql)。

筛选对象改一次，Power BI 仪表板、SQL 抽取和 agent 就一起变。这正是具名、受治理的模型产物能给你、而内联 SQL 谓词给不了的东西。

## Mosaic 如何规划与执行查询

Mosaic 引擎把每次 MCP `query` 调用解析为 Trino 方言的 SQL，把维度引用解析到底层的 Purchase 和 Customer 模型，应用调用者所受的 RLS 或 OLS，并按数据源规划物理 SQL。该方言与 Strategy 为 MCP [query 工具](https://www2.microstrategy.com/producthelp/Current/NextGenAI/en-us/Content/agent_MCPServerIntegration.htm)发布的方言一致，因此 agent 生成的 SQL 在连接同一认证模型的不同 MCP 客户端之间是可移植的。

对于自动注册这个问题，规划过程展开如下：

- 下推到 Amazon Aurora：在 `cid` 上连接 `customer` 和 `rewards_account`，投影档案字段和 `rewards_account.create_date`，筛选注册为空的行。每个未注册客户返回一行。
- 下推到 Amazon Redshift：按 `cid` 分组的 `SUM(price * quantity)`。每个客户返回一行及其消费总额。
- 在 Mosaic 内部合并：在 `cid`（链接属性）上连接两个中间结果集，按生命周期消费额排序，返回前 20 名。

Aurora 执行的是事务型的档案连接。Amazon Redshift 执行的是事实聚合。Mosaic 在一个很小的中间集上处理跨引擎连接（每个客户一行，而不是每个订单一行）。手写流水线能近似出同样的形状，但之后必须永远保持同步。

有一个 SQL 细节很重要。度量是受治理的值，但 Trino 把它们当作选中的列，因此当查询使用 `GROUP BY` 时，度量需要聚合包装，例如 `SUM(metric_name)`。度量的定义、条件和连接路径仍由 Mosaic 解析。外层的聚合属于调用者。因此像钱包份额这样的非可加比率必须在其描述中说明这一点。

### 实时下推还是内存内

每个 Mosaic 模型都以两种模式之一运行。

| **模式** | **行为** | **最适合** |
| --- | --- | --- |
| 实时（Live） | 查询时下推到 Redshift 或 Aurora | 数据持续最新。数据源安全策略直接生效 |
| 内存内（In-memory） | 从 Mosaic 驻留的 cube 返回答案 | 有界的近期窗口。时延可预测。没有按查询的仓库计算开销 |

两种模式执行相同的安全规则。RLS 和 OLS 在模型上设置一次，无论答案来自何处都会被评估。这个选择是性能与成本的问题。

agent 流量是重复且突发的。agent 把 *威斯康星州消费最高的人* 拆成若干探索性追问时，会在同一个近期切片上发出许多小查询。从内存提供这些答案，可以把按查询波动的仓库开销变成固定的 Mosaic 容量，而且通常更快。对于有界窗口上的交互式 agent 工作负载，内存内模式往往既更快也更省钱。在把模型切换到内存内模式之前，先配置好 Mosaic 侧的配额授权，并在你用来验证数字的同一轮测试中验证它们。

## 一份定义，四种接口

上一节构建的度量、属性、层次结构和安全规则，通过原生协议抵达每一个消费者。没有连接器转换，没有度量重实现，也没有漂移。

| **协议** | **典型消费者** | **用它来做什么** |
| --- | --- | --- |
| MCP | AI agent（Strands、Claude、Copilot、ChatGPT、Gemini） | 语义发现 + 受治理查询 |
| SQL / JDBC / ODBC（Trino） | Tableau、SQL 客户端、Python notebook | 灵活性与即席分析 |
| DAX / XMLA | Power BI、Excel 数据透视表 | BI 的语义保真度 |
| REST | 自定义应用、数据科学 | 程序化访问 |

本演练中 Strands agent 所消费的同一个认证 Mosaic 模型，也服务于在 [Amazon Quick](https://aws.amazon.com/quick/) 中工作的业务分析师，Amazon Quick 把 Mosaic MCP 注册为一个经过 OAuth 认证的连接器。无需第二套集成。

## 受治理访问：身份传播与运行时强制执行

Mosaic 在语义层强制执行访问控制，在查询抵达 Amazon Redshift 或 Aurora 之前。HR 和反欺诈角色可以看到 `ssn`、`card_num` 这类个人可识别信息（PII）字段。市场和数据分析角色则不能。无论调用者是经由 MCP 的 Strands agent、经由 XMLA 用 Excel 的分析师，还是经由 JDBC 的 notebook，强制执行都完全相同。一套 RLS 和 OLS 对象、一个认证模型闸门、一次权限检查。标记为敏感的属性与度量还会输入 [Mosaic Sentinel Risk Management](https://www2.microstrategy.com/producthelp/Current/Mosaic/en-us/Content/sentinel_risk_management.htm)，它会对触碰被标记对象的查询发出告警，并检测行为异常，作为 OLS 旁边的纵深防御层。

图 6 展示了跨两条泳道的身份传播链：每个用户执行一次的前门 OAuth 握手，以及每次 agent 工具调用都执行的按请求路径。每条泳道都端到端携带用户身份，使 Mosaic 能针对调用者而非服务账号强制执行 RLS 和 OLS。

![从人类用户经企业 IdP、Amazon Bedrock AgentCore、AWS Secrets Manager 到 Mosaic MCP 端点的身份传播链。前门 OAuth 握手每个用户执行一次（步骤 1-4）。按请求路径在每次 agent 工具调用时执行（步骤 5-10）。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/05/ML-21332-6.png)

图 6：身份传播链。前门 OAuth 握手每个用户执行一次，或在 refresh token 续期时执行（步骤 1-4）。按请求路径在每次 agent 工具调用时执行（步骤 5-10）。链中没有任何环节重新界定为服务账号。Mosaic 按调用者的 Strategy 用户身份评估治理。

该链沿两条泳道展开。

**前门 OAuth 握手（每个用户一次）。** 人类用户针对企业 IdP 完成认证。应用对 Strategy Library 的 `/collaboration/authorize` 发起 OAuth 2.0 授权码流程，scope 为 `offline_access`。Strategy Library 通过 SAML 或 OIDC 联邦到同一个 IdP，在 `/collaboration/token` 返回 refresh token 与 access token 对。应用把 refresh token 持久化到 AWS Secrets Manager，以用户的 IdP sub 声明为键。

**按请求路径（每次 agent 工具调用）。** AgentCore Gateway 校验 IdP 的 JWT 并路由到 AgentCore runtime，后者托管调用 Amazon Bedrock 上 Claude Sonnet 4.6 的 Strands agent。agent 的 MCP 工具从 Secrets Manager 取回用户的 refresh token，用它换取新的 access token，并向 `/collaboration/mcp/mosaic` 出示 `Authorization: Bearer <access_token>`。Mosaic 把令牌解析为某个 Strategy 用户，强制执行 `Use MCP Server` 权限、认证模型闸门以及 RLS 与 OLS，然后针对 Purchase 和 Customer 规划并执行。市场分析师看不到 `ssn` 或 `card_num`。反欺诈分析师能看到。

链中没有任何环节重新界定为服务账号。治理从 IdP 到 Mosaic 引擎始终按调用者身份评估。

## 通过 Mosaic MCP server 暴露该层

Strategy Library 暴露两个 MCP 端点：

| **端点** | **路径** | **作用** |
| --- | --- | --- |
| Agents MCP | `/collaboration/mcp/agent` | 把问题路由到一个认证的 Strategy agent，由它用自己的数据和指令作答 |
| Mosaic MCP | `/collaboration/mcp/mosaic` | 直接查询 Mosaic 模型和启用 AI 的 cube，不需要 Strategy agent |

两者独立工作。本演练使用 [Mosaic MCP](https://www2.microstrategy.com/producthelp/Current/NextGenAI/en-us/Content/agent_MCPServerIntegration.htm)。把语义层直接放在 Strands agent 前面，可以省掉一次推理跳转。

### 工具链

四个工具，从项目到模型、到语义、再到查询依次串联。

| **工具** | **作用** | **参数** |
| --- | --- | --- |
| `get_projects` | 列出调用者可访问的 Strategy 项目 | none |
| `get_models` | 列出某个项目中已认证的 Mosaic 模型和数据集 | project |
| `get_semantics` | 返回模型的完整定义：属性与度量及其数据类型、描述和度量公式 | model |
| `query` | 执行只读的 Trino SQL 查询。写入和 DDL 会被拒绝，返回 `MOSAIC_SQL_WRITE_REJECTED` | sql |

agent 会自动串联这些调用。`get_projects` 和 `get_models` 会在 agent 读取列名之前按描述收窄到正确的模型。`get_semantics` 返回受治理的定义，agent 随后据此针对真实对象名组合 SQL：作为复合度量的 `Sports Share of Wallet`、限定到 Customer 的 `Customer Lifetime Spend`、Category 层次结构，以及每个度量的公式。

有两条 Mosaic 特有的 SQL 约定需要注意。列标识符遵循 `<form>__<name>` 模式，且必须用双引号包裹（`"customer__customer name"`）。时间属性既以基础列形式暴露，也以预先分桶的区间列形式暴露（`(day interval)`、`(month interval)`），文档明确说明按时间分组的聚合要使用区间列，而不是 `date_trunc`。

### 元数据才是准确性的来源

`get_semantics` 返回定义，但 agent 仍然必须选对度量。没有描述时，`Total Spend` 和 `Customer Lifetime Spend` 看起来可以互换，而它们并不是。四类属性承担了大部分工作：对象描述（度量意味着什么、什么时候不该用它，包括非可加度量的聚合行为）、语义定义（复合度量如何组成）、关系（哪些属性是合法的切片维度），以及治理上下文（使 agent 能说明自己看不到什么，而不是把经过筛选的数字当作完整的呈现）。模型描述是 `get_models` 返回的第一项内容，也是 agent 挑选正确模型的依据。Mosaic 可以从上游目录导入元数据，因此已经在维护的列描述会直接流入，而不必重新录入。

## 部署 agent

Strands 是一个用于构建 agent 的小型框架。一个简短的 Python 入口把 Amazon Bedrock 上的 Claude Sonnet 4.6 接到 Mosaic MCP 端点作为工具源。AgentCore runtime 托管该进程。AgentCore Gateway 终止入站请求并转发人类用户的 JWT。

系统提示词很重要。给 agent 明确的指令，要求在写 SQL 之前遵循三步调用模式：`get_projects`，然后 `get_models`，再对目标模型调用 `get_semantics`。告诉它只引用 `get_semantics` 返回过的属性和度量名。加入一小节关于目标模型业务术语的说明（`Customer Lifetime Spend` 是客户全部历史的总计，与当前切片无关。`Sports Share of Wallet` 是一个比率。以此类推）。这是对准确性回报最大的 prompt 工程。

为系统提示词中被复用的部分启用 [Amazon Bedrock prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)。`get_semantics` 的负载达数千 token，且在同一模型版本内不会变化，因此缓存可以降低重复调用时每次调用的 input token 成本。针对稳定语义层的 agent 流量，恰恰是最能从中受益的重复、突发模式。

在 MCP 路径上有两种效应叠加。第一，`get_semantics` 返回的是压缩后的业务上下文（度量定义、层次结构、属性形式），而不是原始 schema DDL，因此模型推理的是更小、信噪比更高的负载。Strategy [发布的基准测试](https://software.strategy.com/blog/your-ai-doesnt-need-more-tokens-it-needs-context)衡量了提供语义上下文相对于原始 schema 在 input token 和每查询成本上的影响。第二，Bedrock prompt caching 让这份已经压缩的负载在调用之间保持热态。对于重复的 agent 流量，两种效应都在每次调用时生效：模型推理压缩后的上下文，重复调用命中缓存。

## 验证

为确认语义层、agent 和身份流按预期工作，我们通过 agent 运行了三类查询，然后以另一个角色对其中一类做了治理复跑。

**查询 1，仅 Aurora。** *列出我们在威斯康星州的客户及其所在城市。*

agent 针对 Customer 模型生成一条查询，投影 Customer 和 City 的显示形式，并把州筛选为 WI：

```
SELECT "customer__customer name", "city__city name"
FROM   "Customer"
WHERE  "state__state name" = 'WI'
ORDER BY "customer__customer name"
```

Mosaic 向 Aurora 下推单条查询并返回这些行。Amazon Redshift 未被触及。

**查询 2，仅 Amazon Redshift。** *按销量计算，我们的前 10 个产品是什么？*

```
SELECT "product__product name", SUM("Units Sold") AS "total_units"
FROM   "Purchase"
GROUP BY "product__product name"
ORDER BY "total_units" DESC
LIMIT 10
```

整条查询下推到 Amazon Redshift。Aurora 未被触及。

**查询 3，跨模型。** *按生命周期消费额排名前 20 的客户中，哪些还没有加入奖励计划？*

```
SELECT "customer__customer name",
       "state__state name",
       SUM("Customer Lifetime Spend") AS "lifetime_spend"
FROM   "Customer"
WHERE  "rewards_account__account_id" IS NULL
GROUP BY "customer__customer name", "state__state name"
ORDER BY "lifetime_spend" DESC
LIMIT 20
```

Mosaic 跨两个模型规划。档案和注册状态来自 Aurora，消费聚合来自 Amazon Redshift，在 Mosaic 引擎内部按 Customer 链接属性连接，然后筛选并取前 N。agent 无需定义 `Customer Lifetime Spend`。它按名称引用该度量，Mosaic 解析出公式、级别限定符和链接路径。

**治理复跑。** 我们在投影中加入 `ssn` 运行查询 1，分别以两个调用者身份执行。作为反欺诈分析师，`get_semantics` 返回了 SSN 属性，查询也返回了这些值。作为市场分析师，`get_semantics` 返回的 Customer 属性完全不含 `ssn`，因此 agent 没有可投影的属性。同样的请求、同样的查询文本，一份定义给出两个正确的答案。

**跨接口确认。** 我们通过 Mosaic XMLA 端点在 Excel 中打开同一个认证 Customer 模型，把 `State` 和 `Customer Lifetime Spend` 拖到数据透视表上。州级总计与 agent 给出的数字完全一致。

在运行早期，agent 曾跨客户对钱包份额求平均，这是典型的非可加错误。在度量描述中加一行（*“比率型度量。不要跨客户求平均，应基于组件重新计算”*）就止住了它。这就是为什么度量描述要写在第一个冲刺而不是最后一个冲刺。

## 扩展到更多数据源

同一套链接机制可以扩展到第三个数据源：通过 Amazon Athena 查询存放在 Amazon Simple Storage Service（[Amazon S3](https://aws.amazon.com/s3/)）中的点击流事件、[Amazon S3 Tables](https://aws.amazon.com/s3/features/tables/)（Amazon S3 的一项能力）上 Apache Iceberg 中的表，或者像 CRM 这样的 SaaS 数据源。在 Mosaic 中对数据源建模，在 Customer 和 Time 上链接它，浏览到购买类的问题就能组合进同一个客户视图，无需第三条流水线。新增数据源不会改变已经存在的度量定义。agent 只能沿建模者声明过的路径行走。[AWS Lake Formation](https://aws.amazon.com/lake-formation/) 治理对底层湖表的访问。Mosaic 的 RLS 和 OLS 在其之上叠加生效。

同一套实时数据源模式适用于 [Strategy 支持的数据源目录](https://software.strategy.com/support/drivers-and-connectors)中的每一个系统，涵盖 PostgreSQL、MySQL 这类本地数据库，以及本文已经提到的仓库和引擎。

## 与 Apache Ossie 的互操作性

有些工具不会对单一语义层产生依赖。[Apache Ossie（孵化中）](https://ossie.apache.org/)正是为这个缺口而设的开放规范，于 2025 年 9 月 23 日以 Open Semantic Interchange 之名发布，现已在 Apache 孵化器中成为 Apache Ossie（孵化中）。它定义了一种厂商中立的格式，用于描述度量、维度、关系和业务概念，使定义可以在工具之间流转而无需重新录入。Strategy 与 Snowflake、Dremio、dbt Labs、Salesforce 等一同参与其中。

Mosaic 可以导出和导入 Ossie 产物。在 Amazon Redshift 上建模的度量与维度定义可以发布为 Ossie YAML，供支持 Ossie 的工具直接消费，无需 Mosaic 连接器。在别处创作的定义（dbt 中维护的度量、在目录中标准化的维度）则流入 Mosaic，而不是被重新实现。产物是纯文本，因此可以放在 Git 中，像其他代码一样在各个环境之间晋升。

Apache Ossie 还很早期。在可移植性最重要、保真度要求最低的地方使用它，例如公式、维度、描述和归属元数据，而把治理策略、执行策略和安全配置保留为 Mosaic 原生。

## 部署：Strategy Cloud

Mosaic 在 Strategy Cloud 上作为托管服务运行。Strategy 负责运营该应用。到 Amazon Redshift 和 Amazon Aurora 的连接从 Strategy Cloud 的出站网络发起。你在数据源的安全组中将 Strategy Cloud 的 CIDR 加入允许列表。

## 可观测性

两个可观测性平面覆盖从问题到答案的整条路径。

**Sentinel 和 Platform Analytics** 覆盖查询侧。Sentinel 捕获近实时的查询时长、慢查询，以及按用户、按工具和按模型的使用情况。

**[AgentCore Observability](https://aws.amazon.com/bedrock/agentcore/)，Amazon Bedrock AgentCore 的一项能力，** 覆盖 agent 侧：规划步骤、工具调用、每轮时延。Sentinel 和 Platform Analytics 展示请求抵达 Mosaic 之后发生了什么。AgentCore Observability 展示 agent 在抵达之前做了什么。

## 结论

可靠的 agentic 分析要把强大的推理、可信的业务上下文和安全的执行结合起来。Amazon Bedrock 提供模型，Strategy Mosaic 提供面向实时数据的受治理语义层，Amazon Bedrock AgentCore 托管 agent 并终止认证。agent 与语义层对话，而不直接与 Amazon Redshift 或 Aurora 对话。schema 演进时，语义模型吸收变更，同一套定义服务于 Power BI、Tableau、notebook、Strands agent 和 Amazon Quick。通过 Apache Ossie，这些定义还能触达不连接 Mosaic 的工具。

### 从哪里入手

- 挑一个当前有争议的度量（NRR、边际贡献、活跃客户是常见候选）。一个在流通中有不止一种定义的度量。
- 围绕它写三到五个业务问题。这些就是你的验收测试。
- 在 Mosaic 中对你的主数据源建模，让该度量返回一个站得住脚的数字。
- 在模型中已有的属性上，一次一个地增量链接更多数据源。
- 为 agent 会看到的每一个度量和属性撰写描述。准确性提升最大的地方就在这里。
- 通过 Mosaic MCP 接入 Strands agent，运行你的验收问题。
- 观察真实查询模式几周，然后把热点部分迁移到内存内。
- 把稳定的定义导出为 Apache Ossie 并纳入版本控制。
