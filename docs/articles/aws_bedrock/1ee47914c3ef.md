# 使用 Strategy Mosaic 和 Amazon Bedrock AgentCore 在 AWS 上构建代理 AI 语义层

*本文由首席产品经理 Cheng Li Cheng、人工智能工程总监 George Earle 和战略销售工程师 Kyler K 共同撰写。*

在[本系列的第一篇文章](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/)中，我们使用Stardog的知识图在[Amazon Aurora](https://aws.amazon.com/rds/aurora/)和[Amazon]上构建了一个语义层。 Redshift](https://aws.amazon.com/redshift/) 并在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上针对该层运行 Strands 代理。 [第二篇文章](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-denodo-and-amazon-bedrock-agentcore/) 保留了相同的客户 360 (C360) 模式并交换到 Denodo 的数据虚拟化平台中，扩展了源组合以包含本地 PostgreSQL 集群。这篇文章再次使用相同的 C360 模式，以 Strategy Mosaic 作为语义层。

Stardog 的语义层是基于本体的：概念和关系建模为 RDF，以 IRI 作为联合单位，以 SPARQL 作为查询语言。 Denodo 是数据虚拟化：由 VQL 组成的基础视图和派生视图。 Mosaic 是维度的：通过 Strategy 的度量表达式语法组成的属性、层次结构、事实和度量，并以链接模型作为联合单位。该模型根据一个定义提供四种本机协议：用于 AI 代理的模型上下文协议 (MCP)、用于 SQL 客户端的 Trino 上的 JDBC/ODBC、用于 Power BI 和 Excel 的 XMLA 以及用于自定义应用程序的 REST。这些协议的背后是[一长串经过认证的数据源](https://software.strategy.com/support/drivers-and-connectors)。支持的系统包括 Snowflake 和 Databricks 等云仓库。操作数据库包括 [Amazon Relational Database Service (Amazon RDS)](https://aws.amazon.com/rds/)、Oracle 和 SQL Server。分析引擎包括 [Amazon Athena](https://aws.amazon.com/athena/)、Trino 和 SAP HANA，软件即服务 (SaaS) 来源包括 Salesforce。链接模型模式超出了本演练使用的 Amazon Redshift 和 Amazon Aurora 对的范围。在本演练中，托管在 AgentCore 运行时（[Amazon Bedrock](https://aws.amazon.com/bedrock/) AgentCore 的功能）上的 Strands 代理通过 MCP 终端节点到达 Mosaic。连接、度量定义以及每个调用者的行和列过滤器位于 Mosaic 内，而不是位于代理提示符中。

我们假设您熟悉本系列第一篇文章中的语义层架构。如果有任何内容是新的，[Stardog 帖子](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-on-aws-with-stardog-and-amazon-bedrock-agentcore/) 涵盖了地面。

读完这篇文章后，您将了解：

- 如何使用两个链接模型在 Strategy Mosaic 中跨 Amazon Redshift 和 Amazon Aurora 建模 C360 域，无需 ETL。
- Mosaic 的度量语法（基本语法、高级语法以及命名过滤器对象、级别限定符和复合语法）如何捕获代理必须推理的业务定义。
- 如何通过 Mosaic MCP 服务器将模型公开给 AgentCore 托管的 Strands 代理，以及如何传播用户身份，以便每用户行级安全性 (RLS) 和对象级安全性 (OLS) 保持端到端。
- 如何针对代理流量在实时下推和内存执行之间进行选择。
- 如何将相同的受控定义发布到 Power BI、Tableau、笔记本和自定义应用程序，以及如何以 Apache Ossie 格式导出它们以用于 Mosaic 之外的工具。

本演练的真实来源是[策略一（2026 年 3 月）](https://www2.microstrategy.com/producthelp/Current/NextGenAI/en-us/Content/agent_MCPServerIntegration.htm)，这是默认情况下可通过 MCP 服务器进行 Mosaic 访问时发布的版本。

## 本文中使用的策略马赛克术语

在我们讨论模型之前先做一个简短的参考。

- **[Mosaic Sc​​hema 和 Mosaic Models](https://software.strategy.com/blog/strategy-mosaic-unlock-decades-of-business-context)。** 一个通用语义层内的两条建模路径。 Mosaic Sc​​hema 是集中管理的企业模型。 Mosaic Models 是 Mosaic Studio 中的自助式 AI 辅助建模路径。模型可以映射到架构属性并继承维度、对象 ACL 和 RLS。本演练使用马赛克模型。
- **[模型](https://www2.strategy.com/producthelp/Current/Mosaic/en-us/Content/mosaic_logical_modeling.htm).** 任一建模路径中的顶级工件。在物理表上发布属性、指标、层次结构和安全规则。本演练使用两个连接在一起的 Mosaic 模型，一个通过 Amazon Redshift，一个通过 Aurora。
- **[属性](https://www2.microstrategy.com/producthelp/Current/Mosaic/en-us/Content/attributes_in_model.htm)。** 业务实体，例如客户。携带多种表格：用于加入的ID表格和用于阅读的显示表格。 Mosaic 使用表单将“Carolyn Inworth”等名称解析为底层的“cid”。
- **[Hierarchy](https://www2.microstrategy.com/producthelp/Current/Mosaic/en-us/Content/Hierarchy_Editor_in_model.htm).** 属性之间的父子关系。类别通过父级向上滚动到部门。地址从城市滚动到州。
- **[事实和指标](https://www2.microstrategy.com/producthelp/Current/Mosaic/en-us/Content/advanced_metrics_in_model.htm)。** 事实是一个数字列。一个指标将其聚合。 “购买金额 = 价格 * 数量”是一个基本指标。指标还可以是高级指标（由指定条件限定的聚合）或复合指标（基于其他指标的公式）。
- **[Filter 对象](https://www2.microstrategy.com/producthelp/Current/FunctionsRef/Content/FuncRef/Filter_expressions.htm)。** 从尖括号中的指标引用的命名条件。 “[大订单]”是一个过滤器，其条件是“购买金额> 500”。指标引用“<[Large Orders]>”而不内联谓词。
- **[级别限定符](https://www2.strategy.com/producthelp/Current/AdvancedReportingGuide/WebHelp/Lang_1033/Content/Level_metrics__Modifying_the_context_of_data_calcu.htm)。** 固定聚合粒度的指标表达式语法。无论查询如何切片，`{~+, !Customer+}` 都会将粒度设置为 Customer。
- **[模型链接](https://www2.microstrategy.com/producthelp/Current/Mosaic/en-us/Content/mosaic_time_analytics.htm)。** 共享属性（客户、时间）的跨模型组合。 Mosaic 将聚合推送到每个源，并在链接属性上连接中间结果。
- **[认证模型](https://www2.microstrategy.com/producthelp/Current/NextGenAI/en-us/Content/agent_MCPServerIntegration.htm)。** 只有经过认证的模型才能通过 MCP 服务器访问。
- **[实时或内存中](https://www2.microstrategy.com/producthelp/current/workstation/en-us/Content/manage_intelligent_cubes.htm)。** 两种每个模型执行模式：实时下推到源，或来自 Mosaic 驻留多维数据集的答案。详细信息将在本文后面介绍。

## 示例：跨 Amazon Redshift 和 Amazon Aurora 的 Customer 360

前两篇文章中的 C360 模式保持不变。该模式改编自 [Stardog 的 C360 知识工具包](https://www.stardog.com/blog/stardog-knowledge-kits-your-path-to-mastery-in-knowledge-graphs/)，因此关注本系列的读者会看到相同的实体、键和锚点问题由不同的语义层回答。零售组织在运营端拥有客户记录、地址、信用卡和奖励注册，在仓库拥有订单、产品和产品类别。业务用户希望得到涵盖两者的答案，但不知道哪个系统保存哪个事实。

这篇文章的不同之处在于 Mosaic 如何到达这两个来源。 Mosaic 不会在查询时跨引擎联合行。它为每个源规划一个查询，下推本机 SQL，并将 Mosaic 引擎中的中间结果集连接到通过模型链接声明的共享属性上。 C360 演练将分析端建模为 Amazon Redshift 上的购买模型，将操作端建模为 Amazon Aurora PostgreSQL 兼容版本上的客户模型。

两个数据库的架构：

**Amazon Aurora PostgreSQL 兼容（运行）**

| **表** | **关键栏目** |
| --- | --- |
| `客户` | `cid` (PK)、`名字`、`姓氏`、`电子邮件`、`ssn`、`电话`、`位置` |
| `地址` | `id` (PK)、`city`、`state`、`zip`、`street_name` |
| `信用卡` | `id` (PK)、`cid`、`card_num`、`card_type` |
| `奖励帐户` | `id` (PK)、`cid`、`account_id`、`create_date` |

**Amazon Redshift（分析）**

| **表** | **关键栏目** |
| --- | --- |
| `购买` | `id` (PK)、`cid`、`pid`、`日期`、`数量`、`价格`、`卡` |
| `产品` | `id` (PK)、`名称`、`品牌`、`价格`、`部门` |
| `类别` | `id` (PK)、`dept_name`、`parent` |
| `供应商` | `id` (PK)、`供应商名称`、`行业` |

共享 ID 是“cid”，它是一个整数，在 Aurora 上的“customer”中显示为主键，在 Amazon Redshift 上的“purchase”中显示为普通列。没有 SQL 约束将它们链接起来，也不可能有，因为它们位于不同的引擎中。将客户与订单联系起来的每个问题都必须在某个地方协调该整数。 Mosaic 通过模型链接而不是具体化的跨引擎连接来吸收它。

运用整个模型的一个代表性问题：*按终身支出排名前 20 位的客户中，哪些尚未加入奖励计划？* 这是来自 [Denodo 帖子](https://aws.amazon.com/blogs/machine-learning/build-semantic-layer-denodo-amazon-bedrock-agentcore/) 的自动注册问题。它需要来自 Aurora 的客户资料、来自 Amazon Redshift 的汇总支出以及来自 Aurora 的注册状态，并根据语义层中的定义进行排名和过滤。

运行时分为入站路径和出站路径。

**入站。** 客户端通过 Amazon Bedrock AgentCore Gateway 发送用户的问题。网关根据企业身份提供商 (IdP) 验证用于识别人类用户的 JSON Web 令牌 (JWT)。然后，它将请求路由到托管 Strands 代理的 Amazon Bedrock AgentCore 运行时。该代理在 Amazon Bedrock 上调用 Anthropic Claude Sonnet 4.6 来解释提示并规划查询。

**出站。** 当代理决定查询语义模型时，其 MCP 工具会通过 HTTPS 直接连接到位于“https://<env-domain>/collaboration/mcp/mosaic”的 Mosaic MCP 端点。代理在“Authorization: Bearer”标头中提供 OAuth 2.0 访问令牌。 Mosaic 根据其捆绑的 OAuth 授权服务器验证令牌，并将调用者解析为策略用户。然后，它应用“使用 MCP 服务器”权限和认证模型门，评估该用户的行级和列级安全性，并计划跨链接的购买和客户模型的查询。 Amazon Redshift 和 Amazon Aurora 响应 Mosaic 引擎针对每个源发出的源本机 SQL。

有两个属性对于本演练的其余部分很重要。跨源连接的发生是因为建模者声明了一个链接，而不是因为两个源恰好可以访问。代理只能遍历模型中存在的链接。到达 Mosaic 的令牌代表人类用户，而不是服务帐户，因此 RLS 和 OLS 会根据调用者的身份进行端到端评估。 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 在调用之间保存调用者的刷新令牌，受管理的访问部分遍历完整的身份链。

## 构建语义层

本演练使用两个 Mosaic 模型，即 Mosaic Studio 中的自助式 AI 辅助建模路径，通过共享属性链接。 Mosaic Studio 是创作套件，本文中的屏幕截图来自其设计中心建模工作区。三遍：每一侧的数据集和连接、属性和层次结构，然后是承载业务逻辑的指标。拥有现有集中管理的 [Mosaic Sc​​hema](https://software.strategy.com/blog/strategy-mosaic-unlock-decades-of-business-context) 的团队可以将模型的属性映射到它，并从企业架构继承维度、对象 ACL 和 RLS，而无需进行并行安全审查。如果您的数据架构师已经维护受管理的架构，请尽早执行此操作。

### 两个链接模型

每个 Mosaic 模型都连接到一个实时信号源。模型链接将它们组合起来。

- **购买**：针对 Amazon Redshift 进行直播。 “购买”表中的事实（“价格 * 数量”）、“产品”、“类别”、“供应商”的维度以及购买日期。
- **客户**：与 Amazon Aurora PostgreSQL 兼容。 “客户”、“地址”、“信用卡”、“奖励帐户”的维度。

在每个模型内，针对源模式声明一次物理连接。购买模型解析“purchase.pid =product.id”、“product.dept =category.id”和“product.brand=vendor.id”，以及部门汇总的“category.parent =category.id”的自引用。 Customer 模型解析 `customer.location = address.id`、`customer.cid = Credit_card.cid` 和 `customer.cid =rewards_account.cid`。这些是 Mosaic 用于规划其下推的源原生 SQL 的关系。采购方和客户之间没有任何物理交叉。

这两个模型与客户和时间相关联。当问题需要两者时（例如，*威斯康星州的最高支出者*从“地址”中提取状态并从“购买”中提取支出），Mosaic 会将适当的聚合推送到每个源，并将结果组合到链接属性上。没有 ETL，没有第三个副本。

域所有权遵循模型边界。 CRM 团队拥有客户，数据系统团队拥有采购。两者都没有交出其来源。他们就链接属性达成一致，并且安全性会自动从底层模型传播。 Amazon Redshift 和 Amazon Aurora 之间没有具体化的跨引擎连接，也没有共享的物理架构。连接是链接属性协议。

- **地址以相同的模式从城市滚动到州。** 这使得“State = 'WI'”成为单个属性限定，而不是代理必须构建的连接。

### 指标：基础、高级、复合、时间智能

基本度量将组函数应用于事实。 “购买金额”是“购买”表中的“总和（价格 * 数量）”。

图 4：在设计中心创建的购买金额指标。该公式将价格乘以数量，描述告诉代理该指标在业务术语中的含义。

有趣的 C360 概念是高级指标：由指定条件限定的聚合。在策略中，条件是对尖括号中的过滤对象的引用，而不是内联谓词。过滤器对象是具有自己的名称、描述和权限的模型对象，因此它们可以在共享定义的指标之间重用和审核。

定义一次过滤器：

| **过滤对象** | **资质** |
| --- | --- |
| `[大订单]` | `购买金额> 500` |
| `[体育类别]` | `类别=“体育”` |
| `[奖励会员]` | `奖励帐户不为空` |
| `[卡片呈现]` | `购买卡不为空` |
| `[大手笔]` | `客户终身支出> 10000` |

每个过滤器对象都带有名称、描述、资格和访问权限。建模者为“[Large Orders]”创作或导出的形状如下所示：
```
name:          [Large Orders]
description:   Purchases whose net line amount exceeds $500.
               Referenced by Large Order Spend and any metric that
               scopes to high-value transactions.
qualification: Purchase Amount > 500
permissions:   read:   Everyone
               modify: Data Modelers
```
然后在指标表达式中引用过滤器。其中每一个都是高级指标：由命名过滤器限定的基本聚合。
```
Large Order Spend    Sum([Purchase Amount]) {~+} <[Large Orders]>
Sports Spend         Sum([Purchase Amount]) {~+} <[Sports Category]>
Rewards Spend        Sum([Purchase Amount]) {~+} <[Rewards Members]>
```
图 5 显示了应用了筛选条件的高级指标的设计中心视图。它使用与前面的“大订单支出”相同的创作模式。

![设计中心中的高级指标创作，基本公式和筛选条件显示在“细分”选项卡上。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/05/ML-21332-5-1.png)

图 5：设计中心中的高级指标创作，显示了从大订单过滤器对象引用的基本公式和过滤条件。

“客户终生支出”也需要一个级别限定符，因为生命周期意味着整个历史，无论当前问题如何分割：
```
Customer Lifetime Spend    Sum([Purchase Amount]) {~+, !Customer+}
```
“Customer”之前的“!”将分组设置为无，因此该指标会返回每个客户在每一行的完整总数，而不是折叠为每个客户一行。有关完整语法，请参阅[策略指标级别符号](https://www2.strategy.com/producthelp/Current/AdvancedReportingGuide/WebHelp/Lang_1033/Content/Level_metrics__Modifying_the_context_of_data_calcu.htm)。

请注意，过滤器表中的“[Big Spender]”符合指标表达式而不是属性谓词。过滤器对象可以对任一对象进行门控。钱包份额是一个复合指标，由其他指标构建而成：
```
Sports Share of Wallet    [Sports Spend] / [Customer Lifetime Spend]
```
组件的级别和条件保持不变。钱包份额是一个比率，因此它不会相加或平均。整个 AWS 区域的份额并不是每个客户份额的平均值，指标描述会告诉代理这一点。请参阅[策略条件指标](https://www2.strategy.com/producthelp/Current/AdvancedReportingGuide/WebHelp/Lang_1033/Content/Conditional_metrics.htm)。

除了基础、高级和复合之外，马赛克飞船还以一流的表达方式管理时间智能指标。 “上一年”、“上一季度”、“年初至今”和“季度至今”在模型上声明一次并通过切片保存，因此像“今年体育支出与去年相比如何”这样的问题变成了属性选择和两个指标引用，而不是手写的 SQL 日期过滤器。自定义日历附加在模型级别，因此相同的同比表达式适用于 9 月结束的会计年度和 12 月结束的日历年。请参阅[Mosaic 中的受控时间智能指标](https://software.strategy.com/blog/time-intelligence-metrics-in-mosaic-year-over-year-and-period-to-date-without-the-sql)。

编辑一次筛选器对象后，Power BI 仪表板、SQL 数据提取和代理就会一起移动。这就是命名的受控模型工件为您提供的内联 SQL 谓词无法提供的功能。

## Mosaic 如何计划和执行查询

Mosaic 引擎将每个 MCP“查询”调用解析为 Trino 方言 SQL，解析对基础购买和客户模型的维度引用，应用调用者所遵循的 RLS 或 OLS，并规划每个源的物理 SQL。该方言与 Strategy 为 MCP [查询工具](https://www2.microstrategy.com/producthelp/Current/NextGenAI/en-us/Content/agent_MCPServerIntegration.htm) 发布的内容相匹配，因此代理发出的 SQL 可跨连接到同一认证模型的 MCP 客户端移植。

对于自动注册问题，规划是这样展开的：

- 下推到 Amazon Aurora：在“cid”上连接“customer”和“rewards_account”，投影配置文件和“rewards_account.create_date”，在注册为空的情况下进行过滤。对于每个未注册的客户，返回一行。
- 下推至 Amazon Redshift：“SUM(价格 * 数量)”按“cid”分组。返回每个客户一行的总支出。
- 在 Mosaic 内组合：在“cid”（链接属性）上连接两个中间结果集，按生命周期花费排名，并返回前 20 个。

Aurora 运行事务配置文件连接。 Amazon Redshift 运行事实聚合。 Mosaic 处理小型中间集上的跨引擎连接（每个客户一行，而不是每个订单一行）。手写管道的形状大致相同，因此必须永远保持同步。

一个 SQL 细节很重要。指标是受控值，但 Trino 将它们视为选定列，因此当查询使用“GROUP BY”时，指标需要一个聚合包装器，例如“SUM(metric_name)”。指标的定义、条件和连接路径仍然由 Mosaic 解析。外部聚合是调用者的。因此，像钱包份额这样的非加性比率需要在其描述中如此说明。

### 实时下推或内存中

每个 Mosaic 模型都以两种模式之一运行。

| **模式** | **行为** | **最适合** |
| --- | --- | --- |
|直播 |在查询时下推到 Redshift 或 Aurora |一致的最新数据。源码安全直接适用 |
|内存中|来自马赛克驻留立方体的回答 |限制最近的窗口。可预测的延迟。无需按查询进行仓库计算 |

两种模式都强制执行相同的安全规则。 RLS 和 OLS 在模型上设置一次并进行评估，无论答案来自何处。选择是一个性能和成本问题。

代理流量具有重复性和突发性。一位代理将“威斯康星州的最高支出者”分解为几个探索性的后续行动，从而针对同一最近的切片引发了许多小查询。从内存中提供服务将可变的每个查询仓库支出转化为固定的 Mosaic 容量，而且通常速度更快。对于有限窗口内的交互式代理工作负载，内存中通常更快、更便宜。在将模型切换到内存中之前配置 Mosaic 端权利，并在用于验证数字的同一测试通道中验证它们。

| MCP| AI 代理（Strands、Claude、Copilot、ChatGPT、Gemini）|语义发现+治理查询|

本演练中的 Strands 代理使用的经过认证的 Mosaic 模型也为在 [Amazon Quick](https://aws.amazon.com/quick/) 中工作的业务分析师提供服务，该分析师将 Mosaic MCP 注册为经过 OAuth 身份验证的连接器。无需进行第二次集成。

## 受控访问：身份传播和运行时强制

在查询到达 Amazon Redshift 或 Aurora 之前，Mosaic 会强制执行语义层中的访问。人力资源和欺诈角色可以查看“ssn”和“card_num”等个人身份信息 (PII) 字段。营销和分析角色则不然。无论调用者是通过 MCP 的 Strands 代理、通过 XMLA 的 Excel 分析师，还是通过 JDBC 的笔记本，执行都是相同的。一组 RLS 和 OLS 对象、一个经过认证的模型门、一个权限检查。标记为敏感的属性和指标还会提供给 [Mosaic Sentinel 风险管理](https://www2.microstrategy.com/producthelp/Current/Mosaic/en-us/Content/sentinel_risk_management.htm)，它会针对接触标记对象的查询发出警报，并检测行为异常，作为 OLS 旁边的深度防御层。

图 6 显示了跨两个通道的身份传播链：每个用户运行一次的前门 OAuth 握手，以及在每个代理工具调用上运行的每个请求路径。每个通道端到端地承载用户的身份，因此 Mosaic 可以对调用者而不是服务帐户强制实施 RLS 和 OLS。

![从人类用户到企业 IdP、Amazon Bedrock AgentCore、AWS Secrets Manager 和 Mosaic MCP 终端节点的身份传播链。每个用户前门 OAuth 握手运行一次（步骤 1-4）。每个请求路径在每个代理工具调用上运行（步骤 5-10）。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/05/ML-21332-6.png)

图 6：身份传播链。前门 OAuth 握手针对每个用户运行一次，或者在刷新令牌更新时运行一次（步骤 1-4）。每个请求路径在每个代理工具调用上运行（步骤 5-10）。链中的任何内容都不会重新范围到服务帐户。 Mosaic 评估对调用者策略用户身份的治理。

链条沿着两条车道行驶。

**前门 OAuth 握手（每个用户一次）。** 人类用户针对企业 IdP 进行身份验证。应用程序在“/collaboration/authorize”处针对策略库启动 OAuth 2.0 授权代码流，范围为“offline_access”。策略库通过 SAML 或 OIDC 联合到同一 IdP，在“/collaboration/token”处返回刷新和访问令牌对。该应用程序将刷新令牌保留到 AWS Secrets Manager，并由用户的 IdP 子声明作为密钥。

**每个请求路径（每个代理工具调用）。** AgentCore Gateway 验证 IdP JWT 并路由到 AgentCore 运行时，该运行时托管在 Amazon Bedrock 上调用 Claude Sonnet 4.6 的 Strands 代理。代理的 MCP 工具从 Secrets Manager 检索用户的刷新令牌，将其交换为新的访问令牌，并将“授权：承载 <access_token>”呈现给“/collaboration/mcp/mosaic”。 Mosaic 将令牌解析为策略用户，强制执行“使用 MCP 服务器”权限、认证模型门以及 RLS 和 OLS，然后针对购买和客户进行计划和执行。营销分析师看不到“ssn”或“card_num”。欺诈分析师确实如此。

链中的任何内容都不会重新范围到服务帐户。治理评估从 IdP 到 Mosaic 引擎的呼叫者身份。

## 通过 Mosaic MCP 服务器暴露图层

策略库公开两个 MCP 端点：

| **端点** | **路径** | **它的作用** |
| --- | --- | --- |
|代理MCP | `/协作/mcp/agent` |将问题发送给经过认证的策略代理，该代理使用自己的数据和指令进行回答 |
|马赛克MCP | `/协作/mcp/马赛克` |直接查询马赛克模型和支持人工智能的立方体，无需策略代理 |

两者独立工作。本演练使用 [Mosaic MCP](https://www2.microstrategy.com/producthelp/Current/NextGenAI/en-us/Content/agent_MCPServerIntegration.htm)。将语义层直接放在 Strands 代理前面会跳过推理跳跃。

### 工具链

四个工具，从项目到模型到语义到查询。

| **工具** | **它的作用** | **参数** |
| --- | --- | --- |
| `获取项目` |列出调用者可以访问的策略项目 |无 |
| `获取模型` |列出项目中经过认证的马赛克模型和数据集 |项目|
| `get_semantics` |返回模型的完整定义：具有数据类型、描述和指标公式的属性和指标 |型号|
| `查询` |运行只读 Trino SQL 查询。写入和 DDL 被“MOSAIC_SQL_WRITE_REJECTED”拒绝 | sql|

代理会自动链接这些调用。在代理读取列名称之前，“get_projects”和“get_models”通过描述缩小到正确的模型。 “get_semantics”返回受管理的定义，然后代理使用该定义根据真实对象名称编写 SQL：“钱包的体育份额”作为复合指标，“客户生命周期支出”范围为客户、类别层次结构以及每个指标的公式。

两个 Mosaic 特定的 SQL 约定很重要。列标识符遵循 `<form>__<name>` 模式，并且必须用双引号引起来 (`"customer__customer name"`)。时间属性既作为基本列又作为预分桶间隔列（“（日间隔）”、“（月间隔）”）公开，并且文档明确表示使用间隔列进行时间分组聚合，而不是“date_trunc”。

### 元数据使其准确

`get_semantics` 返回定义，但代理仍然必须选择正确的度量。如果没有描述，“总支出”和“客户终生支出”看起来可以互换，但事实并非如此。四个属性完成大部分工作：对象描述（指标的含义以及何时不使用它，包括非相加指标的聚合行为）、语义定义（复合指标如何组成）、关系（哪些属性是有效的切片）和治理上下文（因此代理可以说出它看不到的内容，而不是将过滤后的数字显示为完整）。模型描述是“get_models”返回的第一件事，它是代理选择正确模型的方式。 Mosaic可以从上游目录导入元数据，因此列描述已经保持流动而不是重新输入。

## 部署代理

Strands 是一个用于构建代理的小型框架。一个简短的 Python 入口点将 Amazon Bedrock 上的 Claude Sonnet 4.6 连接到 Mosaic MCP 终端节点作为工具源。 AgentCore 运行时托管该进程。 AgentCore Gateway 终止入站请求并转发人类用户的 JWT。

系统提示很重要。在编写 SQL 之前，向代理提供明确的指示，使其遵循三步调用模式：目标模型上的“get_projects”，然后“get_models”，然后“get_semantics”。告诉它仅引用“get_semantics”返回的属性和指标名称。在目标模型中包含有关业务术语的简短部分（“客户终生支出”是客户历史上的总支出，无论当前切片如何。“钱包的体育份额”是一个比率。等等）。这是在准确性方面付出最大代价的即时工程。

为系统提示的重用部分启用 [Amazon Bedrock 提示缓存](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html)。 “get_semantics”有效负载运行数千个令牌，并且在模型版本内不会更改，因此缓存会降低重复调用时每次调用的输入令牌成本。针对稳定语义层的代理流量正是受益最大的重复性突发模式。

MCP 路径上有两种效应复合。首先，“get_semantics”返回压缩的业务上下文（度量定义、层次结构、属性形式）而不是原始模式 DDL，因此模型会通过更小、更高信号的有效负载进行推理。 Strategy 的[已发布基准](https://software.strategy.com/blog/your-ai-doesnt-need-more-tokens-it-needs-context) 衡量服务语义上下文与原始模式对输入令牌和每个查询成本的影响。其次，Bedrock 提示缓存使已压缩的有效负载在调用过程中保持温暖。对于重复的代理流量，两种效果都适用于每个调用：模型对压缩上下文进行推理，并且重复调用会命中缓存。

## 验证

为了确认语义层、代理和身份流按预期工作，我们通过代理运行了三个查询类别，然后将其中一个查询类别作为不同的角色重新运行。

**查询 1，仅限 Aurora。** *列出我们在威斯康星州的客户及其所在城市。*

代理生成针对客户模型的查询，该模型将客户和城市的显示形式投影到 WI 并过滤状态：
```
SELECT "customer__customer name", "city__city name"
FROM   "Customer"
WHERE  "state__state name" = 'WI'
ORDER BY "customer__customer name"
```
Mosaic 将单个查询推送到 Aurora 并返回行。 Amazon Redshift 未受影响。

**查询 2，仅限 Amazon Redshift。** *按销量排名前 10 名的产品是什么？*
```
SELECT "product__product name", SUM("Units Sold") AS "total_units"
FROM   "Purchase"
GROUP BY "product__product name"
ORDER BY "total_units" DESC
LIMIT 10
```
整个查询都会推送到 Amazon Redshift。奥罗拉没有被触动。

**查询 3，跨模型。** *按终身支出排名前 20 位的客户中，哪些尚未加入奖励计划？*
```
SELECT "customer__customer name",
       "state__state name",
       SUM("Customer Lifetime Spend") AS "lifetime_spend"
FROM   "Customer"
WHERE  "rewards_account__account_id" IS NULL
GROUP BY "customer__customer name", "state__state name"
ORDER BY "lifetime_spend" DESC
LIMIT 20
```
两种型号的马赛克计划。个人资料和注册状态来自 Aurora，支出聚合来自 Amazon Redshift，加入 Mosaic 引擎内的客户链接属性，然后进行过滤和 top-N。代理不需要定义“客户终身支出”。它通过名称引用指标，Mosaic 解析公式、级别限定符和链接路径。

**治理重新运行。** 我们运行查询 1，并将“ssn”作为两个调用者添加到投影中。作为欺诈分析师，“get_semantics”返回 SSN 属性，查询返回值。作为营销分析师，“get_semantics”返回了一个根本没有“ssn”的客户属性，因此代理没有项目属性。相同的请求，相同的查询文本，一个定义的两个正确答案。

**跨界面确认。** 我们通过 Mosaic XMLA 端点在 Excel 中打开相同的经过认证的客户模型，并将“状态”和“客户生命周期支出”拖到数据透视表上。州级总数与代理商的数字完全匹配。

在运行初期，代理对客户的钱包份额进行了平均，这是典型的非累加性错误。在指标描述中添加一行（*“比率指标。不要跨客户进行平均，从组件重新计算”*）就可以阻止它。在第一个冲刺而不是最后一个冲刺中编写指标描述就是这种情况。

## 跨数据源扩展

相同的链接机制扩展到第三个来源：通过 Amazon Athena 查询的 Amazon Simple Storage Service ([Amazon S3](https://aws.amazon.com/s3/)) 中的点击流事件、[Amazon S3 表](https://aws.amazon.com/s3/features/tables/) 上的 Apache Iceberg 中的表、Amazon S3 的功能或 CRM 等 SaaS 源。在 Mosaic 中对源进行建模，将其链接到“客户”和“时间”，并将浏览购买问题组合到相同的客户视图中，而无需第三个管道。添加源不会更改已存在的指标定义。代理只能行驶建模者声明的路径。 [AWS Lake Formation](https://aws.amazon.com/lake-formation/) 管理对底层湖表的访问。 Mosaic 的 RLS 和 OLS 适用于顶部。

相同的实时源模式适用于 [Strategy 支持的数据源目录](https://software.strategy.com/support/drivers-and-connectors) 中的每个系统，涵盖 PostgreSQL 和 MySQL 等本地数据库以及本文中已提及的仓库和引擎。

## 与 Apache Ossie 的互操作性

有些工具不会依赖于单个语义层。 [Apache Ossie (incubating)](https://ossie.apache.org/) 是针对这一差距的开放规范，于 2025 年 9 月 23 日作为开放语义交换 (Open Semantic Interchange) 推出，现在作为 Apache Ossie (incubating) 在 Apache 孵化器中。它为指标、维度、关系和业务概念定义了供应商中立的格式，因此定义可以在工具之间移动而无需重新输入。 Strategy 与 Snowflake、Dremio、dbt Labs、Salesforce 等公司一起参与其中。

Mosaic 导出和导入 Ossie 文物。通过 Amazon Redshift 建模的指标和维度定义可作为 Ossie YAML 发布，由 Ossie 感知工具使用，无需 Mosaic 连接器。在其他地方编写的定义（在 dbt 中维护的度量，在目录中标准化的维度）流入 Mosaic，而不是重新实现。这些工件是纯文本，因此它们存在于 Git 中，并通过像其他代码一样的环境进行推广。

阿帕奇奥西很早。在可移植性最重要而保真度最不重要的地方使用它，例如公式、维度、描述和所有权元数据，同时保持 Mosaic 原生的治理策略、执行策略和安全配置。

## 可观察性

两个可观察平面覆盖了从问题到答案的路径。

**Sentinel 和 Platform Analytics** 涵盖查询方面。 Sentinel 捕获近乎实时的查询持续时间、慢速查询以及用户、工具和模型的使用情况。

**[AgentCore 可观测性](https://aws.amazon.com/bedrock/agentcore/) 是 Amazon Bedrock AgentCore 的一项功能，**涵盖代理端：规划步骤、工具调用、每轮延迟。 Sentinel 和 Platform Analytics 显示请求到达 Mosaic 后发生的情况。 AgentCore 可观察性显示代理在到达那里之前正在做什么。

## 结论

可靠的代理分析结合了强大的推理、可信的业务环境和安全的执行。 Amazon Bedrock 提供模型，Strategy Mosaic 提供实时数据的受控语义层，Amazon Bedrock AgentCore 托管代理并终止身份验证。代理与语义层对话，而不是直接与 Amazon Redshift 或 Aurora 对话。模式不断发展，语义模型吸收变化，相同的定义适用于 Power BI、Tableau、笔记本、Strands 代理和 Amazon Quick。通过 Apache Ossie，他们还可以使用不连接到 Mosaic 的工具。

### 从哪里开始

- 选择当前争论的一项指标（NRR、贡献边际、活跃客户是常见的候选指标）。一种度量标准在流通中具有多个定义。
- 写出三到五个与之相关的业务问题。这些将成为您的验收测试。
- 在 Mosaic 中对您的主要来源进行建模，并获取返回可靠数字的指标。
- 在模型中已存在的属性上逐步链接其他源，一次一个。
- 对代理将看到的每个指标和属性进行作者描述。这是准确性变化最大的地方。
- 通过 Mosaic MCP 连接 Strands 代理并运行您的验收问题。
- 观察真实的查询模式几周，然后将热门内容移至内存中。
- 将稳定的定义导出到 Apache Ossie 并将其置于版本控制之下。
