强化学习（RL）后训练正在成为构建有能力的语言模型智能体的标准步骤。模型通过生成轨迹、接收奖励并基于结果更新其策略，学会在多步序列上进行推理和行动。要以规模化方式运行这一过程——跨越多个节点、每次训练需要数百 GPU 小时的 rollout——需要持久化的集群基础设施。该基础设施必须能够支撑长时任务、在硬件故障时不丢失进度地恢复，并在训练动态展开时提供可观测性。

[Amazon SageMaker HyperPod](https://aws.amazon.com/sagemaker/hyperpod/) 为在 [Amazon Elastic Kubernetes Service (Amazon EKS)](https://aws.amazon.com/eks/) 上的大规模机器学习（ML）工作负载提供了这套基础设施。通过其[集群弹性（cluster resiliency）特性](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-resiliency.html)，它持续监控节点健康状况并自动替换故障节点，从而一次硬件故障不会拖垮整个集群。配合 checkpoint 机制，训练任务可以从最后一个保存的步继续，而不必从头重启。这对于多节点长时 RL 运行尤为重要——否则一次硬件故障就会损失数小时的 rollout 进度。结合 [HyperPod 上的 Ray 能力](https://aws.amazon.com/blogs/machine-learning/introducing-new-ray-capabilities-on-sagemaker-hyperpod/)，你可以从 SageMaker Studio 创建 Ray 集群、通过安全连接远程提交任务，并通过 HyperPod Observability EKS 附加组件为你预置的 [Amazon Managed Grafana 仪表盘](https://aws.amazon.com/grafana/)来监控训练。

在这篇文章中，我们展示如何利用这些能力，使用开源 RL 框架 [SkyRL](https://github.com/NovaSky-AI/SkyRL) 在 SageMaker HyperPod 上训练一个 `Qwen3-VL-8B` 视觉语言模型，以在视觉迷宫中导航，训练算法采用 Group Relative Policy Optimization（GRPO）。从 [VisGym SFT checkpoint](https://huggingface.co/VisGym/visgym_model)（一个监督微调（SFT）起点）出发，在 HyperPod 上进行 GRPO 后训练，使迷宫求解率在一个固定的 64 迷宫评测集上从 43.75% 提升到 95% 以上。

## 前提条件

要跟随本文的操作步骤，你需要：

- 一个使用 Amazon EKS 编排的 SageMaker HyperPod 集群，其中至少包含 3 台 ml.g7e.12xlarge 实例和 1 台 ml.r5d.16xlarge 实例。
- 在集群中安装以下 Kubernetes operator：**KubeRay operator**、**HyperPod Observability EKS add-on** 以及 **HyperPod Ray Endpoint Operator**（用于远程任务提交）。参见 [Ray on HyperPod 入门指南](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-ray-getting-started.html)。
- 在集群上安装 [Amazon FSx for Lustre CSI 驱动](https://github.com/kubernetes-sigs/aws-fsx-csi-driver)。你还需要一个 Amazon FSx for Lustre 文件系统、一个由该文件系统支撑的 PersistentVolume，以及一个可供 pod 挂载的 PersistentVolumeClaim（ReadWriteMany）。训练任务在 `/shared` 处使用它来做 checkpoint 存储、Low-Rank Adaptation（LoRA）adapter 同步和评测输出。
- 一个具有连接你的 HyperPod 集群权限的 SageMaker Studio 域。参见[为 Ray 设置 SageMaker Studio](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-ray-studio-setup.html)。
- 已安装 `toolkit-for-ray-on-sagemaker-ai` Python 包。

## 背景

本节回顾训练背后的强化学习概念以及本文所使用的集群拓扑。

### 多轮 RL 与 GRPO

标准的单轮 RL 将奖励赋予单个模型输出。[多轮 RL](https://docs.aws.amazon.com/sagemaker/latest/dg/model-customize-mtrl.html) 则在整个步骤序列上训练智能体：它观察一个状态、采取行动、获得反馈，然后进入下一个状态。策略从整个 episode 累积的奖励中学习，而不是从任何单个步骤学习。

考虑导航一个二维迷宫的示例问题。一个 episode 就是对某个迷宫的一次尝试，每一轮（turn）就是一步移动：模型查看当前迷宫图像，选择一个方向或决定停止，环境再把更新后的视图送回。奖励是稀疏的，只有当模型在移动次数限制内真正到达目标时才会得到 1.0，否则什么都得不到。没有逐步的标准答案可供训练，因为某一步是否好坏取决于它周围的那些步。

这正是 SkyRL 的 Group Relative Policy Optimization（GRPO）发挥作用的地方。对于每个起始位置，智能体在当前策略下多次运行该迷宫，GRPO 将这些运行彼此对照打分：强化那些超过本组平均值的运行，压低落后于平均值的运行。这种组内比较就是全部的训练信号，这使得 GRPO 无需单独的 critic 或 value 模型即可工作。

### 训练拓扑

本文讨论的方案在一个 HyperPod Ray 集群上运行 SkyRL，该集群有三台 GPU 工作节点和一台 CPU 头节点。SkyRL 将推理和训练放在同一批 GPU 上共存：vLLM 引擎生成 rollout（完整的迷宫 episode），而用 Fully Sharded Data Parallel（FSDP）分片的策略模型负责梯度更新。在每个优化器步之后，更新后的 LoRA adapter 权重通过 Amazon FSx for Lustre 共享存储从训练 rank 同步到推理引擎。

以下是我们使用的实例类型。其他 GPU 实例和集群规模同样可行，前提是工作节点有足够的 GPU 显存容纳模型。

- **Workers**：3x `ml.g7e.12xlarge`（每台 2x NVIDIA RTX PRO 6000 Blackwell GPU，共 6 块 GPU）。
- **Head**：`ml.r5d.16xlarge`（512 GB 内存，负责管理 Ray GCS、仪表盘以及 LoRA adapter 归并）。
- **Policy model**：带 LoRA（rank 32）的 `Qwen3-VL-8B`，使用 PyTorch FSDP 分片到 6 块 GPU 上。
- **Rollout engines**：6 个共存的 vLLM 实例，每块 GPU 一个。
- **Shared storage**：位于 `/shared` 的 Amazon FSx for Lustre，用于 LoRA 同步和评测输出。

HyperPod 提供集群基础设施：Ray 集群从 SageMaker Studio 创建，任务提交使用 `sagemaker_ray://` 协议，训练指标通过 HyperPod Observability 附加组件自动流入预置的 Amazon Managed Grafana 仪表盘。

## 方案概览

以下步骤演示如何准备训练环境、启动集群、运行任务、监控进度以及托管训练好的模型。

### 步骤 1：准备容器镜像

为了快速上手，使用以下 Dockerfile 构建一个预装了 SkyRL、VisGym 及其依赖的容器镜像。这就是你在下一步于 HyperPod 上启动 Ray 集群时要指定的镜像。它基于官方的 NovaSky-AI SkyRL 基础镜像，并将 SkyRL 和 VisGym 都固定到特定的 commit SHA，以保证构建可复现：

```
FROM novaskyai/skyrl-train-ray-2.57.0-py3.12-cu13.0

ENV HF_HUB_ENABLE_HF_TRANSFER=1 \
    QWEN_VL_MODEL=Qwen/Qwen3-VL-8B-Instruct \
    UV_PROJECT_ENVIRONMENT=/home/ray/anaconda3

# SkyRL's full FSDP stack into the system python Ray uses (uv .venv is invisible to `ray start`).
# Pinned to a commit SHA so the build is reproducible.
ARG SKYRL_REF=4298730b55bb01fe1b711662df53dca42a3b7615
RUN git clone https://github.com/NovaSky-AI/SkyRL.git /home/ray/skyrl \
    && cd /home/ray/skyrl && git checkout ${SKYRL_REF} \
    && cd /home/ray/skyrl/skyrl-train \
    && uv sync --active --extra fsdp \
    && /home/ray/anaconda3/bin/python -c \
       "import ray, torch, vllm, transformers, flash_attn; \
        from vllm_router.launch_router import launch_router; \
        print('skyrl stack OK', torch.__version__, vllm.__version__)"

# uv sync prunes Ray's dashboard extras; restore ray[default] so the full dashboard starts.
RUN uv pip install --python /home/ray/anaconda3/bin/python "ray[default]==2.57.0" \
    && /home/ray/anaconda3/bin/python -c \
       "from ray.dashboard.optional_deps import aiohttp"

# VisGym maze environment and dataset generator.
ARG VISGYM_REF=184fbd5e5dc81e32c8b944d9e40ac54dad62e3f2
RUN git clone https://github.com/anyscale/VisGym.git /home/ray/visgym \
    && cd /home/ray/visgym && git checkout ${VISGYM_REF} \
    && uv pip install --python /home/ray/anaconda3/bin/python -e . "pygame==2.6.1"

ENV FI_PROVIDER=efa FI_EFA_USE_DEVICE_RDMA=1 NCCL_PROTO=simple NCCL_DEBUG=INFO
WORKDIR /workspace
CMD ["/bin/bash"]
```

构建该镜像并推送到你账户中的 Amazon Elastic Container Registry (Amazon ECR) 仓库。记下完整的镜像 URI，你在下一步创建 Ray 集群时会用到它：

```
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
REGION=us-west-2
IMAGE_URI="${ACCOUNT}.dkr.ecr.${REGION}.amazonaws.com/ray/skyrl-visgym:latest"

aws ecr get-login-password --region ${REGION} | \
  docker login --username AWS --password-stdin ${ACCOUNT}.dkr.ecr.${REGION}.amazonaws.com

docker build -t skyrl-visgym .
docker tag skyrl-visgym ${IMAGE_URI}
docker push ${IMAGE_URI}

echo "Image URI: ${IMAGE_URI}"
```

### 步骤 2：从 SageMaker Studio 启动 Ray 集群

进入 SageMaker Studio，选择 **HyperPod**，选中你的集群，然后转到 **Tasks** 选项卡。从任务类型列表中选择 **RayCluster**，然后选择 **Create Ray Cluster**。

在创建表单中，将集群命名为 `skyrl-visgym`，把头节点实例类型设为 `ml.r5d.16xlarge`，并使用 `ml.g7e.12xlarge` 添加三台 worker。将容器镜像设为你在步骤 1 中推送的 `IMAGE_URI`。

这里列出的实例类型是我们本次演练所用的。其他实例类型也可以工作，但对于头节点要记住一个约束：它需要大内存。头节点在每次保存 checkpoint 时归并来自 GPU worker 的 LoRA adapter 分片，这会将完整的 adapter 权重集短暂加载到 CPU 内存中。我们选用 `ml.r5d.16xlarge` 正是看中了它的大内存容量（512 GB 内存）以容纳这一过程。

#### 挂载 Amazon FSx for Lustre

要附加你的 Amazon FSx 文件系统，点击创建表单右上角的 YAML 按钮切换到原始清单编辑器，然后把 volume 和 mount 同时加入头和 worker 的 pod spec。每个 pod 的相关部分如下所示：

```
containers:
  - name: ray-head  # or ray-worker
    volumeMounts:
      - name: shared
        mountPath: /shared
volumes:
  - name: shared
    persistentVolumeClaim:
      claimName: <your-fsx-pvc-name>
```

将 `<your-fsx-pvc-name>` 替换为由你的 Amazon FSx 文件系统支撑的 PersistentVolumeClaim 的名称。这样配置后，`/shared` 在集群的每个节点上都可用，训练任务可以从 pod 中读写 checkpoint、LoRA 权重和评测输出。

打开 Remote endpoints，这样你就能在没有本地 `kubectl port-forward` 的情况下提交任务并打开仪表盘。集群会为两者生成经 IAM 认证的 URL。

### 步骤 3：准备训练脚本

将以下内容保存为工作目录中的 `train_job.sh`。脚本在首次运行时下载 SFT checkpoint 并生成数据集（两者都写入 Amazon FSx，因此跨运行持久化），然后启动 GRPO 训练任务。

SFT checkpoint 为 GRPO 提供了一个强起点：在 VisGym 演示数据上预训练过的 `Qwen3-VL-8B` 已经知道如何解析迷宫图像并输出结构化的移动动作，因此 GRPO 只需优化哪些序列能到达目标。

当设置 `trainer.placement.colocate_all=true` 时，vLLM rollout 引擎和 FSDP 策略 worker 共享同一批 GPU。在 rollout 阶段，GPU 并行运行推理。在策略更新步阶段，它们以集合通信方式运行 FSDP 训练。`lora_sync_path` 指向 Amazon FSx，因此在每个优化器步之后，更新后的 adapter 权重对该节点上的推理引擎立即可见。若不做共存（colocation），你需要为训练和推理分别准备独立的 GPU 池，而它们会在各阶段之间闲置等待对方——这种乒乓模式会浪费算力。共存让训练和推理在同一硬件上轮流使用，从而避免了这段空闲时间。这也是 `gpu_memory_utilization=0.45` 被保守设置的原因：每块 GPU 需要同时为 FSDP 分片和 vLLM KV cache 留出余量。

还有一些参数值得一提。`n_samples_per_prompt=8` 控制 GRPO 为每个迷宫 prompt 生成多少条 rollout 轨迹以计算组优势（group advantage）。`max_turns=15` 将每个 episode 限制在最多 15 步。`hf_save_interval=20` 每 20 步将 LoRA adapter 分片归并到头节点并保存一个 Hugging Face 兼容的 checkpoint。`eval_interval=10` 每 10 步在留出的 64 迷宫评测集上运行评测，以便你跟踪求解率随训练的进展。

该任务还会写入完整的训练 checkpoint，以便从被打断处恢复。设置 `ckpt_interval=20` 会每 20 步将完整的训练状态保存到 `ckpt_path`。该状态包括模型权重、优化器状态、学习率调度和 dataloader 位置。`resume_mode=latest` 告诉 SkyRL 在任务启动时从该路径下最近的 checkpoint 继续。将 `ckpt_path` 指向不绑定于单个节点的持久共享存储，例如一个 Amazon Simple Storage Service (Amazon S3) 前缀或你的 Amazon FSx 挂载点。跨运行保持该路径稳定，以便重启的任务能找到它的 checkpoint。这就是与 HyperPod 集群弹性相配合之处。当某个节点故障时，HyperPod 会自动检测并替换它，而当你重新提交任务时，它会从最后保存的步继续而非重新开始。此处写入的完整 checkpoint 保存了用于恢复的训练状态，而 `hf_save_interval` 导出的是可直接用于推理的 LoRA adapter，因此两者出于不同目的并行运行。

```
#!/usr/bin/env bash
# GRPO fine-tune from the VisGym SFT checkpoint on maze_2d/easy.
set -euxo pipefail
cd /home/ray/skyrl
export HF_HUB_ENABLE_HF_TRANSFER=0
export SKYRL_RAY_PG_TIMEOUT_IN_S=600
RUN_ID=$(date +%Y%m%d-%H%M%S)
EXPORT_PATH="/shared/runs/${RUN_ID}-train"

ENV_ID=maze_2d/easy
TRAIN_DIR=/tmp/visgym_train_256
EVAL_DIR=/tmp/visgym_eval_seeded
SFT_CKPT=/shared/models/visgym_sft_mixed_qwen3vl

if [ ! -f "$SFT_CKPT/config.json" ]; then
  echo "=== Downloading SFT checkpoint ==="
  mkdir -p "$SFT_CKPT"
  python -c "
from huggingface_hub import snapshot_download
snapshot_download(repo_id='VisGym/visgym_model', allow_patterns='mixed_qwen3vl/*',
    local_dir='$SFT_CKPT', local_dir_use_symlinks=False)
import shutil, os; src='$SFT_CKPT/mixed_qwen3vl'
[shutil.move(os.path.join(src,f),'$SFT_CKPT') for f in os.listdir(src)]; os.rmdir(src)
"
fi

python examples/train/visgym/dataset.py --env_id "$ENV_ID" --num_rows 256 --output_dir "$TRAIN_DIR"
python examples/train/visgym/dataset.py --env_id "$ENV_ID" --num_rows 64  --seed --output_dir "$EVAL_DIR"

python examples/train/visgym/entrypoint.py \
  --env_variant sft \
  data.train_data="['$TRAIN_DIR/train.parquet']" \
  data.val_data="['$EVAL_DIR/train.parquet']" \
  trainer.algorithm.advantage_estimator="grpo" \
  trainer.policy.model.path="$SFT_CKPT" \
  trainer.policy.model.lora.rank=32 \
  trainer.policy.model.lora.alpha=32 \
  trainer.policy.model.lora.lora_sync_path="/shared/lora" \
  trainer.placement.colocate_all=true \
  trainer.strategy=fsdp \
  trainer.placement.policy_num_nodes=3 \
  trainer.placement.policy_num_gpus_per_node=2 \
  trainer.placement.ref_num_nodes=3 \
  trainer.placement.ref_num_gpus_per_node=2 \
  trainer.ref.fsdp_config.cpu_offload=false \
  generator.inference_engine.num_engines=6 \
  generator.inference_engine.tensor_parallel_size=1 \
  generator.inference_engine.gpu_memory_utilization=0.45 \
  generator.inference_engine.engine_init_kwargs.max_model_len=16000 \
  environment.env_class=visgym \
  trainer.epochs=20 \
  trainer.train_batch_size=24 \
  trainer.policy_mini_batch_size=12 \
  trainer.micro_forward_batch_size_per_gpu=1 \
  trainer.micro_train_batch_size_per_gpu=1 \
  trainer.update_epochs_per_batch=1 \
  trainer.max_prompt_length=2048 \
  generator.sampling_params.max_generate_length=1024 \
  generator.sampling_params.temperature=0.7 \
  generator.max_turns=15 \
  generator.max_input_length=8192 \
  generator.n_samples_per_prompt=8 \
  generator.vision_language_generator=true \
  generator.batched=false \
  trainer.remove_microbatch_padding=false \
  trainer.algorithm.use_kl_loss=false \
  trainer.policy.optimizer_config.lr=3.0e-6 \
  trainer.eval_interval=10 \
  trainer.eval_before_train=true \
  trainer.ckpt_interval=20 \
  trainer.hf_save_interval=20 \
  trainer.logger="console" \
  trainer.project_name="vlm_maze_2d_easy" \
  trainer.run_name="sft_grpo_${RUN_ID}" \
  trainer.resume_mode=latest \
  trainer.log_path="/tmp/skyrl-logs" \
  trainer.dump_eval_results=true \
  trainer.export_path="$EXPORT_PATH" \
  trainer.ckpt_path="s3://<your-bucket>/skyrl-visgym/ckpts/sft-grpo"
```

### 步骤 4：远程提交训练任务

当 `toolkit-for-ray-on-sagemaker-ai` 安装好后，Ray 标准的 Jobs CLI 会通过该包注册的 `sagemaker_ray://` 地址方案，经集群的安全端点进行认证。该库使用你的 AWS 凭证对 Ray 端点认证，因此你无需自己处理。这样一来，你就可以从笔记本、CI/CD 流水线或具备 AWS 凭证的环境中提交和跟踪任务，无需 `kubectl port-forward`，也无需到集群的直接网络路径。

首先，对 EKS 集群进行认证：

```
aws eks update-kubeconfig --name <eks-cluster-name> --region us-west-2
```

然后提交任务，把当前目录作为工作目录传入，以便将 `train_job.sh` 上传到集群头节点：

```
# Address format: sagemaker_ray://<ray-cluster-name>/<namespace>
ray job submit \
  --address sagemaker_ray://skyrl-visgym/default \
  --submission-id sft-train \
  --working-dir . \
  -- bash train_job.sh
```

提交后，使用相同地址跟踪进度：

```
# List jobs and check status
ray job list --address sagemaker_ray://skyrl-visgym/default

# Stream logs
ray job logs sft-train \
  --address sagemaker_ray://skyrl-visgym/default --follow
```

你也可以在 SageMaker Studio 的 Tasks 选项卡下跟踪任务，或直接从集群的 Actions 菜单打开 Ray Dashboard，获得带有每个 actor 资源利用率的完整任务视图。

### 步骤 5：监控训练进度

HyperPod 提供两个监控面：Ray Dashboard 用于任务级可见性，Amazon Managed Grafana 用于基础设施和训练指标。两者都可直接从 SageMaker Studio 的 Tasks 选项卡访问。

#### Ray Dashboard

从 SageMaker Studio 的 Tasks 选项卡中选择 Open Ray Dashboard。这会自动为你生成一个短期有效的认证 URL。

你也可以用 [HyperPod CLI](https://github.com/aws/sagemaker-hyperpod-cli) 生成该 URL：

```
hyp create ray-dashboard-connection \
  --cluster-name <ray-cluster-name> \
  --namespace <kubernetes-namespace>
```

#### 跟踪评测准确率

SkyRL 每 `eval_interval=10` 步就在固定的 64 迷宫留出集上运行一次评测，并将 `eval/all/pass_at_1` 记录到控制台。你可以在任务日志中 grep 它：

```
ray job logs sft-train \
  --address sagemaker_ray://skyrl-visgym/default | grep "eval/all/pass_at_1"
```

在我们的实验中，模型大约在 100 步达到 75% 的求解率，并在 160 步达到峰值 96.875%（64 迷宫中解出 62 个），相比之下 GRPO 后训练前的基线为 43.75%（64 迷宫中 28 个）。你的结果会因超参数和迷宫配置而不同。一旦求解率达到你的目标，该步的 LoRA adapter 就可以用于推理了。Checkpoint 每 20 步保存到 `/shared/runs/<run_id>/global_step_<N>/policy/adapter_model.safetensors`。

### 步骤 6：托管训练好的模型用于推理

训练完成后，你要部署的产物是一个 LoRA adapter 而非完整模型，Ray Serve 会在请求时按需加载该 adapter。唯一的要求是 adapter 存放的位置。Ray Serve 的动态 LoRA 加载器从 Amazon S3 这类云存储读取 adapter，因此首先要将该 adapter 暂存到一个 S3 前缀中。把你训练中选定的那个 checkpoint 步的 adapter 复制到该前缀：

```
aws s3 cp --recursive \
  /shared/runs/<run_id>/global_step_N/policy/ \
  s3://<your-bucket>/lora-adapters/maze-grpo/
```

每个 adapter 占据该前缀下自己的子目录，而该子目录名（本例中为 `maze-grpo`）就是端点上线后你请求该 adapter 时使用的名称。

#### 在 Ray 集群上用 Ray Serve 提供服务

要托管该 adapter，在一个由 [AWS Deep Learning Container for Ray Serve LLM](https://aws.github.io/deep-learning-containers/ray-llm/) 构建的 Ray 集群上运行 Ray Serve，该容器打包了 Ray Serve、`ray[llm]` 技术栈以及 vLLM。用它，你可以借助内置的 `ray.serve.llm:build_openai_app` builder 搭建一个 OpenAI 兼容的端点，而无需自定义镜像。我们推荐在 `RayService` 上运行推理，它会被 KubeRay 调和成其自己的一个 Ray 集群（参见 [KubeRay 文档](https://docs.ray.io/en/latest/cluster/kubernetes/getting-started/rayservice-quick-start.html)）。

`RayService` 通过 `serveConfigV2` spec 来描述它的 Serve 应用，而在该 spec 内，`ray.serve.llm:build_openai_app` builder 为每个基础模型接受一个 `llm_configs` 条目，如下方配置所示：

```
serveConfigV2: |
  applications:
    - name: maze-vlm
      route_prefix: /
      import_path: ray.serve.llm:build_openai_app
      args:
        llm_configs:
          - model_loading_config:
              model_id: visgym-qwen3vl
              # base SFT model on FSx
              model_source: /shared/models/visgym_sft_mixed_qwen3vl
            lora_config:
              # adapter prefix in S3
              dynamic_lora_loading_path: s3://<your-bucket>/lora-adapters
              max_num_adapters_per_replica: 1
            engine_kwargs:
              enable_lora: true
              # match the training LoRA rank
              max_lora_rank: 32
              max_loras: 1
              max_model_len: 16000
            deployment_config:
              autoscaling_config: { min_replicas: 1, max_replicas: 1 }
```

在该配置中，`model_source` 指向 Amazon FSx 挂载上的基础 SFT 模型，而 `dynamic_lora_loading_path` 指向前一步中你填充的 S3 前缀。将 `max_lora_rank` 设为与训练时相同的 LoRA rank。最后，确保 Ray Serve 副本能够获得 AWS 凭证，以便从你的 S3 桶读取 adapter。在 Amazon EKS 上，推荐的机制是 [Amazon EKS Pod Identity](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html)。

#### 每次请求的动态 LoRA 加载

有了这套配置，单个部署即可同时服务基础模型以及存放在该 S3 前缀下的每一个 adapter，而你通过每个请求上的 `model` 字段来选择运行哪一个：

- 将 `model` 设为 `visgym-qwen3vl`，则单独运行基础 SFT 模型。
- 将 `model` 设为 `visgym-qwen3vl:maze-grpo`，则在该基础模型之上应用 GRPO adapter。该 ID 遵循 `<base-model-id>:<adapter-name>` 约定，其中 adapter 名是你在 `dynamic_lora_loading_path` 下创建的子目录。

某个 adapter 第一次被请求时，Ray Serve 会从 Amazon S3 将其下载到副本上并缓存起来，因此之后的每个请求都复用已加载的权重而无需再次下载。由于该端点使用 OpenAI API，你可以从任何 OpenAI 兼容的客户端调用它。有关完整的配置选项集，参见 [Ray Serve LLM 文档](https://docs.ray.io/en/latest/serve/llm/index.html)和[多 LoRA 部署指南](https://docs.ray.io/en/latest/serve/llm/user-guides/multi-lora.html)。

部署好 adapter 后，模型就能独立跑完一个完整的迷宫 episode：每一轮接收当前视图，返回它的下一步移动，直到到达目标。驱动这一过程的循环（构造 prompt、编码迷宫图像、解析动作、推进环境）与 SkyRL 和 VisGym 用于 rollout 的循环相同。让那个环境指向所服务的端点，而不是围绕一个裸客户端重建它。

## 清理

完成演练后，清理你创建的资源以停止产生费用。打开 SageMaker Studio 的 **Tasks** 选项卡，选中 `skyrl-visgym` Ray 集群，并从 **Actions** 菜单选择 **Delete**。如果你创建了单独的 `RayService` 来托管训练好的 adapter，也用 `kubectl delete rayservice <name>` 删除它。要释放 GPU 容量本身，缩容你为本次演练添加的 HyperPod 实例组，或从 Amazon SageMaker AI 控制台删除 HyperPod 集群。如果你不再需要 SageMaker Studio 域，也可以从 SageMaker AI 控制台删除它。

## 结论

在这篇文章中，我们完整演练了在 Amazon SageMaker HyperPod 上的端到端多模态 RL 训练工作流：构建自定义容器镜像、从 SageMaker Studio 启动 Ray 集群、从 VisGym SFT checkpoint 出发为 GRPO 提供强初始化、使用 `sagemaker_ray://` 协议提交任务、通过 HyperPod Observability 附加组件预置的 Ray Dashboard 和 Grafana 仪表盘监控评测准确率，并在达到目标求解率后托管训练好的 adapter 用于推理。整个工作流运行在 Amazon SageMaker HyperPod 提供的具备弹性、自愈能力的计算基础设施之上。

同样的模式适用于 SkyRL 工作负载或其他基于 Ray 的 RL 框架。HyperPod 基础设施、Studio 控制台体验以及 Amazon FSx 共享存储都适用于使用标准 Ray API 的框架。

要开始上手，参见 [Amazon SageMaker HyperPod 文档](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod.html)和 [Ray on HyperPod 入门指南](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-ray.html)。
