# CBRE 如何使用 Amazon Bedrock 驱动统一的物业管理搜索与数字助理

*本文与 CBRE 的 Lokesha Thimmegowda、Muppirala Venkata Krishna Kumar 和 Maraka Vishwadev 共同撰写。*

[CBRE](https://www.cbre.com/) 是全球最大的商业地产服务与投资公司。公司在 100 多个国家为客户提供服务，业务范围涵盖资本市场与租赁顾问、投资管理、项目管理和设施管理。

[CBRE 使用 AI](https://www.cbre.com/about-us/technology/artificial-intelligence)，通过高级分析、自动化工作流和预测性洞察来改进商业地产解决方案。在商业地产生命周期中用 AI 释放价值的机会始于大规模数据。凭借业内最大的数据集和一套全面的企业级技术，公司已实施一系列 AI 解决方案，以提升个人生产力并支持大范围转型。

本篇博文介绍 [CBRE](https://www.cbre.com/) 与 AWS 如何合作改变物业管理专业人员获取信息的方式，借助 [Amazon Bedrock](https://aws.amazon.com/bedrock/)、[Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/)、[Amazon Relational Database Service](https://aws.amazon.com/rds/)、[Amazon Elastic Container Service](https://aws.amazon.com/ecs/) 和 [AWS Lambda](https://aws.amazon.com/lambda/)，打造统一的下一代搜索与数字助理体验，打通多种类型的物业数据。

## 统一物业管理搜索的挑战

CBRE 专有的 PULSE 系统整合了范围广泛的重要物业数据——既包括关系型数据库中记录交易的结构化数据，也包括文档存储库中的非结构化数据，后者涵盖从租赁协议到物业巡检的各种内容。过去，物业管理专业人员不得不在数百万份文档中筛选，并在多个不同系统之间切换，才能找到物业维护详情。数据分散在 10 个不同的来源和 4 个独立的数据库中，很难获得完整答案。这种碎片化的设置降低了生产力，也使发掘物业运营的关键洞察变得困难。

物业管理方面的专家（而非数据库语法专家）需要用自然语言提出复杂问题，快速综合多种不同的信息，并避免手动审阅冗长文档。

挑战在于：交付一个直观、统一的搜索解决方案，弥合结构化与非结构化内容，同时具备稳固的安全性、企业级的可靠性和性能。

## 解决方案架构

CBRE 在 PULSE 中实施了一个由 Amazon Bedrock 驱动的全球搜索解决方案，以应对这些挑战。该搜索架构旨在跨多样化数据类型提供无缝、智能且安全的信息检索体验。它编排了用户交互、AI 驱动的处理和稳固的数据存储之间的相互作用。

CBRE 的 PULSE 搜索解决方案使用 Amazon Bedrock，通过单一 API 使用多个基础模型，快速部署生成式 AI 能力。CBRE 的实现使用 Amazon Nova Pro 生成 SQL 查询，处理时间缩短了 67%，而 Claude Haiku 则驱动智能文档交互。该解决方案对所有物业数据保持企业级安全性。通过将 Amazon Bedrock 的能力与检索增强生成（Retrieval Augmented Generation，RAG）及 Amazon OpenSearch Service 相结合，CBRE 打造了横跨 800 多万份文档和多个数据库的统一搜索体验，从根本上改变了物业专业人员访问和分析关键业务信息的方式。

让我们梳理一下该解决方案的流程：

- **物业经理与 PULSE UI：** 物业经理通过直观的 PULSE 用户界面进行交互，该界面既是传统关键字搜索的入口，也是自然语言查询（NLQ）的入口。UI 展示搜索结果，支持文档对话，并在桌面和移动端呈现智能摘要。
- **动态搜索执行：** 当用户提交请求时，系统首先从 [Amazon ElastiCache for Redis](https://aws.amazon.com/elasticache/redis/) 检索用户特定的权限，选择它是因为其低延迟和高吞吐量。随后，跨 [Amazon OpenSearch](https://aws.amazon.com/opensearch-service/) 和事务数据库的搜索操作会受到这些用户特定权限的约束，确保用户只能访问经授权的结果，并具备实时的细粒度控制。
- **编排层：** 这个中央控制枢纽充当应用的大脑，接收来自 PULSE UI 的用户请求，并智能地将其路由到相应的后端服务。主要职责包括：  将查询路由到相关的数据系统（结构化数据库、非结构化文档，或两者兼有以进行深度搜索）。  发起跨 SQL Interact 和 Doc Interact 组件的并行搜索。  合并、去重并排序来自不同来源的结果，形成统一的结果。  通过 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 集成管理对话历史。
- **SQL interact 组件（结构化数据搜索）：** 该路径通过以下关键步骤管理与结构化关系数据库（RDBMS）的交互：  **4.1 数据库元数据检索：** 从 Amazon OpenSearch 索引中动态获取实体（如物业、联系人和租户）的 schema 详情（例如表名、列名、数据类型、关系、约束）。  **4.2 Amazon Bedrock LLM（[**Amazon Nova**](https://aws.amazon.com/ai/generative-ai/nova/) Pro）：** 将用户的自然语言查询与 schema 元数据一起解读，转换为针对该数据库定制的准确、优化的 SQL 查询。该解决方案使用 Amazon Nova Pro 将 SQL 查询生成时间从此前的平均 12 秒缩短到 4 秒。  **4.3 RDBMS 系统（PostgreSQL、MS SQL）：** 实际的事务数据库，例如 PostgreSQL 和 MS SQL，存放核心的结构化物业管理数据（例如物业、联系人、租户、K2 表单）。它们执行 LLM 生成的 SQL 查询，并将结构化的表格结果返回给 SQL Interact 组件。
- **DocInteract 组件（非结构化文档搜索）：** 该路径专为非结构化文档的智能搜索和交互而设计。  **5.1 向量存储（OpenSearch 集群）：** 将文档（包括来自 OpenText 的文档）存储为高维向量，以使用 k-Nearest Neighbors 等技术实现高效的语义搜索，同时通过元数据过滤兼顾速度与准确性。  **5.2 Amazon Bedrock LLM（Claude Haiku）：** 解读 NLQ 并将其转换为优化的 OpenSearch DSL 查询，同时驱动 "Chat With AI" 功能实现直接的文档交互，生成简洁的对话式响应，包括答案、摘要和自然对话。

在确立了包含 SQL Interact 和 DocInteract 组件的核心架构之后，以下各节探讨针对每种数据类型实施的具体优化与创新，首先是从结构化数据搜索的增强开始。

## 结构化数据搜索

在架构中概述的 SQL interact 组件基础上，PULSE Search 应用提供两种访问 PostgreSQL 和 MS SQL 中结构化数据的搜索方法。**关键字搜索**会扫描字段和 schema 以查找特定词项，从而全面覆盖整个数据系统。借助 **自然语言查询（NLQ）搜索**，用户可以用日常语言与数据库交互，将查询转换为数据库查询。两种方法都支持物业经理跨数据库模块高效地定位和检索信息。

### 在 SQL 层面提升数据库层搜索性能

我们面临的独特挑战是实现应用范围内的关键字搜索，它需要扫描数据库表中的各个列——与传统 RDBMS 系统中针对特定索引列的搜索相比，这是一项非常规需求。这种通用搜索能力对用户体验至关重要，让用户无需知道具体的列名或数据结构即可发现信息。

我们利用了 PostgreSQL 和 MS SQL Server 数据库中的原生全文搜索能力：

- **PostgreSQL 实现：**

```
SELECT * FROM dbo.pg_db_view_name bd WHERE textsearchable_all_col @@ to_tsquery('english', 'keyword')
```

- **Microsoft SQL Server 实现**：

```
SELECT * FROM [dbo].ms_db_view_name WHERE CONTAINS(*, '8384F')
```

**注意：** 我们的实现使用专门的文本搜索列（textsearchable_all_col），它拼接了视图 pd_db_view_name 中可搜索的字段，而 ms_db_view_name 表示使用全文搜索索引创建的视图。

这项优化通过利用数据库原生能力，并借助专门的索引算法在全面搜索覆盖与最优数据库性能之间取得平衡，使查询性能提升了 80%。

### 在 SQL interact API 层面提升数据库层搜索性能

我们在数据库搜索功能中实施了多项优化，针对三个关键绩效指标（KPI）：准确性（结果的精确度）、一致性（可复现的结果）和相关性（确保结果符合用户意图）。这些增强措施在降低响应延迟的同时提升了这些 ACR 指标，从而带来更快、更可靠的搜索结果。

**Prompt Engineering 改动：** 我们实施了一套全面的 prompt 管理与优化方法，重点关注以下因素。

- **可配置性**：我们采用存储在外部文件中的模块化 prompt 模板，以实现版本控制、简化管理并减小 prompt 体积，提升性能和可维护性。
- **用于缩小上下文窗口的动态字段选择**：系统使用基于 KNN 的相似度搜索，只筛选并选择与用户意图最相关的 schema 字段，从而缩小上下文窗口大小并优化 prompt 效果。
- **动态 few-shot 示例：** 系统使用基于 KNN 的相似度搜索，从配置文件中智能选择最相关的 few-shot 示例用于 SQL 生成。这种智能的情境感知方法确保 prompt 中只包含最贴切的示例，最大限度减少不必要的数据开销。这种方法有助于从 LLM 获得一致且准确的 SQL 生成。
- **业务规则集成：** 系统在专门的按 schema 划分的配置文件中维护一个集中的业务规则存储库，使规则管理和更新更加精简高效。在 prompt 生成期间，相关业务规则会被动态集成到 prompt 中，既促进规则应用的一致性，又为更新和维护提供灵活性。
- **基于 LLM 分数的相关性**：我们在初始 KNN 检索之后增加了第四次 LLM 调用，用于评估和重排 schema 相关性，解决向量搜索返回不相关或排序不佳 schema 的问题。例如，在处理关于物业或联系人信息的用户查询时，向量搜索可能返回三个 schema，但：  第三个 schema 可能与查询无关。  两个相关 schema 的排序可能无法反映它们与查询的真实相关性。  为应对这些挑战，我们引入了一个额外的 LLM 处理（第 4 次 LLM 并行调用）步骤，它：  评估每个 schema 与用户查询的相关性。  分配相关性分数以确定 schema 的重要性。  根据 schema 与查询的实际相关性重新排序。  这一增强通过以下方式改进了我们的 schema 选择流程：  确保只选择真正相关的 schema。  维持正确的相关性排序。  为后续查询处理提供更准确的上下文。

这些增强通过验证只处理真正相关的 schema、维持正确的相关性排序以及为查询处理提供更准确的上下文，改进了 schema 选择。结果是更精准、更符合情境的响应，并提升了整体应用性能。

### 使用 Amazon Nova Pro 进行 SQL 生成的并行 LLM 推理

我们为 NLQ 到 SQL 的转换实施了一套全面的并行处理架构，提升了系统性能和效率。该方案引入了对 LLM 推理引擎的并发、基于 schema 的 API 调用，并对多个 schema 评估采用异步处理。我们安全第一的方法在执行情境感知的 schema 识别（结合相似度搜索并强制实施访问权限）的同时，对用户权限进行身份验证和校验。系统只处理用户拥有明确授权的 schema，从而奠定数据安全基础。在完成身份验证后，系统动态生成 prompt（详见我们的 prompt engineering 框架），并通过并行 LLM 推理调用启动对最相关 schema 的并发处理。在执行之前，它会为生成的 SQL 查询添加强制的安全连接，以实施楼宇级别的访问控制，将用户限制在其获授权的楼宇内。

最终确定的 SQL 查询会在相应的数据库系统（PostgreSQL 或 SQL Server）上执行。系统处理查询结果，并以结构化的 API 响应返回，在整个工作流中保持安全性和数据完整性。该架构既通过并行处理实现了最优性能，又通过多层访问控制实现了全面的安全性。

这种集成方法纳入了对生成 SQL 查询的并发验证，从而缩短了处理时间、提高了系统吞吐量，并降低了 Amazon Nova Pro 的推理延迟。引入 Nova Pro 后，推理延迟有了显著改善。该框架的架构有助于高效利用资源，同时在 SQL 查询生成方面保持高准确率，使其在处理复杂数据库操作和大批量查询处理需求时尤为有效。

## 增强非结构化数据搜索

PULSE 文档搜索使用两种主要方法，并通过专用的专门搜索功能加以增强。用户可以使用精简的**关键字搜索**在文档和元数据中精确定位词项，在已知精确搜索词时实现快速检索。这种直接的方法确保用户能够在整个文档范围内快速找到精确匹配。第二种方法**自然语言查询（NLQ）搜索**支持用日常语言与文档交互，解读意图并将查询转换为搜索参数——对复杂或基于概念的查询尤为强大。作为对这两种核心搜索方法的补充，系统还提供专门的搜索能力，包括收藏夹和合集搜索，让用户能够高效浏览个人整理的文档集和共享合集。此外，系统提供智能的文档上传搜索功能，帮助用户根据文档类型和物业语境快速找到合适的文档类别和上传位置。

搜索基础设施支持多种文件格式，包括 PDF、Microsoft Office 文档（Word、Excel、PowerPoint）、电子邮件（MSG）、图像（JPG、PNG）、文本文件、HTML 文件以及各种其他文档类型，从而全面覆盖物业管理环境中的文档类别。

### Prompt 工程与管理优化

我们的文档搜索系统融合了先进的 prompt engineering 技术，以提升搜索准确性、效率和可维护性。让我们探讨 prompt 管理系统的关键特性及其为搜索体验带来的价值。

#### 两阶段 prompt 架构与模块化 prompt 管理：

我们系统的核心是两阶段 prompt 架构。这一设计将工具选择与任务执行分离，从而实现更高效、更准确的查询处理。

```
# Modular prompt loading from configuration
get_doc_detect_prompt = get_prompts("doc_prompts/tool_detect/Get_Document_data_detect")
get_doc_prompt = get_prompts("doc_prompts/prepare_prompt/Get_Document_data_prompt")
keyword_search_detect_prompt = get_prompts("doc_prompts/tool_detect/keyword_search_detect")

def detect_tool(user_prompt):
    tool_descriptions = {
        "Get_Document_data": get_doc_detect_prompt,
        "keyword_search": keyword_search_detect_prompt,
        "Get_Fawdocs_collections": faw_collection_detect_prompt,
        "upload_documents": upload_document_detect_prompt
    }
    
    messages = [
        {"role": "system", "content": "You are an AI assistant that determines the most appropriate tool..."},
        {"role": "user", "content": f"Here are the tool descriptions:\n{json.dumps(tool_descriptions, indent=2)}\n\nUser query: {user_prompt}\n\nWhich tool should be used?"}
    ]
```

这种架构通过在每个查询处理阶段只加载必要的 prompt，将 token 使用量最多降低 60%。轻量的初始阶段快速将查询路由到合适的工具，而专门的 prompt 则在聚焦的上下文中处理实际执行，从而同时提升工具选择和查询执行的性能与准确性。

我们的模块化 prompt 管理系统将 prompt 存储在外部配置文件中，以便根据上下文动态加载并支持个性化。它支持在不部署代码的情况下更新 prompt，将更新周期从数小时缩短到数分钟。该架构便于对不同 prompt 变体进行 A/B 测试和快速回滚，增强了系统的适应性和可靠性。

```
def prepare_tool_prompt(detected_tool, userid):
    tool_prompts = {
        "keyword_search": keyword_search_prompt,
        "Get_Document_data": get_doc_prompt.replace("userid", userid),
        "upload_documents": upload_document_prompt,
        "Get_Favdocs_collections": fav_collection_prompt
    }
    return tool_prompts[detected_tool]
```

系统实现了情境感知的 prompt 选择，适配查询类型、文档特征和搜索场景。这确保针对每个独特的搜索场景使用最合适的 prompt 和查询结构。例如，系统区分不同的问题类型（例如 'list_question'），以便对各种查询意图进行定制处理。

### 搜索算法优化

我们的文档搜索系统实施的搜索算法将基于向量的语义搜索与传统基于文本的方法相结合，以跨文档元内容和内容进行搜索。我们采用针对不同搜索场景优化的不同查询策略。

#### 关键字搜索：

关键字搜索采用双重策略，结合使用短语匹配进行元数据和内容搜索。固定的查询模板结构有助于提升效率和一致性，其中纳入了预定义的元数据、内容、权限规则和楼宇 ID 约束，同时动态整合用户特定的词项和角色。这种方法支持快速可靠的搜索，同时维持适当的访问控制和相关性。

用户查询（如 "lease agreement" 或 "property tax 2023"）会被解析为组成词，每个词都需要在文档内容中匹配才具备相关性，从而得到精确的结果。

```
"bool": {
    "must": [
        {"match_phrase": {"srccontent": word}} for word in search_words
    ]
}
```

类似地，对于元数据搜索，系统使用跨元数据字段的短语搜索：

```
"multi_match": {
    "query": search_words,
    "type": "phrase",
    "fields": ["srcmetadata"]
}
```

这种方法提供了跨文档元数据的精确匹配能力，当用户搜索特定文档属性时能得到精确结果。系统并发执行两种搜索类型，随后合并并去重两种搜索的结果，并在两个结果集之间对评分进行归一化。

#### 自然语言查询搜索：

我们的 NLQ 搜索通过两个主要组件将 LLM 生成的查询与基于向量的语义搜索相结合。元数据搜索使用 LLM 从自然语言输入生成 OpenSearch 查询。例如，"查找去年提及科技公司提前终止条款的租赁协议"会被转换为一个结构化查询，跨文档类型、日期、物业名称和其他元数据字段进行搜索。

对于内容搜索，我们采用 K 因子为 5 的 KNN 向量搜索来识别语义相似的内容。系统将查询转换为向量 embedding，并同时执行元数据和内容搜索，合并结果的同时最大限度减少重复。

#### 与文档对话（用于深度文档交互的数字助理）：

"Chat with Document" 功能支持在初始搜索后与特定文档进行自然对话。用户可以通过直接的交互过程提出问题、请求摘要，或从所选文档中查找特定信息。

启用后，系统会使用文档的节点标识符检索完整文档内容，并通过精简的流水线处理用户查询。每个查询由 LLM 使用精心构造的 prompt 处理，这些 prompt 将用户的问题与相关文档上下文结合起来。

借助这一能力，用户可以高效地从复杂文档中提取信息。例如，物业经理无需手动浏览冗长的协议，就能快速理解租赁条款或付款计划。该功能提供即时摘要和解释，便于在文档密集型工作流中快速获取信息和做出决策。

### 扩展文档摄取

为处理高吞吐量的文档处理和企业级的大规模摄取，我们的摄取流水线使用**异步 Amazon Textract** 进行可扩展的并行文本提取。该架构能高效处理多种文件类型——PDF、PPT、Word 文档、Excel 文件和图像——即使文件有数百页或高分辨率内容也不在话下。一旦文档上传到 Amazon S3 桶，一条消息会触发 SQS 队列，调用 Lambda 函数启动异步 Textract 任务，在不阻塞执行的情况下卸载繁重的提取和 OCR 任务。

对于文本文档，系统从 Amazon S3 读取文件并提交到 Amazon Textract 的异步 API，由后者在后台处理文档。任务完成后，检索并解析结果以提取结构化文本。随后，这些文本会基于 token 数量或语义边界被智能分块，并通过 Bedrock embedding 模型（例如 Amazon Titan Text embeddings v2）处理。每个分块都会补充元数据，并被索引到 Amazon OpenSearch 中，以实现快速且情境感知的搜索能力。摄取完成后，由用户和 CBRE 市场查找驱动的智能查询策略会动态地将搜索导向相关的 OpenSearch 索引。

图像文件遵循类似的流程，但在 base64 转换后使用 Amazon Bedrock Claude 3 Haiku 进行 OCR。提取的文本随后像标准文本文档一样被分块、嵌入和索引。

## 安全与访问控制

用户身份验证和授权通过一个多层安全流程进行：

- **访问 token 验证：** 系统通过针对每个请求验证 Microsoft B2C 中的用户身份及其访问 token，来核实用户身份。同时还会检查用户是否具有访问应用的授权。
- **权限验证：** 与此同时，系统会检查用户在 Redis 数据库中的权限，以核实其对应用中特定模块及其有权查询的数据库 schema（entitlements）拥有适当的访问权限。
- **物业访问校验：** 系统还会从 Redis 数据库中检索其获授权的楼宇列表（用户所映射到的楼宇 ID 列表），确保他们只能访问与其业务组合内物业相关的数据。

这种并行校验流程有助于实现更安全、更适当的访问，同时通过 Redis 的高速数据检索能力维持最优性能。Redis 在应用加载期间通过数据库中维护的用户权限与楼宇映射关系进行填充。如果在 Redis 中找不到用户详情，则会调用 API 来补充 Redis 数据库。

## 经验教训与最佳实践

以下是我们基于构建此解决方案的经验总结出的经验教训与最佳实践：

- **使用 prompt 模块化：** Prompt engineering 对于优化应用性能和保持一致的结果至关重要。将 prompt 拆解为模块化组件，有助于更好地管理 prompt，通过简化的版本控制、简化的测试与验证流程以及改进的性能跟踪能力，增强控制力和可维护性。模块化的 prompt 设计方法降低了 token 使用量，进而缩短了 LLM 响应时间并提升了整体系统性能。模块方法还通过更快的故障排查、缩短实施时间和更可靠的查询生成，提升了 SQL 生成效率，从而更快地解决边缘案例和业务规则更新。
- **提供准确的 few shot 示例**：为提高 SQL 生成的准确性和一致性，使用带有模块化组件的动态 few shot 示例，以便无缝更新示例存储库。  纳入覆盖常见用例和边缘场景的示例。  维护一组多样化的高质量示例对，覆盖各种业务场景。  保持示例简洁并聚焦于特定模式。  根据新的业务需求定期更新示例。  移除或更新过时的示例。  将示例限制为相关性最高的前 1 或前 2 个，以管理 token 使用量。  定期验证所选示例的相关性。  建立反馈回路，持续提升示例匹配的准确性。  微调相似度阈值以实现最佳示例匹配。
- **缩小上下文窗口**：为缩小所传递上下文的上下文窗口大小，只从 schema 定义中选择排名靠前的 N 个 KNN 字段以及关键/必填字段。仅对字段数量多、会增大上下文窗口大小的 schema 应用动态上下文字段选择。
- **提升相关性**：LLM 评分机制帮助我们获得正确的相关 schema（模块）集合。利用 LLM 智能处理相关模块的 KNN 结果，帮助我们获得最相关的有序结果。还应考虑：  仅靠向量相似度可能无法捕捉真正的语义相关性。  排名靠前的 K 个近邻并不总能保证上下文准确性。  结果的顺序可能无法反映其与查询的实际相关性。  使用 LLM 评分提供了更准确的 schema 相关性判定。
