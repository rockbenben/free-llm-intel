# 用 CDK 在托管的 Amazon Bedrock 知识库上构建 agentic 检索

本文用 AWS Cloud Development Kit (AWS CDK) 在托管的 Amazon Bedrock 知识库上构建企业级 agentic 检索。要看清这为什么值得做，最好先从普通 Retrieval Augmented Generation (RAG) 在哪里失效说起。大多数 RAG 系统的起点都相同：把问题做 embedding，从一个索引里取回最接近的 chunk，交给模型，返回答案。一次检索，一次生成。对一大类问题来说，这就是正确的设计，没有理由做得更复杂。

它的失效方式是有迹可循的。问一个答案横跨两个语料库的问题，单次检索只会返回模型所需内容的一半，这比什么都不返回更糟，因为答案回来时语句流畅却不完整。问一个*正确来源取决于问题本身*的问题，单个索引没有任何机制来做选择。问一个需要先看第一批结果、再回头把语料库再看一遍的问题，而第二次查看根本没有地方可去。

企业级 agentic 检索把这三个问题都解决了，办法是让一个 推理 agent 进入循环。agent 决定是否检索、查哪个知识库，以及在组织答案之前是否要再去取更多内容。这正是 [Amazon Bedrock Knowledge Bases](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html) 演进的方向。随着托管知识库上线，检索不再是一次 embed-and-fetch 调用，而变成了一项 agentic 能力：多轮规划、由工具驱动的检索，以及有据可依、带引用的答案。AgenticRetrieveStream API 把这个能力作为一等的服务特性提供出来，而不是让你自己拼装。这确实行得通，但它同时也带来一个实打实更难运维的问题。单发流水线是一个你读一遍就能推理清楚的函数。而一个在循环中推理并检索的 agent，每个问题走的路径都不一样。默认情况下，你既看不到它走过的路径，也看不出它给出的答案到底好不好。可观测性不再是可有可无的点缀，而成了判断系统是否正常工作的唯一途径。

2024 年 8 月，[使用 Amazon Bedrock 的 Knowledge Bases 和 AWS CDK 构建端到端 RAG 解决方案](https://aws.amazon.com/blogs/machine-learning/build-an-end-to-end-rag-solution-using-knowledge-bases-for-amazon-bedrock-and-the-aws-cdk/) 把这套单发设计以 CDK 应用的形式部署出来：一个 [Amazon Simple Storage Service (Amazon S3)](https://docs.aws.amazon.com/s3/) 语料库、一个 [Amazon OpenSearch Serverless](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless.html) collection 和索引、一个知识库和一个数据源，作为若干 CDK stack 供给，顺序由你手工排定。这篇文章发布以来，有三件事变了。

- **[Amazon Bedrock](https://docs.aws.amazon.com/bedrock/) 现在提供托管知识库**（Type: MANAGED），摄取、存储、索引和检索都由它自己负责。那篇文章里供给的 OpenSearch Serverless collection 和索引，不再需要你去创建、扩容，也不用为此支付 OpenSearch Compute Units (OCUs) 的费用。
- **[Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/) 提供 agentic 的那一半**，包括一个把每个知识库暴露为 Model Context Protocol (MCP) 工具的 Gateway、一个承载 推理 agent 的 Runtime，以及 AgenticRetrieveStream，它在内部重排并返回一段综合出来的、带引用的答案。Agentic 检索**只**在托管知识库上可用。
- **可观测性与评估现在成了你可以直接供给的东西**，而不是事后外挂上去的。这套方案在同一次部署中交付两个覆盖七层遥测的 [Amazon CloudWatch](https://docs.aws.amazon.com/cloudwatch/) 仪表板，以及两种形式的评估：按需评估和持续评估。

本文构建的就是这套系统：一个跨两个知识库做路由、通过 Gateway 检索、返回有据可依且带引用答案的 agent，它的每一层行为都埋了埋点，整体是一个用 Python 写的 [AWS CDK](https://docs.aws.amazon.com/cdk/) 应用。一条命令部署全部内容，顺序由 CDK 推导。

如果你读过[那篇 2024 年的文章](https://aws.amazon.com/blogs/machine-learning/build-an-end-to-end-rag-solution-using-knowledge-bases-for-amazon-bedrock-and-the-aws-cdk/)，从 Amazon S3 bucket 到知识库这一段会显得很熟悉，之后的一切都是新的：向量存储没了，检索变成 agentic，而且这个应用供给的东西里大约有一半，存在的目的就是告诉你 agent 做了什么。如果你没读过，本文也能独立阅读。

参与其中的服务，以及一个问题穿过它们时走过的路径：agent 决定是否检索、查哪个知识库，Gateway 把每个知识库暴露成它可以调用的工具，托管知识库负责搜索和给出引用，循环按问题需要的次数反复进行。agent 沿途做的一切都落到 Amazon CloudWatch。

## 背景

在动手走一遍之前，先把三件事说清楚：是什么让检索变成 agentic，为什么托管知识库是它的正确基础，以及为什么可观测性和评估应该属于设计本身，而不是事后再外挂。

### 从 RAG 到企业级 agentic 检索

经典的 Retrieval Augmented Generation (RAG) 做一次检索、一次生成。**企业级 agentic 检索**把 推理 agent 放进循环：由它决定*是否*检索以及*检索什么*，可以多次检索以逐步改进，选择*哪个*知识库相关（语义路由），然后才组织出带引用的、有据可依的答案。有了托管知识库，这是一等的服务能力：AgenticRetrieveStream API 负责多轮规划、执行检索并返回带引用的答案，而不需要你在原始向量检索之上自己搭建并维护一层编排。这样在复杂问题上能得到更好的答案，但同时也让系统本身更复杂、更难运维——这正是可观测性和评估要从一开始就内置进来的原因。

### 托管知识库与自建知识库的对比

Amazon Bedrock 现在提供**托管知识库**（Type: MANAGED）：**摄取、存储、索引和检索**都由 Amazon Bedrock 为你管好，默认还包括用服务托管的模型做 embedding 和重排，因此**没有向量数据库需要你去供给、扩容或打补丁**。这与**客户自管**（DIY）知识库不同，后者由你自己选择并运维向量存储（例如 Amazon OpenSearch Serverless）。

对这套方案来说，有两项差异最为关键：

| **能力** | **Amazon Bedrock 托管** | **客户自管 (DIY)** |
| --- | --- | --- |
| Agentic 检索 (AgenticRetrieveStream) | ✅ 支持 | ❌ 不支持 |
| AgentCore Gateway 集成 | ✅ 支持 | ❌ 不支持 |
| 数据存储 | 自动扩缩容，完全由 Amazon Bedrock 托管 | 你自己供给、扩容并维护 |
| Embedding + 重排 | 内置托管模型，无额外费用 | 由你自行配置 |
| 需要管理的基础设施 | **无** | 向量数据库 + 其他 |

由于 agentic 检索和 AgentCore Gateway 连接器只在托管知识库上可用，它自然是企业级 agentic 检索的合适基础。这也意味着存储和索引由 Amazon Bedrock 为你管理，因此这套设计里没有需要供给的 OpenSearch Serverless collection 或 OCU 容量。当你想自己选择并运维向量存储时，客户自管仍然是正确选项，例如复用已有的 OpenSearch Serverless collection，或满足特定的数据驻留、调优或合规要求。对企业级 agentic 检索而言，托管知识库正是这项能力得以成立的前提。

### 为什么需要可观测性与评估

一个只是*返回答案*的 agentic 系统不足以用于生产。你需要看清它表现如何（latency、调用量、token 用量），检索和答案质量如何，而且这些信号要持续可得。这套方案**交付**两个覆盖七层遥测的 CloudWatch 仪表板，外加两种评估形式（按需和持续），全部由同一个 CDK 应用供给。依据支撑、引用和评估这几层同时也支撑负责任的使用。带引用的答案可以回溯到来源段落，响应因此保持可审计；faithfulness 与 correctness 分数则让你能及时发现答案偏离来源，而不必等到生产环境里才知道。

### 为什么这个方案要用 CDK

任何 infrastructure-as-code 工具都能创建这些资源。CDK 在这里能站住脚，有一个针对这个架构的具体理由：**四个 stack 之间交叉引用非常密集**。Gateway 需要两个知识库 id。agent 需要 Gateway 的 URL 和 ARN。仪表板需要 KB id、Gateway ARN，*以及*agent runtime id——七个值跨越 stack 边界，每一个要么是某个指标的一个维度，要么是某个连接器的一个目标。

如果写成原始模板，那就是一堆要靠手工保持一致的 stack export 和跨 stack 查找，再加一个按正确顺序部署、把输出一路传下去的脚本，而任何东西一改名，两者就都开始漂移。在 CDK 里你只需要把 construct 传过去，export 和依赖边都由这一次传递推导出来。2024 年那套方案有三个 stack，依赖链基本是线性的。到了四个 stack、七个值跨越其间的规模，这个差别就不再只是风格问题了。

## 方案概览

下面是一个问题在系统中从头到尾走过的路径。值得慢慢看，因为接下来全文会从左到右逐段走一遍。

下面的图勾勒出端到端的 agentic 检索工作流。用户的问题进入运行在 AgentCore Runtime 上的 agent，Runtime 经由 AgentCore Gateway 把它路由到两个 AgenticRetrieveStream 工具之一——每个托管知识库一个，分别是 financial 和 weather，两者都从 Amazon S3 摄取。被选中的工具返回一段有据可依、带引用的答案，过程中每一步都流式写入 Amazon CloudWatch 和 AWS X-Ray。图中的编号徽标对应下面逐段的讲解。

图中的编号步骤对应下面的工作流，流程如下。

**步骤 0 —— 一次性，在部署时完成。** 在任何问题被提出之前，Amazon S3 中的每个语料库都会被摄取到自己的托管知识库里：Amazon Bedrock 自动完成解析、chunk、embedding 和索引。这发生在 stack 部署时，只做一次，不属于每个问题的路径，所以图中画成虚线箭头并标记为步骤 0。之后每个问题都按步骤 1–6 走。

- **用户把问题发给托管在 Amazon Bedrock AgentCore Runtime 上的 agent**。Runtime 用 OpenTelemetry (OTEL) span 自动为整个 reason-and-act 循环埋点，因此从第一次调用起系统就是可观测的。
- **agent 的推理模型做规划并跨知识库路由。** 由于每个知识库都作为独立的检索工具暴露出来，agent 会挑选主题与问题匹配的那个工具——financial 或 weather——而不是去搜一个混合索引。
- **被选中的工具调用由 AgentCore Gateway 通过 MCP agent 转发**，以 agent 的 IAM task role 授权、用 SigV4 签名，进而调用该知识库在托管知识库上的 AgenticRetrieveStream API。
- **AgenticRetrieveStream 负责知识库内部的工作：** 把问题分解成子查询，在 Amazon Bedrock 管理的数据存储（内容摄取自 Amazon S3 的语料库）中迭代检索，并综合出一段有据可依、带引用的答案，经 Gateway 流式返回。
- **agent 检查返回的上下文是否充分。** 若不充分，它就进入下一轮循环，重新路由并检索，然后才组织最终答案；若充分，它就把带引用的答案返回给用户。
- **整个过程中，Runtime 持续向 Amazon CloudWatch 和 AWS X-Ray 发出 span、token 计数和指标**，填满七层可观测性数据，同时为按需评估和持续评估的分数提供输入。

在内部，这套工作流就是一个 CDK 应用 `app.py`，它声明了四个 stack。顺序不由你决定，CDK 会根据你传入的 construct 引用推导出来：

```
kb_stack = KnowledgeBasesStack(app, f"{project}-kb", env=env)

gateway_stack = AgenticGatewayStack(
    app, f"{project}-gateway", env=env,
    financial_kb=kb_stack.financial_kb,  # ← the reference creates the dependency
    weather_kb=kb_stack.weather_kb,
)

agent_stack = AgentRuntimeStack(
    app, f"{project}-agent", env=env,
    gateway=gateway_stack.gateway,
)

DashboardsStack(
    app, f"{project}-dashboards", env=env,
    financial_kb=kb_stack.financial_kb,
    weather_kb=kb_stack.weather_kb,
    gateway=gateway_stack.gateway,
    agent_runtime=agent_stack.agent_runtime,
)
```

接线到此为止。就是这四次构造函数调用，取代了 export/import 的记账工作和部署脚本。

| **#** | **Stack** | **它创建什么** | **备注** |
| --- | --- | --- | --- |
| 1 | -kb | S3 bucket、语料库上传、两个 Type: MANAGED 知识库、数据源、IAM、摄取 | 知识库达到 ACTIVE，语料库完成摄取 |
| 2 | -gateway | Gateway (AWS_IAM / MCP)、每个知识库对应的 AgenticRetrieveStream 目标 | 无需 Cognito |
| 3 | -agent | ECR、CodeBuild、运行在 Runtime 上并已埋点的 Strands agent、托管的日志与追踪、在线评估 | **~8–10 分钟**（镜像构建） |
| 4 | -dashboards | agentic-observability 和 kb-observability 仪表板 | 在你导入流量之前都是空的 |

agent 跑的是一个 reason-and-act 循环：先思考（一次大语言模型 (LLM) 调用），决定调用哪个知识库工具，读取经 Gateway 返回的内容，往往还要再检索一次，然后才组织出最终的带引用答案。每一步都由 Runtime 自动埋点，所以七层可观测性数据都是从真实流量里填起来的。

**七层数据。** L1 知识库原生指标、L2 摄取、L3 agentic 检索质量、L4 Gateway/MCP 指标、L5 OTEL span 树、L6 token 用量、L7 评估分数。第 1、4、5 层自动产生；第 3、6、7 层由驱动 notebook 以自定义指标的形式发布。

所有可调项都在一个文件 `config.py` 里：

| **设置项** | **含义** | **默认值** |
| --- | --- | --- |
| `EnvSettings.PROJECT_NAME` | **每一个** stack 和资源的前缀名 | `bmkb-obs-cdk` |
| `EnvSettings.ACCOUNT_REGION` | 要部署到的 AWS Region | us-west-2（或你 profile 里的那个） |
| `KbConfig.EMBEDDING_MODEL_TYPE` | `MANAGED`（内置）或 `CUSTOM`（自带 ARN） | `MANAGED` |
| `AgentConfig.MODEL_ID` | agent 的推理模型，也就是第 6 层的花费来源 | Claude Haiku 4.5 |
| `EvalConfig.SAMPLING_PERCENTAGE` | 在线评估的采样率，**见下方声明** | 100 |

改 `PROJECT_NAME` 会得到整套方案的一份独立命名的副本，于是同一账号下可以并存两套部署。驱动 notebook 读的是同一个常量，所以它会自动跟着改名，不需要手工同步任何 stack 名称。

## 描述数据集

这套方案自带两个小语料库，放在仓库的 data/ 目录下：

- **Financial** —— 一份合成的 Octank Financial 10-K（octank_financial_10K.pdf，约 198 KB）。
- **Weather** —— 一份**真实的、公开可获取的**美国国会研究处关于龙卷风的报告（[IF12695](https://sgp.fas.org/crs/misc/IF12695.pdf)，tornadoes_report.pdf，约 560 KB）。

⚠️ **关于数据：** 财务语料库是*合成的*。Octank 是一家虚构公司，那份 10-K 是模型生成的样本数据（CC0 许可）。它**不是**真实财务数据。天气语料库是美国政府的真实公共领域作品，是一份美国国会研究处报告，可在 [sgp.fas.org/crs/misc/IF12695.pdf](https://sgp.fas.org/crs/misc/IF12695.pdf) 公开获取（美国政府的作品不受版权保护）。要换成你自己的数据，只需把文件放到 data/ 下，并调整 `config.py` 中的前缀，不需要其他改动。

这两个语料库是有意做出差异的，这样 agent 就必须把每个问题路由到正确的知识库——这正是语义路由这条线索。因为它们是托管知识库，我们不配置 chunking、embedding 或索引：摄取时 Amazon Bedrock 会解析每个 PDF、做 chunk、用它的托管模型做 embedding，并自动建立索引。

我们用两个彼此独立的知识库，各自通过 Gateway 暴露为自己的检索工具，而不是用一个知识库同时装下两个语料库——这个选择是刻意的。给 agent 两个具名工具，路由就成了一个可以被观察到的、显式的推理行为：span 树显示它针对某个问题选了*哪个*工具，第 3 层的检索质量指标也能按知识库分开，于是 financial 和 weather 的准确率永远不会混成一个数字。如果用一个横跨两个语料库的工具，这个区分就会塌掉，路由决策会退到单个索引的排序内部去、无从窥见，而每一个质量信号都会变成两个不相关领域之间的平均值。把语料库和它们的工具分开，正是让 agent 行为变得可读的原因，而这恰恰是整个练习的意义所在。

在 CDK 里，把语料库放进 S3 就是一个 BucketDeployment：

```
s3deploy.BucketDeployment(
    self, "FinancialCorpus",
    sources=[s3deploy.Source.asset(str(ROOT / "data" / "financial"))],
    destination_bucket=self.source_bucket,
    destination_key_prefix=KbConfig.FINANCIAL_PREFIX,
)
```

BucketDeployment 值得专门了解一下，恰恰是因为替代方案太诱人：不用它的话，触发摄取的那个 custom resource 往往会顺带长出一个上传步骤，于是同一个资源就干起了两件不相干的事。而在这里，它只需要负责*摄取*。

托管摄取会自动扫描、chunk、embedding 并索引每一份文档：每个知识库索引一份文档，零失败。

## 部署方案

本节讲解如何用一条命令部署整套方案。前置条件满足后，`cdk deploy --all` 会按 CDK 推导出的依赖顺序供给全部四个 stack，并自动把每个跨 stack 的值传下去。

### 前置条件

- 一个 AWS 账号，且拥有 Amazon Bedrock、AgentCore (Runtime + Gateway)、[AWS Identity and Access Management (IAM)](https://docs.aws.amazon.com/iam/)、CloudWatch、[AWS X-Ray](https://docs.aws.amazon.com/xray/)、[Amazon Elastic Container Registry (Amazon ECR)](https://docs.aws.amazon.com/ecr/)、[AWS CodeBuild](https://docs.aws.amazon.com/codebuild/)、Amazon S3、[AWS Lambda](https://docs.aws.amazon.com/lambda/) 和 [AWS CloudFormation](https://docs.aws.amazon.com/cloudformation/) 的相应权限。
- 账号中可用 agent 所用的模型（默认 `us.anthropic.claude-haiku-4-5-20251001-v1:0`）。
- 启用 CloudWatch Transaction Search，这样 OTEL span 才会落到 aws/spans，供第 5–7 层使用。
- Node.js 18+ 和 CDK CLI（`npm install -g aws-cdk`），以及 Python 3.13+。
- 账号和 Region 已为 CDK 做过 bootstrap（cdk bootstrap），每个账号/Region 做一次即可。
- 本地不需要 Docker，agent 镜像由 CodeBuild 构建（ARM64）。

### 一条命令

要部署这套方案，克隆仓库、创建虚拟环境、安装依赖，然后运行 `cdk deploy --all`。在终端里执行以下命令：

```
git clone https://github.com/aws-samples/amazon-bedrock-samples.git
cd rag/managed-knowledge-bases/07-IaaC/managed-kb-observability-cdk/
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cdk bootstrap  # once per account/region
cdk deploy --all
```

前两条命令克隆示例代码并进入项目目录。接下来两条创建并激活 Python 虚拟环境，安装 CDK 应用的依赖。`cdk bootstrap` 为 CDK 准备好账号和 Region（每个账号/Region 只需做一次），`cdk deploy --all` 则供给全部四个 stack。

账号和 Region 取自你的 AWS profile（CDK_DEFAULT_ACCOUNT / CDK_DEFAULT_REGION），所以部署这个应用不需要做任何修改。

Region 可用性：托管知识库、agentic 检索 (AgenticRetrieveStream) 以及 Amazon Bedrock AgentCore（Runtime 和 Gateway）并非在每个 AWS Region 都可用。部署前请确认目标 Region 提供以上全部能力，并相应地在 `config.py` 中设置 `ACCOUNT_REGION`。默认是 us-west-2。当前可用性请查阅 [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/) 和 [Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/) 文档，以及 [AWS Regional Services List](https://aws.amazon.com/about-aws/global-infrastructure/regional-product-services/)。

这个版本没有部署脚本，而这正是重点：`cdk deploy --all` 会遍历它从 `app.py` 推导出的依赖图，按顺序部署四个 stack，并自动传递每个跨 stack 的值。终端会逐个报告每个 stack 的完成情况：bmkb-obs-cdk-kb [1/4]（默认的 PROJECT_NAME），然后 gateway [2/4]，然后 agent [3/4]，最后 dashboards [4/4]。这个顺序是推导出来的，不是声明的：它源自各 stack 之间的 construct 引用，因此新增一个消费已有输出的第五个 stack，部署顺序会自动重排。

-agent 这个 stack 用 CodeBuild 构建 agent 容器，所以这一阶段要预留大约 8–10 分钟。另外三个很快。每个 stack 完成后都会打印自己的输出，你就在那里拿到知识库 id、Gateway URL、runtime ARN 和两个仪表板 URL。部署结束时，四个 stack 全部完成。下面的截图是成功执行 `cdk deploy --all` 之后的 AWS CloudFormation 控制台。

### 关于长耗时资源的一点说明

这套方案里有两件事远超 AWS Lambda 函数 15 分钟上限所能支撑的朴素轮询：知识库摄取同步和 CodeBuild 镜像构建。AWS CDK 的 Provider 框架用 `on_event` / `is_complete` 的拆分来处理：一个 handler 启动工作，另一个被轮询直到报告完成。

```
cr.Provider(
    self, "IngestSyncProvider",
    on_event_handler=on_event,        # StartIngestionJob, return the job id
    is_complete_handler=is_complete,  # GetIngestionJob, report IsComplete
    query_interval=Duration.seconds(30),
    total_timeout=Duration.minutes(30),
)
```

没有任何地方会阻塞，回传给 CloudFormation 的响应协议由框架负责，而不是在每个 handler 里手写一遍；30 分钟的时限是一个属性，而不是你得绕着它做工程设计的东西。

```
dimensions_map={"KnowledgeBaseId": kb_id}
```

### 第 5 层：span 树

第 5 层是 aws/spans 里的原始 OTEL span 树，也是能直接看到 agentic 循环的那一层。这一层值得仔细读，因为嵌套关系并不直观：一次 LLM 调用会产生三个 span。Strands 的 `invoke_agent` span 包住整个回合，一个内部的 `chat` span 包住模型调用，而一个类型为 `CLIENT` 的 `chat <model>` span 才是真正的调用，三者重复报告同一组 `gen_ai.usage.*` token 属性。

下面的截图展示 aws/spans 中的 span 树，顶部的行里就能看到这种三层嵌套。

![aws/spans 中的 CloudWatch span 树。顶部三行分别是 invoke_agent 的 Strands Agents 聚合、一个内部 chat span，以及一个 CLIENT chat span，三者都报告相同的 7,299 个输入 token 和 268 个输出 token。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/22/ML-21614-14.png)

图 14：aws/spans 中的第 5 层 span 树，展示单次 LLM 调用的三层 span 嵌套

读顶部三行：先是 invoke_agent 的 Strands Agents 聚合，然后是一个内部 chat span，再是一个 CLIENT chat span，三者都报告相同的 7,299 个输入 token 和 268 个输出 token。这是同一次 LLM 调用出现在树的三个层级上，所以聚合时必须小心。

这个结构在你一开始聚合时就会产生影响。要让每次 LLM 调用只被计一次，就要过滤到 `CLIENT` 叶子节点：

```
fields attributes.gen_ai.request.model as model,
       attributes.gen_ai.usage.input_tokens as in_tok,
       attributes.gen_ai.usage.output_tokens as out_tok
| filter ispresent(in_tok) and kind = 'CLIENT' and name like /^chat /
| stats sum(in_tok) as input_tokens, sum(out_tok) as output_tokens,
        count(*) as llm_calls by model
```

不加这个过滤器，同一个查询会报出三倍的 token 和三倍的调用次数。

加上这个 CLIENT 叶子过滤器后，下面的截图展示了按模型划分的生成 token 用量，每次 LLM 调用只被计一次。

![CloudWatch 结果表，展示按模型划分的生成 token 用量，每次 LLM 调用只计一次：14 次调用，60,472 个输入 token 和 2,709 个输出 token。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/22/ML-21614-15.png)

图 15：按模型划分的生成 token 用量，每次 LLM 调用只计一次

有了这个过滤器，这次运行显示 14 次 LLM 调用，合计 60,472 个输入 token 和 2,709 个输出 token。没有它，同一个查询会报出三倍的调用次数和三倍的 token。

## 清理

用完之后请把方案移除，免得继续计费——存储的知识库数据、ECR 里的 agent 镜像，以及仍在运行的在线评估，在 stack 闲置期间都会一直花钱。一条命令即可全部拆除：

```
cdk destroy --all
```

CDK 会自行按依赖顺序的逆序删除 stack：先 dashboards，再 agent，再 gateway，最后 kb——就是它为部署推导出的同一张图，反着走一遍。没有什么拆除脚本需要和部署脚本保持一致，而把依赖关系只建模一次所带来的价值，安静却实在。

有两个删除相关的行为值得知道，因为它们各自取代了手写的清理代码：

```
self.source_bucket = s3.Bucket(
    self, "SourceBucket",
    removal_policy=RemovalPolicy.DESTROY,
    auto_delete_objects=True,  # replaces a list_object_versions delete loop
)

self.repository = ecr.Repository(
    self, "AgentImageRepo",
    removal_policy=RemovalPolicy.DESTROY,
    empty_on_delete=True,  # replaces an image-delete loop
)
```

这两处设置只是为了示例的整洁；对你真正在意的任何东西，请把 bucket 改成 `RemovalPolicy.RETAIN`。

CDK 的 bootstrap stack（`CDKToolkit`）及其 staging bucket 不会被删除。它们是账号级共享的基础设施，其他 CDK 应用可能依赖它们。

## 相比单发方案的变化

本文和[那篇 2024 年的方案](https://aws.amazon.com/blogs/machine-learning/build-an-end-to-end-rag-solution-using-knowledge-bases-for-amazon-bedrock-and-the-aws-cdk/)都是用 Python 写的 CDK 应用，都用 `cdk deploy` 部署。这里不变的是编写工具，变了的是它底下的架构，而且大部分变化是减法：

| **关注点** | **2024：单发 RAG** | **本方案** |
| --- | --- | --- |
| 向量存储 | 一个由你供给、扩容并按 OCU 计费的 OpenSearch Serverless collection 和索引 | 无。Type: MANAGED，存储和索引由 Amazon Bedrock 负责 |
| 索引生命周期 | 由一个 custom resource 创建索引并等待它变得可搜索 | 无需创建任何东西 |
| Embedding 模型 | 由你选择并授予访问权限 | 默认由服务托管 |
| Stack 数量 | 3：KB role → OpenSearch infra → KB + data source | 4：kb → gateway → agent → dashboards |
| 检索 | 一次 Retrieve，按向量相似度取 top-k 个 chunk | AgenticRetrieveStream，内部重排，返回综合出来的带引用答案 |
| 选择知识库 | 不适用，只有一个索引 | agent 在两个知识库之间做语义路由 |
| 对语料库的二次查看 | 一次调用无法做到 | agent 在作答前会再检索一次 |
| 遥测 | 未供给任何内容 | 七层，两个仪表板 |
| 评估 | 手工进行：同步、选一个模型、提问 | 按需和持续两种，两者都已供给 |
| 闲置时的成本底线 | 无论你查不查，OCU 费用都在累积 | 只有存储成本 |

这个取舍在两个方向上都真实存在。用单个索引回答单发问题，单次查询更便宜，也更容易推理清楚，而当答案就在某一个语料库里时，它完全够用。在不满足这个前提的情况下，再考虑上面那套设计。

### 真正在干活的 CDK construct

这个应用里有四个 construct 承担了大部分工作，值得点名，因为每一个都取代了人们通常要手写的东西：

- **Provider** —— 适用于那些超过 AWS Lambda 函数 15 分钟上限的 custom resource。`on_event` / `is_complete` 的拆分意味着轮询循环里不需要 sleep，回传给 CloudFormation 的响应协议也由框架负责，而不是在每个 handler 里内嵌一份 `urllib` 回调。
- **BucketDeployment** —— 负责上传语料库，这样摄取用的 custom resource 就只管摄取。
- **auto_delete_objects=True** 和 **empty_on_delete=True**，取代了手写的 `list_object_versions` 和删除镜像的循环——没有它们，stack 根本无法被销毁。
- **repository.grant_pull_push(project)** —— 用一行处理 CodeBuild 所需的八个 `ecr:*` action，名字由构造保证不会写错。

还有来自「观测」那一节的带类型仪表板：用 Metric / GraphWidget / Row 对象代替 DashboardBody JSON 字符串，这把「在控制台上渲染成坏样子」的错误变成了「在 `cdk synth` 阶段就失败」。

有两件事 CDK 并不会改变，而且动手之前值得知道：

- **自由格式的 JSON 仍然是 camelCase**。`connector_parameters` 和 `parameter_values` 是原样透传的，所以 AWS CDK 那套从 snake_case 到 PascalCase 的转换在它们内部并不生效。像 `bucketName` 和 `inclusionPrefixes` 这样的键必须严格按照 API 的要求拼写，否则在资源失败之前不会有任何东西提醒你。
- **字符串类型的值终究还是字符串。** 「观测」那一节提到的 `knowledge-base/<id>` 与不带前缀的 `<id>` 在维度上的差异，类型系统完全看不见。带类型的 construct 检查的是*结构*，不是*语义*。

这两点都不构成偏向某个工具而放弃另一个的理由。它们划出了「带类型」所能带来的边界，而知道这条边界画在哪儿，正是 CDK 让人觉得顺手而不是意外的大半原因。

## 结语

我们在托管的 Amazon Bedrock 知识库和 AgentCore 上构建了一套完整的企业级 agentic 检索方案：多知识库语义路由、一个 推理 agent、七层可观测性，以及按需和持续两种评估，并把全部内容作为单个 AWS CDK 应用部署出去。

有两点值得带走。托管知识库是移除了基础设施，而不是增加基础设施：没有向量存储要供给，没有索引要创建和等待，系统闲置时也不会累积 OCU 这一项费用。它同时也是支持 agentic 检索和 AgentCore Gateway 连接器的那种知识库类型，如 [Amazon Bedrock 文档](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html) 所述。而一旦检索变成 agentic，可观测性就不再是可选项。这个应用供给的东西里大约有一半，是为了回答「agent 究竟做了什么、给出的答案到底好不好」，这在 agentic 系统上并不是开销，而是让它真正可运维的那一部分。

CDK 的编写模型正是在这些接缝处证明了自己的价值。这个架构里有七个值跨越 stack 边界，每一个都是一个 construct 引用，而不是一对 export/import，这也正是为什么没有部署脚本、没有拆除脚本，也不需要记住任何固定顺序。

接下来你可以把数据源指向自己的语料库，把 agent 放进 virtual private cloud (VPC)，按你的预算和政策调整在线评估的采样率，或者给路由器再添几个知识库。想了解更多，可以看 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 详情页和 [Amazon Bedrock 文档](https://docs.aws.amazon.com/bedrock/)。这个应用、驱动 notebook 以及那些自包含的工具都在[配套的 GitHub 仓库](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/rag/managed-knowledge-bases/07-IaaC/managed-kb-observability-cdk)里，你可以克隆下来，用一条命令部署自己的副本。
