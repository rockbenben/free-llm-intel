# 使用 Amazon Bedrock AgentCore 构建面向业务支持的 AI agent

为业务支持开发 AI agent 会带来许多组织在尝试自动化日常 HR 任务时所面对的独特挑战。Works Human Intelligence（WHI）为日本大型企业与公益法人开发、销售并支持集成式 HR 系统「COMPANY」。

在本文中，我们分享 [AWS 生成式 AI 创新中心（GenAIIC）](https://aws.amazon.com/generative-ai/innovation-center/) 如何与 Works Human Intelligence（WHI）合作，使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agents/) 构建两个 AI agent。我们讨论遇到的挑战，以及那些把成本降低最多 97%、同时提升运营效率的解决方案。

使用 HR 系统的客户必须应对大量情形，例如组织变更、HR 系统修订、员工信息更新。对于在 HR 系统运营上面对类似挑战的组织来说，AI agent 可以显著减少工作量并提升生产力。当 WHI 开始用 AI agent 构建产品时，出现了若干挑战。为解决这些问题，我们 GenAIIC 与 WHI 团队紧密合作，提供新的视角并支持打造高质量产品。本项目范围覆盖两个旨在支持运营部门工作的 AI agent。通勤津贴 agent 负责处理因搬家等事件而产生的通勤津贴申请的审批。浏览器操作 agent 代表客户操作「COMPANY」。我们将在下面几节讨论这两个 agent 的挑战与解决方案。

## 通勤津贴 agent

该 agent 自动化通勤津贴申请的审批，这是员工调动等事件中出现的日常任务。

### 挑战

通勤津贴 agent 支持审批通勤津贴申请这一日常任务。WHI 当时已经在用 LangGraph、[Amazon Elastic Container Service（Amazon ECS](https://aws.amazon.com/ecs/)）与 [AWS Fargate](https://aws.amazon.com/fargate/) 推进一个概念验证（PoC）。不过，由于 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 在开发期间发布，团队开始考虑迁移。WHI 希望与我们合作，用 AgentCore 构建一个解决方案，来实现与「COMPANY」集成的 AI agent。此外，他们还想迁移到一个集成的多 agent 环境，并使用当时正在开发中的 AWS Fargate 与 [Amazon Cognito](https://aws.amazon.com/cognito/) 实现认证与授权。

### 解决方案概览

通勤津贴 agent 当时正用 LangGraph 与 Amazon ECS 开发，但团队担心那种把所有东西都跑在同一个 Amazon ECS 任务里的单体配置。因此我们一同调整了架构，让各个子 agent 在 AgentCore Runtime 上独立启动。由于需要多租户支持，我们决定用 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 与 Amazon Cognito 管理租户，以保持 WHI 自行构建与管理它的灵活性。

### 架构

Slack 是调用通勤津贴 agent 的入口，因此系统设计为在调用时进行认证，随后由相应的子 agent 处理请求。

### 结果与影响

由于 AgentCore 在本项目期间转为正式可用（GA），我们得以有效地使用它。通勤津贴 agent 仍然继续使用 LangGraph，但我们做了修改，让子 agent 运行在独立的 Runtime 上。这一改动便于将来扩展子 agent。我们也在考虑将来把负责统辖子 agent 的 supervisor agent 换成 Strands Agents。此外，WHI 此前自行托管 Langfuse 来查看 agent 状态，产生运维成本，改用 AgentCore Observability 后减轻了这一负担。

## 浏览器操作 agent

该 agent 使用浏览器访问 HR 系统、检查内容、执行操作，并代表客户收集证据。

### 挑战

第二个 agent 使用浏览器访问「COMPANY」、检查内容、执行操作并获取证据。当时正在用 LangGraph 与 Playwright Model Context Protocol（MCP）推进构建。团队通过以下做法确认浏览器操作的 token 减少了 88%：

- 从 agent 循环中移除过去不必要的部分（AI 与 Playwright MCP 之间的对话历史）。
- 从 Playwright MCP 的返回值中移除浏览器操作不需要的部分。
- 对 TOOL 部分使用 prompt caching。

不过，由于它依赖一套专有实现，团队面临难以迁移到 Strands Agents 等挑战。他们也在考虑进一步减少 token 的方法。正是在这样的背景下，GenAIIC 开始与 WHI 合作。

### 解决方案概览

我们用 Strands Agents 构建了该 agent。在测试多种浏览器操作工具并确认处理成功之后，我们把重点放在减少所用 token 数量上。工作流首先根据用户指令，从知识库中检索最优的操作模板。接着，它用从另一个知识库取得的信息替换所获模板中的占位符，生成一份操作手册。然后 agent 依据这份手册操作浏览器，检查当前信息。基于所获得的信息（例如 CSV），它生成一份变更提案并呈现给用户。最后，在用户批准之后，它再次依据变更提案操作浏览器以执行变更。尽管定义了一套基础工作流，agent 仍可以基于自身的自主判断，灵活处理用户输入不足、或只执行部分任务的情形。

### 架构

从 agent 访问「COMPANY」受到 IP 地址限制。为应对这一点，我们把 AgentCore Runtime 放在虚拟私有云（VPC）内，并配置它通过 NAT 网关以固定 IP 地址访问。我们还构建了一个知识库，用来存放操作模板与创建操作步骤所需的辅助信息。我们使用一个 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/) 存储桶来保存短期信息。

### 结果与影响

浏览器操作 agent 是用 Strands Agents 构建的。我们测试了 browser-use、Playwright 与 fast playwright 等浏览器操作工具，确认 fast playwright 消耗的 token 最少。此外，通过在使用 Amazon Bedrock prompt caching、修改 system prompt 等方面协作改进，我们成功把每次处理的成本降低最多 97%。主要的改进措施如下：

- 对用户消息使用 prompt caching：启用 Amazon Bedrock 的 prompt caching 功能（$14.5 -> $2.1）。
- 优化 agent 行为：改进子 agent 的 prompt 以减少不必要的操作（$2.1 -> $1.0）。
- 更换模型：把模型从 Claude Sonnet 4.5 换成 Haiku 4.5（$1.0 -> $0.4）。

通过这些改进，我们在优化成本的同时成功处理了更复杂的任务。这些任务包括连续执行多项变更的场景，以及指令含糊时 agent 向人提问的场景。

## 结语

通过这次合作，我们成功地把 AI agent 的执行基础设施迁移到 AgentCore Runtime，现在可以用 AgentCore Observability 查看运行状态。WHI 成员表示，使用 AgentCore 显著简化了开发，因为日志检查现在通过托管服务完成。此外，为浏览器 agent 采用 Strands Agents，让我们以最少的实现工作量获得了行为灵活的 agent。在本文中，我们描述了构建 AI agent 如何为日常任务提供支持。我们的合作让 WHI 达到了可以专注于开发业务逻辑的状态。AgentCore 包含作为执行基础的 Runtime 以及其他功能，因此我们正在考虑与 WHI 一起在未来加以利用。此外，AI agent 的行为与成本会随所用模型而变化。通过这个项目，我们确认各项流程按预期运行。我们计划继续评估模型并优化成本。

想体验 Amazon Bedrock AgentCore 如何简化 AI agent 开发，请访问我们的[入门指南](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-get-started-toolkit.html) 或[动手实验](https://github.com/aws-samples/sample-getting-started-with-amazon-agentcore)。无论你是想自动化日常任务、构建多 agent 工作流，还是想用 prompt caching 这类功能优化模型成本，AWS 都有工具支持你。
