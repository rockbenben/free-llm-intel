# Indegene 如何实现生命科学领域企业数据质量的现代化与规模化

*本文由 Indegene Limited 的 Shravan K S 联合撰写。*

企业级 AI 正在为生命科学组织创造新的机会，让它们改进商业、医学、市场准入及其他业务职能中的决策。但每一个 AI 模型、仪表板和业务洞察的质量都取决于一件事：可信的数据。随着企业数据在多个平台、管道和业务域中不断增长，维持一致的数据质量变得越来越困难。手工创建数据质量规则、治理碎片化、业务定义不断变化，这些都让数据质量难以在企业范围内实现规模化。

本文探讨 Indegene 如何在其基于 AWS 的 NEXT Unified Data Platform（NEXT UDP）中，构建一个生产级、由大语言模型（LLM）驱动的 Data Quality Agent。该 agent 生成感知上下文的数据质量规则并对它们进行校验，同时在集中式、人在回路（human-in-the-loop）的治理下产出可直接运行的 SQL 和 Python 代码。这些能力共同帮助组织在企业规模上提升数据质量，同时减少构建和维护数据质量计划所需的工作量。

## 关于 Indegene

[Indegene Limited](http://www.indegene.com/)（BSE: 544172，NSE: INDGN）是生命科学行业的战略运营伙伴，在产品全生命周期中统筹商业、医学、研发与安全运营。全球前 20 大生物制药公司都信赖 Indegene，由它帮助自己在全球规模上运行复杂、高度受监管的工作流。Indegene 把深厚的生命科学专业知识与内嵌 AI 的平台、受治理的运营模式结合起来，提升关键任务运营的速度、一致性和合规性。通过把技术融入工作的执行与扩展方式，Indegene 帮助生命科学组织在受监管的环境中交付可衡量的成果。

## 为什么传统的数据质量计划会难以为继

大多数组织都已经建立了数据质量流程，但随着企业数据生态不断演进，要让这些流程持续有效正变得越来越困难。

最大的挑战之一，是技术规则与业务规则在归属上的割裂。数据工程师通常定义的是确认数据在结构上是否正确的技术规则。例如，核实 HCP ID（Healthcare Professional ID）不为空、符合要求的格式、唯一，并且能映射到有效的参考记录。业务团队定义的是判断数据在其业务上下文中是否合理的规则。例如，确认某个区域内的产品市场份额合计为 100%，或者某位 HCP 的处方活动与其专业领域和资格标准相符。由于技术规则往往以代码维护，而业务规则存在于术语表、SOP 和主题专家的经验和专业知识之中，要让二者在不同数据集和平台之间保持一致并被统一治理就变得很困难。

传统的校验技术也有其固有局限。空值、数据类型、唯一性或参照完整性检查依然必不可少，但它们无法捕捉业务特有的上下文。校验产品层级、客户细分、区域划分或商业化业务规则，需要静态校验逻辑难以表达的领域知识。

创建和维护数据质量规则同样费力。每一个新数据集都需要数据剖析、规则定义、SQL 开发、校验以及持续维护。这些规则往往散落在 SQL 脚本、管道代码、电子表格、数据目录和特定工具的配置里。随着 schema、业务定义或校验阈值发生变化，更新和治理这些规则所需的工作量会显著增长。

此外，其对运营的影响也很明显。新数据集的接入会变慢，因为许多活动都要重复地手工完成。在数百个数据集上维护质量规则会消耗宝贵的工程精力。当校验规则难以理解、难以追溯、难以与业务上下文关联时，业务用户就会失去信心。

结果就是，数据质量往往变成一项周期性的治理活动，而不是一种持续的、可规模化的能力。

## 用生成式 AI 重新思考数据质量

传统的数据质量工具往往以独立能力的方式运行，与更广泛的企业数据生态相脱节。随着组织把 AI 和分析规模化，数据质量需要内嵌到数据平台本身，让治理、元数据、血缘和分析协同工作。

Indegene 通过 *NEXT Unified Data Platform（NEXT UDP）* 来应对这一问题，这是一套专为生命科学打造的现代、AI 驱动的数据平台。NEXT UDP 把分散的商业、医学、临床和企业数据汇聚到单一、受治理的环境中，让组织能够管理从摄取到分析的完整数据生命周期。NEXT UDP 提供了多个可独立使用的 AI agent，例如 Data Ingestion agent、Data Quality agent、Orchestration agent、Data Catalog agent 和 SQL Bot Generator agent。你可以在自己的数据管道中单独使用它们，也可以进一步定制以支持 agent 之间的通信。

通过在统一平台内整合数据摄取、转换、数据质量、治理、元数据管理和分析，NEXT UDP 帮助组织：

- 把分散的企业数据整合成可信的唯一事实来源。
- 在各业务域之间标准化数据质量与治理。
- 提升元数据可见性、血缘和可追溯性。
- 减少数据工程工作流中的人工投入。
- 为企业分析和决策交付可信的、AI-ready 的数据。

### Data Quality Agent 的独特之处是什么？支撑感知上下文的数据质量的两个知识库

任何数据质量工具都能检查空值、重复值或无效的数据类型。AWS Glue Data Quality（AWS Glue 的一项能力）这类服务已经能基于数据统计推荐这些规则，它们依然是坚实的基础。更难的问题是判断数据是否契合它的业务用途。为此，Data Quality Agent 使用两个互补的知识库，把经过梳理的领域知识与在受治理的使用过程中积累的经验结合起来。

第一个是**内部企业知识库（Internal Enterprise knowledge base）：** 它整合了内部业务术语表、数据字典、SOP、监管指南、已批准的数据质量规则、经过验证的脚本、剖析结果、历史异常以及主题专家（SME）反馈。内容经过摄取、向量化，并通过检索增强生成（RAG）进行检索，从而生成以企业标准和已被验证的结果为依据的数据质量规则。

第二个是**外部参考知识库（External Reference knowledge base）：** 它使用已批准的标准化数据质量框架、网络搜索和受控的网页抓取来构建并周期性更新。当选中一个数据集时，agent 会分析表和列的元数据，并从可信来源检索相关的数据质量标准、参考值和校验最佳实践。例如，对于一个 NPI（National Provider Identifier）列，它可以识别适用的质量标准、推荐格式（要求的 10 位数字格式）并执行参照校验。

### 工作机制

![Data Quality Agent 的流程：选择数据源、剖析数据、检测异常、生成并评审规则、集中管理规则。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/27/ML-21740-3.png)

图 3：Data Quality Agent 流程

Data Quality Agent 用单一工作流把用户从数据剖析带到规则创建与治理：

- **选择数据源：** 连接到一个受支持的源，例如 Amazon Redshift 或 Snowflake。
- **选择数据库和 schema：** 浏览可用的表，并显示每个表的规则数量和启用状态。
- **剖析数据：** 方案计算该表的质量指标和列模式，供用户查看。
- **检测异常：** 方案对照历史基线标记异常，用户查看问题总数、严重问题、告警问题以及受影响的记录。
- **管理规则：** 查看某个表的现有规则，或开始创建新规则。
- **选择规则模式：** 选择 Column Level、Table Level 或 Custom Query。
- **生成规则建议：** agent 利用元数据、剖析结果、异常、已有规则和知识库上下文，推荐技术规则和业务规则，每条都带有严重级别。
- **评审、完善并应用：** 用户对每一条建议进行编辑或批准。
- **生成并校验代码：** agent 为已批准的规则生成 SQL 和 Python，并由一个校验环节检查这些代码。
- **存入中央规则库：** 已批准的规则即可用于执行、监控和审计。

### Data Quality Agent 如何构建上下文

在推荐任何校验规则之前，Data Quality Agent 会从六个不同的来源汇集上下文，每个来源回答关于数据的一个不同问题：

| **上下文来源** | **它提供什么** | **它回答的问题** |
| --- | --- | --- |
| **表/列元数据（目录）** | 来自 Data Catalog 的 schema、数据类型 | *这是什么数据？* |
| **数据剖析** | 基于真实数据计算出的列级统计，例如空值率、去重计数、取值范围、高频值和检测到的模式 | *这些数据现在看起来是什么样？* |
| **异常检测结果** | 通过把最新剖析与历史基线比较而标记出的意外变化，例如空值突增、去重值变化或超出范围的值 | *什么变了，或者什么看起来不对？* |
| **现有的启用中的数据质量规则** | 已经应用在表级或列级的规则，从规则库中检索得到 | *已经有哪些规则，以免重复或冲突？* |
| **外部参考知识库** | 通用的、公开确立的数据质量标准与校验最佳实践（例如标识符类字段（如 National Provider Identifier）的格式与结构规则） | *这个字段的行业标准是什么？* |
| **内部企业知识库** | 组织特有的数据质量规则模式、既往评审者反馈，以及经过梳理的业务/技术规则库 | *这个组织如何定义质量？* |

这些来源共同让 agent 能够像一位经验丰富的数据管家那样推理。把每一条建议都建立在数据*是什么*、*标准*要求什么、*企业*如何定义质量，以及*已经*实现了什么之上。

### 这套方案能做什么

Data Quality Agent 会生成多种类别的检查，并让数据管家始终掌握结果的控制权。

#### 异常检查生成

该方案生成的异常检查可以捕捉那些技术上有效、却与药品市场实际运行规律不符的取值。其中包括：切换百分比为负、某个市场内的市场份额加起来不等于 100%、药品排名前后不一致（例如排名第一的药品份额低于排名第二的药品）、评分超出定义的量表范围，以及 panel 规模过小或与受访者数量不匹配。

#### 基于 RAG 的感知上下文规则生成

Data Quality Agent 以三种模式生成规则建议：

| **规则类型** | **说明** |
| --- | --- |
| Column Level | 针对用户选定的某一个具体列生成数据质量规则。agent 读取该列的元数据与剖析信号，建议数据类型校验、空值与必填字段检查、长度与范围校验、模式/格式校验以及唯一性等检查。 |
| Table Level | 由表的元数据及其各列之间的关系驱动，针对整张表生成数据质量规则。这涵盖记录一致性、重复检测、跨列校验、参照完整性检查以及表级的业务一致性。 |
| Custom Query | 从自然语言输入生成基于 SQL 的规则。用户用平实的英语描述业务校验，agent 生成对应的 SQL，之后可以通过对话继续完善，也可以直接编辑，以支持超出标准列级与表级检查范围的复杂校验。 |

Create New Quality Rule 界面分别提供 Column Level、Table Level 和 Custom Query 模式。

**平台同时支持技术校验与业务特有的质量检查。**

对于技术规则，agent 生成的是确认数据在结构上是否完好的检查。这些包括必填字段的空值检查、数据类型校验、数值与日期值的范围校验、标识符与编码这类有格式要求的字段的模式校验、重复检测，以及相互关联的表之间的参照完整性检查。

对于业务规则，agent 生成的是确认数据与业务实际运行方式是否一致的生命科学检查。这些包括客户归属一致性（例如某位医疗服务提供者关联到正确的机构）、细分逻辑、资格标准，以及市场份额与产品份额校验（例如某个区域内的份额之和不超过 100%）。

#### 真实用例示例

设想一张 HCP Product Performance 表，列包括 HCP_ID、Specialty、Territory_ID、Product_ID、Prescription_Volume、Market_Share_Pct、Switch_Pct、Rating_Scale 和 Reporting_Month。借助这张表的剖析结果和两个知识库，Data Quality Agent 按以下方式生成并执行这些检查：

- 执行的异常检查。 切换百分比为负。市场份额总和不匹配。处方量突然增加或减少。产品排名不一致。Rating_Scale 取值无效。
- 生成的技术规则。  HCP_ID 不得为空或重复。Prescription_Volume 必须是数值且非负。Market_Share_Pct 与 Switch_Pct 必须介于 0 到 100 之间。Reporting_Month 必须遵循要求的日期格式。Territory_ID 与 Product_ID 必须与各自的参照表匹配。
- 生成的业务规则。  在每个区域和报告月份，所有产品的市场份额合计必须为 100%。该 HCP 的产品资格必须与其专业领域一致。只有具备资格的 HCP 才能被纳入目标细分。

#### AI 辅助的严重级别推荐

该方案依据数据集上下文、规则类型和业务影响来推荐严重级别。严重级别类别有助于区分：

- **Critical** 严重问题，例如无效的商业指标、错误的标识符或违反业务规则。
- **Basic** 基础校验，包括 schema 一致性、空值检查和长度校验。
- **Complex** 复杂校验，涉及高级 SQL 逻辑、多列规则或领域特有的业务检查。
- **Information：** 仅出于知会和提高透明度的目的开展的校验。除非发现了问题，否则无需采取行动。

#### SQL/Python 代码生成与 ETL 集成

一条规则获得批准后，LLM 会生成对应的 SQL、Python 和 PySpark 代码。在存储之前，代码会自动接受校验：语法检查、对照目标 schema 的检查，以及在语言支持的条件下对样本数据做一次试跑。这意味着现有的抽取、转换、加载（ETL）与编排工具可以把它们作为当前数据管道的一部分来运行。

#### AI 辅助校验

让一个 LLM 充当 Validation Agent，审查由另一个 LLM 生成的数据质量（DQ）规则和脚本，以减少幻觉并改进治理。此外，[Amazon Bedrock](https://aws.amazon.com/bedrock/?trk=5eabf6f5-7510-4f30-9f4b-03d1339cf4e0&sc_channel=ps&ef_id=CjwKCAjwifjVBhBKEiwAYx4K9IwCllm8tAeZE6tmURFkkPl0v7qQkb5fo7N6kr8cN4ClhFAnKcN5GRoCp6UQAvD_BwE:G:s&gads_camp=23846236448&gads_ag=198027706682&gads_ad=808712739102&gads_kw=amazon%20bedrock&gads_matchtype=e&gads_network=g&gads_device=c&gads_geo=9198856&gad_campaignid=23846236448&gbraid=0AAAAADjHtp-2Ie_MZjxtqPc0n3h-vBZK3&gclid=CjwKCAjwifjVBhBKEiwAYx4K9IwCllm8tAeZE6tmURFkkPl0v7qQkb5fo7N6kr8cN4ClhFAnKcN5GRoCp6UQAvD_BwE) 提供[安全、隐私与负责任 AI 控制](https://aws.amazon.com/bedrock/security-privacy-responsible-ai/)。提示词和输出不会被用于训练模型，也不会与模型提供方共享。Amazon Bedrock 符合 HIPAA 适用条件，并纳入 SOC、ISO 和 GDPR 等合规计划的范围，这帮助 Indegene 满足其生命科学客户的要求。[Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 为模型输入和输出增加了可配置的保护措施。它能检测并遮蔽个人身份信息（PII），拦截有害内容和提示注入攻击，并使用上下文依据检查来标记那些检索到的知识无法支撑的回答。

#### 人工监督仍是核心

Data Quality Agent 的设计目标是增强既有的数据质量流程。每条生成的规则都会获得一个置信度分数。只有高置信度、低风险的规则会被自动批准，而严重规则和业务规则一律交由 SME 评审。每一次决策都记录在规则库中，因此规则管理始终处于治理之下、可追溯，并与企业标准保持一致。

## 交付运营影响与业务价值

在生产环境中，在 Indegene 面向生命科学客户部署的 NEXT UDP 上，Data Quality Agent 已把定义并实现数据质量规则的工作量从每个数据集约 30 小时降到约 4 小时，相当于工作量减少约 85%，生产力提升约 7 倍。接入一张新表现在只需 2–4 小时，而不是过去的 2–5 个工作日。数据工程师和数据管家的时间如今用在评审和批准规则上，而不是从零编写规则。

关键成果包括：

- 借助 AI 生成的规则、SQL 和 Python，减少人工投入。

- 规则更一致，因为它们以已批准的标准、企业知识和现有规则为依据。
- 通过评审、完善并批准的工作流，改善业务团队与技术团队之间的协作。
- 通过自动化剖析和异常检测，更早地发现数据质量问题。

## 展望

随着企业数据生态持续增长，依靠人工创建规则和碎片化的治理流程，会越来越难维持一致且可规模化的数据质量。生成式 AI 提供了一个机会：通过加速规则生成、纳入业务上下文、支持受治理的决策来增强这些工作流。

NEXT Unified Data Platform 中由生成式 AI 驱动的 Data Quality Agent 表明，大语言模型、RAG 和集中式规则治理可以协同工作，在简化数据质量的管理的同时，把评审与批准的决定权留在人手中。后续的增强将继续建立在这一基础之上，包括：

- AI 辅助的修复建议，帮助用户解决未通过的数据质量检查。
- 根因分析，用于识别反复出现的异常模式，支持更快地调查重复发生的数据质量问题。

随着这些能力不断演进，关注点始终不变：通过 AI 辅助的自动化帮助组织改进数据质量，同时保持治理、透明度和业务监督。
