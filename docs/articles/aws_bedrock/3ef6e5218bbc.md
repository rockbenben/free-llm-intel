# Indegene 如何实现生命科学领域企业数据质量的现代化和扩展

*这篇文章是与 Indegene Limited 的 Shravan K S 共同撰写的。*

企业人工智能正在为生命科学组织创造新的机会，以改善商业、医疗、市场准入和其他业务职能的决策。但每个人工智能模型、仪表板和业务洞察力的质量都取决于一件事：可信数据。随着企业数据跨多个平台、管道和业务领域增长，保持一致的数据质量变得越来越困难。手动数据质量规则创建、分散的治理和不断变化的业务定义使得在整个企业范围内扩展数据质量变得具有挑战性。

本文探讨了 Indegene 如何在 AWS 上的 NEXT 统一数据平台 (NEXT UDP) 中构建生产级、大型语言模型 (LLM) 驱动的数据质量代理。该代理生成上下文感知的数据质量规则，对其进行验证，并在集中式人机循环治理下生成可立即运行的 SQL 和 Python 代码。这些功能共同帮助组织提高企业规模的数据质量，同时减少构建和维护数据质量计划所需的工作量。

## 关于 Indegene

[Indegene Limited](http://www.indegene.com/)（BSE：544172，NSE：INDGN）是生命科学行业的战略运营合作伙伴，负责协调整个产品生命周期的商业、医疗、研发和安全运营。 Indegene 受到全球 20 强生物制药公司的信赖，帮助在全球范围内运行复杂、高度监管的工作流程。 Indegene 将深厚的生命科学专业知识与人工智能嵌入式平台和受监管的运营模型相结合，以提高关键任务运营的速度、一致性和合规性。通过将技术集成到工作的执行和扩展方式中，Indegene 帮助生命科学组织在监管环境中交付可衡量的成果。

## 为什么传统的数据质量程序会失败

大多数组织都建立了数据质量流程，但随着企业数据生态系统的发展，保持其有效变得越来越困难。

最大的挑战之一是技术和业务规则所有权之间的分歧。数据工程师通常定义技术规则来确认数据结构是否正确。例如，验证 HCP ID（医疗保健专业人员 ID）不为空、遵循所需的格式、唯一并且映射到有效的参考记录。业务团队定义规则来确定数据在其操作上下文中是否有意义。例如，确认某个地区内的产品市场份额总计为 100%，或者 HCP 的处方活动符合其专业和资格标准。由于技术规则通常在代码中维护，而业务规则则驻留在术语表、SOP 和主题专业知识中，因此在数据集和平台之间保持它们的一致性和一致管理变得很困难。

传统的验证技术也有固有的局限性。检查空值、数据类型、唯一性或引用完整性仍然至关重要，但它们无法捕获特定于业务的上下文。验证产品层次结构、客户细分、区域一致性或商业业务规则需要静态验证逻辑无法轻松表示的领域知识。

创建和维护数据质量规则同样要求严格。每个新数据集都需要数据分析、规则定义、SQL 开发、验​​证和持续维护。这些规则通常分布在 SQL 脚本、管道代码、电子表格、数据目录和特定于工具的配置中。随着模式、业务定义或验证阈值的变化，更新和管理这些规则所需的工作量显着增加。

此外，运营影响也很大。由于许多活动都是手动重复的，因此加入新数据集会变得更慢。维护数百个数据集的质量规则需要耗费宝贵的工程精力。当验证规则难以理解、跟踪或与业务上下文相关时，业务用户就会失去信心。

因此，数据质量通常成为一项定期的治理活动，而不是一种持续的、可扩展的能力。

## 使用生成式人工智能重新思考数据质量

传统的数据质量工具通常作为独立功能运行，与更广泛的企业数据生态系统脱节。随着组织扩展人工智能和分析，数据质量需要嵌入数据平台本身，其中治理、元数据、沿袭和分析协同工作。

Indegene 通过 *NEXT 统一数据平台 (NEXT UDP)* 解决了这个问题，这是一个专为生命科学构建的现代人工智能驱动数据平台。 NEXT UDP 将分散的商业、医疗、临床和企业数据汇集到一个单一的受管环境中，以便组织可以管理从摄取到分析的完整数据生命周期。 NEXT UDP 提供多个独立的 AI 代理，例如数据摄取代理、数据质量代理、编排代理、数据目录代理和 SQL Bot 生成器代理。您可以在数据管道中独立使用它们，也可以进一步自定义它们以进行代理间通信。

通过将数据摄取、转换、数据质量、治理、元数据管理和分析集成到一个统一的平台中，NEXT UDP 可以帮助组织：

- 将分散的企业数据整合为可信的事实来源。
- 跨业务领域标准化数据质量和治理。
- 提高元数据可见性、沿袭性和可追溯性。
- 减少数据工程工作流程中的手动工作。
- 为企业分析和决策提供可信的、人工智能就绪的数据。

### 数据质量代理有何独特之处？支持上下文感知数据质量的两个知识库

任何数据质量工具都可以检查空值、重复项或无效数据类型。 AWS Glue 数据质量（AWS Glue 的一项功能）等服务已经从数据统计中推荐了此类规则，并且它们仍然是坚实的基础。更困难的问题是确定数据对其业务目的是否有意义。为了解决这个问题，数据质量代理使用两个互补的知识库，将精选的领域知识与从受控使用中获得的经验相结合。

第一个是**内部企业知识库：**它结合了内部业务术语表、数据字典、SOP、监管指南、批准的数据质量规则、经过验证的脚本、分析结果、历史异常和主题专家 (SME) 反馈。通过检索增强生成 (RAG) 摄取、矢量化和检索内容，以生成基于企业标准和经过验证的结果的数据质量规则。

第二个是**外部参考知识库：**它是使用经过批准的标准化数据质量框架、网络搜索和受控网络抓取来构建和定期更新的。选择数据集后，代理会分析表和列元数据，并从可信来源检索相关数据质量标准、参考值和验证最佳实践。例如，对于 NPI（国家提供商标识符）列，它可以识别适用的质量标准、推荐格式（所需的 10 位数字格式）并执行参考验证检查。

数据质量代理让用户在一个工作流程中完成从数据分析到规则创建和治理的整个过程：

- **选择源：** 连接到受支持的源，例如 Amazon Redshift 或 Snowflake。
- **选择数据库和架构：** 浏览可用表，其中包含每个表的规则计数和活动规则状态。
- **配置文件数据：** 该解决方案计算用户查看的表的质量指标和列模式。
- **检测异常：** 该解决方案根据历史基线标记异常，用户可以查看总数、严重和警告问题以及受影响的记录。
- **管理规则：** 查看表的现有规则或开始创建新规则。
- **选择规则模式：** 选择列级别、表级别或自定义查询。
- **生成规则建议：** 代理使用元数据、分析结果、异常、现有规则和知识库上下文来推荐技术和业务规则，每个规则都有一个严重性。
- **审查、完善和应用：** 用户编辑或批准每项建议。
- **生成和验证代码：** 代理为批准的规则生成 SQL 和 Python，并由验证步骤检查它们。
- **存储在中央规则存储库中：** 批准的规则可用于执行、监控和审核。

### 数据质量代理如何构建上下文

在推荐任何验证规则之前，数据质量代理会从六个不同的来源收集上下文，每个来源回答有关数据的不同问题：

| **上下文来源** | **它提供什么** | **提问即回答** |
| ---| ---| ---|
| **表/列元数据（目录）** |数据目录中的架构、数据类型 | *这个数据是什么？* |
| **数据简介** |根据实际数据计算的列级统计信息，例如空率、不同计数、值范围、频繁值和检测到的模式 | *现在的数据是什么样的？* |
| **异常检测结果** |通过将最新配置文件与历史基线进行比较来标记意外变化，例如空值突然增加、不同值的变化或超出范围的值 | *什么发生了变化或看起来有问题？* |
| **现有的活动数据质量规则** |已在表或列级别应用规则，从规则存储库检索 | *哪些规则已经存在，所以我们不会重复或冲突？* |
| **外部参考知识库** |通用、公开制定的数据质量标准和验证最佳实践（例如国家提供商标识符等标识符的格式和结构规则）| *该领域的行业标准是什么？* |
| **内部企业知识库** |特定于组织的数据质量规则模式、事先审阅者反馈以及精选的业务/技术规则库 | *该组织如何定义质量？* |

这些来源共同让代理能够像经验丰富的数据管理员一样进行推理。每项建议都以数据*是什么*、*标准*要求什么、*企业*如何定义质量以及*已经*实施的内容为基础。

### 解决方案的作用

数据质量代理生成多种类型的检查，并让数据管理员控制结果。

#### 异常检查生成

该解决方案生成异常检查，捕获技术上有效但与制药市场行为不匹配的值。其中包括负转换百分比、市场内的市场份额加起来不等于 100%、药品排名不一致（例如，排名第一的药物的份额低于排名第二的药物）、超出定义范围的评级值以及小组规模太小或与受访者数量不匹配。

#### 使用 RAG 生成上下文感知规则

数据质量代理以三种模式生成规则建议：

| **规则类型** | **描述** |
| ---| ---|
|列级|为用户选择的特定单独列生成数据质量规则。代理读取该列的元数据和分析信号，以建议检查，例如数据类型验证、空字段和强制字段检查、长度和范围验证、模式/格式验证和唯一性。 |
|表级 |由表的元数据及其列之间的关系驱动，为整个表生成数据质量规则。这包括记录一致性、重复检测、跨列验证、引用完整性检查和表范围的业务一致性。 |
|自定义查询 |从自然语言输入生成基于 SQL 的规则。用户用简单的英语描述业务验证，代理生成相​​应的 SQL，然后可以通过对话方式对其进行细化或直接编辑，以支持标准列和表检查之外的复杂验证。 |

创建新质量规则界面提供专用的列级、表级和自定义查询模式。

**该平台支持技术验证和特定于业务的质量检查。**

对于技术规则，代理会生成检查以确认数据结构合理。其中包括强制字段的空检查、数据类型验证、数字和日期值的范围验证、格式化字段（例如标识符和代码）的模式验证、重复检测以及相关表之间的引用完整性检查。

对于业务规则，代理生成生命科学检查，以确认数据与业务运营方式一致。其中包括帐户从属关系一致性（例如，医疗保健提供者与正确的组织相关联）、细分逻辑、资格标准以及市场份额和产品份额验证（例如，某个地区内的份额不超过 100%）。

#### 真实用例示例

考虑一个 HCP 产品绩效表，其中包含 HCP_ID、Specialty、Territory_ID、Product_ID、Prescription_Volume、Market_Share_Pct、Switch_Pct、Rating_Scale 和 Reporting_Month 列。使用表配置文件和两个知识库，数据质量代理如何生成并执行以下检查：

- 执行异常检查。  负切换百分比。市场份额完全不匹配。处方量突然增加或减少。产品排名不一致。无效的评级量表值。
- 生成的技术规则。  HCP_ID 不得为空或重复。 Prescription_Volume 必须是数字且非负数。 Market_Share_Pct 和 Switch_Pct 必须介于 0 和 100 之间。Reporting_Month 必须遵循所需的日期格式。 Territory_ID 和 Product_ID 必须与其参考表匹配。
- 生成业务规则。  每个地区和报告月份的所有产品的市场份额总计必须为 100%。 HCP 的产品资格必须与其专业相一致。只有符合条件的 HCP 才能包含在目标细分中。

#### AI辅助严重性建议

该解决方案根据数据集上下文、规则类型和业务影响来建议严重性。严重性类别有助于区分：

- **关键**问题，例如无效的商业指标、不正确的标识符或违反业务规则。
- **基本**验证，包括模式一致性、空检查和长度验证。
- **复杂**验证涉及高级 SQL 逻辑、多列规则或特定于域的业务检查。
- **信息：** 验证仅出于提高认识和透明度的目的。除非发现问题，否则无需采取任何行动。

#### SQL/Python 代码生成和 ETL 集成

规则获得批准后，LLM 会生成等效的 SQL、Python 和 PySpark 代码。在存储之前，代码会通过语法检查、目标架构检查以及语言支持的示例数据上的测试运行来自动进行验证。这意味着现有的提取、转换和加载 (ETL) 以及编排工具可以将它们作为当前数据管道的一部分来运行。

#### AI辅助验证

#### 人类监督仍然是核心

数据质量代理旨在增强现有的数据质量流程。每个生成的规则都会收到一个置信度分数。只有高置信度、低风险的规则才会自动批准，而关键规则和业务规则始终交由 SME 审查。每个决策都记录在规则存储库中，因此规则管理保持受管控、可跟踪并与企业标准保持一致。

## 展望未来

随着企业数据生态系统的不断发展，使用手动规则创建和分散的治理流程来保持一致和可扩展的数据质量变得越来越困难。生成式人工智能通过加速规则生成、整合业务上下文和支持受治理的决策，提供了增强这些工作流程的机会。

NEXT 统一数据平台中由人工智能驱动的生成式数据质量代理展示了大型语言模型、RAG 和集中式规则治理如何协同工作，以简化数据质量管理，同时让人类控制审查和批准。未来的增强功能将继续在此基础上进行，包括：

- AI辅助修复建议，帮助用户解决失败的数据质量检查。
- 根本原因分析可识别重复出现的异常模式并支持更快地调查重复的数据质量问题。

随着这些功能的发展，重点仍然是相同的：通过人工智能辅助自动化帮助组织提高数据质量，同时保持治理、透明度和业务监督。
