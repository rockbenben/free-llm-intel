# Amazon Nova Forge 上超参数优化的艺术与科学

大语言模型（LLM）在通用任务上表现强劲，但在需要理解专有数据、内部流程或领域专用术语的专门工作中往往力不从心。[Amazon Nova Forge](https://aws.amazon.com/nova/forge/) 通过让你用 [Amazon Nova](https://aws.amazon.com/nova/) 构建自己的前沿模型来应对这一问题。你可以从早期模型检查点开始开发，把专有数据与 Amazon Nova 精选训练数据混合，并把自定义模型安全地托管在 AWS 上。一项关键能力是数据混合（data mixing），它把你的训练数据与精选数据集混合在一起。这有助于模型吸收你的领域知识，同时保留广泛的推理、指令遵循与语言能力。这可以防止通常会削弱领域定制的灾难性遗忘（catastrophic forgetting）。

成功的定制需要细致的超参数调优。学习率、数据混合比例、检查点选择以及训练技巧，彼此之间的相互作用可能悄无声息地毁掉一次训练运行。只要其中任何一项出错，你就是在拿一个问题换另一个问题。本文涵盖 Amazon Nova Forge 上超参数调优的艺术（战略权衡）与科学（指标驱动的决策），帮助你避免代价高昂的失败训练运行。

针对领域特定任务做微调，意味着提升某一领域的效果而不削弱模型的通用能力，而把这种平衡拿捏好，比看起来要难。本文带你走完如何把握这种平衡：从为你的数据和任务选择合适的定制策略，到配置对结果影响最大的训练参数，例如学习率、批大小与检查点。我们还会介绍那些导致训练白跑的常见错误，以及如何及早发现它们，让你在提升领域表现的同时，既不损害通用能力，也不把算力浪费在可以避免的失败上。

读完本文，你将知道如何在提升领域表现的同时不损害通用能力，以及如何避免因平衡没拿捏好而产生的昂贵失败。

## 超参数调优的挑战

要达成这种平衡，比看上去更难。有三个根本性挑战，使得在领域专用模型上做超参数调优格外困难。

### 挑战 1：灾难性遗忘

当你在狭窄的领域数据上训练模型时，模型可能覆盖掉它在预训练阶段学到的通用能力。这一现象称为*灾难性遗忘*，表现为在你训练领域之外的任务上表现下降。模型变得高度专门化，却丧失了指令遵循能力、推理能力与广博知识。在生产环境中，这意味着一个用你的支持工单微调过的客服模型，可能不再能对含义含糊的请求进行推理，也无法维持连贯的多轮对话。

这形成了稳定性与灵活性之间的权衡。理想情况下，模型要足够灵活以学习某个组织的领域知识，又要足够稳定以保留通用能力。Nova Forge 通过数据混合与检查点选择来应对：数据混合在训练期间把你的训练数据与精选数据集混合；检查点选择则让你决定保留多少既有的对齐。

### 挑战 2：找到合适的学习率

学习率控制模型的权重在响应每一批训练样本时改变多少。它是所有定制技术中最敏感的超参数。学习率过高会使模型越过最优状态、在训练中失稳，或者快速遗忘基础能力。学习率过低则会把算力浪费在非常缓慢的收敛上。合适的取值取决于你的数据分布、混合比例与训练技术。

Nova Forge 为每种训练技术提供了经过校准的服务默认值，这些默认值已经考虑了上述相互作用。当你使用数据混合时，敏感性会进一步上升。在把 Nova 数据与你自己的数据混合时偏离默认学习率，是训练不稳定最常见的来源，因此这些服务默认值就是推荐的起点。

### 挑战 3：基线表现约束

强化微调（RFT）是一种通过生成多个候选响应并依据质量标准打分来改进模型行为的技术。模型通过比较自己的输出并强化更好的那些来学习。RFT 只在特定的基线任务准确率区间内才能发挥全部能力，该准确率衡量的是微调之前模型产出正确或高质量响应的频率。如果基线准确率过低（模型很少产出正确响应），就没有足够的好样本可供奖励引导的探索去学习。如果基线准确率已经很高，额外训练带来的收益递减，且有损害既有表现的风险。这意味着 RFT 无法弥合巨大的能力缺口，也就是模型从根本上缺乏尝试某项任务所需的知识或推理能力的情况。它是对模型已经能部分展现的行为加以精炼与强化，而不是从零开始教会全新的能力。

Nova Forge pipeline 同时处理这两个边界。对于低基线场景，先运行监督微调（SFT），建立有效奖励学习所需的基础能力。对于高基线任务，要确保你的奖励函数在模型的质量区间上具有区分力。如果大多数响应得分已经很高，RFT 就没有可供优化的有效信号。

## Nova Forge 定制 pipeline

理解了这些挑战，也就理解了 Amazon Nova Forge 定制 pipeline 的设计思路：它正是为应对这些挑战而构建的。Nova Forge 提供三种互补的定制技术，各自在模型开发生命周期中承担不同的用途。

| **技术** | **作用** | **适用场景** | **输入数据** |
| --- | --- | --- | --- |
| **持续预训练（CPT）** | 通过在大规模无标注的领域专有数据上做自监督学习，扩展基础模型（FM）的知识。CPT 从你的文本语料中教会模型领域术语与模式。 | 你需要模型理解基础模型中不存在的专门词汇、行业概念或组织知识。 | 大量无标注的领域文本。Nova Forge 支持带数据混合的 CPT，并提供三种检查点选项（预训练、中训练、后训练），各自适合不同的数据规模与下游需求。 |
| **监督微调（SFT）** | 使用针对目标任务的输入-输出对训练数据集来定制模型行为。SFT 通过示范教会模型“给定 X，输出 Y”的行为。 | 你需要模型遵循特定的响应格式、采用特定的语气，或执行分类、抽取等结构化任务。 | 每个任务 1,000–10,000 条高质量示范。质量、一致性与多样性比数量更重要。Nova Forge 支持使用 Amazon Nova 精选数据集做数据混合的 SFT，其中包括可保留通用能力的推理-指令遵循类别。 |
| **强化微调（RFT）** | 使用奖励信号把模型输出导向偏好的结果。RFT 在先前训练所建立的行为邻域内，针对单轮或多轮对话任务优化模型。 | 你有清晰的奖励函数可以评估响应质量，并希望把表现推到 SFT 单独所能达到的水平之上。 | prompt 与奖励函数。Nova Forge 支持通过 [AWS Lambda](https://docs.aws.amazon.com/lambda/latest/dg/welcome.html) 接入你自己的外部奖励环境，从而为领域特定的质量评估实现自定义校验逻辑。 |

当三个阶段一起使用（先 CPT，再 SFT，再 RFT）时，效果最强。不过，只要 pipeline 设计得当，每个阶段都可以是可选的。这取决于你的数据可得性、任务类型与起点。只有当基础模型缺乏任务所需的领域词汇或知识时才需要 CPT。SFT 与 RFT 可以独立使用，也可以按任务需求组合使用。

*图 1：Amazon Nova Forge 定制 pipeline。CPT 从无标注文本中传授领域知识，SFT 从示范中传授任务特定行为，RFT 使用奖励信号优化表现。每个阶段都是可选的，而当三者都适用于你的用例时，完整 pipeline（先 CPT，再 SFT，再 RFT）能取得最强的结果。*

[Amazon SageMaker AI](https://aws.amazon.com/sagemaker/) 提供不同的定制环境：SageMaker Serverless 提供由 UI 驱动、自动预置算力的体验；SageMaker AI 训练作业（SMTJ）提供免集群管理的全托管体验；而 [Amazon SageMaker HyperPod](https://aws.amazon.com/sagemaker/hyperpod/) 则为高级分布式训练场景提供专门的环境。

## 战略决策

看清定制 pipeline 之后，下一步是理解那些塑造你配置的定性权衡。这些战略决策与任何单个超参数取值同样重要：检查点选择、数据混合与训练模式。

### 检查点选择（影响最大的决策）

对 CPT 而言，检查点选择比任何超参数的影响都更大。Amazon Nova Forge 提供三种[检查点选项](https://docs.aws.amazon.com/nova/latest/nova2-userguide/nova-forge-cpt.html)，各自适合不同的数据规模与下游需求。

- 预训练检查点最灵活，收敛也最快。这类检查点容易接受新模式，最适合 token 预算超过 1,000 亿的大规模 CPT。在使用预训练检查点处理大数据集时，你可以用更高的学习率（例如 1e-4）来加速知识吸收。随后你需要在运行 SFT 之前把学习率逐步降回约 1e-6 以保证模型稳定，让模型对所学的沉淀下来而不会过冲。要注意，预训练检查点没有任何指令调优。完成 CPT 之后，你必须运行 SFT 才能让模型对下游任务有用。
- 中训练检查点平衡了灵活性与对齐。它们能接受领域知识，同时保留部分指令遵循行为。中训练检查点适用于中等规模的数据集：你希望领域适配比后训练更快，但又要比预训练更稳定。中训练检查点很适合全秩（Full Rank）训练，也就是在微调时更新模型中每一个参数，尤其是配合大型结构化数据集时。
- 后训练检查点最能抵抗新模式，但能保留指令遵循与通用能力。对于规模较小的 CPT，如果保留对齐比最大化领域知识吸收更重要，就使用后训练检查点。后训练检查点是 LoRA（低秩适配，Low-Rank Adaptation）以及其他参数高效微调方法推荐的起点，LoRA 会冻结原始模型权重，在其之上训练小型适配矩阵，因为这些方法在保持模型既有能力的同时允许有针对性的适配。对于小数据集或较晚阶段的检查点，请使用服务默认值中保守的学习率取值。

### 数据混合策略

不做数据混合时，在狭窄的领域数据上训练可能导致模型变得不稳定，产生反复无常的训练行为（梯度不稳定或 loss 尖峰）或者表现突然下滑。

配置数据混合时，[对大多数用例而言，把客户数据控制在总混合量的 50% 左右](https://aws.amazon.com/blogs/machine-learning/nova-forge-sdk-series-part-2-practical-guide-to-fine-tune-nova-models-using-data-mixing-capabilities/)。对于 SFT，务必在 Nova 数据混合中加入“推理-指令遵循”类别。仅这一个类别就能显著提升微调后的通用基准表现。跳过这个类别，是微调模型推理能力退化的常见原因。

数据混合对学习率非常敏感。使用数据混合时偏离默认学习率会导致不稳定。这是实践者最常犯的错误。如果你在使用数据混合时观察到训练不稳定，学习率就是第一个嫌疑对象。

找到最优混合比例需要实验。保持领域数据不变，在多次运行中改变 Nova 数据的比例。通常领域表现保持稳定，而混入的 Nova 数据越多，通用能力就持续改善。把质量最高的数据放在训练的后段，以获得更好的收敛。

### 训练模式：低秩适配（LoRA）与全秩（Full Rank）

Amazon Nova Forge 支持两种训练模式，它们决定训练期间模型参数如何被更新：

- LoRA 只更新适配层，因而算力成本更低、迭代更快，并兼容按需推理。对大多数任务，LoRA 能取得接近全秩的表现，同时对次优超参数更宽容。默认的 alpha 缩放因子 64 适用于大多数任务。如果 LoRA 对你的数据适配不足，就提高 alpha；如果 LoRA 过度适配并开始丢失通用能力，就降低 alpha。请把后训练检查点作为 LoRA 训练的起点。
- 全秩训练更新全部模型参数，提供最大的适配容量。全秩训练部署时需要 Amazon Bedrock Provisioned Throughput（按需模式仅支持基于 LoRA 的定制），训练期也需要更高的算力。当你已经验证过 pipeline，且部署架构足以证明额外成本合理时，再使用全秩训练。中训练检查点很适合配合大型结构化数据集做全秩训练。

先从 LoRA 开始，用来验证你的 pipeline、数据质量与奖励函数（对 RFT 而言）。当你确认这套方法可行，且生产需求足以证明其合理性时（例如模型表现或成本约束），再升级到全秩训练。

## 推荐工作流

把这些战略决策应用到你自己的具体情境，取决于你手上有什么数据与目标。下面这些路径把你的起点条件对应到正确的技术顺序。

如果你有带标签的示范以及可验证的奖励函数（先 SFT 再 RFT）：

- 先用 LoRA 做 SFT，教会目标行为并建立基线能力。
- 启用数据混合，并包含“推理-指令遵循”，以在领域适配过程中保留模型遵循结构化 prompt、产出格式良好输出的能力。
- 直接使用默认学习率，不做修改。
- 监控验证 loss 以选出最好的 SFT 检查点。
- 在该 SFT 检查点上升级到 RFT，通过奖励信号进一步优化。
- 只有在用 LoRA 验证过该方法之后，再考虑全秩训练。
- 在生产部署之前，对你的领域任务和通用基准都做充分测试（示例见“实验与洞见”一节）。

如果你能定义可验证的结果，但难以规模化地为响应打标签（只用 RFT）：

- 先在你的任务的有代表性样本上评估基础模型表现。
- 如果基础模型的正向奖励超过约 5%，直接开始 RFT。
- 如果奖励分数持续接近零，回退到 SFT。模型需要具备基线能力，奖励引导的学习才能生效。

如果基础模型缺乏你的任务所需的领域词汇或知识，就从 CPT 开始：

- 运行 CPT，从无标注文本中吸收领域知识。
- 随后做 SFT。用于 CPT 的预训练检查点没有指令调优，因此 CPT 之后必须做 SFT 才能让模型有用。
- 之后可以选择再做 RFT，进一步优化表现。

## 参数配置

战略决策定下来之后，你就可以优化那些决定每种技术如何执行的具体超参数了。本节为每种技术提供指导。

### 学习率配置

学习率控制模型依据训练信号更新得有多快。服务默认值代表经过测试、能在各种用例中奏效的配置。

- 对 CPT：从服务默认值开始。对于超过一万亿 token 的大数据集，你可以用更高的学习率（例如 1e-4）来加速知识吸收，但需要一个降档阶段，在 SFT 之前把学习率降回约 1e-6 以保证模型稳定。`constant_steps` 参数控制模型在这个降档阶段开始之前、以峰值学习率训练多少步。对于 token 量极大的运行，增加 `constant_steps` 会有帮助，因为在全学习率下跑更多步有利于领域吸收。对于较小的数据集或较晚阶段的检查点，从一开始就使用默认（较低）的学习率。
- 对 SFT：坚持使用服务默认值，尤其是在启用数据混合时。推荐学习率是 LoRA 用 1e-5、全秩 SFT 用 5e-6。混合 Nova 数据时偏离默认学习率会导致不稳定。如果你在使用数据混合时观察到训练不稳定，学习率就是第一个嫌疑对象。
- 对 RFT：从服务默认值开始。只在确有必要时以较小的乘数增量调整。如果奖励突然下降且无法恢复，学习率很可能过高。即使小幅提高乘数，也可能让表现掉到基线之下。

把 warmup 步数配置为总训练步数的约 15%。warmup 通过逐步提高学习率而不是一开始就用满值，使训练初期更稳定。

### 批大小与训练时长

批大小（由 `global_batch_size` 控制）是所有训练方法（CPT、SFT、RFT）与所有环境（SageMaker Serverless、SMTJ、HyperPod）通用的批参数。它定义每个优化器步处理多少训练样本。对 CPT 与 SFT 来说这很直接：一个样本等于一个输入-输出对（SFT）或一个 token 序列（CPT）。RFT 引入了一个额外参数 `number_generation`，控制每个 prompt 生成多少个候选响应用于奖励打分。这个参数在 CPT 或 SFT 的 recipe 中不存在，因为那些方法直接在给定的输入-输出对上训练，而不生成候选。当存在生成数量这个参数时，批大小的含义在不同环境之间会有所不同。搞错这一点会导致意料之外的行为。

- 在 SMTJ 上（仅 RFT）：批大小指每步的 prompt 数。每个 prompt 生成 N 个候选响应（由 `number_generation` 控制）。每步的样本总数等于批大小乘以生成数量。
- 在 SageMaker HyperPod 上（仅 RFT）：批大小指每步的样本总数（prompt 数乘以生成数）。在环境之间迁移配置时要仔细换算。

对 CPT，目标是每步 200 万至 2,000 万 token。token 预算大时用 2,000 万，预算小时用 200 万。把每步 token 数除以最大序列长度，取最接近的 2 的幂，即为全局批大小。例如，每步 400 万 token、序列长度 4096 时，批大小约为 1024。较小的批大小会产生更嘈杂的梯度，这有助于泛化并支持更快的迭代。较大的批大小产生更平滑的梯度，但可能过度平滑领域特定信号。为稳定起见，先从适中的批大小开始。

让最大序列长度匹配你的数据分布。不要超过数据实际所需。较小的上下文长度会提升 token 吞吐并降低训练成本。对 CPT，最多处理数据集的一个 epoch。避免重复数据，因为在有限的 CPT 数据上跑多个 epoch 会导致过拟合并丢失通用能力。监控验证 loss 以跟踪进展。对 SFT，全秩训练通常比 LoRA 需要更少的 epoch。LoRA 训练可以容忍略多的 epoch。监控验证 loss 以发现过拟合并选出最好的检查点。

### RFT 专有参数

RFT 引入了 CPT 或 SFT 中不存在的额外参数。

- 生成数量控制模型为每个 prompt 生成多少候选响应供奖励函数比较。候选更少意味着训练更快，但信号多样性更低。候选太多只会增加噪声而不改进信号，而且几乎让训练时间翻倍。适中的取值能达到最佳的准确率与耗时之比。如果你的任务在响应质量上方差较大，就增加该值。在开发阶段需要快速迭代奖励函数时，就减少该值。
- KL 散度损失系数约束模型的策略能偏离其原始行为多远。该参数仅在 SMTJ 上可用。系数低会让模型自由探索，但可能找到钻奖励函数空子的捷径。系数高则会不断把模型拉回起点，从而妨碍有意义的学习。如果训练期间 KL 散度出现尖峰，就提高该系数，以在真实学习与行为漂移之间取得平衡。
- 推理投入（Reasoning Effort）控制模型在回答之前执行多少思维链推理。高推理投入带来最好的准确率，但会增加延迟与服务成本。低推理投入推理更快，准确率折损有限。在验证时为了最高准确率使用高推理投入，之后对延迟敏感的生产部署可以考虑降低。
- Lambda 并发上限（仅 SMTJ）控制用于奖励评估的并行 AWS Lambda 函数数量。对于执行很快的奖励函数，应显著提高该值，以免评估吞吐成为瓶颈。

记住，批大小的含义在不同平台之间不同。在 SMTJ 上，`global_batch_size` 指每步的 prompt 数，每个 prompt 生成 N 个候选。在 SageMaker HyperPod 上，`global_batch_size` 指样本总数（prompt 数乘以生成数）。在环境之间迁移时要仔细换算。

### 正则化参数

正则化参数有助于防止过拟合，尤其是在较小的数据集上。

- 权重衰减默认值为零。如果你在小数据集上观察到过拟合，可适度提高。权重衰减施加 L2 正则化，以约束参数幅度。
- Dropout（隐藏层与注意力）默认值为零。对较小的数据集，可适度提高隐藏层 dropout 以减少过拟合。提高注意力 dropout 要谨慎，因为取值过高会损害复杂推理能力。
- 裁剪比例与年龄容忍度是 SageMaker HyperPod 的高级参数。裁剪比例限制策略在单个训练步内能改变多少。年龄容忍度决定训练数据在被视为过于陈旧之前能保持有效多久。重拟合频率控制模型多久采集一次新的训练数据。默认值适用于大多数用例。只有在你清楚自己正在解决的具体稳定性问题时，才调整这些高级设置。

## 实验与洞见

带着这些超参数的考虑，我们使用 Amazon Nova 2.0 在多个公开基准上运行了一系列 HPO 实验，包括 [CoCoHD](https://huggingface.co/datasets/gtfintechlab/CoCoHD_transcripts)、[MedReason](https://huggingface.co/datasets/UCSC-VLAA/MedReason) 与 [LLaVA-CoT](https://huggingface.co/datasets/Xkev/LLaVA-CoT-100k)。下表汇总了各参数扫描的实验配置与关键发现。

| **数据集** | **Rank** | **Alpha** | **GBS** | **LR** | **最大步数** | **Warmup** | **基础目标表现** | **SFT 目标表现** | **排名** | **表现差异** |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| MedReason | 32 | 64 | 32 | 1.00E-05 | 312 | 47 | 57.38% | 63.54% | 2 | 10.75% ↑ |
| MedReason | 64 | 64 | 32 | 1.00E-05 | 312 | 47 | 57.38% | 63.78% | 1 | 11.16% ↑ |
| MedReason | 32 | 64 | 32 | 5.00E-06 | 312 | 47 | 57.38% | 63.33% |  |  |
| MedReason | 32 | 64 | 32 | 1.00E-05 | 624 | 94 | 57.38% | 61.42% |  |  |
| LLavaCOT | 64 | 64 | 32 | 1.00E-05 | 312 | 47 | 16.22% | 68.47% | 1 | 322.13% ↑ |
| LLavaCOT | 32 | 128 | 32 | 1.00E-05 | 312 | 47 | 16.22% | 65.77% | 2 | 305.49% ↑ |

我们在 Amazon Nova 2 Lite 上使用 Nova Forge 运行 LoRA SFT，rank 32、alpha 64、批大小 32、15% warmup、1 个 epoch，只扫描学习率，以隔离它对目标准确率的影响。服务默认值 1e-5 取得了最好结果 63.54%，相比 v4 基线提升 10.75%。把学习率降到 5e-6 会损害目标表现，却并没有实质性地保护通用能力，因为 MMLU、IFEval 与 GPQA 的分数与 1e-5 那次运行相比都在噪声范围内。在相同学习率下把 epoch 翻倍到 2，准确率降到 61.42%，证实了在狭窄领域数据上过度训练会同时侵蚀领域表现与通用表现。

我们在一项多模态推理任务上改变 LoRA 的 rank（32 与 64）与 alpha（64 与 128），该任务中基础模型的起点准确率只有 16.22%。最佳配置是 rank 64 配 alpha 64，把准确率提升到 68.47%，相对基线提升 322%。在 rank 32 下把 alpha 翻倍到 128，取得了接近的目标增益（65.77%），但通用能力回退的代价明显更高。对于基线准确率较低的任务，提高 rank 是比提高 alpha 更有杠杆作用的调整。只有当 LoRA 适配不足时才应提高 alpha，而当模型开始丢失通用能力时就应降低 alpha。

没有哪一种超参数配置对所有用例都最优。这些推荐默认值是强有力的起点，而不是最优表现的保证。

## 常见误区及如何避免

下表汇总了实践者在调优 Amazon Nova Forge 模型时最应避免的常见错误。

| **误区** | **症状** | **解决方案** |
| --- | --- | --- |
| 在 RFT 之前跳过 SFT | RFT 没有带来改进，甚至使表现变差 | 先运行 SFT，让模型在 RFT 优化之前进入正确的行为邻域。 |
| 在数据混合时偏离默认学习率 | 训练不稳定、loss 尖峰、能力崩塌 | 使用数据混合时坚持服务默认值。这是最常见的错误。 |
| 奖励函数质量差 | 尽管有训练，准确率仍下降，或模型钻指标的空子 | 在改动任何训练参数之前，先打磨你的奖励函数。至少用两个独立的评判者做验证。 |
| 在有限的 CPT 数据上跑多个 epoch | 过拟合、通用能力丢失、记忆化 | CPT 数据集最多处理一个 epoch。监控验证 loss 以尽早发现过拟合。 |
| 推理设置不匹配 | 推理行为与训练行为不一致 | 让训练与推理的 `reasoning_enabled` 保持一致：训练时启用推理，推理时也启用。 |

调优 Nova Forge 模型时，先把投入放在奖励函数上，再考虑其他。奖励函数差，无论其他超参数怎么选都会降低准确率；而打磨好的奖励函数在同等基础设施上能带来持续的增益。确保你的奖励函数在模型的质量区间上具有区分力，因为如果所有东西得分都很高，RFT 就没有可优化的梯度。

同样的验证纪律也适用于 LLM 作为评判者的选择。你的评判模型必须能在模型的输出区间上可靠地区分质量差异。在投入一次训练运行之前，至少用两个独立的评估者验证评判一致性。

要注意，各平台的训练环境稳定性机制不同。SMTJ 以软约束的形式施加持续的 KL 惩罚，而 SageMaker HyperPod 用梯度裁剪作为每步的硬上限。两者都能达到相当的准确率，但需要不同的调优直觉。不要假设参数能在环境之间直接迁移。

在所有这些之上，请把数据质量置于数量之上。激进地过滤，并确保训练样本准确代表目标行为，会比单纯扩大低质量数据规模效果更好。

## 衡量成功

当你应用了恰当的超参数调优，收效可能相当可观。AWS 中国应用科学团队在他们对 [Amazon Nova Forge 的评估](https://aws.amazon.com/blogs/machine-learning/building-specialized-ai-without-sacrificing-intelligence-nova-forge-data-mixing-in-action/) 中展示了这一点：在一项复杂的客户之声（Voice of Customer）分类任务上取得 17% 的 F1 分数提升，同时 MMLU 分数维持在接近基线的水平。

### 需要监控的关键指标

**训练 loss** 应稳步下降，不应出现突然的尖峰。尖峰往往意味着学习率问题或数据质量问题。

**验证 loss** 能揭示过拟合。如果验证 loss 上升而训练 loss 下降，你就在过拟合。减少 epoch、增加正则化，或加入更多样的数据。

**KL 散度**（对 RFT）显示策略漂移了多远。突然的尖峰说明模型做出了幅度大且可能不稳定的更新。如果出现这种情况，提高 KL 损失系数。

**奖励指标**（对 RFT）应稳步提升。如果奖励快速提升后趋于平台期或下降，模型可能是在钻奖励函数的空子。回头检查你的奖励设计。

## 结论

用 Amazon Nova Forge 优化模型定制需要平衡艺术与科学。艺术在于理解权衡：检查点选择、数据混合策略与训练模式决策，对结果的影响比任何单个超参数都大。科学在于系统性调优：学习率、批大小以及技术专有参数，都需要基于你的数据与目标仔细配置。

数据与奖励的质量，在重要性上超过任何超参数。在调优训练参数之前，先优化你的数据 pipeline 与奖励函数。从服务默认值开始，尤其是学习率与数据混合，因为这些默认值之所以存在，就是因为它们在广泛的用例中都能奏效。

对大多数生产场景，最强的 pipeline 是先 SFT 再 RFT。RFT 精炼既有能力，但无法从低基线中恢复，因此监督微调必须先建立起扎实的表现。数据混合应被视为生产负载的必需品，而不是可选项。它能防止灾难性遗忘，并提供可靠结果所需的优化稳定性。

处理持续预训练时，检查点选择是你将做出的影响最大的决策。让检查点的灵活性与你的数据规模相匹配：大规模领域适配用较早的检查点，较小的数据集、且保留指令遵循行为更重要时用较晚的检查点。

要开始使用 Amazon Nova Forge，请浏览 [Amazon Nova 文档](https://docs.aws.amazon.com/nova/) 与 GitHub 上的 [SageMaker HyperPod recipes 仓库](https://github.com/aws/sagemaker-hyperpod-recipes)。关于数据混合的实操示例，请参阅 [Nova Forge 数据混合博文](https://aws.amazon.com/blogs/machine-learning/building-specialized-ai-without-sacrificing-intelligence-nova-forge-data-mixing-in-action/)。如需深入了解 Nova Forge 的 RFT，请参阅[针对 Amazon Nova 的强化微调：通过反馈教会 AI](https://aws.amazon.com/blogs/machine-learning/reinforcement-fine-tuning-for-amazon-nova-teaching-ai-through-feedback/) 这篇博文。
