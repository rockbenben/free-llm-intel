# 多智能体设计模式、反模式分类及来自制造业的经验教训

企业团队正在构建多 agent 系统，而当早期实现达不到预期时，原因很少是模型本身。多 agent 协调是一个分布式系统问题，而许多接下这项工作的团队还没有建立起分布式系统的直觉。

各方数据彼此吻合：[约 88% 的 AI pilot 从未进入生产](https://www.cio.com/article/3850763/88-of-ai-pilots-fail-to-reach-production-but-thats-not-all-on-it.html)。Stanford HAI 的研究表明，当协调开销超过收益时，[两个模型协作的表现可能比各自单独工作更差](https://hai.stanford.edu/news/ai-coding-agents-fail-at-teamwork)。模式很清楚：团队增加复杂度的速度快于他们建立理解的速度。十个各自 95% 可靠的步骤，端到端可靠性只有 59.9%；二十个步骤则只有 35.8%。这个用于示意的模型假设的是一条严格串行、没有重试的链路，但方向是成立的：每一处有依赖的交接都会放大风险。

本文将介绍如何判断一个用例是否需要多个 agent、如何选择协调模式，以及如何及早发现代价高昂的反模式。你还会看到 takt time、安全边界、边缘数据和班次周期如何塑造架构。

## 多 agent 协调模式

协调模式按「谁控制流转」分为两个层级。在 Tier 1 中，路径由你定义。

在 Tier 2 中，模型在运行时选择路径。这种灵活性可以处理那些你无法预先定义步骤的工作，代价是更高的 token、延迟和调试成本。实践中的默认做法是：先上 Tier 1，只有当子任务是在工作过程中才浮现出来时，才把任务移到 Tier 2。

### Tier 1：各模式（确定性控制流）

**1.1 顺序流水线（Sequential Pipeline）：** 实现线性执行的编排模式，每个节点的输出流入下一个节点（A -> B -> C），支持有顺序、执行时间可预测的处理

在下图中，输入先流向 agent A（抽取），再到 agent B（转换），再到 agent C（校验），然后输出。这个顺序由用户在构建时定义，运行时不做任何决策。因此流水线易于调试和测试，成本也可预测。典型适用场景包括文档处理、extract、transform、load（ETL）链路以及保修索赔分诊。

![顺序流水线：输入依次经过抽取、转换和校验 agent 到达输出](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/16/ML-21577-1-1.png)

图 1：顺序流水线，每个 agent 的输出流入下一个，从抽取到转换再到校验

**1.2 条件工作流（Conditional Workflow）：** 基于逻辑的边按条件选择下一个节点，因此工作流可以分支，把每个 case 送到不同的路径。

在下图中，一个用户请求先到 agent A（写代码），再到 agent B（测代码）。一个通过/不通过的检查把通过的工作送到 agent D（部署）。失败的工作循环回 agent A 重试，最多 N 次，然后升级给人工。编排层负责执行这个上限，例如通过 AWS Step Functions 的迭代次数限制，从而避免这个循环变成本文后面会讲到的「无界迭代」反模式。

![条件工作流：测试 agent 判定通过的工作被部署，失败的工作循环回写代码 agent](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/16/ML-21577-2-1.png)

图 2：条件工作流，失败最多重试 N 次，之后升级给人工

**1.3 条件路由（Conditional Router）**：

一个分类步骤检查输入并把它导向合适的处理路径。每个请求只执行一条路径。最适合意图驱动的分派、质量门决策、客户咨询路由以及异常分诊。

下图展示工厂主管的请求被分类器读取，并准确发送给唯一一个专家。关于零件是否符合规格的问题交给 Quality Agent，逾期未做的设备保养交给 Maintenance Agent，班次变更交给 Scheduling Agent。这个决策在入口处完成。

![条件路由：把每个请求送入唯一一条经过分类的处理路径](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/16/ML-21577-3-1.png)

图 3：条件路由，每个请求只跑一条路径，并在升级给人工之前做有界重试

**1.4 并行工作流（Parallel Workflow）：** 任务拆分成独立的子任务，在各 handler 上同时运行，各自处理自己的数据。当所有 handler 完成后，一个 fan-in 步骤把结果合并；某条路径失败时只重试那条路径。最适合多来源分析、批处理，以及可分解为独立部分的工作。

在下图中，一个研究 orchestrator 把任务分解，并分派给三个并发运行的专家 agent：财务数据 agent、地缘政治 agent 和物流 agent，各自分析自己的来源。一个合并步骤等待三者全部完成，然后综合结果、消解冲突并对发现排序。延迟等于最慢的那个 agent，而不是三者之和。

![并行工作流：fan-out 到并发运行的财务、地缘政治和物流 agent](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/16/ML-21577-4-1.png)

图 4：并行 fan-out 到各专家 agent，随后由一个 fan-in 步骤综合并排序结果

### Tier 2：自主模式（由 LLM 决定控制流）

在自主模式中，控制流由 AI 模型本身在运行时决定，而不是由开发者预先定义。agent 读取任务状态，推理需要什么，并通过共享上下文而非固定路径来协调；这些模式从结构化编排到完全涌现的行为，构成一个谱系。

#### 2.1 基于计划的编排

在基于计划的编排中，单个 orchestrator agent 扮演项目经理。orchestrator 维护一份显式任务计划，包含分配与依赖关系；它能看到全部上下文，而每个 worker 只拿到自己那一部分；它按当前计划动态分配工作，并集中监控进度。关键设计选择是 worker 无状态且相互独立。一个失败不会污染其它 worker，orchestrator 只重试失败的 worker，而不是整个工作流。

下图展示 planner agent 如何把任务分解成一份显式计划，并把每一步分派给 worker agent。每一步交给一个专门的 worker（研究 agent、分析 agent 和报告 agent），它只能看到分配给自己的那一部分。

![基于计划的编排：planner agent 把各步骤分派给研究、分析和报告 worker](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/16/ML-21577-5-1.png)

图 5：基于计划的编排，planner agent 把每一步分配给无状态的 worker agent

#### 2.2 交接模式（Handoff pattern）

各 agent 只掌握有限的本地知识，通过点对点委派来协调。每个 agent 基于任务和它所认识的 agent，就地决定何时移交控制权、移交给谁。控制权是带着状态转移的：每次移交都携带经过校验的任务状态、支撑它的证据以及尚未解决的问题，这样接收方才能继续工作，而不是重新解读一份摘要。只靠对话传递的移交不算交接。

在下图中，客服 agent 连同上下文把控制权移交给技术支持 agent 或账单 agent，技术支持还可以进一步移交给资深工程师。每个 agent 只认识它能移交的那一小群同伴。

![交接模式：客服 agent 把控制权移交给技术支持或账单 agent](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/16/ML-21577-6-1.png)

图 6：交接模式通过本地委派在对等 agent 之间传递经过校验的状态

#### 2.3 对话驱动模式

在对话驱动模式（也称 group chat 模式）中，所有 agent 参与同一条共享对话，编排通过轮流发言而涌现，而不是依赖显式计划或结构化交接。这映射了人类团队协作：每个人都能看到讨论，并在合适的时候贡献内容。

在下图中，一个 agent 选择机制决定轮到谁发言，agent A、B、C 各自向同一条共享对话追加内容，每一轮都是一条消息加一次工具调用。选择机制决定轮流顺序，状态隐含地存在于对话历史中。

![对话驱动模式：选择机制在共享对话中把发言权依次给到 agent A、B、C](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/16/ML-21577-7-1.png)

图 7：对话驱动模式，轮流发言选出下一个 agent，状态存在于对话中

控制流特征：

- 可见性：广播式，所有 agent 都能看到共享对话中的所有消息。
- 决策：下一个发言者根据对话上下文选出，而不是预先确定的计划。
- 状态管理：隐含在对话历史中。
- 轮流机制：由选择机制决定（轮询、AI 驱动）  轮询。agent 按固定的循环顺序轮流发言，直到满足终止条件，因此可预测。AI 驱动。由模型从对话上下文中选出下一个发言者，而不是固定顺序。

#### 2.4 辩论/共识

多个 agent 独立评估同一份输入，然后通过多数表决、评审 agent，或在出现分歧时升级来协调它们的结论。与对话驱动模式不同，这些 agent 在表明立场之前看不到彼此的推理过程，正因如此，分歧才具有信息量，而不是变成社交性趋同。

谨慎使用。辩论是本文中最昂贵的模式，而且在感知类任务上，它买到的是延迟而不是准确率（参见后面反模式 3 中的质量检测案例）。把它保留给高风险、低频率的决策——在这些决策中，出错的代价高于反复斟酌。

### 混合方式

在实践中，大多数生产系统会基于任务分解组合多种模式：

- 对可预测、已被充分理解的组件使用 *工作流模式*。
- 在灵活性与适应性至关重要的地方应用 *自主模式*。
- 在所有编排类型中一致地实现 *任务管理模式*（终止、委派）。
- 设计 *分层组合*，让复杂的 agent 在内部不同层使用不同的模式。

统领原则是：*模式与任务对齐*。让编排方式匹配每个任务固有特性和系统的可靠性要求，而不是把所有东西都塞进单一模式。

## 烧钱的反模式

下面五个反模式在设计阶段看起来都很合理，每一个都会在之后以 token 成本飙升、错过 takt time 窗口，或某个决策悄悄与车间实际脱节的形式浮现出来。

#### 1. 上帝 agent（God agent）

一个 agent 在单个 prompt 里用 15 个或更多工具，同时负责整体设备效率（OEE）分析、可编程逻辑控制器（PLC）诊断和维保。随着工具增多，工具选择能力退化，失败也变得难以归因。

**修复方式：** 使用工具数不超过五个的有界 agent，例如 OEE 分析师、故障诊断师和维保草拟员。

#### 2. 无界迭代

agent 在「再试一次」上循环，没有硬性停止条件。一个四 agent 系统可能在一轮重试之前就烧掉显著更多的 token，而没有哪一次调用会触发告警。重试会放大协调失败，而不是修好它们。

**修复方式：** 在代码里设置硬性迭代上限、每个 agent 的 token 上限、与自动停止联动的预算告警。由基础设施来执行限制，模型不会自己停下来。

#### 3. 自然语言契约

agent 之间互相传递没有 schema 的自由文本。解读在每一跳都会变硬：「可能表明磨损」变成「已确认磨损」，再变成一张维保工单。这种漂移发生在 agent 之间——恰恰是追踪最薄弱的地方。

#### 4. 过早多 agent 化

本来一个带工具组的 agent 就能搞定，却上了多 agent。每多一个 agent 都会带来非线性增长的协调税，而收益在四个左右就开始变平。大多数「专家」不过是同一个模型换了不同的戏服。

**修复方式：** 只有在至少需要两个不同模型、不同工具访问权限、并发执行以及真正相互依赖时才上多 agent。少于两项，用一个带 action group 的 agent 就够。

*检验方法：一个 agent 能不能通过切换工具来处理这些阶段？如果能，这就不是一个多 agent 问题。*

#### 5. 无护栏的客户接触

agent 在没有审批步骤的情况下触发真实世界的动作（邮件、上门服务、机器参数）。幻觉跨入物理世界，不可逆的动作层层累积，责任从一笔退款升级为产品责任。

**修复方式：** 纵深防御：建议 → Amazon Bedrock Guardrails → schema 校验 → 业务规则 → 人工审批 → 执行。

凡是 agent 输出会触达客户或安全系统的每一个点，都是信任边界。

## 选择架构

把模式与反模式都摊开看之后，架构选择归结为一串简短的问题。

- **这个任务需要的动作是否超出文本生成？** 把直接调用模型当作基线，只有存在经过衡量的理由时才加入编排。总结文档或根据规格生成代码，很少构成这样的理由。
- **解法路径是否事先已知？** 如果你能写下什么按什么顺序发生，那你根本没有「要几个 agent」这个决策。你真正的选择更简单：一个调用工具的 agent，或者一条 Tier 1 工作流。
- **这项工作是否需要真正不同的专业能力？** 各有既定交接方式的独立领域，才值得使用专门的 agent。单一领域就属于一个 agent，无论它需要多少工具。
- **解法只能通过探索涌现吗？** 当动作序列已知、可以按「行动—验证」循环运行时，它就属于单个 agent，即使这个 agent 会动态规划自己的步骤。只有当子任务本身是在工作过程中才被发现时，Tier 2 才配得上它额外的成本、延迟和调试负担。

下面的决策树把这四个问题变成一条可以从上到下走完的路径。

![用于选择架构的决策树，判断依据是任务是否需要动作、路径是否已知、是否需要不同专业能力，或是否需要探索](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/16/ML-21577-8-1.png)

图 8：选择最简单架构的决策树，从单次模型调用到 Tier 2 多 agent 模式

这棵树先问：任务是否需要在文本生成之外采取动作。如果不需要，一次简单的模型调用就够了。如果需要，树接着问：解法是否众所周知、能否表达为一个工作流。在已知解法这一侧，受益于专业能力或领域分离的工作走向 Tier 1 多 agent 工作流（流水线、fan-out 或路由器），其余的都走向一个带工具与 action group 的单一 agent。在未知解法这一侧，只有涉及探索或显著副作用的任务才走向 Tier 2 的自主多 agent 模式，其余仍留给单一 agent。指导原则是选择满足需求的最简单架构。

### 应用：把模式映射到制造业用例

| **用例** | **模式** | **理由** |
| --- | --- | --- |
| **班次交接摘要** | 顺序流水线 | 线性：原始日志 → 摘要 → 报告 |
| **多工位根因分析** | 基于计划的 orchestrator | 动态：子任务在分析过程中才被发现 |
| **实时质量门** | 条件路由 + 边缘 agent | 在周期内：由本地模型决定。agent 推理不在关键路径上 |
| **预测性维保排程** | 并行 fan-out/fan-in | 每类资产使用独立模型 |
| **工程变更单影响** | 辩论/共识 | 高风险：对抗式评审是合理的 |
| **供应商沟通草拟** | 顺序 + 人工关卡 | 绝不能自动发送（见「无护栏的客户接触」） |
| **跨厂优化** | 基于计划的 orchestrator | 多来源：动态查询。由求解器完成分配 |

## 制造业视角：改变算账方式的四个约束

制造业不是通用的企业 IT 环境，有四个约束让这笔账算得格外严苛。

### 约束 1：产线延迟 = 直接的收入损失

汽车车身车间里机器人把车身焊在一起，通常每小时跑 60 个工件。其 40 多个工位每个都有 60 秒的 takt time，超过就要影响产线推进。落在工位周期路径上的推理延迟会吃掉这 60 秒，而瓶颈工位上的延迟会拖慢整条产线。即使吞吐量下降 2%，也可能带来可观的年度收入影响。

**架构含义：** 按 p99 而不是平均值来做延迟预算。停线的是尾部。给每个 agent 一个亚秒级的确定性兜底路径，并按风险匹配：

- **建议/质量标记类：** 让零件通过，并打上标记供产线末端复核。
- **安全关键类：** 围堵或确定性停机，而不是继续运行。
- 在部署之前为每个工位确定好这个映射。

### 约束 2：安全有物理后果

聊天机器人产生幻觉会让人尴尬。焊接参数产生幻觉则会造成结构缺陷，在碰撞测试或现场失效中暴露出来，并可能导致安全召回。有两类失效模式反复出现：

- **OT/IT 边界状态失步：** agent 从制造执行系统（MES）读到工位 12 正在加工 Part #A，但一次人工 PLC 覆盖已经把它切到了 Part #B，于是它按错误的零件调整了参数。
- **幻觉出的安全边界：** 一个维保 agent 从零开始推理上锁挂牌（lockout/tagout），在相邻的工位 6 仍在运行时宣布工位 7 可以进入，破坏了互锁区域。

**架构含义：**

边界：保持确定性内核不变——包括 PLC、监控与数据采集（SCADA）系统和 MES——并在其外围包一层建议层。

- agent 观察、分析并给出建议，不执行动作。
- 安全约束作为确定性 guardrails 放在外部服务中，由 agent 查询而不是靠推理。它们绝不写进 prompt，因为写在 prompt 里就可能被「说服」掉。

**校验与审批：** 一条建议要通过 schema 校验和物理仿真，并在执行动作之前立刻对照 OT 的真实来源校验——绝不用超过一个周期的 OT 缓存状态来校验。然后它会在与其影响范围相称的层级上获批：

- **Level 0：** agent 自主解决。
- **Level 1：** 操作员一键确认。
- **Level 2：** 工程师基于呈现的分析做决定。
- **Level 3：** 管理层评估停线建议。

只有到这一步，一个经过校验的命令接口才会把获准的命令传给确定性控制。大语言模型（LLM）提出方案，物理引擎和人类操作员做最终处置。

### 约束 3：数据在边缘

单台冲压机每天产生 50+ GB 的传感器数据，其价值在毫秒间衰减。把这些数据传到云上，带宽成本比计算成本还高，而且等云端给出答案时，冲压机早已过了那个时刻。

**架构含义：** 边缘-云混合是实践中的默认选择，而约束 2 的边界在边缘侧同样成立。

- **边缘（AWS IoT Greengrass）：** 在数据源处做亚 takt 级的异常检测、阈值监控和停止或继续信号：边缘 agent 给建议，PLC 执行动作。
- **云：** 边缘做不到的事：跨班次分析、跨厂趋势关联，以及基于全量设备数据的模型再训练。边缘只提炼并上传真正重要的内容。

### 约束 4：与班次对齐的 agent 生命周期

无界上下文会让 agent 漂移，因为陈旧观察会挤占当前现实。而完全重置又会丢失班次之间的连续性。制造业已经用结构化的班次交接为人类解决了这个问题，agent 也需要同样的纪律。

**架构含义：** 把 agent 记忆限定在班次周期内。

- **初始化：** 班次上下文，包括班组名单、生产目标和上一班的交接内容。
- **累积：** 工作记忆只限于本班次窗口内。
- **交接：** 在班次结束时输出一份摘要，包含未解决问题、已标记异常和各项建议，为下一班提供种子——映射人类交接仪式，同时不带来无界上下文增长。

## 结论

多 agent 系统正在改变汽车制造商大规模编排智能的方式，但前提是建在正确的地基上。

这里的模式与反模式来自真实部署——在这些部署中，糟糕的架构会表现为失控的 token 成本、违反 takt time，最坏情况下还会带来物理安全风险。工厂规模下的经济性毫不宽容，因为 token 用量会随每一个 agent、每一台机器人、每一个班次增长。分层模型选择、上下文压缩和边缘-云分布，是用零头成本交付同等价值的主要杠杆。

这里的建议是：先从 Tier 1 模式开始，证明价值，然后扩展。大多数制造业用例——例如班次交接摘要、质量门决策和预测性维保——用确定性工作流就能很好地满足。把自主编排留给真正开放式的问题，在这些问题里，动态的子任务发现才配得上额外的成本、延迟和调试复杂度。
