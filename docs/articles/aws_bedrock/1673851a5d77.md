# 通过 Amazon Bedrock AgentCore 保护 Snowflake Cortex AI 的 OAuth 模式

如今的企业需要一条清晰的路径，把身份验证与授权控制延伸到 agentic 层，而这往往要么依赖宽泛的服务账号权限，要么依赖自建的认证集成，从而增加运维开销。当运行在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)（一个可用任意框架、任意模型大规模构建、连接和优化 agent 的平台）上的 AI agent 需要通过 [Model Context Protocol](https://modelcontextprotocol.io/)（MCP）调用 [Snowflake 托管的 MCP 服务器](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-mcp)（该服务器把 [Snowflake Cortex Agents](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents) 作为其工具类型之一对外提供）时，企业首先要回答的问题是：agent 如何完成认证？本文介绍我们在 [Amazon Bedrock AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html)（Amazon Bedrock AgentCore 的一项能力）上测试过的三种 Open Authorization（OAuth）配置：Snowflake OAuth（按用户，无外部 Identity Provider，即 IdP）、借助第三方 Identity Provider 的三足 OAuth（企业单点登录，即 SSO），以及借助第三方 Identity Provider 的两足 OAuth（共享服务用户）。Amazon Bedrock AgentCore Identity 还支持 on-behalf-of（OBO）授权（TOKEN_EXCHANGE），可在没有同意提示的情况下为无人值守工作负载提供按用户身份。我们聚焦于端到端测试过的这三种配置，并在行文中标注 OBO 适合放在哪里。读到最后，你将能判断哪种模式适合自己的企业场景。

## 解决方案概览

[Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 是 Amazon Bedrock AgentCore 的一项能力，通过 MCP 服务器目标把 AI agent 连接到外部工具提供商。它以 Snowflake 托管的 MCP 服务器为目标，后者把 Cortex Search 和 Cortex Analyst 呈现为 MCP 工具，供具备 MCP 能力的客户端发现和调用。Gateway 并不充当包装器，而是把所配置各目标的能力聚合成一份统一目录，并以一个 tools/list 响应呈现给 agent。

本文的核心是 Amazon Bedrock AgentCore Gateway 的[出站认证](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html)：它如何获取 OAuth token，并将其呈现给 Snowflake 托管的 MCP 服务器。Amazon Bedrock AgentCore Identity 充当凭证代理：Gateway 先调用 GetWorkloadAccessTokenForJWT 获取工作负载 token（因为 Gateway 的入站认证使用 JSON Web Token（JWT）），再针对已配置的提供商调用 GetResourceOauth2Token。AgentCore Identity 负责 token 保管库、token 刷新以及用户与 token 的绑定，并自动获取、缓存和刷新 token。

Amazon Bedrock AgentCore Identity 支持三种 OAuth 配置，覆盖两种授权类型（authorization_code 和 client_credentials）：

- [Snowflake OAuth](https://docs.snowflake.com/en/user-guide/oauth-snowflake-overview)：Snowflake 自身充当 OAuth 授权服务器。每个用户通过 Authorization Code 授权（3LO）直接向 Snowflake 认证，无需外部身份提供商。
- 使用第三方 Identity Provider 的三足 OAuth：用户通过企业 SSO 配合 Authorization Code 授权完成认证。Snowflake 通过其[外部 OAuth](https://docs.snowflake.com/en/user-guide/oauth-ext-overview) 安全集成信任 IdP 签发的 JSON Web Token（JWT）。
- 使用第三方 IdP 的两足 OAuth 模式：共享服务用户通过 IdP 的 client_credentials 授权完成认证。无需任何用户交互或同意，非常适合机器对机器的工作负载。

Amazon Bedrock AgentCore Identity 还提供 API key 凭证提供商（支持 Snowflake Programmatic Access Token）。本文聚焦 OAuth，因为它能实现按用户归因和自动 token 刷新。每种配置都在 Amazon Bedrock AgentCore Identity 中使用一个凭证提供商（CustomOauth2、OktaOauth2 或 MicrosoftOauth2），并在 Snowflake 侧使用对应的安全集成。

**注意：** 我们用 Okta 和 Microsoft Entra ID 搭配 Snowflake 托管的 MCP 服务器测试了这些模式。模式 2 和模式 3（外部 IdP）遵循标准 OAuth 流程，因此可以推广到其他受 OAuth 保护的 MCP 服务器，但要针对你的 SaaS 提供商校验 token 声明、scope 和 audience 设置。只有模式 1 是 Snowflake 特定的，因为它依赖 Snowflake 内置的 OAuth 授权服务器。Snowflake 特定的元素包括 OAUTH_AUTHORIZATION_SERVER 这个 issuer 锁定参数、session:role: / session:scope: 语法、BLOCKED_ROLES_LIST、LOGIN_NAME / EMAIL_ADDRESS 映射以及 QUERY_HISTORY 归因。如果你的 SaaS 对外暴露自己的内部 OAuth 服务器，那么出站 OAuth 的配置方式与 Snowflake OAuth 相同。

| **模式** | **OAuth 授权** | **AgentCore Identity 凭证提供商厂商** | **Snowflake 安全集成** | **Snowflake 查询身份映射** |
| --- | --- | --- | --- | --- |
| Snowflake OAuth – 3LO | authorization_code | 自定义提供商（CustomOauth2） | TYPE = OAUTH，OAUTH_CLIENT = CUSTOM | 真实用户，及其被分配的角色 |
| 借助外部 IdP 的 3LO | authorization_code | 内置提供商（如 OktaOauth2、MicrosoftOauth2） | TYPE = EXTERNAL_OAUTH + OAUTH_AUTHORIZATION_SERVER（用 ALTER ACCOUNT / DATABASE / SCHEMA 设置）；EXTERNAL_OAUTH_TYPE = OKTA / AZURE / PING_FEDERATE / CUSTOM | 真实用户，及其被分配的角色 |
| 借助外部 IdP 的 2LO | client_credentials | 内置提供商（如 OktaOauth2、MicrosoftOauth2）或 CustomOauth2 | TYPE = EXTERNAL_OAUTH + OAUTH_AUTHORIZATION_SERVER（用 ALTER ACCOUNT / DATABASE / SCHEMA 设置）；EXTERNAL_OAUTH_TYPE = OKTA / AZURE / PING_FEDERATE / CUSTOM | 共享的 Snowflake 服务用户 |

**备注：**

- 2LO 不要求使用内置厂商。配合 CLIENT_CREDENTIALS 授权的 CustomOauth2 可与你所选的任意 OAuth 2.0 授权服务器搭配使用。
- 当由 Amazon Bedrock AgentCore Gateway 代理 token 时（也就是本文的模式），Snowflake 通过 TYPE = EXTERNAL_OAUTH 安全集成对其校验。设置 OAUTH_AUTHORIZATION_SERVER（用 ALTER ACCOUNT、DATABASE 或 SCHEMA）正是让直连 MCP 客户端能经 Protected Resource Metadata 端点自动发现你的 IdP 的原因，同时它把 MCP 端点 issuer 锁定到该集成上。
- 如果你用 OAUTH_AUTHORIZATION_SERVER 把某个 MCP scope issuer 锁定到外部 IdP（模式 2），那么该 scope 内的 MCP 服务器会拒绝 Snowflake OAuth token（模式 1），且不会回退。如果你需要在同一个账户里同时使用两种模式，请按 schema 或 database 分别设置该参数，使每个 scope 解析到正确的授权服务器。

## 模式分析

以下各节逐一细看每种模式：认证流程、配置步骤与取舍，帮你为自己的用例选出合适的做法。

### 模式 1：Snowflake OAuth（三足）

Snowflake OAuth 模式采用三足 OAuth（3LO）流程，在无需外部身份提供商的前提下实现按用户认证。每个用户用自己的凭证向 Snowflake 认证，同意使用某个特定的 Snowflake role，Amazon Bedrock AgentCore Identity 则缓存该用户的 access token 和 refresh token。此后每次调用 Snowflake 都以该用户身份执行，QUERY_HISTORY 记录的是其真实用户名。注意，按 role 同意并不是默认行为。Snowflake 托管的 MCP 服务器对外声明 session:role:all 并回退到 DEFAULT_ROLE，因此你要设置 OAUTH_SCOPES_SUPPORTED（账户级、database 级或 schema 级参数，用 ALTER 设置）来收窄服务器对外声明的 role scope，并限制集成上的 ALLOWED_ROLES_LIST，以强制约束用户可同意哪些 role（PRE_AUTHORIZED_ROLES_LIST 则相反：它列出跳过同意步骤的 role）。

这一模式的吸引力在于简单：不需要外部身份提供商。Snowflake 同时充当授权服务器和资源服务器，对外提供自己内置的 OAuth 端点（/oauth/authorize 和 /oauth/token-request）。配置要按特定顺序进行，因为在凭证提供商创建出来之前，回调 URL 并不存在。管理员先在 Amazon Bedrock AgentCore Identity 中用占位的 client credentials 创建 CustomOauth2 凭证提供商，并记下 AgentCore Identity 返回的 callbackUrl。随后把这个 callbackUrl 注册为 Snowflake 安全集成的 redirect URI，该集成以 TYPE = OAUTH、OAUTH_CLIENT = CUSTOM 创建。最后，管理员用 Snowflake 签发的真实 client ID 和 secret 更新凭证提供商，并为提供商的 oauthDiscovery 配置显式的授权服务器元数据：issuer（Snowflake 账户 URL）、授权端点（/oauth/authorize）和 token 端点（/oauth/token-request）。

[Snowflake OAuth 授权流程](https://docs.snowflake.com/en/user-guide/oauth-snowflake-overview#snowflake-oauth-authorization-flow)的工作方式如下：

- 当某个工具调用需要 Snowflake token 时，Amazon Bedrock AgentCore Gateway 会调用 GetWorkloadAccessTokenForJWT 获取工作负载 token，并调用 GetResourceOauth2Token，在 Amazon Bedrock AgentCore Identity 的 token 保管库中查找该用户的 token。如果没有缓存 token，Gateway 返回 JSON-RPC 错误码 [-32042](https://aws.amazon.com/blogs/machine-learning/connecting-mcp-servers-to-amazon-bedrock-agentcore-gateway-using-authorization-code-flow/)，其中携带一个 URL elicitation。该授权 URL 属于 AgentCore Identity，且为 `session-URI-bound`。客户端在用户的浏览器中打开该 URL，请求被路由到 Snowflake 内置的授权服务器（/oauth/authorize），并显示 Snowflake 登录界面。
- 用户输入自己的 Snowflake 凭证，随后看到同意界面，要求其授权以某个特定的 Snowflake role 访问（例如 ANALYST_ROLE）。请求 scope 中的 role 名必须大写（例如 session:role:ANALYST_ROLE）。
- 用户同意后，Snowflake 的授权服务器把一个授权码返回给 Amazon Bedrock AgentCore Identity 的回调 URL。AgentCore Identity 随后把用户浏览器重定向到带 session URI 的 return URL。
- 只有当应用带上用户身份和 session URI（有效期为 10 分钟）调用 CompleteResourceTokenAuth 之后，AgentCore Identity 才会完成授权码交换。这一步把授权码绑定到最初的请求上，从而阻止授权 URL 劫持。这里使用的 return URL 通过调用 UpdateWorkloadIdentity 注册。在生产环境中，该 URL 对应的端点由你的 Web 应用托管；对于采用 JWT 入站认证的 gateway，则由 AgentCore Identity Consent Portal（`<portal-url>/connect/callback`）托管。agentcore dev CLI 只在本地开发时托管它。随后 AgentCore Identity 在 Snowflake 的 token 端点（/oauth/token-request）用授权码换取 access token，以及可选的 refresh token。
- 当客户端重试该工具调用时，Amazon Bedrock AgentCore Gateway 从 AgentCore Identity 取回缓存的 access token，并呈现给 Snowflake 托管的 MCP 服务器。Snowflake 校验该 token，并创建一个限定在已同意 role 范围内的用户会话。所同意的 scope 只控制**主** role。由于次要 role 由集成管控，请设置 OAUTH_USE_SECONDARY_ROLES = NONE（默认值），这样会话就无法携带超出已同意 role 的权限——若设为 IMPLICIT 则会允许这种情况。

Access token 的有效期很短。默认有效期为 600 秒（最长 3600 秒）。access token 过期后，Amazon Bedrock AgentCore Identity 会自动使用 refresh token 换取新的 access token，无需用户交互。如果安全集成被配置为禁止刷新 token，用户就必须通过同意界面重新授权。refresh token 的有效期由 OAUTH_REFRESH_TOKEN_VALIDITY 控制。参考实现将其设为 86400 秒（1 天），而 Snowflake 最多允许 90 天。OAUTH_ISSUE_REFRESH_TOKENS（默认 TRUE）决定是否签发 refresh token。

**注意：** 默认情况下，Snowflake 会避免 ACCOUNTADMIN、ORGADMIN、GLOBALORGADMIN 和 SECURITYADMIN 这些 role 被用于 OAuth 集成。这由 Snowflake OAuth 的 BLOCKED_ROLES_LIST（外部 OAuth 对应 EXTERNAL_OAUTH_BLOCKED_ROLES_LIST）控制，适用于全部三种模式，且只覆盖主 role。当 OAUTH_USE_SECONDARY_ROLES = IMPLICIT 时，次要 role 仍可能携带这些特权 role。

#### 注意事项

Snowflake OAuth 模式是实现按用户审计留痕的最简路径。它不需要外部 IdP 配置，也不引入额外的厂商依赖。最适合以下场景：

- 用户已经拥有 Snowflake 凭证，并且愿意直接登录。
- 你希望在没有外部身份提供商的情况下，让 QUERY_HISTORY 具备按用户归因。
- 你正处于概念验证阶段，想快速验证按用户模型。
- 合规要求强制个人可问责，因此每条查询都必须能追溯到具体用户，而不是共享服务用户。
- 你希望把用户生命周期（创建、注销、role 授予）完全放在 Snowflake 内管理。
- 你想避开 token 声明映射的复杂性。token 由 Snowflake 签发，它清楚 token 代表哪个用户。

### 模式 2：使用第三方 Identity Provider（IdP）的三足 OAuth（3LO）

这一模式把按用户认证与企业单点登录结合起来。用户通过外部 IdP 登录，由 IdP 强制执行多因素认证（MFA）、条件访问和会话策略。IdP 签发的 JWT 被呈现给 Snowflake，Snowflake 通过其[外部 OAuth 安全集成](https://docs.snowflake.com/en/user-guide/oauth-ext-custom)对其校验（可选择用 OAUTH_AUTHORIZATION_SERVER 把 issuer 锁定到 MCP 服务器所在的 schema、database 或账户）。Snowflake 通过 JSON Web Key Set（JWKS）验证 issuer、audience 和签名。然后它把由 EXTERNAL_OAUTH_TOKEN_USER_MAPPING_CLAIM 设置的可配置声明（[Okta](https://www.okta.com/) 用 sub，[Microsoft Entra ID](https://www.microsoft.com/en-us/security/business/microsoft-entra) 用 upn）映射到 Snowflake 用户的 LOGIN_NAME 或 EMAIL_ADDRESS（通过 EXTERNAL_OAUTH_SNOWFLAKE_USER_MAPPING_ATTRIBUTE），并以该用户身份运行查询。安全集成的参数值区分大小写。

与模式 1 的关键区别在于：授权服务器是你的企业 IdP（例如 Okta、Microsoft Entra ID），而不是 Snowflake。Snowflake 仍是资源服务器。用户用他们在其他所有企业应用中使用的同一套凭证和策略进行认证，无需单独的 Snowflake 密码。

在 Amazon Bedrock AgentCore 侧，Amazon Bedrock AgentCore Identity 为流行的身份提供商提供内置的凭证提供商厂商（例如 OktaOauth2 和 MicrosoftOauth2）。与模式 1 使用的通用 CustomOauth2 提供商不同，这些厂商通过 includedOauth2ProviderConfig 接收 client ID、client secret 和 IdP 端点。Snowflake 托管的 MCP 服务器使用预先注册的 OAuth 客户端，因此你需要提前注册每个 client ID 和 secret，这正是必须先走「创建、记录 callbackUrl、注册、更新」这一顺序的原因。

Snowflake 外部 OAuth 安全集成的流程如下：

- 当某个工具调用需要 Snowflake token 时，Amazon Bedrock AgentCore Gateway 会调用 GetWorkloadAccessTokenForJWT 获取工作负载 token，并调用 GetResourceOauth2Token，在 Amazon Bedrock AgentCore Identity 的 token 保管库中查找该用户的 token。如果没有缓存 token，Gateway 返回携带 URL elicitation 的 JSON-RPC 错误码 -32042。该授权 URL 属于 AgentCore Identity，且为 `session-URI-bound`，而不是 IdP 的。客户端在用户的浏览器中打开该 URL，AgentCore Identity 再把用户路由到 IdP。
- 用户通过第三方 IdP 配合企业 SSO（包括 MFA）完成认证，并同意所请求的 scope。对 Okta 而言，role scope 的形式是 session:role:ANALYST_ROLE。Microsoft Entra ID 的委派流程则使用 session:scope:。
- IdP 把授权码返回给 Amazon Bedrock AgentCore Identity 的回调 URL，AgentCore Identity 把用户浏览器重定向到带 session URI 的 return URL。只有在应用调用 CompleteResourceTokenAuth 校验用户身份和 session URI 之后，AgentCore Identity 才会用授权码换取 access token（如果 IdP 签发 refresh token，也会一并换取）并缓存到按用户的 token 保管库中。
- 当客户端重试该工具调用（以及此后的调用）时，Amazon Bedrock AgentCore Gateway 从 Amazon Bedrock AgentCore Identity 取回缓存的、由 IdP 签发的 JWT，并呈现给 Snowflake 托管的 MCP 服务器。Snowflake 通过其外部 OAuth 集成校验该 token：验证 JWKS 签名和 audience（aud）声明，把配置的用户声明（Okta 用 sub，Microsoft Entra ID 用 upn）映射到 Snowflake 用户，并以已认证用户的身份执行查询。Snowflake 在运行时不会调用 IdP，而是用 IdP 公布的 JWKS 签名密钥在本地校验 token。
- access token 过期后，如果签发了 refresh token（对 Okta，需要请求 offline_access scope），Amazon Bedrock AgentCore Identity 会自动用它刷新。在 refresh token 过期之前，无需用户交互。

Token 生命周期治理：与模式 1 由 Snowflake 控制 token 生命周期不同，这里 access token 和 refresh token 的生命周期由 IdP 决定，Amazon Bedrock AgentCore Identity 负责透明地刷新。如果签发了 refresh token，用户只有在它过期时才需要重新认证，具体取决于 IdP 的会话策略；否则，access token 过期后用户就要重新认证。

#### 注意事项

在以下情况选择使用第三方 IdP 的三足 OAuth（3LO）：

- 你的组织或安全团队要求所有认证都经由企业 SSO，以便集中落实 MFA、条件访问和会话管理。
- 你想利用 IdP 的现有能力，例如基于组的 role 映射、会话超时策略和基于地理位置的条件的访问规则。
- 你需要在 Snowflake 的 QUERY_HISTORY 中获得按用户审计留痕。
- 你希望在所有应用（包括 AI agent）上统一执行安全策略。
- 你需要集中式访问控制。在 IdP 中停用某个用户，有助于阻止新的 Snowflake 授权，但已缓存的 token 在过期前仍然有效。要强制用户重新授权，应用可以在下一次请求时传 forceAuthentication=true，这会清除已存的 refresh token 并开启新的授权流程。要彻底吊销访问，就在 IdP 或 Snowflake 侧撤销授权。

### 模式 3：使用第三方 Identity Provider（IdP）的两足 OAuth（2LO）

两足 OAuth 模式使用 OAuth 2.0 的 client_credentials 授权。这是机器对机器的流程，不需要用户交互。Amazon Bedrock AgentCore Identity 用配置的 client ID 和 client secret 从 IdP 获取 JWT，Amazon Bedrock AgentCore Gateway 把它呈现给 Snowflake，Snowflake 则以共享服务用户的身份执行请求，无论查询最初由哪个终端用户发起。

这一模式在运维上最为直接：没有同意界面、没有按用户的 token 保管库、没有浏览器重定向。用户走的是同一条代码路径。Amazon Bedrock AgentCore Identity 自动获取并缓存 client_credentials token，Amazon Bedrock AgentCore Gateway 在每次向 Snowflake 托管的 MCP 服务器发起出站调用时都呈现它。

与模式 1、模式 2 的关键区别是：不做按用户身份传递。Snowflake 的 QUERY_HISTORY 把查询都记在同一个服务用户名下。代价是用运维上的简化换取了按用户审计的粒度。在 Amazon Bedrock AgentCore 侧，凭证提供商使用 client_credentials 授权类型：可以是内置厂商（OktaOauth2、MicrosoftOauth2），也可以是通用的 CustomOauth2 提供商。配置需要 IdP 的 token 端点、client ID 和 client secret。Amazon Bedrock AgentCore Identity 在第一次工具调用时从 IdP 获取 token（即 Gateway 调用 GetResourceOauth2Token 时），将其缓存；由于 client_credentials 不签发 refresh token，它会在 token 过期前请求一个新的。agent 层代码无需任何改动。

图 10：使用外部 IdP 的 2LO 运行时授权流程：Amazon Bedrock AgentCore Gateway 的 MCP 服务器目标采用 CLIENT_CREDENTIALS 授权，出站认证使用第三方 IdP

Snowflake 外部 OAuth 安全集成的 2LO 流程如下：

- 当某个工具调用需要 Snowflake token 时，Amazon Bedrock AgentCore Gateway 会调用 GetWorkloadAccessTokenForJWT 获取工作负载 token，并调用 Amazon Bedrock AgentCore Identity 凭证提供商上的 GetResourceOauth2Token。如果有有效的缓存 token，Identity 会立即返回。
- Amazon Bedrock AgentCore Identity 用配置的 client ID 和 client secret，以 client_credentials 授权调用第三方 IdP 的 token 端点。对 Okta 而言，请求的 scope 中包含 Snowflake role（例如 session:role:MCP_GATEWAY_ROLE）。对 Microsoft Entra ID 而言，客户端请求 api:`//<application-id>/.default` scope，role 则来自某个 app role 的 roles 声明，该 app role 的值是 session:role:MCP_GATEWAY_ROLE。
- IdP 返回一个 access token（一个 JWT，没有 refresh token），其 aud 声明是 Snowflake 账户 URL，或 EXTERNAL_OAUTH_AUDIENCE_LIST 中列出的额外值（对 Microsoft Entra ID，通常是 Application ID URI）。对 Okta，sub 声明是 client ID。对 Microsoft Entra ID，client ID 放在 appid/azp 中，而 sub 持有服务主体的对象 ID（一个 GUID），因此使用 Entra 时，LOGIN_NAME 必须映射到该 GUID。
- Amazon Bedrock AgentCore Gateway 把该 JWT 呈现给 Snowflake 托管的 MCP 服务器。Snowflake 通过其外部 OAuth 集成校验该 token（可选地用 OAUTH_AUTHORIZATION_SERVER 锁定 issuer，如模式 2 那样）。它通过 EXTERNAL_OAUTH_JWS_KEYS_URL（或 EXTERNAL_OAUTH_RSA_PUBLIC_KEY）验证签名，通过 EXTERNAL_OAUTH_ISSUER 验证 issuer，并对照 Snowflake 账户 URL 加上 EXTERNAL_OAUTH_AUDIENCE_LIST 中的任何额外值来校验 aud 声明（这些安全集成参数值区分大小写）。随后 Snowflake 通过 LOGIN_NAME 把 sub 声明映射到一个 Snowflake 服务用户，并在该服务用户的 role 下执行查询。与模式 2 一样，Snowflake 在本地校验 token，运行时不会调用 IdP。
- Amazon Bedrock AgentCore Identity 把 token 缓存到 token 保管库（跨用户共享，而不是按用户）。后续调用会复用它，而 Identity 会在 token 过期前用 client_credentials 授权请求一个新 token。

由于两足 OAuth 目标不需要用户同意，Amazon Bedrock AgentCore Gateway 会在创建目标时连接 Snowflake 托管的 MCP 服务器，并通过创建目标期间的隐式同步发现工具。在三足 OAuth 模式（模式 1 和模式 2）中，Gateway 目标支持两种创建方式：(1) 由管理员完成授权码流程，使工具通过隐式同步被发现；(2) 由管理员预先提供工具 schema。（发现行为是目标的 ListingMode 属性，而不是授权类型的属性。）

#### 注意事项

对于自动化、无人值守和批处理工作负载，更推荐两足 OAuth 模式。它在以下情况下最理想：

- 你的工作负载是机器对机器的：定时任务、后台流水线，或没有人工介入的系统级 agent。
- 不需要按用户身份，且审计上可以接受共享服务用户。
- 你需要最直接的运维模型：没有同意流程、没有按用户的 token 管理、没有浏览器重定向。
- Gateway 能在创建目标时连接 Snowflake，并通过隐式同步发现 MCP 工具，无需等待用户交互。
- 所有用户在同一个 Snowflake role 下共享相同的数据访问权限。

**接受以下取舍：**

- 由于每个请求都以共享服务用户身份运行，Snowflake 的行级安全（row-level security）和列掩码（column masking）策略会按该用户的权限作用于请求。以 CURRENT_USER() 和 CURRENT_ROLE() 为键的策略都会解析到那一个服务用户及其唯一 role，这正是 on-behalf-of（OBO）方案最有力的理由。
- 不存在用户级的 token 吊销。要切断访问，需在 IdP 侧吊销 client credentials，或停用 Snowflake 安全集成。
- 如果凭证泄露，agent 的访问会受影响。请定期轮换 client secret，并把服务用户限制在最小权限访问范围内。

## 模式对比

| **方面** | **模式 1：Snowflake OAuth（3LO）** | **模式 2：使用外部 IdP 的 3LO** | **模式 3：使用外部 IdP 的 2LO** |
| --- | --- | --- | --- |
| OAuth 授权类型 | authorization_code | authorization_code | client_credentials |
| AgentCore Identity 提供商 | 自定义提供商（CustomOauth2） | 内置提供商（例如 OktaOauth2 或 MicrosoftOauth2） | 内置提供商（例如 OktaOauth2、MicrosoftOauth2）或 CustomOauth2 |
| 授权服务器 | Snowflake 内置 OAuth | 第三方 IdP（例如 Okta、Entra ID） | 第三方 IdP（例如 Okta、Entra ID） |
| Snowflake 可见的身份 | 真实用户 | 真实用户 | 共享服务用户 |
| RBAC 模型 | 按用户的 Snowflake role | 按用户的 Snowflake role | 请求使用的单一 role |
| 审计粒度（QUERY_HISTORY） | 真实用户名 | 真实用户名 | 服务用户 |
| 是否需要外部 IdP | 否 | 是 | 是 |
| Snowflake 安全集成 | TYPE = OAUTH，OAUTH_CLIENT = CUSTOM | TYPE = EXTERNAL_OAUTH + OAUTH_AUTHORIZATION_SERVER（用 ALTER ACCOUNT / DATABASE / SCHEMA 设置） | TYPE = EXTERNAL_OAUTH + OAUTH_AUTHORIZATION_SERVER（用 ALTER ACCOUNT / DATABASE / SCHEMA 设置） |
| 用户登录体验 | Snowflake 登录 + 同意 | 企业 SSO | 无（无用户交互） |
| MFA / 条件访问 | 按 Snowflake 账户设置 | 由 IdP 强制执行 | 不适用 |
| MCP 协议修订版¹ | 2025-11-25 | 2025-11-25 | 2025-11-25（在 2LO gateway 上未固定） |
| Token 生命周期治理 | Snowflake 安全集成 | IdP 授权服务器策略 | IdP 授权服务器策略 |
| 可无人值守运行（定时任务）² | 仅持续到 refresh token 过期（参考应用：1 天，最长 90 天） | 仅持续到 refresh token 过期（取决于 IdP 会话策略） | 是：无需用户交互。 |
| 最适合 | 需要在没有 IdP 的情况下实现按用户审计的 POC | 已有企业 SSO 的企业应用 | 内部 agent、批处理任务、服务间调用 |

¹ MCP 协议修订版：对于三足模式（模式 1 和模式 2），gateway 在其支持的 MCP 修订版中固定为 2025-11-25，这是 URL 模式 elicitation（-32042）握手所要求的。参考实现的 2LO gateway（模式 3）不固定该版本，因为 2LO 没有 elicitation 步骤。在未启用 MCP 版本更新的账户上，受支持的版本集合在 gateway 创建时就已固定。

² 可无人值守运行：模式 1 和模式 2 只能无人值守运行到 refresh token 过期为止。之后重新同意需要活跃的浏览器、同一个用户，并且要在 10 分钟的授权窗口（CompleteResourceTokenAuth）内完成，这就是 3LO 不适合完全无人值守的定时任务的原因。模式 3（2LO）没有 refresh token，也没有同意步骤，因此可以无限期无人值守运行。

本文的三种配置覆盖两种授权类型：authorization_code（模式 1 和模式 2）与 client_credentials（模式 3）。Amazon Bedrock AgentCore Identity 还支持 on-behalf-of（OBO）token 交换（TOKEN_EXCHANGE），它能为无人值守工作负载提供按用户身份，且*无需*同意提示。

OBO 把一个入站用户 token 换成保留真实用户身份的 Snowflake 范围 token，因此 QUERY_HISTORY 能把每条查询归因到真实用户，同时保持模式 3 那种无人值守、机器对机器的流程（没有浏览器重定向，没有同意界面）。在 Snowflake 侧，它使用与模式 2、模式 3 相同的 TYPE = EXTERNAL_OAUTH 集成（可选地用 OAUTH_AUTHORIZATION_SERVER 锁定 issuer）。在 AgentCore 侧，它在 OAuth 凭证提供商上通过 onBehalfOfTokenExchangeConfig 配置（对 Okta/RFC 8693 使用授权模式 TOKEN_EXCHANGE，对 Microsoft Entra 使用 JWT_AUTHORIZATION_GRANT）。OBO 走的是外部 OAuth 路径（模式 2 和模式 3）。

OBO 在 Amazon Bedrock AgentCore Identity 上已正式可用，但它超出了本文测试的这三种配置的范围。

## 结语

本文介绍了三种 OAuth 配置，用于通过 Amazon Bedrock AgentCore Gateway 在 MCP 上为 AI agent 认证访问 Snowflake Cortex AI。Snowflake OAuth 提供了通往按用户审计留痕的最简路径，且不依赖外部 IdP。使用外部 IdP 的三足 OAuth 增加了企业 SSO、集中式 MFA 和条件访问，同时保留按用户身份。使用外部 IdP 的两足 OAuth 则通过共享服务用户服务机器对机器的场景。

在这三种模式中，agent 代码与 Snowflake MCP 工具集保持不变。OAuth 的接线方式在四个具体方面不同：

- 授权类型切换：模式 1 和模式 2 用 authorization_code，模式 3 用 client_credentials。
- AUTHORIZATION_CODE 目标需要一个 return URL，它在目标上通过 defaultReturnUrl 设置，也可以在每次请求时覆盖。2LO 目标不需要。
- 3LO 目标在创建时要求隐式同步或预先提供工具 schema，而 2LO 目标在创建目标期间就同步其工具，没有用户授权步骤。
- 模式 2 和模式 3 可以设置 OAUTH_AUTHORIZATION_SERVER，把某个 MCP scope issuer 锁定到外部 IdP，并让直连 MCP 客户端自动发现它。模式 1 不设置该参数。设置之后，模式 1 和模式 2 无法共享同一个 scope，如前所述。

除此之外，只有 Amazon Bedrock AgentCore Identity 凭证提供商（CustomOauth2、OktaOauth2 或 MicrosoftOauth2）和 Snowflake 安全集成不同。理解了授权类型、token 签发、用户映射和审计行为上的这些差异，你就能针对自己的合规、运维和用户体验需求选出合适的 OAuth 配置。

要上手，请查看我们 [GitHub 仓库](https://github.com/aws-samples/aws-generativeai-partner-samples/tree/main/snowflake/amazon-bedrock-agentcore-snowflake-cortex-mcp)中的参考实现。想进一步了解 Amazon Bedrock AgentCore，请访问 [Amazon Bedrock AgentCore 服务详情页](https://aws.amazon.com/bedrock/agentcore/)或[开发者指南](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)。
