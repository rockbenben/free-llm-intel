# 通过 Amazon Bedrock AgentCore 保护 Snowflake Cortex AI 的 OAuth 模式

如今的企业需要一种清晰的方法将其身份验证和授权控制扩展到代理层，通常需要广泛的服务帐户权限或定制的身份验证集成，从而增加运营开销。当在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)（使用任何框架或模型大规模构建、连接和优化代理的平台）上运行的 AI 代理需要通过 [模型上下文协议](https://modelcontextprotocol.io/) 调用 [Snowflake 管理的 MCP 服务器](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-mcp)（将 [Snowflake Cortex 代理](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents) 作为其工具类型之一）时（MCP），企业首先要回答的问题是：代理商如何认证？在本文中，我们将介绍在 [Amazon Bedrock AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html)（Amazon Bedrock AgentCore 的一项功能）上测试的三种开放授权 (OAuth) 配置：Snowflake OAuth（每用户，无外部身份提供商或 IdP）、使用第三方身份提供商的三足 OAuth（企业单点登录或 SSO）以及使用第三方身份提供商的两足 OAuth（共享服务）用户）。 Amazon Bedrock AgentCore Identity 还支持代表 (OBO) 授权 (TOKEN_EXCHANGE)，无需同意提示即可为无人值守工作负载提供每用户身份。我们重点关注我们端到端测试的三种配置，并标记 OBO 适合的位置。最后，您将能够确定哪种模式适合您的企业场景。

## 解决方案概述

[Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 是 Amazon Bedrock AgentCore 的一项功能，可通过 MCP 服务器目标将 AI 代理连接到外部工具提供商。它的目标是 Sn​​owflake 管理的 MCP 服务器，该服务器将 Cortex Search 和 Cortex Analyst 作为 MCP 工具，MCP 感知的客户端可以发现和调用。网关不是充当包装器，而是将其配置的目标的功能聚合到一个统一的目录中，并将其作为一个工具/列表响应呈现给代理。

本文的核心焦点是 Amazon Bedrock AgentCore Gateway 的[出站身份验证](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-outbound-auth.html)：它如何获取 OAuth 令牌并将其呈现给 Snowflake 管理的 MCP 服务器。 Amazon Bedrock AgentCore Identity 充当凭证代理：网关通过调用 GetWorkloadAccessTokenForJWT 获取工作负载令牌（因为网关使用 JSON Web 令牌 (JWT) 入站身份验证），然后针对配置的提供程序调用 GetResourceOauth2Token。 AgentCore Identity 拥有令牌库、令牌刷新和用户到令牌绑定，并且它会自动获取、缓存和刷新令牌。

Amazon Bedrock AgentCore Identity 支持三种 OAuth 配置，涵盖两种授权类型（authorization_code 和 client_credentials）：

- [Snowflake OAuth](https://docs.snowflake.com/en/user-guide/oauth-snowflake-overview)：Snowflake 充当自己的 OAuth 授权服务器。每个用户通过授权代码授予 (3LO) 直接向 Snowflake 进行身份验证。不需要外部身份提供商。
- 使用第三方身份提供商的三足 OAuth：用户通过企业 SSO 使用授权代码授予进行身份验证。 Snowflake 通过其[外部 OAuth](https://docs.snowflake.com/en/user-guide/oauth-ext-overview) 安全集成信任 IdP 颁发的 JSON Web 令牌 (JWT)。
- 使用第三方 IdP 的两条腿 OAuth 模式：共享服务用户通过 IdP 的 client_credentials 授予进行身份验证。无需用户交互或同意，这对于机器对机器工作负载来说是理想的选择。

Amazon Bedrock AgentCore Identity 还提供 API 密钥凭证提供程序（支持 Snowflake 编程访问令牌）。我们在这里重点关注 OAuth 的每用户归因和自动令牌刷新。每个配置都使用 Amazon Bedrock AgentCore Identity（CustomOauth2、OktaOauth2 或 MicrosoftOauth2）中的凭证提供程序以及 Snowflake 端的相应安全集成。

**注意：** 我们使用 Okta 和 Microsoft Entra ID 通过 Snowflake 管理的 MCP 服务器测试了这些模式。模式 2 和 3（外部 IdP）遵循标准 OAuth 流程，因此它们可以扩展到其他受 OAuth 保护的 MCP 服务器，但会验证 SaaS 提供商的令牌声明、范围和受众设置。只有模式 1 是 Snowflake 特定的，因为它依赖于 Snowflake 的内置 OAuth 授权服务器。 Snowflake 特定的元素是 OAUTH_AUTHORIZATION_SERVER 颁发者锁定参数、session:role: / session:scope: 语法、BLOCKED_ROLES_LIST、LOGIN_NAME / EMAIL_ADDRESS 映射和 QUERY_HISTORY 属性。如果您的 SaaS 公开其自己的内部 OAuth 服务器，则您可以采用与 Snowflake OAuth 相同的方式配置出站 OAuth。

| **图案** | **OAuth 授予** | **AgentCore 身份凭证提供商供应商** | **雪花安全集成** | **雪花查询身份映射** |
| --- | --- | --- | --- | --- |
|雪花 OAuth – 3LO |授权码|自定义提供程序 (CustomOauth2) |类型 = OAUTH，OAUTH_CLIENT = 自定义 |真实用户及其分配的角色 |
|具有外部 IdP 的 3LO |授权码|内置提供程序（例如 OktaOauth2、MicrosoftOauth2）| TYPE = EXTERNAL_OAUTH + OAUTH_AUTHORIZATION_SERVER（使用 ALTER ACCOUNT / DATABASE / SCHEMA 设置）； EXTERNAL_OAUTH_TYPE = OKTA / AZURE / PING_FEDERATE / 自定义 |真实用户及其分配的角色 |
|具有外部 IdP 的 2LO |客户凭证 |内置提供程序（例如 OktaOauth2、MicrosoftOauth2）或 CustomOauth2 | TYPE = EXTERNAL_OAUTH + OAUTH_AUTHORIZATION_SERVER（使用 ALTER ACCOUNT / DATABASE / SCHEMA 设置）； EXTERNAL_OAUTH_TYPE = OKTA / AZURE / PING_FEDERATE / 自定义 |共享 Snowflake 服务用户 |

**笔记：**

- 2LO 不需要内置供应商。具有 CLIENT_CREDENTIALS 授予的 CustomOauth2 可以与您选择的 OAuth 2.0 授权服务器配合使用。
- 当 Amazon Bedrock AgentCore Gateway 代理令牌（本文中的模式）时，Snowflake 通过 TYPE = EXTERNAL_OAUTH 安全集成对其进行验证。设置 OAUTH_AUTHORIZATION_SERVER（使用 ALTER ACCOUNT、DATABASE 或 SCHEMA）可以让直接 MCP 客户端通过受保护的资源元数据端点自动发现您的 IdP，并且颁发者将 MCP 端点锁定到该集成。
- 如果您设置 OAUTH_AUTHORIZATION_SERVER 以将 MCP 范围锁定到外部 IdP（模式 2），则该范围内的 MCP 服务器将拒绝 Snowflake OAuth 令牌（模式 1），并且不会回退。如果您需要在一个帐户中使用两种模式，请为每个架构或数据库设置此参数，以便每个范围解析到正确的授权服务器。

## 模式分析

以下部分详细检查每种模式：身份验证流程、配置步骤和权衡，以帮助您为您的用例选择正确的方法。

### 模式1：雪花OAuth（三足）

Snowflake OAuth 模式使用三足 OAuth (3LO) 流程来提供每用户身份验证，无需外部身份提供程序。每个用户都使用自己的凭证向 Snowflake 进行身份验证，同意特定的 Snowflake 角色，并且 Amazon Bedrock AgentCore Identity 会缓存该用户的访问和刷新令牌。随后的每个 Snowflake 调用都以该用户身份执行，并且 QUERY_HISTORY 记录他们的真实用户名。请注意，每个角色的同意并不是默认的。 Snowflake 管理的 MCP 服务器通告 session:role:all 并回退到 DEFAULT_ROLE，因此您设置 OAUTH_SCOPES_SUPPORTED（使用 ALTER 设置的帐户、数据库或架构级别参数）以缩小服务器通告的角色范围，并限制集成上的 ALLOWED_ROLES_LIST 以强制用户可以同意哪些角色（PRE_AUTHORIZED_ROLES_LIST 执行相反的操作：它列出了跳过同意步骤的角色）。

这种模式的吸引力在于它的简单性：不需要外部身份提供者。 Snowflake 既充当授权服务器又充当资源服务器，公开其自己的内置 OAuth 端点（/oauth/authorize 和 /oauth/token-request）。安装程序遵循特定的顺序，因为在创建凭据提供程序之前回调 URL 不存在。管理员首先使用占位符客户端凭证在 Amazon Bedrock AgentCore Identity 中创建 CustomOauth2 凭证提供程序，并记录 AgentCore Identity 返回的回调Url。然后，该回调Url 将注册为使用 TYPE = OAUTH 和 OAUTH_CLIENT = CUSTOM 创建的 Snowflake 安全集成上的重定向 URI。最后，管理员使用 Snowflake 颁发的真实客户端 ID 和密钥更新凭证提供程序，并使用显式授权服务器元数据配置提供程序的 oauthDiscovery：颁发者（Snowflake 帐户 URL）、授权端点（/oauth/authorize）和令牌端点（/oauth/token-request）。

[Snowflake OAuth 授权流程](https://docs.snowflake.com/en/user-guide/oauth-snowflake-overview#snowflake-oauth-authorization-flow) 的工作原理如下：

- 当工具调用需要 Snowflake 令牌时，Amazon Bedrock AgentCore Gateway 通过调用 GetWorkloadAccessTokenForJWT 获取工作负载令牌，并调用 GetResourceOauth2Token 检查用户的 Amazon Bedrock AgentCore Identity 的令牌库。如果没有缓存令牌，网关将返回带有 URL 引出的 JSON-RPC 错误代码 [-32042](https://aws.amazon.com/blogs/machine-learning/connecting-mcp-servers-to-amazon-bedrock-agentcore-gateway-using-authorization-code-flow/)。该授权 URL 属于 AgentCore Identity，为 `session-URI-bound`。客户端在用户浏览器中打开该 URL，该 URL 被路由到 Snowflake 的内置授权服务器 (/oauth/authorize) 并显示 Snowflake 登录屏幕。
- 用户输入其 Snowflake 凭据，然后会看到一个同意屏幕，要求他们使用特定 Snowflake 角色（例如 ANALYST_ROLE）授权访问。请求范围中的角色名称必须为大写（例如，session:role:ANALYST_ROLE）。
- 经同意后，Snowflake 的授权服务器将授权代码返回到 Amazon Bedrock AgentCore Identity 的回调 URL。然后，AgentCore Identity 将用户的浏览器重定向到带有会话 URI 的返回 URL。
- AgentCore Identity 仅在应用程序使用用户身份和会话 URI 调用 CompleteResourceTokenAuth 后才完成代码交换（有效期 10 分钟）。此步骤将代码绑定到原始请求并阻止授权 URL 劫持。此处使用的返回 URL 是通过调用 UpdateWorkloadIdentity 注册的。在生产中，该 URL 处的端点由您的 Web 应用程序托管，或者对于具有 JWT 入站身份验证的网关，由 AgentCore 身份同意门户 (`<portal-url>/connect/callback`) 托管。 agentcore dev CLI 托管它仅用于本地开发。然后，AgentCore Identity 在 Snowflake 的令牌端点 (/oauth/token-request) 处交换代码以获取访问令牌和刷新令牌（可选）。
- 当客户端重试工具调用时，Amazon Bedrock AgentCore Gateway 会从 AgentCore Identity 检索缓存的访问令牌，并将其提供给 Snowflake 管理的 MCP 服务器。 Snowflake 验证令牌并创建一个范围仅限于同意的角色的用户会话。同意的范围仅控制**主要**角色。由于次要角色由集成控制，因此设置 OAUTH_USE_SECONDARY_ROLES = NONE（默认值），以便会话不能携带比同意的角色更多的权限，这是 IMPLICIT 设置允许的。

访问令牌是短暂的。默认情况下，它们持续 600 秒（最长 3600 秒）。当访问令牌过期时，Amazon Bedrock AgentCore Identity 会自动使用刷新令牌来获取新的访问令牌，无需用户交互。如果安全集成配置为防止刷新令牌，则用户必须通过同意屏幕重新授权。刷新令牌生命周期由 OAUTH_REFRESH_TOKEN_VALIDITY 控制。参考实现将其设置为 86400 秒（1 天），Snowflake 允许最多 90 天。 OAUTH_ISSUE_REFRESH_TOKENS（默认 TRUE）控制是否发出刷新令牌。

**注意：** 默认情况下，Snowflake 有助于防止 ACCOUNTADMIN、ORGADMIN、GLOBALORGADMIN 和 SECURITYADMIN 角色与 OAuth 集成一起使用。这由 Snowflake OAuth 的 BLOCKED_ROLES_LIST（以及外部 OAuth 的 EXTERNAL_OAUTH_BLOCKED_ROLES_LIST）控制，适用于所有三种模式，并且仅涵盖主要角色。使用 OAUTH_USE_SECONDARY_ROLES = IMPLICIT，辅助角色仍然可以承载这些特权角色。

#### 注意事项

Snowflake OAuth 模式是每用户审计跟踪的最简单路径。它不需要外部 IdP 配置，也不需要额外的供应商依赖性。它最适合以下场景：

- 用户已经拥有 Snowflake 凭据，并且可以轻松直接登录。
- 您希望 QUERY_HISTORY 中的每个用户归因无需外部身份提供商。
- 您正处于概念验证阶段，并且希望快速验证每用户模型。
- 合规性要求要求个人承担责任，因此每个查询必须可追溯到特定用户，而不是共享服务用户。
- 您更喜欢完全在 Snowflake 中管理用户生命周期（配置、取消配置、角色授予）。
- 您希望避免令牌声明映射的复杂性。 Snowflake 发行代币并确切地知道它们代表哪个用户。

### 模式 2：使用第三方身份提供商 (IdP) 的三足 OAuth (3LO)

此模式将每用户身份验证与企业单点登录相结合。用户通过外部 IdP 登录，该 IdP 强制执行多重身份验证 (MFA)、条件访问和会话策略。 IdP 颁发的 JWT 将提供给 Snowflake，Snowflake 通过其[外部 OAuth 安全集成](https://docs.snowflake.com/en/user-guide/oauth-ext-custom) 对其进行验证（可选地，颁发者通过 OAUTH_AUTHORIZATION_SERVER 锁定到 MCP 服务器的架构、数据库或帐户）。 Snowflake 通过 JSON Web 密钥集 (JWKS) 验证颁发者、受众和签名。然后，它将使用 EXTERNAL_OAUTH_TOKEN_USER_MAPPING_CLAIM 设置的可配置声明（[Okta](https://www.okta.com/) 的 sub，[Microsoft Entra ID](https://www.microsoft.com/en-us/security/business/microsoft-entra) 的 upn）映射到 Snowflake 用户的 LOGIN_NAME 或 EMAIL_ADDRESS（使用EXTERNAL_OAUTH_SNOWFLAKE_USER_MAPPING_ATTRIBUTE），并以该用户身份运行查询。安全集成参数值区分大小写。

与模式 1 的主要区别：授权服务器是您的公司 IdP（例如 Okta、Microsoft Entra ID），而不是 Snowflake。 Snowflake 仍然是资源服务器。用户使用与其他公司应用程序相同的凭据和策略进行身份验证。不需要单独的 Snowflake 密码。

在 Amazon Bedrock AgentCore 方面，Amazon Bedrock AgentCore Identity 为流行的身份提供商（例如，OktaOauth2 和 MicrosoftOauth2）提供内置凭证提供商供应商。与模式 1 中使用的通用 CustomOauth2 提供程序相比，这些供应商通过 IncludeOauth2ProviderConfig 接受客户端 ID、客户端密钥和 IdP 端点。Snowflake 管理的 MCP 服务器使用预先注册的 OAuth 客户端，因此您需要提前注册每个客户端 ID 和密钥，这就是需要创建、记录 callbackUrl、注册、更新序列的原因。

Snowflake的外部OAuth安全集成流程的工作原理如下：

- 当工具调用需要 Snowflake 令牌时，Amazon Bedrock AgentCore Gateway 通过调用 GetWorkloadAccessTokenForJWT 获取工作负载令牌，并调用 GetResourceOauth2Token 检查用户的 Amazon Bedrock AgentCore Identity 的令牌库。如果没有缓存令牌，网关将返回带有 URL 引出的 JSON-RPC 错误代码 -32042。该授权 URL 属于 AgentCore Identity，并且是 `session-URI-bound`，而不是 IdP。客户端在用户的浏览器中打开该 URL，AgentCore Identity 将用户路由到 IdP。
- 用户通过第三方 IdP 使用公司 SSO（包括 MFA）进行身份验证并同意所请求的范围。对于 Okta，角色范围采用 session:role:ANALYST_ROLE 形式。 Microsoft Entra ID 委托流使用 session:scope: 代替。
- IdP 将授权代码返回到 Amazon Bedrock AgentCore Identity 的回调 URL，AgentCore Identity 将用户的浏览器重定向到包含会话 URI 的返回 URL。仅当应用程序调用 CompleteResourceTokenAuth 来验证用户身份和会话 URI 后，AgentCore Identity 才会将代码交换为访问令牌（如果 IdP 颁发令牌，则还需要刷新令牌）并将其缓存在每用户令牌库中。
- 当客户端重试工具调用（以及以后的调用）时，Amazon Bedrock AgentCore Gateway 会从 Amazon Bedrock AgentCore Identity 检索缓存的 IdP 颁发的 JWT，并将其呈现给 Snowflake 管理的 MCP 服务器。 Snowflake 通过其外部 OAuth 集成验证令牌：它验证 JWKS 签名和受众 (aud) 声明，将配置的用户声明（Okta 的 sub，Microsoft Entra ID 的 upn）映射到 Snowflake 用户，并作为经过身份验证的用户执行查询。 Snowflake 不会在运行时调用 IdP。它使用 IdP 发布的 JWKS 签名密钥在本地验证令牌。
- 当访问令牌过期时，Amazon Bedrock AgentCore Identity 会使用缓存的刷新令牌（如果已颁发）自动刷新它（对于 Okta，请求离线访问范围）。在刷新令牌过期之前不需要用户交互。

令牌生命周期治理：与 Snowflake 控制令牌生命周期的模式 1 不同，访问令牌和刷新令牌生命周期由 IdP 控制，并且 Amazon Bedrock AgentCore Identity 透明地处理刷新。如果颁发了刷新令牌，则用户仅在令牌过期时根据 IdP 的会话策略重新进行身份验证。否则，用户将在访问令牌过期时重新进行身份验证。

#### 注意事项

在以下情况下选择使用第三方 IdP 的三足 OAuth (3LO)：

- 您的组织或安全团队要求所有身份验证都通过公司 SSO 进行，以实现集中式 MFA、条件访问和会话管理。
- 您想要使用现有的 IdP 功能，例如基于组的角色映射、会话超时策略和基于地理位置的条件访问规则。
- 您需要 Snowflake 的 QUERY_HISTORY 中的每个用户审计跟踪。
- 您希望在所有应用程序（包括 AI 代理）中实施统一的安全策略。
- 您需要集中访问控制。在 IdP 中禁用用户有助于防止新的 Snowflake 授权，尽管缓存的令牌在过期之前仍然有效。要强制用户重新授权，应用程序可以在下一个请求中传递forceAuthentication=true，这会清除存储的刷新令牌并启动新的授权流程。要彻底撤销访问权限，请在 IdP 或 Snowflake 中撤销授予。

### 模式 3：使用第三方身份提供商 (IdP) 的两条腿 OAuth (2LO)

两条腿 OAuth 模式使用 OAuth 2.0 client_credentials 授予。这是一个没有用户交互的机器对机器的流程。 Amazon Bedrock AgentCore Identity 使用配置的客户端 ID 和客户端密钥从 IdP 获取 JWT，Amazon Bedrock AgentCore Gateway 将其提供给 Snowflake，Snowflake 在共享服务用户下执行请求，无论哪个最终用户发起查询。

这种模式在操作上是最直接的：没有同意屏幕，没有每用户令牌库，没有浏览器重定向。用户遵循相同的代码路径。 Amazon Bedrock AgentCore Identity 自动获取并缓存 client_credentials 令牌，并且 Amazon Bedrock AgentCore Gateway 在对 Snowflake 管理的 MCP 服务器的每次出站调用时都会显示该令牌。

与模式 1 和 2 的主要区别：不存在每用户身份传播。 Snowflake 的 QUERY_HISTORY 记录单个服务用户的查询。权衡是以每个用户审计粒度为代价的操作简单性。在 Amazon Bedrock AgentCore 端，凭证提供程序使用 client_credentials 授予类型：内置供应商（OktaOauth2、MicrosoftOauth2）或通用 CustomOauth2 提供程序。配置需要 IdP 的令牌端点、客户端 ID 和客户端密钥。 Amazon Bedrock AgentCore Identity 在第一次工具调用时（当网关调用 GetResourceOauth2Token 时）从 IdP 获取令牌，将其缓存，并且由于 client_credentials 不发出刷新令牌，因此会在到期前请求新的令牌。无需更改代理级别的代码。

![2LO 客户端凭据流的序列图：AgentCore Identity 从 Okta 或 Microsoft Entra ID 请求令牌，无需用户步骤，Snowflake 对其进行验证并以共享服务用户身份运行查询。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/16/ML-21095-10-2.png)

图 10：具有外部 IdP 运行时授权流程的 2LO：具有 CLIENT_CREDENTIALS 授予和第三方 IdP 出站身份验证的 Amazon Bedrock AgentCore Gateway MCP 服务器目标

Snowflake 的外部 OAuth 安全集成 2LO 流程的工作原理如下：

- 当工具调用需要 Snowflake 令牌时，Amazon Bedrock AgentCore Gateway 通过调用 GetWorkloadAccessTokenForJWT 获取工作负载令牌，并在 Amazon Bedrock AgentCore 身份凭证提供程序上调用 GetResourceOauth2Token。如果缓存了有效令牌，Identity 会立即返回它。
- Amazon Bedrock AgentCore Identity 使用 client_credentials 授予以及配置的客户端 ID 和客户端密钥来调用第三方 IdP 的令牌终端节点。对于 Okta，请求的范围包括 Snowflake 角色（例如，session:role:MCP_GATEWAY_ROLE）。对于 Microsoft Entra ID，客户端请求 api:`//<application-id>/.default` 范围，并且角色从值为 session:role:MCP_GATEWAY_ROLE 的应用程序角色到达角色声明中。
- IdP 返回一个访问令牌（JWT，没有刷新令牌），其 aud 声明是 Snowflake 帐户 URL 或 EXTERNAL_OAUTH_AUDIENCE_LIST 中列出的附加值（对于 Microsoft Entra ID，通常是应用程序 ID URI）。对于 Okta，子声明是客户端 ID。对于 Microsoft Entra ID，客户端 ID 在 appid/azp 中携带，而 sub 保存服务主体的对象 ID（GUID），因此对于 Entra，LOGIN_NAME 必须映射到该 GUID。
- Amazon Bedrock AgentCore Gateway 将 JWT 呈现给 Snowflake 管理的 MCP 服务器。 Snowflake 通过其外部 OAuth 集成验证令牌（可以选择使用 OAUTH_AUTHORIZATION_SERVER 锁定发行者，如模式 2 所示）。它通过 EXTERNAL_OAUTH_JWS_KEYS_URL（或 EXTERNAL_OAUTH_RSA_PUBLIC_KEY）验证签名，通过 EXTERNAL_OAUTH_ISSUER 验证颁发者，以及针对 Snowflake 帐户 URL 的 aud 声明以及 EXTERNAL_OAUTH_AUDIENCE_LIST 中的任何其他值（这些安全集成参数值区分大小写）。然后，Snowflake 通过 LOGIN_NAME 将子声明映射到 Snowflake 服务用户，并在该服务用户的角色下执行查询。与模式 2 一样，Snowflake 在本地验证令牌，并且不会在运行时调用 IdP。
- Amazon Bedrock AgentCore Identity 将令牌缓存在令牌库中（跨用户共享，而不是每个用户共享）。后续调用会重用它，并且 Identity 在过期之前使用 client_credentials 授予请求一个新令牌。

由于两条腿 OAuth 目标不需要用户同意，因此 Amazon Bedrock AgentCore Gateway 在目标创建时连接到 Snowflake 管理的 MCP 服务器，并在目标创建期间通过隐式同步发现工具。在三足 OAuth 模式（模式 1 和 2）中，网关目标支持两种创建方法：(1) 管理员完成授权代码流，以便通过隐式同步发现工具，或者 (2) 管理员预先提供工具架构。 （发现行为是目标的 ListingMode 属性，而不是授权类型的属性。）

#### 注意事项

两条腿的 OAuth 模式是自动化、无人值守和批量工作负载的首选。它在以下情况下是理想的：

- 您的工作负载是机器对机器的：计划作业、后台管道或系统级代理，循环中无人参与。
- 不需要每个用户的身份，并且共享服务用户可以用于审计目的。
- 您需要最直接的操作模型：无同意流程、每用户令牌管理或浏览器重定向。
- 网关可以连接到 Snowflake 并通过在目标创建时隐式同步来发现 MCP 工具，而无需等待用户交互。
- 所有用户在单个 Snowflake 角色下共享相同的数据访问权限。

**接受这些权衡：**

- 由于每个请求都以共享服务用户身份运行，因此 Snowflake 的行级安全性和列屏蔽策略会将该用户的权限应用于请求。以 CURRENT_USER() 和 CURRENT_ROLE() 为关键的策略全部解析为该单个服务用户及其一个角色，这是代表 (OBO) 方法的最有力的情况。
- 没有用户级令牌撤销。要切断访问，请撤销 IdP 处的客户端凭据或禁用 Snowflake 安全集成。
- 如果凭据遭到泄露，代理访问就会受到影响。定期轮换客户端机密并将服务用户限制为最低权限访问。

## 模式比较

| **方面** | **模式 1：雪花 OAuth (3LO)** | **模式 2：具有外部 IdP 的 3LO** | **模式 3：具有外部 IdP 的 2LO** |
| --- | --- | --- | --- |
| OAuth 授权类型 |授权码|授权码|客户凭证 |
| AgentCore 身份提供商 |自定义提供程序 (CustomOauth2) |内置提供程序（例如，OktaOauth2 或 MicrosoftOauth2）|内置提供程序（例如 OktaOauth2、MicrosoftOauth2）或 CustomOauth2 |
|授权服务器| Snowflake内置OAuth |第三方 IdP（例如 Okta、Entra ID）|第三方 IdP（例如 Okta、Entra ID）|
|雪花可见的身份 |真实用户|真实用户|共享服务用户|
| RBAC模型|每用户 Snowflake 角色 |每用户 Snowflake 角色 |请求的单一角色 |
|审核粒度 (QUERY_HISTORY) |真实用户名 |真实用户名 |服务用户|
|需要外部 IdP |没有 |是的 |是的 |
|雪花安全集成 |类型 = OAUTH，OAUTH_CLIENT = 自定义 | TYPE = EXTERNAL_OAUTH + OAUTH_AUTHORIZATION_SERVER（使用 ALTER ACCOUNT / DATABASE / SCHEMA 设置）| TYPE = EXTERNAL_OAUTH + OAUTH_AUTHORIZATION_SERVER（使用 ALTER ACCOUNT / DATABASE / SCHEMA 设置）|
|用户登录体验 |雪花登录+同意|企业单点登录 |无（无用户交互）|
| MFA / 条件接收 |每个 Snowflake 帐户设置 |由 IdP 强制执行 |不适用 |
| MCP 协议修订 1 | 2025年11月25日 | 2025年11月25日 | 2025-11-25（未固定在 2LO 网关上）|
|代币生命周期治理 |雪花安全集成 | IdP 授权服务器策略 | IdP 授权服务器策略 |
|无人值守工作（预定工作）² |仅直到刷新令牌过期为止（参考应用：1 天，最长 90 天）|仅在刷新令牌过期之前（根据 IdP 会话策略）|是：无需用户交互。 |
|最适合 |在没有 IdP 的情况下需要按用户审核的 POC |具有现有企业 SSO 的企业应用程序 |内部代理、批处理作业、服务到服务 |

1 MCP 协议修订版：对于三足模式（模式 1 和 2），网关在其支持的 MCP 修订版中引脚 2025-11-25，这是 URL 模式引出 (-32042) 握手所需要的。参考 2LO 网关（模式 3）不会固定它，因为 2LO 没有引发步骤。对于未启用 MCP 版本更新的帐户，支持的集在创建网关时是固定的。

² 无人值守工作：模式 1 和 2 仅在刷新令牌过期之前无人值守运行。然后，重新同意需要实时浏览器、同一用户，并在 10 分钟授权窗口内完成 (CompleteResourceTokenAuth)，这就是 3LO 不适合完全无人值守的计划作业的原因。模式 3 (2LO) 没有刷新令牌，也没有同意步骤，因此它无限期地在无人值守的情况下运行。

本文中的三个配置涵盖两种授权类型：authorization_code（模式 1 和 2）和 client_credentials（模式 3）。 Amazon Bedrock AgentCore Identity 还支持代表 (OBO) 令牌交换 (TOKEN_EXCHANGE)，它可以为无人值守工作负载提供每用户身份，*无需*同意提示。

OBO 将入站用户令牌交换为保留真实用户身份的 Snowflake 范围令牌，因此 QUERY_HISTORY 将每个查询归因于实际用户，同时保持模式 3 的无人值守、机器到机器流程（无浏览器重定向、无同意屏幕）。在 Snowflake 方面，它使用与模式 2 和 3 相同的 TYPE = EXTERNAL_OAUTH 集成（可以选择使用 OAUTH_AUTHORIZATION_SERVER 锁定发行者）。在 AgentCore 端，它通过 onBehalfOfTokenExchangeConfig 在 OAuth 凭据提供程序上进行配置（Okta/RFC 8693 的授予模式为 TOKEN_EXCHANGE，或者 Microsoft Entra 的授予模式为 JWT_AUTHORIZATION_GRANT）。 OBO 使用外部 OAuth 路径（模式 2 和 3）。

OBO 通常可在 Amazon Bedrock AgentCore Identity 上使用，但它超出了我们在本文中测试的三种配置的范围。

＃＃ 结论

在这篇文章中，我们介绍了三种 OAuth 配置，用于通过 Amazon Bedrock AgentCore Gateway 对 MCP 上的 Snowflake Cortex AI 进行 AI 代理身份验证。 Snowflake OAuth 提供了最简单的每用户审核跟踪路径，无需外部 IdP 依赖。具有外部 IdP 的三足 OAuth 添加了企业 SSO、集中式 MFA 和条件访问，同时保留每个用户的身份。具有外部 IdP 的两条腿 OAuth 通过共享服务用户提供机器对机器服务。

在所有三种模式中，代理代码和 Snowflake MCP 工具集保持不变。 OAuth 连接在四个具体方面有所不同：

- 授权类型翻转：模式 1 和 2 的授权码，模式 3 的 client_credentials。
- AUTHORIZATION_CODE 目标需要一个返回 URL，在目标上设置为 defaultReturnUrl，并可选择根据请求覆盖。 2LO 目标不需要。
- 3LO 目标创建需要隐式同步或前期工具模式，而 2LO 目标在目标创建期间同步其工具，无需用户授权步骤。
- 可以为模式 2 和 3 设置 OAUTH_AUTHORIZATION_SERVER，以将 MCP 范围锁定到外部 IdP，并让直接 MCP 客户端自动发现它。对于模式 1，它未设置。设置后，模式 1 和模式 2 不能共享同一个范围，如前所述。

除了这四个之外，只有 Amazon Bedrock AgentCore Identity 凭证提供程序（CustomOauth2、OktaOauth2 或 MicrosoftOauth2）和 Snowflake 安全集成有所不同。了解授权类型、令牌颁发、用户映射和审核行为方面的这些差异，使您能够根据合规性、操作和用户体验需求选择正确的 OAuth 配置。
