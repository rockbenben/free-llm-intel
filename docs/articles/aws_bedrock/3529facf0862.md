# 使用 Amazon Bedrock 为医疗健康 API 构建智能安全防护

如果你管理 [Fast Healthcare Interoperability Resources（FHIR）](https://www.hl7.org/fhir/) API，就必须在开放的患者数据访问与严格的数据保护要求之间取得平衡。静态安全规则会随着临床工作流的演进而需要不断更新，而人工维护它们会造成合规缺口。借助 [Amazon Bedrock](https://aws.amazon.com/bedrock/)——一个通过单一 API 提供基础模型（FM）访问的全托管服务——你可以为医疗健康 API 构建智能安全防护。这种安全防护会监控访问模式、自动分类数据敏感度，并以自然语言生成合规报告。这一方法有助于减少文档工作量、减少人工规则维护，并让你的安全监控随临床工作流的变化而调整。

在本文中，你将了解如何使用 Amazon Bedrock 为 FHIR API 添加具备上下文感知能力的安全监控。首先，我们介绍一种把安全监控与 FHIR API 请求路径分离的架构，这样你就能在不影响 API 延迟的情况下加入行为分析。然后，我们演示如何使用 Amazon Bedrock 与 Structured Outputs 实现异常检测，从而捕捉静态规则遗漏的访问模式。接着，我们演示自动化的数据敏感度分类，它免去了硬编码映射表的需要。最后，我们展示如何以自然语言生成合规报告，缩短审计准备时间。该解决方案使用 [AWS Lambda](https://docs.aws.amazon.com/lambda/)、[Amazon API Gateway](https://docs.aws.amazon.com/apigateway/)、[AWS HealthLake](https://docs.aws.amazon.com/healthlake/)、[Amazon EventBridge](https://aws.amazon.com/eventbridge/)、[Amazon Cognito](https://docs.aws.amazon.com/cognito/)、[Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 和 [Amazon Comprehend Medical](https://docs.aws.amazon.com/comprehend-medical/)。它还附带一个[配套代码示例](https://github.com/aws-samples/sample-intelligent-security-for-healthcare-apis)，其中包含完整的 AWS CloudFormation 模板、五个 AWS Lambda 函数，以及你可针对自身环境调整的部署脚本。

## 前提条件

要部署该解决方案，你需要：

- 一个具有管理员访问权限的有效 AWS 账户。
- 已安装并配置好的 AWS Command Line Interface（AWS CLI）v2（`aws configure`）。
- Amazon Bedrock 现在会自动授予对受支持模型的访问权限。请查看 [Amazon Bedrock 模型访问](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)页面，确认这些模型在你的 AWS 区域中可用。
- 一个经过验证的电子邮件地址，用于接收 Amazon Simple Notification Service（Amazon SNS）的安全告警通知。
- 如果你的 AWS 账户从未使用过与 Amazon CloudWatch Logs 集成的 Amazon API Gateway，你必须先在账户的 API Gateway 设置中设置 CloudWatch Logs 角色 ARN。否则部署会失败并提示“CloudWatch Logs role ARN must be set in account settings.”。相关说明请参阅[在 API Gateway 中设置 CloudWatch API 日志记录](https://docs.aws.amazon.com/apigateway/latest/developerguide/set-up-logging.html#set-up-access-logging-using-console)。
- 预计部署时间：10–15 分钟。预计每月成本因使用量而异。当前费率请参阅 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)页面。AWS HealthLake 的费用另行计算。

## 架构概览

你可以看清是谁在访问 FHIR 数据，以及这种访问看起来是否正常。[Amazon Bedrock](https://docs.aws.amazon.com/bedrock/) 中的基础模型会结合用户的历史行为、角色以及所请求数据的敏感度来评估每一个请求。最终得到的是一份用通俗语言表述、可供你采取行动的风险评估。

你现有的授权控制仍然保留。你继续通过 [AWS Lambda](https://docs.aws.amazon.com/lambda/) 授权方强制执行基于角色的访问控制（RBAC），并校验 JSON Web Token（JWT）——即用于证明用户身份的一种签名 token。在此之上，你还获得了行为分析能力，可以捕捉静态规则无法发现的模式。例如，某个用户在自身权限范围内访问数据，但访问量或访问时间异常，就会触发告警。

下图展示了安全监控如何与主 API 路径分开运行，因此它不会给临床工作流增加延迟。

图 1：由 Amazon Bedrock 驱动的 FHIR API 安全监控系统架构

“先请求、后分析”的流程是这样的。[Amazon API Gateway](https://docs.aws.amazon.com/apigateway/) 接收传入的 FHIR 请求，并执行限流与请求校验。AWS Lambda 授权方校验 JWT，并检查存储在 [Amazon DynamoDB](https://docs.aws.amazon.com/dynamodb/) 中的细粒度权限。

随后，[AWS HealthLake](https://docs.aws.amazon.com/healthlake/) 以符合 HIPAA 要求的全托管 FHIR R4 数据存储形式提供 FHIR 数据。FHIR 处理器 AWS Lambda 函数捕获访问详情，并通过 Amazon EventBridge 把它们路由到三个异步 AWS Lambda 函数：异常分析器、敏感度分类器和合规报告器。每个函数都通过一个 Amazon Bedrock Guardrails 资源调用 Amazon Bedrock，该资源会对 prompt 和响应中的受保护健康信息（PHI）进行匿名化处理。异常分析器在写入审计日志之前，还会额外使用 Amazon Comprehend Medical 脱敏 PHI。Amazon CloudWatch 会在整个流程中捕获结构化日志，用于形成审计线索。

你可以受益于完全异步的分析。在 FHIR 响应已经返回给客户端之后，Amazon EventBridge 才把访问事件路由到分析器 AWS Lambda 函数。你的 API 延迟不受影响，同时仍能获得持续的安全监控。

如果分析器暂时不可用，FHIR API 仍会照常处理请求。监控层不会阻塞临床工作流。

## HIPAA 防护措施

该解决方案实现了多层 PHI 保护，防止受保护的健康信息从监控流水线中泄露：

- **Amazon Bedrock Guardrails –** 随 AWS CloudFormation 模板部署了 `AWS::Bedrock::Guardrail` 资源。它会检测并匿名化发送给 Amazon Bedrock 的 prompt 以及模型响应中的个人可识别信息（PII）实体（姓名、社会安全号码、地址、电话号码、病历号）。SSN 和护照号会被完全阻止，而不是匿名化。
- **Amazon Comprehend Medical** – 在把 Amazon Bedrock 的响应写入 Amazon CloudWatch Logs 之前，异常分析器会先把文本通过 Amazon Comprehend Medical 中的 `DetectPHI` API 处理。检测到的 PHI 实体会被替换为类型标签（例如 `[NAME]`、`[DATE]`），这样审计日志既对合规审查有用，又不包含真实的患者数据。
- **IP 泛化 –** 异常分析器的 prompt 从不会把原始 IP 地址发送给 Amazon Bedrock。取而代之的是，它根据 RFC 1918 地址段把来源归类为“内部”或“外部”，从而防止 PII 进入模型上下文。
- **不含 PHI 的告警 –** 当异常分析器触发 Amazon SNS 告警时，通知中只包含一个经过哈希处理的参考 ID 和风险等级。安全团队使用该参考 ID 从审计日志中获取完整细节，这有助于避免电子邮件通知中包含 PHI。
- **Structured Outputs –** 本解决方案中的 Amazon Bedrock 调用使用 Structured Outputs，配合 JSON schema 与受枚举约束的字段（字段被限定为一组固定的有效值）。这减少了自由文本解析，并有助于确认模型响应符合可预期的格式，从而降低意外 PHI 出现在下游处理中的风险。
- **净化后的错误消息 –** FHIR API 的错误响应只向客户端返回通用消息，而不是内部异常细节，因为后者可能无意中包含来自 AWS HealthLake 响应的患者数据。

## 使用 Amazon Bedrock 进行异常检测

通过分析多样化的临床用户群体中的行为模式，你可以检测出基于规则的系统会遗漏的复杂访问异常。分析器 AWS Lambda 函数是这一架构的核心。每一次 API 调用都会生成一个访问事件，基础模型会结合用户的角色、访问历史和请求的性质来评估该事件。

设想一位医生通常在工作时间访问 5–15 份患者记录。如果同一位医生在凌晨 3 点下载 500 份记录，静态规则就需要为每一种角色与时间的组合设定明确阈值。借助 Amazon Bedrock，你可以评估完整的上下文，并获得附带通俗语言解释的风险评估。

临床用户群体是多样化的：医生、护士、计费人员、研究人员以及第三方集成。每个群体都有不同的正常访问模式，而且这些模式会随时间推移而变化。一位开展回顾性研究的研究人员可能确实会在单次会话中合法访问数千条记录。基础模型会通过考察用户的角色、请求的性质以及访问是否遵循正常的身份验证模式，把这种情况与未授权访问区分开来。

异常检测构建的是每个用户的行为基线，而不是套用群体层面的阈值。这种方法降低了系统性地标记夜班临床人员、国际研究人员或随叫随到医生合法访问模式的风险，因为他们经常在标准工作时间之外操作。

不同类型的调用方具有不同的风险特征。SMART on FHIR 应用、患者门户以及健康信息交换（HIE）连接各自都有独特的预期行为。访问事件中包含 OAuth `client_id`，因此分析器可以维护针对具体应用的基线，并根据集成类型施加差异化的风险评分。

组织还可以用临床上下文进一步丰富访问事件，例如值班表、急诊科启动状态或护理团队分配。例如，在群体伤亡事件期间，一位医生在凌晨 3 点访问 500 份记录，不应与平常夜班里同样的模式触发相同的风险评估。prompt 设计在上下文可用时会容纳这些额外信息。

本实现采用 fail-open（故障开放）方式。fail-open 意味着如果分析器遇到错误，它会记录失败，但不会阻塞原始 API 请求。我们选择这种方式而非 fail-closed（故障关闭）方式（后者会在出错时阻塞请求），因为分析器故障不应给临床工作流带来可用性问题。在监控层恢复期间，FHIR API 会继续正常处理请求。

异常分析器使用 Amazon Bedrock Converse API 与 Structured Outputs，强制遵循一个 JSON schema，其中的风险等级受枚举约束（LOW、MEDIUM、HIGH）。Amazon Bedrock Guardrails 资源会匿名化 prompt 与响应中的 PHI，Amazon Comprehend Medical 会在写入审计日志之前脱敏 PHI。对于 HIGH 风险事件，Amazon SNS 会发送一条不含 PHI 的告警，其中只包含经过哈希处理的参考 ID。完整实现请参阅配套代码示例中的 `anomaly_analyzer/handler.py`。

## 数据敏感度分类

FHIR 资源的敏感度各不相同。一条心理健康领域的 Observation 比一次常规血压测量的敏感度更高。某些临床数据类型，例如药物滥用治疗记录，可能需要根据适用法规采取额外防护措施。请注意，敏感度分类为访问决策提供依据，但并不能替代同意管理，后者应按你组织的策略实施。

使用 Amazon Bedrock，你可以在没有硬编码映射表的情况下按敏感度等级对 FHIR 资源分类。当资源在 [AWS HealthLake](https://docs.aws.amazon.com/healthlake/) 中被创建或更新时，一条 Amazon EventBridge 规则会触发分类函数。该函数把资源元数据发送给 Amazon Bedrock，由它评估资源类型、临床代码和类别，然后赋予一个敏感度等级：PUBLIC、INTERNAL、CONFIDENTIAL 或 RESTRICTED。

例如，Amazon Bedrock 会把带有血糖 Logical Observation Identifiers Names and Codes（LOINC）代码（`2345-7`）的 Observation 归类为 INTERNAL，而把带有 HIV 检测结果代码（`7018-2`）的 Observation 归类为 RESTRICTED。模型是根据代码的临床含义作出这一区分的。当出现新的代码系统或资源类别时，分类会自动适应，无需改动代码。

Amazon DynamoDB 会把分类结果与资源 ID 一同存储。当用户请求该资源时，AWS Lambda 授权方会在授予访问权限之前，检查用户的权限等级是否与资源的分类相匹配。这就在标准 RBAC 之上为你提供了一个动态的、内容感知的授权层。

对于分类任务，你使用 Amazon Bedrock 上 Anthropic 的 Claude Haiku 4.5 基础模型（FM），它可以保持低延迟和最低成本。对于更复杂的访问模式分析——准确性比速度更重要——你使用 Amazon Bedrock 上 Anthropic 的 Claude Sonnet 4.5 FM。对于一个每月处理 100,000 次 FHIR API 调用的组织，预期 Amazon Bedrock 成本在几十美元的量级，具体取决于 prompt 长度和模型选择。当前的按 token 定价请参阅 [Amazon Bedrock 定价页面](https://aws.amazon.com/bedrock/pricing/)。你可以在 [AWS Billing and Cost Management 控制台](https://aws.amazon.com/aws-cost-management/)中监控用量与成本。

敏感度分类器使用 Structured Outputs，并限定一组固定的有效值（PUBLIC、INTERNAL、CONFIDENTIAL、RESTRICTED），以保证分类结果有效。如果分类失败，该函数会默认归为 CONFIDENTIAL（fail-secure，故障安全）。请参阅配套代码示例中的 `sensitivity_classifier/handler.py`。

## 合规报告

医疗健康审计需要记录谁访问了哪些数据、何时访问以及为何访问。安全团队通常要花几天时间汇总日志、交叉核对用户活动并撰写叙述性摘要。使用 Amazon Bedrock，你可以自动把原始访问日志转化为可读的合规报告。

一个按计划运行的 [AWS Lambda](https://docs.aws.amazon.com/lambda/) 函数通过 Amazon EventBridge Scheduler 每月执行一次。它检索报告周期内的访问日志，并连同生成合规摘要的指令一起发送给 Amazon Bedrock。输出内容包括按资源类型统计的请求总数、按角色拆分的唯一用户活动、被标记的访问事件及其处理结果，以及改进安全态势的建议。

prompt 会指示基础模型按安全控制类别（管理、物理和技术）组织报告。这种结构有助于安全团队系统性地审查发现的问题。每个被标记的事件都包含原始风险评估、处理状态和已采取行动的时间线。

这种方法把日志汇总、交叉核对和叙述撰写这些人工步骤自动化，减少了合规团队在每份报告上花费的时间。

合规报告器使用 Structured Outputs，其 schema 把每个章节映射到一个安全控制类别。报告会以 AWS Key Management Service（AWS KMS）加密保存到 Amazon Simple Storage Service（Amazon S3），并在一年后归档到 Amazon S3 Glacier。请参阅配套代码示例中的 `compliance_reporter/handler.py`。

## 清理

为避免持续产生费用，请在完成测试后删除该解决方案创建的资源。从配套代码示例运行清理脚本：`./src/scripts/cleanup.sh dev us-east-1`。该脚本会删除由 AWS CloudFormation 管理的资源，包括 API Gateway REST API、全部五个 AWS Lambda 函数、两个 Amazon DynamoDB 表、Amazon EventBridge 事件总线与规则、Amazon Cognito 用户池、Amazon SNS 主题、Amazon S3 合规报告存储桶以及 Amazon CloudWatch 日志组。如果你为端到端测试单独创建了 AWS HealthLake 数据存储，请手动删除它。AWS HealthLake 在运行期间约每小时收费 $0.694（约每月 $500）。

## 结论

你现在拥有一个概念验证级别的安全监控模式，它可以随着访问模式的变化而适应你的环境。在本文中，你了解了如何使用 [Amazon Bedrock](https://docs.aws.amazon.com/bedrock/) 基础模型来检测异常访问模式、自动分类数据敏感度等级，并以自然语言生成安全审计报告。

如果你在评估这一方法，请先阅读本文中的架构图与代码示例。浏览 [Amazon Bedrock 用户指南](https://docs.aws.amazon.com/bedrock/)以了解基础模型能力，并查阅 [AWS HealthLake 用户指南](https://docs.aws.amazon.com/healthlake/)以评估 FHIR R4 数据管理如何契合你的环境。

如果你已准备好部署，请按以下步骤操作：

- 运行 `aws configure` 设置你的 AWS 凭证和目标 AWS 区域（例如 `us-east-1`）。确认目标区域中可以使用 Anthropic 的 Claude Sonnet 4.5 和 Anthropic 的 Claude Haiku 4.5。
- 运行部署脚本：`./src/scripts/deploy.sh your-email@example.com dev us-east-1`。该脚本会打包 Lambda 代码、把它上传到 Amazon S3，并部署带有所需基础设施（Amazon API Gateway、AWS Lambda 函数、Amazon DynamoDB 表、Amazon EventBridge 规则、Amazon Cognito、Amazon SNS、Amazon S3 以及 Amazon Bedrock Guardrails 资源）的 AWS CloudFormation 堆栈。请查看你的电子邮件并确认 Amazon SNS 订阅。
- 调整异常分析器和敏感度分类器 AWS Lambda 函数中的 prompt，使其匹配组织的风险容忍度、临床角色和数据敏感度定义。
- （可选）创建一个 AWS HealthLake 数据存储用于端到端测试。请注意 AWS HealthLake 约每小时收费 $0.694，因此只在积极测试时创建并及时删除。然后通过 Amazon EventBridge 发送测试事件，并查看各个 Lambda 函数的 Amazon CloudWatch Logs 来验证端到端流程。

部署完成后，通过发送具有不同模式的 FHIR API 请求来测试异常检测：

- 通过在非正常时段请求大量记录来模拟异常访问模式。使用有效的 JWT token 向你的 API Gateway 端点发送一个请求 500 个 Patient 资源的 GET 请求。异常分析器应将其标记为 MEDIUM 或 HIGH 风险。
- 通过在工作时间请求少量记录来模拟正常访问模式。分析器应赋予 LOW 风险等级。
- 模拟一次跨角色访问尝试，例如计费用户请求实验室 Observation 等临床数据。这会检验模型是否能识别角色与资源之间的不匹配。

每次测试后，查看异常分析器 Lambda 函数的 Amazon CloudWatch Logs，并确认 Amazon SNS 已为 HIGH 风险事件投递告警。配套代码示例中的 `README` 包含每个测试场景的具体 API 端点和 `curl` 命令。

如果你已经在生产环境中运行 FHIR API，可以把这一监控层与现有的 [Amazon API Gateway](https://docs.aws.amazon.com/apigateway/) 和 [AWS Lambda](https://docs.aws.amazon.com/lambda/) 授权方一起集成，而无需修改请求路径。把异步的 Amazon EventBridge 到 Bedrock 流程作为并行监控通道加入，并调整 prompt 以反映组织特定的角色定义和风险特征。

要进一步扩展该解决方案，可以考虑把 Amazon SNS 告警与现有的安全信息和事件管理（SIEM）工具集成，以实现集中监控。你还可以为常见的医疗健康场景添加 prompt 模板，例如研究数据访问审查、紧急破窗（break-the-glass）覆盖以及批量数据导出风险评估。你也可以调整 prompt 以反映组织特有的风险特征，或者通过调整 [AWS Lambda](https://docs.aws.amazon.com/lambda/) 的并发设置和 [Amazon DynamoDB](https://docs.aws.amazon.com/dynamodb/) 的吞吐量，为高流量环境扩展该架构。

如需更深入的指引，请参阅 [Amazon Bedrock 用户指南](https://docs.aws.amazon.com/bedrock/)、[AWS HealthLake 用户指南](https://docs.aws.amazon.com/healthlake/)、[Amazon API Gateway 开发人员指南](https://docs.aws.amazon.com/apigateway/)以及 [Amazon CloudWatch 用户指南](https://docs.aws.amazon.com/cloudwatch/)。
