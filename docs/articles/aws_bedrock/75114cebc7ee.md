# Strands Agents SDK：深入解析 agent 架构与可观测性

[Strands Agents SDK](https://strandsagents.com/latest/) 是一个用于构建 AI agent 的开源框架，强调模型驱动（model-driven）的做法。Strands 不把复杂任务流硬编码在代码里，而是利用现代大语言模型（LLM）的推理能力，自主完成规划与工具使用。开发者只要给出一个 prompt（定义 agent 的角色或行为）和一份工具清单，就能创建 agent，而由 LLM 驱动的 agent 会自行决定如何串联推理、按需调用工具。与传统基于工作流的框架相比，这大幅简化了 agent 的开发。

在本篇博文中，我们先介绍 Strands Agents SDK 及其核心特性；然后探讨它如何与 AWS 环境集成，以实现安全、可扩展的部署，以及它如何为生产使用提供丰富的可观测性；最后讨论实际用例，并给出一个分步示例来展示 Strands 的实际运行。

## Strands Agents SDK 是什么？

Strands Agents SDK 是一个开源框架，旨在简化健壮的、由 LLM 驱动的 AI agent 的创建。它不要求开发者手工打造复杂工作流，而是采用以三个关键组件为中心的模型驱动做法：一个语言模型、一个 system prompt，以及一组工具。这一架构让 LLM 承担关键的推理工作，根据当前上下文与任务自主决定最优动作以及何时使用工具。这种模型驱动的设计让 agent 灵活、智能且自主，同时把多步或多 agent 交互通常所需的样板代码降到最少。它的效果已经得到验证——多个 AWS 团队正在生产中用 Strands 支撑他们的 AI agent，包括 [Kiro](https://kiro.dev/)、[Amazon Q](https://aws.amazon.com/q/) 和 [AWS Glue](https://aws.amazon.com/glue/)。

## Strands Agents SDK 的关键能力

Strands Agents SDK 提供以下关键能力：

- **轻量、灵活的 agent 循环** – Strands 实现了一个简单但可扩展的 agent 循环来驱动交互。agent 背后的 LLM 会迭代地读取对话（及上下文）、规划一个动作、可能调用某个工具，然后在决定下一步之前把工具的结果纳入进来，直到得出最终答案。这个循环在需要时完全可以定制，但在大多数用例中开箱即用。
- **工具使用与集成** – 工具是 agent 可以调用的外部函数或 API（例如计算器、Web 搜索或数据库查询）。Strands 让用 Python 定义工具变得简单直接：用 `@tool` 装饰器写一个函数，再交给 agent 即可。开发期间 SDK 支持热重载，因此你可以修改或新增工具，它们会被自动识别，无需重启 agent。这加快了迭代和测试。SDK 还附带一个可选的预置工具库（`strands-agents-tools`），提供算术、Web 请求等常见功能。Strands 同时支持 Model Context Protocol（MCP）与 A2A（Agent-to-Agent）。MCP 是一个开放标准，让 agent 可以访问托管在模型服务器上的数千个外部工具，无需定制编码就大幅扩展能力。A2A 允许 agent 互相调用，把彼此当作工具——以极小的开销实现强大的多 agent 协作与专业化分工。
- **模型无关与多模型支持** – Strands 不绑定单一 LLM 提供商。它默认可以配合 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的模型工作（例如 Anthropic 的 Claude 或其他 Amazon Bedrock 模型），同时也支持 Anthropic 自家的 API、LlamaAPI、Ollama、OpenAI 等开源模型，以及通过可插拔的 provider 接口接入的其他模型。例如，只要在代码里更换 model provider，就能把 agent 的模型从托管在 Amazon Bedrock 上的 Anthropic Claude 换成本地的 Meta Llama 3 或 OpenAI GPT-4。有了这种灵活性，你可以选择最契合需求的模型，或在不同的部署中替换模型。
- **从原型到生产的可扩展性** – 同一份 Strands agent 代码可以先在本地运行以快速测试，然后部署到 AWS 用于生产。该 SDK 已经在 AWS 内部用于若干服务的 agent 功能，例如 Amazon Q（开发者助手）、AWS Glue 和 [VPC Reachability Analyzer](https://docs.aws.amazon.com/vpc/latest/reachability/what-is-reachability-analyzer.html)。它支持在多种环境中运行 agent——包括 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2/)（Amazon EC2）、[AWS Lambda](https://aws.amazon.com/lambda/)、[AWS Fargate](https://aws.amazon.com/fargate/) 和 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)——并且可以把工具执行与 agent 隔离，以提升安全性与可靠性。Strands agent 可以在任何地方运行并与云服务集成，而由于它是开源的，你也可以把它们跑在本地环境或其他云上。
- **进阶用例** – 尽管 Strands 在简单的单 agent 助手场景中表现出色，它也支持更复杂的 agent 系统。你可以组合多 agent 应用，让多个 agent 协作或协调（例如一个把子任务分派给其他专业 agent 的 agent）。SDK 支持 agent 层级、agent 网络，甚至 swarm 式协作等模式（下一节会进一步讨论）。它还允许构建完全自主的 agent，在无人输入的情况下循环处理任务，从而实现 agent 的思维链跨越多次工具调用或中间决策的多步工作流。此外，还支持流式响应（token streaming）等特性，用于实时的 agent 交互。
- **开源与社区贡献** – Strands Agents SDK 采用 Apache-2.0 许可，并开放贡献。已有若干公司（Accenture、Anthropic、Meta、PwC 等）为其开发做出贡献。例如 Anthropic 贡献了其 API 的集成，Meta 增加了对其 Llama 模型的支持。这种社区驱动的做法意味着工具与模型生态正在 AWS 之外不断成长。我们鼓励开发者加入 GitHub 上的项目，报告问题、新增工具或 model provider，帮助扩展这个框架。

Strands 提供了一种简洁而强大的构建 AI agent 的方式。用几行 Python 定义 agent 的角色和它可用的工具，剩下的交给 SDK——从对问题做推理，到调用工具、产出答案。接下来的几节将探讨 Strands 如何支持各种 agent 架构，以及它如何让这些 agent 在生产中变得可观测。

## Strands 支持的 agent 架构模式

Strands 支持多种 agent 架构模式，可以从单个自包含的 agent 一直扩展到由协作 agent 组成的复杂网络。本节将解释这些关键模式，以及 Strands SDK 如何实现它们。

### 单 agent 模式

最简单的场景是一个配备了 LLM（以及可选的若干工具）的单个 AI agent，它与用户交互或执行某项工作，而不把任务分派给其他 agent。在 Strands 中，单 agent 由 `Agent` 类表示——你用模型（或接受默认值）以及它可用的工具来初始化它。agent 运行一个内部事件循环来决定如何回答每个查询：它可能直接用模型的知识作答，也可能选择调用某个工具、把结果纳入进来、再调用更多工具，如此往复直到结束。这个循环会一直持续，直到 agent 产出最终答案。

在代码层面，单 agent 的用法很直接。在下面的示例代码中，我们创建一个带有 calculator 工具的基础 agent，并向它提问：

```
from strands import Agent
from strands_tools import calculator 

# Create an agent that can use a calculator tool
agent = Agent(tools=[calculator])
result = agent("What is the square root of 1764?")
print(result)
```

在这个示例中，agent 用它的 LLM 来理解问题。它识别出自己可能需要计算一个平方根，于是调用所提供的 calculator 工具（一个简单的算术函数）取得结果，然后返回答案。Strands 负责 prompt 格式化、调用工具，以及把工具结果插回模型的上下文以形成最终答案。在单 agent 模式下，推理与工具使用都发生在同一个 agent 进程内。

单 agent 适用于许多任务，例如问答、数据检索、简单助手。它让逻辑保持自包含。然而，随着任务复杂度上升，你可能会触及单个 agent（即便配有工具）能有效处理的上限（例如需要多种不同专业知识或并发动作时）。这正是多 agent 模式登场的地方。

### 多 agent 网络（swarm 或点对点 agent）

Strands 支持 agent 网络：多个 agent 在其中运行并通信，协作解决问题。在这种网络中没有单一的编排者；agent 之间以点对点方式或开放拓扑交互。这种模式有时被称为 agent 的 *swarm*（群体）协同工作。网络中的每个 agent 可能拥有专门化的角色或视角，它们共享信息以收敛到某个解决方案。

在 swarm 式网络中，通信模式可以多种多样。一种常见做法是网状（mesh）通信，agent 之间可以自由对话。这适用于头脑风暴类 agent 或需要达成共识、彼此交换想法的场景。其他通信方案还包括使用共享内存或黑板（blackboard，一个供 agent 发布和读取信息的公共仓库），或在特定 agent 对之间建立消息传递通道。

Strands 提供实现这类网络的工具。你可以创建多个 agent 实例（每个都有自己的 prompt、persona 和工具），并把它们连接起来。例如，你可能有一个研究 agent、一个创意 agent 和一个批评 agent 以网状连接在一起。研究 agent 提供事实数据，创意 agent 提出想法，批评 agent 指出缺陷；它们共同迭代逼近答案。Strands SDK 还内置了 `agent_graph` 工具，帮助以编程方式管理这类网络（你可以定义 agent 与连接关系，然后向网络中发送消息）。

agent swarm 中的通信与协调可以按不同理念来设计：

- **协作型 swarm** – agent 主动在彼此的贡献之上叠加，目标是达成共识。这适合创造性问题求解或研究，因为把多种视角结合起来往往能得到最佳结果。
- **竞争型 swarm** – agent 并行处理同一任务（也许采用不同方法或假设），甚至可能互相评判彼此的结果。在多个 agent 尝试各自独立策略以看哪种更好的场景中，这会很有用。
- **混合做法** – 在某些子任务上合作，在其他子任务上独立探索。

Strands 不强制某种特定风格；你可以按需实现消息交换逻辑（SDK 把消息内容与时机留给开发者，甚至留给 agent 自己决定）。新的 `agent_graph` 工具通过指定拓扑（例如全连接网状）来简化网络搭建，然后让你向 agent 广播或定向发送消息。每个 agent 都可以跑在独立的线程或进程中，从而提供可扩展性。在需要同时具备不同技能或视角的复杂问题领域，多 agent 网络尤为擅长。

### Supervisor agent 模型（编排者 + 工具 agent）

Strands 支持的另一种模式是 *supervisor agent* 模型，也被称为 *orchestrator and specialists* 架构或 *agents as tools* 模式。在这种设计中，一个 agent 充当主编排者（supervisor），对接用户或高层任务，并把子任务分派给一个或多个专业 agent。每个专业 agent 实际上都是被包装成可调用工具的 agent，编排者可以在需要时调用它。

管理 agent 判断某个查询需要哪个专业 agent，把请求转发过去，再把结果整合回一个最终答案。例如，你可以设计一个编排者 agent：面对复杂问题时，它可以根据查询内容调用 Research Assistant agent 做事实查找，调用 Math Assistant agent 做计算，或调用 Travel Planner agent 处理行程任务。每个助手都是一个由 LLM 驱动的 agent，拥有自己的 system prompt 和面向本领域的专用工具。

Strands 让这种实现变得直接。你可以创建专业 agent，并用 `@tool` 装饰器把它们暴露为 Python 工具，如下代码所示：

```
from strands import Agent, tool
from strands_tools import retrieve, http_request

# System prompt for a specialized research agent
RESEARCH_ASSISTANT_PROMPT = """
You are a specialized research assistant. Focus on providing factual, well-sourced information for research questions.
Always cite sources in your answers.
"""

@tool
def research_assistant(query: str) -> str:
    """Tool that uses a specialized agent to answer research queries."""
    # Create a specialized agent for research tasks
    research_agent = Agent(
        system_prompt=RESEARCH_ASSISTANT_PROMPT,
        tools=[retrieve, http_request] # this agent can use web retrieval tools
    )
    return research_agent(query) # delegate the query to the research agent
```

在这个示例中，我们把 `research_assistant` 定义为一个工具。该实现会启动一个带有专门 prompt 和几个 Web 研究工具（例如用 `retrieve` 获取文档、用 `http_request` 调用 Web API）的 agent，然后向该 agent 发起查询并返回结果。我们可以用同样方式定义其他专业 agent 工具，例如 `math_assistant` 或 `trip_planner_assistant`，每个都有自己的 prompt 和领域专用工具集。

现在我们可以创建把这些专业 agent 当作工具使用的编排者 agent：

```
# Orchestrator agent that can delegate to specialized assistants
orchestrator_agent = Agent(
    tools=[research_assistant, math_assistant, trip_planner_assistant]
)
# When a user question comes in, the orchestrator can decide which agent to invoke
response = orchestrator_agent(
    "What are the latest NASA findings on Mars, and can you calculate the travel time to Mars at 20km/s?"
)
print (response)
```

当 `orchestrator_agent` 收到这个复杂问题时，它会借助 LLM 的推理（由它的 prompt 引导，我们可以把它定制成通用协调者）来判断如何作答。它可能判断这个问题包含两部分——研究部分（NASA 最新发现）和计算部分（旅行时间）——于是可能对第一部分调用 `research_assistant` 工具，对第二部分调用 `math_assistant` 工具。每个工具都是一个完整的 agent，各自完成自己的子任务（例如研究助手可能用 `http_request` 从 NASA 的 API 或知识库获取数据）。编排者随后组装出最终答案。这种层级关系形成了一条清晰的分派链：顶层 agent 把工作交给专家，再把它们的输出合并起来。

supervisor agent 架构的好处包括关注点分离（每个 agent 各自专业化，使系统易于维护）与模块化（你可以增删专业 agent，而不必重写整个 agent）。它也映射了人类的组织结构——由管理者协调专家——这是扩展 agent 复杂度的一种直观方式。在 Strands 中，只需把 agent 当作又一种工具，就能完整支持这一模式。编排者 agent 的内置逻辑（通过 LLM）会读取工具的 docstring，判断何时使用哪个专业工具——尤其是当你在它的 system prompt 中给出类似“凡是关于科学事实或最新数据的问题，都使用 Research Assistant”这样的指引时。

### 层级式 agent 架构

层级模式是把 supervisor agent 的思路扩展到多层分派。你不再只有一个编排者和一串专家，而是可以有形成层级或树状结构的 agent 层。例如，最上层可能是一个负责总体目标的 executive agent；它把高层任务分派给几个 manager agent，每个 manager agent 再把任务进一步拆解给它们的 worker agent。当问题非常复杂或天然是树状结构（项目管理、多阶段工作流）时，这很有用。

Strands 的 agent graph 概念对这一点做了泛化。在 agent graph 中，节点是 agent，边定义通信或监督关系。层级拓扑是受支持的图模式之一：一棵树，每个父节点指挥其子节点。信息以任务的形式沿树向下流动，以结果或报告的形式沿树向上流动。星型拓扑（一个中心协调者加许多直属专家）实际上是一层级的层级结构（即 supervisor agent 模型），而真正的层级结构可能有多级监督。

使用 Strands SDK，你可以通过组装 agent 并协调它们的调用来手工创建这类结构，但更简单的路径是使用 graph 工具或类似的工具函数。如前所示，你可以用编程方式定义图的节点与边（指定每个 agent 的角色和 prompt），该工具会实例化出这个网络。然后你可以向图中发送消息（例如给 executive agent 一条顶层指令），系统会按照已定义的边把任务向下传播、把解决方案向上传递。层级中的每个 agent 都可以维护自己的状态与关注点——例如中层 manager agent 可以独立跟踪其子任务的进度。

当你需要分层处理或分层决策时，层级式 agent 架构非常理想。例如，设想一个自主的软件工程 agent：executive agent 在总体上决定实现哪个特性，并把它分派给一个设计 agent 和一个编码 agent，而编码 agent 可能再把任务进一步分派给代码生成 agent 和测试 agent。每一层都增加了一层监督，能够捕获错误或细化下一层的需求。这降低了每个个体 agent 的认知负担。Strands 通过提供把 agent 连接成树或图结构、并沿这些链接处理消息传递的机制来支持这一点。内置的为每个 agent 维护会话与状态、控制信息流的能力，意味着你可以精细调节每个 agent 知道什么，从而保证清晰度并防止 agent 之间相互干扰彼此的上下文。

最后，Strands 不会把你锁死在某一种模式里——你可以把它们组合起来。例如，你可以在层级的某一层放一群对等 agent，在它们之上放一个 supervisor；或者让一个编排者把一小群头脑风暴 agent 作为它的工具之一来咨询。SDK 的灵活设计（把 agent 同时当作一等对象和工具）让你可以按问题需要混合各种模式。

## Strands agent 的可观测性

在生产环境中，可观测性对于理解和信任你的 agent 在做什么至关重要。Strands SDK 在设计时就考虑了可观测性，开箱即提供内置的埋点钩子、遥测采集，以及对日志与指标的支持。

### 埋点与 trace

Strands 可以记录 agent 的轨迹（trajectory）——即 agent 针对每个请求所走的步骤序列（例如模型调用、工具调用）。它使用 OpenTelemetry（OTEL）标准输出这些数据，这意味着你可以把它接入其他兼容 OTEL 的监控后端（例如 [AWS X-Ray](https://aws.amazon.com/xray/)、[Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 和 [Jaeger](http://jaegertracing.io/)）来可视化和分析 agent 的行为。

agent 的每一次运行都可能产生一个 *trace*，它由表示每个重要动作的 *span* 组成。例如，当 agent 调用 LLM 模型时，那就是一个 span，其中可以包含 prompt、模型参数（例如 temperature 或 max tokens）和 token 用量计数等元数据。当 agent 调用工具时，那是另一个 span，记录调用了哪个工具以及输入和输出。把这些 span 拼接起来，你就能得到 agent 如何得出答案的端到端时间线。

这种分布式追踪可以跨组件延伸——例如，如果你的 agent 把某个远程微服务当作工具来调用，trace 可以传播到那个服务中（前提是它同样使用 OTEL），从而给你一个跨系统的请求视图。这类洞察对于调试 agent 的推理、优化性能，以及在复杂的多 agent 工作流中定位故障点都极为宝贵。

### 指标跟踪

Strands 还会跟踪 agent 运行的关键指标。指标是聚合测量值，有助于量化性能与使用情况。你可以采集诸如每个工具被调用的次数（以及这些调用的成功率与失败率）、工具调用的运行时长、每次交互运行多少轮或多少个 agent 循环、模型响应的延迟（首字节时间与完成时间），以及每个请求的 token 消耗（prompt token 对 completion token）等指标。Strands 还可以呈现系统指标（CPU，以及相关的内存使用情况）和自定义业务指标，例如用户对 agent 回答满意的频率（如果提供了反馈）。

通过监控这些指标，开发者和运维团队可以确认 agent 运行得高效、可靠。例如，工具错误率突然突增，或每个查询的 token 用量跳升，都可能意味着出现了需要关注的性能退化。指标可以接入仪表盘或告警系统，以维持 AI agent 服务的运行健康度。

### 日志

SDK 会为重要事件输出日志——例如发送给模型的完整 prompt、模型的原始响应、它关于使用哪个工具的决策，以及遇到的错误。这些日志带时间戳，并且可以像其他应用一样配置不同的详细级别（debug、info、error）。日志对深度调试或审计追踪很有用；由于日志可能包含敏感或冗长的信息，Strands 允许按需对日志做结构化或脱敏处理。在生产环境中，你可以把 Strands 的日志接入标准日志基础设施（CloudWatch Logs、ELK stack）做集中分析。

### 可观测性

Strands 鼓励端到端的可观测性。SDK 文档描述了一个框架，让 agent 开发者、数据工程师和产品负责人都能消费遥测数据。例如，开发者用 trace 来诊断 agent 为什么做出某个决策（比如可视化一条 trace，看是什么工具调用链导致了错误答案）。数据工程团队可能把遥测聚合到数据仓库，分析一段时间内的使用模式或成本。AI 研究者可以用日志和 trace 识别失败模式，并微调 prompt 或模型（把 trace 数据当作改进 agent 的反馈）。

Strands 提供了支撑这一点的原始能力（埋点位置与 OTEL 集成），但搭建 collector 和仪表盘要靠实施团队自己。最佳实践包括：统一采用开放格式（如 OTEL）以保证互操作性；用 collector 把遥测路由到多个下游（用于运维或商业智能）；以及对数据做过滤或采样，以控制数据量和隐私。

在 Strands 里，可观测性不是事后补上的东西——它被内建到 agent 循环中，因此当你的 agent 在生产中运行时，你可以监控它的推理与动作。这种对埋点的重视让 Strands 与众不同，尤其是与更早的 agent 框架相比，那些框架往往要开发者自己添加日志或追踪。

## 企业级就绪与部署最佳实践

Strands Agents SDK 的设计初衷就是面向企业生产使用，提供特性与指引，帮助 agent 在业务关键型环境中可靠、可扩展且安全地运行。本节讨论 Strands 如何满足大型组织采用 agentic 工作流所必需的几项关键企业要求。

### 可扩展性与性能

Strands 可以从快速原型无缝扩展到大规模生产部署。在开发者笔记本电脑上运行的同一份 agent 代码，无需改动就能部署到云端。Strands 以轻量方式构建（一个负责编排对 LLM 与工具 API 调用的 Python 框架），因此带来的开销极小。agent 可以并发运行——多 agent 配置中的每个 agent 都可以在自己的线程或进程中执行，以利用多核或多台机器。这意味着编排者 agent 可以把工作分派给运行在并行进程中的专业 agent，在多 CPU 系统上实现并发和更高的吞吐量。当集成到分布式环境（如微服务或无服务器架构）时，你可以在负载均衡器后运行多个 agent 实例来处理高请求量。该框架模型无关的特性也意味着，你可以为更重的工作负载选择更强的模型端点，或把调用分散到不同的 model provider 以避免瓶颈。

实践中，性能通常主要由 LLM 的响应时间和 agent 发起的外部 API 调用决定；Strands 会确保高效地把这些操作流水线化（例如在可用时采用流式响应，以尽快开始输出）。除了计算资源和模型本身的限制，Strands 对 agent 能处理的工具数量或步骤数量没有严格上限——因此它在需要时适合复杂、长时间运行的任务。

### 安全与数据保护

企业应用要求强安全措施，Strands 提供了构建安全 agent 的机制与建议。由于 agent 可以通过工具执行代码或调用外部 API，管理 agent 可用的工具至关重要。Strands 支持对工具访问做细粒度控制——由你决定为每个 agent 纳入哪些工具。

敏感数据处理同样被强调：AWS 建议对 agent 处理的敏感数据实施端到端加密，无论是在静态存储还是传输过程中。例如，如果 agent 存储对话历史或中间结果，这些数据可以加密，或只保留在内存中。输入的净化与校验同样重要；使用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 或自定义校验来过滤 agent 的响应，可以防止 agent 返回机密信息或不被允许的内容。Strands 的日志可以配置为省略或脱敏敏感细节，这样审计日志就不会变成泄露源。

身份认证与授权应当在 agent 端点之前分层实施：当你使用 [Amazon API Gateway](https://aws.amazon.com/api-gateway) 或 Lambda 部署时，可以用 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）角色、[Amazon Cognito](https://aws.amazon.com/cognito/) 或 OAuth token 来确保只有被授权的系统或用户可以调用 agent。在 agent 内部，你还可以实施基于角色的逻辑——例如某些工具只有在发起请求的用户具备相应权限时才启用。对于多 agent 系统，隔离每个 agent 的上下文（Strands 通过会话与独立 prompt 支持这一点）可以落实最小权限原则（每个子 agent 只知道它需要知道的信息）。

AI agent 的威胁建模是一项新但重要的实践；AWS 已发布相关指引，例如用于 agentic AI 威胁建模的 [MAESTRO framework](https://cloudsecurityalliance.org/blog/2025/02/06/agentic-ai-threat-modeling-framework-maestro)。它鼓励团队预判 agent 可能如何被滥用或攻击（例如通过恶意输入实施 prompt injection，或试图让 agent 泄露受保护数据），并实施输入校验、输出过滤和健壮的异常处理等缓解措施。

Strands 为你提供了构建强大自主 agent 的积木，但企业应当用对待任何应用都同样的严谨来包裹这些 agent——加密、监控、访问控制，以及针对对抗性输入的测试——才能安全且负责任地运行它们。

### AWS 服务集成

作为源自 AWS 的项目，Strands Agents SDK 与 AWS 生态集成得很自然。它可以开箱即用地配合 Amazon Bedrock（用于访问基础模型），从而简化了在企业级安全前提下使用高质量、可扩展模型的过程（使用 Amazon Bedrock 时，数据不会被置于未加密状态，也不会被发送给外部第三方）。

除模型托管之外，Strands 对 OTEL 的使用意味着你可以把 trace 数据送入 AWS X-Ray 做分布式追踪可视化，并把指标发送到 CloudWatch 做实时监控。例如，你可以针对工具错误率或每次 agent 调用的延迟等指标设置 CloudWatch 告警，在出现异常时通知运维团队。

Strands 还可以把 AWS 服务当作工具来调用——既可以用 API，也可以用专门化工具。面向 AWS 的社区贡献工具已经可用（例如能执行 AWS SDK 命令或查询 AWS 资源的工具）。在某个场景中，agent 可以用一个 AWS SDK 工具自动修复 AWS 基础设施问题（从而成为一个 DevOps 助手），或用 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 工具在工作流中存入和取回信息。事实上，Strands 的一个示例用例就演示了 agent 把天气数据存入 DynamoDB，展示了 agent 能多么无缝地纳入 AWS 数据服务。由于 Strands 是 Python 框架，它也能顺滑地配合 Lambda 做无服务器部署（本篇博文后面会更多讨论），并在你需要把一次 agent 调用作为更大编排业务流程中的一个步骤时配合 [AWS Step Functions](https://aws.amazon.com/step-functions/) 使用。企业可以利用已有的 AWS 身份与网络特性，如虚拟私有云（VPC）、IAM 或 [AWS Key Management Service](https://aws.amazon.com/kms)（AWS KMS）加密，在云端运行时进一步加固并隔离它们的 agent。

反过来说，Strands 保持了足够的云无关性：如有需要，你可以把它跑在本地环境或其他云环境中——例如通过 Ollama 使用本地模型，或连接第三方 API——从而为混合部署提供灵活性。

### 部署最佳实践

在生产环境中部署 Strands agent 有几种经过验证的模式，SDK 提供了带参考实现的部署工具包。视用例不同，你可以选择以下部署方式之一：

- **无服务器（Lambda）** – 这适合短时的 agent 任务或事件驱动的调用。你可以把 agent 部署为 Lambda 函数，也许用 Lambda function URL 特性或 API Gateway 通过 HTTPS 触发它。这带来了可扩展性（Lambda 会按需启动并发执行）和极低的运维开销。它最适合能在 Lambda 运行时限制内完成、且不需要长生命周期状态的 agent（不过如有需要，你可以用外部存储保存状态）。AWS 提供了按这种方式部署 Strands 的示例，其中也包括使用 Lambda 实现流式响应以获得实时答复。对于交互式或流式 agent，你可能更愿意使用 WebSocket 或异步模式，因为 Lambda 调用是无状态的。
- **容器（AWS Fargate 与 Amazon ECS 或 Amazon EKS）** – 对于长时间运行或有状态的 agent 服务，把 agent 逻辑容器化是常见做法。你可以把 agent 循环托管在容器中（例如一个监听请求、调用 agent 并返回结果的微服务）。参考架构中同时支持 Fargate（无服务器容器）与 [Amazon Elastic Container Service](https://aws.amazon.com/ecs)（Amazon ECS）或 [Amazon Elastic Kubernetes Service](https://aws.amazon.com/eks/)（Amazon EKS）。这种做法很适合流式交互（agent 可能保持连接以流式输出 token）和高并发场景。使用容器，你可以为更大的模型分配更多内存/CPU，或在运行重的本地模型时使用带 GPU 的实例。你还可以水平扩展 agent 服务实例数量，并在多个 agent 服务需要通信时接入服务网格或类似模式。
- **混合式控制权返回（return-of-control）模式** – 在某些企业场景中，出于安全考虑，部分工具执行发生在客户端或独立环境中。Strands 支持这样的架构：agent 托管在一个环境中（例如 AWS），而某些工具在另一个环境中执行（比如用户设备上，或受保护的本地服务中）。return-of-control 模式让 agent 把某些工具调用委派回客户端应用。例如，客户端应用可以向 agent 注册一个本地工具（例如用于访问本地数据库或硬件设备）。当 agent 决定使用该工具时，它会返回一个信号，让客户端去执行并等待结果。同时，其他工具仍可托管在云端。这种模式提供了最大的灵活性，既能回应数据治理方面的顾虑（把部分数据处理留在本地），又能继续享用云端 agent 的推理能力。
- **单体与微服务** – Strands agent 既可以作为单体部署（agent 循环和所有工具在一个进程中），也可以拆分成微服务（每个工具作为独立服务，由 agent 通过 API 调用）。单体部署更简单、延迟更低（内存中的函数调用），但把工具拆成独立服务可以改善故障隔离、让昂贵的工具独立扩展，并支持多语言实现（用其他语言写的工具）。一个最佳实践是先从单体起步以保持简单，然后按需把关键工具重构出去（例如数据密集型工具可能更适合作为可独立扩展的独立服务）。只要 OTEL 追踪被正确传播，Strands 的可观测性仍能捕获跨服务调用，让你看到分布式工作流的完整全貌。
- **Amazon Bedrock AgentCore** – 若要为 Strands agent 做生产级部署，并内置对身份、记忆、可观测性和工具集成的支持，AWS 提供了 Amazon Bedrock AgentCore。这是一个专为在真实应用中运行 AI agent 而设计的安全无服务器运行时。你可以用 `BedrockAgentCoreApp` 包装器包裹 Strands agent，并通过 [AWS Command Line Interface](https://aws.amazon.com/cli)（AWS CLI）或容器工作流部署它。Amazon Bedrock AgentCore 支持长时间运行的任务（最长 8 小时）、异步工具执行，以及基于 MCP、A2A 或 API Gateway 的服务之间的工具互操作。它还包括 OAuth、Amazon Cognito 和 IAM 等安全身份特性，以及配合 CloudWatch 与 OTEL 的原生可观测性。对寻求可扩展、安全且全托管的 agent 基础设施，并能与既有 AWS 服务无缝集成的团队来说，这种做法非常理想。截至 2025 年 7 月，Amazon Bedrock AgentCore 处于公开预览阶段。

在生产中运行 agent 时，还建议实现健壮的错误处理与监控。例如，你可以把 agent 调用包在一个重试循环或回退逻辑中——如果 agent 失败或返回不完整的结果，它会处理异常并优雅地响应（也许返回一个默认答案，或一条表示稍后再反馈的消息）。为工具调用定义超时，并尽可能限制推理循环次数，以避免“失控”的 agent。使用 CloudWatch 或类似的监控系统采集延迟、错误数、token 用量和每请求成本等指标，并为异常设置告警。在企业中，运维卓越与 agent 的准确性同等重要——Strands 提供了达成这一点的钩子（遥测、日志、配置项），但把它们接入你现有的运维工具箱，要靠你的 DevOps 团队。

遵循这些企业部署最佳实践——选择正确的架构、在多个层面落实安全、使用 AWS 的基础设施——企业就能自信地部署 Strands agent，既满足自身的可扩展性、安全与合规要求，又能把先进的 AI 能力交付给最终用户。

## 实用示例：自主工作流的实际运行

为了说明如何用 Strands SDK 搭建一个自主工作流，我们来走一个场景。假设我们要构建一个能执行多步任务的自主研究助手：用户提出一个宽泛的问题，agent 需要从 Web 上收集信息、做一些分析，并给出条理清晰、带有引用的答案。这涉及决策（如何拆解任务）、工具使用（Web 搜索、阅读文档、执行计算）以及结果的综合。

### 定义工具

我们需要一些用于 Web 研究的工具。Strands 包含 `retrieve` 工具（用于搜索和取回文档）和 `http_request` 工具（用于调用 API 或抓取 URL）。如果需要额外处理，我们还可以加入一个 Python 执行工具或其他工具。

### 用合适的 prompt 创建 agent

我们给 agent 一个 system prompt，指示它做一个勤勉的研究助手。例如：“你可以使用 Web 搜索与浏览。始终查找事实性信息并在答案中标注来源。如需计算，请一步步完成。”这个 prompt 设定了上下文，让 LLM 知道该如何行事（也就定义了 agent 的角色与准则）。

```
from strands_tools import calculator

# Orchestrator agent that can both research and calculate
smart_agent = Agent(
    system_prompt="You are an AI research assistant. You answer questions with facts and citations. You have tools for web research and math.",
    tools=[research_assistant, calculator]
)
query = "What are the latest NASA findings on Mars, and how long would it take a spacecraft to travel from Earth to Mars at 20 km/s?"
answer = smart_agent(query)
print(answer)
```

### agent 的推理与工具使用

查询到来时，agent 的 LLM 会解析问题并确定一个计划。得益于 Strands 的模型驱动循环，agent 可以在内部这样推理：“问题要求给出 NASA 关于火星的最新发现，并计算旅行时间。计划：（1）用 Web 搜索工具查找 NASA 近期关于火星的公告，（2）总结发现，（3）用计算器（或内部数学能力）计算旅行时间，（4）撰写最终答案。”

agent 会一步步执行这个计划：用类似 “latest NASA Mars findings” 的查询调用 `retrieve`，拿到结果（也许通过 `http_request` 阅读某篇文章），提取关键信息，完成旅行时间的计算（如果 calculator 工具可用就用它，否则用基础算术），最后把这一切综合成一个连贯的答案，并为火星相关信息标注文章出处。

这一切都在一次 `agent()` 调用中透明地完成。用户只看到最终答案，但 Strands 为了走到这一步编排了多次工具调用和推理迭代。前面介绍的可观测性特性让事后检视这个过程成为可能（例如，我们可以在 trace 中看到 agent 发起了两次工具调用：一次调用 `retrieve` 获取 NASA 信息，一次调用 `calculator` 计算旅行时间）。

### 撰写最终答案

agent 把各工具的结果组合起来，组织出返回给用户的答案。例如：

```
## Latest NASA Findings on Mars (2023-2025)

### Atmospheric Discoveries
1. **First Visible-Light Auroras** (March 2024)
- NASA observed visible-light auroras on Mars after a solar flare and coronal mass ejection
- This event occurred near the peak of the current solar cycle

2. **MAVEN's "Sputtering" Discovery** (2024)
- After a decade of searching, NASA's MAVEN mission made the first direct observation of atmospheric "sputtering"
- This process helps explain how Mars lost its atmosphere over time

### Geological Discoveries
1. **Arsia Mons Volcano Observation** (2025)
- NASA's 2001 Mars Odyssey orbiter captured new images of Arsia Mons, one of Mars' largest volcanoes
- The images show the massive volcano peeking through morning cloud cover

2. **Perseverance Rover's New Explorations** (2025)
- Perseverance began exploring "Krokodillen," a region potentially containing some of Mars' oldest rocks
- The rover continues collecting samples for the future Mars Sample Return mission

3. **Dust Devil Captured in Perseverance Selfie** (May 2024)
- A Martian dust devil was captured in Perseverance's fifth selfie since landing

### Other Notable Findings
- Curiosity rover was photographed in motion by the Mars Reconnaissance Orbiter
- NASA's Europa Clipper spacecraft captured infrared images of Mars during a flyby
- Ongoing updates to the Mars Relay Network for communication between rovers and orbiters

## Earth to Mars Travel Time at 20 km/s
The distance between Earth and Mars varies significantly due to their elliptical orbits:
- **Minimum distance**: 54.6 million km (when planets are at their closest)
- **Maximum distance**: 401 million km (when planets are at their furthest)

At a constant speed of 20 km/s:
- **Minimum travel time**:
- 2,730,000 seconds
- 758.3 hours
- **~31.6 days**

- **Maximum travel time**:
- 20,050,000 seconds
- 5,569.4 hours
- **~232.1 days** (about 7.7 months)

This significant variation in travel time (from approximately 1 month to 7.7 months) demonstrates why launch windows to Mars are carefully planned to coincide with favorable orbital alignments that minimize travel time, fuel consumption, and mission duration.
```

这个答案展示了 agent 如何取回事实数据——具体来说是地球与火星之间的最小和最大距离——并用这些信息计算以 20 km/s 恒定速度飞行所需的旅行时间。它用多种格式（秒、小时、天）表达结果，给出了一个从约 1 个月到 7.7 个月、视行星位置而定的现实旅行区间——而全程都不需要用户另外提示这些步骤。

用 Strands 处理这个工作流，我们不必自己编写“先搜索、再计算”的脚本；agent 会智能地决定顺序。如果问题不同，agent 可能会采取不同做法或调用不同工具，而这一切都基于它的自主推理。通过调整所提供的工具和 system prompt，我们可以引导 agent 在各种自主工作流中的行为（从用代码执行工具写代码，到用数据分析工具分析数据集）。

### 错误处理与反思

实践中，自主 agent 可能会犯错或需要恢复（也许第一次 Web 搜索没有用，它需要换个查询再试）。Strands agent 具备在循环内反思和重试的能力——例如当某个工具的结果出人意料或与问题无关时，agent 可以重新组织自己的方法。我们也可以编写显式的防护栏，或利用可观测性信号在出问题时介入（例如 X 轮之后仍没有有用答案，就停下来，返回一句道歉或请求澄清）。SDK 提供了回调钩子以及集成这类逻辑的能力，但默认情况下，对于中等难度的任务，LLM 自身的迭代推理往往已经足够。

通过这个示例，我们看到 Strands 如何在单一统一 agent 中实现多步决策。它让 agent 能自主行动——决定采取哪些步骤、以什么顺序——靠的是 LLM 强大的推理能力，同时把控制点留给开发者，而且很简单（允许哪些工具、agent 的角色与 prompt 是什么，以及事后分析日志和 trace 的能力）。

## Strands 与其他 agent 框架的对比

随着 AI agent 的迅速崛起，涌现了不少框架。[LangChain](https://python.langchain.com/docs/introduction/) 是构建 LLM 驱动应用与 agent 最流行的库之一。本节概述两者的相似与不同之处，以及何时该考虑用哪一个。

### 核心理念与哲学

Strands 与 LangChain 都支持用 LLM 驱动动作的模式（即推理与工具使用相结合的 ReAct 范式）。它们都允许你定义工具与函数，让模型调用它们来解决问题。最大的差别在于开发者体验与侧重。Strands 主张最小化编排：你提供 prompt 和工具，并相信模型能自己搞清楚顺序。它有意识地避免要求开发者在 agent 周围编写复杂的工作流代码或状态机。

LangChain 起步时的重点是给开发者提供积木，用来构造 LLM 调用与工具的链路或序列。在早期的 LangChain 中，你可能要手工把一系列步骤拼起来，或使用预定义的 agent 模板。随着时间推移，LangChain 增加了 agentic 行为（例如带有 LLM 规划动作的 `AgentExecutor`），但如果你想，它仍提供更多底层控制。LangChain 的最新版本引入了显式的工作流编排工具，例如用于基于 DAG 的流程的 LangGraph，以及 `MultiAgent` 编排引擎。这意味着 LangChain 在需要时可以支持非常细粒度、由开发者定义的工作流（你可以为每个子 agent 及其连接方式写脚本）。而 Strands 默认选择把这些抽象掉——工作流从模型的决策中涌现，而不是来自开发者硬编码的逻辑。

简而言之：Strands 是“LLM 优先”（模型即规划者），而 LangChain 是“开发者优先”（由你组装想要的链路，不过如果使用它的 agent 抽象，也可以把规划委派给模型）。

### 工具生态与集成

两个框架都重视工具（也称为 *skills* 或 *functions*）。LangChain 提供种类繁多的集成——不仅是数学或 Web 搜索这类通用工具，还有到数据库、向量存储和 API 的连接器，且常常以社区贡献的 wrapper 形式提供。

Strands 在工具上拥抱 MCP（model-provided tools）等标准。通过支持 MCP，Strands 可以访问庞大的工具库（例如面向文档的问答、编码辅助工具、云资源操作工具），而每个工具都不需要你在代码里写定制的集成脚本。LangChain 原生并不支持 MCP，但它有自己的工具目录，通常你通过编写一个 Python 函数并把它添加为工具来集成（这与 Strands 的 `@tool` 类似，后者很可能受到了 LangChain 推广的模式的启发）。凭借更成熟，LangChain 拥有更丰富的内置连接器（尤其是对数据存储或 model provider 这类东西），而 Strands 正通过开放协议与社区贡献迅速追赶（Anthropic 和 Meta 已经为各自的系统在 Strands 中添加了兼容性）。

Strands 能自然地与 AWS 服务良好集成（例如 Amazon Bedrock 模型），而 LangChain 在历史上更多与 OpenAI 的 API、自定义本地模型和各种第三方服务搭配使用。两者都可以适配任一用例，但最省事的搭配往往是 Strands 配 Amazon Bedrock、LangChain 配 OpenAI——尽管 Strands 与 OpenAI 配合也完全没问题。

### 多 agent 与 agent 组织方式

Strands 提供对多 agent 系统的一等支持（你可以用 `agent_graph` 工具等内置能力搭出 swarm、图结构和层级式的组合）。LangChain 也进入了这一领域，提供了 `MultiAgentManager/Executor` 之类的东西，甚至还有像 Microsoft AutoGen 集成这样的实验性生态，让多个 agent（比如 user agent 和 system agent）相互对话。不过 LangChain 的多 agent 模式并没有那么统一在一个概念之下；你更多看到的是示例或自定义实现（例如互相批评或在循环中工作的 agent）。

2025 年，LangChain 推出了 LangGraph 及其他特性，让开发者可以显式设计带流程、共享内存与并行能力的多 agent 工作流。这在 LangChain 中给开发者很大的编排能力，但需要你自己规划这些交互。Strands 则为常见模式提供了更多开箱即用的构造（比如把 agent 变成工具的现成方式，或创建网状网络），倾向于合理默认值。

AWS 还有一个独立的库叫 Agent Squad，专注于多 agent 编排（把请求路由到专业 agent）。AWS 建议：当你需要许多具有严格上下文隔离的专业子 agent 时用 Agent Squad；当你想要由 LLM 推理驱动的“带工具的单 agent”做法时用 Strands。这说明 Strands 往往最适合使用工具的单个 agent（或一个受控的 agent 层级），而如果你想要一大群各自拥有模型或知识的异质 agent，你可能需要另一个编排者，并酌情把 Strands agent 纳入其中。不过在大多数情况下，Strands 完全有能力做多 agent 协调。

### 记忆与上下文处理

两个框架都能在 agent 的多轮之间维护状态（对话历史，或更广义的 agent 记忆）。LangChain 有大量用于短期记忆（聊天消息历史）和长期记忆（由向量存储支撑的记忆）的工具。Strands 也提供会话与状态管理——你可以选择把对话历史或其他上下文存到哪里（内存、持久化存储），以及如何截断或取回。原理相似，但 LangChain 有更多预置变体（例如摘要式记忆，或以知识图谱作为记忆），这反映了它在对话式 AI 中更广泛的使用。

对解决方案架构师来说，如果需要超出简单历史记录的记忆（例如集成向量数据库作为知识来源），LangChain 为此提供了可插拔的类；在 Strands 中，你可能会实现一个自定义工具去查询向量数据库（或者，如果已有这样的 MCP 工具，就使用 MCP）。两者都能达成目标，但做法不同（LangChain 会把它当作链路中的 retriever，Strands 会把它当作 agent 可以调用的工具）。

### 可观测性与评估

Strands 借助其 OTEL 集成和对指标的指引，专注于生产可观测性。它把遥测当作在线 agent 的一等关切。LangChain 虽然提供了一些日志与回调（也有 Langfuse 这样的第三方方案来给 LangChain agent 加埋点），但没有 Strands 这种级别的内置分布式追踪或指标系统。实践中，使用 LangChain 的团队常常需要自己添加日志，或用 wrapper 记录 agent 的步骤。而用 Strands，其中大部分已经包含在内，或只需简单配置。这让 Strands 在监控不可或缺的企业与生产场景中颇具吸引力。

在评估方面，Strands 与 LangChain 都承认需要评估 agent 的输出。LangChain 有评估模块（用于给回复打分），Strands 也提供面向 agent 的评估方法（例如收集 trace 用于分析，或使用反馈循环）。得益于内置的 OTEL 支持，遥测方面的优势偏向 Strands。

### 用例适配性

在 Strands 与 LangChain 之间做选择，取决于项目的优先级。如果你想要一个快速、少写样板代码的方案让 agent 跑起来——尤其是当你打算使用 AWS 基础设施或 Amazon Bedrock 模型时——Strands 是个极好的选项。它提供了一条从“prompt 加工具”到可用 agent 的快捷路径，并且当你乐于让一个强大的模型来编排整个过程时，它表现最佳（考虑到如今 GPT-4 或 Anthropic 的 Claude 2 这类 LLM，这通常是合理的选择）。如果生产中的可观测性与可靠性是首要关切，Strands 也是强有力的选择；它由 AWS 以生产为目标设计（AWS 内部团队用 Strands 取代了数月的自定义 agent 折腾，这一点正说明了这种侧重）。

另一方面，如果你的用例需要对每个步骤做大量自定义控制，或涉及大量与外部系统的集成而 LangChain 已经提供了相应模块（例如你需要对接 10 个不同的数据库和专有 API，并且希望有一个对所有这些都有示例的库），那么 LangChain 的生态可能让你更快达成目标。LangChain 目前的社区也更大，因此为小众场景寻找示例与支持可能更快。此外，对于学术性或高度实验性的多 agent 研究，LangChain 在构造新颖 agent 循环或逻辑方面的灵活性可能有用。不过 Strands 演进很快，而且由于是开源的，它可能很快纳入许多所需的集成（你也随时可以把 Strands 与其他库结合使用——例如把 LangChain 的一条链当作 Strands 的工具来调用）。

### 性能

目前没有公开文档化的 Strands 与 LangChain 性能基准。两者主要的时间都花在等待 LLM API 调用或运行模型上，因此原始性能差异很可能取决于它们管理 prompt 与工具的效率。Strands 较为轻量，agent 循环的开销可能更小；而 LangChain 的灵活性有时会引入额外层次（例如用正则或 validator 解析输出）。实践中，两者都足够快，任何延迟都由模型推理和外部 API 调用主导。

## 结语

总而言之，Strands 与 LangChain 目标有重叠，但设计中心不同。来自 AWS 的 Strands 强调以最小的麻烦发挥最先进模型的能力，并确保你能可靠地部署与监控这些 agent。LangChain 提供了更宽泛的工具箱来构造 AI 推理流水线，它可以被塑造成 agent 行为，但也需要开发者对工作流长什么样做更多决策。许多解决方案架构师甚至会把两者一起使用，或用于系统的不同层次（你不必只选一个）。像 Strands 这样的框架正在简化 agent 开发——随着 LLM 进步，开发者可以更多关注想让 agent 达成什么，少关注如何微观管理 agent 的步骤。随着生态演进，我们可以期待 Strands 与 LangChain（以及其他框架）相互学习，共同让 AI agent 比以往任何时候都更强大、更健壮、更容易构建。想进一步了解 Strands Agents SDK，请参阅以下资料：
