# 使用 AWS WAF 保护 Amazon Bedrock AgentCore Runtime

当你把生成式 AI agent 以生产 API endpoint 的形式部署在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上时，你可能希望借助 [AWS WAF](https://aws.amazon.com/waf/) 强制执行 Web 应用防火墙策略、限流、常见 Web 威胁防护或审计控制。

AWS WAF 可与 Elastic Load Balancing 的 [Application Load Balancer](https://aws.amazon.com/elasticloadbalancing/application-load-balancer/)（ALB）、[Amazon CloudFront](https://aws.amazon.com/cloudfront/) distribution 以及 [Amazon API Gateway](https://aws.amazon.com/api-gateway/) REST API 集成。我们使用面向公网的 ALB 作为集成点：它透明地透传 header，支持 VPC 内部路由，并可直接挂载 AWS WAF WebACL。由此，你再通过 Bedrock AgentCore 数据平面服务的 VPC Interface Endpoint 把流量路由到 AgentCore。

挑战正出现在这里。ALB 需要健康检查来确认后端 target 有响应。但 AgentCore Runtime 要求 API 调用（包括健康检查请求）必须经过认证——SigV4 或 OAuth。标准 ALB 健康检查发送的是未认证请求，因此开箱即用就会失败。你需要一种办法，让健康检查在没有凭证的情况下也能工作，同时仍把经过认证的生产流量透传到 AgentCore。

本文介绍两种应对该问题的架构模式。两者都使用面向公网、带 AWS WAF 的 ALB，并通过 VPC Interface Endpoint 把流量路由到 AgentCore Runtime。模式 1 在 ALB 与 VPC Endpoint 之间放置一个 [AWS Lambda](https://aws.amazon.com/lambda/) 代理，让你完全掌控请求转换。模式 2 由 ALB 直接指向 VPC Endpoint 的 ENI IP 地址，彻底去掉 Lambda 这一跳。你还会学到如何用资源策略堵住直接访问的后门，使流量只能经由 AWS WAF 通过。两种模式都已使用 SigV4 与 OAuth（Amazon Cognito JWT）认证做过端到端测试。

## 架构概览

两种模式共享同一基础。客户端应用把经过认证的请求（SigV4 签名或 OAuth Bearer token）发送到面向公网的 ALB。AWS WAF 先检查请求，随后 ALB 将其转发到 HTTPS 443 端口上的 VPC Endpoint ENI。AgentCore 校验认证信息，再把请求路由到 runtime 容器的内部端口 8080。两种模式的差异在于 ALB 与 VPC Endpoint 之间放了什么。

高层架构：Client → AWS WAF → ALB → VPC Endpoint（PrivateLink）→ AgentCore Runtime 容器

该架构包含四个组件：

- **AWS WAF** 挂载在 ALB 上，通过 AWSManagedRulesCommonRuleSet 等托管规则组提供限流、SQL 注入防护、XSS 过滤与 bot 控制。
- **ALB** 面向公网，在 443 端口上配置 HTTPS 监听器，把流量路由到 VPC Endpoint ENI IP target。
- **[VPC Interface Endpoint](https://docs.aws.amazon.com/vpc/latest/privatelink/create-interface-endpoint.html)**（`com.amazonaws.<region>.bedrock-agentcore`）通过 PrivateLink 提供到 AgentCore 的私有连接。
- **AgentCore Runtime** 是运行你的 agent 代码的托管容器，监听内部端口 8080，同时支持 SigV4 与 OAuth 认证。

***注意：** 调用 Runtime 时请使用 `com.amazonaws.<region>.bedrock-agentcore`（数据平面）。共有三个独立的 endpoint 服务：bedrock-agentcore（Runtime、Memory、Tools 的数据平面）、bedrock-agentcore-control（控制平面）与 bedrock-agentcore.gateway（仅 Gateway）。用错 endpoint 将无法路由到你的 Runtime。*

## 前提条件

要跟着本演练操作，你需要：

- 一个已启用 Amazon Bedrock AgentCore 的 AWS 账户。
- 已部署的 AgentCore Runtime（public 或 VPC 模式）。
- 一个在至少两个 Availability Zone 中同时拥有公有子网与私有子网的 VPC。
- 同一 Region 中由 AWS Certificate Manager（ACM）签发的证书，供 ALB 的 HTTPS 监听器使用。
- 一个 [Amazon Cognito](https://aws.amazon.com/cognito/) User Pool（用于 OAuth 模式）或 AWS 凭证（用于 SigV4 模式）。
- 熟悉 ALB、VPC Endpoint 与 AWS WAF。

以下章节介绍两种把 AWS WAF 与 AgentCore 集成的模式。如果你需要在 ALB 与 AgentCore 之间做请求转换、自定义日志或认证方式转换，请从模式 1 开始。如果你想要最简单的架构、最低的延迟且不引入额外组件，可直接跳到模式 2。

## 模式 1：ALB 加 Lambda 代理

在该模式中，Lambda 函数位于 ALB 之后，把请求（包括认证 header）经 VPC Endpoint 转发到 AgentCore。Lambda 函数为你提供一个计算层，可以在请求到达 AgentCore 之前转换请求、在认证方式之间转换，或添加自定义日志。

模式 1 架构：Client（JWT）→ AWS WAF → ALB → Lambda Proxy → VPC → VPC Endpoint → AgentCore Runtime（OAuth authorizer）

如果你需要以下能力，请选择模式 1：

- 请求转换、header 操作、payload 修改或协议转换。
- 在代理层做自定义日志或审计轨迹。
- 在多种认证方式之间转换。
- 在 ALB 与后端之间有一个显式计算层（某些安全策略要求如此）。

### 创建 VPC Endpoint

在你的私有子网中为 AgentCore 数据平面服务创建 VPC Interface Endpoint：

```
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-xxxxxxxxx \
  --service-name com.amazonaws.us-east-1.bedrock-agentcore \
  --vpc-endpoint-type Interface \
  --subnet-ids subnet-aaaa subnet-bbbb \
  --security-group-ids sg-xxxxxxxxx
```

*注意：VPC Interface Endpoint 按每个 Availability Zone 收取小时费用，另按 GB 收取数据处理费用。参见 [VPC 定价](https://aws.amazon.com/vpc/pricing/)。*

把 VPC Endpoint 的安全组配置为仅允许来自 ALB 安全组的入站 HTTPS（443 端口）。这样就限制了访问，只有经 ALB 路由的流量才能到达 VPC Endpoint。例如：

```
aws ec2 authorize-security-group-ingress \
  --group-id <vpce-sg-id> \
  --protocol tcp \
  --port 443 \
  --source-group <alb-sg-id>
```

### 创建 Lambda 代理

Lambda 函数接收来自 ALB 的请求，并经 VPC Endpoint 转发到 AgentCore。对于 OAuth，它原样透传 Authorization header（Bearer token），连同原始请求路径与 body 一起转发，因此 JWT 会原封不动地到达 AgentCore。对于 SigV4，签名绑定在原始请求 host 上，请求转发到 VPC Endpoint 后就失效了，因此代理会使用自己执行角色的凭证重新签名。

下面的 Python 片段展示了核心转发逻辑。该函数从 ALB event 中读取 Authorization header，用 VPC Endpoint 的 DNS 名称构造目标 URL，并在保持原始 header 与 body 不变的情况下转发请求。这条转发路径对 OAuth Bearer token 直接可用。SigV4 请求还需要额外的重签名步骤，该步骤包含在配套仓库中。

```
import json
import urllib3
import os

http = urllib3.PoolManager()
VPCE_DNS = os.environ["VPCE_DNS_NAME"]

def handler(event, context):
    path = event.get("path", "/")
    headers = event.get("headers", {})
    body = event.get("body", "")
    method = event.get("httpMethod", "POST")

    target_url = f"https://{VPCE_DNS}{path}"

    resp = http.request(
        method,
        target_url,
        headers={
            "Authorization": headers.get("authorization", ""),
            "Content-Type": headers.get("content-type", "application/json"),
        },
        body=body,
    )

    return {
        "statusCode": resp.status,
        "headers": {"Content-Type": "application/json"},
        "body": resp.data.decode("utf-8"),
    }
```

为简洁起见，上面的片段只聚焦转发逻辑。完整、可用于生产的实现（包括 SigV4 签名、query string 处理、ALB 健康检查响应与结构化错误处理）见[配套 GitHub 仓库](https://github.com/aws-samples/sample-bedrock-agentcore-waf-patterns/blob/main/lambda/sigv4_proxy.py)。

*注意：Lambda 代理按请求数以及计算时长（GB-秒）计费。参见 [AWS Lambda 定价](https://aws.amazon.com/lambda/pricing/)。*

### 配置带 Lambda target group 的 ALB

创建一个 Lambda target group，注册代理函数，并在 ALB 上创建 HTTPS 监听器。ALB 负责 TLS 终止，并把解密后的请求转发给 Lambda 函数。

*注意：Application Load Balancer 按小时计费，并依据流量收取 Load Balancer Capacity Unit（LCU）费用。参见 [Elastic Load Balancing 定价](https://aws.amazon.com/elasticloadbalancing/pricing/)。*

### 挂载 AWS WAF

将一个 AWS WAF WebACL 与 ALB 关联。一个典型的初始配置包括：用于防护常见 Web 威胁的 AWSManagedRulesCommonRuleSet、用于按来源 IP 限制过量请求的基于速率的规则，以及当你的 agent 面向基于浏览器的客户端时使用的 AWSManagedRulesBotControlRuleSet。你可以根据自身的威胁模型增删托管规则组。这些只是示例，不是规定的最低配置。

*注意：AWS WAF 按每个 WebACL 每月、每条规则以及每百万次检查请求计费。参见 [AWS WAF 定价](https://aws.amazon.com/waf/pricing/)。*

***注意：** Lambda target group 不使用基于路径的健康检查。ALB 通过直接调用函数来确认它可被调用，因此无需特殊的健康检查配置。*

### 模式 1 的取舍

| **方面** | **影响** |
| --- | --- |
| 延迟 | 每个请求增加 50–200 ms（Lambda 冷启动）。可通过预置并发缓解。 |
| 成本 | 每个请求的 Lambda 调用费用。 |
| 复杂度 | 需要额外部署、监控与维护一个组件。 |
| 灵活性 | 完全掌控请求/响应转换与自定义日志。 |

***注意：** Lambda 代理会给每个请求增加约 50–200 ms 的延迟。对于延迟敏感的工作负载，可考虑模式 2，它消除了这部分开销。*

## 模式 2：ALB 直连 VPC Endpoint

在该模式中，ALB 直接在 HTTPS 443 端口上指向 VPC Endpoint 的 ENI IP 地址。没有 Lambda 函数，也没有 Network Load Balancer。ALB 把认证 header 透明地透传给 AgentCore。该架构组件更少，并去掉了 Lambda 代理这一跳。

模式 2 架构：Client（JWT 或 SigV4）→ AWS WAF → ALB → VPC Endpoint ENI（HTTPS 443）→ AgentCore Runtime

如果你想要以下效果，请选择模式 2：

- 组件更少的更简单架构。
- ALB 与 AgentCore 之间不做请求转换。
- 没有额外跳数，延迟最低。
- 由客户端应用自己完成 SigV4 或 OAuth 签名。

### 创建 VPC Endpoint

在你的私有子网中为 com.amazonaws.<region>.bedrock-agentcore 创建 VPC Interface Endpoint，使用模式 1 第 1 步中给出的同一条命令。

### 获取 VPC Endpoint 的 ENI IP 地址

获取由 VPC Endpoint 创建的 ENI 的私有 IP 地址。这些 IP 将成为 ALB target group 的 target。

```
# Get the ENI IDs
aws ec2 describe-vpc-endpoints \
  --vpc-endpoint-ids vpce-xxxxxxxxx \
  --query "VpcEndpoints[0].NetworkInterfaceIds"

# Get the private IPs
aws ec2 describe-network-interfaces \
  --network-interface-ids eni-aaaa eni-bbbb \
  --query "NetworkInterfaces[].PrivateIpAddress"
```

### 创建带健康检查的 IP target group

这一步是让模式 2 成立的关键配置。在 HTTPS 443 端口上创建一个 IP 类型的 target group，其健康检查不需要认证。

```
aws elbv2 create-target-group \
  --name agentcore-vpce-tg \
  --target-type ip \
  --protocol HTTPS \
  --port 443 \
  --vpc-id vpc-xxxxxxxxx \
  --health-check-protocol HTTPS \
  --health-check-port 443 \
  --health-check-path / \
  --matcher HttpCode=200-499
```

*注意：该 target group 本身不产生额外费用，但关联的 Application Load Balancer 会产生小时费与 LCU 费用，VPC Interface Endpoint 也会产生小时费与数据处理费用。参见 [Elastic Load Balancing 定价](https://aws.amazon.com/elasticloadbalancing/pricing/)。*

健康检查使用路径 /，匹配器为 200–499。AgentCore 在 / 上返回 404，因为它不是有效的 API 路径，但 ALB 会把 200–499 范围内的响应视为健康。这样可行，因为目标只是确认 VPC Endpoint 有响应，具体状态码并不重要。这种做法让健康检查无需认证。

### 注册 target

把 VPC Endpoint 的 ENI IP 注册为 target：

```
aws elbv2 register-targets \
  --target-group-arn <tg-arn> \
  --targets Id=10.0.1.100,Port=443 Id=10.0.2.200,Port=443
```

### 创建 HTTPS 监听器

在 ALB 上创建一个转发到该 target group 的 HTTPS 监听器。ALB 使用你的 ACM 证书完成 TLS 终止：

```
aws elbv2 create-listener \
  --load-balancer-arn <alb-arn> \
  --protocol HTTPS \
  --port 443 \
  --certificates CertificateArn=<acm-cert-arn> \
  --default-actions Type=forward,TargetGroupArn=<tg-arn>
```

### 挂载 AWS WAF

使用模式 1 第 4 步所述的同一做法，将 AWS WAF WebACL 与 ALB 关联。

### 认证如何穿过 ALB

ALB 原样透传 Authorization header，不做修改。SigV4 签名与 OAuth Bearer token 都能透明地到达 AgentCore。

对于 SigV4（AWS SDK），把 SDK 指向 ALB 的 endpoint URL。SDK 会自动处理签名：

```
import boto3

client = boto3.client(
    "bedrock-agentcore",
    endpoint_url="https://<alb-dns>"
)

response = client.invoke_agent_runtime(
    agentRuntimeArn="arn:aws:bedrock-agentcore:...",
    payload='{"input": "hello"}'
)
```

对于 OAuth（浏览器或 curl），把 JWT 作为 Bearer token 传入：

```
curl -X POST https://<alb-dns>/runtimes/<runtime-arn>/invocations \
  -H "Authorization: Bearer <jwt>" \
  -H "Content-Type: application/json" \
  -d '{"input": "hello"}'
```

***注意：** 在 Amazon Cognito 中使用 client_credentials 授权类型时，JWT 包含 client_id claim 但不含 aud claim。请用 allowedClients（匹配 client_id）而非 allowedAudience 来配置 AgentCore OAuth authorizer。*

| **方面** | **影响** |
| --- | --- |
| 延迟 | 没有 Lambda 延迟开销，直接透传。 |
| 成本 | 无额外计算成本。 |

## 用资源策略堵住直接访问的后门

两种模式都需要一条资源策略，帮助阻止绕过 AWS WAF 直接访问 AgentCore。没有这条策略，持有有效凭证的用户可以绕过 AWS WAF 防护，直接调用 AgentCore 的公有 endpoint。

无资源策略（左）：直接访问绕过 AWS WAF。有资源策略（右）：只允许 VPC Endpoint 流量。

该资源策略包含两条语句。第一条仅在请求源自你特定的 VPC Endpoint（aws:SourceVpce 条件）时允许 InvokeAgentRuntime。第二条拒绝并非源自该 VPC Endpoint 的 InvokeAgentRuntime 请求，并把 aws:ViaAWSService 设为 false，以避免阻断 AgentCore 内部的服务调用。

使用 put-resource-policy API 应用该策略：

下面是一个示例 resource-policy.json 文件：

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowVPCEOnly",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "bedrock-agentcore:InvokeAgentRuntime",
      "Resource": "<runtime-arn>",
      "Condition": {
        "StringEquals": {
          "aws:SourceVpce": "<vpce-id>"
        }
      }
    },
    {
      "Sid": "DenyDirectAccess",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "bedrock-agentcore:InvokeAgentRuntime",
      "Resource": "<runtime-arn>",
      "Condition": {
        "StringNotEquals": {
          "aws:SourceVpce": "<vpce-id>"
        },
        "Bool": {
          "aws:ViaAWSService": "false"
        }
      }
    }
  ]
}
```

```
aws bedrock-agentcore-control put-resource-policy \
  --resource-arn <runtime-arn> \
  --policy file://resource-policy.json
```

### 验证资源策略

应用资源策略后，请验证直接访问已被阻止，而经 AWS WAF 路由的访问正常工作。下表给出预期结果：

| **测试** | **预期结果** |
| --- | --- |
| 经 ALB → VPC Endpoint 的 OAuth | 200 OK，请求经 WAF 与 VPC Endpoint 通过 |
| 直接访问 AgentCore 公有 endpoint 的 OAuth | 403，not authorized to perform bedrock-agentcore:InvokeAgentRuntime |
| 向配置了 OAuth 的 runtime 发送 SigV4 | 403，Authorization method mismatch |
| 经 ALB 但不带认证 | 401，Missing Authentication Token |

## 纵深防御：安全层次

两种模式都提供多层安全防护。每一层应对不同的威胁向量，合在一起构成 agent runtime 的纵深防御态势。下图与下表展示了这些层次如何从最外层边界（AWS WAF）一直堆叠到最内层控制（VPC Endpoint Policy）。请求必须穿过每一层才能到达你的 agent runtime。

纵深防御层次：AWS WAF → ALB 安全组 → VPC Endpoint 安全组 → AgentCore 认证 → 资源策略 → VPC Endpoint Policy

| **层次** | **防护** | **适用范围** |
| --- | --- | --- |
| AWS WAF | 限流、SQL 注入、XSS、bot 控制、地理封锁 | 两种模式 |
| ALB 安全组 | 网络层访问控制，仅允许来自允许来源的 HTTPS 443 | 两种模式 |
| VPC Endpoint 安全组 | 入站仅限 ALB 安全组 | 两种模式 |
| AgentCore 认证 | 每次调用都要求 SigV4 或 OAuth | 两种模式 |
| 资源策略 | 拒绝并非源自 VPC Endpoint 的访问 | 两种模式 |
| VPC Endpoint Policy（可选） | 限定为特定的 IAM principal 或 action | 两种模式 |

## 如何在两种模式间选择

下表总结了关键差异，帮助你选择正确的做法。

| **标准** | **模式 1（Lambda Proxy）** | **模式 2（直连 VPC Endpoint）** |
| --- | --- | --- |
| 组件 | WAF + ALB + Lambda + VPC Endpoint | WAF + ALB + VPC Endpoint |
| 额外延迟 | 50–200 ms | 无 Lambda 跳数 |
| 额外成本 | Lambda 调用 | 无 |
| 请求转换 | 支持，完全掌控 | 不支持 |
| 健康检查方式 | 由 Lambda 处理健康状态 | 路径 /，匹配器 200–499 |
| 认证 | Lambda 转发 token | ALB 透明透传 |
| 复杂度 | 中等 | 低 |
| 何时选它 | 你需要自定义逻辑或多种认证转换 | 你想要最简单、延迟最低的方案 |

在选择模式之前，请先看以下适用于两种架构的注意事项。它们会影响你配置认证、网络与 endpoint 路由的方式。

## 重要注意事项

**仅 443 端口。** VPC Endpoint 只暴露 HTTPS 443。8080 端口（容器的内部端口）无法通过 VPC Endpoint 访问。AgentCore 在内部把 443 路由到 8080。

**不需要 Private DNS。** ALB 直接指向 VPC Endpoint 的 ENI IP，因此两种模式都不需要在 VPC Endpoint 上启用 Private DNS。

**OAuth 会拒绝 SigV4。** 当 AgentCore Runtime 配置了 OAuth authorizer 时，SigV4 请求会以「Authorization method mismatch」被拒绝。每个 runtime 只能选择一种认证方式。

**VPC Endpoint 服务选择。** Runtime 数据平面请使用 bedrock-agentcore。bedrock-agentcore.gateway endpoint 仅用于 AgentCore Gateway，不会路由到你的 Runtime。

**ENI IP 的稳定性。** VPC Endpoint 的 ENI IP 是稳定的，但如果重建 endpoint 就可能变化。请监控 target 健康状态，并在 IP 变化时更新 target。

## 清理

如果你在跟做过程中创建了资源，请将其删除以避免持续计费。先移除资源策略，再解除 AWS WAF WebACL 与 ALB 的关联。删除 ALB（先删监听器与 target group，再删负载均衡器）、VPC Interface Endpoint 以及关联的安全组。对于模式 1，删除 Lambda 函数。如果你创建了测试用的 AgentCore Runtime 或 Amazon Cognito User Pool，请注意删除它们会分别永久移除 agent 配置与用户。

带命令的详细清理顺序见仓库 [README](https://github.com/aws-samples/sample-bedrock-agentcore-waf-patterns/blob/main/README.md)。

## 结论

现在你有了两种经过验证的架构模式，可把 AWS WAF 置于 Amazon Bedrock AgentCore Runtime 之前。模式 2（直连 VPC Endpoint）组件更少、没有 Lambda 延迟开销，并且在多数用例下没有额外成本。模式 1（Lambda 代理）则在你需要请求转换或 ALB 与 AgentCore 之间的自定义认证逻辑时提供灵活性。

无论选择哪种模式，都要应用资源策略堵住直接访问的后门，使流量经 AWS WAF 通过。结合 VPC Endpoint 安全组与 AgentCore 内置的认证，这些模式为你的 AI agent 部署提供了纵深防御。
