# 理解 Amazon Bedrock 模型生命周期

[Amazon Bedrock](https://aws.amazon.com/bedrock/?trk=aa671e0d-f774-4103-92f0-f97df26c3d18&sc_channel=ps&ef_id=Cj0KCQjw5c_FBhDJARIsAIcmHK8qIvVSmisklV0C8S7K1NfurpscXev5-MwMRa_bVlmoQMJc-KThqrEaAvpmEALw_wcB:G:s&s_kwcid=AL!4422!3!770399507977!e!!g!!amazon%20bedrock!22922842282!188068867590&gad_campaignid=22922842282&gbraid=0AAAAADjHtp9QbXGfqIwjJyk2XIx5VqwNt&gclid=Cj0KCQjw5c_FBhDJARIsAIcmHK8qIvVSmisklV0C8S7K1NfurpscXev5-MwMRa_bVlmoQMJc-KThqrEaAvpmEALw_wcB) 会定期发布在能力、准确率和安全性上更好的新基础模型（FM）版本。理解模型生命周期，对于有效规划和管理构建在 Amazon Bedrock 上的 AI 应用至关重要。在迁移应用之前，你可以通过 Amazon Bedrock 控制台或 API 测试这些模型，评估它们的性能与兼容性。

本文介绍如何在 Amazon Bedrock 中管理 FM 的过渡，让你能确保 AI 应用在模型演进时保持可用。我们会讨论三种生命周期状态、如何借助新的扩展访问功能规划迁移，以及把应用平稳迁移到更新模型的实用策略。

## Amazon Bedrock 模型生命周期概览

在 Amazon Bedrock 上提供的模型可以处于三种状态之一：[Active、Legacy 或 End-of-Life（EOL）](https://docs.aws.amazon.com/bedrock/latest/userguide/model-lifecycle.html)。它们的当前状态在 Amazon Bedrock 控制台和 API 响应中都可见。例如，当你调用 [GetFoundationModel](https://alpha.www.docs.aws.a2z.com/bedrock/latest/APIReference/API_runtime_GetFoundationModel.html) 或 [ListFoundationModels](https://alpha.www.docs.aws.a2z.com/bedrock/latest/APIReference/API_runtime_ListFoundationModels.html) 时，模型状态会显示在响应中的 `modelLifecycle` 字段里。

下图说明了每种模型状态的相关细节。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/22/ml-19718-image-1.png)

各状态的细节如下：

- **ACTIVE** – 活跃模型会持续获得来自其提供方的维护、更新和缺陷修复。当模型处于 `Active` 状态时，你可以通过 `InvokeModel` 或 `Converse` 等 API 用它做推理、对它做定制（若支持），并通过 AWS Service Quotas 申请提高配额。
- **LEGACY** – 当模型提供方把某个模型转为 `Legacy` 状态时，Amazon Bedrock 会在 EOL 日期之前至少提前 6 个月通知客户，为客户留出规划并执行迁移到更新或替代模型版本的必要时间。在 `Legacy` 期间，既有客户可以继续使用该模型，但新客户可能无法访问它，而且既有客户如果连续 15 天或更久不调用该模型，非活跃账户可能会失去访问权。组织应注意：按模型单元新建预置吞吐量将不再可用，模型定制能力也可能受到限制。对于 EOL 日期在 2026 年 2 月 1 日之后的模型，Amazon Bedrock 在 `Legacy` 状态内引入了一个额外阶段：**公开扩展访问期**——在 `Legacy` 状态停留至少 3 个月后，模型进入这一扩展访问阶段。活跃用户可以继续使用它至少再 3 个月，直至 EOL。在扩展访问期间，通过 AWS Service Quotas 提出的配额提高申请预计不会被批准，因此请在模型进入该阶段之前规划好容量需求。在此期间定价可能会调整（见下文“扩展访问期间的定价”），客户也会收到关于过渡日期和任何变更的通知。
- **END-OF-LIFE（EOL）** – 当模型到达 EOL 日期后，它在所有 AWS 区域都将完全无法访问，除非在 [EOL 列表](https://docs.aws.amazon.com/bedrock/latest/userguide/model-lifecycle.html#versions-for-eol) 中特别注明。对 EOL 模型的 API 请求会失败，使这些模型对大多数客户不可用，除非客户与提供方之间就继续访问存在特殊安排。向 EOL 的过渡需要客户主动行动——迁移不会自动发生。组织必须在 EOL 日期到来之前更新应用代码以使用替代模型。一旦到达 EOL，模型对大多数客户来说就完全无法访问了。

模型在 Amazon Bedrock 上线后，至少会在上线后 12 个月内保持可用，并在 EOL 之前至少在 `Legacy` 状态停留 6 个月。这个时间线能帮助客户从容规划迁移。

## 扩展访问期间的定价

在扩展访问期间，定价可能由模型提供方调整。如果有定价变更计划，你会在一开始的 Legacy 公告中以及任何后续变更生效之前收到通知，因此不会出现令人意外的追溯涨价。与模型提供方签有私有定价协议或使用预置吞吐量的客户，在扩展访问期间继续按其现行定价条款运行。这确保已与模型提供方达成特定安排或已投入预置容量的客户，不会意外受到任何定价变动的影响。

## 模型状态变更的沟通过程

当模型提供方把模型转为 Legacy 状态时，客户会在模型 EOL 日期前 6 个月收到通知。这种主动沟通的方式确保客户有足够时间在模型进入 EOL 之前规划和执行迁移策略。
通知内容包括被弃用模型的详情、重要日期、扩展访问的可用性，以及模型何时进入 EOL。AWS 使用多种渠道确保这些重要通信能到达合适的人，包括：

- 电子邮件通知
- [AWS Health Dashboard](https://health.console.aws.amazon.com/health/home#/account/dashboard/scheduled-changes?viewType=table)
- Amazon Bedrock 控制台中的告警
- 通过 API 的程序化访问。

为确保你能收到这些通知，请核实并配置你账户的联系邮箱。默认情况下，通知会发送到账户的根用户邮箱以及备用联系人（运营、安全和账单）。你可以在 [AWS 账户页面](https://console.aws.amazon.com/billing/home#/account) 的 Alternate contacts 区域查看并更新这些联系人。若要添加额外的收件人或投递渠道（例如 Slack 或邮件分发列表），请前往 [AWS User Notifications 控制台](https://console.aws.amazon.com/notifications)，选择 AWS managed notifications subscriptions 来管理你的投递渠道和账户联系人。如果你没有收到预期的通知，请检查这些设置中的邮箱地址是否配置正确，以及来自 health@aws.com 的通知邮件是否被你的邮件提供商过滤。

## 迁移策略与最佳实践

迁移到更新的模型时，请更新应用代码，并检查你的[服务配额](https://docs.aws.amazon.com/general/latest/gr/aws_service_limits.html)能否承受预期流量。提前规划有助于你以最小的中断平稳过渡。

### 规划迁移时间线

模型一进入 `Legacy` 状态就开始规划：

- **评估阶段** – 评估你当前对遗留模型的使用情况，包括哪些应用依赖它、典型的请求模式，以及你的应用所依赖的具体行为或输出。
- **调研阶段** – 调查推荐的替代模型，理解它的能力、与遗留模型的差异、可能增强你应用的新功能，以及新模型的区域可用性。审阅 API 变更和文档。
- **测试阶段** – 用新模型做充分的测试，并比较两个模型之间的性能指标。这有助于识别你的应用代码或 prompt 工程需要做哪些调整。
- **迁移阶段** – 采用分阶段部署的方式来实施变更。在过渡期间监控系统性能，并保持回滚能力。
- **运营阶段** – 迁移之后，持续监控你的应用和用户反馈，确保它们在新模型下按预期运行。

### 技术迁移步骤

彻底测试你的迁移：

- **更新 API 引用** – 修改应用代码，引用新的模型 ID。例如，从 `anthropic.claude-3-5-sonnet-20240620-v1:0` 换成 `anthropic.claude-sonnet-4-5-20250929-v1:0` 或[全球跨区域推理](https://aws.amazon.com/blogs/machine-learning/unlock-global-ai-inference-scalability-using-new-global-cross-region-inference-on-amazon-bedrock-with-anthropics-claude-sonnet-4-5/) `global.anthropic.claude-sonnet-4-5-20250929-v1:0`。按新模型的最佳实践更新 prompt 结构。更详细的指引请参阅[在 Amazon Bedrock 上从 Anthropic 的 Claude Sonnet 3.x 迁移到 Claude Sonnet 4.x](https://aws.amazon.com/blogs/machine-learning/migrate-from-anthropics-claude-sonnet-3-x-to-claude-sonnet-4-x-on-amazon-bedrock/)。
- **申请提高配额** – 在完全迁移之前，若有必要，通过 AWS Service Quotas 控制台申请提高配额，确保新模型有足够的配额。
- **调整 prompt** – 更新的模型对相同 prompt 的响应可能不同。请按新模型的规格审阅并改进你的 prompt。你也可以使用 [Amazon Bedrock 中的 prompt optimizer](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-management-optimize.html) 这类工具，帮助你为目标模型重写 prompt。
- **更新响应处理** – 如果新模型以不同格式或不同特征返回响应，请相应更新你的解析与处理逻辑。
- **优化 token 用量** – 利用更新模型在效率上的改进，审阅并优化你的 token 使用模式。例如，支持 [prompt caching](https://aws.amazon.com/bedrock/prompt-caching/) 的模型可以降低调用的成本与延迟。

### 测试策略

彻底的测试对成功迁移至关重要：

- **并排对比** – 对遗留模型和新模型运行相同的请求，比较输出并找出可能影响你应用的差异。对生产环境，可以考虑影子测试——把重复的请求在你现有模型之外同时发给新模型，而不影响终端用户。用这种做法，你可以在完全迁移之前评估模型的性能、延迟、错误率以及其他运营因素。要做评估用户影响的 A/B 测试，可把受控比例的线上流量路由到新模型，同时监控用户参与度、任务完成率、满意度分数和业务 KPI 等关键指标。
- **性能测试** – 测量响应时间、token 用量以及其他性能指标，了解新模型相比遗留版本的表现。验证业务特定的成功指标。
- **回归与边界情况测试** – 确保现有功能在新模型下继续按预期工作。特别关注那些可能暴露两个模型在处理复杂场景时差异的异常或复杂输入。

## 结论

Amazon Bedrock 的模型生命周期策略为管理 FM 的演进提供了清晰的阶段。过渡期提供扩展访问选项，针对微调模型的规定则帮助你在创新与稳定之间取得平衡。

通过 AWS Health Dashboard 随时了解模型状态，在模型进入 `Legacy` 状态时规划迁移，并彻底测试更新的版本。这些指引可以帮助你在使用更新模型改进能力的同时，保持 AI 应用的连续性。

如果你还有疑问或顾虑，请联系你的 AWS 团队。我们希望帮助你，在你继续利用 FM 技术最新进展的过程中促成平稳过渡。
