# 在多账户环境中启用 Amazon Bedrock 跨区域推理

[Amazon Bedrock](https://aws.amazon.com/bedrock/) 的跨区域推理能力为组织提供了跨 AWS 区域访问基础模型（FM）的灵活性，同时保持最佳性能与可用性。然而，一些企业通过[服务控制策略](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html)（SCP）或 [AWS Control Tower](https://aws.amazon.com/controltower/) 实施严格的区域访问控制以符合合规要求，却无意中阻断了 Amazon Bedrock 的跨区域推理功能。这使组织陷入两难：必须在安全控制与使用 AI 能力之间取得平衡。

本文探讨如何修改区域访问控制，专门放行 Amazon Bedrock 的[跨区域推理](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)，同时保持对其他 AWS 服务的更广泛区域限制。我们为 SCP 修改和 AWS Control Tower 实现都提供了实际示例。

## 理解跨区域推理

在按需模式下运行模型推理时，你的请求可能受服务配额限制，或在用量高峰期受限。跨区域推理让你能够利用不同区域的计算资源，无缝应对非预期的流量突发。借助跨区域推理，你可以在多个区域之间分配流量，从而获得更高的吞吐量。

许多组织通过以下方式实施区域访问控制：

- [AWS Organizations](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_introduction.html) 中的 SCP
- [AWS Control Tower 控制](https://docs.aws.amazon.com/controltower/latest/controlreference/controls.html)
- 自定义的 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）策略

出于安全、合规或成本管理的考虑，这些控制通常会拒绝访问特定区域内的所有服务。然而，这些宽泛的拒绝也会导致 Amazon Bedrock 在需要通过跨区域推理访问这些区域中的模型时无法正常工作。

## 跨区域推理的工作方式及其与 SCP 的交互

Amazon Bedrock 的跨区域推理是一项强大功能，可为推理请求实现自动的跨区域路由。这项能力对使用按需推理模式的开发者尤其有利，因为它提供了无缝方案，在由 Amazon Bedrock 驱动的应用中实现更高吞吐量与性能，同时有效应对传入的流量峰值。

借助跨区域推理，开发者无需再手工预测需求波动。系统会动态地在多个区域之间路由流量，保持最优的资源利用率和性能。重要的是，跨区域推理会尽可能优先选择请求所连的 Amazon Bedrock API 源区域，有助于降低延迟并提升整体响应速度。这种智能路由增强了应用的可靠性、性能和效率，而无需开发团队持续人工盯守。

其核心在于两个关键概念：源区域（source Region）与履行区域（fulfillment Region）。源区域也称为发起区域，是客户端最初发起推理请求的地方。相反，履行区域则是实际为大语言模型（LLM）调用请求提供服务的区域。

跨区域推理采用 Amazon 持续演进的专有自定义路由逻辑，为客户提供最佳推理体验。该路由机制刻意采用启发式方法，首要目标是提供高可用性。默认情况下，服务会尽可能尝试由源区域满足请求，但也会按需把请求无缝路由到其他区域。这种智能路由会考虑区域容量、延迟和可用性等因素以做出最优决策。

尽管跨区域推理提供了强大的灵活性，但它需要能够访问所有潜在履行区域中的模型才能正常工作。正是这一要求，使 SCP 可能显著影响跨区域推理功能。

我们来看一个场景，它凸显了跨区域推理与 SCP 之间的关键交互。如下图所示，我们使用 us-east-1 和 us-west-2 两个区域，并通过一条 SCP 拒绝所有其他区域——这条 SCP 既可以用 AWS Organizations 实现，也可以用 AWS Control Tower 控制实现。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/25/ML-18467-image001.jpg)

该工作流包含以下步骤：

- 用户使用跨区域推理配置文件，向 `us-east-1` 的 Amazon Bedrock 端点（源区域）发起推理请求。
- Amazon Bedrock 基于启发式的路由系统会评估可用于满足请求的区域。
- `us-west-2` 和 `us-east-1` 通过 SCP 被允许访问 Amazon Bedrock 服务，但 `us-east-2` 被 SCP 拒绝。
- 仅这一条区域限制（`us-east-2`）就导致跨区域推理调用失败。
- 即使其他区域可用且被允许，只要存在一个被阻断的区域（`us-east-2`），请求就会失败。
- 客户端收到一个错误，表明其无权执行该操作。

这种行为是设计使然；跨区域推理服务需要能够访问所有潜在履行区域来运行推理，才能保持其最优路由请求的能力。只要有任何潜在目标区域被 SCP 阻断，无论其他区域是否可用，使用跨区域推理的尝试都会失败。要成功实施跨区域推理，组织必须确保其 SCP 允许在目标模型可用的所有区域中调用 Amazon Bedrock API 操作。这意味着要找出托管所需模型的所有区域，修改 SCP 以在这些区域中允许最小必需的 Amazon Bedrock 权限，并在所有相关区域中维持这些权限——即使某些区域并非主要运营区域。我们将在后续小节中给出关于 SCP 修改和 AWS Control Tower 实现的具体指导，以启用跨区域推理功能。

## 用例

在我们的示例用例中，我们使用 `us-east-1` 和 `us-west-2` 两个区域。所有其他区域都通过 landing zone 的区域拒绝控制（[GRREGIONDENY](https://docs.aws.amazon.com/controltower/latest/userguide/region-deny.html)）拒绝。允许使用 Amazon Bedrock 的客户 AWS 账户位于名为 Sandbox 的组织单位（OU）之下。我们希望让 Sandbox OU 下的账户使用 Anthropic 的 Claude 3.5 Sonnet v2 模型进行跨区域推理。该模型在 `us-east-1`、`us-east-2` 和 `us-west-2` 中可用，如下方截图所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/26/ML-18467-image003-new.jpg)

在当前状态下，当用户尝试使用 Anthropic 的 Claude 3.5 Sonnet v2 模型进行跨区域推理时，会收到错误，提示 SCP 正在拒绝该操作。

## 修改现有 SCP 以允许 Amazon Bedrock 跨区域推理

如果你没有使用 AWS Control Tower 来治理多账户 AWS 环境，可以创建新的 SCP 或修改现有 SCP，以允许 Amazon Bedrock 跨区域推理。

以下代码展示了如何修改一条现有 SCP：它拒绝访问特定区域中的所有服务，同时允许 Anthropic 的 Claude 3.5 Sonnet V2 模型通过跨区域推理使用 Amazon Bedrock 推理：

```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenySpecificRegionAllowCRI",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:RequestedRegion": "us-east-2"
        },
        "ArnNotLike": {
          "bedrock:InferenceProfileArn": "arn:aws:bedrock:*:*:inference-profile/us.anthropic.claude-3-5-sonnet-20241022-v2:0"
        }
      }
    }
  ]
}
```

该策略有效阻断了 `us-east-2` 区域中的所有操作，但指定资源除外。这是一条基于拒绝的策略，意味着它应与允许策略配合使用，才能定义完整的权限集合。

在生产环境中实施之前，你应该审阅这个示例，并根据你组织的具体需求和安全要求进行调整。

实施这些策略时，请考虑以下事项：

- 自定义区域和允许的资源，以符合你的具体需求
- 在你的环境中充分测试，确保它不会意外阻断必需的服务或操作
- 记住 SCP 会影响其所附加账户中的用户和角色，包括 root 用户
- 服务相关角色不受 SCP 影响，这使其他 AWS 服务能够与 AWS Organizations 集成

## 使用 AWS Control Tower 实施

AWS Control Tower 会创建 SCP 来管理整个组织的权限。不建议手动编辑这些 SCP，因为这可能导致 AWS Control Tower 环境出现漂移（drift）。不过，有一些方法可以允许特定的 AWS 服务，我们将在后续小节讨论。

## 先决条件

请确保你运行的是最新版本的 AWS Control Tower。如果你使用的版本低于 3.x，且已通过 AWS Control Tower 设置拒绝了某些区域，你需要升级 AWS Control Tower 版本以更新区域拒绝设置。请参阅以下关于从 2.x 升级到 3.x 的 AWS Control Tower[注意事项](https://repost.aws/articles/AROghsOAN3QwOpF9COQDsC3w/upgrade-control-tower-landing-zone-from-2-x-to-3-x)。

此外，请确保 AWS Control Tower 上的 Organization 仪表板没有显示策略漂移，且各 OU 与账户均处于合规状态。

## 选项 1：扩展现有的区域拒绝 SCP 以支持跨区域推理

AWS Control Tower 提供两种主要的区域拒绝控制，用于按区域限制对 AWS 服务的访问：

- [GRREGIONDENY](https://docs.aws.amazon.com/controltower/latest/controlreference/primary-region-deny-policy.html)（landing zone 区域拒绝控制）– 该控制作用于整个 landing zone，而不是特定 OU。启用后，它会禁止在指定区域之外对全局服务和区域服务执行操作，包括 AWS Control Tower 不可用的所有区域以及未选择纳入治理的所有区域。
- [MULTISERVICE.PV.1](https://docs.aws.amazon.com/controltower/latest/controlreference/ou-region-deny.html)（OU 区域拒绝控制）– 这一可配置的控制可以应用于特定 OU，而不是整个 landing zone。它会禁止某个组织单位在指定区域之外对全局和区域 AWS 服务中未列出的操作进行访问。该控制是可配置的。它接受一个或多个参数，例如 `AllowedRegions`、`ExemptedPrincipalARNs` 和 `ExemptedActions`，这些参数描述了对此 OU 中账户允许的操作：  **AllowedRegions** – 指定所选区域，OU 被允许在其中运营。该参数为必填。**ExemptedPrincipalARNs** – 指定不受该控制约束的 IAM 主体，以便它们可以在全局范围内操作某些 AWS 服务。**ExemptedActions** – 指定不受该控制约束的操作，以便这些操作被允许。

我们将使用 [CT.MULTISERVICE.PV.1](https://docs.aws.amazon.com/controltower/latest/controlreference/ou-region-deny.html#configurable-region-deny) 控制，并针对我们的场景进行配置。

- 创建一个 IAM 角色，并附加一条允许通过跨区域推理使用 Amazon Bedrock 推理的 IAM 策略。我们将该 IAM 角色命名为 Bedrock-Access-CRI。稍后我们会用到它。该 IAM 角色将在属于 Sandbox OU 的 AWS 账户中创建。  ` { "Version": "2012-10-17", "Statement": [ { "Sid": "AllowBedrockInference", "Effect": "Allow", "Action": [ "bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream" ], "Resource": [ "arn:aws:bedrock:*:*:inference-profile/us.anthropic.claude-3-5-sonnet-20241022-v2:0", "arn:aws:bedrock:*::foundation-model/anthropic.claude-3-5-sonnet-20241022-v2:0" ] } ] }`

- 前往 **Landing zone settings** 页面，选择 **Modify settings**。
- 启用该区域（在我们的示例中是 `us-east-2`），其余设置保持不变。
- 选择 **Update landing zone** 完成更改。

更新可能需要最多 60 分钟甚至更久，取决于组织的规模。这会更新 landing zone 的区域拒绝设置（`GRREGIONDENY`），把 us-east-2 区域纳入治理。

- landing zone 设置完成后，检查 Organization 设置，确保各 OU 中的 AWS 账户没有待处理的更新。如果你看到待处理的更新，请完成更新，并确保账户状态显示为 **Enrolled**。
- 在 AWS Control Tower 控制台的导航窗格中，在 **Controls library** 下选择 **All controls**，查看控制列表。
- 找到 `MULTISERVICE.PV.1`，选择该策略以打开该控制。
![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/25/ML-18467-image005.jpg)
- 选择 **Control actions**，然后选择 **Enable** 开始配置。
- 在 **Select an OU** 页面上，选择要应用该控制的 OU。对于我们的用例，我们使用 Sandbox OU。
- 选择 **Next**。
![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/25/ML-18467-image007.jpg)
- 在 **Specify Region access** 页面上，选择允许该 OU 访问的区域。对于我们的用例，我们选择 `us-west-2` 和 `us-east-1`。

我们不选择 `us-east-2`，因为我们希望拒绝 `us-east-2` 上的所有服务，只允许 Amazon Bedrock 通过跨区域推理进行推理。

- 选择 **Next**。
- 在 **Add service actions – optional** 页面上，把 Amazon Bedrock 的操作添加到 **NotActions** 中。我们添加 `bedrock:Invoke*`，以允许 Amazon Bedrock 的 InvokeModel 操作。
- 选择 **Next**。
![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/25/ML-18467-image009.jpg)

- 在 **Specify configurations and tags – optional** 页面上，在 **Exempted principals** 下添加我们先前创建的 IAM 角色，然后选择 **Next**。

**注意**：在这种情况下不需要 `ExemptedPrincipalARNs` 参数，因为上一步已经把 `bedrock:Invoke*` 加入 `NotActions`。只要调用方自身的 IAM 策略允许，该控制就不再对 OU 中的任何主体拒绝这些操作。仅当你需要为特定主体豁免超出 `NotActions` 所列范围的操作时，才使用 `ExemptedPrincipalARNs`。豁免某个主体会为该主体移除该控制所覆盖的全部操作的区域限制，而不仅是 Amazon Bedrock 操作。
![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/25/ML-18467-image011.jpg)

- 检查配置并选择 **Enable control**。

控制启用后，你可以通过选择 **OUs enabled**、**Accounts**、**Artifacts** 以及 **Regions** 标签页来查看配置。

至此配置完成。你可以通过假设上一步提到的自定义 IAM 角色（`Bedrock-Access-CRI`），使用 Amazon Bedrock 控制台或 API 测试 Anthropic 的 Sonnet 3.5 v2 的 Amazon Bedrock 推理。

你会看到，从三个区域（`us-east-1`、`us-east-2` 和 `us-west-2`）中的任意一个出发，都能使用跨区域推理仅对 Anthropic 的 Sonnet 3.5 v2 模型发起 Amazon Bedrock 推理调用。由于你先前配置了 `CT.MULTISERVICE.PV.1` 控制，尝试访问 `us-east-2` 上的其他服务都会被阻断。

通过采用这些方法，你可以安全地扩展由 AWS Control Tower 管理的权限，而不会造成漂移或损害你的治理控制。

## 选项 2：使用 AWS Control Tower 启用被拒绝的区域，并通过 SCP 有条件阻断

在这个选项里，我们启用被拒绝的区域（`us-east-2`），并创建一条新的 SCP，有条件地阻断 us-east-2，同时允许 Amazon Bedrock 通过跨区域推理进行推理。

- 前往 **Landing zone settings** 页面，选择 **Modify settings**。
- 启用该区域（在我们的示例中是 `us-east-2`），其余设置保持不变。
- 选择 **Update landing zone** 完成更改。

更新可能需要最多 60 分钟甚至更久，取决于组织的规模。你可以在控制台上监控这次更新的状态。

- landing zone 设置完成后，检查 Organization 设置，确保各 OU 中的 AWS 账户没有待处理的更新。如果你看到待处理的更新，请完成更新，并确保账户状态显示为 **Enrolled**。
- 在 AWS Control Tower 控制台的导航窗格中，在 **Policies** 下选择 **Service Control Policies**。
- 使用前面展示的示例策略创建一条新的 SCP。该 SCP 会拒绝 `us-east-2` 的所有操作，同时允许通过 CRI 配置文件 ARN 对 Anthropic 的 Claude Sonnet 3.5 v2 发起 Amazon Bedrock 推理。
- 将这条 SCP 应用到特定 OU。在本场景中，我们使用 Sandbox OU。

由于你创建的是新的 SCP，而不是修改 AWS Control Tower 创建的现有 SCP，因此不会在 AWS Control Tower 状态中看到漂移。

你现在可以使用 Amazon Bedrock 控制台或 [AWS Command Line Interface](https://aws.amazon.com/cli)（AWS CLI）运行几次推理调用，来测试这次更新。你会看到，从三个区域（`us-east-1`、`us-east-2` 和 `us-west-2`）中的任意一个出发，都能使用跨区域推理仅对 Anthropic 的 Sonnet 3.5 v2 模型发起 Amazon Bedrock 推理调用。对 `us-east-2` 上其他 AWS 服务的访问将被拒绝。

## 总结

Amazon Bedrock 跨区域推理为希望跨区域使用 FM 的组织提供了宝贵的灵活性。通过谨慎修改你的服务控制策略或 AWS Control Tower 控制，你可以在保持更广泛区域访问限制的同时启用该功能。

这种方法使你能够：

- 维持对区域访问要求的合规性
- 充分利用 Amazon Bedrock 的完整能力
- 通过从主区域访问模型来简化应用架构

跨区域推理（包括该功能提供的故障转移能力）不产生额外费用。这涵盖管理、数据传输、加密、网络使用，以及每个模型每百万 token 价格上的潜在差异。你支付的价格与源区域中各个模型每 token 的价格相同。

随着 AI 和机器学习能力持续演进，在安全控制与创新赋能之间找到恰当的平衡，仍将是组织面临的关键挑战。本文所述的方法为这一具体挑战提供了切实可行的解决方案。
