*本文由来自 HEMA 的 Mauro Rallo 和 Patrick van der Plas 联合撰写。*

当 [HEMA](https://corporate.hema.com/en/about-us/) 的工程师需要一个答案时，他们会做门户跳转——在彼此割裂的 wiki、服务目录和 IT 门户之间导航去找它。要把这份摩擦变成即时答案，这家有百年历史的荷兰零售商在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上构建了一个知识层。HEMA 在多个国家拥有超过 750 家门店，由一个由工程师、产品负责人和业务分析师组成的、驱动数字化转型的技术组织服务。它需要一个跨角色和跨工具都能运作的方案。

多年来，HEMA 悄然构建了某种有价值的东西：一幅关于自身技术格局的庞大、有结构的图景。一个服务目录把人员映射到团队、团队映射到服务、服务映射到我们暴露的 API 以及我们支撑的业务能力。问题从来不是知识不存在，而是知识难以触达。随着工程组织成长，那种非正式的“*就问旁边那个人*”的模式失效了，团队最终把答案散落在少数人才知道如何 navigating 的门户、wiki 和文档里。

在本文中，我们描述 HEMA 面对的内部知识碎片化挑战、为什么我们选择用 [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro) (MCP) 和 Amazon Bedrock AgentCore 构建 HAL——HEMA 的内部 AI 助手——以及它如何改变了我们团队的工作方式。

这个想法建立在两个相辅相成的目标之上。HAL 把知识放在一处，而 MCP 把那份知识送进人们已经在使用的工具里（HAL 聊天、[Kiro](https://kiro.dev/)、[Claude](https://claude.ai/) 和其他智能体）。安全锚定在 Microsoft Entra ID，客户端上没有 AWS 凭证。一个起初作为开发者工具的东西，如今已是一个跨角色助手。同一套架构将作为下一步的基础：把 HAL 从一个只读知识层变成一个动作层。

## 挑战：门户跳转与知识碎片化

HEMA 的知识问题有两个不同的层次。

**第一层**——有结构的基础设施知识——其实状况良好。多年来，HEMA 一直维护着一个服务目录，记录了整套技术资产如何拼合在一起：哪些团队拥有哪些服务、那些服务暴露什么 API，以及它们如何映射到业务能力。来自产品信息管理（PIM）引擎和数据网格表等系统的结构化数据已被导入并整理。对于任何“有什么、谁拥有它”的问题，答案通常都可获得——只要你懂得去哪里找。

**第二层**才是缺口。知道有什么，不等于知道怎么做某件事。“*我如何申请一个 API 的访问权？我如何开通一个新群组？我们对 X 的规则是什么？*”这些程序性问题没有一个单一的归宿。当团队小、彼此都认识时，这没问题，人们直接问就是了。随着 HEMA 成长、引入新工程师，那套模式停止扩展，且几乎没有书面文档可作依托。

这转化为对新入职者缓慢的上手、因某人去看哪里而不同的不一致答案、不断的上下文切换，以及把人从其实际工作中拽出的摩擦。过去意味着要 navigating 三四个门户、有时耗掉整个下午才能找一个答案，如今在几秒钟内完成——从集成开发环境（IDE）或聊天窗口内部。

## 为什么选 MCP 和 Amazon Bedrock AgentCore

两个目标塑造了这一方案，并且它们干净地映射到我们选择的这两项技术上。

**第一个目标**属于 **HAL**：把 HEMA 碎片化的知识整合进一个受治理的唯一事实来源。**第二个目标**属于 **MCP**：把那份知识送到人们已经工作的地方，而不是逼他们再去访问又一个门户。

**为什么选 MCP：** Model Context Protocol 在 AI 客户端和后端能力之间给了我们一个标准化接口。我们不必为每个知识源做一个定制集成、并为每个客户端应用重做一遍，而是把每个源作为一次一个 MCP 工具暴露出来。

兼容 MCP 的客户端，如 HAL Web 聊天、Kiro、Claude 和其他智能体，于是可以消费同样的工具而无需定制工作。正是这一点让“从你的日常工具访问”变得可行，而不是一个逐工具的工程项目。

**为什么选 Amazon Bedrock AgentCore：** Amazon Bedrock AgentCore 是一个以任意框架或模型大规模构建、连接并优化智能体的平台。对 HEMA 而言，这意味着构建 HAL 而无需搭建和运营定制的 MCP server 基础设施。最重要的那些能力有：

- [Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-building.html) 直接把 OpenAPI 规范和 [AWS Lambda 函数](https://aws.amazon.com/lambda/) 变成 MCP 工具。没有需要编写或运行的定制 MCP server 代码。
- [Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-oauth.html) 提供受管的入站 JSON Web Token (JWT) 认证，以及到我们内部 API 的受管出站 OAuth2（一个令牌保险库）。
- [Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 以容器形式托管内部智能体（用 Strands 框架构建）。
- [Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html) 和 [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) 提供会话记忆和内容过滤，并带欧盟推理区域和荷兰语支持。

合起来，这些给了我们适合企业的根基：Entra ID OAuth、目前的只读访问，以及由现有 Active Directory 组驱动的访问控制——足够安全地暴露真实的内部知识。

## 一步步构建 HAL

HAL 并非一开始就成形。它以两个刻意的步骤成长起来。首先，团队构建了一个带自己聊天 UI 的独立助手。然后，当那个基础证明自己后，我们通过 MCP 把它开放到人们已经在其中工作的工具里。

### 步骤 1：HAL 作为独立助手

HAL 的第一个版本是一个自包含的助手：一个 Web 聊天 UI（用 `Next.js` 构建），由一个能从 HEMA 知识中回答问题的智能体支撑。那时没有 MCP、没有外部客户端，只有 HAL UI 在与 HAL 智能体对话。

**HAL 智能体**是一个 [Strands](https://github.com/strands-agents/sdk-python) 智能体，被打包成一个 `Linux/ARM64` 容器并托管在 AgentCore runtime 上，连同 AgentCore memory（短期会话上下文）和 Amazon Bedrock Guardrails（Standard 层级，为荷兰语支持用欧盟跨区域推理）。AgentCore runtime 和 AgentCore memory 都是 Amazon Bedrock AgentCore 的能力。

该智能体沿两条不同的路径触达知识：

- **本地工具，直接到知识库。** 智能体的语义搜索工具是本地 Strands 工具，通过 Knowledge Bases 直接调用 Amazon Bedrock Retrieve API，中间没有 gateway。这是那个做基本活的“*从知识库回答*”路径。
- **到 AgentCore Gateway 的 MCP，用于实时 API。** 对于实时数据、完整 OpenAPI 规范、服务目录查找和人员/团队查询，智能体通过 MCP 连接到它自己的 AgentCore Gateway（Amazon Bedrock AgentCore 的一项能力）。这个 Gateway 用 [AWS Identity and Access Management](https://aws.amazon.com/iam/) (IAM) [SigV4](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv.html) 认证，进而调用我们的内部 API。

图 2：步骤 1，HAL 作为独立助手

我们从已有的结构化数据——服务目录——起步，加上最有价值的文档，按痛点和被问频率排序优先级。在 HAL 背后坐着若干建立在 Amazon Bedrock Knowledge Bases 上的知识库——那个完全托管的检索增强生成（RAG）能力：IT 与操作文档、API/OpenAPI 规范、Kafka 事件流主题及其 Avro schema、数据整合层（DCL）数据交换通道，以及服务目录（人员、团队、服务和 API）。

没有定制 MCP server 代码。AgentCore Gateway 为 API 透传目标直接从 OpenAPI 规范生成 MCP 工具，并为知识库上的语义搜索从一个 Lambda 函数生成。把 Gateway 直接指向我们现有的 API 规范并非理想的最终状态。一个为系统到系统使用而设计的 API 并不总能干净地映射到一个智能体可推理的工具，所以我们计划把那些定义重构为更适合智能体的工具。

不过现在，原样暴露这些 API 以小得多的努力交付了高价值。`kb-search` Lambda 封装了对知识库的 Amazon Bedrock Retrieve API。它由 AWS Identity and Access Management (IAM) 限定到具体的 Knowledge Base 的 Amazon Resource Name (ARN)，外加对源文档 [Amazon Simple Storage Service](https://aws.amazon.com/s3/) (Amazon S3) 桶的读访问。

检索遵循一个两步模式：一次初始知识库搜索回答大多数问题，而当单个块不够时 `fetch_full_document` 拉取完整文档。检索质量通过语义查询上的 Amazon Bedrock 重排（reranking）以及用于团队范围查找的 `team_id` 元数据过滤来提升。

### 步骤 2：用 MCP 把 HAL 开放给日常工具

HAL 在自己的聊天 UI 里表现良好，但人们住在其他工具里：他们的 IDE、他们的 AI 助手。第二步是让外部 MCP 客户端（如 Kiro 和 Claude）能触达同样的知识和工具，而不分发 AWS 凭证。那意味着添加第二个 AgentCore Gateway，用 Microsoft Entra ID 而非 IAM 认证。

因为一个 AgentCore Gateway 只支持单一入站认证类型，我们无法把这些外部客户端复用步骤 1 中那个智能体的 IAM 认证 Gateway。于是我们添加了第二个 Gateway——一个通过 Microsoft Entra ID 用定制 JWT 认证的 Entra MCP Gateway，专用于 Kiro、Claude 等外部 MCP 客户端。它与智能体 Gateway 只共享只读的知识库。没有共享代码，因此对外暴露的界面可以演进或失败，而不影响内部智能体。

图 3：步骤 2，用 MCP 把 HAL 开放给日常工具

AgentCore Gateway 从 OpenAPI 规范和 Lambda 函数暴露工具。要把知识库呈现为一个 Gateway target，我们构建了一个小的中间 Lambda 函数，Gateway 把它当工具调用，而它代 Gateway 在知识库上执行语义搜索。相比之下，实时的内部 API 直接作为 OpenAPI target 暴露。

#### 难啃的部分：认证与动态客户端注册（DCR）

有一件有趣的事是外部客户端如何不带 AWS 凭证认证。在 Entra Gateway 前面坐着一个 MCP 认证代理——一个由单个 Lambda 支撑的 [Amazon API Gateway](https://aws.amazon.com/api-gateway/) v2 HTTP API——它调和 MCP OAuth 规范与 Entra ID 的具体细节。它提供 OAuth 发现文档，并把请求的 scope 重写为资源应用的 invoke scope。它还剥离 Entra v2.0 会拒绝的那个遗留 resource 参数，加上 `response_mode=query` 以便桌面客户端能捕获授权码，并用 bearer token 代理 `/mcp`。

有一个细节值得一提，因为它是整个系统中 DCR 唯一出现的地方。MCP 客户端期待 DCR，一个 `POST /register` 调用，返回一个 client ID。代理并没有实现真正的动态注册，而是用一个返回固定、预配置 client ID 的桩 `/register`。DCR 是被模拟的，不是真的。

#### 在 Amazon Bedrock AgentCore 上的部署

基础设施定义在 [AWS Cloud Development Kit](https://aws.amazon.com/cdk/) (AWS CDK) 中，一个用 npm workspaces 的 TypeScript monorepo。内部智能体作为 Docker 容器运行在 AgentCore runtime 上。环境特定的配置，如租户、客户端和资源标识符，通过 AWS Systems Manager (SSM) 参数提供。

#### 测试与上线

上线前，HEMA 把 HAL 部署到一个 staging 环境，并对工程师和业务用户都开放它做为期一个月的上手测试。这在被推广到生产、在组织范围内更广泛采纳之前，验证了答案质量、覆盖缺口和日常可用性。

## 如今谁在用 HAL

HAL 始于一个开发者工具，但它如今已是一个跨角色助手，而这份广度正是要旨。

- **开发者**使用完整的技术面：文档、API 规范、Kafka 主题和 schema、服务目录和 DCL 通道——从 Kiro 内部和聊天中使用。
- **产品负责人**依赖 HAL 获取文档、操作和流程知识：那个曾经没有归宿的程序性层。
- **业务分析师**用 HAL 获取基础设施知识：有哪些服务、它们暴露什么 API、哪些团队拥有它们——直接依托服务目录。

来自非开发者角色的拉力是真实且增长的：HEMA 负责梳理并优化产品经理流程的端到端团队，已经在其工作中接入了 HAL。在内部，HAL 通过一个“Everyone Skill”及配套引导文件分发，并通过每月的 HEMA AI Development Forum 共享和维护。

## 下一步：从答案到动作

如今，HAL 是只读的并交付即时答案。下一步是即时动作，由同一个助手执行。

这之所以现在可行，恰恰因为底层门户已经 API 化，且已经与现有 Microsoft Entra ID 单点登录集成。这意味着 HAL 能用那套已经保护读工具的同款 Entra ID 认证和 Active Directory 组授权模型，把这些操作作为 MCP 动作工具暴露出来。无需新的安全模型，只需要新的、精心限定范围的工具。

旗舰例子是开通一个新的 AWS 账户。今天开发者去一个专用门户申请一个。接下来，他们会直接从聊天、Kiro、Claude 或其他智能体发起同样的请求，而完全不必访问那个门户。而因为 HAL 已经服务产品负责人和业务分析师，同样的动作模式自然地从开发者运维延伸到这些角色每天提出的更广泛运维请求。

这一课的启示是：读架构为写这一步赢得资格——通过为答案把身份、多客户端访问和治理做对，我们已为动作铺好了基础。

## 结论

HAL 把 HEMA 的组织知识放在一个受治理的地方。MCP 和 Amazon Bedrock AgentCore 让那份知识可触达、多客户端且安全，而不强迫每个消费应用从零重建认证、授权或路由。成果不是一个开发者聊天机器人，而是一个面向开发者、产品负责人和业务分析师的跨角色助手。知识层已上线。逻辑上的下一步是把它延伸为一个动作层。在那里，如今回答问题的同一套受治理、经认证的基础设施，明天就能执行请求：开通访问、触发工作流，并代表用户直接从聊天、Kiro、Claude 或其他兼容 MCP 的智能体采取行动。
