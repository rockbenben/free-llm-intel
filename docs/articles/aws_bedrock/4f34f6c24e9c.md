# Benchling 如何用 Amazon Bedrock AgentCore 保障多租户 AI agent 的安全

当 Benchling 需要在数千个生命科学租户之间运行由 AI agent 生成的科学代码时，其安全团队发现传统沙箱并不够用。如今，这套架构每天处理 600 多个代码执行会话、每周覆盖 250 多个租户，且零安全事故。标准网络控制会阻断 HTTP、限制出站端口并限制对外连接。然而，DNS 解析往往仍被允许，而且即便系统默认设置对其加以限制，你也可能既无法看清这些限制、也无法控制它们。这正是 [Benchling](https://www.benchling.com/) 在数千个生命科学租户中部署 AI agent 时所面临的挑战。其安全团队需要对系统默认值之外的网络隔离拥有完全控制权，才能满足他们在大规模执行不可信代码时的威胁模型。

本文介绍 Benchling 如何构建一套纵深防御的安全架构，以在数千个生命科学租户之间运行由 AI agent 生成的科学代码。Amazon Bedrock AgentCore 是一个用于大规模构建、连接和优化 agent 的平台，支持任意框架或模型。Benchling 使用的 AgentCore Code Interpreter（[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 的一项能力）运行在 [Amazon Virtual Private Cloud（VPC）](https://docs.aws.amazon.com/toolkit-for-visual-studio/latest/user-guide/vpc-tkv.html) 模式下。该方法结合了账户级隔离、Amazon Route 53 Resolver DNS Firewall 和 VPC 端点策略，在实施按任务粒度的数据访问控制的同时帮助防止数据外泄。

## 多租户代码执行安全

Benchling 的 AI 应用会生成科学代码，代表数千个租户中的研究人员运行。主要用例是 AI agent 生成的科学代码，不过 Code Interpreter 也用于更简单的计算，以及作为代码生成沙箱。安全要求十分严格。每个会话只能访问该租户自己的数据，不得跨租户可见。代码不能建立未经授权的网络连接，也不能通过任何途径外泄数据。每个执行会话都必须完全隔离，同时该方案不能要求为每个租户配备一个 AWS Identity and Access Management（IAM）角色，因为在这种规模下那会造成难以维系的角色泛滥。

在安全评审期间，Benchling 团队针对自己的威胁模型评估了 Code Interpreter 各网络模式的网络隔离特性。Sandbox 模式虽然把出站访问限制在 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/) 操作上，但 Benchling 的安全要求需要由客户自行控制的网络隔离。他们需要精确界定哪些域名可以解析、哪些端点可以访问。他们还需要通过自己的集成测试套件持续验证这些控制项。对于一个要跨数千个受监管的生命科学租户处理敏感科学数据的应用来说，仅依赖应用层管理的网络限制并不够。他们需要一个由 Benchling 端到端掌握安全控制权的解决方案。该方案必须阻断未经授权的网络途径（包括 DNS），同时既不引入按租户管理的 IAM 角色泛滥，也不把主生产账户暴露给不可信的执行环境。

## 解决方案架构概览

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/31/Benchling-agentcore-ci-revised.drawio.png)

图 1：Benchling 面向多租户代码执行的纵深防御架构

图 1 展示了完整的解决方案架构。左侧的生产账户（Production Account）包含 Benchling Stack、IAM 角色、AWS STS 以及 Amazon S3 中的客户数据。任务会分派到右侧的不可信代码账户（Untrusted Code Account），这是一个独立的 AWS 账户，其中包含 ACCI VPC。该 VPC 没有互联网网关，也没有 NAT 网关。Code Interpreter 运行在仅开放 443 端口的专用安全组内，没有任何通往公网的出站路径。

来自 Code Interpreter 的 DNS 查询由 Route 53 Resolver DNS Firewall 评估，后者应用一套三优先级的解析器策略。优先级 10 阻断已知的恶意域名，优先级 100 只放行显式列出的端点，优先级 200 阻断其余查询。在安全组之下，VPC 端点提供了唯一被允许的网络路径。一个 S3 网关端点和一个接口端点负责获得授权的 S3 访问，而 NACL 与前缀列表路由把流量限制为只能走这些端点。按任务粒度的凭证通过生产账户的 AWS STS 注入每个会话，动态限定数据访问范围。一套持续验证（Continuous Validation）测试套件会运行集成测试，模拟针对该配置的外泄尝试。

Benchling 的解决方案使用一个专用的 AWS 账户来执行不可信代码，与主生产账户分离。AI 生成的代码在这个隔离的“Untrusted Code Account”中运行，从而把影响范围约束在可控边界内。一旦出现问题，承载客户数据和访问角色的 Benchling 主生产账户不会直接暴露。

这个不可信代码账户同时托管 AgentCore Code Interpreter（ACCI）和 Benchling 既有的基于容器的执行环境。后者使用 gVisor（一种容器沙箱运行时，通过拦截应用的系统调用来提供内核级隔离）实现按任务隔离。gVisor 环境是 Benchling 原有的计算隔离层，并不属于本文所给出的模式。两种执行环境各有自己带作用域权限的 IAM 角色，从而确保任何一方都无法越界提升到超出其预期边界的访问权限。

当任务从生产账户分派到不可信账户时，数据访问范围按任务限定。只有该任务所需的特定数据才可访问。生产账户的凭证以及更广泛的客户数据存储不会直接暴露给不可信代码。

为每个租户维护一个 IAM 角色，会在数千个租户的规模下造成难以维系的角色泛滥。取而代之的是，Benchling 通过 AWS Security Token Service（AWS STS）以按任务的方式把凭证注入每个 ACCI 会话，动态限定访问范围，而不积累静态角色。

## DNS Firewall 配置

ACCI VPC 按“除非显式允许，否则一律不放行”的理念设计。这里没有互联网网关，也没有 NAT 网关。在该 VPC 中运行的代码无法直接访问互联网。DNS 外泄防御的核心是 Amazon Route 53 Resolver DNS Firewall。它采用遵循“拒绝列表、允许列表、全部拒绝”模式的三优先级解析器策略：

### P10：高优先级阻断（显式拒绝列表）

第一条被评估的规则位于最高优先级，用于阻断对已知非预期域名的解析。这会在任何允许逻辑生效之前捕获明显的威胁。例如，如果 Benchling 识别出与已知数据外泄工具包或命令与控制基础设施相关的域名，这些域名在这一层就会被阻断，无论其他配置如何。这条规则作为威胁情报的快速通道存在。Benchling 不必只依赖某个域名不在允许列表中，而是可以主动枚举敌意端点，确保它们立即被拒绝。这条规则还提供了可观测性。命中显式拒绝列表的查询会产生 DNS Firewall 日志，标志着潜在的恶意活动，并让安全团队提前获知沙箱中的代码正在尝试可疑的域名解析。

### P100：允许列表（S3 存储桶与显式域名）

第二层是一个允许列表，只对显式列出的域名放行 DNS 解析。实践中，这只限于数据访问所需的 S3 端点，通常别无其他。允许列表被刻意做得极小，因为每一个被允许的域名都代表一个潜在的外泄途径。Benchling 把解析范围限定到任务执行所需的特定 S3 存储桶端点。即使恶意代码试图出于非预期目的联系某个合法的 AWS 服务端点，只要 Benchling 未显式批准，它就无法解析该端点。这让 Benchling 完全拥有网络边界。与依赖随服务版本变动的系统默认值不同，允许列表是由客户控制的产物，Benchling 可以审计、版本化并按自己的节奏更新它。

### P200：全部阻断（兜底 NODATA）

最后一条规则是兜底规则：对于任何未被 P100 显式允许的 DNS 查询，它都返回 NODATA。正是这一点使 DNS 外泄变得不可能。在典型的 DNS 隧道攻击中，恶意代码把窃取的数据编码为 DNS 查询中的子域名标签（例如 base64payload.example.com），并依赖递归解析把该查询投递到攻击者控制的权威名称服务器。有了这条兜底规则，每个不在严格允许列表中的域名都会收到 NODATA 响应。编码后的外泄查询没有任何可通行的解析路径。DNS 递归链在第一跳就被切断。正是这条规则把该 VPC 从“受限”变为“封闭”。没有它，任何新域名或被忽略的端点都会默认获得解析许可。有了它，安全态势就反转过来：除非 Benchling 明确决定允许，否则什么都解析不了。

## 持续验证

Benchling 的产品安全团队先在一个概念验证 VPC 中证明了该方法有效。他们逐层测试了每一道防御。DNS 隧道尝试确认了 Route 53 Resolver DNS Firewall 对任何不在显式允许列表中的域名都返回 NODATA。直连 IP 的尝试确认了前缀列表路由与 NACL 只放行 443 端口和临时端口，没有通往任意外部主机的路径。API 调用尝试确认了 VPC 端点策略会拒绝指向作用域集合之外任何 S3 存储桶的请求。由于不存在互联网网关、NAT 网关和默认安全组，绕过这些控制项的流量根本没有出站路径。

在概念验证验证了该架构之后，Benchling 的基础设施团队把这些外泄模拟纳入其持续集成测试套件。这些测试会演练真实攻击者会使用的同一些途径，包括通过编码子域名查询进行的 DNS 隧道、直连未授权端点，以及尝试访问 VPCE 策略范围之外的 S3 存储桶。只要有任何测试解析了本不该解析的域名、访问到了外部端点，或把数据移出已批准的存储桶，流水线就会失败并阻止发布。

这种做法之所以重要，是因为安全配置并非一成不变。随着基础设施演进，VPC 设置会变化；为支持功能开发，会新增端点；随着团队接入新服务，IAM 策略也会更新。没有持续验证的话，一个在部署时安全的配置，可能在周围环境变化中悄然退化。通过把抗外泄当作一种可测试的属性而非一次性设置，Benchling 确保任何未来无意削弱安全边界的基础设施变更都会在上线之前被发现。

## VPC 端点策略与数据访问控制

由于 VPC 中没有互联网网关或 NAT 网关，对 AWS 服务的访问必须经由 VPC 端点。Benchling 部署了一个网关端点用于区域内的 Amazon S3 访问，并部署一个接口端点用于跨区域 S3 访问。每个端点都附带策略，显式列出它被允许访问哪些 S3 存储桶。任何指向不在该策略中的存储桶的请求，都会在网络层、到达 S3 之前被拒绝。

这形成了一道独立于 IAM 的防御。即便不可信代码获得了某个它本不该访问的存储桶的有效凭证，端点策略仍会阻断该请求。凭证限定的是一个会话被授权做什么，而端点策略限定的是网络实际上能够投递什么。Benchling 并没有给 ACCI 角色授予访问所有租户存储桶的宽泛权限，而是通过 AWS STS 以按任务的方式把限定作用域的凭证注入每个会话。一个被攻陷的会话只能访问它被分派去服务的那个租户。

流量还进一步受到前缀列表路由和 NACL 的约束，只允许 443 端口和临时返回端口上的通信。Code Interpreter 运行在一个没有默认回退规则的专用安全组中。除了经过显式限定作用域的 VPC 端点之外，没有任何端口、协议或网络路径可供数据离开该环境。

### 通过网关 VPC 端点访问 S3

Benchling 为区域内 S3 访问配置网关 VPC 端点，为跨区域 S3 访问配置接口 VPC 端点。每个端点都附带一条 VPCE 策略，只显式列出给定执行上下文被授权的特定 S3 存储桶。任何指向不在该策略中的存储桶的 API 调用，都会在网络层、到达 S3 服务之前被拒绝。这意味着即使不可信代码以某种方式获得了另一个租户存储桶的有效凭证，请求仍然会失败。网络本身拒绝承载该流量。这形成了一道独立于 IAM 的防御，因此仅凭窃取凭证不足以访问未授权的数据。

### 按任务的凭证作用域

Benchling 没有为数千个租户预先配置 IAM 角色，而是通过 AWS Security Token Service（AWS STS）把限定作用域的凭证注入每个 ACCI 会话。每个任务只获得访问其特定租户数据所需的权限。生产账户决定一个任务可以访问哪些数据，生成作用域恰当的临时凭证，并在分派时把它们注入会话。Code Interpreter 执行角色的 S3 访问被限制在主堆栈存储桶上。启动时，会话策略会被传入每一次 Code Interpreter 执行，把 S3 访问限制在已授权存储桶中该租户的路径前缀内。这确保沙箱内运行的代码只能访问它被分派去服务的那个租户的数据。这就是架构图中所示的“按任务的数据导出作用域”。Benchling 评估过另一种方案，即给 ACCI 角色授予访问所有租户存储桶的宽泛权限，但予以否决，因为那样一来单个被攻陷的会话就有了通往任何租户数据的路径。

### 网络层锁定

除了 DNS Firewall 和 VPC 端点策略之外，NACL 只放行 443 端口和临时返回端口，前缀列表路由确保流量只能到达 VPC 端点，Code Interpreter 则运行在没有默认回退规则的专用安全组中。攻击面被收窄到只剩 Code Interpreter 及其限定作用域的 VPC 端点。

## 与自建沙箱相比，为什么选择 AgentCore Code Interpreter

在采用 AgentCore 之前，Benchling 团队评估过自建沙箱方案。需求很明确。他们需要临时性执行会话、按任务隔离、无持久状态，以及能够运行在可施加自有网络安全控制的 VPC 内。自建意味着要设计定制的容器编排、实现沙箱生命周期管理，并从零构建网络隔离原语。他们还需要在跟上不断演进的威胁途径的同时持续修补安全漏洞。这代表着大量持续的工程投入从 Benchling 的核心产品上分流出去，而对他们的客户而言并无差异化价值。

VPC 模式下的 AgentCore Code Interpreter 直接绕过了这整个工作流。每个会话相互隔离且存活时间短，任务之间没有持久状态。AWS 负责沙箱生命周期，包括修补、扩缩容和执行环境的加固。在 Benchling 自己锁定的 VPC 内运行 Code Interpreter，意味着他们可以叠加 DNS Firewall、VPC 端点策略和 NACL 等现有的 AWS 安全原语，而无需自建网络。这解放了 Benchling 的基础设施团队，使其专注于产品安全控制，而不是沙箱维护。

> “借助 AgentCore Code Interpreter，我们得以用‘购买’而非‘自建’的方式获得一个安全的解决方案。”

— Jeremy Stashewsky，Benchling 应用安全工程师

自 2026 年 4 月初以 VPC 模式部署 AgentCore Code Interpreter 以来，Benchling 已扩展到每天 600 多个代码执行会话，每周为 250 多个不同租户提供 AI agent 生成的科学工作负载。这表明其在客户群中获得了广泛采用，同时没有损害其安全态势。自部署以来，Benchling 报告零安全事故、零跨租户数据泄露。

> “为 AI agent 提供代码解释器，是满足客户所要求的科学准确性不可或缺的条件；但我们的威胁模型假定任何由 agent 或用户编写的代码都可能是非预期的。我们需要一个真正的沙箱，除 S3 之外没有任何网络访问。VPC 模式下的 AgentCore Code Interpreter，配合 Route 53 DNS Firewall 和 VPC 端点，让我们在不自建的情况下封堵了我们测试过的每一条外泄途径（包括 DNS）。”

— Benchling

## 结论

在多租户环境中运行 AI 生成的代码，会带来传统沙箱无法完全应对的外泄途径。尤其是 DNS 解析往往被忽视，因为标准网络控制关注的是 HTTP、出站端口和直连。Benchling 实施的这一模式提供了一个蓝图，可以在不自建沙箱基础设施的前提下补上这个缺口。

该架构从账户级隔离开始，把不可信代码执行与生产系统彻底分开。VPC 模式下的 Amazon Bedrock AgentCore Code Interpreter 在该隔离账户内提供托管的临时性执行环境。Route 53 Resolver DNS Firewall 以拒绝列表、允许列表、全部拒绝的策略封死 DNS 外泄途径。VPC 端点策略把服务访问限制到每个任务所需的特定 S3 存储桶。通过 AWS STS 实施的按任务凭证作用域确保即便会话被完全攻陷，也无法触及单个租户数据之外的范围。

该架构中没有任何单一控制项可以独自胜任。正是所有这些层次的组合，并通过自动化测试持续验证，才规避了整类的外泄途径。每一层都能捕获其他层可能遗漏的情况，而持续验证确保随着基础设施演进这一态势依然成立。

要开始使用 VPC 模式下的 Amazon Bedrock AgentCore Code Interpreter，请参阅 [Code Interpreter 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/code-interpreter-tool.html) 和 [VPC 配置指南](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-vpc.html)。你可以按照本文描述的模式，部署一个带 Route 53 DNS Firewall 和 VPC 端点策略的锁定 VPC。如果你已经在沙箱环境中运行不可信代码，请考虑你当前的架构是否把 DNS 视为一条外泄通道，以及你是否有持续验证来证明它确实如此。
