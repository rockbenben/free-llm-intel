# 在 Amazon Bedrock Agents 中实现 human-in-the-loop 确认

agent 正在重塑企业自动化复杂工作流与决策流程的方式。[Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 通过编排多步任务，帮助你加速生成式 AI 应用的开发。agent 借助基础模型（FM）的推理能力，把用户请求的任务拆解为多个步骤。此外，它们还会使用开发者提供的指令制定出一份编排计划，然后通过调用公司 API、并借助检索增强生成（RAG）访问知识库来执行该计划，从而对用户的请求给出回答。

构建能够有效处理用户查询的智能自主 agent，需要细致的规划与稳健的防护措施。尽管基础模型在不断进步，它们仍可能产生不正确的输出；而由于 agent 是复杂系统，错误可能出现在多个环节。例如，agent 可能选错工具，或者用正确的工具搭配错误的参数。尽管 Amazon Bedrock agent 可以通过其推理与行动（[ReAct](https://arxiv.org/abs/2210.03629)）策略自我纠正，但反复重试工具执行对于非关键任务是可以接受的，对于数据库修改这类业务关键操作则有风险。

在这些敏感场景下，human-in-the-loop（HITL）交互对于 AI agent 的成功部署至关重要，它涵盖人与自动化系统之间的多个关键接触点。HITL 可以有多种形式：从最终用户批准操作并提供反馈，到领域专家离线审阅回复，再到 agent 与客服代表协同工作。共同之处在于保持人的监督，并运用人的智慧来提升 agent 的表现。这种人的参与有助于确立真实基准（ground truth）、在上线前校验 agent 的回复，并通过反馈回路实现持续学习。

本文将具体聚焦于如何利用 Amazon Bedrock Agents 的内置功能，让最终用户能够批准操作并提供反馈，也就是为 agent 的安全有效运行提供 HITL 模式。我们用一个帮助员工申请休假的 Human Resources（HR）agent 示例，来探讨可用的各种模式。你可以按照我们的 [GitHub 仓库](https://github.com/awslabs/amazon-bedrock-agent-samples/tree/main/examples/agents/human_in_the_loop)，手动或用 [AWS Cloud Development Kit](https://aws.amazon.com/cdk/)（AWS CDK）重建该示例。我们会从应用开发者的视角展示这些方法长什么样，同时介绍这些概念背后的整体思路。在本文中，我们在 [Amazon Bedrock](https://aws.amazon.com/bedrock/agents/) 上应用 [user confirmation](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-userconfirmation.html) 与 [return of control](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-returncontrol.html) 来实现人工确认。

## Amazon Bedrock Agents 的 human-in-the-loop 确认框架

在 Amazon Bedrock Agents 中实现人工校验时，开发者有两种主要框架可用：user confirmation 与 return of control（ROC）。这两种机制虽然都服务于类似的监督目的，但面向不同的校验需求，并且作用于 agent 工作流的不同层级。

user confirmation 提供了一种直截了当的方式，在执行前暂停并校验特定操作。使用 user confirmation 时，开发者会收到 agent 为完成某项任务想要调用的函数（或 API）及其参数值的信息。开发者随后可以在 agentic 应用里把这些信息呈现给用户，收集“该函数应当被执行”的确认，然后才继续 agent 的编排流程。

使用 ROC 时，agent 会把想要执行的任务信息交给开发者，并完全依赖开发者来执行该任务。在这种方式下，开发者不仅可以校验 agent 的决策，还可以在 agent 的执行过程中补充额外上下文并修改参数。ROC 恰好也是在 [action group](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-action-create.html) 层级配置的，因而可以覆盖多个 action。

下面我们来探讨每种框架如何实现，以及各自的具体用例。

## 自主执行 agent：没有 human-in-the-loop

首先，我们演示一下：如果你的应用没有 HITL，用户体验会是什么样。为此，请看下面的架构。

下面的截图展示了一个 Amazon Bedrock agent 的示例前端 UI，其中带有查询 PTO 与申请新 PTO 的函数。

![HR Assistant 界面截图，显示编号 456 的休假申请已成功提交，剩余余额为 7.25 天。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/31/agent-blog-2.png)

在这次交互中，PTO 申请在没有任何最终用户确认的情况下就被提交了。如果用户其实并不想提交申请，只是想确认这件事可以做呢？如果他们提供的日期不正确、存在笔误呢？对于任何会改变用户 PTO 状态的操作，系统在实际做出这些变更之前先请求确认，会带来更好的用户体验。

## 简单的人工校验：user confirmation

申请 PTO 时，员工期望能够确认自己的操作。这样可以减少误提交的执行，并帮助确认 agent 正确理解了请求及其参数。

对于这类场景，一个布尔型确认就足以继续执行 agentic 流程。Amazon Bedrock Agents 提供了开箱即用的 user confirmation 功能，让开发者可以在其 AI 驱动的工作流中增加一层额外的安全与控制。该机制通过在关键操作执行前确保其经过用户校验，在自动化与人工监督之间取得平衡。借助 user confirmation，开发者可以决定哪些工具可以自动执行、哪些应当先经确认。

在我们的示例中，读取可用 PTO 时长、列出员工过去的 PTO 申请记录，都是可以自动执行的非关键操作。而预订、更新或取消 PTO 申请需要对数据库做变更，属于应在执行前确认的操作。我们按下面更新后的图，把 user confirmation 加入 agent 架构。

![AWS Cloud 架构图，展示员工 PTO 申请工作流以及组件之间带确认操作的执行流。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/31/agent-blog-3.png)

在更新后的架构中，当员工与 HR Assistant agent 交互、且需要调用 `*create_pto_request()*` action 时，agent 会先请求用户确认，然后再执行。

要启用 user confirmation，agent 开发者可以使用 [AWS Management Console](https://aws.amazon.com/console)、[Boto3](https://boto3.amazonaws.com/v1/documentation/api/latest/reference/services/bedrock-agent/client/create_agent_action_group.html) 这样的 SDK，或用 [AWS CloudFormation](https://aws.amazon.com/cloudformation) 做基础设施即代码（IaC）（参见 [AWS::Bedrock::Agent Function](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/aws-properties-bedrock-agent-function.html)）。启用 user confirmation 后的用户体验如下面的截图所示。

![HR Assistant 界面截图，显示针对 3 天休假申请的确认对话框，带有 Confirm 与 Reject 按钮。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/31/agent-blog-4.png)

在这次交互中，agent 为执行操作而向最终用户请求确认。用户随后可以选择是否继续该休假申请。选择 Confirm 会让 agent 依据展示的参数执行该 action。

![HR Assistant 界面截图，显示用户确认休假后的对话框。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/31/agent-blog-5.png)

下图说明了确认该 action 的工作流。

![时序图，描绘 User、Client Side UI、Agent、Model 与 API 之间围绕休假申请的 user confirmation 流程交互。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/31/agent-blog-6.png)

在这一场景中，由开发者决定确认信息在客户端 UI 中如何展示给用户，而 agent 在执行该 action 前会校验确认状态。

## 定制化的人工输入：return of control

user confirmation 提供的是简单的“是/否”校验，但有些场景需要更细致的人工输入。这正是 ROC 发挥作用之处。ROC 允许更深层次的人工介入，使用户能够在 action 执行前修改参数或补充额外上下文。

还是看我们的 HR agent 示例。申请 PTO 时，一项常见的业务需求是让员工在提交前审阅并可能修改自己的申请。这在简单确认用例的基础上做了扩展，允许用户在把请求发给后端之前改动原始输入。Amazon Bedrock Agents 提供了开箱即用的方案，用 ROC 有效地解析用户输入，并以结构化格式回传。

要实现 ROC，我们需要对 agent 架构稍作修改，如下图所示。

![AWS Cloud 架构图，展示 Employee、HR Assistant 与两个 Action Group（Get PTO 与 Request PTO）之间的交互，以及用于处理 PTO 请求的 Lambda 函数。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/31/agent-blog-7.png)

在这一架构中，ROC 在 action group 层级实现。当员工与 HR Assistant agent 交互时，系统要求对“Request PTO Action Group”下的所有函数参数做显式确认，然后才执行该 action group 内的 action。

使用 ROC 后，用户体验变得更富交互性、更灵活。下面的截图展示了我们的 HR agent 应用中的一个示例。

![HR Assistant 界面截图，显示休假申请表单，包含天数（3.00）与开始日期（2025/04/14）字段以及提交按钮。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/31/agent-blog-8.png)

系统不会自动执行 action，也不只是给出确认/拒绝选项，而是向用户呈现一个表单，让其在处理前直接修改自己的意图。在这个例子里，我们的用户可以意识到自己不小心把休假开始日期定在了周日，并在提交前修正这一信息。

用户审阅并可能修改请求之后，就可以批准这些参数。

![HR Assistant 界面截图，显示一段关于申请从 2025-04-14 起休假 3 天的对话，系统回复确认了请求的各个步骤。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/31/agent-blog-9.png)

实现 ROC 时，务必理解参数校验发生在两个不同的时点。agent 在把控制权交还给用户之前会做初次校验（例如检查可用 PTO 余额），而最终执行则依赖应用自身的 API 校验层。

例如，如果用户最初申请 3 天 PTO，agent 会对照其 5 天余额做校验，然后交还控制权。然而，如果用户在 ROC 过程中把请求改成 100 天，最终的校验与强制执行发生在 API 层，而不是通过 agent。这与 agent 直接执行 API 调用的确认流程不同。在 ROC 中，agent 的角色是促成交互并返回 API 响应，而参数校验与执行最终由应用掌控。

ROC 方式的核心区别在于：处理休假申请的责任现在由应用自身承担，而不再由 agent 自动处理。这为更复杂的工作流和更强的人工监督创造了空间。

为了更好地理解 ROC 场景中的信息流，我们来看下面的时序图。

![时序图，展示 User、Client Side UI、Agent、Model 与 Function/API 之间围绕处理休假申请的交互。流程包括预处理、模型判定、参数处理与结果处理。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/03/31/agent-blog-10.png)

在这一工作流中，agent 准备好 action 但并不执行它，而是把控制权交还给应用，由应用把可编辑的信息呈现给用户。用户审阅并可能修改请求之后，应用负责用最终获得用户批准的参数执行该 action。

这种方式带来几项好处：

- **提升准确性** – 用户可以纠正 agent 对其请求理解上的误解或错误
- **灵活性** – 支持在最后一刻对请求做出修改或补充
- **赋能用户** – 让用户对最终 action 有更多控制权，从而增强对系统的信任
- **合规性** – 在受监管行业，这一层级的人工监督对于满足法律或政策要求可能至关重要

与 user confirmation 相比，实现 ROC 需要更多开发投入，因为它涉及在应用内创建用于编辑的 UI，并处理 action 的执行。不过，对于精准度与用户控制至关重要的场景，这些额外的复杂度通常是值得的。

## 结论

本文探讨了在 Amazon Bedrock Agents 中实现人工校验的两种主要框架：user confirmation 与 return of control。这两种机制虽然都服务于类似的监督目的，但面向不同的校验需求，并作用于 agent 工作流的不同层级。user confirmation 提供直截了当的布尔校验，让用户在执行前批准或拒绝特定 action。当简单的“是/否”决策就足以保障安全与准确性时，这种方法最为理想。

ROC 提供了更细致的方式，使用户能在 action 执行前修改参数并补充额外上下文。在需要改变 agent 决策的复杂场景中，这一框架尤其有用。

两种方法共同支撑起稳健的 HITL 做法，为 agentic 应用提供不可或缺的人工校验层。

user confirmation 与 ROC 只是 AI agent 部署中更广泛的 HITL 范式里的两个方面。在后续文章中，我们还会讨论与 agent 进行 HITL 交互的其他关键用例。

要开始构建你自己的、带 HITL 校验的 agentic 应用，我们鼓励你探索本文讨论的 HR 示例。你可以在我们的 [GitHub 仓库](https://github.com/awslabs/amazon-bedrock-agent-samples/) 中找到完整代码与实现细节。
