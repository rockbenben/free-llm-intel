# 使用接口 VPC 端点实现到 Amazon Bedrock AgentCore Gateway 的安全入站连接

[Agentic AI](https://aws.amazon.com/ai/agentic-ai/) 应用是企业自动化领域的一项重要进展：智能 agent 能够自主执行复杂的工作流、访问敏感数据集，并在组织的整个基础设施范围内做出实时决策。[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 通过提供全托管服务来加速企业 AI 转型，这些服务消除了基础设施的复杂性、保持会话隔离，并支持与企业工具无缝集成，使组织能够大规模部署值得信赖的 AI agent。[AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 是 AgentCore 之下的一个模块化服务，它安全地把 API、[AWS Lambda](https://aws.amazon.com/lambda/) 函数和服务转换为 [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro)（MCP）兼容的工具，并通过统一端点提供给 agent，从而简化集成；它内置身份验证和无服务器基础设施，可将运维开销降到最低。

在生产环境中，AI agent 通常部署在虚拟私有云（VPC）内，以维持安全、隔离的网络访问，并满足企业的安全与合规要求。[Amazon Web Services](https://aws.amazon.com/)（AWS）接口 VPC 端点可以在 VPC 内托管的 agent 与 AgentCore Gateway 之间建立私有连接，从而提升 agentic AI 的安全性，让敏感通信始终留在 AWS 的安全基础设施之内。这些端点使用带有私有 IP 地址的专用网络接口，通过直连提供更低的延迟和更优的性能。此外，VPC 接口端点还通过端点策略提供细粒度的访问控制，避免管理代理服务器从而简化运维，降低数据传输成本，并建立自主 AI 系统在企业规模、受监管环境中处理机密数据时所必需的安全基础。

在本文中，我们将演示如何从 VPC 内的一个 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2/)（Amazon EC2）实例通过 VPC 接口端点访问 AgentCore Gateway。我们还会展示如何配置 VPC 端点策略，在保持最小权限原则的同时为 AgentCore Gateway 提供安全访问。

## 架构概览

该架构图展示了一位用户访问某个应用的过程，该应用由部署在各种 AWS 计算服务上的后端 agent 支撑，这些服务包括 EC2 实例、Lambda 函数、[Amazon Elastic Kubernetes Service](https://aws.amazon.com/eks/)（Amazon EKS）或 [Amazon Elastic Container Service](https://aws.amazon.com/ecs/)（Amazon ECS），并且全部运行在 VPC 环境中。这些 agent 与 AgentCore Gateway 通信，以发现、访问和调用已被转换为 agent 兼容资源的外部工具与服务，例如企业 API 和 Lambda 函数。在标准配置下，agent 发往 AgentCore Gateway 的请求会经过公共互联网。通过实施接口 VPC 端点，组织可以让这些通信改走 AWS 安全的内部网络骨干，从而带来显著收益，包括增强安全性、降低延迟，以及为需要严格网络隔离和数据保护标准的受监管工作负载改善合规一致性。该解决方案遵循以下工作流：

- **AI agent 交互** – 运行在 VPC 内的 agent 从身份提供方获得所需的入站授权，向 Gateway 进行身份验证，并通过接口 VPC 端点向 gateway 发送工具使用请求（调用 MCP 工具）。
- **Gateway 处理**：Gateway 管理 OAuth 授权，以确保只有合法的用户和 agent 才能访问工具和资源。入站请求由 Gateway 授权。它使用 Model Context Protocol（MCP）等协议把 agent 请求转换为 API 请求和 Lambda 调用
- **安全访问**：gateway 为每个工具处理凭据注入，使 agent 能够无缝使用具有不同身份验证要求的工具。它借助 [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) 代表 agent 安全地访问后端资源（即*目标*）。
- **目标执行**：gateway 数据平面调用目标，目标可以是一个 Lambda 函数、一份 OpenAPI 规范或一个 Smithy 模型。
- **监控**：AgentCore Gateway 提供内置的可观测性与审计能力。此外，[AWS PrivateLink](https://aws.amazon.com/privatelink/) 会将指标发布到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)，用于监控接口端点。你还可以选择启用 [VPC Flow Logs](https://docs.aws.amazon.com/vpc/latest/userguide/flow-logs.html)，记录发往 AgentCore Gateway 的 IP 流量。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/03/image-1-3.png)

请注意以下关键考量：

- **私有与公共网络通信** – 接口 VPC 端点通过 AWS PrivateLink 为从 agent 到 AgentCore Gateway 的入站流量提供安全通信，确保这些流量始终留在私有网络内。但是，身份验证工作流——包括 OAuth 访问令牌获取，以及 agent 与外部身份提供方系统之间针对入站和出站流程的凭据交换过程——以及从 gateway 到 MCP 工具的出站访问，仍然需要互联网连接，以便与托管在 AWS 环境之外的身份系统和外部资源建立安全会话。
- **数据平面范围** – 需要了解的是，目前接口 VPC 端点支持仅适用于 gateway 的[数据平面端点](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html#gateway-endpoints-quotas)——即你的应用与 agent 工具交互的运行时端点。为了厘清这一区别：虽然你现在可以通过接口 VPC 端点访问 gateway 的运行时端点，但控制平面操作（例如创建 gateway、管理工具和配置安全设置）仍然必须通过标准的公共 AgentCore 控制平面端点执行（例如 `bedrock-agentcore-control.<region>.`[`amazonaws.com`](http://amazonaws.com)）

## 前提条件

要实施该解决方案，你需要以下前提条件：

- 一个具有相应 [AWS Identity and Access Management](https://aws.amazon.com/iam/)（IAM）权限的 AWS 账户，可管理 VPC 和 [Amazon Elastic Compute Cloud](https://aws.amazon.com/ec2/)（Amazon EC2）
- 已配置子网和路由表的现有 VPC 环境
- 已在你的 AWS 账户中预置并配置好 AgentCore Gateway
- 对 VPC 网络概念和安全组配置有基本了解

## 解决方案演练

在接下来的小节中，我们将演示如何使用 [AWS Management Console](https://aws.amazon.com/console/) 配置接口 VPC 端点，并从 VPC 内的测试 EC2 实例建立到 AgentCore Gateway 的安全连接。

### 为 EC2 实例创建安全组

要为 EC2 实例创建安全组，请按以下步骤操作，如下方截图所示：

- 在你偏好的 [AWS Region](https://docs.aws.amazon.com/glossary/latest/reference/glos-chap.html#region) 中打开 [Amazon EC2 控制台](https://console.aws.amazon.com/ec2/)，在导航窗格中的 **Network & Security** 下选择 **Security Groups**。
- 选择 **Create security group**。
- 在 **Security group name** 中，输入一个描述性名称，例如 `ec2-agent-sg`。
- 在 **Description** 中，输入有意义的描述，例如 `Security group for EC2 instances running AI agents`。
- 在 **VPC** 中，选择你的目标 VPC。
- 为 EC2 实例管理添加相关的 **Inbound rules**，例如允许来自你的管理网络或堡垒主机的 SSH（端口 22）。
- 将 **Outbound rules** 保持默认（允许所有出站流量），以确保 agent 能与必要的服务通信。
- 选择 **Create security group**。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/03/image-2.jpeg)

### 为接口 VPC 端点创建安全组

要为接口 VPC 端点创建安全组，请按以下步骤操作：

参照前面的步骤并选择同一个 VPC，创建第二个名为 `vpce-agentcore-sg` 的安全组，它将被挂载到 AgentCore Gateway 接口 VPC 端点。为此安全组配置以下规则，以实现安全且受限的访问：

- **Inbound rules** – 允许 HTTPS（端口 443），用于与 AgentCore Gateway 的安全通信
- **Source** – 选择你在上一节创建的 EC2 安全组（`ec2-agent-sg`），从而只允许来自已授权 agent 实例的流量
- **Outbound rules** – 保持默认（允许所有流量），以支持响应流量

该安全组配置实现了最小权限原则：只有带有 agent 安全组的 EC2 实例才能访问该 VPC 端点，同时阻止 VPC 中其他资源的未授权访问。以下截图展示了这些步骤。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/03/image-3-1.jpeg)

### 在 VPC 内预置 EC2 实例

在同一个 VPC 中预置一个 EC2 实例，并根据你的工作负载需求选择合适的可用区。使用如下列表所示的网络设置配置该实例，确保选择同一个 VPC，并记下所选子网以便配置 VPC 端点：

- **VPC** – 选择你的目标 VPC
- **Subnet** – 选择一个私有子网以增强安全性（记下该子网，用于 VPC 端点配置）
- **Security group** – 挂载你在前面步骤中创建的 EC2 安全组（`ec2-agent-sg`）
- **IAM role** – 配置一个具有访问 Amazon Bedrock 和 AgentCore Gateway 所需权限的 IAM 角色
- **Instance type** – 根据你的 agent 工作负载需求选择合适的实例类型

请记住所选的子网，因为你需要在同一子网中配置 VPC 端点，以实现最优的网络路由和最小延迟。以下截图展示了这些配置。

### 创建接口 VPC 端点

使用 [Amazon Virtual Private Cloud](https://aws.amazon.com/vpc/)（Amazon VPC）创建接口 VPC 端点，它会自动使用 AWS PrivateLink 技术，使你的 EC2 实例能够在不经过公共互联网的情况下与 AgentCore Gateway 安全通信。请按以下步骤操作：

- 打开 [Amazon VPC 控制台](https://console.aws.amazon.com/vpc/)，在导航窗格的 **PrivateLink and Lattice** 区域下选择 **Endpoints**。
- 选择 **Create endpoint**。
- 在 **Name tag** 中，输入一个描述性名称（例如 `vpce-agentcore-gateway`）。
- 在 **Service category** 中，选择 **AWS services**。
- 在 **Services** 中，搜索并选择 `com.amazonaws.<region>.bedrock-agentcore.gateway`（将 `<region>` 替换为你实际的 AWS Region）。

以下截图展示了这些设置。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/03/image-5-2.png)

- 将 VPC 设置为你在整个配置过程中一直使用的同一个 VPC。
- 选择 **Enable** **DNS name**，以允许使用默认域名访问 AgentCore Gateway，这会简化应用配置并保持与现有代码的兼容性。
- 指定 EC2 实例所在的子网，以保持最优的网络路由和最小延迟，如下方截图所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/03/image-6.jpeg)

- 将安全组设置为你之前创建的 VPC 端点安全组（`vpce-agentcore-sg`），以控制对该端点的访问。
- 在初始测试阶段，将策略保持为 **Full access**，允许 VPC 内的 agent 与你的 AWS 账户中的 AgentCore Gateway 通信。在生产环境中，应基于最小权限原则实施更严格的策略。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/03/image-7-1.jpeg)

创建端点后，大约需要 2–5 分钟才能变为可用。你可以在 Amazon VPC 控制台监控其状态，当状态显示为 **Available** 时，就可以继续测试连接了。

### 测试连接

登录到 EC2 实例以执行以下测试。

#### 检查经由接口 VPC 端点的流量

要确认经由 Amazon Bedrock AgentCore Gateway 端点的流量走向，请[检查连接到 AgentCore Gateway 端点的源资源的 IP 地址](https://repost.aws/knowledge-center/vpc-find-owner-unknown-ip-addresses)。当你设置接口 VPC 端点时，AWS 会在子网中部署一个带有私有 IP 地址的弹性网络接口。该部署使 Amazon VPC 内的资源，以及通过 [AWS Direct Connect](https://aws.amazon.com/directconnect/) 或 [AWS Site-to-Site VPN](https://aws.amazon.com/vpn/site-to-site-vpn/) 连接到接口 VPC 端点的本地资源，都能与 AgentCore Gateway 通信。当你采用[集中式接口 VPC 端点架构模式](https://aws.amazon.com/blogs/networking-and-content-delivery/centralize-access-using-vpc-interface-endpoints/)时，它还允许与其他 Amazon VPC 端点中的资源通信。

检查你是否为 AgentCore Gateway 端点开启了私有 DNS。如果开启私有 DNS，AgentCore Gateway 端点就会解析为私有端点 IP 地址。对 AgentCore Gateway 而言，启用私有 DNS 意味着你的 agent 可以继续使用标准的 gateway 端点 URL，同时享受经由 VPC 端点的私有网络路由。

**在创建 VPC 接口端点之前**，如下例所示，DNS 会将 AgentCore Gateway 端点解析为公有 IP 地址：

```
nslookup gateway.bedrock-agentcoreamazonaws.com

Non-authoritative answer:
Name: gateway.bedrock-agentcore..amazonaws.com
Address: 52.86.152.150
```

**在创建 VPC 接口端点并启用私有 DNS 解析之后**，如下例所示，DNS 会解析为私有 IP 地址，该地址取自创建 VPC 端点所在 VPC 的子网 CIDR 范围。

```
nslookup .gateway.bedrock-agentcore..amazonaws.com

Non-authoritative answer:
Name: .gateway.bedrock-agentcore..amazonaws.com
Address: 172.31.91.174
```

当你为 AgentCore Gateway 的 VPC 接口端点选择 **Enable DNS name** 时，AWS 默认会开启 **Enable private DNS only for inbound endpoints** 选项。

#### 启用私有 DNS（cURL）（推荐）

启用私有 DNS 后，你的应用可以无缝使用标准 gateway URL 端点，格式为 https://*{gateway-id}.*gateway.bedrock-agentcore.*{region}*.amazonaws.com，而流量会自动经由 VPC 端点路由。

以下是一个示例 cURL 请求，需从 VPC 内的资源执行。该命令发送一个 JSON-RPC POST 请求，以从 AgentCore Gateway 获取可用工具：

```
curl -sS -i -X POST https://<gatewayid>.gateway.bedrock-agentcore.<region>.amazonaws.com/mcp \
--header 'Content-Type: application/json' \ 
--header "Authorization: Bearer $TOKEN" \ 
--data '{
"jsonrpc": "2.0",
"id": "'"$UNIQUE_ID"'",
"method": "tools/list",
"params": {}
}' 
```

该 cURL 命令向 AgentCore Gateway 的 MCP 端点发送一个 JSON-RPC 2.0 POST 请求，以获取可用工具列表。它使用 bearer token 身份验证，并在输出中包含响应头，通过调用 tools/list 方法发现哪些工具可通过 gateway 访问。

#### 禁用私有 DNS（Python）

禁用私有 DNS 时，你无法通过标准的 AgentCore Gateway 端点直接访问 gateway。此时必须让流量经由下方截图中显示的 VPC DNS 名称，并在 `Host` 头中包含原始 gateway 域名。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/03/image-8.jpeg)

```
curl -sS -i -X POST https://<vpce-dns-name>/mcp \
  --header 'Host: <gatewayid>.gateway.bedrock-agentcore.<region>.amazonaws.com \
  --header 'Content-Type: application/json' \
  --header "Authorization: Bearer $TOKEN" \
  --data '{
    "jsonrpc": "2.0",
    "id": "'$UNIQUE_ID'",
    "method": "tools/list",
    "params": {}
  }'
```

**以下步骤演示如何执行一个使用 `Host` 头的 Python 脚本：**

- 访问你的 EC2 实例。登录到可访问该 VPC 端点的 EC2 实例。
- 配置连接所需的环境变量：
- **GATEWAY_URL** – 用于通过私有网络连接访问 AgentCore Gateway 的 VPC 端点 URL
- **TOKEN** – 用于访问 gateway 的身份验证 bearer token
- **GATEWAY_HOST** – 原始 AgentCore Gateway 域名，在禁用 Private DNS 时必须包含在 Host 头中

例如：

```
export GATEWAY_URL=https://<vpce_id>.gateway.bedrock-agentcore.ap-southeast-2.vpce.amazonaws.com/mcp
export TOKEN=<your-token-here>
export GATEWAY_HOST=<gateway_id>.gateway.bedrock-agentcore.ap-southeast-2.amazonaws.com
```

- 创建并执行测试脚本。将以下 Python 代码复制到名为 agent.py 的文件中。该代码通过发现可用工具、用这些工具创建一个 Strands Agent，然后测试对话式交互（列出工具与天气查询）以及直接调用 MCP 工具，来验证 AgentCore Gateway 工作流。复制该代码：

```
from strands.models import BedrockModel
from mcp.client.streamable_http import streamablehttp_client
from strands.tools.mcp.mcp_client import MCPClient
from strands import Agent
import logging
import os

# Read authentication token and gateway URL from environment variables
token = os.getenv('TOKEN')
gatewayURL = os.getenv('GATEWAY_URL')  #vpc endpoint url
gatewayHost = os.getenv('GATEWAY_HOST') #domain name of the agentcore gateway

def create_streamable_http_transport():
    """Create HTTP transport with proper authentication headers"""
    return streamablehttp_client(
        gatewayURL, 
        headers={
            "Authorization": f"Bearer {token}",
            "Host":gatewayHost
        }
    )
# Initialize MCP client with the transport
client = MCPClient(create_streamable_http_transport)

# Configure Bedrock model - ensure IAM credentials in ~/.aws/credentials have Bedrock access
yourmodel = BedrockModel(
    model_id="amazon.nova-pro-v1:0",
    temperature=0.7,
)

# Configure logging for debugging and monitoring
logging.getLogger("strands").setLevel(logging.INFO)
logging.basicConfig(
    format="%(levelname)s | %(name)s | %(message)s",
    handlers=[logging.StreamHandler()]
)

# Test the complete agent workflow
with client:
    targetname = 'TestGatewayTarget36cb2ebf'
    
    # List available tools from the MCP server
    tools = client.list_tools_sync()
    
    # Create an Agent with the model and available tools
    agent = Agent(model=yourmodel, tools=tools)
    print(f"Tools loaded in the agent: {agent.tool_names}")
    
    # Test agent with a simple query to list available tools
    response1 = agent("Hi, can you list all tools available to you?")
    print(f"Agent response for tool listing: {response1}")
    
    # Test agent with a tool invocation request
    response2 = agent("Get the current weather for Seattle and show me the exact response from the tool")
    print(f"Agent response for weather query: {response2}")
    
    # Direct MCP tool invocation for validation
    result = client.call_tool_sync(
        tool_use_id="get-weather-seattle-call-1",  # Unique identifier for this call
        name=f"{targetname}___get_weather",  # Tool name format for Lambda targets
        arguments={"location": "Seattle"}
    )
    print(f"Direct MCP tool response: {result}")
```

- 使用以下命令运行该脚本：

`python3 agent.py`

## 高级配置：VPC 端点访问策略

VPC 端点策略是一种基于资源的策略，用于控制通过端点访问 AWS 服务的权限。与基于身份的策略不同，端点策略在网络层面提供额外一层访问控制。你可以为 AgentCore Gateway 的 VPC 端点配置访问策略，但需要特别的考量。在为 AgentCore Gateway 创建端点策略时，请考虑以下关键要素：

- **Principal 配置** – `Principal` 字段无法修改，因为 AgentCore Gateway 不使用 IAM 进行身份验证。身份验证是通过 bearer token 而非 IAM principal 处理的。
- **Resource 指定** – 如果要将访问限制到特定 gateway 端点，请明确定义 `Resource` 字段。使用完整的 [Amazon Resource Name](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference-arns.html)（ARN）格式来定位你账户中的特定 gateway，如下方示例策略结构所示。
- **Action 权限** – 对于 `Action` 字段，避免指定控制平面操作。使用通配符（*）来允许 gateway 功能所需的数据平面操作。

以下是一个示例策略结构：

```
{
"Version": "2012-10-17",
"Statement": [
{
"Principal": "*",
"Effect": "Allow",
"Action": "*",
"Resource": "arn:aws:bedrock-agentcore:<region>:<AWS_Account_ID>:gateway/<gateway_id>"
}
]
}
```

当 VPC 端点策略阻止某个请求时，你会看到类似以下的错误响应：

```
{"jsonrpc":"2.0","id":2,"error":{"code":-32002,"message":"Authorization error - Insufficient permissions"}}
```

### 策略缓存行为

AgentCore Gateway 为访问策略实现了缓存机制，这会导致策略变更最多延迟 15 分钟才生效。虽然该缓存显著提升了 gateway 性能，但也意味着策略修改可能不会立即反映到访问控制中。为了与这一行为良好配合，你在更新策略后应至少留出 15 分钟，让变更在整个系统中完全传播。在可能的情况下，把策略修改安排在计划内的维护窗口，以尽量减少对运营的影响。始终先在非生产环境中测试策略变更，再应用到生产 gateway；在诊断访问相关问题时，也要把缓存延迟考虑进去，避免过早开始排障。

## 清理

为避免持续产生费用并保持良好的资源卫生，请按顺序完成以下步骤来清理资源：删除 EC2 实例：

- 打开 Amazon EC2 控制台并选择你的测试实例
- 选择 **Instance state** 和 **Stop instance**，然后等待实例停止
- 选择 **Instance state** 和 **Terminate instance**，以永久删除该实例

删除 VPC 端点：

- 打开 Amazon VPC 控制台并选择 **Endpoints**
- 选择你创建的 VPC 端点（`vpce-agentcore-gateway`）
- 选择 **Actions** 和 **Delete VPC endpoints**
- 确认删除

删除安全组：

- 打开 Amazon EC2 控制台并选择 **Security groups**
- 选择你创建的 EC2 安全组（`ec2-agent-sg`）
- 选择 **Actions** 和 **Delete security groups**
- 对 VPC 端点安全组（`vpce-agentcore-sg`）重复上述操作

## 结论

在本文中，我们演示了如何使用 VPC 接口端点和 AWS PrivateLink 在 VPC 内托管的资源与 Amazon Bedrock AgentCore Gateway 之间建立安全、私有的连接。该架构通过实施与互联网隔离的网络，为企业 agentic AI 部署带来全面的收益，并借助专用的私有网络路径提供更强的安全性。该解决方案通过 VPC 端点策略实现稳健的数据边界，这些策略建立细粒度的访问控制，围绕你的 AI 资源划定严格的数据边界。此外，该架构还为本地环境提供到 Gateway 端点的私有连接，支持横跨云端与本地基础设施的分布式 AI 架构。对于大规模部署自主 AI 系统的组织，实施 VPC 接口端点可以构建高效 agent 运行所必需的安全网络基础，同时通过优化的网络路径降低延迟。这种企业级方案有助于让你的 agentic AI 应用在满足安全与合规要求的同时，获得更好的性能和更短的响应时间。

要了解更多关于实施这些模式和最佳实践的内容，请查阅 [Amazon Bedrock 文档](https://docs.aws.amazon.com/bedrock/)和 [AWS PrivateLink 文档](https://docs.aws.amazon.com/vpc/latest/privatelink/)，获取关于 AI 部署的全面指引。
