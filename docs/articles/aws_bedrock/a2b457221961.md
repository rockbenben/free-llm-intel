借助由智能体（agentic）AI 驱动的视频智能，你可以用自然语言就上传的视频提问，并在几秒内获得答案。媒体、安防、保险和专业服务各行业正在生成超出团队审阅能力的视频量。会议录音在共享盘中不断累积，安防摄像头录下数周无人回看的画面。现场巡检视频在初次审阅之后还长期躺在对象存储里。这些视频里的信息往往很有价值：三周前讨论过的一个设计决策、某人到达门口的确切时刻，或导致车辆碰撞的事件序列。但传统上要获取这些信息，就得人工观看数小时内容。而另一种做法——为每一种特定问题类型构建定制的机器学习（ML）流水线——又需要大量的开发投入。每一个新用例都意味着新的开发工作：

- 用于会议查询的转录流水线。
- 用于视觉搜索的计算机视觉流水线。
- 一个人脸匹配集成。

在本文中，我们讲解一套视频智能方案的架构与关键模式。该方案接受自然语言问题并从视频内容返回答案。方案使用一种在运行时决定调用哪些 AWS 服务的智能体架构。对先前已分析过的内容，响应在不到一秒内返回；对新视频的首次分析则根据时长和所需服务耗时 5–10 分钟。完整实现可在[配套 GitHub 仓库](https://github.com/aws-samples/sample-media-analysis-agent)中获取。

我们没有为每种问题类型预先构建固定流水线，而是使用 Strands Agents SDK 创建单个 AI 智能体，根据用户的问题来编排 [Amazon Bedrock](https://aws.amazon.com/bedrock/)、[Amazon Rekognition](https://aws.amazon.com/rekognition/) 和 [Amazon Transcribe](https://aws.amazon.com/transcribe/)。一家大型媒体与娱乐公司在一次 AWS Professional Services 合作中采用了这一做法。有了这套方案，他们的顾问可以对录制下来的 discovery session 内容进行查询，提取设计决策、行动项和利益相关方的立场。其结果：在一个超过 200 段数小时录音的积压中，人工审阅时间大约减少了 80%——该数据基于客户内部对每段录音分析师工时的前后对比（未经独立验证）。

## 方案概览

该方案是一个 AI 智能体，接受视频文件并让其内容通过自然对话即刻可查询。用户可以上传一段 90 分钟的会议录音并问“这次会议做了哪些决定？”或“有人提到过预算时间表吗？”智能体自行判断要调用转录、视觉分析还是两者兼用，然后把结果综合成一个连贯的回答。同一套系统也能处理安防画面查询（“这个人出现过吗？”）、内容分析（“总结前 30 分钟”）以及调查性问题（“碰撞前哪辆车换了车道？”）。每个用例都不需要单独的处理流水线。

下面的截图展示了这个界面：它提供一个用于自然语言查询的聊天面板，以及一个用于文件上传和分析模式选择的侧边栏。

图 1：视频智能聊天界面

关键的洞见在于流水线是在运行时决定的。对于口头内容的问题，智能体调用 Amazon Transcribe；对于人脸匹配，它转向 Amazon Rekognition；对于关于已处理内容的追问，它复用缓存结果。是模型负责路由，而不是应用代码。

## 前提条件

要跟随本文的实现，你需要：

- 一个 AWS 账户，可访问 Amazon Bedrock（已启用 Anthropic Claude Sonnet）以及 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/)。对于文档处理，需要 Amazon Bedrock Data Automation (BDA)，或者 Amazon Rekognition 与 Amazon Transcribe。参见 [Amazon Bedrock 中各 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。
- Python 3.11 或更高版本，并安装 Strands Agents SDK（`pip install strands-agents strands-agents-tools`）。
- 已配置 AWS Command Line Interface (AWS CLI)，具备前述服务的 AWS Identity and Access Management (IAM) 权限。
- 对 AI 智能体概念（如工具使用和推理循环）有基本了解。

## 架构

该系统由一个连接到多个 AWS AI 服务的智能体编排器组成，Amazon S3 为上传的视频和缓存的分析输出提供存储。智能体编排器是推理引擎。它用 Strands Agents SDK 构建、由 Amazon Bedrock 驱动，使用 Claude Sonnet 或另一个支持工具使用的大语言模型（LLM）。它接收来自用户的自然语言查询，根据问题决定要调用哪些工具，在需要时串联多个服务调用，并把结果综合成对话式响应。智能体维护会话历史，因此后续追问能在先前分析的基础上展开而无需重新处理。

图 2：方案架构

Amazon Rekognition 提供视觉分析，包括在视频帧中检测物体、场景、活动和人脸。当用户的问题涉及视频中可见的内容时，智能体会调用 Amazon Rekognition。Amazon Transcribe 将语音音频转换为文本，具备覆盖 100 多种语言的自动语言检测（参见 Amazon Transcribe 支持的语言）和说话人分离（speaker diarization）。当问题涉及口头内容时，智能体使用 Transcribe。Amazon Bedrock Data Automation (BDA) 提供另一条分析路径，将视频摘要、章节检测和完整转录在一次 API 调用中组合完成。当用户希望一步得到全面分析，或 Amazon Rekognition、Transcribe 不可用时，这很有用。所有上传的视频和分析输出都存储在 Amazon S3 中，并以每用户前缀实现多租户隔离。

这三个服务是起始集合，而非固定集合。因为智能体是从工具描述而非硬编码的工作流逻辑中选择工具，所以同一架构可以接受额外的服务作为工具。我们在*超越视频进行扩展*一节会回到这一点。对于生产部署，我们建议加上 Amazon Bedrock Guardrails，以强制内容过滤并对智能体响应做接地（grounding）检查，尤其是在人脸匹配和监控这类用例中——那里对负责任的 AI 控制不可或缺。

## 智能体编排如何运作

在传统的视频分析应用中，开发者定义一条固定的处理流水线：上传视频、运行转录、执行视觉分析、展示结果。这种方式不管具体查询是什么，都让每个视频走相同的步骤，用户要等整条流水线跑完才能提问。智能体方式将这一模型倒转。在仅限把视频文件上传到 S3 桶的最少预处理下，智能体对每个问题独立推理，只调用回答它所需的服务。

当用户提交查询时，智能体首先解析意图：用户想要转录摘要、视觉搜索，还是人脸匹配？然后检查是否已经做过并缓存了相关的分析。若没有，它选择合适的工具、执行它们（当某个工具的输出喂给另一个工具时，可能会按序执行），并把结果组合成自然语言答案。在我们对 60 分钟视频的测试中，对某个视频的第一个问题通常耗时 5–10 分钟（同时进行转录或视觉分析）。对同一内容的后续问题在不到一秒内返回，因为智能体复用缓存结果。实际时间因视频时长、分辨率和所调用的 AWS 服务而异。

### 配置智能体

下面的代码展示了完整的智能体设置。我们定义模型提供方、一段指导智能体推理行为的 system prompt，以及一组可用工具。使用 Strands 时，整套编排逻辑（决定调用哪些工具、按什么顺序、如何组合它们的输出）都由 LLM 处理，而非应用代码。我们展示两个有代表性的工具实现（`search_faces_in_video` 和 `analyze_with_bda`）。其余工具，包括 `transcribe_video` 和 `analyze_video_visuals`，遵循相同模式，可在 [GitHub 仓库](https://github.com/aws-samples/sample-media-analysis-agent)中获取。

```
from strands import Agent
from strands.models.bedrock import BedrockModel
from tools import (
    transcribe_video, analyze_video_visuals,
    search_faces_in_video, analyze_reference_image,
    analyze_with_bda, upload_video
)

model = BedrockModel(
    model_id="us.anthropic.claude-sonnet-4-5-20250929-v1:0",
    max_tokens=4096
)

SYSTEM_PROMPT = """
You are a video intelligence assistant. For each user query:
1. Determine whether it requires spoken content analysis,
   visual content analysis, or both
2. Check if prior analysis results are already cached
3. Invoke the appropriate tools
4. Synthesize results into a clear answer with timestamps
"""
```

生产环境的 system prompt 约有 250 行源码。下面这个简化示例意在阐明三条有代表性的策略（缓存复用、服务回退、多模态编排），而非逐字复现该 prompt：

```
# --- Cache management (excerpt) ---
CACHE_GUIDANCE = """
Before invoking any analysis tool, check the cache:
- Call get_cached_result(video_id, analysis_type) first
- If cached results exist and are < 24 hours old, use them
- If the user says "re-analyze" or "fresh analysis", bypass cache
- After any new analysis, store results with cache_result()

# --- Tool fallback behavior ---
If a tool call fails or returns low-confidence results:
- Transcribe failure: suggest BDA as fallback
- Rekognition low confidence (<60%): report uncertainty to user
- BDA timeout: fall back to individual Transcribe + Rekognition calls

# --- Multi-modal orchestration ---
When the query requires both audio and visual understanding:
1. Run Transcribe and Rekognition in parallel when possible
2. Correlate timestamps across modalities
3. Synthesize a unified answer referencing both sources
4. Cite specific timestamps for each claim
"""

agent = Agent(
    model=model,
    system_prompt=SYSTEM_PROMPT,
    tools=[transcribe_video, analyze_video_visuals,
           search_faces_in_video, analyze_reference_image,
           analyze_with_bda, upload_video]
)
```

生产 prompt 的其余部分盘点可用工具，并为文件选择、缓存复用与显式重新分析、BDA 设置与访问被拒回退、参考图搜索、转录与字幕、体育集锦、架构图，以及在 BDA 与服务专用分析之间做选择定义了工作流。它还统一多文件响应的规范、在清理前要求确认、对追问复用先前结果，并应用范围与上传进度的护栏。

有了这套配置，智能体自主处理路由、工具排序和响应综合。要增加一个新能力（例如检测屏幕文字），只需定义一个新的工具函数并把它加入 tools 列表，无需改动任何工作流逻辑。

### 用 @tool 装饰器定义工具

每个 AWS 服务都以一个用 `@tool` 装饰的 Python 函数暴露给智能体。函数签名定义了参数，docstring 告诉智能体何时以及如何使用它。这个 docstring 至关重要：它是智能体使用该工具的说明书。下面的例子展示了封装 Amazon Rekognition 的人脸搜索工具：

```
from strands.tools import tool
import boto3

@tool
def search_faces_in_video(
    video_s3_key: str,
    collection_id: str,
    confidence_threshold: float = 80.0
) -> dict:
    """Search for a specific person in video footage.

    Use this tool when the user provides a reference photo
    and asks whether that person appears in a video.
    Requires a face collection created first via
    analyze_reference_image.

    Args:
        video_s3_key: S3 key of the uploaded video
        collection_id: Rekognition collection with the
            indexed reference face
        confidence_threshold: Minimum confidence for a
            match (default 80%)

    Returns:
        Dict with matched_faces containing timestamps
        and confidence scores for each appearance
    """
    rek = boto3.client("rekognition")
    response = rek.start_face_search(
        Video={"S3Object": {
            "Bucket": BUCKET, "Name": video_s3_key}},
        CollectionId=collection_id,
        FaceMatchThreshold=confidence_threshold
    )
```

```
@tool
def analyze_with_bda(
    s3_uri: str,
    analysis_types: list[str] = ["SUMMARY", "CHAPTERS", "TRANSCRIPT"]
) -> dict:
    """Perform comprehensive video analysis using Amazon Bedrock Data Automation.

    Use this tool when the user wants a full video summary, chapter
    breakdown, or complete transcript, or when Rekognition/Transcribe
    are unavailable. Returns all requested analysis types in one call.

    Args:
        s3_uri: S3 URI of the uploaded video (s3://amzn-s3-demo-bucket/key)
        analysis_types: List of analysis types to perform.
            Options: "SUMMARY", "CHAPTERS", "TRANSCRIPT", "IAB"

    Returns:
        Dict with keys for each requested analysis type,
        including timestamps and confidence scores
    """
    bda = boto3.client("bedrock-data-automation-runtime")
    response = bda.invoke_data_automation_async(
        inputConfiguration={"s3Uri": s3_uri},
        dataAutomationConfiguration={
            "dataAutomationArn": BDA_PROJECT_ARN
        },
        outputConfiguration={"s3Uri": f"s3://{BUCKET}/bda-output/"}
    )
    invocation_arn = response["invocationArn"]
    # Poll for completion...
    result = poll_bda_result(invocation_arn)
    return {
        "summary": result.get("summary"),
        "chapters": result.get("chapters", []),
        "transcript": result.get("transcript")
    }
```

### 多步推理的实际运作

为了说明智能体如何串联多个工具调用，考虑一个用户上传参考照片并问“这个人出现在我的安防画面里吗？”的场景。智能体必须先索引参考人脸，然后在视频中搜索它。这是两个相互依赖的顺序操作。下面的追踪展示了智能体的内部推理：

```
[Think] This is a face-matching query. I need to index
the reference photo first, then search the video.

[Act] analyze_reference_image(image="reference.jpg")
[Observe] {"faces_detected": 1, "face_id": "face_001",
"confidence": 99.8}

[Think] Face indexed. Now searching the video.

[Act] search_faces_in_video(
video_s3_key="security_cam_july5.mp4",
collection_id="user_collection")
[Observe] {"matched_faces": [
{"timestamp": "00:14:32", "confidence": 97.2},
{"timestamp": "00:47:15", "confidence": 94.8}]}

[Response] Yes, the person appeared twice: at 14:32
(97% confidence) and 47:15 (95% confidence).
```

智能体自行确定了正确的操作顺序，并处理了它们之间的依赖关系（人脸搜索需要一个已索引的集合）。然后它以对话方式呈现结果。没有任何应用代码定义了这个顺序。模型基于工具描述和用户问题推理出了它。

对于全面分析（当用户说“分析这个视频”或“总结这段录音”时），智能体可以调用 Amazon Bedrock Data Automation (BDA)，而不必分别调用 Amazon Rekognition 和 Transcribe。BDA 在一次异步 API 调用中产出视频摘要、带时间戳的逐章分解以及完整转录：

```
[Think] The user wants a full summary. BDA provides summary +
chapters + transcript in one call, more efficient than
running Rekognition and Transcribe separately.

[Act] analyze_with_bda(s3_uri="s3://amzn-s3-demo-bucket/meeting.mp4")
[Observe] {"summary": "Team discussed Q3 roadmap...",
"chapters": [{"title": "Introductions", "start": "00:00"},
{"title": "Roadmap Review", "start": "05:32"}, ...],
"transcript": "Welcome everyone. Let's start with..."}

[Response] Here's the meeting summary with chapters:
Summary
The team discussed the Q3 roadmap...
Chapters
- 00:00 - Introductions
```

当结果含糊时，智能体会明确表达不确定性。一个临界置信度分数（例如 62%）会产生一个带限定的答案：“我在 14:32 找到一个可能的匹配，但置信度较低，所以你可能想手动核实一下。”如果转录因音频质量差而失败，智能体会建议替代方案：“音频质量太低，无法可靠转录。你想让我改为对演示幻灯片做视觉分析吗？”

## 示例用例

智能体模式广泛适用于这样一种场景：用户需要从视频内容中提取特定信息，而又无法预先知道需要哪种分析类型。

**会议智能** — 一位中途加入项目的团队成员上传先前的会议录音并提出针对性问题：“四月做了哪些架构决定？”“团队什么时候同意用 GraphQL 的？”或“总结关于认证方案的讨论。”智能体进行转录、搜索和摘要，返回带有时间戳、指向录音中具体时刻的答案。

**安防与出入监控** — 一位楼宇经理上传大堂摄像头画面，并配一张预期访客的照片，问“这个人本周进过大楼吗？什么时候？”智能体对视频运行人脸匹配，返回带置信度分数的具体时间戳。

**理赔调查** — 一位保险理赔员上传行车记录仪画面，问“描述碰撞前的事件序列”或“哪辆车在错误的车道上？”智能体将视觉场景分析与音频（言语反应、喇叭声）结合，重建事件时间线。

## 以稳定的工具契约超越视频进行扩展

上面三个例子都分析视频，但架构没有任何视频专属之处。智能体从 docstring 中选择工具，因此增加一个新能力（或一种全新模态）不过是把另一个服务封装成一个 `@tool` 函数并描述何时使用它，无需改动工作流逻辑。同一个编排器、缓存和每用户隔离原样适用。

图 3：将该模式扩展到其他模态

这使该模式成为多模态 AI 助手的通用模板，无论使用 AWS 服务还是第三方模型：

- **用 Amazon Textract 做文档和图理解。** discovery session 很少只存在于视频里。加一个 Textract 工具，从以 PDF 提供的架构图纸和工作文档中提取文本、表格和表单字段，智能体就能把白板上画的东西与录音里说的话交叉对照。这丰富了那个已经在回答会议音频问题的同一会话。
- **用 AWS HealthScribe 处理临床对话。** 把同一模式指向一段医患音频文件，一个 HealthScribe 工具就能返回结构化的临床记录（逐轮转录加上提取的章节，如主诉和治疗计划），于是用户可以针对该录音问“推荐了什么后续措施？”
- **实体与情感抽取，或第三方模型。** 一个 Amazon Comprehend 工具可以从智能体产出的任何转录中抽取实体、关键短语和可识别个人身份信息（PII）。Amazon Bedrock 上可用的模型（包括第三方模型）也可以按同样方式封装，用于领域专用推理。

在每种情况下，扩展点是工具契约而非流水线。已经构建了视频助手的团队，已经具备了编排、缓存、认证和每用户隔离这些脚手架，只需添加工具就能为另一种模态立起一个 AI 助手。

## 成本考量

每次查询的成本取决于智能体调用了哪些 AWS 服务。在首次分析（转录或视觉处理）之后，对同一视频的追问只产生 Amazon Bedrock 推理成本，因为结果已被缓存。下表展示了一个 60 分钟视频的近似成本：

| **服务** | **操作** | **近似成本** |
| --- | --- | --- |
| Amazon Transcribe | 60 分钟音频转录 | $1.44 |
| Amazon Rekognition | 人脸搜索（60 分钟视频） | $6.00* |
| Amazon Rekognition | 标签检测（60 分钟视频） | $6.00* |
| Amazon Bedrock | 智能体推理（每轮） | $0.05–$0.15 |
| Amazon S3 | 存储（500 MB，24 小时） | <$0.01 |

*这 $6.00 的 Amazon Rekognition 成本是每个视频一次性成本（后续查询只产生 Bedrock 推理成本）。*

基于截至 2025 年 7 月的 AWS 服务定价和上面的成本表，对一个 60 分钟视频的典型基于转录的查询，大约需要初始转录加 Bedrock 推理共 $1.50。对同一已转录内容的后续问题每轮只花费 $0.05–$0.15，仅覆盖 Bedrock 推理调用。实际成本取决于模型选择、输入长度和 AWS 区域。要查看当前定价，参见 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)、[Amazon Transcribe 定价](https://aws.amazon.com/transcribe/pricing/) 和 [Amazon Rekognition 定价](https://aws.amazon.com/rekognition/pricing/)。

## 部署

该方案部署在 Amazon Elastic Container Service (Amazon ECS) 上，配合 AWS Fargate。Streamlit 应用和智能体运行时在 Fargate 任务中运行，位于一个内部 Application Load Balancer 之后，而一个 Amazon CloudFront 分配是唯一的公共入口。CloudFront 通过一个专有网络（VPC）源站到达负载均衡器，因此负载均衡器留在私有子网中、没有通往互联网网关的路由，也无法从互联网直接访问。CloudFront 还用其默认的 *.cloudfront.net 证书终止查看端 TLS，从而在无需自定义域名或 AWS Certificate Manager 证书的情况下提供一个受公众信任的 HTTPS 端点。Amazon Cognito 负责认证（仅限受邀，默认强制通过基于时间的一次性密码 (TOTP) 进行多因素认证 (MFA)），上传和缓存输出存储在 Amazon S3 中，按每用户前缀组织并带有 24 小时生命周期策略。

图 4：在 Amazon ECS 和 AWS Fargate 上的部署架构

一个脚本（`./deploy/deploy-ecs.sh`）构建容器镜像、推送到 Amazon Elastic Container Registry (Amazon ECR)，并部署 AWS CloudFormation 栈。部署通常在 15–20 分钟内完成，其中大部分是 CloudFront 传播时间。完整的部署前提条件、`AllowSelfSignup` 参数及其取舍，以及逐步说明都在仓库 README 中。

## 开发工作流

Kiro 是一个 AI 驱动的开发环境，它把高层次想法转化为结构化需求、设计与实现任务，从而支持规格驱动（spec-driven）的软件开发。我们用它的 spec 工作流、持久化项目上下文和 agent hook，从概念推进到一个可部署的示例，同时在每项能力成形之际把安全内建进去。

**规格在实现之前定义了每项能力。** 人脸匹配的 spec 定义了输入（参考照片加视频）、预期行为（索引人脸、搜索并返回时间戳）以及边界情况（未检测到人脸、低置信度匹配）。转录的 spec 覆盖了多语言检测、说话人分离以及对重复查询的缓存行为。Kiro 从每个 spec 生成实现任务，并在整个特性生命周期中维护上下文。基于团队此前构建类似集成的经验，这把一个他们估计通常需要数周的工作压缩成了一个集中的冲刺。

**威胁建模与规格并行进行，而非在其之后。** 每定义一项能力，我们就建模它可能被如何滥用，并把结果记录在一个活的威胁模型中（见配套仓库的 `docs/threat-model.md`）。该模型逐条梳理具体的攻击链（认证绕过、网络暴露、通过 prompt 注入对智能体的利用、过度授权的 IAM，以及规避审计），并为每个威胁指派一种处置方式。每一条 Critical 和 High 级别的发现都在示例中得到了修复。仍保持打开的条目在那里以显式决定记录下来（接受残留风险，或一个记录在案的生产改动）。下一节所描述的那些控制项是这一过程的产出，而非事后补充。

**安全扫描被嵌入到开发循环中。** Kiro Hooks 在改动落地时运行自动化的静态扫描和基础设施即代码扫描，使用诸如 Automated Security Helper (ASH) 之类的工具，并且容器镜像仓库在创建时就启用了推送即扫描。发现结果作为同一个产出该特性的工作流中的任务返回，因此一个错误配置在代码还在编写时就会浮现，而不是在最后的单独评审阶段才被发现。其净效果是一种“左移”的姿态：一个小型团队在同一工作流里既保持特性推进速度又保持安全严谨，安全默认（secure-by-design）成为默认路径而非额外关卡。

## 安全考量

视频常含有敏感的业务讨论和可识别人物，因此一个多用户部署必须控制访问、隔离每个用户的数据，并限制任何单个用户动作的影响。

参考部署实现了四项主要控制：

- 仅限受邀的 Amazon Cognito 账户，强制 MFA。
- 每用户 Amazon S3 前缀，在每个工具边界通过所有权校验来强制执行。
- 一个内部 Application Load Balancer，仅通过 CloudFront 暴露。
- 每用户上传配额，限制跨租户的资源耗尽。

生产部署仍应决定是否使用带更严格查看端 TLS 策略的自定义域名、附加 AWS WAF、扩展审计日志与监控，并为人脸集合、转录和跨区域 Amazon Bedrock 模型推理定义数据处理要求。请与你的法务和隐私团队一起确定适用的同意、保留、删除和驻留要求。完整的逐项控制分析、接受残留风险、攻击链和加固清单，见配套仓库中的 `docs/threat-model.md` 以及 README 的“Security Considerations for Production”。

## 当前限制

超过两到三小时的视频，初次转录需要几分钟，不过后续查询几乎即时从缓存返回。人脸匹配准确率取决于参考照片的质量。清晰、光线良好的图像效果最好，而集体照里模糊的裁剪图可能给出较低的置信度。转录准确率会因背景噪音严重或有说话人重叠而下降。当智能体检测到质量问题时会指出这一点。Web 界面接受最大 2 GB 的 MP4、MOV、AVI 和 MKV 文件，这个上限是刻意设在 Fargate 任务内存以下的，因为 Streamlit 会在内存中缓冲上传。对于更大的媒体，直接上传到 Amazon S3 你的用户前缀下，并要求智能体按 URI 分析该对象（BDA 接受最大 10 GB 的视频对象）。并发能力受任务临时存储和每用户配额限制（在默认设置下约每任务六个并发用户），而自动伸缩会在 CPU 负载下增加任务。

## 清理

如果你部署了这个方案且不再需要它，请移除已配置的资源以避免持续产生费用。拆除涉及三个 CloudFormation 栈，它们靠参数值而非跨栈导出相关联，因此 CloudFormation 不会强制它们的依赖顺序。清空 S3 桶后，按此顺序删除栈：(1) `video-analytic-agent-ecs`（应用），(2) `video-analytic-cognito`（身份），(3) `video-object-locator-infra`（存储）。这些模板还会遗留 Amazon ECR 仓库和镜像，而 AWS Key Management Service (AWS KMS) 密钥会留在其待删除计划上。

Amazon Rekognition 的人脸集合需要单独清理。应用是在运行时创建它们的，所以 CloudFormation 不拥有它们，它们独立于视频桶的 24 小时 S3 生命周期而持续存在。删除上传的对象或删除栈并不会删除已索引的人脸。请显式列出并删除每个集合。完整的拆除顺序，包括先清空带版本控制的 S3 桶，见仓库 README 的“Teardown / clean up”。

## 结论

在本文中，我们展示了使用 Strands Agents SDK、Amazon Bedrock、Amazon Rekognition 和 Amazon Transcribe 构建对话式视频智能方案的架构与关键模式。有了这种智能体架构，你不再需要为每种问题类型预先构建处理流水线。取而代之，单个智能体根据用户的自然语言查询在运行时推理该调用哪些服务。增加新能力只需一个新的 `@tool` 函数和一次 prompt 更新，而不是一条新流水线。

要把这一模式应用到你自己的用例，先用 Bedrock 作为模型提供方配置一个 Strands 智能体，并把每个相关的 AWS 服务封装成一个带描述性 docstring 的工具函数。然后定义一个为你的领域指导推理的 system prompt，并在 ECS Fargate 上部署以供访问，或在本地运行以做原型。完整源码、部署自动化以及所有工具实现都可在[配套 GitHub 仓库](https://github.com/aws-samples/sample-media-analysis-agent)获取。
