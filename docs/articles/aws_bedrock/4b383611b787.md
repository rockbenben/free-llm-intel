# AWS 生成式 AI 模型敏捷性解决方案：面向生成式 AI 生产环境的 LLM 迁移综合指南

保持模型敏捷性对于组织适应技术进展并优化其人工智能（AI）解决方案至关重要。无论是在不同大语言模型（LLM）系列之间切换，还是升级到同一系列内的更新版本，结构化的迁移方法和标准化流程对于在尽量减少运营中断的同时推动性能持续改进都必不可少。然而，构建这样的解决方案在技术和非技术层面都充满挑战，因为该解决方案需要：

- 具备通用性，能覆盖多种用例
- 具备针对性，使新用户能把它应用到目标用例
- 提供全面且公平的 LLM 比较
- 自动化且可扩展
- 融合领域和任务特定的知识与输入
- 具备明确定义的端到端流程，从数据准备指导一直到最终成功标准

在本文中，我们介绍一个用于生成式 AI 生产中 LLM 迁移或升级的系统化框架，涵盖关键工具、方法论和最佳实践。该框架通过提供稳健的 prompt 转换与优化协议，促进不同 LLM 之间的切换。它包含评估多种性能维度的评测机制，通过对源模型和目标模型进行详细对比分析，实现数据驱动的决策。所提出的方法提供了一个全面的解决方案，既涵盖模型迁移的技术层面，也提供可量化的指标来验证迁移是否成功并识别进一步优化的空间，从而实现无缝切换和持续改进。以下是该解决方案的几个亮点：

- 提供多种报告选项，配备多样的 LLM 评测框架，并针对目标用例的指标选择提供全面指导。
- 除进一步优化 prompt 的最佳实践之外，还通过 [Amazon Bedrock Prompt Optimization](https://aws.amazon.com/about-aws/whats-new/2024/11/prompt-optimization-preview-amazon-bedrock/) 和 [Anthropic Metaprompt tool](https://anthropic.com/metaprompt-notebook) 提供自动化的 prompt 优化与迁移。
- 为模型选择提供全面指导，并给出一个端到端解决方案，用于在成本、延迟、准确性和质量方面比较模型。
- 提供功能示例和用例示例，帮助用户快速把解决方案应用到目标用例。
- 遵循该框架完成一次 LLM 迁移或升级所需的总时间为两天到两周不等，取决于用例的复杂程度。

## 解决方案实现

### 数据集准备

包含高质量样本的评估数据集对迁移流程至关重要。对大多数用例来说，需要带标准答案（ground truth）的样本；而对另一些用例，可以使用不要求 ground truth 的指标——例如答案相关性、忠实性、毒性和偏见（参见*评测框架与指标选择*一节）——作为判定指标。请使用以下指导和数据格式为目标用例准备样本数据。

样本数据的建议字段包括：

- 用于源模型的 prompt
- prompt 输入（如有），例如：基于检索增强生成（RAG）的答案生成所使用的问题和上下文
- 调用源模型时使用的配置，例如 temperature、top_p、top_k 等。
- 标准答案（ground truth）
- 源模型的输出
- 源模型的延迟
- 源模型的输入和输出 token，可用于成本计算

需要记住的是，对大多数用例而言，高质量的 ground truth 是成功迁移的关键。ground truth 不仅要验证正确性，还要核实其符合领域专家（SME）的指导和评估标准。参见*错误分析*一节，了解 SME 指导与评估标准的一个示例。

此外，如果已有任何评估指标，例如人工评估分数或 SME 的点赞/点踩，请为每个数据样本附上这些指标以及相应的理由或评论。如果已进行过任何自动化评估，请附上自动化评估的分数、方法和配置。下一节将就选择评测框架和定义指标提供更详细的指导。不过，从相关方那里收集现有的或偏好的评估指标作为参考仍然很有价值。

如适用，请包含以下字段：

- 源模型的现有真人评估指标，例如源模型的 SME 评分。
- 源模型的现有自动化评估指标，例如源模型的 LLM-as-a-judge 评分。

### 模型选择

选择合适的 LLM 需要仔细考量多个因素。无论是迁移到同一 LLM 系列内的模型，还是迁移到不同的 LLM 系列，理解每个模型的关键特性和评估标准对成功都至关重要。在计划跨 LLM 迁移时，请仔细比较和评估各种可用选项，并查看各模型提供方发布的 model card 和相应的 prompt 指南。评估 LLM 选项时，请考虑以下几项关键标准：

- **输入和输出模态**：文本、代码和多模态能力
- **上下文窗口大小**：模型可处理的最大输入 token 数
- 每次推理或每个 token 的**成本**
- **性能指标**：延迟和吞吐量
- **输出**质量与准确性
- **领域专精**与特定用例的兼容性
- **托管选项**：云、本地和混合
- **数据隐私与安全**要求

基于这些特性完成初步筛选之后，应通过在特定任务上评估性能来开展基准测试，以比较入围的模型。Amazon Bedrock 提供了一套全面的解决方案，可通过统一的 API 访问多种 LLM。这让我们能够试验不同的模型、比较它们的性能，甚至并行使用多个模型，同时只维持一个集成点。这种方式不仅简化了技术实现，还通过支持多元化的 AI 模型策略帮助避免厂商锁定。

### prompt 迁移

这里介绍两个自动化的 prompt 迁移与优化工具：[Amazon Bedrock Prompt Optimization](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-management-optimize.html) 和 Anthropic Metaprompt 工具。

#### **Amazon Bedrock Prompt Optimization**

[Amazon Bedrock Prompt Optimization](https://aws.amazon.com/about-aws/whats-new/2024/11/prompt-optimization-preview-amazon-bedrock/) 是 Amazon Bedrock 中提供的一个工具，可自动优化用户编写的 prompt。这帮助用户在 Amazon Bedrock 上构建高质量的生成式 AI 应用，并减少把工作负载从其他提供方迁移到 Amazon Bedrock 时的摩擦。Amazon Bedrock Prompt Optimization 能以最少的 prompt 工程，把现有工作负载从源模型迁移到 Amazon Bedrock 上的 LLM。借助该工具，我们可以选择要针对哪个模型优化 prompt，然后为目标模型生成优化后的 prompt。使用 Amazon Bedrock Prompt Optimization 的主要优势在于可以直接从 Amazon Bedrock 的 AWS 管理控制台使用它。通过控制台，我们可以快速为目标模型生成新的 prompt。我们也可以使用 [Bedrock API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_OptimizePrompt.html) 生成迁移后的 prompt，详见下面的实现细节。

##### **选项 B）使用 Amazon Bedrock API 优化 prompt**

我们也可以使用 Bedrock API 生成迁移后的 prompt：通过 [Agents for Amazon Bedrock runtime 端点](https://docs.aws.amazon.com/general/latest/gr/bedrock.html#bra-rt)发送一个 [OptimizePrompt ](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_OptimizePrompt.html)请求。在 input 对象中提供要优化的 prompt，并在 `targetModelId` 字段中指定要针对哪个模型优化。

响应流会返回以下事件：

- [analyzePromptEvent](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_AnalyzePromptEvent.html) —— 在 prompt 分析完成时出现。包含一条描述该 prompt 分析结果的消息。
- [optimizedPromptEvent](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_OptimizedPromptEvent.html) —— 在 prompt 重写完成时出现。包含优化后的 prompt。

运行以下代码示例来优化 prompt：

```
import boto3

# Set values here
TARGET_MODEL_ID = "anthropic.claude-3-sonnet-20240229-v1:0" # Model to optimize for. For model IDs, see https://docs.aws.amazon.com/bedrock/latest/userguide/model-ids.html
PROMPT = "Please summarize this text: " # Prompt to optimize

def get_input(prompt):
    return {
        "textPrompt": {
            "text": prompt
        }
    }
 
def handle_response_stream(response):
    try:
        event_stream = response['optimizedPrompt']
        for event in event_stream:
            if 'optimizedPromptEvent' in event:
                print("========================== OPTIMIZED PROMPT ======================\n")
                optimized_prompt = event['optimizedPromptEvent']
                print(optimized_prompt)
            else:
                print("========================= ANALYZE PROMPT =======================\n")
                analyze_prompt = event['analyzePromptEvent']
                print(analyze_prompt)
    except Exception as e:
        raise e
 
 
if __name__ == '__main__':
    client = boto3.client('bedrock-agent-runtime')
    try:
        response = client.optimize_prompt(
            input=get_input(PROMPT),
            targetModelId=TARGET_MODEL_ID
        )
        print("Request ID:", response.get("ResponseMetadata").get("RequestId"))
        print("========================== INPUT PROMPT ======================\n")
        print(PROMPT)
        handle_response_stream(response)
    except Exception as e:
        raise e
```

#### **Anthropic Metaprompt 工具**

Metaprompt 是 Anthropic 提供的一个 prompt 优化工具：它让 Claude 根据主题或任务代替用户编写 prompt 模板。我们可以用它教导 Claude 如何最好地构造 prompt，以稳定、准确地达成既定目标。

关键步骤如下：

- 指定原始 prompt 模板，说明任务，并指定输入变量和期望输出。
- 用 Claude LLM（例如 Claude-3-Sonnet）运行 Metaprompt，输入来自源模型的原始 prompt。
- 新的 prompt 模板会遵循 Claude LLM 的最佳实践，以优化后的指令集和格式生成。

使用 metaprompt 的好处：

- 与人工编写的 prompt 相比，prompt 更详细、更全面
- 有助于提高遵循 Anthropic 模型 prompt 最佳实践的可能性
- 允许指定关键细节，例如偏好的语气
- 提升模型输出的质量与一致性

Metaprompt 工具特别适合用来学习 Claude 偏好的 prompt 风格，也可作为一种为给定任务生成多个 prompt 版本的方法，从而简化针对目标用例测试多种初始 prompt 变体的工作。

要实施这一流程，请按照[ Prompt Migration Jupyter Notebook](https://github.com/aws-samples/Prompt-Migration-OpenAI-to-Amazon-Bedrock/blob/main/use-case-examples/rag-investment-analysis-assistant/notebooks/03_Prompt_migration.ipynb) 中的步骤，把源模型的 prompt 迁移为目标模型的 prompt。该 notebook 需要先在 Amazon Bedrock 中通过 Model Access 启用 Claude-3-Sonnet 作为 LLM，以生成转换后的 prompt。

以下是一个金融问答用例中源模型 prompt 的示例：

```
To answer the financial question, think step-by-step:
1. Carefully read the question and any provided context paragraphs related to yearly and quarterly document reports to find all relevant paragraphs. Prioritize context paragraphs with CSV tables.
2. If needed, analyze financial trends and quarter-over-quarter (Q/Q) performance over the detected time spans mentioned in the related time keywords. Calculate rates of change between quarters to identify growth or decline.
3. Perform any required calculations to get the final answer, such as sums or divisions. Show the math steps.
4. Provide a complete, correct answer based on the given information. If information is missing, state what is needed to answer the question fully.
5. Present numerical values in rounded format using easy-to-read units.
6. Do not preface the answer with "Based on the provided context" or anything similar. Just provide the answer directly.
7. Include the answer with relevant and exhaustive information across all contexts. Substantiate your answer with explanations grounded in the provided context. Conclude with a precise, concise, honest, and to-the-point answer.
8. Add the page source and number.
9. Add all source files from where the contexts were used to generate the answers.
context = {CONTEXT}
query = {QUERY}
rephrased_query = {REPHARSED_QUERY}
time_kwds = {TIME_KWDS}
```

完成 notebook 中的步骤后，我们就能自动得到目标模型的优化后 prompt。下面的示例生成的 prompt 针对 Anthropic 的 Claude LLM 做了优化。

```
Here are the steps to answer the financial question:

1. Read the provided <context>{$CONTEXT}</context> carefully, paying close attention to any paragraphs and CSV tables related to yearly and quarterly financial reports. Prioritize context paragraphs containing CSV tables.

2. Identify the relevant time periods mentioned in the <time_kwds>{$TIME_KWDS}</time_kwds>. Analyze the financial trends and quarter-over-quarter (Q/Q) performance during those time spans. Calculate rates of change between quarters to determine growth or decline.

3. <scratchpad>
In this space, you can perform any necessary calculations to arrive at the final answer to the <query>{$QUERY}</query> or <rephrasedquery>{$REPHARSED_QUERY}</rephrasedquery>. Show your step-by-step work, including formulas used and intermediate values.
</scratchpad>

4. <answer>
Provide a complete and correct answer based on the information given in the context. If any crucial information is missing to fully answer the question, state what additional details are needed.

Present numerical values in an easy-to-understand format using appropriate units. Round numbers as necessary.

Do not include any preamble like "Based on the provided context..." Just provide the direct answer.

Include all relevant and exhaustive information from the contexts to substantiate your answer. Explain your reasoning grounded in the provided evidence. Conclude with a precise, concise, honest, and to-the-point final answer.

Finally, cite the page source and number, as well as list all files that contained context used to generate this answer.
</answer>
```

如上一个示例所示，prompt 的风格和格式会自动转换为遵循目标模型的最佳实践，例如使用 XML 标签，并重新组织指令使其更清晰、更直接。

### 生成结果

迁移过程中的答案生成是一个迭代过程。总体流程包括把迁移后的 prompt 和上下文传给 LLM 并生成答案。需要多轮迭代来比较不同的 prompt 版本、多个 LLM 以及每个 LLM 的不同配置，以帮助我们选出最佳组合。在大多数情况下，生成式 AI 系统（例如基于 RAG 的聊天机器人）的整条流水线并不会被迁移，而只是迁移其中一部分。因此，流水线中其余组件有一个固定版本可用就至关重要。例如，在基于 RAG 的问答（Q&A）系统中，我们可能只迁移流水线中的答案生成组件。这样一来，我们就能继续使用现有生产模型已经生成好的上下文。

作为最佳实践，请使用 Amazon Bedrock 模型的标准调用方式（见[迁移代码仓库](https://github.com/aws-samples/Prompt-Migration-OpenAI-to-Amazon-Bedrock/tree/main)），在生成最终响应之外一并生成延迟、首 token 时间、输入 token 和输出 token 等元数据。这些元数据字段会作为新列添加到结果表末尾，供评估使用。输出格式和列名应与评估指标的要求保持一致。下表展示了一个 RAG 用例中样本数据在送入评估流水线之前的示例。

### 评估

评估是迁移流程中最重要的环节之一，因为它直接关联验收标准，并决定迁移是否成功。在大多数情况下，评估聚焦于三大类指标：准确性与质量、延迟和成本。可以使用自动化评估或人工评估来评定模型响应的准确性和质量。

#### 自动化评估

在质量评估流程中引入 LLM 代表了评估方法论的一次重大进步。这些模型擅长在上下文相关性、连贯性和事实准确性等多个维度上执行全面评估，同时保持一致性和可扩展性。这里介绍两类主要的自动化评估指标：

- **预定义指标**：在 [Ragas](https://docs.ragas.io/en/latest/)、[DeepEval](https://docs.confident-ai.com/) 和 [Amazon Bedrock Evaluations](https://aws.amazon.com/bedrock/evaluations/) 等基于 LLM 的评测框架中预定义的指标，或者直接基于非 LLM 算法的指标，例如[*评测框架*](https://aws.amazon.com/blogs/machine-learning/aws-generative-ai-model-agility-solution-a-comprehensive-guide-to-migrating-llms-for-generative-ai-production/#_Evaluation_of_frameworks)中介绍的那些。
- **自定义指标**：由用户提供定义、评估标准或 prompt 的定制指标，用于让 LLM 充当公正的评判者。

**预定义指标**

这些指标要么使用 Ragas、DeepEval 等基于 LLM 的评测框架，要么直接基于非 LLM 算法。这些指标被广泛采用、已预定义，可定制的选项有限。Ragas 和 DeepEval 是我们用于示例的两个基于 LLM 的评测框架与指标，位于[迁移代码仓库](https://github.com/aws-samples/Prompt-Migration-OpenAI-to-Amazon-Bedrock/tree/main)中。

- **Ragas：**Ragas 是一个用于评估 RAG 流水线的开源框架。RAG 指一类使用外部数据来增强 LLM 上下文的 LLM 应用。它提供多种由 LLM 驱动的自动化评估指标。迁移代码仓库中的 [Ragas evaluation notebook](https://github.com/aws-samples/Prompt-Migration-OpenAI-to-Amazon-Bedrock/blob/main/use-case-examples/rag-investment-analysis-assistant/notebooks/05b_Evaluate_QnA_RAGAS.ipynb) 介绍了以下指标。  **答案精确率（Answer precision）：**衡量与标准答案相比，模型生成的答案包含相关且正确论断的准确程度。 **答案召回率（Answer recall）：**评估答案的完整性；即模型检索出正确论断并将其与标准答案对比的能力。高召回率表明答案全面覆盖了与标准答案一致的必要细节。 **答案正确性（Answer correctness）：**对答案正确性的评估包括衡量生成答案与标准答案相比的准确程度。该评估依赖于 `ground truth` 和 `answer`，分数范围为 0 到 1。分数越高表明生成答案与标准答案越接近，即正确性越好。 **答案相似度（Answer similarity）：**评估生成答案与标准答案之间的语义相似程度。该评估基于 `ground truth` 和 `answer`，取值落在 0 到 1 的范围内。分数越高意味着生成答案与标准答案越吻合。

- **DeepEval：**DeepEval 是一个开源的 LLM 评估框架。它类似 Pytest，但专门用于对 LLM 输出做单元测试。DeepEval 结合最新研究，基于 G-Eval、幻觉、答案相关性、Ragas 等指标来评估 LLM 输出。它使用 LLM 以及各种在本地机器上运行的其他自然语言处理（NLP）模型进行评估。在 DeepEval 中，指标是基于特定标准衡量 LLM 输出表现的一种度量标准。DeepEval 提供一系列默认指标以便快速上手。迁移代码仓库中的 [DeepEval evaluation notebook](https://github.com/aws-samples/Prompt-Migration-OpenAI-to-Amazon-Bedrock/blob/main/use-case-examples/rag-investment-analysis-assistant/notebooks/05a_Evaluate_QnA_DeepEval.ipynb) 介绍了以下指标。|  **答案相关性（Answer relevancy）**：答案相关性指标通过评估 LLM 应用的 `actual_output` 与所提供输入的相关程度，来衡量 RAG 流水线生成器的质量。 **忠实性（Faithfulness）**：忠实性指标通过评估 `actual_output` 是否在事实上与 `retrieval_context` 的内容一致，来衡量 RAG 流水线生成器的质量。 **毒性（Toxicity）**：毒性指标是另一种无参考指标，用于评估 LLM 输出中的毒性。 **偏见（Bias）**：偏见指标用于判断 LLM 输出是否包含性别、种族或政治偏见。

- **Amazon Bedrock Evaluations**：Amazon Bedrock Evaluations 是一套工具，用于针对你的特定用例评估、比较和选择基础模型——包括自定义模型或第三方模型。它支持仅模型评估和 RAG 流水线评估。我们可以通过 AWS 控制台或 API 使用 Bedrock Evaluations。Amazon Bedrock Evaluations 为独立 LLM 和完整 RAG 流水线提供了一长串内置指标，包括但不限于：  **准确性（Accuracy）**：衡量模型输出的正确性。 **忠实性（Faithfulness）：**检查事实准确性并避免幻觉。 **有用性（Helpfulness）**：整体衡量响应在回答问题方面的有用程度。 **逻辑连贯性（Logical coherence）**：衡量响应是否没有逻辑空缺、不一致或矛盾。 **有害性（Harmfulness）**：衡量响应中的有害内容，包括仇恨、侮辱、暴力或性内容。 **刻板印象（Stereotyping）**：衡量响应中针对个人或群体的概括性陈述。 **拒答（Refusal）**：衡量响应在回答问题时的回避程度。 **遵循指令（Following instructions）**：衡量模型响应在多大程度上遵循 prompt 中的确切指示。 **专业风格与语气（Professional style and tone）**：衡量响应的风格、格式和语气对专业场景的适合程度。

**自定义指标**

这些指标由用户定义，通常针对特定任务或领域定制。一种流行的方法是用自定义的 LLM 作为评判者，使用用户提供的 prompt 为答案给出评估分数。与使用预定义指标相比，这种方法高度可定制，因为我们可以让 prompt 携带任务特定的评估要求。例如，我们可以要求 LLM 生成一个 10 分制评分体系，并在信息正确性、上下文相关性、细节深度与全面性、整体实用性和有用性等不同维度上，对照标准答案全面评估该答案。

#### 人工评估

尽管量化指标提供了有价值的数据点，仍需要基于专业指南和 SME 反馈的全面定性评估来验证模型性能。有效的定性评估通常覆盖几个关键方面，包括响应主题与语气的一致性、不当或非预期内容的检测、领域特定准确性、日期与时间相关问题等。借助 SME 的专业知识，我们可以识别出量化分析可能遗漏的细微差别和潜在问题。[错误分析](https://aws.amazon.com/blogs/machine-learning/aws-generative-ai-model-agility-solution-a-comprehensive-guide-to-migrating-llms-for-generative-ai-production/#_Error_analysis) 提供了一些可供 SME 用作评估标准的潜在维度，这些维度也可以作为验证和准备标准答案的指导。我们可以使用 Amazon Bedrock Evaluations 等工具进行人工评估。

尽管人工评估或从 UI 收集的用户反馈能直接反映 SME 的评估标准，但它在效率、可扩展性和客观性上都不如自动化评估方法。因此，生成式 AI 系统的开发生命周期可能从人工评估起步，但最终会转向自动化评估。如果自动化评估未达到基线目标或预定义的评估标准，则可以使用人工评估。

#### 延迟指标

在迁移语言模型时，运行时性能指标是衡量运营成功与否的关键指标。总延迟和首 token 时间（Time to first token，TTFT）是最常用的延迟度量指标。

- **总延迟**是一个端到端指标，衡量从初始 prompt 到最终输出完成整段响应生成所需的总时长。它涵盖处理输入、生成响应以及把响应交付给用户。总延迟影响用户满意度、系统吞吐量和资源利用率。
- **首 token 时间（TTFT）**量化初始响应速度——具体来说，是模型生成第一个输出 token 之前的时长。该指标显著影响感知响应速度和用户体验，在交互式应用中尤其如此。TTFT 在对话式 AI 和实时系统（聊天机器人、虚拟助手和交互式搜索系统等应用）中尤为重要，因为用户期望即时反馈。较低的 TTFT 会营造出系统响应迅速的感觉，并能大幅提升用户参与度。

如果结果生成步骤需要多次 LLM 调用，则应提供细分延迟指标，因为在后续的模型比较步骤中，只应比较与 LLM 迁移对应的子模块延迟。

#### 成本计算

对 LLM 调用而言，成本可以根据输入和输出 token 的数量以及相应的每 token 价格来计算：

```
LLM_invocation_cost = number_of_input_tokens * price_per_input_token + number_of_output_tokens * price_per_output_token
```

输入和输出 token 的单价对应的成本计算表可在 [Amazon Bedrock Pricing ](https://aws.amazon.com/bedrock/pricing/) 中找到。

## 进一步优化

在 LLM 迁移或升级过程中增强和优化生成式 AI 生产流水线时，用户通常关注两个关键方面：

- 生成答案的质量
- 响应生成的延迟

### prompt 优化

要优化生成答案的质量，我们需要通过开展错误分析来充分理解这些错误，并识别出需要做 prompt 优化的条目。

#### 错误分析

如果完全不做优化，候选 LLM 不太可能给出尽可能好的响应。因此，开展错误分析并聚焦于可能的错误模式方面，有助于我们评估生成答案的质量并识别改进机会。错误分析也为人工 prompt 工程提供了改进质量的路径。在收集了错误分析洞见和 SME 反馈之后，就可以开展迭代式的 prompt 优化流程。首先，把错误分析洞见和 SME 反馈整理成清晰的指导或标准。理想情况下，这些标准应在开始 prompt 迁移之前就明确下来。这些标准是进一步优化 prompt 的核心依据，有助于提供一致、高质量的响应，达到 SME 的要求。以下是我们可能从 SME 那里获得的一份指导与标准示例。

**SME 在金融问答用例中给出的答案格式风格指南示例：
**

- **正确性**  确保提取的数字正确。所有数字都应与标准答案匹配。确保标准答案中的所有论断都出现在 LLM 答案中。生成的响应不应添加无关句子。
- **时间**  生成的答案必须正确识别问题中的财年和所有需要的季度。在答案中，季度顺序最好从最近到最早。当问题问及同比数据时，答案应说明整体年度或最后一个季度，而不是逐季度呈现。当答案来自单一新闻文档时，请在答案中注明发布日期。
- **主题与语气**  使用专业语言，模仿报纸的风格。
- **格式与摘录**  当用户查询要求列表时，以项目符号格式呈现列表。当用户查询要求摘录时，先给出总结性陈述，然后给出直接从文档中摘录、未经编辑的项目符号列表。要求给出完整清单的查询最好包含项目符号。要求给出带有主观分类的主题或议题的查询最好包含项目符号列表。不要在开头引用上下文（根据上下文）。
- **长度**  大多数响应应在 30–150 词之间。当问题涉及多个实体，或需要响应包含子类别时，可以接受更长的答案。

#### 优化技术

在获得清晰的标准之后，可以使用多种优化技术来满足这些标准，例如：

- 通过 prompt 工程在 prompt 的指令中明确某些标准
- 通过 few-shot learning 明确答案格式和生成答案的示例
- 引入有助于 LLM 理解任务和问题上下文的元信息
- 通过前处理或后处理强制输出格式或解决某些常见的错误模式

### 延迟优化

有几种可行的延迟优化方案：

#### 优化 prompt 以生成更短的答案

LLM 模型的延迟直接受输出 token 数量的影响，因为每多一个 token 都需要对模型单独做一次前向传播，从而增加处理时间。生成的 token 越多，延迟越大，在 Opus 4 这类更大的模型中尤其明显。为降低延迟，我们可以在 prompt 中加入指令，避免给出冗长的答案、无关的解释或填充词。

#### 使用预置吞吐量

吞吐量是指模型处理和返回的输入与输出的数量和速率。购买预置吞吐量（provisioned throughput），为专属托管的模型提供更高水平的吞吐量，相比使用按需模型有可能降低延迟。虽然它不能保证延迟改善，但始终有助于避免请求被限流（throttled）。

#### 改进生命周期

候选 LLM 在完全不做优化的情况下不太可能达到尽可能好的性能。前述优化流程通常也是迭代进行的。因此，改进（优化）生命周期对于提升性能以及识别流水线或数据中的缺口或缺陷至关重要。改进生命周期通常包括：

- prompt 优化
- 答案生成
- 评估指标生成
- 错误分析
- 样本标签核验
- 针对样本缺陷和错误标签更新数据集

任务或领域知识识别　本文描述的迁移流程可用于生成式 AI 解决方案生产生命周期中的两个阶段。

### 端到端 LLM 迁移与模型敏捷性

新的 LLM 发布频繁。没有任何 LLM 能在一个给定用例上持续保持巅峰性能。生产中的生成式 AI 解决方案迁移到另一个 LLM 系列或升级到某个 LLM 的新版本，是很常见的情况。因此，拥有一个标准化、可复用的端到端 LLM 迁移或升级流程，对任何生成式 AI 解决方案的长期成功都至关重要。

### 监控与质量保证

当迁移或更新稳定下来后，应有一套标准的监控与质量保证流程，使用定期刷新的、带标准答案的金标准评估数据集以及自动化或人工评估指标，并对真实用户轨迹进行评估。作为该解决方案的一部分，已建立的评估流程以及数据与标准答案收集流程可以复用于监控与质量保证。

## 提示与建议（经验教训）

以下是确保 LLM 迁移或升级流程成功的一些提示与建议。

- **验收条件**：在开始时定义的数据、评估标准和成功标准应足以让相关方放心地验收该流程。理想情况下，流程期间数据、标准答案或 SME 评估与成功标准都不应发生变化。
- **样本数据与质量**：数据在质量和数量上都应足以支持有把握的评估。标准答案和标签应与 SME 的评估标准和期望完全对齐。理想情况下，流程期间数据、标准答案或 SME 评估标准都不应发生变化。
- **改进生命周期**：务必规划并实施改进生命周期，以最大限度发挥所选 LLM 的价值。
- **模型选择**：在把竞争性的目标模型与源模型对比时，可使用 [Artificial Analysis](https://artificialanalysis.ai/) 基准测试网站等资源，获得对模型的整体比较。这类比较通常涵盖质量、性能和价格分析，可在开始实验之前提供有价值的洞察。这项前期研究有助于缩小最有希望的候选模型范围，并为实验设计提供依据。
- **性能与成本的权衡**：在评估不同模型或解决方案时，务必考虑性能与成本之间的平衡。在某些情况下，某个模型的性能可能略低，但成本降低足够多，使其整体上更具成本效益。当性能差异很小而成本节省可观时，这一点尤其成立。
- **优化技术**：探索 prompt 工程或预置吞吐量等各种优化技术，可以显著改善准确性和延迟等性能指标。这些优化有助于弥合不同模型之间的差距，应作为评估流程的一部分加以考虑。
