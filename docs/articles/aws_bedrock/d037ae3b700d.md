# 在 Amazon Bedrock AgentCore 上借助 Chrome 企业策略控制 AI agent 的浏览范围

具备不受限网络访问能力的 AI agent 会带来显著的安全风险。如果没有 Chrome 企业策略来控制浏览器行为，agent 可能导航到未授权的域名、把凭证存入浏览器的密码管理器，或下载超出审批工作流的文件。拥有使用私有证书颁发机构（CA）的内部服务的组织，还面临额外的障碍：对这类服务的每一次 HTTPS 连接都会因证书校验错误而失败。

[Amazon Bedrock AgentCore Browser](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html) 现在支持 [Chrome 企业策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-enterprise-policies.html) 与 [自定义根 CA 证书](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-root-ca-certificates.html)，让组织能够对 agent 的浏览器行为与网络连通性做细粒度控制。借助 Chrome 策略，你可以配置 450 多项浏览器设置，包括 URL 过滤、下载限制与密码管理器控制，并通过熟悉的 Chrome 企业级 JSON 配置生效。自定义根 CA 支持则让 agent 能够连接内部服务，并在信任组织自己的证书颁发机构的前提下，穿过企业级 SSL 拦截代理工作。可用设置的完整参考见 [Chrome Enterprise policy 列表](https://chromeenterprise.google/policies/)。

在本文中，你将配置 Chrome 企业策略，把浏览器 agent 限制在特定网站；通过会话录制观察策略的执行；并用一个公开测试站点演示自定义根 CA 证书。这套演练产出一个可运行的方案：它在企业浏览器限制之下研究 Amazon Bedrock AgentCore 文档。

## 为什么需要为 AI agent 强制浏览器策略

把 [Chrome 企业策略](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-enterprise-policies.html) 用到 AI 浏览器 agent 上，可以满足组织的三类需要。

第一，你可以把 agent 的活动范围限制在已批准的域名内。URL allowlist 与 denylist 限定 agent 能导航到哪里。一个负责在特定门户上处理发票的 agent，并不需要访问社交媒体或搜索引擎。策略在浏览器层强制执行这些边界，与 agent 的 prompt 或推理无关。

第二，你可以关闭有风险的浏览器功能。借助 Chrome 策略，你可以关掉密码管理器、阻止文件下载、停用自动填充，并控制其他数十项浏览器能力。对与敏感系统交互的数据录入 agent 而言，这些控制降低了意外存储数据或数据外泄的风险。

第三，你可以把策略管理与 agent 开发分开。托管策略通过控制面 API 在浏览器层配置，并对该浏览器创建的每个会话生效。这让你的安全团队定义已批准的浏览器配置，而开发团队专注于 agent 逻辑，无需把策略决策硬编码进应用代码。

## Chrome 策略与根 CA 证书如何生效

这一集成包含两层策略强制执行，以及一项可选的证书信任配置。

托管策略在浏览器层生效。你在通过控制面 API 创建浏览器时，提供存放在 Amazon Simple Storage Service（Amazon S3）中的 Chrome 企业策略 JSON 文件。这些策略由服务保存，并对该浏览器创建的每个会话强制执行。托管策略对应 Chrome 的 `/etc/chromium/policies/managed/` 目录。它们不能被会话级设置覆盖。

推荐策略在会话级生效。你可以在通过数据面 API 启动浏览器会话时，可选地提供额外的策略 JSON 文件。这些文件对应 Chrome 的 `/etc/chromium/policies/recommended/` 目录，作用等同于用户偏好。如果托管策略与推荐策略在同一项设置上冲突，以托管策略优先。这是 Chrome 的默认行为。

你可以使用自定义根 CA 证书，把组织的根 CA 证书存放在 AWS Secrets Manager 中，并在创建浏览器或 AgentCore Code Interpreter 时引用它。服务会把该证书导入证书信任库，因此对内部服务与 SSL 拦截代理的连接无需关闭证书校验即可成功。

## 实操演示

notebook 分为两部分。第一部分创建一个 Chrome 企业策略，把它应用到自定义的 AgentCore Browser，并用 Playwright 验证允许的 URL 能加载、被阻止的 URL 会被拒绝。第二部分用 AgentCore Code Interpreter 演示自定义根 CA 证书。

### 定义 Chrome 企业策略

notebook 最初的几个 cell 定义了一条 Chrome 企业策略，把浏览器限制在 AWS 文档范围内，并关闭 agent 不需要的功能。策略 JSON 使用标准的 Chrome 企业策略设置。

```
policy = {
    "URLBlocklist": ["*"],
    "URLAllowlist": [
        "docs.aws.amazon.com",
        ".aws.amazon.com",
        ".amazonaws.com",
    ],
    "PasswordManagerEnabled": False,
    "DownloadRestrictions": 3,
    "DeveloperToolsAvailability": 0,
    "BookmarkBarEnabled": False,
    "AutofillAddressEnabled": False,
    "AutofillCreditCardEnabled": False,
}
```

下表说明每一项策略设置。

| **策略** | **值** | **效果** |
| --- | --- | --- |
| URLBlocklist | [“*”] | 默认阻止所有 URL |
| URLAllowlist | docs.aws.amazon.com, .aws.amazon.com, .amazonaws.com | 允许 AWS 文档及相关域名 |
| PasswordManagerEnabled | false | 阻止凭证存储 |
| DownloadRestrictions | 3 | 阻止下载 |
| DeveloperToolsAvailability | 0 | 允许 DevTools（CDP/Playwright 自动化必需） |
| BookmarkBarEnabled | false | 隐藏书签栏 |
| AutofillAddressEnabled | false | 停用地址自动填充 |
| AutofillCreditCardEnabled | false | 停用信用卡自动填充 |

请注意，URLAllowlist 使用的是 Chrome 的 URL 过滤模式格式，与常见的 glob 模式不同。像 docs.aws.amazon.com 这样的域名模式匹配精确域名；以点开头，例如 .aws.amazon.com，则匹配子域名。完整的模式语法参见 [URLAllowlist 策略文档](https://chromeenterprise.google/policies/#URLAllowlist)。

还要注意，对于将配合 Playwright 或其他基于 CDP 的自动化使用的浏览器，DeveloperToolsAvailability 必须设为 0（或干脆省略）。AgentCore Browser 自动化使用 Chrome DevTools Protocol（CDP）。把该策略设为 2 会在 Chrome 层禁用 CDP，从而悄悄破坏自动化。WebSocket 连接在代理层会成功，但 Chrome 拒绝 CDP 命令，最终导致超时。

### 创建带托管策略的浏览器

接下来的 cell 创建一个自定义浏览器，对每个会话强制执行该策略。关键的 API 调用使用 enterprise_policies 参数，并把 type 设为 MANAGED。会话录制也一并启用，这样你之后可以回放会话。

```
from bedrock_agentcore.tools import BrowserClient

client = BrowserClient(REGION)

response = client.create_browser(
    name="docs_research_browser",
    execution_role_arn=EXECUTION_ROLE_ARN,
    network_configuration={"networkMode": "PUBLIC"},
    enterprise_policies=[
        {
            "location": {
                "s3": {
                    "bucket": BUCKET_NAME,
                    "prefix": POLICY_KEY,
                }
            },
            "type": "MANAGED",
        }
    ],
    recording={
        "enabled": True,
        "s3Location": {
            "bucket": BUCKET_NAME,
            "prefix": "policy-demo",
        },
    },
)
```

随后 notebook 会轮询 get_browser()，直到状态从 CREATING 变为 READY。

### 用 Playwright 演示 Chrome 策略的强制执行

notebook 启动一个浏览器会话，并用 [Playwright](https://playwright.dev/docs/intro) 导航到两个 URL。第一个 URL docs.aws.amazon.com 被策略允许，因此页面正常加载。第二个 URL www.wikipedia.org 被策略阻止，因此 Chrome 显示错误页。

该测试使用 wait_until=”domcontentloaded”，而不是默认的 load 事件。AWS 文档页面上有分析脚本与追踪像素带来的持续后台网络活动，这会让 Playwright 的 networkidle 与默认 load 状态难以结束。同样地，文本提取使用 page.evaluate() 直接在浏览器上下文中运行 JavaScript，从而避免 Playwright 选择器引擎在 DOM 持续变动的页面上超时。

运行这个 cell 后，你应该看到类似下面的输出：

```
TEST 1: Navigate to docs.aws.amazon.com (ALLOWED)
Page title: Overview - Amazon Bedrock AgentCore
Page text preview: Amazon Bedrock AgentCore ...
Result: PAGE LOADED SUCCESSFULLY

TEST 2: Navigate to www.wikipedia.org (BLOCKED)
Page title:
Result: CHROME POLICY BLOCKED THIS URL
```

这正是 Chrome 策略的核心价值。限制发生在浏览器层，与 agent 的推理或 prompt 指令无关。

## 演示自定义根 CA 证书

使用私有 CA 运行内部服务，或让流量穿过 SSL 拦截式企业代理的组织，需要其 agent 信任这些非公开证书。AgentCore Browser 与 AgentCore Code Interpreter 为此支持自定义根 CA 证书。

本节使用 [https://untrusted-root.badssl.com](https://untrusted-root.badssl.com)，这是一个公开网站，它故意提供由不受信任根 CA 签发的证书。对这个站点的 HTTPS 连接会因证书校验错误而失败，正如在没有正确根 CA 时连接你的内部服务也会失败一样。

notebook 会执行三个步骤。

### 把根 CA 证书存入 AWS Secrets Manager

BadSSL 的不受信任根 CA 证书是公开可得的（来源：[badssl.com/certs/ca-untrusted-root.crt](https://badssl.com/certs/ca-untrusted-root.crt)）。notebook 把它保存到 AWS Secrets Manager，以便 Amazon Bedrock AgentCore 将其导入证书信任库。在生产环境中，组织的内部 CA 证书或 SSL 拦截代理的根 CA 证书会以同样的方式放进 Secrets Manager。

### 展示没有根 CA 时的失败

notebook 创建一个默认的 AgentCore Code Interpreter 会话，并运行一段 Python 代码，对那个不受信任的站点调用 urllib.request.urlopen()。连接会以 SSLCertVerificationError 失败。这与你连接使用私有 CA 的内部企业服务时看到的错误相同。

### 展示使用根 CA 后的成功

接着 notebook 创建一个自定义 AgentCore Code Interpreter，通过 certificates 参数信任 BadSSL 根 CA 证书。这与 BrowserClient.create_browser() 中已可用的模式相同。

```
from bedrock_agentcore.tools import CodeInterpreter, Certificate

ci_client_with_ca = CodeInterpreter(REGION)

response = ci_client_with_ca.create_code_interpreter(
    name="demo_rootca_interpreter",
    execution_role_arn=EXECUTION_ROLE_ARN,
    network_configuration={"networkMode": "PUBLIC"},
    certificates=[Certificate.from_secret_arn(secret_arn)],
)
```

在自定义解释器上运行同一段 urlopen() 代码后，输出显示 Status: 200。连接之所以成功，是因为 BadSSL 根 CA 现在被信任了。无需改动任何代码，信任是在基础设施层配置的。

*完整代码见 [示例 notebook](https://github.com/awslabs/amazon-bedrock-agentcore-samples/tree/main/01-tutorials/05-AgentCore-tools/02-Agent-Core-browser-tool/13-browser-chrome-policies)。*

### 如何应用到你的组织

badssl.com 这个演示对应两个真实场景。

| **场景** | **在 AWS Secrets Manager 中存什么** | **配置** |
| --- | --- | --- |
| 内部企业服务 | 你组织的根 CA 证书（即为你的人力资源门户、Jira、Artifactory 等类似服务签发证书的 CA） | 在创建浏览器或 AgentCore Code Interpreter 时，在 certificates 中引用该 secret ARN |
| SSL 拦截式企业代理 | 你代理的根 CA 证书（Zscaler、Palo Alto Networks 等使用） | 在 certificates 中引用该 secret ARN，并配置代理设置 |

自定义根 CA 证书在 AgentCore Browser 与 AgentCore Code Interpreter 中都可用。在浏览器中，证书被导入 Chrome 的信任库；在解释器中，服务会配置 REQUESTS_CA_BUNDLE 与 SSL_CERT_FILE 等环境变量，使 Python 库信任自定义 CA，无需在代码层做变通。

你可以在同一个浏览器里把根 CA 证书与 Chrome 策略结合起来。下面的示例创建一个接入 VPC 的浏览器，它信任内部 CA，并把导航限制在企业内网。

```
from bedrock_agentcore.tools import BrowserClient, Certificate

response = client.create_browser(
    name="internal_locked_down_browser",
    execution_role_arn=EXECUTION_ROLE_ARN,
    network_configuration={
        "networkMode": "VPC",
        "vpcConfig": {
            "securityGroups": ["sg-0123456789abcdef0"],
            "subnets": ["subnet-0123456789abcdef0"],
        }
    },
    enterprise_policies=[
        {
            "location": {
                "s3": {
                    "bucket": "org-policies",
                    "prefix": "intranet-only-policy.json",
                }
            },
            "type": "MANAGED",
        }
    ],
    certificates=[
        Certificate.from_secret_arn(
            "arn:aws:secretsmanager:us-west-2:123456789012:secret:corp-root-ca"
        )
    ],
)
```

有了这些能力，你可以部署在组织安全与合规边界内运行的 AI agent。Chrome 策略提供浏览器级控制，且独立于 agent 应用代码管理；自定义根 CA 支持则移除了通往内部基础设施的连通性障碍。

## 后续步骤

从创建一个带 URL allowlist 的浏览器开始，按你的用例量身定制。 [Chrome Enterprise policy 列表](https://chromeenterprise.google/policies/) 记录了 450 多项可配置设置。对与敏感表单交互的数据录入 agent，可考虑停用自动填充与密码管理器。对在特定门户上处理文档的 agent，可限制下载并把导航限定到该门户的域名。

如果你的组织使用私有 PKI，请配置根 CA 证书并测试到内部服务的连通性。对在 SSL 拦截代理后方运行的 agent，可把根 CA 配置与 [代理配置](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html) 功能结合，让流量经企业代理转发，同时信任该代理的证书。

关于 Amazon Bedrock AgentCore Browser 能力的更多信息，参见 [Amazon Bedrock AgentCore Browser 文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html)。如有反馈，请在 [Amazon Bedrock AgentCore Python SDK 仓库](https://github.com/aws/bedrock-agentcore-sdk-python) 中提交 issue。
