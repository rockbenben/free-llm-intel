# Amazon Bedrock Agents 自定义 orchestrator 入门

[生成式 AI](https://aws.amazon.com/generative-ai/) agent 的设计目的是与环境交互以实现特定目标，例如自动化重复性任务、增强人的能力。这些 agent 通过编排能够实时适应目标变化的多步骤工作流，提升生产力、减少错误，并提供更个性化的体验。为了有效管理这些复杂工作流，agent 依赖一套编排策略，用来协调与各类工具、知识源及其他 agent 的交互。这种编排让 agent 能够分析数据、解读上下文、安排任务顺序，并适应不断变化的需求，确保工作流保持高效、准确且有韧性。

[Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/) 提供了一套完全托管的方案，使用[基础模型](https://aws.amazon.com/what-is/foundation-models/)（FM）并辅以增强工具，通过编排好的多步骤工作流自主运行任务、达成目标，从而简化生成式 AI 应用的开发。使用默认的编排策略——推理与行动（[ReAct](https://arxiv.org/abs/2210.03629)），用户可以快速构建并部署 agentic 方案。ReAct 是一种通用的解决问题方法，它利用 FM 的规划能力在每一步动态调整动作。尽管 ReAct 通过让 agent 依据变化的需求持续重新评估决策而具备灵活性，但当涉及的工具很多时，其迭代式做法可能导致更高的延迟。

为了获得更强的编排控制力，Amazon Bedrock Agents 推出了[自定义 orchestrator 功能](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-custom-orchestration.html)，用户可以用它来微调 agent 行为，并在每个工作流步骤管理工具交互。这种自定义能力让组织可以针对自身具体的运营需求定制 agent 功能，提升精度、适应性与效率。本文将探讨自定义 orchestrator 的工作原理，并通过默认 Bedrock Agent 的 ReAct 与无观察推理（reasoning without observation，[ReWoo](https://arxiv.org/abs/2305.18323)）示例演示其应用。

## 自定义 orchestrator 概览

Amazon Bedrock Agents 的自定义 orchestrator 由用户以 [AWS Lambda](https://aws.amazon.com/lambda/) 函数的形式实现，可对任务规划、完成与验证提供细粒度控制。与优先保证决策透明度和逐步推理的默认 ReAct 编排方式不同，自定义 orchestrator 让用户能够定义更贴合特定用例需求的策略。在 ReAct 中，FM 与工具的调用遵循顺序式的逐步流程，每个动作都依赖上一个动作的结果。这种结构化、线性的做法带来了透明度，让每个动作与决策背后的推理更容易追溯，同时通过可预测的工作流促进一致性。尽管 ReAct 的设计通过让 agent 在每一步重新评估动作而具备渐进式适应能力，但当需要快速并行执行动作，或工作流要求跨多个步骤即时响应时，其顺序式结构可能带来延迟。这使得 ReAct 不太适合速度与快速顺序处理至关重要的场景，例如复杂的大批量工作流。

自定义 orchestrator 提供了另一种更灵活的做法，用户可以用它定义与自身具体需求更紧密契合的编排策略。借助实时调整以及对 FM 与工具交互的精确控制，用户可以创建在性能、准确性与韧性之间取得最佳平衡的工作流。自定义 orchestrator 创建完成后，可在配置新 agent 时只更新一处引用，就能在多个 agent 之间复用。

自定义 orchestrator 的关键优势包括：

- **完全掌控编排策略** – 针对准确性、速度、韧性等各项指标定制 agent 工作流以获得最佳性能。使用 Amazon Bedrock Agents 与 action group、知识库和 guardrail 的内置集成来简化交互。
- **实时调整** – 基于当前上下文、工具输出或不断变化的用户需求动态调整 agent 动作，使 agent 高效、有效地适应新信息。
- **可复用性与一致性** – 编排策略创建后，可在所有相关 agent 中实施，节省时间并促进一致性。

本文将对比使用默认 ReAct prompt 的 Amazon Bedrock agent 调用，与使用实现了 ReWoo 策略的自定义编排的 Amazon Bedrock agent 调用。首先，我们会考察支撑其适应能力的底层契约与状态管理原则。

## 自定义 orchestrator 的工作流管理

自定义 orchestrator 通过 Amazon Bedrock Agents 与 AWS Lambda 之间基于契约的交互，实现动态决策与可适应的工作流管理。Lambda 函数充当编排引擎，处理上下文输入——例如状态、对话历史、会话参数和用户请求——以生成指令并为后续动作定义状态。收到用户输入后，Amazon Bedrock Agents 会使用自定义 orchestrator 逻辑和 [Amazon Bedrock Converse API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html) 来管理底层 FM 与各类工具（例如 action group、知识库和 guardrail）之间的交互。

下图展示了用户、Amazon Bedrock Agents 与管理工作流的自定义 orchestrator 之间的交互流程：

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/26/custom_orchestrator-1024x450.png)

自定义 orchestrator 工作流包括以下步骤：

- **用户输入** – 流程从用户提交请求或查询开始。该输入被发送到 Amazon Bedrock Agents，从而启动工作流。
- **启动自定义 orchestrator** – Amazon Bedrock Agents 把用户输入传给自定义 orchestrator，后者在 `START` 状态下启动编排流程。orchestrator 引导工作流经过各个中间步骤来处理该输入。
- **工具交互** – Amazon Bedrock Agents 与各类工具交互来处理该请求：  **知识库** – 根据用户输入提供相关上下文或信息。  **Action group** – 调用预定义的 action group，其中包括：  用于自定义逻辑的 Lambda 函数  用于串联步骤的 return of control（RoC）函数  用于执行代码的 code interpreter（CI）函数  **Guardrail** – 确保响应符合预定义标准或安全要求。  **Converse API** – 管理对话流程，并处理 Amazon Bedrock Agents 与 FM 之间的自然语言响应。  **会话属性** – 管理会话专属数据，例如长期记忆、会话属性和知识库配置，实现个性化并在多次交互之间保持上下文。
- **自定义 orchestrator 工作流** – 在 Amazon Bedrock Agents 与各类工具交互的过程中，自定义 orchestrator 通过状态跟踪进度，并按需调整工作流。工作流完成后，orchestrator 使用 `FINISH` 动作事件发出完成信号。
- **最终输出** – Amazon Bedrock Agents 生成最终输出并交付给用户，完成本次交互。

该工作流展现了 Amazon Bedrock Agents 在自定义 orchestrator 引导下如何协调各个步骤、管理信息流以满足用户请求。通过状态转换，orchestrator 确保每个动作按结构化顺序执行，从而实现对工作流的动态、灵活控制。接下来我们会探讨状态转换与基于契约的交互如何构成可定制的工作流管理。

### 状态与事件管理

状态管理是引导交互推进、确定工作流下一步的核心。状态代表特定的阶段或条件，使编排引擎能够跟踪并管理动作。这些状态确保工作流有序推进，每个动作都依赖于当前状态。状态在请求 schema 中从 Amazon Bedrock Agents 传给由 Lambda 函数处理的客户 orchestrator。相比之下，事件是驱动状态转换或触发进一步动作的动作。事件在响应 schema 中从 AWS Lambda 传给 Amazon Bedrock Agents。

agent 与自定义 orchestrator 之间的每次交互都以“START”状态开始，以“FINISH”事件结束。在编排过程中，自定义 orchestrator Lambda 可以接收“START”“MODEL_INVOKED”“TOOL_INVOKED”“APPLY_GUARDRAILS_INVOKED”或自定义状态作为输入，并输出“FINISHED”“INVOKE_MODEL”“INVOKE_TOOL”“APPLY_GUARDRAILS”或自定义事件。状态与事件之间的流转如下图所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/26/custom_orchestrator_states-1024x490.png)

每次状态转换都响应特定事件而发生，使工作流能够基于输入与上下文动态适应。例如，当收到 FINISH 事件响应时，orchestrator 就在表示工作流已完成。随后自定义 orchestrator Lambda 函数把输出流式返回给 Amazon Bedrock Agents，后者再把它流式传给用户。这一机制提供了顺畅、响应迅速的交互，使任务能够被有效编排。请求与响应之间基于契约的交互通过 JSON 事件处理，详见[此处](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-custom-orchestration.html)。

借助这些基于契约的交互，Amazon Bedrock Agents 与自定义 orchestrator Lambda 函数能够有效协作，处理上下文输入、管理状态转换，并产出准确、贴合的响应。这种灵活的架构对于处理需要实时调整并精确控制 agent 行为的复杂工作流至关重要。

## 自定义 orchestrator 的工作流模式：ReAct 与 ReWoo

为展示自定义 orchestrator 的能力与灵活性，下一节将考察两种编排策略——默认 Bedrock Agent 的 ReAct 与 ReWoo——并探讨它们各自如何应对 agent 工作流中的权衡。为进一步探索自定义 orchestrator 的灵活性与潜力，我们来看一个餐厅的示例用例。在该用例中，我们有一个 Amazon Bedrock Agent，它带有一个可连接三个 API 的 action group：创建预订、更新已有预订和删除预订。该 agent 还连接了一个知识库，其中为该餐厅供应的菜品建立了不同菜单的索引。下图展示了该 agent 架构。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/26/restaurant_assistant_agent-1024x436.png)

### 默认 orchestrator：ReAct

默认的 Amazon Bedrock Agents ReAct 做法是一个迭代式决策过程：模型分析每一步，并基于在每个阶段收集到的信息决定下一个动作，如下图所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/26/react_flow-1024x403.png)

这一方法提供了透明度，并允许对动作做清晰的逐步拆解，因而非常适合能从增量调整中获益的工作流。尽管在实时重新评估具有优势的动态环境中行之有效，但当需要复杂计划时，ReAct 的顺序式结构会引入延迟。例如，回到餐厅助手这个例子，当询问“你们晚餐供应什么？”或“你能今晚 7 点为两个人订个位吗？”这类简单查询时，agent 的计划只包含一个动作，延迟不会明显更高。然而，当面对更复杂的查询，例如“你们晚餐供应什么？你能今晚 9 点为四个人订个位吗？”时，agent 的计划将包含多个步骤。每一步都会观察结果，并按下图所示调整计划。请注意，计划是隐含的，由思考内容给出下一步。每一步之后都会进行一次新的模型调用，以确定下一步或给出最终答案。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/26/react_flow-1.gif)

### ReWoo

**ReWoo** 技术通过预先一次性生成完整的任务计划，并在执行过程中不检查中间输出，从而优化性能，如下图所示流程。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/26/rewoo_flow-1024x138.png)

这种做法把模型调用降到最少，对于需要与多个工具交互的查询，可显著缩短响应时间。对于速度优先于迭代调整的任务——或出于安全原因需要隐藏中间推理步骤的场景——ReWoo 相比默认 ReAct 策略具有明显优势。

agent 延迟的一个关键来源是完成任务所需的 FM 调用次数。默认 ReAct 策略对 *N* 个步骤至少需要 *N+1* 次调用，而 ReWoo 无论工具有多少，都能把模型调用减少到最多两次，从而减少模型调用次数，进而缩短响应时间。例如，一个用 ReAct 需要三次模型调用、耗时 9 秒的任务，换成 ReWoo 后差别不大，因为该任务仍需两次模型调用。然而随着复杂度上升，延迟差异会变大。举例来说，一个用六次模型调用、耗时 18 秒的任务，用 ReWoo 可能只需两次模型调用、耗时 9 秒——这种差异会随工作流复杂度一起放大。

在分析“你们晚餐供应什么？你能今晚 9 点为四个人订个位吗？”这一查询时，使用 ReWoo 的 agent 会制定一个计划：访问知识库获取晚餐菜单信息，并调用 action group 创建新的晚餐预订，而不校验中间步骤，如下面的视频片段所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2024/11/26/rewoo_flow.gif)

在使用 Anthropic 的 Claude Sonnet 3.5 v2 的 agent 上运行该查询时，我们观察到这一复杂查询的延迟降低了 50–70%。你可以在我们的 GitHub 仓库 [amazon-bedrock-samples](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/agents-and-function-calling/bedrock-agents/features-examples/14-create-agent-with-custom-orchestration) 中找到该方案的实现。

需要注意的是，尽管 ReWoo 在速度上有优势，但它的 prompt 更复杂，而且你需要为输出构建一个解析器，这使它成为更难以实施的策略。这也是创建新的编排策略时应当权衡速度、准确性与方案复杂度的原因之一。

## 结语

本文探讨了 Amazon Bedrock Agents 如何简化生成式 AI 工作流的编排，尤其是随着自定义 orchestrator 功能的推出。你可以使用自定义 orchestrator 微调并优化 agentic 工作流，使其更紧密地契合具体的业务与运营需求。我们概述了该功能的关键优势，包括完全掌控编排、实时调整以及可复用性，随后拆解了它如何管理 Amazon Bedrock Agents 与 AWS Lambda 之间的状态转换与基于契约的交互。

随后我们深入考察了默认 ReAct 与自定义 ReWoo 两种编排策略，并讨论了灵活性与性能之间的权衡。通过应用于自定义 ReWoo 实现的详细工作流管理、状态事件与契约交互，我们突出了自定义 orchestrator 如何适应动态条件，从而让你能够构建更高效、更准确的 AI 应用。我们还给出了简化后的 ReAct 与 ReWoo 编排策略示例，以及灵活性与性能之间的权衡。

如需进一步了解自定义 orchestrator 技术并使用端到端示例上手，请参阅我们的 [GitHub 仓库](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/agents-and-function-calling/bedrock-agents/features-examples/14-create-agent-with-custom-orchestration)。
