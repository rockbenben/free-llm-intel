# Greenlight Financial 如何在 Amazon Bedrock AgentCore 上构建自主 SOC 解决方案

Greenlight Financial 每月解决多达 4,000 个安全和风险案例中的 90% 以上，无需人工干预。 Greenlight 的 Luna 使用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/)，这是用于大规模构建、连接和优化代理的基础设施。具体来说，Greenlight 使用 AgentCore 运行时（Amazon Bedrock AgentCore 的一项功能）来托管 Luna 的代理代码。它使用 AgentCore 内存（Amazon Bedrock AgentCore 的一项功能）来支持其分层多代理系统。这避免了在内部构建和运营这些功能的需要。 Luna 可在几秒钟内对暗网违规卡警报、身份异常和金融风险事件进行分类。

本文介绍 Greenlight Financial 如何在 Amazon Bedrock AgentCore 上构建自主安全运营中心 (SOC) 解决方案。我们介绍了其多层监管架构、30 多个专业代理、用于持续学习的情景记忆，以及从 SOC 用例扩展到财务风险分类的扩展。我们共享生产指标、基础设施决策以及在受监管行业中构建自主安全运营的模式。

## Greenlight 需要解决什么问题

Greenlight Financial 为家庭提供金融产品：借记卡、储蓄工具以及家庭中心和宠物追踪器等联网设备。该公司按照与主要银行相同的监管要求大规模处理敏感的金融数据。

Greenlight 的 SOC 每月从四个主要媒介收到 3,000-4,000 个安全和风险警报：

- **暗网违规卡** – 卡网络和内部威胁情报标记在暗网上发现的绿光客户卡。
- **身份和访问异常** – 身份提供商 (IdP) 和内部系统中的异常登录模式、权限升级和策略违规。
- **基础设施警报** – 来自 EDR（端点检测和响应）、SIEM（安全信息和事件管理）、资产库存和其他可观察性工具的信号。
- **金融风险事件** – 来自卡处理系统的可疑交易模式、合规触发器和欺诈指标。

每个警报都需要交叉引用多个数据源，然后分析师才能做出结论。单个暗网违规卡通知需要检查该卡是否处于活动状态，根据先前的通知进行重复数据删除，检查客户会话数据并检查开放的支持票证。此工作流程每个案例需要人工分析师 15-30 分钟。每月处理 4,000 起案件，这个数字就被打破了。

Greenlight 需要一个能够：

- 以机器速度自主分类和解决常规案例。
- 将具有完整背景的复杂案例上报给人类分析师。
- 从解决模式中学习，随着时间的推移提高准确性。
- 在金融服务合规护栏内运营。

## 架构：Amazon Bedrock AgentCore 上的分层多代理系统

Greenlight 在 Amazon Bedrock AgentCore 上将 Luna 构建为分层多代理系统。该架构遵循分层监管模式，反映了人类 SOC 团队的运作方式。 L1 处理体积，L2 处理复杂性。

### 一级主管：大容量分类

第 1 层 Supervisor 使用在 Amazon Virtual Private Cloud (Amazon VPC) 内的 Amazon Bedrock AgentCore 运行时上运行的 [通过 Amazon Bedrock 提供的高级语言模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)。运行时使用私有子网并通过 ZIP 文件和 Amazon Simple Storage Service ([Amazon S3](https://aws.amazon.com/s3/)) 进行直接代码部署。它通过协调 30 多个专业代理来处理传入案件的初步分类：

| **域名** | **代理做什么** |
| --- | --- |
|身份和访问|检查登录历史记录、MFA 状态、会话异常 |
|端点检测|提取端点警报、进程树、IOC 匹配 |
|可观察性|将基础设施指标与警报时间相关联 |
|资产盘点|绘制受影响资产、所有权、暴露面的地图 |
|数据分析|查询历史模式和基线偏差 |
|付款处理 |验证卡状态、交易历史记录、帐户状态 |
|客户体验 |审查事件发生期间的客户会话行为 |
|客户支持 |检查相关未决票证、事先投诉 |
|代码和存储库 |跟踪与警报相关的代码更改 |
|项目跟踪 |将事件链接到最近的部署或已知问题 |
|威胁情报|丰富 IOC 的外部威胁背景 |
|自动化（SOAR）|执行批准的补救行动手册|

第 1 层主管通过两个路径接收案例：Amazon API Gateway（公开 Luna Queue API 和模型上下文协议 (MCP) 端点）和 Tines SOAR（用于自动警报摄取）。它根据警报类型确定要调用哪些专门代理，综合他们的发现并做出裁决。常规病例的中位分诊时间为个位数秒。

### 二级主管：深入调查

超过第 1 层置信阈值的案例将升级至第 2 层主管，使用具有扩展推理功能的 [Amazon Bedrock 上的高级基础模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)。该代理可以处理 10% 需要多步骤推理的情况：

- 重新调查具有更深入跨源关联的升级案例。
- 通过具有扩展上下文窗口的“boto3”调用专门代理。
- 跨 3-5 个数据源进行连锁推理以建立因果关系。
- 生成详细的调查报告以及证据链以供人工审查。

第 2 层主管按计划运行，使用 Amazon EventBridge 速率触发器和 Amazon Simple Notification Service (Amazon SNS) 队列完成来批量处理升级案例，并按需处理紧急第 1 层升级案例。

### 不同角色的切入点

不同的团队以不同的方式参与 Luna，因此该应用程序公开了三个入口点。这些范围从全自动警报摄取到交互式按需调查。每个入口点都映射到一个角色以及他们的工作如何到达：

- **Tines SOAR** – 主卷驱动程序。自动警报摄取将案例直接输入第 1 层。
- **安全、风险和 ProdOps 工程师** – 针对临时调查请求的直接 API 访问。
- **Claude 桌面扩展** – 供待命工程师使用的基于聊天的界面。工程师打开扩展程序，描述他们想要调查的内容，然后 Luna 使用完整的工具访问权限进行深入研究。

## 记忆和学习：Luna 如何随着时间的推移变得更聪明

内存层构建在AgentCore内存之上。这一层是将 Luna 与无状态分类工具区分开来的。它支持模式识别、重复数据删除和持续的准确性改进。

### 情景记忆（30 天滚动窗口）

存储最近的事件和解决结果。当新警报到达时，Luna 会检查：“过去 30 天内我是否见过这种模式？结论是什么？这是我应该列入许可名单的已知行为吗？”

**具体示例：** Greenlight 基础设施角色会在每周二凌晨 3 点生成特定的访问模式以进行计划维护。由于没有记忆，卢娜每周都会标记这一点。凭借情景记忆，Luna 在第一个解决方案后了解到这种模式是预期的，并自动将其列入允许名单。

### 长期记忆

在 30 天窗口期后保留语义首选项和解析模板：

- “这种访问模式是预期的，因为这是该角色的目的。”
- Greenlight 的历史案例数据显示“来自该特定暗网来源的卡的误报率为 73% - 优先考虑重复数据删除。”
- 用于编码机构知识的重复案例类型的解决方案模板。

### 案例学习管道

专用管道将解决结果反馈回系统：

- **摄取** – AWS Lambda 函数从 Tines 事件中捕获每个案例解决方案。
- **学习 + 重复数据删除** – DynamoDB 存储解析模式并对类似案例进行重复数据删除。当 Luna 以相同的方式解决一个案件 3 次时，它会将其记录为已确认的模式。
- **摘要** – Lambda 函数将新学到的知识处理成主管在推理时使用的可操作上下文。
- **反馈循环** – 解决方案学习反馈到第 1 层，逐步提高首次通过的准确性。

该管道将​​ Lu​​na 的自主解决率从 83%（仅限第 1 层）提高到 90% 以上（第 1 层、第 2 层和学习）。

## 从 SOC 扩展到金融风险分类

Greenlight 在 SOC 部署后两个月内将 Luna 扩展到财务风险评估。架构上的变化很小：新的专业代理和风险域主管分层到现有的基础设施上。

### 暗网违规卡工作流程

当绿光客户卡出现在暗网上时，Luna 会自主执行此工作流程：

- **摄取** – 威胁情报提供商（万事达卡、内部源）报告受损的卡号。
- **验证** – Luna询问Galileo：这张卡属于Greenlight吗？目前是否活跃？最近的交易历史是什么？
- **重复数据删除** – DynamoDB 检查：这是重复通知吗？这张卡已经修复了吗？多个提供商经常报告相同的违规行为。
- **交叉参考** – 查询 Mixpanel 的客户会话异常情况、Zendesk 的相关票据以及内部欺诈评分。
- **评估并采取行动** – 确定风险级别。低风险：记录和监控。中等风险：标记以供审查。高风险：升级至具有完整证据链的人类分析师。

Greenlight 每天都会收到数百条违规卡通知。 Luna 在几秒钟内处理完每个任务。一名人类分析师做同样的工作，登录 Galileo，检查 DynamoDB，打开 Mixpanel，搜索 Zendesk，每张卡需要 15-30 分钟。

## 结果

下表根据对 SOC 最重要的指标跟踪 Greenlight 的安全操作。它比较了三个阶段：Luna 之前的手动分类、第 1 层自动化以及完整的第 1 层和第 2 层系统。

| **公制** | **在露娜之前** | **使用第 1 层** | **使用第 1 层和第 2 层** |
| --- | --- | --- | --- |
|自主解决率| 0%（全部手动）| 83% |超过90% |
|每月处理的案件数量 | 3,000-4,000 | 3,000-4,000 | 3,000-4,000 |
|中位分诊时间（常规）| 15-30 分钟 |秒|秒|
|人类分析师升级 | 100% 的案例 | 17% | <10% |
|成本规避|基线|重大 |相当于多名全职员工 |
|降低风险 |基线|更快的检测 |始终如一的 24/7 质量 |

**预计节省的分析师时间：**

根据 Greenlight 的案例数量和手动处理时间测量，以每个 15 至 30 分钟的速度处理 4,000 个案例，每月大约需要分析师 1,000-2,000 个小时。 Greenlight 报告称，Luna 可以自主解决 90% 以上的此类案例，每月估计可避免 900-1,800 小时的日常手动工作。分析师可以转而关注需要人类判断的案例。

风险的降低来自两个因素：速度（与分钟相比，秒数减少了暴露窗口）和一致性（Luna 在周六凌晨 3 点应用了与周二上午 10 点相同的分类逻辑，没有疲劳，也没有捷径）。

## 构建 Luna 的五个教训

构建 Luna 并将其从安全运营扩展到财务风险，为在受监管环境中构建多代理系统的团队提供了五个经验教训：

### 1. 从有界域开始，然后水平扩展

Greenlight 从安全分类开始，因为成功标准很明确：正确解决案例或升级。在该模式在 83% 的分辨率下被证明是可靠的之后，扩大财务风险需要添加新的专业代理和风险领域监管者，而不是重建架构。

### 2. 反映你的团队结构

第 1 层/第 2 层模式直接映射到 SOC 团队已经运作的方式。 L1 分析师通过策略来处理交易量。 L2 分析师凭借调查技能处理复杂案件。这使得与安全团队更快地建立信任。他们直观地理解了该模型，因为它符合他们自己的升级逻辑。

### 3. 记忆值的复合

正是情景记忆和长期记忆层将 Luna 的记忆力从 83% 提高到了 90% 以上。每个已解决的案例都会向 Luna 传达一些信息：新的允许模式、已确认的误报来源、解决模板。经过 6 个月的运行，Luna 积累了新的人类分析师需要几个月才能建立的机构知识。

### 4. 先分类，后行动

在受监管的环境中，Greenlight 设计 Luna 进行分类和推荐，而不是在没有明确政策批准的情况下采取自主补救措施。风险扩展也遵循同样的原则。 Luna 提供了支持其建议的证据。在这种人机交互模型中，人类分析师或批准的自动化策略授权并执行补救措施。这种分离满足了 Greenlight 的合规要求，并与风险团队建立了信任。

### 5.跨域共享专业代理

当 Greenlight 扩展到金融风险领域时，他们重用了现有的专业代理（Datadog、Zendesk、Mixpanel）并添加了特定领域的代理（Galileo、欺诈评分）。检查 Zendesk 票证是否存在安全情况的同一代理也会检查其是否存在风险情况。这减少了维护开销并有助于保持跨域的一致性。

## 基础设施堆栈

Luna 完全在托管 AWS 服务上运行。 Amazon Bedrock AgentCore 是编排运行时，堆栈的其余部分处理调度、消息传递、状态、机密和集成。下表列出了每个服务及其在基础架构中的角色：

| **服务** | **角色** |
| --- | --- |
| **Amazon Bedrock代理核心** |多代理编排运行时。 VPC 部署、私有子网、通过 ZIP 和 S3 直接代码 |
| **Amazon EventBridge** |为第 2 层深度挖掘分类周期安排基于速率的触发器 |
| **亚马逊SNS** |队列完成和层之间的通知路由
| **亚马逊 DynamoDB** |学习存储、案例重复数据删除、解析模式持久化 |
| **亚马逊S3** |代理包和 Terraform 状态管理 |
| **亚马逊 CloudWatch 日志** |审计跟踪和合规证据保留 30 天 |
| **AWS Secrets Manager** |外部 API 凭证 |
| **AWS Lambda** |摄取、解析后处理、启动和摘要功能 |
| **亚马逊 API 网关** |用于外部集成的 Luna Queue API 和 MCP 端点

## Greenlight 下一步要做什么

以安全和风险为基础，Greenlight 正在将 Luna 的多代理模式扩展到新的操作领域和工具：

- **全面风险领域覆盖** – 财务和商业风险案例的自主分类（正在进行中，大约一个月前启动）。
- **产品运营** – 探索 AWS DevOps Agent 以进行事件调查、根本原因分析和缓解指导。 Greenlight 还在评估 Luna 的现有特工如何在能力重叠的情况下支持行动调查。
- **自定义操作工作流程** – 探索 AWS DevOps Agent 自定义代理、技能和模型上下文协议集成，以实现可重复的操作工作流程并访问 Greenlight 的内部工具。
- **AWS DevOps Agent 和技能** – 结合 AWS DevOps Agent 的 UI 和技能框架来执行脚本工作流程（90 秒执行时间限制）。
- **架构完善的评论** – 探索模型上下文协议服务器，以根据 AWS 最佳实践进行自动化基础设施评估。

## 结论

根据 Greenlight 的生产测量，Luna 自主解决了公司 90% 以上的安全和风险案例，每月处理多达 4,000 个案例。需要额外判断的案例将升级给人工分析师。这种人机交互方法使 Greenlight 能够自动执行例行分类，同时保留对补救决策的控制。

其他受监管行业的团队可以应用相同的方法，从有限的用例开始，定义明确的升级标准，并随着系统的成熟添加专门的代理和内存。在初始模式被证明可靠后，团队可以将其扩展到相关的操作领域。
