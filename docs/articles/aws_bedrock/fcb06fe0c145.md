# Nippon India Mutual Fund 如何在 Amazon Bedrock 上使用增强 RAG 方法提升 AI 助手回答的准确率

*本文与 Nippon Life India Asset Management Ltd. 的 Abhinav Pandey 共同撰写。*

通过[生成式 AI](https://aws.amazon.com/generative-ai/)驱动的助手实现准确的信息检索，是企业中一个热门的用例。为减少幻觉并提升整体准确率，检索增强生成（Retrieval Augmented Generation，RAG）仍然是用于在回答用户查询时检索可靠且准确、并基于企业数据的回答的最常用方法。RAG 被用于 AI 助手、搜索、实时洞察等用例，并通过使用相关数据生成回答来提升整体内容质量，从而减少幻觉。

[Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 提供托管的 RAG 体验，可用于多种用例。Amazon Bedrock Knowledge Bases 是一项完全托管的服务，承担实现 RAG 模式的繁重工作——包括数据摄取、数据分块（chunking）、数据嵌入（embedding）和查询匹配。Amazon Bedrock 通过单一 API 提供来自 AI21 Labs、Anthropic、Cohere、Meta、Mistral AI、Stability AI 和 Amazon 等领先 AI 公司的高性能基础模型（FM）供你选择，并提供广泛的能力，让你能够以安全、隐私和负责任 AI 的方式构建生成式 AI 应用。使用 Amazon Bedrock Knowledge Bases，你可以快速、无缝地创建 RAG 解决方案。

然而，在拥有大量相关文档的大型企业场景中，最终回答仅基于数据库返回的 top 5 或 top 10 结果生成。由于 RAG 使用的是相似度匹配而非精确匹配，最相关的结果有可能不在数据库返回的 top 结果之中。在此类场景下，常规 RAG 模式可能不够准确。

本文中，我们考察 [Nippon Life India Asset Management Limited](https://mf.nipponindiaim.com/) 采用的一套方案：它通过重写用户查询并对回答进行聚合与重排序（rerank），相比常规（朴素）RAG 方法提升了回答的准确率。该方案使用[重排序](https://docs.aws.amazon.com/bedrock/latest/userguide/rerank.html)等增强 RAG 方法，以提升整体准确率。

## 大量文档场景下朴素 RAG 的局限与变通做法

在处理大量文档时，朴素 RAG 存在以下主要局限：

- **准确性** – 随着文档数量或体积增长，由于返回的文档数量有限，最终提取的 chunk 列表可能漏掉某些相关章节或文档
- **解析复杂结构** – 嵌套表格、图像和图表等实体无法被准确解析
- **相关数据利用有限** – 随着数据集增长，只有配置的 top 结果集合被用作上下文，影响准确性
- **回答复杂问题** – 复合问题（例如包含多个子问题的问题）会给 RAG 方案带来挑战
- **检索正确的上下文** – 法律文档或技术手册等文档在不同页面上存在语义相关的章节，影响整体准确性
- **避免幻觉** – 模型必须生成完整、正确且有依据的回答，不产生幻觉

为应对这些挑战，开发者通常会组合采用以下变通做法：

- **程序化解析** – 使用另一项服务（例如 [Amazon Textract](https://aws.amazon.com/textract/)）将表格内容提取到 markdown（`.MD`）文件中。
- **程序化拆分复合问题** – 以程序方式拆分问题，或以程序方式重构问题后获取回答，再将回答程序化聚合。
- **程序化分块** – 以程序方式为文档创建自定义 chunk，并在向量存储中管理它们。

本节回顾 RAG 的基础知识、Amazon Bedrock Knowledge Bases 以及用于应对上述挑战的增强 RAG 方法。下表详细列出 Nippon 为克服上一节讨论的挑战所采用的具体方案组件。

| **朴素 RAG 的挑战** | **Nippon 如何应对这些挑战** |
| --- | --- |
| 文档量大导致准确性偏低 | 使用 Amazon Bedrock Knowledge Bases 配合增强 RAG 方法，包括语义分块、多查询 RAG 和结果重排序 |
| 解析嵌套表格和文档内图表等复杂文档结构 | 使用 Amazon Textract 将文档解析为 markdown 文件 |
| 处理复合问题 | 使用查询重构和结果重排序来获取相关结果 |
| 从文档中检索当前上下文 | 在 Amazon Bedrock Knowledge Bases 中使用语义分块 |
| 生成有依据、无幻觉的回答 | 使用 Amazon Bedrock Knowledge Bases 的 RAG 评估 |

## RAG 概览

本方案中的 RAG 模式包含两个主要工作流：数据摄取工作流和文本生成阶段，如下图所示。在摄取阶段，方案对源文档内容进行分块，为生成的 chunk 创建 embedding，并将其存入向量数据库。在文本生成工作流中，用户查询被转换为向量 embedding，查询 embedding 与向量数据库中存储的 embedding 进行比较。数据库返回与用户查询接近的 top 结果。随后方案将用户查询连同检索到的 top 结果作为上下文发送给 FM，由 FM 给出最终回答。由于回答基于相关的企业上下文数据，该方案可以减少幻觉。

Amazon Bedrock Knowledge Bases 提供托管 RAG，承担数据摄取与文本生成工作流中核心活动的繁重工作。Nippon 使用 Amazon Bedrock Knowledge Bases 来实现 RAG 模式。下图展示了 Amazon Bedrock Knowledge Bases 提供的完全托管数据摄取工作流。你可以选择数据源，各种格式的数据可从该数据源增量更新。对于内容分块，你可以从以下策略中选择：固定（fixed）、语义（semantic）或层级（hierarchical）。你还可以选择 embedding 模型和向量存储。

## Nippon 采用的增强 RAG 方法

本节回顾 Nippon AI 助手解决方案中使用的关键增强 RAG 方法。

### 增强解析与分块

包含表格、图像和图表的复杂文档会给 RAG 带来挑战，因为默认的固定分块常常丢失上下文。针对这些场景，Nippon 采用以下方法：

- **使用 Amazon Textract 解析文档** – Nippon 使用擅长理解表格等复杂结构的 Amazon Textract，将文档中的细节提取到 markdown 文件（.MD）中。
- **使用带特定指令的 FM 解析文档** – 在这种方法中，Nippon 使用带有特定解析指令的 FM 来提取文档中的细节。Amazon Bedrock Knowledge Bases 提供 LLM 以及用于解析文档的指令。
- **使用第三方解析器解析文档** – 这种方法使用开源文档解析器等第三方解析器，然后对解析后的内容建立索引。

文档解析完成后，Amazon Bedrock Knowledge Bases 对数据进行分块。Amazon Bedrock Knowledge Bases 提供固定分块、语义分块和层级分块策略。你还可以针对特定文档使用 Lambda 函数添加自定义分块。

### 查询重构

如果用户查询较复杂，RAG 方案的整体准确性会下降，因为很难理解复杂问题的全部细微之处。在此类情况下，你可以将复杂问题拆分为多个子问题以提升准确性。Nippon 使用 LLM 将复合查询拆分为多个子查询。各个子查询的搜索结果会同时返回，然后被排序并合并。LLM 使用合并后的数据给出最终回答，如下图所示。

### 多查询 RAG

在多查询 RAG 方法中，你可以将问题重构为不同变体（Amazon Bedrock Knowledge Bases 提供自动查询重构），并并行执行这些查询。随后对这些查询的结果进行汇总并重排序，以得到最终回答，如下图所示。

多查询 RAG

Nippon 使用初始问题，并通过我们选定的 LLM（[Amazon Bedrock 上的 Anthropic Claude3 Sonnet](https://aws.amazon.com/bedrock/claude/)）将其拆分为 `n` 个子问题。通过这一实现，我们的回答质量有所提升，问题也能得到更深入的回答。由于这需要额外处理，响应时间会略长，但回答质量足以证明这是值得的。

### 结果重排序

在拥有大量文档的典型企业场景中，结果排序可能不正确，准确性可能下降。例如，向量数据库返回的默认结果基于向量相似度标准，其排名可能并不准确，也可能与用户的对话历史或查询上下文不相关。在此类场景下，你可以使用另一个 FM 仔细审视结果，并基于对上下文、相关性及其他标准的分析对其重新排序。结果重排序后，你可以确信 top 结果与用户上下文高度相关。每个文档或搜索结果都会依据语义相似度、上下文对齐程度或领域特定特征等标准获得评分，从而提高最终回答的整体准确性、减少幻觉并提升用户满意度。关键的 reranker 策略包括：

- **交叉编码器重排序（Cross-encoder）** – 使用专门训练用于评估查询-文档对相关性的模型
- **混合重排序（Hybrid）** – 结合多种信号，例如向量相似度、关键词匹配、时效性等
- **多阶段检索** – 先用更快的方法检索更大的集合，再对子集应用计算量更大的重排序

Amazon Bedrock 提供 reranker 模型，可计算 chunk 与给定查询的相关性、为 chunk 评分，并基于分数对结果重新排序。通过在 Amazon Bedrock 中使用 reranker 模型，你可以在搜索结果中获得高度相关的 chunk，从而提升整体回答准确性。Nippon 将查询重构与结果重排序相结合，使用 Amazon Bedrock 的 reranker 模型提升了 RAG 方案的整体准确性。

## RAG 评估指标

由于 RAG 方案包含多个可变部件，你需要依据关键成功指标对其进行评估，以确保从知识库获得相关且有上下文的资料。RAG 评估应验证能够生成完整、正确且有依据、无幻觉的回答。你还需要评估 RAG 方案的偏见、安全性和可信度。

Amazon Bedrock Knowledge Bases 内置支持 RAG 评估，包括正确性、完整性和忠实度（幻觉检测）等质量指标；有害性、拒答和刻板印象等负责任 AI 指标；以及与 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 的兼容性。Nippon 使用 RAG 评估，通过自定义数据集与多个评估作业进行对比。

Nippon 目前正在评估更多技术，包括 GraphRAG、元数据过滤和 agentic AI。我们在下面几节中简要总结了 Nippon 正在评估的能力。

### GraphRAG

对于需要与层级相关的数据建立关系的应用（例如知识管理、企业搜索、推荐系统等），Nippon 使用图数据库而非向量数据库。GraphRAG 应用利用丰富且相互关联的实体关系来识别依赖关系，并擅长查询多维关系，从而进一步增强 FM 的上下文。此外，借助图数据库，Nippon 可以高效地查询和遍历数据，其 schema 使其能够容纳动态内容。图数据库帮助 FM 更好地理解语义关系、发现隐藏模式、适应动态知识库，并提供更好的推理能力。

Amazon Bedrock Knowledge Bases 支持完全托管的 GraphRAG，它使用 [Amazon Neptune](https://aws.amazon.com/neptune/) 图数据库。

### 元数据过滤

在少数用例中，你可能需要根据特定的元数据值过滤知识库中的文档。例如，政府监管机构会频繁发布监管指南，文档名称往往相同，只是监管条款有细微差异。当你的查询针对某项特定法规时，你希望返回最新的文档。在此类情况下，你可以依据文档的修改日期对其排序。Amazon Bedrock Knowledge Bases 提供自定义元数据作为过滤器（例如修改日期），以提升搜索结果质量。

### Amazon Bedrock Agents

借助 [Amazon Bedrock Agents](https://aws.amazon.com/bedrock/agents/)，你可以使用工具和信息源编排多步业务流程。Nippon 目前正在为其 AI 助手用例评估 Amazon Bedrock Agents 中的最新 FM。

## 方案流程

下图展示了 Nippon AI 助手解决方案的端到端流程。

Nippon AI 助手解决方案的端到端流程

数据摄取工作流包含以下步骤：

- 来自数据源的文档被准备好以便摄取。
- Nippon 使用自定义解析从表格、图表和图像等复杂元素中提取相关细节。他们使用自定义分块创建 chunk。
- 他们使用 Amazon Bedrock 的 embedding 模型将内容 chunk 转换为向量 embedding，并存入向量数据库。

内容生成工作流如下：

- 用户的查询由 Amazon Bedrock embedding 模型转换为 embedding。
- Nippon 通过为查询创建多个变体并并行执行来使用多查询 RAG。获得的结果使用 reranker 模型重排序，以获得更高的准确性。
- prompt 以源文档中的引用进行增强，以生成引文
- 增强后的 prompt 被发送到 Amazon Bedrock。
- Amazon Bedrock 生成最终回答并发送给用户。

Nippon 计划未来采用 agentic AI 实现，以自动化数据检索、索引和摄取。

## 结果

实施 RAG 后，Nippon 观察到以下改进：

- 准确性提升超过 95%
- 幻觉减少 90–95%
- 他们能够添加源 chunk 和文件链接（通过文件元数据），这提升了用户对回答的信心
- 生成报告所需时间从 2 天缩短到约 10 分钟

![Abhinav Pandey ](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/07/09/image-9-100x137.png)**Abhinav Pandey** 是 Nippon Life India Asset Management Ltd 技术团队的一位资深数据科学家，拥有超过 18 年行业经验，主要深耕 BFSI 领域，热衷于利用生成式 AI 和 agentic AI 变革业务运营。他拥有将数据用于战略决策和业务增长的过硬履历，擅长运用前沿分析技术从复杂数据集中提取可行动的洞察。作为一位战略思考者和创新的问题解决者，他制定了提升运营效率与盈利能力的以数据驱动的策略，同时与跨职能团队高效协作，使数据举措与业务目标保持一致。在领导岗位上，他推动了数据科学举措、培育了创新、保持了结果导向的方法，并持续适应不断演进的技术以走在行业趋势之前。
