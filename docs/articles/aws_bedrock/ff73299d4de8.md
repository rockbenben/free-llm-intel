# Deepgram 如何借助 AWS Trainium 大规模优化语音 AI

随着语音成为 AI 的一等模态，Deepgram 的模型覆盖语音转文本、文本转语音和语音代理。他们现在每年为超过 200,000 名开发者和 1,400 家组织处理以千万亿（quadrillions）计的音频 token。客户既可以通过 Deepgram API 使用这些模型，也可以把它们部署在自己的环境中，包括在 Amazon SageMaker AI 上运行。

对 Deepgram 来说，服务效率决定了在给定的基础设施预算下系统能处理多少音频。高吞吐的批处理工作负载会对此预算造成很大压力，因此每个加速器小时用得越充分，Deepgram 就能在同一批机器上服务越多音频。这使得推理效率成为自然而然的优化目标，Deepgram 也因此转向 AWS AI 芯片来提升它。他们与 AWS 合作，把其 Nova-3 语音转文本模型迁移到 AWS Trainium2，用于联络中心分析、医疗转录等离线批处理工作负载。

这项合作始于 Deepgram 以标准 PyTorch 代码交付 Nova-3。在数月时间里，Deepgram 与 AWS Forward Deployed Engineering（FDE）团队用 PyTorch 重构的方式把 Nova-3 移植到 [AWS Trainium2](https://aws.amazon.com/ai/machine-learning/trainium/)，并针对新硬件做了调优。最终配置在单个 Amazon Elastic Compute Cloud（Amazon EC2）trn2.3xlarge 实例上运行八个模型副本。在 Deepgram 面向吞吐的离线批处理工作负载上，该配置每美元处理的音频量比 Deepgram 此前使用的计算方案多 11–70%。我们是按评估当时的实例价格测算的。这些收益帮助 Deepgram 高效扩展、持续发布更好的模型，并以更低的价格把它们交付给客户。这些好处也可以延伸到那些在自有虚拟私有云（VPC）中的 Amazon SageMaker AI 上自托管 Deepgram 模型的客户。在那里，Deepgram 与 AWS 正持续改善部署的便捷性、可靠性与可观测性。

本文会完整梳理在 Trainium 上的推理优化工作：把 Nova-3 移植到 AWS Neuron 软件栈、随后的 kernel 级调优、让 Deepgram 自有模型服务器得以调用 Trainium 的数据并行 Rust 运行时，以及我们在批量转录上测得的吞吐与成本结果。

## 用原生 PyTorch 把 Nova-3 优化到 Trainium2

从标准 PyTorch 代码出发，我们使用了 TorchNeuron——Neuron Compiler 的原生 PyTorch 集成，它同时支持 eager 执行和 `torch.compile`。我们先在 Trainium2 上以 eager 模式运行 Nova-3，检查哪些算子回退到了 CPU，然后用 `torch.compile` 编译。编译后的路径让所有模型算子都运行在 Trainium2 上，未检测到任何 CPU 回退。

我们用 `torch.compile` 把编码器和解码器分别编译为固定形状的静态图。整个过程我们在两个层面检查数值精度：与 CPU 对比的层级输出一致性，以及端到端的词错误率（WER）——后者必须与 Deepgram 的参考值和目标保持一致。

在这个可用的基线上，我们开始了优化工作：用公共 NKI Library（NKILib）中的融合 kernel 替换若干层。NKILib 是一组用 Neuron Kernel Interface（NKI）编写的预置参考 kernel。这些 kernel 覆盖了融合 QKV 投影、融合前馈网络（FFN）层、深度可分离一维卷积等算子。

我们面向吞吐、并由此面向成本效率做优化，目标是 Deepgram 的离线推理工作负载。吞吐以相对基线配置的增益形式报告，而不是每秒处理的绝对音频量；我们扫描了 1–128 的批大小，以找出吞吐最大的批大小。

### 使用 Neuron Explorer 与 NAD 做 kernel 级调优

启用 kernel 只是优化飞轮的第一步：启用某个 NKI kernel（自写的或来自 NKILib 的），对工作负载做性能剖析，然后根据剖析得到的洞见去调优现有 kernel，或者用新 kernel 替换它。这个循环不断重复，直到达到性能目标。每一步都有 Neuron 软件栈的不同部分在加速工作：NKILib 提供可直接替换的 kernel，Neuron Explorer 是剖析 Neuron 工作负载的首选工具，而 Neuron Agentic Development（NAD）工具包则通过其剖析与 kernel 编写技能，加快剖析分析和 kernel 调优。

在我们的场景里，NKILib 的 kernel 已经解决了大部分问题，而剖析结果指出了手写 kernel 能做得更好的地方。每一次，NAD 的剖析技能都帮我们从 Neuron Explorer 的剖析结果定位到根因，NAD 的 kernel 编写技能则帮助产出替换用的 kernel。

| **层** | **我们的发现与改动** | **收益** |
| --- | --- | --- |
| FFN | 参考 kernel 的分块调度对每个 token 分块都要从片外内存重新加载全部投影权重，因此随着 token 数增长，内存带宽成为吞吐瓶颈。我们手工调优的 kernel 对每个权重分块只加载一次，在多个 token 分块之间复用它，并把权重读取与片上计算流水化。 | 在批大小 96 时，延迟比参考 kernel 低 2.0 倍 |
| 深度可分离 conv1d | 实验性的 NKILib kernel 把该算子表述为隐式通用矩阵乘（GEMM），导致 Tensor Engine 利用率偏低。我们把它改写为运行在 Vector Engine 上的广播乘累加循环，达到了引擎的满利用率，足以抵消 Vector Engine 峰值吞吐较低的影响而有余。 | 在批大小 96 时，比参考 kernel 快 1.5 倍 |
| Conv2d | 模型的 conv2d 层遇到了编译瓶颈：批大小超过 32 之后，这些层使模型无法作为单个图编译。由于 NKILib 没有 conv2d kernel，我们用 NKI 从零写了一个。该 kernel 按前文所述的飞轮经历了多轮依据剖析结果的迭代，解锁了 32 以上的批大小。 | 在批大小 ≤32 时，卷积模块最高提速 50 倍 |

### Rust 实现的数据并行运行时

每块 Trainium2 设备有八个物理 NeuronCore，默认对外暴露为四个逻辑 NeuronCore（LNC2）。由于每个 Nova-3 模型实例都能轻松放进一个物理核，我们把每个逻辑核对应的物理核数降为一个（LNC1）。这一配置让我们能在每块 Trainium2 设备上承载八个模型副本（DP8）。输入被并发处理，同时最大化每台设备的吞吐。数据并行运行时由一个工作窃取队列驱动，每个副本对应一个线程。

Deepgram 的生产服务栈是用 Rust 编写的，因此把 Nova-3 移植到 Trainium2 不只是编译模型：它还必须在服务路径中不依赖 Python 或 PyTorch 也能运行。于是我们构建了一个轻量运行时：由 Rust 通过共享的工作窃取队列协调各模型副本，一个 C 层则通过 Neuron Runtime API（`libnrt`）直接加载并执行提前编译好的 Neuron Executable File Format（NEFF）文件。该运行时直接与 Deepgram 的服务架构集成，并在测试过的每个批大小上都精确复现了参考的 token 序列。

我们把它与多线程（MT）和多进程（MP）的 Python 数据并行运行时做了基准对比。相比 MP 基线，Rust 运行时彻底消除了 Python 解释器的开销；相比 MT 基线，它进一步缓解了全局解释器锁（GIL）造成的串行化，来自并发工作线程的调度调用不再在同一进程内相互争抢。这些收益之所以重要，是因为 Nova-3 对每个音频块都要执行一连串小的解码器调用，使得在低批大小下主机侧调度成为瓶颈。因此吞吐提升在那里最大，即使在吞吐最大的批大小上仍然可观：在该批大小下，Rust 运行时比多进程 Python 基线高 7.5% 的吞吐。

## 成本节约效果

我们以每美元处理的音频量来衡量性价比。在 Deepgram 面向吞吐的离线批处理工作负载上，单设备的 Trainium2 配置（trn2.3xlarge）每美元处理的音频量比 Deepgram 此前使用的计算方案多 11–70%。

## 结论

本文展示了 Deepgram 与 AWS FDE 如何使用 TorchNeuron 把 Nova-3 语音转文本 PyTorch 模型移植到 Trainium 硬件上——TorchNeuron 为 AWS Trainium 提供原生 PyTorch 框架集成。我们通过直接用 NKILib 的预置 kernel 替换若干层来提升性能。随后我们用 Neuron Explorer 评估性能，并使用 Neuron Agentic Development（NAD）的剖析技能来查询剖析数据、加快性能问题的排查。基于这些洞见，我们用 NAD 的 kernel 编写技能改写了 kernel 源码。最后，我们为 AWS Trainium 构建了一个轻量级 Rust 数据并行运行时，从 Rust 调用 Neuron Runtime API。我们的配置在面向吞吐的离线场景中展现了成本节约，验证了 AWS Trainium 是 Deepgram 推理工作负载可行且高效的选择。

要在你自己的模型上尝试这一方法，先从 [AWS Neuron 文档](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/)入手，其中介绍了编译器、运行时以及受支持的框架。[Neuron Kernel Interface（NKI）指南](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/general/nki/index.html)讲解了如何编写本文所述的 kernel，[NKI 示例仓库](https://github.com/aws-neuron/nki-samples)则收录了我们起步时使用的参考 kernel。[Neuron 开发者工具文档](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/tools/index.html)介绍了我们在此用到的剖析与代理式工具，包括 Neuron Explorer 和 Neuron Agentic Development。实例规格与价格请参见 [Amazon EC2 Trn2 实例](https://aws.amazon.com/ec2/instance-types/trn2/)。如需协助评估类似的移植工作，请联系 AWS Forward Deployed Engineering。
