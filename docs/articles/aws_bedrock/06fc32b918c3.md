# Axonius 如何在 Bedrock AgentCore 上构建安全的多租户 AI agent

独立软件供应商（Independent Software Vendors，ISVs）正在扩展产品并加入 AI agent。组织在引入 agentic 工作负载时通常要考虑安全性、可扩展性、上市时间和成本追踪。ISVs 还有一个额外维度：它们为其他组织提供服务，需要为每个客户管理 agentic 工作负载。因此，ISVs 不仅要在整体层面、还要在租户层面应对这些常见挑战。

[Axonius](https://www.axonius.com/) 是资产智能平台，帮助安全与 IT 团队排定风险优先级并协调修复。通过将 1,400 多个系统的数据对账整合为单一权威事实来源，Axonius 让安全团队及其所服务的团队能够高效协作，将安全、审计与合规的人工负担减少高达 50%。Axonius 在 AWS 上运行其软件即服务（SaaS）基础设施，管理着数百个相互隔离的客户环境。

Amazon Bedrock AgentCore 是一个平台，可使用任意框架或模型大规模构建、连接和优化 agent。在本文中，我们介绍 SaaS 提供商部署 AI agent 的可用策略，说明 Amazon Bedrock AgentCore 如何支持这些选项，审视 Axonius 的考量，并分享 Axonius 所选择的架构。我们还会介绍 Axonius 如何将 agentic 工作负载融入其现有方法论。本文面向在 AWS 上构建安全的多租户 AI agent 部署的平台工程师和架构师。

## AI agent 的多租户模式

独立软件供应商（ISVs）倾向于以 SaaS 模式提供服务。在选择架构时，ISVs 有[三种常见的架构模式：silo、bridge 和 pool。](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html)以下各节将详细阐述在借助 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 研究 agentic AI 时，每种模式意味着什么。

*silo 模式*指为租户提供专用资源的架构。放到 AgentCore runtime 中，它意味着每个租户使用一个专用 agent。采用*pool 模式*时，租户共享资源，一个 agent 服务多个租户。借助 AgentCore runtime，你可以通过为每个用户会话分配唯一的会话 ID 来[隔离每个用户会话](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html)。第三种模式是*bridge 模式*，其中部分组件采用 silo 模式，另一些采用 pool 模式。例如，我们可以将一个专用 agent 部署到 AgentCore runtime 中，同时使用共享的 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)——这是一项 AWS 托管的检索增强生成（Retrieval Augmented Generation，RAG）服务。

## 面临的挑战

Axonius 希望在产品中引入 AI agent。他们的第一个 AI agent 用于解读大型企业环境的状态并识别缺口与风险，借助 AI 分析来自数十个并发集成来源的数百万个数据点并理解其含义。这一举措让初级分析师也能够执行复杂分析，而无需让高级分析师耗费数小时的人工劳动。Axonius 选择保留其现有的租户管理方法。

Axonius 的 SaaS 部署模式是 silo。每个客户的工作负载都驻留在专用的 Amazon Virtual Private Cloud（Amazon VPC）中。该 VPC 包含 Application Load Balancer（ALB）、Network Load Balancer（NLB）、数据库和通用计算基础设施。

Axonius 希望在保持 silo 部署模式的同时引入 AI agent。Axonius 需要满足几项关键要求：

- **租户隔离 –** Axonius 处理敏感的客户数据。服务于某个客户的 agent 必须被严格限定在该客户的数据范围内。
- **身份 –** 现有服务已有一个认证与授权模块，位于分配给该租户的 Amazon Elastic Compute Cloud（Amazon EC2）上。Axonius 需要在不造成中断的情况下，将 agent 的身份流程与现有模块集成。
- **成本追踪 –** agentic 成本可能失控。其中大部分来自模型调用，因此按租户追踪模型成本至关重要。在考虑 agentic 产品的定价方案时，了解成本是必不可少的。
- **与服务集成** – 与某个租户关联的 agent 实例需要安全访问该租户工作负载的 API。
- **生命周期管理** – 将 agentic 工作负载纳入现有的 silo 持续交付（Continuous Delivery，CD）工作流。
- **可观测性 –** 采用 silo 模式时，Axonius 将拥有大量 agent。DevOps 团队需要高质量、易于集成的可观测性，能够追踪大规模 agent 集群、在出现问题时发出告警，并提供追踪能力以调试问题。

以下各节介绍 Axonius 评估过的选项及其最终选择。

## 可选方案

在考察租户部署模式时，Axonius 考虑了以下选项。

### 方案 1：Pool——共享 runtime，基于 JWT 的租户路由

AgentCore runtime 通过为每个会话分配专用 microVM 来强制实现结构性隔离。单个 runtime 服务多个租户，同时通过应用层的控制手段保持完全的租户隔离。

#### 工作原理

租户通过 OAuth 2.0 身份提供方（例如 Amazon Cognito）进行认证，JWT 中带有唯一的租户 claim（例如 custom:tenant_id）。runtime 的[内置 JWT authorizer](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/inbound-jwt-authorizer.html) 使用配置的 discovery URL 获取公钥并验证令牌的签发方。随后 agent 代码读取该 claim，将工具调用和数据访问路由到正确的租户环境。

图 1：采用单个共享 runtime、基于 JWT 进行租户路由的 pool 模式

#### 优势

- **运维简单**：只需部署、监控和更新一个 runtime。
- **快速接入**：新客户可立即接入，无需配置基础设施，缩短了产生价值的时间。

#### 劣势

- **依赖应用的隔离**：租户隔离完全依赖应用代码。
- **同质化部署**：针对每个租户的定制需要额外的条件逻辑。

### 方案 2：Bridge——共享 runtime 加网关强制的工具隔离

一种混合方法将单个共享 Runtime 的运维简便性，与通过 AgentCore Gateway 在工具层实施的基础设施级租户强制结合起来。租户共享一个 Runtime，但每次对外工具调用都会经过 Gateway，在工具代码执行前强制落实租户边界。

#### 工作原理

租户连接到同一个 AgentCore runtime，该 runtime 为每个会话使用专用 microVM 实现计算隔离，与方案 1 相同。区别在于，每次工具调用都会经过一个共享的 AgentCore Gateway，并接受两种强制机制的处理：

- **Amazon Bedrock AgentCore 中的策略** – 确定性访问控制。Cedar 规则依据调用者的身份属性（例如 Cognito 群组 claim）评估每次工具调用，并给出 allow/deny 决定。forbid 规则可阻止特定租户群组调用受限工具。
- **AWS Lambda Interceptor（REQUEST）** – 动态校验与上下文增强。在工具调用到达目标之前运行，提取 JWT、查找租户上下文，并通过 STS AssumeRole（“act-on-behalf” 模式）将令牌交换为短期、限定租户范围的 IAM 凭证。下游工具收到的是这些最小权限凭证，而非原始 JWT。

Gateway 会在 Cedar 策略*之前*评估 interceptor，使 interceptor 能够丰富请求上下文，供策略随后评估。

RESPONSE interceptor 还可以根据租户身份过滤工具发现。

这意味着有两套独立机制在基础设施层、而非 agent 代码中强制实现租户隔离。

图 2：采用共享 runtime、由网关强制工具隔离的 bridge 模式

#### 优势

- **分层的基础设施强制：**即使 agent 代码存在路由缺陷，Gateway 也会阻止跨租户工具调用。Cedar 策略（确定性）和 Lambda interceptor（动态）提供了纵深防御。
- **集中治理**：通过单一 Gateway 对所有工具调用审计并执行租户策略，每项决定都会记录到 Amazon CloudWatch。
- **共享效率**：runtime、knowledge bases 和可观测性基础设施集中管理，而不会共享安全风险。

#### 劣势

- **配置复杂：**需要配置 Gateway、REQUEST/RESPONSE interceptor Lambda、租户映射、Cedar 策略和 STS 角色信任关系。相比方案 1 或 3，这大大增加了活动部件。
- **VPC 连接**：后端工具通常位于 VPC 中，需要 VPC endpoint 才能实现 Gateway 的私有连接，这增加了网络复杂性和潜在故障点。

### 方案 3：Silo——每个租户专用 runtime

在 silo 模式中，每个租户都在专用的 AgentCore runtime 上运行。访问控制完全通过 AWS Identity and Access Management（IAM）来强制。Runtime 及其 endpoint 上的基于资源的策略决定了哪些主体（无论是同账户角色还是跨账户身份）可以调用 agent。由于每个租户的工作负载运行在独立的基础设施上，租户之间不存在共享计算。

图 3：每个租户专用 runtime 的 silo 模式

#### 工作原理

每个租户都会获得专用的 AgentCore runtime，并在新客户接入时自动配置（例如使用 AWS CloudFormation 或 CDK）。在该 runtime 内，每个用户会话都运行在自己隔离的 microVM 中，因此即使是同一租户的不同用户之间也不共享任何进程状态。访问控制通过同时附加到 AgentCore runtime 及其 endpoint 的 IAM 基于资源的策略来强制。调用者必须拥有针对其租户特定 runtime 的明确权限。

#### 优势

- **最高隔离度**：每个租户使用专用计算资源，不共享进程状态。每个会话运行在自己的 microVM 中，租户无法访问彼此的基础设施。
- **简单的授权模型**：同时应用于 Runtime 及其 endpoint 的 IAM 基于资源的策略是唯一的强制点。无需应用层的路由逻辑。
- **独立配置**：每个 runtime 都可以运行不同的 agent 版本、模型或 endpoint 配置，而不会影响其他租户。

#### 劣势

- **规模限制**：默认配额是每个 AWS 账户 1,000 个 agent（可通过 Service Quotas 调整），对于庞大的客户群需要做好容量规划。
- **配置延迟**：每个新租户都需要创建专用的 Runtime 和 endpoint，与共享 runtime 模式相比会带来接入延迟。
- **运维开销**：监控、更新和管理数百个 runtime 会增加运维复杂度，需要强大的自动化能力（例如 CDK/CloudFormation 流水线、集中式可观测性）。

## 解决方案概览

Axonius 目前以 silo 模式运行，并选择在引入 agent 时沿用该方式。每个客户都有一个专用 agent。Axonius 使用 Amazon Bedrock 和 AgentCore 设计了一套多租户 agentic AI 架构，包含以下关键组件：

- **AgentCore runtime** – Axonius 使用 AgentCore runtime 为每个客户部署专用 agent，每个用户会话运行在隔离的 microVM 上。
- **Amazon Elastic Container Registry（Amazon ECR）** – 存储每个租户的 agent 容器镜像。
- **Amazon Bedrock** – 为底层基础模型（foundation models，FMs）提供支撑，并通过 IAM 角色标签进行成本分摊。
- **Amazon Bedrock Knowledge Bases（KB）** – Axonius 将 Amazon Bedrock Knowledge Bases（KB）与 Amazon S3 Vectors 结合使用，因为二者具备成本效益和扩展能力。Axonius 使用元数据过滤来隔离租户专属数据。
- **Amazon Bedrock Guardrails** – 提供内容过滤和主题拒绝策略。Guardrails 应用于每个模型响应，在与用户共享之前确保响应安全且不越界。
- **Amazon CloudWatch** – 监控整体工作负载，在成本控制中发挥重要作用。它追踪 token 消耗指标（输入/输出），发出告警并使用 IAM-deny 强制措施进行成本治理。如果客户超出 token 预算，自动化的 IAM 策略会阻止后续调用。
- **Amazon VPC Lattice** – 让 Axonius 能够管理经济高效的私有连接，连通 AgentCore runtime、客户 VPC 和 AWS 服务端点。

该架构使用 AWS CloudFormation 实现按客户自动配置和销毁，使 Axonius 能够在整个客户群中扩展 agent 部署。

## 为何选择 Amazon Bedrock AgentCore runtime？

在评估了多种方案（包括在现有 EC2 实例中以额外容器的方式运行 agent）之后，Axonius 选择了 Amazon Bedrock AgentCore runtime。其专为特定目的打造的能力直接满足了他们的多租户 SaaS 需求。

- **基于 microVM 的会话隔离** – AgentCore runtime 的会话隔离是决定性因素。每个用户会话都运行在一个*专用 microVM* 中，CPU、内存和文件系统资源彼此隔离。会话结束后，整个 microVM 会被终止，内存会被清理。这种确定性的安全模型对 Axonius 至关重要，因为每个客户的数据（包括敏感的网络安全资产清单）都必须完全隔离。
- **框架灵活性与 VPC 集成** – AgentCore runtime 不依赖特定框架的设计，让 Axonius 可以使用自己偏好的工具部署 agent，同时安全连接到现有 VPC 基础设施。每个 agent 通过 ENI 连接到客户的 VPC，从而直接与运行在隔离 EC2 实例中的 Axonius 应用 API 交互。
- **内建可观测性** – 内建的可观测性能力让 Axonius 无需构建定制监控基础设施即可获得所需的可见性。这些能力包括用于日志记录的 CloudWatch 集成、用于分布式追踪的 AWS X-Ray，以及捕获推理步骤和工具调用的 agent 专属追踪。

## 用户会话流程

每个客户都在自己的 VPC 内以专用工作负载运行自己的 Axonius 部署。每个客户还会获得一个专用的 AgentCore runtime：一个按客户划分的 agent，用 Claude 进行推理，从 Amazon Bedrock Knowledge Base 提取产品知识，并回连该客户的 Axonius API 来回答数据问题。客户有一个聊天框可以输入问题。以下流程追踪一个客户问题，例如 *“*我的资产数量与上周相比有什么重大变化吗？*”*

- **认证：**用户已经在其自有实例上登录 Axonius。当他们发送聊天消息时，Axonius 应用会对请求进行认证，并签发一个短期的模拟 JWT，其中包含用户身份、租户 ID、会话 ID 和 actor ID。授权下游一切操作的是这个令牌，而非静态凭证。
- **Runtime 调用**：Axonius 应用控制平面组装调用载荷，并在客户专用的 AgentCore runtime 上调用 InvokeAgentRuntime。载荷只携带租户配置：AgentCore Memory ID、Knowledge Base 和数据源 ID、AWS Region、当前 Axonius 版本，以及客户自有实例的回调地址。JWT 放在自定义的 AgentCore header 中，而非请求体里，因此认证材料不会落入 agent 的保存状态；会话 ID 和 actor ID 则将调用限定在某个用户的对话范围内。
- **专用、隔离的 runtime**：每个客户都有自己的 AgentCore runtime，该 runtime 附加到一个专用弹性网络接口（elastic network interface，ENI），该 ENI 位于客户自己的 VPC 和子网内。AgentCore 创建隔离会话，向客户的 Axonius 应用回验 JWT（签名、有效期、吊销和权限），并将推理限定在该单一租户内。无效令牌会在模型运行之前被拒绝。
- **用 Claude 进行 agent 推理**：团队现有的 LangGraph supervisor 检查问题，并将其路由到合适的专用 agent。该专用 agent 使用 Amazon Bedrock 分析问题，在每一步判断是可以直接回答、需要产品文档，还是需要来自客户环境的实时数据。有关各 Region 的模型可用性，请参阅 Amazon Bedrock 中的[各 AWS Region 支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。
- **知识检索**：当问题涉及 Axonius 的工作方式时，agent 会从 Bedrock Knowledge Base 检索相关段落。通过把最新的 Axonius 文档上传到 Amazon Simple Storage Service（Amazon S3）并同步，该 knowledge base 得以保持最新，从而使响应与客户正在运行的版本一致。
- **访问客户 Axonius API 的工具**：当问题需要实时数据时，例如“给我一份过去 24 小时内发现的所有资产的高层摘要”，agent 会调用其查询工具，该工具：  使用 Knowledge Base 和大语言模型（large language model，LLM）将自然语言问题转换为 Axonius Query Language（AQL）表达式。通过 runtime 的专用 ENI 访问客户的 Axonius 应用实例，因此流量停留在客户 VPC 内部，不会离开 AWS 网络。它携带同一个 JWT 编译查询并获取匹配的资产，因此 agent 只能看到用户本就已被允许查看的数据。将结果返回给 agent，由 agent 基于结果推理并组织响应。
- **Guardrails 与响应**：Amazon Bedrock Guardrails 在服务端应用于每个模型响应，在响应离开 Amazon Bedrock 之前确保其安全且不越界。agent 的答案通过 runtime 以 token 为单位流式返回到聊天 UI，这次交互会持久化到 AgentCore Memory 中，使后续问题保留上下文。

## 租户隔离与私有网络

整个设计建立在严格的按客户隔离与私有连接之上：

- **每个客户专用 runtime**：每个客户都拥有自己的 AgentCore runtime，其 ENI 位于该客户的 VPC 和子网内，因此一个客户的 agent 没有任何网络路径可以通往另一个客户的数据。
- **在网络内访问客户数据**：由于 ENI 位于客户的 VPC 内，runtime 通过私有寻址访问内部的 Axonius EC2 实例。该流量不经过公共互联网，也不会离开 AWS 网络。
- **通过 Amazon VPC Lattice 共享 AWS 服务**：一个专用的 Axonius 服务 VPC 通过一组私有 endpoint 发布 runtime 所依赖的 AWS 服务（Amazon ECR、Amazon S3、Amazon Bedrock 等），并通过 VPC Lattice 与每个客户 VPC 共享。这让 AgentCore runtime 能够私有地从 Amazon ECR 拉取 agent 容器镜像、访问 Amazon Bedrock 和 Knowledge Base，同时限制访问，使只有客户 VPC 及其 runtime 才能触达这些服务。
- **网络成本效益**：Amazon VPC Lattice 让 Axonius 可以为每项 AWS 服务定义一个私有 endpoint，降低成本和管理开销。如果使用 AWS PrivateLink，Axonius 将需要为每个 VPC、每项服务各定义一个私有 endpoint。

这些措施共同维持了一条清晰的信任边界：推理、知识检索和 guardrails 运行在 Amazon Bedrock 上；权威数据和身份留在每个客户自己的 VPC 中；二者之间的每一跳都走 AWS 私有网络。agent 不持有长期凭证，它在一次请求的生命周期内借用用户的 JWT，而每个会话、memory、工具调用和网络路径都限定在单一租户范围内。

## Token 治理与成本管理

Axonius 实施方案中一个值得注意的方面是其 token 治理方法：

- **CloudWatch 指标**追踪每个 agent 的输入和输出 token 总量。此外，Axonius 使用 opentelemetry-instrument 获取实时 token 用量。
- **IAM 角色标签**（使用 Amazon Bedrock 按 IAM 用户/角色划分成本的功能）支持按租户归属成本。
- **自动化 IAM-deny 策略**可通过 CloudWatch 告警触发，以阻止失控的 agent 用量。
- 按模型划分的 **Application Inference Profiles** 支持通过 Amazon EventBridge 进行细粒度的标记、告警和成本控制。

这种方法提供的成本分摊可见性每天更新一到两次，并通过 CloudWatch 提供实时告警，以便立即执行管控。
