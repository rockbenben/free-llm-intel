# bunq 如何用 Amazon Bedrock 处理 97% 的支持工作

*本文与 [*bunq*](https://www.bunq.com/en-nl/) 的机器学习工程负责人 Benjamin Kleppe 共同撰写。*

agentic AI 的集成正在改变银行业，标志着从传统客户服务系统的重大转变。agentic AI 在复杂的金融环境中展现出自主决策能力，使银行能够提供全天候多语言支持、处理交易，并大规模提供个性化财务洞察。

[bunq ](https://www.bunq.com/en-nl/)是欧洲第二大 neobank，旨在为过国际化生活的个人和企业让生活更轻松。bunq 由连续创业者 Ali Niknam 于 2012 年创立，始终把用户放在一切的核心。公司帮助欧洲 2000 万用户在单一、易用且基于用户反馈构建的应用中自信地消费、储蓄、做预算和投资

本文展示 bunq 如何用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 升级其自研生成式 AI 助手 [Finn](https://www.bunq.com/en-us/business-account/banking-features/personal-assistant)，让用户支持与银行运营在多种语言和时区下变得无缝。

## 业务挑战

银行面临的一大挑战是如何在多个渠道、语言和时区提供一致、高质量的客户支持。传统支持系统难以应对金融产品的复杂性、监管要求，以及用户对即时、准确响应日益增长的期待。客户期望即时获得交易争议、账户管理和财务建议等关键银行功能，而银行需要维持严格的安全协议和合规标准。作为以用户为中心的银行，bunq 的用户期望其银行需求（例如申请退款或寻求功能使用指导）能获得全天候支持。传统支持模式无法跟上这种需求，造成令人沮丧的瓶颈并给内部资源带来压力。除直接支持外，bunq 团队还需要高效分析收到的功能请求和缺陷报告，以持续改进系统。显然，bunq 需要一个更智能的解决方案，能够全天候提供即时、准确的协助，并帮助团队把宝贵的用户反馈转化为行动。

## 解决方案概览

bunq 的生成式 AI 助手 Finn 于 2023 年推出，完全在内部构建，是 bunq 自有 AI 技术栈的一部分。Finn 使用领先的 AI 基础模型（FM）和工具，包括通过 Amazon Bedrock 使用 Anthropic 的 Claude 模型。与通用聊天机器人不同，Finn 能处理自然语言并提供实时的智能回答。Finn 可以把 bunq 应用翻译成 38 种语言，并实时翻译与支持团队的语音到语音通话。它还能汇总复杂的银行信息、提供财务洞察和预算建议，甚至能识别图像，自动处理发票处理等繁琐任务。bunq 的做法使用 AWS 服务构建可扩展的 AI agent 基础设施，既能应对现代银行业的需求，又能保持安全与合规。该解决方案使用以下 AWS 服务：

- [Amazon Bedrock](https://aws.amazon.com/bedrock/) – 一项全托管服务，通过统一 API 提供来自领先 AI 公司和 Amazon 的高性能 FM。bunq 使用 Amazon Bedrock 访问 Anthropic 的 Claude 模型，获得增强的安全特性、可扩展性和合规性——这些是银行应用的关键要求。
- [Amazon Elastic Container Service (Amazon ECS)](https://aws.amazon.com/ecs/) – 一项全托管的容器编排服务，让部署、管理和扩展容器化应用变得简单。Amazon ECS 免去了安装和运维容器编排软件或管理虚拟机集群的需要，帮助 bunq 专注于构建 Finn 的多 agent 架构。
- [Amazon DynamoDB](https://docs.aws.amazon.com/dynamodb/) – 一项全托管、无服务器的 NoSQL 数据库服务，专为大规模运行高性能应用而设计。DynamoDB 提供个位数毫秒级性能，并存储 agent 记忆、对话历史和会话数据，使 Finn 能在客户交互之间保持上下文。
- [Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/) – [Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 的按需自动扩缩容配置。OpenSearch Serverless 根据应用需求自动扩展计算资源，并为 Finn 的检索增强生成（RAG）实现提供向量搜索能力，从而在 bunq 的知识库中实现语义搜索。

## 使用 Amazon Bedrock 构建多 agent 实现

用户可以通过 bunq 的应用和 Web 界面与 Finn 交互，用自然语言提出请求，例如账户信息、交易历史、财务建议和支持问题。系统实时处理请求，只访问与请求相关的数据，同时维持严格的安全与隐私控制。用户支持场景所需的能力超出一个 AI agent 能提供的范围。多 agent 架构让专用 agent 处理不同任务——一个 agent 可能擅长理解用户，另一个专注于提取相关文档，第三个处理交易分析或账户操作。对 Finn 来说，这意味着用户询问一笔失败付款时可以触发协同响应：一个 agent 解读问题，另一个查看交易日志，第三个基于相似案例提出解决方案。它们无缝协作，在几秒钟内给出完整答案，而不是把用户在不同部门之间转来转去。面向银行服务的初始多 agent 支持系统遵循一种看似直接的模式：一个中央路由 agent 把用户查询导向专用的子 agent。每个 agent 处理特定领域——技术支持、一般咨询、交易状态、账户管理等等。然而，随着系统增长，需求的规模和复杂度也随之增长。当 bunq 为处理这个新生态而增加更多专用 agent 时，三个问题变得明显：

- **路由复杂度** – 面对多个专用 agent，路由器需要日益复杂的逻辑来确定正确的目的地。
- **能力重叠** – 多个 agent 需要访问相同的数据源和能力，迫使路由器不仅要预测主要意图，还要预测下游可能需要哪些次级 agent——这在规模化时是不可能完成的任务。
- **可扩展性瓶颈** – 每新增一个 agent 或能力都意味着要更新路由器逻辑。添加新的专用 agent 需要对所有路由场景进行全面测试。路由器成了单点故障和潜在的开发瓶颈。

### 重新思考架构

bunq 围绕一个编排 agent 重新设计了系统，它的工作方式与旧路由器有根本不同。编排器不再试图路由到所有可能的 agent，而是执行以下操作：

- 只把查询路由到三到五个主 agent
- 让这些主 agent 在需要时把其他 agent 作为工具调用
- 把决策权交给 agent 自身

借助这种 agent-as-tool 模式，主 agent 能检测自己何时需要专业帮助。工具 agent 由主 agent 动态调用。agent 可以通过定义良好的接口调用其他 agent——它们成为彼此工具包中的工具。

### 编排与 agent 架构

系统的核心是运行在 [Amazon Elastic Container Service](https://aws.amazon.com/ecs)（Amazon ECS）上的编排 agent。该编排器实现 agent-as-tool 模式，把用户查询路由到有限的一组主 agent，而不是试图预测所有可能的场景。编排器维护三到五个主 agent（主 agent 1 至 5），每个都作为容器化服务部署在 Amazon ECS 上。这种设计提供水平可扩展性——随着需求增长，可以自动启动额外的 agent 实例。每个主 agent 都能按需调用专用 agent。这些专用 agent（专用 agent 1、2、3 等）充当主 agent 可调用的工具，用于特定能力，例如分析交易数据、检索文档或处理复杂查询。这种分层结构避免了路由复杂度的瓶颈，同时保持灵活性。

### 基础设施细节

该架构建立在健壮的 AWS 服务基础之上，支撑 Finn 的性能。用户通过 bunq 的应用访问服务，流量由 [AWS WAF](https://aws.amazon.com/waf/) 和 [Amazon CloudFront](https://aws.amazon.com/cloudfront/) 保护，身份验证经由 bunq 自有的身份系统。Amazon Bedrock 提供对 Anthropic 的 Claude 模型的访问，用于自然语言理解，并由 [Amazon SageMaker](https://aws.amazon.com/sagemaker/) 托管的微调模型补充，以应对特定银行场景。agent 记忆和对话历史存储在 DynamoDB 中，OpenSearch Service 作为 RAG 能力的向量存储，从而在 bunq 的知识库中实现语义搜索。[Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）负责文档存储，[Amazon MemoryDB](https://aws.amazon.com/memorydb/) 管理用于实时交互的用户会话。通过 [AWS CloudTrail](https://aws.amazon.com/cloudtrail)、[Amazon GuardDuty](https://aws.amazon.com/guardduty/) 和 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch) 实现的全面可观测性，帮助团队监控性能、检测威胁并保持合规——所有这些都在安全的虚拟私有云（VPC）内完成。

## 真实影响

从 bunq 最初的基于路由器的架构转向基于 Amazon Bedrock 的编排器模式，在用户支持运营中带来了可衡量的改进。多 agent 部署实现了显著的运营效率提升：

- Finn 现在处理 bunq 97% 的用户支持活动，其中超过 82% 完全自动化。平均响应时间降至仅 47 秒，帮助 bunq 提供用户期望的实时解决方案。
- 快速的部署时间线凸显了 bunq 对创新的专注。团队从概念到生产仅用 3 个月，起始时间为 2025 年 1 月。bunq 汇集了一支 80 人的团队——从 AI 工程师到支持人员——共同测试、学习，并每天部署三次更新。
- 在实施编排器架构之前，升级主要是人工流程。新的多 agent 系统提高了自动化程度，改变了端到端支持指标。除此之外，Finn 通过把应用翻译成 38 种语言扩展了 bunq 的覆盖范围，让欧洲数百万用户更容易获得银行服务。
- 该解决方案使 bunq 成为欧洲首家 AI 驱动的银行，提供传统支持系统无法交付的能力：实时语音到语音翻译（全球银行业首创）、用于收据处理和文档验证的图像识别，以及智能财务洞察——同时保持用户所需的全天候可用性。

> “我们从概念到生产只用了 3 个月。在编排器架构之前，升级主要是人工的。现在 Finn 处理 97% 的支持，其中 70% 完全自动化，平均响应时间为 47 秒。” 
>         – Benjamin Kleppe，bunq 机器学习工程负责人。

## 结论

bunq 从人工支持升级到智能多 agent 系统的历程，展示了现代 AI 架构如何改变银行运营。通过从僵化的基于路由器的方法转向基于 Amazon Bedrock 的灵活编排器模式，bunq 在避免可扩展性瓶颈的同时保持了服务欧洲 2000 万用户所需的敏捷性。具备 agent-as-tool 能力的编排器模式被证明对 bunq 的成功至关重要。系统不再预先预测所有可能的用户场景，而是让主 agent 按需动态调用专用 agent。这一架构转变降低了复杂度、加快了开发周期，并帮助 bunq 在初始推广期间每天部署三次更新。结果：97% 的支持交互由 Finn 处理，70% 完全自动化，平均响应时间仅 47 秒。除效率提升外，该方案还把 bunq 的覆盖扩展到 38 种语言，并使公司成为欧洲首家 AI 驱动的银行。通过把内部资源从人工流程中解放出来，bunq 现在可以专注于它最擅长的事：构建一家让用户生活更轻松的银行。
