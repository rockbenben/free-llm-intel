# Amazon Bedrock 上的结构化输出：符合 schema 的 AI 响应

今天我们宣布在 [Amazon Bedrock](https://aws.amazon.com/bedrock)上推出结构化输出——这项能力通过受约束解码实现 schema 合规，从根本上改变了你从基础模型获取经过校验的 JSON 响应的方式。

这代表着 AI 应用开发方式的一次范式转变。你不必再校验 JSON 响应、并为校验失败编写兜底逻辑，可以直接拿数据去构建。有了结构化输出，你可以构建信任模型输出的零校验数据 pipeline、能放心调用外部函数的可靠 agentic 系统，以及不含重试逻辑的简化应用架构。

本文将探讨传统 JSON 生成面临的挑战，以及结构化输出如何解决它们。我们会介绍两个核心机制——JSON Schema 输出格式与严格 tool use——以及实现细节、最佳实践和实用的代码示例。无论你是在构建数据提取 pipeline、agentic 工作流，还是 AI 驱动的 API，都能学到如何用结构化输出打造可靠、可上生产环境的应用。配套的 [Jupyter notebook](https://github.com/aws-samples/amazon-bedrock-samples/tree/main/introduction-to-bedrock/structured-outputs) 为本文涉及的每项功能都提供了动手示例。

## **传统 JSON 生成的问题**

多年来，要从语言模型拿到结构化数据，意味着精心设计 prompt、然后祈祷结果可用，并搭建复杂的错误处理系统。即便 prompt 写得很仔细，开发者仍经常遇到：

- **解析失败**：JSON 语法无效，导致 `json.loads()` 调用报错
- **字段缺失**：响应中缺少必需的数据点
- **类型不匹配**：本应是整数的地方出现字符串，破坏下游处理
- **schema 违规**：响应在技术上能解析，但与你的数据模型不符

在生产系统中，这些失败会叠加放大。一次格式错误的响应就可能在你的 pipeline 中层层级联，从而需要重试，增加延迟与成本。对于模型调用工具的 agentic 工作流，无效参数可能让函数调用彻底失败。

设想一个要求 `passengers: int` 的预订系统。在没有 schema 约束的情况下，模型可能返回 `passengers: "two"` 或 `passengers: "2"`——两者都是语法合法的 JSON，但对你的函数签名而言语义上是错的。

## **结构化输出带来了什么变化**

Amazon Bedrock 上的结构化输出并不是渐进式改良——而是输出格式从概率性到确定性的根本转变。通过受约束解码，Amazon Bedrock 将模型响应限制为符合你指定的 JSON schema。这里有两个互补的机制可用：

| **特性** | **用途** | **使用场景** |
| --- | --- | --- |
| **JSON Schema 输出格式** | 控制模型的响应格式 | 数据提取、报告生成、API 响应 |
| **严格 tool use** | 校验工具参数 | Agentic 工作流、函数调用、多步骤自动化 |

这些特性可以单独使用，也可以组合使用，让你既能精确控制模型输出什么，也能控制它如何调用你的函数。

### **结构化输出带来什么：**

- **始终有效**：不再出现 `JSON.parse()` 错误或解析异常
- **类型安全**：字段类型被强制约束，必需字段始终存在
- **可靠**：不会因 schema 违规而需要重试
- **可用于生产**：可放心地以企业级规模部署

### **结构化输出如何工作**

结构化输出使用带已编译语法产物的受约束采样。发出请求时会经历以下过程：

- **schema 校验**：Amazon Bedrock 依据受支持的 JSON Schema Draft 2020-12 子集校验你的 JSON schema
- **语法编译**：对于新 schema，Amazon Bedrock 会编译一份语法（首次请求可能耗时更长）
- **缓存**：编译后的语法会缓存 24 小时，使后续请求更快
- **受约束生成**：模型生成的 token 会产生符合你 schema 的合法 JSON

### **性能考量：**

- **首次请求延迟**：初次编译可能会给新 schema 增加延迟
- **缓存后的性能**：使用相同 schema 的后续请求开销极小
- **缓存范围**：语法按账户缓存，自首次访问起 24 小时内有效

改动 JSON schema 结构或某个工具的 input schema 会使缓存失效，但只改动 `name` 或 `description` 字段则不会。

## **开始使用结构化输出**

下面的示例演示如何通过 Converse API 使用结构化输出：

```
import boto3
import json
# Initialize the Bedrock Runtime client
bedrock_runtime = boto3.client(
    service_name='bedrock-runtime',
    region_name='us-east-1'  # Choose your preferred region
)
# Define your JSON schema
extraction_schema = {
    "type": "object",
    "properties": {
        "name": {"type": "string", "description": "Customer name"},
        "email": {"type": "string", "description": "Customer email address"},
        "plan_interest": {"type": "string", "description": "Product plan of interest"},
        "demo_requested": {"type": "boolean", "description": "Whether a demo was requested"}
    },
    "required": ["name", "email", "plan_interest", "demo_requested"],
    "additionalProperties": False
}
# Make the request with structured outputs
response = bedrock_runtime.converse(
    modelId="us.anthropic.claude-opus-4-5-20251101-v1:0",
    messages=[
        {
            "role": "user",
            "content": [
                {
                    "text": "Extract the key information from this email: John Smith (john@example.com) is interested in our Enterprise plan and wants to schedule a demo for next Tuesday at 2pm."
                }
            ]
        }
    ],
    inferenceConfig={
        "maxTokens": 1024
    },
    outputConfig={
        "textFormat": {
            "type": "json_schema",
            "structure": {
                "jsonSchema": {
                    "schema": json.dumps(extraction_schema),
                    "name": "lead_extraction",
                    "description": "Extract lead information from customer emails"
                }
            }
        }
    }
)
# Parse the schema-compliant JSON response
result = json.loads(response["output"]["message"]["content"][0]["text"])
print(json.dumps(result, indent=2))
```

**输出：**

```
{
  "name": "John Smith",
  "email": "john@example.com",
  "plan_interest": "Enterprise",
  "demo_requested": true
}
```

响应符合你的 schema——无需再做额外校验。

## **要求与最佳实践**

要有效使用结构化输出，请遵循以下准则：

- **在所有对象上设置 **`additionalProperties: false`**。**这是结构化输出生效的必要条件。缺少它，你的 schema 将不被接受。

```
{
  "type": "object",
  "properties": {
    "name": {"type": "string"}
  },
  "required": ["name"],
  "additionalProperties": false
}
```

- **使用有描述性的字段名和 description。**模型依据属性名和 description 理解要提取哪些数据。`customer_email` 这样清晰的命名效果优于 `field1` 这类泛化命名。
- **对取值受限的字段使用 **`enum`**。**当字段只有有限的一组合法取值时，用 `enum` 约束可选项。这能提升准确率并产出合法取值。
- **先简单，再增加复杂度。**从最少必需字段开始，逐步增加复杂度。简单的 schema 编译更快，也更容易维护。
- **复用 schema 以利用缓存。**在应用设计中让多个请求复用同一 schema。24 小时的语法缓存能显著提升重复查询的性能。
- **检查每个响应中的 **`stopReason`**。**有两种情况会产生不符合 schema 的响应：拒答（模型出于安全原因拒绝）和 token 上限（在完成前达到 `max_tokens`）。请在代码中处理这两种情况。
- **部署前用真实数据测试。**用具有生产代表性的输入验证你的 schema。真实数据中的边界情况常常会暴露 schema 设计问题。

### **支持的 JSON Schema 特性：**

- 所有基本类型：`object`、`array`、`string`、`integer`、`number`、`boolean`、`null`
- `enum`（仅限字符串、数字、布尔值或 null）
- `const`、`anyOf`、`allOf`（有限制）
- `$ref`、`$def` 与 `definitions`（仅限内部引用）
- 字符串格式：`date-time`、`time`、`date`、`duration`、`email`、`hostname`、`uri`、`ipv4`、`ipv6`、`uuid`
- 数组 `minItems`（仅支持 0 和 1）

### **不支持：**

- 递归 schema
- 外部 `$ref` 引用
- 数值约束（`minimum`、`maximum`、`multipleOf`）
- 字符串约束（`minLength`、`maxLength`）
- `additionalProperties` 设为 `false` 之外的任何值

### **面向 agentic 工作流的严格 tool use**

在构建由模型调用工具的应用时，请在工具定义中设置 `strict: true`，把工具参数严格约束为与你的 input schema 完全一致：

```
import boto3
import json
bedrock_runtime = boto3.client('bedrock-runtime', region_name='us-east-1')
response = bedrock_runtime.converse(
    modelId="us.anthropic.claude-opus-4-5-20251101-v1:0",
    messages=[
        {
            "role": "user",
            "content": [{"text": "What's the weather like in San Francisco?"}]
        }
    ],
    inferenceConfig={"maxTokens": 1024},
    toolConfig={
        "tools": [
            {
                "toolSpec": {
                    "name": "get_weather",
                    "description": "Get the current weather for a specified location",
                    "strict": True,  # Enable strict mode
                    "inputSchema": {
                        "json": {
                            "type": "object",
                            "properties": {
                                "location": {
                                    "type": "string",
                                    "description": "The city and state, e.g., San Francisco, CA"
                                },
                                "unit": {
                                    "type": "string",
                                    "enum": ["celsius", "fahrenheit"],
                                    "description": "Temperature unit"
                                }
                            },
                            "required": ["location", "unit"],
                            "additionalProperties": False
                        }
                    }
                }
            }
        ]
    }
)
# Tool inputs conform to the schema
for content_block in response["output"]["message"]["content"]:
    if "toolUse" in content_block:
        tool_input = content_block["toolUse"]["input"]
        print(f"Tool: {content_block['toolUse']['name']}")
        print(f"Input: {json.dumps(tool_input, indent=2)}")
```

使用 `strict: true` 时，结构化输出会把结果约束为以下情形：

- `location` 字段始终是字符串
- `unit` 字段始终是 `celsius` 或 `fahrenheit`
- 输入中不会出现预期之外的字段

## **选择正确的做法**

我们的测试揭示了何时使用各项特性的清晰规律：

**在以下情况使用 JSON Schema 输出格式：**

- 你需要模型以特定结构返回响应
- 构建数据提取 pipeline
- 生成可直接供 API 使用的响应
- 创建结构化报告或摘要

**在以下情况使用严格 tool use：**

- 构建调用外部函数的 agentic 系统
- 实现带工具链的多步骤工作流
- 要求函数调用具有经过校验的参数类型
- 把 AI 连接到数据库、API 或外部服务

**在以下情况同时使用两者：**

- 构建既需要经过校验的工具调用、又需要结构化最终响应的复杂 agent
- 创建让中间工具结果流入结构化输出的系统
- 实现要求端到端 schema 合规的企业工作流

**API 对比：Converse 与 InvokeModel**

Converse API 与 InvokeModel API 都支持结构化输出，只是参数格式略有差异：

| **方面** | **Converse API** | **InvokeModel（Anthropic Claude）** | **InvokeModel（开放权重模型）** |
| --- | --- | --- | --- |
| Schema 位置 | `outputConfig.textFormat` | `output_config.format` | `response_format` |
| 工具严格标志 | `toolSpec.strict` | `tools[].strict` | `tools[].function.strict` |
| Schema 格式 | `jsonSchema.schema` 中的 JSON 字符串 | `schema` 中的 JSON 对象 | `json_schema.schema` 中的 JSON 对象 |
| 最适合 | 对话式工作流 | 单轮推理（Claude） | 单轮推理（开放权重模型） |

**注意**：InvokeModel API 会按模型类型使用不同的请求字段名。对于 Anthropic Claude 模型，JSON schema 输出使用 `output_config.format`；对于开放权重模型，则改用 `response_format`。

多轮对话请选择 Converse API；当你需要以特定提供商自己的请求格式直接访问模型时，请使用 InvokeModel API。
