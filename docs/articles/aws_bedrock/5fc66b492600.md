# Amazon Bedrock 上 AI 开发工具与生产力工具的成本归因与控制

Amazon Bedrock 内置的成本归因无需任何插桩，就能把每次推理调用追溯到发起它的 IAM 委托人。身份信息连同组织标签一起流入 AWS Cost and Usage Reports (CUR 2.0) 和 AWS Cost Explorer，同时数据始终留在 AWS 安全边界内。本文将介绍如何用这些能力回答每一位 FinOps 与 AI 平台负责人在 AI 工具采用规模扩大时都会问的三个问题：每位用户的真实成本是多少？哪些团队产生的支出最多，这些支出与他们交付的价值是否相称？明年的预算该如何随人员编制和采用规模调整？

无论发起调用的是哪款 AI 编码或生产力工具，这套做法都完全一样。Claude Code、Claude Desktop、OpenAI Codex、ChatGPT Work 和 OpenCode 都通过两个推理端点之一调用 Amazon Bedrock：`bedrock-runtime` 或 `bedrock-mantle`；而 Bedrock 的归因机制运行在端点层，位于任何工具专有逻辑之下。身份传播只需配置一次，之后所有经由 Bedrock 路由推理的工具都会自动获得按用户划分的成本可见性。

读完本文，你将完成：把 AWS IAM Identity Center 与外部身份提供商对接以实现按用户归因；让会话标签（团队、成本中心）流入 CUR 2.0；掌握用于持续成本可见性的 Amazon Athena 查询与仪表板方案；并清楚理解 Bedrock 原生的使用控制如何落实支出上限。

## Amazon Bedrock 归因的工作原理

Amazon Bedrock 会记录每个推理调用方的 IAM 身份，你的 API 调用无需任何改动。当用户通过 `bedrock-runtime` 或 `bedrock-mantle` 端点调用模型时，Bedrock 会捕获调用方完整的 IAM ARN（包括联合用户的会话名称），并把它发布到 CUR 2.0 的 `line_item_iam_principal` 列。在计费数据里，用量按每个导出间隔、每个委托人和每个用量类型聚合：按小时导出即每小时一段，按天导出即每天一段。CUR 不包含单次请求的成本。若要逐 prompt 查看明细，请使用模型调用日志或请求元数据标记。

你也可以选择给 IAM 委托人附加标签，或在联合认证时传入会话标签，以补充组织维度。这些标签在 CUR 2.0 中带 `iamPrincipal/` 前缀出现，在 Cost Explorer 中则作为可筛选维度。该机制支持四种访问模式：IAM 用户、按应用划分的角色、联合身份，以及代理到 Bedrock 的大型语言模型 (LLM) 网关。四者的对比参见 [Amazon Bedrock 细粒度成本归因简介](https://aws.amazon.com/blogs/machine-learning/introducing-granular-cost-attribution-for-amazon-bedrock/)。本文采用联合身份模式——对于每位开发人员或知识工作者都单独认证的 AI 编码与生产力工具来说，这是最自然的选择。

除 IAM 委托人跟踪之外，Amazon Bedrock 还提供其他归因机制，组织可按需叠加使用（对比见附录 A）。借助 Application Inference Profiles，你可以在 `bedrock-runtime` 端点上按工作负载标记支出；借助 Projects 和 Workspaces，你可以在 `bedrock-mantle` 端点上隔离并标记支出。对于需要比 CUR 2.0 每个导出间隔按用量类型聚合更细粒度的工作负载，按请求做元数据标记能在模型调用日志里给出逐 prompt、token 级的明细。这些机制可以组合使用，例如用 IAM 委托人归因拿到账单上每位用户的花费，同时用按请求的元数据标签在日志里保留逐 prompt 明细。如何选择取决于目标（参见 [跟踪 Amazon Bedrock 的使用量与成本](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-management.html)）。

## 归因问题

开发工具和生产力工具运行在每位用户的机器上，直接调用 Amazon Bedrock，或经由 LLM 网关调用。用户通过代入一个共享 IAM 角色完成认证，因此每次 API 调用在账单里都显示为 `assumed-role/<role>/<session-name>`。如果所有用户代入角色时都用同一个固定会话名称，或者调用走的是网关自己的角色，CUR 就会把支出汇总到单一委托人上。使用 IAM Identity Center 时，会话名称就是用户的登录名，于是每位用户都有各自的委托人；你还可以用会话标签（团队、成本中心、项目）进一步丰富它。这些字段会流入 CUR 2.0 的 `line_item_iam_principal` 列以及带 `iamPrincipal/` 前缀的成本分配标签，让按用户划分的支出能与具体金额一起被查询，而 Bedrock API 调用无需任何改动。

Claude Platform on AWS 和 Claude for Enterprise 的推理经由 Anthropic 管理的基础设施路由。对于 Claude Platform on AWS，用量可在 Anthropic 管理控制台里按 workspace 和 API key 查看，workspace 标签也会流入 AWS 账单。对于 Claude for Enterprise，按用户划分的用量可在 Anthropic 管理控制台以及 Usage and Cost API 中查看。支出上限由 Anthropic 原生执行。

## 先决条件

开始之前，请确认你已具备：

- 一个 [AWS 账户](https://aws.amazon.com/resources/create-account/)，其 IAM 权限可访问你打算使用的 Bedrock 模型。
- 在管理账户中[启用 AWS IAM Identity Center](https://docs.aws.amazon.com/singlesignon/latest/userguide/enable-identity-center.html)。
- 一个具备 SCIM 预置能力的外部身份提供商（Okta、Microsoft Entra ID 或 Ping Identity）。
- 在开发人员机器上配置好的 [AWS CLI v2](https://docs.aws.amazon.com/cli/latest/userguide/cli-chap-getting-started.html)。
- 已启用并包含 IAM 委托人数据、投递到 S3 存储桶的 [AWS Cost and Usage Report](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/iam-principal-cost-allocation.html) (CUR 2.0)。
- 从管理（付款人）账户激活的[成本分配标签](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-alloc-tags.html)。
- 一个用于查询 CUR 2.0 数据的 Athena 表（可参考 [GitHub 示例](https://github.com/aws-samples/aws-cudos-framework-deployment) 上手）。

## 步骤 1：用外部 IdP 配置 IAM Identity Center

把外部身份提供商配置为 AWS IAM Identity Center 的身份源。依次进入 IAM Identity Center → Settings → Identity source → Change identity source，选择 “External identity provider”，并配置与 IdP 之间的 SAML 2.0 或 SCIM 连接。启用 SCIM 预置，自动同步用户和组，包括团队、部门等组织属性。

**为会话标签配置属性映射**：进入 Settings → Attributes for access control，把 IdP 的组织属性映射到将流入 CUR 2.0 的会话标签。这些属性会作为会话标签（`aws:PrincipalTag/Team`、`aws:PrincipalTag/CostCenter`）随用户发起的每一次 API 调用传播，包括经由 `bedrock-runtime` 和 `bedrock-mantle` 两个端点发起的每一次 Bedrock 调用。

## 步骤 2：创建 Bedrock 访问权限集

在 Identity Center 中创建一个授予 Bedrock 调用权限的权限集。每位用户在该权限集内都有各自的会话，这是按用户归因的基础。具体需要哪些 IAM 操作，取决于工具调用的是哪个 Bedrock 端点。

调用 `bedrock-mantle` 端点的工具（如 Codex 和 ChatGPT Work）需要 `bedrock-mantle:CreateInference` 以及作用域限定到 Project 资源的相关操作。调用 `bedrock-runtime` 端点的工具（如 Claude Code 和 Claude Desktop）需要 `bedrock:InvokeModel` 和 `bedrock:InvokeModelWithResponseStream`，作用域限定到相应基础模型或推理配置文件的 ARN。如果组织在两个端点上都用到工具，可以把两者合并进同一个权限集。

```
{
    "Statement": [
        {
            "Sid": "BedrockMantleAccess",
            "Effect": "Allow",
            "Action": [
                "bedrock-mantle:CreateInference",
                "bedrock-mantle:CountTokens"
            ],
            "Resource": “arn:aws:bedrock-mantle:::project/”
        },
        {
            "Sid": "BedrockModelAccess",
            "Effect": "Allow",
            "Action": [
                "bedrock:InvokeModel",
                "bedrock:InvokeModelWithResponseStream",
                "bedrock:ListInferenceProfiles",
                "bedrock:GetInferenceProfile"
            ],
			“Resource”: [
			“arn:aws:bedrock:::inference-profile/“,
			“arn:aws:bedrock:::application-inference-profile/“,
			“arn:aws:bedrock:::foundation-model/”
			]
        }
    ]
}
```

**注意：** 这些资源模式只是起点，请收窄到你批准的特定推理配置文件和 Projects。把该权限集分配给从 IdP 同步过来的相关组。策略变更即时且全局生效，审计通过 AWS CloudTrail 按每位用户的身份集中记录，用户也不会拿到长期有效的 AWS 凭证。

## 步骤 3：配置用户工作站

用户只需配置一次 AWS CLI profile，无需自定义脚本、凭证助手或浏览器自动化。下面这段 `~/.aws/config` 配置即可建立 SSO 会话：

```
[profile bedrock]
sso_session = corp
sso_account_id = 111122223333
sso_role_name = BedrockDeveloperAccess
region = us-east-1

[sso-session corp]
sso_start_url = https://your-org.awsapps.com/start
sso_region = us-east-1
sso_registration_scopes = sso:account:access
```

用户运行 `aws sso login --profile bedrock` 完成认证：命令会打开浏览器、通过 IdP 认证，并在本地缓存凭证。AWS CLI 和 SDK 会自动刷新访问令牌，直到 IAM Identity Center 会话结束（默认 8 小时）。设置会话时长的核心取舍，是在安全态势与操作便利性之间权衡。

## 步骤 4：把工具指向 Amazon Bedrock

每款 AI 工具只需改一处标准配置，就能把推理路由到 Bedrock。由于 Bedrock 归因运行在端点层，不需要针对具体工具插桩。工具用步骤 3 建立的 AWS 凭证链完成认证，Bedrock 会自动捕获调用方身份。

**Claude Desktop** 从操作系统原生的托管偏好设置读取第三方推理配置（macOS 上是 `/Library/Managed Preferences/com.anthropic.claudefordesktop.plist`，Windows 上是 `HKLM\SOFTWARE\Policies\Claude`）。在应用内窗口（Developer → Configure Third-Party Inference）里编写一次配置，选择 **Export** 即可为移动设备管理 (MDM) 系统生成 `.mobileconfig` 或 `.reg`。要做按用户归因，请使用应用内 AWS 登录：每位用户在应用内对着 IAM Identity Center 认证，设备上无需安装 AWS CLI：

```
inferenceProvider bedrock
inferenceBedrockRegion us-east-1
inferenceBedrockSsoStartUrl https://your-org.awsapps.com/start
inferenceBedrockSsoRegion us-east-1
inferenceBedrockSsoAccountId 111122223333
inferenceBedrockSsoRoleName BedrockDeveloperAccess
inferenceModels ["us.anthropic.claude-sonnet-5","us.anthropic.claude-opus-5"]
```

配置在启动时读取，用户必须退出并重新打开应用。如果开发人员已经在用 AWS CLI v2，改为设置 `inferenceBedrockProfile`，应用会替他们运行 `aws sso login`。

Claude Code CLI 读取标准的 AWS SDK 凭证链，包括 SSO profile。如果设置了 `AWS_BEARER_TOKEN_BEDROCK`，Claude Code 会用该密钥认证而不走凭证链，于是调用被归到该密钥背后的 IAM 用户。需要按用户做 SSO 归因时，请禁用它。

在设置文件中设置 `awsAuthRefresh`，让凭证过期时自动重新认证：

```
{
    "awsAuthRefresh": "aws sso login --profile bedrock",
    "env": {
        "CLAUDE_CODE_USE_BEDROCK": "1",
        "AWS_PROFILE": "bedrock",
        "AWS_REGION": "us-east-1"
    }
}
```

在全量铺开之前固定好模型版本，避免新版本改变用户实际调用的模型：

```
export ANTHROPIC_DEFAULT_OPUS_MODEL='us.anthropic.claude-opus-5'
export ANTHROPIC_DEFAULT_SONNET_MODEL='us.anthropic.claude-sonnet-5'
```

**Codex 和 ChatGPT Work** 读取 `~/.codex/config.toml`。桌面应用和 CLI 使用同一套配置层。针对 `bedrock-mantle` 端点：

```
model_provider = "amazon-bedrock"
model = "openai.gpt-5.6-sol"

[model_providers.amazon-bedrock.aws]
region = "us-east-1"
```

针对 `bedrock-runtime` 端点，请使用推理配置文件 ID：

```
model_provider = "amazon-bedrock-runtime"
model = "us.openai.gpt-5.6-sol"
web_search = "disabled"
```

两个端点都要在环境中设置 `AWS_PROFILE`。桌面应用请把环境变量放在 `~/.codex/.env` 里，因为桌面应用可能不会继承 shell 的环境变量。如果设置了 `AWS_BEARER_TOKEN_BEDROCK`，Codex 会优先于 SSO profile 使用它，调用便归到该 API key 背后的 IAM 用户。需要按用户做 SSO 归因时，请取消该设置。

## 步骤 5：在 CUR 2.0 中启用成本归因

在 AWS Billing Console（Billing → Data Exports → Create export）中，配置以 Parquet 格式、按小时或按天的粒度投递到 S3。选择 “Include caller identity (IAM principal) allocation data”，即可填充 `line_item_iam_principal` 列。Bedrock 的 IAM 委托人成本跟踪对 `bedrock-runtime` 和 `bedrock-mantle` 两个端点都适用。

在管理账户中创建导出，可以覆盖所有账户的 Bedrock 用量。如果你在 IAM 委托人归因功能上线之前就创建过 CUR 2.0 数据导出，必须新建一个勾选了调用者身份选项的导出。

等用户登录并至少发起过一次 Bedrock 调用之后，再激活成本分配标签——委托人发起调用之后，标签才会出现在 Billing 里。在管理账户中打开 Billing → Cost allocation tags，按 IAM principal 类型筛选，激活 `Team` 和 `CostCenter`：

```
aws ce update-cost-allocation-tags-status \
--cost-allocation-tags-status TagKey=Team,Status=Active
aws ce update-cost-allocation-tags-status \
--cost-allocation-tags-status TagKey=CostCenter,Status=Active
```

标签最多需要 24 小时才会出现，最多 48 小时才能在 CUR 2.0 和 Cost Explorer 中看到；激活不会追溯生效。Bedrock 对输入、输出、缓存读取和缓存写入 token 分别计量、分别计费。同一个 IAM 委托人下一小时的活动，通常会产生 4 行 CUR 记录。

## 步骤 6：用 Amazon Athena 查询成本数据

CUR 2.0 投递到 S3、Athena 表也配好之后，就能按需要的粒度查询用量与成本。下面的查询提取每位用户的成本：

```
SELECT
  regexp_extract(line_item_iam_principal, 'assumed-role/[^/]+/(.+)$', 1) AS user_name,
  line_item_usage_type,
  SUM(line_item_unblended_cost) AS total_cost_usd,
  SUM(line_item_usage_amount)   AS usage_units
FROM cur_table
WHERE line_item_product_code IN ('AmazonBedrock', 'AmazonBedrockService')
  AND line_item_iam_principal IS NOT NULL
  AND line_item_line_item_type = 'Usage'
  AND billing_period = '2026-09'
GROUP BY 1, 2
ORDER BY total_cost_usd DESC;
```

按成本中心查看每日支出趋势：

```
SELECT
    DATE(line_item_usage_start_date) AS usage_date,
    element_at(tags, 'iamPrincipal/CostCenter') AS cost_center,
    SUM(line_item_unblended_cost) AS daily_cost_usd
FROM cur_table
WHERE line_item_product_code IN ('AmazonBedrock', 'AmazonBedrockService')
    AND line_item_iam_principal IS NOT NULL
    AND line_item_line_item_type = 'Usage'
    AND billing_period = '2026-09'
GROUP BY 1, 2
ORDER BY 1, daily_cost_usd DESC;
```

Athena 按扫描的数据量计费。列式 Parquet 加上 `billing_period` 过滤，能让查询保持低成本。

## 步骤 7：可视化

AWS Cost Explorer 无需任何配置，标签激活后按标签分组即可。AWS Quick Sight 连接 Athena 提供交互式仪表板，并带有异常检测，可对意外的支出尖峰报警。你还可以集成 [CUDOS dashboard](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-cost-attribution-with-amazon-athena-and-cudos/)——一个开源的 Cloud Intelligence Dashboards (CID) 框架，提供细致的成本洞察。装上 Athena 插件的 Grafana 能把 CUR 数据作为时间序列，与现有基础设施指标并排呈现。

## 实施按用户的使用控制

借 CUR 2.0 中的 IAM 委托人归因建立起按用户的成本可见性之后，组织还需要执行机制来防止费用失控累积。目前有多种做法，各自在执行延迟与运维复杂度之间做取舍。

**AWS Budgets 配合预算操作**是最轻量的方案，不需要自建基础设施。设置一个按 IAM 委托人标签筛选的预算阈值，再挂上一个在突破阈值时触发的操作（例如应用 deny 策略）。代价是：AWS Budgets 每天最多更新三次，而 Bedrock 费用最多要 24 小时才会出现在账单数据里，因此高频用户可能在限制生效前就超支最多一整天。

**Amazon CloudWatch 告警与 AWS Lambda** 借助 Bedrock 原生的 CloudWatch 指标（`InputTokenCount`、`OutputTokenCount`、`Invocations`）实现近实时管控，可按模型 ID 或推理配置文件筛选。执行延迟降到 1–5 分钟。要用这种方案拿到用户级粒度，可以配合 Application Inference Profiles 或按用户划分的角色。

**基于 Amazon DynamoDB 的配额跟踪**在认证层执行限制。Lambda 函数在 DynamoDB 里递增按用户统计的 token 计数器，一旦超限就暂不发放凭证。限制在下一次凭证刷新时生效，而非作用于单次 API 调用，但这样消除了基于预算的方案固有的账单数据滞后。

**LLM 网关代理**能在 Bedrock 模型和 SDK 工作负载上做到逐次调用拦截，代价是运维复杂度最高，且每次请求都增加延迟。参见 [Multi-Provider Generative AI Gateway](https://aws.amazon.com/blogs/machine-learning/multi-provider-generative-ai-gateway/)。

组织通常会把这些方案叠加使用：CUR 2.0 用于报表，网关或基于 DynamoDB 的执行用于实时控制，AWS Budgets 兜底。完整参考见 [如何限制 Amazon Bedrock 的用量与成本](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-management.html)。

## 结论

Amazon Bedrock 的 IAM 委托人归因，能为每一款经由 Bedrock 路由推理的 AI 开发工具与生产力工具提供按用户的成本跟踪，无需自定义凭证脚本、按用户划分的 IAM 角色或额外基础设施。用户用 `aws sso login` 认证——与其他 AWS 访问用的是同一套流程——每次 Bedrock 调用都会自动把身份带进账单数据。

每个组件都可以逐步引入。先把 IdP 接到 Identity Center、分配一个 Bedrock 权限集，立刻就能在 CloudTrail 里拿到会话级归因；再激活成本分配标签，让这些数据在 CUR 2.0 中显现；随着报表需求增长，补上 Athena 查询和仪表板；最后按组织对执行延迟的容忍度，叠加从 AWS Budgets 到实时网关管控的使用控制。

无论组织今天采用、明天新增哪款 AI 工具，本文讲的归因与控制机制都运行在 Bedrock 平台层。配置一次，所有调用 Bedrock 的工具都会继承这套治理能力。
