# Amazon Bedrock 上人工智能开发人员和生产力工具的成本归因和控制

Amazon Bedrock 提供内置的零检测成本归因，可将每个推理调用追溯到发起该调用的 IAM 委托人。身份与组织标签一起流入 AWS 成本和使用情况报告 (CUR 2.0) 和 AWS Cost Explorer，同时将数据保留在 AWS 安全边界内。这篇文章向您展示如何使用这些功能来回答每个 FinOps 和 AI 平台领导者在 AI 工具采用规模扩大时提出的三个问题：每个用户的实际成本是多少？哪些团队产生的支出最多，这些支出与他们交付的价值是否相关？明年的预算应如何根据人员数量和采用情况进行调整？

无论哪种人工智能编码或生产力工具进行调用，该方法的工作原理都是相同的。 Claude Code、Claude Desktop、OpenAI Codex、ChatGPT Work 和 OpenCode 均通过两个推理端点之一调用 Amazon Bedrock：“bedrock-runtime”或“bedrock-mantle”，并且 Bedrock 的归因机制在端点层运行，位于任何特定于工具的逻辑之下。您配置身份传播一次，通过 Bedrock 路由推理的每个工具都会自动继承每个用户的成本可见性。

在本文结束时，您将使用外部身份提供商配置 AWS IAM Identity Center，以实现每用户归因、流入 CUR 2.0 的会话标签（团队、成本中心）、Amazon Athena 查询和控制面板选项以实现持续的成本可见性，并清楚了解 Bedrock 原生使用控制以实施支出限制。

## Amazon Bedrock 归因的工作原理

Amazon Bedrock 记录每个推理调用者的 IAM 身份，无需对 API 调用进行任何更改。当用户通过“bedrock-runtime”或“bedrock-mantle”端点调用模型时，Bedrock 会捕获调用者的完整 IAM ARN，包括联合用户的会话名称，并将其发布到“line_item_iam_principal”列中的 CUR 2.0。在计费数据中，每个导出间隔的每个主体和每个使用类型聚合使用情况：每小时导出一小时，每日导出一天。 CUR 不包含每个请求的成本。对于每个提示的详细信息，请使用模型调用日志或请求元数据标记。

或者，您可以将标签附加到 IAM 委托人或在联合期间传递会话标签以添加组织维度。这些标签在 CUR 2.0 中显示为“iamPrincipal/”前缀，并在 Cost Explorer 中显示为可过滤维度。该机制支持四种访问模式：IAM 用户、每个应用程序角色、联合身份和代理到 Bedrock 的大型语言模型 (LLM) 网关。有关这四种方法的比较，请参阅[Amazon Bedrock 的粒度成本归因简介](https://aws.amazon.com/blogs/machine-learning/introducing-capsular-cost-attribution-for-amazon-bedrock/)。这篇文章遵循联合身份模式，该模式非常适合人工智能编码和生产力工具，其中每个开发人员或知识工作者都单独进行身份验证。

除了 IAM 委托人跟踪之外，Amazon Bedrock 还提供其他归因机制，组织可以根据自己的需求进行分层（请参阅附录 A 进行比较）。借助应用程序推理配置文件，您可以按“Bedrock运行时”端点上的工作负载标记支出。通过项目和工作区，您可以隔离并标记“Bedrock地幔”端点上的支出。每个请求元数据标记在模型调用日志中为需要比 CUR 2.0 每个导出间隔的每个使用类型聚合更精细的粒度的工作负载提供每个提示令牌级别的详细信息。例如，您可以将发票上每用户美元的 IAM 主体归属与日志中每个提示详细信息的每个请求元数据标签结合起来。选择取决于您的目标（请参阅[跟踪 Amazon Bedrock 中的使用情况和成本](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-management.html)）。

## 归因问题

开发人员和生产力工具在每个用户的计算机上运行，​​并直接或通过 LLM 网关调用 Amazon Bedrock。用户通过假定共享 IAM 角色进行身份验证，因此每个 API 调用在账单中显示为“假定角色/<角色>/<会话名称>”。如果每个用户都承担具有相同固定会话名称的角色，或者调用通过网关自己的角色，则 CUR 会将支出聚合到单个主体。对于 IAM Identity Center，会话名称是用户的登录名，因此每个用户都有自己的委托人。您可以使用会话标签（团队、成本中心、项目）进一步丰富它。这些字段流入 CUR 2.0 的“line_item_iam_principal”列和带有“iamPrincipal/”前缀的成本分配标签，使每个用户的支出与美元一起可查询，并且对 Bedrock API 调用的更改为零。

AWS 上的 Claude Platform 和 Claude for Enterprise 通过 Anthropic 管理的基础设施进行路由推理。对于 AWS 上的 Claude Platform，使用情况可通过 Anthropic 管理控制台中的工作区和 API 密钥查看，工作区标签会流向 AWS 账单。对于 Claude for Enterprise，每个用户的使用情况在 Anthropic 的管理控制台以及使用情况和成本 API 中可见。支出限制由 Anthropic 本地强制执行。

## 先决条件

开始之前，请确保您拥有：

- 具有 IAM 权限的 [AWS 账户](https://aws.amazon.com/resources/create-account/)，可以访问您打算使用的 Bedrock 模型。
- 您的管理账户中的 AWS [已启用 IAM Identity Center](https://docs.aws.amazon.com/singlesignon/latest/userguide/enable-identity-center.html)。
- 具有 SCIM 配置功能的外部身份提供商（Okta、Microsoft Entra ID 或 Ping Identity）。
- 在开发人员计算机上配置的 [AWS CLI v2](https://docs.aws.amazon.com/cli/latest/userguide/cli-chap-getting-started.html)。
- [AWS 成本和使用情况报告](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/iam-principal-cost-allocation.html) (CUR 2.0) 使用 IAM 主体数据启用并交付到 S3 存储桶。
- 从管理（付款人）账户激活的[成本分配标签](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-alloc-tags.html)。
- 配置为查询 CUR 2.0 数据的 Athena 表（请参阅 [GitHub 示例](https://github.com/aws-samples/aws-cudos-framework-deployment) 以开始使用）。

## 步骤 1：使用外部 IdP 配置 IAM Identity Center

将您的外部身份提供商配置为 AWS IAM Identity Center 中的身份源。导航到 IAM 身份中心 → 设置 → 身份源 → 更改身份源。选择“外部身份提供商”并配置与您的 IdP 的 SAML 2.0 或 SCIM 连接。启用 SCIM 配置以自动同步用户和组，包括团队和部门等组织属性。

**通过导航到设置→访问控制属性来配置会话标签的属性映射**。将 IdP 的组织属性映射到将流入 CUR 2.0 的会话标签。这些属性作为会话标签（“aws:PrincipalTag/Team”、“aws:PrincipalTag/CostCenter”）在用户进行的每个 API 调用上传播，包括通过“bedrock-runtime”和“bedrock-mantle”端点进行的每个 Bedrock 调用。

## 步骤 2：创建Bedrock访问权限集

在 Identity Center 中创建一个权限集，授予 Bedrock 调用访问权限。每个用户都在此权限集中获得自己的会话。这是每用户归因的基础。具体 IAM 操作取决于该工具调用的 Bedrock 端点。

调用“bedrock-mantle”端点的工具（例如 Codex 和 ChatGPT Work）需要“bedrock-mantle:CreateInference”以及范围为项目资源的相关操作。调用“bedrock-runtime”端点的工具（例如 Claude Code 和 Claude Desktop）需要范围为相关基础模型或推理配置文件 ARN 的“bedrock:InvokeModel”和“bedrock:InvokeModelWithResponseStream”。如果您的组织跨两个端点使用工具，则可以将两者合并到一个权限集中。
```
{
    "Statement": [
        {
            "Sid": "BedrockMantleAccess",
            "Effect": "Allow",
            "Action": [
                "bedrock-mantle:CreateInference",
                "bedrock-mantle:CountTokens"
            ],
            "Resource": “arn:aws:bedrock-mantle:::project/”
        },
        {
            "Sid": "BedrockModelAccess",
            "Effect": "Allow",
            "Action": [
                "bedrock:InvokeModel",
                "bedrock:InvokeModelWithResponseStream",
                "bedrock:ListInferenceProfiles",
                "bedrock:GetInferenceProfile"
            ],
			“Resource”: [
			“arn:aws:bedrock:::inference-profile/“,
			“arn:aws:bedrock:::application-inference-profile/“,
			“arn:aws:bedrock:::foundation-model/”
			]
        }
    ]
}
```
**注意：** 这些资源模式是一个起点。将它们缩小到您批准的特定推理配置文件和项目。将此权限集分配给从您的 IdP 同步的相关组。策略更改是即时且通用的，审核通过 AWS CloudTrail 使用每个用户的身份进行集中，并且用户不会收到长期有效的 AWS 凭证。

## 步骤 3：配置用户工作站

用户配置其 AWS CLI 配置文件一次，无需自定义脚本、凭证帮助程序或浏览器自动化。以下 `~/.aws/config` 条目建立 SSO 会话：
```
[profile bedrock]
sso_session = corp
sso_account_id = 111122223333
sso_role_name = BedrockDeveloperAccess
region = us-east-1

[sso-session corp]
sso_start_url = https://your-org.awsapps.com/start
sso_region = us-east-1
sso_registration_scopes = sso:account:access
```
用户通过运行“aws sso login --profile bedrock”进行身份验证，这会打开浏览器，通过 IdP 进行身份验证，并在本地缓存凭证。 AWS CLI 和开发工具包会自动刷新访问令牌，直到 IAM Identity Center 会话结束（默认为 8 小时）。配置会话持续时间的核心权衡是安全状况和操作便利性之间。

## 步骤 4：将工具指向 Amazon Bedrock

每个 AI 工具只需要更改标准配置即可通过 Bedrock 进行推理。由于 Bedrock 归因在端点层运行，因此不需要特定于工具的检测。该工具使用步骤 3 中建立的 AWS 凭证链进行身份验证，Bedrock 会自动捕获调用者身份。

**Claude Desktop** 从操作系统本机托管首选项（macOS 上的“/Library/Managed Preferences/com.anthropic.claudefordesktop.plist”，Windows 上的“HKLM\SOFTWARE\Policies\Claude”）读取第三方推理设置。在应用程序内窗口（开发人员 → 配置第三方推理）中编写一次配置，然后选择 **导出** 为您的移动设备管理 (MDM) 系统生成“.mobileconfig”或“.reg”。对于每用户归因，请使用应用程序内 AWS 登录，每个用户都根据应用程序内的 IAM Identity Center 进行身份验证，而设备上没有 AWS CLI：
```
inferenceProvider bedrock
inferenceBedrockRegion us-east-1
inferenceBedrockSsoStartUrl https://your-org.awsapps.com/start
inferenceBedrockSsoRegion us-east-1
inferenceBedrockSsoAccountId 111122223333
inferenceBedrockSsoRoleName BedrockDeveloperAccess
inferenceModels ["us.anthropic.claude-sonnet-5","us.anthropic.claude-opus-5"]
```
配置在启动时读取。用户必须退出并重新打开应用程序。如果开发人员已运行 AWS CLI v2，请改为设置“inferenceBedrockProfile”，应用程序会为他们运行“aws sso login”。

Claude Code CLI 读取标准 AWS SDK 凭证链，包括 SSO 配置文件。如果设置了“AWS_BEARER_TOKEN_BEDROCK”，Claude Code 将使用该密钥进行身份验证，并且不使用凭证链，因此调用将归因于该密钥背后的 IAM 用户。当您需要每用户 SSO 归因时禁用它。

在设置文件中设置 `awsAuthRefresh` 以在凭证过期时自动重新进行身份验证：
```
{
    "awsAuthRefresh": "aws sso login --profile bedrock",
    "env": {
        "CLAUDE_CODE_USE_BEDROCK": "1",
        "AWS_PROFILE": "bedrock",
        "AWS_REGION": "us-east-1"
    }
}
```
在队列推出之前固定模型版本，以便新版本不会更改用户调用的内容：
```
export ANTHROPIC_DEFAULT_OPUS_MODEL='us.anthropic.claude-opus-5'
export ANTHROPIC_DEFAULT_SONNET_MODEL='us.anthropic.claude-sonnet-5'
```
**Codex 和 ChatGPT 工作** 阅读 `~/.codex/config.toml`。桌面应用程序和 CLI 都使用相同的配置层。对于“基岩-地幔”端点：
```
model_provider = "amazon-bedrock"
model = "openai.gpt-5.6-sol"

[model_providers.amazon-bedrock.aws]
region = "us-east-1"
```
对于“bedrock-runtime”端点，使用推理配置文件 ID：
```
model_provider = "amazon-bedrock-runtime"
model = "us.openai.gpt-5.6-sol"
web_search = "disabled"
```
在两个端点的环境中设置“AWS_PROFILE”。对于桌面应用程序，请将环境变量放置在 `~/.codex/.env` 中，因为桌面应用程序可能不会继承 shell 环境变量。如果设置了“AWS_BEARER_TOKEN_BEDROCK”，Codex 在 SSO 配置文件之前使用它，并且调用将归因于该 API 密钥背后的 IAM 用户。当您需要每用户 SSO 归属时请取消设置。

## 步骤 5：在 CUR 2.0 中启用成本归因

从 AWS 计费控制台（计费 → 数据导出 → 创建导出），以每小时或每日的粒度配置以 Parquet 格式传输到 S3。选择“包括调用者身份（IAM 主体）分配数据”以填充“line_item_iam_principal”列。 Bedrock 的 IAM 主要成本跟踪适用于“bedrock-runtime”和“bedrock-mantle”端点。

在管理账户中创建导出会捕获所有账户的 Bedrock 使用情况。如果您在启动 IAM 委托人归因之前创建了 CUR 2.0 数据导出，则必须在选择调用者身份选项的情况下创建新导出。

用户登录并至少进行一次 Bedrock 呼叫后激活成本分配标签。仅当委托人拨打电话后，标签才会出现在账单中。在管理账户中，打开账单 → 成本分配标签，按 IAM 主体类型进行筛选，然后激活“Team”和“CostCenter”：
```
aws ce update-cost-allocation-tags-status \
--cost-allocation-tags-status TagKey=Team,Status=Active
aws ce update-cost-allocation-tags-status \
--cost-allocation-tags-status TagKey=CostCenter,Status=Active
```
标签最多允许 24 小时显示，最多 48 小时才能在 CUR 2.0 和 Cost Explorer 中查看。激活不具有追溯力。 Bedrock 分别对输入、输出、缓存读取和缓存写入令牌进行计量和计费。一个 IAM 主体下的一小时活动通常会产生 4 个 CUR 行。

## 步骤 6：使用 Amazon Athena 查询成本数据

将 CUR 2.0 交付到 S3 并配置 Athena 表后，即可按照您所需的粒度查询使用情况和成本。以下查询提取每个用户的成本：
```
SELECT
  regexp_extract(line_item_iam_principal, 'assumed-role/[^/]+/(.+)$', 1) AS user_name,
  line_item_usage_type,
  SUM(line_item_unblended_cost) AS total_cost_usd,
  SUM(line_item_usage_amount)   AS usage_units
FROM cur_table
WHERE line_item_product_code IN ('AmazonBedrock', 'AmazonBedrockService')
  AND line_item_iam_principal IS NOT NULL
  AND line_item_line_item_type = 'Usage'
  AND billing_period = '2026-09'
GROUP BY 1, 2
ORDER BY total_cost_usd DESC;
```
对于每个成本中心的每日支出趋势：
```
SELECT
    DATE(line_item_usage_start_date) AS usage_date,
    element_at(tags, 'iamPrincipal/CostCenter') AS cost_center,
    SUM(line_item_unblended_cost) AS daily_cost_usd
FROM cur_table
WHERE line_item_product_code IN ('AmazonBedrock', 'AmazonBedrockService')
    AND line_item_iam_principal IS NOT NULL
    AND line_item_line_item_type = 'Usage'
    AND billing_period = '2026-09'
GROUP BY 1, 2
ORDER BY 1, daily_cost_usd DESC;
```
雅典娜通过扫描数据收费。 Columnar Parquet 和“billing_period”过滤器使查询成本低廉。

## 步骤 7：可视化

AWS Cost Explorer 需要零设置。一旦标签被激活，就按标签分组。 AWS Quick Sight 连接到 Athena 以获得交互式仪表板，并提供异常检测功能，可针对意外支出高峰发出警报。您可以与 [CUDOS 仪表板](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-cost-attribution-with-amazon-athena-and-cudos/) 集成，这是一个开源云智能仪表板 (CID) 框架，可提供详细的成本洞察。带有 Athena 插件的 Grafana 将 CUR 数据与现有基础设施指标一起呈现为时间序列。

## 实施每个用户的使用控制

一旦通过 CUR 2.0 中的 IAM 主体归因建立了每用户成本可见性，组织就需要执行机制来帮助防止不受控制的累积。目前存在多种方法，每种方法都存在针对操作复杂性的交易执行延迟。

**包含预算操作的 AWS 预算**是最轻的选项，无需自定义基础设施。设置由 IAM 主体标签过滤的预算阈值，并附加在违反阈值时触发的操作（例如应用拒绝策略）。权衡：AWS 预算每天最多更新 3 次，而 Bedrock 费用可能需要长达 24 小时才能出现在账单数据中，因此高速用户可能会在强制生效之前超支最多一天。

**Amazon CloudWatch 警报和 AWS Lambda** 使用按模型 ID 或推理配置文件过滤的 Bedrock 原生 CloudWatch 指标（“InputTokenCount”、“OutputTokenCount”、“调用”）提供近乎实时的执行。执行延迟降至 1-5 分钟。要使用此方法获得用户级粒度，请使用应用程序推理配置文件或每用户角色。

**基于 Amazon DynamoDB 的配额跟踪** 在身份验证层实施限制。 Lambda 函数会增加 DynamoDB 中的每用户令牌计数器，并在超出限制后保留凭证。强制执行在下一次凭证刷新时生效，而不是在单个 API 调用上生效，但消除了基于预算的方法中固有的计费数据滞后。

**LLM 网关代理** 跨 Bedrock 模型和 SDK 工作负载提供每次调用阻塞，但代价是操作复杂性最高，​​并且每个请求的延迟都增加。请参阅[多提供商生成式 AI 网关](https://aws.amazon.com/blogs/machine-learning/multi-provider-generative-ai-gateway/)。

组织通常会对这些选项进行分层：用于报告的 CUR 2.0、用于实时控制的网关或基于 DynamoDB 的实施以及作为后盾的 AWS 预算。有关完整参考，请参阅[如何限制 Amazon Bedrock 上的使用量和成本](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-management.html)。

＃＃ 结论

Amazon Bedrock 的 IAM 主要归因功能让您可以跟踪每个通过 Bedrock 路由推理的 AI 开发人员和生产力工具的每用户成本，无需自定义凭证脚本、每用户 IAM 角色或其他基础设施。用户使用“aws sso login”进行身份验证，这与他们用于其他 AWS 访问的流程相同，并且每个 Bedrock 调用都会自动将其身份带入账单数据中。

每个组件都可以逐步采用。首先将您的 IdP 连接到 Identity Center 并分配 Bedrock 权限集，以立即在 CloudTrail 中获取会话级别归因。激活成本分配标签以在 CUR 2.0 中显示该数据。随着报告需求的增长添加 Athena 查询和仪表板。根据您的组织对执行延迟的容忍度，进行从 AWS 预算到实时网关执行的层使用控制。

无论您的组织今天采用或明天添加哪种人工智能工具，此处描述的归因和控制机制都在 Bedrock 平台层运行。配置一次，每个调用 Bedrock 的工具都会继承治理。
