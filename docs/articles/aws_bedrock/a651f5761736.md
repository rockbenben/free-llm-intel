# 使用 Amazon Bedrock AgentCore payments 的内置护栏实现安全的 agentic 支付

agent 越来越多地代表最终用户执行操作：为达成目标自主选择工具、浏览网页、调用 MCP 服务器。当 agent 触及的工具、MCP 端点或网络资源需要付费时，agent 就会卡住，无法完成交易。与 Coinbase 和 Stripe（Privy）合作发布预览版的 [Amazon Bedrock AgentCore payments](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments.html)，让 agent 能够代表最终用户访问付费资源，从而完成任务。

让自主系统动用真实资金会带来一系列新的风险，这些风险来自 agent 在长会话中自主行动、模型的非确定性，以及 agent 代码与最终用户资金之间更大的暴露面。本文逐一梳理这些风险，以及 AgentCore payments 组合运用来应对每项风险的护栏。

*AgentCore payments 处于预览阶段，可在美国东部（弗吉尼亚北部）、美国西部（俄勒冈）、欧洲（法兰克福）和亚太地区（悉尼）使用。功能与 API 在正式可用前可能发生变化。*

本文通篇使用以下术语：

- *最终用户（end user）：* 资金被使用、agent 代其进行交易的自然人。
- *开发者（developer）：* 将支付能力集成到其 AI agent 中的 AWS 客户。
- *钱包提供商（wallet provider）：* Coinbase Developer Platform（CDP）或 Stripe Privy。
- *嵌入式钱包（embedded wallet）：* 由钱包提供商托管、属于最终用户的自托管钱包。
- *支付会话（payment session）：* 针对单次 agent 交互的限定范围支付上下文，带有可配置的预算与存活时间（time-to-live，TTL）。
- *开发者凭证（developer credentials）：* 钱包提供商签发给开发者的 API 密钥、secret 和授权密钥，由 AgentCore payments 用来调用钱包提供商的 API。

本文讨论设计 agentic 支付系统时会浮现的若干关键风险，以及如何借助 AgentCore payments 的能力来应对它们。

## 挑战：agentic 支付中的安全风险

若干关键风险决定了面向 agent 的支付能力必须如何设计。

### 失控的支出

agent 是自主且长时间运行的。它们代表最终用户做决策，一个会话中往往要做很多次决策，而且在无人值守的情况下持续运行。如果没有明确的护栏，被错误 prompt 引导或被攻陷的 agent 可能造成失控的支出。

大语言模型（LLM）同样是非确定性的，因此你无法保证模型不会把某个响应误解为支出授权，也不会因为意外的重试而重复付款。支出限额必须在模型之外、在基础设施层定义并强制执行。

### 缺少最终用户同意与授权委托

agent 现在可以自主付款，但最终用户必须保留最终控制权。最终用户决定何时授予支出权限、何时为钱包充值、何时提取资金。agent 必须在明确且限定范围的权限下运行，而不是一揽子授权；最终用户可以随时撤销该权限。

### 开发者密钥与钱包 token 泄露

代表最终用户进行交易的 agent 会涉及两类敏感材料。第一类是 AgentCore payments 用来调用钱包提供商 API 的开发者凭证（API 密钥、secret 和授权密钥）。第二类是最终用户嵌入式钱包的密钥（由钱包提供商自托管保管）。两者都必须远离 agent 代码。如果这些凭证被内联存储在 agent 代码或环境变量中，一旦 agent 被攻陷就会泄露它们。agent 不应直接处理这些凭证，而系统为单次支付签发的凭证应当是短期有效的，并绑定到特定会话。

### 最终用户支付工具的暴露

最终用户的卡号、卡验证值（card verification value，CVV）以及其他个人支付信息，绝不应进入 agent 的上下文。能看到信用卡的 agent，其暴露面远大于看不到的 agent，支付卡行业（Payment Card Industry，PCI）标准的适用范围也会随之扩大。agent 的视野应止步于「从用户自有钱包中支出的许可」，不得再进一步。

### 缺少可审计性

当出现问题——例如意外扣费、支付被拒，或者安全团队、财务团队追问发生了什么——必须有一份完整、可靠的记录，说明 agent 做了什么、代表谁做、在哪些限额约束下、付给了哪个商户。这份记录必须自动产生。仅依赖 agent 代码自行记录自己的操作是不够的。

## 使用 AgentCore 服务与控制项应对这些风险

AgentCore payments 与 Amazon Bedrock AgentCore 的其他部分集成，以应对这些挑战。

### 支付限额与工具访问策略

每笔交易都在一个支付*会话*内运行，即为单次 agent 交互限定范围的支付上下文。支付会话有两个可配置的上限：以指定货币表示的最高支出金额，以及过期时间。在签署支付之前，AgentCore payments 会对照会话预算检查请求。会使会话超出上限的请求会被 AgentCore payments 拒绝。如果在服务已从预算中扣减之后签名失败，它会回滚该扣减，因此失败的交易不会消耗预算。

这项检查是确定性的，并在基础设施层执行。Prompt injection 无法抬高上限，因为上限是在模型之外强制执行的。开发者按工作负载配置限额，AgentCore payments 在每次调用时执行这些限额。我们建议先从较小的预算开始，待 agent 在生产环境中证明可靠后再提高。

对于工具级授权，我们建议通过 Amazon Bedrock AgentCore Gateway 暴露付费端点。经由 AgentCore Gateway 的每次调用都会被 AgentCore 中的 Policy 拦截；Policy 是一个基于 Cedar 的引擎，它会评估请求（包括 agent 身份、工具名称与参数），并决定是否放行。这两项控制针对不同的决策。Policy 决定谁能调用哪个付费工具、使用什么参数。AgentCore payments 决定这次调用能花多少钱、能持续多久。两者结合，为工具访问与支出金额提供了相互正交的调节手段。

- 关于创建带有预算与 TTL 配置的支付会话的完整演示，请参阅 Amazon Bedrock AgentCore 开发者指南中的[创建支付会话](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments-create-session.html)。
- 关于按 agent 角色和用户组限定工具访问范围的 Cedar 策略示例，请参阅开发者指南中的 [AgentCore 中的 Policy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html)。

### 用户控制、充值与授权委托

最终用户先为钱包充值，然后显式授予 agent 支出权限，顺序如此。充值是带外（out-of-band）操作。最终用户在钱包提供商的门户（Coinbase WalletHub 或 Stripe Privy 前端）内完成充值，整个流程 agent 既没有 API 接入，也无法看到。即使资金已到账，在最终用户通过钱包提供商的权限原语（Coinbase Spend Permissions 或 Privy Delegated Actions）显式委托该权限之前，agent 也没有交易权限。为钱包充值和授权 agent 是两个独立的决策，都由最终用户在钱包提供商的门户内做出。

钱包本身属于最终用户，无论是 Coinbase Developer Platform（CDP）嵌入式钱包还是 Stripe Privy 嵌入式钱包。密钥由最终用户持有，AWS 不持有，开发者也不持有。最终用户可以自行决定撤销委托。由于钱包属于他们自己，他们可以随时把资金提取回自己控制的地址。

### 用 AgentCore Identity 与 Secrets Manager 存储凭证

AgentCore Identity 在四个层面处理安全。我们将在接下来的小节中逐一介绍。

#### 1. 使用 IAM 或 SigV4 进行入站身份验证

对于 AgentCore payments 的入站访问，开发者配置 AWS Identity and Access Management（IAM）或 SigV4。该服务内置的四角色 IAM 模式把控制平面（用于管理和配置 AgentCore payments 的 API）与数据平面（用于执行交易的 API）分离。

在控制平面上，*ControlPlaneRole* 负责管理服务，*ManagementRole* 负责配置支付管理器与会话。*ManagementRole* 对 *ProcessPayment* 带有显式的 Deny，因此开发者用于配置支付的凭证无法同时执行交易。

在数据平面上，*ProcessPaymentRole* 执行支付，服务本身则代入 *ResourceRetrievalRole*，在运行时获取会话与凭证状态。没有任何单一角色既能提高预算、又能按该预算支出。

#### 2. 用于调用钱包提供商的开发者凭证

当 AgentCore payments 代表最终用户调用 Coinbase Developer Platform 或 Stripe Privy 时，它使用开发者凭证，例如 Coinbase Developer Platform API 密钥、Stripe Privy 应用凭证以及 Privy 授权密钥。AgentCore Identity 将这些凭证存放在其 token 保管库中，并使用 AWS Key Management Service（AWS KMS）在静态存储和传输过程中加密。该保管库与 AWS Secrets Manager 原生集成，因此开发者可以用其安全团队已经在用的工具来管理轮换与访问策略。agent 代码不会直接处理这些开发者凭证。

#### 3. 最终用户钱包地址保存在钱包提供商侧

与上一节中的开发者凭证不同，每个最终用户都有一个嵌入式钱包（Coinbase Developer Platform 钱包或 Stripe Privy 钱包），各有自己的自托管钱包地址。该钱包地址及其控制密钥保存在最终用户与钱包提供商处，AWS 和开发者都不会持有。AgentCore payments 通过句柄（handle）引用钱包，而不是通过密钥。

#### 4. 为每笔支付签发即时 token

当 AgentCore payments 需要执行支付时，它通过 *GetResourcePaymentToken* API 向 Identity 申请一个限定范围的 token。该 token 在运行时签发，绑定到支付会话，仅用于那一次操作。不存在长期开放的支付通道。会话的 TTL 或预算用尽后，运行时会拒绝后续交易；用于调用钱包提供商的 token 只在该操作需要的时间内存在。

### 带外充值让 agent 远离敏感数据

最终用户为钱包充值时，会在钱包提供商托管的入金通道（onramp）内输入信用卡、借记卡或银行信息，即 Coinbase WalletHub 或 Stripe Privy 前端。这些界面由钱包提供商运营，并纳入其 PCI 范围。agent 既没有接入它们的 API，也没有访问它们的 UI 权限。卡号、有效期、CVV 或自动清算所（Automated Clearing House，ACH）信息都不会触及 agent 代码、agent 的 prompt 上下文，也不会触及开发者运营的 AWS 服务。

这种隔离之所以重要，是因为它限定了影响范围（blast radius）。通过 prompt injection、被投毒的工具响应或模型异常行为而被攻陷的 agent，无法从一个它本就无权访问的系统中提取卡号。PCI 负担留在钱包提供商一侧。agent 唯一操作的对象，是一项限定范围、可撤销的许可——从最终用户的嵌入式钱包中支出稳定币或法币；即便这项许可，也受上一节所述会话限额的约束。

从合规角度看，这种设计让开发者可以上线 agentic 支付流程，而不必把自有系统纳入 PCI 范围。agent 的暴露面与开发者的合规范围都被刻意做得很小。AWS 本身不参与资金流转：资金通过钱包提供商的基础设施，在最终用户的嵌入式钱包与商户之间流转。

### 借助 AgentCore Observability 获得端到端洞察

AgentCore payments 与 AgentCore Observability 集成，让开发者能够洞察支付生命周期。对于每次数据平面 API 调用，该服务会自动向你的 Amazon CloudWatch 日志组发送 vended 日志，并向 AWS X-Ray 发送 vended span。

每一次 ProcessPayment 调用，无论是成功、触及预算上限，还是在钱包层失败，都会带着足够详细的记录，使你无需复现即可定位问题。开发者可以监控交易成功率、跟踪各 agent 的支出模式，并在错误发生时立即将其暴露出来。

支付 trace 使用开发者已经依赖的、用于观察 agent 行为的同一套可观测性基础设施。支付活动与工具调用、模型调用和编排步骤出现在同一条时间线上。运维团队可以针对错误率或支出速度设置 CloudWatch 告警，及早捕捉异常。

AgentCore Observability 附带预构建的看板，可按 agent、会话与时间段展示端到端的交易健康状况。由于支付遥测也会流入 CloudWatch 与 X-Ray，开发者可以自行构建看板。单个 CloudWatch 看板就能呈现各 agent 的总支出、按原因分类的拒绝率（预算耗尽、策略拒绝、凭证过期）以及支付延迟的分位数。这让财务、安全与合规团队无需自建报表基础设施，即可获得所需的可审计性。

## 结论

使用 AgentCore payments：

- agent 无法访问最终用户的资金或支付工具。
- IAM 与 SigV4 对每次入站调用强制执行授权，而四角色模式把控制平面（配置支付）与数据平面（执行支付）分离，使任何单一角色都无法既提高预算又按该预算支出。
- 按会话的支出限额与 TTL 在基础设施层强制执行——确定性地、在 agent 代码之外执行——因此 prompt injection 无法抬高它们。
- 最终用户保留对嵌入式钱包的托管权，按自己的条件委托支出，并可随时撤销或提取资金。
- 钱包凭证存放在 AWS KMS 加密的 token 保管库中，仅以即时签发的、与会话绑定的短期 token 形式到达 agent。
- AgentCore Observability 可以自动把每笔交易发送到 Amazon CloudWatch 与 AWS X-Ray，为安全与财务团队提供完整的审计轨迹。
- 资金通过钱包提供商的基础设施、而非 AWS，在最终用户的嵌入式钱包与商户之间流转。

有了这些护栏，agentic 支付就成为一种有边界、可审计、可用于生产环境的托管能力。
