# 真实场景推理：Amazon Nova 2 Lite 如何应对复杂的客户支持场景

人工智能（AI）的推理能力决定了模型能否处理超越简单模式匹配的复杂真实任务。具备强推理能力时，模型能够从模糊的描述中识别问题、在相互竞争的约束条件下执行策略、针对敏感情境调整语气，并给出解决根因的完整方案。而缺乏稳健推理能力时，AI 系统一旦面对需要判断力、情境感知和多步问题求解的微妙场景，就会失效。

本文使用若干检验上述关键维度的实际场景，评估 Nova 家族中最新成员 [Amazon Nova 2 Lite](https://aws.amazon.com/ai/generative-ai/nova/understanding/) 的推理能力。我们将其表现与 Nova 家族的其他模型——Lite、Micro、Pro 和 Premier——进行对比，以阐明最新版本如何在推理质量与一致性上取得进展。

## 方案概览

我们在五个客户支持场景中评估五个 Amazon Nova 模型，并从八个维度衡量其表现：

- 问题识别
- 方案完整性
- 策略遵守
- 事实准确性
- 共情与语气
- 表达清晰度
- 逻辑连贯性
- 实用价值

一个独立的评估模型（[gpt-oss-20b](https://huggingface.co/openai/gpt-oss-20b)）提供自动化、无偏见的评分。

评估架构使用相同的区域：us-east-1，并自动处理不同的 API 格式：Nova 使用 Converse API，gpt-oss-20b 使用 OpenAI Chat Completions。

示例 notebook 可在 [GitHub 仓库](https://github.com/aws-samples/sample-amazon-nova-reasoning-eval) 中获取。

## 测试场景

为生成场景评估数据集，我们在 Amazon Bedrock 上使用 Anthropic 的 [Claude Sonnet 4.5](https://aws.amazon.com/bedrock/anthropic/) 生成 100 个与常见客户支持交互相关的场景样本。我们不使用任何 Nova 模型来生成场景，以避免任何偏见。随后我们随机选取五个场景用于测试，这些场景检验常见的真实推理挑战：

- **愤怒客户投诉** – 检验当客户因配送延迟和服务不佳而威胁要离开时的降级安抚、共情与问题解决能力。
- **软件技术问题** – 评估当应用在上传照片时崩溃、且已尝试基础排查的情况下，模型的技术故障排查能力。
- **账单纠纷** – 评估针对可能表明未授权访问的可疑收费的调查能力与安全意识。
- **产品缺陷报告** – 衡量针对一件已使用两个月的缺陷产品的保修政策应用与客户服务。
- **账户安全疑虑** – 检验针对未授权密码更改与欺诈性购买的紧急响应与安全流程。

每个场景都包含需要识别的关键问题、必需的解决方案以及相关策略——为评估提供客观标准。根据你所处的行业／领域／用例不同，场景及相关上下文可能有所不同。

## 实现细节

该评估框架建立了一套综合方法，用于同时评估模型在多个维度上的表现。这种系统化方法确保每个模型都在完全相同的测试条件下接受检验，从而能够在 Nova 家族内部公平地比较推理能力。技术实现上处理了管理不同 API 格式的复杂性，同时保持评估的一致性。该框架假定已有可用的 AWS 账户、对 Nova 模型和 gpt-oss-20b 的访问权限，以及 boto3 SDK 和 pandas、matplotlib、seaborn、scipy 与 numpy 包的可用性。

### 模型调用

系统会自动检测每个模型需要哪种 API 格式，并据此路由请求。Nova 模型（Lite、Micro、Pro、Premier）使用 Amazon Bedrock Converse API，它提供了用于对话式交互的统一接口。gpt-oss 模型使用 OpenAI Chat Completions 格式，需要通过 InvokeModel API 构建不同的请求结构。调用函数会检查模型标识符以确定合适的格式。对于 gpt-oss 模型，它构造一个包含 messages、token 上限和 temperature 设置的 JSON 请求体，然后解析响应以提取生成内容。对于 Nova 模型，它使用带结构化消息对象和推理配置参数的 Converse API，从输出消息内容中提取响应。这种双 API 方案支持跨不同模型家族的无缝评估，无需单独的代码路径或手工配置更改。同一套评估逻辑适用于所有模型，无论其底层 API 要求如何，系统会透明地处理格式差异。该架构还允许我们在使用不同区域模型的同时维持单一评估工作流。本评估未使用 Nova 模型的扩展思考（extended thinking）。

该评估框架使用由 [Amazon Bedrock Prompt Optimizer API](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-management-optimize.html) 生成的优化提示词。优化器会分析并重写原始提示词，通过更好的结构、清晰度与组织性提升模型表现，并为每个 Nova 模型生成针对该模型的优化。

### 评估框架

评估器会接收场景、模型响应与评估标准。我们采用两步评分流程：首先，评估器给出最能描述该响应的类别标签；然后，评估器给出与该类别标签对应的预定分数。这种方法确保所有模型响应的评分方法一致且统一。

### 统计分析

我们使用的统计评估遵循 Miller, 2024 中概述的方法。为量化模型性能估计中的不确定性，我们按如下方式计算标准误（SE）：

> SE = √(σ^2/n),

其中 σ^2 是样本方差，n 是样本量。SE 衡量我们对均值估计的精确程度，并告诉我们如果重复评估多次，样本均值会有多大波动。标准误使我们能够构造 95% 置信区间（CI = μ± 1.96×SE），其中 μ 是样本均值。这为真实模型性能提供了合理范围，并通过区间重叠分析便于进行统计显著性检验。此外，我们引入一个基于变异系数（CV）的一致性分数，计算方式为 (100 – CV%)，其中 CV% = (σ/μ)×100，σ 是标准差。这将以 0-100 的量表对可靠性测量进行归一化，从而为响应稳定性提供一个直观指标。最后，零值剔除平均可防止失败的评估人为地压低分数，而可视化图表上的误差棒则透明地传达不确定性。为求完整，[GitHub 仓库](https://github.com/aws-samples/sample-amazon-nova-reasoning-eval) 中的代码还计算了其他统计量，例如最小可检测效应（展示了可靠检测有意义性能差异的能力）、用于识别模型响应之间相关性的成对模型比较指标，以及验证所选样本量的功效分析。这些方法将评估从简单的分数比较转变为具有量化不确定性的严谨实验科学，使人们能够对模型性能差异得出有把握的结论。

## 关键发现

评估结果为模型选择与部署策略揭示了关键洞见。这些发现强调应考量多个性能因素，而不是只关注总体分数，因为最优选择取决于具体的应用需求与运行约束。

- **多维推理很重要：**在准确性上得分高但在共情或清晰度上得分低的模型，不适合面向客户的应用。Nova Lite 2 在所有维度上的均衡表现使其可以投入生产。
- **一致性预示生产成功：**与其他模型相比，Nova 2 Lite 的低变异性说明其在多样场景下表现可靠——当不一致的响应损害用户信任时，这一点至关重要。
- **真实场景评估揭示实际能力：**合成基准会遗漏共情、策略遵守和实用价值等关键维度。该框架能够显现与生产相关的能力。

## 实施考量

要成功实施这套评估框架，需要关注那些对评估质量与成本效益有显著影响的运行因素。评估方法、评分机制与技术基础设施的选择，会直接影响结果的可靠性与可扩展性。
