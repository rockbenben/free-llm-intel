# KnowledgeForge：从 ITSM 工单坟场中淘金

[KnowledgeForge](https://github.com/aws-samples/sample-knowledgeforge) 要做的是从 IT 服务管理（ITSM）的工单坟场中淘金：那些已解决的事件工单里，沉睡着从未进入知识库文章的知识。企业 IT 支持团队每个月要解决数千张工单，而每一张都携带着有用的东西：一个现象、一个根因，以及工程师所采取的修复措施。这些知识始终被锁在工单历史里，下一个遇到同样问题的工程师根本找不到它。

知识库本身则面临相反的问题。它在增长，但增长得杂乱：重复文章不断堆积，内容逐渐过时，质量高低取决于每篇文章的作者是谁、写于何时。支持工程师检索一个答案，却要在近乎雷同的草稿之间跋涉，其中一些准确，另一些已经落后了三个产品版本。

我们构建 KnowledgeForge，正是为了同时补上这道缺口的两端。它从已解决的事件工单中挖掘新文章；与此同时，它通过按类型分类、去除重复、质量评分和重写薄弱内容来治理现有知识库。知识管理员会审核并批准最终结果，因此上线什么内容仍然由人来决定。

本文介绍 KnowledgeForge 背后的 AWS 构件：[Amazon Bedrock](https://aws.amazon.com/bedrock/) 负责生成与内容改进，[Amazon S3 Vectors](https://aws.amazon.com/s3/features/vectors/)（Amazon Simple Storage Service（Amazon S3）的一项能力）负责重复检测，[AWS Step Functions](https://aws.amazon.com/step-functions/) 负责编排。我们会逐一说明为什么选择它们，并给出文档链接。如果你正在[生成式 AI](https://aws.amazon.com/ai/generative-ai/)上构建大规模的文档处理 pipeline，这些模式可以直接复用。

## 前提条件

要部署本文的解决方案并跟随实践，你需要：

- 一个可访问 Amazon Bedrock 的 AWS 账户，并且已为 Anthropic Claude Sonnet 4.5 和 [Amazon Titan Text Embeddings V2](https://aws.amazon.com/bedrock/amazon-models/titan/) 模型开通访问权限。
- 创建该解决方案所用资源的权限：[Amazon S3](https://aws.amazon.com/s3/) 存储桶和 Amazon S3 Vectors 索引、AWS Step Functions 状态机、[AWS Lambda](https://aws.amazon.com/lambda/) 函数、运行在 [AWS Fargate](https://aws.amazon.com/fargate/) 上的 [Amazon Elastic Container Service（Amazon ECS）](https://aws.amazon.com/ecs/) 服务、[Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 表、[Amazon Simple Queue Service（Amazon SQS）](https://aws.amazon.com/sqs/) 队列、Amazon Bedrock 护栏，以及 AWS Key Management Service（AWS KMS）密钥。
- 已安装 AWS Cloud Development Kit（AWS CDK），并熟悉 Amazon Bedrock、AWS Step Functions、Amazon ECS 和向量嵌入。
- [aws-samples/sample-knowledgeforge](https://github.com/aws-samples/sample-knowledgeforge) 仓库中的代码。

## 闭环式知识库生命周期

KnowledgeForge 由两个相互供给的子系统构成。生成把聚类后的事件工单变成新的文章草稿：当一组相关工单描述的是同一个问题时，系统会依据该聚类写出一篇知识库文章和一份根因分析文档。治理随后让每一篇文章——无论是新生成的还是已有的——依次走过四个步骤：按类型分类、检查是否重复、质量评分、改进薄弱内容。完成后的文章会送到 ServiceNow，供知识管理员审核。

之所以构成闭环，是因为治理会为每篇文章存下一个向量，而生成在写任何新内容之前会把这些向量读回来。下图展示两个子系统如何连接。

图 1：闭环式知识库生命周期。数据摄取为生成和治理提供输入，知识管理员审核输出，治理为每篇文章生成嵌入，使生成在下一轮运行时可以复用这些向量作为 grounding。

从高层看，一篇文章要经过五个阶段：

- **数据摄取 **– 已解决的工单和现有文章落到 Amazon S3，并由数据目录跟踪。
- **生成 **– 聚类后的工单在运行于 AWS Fargate 的 Amazon ECS 上变成新的文章草稿。
- **治理 **– 每篇文章通过运行在 AWS Lambda 上的 AWS Step Functions 工作流完成分类、去重、质量评分和改进。
- **人工审核 **– 加工后的文章送往 ServiceNow 由知识管理员批准，审核决定会写回 Amazon DynamoDB。
- **闭环 **– 治理把每篇文章嵌入到 Amazon S3 Vectors 索引，生成在下一轮运行时复用这些向量。

两个子系统运行在不同的计算资源上，原因会在接下来跟踪一篇文章走完整个系统的过程中逐步说明。

## 从事件工单聚类生成文章

生成从一组主题相同的工单开始。上游流程按已解决事件所描述的问题对它们分组，并把结果以 JSON 文件的形式放进 Amazon S3 存储桶，范围限定为单个客户。每个主题都带有若干关键词、一个文章范围，以及工单描述和处理备注的样本。

存储桶中出现新文件会向 Amazon SQS 队列发送一个事件。运行在 AWS Fargate 上的 Amazon ECS 容器轮询该队列、读取文件，并为单个客户同时处理最多五个主题。

在动笔之前，系统先以已有内容为 grounding。对每个主题，它从该客户的 Amazon S3 Vectors 索引中检索出五篇最相似的现有文章，并作为参考上下文传给模型。这种检索增强生成（RAG）能保持术语一致，并减少编造出来的操作步骤。当尚不存在可参考的文章时，系统仅依据工单数据生成，并把其中的操作步骤标记为待审核。

生成使用 Amazon Bedrock 中的 Anthropic Claude Sonnet 4.5。对每个主题，模型产出两份结构固定的文档：

- **知识库文章**：标题与摘要、现象、根因、解决步骤、预防措施和相关主题。
- **根因分析文档**：执行摘要、问题描述、客户影响、五问（five-why）分析、临时规避方案与解决方案、纠正与预防措施、关键事件时间线，以及原因代码。

我们使用 Amazon Bedrock 的响应流式传输，让容器在 token 到达时逐步拼装每份文档，而不是等整个响应返回。

### 为什么用容器而不是函数

我们在运行于 AWS Fargate 的 Amazon ECS 上执行生成，原因在于这项工作的形态。为一个主题生成两份完整文档可能要花几分钟，而一个繁忙的文件里包含许多主题，因此单个工作单元可能运行很久。负载还是突发式的：一段时间没有动静，然后一次涌来一大批。一个长时间运行的容器服务，按队列深度扩缩任务数量、在队列排空后缩容，非常契合这种模式。

[AWS Fargate](https://aws.amazon.com/fargate/) 符合这一画像。它以无服务器方式运行我们的容器，随主题到达按需扩缩，并让团队专注于生成逻辑而不是管理计算容量。每份文档都以 JSON 形式落到 Amazon S3，随时可供治理使用。

## 使用 Amazon S3 Vectors 查找重复文章

治理的第一个挑战是判断某篇文章是否已经存在。重复有多种形态：两篇文章用不同措辞描述同一个修复方案，一篇较新的文章取代了较旧的文章，或者工程师复制了一篇文章、改了两行、然后把它当作新文章保存。

我们选择 Amazon S3 Vectors 来解决这个问题。它把嵌入向量直接存储在 Amazon S3 中，从而免去独立的向量数据库。它在每个向量旁保留元数据以支持按客户过滤，并按查询次数和每 GB 计费，而不是按运行节点计费，因此为库中每篇文章都保留一个向量也负担得起。如果你已经把内容存放在 Amazon S3 中，无需新增基础设施就能加上向量搜索。详情请参阅 [Amazon S3 用户指南](https://docs.aws.amazon.com/AmazonS3/latest/userguide/)。

关键词匹配会漏掉这些重复形态，因此 pipeline 按语义匹配。每篇文章都会由 Amazon Titan Text Embeddings V2 生成一个 1,024 维的嵌入，存放在按客户划分的 Amazon S3 Vectors 索引中。向量库通常用于支撑检索，而在这里，同一个索引同时充当重复检测器。新文章被嵌入后，系统会在索引中查询最近的现有向量，凡落在一个很紧的余弦距离阈值之内的一律算作重复。我们从余弦距离 0.05（相似度 0.95 或更高）和 top-K 为 5 起步。我们通过抽样被标记的配对来调校该距离，把它逐步收紧，直到近乎相同的文章能命中，而仅仅是相关的文章不会被抓进来。阈值放宽会产生误判重复，收紧则漏掉改写过的副本。该查询只需一次调用，并按当前客户和处于活跃状态的文章进行过滤：

```
response = s3vectors.query_vectors(
    vectorBucketName=VECTOR_BUCKET,
    indexName=VECTOR_INDEX,
    queryVector={"float32": embedding},
    topK=TOP_K + 1,  # +1 because the article can match itself
    returnMetadata=True,
    returnDistance=True,
    filter={"$and": [
        {"tenant_id": {"$eq": TENANT_ID}},  # per-customer isolation
        {"status": {"$in": ["UNIQUE", "PENDING"]}},  # ignore retired articles
    ]},
)
matches = [v for v in response.get("vectors", []) if v["key"] != article_id]
```

当系统发现一对重复文章时，会保留较新的那篇、让陈旧的那篇退役，而不是默认丢弃新来的文章。最新且准确的版本胜出，这正是支持工程师所期望的行为。

以这种方式复用索引在重试时也有好处。生成嵌入需要消耗一次模型调用。重跑时读回已存储的向量，而不是重新计算，能为整批重跑节省时间和 Amazon Bedrock 开销。

## 用 AWS Step Functions 大规模编排治理

治理要处理一批批文章，需要编排才能把工作分散到多个 worker 并从失败中恢复。AWS Step Functions 用两阶段的分布式 map 提供了这种能力。它管理工作流状态、执行定义中声明的重试与错误处理，并在不需要自定义协调代码的情况下把工作分发到多个 worker。关于分布式 map 的工作方式，请参阅 [AWS Step Functions 开发人员指南](https://docs.aws.amazon.com/step-functions/latest/dg/)。

有两处配置值得点出。第一，我们把 item processor 设为 `STANDARD` 而不是 `EXPRESS`。每篇文章都会发起长时间运行的 Amazon Bedrock 调用，会超出 `EXPRESS` 的 5 分钟限制，而 `STANDARD` 会保留完整的执行历史以便调试。第二，我们把 `ItemReader` 指向 Amazon S3 中的一个清单文件，而不是内联传入条目，从而让工作流状态保持很小。

[Amazon EventBridge](https://aws.amazon.com/eventbridge/) 上的每日计划会启动这次运行。一个 AWS Lambda 函数找出有新文章或文章发生变更的客户，把这些变更分组成批次，并把每个批次放到 Amazon SQS 的先进先出（FIFO）队列上。FIFO 队列以客户 ID 作为消息组键，按客户在多次运行之间对批次排序，因此不同客户之间仍然并行执行。跨运行排序只是故事的一部分。在单次执行内，Phase 2 可以并发处理最多 40 个批次，所以仅靠 FIFO 并不能阻止不同批次中的两处重复相互竞争。真正保护去重的是：去重在 worker 内按批次顺序执行，而质量评分与改进并行执行。每批次内串行去重、质量评分与改进并行、以及由 FIFO 保证的跨运行排序，这三者合起来保持了重复检测的一致性。

一个 dispatcher 函数一次取出一个批次并启动一个 Step Functions 执行。状态机分两个阶段运行，每个阶段都是一个分布式 map，使一个批次内的文章并发处理：

- **分类与嵌入 **– 每篇文章按类型分类，并获得一个向量嵌入。
- **去重、评分与改进 **– pipeline 查找重复、给出质量评分，并改进低于阈值的内容。

下图展示了触发链路、两个阶段，以及保护单次运行的容错机制。

图 2：治理以两阶段分布式 map 运行。批次通过 Amazon SQS FIFO 队列按客户排序，文章内容以 Amazon S3 指针而不是内联状态传递，断路器与死信队列则防止某个坏批次拖住整次运行。

### 传递指针，而不是载荷

一次 Step Functions 执行会在各状态之间携带状态数据，上限为 256 KB。带有完整 HTML 正文的知识库文章很快就会突破这个限制。我们没有把文章内容在整个状态机里一路传递，而是把批次写入 Amazon S3，只在工作流中传递位置。每个 map worker 直接从 Amazon S3 读取自己需要的内容，因此无论文章多大，状态载荷都保持很小。

分布式 map 从 Amazon S3 中的清单读取工作条目，而不是从内联状态读取。一个可容忍失败百分比让这次运行能吸收少量坏文章，而不至于中止整个批次：

```
"Phase1_ClassifyEmbed": {
    "Type": "Map",
    "ItemProcessor": {
        "ProcessorConfig": { "Mode": "DISTRIBUTED", "ExecutionType": "STANDARD" }
    },
    "ItemReader": {
        "Resource": "arn:aws:states:::s3:getObject",
        "ReaderConfig": { "InputType": "JSON" },
        "Parameters": { "Bucket.$": "$.bucket", "Key.$": "$.manifest_key" }
    },
    "MaxConcurrency": 40,
    "ToleratedFailurePercentage": 10
}
```

### 从失败中恢复

有两套机制防止一个坏批次拖垮整次运行：

- **死信队列 **– 反复失败的批次会被放到一边等待排查，而不是阻塞它后面的队列。
- **断路器（尽力而为） **– 连续失败三次后，dispatcher 停止启动新批次，并把受影响的文章重置回初始状态。失败计数器存在于热 Lambda 函数的内存中，因此不会在并发的 dispatcher 容器之间共享，并会在新任务启动时重置。在交错的多租户负载下，断路器可能不会触发，所以我们把它视为尽力而为的兜底，而不是保证。无论哪种情况都不会丢东西：下一次计划运行会接走被重置的文章，而断路器触发则表明某个服务依赖需要先行关注。

## 让 Amazon Bedrock 在大规模下可靠运行，并提升文章质量

工程的着力点在于：在共享的服务配额下并发运行数万次模型调用。pipeline 通过 Amazon Bedrock 的模型推理访问 Anthropic Claude Sonnet（用于生成与改进）和 Amazon Titan Text Embeddings V2（用于去重向量）。关于各 AWS 区域的模型可用情况，请参阅[按 AWS 区域提供的受支持模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

### 让模型调用不越出限制

三项控制措施让生成在负载下保持可预测：

- **硬性 wall-clock 超时**：每次执行都设超时，慢响应无法无限期占住一个 worker。
- **带退避的自动重试 **– Amazon Bedrock 客户端以自适应模式运行，遇到限流时自行重试，对耗时较长的内容改进调用采用指数退避。
- **护栏回退 **– 我们对模型输出运行 Amazon Bedrock 护栏，以过滤非预期内容。护栏是一项生产控制措施，下面这种回退是一种弹性手段，用于在正常条件下让护栏继续生效，并不是说明护栏可选。

护栏 API 有自己的速率限制。一旦它被限流，pipeline 会在不带护栏的情况下处理这篇文章并记录一条警告，而不是直接失败，从而在流量高峰时保持运转。在代码中，这个回退就是模型调用封装里的一小段：

```
try:
    return converse_with_timeout(kwargs, BEDROCK_CALL_TIMEOUT)
except ClientError as e:
    if "ThrottlingException" in str(e) and guardrail_config:
        log.warn("Guardrail throttled, retrying without guardrail")
        del kwargs["guardrailConfig"]
        return converse_with_timeout(kwargs, BEDROCK_CALL_TIMEOUT)
    raise
```

第四项控制处理被截断的输出。内容改进的响应有 token 预算，长文章可能把它用尽，导致 JSON 响应被截断。系统会检测「在 token 上限处停止」的信号，并以双倍预算重试，直到模型的上限。短文章永远不会走到这条路径，因此常见情况下不会为这层安全网付出任何代价。

### 在改进前后分别做质量评分

并非每篇文章都需要改进，而改进也不总是有效。这由一个质量评分来决定。每篇文章会沿十个带权重的维度打分，从权重最高到最低依次为：

- 完整性
- 可操作性
- 结构
- 连贯性
- 可读性
- 自助服务价值
- 时效性
- 自动化就绪度
- 语法
- 安全性

加权总分得出一个分数，由阈值决定文章是原样达标，还是进入改进环节。阈值可配置，因此客户可以对生成内容要求比导入内容更高的门槛。

低于阈值的文章会进入内容改进，同样运行在 Amazon Bedrock 上。这一步有个实际难题：被要求改进文字表述的模型，常常会连图片标签和超链接一起改，并把它们弄坏。占位符解决了这个问题。在改进之前，系统把每个图片和链接替换成带编号的 token，围绕这些 token 改进文字，然后再把真实的媒体换回去。模型始终看不到原始标记，因此标题与结构得以保全。

在代码中，这是夹住改进调用的一对函数。前一个把每个媒体标签和链接替换成带编号的 token，并记录下被替换掉的内容；后一个在模型返回后把原始内容放回去：

```
# Before improvement: swap media/links for [IMG_N] / [LINK_N] tokens
html_with_placeholders, placeholder_map = extract_placeholders(article_html)

enriched = improve_with_bedrock(html_with_placeholders)  # model never sees raw markup

# After improvement: restore the exact original tags in place
restored_html, missing = restore_placeholders(enriched, placeholder_map)
```

由于模型只会看到 `[IMG_1]` 或 `[LINK_3]`，它无法破坏 URL 或图片引用。恢复步骤让已发布文章的媒体与最初完全一致。

改进之后，文章会再次评分。只有当新版本的分数超过原始版本时才保留新版本，否则保留原始版本。这种前后对比检查让 pipeline 能自动改进内容，而不会悄悄把知识库改得更差。

## 安全地服务多个客户

系统在共享基础设施上运行多个客户，而知识库恰恰是客户期望被严格隔离的数据。隔离从一开始就设计在内：每个客户都拥有与其内容相关的每一项资源的独立副本：

- 一个配置档案
- 一个 Amazon S3 Vectors 索引
- 一组模型 prompt
- 一个 Amazon Bedrock 护栏
- 一个 [AWS KMS](https://aws.amazon.com/kms/) 加密密钥

由于这些资源按客户划分，每个客户的数据都留在自己的边界内。重复检查只针对该客户的索引运行，内容改进使用该客户的 prompt，数据以该客户的密钥加密。不存在共享池，因此一个客户的文章不可能出现在另一个客户的结果里。

接入一个客户并不意味着要编辑一张中央清单。系统在运行时从数据目录发现客户，因此新增客户只需为其预置资源，无需改动 pipeline 代码。

## 结果与经验教训

这里描述的表现来自我们的内部测试，并非有保证的服务水平。由于每个客户都有自己流经的 Amazon SQS FIFO 消息组，新增客户等于增加一条并行的工作流，而不会拖慢其他客户。你自己的吞吐量将取决于文章大小、模型延迟以及你的 Amazon Bedrock 配额。

一次有代表性的运行展示了你可以预期的模式。大部分文章在第一轮就完成了完整处理，一小部分被留待改进，更小的一部分作为重复被移除。运行结束时没有死信队列消息，也没有超时。少数文章触及内容改进的 token 上限，被自动重置，并在下一轮以更高的预算重试，而不是直接失败。最后这种情况很重要，因为它说明这些弹性控制把原本会是硬失败的场景变成了自动重试。

有四条经验格外突出。把向量索引复用为重复检测器，把一个难题变成了最近邻查询。通过 Step Functions 传递 Amazon S3 指针而不是文章正文，消除了一类状态体积导致的失败。在改进前后都做质量评分，让自动运行变得安全。把护栏限流当作警告来处理，使 pipeline 在负载高峰中保持健康。更大的要点在于闭环本身：生成的内容反哺治理，治理又为下一轮生成提供 grounding，于是知识库随着系统运行而不断改善。

## 清理资源

本解决方案中的资源都是计费的，完成后请将其删除以免产生持续费用。删除两个 AWS CDK 栈（一个用于知识库生成，一个用于知识库治理）就能移除其中大部分资源，包括 AWS Lambda 函数、AWS Step Functions 状态机、运行在 AWS Fargate 上的 Amazon ECS 服务、Amazon SQS 队列以及 Amazon DynamoDB 表。

少数资源需要手工处理，因为它们存放数据或是按客户创建的：

- **Amazon S3 Vectors 索引与向量桶 **– 逐个删除按客户划分的索引，然后删除向量桶。
- **Amazon S3 存储桶 **– 清空并删除源、输出和 pipeline 存储桶。
- **Amazon Bedrock 护栏 **– 如果栈把它们保留在原处，请手动删除按客户划分的护栏。
- **AWS KMS 密钥 **– 为按客户划分的密钥安排删除。
- **Amazon DynamoDB 表 **– 如果你禁用了时间点恢复保留策略，请确认指标表和文章状态表已被移除。

具体的删除命令请参阅仓库的 README。

## 结语

ITSM 工单坟场是一个看起来像数据问题的知识问题。解决方案其实已经存在，只是被困在无人能够复用的地方，旁边则是一个衰减速度快过任何团队手工治理能力的知识库。KnowledgeForge 用 AWS 上的生成式 AI 补上了这道缺口：它借助 Amazon Bedrock 把工单挖掘成文章，借助 Amazon S3 Vectors 抓出重复，并借助 AWS Step Functions 编排整个流程。上线什么内容，仍然由知识管理员掌控。

要开始构建类似的 pipeline：

- 参照 [Amazon S3 Vectors 文档](https://docs.aws.amazon.com/AmazonS3/latest/userguide/) 创建一个向量索引。
- 对自己的文章取样做嵌入并载入向量。
- 运行前文给出的最近邻查询来标记重复。
- 加入 AWS Step Functions 分布式 map 来批处理文章。
- 在其上叠加「评分—改进—再评分」的质量关卡。

完整代码可在 GitHub 上的 [aws-samples/sample-knowledgeforge](https://github.com/aws-samples/sample-knowledgeforge) 仓库中获取。文中各代码示例展示了每种模式中真正承重的部分，可直接调整以适配你自己的知识库。

想了解更多，请参阅 [Amazon Bedrock 用户指南](https://docs.aws.amazon.com/bedrock/latest/userguide/)、[AWS Step Functions 开发人员指南](https://docs.aws.amazon.com/step-functions/latest/dg/) 和 [Amazon S3 用户指南](https://docs.aws.amazon.com/AmazonS3/latest/userguide/)。
