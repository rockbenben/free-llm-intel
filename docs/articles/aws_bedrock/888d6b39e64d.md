# 基于 Amazon Bedrock 的智能驱动型消息防护与洞察

买卖双方在未经批准的渠道之外直接沟通，每年可能造成可观的收入损失，同时严重损害品牌声誉并破坏宝贵的业务关系。消息系统对现代业务运营不可或缺，也能带来丰富的客户洞察，但当各方绕过经纪（brokerage）系统直接沟通时，它们会带来重大风险。当买卖双方交换联系方式并把交易转到线下，经纪商不仅会损失眼前的收入，还会因 marketplace 价值缩水而遭受长期损害。在经纪业务中这一挑战尤为尖锐，因为这类服务的核心价值就在于促成各方之间安全、可靠的连接。应用内消息可以传达重要的交易细节，例如配送位置“把货放在后门”或具体时间“只在下午 4:00 后配送”，但必须阻止直接联系方式的交换（例如电话号码、公司名称、网站或实际地址），以维持经纪商作为可信中间人的地位。不解决这个问题会引发一连串负面后果，包括佣金收入流失、服务价值下降、合作伙伴关系受损，以及需要多年才能重建的行业地位削弱。

在本文中，你将了解如何在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 中使用 [Amazon Nova Foundation Models](https://aws.amazon.com/ai/generative-ai/nova/)，把生成式 AI 技术同时用于业务防护与业务增强。你可以识别明显以及伪装的直接联系尝试，同时获得关于客户情绪与服务改进机会的宝贵洞察。

## 正则表达式

使用正则表达式（regex）可能是你最先想到的方案，因为它擅长模式匹配与文本操作，为搜索、校验与转换文本数据提供了强大而简洁的方式。regex 在处理电子邮箱地址、电话号码和日期这类结构化模式时表现出色。联系方式遵循可预测的模式：电话号码使用 `XXX-XXX-XXXX` 格式，电子邮箱地址则遵循 name@company.com。正则表达式有助于在文本中识别这些模式。对美国的电话号码，regex 模式 `\d{3}-\d{3}-\d{4}` 匹配三个数字、一个连字符、再三个数字、另一个连字符，以及四个数字。

然而，面对现代文本的复杂情形，regex 表现出明显的局限：HTML 解析（因为嵌套结构与标记写法的差异）、emoji 识别（因为 Unicode 的复杂性以及各服务间 emoji 表示的差异），以及像社交媒体 handle 或不断变化的 URL 这类不断演进的模式。当人们刻意用不断变化的欺骗手法隐藏联系方式时，regex 就显得力不从心。例如，一条写着“Congratulations. Here are some more details 555inches 555inches 5555inches”的消息，显然是在把电话号码伪装成尺寸数据。由于模式已知，像 `(\d+)inches\s+(\d+)inches\s+(\d+)inches` 这样精密的 regex 模式可以有效揭开用“inches”作为诱饵计量单位隐藏的电话号码。但如果模式并不像使用已知计量标识那样简单呢？检测隐藏联系方式的挑战超出了简单模式匹配的范畴，需要更动态的手段。规避手法不断变化，例如用单词替代数字、改用其他单位、变换分隔符，以及把 leetspeak 与 emoji 组合起来。传统 regex 模式难以处理拼写出来的数字、创造性的符号用法（把“@”写成“at”）、依赖上下文指代的公司名称，以及复杂的 leetspeak 组合。

regex 尤其难以胜任高级文本分析需求，例如情绪检测、上下文理解，或识别文本中的用户行为与意图。例如，regex 能找到特定词语，却无法理解情绪基调，也无法判断用户消息是否需要后续处理。当模式变得复杂或需要频繁更新时，regex 的维护会变得困难且易错，往往产出脆弱的方案，一旦文本格式演进就会失效。针对这些场景，可考虑使用 Amazon Bedrock 这类生成式 AI 方案。Amazon Bedrock 提供成熟的语言模型，能够理解上下文、解析复杂结构，并在无需持续人工更新的情况下适应不断演进的文本模式。

## 生成式 AI

Amazon Bedrock 是一项完全托管、无服务器的服务，提供来自领先公司的多种高性能 AI 基础模型。你可以用 Amazon Bedrock，借助熟悉的 AWS 服务来试验、定制生成式 AI 能力，并把它们集成到应用中。Amazon Bedrock 还在 AWS 控制台提供 playground 功能，用于测试 prompt 和多个 LLM。

要在 AWS 控制台上访问 Amazon Bedrock 模型并编写 prompt，你需要：

- 一个有效的 AWS 账户
- 合适的 [IAM permissions](https://docs.aws.amazon.com/bedrock/latest/userguide/security-iam.html)
- 熟悉 AWS 管理控制台
- 对 prompt engineering 概念有基本理解

借助 AWS 管理控制台上的 [Amazon Bedrock playground](https://docs.aws.amazon.com/bedrock/latest/userguide/playgrounds.html)，我们可以在 Single Prompt 模式下用 Chat/Text playground 试验 prompt engineering。使用 Amazon Nova 2 Lite 模型时，我们可以[用推理参数影响响应生成](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-parameters.html)：把响应长度调整为 1,000 tokens，并降低 temperature 设置以获得更一致的输出。

下面这条示例消息用 emoji 混淆了电话号码：

```
I can get that done for you directly :five: :five: :five:-:five: :five: :five:-:zero: :one: :one: :one: .
```

对这样一个聚焦的用例，可以写一个简单的 prompt 来找出基于 emoji 的电话号码：

```
Analyze customer feedback regarding shipping orders for a brokerage and identify 
if the supplier has provided phone numbers. The text may contain emoji to disguise 
the original text.
```

把上面的 prompt 连同输入文本一起填进去，然后点击 Run 按钮。

prompt 需要指导大型语言模型（LLM）如何识别会违反经纪政策的联系方式。由于几乎不可能预测所有手法，我们不能依赖显式的格式与语法来发现隐藏信息。必须指导 Nova 2 Lite 模型去发现不同格式的电话号码、公司名称、电子邮箱地址、邮寄地址、姓名与体貌特征。真实的运输尺寸是允许的，因为那是有效信息。

```
You are a detective that must thoughtfully analyze buyer and seller correspondences 
to discover contact information that violates policy by looking for emojis, leetspeak, 
and other ways used to disguise contact information like spreading the contact 
information across the text for categories phone number, business name, email, 
mailing address, personal information such as name, appearance, etc. 
Be aggressive and creative with how you identify phone numbers. 
All contact information violates policy. Shipping measurements are to be ignored.
```

LLM 会对它为何在文本中发现这些信息给出详尽的解释。这在设计 prompt 时很有用，但对下游处理逻辑更有用的是简洁的 JSON 格式输出，包含 explanation、category 与 confidence 字段。为此，把以下内容追加到原始 prompt 中：

```
Group findings by category and provide a confidence level for each item on a 
scale of 1 to 5, with 5 being the highest confidence. Explain your reasoning 
for the categorization and confidence level. Format your response as a json 
object.
```

这个 prompt 已经可用，但让我们再改进它。[prompt optimizer](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-management-optimize.html) 工具会重写 prompt，使推理结果更契合你的用例与具体模型。重写后的 prompt 也更易读、更易理解。点击屏幕底部以红圈标出的魔棒图标（如下图所示），即可打开 prompt optimizer 工具。

## 结论

真实场景测试展示了生成式 AI 相对传统 regex 方法的优势。在对 10 条真实经纪消息的小样本测试中，生成式 AI prompt 方案在识别被混淆的联系方式上达到 100% 准确率。这种能力可以延伸到许多类型的沟通，从取消订单、反馈这类简单的客户输入，到复杂的经纪人编排。

虽然 regex 对结构化模式已足够，生成式 AI 还能提供：

- 上下文理解：能检测消息中伪装的信息。
- 适应性：无需持续更新即可识别不断演进的规避手法。
- 多维度分析：评估情绪、待办事项与政策违规。
- 置信度评分：支持更细致的决策。
- 自然语言处理：能解释 leetspeak 以及依赖上下文的指代等变体。

借助 Amazon Bedrock 这类服务为应用引入生成式 AI 能力，开发者可以构建健壮、面向未来的方案，帮助在现代数字沟通中保护公司利益。
