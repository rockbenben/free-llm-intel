# 改造，而非重建：用 agentic overlay 变革遗留企业服务

本文所述观点仅代表作者本人，不代表 Cisco 的立场。

企业架构长期以来以 [REST API](https://aws.amazon.com/what-is/restful-api/) 和微服务为核心。这些系统稳定、经过充分测试，并深度嵌入生产环境。它们并非为 [Agent-to-Agent](https://github.com/a2aproject/A2A)（A2A）通信而设计——A2A 是新兴标准，面向通过结构化消息协作、推理与协调的自主 agent。在缺少通用 agent 协议的时代，这套做法行得通，但这也意味着许多现有 agent 如今落在了新兴的 A2A 框架之外。今天的挑战已不只是为传统服务加上 A2A。你还需要把这些基于 REST 的 agent 带入标准化的 agent 间世界。

在 AWS 与作者团队的这次技术合作中，我们提出一个务实的方案：*agentic overlay*。agentic overlay 是轻薄的封装层，能把传统的基于 REST 的服务转换为可参与 A2A 交互的 agent。它还能把 REST API 暴露为与 [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro)（MCP）兼容的工具。两者结合，让企业无需重写业务逻辑、无需重复实现代码、也无需运行并行基础设施，就能为现有 REST 服务增添 A2A 能力。通过把现有服务当作 agent 复用，这一方案减少了基础设施中的 agent 泛滥。我们提供了参考架构与示例代码，展示如何构建 agentic overlay。

## 背景：REST 与 A2A

REST API 面向确定性的客户端-服务器集成。客户端调用定义明确的 endpoint，传入参数，得到可预测的响应，通常是由 HTTP 语义治理的无状态请求-响应流程。这让 REST 非常适合以清晰的契约、良好的兼容性与运维上的简洁性来暴露业务能力（例如创建、读取、更新与删除）。

A2A 则面向自主 agent 之间的互操作。agent 通过元数据（例如 agent card）相互发现、协商能力，并交换结构化消息（通常经由 [JSON-RPC](https://www.jsonrpc.org/)）来协调多步任务。REST 优化的是稳定的服务接口与直接执行，A2A 优化的则是推理驱动的协调、面向任务的消息传递与 agent 协作。由此得到的系统能够跨多个服务规划、委派并组合动作，而不是只调用孤立的 endpoint。

## 迈向 agentic 系统途中的挑战

REST API 与 agentic 系统建立在彼此正交的范式之上，这让企业很难把现有服务迁入标准化的 agentic 通信。但企业又需要在不做大改造的前提下同时使用两者。尽管通过 A2A 进行的新式 agent 通信为企业系统引入了协调模型，推广速度却因需要与现有企业系统并行部署和运维 agentic 基础设施而放缓。这种并行运行增加了运维复杂度与成本，成为有效采用 AI 的障碍。

在 A2A 标准化之前，企业通常把 agent 部署为基于 REST 的或专有协议的服务。他们把这些 agent 当作常规 API，把 agent 特有的逻辑嵌在请求-响应的 endpoint 里。结果，如今许多现有 agent 并非 A2A 原生，这就带来了新的迁移挑战：让这些 agent 在不重写核心逻辑的前提下，使用标准化的 A2A 协议互操作。

## 方案选择

本节讨论为遗留企业系统添加 agentic 能力时可以采用的几种不同方案，并将它们与使用 agentic overlay 的方案作比较。

**维护相互独立的 REST 与 A2A 栈**：一种做法是开发并维护两条并行的路径来暴露同一批能力。这可能意味着：

- 两套 endpoint：`/api/v2/...` 与 `/a2a/...`。
- 两套认证、校验与错误映射的实现（除非经过仔细复用）。
- 两条部署流水线（构建、测试、发布、回滚）。
- 可观测性工作量翻倍：两条路径都要有日志、指标与追踪。
- 不一致风险更高。同一操作由 A2A 与 REST 执行时，可能返回不同的输出。
- 长期来看成本与运维复杂度更高。

![两条并行技术栈的架构图：REST 栈含 REST endpoint，A2A 栈含 A2A endpoint，各自拥有控制器、部署流水线与可观测性工具。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/22/ML-20189-2.png)

*图 2：相互独立的 REST 与 A2A 栈*

**分离技术栈，但共享业务逻辑**：重构现有 endpoint 意味着你要改动当前 REST API 的代码结构（有时还包括行为），好让新接口（例如 A2A）能够复用。你没有让 REST endpoint 保持原样，而是重新组织它们，通常是把业务逻辑抽取到共享服务中，并更新控制器与处理器去调用这些服务。即使对外暴露的 REST 路径保持不变，重构也可能引入回归、行为漂移和沉重的测试负担。

![架构图：相互独立的 REST 与 A2A 控制器栈都通过抽取出的服务调用共享业务逻辑层。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/22/ML-20189-3.png)

## 核心思路：agentic overlay

*agentic overlay* 是一层轻薄的封装，让基于 REST 的服务能够参与 A2A 通信。这层 overlay 会：

- 把 agentic 消息转换为 REST payload，反之亦然。
- 把 REST endpoint 暴露为 agent 任务或工具。

最重要的是，A2A 并不是新的 API，而是通往现有 API 的新接口。底层的 REST 服务保持不变。

### 在应用内部添加 agentic overlay

在这种做法里，你仍然有两套 endpoint——`/api/v2/...` 与 `/a2a/...`（REST 与 A2A），如下图所示，但只有一条用于构建、测试、发布与回滚的部署流水线。借助这一模式，传统 REST API endpoint 可以在不重写核心业务逻辑的情况下转换为 agentic endpoint。服务的部署流程不变。在同一个 host、同一个端口上，你新增路由即可，不过系统可能需要扩容以应对增加的流量。

你可以直接用 agent skill 本身来做路由。MCP server 可用于调用外部服务，但 agent skill 能在 agent 作用域内直接路由请求，无需把 API 作为 skill 导入 MCP server。你手上的任何 endpoint 都可以暴露为 agent skill，而不必单独搭建 MCP server。

![架构图：agentic overlay 部署在现有应用内部，/api/v2 下的 REST endpoint 与 /a2a 下的 A2A endpoint 共享同一 host、端口与部署流水线。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/22/ML-20189-4.png)

*图 4：应用内部的 agentic overlay*

这种做法通过把现有服务复用为 agent，减少了基础设施中的 agent 泛滥。该设计模式很适合功能范围有限的 supervisor agent——它们既需要基于 REST 的能力，也需要 agentic 能力，例如意图分类与路由。

## agentic overlay 示例实现

作为概念验证，本节展示如何用一个 overlay，把基于 Flask 的遗留 REST 计算器服务示例移植为 agentic 系统。在这层 overlay 中，我们加入标准的 A2A 组件（即路由），例如 well-known agent card、agent 消息 endpoint、capabilities、skills 与 health。我们还引入一种消息转换设计模式：把 agentic 消息转换为 REST API 消息，再由 agent 发起 REST 调用。A2A 消息翻译流程如下：

- 接收 JSON-RPC 2.0 请求。
- 把 A2A 任务映射到 REST endpoint。
- 转发认证 header。
- 在内部调用 REST endpoint。
- 把 REST 响应转换为 JSON-RPC 格式。

### 第 0 步：请求-响应格式

本节用后续章节演示的计算器示例，比较 REST 与 A2A 协议的请求-响应格式。

REST 与 A2A 的输入请求：

| **REST** | **A2A** |
| --- | --- |
| { “operation”: “add”, “operands”: [5, 3] } | { “jsonrpc”: “2.0”, “method”: “SendMessage”, “params”: { “message”: { “role”: “user”, “parts”: [ { “kind”: “data”, “data”: { “operation”: “add”, “operands”: [5, 3] } } ] } }, “id”: 1 } |

REST 与 A2A 的输出响应：

| **REST** | **A2A** |
| --- | --- |
| {“result”: 8} | { “jsonrpc”: “2.0”, “result”: { “messageId”: “uuid”, “contextId”: “uuid”, “role”: “agent”, “parts”: [{“kind”: “data”, “data”: {“result”: 8}}], “kind”: “message”, “metadata”: {} }, “id”: 1 } |

### 第 1 步：搭建 agent

这一步创建计算器 agent 示例，并加载 well-known agent card 与 agent skill。`build_agent_card` 函数会动态构建 agent card。

```
"""
A2A Request Translator - Calculator Example.

This module implements the Request Translator Pattern to provide A2A
(JSON-RPC 2.0) compatibility over the existing Calculator REST API.

A2A Spec 0.3 Compliance:
- Agent Card: GET /.well-known/agent-card.json
- JSON-RPC endpoint: POST /a2a
- Methods: SendMessage, SendStreamingMessage
- Message format: { "message": { "parts": [{ "kind": "data", "data": {...} }] } }
"""

# Default A2A API URL (override via build_agent_card(url) if needed)
A2A_API_URL = "http://localhost:5000/a2a"

EXECUTE_TIMEOUT_SECONDS = 30

# Load skills from JSON file
_SKILLS_FILE = Path(__file__).parent / "skills.json"
_SKILLS_CACHE: Optional[List[Dict[str, Any]]] = None

def _load_skills() -> List[Dict[str, Any]]:
    """
    Load skills from the skills.json file.
    Skills are cached after first load to avoid repeated file reads.
    """
    global _SKILLS_CACHE
    if _SKILLS_CACHE is not None:
        return _SKILLS_CACHE
    try:
        with open(_SKILLS_FILE) as f:
            _SKILLS_CACHE = json.load(f)
            return _SKILLS_CACHE
    except FileNotFoundError:
        logger.error(f"Skills file not found: {_SKILLS_FILE}")
        return []
    except json.JSONDecodeError as e:
        logger.error(f"Invalid JSON in skills file: {e}")
        return []

def build_agent_card(api_url: Optional[str] = None) -> Dict[str, Any]:
    """Build the A2A Agent Card (v0.3.0 format) with configurable API URL."""
    if api_url is None:
        api_url = A2A_API_URL
    return {
        "name": "Calculator Agent",
        "description": "Simple calculator supporting basic arithmetic operations",
        "supportedInterfaces": [
            {"url": api_url, "protocolBinding": "JSONRPC", "protocolVersion": "0.3"},
        ],
        "provider": {
            "organization": "Example Organization",
            "url": "",
        },
        "version": "1.0.0",
        "capabilities": {
            "streaming": False,
            "pushNotifications": False,
            "extendedAgentCard": False,
        },
        "defaultInputModes": ["text/plain", "application/json"],
        "defaultOutputModes": ["text/plain", "application/json"],
        "skills": _load_skills(),
    }

# Agent Card built dynamically
AGENT_CARD = build_agent_card()
```

### 第 2 步：实现内部 REST 调用器

```
def invoke_rest_endpoint(
    endpoint: str,
    json_data: Optional[Dict] = None,
    http_method: str = "POST"
) -> Tuple[Optional[Dict], int]:
    """
    Call internal REST endpoint via real HTTP request.

    Uses requests.post/get to call the running server. This ensures
    any middleware, decorators, and headers are properly exercised.

    Args:
        endpoint: REST endpoint path (e.g. "/api/v1/calculate")
        json_data: Request body for POST/PUT
        http_method: HTTP method (GET, POST, etc.)

    Returns:
        Tuple of (response_data, status_code)
    """
    try:
        base_url = request.host_url.rstrip("/")
        url = f"{base_url}{endpoint}"

        headers = {"Content-Type": "application/json"}
        auth_header = request.headers.get("Authorization")
        if auth_header:
            headers["Authorization"] = auth_header

        logger.info(f"Adapter: Delegating to REST {http_method} {url}")

        if http_method.upper() == "POST":
            response = http_requests.post(
                url, json=json_data, headers=headers,
                timeout=EXECUTE_TIMEOUT_SECONDS
            )
        elif http_method.upper() == "GET":
            response = http_requests.get(
                url, headers=headers,
                timeout=EXECUTE_TIMEOUT_SECONDS
            )
        else:
            response = http_requests.request(
                http_method, url, json=json_data, headers=headers,
                timeout=EXECUTE_TIMEOUT_SECONDS
            )

        logger.info(f"Adapter: REST returned {response.status_code}")
        return response.json(), response.status_code

    except http_requests.RequestException as e:
        logger.error(f"Adapter: Error calling REST endpoint: {e}", exc_info=True)
        return {"error": "Internal server error"}, 500
```

### 第 3 步：实现消息 payload 提取（A2A 规范 0.3）

```
def extract_message_payload(message: Dict) -> Optional[Dict]:
    """
    Extract payload from A2A message parts (Spec 0.3 format).

    Expected format:
    {
        "message": {
            "parts": [{"kind": "data", "data": {"operation": "add", "operands": [5, 3]}}]
        }
    }

    Returns:
        Extracted data payload as dict, or None if not found
    """
    try:
        parts = message.get("parts", [])
        for part in parts:
            if isinstance(part, dict) and part.get("kind") == "data":
                return part.get("data")
        return None
    except Exception as e:
        logger.error(f"Error extracting message payload: {e}")
        return None

def build_a2a_message(message_id: str, context_id: str, content: Any) -> Dict:
    """
    Build an A2A-compliant message object (A2A Spec 0.3).

    Response format:
    {
        "messageId": "uuid",
        "contextId": "uuid",
        "role": "agent",
        "parts": [{"kind": "data", "data": {...}}],
        "kind": "message",
        "metadata": {}
    }
    """
    if isinstance(content, dict):
        parts = [{"kind": "data", "data": content}]
    else:
        parts = [{"kind": "text", "text": str(content)}]

    return {
        "messageId": message_id,
        "contextId": context_id,
        "role": "agent",
        "parts": parts,
        "kind": "message",
        "metadata": {}
    }
```

**关于用于流式传输的 Server-Sent Events（SSE）：**

前面的 `extract_message_payload()` 函数对 `SendMessage` 与 `SendStreamingMessage` 的行为相同。

对于瞬时完成的操作（例如我们的计算器），两种方法都返回单个结果。对于长时间运行的操作（例如报告生成或数据分析），SSE 流式传输允许服务器推送增量更新。

### 第 4 步：实现 JSON-RPC 响应构建器

```
# The error codes defined as per JSON-RPC 2.0 specification
class JsonRpcError:
    PARSE_ERROR = -32700
    INVALID_REQUEST = -32600
    METHOD_NOT_FOUND = -32601
    INVALID_PARAMS = -32602
    INTERNAL_ERROR = -32603

def jsonrpc_error(code: int, message: str, data: Any = None, request_id: Any = None) -> Dict:
    """Build a JSON-RPC 2.0 error response."""
    response = {
        "jsonrpc": "2.0",
        "error": {"code": code, "message": message},
        "id": request_id
    }
    if data is not None:
        response["error"]["data"] = data
    return response

def jsonrpc_success(result: Any, request_id: Any = None) -> Dict:
    """Build a JSON-RPC 2.0 success response."""
    return {
        "jsonrpc": "2.0",
        "result": result,
        "id": request_id
    }
```

### 第 5 步：SendMessage —— 从 A2A 委派到 REST

```
def handle_send_message(data: Dict) -> Tuple[Any, int]:
    """
    Handle SendMessage -- dumb pass-through to /api/v1/calculate.
    The adapter does NOT inspect or route based on payload contents.
    """
    request_id = data.get("id")
    params = data.get("params", {})
    message = params.get("message", {})
    context_id = message.get("contextId") or generate_id()
    message_id = generate_id()

    payload = extract_message_payload(message)
    if not payload:
        return jsonify(jsonrpc_error(
            JsonRpcError.INVALID_PARAMS,
            "Invalid params: No data found in message.parts.",
            request_id=request_id
        )), 400

    # Pass through payload as-is to the single REST endpoint
    rest_response, status = invoke_rest_endpoint(
        endpoint="/api/v1/calculate",
        json_data=payload,
        http_method="POST"
    )

    if 200 <= status < 300:
        a2a_message = build_a2a_message(message_id, context_id, rest_response)
        return jsonify(jsonrpc_success(a2a_message, request_id)), 200
    else:
        error_message = "Operation failed"
        if isinstance(rest_response, dict):
            error_message = (rest_response.get("error")
                             or rest_response.get("details")
                             or "Operation failed")
        error_code = (JsonRpcError.INVALID_PARAMS if 400 <= status < 500
                      else JsonRpcError.INTERNAL_ERROR)
        return jsonify(jsonrpc_error(
            error_code, error_message,
            data=rest_response, request_id=request_id
        )), status

# we need to explicitly add the routes as the a2a

def generate_id() -> str:
    """Generate a UUID for message/context IDs."""
    return str(uuid.uuid4())
```

### 第 6 步：搭建 A2A 路由（规范 0.3）

官方 A2A SDK 为 FastAPI 与 Starlette 应用提供了 A2A 库，把添加 A2A 专用路由的复杂度抽象掉。虽然 Flask 应用也有可用的 A2A 库，但我们的示例代码没有使用它们。我们希望让你直截了当地理解：在 Flask 应用之上承载一层 A2A overlay 需要做哪些事。下面的代码片段添加了 A2A 所需的路由。

```
def setup_a2a_routes(app: Flask) -> None:
    """Register A2A protocol v0.3 routes on the Flask application."""
    app.add_url_rule("/.well-known/agent-card.json", "get_agent_card",
                     get_agent_card, methods=["GET"])
    app.add_url_rule("/a2a/capabilities", "get_capabilities",
                     get_capabilities, methods=["GET"])
    app.add_url_rule("/a2a/health", "a2a_health",
                     a2a_health, methods=["GET"])
    app.add_url_rule("/a2a", "a2a_jsonrpc",
                     _handle_jsonrpc, methods=["POST"])
    logger.info("A2A Protocol v0.3 routes registered")
```

### 第 7 步：最后在应用中初始化

```
# app/main.py
from flask import Flask
from app.rest_api import rest_api
from app.a2a_adapter import setup_a2a_routes

def create_app():

```

## 使用 Amazon Bedrock AgentCore Gateway 添加 agentic overlay

Amazon Bedrock AgentCore 是一项无需管理基础设施即可大规模构建、连接与优化 agent 的服务。如下图所示，AgentCore Gateway 可以作为 endpoint 与服务的单一访问入口，从而把 agentic overlay 与应用解耦。这种分离让一个 agentic overlay 可以服务多个服务或应用，而不只是一个。AgentCore Gateway 每个 gateway 最多支持 10 个 target，可原生集成现有 AWS 服务，并支持 OpenAPI endpoint。

![架构图：AgentCore Gateway 作为单一访问入口，把一个 agentic overlay 与多个下游 REST 应用和服务解耦。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/06/22/ML-20189-5.png)

*图 5：使用 Amazon Bedrock AgentCore Gateway 解耦 agentic overlay*

企业级应用往往要编排多个服务来处理复杂任务。例如，一个计算器应用在处理「Calculate 2 * (3 + 4)」时，如下图所示，系统先查询一个运算顺序 endpoint（例如 `/api/order-of-ops/...`）来确定求值顺序，然后依次调用某个 endpoint（例如 `/api/arithmetic/...`）先算出「3 + 4」，再算出「2 * 7」。为每个服务都加一层 agentic overlay 会各自带来开销。反过来，你可以把两个服务拴在同一个 agentic overlay 上，由它按需编排这些调用。

你可以把 agentic overlay 与应用分离，从而按功能而不只按应用来组织你的 agentic overlay。这些 agentic overlay 成为与你的应用和系统交互的 agentic 方式，也是与功能交互的 agentic 方式。

除 AgentCore Gateway 之外，AgentCore 的其他能力还能简化 agentic overlay 的监控、迭代与部署。[AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-overview.html) 负责 agent 与 gateway 组件的认证，支持 OAuth 2.0 provider，并为 Okta、GitHub 与 Slack 提供托管集成。[AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-configure.html) 通过指标、日志与 span 可视化来监控 agent 性能。你可以查看工具调用与延迟等高层数据，也可以借助与 Amazon CloudWatch 的原生集成，深入检查跨组件的细粒度执行路径。[AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 通过容器镜像部署模型——无论是开源模型、自定义模型，还是 [Amazon Bedrock LLM](https://aws.amazon.com/bedrock/?sec=aiapps&pos=2)（例如 Nova 与 Anthropic Claude）——都无需你自行管理大语言模型（LLM）基础设施。

借助 AgentCore 的不同能力，你可以简化 agent 与 agentic overlay 的部署，并顺畅集成到现有 AWS 技术栈中。由于它是托管服务，实现 agentic overlay 所需的工作也更少。

## 合作加速企业采用 AI

这一 agentic overlay 模式体现了作者团队与 AWS 之间更广泛的合作，旨在帮助企业弥合现有基础设施与新兴 AI 能力之间的差距。成功的 AI 落地需要务实的方案：尊重既有投资，并支持渐进式改造。AWS 与作者团队正在共同开发参考架构、实现模式与工具，让企业无需整体替换基础设施就能采用 A2A 通信。agentic overlay 模式正是这一理念的范例：保留行之有效的部分，在需要处扩展，并提供清晰的迁移路径，在最大化价值的同时把风险降到最低。

## 结论

agentic overlay 为企业提供了一条务实路径，既能采用 Agent-to-Agent 通信，又不必抛弃在 REST API 上的投入。通过增加一层把 A2A 消息转换为 REST payload 的轻量翻译层，组织可以在保留稳定、经受过生产检验的业务逻辑的同时，参与到新兴的 agentic 格局中。两种实现模式提供了匹配组织需求的灵活性：应用内 overlay 适合聚焦的用例，AgentCore Gateway 适合企业级部署。无论你是在支撑单个 supervisor agent，还是在编排复杂的多服务工作流，agentic overlay 都能降低并行基础设施的运维开销，以及整体重构带来的回归风险。

当企业从确定性的 REST API 向推理驱动的 agentic 系统过渡时，关键认识依然成立：*A2A 不是新的 API，而是通往你现有 API 的新接口*。这一视角把采用挑战从「重建一切」转向「增量改造」，让组织能够更快兑现 AI 价值，同时有效管控风险。对于准备探索 agentic overlay 的组织，计算器示例提供了一个具体的起点，AgentCore 则为生产部署提供了所需的基础设施。

## 后续步骤

- **评估你的架构** —— 审计 REST 服务，找出适合启用 A2A 的候选者。应用内 overlay 适合单服务 agent，AgentCore Gateway 适合多服务工作流。
- **查看参考实现** —— Flask 计算器示例演示了这套翻译模式，涵盖 agent card 设置、消息提取、REST 调用与响应构建。
- **探索 Amazon Bedrock AgentCore** —— AgentCore Gateway、Identity 与 Observability 为生产级 agentic overlay 提供基础设施。
- **加入 A2A 社区** —— A2A Protocol 规范与 SDK 文档见 [a2a-protocol.org](https://a2a-protocol.org/)，其中包含适用于 Flask、FastAPI 与 Starlette 应用的库。

企业 AI 的未来不在于替换现有系统，而在于用 agentic 能力扩展它们。agentic overlay 让这一未来在今天即可触及。
