# 多模态评估器：Strands Evals 中面向图像到文本任务的 MLLM-as-a-judge

如果你在构建视觉购物、图像或文档理解、或图表分析类应用，就需要一种方法来验证模型响应是否真正以源图像为依据。纯文本评估器无法告诉你：一段描述是否忠实描述了图像、抽取出的发票总额是否与文档一致，或者一段界面摘要是否凭空捏造了页面上根本不存在的按钮。Gartner [预测](https://www.gartner.com/en/newsroom/press-releases/2025-07-02-gartner-predicts-80-percent-of-enterprise-software-and-applications-will-be-multimodal-by-2030-up-from-less-than-10-in-2024)，到 2030 年，80% 的企业软件将是多模态的，而 2024 年这一比例不到 10%。没有自动化的多模态评估，你就只能在昂贵的人工复核与不可靠的纯文本替代指标之间取舍。

今天，我们宣布在 [Strands Evals 软件开发工具包（SDK）](https://strandsagents.com/docs/user-guide/evals-sdk/quickstart/)中为图像到文本任务新增四个**多模态大语言模型（MLLM）-as-a-Judge 评估器**：**Overall Quality**、**Correctness**、**Faithfulness** 和 **Instruction Following**。每个评估器都会针对源图像对图像到文本的输出打分。评估器把图像直接发送给多模态 judge 模型，同时附上查询、响应以及（可选的）参考答案。judge 返回一个以图像为依据的分数，以及一段可用于调试的推理说明。你可以把这些评估器作为纯文本 judge 的直接替代，用在现有的 Strands Evals `Case` → `Experiment` → `Report` 工作流中，并把它们接入持续集成（CI），自动捕获视觉幻觉、事实错误和指令违规。

本文中，你将了解如何：

- 配置四个多模态评估器，并在图像到文本任务上运行它们。
- 用同一个评估器在基于参考与无参考两种评估模式之间切换。
- 为领域专属判据编写自定义多模态评分细则（rubric）。
- 在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上选择在准确度、成本和延迟之间取得平衡的 judge 模型。
- 应用在我们实验中提升了 judge 与人工判断一致性的 prompt 设计选择。

## 先决条件

要跟随本文的实操演练，你需要：

- 环境中安装 Python 3.10 或更高版本。
- 通过 pip install `strands-agents-evals` 安装评估器，通过 pip install `strands-agents` 安装演练中使用的目标 agent。
- 一个可访问 Amazon Bedrock 的 AWS 账户。
- 在本地配置好 AWS 凭据（例如通过 `aws configure` 或 AWS Identity and Access Management（AWS IAM）角色），并具备对 judge 模型的 Amazon Bedrock `InvokeModel` 权限。
- 熟悉 Strands Evals 的 `Case` → `Experiment` → `Report` 工作流。如果你是 Strands Evals 新手，请参阅 [Strands Evals 发布博客文章](https://aws.amazon.com/blogs/machine-learning/evaluating-ai-agents-for-production-a-practical-guide-to-strands-evals/)快速了解。

## 为什么纯文本 judge 会漏掉与图像相关的失败

假设你已经上线了一个能读取发票、汇总仪表板或解说截图的模型。用纯文本 LLM-as-a-Judge 评估响应，你能得到*一些*信号（文笔流畅、结构清晰），但它恰恰漏掉了真正要紧的失败：

- 模型自信地指出某个图表趋势，而图表其实并没有呈现该趋势。
- 它虚构出画面中并不存在的产品、标签或人物。
- 它回答了错误的问题，或者用错误的格式回答了正确的问题。

纯文本 judge 只读输出就予以认可，并未核实图像。真值存在于图像之中，而 judge 从未看到它。

即便你确实从“给整体质量打分”的 holistic judge 那里得到一个低分，仅凭分数也无法告诉你*哪里出了问题*。失败可能是事实错误、凭空捏造的细节，或被忽略的指令。这三种失败模式需要三种不同的修正，把它们压缩成一个分数只会让调试变得比必要更困难。

## 面向图像到文本任务的四个评估器

这四个评估器针对使用最广泛的多模态类别。输入是一张图像（或文档图像）连同文本，输出是文本。该类别涵盖图像描述生成、视觉问答、图表与信息图解读、文档字段抽取、OCR 和截图摘要。下表总结了四个新评估器各自能捕获什么。

|  | **评估器** | **评分** | **核心问题** | **捕获的问题** |
| --- | --- | --- | --- | --- |
| 1 | **Overall Quality** | Likert 1-5 | 响应整体质量如何？ | 相关性差、不准确、回答浅薄、缺乏全面性 |
| 2 | **Correctness** | 二元 | 给定图像和查询，响应在事实上是否正确且完整？ | 事实错误、错误的属性/计数/位置、遗漏 |
| 3 | **Faithfulness** | 二元 | 响应是否以图像为依据、没有幻觉？ | 捏造的对象、无依据的推断、外部知识泄漏 |
| 4 | **Instruction Following** | 二元 | 响应是否遵守查询的约束？ | 格式违规、计数错误、跑题内容、忽略范围 |

每个评估器支持两种模式。**基于参考**模式把响应与金标准答案对比，在你拥有标注测试集时很有用。**无参考**模式仅依据图像进行评判，当系统运行在实时图像上、没有真值可用时，这是唯一选择。

## 端到端演练：评估图表阅读任务

为了让 API 更具体，你将演练单个 `Case`。输入是一张柱状图，展示各区域（美国/加拿大、EMEA、亚太、拉美）每位付费流媒体会员的平均收入。被测系统是一个简单的视觉 agent，它回答关于该图表的一个范围很窄的问题。你在同一个 `Experiment` 中运行四个多模态评估器。它们共享同一个 `MultimodalOutputEvaluator` 基类，并通过 `ImageData` 接收图像。

![柱状图展示各区域每位付费流媒体会员的平均收入：美国与加拿大为 $13.32，EMEA 为 $9.49，亚太为 $5.31，拉美为 $3.97。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/19/ML-21039-2.jpg)

*图 2：各区域每位付费流媒体会员的平均收入（Statista）。被测系统需要回答关于该图表的一个有依据的问题。*

**第 1 步：定义 Case 与评估器。** `Case` 把图像与指令包装进 `MultimodalInput`，提供 `expected_output` 会为支持该模式的评估器启用基于参考的评判。

```
from strands import Agent
from strands_evals import Case, Experiment
from strands_evals.evaluators import (
    MultimodalOverallQualityEvaluator,
    MultimodalCorrectnessEvaluator,
    MultimodalFaithfulnessEvaluator,
    MultimodalInstructionFollowingEvaluator,
)
from strands_evals.types import ImageData, MultimodalInput

cases = [
    Case[MultimodalInput, str](
        name="revenue-chart-1",
        input=MultimodalInput(
            media=ImageData(source="revenue_chart.jpeg"),
            instruction="Which region has the highest average revenue? "
                        "State the region name and the dollar amount shown in the chart.",
        ),
        expected_output="U.S. and Canada has the highest at $13.32.",
        metadata={"dataset": "ChartQA"},
    ),
]

evaluators = [
    MultimodalOverallQualityEvaluator(),       # Likert 1-5
    MultimodalCorrectnessEvaluator(),          # Binary
    MultimodalFaithfulnessEvaluator(),         # Binary
    MultimodalInstructionFollowingEvaluator(), # Binary
]
```

**第 2 步：接入任务并运行实验。** `task` 函数接收每个 `Case`，在图像加指令上运行视觉模型，返回待评估的响应字符串。

```
agent = Agent(callback_handler=None)
task_output = None

def run_task(case):
    global task_output
    image = case.input.media
    messages = [
        {"image": {"format": image.format or "png", "source": {"bytes": image.to_bytes()}}},
        {"text": case.input.instruction},
    ]
    task_output = str(agent(messages))
    return task_output

reports = await Experiment(cases=cases, evaluators=evaluators).run_evaluations_async(
    task=run_task, max_workers=1,
)
```

由于上面每个 `Case` 都带有一个包含 media 的 `MultimodalInput`，四个评估器都会在 judge prompt 中包含图像。若想在自己的数据上消融验证图像模态是否真正有贡献，可以把 `MultimodalInput` 换成纯字符串输入（例如图像的文字描述）后重跑。同一个评估器仅凭文本也能打分。

**第 3 步：检查 Report。** 每个 `Report` 包含逐用例的 `scores`、`test_passes` 和 `reasons`：

```
print(f"Task Output:\n{task_output}\n")
print("=" * 50)
for name, report in zip(
    ["Quality", "Correctness", "Faithfulness", "Instruction"], reports,
):
    reason = report.reasons[0] if report.reasons else ""
    status = "PASS" if report.test_passes[0] else "FAIL"
    print(f"{name}: {report.scores[0]:.2f} [{status}]")
    print(f"  Reason: {reason}\n")
```

在上图基础上运行，产生如下输出记录：

```

revenue per paying streaming membership at $13.32.

==================================================

  revenue region at $13.32, directly addressing both parts of the instruction.
```

有两点值得注意。第一，每个评估器除了分数还会返回 `reason` 字符串，这对调试至关重要。当 CI 中的一次运行失败时，你无需重跑就能看到*为什么*。第二，同一个 `Case` 在单个 `Experiment` 中被四个独立的 judge 打分（一个 Likert、三个二元），因此你的工作流与纯文本 Strands Evals 中的单评估器运行完全一致。

**自定义评分细则。** 对于领域专属判据，基类接受任意 rubric 字符串：

```
from strands_evals.evaluators import MultimodalOutputEvaluator

medical_eval = MultimodalOutputEvaluator(rubric="""Rate diagnostic accuracy:
- 1.0: All findings correctly identified with proper terminology.
- 0.5: Key findings identified but imprecise terminology.
- 0.0: Critical findings missed or misidentified.""")
```

## 我们学到了什么：三个设计问题

### 问题 1：judge 需要看到图像吗？

一个自然的问题是：如果给纯文本 LLM judge 一份详细的自动生成图像描述来替代图像，它能否替代多模态 judge？我们比较了 MLLM-as-a-Judge（图像加文本）与 LLM-as-a-Judge（把长、短两种图像描述喂进同一个 prompt）。

**结论：**多模态 judge 与人工评分的一致性高于两种纯文本变体。一旦把生成图像描述所需的那次额外 LLM 调用算进去，纯文本路线在成本和速度上也并无实质优势。如果你有多模态 judge 可用，就直接用它。

### 问题 2：Amazon Bedrock 上该用哪个模型作为 judge？

我们评估了 Amazon Bedrock 上可用的多个 MLLM 作为 judge，并用与人工评分的一致性、单查询成本和延迟来选定默认项。Amazon Bedrock 上的 Anthropic Claude Sonnet 4.6 在我们的各次运行中提供了最佳的准确度与成本权衡，因此我们把它作为多模态评估器的默认 judge 模型。我们还观察到了两点在尝试过的多个模型上始终成立的规律。第一，具备推理能力的大模型作为 judge 比小模型更可靠。第二，在具备能力的层级内，此任务上高价模型相对中端模型并未获得可测量的准确度提升。

**推荐默认值：**Anthropic Claude Sonnet 4.6。

### 问题 3：哪些 prompt 设计选择真正重要？

我们针对最终推荐 prompt 消融了若干 prompt 设计维度。可跨多次运行推广的结论有：

- **让 judge 先推理再打分。**这是我们测得的单项影响最大的选择。只输出分数更便宜、自洽性也更高，但与人工评分的一致性会明显下降。如果只能记住一件事，就是这一条。
- **加入少量多样的校准示例。**从零样本到几个示例，一致性呈单调提升。
- **使用细粒度、多维度的评分细则**（例如视觉准确性、指令遵循、完整性、连贯性），而不是单一的整体 prompt。把维度分开可以避免一个含糊的分数吸收掉不同的失败模式。

### 附加：基于参考与无参考

在 judge prompt 中注入金标准参考答案有助于内容导向的评估器。当有参考可用时，Overall Quality、Correctness 和 Faithfulness 与人工判断的一致性更高。Instruction Following 则相反。加入参考内容会分散 judge 的注意力，使其偏离对结构约束（格式、范围、顺序、计数）的检查——这些约束仅由查询和响应决定。

**一般准则：**内容导向的指标使用参考，而像指令遵循这类结构性指标则跳过参考。

## 最佳实践

基于我们的实验与集成工作，我们建议：

- **默认用 `MultimodalOverallQualityEvaluator` 做快速健全性检查**，随后在诊断具体失败模式时再加入针对性的二元评估器（Correctness、Faithfulness、Instruction Following）。
- **以 Claude Sonnet 4.6 作为 judge 起步**，只有当成本或延迟成为主要约束时，才降到 Amazon Bedrock 上更小的具备推理能力的 MLLM。避免用小模型做评判。
- **保留 reason+score 的输出格式。**只看分数对成本很诱人，但与人工评分的一致性会明显下降。
- **如果可用，为正确性、忠实性和整体质量使用参考；指令遵循则跳过参考。**

## 结论

Strands Evals 中四个新的 MLLM-as-a-Judge 评估器，把图像到文本评估从昂贵的人工复核或不可靠的纯文本替代指标，转变为自动化的、以图像为依据的评分。Overall Quality、Correctness、Faithfulness 和 Instruction Following 分别针对一种不同的失败模式，既支持基于参考也支持无参考评估，并在每个分数之外返回诊断性推理。在我们的留出验证集上，这四个评估器在多样的图像领域都与人工判断保持良好一致。这是 Strands Evals 走向更广泛多模态评估的第一步。后续工作包括针对多模态工具使用与 agent 轨迹的逐步评估，以及文本到图像、视频到文本、音频到文本等更多模态组合。
