# Amazon SageMaker JumpStart 上的 OpenFold3：预测生物分子结构

您可以从 [Amazon SageMaker JumpStart](https://aws.amazon.com/sagemaker/jumpstart/) 部署 **OpenFold3-preview**。 OpenFold 联盟和哥伦比亚大学的 AlQuraishi 实验室开发了 [OpenFold3](https://github.com/aqlaboratory/openfold-3) 作为开源生物分子结构预测模型。只需几行代码，您通常就可以将 OpenFold3 部署到您自己的 AWS 账户中。然后，您可以预测蛋白质、DNA、RNA、小分子配体及其形成的复合物的 3D 结构。该终端节点在网络隔离的情况下运行，您可以使用它来帮助将序列保留在您的 AWS 账户中。

计算药物发现团队现在使用结构预测作为其工作的核心部分。团队将其用于目标识别、抗体和蛋白质工程以及基于结构的虚拟筛选。团队发现运行这些模型具有挑战性。您需要 GPU 基础设施、有效的 CUDA 和 PyTorch 堆栈、大型模型检查点以及处理需要几分钟而不是几毫秒的请求的服务层。 SageMaker JumpStart 可以为您处理大部分工作。 OpenFold3 在托管 Amazon SageMaker AI 终端节点上的 AWS 维护的容器中运行。该端点旨在处理请求排队和 GPU 预热，并且您可以添加自动缩放。

在这篇文章中，我们向您展示如何：

- 在 SageMaker **异步推理** 端点上部署 OpenFold3-preview。
- 提交结构预测作业并解释结果，包括预测结构和置信度分数。
- 在**多 GPU 实例**上并行运行多个预测。
- 提供您自己的**多序列比对 (MSA)** 以提高预测准确性，同时帮助保持您的序列私密性。
- 通过在空闲时**将端点扩展到零**来帮助降低成本。

## OpenFold3 概述

OpenFold3是一个全原子结构预测模型。它根据一组分子的序列预测其联合 3D 结构。它不仅限于单蛋白质链：它可以在一次预测中折叠多链蛋白质复合物、蛋白质-核酸组装体和蛋白质-配体复合物。

| **属性** | **详情** |
| --- | --- |
|开发商 | OpenFold 联盟/哥伦比亚大学 AlQuraishi 实验室 |
|型号类型|全原子生物分子结构预测|
|输入 |蛋白质、DNA 和 RNA 序列。 SMILES 小分子配体 |
|输出 | mmCIF 格式的预测结构，具有置信度指标（pLDDT、PAE、PDE）|
|版本 | OpenFold3 0.4.1，`of3-p2-155k` 检查点 |
|许可证|阿帕奇2.0 |
| JumpStart 型号 ID | `hugingface-蛋白质折叠-openfold3` |
|支持的实例 | `ml.g6.2xlarge`、`ml.g6.4xlarge`（默认）、`ml.g6.12xlarge` |

OpenFold3开发人员在Apache 2.0许可证下发布了其代码和模型权重，并发布了训练数据和方法。研究组织和制药公司可以检查该模型，对其进行微调，并根据该许可证的条款进行构建。开发人员将 OpenFold3-preview 描述为研究预览。

## 用例

- **目标和复杂结构预测** – 预测没有实验结构的目标的结构，包括多链组装和蛋白质-核酸复合物。
- **蛋白质-配体共折叠** – 将蛋白质与作为 SMILES 提供的小分子折叠在一起，为基于结构的设计生成结合姿势假设。
- **抗体和蛋白质工程** – 通过预测其结构并比较候选者的置信度来评估设计的变体。
- **高吞吐量筛选管道** – 针对自动扩展终端节点对大批量预测作业进行排队，并直接从 Amazon Simple Storage Service (Amazon S3) 处理结果。

## 为什么 OpenFold3 使用异步推理

大多数 JumpStart 模型（例如大型语言模型和嵌入模型）都会部署到**实时**端点。实时端点在单个请求内返回其响应，并且该请求的上限为 60 秒。结构预测的工作方式有所不同。折叠时间随着查询中链的数量和长度而增长，而现实世界的蛋白质和复合物通常需要几分钟的时间。

因此，JumpStart 上的 OpenFold3 在 [SageMaker 异步推理](https://docs.aws.amazon.com/sagemaker/latest/dg/async-inference.html) 上运行：

- 您将请求上传到 Amazon S3 并调用“InvokeEndpointAsync”，该操作会立即返回。
- 端点将请求排队并处理它，调用超时最多为 1 小时。
- 端点将结果或错误详细信息写入您选择的 S3 位置。您可以轮询它或通过 Amazon Simple Notification Service (Amazon SNS) 获取通知。

异步端点的两个属性特别适合科学工作负载。首先，它们在内部对突发请求进行排队，因此您可以提交大量序列，而无需构建自己的作业队列。其次，当队列为空时，它们可以**扩展到零实例**，这有助于您避免为实验之间的空闲实例付费。

## 使用 SageMaker Python SDK 部署 OpenFold3

首先，从 JumpStart 配置构建模型并定义“AsyncInferenceConfig”。输出和故障路径是端点写入结果和错误详细信息的 S3 位置。
```
import json, time, uuid
import boto3
from sagemaker.core.helper.session_helper import Session
from sagemaker.core.inference_config import AsyncInferenceConfig
from sagemaker.core.jumpstart.configs import JumpStartConfig
from sagemaker.core.training.configs import Compute
from sagemaker.serve.model_builder import ModelBuilder

session = Session()
bucket = session.default_bucket()          # sagemaker-{region}-{account-id}
prefix = "openfold3-async"

model_builder = ModelBuilder.from_jumpstart_config(
    jumpstart_config=JumpStartConfig(
        model_id="huggingface-proteinfolding-openfold3",
        accept_eula=True,
    ),
    compute=Compute(instance_type="ml.g6.4xlarge"),
)
model = model_builder.build()

async_config = AsyncInferenceConfig(
    output_path=f"s3://{bucket}/{prefix}/output",
    failure_path=f"s3://{bucket}/{prefix}/failure",
)

endpoint = model_builder.deploy(inference_config=async_config)
endpoint_name = endpoint.endpoint_name
print(f"Deployed asynchronous endpoint: {endpoint_name}")
```
设置 `accept_eula=True` 确认您已查看并接受模型的许可条款，这是部署此模型所必需的。如果您在 SageMaker Studio 外部运行此代码，还可以使用“role_arn="<role-arn>”将您的 SageMaker 执行角色传递到“ModelBuilder.from_jumpstart_config”。

终端节点将您的请求和结果存储在 Amazon S3 中，它们包含您的序列和预测结构。对于专有序列，请考虑使用专用 S3 存储桶或前缀，并使用您管理的 AWS Key Management Service (AWS KMS) 密钥进行服务器端加密。要使用密钥加密结果，请将其 ARN 作为“kms_key_id”传递给“AsyncInferenceConfig”。使用存储桶策略限制访问，仅允许运行此工作流程的角色，并添加 S3 生命周期规则以使您不需要保留的请求和结果对象过期。有关更多信息，请参阅 [Amazon S3 的安全最佳实践](https://docs.aws.amazon.com/AmazonS3/latest/userguide/security-best-practices.html)。

部署通常在几分钟内完成。这包括一个预热步骤，其中容器在每个 GPU 上运行简短的预测，以便在端点达到“InService”时预热 GPU。

> 提示：G6 容量在某些区域可能受到限制。如果部署因 InsufficientInstanceCapacity 而失败，请稍后重试、选择不同的受支持实例大小，或部署在该模型可用的另一个 AWS 区域中。

## 运行结构预测

请求是一个 JSON 文档，其中包含一个或多个命名的**查询**，每个查询都会列出其**链**。查询中的所有链都折叠在一起作为一个复合体。单独的查询是独立折叠的。

每个链都有这些字段：

- `分子类型` – `蛋白质`、`DNA`、`rna` 或`配体`。
- `chain_ids` – 链标识符列表，例如 `["A"]`。要指定相同的副本，例如同二聚体，请使用“[“A”，“B”]`。
- `序列` – 蛋白质、DNA 和 RNA 链的残基序列。
- `smiles` – SMILES 字符串，用于配体链而不是 `sequence`。

以下示例折叠人类泛素，这是一种经过充分表征的 76 个残基蛋白质：
```
s3 = boto3.client("s3")
smr = boto3.client("sagemaker-runtime")

payload = {
    "queries": {
        "ubiquitin": {
            "chains": [
                {
                    "molecule_type": "protein",
                    "chain_ids": ["A"],
                    "sequence": "MQIFVKTLTGKTITLEVEPSDTIENVKAKIQDKEGIPPDQQRLIFAGKQLEDGRTLSDYNIQKESTLHLVLRLRGG",
                }
            ]
        }
    }
}

# 1. Stage the request in S3
input_key = f"{prefix}/input/{uuid.uuid4().hex}.json"
s3.put_object(Bucket=bucket, Key=input_key, Body=json.dumps(payload).encode())

# 2. Submit asynchronously -- returns immediately
resp = smr.invoke_endpoint_async(
    EndpointName=endpoint_name,
    ContentType="application/json",
    InputLocation=f"s3://{bucket}/{input_key}",
    InvocationTimeoutSeconds=3600,
)
output_location, failure_location = resp["OutputLocation"], resp["FailureLocation"]
```
然后轮询 S3 以获得结果或失败记录：
```
def split(uri):
    b, _, k = uri.removeprefix("s3://").partition("/")
    return b, k

result = None
for _ in range(120):                                    # up to ~30 minutes
    for loc, is_failure in ((output_location, False), (failure_location, True)):
        try:
            body = s3.get_object(Bucket=split(loc)[0], Key=split(loc)[1])["Body"].read()
        except s3.exceptions.NoSuchKey:
            continue
        if is_failure:
            raise RuntimeError(body.decode())
        result = json.loads(body)
    if result:
        break
    time.sleep(15)

if result is None:
    raise TimeoutError(f"No result yet; check {output_location}")
if result.get("status") == "error":
    raise RuntimeError(result["error"])
```
具有无效输入（例如格式错误的链或不受支持的 MSA 名称）的请求仍会生成结果对象，但带有“status”：“error”和“error”消息而不是结构。最后一次检查显示了该消息。

预测时间随着输入的大小而增长。在我们对 ml.g6.4xlarge 的测试中，较小的蛋白质比较大的蛋白质完成得更快。

### 解释结果

响应包含“状态”、mmCIF 格式的预测“结构”列表以及它们匹配的“置信度”。默认情况下，OpenFold3 每个查询生成五个扩散样本，因此每个查询返回五个候选结构。每个样本都附带两个置信度文件：详细文件 (`*_confidences.json`) 和摘要文件 (`*_confidences_aggreated.json`)。摘要包含一个“sample_ranking_score”，您可以使用它来选择最佳样本。
```
import os
os.makedirs("structures", exist_ok=True)
for s in result["structures"]:
    path = os.path.join("structures", os.path.basename(s["filename"]))
    with open(path, "w") as f:
        f.write(s["content"])
    print("saved", path, f'({s["size_bytes"]/1024:.0f} KB)')

summaries = {c["filename"]: c["data"] for c in result["confidences"]
             if c["filename"].endswith("_aggregated.json")}
for name, m in sorted(summaries.items(), key=lambda kv: -kv[1]["sample_ranking_score"]):
    print(f'{name}: ranking={m["sample_ranking_score"]:.2f} pLDDT={m["avg_plddt"]:.1f} '
          f'pTM={m["ptm"]:.2f} ipTM={m["iptm"]:.2f}')
```
您可以在任何结构查看器中打开 `.cif` 文件，例如 [PyMOL](https://pymol.org/)、[ChimeraX](https://www.cgl.ucsf.edu/chimerax/) 或 [Mol*](https://molstar.org/)。要查看笔记本中的内联结构，请使用“py3Dmol”：
```
import py3Dmol   # pip install py3Dmol
view = py3Dmol.view(width=600, height=450)
view.addModel(result["structures"][0]["content"], "cif")
# pLDDT is stored in the B-factor field: red = low confidence, blue = high
view.setStyle({"cartoon": {"colorscheme": {"prop": "b", "gradient": "roygb", "min": 50, "max": 90}}})
view.zoomTo(); view.show()
```

图 1：OpenFold3 预测的泛素结构，使用前面的代码渲染并按每个原子置信度 (pLDDT) 着色。本文中的所有图形均使用 3Dmol.js 渲染（Rego 和 Koes，[Bioinformatics，2015](http://dx.doi.org/10.1093/bioinformatics/btu829)）。

该预测显示了泛素的紧凑折叠：混合的 β 片层包裹着单个 α 螺旋。大部分结构是蓝色的（高可信度）。只有位于图像顶部的灵活的 C 末端尾巴转向黄色和红色，这与实验结构中尾巴已知的灵活性相匹配。

置信度指标告诉您每个预测的信任程度：

- **pLDDT（预测局部距离差异测试）** – 局部结构中每个原子的置信度，范围为 0-100。越高越好，大约 70 以上的值通常表明局部结构可靠。摘要文件将平均值报告为“avg_plddt”。
- **pTM 和 ipTM（预测 TM 分数和界面 pTM）** – 对折叠以及链和配体如何相对彼此定位的总体置信度，范围为 0-1。对于复合体，ipTM 是关键数字。摘要文件还报告每对链的“chain_pair_iptm”。
- **PAE（预测对齐误差）** 和 **PDE（预测距离误差）** – 每个残基对误差估计，位于详细的置信度文件中。使用它们来判断域和链的相对位置。

## 在多 GPU 实例上并行运行预测

单个 OpenFold3 预测在一个 GPU 上运行，因此多 GPU 实例不会使单个预测更快。相反，您可以一次运行多个预测。在多 GPU 实例（例如具有四个 GPU 的“ml.g6.12xlarge”）上，容器为每个并发请求分配自己的 GPU。要使用所有 GPU，请将“max_concurrent_in Vocations_per_instance”设置为实例上的 GPU 数量（对于“ml.g6.12xlarge”为 4 个）：
```
multi_gpu_builder = ModelBuilder.from_jumpstart_config(
    jumpstart_config=JumpStartConfig(
        model_id="huggingface-proteinfolding-openfold3",
        accept_eula=True,
    ),
    compute=Compute(instance_type="ml.g6.12xlarge"),
)
multi_gpu_model = multi_gpu_builder.build()

async_config = AsyncInferenceConfig(
    output_path=f"s3://{bucket}/{prefix}/output",
    failure_path=f"s3://{bucket}/{prefix}/failure",
    max_concurrent_invocations_per_instance=4,   # = number of GPUs on the instance
)

multi_gpu_endpoint = multi_gpu_builder.deploy(inference_config=async_config)
```
这会创建第二个端点，因此请记住在完成后也将其删除（请参阅**清理**）。

在我们的测试中，四个并发预测分别在单独的 GPU 上运行，吞吐量随着蛋白质大小的增加而增加。对于较大的蛋白质，我们根据按需实例定价在“ml.g6.12xlarge”上测量的每次预测成本接近于“ml.g6.4xlarge”。您的结果取决于您的输入和区域。有关定价，请参阅 [Amazon SageMaker AI 定价](https://aws.amazon.com/sagemaker/pricing/)。

> 注：ml.g6.12xlarge 容量可有限。如果您所在的区域不可用，您可以使用本文后面描述的自动缩放配置跨多个 ml.g6.4xlarge 实例进行横向扩展，从而提高吞吐量。

使用下表选择实例：

| **工作量** | **推荐实例** | **为什么** |
| --- | --- | --- |
|单个用户的交互式探索 | `ml.g6.2xlarge` 或 `ml.g6.4xlarge` |一个 GPU 一次以受支持实例的最低每小时成本处理一个预测 |
|团队使用或并发请求突发 | `ml.g6.12xlarge` 与 `max_concurrent_inspirations_per_instance=4` |四个预测并行运行而不是排队 |
|高通量筛选 |具有自动缩放功能的“ml.g6.12xlarge” |受支持实例中每个实例的最高吞吐量。随着队列深度横向扩展并返回到零 |

## 使用您自己的 MSA 提高预测准确性

OpenFold3 可以采用**多序列比对 (MSA)** 作为每个蛋白质链的附加输入。 MSA 是一组与您的查询对齐的进化相关序列。这些序列之间的共变表明哪些残基可能接触，因此 MSA 可以显着提高许多蛋白质和复合物的准确性。

为了帮助将序列保留在您的 AWS 账户内，JumpStart 终端节点在 **网络隔离** 下运行，并且不会调用外部 MSA 服务器。相反，它接受请求中的**预先计算的 MSA**。您可以在您控制的基础设施上使用已使用的管道和序列数据库生成比对，并将其传递到端点。这种设计可以帮助需要保密专有序列的药物发现项目。

如果您不提供 MSA，端点将仅根据序列进行预测。这对于小而特征明确的蛋白质（例如泛素）非常有效。对于大多数现实世界的目标和复合体，包括 MSA。本节的其余部分将展示它如何以及如何改进结果。

### 带上您自己的 MSA

每个蛋白质链接受一个“precompulated_msa”字段：一个比对列表，每个比对都有一个“名称”和 A3M 或斯德哥尔摩格式的比对“内容”。对于单个合并对齐，例如 ColabFold MMseqs2 搜索的输出，请使用名称“colabfold_main”：
```
with open("ca2_colabfold.a3m") as f:
    ca2_msa = f.read()

payload["queries"]["ca2_acetazolamide"]["chains"][0]["precomputed_msa"] = [
    {"name": "colabfold_main", "content": ca2_msa}
]
```
这个例子有一条蛋白质链。如果查询有多个不同的蛋白质链，请为每个蛋白质链计算一个 MSA，并将其附加到该链的“precompulated_msa”字段。在一个“chain_ids”条目下一起列出的相同副本（例如同源二聚体）共享一个 MSA。

如果您使用不同的管道生成 MSA，端点还接受其他对齐名称，例如“uniref90_hits”、“mgnify_hits”和“bfd_uniclust_hits”。由于请求在 S3 中暂存，因此您可以发送大型对齐。在我们的测试中，几兆字节的对齐是有效的。

您可以使用 [ColabFold](https://github.com/sokrypton/ColabFold) (MMseqs2) 或 HHblits 或 JackHMMER 等工具生成 MSA。为了帮助将专有序列保留在您的环境中，请在您自己的 AWS 基础设施上针对本地托管的序列数据库运行搜索，而不是将序列发送到公共服务器。例如，ColabFold 的“colabfold_batch”命令默认使用公共 ColabFold MSA 服务器，因此对于专有序列，请使用“colabfold_search”和本地托管数据库。

### MSA 有多大区别？

我们将上一节中的碳酸酐酶 II、锌和乙酰唑酰胺复合物在同一端点上折叠两次：一次在单序列模式下，一次使用来自 ColabFold MMseqs2 搜索的 MSA。

| **公制（5 个样本中的第一个）** | **没有 MSA** | **使用 MSA** |
| --- | --- | --- |
|平均 pLDDT | 30| 98 | 98
| pTM | 0.22 | 0.22 0.98 | 0.98
| ipTM | 0.49 | 0.49 0.98 | 0.98
|锌-His94/His96/His119 距离 | 2.3–9.4 埃 |每个 2.0 Å |
|乙酰唑胺氮锌距离 | 5.6 埃 | 2.0 埃 |
|预测时间| 〜1.5 分钟 | 〜1.5 分钟 |

通过 MSA，OpenFold3 恢复已知的绑定模式。锌离子由三个活性位点组氨酸配位，乙酰唑酰胺磺酰胺氮直接与锌结合，与实验结构相匹配。如果没有 MSA，蛋白质折叠的置信度较低，并且不会形成结合位点。添加 MSA 并没有明显改变预测时间。

![左侧没有 MSA 的碳酸酐酶 II 预测，右侧有 MSA，每个预测都叠加在灰色 PDB 3HS4 晶体上结构](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/12/ML-22226-2.png)

图 2：相同的碳酸酐酶 II、锌和乙酰唑酰胺查询在不带 MSA（左）和带 MSA（右）的情况下折叠。每个预测均由 pLDDT 着色并叠加在实验晶体结构上（灰色，PDB [3HS4](https://www.rcsb.org/struct/3HS4)；Sippel 等人，2009）。

叠加在晶体结构上，基于 MSA 的预测与其紧密匹配：蛋白质主链偏差 0.2 Å (Cα RMSD)，锌离子偏差小于 0.1 Å，乙酰唑酰胺重原子偏差 0.4 Å RMSD。单序列预测错误折叠，Cα RMSD 为 22 Å。

![预测结合位点的特写，显示由 His94、His96、His119 和乙酰唑酰胺磺酰胺配位的锌离子氮](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/12/ML-22226-3.png)

碳酸酐酶 II 与乙酰唑酰胺是蛋白质数据库中研究最广泛的复合物之一，密切相关的结构可能是 OpenFold3 训练数据的一部分。将此示例视为工作流程以及 MSA 重要性的演示，而不是作为新目标准确性的基准。

## 帮助降低成本：空闲时扩展到零

当没有请求排队时，异步端点可以缩小到**零实例**，并在新请求到达时缩小到回缩。这种模式适合经常突发运行的结构预测工作。
```
aas = boto3.client("application-autoscaling")
resource_id = f"endpoint/{endpoint_name}/variant/AllTraffic"

aas.register_scalable_target(
    ServiceNamespace="sagemaker",
    ResourceId=resource_id,
    ScalableDimension="sagemaker:variant:DesiredInstanceCount",
    MinCapacity=0,
    MaxCapacity=4,
)

# Scale out and in to keep about 4 queued requests per instance
aas.put_scaling_policy(
    PolicyName="openfold3-backlog",
    ServiceNamespace="sagemaker",
    ResourceId=resource_id,
    ScalableDimension="sagemaker:variant:DesiredInstanceCount",
    PolicyType="TargetTrackingScaling",
    TargetTrackingScalingPolicyConfiguration={
        "TargetValue": 4.0,
        "CustomizedMetricSpecification": {
            "MetricName": "ApproximateBacklogSizePerInstance",
            "Namespace": "AWS/SageMaker",
            "Dimensions": [{"Name": "EndpointName", "Value": endpoint_name}],
            "Statistic": "Average",
        },
        "ScaleInCooldown": 600,
        "ScaleOutCooldown": 300,
    },
)
```
队列空一段时间后，目标跟踪会将端点缩小到零。在我们的测试中，这大约需要 15-20 分钟。但是，目标跟踪不会将端点从零放大。要在请求到达且没有实例运行时启动实例，请添加由“HasBacklogWithoutCapacity”指标触发的逐步扩展策略：
```
cw = boto3.client("cloudwatch")

step = aas.put_scaling_policy(
    PolicyName="openfold3-scale-from-zero",
    ServiceNamespace="sagemaker",
    ResourceId=resource_id,
    ScalableDimension="sagemaker:variant:DesiredInstanceCount",
    PolicyType="StepScaling",
    StepScalingPolicyConfiguration={
        "AdjustmentType": "ChangeInCapacity",
        "MetricAggregationType": "Average",
        "Cooldown": 300,
        "StepAdjustments": [{"MetricIntervalLowerBound": 0, "ScalingAdjustment": 1}],
    },
)

cw.put_metric_alarm(
    AlarmName=f"{endpoint_name}-has-backlog-without-capacity",
    Namespace="AWS/SageMaker",
    MetricName="HasBacklogWithoutCapacity",
    Dimensions=[{"Name": "EndpointName", "Value": endpoint_name}],
    Statistic="Average",
    Period=60,
    EvaluationPeriods=2,
    DatapointsToAlarm=2,
    Threshold=1,
    ComparisonOperator="GreaterThanOrEqualToThreshold",
    TreatMissingData="missing",
    AlarmActions=[step["PolicyARN"]],
)
```
当请求到达具有零个实例的端点时，它会在实例启动时在队列中等待。从零缩放后的第一个请求将需要更长的时间才能完成，因为它包括触发警报的时间、启动实例的时间以及预测本身的时间。同一突发中的后续请求以正常速度运行。这种权衡对于批量工作负载非常有效。对于交互式使用，请设置“MinCapacity=1”以保持一个实例的温暖。有关更多详细信息，请参阅[自动缩放异步端点](https://docs.aws.amazon.com/sagemaker/latest/dg/async-inference-autoscale.html)。

## 清理

要停止产生费用，请在完成后删除您创建的资源。如果您配置了自动扩展，请先将其删除：删除 Amazon CloudWatch 警报，然后取消注册可扩展目标。然后删除每个端点、其端点配置及其模型，包括多 GPU 端点（如果您部署了它）：
```
# 1. If you configured autoscaling, remove it before deleting the endpoint
cw.delete_alarms(AlarmNames=[f"{endpoint_name}-has-backlog-without-capacity"])
aas.deregister_scalable_target(
    ServiceNamespace="sagemaker",
    ResourceId=resource_id,
    ScalableDimension="sagemaker:variant:DesiredInstanceCount",
)

# 2. Delete the endpoints, endpoint configurations, and models
#    (include only the ones you deployed)
from sagemaker.core.resources import EndpointConfig

for m, ep in ((model, endpoint), (multi_gpu_model, multi_gpu_endpoint)):
    endpoint_config = EndpointConfig.get(endpoint_config_name=ep.endpoint_name)
    m.delete()
    ep.delete()
    endpoint_config.delete()
```
如果您不再需要请求和结果对象，还可以从“s3://<bucket>/openfold3-async/”中删除它们。
