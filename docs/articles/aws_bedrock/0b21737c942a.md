# 使用 Amazon Bedrock AgentCore Runtime 将 AWS API MCP Server 与 AWS Quick 集成

随着你的 AWS 基础设施规模扩大，运维工作流自然也会变得更加复杂。SRE 和 DevOps 工程师花费大量时间在 AWS Management Console、CLI 文档和多个服务仪表盘之间来回切换。他们手动将业务问题转换成正确的 API 语法，跨服务串联调用，并为每个新用例重新构建相同的集成模式。这种摩擦会随着时间累积。事故排查需要在不同界面之间交叉比对 Amazon CloudWatch Logs、Amazon Elastic Compute Cloud（Amazon EC2）实例状态和 AWS Identity and Access Management（IAM）策略。容量规划意味着要手动查询多个服务并拼装结果。安全审计需要一致、可重复的 API 调用序列，而从零开始编写这些脚本非常耗时。

本文向你展示如何使用支持 [Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro) 的 [Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)，通过 AWS API MCP Server 将 [AWS Quick](https://docs.aws.amazon.com/quick/latest/userguide/what-is.html) 与 AWS 服务连接起来，创建一个对话式 AI 助手，将自然语言转换为 AWS Command Line Interface（AWS CLI）命令，让你在关键时刻无需在工具之间切换。

# **解决方案概览**

借助 Amazon Bedrock AgentCore Runtime 和 MCP 支持，自然语言查询可以直接转换为 AWS API 调用。你可以问"显示 us-east-1 中所有正在运行的 EC2 实例"，无需在工具之间切换或记住 API 语法，即可立即获得准确结果。你的请求在现有 IAM 权限范围内安全运行，并带有完整的 Amazon CloudWatch 审计轨迹以满足合规要求。你无需为每个工作流重建连接逻辑，而是可以通过单一、可复用的集成来标准化 AI agents 与 AWS 服务的交互方式。下图展示了 Amazon Bedrock AgentCore Runtime 如何通过 AWS API MCP Server 将 AWS Quick 连接到 AWS 服务。

![Architecture Diagram](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/08/ML-20268-image-1.png)

日常运维中的工作方式：

- **你用自然语言提出问题**："显示 us-east-1 中正在运行的 EC2 实例"。
- **AWS Quick 自定义 agent 解读你的意图。**
- **Amazon Cognito 对请求进行身份验证**：Quick 使用你配置的 Client ID 和 Client Secret，通过 OAuth 2.0 client credentials 流程从你的 Amazon Cognito 用户池获取 JWT token。
- **agent 连接到 AWS API MCP Server**：经过身份验证的请求到达 Amazon Bedrock AgentCore Runtime，后者根据你的 Cognito 身份提供方配置验证 JWT token。
- **AgentCore Runtime 对请求进行授权和路由**：验证你的 Cognito token 后，AgentCore Runtime 安全地调用在容器化环境中运行的 AWS API MCP Server。
- **MCP server 转换你的请求**：你的自然语言查询被转换成相应的 AWS CLI 命令。
- **AWS 服务执行命令**：使用你配置的 IAM 执行角色，该命令以最小权限对 AWS 服务运行。
- **结果以可读格式返回**：无需 CLI 语法。你可以直接在 Quick 界面中获得结构化、可读的结果。

## 设置解决方案

### 手动部署

要实施该解决方案，请完成以下步骤：

- 设置 Amazon Cognito 用户池——用于身份验证。
- 创建 IAM 角色——用于授权。
- 创建 Amazon Bedrock AgentCore Runtime agent。
- 在 AWS Quick 中为 AWS API MCP Server 配置 Integrations。
- 在 AWS Quick 中创建自定义聊天 agent。

本文部分截图中的可视化布局可能与你的 [AWS Management Console](https://aws.amazon.com/console) 中的布局略有不同。

### 设置 Amazon Cognito 用户池

Amazon Cognito 为你的应用程序提供身份验证和授权。在本解决方案中，你配置一个 Cognito 用户池来生成 JWT token，用于对发往 Amazon Bedrock AgentCore Runtime 的请求进行身份验证。使用 Amazon Cognito 进行 JWT 身份验证时，你在 CreateAgentRuntime 操作期间配置授权方（authorizer），指定你的身份提供方（IdP）专属的发现 URL 和允许的客户端。你现有的 agent 代码无需任何修改。你只需将授权方配置添加到运行时部署中。当调用方实体或用户调用你的 agent 时，他们会在 Authorization 标头中将其 IdP 专属的 access token 作为 bearer token 传入。AgentCore Runtime 使用 AgentCore Identity 自动根据你配置的授权方验证该 token，并拒绝未经授权的请求。

创建一个 Amazon Cognito 用户池用于 JWT 身份验证，使用唯一的应用名称，并将应用类型设为 Machine-to-machine application，如下图所示。为该应用提供名称，然后选择 **create user directory**。

当你创建带有 machine-to-machine 应用的 Cognito 用户池时，Amazon Cognito 会为你的应用自动创建一个资源服务器。该资源服务器定义了自定义 OAuth 2.0 scopes，用于指定你的应用可以请求的权限

![AmazonCognito-ApplicationResourceSetup](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/08/ML-20268-image-2.png)

![CognitoUserPool](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/08/ML-20268-image-3.png)

从新建用户池的菜单中，导航到 Branding 并选择 **Domain**。选择刚创建的 Resource server，然后选** edit**。向自定义 scope 添加 write scope，并更新 read 和 write 的描述。

![Cognito-ResouceServer](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/08/ML-20268-image-4.png)

read 和 write scopes 控制对 AWS API MCP Server 的访问：

- **Read scope**——允许应用程序查询 AWS 资源（例如列出 EC2 实例或描述 Amazon Simple Storage Service（Amazon S3）存储桶）。
- **Write scope**——允许应用程序修改 AWS 资源（例如创建资源或更新配置）。

这些 scopes 映射到 MCP server 代表已认证请求执行 AWS CLI 命令时所使用的 IAM 权限。

### 创建 IAM 角色

要在 Amazon Bedrock AgentCore Runtime 中运行 agents 或工具，你需要一个 IAM 执行角色。有关创建 IAM 角色的信息，请参阅 [IAM role creation](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create.html)。

为 Amazon Bedrock AgentCore Runtime 创建所需的信任策略和执行角色。更多细节请参阅 [IAM Permissions for AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-permissions.html)。将下面的 `YOUR_ACCOUNR_ID` 替换为你的 AWS 账户 ID。

以下代码用于 AgentCore Runtime 信任策略：

```

    {
      "Sid": "AssumeRolePolicy",
      "Effect": "Allow",
      "Principal": {
        "Service": "bedrock-agentcore.amazonaws.com"

      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "aws:SourceAccount": "YOUR_ACCOUNT_ID"
        },
        "ArnLike": {
          "aws:SourceArn": "arn:aws:bedrock-agentcore:*:YOUR_ACCOUNT_ID:*"
        }
      }
    }
  ]
}
```

在同一页面的 permissions 下，选择上一步创建的现有角色。

![Agentcore-servicerole](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/08/ML-20268-image-6.png)

在同一页面的 inbound auth 部分，为入站身份验证类型选择 MCP 协议和 JWT token。对于 JWT schema 配置，使用现有的身份提供方配置（第一步创建的 Cognito identity pool）。

![Agentcore-Inboundauth](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/08/ML-20268-image-7.png)

从你的 Cognito 用户池信息中获取发现 URL。查找 Token signing key URL，其格式如下：`https://cognito-idp.$REGION.amazonaws.com/$POOL_ID/.well-known/jwks.json`

将 `jwks.json` 替换为 openid-configuration。你的最终 URL 应类似于以下示例：
`https://cognito-idp.us-east-1.amazonaws.com/us-east-1_ev5CwXjma/.well-known/openid-configuration`

将允许的客户端添加到你的配置中。在左侧面板选择 App Client，导航到 Cognito 用户池中的 App Client 部分。从 App client 信息中复制 client ID，并将其添加到 allowed clients 部分。

为你的 AgentCore Runtime 部署配置高级设置。在 **Advanced configurations,** 下，本次演练保持默认网络模式为 **Public**。这使运行时在初始设置和测试期间可以通过互联网访问。

**对于生产部署，**请选择 **VPC** 选项，将网络访问限制在私有、受控的环境中。对于处理敏感数据或需要网络隔离的工作负载，这是推荐的做法。接下来，按照下一节所示添加环境变量，然后选择 **Create agent**。

- `AUTH_TYPE`: "no-auth"
- `AWS_API_MCP_HOST`: "0.0.0.0"
- `AWS_API_MCP_PORT`: "8000"
- `AWS_API_MCP_STATELESS_HTTP`: "true"
- `AWS_API_MCP_TRANSPORT`: "streamable-http"
- `AWS_API_MCP_ALLOWED_HOSTS` = "*"
- `AWS_API_MCP_ALLOWED_ORIGINS` = "*"

### 理解 AgentCore 上的 AWS API 身份验证

| **变量** | **描述** |
| --- | --- |
| `AWS_API_MCP_TRANSPORT` | 将 MCP 通信的传输协议设置为 streamable HTTP。 |
| `AWS_API_MCP_STATELESS_HTTP` | 启用无状态 HTTP 模式，这是 streamable-http 传输所必需的。 |
| `AWS_API_MCP_PORT` | MCP server 监听传入请求的端口。 |
| `AWS_API_MCP_HOST` | 将服务器绑定到容器内可用的网络接口。 |
| `AWS_API_MCP_ALLOWED_ORIGINS` | 允许来自任何 origin 的请求。在 AgentCore Runtime 受控的执行环境中可以接受。 |
| `AWS_API_MCP_ALLOWED_HOSTS` | 允许来自任何主机的请求。范围限定在 AgentCore Runtime 强制实施的容器网络边界内。 |
| `AUTH_TYPE` | 禁用 MCP server 级别的身份验证。身份验证由 AgentCore Runtime 通过 JWT token 验证来处理。有关信息，请参阅以下安全说明。 |

`AUTH_TYPE` 设置为 no-auth，是因为 MCP server 本身不执行身份验证。在通过 Amazon Bedrock AgentCore Runtime 部署时，这是有意且安全的做法。AgentCore Runtime 充当安全边界。在请求到达你的 MCP server 容器之前，AgentCore Runtime 会强制执行 JWT token 验证。它使用来自 AgentCore Identity 的公钥验证加密签名，校验 token claims（issuer、audience、expiration），并拒绝未携带有效 OAuth 2.0 bearer token 的请求。换句话说：MCP server 信任 AgentCore Runtime 已经对调用方进行了身份验证。这与 API Gateway 后面的内部微服务所采用的模式相同——服务本身不会再次进行身份验证，因为网关已经完成了这一步。

**注意：**如果你在 AgentCore Runtime 之外运行这个 MCP server（例如直接在 EC2 实例上或作为独立容器运行），不要使用 `AUTH_TYPE`： no-auth。在这种情况下，服务器将在没有身份验证层的情况下暴露。

`AWS_API_MCP_ALLOWED_HOSTS` 和 `AWS_API_MCP_ALLOWED_ORIGINS` 的通配符值（*）在本教程中故意设置得较为宽泛。在生产环境中，请将它们替换为你的工作负载所需的具体主机名和 origin，以强制实施最小权限的网络访问。

### 在 AWS Quick 中创建自定义聊天 agent

既然你已经让 AWS API MCP server 在 Amazon Bedrock AgentCore Runtime 中运行起来，接下来在 AWS Quick 中创建一个自定义聊天 agent，用于通过自然语言交互执行 AWS CLI 命令。

导航到 AWS Quick 控制台，访问集成设置。在左侧导航面板中选择 **Integrations, **然后选择 **Actions**。添加 MCP 协议集成，将 AWS Quick 与托管在 Amazon Bedrock AgentCore Runtime 上的 MCP server 连接起来。

要配置集成详情，请输入集成元数据。为你的集成提供一个描述性的 **Name**，然后添加清晰的 **Description** 说明该集成的用途。

![Quick-MCPIntegration](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/08/ML-20268-image-8.png)

对于 endpoint 配置，获取你的 Amazon Bedrock AgentCore Runtime ARN**。 **导航到 agent 的 **Tools Details** 部分。从 **Runtime** 部分复制 Runtime ARN。

示例 ARN 格式：

`arn:aws:bedrock-agentcore:us-east-1:123456789123:runtime/demoagent-LmNop08QoR`

endpoint URL 应采用以下格式，请将 Region 替换为你的 AWS 区域，并按照步骤创建经过 URL 编码的 arn。

`https://bedrock-agentcore.{region}.amazonaws.com/runtimes/{url-encoded-arn}/invocations?qualifier=DEFAULT`

要创建经过 URL 编码的 ARN，请在终端中运行以下命令：

```
echo "YOUR_ARN" | sed 's/:/%3A/g; s/\//%2F/g'
```

```
[System.Uri]::EscapeDataString("YOUR_ARN")
```

**注意：**该 bash 命令需要 Linux、macOS 或安装了 WSL（Windows Subsystem for Linux）的 Windows。Windows PowerShell cmdlet 在 Windows 系统上原生可用，无需额外依赖。最后，保持 enable auto-publishing 选项处于启用状态。要在 AWS Quick 与 MCP server 之间建立安全通信，请使用你的 Amazon Cognito 用户池凭证配置服务身份验证。

**注意：**[Amazon Cognito](https://docs.aws.amazon.com/cognito/latest/developerguide/what-is-amazon-cognito.html) 是一项全托管的 AWS 身份服务，负责处理应用程序的身份验证和授权。App client secrets 在静态存储和传输过程中均以加密形式保存。你的凭证不会以明文传输。Cognito 还支持按需轮换 client secret，因此每个 app client 最多可以维护两个有效的 secret，实现零停机轮换。

当身份验证设置页面出现提示时，选择 **Service Authentication** 作为你的身份验证方式。

**要查找你的 Client ID 和 Client Secret：**

- 打开 [Amazon Cognito console](http://console.aws.amazon.com/cognito/)。
- 选择 **User Pools**，然后选择你的用户池。
- 在左侧导航窗格中，选择 **App clients**（位于 **Applications** 下）。
- 选择你的 app client。**App client ID** 会直接显示在此页面上。
- 选择 **Show client secret** 以显示 **App client secret**。

**注意：**将你的 Client Secret 当作密码对待。对于生产部署，请使用 AWS Secrets Manager 安全存储它。不要将其嵌入客户端代码或版本控制中。

**对于 Token URL，请使用你的用户池域名来构造：**

- 在用户池的左侧导航窗格中，向下滚动到 **Branding** 部分。
- 选择 **Domain**。你的 Cognito 域名会以如下格式显示在此处：`https://your-domain.auth.region.amazoncognito.com`
- 在该域名后追加 `/oauth2/`token，构成完整的 token endpoint：`https://your-domain.auth.region.amazoncognito.com/oauth2/token`

输入 **Client ID**、**Client Secret** 和 **Token URL** 后，选择 **Create and Continue**。

![MCP-ClientCredentials](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/05/08/ML-20268-image-9.png)

**注意：**在 AWS Quick 中，你的凭证使用 AWS Key Management Service（AWS KMS）进行加密。默认情况下，Quick 使用服务托管的 AWS KMS 密钥来加密数据源凭证和 OAuth tokens。对于合规要求更严格的组织，账户管理员可以配置客户管理的密钥，以完全掌控加密密钥的生命周期，包括即时撤销访问权限以及维护可审计的凭证访问日志。

接下来，为此 action 设置共享偏好。选择是否与其他团队成员共享此 action，并配置适当的访问权限。选择 **Done **并确认该 action 出现在 **Actions** 部分。

现在让我们构建一个将自然语言转换为 AWS CLI 命令的对话式 agent。在 AWS Quick 控制台中导航到 agent 创建页面**， **在左侧面板中选择 **Custom Agents**，然后选择 **Create Chat Agent。**

使用一个描述性的 prompt 配置该 agent：

**Prompt：**创建一个对话式 agent，允许用户使用自然语言执行 AWS CLI 命令。通过 aws-api-mcp 连接器将用户请求转换为相应的 AWS API 调用。

AWS Quick 会根据你的 prompt 自动检测并选择 MCP 连接器。确认正确的集成已关联到你的 agent。选择 **Launch Agent** 使其可用于测试。

### 清理

为避免产生持续费用，请清理你作为本解决方案一部分创建的资源。

- **删除 AWS Quick 资源**。移除你启用的 AWS Quick 功能，包括自定义聊天 agent、Spaces 和 Flows。
- **移除 MCP 集成**。删除你创建的 AWS Quick MCP action。
- **清理 Amazon Bedrock 资源**。删除 Amazon Bedrock AgentCore agent 及其关联的 IAM 执行角色。
- **删除 Amazon Cognito 用户池**。最后，移除你为身份验证创建的 Amazon Cognito 用户池。

## 结论

在本文中，你学习了如何使用 Amazon Bedrock AgentCore Runtime 和 AWS API MCP Server 将 AWS Quick 与 AWS 服务连接起来。当你通过 MCP 标准化 AI agents 与基础设施的交互方式时，就可以避免为每个新用例重新构建定制的集成模式。

在此基础上，你可以扩展这一模式来自动化常见的运维查询。你还可以构建面向安全、成本优化或容量规划的领域专用 agents，并使用 [AWS Quick Flows](https://docs.aws.amazon.com/quick/latest/userguide/using-amazon-quick-flows.html) 和 [AWS Quick Automate](https://docs.aws.amazon.com/quick/latest/userguide/using-amazon-quick-automate.html) 与事故管理工作流集成。最终得到一种更一致、更安全、更高效的方式来大规模管理 AWS 基础设施。
