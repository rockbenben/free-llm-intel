# 使用 Amazon Bedrock 为 Quora 的 Poe 构建统一多模态访问层

组织通过 Generative AI Gateway 架构快速部署并集成新的生成式 AI 模型，从而获得竞争优势。这种统一接口的做法简化了对多个基础模型（FM）的访问，解决了一个关键难题：专用 AI 模型不断增多，而每个模型都有各自的能力、API 规范和运行要求。与其为每个模型分别构建和维护集成点，更明智的做法是构建一个抽象层，把这些差异统一收敛到单一而一致的 API 之后。

最近，[AWS Generative AI Innovation Center](https://aws.amazon.com/ai/generative-ai/innovation-center/) 与 [Quora](http://poe.com/) 合作提出了一套创新方案来应对这一难题。双方共同开发了一个统一的 wrapper API 框架，简化了 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 基础模型在 Quora 的 Poe 系统上的部署。该架构带来“一次构建、部署多个模型”的能力，显著缩短了部署时间并减少了工程投入，而且整个代码库中都能看到真实的协议桥接代码。

对于正在大规模推进 AI 多模型部署的技术负责人和开发者来说，这个框架展示了周密的抽象设计与协议转换如何在保持运营可控的同时加快创新周期。

本文介绍 AWS Generative AI Innovation Center 与 Quora 如何合作构建一个统一的 wrapper API 框架，从而大幅加快 Amazon Bedrock 基础模型在 Quora 的 Poe 系统上的部署。我们详细说明桥接 Poe 事件驱动的 ServerSentEvents 协议与 Amazon Bedrock 基于 REST 的 API 的技术架构，演示基于模板的配置系统如何把部署时间从数天缩短到 15 分钟，并分享协议转换、错误处理和多模态能力方面的实现模式。我们还会展示这种“一次构建、部署多个模型”的做法如何帮助 Poe 在文本、图像和视频三类模态上集成 30 多个 Amazon Bedrock 模型，同时把代码改动量减少最多 95%。

## 技术挑战：桥接不同的系统

Poe 与 Amazon Bedrock 的集成带来了根本性的架构挑战，需要创新性的解决方案。这两个系统采用不同的设计理念和通信模式构建，形成了一道显著的技术鸿沟，而 wrapper API 正是要在这道鸿沟上架桥。

### 架构上的差异

核心挑战源自两个系统根本不同的架构方式。理解这些差异是体会集成方案复杂度的前提。Poe 通过 Fast API 库（fastapi_poe）运行在现代的、响应式的、基于 ServerSentEvents 的架构上。该架构针对流式传输做了优化，适合实时交互，并使用事件驱动的响应模型，专为持续的对话式 AI 设计。Amazon Bedrock 则作为企业级云服务运行，提供基于 REST 的方式并配合 AWS SDK 访问模式，有 SigV4 认证要求、按 AWS Region 提供模型可用性的差异，以及传统的请求-响应模式（可选用流式）。这种根本性的 API 不匹配带来了若干技术挑战，Poe wrapper API 逐一解决，详见下表。

| **挑战类别** | **技术问题** | **源协议** | **目标协议** | **集成复杂度** |
| --- | --- | --- | --- | --- |
| **协议转换** | 在基于 WebSocket 的协议与 REST API 之间转换 | WebSocket（双向、持久连接） | REST（请求/响应、无状态） | 高：需要协议桥接 |
| **认证桥接** | 把 JWT 校验与 AWS SigV4 签名连接起来 | JWT token 校验 | AWS SigV4 认证 | 中：需要凭据转换 |
| **响应格式转换** | 把 JSON 响应调整为期望的格式 | 标准 JSON 结构 | 自定义格式要求 | 中：需要数据结构映射 |
| **流式响应对齐** | 把分块响应映射到 ServerSentEvents | 分块 HTTP 响应 | ServerSentEvents 流 | 高：需要实时数据流转换 |
| **参数标准化** | 在各模型之间建立统一的参数空间 | 各模型专有参数 | 标准化参数接口 | 中：需要参数归一化 |

### API 演进与 Converse API

2024 年 5 月，Amazon Bedrock 推出了 [Converse API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html)，其标准化优势显著简化了集成架构：

- 跨不同模型提供商（如 Anthropic、Meta 和 Mistral）的统一接口
- 具备对话记忆，对聊天历史做一致处理
- 通过单一 API 模式支持流式与非流式模式
- 支持文本、图像和结构化数据的多模态能力
- 参数归一化，减少各模型特有的实现怪癖
- 内置的内容审核能力

本文介绍的方案在合适的地方使用 Converse API，同时为专用能力保留与模型专有 API 的兼容性。这种混合方式在获得 Converse API 标准化优势的同时提供了灵活性。

## 方案概览

wrapper API 框架在 Poe 与 Amazon Bedrock 模型之间提供统一接口。它充当一个转换层，把模型与协议之间的差异归一化，同时保留每个模型独有的能力。

该方案架构采用模块化设计，关注点分离，并支持灵活扩展，如下图所示。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/09/11/ML-19292-Diagram-1.png)

wrapper API 由若干关键组件协同工作，共同提供无缝的集成体验：

- **Client** – 入口点，用户通过各种界面使用 AI 能力。
- **Poe layer** – 由以下部分组成：**Poe UI** – 负责用户体验、请求构造、参数控制、文件上传和响应可视化。**Poe FastAPI** – 标准化用户交互，并管理客户端与底层系统之间的通信协议。
- **Bot Factory** – 根据请求的模型类型（chat、image 或 video）动态创建合适的模型处理器（bot）。这种工厂模式为新的模型类型和变体提供了可扩展性。见以下代码：

```
# From core/bot_factory.py - Actual implementation
class BotFactory:
    """
    Factory for creating different types of bots.
    Handles bot creation based on the bot type and configuration.
    """
    @staticmethod
    def create_bot(bot_config: BotConfig) -> PoeBot:
        # Check if a custom bot class is specified
        if hasattr(bot_config, 'bot_class') and bot_config.bot_class:
            # Use the custom bot class directly
            bot = bot_config.bot_class(bot_config)
            
            # Explicitly ensure we're returning a PoeBot
            if not isinstance(bot, PoeBot):
                raise TypeError(f"Custom bot class must return a PoeBot instance, got {type(bot)}")
            return bot

        # Determine bot type based on configuration
        if hasattr(bot_config, 'enable_video_generation') and bot_config.enable_video_generation:
            # Video generation bot
            if 'luma' in bot_config.bot_name:
                from core.refactored_luma_bot import LumaVideoBot
                return LumaVideoBot(bot_config)
            else:
                from core.refactored_nova_reel_bot import NovaReelVideoBot
                return NovaReelVideoBot(bot_config)
                
        elif hasattr(bot_config, 'enable_image_generation') and bot_config.enable_image_generation:
            # Image generation bot
            if hasattr(bot_config, 'model_id') and "stability" in bot_config.model_id.lower():
                # Stability AI image generation bot
                from core.refactored_image_stability_ai import AmazonBedrockImageStabilityAIBot
                return AmazonBedrockImageStabilityAIBot(bot_config)
            else:
                # Other image generation bot (Titan, Canvas, etc.)
                from core.refactored_image_bot_amazon import RefactoredAmazonImageGenerationBot
                return RefactoredAmazonImageGenerationBot(bot_config)
                
        else:
            # Check if this is a Claude 3.7 model
            if hasattr(bot_config, 'model_id') and "claude-3-7" in bot_config.model_id.lower():
                return ClaudePlusBot(bot_config)
            else:
                # Default to standard chat bot
                return RefactoredAmazonBedrockPoeBot(bot_config)
```

- **Service manager**：编排有效处理请求所需的服务。它在不同的专用服务之间协调，包括：**Token services** – 管理 token 上限与计数。**Streaming services** – 处理实时响应。**Error services** – 归一化并处理错误。**AWS service integration** – 管理对 Amazon Bedrock 的 API 调用。
- **AWS services component** – 在 Amazon Bedrock 格式与 Poe 期望的格式之间互相转换响应，处理流式分块、图像数据和视频输出。
- **Amazon Bedrock layer** – Amazon 的基础模型服务，提供实际的 AI 处理能力与模型托管，包括：**Model diversity** – 可访问 30 多个文本模型（如 Amazon Titan、Amazon Nova、Anthropic 的 Claude、Meta 的 Llama、Mistral 等）、图像模型和视频模型。**API structure** – 同时暴露模型专有 API 和统一的 Converse API。**Authentication** – 需要 AWS SigV4 签名才能安全访问模型端点。**Response management** – 返回带有标准化元数据和使用量统计的模型输出。

这个统一 wrapper API 的请求处理流程，展示了在桥接 Poe 事件驱动的 ServerSentEvents 协议与 Amazon Bedrock 基于 REST 的 API 时所需的编排，体现了多个专用服务如何协同提供无缝的用户体验。

流程始于客户端通过 Poe 的界面发出请求，随后转发给 Bot Factory 组件。这个工厂模式根据请求的模型类型（无论是 chat、image 还是 video 生成）动态创建合适的模型处理器。Service manager 组件随后编排有效处理请求所需的各种专用服务，包括 token 服务、流式服务和错误处理服务。

## 多 bot 快速部署的配置模板

wrapper API 最强大的部分是其统一的配置模板系统，它支持以最少的代码改动快速部署和管理多个 bot。这一做法是方案成功缩短部署时间的核心。

这种配置驱动的架构带来若干显著优势：

- **快速部署** – 新增模型只需创建一条新的配置项，而不用编写集成代码。这是部署时间显著改善的关键因素。
- **一致的参数管理** – 公共参数只在 DEFAULT_CHAT_CONFIG 中定义一次，由各 bot 继承，保持一致性并减少重复。
- **按模型定制** – 每个模型可以有自己的独特设置，同时仍能受益于共享基础设施。
- **运维灵活性** – 无需改动代码即可调整参数，便于快速试验和优化。
- **集中式凭据管理** – AWS 凭据集中在一处管理，提升安全性并简化更新。
- **按 Region 部署** – 可按需把模型部署到不同的 Region，Region 设置在配置层控制。

## 高级多模态能力

该框架最强大的方面之一，是通过简单的配置开关处理多模态能力：

- **enable_image_comprehension** – 对 Amazon Nova Micro 这类纯文本模型设为 True 时，Poe 自身会使用视觉能力分析图像，并转换成文本描述发送给 Amazon Bedrock 模型。这样即使模型本身没有内置视觉能力，也能对图像进行分类。
- **expand_text_attachments** – 设为 True 时，Poe 会解析上传的文本文件，并把其内容包含进对话，使模型无需特殊的文件处理能力就能处理文档内容。
- **supports_system_messages** – 该参数控制模型是否可以接受 system prompt，从而使能力不同的模型之间行为保持一致。

这些配置开关构建了一个强大的抽象层，带来以下好处：

- **扩展模型能力** – 纯文本模型通过 Poe 的预处理获得伪多模态能力
- **优化内置特性** – 真正的多模态模型可以发挥内置能力，取得最佳结果
- **简化集成** – 通过简单的配置开关控制，而不用改代码
- **保持一致** – 无论底层模型的原生能力如何，都提供统一的用户体验

接下来，我们更详细地探讨该方案的技术实现。

### 协议转换层

该方案在技术上最具挑战性的部分，是在 Poe 的 API 协议与 Amazon Bedrock 提供的各种模型接口之间架桥。团队通过一个精巧的协议转换层实现了这一点：

```
# From services/streaming_service.py - Actual implementation
def _extract_content_from_event(self, event: Dict[str, Any]) -> Optional[str]:
    """Extract content from a streaming event based on model provider."""
    try:
        # Handle Anthropic Claude models
        if "message" in event:
            message = event.get("message", {})
            if "content" in message and isinstance(message["content"], list):
                for content_item in message["content"]:
                    if content_item.get("type") == "text":
                        return content_item.get("text", "")
            elif "content" in message:
                return str(message.get("content", ""))

        # Handle Amazon Titan models
        if "delta" in event:
            delta = event.get("delta", {})
            if "text" in delta:
                return delta.get("text", "")

        # Handle other model formats
        if "chunk" in event:
            chunk_data = event.get("chunk", {})
            if "bytes" in chunk_data:
                # Process binary data if present
                try:
                    text = chunk_data["bytes"].decode("utf-8")
                    return json.loads(text).get("completion", "")
                except Exception:
                    self.logger.warning("Failed to decode bytes in chunk")

        # No matching format found
        return None
```

这个转换层处理模型之间的细微差异，确保无论使用哪个 Amazon Bedrock 模型，返回给 Poe 的响应都保持一致，并符合 Poe 期望的格式。

### 错误处理与归一化

实现中的一个关键方面是全面的错误处理与归一化。ErrorService 在不同模型之间提供一致的错误处理：

```
# Simplified example of error handling (not actual code)
class ErrorService:
    def normalize_Amazon_Bedrock_error(self, error: Exception) -> str:
        """Normalize Amazon Bedrock errors into a consistent format."""
        if isinstance(error, ClientError):
            if "ThrottlingException" in str(error):
                return "The model is currently experiencing high demand. Please try again in a moment."
            elif "ValidationException" in str(error):
                return "There was an issue with the request parameters. Please try again with different settings."
            elif "AccessDeniedException" in str(error):
                return "Access to this model is restricted. Please check your permissions."
            else:
                return f"An error occurred while communicating with the model: {str(error)}"
        elif isinstance(error, ConnectionError):
            return "Connection error. Please check your network and try again."
        else:
            return f"An unexpected error occurred: {str(error)}"
```

这种做法确保无论底层模型或错误情形如何，用户都能收到有意义的错误信息。

### token 计数与优化

系统实现了精细的 token 计数与优化，以最大限度提高模型的有效利用率：

```
# From services/streaming_service.py - Actual implementation (partial)
# Calculate approximate JSON overhead
user_message_tokens = 0
for msg in conversation['messages']:
    for content_block in msg.get('content', []):
        if 'text' in content_block:
            # Simple word-based estimation of actual text content
            user_message_tokens += len(content_block['text'].split())

# Estimate JSON structure overhead (difference between total and content)
json_overhead = int((input_tokens - system_tokens) - user_message_tokens)

# Ensure we're working with integers for calculations
input_tokens_for_pct = int(input_tokens)
system_tokens_for_pct = int(system_tokens)
json_overhead_for_pct = int(json_overhead)

# Calculate percentage with float arithmetic and proper integer division
json_overhead_percent = (float(json_overhead_for_pct) / max(1, input_tokens_for_pct - system_tokens_for_pct)) * 100
...
```

这种细致的 token 追踪支持准确的成本估算与优化，有助于高效使用模型资源。

### AWS 认证与安全

为高效处理多个并发请求，wrapper 使用 aiobotocore 实现了连接池。这样可以为 Amazon Bedrock 维护一个连接池，减少每次请求都要新建连接的开销：

```
# From services/aws_service.py - Connection management
async def setup_client(self) -> None:
    """Initialize AWS client with proper configuration."""
    async with self._client_lock:
        try:
            # Always clean up existing clients first to avoid stale connections
            if self.Amazon_Bedrock_client:
                await self.cleanup()

            # Increase timeout for image generation
            config = Config(
                read_timeout=300,  # 5 minutes timeout
                retries={'max_attempts': 3, 'mode': 'adaptive'},
                connect_timeout=30  # 30 second connection timeout
            )

            # Create the Amazon Bedrock client with proper error handling
            self.Amazon_Bedrock_client = await self.session.create_client(
                service_name="Amazon_Bedrock-runtime",
                region_name=self.bot_config.aws_region,
                aws_access_key_id=self.bot_config.aws_access_key,
                aws_secret_access_key=self.bot_config.aws_secret_key,
                aws_session_token=self.bot_config.aws_security_token,
                config=config
            ).__aenter__()
        except Exception as e:
            self.Amazon_Bedrock_client = None
            raise
```

```
        # Ensure AWS client is set up

        # Validate and format the conversation

        # Process the request with streaming

                yield chunk
        else:
            # Non-streaming mode
            response_text, input_tokens, output_tokens = await streaming_service.non_stream_Amazon_Bedrock_response(conversation, request_id)
            if response_text:
                yield PartialResponse(text=response_text)
            else:
                yield PartialResponse(text=self.bot_config.fallback_response)
            # Send done event for non-streaming mode
            yield self.done_event()

    except Exception as e:
        # Error handling

        yield PartialResponse(text=error_message)
        yield self.done_event()
```

### 错误恢复与重试逻辑

系统实现了精细的错误恢复与重试逻辑来处理瞬时故障：

```
# From services/streaming_service.py - Retry logic
max_retries = 3
base_delay = 1  # Start with 1 second delay

for attempt in range(max_retries):
    try:
        if not self.aws_service.Amazon_Bedrock_client:
            yield PartialResponse(text="Error: Amazon Bedrock client is not initialized")
            break

        response = await self.aws_service.Amazon_Bedrock_client.converse_stream(**stream_config)
        # Process response...
        break  # Success, exit retry loop

    except ClientError as e:
        if "ThrottlingException" in str(e):
            if attempt < max_retries - 1:
                delay = base_delay * (2 ** attempt)  # Exponential backoff
                await asyncio.sleep(delay)
                continue
        error_message = f"Amazon Bedrock API Error: {str(e)}"
        yield PartialResponse(text=f"Error: {error_message}")
        break
```

### 密钥管理

系统与 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 集成，用于安全地存储和获取敏感凭据：

```
# From services/aws_service.py - Secrets management
@staticmethod
def get_secret(secret_name: str, region_name: str = "us-east-1") -> Dict[str, Any]:
    """
    Retrieve a secret from AWS Secrets Manager.

    Args:
        secret_name: Name of the secret to retrieve
        region_name: AWS region where the secret is stored

    Returns:
        Dict[str, Any]: The secret value as a dictionary
    """
    # Create a Secrets Manager client
    session = boto3.session.Session()
    client = session.client(
        service_name='secretsmanager',
        region_name=region_name
    )

    try:
        get_secret_value_response = client.get_secret_value(
            SecretId=secret_name
        )
    except Exception as e:
        logging.error(f"Error retrieving secret {secret_name}: {str(e)}")
        raise

    # Depending on whether the secret is a string or binary, one of these fields will be populated.
    if 'SecretString' in get_secret_value_response:
        import json
        try:
            # Explicitly annotate the return type for mypy
            result: Dict[str, Any] = json.loads(get_secret_value_response['SecretString'])
            return result
        except json.JSONDecodeError:
            # If not a JSON, return as a single-key dictionary
            return {"SecretString": get_secret_value_response['SecretString']}
    else:
        import base64
        decoded_binary_secret = base64.b64decode(get_secret_value_response['SecretBinary'])
        return {"SecretBinary": decoded_binary_secret}
```

```
# From services/aws_service.py - Secure connection cleanup
async def cleanup(self) -> None:
    """Clean up AWS client resources."""
    try:
        if self.Amazon_Bedrock_client:
            try:
                await self.Amazon_Bedrock_client.__aexit__(None, None, None)
            except Exception as e:
                self.logger.error(f"Error closing Amazon Bedrock client: {str(e)}")
            finally:
                self.Amazon_Bedrock_client = None

        self.logger.info("Successfully cleaned up AWS client resources")
    except Exception as e:
        # Even if cleanup fails, reset the references to avoid stale connections
        self.Amazon_Bedrock_client = None
```

## 经验与最佳实践

通过这次合作，浮现出若干重要的技术洞见，或许对开展类似项目的团队有所帮助：

- **配置驱动架构** – 用配置文件而不是代码来表达模型专有的行为，对可维护性和可扩展性极为有利。这种做法让新模型无需改动代码即可加入，显著降低了引入 bug 的风险。
- **协议转换的挑战** – 最复杂的部分在于处理不同模型之间流式协议的细微差异。构建健壮的抽象需要仔细考虑边界情况并实现全面的错误处理。
- **错误归一化** – 要在各式各样的模型之间营造一致的错误体验，需要精细的错误处理，把模型专有的错误转换为用户友好、可操作的信息。这同时改善了开发者和终端用户的体验。
- **类型安全** – 强类型（大量使用 Python 的类型提示）对于在多人协作的复杂代码库中保持代码质量至关重要。这一实践减少了 bug 并提升了代码可维护性。
- **安全优先** – 从一开始就集成 Secrets Manager，确保凭据在系统整个生命周期内都被安全处理，有助于防止潜在的安全漏洞。
