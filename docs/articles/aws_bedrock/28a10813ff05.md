# 使用 LangChain 与 Amazon Bedrock Knowledge Bases 实现智能体式检索

当用户让客服助手——一个用 LangChain 构建的检索增强生成（Retrieval Augmented Generation，RAG）应用——在三个维度上对比两款产品时，他们实际上同时提出了六个问题。相似度搜索用一个查询向量来承载全部意图，检索器随后给出的只是这些意图平均值的最佳近似。返回的答案很简洁，搜索执行没有报错，相关性分数看起来也合理。但检索到的文档块（chunk）虽然主题相关，却只覆盖了问题真正所问内容的一小部分。

在这篇文章中，我们展示一个运行在 Amazon Bedrock Managed Knowledge Base 上、配合 [LangChain](https://github.com/langchain-ai/langchain-aws) 的 RAG 应用。我们把同一个多部分问题分别交给标准检索和智能体式检索（agentic retrieval），并通过读取 trace 事件来查看模型生成的检索计划。我们还会介绍这两条检索路径各自的费用，以及在什么时候成本更低的那条才是正确的选择。

智能体式检索在 Amazon Bedrock Managed Knowledge Base 上可用。Amazon Bedrock Managed Knowledge Base 不再只做一次搜索，而是对检索进行规划：把问题拆分成多个子查询并逐一执行，判断证据是否充分，不充分就再次搜索。`langchain-aws` 包同时暴露了智能体式检索和标准检索，因此你可以在 LangChain 应用中任选其一。

## 方案总览

[Amazon Bedrock Managed Knowledge Base](https://aws.amazon.com/blogs/aws/introducing-amazon-bedrock-managed-knowledge-base-for-faster-more-accurate-enterprise-ai-applications/) 是 Amazon Bedrock 中的全托管 RAG 能力，它把 RAG 架构里需要自建的向量存储、嵌入模型和重排序模型全部接管掉。你只需配置一个数据源，Amazon Bedrock Managed Knowledge Bases 就会负责分块（chunking）、嵌入（embedding）、存储和检索。本次演练使用 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/pm/serv-s3/?trk=50b671a1-06f5-4224-9505-fa45ee881c08&sc_channel=ps&ef_id=EAIaIQobChMI1uiUo4eXlgMVy1J_AB2pfydUEAAYASAAEgJ6PPD_BwE&gads_camp=23522747487&gads_ag=196433733807&gads_ad=795876995201&gads_kw=amazon%20s3&gads_matchtype=e&gads_network=g&gads_device=c&gads_geo=9022830&gad_campaignid=23522747487&gbraid=0AAAAADjHtp-DJgH1kF6NUslUNqoqqj14q&gclid=EAIaIQobChMI1uiUo4eXlgMVy1J_AB2pfydUEAAYASAAEgJ6PPD_BwE)。

Amazon Bedrock Managed Knowledge Bases 提供两个 API，本文简要讨论它们的差异。[Retrieve](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_Retrieve.html) API 执行一次混合搜索并返回带分数的文档块；[AgenticRetrieveStream](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_AgenticRetrieveStream.html) API 执行一个规划循环，并把各个步骤作为 trace 事件流式返回给你。在 `langchain-aws` 包中，前者是一个可以直接放进链（chain）里的标准 LangChain 检索器，后者是一个直接从知识库检索的函数。

下图展示了方案架构。应用通过 Retrieve API（标准的一次性检索）或 AgenticRetrieveStream API（多步规划循环）向 Amazon Bedrock Knowledge Bases 发起查询。两条路径都会从知识库返回文档块，应用再用这些文档块生成有依据（grounded）的回答。

## 实现演练

## 前置条件

要跟完本文，你需要：

- 一个 AWS 账户，且在 Amazon Bedrock Managed Knowledge Bases 和智能体式检索可用的 Region 中有权访问 Amazon Bedrock。本次演练使用美国东部（弗吉尼亚北部）Region（`us-east-1`），代码也全程假定该 Region。其他 Region 的可用性与支持情况请查阅 AWS [文档](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。
- 两个 AWS Identity and Access Management (IAM) 身份，下一节会详细说明：一个是知识库要扮演的服务角色（service role），另一个是你调用 API 所用身份的权限。
- [Python 3.12](https://www.python.org/downloads/) 或更高版本。
- 一个存放示例文档的 S3 桶。语料库需要若干主题有重叠的文档，这样对比型问题才有可查之处。单个平铺文档无法演示查询规划。

安装包。[Boto3](https://boto3.amazonaws.com/v1/documentation/api/latest/index.html) 的版本很关键：1.43.32 之前不存在 `agentic_retrieve_stream`。

```
langchain-aws>=1.6.3
langchain>=1.0
boto3>=1.43.32
```

## 权限

这里涉及两个身份，刻意把它们分开是值得的。知识库扮演一个服务角色来读取你的文档并调用嵌入模型；你的应用使用一个 AWS Security Token Service (AWS STS) 调用者身份来查询。两者都不需要对方的权限。

如果你授权代劳，Amazon Bedrock 会自动为你创建服务角色。若要自带角色，需给它一条允许 Amazon Bedrock 扮演（assume）它的信任策略，并用 `aws:SourceAccount` 和 `aws:SourceArn` 限定作用域，以防其他账户把它变成混淆代理（confused deputy）：

```
{
    "Version": "2012-10-17",
    "Statement": [{
        "Effect": "Allow",
        "Principal": {"Service": "bedrock.amazonaws.com"},
        "Action": "sts:AssumeRole",
        "Condition": {
            "StringEquals": {"aws:SourceAccount": "111122223333"},
            "ArnLike": {
                "aws:SourceArn": "arn:aws:bedrock:us-east-1:111122223333:knowledge-base/*"
            }
        }
    }]
}
```

服务角色还需要在桶上的 `s3:ListBucket` 权限和对桶内容的 `s3:GetObject` 权限，两者都以 `aws:ResourceAccount` 为条件。创建好知识库之后，把 `knowledge-base/*` 通配符收窄到具体的知识库 ID。

AWS STS 调用者身份需要另一套权限。`bedrock:AgenticRetrieveStream` 和 `bedrock:InvokeModelWithResponseStream` 无法限定到知识库的 Amazon Resource Name (ARN)；`bedrock:Retrieve` 和 `bedrock:GetDocumentContent` 则可以：

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AgenticRetrievalAndPlannerModel",
            "Effect": "Allow",
            "Action": [
                "bedrock:AgenticRetrieveStream",
                "bedrock:InvokeModelWithResponseStream"
            ],
            "Resource": "*"
        },
        {
            "Sid": "RetrieveAndFullDocumentExpansion",
            "Effect": "Allow",
            "Action": ["bedrock:Retrieve", "bedrock:GetDocumentContent"],
            "Resource": "arn:aws:bedrock:<region>:111122223333:knowledge-base/<knowledge-base-id>"
        },
        {
            "Sid": "GenerateAnswersInTheChains",
            "Effect": "Allow",
            "Action": ["bedrock:InvokeModel", "bedrock:Converse", "bedrock:ConverseStream"],
            "Resource": "*"
        }
    ]
}
```

`bedrock:GetDocumentContent` 经常被漏掉。当 `FullDocumentExpansion` 步骤判定某个片段缺少回答所需的上下文时，智能体式检索会调用它。只授予 `bedrock:Retrieve` 的策略起初可以正常工作，直到规划器需要拉取整篇文档，然后在查询中途失败。

要创建和管理知识库本身，调用方角色还需要对 `*` 的 `bedrock:CreateKnowledgeBase` 权限，以及对 `knowledge-base/*` 的 `GetKnowledgeBase`、`UpdateKnowledgeBase`、`DeleteKnowledgeBase`、`StartIngestionJob`、`GetIngestionJob` 和 `ListIngestionJobs` 操作权限。如果你使用护栏（guardrails），再加上 `bedrock:GetGuardrail` 和 `bedrock:ApplyGuardrail`。

运行本次演练可能产生知识库中的文档存储与摄取（ingestion）、检索调用以及基础模型（FM）推理的费用。

定价详情参见 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/)中的 Knowledge Bases 部分。

## 创建并填充知识库

通过 `managedKnowledgeBaseConfiguration` 创建知识库。把 `embeddingModelType` 设为 `MANAGED` 会使用服务托管的嵌入模型。

```
import boto3
import os

REGION = os.environ["AWS_REGION"]
bedrock_agent = boto3.client("bedrock-agent", region_name=REGION)

response = bedrock_agent.create_knowledge_base(
    name=KB_NAME,
    roleArn=KB_ROLE_ARN,
    knowledgeBaseConfiguration={
        "type": "MANAGED",
        "managedKnowledgeBaseConfiguration": {
            "embeddingModelType": "MANAGED",
        },
    },
)
KB_ID = response["knowledgeBase"]["knowledgeBaseId"]
```

这个请求里没有 `storageConfiguration`。若是自管理（self-managed）知识库，你需要传入一个描述自己向量存储的配置。Amazon Bedrock Managed Knowledge Base 不接受该配置——这是 API 层面最清晰的信号：存储层由 Amazon Bedrock 托管。

把 S3 桶挂为数据源，然后启动一个摄取作业。摄取是异步的，所以要轮询直到作业进入终态，而不是固定睡一段时间然后祈祷。

```
import time

SUCCESS_STATES = frozenset({"COMPLETE"})
FAILURE_STATES = frozenset({"FAILED", "STOPPED"})

def wait_for_ingestion(kb_id, ds_id, job_id, timeout_s=1800):
    """Poll an ingestion job until it reaches a terminal state."""
    deadline = time.time() + timeout_s
    while time.time() < deadline:
        job = bedrock_agent.get_ingestion_job(
            knowledgeBaseId=kb_id,
            dataSourceId=ds_id,
            ingestionJobId=job_id,
        )["ingestionJob"]
        status = job["status"]
        if status in SUCCESS_STATES:
            return job
        if status in FAILURE_STATES:
            reasons = job.get("failureReasons") or ["no reason reported"]
            raise RuntimeError(f"Ingestion job {job_id} finished as {status}: " + "; ".join(reasons))
        time.sleep(15)
    raise TimeoutError(f"Ingestion job {job_id} did not finish in {timeout_s}s")
```

完整的数据源配置与错误处理见[示例仓库](https://github.com/aws-samples/sample-rag-bedrock-langchain-blog)。

## 用 LangChain 检索器查询

[AmazonKnowledgeBasesRetriever](https://reference.langchain.com/python/langchain-aws/retrievers/bedrock/AmazonKnowledgeBasesRetriever) 封装了 Retrieve API，行为和任何其他 LangChain 检索器一样。对 Amazon Bedrock Managed Knowledge Bases，要传入 `managedSearchConfiguration`。这一步最容易让人踩坑：`vectorSearchConfiguration` 是旧路径，用于你自己运行向量存储的知识基，也是现存大多数示例展示用的写法。

```
from langchain_aws.retrievers import AmazonKnowledgeBasesRetriever

SIMPLE_QUERY = "What is the restore time objective for the checkout service?"

retriever = AmazonKnowledgeBasesRetriever(
    knowledge_base_id=KB_ID,
    region_name=REGION,
    retrieval_config={
        "managedSearchConfiguration": {
            "numberOfResults": 5,
        }
    },
)
docs = retriever.invoke(SIMPLE_QUERY)
```

每个结果以 LangChain `Document` 返回。相关性分数在 `metadata["score"]` 里，源文档自身的元数据在 `metadata["source_metadata"]` 下（已重命名以免冲突）。如果你想丢弃低置信度的结果，在检索器上设置 `min_score_confidence`，而不是事后再过滤。

对于只有一个明确意图的问题，这就是合适的工具。它只有一次调用，延迟是两者中最低的，而且你完全掌控答案如何生成。生产环境助手收到的大多数查询都是这种形态，用规划循环去回答它们既浪费钱又浪费时间。

## 一次性检索的极限

现在给同一个检索器一个包含多个部分的问题：

```
COMPLEX_QUERY = (
    "Compare the checkout and inventory services across on-call escalation, backup and "
    "restore targets, and deployment rollback procedure. Where do they differ?"
)

docs = retriever.invoke(COMPLEX_QUERY)
```

返回五个文档块，按整个问题的单一嵌入向量的混合分数排序。

这个问题包含六个意图：两个服务乘以三个维度。对检索到的文本按每个意图逐一核对证据，就能具体衡量单一嵌入到底找回了多少内容。

| **numberOfResults** | **文档块数** | **占语料库比例** | **覆盖的子意图** | **缺失** |
| --- | --- | --- | --- | --- |
| 5 | 5 | 10% | 6 个中覆盖 4 个 | checkout 值班、inventory 恢复 |
| 10 | 10 | 19% | 6 个全覆盖 | 无 |

在返回 5 条结果时，一个代表六个意图的嵌入向量漏掉了其中两个。返回 10 条时六个意图都覆盖到了，但浪费肉眼可见：两个子意图被重复覆盖，还有一个文档块完全不相关。

检索器尽了本职。局限是结构性的：一个向量无法表示六个意图，而且整个流程中没有任何一步会追问返回的证据是否足以回答问题。

## 运行智能体式检索

智能体式检索不是 LangChain 检索器，而是 Amazon Bedrock Managed Knowledge Bases 的一项能力。`langchain-aws` 包把它作为独立函数 [agentic_retrieve](https://python.langchain.com/api_reference/aws/retrievers/langchain_aws.retrievers.bedrock.html) 暴露出来，因为底层 API 以流式返回结果，不符合同步的 `BaseRetriever` 接口。`AmazonKnowledgeBasesRetriever` 上并没有一个开关能启用它。

```
from langchain_aws.retrievers.bedrock import agentic_retrieve

result = agentic_retrieve(
    knowledge_base_id=KB_ID,
    query=COMPLEX_QUERY,
    region_name=REGION,
    generate_response=True,
    number_of_results=10,
)
print(result["generatedResponse"]["answer"])
```

设置 `generate_response=True` 时，服务会在检索到的文档块之外返回一个有依据的答案和引用来源，于是你不用再接一个单独的模型调用就能拿到答案。该函数只对 Amazon Bedrock Managed Knowledge Base 生效。

在服务内部，它会规划、检索、评估证据是否充分，不充分则继续迭代。这个辅助函数把一切都藏了起来，只把最终的文档块交给你——方便是方便，代价是你看不到检索计划。

## 读取 trace 事件

想观看模型拆解问题的过程，直接在 [bedrock-agent-runtime](https://docs.aws.amazon.com/boto3/latest/reference/services/bedrock-agent-runtime.html) 客户端上调用 [agentic_retrieve_stream](https://docs.aws.amazon.com/boto3/latest/reference/services/bedrock-agent-runtime/client/agentic_retrieve_stream.html)。这是本次演练中唯一一处绕开 `langchain-aws` 的地方，因为那个辅助函数会丢弃 trace 事件，也不暴露 `maxAgentIteration` 或自定义规划模型。

```
runtime = boto3.client("bedrock-agent-runtime", region_name=REGION)

response = runtime.agentic_retrieve_stream(
    messages=[{"role": "user", "content": {"text": COMPLEX_QUERY}}],
    retrievers=[{
        "configuration": {
            "knowledgeBase": {
                "knowledgeBaseId": KB_ID,
                "retrievalOverrides": {"maxNumberOfResults": 10},
            }
        }
    }],
    agenticRetrieveConfiguration={
        "foundationModelType": "MANAGED",
        "rerankingModelType": "MANAGED",
        # 5 is the API default. Below 4 the planner stops decomposing entirely.
        "maxAgentIteration": 5,
    },
    generateResponse=False,
)

for event in response["stream"]:
    if "traceEvent" in event:
        attrs = event["traceEvent"]["attributes"]
        print(f"{attrs.get('step')}: {attrs.get('status')}")
        for action in attrs.get("actions", []) or []:
            if "retrieve" in action:
                query = action["retrieve"].get("inputQuery", {}).get("text", "")
                print(f" sub-query: {query}")
    elif "result" in event:
        for chunk in event["result"].get("results", []):
            print(chunk.get("content", {}).get("text", "")[:120])
```

只关心检索行为本身时，把 `generateResponse` 设为 `False`。API 默认会生成一个有依据的答案，而你在检查计划期间可能并不需要这次额外的模型调用，等于多花一笔钱。

trace 事件的 `step` 告诉你规划器进行到哪一步。`SpeculativeRetrieval` 在首个计划之前运行，用于降低延迟，不计入你的迭代预算。`Planning` 是模型阅读问题和先前结果并发出子查询的环节。`Retrieval` 每个子查询触发一次。`FullDocumentExpansion` 出现在模型判定某个片段缺乏回答所需上下文、转而拉取整篇文档的时候。每个步骤都带有 `IN_PROGRESS`、`SUCCEEDED` 或 `FAILED` 状态，外加一段人类可读的消息。

最终的文档块单独到达。`result` 是独立的事件类型，而不是第五个步骤，它承载所有迭代去重后的文档块，以及（在开启答案生成时）有依据的答案。要像上面的循环那样按事件 key 分支处理，而不是期待一个终态的 step 值。

子查询文本是最值得记录的部分。它位于 `attributes.actions[].retrieve.inputQuery.text`，不在顶层 trace 字段里，所以只读 `step` 和 `status` 的处理逻辑只能告诉你发生过规划，却看不到规划决定了什么。

下图展示了智能体式检索的规划循环，包括推测性检索、规划、子查询检索、评估以及可选的重新规划等步骤。

图 2：智能体式检索规划循环中的步骤

基于这套机制开发之前，有两个细节值得了解。去重只作用于 `result` 事件，因此一个被三个子查询检索到的文档块在最终结果里出现一次，但在 trace 中出现三次。

第二个细节关于分数。Retrieve 响应会给每个文档块一个带类型的 `score` 字段，保存它与查询的相关性。智能体式检索的结果则携带 `content`、`metadata` 和 `sourceRetriever`，没有对应的带类型分数字段。切换 API 之后仍去读 `result["score"]` 的代码将一无所获。如果你对相关性做排序或过滤，要为这一差异做好准备。

在生产环境中，使用 Amazon Bedrock Guardrails 对生成的回答强制执行内容策略和事实性（grounding）检查。两条检索路径都支持护栏。智能体式检索通过 `policyConfiguration.bedrockGuardrailConfiguration` 支持护栏，而不是 LangChain 检索器所用的 `guardrail_config` 参数，并且只支持 `BLOCK` 模式。如果你依赖 `MASK` 模式，那就是留在 Retrieve API 的一个理由。

`maxAgentIteration` 接受 2 到 10，默认值为 5。保持默认即可。设为 2 或 3 时，规划器只运行一个循环、不发任何子查询，返回的内容就是推测性检索步骤已经找到的东西——相当于用智能体式的价钱获得一次性检索的行为。拆解从 4 开始生效。规划器常在判定证据充分时提前停止，所以上限是一个约束而不是目标。

## 对比两条检索路径

关于这一机制在规模化下的表现，AWS 在 MuSiQue（一个公开的多跳基准测试）上评估了智能体式检索。评估显示其召回率相对一次性检索有所提升，且在最难的问题上收益最大；单跳问题的提升不到 5 个百分点。最后这个数字正好勾勒出权衡的形状：有东西可拆的时候，拆解才有用。

## 构建 RAG 链

对标准检索器，惯常的 [LangChain Expression Language (LCEL)](https://python.langchain.com/docs/concepts/lcel/) 组合方式可以直接使用：

```
from langchain_aws import ChatBedrockConverse
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough

def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

llm = ChatBedrockConverse(model=MODEL_ID, region_name=REGION)
prompt = ChatPromptTemplate.from_template(PROMPT_TEMPLATE)

chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)
```

`format_docs` 比看上去更重要。把 `Document` 对象直接塞进提示词会渲染出它们的 `repr`，模型拿到的上下文里就混进了元数据噪声。

要把智能体式检索放到同样的位置，把它包进 `RunnableLambda`，因为它是一个函数而不是检索器：

```
from langchain_core.runnables import RunnableLambda

def agentic_context(question: str) -> str:
    result = agentic_retrieve(
        knowledge_base_id=KB_ID,
        query=question,
        region_name=REGION,
        number_of_results=10,
    )
    return "\n\n".join(
        item.get("content", {}).get("text", "")
        for item in result.get("results", [])
    )

agentic_chain = (
    {"context": RunnableLambda(agentic_context), "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)
```

注意这里 `generate_response` 是关闭的。服务可以自己生成答案，但在链里你通常想用自己的提示词和模型，所以取回文档块、在下游自己生成。想少写代码、一次调用搞定，就用服务端的生成能力；提示词需要自己掌控，就用包装后的写法。

## 在标准检索与智能体式检索之间选择

对简短、范围明确的问题使用 Retrieve。它更便宜、更快，可以在自管理知识库上工作，并且结果里带分数。大多数生产流量都是这种形态。

当问题多部分、带对比或探索性质，或者证据横跨多个知识库时，使用 AgenticRetrieveStream。它能在单个请求中注册最多五个知识库，并用你为每个知识库附加的自然语言描述来路由子查询。另一个 API 完全做不到这一点。它的单次调用成本更高，会发起多次模型调用，延迟也是两者中较高的。

我们推荐的模式是按查询形态做路由，而不是一刀切地只用一种。一个分类器或对问题的启发式规则，就能把大部分流量送到便宜的路径上，把规划循环留给真正需要它的问题。

## 清理资源

删除知识库、它的数据源、S3 对象和桶，以及你创建的 IAM 角色。存有文档的知识库会持续产生存储费用。

```
bedrock_agent.delete_data_source(knowledgeBaseId=KB_ID, dataSourceId=DS_ID)
bedrock_agent.delete_knowledge_base(knowledgeBaseId=KB_ID)
```

[仓库](https://github.com/aws-samples/sample-rag-bedrock-langchain-blog)中包含一个清理脚本，还会清空桶并删除角色。

## 结论

我们展示了如何用 LangChain 在 Amazon Bedrock Knowledge Bases 上构建 RAG 应用，以及智能体式检索如何处理一次性检索回答得不好的多部分问题。我们也展示了当前集成中的摩擦点：智能体式检索是一个函数而不是 LangChain 检索器，所以要放进链里需要包一层 `RunnableLambda`；要查看展示查询计划的 trace 事件，需要直接调用 `boto3`。

智能体式检索用更高的单次调用成本换取多跳问题上更好的召回，并内置模型完成查询规划。下一个有用的步骤，是在把所有流量都导向规划器之前，先测量你自己的查询组合。

要开始上手，请参阅 Amazon Bedrock Knowledge Bases [文档](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-build-managed.html)及配套示例代码。如需针对你的工作负载落地这套方案，请联系你的 AWS 客户团队。
