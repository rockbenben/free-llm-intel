# 为 AgentCore gateway 上的 AI 流量配置速率限制

[Amazon Bedrock AgentCore gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) 是一项全托管、serverless 的 AI gateway，为 [AI 流量](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-supported-targets.html) 提供单一、安全的入口。AgentCore gateway 将流量路由到各类工具，例如 [managed web search](https://github.com/awslabs/agentcore-samples/tree/main/01-features/07-centralize-and-govern-your-ai-infrastructure/01-gateway/01-attach-targets/mcp/connectors/websearch)、[managed knowledge bases](https://aws.amazon.com/blogs/aws/introducing-amazon-bedrock-managed-knowledge-base-for-faster-more-accurate-enterprise-ai-applications/)、[MCP servers](https://github.com/awslabs/agentcore-samples/tree/main/01-features/07-centralize-and-govern-your-ai-infrastructure/01-gateway/01-attach-targets/mcp)、[inference models](https://github.com/awslabs/agentcore-samples/tree/main/01-features/07-centralize-and-govern-your-ai-infrastructure/01-gateway/01-attach-targets/llm-inference)（LLMs）、[agents](https://github.com/awslabs/agentcore-samples/tree/main/01-features/07-centralize-and-govern-your-ai-infrastructure/01-gateway/01-attach-targets/http/agents)（[A2A](https://github.com/a2aproject/A2A)、agents as tools 等）或 [HTTP](https://github.com/awslabs/agentcore-samples/tree/main/01-features/07-centralize-and-govern-your-ai-infrastructure/01-gateway/01-attach-targets/http) endpoint。今天，我们宣布在 AgentCore gateway 上支持速率限制，让你能够精细控制单个用户可以通过你的 gateway 消耗多少流量。

[速率限制](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-rate-limits.html)在 AgentCore gateway 中让你能够按用户控制用户如何消耗你的工具、inference models 和 agents。你可以定义基于 OAuth 或 IAM 的规则，针对每分钟请求数、并发连接数和 token 吞吐量进行限制，确保下游服务在流量高峰下依然可用。

## 使用 AgentCore gateway 为 AI 流量实施集中式速率限制

AgentCore gateway 提供三种 target 类型：[MCP](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-targets-mcp.html) target、[inference](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-targets-inference.html) target 和 [HTTP](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-targets-http.html) 透传 target。这些 target 支持以下速率限制指标。

- 请求速率限制以每秒请求数（RPS）和每分钟请求数（RPM）衡量，适用于所有 target 类型。每项限制都定义了在给定时间窗口内允许的最大请求数，gateway 会将每个传入请求与该限制进行比对。无论请求完成耗时多久，每个请求都恰好计为配置限制的一个单位——一个在 50 毫秒内完成的请求和一个持续 90 秒的流式请求，各自从每秒或每分钟限制中消耗恰好一个单位。
- **Token 速率限制**以每分钟 token 数（TPM）衡量，仅适用于 inference target。Token 速率限制同时计入 input token 和 output token。一个请求的完整往返 token 成本都会计入限制。AgentCore gateway 使用一个通用 tokenizer 来估算请求的传入 token，并在 gateway 分派 inference 调用之前预先从速率限制桶中扣除。当 inference 调用返回响应（其中包含模型提供方报告的实际 input 和 output token 用量）后，gateway 会根据真实的 token 消耗量对限制进行对账核算。
- **连接速率限制**以每秒连接数（CPS）衡量，适用于所有 target 类型。与请求速率限制不同，连接速率限制跟踪每个请求保持打开连接的时间。例如，如果一个流式 inference 调用耗时 100 秒才完成，那么该请求在整个期间都会占用一个连接槽位。CPS 提供了一种额外的机制来保护 target 免受长时间并发会话的影响，当你需要限制某个 target 能承受的同时连接数（而非每个时间窗口内到达的请求数）时，这一机制尤其有用。

在本用例中，假设有三个用户组：Basic、Advanced 和 Beta。[AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) 使用 [JSON Web Tokens](https://www.jwt.io/introduction#what-is-json-web-token)（JWT）处理入站身份验证，以 [Microsoft Entra ID](https://www.microsoft.com/en-us/security/business/identity-access/microsoft-entra-id) 作为身份提供方，同时也作为出站 target 的 token 发放服务。[Policy in Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html) 强制执行基于角色的访问控制（RBAC），将每个组的访问范围限定在特定的 target 和模型上。下图展示了这一配置。

Basic 用户适用的速率限制比 Advanced 用户更为严格，而 Beta 用户在受限制模型上享有更高的限额，使组织能够在将这些模型推广到整个组织之前，对其性能和适用性进行基准测试。在为每个用户组设置速率限制之前，先了解一下速率限制的结构。

### 速率限制结构

速率限制配置由两部分组成：维度键（dimension keys）和条目（entries）。维度键定义 gateway 如何将传入流量分组到各个速率桶中。条目定义每个桶允许的吞吐量。

在本文中，我们使用 [AWS Command Line Interface (AWS CLI)](https://aws.amazon.com/cli/) 来创建速率限制配置。以下示例展示了维度键与条目之间的关系。这条速率限制使用 `targetName` 作为维度键，并定义了两个条目：一个针对 `Booking` target（MCP server）的特定条目，该 target 是一个高流量 target，速率为每秒 100 个请求；另一个是通配符条目，对其余每个 target 分别应用每秒 10 个请求的速率，也就是说其他每个 target 都获得自己独立的 10 RPS 桶。

图 2：包含维度键和条目的速率限制结构

维度键定义 gateway 如何将流量分组到速率桶中。当请求到达时，gateway 会从请求上下文中解析出每个维度键的值，并使用得到的组合将该请求分配到正确的速率桶。AgentCore gateway 支持以下维度键：`targetName`、`toolName`、`qualifiedModelId`、`$.context.jwt.<claim>`、`$.context.iam.principal` 和 `$.context.iam.sourceIdentity`。我们将在后续章节中通过示例逐一探讨这些维度键。

条目是速率限制中的规则。每个条目指定一组要匹配的维度键，以及该匹配所允许的吞吐量。条目支持特殊的兜底默认值 *，它会为每个不同的值按配置速率提供独立的桶。当 gateway 评估一个请求时，它会先检查是否有条目按名称匹配，然后再回退到通配符。命名条目优先，因为它显式地指向该值，而非依赖兜底规则。

以前面的速率限制为例，当一个针对 `Booking` target（MCP server）的请求到达时，gateway 会匹配第一个条目，允许最高 100 RPS。该条目优先，因为最具体的值匹配胜过默认值 *，因为它按名称指向 `Booking` target。对于任何其他 target，都不存在命名条目，因此 gateway 回退到通配符条目，允许最高每秒 10 个请求。每个匹配通配符的 target（`Docs`、`BedrockMantle`、`CustomPlatform` 和 `awsdocsagent`）都会获得自己独立的桶。

你可以组合多个维度键以实现更精细的控制。例如，dimensionKeys: [“`targetName`”, “`$.context.jwt.role`”] 会同时按 target 和调用方身份的 role claim 对流量分组，为每个用户组（前面示例中的 Basic、Advanced 或 Beta）按 target 提供各自独立的速率桶。

## 速率限制的类型与示例配置

AgentCore gateway 强制执行两层速率限制：客户定义的速率限制和 [Service Quotas](https://docs.aws.amazon.com/general/latest/gr/aws_service_limits.html)。首先评估客户定义的速率限制。如果请求通过，再评估服务配额。以下各节将介绍服务配额以及客户定义速率限制的不同类型。

- **服务托管配额**。

这些是服务按 AWS 账户在 AgentCore gateway 上强制执行的限制。[Service managed quotas](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html#gateway-endpoints-quotas) 定义了客户定义速率限制不得超过的上限。请求的有效速率是客户定义限制与服务托管限制中的较小值。你可以通过 [Service Quotas console](https://console.aws.amazon.com/servicequotas) 申请提高某些配额。

- **客户定义的** **用户限制**。

用户级限制使用 `$.context.jwt.<claim>`、`$.context.iam.principal` 和 `$.context.iam.sourceIdentity` 作为维度键，以控制单个用户或整个用户组可以消耗多少流量。这些限制在你的调用方群体中强制实现公平使用，防止任何单一调用方独占 gateway 容量。以下示例为每个用户组分配不同的请求速率。JWT 的 role claim 是一个数组，因此每个唯一组合都需要自己的条目。

```
aws bedrock-agentcore-control create-gateway-rate-limit \
  --gateway-identifier my-gateway-abc1234567 \
  --dimension-keys '["$.context.jwt.role"]' \
  --description "Per-role request and connection limit" \
  --entries '[
    {
      "dimensions": {"$.context.jwt.role": "[\"Basic\"]"},
      "requests": [{"rate": 100, "period": "minute"}],
      "connections": [{"rate": 50, "period": "second"}]
    },
    {
      "dimensions": {"$.context.jwt.role": "[\"Advanced\"]"},
      "requests": [{"rate": 300, "period": "minute"}],
      "connections": [{"rate": 150, "period": "second"}]
    },
    {
      "dimensions": {"$.context.jwt.role": "[\"Advanced\", \"Beta\"]"},
      "requests": [{"rate": 300, "period": "minute"}],
      "connections": [{"rate": 200, "period": "second"}]
    },
    {
      "dimensions": {"$.context.jwt.role": "*"},
      "requests": [{"rate": 80, "period": "minute"}],
      "connections": [{"rate": 10, "period": "second"}]
    }
  ]'
```

在这个配置中，Basic 用户获得两个桶：100 RPM 和 50 CPS，这意味着任何 Basic 用户发出的每个请求都计入同一个 100 RPM 总量，每个连接都计入同一个 50 CPS 总量。如果一个 Basic 用户在一分钟内发送 80 个请求，那么在该时间窗口内，其他所有 Basic 用户只剩下 20 个请求额度。Advanced 用户获得自己独立的两个桶，分别为 300 RPM 和 150 CPS，遵循同样的集体行为。具有 [“Advanced”, “Beta”] 组成员身份的用户获得两个桶，分别为 300 RPM 和 200 CPS。更高的连接额度是为了满足他们以流式为主的基准测试工作负载。

然而，在一个组内，单个用户仍可能消耗整个组的速率桶，从而拖慢该组中的其他所有人。例如，一个 Basic 用户在一分钟内发送 100 个请求，将导致其他所有 Basic 用户没有任何剩余容量。为防止这种情况，我们还创建了以下速率限制配置。

```
aws bedrock-agentcore-control create-gateway-rate-limit \
  --gateway-identifier my-gateway-abc1234567 \
  --dimension-keys '["$.context.jwt.role", "$.context.jwt.sub"]' \
  --description "Per-user request and connection limit within each role" \
  --entries '[
    {
      "dimensions": {"$.context.jwt.role": "[\"Basic\"]", "$.context.jwt.sub": "*"},
      "requests": [{"rate": 20, "period": "minute"}],
      "connections": [{"rate": 10, "period": "second"}]
    },
    {
      "dimensions": {"$.context.jwt.role": "[\"Advanced\"]", "$.context.jwt.sub": "*"},
      "requests": [{"rate": 60, "period": "minute"}],
      "connections": [{"rate": 30, "period": "second"}]
    },
    {
      "dimensions": {"$.context.jwt.role": "[\"Advanced\", \"Beta\"]", "$.context.jwt.sub": "*"},
      "requests": [{"rate": 60, "period": "minute"}],
      "connections": [{"rate": 50, "period": "second"}]
    },
    {
      "dimensions": {"$.context.jwt.role": "*", "$.context.jwt.sub": "*"},
      "requests": [{"rate": 20, "period": "minute"}],
      "connections": [{"rate": 20, "period": "second"}]
    }
  ]'
```

有了这个配置，每个单独的用户都受到自身速率的限制，无论其组中有多少用户。JWT 中的 `$.context.jwt.sub` claim 唯一标识每个用户，使 gateway 能够在个体层面跟踪并强制执行限制。即使组级限制允许 Basic 总计 100 RPM，任何单个用户也不能从该共享池中消耗超过 20 RPM 和 10 CPS。同样的逻辑也适用于 Advanced 和 Beta 用户各自的上限。组级限制与用户级限制共同构成了一个双层执行模型：组上限有助于防止一个组挤占另一个组的资源，而用户上限有助于防止某个个体挤占同一组内其他成员的资源。

两条速率限制使用 AND 语义独立评估。请求必须同时通过组级限制和用户级限制才能继续。如果任一检查拒绝该请求，gateway 就会返回限流响应。例如，如果 Arnav（Basic）个人已消耗 20 RPM，那么他的下一个请求会被用户级限制拒绝，即使 Basic 组还有 80 RPM 的剩余容量。反之，如果 Basic 组已累计消耗 100 RPM，那么所有 Basic 用户都会被限流，无论其个人消耗量如何。

- **客户定义的 target 级限制**。

Target 级限制使用 `targetName`、`qualifiedModelId` 或 `toolName` 作为维度键，以控制流向特定下游 target、模型或工具的吞吐量。这些限制保护后端容量，并在你的 target 资源之间分散负载。以下示例按 target 对流量进行限制。

```
aws bedrock-agentcore-control create-gateway-rate-limit \
  --gateway-identifier my-gateway-abc1234567 \
  --dimension-keys '["targetName"]' \
  --description "Per-target rate limit" \
  --entries '[
    {
      "dimensions": {"targetName": "Booking"},
      "requests": [{"rate": 20, "period": "second"}]
    },
    {
      "dimensions": {"targetName": "Docs"},
      "requests": [{"rate": 15, "period": "second"}]
    },
    {
      "dimensions": {"targetName": "awsdocsagent"},
      "requests": [{"rate": 10, "period": "second"}],
      "connections": [{"rate": 60, "period": "second"}]
    },
    {
      "dimensions": {"targetName": "BedrockMantle"},
      "tokens": [{"rate": 100000, "period": "minute"}],
      "connections": [{"rate": 250, "period": "second"}]
    },
    {
      "dimensions": {"targetName": "CustomPlatform"},
      "tokens": [{"rate": 50000, "period": "minute"}],
      "connections": [{"rate": 100, "period": "second"}]
    },
    {
      "dimensions": {"targetName": "*"},
      "tokens": [{"rate": 10000, "period": "minute"}],
      "requests": [{"rate": 10, "period": "second"}],
      "connections": [{"rate": 50, "period": "second"}]
    }
  ]'
```

你还可以使用 `qualifiedModelId` 为每个模型设置连接速率限制（CPS），或使用 `toolName` 为每个单独的工具（例如 `Booking___bookTool` 或 `Docs___searchDocsTool`）设置请求速率限制（RPS）。

注意：我们在用例配置中不包含客户定义的 target 级速率限制。Beta 用户对受限制模型运行大量基准测试工作负载，会消耗共享 target 级限制中不成比例的份额。由于这条限制仅以 `targetName` 作为维度，所有用户共享一个上限，这意味着某个组或个体的高流量可能使该 target 上的其他所有人都得不到资源。当预计某部分用户将在特定 target 上占据 token 或连接消耗的主导地位时，应改为按身份来限定限制范围（例如 [“`targetName`”, “`$.context.jwt.role`”]）。请参见以下示例。

- **客户定义的 target-用户级限制。**

混合限制在单个速率限制配置中结合了 target 和用户两个维度，为你提供最精细的控制。借助多维键，你可以将速率限制的范围限定在特定 target、模型或工具上的某个用户或用户组。

以下示例在模型层面强制执行 token 限制，并限定到组内每个用户。`qualifiedModelId` 维度是 inference target 的完全限定模型标识符。它唯一标识被调用的模型（参见[文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-rate-limits-dimensions.html)）。

```
aws bedrock-agentcore-control create-gateway-rate-limit \
  --gateway-identifier my-gateway-abc1234567 \
  --dimension-keys '["$.context.jwt.role", "qualifiedModelId", "$.context.jwt.sub"]' \
  --description "Per-user per-role per-model TPM and access limit" \
  --entries '[
    {
      "dimensions": {"$.context.jwt.role": "[\"Advanced\", \"Beta\"]", "qualifiedModelId": "anthropic.claude-fable-5", "$.context.jwt.sub": "*"},
      "tokens": [{"rate": 80000, "period": "minute"}]
    },
    {
      "dimensions": {"$.context.jwt.role": "[\"Basic\"]", "qualifiedModelId": "anthropic.claude-fable-5", "$.context.jwt.sub": "*"},
      "requests": [{"rate": 0, "period": "second"}]
    },
    {
      "dimensions": {"$.context.jwt.role": "[\"Advanced\"]", "qualifiedModelId": "anthropic.claude-fable-5", "$.context.jwt.sub": "*"},
      "requests": [{"rate": 0, "period": "second"}]
    },
    ... (repeat for openai.gpt-5.6-luna and openai.gpt-5.6-terra)
    {
      "dimensions": {"$.context.jwt.role": "[\"Advanced\"]", "qualifiedModelId": "*", "$.context.jwt.sub": "*"},
      "tokens": [{"rate": 40000, "period": "minute"}]
    },
    {
      "dimensions": {"$.context.jwt.role": "[\"Basic\"]", "qualifiedModelId": "*", "$.context.jwt.sub": "*"},
      "tokens": [{"rate": 20000, "period": "minute"}]
    }
  ]'
```

在这个配置中，anthropic.claude-fable-5 是一个受限制模型。只有具有 [“Advanced”, “Beta”] 角色的用户才能调用它，每个用户获得 80,000 TPM，用于基准测试和评估工作负载。[“Basic”] 和 [“Advanced”] 用户都被以零速率阻止*调用该模型。同样的模式也适用于其他受限制模型（openai.gpt-5.6-luna 和 openai.gpt-5.6-terra），请确保为每个模型按相同结构添加条目。对于普遍可用的模型，Basic 用户通过通配符条目每人获得 20,000 TPM，而 Advanced 用户每人获得 40,000 TPM。

按照最具体匹配优先的规则，特定条目优先于通配符。当 María（sub：“María”，role：[“Advanced”, “Beta”]）调用 anthropic.claude-fable-5 时，gateway 会匹配显式条目，并对 María 个人应用 80,000 TPM。如果 María 耗尽了 80,000 TPM 限额，其他 Beta 用户不会受到影响，因为 `$.context.jwt.sub` 上的 * 为每个用户提供了各自独立的桶。当 John（sub：“John”，role：[“Advanced”]）尝试调用 anthropic.claude-fable-5 时，gateway 会匹配该模型的显式 [“Advanced”] 条目，该条目将请求速率设为零，从而阻止调用。当 John 调用一个普遍可用的模型（如 anthropic.claude-sonnet-5）时，该模型-角色组合不存在显式条目，因此 gateway 会回退到针对 [“Advanced”] 的通配符条目，应用 40,000 TPM。当 Arnav（sub：“Arnav”，role：[“Basic”]）调用同一个普遍可用模型时，他通过 Basic 通配符条目获得 40,000 TPM。

你还可以组合维度，例如用 [“`$.context.jwt.role`”, “`targetName`”] 实现按角色按 target 的请求限制，用 [“`$.context.jwt.sub`”, “`targetName`”] 实现按用户按 target 的组合请求与 token 限制，或用 [“`$.context.jwt.role`”, “`toolName`”] 实现按角色按工具的请求限制。更多速率限制配置，请参见[速率限制 API 示例](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-rate-limits-examples.html)。

## 面向 agentic 工作负载的速率限制

考虑以下 AgentCore gateway 配置：某个用户调用 AWS Documentation Agent。该 agent 通过 gateway 使用两个下游资源：用于文档搜索与检索的 `Docs` MCP target，以及用于通过 anthropic.claude-sonnet-5 模型进行推理的 `BedrockMantle` inference target。以下架构图展示了这一点：

图 3：包含下游资源消耗的 agentic 工作负载速率限制

对于 agentic 工作负载，需要考虑两类速率限制：

- 针对 agent 调用的速率限制。

第一类限制保护用户或其他服务调用 agent 的频率。这些是限定在 agent target 本身的请求（RPM）和连接（CPS）限制。在最简单的层面上，你可以仅以 `targetName` 作为维度，例如 {“`targetName`”: “awsdocsagent”}，这样所有用户共享一个调用上限。为了更精细的控制，可以将 `targetName` 与用户维度配对，例如 [“`targetName`”, “`$.context.jwt.role`”] 或 [“`targetName`”, “`$.context.jwt.role`”, “`$.context.jwt.sub`”]，以限制每个用户组或单个用户调用 agent 的频率。

- 针对 agent 所消耗资源的速率限制。

第二类限制保护 agent 在每次调用时所消耗的下游资源。AWS Documentation Agent 会触发多个下游请求。该 agent 调用 `Docs` MCP target 进行文档检索，并调用 `BedrockMantle` target 进行 inference。你如何对这些下游调用进行速率限制，取决于 agent 在调用这些资源时如何向 gateway 进行身份验证。

如果 agent 基于用户的传入 JWT token 执行 [on-behalf-of](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/on-behalf-of-token-exchange.html)（OBO）token 交换，那么下游请求会携带原始用户的身份。所有现有的基于用户的速率限制都适用。你之前配置的按角色和按用户限制将对 agent 的下游调用生效，就像用户直接发起这些调用一样。

然而，如果 agent 执行 machine-to-machine 授权以获取新 token（例如 [client credentials](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/common-use-cases.html#machine-to-machine-auth) 流程），那么下游请求携带的是 agent 自身的身份，而非调用方的身份。在这种情况下，基于用户的速率限制将无法匹配用户的 claim。你应该添加用于标识 agent 本身的速率限制，根据你的身份提供方，使用一个能唯一标识 agent 的 claim，例如 `$.context.jwt.azp`（authorized party），并相应地进行限制，以防止单个 agent 耗尽共享资源。

## 速率限制最佳实践

使用 AgentCore gateway 创建速率限制时，请遵循以下最佳实践：

- 如果你使用 Policy in AgentCore 来强制执行 RBAC 授权，理解评估顺序非常重要。速率限制先应用；AgentCore Policy 随后评估。这意味着，即使用户或角色最终被 AgentCore Policy 拒绝访问，其请求仍会在拒绝发生之前消耗速率限制桶。为避免这种消耗，请创建一个速率限制条目，显式地为 AgentCore Policy 会阻止的用户或组分配零速率，这样可以确保请求在速率限制层就被拒绝，而不会耗尽授权调用方可用的预算。
- gateway 会优先评估维度键更多的速率限制（更具体的限制优先）。在维度数量相同的情况下，gateway 会优先评估速率更严格（更低）的速率限制。评估在首次拒绝时短路，这意味着一旦请求被拒绝，gateway 就不会再评估其余的速率限制。请设计你的速率限制配置，使最严格的限制位于最高维度层级（例如，三键 [“`$.context.jwt.role`”,“`qualifiedModelId`”,“`$.context.jwt.sub`”] 限制）。
- 无法创建维度键相同但顺序不同的两条速率限制。例如，你不能在同一个 gateway 上创建一条使用 [“`$.context.jwt.role`”, “`qualifiedModelId`”, “`$.context.jwt.sub`”] 维度键、另一条使用 [“`qualifiedModelId`”, “`$.context.jwt.role`”, “`$.context.jwt.sub`”] 维度键的速率限制。不过，维度键的顺序很重要。当一条速率限制有多个维度键时，你声明它们的顺序决定了通配符的使用方式。兜底默认值 * 只能出现在末尾位置。如果你在第 N 个位置使用 *，那么其后所有位置也都必须是 *。这种仅限末尾的约束有助于实现可预测的匹配行为。要理解这一行为，请参见[示例](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-rate-limits-enforcement.html#gateway-rate-limits-enforcement-entry-matching)。
- 避免使用高基数或无界的 JWT claim 作为维度键（例如 `$.context.jwt.jti`、`$.context.jwt.nonce` 或 request ID）。这些会创建数量无限的速率桶，并可能降低速率限制的有效性。应改用稳定、有界的标识符，例如 sub、role、team 或 tier。
- gateway 对速率限制评估采用 fail-open 语义。由于 fail-open 行为，不要仅将速率限制作为安全边界。应将速率限制用于流量管理和服务质量，并使用身份验证、授权和 [AWS WAF](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-waf.html) 规则来实施安全强制。
- 在你的 AgentCore gateway 上启用[应用日志](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-gateway-metrics.html)。这使你能够访问[速率限制日志](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-rate-limits-enforcement.html#gateway-rate-limits-enforcement-tracing)。对于每个评估了客户速率限制的请求，gateway 都会在 server span 上发出 [OpenTelemetry (OTEL)](https://opentelemetry.io/) span 属性。使用这些属性进行调试和监控。
- 确保包含一个兜底条目，为简单起见，考虑一个只有单条速率限制的 gateway：

```
aws bedrock-agentcore-control create-gateway-rate-limit \
  --gateway-identifier my-gateway-abc1234567 \
  --dimension-keys '["$.context.jwt.sub"]' \
  --description "Per-sub request limit" \
  --entries '[
    {
      "dimensions": {"$.context.jwt.sub": "Arnav"},
      "requests": [{"rate": 100, "period": "minute"}]
    }
  ]'
```

在这个配置中，只有 Arnav 有显式条目。如果 John（`$.context.jwt.sub`: “John”）调用 gateway，该请求不匹配任何条目，速率限制实际上被跳过，John 会直接落到服务托管配额，没有任何客户定义的强制措施。添加一个通配符兜底条目，可确保所有没有显式条目的调用方都能获得自己独立的按用户速率限制桶：

```
aws bedrock-agentcore-control create-gateway-rate-limit \
  --gateway-identifier my-gateway-abc1234567 \
  --dimension-keys '["$.context.jwt.sub"]' \
  --description "Per-sub request limit" \
  --entries '[
    {
      "dimensions": {"$.context.jwt.sub": "Arnav"},
      "requests": [{"rate": 100, "period": "minute"}]
    },
    {
      "dimensions": {"$.context.jwt.sub": "*"},
      "requests": [{"rate": 50, "period": "minute"}]
    }
  ]'
```

现在，John、María 以及任何其他调用方都通过通配符各自获得独立的 50 RPM 桶，而 Arnav 保留其显式的 100 RPM 分配。如果没有兜底条目，未匹配的调用方将完全绕过速率限制。

更多最佳实践，请参见 AgentCore gateway [文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-rate-limits-best-practices.html)。

## 结论

在本文中，我们介绍了如何在 Amazon Bedrock AgentCore gateway 上配置速率限制以治理 AI 流量，在角色和用户之间强制实现公平使用，同时帮助防止任何单一调用方或工作负载耗尽共享容量。我们演示了如何分层设置速率限制：用户级限制用于实现按角色和按用户的公平性，target 级限制用于保护下游服务容量，以及多维限制将用户与 target 结合起来以实施精细的速率限制。我们还讨论了 agentic 工作负载的速率限制注意事项，其中下游资源消耗会因 agent 向 gateway 进行身份验证的方式而有所不同。

速率限制只是全面流量管理策略中的一层。结合用于身份验证的 AgentCore Identity、用于基于角色访问控制的 Policy in AgentCore，以及用于可观测性的应用日志，这些工具使你能够自信地运营生产级 AI gateway，促进公平使用、保护后端服务，并在工作负载扩展时保持可用性。
