# 技术深潜：AgentCore Payments 与 agentic commerce 的创新

这个行业正在进入一个世界：数以十亿计的生成式 AI agent 自主运行，代表人类行事、做出决策，并在没有人类干预的情况下完成任务。为支撑这一转变，[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 提供了一个模块化、完全托管的平台，帮助开发者大规模构建、部署和运营生成式 AI agent。通过把服务器管理、安全与集成的复杂性抽象掉，AgentCore 充当基础基础设施层，让开发者腾出手来专注于最重要的事：agent 的逻辑。

这个 agentic 世界已经在重塑内容、API 与软件即服务（SaaS）供应商的运作方式。在 web 上，自动化流量正日益超过人类流量，而 agentic AI 是一个快速增长的细分领域。商业模式被重写，出版商与 API 供应商转向为 agent 访问量身定制的按使用付费模式。出版商与内容分发网络（CDN）开始拦截 agent 流量并将其变现。API 正在转向为 agentic 流量量身定制的按使用付费模式。这一上升趋势指向一个未来：数以十亿计的 agent 自主访问数以十亿计的端点，动态选择服务并实时完成交易，以把事办成。

尽管 AI agent 可以通过 API、MCP 与网页浏览完成复杂任务，但在访问付费服务与内容时，它们会撞上一堵墙。访问外部服务需要与每个供应商分别订阅并管理独立的账单账户，这带来可观的开销。更麻烦的是，大多数 API 调用与内容访问只值几分钱，而信用卡这类传统支付方式包含固定的每笔交易手续费（例如 USD $0.30），使其在高频微交易上在经济上不可行。把第三方钱包、支付编排、对 [x402](https://www.x402.org/) 与 MPP（一些流行的机器对机器支付协议）这类 agentic 协议的支持、边缘情况处理，以及端到端可观测性接在一起，可能要花上数月的工作。除了集成复杂性之外，开发者还必须从零构建治理与预算护栏，以帮助防止失控的花费，并满足支付流程所要求的严格安全与监管合规要求。

[Amazon Bedrock AgentCore Payments](https://aws.amazon.com/blogs/machine-learning/agents-that-transact-introducing-amazon-bedrock-agentcore-payments-built-with-coinbase-and-stripe/) 就是为应对这种复杂性而专门构建的。它现已正式可用，能向付费外部服务发起即时支付，而无需为每个供应商手工配置账单；它提供稳定币支持以实现成本高效的微交易，让低于一美分的交易在经济上可行；它还提供可配置的花费护栏，让你对 agent 预算与交易限额拥有细粒度控制。在本文中，我们带你深入技术细节，剖析 AgentCore Payments。

## 介绍 Amazon Bedrock AgentCore Payments

Amazon Bedrock AgentCore Payments 是 Amazon Bedrock AgentCore 内第一个托管服务，帮助 AI agent 用几行代码为付费 API、MCP 与内容自主执行微交易支付。它提供稳定币支持以实现成本高效的微交易，并提供可配置的护栏来控制 agent 花费，把开发者的工作量从数月缩短到数天。这个完全托管的服务构建在 AgentCore 的安全基础之上，加速了 agentic 支付工作流的上市时间。下图展示了 AgentCore Payments 的预览能力，以及它与相关 AgentCore 服务的交互方式。

## 挑战

为了构建一个真正对 agent 开发者有用的支付能力，团队梳理出了开发者在让自己的 agent 为付费 API、MCP 与内容付款时所面临的关键挑战与问题。

### 我如何为我的 agent 提供资金？

对开发者而言，第一个关键障碍是想清楚如何为支撑其 agent 交易的账户提供资金。由于涉及真金白银，这不仅是管线问题，更是安全问题。与第三方支付钱包集成是一个显而易见的选择，但开发者必须确认认证密钥没有被泄露。他们必须确认已就位的访问控制能够治理谁可以在钱包上执行操作、认证机制足够健壮且防篡改，以及系统中存在额外的安全层来防御未授权访问与欺诈。

为了对支付钱包做安全认证，AgentCore Payments 使用 [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-overview.html)。开发者创建一个 payment connector，即一个针对特定支付供应商的集成资源。这会在 AgentCore Identity 中自动供应一个 payment credential provider，它把支付凭证存放在安全的 token vault 中，并铸造 token 化的访问令牌，而不暴露原始凭证。这个 credential provider 专为高性能、安全的数字签名而设计。它支持 `EdDSA`、`ECDSA` 与 `ES256`，用于与支付供应商进行钱包操作。加密材料存放在 AWS Secrets Manager 中，不会从 API 返回。每个 payment connector 都关联一个唯一的 AgentCore 工作负载身份。该工作负载身份用于从 AgentCore credential provider 系统获取一个限定在此工作负载范围、一次性使用的访问令牌。工作负载身份与用户上下文之间的密码学绑定提供了多租户隔离。

在入站侧，该服务在访问 AgentCore Payments API 的同一请求管线内强制双重认证，即 OAuth 与 AWS SigV4，提供灵活的安全层。对于 OAuth 调用，入站 bearer token 会针对 AgentCore Identity 进行校验，并提取 JWT 声明，为下游操作推导用户身份。对于 SigV4，请求签名使用 AWS Identity and Access Management（IAM）进行校验。

### 我该选哪种支付协议，又需要在它之上构建什么？

agentic 支付领域的格局被众多相互竞争的协议切得支离破碎，让开发者不堪重负，也不清楚哪一种才契合自己的具体用例。上手单一协议就要耗费大量时间与精力，因为每种协议都有各自的细节（版本管理、认证流程、交易模型），开发者在构建任何可用于生产的东西之前必须先理解它们。除协议选择之外，开发者还必须自己构建抽象层来处理这些复杂性。随着排列组合的增长，工作量会成倍增加：跨多个钱包供应商（每一家的认证与钱包 API 都不同）、支付网络与协议来构建，会把看似一次集成的任务变成一个庞杂的组合矩阵。

为应对这一点，AgentCore Payments 提供支付编排——一个专为承载 agentic 支付复杂性而构建的核心引擎。它位于你的 AI agent 与支付供应商之间，暴露单一的 `processPayment` 接口：接收一个支付请求，返回一份支付证明，agent 可以出示它来访问付费服务。AgentCore Payments 通过自动管理 x402 与 MPP 等流行 agentic 支付协议的多步支付流程、重试与边缘情况，把协议复杂性抽象掉。它还处理协议版本之间的差异（例如 x402 v1 与 v2 在支付要求如何构造、期望哪些字段上不同），把这些转化为密码学网络特有的交易数据，实现支付证明生成算法，并通过供应商 API 安全地签署交易，同时强制你配置的花费上限。对于 x402 及“Exact”方案，该服务还支持 x402 内的“upto”方案，它使 agent 可以设置一个花费上限，而不是承诺一个固定价格。这解锁了真正的按推理付费与动态定价。编排器围绕可插拔模型来架构，每个支付协议与供应商都实现为独立接口。这意味着增加对新协议的支持不需要改动核心编排逻辑或面向开发者的 API。开发者继续调用同一个 `processPayment` 接口，编排器根据支付要求路由到正确的 connector 与协议处理器。

### 我如何确认 agent 不会在花费上失控？

agent 天生是自主的，这意味着不受约束的花费是一种真实的可能性。开发者需要以确定性方式实时强制执行花费限额的机制，使代表用户或企业运作的 agent 无法超出预定义的预算，无论这个预算是在会话级还是用户级。没有这些护栏，一次失控的 agent 交互就可能造成巨额的非预期成本。

当一个 agent 处理类似预订行程的用户请求时，它可能并行发起多笔支付（机票、酒店、租车），同时从同一笔预算中支取。如果一个操作在另一个操作完成写入之前读取了可用余额，结果就是陈旧状态与超额花费。在真实的并发负载下，这不是边缘情况，而是预期行为，而把它做错是快速破坏客户信任的一条路。AgentCore Payments 在基础设施层提供内置的花费限额强制，并按规模化运行来设计。花费上限作为 payment session 的一部分被配置——payment session 是一个带作用域、有时间界限的 agent 支付活动上下文，内置花费限额强制，在交易被处理之前生效。从那一点起，每次 `processPayment` 调用都要经过一个三阶段的交易工作流：首先，通过原子地扣减请求金额来预留可用的花费额度。然后通过供应商处理支付。最后，交易在成功时提交、在失败时回滚，把预留金额恢复到可用余额。无论是单个 agent 还是数以千计的 agent 同时对同一笔预算交易，都不会有陈旧读取、不会有覆盖、也不会有超额花费。开发者无需构建自定义的并发或加锁逻辑，就能在规模化下获得花费控制。

### 我如何审计 agent 的花费并衡量成效？

对于一个自主交易的 agent，开发者需要对其支付行为拥有完整可见性。这意味着要能审阅和审计 agent 做过的每一笔交易、把花费追溯到具体的会话或任务，并获取支付运营的高层指标，例如总花费、交易成功率与单位任务成本。没有健壮的可观测性，开发者就无法优化成本、发现异常，也无法证明投资回报。

AgentCore Payments 移除了这份负担。它交付一套三支柱的内建可观测性体系（指标、日志与 trace），直接发布到你的 AWS 账户中，无需任何埋点代码。每个 API 操作都会自动发出 Amazon CloudWatch 指标，涵盖成功次数、失败次数与延迟，并按操作与支付资源维度切分。`processPayment` 还会按 token 类型发出花费金额，因此你可以精确追踪 agent 在每种 token 类型上花了多少。结构化日志通过异步、批处理的管线投递，每条都携带支付资源上下文与请求 ID，用于端到端关联。分布式 trace 建立在 W3C trace context 传播之上，使用与 OpenTelemetry 兼容的 span。这些 span 会补充支付特有的属性，包括花费金额、剩余预算，以及会在顶层 span 上呈现多步签名链性能的 credential provider 遥测。合在一起，这为开发者与企业提供了对每一个支付事件的完整可见性、横跨整个执行栈的可追溯性，并让它们对 agent 如何花钱拥有透明度与掌控力。

## 开始使用 Amazon Bedrock AgentCore Payments

要开始使用，请参阅这份[文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments-prerequisites.html)中的先决条件。你可以通过多种界面设置并使用 AgentCore Payments。

- AWS SDK for Python（Boto3）
- AWS 管理控制台
- [Amazon Bedrock AgentCore SDK ](https://github.com/aws/bedrock-agentcore-sdk-python)
- [Strands Agents 与插件](https://strandsagents.com/docs/community/plugins/agentcore-payments/)
- LangGraph 中间件
- OpenClaw 插件
- AgentCore Payments skills，用于带内置 x402 钩子的 agent 原生集成

下面一节给出代码片段，演示设置并使用 Amazon Bedrock AgentCore Payments 的过程。

### 一次性配置

在向 AgentCore Payments 注册之前，你需要从支付供应商那里取得 API 凭证。对 Stripe，请从 Stripe Dashboard 的 Developers → API Keys 中获取你的 secret API key。对 Coinbase，请在 Coinbase Developer Platform 中创建一个 CDP API key，它会签发一个 key name 与私钥对。

AgentCore Payments 使用这些凭证创建一个 payment connector，即一个针对特定供应商的集成，充当 AgentCore Payments 与你所选供应商之间的桥梁。payment connector 注册在一个 payment manager 之下，后者是把你的 connector 与 instrument 归组在一起的顶层实体，并提供统一的执行引擎来管理支付流程，从钱包供应一直到支付处理。

你只需在此设置过程中提供一次这些凭证。随后 AgentCore Identity 承担凭证存储的职责，使用安全的 token vault，使凭证在运行时不会暴露。agent 本身无法访问原始凭证。token 轮换由基础设施透明处理，而你保持对 credential provider 访问权限的完整控制。只有被授权的角色才能使用 AgentCore Identity 生成一次性、短时效的 token。下面的代码[使用 AgentCore SDK](https://github.com/aws/bedrock-agentcore-sdk-python/tree/main/src/bedrock_agentcore/payments) 在一次调用中完成一次性设置。

```
from bedrock_agentcore.payments import PaymentClient

# Create PaymentClient
payment_client = PaymentClient(region_name="us-west-2")

# Create payment manager with connector and credential provider
response = payment_client.create_payment_manager_with_connector(
    payment_manager_name="myPaymentManager",
    payment_manager_description="myPaymentManager description",
    authorizer_type="AWS_IAM",
    role_arn=ROLE_ARN,
    payment_connector_config={
        "name": "myPaymentConnector",
        "description": "myPaymentConnector description",
        "payment_credential_provider_config": {
            "name": "myCoinbasePaymentCredential",
            "credential_provider_vendor": "<PROVIDER>",
            "credentials": {
                "api_key_id": API_KEY,
                "api_key_secret": API_KEY_SECRET,
                "wallet_secret": WALLET_SECRET,
            },
        },
    }
)

# Extract details from response
payment_manager_arn = response["paymentManager"]["paymentManagerArn"]
payment_connector_id = response["paymentManager"]["paymentConnectorId"]
```

### 设置支付工具

在 payment manager 设置好之后，你通过引用 payment manager 与 payment connector 来创建一个*支付工具*。支付工具就是你的 agent 用来自主交易的东西。一个支付工具本质上是一个嵌入式钱包，一个由支付供应商背书、但由最终用户自行托管的钱包地址。

创建之后，该工具必须先注入资金，并且必须授予签名授权，agent 才能交易。这些是最终用户的操作，应在你的 agent 中使用该支付工具之前完成。具体流程因支付供应商而异：

- **Coinbase** – 你会在支付工具的响应中收到一个 `redirectUrl`，它指向 Coinbase 托管的 WalletHub。把用户重定向到那里，以授予签名权限并转账资金。
- **Stripe** – 你使用提供的 URL 模板托管一个前端页面，最终用户可以在那里执行同样的操作。

两家供应商都支持三种流程：

- **加密资产到加密资产（Crypto-to-crypto）** – 从已有的加密钱包转入。
- **法币到加密资产（Fiat-to-crypto）** – 通过托管 UI，从信用卡或借记卡、或从 Apple Pay 这类第三方钱包转入。
- **委托签名（Delegated signing）** – agent 使用委托密钥代表用户签名。

```
from bedrock_agentcore.payments import PaymentManager

# Initialize manager
manager = PaymentManager(
    payment_manager_arn=payment_manager_arn,
    region_name="us-west-2"
)
instrument = manager.create_payment_instrument(
    user_id="test-user-123",
    payment_connector_id="codeverifymycoinbaseconnector-sfp0lynfjc",
    payment_instrument_type="EMBEDDED_CRYPTO_WALLET",
    payment_instrument_details={
        "embeddedCryptoWallet": {
            "network": "ETHEREUM",
            "linkedAccounts": [{
                "email": {
                    "emailAddress": "test@example.com"
                }
            }]
        }
    },
)
```

### 创建支付会话

你创建一个 payment session，作用域限定在已注入资金的工具与最终用户上，并可选地带上明确的支付限额与超时。这个会话就是 agent 的财务边界；它精确地定义了可以花多少、可以花多久。会话 ID 与 instrument ID 在任务开始时传给 agent。agent 无法延长自己的会话，也无法超出会话支付限额花费。

```
# Create a payment session
session_response = manager.create_payment_session(
    user_id="test-user-123",
    limits={
        "maxSpendAmount": {
            "value": "100.00",
            "currency": "USD"
        }
    },
    expiry_time_in_minutes=60
)
```

### 自主处理支付

当 agent 收到用户任务时，它可能会为服务、API 或内容调用付费端点。这些付费端点会向 agent 返回 `402 Payment Required` 状态。AgentCore Payments 理解 X402 支付协议（包括 X402 版本 1 与版本 2）以及 MPP。该服务会精确处理好如何生成 agent 解锁服务所需的支付证明。

agent 调用 `ProcessPayment`，传入会话 ID、instrument ID 与 x402 支付负载。在幕后，AgentCore Payments 编排支付处理。它提取执行密码学交易所需的属性，应用支付限额护栏，并签署交易以生成支付证明。这套精心设计的编排有助于确保：即便多个 agent 同时对同一会话交易，预算也不会被超支。

```
payment_response = manager.process_payment(
    user_id="user-123",
    payment_session_id=PAYMENT_SESSION_ID,
    payment_instrument_id=PAYMENT_INSTRUMENT_ID,
    payment_input={
        "cryptoX402": {
            "version": "1",
            "payload": {
                "scheme": "exact",
                "network": "base-sepolia",
                "maxAmountRequired": "5000",
                "resource": "https://premiousEndpoint",
                "description": "Premium AI joke generation",
                "mimeType": "application/json",
                "payTo": PAY_TO_ADDRESS,
                "maxTimeoutSeconds": 300,
                "asset": "0xxxxxxxxxxxxxxxxxxxxxxxx",
                "extra": {"name": "USDC", "version": "2"},
            },
        }
    }
)
```

## AgentCore Payments 的用例

支付栈就位之后，你的 agent 可以通过单次 `ProcessPayment` 调用处理 x402 或 MPP 支付。同一套构建块——第三方（3P）钱包、会话作用域预算与支付协议——支撑了一系列 agentic 工作负载。

| **工作负载** | **agent 做什么** | **它如何付费** |
| --- | --- | --- |
| **研究 agent** | 在预算内查询多个付费数据源以汇总分析。 | 通过 HTTP 或 MCP 调用付费 API。支付插件为每个数据源处理 402 检测、签名与重试。 |
| **财务分析 agent** | 访问付费墙后的市场数据、交易服务与专有数据库。 | 在不同商户之间使用相同的支付模式，全部通过一个支付栈。 |
| **浏览器 agent** | 浏览有付费墙的网站，从多个站点提取内容。 | 在无头浏览器会话中拦截 402，完成支付，并在重试时注入证明头。 |
| **按智能付费 agent** | 把任务路由到最合适的 AI 模型，并按 token 付费。 | 每次调用都向模型供应商付费，而不是维护模型订阅。 |
| **按需存储 agent** | 以按使用付费的定价供应临时存储。 | 在请求时支付计算与存储资源费用，无需预先分配容量。 |

每个工作负载都使用相同的面向开发者的 API。区别在于 agent 拿它付费获得的内容去做什么，而不在于它如何付费。下面的示例会走一遍一个能为付费内容付款的研究 agent。

### 深入剖析：AI 驱动的研究助手

一位财务分析师问自己的 AI agent：*“分析 Amazon 的股票，并把它与行业基准做对比。”*

该 agent 需要三个付费来源：一个金融数据 API（每次查询 USD $0.50）、一个供应链分析供应商（每份报告 USD $1.20），以及一个基准数据库（每个数据集 USD $0.80）。应用后端创建一个预算为 USD $10.00 的会话，并把会话 ID 与 instrument ID 传给 agent。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/08/24/Screenshot-2026-08-24-at-6.04.56 PM.png)

*图 6：研究助手架构，展示端到端支付流程。*

agent 调用每个商户服务。每一个都返回 HTTP 402。AgentCore Payments 原子地检查会话预算，通过已配置的钱包供应商签署交易，并返回一份密码学证明。agent 带着证明重试，获得付费内容。三个商户、三笔支付，每笔一次 API 调用。总花费为 USD $2.50，出自 USD $10.00 的预算，剩余 USD $7.50。分析师在无需人工干预的情况下收到了完整分析。

开发者对整个支付流程的全部贡献就是几行插件配置。agent 的逻辑完全围绕研究质量：查询哪些来源、如何综合发现，以及何时停下。

**可与任何框架、任何模型配合。**无论你如何构建 agent，这个流程都是一样的。使用 Strands Agents 时，内置的 `AgentCorePaymentsPlugin` 会自动处理支付。对于其他框架，`ProcessPayment` 是一个标准的 REST 调用。模型选择同样如此。无论 agent 是用 Anthropic Claude、OpenAI GPT、Google Gemini 还是 Meta Llama 推理，支付流程都完全相同。

**可与 Amazon Bedrock AgentCore 的其余部分组合。**由于支付运行在工具调用层，它们能自然地与其他 AgentCore 服务配合。从前面的研究 agent 示例出发，再叠加以下内容：

- **AgentCore Gateway** – 在 Coinbase x402 Bazaar 上发现付费 MCP 工具，无需逐供应商注册。它提供一个 MCP 服务器，其中包含一份基于社会证明、元数据丰富度、描述质量与可用性筛选出的高质量端点清单。
- **AgentCore Tools** – 在同一工作流中使用 Browser 与 Code Interpreter 这类托管工具。Browser 工具浏览有付费墙的网站，并就地支付内容费用。Code Interpreter 处理买来的数据：运行分析、生成图表、转换数据集。无论由哪个工具触发支付，`ProcessPayment` API 都是同一个。
- **AgentCore Runtime** – 使用 `agentcore deploy` 部署 agent。`ProcessPaymentRole` 在基础设施层被强制执行。

增加更多 AgentCore 功能不需要改动支付配置。在支付基础设施被托管之后，你可以把精力放在改进 agent 本身上：添加新数据源、改进综合逻辑、扩展到新领域。这里列出的 AgentCore 服务并非全部。随着服务不断发展，同一套支付原语会延伸到新的能力上。
