# Exowatt 借助 SageMaker serverless 模型定制在准确率上超越前沿模型

Exowatt 构建模块化、可调度的太阳能系统，为 AI 数据中心这类能源密集型应用提供可靠电力。其旗舰产品 Exowatt P3 通过光学透镜收集太阳能，以热能形式存储在长时储热电池中，再通过热机按需发电。与并网的光伏系统不同，P3 在电表之后直接为数据中心供电，帮助数据中心无需等待长达数年的电网互联排队即可上线。Exowatt 构建了一支 AI agent 队伍，用于监视和分诊实时告警，并为太阳能系统的运营决策提供支持——这些工作常常发生在边缘侧，连接有限甚至没有连接。随着其队伍从测试台走向量产以及数千台现场部署单元，运行这些系统的智能层也必须随之扩展。

本文介绍 Exowatt 如何用 Amazon SageMaker AI serverless 模型定制构建一条可重复的 AI 流水线。这条流水线面向边缘和云端两个部署目标产出任务专用的微调模型，准确率高于前沿模型，成本最多低 49 倍。

这里描述的两个模型只是这条流水线的首批产出，而非最终目标。这次合作更持久的成果是流水线本身：一条从原始运营数据到经认证的训练集、再到微调模型和经评估的部署产物的可重复路径。Exowatt 现在只需几天而非几个月就能跑完这条路径。告警分诊与能源市场分析，只是同一方法适用的众多狭窄而高价值任务中的两个。

## 挑战：把 AI 用在实体能源基础设施上

Exowatt 的能源管理系统（EMS）运行在不断扩大的一批运营站点上。每个站点都在持续产生告警：某个硬件组件超出规格运行、连接断开、电压读数越界，以及类似事件。随着队伍规模向数千台现场单元扩展，人类操作员无法实时监控每个站点。Exowatt 需要一个 AI agent，能够读取每个站点的告警状态，并自主、可靠地采取或建议正确的下一步动作。

前沿模型无法解决这个问题，原因有三：

- 任务狭窄且专有。Exowatt EMS 上的告警分诊依赖其特定的硬件、数据和运行逻辑，通用前沿模型并不专门针对它。
- 它必须跑在边缘，没有 GPU，且常常没有互联网。许多站点连接有限或时断时续，因此依赖云端调用前沿模型的 agent，在连接中断时会让操作员失去覆盖。
- 成本无法在机队层面成立。把数千个站点的每一个运营决策都路由到前沿模型，对于一个持续重复的决策来说并不经济。

正是在这里，Exowatt 转向了模型定制。Exowatt 最初的微调工作流依赖这样的流程：先选一个 open-weight 模型、构建容器、创建自定义训练 recipe，然后才能跑任何实验。这对模型实验是一个重大阻碍。此外，他们还得自行决定模型微调的 GPU 硬件需求。随着团队加快实验节奏，每次运行都要先选定具体的 GPU 实例类型，然后等待这批自选容量可用。当选定的实例类型不可用时，这会推迟运行开始，甚至完全阻塞。

他们需要一个足够小、能在无 GPU 的边缘控制器上运行的模型，同时在特定任务上足够准确、可与前沿模型相比并自主行动。微调弥合了这一差距：一个紧凑、任务专用的模型，既能在云端部署，也能在边缘部署。

## 解决方案概览

Exowatt 通过在 Amazon SageMaker AI 上采用云原生、serverless 的模型定制方式来应对这些挑战。同一条训练流水线为两个部署目标（边缘与云端）产出微调模型。

Exowatt 在第一个用例（边缘告警分诊）中把这一方式实现在 Qwen3-1.7B 模型上，随后在第二个用例（云端能源市场分析）中把同样方式用于 Qwen3-14B 模型。公司计划复用这套方案，在整个机队范围内构建更小、任务专用的模型。

以下七项 AWS 服务支撑这条 AI 流水线，无需管理任何实例、集群或 endpoint：

| **AWS 服务** | **用途** |
| --- | --- |
| **Amazon Simple Storage Service（Amazon S3）** | 数据、manifest、模型产物与测试集 |
| **Amazon SageMaker AI serverless 微调** | 每一次微调运行，从 Public Hub recipe 启动 |
| **Amazon SageMaker AI serverless 评估** | 每个候选模型 2,000 条答案，作为托管作业评分 |
| **SageMaker Model Registry** | 每次完成的微调及其证据与指标 |
| **Amazon Bedrock Custom Model Import** | 为 Cloud EMS 托管微调后的 Qwen3-14B，由 Cloud EMS 服务私有调用。无空闲成本 |
| **Amazon Bedrock（Claude、Qwen3）** | 释义改写（训练数据中每条答案三次改写）与前沿模型基准测试 告警分诊的释义改写使用 Amazon Bedrock 上的 Qwen3-VL-235B。能源市场的释义改写使用 Amazon Bedrock 上的 Claude Sonnet 4.6。 |
| **AWS Lambda + Amazon EventBridge** | serverless 评估的评分器，以及定时对自定义模型做 keep-warm 调用 |

工作流分为三个阶段：

**模型定制（云端）：**Exowatt 使用 serverless 模型定制，在 SageMaker AI 上以 Low-Rank Adaptation（LoRA）和监督微调（SFT）微调 open-weight 基础模型。由于 serverless 训练按需分配容量，团队每天可以跑多个实验，而不必等待自选的 GPU。评估之后，最佳模型会注册到 SageMaker AI Model Registry。

**边缘部署：**对于告警分诊这类对延迟敏感、连接受限的工作，微调后的 Qwen3-1.7B 模型会被冻结、量化为 GGUF 格式，并通过场站控制器在边缘的 Kubernetes pod 内用 llama.cpp 运行。这条路径不需要 GPU，且在没有互联网连接的情况下也能运行。

**云端部署（弹性）：**对于联网的机队级分析，微调后的 Qwen3-14B 能源市场模型通过 Amazon Bedrock Custom Model Import 提供服务，它无空闲成本，仅在模型活跃时计费。

## 为什么选择 Amazon SageMaker AI serverless 模型定制

Amazon SageMaker AI serverless 模型定制服务提供了丰富的 open-weight 模型选择，并配有来自 SageMaker Public Hub 的现成微调 recipe，因此团队无需构建和优化自定义训练容器——这项工作否则可能要花上数周。对 Exowatt 而言，这把微调从稀缺的、需要排期的事件变成了日常的按需操作。这让快速的「实验—测试」循环变得可行，同时保持实验成本低廉。

在预置 GPU 上微调需要选定具体的实例类型、申请该容量、等待其可用、运行作业，并在持有实例的整个期间为其付费。持有时间通常还包含实验之间的空闲时间——因为专用实例会一直开着。对于要跑大量实验的小团队来说，这会拖慢创新并推高成本。Amazon SageMaker AI serverless 模型定制会自动管理和编排运行微调作业所需的基础设施，免除容量管理的痛苦，并且只为微调作业实际运行的时间计费。

## 用例 1：用 Qwen3-1.7B 做边缘告警分诊

Exowatt 的站点全天候产生告警。一个部署在场站上的紧凑模型会把每条告警与站点自身的状态和遥测一起读取，并返回一个小的固定分类集合中的某一项，同时附带所引证据（例如系统离线、组件降额运行或传感器不匹配）；当证据不足时则明确弃权。

### 模型选择与训练数据

团队先用提示词加 guardrail 的方式试了 Qwen3-8B，效果停滞在目标之下（macro-F1 为 0.735）。微调后的 Qwen3-1.7B 改变了局面：参数大约只有五分之一，却在这个狭窄的单轮任务上超过了 Qwen3-8B 加提示词的组合，同时小到足以在无 GPU 的边缘侧推理。他们还试了 13 个微调后的 Qwen3-8B 候选模型、覆盖 12 个数据集版本，始终没能超过加提示词的 8B 基线。而数据更多样的更小模型做到了。

训练集小而精：共 2,522 条样本，由 684 条基于生成的站点场景的已核实决策，加上 1,838 条经认证的释义改写构成——后者在改写措辞的同时保持每条决策不变。释义由 Amazon Bedrock 上的 Qwen3-235B 生成，花费约 3.72 美元。只有确定性检查确认决策、标签、证据引用以及每一个数字都未改变时，该释义才会被保留（2,218 个候选中通过了 1,838 个）。有一个故障族被完全排除在训练之外，另有 320 个案例留作测试。

### 训练与部署

在 SageMaker serverless 微调上，训练约 32 分钟完成，花费约 20–25 美元。模型量化为 8 位（约 1.71 GiB），在站点现有 CPU 服务器上的 6 GiB llama.cpp pod 中离线运行。它也能在 t3.2xlarge 实例类型上运行。

## 用例 2：用 Qwen3-14B 做云端能源市场分析

可调度的储能把「时机」变成了运营决策：每个站点都要不断决定为自身负荷保留多少储能、何时释放；对于并网站点，市场状况还会影响这一选择。微调后的模型读取一份六小时的实时市场数据包（约 90 行，包含实时价格、日前预测和电网通知），并在约四秒内返回五种市场事件之一（例如价格尖峰或稀缺加价）。每一项结论都绑定到具体的数据行，以支撑调度策略。

### 为什么选 Qwen3-14B

选择 Qwen3-14B 的原因是：它受 Amazon Bedrock Custom Model Import 支持；它作为 SageMaker Public Hub 模型提供，并带有现成的 LoRA recipe（无需管理自定义容器或实例类型）；而且约 28 GiB 的体积足够小，能以经济的方式提供服务。

### 训练数据与流程

Exowatt 使用取自五年历史的得克萨斯州电力可靠性委员会（ERCOT）公开市场数据微调该模型（约 1.63 亿行，分布在 12 张表中）。团队用规则将这些数据标注为 25,000 条样本（22,000 条用于训练、1,000 条用于验证、2,000 条留作测试）。随后，他们让 Amazon Bedrock 上的 Anthropic Claude Sonnet 4.6 改写每条样本的措辞，同时保持标签和数值字段不变，把训练集扩展到 86,281 行。

训练只跑了一个 LoRA epoch（rank 16，alpha 32），在托管 serverless 微调上约 8.5 小时完成，期间最多同时运行四个作业。从最初的方案到冠军模型在 Cloud EMS 中提供服务，团队在六天里跑了 23 个作业、约 155 小时的托管训练。

决定性的提升来自释义的多样性：每条答案增加三次改写，把 macro-F1 从 0.950 提升到 0.975。基础模型只得到 0.415 的 macro-F1——它能产出合法的 JSON，但还不了解这个市场。微调解决了这个问题。

### 部署

合并后的 checkpoint 在约 14 分钟内导入 Amazon Bedrock Custom Model Import。模型无空闲成本，仅在活跃时按每小时 6.86 美元计费。

## 基准测试结果

在边缘告警分诊任务上，微调后的 Qwen3-1.7B 从一个无法给出有效答案的模型，变成在 320 个测试案例上达到 0.911 macro-F1，超过所有前沿基线。把完全相同的「微调—评估」循环用于 2,000 个测试案例的能源市场任务，Qwen3-14B 达到 0.975 macro-F1，同样超过前沿基线，而成本只占一小部分。两个案例中，一个小巧的微调模型都在特定任务上击败了远比它大的通用模型。

两个模型都返回严格的 JSON，其中每一项结论都引用具体的输入数据行。任何不受支持的结论都会在到达操作员之前被丢弃，这正是团队能在自主的实体环境中信任小模型的原因。

## 业务收益

**更快的迭代与更快的上市时间：**Exowatt 仅用九天就把定制模型从实验推进到生产。如果团队必须自行构建和优化自定义容器与训练 recipe、申请 GPU 并管理基础设施，这个过程可能要花几个月。借助 SageMaker AI serverless 模型定制，团队约 32 分钟训练完 Qwen3-1.7B、约 8.5 小时训练完 Qwen3-14B，无需申请容量，最多可同时运行四个训练作业。在能源市场用例中，Exowatt 跑了 23 个作业、总计约 155 小时的托管训练，并在六天内从基础模型推进到微调模型在 Cloud EMS 中提供服务。合并后的 checkpoint 在约 14 分钟内导入 Amazon Bedrock。端到端流水线使用了七项 AWS serverless 服务，Exowatt 无需管理任何实例、集群或 endpoint。

**相比前沿模型更高的准确率：**两个微调模型都在各自任务上击败了更大的前沿模型：Qwen3-1.7B 达到 0.911 macro-F1（Claude Sonnet 4.6 为 0.698），Qwen3-14B 达到 0.975（Claude Opus 4.7 为 0.625）。

**两种部署的成本都更低：**在云端，Qwen3-14B 以每 1,000 条答案 $0.60 提供服务，而 Claude Opus 4.7 为 $29.26（约低 49 倍），并且无空闲成本，在 Amazon Bedrock Custom Model Import 上仅在活跃时按每小时 6.86 美元计费。在边缘，量化后的 Qwen3-1.7B 运行在站点现有的 CPU 上，没有按次推理成本，也不依赖网络连接。

**有据可依、低风险的输出：**在两个模型中，证据围栏都移除了每一项未引用证据的结论（即任何来源、字段或取值与输入不完全字面匹配的证据引用），边缘模型在不确定时会弃权而不是猜测。正因如此，团队才能让它在某站点的云端托管副本上以影子模式自主运行。

## 经验总结

**针对特定任务，更小的微调大语言模型可以超过大型前沿模型：**微调后的 Qwen3-1.7B 和 Qwen3-14B 模型各自在目标任务上超过了前沿模型，以显著更小的模型提供了更高的准确率，成本只占一小部分。

**数据质量与多样性胜过原始数据量和额外 epoch：**对于范围严格限定的任务，数据质量比模型规模或数据量更重要。在告警分诊模型上，更多已核实的训练多样性把 macro-F1 从 0.584（仅用 684 条已核实决策训练）提升到 0.911（使用释义扩充后的 2,522 行集合）。仅仅在同样的行上跑更多 epoch 反而更差：一次对照运行在 684 条原始行上训练 11 个 epoch（相同的步数），只达到 0.879。贯穿始终，精编的数据比数据集大小更重要。

**去掉资源预置这一步会改变团队的工作方式：**当训练运行不再需要等待 GPU 容量时，微调就从罕见事件变成了日常的、迭代式的操作。

**一条训练流水线服务两个部署目标：**把模型训练与部署分离，使 Exowatt 能用同一条流水线同时支持离线边缘部署和联网的机队级分析，简化运维并加快云端的模型部署。

## 结论

Exowatt 现在拥有了一条可复用的 AI 流水线，能把一个任务从模型特定的数据准备一路带到模型部署。Exowatt 不打算用一个模型去适配不同任务，而是计划把同样的微调原则应用到不同任务上——每个任务有自己的数据、专用模型和评估——随着新设备类型和市场任务上线，在整个机队中推广。

这一模式可以推广到能源行业之外。各行业的 AI 工程师、数据科学家和客户都能采用同样的原则。把 Amazon SageMaker AI serverless 模型定制当作低开销的 AI 流水线，用来微调小巧的任务专用模型，然后把它们部署到工作真正发生的地方：在连接或延迟有要求时部署到边缘，对于弹性工作负载则通过 Amazon SageMaker AI 这样的托管云端 endpoint 提供服务。

了解更多，请参阅 [Amazon SageMaker AI serverless 模型定制](https://aws.amazon.com/sagemaker/ai/model-customization/) 和 [Amazon Bedrock](https://aws.amazon.com/bedrock/)。
