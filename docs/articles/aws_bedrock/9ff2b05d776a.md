# 使用 Amazon Nova Sonic 和 Amazon Bedrock AgentCore 构建多 agent 语音助手

[Amazon Nova Sonic](https://aws.amazon.com/ai/generative-ai/nova/speech/) 是一个基础模型，可为生成式 AI 应用创建自然、拟人的语音到语音对话，让用户能够通过语音与 AI 实时交互，并具备理解语气、保持自然流畅以及执行操作的能力。

多 agent 架构为生产级语音助手提供了一种模块化、健壮且可扩展的设计模式。本文探讨 Amazon Nova Sonic 语音 agent 应用，并演示它们如何与 [Strands Agents](https://strandsagents.com/latest/documentation/docs/) 框架的子 agent 集成，同时利用 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 构建高效的多 agent 系统。

## 为什么选择多 agent 架构？

设想开发一个财务助手应用，负责用户入驻引导、信息收集、身份验证、账户查询、异常处理，并按预定义条件转接给人工客服。随着功能需求扩展，语音 agent 不断新增查询类型。系统提示词变得极其庞大，底层逻辑也愈发复杂，这揭示了软件开发中一个长期存在的挑战：单体式设计会导致系统难以维护和增强。

可以把多 agent 架构想象成组建一支由专业 AI 助手构成的团队，而不是依赖单个全能助手。就像公司把职责划分到不同部门一样，这种方法把复杂任务拆解为更小、更易管理的片段。每个 AI agent 都成为特定领域的专家——无论是事实核查、数据处理，还是处理专业请求。对用户而言，体验是无缝的：没有延迟、没有音色变化，也没有可见的转接。系统在后台运作，指挥每个专家 agent 在恰当的时刻介入。

除了模块化和健壮性之外，多 agent 系统还具备类似微服务架构的优势，微服务是流行的企业软件设计模式，它提供可扩展性、分布性和可维护性，同时让组织能够复用已为其大语言模型（LLM）驱动的应用开发的 agentic 工作流。

## 示例应用

在本文中，我们参考 [Amazon Nova Sonic workshop 多 agent 实验](https://catalog.workshops.aws/amazon-nova-sonic-s2s/02-repeatable-pattern/05-multi-agent-agentcore)的代码，该实验以银行语音助手作为示例，演示如何在 Amazon Bedrock AgentCore 上部署专业化的 agent。它以 Nova Sonic 作为语音接口层，并充当编排器，把详细查询委派给用 Strands Agents 编写、托管在 [AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 上的子 agent。你可以在 [GitHub repo](https://github.com/aws-samples/amazon-nova-samples/tree/main/speech-to-speech/workshops/agent-core) 上找到示例源代码。

在银行语音 agent 示例中，对话流程以问候和收集用户姓名开始，随后处理与银行业务或抵押贷款相关的查询。我们使用三个托管在 AgentCore 上的二级 agent 来处理专业化逻辑：

- Authenticate 子 agent：使用账户 ID 和其他信息处理用户身份验证
- 银行子 agent：处理账户余额查询、对账单及其他银行业务相关查询
- 抵押贷款子 agent：处理抵押贷款相关查询，包括再融资、利率和还款方案

![sonic-multi-agent-diargam](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/10/09/ml-19759-diargam.png)

子 agent 是自包含的，各自处理自己的逻辑，例如输入校验。例如，认证 agent 会校验账户 ID，并在需要时向 Nova Sonic 返回错误。这简化了 Nova Sonic 中的推理逻辑，同时让业务逻辑保持封装，类似于软件工程的模块化设计模式。

## 通过 tool use 事件将 Nova Sonic 与 AgentCore 集成

Amazon Nova Sonic 依赖 [tool use](https://docs.aws.amazon.com/nova/latest/userguide/speech-tools.html) 与 agentic 工作流集成。在 Nova Sonic 的事件生命周期中，你可以通过 [promptStart](https://docs.aws.amazon.com/nova/latest/userguide/input-events.html) 事件提供 tool use 配置，该事件被设计为在 Sonic 收到特定类型的输入时启动。

例如，在下面的 Sonic 工具配置示例中，tool use 被配置为依据 Sonic 内置的推理模型来启动事件，该模型会对查询进行分类，以便路由到相应的银行子 agent。

```
[
    {
        "toolSpec": {
            "name": "bankAgent",
            "description": `Use this tool whenever the customer asks about their **bank account balance** or **bank statement**.  
                    It should be triggered for queries such as:  
                    - "What’s my balance?"  
                    - "How much money do I have in my account?"  
                    - "Can I see my latest bank statement?"  
                    - "Show me my account summary."`,
            "inputSchema": {
                "json": JSON.stringify({
                "type": "object",
                "properties": {
                    "accountId": {
                        "type": "string",
                        "description": "This is a user input. It is the bank account Id which is a numeric number."
                    },
                    "query": {
                        "type": "string",
                        "description": "The inquiry to the bank agent such as check account balance, get statement etc."
                    }
                },
                "required": [
                    "accountId", "query"
                ]
                })
            }
        }
    }
]
```

当用户向 Nova Sonic 提出诸如*“我的账户余额是多少？”*这样的问题时，Sonic 会向客户端应用发送一个 `toolUse` 事件，其中包含配置中指定的 `toolName`（例如 `bankAgent`）。应用随后可以调用托管在 AgentCore 上的子 agent 来处理银行业务逻辑，并把响应返回给 Sonic，Sonic 再为用户生成语音回复。

```
{
  "event": {
    "toolUse": {
      "completionId": "UUID",
      "content": "{\"accountId\":\"one two three four five\",\"query\":\"check account balance\"}",
      "contentId": "UUID",
      "promptName": "UUID",
      "role": "TOOL",
      "sessionId": "UUID",
      "toolName": "bankAgent",
      "toolUseId": "UUID"
    }
  }
}
```

## 语音多 agent 系统的最佳实践

多 agent 架构提供了出色的灵活性和模块化设计方法，让开发者能够高效地组织语音助手，并有可能复用现有的专业化 agent 工作流。在实现语音优先的体验时，有一些重要的最佳实践需要考虑，以应对这种模态特有的挑战。

- **平衡灵活性与延迟：**尽管使用 Nova Sonic tool use 事件调用子 agent 的能力带来了强大的功能，但它可能给语音响应引入额外的延迟。对于需要同步体验的用例，每次 agent 转接都代表交互流程中的一个潜在延迟点。因此，在设计时把响应时间放在心上非常重要。
- **为子 agent 优化模型选择：**从 Nova Lite 这样更小、更高效的模型入手处理子 agent，可以显著降低延迟，同时仍能有效处理专业化任务。把更大、能力更强的模型留给复杂推理，或在必须进行复杂自然语言理解时使用。
- **精心设计面向语音的响应：**语音助手在简洁、聚焦的响应下表现最佳，需要时可以再补充更多细节。这种方法不仅能改善延迟，还能营造更自然的对话流，契合人类对口头交流的预期。

## 考虑无状态与有状态的子 agent 设计

*无状态子 agent* 独立处理每个请求，不保留过往交互或会话级状态的记忆。它们实现简单、易于扩展，适合直接的一次性任务。然而，除非引入外部状态管理，它们无法提供具备上下文感知的响应。

*有状态子 agent* 则在多次交互之间保留记忆，以支持具备上下文感知的响应和会话级状态。这能带来更个性化、更连贯的用户体验，但也带来额外的复杂性和资源需求。它们最适合涉及多轮交互以及用户或会话级上下文缓存的场景。

## 结论

多 agent 架构为复杂的 AI 驱动工作流释放了灵活性、可扩展性和准确性。通过把 Nova Sonic 的对话能力与 Bedrock AgentCore 的编排能力结合起来，你可以构建协同工作的智能专业化 agent。如果你正在探索增强 AI 应用的方法，使用 Nova Sonic 和 AgentCore 的多 agent 模式是一种值得尝试的强大方法。
