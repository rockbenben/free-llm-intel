# Amazon Bedrock 上 Anthropic Claude 模型的结构化输出

Amazon Bedrock 现在为所有 Anthropic Claude 模型提供结构化输出支持，覆盖模型可用的 bedrock-runtime 和 bedrock-mantle 两个端点。

无论你是通过 Boto3 和 bedrock-runtime API 调用 Claude，还是通过 Messages API 和 bedrock-mantle 端点调用，现在都能收到符合 schema、遵循既定结构的 JSON 响应。你不再需要自定义解析、重试逻辑或后处理。

## 实际应用场景

借助 Amazon Bedrock 上 Claude 的结构化输出，你可以在各行各业自动化可靠、符合 schema 的任务。示例包括从财务收益报告和合规文档中提取每一个必需字段、把临床记录解析进电子健康记录（EHR），以及用一致且经过校验的结果丰富产品目录。你还可以分析合同中的关键条款、各方和义务，或者支撑智能化工单路由，让意图、情绪和实体始终匹配应用的数据模型。

## Amazon Bedrock 上结构化输出带来了什么变化

结构化输出使用约束解码，在 token 生成过程中就强制执行你的 JSON schema，而不是事后校验。模型不会生成违反 schema 的 token。这把输出格式从概率性变成了确定性。

现在两个 Amazon Bedrock 端点上都提供两种互补的机制：

| **功能** | **用途** | **使用场景** |
| --- | --- | --- |
| JSON Schema 输出格式 | 控制模型的响应结构 | 数据提取、报告生成、API 响应 |
| 严格工具使用 | 按 schema 校验工具参数 | 智能体工作流、函数调用、多步骤自动化 |

## 这对你意味着什么

每个响应都是合法的 JSON，因此你不会再遇到 `JSON.parse()` 错误或解析异常。响应也是类型安全的：字段类型被强制约束，必需字段始终存在。由于输出始终符合你的 schema，你不需要为重试来处理 schema 违规，集成也更可靠。结构化输出还会把响应限制为仅包含 schema 定义的字段，从而减少输出 token 数量，并可能降低高并发工作负载的推理成本。这些特性让结构化输出达到生产可用，因此你可以大规模部署，而无需额外的 schema 校验代码。

## 支持的模型与可用性

结构化输出可与[批量推理](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference.html)配合使用，因此你可以异步处理大量请求，同时仍然获得符合 schema 的输出。在 bedrock-runtime 端点上，它还可以配合跨区域推理使用，因此你无需额外配置就能在多个 AWS 区域使用。如果你需要实时响应，可以把结构化响应作为带类型的事件流式返回。

## 工作方式

当你用 JSON schema 发起请求时，幕后会发生以下事情：

- **Schema 校验 –** Amazon Bedrock 按受支持的 JSON Schema Draft 2020-12 子集校验你的 JSON schema。
- **语法编译 –** 对于新 schema，Amazon Bedrock 会编译一个语法产物（第一个请求可能稍慢一些）。
- **缓存 –** 编译后的语法会被缓存 24 小时，使后续请求更快。
- **约束生成 –** 模型生成的 token 会产生符合你 schema 的合法 JSON。

## 性能注意事项

在性能方面，使用新 schema 的第一个请求可能耗时更长，因为 Amazon Bedrock 在开始生成之前要先编译语法产物。完成首次编译之后，使用同一 schema 的后续请求开销极小，因为编译后的语法已被缓存。该缓存的作用范围限于你的账户，并从首次访问起持续 24 小时。更改 JSON schema 的结构会使缓存失效并触发重新编译，而只更改 name 或 description 字段则会保留缓存语法不变。

## 入门：使用 InvokeModel API（bedrock-runtime）的结构化输出

InvokeModel API 接受 Anthropic 原生的请求体，因此 schema 要放在 `output_config.format` 中，形式是 JSON 对象而不是 JSON 字符串。下面的示例展示了如何使用 boto3 配合 Anthropic Claude 模型，从客户邮件中提取结构化的潜在客户数据：

Python

```
import boto3
import json

REGION = "us-east-1" # Choose your preferred region
bedrock_runtime = boto3.client(service_name="bedrock-runtime", region_name=REGION)

# Define the JSON schema for structured output
schema = {
    "type": "object",
    "properties": {
        "name": {"type": "string", "description": "Customer name"},
        "email": {"type": "string", "description": "Customer email address"},
        "plan_interest": {"type": "string", "description": "Product plan of interest"},
        "demo_requested": {"type": "boolean", "description": "Whether a demo was requested"}
    },
    "required": ["name", "email", "plan_interest", "demo_requested"],
    "additionalProperties": False
}

# Make a request with structured outputs via the InvokeModel API
# (reusing the schema defined for the Converse example)
response = bedrock_runtime.invoke_model(
    modelId="global.anthropic.claude-sonnet-5-5",
    body=json.dumps({
        "anthropic_version": "bedrock-2023-05-31",
        "max_tokens": 512,
        "messages": [
            {"role": "user", "content": (
                "Paulo Santos (paulo@example.com) is interested in our Enterprise plan "
                "and wants to schedule a demo for next Tuesday at 2pm."
            )}
        ],
        "output_config": {"format": {"type": "json_schema", "schema": schema}}
    })
)

body = json.loads(response["body"].read())

# Check the stop reason before parsing
if body["stop_reason"] == "end_turn":
    result_text = next(b["text"] for b in body["content"] if b["type"] == "text")
    print(json.dumps(json.loads(result_text), indent=2))
elif body["stop_reason"] == "max_tokens":
    print("Response truncated: increase max_tokens and retry.")
```

JSON

```
{
    "name": "Paulo Santos",
    "email": "paulo@example.com",
    "plan_interest": "Enterprise",
    "demo_requested": true
}
```

响应符合你的 schema。无需额外校验。

更多 API 用法示例（包括 Messages API），请参阅随附的[示例 notebook](https://github.com/aws-samples/anthropic-on-aws/blob/main/notebooks/structured_outputs/structured-outputs-on-bedrock.ipynb)。

## 面向智能体工作流的严格工具使用

[Amazon Bedrock Mantle](https://docs.aws.amazon.com/bedrock/latest/userguide/endpoints.html) 面向带服务端工具、后台推理和有状态对话的智能体应用而设计。借助 bedrock-mantle 端点上的严格工具使用，你现在可以保证工具参数与输入 schema 完全匹配。下面的示例展示了如何定义一个带严格 schema 强制的工具：

```
Import json
from anthropic import AnthropicBedrockMantle

# Reusing the client created in the Messages API example
client = AnthropicBedrockMantle(aws_region="us-east-1")

message = client.messages.create(
    model="anthropic.claude-sonnet-5",
    max_tokens=512,
    messages=[{"role": "user", "content": "What's the weather like in San Francisco?"}],
    tools=[
        {
            "name": "get_weather",
            "description": "Get the current weather for a specified location",
            "strict": True,
            "input_schema": {
                "type": "object",
                "properties": {
                    "location": {
                        "type": "string",
                        "description": "The city and state, e.g., San Francisco, CA"
                    },
                    "unit": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"],
                        "description": "Temperature unit"
                    }
                },
                "required": ["location", "unit"],
                "additionalProperties": False
            }
        }
    ]
)

#Tool inputs conform to the schema
for block in message.content:
    if block.type == "tool_use":
        print(f"Tool: {block.name}")
        print(f"Input: {json.dumps(block.input, indent=2)}")
```

设置 `strict: true` 会把模型的工具输入约束为与你的 schema 完全匹配。location 字段始终是字符串，unit 字段始终是 celsius 或 fahrenheit。模型无法添加 schema 之外的字段，因此工具输入只包含 schema 规定的内容。

这对 Amazon Bedrock Mantle 上的智能体用例尤其有价值，因为在这些场景中，模型要用 web search 和代码解释器之类的服务端工具编排多步骤工作流。

## Claude 结构化输出的主要用例

结构化输出在三种常见模式中能最大程度地降低错误处理的复杂度：

- **数据提取：** 把发票、合同、邮件和通话记录中的字段提取成始终匹配 schema 的 JSON，可直接载入数据库或客户关系管理（CRM）系统。
- **可靠的智能体工具调用：** 在生成时就按 schema 校验工具参数，让多步骤智能体工作流不会因格式错误的输入而失败。
- **大规模分类：** 按意图、优先级和情绪对工单、潜在客户或内容分类，用于路由、审核和评估。

Claude Haiku 5.5 能可靠处理快速、重复性的工作负载，例如摘要、压缩、数据库查询和分类请求。下面的示例展示了如何使用 Invoke API 和 Haiku 5.5 对传入数据进行分类与路由：

```
import boto3
import json

REGION = "us-east-1" # Choose your preferred region
bedrock_runtime = boto3.client(service_name="bedrock-runtime", region_name=REGION)

# Classification schema: enums restrict output to a fixed set of labels
schema = {
    "type": "object",
    "properties": {
        "category": {
            "type": "string",
            "enum": ["billing", "technical", "account", "sales", "other"],
            "description": "Primary ticket category"
        },
        "priority": {
            "type": "string",
            "enum": ["low", "medium", "high", "urgent"],
            "description": "Urgency based on business impact"
        },
        "sentiment": {
            "type": "string",
            "enum": ["positive", "neutral", "negative"],
            "description": "Customer sentiment"
        },
        "escalate": {"type": "boolean", "description": "Whether a human should review immediately"},
        "reason": {"type": "string", "description": "One-sentence justification for the classification"}
    },
    "required": ["category", "priority", "sentiment", "escalate", "reason"],
    "additionalProperties": False
}

ticket = (
    "Our production API calls have been failing with 500 errors since this morning. "
    "We're losing orders every minute. This is the second outage this month!"
)

# Make a request with structured outputs via the InvokeModel API
response = bedrock_runtime.invoke_model(
    modelId="global.anthropic.claude-haiku-5-5",
    body=json.dumps({
        "anthropic_version": "bedrock-2023-05-31",
        "max_tokens": 512,
        "system": "You are a support ticket classifier. Classify the ticket accurately.",
        "messages": [
            {"role": "user", "content": f"Classify this support ticket:\n\n{ticket}"}
        ],
        "output_config": {"format": {"type": "json_schema", "schema": schema}}
    })
)

body = json.loads(response["body"].read())

# Check the stop reason before parsing
if body["stop_reason"] == "end_turn":
    result_text = next(b["text"] for b in body["content"] if b["type"] == "text")
    result = json.loads(result_text)
    print(json.dumps(result, indent=2))
    # Route the ticket based on the guaranteed-valid labels
    if result["escalate"]:
        print(f"Escalating to on-call: {result['category']} / {result['priority']}")
elif body["stop_reason"] == "max_tokens":
    print("Response truncated: increase max_tokens and retry.")
```

## 要求与最佳实践

要在 Amazon Bedrock 上有效使用结构化输出，请遵循以下准则：

- **在所有对象上设置 additionalProperties: false**：这是结构化输出正常工作的必要条件。没有它，你的 schema 将不被接受。
- **使用描述性的字段名和描述**：模型依靠属性名和描述来理解应提取哪些数据。像 `customer_email` 这样清晰的名称优于 `field1` 这类通用名称。
- **对受限取值使用 enum**：当某个字段只有有限的有效取值时，用 `enum` 来约束选项。
- **从基础开始，再逐步增加复杂度**：先使用最少必需字段，然后逐步增加复杂度。基础 schema 编译更快、更易调试，而且能让请求负载保持精简，因为 schema 会计入 Converse API 的负载大小。
- **复用 schema 以享受缓存收益**：把应用设计成在多个请求间复用 schema。24 小时的语法缓存能提升重复查询的性能。
- **检查每个响应的 stop reason**：有两种情况会产生不符合约定的响应：拒绝（模型出于安全原因拒绝）和 token 上限（在完成之前就达到 `max_tokens`）。请在你的代码中处理这两种情况。
- **部署前用真实数据测试**：用具有生产代表性的输入校验你的 schema。真实数据中的边界情况往往能暴露 schema 设计问题。

更多最佳实践和 schema 设计建议，请参阅 Amazon Bedrock 用户指南中的[结构化输出](https://docs.aws.amazon.com/bedrock/latest/userguide/structured-output.html)。

## 支持的 JSON Schema 特性

- 所有基础类型：`object`、`array`、`string`、`integer`、`number`、`boolean`、`null`。
- `enum`（仅支持字符串、数字、布尔值或 null）。
- `const`、`anyOf`、`allOf`（有使用限制）。
- `$ref`、`$def` 和 `definitions`（仅支持内部引用）。
- 字符串格式：`date-time`、`time`、`date`、`duration`、`email`、`hostname`、`uri`、`ipv4`、`ipv6`、`uuid`。
- 数组的 `minItems`（仅支持取值 0 和 1）。

### 不支持的特性

这些关键字会被 API 接受，但在生成期间不会被强制执行。包含它们的请求仍会返回成功响应，模型仍可能返回违反这些约束的值。请在你的应用中校验这些约束，而不要依赖 schema 来强制实施。

- 递归 schema。
- 外部 `$ref` 引用。
- 数值约束（`minimum`、`maximum`、`multipleOf`）。
- 字符串约束（`minLength`、`maxLength`）。
- `additionalProperties` 设置为 false 以外的任何值。
