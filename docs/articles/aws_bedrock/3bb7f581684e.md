# AI agent 的土拨鼠日：在 Amazon Bedrock 上使用 OpenAI 模型的提示缓存模式

*每次你派生出一个 agent，它在执行动作之前都得把自己的一生重新读一遍。下文讲的是如何让它记住这一切，而不必每次再喂给它同样的上下文。*

在电影《土拨鼠日》里，比尔·默里的角色每天都要重过同一个 2 月 2 日。他在收音机里听着同一首歌醒来，住在同一家小旅馆，置身同一个小镇，一遍又一遍——据一些影迷估算，这一过就是 34 年。

前一天做成的事，除非他从头再想一遍，否则带不到这一天。AI agent 就活在某个版本的《土拨鼠日》里。agent 每走一步（调用一个工具、读取结果、决定下一步做什么），都得把到目前为止的完整故事发给模型，才能维持连续：工具定义、指令、之前每一次工具调用，以及每一个结果。模型只根据你提供的输入来预测下一个 token。它在两次请求之间没有任何内部记忆，所以必须把这一切重新读一遍。到一次编码会话的第 20 轮时，模型已经把第 1–19 轮重读了一遍，而每一份这样的 token 都要由你来付钱，一遍又一遍。

提示缓存打破了这个循环。该服务会存下你的输入 prompt（指令、工具和内容），在下一次请求时复用它，代价只有输入价格的一小部分。

本文带你走一遍 agent 的一生：从第一轮，到它拿到新工具、派生 辅助 agent 为止。一路上我会展示提示缓存如何压住成本、让 agent 保持响应迅速与表现一致。

## agent 发给它的 LLM 的是什么

在谈缓存之前，先看看一个典型 agent 第一次调用大语言模型（LLM）时送去了什么：

- **工具列表** – agent 可以调用的每个函数的定义。你发布新版本时它会变。
- **指令** – 开发者 prompt：规则、人设、策略、示例。每个版本也会变。
- **历史** – 本次会话至今发生的一切：任务、模型的工具调用，以及工具结果（每一轮都在增长）。
- **新一轮** – 最新的工具结果或用户消息（每次都可能不同）。

## 提示缓存的内部机制

模型读取一段 prompt 时，先做一次称为 *prefill*（预填充）的写入。在 prefill 期间，它处理每一个输入 token，并构建它的 key 和 value 向量（也叫 key-value，即 KV），这些向量构成模型的工作状态。这一步发生在模型写出第一个 token 之前。

提示缓存把这个状态保存下来，其中包含 system prompt、工具、内容、历史等等。当后续请求以相同的输入 token（即相同的文本）开头时，提示缓存服务会加载保存的状态，而不是重新计算。接着它只处理下一次发给模型的新增负载。提示缓存可以是隐式的，由 Amazon Bedrock 决定可复用前缀在哪里结束；也可以是显式的，由你的代码用 `prompt_cache_breakpoint` 标出那个边界点。两种方式可以一起用，我们也推荐这么做。

**隐式还是显式，为什么两种都需要？**

对 agentic 工作负载来说，隐式缓存让 Bedrock 随对话增长自行决定缓存什么。用显式缓存，你可以把共享内容（比如工具和指令）标记出来，以便跨会话复用，也便于在启动 辅助 agent 时复用。你不一定两种都需要，但把它们结合起来，能得到一个可复用的起点，同时由 Bedrock 自动管理不断增长的对话。

新会话同样可以复用那个共享起点，而每个对话则建立在各自缓存的历史之上。本文从第一轮讲起，然后说明如何把缓存内容带到后续轮次、新工具以及各个 子 agent 之间。

## 你好，缓存的世界

第一个收获是缓存 prompt 中静态的那部分：跨请求保持不变的工具和指令。这些示例使用你现有的 Amazon Bedrock 客户端、`TOOLS` 和 `task`。把简写的 `INSTRUCTIONS` 字符串换成你真实的策略和示例。可复用前缀必须达到 1,024 tokens 才算合格。

缓存静态内容时使用显式模式：自行指定保存的前缀在哪里结束。

```
KEY = "support-agent:v7:gpt-6-astra"
INSTRUCTIONS = "Your full support policies and examples..."

# Rendered context: [provider context][TOOLS][INSTRUCTIONS] | [task]
# Cache starts at the beginning; the marker below chooses its end.
resp = client.responses.create(
    model="us.openai.gpt-6-astra",
    store=False,  # Response storage; prompt caching still works.
    include=["reasoning.encrypted_content"],
    prompt_cache_key=KEY,
    prompt_cache_options={"mode": "explicit", "ttl": "30m"},
    tools=TOOLS,  # Rendered before instructions; keep order stable.
    input=[
        {
            "role": "developer",
            "content": [{
                "type": "input_text",
                "text": INSTRUCTIONS,
                # Save through this whole block, including TOOLS.
                "prompt_cache_breakpoint": {"mode": "explicit"},
            }],
        },
        # User message is processed but not cached.
        {"role": "user", "content": task},
    ],
)
```

`prompt_cache_key` 告诉服务哪些请求要共享同一份缓存。我们在讲到新会话读取缓存时会再回来讨论它怎么用。在我们一次使用显式缓存的测试中，约 4,000 tokens 的「工具加指令」前缀在第一次请求时写入了 4,120 tokens，后续请求则读取了这 4,120 tokens。`task`（或用户请求）位于缓存边界之后，因此不会触发一次缓存写入。

要注意，提示缓存只有在你传入完全相同的文本时才生效。确保 agent 的指令和工具列表每次都以相同的方式序列化。Model Context Protocol (MCP) 服务器以及其他工具交付方式需要建立索引，以保证一致性。把任何会变化的东西（比如日期、用户名或请求 ID）放在缓存指令之后。

当内容增多并发生变化（不同的工具和内容）时，改用隐式模式，让服务跟随对话演进。这里，第一个请求没有显式标记。它最新的可参与缓存的消息是用户的任务，因此自动断点落在该任务之后，把工具、指令和任务一并覆盖。尽管隐式是默认模式，下面的例子仍显式写出模式以便说明。设置 `store=False` 会让对话历史留在你的应用里，它并不会关闭缓存。

```
def ask_with_implicit_cache(history):
    return client.responses.create(
        model="us.openai.gpt-6-astra",
        store=False,
        include=["reasoning.encrypted_content"],
        prompt_cache_key=KEY,
        prompt_cache_options={"mode": "implicit", "ttl": "30m"},
        tools=TOOLS,
        input=history,  # Everything gets cached
    )

history = [
    {"role": "developer", "content": INSTRUCTIONS},
    {"role": "user", "content": task},
]
# Automatic endpoint: the end of the user message.
resp = ask_with_implicit_cache(history)
```

这在下一轮继续同一个任务时很有用。换一个任务就不再匹配到旧任务为止的那段前缀，隐式写入也不一定会为「只有工具和指令」单独建一条记录。当你需要那段更短的共享前缀跨任务复用时，就在那里加一个显式标记。

当 agent 既需要共享起点又需要不断增长的历史时，两种都用。下面代码示例从带标记的 developer 块开始，并调用 `ask_with_implicit_cache` 函数。请求级别的模式保持隐式，块级别的标记则在指令之后增加一个显式保存点。服务也可以保存到最新的可参与缓存的消息为止。这样一来，对话增长的同时共享前缀始终可用。

```
history = [
    {
        "role": "developer",
        "content": [{
            "type": "input_text",
            "text": INSTRUCTIONS,
            "prompt_cache_breakpoint": {"mode": "explicit"}, 
        }],
    },
    {"role": "user", "content": task},
]
# Still implicit mode, now with an explicit startup save point in the history.
resp = ask_with_implicit_cache(history)
```

## 缓存对话历史与工具结果

模型按名称请求工具并给出参数，你的应用必须负责执行它们。`execute_function` 是你自己写的辅助函数，把这些请求路由到对应的 Python 函数并返回结果。下面的循环用这个辅助函数运行每个被请求的工具。它把模型输出和所有工具结果追加到 `history` 列表，然后再次发送这个列表，直到模型给出最终答案。在隐式模式下，Amazon Bedrock 可以复用未变的前缀，并把新增内容缓存到最后一个工具结果为止。保持前面的消息和最初的 `TOOLS` 不变。

```
import json

# Map tool names to their Python implementations.
TOOL_HANDLERS = {
    "get_owner": get_owner,
    # Register your other initial tools here.
}

def execute_function(name, arguments):
    """Run the requested tool and return its result."""
    handler = TOOL_HANDLERS.get(name)
    if handler is None:
        return {"error": f"Unknown tool: {name}"}
    return handler(**arguments)

while True:
    # Preserve all output items, including encrypted reasoning.
    history.extend(resp.output)
    calls = [x for x in resp.output if x.type == "function_call"]
    if not calls:
        break
    for call in calls:
        result = execute_function(call.name, json.loads(call.arguments))
        history.append({
            "type": "function_call_output",
            "call_id": call.call_id,
            "output": json.dumps(result),
        })
    # The last result in this group supplies the automatic endpoint.
    resp = ask_with_implicit_cache(history)
```

对于后续追问，追加一条新的用户消息，再次调用辅助函数。保持前面的消息不变，这样它们的缓存端点才仍然可用。

**滚动断点：每一轮都读取它之前的所有内容**

![滚动断点：每一轮读取所有更早的轮次，只写入自己那一条工具结果。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/23/ML-22246-3-1.png)

图 3：滚动断点，每一轮读取它之前的所有内容，只写入自己的工具结果

若要单独跑一遍纯显式的流程，请照着「你好，缓存的世界」中组合式的例子重建那条两条消息的 `history`。这个循环把工具结果包进 `input_text` 块，并标记每一批中的最后一个结果。更早的标记仍保留在 `history` 里。关于长对话，请参见[当前的查找规则](https://developers.openai.com/api/docs/guides/prompt-caching)。

```
import json

while True:
    resp = client.responses.create(
        model="us.openai.gpt-6-astra", store=False,
        include=["reasoning.encrypted_content"],
        tools=TOOLS, prompt_cache_key=KEY, input=history,
        prompt_cache_options={"mode": "explicit", "ttl": "30m"},
    )
    d = resp.usage.input_tokens_details
    print("read", d.cached_tokens, "write", d.cache_write_tokens)
    history.extend(resp.output)  # Includes encrypted reasoning.
    calls = [x for x in resp.output if x.type == "function_call"]
    if not calls:
        break
    batch = []
    for call in calls:
        result = execute_function(call.name, json.loads(call.arguments))
        batch.append({
            "type": "function_call_output", "call_id": call.call_id,
            "output": [{"type": "input_text", "text": json.dumps(result)}],
        })
    # Add the newest boundary; retain every earlier marker.
    batch[-1]["output"][-1]["prompt_cache_breakpoint"] = {"mode": "explicit"}
    history.extend(batch)
```

在这个六轮工作负载中，GPT-6 Astra 的隐式结果并列最佳：相比不做缓存，输入成本降低约 62%。同一模型上，显式滚动断点节省了约 61%。两种方式都随着对话增长复用了更多历史。这些是特定工作负载下的结果，你需要测量自己 agent 的节省幅度。

![柱状图：在 GPT-6 Astra 上比较各缓存配置相对不缓存时的输入成本。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/23/ML-22246-4-1.png)

图 4：GPT-6 Astra 上各种缓存配置相对不缓存时的输入成本

**注意：**

- **纯显式模式下只有一个静态断点** – 工具和指令被缓存了，但不断增长的历史每一轮都要重新处理（0.61）。这个限制不适用于组合式的例子，后者也会保存到可参与缓存的对话结尾。
- **移动单个断点** 在纯显式模式下会让缓存无法复用，并导致反复写入。要把上一轮的断点也保留下来。
- **只有隐式写入且任务在变化** – 新任务可能共享工具和指令，却不共享先前保存的端点。如果不同的任务需要复用那段更短的前缀，就在共享指令之后加一个显式标记。

## 当工具发生变化

有时 agent 的工具列表会变，或者会新增工具。保持最初的列表稳定：增删或重排定义都可能让缓存的前缀失效。选择与工具可用方式相匹配的做法。

**当已知工具在 agent 流程的不同步骤被调用时：** 发送相同的、已排序的 `TOOLS`，并用 `allowed_tools` 限制模型可以调用什么。在 `allowed_tools` 中，`"mode": "auto"` 让模型自行决定是否调用某个被允许的工具，`"mode": "required"` 则要求至少调用一次被允许的工具。把它作为 `tool_choice` 传入。这个限制不会改变缓存下来的工具目录：

```
tool_choice={"type": "allowed_tools", "mode": "auto",
             "tools": [{"type": "function", "name": "get_owner"}]}
```

**会话期间的新增工具。** 对 GPT-6 Astra、GPT-6.1 Sol 和 GPT-5.6 Luna，Amazon Bedrock Runtime 和 Amazon Bedrock Mantle 两种端点都接受一种名为 `additional_tools` 的输入项类型。各 AWS 区域的模型可用情况，请参见 [Amazon Bedrock 中按 AWS 区域划分的受支持模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。在辅助函数 `execute_function` 中注册新工具 `get_due_date`，然后把它的 schema 追加到 agent 循环产出的完整 `history` 后面。保持最初的 `TOOLS` 不变：

```
TOOL_HANDLERS["get_due_date"] = get_due_date
NEW_TOOL = {
    "type": "function", "name": "get_due_date",
    "description": "Return the due date for a support case.",
    "strict": True,
    "parameters": {
        "type": "object",
        "properties": {"case_id": {"type": "string"}},
        "required": ["case_id"], "additionalProperties": False,
    },
}
history.append({
    "type": "additional_tools", "role": "developer",
    "tools": [NEW_TOOL],
})
history.append({
    "role": "user", "content": "Find the due date for case C-123.",
})
# Implicit mode saves through this new user message, including NEW_TOOL.
resp = ask_with_implicit_cache(history)
d = resp.usage.input_tokens_details
print("old prefix read", d.cached_tokens, "new write", d.cache_write_tokens)

# Example output:
# old prefix read 2048 new write 256
```

用新的响应继续工具执行循环。循环把模型输出加入 `history`，运行被请求的工具，并把结果追加进去。在后续请求中保留 `additional_tools` 项，让新工具持续可用。在隐式模式下，Amazon Bedrock 可以缓存到新的用户消息为止，包括它前面的工具定义。在纯显式模式下，保留更早的断点，并在该用户消息的一个 `input_text` 块上再加一个。`additional_tools` 项本身不能承载断点。

**不同角色，不同目录。** 当不同的 agent 角色需要不同的工具时，在每个会话开始时选定一个稳定的工具配置，比如客服或账单。每个配置拥有自己独立的缓存前缀。标记共享指令，让之后使用该配置的任务可以复用它们，然后随着对话增长选用任一种模式。

## 子 agent 与旁路调用

任务委派不该让每个 辅助 agent 都重读同样的背景。共享那段前缀，再把每个 辅助 agent 的任务加在末尾。要意识到，在 AI agent 中使用缓存时，工具和 system prompt 有可能泄漏或被利用。建立负责任的 AI 实践，把你的提示缓存实现纳入那份治理之中。

**先预热，再分派。** 先发一个普通请求，等它跑完再启动 辅助 agent。即使模式是隐式的，也要在每个请求中显式标记共享上下文：

```
shared = {"role": "developer", "content": [{
    "type": "input_text", "text": INSTRUCTIONS,
    "prompt_cache_breakpoint": {"mode": "explicit"},
}]}
warm = client.responses.create(
    model="us.openai.gpt-6-astra", store=False,
    tools=TOOLS, prompt_cache_key=KEY,
    prompt_cache_options={"mode": "implicit", "ttl": "30m"},
    max_output_tokens=16,
    input=[shared, {"role": "user", "content": "Reply READY."}],
)
d = warm.usage.input_tokens_details
if not (d.cache_write_tokens or d.cached_tokens):
    raise RuntimeError("Shared prefix was not cached.")
from concurrent.futures import ThreadPoolExecutor

# helper_tasks contains the task text for each helper.
helper_inputs = [
    [shared, {"role": "user", "content": task}]
    for task in helper_tasks
]
with ThreadPoolExecutor(max_workers=4) as pool:
    helpers = list(pool.map(ask_with_implicit_cache, helper_inputs))
```

辅助 agent 使用与预热时相同的 `TOOLS`、模型和 `KEY`。即使预热请求在输出上限处结束，也足以把缓存填充起来。这项用量检查在 辅助 agent 启动之前确认缓存确有活动。

**让旁路调用拥有相同的开头。** agent 循环通过追加每个 `resp.output` 及其对应的工具结果（包括加密的推理内容）来构建 `history`。父 agent 结束后，复制这份完整列表给摘要器或评判者。同一个辅助函数保持工具、模型和 key 不变：

```
from copy import deepcopy

# history is the completed history built by the agent loop above.
# Copy it so the helper can add instructions without changing the parent.
helper_history = deepcopy(history)
helper_history.append({
    "role": "developer",
    "content": "Summarize this conversation in one sentence. Do not call tools.",
})
summary = ask_with_implicit_cache(helper_history)
d = summary.usage.input_tokens_details
print("history read", d.cached_tokens, "write", d.cache_write_tokens)
print(summary.output_text)

# Example output (assumed values and conversation):
# history read 4096 write 32
# Case C-123 is due on October 31, 2026.
```

辅助 agent 可以复用 `history` 中已缓存的部分，但追加的 developer 消息不会自动把缓存扩展到包含摘要指令。如果后续请求会复用同样的历史和指令，请把该指令放进带 `prompt_cache_breakpoint` 的 `input_text` 块中。只做一次的摘要则不需要额外的标记。

## 暂停、重启与缓存键

**暂停。** 缓存前缀的最短存活时间（TTL）是 30 分钟，每次成功复用都会刷新它，实际还可能保留更久。如果会话很快就会恢复，一次普通的预热就能在过期前刷新前缀。把这次请求的成本和让缓存自然过期对比一下。TTL 规则请参见 Amazon Bedrock 文档。

**新会话。** 对于打算共享前缀的请求，保持 `prompt_cache_key` 稳定。会话专属的键会把各会话隔离开，即使它们的 prompt 相同。在下面的例子中，改用共享键之后各会话便能复用前缀。

**新会话只有共享同一个键时才能复用缓存**

![最初的实验比较了按会话区分的缓存键与一个稳定的共享键。](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/23/ML-22246-8-1.png)

图 8：会话专属的键把缓存条目分隔开，而共享键让匹配的会话复用它们

复用已有的缓存内容需要相同的模型、AWS 账户和区域，并且要有可用的匹配前缀。下面的例子把显式的起始标记与隐式模式结合起来。每个会话都以相同的指令开始，带着各自的任务。两者都使用同一个计算出来的键：

```
import hashlib

def cache_key(app, model, prompt_version, instructions):
    digest = hashlib.sha256(instructions.encode()).hexdigest()[:12]
    return f"{app}:{prompt_version}:{model}:{digest}"

KEY = cache_key("support-agent", "us.openai.gpt-6-astra", "v7", INSTRUCTIONS)
prefix = {"role": "developer", "content": [{
    "type": "input_text", "text": INSTRUCTIONS,
    "prompt_cache_breakpoint": {"mode": "explicit"},
}]}
for label, question in [
    ("session A", "Explain the refund policy without calling tools."),
    ("session B", "Explain the escalation policy without calling tools."),
]:
    # A fresh conversation for each session; the startup prefix matches.
    session_history = [prefix, {"role": "user", "content": question}]
    result = ask_with_implicit_cache(session_history)
    d = result.usage.input_tokens_details
    print(label, "read", d.cached_tokens, "write", d.cache_write_tokens)
```

冷启动时，会话 1 写入共享前缀。哪怕任务不同，会话 2 也能读到它。每个任务本身也可以被隐式缓存。请检查用量计数器：键和标记的匹配只是让复用成为可能，缓存条目本身还得存在。

## 提示缓存能带来什么

**成本。** 对一个由 GPT-6 Astra 驱动、启动前缀为 8,000 tokens、后续六轮每轮增加 2,000 tokens 的 agent 来说，一次性静态缓存把成本降到了 $0.50；滚动断点则把建模后的输入成本降低了 64%：每个会话从 $0.87 降到 $0.32。

## 怎么判断缓存生效了

先看响应的用量。`cached_tokens` 报告从缓存读取的输入量，`cache_write_tokens` 报告写入缓存的输入量。随着对话增长，检查后续轮次是否复用了更早的历史，以及新的写入是否反映了新增的内容。

要在 Amazon Bedrock Runtime 端点上做生产监控，请在 Amazon CloudWatch 中使用 `CacheReadInputTokenCount` 和 `CacheWriteInputTokenCount` 这两个指标。需要单条请求记录时开启模型调用日志，再用 Amazon CloudWatch Logs Insights 查询。对于 Amazon Bedrock Mantle 端点，请把响应的用量字段记录到应用日志里——它对应的 Amazon CloudWatch 命名空间目前没有单独的缓存计数器。

要核对成本，在 **AWS Cost Explorer** 中筛选 Amazon Bedrock，并按 **Usage type** 分组。缓存读取、缓存写入和未缓存输入会按模型各自显示为独立条目。计算它们占输入成本的比例时，请排除输出 token 的条目。

## 一份简短清单

- **保持可复用前缀稳定。** 先放共享的工具和指令，再追加对话历史和新轮次。改动时间戳、消息或工具定义之后，超出该改动范围的部分就无法复用。更短的前缀如果有自己的保存端点，依然可以复用。
- **在你想要复用的内容周围划定边界。** 不断增长的历史用隐式缓存，共享前缀用显式标记，或者两者并用。纯显式模式可以避免写入用完即弃的后缀。扩展纯显式对话时，保留更早的标记，让后续请求能找到已保存的前缀。
- **保持最初的工具目录不变。** 用 `allowed_tools` 限制哪些工具可以被调用。已知的定义用 `additional_tools` 追加，或通过带命名空间的客户端 `tool_search` 发现它们。当不同的 agent 角色需要不同目录时，选定一个稳定的工具配置。
- **检查前缀的大小与存活时间。** 可缓存的前缀至少要包含 1,024 tokens。缓存前缀在最近一次写入或成功复用之后，至少 30 分钟内仍可复用。
- **在启动 辅助 agent 前预热共享内容。** 在预热请求和 辅助 agent 请求中都标记共享前缀，使用隐式模式时也不例外。先等预热请求结束，再发起并行调用。
- **在每个共享组内保持缓存键稳定。** 打算复用前缀的请求必须使用同一个键。不同的键可以把不同客户或用户之间的缓存计费分开。
- **在整个流程上度量节省。** 缓存写入的价格是正常输入费率的 1.25 倍。读取价格取决于模型。开发与监控阶段用响应用量，生产阶段用账单数据，同时跟踪写入成本与读取节省。

本文讲清了如何缓存共享的工具和指令、如何让缓存跨越 agent 的各个轮次增长，以及在新增工具、启动 辅助 agent 或开启新会话时如何保住复用能力。保持共享前缀稳定，随着流程推进不断追加新信息。不断增长的对话用隐式缓存，共享内容用显式断点。两者都需要时把它们结合起来；变化的后缀不太可能被复用时，就选纯显式模式。比较缓存读取、写入、总输入成本和延迟，找出对你的 agent 最有效的方案。要落地这些模式，请参考 [Amazon Bedrock 中针对 OpenAI 模型的提示缓存文档](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html#prompt-caching-openai)，并查看[按 AWS 区域和端点划分的模型可用情况](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)。先从一个流程做起，随着对话增长测量节省。
