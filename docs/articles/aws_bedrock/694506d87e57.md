# Miro 如何借助 Amazon Bedrock 提升软件 bug 路由准确率，把解决时间从数天缩短到数小时

*本文由来自 *[*Miro*](https://miro.com/de/index/) 的 Philipp Pavlov、Dmytro Romantsov、Evgeny Mironenko 和 Gowri Suryanarayana 共同撰写。

[Miro](https://miro.com/de/index/) 是一个由 AI 驱动的创新工作空间，全球用户超过 9500 万，帮助团队把非结构化的想法转化为有序的工作流。为支撑这一规模并持续改进其系统，Miro 的开发者体验团队决定为 Miro 自身打造一个创新工作空间，用现代技术提升开发者生产力。团队面临的关键挑战之一，是把软件 bug 高效地路由给负责的团队。快速而准确的路由能消除不必要的上下文切换、减少开发者的挫败感、改善解决时间（time-to-resolution），最终带来更好的产品和更满意的客户。在 Miro，相当比例的 bug 未能达到内部解决 SLA，主要原因就是路由错误以及团队之间反复转派。这一问题估计每年造成累计 42 年的生产力损失，源自延迟与重复的排查投入。为解决这一问题，Miro 与 AWS Prototyping and Cloud Engineering（PACE）团队合作开发了 BugManager，一个用于自动化 bug 分诊的 AI 驱动解决方案。

在本文中，我们深入介绍用于改进 Miro bug 路由的架构与技术：借助 [Amazon Bedrock](https://aws.amazon.com/bedrock/)，我们把团队重分配次数降低到原来的六分之一，把解决时间缩短到原来的五分之一。

## 挑战：把 bug 报告准确路由到约 100 个软件团队

在现代软件环境中实现 bug 分诊自动化并不简单。bug 报告往往杂乱、缺乏上下文，并包含形形色色的数据，包括文本、堆栈跟踪、截图甚至视频。在拥有众多团队的软件公司里，复杂度会成倍增加，形成一个标签数量众多的多类别分类问题。Miro 的工程组织由近 100 个团队组成，每个团队负责特定的产品方面。高准确率的 bug 分类需要为报告补充来自各类来源的相关产品信息，包括 GitHub pull request、Confluence 文档、README 文件以及此前已解决的工单。此外，组织结构是动态的——团队会合并、新团队会成立、产品会演进，团队职责也随之不断变化。软件功能同样如此：新增、更新或弃用。传统的基于自然语言处理（NLP）的文本分类器，例如微调过的 BERT 模型或微调过的大语言模型（LLM）分类器，在这种动态环境中受到严重限制。它们需要在组织发生变化时重新训练，并且依赖在新结构下可能并不存在的标注数据。Miro 原有的基于微调 GPT 模型的解决方案，性能很快就出现了退化。意识到这些挑战后，Miro 选择了一种由 LLM 驱动的方法，把用于团队分类的优化 prompt 与用于上下文检索的检索增强生成（RAG）结合起来，构建出一个更易适配、零训练、准确率更高的 bug 分诊方案：BugManager。

## BugManager：由 Amazon Bedrock 驱动的基于 RAG 的 bug 分诊

BugManager 采用由 LLM 驱动的方法进行 bug 分类。当收到新的 bug 报告时，BugManager 的分类系统便开始工作。BugManager 首先使用 [Amazon Nova Pro](https://aws.amazon.com/nova/) 的[多模态图像与视频理解能力](https://docs.aws.amazon.com/nova/latest/userguide/modalities.html)解析截图或屏幕录制等非文本数据。随后，系统使用 RAG 从多个知识库（借助 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/)）为解析后的报告补充重要上下文。这些知识库中包含例如此前已解决的 Jira 工单、GitHub pull request、Confluence 文档和 GitHub README。系统使用 Amazon Bedrock 上 [Anthropic 的 Claude Sonnet 4](https://aws.amazon.com/bedrock/anthropic/)，把增强后的 bug 描述与各团队及其职责的详细文字信息合并成一个统一的、优化过的分类 prompt，由它完成到正确团队的路由。作为可选功能，系统还可以生成详细的根因分析，利用已收集的信息并结合相关源码仓库的检索，提供更深入的问题洞察与解决假设。

为便于无缝落地和使用，BugManager 通过一个简单的基于 Slack 的工作流开放给 Miro 工程社区。下面的截图展示了用户与 BugManager 交互的一个示例。基于 bug 的初始描述，BugManager 最多提出五个合适的团队（按优先级排序），并附上理由。默认情况下，bug 会被路由到最可能的团队，但用户可以手动改写这一选择。BugManager 还可以选择性地为工程师提供所报 bug 的根因分析，依据是从整个 Miro 代码库中检索到的信息。

## 架构深入剖析

BugManager 主要使用 Amazon Bedrock，这是一个完全托管的服务，可通过单一 API 提供来自领先 AI 公司的高性能基础模型（FM）选择。借助 Amazon Bedrock Knowledge Bases、Anthropic 的 Claude Sonnet 4 与 Amazon Bedrock 上的 Amazon Nova Pro，我们构建了一套端到端工作流，把发布在 Slack 中的 bug 描述转换成一个在 Jira 中创建、并分配给某个团队解决的 issue。

BugManager 作为 Python 微服务运行在 [Amazon Elastic Kubernetes Service](https://aws.amazon.com/eks/)（Amazon EKS）集群中。下图展示了该架构与应用流程。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/03/11/Picture-2-1024x579.png)

BugManager 工作流包含以下步骤：

- 提交用户反馈报告。
- 解析媒体附件。
- 为用户反馈补充上下文。
- 把用户反馈路由到正确的团队。
- 生成根因分析。
- 把结果返回给用户审阅。

在接下来的章节中，我们将更详细地探讨这些步骤。

### 第 1 步：提交用户反馈报告

用户在专门的 Slack 频道中发布反馈报告（例如某个 bug 的报告）。报告可能包含文本和媒体附件。媒体附件可能包括描述 bug 复现过程的视频（通常是屏幕录制）、描绘该 bug 的截图，或用于功能增强的产品页面截图。bug 报告以 JSON 对象的形式传递，其中包含内容（文本）以及存放在 [Amazon Simple Storage Service](https://aws.amazon.com/s3)（Amazon S3）中的附件链接。

### 第 2 步：解析媒体附件

如果消息中包含媒体附件，就必须把这些附件解析为文本，以便后续步骤以单一模态（文本）进行 bug 分析和分类。我们使用 Amazon Nova Pro 的图像理解能力，把媒体附件的描述解析为文本。这种做法的一个挑战在于，LLM 默认并不具备上下文感知能力；它并不了解图像的类型（通常是 Miro 产品的截图），因而无法以特定且有价值的方式解读图像。因此，为提供所需的上下文，我们首先基于 bug 文本运行 RAG，用可能出现在该媒体素材中的特定功能信息来补充 prompt。我们的 RAG 方案使用 Amazon Bedrock Knowledge Bases 自动从 Miro 内部产品文档中获取数据。这显著提升了从附件中提取信息的具体程度。附件解析完成后，其文本描述会追加到原始 bug 文本之后，并传递给应用工作流中的下一步。

### 第 3 步：为用户反馈补充上下文

我们使用 Amazon Bedrock Knowledge Bases 自动从各类来源获取数据，为基础模型提供来自 Miro 大量内部和外部数据源的上下文信息。Amazon Bedrock Knowledge Bases 是一项完全托管的能力，内置会话上下文管理和来源归属，可帮助你实现整个 RAG 工作流——从摄取到检索再到 prompt 增强——而无需为数据源构建自定义集成或管理数据流。更具体地说，我们使用 Amazon S3 和 Confluence 连接器作为数据源。我们把 [Amazon OpenSearch Serverless](https://aws.amazon.com/opensearch-service/features/serverless/)——[Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 的按需无服务器选项——配置为向量存储。我们在知识库中索引了以下数据源：Confluence 文档、Miro 帮助中心文章、已解决的 Jira 工单、GitHub README 以及 Backstage 文档（技术文档与软件目录）。Amazon Bedrock Knowledge Bases 支持增量重新同步，因此可以低成本地让知识库与文档变更保持同步（只有被修改的文档才会被重新嵌入和重新索引）。

### 第 4 步：把用户反馈路由到正确的团队

借助 Amazon Bedrock 和 Anthropic 的 Claude Sonnet 4，我们把 bug 路由到负责的团队。给 LLM 用于正确分类的上下文包括：增强后的 bug 描述、增强后的附件描述（如果存在附件），以及在 Backstage（由 GitHub 支撑）中集中管理和版本化的团队描述。团队描述是活文档，随时可以更新。Miro 的产品与工程组织是动态构造。产品功能会被新增或弃用，团队职责也会变化。由于 BugManager 采用基于 prompt 的方法，这类更新可以相对轻松地纳入——只要更新相应的团队描述（一个用英文写的 markdown 文件）即可，变更会立即生效。下面是我们用于 bug 到团队分类的 prompt 的简化版本。请注意输出中使用了 `<xml>` 标签，这让输出可以被稳健地解析。

```
ROUTING_PROMPT = """
You are a bug report routing assistant for Miro, a software company providing a collaboration and canvas software. You are responsible for analyzing incoming bug reports and determining which software team should handle them. Your goal is to accurately route each bug report to the most appropriate Miro software team based on their areas of responsibility. 
When analyzing  a bug report, follow these steps:
1. Carefully read the provided team descriptions to understand each team's domain expertise and responsibilities
2. Analyze the bug report for:
- Affected systems or components
- Technical keywords and terminology
- Error messages or stack traces
- User impact and behavior
- Related capabilities, features or functionality
3. Compare the bug details against each team's responsibilities
4. Select the most appropriate Miro software team based on:
- Direct ownership of affected components
- Required technical expertise
- Historical handling of similar issues
- Cross-cutting concerns and dependencies
Return the five most appropriate software teams, provide a confidence of HIGH, MEDIUM, LOW and a rationale per each choice. Enclose your answers in <team>, <confidence> and <rationale> xml tags, respectively.
Details about the bug report and the responsibilities of each Miro software team are provided below:
Bug details and context:
<bug_report>
{bug_report}
</bug_report>
<parsed_bug_attachments>
{parsed_attachments}
</parsed_bug_attachments>
<context>
{parsed_attachments}
</context>
Miro software teams descriptions:
<teams_info>
{teams_info}
</teams_info>
Miro team descrip
Think step-by-step! 
""".strip()
```

BugManager 在 bug 到团队路由上实现了超过 75% 的 top-1 准确率（相比基于微调 NLP 模型的既有内部方案提升 70%）。平均分类延迟为 53 秒，在生产部署中被证明是可用的。BugManager 最多返回五个可能的团队选项（按置信度排序，确切数量可配置）。Top-3 准确率为 95%，配合人在回路（human-in-the-loop）的方式，已被证明能进一步提升分诊准确率。这些结果得益于 [Anthropic Claude 的扩展思考（extended thinking）](https://www.anthropic.com/news/visible-extended-thinking)，它额外带来了 7–9% 的准确率提升。

对于每一次分类，该方案还会给出为何做出某个路由决策的完整理由。相比只返回单一团队、不做任何解释的微调 NLP 方案，这显著提升了用户接受度和信任。

### 第 5 步：生成根因分析

BugManager 可以选择性地生成 bug 的根因分析。同样，我们使用 Amazon Bedrock Knowledge Bases 提供运行此类分析所需的上下文，这一次以整个 Miro GitHub 代码库作为参考。在根因分析过程中，我们把 bug 描述、此前检索到的上下文，以及被选中解决该 bug 的软件团队一并提供给 LLM（启用了扩展思考的 Anthropic Claude Sonnet 4）。随后，LLM 使用 Amazon Bedrock Knowledge Bases 检索相应的代码段，并针对所观察到的 bug 生成一组根因假设。这样做就免去了软件工程师为确定行动方向所必需的研究工作。

### 第 6 步：把结果返回给用户审阅

分类结果和根因分析结果（可选）会作为对所发布初始消息的回复发送到 Slack。用户可以查看路由结果，并在需要时修改默认选择。之后，系统会创建 Jira 工单并分配给选定的团队，其中包含原始 bug 描述、从知识库检索到的支撑文档，以及根因分析的结果。

## 结论

BugManager 具备多项关键特性，使它成为一个由 Amazon Bedrock 驱动、能力出众的 bug 分诊解决方案，并已在 Miro 工程组织中获得显著成功。这些关键特性包括：

- 首次即命中的高准确率 bug 到团队路由
- 通过多类别预测进一步提升性能，支持人在回路决策
- 透明的路由决策，带来用户接受度
- bug 根因分析，加速问题解决
- 借助持续刷新的组织知识进行增强
- 对团队职责变化的健壮性与灵活性

BugManager 已在生产环境中成功路由了数千个 bug 和支持请求，为 Miro 的开发工作流带来了出色的成果。该系统使客户支持请求的团队重分配次数降低到原来的六分之一，并把中位解决时间缩短到原来的五分之一，将过去需要数天的过程转变为数小时的流程。预计 BugManager 每年可节省累计数年的等待与排查时间，最终带来显著更好的 Miro 产品体验。
