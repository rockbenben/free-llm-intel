# 通过文件系统配置持久化会话状态并执行 shell 命令

AI agent 早已远远超越了聊天。编写代码、持久化文件系统状态、执行 shell 命令，以及在文件系统中管理状态，只是它们能做的事情中的一些例子。随着 agentic 编码助手和开发工作流日趋成熟，文件系统已成为 agent 的主要工作记忆，把它们的能力延伸到上下文窗口之外。这一转变带来了两个挑战，每个构建生产级 agent 的团队都会遇到：

- 文件系统是临时的。当 agent 的会话停止时，它创建的一切——例如已安装的依赖、生成的代码或本地 git 历史——都会消失。
- 当你的工作流需要 `npm test` 或 `git push` 这样的确定性操作时，你不得不把它交给大型语言模型（LLM）处理，或者在运行时之外构建自定义工具。这两个选项都不理想。

[Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) 现在用两项能力解决了这两个挑战：用于持久化 agent 文件系统状态的托管会话存储（public preview），以及 execute command（`InvokeAgentRuntimeCommand`），可直接在与每个活动 agent 会话关联的 microVM 内运行 shell 命令。它们各自单独就有用。结合起来，它们解锁了此前不可能实现的工作流。

本文将介绍如何使用托管会话存储持久化 agent 的文件系统状态，以及如何直接在 agent 的环境中执行 shell 命令。

## 走进 AgentCore Runtime 会话

AgentCore Runtime 在专用的 [microVM](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html) 中运行每个会话，其资源相互隔离，包括独立的内核、内存和文件系统。这种架构提供了强大的安全边界，但也意味着每个会话都启动在一个干净的文件系统上。当 microVM 终止时——无论是通过显式 [stop](https://docs.aws.amazon.com/bedrock-agentcore/latest/APIReference/API_StopRuntimeSession.html) 还是 [idle timeout](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_LifecycleConfiguration.html)——agent 创建的一切都会消失。

想想这在实践中意味着什么。你的编码 agent 花了二十分钟搭建一个项目：建立目录结构、安装依赖、生成样板代码、配置构建工具。你去吃午饭，回来后调用同一个会话，agent 却从头开始。每个软件包都要重装，每个文件都要重新生成。在 agent 能再次做有用的事之前，二十分钟的算力已经烧掉了。这一限制可以通过编写检查点逻辑来解决：在停止会话之前把文件上传到 Amazon Simple Storage Service（Amazon S3），并在恢复时下载回来；或者让会话保持活动以避免丢失状态。这种变通做法可行，但它并没有解决文件系统层面的限制，而且会给 agent 代码增加复杂度。

确定性操作也存在同样的摩擦。当 agent 完成一项修复、而你需要运行测试时，把命令作为工具调用交给 LLM 处理，会给一个可预测的操作带来 token 成本、延迟和不确定性。另一种选择是在运行时之外构建独立的编排逻辑，这需要你连接到 agent 的文件系统，从而增加复杂度。

## 托管会话存储（public preview）：可存活的状态

第一个挑战——临时文件系统——由托管会话存储解决。它为你的 agent 提供一个在停止/恢复循环中存活的持久目录。持久化内建于运行时，并在创建 agent 时配置——写入该目录的所有内容即使计算环境被替换也会保留。

### 配置持久化存储

要配置持久化存储，请执行以下操作：

在你的 agent 运行时的 `filesystemConfiguration` 中添加 `sessionStorage`：

```
aws bedrock-agentcore create-agent-runtime \
  --agent-runtime-name "coding-agent" \
  --role-arn "arn:aws:iam::111122223333:role/AgentExecutionRole" \
  --agent-runtime-artifact '{"containerConfiguration": {
    "containerUri": "123456789012.dkr.ecr.us-west-2.amazonaws.com/my-agent:latest"
  }}' \
  --filesystem-configurations '[{
    "sessionStorage": {
      "mountPath": "/mnt/workspace"
    }
  }]'
```

或使用 AWS SDK for Python（Boto3）：

```
import boto3

# Use the control plane client for creating and managing runtimes
control_client = boto3.client('bedrock-agentcore-control', region_name='us-west-2')

response = control_client.create_agent_runtime(
    agentRuntimeName='coding-agent',
    agentRuntimeArtifact={
        'containerConfiguration': {
            'containerUri': '123456789012.dkr.ecr.us-west-2.amazonaws.com/my-agent:latest'
        }
    },
    roleArn='arn:aws:iam::111122223333:role/AgentExecutionRole',
    protocolConfiguration={
        'serverProtocol': 'HTTP'
    },
    networkConfiguration={
        'networkMode': 'PUBLIC'
    },
    filesystemConfigurations=[{
        'sessionStorage': {
            'mountPath': '/mnt/workspace'
        }
    }]
)
```

注意：AgentCore 使用两个 Boto3 服务客户端。控制平面客户端（`bedrock-agentcore-control`）处理运行时生命周期操作，例如 `CreateAgentRuntime`、`GetAgentRuntime` 和 `DeleteAgentRuntime`。数据平面客户端（`bedrock-agentcore`）处理会话操作，例如 `InvokeAgentRuntime` 和 `InvokeAgentRuntimeCommand`。挂载路径必须以 `/mnt` 开头，后接一个文件夹名称（例如 `/mnt/workspace` 或 `/mnt/data`）。配置完成后，agent 写入该路径的任何文件都会自动持久化到托管存储。

### 停止与恢复的体验

你调用 agent，让它搭建一个项目：

```
aws bedrock-agentcore invoke-agent-runtime \
  --agent-runtime-arn "arn:...:agent-runtime/coding-agent" \
  --runtime-session-id "session-001" \
  --payload '{"prompt": "Set up the project and install dependencies in /mnt/workspace"}'
```

agent 在该会话专用的 microVM 中下载代码、安装软件包并生成配置。随后你停止会话，或空闲超时触发，microVM 随之终止。

你回来后，用相同的 `runtime-session-id` 再次调用：

```
aws bedrock-agentcore invoke-agent-runtime \
  --agent-runtime-arn "arn:...:agent-runtime/coding-agent" \
  --runtime-session-id "session-001" \
  --payload '{"prompt": "Run the tests and fix any failures"}'
```

新的计算环境（microVM）启动并挂载同一份存储。agent 看到 `/mnt/workspace` 与它离开时完全一样，包括源文件、`node_modules`、构建产物和 `.git` 历史。agent 可以从思考中断处继续，无需重新安装和重新生成。

从 agent 的角度看，没有什么特别的事情发生。它就像平常一样对目录读写文件。你的 agent 代码无需改动——没有特殊 API，没有保存/恢复逻辑，也没有序列化。把文件写入 `/mnt/workspace`，停止会话，再恢复它，文件还在那里。

昨天那个会话的计算环境（microVM）已经不在了，但文件系统存活了下来。

### 控制数据的保留时长

默认情况下，会话存储数据在空闲 14 天后保留期结束。如果会话未在此窗口内恢复，数据将被清理。当 agent 端点更新到不同版本、并以相同的 `runtime-session-id` 调用时，会话数据会被刷新。这为挂载目录提供了针对新版本的干净上下文。

### 跨多天的开发工作流

我们来看看这在实践中是什么样子。第 1 天——你调用编码 agent，让它下载代码库、检查文件并搭建开发环境：

```
aws bedrock-agentcore invoke-agent-runtime \
  --agent-runtime-arn "arn:...:agent-runtime/coding-agent" \
  --runtime-session-id "fefc1779-e5e7-49cf-a2c4-abaf478680c4" \
  --payload '{"prompt": "Download the code from s3://amzn-s3-demo-bucket/fastapi-demo-main.zip and list all files"}'
```

agent 将仓库下载到 `/mnt/workspace`，解压后回报：

```
Files in the fastapi-demo-main project:
- Dockerfile
- README.md
- main.py
- requirements.txt
```

你合上笔记本回家。第 2 天——你用相同的会话 ID 调用：

```
aws bedrock-agentcore invoke-agent-runtime \
  --agent-runtime-arn "arn:...:agent-runtime/coding-agent" \
  --runtime-session-id "fefc1779-e5e7-49cf-a2c4-abaf478680c4" \
  --payload '{"prompt": "Add a new function called hello_world to main.py"}'
```

agent 看到的项目与它离开时完全一样。它直接修改 `main.py`。无需重新下载，无需重新解压。当你让 agent 列出文件时，一切都在，包括带有新 `hello_world` 函数的已修改 `main.py`。昨天的计算环境（microVM）已经终止，但工作成果保留了下来。

这解决了第一个挑战，但现在你的 agent 写了新代码，你需要验证它能否正常工作。这就是第二项能力登场的地方。

## 执行 shell 命令：在 agent 的环境中直接进行确定性操作

第二个挑战——在不经过 LLM 的情况下运行确定性操作——由 `InvokeAgentRuntimeCommand` 解决。你可以直接在运行中的 AgentCore Runtime 会话内执行 shell 命令，并通过 HTTP/2 流式返回输出。

关键的洞见是：agent 和 shell 命令擅长的事情不同：

| 使用 execute command | 使用 agent |
| --- | --- |
| 操作有已知的命令（`npm test`、`git push`） | 操作需要推理（“分析这段代码并修复这个 bug”） |
| 你希望确定性执行——相同命令，相同结果 | 你希望由 LLM 决定做什么 |
| 你需要从长时间运行的进程获得流式输出 | 你需要 agent 在循环中使用工具 |
| 操作是你工作流中的验证关卡 | 操作是创造性或分析性的工作 |
| 你在 agent 启动前引导环境 | 你让 agent 处理某项任务 |

当 agent 写完代码、而你需要运行测试时，你不应该为此需要 LLM。`npm test` 就是 `npm test`。命令是已知的，行为应当是确定性的，你要的是原始输出，而不是 LLM 对它的解读。

### 运行命令

使用 AWS SDK for Python（Boto3）执行命令：

```
import boto3
import sys

client = boto3.client('bedrock-agentcore', region_name='us-west-2')

response = client.invoke_agent_runtime_command(
    agentRuntimeArn='arn:aws:bedrock-agentcore:us-west-2:111122223333:runtime/my-agent',
    runtimeSessionId='session-id-at-least-33-characters-long',
    body={
        'command': '/bin/bash -c "npm test"',
        'timeout': 60
    }
)

for event in response['stream']:
    if 'chunk' in event:
        chunk = event['chunk']

        if 'contentStart' in chunk:
            print("Command execution started")

        if 'contentDelta' in chunk:
            delta = chunk['contentDelta']
            if delta.get('stdout'):
                print(delta['stdout'], end='')
            if delta.get('stderr'):
                print(delta['stderr'], end='', file=sys.stderr)

        if 'contentStop' in chunk:
            stop = chunk['contentStop']
            print(f"\nExit code: {stop.get('exitCode')}, Status: {stop.get('status')}")
```

响应会实时流式传输三种事件类型：

| **事件** | **何时** | **包含内容** |
| --- | --- | --- |
| `contentStart` | 第一个数据块 | 确认命令已启动 |
| `contentDelta` | 执行过程中 | `stdout` 和/或 `stderr` 输出 |
| `contentStop` | 最后一个数据块 | `exitCode` 和 `status`（`COMPLETED` 或 `TIMED_OUT`） |

由于输出在产生时就被流式传输，你可以在头几秒内发现失败并立即做出反应，而不必等整个运行结束。

### 同一容器、同一文件系统

这是关键的细节：命令在与 agent 相同的容器、文件系统和环境中运行，而不是 sidecar，也不是通过 socket 通信的独立进程。agent 在 `/mnt/workspace/fix.py` 写入的文件，对于正在运行 `cat /mnt/workspace/fix.py` 的命令立即可见。没有同步步骤，没有文件传输，也无需配置共享卷。

AgentCore Runtime 的 microVM 默认不包含开发者工具。这也意味着你的命令所依赖的任何工具——`git`、`npm` 或语言运行时——都必须添加到你的容器镜像中，或在运行时动态安装。

### 影响使用方式的设计选择

- 一次性执行。每条命令都会启动一个新的 bash 进程，运行至完成（或超时）后返回。命令之间没有持久的 shell 会话。这与 agent 框架使用命令执行的方式一致：构造命令、运行它、读取输出、决定下一步做什么。
- 非阻塞。命令执行不会阻塞 agent 调用。你可以在同一会话上并发地调用 agent 和运行命令。
- 命令之间无状态。每条命令都从全新状态开始，没有 shell 历史，之前命令的环境变量也不会延续。如果你需要状态，请把它编码进命令中：`cd /workspace && export NODE_ENV=test && npm test`。

### 人们正在用它构建什么

- 测试自动化——agent 写完代码后，以命令方式运行 `npm test` 或 `pytest`。流式获取输出，并把具体失败反馈给 agent 进行迭代。
- Git 工作流——分支、提交和推送都是确定性的。把它们作为命令运行，让版本控制逻辑不进入 LLM。
- 环境引导——在 agent 启动前克隆仓库、安装软件包、配置构建工具。以直接命令方式完成会更快、更可靠。
- 构建管线——任何有已知命令、且应严格按规定运行的操作，例如：`cargo build --release`、`mvn package`、`go build.`
- 验证关卡——在 agent 写完代码之后、提交之前，运行 linter、类型检查器和安全扫描器作为关卡。
- 调试——检查运行环境：查看已安装的软件包、磁盘占用和运行中的进程。这些对于理解 agent 的失败原因很有用。

## 结合使用更强大：文件系统就是共享上下文

托管会话存储（处于 public preview）解决了临时文件系统的挑战。execute command 解决了确定性操作的挑战。两者各自都有价值，但结合起来更强大，因为它们共享同一个文件系统，而正是这个文件系统把整个工作流串联起来。

当你的 agent 运行时在 `/mnt/workspace` 配置了托管会话存储时，一切都在同一个持久目录上运作：

- `InvokeAgentRuntime` 在 `/mnt/workspace` 中写代码、生成产物并管理文件。
- `InvokeAgentRuntimeCommand` 运行测试、git 操作和构建，读写同一个 `/mnt/workspace`。
- 停止会话。计算资源（microVM）关闭。`/mnt/workspace` 被持久化。
- 第二天恢复。新的计算资源挂载同一份存储。agent 和 execute command 看到相同的文件。

文件系统成为连接 agent 推理、确定性操作和时间的共享上下文。这在代码中是这样的：

```
import boto3
import json

client = boto3.client('bedrock-agentcore', region_name='us-west-2')

AGENT_ARN = 'arn:aws:bedrock-agentcore:us-west-2:111122223333:runtime/my-coding-agent'
SESSION_ID = 'fefc1779-e5e7-49cf-a2c4-abaf478680c4'

def run_command(command, timeout=60):
    """Execute a shell command and return the exit code."""
    response = client.invoke_agent_runtime_command(
        agentRuntimeArn=AGENT_ARN,
        runtimeSessionId=SESSION_ID,
        contentType='application/json',
        accept='application/vnd.amazon.eventstream',
        body={'command': command, 'timeout': timeout}
    )
    for event in response.get('stream', []):
        if 'chunk' in event and 'contentStop' in event['chunk']:
            return event['chunk']['contentStop'].get('exitCode')
    return None

# Step 1: The agent analyzes the issue and writes a fix
# (Reasoning task → use InvokeAgentRuntime)
response = client.invoke_agent_runtime(
    agentRuntimeArn=AGENT_ARN,
    runtimeSessionId=SESSION_ID,
    payload=json.dumps({
        "prompt": "Read JIRA-1234 and implement the fix in /mnt/workspace"
    }).encode()
)
# Process agent response...

# Step 2: Run the test suite
# (Deterministic operation → use InvokeAgentRuntimeCommand)
exit_code = run_command('/bin/bash -c "cd /mnt/workspace && npm test"', timeout=300)

# Step 3: If tests pass, commit and push
# (Deterministic operation → use InvokeAgentRuntimeCommand)
if exit_code == 0:
    run_command('/bin/bash -c "cd /mnt/workspace && git checkout -b fix/JIRA-1234"')
    run_command('/bin/bash -c "cd /mnt/workspace && git add -A && git commit -m \'Fix JIRA-1234\'"')
    run_command('/bin/bash -c "cd /mnt/workspace && git push origin fix/JIRA-1234"')
```

agent 编写代码，平台执行命令。各自做自己擅长的事。由于 `/mnt/workspace` 由托管会话存储支撑，你可以停止这个会话，第二天再回来，整个工作区仍然在那里，等待 agent 继续迭代。

这就是这个模式：agent 负责推理，execute command 负责执行，持久文件系统负责记忆。这三项能力构成一个闭环，即使你合上笔记本也不会中断。

## 开始使用

这两项能力现在都已可用。以下是开始使用它们的方法：

托管会话存储（public preview）——在调用 `CreateAgentRuntime` 时添加带 `sessionStorage` 的 `filesystemConfigurations`。指定一个以 `/mnt` 开头的挂载路径。agent 写入该路径的所有内容都会在停止/恢复循环中持久保留。每个会话允许的最大数据量为 1 GB。

执行命令——对任何活动会话调用 `InvokeAgentRuntimeCommand`，并传入命令字符串和超时时间。命令在与 agent 相同的容器中运行，并可访问相同的文件系统。

要获取教程和示例代码：

- [Execute command 教程与示例](https://github.com/awslabs/amazon-bedrock-agentcore-samples/tree/main/01-tutorials/01-AgentCore-runtime/09-execute-command)（GitHub）
- [通过 FileSystem 使用托管会话存储](https://github.com/awslabs/amazon-bedrock-agentcore-samples/tree/main/01-tutorials/01-AgentCore-runtime/10-managed-session-storage)（GitHub）
- [在 AgentCore Runtime 会话中执行 shell 命令](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-execute-command.html) —— API 文档
- [使用 Amazon Bedrock AgentCore Runtime 托管 agent](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html) —— Runtime 概览

这一切始于两个挑战：会话停止时丢失工作的 agent，以及不得不交给 LLM 处理或在运行时之外构建的确定性操作。托管会话存储和 execute command 解决了这两个挑战。它们之间共享的文件系统形成了一个开发闭环：agent 负责推理，命令负责执行，而工作成果跨会话持久保留。试用 Amazon Bedrock AgentCore 的新能力，并告诉我们你构建了什么。
