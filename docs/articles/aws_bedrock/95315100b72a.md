# Cato Networks 如何借助 Amazon Bedrock 把自由文本搜索转换为结构化 GraphQL 查询

*这是一篇由 Cato Networks 的 Asaf Fried、Daniel Pienica、Sergey Volkovich 撰写的客座文章。*

[Cato Networks](https://www.catonetworks.com/) 是安全访问服务边缘（SASE）领域的领先提供商，这是一种以云为中心的企业网络与安全统一服务，融合了 SD-WAN、云网络和安全服务边缘（SSE）功能，包括防火墙即服务（FWaaS）、安全 Web 网关、零信任网络访问等。

在我们的 SASE 管理控制台上，中央事件页面提供特定账户上所发生事件的全面视图。在选定时间范围内可能存在数百万个事件，目标是通过各种过滤器精炼这些事件，直到筛选出数量可控、可供分析的相关事件。用户可以查看不同类型的事件，例如安全、连接、系统和管理类事件，每一类都按特定条件分类，例如威胁防护、LAN 监控和固件更新。然而，向搜索查询添加过滤器的过程是手工的，而且可能很耗时，因为这要求对产品词汇表有深入的了解。

为应对这一挑战，我们最近让客户能够在事件管理页面上执行自由文本搜索，使新用户只需极少的产知识即可运行查询。这是通过使用基础模型（FM）把自然语言转换为与我们的产品 GraphQL API 兼容的结构化查询来实现的。

在本文中，我们演示了如何使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/)——一项全托管服务，通过 API 提供来自领先 AI 初创公司和 Amazon 的 FM，因此你可以从广泛的 FM 中选择最适合自己用例的模型。借助 Amazon Bedrock 的无服务器体验，你可以快速上手、用自有数据私密地定制 FM，并使用 AWS 工具快速集成和部署到应用中，而无需管理基础设施。Amazon Bedrock 使我们能够用产品特定知识增强 FM，并把用户的自由文本输入转换为面向产品 API 的结构化搜索查询，从而极大提升数据管理应用中的用户体验与效率。

## 解决方案概览

**Events** 页面包含一个筛选栏，其中有事件过滤器和时间范围过滤器。这些过滤器需要针对每个查询手动添加和更新。下面的截图展示了筛选栏上事件过滤器（1）和时间过滤器（2）的示例（来源：[Cato 知识库](https://support.catonetworks.com/hc/en-us/articles/4413273461905-Analyzing-Events-in-Your-Network)）。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/15/cato-solution-overview-1.png)

事件过滤器是以下形式语句的合取：

- **Key** – 字段名
- **Operator** – 求值运算符（例如 is、in、includes、greater than 等）
- **Value** – 单个值或值的列表

例如，下面的截图展示了一个 ***for action in [ Alert, Block ]*** 过滤器。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/15/cato-solution-overview-2.png)

时间过滤器是遵循 [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601#Time_intervals) 时间间隔标准的时间范围。

例如，下面的截图展示了 `UTC.2024-10-{01/00:00:00--02/00:00:00}` 的时间过滤器。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/01/15/cato-solution-overview-3.png)

把自由文本转换为由事件过滤器与时间过滤器构成的结构化查询，是一项复杂的自然语言处理（NLP）任务，可以借助 FM 完成。针对特定任务定制专用 FM，通常采用以下方法之一：

- **Prompt engineering** – 在模型的上下文/输入窗口中添加指令，帮助模型成功完成任务。
- **检索增强生成（RAG）** – 基于输入查询，从知识库中检索相关上下文。该上下文被追加到原始查询中。这种方法用于把提供给模型的上下文缩减到仅相关数据。
- **Fine-tuning** – 在与任务相关的数据上训练 FM。在这种情况下，相关上下文将被嵌入模型权重，而不再是输入的一部分。

针对我们的具体任务，我们发现 prompt engineering 已足以取得所需的结果。

由于 **Events** 页面上的事件过滤器是我们产品特有的，我们需要向 FM 提供基于自由文本查询生成这些过滤器的精确指令。创建 prompt 时的主要考量是：

- **包含相关上下文** – 这包括以下内容：模型可以使用的可用键、运算符和值。以及具体指令。例如，数值运算符只能与具有数值的键一起使用。
- **确保易于校验** – 鉴于指令和限制条件数量庞大，我们不能在未检查结果有效性的情况下信任模型输出。例如，如果模型生成了一个我们的 API 不支持的键的过滤器，该怎么办？

与其要求 FM 直接生成 GraphQL API 请求，我们可以采用以下方法：

- 指示模型按照广为人知的 [JSON schema 校验](https://json-schema.org/) IETF 标准返回响应。
- 对响应进行 JSON schema 校验。
- 把它转换为 GraphQL API 请求。

## 请求 prompt

基于前面的示例，system prompt 的结构将如下所示：

```
# Genral Instructions

Your task is to convert free text queries to a JSON format that will be used to query security and network events in a SASE management console of Cato Networks. You are only allowed to output text in JSON format. Your output will be validated against the following schema that is compatible with the IETF standard:

# Schema definition
{
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "title": "Query Schema",
   "description": "Query object to be executed in the 'Events' management console page. ",
    "type": "object",
    "properties":
    {
        "filters":
        {
            "type": "array",
           "description": "List of filters to apply in the query, based on the free text query provided.",
            "items":
            {
                "oneOf":
                [
                    {
                        "$ref": "#/$defs/Action"
                    },
                    .
                    .
                    .
                ]
            }
        },
        "time":
        {
            "description": "Start datetime and end datetime to be used in the query.",
            "type": "object",
            "required":
            [
                "start",
                "end"
            ],
            "properties":
            {
                "start":
                {
                    "description": "start datetime",
                    "type": "string",
                    "format": "date-time"
                },
                "end":
                {
                    "description": "end datetime",
                    "type": "string",
                    "format": "date-time"
                }
            }
        },
        "$defs":
        {
            "Operator":
            {
                "description": "The operator used in the filter.",
                "type": "string",
                "enum":
                [
                    "is",
                    "in",
                    "not_in",
                    .
                    .
                    .
                ]
            },
            "Action":
            {
                "required":
                [
                    "id",
                    "operator",
                    "values"
                ],
                "description": "The action taken in the event.",
                "properties":
                {
                    "id":
                    {
                        "const": "action"
                    },
                    "operator":
                    {
                        "$ref": "#/$defs/Operator"
                    },
                    "values":
                    {
                        "type": "array",
                        "minItems": 1,
                        "items":
                        {
                            "type": "string",
                            "enum":
                            [
                                "Block",
                                "Allow",
                                "Monitor",
                                "Alert",
                                "Prompt"
                            ]
                        }
                    }
                }
            },
            .
            .
            .
        }
    }
}
```

每个用户查询（追加到 system prompt 之后）的结构将如下所示：

```
# Free text query
Query: {free_text_query}

# Add current timestamp for context (used for time filters) 
Context: If you need a reference to the current datetime, it is {datetime}, and the current day of the week is {day_of_week}
```

prompt 中包含的同一份 JSON schema 也可以用来校验模型的响应。这一步至关重要，因为模型行为本质上是不确定的，而不符合我们 API 的响应会破坏产品功能。

除了校验一致性之外，JSON schema 还能指出确切的 schema 违规之处。这让我们可以针对不同的失败类型制定策略。例如：

- 如果存在被标记为 [required](https://json-schema.org/understanding-json-schema/reference/object#required) 的缺失字段，则向用户输出转换失败
- 如果为某个事件过滤器给出的值不符合 [format](https://json-schema.org/understanding-json-schema/reference/string#format)，则移除该过滤器，用其他值创建 API 请求，并向用户输出转换警告

在 FM 成功把自由文本转换为结构化输出之后，将其转换为 API 请求（例如 GraphQL）是一个直接且确定的过程。

为验证这一方法，我们创建了一个包含数百条文本查询及其对应预期 JSON 输出的基准。例如，让我们看下面这条文本查询：

`Security events with high risk level from IPS and Anti Malware engines`

对于该查询，我们期望模型基于所提供的 JSON schema 返回以下响应：

```
{
    "filters":
    [
        {
            "id": "risk_level",
            "operator": "is",
            "values":
            [
                "High"
            ]
        },
        {
            "id": "event_type",
            "operator": "is",
            "values":
            [
                "Security"
            ]
        },
        {
            "id": "event_subtype ",
            "operator": "in",
            "values":
            [
                "IPS",
                "Anti Malware"
            ]
        }
    ]
}
```

对于 FM 的每个响应，我们定义三种不同的结果：

- **Success**：JSON 有效，符合 schema，过滤器完全匹配
- **Partial**：JSON 有效，符合 schema，过滤器部分匹配
- **Error**：JSON 无效，或不符合 schema

由于转换失败会导致糟糕的用户体验，该功能的发布以错误率低于 0.05 为条件，最终选定的 FM 是满足该标准且成功率（过滤器完全匹配的响应比例）最高的那个。

## 使用 Amazon Bedrock

Amazon Bedrock 是一项全托管服务，通过单一的无服务器 API 简化了对广泛前沿 FM 的访问。它提供可用于生产的服务，能够高效处理大规模请求，因此非常适合企业级部署。

Amazon Bedrock 使我们能够在不同模型之间高效切换，从而可以简单地针对准确率、延迟和成本进行基准评估与优化，而无需管理底层基础设施的复杂性。此外，Amazon Bedrock 生态中的一些提供商，例如 [Cohere](https://aws.amazon.com/bedrock/cohere/) 和 Anthropic 的 [Claude](https://aws.amazon.com/bedrock/claude/)，提供原生理解 JSON schema 和结构化数据的模型，进一步增强了它们对我们这项具体任务的适用性。

利用我们的基准，我们评估了 Amazon Bedrock 上的多个 FM，综合考虑了准确率、延迟和成本。基于结果，我们选择了 anthropic.claude-3-5-sonnet-20241022-v2:0，它满足错误率标准并取得了最高的成功率，同时保持了合理的成本与延迟。接下来，我们着手开发完整解决方案，其中包含以下组件：

- **管理控制台** – Cato 的管理应用，用户通过它交互，查看其账户的网络与安全事件。
- **GraphQL 服务器** – 一个后端服务，提供用于访问 Cato 账户数据的 GraphQL API。
- **Amazon Bedrock** – 负责托管并处理发往 FM 请求的云服务。
- **自然语言搜索（NLS）服务** – 一个基于 [Amazon Elastic Kubernetes Service](https://aws.amazon.com/eks/)（Amazon EKS）的服务，用于在 Cato 管理控制台与 Amazon Bedrock 之间衔接。该服务负责为 FM 创建完整的 prompt，并使用 JSON schema 校验响应。

## 业务影响

最近的功能更新获得了积极的客户反馈。用户——尤其是那些不熟悉 Cato 的用户——发现新的搜索能力更直观，使得在系统中导航和交互变得简单直接。此外，FM 原生的多语言输入支持让 **Events** 页面更易于非英语母语者使用，帮助他们在自己的语言环境中交互并发现洞察。

最突出的影响之一是查询时间的大幅缩短——从数分钟的手动过滤缩短到近乎即时的结果。使用这项新功能的账户管理员报告称，价值实现时间几乎为零，以极小的学习成本立即获得了收益。

## 结论

把自由文本输入准确转换为结构化数据，对于涉及数据管理和用户交互的应用至关重要。在本文中，我们介绍了 [Cato Networks](https://www.catonetworks.com/) 的一个真实业务用例，它显著提升了用户体验。

通过使用 Amazon Bedrock，我们得以使用最前沿的生成式语言模型，这些模型内置对 JSON schema 和结构化数据的支持。这使我们能够针对成本、延迟和准确率进行优化，而无需管理底层基础设施的复杂性。

尽管 prompt engineering 方案满足了我们的需求，但处理复杂 JSON schema 的用户可能希望探索其他方法来降低成本。在 prompt 中包含整个 schema 可能导致单次查询的 token 数显著偏高。在这种情况下，可以考虑使用 Amazon Bedrock [微调模型](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-models.html)，以更高效地嵌入产品知识。
