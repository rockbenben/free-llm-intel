# Bayer Crop Science 如何使用 AWS Unified Operations 在 Amazon Bedrock AgentCore 上构建代理决策引擎

植物育种决策取决于基因组学、田间试验、图像、环境条件和模型输出的数据。拜耳作物科学针对跨作物、地区和团队的数据运行数百个机器学习 (ML) 模型配置，并且每次运行都需要可重复和管理。为了满足这一要求，拜耳构建了互联决策引擎 (CDE)，这是一个用于部署、编排、监控和重用机器学习工作流程的系统。 CDE 为育种者、分析师、研究人员、数据科学家和数据工程师提供了一种一致的方式来运行分析，同时保留执行历史记录和操作控制。

随着采用率的增长，瓶颈从运行工作流程转变为理解它们。解释结果意味着将 API、文档、元数据存储、仪表板和日志中的上下文拼凑在一起。想要知道工作流程失败的原因、模型做了什么或者结果来自哪里的用户仍然必须知道要检查哪个系统。为了缩小这一差距，拜耳构建了代理决策引擎 (ADE)，这是一个基于 CDE 的多代理自然语言接口。主管代理将每个问题发送给专家代理，专家从相关系统检索上下文，用户无需导航操作堆栈即可收到答案。在第一阶段，ADE 解决了大约 80% 的用户问题，而无需工程师参与。

ADE 在 [Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 上运行，这是一项 AWS 服务，可使用任何框架或模型大规模构建、连接和优化代理。 AgentCore 让团队专注于代理行为，而不是构建和运营自己的代理托管、会话隔离和工具访问层。 AgentCore 的三个功能推动了这一选择：隔离每个用户会话的托管运行时、通过 AgentCore Gateway 访问 AWS Identity and Access Management (IAM) 范围内的工具、将身份验证和授权保持在代理代码之外的 Amazon Bedrock AgentCore 功能，以及允许团队带来自己的 LangGraph 编排和模型选择的与框架无关的设计。

为了准备启动并随后运营 ADE，拜耳聘请了 [AWS 统一运营](https://aws.amazon.com/premiumsupport/plans/unified-operations/)。此次合作提供了一名指定的技术客户经理 (TAM) 和一名生成人工智能领域专家工程师 (DSE)，他们作为 ADE 团队的延伸，从设计到生产。 TAM 作为拜耳的战略顾问，对拜耳的运营模式和业务重点有了既定的了解。 DSE 在 AWS 上带来了生成式 AI 领域的专业知识。在每周三次的技术站立会议中，团队审查并做出设计决策。 DSE 建立了 ADE 工作负载以及拜耳团队运作方式的工作知识，因此技术指导反映了 AWS 服务行为和拜耳的背景。这篇文章讲述了这段旅程：ADE 架构、构建过程中做出的五个设计决策、为生产准备平台的工作以及发布后如何运行。

## 架构概述

ADE 分为四层：用户体验、代理编排、专业代理以及这些代理调用的工具和数据源（图 1）。用户通过 React Web 前端访问 ADE，请求在到达代理之前先通过 Microsoft Entra ID 的身份代理。 GitHub Actions 构建代理容器映像，将它们推送到 [Amazon Elastic Container Registry (Amazon ECR)](https://aws.amazon.com/ecr/)，并将它们部署到 AgentCore 运行时（Amazon Bedrock AgentCore 的一项功能）。

Amazon Bedrock AgentCore 运行时托管代理，并且由于运行时与框架无关，因此团队直接在其上运行自己的基于 LangGraph 的编排。该团队选择 LangGraph 是因为其显式的基于图形的控制流和多步骤工作流程的检查点。 LangGraph 协调工作流程，以 Supervisor 代理作为入口点，对每个请求进行分类，选择专家，并在问题跨越领域时组合结果。数据平面按职责分开。 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 存储 LangGraph 检查点状态。 [Amazon Aurora](https://aws.amazon.com/rds/aurora/) PostgreSQL 存储会话记录、用户反馈和分析。 [Amazon ElastiCache](https://aws.amazon.com/elasticache/) 缓存具有生存时间 (TTL) 的代理响应。 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 中的域内容使用 Amazon Titan Text Embeddings V2 嵌入，并在 [Amazon OpenSearch](https://aws.amazon.com/opensearch-service/) 无服务器检索增强生成 (RAG) 中编制索引。 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 捕获运行时和应用程序遥测数据。 AgentCore Gateway 将后端 API 作为模型上下文协议 (MCP) 工具向代理公开，并将身份验证和授权保留在代理代码之外。

当育种者问“为什么我的表型分析工作流程昨天失败了？”时，主管会对意图进行分类，并将请求发送给故障排除代理。该代理通过 AgentCore Gateway 从 CDE API 读取 CloudWatch 中工作流的遥测数据及其状态，识别故障点，并通过 Supervisor 返回诊断结果（图 2）。饲养员不直接搜索日志。有了故障排除代理，以前需要花费一个多小时手动查找日志并等待工程师支持的诊断现在只需不到 10 分钟。

## 生产过程中的五个设计决策

统一运营 TAM 和 DSE 作为工作团队成员参与了以下决策，而不是作为事后升级点。这使得拜耳可以在提交之前针对 AWS 服务行为测试每个设计，同时保留架构和最终调用的所有权。

### 1. 外部化编排状态，而不将运行时视为无状态

AgentCore 运行时提供隔离会话，在会话生命周期内跨调用保留执行上下文。该上下文不是多步骤工作流程的持久存储。 ADE 将 LangGraph 检查点写入 DynamoDB，以便图表可以在横向扩展事件、重新启动或会话边界后恢复，而不依赖于剩余可用的执行环境。

**原理：** 使用运行时会话主动执行，并将恢复或重建工作流所需的状态持久化在持久服务中。

### 2、企业身份、网关访问、下游授权分离

拜耳在 Microsoft Entra ID 上实现用户身份标准化，而 ADE 的服务则通过 AWS 原生机制相互授权。该团队并没有强迫一个代币跨越每个信任边界，而是为每个边界提供了自己的机制。

Entra ID 仍然是用户身份的来源。 AWS Identity and Access Management (IAM) 授权服务到服务的调用。 AgentCore Gateway 出站授权处理对下游 CDE 服务的访问。请求拦截器 AWS Lambda 函数执行自定义验证并传递下游工具所需的授权属性。该团队在与 DSE 的每一跳都完成了代币合约。

**原理：** 代理系统中的身份失败会在用户身份、代理身份和工具身份之间的转换时聚集。在每一跳定义颁发者、受众、声明、范围和凭证生命周期，而不是在下一边界重复使用对一个边界有效的令牌。

### 3.将模型选择视为接口契约

在构建过程中，团队评估了启用推理模式的较新模型版本。对于该版本，ADE 所依赖的工具使用和结构化输出的组合与其代理的实现方式不兼容。 DSE 确认了该约束，团队保留了当前版本的模型。

**原理：** 对于使用工具的代理，模型选择受到完整接口的限制：工具调用、结构化输出、流行为、推理功能、延迟、配额可用性和特定于模型的请求语义。较新的型号不会自动替代。

### 4.先控制工具表面，再控制提示

CDE 管理 500 多个模型配置。每个 API 的专用 MCP 服务器会增加部署、身份验证和版本管理开销。相反，ADE 向 AgentCore Gateway 注册 OpenAPI 规范，从而将 REST 操作公开为 MCP 工具。添加或更改 API 会成为架构和网关配置更改，而不是新的服务器部署。

工具模式和描述也会消耗输入令牌并与用户的请求和检索到的上下文竞争。 ADE 由专业代理确定工具范围，而不是为每个代理提供完整的目录。对于较大的目录，AgentCore Gateway 支持语义工具搜索，因此代理可以找到相关工具，而无需每次都加载整个目录。

**原则：** 按代理确定工具目录的范围。每个工具定义都会添加标记并扩大模型的决策空间。

### 5. 将复杂的功能从工具提升到代理

可视化最初是作为其他代理调用的工具。随着它的发展，它需要自己的数据检索、图表选择逻辑、重试、错误处理以及是否生成图表或返回现有仪表板的决策。该团队将其转移到专业的可视化代理中。该代理在 AgentCore Code Interpreter 中使用 matplotlib 和 Plotly 生成按需图表，AgentCore Code Interpreter 是 Amazon Bedrock AgentCore 的一项功能，可提供沙盒代码执行环境，并通过 Amazon S3 与其交换数据。当预构建的仪表板是更好的答案时，代理会返回现有的 Amazon Quick 或 Power BI 资产。

**原理：** 工具执行有界操作。当功能开始拥有状态、重试、规划、策略或表示决策时，将其建模为代理。

## 准备 ADE 进行生产

随着构建走向发布，重点从设计转向可操作性：检测代理故障、归因推理成本以及强化部署。

### 可观察性：测量任务失败，而不仅仅是异常

监管架构将一个用户请求转化为一系列模型调用、工具调用和代理切换。即使每个 HTTP 请求都成功，最终的答案也可能是错误的。 ADE 直接遇到了这种情况：应用程序异常处理程序捕获代理错误并返回监控视为成功的响应。使用 DSE 重现问题后，团队在故障路径中添加了自定义 CloudWatch 指标，并针对代理特定条件发出警报：工具调用错误、限制、模型超时和结构化输出验证失败。跟踪和调用日志遵循主管和专家的每个请求。

**原则：** 区分运输成功和任务成功。代理可观察性应显示任务是否完成、哪个代理或工具改变了结果，以及响应是否使用了预期的源。

### 成本归因：将计费归因与请求级遥测相结合

一个 ADE 请求可以调用多个模型和工具，因此账户级别的 Amazon Bedrock 支出并不能解释单位经济效益。该团队使用 DSE 设计了归因方法，使用三种机制来回答不同的问题。 Amazon Bedrock 应用程序推理配置文件将计费模型使用情况归因于应用程序或工作负载。请求元数据和模型调用日志记录将令牌使用与特定代理、功能或请求相关联。 IAM 主体归因添加了身份维度。它们一起让团队估算每次交互的成本，识别昂贵的代理，并确定提示、检索的上下文或工具定义是否驱动令牌的使用。在实践中，依赖 MCP 工具和多个工具调用的可视化和操作代理消耗了最多的代币。

相同的遥测在启动准备期间显示出工作负载，其中包含大量重复输入前缀并且没有提示缓存活动。对于支持的模型，将稳定的指令和工具定义放置在可缓存的提示前缀中可以减少重复的输入处理，从而降低延迟和令牌成本。对于 ADE，缓存稳定的提示前缀可将输入令牌成本降低 20-30%。

### 安全和启动准备

IAM 角色的范围取决于每个代理的职责。故障排除代理可以读取诊断所需的操作数据，但无法修改工作流程。领域专家代理可以查询其检索索引，但不能调用不相关的CDE API。在当今的生产中，ADE 的代理响应由最低权限、仅限于每个代理的只读工具访问、代理响应的结构化输出验证以及基于检索到的 CDE 数据和遥测而不是开放式生成的答案来控制。拜耳还计划评估 Amazon Bedrock Guardrails 作为这些控件的附加层，以补充 CDE 多轮工作流程中已使用的自定义安全检查。

在发布之前，Unified Operations 与 ADE 团队一起使用生成式 AI 镜头进行了关键工作负载审查和架构完善的审查。由于 DSE 已经了解工作负载，因此两项审查都针对 ADE 的特定故障模式、容量风险和部署差距，而不是通用的最佳实践。调查结果包括主管和专业代理之间的故障可见性方面的差距、可变的容器映像标签、有限的映像可追溯性以及缺失的漏洞扫描。该团队通过更强的警报、不可变的版本化图像、Amazon ECR 中的推送扫描以及针对未使用图像的生命周期策略进行响应。

DSE 还与团队一起审查了扩展和配额要求。负载测试验证了应用程序及其服务配额，并暴露了返回空响应的网络故障模式，团队在生产事件之前修复了该模式。截至发布时，该团队已跟踪 35 个阻碍因素，并通过统一运营予以解决。

## 启动、运营和后续步骤

拜耳向一个封闭的群体推出了 ADE，而不是立即向整个组织开放。自推出以来，拜耳作物科学已有 100 多名用户使用 ADE，其中包括育种者、分析师、研究人员、数据科学家和工程师。除了 22 个专业代理之外，ADE 还公开了大约 20 个 API 工具，并且可以在扩展时托管第三方代理。通过 AgentCore Gateway 公开这些 API，而不是为每个 API 使用专用服务器，可以将每个 API 的集成开销减少 99% 以上。在第一阶段，ADE 已经解决了大约 80% 的用户问题，而无需工程师参与。

CDE 仍然是分析的受控执行层。 ADE 在其之上添加了自然语言层，因此用户可以询问工作流状态、结果、模型行为和故障，而无需了解每个底层系统的位置或接口。

随后，工作内容从发射准备转向持续运营。 DSE 继续与团队会面，因此问题分类和运营审查从 ADE 的现有知识开始，而不是从新的提升开始。 ADE 的关键 CloudWatch 警报（包括前面描述的特定于代理的警报）已加入 AWS 事件检测和响应。当发生故障时，AWS 事件管理工程师会在 5 分钟内介入，并从工作负载的上下文开始，而不是从头开始。在安全方面，AWS 安全事件响应工程师在潜在或活动的安全事件期间为团队提供支持，因此 ADE 拥有针对操作和安全问题的 AWS 监控和响应范围。

随着代理之间的通信已经到位，拜耳接下来将重点关注混合云代理的互操作性。该团队正在探索在不同环境中运行的代理如何在无需手动配置的情况下发现彼此并进行通信。

## 结论

拜耳并未用 ADE 取代其分析平台。它使CDE更易于查询和操作。大多数生产工作都在提示之外：持久状态、身份边界、工具范围、任务级可观察性、成本归因和发布准备情况。拜耳拥有架构和每项决策。该团队通过 AWS Unified Operations 与指定的 DSE 和 TAM 合作，在设计过程中根据 AWS 服务行为测试了这些决策，并将相同的上下文引入生产中。
