# 端到端管理 Amazon Bedrock 成本：FinOps 和平台团队的手册

生成式人工智能的成本管理是构建应用程序的团队和负责云支出的团队之间的共同责任。许多团队首先比较每个模型的令牌率并要求应用程序团队缩短提示。这些步骤有所帮助，但它们并没有回答财务和工程领导者在使用规模方面提出的问题：哪个团队花费了这笔钱，用于哪些工作负载，以及这笔支出是否在批准的预算范围内？

代理工作负载使这些问题变得更加紧迫。会话助理通常在每个用户回合发出一次模型调用。代理工作流程（例如计划更改、读取文件、调用工具和迭代的 AI 编码助手）会为每个任务发出许多调用，并在每个调用上携带更大的上下文。因此，令牌消耗随着您授予工作流的自主程度及其所承载的上下文的大小而变化，而不是随着用户交互的数量而变化。由于消耗取决于工作负载的设计和操作方式，因此生成式 AI 的成本管理是一门架构和操作学科。发布的平均值并不能很好地替代您自己的数据：使用 [AWS 定价计算器](https://calculator.aws/) 和 [Amazon Bedrock 定价页面](https://aws.amazon.com/bedrock/pricing) 对费率进行建模，并使用本文的第 2 步来衡量您的工作负载实际消耗的量。

解决方案不是更便宜的型号或更小的提示。这是一种运营模式：一个可重复的循环，将每一美元归属于所有者，使每个请求都可观察，在超支之前发出警报并强制执行预算，优化导致大多数浪费的平台默认值，并按节奏审查整个系统。

在本文中，您将了解如何通过五个步骤来管理 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 成本。您将每一美元归属于所有者，使每个请求都可观察，通过预算和执行控制支出，优化平台默认值以推动最可避免的支出，并运行将数据转化为决策的审查节奏。此方法是根据 AWS 构建块构建的，您可以对其进行自定义并将其应用到您自己的环境中。这篇文章是为两种受众编写的：负责归因、退款、预算和异常审查的 FinOps 从业者，以及负责日志记录、请求元数据、执行和路由默认设置的平台工程团队。

## 操作模型一目了然

五个阶段​​，循环运行。属性：每个 Amazon Bedrock 美元都落在计费管道中的身份、团队和应用程序上。观察：每个请求都记录有足够的元数据来解释产生支出的原因。执行：预算是有约束力的，在最低限度发出警报，并在风险需要时采取硬性阻止。优化：平台默认设置（模型路由、缓存、令牌限制）集中消除浪费，而不是要求每个团队都小心谨慎。操作：一个小记分卡和审查节奏将数据转化为决策。 FinOps 领先第一阶段和第五阶段。平台工程领先二至四名。审查是联合的。这些阶段的顺序是有意安排的。每一项都依赖于前一项，而在没有归因和可观察性的情况下直接跳到优化的团队只是在猜测。

## 第一阶段：归因每一美元

您无法管理无法归因的内容，下游的所有内容（退款、预算、执行、异常检测）都取决于此阶段。其基础是 Amazon Bedrock 的精细成本归因（请参阅 [Amazon Bedrock 精细成本归因简介](https://aws.amazon.com/blogs/machine-learning/introducing-capsular-cost-attribution-for-amazon-bedrock/)）：Amazon Bedrock 自动将推理成本归因于在所有模型中进行调用的 AWS Identity and Access Management (IAM) 委托人，无需管理任何资源。调用者的 ARN 位于 [AWS 成本和使用情况报告 (CUR) 2.0](https://docs.aws.amazon.com/cur/latest/userguide/what-is-cur.html) 的“line_item_iam_principal”列，覆盖范围涵盖 IAM 用户、角色、联合身份和 API 密钥。

设置分为四个步骤：

- 在 CUR 2.0 数据导出中打开 IAM 主体数据。
- 使用团队、应用程序和成本中心等业务维度标记您的 IAM 主体。对于联合访问，将您的身份提供程序配置为通过 OIDC 或 SAML 声明传递会话名称和标签。
- 在 AWS Billing 中激活这些标签作为成本分配标签（控制台或“UpdateCostAllocationTagsStatus” API）。
- 分析标签：它们在 CUR 2.0 中以“iamPrincipal/”前缀（例如“iamPrincipal/team”）出现，并在激活后 24-48 小时内出现在 IAM 类别下的 [AWS Cost Explorer](https://aws.amazon.com/aws-cost-management/aws-cost-explorer/) 中，准备好按团队、应用程序或成本中心进行过滤和分组。

这是发票级的按身份归因，无需自定义基础设施。

### 共享角色问题

最值得关注的模式是共享角色问题，因为这是大多数平台默默失去归属的地方。通过单个 IAM 角色调用 Amazon Bedrock 的大型语言模型 (LLM) 网关将每一美元都归属于该角色，从而完全消除了每个用户的可见性。修复方法是按用户会话管理。网关为每个用户承担一次 Amazon Bedrock 调用角色，将用户的身份作为角色会话名称传递，将其属性作为会话标签传递，然后将这些凭证缓存长达一小时（每个用户每小时一次 AWS Security Token Service (AWS STS) 调用，而不是每个请求）。

这需要两个角色：持有“sts:AssumeRole”和“sts:TagSession”权限的网关执行角色，以及它所承担的 Amazon Bedrock 调用角色。结果是“line_item_iam_principal”条目，例如“assumed-role/BedrockRuntimeRole/gw-alex”，每个条目都带有其用户的标签：在共享网关后面恢复的每用户和每租户归因。
```
import boto3

sts = boto3.client("sts")

# One call per user; cache the returned credentials up to 1 hour
response = sts.assume_role(
    RoleArn="arn:aws:iam::123456789012:role/BedrockRuntimeRole",
    RoleSessionName="gw-alex", # the user, not the gateway
    Tags=[
        {"Key": "team", "Value": "sales-ai"},
        {"Key": "application", "Value": "renewal-agent"},
        {"Key": "costCenter", "Value": "CC-2041"}
    ]
)
```
### 关于应用程序推理配置文件和项目的说明

Amazon Bedrock 还提供了两种归因机制，每种机制都适合不同的模式。 [应用程序推理配置文件](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-create.html) 是在带有成本分配标签的“bedrock-runtime”端点上预先创建的每个应用程序资源。您可以为每个 AWS 区域的每个应用程序、每个模型创建一个配置文件，调用者会引用该配置文件 ARN，该配置文件适合拥有一组小型且稳定的应用程序和模型的团队。 [项目和工作区](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-projects.html) 为“bedrock-mantle”端点（响应 API、聊天完成 API）提供服务。项目不与特定模型绑定，因此单个项目 ID 跨越多个模型，这适合模型使用频繁变化的团队。您在客户端初始化时传递项目 ID，其标签流向 CUR 2.0 和 Cost Explorer（请参阅[使用 Amazon Bedrock 项目管理 AI 成本](https://aws.amazon.com/blogs/machine-learning/manage-ai-costs-with-amazon-bedrock-projects/)）。项目是 Amazon Bedrock 上兼容 OpenAI 的工作负载的归属路径。

对于“Bedrock运行时”工作负载，我们建议通过会话标签将 IAM 主体归因作为主要机制。它可以根据您的身份系统进行扩展，不需要预先创建的资源，并且涵盖每个模型和 API 操作。当一小部分稳定的业务部门需要发票级计费分离且无需更改身份设计时，应用程序推理配置文件可以很好地发挥作用。将项目用于使用响应 API 或聊天完成 API 的“Bedrock地幔”工作负载。

## 第 2 阶段：使每个请求都可观察

CUR 告诉您谁花了。调用日志会告诉您发生了什么。 Amazon Bedrock 支持将请求数据、响应数据和元数据的模型调用日志记录到 Amazon CloudWatch Logs、Amazon Simple Storage Service (Amazon S3) 或两者。使用 Amazon CloudWatch 进行快速操作查询，使用 S3 加 Amazon Athena 进行长期商业智能 (BI) 访问。将日志记录视为基础设施，而不是手动切换：通过代码配置日志组或存储桶，定义保留和加密策略，并在环境设置期间验证交付。如果日志记录仅存在于开发中或仅存在于一个区域，那么随着使用量的增长，您的成本计划就会变得支离破碎。

日志记录还缩小了延迟差距：CUR 归因滞后大约 24 小时，但 CloudWatch 加上 OpenTelemetry 可以支持近乎实时的仪表板，在几分钟内显示每个开发人员的支出（[使用 CloudWatch 和 OpenTelemetry 分析 Claude Code 使用情况](https://aws.amazon.com/blogs/mt/analyzing-claude-code-usage-with-cloudwatch-and-opentelemetry/) 演示了这一端到端）。

### 请求工作负载级别归因的元数据

原始日志回答身份级别的问题。要回答工作负载级别的问题（哪个功能、工作流程或租户生成了令牌），请在每次调用时标记[请求元数据](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html#bedrock-runtime_Converse-request-requestMetadata)。 Amazon Bedrock 在调用日志中捕获此元数据以供以后分析：

以下示例通过美国跨区域推理配置文件在 Amazon Bedrock 上使用 Anthropic Claude Sonnet 5.5。有关模型的完整列表，请参阅 [Amazon Bedrock 中支持的基础模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)。有关按区域划分的可用性，请参阅 [Amazon Bedrock 中 AWS 区域的模型支持](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。
```
response = client.converse(
    modelId="us.anthropic.claude-sonnet-5-5",
    messages=[...],
    requestMetadata={
        "application": "renewal-copilot",
        "workflow": "renewal-risk-summary",
        "tenant": "enterprise-sales",
        "agent": "renewal-agent"
    }
)
```
Amazon Bedrock 不强制执行请求元数据，当每个应用程序执行自己的操作时，团队会很快陷入不一致的架构。平台团队应在共享 SDK 包装器或网关中集中注入强制元数据，规范化密钥集，并将元数据覆盖率视为平台健康指标。

### 诊断查询

日志和元数据就位后，CloudWatch Logs Insights 可以回答长期存在的问题。 *谁消耗了最多的代币*：
```
fields @timestamp, identity.arn as caller, modelId,
input.inputTokenCount as inTokens,
output.outputTokenCount as outTokens
| stats sum(inTokens + outTokens) as totalTokens,
count(*) as calls
by caller, modelId
| sort totalTokens desc
| limit 25
```
按“requestMetadata.application”和“requestMetadata.workflow”而不是“caller”分组的相同查询会生成工作负载级别排行榜：查看产品和工程团队将在退款对话开始时向 FinOps 询问。

**注意：** 前面的查询中显示的字段路径是说明性的。根据您的调用日志架构进行验证，该架构可能因模型、API 操作和日志记录配置而异。

## 第三阶段：执行预算

有了归因和可观察性，执行就成为一种架构选择，而不是一种愿望。共有三个可行的层级。正确的工具取决于您的支出速度、超支的风险承受能力以及您的工具如何连接到 Amazon Bedrock。

### 第 1 层：监控和警报（无阻塞）

Amazon Bedrock 会自动将主体身份写入计费管道。您可以将 AWS 预算置于阈值警报的顶部，并使用第 2 阶段的 OpenTelemetry 仪表板缩小 24 小时 CUR 差距，以实现日常可见性。无需部署，原生 AWS 计费，推理调用不会增加延迟。它与直接调用 Amazon Bedrock 的工具配合使用。没有什么可以阻止消费，所以你会在问题发生后才看到问题。适合早期采用，其中警报加上人工干预就足够了。两个构建器指南介绍了它：[限制 Bedrock 使用和控制成本](https://builder.aws.com/content/3DIYzXtsMwvVh1jsn1CSpa8k2rL/limiting-bedrock-usage-and-controlling-costs)，以及[深入探讨使用 AWS 预算和 Claude 代码管理 Bedrock标签](https://builder.aws.com/content/3EMlLuVf7JSb1fwM8xeQfSi5cz5/deep-dive-on-managing-bedrock-in-claude-code-over-bedrock-with-aws-budgets-tags)。

### 第 2 层：IAM 标签强制执行（拒绝违规）

聚合器 AWS Lambda 函数根据调用日志数据统计 Amazon DynamoDB 中的每个用户令牌和美元计数器。当用户违反其阈值时，该功能会将其身份添加到共享 IAM 拒绝策略（拒绝“bedrock:*”），直到每月重置或管理员覆盖。此实施完全基于 IAM 和 Amazon Bedrock 日志记录运行，推理路径中没有第三方组件，并且它与直接调用 Amazon Bedrock 的工具配合使用。 AWS 解决方案库中的[Claude Code with Amazon Bedrock 指南](https://github.com/aws-solutions-library-samples/guidance-for-claude-code-with-amazon-bedrock) 提供了一个可部署的变体。它在颁发凭证时根据每个用户和每个团队的限制检查每个用户的使用情况，并在用户超出其限制时扣留凭证。由于该检查使用客户端发出的使用情况遥测数据，因此其数字可能与 CUR 不同。无论哪种形式，执行都是异步的。阻止会在 IAM 策略更新的违规调用后几秒到几分钟生效，或者在下次凭证检查的凭证刷新时生效。您的平台团队拥有管道。此层适合需要真正执行、可以容忍延迟并希望将第三方软件排除在数据路径之外的团队。

### 第 3 层：网关执行（同步块）

网关位于推理数据路径中并同步执行预算，在用户或团队超出其限制时返回 HTTP 429。您可以获得亚秒级阻止、每用户模型白名单、令牌速率限制和集中强制的路由规则。权衡：数据路径中必须部署、扩展和安全审查的组件。客户端必须配置为通过网关发送请求。

对于 Claude Code 和 Claude Desktop 队列，官方建议使用 [AWS 的 Claude 应用程序网关](https://aws.amazon.com/blogs/machine-learning/introducing-claude-apps-gateway-for-aws/)。它包含在 CLI 二进制文件中，并作为由 PostgreSQL 支持的单个无状态容器运行。它提供 OIDC 身份、集中管理策略、OpenTelemetry 遥测、多区域 Amazon Bedrock 路由以及开箱即用的每用户/组/组织支出上限。对于跨越多个提供商的混合模型工作负载，通用网关仍然是正确的选择：LiteLLM 通过 [AWS Fargate 参考架构上的 Amazon Elastic Container Service (Amazon ECS)](https://github.com/aws-samples/sample-claude-code-with-litellm-and-bedrock)，或 [为 Amazon Bedrock 构建主动 AI 成本管理系统，部分]中描述的无服务器替代方案2](https://aws.amazon.com/blogs/machine-learning/build-a-proactive-ai-cost-management-system-for-amazon-bedrock-part-2/)。

### 选择等级

有两个因素占主导地位。

**连接性：** 如果开发人员在没有代理的情况下直接调用 Amazon Bedrock，则只有第 1 层和第 2 层可行。

**支出速度：** 如果支出已经达到每月数百万，请立即加强执行。如果警报可以再维持一个季度，请首先投资第一阶段和第二阶段，并在数据需要时增加实施。

大多数组织应该分阶段进行：在第一层观察，然后升级。将这三者视为桥梁，而不是目的地：[架构完善的 Agentic AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentcost07.html) 已经将代理成本治理列为一流的架构问题，而第一阶段的归因基础是任何托管实施的基础。

## 第 4 阶段：优化默认值

大多数Amazon Bedrock废物并非个人疏忽所致。这是无人设置的平台默认值。两个影响最大的杠杆都是平台控制的。

### 模型路由

并非每个任务都需要前沿模型。例程完成（样板、linting 建议、小型重构）可以在更小、更便宜的模型上运行，并通过模型系列中的 [智能提示路由](https://docs.aws.amazon.com/bedrock/latest/userguide/intelligent-prompt-routing.html) 或网关处的路由规则，在更小、更便宜的模型上运行，并为复杂推理保留质量（请参阅[使用 Amazon Bedrock 智能提示路由和提示降低成本和延迟]缓存]（https://aws.amazon.com/blogs/aws/reduce-costs-and-latency-with-amazon-bedrock-intelligent-prompt-routing-and-prompt-caching-preview）了解完整演练）。哪些工作流程可以降级是一个经验问题：从第 2 阶段拉出工作负载排行榜，对排名靠前的条目的更便宜的模型进行质量评估，并路由通过的内容。对于代理编码团队来说，样板文件在呼叫量中占主导地位，超过一半的呼叫落在更便宜的型号上是可以实现的目标。

### 提示缓存

提示缓存奖励稳定的重复前缀。截至 2026 年 10 月，已发布的针对美国东部（弗吉尼亚北部）Anthropic Claude 模型的 [Amazon Bedrock 定价](https://aws.amazon.com/bedrock/pricing/) 按基本输入速率的 1.25 倍计费，生存时间 (TTL) 为 5 分钟（TTL 为 2 倍）。在 Claude Sonnet 4.6 和 Claude Haiku 4.5 上，缓存读取按基本输入速率的 0.1 倍计费；在 Claude Sonnet 5.5 和 Claude Opus 5.5 上，按 0.05 倍计费。检查您的型号和区域的定价页面，因为这些乘数因型号而异，并且可能会发生变化。盈亏平衡数学比团队想象的更友好。对于 5 分钟 TTL，单次重用已经支付了写入费用，针对稳定前缀的 10 次调用成本约为未缓存价格的五分之一（在 0.1 倍读取速率下约为 22%，在 0.05 倍读取速率下约为 17%）。唯一失败的情况是永远不会重新读取的写入，对于 5 分钟 TTL，这要额外花费 25%，对于 1 小时 TTL，则要多花一倍。因此，平台仪表板应该跟踪每个工作流程的缓存读取量和缓存写入量。低读取率意味着前缀实际上不稳定（通常是嵌入在缓存点之前的时间戳或会话 ID）。

候选人直接从调用日志中出现：
```
fields requestMetadata.workflow as workflow, modelId,
input.inputTokenCount as inTokens
| stats count(*) as calls,
avg(inTokens) as avgInputTokens,
sum(inTokens) as totalInputTokens
by workflow, modelId
| filter calls > 50 and avgInputTokens > 2000
| sort totalInputTokens desc
| limit 25
```
**注意：** 前面的查询中显示的字段路径是说明性的。根据您的调用日志架构进行验证，该架构可能因模型、API 操作和日志记录配置而异。

### 应用级优化

第三类节省（及时检索而不是填充上下文、压缩长对话、将稳定的大容量工作流提炼到较小的模型上）属于应用程序团队而不是平台。该平台的工作是让这些节省变得可见：发布每个工作流程的代币排行榜，为每个模型和工作流程设置代币限制，并让拥有昂贵工作流程的团队准确了解他们的立场。

## 第 5 阶段：运行循环

前四个阶段产生数据。这会将其转化为决定。平台团队运行一个常设健康仪表板，其中包含四个信号：

- **模型组合：** 调用哪些模型以及调用频率，是路由规则的直接衡量标准。
- **请求失败率：** 错误、限制和超时。每次重试都会增加延迟，并且在服务端仍完成的请求的客户端超时可能会计费两次，一次针对放弃的调用，一次针对重试。
- **缓存有效性：** 第 4 阶段的读取与写入比率。
- **元数据覆盖率：** 具有完整元数据的生产调用的百分比。每一个未被覆盖的电话都是一个归因盲点，它会悄悄地降低所有其他号码的质量。

当信号发生漂移时，补救措施是策略更改（路由规则、令牌限制、元数据执行），而不是要求团队小心的电子邮件。

### 金钱循环

FinOps 在相同的数据上运行资金循环。当归因干净时，异常检测就会成为调查流，而不是惊慌失措的全体人员：标记的团队或应用程序中的峰值会触发第 2 阶段排行榜中的查找，而不是作战室。退款根据团队和应用程序的 CUR 分组运行。

### 记分卡

以下阈值是起点，而不是处方。在采用它们作为政策之前，请根据您自己的车队数据和定价等级对其进行校准。

| **尺寸** | **公制** | **绿色** | **黄色** | **红色** |
| ---| ---| ---| ---| ---|
| **单位经济效益** |每次成功结果的成本| ≤ 预算 | 1–1.5 倍预算 | >1.5 倍预算 |
| **每开发成本** |每个开发者的每日支出| <100 美元 | $100–$300 | >$300 |
| **模型路由** |调用经济高效模型的百分比 | >50% | 30–50% | <30% |
| **缓存效率** |缓存读取命中率 | >60% | 30–60% | <30% |

绿色意味着工作负载在其经济范围内运行。黄色表示路由或缓存规则正在下滑。红色意味着支出集中在高级模型或未缓存的上下文中，第 3 阶段和第 4 阶段的控制是补救路径。定期审查此记分卡（高速车队每周一次，否则每两周一次），并将其视为 FinOps 加平台联合决策面。

## 结论

在这篇文章中，您学习了如何构建一个五阶段运营模型，使 Amazon Bedrock 支出从不受控制变为完全受管控：

- 使用 IAM 主体标签、会话标签和 CUR 2.0 **将每一美元归属于所有者。
- **通过模型调用日志记录和标记的请求元数据观察**每个请求。
- **在与您的风险相匹配的层级执行**预算：仅监控、IAM 违规拒绝或同步网关阻止。
- **优化**平台默认设置，具有智能提示路由和提示缓存，以集中消除浪费。
- **操作**记分卡并审查将遥测数据转化为政策决策的节奏。

请注意该记分卡的第一行：每个成功结果的成本，而不是每个呼叫的成本。这个区别正是本剧本的重点。这里的一切都使 Amazon Bedrock 支出可见、可归因、有上限且高效，但工作流程可能非常高效，但仍然不值得运行。做出这一决定需要根据其所取代的人工流程来衡量代理，这是一门产品和分析学科，而不是金融运营学科。成本平台贡献的是基础：清晰的归因和每个工作流程的成本数据正是结果衡量所结合的输入。

建立五个阶段，您就可以从头到尾地回答：谁花了它，为什么，以及它是否受到控制。这就是管理 Amazon Bedrock 成本的意义，也是每月账单审核和运营模式之间的区别。
