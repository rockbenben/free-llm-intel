# 为 Amazon Bedrock Knowledge Bases 选择向量存储

在使用 [Amazon Bedrock Knowledge Bases](https://aws.amazon.com/bedrock/knowledge-bases/) 构建检索增强生成（RAG）解决方案时，选对向量存储会影响性能与成本。Amazon Bedrock Knowledge Bases 提供全托管选项，也提供由客户自管的选项（即自行选择向量存储）。本文聚焦客户自管这条路径，针对不同的 RAG 使用场景，对比三种受支持的后端：[Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/)、[带 pgvector 的 Amazon Aurora PostgreSQL](https://aws.amazon.com/rds/aurora/)，以及 [Amazon S3 Vectors](https://aws.amazon.com/s3/features/vectors/)——它是 Amazon Simple Storage Service（Amazon S3）的一项能力。

若需要覆盖所有 AWS 向量解决方案的更广泛指引，请参阅 [AWS 向量解决方案：在你的数据所在之处构建 agentic AI](https://aws.amazon.com/blogs/machine-learning/aws-vector-solutions-build-agentic-ai-where-your-data-lives/)。关于向量数据存储（vector datastore）在生成式 AI 应用中的角色，请参阅[向量数据存储（vector datastore）在生成式 AI 应用中的角色](https://aws.amazon.com/blogs/database/the-role-of-vector-datastores-in-generative-ai-applications/)。关于 RAG 向量数据库的规范性指引，请参阅[为 RAG 使用场景选择 AWS 向量数据库](https://docs.aws.amazon.com/prescriptive-guidance/latest/choosing-an-aws-vector-database-for-rag-use-cases/vector-db-comparison.html)。

## 向量数据库如何融入 RAG 解决方案

RAG 架构将大语言模型（LLM）的能力与信息检索系统结合起来，以生成更准确、更新、且与上下文更相关的回答。它基于 *向量*（vector）这一数学概念：文本被转换为与自身含义对齐的向量。在向量上执行搜索，会找到与问题含义相似的结果，这在捕捉语义相似度上比关键词匹配更有效。

当用户提交查询时，查询会通过嵌入模型转换为向量嵌入。向量数据库中的文档内容已预先经过处理、分块，并以向量嵌入的形式存储；数据库执行相似度搜索，找出嵌入与查询最相似的块。系统通常会检索前 *n* 个块（例如最相似的前五个）来丰富原始查询。这些被检索到的块作为附加上下文提供给 LLM，使其能够生成更有依据、更准确的回答。

向量数据库是原始信息与上下文理解之间的关键桥梁。它把非结构化数据转化为可搜索、具备语义意义的知识空间，帮助大语言模型给出更精确、更相关的回答。向量数据库通过将嵌入向量存储在一种称为向量索引的高效数据结构中来实现这一点，该结构支持快速的高维语义搜索，并能近乎即时地检索语义相似的信息。

## Amazon Bedrock Knowledge Bases 的向量存储后端

采用客户自管（非托管）配置的 Amazon Bedrock Knowledge Bases 支持三种向量存储后端。若需涵盖六项服务的完整 AWS 向量产品组合，请参阅 [AWS 向量解决方案：在你的数据所在之处构建 agentic AI](https://aws.amazon.com/blogs/machine-learning/aws-vector-solutions-build-agentic-ai-where-your-data-lives/)。

[Amazon OpenSearch Service](https://aws.amazon.com/opensearch-service/) 能从保存在内存中的数据提供高速结果。它支持高维向量嵌入，提供托管集群与无服务器两种部署选项，并具备 k-NN 搜索以及结合词法与向量方法的混合搜索等特性。Amazon Bedrock Knowledge Bases 同时支持 Amazon OpenSearch Managed Clusters 与 Amazon OpenSearch Serverless 作为向量存储后端。

[带 pgvector 的 Amazon Aurora PostgreSQL](https://aws.amazon.com/rds/aurora/) 将 Amazon Aurora 的高性能关系型数据库能力与 pgvector 的向量相似度搜索功能结合起来。它支持多种索引方法（IVFFlat 与 HNSW）、多种距离度量（L2、余弦、内积），并可在单精度下处理最高 2,000 维的向量。

[Amazon S3 Vectors](https://aws.amazon.com/s3/features/vectors/) 是具备原生向量支持的 AWS 云对象存储服务，专为大规模向量嵌入的低成本存储与查询而设计。它为相似度搜索提供亚秒级查询性能，同时相比传统向量数据库可将向量存储成本降低最多 90%。

为了解这些选项在实践中表现如何，我们来看三个不同的 RAG 使用场景，它们对延迟、成本与搜索的要求各不相同，并看看哪种向量数据库最适合每个场景。

## 使用场景 1：商品目录搜索

电商平台面临的一个挑战是：帮助客户在数千种商品中准确找到他们想要的东西。有效的商品搜索工具必须理解自然语言查询，并能在购物高峰期扩展以处理数千个并发查询，同时保持低延迟。

### 为什么 Amazon OpenSearch 最适合这一场景

Amazon OpenSearch Serverless 非常适合商品目录搜索，因为它通过混合搜索能力，将语义理解与传统关键词匹配结合起来。面对庞大的商品目录时，性能至关重要。Amazon OpenSearch Serverless 处理向量搜索的查询延迟处于较低的个位数毫秒区间。

它对电商尤其有价值之处，在于内置支持复杂过滤与聚合，从而支撑分面导航（比如按价格、品牌或颜色筛选）。你还可以从余弦相似度、欧氏距离等多种距离度量中选择，以便根据具体需求精细调整商品相似度的计算方式。

Amazon OpenSearch Serverless Classic 集合提供若干优化选项，用于在成本与搜索质量之间取得平衡，详见下一节。

**注意：** Amazon Bedrock Knowledge Bases 同时支持 Amazon OpenSearch Serverless 与 Managed Clusters。以下基准测试在 Serverless Classic 集合上运行。Amazon OpenSearch Serverless NextGen 集合（2026 年 5 月正式可用）目前尚与 Amazon Bedrock Knowledge Bases 的 Retrieve API 不兼容。NextGen 通过从索引映射中移除 engine 与 mode 参数简化了索引创建，默认启用 32 倍压缩与 GPU 加速的索引构建，并支持缩容至零（scale-to-zero）。本文的基准测试使用 Classic 集合，其中 engine、mode 与 HNSW 参数均为显式配置。Managed Clusters 提供额外的调优选项（自动优化、GPU 加速索引、可配置实例规格），可能带来不同结果。

Amazon Bedrock Knowledge Bases 现在已支持 Amazon OpenSearch Serverless NextGen 集合。详情请参阅[博文](https://builder.aws.com/content/3LcIGCDamnUlKFaWv7UMZN07DYi/cut-bedrock-knowledge-base-costs-with-scale-to-zero-opensearch-serverless)。

### Amazon OpenSearch Serverless 向量搜索的性能分析与优化

Amazon OpenSearch 高度可配置，提供多种配置选项。选择这些选项时需谨慎，因为它们会显著影响向量索引的性能。我们挑出其中一些以优化成本和数据库规模为目标的选项，定量展示它们对向量索引性能的影响。

一些常见的优化选项包括：

- **向量嵌入的规模**：更大的向量通常能承载更多关于被嵌入文本的语义信息。但它也会带来更高的内存消耗，从而增加向量索引的规模与成本。像 Amazon Titan Text Embedding v2 这样的现代嵌入模型支持以不同尺寸的向量嵌入文本（Amazon Titan 支持 1024、512 或 256）。针对特定使用场景，对不同尺寸的嵌入做基准测试，以定量衡量其对性能与成本的影响，是很有价值的。各 AWS 区域的模型可用性请参阅 [Amazon Bedrock 中各 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。
- **嵌入的数据类型**：我们还可以通过以更低精度的数据类型（例如二值嵌入，binary embeddings）存储嵌入来减小向量索引规模（从而降低成本）。这能显著缩小向量索引的体积。
- **磁盘优化存储**：Amazon OpenSearch Serverless Classic 集合提供基于磁盘的向量搜索（on_disk 模式），它在内部应用 32 倍二值量化，同时用磁盘上的全精度向量进行重打分。这在降低内存占用时保住了质量，代价是更高的延迟。注意 on_disk 要求 float 数据类型，且不能与二值嵌入同时使用。

根据所用的索引算法，用户还可以配置 HNSW 参数（ef_construction、m），以权衡索引构建时间、内存占用与搜索准确率（实用指引见[选择 HNSW 超参数的实用指南](https://opensearch.org/blog/a-practical-guide-to-selecting-hnsw-hyperparameters/)）。此外，Classic 集合上可使用 Faiss 16 位标量量化来降低内存占用。选择嵌入维度与数据类型需要针对你自己的相关性数据做评估，因为它们会改变嵌入空间本身。选定之后，[auto-optimize](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-auto-optimize.html) 功能可以通过按召回率与延迟阈值评估索引配置，在一小时内消除剩余的 HNSW 与量化调优工作（Amazon OpenSearch Serverless 与使用 Faiss 引擎的 Managed Clusters 均可用）。

### 数据集

我们使用 “Shopping Queries Data Set”（ESCI），这是 Amazon 提供的一个包含大量困难搜索查询的大型数据集。该数据集包含 1,215,851 个不重复的美国商品（标题、描述、要点与品牌；中位数约 1,140 个字符）以及 97,345 条有标注的查询。对每条查询，数据集给出分级相关性标签：Exact（3）、Substitute（2）、Complement（1）与 Irrelevant（0）。下面的示例展示了一条查询，以及一个相关商品和一个不相关商品。

查询：

`self-seal envelopes without window`

相关商品标题：

`BAZIC Security Self Seal Envelope 4 1/8" x 9 1/2" #10, No Window Tint Pattern Mailing Envelopes, Peel & Seal, Office Checks Invoices (30/Pack), 1-Pack`

不相关商品标题：

`ValBox 200 Count #8 Double Window Envelopes 3 5/8" x 8 11/16" Flip and Seal Double Window Security Check Envelopes- Security Tint Pattern Designed for Home Office Secure Mailing`

我们抽样 5,000 条查询（每条查询约有 19 个有标注商品，其中约 17 个相关），并为全部 1,215,851 条商品描述建立索引用于基准测试。我们测量检索质量（NDCG@10）、延迟（并发度为 1 与 10 时的 p50/p95/p99）以及索引规模（ANN 内存占用）。

### 向量索引构建

我们测试了嵌入维度（1024、512、256）与数据类型（float、binary）的所有组合，共六种配置，另加默认 compression_level: 32x 下 on_disk 模式的 1024-float 配置，与 1024-float 内存基线对比（共七种配置）。所有索引均使用 FAISS 与 HNSW（ef_construction=128，m=24），float 嵌入使用 l2 距离，二值嵌入使用 hamming 距离。注意 on_disk 模式要求 data_type: float，并在内部自行以 32× 施加二值量化，再用从磁盘读取的全精度向量做重打分。因此“1024 维二值 on_disk”不是有效的索引配置。每个索引都在集合中单独创建，摄入全部 1.22M 条文档，预热至延迟稳定后测量，然后删除并冷却 15 分钟再开始下一个配置。

### 评估方法

对每种配置，我们在 Amazon OpenSearch Serverless（Classic 集合）中创建向量索引，摄入全部 1,215,851 个商品，等待段合并稳定，然后运行自适应预热直至延迟稳定再开始测量。我们在并发度 1 与并发度 10 下测量 1,000 条查询 × 3 次重复。配置的执行顺序被打散交错，使数据类型与维度同时间解耦。主要基准（表 1）使用语义搜索（仅 k-NN）。我们在表 2 中单独评估混合搜索（语义 + 基于 BM25 的关键词）。我们评估：

- 检索延迟：延迟按 Amazon OpenSearch 结果所报告的、从向量索引中检索相关匹配所耗的时间来测量。它不包含将文本转换为嵌入的时间。
- 检索性能：我们使用[归一化折损累计增益（NDCG）](https://en.wikipedia.org/wiki/Discounted_cumulative_gain#Normalized_DCG)指标为每条查询的检索结果打分。该指标同时考虑被检索文档的相关性及其在排序中的位置，从而衡量排序检索结果的质量。排名更高的相关文档对总分的贡献大于排名更低的文档。分数会以理想排序为参照做归一化，落在 0–1 之间；这在商品搜索中尤为重要，因为用户更可能只看靠前的结果。
- 索引规模：我们报告 ANN（近似最近邻）索引规模，即驱动搜索计算成本、决定容量需求的内存结构。它与总存储规模不同，后者包含每个文档的 _source JSON 副本，并随文档文本量变化。

### 结果

表 1：七种 Amazon OpenSearch Serverless 配置下语义搜索（仅 k-NN）的性能（1,215,851 个已索引向量、5,000 条查询、k=10）。除特别说明外，延迟为并发度 1 下的服务端延迟。差值是与 1024-float 内存基线做配对 bootstrap 得到的。混合搜索结果见表 2。

- 降低维度并不总能降低质量。在这个数据集上，512-float 与 1024-float 基线在统计上无法区分（NDCG 0.3628 对 0.3627，p = 0.87），而索引规模减半（2.79 对 5.34 GiB）、延迟更低（p50 25 对 31 ms）。降到 256 维则出现可测量的 4.4% 质量损失。“无损”与“有损”维度缩减之间的差距将取决于嵌入模型与数据集。
- 二值化能大幅缩小索引规模，但质量代价取决于维度数量。在 1024 维下，二值嵌入将索引规模缩小 13.4 倍（0.40 对 5.34 GiB），NDCG 损失 5.2%，延迟相当（p50 22 对 31 ms）。在 256 维下，质量代价升至 28.3%，而增量规模收益小得多（5.0 倍）。在这个数据集上趋势很清晰：维度越低，二值化的惩罚越大，说明在高维下降低精度比同时降低精度与维度更划算。
- 磁盘模式（on_disk 32×）以延迟为代价保住质量。在 1024 维下，磁盘模式的 NDCG 为 0.3610（相对基线 −0.5%），索引规模与 1024-binary 同为 0.40 GiB，但延迟约为 3 倍（p50 99 ms 对内存模式 31 ms）。1024-binary 与 on_disk 都把索引缩小了 13.4 倍，但磁盘模式保住的质量明显更多（−0.5% 对 −5.2%）。约 3 倍的延迟比在 p50、p95、p99 上一致。在较小的语料规模下这一惩罚可能不显现，因为索引能装进页缓存；到了生产规模它就会出现。

| **配置** | **NDCG@10** | **相对基线 Δ** | **p50 (ms)** | **p95 (ms)** | **p99 (ms)** | **索引规模（ANN）** | **并发 10 下的 p50** |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1024 float | 0.3627 | 基线 | 31 | 44 | 52 | 5.34 GiB | 161 ms |
| 512 float | 0.3628 | +0.0002 | 25 | 37 | 62 | 2.79 GiB | 149 ms |
| 256 float | 0.3468 | −4.4% | 22 | 35 | 47 | 1.51 GiB | 85 ms |
| 1024 binary | 0.3438 | −5.2% | 22 | 37 | 55 | 0.40 GiB | 70 ms |
| 512 binary | 0.3200 | −11.8% | 19 | 30 | 47 | 0.32 GiB | 57 ms |
| 256 binary | 0.2600 | −28.3% | 17 | 24 | 32 | 0.28 GiB | 52 ms |
| 1024 float, on_disk 32× | 0.3610 | −0.5% | 99 | 139 | 176 | 0.40 GiB | 255 ms |

### 混合搜索结果

表 2：1024 维下的混合搜索对比（1,215,851 个向量、5,000 条查询、k=10）。混合搜索使用 normalization-processor，语义权重 0.7、词法权重 0.3。

| **方法** | **1024-float NDCG** | **float p50** | **1024-binary NDCG** | **binary p50** |
| --- | --- | --- | --- | --- |
| 关键词（BM25） | 0.3141 | 11 ms | 0.3177 | 17 ms |
| 语义（k-NN） | 0.3633 | 30 ms | 0.3451 | 17 ms |
| 混合 | 0.3850 | 38 ms | 0.3658 | 35 ms |

相比仅语义搜索，混合搜索带来一致的质量提升。在这个数据集上，混合搜索在 float（0.3633 → 0.3850）与 binary（0.3451 → 0.3658）两种情况下都把 NDCG 提高了 +6.0%。尤其是，1024-binary 加混合搜索（0.3658）超过了仅语义的 1024-float（0.3633），而内存只用了约 1/13（0.40 对 5.34 GiB）。这说明开启混合搜索可以抵消二值化带来的质量代价。

混合搜索会增加延迟。融合步骤大约使串行延迟翻倍（float 从 30 → 38 ms，binary 从 17 → 35 ms），并且在并发下差距会拉大。

注意：该数据集（商品搜索）偏向关键词匹配：仅 BM25 就达到 NDCG 0.314，只比语义搜索低 13%。在自然语言的 RAG 查询上，混合搜索的绝对提升可能不同。融合权重（0.7/0.3）是为演示而设，并非调优结果。

## 使用场景 2：深度研究 agent

深度研究 agent 代表着对传统 RAG 系统的一次显著演进。标准 RAG 执行单次“检索—生成”循环，而深度研究 agent 通过动态推理、自适应规划与迭代式信息检索来完成复杂的多轮研究任务。这类 agent 可以搜索信息、分析发现、根据中间结果调整策略，并在较长时间内综合出全面的报告。

深度研究 agent 的一个关键特征，是它们愿意用更高的延迟换取彻底性。实时搜索应用的用户期待亚秒级响应，而深度研究工作流可能运行数分钟甚至数小时，因此成本效率与可扩展性远比原始查询速度重要。

这一场景的向量存储层必须以最低成本高效处理数千万条嵌入，同时支持用于周期性重建索引的批量操作、灵活的元数据过滤，以及弹性扩展到数百万个向量的能力。

### 为什么 S3 Vectors 最适合这一场景

对于在超大规模嵌入集合上运行的深度研究 agent，Amazon S3 Vectors 是一个实用且高效的向量存储选项。相比传统向量数据库，它大幅降低了存储与查询向量的成本，使得处理从大型文档集合中派生出的数十亿条嵌入变得可行。Amazon S3 Vectors 无需预置基础设施即可弹性伸缩，每个索引支持数千万个向量、每个桶支持数千个索引，适合数据集不断增长的长时运行研究系统。它支持广泛的嵌入维度，并针对批量摄入与检索做了优化，可高效地对大型集合进行后台处理。它与其他 AWS 服务集成，例如 Amazon Bedrock Knowledge Bases（全托管 RAG 能力）与 Amazon OpenSearch，因此团队在需要时可以组合低成本存储与更专业的检索或 RAG 工作流。其按需付费的定价模式进一步适配用量多变或难以预测的研究负载。

### 数据集

我们使用英文维基百科的一个子集，包含超过 600 万篇文章。为进行基准测试，我们按多个规模创建了向量索引，以评估 Amazon S3 Vectors 随数据集增长的表现：

| Small | 250,000 |
| Medium | 500,000 |
| Large | 1,000,000 |

每篇维基百科文章用基于 token 的切分器切成 300 token 的片段。

### 向量索引构建

我们使用 Amazon Titan Text Embedding v2 构建向量索引，它生成 1024 维 float32 嵌入。我们的摄入 pipeline 使用以下配置：

### 结果

我们使用由维基百科内容生成的 100 个研究式问题，在四种索引规模上测量查询延迟。每条查询检索最相似的前 50 个向量。延迟测量不含嵌入生成时间，以单独考察 Amazon S3 Vectors 的性能。

查询示例：

`What factors influence the career trajectories of government officials and policymakers?`

| **索引规模** | **向量数** | **p50 (ms)** | **p95 (ms)** | **p99 (ms)** |
| --- | --- | --- | --- | --- |
| XSmall | 5,314 | 82 | 180 | 220 |
| Small | 250,514 | 205 | 416 | 527 |
| Medium | 500,401 | 266 | 386 | 479 |
| Large | 1,000,413 | 294 | 395 | 506 |

主要发现如下：

- 次线性扩展：查询延迟的增长远慢于索引规模。从 5K 向量增至 1M 向量（200 倍增长），p50 延迟仅增加约 3.5 倍（82ms → 294ms）。这体现了 Amazon S3 Vectors 高效的索引结构。
- 规模化下尾延迟趋稳：p50 → p95 的差距从 5K 向量时的约 100ms 扩大到 250K 时的约 210ms，但随后收窄，并在 500K 到 1M 向量之间稳定在约 100-120ms。这表明索引达到中等规模后，最坏情况的表现变得可预测，继续增加向量不会按比例抬高尾延迟。
- 规模化下的亚秒级查询：即使在 100 万向量下，p99 延迟仍低于 510ms。对于要花数秒在检索到的上下文上推理的深度研究 agent 来说，这一检索开销是可以接受的。

### 与 Amazon OpenSearch 集成以支持混合搜索工作流

对于需要超出纯向量相似度的高级搜索能力的研究负载，Amazon S3 Vectors 通过两种互补的模式与 Amazon OpenSearch Service 集成。

第一种是把 Amazon S3 Vectors 作为高性价比的存储引擎直接用在 Amazon OpenSearch 托管集群之中，让团队既能使用 Amazon OpenSearch 的混合搜索、聚合与复杂过滤，又能保持 Amazon S3 Vectors 的低存储成本。

第二种模式支持将 S3 向量索引一次性导出到 Amazon OpenSearch Serverless 集合，用于特定数据子集需要高查询吞吐或低于 100ms 延迟的实时应用。通过这种分层方式，研究团队可以把全量语料以低成本存放在 Amazon S3 Vectors 中，同时有选择地把高优先级向量提升到 Amazon OpenSearch，以服务性能关键的查询。两种集成方式都保留向量维度与元数据，支持随研究需求演进在存储层之间平滑迁移。

## 使用场景 3：面向客户的 RAG 聊天机器人

面向客户的聊天机器人已成为企业为用户提供即时、个性化支持的重要工具。由 RAG 驱动时，这类聊天机器人可以把回答建立在可信的知识源上，从而给出准确、贴合上下文的回应。然而，源数据类型的多样以及用户组织问题方式的多样，意味着必须能够调优 RAG 查询，以找到符合客户预期的结果。

面向客户的聊天机器人的一个典型场景，是依据内部知识库的内容回答客户问题。知识库会随着时间的推移，围绕客户提问以及构建或改造内部系统的项目逐步积累。它们很可能包含客户问题的答案，但不一定包含与问题中术语相匹配的关键词或直接引用。对知识库检索系统的要求是：

- 能从间接提问中找到原始素材。
- 快速给出答案。
- 可扩展到容纳大型知识库。

### 为什么针对大型知识库的这一场景 Aurora 最合适

对于知识库庞大的面向客户 RAG 聊天机器人，带 pgvector 的 Amazon Aurora PostgreSQL 在 S3 与 Amazon OpenSearch 的容量与性能之间取得平衡，并能更换索引方法，针对任一份数据集优化检索。

Amazon Aurora Serverless 也可用于开发环境等场景，在这些场景中自动的数据库伸缩能在成本或性能上带来好处。

### Aurora PostgreSQL 的性能分析与优化

PostgreSQL 提供多种向量搜索索引算法，包括 HNSW 与 IVFFlat。HNSW（Hierarchical Navigable Small World）构建多层图以进行快速的近似最近邻搜索，查询更快，代价是更高的内存占用与更慢的索引构建。IVFFlat（Inverted File with Flat compression）把向量划分为簇以进行高效搜索，内存占用更低，但需要随数据变化周期性重建索引。关于这些算法的详细对比，请参阅[使用 pgvector 索引优化生成式 AI 应用：深入解析 IVFFlat 与 HNSW 技术](https://aws.amazon.com/blogs/database/optimize-generative-ai-applications-with-pgvector-indexing-a-deep-dive-into-ivfflat-and-hnsw-techniques/)。能够在同一数据集上对多种索引做 A/B 测试，有助于团队针对具体场景优化检索性能。关键的优化因素包括：

- **数据库预置**：实例规格选择与预热考量。
- **索引选择**：针对不同查询模式在 HNSW 与 IVFFlat 之间权衡。
- **索引参数**：每类算法的配置选项。

Amazon Relational Database Service（RDS）提供丰富的实例规格与部署选项，例如多可用区与无服务器运行。这让你可以借助云开发与运维团队熟悉的技能来调优数据库的成本与性能。能够快速切换索引类型，也支持针对真实客户查询做测试，以确定哪种方式效果更好。

### 数据集

测试环境使用一个书籍摘要知识库，具有以下特征：

- 向量数据库中有 500,000 个块。
- 5,000 条随机查询，使用 1024 维嵌入。
- Amazon Aurora v15.15。
- 查询通过 RDS API 接口执行，以便标准化性能测量。
- 数据库实例为预置类型，且已运行至少 15 分钟，以消除启动延迟。

### 向量索引构建

我们构建了两种向量索引用于对比：HNSW 与 IVFFlat。两种索引都使用 1024 维嵌入，并配置了 pgvector 扩展。其余所有参数在两种索引之间保持一致，以保证对比公平。

### 结果

下表给出两种索引类型在 5,000 条查询上的查询延迟测量结果：

| **索引类型** | **p50 (ms)** | **p95 (ms)** | **p99 (ms)** |
| --- | --- | --- | --- |
| HNSW | 31.91 | 38.20 | 89.00 |
| IVFFLAT | 35.94 | 42.38 | 94.08 |

主要发现是：

- **性能相当**：在这个数据集上，HNSW 与 IVFFlat 的中位性能存在稳定差异，两者中位查询时间都在 50ms 以内，但 HNSW 快 4ms。
- **低延迟**：两种索引类型的延迟都适合实时聊天机器人响应，中位耗时低于 50ms。
- **尾延迟稳定**：两种索引类型的 p95 延迟都低于 60ms，说明对大多数查询性能可预测。

这些结果表明，Amazon Aurora PostgreSQL 为面向客户的 RAG 聊天机器人提供了一种平衡方案：延迟介于高性能的 Amazon OpenSearch 与成本优化的 Amazon S3 Vectors 之间，同时保留根据实际使用模式优化索引策略的灵活性。

## Amazon Bedrock Knowledge Bases 的选择指引

以下指引专门针对在 Amazon Bedrock Knowledge Bases 提供的三种向量存储后端之间做选择。若需覆盖全部六项服务的完整 AWS 向量解决方案选择框架，请参阅 [AWS 向量解决方案：在你的数据所在之处构建 agentic AI](https://aws.amazon.com/blogs/machine-learning/aws-vector-solutions-build-agentic-ai-where-your-data-lives/) 中的决策模型。如果你的数据已经存放在支持向量的 AWS 数据存储中，推荐做法是在该现有服务上添加向量搜索，而不是引入新服务。

### 第 1 步：梳理你的应用特征

首先判断你的应用最接近哪种模式：

| . | **实时搜索** | **对话式 AI** | **后台处理** |
| --- | --- | --- | --- |
| **示例** | 商品目录、自动补全、分面搜索 | 客户支持聊天机器人、内部知识助手 | 研究 agent、批量分析、文档处理 |
| **延迟容忍度** | <50ms | <100ms | <1 秒 |
| **查询模式** | 大体量、并发 | 中等、基于会话 | 低频、复杂 |
| **需要混合搜索吗？** | 通常至关重要 | 有时有用 | 很少需要 |
| **成本敏感度** | 较低（性能优先） | 中等 | 较高（成本效率优先） |

大多数应用都能清楚地归入其中一类。如果你的应用跨越多类（例如一个同时支撑面向用户摘要视图的研究 agent），可以考虑分层架构，让不同的向量存储服务工作流的不同部分。

### 第 2 步：把应用特征匹配到向量数据库

了解应用特征之后，就可以把它映射到某个向量数据库：

| **如果你的主要需求是……** | **那么从……开始** | **因为……** |
| --- | --- | --- |
| 具备混合搜索能力的低延迟（<50ms） | **Amazon OpenSearch Service** | 通过内存中的 HNSW 索引提供个位数毫秒延迟，并原生支持结合词法与向量搜索 |
| 平衡的延迟（~100ms）加上关系型数据需求 | **带 pgvector 的 Aurora PostgreSQL** | 提供 50ms 以内的查询耗时，支持对索引类型（HNSW 与 IVFFlat）做 A/B 测试，并与现有 PostgreSQL 工作流自然集成 |
| 超大规模下的低成本存储 | **Amazon S3 Vectors** | 相比传统向量数据库可将向量存储成本降低最多 90%，弹性扩展到数百万向量且无需管理基础设施 |
| 最低的运维开销 | **Amazon S3 Vectors** | 全托管、按需付费——无需预置、打补丁或容量规划 |

### 第 3 步：考虑你的增长路径

今天的选择不必是永久的。随着需求演进，这些服务可以互相补充：

- **从 Amazon S3 Vectors 开始**，如果你在构建原型或对成本敏感的研究负载。如果之后需要对某部分数据获得更快的查询，你可以把向量导出到 Amazon OpenSearch 或 Amazon Aurora，而无需重新嵌入。
- **从 Amazon Aurora PostgreSQL 开始**，如果你需要在单条查询中把向量结果与关系型数据做连接。它是这里唯一能做到这一点的选项。如果你的团队已经在运行 PostgreSQL，它也是自然之选，因为熟悉的运维模式能降低学习曲线。
- **从 Amazon OpenSearch 开始**，如果 20ms 以内的延迟或混合搜索是第一天就有的硬性要求。你可以把 Amazon S3 Vectors 作为全量语料的高性价比后备存储，由 Amazon OpenSearch 服务实时查询。

分层存储模式对超出单一场景的应用尤其强大。用 Amazon S3 Vectors 存放全量语料，用 Amazon OpenSearch Service 或 Amazon Aurora 服务性能关键的子集。

## 结论

使用 Amazon Bedrock Knowledge Bases 构建有效的 RAG 解决方案，需要选择一个能在应用性能需求与运维、成本约束之间取得平衡的向量存储。

通过对三个不同使用场景的分析，可以清晰看出 Amazon Bedrock Knowledge Bases 的每种向量存储后端如何契合不同需求。在需要实时性能与混合搜索的场合，Amazon OpenSearch Serverless 非常合适，它提供低延迟结果，并能灵活结合语义与关键词搜索。带 pgvector 的 Amazon Aurora PostgreSQL 为对话类应用提供了平衡的中间地带，以 PostgreSQL 熟悉的运维方式提供 100ms 以内的延迟，并能迭代索引策略。Amazon S3 Vectors 应对成本敏感的大规模负载，让团队无需承担专用基础设施开销即可存储并查询数百万条嵌入。

本文中的示例与数字来自针对各自数据库定制的不同负载，而不是在共享数据集上的一次正面对比基准，因此这些数字说明的是各选项取舍的形态，而非直接的同类对比。理解这些取舍并针对你自己的负载进行测量，才是选对方案的关键。

随着 RAG 应用走向成熟，你可能会发现分层架构能带来两全其美：规模、性能与成本效率协同工作。这种方式用 Amazon S3 Vectors 低成本存储完整的嵌入语料，同时有选择地把高流量向量提升到 Amazon OpenSearch Service 或 Amazon Aurora。

我们建议你使用本文概述的基准测试方法，针对自己的数据与查询模式评估这些选项。最终，正确的向量存储就是最契合你负载在延迟、成本与检索质量方面需求的那一个。
