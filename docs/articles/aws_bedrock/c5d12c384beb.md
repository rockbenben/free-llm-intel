# 使用 Amazon Bedrock Data Automation 自动生成讲义笔记

各行各业的组织在把会议录音或录制的演示转化为结构化文档时，都面临重大挑战。从演示制作讲义的过程需要大量人工投入，例如回看录像以识别幻灯片切换、转写口述内容、截取并整理截图、让视觉元素与演讲者备注同步，以及排版内容。这些挑战会影响生产效率与可扩展性，尤其在需要处理多份演示录像、会议场次、培训材料和教育内容时。

本文展示如何构建一套自动化、无服务器的方案，使用 [Amazon Bedrock Data Automation](https://aws.amazon.com/bedrock/bda/) 进行视频分析，把网络研讨会录像转化为完整的讲义。我们会带你走一遍实现过程：用 Amazon Bedrock Data Automation 转写内容并检测幻灯片变化，使用 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 基础模型（FM）精修转写文本，并结合由 [AWS Step Functions](https://aws.amazon.com/step-functions/) 编排的自定义 [AWS Lambda](https://aws.amazon.com/lambda/) 函数。通过详尽的实现细节、架构模式与代码，你将学会如何构建一条自动完成讲义创建流程的工作流。

## Amazon Bedrock Data Automation

Amazon Bedrock Data Automation 使用生成式 AI，自动把多模态数据（如图像、视频等）转化为可定制的结构化格式。结构化格式的例子包括视频场景摘要、文本与图像中的不安全或露骨内容，或按广告、品牌整理的内容。本文提出的方案使用 Amazon Bedrock Data Automation 抽取音频片段与视频中的不同镜头。

## 方案概览

我们的方案采用由 Step Functions 编排的无服务器架构，把演示录像处理成完整的讲义。该工作流包含以下步骤：

- 工作流在视频上传到 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）时开始，这会通过 [Amazon EventBridge](https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventBridge.html) 规则触发事件通知，从而启动我们在 Step Functions 中的视频处理工作流。
- 工作流触发后，Amazon Bedrock Data Automation 会启动一个视频转换任务，识别视频中的不同镜头。在我们的场景中，这体现为幻灯片切换。工作流进入等待状态，并检查转换任务的进度。若任务仍在进行，工作流返回等待状态。任务完成后，工作流继续执行，此时我们已抽取到视觉镜头与口述内容。
- 这些视觉镜头与口述内容进入同步步骤。在这个 Lambda 函数中，我们使用 Amazon Bedrock Data Automation 任务的输出，依据时间戳的匹配关系，把口述内容对应到相应的镜头。
- 函数把口述内容与视觉镜头匹配完成后，工作流进入并行状态。该状态的一个步骤是生成截图。我们使用启用了 [FFmpeg](https://ffmpeg.org/ffmpeg.html) 的 Lambda 函数，为每个识别出的视频镜头创建图像。
- 并行状态的另一个步骤是精修我们的转换结果。Amazon Bedrock 通过一个 Map 状态处理并改进每个原始转写片段。这有助于我们去除口语中的不流畅成分并改善句子结构。
- 最后，在截图与精修后的转写文本生成之后，工作流使用一个 Lambda 函数创建讲义。我们使用 [Python-PPTX](https://python-pptx.readthedocs.io/en/latest/) 库，它生成内容同步的最终演示文稿。这些最终讲义存放在 Amazon S3 中以便分发。

## 视频上传与初始处理

工作流始于 Amazon S3，它是我们视频处理 pipeline 的入口。当视频上传到专用的 S3 桶时，会触发事件通知，该通知经 EventBridge 规则启动我们的 Step Functions 工作流。

## 使用 Amazon Bedrock Data Automation 进行镜头检测与转写

这一步使用 Amazon Bedrock Data Automation 检测幻灯片切换并生成视频转写。要把它集成为工作流的一部分，你必须创建一个 [Amazon Bedrock Data Automation project](https://docs.aws.amazon.com/bedrock/latest/userguide/bda-projects.html)。project 是输出配置的分组。每个 project 既可以包含标准输出配置，也可以包含面向文档、图像、视频和音频的自定义 output blueprint。该 project 已作为 AWS CDK 栈的一部分创建好。设置好 project 之后，你可以使用 [InvokeDataAutomationAsync](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_data-automation-runtime_InvokeDataAutomationAsync.html) API 处理内容。在我们的方案中，我们使用 Step Functions 的服务集成来执行这次 API 调用，并启动异步处理任务。系统会返回一个 job ID 用于跟踪进度。

此时工作流必须先检查处理任务的状态，才能继续讲义创建流程。做法是用 [GetDataAutomationStatus](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_data-automation-runtime_GetDataAutomationStatus.html) API 定期向 Amazon Bedrock Data Automation 轮询任务状态。通过组合 Step Functions 的 Wait 与 Choice 状态，我们可以让工作流按固定间隔轮询该 API。这不仅让你能按需自定义间隔，也有助于控制工作流成本，因为在本方案使用的 Standard 工作流中，每次状态转换都会计费。

当 `GetDataAutomationStatus` API 的输出显示为 `SUCCESS` 时，循环退出，工作流进入下一步——把转写文本与视觉镜头匹配起来。

## 将音频片段与对应的镜头匹配

要生成完整的讲义，你必须建立视觉镜头与其对应音频片段之间的映射。这一映射至关重要，它确保最终讲义同时准确呈现演示的视觉内容与口述叙述。

一个*镜头 *表示演示过程中捕获的一系列相互关联的连续画面，通常代表一个明确的视觉状态。在演示这一语境下，一个镜头对应一张新幻灯片，或一次显著增删内容的幻灯片动画。

一个*音频片段*是录音中特定的一段，其中包含不间断的口语，停顿或中断极少。该片段捕获了自然的语流。Amazon Bedrock Data Automation 的输出提供 `audio_segments` 数组，每个片段都包含精确的时间信息，例如该片段的开始与结束时间。这使得与视觉镜头进行准确同步成为可能。

镜头与音频片段之间的同步，对于生成能保留演示叙述流的准确讲义至关重要。为实现这一点，我们实现了一个 Lambda 函数，通过三个步骤管理匹配过程：

- 该函数从 Amazon S3 取回处理结果，其中同时包含视觉镜头与音频片段。
- 它把这些组件构造成结构化的 JSON 数组，为匹配算法做好准备。
- 它执行匹配算法，分析音频片段与镜头的各个时间戳，并基于这些时间戳进行匹配。该算法还考虑镜头与音频片段之间的时间戳重叠。

对于每个镜头，函数检查各音频片段，找出时间戳与该镜头持续时间重叠的片段，确保相关的口述内容在最终讲义中与其对应的幻灯片关联起来。函数把匹配结果直接返回给 Step Functions 工作流，作为下一步的输入——在那里，Amazon Bedrock 将精修转写内容，同时我们会并行生成截图。

## 生成截图

拿到每个镜头及关联音频片段的时间戳之后，你就可以截取演示中的幻灯片来生成完整讲义。Amazon Bedrock Data Automation 检测出的每个镜头都代表演示中一个明确的视觉状态——通常是一张新幻灯片或一次显著的内容变更。在这些精确时刻生成截图，我们就能确保讲义准确反映原始演示的视觉流。

这由一个使用 [ffmpeg-python](https://github.com/kkroening/ffmpeg-python) 库的 Lambda 函数完成。该库是 [FFmpeg media framework](https://ffmpeg.org/) 的 Python 绑定，因此你可以用 Python 方法执行 FFmpeg 终端命令。在我们的场景中，我们可以在 Amazon Bedrock Data Automation 识别出的特定时间戳上从视频中抽帧。截图存放在 S3 桶中，供创建讲义时使用，如下代码所示。要在 Lambda 中使用 `ffmpeg-python`，我们创建了一个包含运行该代码所需依赖的 Lambda ZIP 部署包。如何创建 ZIP 文件的说明可参见我们的 [GitHub repository](https://github.com/aws-samples/sample-automated-handout-notes-with-bedrock-data-automation)。

以下代码展示了如何用 `ffmpeg-python` 截取一张截图。完整的 Lambda 代码可在 [GitHub](https://github.com/aws-samples/sample-automated-handout-notes-with-bedrock-data-automation/blob/main/lambda/screenshot/lambda_function.py) 上查看。

```
## Taking a screenshot at a specific timestamp 
ffmpeg.input(video_path, ss=timestamp).output(screenshot_path, vframes=1).run()
```

## 使用 Amazon Bedrock 精修转写文本

在与截图生成并行的同时，我们使用大语言模型（LLM）精修转写文本。这样做是为了提升转写质量，并过滤掉错误与口语中的不流畅成分。该过程使用 Amazon Bedrock 模型提升已匹配转写片段的质量，同时保持内容准确。我们使用一个通过 Python Boto3 client 与 Amazon Bedrock 集成的 Lambda 函数，并用一个 prompt 引导模型的精修过程。随后该函数可以处理每个转写片段，指示模型执行以下操作：

- 修正拼写错误与语法错误
- 去除口语中的不流畅成分（如“uh”和“um”）
- 保持原意与技术准确性
- 保留演示的上下文

在我们的方案中，我们使用了以下 prompt，其中包含三组示例输入与输出：

```
prompt = '''This is the result of a transcription. 
I want you to look at this audio segment and fix the typos and mistakes present. 
Feel free to use the context of the rest of the transcript to refine (but don't leave out any info). 
Leave out parts where the speaker misspoke. 
Make sure to also remove works like "uh" or "um". 
Only make change to the info or sentence structure when there are mistakes. 
Only give back the refined transcript as output, don't add anything else or any context or title. 
If there are no typos or mistakes, return the original object input. 
Do not explain why you have or have not made any changes; I just want the JSON object. 

These are examples: 
Input: <an example-input> 
Output: <an example-output>

Input: <an example-input> 
Output: <an example-output>

Input: <an example-input> 
Output: <an example-output>

Here is the object: ''' + text
```

下面是一个示例输入与输出：

```
Input: Yeah. Um, so let's talk a little bit about recovering from a ransomware attack, right?

Output: Yes, let's talk a little bit about recovering from a ransomware attack.
```

为了在遵守 Amazon Bedrock InvokeModel API 最大 token 限制的同时优化处理速度，我们使用 Step Functions 的 Map 状态。这让多个转写片段可以并行处理，每个片段对应一段独立的视频。由于这些转写必须逐个处理，Map 状态会高效地分发工作负载。此外，它还通过托管集成减少了运维开销——以数组作为输入，把每个元素传给 Lambda 函数，并在完成后自动重建数组。Map 状态把精修后的转写直接返回给 Step Functions 工作流，在保持匹配片段结构的同时，为最终讲义生成提供更干净、更专业的文本内容。

## 生成讲义

工作流的最后一步是使用 python-pptx 库创建讲义。这一步把精修后的转写文本与已生成的截图结合起来，生成一份完整的演示文档。

该 Lambda 函数顺序处理已匹配的片段，为每张截图创建一张新幻灯片，同时把对应的精修转写作为演讲者备注加入。实现中使用了一个包含 python-pptx 包的自定义 [Lambda layer](https://docs.aws.amazon.com/lambda/latest/dg/chapter-layers.html)。为了在 Lambda 中启用这一功能，我们用 Docker 创建了自定义 layer。用 Docker 创建 layer，可以确保依赖在与 Lambda 运行时匹配的环境中编译。创建该 layer 的说明以及 layer 本身，都可以在我们的 [GitHub repository](https://github.com/aws-samples/sample-automated-handout-notes-with-bedrock-data-automation) 中找到。

该 Lambda 函数的实现使用 python-pptx 创建结构化的演示文稿：

```
import boto3
from pptx import Presentation
from pptx.util import Inches
import os
import json

def lambda_handler(event, context):
    # Create new presentation with specific dimensions
    prs = Presentation()
    prs.slide_width = int(12192000)  # Standard presentation width
    prs.slide_height = int(6858000)  # Standard presentation height
    
    # Process each segment
    for i in range(num_images):
        # Add new slide
        slide = prs.slides.add_slide(prs.slide_layouts[5])
        
        # Add screenshot as full-slide image
        slide.shapes.add_picture(image_path, 0, 0, width=slide_width)
        
        # Add transcript as speaker notes
        notes_slide = slide.notes_slide
        transcription_text = transcription_segments[i].get('transcript', '')
        notes_slide.notes_text_frame.text = transcription_text
    
    # Save presentation
    pptx_path = os.path.join(tmp_dir, "lecture_notes.pptx")
    prs.save(pptx_path)
```

该函数顺序处理各片段，生成一份把视觉镜头与其对应音频片段结合的演示文稿，从而得到可直接分发的讲义。

## 结论

本文演示了如何构建一套无服务器方案，自动从录制的幻灯片演示中生成讲义笔记。通过把 Amazon Bedrock Data Automation 与自定义 Lambda 函数结合，我们构建了一条可扩展的 pipeline，显著减少了制作讲义材料所需的人工投入。我们的方案解决了内容创建中的若干关键挑战：

- 借助 Amazon Bedrock Data Automation 的视频模态能力，自动检测幻灯片切换、内容变更，并准确转写口述内容
- 使用 Amazon Bedrock 对转写文本进行智能精修
- 通过自定义匹配算法实现视觉与文本内容的同步
- 在 Lambda 中使用 ffmpeg-python 与 python-pptx 库生成讲义

这套由 Step Functions 编排的无服务器架构在保持成本效率的同时提供可靠执行。通过为 FFmpeg 使用 Python 包、为 python-pptx 使用 Lambda layer，我们克服了技术限制，构建出一套能处理各种演示格式与长度的稳健方案。该方案可以针对不同用例扩展与定制，从教育机构到企业培训项目皆可。某些步骤（如转写文本精修）还有改进空间，例如增加翻译能力以照顾多元的受众。
