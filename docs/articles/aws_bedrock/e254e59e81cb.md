# 使用 NVIDIA NeMo、Amazon Bedrock AgentCore 与 Strands Agents 构建并部署可扩缩的 AI agent

*本文由来自 NVIDIA 的 Ranjit Rajan、Abdullahi Olaoye 和 Abhishek Sawarkar 共同撰写。*

AI 的下一个前沿不只是更聪明的聊天式助手，而是能在整个系统中推理、规划并执行的自主 agent。但要实现这一点，企业开发者需要从原型走向可安全扩缩的生产级 AI agent。随着企业问题变得愈发复杂，这一挑战也随之增长——它要求架构能够由多个专用 agent 协作完成复杂任务。

在开发阶段构建 AI agent 与在规模化环境部署它们有着根本区别。开发者在原型与生产之间存在一道鸿沟，要在性能优化、资源扩缩、安全实现与运营监控之间挣扎。典型做法让团队不得不来回折腾多个彼此割裂的工具与框架，难以在从开发到部署的全过程中以最佳性能保持一致。这正是 [Strands Agents](https://strandsagents.com/latest/)、[Amazon Bedrock AgentCore](https://aws.amazon.com/bedrock/agentcore/) 与 [NVIDIA NeMo Agent Toolkit](https://developer.nvidia.com/nemo-agent-toolkit) 这套强大组合的用武之地。你可以把这些工具配合使用，设计复杂的多 agent 系统，编排它们，并在生产中以内置的可观测性、agent 评估、性能分析与性能优化来安全地扩缩。本文演示如何使用这一集成方案在 [Amazon Web Services](https://aws.amazon.com/)（AWS）上构建、评估、优化并部署 AI agent，覆盖从最初开发到生产部署的全过程。

## 面向企业级 agent 的基础

开源的 Strands Agents 框架通过其模型驱动的方式简化了 AI agent 开发。开发者使用三个组件来创建 agent：

- [基础模型](https://aws.amazon.com/what-is/foundation-models/)（FM），例如 [Amazon Nova](https://aws.amazon.com/nova/)、Anthropic 的 Claude 以及 Meta 的 Llama
- 工具（20 多个内置工具，以及使用 Python 装饰器编写的自定义工具）
- 引导 agent 行为的 prompt。

该框架内置了与 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 和 [Amazon Simple Storage Service](https://aws.amazon.com/s3/)（Amazon S3）等 AWS 服务的集成，还支持本地测试、持续集成与持续开发（CI/CD）工作流、多种部署选项，以及 [OpenTelemetry](https://opentelemetry.io) 可观测性。

Amazon Bedrock AgentCore 是一个 agentic 平台，用于大规模安全地构建、部署和运营高效的 agent。它提供可组合、全托管的服务：

- Runtime——用于安全、无服务器的 agent 部署
- Memory——用于保留短期与长期上下文
- Gateway——通过把 API 和 [AWS Lambda](https://aws.amazon.com/lambda/) 函数转换为 agent 可用的工具，并连接现有的 [Model Context Protocol](https://modelcontextprotocol.io/)（MCP）服务器，实现安全的工具访问
- Identity——用于安全的 agent 身份与访问管理
- Code Interpreter——用于在沙箱环境中安全执行代码
- Browser——用于快速、安全的 Web 交互
- Observability——提供全面的运营洞察，用于追踪、调试和监控 agent 性能
- Evaluations——基于真实世界行为持续检查 agent 质量
- Policy——使 agent 保持在既定边界之内

这些服务既可独立使用也可协同工作，它们抽象掉了构建、部署和运营复杂 agent 的复杂性，同时可与开源框架或模型配合，提供企业级的安全与可靠性。

## 使用 NeMo Agent Toolkit 进行 agent 评估、性能分析与优化

NVIDIA NeMo Agent Toolkit 是一个开源框架，旨在帮助开发者构建、分析和优化 AI agent，而不论其底层框架为何。它与框架无关的设计意味着可与 Strands Agents、LangChain、LlamaIndex、CrewAI 以及自定义企业框架无缝协作。此外，不同框架在 NeMo Agent Toolkit 中连接后还能互操作。

该 toolkit 的 profiler 提供完整的 agent 工作流分析，追踪单个 agent 与工具的 token 用量、耗时、特定工作流延迟、吞吐量以及运行时间，从而实现有针对性的性能改进。它构建在该 toolkit 的评估 harness 之上，包含针对 [检索增强生成](https://aws.amazon.com/what-is/retrieval-augmented-generation/)（RAG）的专项评估器（例如答案准确率、上下文相关性、响应有据性与 agent 轨迹），并支持针对特定用例的自定义评估器，从而实现有针对性的性能优化。自动化超参数优化器会分析并系统地发现 temperature、top_p 和 max_tokens 等参数的最优取值，同时最大化准确率、有据性与上下文相关性，并最小化 token 用量与延迟，同时还能针对其他自定义指标进行优化。这种自动化方式会分析你完整的 agent 工作流，识别瓶颈，并发现人工调优可能遗漏的最优参数组合。该 toolkit 的智能 GPU 规模计算器通过模拟 agent 延迟与并发场景，并预测生产部署所需的精确 GPU 基础设施，来减少猜测。

该 toolkit 的可观测性集成可连接流行的监控服务，包括 Arize Phoenix、Weights & Biases Weave、Langfuse 以及支持 OpenTelemetry 的系统（例如 [Amazon Bedrock AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html)），形成持续优化与维护的反馈闭环。

### 真实场景实现

本示例演示一个基于知识的 agent，它从网页 URL 检索并综合信息来回答用户查询。该解决方案使用 Strands Agents 并集成 NeMo Agent Toolkit 构建，经过容器化以便快速部署到 [Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)，并利用 Bedrock AgentCore 的各项服务，例如 AgentCore Observability。此外，开发者还可以灵活地集成 Amazon Bedrock 中的全托管模型、托管在 [Amazon SageMaker AI](https://aws.amazon.com/sagemaker/ai/) 中的模型、运行在 [Amazon Elastic Kubernetes Service](https://aws.amazon.com/eks/)（Amazon EKS）中的容器化模型，或其他模型 API 端点。整体架构旨在实现流畅的工作流：从 agent 定义与优化，到容器化与可扩缩部署。

### agent 开发与评估

首先在 Strands Agents 中定义你的 agent 与工作流，然后使用 NeMo Agent Toolkit 对其进行封装，以配置推理用的[大语言模型](https://aws.amazon.com/what-is/large-language-model/)（LLM）与工具等组件。详细的环境搭建指南请参考 GitHub 上的 [Strands Agents 与 NeMo Agent Toolkit 集成示例](https://github.com/NVIDIA/NeMo-Agent-Toolkit/tree/develop/examples/frameworks/strands_demo)。配置好环境后，用一条示例 prompt 从命令行运行单个工作流，以验证你的 agent 逻辑：

```
nat run --config_file examples/frameworks/strands_demo/configs/config.yml --input "How do I use the Strands Agents API?"
```

以下是截断后的终端输出：

```
Workflow Result: 
['The Strands Agents API is a flexible system for managing prompts, including both 
system prompts and user messages. System prompts provide high-level instructions to 
the model about its role, capabilities, and constraints, while user messages are your 
queries or requests to the agent. The API supports multiple techniques for prompting, 
including text prompts, multi-modal prompts, and direct tool calls. For guidance on 
how to write safe and responsible prompts, please refer to the Safety & Security - 
Prompt Engineering documentation.']  
```

为了模拟真实世界场景，你可以用 `serve` 命令启动一个可处理并发请求的长时间运行的 API 服务器，而不是执行单个工作流后就退出：

```
nat serve --config_file examples/frameworks/strands_demo/configs/config.yml
```

以下是截断后的终端输出：

```
INFO:     Application startup complete. 
INFO:     Uvicorn running on http://localhost:8000 (Press CTRL+C to quit) 
```

agent 现在在本地 8000 端口上运行。要与 agent 交互，请打开一个新终端并执行以下 cURL 命令。它将产生与前面 `nat run` 步骤类似的输出，但 agent 会作为常驻服务持续运行，而不是执行一次就退出。这模拟了生产环境中 Amazon Bedrock AgentCore 将 agent 作为容器化服务运行的情形：

```
curl -X 'POST' 'http://localhost:8000/generate' -H 'accept: application/json' -H 'Content-Type: application/json' -d '{"inputs" : "How do I use the Strands Agents API?"}'
```

```

该 toolkit 会针对加权多目标分数评估每一组参数，力求在最大化质量（例如准确率、有据性或工具使用）的同时最小化 token 成本与延迟。完成后，它会生成详细的性能产物与汇总表，方便你快速识别并选出适合生产的最优配置。以下是超参数优化器配置：

    model_name: meta/llama-3.3-70b-instruct

    top_p: 0.9 
    max_tokens: 4096 
    # Enable optimization for these parameters 
    optimizable_params: 
      - temperature 
      - top_p 
      - max_tokens 
    # Define search spaces 
    search_space: 
      temperature: 
        low: 0.1 
        high: 0.7 
        step: 0.2  # Tests: 0.1, 0.3, 0.5, 0.7 
      top_p: 
        low: 0.7 
        high: 1.0 
        step: 0.1  # Tests: 0.7, 0.8, 0.9, 1.0 
      max_tokens: 
        low: 4096 
        high: 8192 
        step: 512  # Tests: 4096, 4608, 5120, 5632, 6144, 6656, 7168, 7680, 8192 
```

在本例中，NeMo Agent Toolkit Optimize 系统地评估了各种参数配置，并把 temperature ≈ 0.7、top_p ≈ 1.0、max_tokens ≈ 6k（6144）认定为在 20 次试验中取得最高准确率的最优配置。该配置相比基线带来了 35% 的准确率提升，同时相比 8192 的 max_tokens 设置取得了 20% 的 token 效率提升——为这些生产部署同时最大化了性能与成本效率。

优化器会绘制成对的帕累托曲线（如下面的成对矩阵对比图所示），以分析不同参数之间的权衡。紧随矩阵对比图之后的平行坐标图显示了达到高质量分数（0.8–1.0）的最优试验（红线）——它们在准确率、有据性与相关性上表现优异，同时以牺牲部分效率为代价：token 用量与延迟在归一化尺度上降至 0.6–0.8。成对矩阵确认了各项质量指标之间的强相关性，并显示实际 token 消耗在所有试验中都紧密聚集在 2,500–3,100 个 token 附近。这些结果表明，通过 prompt 工程可能还能进一步提升准确率与 token 效率。开发团队可以利用 NeMo Agent Toolkit 的 prompt 优化能力实现这一点，在最大化性能的同时帮助降低成本。

### 为生产 GPU 基础设施做合理规模规划

在 agent 完成优化、运行时或推理配置最终确定之后，你可以把注意力转向评估模型部署基础设施。如果你是在一组由 GPU 驱动的 EC2 实例上自管理模型部署，那么把 agent 推向生产最困难的一个环节就是：准确预测需要多少计算资源才能支撑目标用例与并发用户，同时既不超预算也不引发超时。NeMo Agent Toolkit 的 GPU 规模计算器通过使用你 agent 的实际性能画像来确定满足特定服务等级目标（SLO）的最优集群规模，从而应对这一挑战；这种合理规模规划缓解了性能与成本之间的取舍。要生成规模画像，你需要在一系列并发水平（例如 1–32 个同时在线用户）下运行规模计算器：

```
nat sizing calc --config_file examples/frameworks/strands_demo/configs/sizing_config.yml --calc_output_dir /tmp/strands_demo/sizing_calc_run1/ --concurrencies 1,2,4,8,12,20,24,28,32 --num_passes 2
```

nat sizing calc --offline_mode --calc_output_dir /tmp/strands_demo/sizing_calc_run1/ --test_gpu_count 8 --target_workflow_runtime 50 --target_users 25

```
gpu_estimate = (target_users / calculated_concurrency) * test_gpu_count
calculated_concurrency = (target_time_metric - intercept) / slope 
```

### 将生产 agent 部署到 Amazon Bedrock AgentCore

在完成 agent 的评估、性能分析与优化之后，把它部署到生产。虽然在本地运行 agent 已足以用于测试，但企业部署需要一个有助于提供安全性、可扩缩性与稳健内存管理的 agent 运行时，且无需承担管理基础设施的开销。这正是 Amazon Bedrock AgentCore Runtime 的用武之地——它提供企业级无服务器 agent 运行时，且没有基础设施开销。分步部署指南请参考 [NeMo Agent Toolkit 仓库](https://github.com/NVIDIA/NeMo-Agent-Toolkit/tree/develop/examples/frameworks/strands_demo/bedrock_agentcore)。通过把优化后的 agent 打包进容器并部署到无服务器的 Bedrock AgentCore Runtime，你的原型 agent 就升级为一个能应对长时间运行任务与并发用户请求的韧性应用。部署 agent 之后，可见性变得至关重要。这一集成打造了统一的可观测性体验，把不透明的黑盒执行转变为深度可见。你将获得生产环境中每次交互的精确 trace、span 与延迟明细，并通过 OpenTelemetry 集成到 Bedrock AgentCore Observability 中。

下面的截图展示了 Amazon CloudWatch 仪表盘，其中显示 Amazon Bedrock AgentCore 的 trace 与 span，可视化已部署 Strands agent 的执行路径与延迟。

![](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2025/12/17/ML-20105-image-6.png)

Amazon Bedrock AgentCore 的服务远不止 agent 运行时管理与可观测性。你已部署的 agent 可以无缝使用额外的 Bedrock AgentCore 服务，包括用于身份验证与授权的 [Amazon Bedrock AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html)、用于工具访问的 [Amazon Bedrock AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)、用于上下文感知的 [Amazon Bedrock AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html)、用于安全代码执行的 [Amazon Bedrock AgentCore Code Interpreter](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/code-interpreter-tool.html)，以及用于 Web 交互的 [Amazon Bedrock AgentCore Browser](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html)，从而构建企业级 agent。

## 结论

生产环境的 AI agent 需要性能可见性、优化以及可靠的基础设施。就该示例用例而言，这一集成在三个方面都达到了目标：取得 20% 的 token 效率提升、该示例用例 35% 的准确率提升，以及针对目标并发度校准过的性能调优 GPU 基础设施。通过把负责基础 agent 开发与编排的 Strands Agents、负责深入 agent 性能分析、优化与生产 GPU 基础设施合理规模规划（right-sizing）的 NVIDIA NeMo Agent Toolkit，以及负责安全、可扩缩 agent 基础设施的 Amazon Bedrock AgentCore 结合起来，开发者可获得一个有助于提供可预测结果的端到端解决方案。现在，你可以使用这一集成方案在 AWS 上大规模构建、评估、优化并部署 agent。要开始使用，请查看 [Strands Agents 与 NeMo Agent Toolkit 集成示例](https://github.com/NVIDIA/NeMo-Agent-Toolkit/tree/develop/examples/frameworks/strands_demo) 以及[将 Strands Agents 与 NeMo Agent Toolkit 部署](https://github.com/NVIDIA/NeMo-Agent-Toolkit/tree/develop/examples/frameworks/strands_demo/bedrock_agentcore)到 Amazon Bedrock AgentCore Runtime。
