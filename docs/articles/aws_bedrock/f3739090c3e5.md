# 使用 LLM 进行与模型无关的 PII 检测

*一种可配置、由指令驱动的检测器，可运行在任何托管于 Amazon Bedrock 的大语言模型（LLM）上，并已在五个公开 PII 语料上、针对九种基于 LLM 的检测器（包括 OpenAI PrivacyFilter）完成评测。*

自由文本数据集可能包含个人可识别信息（PII），例如姓名、电子邮件或电话号码，组织在准备用于机器学习的文本时，可能会选择把检测 PII 作为一项数据卫生步骤。本文介绍一种基于大语言模型（LLM）构建的可配置、与模型无关的检测器，讲解其实现，把它与现成工具做基准对比，并演示如何在你自己的数据上运行它。

**示例代码：** 本文描述的检测器以 pii-detector 包的形式提供，可在 [sample-llm-pii-detection 仓库](https://github.com/aws-samples/sample-llm-pii-detection) 中获取。下面出现的每一段代码都取自该包，*端到端运行检测器* 一节则讲解如何安装它并在你自己的数据上运行。

PII 很少老老实实待在规整的表单字段里。它藏在客户支持对话记录、HR 档案、聊天日志，以及团队用来做微调的自定义数据集里那些冗长的自由文本列中。它以杂乱、多语言的格式出现，没有任何固定 schema 能预先设想。常用的工具是双向 token 分类模型：即 transformer 标注器，为每个 token 打上在训练时就已经固定下来的 PII 类型标签。像员工 ID 或加密钱包地址这样的领域特定标识符，恰恰是自定义微调语料会引入的东西，而它落在那个被冻结的 schema 之外。要把它加进去，就得重新标注、重新训练。而且这类工具被锁定在一个模型、一种部署方式上。

大语言模型重新定义了这个问题。LLM 在推理时读取自己的指令，因此要检测哪些实体、输出什么格式、部署在哪个后端，全都可以变成配置而不是代码。同一个检测器只需修改 prompt 而不必重新训练，就能针对新的实体类型。它既可以运行在托管 API 上，也可以运行在你自己的虚拟私有云（VPC）内，并能在八种语言之间进行上下文推理，无需翻译环节。本文余下部分将介绍这样一个检测器，讲解其背后的工程实现，并展示它相对现有工具的表现。

## 解决方案概览

该检测器把语言模型视为可配置、可替换的组件。你把输入文本包在指令中，由指令定义要检测的 PII 实体以及期望的输出。模型随后返回一份结构化的已检测实体列表。两个设计选择使它做到与模型无关：

- **指令驱动的检测：** 检测逻辑完全存在于指令和一个轻量解析层中。这使它不依赖任何单一模型的怪癖。
- **可配置后端：** 模型通过统一的推理接口 Inferencer 访问。该包自带 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 的适配器（托管方式，例如 Mistral 或 OSS-GPT）。同一接口也接受面向开源模型的自定义适配器，例如在你自己带 GPU 的基础设施上服务的 OSS-GPT 20B。这覆盖了无法访问 Amazon Bedrock 的安全或隔离网络环境。任何接收消息列表并返回助手文本的对象都满足该接口，因此检测器对所持有的后端保持中立。

定制化来自两个相互独立的组件。第一个是模型，它决定准确率、延迟与成本：你可以选择前沿的 Amazon Bedrock 模型，也可以选择单张 GPU 上的小型开源模型。第二个是实体集合，它定义什么算作 PII。要扩展它，你只需加入一个领域特定标识符，或删掉一个你不需要的。修改实体集合只是对指令做一行编辑，无需重新训练，也无需重新部署。

LLM 的任务范围狭窄且定义明确。它读取文本，识别出所有 PII 片段，并按 schema 为每个片段标注实体类型。它把这些片段以结构化 JSON 返回，再由一个后处理步骤计算精确的字符偏移并去除重复项。

为了把这个方法放进参照系中，我们把它与另外八种基于 LLM 的检测器（包括 [OpenAI PrivacyFilter](https://github.com/openai/privacy-filter)）逐个片段地一起评测。所有检测器都在同一份 ground truth 上打分。

## 技术实现

该检测器由四部分组成。一个 prompt 定义 schema，一个后端运行模型，一个解析与偏移层把响应转换为定位好的片段，一个轻量的调用序列把它们串起来。本节按照请求在系统中流转的顺序逐一讲解各部分，并指出包仓库中实现它的模块。

### PII schema 与检测 prompt

schema 存在于单个系统 prompt 模板中，那是检测器的核心：十五个实体类别，每个都带一行定义；一份 *do-not-flag* 列表；可选的 few-shot 示例；以及输入文本。因为 schema 就是文本，增删一个类别只是改一行。模型被要求以 JSON 列表作答，每个检测到的实体一个对象，携带实体类型与找到的精确文本值。它不返回字符偏移，因为 LLM 无法可靠地给出偏移。这些偏移在后处理阶段回填：

```
[{"pii_entity_type": "FULL_ADDRESSES", "pii_entity_value": "82 Oak Street"},
{"pii_entity_type": "CONTACT_INFO", "pii_entity_value": "bob@example.com"}]
```

完整的 prompt 在 [pii_detector/templates.py](https://github.com/aws-samples/sample-llm-pii-detection/blob/mainline/pii_detector/templates.py) 中，紧随其后的端到端演练会按原样对一条示例字符串运行它。

### LLM 后端集成

因为检测逻辑存在于 prompt 中，后端可以自由选择。在我们提供的实现里，检测器通过一个小接口 Inferencer 与模型对话：*消息进，文本出*。因此同一个检测器既能跑在 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的托管模型上，也能跑在你自己托管于 Amazon Elastic Compute Cloud（Amazon EC2）上的开源模型上。该包自带 Amazon Bedrock 适配器（[pii_detector/bedrock_inferencer.py](https://github.com/aws-samples/sample-llm-pii-detection/blob/mainline/pii_detector/bedrock_inferencer.py)），它是对 [Converse API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html) 的轻量封装。后面的演练会端到端地跑通这条路径。

### 后处理

模型的原始文本分三步变成一份干净的、已定位的片段列表，全部位于 [pii_detector/detector.py](https://github.com/aws-samples/sample-llm-pii-detection/blob/mainline/pii_detector/detector.py) 中：

- **JSON 解析：** 文本响应被转换为字典列表，每一项对应一个检测到的 PII（如果该记录不含任何 PII，则为空列表）。
- **偏移计算：** 因为模型返回的是值而不是位置，所以每个值都用正则表达式在源文本中定位。
- **幻觉标签纠正：** LLM 经常输出近似的标签（把 DATES 写成 DATE、把 CONTACT_INFO 写成 EMAIL），因此每个输出标签都会通过形态学与一张精编的别名表重新归位到 prompt 自身的词表上。任何层级都无法映射的标签会被标记为 UNK，而不是强行套入，这样真正的幻觉仍然可见。

### 端到端运行检测器

本节讲解如何在你自己的数据上运行该检测器，从准备工作一直到清理。每一步都使用本文开头提到的 pii-detector 包。

#### 准备工作

要跟着操作，你需要具备以下准备工作。

- **Python：** Python 3.11 或更高版本。
- **具备 Amazon Bedrock 模型访问权限的 AWS 账户：** 一个其凭证可调用 Amazon Bedrock Converse API 的 AWS 账户。你还需要在 Amazon Bedrock 控制台中为你选定的模型（例如 Mistral 或 OSS-GPT 模型）[启用模型访问权限](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)。各 AWS 区域的模型可用性请参阅 Amazon Bedrock 中的[各 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。检测器通过标准 AWS 凭证链解析凭证，因此要在环境中设置 AWS_PROFILE（或一个 IAM 角色 / SSO 配置文件）以及 AWS_REGION。
- **Python 依赖项：** Boto3，唯一的运行时依赖，需安装到虚拟环境中（见第 1 步）。

以下步骤假设你已克隆 pii-detector 仓库，并在其根目录下操作。

#### 第 1 步：安装包及其依赖

创建虚拟环境并安装 boto3。该包从仓库根目录运行，因此要设置 PYTHONPATH 以让 pii_detector 模块可被解析。

```
cd pii-detector
python -m venv .venv && source .venv/bin/activate
pip install boto3
export PYTHONPATH=.  # so `import pii_detector` resolves from the repo root
```

#### 第 2 步：为 Amazon Bedrock 配置 AWS 凭证

将 Boto3 指向一个可访问 Amazon Bedrock 的账户，并选择你已启用模型访问权限的区域。

```
export AWS_PROFILE=my-bedrock-profile
export AWS_REGION=us-east-1
```

如果你不使用具名配置文件，Boto3 也支持 AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY，但我们建议使用 AWS Identity and Access Management（IAM）角色或 SSO 配置文件，而不是长期有效的静态密钥。

#### 第 3 步：运行随包示例

仓库自带一个可运行的示例（[examples/detect.py](https://github.com/aws-samples/sample-llm-pii-detection/blob/mainline/examples/detect.py)），用于检测示例字符串中的 PII。请从仓库根目录以模块方式运行它。如果凭证或模型访问权限缺失，它会快速失败并给出可操作的指引。

```
python -m examples.detect
```

#### 第 4 步：对自己的文本调用检测器

用任意 Amazon Bedrock Converse 模型 id 构造一个 Amazon Bedrock 推理器，把它包在 PiiDetector 中，然后对字符串调用检测器。它返回已定位的片段列表，每个片段都带精确的字符偏移，可直接送入下游的脱敏步骤。没有需要管理的服务器，因为 Amazon Bedrock 是全托管的。

```
from pii_detector import BedrockInferencer, PiiDetector

inferencer = BedrockInferencer(
    model_id="openai.gpt-oss-20b-1:0",
    region="us-east-1",
)
detector = PiiDetector(inferencer)

spans = detector("Email bob@example.com or call Jane at 555-0142.")
# -> [{'pii_entity_type': 'CONTACT_INFO', 'pii_entity_value': 'bob@example.com',
# 'start': 6, 'end': 21}, ...]
```

`model_id` 可以是任何 Amazon Bedrock Converse 模型 id 或推理配置（inference-profile）id，例如 amazon.nova-lite-v1:0 或 mistral.mistral-large-3-675b-instruct。切换模型只是改一行。检测器与调用点保持完全不变。

#### 第 5 步：清理

Amazon Bedrock 是无服务器的，因此没有基础设施需要拆除，你只为使用的 token 付费。要清理，停用虚拟环境（deactivate），如果不再需要，就关闭你在 Amazon Bedrock 控制台中启用的模型访问权限。如果你用自托管后端替代 Amazon Bedrock，记得自行关闭那台主机，因为检测器不管理后端基础设施。

### 基准测试

评测使用来自 Hugging Face 的五个公开 PII 语料，每个都带有 ground-truth 片段，每个数据集抽样约 10,000 行。它们合计覆盖 49,365 条记录、222,114 个 ground-truth 核心片段，横跨八种语言（de、en、es、fr、hi、it、nl、te）。其领域从多语言合成档案到英文 HR 与客户服务文档，因此这个汇总是一份公平的压力测试。

| **#** | **数据集** | **记录数** | **核心 GT** | **备注** |
| --- | --- | --- | --- | --- |
| 1 | [ai4privacy_500k](https://huggingface.co/datasets/ai4privacy/open-pii-masking-500k-ai4privacy) | 9,947 | 23,822 | 多语言。额外包含 sex/gender、organization |
| 2 | [ai4privacy](https://huggingface.co/datasets/ai4privacy/pii-masking-300k) | 9,936 | 70,720 | 6 种语言。姓名 / 地址 / 电子邮件 / 电话 |
| 3 | [gretel](https://huggingface.co/datasets/gretelai/gretel-pii-masking-en-v1) | 9,991 | 41,967 | 英文。HR / 财务 / 客户服务文档 |
| 4 | [isotonic](https://huggingface.co/datasets/Isotonic/pii-masking-200k) | 9,498 | 21,674 | 另含 15+ 个领域类别 |
| 5 | [nemotron](https://huggingface.co/datasets/nvidia/Nemotron-PII) | 9,993 | 63,931 | 美国/英国。30+ 个原始实体类别 |
| . | 合计 | 49,365 | 222,114 | . |

*预测片段与 ground truth 通过精确的 (start, end, label) 重叠（IoU = 1.0）匹配，并用 Precision、Recall 与 F1 打分。*

在这些数据集之间比较检测器比看上去更难，因为标签对不上。每个检测器和每个数据集都用自己的词表：`PRIVATE_NAMES` 对 `NAME`，`street_address` 对 `street`。为使比较公平，所有原始标签——无论来自检测器输出还是数据集 ground truth——都会映射到由十二个常见实体组成的单一规范分类体系上。然后，每个检测器只在其与数据集双方都声明的标签范围交集上打分。这样，任何检测器都不会因为自己从未声称支持的类别而被扣分。

| **规范实体** | **覆盖范围** |
| --- | --- |
| NAME | 私人与公众人物姓名 |
| ADDRESS | 完整与部分地址、地点 |
| CONTACT_INFO | 电子邮件与电话 |
| DATE | 出生日期、预约、纪念日 |
| AGE | 带单位的年龄 |
| SSN | 社会安全号码与国民编号 |
| FINANCIAL | 信用卡与银行账户 |
| IP_ADDRESS | IPv4、IPv6、MAC |
| URL | 公开与私有 URL |
| USERNAME | 用户名 |
| PASSWORD | 密码、PIN、访问密钥 |
| ID_NUMBER | 护照、执照、客户/员工 ID |

*规范核心实体分类体系。这十二种类型在数据集与检测器中都很常见，因此构成头号对比的基础。包仓库给出了五个数据集各自的原始标签到规范标签的精确映射。*

该分类体系定义了两个报告范围。Core F1 是公平的正面比较数字，覆盖十二种常见实体类型。Extended-entity F1 覆盖数据集特有的类别（职业、公司名称、加密钱包地址等），大多数现成检测器对这些类别毫无概念。我们会在「定制化」一节中讨论该范围。

头号指标是片段级 Core F1。下表把它与一组有代表性的 LLM 检测器的单次检测延迟估算一起报告。表中涵盖 Amazon Bedrock 上的托管模型与在 Amazon EC2 上服务的开源模型，包括 OpenAI PrivacyFilter。所选的开源模型既有比 OSS-GPT 20B 小的、也有比它大的，以便看清范围。Amazon Bedrock 与模型无关，因此正确的选择取决于你的工作负载对准确率、延迟与成本的需求，而不是某一个排名。结果因模型而异。[docs/benchmarks.md](https://github.com/aws-samples/sample-llm-pii-detection/blob/mainline/docs/benchmarks.md) 给出了包含我们测试过的每个模型的完整表格。

| **#** | **检测器** | **后端** | **实例** | **Core F1** | **单次检测（秒）** |
| --- | --- | --- | --- | --- | --- |
| 1 | Mistral Large 3 | Bedrock | — | 83.1% | 1.16 |
| 2 | OSS-GPT 120B | Bedrock | — | 79.4% | 3.91 |
| 3 | Amazon Nova Lite 2 | Bedrock | — | 74.9% | 0.77 |
| 4 | PrivacyFilter | EC2 | g4dn.xlarge | 80.7% | 2.15 |
| 5 | OSS-GPT 20B | EC2 | g5.12xlarge | 81.6% | 1.17 |
| 6 | Qwen3.6-27B | EC2 | g5.12xlarge | 79.5% | 12.79 |
| 7 | Gemma-4-E4B-it | EC2 | g5.xlarge | 79.4% | 0.43 |
| 8 | Qwen3.6-35B-A3B | EC2 | g5.12xlarge | 79.4% | 5.59 |
| 9 | Qwen3.5-9B | EC2 | g5.12xlarge | 76.4% | 15.31 |

*片段级 Core F1（全部五个数据集，49,365 条记录）与估算的单次检测延迟，按后端（Amazon Bedrock、Amazon EC2）分组。实践中检测会以并行工作线程在大量记录上运行。单次检测数值是把总墙钟时间外推回单条记录得到的结果，因此它只是指示性的，而非严格的单次调用测量。*

在同一批语料上，Core F1 从 74.9%（Nova Lite 2）到 83.1%（Mistral Large 3），PrivacyFilter 为 80.7%。Mistral Large 3 与 OSS-GPT 120B 运行在 Amazon Bedrock 上，而 OSS-GPT 20B（81.6%）运行在你自己掌控的硬件上。延迟由模型决定，而不是由参数量决定。OSS-GPT 20B 在 Amazon EC2 上约 1.2 秒，而体量相近的 Qwen3.6-27B 约需 12.8 秒，因为推理的冗长程度与架构比原始规模更重要。后端也是自由选择，因为 OSS-GPT 20B 在 Amazon EC2（81.6%）与 Amazon Bedrock（81.3%）上的得分只差 0.3 分。

准确率在各语言与关键标识符上保持稳定。按 ai4privacy_500k 的细分结果（见包仓库），OSS-GPT 20B 在全部八种语言上都稳居 83–90% 的 Core-F1 区间，包括非拉丁文字的印地语与泰卢固语。它在 SSN、金融与 ID 编号上也达到或超过前沿模型，全部高于 95%。共同的短板是 DATE，约 50%，因为其片段边界与格式确实存在歧义。

### 定制化

到此为止的准确率结果都是在考察「模型」这个杠杆，即用准确率换取延迟与成本。第二个杠杆是要检测的实体集合，它完全由指令定义。这正是该方法超出固定范围工具的地方，最清晰的证据就在那些罕见、领域特定的实体上。

每个数据集都标注了自己的核心之外类别。nemotron 与 gretel 语料标注职业、职位名称与公司名称。isotonic 语料标注加密钱包（比特币与以太坊）地址、车辆标识符与 user-agent 字符串。`ai4privacy_500k` 语料标注 sex、gender 与 organization。运行基础配置的检测器对这些类别毫无概念，得分接近零。

恢复它们不需要新模型、不需要重新训练，只需改指令。我们称之为 *Ext*（Extended）配置。它把每个数据集的额外类别定义与若干示例加入 prompt。它还会移除那些原本会与之冲突的 *do-not-flag* 行，例如一旦公司名称成为目标，就把 “business addresses” 从公开列表中删掉。包仓库列出了完整的额外类别定义。

效果很大，而且在我们测试过的所有模型上都成立，无论前沿还是小型。Extended-entity F1 提升数倍，而核心准确率不变或略好：

| **#** | **检测器** | **后端** | **Extended-entity F1（base ▸ Ext）** | **Core F1（base ▸ Ext）** |
| --- | --- | --- | --- | --- |
| 1 | Qwen3.6-35B-A3B | EC2 | 9.4% ▸ 80.5% | 79.4% ▸ 83.5% |
| 2 | OSS-GPT 20B | EC2 | 12.1% ▸ 73.3% | 81.6% ▸ 83.1% |
| 3 | Mistral Large 3 | Bedrock | 17.3% ▸ 72.7% | 83.1% ▸ 89.1% |
| 4 | Gemma-4-E4B-it | EC2 | 12.5% ▸ 72.5% | 79.4% ▸ 83.8% |

*基础 prompt 与 Extended（Ext）配置在五个公开数据集上的对比，按 Extended-entity F1 排序。加入额外的类别定义后，extended-entity F1 提升约六倍，核心 F1 也跟着略有上升。这在所有被测模型上都有效，而固定范围的标注器不经重新训练就无法针对这些类别。*

同一个杠杆也可推广到全新的实体类型。要针对某个特定领域的目标实体，只需把它的定义与一个示例加入 prompt。无需微调模型，也无需重新部署 pipeline。加上可以自由选择其背后的模型，这就让同一个检测器能在指令层面适配各领域的词表。

## 结论

基于 LLM 的 PII 检测器把现成工具最难的约束——固定的实体范围，以及对单一模型、单一部署的锁定——变成了由两个杠杆设定的配置。模型杠杆设定准确率、延迟与成本。在横跨八种语言的五个公开语料上，九种检测器的 Core F1 落在 74.9–83.1% 之间，PrivacyFilter 为 80.7%。开源的 OSS-GPT 20B（81.6%）在 Amazon Bedrock 或你自己的 GPU 上表现相同。实体杠杆设定什么算作 PII：Extended 配置在所有被测模型上把 extended-entity F1 从约 12% 提升到约 73%，无需重新训练。因为检测逻辑是文本而不是权重，同一个检测器无需新模型就能适配新的领域或后端。

接下来，如果你想把它应用到自己的数据上，请按 *端到端运行检测器* 一节中的演练操作：

- **试用检测器：** 安装该包，并用随包示例在你自建语料的样本上运行，看看它会标记出什么。
- **选择后端：** 若要在不自行托管的前提下取得最高准确率，请使用 Amazon Bedrock 上的托管模型，例如 Mistral Large 3 或 OSS-GPT 20B。若要对数据驻留拥有控制权，请为开源模型（例如在你自己的 GPU 上服务的 OSS-GPT 20B）提供你自己的适配器。
- **扩展 schema：** 以包仓库中记录的 Extended 配置为模板，在 prompt 中加入你的领域特定实体定义，然后在样本上重新运行。
- **闭环：** 把检测到的片段（带精确字符偏移）送入脱敏步骤，让清洗后的文本流入你的训练 pipeline。

从那里开始，自然的扩展都遵循同样的模式。支持新的实体类型或更多语言，只是一次指令修改，而不是一个新模型。
