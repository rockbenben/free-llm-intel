# 使用 SageMaker AI 与 Bedrock AgentCore 构建 agentic 工作流

构建 agentic 工作流时一个常见的挑战是：如何把托管的基础模型（FM）与你自己的、经过成本优化或面向特定领域的模型混合使用，而不必为此重写你的 agent 框架。本文展示如何把 Amazon SageMaker AI 上的 OpenAI 兼容端点与 Amazon Bedrock AgentCore runtime（Amazon Bedrock AgentCore 的一项能力）及其托管部署结合起来。专用的 agent 可以协作处理复杂任务，同时各自使用最适合自身工作的模型。这种组合让你在单一的生产级架构中同时获得成本优化、数据驻留和模型灵活性。

我们将逐步演示如何在 Amazon SageMaker AI 上部署 Qwen 3.5 9B、把它与 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 上的模型一起集成进 [Strands Agents](https://strandsagents.com/) 多 agent 系统，并把整个工作流交付到 Amazon Bedrock AgentCore runtime。重点在于集成机制，包括如何从 SageMaker 端点获得 token 级可观测性——这是 Strands 默认并不提供的。

## 解决方案概览

该架构通过单个 Amazon Bedrock AgentCore 容器连接三条模型托管路径：

- **编排 agent（Bedrock 上的 Claude Haiku 4.5）**——对用户意图分类，并通过 Global 跨区域推理路由任务。
- **预算 agent（Bedrock 上的 Claude Sonnet 4.6）**——以结构化 Pydantic 输出处理 50/30/20 预算拆分。
- **金融分析 agent（Amazon SageMaker AI 上的 Qwen 3.5 9B）**——使用工具调用进行股票分析和投资组合构建。

Amazon Bedrock 的模型可用性因 AWS 区域而异。请参阅 [Amazon Bedrock 中按 AWS 区域支持的模型](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

用户请求进入运行在 Amazon Bedrock AgentCore runtime 内的编排 agent。编排者使用 Strands Agents 的*agents as tools*模式，把请求路由到预算 agent 或金融分析 agent。两个专用 agent 各自调用对应的模型。预算 agent 通过 Amazon Bedrock 调用 Claude Sonnet 4.6，金融分析 agent 通过使用 OpenAI 兼容 API 的 SageMaker AI 实时端点调用 Qwen 3.5 9B。结果经编排者返回给用户。完整源代码请参阅[配套的 GitHub 仓库](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/05-agents/strands/sagemaker-open-ai-compatible-endpoints-agentcore-runtime)。下图展示了该架构。

## 前置条件

要跟着本文动手，你需要具备以下前置条件。

- 一个对 Amazon SageMaker AI、Amazon Bedrock 和 AgentCore 拥有权限的 AWS 账户。

`pip install sagemaker-core openai httpx strands-agents[otel] yfinance pydantic bedrock-agentcore`.

- 一个带有 `sagemaker:InvokeEndpoint` 和 `sagemaker:CallWithBearerToken` 的 AWS Identity and Access Management（IAM）角色。
- 已开通 Claude Haiku 4.5 和 Claude Sonnet 4.6 的 Bedrock 模型访问权限。
- Python 3.12+。

## 步骤 1：在 SageMaker AI 上部署 Qwen 3.5 9B

使用 vLLM Deep Learning Container（DLC）在 `ml.g6e.2xlarge` 上部署 Qwen 3.5 9B，镜像为 `vllm:0.22.1-gpu-py312-cu130`。

```
region = "us-west-2"
model_id = "Qwen/Qwen3.5-9B"
instance_type = "ml.g6e.2xlarge"  # 1x L40S (48GB VRAM)
num_gpu = 1

# vLLM 0.22.1, Python 3.12, CUDA 13.0, Ubuntu 22.04
inference_image = f"763104351884.dkr.ecr.{region}.amazonaws.com/vllm:0.22.1-gpu-py312-cu130-ubuntu22.04-sagemaker"

env = {
    "SM_VLLM_MODEL": model_id,
    "SM_VLLM_TENSOR_PARALLEL_SIZE": "1",
    "SM_VLLM_MAX_MODEL_LEN": "32768",
}

# Create Model
sm.create_model(
    ModelName=model_name,
    ExecutionRoleArn=role,
    PrimaryContainer={"Image": inference_image, "Environment": env},
)

# Create Endpoint Config + Endpoint
sm.create_endpoint_config(
    EndpointConfigName=endpoint_config_name,
    ProductionVariants=[{
        "VariantName": "v1",

    }],
)

sm.create_endpoint(EndpointName=endpoint_name, EndpointConfigName=endpoint_config_name)
```

## 步骤 2：构建多 agent 系统

SageMaker AI 的 OpenAI 兼容 API 需要 bearer token。token 会过期，因此对于任何长时间运行的 agent 会话，你都需要在每次请求时刷新它。用一个 `httpx.Auth` 子类实现自动刷新的 bearer token：

```
import httpx
from openai import AsyncOpenAI
from sagemaker.core.token_generator import generate_token

class SageMakerAuth(httpx.Auth):
    def __init__(self, region): self.region = region
    def auth_flow(self, request):
        request.headers["Authorization"] = f"Bearer {generate_token(region=self.region)}"
        yield request

strands_client = AsyncOpenAI(
    base_url=f"https://runtime.sagemaker.{REGION}.amazonaws.com/endpoints/{ENDPOINT_NAME}/openai/v1",
    api_key="sagemaker",
    http_client=httpx.AsyncClient(auth=SageMakerAuth(region=REGION)),
)
```

使用 Strands Agents 的*agents as tools*模式构建，每次调用都使用全新的 agent 实例。

```
from strands import Agent, tool
from strands.models.openai import OpenAIModel

qwen_model = OpenAIModel(
    client=strands_client, model_id="",
    params={"temperature": 0.7, "max_tokens": 4096, "stream_options": {"include_usage": True}},
)

@tool
def financial_analysis_agent_tool(query: str) -> str:
    fresh = Agent(model=qwen_model, tools=[...], callback_handler=None)
    return str(fresh(query))

orchestrator = Agent(
    model=BedrockModel(model_id="global.anthropic.claude-haiku-4-5-20251001-v1:0"),
    tools=[budget_agent_tool, financial_analysis_agent_tool],
)
```

## 步骤 3：部署到 Amazon Bedrock AgentCore runtime

使用 `bedrock-agentcore-starter-toolkit` 部署。完整的部署 notebook 见 [deploy_agentcore.ipynb](https://github.com/aws-samples/sagemaker-genai-hosting-examples/blob/main/05-agents/strands/sagemaker-open-ai-compatible-endpoints-agentcore-runtime/Lab3/deploy_agentcore.ipynb)。

        "AGENT_OBSERVABILITY_ENABLED": "true",
    }
)
```

## 为 SageMaker 端点配置可观测性

Amazon Bedrock AgentCore runtime 会自动用 OpenTelemetry 为你的 agent 做埋点，但这种埋点并不会平等地覆盖每个模型提供商。要在 Amazon SageMaker AI 上监控 Qwen 模型的成本和延迟，你必须先理解默认埋点在哪些地方不足，以及如何补上这个缺口。

### 挑战：不可见的 token 用量

Amazon Bedrock AgentCore runtime 使用 OpenTelemetry 自动为 agent 做埋点。然而存在一个关键缺口：

- **Amazon Bedrock 模型调用**会自动获得完整的生成式 AI span 以及 token 计数。无需额外工作。
- **Amazon SageMaker OpenAI 兼容端点**（经由 Strands `OpenAIModel`）不会获得自动的 token 遥测。埋点并不把它们识别为生成式 AI 调用。

这意味着金融分析 agent 调用 Amazon SageMaker 上的 Qwen 3.5 9B 所消耗的 token 在 trace 中完全不可见。你无法监控成本、检测回归，也无法调试延迟。

**根本原因：** Strands 的 OTEL 集成会为工具调用和 agent 生命周期事件发出 span，但对 `OpenAIModel` 提供商并不发出带 token 属性的 `gen_ai.chat` span。AgentCore 的自动埋点只把（经由 `boto3` 发起的）Amazon Bedrock 模型推理调用识别为生成式 AI 操作。

### 解决方案：自定义 OpenTelemetry span

手动发出一个 `gen_ai.chat` span，包裹 Amazon SageMaker 的 agent 调用，并从 Strands 内部的 `AgentResult.metrics.accumulated_usage` 中提取 token 用量：

```
from opentelemetry import trace

tracer = trace.get_tracer("financial_analysis_agent")

@tool
def financial_analysis_agent_tool(query: str) -> str:
    """Route investment queries to Qwen on SageMaker with observability."""
    with tracer.start_as_current_span("gen_ai.chat", attributes={
        "gen_ai.system": "openai",
        "gen_ai.request.model": f"qwen3.5-9b ({SAGEMAKER_ENDPOINT_NAME})",
        "gen_ai.operation.name": "chat",
    }) as span:
        fa_agent = Agent(
            model=OpenAIModel(
                client=strands_client, model_id="",
                params={"temperature": 0.7, "max_tokens": 4096,
                        "stream_options": {"include_usage": True}},
            ),
            system_prompt=FINANCIAL_ANALYSIS_PROMPT,
            tools=[get_stock_analysis, create_diversified_portfolio, compare_stock_performance],
            callback_handler=None,
        )
        result = fa_agent(query)
        # Extract token usage from Strands agent metrics
        usage = result.metrics.accumulated_usage
        span.set_attribute("gen_ai.usage.input_tokens", usage.get("inputTokens", 0))
        span.set_attribute("gen_ai.usage.output_tokens", usage.get("outputTokens", 0))
        span.set_attribute("gen_ai.usage.total_tokens", usage.get("totalTokens", 0))
        return str(result)
```

**关键细节：** Strands 在内部用 `inputTokens`、`outputTokens` 和 `totalTokens` 这几个键跟踪 token 用量。只有当模型提供商返回用量数据时，这个 dict 才会被填充。

### 为什么 vLLM 必须使用 stream_options

默认情况下，vLLM 在流式响应中不包含 usage 块。Strands 收到的是文本块，但永远收不到最终的 usage 对象。结果就是 `accumulated_usage` 一直是零。加上 `stream_options: {"include_usage": True}` 会告诉 vLLM 额外发送一个带 token 计数的最终块：

```
qwen_model = OpenAIModel(
    client=strands_client,
    model_id="",
    params={
        "temperature": 0.7,
        "max_tokens": 4096,
        "stream_options": {"include_usage": True},  # Critical for token tracking
    },
)
```

没有这个参数，你的 `gen_ai.chat` span 会报告 0 个 token。这会让自定义 span 失去意义。

### 分步配置

- **开启 Amazon CloudWatch Transaction Search**（每个账户或区域一次性操作）：  `aws xray update-trace-segment-destination --region ap-south-1 --destination CloudWatchLogs aws xray update-indexing-rule --region ap-south-1 --name "Default" \ --rule '{"Probabilistic": {"DesiredSamplingPercentage": 100}}'`
- **安装带 OTEL 扩展的 Strands：** `strands-agents[otel]>=1.0.0`。
- **设置** `AGENT_OBSERVABILITY_ENABLED=true`，写在代码或环境变量里。
- **使用** `opentelemetry-instrument` 作为容器 CMD。
- **为** `OpenAIModel` 参数**添加** `stream_options: {"include_usage": True}`。
- **创建自定义** `gen_ai.chat` span，包裹 SageMaker 的 agent 调用。

### 关键经验

- **Amazon Bedrock AgentCore 会自动埋点 Bedrock 调用**——对 Claude 或 Amazon Nova 无需额外工作。
- **SageMaker OpenAI 端点需要手动 span**——Strands 不会为 `OpenAIModel` 发出 `gen_ai.chat` span。
- **token 用量需要 stream_options**——vLLM 默认不在流式响应中发送 usage。
- **使用 result.metrics.accumulated_usage**——键为：`inputTokens`、`outputTokens`、`totalTokens`。
- **AWS X-Ray 采样率很关键**——默认的 1% 会丢掉大部分 trace。开发期间请用 100%。
- **每次请求使用全新的 agent 实例**——单例会导致并发调用错误。

### 扩展这一模式

这套架构是可组合的。有几个方向可以探索：

- **换成微调模型**：把 `SM_VLLM_MODEL` 指向你在 Amazon Simple Storage Service（Amazon S3）上的微调 checkpoint。认证层、OTEL span 和 AgentCore 部署都保持不变。
- **用推理组件做 A/B 测试：** 在同一个 Amazon SageMaker 端点上部署基线和微调两个变体。给你的 OTEL span 增加一个 variant 属性，以便在 trace 中比较质量。
- **成本感知路由：** 在派发之前检查查询复杂度。把简单查询路由到 Amazon Bedrock 上的 Haiku。把 Amazon SageMaker 的 GPU 端点留给多步推理任务。

## 清理

```

## 结论

本文展示了如何把 Amazon SageMaker AI 上的自托管模型连接到 Amazon Bedrock AgentCore runtime，并且关键的是，如何从 Strands Agents 默认不埋点的 Amazon SageMaker 端点获得完整的 token 级可观测性。

- `httpx.Auth` + `generate_token()` + `AsyncOpenAI`——在 AgentCore 内部实现生产级 SageMaker 认证。
- 自定义 `gen_ai.chat` OTEL span + `stream_options: {"include_usage": True}`——为 Amazon SageMaker 端点提供完整的 token 可见性。
- `result.metrics.accumulated_usage`——用于提取 token 计数的 Strands API。
