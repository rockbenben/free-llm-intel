# Amazon SageMaker AI 实时端点现在支持 KV 缓存感知路由

今天，Amazon SageMaker AI 推出了 KV 缓存感知路由（KV 感知路由），这是一种针对实时终端节点的新路由策略。它使用模型容器报告的缓存状态。它将每个请求发送到一个实例，该实例已经保存了其提示的长缓存匹配，并且不太忙。它适用于为具有多轮对话、长共享提示或重负载的大型语言模型 (LLM) 提供服务的团队。您可以在两个位置将其打开：向模型添加一个环境变量，以便容器报告其缓存内容，并在端点配置中将 `RoutingStrategy` 设置为 `KV_AWARE`。您的客户端使用与以前相同的 API 调用端点。

它解决的问题如下：LLM 应用程序（例如聊天助手、检索增强生成 (RAG)）和具有长系统提示的代理会发送许多以相同文本开头的请求。模型将其在提示时所做的工作保留在 GPU 内存、KV 缓存中，并在同一启动再次到达同一实例时跳过该工作。在[本系列的第 1 部分](https://aws.amazon.com/blogs/machine-learning/reduce-llm-latency-with-prefix-aware-routing-on-amazon-sagemaker-inference/) 中，我们为 Amazon SageMaker AI 引入了前缀感知路由，它将以相同方式启动的请求发送到同一实例。前缀感知路由仅从请求中推断出前缀的缓存位置，因此它无法判断实例何时逐出该缓存。

前缀感知路由仅从请求中选择一个实例。它对请求的开头进行哈希处理，直到您配置的 `PrefixLength`（`InvokeEndpoint` 有效负载的字节，或 OpenAI 兼容的聊天完成 API 的消息文本的字符），并将以相同方式开始的请求发送到同一实例。它永远看不到实例实际缓存的内容。当每个请求都以相同的共享文本开始时，这种方法效果很好，但在两种情况下效果较差：

实例上的缓存会随着时间而变化。当实例的 GPU 内存填满时，实例会逐出旧的 KV 缓存条目，但路由器会继续向那里发送匹配的请求，就好像缓存仍然是热的一样。

谈话一开始很简短。在多回合聊天中，每个回合都会添加到历史记录中。虽然请求仍然比 `PrefixLength` 短，但每个新回合都会更改路由器散列的文本，因此下一回合可以落在与缓存较早回合的实例不同的实例上。仅当请求增长超过 `PrefixLength` 后，会话才会停留在一个实例上。

在这篇文章中，我们将解释 KV 感知路由的工作原理、何时使用它，以及如何在单个模型端点和推理组件端点上启用、调用和验证它。

## KV 感知路由的工作原理

KV 感知路由由三个部分组成：模型容器报告其已缓存的内容，SageMaker AI 为端点保留该状态的托管缓存索引，端点使用该索引为每个请求选择一个实例。

当您使用 `SM_VLLM_KV_EVENTS_CONFIG` 打开事件时，容器每次存储或逐出缓存条目时都会发布 KV 缓存事件，并且 SageMaker AI 使用这些事件来保持索引最新。索引仅保存指针：缓存内容的单向、截断哈希值，每个都映射到保存它的实例或推理组件副本。它从不存储提示、令牌 ID、请求负载或 KV 张量。当请求到达时，端点对提示进行标记并在索引中查找标记。该索引返回在其缓存中保存部分提示的实例或推理组件副本，以及每个实例或推理组件副本保存的数量。例如，如果实例 A 保存会话的缓存开始，则该会话的下一回合将转到 A。由于索引匹配令牌而不是固定数量的字节，因此多回合历史记录可以随着其增长而完全匹配。仅共享部分提示的请求仍会发送到具有最长匹配的实例。

然后，端点通过权衡每个候选者缓存的提示量和繁忙程度来在这些候选者中进行选择。太忙的候选者将被跳过，因此，如果最长匹配的实例很忙，则请求将转到下一个可用的最佳实例。如果没有候选者具有有用的匹配或所有候选者都很忙，则请求将回退到负载感知路由，如路由开销和回退中所述。您不必像配置前缀感知路由那样为此配置并发阈值。该指数还关注船队。当您缩小规模时，已删除实例的条目将被删除。当您横向扩展或更新替换实例时，新实例会从空缓存开始，因此短时间内延迟可能会更高。

## SageMaker AI 上的路由策略

通过此次发布，SageMaker AI 为实时端点提供了四种路由策略。您可以在端点配置的 `RoutingConfig` 中设置每个生产变体的策略。

| **策略** | **它的路线** | **推荐用于** |
| --- | --- | --- |
|随机（默认）|将每个请求发送到随机选择的实例。 |通用工作负载、非 LLM 模型和可互换的请求。 |
|最少未完成的请求 |将每个请求发送到正在进行的请求最少的实例。 |处理时间各不相同并且您希望所有实例保持同样繁忙的工作负载。 |
| PREFIX_AWARE | 前缀_AWARE将共享相同提示前缀（最多 PrefixLength）的请求发送到同一实例。溢出到 ConcurrencyThreshold 的另一个实例。 |在任何支持前缀缓存的服务框架上，LLM 工作负载在请求开始时的固定位置处具有共享文本。 |
| KV_AWARE（新）|根据容器报告的缓存状态，将每个请求发送到保存匹配缓存前缀的实例，权衡匹配长度和负载。回退到负载感知路由。 |支持的容器上的 LLM 工作负载具有多轮对话、频繁的缓存逐出或仅共享其启动部分的请求。 |

### 前缀感知或 KV 感知

两种策略都会将请求发送到可能缓存其前缀的位置。它们的不同之处在于如何知道它在哪里，以及它们需要从容器中获得什么。

|  | **前缀感知路由** | **KV 感知路由** |
| --- | --- | --- |
|缓存位置来源 |从请求前缀推断 |容器报告的缓存状态 |
|每个请求增加了延迟 |第 1 部分中的 1.3–1.9 毫秒 |短提示需要几毫秒，长提示需要更多毫秒，主要用于标记化 |
|匹配|第一个 PrefixLength 字节（调用 API）或字符（OpenAI 兼容 API）|令牌、最长缓存匹配 |
|参数|前缀长度、并发阈值 |不需要 |
|集装箱|任何带有前缀缓存的容器 |受支持的容器，具有前缀缓存和 KV 缓存事件（请参阅要求和限制）|
|请求有效负载 |任何 | OpenAI 兼容的补全或聊天补全格式 |

## 性能

我们通过两种方式测量 KV 感知路由与随机路由：对生产规模的实例进行大规模基准测试，以及您可以在验证 KV 感知路由是否正常工作中进行的较小的、可重现的比较。

### 基准测试结果

在我们对 7 个 `ml.p5.48xlarge` 实例上的 Llama 3.1 70B Instruct 进行的基准测试中，我们对 20 或 100 名模拟用户进行了 30 分钟的测试，进行多轮聊天和文档问答会话，并提示最多约 64,000 个代币。与随机路由相比，在负载下长时间提示的情况下，KV 感知路由将 p50 首个令牌时间 (TTFT) 缩短了高达 97%，并将吞吐量提高了高达 234%。它将 KV 缓存命中率从 3-48% 提高到 80-93%。即使在较低负载下也能获得较长的提示。提示较短时的增益最小，需要保存的预填充较少。结果取决于您的工作量。要测量您自己的流量，请使用验证 KV 感知路由是否正常工作中的检查。

### 路由开销和后备

在路由请求之前，端点会标记提示并在托管缓存索引中查找它。对于短提示，查找需要几毫秒，对于长提示，查找需要更长的时间，主要是为了标记化，但在缓存命中保存时，它仍然很小。对于使用标准选项的纯文本请求，它计算的标记将传递给模型，因此提示不会被标记两次。

如果查找速度很慢，找不到有用的匹配，或者所有匹配实例都很忙，则端点会使用负载感知路由来路由请求，其行为与 `LEAST_OUTSTANDING_REQUESTS` 策略相同。请求仍会得到服务，但没有缓存优势。当端点无法标记请求时，也会发生同样的情况，调用端点中描述的两种错误情况除外。这些回退不会在启动时在 SageMaker AI 控制台或指标中报告，因此请使用验证 KV 感知路由是否正常工作中的检查来确认路由对您的流量有效。

由于提示很短，需要保存的预填充内容较少，因此前缀感知路由就可以满足您的需求。

## 何时使用 KV 感知路由

前缀感知路由不需要对容器进行任何更改，但它无法查看实例实际包含的内容。 KV 感知路由会询问容器它持有什么，这使得它更加精确。当有大量缓存上下文可供重用并且缓存面临压力时，它会得到回报：长提示、高负载以及 KV 缓存的 GPU 内存不足的实例。发生这种情况时，容器会逐出缓存中最近最少使用的部分，包括共享提示和对话历史记录的部分。

例如，支持助理在三个实例上运行，每次对话都以相同的 6,000 个令牌知识库摘录开始。对话 1 在实例 A 上开始，实例 A 缓存摘录。流量增加，A 内存不足，容器驱逐了大部分摘录。实例 B 最近通过同一摘录提供了另一次对话，并且仍然持有其前 4,000 个令牌。当下一轮对话 1 到达时，前缀感知路由再次将其发送给 A，A 重新计算摘录。通过KV感知路由，A的容器已经报告了驱逐，因此索引显示B拥有最长的匹配，并且请求发送到B，B仅重新计算剩余的令牌。在低负载时，A 不会驱逐任何内容，并且两种策略都会将请求发送到 A，并且缓存完好无损。

当请求以固定长度前缀无法捕获的方式重用缓存的上下文时，KV 感知路由最有帮助：

**多轮对话：** 每轮都会发送完整的对话历史记录，因此缓存的前缀会随着每轮而增长。 KV 感知路由匹配整个缓存的历史记录，并将每个对话保留在保存它的实例上。这对于长时间的对话来说最重要。托管缓存索引反映驱逐后，路由器不会继续将会话发送到已删除其缓存的实例。

**具有共享上下文的高吞吐量推理：** RAG 应用程序会预先考虑检索到的文档，并且助手会针对每个请求发送长系统提示。当这些提示很长并且实例面临内存压力时，KV 感知路由就适合。具有稳定的共享前缀和适中的负载，前缀感知路由也适合。将共享内容放在前面并按相同的顺序放置：如果​​相同的文档以不同的顺序出现，提示将不再共享开头，因此它们不匹配。

**前缀长度难以调整的工作负载：** 通过前缀感知路由，您可以选择覆盖共享文本的 `PrefixLength`，而不会分散应保持在一起的请求。 KV 感知路由无需调整前缀长度，因为它与实际缓存的内容相匹配。

如果您的请求在开始时共享稳定的系统提示或文档，您的提示很短，或者负载适中，那么前缀感知路由非常适合，无需更改容器。在这些情况下，实例有足够的 GPU 内存来缓存共享文本​​，因此两种策略都能找到它。如果 KV 感知路由不支持您的容器，则也可以选择前缀感知路由，因为它适用于任何打开了前缀缓存的容器。如果您的请求简短且可互换，或者您的模型不是 LLM，则几乎没有可重用的缓存上下文，因此请使用 `RANDOM` 或 `LEAST_OUTSTANDING_REQUESTS`。

如果您不确定哪个适合，请从前缀感知路由开始，针对 `KV_AWARE` 端点运行您自己的流量，并将时间与第一个令牌、吞吐量和命中率进行比较，如验证 KV 感知路由是否正常工作中所述。

## 要求和限制

在启用 KV 感知路由之前，请检查您的容器、端点和请求是否满足以下要求：

**容器：** 发布时，KV 感知路由支持适用于 SageMaker AI 的 AWS vLLM 深度学习容器：vLLM 0.33.0 或更高版本的映像，或者 Amazon Linux 版本 `server-sagemaker-cuda-v2.8.0` 或更高版本。必须打开前缀缓存（这是默认设置），并且必须使用 `SM_VLLM_KV_EVENTS_CONFIG` 环境变量打开 KV 缓存事件，如如何启用它所示。 SageMaker AI 不会为您设置。

**端点和实例：** GPU 实例类型上的实时单模型端点和推理组件端点，包括动态低秩适应 (LoRA) 适配器。您还可以使用 AWS CloudFormation 配置 KV 感知路由。仅当单个模型端点的至少两个实例或推理组件的至少两个副本（可以位于同一实例上）时，路由才处于活动状态。如果数量较少，您仍然可以设置 `KV_AWARE` 并且端点不会被拒绝，但每个请求都会发送到单个实例或副本。

**请求：** OpenAI 兼容的完成或聊天完成负载，通过 `InvokeEndpoint`、`InvokeEndpointWithResponseStream` 或 SageMaker AI OpenAI 兼容的聊天完成 API 发送。不支持 `InvokeEndpointWithBidirectionalStream`。如果设置 `model` 字段，它必须与 `SM_VLLM_MODEL` 的值匹配。

**SDK 版本：** 用于跟踪 KV 缓存命中率的详细可观测性需要 AWS 命令​​行界面 (AWS CLI) 版本 2.35.6 或更高版本，或者 Boto3 版本 1.43.31 或更高版本。

SageMaker AI 在端点提供流量之前检查这些要求。如果检查失败，请求或部署将失败，并显示一条消息，描述缺少的内容。有关设置、验证行为和配额的完整列表，请参阅 SageMaker AI 文档。

## 如何启用它

您可以在两个位置打开 KV 感知路由：模型和端点配置。 [示例笔记本](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/03-features/kv-aware-routing) 针对单个模型端点和推理组件端点端到端地运行每个步骤。

**1.在模型中开启KV缓存事件 –** 创建模型时，将`SM_VLLM_KV_EVENTS_CONFIG`添加到容器环境中。如果没有它，端点就没有可用于路由的缓存状态。此设置中的端口仅在实例内部使用，因此您不会向网络开放它们。
```
"Environment": {
    "SM_VLLM_MODEL": "<model-id-or-/opt/ml/model>",
    "SM_VLLM_KV_EVENTS_CONFIG": "{\"enable_kv_cache_events\": true, \"publisher\": \"zmq\", \"endpoint\": \"tcp://*:5557\", \"topic\": \"kv-events\", \"replay_endpoint\": \"tcp://*:5658\"}"
}
```
**2.在端点配置中选择 KV 感知路由 –** 在生产变体的 `RoutingConfig` 中将 `RoutingStrategy` 设置为 `KV_AWARE`：
```
"RoutingConfig": {
    "RoutingStrategy": "KV_AWARE"
}
```
如果您的容器映像是为 CUDA 13 构建的，还要将生产变体中的 `InferenceAmiVersion` 设置为支持它的 AMI，例如 `al2023-ami-sagemaker-inference-gpu-4-1`。否则容器可能无法启动。请参阅[推理 GPU 驱动程序](https://docs.aws.amazon.com/sagemaker/latest/dg/inference-gpu-drivers.html)。

检查您的账户对于您选择的实例类型和数量是否有足够的终端节点配额，并根据需要请求增加服务配额。

相同的 `RoutingConfig` 设置适用于推理组件端点，包括动态 LoRA 适配器。对于适配器，KV 感知路由会在已加载适配器的实例中进行选择。

## 调用端点

调用端点的方式没有任何变化。使用 `InvokeEndpoint` 或请求正文中的 `InvokeEndpointWithResponseStream` 和 `"stream": true` 发送聊天完成负载：
```
{"messages": [{"role": "user", "content": "What is your return policy?"}]}
```
您还可以通过 SageMaker AI OpenAI 兼容的聊天完成 API 使用 OpenAI Python 客户端调用端点。 GitHub 上的[将 OpenAI 兼容 API 与 SageMaker AI 结合使用](https://github.com/aws-samples/sagemaker-genai-hosting-examples/blob/main/03-features/openai/sagemaker-inference-openai-api.ipynb) 笔记本展示了如何针对单个模型端点和推理组件。

KV 感知路由不应用第 1 部分中的多租户前缀隔离：它忽略前缀感知 ID 标头和 `prompt_cache_key` 字段。将顶级 `cache_salt` 字段设置为非空值的请求将被拒绝，并显示 400 错误。

KV 感知路由添加了两种错误情况：`model` 字段命名容器不提供的模型的请求失败，并显示 `ModelError`；具有非空 `cache_salt` 的请求被拒绝，并显示 400 错误。推理本身的错误会像以前一样返回，并且 Amazon CloudWatch 中模型容器自己的日志可以帮助您找到原因。端点不会将有关其 KV 感知路由决策的日志传送到您的账户，因此请使用验证 KV 感知路由是否正常工作中的检查（例如每个请求的 `cached_tokens` 和 KV 缓存命中率）来查看路由的行为方式。

## 验证 KV 感知路由是否正常工作

KV 感知路由不会添加自己的指标，因此您需要检查它对模型的影响。有三种方法可以做到这一点。

**检查每个请求的缓存命中率 –** 默认情况下，容器不会报告提示令牌详细信息，因此在模型环境中将 `SM_VLLM_ENABLE_PROMPT_TOKENS_DETAILS` 设置为 `true`。 Each response then includes `usage.prompt_tokens_details.cached_tokens`, the number of prompt tokens that were served from the KV cache.当您发送后续轮次或以与前一个请求相同的方式启动的另一个请求时，非零值表明该请求已到达保留其前缀的实例。

**检查 Amazon CloudWatch 中的模型指标 –** 通过在创建终端节点配置时添加 `--metrics-config '{"EnableDetailedObservability": true}'` 并使用要求和限制中的 SDK 版本来打开详细的可观察性。 SageMaker AI then publishes the model container’s metrics, including the KV cache hit rate and TTFT. Query them as described in [Detailed observability with PromQL](https://docs.aws.amazon.com/sagemaker/latest/dg/monitoring-detailed-observability-promql.html).

![后续请求响应，其中包含 KV 缓存提供的大多数提示令牌，以及 SageMaker AI Insights 仪表板中的 KV 缓存命中率图表](https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/11/17/ML-22381-2-1.png)

**Compare with the strategy you would otherwise use –** For most LLM workloads the real choice is between `KV_AWARE` and `PREFIX_AWARE`, so compare those two, and add a `RANDOM` endpoint as a baseline. Use the same model, instance type, and instance count for each endpoint, and send the same prompts at the same concurrency for the same duration, so that the only difference is the routing strategy. Make sure your test reuses context the way your production traffic does, for example with multi-turn conversations or shared documents. If `KV_AWARE` and `PREFIX_AWARE` perform about the same for your traffic, prefix-aware routing is the simpler choice.

As an example of this comparison, we compared `RANDOM` and `KV_AWARE` on a small endpoint. We sent the same multi-turn workload to two endpoints that differ only in routing strategy. Each endpoint had two `ml.g5.xlarge` instances serving `Qwen3-4B-Instruct-2507` on a supported container. Each run sent 128 requests: 32 simulated users, each asking 4 questions about a document chosen from 12 documents of about 7,400 tokens. Each question resends the conversation so far, so every question after the first can reuse cached context. We ran two pairs of runs, with `RANDOM` first in pair 1 and `KV_AWARE` first in pair 2, and used new documents for each pair so that both endpoints started with empty caches. ## 实用指导

这三种做法可以帮助您在开启 KV 感知路由后保持其有效性。

**监控 KV 缓存命中率 –** 在启动后保持详细的可观察性，并在 SageMaker AI Insights 仪表板中观察 KV 缓存命中率随时间的变化（图 2b），或使用 PromQL 进行查询，如验证 KV 感知路由是否正常工作中所述。

**计划冷启动 –** 具有新上下文的第一个请求（例如新文档或对话的第一轮）在任何实例上都没有缓存任何内容。 KV 感知路由会加速后续请求，而不是第一个请求。

**在扩展和更新期间规划缓存重建 –** 如 KV 感知路由如何工作中所述，新实例从空缓存开始。要缓解延迟增加，请对单个模型端点使用滚动更新或蓝/绿更新，或对推理组件使用 `RollingUpdatePolicy`。

## 结论

KV 感知路由为 SageMaker AI 实时端点提供了第二种将请求发送到缓存提示的位置的方式。它使用模型容器报告的缓存状态，因此当实例在内存压力下驱逐缓存时，它会遵循缓存。 [本系列第 1 部分](https://aws.amazon.com/blogs/machine-learning/reduce-llm-latency-with-prefix-aware-routing-on-amazon-sagemaker-inference/) 中的前缀感知路由仍然是稳定共享提示、简短上下文和中等负载的更简单选择。 SageMaker AI 处理两种策略的端点内部的路由，因此您无需自行构建或运行路由层。您可以使用模型中的一个环境变量和端点配置中的 `"RoutingStrategy": "KV_AWARE"` 将其打开。

KV 感知路由现已在所有支持 SageMaker AI 实时推理的商业 AWS 区域推出，适用于使用受支持容器的终端节点。无需额外付费。 SageMaker AI 为您运行和管理缓存索引，您只需为端点使用的实例付费。 `KV_AWARE` 是现有 `RoutingStrategy` 字段的新值，因此您不需要新的配置对象，旧版本的 AWS CLI 和 Boto3 接受它。首先，请阅读 [文档](https://docs.aws.amazon.com/sagemaker/latest/APIReference/API_ProductionVariantRoutingConfig.html)，在小型端点上运行示例 [笔记本](https://github.com/aws-samples/sagemaker-genai-hosting-examples/tree/main/03-features/kv-aware-routing)，然后在您自己的流量副本上将 `KV_AWARE` 与 `PREFIX_AWARE` 进行比较。
