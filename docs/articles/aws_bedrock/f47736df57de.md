*本文由 Datacor 的 TrackAbout 工程与产品团队贡献撰写。*

对气体和焊接分销商而言，钢瓶和储罐这类资产的租赁计费占总收入的很大份额。然而管理这些资产所需的数据常常锁在彼此割裂的系统里，只有经 IT 才能访问。由此产生的报告对车队利用率、费率表现或收入回收只能给出有限的洞察。

[Datacor](https://www.datacor.com/) 是流程制造、化工分销和工程领域久经验证的软件与专业知识的可靠来源。它的 [TrackAbout](https://www.datacor.com/products/trackabout) 方案帮助工业气体和焊接分销商在整个供应链中跟踪和管理钢瓶与容器资产。TrackAbout 客户合计管理 2,750 万个资产和每月超过 725,000 张账单。在这样的规模上，无法访问的数据会以未计费的租赁天数和从未被捕获的收入形式带来直接代价。

为解决这一点，Datacor 把 [Amazon Quick Sight](https://aws.amazon.com/quicksight/) 集成进 TrackAbout 方案，为它配上交互式仪表盘和一个自然语言搜索栏。Amazon Quick Sight 是 Amazon Quick 内的嵌入式分析能力。结果是一个自助分析体验，业务用户可以在其中探索租赁表现数据、用自然语言提问并做出数据驱动的决策。用户不再需要提交 IT 工单或等待定制报告。

在本文中，我们描述 Datacor 如何解决租赁数据散落在各运营系统、只能经 IT 生成的报告才能访问的挑战。Datacor 构建了一个自动化的跨云数据流水线、嵌入式仪表盘，以及由 Amazon Quick Sight 中生成式商业智能（BI）驱动的自然语言查询。我们逐步讲解业务挑战、架构，以及一路上学到的经验。

## 业务挑战

Datacor 在气体和焊接行业的 TrackAbout 客户把租赁计费当作最关键的收入来源，但多数没有直接分析它的办法。租赁数据活在 TrackAbout 的运营系统内部，但要提取有意义的洞察需要通过 Datacor 的支持团队。客户提交定制 SSRS（SQL Server Reporting Services）报告或原始数据导出的请求，然后等待数天乃至数周才收到。他们得到只回答最初那个问题的静态输出。后续分析又从头开始这一循环。

其代价不止于不便。因为每一份新报告都需要双方都投入技术资源，客户无法迭代：他们无法问“如果我把乙炔费率提高百分之五会怎样？”并在当天得到答案。直接支配收入回收的费率决策，是在不完整信息下做出的。

预构建的报告解决不了这一点。分销商在车队规模、产品组合、地域和计费结构上各不相同，因此没有单一标准报告能满足所有人。人工流程无法扩展到逐个服务每一家分销商。客户系统性地低估了他们已经在生成的数据的用途，把可回收的收入留在了桌上。

Datacor 认识到客户需要一种自助分析的方式，从其租赁数据中获得全部价值。这一方式必须让数据广泛可及，同时容纳气体和焊接分销商多样的分析需求。

> “有意思的部分不是 AI——而是它底下那些不起眼的活儿：跨云摄入、行数校验、一个我们确实可以审计的租户隔离模型。正是这些让我们有资格把一个客户收入数据前的自然语言查询做出来。”Datacor 首席 AI 官 Sundar Kuppuswamy 说。“我们用一件事衡量那份投资的回报：它是否把决策权交回到客户手中。一个分销商问‘如果我把乙炔费率提高百分之五会怎样？’并在同一个会议里得到答案——这就是那个标准。我们对在哪里应用这一能力刻意保守，因为对一个客户收入数据自信却错误的答案，比没有答案更糟。”

## 方案

Datacor 与 [Amazon Web Services](https://aws.amazon.com/) (AWS) 协作，通过构建一个多租户租赁分析方案来应对这一挑战——用 Quick Sight 把交互式仪表盘和一个自然语言搜索栏直接集成进 TrackAbout 应用。该方案给业务用户一条通往租赁表现洞察的自助路径，标准分析无需 IT 参与。

这一体验的核心是 Amazon Quick Sight 中的生成式 BI 能力（Amazon Q in Quick Sight），一个由生成式 AI 驱动的商业智能助手。业务用户可以用大白话就他们的租赁数据提问，并获得由定期刷新的数据集支撑的、准确的、上下文相关的答案。用户可以问这样的问题：

- “显示我上季度按产品类型分的租赁收入”
- “本月哪些客户有最多未归还的钢瓶？”
- “我前 20 个账户按资产类别的平均租赁费率是多少？”
- “有多少钢瓶已出库超过 90 天？”

该方案还提供预构建、上下文感知的仪表盘，呈现关键租赁指标：车队利用率、计费异常摘要、收入回收趋势，以及客户级的资产账龄。这些仪表盘使用一种为业务用户（而非数据分析师）设计的可视化形式。

在分析层之下，是一条自动化的跨云流水线，定期把来自 TrackAbout 第三方云环境的运营数据摄入并转换到 AWS。这条流水线按计划刷新 [Amazon Quick Sight SPICE](https://docs.aws.amazon.com/quicksuite/latest/userguide/spice.html)（Super-fast, Parallel, In-memory Calculation Engine）中的数据集，因此用户看到的仪表盘反映近期的运营数据。

## 架构讲解

Datacor 的 TrackAbout 租赁分析方案使用一个跨数据摄入、转换、存储和展示的分层架构。下图展示从 TrackAbout 运营系统到 TrackAbout 应用内嵌入式 Amazon Quick Sight 仪表盘和自然语言搜索栏的端到端流程。

图 1：Datacor 的 TrackAbout 租赁分析架构

### 跨云数据摄入

TrackAbout 的运营数据位于 Azure SQL 数据库。一条 Azure Data Factory 流水线把源表提取为 Apache Parquet 文件，并把它们流入 [Amazon Simple Storage Service](https://aws.amazon.com/s3/) (Amazon S3)。该流水线支持全量和增量加载，用变更跟踪在增量运行期间只传输被修改的行。新数据到达 Amazon S3 会触发一个基于 [AWS Lambda](https://aws.amazon.com/lambda/)、[AWS Glue](https://aws.amazon.com/glue/) 和 [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 构建的编排层。这一层派发逐表处理作业，并强制有序的、单线程的执行。

AWS Glue 作业把增量更新合并进 Amazon S3 上的 Apache Iceberg 表，而一个 [AWS Step Functions](https://aws.amazon.com/step-functions/) 工作流校验行数并构建最终的 BI 就绪表。每次成功运行后，Datacor 刷新 Amazon Quick Sight SPICE 数据集，使仪表盘反映近期的运营数据。

### 多租户数据隔离

因为 TrackAbout 是一个多租户软件即服务（SaaS）应用，分析层使用 Amazon Quick Sight 行级安全（RLS）。RLS 把每个仪表盘和自然语言查询限定到请求客户的数据。每个 SPICE 数据集有一个关联的 RLS 数据集，把用户身份映射到租户标识符，并在查询时自动应用。这一设计：

- 在新租户上线时无需改动仪表盘定义。
- 扩展到数百个租户而无需复制数据集或仪表盘。
- 一致地应用于嵌入式仪表盘和自然语言查询两者。
- 把访问控制集中到 RLS 配置中，降低维护开销。

### 嵌入式分析

Datacor 用 Amazon Quick Sight Embedding SDK 在 TrackAbout 内部交付分析体验，它在 TrackAbout Web UI 中原生地渲染完全交互式的仪表盘和自然语言搜索栏。当用户打开分析区时，应用服务器调用 Amazon Quick Sight API 生成一个短期有效、经签名的、限定到该用户身份的嵌入 URL。对于自然语言查询，Datacor 配置了把业务术语映射到数据集字段的生成式 BI 主题（topic），使自然语言助手能回答用户实际会问的问题。

## 实现策略

架构确立后，Datacor 开发了一种旨在增量交付价值、降低集成风险、并支持 SaaS 产品多租户要求的实现方法。本节描述塑造方案如何被构建和部署的那些关键决策。

### 分阶段上线

Datacor 分阶段而非以一次大版本发布租赁分析方案。第一阶段始于 2025 年 7 月，聚焦数据流水线，建立跨云摄入、验证数据质量并把历史记录加载进 SPICE。这一阶段与现有 SSRS 报告环境并行运行，因此团队能在停用旧报告前验证输出准确性。

第二阶段在 2025 年 9 月把嵌入式仪表盘体验引入一个 6–7 家客户的试点组。在纳入试点反馈并完成额外验证后，Datacor 于 2025 年 11 月向使用租赁功能的 TrackAbout 客户发布了该方案。发布反响良好，客户渴望从新的视角看到他们的租赁数据。

### 多租户上线自动化

上线一个新客户需要配置一个 Amazon Quick Sight 用户身份、配置 RLS 权限，并把租户与正确的 SPICE 数据集关联。没有自动化，这一流程每个客户可能需要 15–30 分钟。当方案从最初的 50 家客户扩展到更广的 TrackAbout 客户群时，它无法伸缩。

Datacor 在 TrackAbout 内部把这一切自动化。在用户首次访问时，应用从其现有角色创建 Amazon Quick Sight 身份、把租户标识符加入 RLS 配置，并为其订阅层级分派仪表盘集，无需手动设置。

### 自然语言配置

配置自然语言助手需要 Datacor 产品团队与 TrackAbout 领域专家紧密协作。他们共同验证助手理解气体与焊接词汇，如“周转时间”“丢失钢瓶”“滞期费”和“灌装周期”。Datacor 为每个数据集列定义了友好的字段名和同义词、把平均租赁时长和收入回收率这类计算指标配置为预构建的量度，并针对一个真实客户问题库测试主题覆盖。结果是一个讲租赁业务语言的助手，因此用户无需了解底层数据模型就能得到准确答案。

## 仪表盘

仪表盘是为管理气体和焊接运营的业务用户专门打造的。Datacor 不是把原始数据暴露在一个通用工具里，而是围绕一组具体的业务问题设计每个仪表盘，让用户在他们已经在工作的 TrackAbout 应用内部访问。

图 2：Datacor 的 TrackAbout Rental Summary 仪表盘

**Rental Summary** 仪表盘给高管和经理提供对租赁健康度和趋势的可见性。客户可以定制他们的视图，因此一个仪表盘服务于有不同报告需求的分销商。一个关键增强是自然语言查询的集成。业务用户可以用大白话提问并立即收到可视化洞察，在没有 Datacor 支持团队帮助的情况下呈现收入趋势和异常。

图 3：Datacor 的 TrackAbout Rental Revenue Generator 仪表盘

**Rental Revenue Generator** 仪表盘交付假设分析（what-if analysis），让分销商能建模定价场景。客户可以探索像“如果我把乙炔费率提高 5% 会怎样？”这样的问题，并详细看到即时的收入影响，从而他们能在全年主动调整租赁费率，而非一年只被动反应一次。

## 收益与结果

TrackAbout 租赁分析方案于 2025 年 11 月向客户发布。自那以来，Datacor 已为超过 50 家客户组织启用了该功能，有超过 60 名业务用户积极使用这些仪表盘。因为 Quick Sight 身份在首次访问时自动配置，这份采纳没有需要 Datacor 投入任何上线努力。业务用户如今在几分钟内而不是几天内得到答案。以下成果反映了早期采用者的反馈。

### 自助分析采纳

在方案上线之前，绝大多数租赁分析请求都通过 IT。用户如今在 Amazon Quick Sight 里自助做同样的分析，新客户分析上线完全自动化。无需懂 SQL 或与开发者协调就能回答像“我哪些客户现在有最多的钢瓶出库？”这样的问题。用户用自然语言提问并得到由最新刷新的分析数据支撑的答案。

### 收入回收

Rental Summary 和 Rental Revenue Generator 仪表盘帮助用户识别先前不可见的收入回收机会。通过让未归还资产数和计费差异在交互式仪表盘中可见，该方案呈现那些先前在静态报告中丢失、或只在年度审计中才被发现的问题。借助资产账龄视图，用户可以识别那些在客户现场已经数月没有产生租赁收入的容器。然后他们可以发起有针对性的外联，把资产重新投入流转或启动计费纠正。

### 运营效率

在方案之前，租赁分析需要 IT 为每个请求构建定制 SSRS 报告。自动化的跨云流水线彻底缓解了这层依赖。数据如今从运营系统流入 Quick Sight 仪表盘而无需人工干预，用户通过自然语言查询自行探索它。这释放了 IT 团队去专注于更高价值的工作。

### 方案扩展

最初的发布聚焦于租赁分析——一个只被部分客户使用的 TrackAbout 模块。Datacor 此后把同样的架构应用于涉及其整个客户群的分析，构建了三个新的仪表盘套件：Customer Overview、Inventory Insights 和 Process Inconsistencies。这些在 2026 年 5 月发布给一个试点组，正式发布计划于 2026 年 9 月。

这一扩展不需要新基础设施。为每个主题域添加了新数据集，但它们流经同样的跨云流水线、行级安全模型和嵌入方法。把分析延伸到新领域不需要重建基础。客户在没有单独实现的情况下获得了对其运营新领域的可见性，而 Datacor 无需重新设计系统就能扩展该产品。

## 经验教训

构建 TrackAbout Rental Analytics 方案浮现出对任何把嵌入式分析集成进多租户 SaaS 产品的团队都切题的实践教训。

### 从业务问题开始，而非从数据开始

最被广泛采纳的仪表盘都从一个具体的业务问题开始，比如“哪些客户因费率分配不当而最面临收入流失风险？”，然后倒推到所需的数据。同样的原则也适用于自然语言助手：围绕用户实际会问的问题来设计主题覆盖，比映射整个 schema 产出更高的答案准确性。

### 在投资可视化之前先投资数据质量

团队把数据质量工作前置，而非把它当作上线后的清理。AWS Glue 校验层（它检查源到目标的行数并标记差异）对于建立用户信任不可或缺。仪表盘上的数字必须与用户在其运营系统里看到的相符。

### 行级安全设计需要周密的规划

多租户 RLS 很强大，但需要事先规划。让 RLS 模型与一个现有的租户标识符（流水线中已存在的客户端数据库名）对齐，意味着团队能跨数据集统一地应用规则。把它记录为一个正式的数据访问策略，让系统更易于审计和扩展。

### 嵌入式分析改善了用户体验

把仪表盘直接嵌入 TrackAbout 界面而非一个单独的门户，改善了采纳，因为体验感觉是原生的。低的上手摩擦、一个就地的仪表盘选择器，以及相邻的自然语言搜索栏，帮助用户无需培训就能采纳分析。

## 展望未来

租赁分析方案是一段更长远路线图的第一章。计划的增强包括：

- 用于车队规划的预测分析，使用历史条码和射频识别（RFID）扫描数据以及季节性需求模式，按地点预测容器需求。
- 扩展的资产覆盖，把储罐和专用工业设备引入与钢瓶相同的分析框架。
- 覆盖财务分析用例的额外自然语言主题配置，包括按客户细分的利润分析和合同表现跟踪。
- 与客户企业资源规划（ERP）系统集成，以闭合租赁分析发现与财务记录更新之间的环。

自动化的数据流水线、嵌入式分析和自然语言查询的结合，提供了一个 Datacor 可以扩展到新领域、而无需每次重建基础设施的基础。

你也许在考虑一条类似的路径：把分析嵌入一个多租户 SaaS 应用、构建一个跨云数据流水线，或部署生成式 BI 能力。如果是，我们鼓励你探索以下资源。从一个针对你最高优先级业务问题的、聚焦的试点开始，然后从那里扩展。
