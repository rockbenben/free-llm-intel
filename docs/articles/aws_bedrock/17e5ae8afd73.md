# 使用 Amazon Bedrock AgentCore 部署多模态 WhatsApp 点餐助手

本文展示如何部署一个多模态 WhatsApp 点餐助手，它基于 [Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-get-started-toolkit.html) 和 [Amazon Nova 2](https://aws.amazon.com/nova/models/) 构建。许多快餐店把点餐分散在 app、网站、电话线路和柜台之间。每一处都是需要单独构建和运行的系统。每一处也都会割裂顾客的历史记录，使同一个人在每个渠道看起来都像陌生人。顾客早已生活在他们的消息应用里。WhatsApp 覆盖超过 20 亿人。一个能在同一段对话里发消息、发语音或拨打电话的顾客，不需要安装任何东西或登录。

一个 WhatsApp Business 号码承载这个助手。顾客可以给餐厅发消息、发语音，或拨打语音电话。一个 AI agent 端到端完成点餐，从打招呼到确认。三个渠道共享同一个后端和同一份跨渠道 memory。今天发消息、明天打电话的顾客会被识别为同一个人。

该方案使用 [Meta WhatsApp Business Platform](https://developers.facebook.com/docs/whatsapp/cloud-api/) 作为顾客入口。Amazon Bedrock AgentCore 托管这些 agent。[Amazon Nova 2 Lite](https://aws.amazon.com/nova/models/) 通过 [Amazon Bedrock Converse API](https://docs.aws.amazon.com/bedrock/latest/userguide/converse-api.html) 处理文本，[Amazon Nova 2 Sonic](https://aws.amazon.com/ai/generative-ai/nova/speech/) 处理语音消息和通话中的实时语音。这些 agent 通过 [Model Context Protocol (MCP)](https://modelcontextprotocol.io/) 访问餐厅后端。你用 [AWS Cloud Development Kit (AWS CDK)](https://aws.amazon.com/cdk/) 部署整个系统。渠道与点餐逻辑保持分离，因此增删渠道时后端无需改动。

## 方案概览

该设计将三者分开：（1）WhatsApp 层处理对话，（2）三个 agent runtime 为各自渠道运行对话，（3）后端保存菜单、购物车、订单和门店位置。入站流量到达单个 HTTPS webhook，立即以 `200` 确认，然后异步处理，因此没有请求会阻塞响应。这种分离让每一层都能独立部署，也易于理解。

顾客入口是 [Meta WhatsApp Business Platform](https://developers.facebook.com/docs/whatsapp/cloud-api/)。它提供 Cloud API webhook、Messages API、Media API 和 Calling API。这项服务由 Meta 管理。你需要先行设置并连接它，作为前置条件，而不是由本方案来部署。AWS CDK 负责配置 AWS 侧的一切。它会输出你要在 Meta 注册的 webhook URL。

你用 AWS CDK 按依赖顺序将下列 AWS 资源部署为一组 stack，这里按功能分组。

- [Amazon API Gateway](https://aws.amazon.com/api-gateway/) 提供两个 REST API。第一个是区域级 HTTPS webhook，使用 AWS 托管证书。它是唯一的公有端点。第二个是位于点餐逻辑之前的 AWS Identity and Access Management (IAM) 授权的后端 API。
- [AWS Lambda](https://aws.amazon.com/lambda/) 运行 webhook 接收、webhook worker、消息发送和点餐业务逻辑。
- [Amazon Simple Queue Service (Amazon SQS)](https://aws.amazon.com/sqs/) 提供入站队列及死信队列，将快速确认与其余处理解耦。
- [AgentCore runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)，即 Amazon Bedrock AgentCore 的一项能力，托管这三个 agent。每段对话运行在自己的 microVM 中。会话保持隔离。
- Amazon Nova 2 Lite（通过 Converse API 处理文本）和 Amazon Nova 2 Sonic（语音的 speech-to-speech）通过 [Amazon Bedrock](https://aws.amazon.com/bedrock/) 调用。
- [AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html)，即 Amazon Bedrock AgentCore 的一项能力，是一个托管的 MCP server，将后端 REST API 暴露为 MCP tools，agent 按名称调用。
- [AgentCore memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html)，即 Amazon Bedrock AgentCore 的一项能力，是一份共享的跨渠道记录，以哈希后的 customer ID 为键。
- [Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 存储顾客画像、订单、菜单项、购物车和门店位置。它还为 WhatsApp 层保存一张 *last inbound* 窗口表。
- [Amazon Location Service](https://aws.amazon.com/location/) 处理地理编码和最近门店查询。
- [Amazon Kinesis Video Streams (Amazon KVS)](https://aws.amazon.com/kinesis/video-streams/) 提供信令通道，语音通话 runtime 用它来为托管的 Traversal Using Relays around NAT (TURN) 中继生成凭证，该中继承载通话媒体。
- [Amazon Virtual Private Cloud (Amazon VPC)](https://aws.amazon.com/vpc/) 配单个 network address translation (NAT) 网关，是语音通话 runtime 的出站路径。这是唯一需要 VPC 的 runtime。
- [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 保存 Meta Access Token、App Secret 和 Verify Token，它们被创建为空容器，由你带外填充。[AWS Systems Manager Parameter Store](https://aws.amazon.com/systems-manager/) 保存 customer-id pepper。
- [Amazon Elastic Container Registry (Amazon ECR)](https://aws.amazon.com/ecr/)、[AWS CodeBuild](https://aws.amazon.com/codebuild/) 和 [Amazon Simple Storage Service (Amazon S3)](https://aws.amazon.com/s3/) 构建并存储 ARM64 agent 容器镜像。
- [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/) 采集日志和指标，[AWS Key Management Service (AWS KMS)](https://aws.amazon.com/kms/) 加密静态数据。

图 1：AWS 上的多模态 WhatsApp 点餐架构

- A. WhatsApp ingress 与投递：webhook API Gateway、ingest、worker 和 sender Lambda，以及 Amazon SQS 队列。ingest 验证 Meta 签名并将消息入队。worker 处理其余工作。Sender Lambda 投递回复。
- B. Agent runtime：AgentCore runtime 上的三个 agent，各为一个 ARM64 容器，每个渠道一个：文字聊天（Amazon Nova 2 Lite）、语音消息（Amazon Nova 2 Sonic），以及语音通话（基于 Web Real-Time Communication，即 WebRTC 的 Amazon Nova 2 Sonic）。只有语音通话 runtime 运行在 VPC 中。
- C. 人工智能与机器学习 (AI/ML)：通过 Amazon Bedrock 调用的 Amazon Nova 2 Lite 和 Amazon Nova 2 Sonic，以及以哈希后的 `customer_id` 为键的共享 AgentCore memory，用于保持跨渠道连续性。
- D. MCP server（托管）：AgentCore Gateway 将后端 REST API 暴露为可发现的 MCP tools（`GetMenu`、`AddToCart`、`PlaceOrder` 等），每个 runtime 按名称调用。
- E. API 与计算：IAM 授权的后端 API Gateway，以及承载业务逻辑的点餐 Lambda。
- F. 数据存储：Amazon DynamoDB 存储顾客画像、订单、菜单项、购物车和门店位置。
- G. 网络与位置：Amazon Location Service 用于地理编码和最近门店查询，Amazon KVS 托管的 TURN 中继用于语音通话媒体，以及带 NAT 网关的 VPC 作为语音通话 runtime 的出站路径。

两组支撑组件位于请求路径之外。构建流水线（AWS CDK、AWS CodeBuild、Amazon ECR 和 Amazon S3）在部署时运行一次，用于构建并存储 ARM64 agent 镜像。它不在任何请求的路径上。安全与监控（AWS Secrets Manager、AWS Systems Manager Parameter Store、Amazon CloudWatch 和 AWS KMS）在运行时为所有渠道提供支撑。

以下步骤追踪单个请求端到端穿过整个架构的过程：

- Meta 将入站 webhook（文本、语音消息或通话事件）投递到 Webhook API Gateway 和 Webhook Ingest Lambda。
- ingest 验证 Meta 签名，入队到 Amazon SQS，并在 Meta 的时限内返回 `200`。
- Webhook Worker 使用 AWS Systems Manager Parameter Store 中的 pepper 派生一个假名的 `customer_id`。
- worker 从 Meta Media API 获取媒体，并以 `session_id = customer_id` 调用 Amazon Bedrock AgentCore runtime 上对应的 agent（聊天、语音消息或语音通话）。
- runtime 在会话开始时从 AgentCore memory 读取顾客的长期洞察。
- 它通过 Amazon Bedrock 用 Amazon Nova 2 Lite（文本）或 Amazon Nova 2 Sonic（语音）运行对话。
- AgentCore Gateway 是托管的 MCP server。它将后端 REST API 暴露为 MCP tools，agent 按名称调用。
- tools 经后端 API Gateway 路由到 AWS Lambda、Amazon DynamoDB 和 Amazon Location Service。语音通话媒体使用 Amazon KVS TURN 中继（runtime 位于 VPC 中）。
- 回复通过 Sender Lambda（文本）或 worker（语音）发出。事件在会话结束时写回 memory。
- AWS CDK 通过 AWS CodeBuild 构建 ARM64 镜像并推送到 Amazon ECR。Amazon CloudWatch 记录各组件日志，AWS KMS 加密静态数据。

简而言之，每个请求都从 Meta 的 webhook 出发，经 ingest、队列、worker 和 agent runtime 到达后端 tools，再回到 WhatsApp 上的顾客。

## 渠道流程

三个渠道共享同一入口、同一套后端 tools 和同一份 memory。不同的是线路上的媒体类型以及处理它的 runtime。

文本消息：文本消息到达 webhook。worker 派生 `customer_id` 并调用聊天 runtime，后者读取 memory，通过 Converse API 流式调用 Amazon Nova 2 Lite，并按需通过 MCP gateway 调用后端 tools。回复经 Sender Lambda 发出，事件在会话结束时写入 memory。

## 前置条件

本方案有两个方面的前置条件：你的 AWS 账户和你的 Meta WhatsApp 设置。在运行部署之前先完成这两项，因为部署会要求你提供特定的 WhatsApp 值，在这些值就位之前 agent 无法回复。

### AWS 前置条件

- 你需要一个活跃的 AWS 账户，并在部署区域为 Amazon Nova 2 Lite (`amazon.nova-2-lite-v1:0`) 和 Amazon Nova 2 Sonic (`amazon.nova-2-sonic-v1:0`) 启用 Amazon Bedrock 模型访问。你的 IAM 用户或角色必须有权限部署 AWS CDK stack 并创建本方案使用的资源，包括 AgentCore runtime、Gateway 和 memory。在本地机器上安装 `Node.js` 24.x 或更高版本、配置了凭证的 AWS CLI 2.x，以及 git。最后，在目标账户和区域中引导 AWS CDK（`npx cdk bootstrap aws://<ACCOUNT_ID>/<REGION>`）。

agent 容器在 AWS CodeBuild 中基于 ARM64 构建，因此本地无需 Python、Docker 或音频工具链。请选择一个 Amazon Nova 2 Lite、Amazon Nova 2 Sonic 以及 AgentCore runtime、Gateway 和 memory 均可用的 AWS 区域进行部署。美国东部（弗吉尼亚北部）区域 (us-east-1) 是一个不错的起点。

有关各区域的模型可用性，请参阅 [Supported models by AWS Region in Amazon Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/models-regions.html)。

### WhatsApp Business Platform (Meta) 前置条件

WhatsApp 侧在 Meta 控制台中一次性设置，作为前置条件而非本演练中的一个步骤。没有 AWS API 能替你创建 Meta app，因此请先完成它，并在部署前把相关值准备好。做演示时，Meta 沙箱测试号码（无需额外费用）就足够了。你不需要企业验证或生产号码。完整流程见 Meta 文档，链接在下一节给出。

部署前请准备好以下各项。

- 一个添加了 WhatsApp 产品并关联到 Business portfolio 的 Meta Developer App。添加该产品会免费开通一个 WhatsApp Business Account (WABA) 和一个沙箱测试号码。请参阅 [Get started with the Cloud API](https://developers.facebook.com/docs/whatsapp/cloud-api/get-started)。
- App ID 和 App Secret。App Secret 是 Meta 用来对每个 webhook 签名的密钥，webhook Lambda 会重新计算该签名。
- 一个 Access Token。临时令牌可用于快速测试，约 24 小时后过期。若要长期有效，请创建一个 [System User token](https://developers.facebook.com/documentation/business-messaging/whatsapp/access-tokens)，并赋予 `whatsapp_business_messaging` 和 `whatsapp_business_management` 权限范围。
- Business portfolio ID（setup CLI 可自动发现 Phone Number ID 和 WABA ID）。
- 一个由你自行设定的 Verify Token。它是一个难以猜测的字符串，Meta 会在一次性的 [webhook verification handshake](https://developers.facebook.com/docs/graph-api/webhooks/getting-started) 中回显它。
- 如需语音通话，在该号码上启用 [WhatsApp Calling API](https://developers.facebook.com/docs/whatsapp/cloud-api/calling)。

这些值都不要存入源代码仓库。Access Token、App Secret 和 Verify Token 是机密，会在部署时进入 AWS Secrets Manager，而不是写进 CDK 模板。

## 使用 AWS CDK 部署方案

完整方案位于 [GitHub 上的示例仓库](https://github.com/aws-samples/sample-multimodal-whatsapp-restaurant-agent)。该仓库包含三个 agent 容器、AWS CDK 基础设施代码，以及将 WhatsApp webhook 接入你账户的设置脚本。克隆它，运行预检，然后带一个前缀部署。该前缀会加到每个资源名称上，因此你可以在同一账户中多次部署。

```
git clone https://github.com/aws-samples/sample-multimodal-whatsapp-restaurant-agent.git
cd sample-multimodal-whatsapp-restaurant-agent
./scripts/preflight-check.sh
./scripts/deploy-all.sh --deploymentPrefix qsr-wa
```

该脚本按依赖顺序配置每个 stack，并将每个 stack 的输出传给下一个。它先部署共享 VPC。然后部署后端：Amazon DynamoDB、Amazon Location Service、点餐 Lambda 和后端 REST API。接着部署 AgentCore Gateway 和共享的 AgentCore memory。然后用 AWS CodeBuild 构建每个 ARM64 容器，推送到 Amazon ECR，并部署三个 runtime。之后部署 WhatsApp webhook 和订单通知器。再然后填充示例菜单和门店数据。每个容器的首次构建大约需要 8–12 分钟。若想获得带引导的浏览器式体验，可使用 `./scripts/deploy-all.sh --interactive-web-ui`。

WhatsApp 各项值如何传入部署对安全性很重要。CDK 为三个机密创建空的 Secrets Manager 容器。它不把机密作为 CDK 参数接收，否则会将其烧进合成后的模板。你以带外方式填充机密值，而非机密标识符（Phone Number ID、WABA ID、App ID）则作为参数传入。`scripts/whatsapp-setup/` CLI 通过两个流程处理这件事。部署前流程验证 Access Token 并自动发现 WABA 和 Phone Number ID。它会按需生成 Verify Token 并填充机密。部署输出 webhook URL 后，部署后流程在 Meta 中设置回调 URL、Verify Token 和订阅字段。然后它订阅 WABA 并完成验证握手。

```
cd scripts/whatsapp-setup
npm start          # choose "Pre-deploy", then "Post-deploy" after deploy
node whatsapp-setup.mjs --doctor   # read-only end-to-end check
```

webhook 完成订阅且机密填充完毕后，该号码即上线，agent 会在三个渠道上回复。

## 快速确认与异步处理

Meta 期望收到带 `200 OK` 状态码的及时 HTTP 响应。接单、获取媒体、调用 agent 以及转发通话信令，所需时间略超过那个短暂的确认窗口所允许的。因此工作被拆成两部分。Webhook Ingest Lambda 只负责快速、安全的部分：验证签名、入队到 Amazon SQS 并返回 `200`。随后 Webhook Worker Lambda 消费队列并完成其余处理。突发的一批消息变成一个待处理的队列，而公开面仍停留在单一端点。如果 worker 处理某条消息失败，该消息会回到队列重试。几次失败后，消息进入死信队列，供后续检查。

## 三个渠道共享一份 memory

让这一切感觉像一个助手的是共享 memory。单个 AgentCore memory 资源以哈希后的 `customer_id` 为键，三个 runtime 都使用同一个键。每个 runtime 在会话开始时读取顾客的长期洞察，并在结束时写回事件。这些洞察包括过去的订单、喜欢的商品以及顾客此前提到的偏好。因为每个渠道都把同一顾客解析到同一份 memory，今天发消息、明天打电话的顾客会在同一个号码下被识别为同一个人。无需对账独立的跨渠道状态。

## 用 MCP 将 agent 连接到后端 tools

没有任何 AgentCore runtime 直接调用后端 Lambda 函数。AgentCore Gateway 是一个托管的 MCP server。每个 AgentCore runtime 作为 MCP client 通过 HTTPS 连接它，用该 runtime 的 IAM 角色完成认证，并按名称发现 tools。每个 runtime 携带自己的角色，因此 gateway 只授予该 runtime 所需的访问权限。gateway 背后没有单独的 MCP server。gateway 位于后端 REST API 之前，为每个端点生成一个 MCP tool。当 agent 调用 `PlaceOrder` 这样的 tool 时，gateway 将其转换为 REST 请求，由后端 API Gateway 路由到对应的 Lambda。由于 agent 面向的是具名 tools 而非具体函数，你可以在不改动任何 agent 的情况下更换 handler 或新增 tool。三个渠道都针对同一套 tools 和数据下单。定价与合计全部由购物车和订单 tools 负责。agent 不计算这些值，每笔订单都以 `channel = "whatsapp"` 持久化到 Amazon DynamoDB。

## 存储菜单、购物车和订单

Amazon DynamoDB 表覆盖整个工作流。它们是 Customers（用于识别回头客的画像）、Orders（含取餐门店和渠道的历史记录）、Menu（商品、价格和可售状态）、Carts（带 time-to-live 的进行中购物车）以及 Locations（坐标、营业时间和用于合计与推荐的税率）。按需容量随流量伸缩，因此无需管理吞吐量。

## 查找取餐门店

[Amazon Location Service](https://docs.aws.amazon.com/location/latest/developerguide/what-is.html) 帮助顾客少输入内容就能找到取餐点。agent 传入邮政编码或地址，将其地理编码为坐标。然后后端对最近的餐厅排序，返回顾客可直接选择的具体选项。

## 无需登录即可识别顾客

WhatsApp 顾客不登录，因此系统以电话号码作为身份基础。它用 AWS Systems Manager Parameter Store 中的秘密 pepper 对 E.164 号码做哈希，结果成为 `customer_id`（`"wa-" + sha256(E164 || Pepper)[:16]`）。原始号码不存储在 memory 或会话状态中，这有助于满足 personally identifiable information (PII) 要求。如果匹配到已知顾客，agent 会以名字打招呼并回忆其偏好。否则按新顾客下单。发送回复的 runtime 不持有令牌或电话号码。Sender Lambda 在发送时从一张 "last inbound" 窗口表中解析收件人。这是识别，而非身份验证。需要验证的部署可以加一步，例如一次性密码。

## 点餐演练

没有 Web UI 或测试客户端。用安装了 WhatsApp 的手机给该 WhatsApp Business 号码发消息或打电话。下面的例子展示一次典型交互（以 "Agent" 开头的行是助手的回复，方括号内是 tool 调用）。

```
Customer: What's on the menu near 75201?

Agent:    [tools: GeocodeAddress, GetNearestLocations, GetMenu]
          Here's what's available at Amazing Burgers - Dallas:
          - Burger Combo ($8.99)
          - Chicken Tenders ($6.49)
          ...

Customer: A burger combo and a milkshake, please.

Agent:    [tools: AddToCart, GetCart]
          Added to your cart:
          - 1x Burger Combo - $8.99
          - 1x Milkshake - $3.49
          Total: $12.48. Want me to place the order?

Customer: Yes.

Agent:    [tools: PlaceOrder]
          Your order is placed and is being prepared for pickup at
          Amazing Burgers - Dallas. I'll let you know when it's ready.
```

语音消息和语音通话通过 Amazon Nova 2 Sonic 走同样的流程。你说出订单，agent 用语音回复。随着订单推进，订单通知器会主动将状态更新投递回 WhatsApp。你可以在 Amazon CloudWatch Logs 中跟踪对话。

## 成本

你需要为系统使用的 AWS 服务付费，并另行支付 Meta 的 WhatsApp 消息费用。成本主要随对话量以及语音流量占比增长，语音每会话消耗的资源比文本更多。本示例部署了全部三个渠道（文本、语音消息和语音通话），因此将部署限制在特定渠道可以降低基线成本。要获得按区域细分的详细估算，请使用 [AWS Pricing Calculator](https://calculator.aws/) 并参阅 [Meta 的 WhatsApp Business Platform 定价页面](https://business.whatsapp.com/products/platform-pricing)。在 AWS Cost Explorer 中设置预算，以便随流量增长跟踪支出。

## 需要考虑的事项

WhatsApp 还能接收图片和文档。本方案专注于接单，不处理这些附件。如果你的用例需要它们，可以配置后端和聊天 agent 来处理，因为 Amazon Nova 2 Lite 本身已具备多模态能力。agent 可以读取会员卡照片或 PDF 餐饮需求，并将其转换为结构化订单。

这一模式也不仅限于餐厅。核心构件是一个商务号码、若干对话渠道、共享 memory，以及后端之前的 MCP tools。同样的形态适用于零售客服、医疗接诊、现场服务调度等许多领域。你只需调整后端 tools 和数据，渠道层和 agent 层保持不变即可。

对于生产部署，可考虑启用 [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/guardrails/) 以增加内容过滤和事实依据校验。这有助于确保 agent 的回复保持在策略边界内，并减少幻觉输出。

## 清理资源

为避免持续产生费用，完成后请移除资源。清理脚本按相反顺序销毁 stack，每个消费者都先于其生产者被销毁。

```
./scripts/cleanup-all.sh --dry-run   # preview without removing anything
./scripts/cleanup-all.sh             # delete every stack the deploy created
```

清理是不可逆的。它会删除 Amazon DynamoDB 中的订单历史、Parameter Store 中的 pepper、Secrets Manager 中的机密以及 Amazon ECR 中的镜像。请先备份任何想保留的内容。它不会触碰 Meta 侧，因此请在 Meta 控制台中单独取消订阅 webhook 并吊销令牌。完成后，在 [AWS CloudFormation 控制台](https://console.aws.amazon.com/cloudformation/) 中确认 stack 已消失。

## 结论

本文梳理了一个多模态 WhatsApp 点餐助手的架构与部署，它在一个商务号码上通过文本、语音消息和语音通话端到端完成点餐。异步 webhook 快速接收流量，其余工作进入队列。AgentCore runtime 上的三个 runtime 各自处理其渠道。Amazon Nova 2 Lite 和 Amazon Nova 2 Sonic 运行对话。AgentCore Gateway 通过 MCP tools 将 agent 连接到后端。单个 AgentCore memory 为每位顾客提供跨渠道的连续关系。要开始使用，请克隆 [GitHub 上的示例仓库](https://github.com/aws-samples/sample-multimodal-whatsapp-restaurant-agent)，并按你的菜单和门店加以调整。欢迎在评论中分享你如何把这一模式适配到自己的渠道。
