*本文由 Aderant 的 Angela Mapes 和 Adam Walker 联合撰写的客座文章。*

在本文中，我们分享面向法律行业的全球业务管理软件提供商 [Aderant](https://www.aderant.com/) 如何借助 Amazon Bedrock，使用 [Amazon Nova](https://aws.amazon.com/nova/) Lite 构建一套智能工单分类（ticket triage）系统。Aderant 的方案自动化了支持工单分类所需的诸多环节：上下文收集、分类、路由和知识丰富化。

Intelligent Ticket Analyzer 支持 Aderant 的 38 人 SierraOps 团队，该团队在全球 268 个客户环境中运营 Expert Sierra。它在每个工作日按预定的每小时处理周期审阅新提交、尚未分配的工单。它从 Jira、Confluence、[Amazon Athena](https://aws.amazon.com/athena/) 和 Microsoft SharePoint 收集运营上下文，以推荐一个团队分配和解决起点，并自动化已获批准的路由和沟通动作。

在生产运行的头 2.5 周里（2026 年 6 月 30 日至 7 月 17 日），该分析器审阅了 109 个工单，达到了约 96% 的路由准确率。基于团队测量的自动化前分类基线，Aderant 估计该系统每周挽回 8–14 个工程小时，而总运行成本低于每月 30 美元。

此次部署将 [Aderant 早前的 AI 之旅](https://aws.amazon.com/blogs/machine-learning/aderant-transforms-cloud-operations-with-amazon-quick/) 作了延伸：从用 [Amazon Quick](https://aws.amazon.com/quick/) 实现统一搜索与按需调查，迈向由 Amazon Nova 驱动的、预定时的自主运营工作流。

## 挑战：减少运营负担而不失控

Aderant 的 SierraOps 团队平均每周处理 34–40 个支持工单。在自动化之前，每个工单在开始解决工作前都需要 15–25 分钟的人工调查。工程师必须解读请求、定位客户环境细节、确定归属、搜索文档和工单历史，然后再分派或转派工作。

其代价不止于分类时间本身。误路由的工单可能一直滞留在错误的队列里，直到某位工程师发现它；而经验较少的团队成员需要更多时间或资深工程师的指导，才能找到正确的上下文并做出路由决定。

Aderant 需要自动化、可重复的调查工作流，好让工程师专注于复杂排障、平台改进和主动运营，同时为低置信度的决策保留人工审阅。

## 方案：用 Amazon Nova 实现带人工护栏的自主工单分析

Aderant 把 Intelligent Ticket Analyzer 构建为一个由单个 AWS Lambda 函数编排、并由 [Amazon EventBridge](https://aws.amazon.com/eventbridge/) 在工作日每小时触发一次的无服务器工作流。对于 CloudOps 队列中每个未分配的工单，方案遵循五个阶段：

- **识别（Identify）：** 从 Jira 检索未分配的工单。
- **丰富（Enrich）：** 从 Amazon Athena 收集客户元数据、从 Confluence 和 SharePoint 收集相关知识、从 Jira 收集相似的历史已解决工单。
- **分类（Classify）：** 通过 Amazon Bedrock Converse API，把工单和已组装的上下文发送到 Amazon Nova Lite，进行结构化分类并推荐下一步。
- **执行（Act）：** 发布分析和确认信息、重新分派误路由的工单、通知合适的 Microsoft Teams 频道，并对支持可解决的场景应用预定义动作。
- **观察与改进（Observe and improve）：** 将运营指标发布到 [Amazon CloudWatch](https://aws.amazon.com/cloudwatch/)，并把低置信度的分类路由给人工审阅。

当置信度达到配置的阈值时，路由和重派决策可以自主运行。低置信度的工单会被标记为需人工审阅。团队持续监控置信度、误路由和处理延迟，每周审阅路由纠正情况，并利用这些发现来优化 prompt 和路由逻辑。

### 为什么选择 Amazon Nova

Aderant 在通过 Amazon Bedrock 使用真实工单数据评估多个基础模型之后，选择了 Amazon Nova Lite。三个因素推动了这一决定。

**运营针对性：** 在使用相同的工单内容、环境数据、runbook 和解决历史进行比较时，团队发现 Amazon Nova Lite 比其他被评估的模型能提取出更具体的解决步骤，并能更有效地关联过往问题。

**原生 AWS 集成：** Amazon Nova Lite 与 Amazon Bedrock Converse API、AWS Identity and Access Management (IAM) 权限、AWS SDK 以及现有的 AWS 环境集成，减少了对额外外部模型提供方或厂商合同的需求。

**工单规模下的经济性：** 该模型的成本结构使得分析常规工单（而不仅是高优先级案例）变得可行。在初始生产期内，系统总成本保持在每月 30 美元以下，而 Bedrock 推理成本保持在每月 1 美元以下。

Amazon EventBridge 触发 AWS Lambda。该函数从 [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) 检索凭证、通过 Amazon Athena 查询环境元数据，并调用 Jira、Confluence 和 Microsoft Graph API 获取工单和知识上下文。Amazon Bedrock 返回来自 Amazon Nova Lite 的结构化分类输出。[Amazon DynamoDB](https://aws.amazon.com/dynamodb/) 支持跨工单的模式跟踪，而 Jira、Microsoft Teams 和 Confluence 接收由此产生的动作和更新。Amazon CloudWatch 提供运营监控。

**数据边界：** 该分析器使用内部运营工单数据、运营元数据和内部知识源。它不会访问、处理或存储客户案件数据或客户应用程序业务数据。

## 早期运营影响

生产的头 2.5 周为准确率和效率提供了初步观察。路由准确率通过比较分析器的分配与最终解决每个工单的团队来测量。时间节省基于部署前四周的基线——每个工单 15–25 分钟的人工分类。

| **指标** | **早期生产结果** |
| --- | --- |
| 生产测量期 | 2026 年 6 月 30 日–7 月 17 日 |
| 分析的工单数 | 109 |
| 路由准确率 | 约 96%（4 次误路由） |
| 平均工单量 | 每周 34–40 |
| 测量的人工分类基线 | 每个工单 15–25 分钟 |
| 估计挽回的工程时间 | 每周 8–14 小时 |
| 估计挽回的月时间 | 32–56 小时 |
| 系统总成本 | 每月不到 30 美元 |
| Amazon Bedrock 推理成本 | 每月不到 1 美元 |

挽回的产能被重新投向复杂排障、基础设施改进以及需要人类判断的主动性工作。这些发现代表一个早期的生产阶段，应被理解为初步运营结果，而非长期性能基准。

## 三个生产示例

**纠正一个误路由的请求**
一个描述 Azure DevOps 站点 404 错误的工单被投到了 CloudOps 的 AWS 队列。分析器将其归类为 CloudOps 的 Azure 问题，更新了团队字段，并通知请求者已改派。

**加速解决就绪**
对于一条非工作时间的远程访问配置请求，分析器将客户环境数据与一篇相关的 Confluence 文章合并，并把该操作程序作为内部评论发布。工程师第二天上午在 30 分钟内完成了任务，无需额外调查。

**将专业能力延伸到新工程师**
对于一项需要 PowerShell 脚本和服务验证的部署请求，分析器提供了命令、预期输出、排障指导和相关参考。工程师当天解决了该请求，无需升级到资深工程师。

## 把反复出现的问题转化为可复用的知识

该分析器还能在同一软件版本的多个客户之间检测反复出现的问题模式。当达到配置的阈值时，工作流会记录该模式、更新一个专用的 Confluence 跟踪页、监控已解决工单以确认修复，并把未来匹配的工单链接到已记录的解决方案。

这形成了一个持续的知识闭环：识别一个反复出现的模式、记录下来、捕获已确认的解决方案，并让该解决方案可用于未来的工单。这项能力减少了重复的发现工作，帮助运营知识在整个团队间可复用。

## 加速入职与知识获取

在分析器出现之前，陌生的工单类型往往需要人工在 Confluence 里搜索或向资深工程师请教。如今，这个自动化工作流会在工程师开始工作前，把客户环境上下文、匹配到的知识文章和推荐步骤直接放进工单。

这并不取代工程判断。它为新工程师提供了更强的起点，帮助他们在入职更早阶段处理陌生场景，并让经验丰富的工程师能把更多时间花在复杂工作上。

## 从概念到生产五周

Aderant 采用渐进式验证，而非直接跳到自主动作：

- 基于规则的起步：一条 Jira 自动化规则确立了最初的分类路由概念，但无法纳入 AWS 上下文、工单历史或模型推理。
- AI 辅助验证：现有的 Amazon Quick CloudOps Helper 智能体证明运营数据可以支持有用的路由和解决方案推荐。
- 生产构建：团队用 AWS Lambda 和 Amazon Nova Lite 实现了该工作流。Kiro 支持了集成脚手架、架构验证和测试生成。
- 仅监控测试：分析器在约两周里针对实时工单运行，同时其分类结果与人工决策做对比，并据此优化 prompt 和路由逻辑。
- 生产上线：该方案于 2026 年 6 月 30 日正式上线，距最初概念五周。

## 展望未来

**更深入的客户历史分析：** 随时间连接相关工单，以提供更完整的、正在进行的客户工作视图。

**改进的知识匹配：** 当工单与文档术语不一致时，评估 Amazon Bedrock Knowledge Bases 做语义匹配。

**分层的 AI 支持：** 继续用该分析器做定时分类，同时保留 CloudOps Helper 机器人以进行更深入、按需的调查和追问。

## 结论

Aderant 的 Intelligent Ticket Analyzer 展示了运营团队如何从 AI 辅助搜索走向受治理的自动化。在生产的头 2.5 周里，该系统审阅了 109 个工单，达到约 96% 的路由准确率，估计每周挽回 8–14 个工程小时，而运行成本低于每月 30 美元。

核心的设计选择不在于让 AI 取代工程师或独立解决每一个问题。相反，Aderant 把 Amazon Nova Lite 应用于那些拖延解决的、可重复的调查工作上：组装上下文、识别相关知识、检测模式，并带着一个有用的起点来路由工作。对于低置信度的决策，人工审阅仍保留在控制模型之中。

通过结合自主分类、运营护栏和可复用的知识闭环，Aderant 为减少运营负担、把工程产能导向更高价值的工作打造了一个可扩展的基础。
