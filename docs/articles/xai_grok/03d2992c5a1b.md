# SpaceXAI 如何用 Grok Bot 扩展客户支持

我们围绕 Grok Bot 重构了 SpaceXAI 与 Cursor 合并后的支持体系，在产品组合大幅扩张的同时没有增加人手。

8 月 14 日 Cursor 成为 SpaceXAI 的一部分后，我们的两支客户支持团队开始围绕一个远为更广的产品组合合流。

与此同时，我们正在准备发布 [Grok Bot](https://x.ai/bot)——一个可以交付真实工作的 AI 队友。我们预期该产品会快速增长，带来又一波用户和支持需求。

我们决定用 Grok Bot 本身来帮助满足这一需求，把它部署到支持体系的各个环节。它登录了我们团队使用的同一套工具，其角色从解决单个工单，到帮助我们理解并改进整个支持体系。

合并后的新团队支持工单量增长了 175%，但得益于 Grok Bot，我们没有招聘任何新人。否则我们可能需要新增 200 人。

我们的成本也只有通常水平的一小部分。传统 AI 客服工具按每次解决收取 $1 到 $4 的固定费用。用 Grok Bot，你只需为实际用量付费，而这些用量已包含在你的套餐里。稍加优化后，我们把单个工单的解决成本降到了低至 $0.20 到 $0.30。

## [打好基础](https://x.ai/news/grok-bot-customer-support#establishing-the-foundation)

在为 Grok Bot 做配置时，我们采取了"crawl, walk, run"（先爬、再走、后跑）的方式。起初我们把它接入几个核心系统，包括用于工单的 Plain 和用于问题跟踪的 Linear。然后让它表现得像工单负责人，但限制它只能写内部备注，并且每次写入操作都需要人工批准。这让我们能检验它是否理解了每个问题、是否提出了正确的下一步，同时不影响客户体验。

随着结果越来越可靠，我们为每次运行加上了轨迹记录与评估。出了问题时，我们能看到 Grok Bot 在哪里跑偏、做出调整、再试一次。Grok Bot 自己也能分析这些运行。这个反馈回路让我们既能快速推进，又让整个过程保持受控。

基础打牢之后，我们从复杂度最低的工单开始让 Grok Bot 上岗。第一天，我们人工复核它对问题的解读和拟议回复是否准确、语气是否合适、是否遵循了我们的指令。到当天结束，我们已有足够信心让它开始直接回复客户。此后，我们逐步扩大它能处理的工单范围。

## [从接入到解决](https://x.ai/news/grok-bot-customer-support#from-intake-to-resolution)

若以端到端解决一个工单所需的时间来看，大头都花在发现、排查和故障诊断上。我们从工单进入系统的那一刻起，就把 Grok Bot 作为预排查步骤应用到每个工单。这可能成本不菲，因此我们梳理了常见工单、给常见问题分类，以减少需要花费的 tokens。当一个简单的帮助中心查询就能解决问题时，我们也不会耗尽大量排查算力。

每当遇到已知问题（它连接着我们的 Linear 实例），或后端出现常见错误（它连着 Datadog），我们都训练了 Grok Bot：要么追加到现有 issue，要么新建一个 issue。Grok Bot 还会用视频复现问题，帮助工程团队快速解决。

当然，我们还要确保客户收到我们清晰的答复。我们用超过一百万次客户交互训练了 Grok Bot，让它直接从我们人类客服那里学会了语气和风格。Grok Bot 被训练为不仅回复，而且始终推动工单走向解决。它通过提出相关问题来实现这一点（例如，答案已在日志里的问题它不会重复问）。

Grok Bot 还能代表客户采取行动。例如，我们为它提供了明确的退款指引，99% 的退款请求无需人工介入即可解决。

## [实时管理队列](https://x.ai/news/grok-bot-customer-support#managing-the-queue-in-real-time)

解决单个工单只是工作的一部分，我们还需要理解整个队列中正在发生什么。Grok Bot 持续盯住进线量，并根据哪些需要关注来调整队列：重新排定工单优先级、按紧急程度重新分配负责人，并在快要突破响应时限 SLA 时向组织发出警报。

Grok Bot 还会跨工单寻找模式。当某个问题的工单量达到设定阈值，它可以自动宣布一次事故（incident）。它监控 X 上情绪的变化和同一问题的反复报告，让我们看到那些没有直接联系客服的客户。这些信号共同帮助我们及早发现苗头问题。

在我们目前的规模下，原始的进线量警报会造成大量噪音。Grok Bot 会评估某个激增是否反映真实的支持问题，并在通知团队前先开始调查。这让我们在保全团队时间与精力的同时，对需要行动的事项获得更多上下文。

## [持续改进我们的客户支持体系](https://x.ai/news/grok-bot-customer-support#continually-improving-our-customer-support-system)

随着 Grok Bot 承担更多客户支持工作，它也给了我们改进支持体系本身的新途径。它会复盘人类和 Bots 处理的客户交互，就哪里可以改进给出具体反馈，并为个别团队成员和 Bots 发掘辅导机会。

每周，Grok Bot 会给管理团队发送一份摘要，说明我们的 AI 回复在哪里做得不够好。有时答案是需要更多训练或更好的文档；有时摘要会确认我们设置的护栏正在起作用。这让我们对质量保持定期更新的视野，帮助我们及早处理成型的模式。

随着越来越多用户向 Grok 寻求支持，我们的帮助中心日益成为其答案的原始素材。为保持答案准确，Grok Bot 会审阅我们代码库的变更，并建议对帮助中心做相应更新。

我们如今已走到 Grok Bots 可以辅导其他 Grok Bots 的阶段。它们发现知识体系的缺口、补上缺口，并把所学反馈回系统。我们正在整个产品组合中扩展这个循环，让它覆盖每一个产品触点。

## [把客户支持数据变成决策](https://x.ai/news/grok-bot-customer-support#turning-customer-support-data-into-decisions)

Grok Bot 已成为我们默认的数据分析师，把它在客户支持中看到的一切转化为发到我们 Slack 频道的日报。当它察觉糟糕客户体验的早期征兆，就会标记情况，让团队还来得及扭转结果。

一个例子：当工单在客户与我们团队成员（人类或 Bot）之间来回超过三次，Grok Bot 就会把该交互标记给管理层审阅，给领导层一个介入并挽回体验的机会。这类交互也有助于训练 Grok Bot——随着它学会哪些信号对团队有用，报告会随时间越来越切题。

同样的分析也帮助我们提升产品质量。Grok Bot 每天从客户支持工单中综合超过 20,000 条产品反馈，把它们整理成清晰的主题带给工程团队。这让产品团队能更宏观地看到客户在哪里挣扎、产品哪里需要打磨。

## [Grok Bot 如何改变一支客户支持团队](https://x.ai/news/grok-bot-customer-support#how-grok-bot-changes-a-customer-support-team)

Grok Bot 仍是一种新的工作方式，但它已经改变了我们团队的运转方式。我们不再把一天的大部分时间耗在重复性支持工作上，而是专注于设定护栏、处理需要判断力的案例、决定整个体系该如何改进。这让工作更有吸引力，也让人们有更多空间把经验用在更难的题目上。

我们仍在学习这种模式的可能性。随着客户支持角色的持续演变，我们会不断分享我们的发现。
