# 在 Xeon 上用 Optimum Intel 加速 StarCoder：Q8/Q4 与投机解码

## 引言

近来，代码生成模型变得非常流行，尤其是 BigCode 的 [StarCoder](https://huggingface.co/blog/starcoder) 和 Meta AI 的 [Code Llama](https://ai.meta.com/blog/code-llama-large-language-model-coding) 这类最先进开源模型的发布。越来越多的工作致力于让大语言模型（LLM）更优化、更易用。在这篇博客中，我们很高兴分享在 Intel Xeon 上对流行代码生成 LLM StarCoder 做优化的最新成果。

StarCoder 模型是专为协助用户完成各类编码任务而设计的前沿 LLM，比如代码补全、bug 修复、代码摘要，甚至从自然语言描述生成代码片段。StarCoder 模型是 StarCoder 家族的一员，家族中还有 StarCoderBase 变体。这些代码大语言模型（Code LLM）在来自 GitHub 的宽松许可数据上训练，覆盖 80 多种编程语言，还包括 Git commit、GitHub issue 和 Jupyter notebook。在这项工作中，我们展示了通过在 Intel 第四代 Xeon 上将 8bit 和 4bit 量化与[辅助生成（assisted generation）](https://huggingface.co/blog/assisted-generation)相结合，实现 StarCoder-15B 模型超过 7 倍的推理加速。

可以试试我们在 Hugging Face Spaces 上的 [demo](https://huggingface.co/spaces/Intel/intel-starcoder-playground)，它跑在一颗第四代 Intel Xeon 可扩展处理器上。

## 第 1 步：基线与评测

我们用 StarCoder（15B）配合 PyTorch 和 [Intel Extension for PyTorch](https://github.com/intel/intel-extension-for-pytorch)（IPEX）建立基线。有不少数据集专为评估自动代码补全质量而设计。本工作使用流行的 [HumanEval](https://huggingface.co/datasets/openai_humaneval) 数据集来评估模型的质量与性能。HumanEval 包含 164 道编程题，形式为"函数签名 + docstring"，由模型补全函数代码。提示词平均长度为 139。我们用 Bigcode Evaluation Harness 衡量质量，报告 pass@1 指标。模型性能的衡量方式是在 HumanEval 测试集上测量首 token 时间（TTFT）与每输出 token 时间（TPOT），并报告平均 TTFT 和 TPOT。第四代 Intel Xeon 处理器内置了被称为 Intel® Advanced Matrix Extensions（Intel® AMX）的 AI 加速能力。具体来说，每个核心都内置 [BFloat16](https://en.wikipedia.org/wiki/Bfloat16_floating-point_format)（BF16）和 Int8 GEMM 加速器，可加速深度学习训练与推理负载。AMX 加速推理通过 PyTorch 2.0 和 [Intel Extension for PyTorch](https://github.com/intel/intel-extension-for-pytorch)（IPEX）引入，同时 IPEX 还为 LLM 推理中常用的各类算子提供其他优化（如 layer normalization、SoftMax、scaled dot product）。作为起点，我们使用 PyTorch 和 IPEX 开箱即用的优化，以 BF16 模型执行推理。图 1 展示了基线模型的延迟，表 1 和表 2 也给出了其延迟与精度。

### LLM 量化

LLM 的文本生成是自回归方式进行的，因此每生成一个新 token，都要把整个模型从内存加载到 CPU。我们发现，片外内存（DRAM）与 CPU 之间的带宽是 token 生成过程中最大的瓶颈。量化是缓解该问题的常用手段：它缩小模型体积，从而缩短模型权重的加载时间。

本工作聚焦两种量化：

- 仅权重量化（Weight Only Quantization，WOQ）——只量化模型权重、不量化激活，计算在高精度（如 BF16）下进行，因此需要反量化。
- 静态量化（Static Quantization，SQ）——权重和激活都量化。该量化过程通过校准步骤预先计算量化参数，使计算可以在更低精度（如 INT8）下执行。图 2 展示了 INT8 静态量化的计算流程。

## 第 2 步：8bit 量化（INT8）

[SmoothQuant](https://huggingface.co/blog/generative-ai-models-on-intel-cpu) 是一种训练后量化算法，用于把 LLM 量化为 INT8 并将精度损失降到最低。静态量化方法在 LLM 上被证明表现不佳，原因是激活的某些通道中存在大幅值离群点。由于激活按 token 逐个量化，静态量化要么截断离群值，要么让低幅值激活下溢。SmoothQuant 通过引入量化前阶段解决了这个问题：对激活和权重同时施加额外的平滑缩放因子，从而平滑激活中的离群点，并确保量化级别得到更好的利用。

![INT8 quantization](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/174_intel_quantization_starcoder/int8_diagram.png)
 *图 2. INT8 静态量化的计算示意图。*

我们借助 IPEX 对 StarCoder 模型应用 SmoothQuant，用 [MBPP](https://huggingface.co/datasets/nuprl/MultiPL-E) 数据集的 test 划分作为校准数据集，得到了 Q8-StarCoder。评测显示，Q8-StarCoder 相对基线没有精度损失（事实上还略有提升）。性能方面，Q8-StarCoder 在 TTFT 上取得 **约 2.19 倍** 加速，TPOT 上 **约 2.20 倍** 加速。图 3 展示了 Q8-StarCoder 与 BF16 基线模型的延迟（TPOT）对比。

![INT8 latency](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/174_intel_quantization_starcoder/latency_int8_model.png)
 *图 3. 8-bit 量化模型的延迟加速。*

## 第 3 步：4bit 量化（INT4）

虽然 INT8 相比 BF16 把模型体积缩小了 2 倍（每权重 8 bit 对 16 bit），但内存带宽依然是最大瓶颈。为了进一步缩短模型从内存加载的时间，我们用 WOQ 把模型权重量化到 4 bit。注意，4bit WOQ 需要在计算前反量化到 16bit（图 4），这意味着存在计算开销。

![INT4 quantization](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/174_intel_quantization_starcoder/int4_diagram.png)
 *图 4. INT4 量化模型的计算示意图。*

张量级（tensor-wise）非对称最近舍入（RTN）量化是一种基础的 WOQ 技术，它面临挑战、常常导致精度下降；不过[文献](https://arxiv.org/pdf/2206.01861.pdf)（Zhewei Yao, 2022）表明，对模型权重做分组（groupwise）量化有助于保持精度。为避免精度退化，我们的 4-bit 量化沿输入通道按连续数值分组（如 128 个一组），缩放因子按组计算。我们发现分组 4bit RTN 足以保持 StarCoder 在 HumanEval 数据集上的精度。4bit 模型相对 BF16 基线在 TPOT 上取得 **3.35 倍** 加速（图 5），但由于计算前 4bit 到 16bit 的反量化开销，TTFT 出现了预期的 0.84 倍减速（表 1）。

![INT4 latency](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/174_intel_quantization_starcoder/latency_int4_model.png)
 *图 5. 4-bit 量化模型的延迟加速。*

## 首个 token 与后续 token 的瓶颈差异

生成第一个 token 这一步要并行处理整个输入提示词，当提示词很长时对计算资源的需求很高，此时计算成为瓶颈。因此，这一步从 BF16 切换到 INT8 精度会带来相对基线的性能提升（也优于带反量化计算开销的 4bit WOQ）。但从第二步开始，系统以自回归方式逐个生成其余 token，每生成一个新 token 都要反复把模型从内存加载进来。此时瓶颈变成内存带宽，而非计算量（FLOPS），所以 INT4 优于 INT8 和 BF16。

## 第 4 步：辅助生成（AG）

另一种降低推理高延迟、缓解内存带宽瓶颈的方法是[辅助生成](https://huggingface.co/blog/assisted-generation)（AG），它是[投机解码（speculative decoding）](https://arxiv.org/pdf/2211.17192.pdf)的一种实用实现。AG 通过更好地平衡内存与计算操作来缓解该问题，其前提是：一个更小更快的辅助草稿模型生成的 token 往往与大目标模型相同。

AG 使用一个小的快速草稿模型贪心地生成 K 个候选 token。这些输出 token 生成得快得多，但其中一些可能与原目标模型的输出 token 不一致。于是下一步，目标模型在一次前向传播中并行校验全部 K 个候选 token 的有效性。这个过程加速了解码，因为并行解码 K 个 token 的延迟小于自回归逐个生成 K 个 token。

为加速 StarCoder，我们使用 [bigcode/tiny_starcoder_py](https://huggingface.co/bigcode/tiny_starcoder_py) 作为草稿模型。该模型与 StarCoder 架构相似，但只有 1.64 亿参数——比 StarCoder **小约 95 倍**，因而快得多。为了获得更大加速，我们在量化目标模型的同时也对草稿模型做量化。我们分别考虑草稿模型和目标模型都用 8bit SmoothQuant 与 4bit WOQ。评估两种组合后，我们发现两个模型都用 8bit SmoothQuant 效果最好：TPOT 加速 **约 7.30 倍**（图 6）。

这些量化选择有以下观察作为依据：

- 草稿模型量化：当用 8bit 量化、1.64 亿参数的 StarCoder 作为草稿模型时，模型基本能装进 CPU 缓存。于是内存带宽瓶颈得到缓解，因为生成 token 时无需每 token 都从片外内存重复读取目标模型。这种情况下不存在内存瓶颈，所以我们看到 StarCoder-164M 量化到 8bit 比量化到 4bit WOQ 加速更好。需要说明：4bit WOQ 在内存带宽是瓶颈时更有优势（内存占用更小），但 4bit 也有计算开销——计算前必须做 4bit 到 16bit 的反量化。
- 目标模型量化：在辅助生成中，目标模型要处理草稿模型生成的 K 个 token 序列。让 K 个 token 一次性（并行）通过目标模型，而不是按"标准"的自回归顺序逐个处理，会把瓶颈从内存带宽转移到计算。因此我们观察到，使用 8bit 量化的目标模型比 4bit 模型带来更高加速——因为后者需要对每个值做 4bit 到 16bit 反量化，额外计算开销更大。

要加载这些模型并运行推理，只需把 `AutoModelForXxx` 类替换成 [`optimum-intel`](https://github.com/huggingface/optimum-intel) 中对应的 `IPEXModelForXxx` 类。

开始前，请确保安装了所有必需的库：

```
pip install --upgrade-strategy eager optimum[ipex]
```

```
- from transformers import AutoModelForCausalLM
+ from optimum.intel import IPEXModelForCausalLM
  from transformers import AutoTokenizer, pipeline

- model = AutoModelForCausalLM.from_pretrained(model_id)
+ model = IPEXModelForCausalLM.from_pretrained(model_id)
  tokenizer = AutoTokenizer.from_pretrained(model_id)
  pipe = pipeline("text-generation", model=model, tokenizer=tokenizer)
  results = pipe("He's a dreadful magician and")
```
