# Mini-R1：用 RL 教程复现 DeepSeek R1 的"顿悟时刻"

*本文作者是 [Philipp Schmid](https://huggingface.co/philschmid)，最初发表于 [philschmid.de](https://www.philschmid.de/mini-deepseek-r1)，代码在[这里](https://github.com/philschmid/deep-learning-pytorch-huggingface/blob/main/training/mini-deepseek-r1-aha-grpo.ipynb)。*

Deepseek R1 的发布震动了业界。为什么？因为 DeepSeek-R1 是一个在复杂推理任务上可与 OpenAI o1 匹敌的开放模型，使用了组相对策略优化（GRPO）和以 RL 为核心的多阶段训练方法。他们不仅发布了模型，还发布了一篇介绍做法的论文。

在[论文](https://arxiv.org/abs/2501.12948)中，他们描述了用纯 RL 训练模型时出现的一个"顿悟时刻（aha moment）"。在这个阶段，DeepSeek-R1-Zero（DeepSeek-R1 的首个测试版）在没有人类反馈、也没有任何教它这么做的数据的情况下，学会了对一个问题分配更多思考时间——重新评估自己最初的解法。他们这样描述这个"顿悟时刻"：

> 这种行为不仅见证了模型不断成长的推理能力，也是强化学习如何带来出乎意料且精妙结果的一个迷人范例。

在这篇博文中，我们想用组相对策略优化（GRPO）和 Countdown 游戏复现 DeepSeek-R1 小小的"顿悟时刻"。我们用强化学习训练一个开放模型，让它凭自己学会自我验证与搜索，去解 Countdown 游戏。Countdown 是一个数字谜题：玩家用一组随机抽到的数字和基础四则运算（+、-、×、÷），凑出目标数字或尽可能接近它。

```
Target Number: 952
Available Numbers: 25, 50, 75, 100, 3, 6

(100 × (3 × 3)) + (50 + 6 / 3) = 952
```

博文聚焦于使用 Deepspeed 和 vLLM 的分布式训练，在 4 块 NVIDIA H100 GPU 上运行。

- [搭建开发环境](https://huggingface.co/blog/open-r1/mini-r1-contdown-game#1-setup-the-development-environment)
- [使用 Deepspeed 与 vLLM 的 GRPO 分布式训练示例](https://huggingface.co/blog/open-r1/mini-r1-contdown-game#2-distributed-training-example-for-grpo-using-deepspeed-and-vllm)
- [结果与训练观察](https://huggingface.co/blog/open-r1/mini-r1-contdown-game#3-results-and-training-observations)

*注：本文受 [Jiayi Pan](https://x.com/jiayi_pirate/status/1882839370505621655) 启发，他最初探索了这个想法并用一个小模型验证了可行性。*

正式开始前，先看看 [组相对策略优化（GRPO）](https://arxiv.org/abs/2402.03300)，理解它是怎么工作的。

**组相对策略优化（GRPO）**

组相对策略优化（GRPO）是一种提升 LLM 推理能力的强化学习算法，出自 [DeepSeekMath](https://arxiv.org/abs/2402.03300) 论文，用在数学推理场景。GRPO 对传统近端策略优化（PPO）的修改在于去掉了价值函数模型的需求，改用组内得分估计基线，从而降低内存占用和计算开销。GRPO 现在也被 Qwen 团队使用，既可以配合规则/二值奖励，也可以用通用奖励模型来提升模型 helpfulness。

- **采样**：用当前策略为每个提示词生成多个输出
- **奖励打分**：每个生成用奖励函数打分，可以是基于规则或基于结果的
- **优势计算**：以生成输出的平均奖励作为基线，组内每个解的优势相对该基线计算，奖励在组内归一化。
- **策略优化**：策略尝试最大化 GRPO 目标，其中包含算出的优势项和一个 KL 散度项。这与 PPO 把 KL 项放进奖励里的实现方式不同。

## 2. 使用 Deepspeed 与 vLLM 的 GRPO 分布式训练示例

我们将使用 [Jiayi-Pan/Countdown-Tasks-3to4](https://huggingface.co/datasets/Jiayi-Pan/Countdown-Tasks-3to4) 数据集，其中包含 3 到 4 个数字的题目及解法。模型用 [Qwen/Qwen2.5-3B-Instruct](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct)，一个 3B 参数的指令微调模型。它本来就能遵循指令，这让"顿悟时刻"更容易展示。[Jiayi-Pan](https://x.com/jiayi_pirate/status/1882839487417561307) 的探索表明，模型需要达到一定质量（参数 > 1.5B）才能学会推理过程。

TRL 通过专门的 [GRPOTrainer](https://huggingface.co/docs/trl/main/en/grpo_trainer) 支持组相对策略优化（GRPO），用于从偏好数据对齐 LLM，方法出自 [DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models](https://arxiv.org/abs/2402.03300)。`GRPOTrainer` 是 `transformers` 库中 `Trainer` 的子类，支持同样的全部功能，包括日志、checkpoint、分布式训练和参数高效微调（PEFT）。

`GRPOTrainer` 支持通用结果奖励模型（ORM）和自定义奖励函数，可以用来实现基于规则的奖励模型。Deepseek R1 论文中实现了基于规则的奖励模型来验证生成解法的正确性。我们的示例也采用类似做法，创建 2 个奖励函数：

- **格式奖励（Format Reward）**：检查生成格式是否正确：`<think> [thinking] </think><answer> [answer] </answer>`
- **正确性奖励（Accuracy Reward）**：从 `<answer>` 标签中提取算式，对照目标值求值，并检查每个数字是否恰好使用一次。

*注：本例中正确的 `<answer>` 包含算式，例如 `<answer> 55 + 36 - 7 - 19 </answer>`*

Hugging Face TRL 增加了对 Deepspeed 分布式训练以及用 vLLM 加速生成的支持。我准备了一个 [run_r1_grpo.py](https://github.com/philschmid/deep-learning-pytorch-huggingface/blob/main/training/scripts/run_r1_grpo.py) 脚本和一个 [receipes/grpo-qwen-2.5-3b-deepseek-r1-countdown.yaml](https://github.com/philschmid/deep-learning-pytorch-huggingface/blob/main/training/receipes/grpo-qwen-2.5-3b-deepseek-r1-countdown.yaml) 配置文件来运行训练。

这套配置在带 4× H100 80GB 的节点上经过测试和验证，单个 step 约需 45-60 秒，因为我们用 vLLM 生成、DeepSpeed 分布式训练。所以务必把 `num_processes` 正确设置为你拥有的 GPU 数减 1——最后一块留给 vLLM 做生成。如果你用更多 GPU，需要把配置文件里的 `vllm_device` 改成最后一个索引，例如有 8 块 GPU 时设 `vllm_device=7`、`num_processes` 设为 7。

运行训练的命令：

```
accelerate launch --num_processes 3 --config_file configs/accelerate_configs/deepspeed_zero3.yaml scripts/run_r1_grpo.py --config receipes/grpo-qwen-2.5-3b-deepseek-r1-countdown.yaml
```

在优化后的分布式训练下，4× H100 80GB 上每个样本 8 次生成的单个 step 约 45-60 秒。完整训练 450 步约需 6 小时。

## 3. 结果与训练观察

脚本会把随机补全保存到 `completion_samples` 文件夹，你可以用它检查模型的进展。里面有 `completion_samples.txt` 和 `success_completion_samples.txt`：前者包含所有补全，后者是正确解出算式的补全。下面是关于性能随时间变化的有趣训练观察，以及 Tensorboard 日志和成功的推理样本。

每 25 步一个 checkpoint 的模型在 [philschmid/qwen-2.5-3b-r1-countdown](https://huggingface.co/philschmid/qwen-2.5-3b-r1-countdown)。

### 超参数

我最初按 [DeepSeekMath](https://arxiv.org/abs/2402.03300) 论文的超参数开始实验：学习率 1e-6、beta（KL 系数）0.04，但约 150 步后训练变得不稳定。我做了几次小规模消融，依据 [OpenRLHF](https://hijkzzz.notion.site/unraveling-rlhf-and-its-variants-engineering-insights#147d9a33ecc9806090f3d5c749d31f05) 的一个测试，把学习率降到 5e-7、beta 降到 0.001。我没能测试把 `num_generations` 从 8 增加到 64 会怎样影响训练（64 是 DeepSeekMath 论文使用的生成数）。其余参数见 [grpo-qwen-2.5-3b-deepseek-r1-countdown.yaml](https://github.com/philschmid/deep-learning-pytorch-huggingface/blob/main/training/receipes/grpo-qwen-2.5-3b-deepseek-r1-countdown.yaml) 配置文件。

### 训练观察：

- 约 50 步时，模型学会了正确格式 `<think>...</think>\n<answer>...</answer>`。
- 100 步时，解出算式的成功率约 25%。模型开始用文字"推理"，样例见下文。
- 200 步时，性能收敛明显变慢，成功率约 40%。模型开始学习一种新"格式"，用类似程序化的方式解题：尝试不同组合并检查结果，见"200 到 450 步之间的成功推理样本"。
- 450 步时，解出算式的成功率达到 50%。性能仍在缓慢提升，模型保持着 200 步时形成的新格式。

关于模型为何从"文字推理"转向"程序化执行"，我有 3 个可能的假设：

- Qwen 2.5 3B 不够强或太小，Deepseek 提到需要非常强的基座模型。
- 奖励函数定义得不够好，模型找到了奖励漏洞（reward hack），用解方程的方式"钻空子"。我们可以尝试强制它使用文字，比如设置数字/文字词频条件。（我们对 Deepseek 的奖励函数知之甚少）
- 只在 Countdown 游戏任务上训练，可能自然地迫使模型学习解方程最有效的表达方式，因为不需要其他格式。
- 我们训练得不够久，R1 论文展示的训练可视化超过了 8000 步。

## 结论

DeepSeek R1 及其论文的发布，可能是开放科学与开源发展的一个分水岭。就在 DeepSeek 发布一周后，我们已经能用 GRPO 和 Countdown 游戏复现 R1 学会"推理"的简化版本。虽然我们的实现聚焦特定任务而非通用推理，并且收敛到了一种非常特定的"推理"格式，但它证明了这套方法是有效的。

展望 2025，我们显然正处于更大进步的门槛上。RL 会变得更易得、更好用，更多研究者和开发者将探索它的潜力——但相比监督微调，它也需要比以前更多的算力。
