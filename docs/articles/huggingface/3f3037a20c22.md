# 用 AutoGPTQ 和 transformers 让 LLM 更轻量

这篇文章也有中文版 [简体中文](https://huggingface.co/blog/zh/gptq-integration)。

大语言模型在理解和生成类人文本方面展现出非凡能力，正在革新各个领域的应用。但它们对消费级硬件在训练和部署上的要求，也越来越难以满足。

🤗 Hugging Face 的核心使命是*让好的机器学习走向大众*，这包括让大模型对尽可能多的人变得触手可及。秉持与我们 [bitsandbytes 合作](https://huggingface.co/blog/4bit-transformers-bitsandbytes)相同的精神，我们刚刚把 [AutoGPTQ](https://github.com/PanQiWei/AutoGPTQ) 库集成进了 Transformers，让用户可以用 GPTQ 算法（[Frantar et al. 2023](https://arxiv.org/pdf/2210.17323.pdf)）以 8、4、3 甚至 2 bit 精度量化和运行模型。4 bit 量化的精度损失可以忽略不计，且在小 batch size 下推理速度与 `fp16` 基线相当。注意 GPTQ 方法与 bitsandbytes 提出的训练后量化方法略有不同，它需要传入一个校准数据集。

该集成同时支持 Nvidia GPU 和基于 RoCm 的 AMD GPU。

## **GPTQ 论文轻量导读**

量化方法通常属于两类之一：

- 训练后量化（PTQ）：用适中的资源量化一个预训练模型，例如一份校准数据集和几个小时计算。
- 量化感知训练（QAT）：在训练或进一步微调之前进行量化。

GPTQ 属于 PTQ 一类，这对超大模型尤其有意义——这类模型的完整训练甚至微调都可能非常昂贵。

具体来说，GPTQ 采用 int4/fp16 混合量化方案：权重量化为 int4，激活保持 float16。推理时权重在线反量化，实际计算在 float16 下进行。

这种方案的好处有两方面：

- int4 量化下接近 4 倍的内存节省，因为反量化发生在紧邻计算单元的融合 kernel 内，而不是在 GPU 全局显存里。
- 潜在的加速：权重位宽更低，数据传输上省下的时间可以带来速度提升。

GPTQ 论文解决的是逐层压缩问题：

给定层 lll，其权重矩阵为 WlW_{l}Wl​、层输入为 XlX_{l}Xl​，我们想找到权重的量化版本 W^l\hat{W}_{l}W^l​，使均方误差（MSE）最小：

W^l∗=argminWl^∥WlX−W^lX∥22{\hat{W}_{l}}^{*} = argmin_{\hat{W_{l}}} \|W_{l}X-\hat{W}_{l}X\|^{2}_{2}W^l​∗=argminWl​^​​∥Wl​X−W^l​X∥22​

逐层求解之后，把各层解组合起来即可得到全局问题的解。

为求解这个逐层压缩问题，作者使用了 Optimal Brain Quantization 框架（[Frantar et al 2022](https://arxiv.org/abs/2208.11580)）。OBQ 方法始于一个观察：上式可以写成对 WlW_{l}Wl​ 每一行的平方误差之和。

∑i=0drow∥Wl[i,:]X−W^l[i,:]X∥22 \sum_{i=0}^{d_{row}} \|W_{l[i,:]}X-\hat{W}_{l[i,:]}X\|^{2}_{2} ∑i=0drow​​∥Wl[i,:]​X−W^l[i,:]​X∥22​

这意味着我们可以逐行独立量化，即所谓的逐通道量化（per-channel quantization）。对每一行 Wl[i,:]W_{l[i,:]}Wl[i,:]​，OBQ 一次量化一个权重，同时始终更新所有尚未量化的权重，以补偿量化单个权重带来的误差。对被选中的权重的更新有闭式公式，利用 Hessian 矩阵完成。

GPTQ 论文在此基础上引入一组优化，降低量化算法复杂度的同时保留模型精度。

与 OBQ 相比，GPTQ 的量化步骤本身也更快：OBQ 量化一个 BERT 模型（336M）需要 2 GPU 小时，而 GPTQ 量化一个 Bloom 模型（176B）不到 4 GPU 小时。

想深入了解具体算法以及困惑度和加速方面的各项基准，请阅读原始[论文](https://arxiv.org/pdf/2210.17323.pdf)。

## AutoGPTQ 库——高效利用 GPTQ 服务 LLM 的一站式库

AutoGPTQ 库让用户可以用 GPTQ 方法量化 🤗 Transformers 模型。同期的社区项目如 [GPTQ-for-LLaMa](https://github.com/qwopqwop200/GPTQ-for-LLaMa)、[Exllama](https://github.com/turboderp/exllama) 和 [llama.cpp](https://github.com/ggerganov/llama.cpp/) 的量化方法严格只针对 Llama 架构，而 AutoGPTQ 凭借对一大片 transformer 架构的顺畅覆盖赢得了人气。

由于 AutoGPTQ 库覆盖的 transformer 模型更广，我们决定提供一个集成的 🤗 Transformers API，让 LLM 量化对人人更触手可及。目前我们集成了最常用的优化选项，例如 CUDA kernel。若要使用更高级的选项，如 Triton kernel 或 fused-attention 兼容性，请查看 [AutoGPTQ](https://github.com/PanQiWei/AutoGPTQ) 库。

## 🤗 Transformers 对 GPTQ 模型的原生支持

[安装 AutoGPTQ 库](https://github.com/PanQiWei/AutoGPTQ#quick-installation)和 `optimum`（`pip install optimum`）之后，在 Transformers 里运行 GPTQ 模型简单到只需：

```
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained("TheBloke/Llama-2-7b-Chat-GPTQ", torch_dtype=torch.float16, device_map="auto")
```

更多功能请查阅 Transformers [文档](https://huggingface.co/docs/transformers/main/en/main_classes/quantization)。

我们的 AutoGPTQ 集成有很多优点：

- 量化后的模型可以序列化，并能分享到 Hub。
- GPTQ 大幅降低运行 LLM 的内存需求，同时推理延迟与 FP16 推理不相上下。
- AutoGPTQ 支持多种架构的 Exllama kernel。
- 集成原生支持基于 RoCm 的 AMD GPU。
- 支持[用 PEFT 微调](https://huggingface.co/blog/gptq-integration#--fine-tune-quantized-models-with-peft--)。

你可以在 Hub 上查看你心仪的模型是否已经被量化过。TheBloke 是 Hugging Face 的顶级贡献者之一，已经用 AutoGPTQ 量化了大量模型并分享到 Hugging Face Hub。我们与其合作确保这些仓库配合我们的集成可以开箱即用。

这是一个 batch size = 1 情形的基准样例。基准在单张 NVIDIA A100-SXM4-80GB GPU 上运行，提示词长度 512，恰好生成 512 个新 token。第一行是未量化的 `fp16` 基线，其余行展示使用不同 AutoGPTQ kernel 时的内存消耗和性能。

## **用 Optimum 库**量化模型

为了把 AutoGPTQ 无缝集成进 Transformers，我们使用了 AutoGPTQ API 的精简版，它可在 [Optimum](https://github.com/huggingface/optimum)（Hugging Face 的训练与推理优化工具箱）中找到。按这条路线，我们既实现了与 Transformers 的轻松集成，又让大家在想量化自己的模型时可以直接使用 Optimum API！想量化自己的 LLM，请查阅 Optimum [文档](https://huggingface.co/docs/optimum/llm_quantization/usage_guides/quantization)。

用 GPTQ 方法量化 🤗 Transformers 模型只需几行：

```
from transformers import AutoModelForCausalLM, AutoTokenizer, GPTQConfig

model_id = "facebook/opt-125m"
tokenizer = AutoTokenizer.from_pretrained(model_id)
quantization_config = GPTQConfig(bits=4, dataset = "c4", tokenizer=tokenizer)

model = AutoModelForCausalLM.from_pretrained(model_id, device_map="auto", quantization_config=quantization_config)
```

量化一个模型可能耗时很长。注意：对于 175B 模型，如果使用大数据集（例如 `"c4"`），至少需要 4 GPU 小时。如前所述，Hugging Face Hub 上已有大量 GPTQ 模型，多数场景下不必亲自量化。不过，你也可以使用适合自己所处领域的自有数据集来量化模型。

## 通过 ***Text-Generation-Inference*** 运行 GPTQ 模型

与 Transformers 中集成 GPTQ 并行，[Text-Generation-Inference 库](https://github.com/huggingface/text-generation-inference)（TGI）也加入了 GPTQ 支持——TGI 面向生产环境服务大语言模型。现在 GPTQ 可以与动态批处理、paged attention、flash attention 等特性配合使用，覆盖[广泛的架构](https://huggingface.co/docs/text-generation-inference/main/en/supported_models)。

举个例子，这个集成让 70B 模型能在单张 A100-80GB GPU 上服务！用 fp16 权重做不到这一点，因为会超出可用显存。

GPTQ 在 TGI 中的用法详见[文档](https://huggingface.co/docs/text-generation-inference/main/en/basic_tutorials/preparing_model#quantization)。

注意，TGI 中集成的 kernel 在大 batch size 下扩展性一般。虽然该方案节省内存，但在更大的 batch size 下会出现减速。

## **用 PEFT 微调量化模型**

量化后的模型无法用常规方法继续训练。不过，借助 PEFT 库，你可以在其上训练适配器（adapter）！做法是冻结量化模型的所有层，添加可训练适配器。PEFT 配合 GPTQ 模型的用法见这些例子：[colab notebook](https://colab.research.google.com/drive/1VoYNfYDKcKRQRor98Zbf2-9VQTtGJ24k?usp=sharing) 和[微调](https://gist.github.com/SunMarc/dcdb499ac16d355a8f265aa497645996)脚本。

## 改进空间

我们的 AutoGPTQ 集成已经以很小的预测质量代价带来了可观的收益，但量化技术和 kernel 实现都仍有改进空间。

首先，虽然 AutoGPTQ 集成的（据我们所知）是性能最好的 W4A16 kernel（权重 int4、激活 fp16），来自 [exllama 实现](https://github.com/turboderp/exllama)，但这个 kernel 很可能还能继续改进。[Kim et al.](https://arxiv.org/pdf/2211.10017.pdf) 和 [MIT Han Lab](https://github.com/mit-han-lab/llm-awq) 的其他实现也很有前景。另外从内部基准来看，目前仍没有用 Triton 编写的高性能开源 W4A16 kernel，这可能是一个值得探索的方向。

量化侧方面，再次强调：这个方法只量化权重。还有其他针对 LLM 量化的方案可以在很小的预测质量代价下同时量化权重和激活，例如 [LLM-QAT](https://arxiv.org/pdf/2305.17888.pdf)，它可以使用 int4/int8 混合方案，还能量化 key-value cache。这项技术的一大优势是可以用真正的整数运算做计算，例如 [Nvidia Tensor Core 支持 int8 计算](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/a100/pdf/nvidia-a100-datasheet-us-nvidia-1758950-r4-web.pdf)。不过据我们所知，目前还没有开源的 W4A8 量化 kernel，但这很可能是一个[值得探索的方向](https://www.qualcomm.com/news/onq/2023/04/floating-point-arithmetic-for-ai-inference-hit-or-miss)。

kernel 侧同样如此：为更大 batch size 设计高性能 W4A16 kernel 仍是未解难题。

### 支持的模型

在当前这版实现中，仅支持 decoder-only 或 encoder-only 架构的大语言模型。这听起来有点限制，但它覆盖了绝大多数前沿 LLM，例如 Llama、OPT、GPT-Neo、GPT-NeoX。

超大的视觉、音频和多模态模型目前暂不支持。
