# 辅助生成：迈向低延迟文本生成的新方向

如今大语言模型正当红，许多公司投入大量资源把它们做大，以解锁新的能力。但作为注意力持续时间越来越短的人类，我们也不喜欢它们缓慢的响应速度。延迟对良好的用户体验至关重要，即便质量打折，人们常常还是选择小模型（比如用于[代码补全](https://ai.googleblog.com/2022/07/ml-enhanced-code-completion-improves.html)）。

为什么文本生成这么慢？是什么阻止你不破产就部署低延迟的大语言模型？在这篇博文里，我们会重新梳理自回归文本生成的瓶颈，并介绍一种应对延迟问题的新解码方法。你会看到，通过我们的新方法——辅助生成（assisted generation），在普通硬件上就能把延迟降低多达 10 倍！

## 理解文本生成的延迟

现代文本生成的核心其实很好理解。我们来看关键部件——模型本身。它的输入是一个文本序列，包含目前已生成的文本，可能还有其他模型特有的部分（例如 Whisper 还有音频输入）。模型接收输入并运行一次前向传播：输入被喂给模型，沿各层依次传递，直到预测出下一个 token 的未归一化对数概率（也就是 logits）。一个 token 可能是完整的单词、子词或单个字符，具体取决于模型。想更深入地了解文本生成的这部分，[图解 GPT-2](https://jalammar.github.io/illustrated-gpt2/) 是一份很好的参考资料。

模型的一次前向传播得到下一个 token 的 logits，你可以自由地操作它们（例如把不希望出现的单词或序列的概率设为 0）。文本生成的下一步是从这些 logits 中选出下一个 token。常用策略包括选出概率最高的 token（即贪心解码），或从其分布中采样（即多项式采样）。把模型前向传播与下一 token 选择反复串联起来，就得到了文本生成。要说解码方法，这只是冰山一角；请参阅[我们关于文本生成的博文](https://huggingface.co/blog/how-to-generate)做深入探索。

从上面的描述来看，文本生成的延迟瓶颈很清楚：大模型跑一次前向传播就很慢，而且你可能需要连续跑上百次。但我们再深挖一层：前向传播为什么慢？前向传播通常以矩阵乘法为主，简单看一眼 [维基百科对应章节](https://en.wikipedia.org/wiki/Matrix_multiplication_algorithm#Communication-avoiding_and_distributed_algorithms)就能知道，这个操作的受限因素是内存带宽（例如从 GPU 显存到 GPU 计算核心）。换句话说，*前向传播的瓶颈在于把模型各层权重加载进设备的计算核心，而不在于计算本身*。

眼下，要榨干文本生成的性能，主要有三条路可走，都针对模型前向传播的性能。第一是面向具体硬件的模型优化。例如你的设备可能支持 [Flash Attention](https://github.com/HazyResearch/flash-attention)，通过重排运算来加速注意力层；或者支持 [INT8 量化](https://huggingface.co/blog/hf-bitsandbytes-integration)，以减小模型权重的体积。

第二，当你明确会有并发的文本生成请求时，可以把输入批处理（batch），用很小的延迟代价大幅提升吞吐量。加载进设备的模型层权重现在可以并行用于多个输入行，也就是说大致相同的内存带宽负担能产出多得多的 token。批处理的代价是需要额外的设备内存（或者把内存卸载到别处）——在这条路的尽头，你可以看到 [FlexGen](https://github.com/FMInference/FlexGen) 这样的项目，它以牺牲延迟为代价优化吞吐量。

```
# Example showcasing the impact of batched generation. Measurement device: RTX3090
from transformers import AutoModelForCausalLM, AutoTokenizer
import time

tokenizer = AutoTokenizer.from_pretrained("distilgpt2")
model = AutoModelForCausalLM.from_pretrained("distilgpt2").to("cuda")
inputs = tokenizer(["Hello world"], return_tensors="pt").to("cuda")

def print_tokens_per_second(batch_size):
    new_tokens = 100
    cumulative_time = 0

    # warmup
    model.generate(
        **inputs, do_sample=True, max_new_tokens=new_tokens, num_return_sequences=batch_size
    )

    for _ in range(10):
        start = time.time()
        model.generate(
            **inputs, do_sample=True, max_new_tokens=new_tokens, num_return_sequences=batch_size
        )
        cumulative_time += time.time() - start
    print(f"Tokens per second: {new_tokens * batch_size * 10 / cumulative_time:.1f}")

print_tokens_per_second(1)   # Tokens per second: 418.3
print_tokens_per_second(64)  # Tokens per second: 16266.2 (~39x more tokens per second)
```

最后，如果你有多块设备可用，可以用 [Tensor Parallelism（张量并行）](https://huggingface.co/docs/transformers/main/en/perf_train_gpu_many#tensor-parallelism)来分摊负载，从而获得更低的延迟。张量并行把内存带宽的负担分散到多块设备上，但除了多设备的费用，你还得考虑设备间的通信瓶颈。收益大小主要取决于模型规模：能轻松放进单块消费级设备的模型，收益非常有限。参考这篇 [DeepSpeed 博文](https://www.microsoft.com/en-us/research/blog/deepspeed-accelerating-large-scale-model-inference-and-training-via-system-optimizations-and-compression/)的结果，你可以把一个 17B 参数的模型拆分到 4 块 GPU 上，把延迟降低 1.5 倍（图 7）。

这三类优化可以结合起来用，从而得到[高吞吐方案](https://github.com/huggingface/text-generation-inference)。但在做完硬件层面的优化之后，能进一步降低延迟的手段就很有限了——而且现有手段都很贵。我们来解决这个问题！

## 重新审视语言解码器的前向传播

上面你读到，每次模型前向传播会给出下一个 token 的 logits，但这其实是个不完整的描述。在文本生成期间，典型的迭代是：模型接收最新生成的 token 作为输入，再加上对所有先前输入的内部计算缓存，返回下一个 token 的 logits。使用缓存是为了避免重复计算，从而加快前向传播，但缓存并非必须（也可以部分使用）。当禁用缓存时，输入包含到目前为止生成的完整 token 序列，而输出则包含序列中*所有位置*对应的下一 token 的 logits！位置 N 处的 logits 对应这样一个分布：假设输入就是前 N 个 token、忽略序列中其后的所有 token 时，下一个 token 的分布。在贪心解码这个特例中，如果你把生成的序列作为输入传进去，并对得到的 logits 施加 argmax 运算，你会原样拿回这个生成序列。

```
from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("distilgpt2")
model = AutoModelForCausalLM.from_pretrained("distilgpt2")

inputs = tok(["The"], return_tensors="pt")
generated = model.generate(**inputs, do_sample=False, max_new_tokens=10)
forward_confirmation = model(generated).logits.argmax(-1)

# We exclude the opposing tips from each sequence: the forward pass returns
# the logits for the next token, so it is shifted by one position.
print(generated[0, 1:].tolist() == forward_confirmation[0, :-1].tolist())  # True
```

这意味着你可以把一次模型前向传播用于另一个目的：除了喂一些 token 来预测下一个，你还可以把一个序列喂给模型，核查模型是否会生成同样的序列（或其中一部分）。

假设一瞬间：你能用一个没有延迟魔力的 oracle 模型，对任何给定输入都生成与你模型相同的序列。为了论证方便，它不能直接使用，只能充当你的生成过程的助手。利用上面描述的性质，你可以用这个助手模型拿到候选输出 token，然后用你的模型做一次前向传播来确认它们确实正确。在这个乌托邦式的情景里，文本生成的延迟会从 `O(n)` 降到 `O(1)`，其中 `n` 是生成的 token 数。对于长文本生成，这可是好几个数量级的差距。

往现实走一步：假设助手模型失去了 oracle 属性。现在它是一个无延迟模型，但按你的模型来看，它会答错一些候选 token。由于任务的自回归性质，助手一旦答错某个 token，其后的所有候选都必须作废。不过这不妨碍你在用自己的模型纠正错误 token 之后再次询问助手，并迭代重复这个过程。就算助手错了一些 token，文本生成的延迟仍会比原始形态低一个数量级。

显然，不存在无延迟的助手模型。但是，找到一个近似另一个模型文本生成输出的模型并不难——同样架构、同样方式训练出来的小版本模型往往就符合这个性质。而且，当两个模型的规模差距足够大时，把小模型用作助手的成本相对于跳过几次前向传播的收益而言根本不值一提！现在你理解了*辅助生成*的核心。

## 辅助生成下的贪心解码

辅助生成是一种平衡术。你希望助手快速生成候选序列，同时尽量准确。如果助手质量太差，你只会付出使用助手模型的开销，收益几乎没有；反之，如果为了优化候选序列的质量而用很慢的助手，结果反而是净减速。虽然我们无法替你自动选择助手模型，但我们附加了一条硬性要求和一条启发式规则，确保花在助手上的时间保持在可控范围内。

先说要求——助手必须与你的模型使用完全相同的 tokenizer。如果没有这个要求，就得加上昂贵的 token 解码再重新编码的步骤。而且这些额外步骤发生在 CPU 上，可能还需要缓慢的设备间数据传输。快速使用助手模型，是让辅助生成收益显现的关键。

最后是启发式规则。读到这里，你可能已经发现电影《盗梦空间》和辅助生成之间的相似之处了——你毕竟是在文本生成里面跑文本生成。每个候选 token 都要消耗一次助手模型的前向传播，而我们知道前向传播很贵。虽然你无法预知助手模型能答对多少个 token，但你可以记录这些信息并利用它来限制向助手请求的候选 token 数量——输出的某些部分就是比其他部分更容易预测。

把以上所有汇总，就是我们辅助生成循环的最初实现（[代码](https://github.com/huggingface/transformers/blob/849367ccf741d8c58aa88ccfe1d52d8636eaf2b7/src/transformers/generation/utils.py#L4064)）：

- 用贪心解码让助手模型生成一定数量的候选 token，得到 `candidates`。首次调用辅助生成时，候选 token 数量初始化为 `5`。
- 用你的模型对 `candidates` 做一次前向传播，得到 `logits`。
- 用 token 选择方法（贪心搜索用 `.argmax()`，采样用 `.multinomial()`）从 `logits` 中得到 `next_tokens`。
- 把 `next_tokens` 与 `candidates` 比较，统计匹配的 token 数。记住，这个比较必须按从左到右的因果顺序进行：出现第一个不匹配后，所有后续候选都作废。
- 用匹配数量做切片，丢弃与未确认候选 token 相关的变量。本质上就是在 `next_tokens` 中保留匹配的 token 加上第一个分歧 token（它是由你的模型从有效的候选子序列生成的）。
- 调整下一轮迭代要生成的候选 token 数量——我们的初始启发式是：若全部 token 匹配则加 `2`，否则减 `1`。

我们把 🤗 Transformers 的 API 设计成让这个过程对你毫无负担。你只需把助手模型通过新的 `assistant_model` 关键字参数传进来，就能收获延迟收益！在本博文发布之时，辅助生成的批大小上限为 `1`。

```
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

prompt = "Alice and Bob"
checkpoint = "EleutherAI/pythia-1.4b-deduped"
assistant_checkpoint = "EleutherAI/pythia-160m-deduped"
device = "cuda" if torch.cuda.is_available() else "cpu"

tokenizer = AutoTokenizer.from_pretrained(checkpoint)
inputs = tokenizer(prompt, return_tensors="pt").to(device)

model = AutoModelForCausalLM.from_pretrained(checkpoint).to(device)
assistant_model = AutoModelForCausalLM.from_pretrained(assistant_checkpoint).to(device)
outputs = model.generate(**inputs, assistant_model=assistant_model)
print(tokenizer.batch_decode(outputs, skip_special_tokens=True))
# ['Alice and Bob are sitting in a bar. Alice is drinking a beer and Bob is drinking a']
```

这些额外的内部复杂度值得吗？我们来看看贪心解码情形下的延迟数据（采样的结果在下一节），批大小为 `1`。这些数据直接取自 🤗 Transformers，没有做任何额外优化，你应该能在自己的环境里复现它们。

扫一眼收集到的数据，可以看到辅助生成在各种设置下都能带来可观的延迟降低，但它不是银弹——用之前应该先针对你的使用场景做基准测试。我们可以总结如下：辅助生成——

- 🤏 需要一个至少比你的模型小一个数量级的助手模型（差距越大越好）；
- 🚀 在模型能装进 GPU 显存的情况下，使用 INT8 时最高提速 3 倍，否则最高 2 倍；
- 🤯 如果你在玩装不进 GPU、依赖内存卸载的模型，可以看到最高 10 倍的提速；
- 📄 在输入驱动型任务上表现亮眼，比如自动语音识别或摘要。

## 辅助生成下的采样

贪心解码适合输入驱动型任务（自动语音识别、翻译、摘要……）或寻求事实知识的场景。而需要高度创造力的开放式任务，比如把语言模型当聊天机器人的大多数用法，应该改用采样。辅助生成天然为贪心解码而设计，但这并不意味着不能配合多项式采样使用！

从下一 token 的概率分布中采样会让我们的贪心助手更频繁地答错，从而削弱延迟收益。不过，我们可以控制下一 token 概率分布的尖锐程度——借助大多数采样应用中都有的温度系数。在一端，温度接近 0 时，采样会近似贪心解码，偏向最可能的 token；在另一端，温度远大于 1 时，采样会变得混乱，从均匀分布中抽取。因此，低温对助手模型更友好，能保留辅助生成的大部分延迟收益，如下所示。

## 未来方向

辅助生成表明，现代文本生成策略充满了可优化空间。理解它目前是内存受限问题而非算力受限问题，让我们能用简单的启发式规则充分利用可用的内存带宽，缓解瓶颈。我们相信，进一步打磨助手模型的使用方式还能带来更大的延迟降低——例如，如果让助手生成多个候选续写，我们也许能再跳过更多次前向传播。当然，发布可用作助手的高质量小模型，将是实现并放大这一收益的关键。

辅助生成最初发布在我们的 🤗 Transformers 库里，配合 `.generate()` 函数使用；我们期待把它推广到整个 Hugging Face 生态。其实现也完全开源，如果你在做文本生成但没有使用我们的工具，欢迎把它作为参考。

最后，辅助生成重新抛出了文本生成领域的一个关键问题。这个领域一直沿着一条约束演进：对给定模型而言，每个新 token 都消耗固定量的算力，纯粹的自回归式——每个 token 对应一次同质的前向传播。这篇博文强化了一个观点：这本不该如此。生成输出中很大的片段，完全可以由尺寸只有几分之一的模型同等地生成。为此，我们需要新的模型架构和解码方法——对未来，我们很期待！
