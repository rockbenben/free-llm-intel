# ScarfBench：面向企业 Java 框架迁移的 AI 智能体基准测试

[ ⭐ Star ScarfBench on GitHub ](https://github.com/scarfbench/benchmark)

企业应用现代化是组织正在进行的最大、最昂贵的软件工程活动之一。团队把应用从一个框架迁移到另一个框架，以提升可维护性、云就绪度、开发者生产力，并获得现代能力。

编码智能体（coding agent）的最新进展让人们对 AI 辅助现代化充满期待。但一个关键问题仍待回答：

**AI 智能体能否可靠地现代化真实的企业应用？**

现有的软件工程基准测试在 bug 修复和代码生成上已展示了惊人的进步，但框架迁移是一个本质不同的挑战。成功不仅需要翻译代码，还要保持行为不变、适配构建系统，并处理运行时依赖。

为了填补这个空白，我们推出 **ScarfBench（Self-Contained Application Refactoring Benchmark，自包含应用重构基准）**——一个开放基准，用于评估 AI 智能体在企业 Java（Enterprise Java）跨框架迁移任务上的表现。

ScarfBench 聚焦于三大 Java 生态之间的迁移：

- Spring
- Jakarta EE
- Quarkus

与传统基准对比生成代码和参考实现不同，ScarfBench 评估的是迁移后的应用能否真正构建、部署并保持行为一致。

## 迁移为什么难

框架迁移远不止替换注解那么简单。

哪怕是一个简单的仓库迁移，也可能需要改动依赖注入、持久化配置、查询语句和框架描述文件。任何一环上的小错误都可能导致部署失败。

框架迁移要求翻译的是框架语义，而不仅仅是源代码。

## ScarfBench 简介

[ScarfBench](https://huggingface.co/spaces/ibm-research/ScarfBench) 提供了一套系统化的方法，用来评估 AI 智能体在企业 Java 框架迁移任务上的表现。

应用必须满足：

- 构建成功。
- 部署正确。
- 通过行为校验。

这为现代化质量提供了远为现实的衡量标准。

## 关于用于 Java 现代化的 AI 智能体，我们学到了什么

除了测量成功率，ScarfBench 还帮助我们理解智能体在现代化过程中的行为方式。

### 智能体能可靠地判断迁移何时完成吗？

迁移后的应用只有在真正能构建、能运行时才有用。

因此我们把智能体自报的结果与独立的构建验证做了对比。

#### 发现：智能体过于自信

Claude Code 报告 30 个完整应用中有 29 个构建成功。

而实际构建成功的只有 22 个。

与此同时，被智能体判定为失败的那 1 个应用最终其实是正常构建的。

这说明智能体的自我评估不能作为迁移已完成的可靠信号。

独立的构建和测试验证仍然必不可少。

### 智能体如何处理应用依赖？

框架迁移很少只影响单个文件或单层。

配置、服务、数据库和 Web 组件的改动往往会在整个应用里连锁扩散。

#### 发现：迁移是迭代式的，而非线性的

被反复访问最多的层是：

- Configuration（配置）
- Web
- Database（数据库）
- Service（服务）

常见的转移路径包括：

- Configuration ↔ Web
- Service ↔ Database

这表明迁移是一个迭代式的依赖解析过程，而不是简单的源码到源码的转换。

### 智能体的精力主要花在哪里？

我们用"层的重复访问频率"作为迁移工作量的代理指标。需要反复访问的层，通常涉及调试、依赖解析或框架适配。

#### 发现：配置占据了迁移工作量的大头

智能体并非线性推进，而是在解决框架差异和依赖问题的过程中反复回到配置相关的产物。

### 有哪些挑战与代码转换无关？

并非所有迁移问题都源自源代码。

#### 发现：环境和工具链很关键

智能体经常在各种环境问题上栽跟头，包括：

- Docker 缓存不一致
- 端口连通性问题
- Maven wrapper 和构建工具问题

即便源码迁移本身基本完成，这些运维层面的问题也常常拖慢验证。

[![failure-distribution](https://cdn-uploads.huggingface.co/production/uploads/649c1276a83f996b4191a8f1/BtWLPGsif0O4VoQfVppIC.png)](https://cdn-uploads.huggingface.co/production/uploads/649c1276a83f996b4191a8f1/BtWLPGsif0O4VoQfVppIC.png)

**图：失败模式分布**

现代化的失败点遍布构建系统、部署环境、依赖注入、数据库、端点、断言和基础设施。

## 核心结论

框架现代化最大的挑战不是翻译 Java 代码。

而是管理贯穿配置、基础设施和运行时环境的依赖网络。

虽然前沿智能体已经能自动化迁移流程的相当大部分，但要取得真正成功的结果，可靠的验证和架构层面的推理依然关键。

ScarfBench 有助于暴露这些挑战，并为衡量迈向真正自主应用现代化的进展提供标准化手段。
