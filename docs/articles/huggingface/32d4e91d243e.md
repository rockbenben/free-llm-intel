*一个 20 亿个参数模型，可以从任何文档类型中准确提取您要求的字段，其性能优于我们测试过的每个前沿LLM，而成本仅为其一小部分。 *

[![cover_combined_1](https://cdn-uploads.huggingface.co/product/uploads/6a725daa5ca641a21ab61956/JIRHcND5LFS_JhgA e-ObV.png)](https://cdn-uploads.huggingface.co/product/uploads/6a725daa5ca641a21ab61956/JIRHcND5LFS_JhgAe-ObV.png) 4 月份，我们发布了 [DharmaOCR-LITE](https://huggingface.co/Dharma-AI/Dharma-OCR-LITE)，这是一个专门用于 OCR 的模型，涵盖从合同和法庭文件到发票、ID 和表格等各种文档。其背后的[论文](https://arxiv.org/abs/2604.14314)为领域专业化提出了一个狭窄的、经过精心衡量的案例：一个更接近其任务的较小模型在该任务上击败了通用前沿 API。

OCR 为您提供页面上的文本，忠实于原始格式。当工作是整个文档时，这正是您想要的，例如您将从头到尾阅读的合同或您正在数字化的手稿。

然而，有一个不同的用例：您不需要页面，您想要其中的特定字段，以下游系统可以使用的形状。发票上的每个行项目，作为列表。医疗申请中的患者姓名、检查类型和日期，已准备好安排。 ID 的字段映射到员工记录的列。

通过 OCR 运行该文档，您将逐行返回打印在文档上的所有内容，但不会指示哪个字符串是考试类型、哪个是日期或哪个数字是总数。在每个值到达数据库之前，仍然需要有人编写将每个值映射到正确字段的代码。

如今，只要仔细提示，通用LLM就可以完成这项工作。在前沿 API 定价和延迟方面，许多企业需要大量运行任务，这很快就会成为解决明确定义的问题的昂贵方法。

所以我们为它建立了一个模型。字段提取器获取文档图像以及对其能找到的所有内容的请求，或者要填充的精确模式，然后返回结构化 JSON：类型化、逐个字段、嵌套在文档嵌套的位置。发票以有序列表的形式返回每个行项目，每个项目都有自己的数量和价值以及总计。 ID 作为您将存储的字段返回，并使用您的系统已使用的名称。相同的检查点处理所有这些，无需针对每种类型进行微调。

您可以自己尝试一下[此处](https://ocr-portal.prd-us-east-2.dharma-ai.com/login)。

## 模型的作用

假设每天早上收到一批供应商发票，您需要将每张发票中的四项信息推入系统：供应商、发票编号、到期日、总计。对于进入调度程序的医疗申请或为合规系统提供合同的情况也是如此，重要的是当事人、期限、处罚和罚款金额。您不需要页面，您需要某些字段。使用字段提取器，有两种方法可以获取它们：

[![field-extractor-1280](https://cdn-uploads.huggingface.co/product/uploads/6a725daa5ca641a21ab61956/j-k3pMh-GwLH6b gsRZ-4u.gif)](https://cdn-uploads.huggingface.co/product/uploads/6a725daa5ca641a21ab61956/j-k3pMh-GwLH6bgsRZ-4u.gif)

- **打开**：未提供架构。该模型读取页面并从上下文和布局而不是从固定的字段名称列表中找出其中的哪些部分是结构化字段（一个标签后跟一个值，一个在其列上有标题行的表格），并将它找到的所有内容作为键值对返回。
- **架构导向**：您可以在系统已使用的键名称下逐个字段指定所需的确切形状，并为每个字段指定一个类型（字符串、数字或布尔值）。询问“service_provider”和“client_company”，这些就是返回的确切密钥。请求一个表格，它会逐行、逐列地填充它，将每个单元格与其所属的键相匹配。请求一个不在文档中的字段，它会返回 null 而不是发明一个值。

选择取决于您已经知道的内容。当您不知道文档包含什么内容时，请发送开放请求。当输出必须与其他地方已经存在的形状匹配时发送模式。

无论哪种方式，返回的是 JSON：字段作为键，根据请求键入的值，以及“null”（如果文档没有您所要求的内容）。当您发送模式时，输出完全遵循它，具有相同的键并且没有额外的字段，因此它可以直接进入下一个系统。

## 它是如何训练的

基本模型是 DharmaOCR-LITE v1.1，这是一个新的 20 亿参数版本，在论文中的模型的基础上进行了优化，并且已经通过监督微调和 DPO 专门用于 OCR。在该检查点之上，我们在涵盖两种请求模式的 43,384 个训练示例上训练了 LoRA 适配器。

数据被组织成三个流：

- **英语多域数据**：从公共网络收集的各种文档，涵盖多种文档类型。
- **巴西域名数据**：内部来源的真实巴西文档，采用葡萄牙语。
- **多语言数据**：覆盖其他欧洲和亚洲语言的较小份额，用于英语和葡萄牙语以外的更广泛的概括。

所有三个流都在字段级别进行注释。这种混合是有意的多领域：收据、商业发票、表格、银行对账单、身份证件和综合文件，而不是一种归档类型。

## 基准的界限在哪里

完整的基准测试涵盖了三个请求场景中的 546 个文档，总共 1,638 个案例：提取没有模式的每个字段、仅命名真实字段的部分模式以及还包含故意不存在的字段的模式。分数是字段级 F1（按路径匹配，包括表内的位置），乘以匹配值的 Levenshtein 相似度以及作为有效 JSON 返回的输出份额。

我们针对四种通用前沿配置运行了相同的基准测试。

[![图片](https://cdn-uploads.huggingface.co/product/uploads/6a725daa5ca641a21ab61956/rGnjzOfdYJrtG8gG_6kZc。 png)](https://cdn-uploads.huggingface.co/product/uploads/6a725daa5ca641a21ab61956/rGnjzOfdYJrtG8gG_6kZc.png)

与通用LLM相比，质量差距从 1.8 分（Claude Opus 5，最接近）到 9.3 分（GPT-5.6 Luna，最宽）。

[![图片](https://cdn-uploads.huggingface.co/product/uploads/6a725daa5ca641a21ab61956/bHPhh4WTqoSI2Aqg0NAii。 png)](https://cdn-uploads.huggingface.co/product/uploads/6a725daa5ca641a21ab61956/bHPhh4WTqoSI2Aqg0NAii.png)

成本从大约低 6 倍 (GPT-5.6 Luna) 到大约低 147 倍 (GPT-5.6 Sol)。两侧的价格不同。前沿数据来自测量的每页平均输入和输出令牌（包括推理令牌），以及每个提供商发布的定价列表。每个前沿模型都在推理设置为低的情况下运行。 Claude Opus 5 使用了自适应努力，可以跳过较简单页面上的推理，同时保持较低水平。我们的模型不按代币计费：该模型运行自托管，因此该数字是单个 L40S 上的 GPU 时间，每小时 2.24 美元。

这不是销售价格。自托管成本取决于每个部署所需的硬件、数量和延迟。此处的比较表明，部署在您自己的基础设施上的主权 SSLM 是前沿 API 的真正替代方案。

## 泛化测试

SROIE 和 FUNSD 是我们基准测试中的两个公共数据集，未在训练中使用。下面是每个例子的一个例子。

在 SROIE 收据上，我们要求提供打印在其上的所有 18 个字段，这次没有虚拟字段，并且每个字段都正确返回：作为单个字段捕获的多行、未标记的帐单地址、两个空白字段（销售人员和参考人）正确返回为 null，并且收据上的每个数字都与分相匹配。

[![sroie_combined](https://cdn-uploads.huggingface.co/product/uploads/6a725daa5ca641a21ab61956/m3CfHgYlaDZ9srzt2 X99_.png)](https://cdn-uploads.huggingface.co/product/uploads/6a725daa5ca641a21ab61956/m3CfHgYlaDZ9srzt2X99_.png)

在 FUNSD 复印差异表单（包含 12 个布尔字段的清单，其中包含五个子选项的嵌套组）上，模型将选中的一个框（质量较差的原件，旁边有手写的“褪色”注释）准确标记为 true，将其他 11 个框标记为 false，与表单完全匹配。它还可以正确读取页面上的手写 Bates ID，并为留空的两个字段返回 null。

[![funsd_combined](https://cdn-uploads.huggingface.co/product/uploads/6a725daa5ca641a21ab61956/GRHwR5tiDzDKVUtMo tsAb.png)](https://cdn-uploads.huggingface.co/product/uploads/6a725daa5ca641a21ab61956/GRHwR5tiDzDKVUtMotsAb.png)

## 同时兼顾质量和成本

20 亿参数模型的得分为 0.834，高于我们测试的所有前沿配置，从 Claude Opus 5 的 0.816 到 GPT-5.6 Luna 的 0.741，同时在单个 L40S 上运行，每次提取的成本低于比较中的每个 API。在相同的基准、相同的运行中测量，质量更高，成本更低。

这不是我们第一次测量它。我们的 OCR 论文将第一个 DharmaOCR-LITE（一个 30 亿参数模型）置于在巴西葡萄牙语上测试的所有商业前沿 API 之上；三个月后，更新、资源更丰富的型号问世，差距依然存在。现在，一个 20 亿参数的模型可以通过字段提取来实现这一点。每个结果都为我们开始 Dharma-AI 的论点提供了证据：在有界任务上，接近该任务训练的小型模型通常会击败要求做同样事情的前沿模型。在此基准测试中，运行成本也降低了 6 至 147 倍。

参数count设置上限；训练决定了模型能完成多少任务。您的企业不需要最大的型号。它需要一位针对您的问题进行过培训的人员。
