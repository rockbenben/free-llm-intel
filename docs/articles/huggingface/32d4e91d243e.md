*一个 20 亿参数的模型，能从任意文档类型里精准抽出你要求的那些字段，性能超过我们测试过的每一款前沿 LLM，而成本只有一小部分。*

[![cover_combined_1](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/JIRHcND5LFS_JhgAe-ObV.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/JIRHcND5LFS_JhgAe-ObV.png) 4 月，我们发布了 [DharmaOCR-LITE](https://huggingface.co/Dharma-AI/Dharma-OCR-LITE)，一个专门做 OCR 的模型，覆盖很宽的一类文档，从合同、法庭文件到发票、身份证件和表单。它背后的[论文](https://arxiv.org/abs/2604.14314)为领域专门化给出了一个切口很窄、度量扎实的论证：一个更小的模型，只要训练得更贴近自己的任务，就能在那项任务上打赢通用的前沿 API。

OCR 给你的是页面上的文字，忠于原始排版。当你要处理的对象是整份文档时——比如一份会从头读到尾的合同，或者一部正在数字化的手稿——这正是你想要的。

但还有另一种用例：你不要那一页，你要从里面取出特定字段，而且要是下游系统能直接消费的形状。发票上的每一条行项目，做成一个列表。医疗申请单上的患者姓名、检查类型和日期，随时可以拿去排期。证件上的字段，映射到员工档案的列上。

把这样一份文档丢给 OCR，你会拿到它上面印的所有内容，逐行返回，却没有任何标注说明哪个字符串是检查类型、哪个是日期、哪个数字是总额。仍然得有人写一段代码，在每个值进入数据库之前，把它们映射到正确的字段上。

通用 LLM 今天也能做这项工作，只要提示词写得足够谨慎。但按前沿 API 的价格和延迟，去跑一个许多企业需要大批量执行的任务，很快就会变成解决一个定义明确的问题的昂贵方式。

所以我们转而专门为它做了一个模型。Field Extractor 接收一张文档图像，再加上一个「把能找到的一切都抽出来」的请求，或者一份要照着填的精确 schema，返回结构化 JSON：逐字段带类型，文档嵌套它就嵌套。一张发票返回时，每一条行项目都是一个有序列表，各自带自己的数量和金额，与总额并列。一张证件返回时，就是你准备存下的那些字段，用的是你系统里已有的名字。同一个 checkpoint 就能处理全部这些，不需要按类型分别微调。

## 这个模型做什么

假设每天早晨都有一批供应商发票落进来，你需要从每张上取出四样东西推进你的系统：供应商、发票号、到期日、总额。要进排期系统的医疗申请单同理，要喂给合规系统的合同也同理——要紧的是当事方、期限、违约条款和罚金数额。你不要那一页，你要某些字段。用 Field Extractor，有两种提法：

[![field-extractor-1280](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/j-k3pMh-GwLH6bgsRZ-4u.gif)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/j-k3pMh-GwLH6bgsRZ-4u.gif)

- **Open**：不提供 schema。模型读这一页，靠上下文和版式判断哪些部分是结构化字段（一个标签后面跟着一个值、一张表头行压着各列的表格），而不是靠一份固定的字段名清单，并把它找到的所有内容以键值对形式返回。
- **Schema-directed**：你指定要的确切形状，一个字段一个字段地写，每个字段各带一个类型（string、number 或 boolean），键名就用你系统里已有的那些。你要 "service_provider" 和 "client_company"，回来的就是这两个确切的键。你要一张表，它就一行一行、一列一列地填满，把每个单元格归到它所属于的那个键下面。你要一个文档上并不存在的字段，它返回 null，而不是编一个值出来。

怎么选取决于你已经知道什么。不知道文档里有什么，就发一个 open 请求。输出必须对上别处已经存在的形状，就发一份 schema。

两种方式返回的都是 JSON：字段作键，值按要求的类型给出，文档里没有你要求的内容就留 `null`。当你发送 schema 时，输出严格照着它来，键相同、没有多余字段，所以可以直接进入下一个系统。

## 它是怎么训练的

基座模型是 DharmaOCR-LITE v1.1，一个在论文里那一版基础上优化出来的新 20 亿参数版本，已经通过监督微调和 DPO 针对 OCR 做过专门化。在那个 checkpoint 之上，我们用 43,384 条训练样本训练了一个 LoRA adapter，样本覆盖两种请求方式。

数据组织成三条流：

- **英语多领域数据**：从公开网页收集的多样文档，横跨许多文档类型。
- **巴西领域数据**：内部获取的真实巴西文档，葡语。
- **多语言数据**：占比更小，覆盖其他欧洲与亚洲语言，为的是在英语和葡语之外有更广的泛化。

三条流都按字段级别标注。这个配比刻意做成多领域的：收据、商业发票、表单、银行对账单、证件和合成文档，而不是某一种归档类型。

[![03_training_data_mix_v2](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/SuMRjXc_gcp3LZm3K_mWs.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/SuMRjXc_gcp3LZm3K_mWs.png)

## 基准把线划在哪里

完整基准覆盖 546 份文档、三种请求场景，合计 1,638 个用例：不提供 schema 抽出每一个字段；只提供一份仅点名真实字段的部分 schema；以及一份还故意包含不存在字段的 schema。分数是字段级 F1（按路径匹配，包括在表格中的位置），再乘上匹配上的那些取值之间的 Levenshtein 相似度，以及输出能作为合法 JSON 返回的比例。

我们把同一份基准跑在四种通用前沿配置上。

[![image](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/rGnjzOfdYJrtG8gG_6kZc.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/rGnjzOfdYJrtG8gG_6kZc.png)

对比通用 LLM，质量差距从 1.8 分（Claude Opus 5，差距最小）到 9.3 分（GPT-5.6 Luna，差距最大）不等。

[![image](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/bHPhh4WTqoSI2Aqg0NAii.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/bHPhh4WTqoSI2Aqg0NAii.png)

成本从大约低 6 倍（GPT-5.6 Luna）到低 147 倍（GPT-5.6 Sol）不等。两侧计价方式不同。前沿那一侧的数字来自实测的每页平均输入与输出 token 数（含 reasoning token），再按各家服务商公布的牌价折算。每一款前沿模型都把 reasoning 设为 low 来跑；Claude Opus 5 用的是 adaptive effort，它可以在较简单的页面上跳过 reasoning，同时保持在 low 这一档。我们那个不按 token 计费：模型是自托管运行的，所以这个数字是单张 L40S 上的 GPU 时长，每小时 $2.24。

这不是售价。自托管成本取决于每一次部署所需的硬件、吞吐量和延迟。放这个对比在这里，是为了说明一个主权的 SSLM 部署在你自己的基础设施上，是前沿 API 一个实实在在的可选项。

## 一次泛化能力的检验

SROIE 和 FUNSD 是我们基准里的两个公开数据集，没有用于训练。下面各举一个例子。

在一张 SROIE 收据上，我们要求抽出它上面印的全部 18 个字段，这一次不掺入不存在的字段，结果每一个都正确返回：那串跨多行、没有标签的账单地址被收成一个字段，两个空白字段（salesperson 和 ref）正确地返回 null，收据上的每一个数字都一分不差。

[![sroie_combined](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/m3CfHgYlaDZ9srzt2X99_.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/m3CfHgYlaDZ9srzt2X99_.png)

在一张 FUNSD 的复印差异表上——十二个 boolean 字段的清单，其中一组嵌套了五个子选项——模型恰好把唯一被勾选的那一格（原件质量差，旁边手写着 "faded"）标成 true，其余十一个标成 false，与表单完全一致。它还正确读出了页面上手写的 Bates ID，并对留空的两个字段返回 null。

[![funsd_combined](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/GRHwR5tiDzDKVUtMotsAb.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/GRHwR5tiDzDKVUtMotsAb.png)

## 质量与成本，同时拿到

一个 20 亿参数的模型拿到 0.834 分，高于我们测试过的每一种前沿配置，从 0.816 的 Claude Opus 5 到 0.741 的 GPT-5.6 Luna，同时跑在单张 L40S 上，每次抽取的成本都比对比里的每一个 API 更低。质量更高、成本更低，在同一份基准上、同一次运行里量出来的。

这不是我们第一次量这件事。我们的 OCR 论文把第一版 DharmaOCR-LITE——一个 30 亿参数的模型——放到了巴西葡语上测试过的每一个商业前沿 API 之上；三个月后，更新的、资源更雄厚的模型来了，差距仍然成立。现在，一个 20 亿参数的模型在字段抽取上做到了同样的事。每一个结果都为我们创立 Dharma-AI 时那个论断再添一分证据：在一项有边界的任务上，一个贴近该任务训练的小模型，会打赢被要求以通用方式做同一件事的前沿模型。在这份基准上，跑起来的成本还低了 6 到 147 倍。

参数量决定天花板，训练决定模型在你的任务上能摸到多高。你的业务不需要手头最大的那个模型。它需要一个为你的问题训练过的模型。
