# 在生产环境中优化你的 LLM

Patrick von Platen（patrickvonplaten）

本文另有中文版本 [简体中文](https://huggingface.co/blog/zh/optimize-llm)。

***注***：*本博客也作为 [Transformers](https://huggingface.co/docs/transformers/llm_tutorial_optimization) 的文档页提供。*

像 GPT3/4、[Falcon](https://huggingface.co/tiiuae/falcon-40b) 和 [LLama](https://huggingface.co/meta-llama/Llama-2-70b-hf) 这样的大语言模型（LLM）在应对以人为中心的任务方面能力飞速提升，正在确立自己作为现代知识型行业必备工具的地位。然而，把这些模型部署到真实任务中仍然有挑战：

- 要展现接近人类的文本理解与生成能力，LLM 目前需要由数十亿参数构成（见 [Kaplan et al](https://arxiv.org/abs/2001.08361)、[Wei et. al](https://arxiv.org/abs/2206.07682)）。这相应地放大了推理对内存的需求。
- 在许多真实任务中，需要给 LLM 提供大量的上下文信息。这要求模型在推理时能管理非常长的输入序列。

这些挑战的核心在于增强 LLM 的算力与内存能力，尤其是在处理庞大的输入序列时。

在这篇博客里，我们会过一遍截至撰写本文时应对这些挑战、实现高效 LLM 部署最有效的技术：

- **更低精度**：研究表明，以更低的数值精度（即 8-bit 和 4-bit）运行，可以在不明显降低模型性能的前提下取得计算上的优势。
- **Flash Attention**：Flash Attention 是注意力算法的一个变体，不仅提供了更省内存的方式，还因优化了 GPU 内存利用率而实现了更高的效率。
- **架构创新**：考虑到 LLM 在推理时总是以相同方式使用——即用很长的输入上下文做自回归文本生成——人们提出了专门能让推理更高效的模型架构。其中最重要的架构进展是 [Alibi](https://arxiv.org/abs/2108.12409)、[Rotary embeddings](https://arxiv.org/abs/2104.09864)、[Multi-Query Attention (MQA)](https://arxiv.org/abs/1911.02150) 和 [Grouped-Query-Attention (GQA)](https://huggingface.co/blog/(https://arxiv.org/abs/2305.13245))。

Throughout 本文，我们会从张量的视角分析自回归生成。我们会深入探讨采用更低精度的利弊、对最新注意力算法做全面探索，并讨论改进的 LLM 架构。在此过程中，我们运行一些实际示例来展示每一项特性改进。

### 1. 利用更低精度的力量

LLM 的内存需求，最好通过把 LLM 看作一组权重矩阵和向量、把文本输入看作一串向量来理解。下文中的定义 *weights* 用来表示所有模型权重矩阵和向量。

在本文撰写之时，LLM 至少由几十亿参数组成。每个参数是一个小数，比如 `4.5689`，通常以 [float32](https://en.wikipedia.org/wiki/Single-precision_floating-point_format)、[bfloat16](https://en.wikipedia.org/wiki/Bfloat16_floating-point_format) 或 [float16](https://en.wikipedia.org/wiki/Half-precision_floating-point_format) 格式存储。这让我们能轻松算出把 LLM 加载进内存所需的内存量：

> 加载一个有 X 十亿参数的模型的权重，在 float32 精度下大约需要 4 * X GB 的 VRAM

如今，模型很少再以完整 float32 精度训练，而通常以 bfloat16 精度、较少以 float16 精度训练。因此经验法则变成：

> 加载一个有 X 十亿参数的模型的权重，在 bfloat16/float16 精度下大约需要 2 * X GB 的 VRAM

对于较短的文本输入（少于 1024 token），推理的内存需求主要由加载权重的内存需求主导。因此，目前我们先假设推理的内存需求等于把模型加载进 GPU VRAM 的内存需求。

举一些在 bfloat16 下加载模型大约需要多少 VRAM 的例子：

- **GPT3** 需要 2 * 175 GB = **350 GB** VRAM
- [**Bloom**](https://huggingface.co/bigscience/bloom) 需要 2 * 176 GB = **352 GB** VRAM
- [**Llama-2-70b**](https://huggingface.co/meta-llama/Llama-2-70b-hf) 需要 2 * 70 GB = **140 GB** VRAM
- [**Falcon-40b**](https://huggingface.co/tiiuae/falcon-40b) 需要 2 * 40 GB = **80 GB** VRAM
- [**MPT-30b**](https://huggingface.co/mosaicml/mpt-30b) 需要 2 * 30 GB = **60 GB** VRAM
- [**bigcode/starcoder**](https://huggingface.co/bigcode/starcoder) 需要 2 * 15.5 = **31 GB** VRAM

截至撰写本文，市场上最大的 GPU 芯片是提供 80GB VRAM 的 A100。上述大多数模型仅加载就需要超过 80GB，因此必然需要 [tensor parallelism](https://huggingface.co/docs/transformers/perf_train_gpu_many#tensor-parallelism) 和/或 [pipeline parallelism](https://huggingface.co/docs/transformers/perf_train_gpu_many#naive-model-parallelism-vertical-and-pipeline-parallelism)。

🤗 Transformers 不开箱支持 tensor parallelism，因为这要求模型架构以特定方式编写。如果你有兴趣以 tensor-parallelism 友好的方式编写模型，可以参考 [text-generation-inference 库](https://github.com/huggingface/text-generation-inference/tree/main/server/text_generation_server/models/custom_modeling)。

朴素的 pipeline parallelism 是开箱支持的。为此，只需以 `device="auto"` 加载模型，它会自动把不同的层放到可用 GPU 上，如[这里](https://huggingface.co/docs/accelerate/v0.22.0/en/concept_guides/big_model_inference)所述。不过要注意，这种朴素 pipeline parallelism 虽很有效，但并不解决 GPU 空闲的问题。为此需要更先进的 pipeline parallelism，如[这里](https://huggingface.co/docs/transformers/v4.15.0/parallelism#naive-model-parallel-vertical-and-pipeline-parallel)所述。

那如果你的 GPU 没有 32 GB VRAM 呢？人们发现，模型权重可以量化到 8-bit 或 4-bit 而不显著损失性能（见 [Dettmers et al.](https://arxiv.org/abs/2208.07339)）。模型甚至可以量化到 3 或 2 bit 并带来可接受的损失，正如近期 [GPTQ 论文](https://arxiv.org/abs/2210.17323) 所示 🤯。

不深入细节，量化方案旨在降低权重精度的同时，尽可能让模型的推理结果保持准确（*a.k.a* 尽可能接近 bfloat16）。注意量化在文本生成上效果尤佳，因为我们关心的只是选择*最可能的下一 token 集合*，并不太在意下一 token *logit* 分布的确切值。要紧的是下一 token *logit* 分布大致保持一致，使得 `argmax` 或 `topk` 操作给出相同结果。

有各种量化技术，我们这里不逐一讨论，但一般而言所有量化技术都如下运作：

- 把所有权重量化到目标精度
- 加载量化后的权重，并以 bfloat16 精度传入向量输入序列
- 动态地把权重反量化为 bfloat16，以 bfloat16 精度和它的输入向量执行计算
- 在与输入完成计算后，再把权重重新量化到目标精度。

简而言之，这意味着*输入-权重矩阵*乘法，其中 X X X 是*输入*，W W W 是权重矩阵，Y Y Y 是输出：

Y=X∗W Y = X * W Y=X∗W

在每次矩阵乘法处都被改为

Y=X∗dequantize(W);quantize(W) Y = X * \text{dequantize}(W); \text{quantize}(W) Y=X∗dequantize(W);quantize(W)

反量化和重量化在所有权重矩阵上随输入通过网络图顺序执行。

因此推理时间往往**不**会因使用量化权重而缩短，反而会增加。够了理论，我们试试！要用 Transformers 量化权重，你需要确保安装了 [`bitsandbytes`](https://github.com/TimDettmers/bitsandbytes) 库。

总体上我们看到，把 OctoCoder 以 8-bit 精度运行，所需 GPU VRAM 从 32G 降到仅 15GB，而以 4-bit 精度运行进一步把所需 VRAM 降到略高于 9GB。

4-bit 量化让模型能在像 RTX3090、V100 和 T4 这样的 GPU 上运行，这些对大多数人相当易得。

关于量化的更多信息，以及看到如何量化模型使其所需 GPU VRAM 甚至低于 4-bit，我们建议查看 [`AutoGPTQ`](https://huggingface.co/docs/transformers/main/en/main_classes/quantization#autogptq-integration%60) 实现。

> 作为结论，重要的是记住模型量化是以改善内存效率换取精度，某些情况下还换取推理时间。

如果 GPU 内存对你的用例不构成限制，往往不必考虑量化。但许多 GPU 没有量化方法根本跑不了 LLM，这种情况下 4-bit 和 8-bit 量化方案是极其有用的工具。

要了解更多使用细节，我们强烈建议查看 [Transformers 量化文档](https://huggingface.co/docs/transformers/main_classes/quantization#general-usage)。接下来我们看看如何通过更好的算法和改进的模型架构来提升算力和内存效率。

## 2. Flash Attention：一次飞跃

如今性能顶尖的 LLM 大体共享同一套基础架构，由前馈层、激活层、层归一化层，以及最关键的自注意力层组成。

自注意力层在 LLM 中之所以核心，是因为它让模型能理解输入 token 之间的上下文关系。然而，自注意力层的 GPU 内存峰值消耗，随输入 token 数（也叫*序列长度*，下文记作 N N N）在计算和内存复杂度上都呈*二次方*增长。对较短的输入序列（最多 1000 个输入 token）这不太明显，但对更长的输入序列（约 16000 个输入 token）就成了严重问题。

我们细看。对长度为 N N N 的输入 X \mathbf{X} X 计算自注意力层输出 O \mathbf{O} O 的公式是：

O=Attn(X)=V×Softmax(QKT) with Q=WqX,V=WvX,K=WkX \textbf{O} = \text{Attn}(\mathbf{X}) = \mathbf{V} \times \text{Softmax}(\mathbf{QK}^T) \text{ with } \mathbf{Q} = \mathbf{W}_q \mathbf{X}, \mathbf{V} = \mathbf{W}_v \mathbf{X}, \mathbf{K} = \mathbf{W}_k \mathbf{X} O=Attn(X)=V×Softmax(QKT) with Q=Wq​X,V=Wv​X,K=Wk​X X=(x1,...xN) \mathbf{X} = (\mathbf{x}_1, ... \mathbf{x}_{N}) X=(x1​,...xN​) 是注意力层的输入序列。投影 Q \mathbf{Q} Q 和 K \mathbf{K} K 各由 N N N 个向量组成， resulting 的 QKT \mathbf{QK}^T QKT 规模为 N2 N^2 N2。

LLM 通常有多个注意力头，因此并行做多次自注意力计算。假设 LLM 有 40 个注意力头、以 bfloat16 精度运行，我们可以算出存储 QKT \mathbf{QK^T} QKT 矩阵所需的内存为 40∗2∗N2 40 * 2 * N^2 40∗2∗N2 字节。对 N=1000 N=1000 N=1000，只需约 50 MB VRAM，但对 N=16000 N=16000 N=16000 我们需要 19 GB VRAM，而对 N=100,000 N=100,000 N=100,000 仅存储 QKT \mathbf{QK}^T QKT 矩阵就需要近 1TB。

长话短说，默认自注意力算法在大输入上下文下很快变得内存上不可承受。

随着 LLM 在文本理解与生成上不断进步，它们被应用到日益复杂的任务上。模型曾经只处理几个句子的翻译或摘要，如今要管理整页内容，要求处理极长的输入长度。

我们怎样才能摆脱大输入长度那高得离谱的内存需求？我们需要一种新的计算自注意力机制的方式，去掉 QKT QK^T QKT 矩阵。[Tri Dao et al.](https://arxiv.org/abs/2205.14135) 正是开发了这样一种新算法，叫作 **Flash Attention**。

简而言之，Flash Attention 把 V×Softmax(QKT\mathbf{V} \times \text{Softmax}(\mathbf{QK}^TV×Softmax(QKT) 计算拆开，改为通过迭代多个 softmax 计算步骤来计算较小的输出块：

Oi←sija∗Oi+sijb∗Vj×Softmax(QKi,jT) for multiple i,j iterations \textbf{O}_i \leftarrow s^a_{ij} * \textbf{O}_i + s^b_{ij} * \mathbf{V}_{j} \times \text{Softmax}(\mathbf{QK}^T_{i,j}) \text{ for multiple } i, j \text{ iterations} Oi​←sija​∗Oi​+sijb​∗Vj​×Softmax(QKi,jT​) for multiple i,j iterations

其中 sija s^a_{ij} sija​ 和 sijb s^b_{ij} sijb​ 是某些 softmax 归一化统计量，需要对每个 i i i 和 j j j 重新计算。

请注意整个 Flash Attention 其实更复杂，这里做了很大简化，因为深入太多细节超出了本文范围。欢迎读者查阅写得很好的 [Flash Attention 论文](https://arxiv.org/abs/2205.14135) 了解更多。

这里主要要点是：

> 通过跟踪 softmax 归一化统计量并使用一些巧妙的数学，Flash Attention 给出的数值输出与默认自注意力层完全相同，但内存成本只随 N N N 线性增长。

看着这个公式，人们直觉上会说 Flash Attention 一定比默认自注意力公式慢得多，因为要做更多计算。的确，Flash Attention 比普通注意力需要更多 FLOPs，因为 softmax 归一化统计量必须不断重算（感兴趣的话见[论文](https://arxiv.org/abs/2205.14135)）。

> 然而，Flash Attention 在推理上比默认注意力快得多，这来自它显著降低了对慢速、高带宽 GPU 内存（VRAM）的需求，转而聚焦更快的片上内存（SRAM）。

本质上，Flash Attention 确保所有中间读写操作都能用快速的*片上* SRAM 完成，而不必为了计算输出向量 O \mathbf{O} O 去访问较慢的 VRAM 内存。

实践中，目前绝对没有任何理由在可用时**不**使用 Flash Attention。该算法给出数学上相同的输出，而且既更快又更省内存。

我们看一个实际例子。

我们的 OctoCoder 模型现在拿到一个显著更长的输入提示词，其中包含一个所谓的*系统提示词（system prompt）*。系统提示词用来把 LLM 引导成一个更贴合用户任务的助手。下面我们用一段让 OctoCoder 成为更好编码助手的系统提示词。


## 3. LLM 架构背后的科学：为长文本输入与聊天做策略性选择

到目前为止，我们通过以下方式提升算力和内存效率：

- 把权重转换成更低精度格式
- 用更省内存和算力的版本替换自注意力算法

现在我们来看看如何修改 LLM 的架构，使其对需要长文本输入的任务最有效、最高效，例如：

- 检索增强问答，
- 摘要，
- 聊天

注意 *聊天* 不仅要求 LLM 处理长文本输入，还要求它能高效处理用户与助手（如 ChatGPT）之间的来回对话。

一旦训练完成，LLM 的基础架构很难更改，所以事先就 LLM 的任务做考量、并相应优化模型架构非常重要。模型架构里有两个组件在大输入序列下很快成为内存和/或性能瓶颈。

- 位置嵌入
- key-value 缓存

我们更详细地看看每个组件。

### 3.1 改进 LLM 的位置嵌入

自注意力把每个 token 与其他 token 建立关系。举个例子，文本输入序列 *"Hello", "I", "love", "you"* 的 Softmax(QKT) \text{Softmax}(\mathbf{QK}^T) Softmax(QKT) 矩阵可能如下：

[![](https://huggingface.co/blog/assets/163_optimize_llm/self_attn_tokens.png)](https://huggingface.co/blog/assets/163_optimize_llm/self_attn_tokens.png)

每个词 token 被赋予一个概率质量去关注所有其他词 token，从而与所有其他词 token 建立关系。例如词 *"love"* 以 5% 关注 *"Hello"*，以 30% 关注 *"I"*，以 65% 关注自身。

一个基于自注意力、但没有位置嵌入的 LLM，将很难理解文本输入彼此之间的位置。这是因为 QKT \mathbf{QK}^T QKT 算出的概率分数把每个词 token 与所有其他 token 建立关系，无论它们相对位置的距离如何，都只需 O(1) O(1) O(1) 次计算。因此，对没有位置嵌入的 LLM，每个 token 看似与其他所有 token 等距，*e.g.* 区分 *"Hello I love you"* 和 *"You love I hello"* 会很困难。

为了让 LLM 理解语序，需要一个额外的*提示*，通常以*位置编码*（或叫*位置嵌入*）的形式施加。位置编码把每个 token 的位置编码成一种 LLM 能加以利用、从而更好理解语序的数值表示。

[*Attention Is All You Need*](https://arxiv.org/abs/1706.03762) 的作者引入了正弦位置嵌入 P=p1,…,pN \mathbf{P} = \mathbf{p}_1, \ldots, \mathbf{p}_N P=p1​,…,pN​，其中每个向量 pi \mathbf{p}_i pi​ 是其位置 i i i 的正弦函数计算得到。位置编码随后被简单加到输入序列向量上 X^=x^1,…,x^N \mathbf{\hat{X}} = \mathbf{\hat{x}}_1, \ldots, \mathbf{\hat{x}}_N X^=x^1​,…,x^N​ = x1+p1,…,xN+pN \mathbf{x}_1 + \mathbf{p}_1, \ldots, \mathbf{x}_N + \mathbf{p}_N x1​+p1​,…,xN​+pN​，从而暗示模型更好地学习语序。

除使用固定位置嵌入外，其他人（如 [Devlin et al.](https://arxiv.org/abs/1810.04805)）使用了学习式位置编码，其位置嵌入 P \mathbf{P} P 在训练期间被学习。

正弦和学习式位置嵌入曾是向 LLM 编码语序的主流方法，但人们发现这些位置编码存在几个问题：

- 正弦和学习式位置嵌入都是绝对位置嵌入，*i.e.* 为每个位置 id 编码唯一嵌入：0,…,N 0, \ldots, N 0,…,N。正如 [Huang et al.](https://arxiv.org/abs/2009.13658) 和 [Su et al.](https://arxiv.org/abs/2104.09864) 所展示，绝对位置嵌入在长文本输入上导致 LLM 性能不佳。对长文本输入，让模型学习输入 token 彼此间的*相对*位置距离比学习它们的绝对位置更有利。
- 使用学习式位置嵌入时，LLM 必须在固定输入长度 N N N 上训练，这使它难以外推到比训练时更长的输入长度。

近期，能解决上述问题的相对位置嵌入变得更流行，最著名的是：

- [Rotary Position Embedding (RoPE)](https://arxiv.org/abs/2104.09864)
- [ALiBi](https://arxiv.org/abs/2108.12409)

*RoPE* 和 *ALiBi* 都主张：把语序提示给 LLM 最好直接施加在自注意力算法里，因为正是那里把词 token 彼此建立关系。更具体地，语序应通过修改 QKT \mathbf{QK}^T QKT 计算来提示。

不深入细节，*RoPE* 指出位置信息可以编码进 query-key 对，*e.g.* qi \mathbf{q}_i qi​ 和 xj \mathbf{x}_j xj​，办法是把每个向量分别按角度 θ∗i \theta * i θ∗i 和 θ∗j \theta * j θ∗j 旋转，其中 i,j i, j i,j 描述每个向量的句子位置：

q^iTx^j=qiTRθ,i−jxj. \mathbf{\hat{q}}_i^T \mathbf{\hat{x}}_j = \mathbf{{q}}_i^T \mathbf{R}_{\theta, i -j} \mathbf{{x}}_j. q^​iT​x^j​=qiT​Rθ,i−j​xj​。Rθ,i−j \mathbf{R}_{\theta, i - j} Rθ,i−j​ 是一个旋转矩阵。θ \theta θ 在训练时*不*被学习，而是被设成一个依赖训练时最大输入序列长度的预定义值。

> 这样做之后，qi \mathbf{q}_i qi​ 和 qj \mathbf{q}_j qj​ 之间的概率分数只有在 i≠j i \ne j i≠=j 时才受影响，且仅取决于相对距离 i−j i - j i−j，而与每个向量自身的具体位置 i i i 和 j j j 无关。

*RoPE* 用于当今多个最重要的 LLM，例如：

- [**Falcon**](https://huggingface.co/tiiuae/falcon-40b)
- [**Llama**](https://arxiv.org/abs/2302.13971)
- [**PaLM**](https://arxiv.org/abs/2204.02311)

作为替代，*ALiBi* 提出一个简单得多的相对位置编码方案。输入 token 彼此间的相对距离被作为一个负整数、按一个预定义的 `m` 值缩放，加到 QKT \mathbf{QK}^T QKT 矩阵每个 query-key 项上，紧接在 softmax 计算之前。

[![](https://huggingface.co/blog/assets/163_optimize_llm/alibi.png)](https://huggingface.co/blog/assets/163_optimize_llm/alibi.png)

正如 [ALiBi](https://arxiv.org/abs/2108.12409) 论文所示，这种简单的相对位置编码让模型即使在非常长的文本输入序列上也能保持高性能。

*ALiBi* 用于当今多个最重要的 LLM，例如：

- [**MPT**](https://huggingface.co/mosaicml/mpt-30b)
- [**BLOOM**](https://huggingface.co/bigscience/bloom)

*RoPE* 和 *ALiBi* 位置编码都能外推到训练时没见过的输入长度，而已有证据表明相比之下 *ALiBi* 的零样本外推比 *RoPE* 效果好得多。对 ALiBi，只需增大下三角位置矩阵的值以匹配输入序列长度。对 *RoPE*，保持训练时所用的同一 θ \theta θ 会在传入远长于训练时所见文本输入时导致糟糕结果，*c.f* [Press et al.](https://arxiv.org/abs/2108.12409)。不过社区找到了几个有效的 trick 来适配 θ \theta θ，从而使 *RoPE* 位置嵌入对外推文本输入序列也能奏效（见[这里](https://github.com/huggingface/transformers/pull/24653)）。

> RoPE 和 ALiBi 都是相对位置嵌入，不在训练时被学习，而是基于以下直觉：

- 关于文本输入的位置提示应被直接施加给自注意力层的 QKT QK^T QKT 矩阵
- LLM 应被激励去让位置嵌入彼此间保持一个恒定的*相对*距离
- 文本输入 token 彼此距离越远，其 query-value 概率越低。RoPE 和 ALiBi 都降低彼此距离远的 token 的 query-key 概率。RoPE 通过增大 query-key 向量之间的角度来减小其向量积；ALiBi 通过给向量积加上很大的负数

总之，那些被设计用于处理大文本输入任务的 LLM，最好用相对位置嵌入（如 RoPE 和 ALiBi）来训练。也注意，即便一个用 RoPE 和 ALiBi 的 LLM 只在固定长度（比如 N1=2048 N_1 = 2048 N1​=2048）上训练过，通过外推位置嵌入，它仍能在实践中用于远大于 N1 N_1 N1​ 的文本输入，比如 N2=8192>N1 N_2 = 8192 > N_1 N2​=8192>N1​。

### 3.2 key-value 缓存

LLM 的自回归文本生成运作方式是：迭代地放入一个输入序列、采样下一个 token、把下一个 token 追加到输入序列，如此继续直到 LLM 产生一个标志生成结束的信号 token。

请参考 [Transformer 生成文本教程](https://huggingface.co/docs/transformers/llm_tutorial#generate-text) 来获得自回归生成如何工作的更直观解释。

我们运行一个简短代码片段来看看自回归在实践中如何工作。我们只取最可能的下一个 token，用 `torch.argmax`。

```
input_ids = tokenizer(prompt, return_tensors="pt")["input_ids"].to("cuda")

for _ in range(5):
  next_logits = model(input_ids)["logits"][:, -1:]
  next_token_id = torch.argmax(next_logits,dim=-1)

  input_ids = torch.cat([input_ids, next_token_id], dim=-1)
  print("shape of input_ids", input_ids.shape)

generated_text = tokenizer.batch_decode(input_ids[:, -5:])
generated_text
```

**输出**：

```
shape of input_ids torch.Size([1, 21])
shape of input_ids torch.Size([1, 22])
shape of input_ids torch.Size([1, 23])
shape of input_ids torch.Size([1, 24])
shape of input_ids torch.Size([1, 25])
[' Here is a Python function']
```

如我们所见，每次我们都用刚采样的 token 增加文本输入 token。

除极少数例外，LLM 都用[因果语言建模目标](https://huggingface.co/docs/transformers/tasks/language_modeling#causal-language-modeling)训练，因此会掩码注意力分数的上三角矩阵——这就是为什么上面两张图里注意力分数留空（*a.k.a* 概率为 0）。关于因果语言建模的快速回顾，可参考 [*Illustrated Self Attention blog*](https://jalammar.github.io/illustrated-gpt2/#part-2-illustrated-self-attention)。

因此，token *从不*依赖于未来的 token，更具体地说，qi \mathbf{q}_i qi​ 向量从不与任何 j>i j > i j>i 的 key、value 向量 kj,vj \mathbf{k}_j, \mathbf{v}_j kj​,vj​ 建立关系。取而代之，qi \mathbf{q}_i qi​ 只关注先前 key-value 向量 km<i,vm<i , for m∈{0,…i−1} \mathbf{k}_{m < i}, \mathbf{v}_{m < i} \text{ , for } m \in \{0, \ldots i - 1\} km<i​,vm<i​ , for m∈{0,…i−1}。为减少不必要的计算，人们可以为所有先前的时间步缓存每一层的 key-value 向量。

接下来，我们会让 LLM 通过检索并在每次前向传播中转发来使用 key-value 缓存。在 Transformers 里，我们可以通过给 `forward` 调用传 `use_cache` 标志来检索 key-value 缓存，并随后把它与当前 token 一起传入。

```
past_key_values = None # past_key_values is the key-value cache
generated_tokens = []
next_token_id = tokenizer(prompt, return_tensors="pt")["input_ids"].to("cuda")

for _ in range(5):
  next_logits, past_key_values = model(next_token_id, past_key_values=past_key_values, use_cache=True).to_tuple()
  next_logits = next_logits[:, -1:]
  next_token_id = torch.argmax(next_logits, dim=-1)

  print("shape of input_ids", next_token_id.shape)
  # past_key_values are a tuple (one for each Transformer layer) of tuples (one for the keys, one for the values)
  # cached keys and values each are of shape (batch_size, num_heads, sequence_length, embed_size_per_head)
  # hence let's print how many cached keys and values we have for the first Transformer layer
  print("number of cached keys of the first Transformer layer", len(past_key_values[0][0][0,0,:,:]))
  print("number of cached values of the first Transformer layer", len(past_key_values[0][1][0,0,:,:]))
  
  generated_tokens.append(next_token_id.item())

generated_text = tokenizer.batch_decode(generated_tokens)
generated_text
```

**输出**：

```
shape of input_ids torch.Size([1, 1])
number of cached keys of the first Transformer layer: 20
number of cached values of the first Transformer layer: 20
shape of input_ids torch.Size([1, 1])
number of cached keys of the first Transformer layer: 21
number of cached values of the first Transformer layer: 21
shape of input_ids torch.Size([1, 1])
number of cached keys of the first Transformer layer: 22
number of cached values of the first Transformer layer: 22
shape of input_ids torch.Size([1, 1])
number of cached keys of the first Transformer layer: 23
number of cached values of the first Transformer layer: 23
shape of input_ids torch.Size([1, 1])
number of cached keys of the first Transformer layer: 24
number of cached values of the first Transformer layer: 24
[' Here', ' is', ' a', ' Python', ' function']
```

可以看到，使用 key-value 缓存时，文本输入 token *并不*增长长度，而始终是单个输入向量。而 key-value 缓存的长度在每个解码步则增加一个。

> 使用 key-value 缓存意味着 QKT \mathbf{QK}^T QKT 本质上简化为 qcKT \mathbf{q}_c\mathbf{K}^T qc​KT，其中 qc \mathbf{q}_c qc​ 是当前传入 token 的 query 投影，它始终只是一个向量。

使用 key-value 缓存有两个好处：

- 显著提升计算效率，因为相比计算完整的 QKT \mathbf{QK}^T QKT 矩阵做了更少计算，从而提升推理速度
- 所需最大内存不再随生成 token 数二次增长，而只线性增长。

> 人们应当始终使用 key-value 缓存，因为它给出相同结果，并对较长输入序列带来显著加速。当使用文本 pipeline 或 generate 方法时，Transformers 默认启用 key-value 缓存。

注意 key-value 缓存对像聊天这种需要多轮自回归解码的应用尤其有用。我们看一个例子。

```
User: How many people live in France?
Assistant: Roughly 75 million people live in France
User: And how many are in Germany?
Assistant: Germany has ca. 81 million inhabitants
```

在这段对话里，LLM 运行了两次自回归解码：

- 第一次，key-value 缓存为空，输入提示词是 `"User: How many people live in France?"`，模型自回归生成 `"Roughly 75 million people live in France"`，同时每个解码步都在增大 key-value 缓存。
- 第二次输入提示词是 `"User: How many people live in France? \n Assistant: Roughly 75 million people live in France \n User: And how many in Germany?"`。得益于缓存，前两句的所有 key-value 向量已经算好。因此输入提示词只包含 `"User: And how many in Germany?"`。在处理这个较短输入提示词时，它算得的 key-value 向量被拼接到第一次解码的 key-value 缓存上。第二次助手的回答 `"Germany has ca. 81 million inhabitants"` 随后用由 `"User: How many people live in France? \n Assistant: Roughly 75 million people live in France \n User: And how many are in Germany?"` 的已编码 key-value 向量组成的缓存自回归生成。

这里有两点要注意：

- 为聊天中部署的 LLM 保留所有上下文至关重要，这样 LLM 能理解对话中所有先前的上下文。例如上面的例子里，当用户问 `"And how many are in Germany"` 时，LLM 需要理解用户指的是人口。
- key-value 缓存在聊天中极其有用，因为它让我们能持续增长已编码的聊天历史，而不必从头重新编码聊天历史（正如用 encoder-decoder 架构时那样）。

不过有一个坑。虽然 QKT \mathbf{QK}^T QKT 所需峰值内存显著降低，但在长输入序列或多轮聊天下，把 key-value 缓存保持在内存里可能变得非常耗内存。记住 key-value 缓存需要为所有先前输入向量 xi, for i∈{1,…,c−1} \mathbf{x}_i \text{, for } i \in \{1, \ldots, c - 1\} xi​, for i∈{1,…,c−1} 存储 key-value 向量，为所有自注意力层、所有注意力头都要存。

我们来计算本文所用 LLM `bigcode/octocoder` 的 key-value 缓存需要存多少浮点值。浮点值数量等于两倍序列长度乘以注意力头数乘以注意力头维度再乘以层数。在假设输入序列长度 16000 下为我们的 LLM 算得：

```
config = model.config
2 * 16_000 * config.n_layer * config.n_head * config.n_embd // config.n_head
```

**输出**：

```
7864320000
```

约 80 亿浮点值！以 `float16` 精度存储 80 亿浮点值需要约 15 GB 内存，约相当于模型权重本身的一半！研究者提出了两种方法，能显著降低存储 key-value 缓存的内存成本：

- [Multi-Query-Attention (MQA)](https://arxiv.org/abs/1911.02150)

Multi-Query-Attention 在 Noam Shazeer 的 *Fast Transformer Decoding: One Write-Head is All You Need* 论文中提出。正如标题所言，Noam 发现，与其用 `n_head` 套 key-value 投影权重，可以用一对跨所有注意力头共享的 head-value 投影权重，而模型性能不会显著退化。

> 通过使用单对 head-value 投影权重，key-value 向量 ki,vi \mathbf{k}_i, \mathbf{v}_i ki​,vi​ 在所有注意力头上必须相同，这反过来意味着我们只需在缓存里存 1 对 key-value 投影，而非 n_head 对。

由于大多数 LLM 使用 20 到 100 个注意力头，MQA 显著降低了 key-value 缓存的内存消耗。对本文所用的 LLM，在输入序列长度 16000 下我们能把所需内存消耗从 15 GB 降到不足 400 MB。

除内存节省外，MQA 也带来计算效率的提升，如下所述。在自回归解码中，较大的 key-value 向量需要被反复加载、与当前 key-value 向量对拼接，然后在每一步送入 qcKT \mathbf{q}_c\mathbf{K}^T qc​KT 计算。对自回归解码，不断重新加载所需的内存带宽会成为严重的耗时瓶颈。通过减小 key-value 向量的尺寸，需要访问的内存更少，从而减少内存带宽瓶颈。更多细节请参考 [Noam 的论文](https://arxiv.org/abs/1911.02150)。

这里要理解的关键点是，把 key-value 注意力头数减少到 1，只有在用 key-value 缓存时才有意义。不使用 key-value 缓存的单次前向传播的模型峰值内存消耗保持不变，因为每个注意力头仍有唯一的 query 向量，所以每个注意力头仍有不同的 QKT \mathbf{QK}^T QKT 矩阵。

MQA 已被社区广泛采用，现被许多流行 LLM 使用：

- [**Falcon**](https://huggingface.co/tiiuae/falcon-40b)
- [**PaLM**](https://arxiv.org/abs/2204.02311)
- [**MPT**](https://huggingface.co/mosaicml/mpt-30b)
- [**BLOOM**](https://huggingface.co/bigscience/bloom)

另外，本文所用的 checkpoint `bigcode/octocoder` 也用了 MQA。

- [Grouped-Query-Attention (GQA)](https://arxiv.org/abs/2305.13245)

Grouped-Query-Attention 由 Google 的 Ainslie 等人提出，他们发现使用 MQA 相比使用多 key-value head 投影常常导致质量退化。该论文主张，通过不那么激进地减少 query head 投影权重，能保留更多模型性能。与其只用单对 key-value 投影权重，应使用 `n < n_head` 套 key-value 投影权重。通过把 `n` 选成远小于 `n_head` 的值（如 2、4 或 8），几乎可以保留 MQA 的全部内存和速度收益，同时牺牲更少的模型容量、因而更少性能。

此外，GQA 的作者发现已有的模型 checkpoint 可以被*uptrain* 成 GQA 架构，只需原始预训练算力的约 5%。虽然 5% 的原始预训练算力仍可能是庞大数字，但 GQA *uptraining* 让已有 checkpoint 能为更长输入序列所用。

GQA 是近期才提出的，因此在本文撰写时采用较少。GQA 最重要的应用是 [Llama-v2](https://huggingface.co/meta-llama/Llama-2-70b-hf)。

> 作为结论，如果 LLM 部署时配合自回归解码、且需要处理大输入序列（如聊天），强烈建议使用 GQA 或 MQA。

## 结论

研究社区不断提出更新颖的方式，为越来越大的 LLM 加速推理。作为一个有前景的研究方向的例子是[投机解码 speculative decoding](https://arxiv.org/abs/2211.17192)，其中"容易的 token"由更小更快的语言模型生成，只有"难的 token"才由 LLM 本身生成。深入展开超出本文范围，但可以读这篇[不错的博客](https://huggingface.co/blog/assisted-generation)。

像 GPT3/4、Llama-2-70b、Claude、PaLM 这样的大型 LLM 能在 [Hugging Face Chat](https://huggingface.co/chat/) 或 ChatGPT 这样的聊天界面里跑得这么快，很大程度上归功于上面提到的精度、算法和架构的改进。展望未来，像 GPU、TPU 这样的加速器只会更快并允许更多内存，但人们仍应始终确保使用最佳的可用算法和架构，以获得最大的性价比 🤗
