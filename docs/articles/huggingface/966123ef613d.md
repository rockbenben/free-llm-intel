# Hugging Face Inference Endpoints、Jobs 和 Buckets 如何为 Papers with Code 的搜索提供动力

Niels Rogge

nielsr

3 个月前，我们启动了 [Papers with Code](https://paperswithcode.co) 的[复活计划](https://www.reddit.com/r/MachineLearning/comments/1tgmwqr/reviving_paperswithcode_by_hugging_face_p/)（另见[公告推文](https://x.com/NielsRogge/status/2056366395605078252)）。它的目标是让开放 AI 研究变得触手可及、易于消化：人们可以轻松找到论文相关的产出物，查看 AI 各领域的最先进水平（SOTA），分享有趣的研究并在彼此的工作上继续建设。换句话说，它的使命是为催生下一篇 [Transformer](https://paperswithcode.co/paper/1706.03762) 的研究浪潮提供动力。

当然，要让 AI 研究触手可及，需要一个强大的搜索引擎，让人和智能体都能通过网站或 `pwc search` [CLI 命令](https://github.com/huggingface/pwc-cli)快速找到相关的、相近的工作——智能体还可以通过 [Skill](https://github.com/huggingface/pwc-cli/blob/main/standalone_cli/SKILL.md) 使用它。

需要强调的是，搜索研究和搜索普通文本并不完全一样。一个好用的论文搜索引擎应该能找到精确的标题或 arXiv ID，也应该能理解"small language models for code generation"这种查询——即使这些词并没有同时出现在某篇论文里。它要能识别"the original BERT paper"是一个导航式请求，能容忍残缺的标题和拼写错误，还要在模型服务处于冷启动或暂时不可用时快速给出响应。

查询 DINO 时 Papers with Code 的搜索结果。

我们为 [Papers with Code](https://paperswithcode.co) 构建了这样一个**混合检索（hybrid search）**系统。这也源自我们在 [ML6](http://ml6.eu/) 的既有经验——我们曾为客户开发基于 [RAG](https://paperswithcode.co/paper/2005.11401) 的系统。实践表明，混合搜索通常优于纯关键词或纯向量搜索系统，因为它取两者之长（更多信息见[这篇博客](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/azure-ai-search-outperforming-vector-search-with-hybrid-retrieval-and-reranking/3929167)）。关键词搜索能找到精确提及，向量搜索则能找到更模糊、语义相近的词。注意，[reranker](https://www.pinecone.io/learn/series/rag/rerankers/)（也叫 cross-encoder）可以进一步改善结果，但也会带来额外开销和延迟。

混合检索优于纯关键词和纯向量搜索。图片来自 Microsoft，

Azure AI Search: Outperforming vector search with hybrid retrieval and reranking

(2023)。

Papers with Code 依赖 PostgreSQL 数据库，它的全文本搜索能力提供了快速的词法基线。稠密 embedding 方面，用 [pgvector](https://github.com/pgvector/pgvector) 增加语义召回，再用[倒数排名融合（reciprocal rank fusion, RRF）](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)算法把两路合并。稠密 embedding 用到了三个 Hugging Face 服务：

- [Hugging Face Jobs](https://huggingface.co/docs/hub/jobs)：提供可弹性的 GPU 算力，用于给论文语料做 embedding。
- [Hugging Face Storage Buckets](https://huggingface.co/docs/hub/storage-buckets)：在数据库、实验和 Jobs 之间提供持久的数据交接。
- [Hugging Face Inference Endpoints](https://huggingface.co/docs/inference-endpoints/index)：为在线查询和增量更新提供低延迟 embedding。

如今，这套系统维护着来自 [arXiv](https://arxiv.org/) 和 [Daily Papers](https://hf.co/papers) 的 11 万多篇在架论文的 embedding。本文介绍它的架构、背后的设计决策，以及把它推上生产过程中的经验教训。

## TL;DR

我们刻意把搜索拆成离线的语料构建和在线的搜索服务两部分：

离线语料构建与在线混合搜索流水线的架构。

昂贵、面向吞吐的工作跑在 Jobs 上，持久产物放在 Bucket 里，请求路径上只留下很小的查询 embedding 这一步，挡在一个受保护的 Inference Endpoint 后面服务于在线搜索。如果该 endpoint 冷启动、繁忙或不健康，搜索会立即回退到全文本检索。这种拆分让系统既强大又快。

## 从一份严格的 embedding 契约开始

embedding 流水线常常以微妙的方式出错：模型 revision 变了，query 和 document 的提示用混了，向量截断方式不一致，或者更新过的摘要与已存储的向量对不上了。

我们的做法是把 embedding 格式当作带版本的 API 来对待。每篇论文都编码为：

```
normalized title + "\n\n" + normalized abstract
```

对每一代向量，我们都记录：

- 模型仓库和精确的 revision；
- 输出维度；
- 输入格式版本；
- 输入是 query 还是 document；
- 归一化方法；
- 源标题与摘要的内容哈希。

我们的生产向量代使用 [`Qwen/Qwen3-Embedding-0.6B`](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)，钉住精确 revision，输出 256 维、L2 归一化的向量。选模型时参考了 [MTEB leaderboard](https://huggingface.co/spaces/mteb/leaderboard)——比较 embedding 模型的首选基准。注意，像 Qwen3 这样的新 embedding 模型支持两个新特性：

- 可以指定**动态 embedding 尺寸**，在质量与速度/存储成本之间做取舍。Qwen 系模型称之为 "MRL"，即 [Matryoshka Representation Learning](https://paperswithcode.co/paper/2205.13147)（俄罗斯套娃表示学习）的缩写，详细介绍见[这里](https://huggingface.co/blog/matryoshka)。我们选了 256 维的 embedding 尺寸来保证搜索速度。
- 可以提供**指令提示**。Qwen embedding 模型支持 `document` 提示（我们用它给论文编码），在线搜索则用 `query` 提示（给用户查询编码）。

这份契约贯穿一个 embedding 的全程：从导出、GPU 推理，进 PostgreSQL，直到在线检索。

## Jobs 把数据库快照变成向量语料

全语料 embedding 是典型的批处理负载：需要 GPU 的时间相对短、追求高吞吐、两次运行之间不应占用资源。[Hugging Face Jobs](https://huggingface.co/docs/huggingface_hub/guides/jobs) 很契合这种形态：一个 Job 由一条命令、一个[硬件规格](https://huggingface.co/docs/hub/main/en/jobs-pricing#pricing)和可选的 Docker 镜像定义，还能运行用 [uv](https://docs.astral.sh/uv/) 编写的脚本，依赖直接在文件里声明。

我们的语料构建从一个可重复读的 PostgreSQL 快照中导出每篇论文的最新版本。导出程序流式写行、而不是把整个目录加载进内存，输出有界的 JSONL 分片，并生成一份包含行数与 SHA-256 校验和的清单（manifest）。

我们把这个不可变的 run 目录同步到一个私有 [Storage Bucket](https://huggingface.co/docs/hub/storage-buckets)，然后用 [hf-mount](https://github.com/huggingface/hf-mount) 把 Bucket 直接挂载进一个 `l4x1` Job（一块 NVIDIA L4 GPU，24GB 显存）。从 worker 的视角看，它就是一个文件系统：

```
hf jobs uv run \
  --flavor l4x1 \
  --timeout 6h \
  --volume hf://buckets/OWNER/pwc-paper-embeddings:/bucket \
  embed_papers_job.py \
  --input /bucket/runs/RUN_ID/input \
  --output /bucket/runs/RUN_ID/output \
  --model Qwen/Qwen3-Embedding-0.6B \
  --revision MODEL_REVISION \
  --dimensions 256 \
  --allow-matryoshka
```

Worker 会：

- 校验输入清单和每个分片的校验和；
- 加载钉住的模型 revision；
- 按长度给文本排序以减少 padding；
- 分批调用 `encode_document`（如[模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)所述）；
- GPU 显存不够时自动缩小批大小；
- 把 [Matryoshka 表示](https://huggingface.co/blog/matryoshka)截断到 256 维并归一化；
- 以原子方式写入 float16 的 Parquet 分片；并
- 记录吞吐、包版本、硬件、显存峰值、行数和输出校验和。

每个完成的分片都有自己的标记文件，重启的 Job 可以跳过已验证的工作。这对大语料很有用：重试就只是继续干活，而不是覆盖已有的 embedding。

在 5,000 篇论文的试点中，Qwen Job 在 L4 GPU 上以 1024 维大约每秒编码 75 篇。同一次计算可以确定性地物化成 512 维和 256 维，因此我们不用再花钱推理就能对比存储与检索的取舍。

## Buckets 是结缔组织

[Storage Buckets](https://huggingface.co/docs/hub/storage-buckets) 是 Hub 上可变的、类 S3 的对象存储，为 AI 负载优化。可以用 `hf://buckets/...` 路径访问，也可以在 Jobs 中以读写方式[挂载](https://github.com/huggingface/hf-mount)，无需另行开发存储集成。

对我们来说，Bucket 不只是放向量的地方，它是三个生命周期不同的系统之间的边界：

- 生产数据库导出源记录；
- 短时存在的 Jobs 消费这些记录并产出向量；
- 导入器在校验结果之后才触碰搜索索引。

我们把产物组织在不可变的 run 前缀之下：

```
runs/<run-id>/
├── input/
│   ├── manifest.json
│   └── papers-*.jsonl
└── output/
    ├── manifest.json
    ├── embeddings-*.parquet
    └── embeddings-*.complete.json
```

Bucket 本身刻意是可变的，所以"不可变"是应用层规则：run ID 一旦被写入永不覆盖，每个产物都有清单和校验和覆盖。

这带来几个有用的性质：

- **可复现：** 我们可以把数据库里的某一代向量追溯到确切的语料快照、模型 revision 和一组产物。
- **安全重试：** Jobs 可以在同一 run 前缀内从已完成的分片继续。
- **便宜的实验：** 多个模型或多个维度可以复用同一份经过验证的输入快照。
- **受控上线：** 导入一代向量不等于启用它，我们先验证覆盖率并构建它的索引。
- **简单回滚：** 上一代及其产物会一直保留，直到新的被证明稳定。

只有在导入器重新核验了 schema、校验和、维度、归一化、唯一论文 ID 和当前内容哈希之后，我们才把向量装载进 PostgreSQL。随后为新的一代单独构建 [HNSW](https://en.wikipedia.org/wiki/Hierarchical_navigable_small_world) 索引，只有当每一篇在架合格论文都被覆盖时，才原子地把它标记为激活（HNSW 就是支撑快速向量搜索的基于图的算法）。

## Inference Endpoints 把语义搜索放上请求路径

批处理 embedding 解决了检索的文档侧。用户查询仍需要在请求时用同一份模型契约做 embedding。

我们把钉住的模型部署为一个带认证的 [Inference Endpoint](https://huggingface.co/docs/inference-endpoints/index)，后端是 [Text Embeddings Inference (TEI)](https://github.com/huggingface/text-embeddings-inference)。这个 endpoint 接受查询文本，用模型的 `query` 提示返回归一化后的 256 维向量。注意这里也可以选择 [vLLM](https://github.com/vllm-project/vllm) 或 [SGLang](https://github.com/sgl-project/sglang)。

Papers with Code 查询 embedding 模型的 Hugging Face Inference Endpoint。

API 随后在激活的 pgvector 代上做余弦距离搜索：

```
SELECT paper_id,
       embedding <=> CAST(:query_vector AS halfvec(256)) AS distance
FROM paper_embeddings
WHERE generation_id = :active_generation
ORDER BY embedding <=> CAST(:query_vector AS halfvec(256))
LIMIT 50;
```

HNSW 索引让这个查找保持飞快。在 5,000 篇论文的试点中，256 维的 Qwen 索引相对精确搜索达到 0.9955 的 Recall@20，HNSW 查找延迟 p50 为 1.31 ms、p95 为 2.21 ms。它的表和索引只用了 1024 维版本约 27% 的存储，而在这个测试中基本保住了同样的 ANN 召回率。

该 Endpoint 配置为最多 1 个副本，空闲时可以[缩容到零](https://huggingface.co/docs/inference-endpoints/guides/autoscaling)。这是个好用的成本杠杆——没有用量就不花钱。但这也意味着冷启动必须被纳入应用设计，而不是当作偶发事件，因为 endpoint 从启动到能服务需要一些时间。

因此我们的查询客户端有刻意严格的行为：

- 生产环境 1 秒超时；
- 非阻塞的并发上限；
- 对响应维度、数值有限性和范数做校验；
- 一个按查询和 embedding 代数为键的短时缓存；
- 反复失败后的熔断器；以及
- 日志里没有原始查询文本，只有归一化后的指纹。

如果 endpoint 正在扩容、超时、返回畸形向量，或没有可用并发，我们就立刻跳过语义分支。用户拿到的还是词法结果，而不是等在一个不可靠的依赖上。

Inference Endpoints 运行得非常可靠，还带有漂亮的 dashboard，关键分析一目了然。

Inference Endpoint 的分析面板：请求量、错误、延迟与副本状态。

## 混合检索强于任何一个单独分支

对每个查询，词法分支用带权重的 PostgreSQL 全文本检索最多召回 50 个候选；语义分支从 pgvector 最多召回 50 个候选。

我们用带权重的倒数排名融合（RRF）合并两路的排名：

score(d) = Σ_{r ∈ {lexical, semantic}} w_r / (k + rank_r(d))

RRF 简单而稳健，因为它融合的是排名而不是两套不同量纲的分数。基本直觉是：如果一篇论文在词法分支和语义分支都排得靠前，它被混合搜索排到前面的机会就更大。我们目前两路权重相等，`k = 60`（k 是 RRF 算法的"排名常数"超参数）。

稠密检索提升概念性查询的召回；全文本检索在精确术语、标识符和罕见名称上依旧出色。我们在融合排名之上还保留了确定性的身份行为：

- 精确标题和 arXiv ID 保持在最上面；
- [方法分类体系](https://paperswithcode.co/methods)能识别"the original BERT paper"这类导航式搜索；
- 残缺标题和有限的拼写错误使用保守的三元组（trigram）候选；
- 含糊的模糊匹配宁可不给结果，也不硬凑一个错的。

注意：混合搜索并非永远是最佳选项。建议先用关键词搜索作为便宜快速的选择，确认语义和/或混合搜索确实能带来合理的检索质量提升之后再加上去。还可以在关键词/语义/混合检索之后接一个 reranker 进一步提升搜索质量，例如使用 [Qwen3-Reranker](https://huggingface.co/collections/Qwen/qwen3-reranker) 这类模型。

## 一个 Endpoint，两条更新路径

庞大的初始语料由 Jobs 完成 embedding，但 Papers with Code 是持续变化的：新论文到达、摘要被更正、arXiv 新版本成为当前版本。

为少量变更行启动一个 GPU Job 会带来不必要的启动和编排开销。取而代之的是一个每小时的增量进程，它挑选缺失或内容发生变化的论文，把一份有界的增量发给同一个 TEI Endpoint——这次用 `document` 提示。

每轮最多处理 500 篇论文，按 16 条一批。写入 embedding 之前，会锁定源行并再次核对内容哈希。如果论文在推理期间变了，那个向量就被丢弃，留到下一轮处理。

这样我们就有了一个合理的分工：

- **Jobs** 负责全量重建、新模型代和大规模回填。
- **Inference Endpoints** 负责交互式查询 embedding 和小规模的增量文档更新。
- **Buckets** 保存大型构建的产物，让这些构建可续跑、可审计。

每小时路径让激活的索引与线上目录保持接近，同时不把在线 endpoint 变成无界的批处理器。

## 相关论文几乎免费

同一套文档 embedding 还为每篇论文页面的"相关论文"推荐供能。

[SenseNova-U1](https://paperswithcode.co) 页面的相关论文。

因为源论文已有存好的向量，相关论文检索在请求时不需要任何模型调用——只是对激活向量代的一次最近邻查询。如果某个向量暂时缺失，应用可以使用之前的 arXiv 版本，或者用现有的任务/引用回退来补齐结果。引用数据通过 [Semantic Scholar API](https://www.semanticscholar.org/product/api) 获取，我们还做了 [`s2-cli`](https://github.com/huggingface/s2-cli)——一个查询其引用图的命令行工具，后者被 [https://paperswithcode.co/chat](https://paperswithcode.co/chat) 的智能体使用。

## 我们学到了什么

### 1. 把吞吐型工作和延迟敏感型工作分开

语料 embedding 和查询 embedding 用同一个模型，但它们是两个不同的基础设施问题。Jobs 追求吞吐和有界成本；Inference Endpoints 追求可用性和请求延迟。

### 2. 让存储成为计算与生产之间的显式契约

Bucket 在计算与生产之间提供了显式交接。带校验和的产物在数据进入生产索引之前形成一个可审查的边界。

### 3. 钉住的不该只是模型名

revision、维度、提示、归一化和输入格式化器都会影响检索。把它们存在一起，并在所有环节校验。

### 4. 为冷启动做设计

流量时有时无时，缩容到零很有价值——但前提是产品有快速的回退方案。混合搜索天然给了我们这个回退：词法搜索自己就永远有用。

### 5. 更小的向量可以是一种系统特性

Matryoshka embedding 让我们把质量、内存、索引大小和延迟当作同一个取舍来评估。在我们的试点中，256 维保住了 ANN 召回，而相对 1024 维显著缩减了存储。

### 6. 激活应该波澜不惊

新的一代在旁边导入、独立建索引、检查覆盖完整且是最新内容，然后原子地激活。回滚是一次配置变更，而不是一场紧急重算。
