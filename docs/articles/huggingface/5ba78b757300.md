在[上一篇博文](https://huggingface.co/blog/ibm-research/altk-evolve-sldd/)中，我们把 **[ALTK-Evolve](https://agenttoolkit.github.io/altk-evolve/)** 与 [ACE](https://arxiv.org/abs/2510.04618) 做了对比，展示了*如何*交付 agent 自蒸馏的准则——每个任务检索少量 vs. 注入全量——会同时驱动准确率与成本。本篇退回到更早的问题：*应该给多少*？

给 agent 配备 agentic memory 听起来很简单：从它过去的工作里蒸馏经验教训、放回上下文，经验更多就该表现更好。但现实并非总是如此。当我们把评测扩展到 **8 个模型**——从 30B 稠密模型到前沿专有系统——有一条发现格外醒目：

> Agentic memory 不是一个你打开就用的功能开关，而是需要按模型校准的剂量。

**TL;DR**

- **ALTK-Evolve** 让 agent 从自己的历史轨迹中学习：蒸馏出可复用的准则并在推理时注回，不需要更新权重，也不需要人工标注。
- **正确剂量因模型层级而异**：有余力的强模型要全量准则集；弱模型最好是紧凑核心加按任务检索；饱和模型则没有可测量的收益。
- **精选检索可以同时是最准也最便宜的方案**：gpt-oss-120b 在仅 +5% token 的代价下任务完成率提升 +16.1pp——而 prompt caching 让全量准则集在生产中也负担得起。

## 关键洞见：剂量取决于能力

并非所有模型都受益于同样多的记忆。在横跨能力谱系的 8 个模型中，我们观察到三种反复出现的模式：

- **有余力的强模型**要全量准则集——包括罕见边角案例的教训。它们有容量去吸收并运用全部内容。DeepSeek-V3.2（671B MoE）在拿到全量自挖准则集后，任务完成率提升 **+9.5 个百分点**。
- **较小或较弱的模型会被大准则集淹没。** 对它们来说，一个紧凑、高置信度的核心加上每任务检索的少量相关准则效果最好。gpt-oss-120b（117B MoE）用这种选择性方案提升了 **+16.1pp**——而全量准则集收益更低*且*多花约 50% 的 token。
- **已经饱和的模型没有可测量收益。** 我们称之为饱和模式——这个标签描述的是我们的观察，而非已被证实的因果。模型可能本就接近这些任务的上限，准则可能没命中它剩余的失败点，或者它没能有效运用这些指引。GLM-5（745B MoE）在我们的运行中属于此类。

*决定一个模型落入哪种模式的，并不只是参数量。* 基准余量、上下文窗口大小、架构、准则质量、任务分布，看起来都会影响模型的落点，而分离这些因素仍是进行中的工作。但无论机理如何，实用结论都成立：**正确的记忆剂量取决于模型，而我们可以校准它。**

## 学习发生在模型周围，而不是模型内部

这里的「记忆」不是重放过去的对话记录，而是一个**准则集**——有效的策略、要避免的错误、边角案例——从 agent 自己的历史轨迹中蒸馏而来。循环很直白：

- Agent 尝试任务并产生轨迹。
- ALTK-Evolve 从成功与失败的运行中提取行为准则。
- 把这些准则整理成一个可复用的集合。
- 推理时，agent 收到全量准则集或按任务相关的选子集。

不更新任何模型权重。学习循环改变的是*agent 可获得的指引*，而不是底层模型——这正是它采用成本低、并能跨我们测试的 8 个模型移植的原因。

## 全谱系的结果

我们在 **AppWorld** 上评测——585 个多步骤任务（168 个 `test_normal` + 417 个 `test_challenge`），横跨 9 个模拟应用（日历、消息、支付等）。任务有两种打分方式：agent 是否完整完成每个任务（**TGC — Task Goal Completion**），以及某个场景的*每一个*变体是否都通过（**SGC — Scenario Goal Completion**，更严格的全有或全无标准）。完整定义见附录。

### 我们对比的三种配置

由于任何记忆研究最容易混淆的点是*上下文窗口里到底装了什么*，我们先明确定义各配置。

两种带记忆的配置都取自**同一份准则集**——通过上述循环仅从 AppWorld 的**训练划分**挖掘一次。它们之间变的只有*这份集合如何交付*——**全量准则集**每一步注入所有内容，而**精选检索**只交付选定的子集——准则的产生方式不变，且测试划分的数据从不参与构建。

| Configuration | What's in the agent's context |
| --- | --- |
| Baseline | No memory — the agent as shipped. |
| Full guideline set | Every mined guideline, injected on every ReAct step. |
| Curated retrieval | A fixed, high-confidence core of those same guidelines plus a few task-relevant ones retrieved for each task (a fixed portion + a variable portion). |

各模型挖出的准则数量取决于它自身能力，因此我们按**策略**报告配置——「全量准则集」vs.「精选检索」——而不报原始条数，后者跨模型不可比。

看 SGC 列：更严格的指标往往比 TGC 动得更多——DeepSeek 的 SGC 跃升 **+16.1pp**，而 TGC 只提升 **+9.5pp**——因为好的准则尤其能帮助 agent 通过场景的*每一个*变体，而不只是平均水平。而且这一效果在高分段并未消失：GPT-5.5 与 Opus 在 TGC 上都接近天花板，仍分别获得 **+7.2** 与 **+7.1pp 的 SGC** 提升。只要模型还有可针对的剩余失败模式，记忆就持续有回报。

## 最省钱的记忆策略也可以是最好的

一个现实问题：注入全量准则集会抬高每个 ReAct 步骤的输入，因为准则每轮都要重发。我们观察到：

| Model | Config | Tokens/task (baseline) | Tokens/task (+ memory) | Overhead |
| --- | --- | --- | --- | --- |
| DeepSeek-V3.2 | full guideline set | 148K | 263K | +78% |
| gpt-oss-120b | full guideline set | 110K | 166K | +51% |
| gpt-oss-120b | curated retrieval | 110K | 116K | +5% |

*表 1. 每任务平均 token 用量，跨 agent 步骤累积，相对无记忆 baseline 测得。*

两点结论：

- **精选检索让成本贴近 baseline。** 对弱模型——选择性方案在准确率上获胜的场景——它在成本上也获胜，鱼与熊掌兼得（gpt-oss-120b：**仅 +5% token 换来 +16.1pp TGC**）。这里的更好性能**不**需要更多推理成本。
- **记忆不会让推理循环爆炸。** DeepSeek 带记忆与不带记忆的 ReAct 步数基本相当（平均约 18–19 步），所以增加的成本是输入 token 膨胀，而非更长的轨迹。

生产中真正的效率杠杆是 **prompt caching**：准则集的静态部分在各步骤间完全相同，可以缓存，从而大幅削减有效成本。值得在工程上投入做缓存友好的 prompt 设计——保持共享的准则集前缀稳定以持续可缓存。我们还推测**上下文窗口大小**也起作用：窗口更大的模型可能更好地吸收全量准则集，而小上下文模型更受益于保持注入内容紧凑的检索。这一因素我们尚未做受控实验隔离验证。

## 记忆应当被校准，而不只是积累

教训不是把 agent 学到的一切都给它，而是给它真正用得上的那部分经验。

- 对**弱模型**，那意味着紧凑核心加少量任务特定的教训——顺带说，这也是最便宜的选项。
- 对**有余力的强模型**，那意味着保留全量准则集，并用 prompt caching 让它在生产中负担得起。
- 对**饱和模型**，那意味着在弄清其剩余失败模式之前，不额外花上下文。

收益在所有情形下都是真实的——全自动、无泄漏、不需要人工标注——但前提是剂量与模型匹配。

## 下一步

这只是起点，不是终点：

- **可学习的检索器。** 我们目前的检索按余弦相似度给准则排序，而我们已经证明它不能完美预测哪些准则对给定任务有帮助。用结果信号训练一个检索器是自然的下一步。
- **给很弱模型的记忆。** 低于某个能力底线时，自蒸馏缺乏信号。为很弱模型做 teacher-distilled memory 是我们正在探索的另一个问题。
- **走出 AppWorld。** 这些结果在 AppWorld 上得到验证——一个严格的多步骤基准，但仍是单一的。更广的 agent 基准与真实部署正在推进。
- **隔离上下文窗口。** 如上所述，我们想要能分离「上下文窗口大小」与「原始能力」的受控实验。

> 试试 ALTK-Evolve 库——其中包含本文使用的提取、整理与检索流水线——或阅读完整技术报告了解全部方法与消融实验。

## 附录：理解指标

AppWorld 任务用两个指标评分，都以百分比报告（越高越好）：

- **TGC — Task Goal Completion。** agent 完整且正确完成的单个任务占比。这是「它把活干成了吗」的头条数字。
- **SGC — Scenario Goal Completion。** 更严格的全有或全无指标。每个*场景*捆绑同一任务的多个变体（同样的请求，不同数据、措辞或边角条件）。只有 agent 在**每个**变体上都成功，SGC 才计该场景通过。它衡量**可靠性**——一个多数时候能解决任务但某个变体失手的 agent，在 TGC 上有分，在 SGC 上没有。
