# 跨 HF Jobs 用 LoRA 的异步 GRPO：一个存储桶、一个代理、没有 NCCL

> TL;DR
> 
> AsyncGRPOTrainer 现在可以只训练一个 LoRA adapter，并且只把这个 adapter 同步给 vLLM（TRL v1.14）。
> 一个 rank-1 的 adapter 只有几 MB，因此它可以走一个挂载在每个 Job 里的 Storage Bucket，而不必走 NCCL。训练器和 vLLM 副本作为两个独立的 Hugging Face Jobs 运行在不同机器上。
> 副本前面的一个小代理负责加上鉴权 header、把每个 rollout 路由到已持有其 KV 前缀的副本，并向所有副本广播 adapter 加载。
> AsyncGRPO 的指标能指出瓶颈在哪。五次实验把同一个配方从 3 小时 27 分压到 53 分钟跑完 500 步。

LoRA 支持最近进入了 TRL 的 [`AsyncGRPOTrainer`](https://huggingface.co/docs/trl/en/async_grpo_trainer)（[PR #7017](https://github.com/huggingface/trl/pull/7017)），随 TRL v1.14 发布。异步训练器现在可以训练一个 adapter 而不是整个模型，并且只把 LoRA adapter 同步给 vLLM。本文介绍一个基于它构建的真实项目——在这个项目里，训练和推理不再共享一台机器。

LoRA 训练特别适合 RL，Thinking Machines 的博客 [LoRA Without Regret](https://thinkingmachines.ai/blog/lora/) 已经说明。他们证明在 policy-gradient RL 中，LoRA 可以媲美全参数微调，哪怕 rank 只有 1。原因在于 advantage 函数每个 episode 只提供 `~O(1)` bit 的信息，从总信息量的角度看，每一步可学的东西并不多，rank-1 adapter 的容量足以吸收它。

LoRA 训练还有一个系统层面的红利。1.5B 模型的 rank-1 adapter 只有几 MB，而全模型约 3 GB。每次更新之后，我们不必把整个 policy 发给推理 worker，只发 adapter 就行。vLLM 还能同时加载多个 adapter。旧的 rollout 以启动它时的 policy 跑完，新的 rollout 则用最新的 policy。

TRL 的 `AsyncGRPOTrainer` 本身已经把训练和生成分开。训练器和 vLLM 可以运行在不同机器上、各按各的节奏。在单机或集群环境里这很容易，因为两个进程可以共享文件系统或组建 NCCL group。

我们想要的是用 [Hugging Face Jobs](https://huggingface.co/docs/huggingface_hub/guides/jobs) 跑同样的架构。本质上，一个 HF Job 就是一个 VM 上跑一个容器。这意味着一个 Job 无法（至少目前不能）拉起多个节点来容纳一个训练器和一支 vLLM 服务器舰队（单机最多 8xH200）。`AsyncGRPOTrainer` 正是为这种规模设计的，于是问题变成：如果放弃「训练器和推理服务器共享一个节点」这个前提，我们最多能走多远？

嗯，如果用全权重同步，答案是「走不远」。每次更新都得在机器之间搬运 GB 级数据——那是 NCCL 在密集集群里的用途，但 Jobs 无法*跨*节点通信。既没有共享本地盘，显然也没有共享的 `localhost`。而用 LoRA，一次同步只有几 MB。文件系统方面，HF Jobs 提供由 [Storage Bucket](https://huggingface.co/docs/hub/storage-buckets) 支撑的 volume！这些 bucket 可以以 FUSE 文件系统形式挂载进每个 Job，足以充当节点间的共享 FS。Job 之间完全不需要网络通路。

最终这套东西其实很小：

- 一个**训练器 Job**，运行带 LoRA（以及 FSDP，后面细说）的 `AsyncGRPOTrainer`，
- **两个 vLLM Job**，每个都提供 base model 加训练器最近发布的任意 adapter，
- 一个 **Storage Bucket**，以相同路径挂载进以上三个 Job——adapter 就是这样从训练器到达服务器的，
- 一个**代理服务器**。后面细说为什么需要它，但大体上我们需要一个代理：把每个 rollout 路由到最可能持有其 KV cache 的副本，并把每次 adapter 更新广播到所有 vLLM 副本。

## 架构：用好 Hugging Face Jobs 和 Storage Buckets 🪣

`AsyncGRPOTrainer` 新的「仅 adapter 同步」路径是这样工作的。训练器不向 vLLM 发送张量。每隔几个优化步，它把 adapter 保存到 `<output_dir>/.vllm_lora/trl-policy-v{N}`，用一次原子重命名发布该目录，然后把路径发给 vLLM 的 `/v1/load_lora_adapter` 端点。vLLM 从磁盘加载文件，之后 rollout worker 就可以请求 `model="trl-policy-v{N}"`。

vLLM 的运行时加载 adapter 本来就是这么工作的。该端点接收的是路径而不是张量，因此预期训练器和服务器共享文件系统。在 Slurm 集群上，那是网络文件系统。在 Jobs 上，我们通过在每个 Job 中把同一个 [Storage Bucket](https://huggingface.co/docs/hub/storage-buckets) 挂载到同一路径得到同样的效果（前面说过）。底层用的是 [`hf-mount`](https://github.com/huggingface/hf-mount)，它把 bucket 以 POSIX 文件系统形式暴露进容器：

```
# every Job gets the same bucket at the same absolute path
hf jobs run ... -v hf://buckets/aminediroHF/asyncgrpo-lora-buckets:/lora ...
```

TRL 和 vLLM 都不用为此改任何东西。训练器写 `/lora/<run>/.vllm_lora/`，服务器从同一路径读。POST 请求里发送的路径在每个容器内本来就直接有效。

三个 Job 和 bucket。TRL 通过 localhost 与代理对话，代理通过 HTTPS 与副本对话，adapter 目录则经由 bucket 挂载传输。

注意我们也把 checkpoint 和最终 adapter 存进 bucket。HF Jobs 是短命的，但一个被抢占（preempted）的训练器可以恢复训练——最终 adapter 始终持久化在 bucket 里，Job 停止也不会丢。

## 三个 Job

### vLLM 副本

每个副本用一个 GPU 和原版 `vllm/vllm-openai` 镜像。我们只需要启用[运行时 LoRA](https://docs.vllm.ai/en/latest/features/lora/?h=lora#serving-lora-adapters)加载，并留够 adapter 槽位。

adapter 槽位数量由 `max_staleness` 决定。在 `AsyncGRPOTrainer` 中，每次权重同步都会把 policy 版本号加一，而 `max_staleness` 规定一个 rollout 样本在多大落后于当前 policy 之前仍会被训练器采用。`max_staleness=4` 时，在 `trl-policy-v3` 下生成的样本，训练器到了 `v7` 时依然会用来训练。而一个从 `v3` 开始的 rollout 也必须能在 `v3` 下跑完。所以任意时刻，vLLM 都要同时服务当前 policy 加之前的四个。这就是训练器保持注册 `max_staleness + 1` 个 adapter 版本、并卸载更旧版本的原因。每次同步先加载新版本、再卸载最旧的，交换期间需要多一个槽位。于是得到 `--max-loras 6`。若只有 5，每次同步时 vLLM 会静默淘汰一个还有 rollout 在途的 policy。

```
# --expose 8000                       reachable at https://<job_id>--8000.hf.jobs
# -v ...:/lora:ro                     read-only: the server only reads adapters
# VLLM_ALLOW_RUNTIME_LORA_UPDATING=1  enables /v1/load_lora_adapter
# VLLM_SERVER_DEV_MODE=1              enables /pause, /resume, /server_info (TRL needs all three)
# --max-loras 6                       max_staleness=4 -> 4+2 adapter slots
for replica in 1 2; do
hf jobs run --detach --flavor h200 --timeout 8h --secrets HF_TOKEN \
    --expose 8000 \
    -v "hf://buckets/${BUCKET}:/lora:ro" \
    -e VLLM_ALLOW_RUNTIME_LORA_UPDATING=1 \
    -e VLLM_SERVER_DEV_MODE=1 \
    -- vllm/vllm-openai:v0.27.1 \
    vllm serve Qwen/Qwen2.5-Math-1.5B --host 0.0.0.0 --port 8000 \
        --max-model-len 4096 --logprobs-mode processed_logprobs --generation-config vllm \
        --enable-lora --max-lora-rank 1 --max-loras 6
done
```

我们把 vLLM 锁定在 `v0.27.1`。vLLM 迭代很快，上面这些 flag 和运行时 LoRA 端点是该版本提供的，请把版本当作配方的一部分。

还有一种可能的设计：训练器只保留最新 adapter，并永远以同一个名字发布。我们没有这样做，因为 vLLM 的前缀缓存是按 adapter 名字作 key 的。只用一个名字时，交换权重后基于旧权重算出的 KV block 仍然会命中，prefill 就不会重做，一次 rollout 的前缀可能来自某个 policy 版本、解码却来自下一个版本。训练器无从察觉，它只会表现为 `ratio` 偏离 1。用带版本号的名字就让这事不可能发生：一个名字永远对应一组权重，缓存的前缀不可能匹配到更新的版本。

### 数据集选择：Sanity 集

我们选了 [`sail/Sanity-Test-R1D-1.5B`](https://huggingface.co/datasets/sail/Sanity-Test-R1D-1.5B)，出自论文 [Defeating the Training-Inference Mismatch via FP16](https://huggingface.co/papers/2510.26788)（Qi et al., 2025）。复现代码在 [`sail-sg/Precision-RL`](https://github.com/sail-sg/Precision-RL)。

作者用 [DeepSeek-R1-Distill-Qwen-1.5B](https://huggingface.co/deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B) 对每道 MATH 题生成 40 个答案，保留了成功率在 20% 到 80% 之间的题，共 1,460 道。这个数据集对 RL 验证非常好：这些题对该模型既不是早已解决、也不是完全无望，意味着模型早期就能拿到有效信号去训练和提升。

作为健壮的端到端测试这非常合适：如果某个 vLLM 副本悄悄在 adapter 名字下服务的是 base model，我们希望几十步内就能从曲线上看出来。而且这个数据集足够小，不到两小时就能过完一轮。

超参数也取自论文的 LoRA 脚本 [`oat/scripts/lora`](https://github.com/sail-sg/Precision-RL/tree/main/oat/scripts/lora)：`Qwen/Qwen2.5-Math-1.5B`、LoRA rank 1、alpha 2、学习率 4e-5、每个 prompt 采样 8 条、每步 128 条 completion、最多生成 3,000 个 token、上下文 4,096 token。

### 训练器

训练器使用同一个 `vllm/vllm-openai:v0.27.1` 镜像，之上安装 TRL。当时我们跑的是 PR 分支；同样的代码现已进入 TRL v1.14。训练脚本就是一个普通的 `AsyncGRPOTrainer` 脚本，只有输出目录和服务器 URL 这两个值与 Job 相关。

```
from peft import LoraConfig
from trl.experimental.async_grpo import AsyncGRPOConfig, AsyncGRPOTrainer

config = AsyncGRPOConfig(
    output_dir="/lora/sanity-lora-r1",       # on the bucket: adapters, checkpoints and the final adapter all land here
    vllm_server_base_url="http://localhost:8000",   # the proxy, not a vLLM Job; TRL never sees the Jobs URLs
    max_staleness=4,
    weight_sync_steps=4,                     # publish an adapter every 4 optimizer steps
    save_strategy="steps", save_steps=50,    # checkpoints go to the same bucket -> resume after preemption
    ...
)
trainer = AsyncGRPOTrainer(
    model="Qwen/Qwen2.5-Math-1.5B",
    args=config,
    peft_config=LoraConfig(r=1, lora_alpha=2, target_modules="all-linear"),  # plain LoRA vLLM can serve as-is
    ...
)
```

> 初始化期间，TRL 会调用 /server_info。若发现 lora_config，就启用仅 adapter 同步。vLLM 无法直接serve的配置——如 DoRA、modules_to_save、或超过 --max-lora-rank 的 rank——会带着警告退回「合并权重」同步。日志里应能看到 Adapter-only vLLM sync enabled。

## 代理

接下来说有意思的部分。我们需要在训练器和 vLLM Job 之间架一个代理，原因有二：

- 暴露的 Job 端口要求每个请求都带 `Authorization: Bearer <HF token>` header。代理就是加这个 header 的地方，TRL 不需要知道它的存在。
- 我们希望不止一个 GPU 在生成。单台 vLLM 服务器上通常用 `--data-parallel-size > 1` 实现，但 TRL 在该模式下拒绝仅-adapter 同步，这有充分理由：对 `/v1/load_lora_adapter` 的调用只会到达响应它的那个 DP rank，其他 rank 会继续用 base model 顶着新 policy 的名字响应。在 Jobs 上这个问题压根不存在，因为每个副本都是自己一台机器。于是数据并行必须上浮一层，放到一个能把 adapter 加载扇出到所有副本的东西里。

所以我们在训练器 Job 上的 `127.0.0.1:8000` 跑一个小代理，把 TRL 指过去，仿佛它是一台单机 vLLM。除了加 header，代理在功能上只做两件事：

- 把每个 completion 请求发给一个副本，选择标准是让同一个 prompt 的八个 rollout 落在已缓存其前缀的地方（细节见下文）。
- 把每个*改变状态*的请求——如 **adapter 加载、pause 和 resume**——广播到所有副本，让同一个 policy 名字在每个副本上含义一致。

### 按 KV 前缀路由 rollout

先快速回顾为什么这件事重要。生成一条 completion 有两个负载特征截然不同的阶段：

- prefill 阶段**一次性处理整个 prompt**，为每个 prompt token 计算注意力的 key 和 value。
- decode 阶段随后一次产出 token，每个新 token 都要注意到它前面所有 token 的 key 和 value。

这些 key 和 value 就是 KV cache。因为注意力是因果的，某个 token 的 KV 只取决于它之前的 token、与后面无关。两个共享前缀的请求因此共享那段前缀的 KV，而已经缓存了它的副本可以**完全跳过 prefill 的那一部分**。现在的全部功夫就在于找到那个副本，让请求落到已经见过其前缀的地方。

vLLM 的[前缀 KV cache](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/kv_cache_utils.py)按 16 token 一个 block 存储。由于 GRPO，rollout worker 会对同一个 prompt 发出 `G` 个请求（我们这里 `G=8`）。如果它们都到达同一个副本，第一个请求算 prefill，后七个直接复用。若是轮询路由，就有一半会落到没缓存该前缀的副本，那四个请求会重做 prefill，浪费宝贵的 GPU 算力。

[我们的路由器](https://github.com/AmineDiro/hfjobs-lora-buckets/blob/main/src/lora_proxy.py)的职责是追踪哪个副本见过哪个 **block hash**。一个重要细节是哈希是链式的：block 3 的 hash 代表的是 block 1、2、3，而不只是 block 3。这正对应因果注意力：block 3 的 KV 只有在 block 1 和 2 也相同时才有效。我们还会用 adapter 名字给哈希链做种子，因为 KV cache 也取决于生成它的 adapter：为 policy v3 缓存的前缀对 policy v4 毫无用处！

两个 prompt、四个请求在两个副本上的路由决策：16-token block、链式哈希、公共前缀、一次亲和命中、一次溢出。

视频完整演示了选择副本的决策过程。下面的步骤走一遍一个真实的 135-token completion 请求示例（来自 Sanity 数据集中的题）：

**1. 把 prompt 切成 block。** 路由器收到 token ids，像 vLLM 一样把它们切成 16-token 的 block。它只对完整 block 做哈希，所以这里最后 7 个 token 被忽略。

**2. 哈希前缀。** 每个 block 与前一个哈希一起参与哈希，从 adapter 种子开始。于是 `h3` 按序标识 block 1、2、3。前 `k` 个 block 相同的两个 prompt，其哈希直到 `hk` 都相同；一旦某个 block 变了，其后所有哈希都会变。这就是为什么用 adapter 名字做种子：同一个 prompt 在 `trl-policy-v4` 下从另一个种子出发，不可能匹配 `v3` 的记录。这正是我们想要的，因为旧 KV block 是用不同权重算出来的。

**3. 比较两个 prompt。** 问题 1 有 103 个 token。两个 prompt 都以相同的 23-token 聊天模板开头。它们的第一个 block 相同，但 block 2 已经包含题面文本，哈希从这里开始不同。

**4. 记录归属。** 对每个哈希，路由器记住哪些副本服务过它、以及它后面跟过哪些哈希（后继集合上限设为 2，因为我们只需要知道一个 block 有单一延续还是多个延续）。跑过几个 prompt 之后：模板 block `h1` 由两个副本共同所有、且已有多个后继；`h2` 到 `h8` 仅由 A 所有、各自只有单一后继；`h2'` 到 `h6'` 仅由 B 所有。

实际运行中，每个 prompt 都以相同的 token 开头。这里是聊天模板加系统提示，占 1,460 道题全部的前 23 个 token。换成 agent 场景就是工具描述，多轮对话场景就是共享的会话历史。这些 block 在几秒内就进入每个副本的缓存，所以匹配上它们并不能说明某个具体 prompt 在哪里。

若每个副本都服务过某个 block，或它有多个后继，该 block 就是*公共的*。路由时忽略公共 block，因为它们无法标识具体 prompt。下文继续展开！

**5. 选一个副本。** 路由器统计每个副本匹配了多少个前导 block，再减去公共前缀，剩下的是本 prompt 独有的 block 数。然后：

- 若某个副本有独有 block 且它不算忙——即它最多只比最闲副本多 8 个在途请求——请求就去那里。我们称之为 **affinity（亲和）**命中。
- 若某副本有独有 block 但它已多出 8 个以上在途请求，我们放弃缓存，把请求发给最闲的副本。我们称之为 **spill（溢出）**。
- 若没有任何副本有独有 block，这是一个新 prompt。它去最闲的副本，并列时轮询。我们称之为 **unmatched（未匹配）**。

下面把规则应用到四个请求。初始状态：副本 A 和 B 各有 3 个在途请求，两个副本上只有模板 block `h1` 已知。

- **请求 1，问题 0，rollout 1。** 两个副本各匹配 1 个 block——模板——且该 block 是公共的。所以没有任何独有匹配。请求 unmatched，两个副本负载相同，轮询把它派给 A。路由器记录 `h2` 到 `h8` 归 A 所有。A 现在有 4 个在途请求。
- **请求 2，问题 0，rollout 2。** 同一个 prompt。A 匹配全部 8 个 block，B 只匹配模板。减去 1 个公共 block 后，A 有 7 个独有 block、B 有 0 个。A 只比 B 多 1 个请求，远小于 8 的上限，于是请求去 A。这是一次亲和命中：A 的 KV cache 里已经有整个 prompt。
- **请求 3，问题 1，rollout 1。** 新 prompt。两个副本都只匹配模板 block，没有独有匹配。请求 unmatched，去最闲的副本 B——它 3 个在途，A 已有 5 个。路由器记录 `h2'` 到 `h6'` 归 B 所有。
- **请求 4，问题 0，rollout 9。** 假设此刻 A 有 12 个在途而 B 回到 3。A 仍有那 7 个独有 block，但它现在比 B 多 9 个请求，超过上限。请求溢出到 B。B 把问题 0 prefill 一次，路由器把 `h2` 到 `h8` 也记为 B 所有。现在每个副本都服务过这些 block，问题 0 也变成公共的，其后续 rollout 只按负载放置。

**6. 复用 prefill。** 请求 2 就是我们做这一切的理由：它复用了请求 1 计算的 prefill——block 1 到 8 已在 A 的 KV cache 里，A 直接开始解码 completion。若派到 B，B 会重算全部 135 个 token 的 prefill，而 A 的缓存干放着没用。请求 3 说明了为什么需要 `common` 规则：没有它，共享的聊天模板会让每个新 prompt 都看起来像缓存命中。请求 4 说明负载有界的重要性：为了省一次 prefill 让某副本远远落后，不值得。

```
def choose(self, upstreams, model, prompt):
    hashes = self.block_hashes(model, prompt)         # chained blake2b over 16-token blocks, seeded with `model`
    matched = self.matched_prefix(hashes)             # per replica: leading blocks it has served
    common = self.common_prefix_len(hashes)           # leading blocks that identify no prompt (see below)
    specific = [max(0, m - common) for m in matched]  # what actually distinguishes replicas
    least = min(u.inflight for u in upstreams)
    best = max(range(self.n), key=lambda i: (specific[i], -upstreams[i].inflight))

    if specific[best] > 0 and upstreams[best].inflight - least <= self.cfg.imbalance:
        pick = best                                   # affinity: the replica that has this prompt, and is not swamped
    else:
        candidates = [i for i in range(self.n) if upstreams[i].inflight == least]
        pick = candidates[self.rr % len(candidates)]  # spill or new prompt: least-loaded, round robin on ties
        self.rr += 1
    ...record `pick` as an owner of every block, and each block's successor...
    return upstreams[pick]
```

`common` 前缀是最麻烦的一块。每个请求都以相同的系统提示和聊天模板开头。简单做最长前缀匹配的话，第一个副本几乎对每个新 prompt 都能命中。我们改用「扇出」来检测共享前缀：有多个不同后继的 block 是公共的；永远只有同一个后继的 block 才属于某个具体 prompt。只有公共前缀之后的 block 才计入亲和。

### 广播 adapter

代理还需要把 adapter 加载广播到每个副本。我们把该操作当作**全有或全无**。每个副本有自己的 bucket 挂载，它们不一定在同一时刻看到新 adapter。`No adapter found for <path>` 错误通常意味着某个 bucket 挂载还没跟上，我们只对那个副本重试。出现任何其他错误，我们就把已接受该 adapter 的副本上的它卸载掉，绝不让一个 policy 名字只存在于部分副本上。

```
async def load_one(u):
    while True:
        status, _, out = await send(u, "POST", "/v1/load_lora_adapter", headers, body)
        if status == 200 or "No adapter found" not in out.decode() or time.monotonic() > deadline:
            return u, status, out
        await asyncio.sleep(cfg.lora_retry_s)          # this replica's mount has not seen the directory yet

results = await asyncio.gather(*(load_one(u) for u in ups))
if any(st != 200 for _, st, _ in results):
    await asyncio.gather(*(send(u, "POST", "/v1/unload_lora_adapter", headers, unload) for u, st, _ in results if st == 200))
    return web.Response(status=504 if timed_out else st, text="rolled back on the others")
```

`/pause`、`/resume` 和 `/v1/unload_lora_adapter` 也用同样方式广播。`/health` 只有所有副本健康才返回 200。`/server_info` 和 `/v1/models` 只需要一份回答。从 TRL 的视角看，代理就是一台 `data_parallel_size=1` 的服务器，所以它选择仅-adapter 同步。

我们起初还担心一个 Python asyncio 代理会不会成为瓶颈。它不会（至少在这个规模上）。在途的非流式 JSON 请求最多 128 个，路由只算几个哈希，一个线程轻松搞定。若要处理更大流量，一个更精细的路由器大概率得用更快的语言重写（说的就是你 🦀）。

## 追逐瓶颈的乒乓

异步 RL 是训练与生成之间的流水线。一边提速，如果另一边跟不上，毫无意义。好在 `AsyncGRPOTrainer` 里我们加了足够多的计时和指标，可以直接看清这一点。

所有有用指标都记录在 [Logged metrics](https://huggingface.co/docs/trl/en/async_grpo_trainer#logged-metrics) 一节。`perf/rollout_wait_s` 告诉我们训练器等待样本多久；`rollout/backpressure_s` 告诉我们生成侧为队列空位等待多久。两者完全对立，不应同时很高。它们和队列大小一起，指出哪一侧慢了。

我们跑了五个实验。每一个都始于上一次运行仪表盘上暴露的问题。除非另有说明，模型、配方和三 Job 布局不变。下面的名字就是 trackio 的运行名。

### 读仪表盘

我们保持这四组指标可见：

- **`perf/step_s`** 和 **`perf/fwd_bwd_s`**：一个优化步耗时多久、其中 forward+backward 占多少。若一步的耗时几乎等于 forward+backward，训练器明显是计算受限的。
- **`perf/rollout_wait_s`**：训练器为了拿到样本开始一步而干坐了多久。接近零表示生成跑在训练前面，样本立即可用。
- **`sample/rollout_queue_size`** 对比 `queue_maxsize`：两侧之间的缓冲。满表示生成被节流；空表示训练器在挨饿。
- **`rollout/backpressure_s`** 和 **`rollout/score_block_s`**：rollout worker 因缓冲满而被堵住多久。worker 是两级流水线：生成把完成的组交给打分（scoring）阶段，打分再把打完分的样本推入 rollout 缓冲。缓冲满时打分无法入队而被堵住，即 `rollout/backpressure_s`。打分随之停止消化自己的输入队列，生成也就无法交出下一组，即 `rollout/score_block_s`。两者是同一次停顿，先在打分阶段看到、再传导回生成阶段。

诊断很简单：队列满、rollout 等待为零、背压高——训练器太慢。队列空、rollout 等待上升、没有背压——生成太慢。对比 `perf/mfu_wall_clock` 与 `perf/mfu_fwd_bwd` 还能看出训练器 GPU 有多少时间在等待而不是训练。

### 运行 1，`r1-dp2`：跟不上的训练器

[![Figure 2](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig1-r1-dp2-trainer-bound.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig1-r1-dp2-trainer-bound.png)

*图 2。trackio 运行 `r1-dp2`。面板：`perf/step_s`、`perf/fwd_bwd_s`、`sample/rollout_queue_size`、`rollout/backpressure_s`。步时与 forward+backward 几乎完全重叠；队列钉在 512 中的 476 附近，背压每组 rollout 从不低于 11 s：训练器受限。*

`perf/step_s` 为 22.9 s，`perf/fwd_bwd_s` 为 21.9 s。forward 和 backward 占步时的 96%。队列保持满员，训练器等 rollout 只需 0.02 s，而 rollout worker 每组要背压阻塞 15 秒。两个 vLLM 副本的生成速度比训练器消费速度快。报告的 4.6k tokens/s 不是它们的真实上限——只是没地方放更多输出。

batch 指标解释了糟糕的 3.9% MFU。`batch/microbatches_per_step` 是 64，`batch/samples_per_row` 是 1.0。每个 rank 每个步处理 64 次、每次一条约 1.2k token 的序列。这来自参考配方的 `per_device_train_batch_size=1`。对 1.5B 模型配 H200，这完全是延迟受限（latency-bound）。

### 运行 2，`r1-dp2-tb16k`：把 microbatch 装填密集

修法不是改 batch size。我们保持每个优化步 128 条 completion，只改它们在 GPU 上的摆放：不再是每个 microbatch 一条序列，而是把多条序列密集打包进每一行。训练器通过 **token-budget batching（token 预算批处理）**支持这一点。`token_budget > 0` 时，它把多个样本打包成每个 rank 一行无 padding 的数据。一个优化步处理 `gradient_accumulation_steps` 行。我们设 `token_budget=16384`、`gradient_accumulation_steps=6`。

[![Figure 3](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig2-r1-dp2-vs-tb16k-packing.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig2-r1-dp2-vs-tb16k-packing.png)

*图 3。trackio 运行 `r1-dp2` 与 `r1-dp2-tb16k` 前 154 步叠加。面板：`batch/samples_per_row`、`batch/microbatches_per_step`、`perf/step_s`、`perf/fwd_bwd_s`、`perf/mfu_fwd_bwd`、`rollout/generated_tok_s`。打包后每行样本数从 1 到 13，microbatch 从 64 降到 6，步时从 23 s 降到 5.9 s，生成从 4.2k 升到 27.5k tok/s——vLLM 侧什么都没改。*

`batch/samples_per_row` 从 1.0 升到约 12.7，microbatch 数量从 64 降到 6。行有 95% 是满的！forward 和 backward 从 21.9 s 降到 5.6 s，MFU 从 3.9% 升到 19%。现在每步约训练 150 个样本，因为行装填得比按平均长度估计的更好。

生成也从 4.6k 跳到 25k tokens/s，尽管 vLLM 侧没有任何改动。队列不再常年满员，副本终于可以放开跑了。这就是我们不喜欢孤立地优化流水线某一级的原因。要谨慎地评估整个系统——一个慢的级会掩盖其上游所有环节的真实性能。

### 运行 3，`r1-dp2-tb16k-nockpt`：别再重算 forward

`perf/fwd_s` 是 1.34 s，而 `perf/fwd_bwd_s` 是 5.6 s。正常的 backward 大约是 forward 的两倍开销，而 base 权重冻结时应该更接近一倍。3.2 的比值可疑。

原因是 `AsyncGRPOConfig` 默认 `gradient_checkpointing=True`。每个 microbatch 在 backward 期间重算自己的 forward。这也解释了 16k-token 的行在 141 GB 的 H200 上只用 25 GB！这是给训练器省显存的优化，但这个具体场景不需要：模型足够小，激活留着做 backward 也装得下。

[![Figure 4](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig3-tb16k-vs-nockpt-crossover.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig3-tb16k-vs-nockpt-crossover.png)

*图 4。trackio 运行 `r1-dp2-tb16k` 与 `r1-dp2-tb16k-nockpt` 前 134 步叠加。面板：`perf/fwd_s`、`perf/fwd_bwd_s`、`perf/weight_sync_s`、`sample/rollout_queue_size`、`perf/rollout_wait_s`、`perf/mfu_fwd_bwd`。forward+backward 少了一个 forward 的量；队列从约 420 掉到约 60，rollout 等待从 0.02 s 升到 0.5 s：瓶颈转向生成。*

设 `gradient_checkpointing=False` 后，forward 加 backward 降到 4.6 s，几乎正好少一个 forward，MFU 达到 23%。队列降到 71，rollout 等待从 0.04 s 升到 0.6 s。训练器消费样本比两个副本生成更快。我们*成功地*把瓶颈移到了生成侧。

这暴露出另外两项成本。每四步一次、7.6 秒的权重同步现在占墙钟时间的 25%——之前每步 23 秒时它只占 8%。另外，backward 仍比 forward 慢 2.5 倍。在 base 权重冻结的前提下，每步仍有约 2 秒看起来不像正常的模型计算。

### 运行 4，`r1-dp3-tb16k-nockpt`：三个副本，和一个意外

既然生成太慢，我们加了第三个副本。同时把代理里的 adapter 重试间隔从 2 s 降到 0.5 s，并关闭 `fsdp_reshard_after_forward`，以验证 backward 里多出的 2 秒是不是 FSDP2 的重新 gather 造成的。

[![Figure 5](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig4-dp2-vs-dp3-inflight-cap.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig4-dp2-vs-dp3-inflight-cap.png)

*图 5。trackio 运行 `r1-dp2-tb16k-nockpt` 与 `r1-dp3-tb16k-nockpt` 前 134 步叠加。面板：`perf/weight_sync_s`、`rollout/generated_tok_s`、`rollout/inflight`、`perf/fwd_bwd_s`。同步从 7.6 s 降到 5.8 s；生成和 forward+backward 纹丝不动；两次运行的 `rollout/inflight` 都是 128——这正是第三个副本撞上的上限。*

权重同步从 7.6 s 降到 5.8 s，说明缩短重试间隔有效。forward 和 backward 保持 4.6 s，排除了 resharding。生成从 25k 只升到 26k tokens/s。第三个副本基本白加。

原因就躺在 `rollout/inflight` 里：每次运行都是 128。代理显示这些请求按 44 + 43 + 41 分摊到三个副本。`max_inflight_tasks` 限制的是整个 rollout worker 的并发，不是每个副本的并发。1.5B 模型在 H200 上处理 43 条和 130 条并发序列的单 token 成本几乎一样。把 128 个请求摊到三块 GPU 上和摊到两块上的吞吐几乎相同。

所以 vLLM 不是瓶颈，是我们自己客户端里的常量才是。当初保守设它，是因为不知道几百个长 HTTPS 请求经公开 Jobs 代理会是什么表现。而到这里，130,000 条 rollout completion 已经全部穿过它，零传输错误。

### 运行 5，`r1-dp3-inflight384`：抬高在途请求上限

`max_inflight_tasks=384`、`queue_maxsize=768`，其他一律不动。

[![Figure 6](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig5-all-runs-scoreboard.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/asyncgrpo-lora-hfjobs/fig5-all-runs-scoreboard.png)

*图 6。全部五个 trackio 运行（`r1-dp2`、`r1-dp2-tb16k`、`r1-dp2-tb16k-nockpt`、`r1-dp3-tb16k-nockpt`、`r1-dp3-inflight384`）叠加，横轴为步。面板：`perf/step_s`、`reward`、`sample/rollout_queue_size`、`sample/staleness_mean`。整个系列里步时从 22.9 s 降到 4.8 s，而 reward 曲线彼此重叠；最后一次运行的队列回升到 768 中的约 690，staleness 稳定在 2。运行 2 到 4 在仪表盘回答问题后就被提前停掉了。*

384 个在途请求时，每个副本分到 128。队列迅速填到 768 中的约 690 并保持。背压回到 5 秒，rollout 等待降到 0.03 秒。训练器又是瓶颈了！forward 和 backward 4.6 秒，权重同步摊销 1.5 秒，步时中位数 4.8 秒。

平均 staleness 从 1.5 升到 2.0 个版本，因为样本在更大的队列里等得更久。这仍低于 `max_staleness=4`，且 `ratio` 依然非常接近 1.000。
