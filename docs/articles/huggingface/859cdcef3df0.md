## 下一个真正的约束是利用率，而不是智能。

航空业是吃过苦头才学会这一点的。在这个行业历史的大部分时间里，最能预测一家航空公司能否活下来的数字，是每架飞机每天花在地面上的时间。

原因是结构性的。飞机的成本按日历小时累积：融资、折旧、机身保险、定期维护、机组合同。而它的收入只按飞行小时累积。在地面上的每一个小时都在压缩这个等式的产出端，成本端却一如既往照跑不误。利用率还几乎处于航空公司所有其他工作的下游：过站周转纪律、航线网络设计、维修计划、机组排班、航材供应，最终都会体现在这一个数字上——因为 underneath 它任何环节出了问题，不管别的做得多好，飞机都会停在地面。

机队更大当然仍然有帮助。更多的飞机意味着更多可用运力，简单明了。但两家在相当机队、相当航线上运营的航空公司，经济表现可能天差地别，而其中大部分差距要追溯到这一个度量，而不是机队规模。

企业 AI 正在不同的硬件上撞上同一个结构。GPU 的成本同样按日历小时累积——融资、折旧、电力、散热——不管它在某个时刻有没有在做有用的事。而它的产出只按计算小时累积。更多 GPU 的作用大致类似于更大机队对航空公司的作用：真实的容量、真实的优势，但依然不保证决定胜负的那个结果。两家 GPU 预算相当的公司日益拉开差距，取决于这些硬件在任何给定时刻有多大比例在做有用的事，而不取决于各自拥有多少。这个数字也和航空公司的利用率一样，处于公司几乎每一项基础设施决策的下游。智能已经把这个行业带到了今天。下一个真正的约束，正在利用率处成形。

### 瓶颈从模型转移到了算力

随着 AI 规模化，稀缺性并没有消失。它沿着链条上移，落在了完全不同的资源上。

企业 AI 的第一波是靠模型质量赢得的。更大的模型、更多的算力训练、更难的基准评测：参数量和排行榜名次主导了对话，而这场竞赛确实产出了足以承担真实企业工作负载的模型。但这种能力是附带一个依赖而来的：生产 AI 运行在专用硬件上，而今天这种硬件几乎完全是 GPU。

GPU 昂贵、供给受限、需求远超可得——即便在市场的最顶端也是如此。2020 年，微软为 OpenAI 打造了一台专用超级计算机：超过 10,000 块 GPU 和 285,000 个 CPU 核心，当时被报道为全球最大的五套系统之一，用来训练后来的 GPT-3。在当时，这看起来像是近乎不可想象的硬件集中度，那种让算力看起来对能拿到它的人来说已是 solved problem 的数字。六年过去，这个数字读起来更像起点而非天花板。到 2026 年，即便是全球资金最充裕的实验室，也把算力获取视为一个活的战略约束而非已解决的问题。仅 Anthropic 一家就在四个不同硬件平台——Amazon、Google、Microsoft 和 AMD——同时推进多吉瓦级的承诺，且数月内层层叠加；Meta 则签下了规模相当的多吉瓦协议。把承诺同时分散到四家供应商，正是一个买家资本实际上无限却仍无法从任何单一来源获得足够供给时，算力稀缺的样子。

相隔六年的两件事，都标记了一个实验室仅为保持竞争力所需资源的 frontier。其间的变化，与 AI 变得更强关系不大，而与「能力不再是绑定约束」息息相关。

同样的模式在实验室下游以不同形态出现。通过 API 消费这些模型的企业，撞上的是定价问题多过硬件问题。成本随使用的 token 线性增长，而这一个事实几乎完全分割了 PoC 的经济性和生产环境的经济性。每月处理几千次请求的 PoC 看起来负担得起。同样的工作负载到了生产规模，可能变成一条始终消化不掉的成本线。正在获得优势的替代方案足够直白：企业自购 GPU、本地运行模型，用一个可变的线性成本换一笔固定的资本开支。

[![dharma_fig1_cost_curve (1)](https://cdn-uploads.huggingface.co/production/uploads/69d815b52c6db28cfdfdd422/rPuuLzwC5gUqx1nAgQg_f.png)](https://cdn-uploads.huggingface.co/production/uploads/69d815b52c6db28cfdfdd422/rPuuLzwC5gUqx1nAgQg_f.png) `API 成本随用量上升，而自有基础设施近乎固定。越过盈亏平衡点后，这笔交易就反转了。`

这一转变让 GPU 成为基础设施而非一笔费用科目：按增长定容、按需求峰值定容，因此也就高于任何一周的实际所需。这意味着购买并没有终结问题，而是打开了一个新问题。集群上线的那天，问题就从*我们拿不拿得到加速器*变成*我们能不能让它们保持忙碌*——而只有前一个问题配有采购团队。签硬件合同的那部分有截止日期、有负责人。让飞机离地的那部分，才是在悄无声息地决定这笔交易签得值不值。

这些交易描述的是容量承诺，不是效率。这份容量被用得多好，是一个独立的问题：由不同的人负责，度量远不严格，也远未被解决。

### 为什么忙碌的集群仍在浪费容量

一个 GPU 全都在忙碌的集群，依然可能把大部分潜力浪费掉，而原因几乎总是同一个。GPU 日以继夜地运行，而对它们的需求不是。基础设施必须按峰值定容——训练、批处理作业和实时流量同时压上来的那一刻——这让相当一部分容量在峰值之外被 provisioning 出来却无人使用。如果每块 GPU 都能 equally 好地吸收每种工作，更好的预测本可以单独解决这个问题。但很少有能力做到的，而这恰恰是这个难题更难的那一半。

错配发生在更深一层。

在企业 AI 的第一代，GPU 的工作基本是单一的：跑推理。今天，同一批硬件要支撑训练、微调、量化、实时推理、批量推理、embedding 生成和模型评估——常常是同一组织，有时是同一个模型，同一个集群。每一种工作负载对硬件的诉求都不同，而且差异很深。实时推理几乎把低延迟置于一切之上，因为慢的响应就等于失败的响应。批处理在意吞吐量、容忍延迟，有时一忍就是几小时。训练可以连续占用一块 GPU 数小时乃至数天。量化需要大量容量，但只持续很短时间。为其中一种调优的调度器，几乎默认就会把另外三种分配错。这种失败也不一定反映在利用率看板上：一个集群可能报告很高的平均占用率，而几个排队的作业正在等待一块恰好忙着跑别的东西的 GPU 的「形状」。

具体的工作负载组合因组织而异，问题的形状则不变。这也是飞机类比触到极限的地方，而这个极限本身教给我们一些东西，而不只是给类比打个补丁。一架空闲的飞机通常可以被重新派往机队中的任何航线：停在芝加哥的 737 改飞丹佛而不是达拉斯，几乎没有额外代价。一块空闲的 GPU 只能吸收内存、延迟、时长画像上它确实能服务的工作负载。这个差别让编排比机队排班更难，也是为什么问题从「GPU 有没有被占用」变成「哪个工作负载应该在哪块 GPU 上、在什么时间、以什么优先级运行」。再买一机架 GPU 增加的是容量和成本，不是错配的解药——新容量同样可能以错误的形状出现在错误的时刻，正如已安装的容量。

### 智能搬进了基础设施

最大化 GPU 的投资回报，不是一次性的 provisioning 决策就能完成的。它要求对基础设施本身进行持续的、主动的管理——每小时都在运行，而不只是在采购的那一刻。作为回应正在成形的是一门独立的学科：GPU 管理（GPU Management）——一个位于工作负载、模型和硬件之间的编排层。它的职责是持续地决定：哪个工作负载运行、何时运行、如何运行、跑在集群里哪一块具体的 GPU 上。这些概念都不稀奇。它更接近一支优秀运维团队凭直觉已经在做的事，只是被形式化了，并且持续运行，不再依赖某个人恰好注意到问题。

[![dharma_fig2_gpu_orchestration_v2_radial](https://cdn-uploads.huggingface.co/production/uploads/69d815b52c6db28cfdfdd422/qVOVbLxbkm4xCsB6sZJgo.png)](https://cdn-uploads.huggingface.co/production/uploads/69d815b52c6db28cfdfdd422/qVOVbLxbkm4xCsB6sZJgo.png) `智能不会止步于模型的边界。编排层正在做出模型本身毫无可见度的实时分配决策。`

智能过去几乎完全坐在模型里：更大、训练得更好、能力更强，这就是比赛的主要内容。现在它还必须坐在基础设施里，坐在那个每时每刻决定几个相互竞争的工作负载中谁拿到刚释放的 GPU、以及相对队列里其他一切以什么优先级的层里。「保持 GPU 忙碌」不再本身就是目标，因为跑一些本可以等待的低优先级工作很容易伪造成「忙碌」。让每块已安装 GPU 产生的回报最大化才是真正的目标，而这被证明是一个比它前面的 provisioning 问题连续得多的问题。

把 provisioning 做好并不会让这个问题消失，只会改变它的形状。Provisioning 决策一次做出，在采购时。分配决策则不断做出：每次作业结束、每个新请求到来、客户服务与内部训练之间每一次优先级消长。这种频率解释了为什么这个决策已从「人逐案处理的事」变成「必须自动运行的事」。没有工程师会在凌晨三点盯着看板，决定一个刚跑完的训练该把它的手 GPU 交给排队的批作业，还是留着迎接即将到来的客户流量洪峰。必须有别的东西来持续做这个判断，并且正确到不需要任何人检查的频率。

这门学科足够新，其工具与惯例仍在成形，关于成熟的 GPU 管理实践长什么样，尚未出现单一的行动手册。至少已经确定的是：约束转移到了哪里。

### 专业化释放容量；编排把容量花出去

专业化和编排解决的是同一问题的两半。

专业的小型模型可以以大型通才模型完成同样工作所需资源的一小部分，执行特定任务，同时不牺牲任务所需的质量。这对利用率有直接影响：曾经需要单个大模型、在整个作业期间占据集群容量相当份额的工作负载，现在可以跑在占据其中一小块 footprint 的小型任务专用模型上。曾经被完全占死的容量突然空了出来。

专业化能释放多少容量因工作负载和模型而异，但释放出的容量总得有个去处，否则它就只是待在那里。一个更小的专用模型只有在有东西主动决定它腾出来的空间接下来怎么办——把它重新分配给另一个工作负载、另一个模型、队列后面等待的另一个任务——时才能转化为 GPU ROI。若无人管理，释放的容量会变成另一种风味的闲置而不是胜利：以一种不同于「明显未使用的 GPU」的方式隐形，但同样没有生产力。

[![dharma_fig3_specialization_matrix](https://cdn-uploads.huggingface.co/production/uploads/69d815b52c6db28cfdfdd422/uYM6Wj9TrcySE-l-LlI8O.png)](https://cdn-uploads.huggingface.co/production/uploads/69d815b52c6db28cfdfdd422/uYM6Wj9TrcySE-l-LlI8O.png) `没有编排的专业化，释放的是无人认领的容量。没有专业化的编排，本来就没有多少值得认领的容量。两根杠杆没有哪根能单独完成全部工作。`

没有编排的专业化释放的是无人认领的容量。没有专业化的编排，本来就没有多少值得认领的容量——因为模型仍然庞大，它们留下的空间仍然很小。两根杠杆没有哪根能单独完成全部工作；每一根都抬高了另一根所能达到的上限。如果目标是真正弥合已安装容量与有效产出之间的差距——而不是把浪费挪个位置——那么两根杠杆一根都不能少。

这正是为什么模型架构与 GPU 管理是应对同一问题的两种途径：从两个不同方向切入，最终彼此依靠。一个缩小每个工作负载所需；另一个持续决定差额流向何处。

更大的机队从来都是真实的优势，这里没有说的不是相反的话。在机队相当的航空公司之间——有时甚至是较小的机队面对较大的对手——赢家通常是那家更充分飞完手上飞机的，承载着这家航空公司在底下做好的一切的重量。企业 AI 正在从另一个方向抵达同一门学科。GPU 已经安装、已经在折旧、已经承诺出去了。专业化模型和 GPU 管理是平行的解，或者说双价策略。专业化缩小每个工作负载的需求；管理最大化基础设施的回报。同时掌握这两者的企业，将为下一个十年的 AI 竞争定速。
