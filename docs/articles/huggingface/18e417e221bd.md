## Bark 架构

**Bark** 是 Suno AI 在 [suno-ai/bark](https://github.com/suno-ai/bark) 中提出的基于 transformer 的文字转语音模型。它能生成多种音频输出：语音、音乐、背景噪声和简单音效，还能产出非语言交流声，比如大笑、叹息和啜泣。

Bark 从 🤗 Transformers v4.31.0 起就已提供！

你可以在[这里](https://colab.research.google.com/github/ylacombe/notebooks/blob/main/Bark_HuggingFace_Demo.ipynb)把玩 Bark、探索它的能力。

Bark 由 4 个主要模型构成：

- `BarkSemanticModel`（也称"文本"模型）：一个因果自回归 transformer 模型，输入是分词后的文本，预测捕捉文本含义的语义文本 token。
- `BarkCoarseModel`（也称"粗声学"模型）：一个因果自回归 transformer，输入是 `BarkSemanticModel` 的结果，目标是预测 EnCodec 所需的前两个音频码本。
- `BarkFineModel`（"细声学"模型）：这次是非因果自编码器 transformer，基于先前码本嵌入之和迭代预测后面的码本。
- 预测出 [`EncodecModel`](https://huggingface.co/docs/transformers/v4.31.0/model_doc/encodec) 的全部码本通道后，Bark 用它解码出输出音频数组。

写作本文时，有两个 Bark 检查点可用：[较小版](https://huggingface.co/suno/bark-small)和[较大版](https://huggingface.co/suno/bark)。

### 加载模型与处理器

预训练的 Bark small 和 large 检查点可以从 Hugging Face Hub 上的[预训练权重](https://huggingface.co/suno/bark)加载。你可以通过更换 repo-id 来选择想用的检查点规模。

为了速度快，我们默认用 small 检查点。想试 large 的话把 `"suno/bark-small"` 换成 `"suno/bark"` 即可。

```
from transformers import BarkModel

model = BarkModel.from_pretrained("suno/bark-small")
```

把模型放到加速设备上，才能最大化优化技术的效果：

```
import torch

device = "cuda:0" if torch.cuda.is_available() else "cpu"
model = model.to(device)
```

加载处理器（processor），它负责分词和可选的说话人嵌入。

```
from transformers import AutoProcessor

processor = AutoProcessor.from_pretrained("suno/bark-small")
```

## 优化技术

本节探索如何用 🤗 Optimum 和 🤗 Accelerate 的现成功能优化 Bark 模型，代码只需极小改动。

### 一些准备工作

准备输入，并定义一个测量 Bark 生成方法延迟和 GPU 内存占用的函数。

```
text_prompt = "Let's try generating speech, with Bark, a text-to-speech model"
inputs = processor(text_prompt).to(device)
```

测量延迟和 GPU 内存占用需要特定的 CUDA 方法。我们定义一个工具函数，同时测量模型推理时的延迟与 GPU 内存占用。为了让指标可信，我们对指定的 `nb_loops` 次运行取平均：

```
import torch
from transformers import set_seed


def measure_latency_and_memory_use(model, inputs, nb_loops = 5):

  # define Events that measure start and end of the generate pass
  start_event = torch.cuda.Event(enable_timing=True)
  end_event = torch.cuda.Event(enable_timing=True)

  # reset cuda memory stats and empty cache
  torch.cuda.reset_peak_memory_stats(device)
  torch.cuda.empty_cache()
  torch.cuda.synchronize()

  # get the start time
  start_event.record()

  # actually generate
  for _ in range(nb_loops):
        # set seed for reproducibility
        set_seed(0)
        output = model.generate(**inputs, do_sample = True, fine_temperature = 0.4, coarse_temperature = 0.8)

  # get the end time
  end_event.record()
  torch.cuda.synchronize()

  # measure memory footprint and elapsed time
  max_memory = torch.cuda.max_memory_allocated(device)
  elapsed_time = start_event.elapsed_time(end_event) * 1.0e-3

  print('Execution time:', elapsed_time/nb_loops, 'seconds')
  print('Max memory footprint', max_memory*1e-9, ' GB')

  return output
```

### 1. 🤗 Better Transformer

Better Transformer 是 🤗 Optimum 的一项功能，底层执行算子融合（kernel fusion）。这意味着模型的某些运算在 GPU 上会得到更好的优化，模型整体更快。

具体来说，🤗 Transformers 支持的大多数模型都依赖注意力机制——生成输出时选择性聚焦输入的某些部分，让模型能有效处理长程依赖、捕捉数据中复杂的上下文关系。

朴素的注意力技术可以通过 [Flash Attention](https://arxiv.org/abs/2205.14135) 大幅优化，这是 Dao 等人在 2022 年提出的。

Flash Attention 是更快更高效的注意力计算算法，它结合传统方法（如 tiling 与重计算）来最小化内存使用、提升速度。与之前的算法不同，Flash Attention 把内存占用从序列长度的二次方降到线性，特别适合对内存效率要求高的应用。

事实证明 Flash Attention 是 🤗 Better Transformer 开箱即用的！导出一行代码就能把模型导出到 🤗 Better Transformer 并启用 Flash Attention：

```
model =  model.to_bettertransformer()

with torch.inference_mode():
  speech_output = measure_latency_and_memory_use(model, inputs, nb_loops = 5)
```

**输出：**

```
Execution time: 5.43284375 seconds
Max memory footprint 1.9151841280000002  GB
```

### 2. 半精度

大多数 AI 模型通常使用单精度浮点存储格式，即 `fp32`。这是什么意思？每个数用 32 位存储。

你可以选择用 16 位编码数字——即半精度浮点（half-precision floating point），`fp16`——存储量直接减半！不仅如此，推理速度也会提升！

当然，代价是模型内部运算不如 `fp32` 精确，性能会有轻微下降。

加载 🤗 Transformers 模型时使用半精度，只需在 `BarkModel.from_pretrained(...)` 一行加上 `torch_dtype=torch.float16`！

也就是说：

```
model = BarkModel.from_pretrained("suno/bark-small", torch_dtype=torch.float16).to(device)

with torch.inference_mode():
  speech_output = measure_latency_and_memory_use(model, inputs, nb_loops = 5)
```

**输出：**

```
Execution time: 7.00045390625 seconds
Max memory footprint 2.7436124160000004  GB
```

输出听起来是这样（[下载音频](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/bark_optimization/audio_sample_fp16.wav)）：

### 3. CPU offload

如本教程第一节所述，Bark 由 4 个子模型组成，生成音频时依次调用。**也就是说，一个子模型在工作时，其他子模型都是闲着的。**

为什么这是个问题？在 AI 里 GPU 内存非常宝贵——它的运算最快，也常常是瓶颈。

一个简单的解法：子模型闲置时就从 GPU 卸载。这个操作叫 CPU offload。

**好消息：** Bark 的 CPU offload 已经集成进 🤗 Transformers，一行代码即可启用。

只需确保安装了 🤗 Accelerate！

```
model = BarkModel.from_pretrained("suno/bark-small")

# Enable CPU offload
model.enable_cpu_offload()

with torch.inference_mode():
  speech_output = measure_latency_and_memory_use(model, inputs, nb_loops = 5)
```

**输出：**

```
Execution time: 8.97633828125 seconds
Max memory footprint 1.3231160320000002  GB
```

输出听起来是这样（[下载音频](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/bark_optimization/audio_sample_cpu_offload.wav)）：

**它带来了什么？**

速度只有轻微损失（10%），换来内存占用的巨大缩减（60% 🤯）。

启用该特性后，`bark-large` 的占用只有 2GB，而不是 5GB——和 `bark-small` 一个量级！

### 使用批处理

还想要更多？

三种优化技术合在一起，配合批处理效果更好。批处理就是把多个样本的运算合并，总体生成时间低于逐样本生成。

用法示例：

```
text_prompt = [
    "Let's try generating speech, with Bark, a text-to-speech model",
    "Wow, batching is so great!",
    "I love Hugging Face, it's so cool."]

inputs = processor(text_prompt).to(device)


with torch.inference_mode():
  # samples are generated all at once
  speech_output = model.generate(**inputs, do_sample = True, fine_temperature = 0.4, coarse_temperature = 0.8)
```

## 基准测试结果

如前所述，我们做的小实验只是一种思路演练，要更准确地衡量性能还需要扩展。测量前应先用几次空迭代把 GPU "热身"。

下面是对 100 个样本、扩展测量后的基准结果，**使用 Bark large 版本**。

基准测试在 NVIDIA TITAN RTX 24GB 上运行，最多生成 256 个新 token。

### 如何解读结果？

#### 延迟

衡量一次生成方法调用的时长，与批量大小无关。

也就是 elapsedTime / nbLoops。

**越低越好。**

#### 最大内存占用

衡量一次生成方法调用期间的最大内存使用量。

**越低越好。**

#### 吞吐量

衡量每秒生成的样本数，这次会把批量大小计入。

也就是 (nbLoops * batchSize) / elapsedTime。

**越高越好。**

### 不做批处理

以下是 `batch_size=1` 的结果。

| 绝对值 | 延迟 | 内存 |
| --- | --- | --- |
| 无优化 | 10.48 | 5025.0M |
| 仅 bettertransformer | 7.70 | 4974.3M |
| offload + bettertransformer | 8.90 | 2040.7M |
| offload + bettertransformer + fp16 | 8.10 | 1010.4M |

| 相对值 | 延迟 | 内存 |
| --- | --- | --- |
| 无优化 | 0% | 0% |
| 仅 bettertransformer | -27% | -1% |
| offload + bettertransformer | -15% | -59% |
| offload + bettertransformer + fp16 | -23% | -80% |

#### 点评

不出所料，CPU offload 大幅降低内存占用，同时轻微增加延迟。

但与 bettertransformer 和 `fp16` 组合后，我们鱼与熊掌兼得——延迟和内存双双大幅下降！

### 批量大小设为 8

以下是 `batch_size=8` 并测量吞吐量的基准结果。

注意，由于 `bettertransformer` 是"免费"优化——它做的运算与非优化模型完全相同、内存占用也一样，只是更快——本基准**默认启用该优化**。

| 绝对值 | 延迟 | 内存 | 吞吐量 |
| --- | --- | --- | --- |
| 基线（bettertransformer） | 19.26 | 8329.2M | 0.42 |
| + fp16 | 10.32 | 4198.8M | 0.78 |
| + offload | 20.46 | 5172.1M | 0.39 |
| + offload + fp16 | 10.91 | 2619.5M | 0.73 |

| 相对值 | 延迟 | 内存 | 吞吐量 |
| --- | --- | --- | --- |
| 基线（bettertransformer） | 0% | 0% | 0% |
| + fp16 | -46% | -50% | 87% |
| + offload | 6% | -38% | -6% |
| + offload + fp16 | -43% | -69% | 77% |

#### 点评

这里正是三种优化组合威力的体现！

`fp16` 对延迟的影响在 `batch_size = 1` 时不算明显，但在这里价值巨大：延迟几乎减半，吞吐量几乎翻倍！
