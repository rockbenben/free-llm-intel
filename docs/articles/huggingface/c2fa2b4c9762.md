# 高效的请求排队——LLM 性能优化

同时为众多应用和用户服务 LLM 很具挑战，因为它们竞争有限的 GPU 资源。本文是关于 LLM 性能系列的第一篇，基于我们在 TNG Technology Consulting GmbH 自托管 LLM 的服务经验。第一部分聚焦排队带来的影响，并讨论不同的调度策略。

### 起点：一个裸推理引擎

像 [vLLM](https://github.com/vllm-project/vllm) 或 [HuggingFace TGI](https://github.com/huggingface/text-generation-inference/) 这样的推理引擎由以下部分组成：

- 一个 worker，负责计算请求中下一个 token 的实际工作
- 一个队列，请求刚到达时加入此处
- 一个调度器，从队列取请求并交给 worker

为什么这里需要队列？因为 GPU 上的计算按批次做比逐个请求孤立地做更高效、更省资源。这个后端队列让调度器可以挑选多个请求放进同一个批次处理。

注意，通常每个推理引擎只服务单个模型，我们为不同模型并行运行多个部署。

### 问题："重度用户"会阻塞其他用户

当单个用户 "A" 发送大量请求时，会迅速把队列占满。稍后发送请求的其他用户（"B" 和 "C"）将被阻止使用该模型（直到 A 的全部请求处理完毕）。注意图中以 vLLM 为推理引擎，但问题更普遍，对其他后端同样成立。

[![image/png](https://cdn-uploads.huggingface.co/production/uploads/65263bfb3177c2a794997821/4brEVTNStGfeB0mPXt4PN.png)](https://cdn-uploads.huggingface.co/production/uploads/65263bfb3177c2a794997821/4brEVTNStGfeB0mPXt4PN.png)

### 解决方案：公平调度

在 TNG，用户不是把请求直接发给 vLLM 后端，而是发给一个 API Server（我们称为 "LLM-Server"）。这里可以为每个用户（和模型）设置独立队列，调度器不再是 FIFO（先进先出），而是对所有用户队列轮询（round-robin）。这实现了某种**公平调度**：例如在图中，用户 B 和 C 稍晚发送请求，此时用户 A 的第一个请求已被调度。那时 A 的三个请求已等待了一段时间，但用户 C 只需等 A 的一个请求完成。

关键思想是：在我们自己的组件而非推理后端中，对不同用户的请求做优先级排序！通常，请求一旦发进推理引擎就无法再改变顺序，所以你必须在它们还留在 LLM-Server（我们拥有完全控制的地方）时把它们排成正确的顺序。

[![image/png](https://cdn-uploads.huggingface.co/production/uploads/65263bfb3177c2a794997821/ftwRe4gwSxdeDQmje9Tk2.png)](https://cdn-uploads.huggingface.co/production/uploads/65263bfb3177c2a794997821/ftwRe4gwSxdeDQmje9Tk2.png)

#### 可能的扩展

你可以从不同方面判断什么样的调度算"公平"。上面的例子中，任何只有一个新请求的用户应先于任何被连续服务两次以上的用户得到服务。这是在请求数量层面的"公平"。但你也可以看**处理时间**：一个请求会让后端忙碌多久？长 prompt 和长生成会为其他用户"阻塞"LLM 更长时间，那么也许更短的请求应有优先权？遗憾的是，生成长度非常难估计。虽然有些请求带 "max_tokens" 限制，但交互式 AI 助手的典型聊天消息没有 token 上限，生成长度可能从极短（"总结这段文字"）到极长（"给我讲个故事"/"写出 xyz 的全部代码"）不等。

根据 prompt 内容，按相似度组织请求可以让 vLLM **最大化缓存命中**从而提升性能，可能有些收益。这种 KV-cache 感知的路由近期因 [NVIDIA Dynamo](https://github.com/ai-dynamo/dynamo) 和 [AIBrix](https://github.com/vllm-project/aibrix/) 等框架受到关注。

在业务场景和托管 LLM 中，单个请求的**成本**可以是另一个考量指标，但同样有类似挑战。

解决方案还可以扩展：不只为每个用户（和模型）设一个队列，而是设**多个不同优先级的队列**。例如，带聊天界面的交互应用（如 [TNG 的 AI Assistant](https://taia.tngtech.com/welcome)）应有更高优先级，因为五秒内看不到进展的用户会以为应用坏了。而为几十个文件、数千行代码生成代码审查的用户，则预期 LLM 请求要花些时间。还有些用例（如通过 batch API 调度的基准测试运行）优先级应足够低，低到不打扰其他用例、只在无事运行时才被调度。

### 问题：后端队列没有背压

再考虑一个场景：用户 A 一次发送大量请求，一段时间后新用户 C 加入，想调度一个请求。如果 LLM-Server 侧的调度器按公平优先级立即把所有请求发给后端，A 的所有请求又会堆积在 FIFO 队列里。新用户 C 仍要等所有先前请求处理完。相比没有 LLM-Server 的初始场景几乎没有任何改善。

理想情况下可以限制后端队列的最大元素数，但 vLLM 不提供这个选项。因此我们必须动态调整 LLM-Server 侧调度器向后端发送新请求的速率。我们的目标是：**保持后端队列短小**，把新用户感受到的延迟降到最低。

（最简单的做法是静态限速，但当大多数请求都很短时，这很可能导致利用率不足，而且很难针对不同模型和负载模式校准。）

### 解决方案：抓取指标

为了在后端队列长度信息在 LLM-Server 中可用，我们需要从 vLLM 的 /metrics 端点抓取相应的 Prometheus 指标。我们的公平调度器仅当**后端队列长度指标**小于（例如）三时才被允许向后端发送请求。这个后端队列目标长度可以调低，让新用户的延迟更短，直到批次利用率不足、效率下降——这是权衡。但请记住，目标队列长度并不反映最大并发数；仍可能有超过三个请求并行处理——vLLM 一旦有足够空间就会把排队请求加入当前批次（"continuous batching"）。

#### 可能的扩展

一旦你在后端队列与 LLM-Server 调度器之间建立了反馈回路，就可以轻松扩展用于调度决策的 vLLM 指标集合。例如，为了给 TNG 的交互 AI 助手良好的用户体验，我们追求较高的 token 生成速度（例如 >7 tokens/s，即约每 token 150ms）；如果报告的 **time-per-output-token 指标**超过 150ms，就不再调度新请求。

你还可以**为不同的请求优先级设置不同的指标阈值**。例如，对来自 batch API 的低优先级请求，只有在后端队列完全为空时才调度：我们宁可冒 GPU 短暂闲置的风险，也不愿推高后来更高优先级请求的延迟。

这里还有相当大的优化空间：例如，若你允许队列长度短于三时调度，而当前指标为零，你可以立即向后端发三个请求而无需先再抓取指标。最坏情况是它们全都进不了当前批次、全在后端队列里（此时新长度为三，正好达标）。

### 替代方案：后端侧优先级调度

最近，vLLM 在 FIFO 之外新增了基于优先级的调度选项。对这一新特性，请求在发送到后端之前被打上优先级标签。vLLM 会定期检查是否有更高优先级的请求在排队，然后按优先级对所有请求排序（包括运行批次和等待队列）。这不仅让高优先级请求字面意义上的插队，甚至直接移入正在处理的批次。代价（除排序带来的部分开销外）是低优先级请求会被逐出运行批次、放回等待队列。

[![image/png](https://cdn-uploads.huggingface.co/production/uploads/65263bfb3177c2a794997821/uZ0L5uHQA_e-u1SSRifsz.png)](https://cdn-uploads.huggingface.co/production/uploads/65263bfb3177c2a794997821/uZ0L5uHQA_e-u1SSRifsz.png)

#### 后端侧优先级调度能取代 LLM-Server 侧的全部队列吗？

vLLM 把请求优先级理解为连续数值。这不仅允许你区分默认、高优先级（交互 AI 助手）和低优先级（batch API），你甚至可以对用户已发往后端、响应仍未到达的每个请求逐级减小额度。例如用户 B 和 C 只发送单个请求，优先级为零。用户 A 一次发送四个请求：第一个优先级也是零，但随后的优先级分别为一、二、三，会被更晚处理（数字越大优先级越低）。

仍有几个注意点：

- 后端优先级特性只有 vLLM 支持，HuggingFace TGI 不支持。
- 在 LLM-Server 侧设调度器，让你能基于 time-per-output-token 调整调度速率。后端优先级调度不控制调度速率。
- 频繁重排队列和批次对延迟的影响，仍需在真实负载场景中测量。

总体而言，对基于 vLLM 的系统，后端侧优先级调度可以是不错的策略，因为它简化了上游 LLM-Server 的排队逻辑。遗憾的是，在真实环境中你无法摆脱作为额外调度层的 LLM-Server，因为需要某个客观主体来为单个请求分派优先级。

### 总结与展望

对拥有多个用户、优先级各异的客户端的应用，排队与调度至关重要，因为它们显著影响用户体验。尤其在多个客户端并行提交请求的场景，值得采用专门的"公平调度"策略。虽然优先级调度这类后端特性能简化优化，要完全驾驭这些复杂性，上游网关服务器仍然必不可少。
