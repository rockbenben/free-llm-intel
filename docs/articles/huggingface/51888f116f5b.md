#### 这是 Microsoft 与 Hugging Face 的联合博客，特别感谢 Microsoft 的 Mirco Milletari 和 Xiang Jiang、Hugging Face 的 Sergio Paniego，以及我们的前实习生 Zhuochun Li（匹兹堡大学）在共同撰写/审阅上的付出。

我们构建 ThinkingBox，是为了抓住那些说自己做完了、其实并没有的智能体。

ThinkingBox-Bench（我们的基准数据集）里的 507 个任务，每一个都会给智能体一个真实后端和一组工具，让它动手干活，然后检查数据库里究竟发生了什么变化。[在第一篇文章中](https://huggingface.co/blog/microsoft/thinkingbox)，我们抓到一个模型把客户的工单标为 **resolved**，而背后承运商的异常记录仍然开着。九次看起来很像样的工具调用，一行**错误**的数据库记录。

接着我们注意到了自己造出来的东西。对大多数任务而言，可执行检查可以直接从最终数据库状态返回 1 或 0。那就不只是一个评分器了。**这可以是一个奖励函数。**+

于是我们把基准之外、ThinkingBox 格式的任务搭成一个训练池，并用它们的可执行结果作为奖励。难点在于选出**哪些**任务适合智能体训练：大多数任务要么已经被解决，要么对眼前的这个模型毫无希望，而这两种情况都教不会它任何东西。

> 难度是相对于策略的：一个任务只在该模型学会它之前，才对这个模型来说很难。

我们称之为**离线策略相对难度**。训练之前，我们用基础策略把每个任务的单次成功概率估计一遍，并在整个训练过程中保持选定的训练池固定不变。

### 训练之后发生了什么

我们用离线策略相对难度构建训练池，随后用 GRPO 对 Qwen3.8-27B 微调 50 步。回顾一下设定：我们对 507 个基准任务各评估 20 次。pass@1 衡量全部 10,140 次尝试的平均成功率。pass@20 衡量至少被解决一次的任务占比。观测到的 20/20 衡量在每一次记录下来的尝试中都通过的任务占比。

*表 1。在离线选出的训练池上执行 50 步 GRPO 前后的 Qwen3.8-27B 结果。*

| 指标 | 基础 |  | RL 微调 | 变化 |
| --- | --- | --- | --- | --- |
| **观测到的 20/20** | 38 (7.50%) | → | **107 (21.10%)** | **+69 个任务** |
| pass@1（成功尝试） | 5,242 (51.70%) | → | **6,163 (60.78%)** | **+9.08 个百分点** |
| pass@20（至少解决一次的任务） | 453 (89.35%) | → | **446 (87.97%)** | **−7 个任务** |

训练**大幅提升**了可重复的成功率，同时至少一次覆盖率略有下降。本文余下部分会解释我们如何挑选练习任务、如何搭建奖励循环，以及如何衡量这一取舍。

**这种改进在单个任务上是什么样子？** 一位旅客申请把房间降级，但公司政策要求先取得经理批准。训练之前，智能体在 20 次尝试中有 15 次未经批准就更改了预订并办理了退款。经过 RL 微调之后，它在全部 20 次中都保住了预订与支付状态。

## 基准发现了什么，六十秒读完

[ThinkingBox-Bench](https://huggingface.co/datasets/microsoft/ThinkingBox-Bench) 按智能体留下的数据库记录给它评分。它的 507 个任务每一个都启动一个真实后端，交给智能体一组 MCP 工具和一个带有私有上下文的模拟 LLM 用户，最后针对终端数据库状态运行可执行检查。检查针对的是必须正确的那条后端记录，而不是具体的工具调用。这会激励模型去发现可能全新的解题路径，而不是"重新发现"人类写出的那个解法——后者即便正确，也可能并不是最优的。

[在我们的第一篇文章中](https://huggingface.co/blog/microsoft/thinkingbox)，我们让十八个模型各跑了二十遍该基准，并报告了一个被头条准确率掩盖的差距。Kimi-K3 *至少一次*解决了 93.89% 的任务，但在**全部二十次记录尝试**中只完成了 507 个任务里的 68 个（13.41%）。Claude Opus 5 正好相反：覆盖面更窄，一致性高得多。

而且更大或更好的模型并没有填上这道沟。Claude Opus 5.5 在 pass@1 上比 Claude Opus 5 高 0.66 个百分点，但在全部二十次尝试中通过的任务数量**完全相同，都是 241 个**。头条准确率上的这点增益，买到的额外可靠性是零。

如果你要为会触碰生产数据库记录的工作挑选模型，pass@1 不该被单独解读。观测到的 20/20 显示的是哪些任务在每一次尝试中都成功，这更接近生产可靠性所要求的东西。

可执行的终端状态判决同时也是训练奖励。在展开训练循环之前，先看看在被封存的基准上发生了什么变化。

## 结果：可靠性那一列动了

训练完 Qwen3.8-27B 之后，我们在它从未训练过的 507 任务基准上评估了选定的 step-50 checkpoint。这 507 个任务构成了一个分布外测试集：它们的领域、数据库以及大多数 MCP 工具，在 RL 训练期间都没有出现过。

| 模型 | 零售 | 汽车保险 | 旅行 | 数字银行 | 咨询 | 总体 | 观测到的 20/20 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Claude Opus 5.5 | 80.97 | **68.40** | 54.28 | **71.25** | 61.58 | **67.16** | **241 (47.53%)** |
| Claude Opus 5 | 80.71 | 65.80 | 49.95 | 70.62 | **66.19** | 66.50 | **241 (47.53%)** |
| GPT-5.4 | 76.33 | 62.65 | **68.12** | 65.34 | 54.60 | 65.36 | 128 (25.25%) |
| GPT-5.6 Sol | 67.65 | 65.30 | 60.34 | 59.09 | 57.52 | 61.91 | 82 (16.17%) |
| **Qwen3.8-27B RLFT** | 67.91 | 56.45 | 62.69 | 62.40 | 54.51 | 60.78 | 107 (21.10%) |
| Claude Sonnet 4.6 | 72.35 | 54.40 | 58.94 | 56.39 | 54.31 | 59.19 | 102 (20.12%) |
| GPT-6 Astra | 71.73 | 46.55 | 55.87 | 60.87 | 56.83 | 58.31 | 231 (45.56%) |
| Kimi-K3 | **82.24** | 50.80 | 61.83 | 41.35 | 51.63 | 57.37 | 68 (13.41%) |
| Qwen3.8-27B | 64.03 | 47.85 | 53.41 | 47.88 | 45.69 | 51.70 | 38 (7.50%) |

**头条结果是表 1 中观测到的 20/20 那一行。** 一个**27B 模型**最初只能在每一次尝试中完成 ThinkingBox-Bench 的 38 个任务（7.5%），现在每一次尝试能完成 107 个（21.1%），几乎是原来的三倍。作为对照，Kimi-K3 的观测 20/20 是 68，GPT-5.4 是 128，GPT-6 Astra 是 231，Claude Opus 5.5 以 241 领先。

**平均成功率与可重复性会给出不同的排序。** 在表 2 中我们注意到，GPT-5.6 Sol 的 pass@1 略高于 RL 微调后的 Qwen3.8-27B（61.91% 对 60.78%），但在全部 20 次记录尝试中通过的任务更少：82 对 107。Claude Sonnet 4.6 的 pass@1 更低，为 59.19%，但每次都能通过几乎同样多的任务，为 102 个。单看任一指标都无法呈现全貌。

观测到的模式与"锐化"一致：可重复的成功率上升，而至少一次覆盖率小幅下降。这与[先前的工作](https://arxiv.org/abs/2504.13837)相符。一种解释是，概率分布向那些能反复奏效的轨迹移动，同时一些低概率路径消失了。

> 总体而言，模型并没有变得更宽。它变得更能重复。下一个问题是这些增益落在了哪里。

## 可靠性要付出什么代价

[第一篇文章](https://huggingface.co/blog/microsoft/thinkingbox)用简单算术给一致性定了价：把**完整的 20 次评测活动的预估成本**，除以模型每一次都通过的任务数。

> 每个可靠任务的成本 = 507 × 20 评测活动的预估成本 ÷ 通过 20/20 的任务数

把同样的成本算术套用到微调 checkpoint 的实测 token 用量上：

*表 3。基础版与 RL 微调版 Qwen3.8-27B 的预估评测成本与可靠性。每次成功尝试的成本，等于评测活动总预估成本（507 x 20）除以通过的尝试次数。*

| 度量 | 基础 |  | RL 微调 | 变化 |
| --- | --- | --- | --- | --- |
| 评测活动成本，20 次运行 | $925.80 | → | **$855.58** | **−7.6%** |
| 每次成功尝试的成本 | $0.177 | → | **$0.139** | **−21.4%** |
| 通过 20/20 的任务数 | 38 | → | **107** | **2.8 倍** |
| **每个可靠任务的成本** | $24.36 | → | **$8.00** | **−67.2%** |

以每个可靠任务 $8.00 计，微调后的模型在配套对比中已接近 GPT-5.4（$6.80）、GPT-6 Astra（$7.45）和 Claude Opus 5.5（$7.80）。

[![fig3-cost-frontier](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/HPq2TNCT8yskCAGtKe86l.png)](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/HPq2TNCT8yskCAGtKe86l.png)

这一移动把微调后的 checkpoint 放到了 GPT-5.6 Sol 附近，不过 GPT-5.6 Sol 依然更便宜，pass@1 也略高。[我们的论文](https://arxiv.org/abs/2608.19741)中定价的四个模型落在绘图范围之外。

这些美元数值是相对性的服务指数，不是账单或云费用。服务微调后的 checkpoint 与基础模型相同。计算包含模型推理成本，不包含训练运行成本，也不包含为整理训练数据集而做策略探测的成本。

这些结果告诉我们什么移动了。接下来的几节会解释训练循环，以及为什么选对任务最为关键。

## 训练循环

[![fig4-training-overview](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/ZaqyG8RtqCRsxGdxUQMfi.png)](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/ZaqyG8RtqCRsxGdxUQMfi.png)

*图 5。六个阶段放在上下文中：候选任务输入，前三个阶段离线只跑一次，后三个阶段在训练运行中为每个组重复。训练出的 checkpoint 用 ThinkingBox-Bench 评估。*

选择只离线跑一次，针对基础策略模型，也就是本例中的 Qwen3.8 27B；训练随后使用这个已经整理好、固定不变的池子。图 5 中的琥珀色虚线箭头标出我们没有走的那条路：在训练运行期间重新探测难度。

每次 rollout 都是一个完整回合，而不是一次文本补全。它拿到全新的后端、隔离的 MCP 会话，以及作为模拟用户的 GPT-5 Chat。大多数奖励来自确定性的终端状态检查；少数狭窄的评分细则要求可以调用配置好的裁判（GPT-5 Chat）。

**训练与评估必须以相同方式解释 Qwen 的输出。** 这包括推理内容抽取、工具调用、参数类型、渲染，以及隔离的任务状态。否则奖励衡量的就是另一个智能体，而不是被评估的那个。共享的解释代码在 [`trainer/core/tb_interpret.py`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/trainer/core/tb_interpret.py)。

在参考运行中，我们用 token-mean GRPO 在 187 个任务上做了全参数 RL 微调 Qwen3.8-27B。每次更新生成 18 组、每组 8 次 rollout，共 144 个回合，跑在 24 张 H100 上。训练同步进行，采用参数与优化器 offload；AdamW 使用 `1e-6` 学习率和零权重衰减。我们训练了 50 步。

训练期间，零方差组按 [DAPO 的方式](https://arxiv.org/abs/2503.14476)被替换。系统错误单独处理：后端超时不是智能体的错误结果，因此受影响的组被补满，而不是记为失败。

这解释了保留下来的任务是如何训练的。剩下的问题是哪些任务进入了训练池。

## 离线策略相对难度

在深入训练任务的选择之前，先说一句免责声明：

> RL 训练池中没有包含任何 ThinkingBox-Bench 任务。该基准被保留用于评估。

相对于 RL 训练池，ThinkingBox-Bench 是分布外的：它的领域、数据库、策略以及大多数工具在 RL 训练期间都没有出现。两个集合仍然共享 ThinkingBox 框架、模拟用户机制、可执行的终端状态评分、少数通用工具，以及相似的任务风格。这些共享要素限定了迁移结论的范围。

为什么选择如此重要，归结为 GRPO 的一个算术事实。如果八次 rollout 全部失败，奖励向量就是 `[0, 0, 0, 0, 0, 0, 0, 0]`。如果八次全部成功，就是 `[1, 1, 1, 1, 1, 1, 1, 1]`。两种情况下，组内中心化都不会产生任何任务奖励优势，因为没有哪条轨迹比其他轨迹做得更好。++

而像 `[0, 0, 0, 1, 1, 1, 1, 1]` 这样的混合组，提供了 GRPO 可以学习的对比。对一个有状态的智能体来说，这种区分很贵：每次 rollout 都要准备隔离的后端、运行真实的工具会话，并调用另一个模型来扮演用户。

因此塑造这项工作的关键问题，不只是*用哪个模型或优化器？* 而是：**哪些候选任务应当进入固定的训练池？**

我们用在后验上的离线通过率过滤器来挑选训练池。它估计哪些任务在基础策略下有可能产生形成对比的终端奖励。

于是我们去探测。每个候选任务都在**基础策略**模型上反复运行。用大白话说，规则很简单：模型总是失败的任务，眼下大概还教不会它；模型总是通过的任务，已经学会了；**模型有时能解决的任务，才是结果能提供对比的地方。**

### 用有限次探测估计难度

每个候选任务运行 *n* 次，产生 *k* 次成功。我们用 Jeffreys 后验概率为其潜在成功率建模：

> 成功概率 | n 次探测中的 k 次成功  ~  Beta(k + ½, n − k + ½)

[![fig5-policy-relative-difficulty](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/eR45y7Dl0VFFK3HinwDYg.png)](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/eR45y7Dl0VFFK3HinwDYg.png)

*图 6。离线策略相对难度由反复的基础策略探测估计得出，用于保留那些有可能产生对比奖励的任务。*

我们把单位区间划分成五个桶，边界取 0.08、0.40、0.60 和 0.90，作为这几轮运行的超参数。每个任务被分配到后验质量最大的那个桶：

- **极少解决 [0, 0.08)：** 丢弃
- **困难 [0.08, 0.40)：** 保留
- **中间 [0.40, 0.60)：** 保留
- **经常解决 [0.60, 0.90)：** 保留用于全参数 RLFT
- **几乎总能解决 [0.90, 1]：** 丢弃

更多细节见[我们 ThinkingBox 论文的附录 C.4](https://arxiv.org/pdf/2608.19741)。

### 一个任务，端到端

[![fig6-worked-example](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/IBBkNpYKQRK6jBLSusMXw.png)](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/IBBkNpYKQRK6jBLSusMXw.png)

*图 7。放大来看，一个任务走完六个阶段：GPT-5.4 筛查、基础模型探测、难度分类、一次 rollout 组、终端状态评分，以及一次 GRPO 更新。*

图 7 追踪的是一个有可能进入训练池的候选任务。对于 Qwen3.8 27B 的全参数池，GPT-5.4 先充当可解性筛查器。随后基础策略在探测中只成功了少数几次，例如 8 次中成功 3 次，得到一个 Beta(3.5, 5.5) 后验。其后验质量的最大部分 54.0% 落在"困难"档。

被采样用于训练时，这个任务产生了混合奖励组 `[0, 0, 0, 0, 1, 1, 1, 1]`。于是成功的轨迹获得高于均值的任务优势，失败的轨迹获得低于均值的优势，为 GRPO 提供了可学习的对比。换一个策略模型，同一个任务可能被放进不同的难度档。

Qwen3.8-27B 最终整理出的训练池包含 187 个任务。

## 什么能拿到奖励

跟轨迹本身毫无关系。奖励是任务自带的那个可执行判决。

当一个回合结束，沙箱会抽取后端中实际发生的变化，并针对终端状态运行该任务的确定性检查。任何产生正确终态的轨迹都算通过。错误、缺失或多余的副作用都算失败。奖励是 1 或 0。

在基准里，数据库评分器可以看作"考官"：它抓到了那些汇报成功却留下错误记录的智能体。在训练里，同一类检查可以在另一组不相交的任务上被看作"老师"。

> 两条奖励路径，一个二元判决
> 
> 可执行检查（绝大多数）。当所需结果体现在终端状态或副作用中时，一个确定性测试接受或拒绝它；无需调用 LLM 裁判。
> 裁判辅助检查（少数）。当某项狭窄要求无法从数据库状态干净地判定时，配置好的 LLM 裁判回答一个二元细则问题，供可执行测试使用。

## 跑起训练栈

我们在 [microsoft/thinkingbox-training](https://github.com/microsoft/thinkingbox-training) 中发布了用于训练 Qwen3.8-27B 的数据选择、rollout、奖励以及 Verl 集成。仓库的 README 是入口。详细指南包括：

- [`docs/data-preparation.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/data-preparation.md)，涵盖任务注入、策略探测、基准排除以及训练/验证划分；
- [`docs/reference-q38-run.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/reference-q38-run.md)，涵盖经过验证的 24 卡 H100 Qwen3.8 配置；
- [`docs/evaluation.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/evaluation.md)，涵盖合并 checkpoint 并运行 ThinkingBox-Bench 507 x 20。

### 开始之前

在 Linux 和 WSL 上以 Python 3.12 和 [uv](https://docs.astral.sh/uv/) 测试通过。你需要具备兼容 CUDA/NCCL 软件栈的 NVIDIA GPU、本地的 Qwen3.8-27B checkpoint，以及供模拟用户和裁判使用的 OpenAI 兼容端点。经过验证的参考配置使用 3 个节点 × 8 张 H100 GPU；更小的自定义配置取决于模型规模、上下文长度和 rollout 并发度。

公开的示例任务列表用于跑通接口。它不是报告中所用、私有的 187 任务训练池。请提供一个获得授权的训练数据源，并保证它与公开基准不相交。

### 安装

把三个仓库并排放在一起：

```
mkdir -p ~/thinkingbox-workspace
cd ~/thinkingbox-workspace

git clone https://github.com/microsoft/thinkingbox.git
git clone https://github.com/microsoft/thinkingbox-data.git
git clone --branch main https://github.com/microsoft/thinkingbox-training

git -C thinkingbox checkout 892964e7226044e5463ad188da119df838f4bec1
git -C thinkingbox-data checkout thinkingbox-bench-v1.0
```

### 创建经过验证的环境

发布的这套栈面向 Linux、Python 3.12、Verl 0.9.0 以及锁定的依赖包版本：

```
cd ~/thinkingbox-workspace/thinkingbox-training

uv venv --python 3.12
source .venv/bin/activate

uv sync --frozen --extra fast --extra tracking --extra eval-proxy
uv pip install -e ../thinkingbox
uv pip install --config-settings editable-mode=compat \
  -e ../thinkingbox-data/servers/thinkingbox_tools
uv pip install --config-settings editable-mode=compat \
  -e ../thinkingbox-data/servers/tb_business_ops_servers_202606

python scripts/prepare_verl.py --dest .deps/verl --install
python scripts/verify_verl_install.py
uv pip check
```

最后两条命令应当报告：已验证打过补丁的 Verl checkout，且没有损坏的依赖关系。此后不要再跑另一次自动依赖同步：它可能用原版 Verl wheel 覆盖掉打过补丁的源码安装。

### 准备训练数据

从公开提供的样本开始，或者按 ThinkingBox 格式加入你自己的授权数据集。然后运行仓库的准备脚本：

```
cd ~/thinkingbox-workspace/thinkingbox-training
source .venv/bin/activate
python data/prepare_data.py --help
```

该脚本汇总策略探测结果、应用离线策略相对难度过滤与基准排除，并写出选定的 `train.yaml` 与 `test.yaml` 文件。[`docs/data-preparation.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/data-preparation.md) 记录了输入字段、加载器契约和完整命令。

### 配置并检查启动

按照 [`docs/reference-q38-run.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/reference-q38-run.md) 启动 Typesense 和 MCP 服务器，配置模拟用户与裁判，设置模型、任务列表、checkpoint 和拓扑相关变量，并准备好 Ray 集群。请把凭据放在运行时密钥注入里，而不是提交进文件或留在 shell 历史中。

在分配训练作业之前，先运行指南里的 dry-run 命令：

```
DRY_RUN=true ./scripts/run_train.sh \
  trainer.total_training_steps=50 \
  trainer.save_freq=5
```

它必须以零退出码结束，且不启动 Ray、不占用 GPU。启动正式运行之前，读一遍它输出的 `python -m verl.trainer.main_ppo` 命令以及每一项解析后的覆盖参数。

### 训练

启动器只负责配置训练，不负责准备主机。在参考的三节点拓扑上，在每个节点上导出相同的环境变量，把 `CHECKPOINT_DIR` 挂载到相同的绝对路径，然后启动 Ray：

```
# head node
ROLE=head NODE_IP="$HEAD_IP" GPUS_PER_NODE=8 \
  ./scripts/start_ray.sh

# each worker node
ROLE=worker NODE_IP="$WORKER_IP" \
  HEAD_ADDRESS="$HEAD_IP:6379" GPUS_PER_NODE=8 \
  ./scripts/start_ray.sh
```

等 `ray status` 报告全部 24 张 GPU 之后，在 head 节点上启动一次：

```
export RAY_ADDRESS=auto
export GPUS=0,1,2,3,4,5,6,7

./scripts/run_train.sh \
  trainer.project_name=thinkingbox-training \
  trainer.experiment_name=q38-full-rlft \
  trainer.total_training_steps=50 \
  trainer.save_freq=5
```

### 通过 OpenEnv 评估 checkpoint

[第一篇 ThinkingBox 文章](https://huggingface.co/blog/microsoft/thinkingbox#run-it-yourself)涵盖了 Typesense、MCP Session Proxy 和 OpenEnv 的设置。按照 [`docs/evaluation.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/evaluation.md) 合并训练好的 checkpoint，然后用 vLLM 提供服务。

在 OpenEnv 仓库根目录下，把 `MERGED_MODEL` 设为合并后的模型目录，把 `THINKINGBOX_DATA` 设为锁定版本的基准 checkout。历史上做 checkpoint 评估时使用的是这套八卡 A100 服务配置：

```
vllm serve "$MERGED_MODEL" \
  --served-model-name q38-rlft \
  --host 127.0.0.1 \
  --port 8001 \
  --tensor-parallel-size 8 \
  --dtype bfloat16 \
  --max-model-len 262144 \
  --gpu-memory-utilization 0.85 \
  --max-num-seqs 16 \
  --max-num-batched-tokens 8192 \
  --language-model-only \
  --enable-chunked-prefill \
  --enable-prefix-caching \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_xml
```

在另一个终端里，从 ThinkingBox Training 的 checkout 启动针对 Qwen 对话模板的 OpenEnv 兼容代理。它监听 8014 端口，并转发到 8001 上的 vLLM：

```
cd ~/thinkingbox-workspace/thinkingbox-training
source .venv/bin/activate
bash scripts/launch_sysmerge.sh
```

评估期间保持它运行。再从另一个终端检查就绪状态：

```
curl --fail http://127.0.0.1:8014/readyz
```

更新现有 `thinkingbox.yaml` 中的 agent 条目；保留它的 MCP、模拟用户和裁判配置：

```
orchestrator:
  agent_model:
    type: aoai
    endpoint_url: http://127.0.0.1:8014/v1/chat/completions
    deployment: q38-rlft
    credential:
      type: api-key
      api_key: <your_api_key>
    is_reasoning: true
    temperature: 1.0
    top_k: 20
    top_p: 0.95
    max_completion_tokens: 8192
    timeout: 1800
```

像第一篇文章那样启动 OpenEnv，把 `OPENENV_TB_CONFIG` 指向这个 `thinkingbox.yaml`，把 `OPENENV_TB_DATASET` 指向 `$THINKINGBOX_DATA`。等 `/ready` 成功后，跑完整协议：507 个任务 × 20 次尝试：

```
uv run --project envs/thinkingbox_env --frozen \
  thinkingbox-eval \
  --config "$PWD/thinkingbox.yaml" \
  --base-url http://127.0.0.1:8000 \
  --dataset "$THINKINGBOX_DATA" \
  --output q38-rlft-full.jsonl \
  --errors-output q38-rlft-full-errors.jsonl \
  --repeat 20 \
  --coverage-profile full \
  --aggregate-output q38-rlft-full-aggregate.json \
  --message-timeout 1800
```

`full` 配置会在聚合之前校验全部 10,140 个预期的任务/重复键。

## 接下来往哪儿走

这项工作有用的部分不是一个 Qwen3.8-27B checkpoint，而是把可执行结果变成奖励的训练循环与训练数据整理流程。

如果你正在训练或评估一个会触碰真实数据库记录的智能体：

- **训练之前先探测。** 拿你自己的智能体任务集，让基础策略对它跑 *n* 次，然后看分档直方图。就我们的经验而言，团队常常没有检查过这个分布，而它通常比预想的更偏斜。
- **检查一致性。** 把同一份记录下来的模型输出分别喂给训练解析器和评估解析器重放一遍，确认两者抽取出完全相同的工具名与参数。否则，训练可能奖励了评估会以不同方式解释的行为。
- **同时报告覆盖率和可重复性。** 说明有多少任务在 *k* 次尝试中至少通过一次，以及有多少任务 *k* 次全通过。一个偶尔能找到解法的模型，未必是能稳定复现解法的模型。
