####这是微软和Hugging Face的联合博客，特别感谢微软的Mirco Milletari和Xiang Jiang、Hugging Face的Sergio Paniego和我们前实习生李卓春（匹兹堡大学）的共同撰写/审阅工作。

我们构建 ThinkingBox 来捕获那些声称已完成但实际上尚未完成的代理。

ThinkingBox-Bench（我们的基准数据集）中的 507 个任务中的每一个都为代理提供了一个真正的后端和一组工具，让它工作，然后检查数据库中真正发生的变化。 [在第一篇文章中](https://huggingface.co/blog/microsoft/thinkingbox)，我们发现一个模型将客户的机票关闭为**已解决**，而其背后的承运人例外仍然处于开放状态。九个看起来很有效的工具调用，一个**错误**的数据库行。

然后我们注意到我们所建造的东西。对于大多数任务，可执行检查可以直接从最终数据库状态返回 1 或 0。这不仅仅是一个评分者。 **这可以是一个奖励函数。**+

因此，我们根据基准之外的 ThinkingBox 格式任务构建了一个训练池，并将其可执行结果用作奖励。问题在于选择**哪些**任务适合代理训练：大多数任务要么已经解决，要么对于你面前的模型来说毫无希望，并且都没有教给它任何东西。

> 难度与策略相关：任务对于当前模型来说是困难的，直到该模型学会它为止。

我们称之为**线下政策相关难度**。我们在训练前使用基本策略估计每个任务的成功概率，并在整个运行过程中保持选定的训练池固定。

### 训练后发生了什么

我们使用离线策略相关难度来构建训练池，然后使用 GRPO 对 Qwen3.8-27B 进行 50 个步骤的微调。回顾一下，我们对 507 项基准任务中的每一项进行了 20 次评估。 pass@1 衡量所有 10,140 次尝试的平均成功率。 pass@20 衡量至少解决一次的任务的比例。观察 20/20 衡量通过每次记录的尝试的任务比例。

*表1.在离线选择的训练池上GRPO 50步前后的Qwen3.8-27B结果。*

|公制|基地|  | RL 微调 |改变 |
| --- | --- | --- | --- | --- |
| **20/20 观察** | 38 (7.50%) | → | **107 (21.10%)** | **+69 项任务** |
| pass@1（成功尝试）| 5,242 (51.70%) | → | **6,163 (60.78%)** | **+9.08 分** |
| pass@20（任务至少解决一次）| 453 (89.35%) | → | **446 (87.97%)** | **−7 任务** |

训练大幅**增加**可重复成功率，但至少一次覆盖率略有下降。文章的其余部分解释了我们如何选择练习任务、构建奖励循环并衡量这种权衡。

**一项任务的改进效果如何？** 旅行者请求房间降级，但公司政策要求首先获得经理批准。培训前，代理人在20次尝试中，有15次未经批准更改预订并退款。经过RL微调后，它保留了所有20个中的预订和支付状态。

## 六十秒内基准测试发现了什么

[ThinkingBox-Bench](https://huggingface.co/datasets/microsoft/ThinkingBox-Bench) 根据代理留下的数据库记录对他们进行评分。它的 507 个任务中的每一个都启动一个真实的后端，向代理提供一组 MCP 工具和一个具有私有上下文的模拟 LLM 用户，最后对终端数据库状态运行可执行检查。检查是针对需要正确的后端记录，而不是特定的工具调用。这会激励模型发现可能的新解决方案路径，而不是“重新发现”人类支持的解决方案，这可能是次优的，尽管是正确的。

[在我们的第一篇文章中](https://huggingface.co/blog/microsoft/thinkingbox)，我们通过该基准运行了 18 个模型，每个模型 20 次，并报告了标题准确性隐藏的差距。 Kimi-K3 *至少一次*解决了 93.89% 的任务，但在 **所有 20 次记录的尝试**中仅完成了 507 项任务中的 68 项 (13.41%)。 Claude Opus 5 则相反：覆盖范围更窄，一致性更高。

更大或更好的模型并没有关闭它。 Claude Opus 5.5 在 pass@1 上的得分比 Claude Opus 5 高 0.66 个百分点，但在所有 20 次尝试中通过了**完全相同数量的任务，241**。标题准确性的提高带来了零额外的可靠性。

如果您正在为涉及生产数据库记录的工作选择模型，则不应单独读取 pass@1。观察到的 20/20 显示哪些任务在每次尝试中都成功，这更接近生产可靠性要求。

可执行的最终状态判决也是训练奖励。在解开训练循环之前，以下是密封基准测试中发生的变化。

观察到的模式与锐化一致：可重复成功率上升，而至少一次覆盖率略有下降。这与[之前的工作](https://arxiv.org/abs/2504.13837)一致。一种解释是，概率分布朝着重复工作的轨迹发展，而一些低概率路径消失了。

> 总体而言，该模型并没有变得更广泛。它变得更加可重复。下一个问题是这些收益落在哪里。

## 可靠性的代价是什么

> 每个可靠任务的成本 = 507 × 20 活动的估计成本 ÷ 通过 20/20 的任务

将相同的成本数学应用于微调检查点的测量令牌使用情况：

*表 3. 基础和 RL 微调 Qwen3.8-27B 的估计评估成本和可靠性。每次成功尝试的成本将预估活动总成本 (507 x 20) 除以通过尝试的次数。*

| --- | --- | --- | --- | --- |

每个可靠任务的价格为 8.00 美元，经过微调的模型在同伴比较中接近 GPT-5.4（6.80 美元）、GPT-6 Astra（7.45 美元）和 Claude Opus 5.5（7.80 美元）。

## 训练循环

[![fig4-training-overview](https://cdn-uploads.huggingface.co/product/uploads/64b8491203124195cd795cad/ZaqyG8RtqCRsx GdxUQMfi.png)](https://cdn-uploads.huggingface.co/product/uploads/64b8491203124195cd795cad/ZaqyG8RtqCRsxGdxUQMfi.png)

*图 5. 现在的上下文中的六个阶段：候选任务输入，前三个阶段离线运行，最后三个阶段对训练运行中的每个组重复。训练后的检查点根据 ThinkingBox-Bench 进行评估。*

选择针对基本策略模型离线运行一次，即本例中的 Qwen3.8 27B；然后训练使用已策划的固定池。图 5 中的虚线琥珀色箭头标记了我们没有采取的路径：在训练运行期间重新探测难度。

每次推出都是一个完整的剧集，而不是文本完成。它获得一个新的后端、一个独立的 MCP 会话以及作为模拟用户的 GPT-5 聊天。大多数奖励来自确定性的终端状态检查；少数狭窄的标题要求可以调用配置的法官（GPT-5 聊天）。

**训练和评估必须以相同的方式解释 Qwen 输出。** 这包括推理提取、工具调用、参数输入、渲染和隔离任务状态。否则，奖励衡量的是与评估的代理人不同的代理人。共享解释代码位于 [`trainer/core/tb_interpret.py`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/trainer/core/tb_interpret.py)。

对于参考运行，我们使用 token-mean GRPO 在 187 个任务上运行全参数 RL 微调 Qwen3.8-27B。每次更新都会在 24 个 H100 中生成 18 组，每组 8 次部署，或 144 集。训练与参数和优化器卸载同步运行； AdamW 使用“1e-6”学习率和零权重衰减。我们进行了 50 步的训练。

在训练过程中，零方差组被替换为[DAPO风格](https://arxiv.org/abs/2503.14476)。系统错误是单独处理的：后端超时并不是不正确的代理结果，因此受影响的组会被重新填充，而不是被评分为失败。

这解释了保留任务是如何训练的。剩下的问题是哪些任务进入了训练池。

## 线下政策相关难度

在深入研究训练任务的选择之前，有一个免责声明：

> RL 训练池中不包含 ThinkingBox-Bench 任务。该基准保留用于评估。

ThinkingBox-Bench 相对于 RL 训练池来说是分布外的：它的领域、数据库、策略和大多数工具在 RL 训练期间都没有遇到。这两个集合仍然共享 ThinkingBox 框架、模拟用户机制、可执行的终端状态分级、一些通用工具和类似的任务风格。这些共享要素限制了转让权利要求的范围。

为什么选择很重要，可以归结为有关 GRPO 的一个算术事实。如果所有八次部署都失败，则奖励向量为“[0, 0, 0, 0, 0, 0, 0, 0]”。如果八个都成功，则为“[1, 1, 1, 1, 1, 1, 1, 1]”。无论哪种情况，以群体为中心都不会产生任务奖励优势，因为没有一条轨迹比另一条轨迹做得更好。++

诸如“[0, 0, 0, 1, 1, 1, 1, 1]”之类的混合组提供了 GRPO 可以学习的对比。这种区别对于有状态代理来说是昂贵的：每次部署都会提供一个隔离的后端，运行一个真正的工具会话，并调用一个单独的模型来扮演用户。

因此，影响这项工作的问题不仅仅是*哪种模型或优化器？*而是：**哪些候选任务应该进入固定训练池？**

我们在后验上使用离线通过率过滤器来选择训练池。它估计哪些任务可能在基本策略下产生对比的最终奖励。

所以我们进行探索。每个候选任务都会针对**基本策略**模型重复运行。通俗易懂的规则很简单：模型总是失败的任务不太可能教它；它总是传递的任务是已经学会的； **它解决的任务有时是结果可以提供对比的地方。**

### 从有限的探测中估计难度

每个候选任务运行 *n* 次，产生 *k* 次成功。我们用 Jeffrey 后验概率对其潜在成功概率进行建模：

> 成功概率 | n 次探测中 k 次成功 ~ Beta(k + ½, n − k + ½)

[![fig5-policy-relative-difficulty](https://cdn-uploads.huggingface.co/product/uploads/64b8491203124195cd795cad/eR45y7Dl0 VFFK3HinwDYg.png)](https://cdn-uploads.huggingface.co/product/uploads/64b8491203124195cd795cad/eR45y7Dl0VFFK3HinwDYg.png)

*图 6. 离线策略相对难度是通过重复的基本策略探测来估计的，并用于保留可能产生对比奖励的任务。*

我们将单位间隔划分为五个桶，边界分别为 0.08、0.40、0.60 和 0.90，选择这些桶作为这些运行的超参数。每个任务都分配给包含最大后验质量的桶：

- **很少解决 [0, 0.08):** 掉落
- **困难 [0.08, 0.40):** 保留
- **中级 [0.40, 0.60):** 保留
- **经常解决的[0.60, 0.90)：**保留用于全参数RLFT
- **几乎总是解决 [0.90, 1]:** 下降

更多详细信息请参见 [ThinkingBox 论文的附录 C.4](https://arxiv.org/pdf/2608.19741)。

### 一项任务，端到端

[![fig6-worked-example](https://cdn-uploads.huggingface.co/product/uploads/64b8491203124195cd795cad/IBBkNpYKQRK6jBL SusMXw.png)](https://cdn-uploads.huggingface.co/product/uploads/64b8491203124195cd795cad/IBBkNpYKQRK6jBLSusMXw.png)

*图 7. 放大，一项任务贯穿所有六个阶段：GPT-5.4 筛选、基本模型探测、难度分类、推出组、最终状态分级和 GRPO 更新。*

图 7 展示了一项可能进入训练池的候选任务。对于 Qwen3.8 27B 全参数池，GPT-5.4 首先充当可解性筛选。然后，基本策略在少数探针上取得了成功，例如 8 个探针中的 3 个，产生了 Beta(3.5, 5.5) 后验。其最大质量为 54.0%，属于困难带。

当采样进行训练时，任务产生了混合奖励组“[0, 0, 0, 0, 1, 1, 1, 1]”。因此，成功的轨迹获得了高于平均水平的任务优势，而失败的轨迹则获得了低于平均水平的优势，从而为 GRPO 提供了可供学习的对比。不同的政策模型可能会将相同的任务置于不同的难度范围内。

最终的 Qwen3.8-27B 策划的训练池包含 187 个任务。

## 什么可以获得奖励

与轨迹无关。奖励是任务自己的可执行判决。

当一个情节结束时，沙箱会提取后端实际发生的更改，并针对最终状态运行任务的确定性检查。任何产生正确最终状态的轨迹都会通过。错误、缺失或额外的副作用会导致失败。奖励是1或0。

在基准测试中，数据库分级器可以被认为是“检查员”：它捕获报告成功并留下错误记录的代理。在训练中，同一种检查可以被视为不同的、不相交的任务集的“老师”。

> 两种奖励路径，一种二元判决
> 
> 可执行检查（绝大多数）。当所需的结果以最终状态或副作用表示时，确定性测试会接受或拒绝它；不需要法学硕士评审。
> 法官协助检查（少数）。当无法从数据库状态明确确定狭义需求时，配置的 LLM 判断会回答可执行测试使用的二进制标题问题。

## 运行训练堆栈

我们在 [microsoft/thinkingbox-training](https://github.com/microsoft/thinkingbox-training) 中发布了用于训练 Qwen3.8-27B 的数据选择、推出、奖励和 Verl 集成。存储库 README 是入口点。详细指南是：

- [`docs/data-preparation.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/data-preparation.md)用于任务水合作用、策略探测、基准排除和训练/验证分割；
- [`docs/reference-q38-run.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/reference-q38-run.md) 用于经过验证的 24-H100 Qwen3.8 配置；
- [`docs/evaluation.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/evaluation.md) 用于合并检查点并运行 ThinkingBox-Bench 507 x 20。

### 开始之前

使用 Python 3.12 和 [uv](https://docs.astral.sh/uv/) 在 Linux 和 WSL 上进行了测试。您需要具有兼容 CUDA/NCCL 堆栈的 NVIDIA GPU、本地 Qwen3.8-27B 检查点以及用于模拟用户和判断的 OpenAI 兼容端点。经验证的参考配置使用 3 个节点 x 8 个 H100 GPU；较小的自定义配置取决于模型大小、上下文长度和部署并发性。

公共示例任务列表练习了该界面。它不是用于报告运行的私人 187 任务训练池。提供与公共基准保持脱节的授权培训来源。

### 安装

并排保留三个存储库：
```
mkdir -p ~/thinkingbox-workspace
cd ~/thinkingbox-workspace

git clone https://github.com/microsoft/thinkingbox.git

git -C thinkingbox checkout 892964e7226044e5463ad188da119df838f4bec1
git -C thinkingbox-data checkout thinkingbox-bench-v1.0
```
### 创建经过验证的环境

已发布的堆栈针对 Linux、Python 3.12、Verl 0.9.0 和固定包锁：
```
cd ~/thinkingbox-workspace/thinkingbox-training

uv venv --python 3.12
source .venv/bin/activate

uv sync --frozen --extra fast --extra tracking --extra eval-proxy
uv pip install -e ../thinkingbox
uv pip install --config-settings editable-mode=compat \
```

最后两个命令应该报告经过验证的修补 Verl 签出并且没有损坏的要求。之后不要运行另一个自动包同步：它可以用 vanilla Verl 轮替换修补的源安装。

### 准备训练数据

从公开提供的示例开始，或者以 ThinkingBox 格式添加您自己的授权数据集。然后运行存储库的准备脚本：
```
cd ~/thinkingbox-workspace/thinkingbox-training
source .venv/bin/activate
```

该脚本聚合策略探测，应用离线策略相关难度过滤器和基准排除，并写入选定的“train.yaml”和“test.yaml”文件。 [`docs/data-preparation.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/data-preparation.md) 记录输入字段、加载程序契约和完整命令。

### 配置并检查启动

按照[`docs/reference-q38-run.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/reference-q38-run.md)启动Typesense和MCP服务器，配置模拟用户和判断，设置模型、任务列表、检查点和拓扑变量，并准备 Ray 集群。将凭据保存在运行时秘密注入中，而不是保存在提交的文件或 shell 历史记录中。

在分配训练作业之前，请使用指南的试运行命令：
```
DRY_RUN=true ./scripts/run_train.sh \
  trainer.total_training_steps=50 \

```
它必须退出零而不启动 Ray 或分配 GPU。在启动运行之前，请阅读发出的“python -m verl.trainer.main_ppo”命令和每个已解决的覆盖。

### 火车

启动器配置训练；它不提供主机。在参考三节点拓扑上，在每个节点上导出相同的环境，将 `CHECKPOINT_DIR` 挂载到相同的绝对路径，然后启动 Ray：

```
ROLE=head NODE_IP="$HEAD_IP" GPUS_PER_NODE=8 \

# each worker node

  HEAD_ADDRESS="$HEAD_IP:6379" GPUS_PER_NODE=8 \
  ./scripts/start_ray.sh
```
在 `ray status` 报告所有 24 个 GPU 后，从头节点启动一次：
```
export RAY_ADDRESS=auto

  trainer.project_name=thinkingbox-training \
  trainer.experiment_name=q38-full-rlft \
  trainer.total_training_steps=50 \
  trainer.save_freq=5
```
### 通过 OpenEnv 评估检查点

[第一篇 ThinkingBox 帖子](https://huggingface.co/blog/microsoft/thinkingbox#run-it-yourself) 介绍了 Typesense、MCP 会话代理和 OpenEnv 设置。将经过训练的检查点合并到 [`docs/evaluation.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/evaluation.md) 之后，然后使用 vLLM 提供服务。

从 OpenEnv 存储库根目录中，将“MERGED_MODEL”设置为合并模型目录，将“THINKINGBOX_DATA”设置为固定基准检查。历史检查点评估使用了八台 A100 服务配置：
```
vllm serve "$MERGED_MODEL" \
  --served-model-name q38-rlft \
  --host 127.0.0.1 \
  --port 8001 \
  --tensor-parallel-size 8 \
  --dtype bfloat16 \
  --max-model-len 262144 \
  --gpu-memory-utilization 0.85 \
  --max-num-seqs 16 \
  --max-num-batched-tokens 8192 \
  --language-model-only \
  --enable-chunked-prefill \
  --enable-prefix-caching \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_xml
```

在单独的终端中，从 ThinkingBox Training 结帐启动 Qwen 聊天模板的 OpenEnv 兼容性代理。它侦听端口 8014 并转发到 8001 上的 vLLM：
```

source .venv/bin/activate

```
在评估期间保持其运行。从另一个终端检查准备情况：
```

```
更新现有 `thinkingbox.yaml` 中的代理条目；保留其 MCP、模拟用户和判断配置：
```
orchestrator:
  agent_model:
    type: aoai
    endpoint_url: http://127.0.0.1:8014/v1/chat/completions
    deployment: q38-rlft

      type: api-key
      api_key: <your_api_key>
```

## 接下来会发生什么

这项工作的有用部分不是一个 Qwen3.8-27B 检查点。正是训练循环和训练数据管理将可执行的结果转化为奖励。

如果您正在训练或评估接触真实数据库记录的代理：

- **训练前进行探测。** 采用您自己的代理任务集，对其运行基本策略 *n* 次，然后查看带状直方图。根据我们的经验，团队通常没有检查这种分布，而且它通常比预期更不平衡。
- **检查奇偶性。** 通过训练和评估解析器重放相同记录的模型输出，并验证两者是否提取相同的工具名称和参数。否则，培训可能会奖励评估以不同方式解释的行为。
- **报告覆盖率和重复性。** 说明有多少任务在 *k* 次尝试中至少通过一次，以及有多少任务通过所有 *k* 次。偶尔找到解决方案的模型不一定是始终如一地重复它的模型。
