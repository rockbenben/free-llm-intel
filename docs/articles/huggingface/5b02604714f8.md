> 你无法剖析的东西，就无法优化。

无论你是想从一个大语言模型（LLM）里榨出更多 token/秒、把推理的毫秒数砍下来，还是只是想搞明白为什么你的训练循环比规格表承诺的还慢，这条路最终都要穿过性能剖析（profiling）。

问题在于剖析的上手门槛 **很陡**。trace 是一堵堵由彩色矩形组成的密墙，事件带着让人发怵的名字。多数教程都假设你已经能读懂它们。所以即使我们 *知道* 自己该做剖析，打开一个 trace 仍像一件最好留给以后（或留给别人）的苦差事。这篇博客，以及它开启的系列，就是我们降低这个门槛的尝试。

我们从新手的视角记录这段旅程。除了基础 PyTorch 之外没有先修要求。把这当作一篇轻松的读物，中间会有一些"原来如此！"的时刻。文章结构刻意以问题为导向：我们打开一个 trace，问"等等，为什么 *那个* 会发生？"，然后一路追到答案、直到某个东西想通。读完你应该知道：

- 如何配置 `torch.profiler` 以及它到底交回什么，
- 如何读 profiler 表和 trace（CPU 泳道、GPU 泳道，以及中间那些可疑的空隙），
- 从一个 Python 调用一路向下到一个 CUDA kernel 的事件链，
- 当你在上面套一个 `torch.compile` 时会发生什么变化（以及更有意思的是，什么 **不** 会变化）。

开始之前，先给两个能让下文读起来更顺的定义：

- GPU **kernel** 是一个在 GPU 上许多线程并行运行的程序。
- CPU **调度并启动（launch）** 这些 kernel。

你通常不必自己写 GPU kernel；当你用一个 PyTorch 操作时，它会自动被转换成一个或多个在 GPU 上干活的 kernel。

把这两个想法揣在兜里，我们开始提问。

> 这是我们在本文里用到的完整脚本：01_matmul_add.py。我们建议把这个脚本另开一个标签页，一步步走读代码。我们用 NVIDIA A100-SXM4-80GB GPU 运行脚本。在 Hugging Face 基础设施上搭一块 GPU、用 Spaces 的 Dev Mode 实验脚本非常容易。也可以用 Hugging Face Jobs 流水线跑脚本。（注：本博客的 trace 是用 PyTorch 2.13 生成的。如果你用其他版本，像 CompiledFxGraph 这样的某些 trace 细节可能不同或缺失。）

## 矩阵乘法与加法操作

正如 [Sara Hooker 博士一针见血](https://youtu.be/7knwihgj0fU?si=uvzGH-J9bsCHP4Nn&t=2199) 所说，正如我们主要由水构成，深度神经网络主要由矩阵乘法构成。矩阵乘法既然如此基础，我们要是拿别的东西开启剖析之旅就太可惜了。

```
def fn(x, w, b):
  return torch.add(torch.matmul(x, w), b)
```

> 矩阵加法连同矩阵乘法，模拟了神经元里权重和偏置的交互方式。这个加法（双关）将帮助我们理解它如何为文章后面讲编译铺路。

要做剖析，我们使用 `torch.profiler` 模块。涉及的步骤是：

- [准备好待剖析的代码](https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L26-L27)（这里是 `def fn`，包装了矩阵乘法和矩阵加法）
- [标注](https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L32) 算法。这完全是可选的，但我们建议做。`record_function` 把我们的函数标注成 `matmul_add`，这在 trace 里很容易导航（我们后面会看到）

```
def step():
  with torch.profiler.record_function("matmul_add"):
    return fn(x, w, b)
```

- 用 `torch.profiler.profile` [上下文管理器](https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L53-L62) 包住代码

```
  with torch.profiler.profile(
    activities=[
        torch.profiler.ProfilerActivity.CPU,  # the cpu activities
        torch.profiler.ProfilerActivity.CUDA, # the gpu activities
    ],
  ) as prof:
    # it is recommended to run events multiple times to warm up the GPUs
    for _ in range(5):
      step()
      prof.step()
```

- 导出 [profile](https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L70)

```
# the profiler table
prof.key_averages().table(sort_by="cuda_time_total", row_limit=15)

# the profiler trace
prof.export_chrome_trace(trace_path)
```

profiler 导出两种不同的产物：

- Profiler 表：给出算法的统计摘要。它回答"什么最耗时"，这对找出热点很有帮助。热点就是那些占用时间最多的事件，可能是流水线的瓶颈，也可能是被触发很多次的某个事件。
- Profiler trace：给出时间执行视图。回答"一个操作何时、为什么发生"，描绘 CPU 和 GPU 上进行的活动。当我们要调查启动了哪些 kernel、启动它们有没有延迟、CPU 和 GPU 活动有没有重叠等，这就很有用。

让我们在第一次执行里看看这两者的实际表现。([这里是完整的 `01_matmul_add.py` 脚本](https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py))

> 建议在带 GPU 的机器上运行此脚本。

```
uv run 01_matmul_add.py --size 64
```

如果你在 GPU 机器上运行上面的脚本，你会找到一个 `traces/01_matmul_add` 文件夹，里面有这两个产物：

```
64_bf16_cold_eager.json
64_bf16_cold_eager.txt
```

| [![64 尺寸矩阵 matmul add 的 profiler 表](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/profile-table-64.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/profile-table-64.png) |
| --- |
| 图 1：64 尺寸矩阵 matmul add 的 profiler 表 |

`.txt` 文件保存 profiler 表。打开文件，如图 1 所示，你会看到一张大表，第一列是在 profile 作用域内触发的事件。

其余各列与该事件在 `torch.profiler.profile` 中 `activities` 指定的 CPU 或 GPU 或任何其他设备上所花的时间有关。看看哪些事件最耗时，并凭直觉判断那个事件是否真的应该花那么久。看"# of Calls"（调用次数）这一列也很重要，它说明事件被触发了多少次。

既然说到这里，也聊聊 "Self CPU/CUDA" 与 "CPU/CUDA total" 的区别。"Self" 列只测量事件自身内部花费的时间，不含它的子事件。"total" 列把事件和它所有子事件一起计入。所以如果你看 `matmul_add` 的"CPU total"，它包含自身耗时加上它触发的子事件的耗时。这是一个需要注意的重要细节。

如果你看表格最后两行，会注意到 profiler 告诉我们

```
Self CPU time total: 2.314ms
Self CUDA time total: 23.104us
```

CPU 时间单位是 `ms` 而 GPU 时间单位是 `us`。为了有个概念，GPU 上花的时间（kernel `ampere_bf16_s16816gemm...`）不到 CPU 上所花时间（`matmul_add` 操作）的 1%。GPU 大部分时间闲置，这是立刻亮起的红灯。之所以这样，是因为 GPU 算一个小 matmul 非常快，所以我们的代码大部分时间花在准备 kernel、把它们 launch 到 GPU、发送要相乘的数据、收集结果上。这个概念叫 *overhead-bound*（受开销限制）的算法。

摆脱这种机制最简单的方法是用更大的矩阵乘法。

```
uv run 01_matmul_add.py --size 4096 
```

| [![4096 尺寸矩阵 matmul add 算法的 profiler 表](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/profiler-table-4096.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/profiler-table-4096.png) |
| --- |
| 图 2：4096 尺寸矩阵 matmul add 的 profiler 表 |

图 2 的最后两行是：

```
Self CPU time total: 4.908ms
Self CUDA time total: 4.495ms
```

两个时间单位都是 ms，意味着我们仅通过增大矩阵乘法的尺寸，就把更多 GPU 时间兑现了出来。如果你看图 2，还会注意到现在最多的 CUDA 时间被 GPU kernel（`ampere_bf16_s16816gemm_..`）占据，而不是启动它的那个 CPU 操作（`matmul_add`）。这说明我们确实从 overhead-bound 移到了 compute-bound（受计算限制）。

现在我们进入可视化调度链，它存在于 `.json` 产物里。你可以把它们上传到 [Perfetto UI](https://ui.perfetto.dev) 看 trace，或者用 `uvx trace-util -f traces -b <hf_uname>/traces` 直接生成 Perfetto 链接。

### 为什么 ProfilerStep#2 花这么长时间？

| [![PyTorch profiler trace 中 ProfileStep#2 比 ProfileStep#3 和 ProfileStep#4 更宽](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/why-is-step-2-big.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/why-is-step-2-big.png) |
| --- |
| 图 5：`ProfileStep#2` 明显比它之后的步骤宽 |

在图 5 里，我们注意到 `ProfileStep#2` 比其他步骤花更多时间，仔细看你还会在 `matmul_add` 标注上看到同样的模式。真正的烟枪在标注内部，而不是标注本身：

| Step | `matmul_add` start | `aten::matmul` start | gap |
| --- | --- | --- | --- |
| #2 | 138.736 | 366.493 | 227.757 µs |
| #3 | 517.926 | 523.447 | 5.521 µs |
| #4 | 610.039 | 614.527 | 4.488 µs |

| [![profile step 2 中 record_function matmul_add 与 aten::matmul 调度之间约 228 微秒的空隙](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/gap-227.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/gap-227.png) |
| --- |
| 图 6：`record_function("matmul_add")` 与 `aten::matmul` 之间约 228 µs 的"死窗口" |

图 6 显示的那约 228 µs 是进入 `record_function("matmul_add")` 与 PyTorch 实际调度 `aten::matmul` 之间的"死窗口"。这可能出于多个原因，包括 workspace 分配、[cuBLAS](https://developer.nvidia.com/cublas)（NVIDIA 专有的 GPU 加速库，用于执行基础线性代数运算）启发式，或惰性模块加载。我们可以要么移开目光，要么在剖析之前 [多跑几个 warmup step](https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/01_matmul_add.py#L35-L39)（这是标准做法）。

就剖析而言，warmup 就是你在真正剖析某个事件之前先跑几遍。GPU 做的预备工作（包括上面提到的那些）是一次性的，我们不想剖析它们。在我们的示例里，有两个 warmup 阶段，一个是在进入 profiler 之前实际循环调用函数，另一个是在 profiler 内部，由 `warmup` 参数实现。在本节里，我们启用了实际迭代连同 schedule。

```
uv run 01_matmul_add.py --warmup
```

[64x64 带 Warmup 的 Perfetto Trace](https://ui.perfetto.dev/#!/?url=https://huggingface.co/buckets/ariG23498/traces/resolve/01_matmul_add/64_bf16_warm_eager.json)

| [![warmup steps 之后的 PyTorch profiler trace，ProfileStep#2 不再显示冷启动开销](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/warmup.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/warmup.png) |
| --- |
| 图 7：预热之后，每个 profile step 花的时间相近 |

在图 7 里我们看到每个 profile step 花的时间相近，但这并不意味着我们把一次性开销优化掉了。我们只是预热了运行，让那些开销不被剖析。我们认为就这样草草结束这一节、不提示如何解决，对读者不公，所以这里给一个 [链接](https://pytorch.org/blog/accelerating-generative-ai-2/) 去阅读如何进一步优化 launch 开销。

### 为什么 CPU 和 GPU 泳道之间有约 2.5 ms 的偏移？

| [![PyTorch profiler trace 中 CPU 泳道与 GPU 泳道之间 2.32 毫秒的偏移](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/gap-bw-kernel-launch.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/gap-bw-kernel-launch.png) |
| --- |
| 图 8：CPU 与 GPU 泳道之间约 2.5 ms 的偏移 |

在图 8 里，我们看到 CPU 和 GPU 泳道有约 2.5 ms 的偏移：这是 CPU 提交 CUDA kernel 之后到它们实际开始执行之间的延迟。有人可能觉得 warmup 阶段加上 schedule 的 `wait` 和 `warmup` 应该让 GPU 一直忙、从而消除偏移。

为了揭示真正发生了什么，我们稍微改一下 schedule：

```
- schedule = torch.profiler.schedule(wait=1, warmup=1, active=3, repeat=1)
+ schedule = torch.profiler.schedule(wait=0, warmup=0, active=3, repeat=1)
```

| [![wait=0 warmup=0 的 PyTorch profiler trace，显示步骤之间的 Activity Buffer Request](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/full-profile.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/full-profile.png) |
| --- |
| 图 9：`wait=0` 和 `warmup=0` 时，trace 揭示了一个 `Activity Buffer Request` |

图 9 告诉我们，在任何操作之前，GPU 泳道上有一个 `Activity Buffer Request`。让我们再放大一点。

| [![剖析器 buffer 请求导致 matmul 与 add CUDA kernel 之间出现空隙](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/mat-add-gap.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/mat-add-gap.png) |
| --- |
| 图 10：profile step 1 上 matmul 和 add kernel 之间出现空隙 |

放大 GPU trace 后，我们注意到 `ProfileStep#0` 的 matmul 和 add kernel（它的 CPU trace 在图中不可见）是一个接一个发生的，而 `ProfileStep#1` 的 kernel 中间有一个窗口。对此最好的解释是 buffer 溢出了，并且在 kernel 执行期间又发出了另一个 buffer 请求（在 GPU 显存上分配一些内存的请求）。

排除其他可能性的最好办法是多剖析几次迭代，看看类似的窗口是否出现在 trace 的其他地方。为此我们用 `active=20` 运行。

| [![20 个 active 迭代的 PyTorch profiler trace，确认 buffer 请求空隙只出现一次](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/20-iters.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/20-iters.png) |
| --- |
| 图 11：20 个 active step 下空隙只出现一次，确认是 buffer 请求 |

如图 11 所示，我们在 `ProfileStep#1` 看到类似趋势。这与我们之前的发现一致，可以安心断定它确实是另一个 buffer 请求。

### 事件链

| [![PyTorch profiler 中嵌套的 CPU 调度链：ProfileStep、matmul_add、aten::matmul、aten::mm](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/cpu-nests.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/cpu-nests.png) |
| --- |
| 图 12：调度链 |

在图 12 里，我们看到嵌套的 CPU 调用。这是一个重要的可视化，让人理解一条真正的调度链长什么样。

我们从 `ProfileStep#<id>` 开始，它封装了一个剖析步骤。由于我们标注了该步骤，所以看到 `matmul_add` 行。`matmul_add` 包含两个 `aten` 调用，一个做矩阵乘法，一个做矩阵加法。

`aten::matmul` 是面向用户的 PyTorch matmul 调用落到的 [ATen 层](https://github.com/pytorch/pytorch/tree/main/aten/src/ATen) 调度。`aten::mm` 是 2D 矩阵-矩阵乘法的后端。

很值得注意的是，如果我们给矩阵加上 batch 轴，PyTorch 就会调用 `aten::bmm`（批量矩阵乘法）。我们绕个路，看看 `aten::bmm` 的实际表现。

```

- w = torch.randn( args.size, args.size, device=device, dtype=dtype)
- b = torch.randn(args.size, args.size, device=device, dtype=dtype)

+ # adding a batch size of 8
+ x = torch.randn(8, args.size, args.size, device=device, dtype=dtype)
+ w = torch.randn(8, args.size, args.size, device=device, dtype=dtype)
+ b = torch.randn(8, args.size, args.size, device=device, dtype=dtype)
```

| 图 13：批量矩阵乘法 |

在图 13 里，给输入加上 batch 轴之后，`aten::matmul` 现在除了 `aten::bmm`（而非 `aten::mm`）还封装了一堆其他前置的 CUDA 运行时调用。这也暗示了 cuBLAS 为了把最合适的 kernel 调度给程序而需要做的启发式。

### 为什么 matmul 多了一个 CUDA 运行时调用？

| [![CPU 泳道显示 cudaOccupancyMaxActiveBlocksPerMultiprocessor 出现在 matmul 的 cudaLaunchKernel 之前](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/cudaoccupancy.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/cudaoccupancy.png) |
| --- |
| 图 14：一次 CUDA occupancy 查询发生在 matmul kernel launch 之前 |

我们注意到对 `aten::mm` 有两个 CUDA Runtime 调用，即 `cudaOccupancyMaxActiveBlocksPerMultiprocessor`（图 14 中框出）和 `cudaLaunchKernel`，而对 `aten::add` 只有 `cudaLaunchKernel`。

`cudaOccupancyMaxActiveBlocksPerMultiprocessor` 是一个规划调用，纯粹在 CPU 侧。它问的是："给定一个 kernel 函数、一个选定的 block 大小和一个选定的动态共享内存大小，这个 kernel 的多少个 block 能同时驻留在一个 SM（流式多处理器）上？"

这引出了问题：为什么 matmul 需要规划而 add 不需要？

要理解这一点，我们得看 kernel 的资源占用。如果你点击 GPU kernel，就能查看各 kernel 的资源占用。

| [![cuBLAS matmul kernel 在 Perfetto 中的资源占用：寄存器、共享内存和 block 大小](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/matmul-footprint.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/matmul-footprint.png) | [![带 32 个寄存器、零共享内存的元素级 add CUDA kernel 资源占用](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/add-footprint.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/add-footprint.png) |
| --- | --- |
| 图 15：Matmul 占用 | 图 16：Add 占用 |

在图 15 里，我们注意到对矩阵乘法而言 `registers per thread` 和 `shared memory` 是动态的（基于矩阵大小）。cuBLAS 附带了数百种 kernel 变体，每种都有一个启发式驱动的 launch 路径，需要关于硬件容量的运行时信息。occupancy 查询是该启发式的一部分。概念上，我们可以把 GPU 加速的 matmul 想成 [在独立的 tile 上工作](https://alvinwan.com/how-to-tile-matrix-multiplication/)：我们用多少 tile、每个 tile 该多大，取决于矩阵和硬件。现代算法比这复杂得多，但这仍是一个不错的参考框架。

从图 16 我们看到加法的占用写着 32 个寄存器和零共享内存，这轻松就容纳得下。没什么可查询的，因为没有硬件资源会限制 occupancy。这个 kernel 在设计上就是资源轻量的。

> 你在读任何 trace 时都可以把它当作一个快速诊断。扫描 CPU 泳道里的 cudaOccupancyMaxActiveBlocksPerMultiprocessor。每次出现都标记了一个"重型、自适应 launch"的 kernel，通常是 GEMM（GEneral Matrix Multiplication，通用矩阵乘法）、conv 或类似。前面没有 occupancy 查询的 kernel，就是 PyTorch 机械式 launch 的那批元素级/归约 kernel。

### 为什么 cudaDeviceSynchronize 这么大（约 1.78 ms）？

`cudaDeviceSynchronize` 会阻塞 CPU 直到该设备上所有 GPU 工作完成。profiler 在 active 窗口末尾发出这个 sync 来冲刷事件。没有它，kernel 计时就会缺失。

一个 1.78 ms 的 sync 却覆盖 26 µs 的真实 GPU 工作，告诉你这次运行 98% 是空闲。这就是教科书式的 overhead-bound 症状。

## 让我们看看 torch.compile 干活

和 `torch.compile` 打交道总让我们惊叹。你写的是普通 eager PyTorch 代码，但 PyTorch 会尝试捕获张量密集区域、把它们变成图、优化它们、并运行生成的代码。默认后端通常是 `TorchInductor`，大致流水线是：

- `TorchDynamo` 把 Python 执行捕获成一张 FX 图
- `AOTAutograd` 在涉及梯度时准备前向/反向图
- `Inductor` 把图降级（lower）成优化的 CPU 或 GPU 代码。

本节我们谈编译并查看 profiler trace。

```
uv run 01_matmul_add.py --size 4096 --warmup --compile
```

`args.compile` 标志触发以下代码：

```
def fn(x, w, b):
  return torch.add(torch.matmul(x, w), b)

fn = torch.compile(fn) if args.compile else fn
```

在图 19 里，我们看到名为 `Torch-Compiled Region: 0/0` 的新 CPU 行，它指向正在被使用的编译函数。

### 我们把 matmul 和 add kernel 融合成一个了吗？

| [![编译后的 trace，aten::addmm 取代了 eager 的 aten::add 和 aten::mm 组合](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/fused-ops.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/fused-ops.png) |
| --- |
| 图 20：编译运行只调度一个 `aten::addmm` |

看图 20 我们发问：我们真的把乘法和加法操作融合成一个了吗？

这是图层面的算子融合。Inductor 把我们的 `torch.add(torch.matmul(x, w), b)` 改写成了一个 `aten::addmm(b, x, w)` 调用。这里要记住的重点是它并 **没有** 产生一个 **新的** 融合 CUDA kernel。实际的 GPU 工作仍是 `ampere_bf16_s16816gemm_bf16_128x256_ldg8_f2f_stages_64x3_nn`，和 eager 模式用的是同一个 cuBLAS kernel。所以这里的"融合"发生在调度器层面，不在 kernel 层面。

> PyTorch 提供了 torch.addmm 函数，把我们分两步做的事——先乘再加——一步做了。我们鼓励读者看看这个函数的 trace，并在下方评论区写下你的观察！

### torch.compile 的运行时架构

虽然我们理论上知道编译函数时会发生什么，但同样重要的是看它实际如何。我们来看看反映 `torch.compile` 运行时架构的 CPU 侧层级。

**TorchDynamo Cache Lookup** 是 Dynamo 检查当前调用是否仍匹配用相同输入形状、dtype、设备和张量元数据所编译结果的地方。如果有任何不匹配，Dynamo 就会重新编译。这个成本每次调用都要付，即便编译之后。

**Torch-Compiled Region** 是"进入"编译版本的包装器。**AOTDispatcher Runtime Wrapper Prologue** 是 AOT Autograd 的运行时包装器。尽管这里我们不需要梯度，AOTDispatcher 总在栈里处理张量元数据、视图跟踪，并在 `requires_grad` 为真时会准备反向传播。

**## Call CompiledFxGraph ** 是实际生成代码运行的地方。"CompiledFxGraph" 之后的字符串是 FX 图的内容哈希。它在三个 active step 间都相同，确认了缓存命中。

> 你可以在磁盘上的 /tmp/torchinductor_<user>/fxgraph 下用该哈希找到生成的代码，当你想读 Inductor 实际产出的 Triton/C++ 时很有用。

### CUDA launch 次数减半了吗？

| [![编译后的 matmul trace，显示每步启动的 Memcpy DtoD 和 GEMM kernel](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/memcpy.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-profiler/memcpy.png) |
| --- |
| 图 21：每个编译步骤仍启动两个 GPU kernel，一个 Device-to-Device memcpy 和 GEMM |

看图 21 的 trace，我们很高兴地注意到每步只有一个 `cudaLaunchKernel`。这个观察直接与我们在 GPU trace 里看到的相矛盾。每步仍启动两个 kernel，即 `Memcpy DtoD (Device -> Device)` 和 GEMM。回到 CPU trace，我们发现自己完全漏看了 `cudaMemcpyAsync` 的调度。

`addmm` 计算 `out = α·A·B + β·C`，而 cuBLAS 的 GEMM-with-bias-add 写回（epilogue）要写进一个目的地缓冲，该缓冲需要已经含有偏置。epilogue 可以理解为在 GEMM *之后* 发生的所有操作。在深度学习世界里，我们不断遇到 GEMM-Epilogue，比如激活、偏置加法、归一化等等。这就是为什么有 cuBLAS GEMM-with- kernel 变体。

> 如果你用不同的 torch.compile 模式，你会注意到会启动不同的 kernel 变体。你可以自己试，并在下方评论你的观察！

所以 Inductor 生成的代码做的是：

- `out = copy(C)` ← 那就是 DtoD memcpy（32 MB，约 33 µs）
- `out = α·(A·B) + β·out` ← `α=β=1` 的 GEMM，把偏置加法融进写回

结果在数学上仍相同。偏置加法并不免费，因为我们要预付一次 memcpy，外加一个略贵一点的 GEMM epilogue。

有人可能期望的那种真正融合——把 `x·w + b`（这里 `out = α·A·B + β·C`）收敛成一个 kernel、没有额外内存流量——并不是发生的事。Inductor 保留了两个触碰内存的操作，它只是把偏置复制标成 memcpy、把加法标成 GEMM epilogue。

一个真正融合的实现会跳过 memcpy。FlashAttention 式手写 kernel 就是这么做的，而 Inductor 也能通过 Triton codegen 做到，但对一个 `4096×4096 bf16 matmul`，Inductor 显然认定"用 cuBLAS，把偏置通过 epilogue 设置来做"是最佳路径。

### CPU 开销上升了，没降

比较 eager 和编译运行时，最容易忽略的就是这一点：

| step | eager 时长 (ms) | compile 时长 (ms) |
| --- | --- | --- |
| #2 | 0.1 | 0.2 |
| #3 | 0.07 | 0.1 |
| #4 | 0.07 | 0.1 |

`torch.compile` 每步在 CPU 上大约贵 2 倍。这是因为每次调用都走完整的 Dynamo > AOTAutograd > Inductor 栈，叠加在我们本来就有的那个 `aten::addmm` 调度之上。编译流水线是为有几十个操作的 ML 模型设计的，那里每次调用的开销会被摊薄（对单个操作它是一种税负）。

> torch.compile 有一个 mode 参数。留给读者作为课后作业：读文档，找出一个能把 CPU 开销降下来的 mode。🤗

## Trace 阅读速查表

对我们走过的那些模式做一个快速参考。思路是：如果你在 trace 里看到这个，它通常意味着这个。

### Profiler 表

| 你看到什么 | 它通常意味着什么 |
| --- | --- |
| `Self CPU time total` ≫ `Self CUDA time total`（CPU 用 ms，GPU 用 µs） | overhead-bound。CPU 花在调度上的时间多于 GPU 花在计算上的时间。把工作做大（更大的矩阵、批量操作）或融合调用。 |
| `Self CPU time total` ≈ `Self CUDA time total`，两者都用 ms | compute-bound。GPU 是瓶颈，通常正是你想要的。 |
| 某个事件主导了 `CUDA total` | 那是你的热点。优化从那里开始。 |
| 某个事件 `# of Calls` 巨大 | 潜在瓶颈，即便每次调用都很便宜。看它能否被融合或批量化。 |
| 某一行 `CPU total` ≫ `Self CPU` | 大部分成本在子事件里。钻进嵌套事件，而不是父事件。 |

### CPU 泳道

| 你看到什么 | 它通常意味着什么 |
| --- | --- |
| 第一个 `ProfileStep` 比其他宽得多 | 冷启动开销：workspace 分配、cuBLAS 启发式、惰性模块加载。加上 warmup 迭代和/或 schedule 的 `warmup` 参数。 |
| `record_function("...")` 开始与其内部第一个 `aten::*` 之间有大空隙 | 同样的冷启动税，只是放大了。标注进入了，但调度还没发生。 |
| 在 `cudaLaunchKernel` 前有 `cudaOccupancyMaxActiveBlocksPerMultiprocessor` | 一个重型、自适应 launch 的 kernel（GEMM、conv 等）。cuBLAS 在问驱动有多少 block 能装进一个 SM，以便挑一个 kernel 变体。 |
| `cudaLaunchKernel` 前面没有 occupancy 查询 | 一个固定、资源轻量占用的元素级或归约 kernel。无需规划。 |
| active 窗口末尾一个很长的 `cudaDeviceSynchronize` | profiler 在冲刷事件。它的时长主要是 GPU 收尾待处理工作，不是真实 CPU 成本。一个 sync 覆盖很小的 GPU 工作是经典的 overhead-bound 症状。 |
| 一个你没写的 `cudaMemcpyAsync` | 常是一次隐藏的 Device-to-Device 拷贝。常见于 `addmm` 在 GEMM epilogue 之前用偏置给目的地缓冲播种。 |

### GPU 泳道

| 你看到什么 | 它通常意味着什么 |
| --- | --- |
| GPU 泳道上的 `Activity Buffer Request` | profiler 在分配/补充它自己的事件缓冲。第一个通常解释了初始 CPU↔GPU 泳道偏移。 |
| 单步内两个 kernel 之间的空隙 | 很可能又是执行中途的一次 buffer 请求。多跑几次确认：如果只出现一次，那是 profiler，不是你的代码。 |
| 同一个 kernel 在各步骤计时不同 | GPU 时钟、温度、电源管理、驱动杂务。读 trace，不只看均值。 |
| 一个名字形如 `ampere_bf16_s16816gemm_...` 的 kernel | matmul 的实际 cuBLAS GPU 工作。对相同形状/dtype，kernel 名在 eager 和编译模式下通常相同。 |
| GEMM 之前紧跟的 `Memcpy DtoD` | `addmm` epilogue 的偏置拷贝。"融合"在调度器层面，不在 kernel 里。 |

### 调度链

| 你看到什么 | 它通常意味着什么 |
| --- | --- |
| `ProfileStep#N` → `<record_function name>` → `aten::*` → `aten::mm` / `aten::bmm` / `aten::add` | 规范的嵌套调用层级。Self time 不含子事件；Total time 含子事件。 |
| `aten::matmul` 解析到 `aten::mm` | 2D × 2D 矩阵乘法。 |
| `aten::matmul` 解析到 `aten::bmm`（带额外 CUDA 运行时调用） | 3D 及以上张量的批量 matmul。cuBLAS 需要做更多启发式来挑变体。 |
| 用单独的 `aten::add` + `aten::mm` 之外的 `aten::addmm(b, x, w)` | 调度器层面的算子融合。GPU kernel 仍是同一个 GEMM，偏置加法被折进 epilogue。 |

### torch.compile

| 你看到什么 | 它通常意味着什么 |
| --- | --- |
| CPU 泳道里一个 `Torch-Compiled Region: K/M` 行 | 你正处在一个编译函数里。 |
| 每步都有 `TorchDynamo Cache Lookup` | Dynamo 在验证形状/dtype/设备是否匹配缓存的编译结果。每次调用都付，即便编译之后。 |
| 没有梯度时仍有 `AOTDispatcher Runtime Wrapper Prologue` | AOTAutograd 的运行时包装器总在栈里，处理张量元数据和视图跟踪。 |
| 各步骤间哈希相同的 `## Call CompiledFxGraph <hash>` | 生成代码缓存命中。生成的源码位于 `/tmp/torchinductor_<user>/fxgraph/<hash>`。 |
| 小操作下 `torch.compile` 的每步 CPU 时间高于 eager | 预期之内。Dynamo → AOTAutograd → Inductor 栈是一种税负，只有跨许多操作才摊得薄。 |

## 结论

我们从极小的 `matmul + add` 开始，并把它当作借口来学习如何读 PyTorch profiler。一路上我们拾起了几个能很好迁移到更大负载的心智模型。这是 **PyTorch 性能剖析** 系列的第一站。在 [后续的帖子](https://huggingface.co/blog/torch-mlp-fusion) 里，我们会逐渐抛开这个两操作的玩具，沿复杂度阶梯往上走，看更大的构建块，最终看真实的模型。

> 本博客是用 LLM 润色过的。这绝不意味着我们让一个 agent 在后台跑、让它生成博客。我们团队里有些人不是英语母语者，认为 LLM（大多在英语上训练）能纠正琐碎的语法错误、把句子重述得不那么吓人、更干净。希望这能解答"如果这是 LLM 生成的，我为什么要读"这个疑问。🤗

首先，谢谢你的问题。回答 `2`：你是对的，上下文管理器应该会处理它，但我个人喜欢多放一个 sync 以保险。在你自己的脚本里你可以省略它。
