过去几个月，基于 Transformer 的扩散主干网络在高分辨率文生图（T2I）生成中迅速兴起。这些模型用 transformer 架构充当扩散过程的积木，取代了早期许多扩散模型中占主导的 UNet 架构。得益于 Transformer 的本性，这些主干扩展性良好，模型规模从 0.6B 到 8B 不等。

模型变大，内存需求随之上升。问题还被放大了，因为一条扩散流水线通常由多个组件构成：文本编码器、扩散主干、图像解码器。而且现代扩散流水线使用多个文本编码器——比如 Stable Diffusion 3 就有三个。以 FP16 精度运行 SD3 推理需要 18.765 GB 显存。

这些高内存需求会让消费级 GPU 难以使用这些模型，拖慢采用、也让实验更困难。本文中，我们展示如何通过 Diffusers 库调用 Quanto 的量化工具，提升基于 Transformer 的扩散流水线的内存效率。

## 预备知识

关于 Quanto 的详细介绍请看[这篇文章](https://huggingface.co/blog/quanto-introduction)。简言之，Quanto 是构建在 PyTorch 上的量化工具包，属于 [Hugging Face Optimum](https://github.com/huggingface/optimum)——一组面向硬件优化的工具。

模型量化在 LLM 实践者中很流行，但在扩散模型上并不如此。Quanto 可以弥合这个差距，在质量几乎不降甚至不降的前提下省下内存。

基准测试使用 H100 GPU，环境如下：

- CUDA 12.2
- PyTorch 2.4.0
- Diffusers（从[该 commit](https://github.com/huggingface/diffusers/commit/bce9105ac79636f68dcfdcfc9481b89533db65e5)安装）
- Quanto（从[该 commit](https://github.com/huggingface/optimum-quanto/commit/285862b4377aa757342ed810cd60949596b4872b)安装）

除非另有说明，我们默认以 FP16 计算。我们选择不量化 VAE，以避免数值不稳定问题。基准测试代码在[这里](https://huggingface.co/datasets/sayakpaul/sample-datasets/blob/main/quanto-exps-2/benchmark.py)。

写稿时，Diffusers 中用于文生图的基于 Transformer 的扩散流水线有：

- [PixArt-Alpha](https://huggingface.co/docs/diffusers/main/en/api/pipelines/pixart) 和 [PixArt-Sigma](https://huggingface.co/docs/diffusers/main/en/api/pipelines/pixart_sigma)
- [Stable Diffusion 3](https://huggingface.co/docs/diffusers/main/en/api/pipelines/stable_diffusion/stable_diffusion_3)
- [Hunyuan DiT](https://huggingface.co/docs/diffusers/main/en/api/pipelines/hunyuandit)
- [Lumina](https://huggingface.co/docs/diffusers/main/en/api/pipelines/lumina)
- [Aura Flow](https://huggingface.co/docs/diffusers/main/en/api/pipelines/aura_flow)

我们还有 [Latte](https://huggingface.co/docs/diffusers/main/en/api/pipelines/latte)，基于 Transformer 的文生视频流水线。

为简明起见，我们的研究限于三个：PixArt-Sigma、Stable Diffusion 3 和 Aura Flow。下表列出它们扩散主干的参数量：

| **模型** | **Checkpoint** | **参数量（十亿）** |
| --- | --- | --- |
| PixArt | [https://huggingface.co/PixArt-alpha/PixArt-Sigma-XL-2-1024-MS](https://huggingface.co/PixArt-alpha/PixArt-Sigma-XL-2-1024-MS) | 0.611 |
| Stable Diffusion 3 | [https://huggingface.co/stabilityai/stable-diffusion-3-medium-diffusers](https://huggingface.co/stabilityai/stable-diffusion-3-medium-diffusers) | 2.028 |
| Aura Flow | [https://huggingface.co/fal/AuraFlow/](https://huggingface.co/fal/AuraFlow/) | 6.843 |

请记住，本文主要关注内存效率，代价是轻微或可忽略的推理延迟。

## 用 Quanto 量化 `DiffusionPipeline`

用 Quanto 量化模型很直接。

```
from optimum.quanto import freeze, qfloat8, quantize
from diffusers import PixArtSigmaPipeline
import torch

pipeline = PixArtSigmaPipeline.from_pretrained(
    "PixArt-alpha/PixArt-Sigma-XL-2-1024-MS", torch_dtype=torch.float16
).to("cuda")

quantize(pipeline.transformer, weights=qfloat8)
freeze(pipeline.transformer)
```

我们对要量化的模块调用 `quantize()`，并指定量化什么。上面的例子只量化参数，激活保持原样。我们量化到 FP8 数据类型。最后调用 `freeze()`，用量化的参数替换原始参数。

然后就可以正常调用 `pipeline`：

```
image = pipeline("ghibli style, a fantasy landscape with castles").images[0]
```

| FP16 | FP8 的 Diffusion Transformer |
| --- | --- |
| ![FP16 image.](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/quanto-diffusers/ckptpixart-bs1-dtypefp16-qtypenone-qte0.png) | ![FP8 quantized image.](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/quanto-diffusers/ckptpixart-bs1-dtypefp16-qtypefp8-qte0.png) |

使用 FP8 时我们观察到如下内存节省，延迟略高、质量几乎无损：

| **Batch Size** | **量化** | **内存（GB）** | **延迟（秒）** |
| --- | --- | --- | --- |
| 1 | 无 | 12.086 | 1.200 |
| 1 | FP8 | **11.547** | 1.540 |
| 4 | 无 | 12.087 | 4.482 |
| 4 | FP8 | **11.548** | 5.109 |

文本编码器也可以用同样的方式量化：

```
quantize(pipeline.text_encoder, weights=qfloat8)
freeze(pipeline.text_encoder)
```

文本编码器也是 transformer 模型，同样可以量化。同时量化文本编码器与扩散主干会带来大得多的内存改善：

| **Batch Size** | **量化** | **量化 TE** | **内存（GB）** | **延迟（秒）** |
| --- | --- | --- | --- | --- |
| 1 | FP8 | False | 11.547 | 1.540 |
| 1 | FP8 | True | **5.363** | 1.601 |
| 4 | FP8 | False | 11.548 | 5.109 |
| 4 | FP8 | True | **5.364** | 5.141 |

量化文本编码器产生的结果与上一种情况非常接近：

[![ckpt@pixart-bs@1-dtype@fp16-qtype@fp8-qte@1.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/quanto-diffusers/ckptpixart-bs1-dtypefp16-qtypefp8-qte1.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/quanto-diffusers/ckptpixart-bs1-dtypefp16-qtypefp8-qte1.png)

## 观察结论的普适性

把文本编码器和扩散主干一起量化，在我们试过的模型上普遍可行。Stable Diffusion 3 是特例，它使用三个不同的文本编码器。我们发现量化*第二个*文本编码器效果不好，因此推荐以下替代方案：

- 只量化第一个文本编码器（[`CLIPTextModelWithProjection`](https://huggingface.co/docs/transformers/en/model_doc/clip#transformers.CLIPTextModelWithProjection)）或
- 只量化第三个文本编码器（[`T5EncoderModel`](https://huggingface.co/docs/transformers/en/model_doc/t5#transformers.T5EncoderModel)）或
- 量化第一和第三个文本编码器

| 1 ✅ | FP8 | 0 | 0 | 1 | 8.294 | 2.781 |
| 1 | FP8 | 1 | 1 | 0 | 14.384 | 2.833 |
| 1 | FP8 | 0 | 1 | 0 | 14.475 | 2.818 |
| 1 ✅ | FP8 | 1 | 0 | 0 | 14.384 | 2.730 |
| 1 | FP8 | 0 | 1 | 1 | 8.325 | 2.875 |
| 1 ✅ | FP8 | 1 | 0 | 1 | 8.204 | 2.789 |
| 1 | 无 | - | - | - | 16.403 | 2.118 |

| 量化的文本编码器：1 | 量化的文本编码器：3 | 量化的文本编码器：1 和 3 |

## 其他发现

### H100 上 `bfloat16` 通常更好

在受支持的 GPU 架构（如 H100 或 4090）上，使用 `bfloat16` 可以更快。下表是 PixArt 在我们的 H100 参考硬件上测得的一些数字：

| **Batch Size** | **精度** | **量化** | **内存（GB）** | **延迟（秒）** | **量化 TE** |
| --- | --- | --- | --- | --- | --- |
| 1 | FP16 | INT8 | 5.363 | 1.538 | True |
| 1 | BF16 | INT8 | 5.364 | **1.454** | True |
| 1 | FP16 | FP8 | 5.363 | 1.601 | True |
| 1 | BF16 | FP8 | 5.363 | **1.495** | True |

### `qint8` 的潜力

我们发现用 `qint8`（而非 `qfloat8`）量化在推理延迟上普遍更好。当我们水平融合注意力的 QKV 投影（在 Diffusers 中调用 `fuse_qkv_projections()`）、把 int8 kernel 的维度"加厚"以加速计算时，这个效果更明显。下面给出 PixArt 的一些证据：

| **Batch Size** | **量化** | **内存（GB）** | **延迟（秒）** | **量化 TE** | **QKV 投影融合** |
| --- | --- | --- | --- | --- | --- |
| 1 | INT8 | 5.363 | 1.538 | True | False |
| 1 | INT8 | 5.536 | **1.504** | True | True |
| 4 | INT8 | 5.365 | 5.129 | True | False |
| 4 | INT8 | 5.538 | **4.989** | True | True |

### INT4 呢？

我们还在 `bfloat16` 下额外试验了 `qint4`。这只适用于 H100 上的 `bfloat16`，其他配置尚不支持。用 `qint4`，内存消耗可望进一步下降，代价是推理延迟上升。延迟上升在预期之内，因为 int4 计算没有原生硬件支持——权重以 4 bit 传输，但计算仍在 `bfloat16` 下进行。下表是 PixArt-Sigma 的结果：

| **Batch Size** | **量化 TE** | **内存（GB）** | **延迟（秒）** |
| --- | --- | --- | --- |
| 1 | 否 | 9.380 | 7.431 |
| 1 | 是 | **3.058** | 7.604 |

但要注意，INT4 的激进离散化会伤害最终效果。因此对基于 Transformer 的模型，我们通常把最后的投影层留在量化之外。在 Quanto 中这样做：

```
quantize(pipeline.transformer, weights=qint4, exclude="proj_out")
freeze(pipeline.transformer)
```

`"proj_out"` 对应 `pipeline.transformer` 的最后一层。下表给出各种设置下的结果：

| 量化 TE：否，排除层：无 | 量化 TE：否，排除层："proj_out" | 量化 TE：是，排除层：无 | 量化 TE：是，排除层："proj_out" |
| --- | --- | --- | --- |
| ![Image 1 without text encoder quantization.](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/quanto-diffusers/ckpt%40pixart-bs%401-dtype%40bf16-qtype%40int4-qte%400-fuse%400.png) | ![Image 2 without text encoder quantization but with proj_out excluded in diffusion transformer quantization.](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/quanto-diffusers/ckpt%40pixart-bs%401-dtype%40bf16-qtype%40int4-qte%400-fuse%400-exclude%40proj_out.png) | ![Image 3 with text encoder quantization.](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/quanto-diffusers/ckpt%40pixart-bs%401-dtype%40bf16-qtype%40int4-qte%401-fuse%400.png) | ![Image 3 with text encoder quantization but with proj_out excluded in diffusion transformer quantization..](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/quanto-diffusers/ckpt%40pixart-bs%401-dtype%40bf16-qtype%40int4-qte%401-fuse%400-exclude%40proj_out.png) |

要找回损失的图像质量，常见做法是量化感知训练（quantization-aware training），Quanto 也支持。该技术超出本文范围，感兴趣欢迎联系我们！

本文所有实验的结果都在[这里](https://huggingface.co/datasets/sayakpaul/sample-datasets/tree/main/quanto-exps-2)。

## 彩蛋 - 用 Quanto 保存与加载 Diffusers 模型

量化的 Diffusers 模型可以保存和加载：

```
from diffusers import PixArtTransformer2DModel
from optimum.quanto import QuantizedPixArtTransformer2DModel, qfloat8

model = PixArtTransformer2DModel.from_pretrained("PixArt-alpha/PixArt-Sigma-XL-2-1024-MS", subfolder="transformer")
qmodel = QuantizedPixArtTransformer2DModel.quantize(model, weights=qfloat8)
qmodel.save_pretrained("pixart-sigma-fp8")
```

得到的 checkpoint 体积为 ***587MB***，而原始是 2.44GB。然后可以加载：

```
from optimum.quanto import QuantizedPixArtTransformer2DModel
import torch

transformer = QuantizedPixArtTransformer2DModel.from_pretrained("pixart-sigma-fp8") 
transformer.to(device="cuda", dtype=torch.float16)
```

并在 `DiffusionPipeline` 中使用它：

```
from diffusers import DiffusionPipeline
import torch

pipe = DiffusionPipeline.from_pretrained(
    "PixArt-alpha/PixArt-Sigma-XL-2-1024-MS", 
    transformer=None,
    torch_dtype=torch.float16,
).to("cuda")
pipe.transformer = transformer

prompt = "A small cactus with a happy face in the Sahara desert."
image = pipe(prompt).images[0]
```

未来，我们有望在初始化流水线时直接传入 `transformer`，让下面这种写法生效：

```
pipe = PixArtSigmaPipeline.from_pretrained(
    "PixArt-alpha/PixArt-Sigma-XL-2-1024-MS", 
-    transformer=None,
+    transformer=transformer,
    torch_dtype=torch.float16,
).to("cuda")
```

`QuantizedPixArtTransformer2DModel` 的实现见[这里](https://github.com/huggingface/optimum-quanto/blob/601dc193ce0ed381c479fde54a81ba546bdf64d1/optimum/quanto/models/diffusers_models.py#L184)供参考。如果你希望更多 Diffusers 模型支持在 Quanto 中保存与加载，请在[这里](https://github.com/huggingface/optimum-quanto/issues/new)提 issue 并 @ `@sayakpaul`。

## 技巧

- 根据需求，你可以对流水线的不同模块应用不同类型的量化。例如文本编码器用 FP8、diffusion transformer 用 INT8。多亏 Diffusers 和 Quanto 的灵活性，这一切可以无缝完成。
- 为针对你的用例优化，甚至可以把量化与 Diffusers 的其他[内存优化技术](https://huggingface.co/docs/diffusers/main/en/optimization/memory)组合使用，如 `enable_model_cpu_offload()`。

## 结论

本文中，我们展示了如何量化 Diffusers 里的 Transformer 模型并优化其内存占用。当进一步量化混入的文本编码器时，量化的效果更加明显。希望你在自己的项目中应用这些工作流并受益 🤗。
