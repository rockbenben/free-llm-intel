# Reachy Mini 实现完全本地化

作者：Amir Mahla（A-Mahla）、Andres Marafioti（andito）

组装好你的 Reachy Mini 后，你会安装[对话应用](https://github.com/pollen-robotics/reachy_mini_conversation_app)并开始和它说话。到目前为止，你得把音频发到服务器才行。但现在不用了。今天我们就带你把整个技术栈跑在本地。

这套栈由 [`speech-to-speech`](https://github.com/huggingface/speech-to-speech) 驱动——我们的级联 VAD → STT → LLM → TTS 流水线，对外暴露兼容 Realtime API 的 `/v1/realtime` WebSocket。启动后端之后，在 UI 里把机器人指向它即可。

级联（cascade）是当前开源方案里最灵活的选择，配上合适的组件，它同时也是最快的。我们会推荐自己最满意的组件，但级联的意义就在于：任何一个都能换。新模型每周都在冒出来。

> TL;DR
> 
> 为 Reachy Mini 部署本地语音后端。
> 我们使用自家 speech-to-speech 库，采用级联方案。
> 推荐配置：llama.cpp + Gemma 4、Silero VAD、Parakeet-TDT 0.6B v3 STT、Qwen3-TTS。

## 快速开始

本博客带你完全在本地运行 Reachy Mini 对话。没有云、没有 API key、数据不出你的机器。这里有一段实机视频：

### 本地部署 LLM

跑 LLM 我们用 Hugging Face 的 `llama.cpp`。如果还没装，最简单的办法是 `brew install llama.cpp` 或 `winget install llama.cpp`；更多帮助请看[文档](https://github.com/ggml-org/llama.cpp/blob/master/docs/install.md)。先运行：

```
llama-server -hf ggml-org/gemma-4-E4B-it-GGUF -np 2 -c 65536 -fa on --swa-full
```

搞定！第一次会下载模型，之后再启动就很快了。

这些参数都是干什么的？

- `-hf ggml-org/gemma-4-E4B-it-GGUF` —— 直接从 Hub 拉取模型。第一次运行下载，之后走缓存。
- `-np 2` —— 两个并行槽位。让服务器在处理第一个请求的同时还能接住第二个请求（比如一次快速插话），互不阻塞。
- `-c 65536` —— 64k 上下文窗口，各槽位共享。长对话绰绰有余。
- `-fa on` —— flash attention。更快、更省内存，在现代硬件上基本是白送的。
- `--swa-full` —— 保留完整的滑动窗口注意力缓存而不是重算。用一点内存换 Gemma 上明显更快的 prompt 处理。

### 部署 speech-to-speech

我们先简单地安装这个库

```
uv pip install speech-to-speech
```

然后，在另一个终端服务着 LLM 的同时，直接运行：

```
speech-to-speech --responses_api_base_url "http://127.0.0.1:8080" --responses_api_api_key "" --mode local
```

你就可以在终端里跟模型对话了！第一次需要下载 Parakeet-TDT 0.6B v3 和 Qwen3TTS，之后启动就很快。

llama.cpp 和 speech-to-speech 都跑起来后，用桌面应用启动机器人、打开对话应用。在对话应用的 UI 里，点 HF 后端的 "edit connection" 选择本地模式。怎么做见这段视频：

## 深入

### 为什么要自建 Speech-to-Speech 服务器？

托管的实时后端很方便，但自建引擎能解锁三样东西：

- **隐私。** 音频不出你的网络，整条流水线跑在你自己控制的硬件上。
- **没有 API 费用。** 没有按分钟、按 token 的收费。
- **对流水线的完全控制。** 想换就换：VAD、STT、LLM、TTS。Hub 🤗 上一有好东西就能上。

`speech-to-speech` 仓库把这些全部装进一个 CLI。它在 `/v1/realtime` 启动一个 WebSocket 服务，说的是 Reachy Mini 本来就听得懂的协议。

### 我们有主见的默认配置：VAD、STT、TTS

级联语音流水线有四个阶段：VAD、STT、LLM 和 TTS。其中三个我们选了靠谱的默认值，好让你专心挑 LLM：

| 阶段 | 选择 | 原因 |
| --- | --- | --- |
| VAD | **Silero VAD v5** | 小巧、准确、跑在 CPU 上。开源语音智能体圈的事实默认项。 |
| STT | **Parakeet-TDT 0.6B v3** | 适合流式、非常快、英文质量出色。 |
| TTS | **Qwen3-TTS** | 表现力强、低延迟、多语言，支持自定义音色。 |

这些选择我们是带立场的；如果你有自己的偏好，尽管替换。

### 挑选你的 LLM

LLM 是对系统延迟和整体性能影响最大的一层。我们支持两种玩法：**本地跑模型**（llama.cpp、MLX、Transformers、vLLM），或**使用带 Responses API 的服务器**（OpenAI、Gemini、HF Inference Endpoints、llama.cpp、vLLM 等）。

#### Responses API：把"大脑"从语音循环里解耦

系统的主要瓶颈是 LLM 推理延迟。为应对这一点，我们通过 Responses API 协议支持外接推理引擎。

因此 `speech-to-speech` 引擎支持第二种模式：LLM 活在独立进程里，只要它说 Responses API 协议。你在一个终端启动模型服务器，在另一个终端启动语音循环，两者通过 HTTP 对话。

##### 方案 1：一个终端 llama.cpp，另一个终端 speech-to-speech

**终端 1：llama.cpp 服务器：**

```
llama-server -hf ggml-org/gemma-4-E4B-it-GGUF -np 2 -c 65536 -fa on --swa-full
```

**终端 2：speech-to-speech 客户端：**

```
speech-to-speech \
  --mode realtime \
  --stt parakeet-tdt \
  --tts qwen3 \
  --llm_backend responses-api \
  --model_name "ggml-org/gemma-4-E4B-it-GGUF" \
  --responses_api_base_url "http://127.0.0.1:8080/v1"
```

##### 方案 2：一个终端 vLLM，另一个终端 speech-to-speech

> 需要 vLLM ≥ 0.21.0。对 Responses API 协议的完整支持——包括 speech-to-speech 后端用到的工具调用流式传输——在 vLLM 0.21.0 落地。旧版本能启动，但助手一旦尝试调用工具就会出错。

在这条流水线里通过 vLLM 服务模型时，有三个参数实际上是必须的：

- `--enable-auto-tool-choice`
- `--tool-call-parser <tool_parser_name>` —— 选择按模型家族解析、把模型原始输出变成结构化工具调用的 parser（如 Qwen3 instruct 模型用 `qwen3_coder`，Llama 3 用 `llama3_json`，Hermes 系模型用 `hermes`……）。
- `--default-chat-template-kwargs '{"enable_thinking":false}'`：对支持的模型关闭 `<think>` 推理通道。做更重的 agent 任务时你可以把它翻成 `true` 让模型先推理，但对自然流畅的对话我们强烈建议保持关闭：每一个 thinking token 都是机器人开口前用户听到的沉默延迟。

**终端 1：vLLM 推理服务器（`Qwen/Qwen3-4B-Instruct-2507`）：**

```
vllm serve Qwen/Qwen3-4B-Instruct-2507 \
  --port 8000 \
  --host 127.0.0.1 \
  --max-model-len 32768 \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder \
  --default-chat-template-kwargs '{"enable_thinking":false}' \
  --speculative-config '{"method":"qwen3_next_mtp","num_speculative_tokens":1}'
```

> `--speculative-config` 这一行启用了多 token 预测（MTP）。它是可选的，但对端到端延迟影响很大。只要模型支持，就开着。

**终端 2：speech-to-speech 客户端：**

```
speech-to-speech \
  --mode realtime \
  --stt parakeet-tdt \
  --tts qwen3 \
  --llm_backend responses-api \
  --model_name "Qwen/Qwen3-4B-Instruct-2507" \
  --responses_api_base_url "http://127.0.0.1:8000/v1"
```

##### 方案 3：Hugging Face Inference Endpoints

同样的协议，只不过模型跑在 Hugging Face 托管 GPU 上。把任意 chat 模型部署成 Inference Endpoint，然后让语音循环指向端点 URL：

```
speech-to-speech \
  --mode realtime \
  --stt parakeet-tdt \
  --tts qwen3 \
  --llm_backend responses-api \
  --model_name "Qwen/Qwen3-4B-Instruct-2507" \
  --responses_api_base_url "https://<your-endpoint>.endpoints.huggingface.cloud/v1" \
  --responses_api_api_key "$HF_TOKEN"
```

##### 方案 4：Hugging Face Inference Providers

如果不想自己管端点，用 [Inference Provider](https://huggingface.co/docs/inference-providers)。Hugging Face 会把请求路由给第三方后端（如 Together、Fireworks、Replicate），只有一个 URL：

```
speech-to-speech \
  --mode realtime \
  --stt parakeet-tdt \
  --tts qwen3 \
  --llm_backend responses-api \
  --model_name "Qwen/Qwen3.6-35B-A3B:deepinfra" \
  --responses_api_base_url "https://router.huggingface.co/v1" \
  --responses_api_api_key "$HF_TOKEN"
```

##### 方案 5：OpenAI（或任何 OpenAI 兼容提供商）

想在零基础设施的情况下拿前沿模型做测试，把同一个参数指向 OpenAI 即可：

```
speech-to-speech \
  --mode realtime \
  --stt parakeet-tdt \
  --tts qwen3 \
  --llm_backend responses-api \
  --model_name "gpt-5.4" \
  --responses_api_api_key "$OPENAI_API_KEY"
```

`--responses_api_*` 参数对所有实现该协议的提供商（OpenRouter、Together、Fireworks……）用法一致。换 base URL 和 API key，流水线的其余部分保持不变。

#### 在进程内运行 LLM

##### 方案 1：MLX 本地 LLM（Apple Silicon）

如果你在 Mac 上，MLX 是以可接受的延迟跑真实模型最省事的方式。我们推荐 **Qwen3-4B-Instruct-2507**——小到在 M 系列芯片上感觉即发即至，又强到能撑住一场对话。

```
speech-to-speech \
  --llm_backend mlx-lm \
  --model_name "mlx-community/Qwen3-4B-Instruct-2507-bf16"
```

服务器默认监听 `ws://127.0.0.1:8765/v1/realtime`。让它挂着，把对话应用连到本地后端，你就能跟机器人说话了。

##### 方案 2：Transformers 本地 LLM（CUDA / CPU / MPS）

思路相同，但用原生 `transformers`。适合 CUDA 机器、Linux，或者想自由换模型而不用为 MLX 重新转换权重的场景。

```
speech-to-speech \
  --llm_backend transformers \
  --model_name "Qwen/Qwen3-4B-Instruct-2507"
```

> 提示。Qwen3-4B-Instruct-2507 是 LLM 的另一个好选择——单张消费级显卡上速度和质量的平衡不错。`--model_name` 可以指向后端支持的任何 HF 模型——比如更大的 Gemma、Qwen 或 Mistral。

### 引擎跑在笔记本上、应用跑在机器人上

如果你在笔记本上跑语音引擎、在 Reachy Mini Wireless 上跑对话应用，唯一要变的是 URL。确保引擎绑定到局域网地址（而不是只有 `127.0.0.1`），并在 UI 选择 IP 时让机器人用笔记本的 IP。

不知道自己的 IP？这样查：

macOS

```
ipconfig getifaddr en0    # wifi
ipconfig getifaddr en1    # ethernet (sometimes en0, varies)
```

Linux

```
hostname -I
```

Windows

```
ipconfig
```

在活动网卡下找 "IPv4 Address"。

要的是 `192.168.x.x` 或 `10.x.x.x` 那个。如果你看到 `169.254.x.x`，说明其实没连上网络。

## 收尾

现在你有了一条完全本地的语音循环：

- 机器人用 **Silero** 听，
- 用 **Parakeet-TDT 0.6B v3** 转录，
- 用你选的任何 LLM 思考——本地 MLX、本地 Transformers、隔壁的 vLLM 或 llama.cpp 服务器，或托管的 Responses API 端点，
- 用 **Qwen3-TTS** 回答。
