[Sentence Transformers](https://sbert.net/) 是一个用于使用和训练 embedding 与 reranker 模型的 Python 库，服务于检索增强生成（RAG）、语义搜索等应用。随着 v6.0 更新，它新增了第四种模型类型：`MultiVectorEncoder`，用于 ColBERT 风格的后期交互（late interaction）检索。任何 [PyLate](https://github.com/lightonai/pylate) checkpoint、任何 [Stanford-NLP ColBERT](https://github.com/stanford-futuredata/ColBERT) checkpoint 都能直接加载，面向视觉文档检索的 [colpali-engine](https://github.com/illuin-tech/colpali) 模型同样可以通过你已在用于稠密（dense）、稀疏（sparse）和 reranker 模型的那套熟悉 API 使用。

普通 embedding 模型把整段文本压成一个向量，而多向量模型保留**每个 token 一个向量**，用 MaxSim 算子给 query 和 document 打分。这保住了单个向量不得不平均掉的 token 级匹配信息，代价通常是更大的索引，换来的是更强的检索。它也是视觉文档检索的最先进水平：文本查询直接与页面图像匹配，中间不需要 OCR 步骤。

本文演示如何使用这些模型：加载各种 checkpoint 格式、编码与打分、接入搜索栈、在页面图像上运行，以及让索引保持在可承受的规模。下面所有内容用普通的 `pip install -U sentence-transformers` 就能跑。

> 本文讲的是使用多向量模型。想了解如何训练它们，请看配套博客《用 Sentence Transformers 训练和微调多向量 Embedding 模型》。

## 什么是多向量模型？

稠密 embedding 模型读入一段文本，返回一个固定尺寸的向量。模型注意到的一切都要塞进那 384、768 或 1024 个数字里，相似度就是两个这样的摘要之间的一次点积。这招出奇地好用，但这种压缩有一种特定的有损性：一个罕见实体、一个精确标识符、长文中一个关键子句，都得在同一个向量里争地方。带有多个需求的查询也会撞上同一堵墙。对于"带木腿和圆垫的绿色沙发"，单个向量必须把四个要求混成一个点，于是"腿不对的绿色沙发"也会离你要的东西很近。

多向量模型（也叫后期交互或 ColBERT 风格模型，源自 [ColBERT 论文](https://arxiv.org/abs/2004.12832)）跳过了这种压缩。它跑同样的 Transformer，但不把 token embedding 池化成一个向量，而是把每个 token embedding 投影到一个较小的维度（经典值是 128）并全部保留。一个 9 token 的文档就变成 9x128 的矩阵，而不是 1x128 的向量。

query 与 document 之间的交互被推迟到打分时进行——"后期交互"之名由此而来。Cross-encoder 是"早期交互"：两段文本一起过模型，很准，但没什么可以预计算，因为每个新 query 都要把所有文档重新编码一遍。Bi-encoder（上面说的稠密 embedding 模型就是）几乎不交互（两个成品摘要之间一次点积），而这正是你能一次性编码整个集合、快速查询的原因。后期交互介于两者之间。文档依然独立编码、可离线建索引，但打分时每个 query token 都与每个 document token 比较，给两者留下了大得多的交互空间。

[![Dense embedding versus multi-vector late interaction: a dense model encodes each text into one vector and scores with cosine similarity, while a multi-vector model keeps one vector per token and scores every query token against every document token with MaxSim](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/multi-vector-encoder/maxsim_explainer.gif)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/multi-vector-encoder/maxsim_explainer.gif)

### MaxSim 算子

打分用 MaxSim：对每个 query token，取它与任意 document token 相似度的最大值，然后把这些最大值沿 query 求和。

MaxSim(Q, D) = Σ_{Qi ∈ Q} max_{Dj ∈ D} Qi · Dj

由于 token embedding 做过 L2 归一化，每个点积都是 `[-1, 1]` 范围内的余弦相似度，所以总和落在 `[-num_query_tokens, num_query_tokens]` 之间。

你可以把这个算子理解为一种软对齐：每个 query token 指向最能解释它的那个 document token，分数则衡量文档对 query 的整体支撑程度。

这种对齐不必是字面的，因为 token embedding 带有上下文。用 [`lightonai/mLateOn`](https://huggingface.co/lightonai/mLateOn) 把 "Where do penguins live?" 对 "Penguins inhabit Antarctica." 编码，query token `live` 在 `inhabit` 上找到最佳匹配，得分 0.94——一个与它没有任何共同字符的词！这是词法检索做不到的事：BM25 及其亲戚需要词本身出现，所以同义词和改写会从它们眼皮底下溜走。稠密 embedding 模型当然也能跨过这道沟，后期交互的额外价值在于它不必牺牲另一个方向：当精确匹配才是关键（产品代码、姓氏、函数名）时，MaxSim 手里还捏着那个独立的 token，而单向量模型早把它跟别的东西平均掉了。而且对齐也不是一对一的：多个 query token 常常落在同一个 document token 上。

### 得到什么，付出什么

你得到检索质量，尤其是在这些场景：文档中某一处特定内容决定了它的相关性；像上面沙发那样的多需求查询，每个要求都能各自找到证据；以及稠密模型的压缩没有针对其分布调优过的域外数据——那种压缩是从训练查询学来的，模型学会了保留它们需要的、丢掉其余的一切，而那"其余"里可能恰好包括你生产环境查询要问的东西。文档越长影响越大，因为更多的文本要塞进同一个固定向量。

代价是索引体积。每个 token 一个向量取代每个文档一个向量，向量数量暴增，较小的维度只能部分抵消。用 [`lightonai/LateOn`](https://huggingface.co/lightonai/LateOn) 编码 4,874 条 Natural Questions 段落，得到 608,414 个 token 向量，平均每段 124.8 个：

| 表示方式 | 向量数 | 维度 | float32 大小 |
| --- | --- | --- | --- |
| 稠密，[`all-MiniLM-L6-v2`](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2) | 4,874 | 384 | 7.5 MB |
| 稠密，[`gte-modernbert-base`](https://huggingface.co/Alibaba-NLP/gte-modernbert-base) | 4,874 | 768 | 15.0 MB |
| 多向量，`LateOn` | 608,414 | 128 | 311.5 MB |

这大约是 MiniLM 索引存储量的 42 倍，即每段 62 KiB。不过索引通常会压缩，比如同样这 608,414 个向量做成 [fast-plaid](https://huggingface.co/blog/multi-vector-encoder#indexing) 索引只要 92 MB，因为 PLAID 对每个向量只存一个质心 id 加一个量化残差，而不是向量本身。做个对比：一个 4096 维的稠密模型如 [Qwen3-Embedding-8B](https://huggingface.co/Qwen/Qwen3-Embedding-8B) 对这同样 4,874 段文本大约需要 80 MB，所以压缩后的多向量索引和大家已经在跑的稠密索引处在同一量级。[Token 池化](https://huggingface.co/blog/multi-vector-encoder#token-pooling)能在这一切之前先把向量数砍下来，[检索再重排](https://huggingface.co/blog/multi-vector-encoder#retrieve-and-rerank)则可以完全不用建索引。

[PyLate](https://github.com/lightonai/pylate) 在后文反复出现，先交代来龙去脉：Sentence Transformers 过去只支持稠密和稀疏模型、不支持后期交互，于是 [LightOn](https://huggingface.co/lightonai) 在其之上构建 PyLate 补上这个空缺，添加了这些模型所需的训练、推理和检索组件。下面要加载的模型很多就是用它训练的，LightOn 还围绕它建了生态，包括出现在[索引](https://huggingface.co/blog/multi-vector-encoder#indexing)一节的后期交互索引 [fast-plaid](https://github.com/lightonai/fast-plaid)。v6.0 把这些能力收进了 Sentence Transformers 本体。

权衡讲清了，来跑一个模型吧。

## 安装

普通安装即可使用多向量模型：

```
pip install -U sentence-transformers
```

要做 ColPali 风格的视觉文档检索，还需要图像依赖（所有 extras 见[安装文档](https://sbert.net/docs/installation.html)，多模态支持总览见[多模态 Embedding 与 Reranker 模型](https://huggingface.co/blog/multimodal-sentence-transformers)）：

```
pip install -U "sentence-transformers[image]"
```

> Sentence Transformers v6.0 要求 transformers v5.x、torch 2.2+ 和 huggingface-hub v1.x。如果你把其中任何一个锁定在更低版本，请先规划升级。破坏性变动的完整清单见迁移指南（Migration Guide）。

## 加载模型

加载多向量模型和加载其他任何 Sentence Transformers 模型一模一样：

```
from sentence_transformers import MultiVectorEncoder

model = MultiVectorEncoder("lightonai/LateOn")
```

想找到可用的模型，在 Hub 上搜 [`multi-vector` 和 `sentence-transformers` 标签](https://huggingface.co/models?library=sentence-transformers&other=multi-vector)。带这两个标签的模型都能用上面那行代码加载——不管它原本是 PyLate checkpoint、Stanford-NLP ColBERT checkpoint，还是用于视觉文档检索的 ColPali 家族模型。我们正在梳理整个生态，把标签加到每一个可用模型上，所以这个列表还在变长。

底层上，`MultiVectorEncoder` 能识别这些 checkpoint 历年发布的各种格式，所以即使某些模型还没加标签，PyLate 和 Stanford-NLP 的 checkpoint 也能直接加载：

```
from sentence_transformers import MultiVectorEncoder

# Native Sentence Transformers checkpoints. PyLate builds on the same schema,
# so any PyLate checkpoint loads identically
model = MultiVectorEncoder("lightonai/LateOn")
model = MultiVectorEncoder("mixedbread-ai/mxbai-edge-colbert-v0-17m")
model = MultiVectorEncoder("LiquidAI/LFM2.5-ColBERT-350M", trust_remote_code=True)

# Any Stanford-NLP ColBERT checkpoint, detected via the `HF_ColBERT` architecture
# marker. The inline projection weight and the recipe come from `artifact.metadata`
model = MultiVectorEncoder("colbert-ir/colbertv2.0")
model = MultiVectorEncoder("answerdotai/answerai-colbert-small-v1")

# A bare transformer: a fresh random projection is appended, so training is required
model = MultiVectorEncoder("answerdotai/ModernBERT-base")
```

视觉文档检索模型是例外。ColPali 家族的 checkpoint 以 colpali-engine 自己的格式发布，其中没有 Sentence Transformers 能用的信息，所以每个模型都需要先在其仓库里补充一份小配置才能加载。大部分这类工作已经完成、正等待合并。当前状态和今天如何加载见[支持的模型](https://huggingface.co/blog/multi-vector-encoder#supported-models)。

### 查看 checkpoint 的配置

多向量模型带有若干随 checkpoint 而异的"配方"旋钮：query 和 document 的标记前缀、长度上限、query 是否用 `[MASK]` token 补齐，以及给文档打分时跳过哪些 token。这些都在模块配置里，所以 `print(model)` 会让你清楚看到加载了什么。下面是原版 ColBERTv2 checkpoint，它把每个 query 补齐到恰好 32 个 token，并把文档截断在 180：

```
from sentence_transformers import MultiVectorEncoder

model = MultiVectorEncoder("colbert-ir/colbertv2.0")
print(model)
"""
MultiVectorEncoder(
  (0): Transformer({..., 'document_length': 180,
                    'query_expansion': {'strategy': 'fixed', 'attend': False, 'token': None, 'length': 32}})
  (1): Dense({'in_features': 768, 'out_features': 128, 'bias': False, ...})
  (2): MultiVectorMask({'skiplist_words': ['!', '"', '#', ...], 'skiplist_tasks': ['document'], ...})
  (3): Normalize({...})
)
"""
print(model.prompts)
# {'query': '[unused0] ', 'document': '[unused1] '}
```

这就是经典 ColBERT 流水线：`Transformer` 产出上下文化 token embedding，token 级的 `Dense` 把它们各自投影到 128 维，`MultiVectorMask` 决定打分时哪些 token 有效，最后是 token 级的 `Normalize`。其他 checkpoint 会填入不同的值。`lightonai/GTE-ModernColBERT-v1` 用同样的四个模块，前缀是 `[Q] ` 和 `[D] `，没有 query 扩展，长度上限分别是 48 和 300。

这些你几乎不用动手，因为每个已发布的 checkpoint 都会自配置。只有当你从裸骨干（bare backbone）搭模型时才需要关心，那在[创建自定义模型](https://sbert.net/docs/multi_vector_encoder/usage/custom_models.html)里有讲。

不过有一个值值得对照你自己的数据检查：`document_length` 是截断，超过它的内容永远进不了索引。例如一段 662 token 的段落经过 LateOn 的 300 上限后只剩 273 个向量，其余部分直接消失。这些 checkpoint 大多在短段落上训练，所以如果你的 chunk 比上限长，可以在单次调用里用 `encode_document(..., processing_kwargs={"text": {"max_length": 512}})` 抬高中上限——注意这会让模型跑超过它训练时的长度，而且索引大小大致成比例增长。多向量模型通常对这种超出承受得很好。在长文档检索基准 [MLDR](https://huggingface.co/datasets/Shitao/MLDR) 上，上面那对模型的多语言版本差距很明显：[mLateOn 得 77.92，mDenseOn 只有 51.59](https://huggingface.co/blog/lightonai/mdenseon-mlateon#long-document-retrieval-mldr)。

## 编码查询与文档

多向量模型是非对称的：query 和 document 走不同的前缀、不同的长度上限、不同的打分掩码。与许多稠密模型（两者可互换）不同，这里必须用 [`encode_query()`](https://sbert.net/docs/package_reference/multi_vector_encoder/model.html#sentence_transformers.multi_vector_encoder.model.MultiVectorEncoder.encode_query) 和 [`encode_document()`](https://sbert.net/docs/package_reference/multi_vector_encoder/model.html#sentence_transformers.multi_vector_encoder.model.MultiVectorEncoder.encode_document)才能得到正确的 embedding：

```
from sentence_transformers import MultiVectorEncoder

model = MultiVectorEncoder("lightonai/mLateOn")

queries = ["What is the capital of France?"]
documents = [
    "Paris is the capital of France.",
    "Berlin is the capital and largest city of Germany, by both area and population.",
]

query_embeddings = model.encode_query(queries)
document_embeddings = model.encode_document(documents)

print(query_embeddings[0].shape)
# (10, 128)
print(document_embeddings[0].shape, document_embeddings[1].shape)
# (10, 128) (19, 128)
```

返回的是 2D 张量的*列表*，每个输入对应一个，形状为 `(num_tokens, embedding_dim)`。与稠密 embedding 不同，这些没法堆成一个矩形张量，因为每个输入的 token 数都不同。第二篇文档比第一篇长，所以它回来的是更高的矩阵。

每次调用都会应用模型自己的配方。`encode_query` 加上 query 标记、按 checkpoint 要求把 query 扩展到固定长度、并截断到 query 长度上限。`encode_document` 加上 document 标记、截断到文档长度上限，并在打分掩码中剔除 skiplist 中的 token（多数 checkpoint 是标点）。

`encode()` 常用的参数全都有效，所以 `batch_size`、`show_progress_bar`、`convert_to_numpy`、`device` 和多进程池都照常工作：

```
document_embeddings = model.encode_document(
    documents,
    batch_size=64,
    show_progress_bar=True,
)
```

## 用 MaxSim 打分

[`model.similarity()`](https://sbert.net/docs/package_reference/multi_vector_encoder/model.html#sentence_transformers.multi_vector_encoder.model.MultiVectorEncoder.similarity) 计算完整的全对 MaxSim 矩阵：

```
from sentence_transformers import MultiVectorEncoder

model = MultiVectorEncoder("lightonai/LateOn")

query_embeddings = model.encode_query(["Which planet is known as the Red Planet?"])
document_embeddings = model.encode_document([
    "Venus is often called Earth's twin because of its similar size and proximity.",
    "Mars, known for its reddish appearance, is often referred to as the Red Planet.",
    "Jupiter, the largest planet in our solar system, has a prominent red spot.",
    "Saturn, famous for its rings, is sometimes mistaken for the Red Planet.",
])

scores = model.similarity(query_embeddings, document_embeddings)
print(scores)
# tensor([[10.7942, 11.1104, 10.9743, 11.0811]])
```

Mars 胜出，理应如此，只是其余候选咬得很紧。Saturn 也包含字面短语 "the Red Planet"，Jupiter 是有一颗红斑的行星，所以 token 级算子在三个候选里都有东西可抓。重要的是排序。

分数经常这么接近，[GLInt](https://huggingface.co/blog/chungimungi/glint#1-mining-in-maxsim-space) 通过测量整个候选池上的散布证明了这一点。MaxSim 对每个 query token 取*最大值*，所以文档通常能给每个 query token 一个不错的最佳匹配，分数起点就不低。而且上下文化 token embedding 是各向异性的，聚在一个狭窄的锥体里而不是均匀散布，所以任意 token 对的得分都倾向于偏高。

还有 [`model.similarity_pairwise()`](https://sbert.net/docs/package_reference/multi_vector_encoder/model.html#sentence_transformers.multi_vector_encoder.model.MultiVectorEncoder.similarity_pairwise)，适用于你已经有一一配对的 query-document、只想要成对分数而不是完整相似度矩阵的场景：

```
scores = model.similarity_pairwise(query_embeddings, document_embeddings[:1])
print(scores)
# tensor([10.7942])
```

### 分数量级与 MeanMaxSim

MaxSim 沿 query token 求和，量级随 query token 数缩放，这意味着你没法在不同 query 配方的模型之间比较分数。LateOn 把上面那句 Red Planet 查询编码为 12 个 token。同样这句 query、同样这些文档换成 ColBERTv2 跑——它把每个 query 补齐并截断到恰好 32 个 token——分数就落在完全不同的区间：

```
model = MultiVectorEncoder("colbert-ir/colbertv2.0")
# ... same encode_query / encode_document / similarity calls ...
print(scores)
# tensor([[12.7970, 27.1945, 23.8495, 24.5656]])
```

在同一个模型内部只需要排序，但如果你想要有界区间的分数，把模型的相似度函数换成 MeanMaxSim——它除以 query token 数。回到 LateOn：

```
model = MultiVectorEncoder("lightonai/LateOn", similarity_fn_name="meanmaxsim")
# or on an already-loaded model: model.similarity_fn_name = "meanmaxsim"

print(model.similarity(query_embeddings, document_embeddings))
# tensor([[0.8995, 0.9259, 0.9145, 0.9234]])
```

现在每个分数都是 `[-1, 1]` 内的平均余弦相似度，尽管实际上你只会看到 `[0, 1]`。

## 语义搜索

如果你的语料库不大，对全库穷举 MaxSim 是最简单可行的办法。语料编码一次，然后每个 query 和全部文档打分：

```
import time

from datasets import load_dataset

from sentence_transformers import MultiVectorEncoder

dataset = load_dataset("sentence-transformers/natural-questions", split="train[:5000]")
# Several questions share an answer passage, so drop repeats but keep the order
corpus = list(dict.fromkeys(dataset["answer"]))  # 5,000 rows -> 4,874 passages

model = MultiVectorEncoder("lightonai/LateOn")
corpus_embeddings = model.encode_document(corpus, show_progress_bar=True)

query = "when did richmond last play in a preliminary final"
start = time.perf_counter()
query_embeddings = model.encode_query([query])
scores = model.similarity(query_embeddings, corpus_embeddings)[0]  # 98ms
top_scores, top_indices = scores.topk(3)
print(f"Search took {(time.perf_counter() - start) * 1000:.1f}ms")

for score, index in zip(top_scores.tolist(), top_indices.tolist()):
    print(f"{score:.4f}  {corpus[index][:100]}")
"""
Search took 122.7ms
11.9192  Richmond Football Club Richmond began 2017 with 5 straight wins, a feat it had not achieved
11.7591  2017 AFL Grand Final The 2017 AFL Grand Final was an Australian rules football game contest
11.6710  Battle of Appomattox Court House The Battle of Appomattox Court House (Virginia, U.S.), fou
"""
```

这 4,874 段文本在一块 RTX 3090 上 20 秒编码完，每次搜索端到端约 120ms，其中大头是对全部 608,414 个 token 向量做 MaxSim 打分。这是精确计算，但耗时随语料总 token 数线性增长，且所有 token 向量都要驻留内存，所以它适用于几千而非几百万文档的规模。此脚本的可运行版本在 [semantic_search.py](https://github.com/huggingface/sentence-transformers/blob/main/examples/multi_vector_encoder/applications/semantic_search.py)。

超过这个规模你就需要一个真正的后期交互索引，而 Sentence Transformers 不自带。它也不必自带：这些索引存的就是 `encode_document` 产出的东西，所以你在这里编码，把 token embedding 交给为它们而造的组件即可。[索引](https://huggingface.co/blog/multi-vector-encoder#indexing)一节给了四个可用选项的代码片段，紧接其后的下一节讲如何完全跳过索引。

## 检索再重排

你也可以不维护后期交互索引就获得后期交互的质量——把多向量模型用作*重排器（reranker）*。快速的 bi-encoder 先把大语料收窄到少量候选，再由多向量模型只对它们重新打分：

```
from datasets import load_dataset

from sentence_transformers import MultiVectorEncoder, SentenceTransformer
from sentence_transformers.util import semantic_search

dataset = load_dataset("sentence-transformers/natural-questions", split="train[:50000]")
corpus = list(dict.fromkeys(dataset["answer"]))

retriever = SentenceTransformer("jinaai/jina-embeddings-v5-text-nano-retrieval")
reranker = MultiVectorEncoder("perplexity-ai/pplx-embed-v1-late-0.6b", trust_remote_code=True)

# First stage: index the corpus once with a fast bi-encoder
corpus_embeddings = retriever.encode_document(corpus, convert_to_tensor=True, show_progress_bar=True)

# Retrieve the top 50
query = "when did richmond last play in a preliminary final"
hits = semantic_search(retriever.encode_query([query], convert_to_tensor=True), corpus_embeddings, top_k=50)[0]
candidates = [corpus[hit["corpus_id"]] for hit in hits]

# Second stage: rescore just those candidates with MaxSim
query_embeddings = reranker.encode_query([query])
document_embeddings = reranker.encode_document(candidates)
scores = reranker.similarity(query_embeddings, document_embeddings)[0]

for index in scores.argsort(descending=True)[:3].tolist():
    print(f"{scores[index].item():.4f}  {candidates[index][:100]}")
```

只有这 50 个候选会被编码成多向量，所以你的索引仍是普通稠密索引，token 向量只是转瞬即逝。这和在检索-重排栈中 cross-encoder 扮演的角色相同，但多向量模型每个候选的开销要低得多：文档一次批量编码、用一次矩阵乘法打分，而不是每个 query-document 对做一次前向。可运行脚本是 [retrieve_rerank.py](https://github.com/huggingface/sentence-transformers/blob/main/examples/multi_vector_encoder/applications/retrieve_rerank.py)，它会打印两个阶段各自的耗时。

## 索引

多家向量数据库原生支持多向量的索引与打分：[Qdrant](https://qdrant.tech/documentation/concepts/vectors/)（自 v1.10）、[Weaviate](https://docs.weaviate.io/weaviate/tutorials/multi-vector-embeddings)（自 v1.29）、[Vespa](https://blog.vespa.ai/announcing-long-context-colbert-in-vespa/)（已支持多年）、[LanceDB](https://docs.lancedb.com/search/multivector-search)（自 v0.15.0），以及 [VectorChord](https://docs.vectorchord.ai/vectorchord/usage/indexing-with-maxsim-operators.html)——它给 Postgres 加了普通 pgvector 没有的 MaxSim 算子。[Milvus](https://milvus.io/docs/array-of-structs.md) 在 v2.6.4 也加入了这一行列，用的是 array-of-structs 特性（与它另一个叫 multi-vector search 的不相关特性不同）。如果你根本不想跑服务器，LightOn 的 [fast-plaid](https://github.com/lightonai/fast-plaid) 一条 `pip install` 就能装，直接实现了 PLAID；[PyLate](https://github.com/lightonai/pylate) 则在外面包了更完整的检索栈。

还有一些能部分支持：[OpenSearch](https://docs.opensearch.org/latest/search-plugins/search-relevance/rerank-by-field-late-interaction/) 和 [Elasticsearch](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/rank-vectors) 能用 MaxSim 给候选重排，但不能用它做召回，而且 Elasticsearch 的该字段还在技术预览阶段且属 Enterprise 层级。[turbopuffer](https://turbopuffer.com/docs/schema) 的后期交互索引在私有 beta 中。

下面的片段索引的是文本，但其中没有任何文本专属的东西。`encode_document` 交回来的都是同一格式的 token 向量矩阵列表——不管文档是一段文字、一页图像、一段音频还是一段视频——所以[视觉文档检索](https://huggingface.co/blog/multi-vector-encoder#visual-document-retrieval)一节那些 ColPali 风格模型可以原样放进以上任何一个库。只是每篇文档的向量更多，这也是为什么在那里更值得尽早用[token 池化](https://huggingface.co/blog/multi-vector-encoder#token-pooling)。

fast-plaid、Qdrant、Weaviate 和 Vespa 都直接接受 `encode_document` 的返回值，所以除了客户端库，代码完全一样。下面是每个库的可用片段，都针对[语义搜索](https://huggingface.co/blog/multi-vector-encoder#semantic-search)示例中的 4,874 段文本和 608,414 个 token 向量运行。每段代码旁标注了在同一台机器（RTX 3090、i7-13700K）上产生的入库和查询耗时，除代码所示外没做任何调优，只为让你对工作量的形状有个感觉。四者的查询都快于那一节 `model.similarity` 的 98ms，其中三个还在 CPU 上跑——这里只有 fast-plaid 用了 GPU。

### fast-plaid

[fast-plaid](https://github.com/lightonai/fast-plaid) 是 LightOn 用 Rust 实现的 PLAID——ColBERT 最初就是围绕这种索引构建的。没有服务器要启动，它直接读取 `encode_document` 交回的张量，无需任何转换。

```
# pip install sentence-transformers datasets fast-plaid
from datasets import load_dataset
from fast_plaid import search
from sentence_transformers import MultiVectorEncoder

dataset = load_dataset("sentence-transformers/natural-questions", split="train[:5000]")
corpus = list(dict.fromkeys(dataset["answer"]))
model = MultiVectorEncoder("lightonai/LateOn")
query = "when did richmond last play in a preliminary final"

document_embeddings = model.encode_document(corpus, batch_size=32)
query_embedding = model.encode_query(query)

fast_plaid = search.FastPlaid(index="natural-questions", device="cuda")

# 4,874 documents (608,414 token vectors) indexed in 5s
fast_plaid.create(documents_embeddings=document_embeddings)

results = fast_plaid.search(queries_embeddings=query_embedding.unsqueeze(0), top_k=3)  # 11ms

for index, score in results[0]:
    print(f"{score:.4f}  {corpus[index][:90]}")
"""
11.8828  Richmond Football Club Richmond began 2017 with 5 straight wins, a feat it had not achieve
11.7676  2017 AFL Grand Final The 2017 AFL Grand Final was an Australian rules football game contes
11.6758  Battle of Appomattox Court House The Battle of Appomattox Court House (Virginia, U.S.), fo
"""
```

`index` 参数是一个目录而不只是一个标签，所以索引在构建时就直接落盘。新的 `FastPlaid` 指向同一路径就能重新打开它做查询或追加文档，不用每次从 embedding 重建。在这份语料上它占 92 MB，而原始 float32 向量要 311.5 MB。

四个里只有它是近似的，也正是本节中唯一一处分数与穷举 MaxSim 不一致的地方。PLAID 用质心做剪枝、存量化残差，所以三个分数相对于前文的 11.9192 / 11.7591 / 11.6710 双向漂移了几个百分位。这里排序没有受影响，而这正是 PLAID 做的取舍。它的设计对象是远比这里大的语料——那种场景下扫描一切不是一个可选项。

### Qdrant

[Qdrant](https://qdrant.tech/documentation/concepts/vectors/) 需要一个服务器：`docker run -p 6333:6333 qdrant/qdrant`。客户端也有不需要服务器的本地模式（`QdrantClient(":memory:")`），但那是纯 Python 重新实现，适合尝鲜、不适合计时。

```
# pip install sentence-transformers datasets qdrant-client
from datasets import load_dataset
from qdrant_client import QdrantClient, models
from sentence_transformers import MultiVectorEncoder

dataset = load_dataset("sentence-transformers/natural-questions", split="train[:5000]")
corpus = list(dict.fromkeys(dataset["answer"]))
model = MultiVectorEncoder("lightonai/LateOn")
query = "when did richmond last play in a preliminary final"

document_embeddings = model.encode_document(corpus, batch_size=32)
query_embedding = model.encode_query(query)

client = QdrantClient("http://localhost:6333")
client.create_collection(
    collection_name="natural-questions",
    vectors_config=models.VectorParams(
        size=model.get_embedding_dimension(),
        distance=models.Distance.COSINE,
        multivector_config=models.MultiVectorConfig(
            comparator=models.MultiVectorComparator.MAX_SIM
        ),
        # MaxSim never walks the HNSW graph, so skip building one
        hnsw_config=models.HnswConfigDiff(m=0),
    ),
)

# 4,874 documents (608,414 token vectors) ingested in 26.3s
client.upload_points(
    collection_name="natural-questions",
    points=[
        models.PointStruct(id=idx, vector=embedding, payload={"text": text})
        for idx, (embedding, text) in enumerate(zip(document_embeddings, corpus))
    ],
    batch_size=64,
)

results = client.query_points(
    collection_name="natural-questions",
    query=query_embedding,
    limit=3,
    with_payload=True,
).points  # 18ms

for result in results:
    print(f"{result.score:.4f}  {result.payload['text'][:90]}")
"""
11.9192  Richmond Football Club Richmond began 2017 with 5 straight wins, a feat it had not achieve
11.7591  2017 AFL Grand Final The 2017 AFL Grand Final was an Australian rules football game contes
11.6710  Battle of Appomattox Court House The Battle of Appomattox Court House (Virginia, U.S.), fo
"""
```

`MAX_SIM` 是 Qdrant 提供的唯一比较器；`hnsw_config=HnswConfigDiff(m=0)` 是他们对后期交互字段的推荐配置，因为这些向量用于重排而不是图遍历。注意 Qdrant 官方建议把后期交互留给对几百个候选的重排，而非全集合扫描——也就是[检索再重排](https://huggingface.co/blog/multi-vector-encoder#retrieve-and-rerank)模式。在 4,874 篇文档的规模下全扫描只要 18ms 且是精确的，但这个数字外推不了。

### Weaviate

[Weaviate](https://docs.weaviate.io/weaviate/tutorials/multi-vector-embeddings) 也需要服务器：`docker run -p 8080:8080 -p 50051:50051 cr.weaviate.io/semitechnologies/weaviate:1.34.0`。多向量支持需要 1.29 或更新版本，且内嵌模式（embedded mode）在 Windows 上不可用。

```
# pip install sentence-transformers datasets weaviate-client
import weaviate
from datasets import load_dataset
from sentence_transformers import MultiVectorEncoder
from weaviate.classes.config import Configure, DataType, Property
from weaviate.classes.query import MetadataQuery

dataset = load_dataset("sentence-transformers/natural-questions", split="train[:5000]")
corpus = list(dict.fromkeys(dataset["answer"]))
model = MultiVectorEncoder("lightonai/LateOn")
query = "when did richmond last play in a preliminary final"

document_embeddings = model.encode_document(corpus, batch_size=32)
query_embedding = model.encode_query(query)

client = weaviate.connect_to_local()
collection = client.collections.create(
    "Documents",
    # self_provided turns on MaxSim late interaction
    vector_config=[Configure.MultiVectors.self_provided(name="colbert")],
    properties=[Property(name="text", data_type=DataType.TEXT)],
)

# 4,874 documents (608,414 token vectors) ingested in 41s
with collection.batch.fixed_size(batch_size=64) as batch:
    for text, embedding in zip(corpus, document_embeddings):
        batch.add_object(properties={"text": text}, vector={"colbert": embedding.tolist()})

results = collection.query.near_vector(
    near_vector=query_embedding.tolist(),
    target_vector="colbert",
    limit=3,
    return_metadata=MetadataQuery(distance=True),
)  # 17ms

for result in results.objects:
    # Weaviate reports the MaxSim score as a negated distance
    print(f"{-result.metadata.distance:.4f}  {result.properties['text'][:90]}")
"""
11.9192  Richmond Football Club Richmond began 2017 with 5 straight wins, a feat it had not achieve
11.7591  2017 AFL Grand Final The 2017 AFL Grand Final was an Australian rules football game contes
11.6710  Battle of Appomattox Court House The Battle of Appomattox Court House (Virginia, U.S.), fo
"""

client.close()
```

这里用默认配置就够了。Weaviate 的动态 `ef` 对 top-3 查询会解析为 100，而从大约 32 开始排序已经精确。这个余量来自 embedding 的性质而非 Weaviate 本身，所以值得在你自己的模型上验证，而不是假设默认值总成立。

Weaviate 还支持 MUVERA 编码，在我们的测试中它让入库快 3 倍、查询快 1.8 倍。但在这个规模上它牺牲的精度远超那点速度带来的价值——正确答案里的第三篇文档连它的前 50 都没进。

### Vespa

[Vespa](https://docs.vespa.ai/en/tensor-user-guide.html) 也跑在容器里，不过 `pyvespa` 会替你启动它，没有单独的 `docker run`。

```
# pip install sentence-transformers datasets pyvespa
from datasets import load_dataset
from sentence_transformers import MultiVectorEncoder
from vespa.deployment import VespaDocker
from vespa.package import (
    ApplicationPackage, Document, Field, FirstPhaseRanking, Function, RankProfile, Schema,
)

dataset = load_dataset("sentence-transformers/natural-questions", split="train[:5000]")
corpus = list(dict.fromkeys(dataset["answer"]))
model = MultiVectorEncoder("lightonai/LateOn")
query = "when did richmond last play in a preliminary final"

document_embeddings = model.encode_document(corpus, batch_size=32)
query_embedding = model.encode_query(query)

# "dt" is a mapped dimension over the variable token count, "x" the dense 128-dim vector
package = ApplicationPackage(
    name="colbert",
    schema=[
        Schema(
            name="doc",
            document=Document(fields=[
                Field(name="text", type="string", indexing=["summary"]),
                Field(name="colbert", type="tensor<float>(dt{}, x[128])", indexing=["attribute"]),
            ]),
            rank_profiles=[
                RankProfile(
                    name="colbert",
                    inputs=[("query(qt)", "tensor<float>(qt{}, x[128])")],
                    functions=[Function(
                        name="max_sim",  # per query token take the best document token, then sum
                        expression="sum(reduce(sum(query(qt) * attribute(colbert), x), max, dt), qt)",
                    )],
                    first_phase=FirstPhaseRanking(expression="max_sim"),
                )
            ],
        )
    ],
)
app = VespaDocker(port=8080).deploy(application_package=package)  # ~40s to boot

# Vespa reads a mixed tensor as {token index: vector}, for documents and queries alike
def to_tensor(embedding):
    return {str(token): vector for token, vector in enumerate(embedding.tolist())}

# 4,874 documents (608,414 token vectors) ingested in ~80s
app.feed_iterable(
    ({"id": str(idx), "fields": {"text": text, "colbert": to_tensor(embedding)}}
     for idx, (text, embedding) in enumerate(zip(corpus, document_embeddings))),
    schema="doc",
)

response = app.query(body={
    "yql": "select text from doc where true",
    "ranking.profile": "colbert",
    "hits": 3,
    "input.query(qt)": to_tensor(query_embedding),
})  # ~75ms warm, ~115ms on the first call

for hit in response.hits:
    print(f"{hit['relevance']:.4f}  {hit['fields']['text'][:90]}")
"""
11.9192  Richmond Football Club Richmond began 2017 with 5 straight wins, a feat it had not achieve
11.7591  2017 AFL Grand Final The 2017 AFL Grand Final was an Australian rules football game contes
11.6710  Battle of Appomattox Court House The Battle of Appomattox Court House (Virginia, U.S.), fo
"""
```

四个里 Vespa 要求的前置结构最多，因为你是在声明一条排序流水线，而不仅仅是一个索引。作为交换，你可以把 MaxSim 写成一个张量表达式，清楚看到它到底在算什么。这个版本把 MaxSim 放在 `where true` 之上的 `first-phase` 里，会给全部 4,874 篇文档打分，所以输出与穷举 MaxSim 完全一致。这刻意不是 Vespa 在大规模下的推荐做法。他们的 [ColBERT 示例应用](https://github.com/vespa-engine/sample-apps/tree/master/colbert)存的是 int8 二值化向量，并把 MaxSim 移到 `second-phase`，只重排一个更便宜的第一阶段。

要迁移到那种分阶段结构需要小心，因为 `second-phase` 默认只重排第一阶段最好的 100 个候选，而在本例中这个窗口让三篇正确文档中的两篇根本没被打分。把 `rerank-count` 提高到覆盖你的候选集可以解决，不过在这个规模下分阶段版本仍比直接全扫描更慢。

## 视觉文档检索

后期交互是视觉文档检索的最先进水平：文本查询直接与页面*图像*匹配，图表、表格、版式原样保留，没有 OCR 步骤。这正是 [ColPali](https://arxiv.org/abs/2407.01449) 家族模型做的事，那些 checkpoint 通过同一套 API 加载和运行，只需用 `revision` 钉住那个为对应模型添加 Sentence Transformers 配置的、仍处于开放状态的 pull request（完整列表见[支持的模型](https://huggingface.co/blog/multi-vector-encoder#visual-document-retrieval-models)）。图像文档可以传 URL、本地路径或 PIL 图像：

```
from sentence_transformers import MultiVectorEncoder

model = MultiVectorEncoder("vidore/colqwen2.5-v0.2")

queries = [
    "What is the variable represented on the y-axis of the graph?",
    "Total outlay is maximum in which year?",
]
images = [
    "https://huggingface.co/datasets/sentence-transformers/example-documents/resolve/main/doc1.jpg",
    "https://huggingface.co/datasets/sentence-transformers/example-documents/resolve/main/doc2.jpg",
    "https://huggingface.co/datasets/sentence-transformers/example-documents/resolve/main/doc3.jpg",
    "https://huggingface.co/datasets/sentence-transformers/example-documents/resolve/main/doc4.jpg",
]

query_embeddings = model.encode_query(queries)
document_embeddings = model.encode_document(images)
print(query_embeddings[0].shape, document_embeddings[0].shape)
# (25, 128) (755, 128)

scores = model.similarity(query_embeddings, document_embeddings)
print(scores)
# tensor([[13.8672, 12.3115, 12.1670, 11.0293],
#         [ 7.2012, 14.7207,  6.9414,  6.9746]])
```

每个 query 都召回了自己那一页（对角线），第二个 query 比第一个分离得干净得多，因为四页里只有一页是关于历年总支出的。

代码没有任何变化。底层由处理器（processor）负责视觉提示和图像 patch，MaxSim 拿 query 文本 token 对文档图像 patch 打分。一页上有许多彼此独立的区域，而这正是后期交互如此契合的场景——单个向量就得把一张图、一张表和三段文字平均成一个摘要。这种保真度同样要拿索引空间来换。上面的形状是一页 755 个 token 向量、query 才 25 个，而前文 Natural Questions 的段落平均每段约 125 个，所以对图像来说，[token 池化](https://huggingface.co/blog/multi-vector-encoder#token-pooling)比文本更值得尽早安排。

这些是 VLM，请按它们所需的内存做规划。[支持的模型一节](https://huggingface.co/blog/multi-vector-encoder#visual-document-retrieval-models)的参数表从 252M 到 8.8B，小的一端在 CPU 上还现实，几十亿参数的就不现实了。

页面图像是最常见的情形，但不是唯一的非文本模态。Sentence Transformers 接受文本、图像、音频和视频，一个 checkpoint 支持其中哪些取决于它的处理器，`model.modalities` 会报告。单个文档也可以组合模态，传一个像 `{"text": ..., "image": ...}` 这样的 dict 来代替单个值即可。[多模态 Embedding 与 Reranker 模型](https://huggingface.co/blog/multimodal-sentence-transformers)更全面地讲了 Sentence Transformers 的多模态模型，[用法文档](https://sbert.net/docs/sentence_transformer/usage/usage.html)列出了每种模态接受的具体输入格式。

## 音频检索

[vidore/colqwen-omni-v0.1](https://huggingface.co/vidore/colqwen-omni-v0.1) 基于 Qwen2.5-Omni 构建，四种模态全收。用它检索一段录音对话，和检索一页一样只要两个调用：

```
# pip install -U "sentence-transformers[audio,video]"
import torch
from datasets import Audio, load_dataset

from sentence_transformers import MultiVectorEncoder

model = MultiVectorEncoder(
```

ColQwen-Omni 完全在图文对上训练，所以它的音频检索是 zero-shot 的：它从未听过任何训练样例，整个流程里也没有转录步骤。查询说的是 `nausea`，录音里说的是 `carsickness`，它仍以明显优势从二十段里挑出了那段药房对话。

## 视频检索

视频同理，但一定要抽帧，否则它会吃掉你的 VRAM。其[发布博客](https://huggingface.co/blog/manu/colqwen-omni-omnimodal-retrieval)说得很直白：视频"非常耗内存，最适合的是短片段"：

```
import torch

from sentence_transformers import MultiVectorEncoder

model = MultiVectorEncoder(
    "vidore/colqwen-omni-v0.1",
    model_kwargs={"dtype": torch.bfloat16},
)

# Sparse, low-resolution frames: 0.5 fps rather than the full frame rate
model[0].processing_kwargs.update(
    {"video": {"max_pixels": 32 * 28 * 28, "do_sample_frames": True, "fps": 0.5}}
)

query_embeddings = model.encode_query(["How to cook Mapo Tofu?"])
document_embeddings = model.encode_document([
    "https://huggingface.co/datasets/sentence-transformers/example-documents/resolve/main/mapo_tofu.mp4",
    "https://huggingface.co/datasets/sentence-transformers/example-documents/resolve/main/zhajiang_noodle.mp4",
], batch_size=1)
print(model.similarity(query_embeddings, document_embeddings))
# tensor([[53.3100, 51.0561]])
```

如果按 1 fps、全分辨率处理，同样这两个视频会产生 8,426 和 5,137 个 token 向量、VRAM 峰值 20.8 GB；而这里的设置（0.5 fps、低分辨率）是 4,240 和 2,446 个向量、12.5 GB——模型本身就占 9.0 GB。两种方式的排序完全相同。长音频也需要同样的处理，发布博客建议切成 30 秒的 chunk，每块大约 800 个 token。

## 可解释性

因为 MaxSim 是逐 query token 最大值的求和，排序可以被精确分解：文档得分的每一个点都属于某个 query token 和某个 document token。这让你能精确回答"为什么排在这里"，而不必靠目测。

对图像文档，`sentence_transformers.multi_vector_encoder.interpretability` 会把这个分解以标准 ColPali 热力图叠加到页面上，既可沿 query 聚合成一张图，也可每个 query token 一张。对前面那张支出页面问 "How much was spent on water resources and power?"，`water` 这个 token 去了这里：

## Token 池化

如果索引体积让你头疼，最有效的旋钮是少存一些 token 向量。`HierarchicalTokenPooling` 实现了 Clavié、Chaffin 和 Adams 的 [token pooling](https://arxiv.org/abs/2409.14683v1) 技术：用 cosine 距离上的 Ward 层次聚类对每个文档的 token 向量聚类，把每个簇替换为其均值，大致保留 `1 / pool_factor` 的 token。在同一文档内，很多 token 向量彼此很接近，所以你丢掉的大多是冗余而不是信号：

```
from datasets import load_dataset

from sentence_transformers import MultiVectorEncoder
from sentence_transformers.multi_vector_encoder.modules import HierarchicalTokenPooling

dataset = load_dataset("sentence-transformers/natural-questions", split="train[:5000]")
documents = list(dict.fromkeys(dataset["answer"]))

model = MultiVectorEncoder("lightonai/LateOn")

pooling = HierarchicalTokenPooling(pool_factor=2)
document_embeddings = model.encode_document(documents, token_pooling=pooling)
```

有三个地方可以应用它，取决于你想在什么时候付出这个开销：

```
# 1. Per encode call, as above
document_embeddings = model.encode_document(documents, token_pooling=pooling)

# 2. Standalone, on embeddings you already have saved (e.g. list of [num_tokens, num_dims] tensors)
pooled = pooling.pool(document_embeddings)

# 3. Baked into the model, so every consumer of the checkpoint gets pooled documents
model.append(HierarchicalTokenPooling(pool_factor=2))
model.save_pretrained("my-pooled-colbert")
```

默认只对文档做池化，因为 query 很短，而且是不容失真的那一侧。在前文的 Natural Questions 语料上，缩减比例与 `pool_factor` 高度吻合，对全部 60.8 万个 token 向量做池化大约耗时 6 秒：

| `pool_factor` | Token 向量数 | 缩减倍数 | float32 索引 |
| --- | --- | --- | --- |
| 1（关闭） | 608,414 | 1.00x | 311.5 MB |
| 2 | 305,438 | 1.99x | 156.4 MB |
| 3 | 204,407 | 2.98x | 104.7 MB |
| 4 | 153,936 | 3.95x | 78.8 MB |

簇均值对 query token 的匹配能力不如其成员中最好的那个，簇越粗糙这一点越明显。[原始实验](https://arxiv.org/abs/2409.14683v1)在 BEIR 上测量了这个代价，发现非常小：`pool_factor=2` 时平均达到未池化检索性能的 100.6%，`pool_factor=3` 时是 99.0%。索引体积直接减半几乎不花代价，所以从 2 开始是合理的。不过在你的数据上代价多大是语料相关的，定倍数之前先用一个[评估器](https://huggingface.co/blog/multi-vector-encoder#evaluating-a-model)量一量。可运行的对比脚本是 [token_pooling.py](https://github.com/huggingface/sentence-transformers/blob/main/examples/multi_vector_encoder/compression/token_pooling.py)。

`pool_factor` 能推多高也部分取决于模型本身。LightOn 的[层次池化正则化（hierarchical pooling regularization）](https://huggingface.co/blog/lightonai/lateon-hpool-regularization)正是为此训练：塑造 embedding 空间使池化代价更低，并报告 5 倍压缩下保留 99.4% 的性能。带这个正则项的训练方法还没进 Sentence Transformers，但产出的 checkpoint 就是普通的 PyLate 模型，所以 [`lightonai/LateOn-hpool-regularized`](https://huggingface.co/lightonai/LateOn-hpool-regularized) 的加载和池化与其他模型无异。

## 加速推理

多向量模型和 Sentence Transformers 的其他成员共用同一套后端机制，所以你有 `torch`（默认）、`onnx`、`openvino` 可选，也能配合半精度、Flash Attention 和 `torch.compile`。

在 GPU 上，我们测得的最佳配置是 fp16 加 Flash Attention：吞吐是 fp32 的 2.44 倍，检索质量无可测损失。Flash Attention 对多向量模型的帮助比一般模型更大，因为文档只做截断、从不 padding 到统一长度，所以批次内序列长短差异很大，正好能被去 padding 利用：

```
from sentence_transformers import MultiVectorEncoder

model = MultiVectorEncoder(
    "lightonai/GTE-ModernColBERT-v1",
    model_kwargs={"attn_implementation": "flash_attention_2", "dtype": "float16"},
)
```

GPU

CPU

> 采用非 attend 的 query 扩展（attend=False，包括 colbert-ir/colbertv2.0 和 answerdotai/answerai-colbert-small-v1 等 Stanford-NLP checkpoint）的模型会在加载时拒绝 Flash Attention。Flash Attention 会裁掉 attention_mask=0 的位置，而那些参与 MaxSim 打分的 [MASK] 扩展 token 就永远得不到注意力更新。这些模型请用 "sdpa"。

## 评估模型

`MultiVectorNanoBEIREvaluator` 用 MaxSim 打分跑 [NanoBEIR](https://huggingface.co/collections/zeta-alpha-ai/nanobeir-66e1a0af21dfd93e620cd9f6) 套件的 13 个小型 BEIR 子集，不需要你做任何数据准备：

```
from sentence_transformers import MultiVectorEncoder
from sentence_transformers.multi_vector_encoder.evaluation import MultiVectorNanoBEIREvaluator

model = MultiVectorEncoder("lightonai/GTE-ModernColBERT-v1")
evaluator = MultiVectorNanoBEIREvaluator(batch_size=16)
results = evaluator(model)
print(f"{evaluator.primary_metric}: {results[evaluator.primary_metric]:.4f}")
```

这也让验证本文开头的那个论断变得容易。[`lightonai/LateOn`](https://huggingface.co/lightonai/LateOn) 和 [`lightonai/DenseOn`](https://huggingface.co/lightonai/DenseOn) 由 LightOn 用相同数据、相同 ModernBERT 骨干、相同 149M 参数训练，唯一区别是保留每 token 一向量还是池化成每文档一向量。把两者在全部 13 个 NanoBEIR 数据集上跑一遍，就隔离出了这个选择带来的差异：

| NanoBEIR 数据集 | LateOn（多向量，128d） | DenseOn（稠密，768d） |
| --- | --- | --- |
| MSMARCO | **0.7194** | 0.6517 |
| NQ | **0.7810** | 0.7511 |
| HotpotQA | **0.9295** | 0.8802 |
| FEVER | **0.9702** | 0.9612 |
| ClimateFEVER | **0.4887** | 0.4846 |
| DBPedia | **0.6836** | 0.6748 |
| QuoraRetrieval | **0.9795** | 0.9687 |
| Touche2020 | **0.5938** | 0.5673 |
| ArguAna | 0.5562 | **0.5660** |
| NFCorpus | **0.3949** | 0.3851 |
| SciFact | 0.7978 | **0.8057** |
| SCIDOCS | 0.4469 | **0.4484** |

## 从 PyLate 或 colpali-engine 迁移

`MultiVectorEncoder` 吸收了这两个库的建模、推理、训练和评估。所有 PyLate checkpoint 直接加载；[支持的模型](https://huggingface.co/blog/multi-vector-encoder#supported-models)列出了 colpali-engine 的 checkpoint 以及仍需要时该传的 `revision`。如果你在迁移，需要改动的调用如下：

| PyLate | Sentence Transformers |
| --- | --- |
| `pylate.models.ColBERT(model_name_or_path=...)` | `MultiVectorEncoder(...)` |
| `model.encode(..., is_query=True)` | `model.encode_query(...)` |
| `model.encode(..., is_query=False)` | `model.encode_document(...)` |
| `pylate.scores.colbert_scores` | `model.similarity` |
| `pylate.indexes.PLAID` / `pylate.retrieve.ColBERT` | 无对应物，保留 PyLate 的 PLAID 或参见[索引](https://huggingface.co/blog/multi-vector-encoder#indexing) |

| colpali-engine | Sentence Transformers |
| --- | --- |
| `ColQwen2.from_pretrained(...)` + `ColQwen2Processor` | `MultiVectorEncoder(...)` |
| `processor.process_queries(...)` + `model(**batch)` | `model.encode_query(queries)` |
| `processor.process_images(...)` + `model(**batch)` | `model.encode_document(images)` |
| `processor.score_multi_vector(qs, ds)` | `model.similarity(query_embeddings, document_embeddings)` |
| `mask_non_image_embeddings=True` | `MultiVectorMask(keep_only_token_ids=[...])` |
| `HierarchicalTokenPooler` | `HierarchicalTokenPooling` |
| `colpali_engine.interpretability` | `sentence_transformers.multi_vector_encoder.interpretability` |

值得留意的一处差异在裸（非 ColBERT）checkpoint 上：PyLate 的 `ColBERT("bert-base-uncased")` 默认套用经典配方，而 `MultiVectorEncoder("bert-base-uncased")` 搭的是一个素净的栈，把前缀、query 扩展和 skiplist 留给你显式选择。训练损失和评估器的对应物、以及数据处理上的差异，见[迁移指南](https://sbert.net/docs/migration_guide.html#migrating-from-pylate)。

所有情况下，保存的兼容都是单向的：PyLate、Stanford-NLP ColBERT 和 colpali-engine 的 checkpoint 都能加载进 `MultiVectorEncoder`，但 `MultiVectorEncoder.save_pretrained` 的输出它们都不能加载。
