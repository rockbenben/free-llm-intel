在微调 SOTA 视觉语言模型 BridgeTower 时，Habana Gaudi2 上的 [Optimum Habana v1.7](https://github.com/huggingface/optimum-habana/tree/main) 相比 A100 实现了 **2.5 倍加速**、相比 H100 实现了 **1.4 倍加速**。这一性能提升依赖于硬件加速的数据加载，以最大限度发挥设备的效能。

*这些技术适用于任何受数据加载制约的工作负载——许多类型的视觉模型常常如此。* 本文将带你了解我们在 Habana Gaudi2、Nvidia H100 与 Nvidia A100 80GB 上对比 BridgeTower 微调所采用的流程和基准，并展示在基于 transformers 的模型中启用这些特性有多简单。

## BridgeTower

近年来，[视觉语言（VL）模型](https://huggingface.co/blog/vision_language_pretraining)获得了极大的重要性，并在多种 VL 任务上占据主导地位。最常见的做法是利用单模态编码器从各自模态中提取表征，随后将这些表征融合，或输入跨模态编码器。为了高效应对 VL 表征学习中的一些性能局限与约束，[BridgeTower](https://huggingface.co/papers/2206.08657) 引入了多个*桥接层（bridge layers）*，在单模态编码器的顶层与跨模态编码器的每一层之间建立连接。这使得视觉与文本表征能够在跨模态编码器中不同语义层级之间进行有效的自底向上跨模态对齐与融合。

仅用 400 万张图像预训练（详见[下文](https://huggingface.co/blog/bridgetower#benchmark)），BridgeTower 就在多种下游视觉语言任务上取得了最先进性能。具体而言，BridgeTower 在 VQAv2 test-std 集上取得 78.73% 的准确率，在使用相同预训练数据、几乎可忽略的额外参数与计算成本的情况下，比此前的最先进模型（METER）高 1.09%。值得注意的是，进一步扩展模型后，BridgeTower 达到 81.15% 的准确率，超越了在数量级更大的数据集上预训练的模型。

## 硬件

[NVIDIA H100 Tensor Core GPU](https://www.nvidia.com/en-us/data-center/h100/) 是 Nvidia GPU 最新、最快的一代。它包含专用 Transformer Engine，可执行 fp8 混合精度运行。单卡有 80GB 显存。

[Nvidia A100 Tensor Core GPU](https://www.nvidia.com/en-us/data-center/a100/) 采用第 3 代 [Tensor Core 技术](https://www.nvidia.com/en-us/data-center/tensor-cores/)。它仍是你在大多数云服务商处能找到的最快 GPU。这里我们使用 80GB 显存版本，其内存带宽也快于 40GB 版本。

[Habana Gaudi2](https://habana.ai/products/gaudi2/) 是 Habana Labs 设计的第二代 AI 硬件加速器。单台服务器包含 8 个称为 HPU 的加速设备，每个有 96GB 内存。更详细的介绍以及如何通过 [Intel Developer Cloud](https://www.intel.com/content/www/us/en/secure/developer/devcloud/cloud-launchpad.html) 访问它，请查看[我们之前的博客](https://huggingface.co/blog/habana-gaudi-2-bloom#habana-gaudi2)。与市面上许多 AI 加速器不同，借助 [Optimum Habana](https://huggingface.co/docs/optimum/habana/index)，高级特性非常容易应用以充分发挥 Gaudi2 的潜力——用户只需 2 行改动，就能把兼容 Transformers 的脚本移植到 Gaudi 上。

## 基准测试

为对训练做基准，我们将微调一个由 866M 参数构成的 [BridgeTower Large checkpoint](https://huggingface.co/BridgeTower/bridgetower-large-itm-mlm-itc)。该 checkpoint 使用掩码语言建模、图文匹配与图文对比损失，在 [Conceptual Captions](https://huggingface.co/datasets/conceptual_captions)、[SBU Captions](https://huggingface.co/datasets/sbu_captions)、[MSCOCO Captions](https://huggingface.co/datasets/HuggingFaceM4/COCO) 和 [Visual Genome](https://huggingface.co/datasets/visual_genome) 上以英语预训练。

我们在此 checkpoint 基础上进一步用 [New Yorker Caption Contest 数据集](https://huggingface.co/datasets/jmhessel/newyorker_caption_contest) 微调——它由《纽约客》的漫画及得票最高的配文组成。

所有加速器的超参数相同。我们为每台设备使用 48 个样本的 batch size。Gaudi2 的超参数见[这里](https://huggingface.co/regisss/bridgetower-newyorker-gaudi2-8x#training-hyperparameters)，A100 见[那里](https://huggingface.co/regisss/bridgetower-newyorker-a100-8x#training-hyperparameters)。

**在处理涉及图像的数据集时，数据加载常常是瓶颈**，因为许多高开销的操作在 CPU 上计算（图像解码、图像增强），然后完整图像被发送到训练设备。理想情况下，*我们只想把原始字节发送给设备，然后在设备上执行解码和各种图像变换*。但先看看如何*轻松地*为数据加载分配更多资源以加速你的运行。

### 善用 `dataloader_num_workers`

当图像加载在 CPU 上进行时，一种快速的提速办法是为数据加载分配更多子进程。用 Transformers 的 `TrainingArguments`（或其 Optimum Habana 对应版本 `GaudiTrainingArguments`）非常容易做到：你可以使用 `dataloader_num_workers=N` 参数来设置分配给 CPU 用于数据加载的子进程数量（`N`）。

默认值是 0，意味着数据在主进程中加载。这可能不够优，因为主进程已经有很多事情要管。我们可以设为 1，让一个完全专用的子进程负责数据加载。当分配多个子进程时，每个子进程负责准备一个 batch。这意味着内存消耗会随 worker 数量增长。一个建议是设为 CPU 核心数，但这些核心未必完全空闲，所以需要你自己尝试找到最佳配置。

我们运行下面三个实验：

- 一个混合精度（*bfloat16*/*float32*）、分布在 8 台设备上的运行，数据加载与其他工作由同一进程执行（即 `dataloader_num_workers=0`）
- 一个混合精度（*bfloat16*/*float32*）、分布在 8 台设备上的运行，用 1 个专用子进程加载数据（即 `dataloader_num_workers=1`）
- 同样的运行但 `dataloader_num_workers=2`

以下是我们在 Gaudi2、H100 和 A100 上得到的吞吐量：

| Device | `dataloader_num_workers=0` | `dataloader_num_workers=1` | `dataloader_num_workers=2` |
| --- | --- | --- | --- |
| Gaudi2 HPU | 601.5 samples/s | 747.4 samples/s | 768.7 samples/s |
| H100 GPU | 336.5 samples/s | 580.1 samples/s | 602.1 samples/s |
| A100 GPU | 227.5 samples/s | 339.7 samples/s | 345.4 samples/s |

首先可以看到，在 `dataloader_num_workers=2` 时 **Gaudi2 比 H100 快 1.28 倍**，在 `dataloader_num_workers=1` 时快 1.29 倍，在 `dataloader_num_workers=0` 时快 1.79 倍。Gaudi2 也远快于上一代：**比 A100 快 2.23 倍**（`dataloader_num_workers=2`）、快 2.20 倍（`dataloader_num_workers=1`）、快 2.64 倍（`dataloader_num_workers=0`）——甚至比[我们之前报告的加速比](https://huggingface.co/blog/habana-gaudi-2-benchmark)还要好！

其次可以看到，**为数据加载分配更多资源可以带来轻松的加速**：Gaudi2 上 1.28 倍、H100 上 1.79 倍、A100 上 1.52 倍。

我们也用多个专用子进程做了数据加载实验，但所有加速器的性能都不优于 `dataloader_num_workers=2`。因此，**使用 `dataloader_num_workers>0` 通常是加速涉及图像的运行的一种好的第一步！**

Tensorboard 日志：Gaudi2 见[这里](https://huggingface.co/regisss/bridgetower-newyorker-gaudi2-8x/tensorboard)，A100 见[那里](https://huggingface.co/regisss/bridgetower-newyorker-a100-8x/tensorboard)。

### 用 Optimum Habana 实现硬件加速的数据加载

想要更快的加速，我们现在要把尽可能多的数据加载操作从 CPU 移到加速设备（Gaudi2 上的 HPU 或 A100/H100 上的 GPU）。在 Gaudi2 上，这可以通过 Habana 的 [media pipeline](https://docs.habana.ai/en/latest/Media_Pipeline/index.html) 实现。

给定一个数据集，大多数 dataloader 遵循如下流程：

- 获取数据（例如你的 JPEG 图像存储在磁盘何处）
- CPU 读取编码后的图像
- CPU 解码图像
- CPU 应用图像变换以增强图像
- 最后，图像被发送到设备（虽然这一步通常不由 dataloader 本身完成）

与其在 CPU 上完成整个流程再把可直接训练的数据发给设备，更高效的工作流是先把编码图像发给设备，然后在设备上执行图像解码与增强：

- 同上
- 同上
- 编码图像发送到设备
- 设备解码图像
- 设备应用图像变换以增强图像

这样我们就能利用设备的算力加速图像解码与变换。注意这样做时有两个坑需要提前知晓：

- 设备内存占用会上升，如果可用内存不足，你可能不得不缩小 batch size，这会削弱该方法带来的加速。
- 如果在 CPU 上做数据加载时设备已被高强度使用（100% 或接近），那么把加载移到设备上不要指望有加速，因为设备已经满负荷了。

在 Gaudi2 上我们已为你实现好这一切：Optimum Habana 的[图文对比示例](https://github.com/huggingface/optimum-habana/tree/main/examples/contrastive-image-text)现在提供了开箱即用的 media pipeline，可用于包含文本和图像的 COCO 类数据集！你只需在命令中加上 `--mediapipe_dataloader` 即可使用。

感兴趣的读者可在 Gaudi 文档[这里](https://docs.habana.ai/en/latest/Media_Pipeline/index.html)查看更底层的概述，所有支持算子的列表在[那里](https://docs.habana.ai/en/latest/Media_Pipeline/Operators.html)。

由于 `mediapipe_dataloader` 与 `dataloader_num_workers` 兼容，我们现在加上该参数重跑之前的实验：

| Device | `dataloader_num_workers=0` | `dataloader_num_workers=2` | `dataloader_num_workers=2` + `mediapipe_dataloader` |
| --- | --- | --- | --- |
| Gaudi2 HPU | 601.5 samples/s | 768.7 samples/s | 847.7 samples/s |
| H100 GPU | 336.5 samples/s | 602.1 samples/s | / |
| A100 GPU | 227.5 samples/s | 345.4 samples/s | / |

相比仅用 `dataloader_num_workers=2` 的上一次运行，我们又获得了 1.10 倍额外加速。这最后一次运行在 Gaudi2 上比基础运行快 1.41 倍——**仅仅加了 2 个开箱即用的训练参数。** 在 `dataloader_num_workers=2` 下，它还比 **H100 快 1.41 倍**、比 **A100 快 2.45 倍**！

### 复现该基准

要复现这个基准，你首先需要通过 [Intel Developer Cloud](https://www.intel.com/content/www/us/en/secure/developer/devcloud/cloud-launchpad.html) 访问 Gaudi2（更多信息见[本指南](https://huggingface.co/blog/habana-gaudi-2-benchmark#how-to-get-access-to-gaudi2)）。

然后安装最新版 Optimum Habana 并运行 `run_bridgetower.py`，脚本在[这里](https://github.com/huggingface/optimum-habana/blob/main/examples/contrastive-image-text/run_bridgetower.py)。步骤如下：

```
pip install optimum[habana]
git clone https://github.com/huggingface/optimum-habana.git
cd optimum-habana/examples/contrastive-image-text
pip install -r requirements.txt
```

运行脚本的基础命令行为：

```
python ../gaudi_spawn.py --use_mpi --world_size 8 run_bridgetower.py \
--output_dir /tmp/bridgetower-test \
--model_name_or_path BridgeTower/bridgetower-large-itm-mlm-itc \
--dataset_name jmhessel/newyorker_caption_contest --dataset_config_name matching \
--dataset_revision 3c6c4f6c0ff7e902833d3afa5f8f3875c2b036e6 \
--image_column image --caption_column image_description \
--remove_unused_columns=False \
--do_train --do_eval --do_predict \
--per_device_train_batch_size="40" --per_device_eval_batch_size="16" \
--num_train_epochs 5 \
--learning_rate="1e-5" \
--push_to_hub --report_to tensorboard --hub_model_id bridgetower\
--overwrite_output_dir \
--use_habana --use_lazy_mode --use_hpu_graphs_for_inference --gaudi_config_name Habana/clip \
--throughput_warmup_steps 3 \
--logging_steps 10
```

这对应 `--dataloader_num_workers 0` 的情况。你可以再添加 `--dataloader_num_workers N` 和 `--mediapipe_dataloader` 以测试其他配置。

要把模型和 Tensorboard 日志推送到 Hugging Face Hub，需事先登录你的账户：

```
huggingface-cli login
```

对于 A100 和 H100，你可以使用同一个 `run_bridgetower.py` 脚本，只需少量改动：

- 把 `GaudiTrainer` 和 `GaudiTrainingArguments` 替换为 Transformers 的 `Trainer` 和 `TrainingArguments`
- 删除对 `GaudiConfig`、`gaudi_config` 和 `HabanaDataloaderTrainer` 的引用
- 直接从 Transformers 导入 `set_seed`：`from transformers import set_seed`

本基准展示的结果由 Nvidia H100 Lambda 实例与 Nvidia A100 80GB GCP 实例（均为 8 设备）测得，使用 [Nvidia 的 Docker 镜像](https://docs.nvidia.com/deeplearning/frameworks/pytorch-release-notes/index.html)。

注意 `--mediapipe_dataloader` 仅兼容 Gaudi2，不适用于 A100/H100。

关于 H100 上使用 [Transformer Engine](https://docs.nvidia.com/deeplearning/transformer-engine/user-guide/index.html) 的 fp8 结果：目前没有提供，因为代码会崩溃，需要修改 Transformers 里 BridgeTower 的 modeling。待 Gaudi2 支持 fp8 后我们会重访这一对比。

## 结论

面对图像时，我们介绍了两种加速训练工作流的方案：为 dataloader 分配更多资源；直接在加速设备上而非 CPU 上解码和增强图像。我们展示了这能带来剧烈的加速——训练像 BridgeTower 这样的 SOTA 视觉语言模型时：**配备 Optimum Habana 的 Habana Gaudi2 大约比使用 Transformers 的 Nvidia H100 快 1.4 倍、比 Nvidia A100 80GB 快 2.5 倍！** 而且上手极其简单，只需提供几个额外的训练参数。
