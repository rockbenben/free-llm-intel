# 用 Core ML 和 dots.ocr 实现 SOTA OCR

作者：Christopher Fleetwood（FL33TW00D-HF）、Pedro Cuenca（pcuenq）

每一年，硬件都更强一点，每个参数的模型都更聪明一点。2025 年，在端侧运行真正有竞争力的模型比以往任何时候都可行。RedNote 的 3B 参数 OCR 模型 [dots.ocr](https://huggingface.co/rednote-hilab/dots.ocr) 在 [OmniDocBench](https://github.com/opendatalab/OmniDocBench) 上超过了 Gemini 2.5 Pro，让 OCR 成为一个真正不打折的端侧用例。对开发者来说，端侧跑模型确实诱人：不用藏 API key、零成本、不需要网络。不过，要让这些模型跑在端侧，就必须正视有限的算力和功耗预算。

这时神经网络引擎（Neural Engine）登场——Apple 的自研 AI 加速器，自 2017 年起随每一款 Apple 设备出货。它的目标就是高性能的同时极省电池。我们的一些测试发现，Neural Engine 比 CPU **省电 12 倍**、比 GPU **省电 4 倍**。

听起来很美，可惜 Neural Engine 只能通过 [Core ML](https://developer.apple.com/documentation/coreml)——Apple 的*闭源* ML 框架——访问。而且，光是把模型从 PyTorch 转成 Core ML 就有不少坑，没有现成的转换后模型、又不了解那些雷点的话，对开发者相当吃力。好在 Apple 还提供 [MLX](https://mlx-framework.org)——一个更现代、更灵活的 ML 框架，目标硬件是 GPU（不是 Neural Engine），可以与 Core ML 配合使用。

在这个三部曲系列中，我们给出一份*推理过程记录*：如何把 `dots.ocr` 转换成端侧运行，组合使用 `CoreML` 和 `MLX`。这套流程适用于很多其他模型，希望能帮想在端侧跑自己模型的开发者理清思路和所需工具。

想跟着做，克隆[这个仓库](https://github.com/FL33TW00D/dots.ocr.ne)。需要装好 `uv` 和 `hf` 才能跑 setup 命令：

```
./boostrap.sh
```

想直接跳过、用转换好的模型，可以在[这里](https://huggingface.co/FL33TW00D-HF/dots.ocr.ne)下载。

## 转换

PyTorch 转 CoreML 分两步：

- 捕获 PyTorch 执行图（通过 [`torch.jit.trace`](https://docs.pytorch.org/docs/stable/generated/torch.jit.trace.html)，或更现代的 [`torch.export`](https://docs.pytorch.org/docs/stable/export.html)）。
- 用 [`coremltools`](https://github.com/apple/coremltools) 把转换后的图编译成 `.mlpackage`。

虽然第 2 步有几个可调旋钮，但我们的大部分掌控在第 1 步——喂给 `coremltools` 的那张图。

遵循程序员的祷文[`先让它跑起来，再让它正确，最后让它快`](https://wiki.c2.com/?MakeItWorkMakeItRightMakeItFast)，我们先在 GPU、FLOAT32、静态形状下把转换跑通。有了这个基础，再降精度、尝试移到 Neural Engine。

## Dots.OCR

Dots.OCR 由两个核心组件构成：一个从零训练、基于 [NaViT 架构](https://arxiv.org/pdf/2307.06304)的 1.2B 参数视觉编码器，以及 Qwen2.5-1.5B 主干。我们用 `CoreML` 跑视觉编码器，用 `MLX` 跑 LM 主干。

## 第 0 步：理解并简化模型

要转换模型，最好先弄清结构和功能再动手。看原始视觉建模文件[这里](https://github.com/FL33TW00D/dots.ocr.ne/blob/12c57588a97584b1c95e811475791e298e04162d/modeling_dots_vision.py)，视觉编码器与 QwenVL 家族类似。和许多视觉编码器一样，`dots` 的视觉编码器按 patch 工作，这里是 `14x14` 的 patch。`dots` 视觉编码器能处理视频和图像批次。这给了我们简化机会：一次只处理单张图像。端侧应用常这么做——先转换出核心功能的模型，需要多图处理时再迭代。

开始转换时，最好从一个最小可用模型起步：砍掉一切非必需的装饰。我们的情况里，dots 的视觉编码器和 LM 主干都挂着很多种注意力实现。CoreML 有大量围绕 [`scaled_dot_product_attention` 算子](https://apple.github.io/coremltools/source/coremltools.converters.mil.mil.ops.defs.html#coremltools.converters.mil.mil.ops.defs.iOS18.transformers.scaled_dot_product_attention)的基础设施（iOS 18 引入）。我们可以删掉其他所有注意力实现，只保留简单的 `sdpa`（[不是省内存变体](https://github.com/FL33TW00D/dots.ocr.ne/commit/d51b0478aacf569146cfd6f6a7542850fe61b11c)），[commit 在这里](https://github.com/FL33TW00D/dots.ocr.ne/commit/2cde03299efb7b64c567a3c197ef4a0259768849)。

做完后，加载模型时会看到一条吓人的警告：

```
Sliding Window Attention is enabled but not implemented for `sdpa`; unexpected results may be encountered.
```

模型运行并不依赖滑动窗口注意力，可以放心继续。

## 第 1 步：一个简单的测试壳

用 `torch.jit.trace` 转 CoreML 至今仍是最成熟的路线。我们通常把它包一个简单的 harness，可以改计算单元和精度选择。

最初的 harness 见[这里](https://github.com/FL33TW00D/dots.ocr.ne/blob/master/convert.py)。对原始代码实现运行：

```
uv run convert.py --precision FLOAT32 --compute_units CPU_AND_GPU
```

我们就会撞上第一个（还有很多在后面）问题。

## 第 2 步：捉虫

模型一次就转换成功是小概率事件。通常要沿执行图一路往下 progressively 修改，直到最后一个节点。

第一个问题是这个错误：

```
ERROR - converting 'outer' op (located at: 'vision_tower/rotary_pos_emb/192'):
In op "matmul", when x and y are both non-const, their dtype need to match, but got x as int32 and y as fp32
```

好在这个信息量不少。查看 `VisionRotaryEmbedding` 层，代码是这样的：

```
def forward(self, seqlen: int) -> torch.Tensor:
    seq = torch.arange(seqlen, device=self.inv_freq.device, dtype=self.inv_freq.dtype)
    freqs = torch.outer(seq, self.inv_freq)
    return freqs
```

虽然 `torch.arange` 有 `dtype` 参数，但 `coremltools` 对 `arange` 会忽略它、永远输出 `int32`。只需在 `arange` 后加一个 cast，即可修复，[commit 在这里](https://github.com/FL33TW00D/dots.ocr.ne/commit/fb968c54d35f7331d8b36b53d69e9767daba4ad3)。

修好后重新转换，下一个问题出在 `repeat_interleave`：

```
ERROR - converting 'repeat_interleave' op (located at: 'vision_tower/204'):
Cannot add const [None]
```

这个错误信息少了些，但视觉编码器里只有一处 `repeat_interleave` 调用：

```
cu_seqlens = torch.repeat_interleave(grid_thw[:, 1] * grid_thw[:, 2], grid_thw[:, 0]).cumsum(
    dim=0,
    dtype=grid_thw.dtype if torch.jit.is_tracing() else torch.int32,
)
```

[`cu_seqlens`](https://github.com/Dao-AILab/flash-attention/issues/850) 用于 `flash_attention_2` 中变长序列的掩码，由 `grid_thw` 张量推导而来（表示 `time`、`height`、`width`）。我们只处理单张图像，这段直接删掉即可，[commit 在这里](https://github.com/FL33TW00D/dots.ocr.ne/commit/417512e522b595e5fbddb19c6c66f69db0ecca78)。

继续！这次是一个更晦涩的错误：

```
ERROR - converting '_internal_op_tensor_inplace_fill_' op (located at: 'vision_tower/0/attn/301_internal_tensor_assign_1'):
_internal_op_tensor_inplace_fill does not support dynamic index
```

这还是处理变长序列的掩码逻辑。既然只处理单张图（不是视频或图像批），其实根本不需要注意力掩码！于是可以全用 `True` 的掩码。也为 Neural Engine 转换做好准备：把布尔掩码换成全零的浮点掩码——Neural Engine 不支持 `bool` 张量，[commit 在这里](https://github.com/FL33TW00D/dots.ocr.ne/commit/9a1cd2a4d9d4d0c0c96aef5265f6bd306f1d603e)

都改完后，模型应该能顺利转成 CoreML 了！然而，当我们*运行*模型时，出现这个错误：

```
error: 'mps.reshape' op the result shape is not compatible with the input shape
```

这个 reshape 可能出现在多处！好在之前的一个警告帮我们定位问题：

```
TracerWarning: Iterating over a tensor might cause the trace to be incorrect. Passing a tensor of different shape won't change the number of iterations executed (and might lead to errors or silently give incorrect results).
  for t, h, w in grid_thw:
```

多数 ML 编译器[都**不**喜欢动态控制流](https://x.com/tenderizzation/status/1930437803097371080)。幸运的是，我们只处理单张图，可以去掉循环、直接处理这一对 `h, w`，[commit 在这里](https://github.com/FL33TW00D/dots.ocr.ne/commit/c1049e0d53b20c30a612428a84a2b6203b3273f7)。

搞定！再跑一次转换，模型成功转换并且与原 PyTorch 的数值一致：

```
Max difference: 0.006000518798828125, Mean difference: 1.100682402466191e-05
```

## 第 3 步：基准测试

模型能跑了，来评估大小和性能。好消息是模型工作正常；坏消息是它超过 5GB！端侧部署完全不可接受。要测计算耗时，可以用 XCode 自带工具：

```
open DotsOCR_FLOAT32.mlpackage
```

这会打开该模型的 XCode inspector。点 `+ Performance Report`，在所有计算设备上跑一份报告，你会看到类似的结果：

视觉编码器单次前向传播超过了 1 秒！我们还有很多活要干。
