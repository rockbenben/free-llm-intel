# 从 Hugging Face Hub 到机器人硬件：用 Strands Agents 和 LeRobot

*Strands Robots 中 LeRobot 集成的完整走查——一个代理循环，从 Hub 数据集到物理机器人；sim-to-real 数据集使用同样的磁盘格式，策略（policy）只需改一个字符串即可互换。*

你有一台机器人、[Hugging Face Hub](https://huggingface.co) 上的一文件夹演示数据，以及一个你想让它学的新任务。今天这件事需要五个互不相干的工具：一个录制新演示，一个训练，一个在仿真中测试，部署到硬件要写定制代码，如果你有多台机器人，还得再加一个来做协调。这些工具各自都能工作，但它们互相不说话。

[Strands Robots](https://github.com/strands-labs/robots) 是 AWS 的开源 SDK（[Apache 2.0](https://www.apache.org/licenses/LICENSE-2.0)），它把机器人抽象、仿真以及 [LeRobot](https://github.com/huggingface/lerobot) 技术栈封装成 AgentTool，供你组合进单个 Strands 代理。这个集成刻意做得很薄：硬件录制和校准仍由 LeRobot 自己的脚本负责，Strands AgentTool 只接管代理真正需要编排的部分。仿真工具写出的 LeRobotDataset 与 LeRobot 在硬件上写出的格式完全相同。[GR00T](https://github.com/NVIDIA/Isaac-GR00T) 和 [LerobotLocal](https://strands-labs.github.io/robots/policies/lerobot-local/) 在统一接口后面提供策略推理服务，MolmoAct2 checkpoint 走 LerobotLocal 路径运行。对等网状网络（peer mesh）把一个代理扇出到远程的多台机器人。数据集格式原样保持 LeRobot 写出的样子；代理循环就是那层粘合剂。

本文带你走过单个代理内部的五个步骤：基于 LeRobot AgentTool 构建代理、在仿真中把演示录制为 LeRobotDataset、在同一台机器人上运行策略、只改一个关键字参数就把同样的代理代码部署到物理 [SO-101](https://github.com/TheRobotStudio/SO-ARM100)，再通过 [Zenoh](https://zenoh.io) 网格在机器人舰队中广播命令。最后你可以从 GitHub 克隆可用的示例应用，在笔记本上以仿真方式运行。默认路径不需要硬件、不需要 GPU，也不需要 Hugging Face 凭证。本文的可运行配套文件位于 [`examples/lerobot/hub_to_hardware.py`](https://github.com/strands-labs/robots/blob/main/examples/lerobot/hub_to_hardware.py) 和 [`hub_to_hardware.ipynb`](https://github.com/strands-labs/robots/blob/main/examples/lerobot/hub_to_hardware.ipynb)。notebook 默认仅仿真、使用 Mock 策略。

## 你将构建什么

Strands Robots SDK 把 LeRobot 技术栈封装为 AgentTool，供你组合成一个 Strands 代理。本文中的示例代理做四件事：在仿真中录制新演示、把结果作为 LeRobotDataset 推送到 Hub、在仿真中以同一格式运行策略、只改一个关键字参数就把同样的代理代码部署到物理机器人。当你有多台机器人时，代理可以通过内置的对等网格协调整个舰队。硬件录制与校准由 LeRobot 自家的 CLI（`lerobot-record`、`lerobot-calibrate`）完成启动工作；代理从那里接手。

[![arch_hugginface](https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/23tSv83E-Y06YWhpso9AS.png)](https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/23tSv83E-Y06YWhpso9AS.png)

**图 1。*`Robot("so100")` 默认返回由 MuJoCo 支撑的仿真；`mode="real"` 返回由 LeRobot 驱动的硬件机器人。两种模式共享同一个 DatasetRecorder 和同一批策略 provider，因此仿真中采集的数据集与硬件上采集的数据集使用完全相同的磁盘 LeRobotDataset 格式。***

有两个设计选择支撑了这一切。第一，[Robot("so100")](https://strands-labs.github.io/robots/getting-started/robot-factory/) 默认返回仿真（无需硬件、没有风险），`mode="real"` 则返回由 LeRobot 驱动的硬件机器人，两种模式下的代理代码完全一致。第二，负责写 LeRobotDataset 的 DatasetRecorder 在[仿真路径](https://strands-labs.github.io/robots/simulation/overview/)与 LeRobot 自己的硬件录制之间共用，所以从 [MuJoCo](https://mujoco.org) 采集的数据集和从物理 [SO-101](https://github.com/TheRobotStudio/SO-ARM100) 采集的数据集格式相同。

整个工作流用五行 Python 概括：

```
from strands_robots import Robot
from strands import Agent

arm = Robot("so100") # mode="sim" (default - safe, no hardware)
agent = Agent(tools=[arm])
agent("Pick up the red cube")
```

接下来我们逐步拆解这次调用内部真正发生的事情。

## 前置条件

#### 最小配置（默认仿真路径）

- Python 3.12+，运行于 Linux 或 macOS（MuJoCo 后端支持 Apple Silicon）。
- 一个与 Strands 兼容、供代理推理的模型 provider。[Amazon Bedrock](https://aws.amazon.com/bedrock/)（配 AWS 凭证）、[Anthropic API](https://docs.anthropic.com)、OpenAI，或本地运行的 [Ollama](https://ollama.com)。
- 安装了 [install extras](https://strands-labs.github.io/robots/getting-started/installation/) 的 Strands Robots：`uv pip install "strands-robots[sim-mujoco,lerobot,mesh]" `

就这些。本文的示例用这三样就能在笔记本上端到端运行。

#### 进阶配置（硬件部署、真实策略、Hub 推送）

- 一个拥有写权限 Hugging Face 账户和 token，用于推送数据集和从 Hub 拉取策略 checkpoint。
- 硬件路径：一对 SO-101 follower 和 leader，或任何其他 LeRobot 支持的机器人。两台设备都需要 `~/.cache/huggingface/lerobot/calibration/` 下的校准文件。
- 本地 GR00T 推理：至少 16 GB 显存的 NVIDIA GPU 并安装 Docker。本文使用 gr00t_inference 工具的 lifecycle="full" 动作，一次调用即可完成拉镜像、下载 checkpoint 和启动容器。

## 第 1 步 - **准备示例**

安装 Strands Robots 并获取示例文件：

```
uv pip install "strands-robots[sim-mujoco,lerobot,mesh]"
git clone https://github.com/strands-labs/robots.git
cd robots
```

如果你希望代理推送数据集或从 Hub 拉取策略，请导出你的 Hugging Face token。对本文的默认仿真路径这是可选的；示例使用 Mock 策略即可端到端运行，数据集写入本地缓存，无需 Hub 访问。

```
export HF_TOKEN=hf_...
```

可运行示例位于 `strands-labs/robots` 仓库的 `examples/lerobot/hub_to_hardware.py`（Python 脚本）和 `hub_to_hardware.ipynb`（notebook），与 MuJoCo 和 LIBERO 示例放在一起。推荐使用 notebook 起步：在 [JupyterLab](https://jupyterlab.readthedocs.io) 中打开，在不连接任何硬件的情况下以仿真模式从上到下运行单元格。

## 第 2 步 - 录制演示并推送到 Hub

仿真工具以 LeRobot 在硬件上写入的相同格式[录制 LeRobotDataset](https://strands-labs.github.io/robots/recording/)，不需要硬件。`Simulation` 工具的 `start_recording` 动作走同一个 `DatasetRecorder` 类：关节状态和 action 的 parquet schema 相同，每个摄像头的 MP4 布局也相同。代理 prompt 几乎一模一样：

```
from strands import Agent
from strands_robots import Robot

robot = Robot("so100")  # mode="sim" by default
agent = Agent(tools=[robot])

agent(
    "Record a demonstration of 'pick the red cube and place it in the box' "
    "using the Mock policy provider at FPS 30. Write the dataset to "
    "my_user/cube_picking_sim and push to the Hub when done."
)
```

[![sim_scene](https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/DBe5futoSUQ9z9s4ECZ79.png)](https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/DBe5futoSUQ9z9s4ECZ79.png)

**图 2。*MuJoCo 仿真中的录制场景：SO-100 机械臂伸向地面上的红色方块，录制为 LeRobotDataset。这条默认路径不需要硬件、不需要 GPU、不需要 Hugging Face 凭证。***

刻意选择 Mock 策略的原因：它生成占位的关节动作，让整个工作流无需训练好的 checkpoint 也能端到端跑通。机器人做的是随机运动而不是真正完成抓取，录制的结构是完整的（合法的关节状态、合法的相机帧、格式良好的 LeRobotDataset episode），但这份演示本身作为训练数据没有价值。下面的第 3 步会换成 GR00T 或 LerobotLocal 以获得真实的抓取行为。要在本步就看到真实的抓方块行为，可以运行 `--policy lerobot_local --checkpoint allenai/MolmoAct2-SO100_101`（一个 [MolmoAct2 checkpoint](https://huggingface.co/allenai/MolmoAct2-SO100_101)，会从它的 config.json 自动识别并路由到 LerobotLocal 路径）；prompt、数据集格式和代理代码保持不变。

真正的证明发生在之后。LeRobot 自己的数据集加载器读取仿真录制的数据时，没有任何 Strands 专用的代码路径：

```
from lerobot.datasets.lerobot_dataset import LeRobotDataset

dataset = LeRobotDataset("my_user/cube_picking_sim")
print(dataset.features)
# {'observation.state': Sequence(...),
#  'observation.images.front': VideoFrame(...),
#  'action': Sequence(...),
#  'episode_index': Value(...), 'frame_index': Value(...), ...}
```

这个 features dict 的形状与 Hub 上任何 LeRobot 数据集完全一致：列名相同、parquet+MP4 布局相同、加载路径相同。消费硬件录制数据的训练脚本无需修改即可消费仿真录制的数据。如果你愿意，从仿真推送的数据集可以和硬件录制并存于同一个 Hub 仓库中。

*一段录制好的 LeRobotDataset episode，由录制器写出的每相机 MP4 回放而来——训练脚本读到的磁盘视频正是同一份。*

#### **在硬件上录制**

如果要在物理 SO-101 而不是仿真中录制演示，直接使用 LeRobot 的 record CLI。Strands 集成没有把这条命令包装成 AgentTool，因为 LeRobot 已经把它干得很干净：

```
lerobot-calibrate --robot.type=so101_follower --robot.id=my_follower
lerobot-calibrate --robot.type=so101_leader   --robot.id=my_leader

lerobot-record \
  --robot.type=so101_follower --robot.id=my_follower \
  --teleop.type=so101_leader  --teleop.id=my_leader \
  --dataset.repo_id=my_user/cube_picking \
  --dataset.single_task='Pick up the red cube and place it in the box' \
  --dataset.num_episodes=25 \
  --dataset.push_to_hub=true
```

这条命令推送到 Hub 的数据集与仿真录制格式相同。要在其上微调策略，运行 LeRobot 的训练 CLI（`lerobot-train`）；训练本身不在本文范围内，遵循标准 LeRobot 工作流即可。从第 3 步开始，代理对原始 checkpoint 或微调后的 checkpoint 可以互换使用。完整的 SO-101 硬件搭建、校准走查和排障，见[示例文件夹中的 README](https://github.com/strands-labs/robots/blob/main/examples/lerobot/README.md)。

## 第 3 步 - 在仿真中运行策略

数据集上了 Hub 之后，下一步是运行策略。示例使用 `Robot()` 工厂的默认仿真模式，然后挂上 `gr00t_inference`，让代理能管理推理容器：

```
from strands import Agent
from strands_robots import Robot, gr00t_inference

robot = Robot("so100")  # mode="sim" by default
agent = Agent(tools=[robot, gr00t_inference])

agent(
    "Start GR00T inference on port 5555 with the cube-picking checkpoint "
    "from my_user/cube-picker. Then ask the robot to pick up the red cube."
)
```

在底层，代理先执行 `gr00t_inference(action="lifecycle", lifecycle="full", ...)` 来拉取 [GR00T 容器镜像](https://strands-labs.github.io/robots/policies/groot/)、从 Hub 下载 checkpoint 并启动推理服务。然后以 `policy_provider="groot"` 在仿真机器人上执行 `run_policy` 动作，在 `policy_config` dict 里传入 GR00T 服务的 host 和 port（容器在 5555 端口可达）。仿真按策略的 action chunk 步进，结果渲染可通过 `Simulation.render` 查看。

[![sim_grasp](https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/70ZHVAM2CTkP0_kjNy08U.png)](https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/70ZHVAM2CTkP0_kjNy08U.png)

**图 3。*换上训练好的策略（GR00T 或 MolmoAct2 checkpoint）后，代理驱动 SO-100 在仿真中抓起红色方块——这正是 Mock 策略所模拟的行为位置。***

偏好进程内推理（无容器、无 ZeroMQ（ZMQ））的开发者，可以把 `gr00t_inference` 换成从 Hub 仓库加载的 `LerobotLocalPolicy` 实例。该 provider 会把 `lerobot/` 组织下的任何 model ID 路由到进程内路径：

```
from strands_robots.policies import create_policy
policy = create_policy("lerobot/act_aloha_sim_transfer_cube_human")
```

`LerobotLocalPolicy` 支持 [ACT](https://tonyzhaozh.github.io/aloha/)、[Diffusion Policy](https://diffusion-policy.cs.columbia.edu)、[SmolVLA](https://huggingface.co/blog/smolvla)、[π0](https://www.pi.website/blog/pi0) 和 [π0.5](https://www.pi.website/blog/pi05)——凡是 LeRobot 自己的策略注册表能从 `config.json` 解析出来的模型都行。自带 `rtc_config` 的 flow-matching 策略（π0、SmolVLA）会自动启用 [Real-Time Chunking](https://www.pi.website/research/real_time_chunking)。

NVIDIA 新近发布的 [Cosmos 3](https://huggingface.co/nvidia/Cosmos3-Nano) 也作为策略 provider 提供，接口完全相同，因此无论指向哪个 provider，代理代码都不用变。

*注意：LerobotLocalPolicy 以 trust_remote_code=True 加载 Hugging Face 模型。请设置* `STRANDS_TRUST_REMOTE_CODE=1` *来选择启用，并且只加载你信任的组织的 checkpoint。*

## 第 4 步 - **把策略部署到物理硬件**

这段代码与第 3 步相同，只改了一个关键字参数。`Robot` 工厂返回由 LeRobot 的 `make_robot_from_config` 驱动的硬件机器人：

```
robot = Robot(
    "so100",
    mode="real",
    port="/dev/ttyACM0",
    data_config="so100_dualcam",
    cameras={
        "front": {"type": "opencv", "index_or_path": "/dev/video0", "fps": 30},
        "wrist": {"type": "opencv", "index_or_path": "/dev/video2", "fps": 30},
    },
)
agent = Agent(tools=[robot, gr00t_inference])

agent(
    "Start GR00T inference on port 5555 with the cube-picking checkpoint "
    "from my_user/cube-picker. Then ask the robot to pick up the red cube."
)
```

同样的代理 prompt 现在跑在真实的机械臂上。硬件路径使用 LeRobot 的机器人抽象来下发关节命令和读取相机，5555 端口可达的 GR00T 容器负责生成 action chunk。

在对你的 SO-101 运行之前，follower 和 leader 都必须已完成校准。对每台设备运行一次 LeRobot 的校准命令（`lerobot-calibrate`）；校准文件落在 ~/.cache/huggingface/lerobot/calibration/ 下，任何触碰硬件的 Strands 代码路径都从那里读取。若缺少校准，代理会把 LeRobot 驱动层的错误原样呈现出来。

## 第 5 步 - 用网格协调多台机器人

到目前为止我们一次只驱动一台机器人。[网格（mesh）](https://strands-labs.github.io/robots/mesh/)是 Strands Robots 处理多台机器人的方式。想象这些场景：你桌上的 leader 臂遥操作另一个房间里的 follower 臂；五台 SO-101 并行执行同一个仓库任务；或者人形机器人与移动底座协同。这些都是网格模式。网格构建在 Zenoh 这一开源点对点协议之上，你不用管理 IP 地址、不用写发现代码、也不用挑 broker；新机器人一上线就出现在网格里，代理可以同时与所有机器人对话。

每个 `Robot()` 和每个 `Simulation()` 都会自动加入 Zenoh 对等网格。`robot_mesh` 工具给了代理一套舰队操作的词汇：发现、结构化命令、广播和急停：

```
agent = Agent(tools=[robot_mesh])

agent(
    "List every robot and simulation on the mesh. "
    "Then send 'go to home pose' to each one in parallel."
)
```

代理先调用 `robot_mesh(action="peers")` 枚举本地与已发现的 peer，再调用 `robot_mesh(action="broadcast", ...)` 把结构化命令带超时地发送给每个 peer。加上 `[mesh-iot]` extra 可以把这些流量路由到 AWS IoT Core，用于跨网络的舰队。项目文档中 `robot_mesh` 工具的动作参考覆盖了完整词汇表：subscribe、watch、inbox 以及结构化的点对点命令。

默认情况下，每个会驱动物理动作的网格动作在执行前都会暂停，等待人工审批中断：舰队级广播和 emergency_stop，以及针对单 peer 的 tell、send 和 stop。你可以用 STRANDS_MESH_HITL_ACTIONS 环境变量调整这个集合（设为 all、none 或逗号分隔的子集）。第一次运行此示例时，你会在终端看到 robot_mesh-broadcast-approval 提示；输入 y（或 yes / approve）授权广播。审批独立于 LLM 的 tool 参数送达，因此试图把审批标记塞进命令体的 prompt 注入无法绕过这道闸。

传输层可以扩展而无需改动代理代码。内置的 Zenoh 网格是自动回退方案：在局域网内，Zenoh 组播无需 broker 即可完成 peer 发现；加上 [mesh-iot] extra 后流量经 [AWS IoT Core](https://aws.amazon.com/iot-core/)（MQTT5 + mTLS）路由到云端舰队；还有一个 BridgeTransport 在一个 API 后面把局域网和云端扇接在一起（用 STRANDS_MESH_BACKEND=bridge 选择）。

对于生产舰队，与 Arm 合作开发的设备感知网络层 Device Connect 负责发现、在线状态、结构化 RPC、事件路由和安全。`robot_mesh` 工具在 Device Connect 可用时经由它分发，否则回退到内置 Zenoh 网格，因此本文的代理代码在两种方式下都不变。部署与当前可用性见 [Device Connect 文档](https://strands-labs.github.io/robots/device-connect/)。

## 用示例应用试一试

完整示例在 GitHub 的 [strands-labs/robots](https://github.com/strands-labs/robots) 仓库 examples/lerobot/ 文件夹里。它把全部五个步骤打包成一个 CLI 脚本（hub_to_hardware.py）和一个 notebook（hub_to_hardware.ipynb）。CLI 默认使用 Mock 策略在仿真中端到端运行，不需要 GPU、Docker 或 Hugging Face 凭证。

```
uv pip install "strands-robots[sim-mujoco,lerobot,mesh]"
git clone https://github.com/strands-labs/robots.git
cd robots

export STRANDS_MESH_LOCAL_DEV=1

python examples/lerobot/hub_to_hardware.py
```

录制的数据集会出现在 `~/.cache/huggingface/lerobot/local/strands-cube-pick/`。如果想推送到 Hugging Face Hub 而不是留在本地，先导出带写权限的 HF_TOKEN，然后加 `--hf-user <your-user>`。要在第 3 步获得真实抓取行为，传 `--policy groot --checkpoint <hf_repo>`（需要 Docker + NVIDIA GPU）或 `--policy lerobot_local --checkpoint <hf_repo>`（需要 GPU 和 `STRANDS_TRUST_REMOTE_CODE=1`）。

notebook（examples/lerobot/hub_to_hardware.ipynb）逐单元格走一遍同样的工作流，每一步之间有讲解。在 JupyterLab 中打开，以仿真模式从上到下运行即可。

## 安全考量

这套配置中展示的代码片段只是用 Strands Robots 搭配 HuggingFace 搭建的"hello world"示例。对于更严肃、面向生产的使用场景，用户需要了解几个重要事项：

#### Prompt 注入

向代理供给不可信数据可能导致 prompt 注入——不可信的上下文被当成 LLM 指令执行。考虑到这些机器人会在物理空间里执行动作，这是必须跟踪的重要风险。要缓解这一行为，开发者应小心地只向机器人喂来自可信来源的数据。如果无法保证所有输入数据可信，开发者应限制代理可用的工具，防止机器人执行安全关键动作。

#### 机器人网格的认证行为

本文代码片段中使用的 `STRANDS_MESH_LOCAL_DEV=1` 设置会以无认证、无访问控制的模式初始化机器人网格。这意味着同网络上的任何设备都能向机器人舰队下发命令。这对可信的开发环境可以接受，但不适合不可信网络或生产环境。这些场景必须使用 `STRANDS_MESH_AUTH_MODE=mtls`。

#### **舰队级动作的操作员审批**

`robot_mesh` 工具中会驱动物理动作的操作会影响网络上的 peer：broadcast 和 emergency_stop 触达所有 peer，tell、send 和 stop 触达单个目标 peer。为防止代理自主（或在 prompt 注入下）发出这些命令，这五个动作默认都被 human-in-the-loop 中断拦下。当代理调用受闸门控制的动作时，Strands 运行时暂停代理循环，并在 LLM 的 tool 参数之外请操作员审批。你可以用 STRANDS_MESH_HITL_ACTIONS 环境变量调整受控集合（all、none 或逗号分隔子集）。与中断并行的还有逐动作限流、命令校验和审计追踪。在代理循环之外（裸脚本或单元测试），受控动作会 fail closed（直接失败）。

## 清理

前面的工作流会启动 GR00T 容器、在硬件上打开串口、并写出本地数据集缓存。要让环境回到干净状态：

- **停止 GR00T 推理容器：** `agent.tool.gr00t_inference(action="stop", port=5555)`，或用 `lifecycle="teardown"` 一并删除容器。
- **释放串口：** 如果你跑过硬件路径，断开 SO-101 的 follower 和 leader。
- **可选：删除本地数据集缓存：** 录制的数据集位于 `~/.cache/huggingface/lerobot/<repo_id>`。已推送到 Hub 的数据集不受影响。

## 整体如何咬合

这套集成的核心设计选择是：Strands Robots 不重新实现 LeRobot 已经提供的东西。硬件抽象、校准和数据集格式都留在上游。Strands 增加的是让它们可以通过自然语言组合使用的 AgentTool 接口。

由此带来两个结果。对用户而言，Hub 上的每个数据集都是代理可以扩展、基于其微调、直接部署的资产，不需要任何转换步骤。对开发者而言，仿真数据与硬件数据共享同一个文件格式，为其中一种编写的训练脚本可以原样消费另一种。仿真与真实之间的界限，从此变成部署细节，而不再是架构鸿沟。
