语言模型可以做很多事情。他们编写、总结、翻译和调用工具。但它们只是机器学习功能的一小部分。

假设客户致电您的支持热线。首先，您想知道他们说了什么（语音识别）。然后，您要决定将它们发送到哪里（决策）。您“可以”将两者都交给语言模型，但是为每种语言构建的模型都更好、更快且更便宜。

在我们的 [AnyLanguageModel 1.0 回顾](https://huggingface.co/blog/anylanguagemodel-1-0) 中，我们回顾了 Swift 中本地和托管模型的一年。随着 AnyLanguageModel 和 swift-huggingface 现在发布 1.x 版本，我们正在将相同的方法扩展到语音和决策：熟悉的 Swift API 以及模型选择。

今天我们宣布推出两个套餐：

- [AnySpeechRecognizer](https://github.com/mattt/AnySpeechRecognizer) 实现了 Apple 新的语音转文本 API，并可选择识别引擎，包括在 Core ML 上本地运行的 NVIDIA 的 Parakeet 和阿里巴巴的 Qwen3-ASR，并添加了说话人分类功能以跟踪谁在何时说话。
- [AnyDecisionModel](https://github.com/mattt/AnyDecisionModel) 通过输入结果和概率回答是或否、多项选择和评级量表问题。它使用设备上的 MLX、Core AI 或 llama.cpp 模型，或者来自 Jev 或 Ollama 的决策模型，根据模型的概率得出每个答案，而不是生成文本。

这两个包都可以从 Hugging Face Hub 下载开放模型并在设备上运行。

## AnySpeechRecognizer

计算机转录语音已有几十年的历史，在过去的几年里，它们在这方面做得非常好。苹果平台已经有一个API。 macOS 26 和 iOS 26 引入了 Apple 新的语音转文本 API“SpeechAnalyzer”。您可以将“SpeechTranscriber”和“SpeechDetector”等模块添加到分析器中，为其提供一个文件或音频缓冲区流，并在异步序列到达时读取结果。 `AssetInventory` 安装模型，因此您的应用程序决定何时进行下载。

它是一个设计良好的 API，但其背后唯一的引擎是 Apple 的。 AnySpeechRecognizer 保留 API 并让您选择引擎：
```
- import Speech
+ import AnySpeechRecognizer
```
该包镜像了“SpeechAnalyzer”、“SpeechTranscriber”、“DictationTranscriber”、“SpeechDetector”和“AssetInventory”，并以 Apple 的语音框架作为默认引擎。如果您的代码使用该共享 API，则更改导入就足够了。要使用 Parakeet，只需更改创建转录器的方式：
```
let transcriber = SpeechTranscriber(
    model: ParakeetSpeechModel(variant: .v3),
    transcriptionOptions: [],
    reportingOptions: [.volatileResults],
    attributeOptions: [.audioTimeRange]
)
```
安装资产、运行分析器和读取结果的步骤保持不变。 [README](https://github.com/mattt/AnySpeechRecognizer#transcribe-a-file) 有一个完整的示例，并[列出了 Apple 框架的差异](https://github.com/mattt/AnySpeechRecognizer#differences-from-apples-speech-framework)。

### 认识模特

**Parakeet v3** 是 NVIDIA 的 [Parakeet TDT 0.6B v3](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3)。它是一种多语言程序：它可以识别 25 种欧洲语言，并确定它听到的是哪一种语言，因此您无需通过区域设置。

**Parakeet Ultra** 是 Moondream 的 [经过训练的 v3](https://huggingface.co/moondream/parakeet-ultra)。在我们的大多数测量中它都更加准确。

**Parakeet Unified** 是 NVIDIA 的 [仅英文版 Parakeet](https://huggingface.co/nvidia/parakeet-unified-en-0.6b)。

所有三个 Parakeets 都在该包自己的 Core ML 运行时上运行，该运行时支持文件和实时输入、易失性结果、单词计时和单词置信度。

**Qwen3-ASR** 是阿里巴巴的语音模型，大小为 [0.6B](https://huggingface.co/Qwen/Qwen3-ASR-0.6B-hf) 和 [1.7B](https://huggingface.co/Qwen/Qwen3-ASR-1.7B-hf)。它可以识别 30 种语言和 22 种中国方言，包括普通话、粤语、日语和韩语，而 Parakeet 不涵盖这些内容。它会自动检测语言，或者您可以设置一种语言：
```
let transcriber = SpeechTranscriber(
    model: QwenSpeechModel(variant: .large, language: Locale.Language(identifier: "yue")),
    transcriptionOptions: [],
    reportingOptions: [],
    attributeOptions: []
)
```
Qwen3-ASR 在长达 40 秒的时间内为每个片段给出一个最终结果，没有不稳定的结果、单词计时或置信度。它在 GPU 上运行，速度比 Parakeet 慢，因此它比实时输入更适合转录文件。

要添加另一个引擎，请为其配置实现“SpeechRecognitionModel”，并为一个模块的会话实现“SpeechRecognitionExecutor”。自述文件包括一个[小型提供程序](https://github.com/mattt/AnySpeechRecognizer#custom-providers)，它报告占位符文本以帮助您入门。

每个存储库都会记录其源检查点和每个文件的校验和，并且包将其固定到固定修订版。 Parakeet 存储库添加了一个用于实时输入的 8 秒编码器，这将实时分析时间减少了约三分之一，但代价是字错误率稍高。该存储库还具有转换工作流程，其中大部分遵循 FluidInference 的 [mobius](https://github.com/FluidInference/mobius) 脚本，并根据原始模型检查每个转换。

仅当您的应用程序要求时才会进行下载：每个 Parakeet 大约 600 MB，加上实时编码器大约 590 MB，Qwen3-ASR 0.9 到 2.4 GB，Sortformer 大约 250 MB。文件位于标准 Hugging Face 缓存中，因此沙箱外的 Mac 应用程序可与 Python 和其他 Hugging Face 工具共享它们。

### 说话人分类

当您转录对话时，您通常想知道谁说了什么。这就是说话人分类，Apple 的语音框架没有相应的模块，因此 AnySpeechRecognizer 添加了一个模块。 `SpeakerDiarizer` 在 Core ML 上与 Apple 或 Parakeet 转录器一起在同一时间线上运行 NVIDIA 的 [Streaming Sortformer](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2)：
```
let diarizer = SpeakerDiarizer(model: SortformerDiarizationModel())
if let request = try await AssetInventory.assetInstallationRequest(
    supporting: [transcriber, diarizer]
) {
    try await request.downloadAndInstall()
}
let analyzer = SpeechAnalyzer(modules: [transcriber, diarizer])
```
日记记录器最多可跟踪四个发言者，即使他们互相交谈也是如此。 “SpeakerTimeline”收集其结果并将每个定时单词归因于演讲者，因此您可以按演讲者轮流打印文字记录。就像 AnyLanguageModel 中的图像支持一样，这超出了 Apple API 目前提供的范围。

分类器默认使用 Sortformer v2。您还可以选择 [v2.1](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2.1)，NVIDIA 使用更多会议数据对其进行训练，并且在我们的测量中，它在会议上也更加准确。

### 效果如何？

我们在装有 macOS 27.0.1 的 M4 Max Mac Studio 上使用“hear”命令行工具对该包进行了测量。以下是 LibriSpeech 文件中 3 到 8 分钟的单词错误率：

|转录员 |测试清洁 |测试其他|
| ---| ---| ---|
| Parakeet v3，文件 | 1.55% | 2.78% |
| Parakeet v3，实时 | 4.73% | 4.29% |
| Parakeet Ultra，文件 | 1.66% | 2.55% |
| Parakeet Ultra，直播 | 2.65% | 3.28% |
|鹦鹉统一，文件 | 1.43% | 2.19% |
| Parakeet Unified，实时 | 1.45% | 2.42% |
| Apple 的转录器、文件 | 2.12% | 3.97% |

Core ML 编译模型后，Parakeet 会在大约 20 到 40 秒的时间内从文件转录一个小时的音频，或者大约 1.5 到 2.5 分钟的实时音频，并使用大约 100 MB 的内存。 Qwen3-ASR 速度慢得多，并且需要几 GB 内存。会议对每个人来说都很困难：在 AMI 录音中，人们互相交谈，我们测试的每个引擎的单词错误率都超过 23%。

这些数字来自一台机器和一些数据集，因此请使用您自己的硬件和音频进行测量。 “hear evaluate”适用于您自己的文件，并且存储库的“natural-speech-eval.py”工具[重现这些测量结果](https://github.com/mattt/AnySpeechRecognizer#accuracy-and-performance)。到目前为止，我们仅在 macOS 27 上进行了测试，尚未在 iPhone 上进行测试。

接下来，我们希望添加更多引擎，包括 macOS 27 和 iOS 27 上的 Core AI。

## 任何决策模型

AnyDecisionModel 则是另一回事。确切地说，没有可映射的苹果框架，而且决策模型也不是什么新鲜事。

> 只有来自法国Décision地区的才是决策模型；
> 否则，它就是闪闪发光的零样本分类。

新鲜的是名字、大量的炒作以及一系列经过训练来做出决策的模型。我们认为这就是事情的发展方向，因此我们需要一个为他们做好准备的 Swift API。

应用程序经常要求语言模型来做出决定。 *这条消息紧急吗？* *哪个团队应该处理这张票？* *这个客户有多沮丧？* 通常的方法是提示语言模型并解析它生成的文本。这给了你一个答案，但没有显示它分配给替代方案的概率。

Swift 中的决策如下所示：
```
import AnyDecisionModel

enum Department: String, Choosable {
    case billing, technical, sales
}

let ticket = "I was charged twice for my order, and now the app logs me out when I try to ask for a refund."

let model = MLXDecisionModel(modelID: "mlx-community/Qwen3-4B-Instruct-2507-4bit")
let session = DecisionSession(model: model, state: .text(ticket))

let urgent = try await session.probability(of: "Does this convey urgency?")
let team = try await session.choice("Which team?", from: Department.self)
let anger = try await session.score(
    "How frustrated?",
    levels: ["Calm", "Frustrated", "Very angry"]
)
```
“紧急”是“双倍”。 `team` 是一个 `Choice<Department>`，包含所选案例、每个选项的概率和置信度值。 “anger”是一个“Score”，包含预期级别、每个级别的概率和置信度值。因为“Department”符合“Choosable”，所以“team.value”是一个可以在详尽的“switch”中使用的“Department”。

如果您使用过 Foundation Models 或 AnyLanguageModel，模型和会话模式看起来会很熟悉。 “DecisionSession”保存一个状态，可以是文本或 JSON，每个问题都与该状态有关。问题是独立的：答案永远不会成为后面问题的输入。要同时提出几个问题，请将它们作为批处理传递给“decide(_:)”。

对于每个问题，MLX 后端都会为每个允许的答案构建一个带有单标记标签的提示，然后从一次前向传递中读取每个标签的概率。

### 尝试一下：表情符号磁铁

Emoji Magnet 是一款 macOS 应用，在一堆 343 个表情符号上方有一个文本字段。输入一个短语，例如“你穿的东西”，匹配的表情符号就会从一堆中出现。将其细化为“冬天穿的衣服”，不再匹配的表情符号会回退。

该应用程序没有内置的关键字规则；模型在推理时决定一切。当您暂停打字时，它会针对每个表情符号向模型询问一个是或否问题，例如：
```
Statement: a heavy winter coat fits the description "things you wear". Is this statement true?
```
会话的状态保存该短语。上面的演示使用托管的 Jev 后端，它在一个请求中回答所有 343 个问题，因此表情符号在每个短语大约半秒内稳定下来。如果没有“TYPESAFE_AI_API_KEY”，该应用程序将在具有 MLX 后端的 Mac 上运行 Qwen3 4B。该后端使用前缀缓存来评估状态一次，然后每次前向传递回答 16 个问题。在 M4 Max 上，模型加载后 16 个一组大约需要 0.45 秒。完整浏览全部 343 个表情符号大约需要 10 秒，每组的结果一到达就会显示。

表情符号磁铁位于 [AnyDecisionModel-Examples](https://github.com/mattt/AnyDecisionModel-Examples) 存储库中。

### 决策负责人和 Clef

读取下一个标记的概率适用于通用语言模型，但这些模型没有经过训练来做出决策。 Cloudflare 的 [Clef](https://huggingface.co/Cloudflare/clef) 模型是一种较新方法的示例：一种具有训练有素的决策头的模型，可将键入问题的状态和模式转化为决策，在一次前向传递中返回问题中所有允许选项的概率。 [Clef-Flash](https://huggingface.co/Cloudflare/clef-flash) 是 9B 变体。

AnyDecisionModel 在带有 MLX 的 Mac 上运行 Clef-Flash：
```
let model = MLXHeadDecisionModel(
    modelID: "mlx-community/clef-flash-4bit",
    head: .jointSchema
)
```
您使用相同的会话和问题，但“MLXHeadDecisionModel”从 Clef 训练有素的决策头读取每个决策，而不是从下一个令牌概率读取。 [4位模型](https://huggingface.co/mlx-community/clef-flash-4bit)下载量为6.2 GB，其模型卡建议Mac至少具有16 GB内存。 Clef 可以读取图像和视频，但此后端仅接受文本和 JSON 状态。

### 校准和检查概率

语言模型的原始概率通常过于自信。本地后端接受“校准”，它将温度应用于每个答案，并对是或否答案应用偏差。使用单独的数据集来拟合校准并评估结果。

语言模型也可能因为某个选项在列表中的位置而青睐它。在 MLX、Core AI 和 llama.cpp 下一个令牌后端上，打开“rotationDebiasing”，为选项的每次轮换询问一次选择问题并平均概率。每轮转需要一次即时评估。

每个局部选择和分数还包括基于其概率熵的置信值。它衡量的是概率的集中程度，而不是答案是否正确，因此在选择阈值之前请检查您自己的数据的错误率。下一个令牌后端的诊断报告模型分配给允许答案的概率有多大。较低的值意味着它将大部分概率分配到其他地方。

### 后端

AnyDecisionModel 有六个后端：

- **MLX** 使用 [mlx-swift-lm](https://github.com/ml-explore/mlx-swift-lm) 在 Apple 芯片上运行小型语言模型，并从 Hub 下载它。
- **MLX 决策头** 使用自己训练有素的决策头运行模型，例如 Clef。
- **Core AI** 在 macOS 27 和 iOS 27 上与具有 Core AI 模型的 MLX 执行相同的操作。
- **llama.cpp** 通过 [llama.swift](https://github.com/mattt/llama.swift) 从本地 GGUF 模型读取决策。
- **Jev** 通过 [System One API](https://docs.typesafe.ai/api/system-one) 或任何实现它的服务器（例如 [Kev](https://github.com/jaredpalmer/kev)）调用 TypeSafe 的 Jev。
- **Ollama** 在本地 Ollama 服务器或 Ollama 云中调用系统一决策模型。它需要 Ollama 0.35.0 或更高版本，或者云模型需要 0.40.5 或更高版本。

下一个令牌后端标签回答“是”和“否”，A 到 Z，或 0 到 9，因此一个选择最多可以有 26 个选项，分数最多为 10 个级别。决策负责人没有这样的限制。

与 AnyLanguageModel 一样，该包使用 Swift 包特征。没有特征，它就没有第三方依赖项。您可以获得核心类型以及 Jev 和 Ollama 后端，它们也构建在 Linux 上。为本地后端启用“MLX”、“CoreAI”或“Llama”特征。

## 开始吧

这两个软件包都需要 Swift 6.2 或更高版本以及 macOS 26 或 iOS 26 或更高版本。 Parakeet 和 Sortformer 运行时以及 MLX 后端需要 Apple 芯片。 AnyDecisionModel 的 MLX 构建任务使用 Xcode 的 Swift 6.4 或更高版本以及 Metal 工具链；核心 AI 需要 Xcode 27 和 OS 27 运行时。

将包添加到您的 `Package.swift` 中：
```
dependencies: [
    .package(url: "https://github.com/mattt/AnySpeechRecognizer", from: "0.1.0"),
    .package(
        url: "https://github.com/mattt/AnyDecisionModel",
```

目前，AnyDecisionModel 的“CoreAI”特征无法与 AnySpeechRecognizer 结合使用，因为 coreai-kit 0.7.3 要求 swift-huggingface 低于 1.0，而 AnySpeechRecognizer 需要 1.x。

每个自述文件都有更多有关需求和后端的示例和详细信息。 AnySpeechRecognizer 还包括一个命令行工具“hear”，它可以转录本地文件、标记说话者并评估结果。每个“hear”命令都需要“--backend apple”、“--backend parakeet”或“--backend qwen”；在分析之前使用相同的后端和模型选项运行“hearprepare”以安装所需的资产。

在您的应用程序中尝试它们，并告诉我们哪些有效，哪些无效。这两个存储库都欢迎提出问题和拉取请求。
