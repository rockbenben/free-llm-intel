语言模型能做的事情很多。它们写作、总结、翻译、调用工具。但它们只是机器学习所能做的一小部分。

假设一位客户打来你的支持热线。首先，你想知道他说了什么（语音识别）。然后，你想决定把他转给谁（决策）。你*可以*把这两件事都交给语言模型，但每个任务都有专门为它构建的模型——更好、更快、也更便宜。

在我们的 [AnyLanguageModel 1.0 回顾](https://huggingface.co/blog/anylanguagemodel-1-0)中，我们盘点了一年以来的本地与托管模型在 Swift 上的发展。随着 AnyLanguageModel 和 swift-huggingface 都进入 1.x 版本，我们把同样的思路扩展到语音和决策：熟悉的 Swift API，外加可选择的模型。

今天我们发布两个包：

- [AnySpeechRecognizer](https://github.com/mattt/AnySpeechRecognizer) 用可选择的识别引擎实现了 Apple 新的语音转文本 API，包括在 Core ML 上本地运行的 NVIDIA Parakeet 和 Alibaba 的 Qwen3-ASR，并新增说话人分离来追踪谁在什么时候说话。
- [AnyDecisionModel](https://github.com/mattt/AnyDecisionModel) 用带类型的结果和概率回答是/否、多选和评分量表问题。它不生成文本，而是直接从模型的概率推出每个答案——可以在你的设备上用 MLX、Core AI 或 llama.cpp 跑模型，也可以使用 Jev 或 Ollama 的决策模型。

两个包都可以从 Hugging Face Hub 下载开放模型并在设备端运行。

## AnySpeechRecognizer

计算机转录语音已经有几十年历史，而在过去几年里，它们把这件事做得非常好。Apple 平台本来就有相应的 API。macOS 26 和 iOS 26 引入了 `SpeechAnalyzer`，这是 Apple 新的语音转文本 API。你往分析器里添加 `SpeechTranscriber`、`SpeechDetector` 这样的模块，给它一个文件或一串音频缓冲区组成的流，结果会以异步序列的形式随到随读。模型由 `AssetInventory` 安装，所以下载何时发生由你的 app 决定。

这是一套设计得很好的 API，但它背后的引擎只有 Apple 一家。AnySpeechRecognizer 保留这套 API，让你可以选择引擎：

```
- import Speech
+ import AnySpeechRecognizer
```

这个包复刻了 `SpeechAnalyzer`、`SpeechTranscriber`、`DictationTranscriber`、`SpeechDetector` 和 `AssetInventory`，默认引擎是 Apple 的 Speech framework。如果你的代码用的是这套共享 API，改一下 import 就够了。想改用 Parakeet，只需改变创建 transcriber 的方式：

```
let transcriber = SpeechTranscriber(
    model: ParakeetSpeechModel(variant: .v3),
    transcriptionOptions: [],
    reportingOptions: [.volatileResults],
    attributeOptions: [.audioTimeRange]
)
```

安装资产、运行分析器、读取结果的步骤保持不变。[README](https://github.com/mattt/AnySpeechRecognizer#transcribe-a-file) 里有一个完整示例，并[列出了与 Apple framework 的差异](https://github.com/mattt/AnySpeechRecognizer#differences-from-apples-speech-framework)。

### 认识这些模型

**Parakeet v3** 是 NVIDIA 的 [Parakeet TDT 0.6B v3](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3)。它是多语型的：能识别 25 种欧洲语言，并自己判断正在听的是哪一种，所以你不用传入 locale。

**Parakeet Ultra** 是 Moondream 对 v3 的[后训练版本](https://huggingface.co/moondream/parakeet-ultra)。在我们的大部分测量中，它更准。

**Parakeet Unified** 是 NVIDIA 的[仅支持英语的 Parakeet](https://huggingface.co/nvidia/parakeet-unified-en-0.6b)。

这三个 Parakeet 都运行在这个包自有的 Core ML 运行时上，该运行时支持文件与实时输入、易变结果、词级时间戳和词级置信度。

**Qwen3-ASR** 是 Alibaba 的语音模型，有 [0.6B](https://huggingface.co/Qwen/Qwen3-ASR-0.6B-hf) 和 [1.7B](https://huggingface.co/Qwen/Qwen3-ASR-1.7B-hf) 两个尺寸。它能识别 30 种语言和 22 种中文方言，包括普通话、粤语、日语和韩语——这些是 Parakeet 覆盖不到的。它会自动检测语言，你也可以指定一种：

```
let transcriber = SpeechTranscriber(
    model: QwenSpeechModel(variant: .large, language: Locale.Language(identifier: "yue")),
    transcriptionOptions: [],
    reportingOptions: [],
    attributeOptions: []
)
```

Qwen3-ASR 对每段最长 40 秒的音频只给出一个最终结果，没有易变结果、词级时间戳或置信度。它跑在 GPU 上，比 Parakeet 慢，所以更适合转录文件而不是实时输入。

要添加其他引擎，请为其配置实现 `SpeechRecognitionModel`，为单个模块的会话实现 `SpeechRecognitionExecutor`。README 里有一个[小型 provider](https://github.com/mattt/AnySpeechRecognizer#custom-providers)，只返回占位文本，可以帮你起步。

每个仓库都记录了它的源 checkpoint 和每个文件的校验和，包则把它钉在一个固定 revision 上。Parakeet 仓库额外提供了一个用于实时输入的 8 秒编码器，它把实时分析时间缩短约三分之一，代价是词错误率略有升高。仓库里还有转换工作流，其中大部分沿用 FluidInference 的 [mobius](https://github.com/FluidInference/mobius) 脚本，并且每次转换都会对照原始模型校验。

下载只在你的 app 请求时才发生：每个 Parakeet 约 600 MB，实时编码器再加约 590 MB，Qwen3-ASR 为 0.9 到 2.4 GB，Sortformer 约 250 MB。文件放进标准的 Hugging Face 缓存，所以沙盒之外的 Mac app 能与 Python 及其他 Hugging Face 工具共享它们。

### 说话人分离

转录一段对话时，你往往想知道每句话出自谁口。这就是说话人分离，而 Apple 的 Speech framework 没有对应模块，所以 AnySpeechRecognizer 加了一个。`SpeakerDiarizer` 在 Core ML 上运行 NVIDIA 的 [Streaming Sortformer](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2)，与 Apple 或 Parakeet 的 transcriber 在同一条时间轴上：

```
let diarizer = SpeakerDiarizer(model: SortformerDiarizationModel())
if let request = try await AssetInventory.assetInstallationRequest(
    supporting: [transcriber, diarizer]
) {
    try await request.downloadAndInstall()
}
let analyzer = SpeechAnalyzer(modules: [transcriber, diarizer])
```

这个分离器最多追踪四位说话人，即使他们抢话重叠也是如此。`SpeakerTimeline` 汇集它的结果，把每个带时间戳的词归属到某位说话人，于是你可以按说话轮次打印转录文本。和 AnyLanguageModel 的图像支持一样，这超出了 Apple API 今天能提供的范围。

分离器默认使用 Sortformer v2。你也可以选 [v2.1](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2.1)——NVIDIA 用更多会议数据训练了它，在我们的测量中它在会议场景下也更准。

### 效果如何？

我们在一台运行 macOS 27.0.1 的 M4 Max Mac Studio 上，用这个包自带的 `hear` 命令行工具做了测量。以下是 3 到 8 分钟长的 LibriSpeech 文件上的词错误率：

| Transcriber | test-clean | test-other |
| --- | --- | --- |
| Parakeet v3，文件 | 1.55% | 2.78% |
| Parakeet v3，实时 | 4.73% | 4.29% |
| Parakeet Ultra，文件 | 1.66% | 2.55% |
| Parakeet Ultra，实时 | 2.65% | 3.28% |
| Parakeet Unified，文件 | 1.43% | 2.19% |
| Parakeet Unified，实时 | 1.45% | 2.42% |
| Apple 的 transcriber，文件 | 2.12% | 3.97% |

Parakeet 转录一小时的音频，从文件处理约需 20 到 40 秒，实时输入约需 1.5 到 2.5 分钟，Core ML 编译完模型后内存占用约 100 MB。Qwen3-ASR 慢得多，且需要几 GB 内存。会议对谁都是难题：在人们互相抢话的 AMI 录音上，我们测过的每个引擎词错误率都超过 23%。

这些数字来自一台机器和几个数据集，所以请用你自己的硬件和音频实测。`hear evaluate` 可以作用于你自己的文件，仓库里的 `natural-speech-eval.py` 工具[可复现这些测量](https://github.com/mattt/AnySpeechRecognizer#accuracy-and-performance)。到目前为止我们只在 macOS 27 上测试过，还没在 iPhone 上测。

接下来，我们想加入更多引擎，包括 macOS 27 和 iOS 27 上的 Core AI。

## AnyDecisionModel

AnyDecisionModel 则是另一回事。没有 Apple 的 framework 可以对照映射，而决策模型严格说也不算新东西。

> 只有产自法国 Décision 地区的才叫 decision model（决策模型）；
> 否则，不过是起泡版的 zero-shot 分类。

新的是这个名字、一大波热度，以及一批专为做决策而训练的模型。我们认为事情正在朝这个方向走，所以我们想要一个为此准备好的 Swift API。

应用经常让语言模型来做决策。*这条消息紧急吗？* *这张工单该派给哪个团队？* *这位客户有多恼火？* 常规做法是给语言模型写 prompt、再解析它生成的文本。这样你能得到一个答案，但看不到它给其他选项分配的概率。

在 Swift 里，一次决策长这样：

```
import AnyDecisionModel

enum Department: String, Choosable {
    case billing, technical, sales
}

let ticket = "I was charged twice for my order, and now the app logs me out when I try to ask for a refund."

let model = MLXDecisionModel(modelID: "mlx-community/Qwen3-4B-Instruct-2507-4bit")
let session = DecisionSession(model: model, state: .text(ticket))

let urgent = try await session.probability(of: "Does this convey urgency?")
let team = try await session.choice("Which team?", from: Department.self)
let anger = try await session.score(
    "How frustrated?",
    levels: ["Calm", "Frustrated", "Very angry"]
)
```

`urgent` 是一个 `Double`。`team` 是一个 `Choice<Department>`，包含被选中的 case、每个选项的概率和一个置信度值。`anger` 是一个 `Score`，包含期望等级、每个等级的概率和一个置信度值。因为 `Department` 遵循了 `Choosable`，`team.value` 就是一个可以直接用于穷尽 `switch` 的 `Department`。

如果你用过 Foundation Models 或 AnyLanguageModel，模型与会话这套模式会眼熟。`DecisionSession` 持有单一状态，可以是文本或 JSON，每个问题都是关于这个状态的。问题彼此独立：一个答案绝不会成为后续问题的输入。要一次问多个问题，把它们作为一批传给 `decide(_:)`。

对每个问题，MLX 后端会用一个单 token 标签来构造每个允许答案的 prompt，然后从一次前向传播中读出每个标签的概率。

### 上手试试：Emoji Magnet

Emoji Magnet 是一个 macOS app，一个文本框悬在一堆 343 个 emoji 上方。输入一个短语，比如 "things you wear"，匹配的 emoji 会从堆里浮起来。把它改成 "things you wear in winter"，不再匹配的 emoji 就落回去。

这个 app 没有任何内置关键词规则；一切都由模型在推理时决定。你停下打字时，它对每个 emoji 向模型问一个是/否问题，例如：

```
Statement: a heavy winter coat fits the description "things you wear". Is this statement true?
```

会话的状态里存着这个短语。上面那个演示用的是托管的 Jev 后端，一次请求就能回答全部 343 个问题，所以每个短语的 emoji 大约半秒就落定。没有 `TYPESAFE_AI_API_KEY` 时，app 会用 MLX 后端在你的 Mac 上跑 Qwen3 4B。该后端利用前缀缓存对状态只求值一次，然后每次前向传播回答 16 个问题。在一台 M4 Max 上，模型加载后每 16 个一组大约耗时 0.45 秒。把 343 个 emoji 全部过一遍大约需要 10 秒，每组的结果一到就显示。

Emoji Magnet 在 [AnyDecisionModel-Examples](https://github.com/mattt/AnyDecisionModel-Examples) 仓库里。

### 决策头与 Clef

读取 next-token 概率对通用语言模型也管用，但这些模型并不是为做决策而训练的。Cloudflare 的 [Clef](https://huggingface.co/Cloudflare/clef) 模型是一种更新思路的例子：它带一个经过训练的决策头，把状态和一份带类型问题的 schema 转成决策，在一次前向传播中返回所有问题全部允许选项的概率。[Clef-Flash](https://huggingface.co/Cloudflare/clef-flash) 是它的 9B 版本。

AnyDecisionModel 可以在 Mac 上用 MLX 跑 Clef-Flash：

```
let model = MLXHeadDecisionModel(
    modelID: "mlx-community/clef-flash-4bit",
    head: .jointSchema
)
```

会话和问题用法不变，但 `MLXHeadDecisionModel` 从 Clef 经过训练的决策头读取每个决策，而不是从 next-token 概率。这个 [4-bit 模型](https://huggingface.co/mlx-community/clef-flash-4bit)是 6.2 GB 的下载量，其 model card 建议至少 16 GB 内存的 Mac。Clef 能读图像和视频，但这个后端只接受文本和 JSON 状态。

### 校准与检验概率

语言模型的原始概率往往过度自信。本地后端接受一个 `Calibration`，它对每个答案施加温度、对是/否答案施加偏置。请用相互独立的数据集来拟合校准并评估结果。

语言模型还可能因为某个选项在列表中的位置而偏向它。在 MLX、Core AI 和 llama.cpp 的 next-token 后端上，打开 `rotationDebiasing`，对每个选项旋转各问一次选择题并平均概率。代价是每个旋转多一次 prompt 求值。

每个本地的 choice 和 score 还带一个基于其概率熵的置信度值。它衡量概率有多集中，而不是答案对不对，所以请先在你自己的数据上核查错误率，再选定阈值。next-token 后端的诊断会报告模型把多少概率分给了允许的答案。数值低，说明大部分概率被分到了别处。

### 后端

AnyDecisionModel 有六个后端：

- **MLX** 用 [mlx-swift-lm](https://github.com/ml-explore/mlx-swift-lm) 在 Apple silicon 上运行一个较小的语言模型，并从 Hub 下载它。
- **MLX 决策头**运行自带训练决策头的模型，例如 Clef。
- **Core AI** 与 MLX 相同，只是在 macOS 27 和 iOS 27 上使用 Core AI 模型。
- **llama.cpp** 通过 [llama.swift](https://github.com/mattt/llama.swift) 从本地 GGUF 模型读取决策。
- **Jev** 通过 [System One API](https://docs.typesafe.ai/api/system-one) 调用 TypeSafe 的 Jev，或任何实现了该 API 的服务器，例如 [Kev](https://github.com/jaredpalmer/kev)。
- **Ollama** 调用本地 Ollama 服务器或 Ollama 云端上的 System One 决策模型。需要 Ollama 0.35.0 或更新版本；云端模型则需要 0.40.5 或更新版本。

next-token 后端把答案标成 "yes" 和 "no"、A 到 Z 或 0 到 9，所以一道 choice 最多 26 个选项，score 最多 10 个等级。决策头没有这个限制。

和 AnyLanguageModel 一样，这个包使用 Swift package traits。不启用 traits 时，它没有任何第三方依赖：你会得到核心类型以及 Jev 和 Ollama 后端，它们也能在 Linux 上构建。要用本地后端，请启用 `MLX`、`CoreAI` 或 `Llama` trait。

## 开始使用

两个包都要求 Swift 6.2 或更新版本，以及 macOS 26 或 iOS 26 或更新版本。Parakeet 与 Sortformer 运行时以及 MLX 后端要求 Apple silicon。AnyDecisionModel 的 MLX 构建任务使用 Xcode 的 Swift 6.4 或更新版本和 Metal 工具链；Core AI 需要 Xcode 27 和 OS 27 运行时。

把这两个包加进你的 `Package.swift`：

```
dependencies: [
    .package(url: "https://github.com/mattt/AnySpeechRecognizer", from: "0.1.0"),
    .package(
        url: "https://github.com/mattt/AnyDecisionModel",
        from: "0.6.0",
        traits: ["MLX"]
    ),
]
```

目前，AnyDecisionModel 的 `CoreAI` trait 不能与 AnySpeechRecognizer 组合使用，因为 coreai-kit 0.7.3 要求 swift-huggingface 低于 1.0，而 AnySpeechRecognizer 要求 1.x。

各 README 里有更多示例，以及关于要求和后端的细节。AnySpeechRecognizer 还带一个命令行工具 `hear`，可以转录本地文件、标注说话人并评估结果。每条 `hear` 命令都必须指定 `--backend apple`、`--backend parakeet` 或 `--backend qwen`；分析之前，用相同的后端与模型选项运行 `hear prepare` 来安装所需资产。

把它们用进你的 app，告诉我们哪些行、哪些不行。两个仓库都欢迎 issue 和 pull request。
