# 个人 Copilot：训练你自己的编码助手

Sourab Mangrulkar (smangrul)

Sayak Paul (sayakpaul)

在编程与软件开发不断演进的版图中，对效率和生产力的追求催生了引人注目的创新。其中之一就是代码生成模型的兴起，如 [Codex](https://openai.com/blog/openai-codex)、[StarCoder](https://arxiv.org/abs/2305.06161) 和 [Code Llama](https://arxiv.org/abs/2308.12950)。这些模型在生成类人代码片段上展现了卓越能力，作为编码助手潜力巨大。

不过，虽然这些预训练模型在众多任务上表现惊艳，地平线上还有一个更激动人心的可能：把代码生成模型**定制**到你自己的需求上。想象可以按企业规模使用的个性化编码助手。

本文展示我们如何打造 HugCoder 🤗——一个在 [`huggingface` GitHub 组织](https://github.com/huggingface)公开仓库代码内容上微调的代码 LLM。我们会讲数据收集工作流、训练实验和一些有趣的结果。照着做，你就能基于自己的私有代码库打造专属 copilot。最后我们还会留下几个可以继续实验的方向。

开始吧 🚀

## 数据收集工作流

我们想要的数据集概念上很简单，结构如下：

|  |  |  |
| --- | --- | --- |
| 仓库名 | 仓库内文件路径 | 文件内容 |
| --- | --- | --- |
| --- | --- | --- |

用 [Python GitHub API](https://github.com/PyGithub/PyGithub) 从 GitHub 抓代码内容很直接。但根据仓库数量和仓库内代码文件数量，很容易撞上 API 限流问题。

为了避免这类问题，我们决定把所有公开仓库 clone 到本地，直接从本地提取内容而不走 API。我们用 Python 的 `multiprocessing` 模块并行下载所有仓库，见[这个下载脚本](https://github.com/sayakpaul/hf-codegen/blob/main/data/parallel_clone_repos.py)。

仓库里常有非代码文件，比如图片、演示文稿等资产，我们对其内容不感兴趣。我们建了一份[扩展名列表](https://github.com/sayakpaul/hf-codegen/blob/f659eba76f07e622873211e5b975168b634e6c22/data/prepare_dataset.py#L17C1-L49C68)把它们过滤掉。对于 Jupyter Notebook 之外的代码文件，直接用 "utf-8" 编码解析即可；对于 notebook，只取代码单元。

我们还排除了所有与代码无直接关系的路径，包括：`.git`、`__pycache__`、`xcodeproj`。

为了让内容序列化更省内存，我们用了分块和 [feather 格式](https://arrow.apache.org/docs/python/feather.html#:~:text=Feather%20is%20a%20portable%20file,Python%20(pandas)%20and%20R.)。完整实现见[这个脚本](https://github.com/sayakpaul/hf-codegen/blob/main/data/prepare_dataset.py)。

## 微调你自己的个人 Co-Pilot

本节展示如何微调以下模型：[`bigcode/starcoder`](https://hf.co/bigcode/starcoder)（155 亿参数）、[`bigcode/starcoderbase-1b`](https://hf.co/bigcode/starcoderbase-1b)（10 亿参数）、[`Deci/DeciCoder-1b`](https://hf.co/Deci/DeciCoder-1b)（10 亿参数）。所有实验都只用一个 A100 40GB 的 Colab Notebook 加 🤗 PEFT（参数高效微调）。此外我们还会演示如何用 🤗 Accelerate 的 FSDP 集成，在 8 块 A100 80GB 的机器上全量微调 `bigcode/starcoder`（155 亿参数）。训练目标是 [fill-in-the-middle（FIM）](https://arxiv.org/abs/2207.14255)：把训练序列的一部分挪到末尾，然后自回归地预测重排后的序列。

为什么用 PEFT？全量微调太贵。看几个数字就有概念了：

全量微调所需的最低 GPU 内存：

- 权重：2 字节（混合精度训练）
- 权重梯度：2 字节
- 使用 Adam 时的优化器状态：4 字节（原始 FP32 权重）+ 8 字节（一阶和二阶动量估计）
- 以上加起来每个参数的成本：16 字节/参数
- **15.5B 模型 -> 248GB GPU 内存——这还没算存放中间激活的巨大需求 -> 至少需要 4 块 A100 80GB**

既然硬件需求这么大，我们就用参数高效微调，具体用 [QLoRA](https://arxiv.org/abs/2305.14314)。以下是用 QLoRA 微调 StarCoder 的最低 GPU 内存需求：

> trainable params: 110,428,160 || all params: 15,627,884,544 || trainable%: 0.7066097761926236

- 基座模型权重：0.5 字节 × 15.51B 冻结参数 = 7.755 GB
- Adapter 权重：2 字节 × 0.11B 可训练参数 = 0.22GB
- 权重梯度：2 字节 × 0.11B 可训练参数 = 0.12GB
- Adam 优化器状态：4 字节 × 0.11B 可训练参数 × 3 = 1.32GB
- **以上相加 -> 9.51 GB ≈ 10GB -> 1 块 A100 40GB 即可** 🤯。选 A100 40GB 的原因是：2048 长序列 + batch size 4 的训练会产生较高的中间激活内存。如下文所见，实际 GPU 内存为 26GB，A100 40GB 刚好能装下。另外 A100 与 Flash Attention 2 的兼容性更好。

上面的估算没有计入中间激活检查点所需内存，那部分相当可观。我们借助 Flash Attention V2 和 Gradient Checkpointing 来克服这个问题。

- QLoRA + Flash Attention V2 + gradient checkpointing：在单块 A100 40GB 上模型总占用为 **26 GB**，**batch size 为 4**。
- 用 FSDP 全量微调 + Flash Attention V2 + gradient checkpointing：每块 GPU 占用 **70 GB 到 77.6 GB**，**每 GPU batch size 为 1**。

想方便地估算在 🤗 Hugging Face Hub 模型上训练或做大模型推理需要多少显存，请参考 [model-memory-usage](https://huggingface.co/spaces/hf-accelerate/model-memory-usage)。

## 全量微调

来看如何用 PyTorch Fully Sharded Data Parallel（FSDP）在 8 块 A100 80GB 上全量微调 `bigcode/starcoder`（150 亿参数）。关于 FSDP 的更多信息请看 [Fine-tuning Llama 2 70B using PyTorch FSDP](https://huggingface.co/blog/ram-efficient-pytorch-fsdp) 和 [Accelerate Large Model Training using PyTorch Fully Sharded Data Parallel](https://huggingface.co/blog/pytorch-fsdp)。

**资源**

- 代码库：[link](https://github.com/pacman100/DHS-LLM-Workshop/tree/main/personal_copilot/training)。使用了 Transformers 新加入的 Flash Attention V2 支持。
- FSDP 配置：[fsdp_config.yaml](https://github.com/pacman100/DHS-LLM-Workshop/blob/main/personal_copilot/training/configs/fsdp_config.yaml)
- 模型：[bigcode/stacoder](https://huggingface.co/bigcode/starcoder)
- 数据集：[smangrul/hf-stack-v1](https://huggingface.co/datasets/smangrul/hf-stack-v1)
- 微调后的模型：[smangrul/peft-lora-starcoder15B-v2-personal-copilot-A100-40GB-colab](https://huggingface.co/smangrul/peft-lora-starcoder15B-v2-personal-copilot-A100-40GB-colab)

启动训练的命令见 [run_fsdp.sh](https://github.com/pacman100/DHS-LLM-Workshop/blob/main/personal_copilot/training/run_fsdp.sh)。

```
accelerate launch --config_file "configs/fsdp_config.yaml"  train.py \
    --model_path "bigcode/starcoder" \
    --dataset_name "smangrul/hf-stack-v1" \
    --subset "data" \
    --data_column "content" \
    --split "train" \
    --seq_length 2048 \
    --max_steps 2000 \
    --batch_size 1 \
    --gradient_accumulation_steps 2 \
    --learning_rate 5e-5 \
    --lr_scheduler_type "cosine" \
    --weight_decay 0.01 \
    --num_warmup_steps 30 \
    --eval_freq 100 \
    --save_freq 500 \
    --log_freq 25 \
    --num_workers 4 \
    --bf16 \
    --no_fp16 \
    --output_dir "starcoder-personal-copilot-A100-40GB-colab" \
    --fim_rate 0.5 \
    --fim_spm_rate 0.5 \
    --use_flash_attn
```

总训练时长 **9 小时**。按 [lambdalabs](https://lambdalabs.com/service/gpu-cloud/pricing) 8x A100 80GB 每小时 $12.00 计算，总成本为 **$108**。

## LoRA 之舞

如果你玩过 Stable Diffusion 和 LoRA 做自己的 Dreambooth 模型，你应该熟悉这些概念：不同 LoRA 按不同权重组合、把 LoRA 用到非训练时的另一个基座模型上。在文本/代码领域，这还是一块未开垦之地。我们在这方面做了实验，结果非常可观。准备好了吗？出发！🚀

### 自由混搭 LoRA

PEFT 目前支持 3 种 LoRA 组合方式：`linear`、`svd`、`cat`。详情见 [tuners#peft.LoraModel.add_weighted_adapter](https://huggingface.co/docs/peft/main/en/package_reference/tuners#peft.LoraModel.add_weighted_adapter)。

我们的 notebook [Dance_of_LoRAs.ipynb](https://github.com/pacman100/DHS-LLM-Workshop/blob/main/personal_copilot/inference/Dance_of_LoRAs.ipynb) 包含全部推理代码和各种 LoRA 加载组合，比如把 chat assistant 加载到 `starcoder` 之上——而我们微调它时用的基座是 `starcodeplus`。

这里我们考虑 2 种能力（`chatting/QA` 与 `code-completion`）乘以 2 种数据分布（`top 10 public hf codebase` 与 `generic codebase`），也就是 4 个维度做定性评估分析。

##### 先看 `chatting/QA` 任务。

如果禁用所有 adapter，两个数据集上的任务都会失败，因为基座模型（`starcoder`）只做代码补全，不适合`聊天/问答`。启用 `copilot` adapter 的表现和禁用时差不多，因为这个 LoRA 也是专门为代码补全微调的。

现在启用 `assistant` adapter。

[![assistant_chat_generic](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/generic_qa_short.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/generic_qa_short.png) 基于通用代码的问答

[![assistant_chat_hf](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/qa_hf.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/qa_hf.png) 基于 HF 代码的问答

可以看到，关于 `scrapy` 的通用问题回答得不错；但对 HF 代码的问题就答不上来——这不在它的预训练数据里。

###### 再看 `code-completion` 任务。

禁用 adapter 时，通用 two-sum 的代码补全符合预期；但 HF 代码补全会在 `LoraConfig` 的参数上出错，因为基座模型在预训练中没见过它。启用 `assistant` 的表现与禁用时类似，因为它训练用的自然语言对话里没有任何 Hugging Face 代码仓库。

现在启用 `copilot` adapter。

[![copilot_code_generic](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/infill.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/infill.png)

可以看到 `copilot` adapter 两种情况都答对了。也就是说无论 HF 专属代码库还是通用代码库，它在代码补全上的表现都符合预期。

**现在，作为一个用户，我想同时拥有 `assistant` 和 `copilot` 两种能力。这样我在 IDE 里写代码时可以用它补全，也可以把它当聊天机器人，回答我关于 API、类、方法、文档的问题。它应该能回答这类问题：`怎么用 x`、`请为 Y 写一段代码`——针对我自己的代码库。**

PEFT 的 `add_weighted_adapter` 就能做到。我们新建一个 adapter `code_buddy`，给 `assistant` 和 `copilot` 各一半权重。

[![combining_loras](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/combine_adapters.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/combine_adapters.png) 组合多个 adapter

[![mix_chat_hf](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/qa_combined_hf.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/qa_combined_hf.png)

可以看到 `code_buddy` 的表现比单用 `assistant` 或 `copilot` 好得多！它能响应*写一段代码示例*的请求，展示如何使用某个 HF 仓库的 API。当然它也幻觉出了错误的链接/解释——这仍是 LLM 的未解难题。

下面是 `code_buddy` 在代码补全任务上的表现。

## 怎么在本地跑？

我知道，看完这些，你想在自己的代码库上微调 starcoder，然后在消费级硬件上本地使用——Mac 的 M1 GPU 笔记本、Windows 配 RTX 4090/3090……别急，安排上了。

我们要用一个超酷的开源库 [mlc-llm](https://github.com/mlc-ai/mlc-llm) 🔥。具体用的是这个 fork [pacman100/mlc-llm](https://github.com/pacman100/mlc-llm)，它做了改动以配合 Hugging Face Code Completion VS Code 扩展。在我的 Mac（M1 Metal GPU）上，15B 模型慢得难受。所以我们改用小模型：训练 `bigcode/starcoderbase-1b` 的 PEFT LoRA 版本和全量微调版本。训练 colab notebook 链接如下：

- `starcoderbase-1b` 全量微调与 PEFT LoRA 微调的 Colab notebook：[link](https://colab.research.google.com/drive/1tTdvc2buL3Iy1PKwrG_bBIDP06DC9r5m?usp=sharing)

训练损失、评估损失和学习率调度曲线如下：

[![loss_plots](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/loss_plots.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/loss_plots.png)

接下来看在本地托管合并模型 [smangrul/starcoder1B-v2-personal-copilot-merged](https://huggingface.co/smangrul/starcoder1B-v2-personal-copilot-merged)，并配合 🤗 [llm-vscode](https://marketplace.visualstudio.com/items?itemName=HuggingFace.huggingface-vscode) VS Code 扩展使用的详细步骤。

- 克隆仓库

```
git clone --recursive https://github.com/pacman100/mlc-llm.git && cd mlc-llm/
```

- 安装 mlc-ai 和 mlc-chat（editable 模式）：

```
pip install --pre --force-reinstall mlc-ai-nightly mlc-chat-nightly -f https://mlc.ai/wheels
cd python
pip uninstall mlc-chat-nightly
pip install -e "."
```

- 编译模型：

```
time python3 -m mlc_llm.build --hf-path smangrul/starcoder1B-v2-personal-copilot-merged --target metal  --use-cache=0
```

- 按下面内容更新 `dist/starcoder1B-v2-personal-copilot-merged-q4f16_1/params/mlc-chat-config.json`：

```
{
    "model_lib": "starcoder7B-personal-copilot-merged-q4f16_1",
    "local_id": "starcoder7B-personal-copilot-merged-q4f16_1",
    "conv_template": "code_gpt",
-    "temperature": 0.7,
+    "temperature": 0.2,
-    "repetition_penalty": 1.0,
    "top_p": 0.95,
-    "mean_gen_len": 128,
+    "mean_gen_len": 64,
-    "max_gen_len": 512,
+    "max_gen_len": 64, 
    "shift_fill_factor": 0.3,
    "tokenizer_files": [
        "tokenizer.json",
        "merges.txt",
        "vocab.json"
    ],
    "model_category": "gpt_bigcode",
    "model_name": "starcoder1B-v2-personal-copilot-merged"
}
```

- 启动本地服务：

```
 python -m mlc_chat.rest --model dist/starcoder1B-v2-personal-copilot-merged-q4f16_1/params --lib-path dist/starcoder1B-v2-personal-copilot-merged-q4f16_1/starcoder1B-v2-personal-copilot-merged-q4f16_1-metal.so
```

- 把 VS Code 中 HF Code Completion 扩展的 endpoint 指向本地服务：

[![local_endpoint](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/local_endpoint.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/local_endpoint.png)

- 在 VS Code 新建文件，粘贴下面的代码，把光标放在文档字符串引号中间，让模型尝试填充 docstring：

[![local_inference](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/local_inference.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/personal_copilot/local_inference.png)

### 结论

在这篇博客里，我们展示了如何微调 `starcoder` 打造一个了解自己代码的个人 co-pilot。因为我们是在 Hugging Face 的代码上训练的，所以叫它 🤗 HugCoder :）。在看完数据收集工作流后，我们对比了 QLoRA 与全量微调训练。我们还做了组合不同 LoRA 的实验——这在文本/代码领域仍是未开垦的方向。部署方面，我们试验了通过 🤗 Inference Endpoints 的远程推理，还演示了用 VS Code 和 MLC 在端侧运行小模型。
