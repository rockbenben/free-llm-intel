如果你今天用 agent 做开发，你大概知道三个协议。MCP 给 agent 提供了调用工具的标准方式。Skills 给 agent 提供了消费指令的方式。A2A 给 agent 提供了调用其他 agent 的方式。这三者都默认用户已经知道需要哪个工具、指令或 agent。发现、集成并维护这些能力，责任仍然在使用者。

Agentic Resource Discovery（ARD）规范就是坐在它们前面的那一层「发现层」。它是一份草案阶段的开放规范，由来自 Microsoft、Google、GoDaddy、Hugging Face 等的贡献者共同开发，获得了业界的广泛参与。它定义了 agent 和工具如何在联邦式注册表中被编目、索引和搜索，让 agent 能在运行时找到能力，而不是需要预先安装。它不是产品，也不是市场。它是一项共享标准，任何公司都可以独立实现，任何 agent 或工具都可以参与。

在本文中，我们将探讨这份规范、Hugging Face 的实现，以及如何开始在 ARD 上构建。

## 发现问题

当前 agent 能力的模式是「先安装、后使用」。开发者把某个 MCP server 的 URL 硬编码进配置文件。用户通过插件给 AI 应用连上某个服务并复用。这对 agent 每天使用的那几个工具可行，却无法扩展到数千个临时性的接触面。

权宜之计是把所有可用工具的描述塞进 LLM 的上下文窗口，让模型自己挑。这受制于上下文预算。这里也有基于搜索的策略，但描述往往太单薄，难以充分消歧。

ARD 把选择挪到了 LLM 之外。注册表用更丰富的信号为能力建索引，例如发布者身份、代表性查询、合规证明和标签。它暴露一个 REST 端点。客户端用自然语言搜索，模型则调用搜索返回的任何东西。转变在于：从人工安装的静态目录，转向基于意图的搜索——让 agent 动态找到合适的能力，触达不断壮大的 MCP 工具、A2A agent 和其他服务的生态，而无需逐一预配置。

规范定义了两样东西：

- 一种叫 `ai-catalog.json` 的静态 manifest 格式，让发布者把自己的能力托管在一个 well-known URL 上。
- 一个动态注册表 API `POST /search`，提供实时的、带排名的发现。

## ARD 在 Hugging Face Hub 上

Hugging Face 的 [Discover Tool](https://github.com/huggingface/hf-discover) 是我们在 ARD 上的参考实现。它提供对数千个 Skills、ML 应用和 MCP Servers 的搜索访问——既包括 Hugging Face 上的，也覆盖其他 ARD 发现服务。

它的原理是把 Hub 现有的、针对 Spaces 的语义搜索与我们的 Agent Skills 结合，并把结果以 ARD catalog 条目的形式提供。Hub 已经托管着一个由运行 Gradio 应用、MCP server 和 demo 组成的 Spaces 目录。其语义搜索支持 `agents=true` 标志，可以按 agent 导向的元数据对 Spaces 排名，而 Discover 把这一搜索翻译成 ARD 规范。

该适配器施加两个过滤。第一，响应只包含 runtime stage 为 `RUNNING` 的 Spaces。第二，响应的 media type 由请求决定。共支持三种 media type：

- `application/ai-skill`：默认。生成的 `SKILL.md`，包装 Space 的 `agents.md`。
- `application/mcp-server+json`：为打了 `mcp-server` 标签的 Spaces 生成的 MCP server 目录条目。
- `application/vnd.huggingface.space+json`：供想自行处理的客户端使用的原始 Space 元数据。

skill 类型还涉及一个额外转换。许多 Spaces 会附带一个描述 agent 应如何与之交互的 `agents.md` 文件。Discover 读取该文件，并用 skill 消费者期望的 frontmatter 包装：`name`、`description`，以及涵盖 Space ID、Hub URL、应用 URL 和原始 `agents.md` URL 的来源元数据。产出的是任何支持 skill 的客户端都能通过其常规 skill 流程安装或加载的 skill。

对于打了 MCP 标签的 Spaces，适配器生成一个指向该 Space 基于 HTTP 传输的 Gradio MCP 端点的目录条目。若 Hub 提供了 runtime 域名就用它，否则使用标准的 `.hf.space` slug 约定。

## 使用方式

`discover` 已内置于 [Hugging Face CLI](https://github.com/huggingface/huggingface_hub)（`hf`）。要开始并让你或你的 agent 获得访问：

```
# Install the Hugging Face CLI tool:
uv tool install huggingface_hub

# Search for resources to train a model
hf discover search "Fine tune a language model"

# Find MCP Servers to generate an image
hf discover search "Generate an image" --json --kind mcp

# Search other registries
hf discover search "Purchase aeroplane tickets" --registry-url <catalog-url>
```

### REST API 与 MCP Tool

你也可以用 REST API 或 MCP Server 直接搜索 catalog。

Hugging Face 的 catalog 发布在其 well-known URL 上：

```
https://huggingface.co/.well-known/ai-catalog.json
```

直接调用搜索：

```
POST https://huggingface-hf-discover.hf.space/search
```

```
curl -s https://huggingface-hf-discover.hf.space/search \
  -H "Content-Type: application/json" \
  -d '{
    "query": {
      "text": "fine tune a sentence transformer",
      "filter": {
        "type": ["application/ai-skill"]
      }
    },
    "pageSize": 5
  }'
```

搜索 MCP servers

```
curl -s https://huggingface-hf-discover.hf.space/search \
  -H "Content-Type: application/json" \
  -d '{
    "query": {
      "text": "transcribe some audio",
      "filter": {
        "type": ["application/mcp-server-card+json"]
      }
    },
    "pageSize": 5
  }'
```

另外，任何 MCP Client 都可以通过 MCP 端点连接并使用 [https://huggingface-hf-discover.hf.space/mcp](https://huggingface-hf-discover.hf.space/mcp) 来搜索 catalog。

## 这对规范意味着什么

ARD 把发现与执行分离。静态 manifest 格式由 media type 驱动，因此任何工件协议都可以搭同一个信封，无需修改规范本身。注册表 API 就是普通的 HTTP REST，任何客户端都可以对其做联邦。Discover 是该规范在生态中的若干参考实现之一，而且因为联邦已内建于协议，经由一个服务的搜索可以浮现出由另一个服务托管的能力。

Discover Tool 是这一设计的一次实战检验。它没有发明新的工件格式，而是用一个现有搜索后端——Hub——套上规范的信封，让同一批 Spaces 根据客户端的请求浮现为 skills 或 MCP servers。

下一步是与规范的联邦模式（`auto`、`referrals`、`none`）更紧密的集成，以及 Hub 侧对用户和组织主页上静态 `ai-catalog.json` manifest 的支持。一旦落地，任何 Space 发布者都能通过标准的 well-known URI 机制宣告自己的能力。
