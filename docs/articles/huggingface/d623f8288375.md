# 长 Prompt 如何阻塞其他请求——LLM 性能优化

在 TNG，我们在由 24 块 H100 GPU 组成的集群上自托管了大量大语言模型。为 50 多个应用提供 LLM 服务——每天消耗超过 1 亿 token 同时生成超过 1000 万 token——要求我们精细调优请求处理。

在我们 LLM 性能系列的[上一篇文章](https://huggingface.co/blog/tngtech/llm-performance-prefill-decode-concurrent-requests)中，我们探讨了 token 生成过程中 prefill 与 decode 阶段的差异。简而言之：第一个输出 token（**prefill 步骤**）需要处理整个 prompt，可以高效并行化并把 GPU 利用率打满；而后续所有输出 token（**decode 步骤**)只需处理单个新增 token，计算强度较低但必须串行进行。当许多请求并发处理时，任何以低延迟为目标的策略都必须在新请求到达时运行其 prefill 步骤，同时此前已调度请求的 decode 步骤仍在进行。因此，并发处理新旧请求需要在 prefill 和 decode 阶段之间仔细权衡，这带来两大挑战，下面逐一讨论。其中一个是容易解决的问题，另一个则是更根本的缺陷。

### 较简单的挑战：长 Prompt 阻塞队列

由于单个 decode 步骤计算量不大，可以通过把多个请求的 decode 批量处理来提高吞吐。但对 prefill，这种做法行不通。由于所有 prompt token 是并行处理的，单个 prefill 步骤就可能已经把 GPU 利用率打满。因此，在 vLLM 默认的 chunked-prefill 策略中，每个 prefill chunk 只包含单个请求的 prompt token。排在后面的请求必须等待前一个 prefill 阶段完成，自己的 prefill 阶段才能开始。

不同请求的 prefill chunk 串行调度带来了这样一个挑战：只要一个带超长 prompt 的请求被调度做 prefill，其后的任何请求都必须等待这段长 prefill 的耗时才能开始处理；**长 prompt 会阻塞 prefill 队列**。（注意：prefill 的串行处理是 *chunked-prefill* 的默认特性，只在已有并发请求处于 decode 阶段时才会出现；因此叫作"partial prefill"。）

默认情况下，与其他 decode 并发执行时，新请求的 prefill 会被串行调度。单个长 prompt 请求可以让后续请求在生成第一个输出 token 之前长时间等待，如下述测量所示。注意第二个请求的最后一个 prefill chunk 留出了并行处理第三个请求 prefill 的空间。

遗憾的是，这个挑战既不能用 vLLM 侧的优先级调度解决（参见[本系列第一篇文章](https://huggingface.co/blog/tngtech/llm-performance-request-queueing)），也不能用更精巧的上游调度器解决。原因是长 prompt 可以在任何后续请求出现之前就被调度，调度器无从"等待"。

#### 请求级并行 Prefill

一个直观的解决方案是并行处理不同请求的 prefill chunk。这可能不是资源最优的，因为单请求的 prefill chunk 就可能已经把算力打满。任何并行的额外 prefill 很可能略微拉长 prefill 耗时，并进一步拖慢并发的 decode 请求。如果这样能降低短请求的延迟、让系统显得更敏捷，那还是可以接受的。但如果排队的下一个请求同样是长 prompt，这个方法就失效了：两个计算密集的 prefill 会被批到一起，造成严重减速。

在 vLLM 最近的一次更新中，实现了一个改进策略：允许不同请求并行 prefill，但限制并发处理的长 prompt 请求数量。例如一个配置可以允许四个请求的 prefill 批处理，但其中只能有一个超过 10,000 prompt token。在这种配置下，长请求的行为与以前一致：**长 prompt 仍串行处理**。但短请求不再需要等前一个请求的长 prefill 完成；**短 prompt 可以走快速通道**。这些请求不再受长时间等待之苦，*time-to-first-token* 指标显著降低。

当然，并行 prefill 只能减少等待时间；在长 prefill 并发执行期间，***time-per-output-token* 仍然会升高**。在这方面，请求级并行 prefill 与标准 chunked-prefill 表现出相同的行为和性能，只是 time-to-first-token 更短。

启用并行 partial prefill 后，新请求无需等待先前请求完成 prefill 阶段即可开始自己的 prefill，从而获得很短的首 token 时间。总完成时间只有小幅改善，因为 decode 步骤仍会被并发 prefill 拖慢。我们的测量显示，与串行 partial prefill 场景相比，第三个请求的 time-to-first-token 明显降低。

### 根本缺陷：并行 Prefill 拖慢 token 生成

每当不同请求的 prefill 和 decode 在同一个 GPU 操作中执行时，其耗时就比孤立的 decode 步骤更长。用户会感受到 token 生成被后续请求打断或拖慢。尤其地，**单个长 prompt 请求就足以拖慢所有已被调度、处于 decode 阶段的请求**。

这是在相同 GPU 上并发处理 prefill 和 decode 的根本缺陷，因为可做的事情很少：

- (a) 你可以**惩罚长 prompt 让它们等待**（例如等所有短的高优先级请求完成）。代价是这些请求的延迟增加，而且没有解决根源：特别是启用请求级并行 prefill 后，被拖慢的还有排在长 prompt 之后调度的短 prompt 请求。此外，在高负载时期，长 prompt 请求在合理时间内被调度的机会可能非常小。在 TNG，我们在一个面向批量请求的 API 中实现了类似策略，这些请求以极低的优先级被调度。
- (b) 你可以为长 prompt 请求设置**独立的推理服务器**，并配一个根据负载和 prompt 长度转发请求的路由器。这种方法需要更多 GPU 资源，但短上下文请求的推理服务器对 GPU 显存要求更低（例如 Llama-3.3-70B 在 130k token 上下文长度下需要四块 H100，而第二个只有两块 H100 的部署就能服务上下文长度 <10k token 的请求）。不过需要精心设计的路由才能优化资源利用率。例如，当没有长 prompt 请求时，较大的推理服务器仍应被利用起来。
- (c) 你可以为 prefill 和 decode 设置分离的**推理引擎**。这种 *disaggregated prefill*（分离式 prefill）架构组合多个 vLLM 部署，每个只运行 prefill 或只运行 decode。prefill 阶段完成后，KV cache 会被传输给 decode worker，带来少量通信开销。但由于 prefill 和 decode 在不同 GPU 上隔离运行，并发 prefill 不再直接干扰 decode。

#### Disaggregated Prefill——为延迟优化

分离 prefill 和 decode 在很大程度上消除了 token 生成在其他请求存在时被拖慢的问题，这使它成为一个非常有吸引力的策略。代价是需要第二个全尺寸 vLLM 部署（例如对 Llama-3.3-70B，若要支持最大 130k token 的上下文长度，需要一个四块 H100 的 prefill worker，再加另一个四块 H100 的 decode worker）。另一个缺点是 GPU 利用率不均衡：prefill 计算密集而 decode 不是，因此 prefill worker 很可能先于 decode worker 打满 GPU 利用率。但另一方面，大型集群可以按不同比例配置 prefill 和 decode worker 数量（取决于负载模式），以优化资源利用率。

Disaggregated prefill 的目的不是提升总吞吐，而是提升总"goodput"（即满足延迟目标的请求比率）。因此，如果你的应用对单个请求的延迟不敏感，它就不是 GPU 资源的最佳用法。

还有一个注意事项：vLLM 中的 disaggregated prefill 特性仍处于实验阶段，部分优化和特性尚不可用。例如，上下文长度目前有更低的限制，且 decode worker 没有一致地使用 CUDA graphs，导致上图中长 prompt 请求的 decode 更慢。好在这些都不是根本性障碍，未来版本的 vLLM 大概率会解决。
