# 流式数据集：效率提升 100 倍

## 太长不看版

> 我们大幅增强了 `load_dataset('dataset', streaming=True)`——一行代码流式读取数据集，无需下载！
> 多 TB 数据集可以立刻开训，不需要复杂配置、不需要下载、没有"磁盘空间不足"，也没有 429 "别再请求了！"错误。速度超快！在 64xH100、256 个下载数据的工作者的规模下，速度快到跑赢我们的本地 SSD。
> 我们把流式读取的请求数降到原来的百分之一 → 数据解析快 10 倍 → 2x 样本/秒 → 256 个并发工作者下零崩溃。

加载数据——尤其是 TB 级别——在任何机器学习工作流里都是大麻烦。我们在训练 [SmolLM3](https://huggingface.co/blog/smollm3) 时就吃过这个苦，一度每次开跑前要花 3 小时下载足够的数据。

`datasets` 库一直支持流式读取，但用超大数据集做大规模训练始终是个挑战。今天改变发生了 🔥。我们花了几个月改进后端，聚焦流式数据集，让它更快、更高效。

我们具体做了什么？⤵️

## 流式读取：还是那套简单的 API

首先要说：我们的改动向后兼容。你仍然可以用同样简单的 `streaming=True` 标志流式读取 Hub 上的任何数据集。一如既往地简单。🚀

```
from datasets import load_dataset

# Stream a dataset instead of downloading it
dataset = load_dataset("HuggingFaceM4/FineVisionMax", split="train", streaming=True)
# Get the first example
print(next(iter(dataset)))
```

全球成千上万的 AI 开发者每天都在用 `datasets`；他们不费吹灰之力就能享受性能提升。

## 挑战：规模化流式读取

要看懂一个数据集，流式读取是救命稻草；但要训练模型，人们通常还是把数据下载到本地，或者用 S3 这样的云存储服务。我们训练 [SmolVLM](https://huggingface.co/blog/smolvlm2) 时就是这样——所有数据放在 S3 上，直接从中流式读取。

我们想改变这一点，于是在开发 [nanoVLM](https://github.com/huggingface/nanoVLM) 时尝试从 Hub 直接流式读取。很快我们就撞上大问题：一次测试运行在不到一分钟内产生了超过 10 万次请求，我们的 IP 被 Hub 封了！😅 原因在于每个 DataLoader 工作者都在独立初始化数据集。深入调查后我们发现，这会掀起一场冗余请求风暴，其中许多请求完全没必要。我们的改动最终把启动请求减少了 100 倍。总的改进成果：

- 数据文件解析时间：快 10 倍
- 启动请求：效率最高提升 100 倍
- 流式速度：最高快 2 倍
- 并发请求：效率最高提升 2 倍

## 底层：我们改进了什么

到底改了什么？我们聚焦两个阶段：启动和流式读取。

**1. 启动 ⚡️** 数据文件的初始解析会产生大量请求。我们做了两项大改动：

- 持久化数据文件缓存：现在我们在所有 DataLoader 工作者之间缓存数据文件列表。第一个工作者从 Hub 解析文件列表，其余工作者直接读这个本地缓存——启动请求几乎清零，解析时间大幅缩短。请求风暴一去不返！
- 优化解析逻辑：我们还把第一个工作者拉取文件列表所需的 API 调用降到最低，尽可能把请求打包，进一步压缩延迟。

**2. 流式读取 🏎️** 为了提升流式过程本身的吞吐，我们引入两个新功能：

- Parquet 预取：为 Parquet 数据集启用预取。模型在处理当前数据块时，datasets 库已在后台拉取下一块。数据管线始终保持充盈，GPU 不会干等数据。
- 可配置缓冲：高级用户现在可以针对自己的硬件和网络环境微调流式性能。我们暴露了缓冲块大小和预取量的配置项，给你优化 I/O 的最大控制权。

这样一来，流式读取的最小请求大小可以从默认的 32MiB 提到 128MiB，并配置预取：

```
import pyarrow
import pyarrow.dataset

fragment_scan_options = pyarrow.dataset.ParquetFragmentScanOptions(
    cache_options=pyarrow.CacheOptions(
        prefetch_limit=1,
        range_size_limit=128 << 20
    ),
)
ds = load_dataset(parquet_dataset_id, streaming=True, fragment_scan_options=fragment_scan_options)
```

这些改进合起来可以让数据吞吐翻倍，训练更快、更高效。

## 为什么我们比裸 S3 快：Xet

Hugging Face 使用 Xet：一种基于去重的存储，支持快速去重上传与下载。与传统远程存储不同，Xet 上的数据传输更快——重复的数据只传一次。例如：向 Hugging Face 上传大规模数据集会借助 Xet 加速。数据集一旦上传完成，就可以立即流式读取。

Parquet 的去重通过 [Parquet Content Defined Chunking（CDC）](https://huggingface.co/blog/parquet-cdc)启用。得益于 Parquet CDC 与 Xet 去重，在 Hugging Face 上上传数据集比任何传统远程存储都快。

这由我们的 `pyspark_huggingface` 包支持——一个用于读写 HF 数据集的 Spark Data Source。它内置 Parquet CDC 与 Xet 支持，大幅加速 HF 上的数据传输。

## 需要自定义流式管线？

有些数据文件格式 `datasets` 不支持，有时你也需要更多控制权，所以我们让构建自定义流式管线变得简单。这条路径已经在 LeRobot 库中采样视频帧、在 `WebDataset` 库中流式读取 TAR 归档上经过实战检验。

我们改进了 `huggingface_hub` 库中的 [HfFileSystem](https://huggingface.co/docs/huggingface_hub/guides/hf_file_system)，可以高效地从远程 Hugging Face 数据集仓库读文件、流式传输数据：

```
from huggingface_hub import HfFileSystem

path = f"hf://datasets/{dataset_id}/{path_in_repo}"
with HfFileSystem().open(path) as f:
    # loop with .read() or .readline() to stream data
    # or do random access with .seek()
```

把 `HfFileSystem` 传给 torch 的 `DataLoader`，会复用 `.ls()` 和 `.glob()` 的缓存结果，列出数据文件时不再需要额外请求。

## 把流式读取推到极限

我们现在正在 nanoVLM 中用这些流式增强来训练下一代 SmolVLM。有了这些调优，流式读取的性能超过了在集群分级硬盘上训练。事实上，现在的流式速度和读本地 SSD 一样快！以前，把数据搬到本地 SSD 正是让每次训练拖延三小时的环节。更多细节请看我们的 GitHub。
