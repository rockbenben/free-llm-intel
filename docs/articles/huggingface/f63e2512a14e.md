我们很高兴开源 PipelineRL——一个实验性的 RL 实现，解决大规模 LLM 强化学习中的一个根本挑战：推理吞吐量与 on-policy 数据收集之间的取舍。PipelineRL 的关键创新是 RL 训练期间的**在飞行中权重更新（inflight weight updates）**（见下方图 1）。这让 PipelineRL 能持续保持高推理吞吐，并最小化 rollout 所用权重与最近更新模型权重之间的滞后。结果：面向大语言模型的快速、稳定的 RL 训练。

[![image/jpeg](https://cdn-uploads.huggingface.co/production/uploads/6338a9f676421c054312d8c1/sBXLyV1PHAj-Uy5Uk1FRP.jpeg)](https://cdn-uploads.huggingface.co/production/uploads/6338a9f676421c054312d8c1/sBXLyV1PHAj-Uy5Uk1FRP.jpeg)

在这篇博客中，我们展示：1）在飞行中的权重更新不会损害训练过程；2）PipelineRL 在使用更简单 RL 算法的同时，取得了与 Open-Reasoner-Zero 有竞争力的结果。我们还将介绍模块化的 PipelineRL 架构——它便于尝试新的推理/训练器组合。

## 传统 RL 与 PipelineRL

在常规 RL 方法（图 1a）中，高吞吐推理与 on-policy 数据收集之间存在取舍。为解释这个取舍，先用算法方式定义常规 RL：

```
current_policy = initial_policy
opt_state = init_optimizer(current_policy)

while True:
    # RL step starts
    # inference
    inference_policy = current_policy
    list_of_prompts = [sample_prompts(training_batch_size) \
        for _ in range(num_grad_steps)]
    list_of_rollouts = [sample_rollouts(prompts, inference_policy) \
        for prompts in list_of_prompts]
    # training
    lag = 0 # lag between the inference and current policies
    for rollouts in list_of_rollouts:
        current_policy, opt_state = policy_update(current_policy, opt_state, rollouts)
        lag += 1
    # RL step ends
```

要达到高吞吐，推理服务器必须使用大 batch size，因此会一次生成可供多个策略优化步使用的数据。然而每步优化都会加大当前策略与用推理策略收集的数据之间的滞后，使收集的数据越来越 off-policy、对训练越来越低效。On-policy 学习只需要单个优化步的数据。但用很多 GPU 生产少量数据是低效的，因为这意味着每 GPU 的 batch size 太小。而且当推理服务器跑完短序列、只剩少数最长的序列在进行时，batch size 还会进一步下降。

PipelineRL（图 1b）通过在飞行中的权重更新来消除这一取舍。我们在每个优化器步之后更新推理服务器中的权重，**且从不停止推理**。我们只在所有推理服务器上暂停刚刚够接收新权重的时间。在飞行中的权重更新让推理服务器能持续保持最优 batch size，同时确保数据保持 on-policy 或近乎 on-policy，分别带来更好的 GPU 利用率和更有效的学习。

## PipelineRL 有效！

[![image/png](https://cdn-uploads.huggingface.co/production/uploads/6338a9f676421c054312d8c1/yjEGi3ShDIv6YwC_MHFDQ.png)](https://cdn-uploads.huggingface.co/production/uploads/6338a9f676421c054312d8c1/yjEGi3ShDIv6YwC_MHFDQ.png)

为了证明 PipelineRL 的有效性和在飞行中权重更新的收益，我们在 Open-Reasoner-Zero 数据集上训练了一个 7B 模型和一个 32B 模型。看学习曲线，PipelineRL 在流行推理测试基准 AIME 2024 和 MATH 500 上追平或超过了 Open-Reasoner 的表现（见上图 2）。

值得注意的是，我们的 RL 实现比 Open-Reasoner-Zero 简单得多。Open-Reasoner-Zero 使用价值函数，而我们的实现是 GRPO 的简化版。特别地，我们发现信任域重要性权重夹断（clamping）对稳定训练并不必要；[DAPO 论文](https://arxiv.org/abs/2503.14476)中的超长序列过滤和 reward shaping 也不必要。归一化损失时，我们只把 batch 中的序列数作为分母，对所有 token 一视同仁。我们没有用 KL 惩罚，也没有熵奖励（尽管我们的实现确实支持参考模型 KL）。尽管实现简单——或者说正因如此——训练非常稳定，可见这份 [wandb 报告](https://wandb.ai/apiche/pipeline-rl/reports/Blog-post-results--VmlldzoxMjQ0MjcwNg)。

人们可能预期在飞行中权重更新会导致训练过程不稳定，因为**序列生成会带着用先前模型版本算出的陈旧 keys 和 values 的 KV cache 继续推进**。然而我们的实验表明，这并不会对稳定性造成不利影响。

## PipelineRL 架构

[![image/jpeg](https://cdn-uploads.huggingface.co/production/uploads/6338a9f676421c054312d8c1/zG5uLW5c8uCTIOjLTN_FX.jpeg)](https://cdn-uploads.huggingface.co/production/uploads/6338a9f676421c054312d8c1/zG5uLW5c8uCTIOjLTN_FX.jpeg)

PipelineRL 以模块化方式构建，以便受益于高度专业化的推理与训练软件的快速进步（SGLang、vLLM、Nvidia Dynamo、DeepSpeed、FSDP、TorchTitan、FastLLM 等）。我们在推理组件与训练组件之间提出清晰的契约，让新的推理和训练方案一旦出现就能轻松接入。

### 推理契约

推理软件必须向 PipelineRL 暴露以下 API[1]：

- **进程组初始化**：启动时，Trainer 0（指定的协调者）向所有推理服务器发送 HTTP `POST /init_process_group` 请求。该请求初始化用于发送权重更新的进程组。
- **权重更新触发**：一旦训练器完成一个学习步（优化器步与权重收集），Trainer 0 向推理端点提交 HTTP `POST /request_weight_update` 请求。请求包含主训练进程即将通过 NCCL 传输的权重的顺序与形状细节。推理服务器必须暂停推理并接收权重广播。
- **Chat completion**：actor 进程通过 HTTP `POST /v1/chat/completion` 请求与 actor LLM 交互。

如果 `init_process_group` 和 `request_weight_update` API 成为行业标准，人们将能够即插即用地在 PipelineRL 中使用不同的推理实现。

### 训练器契约

PipelineRL 训练代码一旦为每个 trainer worker 累积到合适的训练 token 数，就立即把新生成的训练数据喂给它。任何暴露以下 Python API 的训练软件都可以与 PipelineRL 配合：

- **Worker 初始化**：加载并分片训练权重与优化器状态。
- **前向传播**：给定输入产出 token 的对数似然。
- **反向步**：计算并累积表示所选 RL 目标的标量的梯度。
- **优化器步**：执行优化器步。
- **权重收集与广播**：优化器步之后，训练软件必须逐层收集更新后的模型权重，为向推理服务器广播做准备。

PipelineRL 目前使用 HuggingFace `accelerate` 库，让用户可以在 DeepSpeed 和 FSDP 之间选择。但我们发现 `accelerate` 的契约过于灵活、可能造成困惑。我们将转向上述更严格的契约，让使用其他训练器更容易。

## PipelineRL 的下一步？

**即将推出的特性。** 我们的实现仍是实验性的，缺少一些重要功能。我们的头号优先事项包括：用协程实现更精确的推理 batch size 控制、多模态支持、序列并行训练。我们也欢迎更多推理服务器与训练器集成的贡献。不过，我们不会试图把 `pipeline-rl` 仓库做成支持所有可能算法和奖励函数的框架。我们的态度是：`pipeline-rl` 应当是一个可魔改、快速的 GRPO 参考实现，配上易于验证的奖励。如果你想用 PipelineRL 做研究项目，直接 fork 仓库、尽情折腾代码就好！

**更多研究即将到来。** 还需要更多分析来理解在飞行中权重更新如何影响训练动力学，并仔细测量 PipelineRL 带来的加速。此外，关于 PipelineRL 与高度相关的 LLM 异步强化学习先前工作之间的相似之处，也有很多可说。所有这一切及更多内容，敬请期待我们即将发布的研究论文！

## 实验细节

我们对本文报告的 7B 和 32B 实验使用相同超参数：

- batch size 4096
- 学习率 1e-6
- 最大生成 token 数 8192（注意 OpenReasoner 的运行允许生成 16K token）

报告实验所用算力：

- 7B 模型：约 3.5 天，2 个节点
- 32B 模型：约 6 天，4 个节点
