## 太长不看

这篇博客介绍 [SmolLM](https://huggingface.co/collections/HuggingFaceTB/smollm-models-6695016cad7167254ce15966)——一个最先进的小型模型家族，包含 135M、360M 和 1.7B 三种参数规模，在一个全新的高质量数据集上训练。内容涵盖数据整理、模型评估与使用。

## 引言

人们对能在本地设备上运行的小语言模型兴趣日增。这一趋势既包括蒸馏、量化等压缩大模型的技术，也包括在大规模数据上从零训练小模型的做法。这些路径在大幅降低推理成本、改善用户隐私的同时，催生了全新的应用形态。

微软的 Phi 系列、阿里巴巴的 Qwen2（2B 以下）和 Meta 的 MobileLLM 都证明：设计和训练得当，小模型也能取得亮眼的成绩。但这些模型关于数据整理和训练的大部分细节并未公开。

在这篇博客中，我们兴奋地推出 [SmolLM](https://huggingface.co/collections/HuggingFaceTB/smollm-models-6695016cad7167254ce15966)——一系列最先进的小型语言模型，提供 135M、360M 和 1.7B 三种尺寸。这些模型建立在精心整理的高质量训练语料之上，该语料以 [SmolLM-Corpus](https://huggingface.co/datasets/HuggingFaceTB/smollm-corpus) 之名一同开放。SmolLM Corpus 包含：

- **Cosmopedia v2**：由 Mixtral 生成的合成教科书与故事集合（28B 词元）
- **Python-Edu**：来自 The Stack 的教学型 Python 样例（4B 词元）
- **FineWeb-Edu（去重版）**：来自 FineWeb 的教学型网页样例（220B 词元）

我们的评估表明，在覆盖常识推理与世界知识的多样基准上，SmolLM 模型在各自尺寸档位中都胜过其他模型。下文我们将依次介绍训练语料各子集的整理过程，然后讨论 SmolLM 模型的训练与评估。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled.png)
 *SmolLM 模型在不同推理与常识基准上的评估。*

## 数据整理

### 从 Cosmopedia v1 到 v2

[Cosmopedia v2](https://huggingface.co/datasets/HuggingFaceTB/smollm-corpus) 是 Cosmopedia 的增强版——目前最大的预训练合成数据集，包含超过 3,000 万篇由 Mixtral-8x7B-Instruct-v0.1 生成的教科书、博客文章和故事。大多数样本的生成方式是：让模型围绕特定主题、参考一个被称为"种子样本"的网页来生成内容，如图 1 所示。使用网页样本是为了增加多样性并扩大提示词的范围。更多细节见这篇[博客](https://huggingface.co/blog/cosmopedia)。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%201.png)
 *图 1. 一个 Cosmopedia 提示词示例。*

为了在 v2 中改进数据集，我们尝试了两种策略：

- 用更强的模型配合原有提示词
- 直接优化提示词本身

对于第一种策略，我们实验了 llama3-70B-Instruct、Mixtral-8x22B-Instruct-v0.1 和 Qwen1.5-72B-Chat，但发现用这些替代模型生成的教科书训练出的模型并没有显著提升。因此本节后续聚焦第二种策略：我们如何改进提示词。

#### 寻找更好的主题与种子样本

每个提示词有三个主要组成部分：主题、种子样本和生成风格——后者指定目标读者和我们希望模型生成的内容类型。

为了保证生成质量稳定，种子样本必须与给定主题紧密相关。在 Cosmopedia v1 中，我们对 FineWeb 样本做无监督聚类来同时确定主题和对应的网页样本，如图 2 所示。这种方式有两个主要局限：

- 主题列表反映的是网页/FineWeb 的聚类，虽然全面，但限制了我们对主题的掌控。
- 每个聚类内的网页样本没有进一步过滤，可能混入一些低质量样本。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%202.png)
 *图 2. FineWeb 聚类。*

在 v2 中，我们放弃了无监督聚类，改用一份预定义的 34,000 个主题清单——来自 [BISAC 图书分类法](https://www.bisg.org/complete-bisac-subject-headings-list)，这是一套按主题给图书分类的标准，既全面又偏教育。我们从属于 51 个类别的 5,000 个主题出发，让 Mixtral 为其中某些主题生成子主题。下面是每个类别最终的子主题分布：

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%203.png)
 *图 3. 用于生成提示词的各顶级类别的主题分布。*

定义好主题之后，还需要找到与它们相关的网页。就像用搜索引擎找特定主题的内容一样，我们实现了一个搜索工具，为每个主题检索最相关的页面。我们用 BISAC 类别及其子主题作为查询，在 FineWeb 的 CC-MAIN-2024-10 和 CC-MAIN-2023-50 两个 dump（合计超过 5.2 亿条样本）上运行该工具。每个查询检索 1,000 个页面，确保只取回最相关的内容。部署和运行该搜索工具的代码见[这里](https://github.com/huggingface/cosmopedia/tree/main/fulltext_search)。

最终我们汇集了 34,000 个主题下的 3,400 万个网页。下一步是确定哪种生成风格最有效。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%204.png)
 *图 4. "医疗"类别下的主题及其检索到的样本。*

#### 生成风格

为了确定最有效的生成风格，我们做了消融研究：用 Cosmopedia v1 不同子集的 8B 词元训练 1.8B 模型。对新生的数据，只生成 2B 词元并训练 4 个 epoch 以节省时间（用 Mixtral 生成 2B 词元大约需要 1000 GPU 小时）。我们使用与 [FineWeb 消融模型](https://huggingface.co/spaces/HuggingFaceFW/blogpost-fineweb-v1)相同的训练和评估设置。每个实验用两个不同种子各跑一遍，分数取平均。

我们对比了 Cosmopedia v1 以下几个子集的表现：

- 网页教科书子集
- 故事子集
- Stanford 与 OpenStax 子集

结果发现，基于 Stanford、OpenStax 这类精选来源的主题与种子样本生成的教科书整体表现最好，在 MMLU 和 ARC 基准上优于网页教科书。故事似乎对常识类基准有帮助。在 v2 中实现了新的主题与种子样本检索方式之后，我们用网络种子就能匹配精选来源的表现，证实了新提示词的质量。

接下来我们探索哪种目标读者风格最好。我们用同样的网络教科书提示词，分别面向中学生和大学生生成教科书。结果发现，以中学生为主要读者的教科书训练出的模型，除 MMLU 外在所有基准上都拿到最好分数。这不难解释：多数基准考察的是基础常识和中小学到中级科学知识，而 MMLU 有一部分题目需要高级知识和专业经验。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%205.png)
 *面向不同读者的教科书评估。*

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%206.png)
 *面向不同读者的教科书评估。*

在 v2 中，我们决定 40% 的内容面向中学生，30% 面向大学生，其余 30% 混合其他读者与风格——包括沿用 Cosmopedia v1 的一些子集，如故事和基于 Stanford 课程的教科书。此外，我们还基于 AutoMathText 数据集的 Python 种子样本生成了 10 亿词元的代码教科书。

最终我们产出了 3,900 万篇合成文档，共 28B 词元，涵盖教科书、故事、文章和代码，读者类型多样，主题超过 34,000 个。

### FineWeb-Edu

FineWeb-Edu 是我们几个月前随 FineWeb [技术报告](https://huggingface.co/spaces/HuggingFaceFW/blogpost-fineweb-v1)发布的数据集。它从 🍷 FineWeb 数据集中筛选出**1.3T 词元**的教育类网页。

我们利用 Llama3-70B-Instruct 生成的标注，开发了一个[**教育质量分类器**](https://huggingface.co/HuggingFaceFW/fineweb-edu-classifier)，然后用它只保留 FineWeb 中最具教育意义的网页。FineWeb-Edu 在流行基准上优于 FineWeb，展示了在合成数据上训练分类器的威力。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%207.png)
 *FineWeb-Edu 与其他开放网络数据集的对比。*

在 SmolLM-Corpus 中，我们收录了 FineWeb 去重后的 220B 词元。

### Stack-Edu-Python

我们把 FineWeb-Edu 的思路用到了代码上。我们用 Llama3 标注了 The Stack 数据集中的 50 万个 Python 样本，并用与 FineWeb-Edu 分类器相同的配方训练了一个[教育代码分类器](https://huggingface.co/HuggingFaceTB/python-edu-scorer)。然后对该分类器应用到 StarCoder 模型训练语料的 Python 子集。在可用的 40B Python 词元中，我们只保留得分 4 分及以上的样本，最终得到精炼后的 4B 词元数据集。

下图把 Python-Edu 与未经过滤的 Python 代码、以及更宽松的 3 分阈值做了对比。可以看到，在 Python-Edu 上训练的模型收敛速度比在未过滤 Python 代码上训练的模型快 3 倍以上——仅需 12B 词元就达到了 16% 的 pass@1。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%208.png)
 *Python-Edu 与未过滤 Python 代码的对比。*

## 训练

SmolLM 模型有三种尺寸，训练数据配比如下：

- 135M 和 360M 模型：各在 [SmolLM-Corpus](https://huggingface.co/datasets/HuggingFaceTB/smollm-corpus) 的 600B 词元上训练
- 1.7B 模型：在 SmolLM-Corpus 的 1T 词元上训练

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%209.png)
 *SmolLM 模型的训练配比。*

### 超参数选择

我们采用梯形（trapezoidal）学习率调度器，冷却阶段占总训练时长的 20%。需要说明，该调度的原始实验是在更小规模上做的，我们针对自己的更大模型做了适配。

135M 和 360M 模型的架构采用了与 [MobileLLM](https://arxiv.org/abs/2402.14905) 类似的设计，引入分组查询注意力（GQA），并且重深度轻宽度。1.7B 模型则使用更传统的架构。三个模型都使用词嵌入绑定（embedding tying），上下文长度为 2048 词元。借助一些长上下文微调，这个上下文长度还可以进一步扩展。

### 实验

梯形调度器的一个好处是可以缩短尺度定律（scaling law）实验所需的时间，正如 [Hägele et al.](https://arxiv.org/pdf/2405.18392) 所示。我们用最小模型 SmolLM-125M 做了一个小型尺度定律研究来说明这一点。我们观察到，训练时间更长时性能持续提升，甚至超过 Chinchilla 最优点。因此我们决定 1.7B 模型训练 1 万亿词元，135M 和 360M 模型训练 600B 词元——因为对这两个小模型来说，400B 词元之后部分基准的收益增长开始放缓。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%2011.png)
 *在不同词元数上训练的 125M SmolLM 模型评估。*

我们尝试在冷却阶段加入指令数据集并上采样精选的 Cosmopedia 子集，但没有看到显著收益。这可能是因为主数据配比本身已经质量很高，这些改动的影响有限。

为了跟踪训练进度，我们对两个最小的模型每 2B 词元评估一次。下图展示了它们在若干基准上的表现：

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%2012.png)
 *SmolLM-135M 与 SmolLM-360M 在不同基准上的中间评估。*

## 评估

本节评估不同参数规模的 SmolLM 模型，并与各自档位中最好的模型对比。我们在覆盖常识推理与世界知识的多样基准上评估。所有模型使用统一的评估[配置](https://github.com/huggingface/cosmopedia/tree/main/evaluation)（基于 `lighteval` 库）。HumanEval 则使用 [bigcode-evaluation-harness](We use temperature 0.2, top-p 0.95 with 20 samples.)，温度 0.2、top-p 0.95，采样 20 次。对未公开的 MobileLLM，我们尽可能采用论文中报告的数字。

我们发现：

- SmolLM-135M 胜过当前 200M 参数以下的最佳模型 MobileLM-125M——尽管它只训练了 600B 词元，而 MobileLM 用了 1T 词元。
- SmolLM-360M 超越了所有 500M 参数以下的模型——尽管它的参数更少、训练词元也不足万亿（600B），而 MobileLM-350M 和 Qwen2-500M 不然。
- SmolLM-1.7B 击败了所有 2B 参数以下的其他模型，包括微软的 Phi1.5、MobileLM-1.5B 和 Qwen2-1.5B。
- SmolLM-1.7B 展现出强劲的 Python 编码能力，pass@1 达 24。注意我们对 Qwen2-1.5B 的评测分数与 Qwen 团队报告的 31.1 pass@1 不同。我们使用温度 0.2、top-p 0.95，采样 20 次。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%2014.png)
 *SmolLM 模型与其他 SLM 的对比。除 MobieLLM（未公开）外，所有模型均在相同设置下评估。*

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/image.png)
 *SmolLM 模型在 HumanEval 上的评估。*

我们还使用公开的、许可宽松的指令数据集对模型做了指令微调。三个模型都在 [WebInstructSub 数据集](https://huggingface.co/datasets/TIGER-Lab/WebInstructSub)的宽松子集（与 StarCoder2-Self-OSS-Instruct 合并）上训练一个 epoch。随后进行一轮 epoch 的 DPO（直接偏好优化）：135M 和 1.7B 模型用 [HelpSteer](https://huggingface.co/datasets/nvidia/HelpSteer)，360M 模型用 [argilla/dpo-mix-7k](https://huggingface.co/datasets/argilla/dpo-mix-7k)。训练参数遵循 [alignment handbook](https://github.com/huggingface/alignment-handbook/blob/main/recipes/zephyr-7b-gemma/README.md) 中 Zephyr-Gemma 配方，但把 SFT（监督微调）学习率调整为 3e-4。

下表展示 SmolLM-Instruct 与其他模型在 IFEval 基准（Prompt Strict Accuracy）上的表现。Qwen2-1.5B-Instruct 得分最高，为 29.94；只使用公开的宽松数据集，SmolLM-Instruct 系列在模型尺寸与性能之间提供了很好的平衡。

## 如何本地运行？

我们的模型专为小巧设计，可以在各种硬件配置上本地运行。作为参照，iPhone 15 有 6GB DRAM，iPhone 15 Pro 有 8GB。这些内存需求让我们的模型适合部署从手机到笔记本的广泛设备。我们对三种尺寸的内存占用做了基准测试：

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/Untitled%2013.png)
 *SmolLM 模型的内存占用。*

除了 transformers 检查点，我们还发布了 ONNX 检查点，并计划提供兼容 `llama.cpp` 的 GGUF 版本。SmolLM-135M 和 SmolLM-360M 的 WebGPU 演示在 [https://huggingface.co/spaces/HuggingFaceTB/SmolLM-135M-Instruct-WebGPU](https://huggingface.co/spaces/HuggingFaceTB/SmolLM-135M-Instruct-WebGPU) 和 [https://huggingface.co/spaces/HuggingFaceTB/SmolLM-360M-Instruct-WebGPU](https://huggingface.co/spaces/HuggingFaceTB/SmolLM-360M-Instruct-WebGPU)。

## 结论

在这篇博客中，我们介绍了 SmolLM 模型——一个最先进的小型 LLM 新家族。它们证明了小语言模型在高质量数据集上高效训练即可取得高性能，在尺寸与性能之间提供有力的平衡。
