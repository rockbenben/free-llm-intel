# 没错，Transformers 适合时间序列预测（+ Autoformer）

作者：Eli Simhayev（elisim，客座作者）、Kashif Rasul（kashif）、Niels Rogge（nielsr）

## 引言

几个月前，我们介绍了 [Informer](https://huggingface.co/blog/informer) 模型（[Zhou, Haoyi, et al., 2021](https://arxiv.org/abs/2012.07436)），这是一个获得 AAAI 2021 最佳论文奖的时间序列 Transformer，我们还给出了用 Informer 做多变量概率预测的示例。在这篇文章里，我们讨论这样一个问题：[Are Transformers Effective for Time Series Forecasting?](https://arxiv.org/abs/2205.13504)（AAAI 2023）。正如我们将看到的，答案是肯定的。

首先，我们会给出实证证据，证明 **Transformers 确实适合时间序列预测**。我们的对比显示，被称为 *DLinear* 的简单线性模型并不像论文声称的那样优于 Transformers。在与线性模型相同设置下、参数量相当的 Transformer 模型对比中，Transformer 模型在我们关注的测试集指标上表现更好。之后，我们将介绍 *Autoformer* 模型（[Wu, Haixu, et al., 2021](https://arxiv.org/abs/2106.13008)），它是在 Informer 之后发表于 NeurIPS 2021 的模型。Autoformer 模型[现已提供](https://huggingface.co/docs/transformers/main/en/model_doc/autoformer)于 🤗 Transformers。最后，我们会讨论 *DLinear* 模型，它是一个使用了 Autoformer 分解层的简单前馈网络。DLinear 首次出现在 [Are Transformers Effective for Time Series Forecasting?](https://arxiv.org/abs/2205.13504) 中，并被声称在时间序列预测上超过了基于 Transformer 的模型。

## 基准测试 - Transformers vs. DLinear

在近期发表于 AAAI 2023 的论文 [Are Transformers Effective for Time Series Forecasting?](https://arxiv.org/abs/2205.13504) 中，作者声称 Transformers 对时间序列预测并不有效。他们把基于 Transformer 的模型与一个简单线性模型对比，称之为 *DLinear*。DLinear 使用了 Autoformer 模型的分解层，我们将在本文后面介绍。作者声称 DLinear 在时间序列预测上优于基于 Transformer 的模型。真是这样吗？我们来验证一下。

| 数据集 | Autoformer（单变量）MASE | DLinear MASE |
| --- | --- | --- |
| `Traffic` | 0.910 | 0.965 |
| `Exchange-Rate` | 1.087 | 1.690 |
| `Electricity` | 0.751 | 0.831 |

上表展示了 Autoformer 与 DLinear 在论文使用的三个数据集上的对比结果。
结果显示，Autoformer 在全部三个数据集上都优于 DLinear。

接下来，我们将介绍新的 Autoformer 模型以及 DLinear 模型。我们将演示如何在上面表格中的 Traffic 数据集上对它们进行比较，并对得到的结果给出解释。

**TL;DR：** 简单线性模型虽然在某些场景有优势，但在单变量设定下，它没有能力像 Transformer 这样更复杂的模型那样纳入协变量。

## Autoformer - 内部原理

Autoformer 建立在把时间序列分解为季节性和趋势-周期成分的传统方法之上。这是通过引入一个*分解层（Decomposition Layer）*实现的，它增强了模型准确捕捉这些成分的能力。此外，Autoformer 引入了一种创新的自相关机制，取代了标准 Transformer 中的自注意力。该机制让模型能够利用注意力中基于周期的依赖关系，从而提升整体性能。

在后面的章节中，我们将深入 Autoformer 的两个核心贡献：*分解层*和*注意力（自相关）机制*，并提供代码示例来说明这些组件在 Autoformer 架构中如何工作。

### 分解层

分解早就是时间序列分析中流行的方法，但在 Autoformer 论文出现之前，它并没有被广泛整合进深度学习模型。在简要解释这一概念后，我们将展示这个想法如何通过 PyTorch 代码应用在 Autoformer 中。

#### 时间序列的分解

在时间序列分析中，[分解](https://en.wikipedia.org/wiki/Decomposition_of_time_series)是把时间序列拆分为三种系统性成分的方法：趋势-周期、季节变化和随机波动。趋势成分代表时间序列的长期走向，可以随时间递增、递减或保持稳定。季节成分代表时间序列中重复出现的模式，例如年度或季度周期。最后是随机成分（有时称"不规则"成分），代表数据中无法用趋势或季节成分解释的随机噪声。

分解的两种主要类型是加性分解和乘性分解，在 [优秀的 statsmodels 库](https://www.statsmodels.org/dev/generated/statsmodels.tsa.seasonal.seasonal_decompose.html)中都有实现。通过把时间序列分解为这些成分，我们可以更好地理解和建模数据背后的潜在模式。

但我们如何把分解整合进 Transformer 架构？我们来看 Autoformer 是怎么做的。

如上文的 Autoformer 架构图所示，Autoformer 把分解模块作为模型的内部运算。可以看到，编码器和解码器都使用一个分解模块来聚合趋势-周期部分，并逐级从序列中提取季节部分。自 Autoformer 发布以来，内部分解这一概念已经证明了它的实用性，随后被 FEDformer（[Zhou, Tian, et al., ICML 2022](https://arxiv.org/abs/2201.12740)）和 DLinear（[Zeng, Ailing, et al., AAAI 2023](https://arxiv.org/abs/2205.13504)）等其他时间序列论文采纳，凸显了它在时间序列建模中的重要性。

现在，让我们形式化地定义分解层：

对于长度为 LLL 的输入序列 X∈RL×d\mathcal{X} \in \mathbb{R}^{L \times d}X∈RL×d，分解层返回按如下定义的 Xtrend,Xseasonal\mathcal{X}_\textrm{trend}, \mathcal{X}_\textrm{seasonal}Xtrend​,Xseasonal​：

Xtrend=AvgPool(Padding(X))Xseasonal=X−Xtrend \mathcal{X}_\textrm{trend} = \textrm{AvgPool(Padding(} \mathcal{X} \textrm{))} \\ \mathcal{X}_\textrm{seasonal} = \mathcal{X} - \mathcal{X}_\textrm{trend} Xtrend​=AvgPool(Padding(X))Xseasonal​=X−Xtrend​

其在 PyTorch 中的实现：

```
import torch
from torch import nn

class DecompositionLayer(nn.Module):
    """
    Returns the trend and the seasonal parts of the time series.
    """

    def __init__(self, kernel_size):
        super().__init__()
        self.kernel_size = kernel_size
        self.avg = nn.AvgPool1d(kernel_size=kernel_size, stride=1, padding=0) # moving average 

    def forward(self, x):
        """Input shape: Batch x Time x EMBED_DIM"""
        # padding on the both ends of time series
        num_of_pads = (self.kernel_size - 1) // 2
        front = x[:, 0:1, :].repeat(1, num_of_pads, 1)
        end = x[:, -1:, :].repeat(1, num_of_pads, 1)
        x_padded = torch.cat([front, x, end], dim=1)

        # calculate the trend and seasonal part of the series
        x_trend = self.avg(x_padded.permute(0, 2, 1)).permute(0, 2, 1)
        x_seasonal = x - x_trend
        return x_seasonal, x_trend
```

可以看到，实现相当简单，并且可以用于其他模型，我们接下来在 DLinear 中就会看到。现在来讲第二个贡献——*注意力（自相关）机制*。

### 注意力（自相关）机制

| --- |
| 标准自注意力 vs 自相关机制，来自[论文](https://arxiv.org/abs/2106.13008) |

除了分解层，Autoformer 还采用了一种新颖的自相关机制，无缝替换了自注意力。在[标准 Time Series Transformer](https://huggingface.co/docs/transformers/model_doc/time_series_transformer) 中，注意力权重在时域计算、逐点聚合；而在如上图所示的 Autoformer 中，它们在频域计算（使用[快速傅里叶变换](https://en.wikipedia.org/wiki/Fast_Fourier_transform)）并按时间延迟聚合。

在后面的小节中，我们会详细深入这些主题并用代码示例说明。

#### 频域注意力

| [![autoformer_autocorrelation_only_attention](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/148_autoformer/autoformer_autocorrelation_only_attention.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/148_autoformer/autoformer_autocorrelation_only_attention.png) |
| --- |
| 使用 FFT 在频域计算注意力权重，来自[论文](https://arxiv.org/abs/2106.13008) |

理论上，给定时间延迟 τ\tauτ，单个离散变量 yyy 的*自相关*用于衡量该变量在 ttt 时刻的当前值与其在 t−τt-\tau t−τ 时刻历史值之间的"关系"（皮尔逊相关）：

Autocorrelation(τ)=Corr(yt,yt−τ) \textrm{Autocorrelation}(\tau) = \textrm{Corr}(y_t, y_{t-\tau}) Autocorrelation(τ)=Corr(yt​,yt−τ​)

Autoformer 利用自相关，从 queries 和 keys 中提取基于频率的依赖关系，而不是做它们之间的标准点积。你可以把它理解为自注意力中 QKTQK^TQKT 项的替代品。

实践中，queries 和 keys 在**所有延迟**上的自相关通过 FFT 一次性算出。这样一来，自相关机制达到了 O(Llog⁡L)O(L \log L)O(LlogL) 的时间复杂度（LLL 为输入时间长度），与 [Informer 的 ProbSparse 注意力](https://huggingface.co/blog/informer#probsparse-attention)类似。注意，用 FFT 计算自相关的理论基于[维纳-辛钦定理](https://en.wikipedia.org/wiki/Wiener%E2%80%93Khinchin_theorem)，这超出了本篇博客的讨论范围。

现在，我们可以看 PyTorch 代码了：

```
import torch 

def autocorrelation(query_states, key_states):
    """
    Computes autocorrelation(Q,K) using `torch.fft`. 
    Think about it as a replacement for the QK^T in the self-attention.
    
    Assumption: states are resized to same shape of [batch_size, time_length, embedding_dim].
    """
    query_states_fft = torch.fft.rfft(query_states, dim=1)
    key_states_fft = torch.fft.rfft(key_states, dim=1)
    attn_weights = query_states_fft * torch.conj(key_states_fft)
    attn_weights = torch.fft.irfft(attn_weights, dim=1)  
    
    return attn_weights
```

很简单吧！😎 请注意，这只是 `autocorrelation(Q,K)` 的部分实现，完整实现可以在 🤗 Transformers 中找到。

接下来，我们看看如何按时间延迟把 `attn_weights` 与 values 聚合，这个过程称为*时间延迟聚合*。

#### 时间延迟聚合

| [![autoformer_autocorrelation_only_aggregation](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/148_autoformer/autoformer_autocorrelation_only_aggregation.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/148_autoformer/autoformer_autocorrelation_only_aggregation.png) |
| --- |
| 按时间延迟聚合，来自 [Autoformer 论文](https://arxiv.org/abs/2106.13008) |

把自相关（记作 `attn_weights`）看作 RQ,K\mathcal{R_{Q,K}}RQ,K​。问题是：如何把这些 RQ,K(τ1),RQ,K(τ2),...,RQ,K(τk)\mathcal{R_{Q,K}}(\tau_1), \mathcal{R_{Q,K}}(\tau_2), ..., \mathcal{R_{Q,K}}(\tau_k)RQ,K​(τ1​),RQ,K​(τ2​),...,RQ,K​(τk​) 与 V\mathcal{V}V 聚合？在标准自注意力机制中，这个聚合通过点积完成。但在 Autoformer 中我们用了不同的做法。首先，通过对每个时间延迟 τ1,τ2,...τk\tau_1, \tau_2, ... \tau_kτ1​,τ2​,...τk​ 计算其对应取值来对齐 V\mathcal{V}V，也就是所谓的 *Rolling*（滚动）。然后在对齐后的 V\mathcal{V}V 与自相关之间做逐元素相乘。在上面给出的图中，左侧展示的是按时间延迟滚动 V\mathcal{V}V，右侧展示的是与自相关做逐元素相乘。

可以用以下公式概括：

τ1,τ2,...τk=arg Top-k(RQ,K(τ))R^Q,K(τ1),R^Q,K(τ2),...,R^Q,K(τk)=Softmax(RQ,K(τ1),RQ,K(τ2),...,RQ,K(τk))Autocorrelation-Attention=∑i=1kRoll(V,τi)⋅R^Q,K(τi) \tau_1, \tau_2, ... \tau_k = \textrm{arg Top-k}(\mathcal{R_{Q,K}}(\tau)) \\ \hat{\mathcal{R}}\mathcal{_{Q,K}}(\tau _1), \hat{\mathcal{R}}\mathcal{_{Q,K}}(\tau _2), ..., \hat{\mathcal{R}}\mathcal{_{Q,K}}(\tau _k) = \textrm{Softmax}(\mathcal{R_{Q,K}}(\tau _1), \mathcal{R_{Q,K}}(\tau_2), ..., \mathcal{R_{Q,K}}(\tau_k)) \\ \textrm{Autocorrelation-Attention} = \sum_{i=1}^k \textrm{Roll}(\mathcal{V}, \tau_i) \cdot \hat{\mathcal{R}}\mathcal{_{Q,K}}(\tau _i) τ1​,τ2​,...τk​=arg Top-k(RQ,K​(τ))R^Q,K​(τ1​),R^Q,K​(τ2​),...,R^Q,K​(τk​)=Softmax(RQ,K​(τ1​),RQ,K​(τ2​),...,RQ,K​(τk​))Autocorrelation-Attention=i=1∑k​Roll(V,τi​)⋅R^Q,K​(τi​)

就这样！注意，kkk 由一个名为 `autocorrelation_factor` 的超参数控制（类似于 [Informer](https://huggingface.co/blog/informer) 中的 `sampling_factor`），并且 softmax 在相乘之前应用于自相关。

现在我们可以看最终的代码了：

```
import torch
import math

def time_delay_aggregation(attn_weights, value_states, autocorrelation_factor=2):
    """
    Computes aggregation as value_states.roll(delay) * top_k_autocorrelations(delay).
    The final result is the autocorrelation-attention output.
    Think about it as a replacement of the dot-product between attn_weights and value states.
    
    The autocorrelation_factor is used to find top k autocorrelations delays.
    Assumption: value_states and attn_weights shape: [batch_size, time_length, embedding_dim]
    """
    bsz, num_heads, tgt_len, channel = ...
    time_length = value_states.size(1)
    autocorrelations = attn_weights.view(bsz, num_heads, tgt_len, channel)

    # find top k autocorrelations delays
    top_k = int(autocorrelation_factor * math.log(time_length))
    autocorrelations_mean = torch.mean(autocorrelations, dim=(1, -1))  # bsz x tgt_len
    top_k_autocorrelations, top_k_delays = torch.topk(autocorrelations_mean, top_k, dim=1)

    # apply softmax on the channel dim
    top_k_autocorrelations = torch.softmax(top_k_autocorrelations, dim=-1)  # bsz x top_k

    # compute aggregation: value_states.roll(delay) * top_k_autocorrelations(delay)
    delays_agg = torch.zeros_like(value_states).float()  # bsz x time_length x channel
    for i in range(top_k):
        value_states_roll_delay = value_states.roll(shifts=-int(top_k_delays[i]), dims=1)
        top_k_at_delay = top_k_autocorrelations[:, i]
        # aggregation
        top_k_resized = top_k_at_delay.view(-1, 1, 1).repeat(num_heads, tgt_len, channel)
        delays_agg += value_states_roll_delay * top_k_resized

    attn_output = delays_agg.contiguous()
    return attn_output
```

完成了！Autoformer 模型[现已提供](https://huggingface.co/docs/transformers/main/en/model_doc/autoformer)于 🤗 Transformers 库，直接通过 `AutoformerModel` 调用。

我们对该模型的策略是：展示单变量 Transformer 模型相对于 DLinear 模型的性能——正如接下来将展示的，DLinear 本质上是单变量的。我们还将展示在相同数据上训练的*两个*多变量 Transformer 模型的结果。

## DLinear - 内部原理

实际上，DLinear 概念上很简单：就是一个全连接层加上 Autoformer 的 `DecompositionLayer`。它使用上面的 `DecompositionLayer` 把输入时间序列分解为残差（季节性）部分和趋势部分。在前向传播中，每个部分各自经过一个独立的线性层，把信号投影到合适大小的 `prediction_length` 输出。在点预测模型中，最终输出是两个对应输出之和：

```
def forward(self, context):
    seasonal, trend = self.decomposition(context)
    seasonal_output = self.linear_seasonal(seasonal)
    trend_output = self.linear_trend(trend)
    return seasonal_output + trend_output
```

在概率设定下，可以通过 `linear_seasonal` 和 `linear_trend` 层把长度为 context length 的数组投影到 `prediction-length * hidden` 维度。将得到的输出相加后 reshape 为 `(prediction_length, hidden)`。最后，一个概率化预测头把维度为 `hidden` 的隐表示映射到某个分布的参数上。

在我们的基准测试中，使用的是 [GluonTS](https://github.com/awslabs/gluonts) 中 DLinear 的实现。

## 定义变换

接下来定义数据的变换，特别是时间特征（基于数据集的或通用的）的创建。

```
        remove_field_names.append(FieldName.FEAT_STATIC_REAL)
    if config.num_dynamic_real_features == 0:
        remove_field_names.append(FieldName.FEAT_DYNAMIC_REAL)
    if config.num_static_categorical_features == 0:
        remove_field_names.append(FieldName.FEAT_STATIC_CAT)

    return Chain(
        # step 1: remove static/dynamic fields if not specified
        [RemoveFields(field_names=remove_field_names)]
        # step 2: convert the data to NumPy (potentially not needed)
        + (
            [
                AsNumpyArray(
                    field=FieldName.FEAT_STATIC_CAT,
                    expected_ndim=1,
                    dtype=int,
                )
            ]
            if config.num_static_categorical_features > 0
            else []
        )
        + (
            [
                AsNumpyArray(
                    field=FieldName.FEAT_STATIC_REAL,
                    expected_ndim=1,
                )
            ]
            if config.num_static_real_features > 0
            else []
        )
        + [
            AsNumpyArray(
                field=FieldName.TARGET,
                # we expect an extra dim for the multivariate case:
                expected_ndim=1 if config.input_size == 1 else 2,
            ),
            # step 3: handle the NaN's by filling in the target with zero
            # and return the mask (which is in the observed values)
            # true for observed values, false for nan's
            # the decoder uses this mask (no loss is incurred for unobserved values)
            # see loss_weights inside the xxxForPrediction model
            AddObservedValuesIndicator(
                target_field=FieldName.TARGET,
                output_field=FieldName.OBSERVED_VALUES,
            ),
            # step 4: add temporal features based on freq of the dataset
            # these serve as positional encodings
            AddTimeFeatures(
                start_field=FieldName.START,
                target_field=FieldName.TARGET,
                output_field=FieldName.FEAT_TIME,
                time_features=time_features_from_frequency_str(freq),
                pred_length=config.prediction_length,
            ),
            # step 5: add another temporal feature (just a single number)
            # tells the model where in the life the value of the time series is
            # sort of running counter
            AddAgeFeature(
                target_field=FieldName.TARGET,
                output_field=FieldName.FEAT_AGE,
                pred_length=config.prediction_length,
                log_scale=True,
            ),
            # step 6: vertically stack all the temporal features into the key FEAT_TIME
            VstackFeatures(
                output_field=FieldName.FEAT_TIME,
                input_fields=[FieldName.FEAT_TIME, FieldName.FEAT_AGE]
                + (
                    [FieldName.FEAT_DYNAMIC_REAL]
                    if config.num_dynamic_real_features > 0
                    else []
                ),
            ),
            # step 7: rename to match HuggingFace names
            RenameFields(
                mapping={
                    FieldName.FEAT_STATIC_CAT: "static_categorical_features",
                    FieldName.FEAT_STATIC_REAL: "static_real_features",
                    FieldName.FEAT_TIME: "time_features",
                    FieldName.TARGET: "values",
                    FieldName.OBSERVED_VALUES: "observed_mask",
                }
            ),
        ]
    )
```

## 定义 `InstanceSplitter`

针对训练/验证/测试，我们接着创建用于从数据集中采样窗口的 `InstanceSplitter`（记住，出于时间和内存限制，我们不能把全部历史值都喂给模型）。

实例采样器会从数据中随机采样 `context_length` 大小及其后的 `prediction_length` 大小的窗口，并为对应窗口中 `time_series_fields` 里的时间键添加 `past_` 或 `future_` 前缀。实例采样器可以配置为三种模式：

- `mode="train"`：从传给它的数据集（训练集）中随机采样 context 和 prediction 长度窗口
- `mode="validation"`：从传给它的数据集中采样最后一个 context 长度窗口和 prediction 窗口（用于回测或验证似然计算）
- `mode="test"`：只采样最后一个 context 长度窗口（用于预测场景）

```
from gluonts.transform import InstanceSplitter
from gluonts.transform.sampler import InstanceSampler
from typing import Optional


def create_instance_splitter(
    config: PretrainedConfig,
    mode: str,
    train_sampler: Optional[InstanceSampler] = None,
    validation_sampler: Optional[InstanceSampler] = None,
) -> Transformation:
    assert mode in ["train", "validation", "test"]

    instance_sampler = {
        "train": train_sampler
        or ExpectedNumInstanceSampler(
            num_instances=1.0, min_future=config.prediction_length
        ),
        "validation": validation_sampler
        or ValidationSplitSampler(min_future=config.prediction_length),
        "test": TestSplitSampler(),
    }[mode]

    return InstanceSplitter(
        target_field="values",
        is_pad_field=FieldName.IS_PAD,
        start_field=FieldName.START,
        forecast_start_field=FieldName.FORECAST_START,
        instance_sampler=instance_sampler,
        past_length=config.context_length + max(config.lags_sequence),
        future_length=config.prediction_length,
        time_series_fields=["time_features", "observed_mask"],
    )
```

## 创建 PyTorch DataLoader

接下来创建 PyTorch DataLoader，它让我们得到（输入，输出）对的批次——也就是（`past_values`, `future_values`）。

```
from typing import Iterable

import torch
from gluonts.itertools import Cyclic, Cached
from gluonts.dataset.loader import as_stacked_batches


def create_train_dataloader(
    config: PretrainedConfig,
    freq,
    data,
    batch_size: int,
    num_batches_per_epoch: int,
    shuffle_buffer_length: Optional[int] = None,
    cache_data: bool = True,
    **kwargs,
) -> Iterable:
    PREDICTION_INPUT_NAMES = [
        "past_time_features",
        "past_values",
        "past_observed_mask",
        "future_time_features",
    ]
    if config.num_static_categorical_features > 0:
        PREDICTION_INPUT_NAMES.append("static_categorical_features")

    if config.num_static_real_features > 0:
        PREDICTION_INPUT_NAMES.append("static_real_features")

    TRAINING_INPUT_NAMES = PREDICTION_INPUT_NAMES + [
        "future_values",
        "future_observed_mask",
    ]

    transformation = create_transformation(freq, config)
    transformed_data = transformation.apply(data, is_train=True)
    if cache_data:
        transformed_data = Cached(transformed_data)

    # we initialize a Training instance
    instance_splitter = create_instance_splitter(config, "train")

    # the instance splitter will sample a window of
    # context length + lags + prediction length (from the 366 possible transformed time series)
    # randomly from within the target time series and return an iterator.
    stream = Cyclic(transformed_data).stream()
    training_instances = instance_splitter.apply(stream)

    return as_stacked_batches(
        training_instances,
        batch_size=batch_size,
        shuffle_buffer_length=shuffle_buffer_length,
        field_names=TRAINING_INPUT_NAMES,
        output_type=torch.tensor,
        num_batches_per_epoch=num_batches_per_epoch,
    )

def create_backtest_dataloader(
    config: PretrainedConfig,
    freq,
    data,
    batch_size: int,
    **kwargs,
):
    PREDICTION_INPUT_NAMES = [
        "past_time_features",
        "past_values",
        "past_observed_mask",
        "future_time_features",
    ]
    if config.num_static_categorical_features > 0:
        PREDICTION_INPUT_NAMES.append("static_categorical_features")

    if config.num_static_real_features > 0:
        PREDICTION_INPUT_NAMES.append("static_real_features")

    transformation = create_transformation(freq, config)
    transformed_data = transformation.apply(data)

    # we create a Validation Instance splitter which will sample the very last
    # context window seen during training only for the encoder.
    instance_sampler = create_instance_splitter(config, "validation")

    # we apply the transformations in train mode
    testing_instances = instance_sampler.apply(transformed_data, is_train=True)

    return as_stacked_batches(
        testing_instances,
        batch_size=batch_size,
        output_type=torch.tensor,
        field_names=PREDICTION_INPUT_NAMES,
    )

def create_test_dataloader(
    config: PretrainedConfig,
    freq,
    data,
    batch_size: int,
    **kwargs,
):
    PREDICTION_INPUT_NAMES = [
        "past_time_features",
        "past_values",
        "past_observed_mask",
        "future_time_features",
    ]
    if config.num_static_categorical_features > 0:
        PREDICTION_INPUT_NAMES.append("static_categorical_features")

    if config.num_static_real_features > 0:
        PREDICTION_INPUT_NAMES.append("static_real_features")

    transformation = create_transformation(freq, config)
    transformed_data = transformation.apply(data, is_train=False)

    # We create a test Instance splitter to sample the very last
    # context window from the dataset provided.
    instance_sampler = create_instance_splitter(config, "test")

    # We apply the transformations in test mode
    testing_instances = instance_sampler.apply(transformed_data, is_train=False)
    
    return as_stacked_batches(
        testing_instances,
        batch_size=batch_size,
        output_type=torch.tensor,
        field_names=PREDICTION_INPUT_NAMES,
    )
```

在推理时，我们使用模型的 `generate()` 方法，从训练集中每条时间序列的最后一个上下文窗口出发，预测未来 `prediction_length` 步。

```
from accelerate import Accelerator

accelerator = Accelerator()

forecasts_ = []
for batch in test_dataloader:
    outputs = model.generate(
        static_categorical_features=batch["static_categorical_features"].to(device)
        if config.num_static_categorical_features > 0
        else None,
        static_real_features=batch["static_real_features"].to(device)
        if config.num_static_real_features > 0
        else None,
        past_time_features=batch["past_time_features"].to(device),
        past_values=batch["past_values"].to(device),
        future_time_features=batch["future_time_features"].to(device),
        past_observed_mask=batch["past_observed_mask"].to(device),
    )
    forecasts_.append(outputs.sequences.cpu().numpy())
```

模型输出一个形状为 (`batch_size`, `number of samples`, `prediction length`, `input_size`) 的张量。

在本例中，对测试 DataLoader 批次（回顾上文，批次大小为 `64`）里的每条时间序列，我们得到未来 `24` 小时的 `100` 个可能取值：

`traffic` 数据集在工作日和周末之间的传感器模式存在分布漂移。那这里发生了什么？由于 DLinear 模型没有能力纳入协变量——特别是任何日期时间特征——我们给它的上下文窗口没有足够信息来判断预测目标属于周末还是工作日。因此模型会预测更常见的模式，也就是工作日，导致在周末上的表现更差。当然，如果给它更大的上下文窗口，线性模型也能发现周周期模式，但数据里可能还有月度或季度模式，那就需要越来越大的上下文。

## 结论

基于 Transformer 的模型与上面的线性基线相比如何？我们训练的各模型的测试集 MASE 指标如下：

| 数据集 | Transformer（单变量） | Transformer（多变量） | Informer（单变量） | Informer（多变量） | Autoformer（单变量） | DLinear |
| --- | --- | --- | --- | --- | --- | --- |
| `Traffic` | **0.876** | 1.046 | 0.924 | 1.131 | 0.910 | 0.965 |

可以看到，我们去年引入的[标准 Transformer](https://huggingface.co/docs/transformers/model_doc/time_series_transformer) 在这里取得了最好的结果。其次，多变量模型通常*比*单变量模型差，原因是估计跨序列相关性/关系的难度较大。这些估计带来的额外方差往往会损害预测结果，或者模型会学到虚假相关。像 [CrossFormer](https://openreview.net/forum?id=vSVLM2j9eie)（ICLR 23）和 [CARD](https://arxiv.org/abs/2305.12095) 这样的新论文正试图解决 Transformer 模型中的这一问题。多变量模型在海量数据上训练时表现良好，但与单变量模型相比——尤其在较小的开放数据集上——单变量模型往往提供更好的指标。把线性模型与同等规模的单变量 Transformer（或事实上任何其他神经单变量模型）对比，通常会得到更好的性能。

总之，在时间序列预测方面，Transformers 绝对谈不上过时！不过，大规模数据集的可用性对于充分发挥其潜力至关重要。与 CV 和 NLP 不同，时间序列领域缺乏公开可访问的大规模数据集。大多数现有的时间序列预训练模型都是在 [UCR 和 UEA](https://www.timeseriesclassification.com/) 等档案库的小样本上训练的，这些库只有几千甚至几百个样本。尽管这些基准数据集对时间序列社区的进展功不可没，但它们有限的样本量和不通用性给深度学习预训练模型带来了挑战。

因此，开发大规模、通用的时间序列数据集（类似 CV 中的 ImageNet）至关重要。构建这样的数据集将有力推动专门面向时间序列分析的预训练模型的进一步研究，并提高预训练模型在时间序列预测中的适用性。
