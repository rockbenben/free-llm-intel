## 推测解码

[推测解码（Speculative decoding）](https://arxiv.org/abs/2211.17192)是一种流行的技术，可在保持大语言模型准确率的同时加速推理。如下图所示，推测解码把生成过程拆成两个阶段。第一阶段，一个快速但欠准确的*草稿（draft）*模型（又称辅助模型，assistant）自回归地生成一串 token。第二阶段，一个大而更准确的*目标（target）*模型对生成的草稿 token 做并行验证。这让目标模型能在一次前向传播中产出多个 token，从而加速自回归解码。推测解码的成功在很大程度上取决于*推测步长（speculation lookahead，SL）*——即草稿模型每轮迭代产生的 token 数。实践中，SL 要么取静态值、要么基于启发式规则，两者都不是榨取推理最大性能的最优解。

![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/dynamic_speculation_lookahead/spec_dec_diagram.png)
 *推测解码的一轮迭代。*

## 动态推测解码

[Transformers🤗](https://github.com/huggingface/transformers) 提供两种不同的方法来确定推理期间草稿（辅助）token 数量的调整策略。一种直截了当的方法基于 [Leviathan et al.](https://arxiv.org/pdf/2211.17192)：使用静态的推测步长值，每次推测迭代生成恒定数量的候选 token。另一种是[基于启发式的方法](https://huggingface.co/blog/assisted-generation)：根据当前迭代的接受率调整下一迭代的候选 token 数——若所有推测 token 都正确，候选数增加；否则减少。

我们预计，针对生成草稿 token 数量的更优管理策略，还能进一步压降延迟。为验证这一论断，我们使用一个 oracle（先知基准）来确定每次推测迭代的最优推测步长。该 oracle 让草稿模型自回归地生成 token，直到草稿模型与目标模型的预测 token 出现分歧；对每次推测迭代重复此过程，最终识别出每轮被接受的最优（最大）草稿 token 数。草稿/目标 token 的不一致用 Leviathan et al. 提出的拒绝采样算法（rejection sampling）在零温度下判定。这个 oracle 充分发挥了推测解码的潜力：每步生成最大数量的有效草稿 token，并把草稿模型与目标模型的调用次数都降到最少。

下面左图展示了 [MBPP](https://huggingface.co/datasets/google-research-datasets/mbpp) 数据集一个代码生成示例中，oracle 与静态推测步长在各次推测迭代上的取值。可以看到 oracle 推测步长（橙色柱）方差很大。静态推测步长（蓝色柱）固定草稿 token 数为 5，需要 38 次目标模型前向、192 次草稿模型前向；而 oracle 推测步长只需 27 次目标前向和 129 次草稿前向——显著减少。右图展示了整个 [Alpaca](https://huggingface.co/datasets/tatsu-lab/alpaca) 数据集上的 oracle 与静态推测步长。

![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/dynamic_speculation_lookahead/oracle_K_2.png)
 *某个 MBPP 示例上的 oracle 与静态推测步长（SL）值。*

![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/dynamic_speculation_lookahead/Alpaca.png)
 *整个 Alpaca 数据集的 oracle 平均推测步长。*

两图都显示 oracle 推测步长存在巨大波动，说明静态推测步长可能是次优的。

为了逼近 Oracle 并获得额外加速，我们开发了一种简单的方法，在每次迭代动态调整推测步长。每生成一个草稿 token，我们就判断草稿模型应继续生成下一个 token，还是切换到目标模型进行验证。这一决策基于辅助模型对其预测的信心——用 logits 的 softmax 估计。若辅助模型对当前 token 预测的信心低于预设阈值（即 `assistant_confidence_threshold`），即便还没达到最大推测 token 数 `num_assistant_tokens`，它也会中止本轮迭代的 token 生成。一旦中止，当前迭代产生的草稿 token 就被送往目标模型验证。

## 基准测试

我们在一系列任务与模型组合上把动态方法与启发式方法做了基准对比。动态方法在所有测试中表现都更好。值得注意的是，用 `Llama3.2-1B` 作为 `Llama3.1-8B` 的辅助模型时，动态方法带来最高 1.52 倍加速，而相同设置下启发式方法几乎提速。另一个观察是：`codegen-6B-mono` 在启发式方法下反而*变慢*，而动态方法实现了加速。

| Target model | Draft (Assistant) model | Task | Speedup - heuristic | Speedup - dynamic |
| --- | --- | --- | --- | --- |
| `facebook/opt-6.7b` | `facebook/opt-125m` | summarization | 1.82x | **2.71x** |
| `facebook/opt-6.7b` | `facebook/opt-125m` | open-ended generation | 1.23x | **1.59x** |
| `Salesforce/codegen-6B-mono` | `Salesforce/codegen-350M-mono` | code generation (python) | 0.89x | **1.09x** |
| `google/flan-t5-xl` | `google/flan-t5-small` | summarization | 1.18x | **1.31x** |
| `meta-llama/Llama-3.1-8B` | `meta-llama/Llama-3.2-1B` | summarization | 1.00x | **1.52x** |
| `meta-llama/Llama-3.1-8B` | `meta-llama/Llama-3.2-1B` | open-ended generation | 1.00x | **1.18x** |
| `meta-llama/Llama-3.1-8B` | `meta-llama/Llama-3.2-1B` | code generation (python) | 1.09x | **1.15x** |

- 表中结果反映贪心解码（temperature = 0）。采用采样（temperature > 0）时观察到类似趋势。
- 所有测试在 RTX 4090 上进行。
- 我们的基准已公开，人人可评估进一步的改进：[https://github.com/gante/huggingface-demos/tree/main/experiments/faster_generation](https://github.com/gante/huggingface-demos/tree/main/experiments/faster_generation)

## 代码

动态推测已并入 Hugging Face Transformers 库的 [4.45.0](https://github.com/huggingface/transformers/releases/tag/v4.45.0) 版本，并作为辅助解码的默认运行模式。要用带动态推测的辅助生成，无需改任何代码——照常运行即可：

```
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

prompt = "Alice and Bob"
checkpoint = "EleutherAI/pythia-1.4b-deduped"
assistant_checkpoint = "EleutherAI/pythia-160m-deduped"
device = "cuda" if torch.cuda.is_available() else "cpu"

tokenizer = AutoTokenizer.from_pretrained(checkpoint)
inputs = tokenizer(prompt, return_tensors="pt").to(device)

model = AutoModelForCausalLM.from_pretrained(checkpoint).to(device)
assistant_model = AutoModelForCausalLM.from_pretrained(assistant_checkpoint).to(device)

outputs = model.generate(**inputs, assistant_model=assistant_model)
```

默认的动态推测步长参数已反映最优值，但对特定的模型对或数据集，可以用下面的代码微调参数进一步提升性能：

```
# confidence threshold
assistant_model.generation_config.assistant_confidence_threshold=0.4

# 'constant' means that num_assistant_tokens stays unchanged during generation
assistant_model.generation_config.num_assistant_tokens_schedule='constant'

# the maximum number of tokens generated by the assistant model.
# after 20 tokens the draft halts even if the confidence is above the threshold
assistant_model.generation_config.num_assistant_tokens=20
```

要退回**启发式**或**常量**（如 [Leviathan et al.](https://arxiv.org/pdf/2211.17192)）方案，只需把 `num_assistant_tokens_schedule` 分别设为 `'heuristic'` 或 `'constant'`，并按如下设置 `assistant_confidence_threshold=0` 与 `num_assistant_tokens=5`：

```
# Use 'heuristic' or 'constant' or 'dynamic'
assistant_model.generation_config.num_assistant_tokens_schedule='heuristic'
assistant_model.generation_config.assistant_confidence_threshold=0
assistant_model.generation_config.num_assistant_tokens=5
```

## 接下来？

我们引入了名为*动态推测解码*的更快的辅助生成策略，它既胜过基于启发式的方法，也胜过生成恒定候选 token 数的方法。

在即将发布的博文中，我们将展示辅助生成的一项新方法：任意目标模型都能搭配任意辅助模型！这将为加速 Hugging Face Hub 上海量没有足够小的辅助变体的模型打开大门。例如，`Phi 3`、`Gemma 2`、`CodeLlama` 等许多模型都将具备推测解码条件。敬请期待！
