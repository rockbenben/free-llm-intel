# 为 GPT-OSS 解锁智能体强化学习训练：一次实践回顾

智能体强化学习（agentic RL）通过不仅优化单轮回复、而是优化在训练期间通过与环境直接交互学得的整个决策过程，扩展了传统的 LLM 训练。与依赖静态数据集的传统单轮强化学习或离线偏好方法不同，智能体 RL 通过主动收集 on-policy 数据来训练策略：智能体规划动作、调用工具、观察结果，并在模拟或真实环境的多步轨迹中随时间调整其行为。这种交互驱动的优化将信用（credit）分配到跨越长视界的决策上，其中诸如查询改写、工具选择和执行顺序等中间选择会直接影响下游成功。训练遵循一个迭代的闭环：智能体与环境交互以收集 rollout 轨迹，在这些轨迹上计算奖励，基于观察到的结果更新策略，然后使用更新后的策略来驱动下一轮交互和数据收集，例如 GRPO 或 PPO 算法。

LinkedIn 是一家 AI 优先的公司，我们构建了智能体来帮助职场人士更成功地达成目标。在这种场景下，模型必须在不完整信息上进行推理、与结构化服务交互，并在多步骤中适应不断演变的用户意图，而不是生成一个静态的单一回复。这些能力对于那些支持招聘者、求职与知识寻求者以及学习者等终端用户目标的智能体尤为关键，例如检索信息、优化查询、协调工具以及执行多步工作流。通过交互学习鲁棒的决策策略，智能体 RL 通过端到端优化为构建可扩展、可靠且可适应的 AI 系统提供了一个有原则的基础。

GPT-OSS 模型展现出了与 OpenAI o3-mini 和 o4-mini 相当的性能 [[ref](https://openai.com/index/introducing-gpt-oss/)]，但它是否适合智能体强化学习训练尚未得到验证。大多数近期工作聚焦于不带工具调用的微调，例如：[Fine-tuning with gpt-oss and Hugging Face Transformers](https://cookbook.openai.com/articles/gpt-oss/fine-tune-transfomers) 和 [unsloth tutorial: how to fine-tune gpt-oss](https://unsloth.ai/docs/models/gpt-oss-how-to-run-and-fine-tune/tutorial-how-to-fine-tune-gpt-oss)。本文探索了为 GPT-OSS 解锁 [agentic RL](https://github.com/volcengine/verl/issues/3794) 训练、将其作为智能体应用潜在骨干模型的历程。

在我们的实验中，我们使用 [verl](https://github.com/volcengine/verl) 作为训练框架，因为它是开源社区中最流行、被广泛采用的框架之一。我们使用 gsm8k、[Retool](https://github.com/verl-project/verl-recipe/tree/21892b9276936efab5375c3f6b8415e472ef7118/retool) 任务、[verifiable instruction following task](https://arxiv.org/abs/2507.02833)，这些都是 RL 训练中常用的任务。我们重点展示 GPT-OSS-20B 模型的实验结果，而我们的 attention-sink 修复同样适用于 GPT-OSS-120B。此外还使用 Qwen-2.5-32B 模型来基准测试 RL 训练期间标准指标的趋势。

## GPT-OSS RL 训练的挑战

verl 一直是团队使用的 OSS 框架，团队此前也与之协作并做出贡献，以帮助智能体强化学习训练的普惠化。随着 GPT-OSS 引入新的 Harmony 聊天模板，第一步是确保训练框架完全支持 Harmony 所要求的更新后的消息格式与会话语义。这一步有助于在新模板下让 rollout 生成、轨迹构建和工具解析保持一致且正确。

团队使用 ReTool 作为验证代码正确性的代表性示例。ReTool 是一个智能体编码任务，其中模型被要求在代码编译器工具的辅助下求解一道数学题。这种设置让模型专注于核心推理和算法逻辑，而把实际的算术和执行交给工具。在一个 episode 中，模型会与代码工具多次交互，使用执行结果作为反馈来优化其解答。在轨迹结束时，模型给出一个最终答案，并据此计算奖励。

在最初的训练运行中，我们观察到 KL 散度和熵爆炸，以及奖励不再增长，这表明 GPT-OSS 训练设置中存在底层问题，如图 1 所示。

## verl 中的一次实践调试历程：恢复 PPO 的 on-policy 完整性

### 恢复 PPO 的 on-policy 完整性：针对 MoE 对数概率失配的修复

![](https://cdn-uploads.huggingface.co/production/uploads/64efbd469e7770db74cb72f5/21xIlXKeAlTK5qKSp-TkX.png)

**图 2.** 即使在 on-policy 训练下，重要性采样裁剪值也非零。

我们聚焦 on-policy 方法，因为它们提供了更高的稳定性和更可靠的收敛。纯 on-policy 近端策略优化（PPO）的基础要求重要性采样比率必须恰好为 1。重要性比率的数学定义为：

ratio = π(a | s) / π_old(a | s)

这一要求确保策略更新仅在当前策略生成的数据上执行（π(a | s) = π_old(a | s)），从而防止非预期的裁剪。

我们在 ReTool 训练中观察到了非零的裁剪值，如图 2 所示，其根源在于两个对数概率之间的失配：

- 当前对数概率 `log_prob`：log(π(a | s))
- 旧对数概率 `old_log_prob`：log(π_old(a | s))

**根本原因：双向前向传播与 MoE 架构**

在 verl 0.3.0 之前，实现依赖于两次独立的前向传播（一次计算当前 `log_prob`，一次获取存储的 `old_log_prob`），针对同一状态-动作对。

在像 GPT-OSS 这样的专家混合（Mixture of Experts, MoE）架构中，门控网络将输入路由到不同的专家。由于实现层面的因素（例如细微的浮点差异或显式的随机性），两次传播之间的专家路由可能略有不同。感兴趣的读者可以进一步阅读 *[Stabilizing MoE Reinforcement Learning by Aligning Training and Inference Routers](https://arxiv.org/pdf/2510.11370v1)*。

这种路由差异导致：

log(π(a | s)) ≠ log(π_old(a | s))

由此得到的比率偏离 1，错误地触发了 PPO 裁剪，违反了核心的 on-policy 假设。

**解决方案：通过对数概率替换强制比率 = 1**

当已知环境是 on-policy 时（即 mini-batch 大小等于全局 batch 大小时），该修复通过逻辑上覆盖存在缺陷的计算来解决问题：

```
if on_policy:
    old_log_prob = log_prob.detach()
else:
    old_log_prob = model_inputs["old_log_probs"]
```

通过将 `old_log_prob` 设为等于新计算的 `log_prob`（detach 以防止梯度流过该参考值），重要性比率在数学上被强制回到 1。这一策略绕过了 MoE 非确定性路由造成的不稳定性，并在 PPO 训练期间保证严格的 on-policy 行为。

### 纠正训练-推理失配

尽管修复对数概率失配将重要性采样裁剪比降至零，梯度范数仍在继续爆炸，奖励也无法提升。为了隔离问题，我们将训练简化为 GSM8K，一个不涉及智能体工具使用的单步任务。同样的不稳定性依然存在，如图 3 中的绿色曲线所示，这表明**在 verl 下用 GPT-OSS 进行基本 RL 训练存在一个根本性问题。**

我们假设**训练-推理失配**可能是一个潜在原因：推理时的执行——vLLM 和 SGLang 等引擎为吞吐量进行激进优化——与训练时在 FSDP 下优先考虑数值精度与稳定性的执行之间存在差异，这种差异会有效地把原本**on-policy 的 RL 变成 off-policy 的优化。**

这篇 [blog](https://yingru.notion.site/When-Speed-Kills-Stability-Demystifying-RL-Collapse-from-the-Training-Inference-Mismatch-271211a558b7808d8b12d403fd15edda) 详述了此类失配为何会导致梯度不稳定和奖励不提升。图 3 对比了带与不带 rollout 纠正（详见这个 [verl blog](https://verl.readthedocs.io/en/latest/algo/rollout_corr.html)）的训练运行。应用 rollout 纠正后，训练动态显著改善，梯度范数保持稳定而非爆炸。

然而，如图 4 左图所示，奖励仅小幅增长，且相比更小的稠密模型变体，在简单的 GSM8K 任务上收敛仍明显更慢。

## FlashAttentionV3 中的 Attention Sink 支持

GPT-OSS 使用的 attention sink 是可学习的标量参数（每个注意力头一个），在 softmax 计算中充当"虚拟 token"。它们允许模型将注意力质量分配给一个学习到的 sink，而不是强迫所有注意力都分配给内容 token，这已被证明能在使用滑动窗口注意力的流式推理和训练中提升注意力稳定性。

经过更深入的调查，我们发现了几个主要问题：

- verl 在 `fsdp_worker` 中硬编码了 FlashAttention v2，而它不支持 attention sink。
- FlashAttention v2 和 v3 都不支持 attention sink 的反向传播，因此即便启用 FlashAttention v3，它也无法按预期工作。
- 由于前向传播尚未合并进原始的 FlashAttention v3 仓库，我们借助了 vLLM 的 FlashAttention fork 的前向传播（[PR #75](https://github.com/vllm-project/flash-attention/pull/75)）并实现了反向传播来计算 sink 梯度。

### 标准注意力

```
scores = QK^T / sqrt(d)               # [B, H, N_q, N_k]
probs = softmax(scores, dim=-1)       # Σ_j P_ij = 1
output = probs @ V                   # [B, H, N_q, d_v]
```

### 带 Sink 的注意力（GPT-OSS）

```
scores = QK^T / sqrt(d)                               # [B, H, N_q, N_k]
combined = concat([scores, sink_param], dim=-1)       # [B, H, N_q, N_k+1]
probs = softmax(combined, dim=-1)                     # Σ_j P_ij + P_sink = 1
probs_content = probs[..., :-1]                       # Drop sink component
output = probs_content @ V                           # [B, H, N_q, d_v]
```

**关键区别：** sink 参与 softmax 归一化，但不贡献给输出。

### 数学表述

第 i 行中内容 token j 的注意力权重定义为：

P_ij = exp(S_ij) / ( Σ_{j'=1}^{N_k} exp(S_ij') + exp(S_h) )

**其中：**

- S_ij = Q_i K_j⊤ / √d 是注意力分数
- P_ij 是内容 token 的注意力权重
- S_h 是头 h 的可学习 sink 参数

**Sink 概率：**

sink 概率会被计算，但不用于输出：

P_{i,h} = exp(S_h) / ( Σ_{j'=1}^{N_k} exp(S_ij') + exp(S_h) )

### 反向传播

损失 L 对 sink 参数 S_h 的梯度为：

∂L/∂S_h = - Σ_i P_{i,h} ( ∂L/∂S_{i,h} - Σ_{j∈{1,…,N_k}} P_ij ∂L/∂S_ij )

**其中：**

- P_{i,h} 是第 i 行的 sink 注意力概率
- ∂L/∂S_ij 是对注意力分数（包括 sink）的梯度

**简化梯度：**

由于 sink 被计算但不用于输出，其梯度 ∂L/∂S_{i,h} = 0。

因此，反向方程简化为：

∂L/∂S_h = - Σ_i P_{i,h} ( Σ_{j∈{1,…,N_k}} P_ij ∂L/∂S_ij )

前向传播改编自 vLLM 的 FlashAttention fork，我们实现了反向传播以计算 sink 参数的梯度。该实现将在内部评审流程之后发布。

### 结果

在 FlashAttention v3 中应用该修复后，我们观察到 GPT-OSS-20B 在一系列强化学习任务上收敛显著加快。这些任务包括数学推理上的单轮 RL（GSM8K——图 5 中红色曲线）、指令遵循（VerifyIf，在一个域外 multi-if 基准上评估——图 6），以及带工具使用的多轮智能体 RL（ReTool——图 7）。

在所有设置下，训练变得稳定，并表现出稳步的奖励提升。

## 内存高效训练

### 缓解由重复 MoE 专家实体化导致的 FSDP 内存暴涨

我们始终遇到的一个问题是 FSDP 前向传播期间过度的内存分配，这导致在 16 个 H200 节点上训练 GPT-OSS-20B bf16 模型（最大响应长度：16k，提示长度：8k）时反复出现内存不足（OOM）失败。对于一个 200 亿参数的 MoE 模型而言，这种行为极为出乎意料。

```

2025-11-27T11:15:27.927Z [36m(TaskRunner pid=32081)[0m hidden_states = hidden_states.repeat(num_experts, 1)
2025-11-27T11:15:27.927Z [36m(TaskRunner pid=32081)[0m torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 180.00 GiB. GPU 0 has a total capacity of 139.72 GiB of which 110.94 GiB is free. Process 685851 has 24.88 GiB memory in use. Process 692458 has 3.87 GiB memory in use. Of the allocated memory 23.28 GiB is allocated by PyTorch, and 84.43 MiB is reserved by PyTorch but unallocated.
```

我们将问题定位为源于 Hugging Face Transformers 中 MoE 前向路径的两种不同实现。其他用户也报告了该问题：[https://github.com/huggingface/transformers/issues/40073](https://github.com/huggingface/transformers/issues/40073)；当 verl 在 FSDP 下计算对数概率时，会触发推理前向路径。在当前的 Hugging Face 实现中，该路径会为所有专家复制隐藏状态并执行批量矩阵乘法，在 GPU 内存中实体化出极大的张量。相比之下，训练前向路径使用 for 循环逐个顺序处理每个专家，然后组合结果。虽然更慢，但这种方式在内存上显著更高效。

```
    @GPUMemoryLogger(role="dp actor", logger=logger)
    def compute_log_prob(self, data: DataProto, calculate_entropy=False) -> torch.Tensor:
        """
        ....
        """
        # set to eval, this essentially prioritizes parallelism at the cost of memory efficiency
        self.actor_module.eval()
        ...
```

我们修补了 Hugging Face 的实现，以使用更内存高效的执行路径，避免重复实体化专家。

### 结合 Flash Attention V3 的序列并行

智能体 RL 要求智能体在多步骤中与环境交互，同时维护一个不断扩大的上下文。每一步的观察和环境反馈都被追加到上下文并用作后续决策的输入，这在训练期间给内存效率和可扩展性带来了显著挑战。

在完全分片数据并行（FSDP）下，模型参数、优化器状态和梯度被分片到整个 world size（即训练集群中的所有 GPU）上。每个 GPU 只存储和更新其被分配的参数分片，而 rollout 数据被复制到所有 GPU 上——意味着每个 GPU 会为每次 rollout 处理完整的智能体交互历史。

在前向传播期间，当计算到达一个参数不在本地的层时，会触发一次 `all_gather` 操作以在所有 GPU 上实体化完整参数。在反向传播期间，相应的 `reduce_scatter` 操作聚合梯度，并确保每个 GPU 只保留其本地分片。这提供了一定程度的可扩展性：随着 GPU 数量增加，单 GPU 的内存占用减少。

FSDP 通过将模型参数、梯度和优化器状态分片到各 GPU 上来提供模型级的扩展。序列并行（或上下文并行）通过将输入序列划分到各设备上进一步降低单 GPU 内存消耗，从而降低每个 GPU 上的峰值激活内存。

随着序列并行维数增加，每 GPU 的最大激活内存相应下降。我们实现了能感知 attention-sink 并与 FlashAttention v3 兼容的序列并行（图 8，右）。

[![SP  (2)](https://cdn-uploads.huggingface.co/production/uploads/64efbd469e7770db74cb72f5/ryT_y9BpbFSdMDxNYlVlK.png)](https://cdn-uploads.huggingface.co/production/uploads/64efbd469e7770db74cb72f5/ryT_y9BpbFSdMDxNYlVlK.png)

**图 8**. 左：不带序列并行的推理。右：带序列并行的推理，其中在注意力层前后执行额外的 all-to-all 通信。这将序列划分到各并行 worker 上，并使注意力计算的峰值内存占用按与序列并行度成正比的因子下降。

序列并行沿序列维度扩展，以降低每 GPU 的激活占用。所有序列的输入 token 通过移除 padding token 被打包进一个连续的列表，同时用 position ID 来区分属于不同序列的 token。这一设计天然受益于 FlashAttention 的变长支持。对于序列并行，除注意力层以外的层没有跨位置依赖；因此它们不要求每个 GPU 都持有一个完整的序列分片，这些层也无需额外通信。

然而，注意力层要求属于同一序列的所有 token 存在于同一 GPU 上，以便正确计算注意力权重。为满足这一约束，执行一次 all-to-all 通信以聚合序列元素，划分在注意力头级别进行。这一设计避免了在注意力计算内部的通信，否则那会代价高得令人却步。在注意力层之后，一次 all-to-all 通信将输出重新分配回它们原来的序列并行布局，此后其余非注意力层无需进一步同步即可继续。

## 结论

我们为 GPT-OSS 骨干模型启用智能体 RL 训练的历程是一次实践回顾，它凸显出：要在开源 LLM 中解锁先进能力，需要细致、深入的工程。

我们做出的贡献改变了 GPT-OSS 用于智能体应用的可行性，具体而言：

- **稳定 PPO：** 我们贡献了一个恢复 on-policy 完整性的修复，覆盖了由 MoE 架构非确定性引起的对数概率失配（图 2）。
- **启用 Attention Sink 支持：** 我们成功实现并将 attention sink 反向传播集成进 FlashAttention v3，纠正了此前造成长期不稳定和收敛缓慢的灾难性训练-推理失配（图 5、6 和 7）。
- **扩展内存效率：** 我们引入了关键的内存优化，包括修补 MoE 实体化过程，并将序列并行与新的 attention sink 支持集成，从而能够用多步智能体所必需的长上下文窗口进行训练（图 8）。

这些工程努力验证了 GPT-OSS 是一个可扩展、高性能的骨干，可用于构建下一代智能的、多步决策的智能体。
