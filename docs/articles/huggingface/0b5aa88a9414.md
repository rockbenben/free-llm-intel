# 告别冷启动——我们如何将 LoRA 推理提速 300%

tl;dr：我们按用户请求切换 Stable Diffusion 的 LoRA 适配器（adapter），同时让基座模型保持热（warm），从而在多个用户之间实现快速 LoRA 推理。你可以逛逛我们的 [LoRA 目录](https://huggingface.co/models?library=diffusers&other=lora)、把玩推理组件来体验。

[![推理组件示例](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/171_load_lora_adapters/inference_widget.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/171_load_lora_adapters/inference_widget.png)

本文详细讲解我们是如何做到的。

我们大幅提速了 Hub 上"公开 LoRA × 公开 Diffusion 模型"组合的推理。这帮我们节省算力，并提供了更快、更好的用户体验。

对某个模型执行推理有两个步骤：

- 预热阶段——下载模型并搭好服务（25 秒）。
- 然后是推理任务本身（10 秒）。

经过优化，预热时间从 25 秒降到 3 秒。我们现在用不到 5 块 A10G GPU 就能服务上百个不同的 LoRA，同时用户请求的响应时间从 35 秒降到 13 秒。

接下来谈谈我们如何利用 [Diffusers](https://github.com/huggingface/diffusers/) 库中的一些新特性，用单一服务动态地服务众多不同的 LoRA。

## LoRA

LoRA 是一种微调技术，属于"参数高效"（PEFT）方法家族，这类方法尽量减少受微调过程影响的可训练参数量。它提升微调速度，同时缩小微调后 checkpoint 的体积。

与其对整个模型的全部权重做微调式的小改动，我们冻结大部分层，只训练注意力模块里的少数特定层。而且我们不直接动这些层的参数，而是在原始权重上加上两个更小矩阵的乘积。被更新的就是这两个小矩阵的权重，微调后保存的也是它们。这意味着模型的全部原始参数都原封不动，我们可以用适配方法把 LoRA 权重叠加加载上去。

LoRA 之名（Low Rank Adaptation，低秩适配）就来自前面说的那两个小矩阵。想了解方法的更多细节，请看[这篇博客](https://huggingface.co/blog/lora)或[原论文](https://arxiv.org/abs/2106.09685)。

[![LoRA 分解](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/171_load_lora_adapters/lora_diagram.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/171_load_lora_adapters/lora_diagram.png)

上面的示意图展示了作为 LoRA 适配器一部分保存的两个橙色小矩阵。之后我们可以加载 LoRA 适配器并与蓝色基座模型合并，得到黄色的微调模型。关键是，适配器也可以*卸载*（unload），让我们随时还原到原始基座模型。

换句话说，LoRA 适配器就像基座模型的一个附加组件，按需装卸。由于 A、B 的低秩，它相对模型体积非常轻量，因此加载它比加载整个基座模型快得多。

看看 Hub 上被众多 LoRA 当作基座模型的 [Stable Diffusion XL Base 1.0 仓库](https://huggingface.co/stabilityai/stable-diffusion-xl-base-1.0/tree/main)，体积约 **7 GB**。而像[这个](https://huggingface.co/minimaxir/sdxl-wrong-lora/)典型 LoRA 适配器，只占 **24 MB**！

Hub 上蓝色基座模型的数量远少于黄色微调模型。如果我们能在蓝色和黄色之间快速切换，那就意味着用少量几种蓝色部署就能服务众多不同的黄色模型。

关于 LoRA 更完整的介绍，请阅读博客 [Using LoRA for Efficient Stable Diffusion Fine-Tuning](https://huggingface.co/blog/lora)，或直接看[原论文](https://arxiv.org/abs/2106.09685)。

## 收益

Hub 上大约有 **2500** 个不同的公开 LoRA，其中绝大多数（**约 92%**）基于 [Stable Diffusion XL Base 1.0](https://huggingface.co/stabilityai/stable-diffusion-xl-base-1.0) 模型。

在做这种共享之前，意味着要给每一个都部署专用服务（即上图所有黄色合并矩阵；发布 + 至少预留一块新 GPU）。服务启动到能响应某个特定模型的请求大约 **25 秒**，这之后还要加上推理时间（A10G 上做 1024x1024 的 SDXL 推理、25 步扩散约 **10 秒**）。如果某个适配器只是偶尔被请求，它的服务会被停掉，把资源让给被抢占的其他模型。

假如你请求的是一个不那么热门的 LoRA——即便它像 Hub 上绝大多数适配器一样基于 SDXL——第一个请求也要花 **35 秒**来预热并出答案（后续请求只需推理时间，例如 **10 秒**）。

现在：由于所有适配器只会用到少数几种"蓝色"基座模型（Diffusion 方向大概 2 种主力），请求时间从 35 秒降到 13 秒。即便你的适配器不热门，它的"蓝色"服务也大概率已经预热好了。也就是说，大概率可以跳过 25 秒的预热，哪怕你不常请求自己的模型。蓝色模型已经下载就绪，我们只需要卸载上一个适配器、加载新的——正如[下文](https://huggingface.co/blog/lora-adapters-dynamic-loading#loading-figures)所示，这只需 **3 秒**。

总体上，服务所有不同模型所需的 GPU 更少了——尽管我们原本就有 GPU 共享机制来最大化算力利用。在 **2 分钟**的时间窗口内，大约会有 **10** 种不同的 LoRA 权重被请求。与其启动 10 个部署并保持热着，我们只需 1 到 2 块 GPU（请求激增时更多）就能全部服务。

## 实现

我们在 Inference API 中实现了 LoRA 共享。当对平台上某个模型的请求到来时，我们先判断它是否为 LoRA，然后找出该 LoRA 的基座模型，并把请求路由到一个公共后端集群——它有能力服务该模型。推理请求的处理方式是：基座模型保持热，LoRA 动态加载/卸载。这样我们就能用同一份算力同时服务许多不同的模型。

### LoRA 结构

在 Hub 上，LoRA 可以通过两个属性识别：

[![Hub](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/171_load_lora_adapters/lora_adapter_hub.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/171_load_lora_adapters/lora_adapter_hub.png)

LoRA 会有一个 `base_model` 属性，就是该 LoRA 为之而构建、推理时应将其应用于其上的模型。

由于并非只有 LoRA 才有这个属性（任何复制的模型都会有），LoRA 还需要一个 `lora` 标签才能被正确识别。

### Diffusers 里 LoRA 的加载/卸载 🧨

注意，用 [peft](https://github.com/huggingface/peft) 库可以更顺滑地完成本节展示的内容，详见[文档](https://huggingface.co/docs/diffusers/main/en/tutorials/using_peft_for_inference)。原理不变（在上面[示意图](https://huggingface.co/blog/lora-adapters-dynamic-loading#diagram)里蓝盒与黄盒之间的来回切换）。

Diffusers 库用 4 个函数来加载和卸载不同的 LoRA 权重：

`load_lora_weights` 和 `fuse_lora`，用于加载以及把权重合并进主层。注意，在推理前把权重与主模型融合可以让推理时间下降 30%。

`unload_lora_weights` 和 `unfuse_lora`，用于卸载。

下面示例演示如何借助 Diffusers 库在基座模型上快速加载多个 LoRA 权重：

```
import torch


from diffusers import (
    AutoencoderKL,
    DiffusionPipeline,
)

import time

base = "stabilityai/stable-diffusion-xl-base-1.0"

adapter1 = 'nerijs/pixel-art-xl'
weightname1 = 'pixel-art-xl.safetensors'

adapter2 = 'minimaxir/sdxl-wrong-lora'
weightname2 = None

inputs = "elephant"
kwargs = {}

if torch.cuda.is_available():
    kwargs["torch_dtype"] = torch.float16

start = time.time()

# Load VAE compatible with fp16 created by madebyollin
vae = AutoencoderKL.from_pretrained(
    "madebyollin/sdxl-vae-fp16-fix",
    torch_dtype=torch.float16,
)
kwargs["vae"] = vae
kwargs["variant"] = "fp16"

model = DiffusionPipeline.from_pretrained(
    base, **kwargs
)

if torch.cuda.is_available():
    model.to("cuda")

elapsed = time.time() - start

print(f"Base model loaded, elapsed {elapsed:.2f} seconds")


def inference(adapter, weightname):
    start = time.time()
    model.load_lora_weights(adapter, weight_name=weightname)
    # Fusing lora weights with the main layers improves inference time by 30 % !
    model.fuse_lora()
    elapsed = time.time() - start

    print(f"LoRA adapter loaded and fused to main model, elapsed {elapsed:.2f} seconds")

    start = time.time()
    data = model(inputs, num_inference_steps=25).images[0]
    elapsed = time.time() - start
    print(f"Inference time, elapsed {elapsed:.2f} seconds")

    start = time.time()
    model.unfuse_lora()
    model.unload_lora_weights()
    elapsed = time.time() - start
    print(f"LoRA adapter unfused/unloaded from base model, elapsed {elapsed:.2f} seconds")


inference(adapter1, weightname1)
inference(adapter2, weightname2)
```

## 加载耗时

下面所有数字单位为秒：

| GPU | T4 | A10G |
| --- | --- | --- |
| 基座模型加载 - 未缓存 | 20 | 20 |
| 基座模型加载 - 已缓存 | 5.95 | 4.09 |
| 适配器 1 加载 | 3.07 | 3.46 |
| 适配器 1 卸载 | 0.52 | 0.28 |
| 适配器 2 加载 | 1.44 | 2.71 |
| 适配器 2 卸载 | 0.19 | 0.13 |
| 推理时间 | 20.7 | 8.5 |

每次推理额外只花 2 到 4 秒，就能服务众多不同的 LoRA。不过在 A10G 上，推理时间下降很多而适配器加载耗时变化不大，所以 LoRA 的加载/卸载相对而言更贵。

### 服务请求

我们使用[这个开源社区镜像](https://github.com/huggingface/api-inference-community/tree/main/docker_images/diffusers)来服务推理请求。

前面描述的机制可以在 [TextToImagePipeline](https://github.com/huggingface/api-inference-community/blob/main/docker_images/diffusers/app/pipelines/text_to_image.py) 类中找到其用法。

当一个 LoRA 被请求时，我们先看当前加载的是哪个，只在必要时更换，然后照常执行推理。这样我们就能同时服务基座模型和众多不同适配器的请求。

下面是测试和请求该镜像的示例：

```
$ git clone https://github.com/huggingface/api-inference-community.git

$ cd api-inference-community/docker_images/diffusers

$ docker build -t test:1.0 -f Dockerfile .

$ cat > /tmp/env_file <<'EOF'
MODEL_ID=stabilityai/stable-diffusion-xl-base-1.0
TASK=text-to-image
HF_XET_HIGH_PERFORMANCE=1
EOF

$ docker run --gpus all --rm --name test1 --env-file /tmp/env_file_minimal -p 8888:80 -it test:1.0
```

然后在另一个终端里向基座模型和/或 HF Hub 上的各种 LoRA 适配器发请求。

```
# Request the base model
$ curl 0:8888 -d '{"inputs": "elephant", "parameters": {"num_inference_steps": 20}}' > /tmp/base.jpg

# Request one adapter
$ curl -H 'lora: minimaxir/sdxl-wrong-lora' 0:8888 -d '{"inputs": "elephant", "parameters": {"num_inference_steps": 20}}' > /tmp/adapter1.jpg

# Request another one
$ curl -H 'lora: nerijs/pixel-art-xl' 0:8888 -d '{"inputs": "elephant", "parameters": {"num_inference_steps": 20}}' > /tmp/adapter2.jpg
```

### 批处理（batching）呢？

最近有一篇很有趣的[论文](https://arxiv.org/abs/2311.03285)，介绍如何对 LoRA 模型做批量推理来提高吞吐：把所有推理请求攒成一个批次，先一次性完成公共基座模型相关的计算，再计算各适配器特有的乘积。我们并没有实现这种技术（它接近 [text-generation-inference](https://github.com/huggingface/text-generation-inference/) 为 LLM 采用的路线），而是坚持单条顺序请求。原因是我们观察到批处理对 diffusers 并不划算：吞吐不随批大小显著增长。在我们做的简单图像生成基准上，批大小 8 只换来 25% 的提升，而延迟要增加 6 倍！相比之下，批处理对 LLM 大有裨益——8 倍顺序吞吐只要 10% 的延迟增幅。这就是我们没有为 diffusers 实现批处理的原因。

## 结论：还是**时间**！

借助动态 LoRA 加载，我们既节省了算力，又提升了 Hub Inference API 的用户体验。尽管流程里多了"卸载上一个适配器、加载目标适配器"的时间，但服务进程绝大多数时候已经在线，整体推理响应因此快得多。

注意，一个 LoRA 想在 Hub 上享受这一推理优化，必须同时满足：公开、非 gated，且基于一个非 gated 的公开模型。如果你也在自己的部署里用了同样方法，欢迎告诉我们！
