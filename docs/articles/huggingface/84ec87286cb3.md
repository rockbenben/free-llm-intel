LLM 依靠其上下文来生成下一组令牌。在很长的轨迹中，上下文充满了多种类型的组件：系统提示、过去的对话轮次、作用于检索到的文档的指令、工具响应或用户数据、限制允许输出的要求以及推理链。上下文具有丰富的结构，其中大部分结构要么是模型隐式的，要么以 JSON 等格式进行编码，而这些格式并非旨在被 LLM 消化。这是LLM（尤其是规模较小的LLM）脆弱且有时会以意想不到的方式失败的主要原因之一。缺乏显式结构也可能被攻击者利用，例如以提示注入的形式。

为了解决这个问题，我们开发了 LLMON（LLM 对象表示法，发音为“lemon”），这是一种 LLM 原生标记语言，用于向模型显式传达结构和语义。语义一致的组件标有有意义的标签，这些标签包含在保留的特殊令牌分隔符中。数据模式（包括嵌套）以因果LLM明确的方式表述。唯一的 ID 可以指向特定的指令，这些指令可以驻留在上下文中的任何位置，并将它们绑定到它们应该执行操作的数据有效负载，类似于在编程语言中调用函数和将参数传递给它们的方式。

今天，我们发布了两个实验性预览模型，它们源自 Granite 4.1 基本模型，经过训练可以使用和生成 LLMON 标记的文本：[granite-4.1-3b-LLMON-preview](https://huggingface.co/ibm-granite/granite-4.1-3b-llmon-preview) 和[granite-4.1-8b-LLMON-preview](https://huggingface.co/ibm-granite/granite-4.1-8b-llmon-preview)。我们还发布了一个 [GitHub](https://github.com/generative-computing/llmon) 存储库，其中包括用于使用 LLMON 的工具包以及工作流程和模板的示例。

**它能实现什么：**

- 由于显式指令/数据分离，隐藏在用户数据中的间接提示注入大多被 LLMON 模型忽略。对于某些基准测试，攻击成功率几乎降至零，而常规指令调整模型很可能被劫持。这是在保持与 Granite 4.1 Instruct 模型相关的一般功能的同时实现的。
- 不相关的段落、旧的聊天回合和工具输出不会被纳入答案，因为每条指令都与其适用的确切数据绑定。
- 指令、数据和需求均被清晰标记，以便模型可以利用它们在应用程序代码级别的结构和含义。在 [Mellea](https://github.com/generative-computing/mellea) 中尝试一下，它通过自动 LLMONizing 其 LLM 调用来启用本机 LLMON 支持。
- 您不再需要担心强迫LLM遵守 JSON 结构。使用我们的转换器将现有 JSON 无损转换为 LLMON。您还可以定义自己的结构和关联标签，并在 LLMON 模型之上调整 LoRA 以理解它。

### 为什么不是 JSON？

JSON 是为解析器设计的，而不是为因果语言模型设计的。分词器不限于遵守语法，结构由也可能出现在普通文本中的标记 ({, ", :) 进行编码。对于模型来说，文档内的引号和关闭字段的引号是相同的标记。解析器清楚的转义规则只是模型的统计模式。嵌套深度是通过计算括号来编码的，众所周知，变压器在这方面很弱，尤其是在长跨度上。

另一方面，LLMON 是一种类似 XML 的标记，其结构分隔符是保留的特殊标记而不是字符，因此结构和内容使用词汇表的不同部分。标签在每个跨度的开头进行说明，并且跨度之间的界限是明确的。嵌套结构是在本地声明的，因此模型不需要跟踪长跨度的层次结构。

由于大多数团队已经拥有围绕 JSON 构建的管道，因此我们创建了[转换工具](https://github.com/generative-computing/llmon/tree/main/llmon/lang) 和示例笔记本，以无损的方式将 JSON 转换为 LLMON 并返回。

### LLMON 与聊天模板有何关系？

LLMON 不会取代聊天模板；相反，它丰富了他们。常规聊天模板告诉模型哪个部分属于哪个角色（系统、用户、助理），而 LLMON 则告诉模型每个组件的含义以及组件在角色内部和角色之间如何相互关联。

LLMON 预览模型附带了自己的聊天模板，因此您可以构建传递给任何聊天模型的相同“消息”列表，并像往常一样调用“apply_chat_template”；它呈现如下所示的 LLMON。唯一的区别是，回合现在可以为其部分命名并标记每个“exec”：“True”或“False”。标记为“True”的部分被绑定到渲染输出底部的“exec”块中，该块声明要运行哪条指令以及它的操作内容；标记为“False”的部分仍会呈现到上下文中，但不会被任何内容引用。
```
messages = [ { "role": "user",
               "instruction": [{ "value": "Write a short paragraph about", "exec": True }],
               "data": [{ "value": "IBM Company", "exec": True }],
               "requirement": [ {"value": "Use less than 10 words", "exec": True},
                                {"value": "Do not use commas", "exec": True}]
             } ]
```

两个字符的块 ID 是从该标记生成器编码为单个标记的固定集合中提取的，因此无论提取哪个 ID，寻址块总是花费两个标记。

该角色仍然是单用户回合，但其组件作为五个独立的可寻址块到达模型，由第六个块（exec 块）绑定在一起，该块声明：根据这两个要求，在此数据上运行此指令，并将答案放入此处命名的块中，该块与模型随后填充的辅助块相同。传统的模板会将所有组件扁平化为一个字符串，并让模型推断哪一部分是任务，哪一部分是主题，哪一部分是约束。

### LLMON 如何解决提示注入攻击

间接提示注入是一种攻击类型，其中恶意指令隐藏在数据有效负载中，例如检索到的文档、工具响应或用户提供的数据。这就是 LLMON 指令/数据分离旨在解决的问题。

我们将 LLMON 预览版与几个开源和闭源模型进行了比较。我们在 [OPI](https://arxiv.org/abs/2310.12815) 基准上进行了评估，该基准将注入放入经典 NLP 任务的数据中。采用了多种攻击策略。我们报告鲁棒性，定义为 1 − 攻击成功率：模型不执行注入指令的攻击比例。

[![OPI](https://cdn-uploads.huggingface.co/product/uploads/6484ca4d5ff9a3d2ee52a83b/3UqXuyb58P8n3NiHnJiK4.p ng)](https://cdn-uploads.huggingface.co/product/uploads/6484ca4d5ff9a3d2ee52a83b/3UqXuyb58P8n3NiHnJiK4.png)

所有非 LLMON 模型都非常容易受到影响，以高概率执行注入的指令。 LLMON 实际上消除了该基准测试中的问题，相对于我们测试的最佳前沿模型，避免的攻击多了 47%，比最佳开源模型多避免了 95%。我们在其他基准上观察到类似的趋势（[ASB](https://arxiv.org/pdf/2410.02644) 和 [StruQ](https://arxiv.org/pdf/2402.06363)）。值得注意的是，这些基准测试测试静态间接提示注入的稳健性。指令/数据分离直接解决了此类攻击。我们还积极致力于改进在许多聊天回合中展开的自适应攻击。

### 一般能力

安全收益不会以牺牲一般能力为代价。在标准基准测试类别中，LLMON 模型的性能与 Granite 4.1 Instruct 模型相当。

[![Granite-4.1 与LLMON](https://cdn-uploads.huggingface.co/product/uploads/6484ca4d5ff9a3d2ee52a83b/VMIEO4qYlmxLhK0DmMO6C.p ng）]（https://cdn-uploads.huggingface.co/product/uploads/6484ca4d5ff9a3d2ee52a83b/VMIEO4qYlmxLhK0DmMO6C.png）

简而言之，如果您今天正在尝试 Granite 4.1 3B 或 8B，则可以更换 LLMON 预览版，并且应该会看到相当的总体性能，并且对提示注入的抵抗力要强得多。不需要转换管道。命名回合的各个部分（例如上例中的指令、数据、要求）就足够了。附带的聊天模板将这些内容转换为 LLMON 块。我们的 LLMON 转换器库更深入了一层：如果某个部分本身是结构化的，例如 JSON 文档，则 LLMONizing 会将该结构保留为类型化、可单独寻址的块，而不是一个不透明的字符串。

### 我们如何训练模型

这些模型从 [Granite 4.1](https://huggingface.co/ibm-granite/granite-4.1-8b-base) 基础检查点开始，而不是从已发布的指令模型开始，因此 LLMON 行为是在训练后学习的，而不是在现有聊天格式上分层。

LLMON定义了六个分隔符，标记标签的开始和结束，并允许嵌套和锚定；它们作为保留的单个令牌安装在分词器中。我们将传统的指令调整语料库重新序列化为 LLMON：每个提示组件都成为其自己的可寻址块，并且每个回合都带有一个执行块，用于命名要运行的指令、操作的输入以及输出的去向。任务组合是普通指令模型所看到的（聊天、多回合、RAG、工具调用），这就是基准性能保持接近传统调整模型的原因。此外，我们使用上下文中存在的诱饵指令和数据块来扩充数据，但故意保持未绑定状态，而目标输出保持不变。因此，模型学习遵循执行块指示的依赖关系并忽略其余部分。强化学习如下：五个连续的 GRPO 阶段，涵盖多领域推理、RLHF、知识校准和数学，然后是最终的 DPO 阶段，基于模型自身对注入尝试的响应构建的一千个策略偏好对。

由此产生的权限规则不在这种布局中，而不是添加的护栏：通过执行块到达的指令是权威的，而作为输入到达的任何内容（数据、文档、工具模式、工具结果）都是可读的材料，而不是要遵循的命令。此外，执行块中未调用的指令和数据范围将被忽略。这是一种习得的行为，而不是强制的保证。要了解这是如何在 LLMON 模型的注意力层中发挥作用的，请尝试 Hugging Face Spaces 上的 [LLMON Attention Visualization](https://huggingface.co/spaces/ibm-granite/LLMON-Attention-Visualization)。

### 带上你自己的词汇（科学世界）

LLMON 不依赖于固定模式：您可以选择适合您的域的标签名称和结构，并微调适配器来读取和写入它们。我们在 ScienceWorld 上演示了这一点，这是一种基于文本的基准，其中代理通过一次发出一个命令并从模拟器接收分数来执行基本的科学任务（例如烧水）。我们定义了一个词汇表，捕获解决这些任务所涉及的规划轨迹的结构。词汇表包括“instr.task.goal”、“req.planning_policy.rule”、“data.state.room”、“data.state.inventory”和“assistant.next_action”等标签。我们使用这些标签呈现 ScienceWorld 参考解决方案的每一步，并在 LLMON 模型之上调整 LoRA。然后，经过训练的模型会玩保留的游戏，并用新词汇编写其下一步动作。 [本笔记本](https://github.com/generative-computing/llmon/blob/main/llmon/examples/lora-finetuning/byo-vocab_LoRA_scienceworld.ipynb) 介绍了完整的工作流程，从转换参考轨迹到玩测试游戏，再到针对未经训练的基本模型对适配器进行评分。工具调用代理的另一个示例可以在[本笔记本](https://github.com/generative-computing/llmon/blob/main/llmon/examples/lora-finetuning/byo-vocab_LoRA_for_agents.ipynb)中找到。
