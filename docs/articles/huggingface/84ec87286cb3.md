LLM 依靠上下文来生成下一组 token。在很长的轨迹里，上下文会塞满各类组件：system prompt、过去的对话轮次、作用于检索文档的指令、工具响应或用户数据、约束允许输出的要求，以及推理链。上下文承载着丰富的结构，其中大部分要么对模型是隐式的，要么用 JSON 之类并非为供 LLM 消化而设计的格式编码。这正是 LLM（尤其是规模较小的一端）脆弱、有时会以意外方式失败的主要原因之一。缺少显式结构也可能被攻击者利用，比如做成 prompt injection。

为此我们开发了 LLMON（LLM Object Notation，读作 “lemon”），一种 LLM 原生的标记语言，用来向模型显式传达结构和语义。语义上连贯的组件会用有含义的标签标出，标签包在保留的特殊 token 分隔符里。数据 schema（包括嵌套）以一种对 causal LLM 无歧义的方式陈述。唯一 ID 让你可以指向某条特定指令——它可以位于上下文任意位置——并把它绑定到应当作用的数据 payload 上，类似于编程语言里调用函数、把参数传进去。

今天我们发布两个实验性 preview 模型，它们基于 Granite 4.1 base 模型训练，能够消费和生成带 LLMON 标记的文本：[granite-4.1-3b-LLMON-preview](https://huggingface.co/ibm-granite/granite-4.1-3b-llmon-preview) 和 [granite-4.1-8b-LLMON-preview](https://huggingface.co/ibm-granite/granite-4.1-8b-llmon-preview)。我们还发布了一个 [GitHub](https://github.com/generative-computing/llmon) 仓库，其中包含使用 LLMON 的工具包，以及工作流和模板的示例。

**它能带来什么：**

- 藏在用户数据里的间接 prompt injection，大多会被 LLMON 模型忽略，因为指令与数据是显式分离的。在某些 benchmark 上，攻击成功率几乎降到零，而常规的指令微调模型大概率会被劫持。做到这一点的同时，相对 Granite 4.1 Instruct 模型仍保持了通用能力。
- 不相关的段落、旧的对话轮次和工具输出不会被卷进答案，因为每条指令都绑定到它所适用的确切数据。
- 指令、数据和要求都被清楚标记，模型便能在应用程序代码层面利用它们的结构和含义。可以在 [Mellea](https://github.com/generative-computing/mellea) 里试，它原生支持 LLMON，会自动把自己的 LLM 调用 LLMON 化。
- 你不必再操心怎么强迫 LLM 遵守 JSON 结构。用我们的转换器可以把现有 JSON 无损转成 LLMON。你也可以定义自己的结构和配套标签，在 LLMON 模型之上微调 LoRA 来理解它。

### 为什么不用 JSON？

JSON 是为解析器设计的，不是为 causal 语言模型设计的。tokenizer 不受语法约束，结构靠 `{`、`"`、`:` 这类 token 编码，而它们也可能出现在普通文本里。对模型来说，文档内部的引号和结束字段的引号是同一个 token。解析器一眼就懂的转义规则，对模型只是统计规律。嵌套深度靠数括号来编码，而 transformer 出了名地不擅长这个，跨度一长更明显。

相比之下，LLMON 是一种类 XML 的标记，它的结构分隔符是保留的特殊 token，而不是字符，因此结构和内容占用词表的不同部分。标签在每个片段的开头声明，片段之间的边界是显式的。嵌套结构就地声明，模型不必在很长的跨度上一直追踪层级。

由于大多数团队已经有围绕 JSON 搭建的流水线，我们做了[转换工具](https://github.com/generative-computing/llmon/tree/main/llmon/lang) 和示例 notebook，可以无损地在 JSON 与 LLMON 之间来回转换。

### LLMON 与 chat template 有什么关系？

LLMON 并不取代 chat template，而是对它的丰富。常规 chat template 告诉模型哪一部分属于哪个角色（system、user、assistant），LLMON 则告诉模型每个组件是什么含义、组件在角色内部和跨角色之间如何关联。

LLMON preview 模型自带 chat template，所以你照常构建传给任何聊天模型的 `messages` 列表、照常调用 `apply_chat_template`；它渲染出的就是下面这样的 LLMON。唯一的区别是，一轮对话现在可以给自己的各部分命名，并把每部分标成 `exec`: `True` 或 `False`。标成 `True` 的部分会绑定进渲染输出底部的 `exec` 块，这个块声明要运行哪条指令、它作用于什么；标成 `False` 的部分仍会渲染进上下文，但不被任何东西引用。

```
messages = [ { "role": "user",
               "instruction": [{ "value": "Write a short paragraph about", "exec": True }],
               "data": [{ "value": "IBM Company", "exec": True }],
               "requirement": [ {"value": "Use less than 10 words", "exec": True},
                                {"value": "Do not use commas", "exec": True}]
             } ]
```

模型实际收到的是下面这样（这里为便于阅读加了换行和缩进，模板本身不输出这些）：

```
<|open|>instr<|:|>»ñ<|close|>Write a short paragraph about<|open_end|>
<|open|>data<|:|>ä¦<|close|>IBM Company<|open_end|>
<|open|>req<|:|>Á¼<|close|>Use less than 10 words<|open_end|>
<|open|>req<|:|>¢¬<|close|>Do not use commas<|open_end|>
<|open|>exec<|:|>ÄÐ<|close|>
    <|open|>exec<|.|>instruction<|close|>instr<|:|>»ñ<|open_end|>
    <|open|>exec<|.|>input<|close|>data<|:|>ä¦<|open_end|>
    <|open|>exec<|.|>requirement<|close|>req<|:|>Á¼<|open_end|>
    <|open|>exec<|.|>requirement<|close|>req<|:|>¢¬<|open_end|>
    <|open|>exec<|.|>output<|close|>assistant<|:|>ãø<|open_end|>

<|open|>assistant<|:|>ãø<|close|>
```

两个字符的块 ID 取自一个固定集合，这个 tokenizer 把它们编码成单个 token，所以无论抽到哪个 ID，寻址一个块都只花两个 token。

角色仍然只有一个 user 轮次，但它的各个组件以五个独立可寻址的块抵达模型，由第六个块（`exec` 块）绑在一起，后者声明：在这些数据上运行这条指令、受这两条要求约束，并把答案放进这里命名的块——也就是模型随后填充的那个 assistant 块。传统 template 会把所有组件压平成一个字符串，让模型自己去推断哪部分是任务、哪部分是主题、哪些是约束。

### LLMON 如何应对 prompt injection 攻击

间接 prompt injection 是一类攻击：把恶意指令藏进数据 payload，比如检索到的文档、工具响应或用户提供的数据。LLMON 的指令/数据分离正是为解决这个问题设计的。

我们把 LLMON preview 与多个开源和闭源模型做了对比，在 [OPI](https://arxiv.org/abs/2310.12815) benchmark 上评估，它把注入放在经典 NLP 任务的数据里，并采用多种攻击策略。我们报告鲁棒性，定义为 1 − 攻击成功率：即模型没有执行注入指令的攻击占比。

[![OPI](https://cdn-uploads.huggingface.co/production/uploads/6484ca4d5ff9a3d2ee52a83b/3UqXuyb58P8n3NiHnJiK4.png)](https://cdn-uploads.huggingface.co/production/uploads/6484ca4d5ff9a3d2ee52a83b/3UqXuyb58P8n3NiHnJiK4.png)

所有非 LLMON 模型都极易受影响，大概率会执行注入的指令。LLMON 在这个 benchmark 上基本消除了该问题：相比我们测过的最佳前沿模型多挡掉 47% 的攻击，相比最佳开源模型多挡掉 95%。其他 benchmark（[ASB](https://arxiv.org/pdf/2410.02644) 和 [StruQ](https://arxiv.org/pdf/2402.06363)）上也观察到类似趋势。值得一提的是，这些 benchmark 测的是对静态间接 prompt injection 的鲁棒性，而指令/数据分离正是直接针对这类攻击。我们也在积极改进对跨多轮对话展开的自适应攻击的防御。

### 通用能力

安全性上的收益并没有以牺牲通用能力为代价。在标准 benchmark 类别上，LLMON 模型的表现与 Granite 4.1 Instruct 模型相当。

[![Granite-4.1 与 LLMON](https://cdn-uploads.huggingface.co/production/uploads/6484ca4d5ff9a3d2ee52a83b/VMIEO4qYlmxLhK0DmMO6C.png)](https://cdn-uploads.huggingface.co/production/uploads/6484ca4d5ff9a3d2ee52a83b/VMIEO4qYlmxLhK0DmMO6C.png)

简而言之，如果你现在在试用 Granite 4.1 3B 或 8B，可以直接换成 LLMON preview，通用性能应当相当，而对 prompt injection 的抵抗力会强得多。不需要任何转换流水线。只要给一轮对话的各部分命名（如上例中的 instruction、data、requirement）就够了。自带的 chat template 会把它们变成 LLMON 块。我们的 LLMON-converters 库还更进一层：如果某个部分本身是结构化的，比如一份 JSON 文档，把它 LLMON 化会保留这层结构，成为带类型、可单独寻址的块，而不是一个不透明的字符串。

### 我们如何训练这些模型

这些模型从 [Granite 4.1](https://huggingface.co/ibm-granite/granite-4.1-8b-base) base checkpoint 起步，而不是已发布的 instruct 模型，所以 LLMON 行为是在后训练阶段学到的，而不是叠加在已有 chat 格式之上。

LLMON 定义了六个分隔符，用来标记标签的起止，并支持嵌套和锚定；它们作为保留的单个 token 装进 tokenizer。我们把一套常规的指令微调语料重新序列化成 LLMON：每个 prompt 组件都成为自己独立的可寻址块，每一轮都带一个执行块，指明要运行哪条指令、它作用于哪些输入、输出放到哪里。任务组合与普通 instruct 模型所见一致（chat、多轮、RAG、工具调用），这也是 benchmark 性能与常规微调模型接近的原因。此外，我们还在数据里加入诱饵指令和数据块：它们出现在上下文中，却刻意不绑定，而目标输出保持不变。这样模型就学会遵循执行块所规定的依赖，忽略其余部分。随后是强化学习：五个连续的 GRPO 阶段，覆盖多领域推理、RLHF、知识校准和数学，最后是一个 DPO 阶段，用一千个 on-policy 偏好对，这些偏好对来自模型自身对注入尝试的响应。

由此产生的权限规则是从这套布局里自然长出来的，而不是外加的护栏：经执行块抵达的指令是权威的，而作为输入抵达的一切（数据、文档、tool schema、tool result）都是供阅读的材料，不是要遵循的命令。此外，执行块里没有被调用的指令和数据片段会被忽略。这是学出来的行为，不是强制保证。想看它在 LLMON 模型的注意力层里如何体现，可以试试 Hugging Face Spaces 上的 [LLMON Attention Visualization](https://huggingface.co/spaces/ibm-granite/LLMON-Attention-Visualization)。

### 带上你自己的词表（ScienceWorld）

LLMON 并不绑定固定的 schema：你可以选适合自己领域的标签名和结构，再微调一个 adapter 来读写它们。我们在 ScienceWorld 上演示了这一点——这是一个基于文本的 benchmark，agent 每次发出一条命令、从模拟器拿到一个分数，以此完成基础科学任务（比如烧水）。我们定义了一套词表，捕捉解决这些任务所涉及的规划轨迹的结构，其中包含 `instr.task.goal`、`req.planning_policy.rule`、`data.state.room`、`data.state.inventory`、`assistant.next_action` 这类标签。我们用这些标签渲染 ScienceWorld 参考解法的每一步，并在一个 LLMON 模型之上微调 LoRA。训练后的模型随后玩留出（held-out）的游戏，用新词表写出下一步动作。[这篇 notebook](https://github.com/generative-computing/llmon/blob/main/llmon/examples/lora-finetuning/byo-vocab_LoRA_scienceworld.ipynb) 走完整个流程：从转换参考轨迹，到玩测试游戏，再到拿 adapter 与未训练的 base 模型对比打分。工具调用 agent 的另一个示例见[这篇 notebook](https://github.com/generative-computing/llmon/blob/main/llmon/examples/lora-finetuning/byo-vocab_LoRA_for_agents.ipynb)。
