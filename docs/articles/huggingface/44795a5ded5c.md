# 🤗 Accelerate 如何借助 PyTorch 运行超大模型

## 加载并运行大模型

Meta AI 和 BigScience 最近开源了非常大的语言模型，它们放不进大多数消费级硬件的内存（RAM 或 GPU）。在 Hugging Face，我们的使命之一就是让这些大模型也能触手可及，因此我们开发了一些工具，让你即便没有超级计算机也能运行这些模型。本文中挑选的所有示例都能在一个免费 Colab 实例（RAM 和磁盘空间有限）上运行；如果你有更多磁盘空间，尽管挑更大的检查点。

这是我们如何运行 OPT-6.7B 的方法：

```
import torch
from transformers import pipeline

# This works on a base Colab instance.
# Pick a larger checkpoint if you have time to wait and enough disk space!
checkpoint = "facebook/opt-6.7b"
generator = pipeline("text-generation", model=checkpoint, device_map="auto", torch_dtype=torch.float16)

# Perform inference
generator("More and more large language models are opensourced so Hugging Face has")
```

我们一会儿会解释每个参数做什么，但首先考虑一下 PyTorch 里传统的模型加载流水线：它通常由以下组成：

- 创建模型
- 在内存中加载它的权重（一个通常叫 `state_dict` 的对象）
- 把这些权重加载进创建好的模型
- 把模型移动到用于推理的设备上

虽然过去这些年这套做法运转得挺好，但超大模型让这种方式变得棘手。这里选中的模型有 67 亿参数。在默认精度下，这意味着仅第 1 步（创建模型）就会在 RAM 中占据约 **26.8GB**（一个 float32 参数在内存中占 4 字节）。这甚至放不进你在 Colab 上得到的 RAM。

然后第 2 步会在内存中加载模型的第二份拷贝（于是默认精度下又是 26.8GB RAM）。如果你想像这样加载最大的模型，例如 BLOOM 或 OPT-176B（都有 1760 亿参数），你需要 1.4 **太字节**的 CPU RAM。这实在有点过分！而这一切只是为了在第 4 步把模型移动到一个（或多个）GPU 上。

显然我们需要更聪明的办法。在这篇文章中，我们会解释 Accelerate 如何利用 PyTorch 的特性来加载和运行超大模型的推理，即便它们放不进 RAM 或单个 GPU。简而言之，它把上面的流程改成这样：

- 创建一个空的（即没有权重的）模型
- 决定每一层将要放到哪里（当有多个设备可用时）
- 在内存中加载其权重的一部分
- 把这些权重加载进空模型
- 把权重移动到用于推理的设备上
- 对下一批权重从第 3 步重复，直到所有权重都加载完毕

## 创建一个空模型

PyTorch 1.9 引入了一种叫 *meta* 设备的新设备类型。这让我们能创建不附带任何数据的张量：meta 设备上的张量只需要一个形状。只要你还在 meta 设备上，你就能创建任意大的张量而无需担心 CPU（或 GPU）的 RAM。

例如，下面这段代码在 Colab 上会崩溃：

```
import torch

large_tensor = torch.randn(100000, 100000)
```

因为这个大张量需要 `4 * 10**10` 字节（默认精度是 FP32，所以张量的每个元素占 4 字节），也就是 40GB 的 RAM。然而在 meta 设备上同样的东西完全没问题：

```
import torch

large_tensor = torch.randn(100000, 100000, device="meta")
```

如果你尝试显示这个张量，PyTorch 会打印如下内容：

```
tensor(..., device='meta', size=(100000, 100000))
```

如我们前面所说，这个张量没有关联的数据，只有一个形状。

你可以直接在 meta 设备上实例化一个模型：

```
large_model = torch.nn.Linear(100000, 100000, device="meta")
```

但对于一个已有的模型，这个语法会要求你重写所有建模代码，让每个子模块都接受并传递一个 `device` 关键字参数。由于这对 Transformers 库的 150 个模型不切实际，我们开发了一个上下文管理器，它会为你实例化一个空模型。

这是你如何实例化一个 BLOOM 的空版本：

```
from accelerate import init_empty_weights
from transformers import AutoConfig, AutoModelForCausalLM

config = AutoConfig.from_pretrained("bigscience/bloom")
with init_empty_weights():
    model = AutoModelForCausalLM.from_config(config)
```

这对任何模型都有效，但你得到的是一个无法直接使用的空壳：一些操作在 meta 设备上实现了，但还不是全部。例如此处，你可以用一个输入来使用上面定义的 `large_model`，但不能用 BLOOM 模型。即便使用它，输出也会是一个 meta 设备上的张量，所以你会得到结果的形状，但仅此而已。

作为这项工作的后续，PyTorch 团队正在开发一个新的 [`FakeTensor` 类](https://pytorch.org/torchdistx/latest/fake_tensor.html)，它有点像 meta 设备上的张量，但带有设备信息（在形状和 dtype 之上）。

由于我们知道每个权重的形状，我们能够知道一旦把预训练张量完全加载后它们总共会消耗多少内存。因此，我们可以决定如何把模型拆分到 CPU 和 GPU 上。

## 计算一个设备映射

在我们开始加载预训练权重之前，我们需要知道希望把它们放到哪里。这样每次把一个权重放到它该在的位置后，我们就能释放对应的 CPU RAM。这可以在 meta 设备上的空模型上完成，因为我们只需要知道每个张量的形状和它的 dtype，就能计算它在内存中会占据多少空间。

Accelerate 提供了一个函数来从空模型自动确定一个 *device map*。它会尝试最大化利用所有可用的 GPU，然后是 CPU RAM，最后把放不下的权重标记为磁盘卸载。我们用 [OPT-13b](https://huggingface.co/facebook/opt-13b) 来看一看。

```
from accelerate import infer_auto_device_map, init_empty_weights
from transformers import AutoConfig, AutoModelForCausalLM

config = AutoConfig.from_pretrained("facebook/opt-13b")
with init_empty_weights():
    model = AutoModelForCausalLM.from_config(config)

device_map = infer_auto_device_map(model)
```

这会返回一个把模块或权重映射到设备的字典。例如在一台有一块 Titan RTX 的机器上，我们得到如下结果：

```
{'model.decoder.embed_tokens': 0,
 'model.decoder.embed_positions': 0,
 'model.decoder.final_layer_norm': 0,
 'model.decoder.layers.0': 0,
 'model.decoder.layers.1': 0,
 ...
 'model.decoder.layers.9': 0,
 'model.decoder.layers.10.self_attn': 0,
 'model.decoder.layers.10.activation_fn': 0,
 'model.decoder.layers.10.self_attn_layer_norm': 0,
 'model.decoder.layers.10.fc1': 'cpu',
 'model.decoder.layers.10.fc2': 'cpu',
 'model.decoder.layers.10.final_layer_norm': 'cpu',
 'model.decoder.layers.11': 'cpu',
 ...
 'model.decoder.layers.17': 'cpu',
 'model.decoder.layers.18.self_attn': 'cpu',
 'model.decoder.layers.18.activation_fn': 'cpu',
 'model.decoder.layers.18.self_attn_layer_norm': 'cpu',
 'model.decoder.layers.18.fc1': 'disk',
 'model.decoder.layers.18.fc2': 'disk',
 'model.decoder.layers.18.final_layer_norm': 'disk',
 'model.decoder.layers.19': 'disk',
 ...
 'model.decoder.layers.39': 'disk',
 'lm_head': 'disk'}
```

Accelerate 评估出嵌入和解码器直到第 9 个块都能放进 GPU（设备 0），然后第 10 个块的一部分需要放在 CPU 上，随后直到第 17 层的权重也放 CPU。接着第 18 层被拆分到 CPU 和磁盘之间，而其后的各层都必须卸载到磁盘。

其实稍后直接使用这个 device map 不会奏效，因为组成这个模型的各层有残差连接（块的输入被加到块的输出上），所以同一个给定层的所有部分都应在同一个设备上。我们可以通过用 `no_split_module_classes` 关键字参数传入一个不应被拆分的模块名列表来把这一点告诉 Accelerate：

```
device_map = infer_auto_device_map(model, no_split_module_classes=["OPTDecoderLayer"])
```

这会随后返回

```
'model.decoder.embed_tokens': 0,
 'model.decoder.embed_positions': 0,
 'model.decoder.final_layer_norm': 0,
 'model.decoder.layers.0': 0,
 'model.decoder.layers.1': 0,
 ...
 'model.decoder.layers.9': 0,
 'model.decoder.layers.10': 'cpu',
 'model.decoder.layers.11': 'cpu',
 ...
 'model.decoder.layers.17': 'cpu',
 'model.decoder.layers.18': 'disk',
 ...
 'model.decoder.layers.39': 'disk',
 'lm_head': 'disk'}
```

现在，每一层始终都在同一个设备上。

在 Transformers 中，当在 `from_pretrained()` 方法或 `pipeline` 里使用 `device_map` 时，这些应当留在同一设备上的块类别会自动提供，所以你无需为它们操心。注意 `device_map` 你有以下选项（仅当你有一个以上 GPU 时才相关）：

- `"auto"` 或 `"balanced"`：Accelerate 会拆分权重，使每块 GPU 被等量使用；
- `"balanced_low_0"`：Accelerate 会拆分权重，使每块 GPU 被等量使用，除了第一块，对第一块它会尽量少放权重（当你想在单块 GPU 上处理模型输出时很有用，例如使用 `generate` 函数时）；
- `"sequential"`：Accelerate 会按顺序填满 GPU（所以最后几块可能根本不会被使用）。

只要遵循我们前面见过的格式（字典：层/模块名到设备），你也可以传入你自己的 `device_map`。

最后，注意你收到的 `device_map` 结果取决于所选的 dtype（不同类型的浮点占据的空间不同）。提供 `dtype="float16"` 会给出不同的结果：

```
device_map = infer_auto_device_map(model, no_split_module_classes=["OPTDecoderLayer"], dtype="float16")
```

在这个精度下，我们能把模型放到第 21 层都放进 GPU：

```
{'model.decoder.embed_tokens': 0,
 'model.decoder.embed_positions': 0,
 'model.decoder.final_layer_norm': 0,
 'model.decoder.layers.0': 0,
 'model.decoder.layers.1': 0,
 ...
 'model.decoder.layers.21': 0,
 'model.decoder.layers.22': 'cpu',
 ...
 'model.decoder.layers.37': 'cpu',
 'model.decoder.layers.38': 'disk',
 'model.decoder.layers.39': 'disk',
 'lm_head': 'disk'}
```

现在我们知道了每个权重应当去哪里，就能逐步把预训练权重加载进模型。

## 对 state dict 分片

传统上，PyTorch 模型保存在一个包含从参数名到权重映射的完整文件里。这个映射通常称为 `state_dict`。这是 [PyTorch 文档](https://pytorch.org/tutorials/beginner/basics/saveloadrun_tutorial.html)关于保存和加载的一段摘录：

```
# Save the model weights
torch.save(my_model.state_dict(), 'model_weights.pth')

# Reload them
new_model = ModelClass()
new_model.load_state_dict(torch.load('model_weights.pth'))
```

这对参数少于 10 亿的模型运转良好，但对更大的模型，这对 RAM 是极大的负担。BLOOM 模型有 1760 亿参数；即便权重以 bfloat16 保存来省空间，它整体仍占据 352GB。虽然训练这个模型的超级计算机可能拥有这么多可用内存，但对推理要求这么多是不现实的。

这正是 Hugging Face Hub 上的大模型不用一个包含所有权重的大文件、而用**多个**文件来保存和共享的原因。例如你去 [BLOOM 模型页面](https://huggingface.co/bigscience/bloom/tree/main)，你会看到有 72 个名为 `pytorch_model_xxxxx-of-00072.bin` 的文件，每个都包含模型权重的一部分。用这种格式，我们可以把 state dict 的一部分加载进内存，把权重放进模型，把它们移动到正确的设备，然后在进入下一部分之前丢弃这份 state dict。与其要求有足够的 RAM 来容纳整个模型，我们只需要足够的 RAM 来加载最大的那个检查点分片——我们称之为一个 **shard**——在 BLOOM 的情况下是 7.19GB。

我们把像 BLOOM 这样保存在多个文件里的检查点称为*分片检查点（sharded checkpoints）*，并把它们的格式标准化如下：

- 一个文件（叫 `pytorch_model.bin.index.json`）包含一些元数据，以及一个从参数名到文件名的映射，指明在哪里能找到每个权重
- 所有其他文件都是标准的 PyTorch state dict，它们只是包含模型的一部分而非全部。你可以在[这里](https://huggingface.co/bigscience/bloom/blob/main/pytorch_model.bin.index.json)查看索引文件的内容。

要把这样一个分片检查点加载进模型，我们只需遍历各个分片。Accelerate 提供了一个叫 `load_checkpoint_in_model` 的函数，如果你克隆了 Hub 的某个仓库，它会替你完成这件事；或者你可以直接使用 Transformers 的 `from_pretrained` 方法，它会替你处理下载和缓存：

```
import torch
from transformers import AutoModelForCausalLM

# Will error
checkpoint = "facebook/opt-13b"
model = AutoModelForCausalLM.from_pretrained(checkpoint, device_map="auto", torch_dtype=torch.float16)
```

如果自动计算的 device map 需要某些权重被卸载到磁盘（因为你没有足够的 GPU 和 CPU RAM），你会得到一个错误，提示你需要提供一个文件夹来存放那些应当存在磁盘上的权重：

```
ValueError: The current `device_map` had weights offloaded to the disk. Please provide an 
`offload_folder` for them.
```

加上这个参数应当能解决该错误：

```
import torch
from transformers import AutoModelForCausalLM

# Will go out of RAM on Colab
checkpoint = "facebook/opt-13b"
model = AutoModelForCausalLM.from_pretrained(
    checkpoint, device_map="auto", offload_folder="offload", torch_dtype=torch.float16
)
```

注意，如果你试图加载一个在 CPU 卸载之上还需要磁盘卸载的超大模型，当检查点最后的分片被加载时你可能会 RAM 耗尽，因为留在 CPU 上的那部分模型也在占用空间。如果确实如此，使用 `offload_state_dict=True` 选项，在权重全部加载期间临时把留在 CPU 上的那部分模型卸载到磁盘，并在所有权重处理完毕后将其重新加载进 RAM。

```
import torch
from transformers import AutoModelForCausalLM

checkpoint = "facebook/opt-13b"
model = AutoModelForCausalLM.from_pretrained(
    checkpoint, device_map="auto", offload_folder="offload", offload_state_dict = True, torch_dtype=torch.float16
)
```

这能放进 Colab，但会用得如此接近所有可用 RAM，以至于当你尝试生成一个预测时会 RAM 耗尽。要得到一个我们能使用的模型，我们需要再往磁盘上卸载一层。我们可以通过取上一节计算出的 `device_map`、略作调整，然后把它传给 `from_pretrained` 调用来做到这点：

```
import torch
from transformers import AutoModelForCausalLM

checkpoint = "facebook/opt-13b"
device_map["model.decoder.layers.37"] = "disk"
model = AutoModelForCausalLM.from_pretrained(
    checkpoint, device_map=device_map, offload_folder="offload", offload_state_dict = True, torch_dtype=torch.float16
)
```

## 运行一个拆分在多设备上的模型

我们尚未涉及的最后一部分，是 Accelerate 如何让你的模型在其权重分散在多块 GPU、CPU RAM 和磁盘文件夹的情况下运行。这是用一个非常简单的机制——钩子（hooks）——完成的。

> 钩子是一个 PyTorch API，它添加在每次前向传播之前紧接着执行的函数

我们本来无法直接使用它，因为它们只支持 forward 中带常规参数、不带关键字参数的模型，但我们采用了同样的思路。一旦模型加载完毕，`dispatch_model` 函数会为每个模块和子模块添加钩子，它们在每次前向传播前后被执行。它们会：

- 确保模块的所有输入都和权重在同一个设备上；
- 如果权重被卸载到了 CPU，就在前向传播之前把它们移动到 GPU 0，并就在前向传播之后移回 CPU；
- 如果权重被卸载到了磁盘，就在前向传播之前把它们加载进 RAM 再到 GPU 0，并就在前向传播之后释放这份内存。

整个过程在下面的视频中做了总结。

这样一来，即便你没有足够的 GPU RAM 和 CPU RAM，你的模型也能被加载和运行。你所需要的只是磁盘空间（以及大量的耐心！）虽然这个方案如果你有多块 GPU 时相当朴素（不涉及巧妙的流水线并行，只是按顺序使用各 GPU），但它仍为 BLOOM 带来了[相当不错的结果](https://huggingface.co/blog/bloom-inference-pytorch-scripts)。而且它让你能在更小的配置上运行模型（尽管更慢）。

要了解更多关于 Accelerate 大模型推理的内容，请参阅[文档](https://huggingface.co/docs/accelerate/usage_guides/big_modeling)。
