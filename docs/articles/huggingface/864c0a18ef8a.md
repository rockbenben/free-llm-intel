# Open LLM 排行榜发生了什么？

最近，随着 [**Falcon 🦅**](https://huggingface.co/tiiuae/falcon-40b) 发布并被加入 [Open LLM Leaderboard](https://huggingface.co/spaces/HuggingFaceH4/open_llm_leaderboard)（一个对比开放访问大语言模型的公开排行榜），Twitter 上掀起了一场有趣的讨论。

讨论的焦点是排行榜展示的四个评测之一：一个用于衡量 [Massive Multitask Language Understanding](https://arxiv.org/abs/2009.03300)（简称 MMLU）的基准。

让社区感到意外的是，排行榜当前头名 [**LLaMA 模型 🦙**](https://ai.facebook.com/blog/large-language-model-llama-meta-ai/) 的 MMLU 评测分数，比 [LLaMA 论文](https://arxiv.org/abs/2302.13971)中报告的数字低了一大截。

于是我们决定钻进兔子洞，搞清楚到底发生了什么、该怎么修 🕳🐇

在这个过程中，我们和两位大牛做了交流：参与过 LLaMA 评测的 [@javier-m](https://huggingface.co/javier-m)，以及 Falcon 团队的 [@slippylolo](https://huggingface.co/slippylolo)。话虽如此，下文中的所有错误当然都应该归咎于我们，而不是他们！

跟着我们走完这段旅程，你会了解到：可以用哪些方式在单个评测中衡量一个模型，以及在网上和论文里看到的数字到底值不值得信。

准备好了吗？系好安全带，我们要起飞了 🚀。

## 什么是 Open LLM Leaderboard？

首先注意，[Open LLM Leaderboard](https://huggingface.co/spaces/HuggingFaceH4/open_llm_leaderboard) 实际上只是一个包装器，底层跑的是开源基准测试库 [Eleuther AI LM Evaluation Harness](https://github.com/EleutherAI/lm-evaluation-harness)。这个库由非营利 AI 研究实验室 [EleutherAI](https://www.eleuther.ai/) 打造——他们以创建 [The Pile](https://pile.eleuther.ai/) 和训练 [GPT-J](https://huggingface.co/EleutherAI/gpt-j-6b)、[GPT-Neo-X 20B](https://huggingface.co/EleutherAI/gpt-neox-20b)、[Pythia](https://github.com/EleutherAI/pythia) 而闻名。这支团队在 AI 圈的资历相当硬核！

这个包装器利用 Hugging Face 计算集群的闲置算力，用 Eleuther AI harness 跑评测，把结果存到 hub 上的一个 dataset 里，再展示到 [线上排行榜 space](https://huggingface.co/spaces/HuggingFaceH4/open_llm_leaderboard)。

对于 LLaMA 系列模型，用 [Eleuther AI LM Evaluation Harness](https://github.com/EleutherAI/lm-evaluation-harness) 得到的 MMLU 数字与 LLaMA 论文中报告的数字差距明显。

这是为什么呢？

## MMLU 的一千零一种做法

原来，LLaMA 团队参考的是网上另一份代码实现：由开发 MMLU 基准的 UC Berkeley 原班团队提出的评测代码（见 [https://github.com/hendrycks/test](https://github.com/hendrycks/test)），我们在这里称之为**"Original implementation（原始实现）"**。

再深挖一层，我们又发现了针对同一个 MMLU dataset 的第三种评测实现：Stanford [CRFM](https://crfm.stanford.edu/) 那份非常全面的评测基准 [Holistic Evaluation of Language Models](https://crfm.stanford.edu/helm/latest/) 提供的评测代码，我们称之为 **HELM 实现**。

EleutherAI Harness 和 Stanford HELM 这两个基准的价值在于，它们把大量评测（包括 MMLU）收拢在一个代码库里，因此能给出模型性能的全景视图。这也是 Open LLM Leaderboard 选择包装这类"整体式"基准、而不是为每个评测单独用一套代码库的原因。

为了把这事定下来，我们决定把这三种同一 MMLU 评测的实现都跑一遍，对一组模型做评测，并按结果给它们排名：

- Harness 实现（[commit e47e01b](https://github.com/EleutherAI/lm-evaluation-harness/tree/e47e01beea79cfe87421e2dac49e64d499c240b4)）
- HELM 实现（[commit cab5d89](https://github.com/stanford-crfm/helm/tree/cab5d89fadbff86190f29ddfa497301958eaf2ec)）
- 原始实现（由 [@olmer](https://huggingface.co/olmer) 做了 Hugging Face 集成，见 [https://github.com/hendrycks/test/pull/13](https://github.com/hendrycks/test/pull/13)）

（注意，Harness 实现最近已经更新了——详情见本文末尾）

结果令人意外：

[![png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-01-ter-01.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-01-ter-01.png)

完整的评测数字可以在文末找到。

同一个基准的这几份不同实现给出的数字差距很大，甚至连排行榜上模型的排名顺序都会改变！

我们先来弄清楚这种差异从何而来 🕵️ 不过在那之前，先简要了解一下我们是怎样自动评估现代 LLM 的行为的。

## 在当今的 LLM 时代，我们如何自动评测一个模型

MMLU 是一份四选一的选择题测试，算是相当简单的基准（相比开放式问答而言），但正如我们将看到的，这仍给实现细节和差异留下了很大空间。该基准的问题覆盖 57 个通用知识领域，归入几个粗粒度类别："人文"、"社会科学"、"STEM" 等，每个问题有四个候选答案。

每个问题只有一个正确答案。这里举个例子：

```
Question: Glucose is transported into the muscle cell:


Choices:
A. via protein transporters called GLUT4.
B. only in the presence of insulin.
C. via hexokinase.
D. via monocarbylic acid transporters.


Correct answer: A
```

注：你可以很方便地在 hub 的 [dataset viewer](https://huggingface.co/datasets/cais/mmlu/viewer/college_medicine/dev?row=0) 里浏览这个 dataset 的更多内容。

大语言模型在 AI 模型动物园里算是简单的模型。它们以*一段文本字符串*作为输入（称为 "prompt"），输入被切分成 token（词、子词或字符，取决于模型的构建方式）后喂给模型。模型基于这个输入，在它所知道的全部 token（即模型的"词表 / vocabulary"）上生成下一个 token 的概率分布；因此你就能知道任意 token 作为输入 prompt 的延续有多大 `概率`。

我们可以利用这些概率来挑选 token，比如挑概率最高的那个（也可以用采样引入一点噪声，避免答案显得"太机械"）。把选出的 token 追加到 prompt 上再喂回模型，就能生成下一个 token，如此往复，直到整句整句地续写出输入 prompt 之后的内容：

[![png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-01.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-01.png)

ChatGPT 和 Hugging Chat 生成答案靠的就是这个机制。

总结一下，我们从模型中提取信息用于评测主要有两种方式：

- 获取某些特定 token 组作为 prompt 延续的**概率**——并针对预先设定的几个候选答案**把这些概率放在一起比较**；
- 让模型做一次**文本生成**（如前所述反复挑选 token）——并**把生成的文本**与几个预定义候选答案的文本做比较。

带着这些知识，我们来深入剖析 MMLU 的三种实现，看看各自给模型发送什么样的输入、期望什么样的输出、以及输出是如何被比较的。

## 那么，拿到 prompt 之后如何评测模型？

先看 [原始 MMLU 实现](https://github.com/hendrycks/test/pull/13)是如何提取模型预测的。在原始实现中，我们只比较模型对四个答案字母预测的概率：

[![png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-02.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-02.png)

某些情况下这对模型是有利的，比如下面的例子：

[![png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-03.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-03.png)

在这个例子里，模型把正确答案排在了 4 个选项中的第一位，于是拿到 +1 分。但如果看完整词表，它其实更倾向于生成一个四个选项之外的词："Zygote"（这只是个示意例子，不是真实用例 🙂）

怎样才能让模型尽量少犯这类错误？

可以用 **few shots（少样本）**方法：在 prompt 里给模型提供一个或多个示例，并附上期望的答案。看起来是这样的：

[![png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-04.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-04.png)

这里，模型有了一个期望行为的示例，就不太可能给出预期范围之外的答案了。

由于这种方法能提升性能，在我们所有的评测（原始实现、EleutherAI LM Harness 和 HELM）中，MMLU 通常都采用 5-shot（每个 prompt 前面拼 5 个示例）来评测。（注意：各基准虽然用的是同样 5 个示例，但向模型展示它们的顺序可能不同，这也是一个潜在的差异来源，我们在这里不予深究。另外显然还要注意别在你用的 few-shot 示例里泄露答案……）

**HELM：** 接下来看 [HELM 实现](https://github.com/stanford-crfm/helm/tree/cab5d89fadbff86190f29ddfa497301958eaf2ec)。虽然 few-shot prompt 大体相似，但对模型的评测方式和刚才的原始实现截然不同：我们用模型的下一个 token 输出概率来选定一段生成文本，再把它和期望答案的文本做比较，如图所示：

[![png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-05.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-05.png)

这种情况下，如果 "Zygote" 这个 token 的概率反而最高（如前文所示），模型的答案（"Zygote"）就是错的，这道题模型一分也拿不到：

[![png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-06.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-06.png)

**Harness：** 最后来看 [截至 2023 年 1 月的 EleutherAI Harness 实现](https://github.com/EleutherAI/lm-evaluation-harness/tree/e47e01beea79cfe87421e2dac49e64d499c240b4)——排行榜最早那批数字就是用它算出来的。如我们所见，这里又是另一种在同一个评测 dataset 上给模型打分的方式（注意这个实现最近已更新——详情见文末）。

这种方法同样用概率，但用的是完整答案序列的概率：字母加上答案文本，例如 "C. The second pharyngeal arch"。要计算完整答案的概率，先像前面那样拿到每个 token 的概率，再把它们汇总起来。为了数值稳定，汇总方式是取概率的对数再求和，并且可以选择是否做归一化——把总和除以 token 数，避免给长答案太多优势（详情后文展开）。看起来是这样的：

[![png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-07.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/evaluating-mmlu-leaderboard/LLM-07.png)

这里用一个表格总结三种实现提供给模型的答案和期望模型生成的内容，回顾一下到目前为止的内容：

| Original implementation | HELM | AI Harness (as of Jan 2023) |
| --- | --- | --- |
| 我们比较以下答案字母的预测概率： | 模型应生成以下答案字母对应的文本： | 我们比较以下完整答案的概率： |
| A   B   C   D | A | A. It damaged support for the US model of political economy and capitalism   B. It created anger at the United States for exaggerating the crisis   C. It increased support for American global leadership under President Obama   D. It reduced global use of the US dollar |

三种方式都讲完了！

现在来比较模型在这三种评测方式下的得分：

|  | MMLU (HELM) | MMLU (Harness) | MMLU (Original) |
| --- | --- | --- | --- |
| llama-65b | **0.637** | 0.488 | **0.636** |
| tiiuae/falcon-40b | 0.571 | **0.527** | 0.558 |
| llama-30b | 0.583 | 0.457 | 0.584 |
| EleutherAI/gpt-neox-20b | 0.256 | 0.333 | 0.262 |
| llama-13b | 0.471 | 0.377 | 0.47 |
| llama-7b | 0.339 | 0.342 | 0.351 |
| tiiuae/falcon-7b | 0.278 | 0.35 | 0.254 |
| togethercomputer/RedPajama-INCITE-7B-Base | 0.275 | 0.34 | 0.269 |

可以看到，面对同一个 dataset，无论是绝对分数还是模型排名（见第一张图），对评测方法的选择都非常敏感。

假设你自己训练出一份对 LLaMA 65B 的完美复现，用 harness 评测（得分 0.488，见上表），现在拿去和论文里的数字（在原始 MMLU 实现上评测，得分 0.637）比较。分数差了 30%，你大概会想："天哪，我的训练肯定彻底搞砸了 😱"。但事实恰恰相反——这两个数字根本不可比，哪怕它们都叫"MMLU 分数"，哪怕它们是在同一个 MMLU dataset 上评出来的。

那么，在我们看到的这几种方法里，有没有"最佳评测方式"？这是个棘手的问题。正如排名会变化所显示的，不同模型用不同方法评测可能表现各异。为了尽量公平，人们可能倾向于选那种让所有被测模型平均分最高的实现，这样就能从模型中"解锁"尽可能多的能力。按我们的数据，那就意味着用原始实现的 log-likelihood 选项。但如前所述，使用 log-likelihood 其实也在某种程度上给模型提供了提示——它限制了候选答案的范围，从而可能过多地帮助了较弱的模型。而且 log-likelihood 对开源模型容易获取，对闭源 API 模型却不一定暴露。

## 结论

这段旅程的一个重要启示是：评测与其实现深度绑定——细到 prompt 和 tokenization 这样的微小细节。仅仅标注"MMLU 结果"这几个字，并不能告诉你多少把它和其他库评出的数字做比较的依据。

这正是开放的、标准化的、可复现的基准——如 [EleutherAI Eval Harness](https://github.com/EleutherAI/lm-evaluation-harness/) 和 [Stanford HELM](https://github.com/stanford-crfm/helm/)——对社区弥足珍贵的原因。没有它们，跨模型、跨论文比较结果将无从谈起，LLM 的改进研究也会被拖慢。

**附记**：就 Open LLM Leaderboard 而言，我们决定坚持使用社区维护的评测库。幸运的是，在撰写这篇博客期间，EleutherAI Harness 社区（尤其是 [ollmer](https://github.com/EleutherAI/lm-evaluation-harness/issues/475)）完成了一项出色工作：更新了 harness 中的 MMLU 评测，使其与原始实现一致、数字对得上。

我们目前正在用更新版的 [EleutherAI Eval Harness](https://github.com/EleutherAI/lm-evaluation-harness/) 刷新整个排行榜，接下来几周会看到来自 Eleuther Harness v2 的新分数！（把所有模型重跑一遍需要一些时间，敬请期待 :hugs:）
