# Harness、Scaffold，以及值得说清楚的 AI 智能体术语

当一个领域快速演进时，它的词汇往往比它的共识演进得更快。术语开始变得模糊、在不同语境里被重复使用，或成为一些从未被彻底解释清楚的念头的简写。我们如今正看到 AI 智能体领域发生这种情况——概念被混在一起，有些被改名，另一些被广泛使用了几个月后又悄然消失。

这对新人来说可能令人不知所措，甚至对试图跟上最新进展的从业者也是如此。ICLR 2026 之后，我们中的一位（[@ariG23498](https://x.com/ariG23498/status/2049668725511737663)）发布了一个很好地捕捉到这种困惑的问题：

> "在智能体的语境里，你们说的 'harness' 和 'scaffold' 这两个词到底是什么意思？我在 ICLR 期间听了很多解释，但我无法理解它们为什么没有收敛到一个统一的解释。"

这份术语表是我们试图为那些反复出现却没有清晰、一致解释的术语奠基的尝试。它并不打算成为该领域每个术语的完整词典。相反，我们聚焦于那些常被混淆、被以不同方式使用、或被视为不言自明其实并非如此的诸概念。

无论你是在构建智能体、部署一个，还是仅仅使用 Claude Code、Codex 或 Hermes Agent 这类工具，其中大多数术语都会出现。最后一节涵盖与训练模型相关、更契合你那一边工作的概念。

> 这些术语中的许多还没有被普遍接受的定义，而不同框架对同一个词用法各异。这里的目标不是强行推行一套正确的词汇，而是提供一个实用的心智模型，让讨论更容易跟上。

我们开始吧。

## 模型（Model）

模型就是那个 LLM：它接收文本输入、产出文本输出（例如 Claude、Qwen、GPT、Kimi、DeepSeek……）。就其本身而言，它在两次调用之间没有记忆，也没有循环。模型可以表达调用一个工具的意图，但它需要一个 harness 来真正执行它。它回答一个提示然后就停下。把它包进 scaffold 和 harness，它就变成了一个智能体。

## 脚手架（Scaffolding）

围绕模型、定义行为的那一层：系统提示、工具描述、模型回复如何被解析、它在各步之间记住什么（上下文管理）。无论在训练期间还是推理期间，它都塑造着模型如何看待世界并在其中行动。

Claude Code、Codex、Antigravity CLI 这样的产品把整个东西称为一个 harness。Claude Code 的[官方文档](https://code.claude.com/docs/en/how-claude-code-works)直接这么说："Claude Code 充当 Claude 周围的 agentic harness。"这是宽泛用法：harness 意味着除模型之外的一切。scaffold 与 harness 的区分，在你需要分别推理它们时最为重要，比如在一条训练流水线里。你也会听到 "scaffold" 被更宽泛地使用，以涵盖 harness 所依赖的任何基础设施：hooks、运行时配置，甚至目录结构。

一些产品（如 Claude Code 和 Codex）与其提供方的模型紧密耦合。另一些（如 Antigravity CLI 和 Hermes Agent）则让你插入任何模型。

## 线束（Harness）

智能体内部的执行层：它调用模型、处理模型的工具调用、决定何时停止。harness 是让智能体跑起来的东西。上面定义的 scaffolding 是模型据以工作的东西：它的指令、它的工具、它的格式。

**Harness 工程（harness engineering）** 是把这一层设计好的学问：决定智能体何时应当停止、错误如何处理，以及用哪些护栏让它保持在轨道上。它在训练和推理两端都适用。[Addy Osmani 的文章](https://www.oreilly.com/radar/agent-harness-engineering/)和 [OpenAI 关于用 Codex 构建的记述](https://openai.com/index/harness-engineering/)都从推理一侧涵盖了这一点。

在评估时，同一模式以一个 **eval harness（评估线束）** 的形式出现：它不收集训练数据，而是在一个模型检查点上运行一整套固定场景，并记录指标而非更新权重。

一些框架用 **orchestrator（编排器）** 指一个更高层的控制器，它跨多个智能体协调工作。与把模型驱动过一个执行循环的 harness 不同，orchestrator 把智能体作为单元来管理，每个都运行自己的 harness（见下文 Sub-agents）。

## 智能体（Agent）

这个术语来自强化学习，在强化学习中一个智能体只是一个接收观察、返回动作的函数。环境接收那个动作、返回一个新观察，循环重复。这个循环仍是 LLM 智能体如何工作的核心。

在 LLM 世界里，这个术语已经扩展。一个智能体是一个模型加上围绕它的一切，让它能行动，而非只是响应。它把原始的文本生成变成某种能在循环中行动的东西：接收信息、决定做什么、并根据结果行动。

以一个编码智能体为具体例子。系统提示、工具描述，以及模型遵循的输出格式，构成 scaffolding。那个调用模型、处理它的工具调用、决定何时停止的循环就是 harness。在训练时，harness 还会并行运行许多这样的循环，并把结果反馈回来以更新模型。

[![Agent diagram showing Harness, Scaffold, and Model as components inside Agent, with Sub-agent below](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/agent-glossary/agent-diagram.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/agent-glossary/agent-diagram.png)

在社区里，它通常被表述为 **Agent = Model + Harness**（参考 [@Vtrivedy10](https://x.com/Vtrivedy10/status/2031408954517971368) 和 [Will Brown 的推文](https://x.com/willccbb/status/2049844685095715289)）。如果你不是模型，你就是 harness。harness 与 scaffold 之间那个造成绝大部分困惑的微妙区别，正是上面两节要处理的。

当人们谈论像 Claude Code、Codex 或 Cursor 这样的产品时，他们指的是一个建立在某个特定模型之上、被一起设计和优化的特定 harness。两个使用同一底层模型的产品可能感觉完全不同，因为它们的 harness 做了不同的选择。而把一个更好的模型换进同一个 harness，同样会改变体验。模型、harness 和产品是三样不同的东西。

## 上下文工程（Context Engineering）

设计哪些东西进入智能体的上下文窗口：模型在每一步看到什么、系统提示、工具描述、对话历史、检索到的知识。它不是一次性的决策：随着模型运行，先前的轮次塑造着未来调用里的内容，而 harness 在整个运行期间主动管理这些。它在训练和推理两端都适用，但出错的代价大不相同。在训练时，模型看到什么会塑造学到什么。搞错了，你就得重训。在推理时，它只是文本：改一个提示、重新部署即可。[HF 上下文工程课程](https://huggingface.co/learn/context-course/en/unit0/introduction)对此做了深入讲解。

记忆是这幅图景的一部分。**短期记忆**是单次运行期间留在上下文窗口里的东西：对话历史、工具结果、先前的推理。**长期记忆**跨会话持久存在，被外部存储、按需检索，然后在相关时注入回上下文。

## 策略（Policy）

策略是智能体所遵循的行为：给定任何情境，它定义采取每个可能动作的概率。在 LLM 系统中，那策略的一部分在模型权重中被学到，但行为也取决于周围的 scaffolding 和 harness。同一个模型，根据其提示、工具、记忆和执行循环的不同，可能表现得非常不同。

策略不是智能体。策略定义行为；智能体是在环境中行动的完整系统。把一个检查点包进 scaffolding 和 harness 并部署它，你就得到一个行为即策略的智能体。

## 工具使用（Tool Use）

智能体如何伸向自身之外：API、代码解释器、数据库、web 搜索、文件系统。模型以结构化格式表达使用某个工具的意图。现代推理 API 把这呈现为一等对象：harness 直接接收该调用并把它路由到正确的函数。结果被反馈回上下文，循环继续。

## 技能（Skills）

可复用的、结构化的知识包，用于支撑多步任务。如果说一个**工具（tool）**是一个动作（"运行这个命令"），那么一个**技能（skill）**打包了达成某个目标所需的一切（"调查这个 bug、形成假设、写一个修复"）。它们可在智能体之间移植，并按需加载。工具、技能与子智能体之间的界限在不同框架间会移动。[HF 上下文工程课程](https://huggingface.co/learn/context-course/en/unit1/introduction)对技能做了深入讲解。

## 子智能体（Sub-agents）

由另一个智能体调用、用来处理某个具体子任务的智能体。它有自己的模型和 scaffold，独立推理，并返回一个结果。调用的那个智能体无需知道它内部如何工作。这正是一个**子智能体**区别于一个**工具**（一次函数调用）或一项**技能**（打包的知识）之处：子智能体自身能推理、使用工具，并调用进一步的子智能体。调用的那个智能体有时被称为一个 **orchestrator（编排器）**。

## 训练（Training）

上面的术语无论你是在训练还是部署都适用。下面这四个是训练特有的——在训练里，智能体跑过任务、被打分，其模型权重被更新。每个面向 LLM 的 RL 训练系统都建立在同一条流水线周围：

### RL 环境（RL Environment）

环境是你能够与之交互的任何东西：一个有状态的对象，它接收一个动作作为输入、更新其内部状态、并返回一个观察。在 LLM 语境中，动作通常是工具调用。文件系统是一个简单例子：动作 `touch foo.txt` 通过创建文件来更新状态，而观察可能是更新后的文件列表。定义在各框架间有所不同。

我们最近发布了一份专门指南，所以与其在这里压缩，请看[《RL 环境终极指南》](https://huggingface.co/spaces/AdithyaSK/rl-environments-guide)以获得类型、框架和示例的完整拆解。

### 训练器（Trainer）

训练器是让智能体变得更好的东西：它运行许多智能体 episode、对结果打分并用它们来更新内部模型的权重。[TRL 的 GRPOTrainer](https://huggingface.co/docs/trl/main/en/grpo_trainer) 是一个具体例子：一个单独处理 episode 生成、奖励打分和权重更新的类。

### 轨迹采样（Rollout）

一次 rollout 是从头到尾的一整趟智能体运行：智能体看到了什么、做了什么，以及每一步得到了什么奖励。根据语境，它也被称作*trajectory（轨迹）*或*trace（痕迹）*。这是 RL 算法从中学习的原始数据。

### 奖励（Reward）

告诉训练算法模型是否在变好的那个分数。它可以是*可验证的*（测试通过/失败、答案匹配），或*学得的*（人类偏好、LLM-as-judge），*稀疏的*（在 episode 末尾一个分数），或*稠密的*（每一步一个分数）。这是训练器实际用来更新内部模型权重的东西。要对每种类型做彻底拆解，请看 [Adithya](https://huggingface.co/AdithyaSK) 的指南中的 [Reward Architecture](https://huggingface.co/spaces/AdithyaSK/rl-environments-guide#dimension-4-reward-architecture) 一节。

**评分细则（Rubrics）** 把奖励拆分成带权重的显式维度，而非一个单一数字。[OpenEnv](https://github.com/meta-pytorch/OpenEnv) 和 [Verifiers](https://github.com/willccbb/verifiers) 把评分细则实现为你可以组合的对象（`WeightedSum`、`Sequential`、`Gate`）。
