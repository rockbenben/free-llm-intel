Open Responses 是一项全新的开放推理标准。它由 OpenAI 发起、开源 AI 社区共建、并获得 Hugging Face 生态支持。Open Responses 基于 Responses API 设计，面向智能体（Agents）的未来。在这篇博客中，我们将看看 Open Responses 是如何工作的，以及开源社区为什么应该使用它。

聊天机器人的时代早已过去，智能体主导着推理工作负载。开发者正转向能够推理、规划并在长时间跨度上行动的智能系统。尽管发生了这种转变，生态中很大部分仍在用 **Chat Completion** 格式——它是为回合制对话设计的，用于智能体场景力不从心。**Responses 格式**为弥补这些局限而生，但它闭源、尚未被广泛采用。尽管有替代方案，**Chat Completion** 仍是事实上的标准。

智能体工作流需求与根深蒂固的接口之间的这种错位，催生了对开放推理标准的需求。未来几个月，我们将与社区和推理提供商合作，把 Open Responses 实现并适配为一个共享格式，实际能力上足以取代 chat completions。

Open Responses 延续了 OpenAI 在 2025 年 3 月推出的 [*Responses API*](https://platform.openai.com/docs/api-reference/responses) 的方向。该 API 取代了原有的 Completion 和 Assistants API，用一致的方式实现：

- 生成文本、图像和 JSON 结构化输出
- 通过独立的基于任务（task-based）的端点创建视频内容
- 在提供商侧运行智能体循环，自主执行工具调用并返回最终结果。

## 什么是 Open Responses？

Open Responses 扩展并开源了 Responses API，让构建者和路由提供商更容易互操作、在共同利益上协作。

几个要点：

- 默认无状态（stateless），并为有需要的提供商支持加密推理。
- 标准化的模型配置参数。
- 流式被建模为一连串语义事件，而非原始文本或对象增量。
- 可扩展：针对特定模型提供商的可配置参数。

## 用 Open Responses 构建需要知道什么？

我们简要浏览一下对大多数社区成员影响最大的核心变化。想深入研读规范，请查看 [Open Responses 文档](https://www.openresponses.org/)。

### 客户端向 Open Responses 发起请求

向 Open Responses 的客户端请求与现有的 Responses API 类似。下面用 curl 演示一次对 Open Responses API 的请求。我们调用的是一个代理端点，它按 Open Responses API schema 路由到 Inference Providers。

```
 curl https://evalstate-openresponses.hf.space/v1/responses \
   -H "Content-Type: application/json" \
   -H "Authorization: Bearer $HF_TOKEN" \
+  -H "OpenResponses-Version: latest" \
   -N \
   -d '{
         "model": "moonshotai/Kimi-K2-Thinking:nebius",
         "input": "explain the theory of life"
       }'
```

### 推理客户端与提供商需要做的改变

已支持 Responses API 的客户端可以相对省力地迁移到 Open Responses。主要变化在于推理内容如何暴露：

- 推理可见性扩展：Open Responses 为推理条目正式定义了三个可选字段：`content`（原始推理轨迹）、`encrypted_content`（提供商特定的受保护内容）和 `summary`（由原始轨迹净化而来）。

OpenAI 的模型过去只暴露 `summary` 和 `encrypted_content`。有了 Open Responses，提供商可以通过 API 暴露其原始推理。以前只能拿到摘要和加密内容的提供商，其客户端在所选提供商支持时，将有机会接收并处理原始推理流。

- 实现更丰富的状态变化与负载，包括更细的可观测性——例如，托管的 Code Interpreter 可以发送一个特定的 `interpreting` 状态，改善长时间运行操作期间智能体和用户的可见性。

对模型提供商而言，如果已经遵循 Responses API 规范，实现 Open Responses 的改动应当不难。对路由器（Routers）而言，现在有机会统一到一致的端点上，并在需要时支持用于定制的配置选项。

随着时间推移、提供商持续创新，某些功能会被标准化进基础规范。

总之，迁移到 Open Responses 会让推理体验更一致、质量更高——旧 Completions API 的未记载扩展、各种解读和变通做法，都会在 Open Responses 中被规范化。

下面可以看到如何流式接收推理分块。

```
 {
  "model": "moonshotai/Kimi-K2-Thinking:together",
  "input": [
    {
      "type": "message",
      "role": "user",
      "content": "explain photosynthesis."
    }
  ],
  "stream": true
}
```

以下是获取 Open Response 与使用 OpenAI Responses 在推理增量上的区别：

```
// Open weight models stream raw reasoning
event: response.reasoning.delta
data: { "delta": "User asked: 'Where should I eat...' Step 1: Parse location...", ... }

// Models with encrypted reasoning send summaries, or sent as a convenience by Open Weight models
event: response.reasoning_summary_text.delta
data: { "delta": "Determined user wants restaurant recommendations", ... }
```

### 用于路由的 Open Responses

Open Responses 区分"模型提供商"（Model Providers，提供推理的一方）和"路由器"（Routers，在多个提供商之间做编排的中间层）。

客户端现在可以在发起请求时指定提供商以及提供商特有的 API 选项，让中间的路由器能在上游提供商之间编排请求。

### 工具

Open Responses 原生支持两类工具：内部工具和外部工具。外部托管工具在模型提供商系统之外实现，例如待执行的客户端函数或 MCP 服务器。内部托管工具位于模型提供商系统之内，例如 OpenAI 的文件搜索或 Google Drive 集成。模型在提供商基础设施内完整地调用、执行并获取结果，无需开发者介入。

### 子智能体循环

Open Responses 把智能体循环正式化了——它通常是由推理、工具调用、响应生成构成的重复循环，使模型能够自主完成多步骤任务。

[![process diagram](https://huggingface.co/huggingface/documentation-images/resolve/main/openresponses/image1.png)](https://huggingface.co/huggingface/documentation-images/resolve/main/openresponses/image1.png)

[图片来源：openresponses.org](https://www.openresponses.org/specification#the-agentic-loop)

循环的运行方式如下：

- API 收到用户请求，从模型采样
- 如果模型发出工具调用，API 就执行它（内部或外部）
- 工具结果被回传给模型以继续推理
- 循环重复，直到模型发出完成信号

对于内部托管工具，提供商管理整个循环：执行工具、把结果返回给模型、流式输出。这意味着"搜索文档、总结发现、然后起草邮件"这样的多步骤工作流只需一次请求。

客户端可以通过 `max_tool_calls` 限制迭代次数，通过 `tool_choice` 约束哪些工具可被调用：

```
{
  "model": "zai-org/GLM-4.7",
  "input": "Find Q3 sales data and email a summary to the team",
  "tools": [...],
  "max_tool_calls": 5,
  "tool_choice": "auto"
}
```

响应中包含所有中间条目：工具调用、结果、推理。

## 下一步

Open Responses 扩展并改进了 Responses API，提供更丰富细致的内容定义、兼容性和部署选项。它还为在主推理调用中执行子智能体循环提供了标准方式，为 AI 应用打开了强大的能力空间。我们期待与 Open Responses 团队**以及整个社区**在未来共同推进规范的演进。
