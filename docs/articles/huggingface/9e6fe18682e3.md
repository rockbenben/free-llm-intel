# 从文件到数据块：提升 HF 存储效率

本文另有中文版本 [简体中文](https://huggingface.co/blog/zh/from-files-to-chunks)。

Hugging Face 在 [Git LFS 仓库](https://huggingface.co/docs/hub/en/repositories-getting-started#requirements)中存储了超过 [30 PB 的模型、数据集和 spaces](https://huggingface.co/spaces/xet-team/lfs-analysis)。由于 Git 以文件为单位存储和版本化，对文件的任何改动都需要重新上传整个资产——这在 Hub 上代价高昂：平均 Parquet 和 CSV 文件在 200—300 MB 之间，平均 Safetensor 文件约 1 GB，GGUF 文件可超过 8 GB。想象一下只改一行 GGUF 文件的元数据，却要等待几 GB 的文件上传：除了用户时间和传输成本，Git LFS 还需要保存两个文件的完整版本，使存储成本膨胀。

下图展示了 2022 年 3 月至 2024 年 9 月间，Hub 上模型、数据集和 space 仓库的 LFS 存储增长情况：

![Parquet Layout](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/from-files-to-chunks/lfs-analysis-min.png)

Hugging Face 的 Xet 团队正采用一种把文件存为数据块（chunk）的不同存储思路。只传输被修改的数据块，我们就能大幅提升存储效率和迭代速度，同时确保对不断演进的数据集和模型的可靠访问。其工作原理如下。

## 内容定义分块（CDC）基础

我们用来分块的方法叫内容定义分块（content-defined chunking，CDC）。CDC 不把文件看作不可分割的整体，而是用数据本身定义边界，把文件拆解成可变大小的数据块。为了计算数据块，我们应用一个[滚动哈希算法](https://en.wikipedia.org/wiki/Rolling_hash)扫描文件的字节序列。

考虑一个内容如下的文件：

```
transformerstransformerstransformers
```

这里用文本便于说明，实际上可以是任意字节序列。

滚动哈希算法会在数据的滑动窗口上计算哈希。以本例，窗口长度为 4 时，先对 `tran` 计算哈希，再是 `rans`、`ansf`……直到文件末尾。

当哈希满足某个预定义条件（例如）时，就确定一个数据块边界：

```
hash(data) % 2^12 == 0
```

如果序列 `mers` 产生的哈希恰好满足这个条件，文件就会被拆成三个数据块：

```
transformers | transformers | transformers
```

这些数据块的内容会被哈希，建立 chunk hash 到字节的映射，最终存入内容寻址存储（CAS）。由于三个数据块完全相同，CAS 中只需存一份，实现内建去重。🪄

## 插入与删除

当文件内容发生变化时，CDC 允许细粒度更新，对插入和删除非常稳健。我们在文件中插入 `super`，新文件内容变为：

```
transformerstransformerssupertransformers
```

用同样的边界条件重新应用滚动哈希后，新的数据块变成：

```
 transformers | transformers | supertransformers
```

我们已经见过的数据块无需再存——它们已经在那里了。而 `supertransformers` 是新数据块。因此，保存这个文件的更新版本的唯一成本，就是上传和存储这一个新数据块。

为了在真实世界验证这一优化，我们对比基准测试了 XetHub 此前基于 CDC 的存储实现与 Git LFS，在三个迭代开发用例中，存储和传输性能一致提升约 50%。其中一个例子是 [CORD-19 数据集](https://ai2-semanticscholar-cord-19.s3-us-west-2.amazonaws.com/historical_releases.html)——2020 至 2022 年间整理的 COVID-19 研究论文集，包含 50 次增量更新。Xet 后端与 Git LFS 后端仓库的对比汇总如下：

| Metric | Git LFS-backed Repository | Xet-backed Repository |
| --- | --- | --- |
| Average Download Time | 51 minutes | 19 minutes |
| Average Upload Time | 47 minutes | 24 minutes |
| Storage Used | 8.9 GB | 3.52 GB |

通过只传输和保存被修改的数据块，使用 CDC（配合多种提升压缩率和精简网络请求的技术）的 Xet 后端仓库，上传/下载显著更快，保存数据集全部版本所需的存储也大幅削减。想深入了解？阅读[完整基准测试报告](https://xethub.com/blog/benchmarking-the-modern-development-experience)。

## CDC 对 Hub 意味着什么

CDC 在 Hugging Face Hub 存储的文件类型上会如何工作？我们随手做了一个简单的[去重估算器](https://github.com/huggingface/dedupe_estimator)，可视化对一组文件应用 CDC 后的潜在存储节省。在 [openai-community/gpt2](https://huggingface.co/openai-community/gpt2) 仓库提交历史中上传的两个版本的 `model.safetensors` 文件上运行该工具，得到如下结果：

![Parquet Layout](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/from-files-to-chunks/safetensors_dedupe_image.png)

图中的绿色表示两个版本之间有大量重叠，因此无论在单个文件内部还是跨版本都存在去重机会。

|  | Git LFS Storage Required | Xet-backed Storage Required |
| --- | --- | --- |
| Version 1 | 664 MB | 509 MB |
| Version 2 | 548 MB | 136 MB |
| Total | 1.2 GB | 645 MB |

在这个例子中，使用我们的 Xet 存储后端不仅能节省第二个版本相当可观的上传/下载时间，还能把总存储占用减少 53%。算上压缩，我们估计还能再多省约 10%。

我们对 Hub 上仓库的初步研究显示：部分微调模型和许多模型 checkpoint 效果可观。微调模型只修改一部分参数，大部分模型内容跨版本不变，非常适合去重。模型 checkpoint 记录的是增量训练状态，checkpoint 之间的改动通常很小，同样是理想目标。二者的去重比例在 30%—85% 区间。PyTorch 模型 checkpoint 约占 Hub 总存储的 200 TB，按 50% 去重计算，可立省多达 100 TB 存储，未来每月还能再省约 7—8 TB。

除降低存储成本外，数据块级去重也提升了上传/下载速度，因为只有被修改的数据块需要传输。这对使用模型或数据集多个版本的团队是巨大利好，最大限度减少了人和机器的等待时间。
