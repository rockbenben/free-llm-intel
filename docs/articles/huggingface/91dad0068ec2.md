# 推出 @huggingface/kernels：200+ 个面向本地 AI 的 WebGPU 内核

Nico Martin（nico-martin）

Joshua（Xenova）

在 Hugging Face 的 WebAI 团队，我们最大的目标之一是把浏览器推理做得尽可能快、尽可能好用。这件事要分好几层发力：模型需要浏览器友好的表示格式，运行时要有高效的执行计划，而整个技术栈最底层的各个 GPU 操作则要在五花八门的设备和浏览器实现上把性能榨干。

今天，我们发布这项工作的第一层：[`@huggingface/kernels`](https://www.npmjs.com/package/@huggingface/kernels)——一个极简的库，用于从 Hugging Face Hub 加载并运行优化过的 WebGPU 内核；同时发布首批 **207 个内核**集合，位于 [huggingface.co/webgpu-kernels](https://huggingface.co/webgpu-kernels)。

这套集合覆盖了各种机器学习架构和工作负载中常用的操作。更重要的是，每个内核都作为一个完整的、带版本号的包发布：接口、着色器模板、正确性用例、基准用例、使用说明，全部放在一起托管在 Hub 上。

我们同时上线了 [Fleet](https://webgpu-kernels-fleet.hf.space/)——一个浏览器内的 GPU 基准测试套件，在你自己的硬件上运行并给内核打分。除了自己机器的结果，Fleet 还让社区能为我们贡献性能与正确性证据——那些传统测试实验室永远覆盖不到的设备。在你同意的前提下，每次运行都会私下贡献一份证据，帮我们发现问题（结果不正确、病态慢的用例等）、改进内核变体，并在真实硬件上做出更好的优化决策。

## TL;DR

- **207 个 WebGPU 内核**，以独立仓库发布在 [`webgpu-kernels`](https://huggingface.co/webgpu-kernels) 组织下，Apache-2.0 协议。
- **一个 JavaScript 加载器** `@huggingface/kernels`，直接从 Hub 下载、准备并运行内核。
- 每个内核都有**显式契约与可复现证据**，包括清单（manifests）、正确性测试、基准用例和 WGSL 着色器模板。
- **Fleet**：基于浏览器的基准工具，跨真实 GPU 众包正确性与性能证据，帮我们改进内核及其变体。

## 为什么从内核起步？

模型在浏览器里跑，最终都会变成一串 GPU 操作：矩阵乘、归一化、卷积、注意力原语、量化操作、数据布局变换等等。WebGPU 通过一个可移植 API 让现代浏览器都能用上这些操作，WGSL 则为执行它们的着色器提供了通用语言。

但可移植并不自动等于高性能。两个着色器可以实现同一个操作、产出同样的输出，却在不同加速器上表现天差地别。workgroup 大小、内存访问模式、向量化、数据类型、融合策略，全都影响性能。最优选择还会随输入形状、设备、浏览器和可用的 WebGPU 特性而变化。

这正是内核构成浏览器快速推理底层基础的原因。高层运行时的效率，上限就是它派发的操作的效率。把这些操作做成可独立发现、可测试、可基准、可版本化的对象，我们就能独立改进地基，同时给上层保持稳定的契约。

## 是一个内核仓库，而不只是一段着色器

集合中的每个内核都有自己的仓库和内核卡片。卡片记录了操作的语义、输入、输出、属性、支持的数据类型、源文件，以及一个开箱即用的 `@huggingface/kernels` 示例。

比如 [`ai.onnx.Add`](https://huggingface.co/webgpu-kernels/ai.onnx.Add) 实现带多向广播的逐元素加法。它是神经网络里最简单的操作之一，从残差连接到加 bias 到处都在用。它的卡片记录了两个输入、广播后的输出形状、支持的数据类型，以及针对不同形状和设备可用的变体。

`ai.onnx.Add` 仓库把它的清单、正确性与基准用例、WGSL 着色器模板打包在一起。

卡片背后，仓库里是理解和评估这个实现所需的全部工件：

- **`manifest.json`** 是操作契约的唯一权威来源，定义输入、输出、属性、类型约束和形状推导规则。
- **`metadata.json`** 记录内核标识符、摘要（digests）与来源溯源。
- **`test.json`** 是正确性用例，实现可以对照预期行为做校验。
- **`bench.json`** 是基准与调优用例，代表评估该内核所用的工作负载。
- **`*.wgsl.jinja`** 是参数化的 WGSL 实现，用来为特定请求和设备生成着色器。

这套结构把一段着色器变成了可复用的软件工件：不用读 WGSL 也能检查接口；正确性与性能用例跟着实现一起走；发布的版本可以被显式加载，而不是依赖一个无版本号的 URL。我们的内核还可以作为参考实现，供开发者构建自定义 WebGPU 内核或把这些操作集成进自己的运行时。

## 从 Hub 加载一个内核

从 npm 安装这个包：

```
npm install @huggingface/kernels@preview
```

> 运行这些内核需要支持 WebGPU 的浏览器。WebGPU 是否可用取决于浏览器、操作系统、GPU 和驱动。你可以在 JavaScript 里用 "gpu" in navigator 检查。

`@huggingface/kernels` 是内核仓库与应用之间的桥梁。用 Hub 仓库 ID 和一个契约版本号调用 `getKernel`，然后用带类型的输入数据和张量形状调用返回的函数。一个小的 bias-add 示例：

```
import { getKernel } from "@huggingface/kernels";

const add = await getKernel("webgpu-kernels/ai.onnx.Add", { version: 1 });

const { c } = await add({
  a: {
    data: new Float32Array([1, 2, 3, 4, 5, 6]),
    shape: [2, 3],
  },
  b: {
    data: new Float32Array([10, 20, 30]),
    shape: [3],
  },
});
```

第二个输入会沿第一个维度广播，输出形状为 `[2, 3]`。加载器根据 manifest 契约和输入推导出这个输出形状与逻辑数据类型，然后自动分配 `c`。

故意用 6 个浮点数做加法，是因为这是可能的最小 demo。这个规模下，GPU 往返的开销远超计算本身。重点在调用模式：对那些优化内核真正划算的重型操作（比如矩阵乘 `ai.onnx.MatMul`），这套模式完全不变，变的只有仓库 ID 和输入。

连这么基础的操作都说明了内核为什么需要变体：同形状加法可以走直接的向量化路径，而广播输入需要不同的索引逻辑。发布的 Add 内核就包含同形状、向量化广播、标量处理、通用广播等变体。运行时可以为当前调用和设备挑选合适的实现，而面向应用的 API 保持不变。

`version: 1` 选项选择的是已发布**内核契约**的 1 版。它与 ONNX opset、算子的 `since_version` 或模型 revision 都是两码事。把这些概念区分开，应用就能依赖一个稳定的面向 JavaScript 的契约，内核实现可以在契约背后持续演化。

## 这些内核有多快？

那么优化内核到底能带来多大差别？我们在一块 Apple M4 GPU 上让自己的集合与 ORT WebGPU 正面对决，使用 ONNX Runtime Web `1.30.0-dev.20260826-b1f76d586a`。我们从全部 207 个操作的 1,756 个测试用例开始，保留了双方输出一致、计时可靠的 809 个用例。

在这些对比中，我们的内核**几何平均快 2.57 倍**，**中位数快 1.90 倍**，629 胜、176 负、4 平。下面是四个常见操作的细节：

| 操作 | 对比用例数 | 我们的 WebGPU 内核 | ORT WebGPU | 加速比 |
| --- | --- | --- | --- | --- |
| Add | 5 | 0.064 ms | 0.227 ms | **3.52x** |
| MatMul | 29 | 0.115 ms | 0.131 ms | **1.14x** |
| Softmax | 12 | 0.114 ms | 0.240 ms | **2.11x** |
| LayerNormalization | 6 | 0.061 ms | 0.135 ms | **2.22x** |

有些单项胜利大得多。一个特别棘手的 bilinear Einsum 用例（`i,ij,j`，size 4096）：我们的内核跑 0.136 ms，ORT WebGPU 要 1,396 ms——快了**一万倍以上**。`[256, 4096]` 上的按行 CumSum **快 301 倍**：0.016 ms 对 4.784 ms。这些不是普遍预期，而是特殊用例，但它们说明当通用实现撞上慢路径时，专用内核能帮多大的忙。

我们计时的是 GPU 上本身干的活，不含加载内核、创建 session、上传输入、编译着色器、读回输出等准备开销。极短的工作负载天然更难测准，小用例还可能受益于 GPU 缓存，所以这些数字更适合作为有用的对比来读，而不是对每个应用的性能承诺。

这些也只是单个操作的结果，不是完整模型。确切性能会随 GPU 和浏览器变化——这正是 Fleet 如此重要的原因，它能帮我们拼出更完整的图景。

我们也在与 ONNX Runtime 团队合作，把这些改进贡献回上游，让整个 ONNX Runtime Web 生态都受益。

## 从一台设备到一个机群

WebGPU 性能因 GPU、浏览器、驱动而异，一台机器的结果只说明一部分问题。[Fleet](https://webgpu-kernels-fleet.hf.space/) 让任何人都能在浏览器里运行正确性和性能检查，看看这些内核在自己的硬件上表现如何。

在你同意的前提下，每次运行都会私下贡献证据，帮我们发现设备特有问题、比较变体、改进选择规则。目标很简单：用广泛的真实设备覆盖，让内核对所有人都更快、更可靠。

## 为 WebAI 共建地基

首批 207 个内核只是起点，不是终点。把内核以独立形式发布在 Hub 上，给了我们一个共同的场所：查契约、比实现、复现正确性检查、改进性能，而不必把每个着色器塞进每个运行时。

这个集合也是 Hub 更大内核生态的一部分：在 [Kernels 页面](https://huggingface.co/kernels?platform=webgpu&sort=trending)上，WebGPU 内核与 CUDA、ROCm、Metal 及其他平台的内核并排放置，可以像 Hub 上的任何其他工件一样筛选、排序和探索。

Hub 的 Kernels 页面上全部 207 个 WebGPU 内核，可按平台筛选。

这些组件相互支撑：

- 内核仓库定义透明、带版本的操作契约。
- `@huggingface/kernels` 让这些操作从 JavaScript 加载运行变得简单直接。
- Fleet 众包的证据覆盖远超传统基准实验室的设备范围。
- 每一次贡献的运行都可能揭示故障、指导调优、改进变体选择，并帮助验证未来的内核版本。

这就是我们浏览器推理栈下一步的底层地基。我们很期待把这些内核接入更高层的模型工具、继续扩展操作覆盖、让整个 WebAI 生态里的本地快速推理更易用上。

来探索 [WebGPU 内核集合](https://huggingface.co/webgpu-kernels)，试试 [`@huggingface/kernels`](https://www.npmjs.com/package/@huggingface/kernels)，并[加入 Fleet](https://webgpu-kernels-fleet.hf.space/)——用你的设备贡献证据，帮我们把内核做得更好。
