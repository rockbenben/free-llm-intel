Muse Spark Open 是 Meta 推出的开放权重模型。这个混合专家（mixture of experts）模型把文本、图像、音频和视频汇聚进同一个模型，参数量约 8160 亿，每个 token 激活约 420 亿参数，上下文窗口最高可达 100 万 token。它输出文本，为开发者提供了一个统一的接口，用来针对各种不同类型的输入提问。

在 Muse Glimmer 之后，Muse Spark Open 把混合专家架构带到一个大得多的规模上，是迄今为止能力最强的美国开放权重模型。

Meta 面向智能体编程（agentic coding）训练了 Muse Spark Open：读懂代码库、编写和调试代码、调用工具。它同时接受图像、音频和视频作为输入，因此同一个模型可以在处理你的代码时读懂截图、听一段语音留言、看一段屏幕录制。本文会展示如何运行它、如何微调它，以及我们用它做出了什么。所有模型可在[这里](https://huggingface.co/collections/meta-models/muse-spark-open)找到。

## 整体能力与架构

Meta 把 Muse Spark Open 描述为一个针对编程优化的模型，它在真实开发者工作流上训练过，例如多文件重构和长时间的调试会话。Muse Spark Open 是一个以智能体为重心的模型，会在长任务中规划、行动、观察并自我纠错，其中包括带着图像浏览网页。

| 功能 | Muse Spark Open |
| --- | --- |
| 模型规模 | 总参数约 816B；每 token 激活约 42B |
| 专家路由 | 每个 MoE 层 256 个专家；每 token 选出 8 个 |
| 输入 | 文本、图像、音频和视频 |
| 输出 | 文本 |
| 上下文窗口 | 最高 1M token |
| checkpoint 格式 | BF16 和 NVFP4 |

checkpoint 仓库是 Muse-Spark-Open-816B-A42B 和 Muse-Spark-Open-816B-A42B-NVFP4。

[![模型示意图](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/model.png)](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/model.png)

Muse Spark Open 是 Muse 系列模型中的完整尺寸模型。Meta 在 8 月发布的 Muse Glimmer 是同系列里的小型稠密模型，适合在本地运行。两个模型使用同一个 tokenizer 和同一份词表。chat template 沿用 Muse Glimmer 模板，并为新增的模态做了扩展。在 Muse Spark Open 中，输入嵌入和输出层是两个彼此独立的矩阵，各自约 1.66B 参数。

### 混合专家（Mixture of Experts）

语言模型有 62 层，隐藏维度为 8192。每一层有 128 个 query head 和 16 个 key-value head（分组查询注意力，grouped-query attention）。每个 head 的维度是 64。注意力块带有一个输出门（output gate）和一个输出归一化层。模型还对 query 和 key 施加归一化（QK-norm）。每个块通过一个学习到的残差门来组合它的输入与输出，而不是简单地相加。

Muse Glimmer 在每一层使用一个稠密前馈网络。Muse Spark Open 把这个稠密网络替换成 Mixture-of-Experts（MoE，混合专家）块。每个 MoE 块有 256 个专家，路由器为每个 token 选出 8 个专家。每个专家都是一个前馈网络，把维度从 8192 投影到 4096 再投影回 8192，然后对自己的输出施加独立的归一化。这些专家承载了模型总参数的约 97%。

每个 token 只运行 8 个专家，所以模型是以约 42B 参数量来完成每个 token 的计算。但全部 256 个专家都常驻内存，因此部署时需要相当于一个 816B 参数模型的内存，跑起来却是 42B 模型那快得多的速度。BF16 checkpoint 采用 safetensors 格式，约 1.5 TB。NVFP4 checkpoint 以 4-bit 精度存储参数，精度损失可以忽略，专门为 NVIDIA Blackwell GPU 准备。在 transformers 里，BF16 checkpoint 可以用张量并行（TP=32）跑在 4 个节点、每节点 8 张 H200 GPU 上，而 NVFP4 可以跑在单个 B200 节点上。如果你想部署 Muse Spark Open，请看看下面的 `llama.cpp`、vLLM 和 SGLang 方案。

### Perception Encoder

感知编码器（perception encoder）把图像和视频帧转换成语言模型使用的 token，这一点与 Muse Glimmer 相同。该编码器有 1.8B 参数、50 层、隐藏维度 1536、16 个注意力头。它把每张图像切成 14×14 的 patch，产出 4096 维特征。位置信息来自学习到的绝对嵌入（absolute embeddings）和 2D RoPE。每层的前馈网络使用 LayerNorm 和 GELU。每隔四层的那一层以及最后一层使用全注意力，其余层使用稀疏注意力。

[![图像流水线示意图](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/image_pipeline.png)](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/image_pipeline.png)

Muse Glimmer 30B 使用架构相同的编码器。其设计沿用 Meta 的 [Perception Encoder](https://huggingface.co/papers/2504.13181) 工作。视频输入和图像走同一个编码器。

### 音频编码器

[![音频示意图](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/audio_encoder.png)](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/audio_encoder.png)

Muse Spark Open 通过它的音频编码器接受音频作为输入。音频 tokenizer 把音频转换成 token，chat template 则用 `<|audio|>` token 标记音频所在的位置。编码器每 80 毫秒输出一个音频 token，也就是每秒 12.5 个 token。举例来说，如果你有一段 10 秒的音频，输入音频 token 的数量就是 125 个。编码器本身是一个卷积金字塔，每个 stage 由一个采用不同 patch 尺寸的 patch embedder 和 2 个卷积块组成，卷积核是尺寸 7、步长为 1 的一维核。这些 stage 针对 patch 尺寸 [16, 6, 5, 4] 依次重复。在最后一个 stage 末尾，时间帧被送入由 RMSNorm → 线性投影 → RMSNorm 组成的收尾模块。

### 长上下文

推理时上下文窗口为 1M token。配置里把 `max_position_embeddings` 设为 1,048,576。图像、视频和音频 token 与文本共享同一个窗口，都算在这 1M 里。

分组查询注意力（grouped-query attention）让这一规模的模型能把 KV cache 保持得很小。每个 token 向缓存新增 2 × 16 heads × 64 dimensions × 62 layers = 126,976 个数值。以 BF16 计算，大约是每 token 250 KB，撑满 1M token 的上下文则约为 266 GB。

## 推理支持

### Transformers

Muse Spark Open 的实现提供了 `MuseSparkForConditionalGeneration`，用于从多模态输入生成文本；以及 `MuseSparkProcessor`，用于准备对话。该 processor 把 tokenizer、图像与视频处理器、音频特征提取器和 chat template 组合在一起。

使用 `DistributedConfig` 来配置并行设置。`tp_size` 是稠密层被切分到的设备数量，`ep_size` 是专家被分发到的设备数量。

你可以按下面这样初始化模型和 processor。

```
import os

from transformers import AutoModelForMultimodalLM, AutoTokenizer, DistributedConfig

distributed_config = DistributedConfig(
    tp_size=int(os.environ["WORLD_SIZE"]),
    ep_size=int(os.environ["WORLD_SIZE"]),
)

tokenizer = AutoTokenizer.from_pretrained("meta-models/Muse-Spark-Open-816B-A42B
")
model = AutoModelForMultimodalLM.from_pretrained(
    "meta-models/Muse-Spark-Open-816B-A42B",
    distributed_config=distributed_config,
)

messages = [
    {"role": "user", "content": "Explain in one sentence why the sky is usually blue."},
]
inputs = tokenizer.apply_chat_template(
    messages,
    reasoning_effort="medium",  # default: xhigh, options: low/medium/high/xhigh
    add_generation_prompt=True,
    tokenize=True,
    return_dict=True,
    return_tensors="pt",
).to(model.device).to(model.dtype)

input_len = inputs["input_ids"].shape[-1]

outputs = model.generate(**inputs, max_new_tokens=2000)
```

#### 纯文本推理

先准备好对话，然后把 messages 传给 `processor.apply_chat_template`，并启用 `add_generation_prompt=True`、`tokenize=True`、`return_dict=True` 和 `return_tensors="pt"`。再把 processor 的输出传给 `model.generate`，只对新生成的 token 解码，排除输入前缀。processor 上有一个调节推理强度的档位，它把符号化档位（low/medium/high/xhigh）映射到模型本身接受的整数（16、64、256、512）。注意 Muse Spark Open 无法关闭推理，所以如果你想在更简单的任务上少消耗一些 token，就把模型推理保持在 “low”。你也可以在 system prompt 里加上一行 `Reasoning strength: 1` 这样的文字来设定数值化的强度。

```
messages = [
    {"role": "system", "content": "You should only answer with a number."},
    {"role": "user", "content": "What is 17 * 23?"},
]

inputs = processor.apply_chat_template(
    messages,
    add_generation_prompt=True,
    tokenize=True,
    return_dict=True,
    return_tensors="pt",
    reasoning_effort="high", # options:low/medium/high/xhigh
).to(model.device).to(model.dtype)

output = model.generate(**inputs, max_new_tokens=2000)
generated_tokens = output[0][inputs["input_ids"].shape[1] :]
print(processor.decode(generated_tokens, skip_special_tokens=False))
```

#### 图像与文本

Muse Spark Open 的 processor 会把每个图像标记展开成处理后图像所需的 patch token 数量，并在两侧加上图像边界 token。这样的展开能让文本位置与传给模型的视觉特征保持对齐。processor 还支持在单个 prompt 中处理多张图像。

```
image_url = (
    "https://huggingface.co/datasets/merve/vl-test-suite/"
    "resolve/main/pills.jpg"
)
messages = [
    {
        "role": "user",
        "content": [
            {
                "type": "image",
                "image": image_url,
            },
            {
                "type": "text",
                "text": "Do any of the components in this supplement interact?",
            },
        ],
    },
]

inputs = processor.apply_chat_template(
    messages,
    tokenize=True,
    add_generation_prompt=True,
    reasoning_effort="medium",
    return_dict=True,
    return_tensors="pt",
).to(model.device).to(model.dtype)
input_len = inputs["input_ids"].shape[-1]

outputs = model.generate(**inputs, max_new_tokens=2000)
response = processor.decode(outputs[0][input_len:], skip_special_tokens=False)

processor.parse_response(response)
```

#### 视频推理

视频 prompt 既包含视觉内容，也包含帧的时间信息。processor 能够处理自带音频的视频（多亏了音频编码器，这是相对 Muse Glimmer 的一项升级）。processor 会对视频帧和音频做降采样，把帧对齐到一起。默认情况下视频按 2 FPS 采样，上限 96 帧。你可以通过设置 video processor 的 fps 来修改这一点：

```
processor.video_processor.fps = 4.0
```

一般经验是，视频就是按时间顺序排列的帧，降采样越厉害，特定事件之间丢掉的帧就越多，所以想要更准确的生成结果就得保持较高的 fps。但这里有取舍：你会需要更多内存，prefill 的延迟也会上升。帧会与标注时间戳的文本输入交错排列（例如 “Time: 3.5s”）。要启用带音频的视频输入，请给 `apply_chat_template` 传入 `load_audio_from_video=True`。

用 `return_metadata=True` 准备输入时请保留视频的元数据，这样 processor 才能指定正确的帧率。

```
import torch

messages = [
    {
        "role": "user",
        "content": [
            {
                "type": "text",
                "text": (
                    "Describe what happens in this video. "
                    "Use timestamps and include relevant speech or sounds."
                ),
            },
            {
                "type": "video",
                "url": "https://huggingface.co/datasets/merve/vlm_test_images/resolve/main/ramen.mp4"
            },
        ],
    }
]

inputs = processor.apply_chat_template(
    messages,
    add_generation_prompt=True,
    tokenize=True,
    return_dict=True,
    return_tensors="pt",
    load_audio_from_video=True,
    return_metadata=True,
).to(model.device).to(model.dtype)

with torch.inference_mode():
    output_ids = model.generate(
        **inputs,
        max_new_tokens=256,
        do_sample=False,
    )

generated_ids = output_ids[:, inputs["input_ids"].shape[1] :]
response = processor.batch_decode(
    generated_ids,
    skip_special_tokens=True,
)[0]

print(response)
```

### 音频推理

Muse Spark Open 的 audio tower 接收原始波形。processor 期望 24 kHz 的单声道音频，并把波形补齐到 1,920 个采样点的整数倍，对应每 80 毫秒一个音频 embedding。如果你以其他采样率把音频直接提供给 processor，必须先做重采样。可以用 transformers 的 `load_audio` 工具来完成这件事。`load_audio` 使用 torchcodec、librosa 或 torchaudio 后端，所以在运行推理之前请确保本地已安装其中之一。

不过，如果你只是想用 `apply_chat_template` 搭配 messages，这些细节都已在底层替你处理好了：

```
import torch
from transformers import AutoProcessor, AutoModelForMultimodalLM

model_id = "meta-models/Muse-Spark-Open-816B-A42B"
processor = AutoProcessor.from_pretrained(model_id)

model = AutoModelForMultimodalLM.from_pretrained(model_id).eval()

messages = [
    {
        "role": "user",
        "content": [
            {
                "type": "audio",
                "url": "https://huggingface.co/buckets/huggingface/audio-samples/resolve/bbaudio_question_39.mp3",
            },
            {
                "type": "text",
                "text": "Answer the question.",
            },
        ],
    }
]

# Downloads the audio, decodes it as mono, resamples it to 24 kHz, pads it, creates input_values_mask, and expands the audio placeholders.
inputs = processor.apply_chat_template(
    messages,
    add_generation_prompt=True,
    tokenize=True,
    return_dict=True,
    return_tensors="pt",
    load_audio_backend="auto",
).to(model.device).to(model.dtype)

with torch.inference_mode():
    output_ids = model.generate(
        **inputs,
        max_new_tokens=128,
        do_sample=False,
    )

# Decode only newly generated tokens
prompt_length = inputs["input_ids"].shape[1]
generated_text = processor.batch_decode(
    output_ids[:, prompt_length:],
    skip_special_tokens=True,
)

print(generated_text[0])
```

processor 会在音频边界标记之间插入数量相匹配的音频 token。它同时返回一个标识真实采样点的掩码，使模型能够排除用于补齐的音频 embedding。

#### 工具调用

Muse Spark Open 支持纯文本和多模态的工具调用。你可以按下面这样让模型调用工具。

```
from transformers import AutoProcessor, AutoModelForMultimodalLM

MODEL_ID = "meta-models/Muse-Spark-Open-816B-A42B"

# Load model
processor = AutoProcessor.from_pretrained(MODEL_ID)
model = AutoModelForMultimodalLM.from_pretrained(
    MODEL_ID,
    dtype="auto",
    device_map="auto"
)

tools = [
    {
        "type": "function",
        "function": {
            "name": "weather.get",
            "description": "Get the current weather for a city.",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string"},
                },
                "required": ["city"],
            },
        },
    }
]


messages = [
    {
        "role": "user",
        "content": [
            {"type": "image", "image": "https://huggingface.co/datasets/merve/vl-test-suite/resolve/main/SF.png"},
            {"type": "text", "text": "I'm going to the city in this picture. What clothes should I wear?"},
        ],
    },
]

inputs = processor.apply_chat_template(
    messages,
    tools=tools,
    tokenize=True,
    return_dict=True,
    return_tensors="pt",
    add_generation_prompt=True,
    reasoning_strength="high"
).to(model.device).to(model.dtype)

input_len = inputs["input_ids"].shape[-1]
outputs = model.generate(**inputs)
response = processor.parse_response(
      completion,
      prefix=inputs["input_ids"][0],
      tools=tools,
  )
print(response)
```

Muse Spark Open 使用基于通道（channel）的 chat template（Harmony，最早由 gpt-oss 引入）。注意你不必了解它的内部实现，但如果输出质量不高，检查模型把内容路由到了哪些通道会很有用。在下面的输入消息中：

```
<|begin_of_text|>
  <|start|>system<|message|>
  You are a helpful AI assistant.
  Knowledge cutoff: 2026-01-04.
  Current date: ...
  ...
  <|eot|>
  <|start|>user<|message|>...
  <|eot|>
  <|start|>assistant
```

`<|start|>assistant` 是故意留空的，由模型自己用 `to=` 来选择接收方。模型有不同的接收方，例如 `self` 是让模型进行推理，

```
to=self<|message|>the model reasons here<|eom|> # reasoning
<|start|>assistant to=user<|message|>final answer<|eot|> # final answer
```

`self` 用于推理，`commentary` 是工具调用之前与之间、对最终用户可见的说明文字，`user` 是最终回复。
工具调用的路由按下面这样解析（前提是你已把 `tools` 传给 `apply_chat_template`：

```
<|start|>assistant to=weather.get<|message|>
  <atem:function_calls>
  <atem:invoke name="weather.get">
  <atem:parameter name="city">San Francisco</atem:parameter>
  </atem:invoke>
  </atem:function_calls>
  <|eot|>
```

### Llama.cpp

在 Llama Server 上运行的 Muse Spark 2-bit

Muse Spark Open 已集成进 llama.cpp，并包含在预编译二进制里。你可以用下面的命令安装：

```
curl -LsSf https://llama.app/install.sh | sh
```

你可以按下面这样启动服务器，在模型 ID 后面附上量化后缀：

```
llama serve -hf ggml-org/Muse-Spark-Open-816B-A42B-GGUF:Q2_K
```

包含量化版本的仓库在[这里](https://huggingface.co/ggml-orgf/Muse-Spark-Open-816B-A42B-GGUF)。服务器启动后，你可以前往 localhost:9931，用内置的 WebUI 与它对话。在这个 web UI 里你可以添加音频和图像来做推理，也可以调节推理档位。
注意 Muse Spark Open 无法关闭推理，所以如果你想在更简单的任务上少消耗一些 token，就把模型推理保持在 “low”。
我们在 Mac M3 Ultra（512GB）上测试了各档量化。经过 imatrix 校准的 2-bit 量化能以 18 tokens/s 运行，同时给 KV cache 留出充裕的空间（模型本身占用 304 GB）。

你也可以按下面这样查询服务器。关于多模态、工具调用等更多内容，欢迎查阅 [API 参考文档](https://llama.app/docs/serve)。

```
## Text-only inference
curl http://localhost:8080/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d '{
        "messages": [
            {"role": "system", "content": "You are a helpful assistant."},
            {"role": "user", "content": "Write a limerick about python exceptions"}
        ]
    }'

## Image-text inference
curl -s http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" -H "Authorization: Bearer <your-key>" \
  -d '{"model":"muse-spark-open","messages":[{"role":"user","content":[
        {"type":"text","text":"What is in this image?"},
        {"type":"image_url","image_url":{"url":"data:image/png;base64,..."}}
      ]}],"temperature":0}'

## Audio-text inference
curl -s http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" -H "Authorization: Bearer <your-key>" \
  -d '{"model":"muse-spark-open","messages":[{"role":"user","content":[
        {"type":"text","text":"Transcribe this audio."},
        {"type":"input_audio","input_audio":{"data":"data:audio/wav;base64,..."}}
      ]}],"temperature":0}'
```

llama.cpp 团队提供了不同的量化版本。我们在 Apple Silicon 芯片上测试过 Q2_K、Q4_K_S 和 Q_8。把量化标识作为后缀加上去就能运行对应的量化版本，`llama serve -hf ggml-org/Muse-Spark-Open-816B-A42B:Q2_K`。

### SGLang

SGLang 的 Muse Spark Open 集成支持文本、图像、音频和视频输入。NVFP4 参考配置在四张 GB300 GPU 上运行。

在 SGLang 集成环境里，从 Hugging Face Hub 下载 checkpoint 并启动服务器：

```
export MODEL_ID=meta-models/Muse-Spark-Open-816B-A42B-NVFP4
export CKPT="$(hf download "$MODEL_ID")"

SGLANG_FLASHINFER_NVFP4_PER_TOKEN_ACTIVATION=1 \
uv run sglang_meta serve \
  --model-path "$CKPT" \
  --served-model-name "$MODEL_ID" \
  --quantization modelopt_fp4 \
  --moe-runner-backend flashinfer_trtllm \
  --tp-size 4 \
  --ep-size 4 \
  --port 30000
```

checkpoint 里包含 chat template，我们把它显式传入。启动器会配置好 Muse 的推理解析器和工具调用解析器。

通过 OpenAI 兼容 API 发送一个请求：

```
curl http://localhost:30000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "meta-models/Muse-Spark-Open-816B-A42B-NVFP4",
    "messages": [{
      "role": "user",
      "content": "Explain how a mixture-of-experts model works."
    }],
    "max_tokens": 2048
  }'
```

响应会把 `reasoning_content` 里的推理轨迹与 `content` 里的最终答案分开。

### vLLM

vLLM 的 Muse Spark Open 参考集成支持文本和图像输入，使用 NVFP4 checkpoint，需要 Blackwell 系列 GPU。

安装好参考插件及其依赖后，从 Hugging Face Hub 下载 checkpoint 并启动服务器：

export MODEL_ID=meta-models/Muse-Spark-Open-816B-A42B-NVFP4

## MLX

Muse Spark Open 如今已可在 [oMLX](https://github.com/jundot/omlx) 和 [mlx-lm](https://github.com/ml-explore/mlx-lm) 中使用。为 oMLX 优化的 oQ 量化已提供 [3-bit](https://huggingface.co/mlx-community/Muse-Spark-Open-816B-A42B-oQ3e) 和 [4-bit](https://huggingface.co/mlx-community/Muse-Spark-Open-816B-A42B-oQ4e) 版本，开箱即用。

我们在 M3 Ultra（512 GB）上测试了 oQ3e 量化。模型占用约 344 GB，给 KV cache 留出了空间；在 1024 token 的 prompt、生成 128 个 token 的设置下，prefill 约 225 tok/s，生成约 21 tok/s。

通过 oMLX 界面下载模型后，你就能在内置的聊天 UI 里与它对话。在这个聊天 UI 中你可以添加图像，并随时调节推理强度，从 low 到 xhigh。模型的推理以一个可折叠的思考区块呈现，与最终答案分开。

注意推理是无法关闭的，而默认值（Auto）用的是 xhigh。如果你想在更简单的任务上少用一些 token，请把它设为 “low”。[![omlx](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/omlx_muse_spark_open_reasoning_screenshot.png)](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/omlx_muse_spark_open_reasoning_screenshot.png)

语言模型同样已经出现在官方 mlx-lm 仓库的[这个 PR](https://github.com/ml-explore/mlx-lm/pull/1975) 中。你可以按下面这样在同样高质量的 oQ3e 量化上运行它：

```
mlx_lm.generate --model mlx-community/Muse-Spark-Open-816B-A42B-oQ3e \
  --prompt "Explain convolutional networks like I am 5" \
  --max-tokens 5000
```

这是一个很大的模型，正如上面所说，即使 3-bit 量化也需要 256 GB 以上的内存。你也可以跨多台计算机运行分布式推理，具体细节请参考文档。

## 用 Inference Endpoints 部署 Muse Spark Open

你可以在 Inference Endpoints 上部署 Muse Spark Open，使用针对 NVFP4 变体预先验证过的 SGLang 方案：它既可以在 8 × NVIDIA RTX Pro 6000 98 GB 上运行、上下文长度 131072，如果你想要 1048576 的上下文长度，也可以在 8 x NVIDIA H200 141GB 上运行。

## 用 TRL 微调

你可以用 TRL 的 `SFTTrainer` 微调 816B checkpoint。本节展示我们如何在 8 个节点、每节点 8 张 H100 GPU 上用 TRL 完成微调。该方案在注意力层上训练 LoRA adapter，专家保持冻结。完整脚本在 [TRL examples](https://github.com/huggingface/trl/tree/main/examples/sft_muse_spark_open) 中。

首先，我们需要把模型切分到 64 个 GPU 设备上。鉴于模型体量巨大，必须在多个维度上并行。我们用 FSDP 对模型分片，并把专家分散到各 GPU 上，靠的是 `DistributedConfig`，它告诉 `transformers` 在加载模型时如何切分：

```
from transformers.distributed import DistributedConfig

distributed_config = DistributedConfig(fsdp_size=64, ep_size=8)
```

上面的片段中，`fsdp_size=64` 用 FSDP2 把模型分片到全部 64 张 GPU 上，`ep_size=8` 把每一层的 256 个专家分成 8 组。Transformers 会把每个 token 发送到持有其专家的 GPU 上，因此每张 GPU 都在自己那一份 batch 切片上训练。

接下来为这次训练配置 `SFTConfig`。这里我们只做了一个简单任务，在一个开源数据集上适配模型的 chat template，但你可以把它套用到自己的场景。

```
import torch
from datasets import load_dataset
from peft import LoraConfig
from transformers.distributed import DistributedConfig
from trl import SFTConfig, SFTTrainer

train_dataset = load_dataset("allenai/tulu-3-sft-mixture", split="train[:500000]")

training_args = SFTConfig(
    output_dir="muse-spark-lora-sft",
    model_init_kwargs={"dtype": torch.bfloat16, "distributed_config": DistributedConfig(fsdp_size=64, ep_size=8)},
    per_device_train_batch_size=1,
    max_steps=500,
    max_length=2048,
    packing=True,
    save_only_model=True,
    logging_steps=1,
    report_to="trackio",
)

trainer = SFTTrainer(
    model="meta-models/Muse-Spark-Open-816B-A42B",
    args=training_args,
    train_dataset=train_dataset,
    peft_config=LoraConfig(r=16, lora_alpha=32, target_modules=["q_proj", "k_proj", "v_proj", "o_proj"]),
)
trainer.train()
```

这里的核心是 `packing=True`，它把样本拼接成 2048 token 的序列而不做补齐，并用块对角掩码让各样本彼此隔离。`save_only_model=True` 只保存 adapter、不保存优化器状态，因为 trainer 无法恢复一个在加载时被分片的模型。`LoraConfig` 指向四个注意力投影矩阵，每一层的 256 个专家保持冻结。

然后我们可以在每个节点上运行这条命令：

```
torchrun --nnodes 8 --nproc_per_node 8 --rdzv_backend c10d --rdzv_endpoint "$MASTER_IP:29700" sft_muse_spark_open.py
```

我们训练了 500 步，在 64 张 H100 上耗时约 2 小时，速度约为每秒 8,000 token。平均 token 准确率从 72% 升到 84%，loss 从 1.26 降到 0.57，说明这是一次不错的微调。

[![Loss](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/training_loss.png)](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/training_loss.png)

[![Acc](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/token_acc.png)](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/token_acc.png)

## 演示

Muse Spark Open 是一个编程与智能体模型。我们想亲自验证这一点，于是尝试了一系列多模态与智能体任务，都用到了模型的图像和音频输入。下面每一项你都可以直接运行或 fork。

### 3D 资产生成器

我们把 2-bit 量化的 Muse Spark Open（由 llama.cpp 提供服务）与 Pi 编程 agent 结合起来，用来在 [Three.js](http://Three.js) 中生成 3D 资产并迭代改进。prompt 可以在[这里](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/pi-3d-prompt.txt)找到；由于模型经过了量化，它需要稍多一些的引导。在 Mac Ultra 上用 llama.cpp 我们能得到 18 TPS。

[![Pi demo](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/pi-demo.png)](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/pi-demo.png)

我们先描述想要的资产，Pi 用模型生成该资产的 Three.js 代码，在浏览器里渲染出结果，并从多个角度截图。随后它把这些图像送回 llama server 上的同一个模型获取视觉反馈。Pi 依据那份反馈修改代码，然后重复整个过程。

### 用 OpenEnv 与 Hugging Face Sandbox 进行浏览器交互

我们在 computer use 任务上测试了 Spark，被它的表现惊艳到了，因此做了一个精简的 demo，它同时也能教你理解 computer use agent 是如何工作的。你还可以按自己的需求进一步定制它。它既是一个教学示例，也是几行代码就能跑起来的东西。可以[在这里](https://huggingface.co/docs/openenv/main/en/environments/helium_browser)找到它。

配合 OpenEnv 与 HF Sandboxes 的 Muse Spark NVFP4 浏览器 Agent

[Hugging Face Sandboxes](https://huggingface.co/docs/huggingface_hub/en/guides/sandbox) 是构建在 Hugging Face Jobs 之上、用于便捷执行代码的沙箱。这个 demo 由三个组件构成：

- 通过 Inference Endpoints 提供服务的 Muse Spark Open，
- 用 helium 和 selenium 包装 web driver 动作（点击、输入、滚动等）、定义浏览器环境的 reset、step、observation、termination 接口的 OpenEnv，
- Chromium 网页浏览器

其中远程沙箱包含环境与浏览器，如下图所示。

[![Diagram](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/browser_server.png)](https://huggingface.co/datasets/merve/meta-muse-spark-open-assets/resolve/main/browser_server.png)

照着示例里的说明，几个步骤就能轻松试用：用 Muse Spark Open 启动 Inference Endpoint（NVFP4 也很好用！），把你的 endpoint URL 加为环境变量，在 Spaces 里发布你的 OpenEnv server 并把它也提供进去，然后你就能运行 agent 循环。Muse Spark Open 看到的是此前的动作、system prompt、url 和浏览器截图，据此采取行动，仅此而已（没有 DOM，没有 HTML 代码，什么都没有），所以这是一个真正意义上的多模态浏览器 demo。

### 调用你的浏览器

最后，我们想把 Spark 的智能体多模态能力推到极限，于是搭了[这个 space](https://huggingface.co/spaces/burtenshaw/muse-spark-call-your-browser)，把模型的音频、图像与智能体特性组合成一个浏览器 agent。我们给模型一段关于所需之物的笼统描述，它就与内置的浏览器交互，在 Amazon 上找出候选选项。

Muse Spark Open 接收语音输入，推理出符合描述的商品类型，在 Amazon 上搜索它，并依据条件挑出最合适的那个。

## 小结

Muse Spark Open 是 Muse 系列中的完整尺寸开放权重模型。可以从 [BF16](https://huggingface.co/meta-models/Muse-Spark-Open-816B-A42B) 或 [NVFP4](https://huggingface.co/meta-models/Muse-Spark-Open-816B-A42B-NVFP4) checkpoint 开始，或者试试出色的 `llama.cpp quants` 之一。如果你用 Muse Spark Open 做出了什么东西，欢迎分享出来，并在[仓库的 discussions](https://huggingface.co/meta-models/Muse-Spark-Open-816B-A42B/discussions) 里告诉我们。
