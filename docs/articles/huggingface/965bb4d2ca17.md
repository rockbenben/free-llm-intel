**免费是指免酒钱，不含电费，并且假设你已经拥有硬件*

2026 年 6 月将被铭记为人们意识到闭源模型随时可能被收回的时刻。Anthropic 最新旗舰模型 Claude Fable 5 被下架一事记忆犹新，不难理解：拥有自己的 AI 技术栈、能够本地运行模型，如今比以往任何时候都重要——尤其是当你的业务建立在 AI 之上时。

有鉴于此，我们想分享如何在智能体运行框架（agent harness）中使用 Gemma、Qwen 这类本地模型来执行分类任务[[1]](https://huggingface.co/blog/local-models-pr-triage#note-1)。这种做法与用 BERT 这类模型做分类不同。像 Pi 这样的智能体运行框架中的本地模型，可以配合结构化输出来打标签。我们选择这条路线，是因为手边刚好有本地模型和运行框架，并且我们坚信：随着本地模型能力不断提升，类似配置会越来越流行。[[2]](https://huggingface.co/blog/local-models-pr-triage#note-2)

我们的起点是 OpenClaw 仓库里的开源贡献。OpenClaw 每天收到数百个 issue 和 PR，需要分诊、排优先级并转派给维护者。我（Onur）的工作是让本地模型与 OpenClaw 良好协作。作为这个具体方向的维护者，我需要对任何 P0 问题快速响应。

如果用的是 GPT-5、Opus、Sonnet 这类 SOTA 闭源模型，这本来是个相当简单的任务。但我恰好坐拥 128 GB 统一内存，也就是一台 NVIDIA GB10。于是我接下了这个挑战：

> 我能不能用一个本地开源权重模型，搭建一个实时通知系统，只过滤并提醒我负责的那部分 issue？

这台小盒子（ aka DGX Spark）可以高并发地运行 gemma-4-26b-a4b，每秒生成数百个词元。

如果我让跑在 $200/月 ChatGPT Pro 套餐上的 OpenClaw 主智能体在每个新 issue 或 PR 出现时触发一个任务，会把我的配额用光。我也许会改为每 2 小时或 6 小时跑一次。这样会把一段时间内的 issue 攒批处理，等于用延迟处理换取实时通知。

如果我在我已有的、一直开着的硬件上用本地模型跑这套东西，不仅能获得近乎实时的通知，而且几乎免费（准确地说，只花电费）。

## 给 issue 和 PR 分类

我们拟定了一个有限标签集合，代表我们需要分诊的 issue 类别，然后用本地模型把每个 issue 分类到其中一类，比如 `local_models`、`self_hosted_inference`、`acp`、`agent_runtime`、`codex`、`ui_tui` 等等。[[3]](https://huggingface.co/blog/local-models-pr-triage#note-3)

但 PR 怎么分类？向 Chat Completions 端点发一个简单的单次请求、带上把主题作为枚举的 tool JSON schema？

差不多。但现在是 2026 年，不是 2023 年，我们有智能体（AGENTS）。可以做得更好！

本地模型方面，我们测试了 `gemma-4-26b-a4b` 和 `qwen3.6-35b-a3b`。经过性能优化，两者都能在本地每秒生成数百个词元。

我们用智能体运行框架来驱动分类流程。为此我们把 [pi](https://pi.dev) 打包为一个可以调用本地模型端点的框架。

智能体默认在第一个提示词中收到 PR 的标题、正文和 PR diff 的截断摘录。之后，它可以选用 `bash` 工具对 OpenClaw 仓库执行只读操作（当它需要查看代码库时），或者用 `final_json` 工具提交最终分类结果。

你不会想把完整的 bash 权限交给在这种高吞吐环境下运行的本地模型，因为一个被提示词注入的 issue 或 PR 可能把模型带偏，去做与分类无关的事情。

因此我们用 [`reposhell`](https://github.com/osolmaz/localpager/tree/main/reposhell) 代替 `bash`：一个受限的类 `bash` shell，只允许对 OpenClaw 仓库执行只读操作（`ls`、`find`、`cat`、`grep` 等）。模型以为自己用的是 `bash`，但任何不允许的操作都会被拒绝：

```
reposhell bound cwd=/repo/openclaw repos=openclaw
type help for allowed commands; exit or quit to leave

reposhell /repo/openclaw> help
allowed: pwd, ls, find, rg, grep, sed -n, cat, head, tail, wc -l, git status --short, git show --name-only, git grep, git ls-files
search: rg -n -i "lm studio" or grep -R -n -i "lm studio" .
files: rg --files -g "*.ts" or git ls-files src
examples: rg -n reposhell README.md | sed is not allowed; use one simple command at a time

reposhell /repo/openclaw> head README.md
# 🦞 OpenClaw — Personal AI Assistant

<p align="center">
    <picture>
        <source media="(prefers-color-scheme: light)" srcset="https://raw.githubusercontent.com/openclaw/openclaw/main/docs/assets/openclaw-logo-text-dark.svg">
        <img src="https://raw.githubusercontent.com/openclaw/openclaw/main/docs/assets/openclaw-logo-text.svg" alt="OpenClaw" width="500">
    </picture>
</p>

<p align="center">

reposhell /repo/openclaw> curl localhost

exit_code=2

reposhell /repo/openclaw>
```

这里有一个该机制真正发挥作用的实例。在一份[保存的会话示例](https://huggingface.co/datasets/dutifuldev/openclaw-classification-dataset/blob/main/session-examples/README.md)中，`qwen3.6-35b-a3b` 正在分类 [`openclaw/openclaw#84621`](https://github.com/openclaw/openclaw/pull/84621)，标题是 `Fix Kimi tool-call rewriting stop reason handling`。思考区块显示模型最初考虑 `coding_agent_integrations`，因为改动路径 `extensions/kimi-coding` 看起来很符合。模型用 reposhell 通过 `ls extensions`、`ls extensions/kimi-coding`、`cat extensions/kimi-coding/package.json` 等简单只读命令检查了本地仓库。该包的元数据显示这个扩展实际上是 `@openclaw/kimi-provider`，一个 OpenClaw 的 Kimi provider 插件。于是模型把最终标签更正为 `inference_api` 和 `tool_calling`，并明确排除了 `coding_agent_integrations`。

前面提到，我们打包了一个只能执行只读操作并返回分类结果的特定 `pi` 配置。我们叫它 [`localpager-agent`](https://github.com/osolmaz/localpager/tree/main/localpager-agent)，名字来源于本项目的主工程 `localpager`。每个 PR 和 issue 会生成一个提示词，连同其他参数一起按下面的方式传给 CLI：

```
localpager-agent \
  --model "<model-id>" \
  --base-url "<openai-compatible-base-url>" \
  --session-dir "<session-output-dir>" \
  --final-schema "<runtime-schema.json>" \
  --tools bash,final_json \
  --reposhell-socket "<reposhell.sock>" \
  --reposhell-default-repo "<repo-id>" \
  --reposhell-visible-repos "<repo-id>[,<repo-id>...]" \
  -p "$(cat <rendered-prompt.md>)"
```

## 处理进来的 PR 和 issue

那么，在进来的 PR/issue 和 Discord 上的最终通知之间，是谁在编排一切？

这就是最终过滤后的 Discord 通知的样子：一个关于目标方向的 PR 被转派给了我。

围绕这一点的编排非常简单；只有分类步骤涉及 LLM：

- 我们用 [openclaw/gitcrawl](http://github.com/openclaw/gitcrawl) 作为仓库的本地镜像。每当有新的 PR 或 issue，每一条都会被规范化为统一格式并写入 localpager 自己的 SQLite 数据库。如果是新条目，localpager 会为它创建一个分类任务。
- 接着，一个 worker 从队列中领取任务。它构建一个 GitHub 上下文对象，包含 issue 或 PR 的标题、正文、标签、作者、状态，以及可选的评论、改动文件和选定的 diff 摘录。这意味着本地模型大多数时候不需要自己浏览 GitHub 或打开 URL——所有相关上下文都直接递到了它手上。
- 上下文对象被渲染成提示词，按上一节所述传给 `localpager-agent`。智能体可以思考、可以使用 reposhell，但最终必须按定义好的 schema 输出分类结果。
- 输出存回 localpager 的 SQLite 数据库，并根据用户配置的通知策略转发到 Discord（即这些主题提醒我，那些主题不提醒）。

下面是展示 localpager 整体架构的图：

这套架构是半智能体式（semi-agentic）的。打标签以智能体方式完成，而发送通知由确定性规则处理。这样做的目的是让任务中最直白的部分不再需要推理，从而加快通知管线。本地推理是免费的，但每个任务都有资源争用成本：GPU 带宽应当留给绝对需要推理的任务。这同时也降低了通知出错的概率。

## 本地模型能胜任 PR 分诊吗？

坦率地说：这套系统最早的本地版本噪声很大。第一个测试的模型 `gemma-4-e4b-it` 对跑通端到端本地管线很有用，但它倾向于给一个 PR 或 issue 打上太多不相关的标签。假阳性标签会让 Discord 信息流变得嘈杂，无法把我的注意力聚焦在正确的 issue 上。这推动我们去测试更大的本地模型，包括 `gemma-4-26b-a4b` 和 `qwen3.6-35b-a3b`，并在下面这个 330 行的评估集上进行验证。

在早期提示词工作中，我们还通过 antirez 的 DS4 实现[[4]](https://huggingface.co/blog/local-models-pr-triage#note-4)使用 `DeepSeek-V4-Flash` 来制作早期数据集标签。该配置通过 CUDA 使用 DS4 服务器。我们最终放弃了用 DS4 打标签，因为它在不同运行之间的标注不一致。我们也没有考虑把它作为 `localpager-agent` 的主力模型，因为它太大，在我们的硬件上达不到足够的吞吐：DS4 服务器只有大约每秒 14 个词元，且最大并发为 1。

为了测试模型表现，我们挑选并生成了 330 个 GitHub issue 和 PR 的标签。每条数据被标注五次（3 次 GPT-5.5、2 次 Opus 4.8），要求模型意见一致才被接受。这个过程包括人工裁定、改进标签定义，以及向模型说明内部产品设计选择。我们由此得到一组稳定、可复现的标签，用来与小模型对比。

在这个评估集上拿到可用结果之前，我们并不需要为 `gemma-4-26b-a4b` 或 `qwen3.6-35b-a3b` 做提示词优化。使用相同的路由提示词，Gemma 的召回率更高、每行墙钟时间更短，而 Qwen 的精确率更高、精确匹配更高、假阳性更少。我们还在同一数据集上跑了 `DeepSeek-V4-Flash` 作为参照。它的假阳性最少，但模型尺寸和吞吐量使其无法在 NVIDIA GB10 上实时执行这些任务。由于每行可以有多个标签，假阳性和假阴性是所有行的标签总数。下表中 Qwen 的结果已对结构化输出失败（模型在调用 `final_json` 前耗尽输出词元）进行了重试。Gemma 和 Qwen 的重复运行指标为三次运行的均值 ± 样本标准差。`DeepSeek-V4-Flash` 作为参照只跑了一次。

| 指标 | `gemma-4-26b-a4b` | `qwen3.6-35b-a3b` | `DeepSeek-V4-Flash` |
| --- | --- | --- | --- |
| 精确率 | 0.716 ± 0.010 | 0.831 ± 0.007 | 0.938 |
| 召回率 | 0.905 ± 0.004 | 0.818 ± 0.006 | 0.714 |
| F1 | 0.800 ± 0.008 | 0.824 ± 0.002 | 0.811 |
| 精确匹配 | 0.410 ± 0.014 | 0.540 ± 0.014 | 0.509 |
| 假阳性 | 227.0 ± 10.5 | 105.7 ± 6.4 | 30 |
| 假阴性 | 60.0 ± 2.6 | 115.3 ± 4.0 | 181 |
| 每行墙钟秒数 | 1.41 ± 0.04 | 13.51 ± 0.79 | 144.14 |
| 每 worker 输出词元/秒 | 25 | 50 | 13 |
| 聚合输出词元/秒 | 402.6 | 145.3 | 13 |
| 并发数 | 16 | 4 | 1 |
| 总参数量 | 26B | 35B | 284B |
| 激活参数量 | 4B | 3B | 13B |

这里的吞吐和墙钟数字不是这些模型在该硬件上的极限性能，只是我们当时可用的优化配置下的设置。例如在另一次探测中，`gemma-4-26b-a4b` 还支持并发 32，聚合输出速度超过了每秒 700 个词元。

在 330 行标签集上的基准对比。每个子图使用各自的纵轴刻度；蓝色标出该指标下的最优值。精确率和召回率上的误差线显示 Gemma 与 Qwen 三次运行的样本标准差。

Gemma 的基准测试中，我们用 vLLM 服务 `gemma-4-26b-a4b`，并启用了为该配置找到的各项优化。其中很大一块是 NVFP4 量化：在 GB10 级别的 Blackwell 硬件上，它不只是一个更小的模型文件，而是一种硬件友好的格式，比 Q4_K_M 这类可移植的 GGUF 量化更能直接利用 NVIDIA/vLLM 的执行路径。实际上这意味着更少的内存流量和更大的批处理空间。我们还启用了前缀缓存、FP8 KV cache、CUTLASS MoE 后端和仅语言模型模式。完整的 330 行运行在并发 16 下约 7.5 分钟完成。

## 用 OpenClaw 跟踪并验证实时表现

前面提过，除了每个新 issue 或 PR 都触发一个本地模型任务外，我们还可以每 n 小时（例如每 2 小时）用一个 SOTA 云端模型（比如在 OpenClaw 中运行的 GPT-5.5）跑一个批处理任务来达到同样目的。[[5]](https://huggingface.co/blog/local-models-pr-triage#note-5)

那样的话需要一个 ChatGPT Pro 套餐。由于模型是 SOTA，即便把 2 小时的 issue/PR 攒成一批，仍然可以期待它有不错的表现。

因为我们想看本地分类器对比 GPT-5.5 的表现如何，我们同时运行两者，每 2 小时让 GPT-5.5 来裁定假阳性和假阴性。

为稳妥起见，OpenClaw 任务运行在沙箱中，只能访问我们汇报结果用的[公开仓库](https://github.com/osolmaz/onurclaw)。在我们的场景里，我们让 OpenClaw 任务更新一个机器可读文件，然后由一个简单的脚本读取 Codex 分配的标签并计算假阳/假阴性状态。输出示例：

> 假阴性
> 
> Issue #88499 openai-responses provider: 404 on previous_response_id when store=false (default)
> inventory area: OpenAI-compatible/proxy; notifier topics: agent_runtime, api_surface, sessions; notification: none
> 
> 
> 
> 假阳性
> 
> PR #88275 fix(models-config): allow self-hosted providers without apiKey in models.json (#88267)
> notifier interest: i0; topics: self_hosted_inference, local_model_providers, config; notification: sent
> 
> 
> PR #88266 refactor: extract model catalog core package
> notifier interest: i1; topics: config, api_surface, local_model_providers; notification: sent
> 
> 
> PR #88247 feat: add hosted model providers
> notifier interest: i0; topics: local_model_providers, model_serving, docs, api_surface; notification: sent

如何分类、如何编辑机器可读文件、如何用脚本获取假阳性和假阴性的说明，都写在一个[智能体技能](https://github.com/osolmaz/onurclaw/blob/main/.agents/skills/openclaw-onur-inventory/SKILL.md)中，该技能被一个每 2 小时运行一次的 [OpenClaw cron 任务](https://docs.openclaw.ai/automation/cron-jobs)引用。OpenClaw 智能体会摄取所有新的 issue 或 PR，用合适的标签把它们加入 JSON 文件，运行脚本，并在同一个 Discord 频道里汇报。这样，我们每几小时就能观察到本地模型的表现，并收到漏报提醒。

## 结论

我们认为 issue/PR 分诊是一大类更宽泛任务的特例，我们把这类任务称为"高吞吐分诊"。本文只在开源贡献这一个领域探索了用本地模型实时过滤信息的想法。像 `gemma-4-26b-a4b` 和 `qwen3.6-35b-a3b` 这样的中型本地模型，无需任何微调就能以良好准确率完成零样本分类，使它们成为快速原型阶段的优先选择，之后你再逐步转向更节省成本的传统分类模型。

不过，同样的方法也可以应用到其他领域：

- 新闻业中的资讯分类
- 在 X 或 Reddit 等社交媒体和论坛中筛选感兴趣的内容
- 客户支持工单分诊
- 内容审核申诉分诊
- 销售过程中筛选潜在的外联对象
- 研究中筛选 arXiv 上的特定主题

这份清单还可以继续扩展，但我想思路已经清楚了。

除了分诊，我们还探索了如何让运行高速本地模型的智能体框架以安全的方式完成分类。这种方法有个贴切的叫法——*智能体式分类*（agentic classification）：模型不是一开始就收到全部信息，而是可以先搜索更多上下文，再返回结构化数据。虽然不能完全称之为新方法，但我们希望这篇博客能作为 [Pi](https://pi.dev)+受限 shell+`final_json` 这一具体配方的良好参考。
