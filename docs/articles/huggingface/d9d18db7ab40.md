# 连续批处理

作者：Rémi Ouazan Reboul（ror）、Arthur Zucker（ArthurZ）、Luc Georges（mcpotato）

[![Title card](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/banner.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/banner.png)

*TL;DR：本博客从注意力机制和 KV 缓存出发，以吞吐为目标，推导出连续批处理（continuous batching）。*

如果你用过 Qwen、Claude 或任何 AI 聊天机器人，大概注意到过这个现象：回答的第一个词要等一会儿才出现，然后词就一个接一个地蹦上屏幕（希望如此）节奏稳定且轻快。这是因为本质上所有 LLM 都只是高级的下一 token 预测器。LLM 先处理你的整个提示词，产出一个新 token；然后每次读完此前的一切，再逐字追加 token，直到它判断生成结束。

这个生成过程计算代价很高：每生成一个 token，都要把输入过一遍数十亿参数。为了让这些模型在现实应用（尤其是同时服务大量用户）中变得可行，研究者和工程师发展了一系列高效推理技术。其中影响最大的优化之一就是**连续批处理**：尽可能同时处理多个会话，并在会话结束时把它们换出，以此榨取性能。

要理解连续批处理如何工作、为什么它在高负载服务场景如此高效，我们从 LLM 处理 token 的基本原理开始搭建。

## 注意力

注意力机制是 LLM 工作方式的核心。语言模型把文本拆成称为 token 的片段来处理。概念上我们可以把 "token" 当作"词"，但有时一个词会由多个 token 组成。对每个 token 序列，网络都预测下一个 token 应该是什么。

网络中的许多操作是 **token 级（token-wise）**的：每个 token 独立处理，某个 token 的输出只取决于该 token 自身的内容，与序列里的其他 token 无关。这类操作包括层归一化或矩阵乘法。但要让句子中的词建立关联，我们就需要 token 之间能互相影响的操作。

这就是注意力登场的地方。**注意力层是唯一不同 token 相互交互的地方**。理解网络如何把 token 关联起来，就是理解注意力。

我们来看它实际如何运作——先只考虑一个输入提示的情形。

设初始提示为 `I am sure this project`，被切分为 7 个 token：`[<bos>, I, am, sure, this, pro, ject]`。`<bos>`（Beginning of Sequence，序列开始）是我们加在提示开头的特殊 token，告诉语言模型新会话从这里开始。

每个 token 在网络内用一个长度为 `d` 的向量表示（*隐藏维度*）。于是这七个输入 token 组成张量 xxx，形状 [1,7,d]\left[1, 7, d \right][1,7,d]。`1` 是序列数，即批大小——我们的场景就是 1。`7` 是序列长度，`d` 是隐藏维度，即每个 token 表示的大小。往后我们用 nnn 而不是 `7` 来表示序列长度。

输入张量 x x x 随后被三个矩阵投影：query 投影 Wq W_q Wq​、key 投影 Wk W_k Wk​ 和 value 投影 Wv W_v Wv​。得到三个张量 Q Q Q、K K K、V V V，形状都是 [1,n,A] \left[1, n , A \right] [1,n,A]，其中 A A A 是注意力头的维度。它们分别被称为 **query、key 和 value states（查询、键、值状态）**。下图左侧展示了这一过程。

[![proj_and_mul.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/proj_and_mul.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/proj_and_mul.png)

接下来，张量 Q Q Q 和 K K K 相乘，衡量 token 之间的相似度，得到形状 [1,n,n] \left[ 1, n , n \right] [1,n,n] 的张量。这就是为什么说注意力对序列长度是二次复杂度。计算 QKT QK^T QKT 需要 O(n2d) \mathcal{O} \left( n^2 d \right) O(n2d) 次运算，成本是序列长度 n n n 的平方。上图右侧即为此。

然后我们把一个布尔 **注意力掩码（attention mask）**应用到 QKT QK^T QKT 上，控制哪些 token 可以交互，如下图。图中这个掩码是**因果掩码（causal mask）**：每个 token 只与它之前的 token 交互。直觉上，因必须在前、果才能在後，所以叫因果掩码。注意力掩码至关重要，因为它规定了整个网络中的所有 token 交互。**把注意力掩码全部置 False，整个网络里就没有任何两个 token 会交互。**几段之后我们再细看注意力掩码。

[![masking_and_softmax.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/masking_and_softmax.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/masking_and_softmax.png)

最后，应用掩码后做 token 级 softmax（也就是按行 softmax），再乘以 value 投影 V V V，得到一个注意力头的输出，形状 [1,n,A] \left[ 1, n , A \right] [1,n,A]。下图是整个过程的视觉总结。

[![attention.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/attention.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/attention.png)

本文会大量使用注意力可视化，为简化起见，我们把上图稍微压缩一下。

**为什么这很重要：** 在连续批处理中，Q Q Q、K K K、V V V 的 token 数可能不同——如后文所见，我们会同时处理不同阶段（prefill 和 decode）。更一般地，设 Q Q Q 形状为 [1,nQ,A] \left[1, n_Q , A \right] [1,nQ​,A]，K K K 为 [1,nK,A] \left[ 1, n_K , A \right] [1,nK​,A]，V V V 为 [1,nV,A] \left[ 1, n_V , A \right] [1,nV​,A]。

注意力分数 QKT QK^T QKT 的形状于是是 [1,nQ,nK] \left[ 1, n_Q , n_K \right] [1,nQ​,nK​]；掩码逐点作用于分数，形状相同。

应用掩码并按行 softmax 后，我们乘以 V V V。用 [1,nQ,nK] \left[ 1, n_Q , n_K \right] [1,nQ​,nK​] 的矩阵乘 [1,nV,A] \left[ 1, n_V , A \right] [1,nV​,A] 的矩阵，内维必须一致：nK=nV n_K = n_V nK​=nV​。也就是说 V V V 和 K K K 永远等长，可视化时可以只画 K K K。如果这看起来很抽象别担心：图会让它具体起来。

此外，既然知道注意力掩码作用于 QKT QK^T QKT，我们就知道两者同形。与其画注意力分数，不如在原位画注意力掩码。最后，Q Q Q、K K K、V V V 都是 x x x 的直接投影，没必要再画 x x x。于是得到只画 Q Q Q、K K K 和注意力掩码的简化图：

[![simple_attention.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/simple_attention.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/simple_attention.png)

这个表示也点明了我们如何**读一个注意力掩码**。

掩码按行读，等同于按 token 读：每一行对应一个 token 的注意力计算。位置（第 i 行，第 j 列）的**绿色方块**表示 `True`：token j 可以影响 token i。**白色方块**表示 `False`：不允许交互。

例如，看第三个 token "*am*" 的那一行："*I*" 列是绿的，所以 "*I*" 影响 "*am*" 的计算；"*pro*" 列是白的，所以 "*pro*" 不影响 "*am*"。这就是因果掩码在起作用：未来的 token 无法影响过去的。

模型的最后一层为每个输入 token 输出一个 token 预测。在我们的场景——为单个提示生成续写——我们只关心最后一个 token 的下一 token 预测。上图中最后一个 token 是 "*ject*"，对应的预测是 "*will*"。

刚才描述的过程——拿整个输入序列，过多个注意力层，算出下一个 token 的分数——叫 **prefill（预填充）**。因为如后文所见，我们做的大量计算可以被缓存复用——所以我们是在*预先填充*缓存。得益于这个缓存，序列生成可以在一个叫 **decoding（解码）**的阶段用少得多的计算继续。解码阶段生成一个新 token，比最初的整序列计算快得多。我们来看为什么。

要继续生成，我们开始一次新的前向传播，天真的做法看起来是这样：

[![naive_generate.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/naive_generate.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/naive_generate.png)

要计算新 token 的注意力分数，我们仍然需要之前所有 token 的 key 和 value 投影。于是不得不把旧 token（上图中灰色部分）与 Wk W_k Wk​、Wv W_v Wv​ 的矩阵乘法再做一遍，去拿一个以前已经算过的结果。换句话说，我们在浪费算力。看看如何避免。

## KV 缓存

一眼就能注意到：最后一个 token 不影响其他 token 的注意力计算：

[![cant_see_me.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/cant_see_me.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/cant_see_me.png)

这符合因果掩码的思想："*will*" 排在所有先前 token 之后，不会改变它们的注意力计算。文本生成中，因果注意力是最常见的，接下来我们聚焦这种情况。请记住也还存在非因果注意力方案，尤其处理图像时。既然我们只需要 "*will*" 这个 token 的下一 token 预测，注意力机制可以简化为只计算这个 token 的输出。

此外，我们上一次前向传播已经算过 "*<bos>*"、……、"*ject*" 这些 token 的 K K K 和 V V V 状态：只要存下来，就不必重算。这就是 **KV 缓存**：生成过程中创建的 key 和 value 状态的清单。它把生成第 n+1 n+1 n+1 个 token 的计算成本从 O(n2) \mathcal{O} \left( n^2 \right) O(n2) 降到 O(n) \mathcal{O} \left( n \right) O(n)——代价是避免重算 key/value 投影，付出 O(n) \mathcal{O} \left( n \right) O(n) 的内存成本。

[![kv_cache.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/kv_cache.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/kv_cache.png)

上图中只有白色的 token 是（新）计算的：与其为 8 个 token 算 key 和 value，我们只为 1 个算。可以看到 KV 缓存省下了大量计算。想看更多 KV 缓存可视化，读[这篇文章](https://huggingface.co/blog/not-lain/kv-caching)；想看实践实现示例，读[这篇](https://huggingface.co/blog/kv-cache)。

再具体说说缓存大小，这正好是审视模型中各种形状的机会。对于有 L \mathcal L L 个注意力层、H H H 个注意力头、头维度 A A A 的模型，存储一个 token 所需缓存总量为 2∗L∗AH 2 *\mathcal L * AH 2∗L∗AH，因子 2 2 2 对应 K K K 和 V V V 两者。例如 Llama-2-7B，L=32 \mathcal{L}=32 L=32 层、H=32 H=32 H=32 头、A=128 A=128 A=128，每 token 每层需要 2×32×128=8,192 2 \times 32 \times 128 = 8,192 2×32×128=8,192 个值。用 `float16` 精度，这占 2AH×2 2AH \times 2 2AH×2 字节 =16 = 16 =16 KB 内存。

KV 缓存在我们想生成下一个 token——即**解码**阶段——时很有用。但它在 **prefill** 阶段同样有用：处理初始提示、输入 token 很多的时候，尤其是无法一次性放进 GPU 显存的大提示。

## 分块 Prefill

到目前为止，我们的 prefill 例子只有 n=7 n=7 n=7 个 token，而实际中初始提示可能长得多。比如使用 Cursor 时可以把整个代码仓库加入提示充当上下文，这会显著加大提示规模。这种情况下，n n n 个 token 的激活存储可能超过 GPU 可用显存。于是 prefill 无法在单次前向传播里完成：必须把 prefill 拆成分块。这就是 **chunked prefill（分块预填充）**，它是实现高效推理的组件之一。

假设可用显存非常紧张，每次前向传播只能过 m=4 m=4 m=4 个 token。若初始提示有 n=7 n = 7 n=7 个 token，就需要拆成 ⌈n/m⌉=2 \lceil n /m \rceil = 2 ⌈n/m⌉=2 块（7/4 = 1.75 向上取整为 2）。下面用同样的 n n n、m m m 记号示意：

[![chunked prefill.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/chunked_prefill.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/chunked_prefill.png)

能这么做靠的是 KV 缓存：第一块 prefill 时把 KV 状态存下来，第二块时把已存的 KV 状态接在新的 KV 状态前面。注意力掩码也相应调整。视觉上，就好像把不分块的 prefill 从中间切开了。

关键洞见：缓存的 KV 状态让我们能增量处理提示而不丢失信息。

虽然这里展示的是拆成 2 块的例子，chunked prefill 可以按任意方式拆分，灵活适配显存约束。

现在，理解连续批处理所需的全部工具终于集齐了。

## 连续批处理

前面的例子只考虑了批大小为 1 的情形——一次只为一个提示生成 token。在评估或模型服务场景中，我们要为大量提示生成 token。要提升**吞吐（throughput）**——每秒生成的 token 数——最佳做法就是为一个批次的多个提示并行生成 token。

把提示凑成一个批，天真的做法是给输入张量（token 序列和注意力掩码）各加一个轴。但这对输入形状有个约束：所有提示必须等长，因为张量必须是矩形的。为此我们通常在左侧加 padding，使新的 token 预测永远来自最右侧 token。每个提示的注意力掩码也相应修改，如下所示：

[![padding.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/padding.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/padding.png)

其中 padding token `<pad>` 用橙色标出。然后可以像以前一样做前向传播，只是多了批大小这一维。这叫**批量生成（batched generation）**：对等长提示很高效，长度不一时则浪费。下图用 4 个生成步骤演示：一步 prefill（顶部），其后 3 步解码（各条 "Forward pass" 线下方）。

[![batched_generation.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/batched_generation.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/batched_generation.png)

其中 `<eos>` 指 "End Of Sequence"（序列结束），是表示模型对相应序列已完成生成的特殊 token。

批量生成的缺点是：如果一个提示先生成出 `<eos>` token 结束，之后所有生成的 token 都是废的——一直 waste 到批中最长的请求也结束为止。当然，可以把已到 `<eos>` 的提示移出批次，省一些算力和内存，但这里节省资源不是目标：吞吐才是。

与其把完成的提示直接移出批次，不如用排队等待生成的提示顶上。我们称之为**动态调度（dynamic scheduling）**，也就是动态批处理。动态调度能维持吞吐、保证前向传播生成的每个 token 都有意义。但由于我们凑批的方式，它有个大缺点：交换提示时需要大量 padding。因为新插入的提示要走 prefill，而其他提示都在一次一个 token 地解码——新提示里几乎每个 token 都要配一份 padding。

[![dynamic_batching.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/dynamic_batching.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/dynamic_batching.png)

批大小更大、初始提示更长时，问题更糟。padding 成本随批大小和提示长度呈平方增长。若批中有 B B B 个处于解码阶段的提示，其中一个完成，动态插入一个 n n n 个初始 token 的提示需要 (n−1)(B−1) (n-1)(B-1) (n−1)(B−1) 个 padding token。比如 B=8 B=8 B=8、n=100 n=100 n=100 时，就需要 99×7=693 99 \times 7 = 693 99×7=693 个 padding token！

此外，像 CUDA graphs 或 `torch.compile` 这样的实际优化要求张量形状固定。这迫使我们把所有提示 pad 到统一的最大长度，padding 浪费急剧上升。

此时我们的主要矛盾是 padding，而它是为凑批加的那个轴带来的后果。理想的办法是彻底去掉这个轴——对批处理的彻底重构。这样做之后，把提示凑在一起的唯一方式就是拼接：

[![concatenate.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/concatenate.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/concatenate.png)

但我们不希望提示 0 的 token 与提示 1 的 token 交互！幸运的是，我们有控制 token 互相影响的手段：注意力掩码。做法如下图：

[![ragged_batching.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/ragged_batching.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/ragged_batching.png)

虽然图中用不同深浅的绿色示意掩码的不同部分，它仍然是布尔掩码：绿色即 `True`，白色即 `False`。这种凑批方式叫 **ragged batching（参差批处理）**——因为序列长度是"参差不齐"的——它能在不引入 padding token 的情况下提升吞吐。

上图中我们用 ragged batching 把两个完整提示合在一起，但我们可以凑到显存允许为止。唯一的限制是 m m m——一个批次能装下的 token 数——取决于 GPU 可用显存。

Ragged batching 是连续批处理的关键组件之一。为最大化吞吐，我们可以按如下算法把 prefill 和解码序列混合：

- 每个批次尽量打满 m m m 个 token 的显存预算
- 先把所有处于解码阶段的提示放进批次，每个占 1 个 token
- 剩余空间用 prefill 阶段的提示填充，借 chunked prefill 的灵活性按需拆分输入

动态调度是构成*连续批处理*技术的最后一块拼图：提示一完成就立刻移出批次，用对应新请求的分块提示顶上。

Ragged batching 与动态调度的这个组合就叫**连续批处理**，它是现代 LLM 服务系统背后的技术。

[![continuous_batching.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/continuous_batching.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_batching/continuous_batching.png)

## 结论

连续批处理组合了三项关键技术来最大化 LLM 服务吞吐：

- **KV 缓存**：避免重算历史 token 表示
- **分块 Prefill**：在显存约束内处理变长提示
- **Ragged batching + 动态调度**：消除 padding 浪费，让 GPU 始终满载

通过去掉批维度、用注意力掩码控制 token 交互，连续批处理让 prefill 与解码阶段混在同一批次里，多请求服务的效率大幅提升。这就是 ChatGPT 之类的服务能高效支撑数千并发用户的原因。
