## Huggy Lingo：用机器学习改进 Hugging Face Hub 上的语言元数据

**tl;dr**：我们用机器学习检测 Hub 上没有语言元数据的数据集的语言，并用 [librarian-bots](https://huggingface.co/librarian-bots) 发起 pull request 补上这些元数据。

Hugging Face Hub 已成为社区分享机器学习模型、数据集与应用的地方。随着数据集数量增长，元数据作为「为你的用例找到合适资源」的工具愈发重要。

在这篇博文中，我很高兴分享一些早期实验——它们试图用机器学习改进 Hugging Face Hub 上数据集的元数据。

### Hub 数据集的语言元数据

目前 Hugging Face Hub 上约有 5 万个公开数据集。数据集所用语言的元数据，可以在[数据集卡片](https://huggingface.co/docs/datasets/upload_dataset#create-a-dataset-card)顶部的 [YAML](https://en.wikipedia.org/wiki/YAML) 字段中指定。

所有公开数据集通过元数据中的语言标签共指定了 1,716 种不同语言。注意，其中一些其实是同一语言的不同写法造成的，比如 `en`、`eng`、`english`、`English`。

例如，[IMDB 数据集](https://huggingface.co/datasets/imdb)在 YAML 元数据中指定 `en`（表示英语）：

![Screenshot of YAML metadata](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/huggy_lingo/lang_metadata.png)
 *IMDB 数据集 YAML 元数据的片段*

英语是 Hub 上数据集最常见的语言——这可能毫不意外：约 19% 的 Hub 数据集把语言标为 `en`（这还不包括 `en` 的各种变体，所以实际比例可能更高）。

![Distribution of language tags](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/huggy_lingo/lang_freq.png)
 *Hugging Face Hub 数据集语言标签的频率与占比*

如果剔除英语，语言分布是什么样？可以看到有几个主导语言聚成一小组，其后语言出现频率呈相当平滑的下降。

![Distribution of language tags](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/huggy_lingo/lang_freq_distribution.png)
 *剔除英语后 Hub 数据集语言标签的分布*

不过，这里有一个大问题：绝大多数数据集（约 87%）没有指定所用语言；只有约 13% 的数据集在元数据中包含语言信息。

![Barchart](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/huggy_lingo/has_lang_info_bar.png)

#### 语言元数据为何重要？

语言元数据是寻找相关数据集的重要工具。Hugging Face Hub 支持按语言筛选数据集。例如，想找荷兰语数据集，我们可以在 Hub 上使用一个[筛选器](https://huggingface.co/datasets?language=language:nl&sort=trending)，只包含含荷兰语数据的数据集。

目前这个筛选返回 184 个数据集。然而，Hub 上还有一些包含荷兰语却没在元数据中说明的数据集。随着 Hub 数据集数量增长，这类数据集越来越难找。

许多人希望能按特定语言找到数据集。为某种语言训练优秀开源 LLM 的主要障碍之一，就是高质量训练数据的匮乏。

如果切换到寻找相关机器学习模型的任务：知道模型的训练数据包含哪些语言，能帮我们找到面向我们感兴趣语言的模型——而这依赖数据集把信息写明。

最后，了解 Hub 上（以及缺失）了哪些语言，有助于我们理解 Hub 的语言偏差，并为社区填补特定语言空白的努力提供方向。

### 用机器学习预测数据集的语言

我们已经看到，Hub 上许多数据集没有包含语言元数据。但既然这些数据集已经公开共享，我们也许可以直接查看数据集本身，用机器学习识别其语言。

#### 获取数据

访问数据集中部分样本的一种方式，是用 datasets 库下载数据集，例如：

```
from datasets import load_dataset

dataset = load_dataset("biglam/on_the_books")
```

但对 Hub 上的某些数据集，我们未必想把整个数据集下载下来。我们可以改为加载数据集的抽样，但取决于数据集的创建方式，这可能仍会把比需求更多的数据拉到我们的工作机器上。

幸好，Hub 上许多数据集可通过[数据集查看器 API（dataset viewer API）](https://huggingface.co/docs/datasets-server/index)访问，让我们无需本地下载即可使用 Hub 上的数据集。该 API 正是你在 Hub 上看到的数据集查看器背后的支撑。

在这个「为数据集预测语言」的首个实验中，我们定义了一份可能与文本内容相关的列名与数据类型清单——例如 `text` 或 `prompt` 这类列名、`string` 特征很可能是相关的，而 `image` 则不是。这样我们可以对语言信息不太相关的数据集（例如图像分类数据集）跳过语言预测。我们用数据集查看器 API 取 20 行文本数据喂给机器学习模型（这个数字可以调整，多取或少取）。

这一做法意味着，对 Hub 上的大多数数据集，我们都能快速请求其前 20 行中可能是文本列的内容。

#### 预测数据集的语言

拿到一些文本样本后，我们需要预测语言。做法有多种，这里我们用了 [facebook/fasttext-language-identification](https://huggingface.co/facebook/fasttext-language-identification) fastText 模型——由 [Meta](https://huggingface.co/facebook) 在 [No Language Left Behind](https://ai.facebook.com/research/no-language-left-behind/) 工作中创建。该模型能检测 217 种语言，应该已能覆盖 Hub 上数据集的绝大多数语言。

我们把数据集 20 行样本表示的 20 个示例传给模型，每个数据集因此得到 20 个独立的语言预测（每行一个）。

得到预测后，我们再做一层过滤，决定这些预测能否被接受为元数据建议。过滤规则大致是：

- 按语言对每个数据集的预测分组：有些数据集会返回多种语言的预测。我们把同一语言的预测归为一组——例如某数据集同时返回英语和荷兰语预测，我们就把英语与荷兰语的预测分别归拢。
- 对预测出多种语言的数据集，统计每种语言有多少个预测。若某语言的预测占比低于 20%，我们丢弃该预测。例如 18 个预测是英语、只有 2 个是荷兰语，就丢弃荷兰语预测。
- 计算某语言全部预测的平均分数。若该语言预测的均分低于 80%，我们丢弃该预测。

![Prediction workflow](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/huggy_lingo/prediction-flow.png)
 *展示预测如何被处理的示意图。*

完成过滤后，还要决定如何使用这些预测。fastText 语言预测模型以 [ISO 639-3](https://en.wikipedia.org/wiki/ISO_639-3) 代码（语言代码国际标准）加书写体系返回预测。例如 `kor_Hang` 是朝鲜语（kor）的 ISO 639-3 语言代码 + 谚文（Hangul）书写体系，其中书写体系用 [ISO 15924](https://en.wikipedia.org/wiki/ISO_15924) 代码表示。

我们丢弃书写体系信息，因为 Hub 上目前并未一致地采集它；并在可行时把模型返回的语言预测从 [ISO 639-3](https://en.wikipedia.org/wiki/ISO_639-3) 转换为 [ISO 639-1](https://en.wikipedia.org/wiki/ISO_639-1) 语言代码。这主要是因为 Hub 界面用这些代码浏览数据集的支持更好。

有些 ISO 639-3 代码没有对应的 ISO 639-1 代码。对这类情况，若我们认为映射合理就手动指定，例如把标准阿拉伯语（`arb`）映射到阿拉伯语（`ar`）。在无法给出明显映射时，我们暂不为该数据集建议元数据。未来的迭代可能采用不同做法。要认识到这一方案确有代价：它减少了可能被建议的语言多样性，也依赖「哪些语言可以映射到哪些语言」的主观判断。

但流程到此还没有结束。毕竟，预测出数据集的语言如果不与社区分享，又有什么用处？

### 用 Librarian-Bot 更新元数据

为确保这些宝贵的语言元数据回流到 Hub，我们请出 Librarian-Bot！Librarian-Bot 接收 Meta 的 [facebook/fasttext-language-identification](https://huggingface.co/facebook/fasttext-language-identification) fastText 模型产出的语言预测，并为每个相应数据集开 pull request，把信息加入其元数据。

这套系统不仅快速、高效地用语言信息更新数据集、无需人工干预，而且一旦仓库负责人批准并合并该 pull request，语言元数据即可供所有用户使用，显著提升 Hugging Face Hub 的可用性。你可以[在这里](https://huggingface.co/librarian-bot/activity/community)追踪 librarian-bot 的动态！

#### 下一步

随着 Hub 上数据集数量增长，元数据愈发重要。语言元数据尤其宝贵——它是为你的用例找到正确数据集的关键。

借助数据集查看器 API 与 [Librarian-Bots](https://huggingface.co/librarian-bots)，我们能够以人工无法企及的规模更新数据集元数据。由此，我们在丰富 Hub 的内容，让它成为全球数据科学家、语言学家与 AI 爱好者更强大的工具。

作为 Hugging Face 的机器学习馆员（ML librarian），我会继续探索为 Hub 上的机器学习工件做自动元数据富化的机会。如果你有想法或想参与这项努力，欢迎联系我（daniel at thiswebsite dot co）！
