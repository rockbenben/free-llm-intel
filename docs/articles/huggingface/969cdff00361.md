# 模型路由很简单——直到它不那么简单

给 agent 加一个路由器听起来像是唾手可得的胜利：把简单请求发给更便宜的模型，把昂贵模型留给更难的任务；或者按专长路由——代码用 Claude，多模态用 Gemini，诸如此类。一个分类器或启发式规则做完选择，成本降下来，性能保持住。完事。

然而并非如此。大多数路由系统把模型选择当作一个分类问题。根据我们在 agentic 系统中构建路由的经验，这个看似「选模型」的问题很快会变成「系统优化」问题。有三个维度让我们深感其难。

## 1. 成本不止是模型定价

我们本以为 GPT-4.1 会比 Claude Sonnet 4.6 便宜。事实并非如此。

在 AppWorld Test Challenge 的 417 个任务上，使用同一个 CodeAct agent，Sonnet 总共花费 79 美元（0.19 美元/任务），而 GPT-4.1 花费 155 美元（0.37 美元/任务）——几乎是两倍。按账面看这说不通：GPT-4.1 的输入和输出 token 单价都更低，而 Sonnet 完成同样任务大约要多花三倍的推理步数。单看标价，GPT-4.1 应该轻松胜出。

解释是什么？缓存——这是大多数路由讨论完全忽略的因素。Agent 工作负载往往在各步骤间复用大段上下文。当缓存命中率高时，有效输入成本会大幅下降。Sonnet 更低的缓存读取定价让它从这种模式中受益远超预期，足以抵消它更高的基础定价和更长的执行轨迹。

结论：实际成本取决于模型、工作负载和服务基础设施三者之间的相互作用。只看价格表的路由器，是在对着错误的数字做优化。

## 2. 复杂度不止是任务难度

一种常见的路由策略是先估计任务有多难，再把更难的任务交给更强的模型。这一直觉在两个方面会失效。

其一，难度在路由时刻往往是不可见的。像「总结这份合同」这样的请求看起来简单，但完成之前可能触发检索、合规检查、工具调用和多轮打磨。与此同时，一个看似高度技术化的 prompt 可能由更小的专门模型高效处理。在任务真正执行起来之前，你往往不知道它到底有多难。

其二，即使你能完美估计难度，那也只是众多信号之一。在生产环境中，路由器需要同时权衡成本、延迟、模型专长和可靠性。企业级部署还叠加更多约束：合规要求、数据驻留规则、隐私限制、经批准的模型清单。一个理想情况下应该交给某个模型的任务，可能因为治理要求必须去别处——路由器必须优雅地处理这一点。

路由器解决的从来不是单个问题，而是在成本、质量、延迟、合规与可靠性之间持续地多线平衡。

## 3. 延迟不止是模型速度

人们容易单纯从模型规模考虑延迟——大模型慢，小模型快。但用户实际体验取决于远不止于此的因素。

路由本身就增加开销。基础设施因素——模型跑在什么硬件上、缓存是否预热、endpoint 有多繁忙——常常主导端到端响应时间。如果服务条件不对，理论上更快的模型仍可能带来更慢的体验。

还有路由粒度问题。每个任务只路由一次的开销很小。但如果每一步都路由——虽然让你在执行中途有更大的适应余地——意味着每个额外的决策点都会引入延迟和运维复杂度。

忽视服务系统的路由器，是在对着错误的现实做优化。

## 那么，我们是怎么处理的？

这些经验塑造了我们路由器的构建方式。关键转变：我们不再把路由当分类问题，而是当作优化问题。我们的算法不再问「哪个模型最适合这个任务？」，而是同时在成本、质量和延迟之间做优化——同时保持足够轻量，避免自己成为瓶颈。

下图展示了 CodeAct agent 在 AppWorld Test Challenge 上的结果。每个蓝色方块是我们路由器的不同配置，勾勒出成本-准确率前沿。重点不在于任何一个点——而在于路由器给了你一系列可选择的运行点，取决于你优先成本、延迟还是准确率。配置 1（延迟优化）在 84% 准确率下花费 93 美元、83 秒——相比单独运行 Opus，成本降低 21%、延迟降低 9%，而准确率只下降 4%。配置 2 把成本压得更低。

[![Routing results on AppWorld Test Challenge with a CodeAct agent](https://raw.githubusercontent.com/AgentToolkit/altk-main/main/assets/routing-results-hf-blog.png)](https://raw.githubusercontent.com/AgentToolkit/altk-main/main/assets/routing-results-hf-blog.png)

注意，标准的基于难度的路由器（青色菱形）落在相近的准确率区间，但成本更高——它无法像基于优化的方法那样遍历完整的权衡空间。而且由于优化本身非常轻量（大约每任务 6 ms、2 kB 内存），路由器没有变成我们之前警告过的那个瓶颈。

## 更大的图景

我们从这项工作中得到的经验是：路由的本质不是选择模型，而是优化系统。模型只是一个变量——很重要，但只是缓存行为、基础设施状态、合规约束和工作负载模式等众多因素之一。

路由做得好时，很少是因为它给某个任务找到了「最好」的模型，而是因为它为整个系统找到了最佳的运行点。这是比分类更难的问题，但也是值得解决的问题。

我们会在后继文章中分享方法论背后更多技术细节。在此期间，如果你正在自己的 agentic 系统中构建路由，我们很乐意听到你遇到了哪些权衡。
