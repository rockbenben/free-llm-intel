# 我们为何转向 Hugging Face Inference Endpoints，也许你也该如此

Hugging Face 最近上线了 [Inference Endpoints](https://huggingface.co/inference-endpoints)；按官方的说法，它"解决了生产环境中的 transformers"。Inference Endpoints 是一个托管服务，让你能够：

- 部署 Hugging Face Hub 上（几乎）任何模型
- 部署到任意云（AWS 和 Azure，GCP 在路上）
- 选用多种实例类型（包括 GPU）
- 我们正把一些在 CPU 上做推理的机器学习（ML）模型迁移到这个新服务。本文讲为什么，以及你为什么也可能需要考虑它。

## 我们之前在做什么？

迁移到 Inference Endpoints 的那些模型，此前由我们内部管理，运行在由 [AWS Fargate](https://aws.amazon.com/fargate/) 支撑的 AWS [Elastic Container Service](https://aws.amazon.com/ecs/)（ECS）上。ECS 给你一个无服务器集群，可以运行基于容器的任务。我们的流程是：

- 在 GPU 实例上训练模型（由 [CML](https://cml.dev/) 开通，用 [transformers](https://huggingface.co/docs/transformers/main/) 训练）
- 上传到 [Hugging Face Hub](https://huggingface.co/models)
- 构建模型服务 API（[FastAPI](https://fastapi.tiangolo.com/)）
- 把 API 包进容器（[Docker](https://www.docker.com/)）
- 把容器上传到 AWS [Elastic Container Repository](https://aws.amazon.com/ecr/)（ECR）
- 把模型部署到 ECS 集群

你完全可以说 ECS 不是服务 ML 模型的最佳方案，但它撑到了现在，而且让 ML 模型能和其他容器服务并肩运行，减少了心智负担。

## 我们现在在做什么？

有了 Inference Endpoints，我们的流程变成：

- 在 GPU 实例上训练模型（由 [CML](https://cml.dev/) 开通，用 [transformers](https://huggingface.co/docs/transformers/main/) 训练）
- 上传到 [Hugging Face Hub](https://huggingface.co/models)
- 用 Hugging Face Inference Endpoints 部署。

这显著更简单了。我们也可以用其他托管服务，比如 [SageMaker](https://aws.amazon.com/es/sagemaker/)、[Seldon](https://www.seldon.io/) 或 [Bento ML](https://www.bentoml.com/) 等，但既然我们本来就把模型上传到 Hugging Face Hub 当模型仓库用，又深度投入了 Hugging Face 的其他工具（transformers、[AutoTrain](https://huggingface.co/autotrain) 等），用 Inference Endpoints 对我们来说非常顺理成章。

## 延迟和稳定性如何？

在切换到 Inference Endpoints 之前，我们用 [ab](https://httpd.apache.org/docs/2.4/programs/ab.html) 测试了不同的 CPU 端点类型。

对 ECS 我们没测那么多，但我们知道一个大容器在同区域实例上的延迟约 200ms。对 Inference Endpoints 的测试基于一个在 [RoBERTa](https://huggingface.co/roberta-base) 上微调的文本分类模型，测试参数如下：

- 请求方区域：eu-east-1
- 请求方实例大小：t3-medium
- Inference Endpoint 区域：eu-east-1
- 端点副本数：1
- 并发连接：1
- 请求数：1000（对这款应用来说，1-2 分钟内 1000 个请求——即便来自单个连接——已经代表非常高的使用强度）

下表给出四种配备 Intel Ice Lake 的 CPU 端点的延迟（ms ± 标准差，以及完成测试的秒数）。

```
size   |  vCPU (cores) |   Memory (GB)  |  ECS (ms) |  🤗 (ms)
----------------------------------------------------------------------
small  |  1            |  2             |   _       | ~ 296   
medium |  2            |  4             |   _       | 156 ± 51 (158s)  
large  |  4            |   8            |   ~200    | 80 ± 30 (80s)   
xlarge |  8            | 16             |  _        | 43 ± 31 (43s)    
```

这些结果相当令人鼓舞。消费这些端点的应用要实时处理请求，所以延迟越低越好。可以看到，原生 Hugging Face 容器比我们跑在 ECS 上的定制容器快了一倍还多——我们从大规格 Inference Endpoint 收到的最慢响应也只有 108ms。

## 成本如何？

这套方案到底花多少钱？下表对比我们之前的做法（ECS + Fargate）与使用 Inference Endpoints 的价格。

```
size   |  vCPU         |   Memory (GB)  |  ECS      |  🤗       |  % diff
----------------------------------------------------------------------
small  |  1            |  2             |  $ 33.18  | $ 43.80   |  0.24
medium |  2            |  4             |  $ 60.38  | $ 87.61   |  0.31 
large  |  4            |  8             |  $ 114.78 | $ 175.22  |  0.34
xlarge |  8            | 16             |  $ 223.59 | $ 350.44  | 0.5 
```

关于这点可以说几句。首先，我们要的是托管式部署方案——我们（还）没有专职 MLOps 团队——所以在寻找一个能帮我们把部署时间降到最低的解决方案，哪怕比自己动手部署贵一点。

Inference Endpoints 比我们之前的做法更贵，成本增加 24% 到 50%。以我们目前的规模，这笔额外开销——一台大 CPU 实例每月约 60 美元的差价——与我们在 API 和容器上省下的时间与心智负担相比不值一提。如果我们要部署上百个 ML 微服务，可能就得重新盘算了，不过这在很多托管方案里都一样。

## 一些说明与注意事项：

- Inference Endpoints 的定价可在[这里](https://huggingface.co/pricing#endpoints)查到，但从 [GUI](https://ui.endpoints.huggingface.co/new) 新部署端点时显示的是另一个数字。我用的是后者，更高。
- 我在表里给的 ECS + Fargate 数值是低估，但相差不远。数字取自 [Fargate 定价页](https://aws.amazon.com/fargate/pricing/)，只含实例托管成本，没算数据流入/流出（大头可能是从 Hugging Face Hub 下载模型），也没算 ECR 相关成本。

## 其他考量

### 部署方式

目前你可以从 [GUI](https://ui.endpoints.huggingface.co/new) 部署 Inference Endpoint，也可以用 [RESTful API](https://huggingface.co/docs/inference-endpoints/api_reference)。你还可以使用我们的命令行工具 [hugie](https://github.com/MantisAI/hfie)（以后会专门写一篇博客），传入一份配置、一行代码就能启动 Inference Endpoint，就是这么简单：

```
hugie endpoint create example/development.json
```

对我个人而言，缺的是一个 [自定义 terraform provider](https://www.hashicorp.com/blog/writing-custom-terraform-providers)。用 hugie 在 [GitHub action](https://github.com/features/actions) 里部署 inference endpoint 已经不错了（我们就这么做），但若能借助 terraform 强大的状态机来跟踪这些端点会更好。我相当确信很快会有人（如果不是 Hugging Face 自己）写一个——如果没有，我们会。

### 单端点托管多个模型

Philipp Schmid 写过一篇很棒的博客，讲如何编写自定义 [Endpoint Handler](https://www.philschmid.de/multi-model-inference-endpoints) 类，在单个端点上托管多个模型，有可能帮你省下一笔钱。他那篇讲的是 GPU 推理，唯一的实际限制是 GPU 内存能装下多少模型。我猜在 CPU 实例上也行，只是还没试过。

## 小结…

我们发现 Hugging Face Inference Endpoints 是一种既简单又方便的部署方式，把 transformer（以及 [sklearn](https://huggingface.co/scikit-learn)）模型变成应用可直接调用的端点。虽然成本比之前用的 ECS 方案略高，但非常值——它省下我们琢磨部署的时间，让我们专心做真正想做的事：为客户构建 NLP 解决方案、帮他们解决问题。
