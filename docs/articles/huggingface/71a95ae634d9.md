# 使用 PyTorch 全分片数据并行（FSDP）加速大型模型训练

Sourab Mangrulkar

smangrul

Sylvain Gugger

sgugger

本文另有简体中文版本 [简体中文](https://huggingface.co/blog/zh/pytorch-fsdp)。

本文中，我们将看看如何利用 **[Accelerate](https://github.com/huggingface/accelerate)** 库训练大模型——它让用户可以用上 **[PyTorch FullyShardedDataParallel (FSDP)](https://pytorch.org/blog/introducing-pytorch-fully-sharded-data-parallel-api/)** 的最新特性。

## 动机 🤗

**机器学习（ML）模型的规模、体积和参数量一直在增长，ML 从业者发现想在自家硬件上训练、甚至只是加载这些大模型都越来越难。** 一方面，人们发现大模型学得更快（对数据和计算更高效），性能也显著优于小模型 [1]；另一方面，在大多数现有硬件上训练这样的模型又力不从心。

分布式训练是训练这类大 ML 模型的关键。**大规模分布式训练**领域近期取得了重要进展，最值得一提的有：

- 用 ZeRO（Zero Redundancy Optimizer，零冗余优化器）做数据并行 [2]：Stage 1 在数据并行 worker/GPU 之间分片优化器状态；Stage 2 分片优化器状态+梯度；Stage 3 分片优化器状态+梯度+模型参数；CPU Offload：在 ZeRO Stage 2 基础上把梯度和优化器状态卸载到 CPU [3]
- 张量并行（Tensor Parallelism）[4]：模型并行的一种形式，把单个巨大量级参数层的参数以巧妙的方式分片到多张卡上，既实现并行计算，又避免昂贵的通信同步开销。
- 流水线并行（Pipeline Parallelism）[5]：模型并行的另一种形式，把模型的不同层放到不同的卡上，并用流水线技术让所有卡同时保持忙碌。例如第二张卡在处理第一个 micro-batch 时，第一张卡已经在算第二个 micro-batch。
- 3D 并行 [3]：ZeRO 数据并行 + 张量并行 + 流水线并行组合起来，训练参数量达数千亿级别的巨型模型。例如 BigScience 176B 参数语言模型就是这么做的 [6]。

本文聚焦 ZeRO 数据并行，更具体地说，是 PyTorch 的最新特性 **[FullyShardedDataParallel (FSDP)](https://pytorch.org/blog/introducing-pytorch-fully-sharded-data-parallel-api/)**。**[DeepSpeed](https://github.com/microsoft/deepspeed)** 和 **[FairScale](https://github.com/facebookresearch/fairscale/)** 都实现了 ZERO 论文的核心思想，且已经集成进 `transformers` 的 Trainer，还配有优秀博客 [Fit More and Train Faster With ZeRO via DeepSpeed and FairScale](https://huggingface.co/blog/zero-deepspeed-fairscale) [10]。PyTorch 最近把 Fairscale 的 FSDP 上游合入了 PyTorch Distributed 并做了额外优化。

## Accelerate 🚀：不改一行代码用上 PyTorch FSDP

我们来看用 GPT-2 Large（762M）和 XL（1.5B）变体做因果语言建模的任务。

下面是 GPT-2 预训练代码。它与官方的因果语言建模示例[（这里）](https://github.com/huggingface/transformers/blob/main/examples/pytorch/language-modeling/run_clm_no_trainer.py)基本一致，只是多了 `n_train`（2000）和 `n_val`（500）两个参数，用来避免对全量数据做预处理/训练，方便快速做概念验证基准。

[run_clm_no_trainer.py](https://huggingface.co/blog/assets/62_pytorch_fsdp/run_clm_no_trainer.py)

### 多 GPU FSDP

这里我们实验单节点多 GPU 设置，比较分布式数据并行（DDP）与各种 FSDP 配置的性能。先用 GPT-2 Large（762M）模型——DDP 在某些批大小下不会报 OOM；再用 GPT-2 XL（1.5B）——DDP 即使批大小为 1 也会 OOM。我们会看到：FSDP 让 GPT-2 Large 支持更大的批大小，还能以不错的批大小训练 DDP 根本装不下的 GPT-2 XL。

**硬件环境**：2 张 24GB NVIDIA Titan RTX。

训练 GPT-2 Large 模型（762M 参数）的命令：

```
export BS=#`try with different batch sizes till you don't get OOM error,
#i.e., start with larger batch size and go on decreasing till it fits on GPU`

time accelerate launch run_clm_no_trainer.py \
--model_name_or_path gpt2-large \
--dataset_name wikitext \
--dataset_config_name wikitext-2-raw-v1 \
--per_device_train_batch_size $BS 
--per_device_eval_batch_size $BS 
--num_train_epochs 1 
--block_size 12
```

FSDP 运行示例：[![Sample FSDP Run](https://huggingface.co/blog/assets/62_pytorch_fsdp/sample_fsdp_run.png)](https://huggingface.co/blog/assets/62_pytorch_fsdp/sample_fsdp_run.png)

| 方法 | 最大批大小 ($BS) | 大致训练时间（分钟） | 备注 |
| --- | --- | --- | --- |
| DDP (Distributed Data Parallel) | 7 | 15 |  |
| DDP + FP16 | 7 | 8 |  |
| FSDP with SHARD_GRAD_OP | 11 | 11 |  |
| FSDP with min_num_params = 1M + FULL_SHARD | 15 | 12 |  |
| FSDP with min_num_params = 2K + FULL_SHARD | 15 | 13 |  |
| FSDP with min_num_params = 1M + FULL_SHARD + Offload to CPU | 20 | 23 |  |
| FSDP with min_num_params = 2K + FULL_SHARD + Offload to CPU | 22 | 24 |  |

表 1：GPT-2 Large（762M）模型上的 FSDP 基准

相对 DDP，从表 1 可以看到 FSDP **支持更大的批大小**：不用 CPU 卸载时最高 2 倍，用 CPU 卸载时最高 3 倍。训练时间方面，混合精度 DDP 最快，其次是 FSDP 的 ZERO Stage 2 和 Stage 3。由于因果语言建模的上下文序列长度固定（--block_size），FSDP 带来的训练时间加速不算大。对于动态批处理的应用，FSDP 的大批大小应该能带来可观的训练提速。FSDP 的混合精度目前与 transformer 一起使用时还有几个[问题](https://github.com/pytorch/pytorch/issues/75676)，一旦支持，训练时间的提速还会明显提高。

| DDP + FP16 | 1 | 1 | 无 | OOM 错误 RuntimeError: CUDA out of memory. Tried to allocate 40.00 MiB (GPU 0; 23.65 GiB total capacity; 22.27 GiB already allocated; 20.31 MiB free; 22.76 GiB reserved in total by PyTorch) |
| FSDP with min_num_params = 2K | 5 | 2 | 0.6 |  |
| FSDP with min_num_params = 2K + Offload to CPU | 10 | 1 | 3 |  |

表 2：GPT-2 XL（1.5B）模型上的 FSDP 基准

从表 2 可以看到，DDP（无论有没有 fp16）连批大小 1 都跑不起来，直接 CUDA OOM。FSDP 的 Zero-Stage 3 可以在 2 张卡上跑批大小 5（有效批大小 = 10 = 5×2）。FSDP 加 CPU 卸载则可在 2 卡时把单卡最大批大小提高到 14。**FSDP 加 CPU 卸载让单张 GPU 就能以批大小 10 训练 GPT-2 1.5B 模型。**这让算力资源有限的 ML 从业者也能训练这样的大模型，从而让大模型训练更普惠。

### FSDP 集成的能力与限制

来看看 Accelerate 当前对 FSDP 的支持范围和已知限制。

**支持 FSDP 所需的 PyTorch 版本**：PyTorch Nightly（若本文发布后 1.12.0 已出，也可用 1.12.0），因为在 FSDP 下保存模型只有新版本才修好。

**通过 CLI 配置：**

- **Sharding Strategy（分片策略）**：[1] FULL_SHARD，[2] SHARD_GRAD_OP
- **Min Num Params**：FSDP 默认 Auto Wrapping 的最小参数量。
- **Offload Params**：是否把参数和梯度卸载到 CPU。

想要更多控制，用户可以使用 `FullyShardedDataParallelPlugin`，指定 `auto_wrap_policy`、`backward_prefetch` 和 `ignored_modules`。

创建该类实例后，在构造 Accelerator 对象时传入即可。

关于这些选项的更多信息，请参考 PyTorch [FullyShardedDataParallel](https://github.com/pytorch/pytorch/blob/0df2e863fbd5993a7b9e652910792bd21a516ff3/torch/distributed/fsdp/fully_sharded_data_parallel.py#L236) 源码。

接下来看 `min_num_params` 配置为何重要。下面摘录自 [8]，说明 FSDP Auto Wrap Policy 的重要性。

[![Importance of FSDP Auto Wrap Policy](https://huggingface.co/blog/assets/62_pytorch_fsdp/auto_wrap_importance.png)](https://huggingface.co/blog/assets/62_pytorch_fsdp/auto_wrap_importance.png)

（来源：[链接](https://pytorch.org/tutorials/intermediate/FSDP_tutorial.html)）

使用 `default_auto_wrap_policy` 时，如果某一层的参数量超过 min_num_params，该层就会被包进 FSDP 模块。微调 BERT-Large（330M）在 GLUE MRPC 任务上的代码，就是官方完整 NLP 示例——演示如何正确使用 FSDP 特性——外加了追踪峰值内存用量的工具。

[fsdp_with_peak_mem_tracking.py](https://github.com/huggingface/accelerate/tree/main/examples/by_feature/fsdp_with_peak_mem_tracking.py)

我们利用 Accelerate 的追踪功能，记录训练和评估的峰值内存以及评估指标。下面是 wandb [run](https://wandb.ai/smangrul/FSDP-Test?workspace=user-smangrul) 的截图。[![Wandb Run](https://huggingface.co/blog/assets/62_pytorch_fsdp/wandb_run.png)](https://huggingface.co/blog/assets/62_pytorch_fsdp/wandb_run.png)

可以看到：DDP 的内存占用是"带 auto wrap 的 FSDP"的两倍；不带 auto wrap 的 FSDP 比带 wrap 的多，但明显小于 DDP；`min_num_params=2k` 的 FSDP 比 `min_num_params=1M` 的仅省一点点。这正说明 FSDP Auto Wrap Policy 的重要性——用户应多试不同的 `min_num_params`，找到既能显著省内存、又不会造成大量通信开销的设置。如 [8] 所述，PyTorch 团队正在为该配置开发自动调优工具。

#### **需要注意的几个坑**

- PyTorch FSDP 会自动包装子模块、展平参数并原地分片参数。因此，在模型包装之前创建的优化器会失效并占用更多内存。所以强烈建议（也更高效）在创建优化器之前先 prepare 模型。对于单模型，`Accelerate` 会自动帮你包装模型并创建优化器，同时给出警告。FSDP Warning: When using FSDP, it is efficient and recommended to call prepare for the model before creating the optimizer

使用 FSDP 时，推荐的模型/优化器准备方式如下：

```
model = AutoModelForSequenceClassification.from_pretrained("bert-base-cased", return_dict=True)
+ model = accelerator.prepare(model)

optimizer = torch.optim.AdamW(params=model.parameters(), lr=lr)

- model, optimizer, train_dataloader, eval_dataloader, lr_scheduler = accelerator.prepare(model,
-        optimizer, train_dataloader, eval_dataloader, lr_scheduler
-    )

+ optimizer, train_dataloader, eval_dataloader, lr_scheduler = accelerator.prepare(
+         optimizer, train_dataloader, eval_dataloader, lr_scheduler
+        )
```

- 单模型场景下，如果你在包装前创建了多参数组的优化器，然后放在一起调用 prepare，参数组会丢失，并显示警告：FSDP Warning: When using FSDP, several parameter groups will be conflated into a single one due to nested module wrapping and parameter flattening.

## 工作原理 📝

[![FSDP Workflow](https://huggingface.co/blog/assets/62_pytorch_fsdp/FSDP_workflow.png)](https://huggingface.co/blog/assets/62_pytorch_fsdp/FSDP_workflow.png)

（来源：[链接](https://pytorch.org/blog/introducing-pytorch-fully-sharded-data-parallel-api/)）

上面的流程图概括了 FSDP 激活后底层发生了什么。先理解 DDP 怎么工作，再看 FSDP 如何改进。DDP 中，每个 worker/卡/GPU 都持有一份完整的模型参数、梯度和优化器状态副本。每个 worker 拿到不同的数据批次，做前向、算损失，再反向传播产生梯度。随后执行 all-reduce：每个 worker 收到其他 worker 的梯度并求平均。这样每个 worker 得到相同的全局梯度，交给优化器更新模型参数。可见，完整副本消耗了大量冗余显存，限制了批大小，也限制了能训练的模型大小。

FSDP 正是对症下药：把优化器状态、梯度和模型参数分片到各数据并行 worker 上，还支持把这些张量卸载到 CPU，从而能加载装不进 GPU 显存的大模型。与 DDP 类似，每个 worker 拿不同的批次。前向传播时，若启用了 CPU 卸载，先把本地分片的参数拷贝到 GPU/加速器；随后每个 worker 对给定的 FSDP 包装模块/层执行 all-gather 取得所需参数，完成计算后释放/清空其他 worker 的参数分片，对所有 FSDP 模块重复这一过程。前向后计算损失；反向传播时再次 all-gather 得到该 FSDP 模块所需参数，算出本地梯度后释放其他分片。然后本地梯度经 reduce-scatter 求平均并分发给各相关 worker，让每个 worker 更新自己本地分片的参数。若启用 CPU 卸载，梯度会传回 CPU，直接在 CPU 上更新参数。

关于 PyTorch FSDP 工作原理的深度细节和大量实验，见文献 [7, 8, 9]。
