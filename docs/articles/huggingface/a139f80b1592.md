本指南是一份完全公开、成本极低的配方，让一个小模型在结构化输出合规性上有大幅提升。我们用 [TRL 库](https://huggingface.co/docs/trl/en/index)通过组相对策略优化（Group Relative Policy Optimization，GRPO）微调 [LFM2.5-350M](https://huggingface.co/LiquidAI/LFM2.5-350M)，并在 [IFStruct 基准](https://huggingface.co/datasets/LiquidAI/ifstruct-v1.0)上做评估。整个训练只有约 500 条样本、100 个 step，小到账外免费的 Colab 或 Kaggle GPU 就能跑，代码见 [GitHub](https://github.com/Liquid4All/cookbook/blob/main/finetuning/notebooks/grpo_with_trl_ifstruct.ipynb)。结果显示，即使是轻量微调，也能把 IFStruct 基准上的表现从 **22.6% 提升到 29.7%**。

结构化输出是 LLM 最常见的现实任务之一，但大多数基准都把它混在更广的推理或抽取分数里，而不是单独度量。模型能否可靠地返回按要求的格式和形状、可解析的有效输出——即 schema 合规性——往往决定了它能不能接入下游系统。

*注意，这里描述的训练流水线并不是 [IFStruct 博客](https://www.liquid.ai/blog/ifstruct-v1.0)里那个 RL 模型所用的训练管线。本 notebook 不追求复现 IFStruct 基准分数，而是展示针对任务的微调如何提升小模型的表现、追平大得多的模型。*

## 前置条件

本指南分两半，运行在不同地方：

- **微调**在 GPU 上跑。配套 notebook 按账外免费档 Colab 或 Kaggle GPU 的规模设计。
- **评估**可以通过 `llama.cpp` 在本机 MacBook（一台配备 Apple M5 Max、36 GB 统一内存的 MacBook Pro）上跑。llama.cpp 会暴露一个 OpenAI 兼容服务器，供 IFStruct 评估器调用。

Python 工具链需要 [`uv`](https://docs.astral.sh/uv/)，服务化需要 `llama.cpp`。按照 [Liquid AI 的 llama.cpp 部署文档](https://docs.liquid.ai/deployment/on-device/llama-cpp)，用 Homebrew 安装 `llama.cpp`，并确认 `llama-server` 可用：

```
brew install llama.cpp
llama-server --version
```

## 在 LFM2.5-350M（基础模型）上做 IFStruct 评估

开始之前，我们先在 [IFStruct 基准](https://huggingface.co/datasets/LiquidAI/ifstruct-v1.0)上评估 LFM2.5-350M，看看能否**复现报道的 21.1% 分数**。

**IFStruct** 是一个测试 LLM 输出有效性和 schema 遵循的基准。基准以开源方式放在 [Liquid4All/ifstruct](https://github.com/Liquid4All/ifstruct)，公开的基准数据集在 Hugging Face 上：[LiquidAI/ifstruct-v1.0](https://huggingface.co/datasets/LiquidAI/ifstruct-v1.0)。

```
git clone https://github.com/Liquid4All/ifstruct.git
```

为了做评估对比，我们用 `llama.cpp` 在 MacBook 上本地服务模型。使用的是 `BF16` GGUF（[LiquidAI/LFM2.5-350M-GGUF](https://huggingface.co/LiquidAI/LFM2.5-350M-GGUF)）。

然后用下面的命令启动基础模型服务器：

```
llama-server \
  -hf LiquidAI/LFM2.5-350M-GGUF:BF16 \
  -c 32768 \
  -np 4 \
  -ngl 99 \
  --alias LiquidAI/LFM2.5-350M \
  --host 127.0.0.1 \
  --port 8080
```

- `--alias`：IFStruct 发给 OpenAI 兼容端点的模型名
- `-ngl 99`：让 `llama.cpp` 在有 GPU 时把所有层卸载到 GPU
- `-np 4`：并行处理四个请求
- `-c 32768`：prompt 上下文大小

服务器跑起来后，就可以用 2000 条样本跑完整基准：

```
uv run ifstruct-eval \
  --model LiquidAI/LFM2.5-350M \
  --base-url http://localhost:8080/v1 \
  --api-key dummy \
  --dataset data/test.jsonl \
  --results-file results/lfm2.5-350m-llamacpp-base.json \
  --n-threads 4 \
  --max-tokens 2048 \
  -v
```

## 用 TRL 对结构化输出做 GRPO 微调

完整可跑的流水线在[配套 notebook](https://github.com/Liquid4All/cookbook/blob/main/finetuning/notebooks/grpo_with_trl_ifstruct.ipynb)里。本节只讲相关部分。

### 训练数据

我们用 [`nvidia/Nemotron-RL-instruction_following-structured_outputs`](https://huggingface.co/datasets/nvidia/Nemotron-RL-instruction_following-structured_outputs)，每条 prompt 都配一个目标 JSON Schema 和期望字段数。训练约用 500 条样本。

由于 Nemotron 的数据分布与 IFStruct 评估不同，我们对 prompt 做了增强，以弥合两者间的两个差距：

- **40%** 追加一句"把输出放在围栏代码块中返回"的指令，让模型学会*遵循*格式指令，而不是一律输出裸 JSON。
- 另 **20%**（不重叠）被转换成顶层数组任务（schema 包在一个 `array` 里并要求元素数量），以此训练裸列表输出和数量合规。

### 模型与 LoRA

我们加载 `LiquidAI/LFM2.5-350M` 并挂上 LoRA adapter。由于 LFM2.5 采用注意力/卷积混合架构，我们瞄准 LFM 特有的模块名：

```
lora_config = LoraConfig(
    r=16, 
    lora_alpha=32, 
    bias="none", 
    task_type="CAUSAL_LM",
    target_modules=[
        "q_proj", "k_proj", "v_proj", "out_proj", "in_proj",
        "w1", "w2", "w3",
    ],
)
```

这大约训练 6M 参数，占模型的 1.66%。

### 奖励函数

然后我们定义三个奖励函数，都按 `[0, 1]` 刻度给每个 completion 的*结构*正确性打分：

- `json_format_reward`：输出是否可解析？形式是否符合要求？形式正确（围栏 vs 裸格式）得满分（`1.0`），格式不对但可解析得 `0.2`，不可解析得 `0.0`。
- `field_count_reward`：对象的顶层字段数量是否符合预期？精确匹配得 `1.0`，偏差按线性衰减扣分。
- `schema_validation_reward`：输出能否通过该行 JSON Schema 的验证？它会统计所有约束违反，并按必需键覆盖情况给出部分得分。

我们以加权和组合三个奖励：`reward_weights=[1.0, 0.5, 2.0]`。

### 训练

我们训练 100 步，每个 prompt 组采样 8 个 generation，按免费档 16 GB GPU 配置：

```
from trl import GRPOConfig

training_args = GRPOConfig(
    output_dir="./outputs/lfm25-350m-nemotron-schema-grpo",
    learning_rate=5e-5,
    max_steps=100,
    warmup_steps=10,
    num_generations=8,              # completions sampled per prompt group
    per_device_train_batch_size=4,
    gradient_accumulation_steps=8,  # 4 prompt groups per optimizer step
    steps_per_generation=2,
    max_completion_length=1024,     # room for nested JSON
    mask_truncated_completions=False,
    temperature=1.1,                # hotter sampling keeps groups varied
    beta=0.01,                      # KL penalty toward the reference model
    reward_weights=[1.0, 0.5, 2.0], # json_format, field_count, schema_validation
    logging_steps=1,
    save_steps=100,
)
```

从 notebook 中可以看到，整个训练过程中三个奖励分量都在上升，与参考模型的 KL 在 warmup 后离开零点，而被截断 completion 的比例始终接近零。

### 合并并保存模型

最后，我们把 LoRA adapter 合并回基础权重，存成一个自包含的 checkpoint，方便转成 GGUF 用于服务：

```
MERGED_DIR = f"{training_args.output_dir}-merged"

merged_model = trainer.model.merge_and_unload()
merged_model.save_pretrained(MERGED_DIR)
tokenizer.save_pretrained(MERGED_DIR)
```

## 在 GRPO 调优后的 LFM2.5-350M 上做 IFStruct 评估

GRPO 微调后，我们重新跑 IFStruct 评估。为此需要把合并后的 checkpoint 转成 BF16 GGUF。转换脚本随 llama.cpp 源码发布，所以我们把仓库 clone 一次，再安装转换器的 `gguf` 包。

```
git clone --depth 1 https://github.com/ggml-org/llama.cpp
pip install ./llama.cpp/gguf-py

mkdir -p models
python llama.cpp/convert_hf_to_gguf.py \
  PATH_TO_YOUR_MERGED_MODEL \
  --outfile ./models/lfm25-350m-grpo-bf16.gguf \
  --outtype bf16
```

然后用下面命令服务合并后的模型：

```
llama-server \
  -m ./models/lfm25-350m-grpo-bf16.gguf \
  --alias lfm25-350m-grpo-structured-output \
  -c 32768 \
  -np 4 \
  -ngl 99 \
  --host 127.0.0.1 \
  --port 8081
```

接着再次用微调后的模型跑完整的 IFStruct 评估：

```
uv run ifstruct-eval \
  --model lfm25-350m-grpo-structured-output \
  --base-url http://localhost:8081/v1 \
  --api-key dummy \
  --dataset data/test.jsonl \
  --results-file results/lfm25-350m-grpo.json \
  --n-threads 4 \
  --max-tokens 2048 \
  -v
```

增益恰好出现在训练瞄准的地方：JSON 通过率提高了近 14 个百分点（18.0% → 31.9%），而 YAML 基本没变。虽然这仍低于 [Qwen3.5-2B 的 33.15%](https://www.liquid.ai/blog/ifstruct-v1.0)，但它说明：即使是轻量的任务定制微调，也能让小模型逼近大模型。

## 结论

一次只有约 500 条样本、100 步的短 GRPO 训练，就能把 350M 参数小模型在 IFStruct 上从 22.6% 拉到 29.7%。要点在于：廉价的、针对任务的奖励信号可以让小模型在*形式*上可靠得多，缩小与体量数倍于己的模型之间的差距。

要复现或扩展这项工作，可参考原始的 [IFStruct v1.0 博客](https://www.liquid.ai/blog/ifstruct-v1.0)、[Liquid4All/ifstruct](https://github.com/Liquid4All/ifstruct) 基准仓库，以及 [LiquidAI/ifstruct-v1.0](https://huggingface.co/datasets/LiquidAI/ifstruct-v1.0) 数据集。
