## 用 PyTorch / XLA 在 Cloud TPU 上训练你喜欢的 Transformer

PyTorch-TPU 项目源自 Facebook PyTorch 团队与 Google TPU 团队的协作，2019 年在 PyTorch Developer Conference 上正式发布。此后我们与 Hugging Face 团队合作，带来使用 [PyTorch / XLA](https://github.com/pytorch/xla) 在 Cloud TPU 上训练的一等公民支持。这次集成让 PyTorch 用户能在 Cloud TPU 上运行并扩展自己的模型，同时完全保持 Hugging Face trainers 的接口不变。

本文概述 Hugging Face 库做了哪些改动、PyTorch / XLA 库做什么、一个帮你开始在 Cloud TPU 上训练喜欢的 Transformer 的示例，以及性能基准。如果你已经等不及想上 TPU，可以直接跳到[“在 Cloud TPUs 上训练 Transformer”](https://huggingface.co/blog/pytorch-xla#train-your-transformer-on-cloud-tpus)一节——所有 PyTorch / XLA 的机制我们都已经在 `Trainer` 模块里替你处理好了！

### XLA:TPU 设备类型

PyTorch / XLA 为 PyTorch 新增了一个 `xla` 设备类型。这个设备类型和其他 PyTorch 设备类型用法完全一样。例如下面是创建并打印一个 XLA 张量：

```
import torch
import torch_xla
import torch_xla.core.xla_model as xm

t = torch.randn(2, 2, device=xm.xla_device())
print(t.device)
print(t)
```

这段代码应该看起来很熟悉。PyTorch / XLA 使用与普通 PyTorch 相同的接口，只有少量新增。导入 `torch_xla` 会初始化 PyTorch / XLA，`xm.xla_device()` 返回当前 XLA 设备。根据你的环境，它可能是 CPU、GPU 或 TPU，但本文主要聚焦 TPU。

`Trainer` 模块依靠 `TrainingArguments` 数据类来定义训练细节。它处理各种参数——批大小、学习率、梯度累积等等——也包括所用设备。如上所述，在 `TrainingArguments._setup_devices()` 中，当使用 XLA:TPU 设备时，我们直接返回 `Trainer` 要用的 TPU 设备：

```
@dataclass
class TrainingArguments:
    ...
    @cached_property
    @torch_required
    def _setup_devices(self) -> Tuple["torch.device", int]:
        ...
        elif is_torch_tpu_available():
            device = xm.xla_device()
            n_gpu = 0
        ...

        return device, n_gpu
```

### XLA 设备的 Step 计算

在典型的 XLA:TPU 训练场景中，我们是在多个 TPU 核上并行训练（单台 Cloud TPU 设备包含 8 个 TPU 核）。所以要确保所有梯度在数据并行副本之间交换——合并梯度并执行一次优化器 step。为此我们提供 `xm.optimizer_step(optimizer)`，它负责梯度合并与 step 执行。Hugging Face trainer 相应地更新了训练 step 来使用 PyTorch / XLA 的 API：

```
class Trainer:
…
   def train(self, *args, **kwargs):
       ...
                    if is_torch_tpu_available():
                        xm.optimizer_step(self.optimizer)
```

### PyTorch / XLA 输入管线

运行 PyTorch / XLA 模型主要有两块：(1) 惰性追踪并执行你的模型图（详见下文["PyTorch / XLA 库"](#pytorch--xla-library)一节），(2) 给模型喂数据。不做任何优化时，模型的追踪/执行与喂数据会串行进行，导致宿主机 CPU 和 TPU 加速器各自出现空闲时间段。为避免这点，我们提供的 API 会把两者流水化，从而在第 n 步执行的同时就能重叠第 n+1 步的追踪。

```
import torch_xla.distributed.parallel_loader as pl
...

```

### Checkpoint 的写入与加载

当 XLA 设备上的张量被 checkpoint 后再从 checkpoint 加载回来时，会先回到原来的设备。所以在 checkpoint 模型中的张量之前，你要确保所有张量都转到 CPU 设备而非 XLA 设备。这样加载回来时先经 CPU，你才有机会把它们放到任何你想要的 XLA 设备上。我们提供 `xm.save()` API，它已经处理好"每个宿主机上只有一个进程（若宿主机间共享文件系统，则全局只有一个）负责写存储"这件事。

```
class PreTrainedModel(nn.Module, ModuleUtilsMixin, GenerationMixin):
…
    def save_pretrained(self, save_directory):
        ...
        if getattr(self.config, "xla_device", False):
            import torch_xla.core.xla_model as xm

            if xm.is_master_ordinal():
                # Save configuration file
                model_to_save.config.save_pretrained(save_directory)
            # xm.save takes care of saving only from master
            xm.save(state_dict, output_model_file)
```

```
class Trainer:
…

           xm.save(self.lr_scheduler.state_dict(),
                   os.path.join(output_dir, "scheduler.pt"))
```

## PyTorch / XLA 库

PyTorch / XLA 是一个 Python 包，用 XLA 线性代数编译器把 PyTorch 深度学习框架与 XLA 设备连接起来——包括 CPU、GPU 和 Cloud TPU。下文部分内容也见我们的 [API_GUIDE.md](https://github.com/pytorch/xla/blob/master/API_GUIDE.md)。

### PyTorch / XLA 张量是惰性的

使用 XLA 张量和设备只需改动几行代码。不过尽管 XLA 张量表现得很像 CPU 和 CUDA 张量，内部机制却不同。CPU 和 CUDA 张量立即（eager）下发操作，XLA 张量则是惰性的：它们把操作记录进一张图，直到需要结果时才执行。这样推迟执行让 XLA 得以优化——多个独立操作组成的图可能被融合成单个优化后的操作。

惰性执行通常对调用方透明。PyTorch / XLA 自动构图、把图发送到 XLA 设备、并在 XLA 设备与 CPU 之间拷贝数据时做好同步。在优化器 step 时插入屏障会显式同步 CPU 与 XLA 设备。

也就是说，当你调用 `model(input)` 前向、计算损失 `loss.backward()`、执行 `xm.optimizer_step(optimizer)` 时，后台其实在构建所有操作的图。只有当你显式求值张量（例如打印它、或把它移到 CPU 设备）或标记一个 step（每次迭代 `MpDeviceLoader` 时会自动做）时，整步才真正执行。

### 追踪、编译、执行、循环往复

从用户视角看，跑在 PyTorch / XLA 上的模型的典型训练流程是前向、反向、优化器 step。从 PyTorch / XLA 库视角看，情况略有不同。

用户运行前向和反向时，一张中间表示（IR）图被即时追踪。通向每个根/输出张量的 IR 图可以这样查看：

```
>>> import torch
>>> import torch_xla
>>> import torch_xla.core.xla_model as xm
>>> t = torch.tensor(1, device=xm.xla_device())
>>> s = t*t
>>> print(torch_xla._XLAC._get_xla_tensors_text([s]))
IR {
  %0 = s64[] prim::Constant(), value=1
  %1 = s64[] prim::Constant(), value=0
  %2 = s64[] xla::as_strided_view_update(%1, %0), size=(), stride=(), storage_offset=0
  %3 = s64[] aten::as_strided(%2), size=(), stride=(), storage_offset=0
  %4 = s64[] aten::mul(%3, %3), ROOT=0
}
```

在用户程序跑前向和反向的过程中，这张活动图不断累积；一旦调用 `xm.mark_step()`（由 `pl.MpDeviceLoader` 间接调用），活动张量的图就被切一刀。这次截断标志一步的完成，随后我们把 IR 图下降（lower）为 XLA 高级操作（HLO）——XLA 自己的 IR 语言。

这张 HLO 图随后被编译成 TPU 二进制并在 TPU 设备上执行。不过编译步骤很昂贵——通常比单步执行还久，如果每一步都重新编译用户程序，开销会很高。为此我们有缓存，用 HLO 图的唯一哈希标识来存储已编译的 TPU 二进制。第一步之后缓存建好，后续各步通常无需重新编译，直接从缓存查表即可。

由于 TPU 编译通常远慢于单步执行时间，如果图的形状一直变化，就会不断缓存未命中、编译过频。为了把编译成本压到最低，我们建议尽量保持张量形状固定。Hugging Face 库的形状基本已经是静态的——输入 token 会被合适地 padding——所以整个训练期间缓存应该一直命中。可以用 PyTorch / XLA 提供的调试工具检查。下面这个例子里，编译只发生了 5 次（`CompileTime`），而执行在 1220 步的每一步都发生（`ExecuteTime`）：

### 在 Cloud TPUs 上训练 Transformer

配置你的 VM 和 Cloud TPU，请依次按照["设置 Compute Engine 实例"](https://cloud.google.com/tpu/docs/tutorials/transformer-pytorch#set_up_a_instance)和["启动 Cloud TPU 资源"](https://cloud.google.com/tpu/docs/tutorials/transformer-pytorch#launch-tpu)（写作时为 pytorch-1.7 版本）两节操作。VM 和 Cloud TPU 建好后，SSH 连上你的 GCE VM，运行下面的命令即可开始训练 `bert-large-uncased`（批大小按 v3-8 设备设置，v2-8 上可能 OOM）：

```
conda activate torch-xla-1.7
export TPU_IP_ADDRESS="ENTER_YOUR_TPU_IP_ADDRESS"  # ex. 10.0.0.2
export XRT_TPU_CONFIG="tpu_worker;0;$TPU_IP_ADDRESS:8470"
git clone -b v4.2.2 https://github.com/huggingface/transformers.git
cd transformers && pip install .
pip install datasets==1.2.1
python examples/xla_spawn.py \
  --num_cores 8 \
  examples/language-modeling/run_mlm.py \
  --dataset_name wikitext \
  --dataset_config_name wikitext-103-raw-v1 \
  --max_seq_length 512 \
  --pad_to_max_length \
  --logging_dir ./tensorboard-metrics \
  --cache_dir ./cache_dir \
  --do_train \
  --do_eval \
  --overwrite_output_dir \
  --output_dir language-modeling \
  --overwrite_cache \
  --tpu_metrics_debug \
  --model_name_or_path bert-large-uncased \
  --num_train_epochs 3 \
  --per_device_train_batch_size 8 \
  --per_device_eval_batch_size 8 \
  --save_steps 500000
```

上面的训练应在大约不到 200 分钟内完成，评估困惑度约 3.25。
