像 [ChatGPT](https://huggingface.co/blog/%5Bhttps://openai.com/blog/chatgpt%5D(https://openai.com/blog/chatgpt))、[GPT-4](https://huggingface.co/blog/%5Bhttps://openai.com/research/gpt-4%5D(https://openai.com/research/gpt-4)) 和 [Claude](https://huggingface.co/blog/%5Bhttps://www.anthropic.com/index/introducing-claude%5D(https://www.anthropic.com/index/introducing-claude)) 这样的模型是强大的语言模型，它们用一种叫"人类反馈强化学习"（Reinforcement Learning from Human Feedback，RLHF）的方法做了微调，以更好地与我们期望它们表现和使用了它们的方式对齐。

在这篇博客里，我们展示用 RLHF 训练一个 [LlaMa 模型](https://ai.facebook.com/blog/large-language-model-llama-meta-ai) 来回答 [Stack Exchange](https://stackexchange.com) 上的问题所涉及的全部步骤，它结合了三步：

- 监督微调（Supervised Fine-tuning，SFT）
- 奖励/偏好建模（Reward / preference modeling，RM）
- 人类反馈强化学习（RLHF）

[![](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/instructGPT.png)](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/instructGPT.png) *取自 InstructGPT 论文：Ouyang, Long, et al. "Training language models to follow instructions with human feedback." arXiv preprint arXiv:2203.02155 (2022).*

通过结合这些方法，我们发布了 StackLLaMA 模型。该模型可在 [🤗 Hub](https://huggingface.co/trl-lib/llama-se-rl-peft) 上获取（原始 LLaMA 模型见 [Meta 的 LLaMA 发布](https://ai.facebook.com/blog/large-language-model-llama-meta-ai/)），而 [整条训练流水线](https://huggingface.co/docs/trl/index) 作为 Hugging Face TRL 库的一部分提供。为了让你先尝一口模型能做什么，试试下面的演示！

## LLaMA 模型

做 RLHF 时，从一个有能力的模型起步很重要：RLHF 那一步只是一个把模型对齐到我们希望如何与它交互、以及我们希望它如何响应的微调步骤。因此我们选择用最近提出、表现出色的 [LLaMA 模型](https://arxiv.org/abs/2302.13971)。LLaMA 模型是 Meta AI 开发的最新大型语言模型，参数规模从 7B 到 65B，训练量在 1T 到 1.4T token 之间，能力非常强。下面所有步骤我们都用 7B 模型作基座！要访问模型，请使用 Meta AI 的 [表单](https://docs.google.com/forms/d/e/1FAIpQLSfqNECQnMkycAp2jP4Z9TFX0cGR4uf7b_fBxjY_OjhJILlKGA/viewform)。

## Stack Exchange 数据集

收集人类反馈是一项复杂而昂贵的事业。为了在这个示例里把流程引导起来、同时仍构建一个有用的模型，我们使用 [StackExchange 数据集](https://huggingface.co/datasets/HuggingFaceH4/stack-exchange-preferences)。该数据集包含来自 StackExchange 平台的问题及其对应答案（包括用于代码的 StackOverflow 以及许多其他主题）。它对这个用例很有吸引力，因为答案带着点赞数，以及一个"采纳答案"的标签。

我们遵循 [Askell et al. 2021](https://arxiv.org/abs/2112.00861) 描述的方法，给每个答案分配一个分数：

`score = log2 (1 + upvotes) rounded to the nearest integer, plus 1 if the questioner accepted the answer (we assign a score of −1 if the number of upvotes is negative).`

对于奖励模型，正如我们将看到的，每个问题总是需要两个答案来比较。有些问题有几十个答案，导致很多可能的配对。我们为每个问题最多采样十对答案，以限制每个问题的数据点数量。最后，我们通过把 HTML 转成 Markdown 来清理格式，让模型的输出更易读。你可以在 [这里](https://huggingface.co/datasets/lvwerra/stack-exchange-paired) 找到数据集以及处理 notebook。

## 高效训练策略

即便训练最小的 LLaMA 模型也需要巨量内存。简单算一下：在 bf16 下，每个参数用 2 字节（fp32 下是 4 字节），外加例如在 Adam 优化器里用的 8 字节（见 Transformers 的 [性能文档](https://huggingface.co/docs/transformers/perf_train_gpu_one#optimizer)）。所以一个 7B 参数模型仅为了装进内存就要 `(2+8)*7B=70GB`，而且在计算注意力分数这类中间值时很可能还需要更多。这样你连一块 80GB 的 A100 都装不下。你可以用些技巧，比如更高效的优化器或半精度训练，再往内存里塞一点，但迟早会用完。

另一个选择是使用参数高效微调（Parameter-Efficient Fine-Tuning，PEFT）技术，例如 [`peft`](https://github.com/huggingface/peft) 库，它能在一个以 8-bit 加载的模型上做低秩适配（Low-Rank Adaptation，LoRA）。

[![](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/lora-animated.gif)](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/lora-animated.gif)
*线性层的低秩适配：附加参数（橙色）被加在冻结层（蓝色）旁边，所得的编码隐藏状态与冻结层的隐藏状态相加。*

以 8bit 加载模型大幅减少了内存占用，因为权重每个参数只需一字节（例如 7B LlaMa 内存里只有 7GB）。LoRA 不直接训练原始权重，而是在某些特定层（通常是注意力层）之上加小的适配层；于是可训练参数量被大幅削减。

在这种情况下，一个经验法则是每十亿参数分配约 1.2-1.4GB（取决于批大小和序列长度）来容纳整个微调设置。如上面附带的博客所详述的，这让低成本微调更大的模型（在 NVIDIA A100 80GB 上可达 50-60B 规模）成为可能。

这些技术让在消费级设备和 Google Colab 上微调大模型成为可能。值得注意的演示有微调 `facebook/opt-6.7b`（`float16` 下 13GB）和 `openai/whisper-large` 在 Google Colab（15GB GPU 显存）上。要了解更多关于使用 `peft` 的内容，参考我们的 [github 仓库](https://github.com/huggingface/peft) 或 [上一篇博客](https://huggingface.co/blog/trl-peft)([https://huggingface.co/blog/trl-peft](https://huggingface.co/blog/trl-peft)))，讲的是在消费级硬件上训练 20b 参数模型。

现在我们可以把非常大的模型塞进单块 GPU，但训练可能仍然很慢。这种情况下最简单的策略是数据并行：我们把相同的训练设置复制到分开的 GPU 上，给每块 GPU 传不同的批次。这样你可以并行化模型的前向/反向传播，并随 GPU 数量扩展。

[![chapter10_ddp.png](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/chapter10_ddp.png)](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/chapter10_ddp.png)

我们要么用 `transformers.Trainer`，要么用 `accelerate`，二者都支持无需任何代码改动的数据并行，只需用 `torchrun` 或 `accelerate launch` 调用脚本时传入参数即可。下面分别在单台机器上用 8 块 GPU 以 `accelerate` 和 `torchrun` 运行一个训练脚本。

```
accelerate launch --multi_gpu --num_machines 1  --num_processes 8 my_accelerate_script.py
torchrun --nnodes 1  --nproc_per_node 8 my_torch_script.py
```

## 监督微调

在我们开始训练奖励模型、并用 RL 调优模型之前，如果模型在我们感兴趣的领域已经不错，会很有帮助。在我们的情形里，我们希望它回答问题；对其他用例，我们也许希望它遵循指令，那时指令微调是个好主意。实现这一点的最简单方式，是用语言建模目标在该领域或任务文本上继续训练语言模型。[StackExchange 数据集](https://huggingface.co/datasets/HuggingFaceH4/stack-exchange-preferences) 非常庞大（超过 1000 万条指令），所以我们可以轻松地在它的子集上训练语言模型。

在做 RLHF 之前微调模型没有什么特别的——只是把预训练里的因果语言建模目标施加在这里。为了高效利用数据，我们使用一种叫打包（packing）的技术：不是每个批次样本有一段文本然后填充到最长文本或模型最大上下文，而是把很多文本用 EOS token 连接起来，再切成上下文大小的块来填满批次，完全不填充。

[![chapter10_preprocessing-clm.png](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/chapter10_preprocessing-clm.png)](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/chapter10_preprocessing-clm.png)

用这种方法训练效率高得多，因为经过模型的每个 token 也都被训练，而不像填充 token 那样通常被从损失中掩码掉。如果你数据不多、更担心偶尔截断溢出上下文的 token，也可以用经典的数据加载器。

打包由 `ConstantLengthDataset` 处理，加载模型后用 `peft` 即可使用 `Trainer`。首先我们以 int8 加载模型、为训练做准备，然后加上 LoRA 适配器。

```
# load model in 8bit
model = AutoModelForCausalLM.from_pretrained(
        args.model_path,
        load_in_8bit=True,
        device_map={"": Accelerator().local_process_index}
    )
model = prepare_model_for_int8_training(model)

# add LoRA to model
lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
)

model = get_peft_model(model, lora_config)
```

我们用因果语言建模目标训练模型几千步并保存模型。由于我们会用不同的目标再次调优模型，我们把适配器权重与原始模型权重合并。

**声明：** 由于 LLaMA 的许可证，本模型以及后面各节的模型检查点我们只发布适配器权重。你可以填写 Meta AI 的 [表单](https://docs.google.com/forms/d/e/1FAIpQLSfqNECQnMkycAp2jP4Z9TFX0cGR4uf7b_fBxjY_OjhJILlKGA/viewform) 申请基座模型权重，然后运行这个 [脚本](https://github.com/huggingface/transformers/blob/main/src/transformers/models/llama/convert_llama_weights_to_hf.py) 把它们转成 🤗 Transformers 格式。注意在 `v4.28` 发布之前你还需要从源码安装 🤗 Transformers。

现在我们已经为任务微调了模型，准备好训练一个奖励模型。

## 奖励建模与人类偏好

原则上，我们可以直接用人类标注做 RLHF 来微调模型。然而这要求我们在每次优化迭代之后把一些样本发给人类打分，这既昂贵又慢——考虑到收敛所需的训练样本数量，以及人类阅读和标注速度的固有延迟。

一个比直接反馈更有效的技巧，是在 RL 循环之前用已收集的人类标注训练一个奖励模型。奖励模型的目标是模仿人类会如何给文本打分。构建奖励模型有若干可能策略：最直接的方式是预测标注（例如评分值或"好/坏"的二值）。实践中，更好的是预测两个样例的排序——给定一个提示词 x x x，奖励模型面对两个候选 (yk,yj) (y_k, y_j) (yk​,yj​)，要预测人类标注者会给哪一个更高分。

这可以转化为以下损失函数：

loss⁡(θ)=−E(x,yj,yk)∼D[log⁡(σ(rθ(x,yj)−rθ(x,yk)))] \operatorname{loss}(\theta)=- E_{\left(x, y_j, y_k\right) \sim D}\left[\log \left(\sigma\left(r_\theta\left(x, y_j\right)-r_\theta\left(x, y_k\right)\right)\right)\right] loss(θ)=−E(x,yj​,yk​)∼D​[log(σ(rθ​(x,yj​)−rθ​(x,yk​)))]

其中 r r r 是模型的分数，yj y_j yj​ 是受偏好的候选。

用 StackExchange 数据集，我们可以根据分数推断两个答案中哪个更受用户偏好。有了这个信息和上面定义的损失，我们就可以通过加一个自定义损失函数来修改 `transformers.Trainer`。

```
class RewardTrainer(Trainer):
    def compute_loss(self, model, inputs, return_outputs=False):
        rewards_j = model(input_ids=inputs["input_ids_j"],  attention_mask=inputs["attention_mask_j"])[0]
        rewards_k = model(input_ids=inputs["input_ids_k"], attention_mask=inputs["attention_mask_k"])[0]
        loss = -nn.functional.logsigmoid(rewards_j - rewards_k).mean()
        if return_outputs:
            return loss, {"rewards_j": rewards_j, "rewards_k": rewards_k}
        return loss
```

我们使用一个 10 万对候选的子集，并在保留的 5 万对上评估。以不大的训练批大小 4，我们用 LoRA `peft` 适配器以 Adam 优化器、BF16 精度训练 LLaMA 模型一个 epoch。我们的 LoRA 配置是：

```
peft_config = LoraConfig(
    task_type=TaskType.SEQ_CLS,
    inference_mode=False,
    r=8,
    lora_alpha=32,
    lora_dropout=0.1,
)
```

训练通过 [Weights & Biases](https://wandb.ai/krasul/huggingface/runs/wmd8rvq6?workspace=user-krasul) 记录，在 8 块 A100 GPU 上用 🤗 研究集群跑了几个小时，模型最终达到 **67% 的准确率**。虽然听起来分数不高，但任务也很难，对人类标注者也一样。

如下一节所详述，所得适配器可以合并进冻结模型并保存，用于后续下游使用。

## 人类反馈强化学习

手里有了微调后的语言模型和奖励模型，现在我们准备好运行 RL 循环。它大致遵循三步：

- 从提示词生成响应
- 用奖励模型给响应打分
- 用这些分数运行一个强化学习策略优化步骤

[![Untitled](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/trl_loop.png)](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/trl_loop.png)

问题（Query）和回答（Response）提示在被分词并传给模型之前按如下模板处理：

```
Question: <Query>

Answer: <Response>
```

SFT、RM 和 RLHF 阶段都用了同样的模板。

用 RL 训练语言模型的一个常见问题是，模型可能学会通过生成完全胡言乱语来利用奖励模型，导致奖励模型给出高奖励。为了平衡这一点，我们在奖励上加一个惩罚：我们保留一份不训练的模型参照，并通过计算 KL 散度把新模型的生成与参照进行比较：

R⁡(x,y)=r⁡(x,y)−βKL⁡(x,y) \operatorname{R}(x, y)=\operatorname{r}(x, y)- \beta \operatorname{KL}(x, y) R(x,y)=r(x,y)−βKL(x,y)

其中 r r r 是来自奖励模型的奖励，KL⁡(x,y) \operatorname{KL}(x,y) KL(x,y) 是当前策略与参照模型之间的 KL 散度。

再一次，我们用 `peft` 做内存高效训练，这在 RLHF 语境里带来额外优势。这里参照模型和策略共享同一个基座，即 SFT 模型，我们以 8-bit 加载并在训练期间冻结。我们用 PPO 只优化策略的 LoRA 权重，同时共享基座模型的权重。

```
for epoch, batch in tqdm(enumerate(ppo_trainer.dataloader)):
    question_tensors = batch["input_ids"]
        
    # sample from the policy and generate responses
    response_tensors = ppo_trainer.generate(
        question_tensors,
        return_prompt=False,
        length_sampler=output_length_sampler,
        **generation_kwargs,
    )
    batch["response"] = tokenizer.batch_decode(response_tensors, skip_special_tokens=True)

    # Compute sentiment score
    texts = [q + r for q, r in zip(batch["query"], batch["response"])]
    pipe_outputs = sentiment_pipe(texts, **sent_kwargs)
    rewards = [torch.tensor(output[0]["score"] - script_args.reward_baseline) for output in pipe_outputs]

    # Run PPO step
    stats = ppo_trainer.step(question_tensors, response_tensors, rewards)
    # Log stats to WandB
    ppo_trainer.log_stats(stats, batch, rewards)
```

我们在 3x8 A100-80GB GPU 上用 🤗 研究集群训练 20 小时，但你也能更快拿到还不错的结果（例如在 8 块 A100 GPU 上约 20 小时）。整次训练的所有训练统计都可在 [Weights & Biases](https://wandb.ai/lvwerra/trl/runs/ie2h4q8p) 上查看。

[![Per batch reward at each step during training. The model’s performance plateaus after around 1000 steps.](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/wandb_reward.png)](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/wandb_reward.png) *训练期间每一步每个批次的奖励。模型表现在约 1000 步后趋于平稳。*

## 挑战、不稳定与权宜之计

用 RL 训练 LLM 并非一帆风顺。我们今天演示的模型是大量实验、失败运行和超参扫描的结果。即便如此，模型也远非完美。这里我们分享在做出这个示例过程中遇到的一些观察和头疼之处。

### 奖励越高意味着表现越好，对吧？

[![Wow this run must be great, look at that sweet, sweet, reward!](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/logs_high_reward.png)](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/logs_high_reward.png) *哇这次运行一定很棒，看看那美美的奖励！*

在 RL 里通常你希望拿到最高奖励。在 RLHF 里我们用一个不完美的奖励模型，一旦有机会，PPO 算法就会利用这些不完美。这表现为奖励的突然上升，然而当我们看策略生成的文本，它们大多是 ``` 字符串的重复，因为奖励模型发现含代码块的 Stack Exchange 答案通常比不含的排名更高。所幸这个问题观察到得相当少，而总体上 KL 惩罚应当能抵消这类利用。

### KL 不总是正值吗？

正如我们前面所说，使用 KL 惩罚项是为了把模型输出推得更接近基策略的输出。一般而言，KL 散度衡量两个分布之间的距离，永远是一个正量。然而在 `trl` 里我们用一个 KL 估计，其期望等于真实的 KL 散度。

KLpen(x,y)=log⁡(πϕRL(y∣x)/πSFT(y∣x)) KL_{pen}(x,y) = \log \left(\pi_\phi^{\mathrm{RL}}(y \mid x) / \pi^{\mathrm{SFT}}(y \mid x)\right) KLpen​(x,y)=log(πϕRL​(y∣x)/πSFT(y∣x))

显然，当从策略采样的某个 token 比 SFT 模型的概率低时，会导致负的 KL 惩罚，但平均而言它会为正，否则你就没有正确地按策略采样。然而一些生成策略会强制某些 token 被生成，或抑制某些 token。例如批量生成时已完成的序列会被填充，而设置最小长度时 EOS token 会被抑制。模型会给这些 token 分配很高或很低的概率，从而导致负的 KL。由于 PPO 算法优化奖励，它会追逐这些负惩罚，导致不稳定。

[![Negative KL](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/logs_neg_kl.png)](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/logs_neg_kl.png)

在生成响应时要当心，我们建议总是先使用一个简单的采样策略，再诉诸更复杂的生成方法。

### 尚存的问题

仍有一些问题需要我们更好地理解并解决。例如，损失偶尔会出现尖峰，可能引发进一步的不稳定。

[![Loss spikes](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/logs_loss_spikes.png)](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/blog/stackllama/logs_loss_spikes.png)

随着我们发现并解决这些问题，我们会把改动贡献到 `trl`，确保社区能受益。

## 结论

在这篇博客里，我们走完了 RLHF 的整个训练循环，从准备一份带人类标注的数据集开始，把语言模型适配到领域、训练一个奖励模型，最后用 RL 训练一个模型。

通过用 `peft`，任何人都能在单块 GPU 上跑我们的示例！如果训练太慢，你可以无需改代码地使用数据并行，并通过加更多 GPU 来扩展训练。

对一个真实用例来说，这只是第一步！一旦有了训练好的模型，你必须评估它并与其他模型比较，看它有多好。可以通过给不同模型版本的生成做排序来实现，类似我们构建奖励数据集的方式。

加上评估步骤之后，乐趣就开始了：你可以开始迭代你的数据集和模型训练设置，看看有没有办法改进模型。你可以往混合里加其他数据集，或对现有数据集应用更好的过滤器。另一方面，你可以尝试不同的模型尺寸和奖励模型架构，或训练更久。

我们在积极改进 TRL，让 RLHF 涉及的每一步都更易用，并对大家用它造出的东西感到兴奋！如果你有兴趣贡献，看看 [GitHub 上的 issues](https://github.com/lvwerra/trl/issues)。
