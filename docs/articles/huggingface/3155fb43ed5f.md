# 迈向 100 万 Gradio 用户的旅程！

5 年前，我们把 Gradio 作为一个简单的 Python 库发布，让 Stanford 的研究员能用 Web 界面轻松演示计算机视觉模型。

今天，每月有超过 100 万开发者用 Gradio 构建和分享 AI Web 应用。其中包括一些史上最受欢迎的开源项目，比如 [Automatic1111](https://github.com/AUTOMATIC1111/stable-diffusion-webui)、[Oobabooga 的 Text Generation WebUI](https://github.com/oobabooga/text-generation-webui)、[Dall-E Mini](https://huggingface.co/spaces/dalle-mini/dalle-mini) 和 [LLaMA-Factory](https://huggingface.co/spaces/hiyouga/LLaMA-Board)。

[![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/gradio-guides/maus.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/gradio-guides/maus.png)

我们是怎么走到今天的？在竞争如此激烈的开源 Python 库领域，Gradio 凭什么持续增长？正在做自己开源库的朋友经常问我这个问题。这篇文章提炼了我过去几年学到的一些经验：

- 投资好的基础构件（primitives），而不是高层抽象
- 把传播性直接嵌进你的库
- 聚焦一个（在增长的）细分领域
- 你唯一的路线图就应该是快速迭代
- 让用户消费你库产出的方式最大化

**1. 投资好的基础构件，而不是高层抽象**

Gradio 刚发布时，我们只提供一个高层类（`gr.Interface`），用一个 Python 函数就能生成完整的 Web 应用。我们很快意识到开发者想构建其他类型的应用（比如多步工作流、聊天机器人、流式应用），但当我们把用户想建的应用列出来时，我们明白了该做什么：往底层走。

我们没有针对不同用例建许多高层类，而是构建了一个叫 Gradio Blocks 的低层 API，让用户用组件、事件和布局这些模块化部件来拼装应用。尽管通常写起来更费劲，但 `gr.Blocks` 如今占 Gradio 用量的 80%——包括上面提到的那些超人气应用。

团队规模小，专注低层抽象就意味着我们不可能去追很多诱人的高层抽象。但这种专注让我们避开了两个常见坑：

- **定制化-维护陷阱**：高层抽象好用，但用户会要求额外参数来定制它们，而这反过来加重维护负担——每个抽象和参数都要实现、维护、测试才能避免 bug。
- **生产力幻觉**：用高层抽象看起来活儿更少，直到用户需要某个不被支持的功能（这在项目初期很难预测），逼着开发者做昂贵的重写。

第一个问题浪费的是*我们维护者的时间*，第二个问题浪费的是*用户的时间*。直到今天，Gradio 也只包含两个高层抽象（`gr.Interface` 和 `gr.ChatInterface`），而它们本身就是用 Blocks 构建的。

在 AI 辅助编程的时代，好 primitives 的优势更加明显——我们发现 LLM 通常很擅长通读文档、用基础构件搭出复杂应用（看看用 `three.js` 做的那么多游戏就知道了）。低层代码让 AI 替你写，并不会多花多少时间。

**2. 聚焦一个（在增长的）细分领域**

你的库最好的代言不是你自己，而是一个热情的用户。由此推论，你应该想办法让用户在工作流中分享你的库或它的产物。Gradio 的早期增长得益于我们的「share link」功能——一行代码就能为你的 Gradio 应用创建一个临时公开链接。Gradio 用户不用再操心打包，也不用操心把代码部署到有合适算力的 Web 服务器上，立刻就能把应用分享给同事。

加入 Hugging Face 之后，我们还受益于成为 Hugging Face Spaces 的标准 UI——机器学习研究社区广泛使用它。最火的 Spaces 吸引了数百万访客，让开发者接触到 Gradio，他们进而分享并构建自己的 Gradio 应用，并把这些 Spaces 公开的代码当作学习 Gradio 用法的资源。

**3. 为一个（在增长的）细分用例构建**

早期我们面临一个关键抉择：Gradio 应该做一个通用 Python Web 框架，还是专注构建机器学习 Web 应用？我们选了后者，这带来了一切不同。

在拥挤的 Python Web 库生态里，人们经常问我们「Gradio 和 X 有什么区别？」我们简洁的回答是——Gradio 为机器学习 Web 应用做了优化——既好记又本质准确。每个 Gradio 应用都自带特别适合 ML 工作流的功能，比如内置队列，能高效管理长时间运行的 ML 任务，即使有数千并发用户。我们设计的组件专门针对 ML 用例打磨。反过来说，有很长时间 Gradio 连链接按钮这样的功能都没有，只因为核心用户根本不需要。通过收窄焦点，Gradio 很快成了机器学习开发者的默认选择——「AI 的默认 UI」。

当然，选一个本身在增长的细分领域让我们受益匪浅。近来推动一切 AI 相关事物的顺风对我们帮助巨大；如果我们聚焦的是数据科学或仪表盘之类的方向，大概率不会有同样的增长。

**4. 你唯一的路线图应该是快速迭代**

和一些库不同，Gradio 不发布路线图。我们跟踪机器学习领域的新趋势，然后对应地行动。在开源软件里——尤其是 AI——根据社区需求发布功能（并弃用不再需要的功能）是持续增长的关键。举个具体例子：Gradio 早期版本我们为开发者提供了展示机器学习模型「解释（interpretation）」的专门功能——那是 2020-21 年前后很热门的用法。随着大家对解释的兴趣降温，我们把它弃用，把精力全部投入到音视频流式和聊天相关功能上。

我们的内部流程同样是去中心化的。Gradio 团队的 11 位工程师和开发者布道师都被鼓励去发现有影响力的点子、快速做原型、通过 GitHub、Hugging Face 和社交媒体直接与开源社区互动。每位成员把点子带回团队，我们持续围绕「哪些想法可能有影响力」建立和重建共识，并把资源集中到最有影响力的方向上继续增长。

**5. 让用户消费库产出的方式最大化**

当你创建了一个 Gradio 应用并 `launch()` 它时，你会在浏览器里得到一个运行中的 Web 应用。但这不是全部——你还得到每个 Python 函数的 API 端点，以及每个端点自动生成的文档。这些端点可以通过我们团队构建的 Python 或 JavaScript 客户端来调用，也可以直接用 cURL。

我们这么做的原因，是希望开发者花在 Gradio 上的每一分钟都尽可能有用。一个 Gradio 应用应该能在本地运行，也能不改任何代码就部署到 Hugging Face Spaces 或你自己的服务器上，或程序化地集成进更大的应用，甚至通过 MCP 被 AI 智能体调用（这点很快详谈！）。通过专注最大化可用性，我们希望开发者能不断从 Gradio 库里获得更多。

**向 1000 万进发！**
