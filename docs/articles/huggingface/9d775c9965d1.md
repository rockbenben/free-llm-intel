你是否厌倦了管理多个 AI 模型的复杂与昂贵？**如果一次部署就能服务 30 个模型呢？**在当下的机器学习世界里，想要释放数据价值的组织多半会走向一个*微调化的世界*：构建一大堆模型，每个都为特定任务高度定制。但你要如何应对为每个用例各部署一个模型的麻烦和成本？答案就是 Multi-LoRA 服务（Multi-LoRA serving）。

## 动机

对组织而言，通过微调构建大量模型有很多合理的理由。

- **性能 -** 有[有力证据](https://huggingface.co/papers/2405.09673)表明，在其训练的目标任务上，小型专用模型胜过更大的通用模型。Predibase [[5]](https://huggingface.co/blog/multi-lora-serving#5) 展示了以 [mistralai/Mistral-7B-v0.1](https://huggingface.co/mistralai/Mistral-7B-v0.1/tree/main) 为基座、配合任务专用 LoRA，性能可以超过 GPT-4。
- **适应性 -** Mistral、Llama 这类模型极其多才多艺。你可以选一个作为基座模型，构建许多专用模型，即使[下游任务差异很大](https://predibase.com/blog/lora-land-fine-tuned-open-source-llms-that-outperform-gpt-4)也不例外。另外注意你不会被锁死——可以随时更换基座，用自己的数据在别的基座上重新微调（后面详述）。
- **独立性 -** 对组织关心的每个任务，不同团队可以各自负责不同的微调版本，从而在数据准备、配置、评估标准和模型更新节奏上都保持独立。
- **隐私 -** 专用模型在训练数据隔离和按数据隐私要求对不同用户做访问限制方面更灵活。此外，在需要本地运行模型的场合，小模型也能为特定任务做到很强，同时保持足够小的体积以在设备上运行。

总之，微调让组织能够释放数据价值；而当组织使用独属于自己的高度专业化数据时，这一优势会变得格外显著，甚至具有颠覆性。

那么，坑在哪里？部署和服务大语言模型（LLM）在许多方面都有挑战。部署单个模型时，成本和运维复杂度已经是关键考量，更不用说 *n* 个模型。这意味着尽管微调光环闪耀，它却让 LLM 的部署和服务难上加难。

这就是为什么今天我们超级兴奋地推出 TGI 的最新特性——**Multi-LoRA 服务**。

## LoRA 背景

LoRA 即 [Low-Rank Adaptation（低秩适配）](https://huggingface.co/papers/2106.09685)，是一种高效微调大型预训练模型的技术。核心思想是：把大型预训练模型适配到具体任务时不必重训整个模型，只需训练一小套称为适配器（adapter）的参数。相比预训练 LLM 的体积，这些适配器通常只增加约 1% 的存储和内存开销，同时保持与全量微调模型相当的质量。

LoRA 的好处显而易见：降低内存需求，让微调便宜得多。它还[减轻灾难性遗忘](https://huggingface.co/papers/2405.09673)，并且更适应[小数据集](https://huggingface.co/blog/peft)。

## Multi-LoRA 服务

理解了 LoRA 提出的模型适配基本思想后，我们可以深入 Multi-LoRA 服务了。概念很简单：给定一个预训练基座模型和你已经为其微调了不同 LoRA 的多个任务，Multi-LoRA 服务就是根据进来的请求动态选择所需 LoRA 的机制。

*图 2* 展示了这种动态适配如何工作。每个用户请求除了输入 `x` 之外，还带与该请求对应的 LoRA id（我们把这称为异构请求批）。任务信息使 TGI 能够挑选正确的 LoRA 适配器。

Multi-LoRA 服务让你只需部署一次基座模型。由于 LoRA 适配器很小，你可以加载很多个。具体能加载多少取决于你的 GPU 资源和所部署的模型。其效果实际上等同于在单个部署中拥有多个微调模型。

LoRA（适配器权重）会因秩和量化不同而大小不一，但总体都非常小。快速感受一下这些小适配器有多小：[predibase/magicoder](https://huggingface.co/predibase/magicoder/tree/main) 只有 13.6MB，还不到 [mistralai/Mistral-7B-v0.1](https://huggingface.co/mistralai/Mistral-7B-v0.1/tree/main)（14.48GB）的千分之一。相对地，把 30 个适配器加载进内存也只让 VRAM 增加 3%。对大多数部署来说这根本不算问题。因此，一次部署就能服务很多模型。

# 如何使用

## 收集 LoRA

首先，你需要训练自己的 LoRA 模型并导出适配器。微调 LoRA 适配器的[指南在这里](https://huggingface.co/docs/peft/en/task_guides/lora_based_methods)。注意，把微调模型推到 Hub 时，你只需要推适配器，而不需要推完整的合并模型。从 Hub 加载 LoRA 适配器时，基座模型会从适配器的模型卡推断出来并另行加载。需要更深入的支持，请了解我们的 [Expert Support Program](https://huggingface.co/support)。真正的价值来自你为自己的具体用例创建自己的 LoRA。

### 低代码团队

对某些组织来说，为每个用例训练一个 LoRA 可能很难，因为它们可能缺乏专门技术或其他资源。即使选定了基座、准备好了数据，你还需要跟进最新技术、探索超参数、寻找最优硬件资源、写代码、然后做评估。即使对经验丰富的团队，这也是一件不小的工程。

AutoTrain 能大幅降低这一门槛。AutoTrain 是一套无代码方案，只需几次点击就能训练机器学习模型。使用 AutoTrain 有好几种途径。除了[本地/私有部署](https://github.com/huggingface/autotrain-advanced?tab=readme-ov-file#local-installation)，还有：

| AutoTrain 环境 | 硬件细节 | 代码要求 | 备注 |
| --- | --- | --- | --- |
| [Hugging Face Space](https://huggingface.co/login?next=%2Fspaces%2Fautotrain-projects%2Fautotrain-advanced%3Fduplicate%3Dtrue) | 多种 GPU 和硬件 | 无代码 | 灵活且易于共享 |
| [DGX cloud](https://huggingface.co/blog/train-dgx-cloud) | 最高 8xH100 GPU | 无代码 | 更适合大型模型 |
| [Google Colab](https://colab.research.google.com/github/huggingface/autotrain-advanced/blob/main/colabs/AutoTrain.ipynb) | 可使用一块 T4 GPU | 少量代码 | 适合小负载和量化模型 |

## 部署

我们的示例将使用 [Predibase 的 LoRA Land](https://predibase.com/blog/lora-land-fine-tuned-open-source-llms-that-outperform-gpt-4) 中两个出色的适配器：

- [predibase/customer_support](https://huggingface.co/predibase/customer_support) 在 [Gridspace-Stanford Harper Valley 语音数据集](https://github.com/cricketclub/gridspace-stanford-harper-valley)上训练，增强了准确理解和回应客服交互的能力。这提升了模型在语音识别、情绪检测、对话管理等任务上的表现，让客服更高效也更有人情味。
- [predibase/magicoder](https://huggingface.co/predibase/magicoder) 在 [ise-uiuc/Magicoder-OSS-Instruct-75K](https://huggingface.co/datasets/ise-uiuc/Magicoder-OSS-Instruct-75K) 上训练，这是一个合成生成的代码指令数据集。

### TGI

关于[如何部署 TGI](https://github.com/huggingface/text-generation-inference)已经有很多很好的资料。按常规方式部署即可，但请确保：

- 使用大于等于 `v2.1.1` 的 TGI 版本
- 部署你的基座：`mistralai/Mistral-7B-v0.1`
- 部署时添加 `LORA_ADAPTERS` 环境变量 示例：`LORA_ADAPTERS=predibase/customer_support,predibase/magicoder`

```
model=mistralai/Mistral-7B-v0.1
# share a volume with the Docker container to avoid downloading weights every run
volume=$PWD/data

docker run --gpus all --shm-size 1g -p 8080:80 -v $volume:/data \
    ghcr.io/huggingface/text-generation-inference:2.1.1 \
    --model-id $model \
    --lora-adapters=predibase/customer_support,predibase/magicoder
```

### Inference Endpoints 图形界面

[Inference Endpoints](https://huggingface.co/docs/inference-endpoints/en/index) 让你在几次点击之内，把任意 Hugging Face 模型部署到 AWS、GCP、Azure 上的[多种 GPU 及替代硬件类型](https://huggingface.co/docs/inference-endpoints/en/pricing#gpu-instances)。在 GUI 中部署很简单。底层默认使用 TGI 做文本生成（不过你[可以](https://huggingface.co/docs/inference-endpoints/en/guides/custom_container)选择任意镜像）。

要在 Inference Endpoints 上使用 Multi-LoRA 服务，只需进入你的[控制台](https://ui.endpoints.huggingface.co/)，然后：

- 选择基座模型：`mistralai/Mistral-7B-v0.1`
- 选择你的 `Cloud` | `Region` | `HW` 我用 `AWS` | `us-east-1` | `Nvidia L4`
- 选择 Advanced Configuration（高级配置） 你会看到已选中 `text generation` 其余按需配置即可
- 在环境变量中添加 `LORA_ADAPTERS=predibase/customer_support,predibase/magicoder`
- 最后 `Create Endpoint`！

这是最低配置，其他设置你可以按需要自行配置。

### Inference Endpoints 代码

也许你们当中有人[惧鼠症](https://en.wikipedia.org/wiki/Fear_of_mice_and_rats)（大概也怕用鼠标），不想用鼠标——我们不评判。用代码自动化这一切也很简单，只用键盘就好。

```
from huggingface_hub import create_inference_endpoint

# Custom Docker image details
custom_image = {
    "health_route": "/health",
    "url": "ghcr.io/huggingface/text-generation-inference:2.1.1",  # This is the min version
    "env": {
        "LORA_ADAPTERS": "predibase/customer_support,predibase/magicoder",  # Add adapters here
        "MAX_BATCH_PREFILL_TOKENS": "2048",  # Set according to your needs
        "MAX_INPUT_LENGTH": "1024", # Set according to your needs
        "MAX_TOTAL_TOKENS": "1512", # Set according to your needs
        "MODEL_ID": "/repository"
    }
}

# Creating the inference endpoint
endpoint = create_inference_endpoint(
    name="mistral-7b-multi-lora",
    repository="mistralai/Mistral-7B-v0.1",
    framework="pytorch",
    accelerator="gpu",
    instance_size="x1",
    instance_type="nvidia-l4",
    region="us-east-1",
    vendor="aws",
    min_replica=1,
    max_replica=1,
    task="text-generation",
    custom_image=custom_image,
)
endpoint.wait()

print("Your model is ready to use!")
```

这个配置大约花了 3 分 40 秒完成部署。注意模型更多时耗时会更长。如果加载时间遇到问题，欢迎提 [github issue](https://github.com/huggingface/text-generation-inference/issues)！

## 调用

调用端点时，你需要指定 `adapter_id`。这里是一个 cURL 示例：

```
curl 127.0.0.1:3000/generate \
    -X POST \
    -H 'Content-Type: application/json' \
    -d '{
  "inputs": "Hello who are you?",
  "parameters": {
    "max_new_tokens": 40,
    "adapter_id": "predibase/customer_support"
  }
}'
```

或者，也可以用出色的 [Hugging Face Hub Python 库](https://huggingface.co/docs/huggingface_hub/index)中的 [InferenceClient](https://huggingface.co/docs/huggingface_hub/guides/inference)：

```
from huggingface_hub import InferenceClient

tgi_deployment = "127.0.0.1:3000"
client = InferenceClient(tgi_deployment)
response = client.text_generation(
    prompt="Hello who are you?",
    max_new_tokens=40,
    adapter_id='predibase/customer_support',
)
```

## 实践考量

### 成本

爬这座山的不止我们一家，正如[下文](https://huggingface.co/blog/multi-lora-serving#Acknowledgements)所述。LoRAX 背后的团队 Predibase 有一篇很棒的[文章](https://predibase.com/blog/lorax-the-open-source-framework-for-serving-100s-of-fine-tuned-llms-in)。一定要看看，本节正是基于他们的工作。

| --- |
| *图 5：Multi-LoRA 成本* 对于 TGI，我以 nvidia-l4 部署了 [mistralai/Mistral-7B-v0.1](https://huggingface.co/mistralai/Mistral-7B-v0.1) 作为基座，在 [Inference Endpoints](https://huggingface.co/docs/inference-endpoints/en/index) 上的[成本](https://huggingface.co/docs/inference-endpoints/en/pricing#gpu-instances)为 $0.8/小时。我在平均 450 个输入词元、234 个输出词元的条件下达到了 75 请求/秒，并据此对 GPT3.5 Turbo 做了相应调整。 |

Multi-LoRA 服务的最大好处之一是**多个模型不需要多个部署**，最终这会便宜得多。这应该符合你的直觉：多个模型意味着需要全部权重，而不只是小小的适配层。如*图 5* 所示，即使用 TGI Multi-LoRA 加入更多模型，每 token 的成本也不变；而 TGI 独立部署的成本会随着每个微调模型都需要一个新部署而水涨船高。

部署多个模型时的一个现实挑战，是使用模式差异巨大。有些模型用量很低；有些是脉冲式的；还有些是高频的。这让扩展变得非常困难，尤其当每个模型各自独立时。每次"不得不再加一块 GPU"带来的取整误差会迅速累积。理想情况下，你会把每块 GPU 的利用率拉满且不多用一块，同时还要确保备有足够的 GPU——明知其中一些会闲置，这相当麻烦。

用 Multi-LoRA 合并之后，用量会稳定得多。*图 6* 的结果可以说明这一点：尽管由更易波动的模式组成，Multi-Lora Serving 模式依然相当平稳。把模型合并起来，让用量更平滑、扩展更好管理。注意这些只是示意性的模式——请认真思考你自己的模式，以及 Multi-LoRA 能如何帮到你。扩展 1 个模型，而不是 30 个！

## 更换基座模型

在 AI 以狂飙速度演进的现实世界里，如果你想要选择一个不同的/更新的模型作基座怎么办？虽然我们的示例用 [mistralai/Mistral-7B-v0.1](https://huggingface.co/mistralai/Mistral-7B-v0.1) 作为基座模型，但还有其他选择，比如 Mistral 的 [v0.3](https://ubiops.com/function-calling-deploy-the-mistral-7b-v03/) 支持[函数调用](https://ubiops.com/function-calling-deploy-the-mistral-7b-v03/)，以及完全不同的模型家族如 Llama 3。总体而言，更高效、性能更强的新基座模型会持续涌现。

不过别担心！如果你有*充分的理由*更新基座模型，重新训练 LoRA 并不算难。训练相对便宜——实际上 [Predibase 发现](https://predibase.com/blog/lora-land-fine-tuned-open-source-llms-that-outperform-gpt-4)训练每个 LoRA 只需约 $8.00。借助现代框架和常见工程实践，所需代码改动极小：

- 保存训练模型所用的 notebook/代码
- 对数据集做版本管理
- 记录使用的配置
- 用新的模型/设置更新

## 结论

Multi-LoRA 服务代表着 AI 模型部署的一种变革性思路，为管理多个专用模型相关的成本与复杂度难题提供了解决方案。通过利用单一基座模型并动态应用微调适配器，组织可以大幅降低运维开销，同时在多样任务上保持甚至提升性能。**AI 负责人们，我们请你们大胆一些，选一个基座模型、拥抱 Multi-LoRA 范式**，简单与省钱终将带来超额回报。让 Multi-LoRA 成为你 AI 战略的基石，确保你的组织在瞬息万变的技术格局中保持领先。
