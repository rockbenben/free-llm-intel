# Hugging Face 模型页面新增 Every Eval Ever 结果展示

Every Eval Ever（EEE）和 Hugging Face Community Evals 现在已实现互操作。我们支持评测结果的跨平台发布与解读，并把它们与开放模型、排行榜以及统一的标准化元数据存储连接起来。

EEE 于 2026 年 2 月[上线](https://evalevalai.com/infrastructure/2026-02-17/everyevalever-launch/)，是 [EvalEval 联盟](https://evalevalai.com/)的项目——这是首个跨机构合作项目，旨在改进第一方和第三方评测者报告 AI 评测结果的方式。Hugging Face 也在 2026 年 2 月推出了 [Community Evals](https://huggingface.co/blog/community-evals)，让 Hub 上的基准分数报告走向去中心化。两者结合，补上了用户、研究者与政策制定者在信任、理解和选择评测与模型方面的缺口。

评测结果是我们衡量模型能力、相互比较模型、并推理安全与治理问题的依据，但它们却四处散落、难以比较。它们存在于论文、排行榜、博客文章、评测框架（harness）日志等地方，各有各的格式。同一个模型在同一个基准上，往往因为「谁跑的、怎么跑的」不同而给出不同分数：仅 LLaMA 65B 一项，[MMLU](https://huggingface.co/blog/open-llm-leaderboard-mmlu) 上就出现过 63.7 和 48.8 两个版本。这些差距可能来自[我们发现的评测设置普遍未被报告](https://huggingface.co/papers/2606.14516)的问题。

对于报告这一侧，EEE 是我们的解法。它是一个描述评测结果的 JSON schema，记录：

- 谁跑的
- 哪个模型
- 以什么方式访问模型
- 生成设置
- 指标的真正含义
- [推荐] 记录逐样本输出的配套 JSONL 文件

这个 schema 在研究者和政策研究者的反馈下建成，能接收任何来源的结果，所以评测框架日志、排行榜抓取和论文数字最终都会被统一成同一种形态。[GitHub 仓库](https://github.com/evaleval/every_eval_ever)里有转换器、示例和贡献者指南。自上线以来，Hugging Face 上的[数据存储](https://huggingface.co/datasets/evaleval/EEE_datastore)已增长到约 229,000 条评测结果，覆盖 22,000 多个模型和 2,200 多个基准，来自 31 种不同的报告格式。仅仅把这些跑测从零重现一遍就要花数十万美元——所以既然有人付钱生成了数据，就别让它散落各处，这个理由足够充分。

想了解 schema 详情和贡献方式，见[这里](https://evalevalai.com/infrastructure/2026-02-17/everyevalever-launch/)。

现在，它带来了更好的集成与署名。贡献者可以把 EEE 结果发送到 Hugging Face Community Evals。我们构建了一个转换器，把你的 EEE 记录写成 Hugging Face 需要的小型 YAML 文件，你就不用手动把同一份结果维护成两种格式了。

[![Verified Evaluators on Eval Cards](https://cdn-uploads.huggingface.co/production/uploads/6413251362e6057cbb6259bd/czIJDDShvtMBs2M2T7B45.gif)](https://cdn-uploads.huggingface.co/production/uploads/6413251362e6057cbb6259bd/czIJDDShvtMBs2M2T7B45.gif)

这是面向所有报告或阅读评测的人的新功能，不只服务现有 EEE 贡献者。报告自家模型的第一方评测者，以及报告他人模型的第三方评测者，都可以同时向 Community Evals 和 EEE 提交；而所有浏览 Hub 的人都能拿到可以追溯到完整记录的结果。当你通过所在组织的官方 Hugging Face 账户提交数据时，你的结果在 EvalEval 上会带有一个[已验证](https://evalcards.evalevalai.com/help/get-verified)的对勾，向读者表明数字直接来自源头。本文其余部分会介绍 Community Evals 是什么、转换器做了什么。

## Hugging Face Community Evals 如何与 EvalEval 协作

Hugging Face Community Evals 有两侧。

基准存放在一个数据集仓库里，通过添加一个 `eval.yaml` 完成注册。注册之后，该数据集页面会收集并展示整个 Hub 上针对它报告的每一个分数构成的排行榜。[官方基准](https://huggingface.co/datasets?benchmark=benchmark:official&sort=trending)列表会随时间不断扩充。

模型的分数存放在模型仓库内的 `.eval_results/*.yaml` 中。它们会显示在模型卡片上，并汇入对应的基准排行榜。模型作者自己的结果和其他人通过 pull request 提交的结果都会被聚合，每个分数都带有徽章，说明它是作者提交、社区提交还是独立验证过的。任何人都可以通过提交带正确 YAML 文件的 PR 给任何模型添加分数；模型作者可以在自己的仓库里关闭 PR 或隐藏结果。

这是其中一个排行榜的样子：

*Hub 上 [Humanity's Last Exam](https://huggingface.co/datasets/cais/hle) 的 Community Evals 排行榜*

这正是 EEE 与 Community Evals 的衔接之处。当你把结果同时发给两边时会发生两件事：第一，你的分数出现在 Hugging Face 模型页面上，并被吸入该基准的排行榜。第二，它带有一个来源徽章，直接链回完整的 EEE 记录——那里有生成配置、评测框架版本、可复现性说明以及实例级数据。

[![EvalEval as source on SmolLM2 Model Page](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/eee_commevals/smollm2.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/eee_commevals/smollm2.png)

*来自 EEE 数据存储的评测（MMLU-Pro）(a) 在文件级别与 Hugging Face 模型卡片 (b) 交叉链接。EvalEval 来源徽章链向完整的 JSON 记录。*

**两个去向为同一个目标承担不同的工作。Hugging Face 把你的结果放到人们看模型的地方，并留下指回来源的链接。EEE 保存让结果可被解读的完整结构化记录，并在此基础上支撑 [Eval Cards](https://evalevalai.com/projects/eval-cards/)。** 把数据同时发到两边，同一次评测就能既可见又可读——这本就是报告评测的意义所在。

## 工作原理

Hugging Face 把评测分数以 YAML 形式存放在模型仓库的 `.eval_results/` 下。必填字段只有基准数据集、任务（task）和值（value）。source 块是生成指回 EEE 反向链接的部分。

```
- dataset:
    id: openai/gsm8k
    task_id: gsm8k
  value: 96.8
  date: '2024-07-16'
  notes: '8-shot CoT'
  source:
    url: https://huggingface.co/datasets/evaleval/EEE_datastore/blob/main/flat/objects/<xx>/<yy>/<uuid>.json
    name: EvalEval
```

**转换器会根据你已有的记录自动填好这些。** 它把 `source_data.hf_repo` 映射到 `dataset.id`，`evaluation_name` 映射到 `task_id`，`score_details.score` 映射到 `value`，`evaluation_timestamp` 映射到 `date`，然后把数据存储对象 URL 放进 source，指向逐条记录的 EEE JSON。它目前支持四个官方基准：MMLU-Pro、GPQA、HLE 和 GSM8K。

**转换器做的不只是改字段形状。** 你指定一个 EEE 数据存储集合，它会下载该集合并顺带下载其引用的记录，校验对象哈希，然后找出映射到受支持基准的分数。在真正写入之前它会先审计已有内容：读取模型 main 分支和未合并 PR 里的每个 `.eval_results` YAML，按数据集和任务而不是文件名来比对。如果分数已存在就标记 `already_present`；如果存在的是不同的分数就标记为 `score_conflict`；如果模型仓库在 Hub 上找不到就标记 `missing_hf_model`。其余全部标记为 `ready`。

**未经你确认，什么都不会推送。** 工具会在本地写出 YAML 预览和供你检查的评审文件，生成一份「哪些就绪、哪些需要处理」的报告，只有当你输入 `OPEN PRS` 并填写提交信息后才会真正开 PR。重跑时会使用集合的缓存结果，除非你传 `--force`。

[![TUI of the Converter](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/eee_commevals/terminal%20shot.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/eee_commevals/terminal%20shot.png)

*转换器的评审步骤。被排除的条目（这里是 Hub 上找不到对应仓库的模型）会连同其 EEE 来源 URL 列出，而就绪的 PR 等待你显式输入 OPEN PRS 确认。*

## 从这里开始

把你的完整记录提交到 [EEE 数据存储](https://huggingface.co/datasets/evaleval/EEE_datastore)。

采用 EEE 只需要多一步，而且转换器已基本把它自动化。[community eval 转换工具](https://github.com/evaleval/every_eval_ever/blob/main/every_eval_ever/tools/hf_community_evals.py)可以在 GitHub 仓库找到。要处理一个集合，执行：

```
uv run tools/hf-community-evals/community_evals_converter.py MMLU-Pro \
  --datastore evaleval/EEE_datastore@main
```

检查预览和生成的报告，准备好后输入 `OPEN PRS` 提交。schema、CLI 和转换器的完整文档在 [evalevalai.com/every_eval_ever/hf-community-evals](https://evalevalai.com/every_eval_ever/hf-community-evals/)。
