2026 年 7 月 30 日，Transformers 为 T5 启用了 PyTorch 的扩展点积注意力 (SDPA)。作为副作用，UMT5 的解码器可能会关注未来的代币。在训练期间，它可以查看它应该预测的答案。没有发生任何崩溃，并且该错误在 main 中停留了近两个月。

当我们后来重放这些提交时，在 CPU 上运行的一个小型 UMT5 模型在每个提交上都标记了它。这篇文章是关于该模型以及围绕它构建的测试的。

## 为什么 bug 会到达 main

[Transformers](https://github.com/huggingface/transformers) 支持超过 750 种模型类型，其测试套件很大：**主线程上有 88,000 多个 CPU 测试，加上每天运行的 200,000 多个 GPU 测试。** 模型测试只是其中的一部分：我们还测试管道、训练、分布式执行、量化和注意力内核。

[！[变形金刚测试：每天对主处理器进行 88,000 多项 CPU 测试，以及 200,000 多项 GPU 测试。硬件包括 CPU、NVIDIA GPU、AMD GPU、Intel XPU 和 Gaudi 3。PR 运行选定的测试。](https://huggingface.co/blog/assets/transformers-mic/ci-test-suite.svg)](https://huggingface.co/blog/assets/transformers-mic/ci-test-suite.svg)

集成测试加载真实的检查点并在真实的硬件上运行模型的 API。在每个 PR 上运行所有这些意味着让大量 GPU 整天忙碌，这是不切实际的。当计划的运行发现回归时，它可能已经在 main 中了。

我们的方法是缩小模型。我们构建一个**夹具**：一个由真实检查点配置制成的小模型，层数更少且更窄，但它拥有的每种层，其标记器和处理器文件保持不变。它发布一次，然后重复使用。我们在廉价的 CPU 运行器上对其运行“快速集成测试”。在我们的 [CPU 研究](https://github.com/huggingface/transformers-mic/blob/main/docs/evidence.md#on-cpu) 中，实验性 UMT5 夹具使用了 66 MB 的权重；源检查点为 1,227 MB。

这还涵盖非常大的模型：有些模型不适合我们的标准 GPU 运行器，但它们的装置在 CPU 上运行。

模型集成商已经构建了微型测试模型（变形金刚的“微型随机*”检查点）。我们想要一个通用的配方，并检查超出加载模型和运行前向传递的范围。 UMT5 bug 可以很好地通过前向传球。

Fixtures 不会取代完整的集成测试，但在 PR 上，它们让我们有机会在 bug 到达 main 之前捕获它们。

## 引入模型集成合约

[transformers-mic](https://github.com/huggingface/transformers-mic) 是打包这些测试的拟议标准。模型集成合约 (MIC) 包含三个部分：

- **固定装置**：上述缩小的模型，发布一次并固定
- **使用路径**：可运行的 Markdown 示例，说明人们使用模型执行的操作，例如生成文本或运行训练步骤
- **基线**：运行该示例时记录的输出，由人工审核

如果在装置上运行使用路径仍然产生基线，则合同成立。

合约涵盖架构和使用路径，而不是单个检查点：兼容的检查点可以共享固定装置，而每个检查点都保留自己的预期结果。我们将它们发布在 [huggingface-mic](https://huggingface.co/huggingface-mic) 中。

例如，SmolLM 合约根据“法国的首都是”等提示生成，并将其代币 ID 与记录的答案进行比较。加载模型和分词器后，生成代码被简化为一个提示：
```
inputs = tokenizer("The capital of France is", return_tensors="pt")
outputs = model.generate(**inputs, max_new_tokens=4, do_sample=False)
new_tokens = outputs[:, inputs["input_ids"].shape[1]:]
print(tokenizer.batch_decode(new_tokens, skip_special_tokens=True))
```
它还比较训练损失，检查梯度是否有限，并验证优化器步骤是否改变了权重。请参阅完整的 [usage.md](https://huggingface.co/huggingface-mic/smollm-mic/blob/main/integrations/transformers/usage.md)。

Hub 上的 [fleet 数据集](https://huggingface.co/datasets/huggingface-mic/transformers-fleet) 将每个 MIC 固定到冻结版本，以及用于记录其基线的软件包版本。每次 CI 运行都会记录它使用的机群修订版本，以便我们稍后可以重现它。

在 PR 中，我们根据补丁更改的文件选择 MIC。

## UMT5 回归

我们重播了五个月以来 Transformers 提交中冻结的 MIC。小型 UMT5 装置标记了从 [2026 年 7 月 30 日](https://github.com/huggingface/transformers/commit/560f36cc561fa154d224b7a6dfcba1d57a621d7b) 推出以来的回归，直到 [9 月] 修复28]（https://github.com/huggingface/transformers/commit/d7ba937671edb174fd80d33f9ecbd38f6559dfca）。标签对数概率与审查的基线相差 1.22，训练损失约为 0.20。

有一个细节很重要：合约使用了 SDPA，即默认的注意力路径。仅运行急切注意变体错过了该错误。固定装置只有在与真实检查点执行相同的代码时才会有帮助。

然后我们恢复了对 Transformers CI 中的一个证明分支的修复。检查失败，但存在同样的差异，所选 T5 合约的运行步骤在 CPU 上花费了 13.4 秒（不包括设置）。

[重播结果](https://github.com/huggingface/transformers-mic/blob/main/docs/evidence.md#shadow-backfill) 和 [CI 演示](https://github.com/huggingface/transformers-mic/blob/main/docs/evidence.md#transformers-ci-proof) 具有测量和再现详细信息。

## 模型如何缩小

第一个秘诀很简单：缩小尺寸并减少层数。对于混合架构来说这还不够。如果都使用滑动注意力并且全注意力层消失，那么保留两层是没有用的。

该配方现在有四个步骤：

- **缩小配置。** 从真实的检查点开始，减少隐藏尺寸、注意力头和深度。保留不同的层类型，包括滑动层和充分注意层或密集层和 MoE 层的混合。某些架构需要额外的规则来保持其组件兼容。我们还查看了模型自己的 Transformers 测试：“test_modeling_<model>.py”中的“ModelTester”已经手动选择了一个小配置，因此我们采用通用规则不知道名称的任何宽度的尺寸。
- **保持预处理不变。** 保留词汇、特殊标记和输入维度，并逐字节复制标记器和处理器文件。加载和预处理是我们想要测试的一部分。
- **构建并验证权重。** 尝试种子随机权重并更改输入以检查模型是否响应。如果没有，请尝试在合同的小批量示例上对其进行训练。重新加载保存的模型并检查输出、损失和梯度是否有限。拒绝失败的构建。
- **冻结并记录。** 保存接受的重量并在已知良好的 Transformers 构建上测量可重复的输出。查看每个支持的平台和精度的基线，然后发布固定快照。 CI 重用它；它不会为每个 PR 重建固定装置。

我们还保留原始权重文件格式。否则，我们将跳过用户加载真实检查点时运行的转换代码。 [完整配方](https://github.com/huggingface/transformers-mic/blob/main/docs/fixtures.md#recipe) 有更多细节。

[Llama 4 Scout 缩小报告](https://huggingface-mic-mic-coverage.static.hf.space/shrink/Llama-4-Scout-17B-16E-Instruct-mic.html) 显示了大模型上的情况。 1086 亿个参数变为 4470 万个。视觉堆栈从 34 层变为 2 层，语言堆栈从 48 层变为 4 层，保留检查的层类型和 MoE 路由样式。

### 与代理一起构建 MIC

我们的 CLI“tmic”创建合约并构建固定装置。对于新模型，LLM起草使用代码和清单，CPU 和 GPU 运行测量候选基线。 LLM草稿；它不同意。改变的期望需要人工审查。

要在您的计算机上尝试它，请使用源检查点代替“org/model”：
```
pip install "transformers-mic[runtime]" "hf-doc-builder @ git+https://github.com/huggingface/doc-builder.git"
hf auth login
tmic run org/model --local-only --fixtures-only --no-history --bill-to ''
```
它起草合同，构建夹具并在您的机器上记录其基线，要求您检查每个步骤，并在上传任何内容之前停止。对于新模型，草稿来自LLM通过推理提供商，记入您自己的帐户（`--bill-to ''`）。 [CLI 文档](https://github.com/huggingface/transformers-mic/blob/main/docs/cli.md#automated-mode) 涵盖了各个步骤。

我们使用代理来跨模型系列构建 MIC。当他们遇到边缘情况时，我们在模型专家的帮助下修复了配方本身，而不是单个固定装置。已发布的模型和剩余的空白位于[覆盖空间](https://huggingface.co/spaces/huggingface-mic/mic-coverage)。

## 随机与过度拟合

在随机权重的情况下，我们的 Whisper 灯具几乎无法响应音频的变化。它运行了，但这使得它成为对音频路径的一个糟糕的测试。

因此，我们用一些与“红色”和“绿色”等单词配对的音调来训练它。我们并没有教它语音识别，只是让音频变化在其输出中可见。在我们的[权重初始化研究](https://github.com/huggingface/transformers-mic/blob/main/docs/fixtures.md#choosing-the-weights)中，随机 Whisper 装置捕获了 24 个注入故障中的 18 个。过拟合的装置捕获了全部 24 个。

这为我们提供了两种构建权重的方法：

- 从随机权重和固定种子开始。
- 在一些例子上过度拟合，例如“法国的首都是”=>“巴黎”。

Whisper 结果并没有决定哪个更好。这些都是综合错误，我们还没有发现仅由过拟合版本捕获的真正回归。两个版本都错过了真正的 Whisper 检查点暴露的辅助解码错误。

因此，当它们通过检查时，我们保留随机权重，当我们需要更好的灵敏度或可读答案时，我们会过度拟合。训练需要几秒钟，但这又是一个可能无法收敛的步骤，也是一件需要维护的事情。 [比较](https://github.com/huggingface/transformers-mic/blob/main/docs/fixtures.md#overfit-versus-random-what-c​​an-we-conclusion) 具有两者的结果。

## 开放式问题

自 2026 年 11 月 1 日起，[Transformers CI 中的 MIC 作业](https://transformers-ci.huggingface.cool/d/mic-failures/mic-failures?from=now-4w&to=now&timezone=browser) 会报告故障，但不会阻止 PR。它是否应该阻塞取决于我们尚未测量的事情：

- 它在 PR 中发现了多少真正的错误，而不仅仅是在重播中？
- 我们多久会遇到一次误报？
- 基线审查需要做多少工作？

我们也不知道有多少错误（例如 Whisper 辅助解码错误）仅在真实权重时出现，也不知道过度拟合是否捕获了随机权重错过的真实错误。

跨模型系列和人们使用的 API 的覆盖范围仍然是部分的。当回归发生时，我们可以添加缺失的使用路径，并在损坏和修复的版本上重放它。我们将保留现有测试，直到考虑到其覆盖范围。

最后，我们希望将原始 Hub 模型页面链接到其 MIC，以便使用检查点的开发人员或代理可以从在该检查点、其环境及其预期输出上测试的示例开始。

想帮忙吗？从[覆盖空间](https://huggingface.co/spaces/huggingface-mic/mic-coverage)中选择一个未覆盖的模型，尝试[tmic工作流程](https://github.com/huggingface/transformers-mic/blob/main/docs/cli.md#automated-mode)，并贡献使用路径或查看生成的合约。
