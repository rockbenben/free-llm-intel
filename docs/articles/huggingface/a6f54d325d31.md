2026 年 7 月 30 日，Transformers 为 T5 启用了 PyTorch 的 scaled dot-product attention（SDPA）。副作用是，UMT5 的 decoder 可以去 attend 未来的 token。训练时，它能偷看自己本该预测的那个答案。什么都没有崩溃，而这个 bug 在 main 上待了将近两个月。

后来我们重放那些 commit 时，一个跑在 CPU 上的小 UMT5 模型在每一个 commit 上都把它标了出来。本文讲的就是那个模型，以及围绕它建起来的那些测试。

## 为什么 bug 能进到 main

[Transformers](https://github.com/huggingface/transformers) 支持超过 750 种模型类型，而它的测试套件非常大：**main 上有 88,000+ 个 CPU 测试，另有每天一次的 200,000+ 个 GPU 测试。** 模型测试只是其中一部分：我们还测试 pipeline、训练、分布式执行、量化和 attention kernel。

[![Transformers 的测试情况：main 上 88,000+ 个 CPU 测试，每天 200,000+ 个 GPU 测试。硬件包括 CPU、NVIDIA GPU、AMD GPU、Intel XPU 和 Gaudi 3。PR 上跑的是筛选出来的测试。](https://huggingface.co/blog/assets/transformers-mic/ci-test-suite.svg)](https://huggingface.co/blog/assets/transformers-mic/ci-test-suite.svg)

集成测试会加载真实的 checkpoint，并在真实硬件上调用模型的 API。如果在每个 PR 上都把这些跑一遍，就意味着要让一大批 GPU 一整天忙个不停，这并不现实。等到排定的那轮跑测发现回归时，它可能已经进了 main。

我们的做法是转而把模型缩小。我们构建一个 **fixture**：一个由真实 checkpoint 的配置做出的小模型，层数更少、每层更窄，但它有的每一种层都保留下来，而它的 tokenizer 和 processor 文件原封不动。它发布一次，然后反复复用。我们在一台便宜的 CPU runner 上对它跑「快速集成测试」。在我们的 [CPU 研究](https://github.com/huggingface/transformers-mic/blob/main/docs/evidence.md#on-cpu)里，实验用的 UMT5 fixture 用了 66 MB 权重；源 checkpoint 是 1,227 MB。

这也覆盖了非常大的模型：有些装不进我们标准的 GPU runner，但它们的 fixture 能跑在 CPU 上。

模型集成者本来就会构建很小的测试模型（Transformers 的 `tiny-random-*` checkpoint）。我们想要的是一份通用的 recipe，以及一些超出「加载模型、跑一次 forward」的检查。UMT5 那个 bug 跑一次 forward 完全能顺利通过。

fixture 不会取代完整的集成测试，但在 PR 上，它们让我们有机会在 bug 进到 main 之前就把它抓住。

## 引入模型集成契约

[transformers-mic](https://github.com/huggingface/transformers-mic) 是一项关于如何打包这些测试的提案标准。一个模型集成契约（Model Integration Contract，MIC）有三部分：

- 一个 **fixture**：上文描述的那个缩小版模型，发布一次并钉住
- 一条 **usage path**：一段可运行的 Markdown 示例，展示人们拿这个模型做什么，比如生成文本或者跑一个训练 step
- **baselines**：运行那段示例时记录下来的输出，经过人工审阅

如果在 fixture 上跑这条 usage path 仍然产出那些 baselines，这份契约就成立。

一份契约覆盖的是一个架构加一条 usage path，而不是某一个 checkpoint：兼容的 checkpoint 可以共享一个 fixture，而各自保留自己的期望结果。我们把它们发布在 [huggingface-mic](https://huggingface.co/huggingface-mic) 里。

举例来说，SmolLM 的契约用诸如 "The capital of France is" 这样的 prompt 生成内容，并把它的 token ID 与一个记录下来的答案做比对。加载模型和 tokenizer 之后，生成代码是下面这样（简化为一个 prompt）：

```
inputs = tokenizer("The capital of France is", return_tensors="pt")
outputs = model.generate(**inputs, max_new_tokens=4, do_sample=False)
new_tokens = outputs[:, inputs["input_ids"].shape[1]:]
print(tokenizer.batch_decode(new_tokens, skip_special_tokens=True))
```

它还会比对训练 loss，检查梯度全是有限值，并验证一次 optimizer step 确实改变了权重。完整版见 [usage.md](https://huggingface.co/huggingface-mic/smollm-mic/blob/main/integrations/transformers/usage.md)。

Hub 上的一个 [fleet 数据集](https://huggingface.co/datasets/huggingface-mic/transformers-fleet)把每个 MIC 钉在一个冻结的 revision 上，连同记录其 baselines 时所用的包版本。每次 CI 运行都会记录它用了哪个 fleet revision，所以我们之后能把它复现出来。

在一个 PR 上，我们依据补丁改动了哪些文件来挑选 MIC。

## UMT5 回归

我们把冻结的 MIC 在五个月的 Transformers commit 上做了重放。那个小的 UMT5 fixture 把这次回归从它在 [2026 年 7 月 30 日](https://github.com/huggingface/transformers/commit/560f36cc561fa154d224b7a6dfcba1d57a621d7b)被引入起，一路标到它在 [9 月 28 日](https://github.com/huggingface/transformers/commit/d7ba937671edb174fd80d33f9ecbd38f6559dfca)被修好为止。标签的 log-probability 与被审阅的 baseline 相差 1.22，训练 loss 相差约 0.20。

有一个细节很关键：这份契约用的是 SDPA，也就是默认的 attention 路径。只跑 eager attention 那一个变体会漏掉这个 bug。fixture 只有在走的是和真实 checkpoint 相同的代码时才有用。

随后我们在 Transformers 的 CI 上开了一个验证分支，把那个修复还原回去。检查以同样的差值失败，而被选中的那份 T5 契约的 runner step 在 CPU 上耗时 13.4 秒，不含环境准备。

[重放结果](https://github.com/huggingface/transformers-mic/blob/main/docs/evidence.md#shadow-backfill)和 [CI 演示](https://github.com/huggingface/transformers-mic/blob/main/docs/evidence.md#transformers-ci-proof)里有这些测量值和复现细节。

## 模型是怎么被缩小的

最初的 recipe 很简单：把维度做小、层数留少。这对混合架构来说不够。如果留下的两层都用 sliding attention，而 full-attention 层全都消失了，留两层毫无用处。

现在这份 recipe 有四步：

- **缩小配置。** 从一个真实的 checkpoint 出发，缩减 hidden size、attention head 数量和深度。保留不同的层种类，包括 sliding 与 full attention 的混合、dense 与 MoE 层的混合。有些架构需要额外的规则来让它们的各种组件保持兼容。我们也会看模型自己的 Transformers 测试：`test_modeling_<model>.py` 里的 `ModelTester` 已经手工挑好了一份小配置，所以凡是我们的通用规则叫不出名字的宽度，就直接取它给出的尺寸。
- **保持预处理不变。** 保留词表、特殊 token 和输入维度，并逐字节复制 tokenizer 和 processor 文件。加载和预处理本身就是我们要测的东西的一部分。
- **构建并校验权重。** 先用带种子的随机权重，并改变输入来检查模型有没有响应。如果没有响应，就用这份契约的那一小批样本试着训练它。重新加载保存下来的模型，检查输出、loss 和梯度都是有限值。构建不合格的直接拒掉。
- **冻结并记录。** 保存被接受的权重，并在一个已知良好的 Transformers build 上测量可复现的输出。针对每个支持的平台和精度分别审阅 baselines，然后发布一个钉住的快照。CI 复用它；它不会为每个 PR 重新构建 fixture。

我们也保留原始的权重文件格式。否则我们就会跳过用户加载真实 checkpoint 时会执行的那段转换代码。[完整 recipe](https://github.com/huggingface/transformers-mic/blob/main/docs/fixtures.md#recipe)里有更多细节。

[Llama 4 Scout 的缩小报告](https://huggingface-mic-mic-coverage.static.hf.space/shrink/Llama-4-Scout-17B-16E-Instruct-mic.html)展示了这在一个大模型上是什么样子。1,086 亿参数变成 4,470 万。视觉栈从 34 层降到 2 层，语言栈从 48 层降到 4 层，同时保留被检查的层种类和 MoE 路由方式。

### 用 agent 构建 MIC

我们的 CLI `tmic` 会创建契约并构建 fixture。对一个新模型，由一个 LLM 起草 usage 代码和 manifest，再由 CPU 与 GPU 上的运行测出候选的 baselines。LLM 负责起草，不负责批准。期望值发生改变时需要人工审阅。

想在你的机器上试试，就把你的源 checkpoint 用在 `org/model` 的位置上：

```
pip install "transformers-mic[runtime]" "hf-doc-builder @ git+https://github.com/huggingface/doc-builder.git"
hf auth login
tmic run org/model --local-only --fixtures-only --no-history --bill-to ''
```

它会在你的机器上起草这份契约、构建 fixture 并记录它的 baselines，逐步请你审阅，并在上传任何东西之前停下。对于新模型，草稿来自一个经由 Inference Providers 的 LLM，费用记在你自己的账号上（`--bill-to ''`）。[CLI 文档](https://github.com/huggingface/transformers-mic/blob/main/docs/cli.md#automated-mode)覆盖了其中各个单独的步骤。

我们用 agent 在各个模型家族上构建 MIC。它们撞到边缘情况时，我们修的是 recipe 本身而不是那一个 fixture，并得到模型专家的帮忙。已发布的模型和剩下的缺口都在 [coverage space](https://huggingface.co/spaces/huggingface-mic/mic-coverage) 里。

## 随机权重与过拟合

用随机权重时，我们的 Whisper fixture 几乎不响应音频的变化。它跑得起来，但这就让它成了一个对音频路径很差的测试。

于是我们拿几个音调与 "red"、"green" 这类词配对的数据去训练它。我们并不是在教它语音识别，只是要让音频上的变化在它的输出里看得见。在我们的[权重初始化研究](https://github.com/huggingface/transformers-mic/blob/main/docs/fixtures.md#choosing-the-weights)里，随机权重的 Whisper fixture 在 24 个注入的故障中抓到了 18 个，而过拟合的 fixture 抓到了全部 24 个。

这就给了我们两种构建权重的方式：

- 从随机权重和一个固定的种子开始。
- 在少量样本上过拟合，比如 "The capital of France is" => "Paris"。

Whisper 的这个结果并不能判定哪种更好。那些是合成的故障，而我们还没有找到一个只有过拟合版本才抓到的真实回归。两个版本都漏掉了一个 assisted-decoding 的 bug，而真实的 Whisper checkpoint 把它暴露了出来。

所以，随机权重能通过检查时我们就保留随机权重，需要更好的灵敏度或可读的回答时才把它训练到过拟合。训练只要几秒，但它多了一个可能不收敛的步骤，也多一样需要维护的东西。[对比](https://github.com/huggingface/transformers-mic/blob/main/docs/fixtures.md#overfit-versus-random-what-can-we-conclude)里有两者的结果。

## 尚未解决的问题

截至 2026 年 11 月 1 日，[Transformers CI 里的 MIC 任务](https://transformers-ci.huggingface.cool/d/mic-failures/mic-failures?from=now-4w&to=now&timezone=browser)只报告失败，并不阻塞 PR。它该不该阻塞，取决于一些我们还没有测量的事情：

- 它在 PR 上能抓到多少真实 bug，而不只是在重放里抓到？
- 它有多少次让我们去追一场误报？
- 审阅 baselines 要花多少工作量？

我们也不知道有多少 bug——比如 Whisper 那个 assisted-decoding 的——只有在真实权重下才会显现，也不知道过拟合能不能抓到随机权重漏掉的真实 bug。

覆盖率仍然不完整，无论是模型家族还是人们实际用到的 API。当一个回归漏过去时，我们可以补上缺失的那条 usage path，并在坏掉的版本和修好的版本上重放它。在现有测试的覆盖被算清楚之前，我们会保留它们。

最后，我们想把 Hub 上的原始模型页链接到它们各自的 MIC，这样一位开发者或一个使用某个 checkpoint 的 agent 就能从一份已在该 checkpoint、它的环境和它的期望输出上验证过的示例出发。

想搭把手？从 [coverage space](https://huggingface.co/spaces/huggingface-mic/mic-coverage) 里挑一个还没被覆盖的模型，试试 [tmic 工作流](https://github.com/huggingface/transformers-mic/blob/main/docs/cli.md#automated-mode)，贡献一条 usage path，或者审阅一份生成出来的契约。
