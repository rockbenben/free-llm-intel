在自定义任务分布上结合 RL 与你最喜欢的 agent harness，可为该目标 harness 和任务分布带来更准确、更高效的模型。

模型并未针对所有 harness 和你正在执行的任务进行完全优化，而是面向通用性能。因此，当你把模型和 harness 组合使用时，实际上是在为你真正在做的事情上放弃了性能和效率。借助 RL，你可以训练一个自定义 harness 适配器，为你的 harness 与任务组合充分压榨模型的能力。

以 Qwen3.8-27B 为例，它在 pi harness 上的 Terminal-Bench 2.1 得分为 39%，平均每任务使用 2.9K token。如果我们冻结这些权重，并加入一个由 RL 训练的自定义 LoRA 适配器，可以得到 55% 的 pass@1，平均 token 使用量为 1.5K。这主要归功于模型推理更少、调用工具更少，并且首次尝试表现更好。

我们早期的工作（[multi-harness RL](https://huggingface.co/spaces/FineEnvs/multi-harness-rl)、[harness 适配器](https://huggingface.co/blog/harness-hub/harness-adapters)）表明，在你自己的任务分布上、在你自己的 harness 内进行 RL，可以得到更准确、更高效的模型。那些实验涵盖了数据分析和代码构建任务。在这里，我们希望进一步推进，探索这一结果是否在 27B 规模、更困难的真实世界软件工程任务上、跨三个 harness（Pi、OpenCode 和 Hermes Agent）依然成立。最重要的是，分享一套完全可复用的配方，以便你可以在自己的任务、harness、模型组合上复现。

## TL;DR

- 我们为每个 agent harness（pi、Hermes Agent、OpenCode）各训练了一个 Qwen3.8-27B 的 LoRA 适配器，RL 在 harness 自身内部进行。
- 数据集、训练和 agent rollout 都在 Hub 上的 Jobs 中完成，使用 TRL 的 `AsyncGRPOTrainer`、OpenEnv 和 harbor。
- 每个 harness 适配器在其自身 harness 下、在两个基准测试上都优于基座模型，无论是性能还是效率。
- 这三个 LoRA 还合并为一个单一的 super adapter，可在 pi、Hermes Agent 和 OpenCode 下原样运行。
- 所有产物（适配器、GGUF、RL 任务、safeagents 插件）都可以通过这个 [Hugging Face collection](https://huggingface.co/collections/harness-hub/qwen38-27b-harness-adapters) 浏览。

## 在 agent harness 内部训练

我们利用 [OpenEnv 中的 Harbor 集成](https://huggingface.co/docs/openenv/environments/harbor) 和 [TRL 的 OpenEnv](https://huggingface.co/docs/trl/openenv) 指南，在我们为最终训练所选的 harness 内部训练模型。我们为所有 RL 任务构建了即用型 Docker 镜像，其中已预装了目标 harness。在最终的 Docker 镜像中，我们使用 Pi `1.5.2`、OpenCode `2.2.7` 和 Hermes Agent `v0.22.6`。下面这张来自前述博客文章的示意图很好地解释了整个协议：

大多数 RL 框架训练的是 agent 循环的重新实现：agent 是针对框架自己的接口编写的，例如 [verl 的 AgentLoop](https://verl.readthedocs.io/en/latest/advance/agent_loop.html)、[SkyRL-Gym](https://github.com/NovaSky-AI/SkyRL) 环境、[rLLM](https://github.com/rllm-org/rllm) 的 agent 和环境类、[slime](https://github.com/THUDM/slime) 的自定义 rollout 函数，或 [ART](https://github.com/OpenPipe/ART) 在你自己的 Python agent 中的客户端。而在这里，harness 完全按发布时的样子运行，训练器从它产生的确切 token 中学习，这些 token 由 harness 与 vLLM 之间的代理记录。近期的工作也朝着同一方向推进：[Agent Lightning v1.0](https://huggingface.co/papers/2608.17528) 通过代理将部署时的 harness 保持在循环中（“harnessed agentic RL”），[SkyRL 的 Harbor 集成](https://novasky-ai.notion.site/skyrl-harbor) 在 Harbor trial 上训练，并将其聊天历史转换为训练器所需的 token。

## 在 Hugging Face 上生成自定义 RL 任务

在这套配方中，我们使用 Hub、OpenEnv 和 [Repo2RLEnv](https://github.com/huggingface/Repo2RLEnv) 创建了一个用于 agentic coding 的自定义数据集。我们将现有 RL 环境的任务检索、使用 Repo2RLEnv 的任务生成、使用 OpenEnv 的任务验证，以及采样整合到一个单一的数据流水线中。这为我们提供了质量最高的一组经过验证且相关的任务，用于提升 Qwen3.8-27B 在 agentic coding 上的表现。在本节中，我们将介绍它是如何构建的，以便你在自己的领域中尝试。

RL 训练需要 agent 可以尝试的任务、对每次尝试打分的验证器，以及证明验证器正确的证据。接受错误答案的验证器会教出错误的行为。已经可行的任务不会教给模型任何东西。

本节描述了我们如何从三个来源构建任务集：两个来自 Hugging Face Hub，第三个使用 Tasksmith（Repo2RLEnv 中的流水线）生成。每个任务都通过 `openenv validate` 的资格筛选，并对基座模型 Qwen3.8-27B 进行同样的难度检查。

![任务流水线：Tasksmith、SWE-smith 和 SWE-Gym 来源经过资格筛选、Harbor 打包、在 Hugging Face Jobs 上运行 openenv validate，以及用 Qwen3.8-27B 进行难度检查](https://huggingface.co/buckets/huggingface/harness-adapters-blog-assets/resolve/images/task-pipeline.png)

### 三个来源

每个任务使用 Harbor 格式，Terminal-Bench 2.1 也使用该格式。在 Hub 上对 Harbor 环境的广泛搜索返回了约 59,000 个任务，但它们包含重复项、评估集和标记为不可用于训练的任务。我们筛选出仅两个专为训练构建的 Hub 来源，并自行生成了第三个集合：

- SWE-smith（[Python](https://huggingface.co/datasets/SWE-bench/SWE-smith-py)、[Go](https://huggingface.co/datasets/SWE-bench/SWE-smith-go)）向真实的 Python 和 Go 仓库注入 bug，通过 LLM 改写或诸如翻转运算符之类的变异实现。捕获每个 bug 的测试成为该任务的测试。它增加了数据量。
- SWE-Gym，以 Harbor 任务形式打包在 [TaskTrove](https://huggingface.co/datasets/open-thoughts/TaskTrove) 中，将真实 GitHub issue 及其已合并的修复转化为任务。它增加了真实世界中的 bug。
- [Tasksmith](https://huggingface.github.io/Repo2RLEnv/pipelines/tasksmith/) 从已合并的 pull request 生成任务。一个 LLM agent 编写指令和测试，Tasksmith 检查结果：参考解和一个有效的替代解必须通过，而未修复的代码和一个已知错误的解必须失败。

我们使用 Tasksmith 来针对性地填补缺口。我们梳理了目标基准测试（Terminal-Bench 2.1、SWE-bench Pro 的困难子集和 DeepSWE）所测试的技能，然后选择能锻炼这些技能的 pull request，例如 HTTP 流式传输、文件系统操作和序列化。从 30 个已合并的 pull request 中，Tasksmith 在 10 个 Python 仓库中生成了 24 个通过其检查的任务，其中 17 个是在第二次运行时通过的。它的检查不能取代我们的检查，因此这些任务与其他任务一样经过相同的流水线。

### 使用 `openenv validate` 进行验证

首先运行元数据筛选。它保留来自训练划分、具有宽松许可证的任务。它丢弃重复项、标记为不可用于训练的任务、我们目标基准测试中的 253 个任务，以及来自这些基准测试所用仓库的任何任务。然后我们在全新 trial 中对每个任务运行 `openenv validate` 的语义检查：

- 参考解获得最高奖励（`semantic.oracle_max`）。
- 什么都不做得分明显更低（`semantic.floor_gap`）。
- 没有任何 canary 得分高于什么都不做（`semantic.canary_floor`）。
- 重放参考解得到相同奖励（`runtime.episode_determinism`）。

每个 trial 作为独立的 Hugging Face Job 运行，这让我们可以一次验证数十个任务。`openenv validate` 为任何 Harbor 任务提供相同的选项：

```
openenv validate path/to/task --sandbox hf-sandbox
```

1,127 个 Hub 候选任务中有 858 个通过。错误答案对照捕获了缺陷，包括一个接受不完整实现的 Tasksmith 任务，以及一个接受已知错误答案的 Terminal-Bench 2.1 验证器（regex-log）。大多数失败是基础设施问题，例如镜像未能启动。失败的任务保留在 rejected 划分中，并记录失败的检查。

### 使用基座模型进行难度检查

一个有效的任务仍然可能教不了任何东西。GRPO（group relative policy optimization）将每次尝试与同一任务的其他尝试进行对比打分，因此如果一个任务的每次尝试都通过，或每次尝试都失败，就不会提供学习信号。在训练之前，Qwen3.8-27B 对每个任务尝试 4 次，或对每个仓库分层抽样的六个任务尝试 8 次。

在 442 个已打分任务中，Qwen3.8-27B 每次都解决了 151 个，从未解决 120 个。它仅有时解决的 171 个任务构成合格集。下图显示了得分如何在两端堆积，以及它们如何因来源而异。模型每次都解决大多数 Go 任务，在超过三分之一的 SWE-smith Python 任务上每次尝试都失败，并在 73% 的 SWE-Gym 任务上处于中间水平。

![Qwen3.8-27B 在 442 个已打分任务上的结果，按解决的尝试次数和来源划分](https://huggingface.co/buckets/huggingface/harness-adapters-blog-assets/resolve/images/difficulty-check.png)

*Qwen3.8-27B 在 442 个已打分任务上的结果。绿色标记的是合格任务，即模型在某些尝试中解决但并非全部。*

这个例子展示了我们如何将 1,127 个任务筛选和验证为 278 个，并直接纳入最终数据集。该流水线随后将剩余的 522 个被拒绝任务，使用 Tasksmith 进行修复和复杂化，并重复验证。

## 通过短训练运行测试过滤器

该流水线应用两个过滤器：验证移除损坏的任务，难度检查保留基座模型仅有时解决的任务。本节测试这些过滤器是否改变模型所学的内容。我们进行了四次短训练运行，每次最多 50 步，各自使用来自流水线不同阶段的任务，并在 Terminal-Bench 2.1 上与基座模型进行比较。

每次运行使用 LoRA 和 GRPO、TRL 的 `AsyncGRPOTrainer`，在 32 个任务上训练 Qwen3.8-27B。所有四次运行使用相同的 agent harness（OpenCode，最多 48 次模型调用）、相同的设置和一个 8×H200 Hugging Face Job，奖励是验证器的通过或失败。任务集的区别在于它们的过滤方式：

- **未验证**：24 个接受的任务加上 8 个未通过验证的任务。
- **已验证**：32 个接受的任务，不考虑难度选择。
- **不合格**：32 个接受的任务，基座模型总是或从不解决。
- **合格**：32 个接受的任务，基座模型在某些尝试中解决。

## `AsyncGRPOTrainer`：更高效的 GRPO 训练

我们利用了 TRL 中稳定版本的 `AsyncGRPOTrainer`，该训练器的主要优势在于它不必等到所有 rollout 完成后才进入下一个训练优化步骤。

有关该训练器及其构建块的更详细阅读，请参阅 [AsyncGRPO 博客文章](https://huggingface.co/spaces/trl-lib/async-grpo-stable)。

## 训练设置

为了得到最终的 harness 适配器，我们使用 TRL 的 `AsyncGRPOTrainer` 在 [Qwen/Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B) 之上训练了 LoRA 适配器。适配器通过 `all-linear` 标志附加到模型。为了最大化训练效率，在 rollout 阶段关闭了 thinking 模式，并且我们在开启和关闭 thinking 的情况下评估了最终适配器，以便进行更广泛的比较。

最终奖励函数由验证器的正确性加上一个小的工具效率奖励（0.1，源自 [上一轮 harness 适配器早期实验](https://huggingface.co/blog/harness-hub/harness-adapters)，该实验表明 0.1 效果最佳）组成。

我们使用 Termgrade 环境进行了 50 步的小型 LR 扫描（1e-5、5e-5 和 1e-4），注意到 1e-5 几乎不改变训练正确性（从 0.52 到 0.50），1e-4 导致 rollout 崩溃而非改善（每次 rollout 的轮数从 18 降到 6，熵上升），只有 5e-5 明显改善（到第 40 步时从 0.49 到 0.60）。更长的 5e-5 运行随后显示出不稳定迹象（rollout 长度崩溃、熵上升），因此我们在最终运行中选定 2e-5。

### 训练基础设施

每个 harness 适配器使用 NVIDIA 2xB200 GPU 训练，其中一个 GPU 分配给 vLLM 服务器，另一个分配给训练进程。我们首先进行了一些压力测试，以最大化单个优化步骤内可训练的 RL 任务数量。为此，我们将 `AsyncGRPOTrainer` 的 `--token-budget` 参数在我们设置下的上限“拉满”。下图显示了每个 harness 每步组数的演变（蓝色：Pi，绿色：OpenCode，橙色：Hermes）。

随着模型在训练过程中越来越好，它能够在每个训练步骤中容纳越来越多的组，这使模型在每个优化步骤获得的信号更加多样化。

### 最终混合

最终数据混合由来自 [harness-adapters RL 环境](https://huggingface.co/datasets/harness-hub/harness-adapters)的 750 个任务和来自 [termgrade](https://huggingface.co/datasets/ai-and/termgrade-environments) 的 300 个任务组成。为了最大化训练期间采样任务的多样性，我们对数据采样策略进行了轻微定制，下面将进行解释：

在训练之前，任务按家族（即我们生成的 RL 环境的仓库。对于 Termgrade，我们只是按名称排序，因为每个任务被视为自己的家族）交错排列成固定顺序，因此每个训练步骤在遵循混合分布的同时尽可能混合多个仓库。

### 循环中的 safeagents

我们还插入了 [safeagents](https://github.com/huggingface/safeagents) 工具，以便在训练期间阻止模型的任何不当行为。最终插件（由针对 RL 任务和测试路径的正则与模式规则组成）托管在 [harness-hub/qwen-safeagents-plugin](https://huggingface.co/harness-hub/qwen-safeagents-plugin)，可使用最新版本的 safeagents 开箱即用，以便任何想复现训练设置的人使用。

safeagents 阻止的工具数量在训练期间持续下降，这表明模型在每个优化步骤后变得“越来越安全”。下图显示了每个 harness 适配器按训练步骤统计的每 1000 次工具调用中被 safeagents 阻止的调用数。

![pi、hermes 和 opencode 适配器按训练步骤统计的每 1,000 次工具调用中被 safeagents 阻止的调用数](https://huggingface.co/buckets/huggingface/harness-adapters-blog-assets/resolve/images/safeagents-blocked.png)

## Super-adapter：将所有适配器合并为一个

模型合并通常会将它们的能力结合起来，同时保留每个模型所能做的大部分事情。在三个 harness 适配器训练完成后，我们提出了两个问题：合并它们会损失准确率吗？一个单一的“super-adapter”能否在每个 harness 下都准确且高效？

我们首先逐层比较三个适配器的权重更新。它们中任意两个之间的余弦相似度约为 0.01–0.02：每个适配器在训练期间将模型推向几乎正交的方向。这是合并的最佳情况，因为更新几乎不相互干扰。

我们沿 rank 维度拼接三个 LoRA 适配器（PEFT 的 `combination_type="cat"`）。合并后的适配器 rank 为 96（3 × 32），精确应用 w · (ΔW_pi + ΔW_hermes + ΔW_opencode)。先前的合并工作（[task arithmetic](https://huggingface.co/papers/2212.04089)、[TIES](https://huggingface.co/papers/2306.01708)、[KnOTS](https://huggingface.co/papers/2410.19735)）发现将每个更新缩放到 1 以下效果最佳，因此我们在每个 harness 下、在所有 89 个 Terminal-Bench 2.1 任务上，使用第 120 步的适配器比较了三种权重：

- ⅓（平均值）：每个 harness 只保留自己更新的三分之一。
- ½：每个更新以一半强度应用。
- 1（直接求和）：每个更新完整应用。

| 权重 | pi | hermes | opencode | 所有三个 harness | 每任务工具调用数 |
| --- | --- | --- | --- | --- | --- |
| 基座模型 | 39.1% | 46.0% | 44.8% | 43.3% | 49.2 |
| ⅓（平均） | 49.4% | 51.2% | 47.1% | 49.2% | 35.6 |
| **½** | 48.8% | 53.5% | 55.2% | **52.5%** | 25.9 |
| 1（求和） | 40.2% | 62.8% | 47.1% | 50.0% | 13.4 |

直接求和会过度应用更新。agent 变得非常短（每任务 13 次工具调用，而基座模型为 49 次），虽然 Hermes 达到 62.8% 的峰值，但 pi 回落到基座模型的水平。平均值稀释了每个 harness 自己的更新。½ 提供了最佳平衡，因此我们使用发布的 checkpoint（pi 第 160 步、hermes 第 160 步、opencode 第 150 步）以权重 ½ 构建了最终的 super-adapter。

### 适配器合并评估结果

在每个 harness 下，在所有运行都评分的任务上（SWE-bench Pro 上 50–51 个，Terminal-Bench 2.1 上 82–85 个），每任务一次尝试（括号中为相对于基座模型的效率提升）：

| Harness | 基准测试 | [Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B) | Qwen3.8-27B-<harness>-adapted | [Qwen3.8-27B-super-adapter](https://huggingface.co/harness-hub/Qwen3.8-27B-super-adapter) | [Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B)，thinking | [Qwen3.8-27B-super-adapter](https://huggingface.co/harness-hub/Qwen3.8-27B-super-adapter)，thinking |
| --- | --- | --- | --- | --- | --- | --- |
| pi | SWE-bench Pro（困难 51） | 40.0% | 64.0%（−60%） | 46.0%（−73%） | 74.0% | 74.0%（−48%） |
| hermes | SWE-bench Pro（困难 51） | 29.4% | 43.1%（−56%） | 47.1%（−60%） | 45.1% | 60.8%（−36%） |
| opencode | SWE-bench Pro（困难 51） | 35.3% | 51.0%（−72%） | 45.1%（−63%） | 47.1% | 66.7%（−31%） |
| pi | Terminal-Bench 2.1 | 40.0% | 56.5%（−56%） | 48.2%（−56%） | 52.9% | 57.6%（−25%） |
| hermes | Terminal-Bench 2.1 | 44.7% | 58.8%（−70%） | 55.3%（−53%） | 58.8% | 63.5%（−19%） |
| opencode | Terminal-Bench 2.1 | 47.6% | 52.4%（−53%） | 52.4%（−68%） | 54.9% | 58.5%（−22%） |

“Thinking”指聊天模板在默认努力程度（xhigh）下的 thinking 模式。专用适配器在关闭 thinking 的情况下训练和提供服务。

在关闭 thinking 的情况下，super-adapter 在所有六个 harness–基准测试组合上都优于基座模型（平均 pass@1 39.5% → 49.0%；新解决 71 个任务，丢失 34 个，p < 0.001）。

尽管完全没有在开启 thinking 的情况下训练，它却是我们评估过的开启 thinking 模式的最强模型。与相同努力程度下开启 thinking 的基座模型相比，它在六个组合中赢下五个，并在第六个上持平（平均 55.5% → 63.5%；新解决 67 个，丢失 37 个，p = 0.004）。最大增益在 SWE-bench Pro 上：hermes 下 +16 分，opencode 下 +20 分。在 pi 下的 SWE-bench Pro 上，仅 thinking 就已达到 74%，它持平。

关闭 thinking 时使用专用 harness 适配器。每个 harness 自己的适配器在六个组合中的四个上领先，其中 pi 下领先最多（SWE-bench Pro 上 64.0% 对 46.0%，Terminal-Bench 上 56.5% 对 48.2%）。将一个模型拆分到三个 harness 上，pi 损失了最多的增益。如果你只使用一个 harness 并保持 thinking 关闭，就使用它的专用适配器。

super adapter 的效率也高得多。在基座模型和 super-adapter 都能解决的任务上，关闭 thinking 时，它每任务减少 53–73% 的工具调用，生成减少 44–60% 的 token，在 130 个任务中的 111 个上工具调用更少。开启 thinking 时，它在 SWE-bench Pro 上仍将工具调用减少 31–48%，token 减少 24–43%。在 Terminal-Bench 上，工具调用减少 19–25%，token 数大致相同。

½ 权重是在 Terminal-Bench 2.1 上使用第 120 步适配器选定的，因此 Terminal-Bench 的数字略有乐观；SWE-bench Pro 未参与该选择。完整的配对结果在 [super-adapter 的模型卡](https://huggingface.co/harness-hub/Qwen3.8-27B-super-adapter)中。

## 最终结果

本节报告训练期间发生的情况，然后说明适配器在其自身 harness 内外、在留出基准测试上的得分。

### 训练结果

训练累计运行了 598 步，总共训练了 78,114 个样本，正好相当于 167M 个训练 token。

在训练期间，我们看到一个明确的信号：模型学会用越来越少的步骤解决任务，且没有明显的饱和迹象。尽管有时有明显的上升趋势，训练正确性总体上似乎持平。这可以解释为：模型在训练期间遇到新任务，但随着轨迹变短，一个步骤 token 预算内能容纳的组数增加了一倍以上。准确率增益出现在下面一节的留出基准测试中。

另一方面，safeagents 成功阻止了多次可疑尝试。在三次训练运行中，总共检查了 1.3M 次工具调用，共阻止了 647 次工具调用。

### 评估结果

本节涵盖评估设置、harness 内结果、跨 harness 迁移，以及一项分布外检查。

#### 评估设置

我们在每个适配器训练所在的 harness 内评估它，使用两个 agentic coding 基准测试：所有 89 个 [Terminal-Bench 2.1](https://huggingface.co/datasets/harborframework/terminal-bench-2.1) 任务（每任务 1 小时和 100 个 agent 步骤）以及 SWE-bench Pro 的 51 个最困难任务（2 小时和 100 个 agent 步骤）。我们将每任务的最大 token 数上限设为 131072。我们不调整 agent 设置，并对所有 harness 使用默认设置。例如，Pi 不保留之前的推理轮次，而 OpenCode 和 Hermes 会保留，这主要由于上下文快速溢出而影响 SWE-bench Pro 的结果。因此你不能跨不同 harness 比较结果（使用 Pi 不一定比 Hermes 或 OpenCode 带来更好的结果），但在同一 harness 内比较结果并得出结论是公平的。

每次 rollout 都通过与训练相同的 Harbor 和 OpenEnv 栈运行，在 HF sandbox 中，每任务一次尝试，温度 0.8、thinking 关闭。每个 LoRA checkpoint 合并到基座权重中，并在单个 GPU 上用 vLLM 单独提供服务，并发与基座模型的评估相同。

对于所有评估基准测试，我们报告 pass@1 以及工具调用次数、总轮数，针对所有任务和已解决任务。

为了开放，最终评估的所有模型轨迹都推送到了这个公共 bucket：[harness-hub/harness-adapters-trajectories](https://huggingface.co/buckets/harness-hub/harness-adapters-trajectories)。

#### 最终评估结果

所有三个专用适配器在其自身 harness 下、在两个基准测试上都优于基座模型。在 SWE-bench Pro（困难 51）上，pi 从 39.2% 到 64.7%（+25.5 分：新解决 15 个任务，丢失 2 个，p = 0.002），hermes 从 29.4% 到 43.1%，opencode 从 35.3% 到 51.0%。在完整的 Terminal-Bench 2.1 上，pi 提升 +16.3 分（16 对 2，p = 0.001），hermes 提升 +14.1（19 对 7，p = 0.03）。Opencode 总体提升 +6.0，在未参与其 checkpoint 选择的 66 个任务上提升 +13.6（12 对 3，p = 0.035）。

适配器解决任务的效率也高得多：在它们和基座模型都能解决的任务上，它们在 SWE-bench Pro 上每任务减少 56–72% 的工具调用，在 Terminal-Bench 2.1 上减少 53–70%。单一的 super-adapter 在所有三个 harness 下也优于基座模型（SWE-bench Pro 上 +6 到 +18 分，Terminal-Bench 2.1 上 +5 到 +10），工具调用减少幅度同样大（53–73%）。在关闭 thinking 的情况下，它保留每个专用适配器增益的程度较低，pi 下最低，但在开启 thinking 的情况下，它在六个 harness–基准测试组合中的五个上优于相同努力程度的基座模型 thinking（见 [super-adapter 部分](https://huggingface.co/blog/harness-adapters-at-scale#super-adapter-merging-all-adapters-into-one)）。每个模型卡都有完整的配对结果。

#### 效率和性能能力能否跨 harness 迁移？

为了回答这个问题，我们还评估了 pi harness 适配器在 Hermes Agent 和 OpenCode 下的表现。

在 OpenCode 下，它在 Terminal-Bench 2.1 上与 OpenCode 自己的专用适配器持平（44.8% → 54.0%，对照 46.4% → 52.4%）。在 Hermes 下，它保留了专用适配器约三分之二的增益（46.3% → 56.1%，对照 44.7% → 58.8%），两者工具调用减少幅度相同，约 45%。因此，新学到的能力似乎可以跨 harness 迁移。

#### 分布外任务和设置的评估

如果我们在分布外任务上评估、在适配器训练所用的 harness 之外评估，会发生什么？

我们在 300 个 [AutomationBench 任务](https://github.com/zapier/AutomationBench)上运行了所有五个模型，这些任务由业务自动化工作流评估组成，使用 AutomationBench 自己的 agent 循环，而不是 Pi、Hermes 或 OpenCode。这样，我们可以交叉检查两个不同的问题：模型能否解决 SWE 相关任务之外的问题？当模型被置于其训练所用 harness 之外时会发生什么？

结果表明，适配器与基座模型接近。Pi 和 OpenCode 略领先（27.0% 和 25.3% pass@1，对照 23.0%），合并适配器持平（23.7%），Hermes 落后几分（17.7%）。除 Hermes 外，差异都在噪声范围内，因此 harness 内的 RL 既没有明显迁移到这个非常不同的设置，也没有在这个设置上破坏模型。

| 模型 | pass@1（满足所有断言） | 相对基座 | 部分得分（满足断言的比例） | 相对基座 |
| --- | --- | --- | --- | --- |
| base | 23.0% |  | 62.2% |  |
| pi 160 | 27.0% | +4.0 | 66.2% | +4.0 |
| opencode 150 | 25.3% | +2.3 | 65.2% | +3.0 |
| merged | 23.7% | +0.7 | 60.6% | −1.6 |
| hermes 160 | 17.7% | −5.3 | 56.6% | −5.6 |

## 开放问题：模型究竟学会了做什么？

我们感谢用户和社区的反馈，社区的初步测试和结果总体上似乎非常积极，我们希望未来继续朝这个方向努力。我们也看到了一些令人惊讶的结果，例如用户报告 [harness 适配器在 Qwen3.8 衍生模型（如 Swift-1.5）下效果非常好](https://huggingface.co/harness-hub/Qwen3.8-27B-opencode-adapted-GGUF/discussions/2)。

这个问题是我们在发布后思考的一个开放问题。在仔细检查评估基准生成的轨迹后，我们发现模型在非 thinking 模式下，倾向于在提出工具调用之前生成一些短文本，而基座模型几乎不生成任何文本就直接生成工具调用。

这种现象可以看作一种“推理泄漏”，模型学会通过生成一些有时看起来像推理轨迹的文本（例如：..wait? ..let me see 等）来“逃逸”其非 thinking 版本，进入 thinking 版本。[最近的一篇论文](https://huggingface.co/papers/2610.14270)也很好地描述了 LLM 在 RL 阶段的行为。

这是否使我们的模型失效？我们不这么认为，因为最终结果仍然有效；在完全相同的条件下（固定 token 预算），我们的适配器确实（远远）优于基座非 thinking 模型，并达到 thinking 版本的性能，同时 token 效率高得多。社区的积极反馈进一步证实了这一点。

然而，这提出了进行适当后续工作的必要性，我们将尝试对纯 thinking 模型重新应用相同的流水线，并探索混合 thinking / 非 thinking 训练，以更好地理解 RL 训练在混合 thinking 模型上的行为。一旦我们获得结论性结果，我们将与社区分享我们的下一步发现（以及 harness 适配器）。

## 结语与未来方向

在这项工作中，我们证明了在目标 harness 内对模型进行 RL 训练，会在相同条件下评估时带来更高效、因而更准确的最终模型。这一观察与 Hugging Face 团队之前的几项工作一致并延续，例如 [multi-harness-RL](https://huggingface.co/spaces/FineEnvs/multi-harness-rl) 或 [harness 适配器的早期迭代](https://huggingface.co/blog/harness-hub/harness-adapters)。

未来，我们将探索将此配方应用于更多模型，同时更好地研究混合 thinking / 非 thinking 模型的训练策略。

我们还公开与社区分享完整的配方和流水线，以便复现一切，并邀请每个人从自己的代码库或任何相关材料中构建自己的 RL 任务，并将相同的训练配方和想法应用于他们最喜欢的模型和 harness，以获得更高效的 agentic 模型。我们希望这篇博客文章能成为构建者未来构建和分享自己的 harness 适配器的起点。
