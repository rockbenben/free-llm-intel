在自定义任务分布上做 RL，再配上你最常用的 agent harness，可以为这个目标 harness 和任务分布得到更准确、更高效的模型。

模型并没有针对所有 harness、也没有针对你手头的任务做过充分优化，它们优化的是通用性能。因此，把一个模型和某个 harness 组合起来使用时，你实际上是在自己真正要做的事情上白白丢掉了性能和效率。借助 RL，你可以训练一个定制的 harness 适配器，在你自己的 harness 与任务组合上，把模型的潜力全部榨出来。

以 Qwen3.8-27B 为例，它在 pi harness 上的 Terminal-Bench 2.1 得分是 39%，平均每个任务消耗 2.9K token。如果我们把这些权重冻结住，再加上一个用 RL 训练出来的定制 LoRA 适配器，pass@1 可以做到 55%，平均 token 用量降到 1.5K。这主要归功于模型思考得更少、调用的工具更少，而且第一次尝试就能做对。

我们早前的工作（[multi-harness RL](https://huggingface.co/spaces/FineEnvs/multi-harness-rl)、[harness adapters](https://huggingface.co/blog/harness-hub/harness-adapters)）已经表明：在你自己的任务分布上、在你自己的 harness 内部做 RL，能得到更准确、也更高效的模型。那些实验覆盖的是数据分析和代码构建类任务。这一次我们想把结论再往前推一步，看看它在 27B 规模、在更难的现实软件工程任务上、并且在三个 harness（Pi、OpenCode 和 Hermes Agent）上是否依然成立。最重要的是，我们要分享一套完全可复用的配方，让你能在自己的任务、harness、模型组合上把它复现出来。

## TL;DR

- 我们为每个 agent harness（pi、Hermes Agent、OpenCode）各训练了一个 Qwen3.8-27B 的 LoRA 适配器，RL 直接在 harness 内部进行。
- 数据集、训练和 agent rollout 全部在 Hub 的 Jobs 上完成，用的是 TRL 的 `AsyncGRPOTrainer`、OpenEnv 和 harbor。
- 每个 harness 适配器在自己的 harness 下，在两个基准测试上的性能和效率都优于基座模型。
- 这三个 LoRA 还会被合并成一个 super adapter，在 pi、Hermes Agent 和 OpenCode 下都能原样运行。
- 所有产物（适配器、GGUF、RL 任务、safeagents 插件）都可以在这个 [Hugging Face collection](https://huggingface.co/collections/harness-hub/qwen38-27b-harness-adapters) 里浏览。

## 在 agent harness 内部训练

我们借助 [OpenEnv 中的 Harbor 集成](https://huggingface.co/docs/openenv/environments/harbor)和 [TRL 的 OpenEnv](https://huggingface.co/docs/trl/openenv) 指南，在我们为最终训练选定的几个 harness 内部训练模型。我们为所有 RL 任务都构建了开箱即用的 Docker 镜像，里面已经预装好目标 harness。最终的镜像里用的是 Pi `1.5.2`、OpenCode `2.2.7` 和 Hermes Agent `v0.22.6`。下面这张图出自前面提到的那篇博客，把整个协议讲得很清楚：

大多数 RL 框架训练的都是 agent 循环的一个重新实现：agent 是照着框架自己的接口写的，比如 [verl 的 AgentLoop](https://verl.readthedocs.io/en/latest/advance/agent_loop.html)、[SkyRL-Gym](https://github.com/NovaSky-AI/SkyRL) 环境、[rLLM](https://github.com/rllm-org/rllm) 的 agent 与环境类、[slime](https://github.com/THUDM/slime) 的自定义 rollout 函数，或者 [ART](https://github.com/OpenPipe/ART) 放在你自己 Python agent 里的客户端。而在我们这里，harness 完全按照它发布时的样子运行，训练器学的是它实际产出的那些 token——由 harness 与 vLLM 之间的一个 proxy 记录下来。近期的工作也在朝同一个方向走：[Agent Lightning v1.0](https://huggingface.co/papers/2608.17528) 通过一个 proxy 把部署时的 harness 留在循环之中（“harnessed agentic RL”），[SkyRL 的 Harbor 集成](https://novasky-ai.notion.site/skyrl-harbor)则在 Harbor trial 上训练，把 trial 的聊天历史转成训练器可用的 token。

## 在 Hugging Face 上生成自定义 RL 任务

为了这套配方，我们用 Hub、OpenEnv 和 [Repo2RLEnv](https://github.com/huggingface/Repo2RLEnv) 构建了一个面向 agentic coding 的自定义数据集。我们把从现有 RL 环境里检索任务、用 Repo2RLEnv 生成任务、用 OpenEnv 验证任务、以及采样这几步，合并成了一条数据流水线。这样我们就得到了一批质量最高、既经过验证又与目标相关的任务，用来提升 Qwen3.8-27B 在 agentic coding 上的表现。本节会带你看我们是怎么把它搭起来的，方便你在自己的领域里照样试一遍。

RL 训练需要三样东西：agent 可以尝试的任务、给每次尝试打分的验证器，以及证明验证器判得对的证据。一个会接受错误答案的验证器，教出来的是错误行为；一个本来就做得出来的任务，也教不了模型任何东西。

本节说明我们如何从三个来源构建任务集：两个来自 Hugging Face Hub，第三个由 Tasksmith（Repo2RLEnv 里的一条流水线）生成。每个任务都要通过 `openenv validate` 的资格筛查，还要对基座模型 Qwen3.8-27B 做同一套难度检查。

![任务流水线：Tasksmith、SWE-smith 和 SWE-Gym 三个来源经过资格筛查、Harbor 打包、在 Hugging Face Jobs 上执行 openenv validate，再用 Qwen3.8-27B 做难度检查](https://huggingface.co/buckets/huggingface/harness-adapters-blog-assets/resolve/images/task-pipeline.png)

### 三个来源

每个任务都采用 Harbor 格式，Terminal-Bench 2.1 用的也是这个格式。我们在 Hub 上对 Harbor 环境做过一次大范围搜索，返回了大约 59,000 个任务，但其中混着重复项、评估集，以及标注为不可用于训练的任务。我们最后只留下两个专为训练构建的 Hub 来源，第三批则由我们自己生成：

- SWE-smith（[Python](https://huggingface.co/datasets/SWE-bench/SWE-smith-py)、[Go](https://huggingface.co/datasets/SWE-bench/SWE-smith-go)）会往真实的 Python 和 Go 仓库里注入 bug，方式要么是让 LLM 改写，要么是做一次变异，比如翻转某个运算符。能捕获对应 bug 的测试，就成了这个任务的测试。它带来的是数量。
- SWE-Gym 以 Harbor 任务的形式打包在 [TaskTrove](https://huggingface.co/datasets/open-thoughts/TaskTrove) 里，把真实的 GitHub issue 及其已合并的修复转成任务。它带来的是真实世界里的 bug。
- [Tasksmith](https://huggingface.github.io/Repo2RLEnv/pipelines/tasksmith/) 从已合并的 pull request 生成任务。一个 LLM agent 写出指令和测试，Tasksmith 再校验结果：参考解和一个合理的替代解必须通过，而未修复的代码和一个已知错误的解法必须失败。

我们用 Tasksmith 来补缺口。我们先梳理了目标基准测试（Terminal-Bench 2.1、SWE-bench Pro 的困难子集，以及 DeepSWE）考察哪些能力，然后挑出能练到这些能力的 pull request，比如涉及 HTTP 流式传输、文件系统操作和序列化的那些。从 30 个已合并的 pull request 里，Tasksmith 在 10 个 Python 仓库上产出了 24 个通过其校验的任务，其中 17 个是在第二次运行时才通过的。它的校验替代不了我们自己的校验，所以这些任务照样要走和其他任务一样的流水线。

### 用 `openenv validate` 做验证

先跑一遍元数据筛查。它会保留来自训练划分、并且许可证宽松的任务。它会丢掉重复项、标注为不可用于训练的任务、我们目标基准测试里的 253 个任务，以及来自这些基准测试所使用仓库的任何任务。之后我们在全新的 trial 里，对每个任务运行 `openenv validate` 的语义检查：

- 参考解能拿到最高奖励（`semantic.oracle_max`）。
- 什么都不做，得分明显更低（`semantic.floor_gap`）。
- 没有任何 canary 的得分高于什么都不做（`semantic.canary_floor`）。
- 重放参考解，得到相同的奖励（`runtime.episode_determinism`）。

每个 trial 都作为独立的 Hugging Face Job 运行，这让我们能同时验证几十个任务。对任何 Harbor 任务，`openenv validate` 都提供同样的选项：

```
openenv validate path/to/task --sandbox hf-sandbox
```

1,127 个 Hub 候选任务里有 858 个通过。错误答案对照组抓出了缺陷，包括一个会接受不完整实现的 Tasksmith 任务，以及一个会接受已知错误答案的 Terminal-Bench 2.1 验证器（regex-log）。大多数失败是基础设施问题，比如镜像起不来。失败的任务会留在 rejected 划分里，并记录下失败的检查项。

### 用基座模型做难度检查

一个有效的任务，也可能什么都教不了。GRPO（group relative policy optimization）是把同一任务上的每次尝试相互比较来打分，所以如果某个任务每次尝试都通过、或者每次尝试都失败，就提供不了学习信号。训练之前，Qwen3.8-27B 对每个任务尝试 4 次；对每个仓库分层抽样出的 6 个任务，则尝试 8 次。

在 442 个已评分的任务里，Qwen3.8-27B 有 151 个每次都解出，120 个从未解出。它只在部分尝试中解出的 171 个任务，构成了本次的合格集。下图展示了得分如何在两端堆积，以及不同来源之间的差异。模型对大多数 Go 任务每次都能解出，在超过三分之一的 SWE-smith Python 任务上每次尝试都失败，而在 73% 的 SWE-Gym 任务上处于中间水平。

![Qwen3.8-27B 在 442 个已评分任务上的结果，按解出的尝试次数和来源划分](https://huggingface.co/buckets/huggingface/harness-adapters-blog-assets/resolve/images/difficulty-check.png)

*Qwen3.8-27B 在 442 个已评分任务上的结果。绿色标记的是合格任务，也就是模型只在部分尝试中解出的那些任务。*

这个例子说明了我们如何把 1,127 个任务筛到 278 个，并直接放进最终数据集。流水线随后把剩下 522 个被拒任务交给 Tasksmith 做修复和复杂化，再重复一遍验证。

## 用短训练运行检验过滤器

这条流水线有两道过滤器：验证环节剔除坏掉的任务，难度检查则只留下基座模型时对时错的任务。本节要检验的是，这两道过滤器会不会改变模型学到的东西。我们做了四次短训练，每次最多 50 步，分别使用流水线不同阶段的任务，并在 Terminal-Bench 2.1 上与基座模型做对比。

每次运行都用 LoRA 和 GRPO，配合 TRL 的 `AsyncGRPOTrainer`，在 32 个任务上训练 Qwen3.8-27B。四次运行使用相同的 agent harness（OpenCode，最多 48 次模型调用）、相同的设置，各占一个 8×H200 的 Hugging Face Job，奖励就是验证器给出的通过或不通过。四组任务的区别在于过滤方式：

- **未验证**：24 个通过的任务，加上 8 个验证失败的任务。
- **已验证**：32 个通过的任务，选择时不考虑难度。
- **不合格**：32 个通过的任务，但基座模型总是解出、或者从不解出。
- **合格**：32 个通过的任务，并且基座模型只在部分尝试中解出。

下图展示了这些任务如何影响模型学习。表格列出每次运行的步数以及我们评估的 checkpoint。图表追踪的是在不同验证状态的任务子集上的训练奖励。

## `AsyncGRPOTrainer`：更高效的 GRPO 训练

我们用的是 TRL 里稳定版的 `AsyncGRPOTrainer`。这个训练器最主要的优势在于，它不必等到所有 rollout 都完成，才进入下一个训练优化步。

关于这个训练器及其各个组件，如果想读得更细，请参阅 [AsyncGRPO 博客文章](https://huggingface.co/spaces/trl-lib/async-grpo-stable)。

## 训练设置

为了得到最终的 harness 适配器，我们用 TRL 的 `AsyncGRPOTrainer`，在 [Qwen/Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B) 之上训练 LoRA 适配器，并通过 `all-linear` 标志把它们挂到模型上。为了最大化训练效率，rollout 阶段关闭了 thinking 模式；最终的适配器我们分别在开启和关闭 thinking 的情况下做了评估，以便比较得更全面。

最终的奖励函数，由验证器给出的正确性，加上一点工具效率奖励（0.1）组成。这个系数来自[上一轮 harness 适配器的早期实验](https://huggingface.co/blog/harness-hub/harness-adapters)，当时发现 0.1 效果最好。

我们用 Termgrade 环境做了 50 步的小规模学习率扫描（1e-5、5e-5 和 1e-4）：1e-5 几乎没让训练正确率变动（0.52 → 0.50）；1e-4 让 rollout 直接崩掉，而不是变好（每个 rollout 的轮数从 18 掉到 6，熵反而上升）；只有 5e-5 有明显提升（到第 40 步时从 0.49 升到 0.60）。但更长的 5e-5 训练随后出现了不稳定迹象（rollout 长度塌缩、熵上升），所以我们最终把学习率定在 2e-5。

### 训练基础设施

每个 harness 适配器都用 NVIDIA 2xB200 GPU 训练，一块 GPU 分给 vLLM 服务器，另一块分给训练进程。我们先做了一轮压力测试，想把单个优化步内能训练的 RL 任务量拉到最大。为此，我们把 `AsyncGRPOTrainer` 的 `--token-budget` 参数，在我们的配置下顶到了上限。下图是每个 harness 每步组数的变化（蓝色：Pi，绿色：OpenCode，橙色：Hermes）。

随着模型在训练中越来越强，每个训练步能装下的组越来越多，这让模型在每个优化步拿到的信号也更加多样。

### 最终的数据混合

最终的数据混合，由 750 个来自 [harness-adapters RL 环境](https://huggingface.co/datasets/harness-hub/harness-adapters)的任务和 300 个来自 [termgrade](https://huggingface.co/datasets/ai-and/termgrade-environments) 的任务组成。为了尽量提高训练期间采样任务的多样性，我们对数据采样策略做了一点定制，下面具体说明：

训练开始之前，任务会按家族排成一个固定顺序并交错排列（对我们生成的 RL 环境来说，家族就是任务所在的仓库；Termgrade 则直接按名称排序，因为每个任务都自成一个家族）。这样一来，每个训练步在遵循混合分布的同时，能尽可能多地混入不同的仓库。

### 让 safeagents 参与循环

我们还接入了 [safeagents](https://github.com/huggingface/safeagents) 这个工具，用来在训练期间拦截模型的任何不当行为。最终插件（由针对这些 RL 任务和测试路径的正则与模式规则组成）托管在 [harness-hub/qwen-safeagents-plugin](https://huggingface.co/harness-hub/qwen-safeagents-plugin)，想复现这套训练配置的人，可以直接用最新版 safeagents 开箱使用。

训练过程中，被 safeagents 拦下的工具调用数量持续下降，说明模型在每个优化步之后都变得“更守规矩”。下图是各个 harness 适配器每 1,000 次工具调用中被 safeagents 拦截的调用数，按训练步数统计。

![pi、hermes 和 opencode 适配器按训练步统计的每 1,000 次工具调用中被 safeagents 拦截的调用数](https://huggingface.co/buckets/huggingface/harness-adapters-blog-assets/resolve/images/safeagents-blocked.png)

## Super-adapter：把三个适配器合并成一个

模型合并通常能把各自的能力合到一起，同时保留每个模型原本能做的大部分事情。三个 harness 适配器训练完之后，我们问了两个问题：把它们合并起来会损失精度吗？一个“super-adapter”能否在每个 harness 下都既准确又高效？

我们先逐层比较了三个适配器的权重更新。任意两者之间的余弦相似度只有约 0.01–0.02：训练中每个适配器都把模型推向了一个几乎正交的方向。这是合并最理想的情况，因为更新之间几乎不会互相干扰。

我们沿着 rank 维度把三个 LoRA 适配器拼接起来（PEFT 的 `combination_type="cat"`）。合并后的适配器 rank 为 96（3 × 32），精确施加的是 w · (ΔW_pi + ΔW_hermes + ΔW_opencode)。此前的合并研究（[task arithmetic](https://huggingface.co/papers/2212.04089)、[TIES](https://huggingface.co/papers/2306.01708)、[KnOTS](https://huggingface.co/papers/2410.19735)）发现，把每个更新缩放到 1 以下效果最好，所以我们用第 120 步的适配器，在每个 harness 下对全部 89 个 Terminal-Bench 2.1 任务比较了三种权重：

- ⅓（取平均）：每个 harness 只保留自己更新的三分之一。
- ½：每个更新以一半强度施加。
- 1（直接相加）：每个更新都完整施加。

| 权重 | pi | hermes | opencode | 三个 harness 合计 | 每任务工具调用数 |
| --- | --- | --- | --- | --- | --- |
| 基座模型 | 39.1% | 46.0% | 44.8% | 43.3% | 49.2 |
| ⅓（平均） | 49.4% | 51.2% | 47.1% | 49.2% | 35.6 |
| **½** | 48.8% | 53.5% | 55.2% | **52.5%** | 25.9 |
| 1（求和） | 40.2% | 62.8% | 47.1% | 50.0% | 13.4 |

直接相加会过度施加更新。agent 变得非常短（每任务 13 次工具调用，基座模型是 49 次），Hermes 虽然冲到 62.8% 的峰值，但 pi 掉回了基座模型的水平。取平均则会稀释每个 harness 自己的更新。½ 的平衡最好，所以我们用已发布的 checkpoint（pi 第 160 步、hermes 第 160 步、opencode 第 150 步），以权重 ½ 构建了最终的 super-adapter。

### 适配器合并的评估结果

下表是每个 harness 下、各次运行都评过的那些任务上的结果（SWE-bench Pro 上 50–51 个，Terminal-Bench 2.1 上 82–85 个），每任务一次尝试（括号内是相对基座模型的效率提升）：

| Harness | 基准测试 | [Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B) | Qwen3.8-27B-<harness>-adapted | [Qwen3.8-27B-super-adapter](https://huggingface.co/harness-hub/Qwen3.8-27B-super-adapter) | [Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B)，thinking | [Qwen3.8-27B-super-adapter](https://huggingface.co/harness-hub/Qwen3.8-27B-super-adapter)，thinking |
| --- | --- | --- | --- | --- | --- | --- |
| pi | SWE-bench Pro（困难 51） | 40.0% | 64.0%（−60%） | 46.0%（−73%） | 74.0% | 74.0%（−48%） |
| hermes | SWE-bench Pro（困难 51） | 29.4% | 43.1%（−56%） | 47.1%（−60%） | 45.1% | 60.8%（−36%） |
| opencode | SWE-bench Pro（困难 51） | 35.3% | 51.0%（−72%） | 45.1%（−63%） | 47.1% | 66.7%（−31%） |
| pi | Terminal-Bench 2.1 | 40.0% | 56.5%（−56%） | 48.2%（−56%） | 52.9% | 57.6%（−25%） |
| hermes | Terminal-Bench 2.1 | 44.7% | 58.8%（−70%） | 55.3%（−53%） | 58.8% | 63.5%（−19%） |
| opencode | Terminal-Bench 2.1 | 47.6% | 52.4%（−53%） | 52.4%（−68%） | 54.9% | 58.5%（−22%） |

“Thinking” 指的是聊天模板的 thinking 模式在默认强度（xhigh）下的表现。几个专用适配器的训练和推理都是在关闭 thinking 的情况下进行的。

关闭 thinking 时，super-adapter 在全部六个 harness–基准测试组合上都优于基座模型（平均 pass@1 39.5% → 49.0%；新解出 71 个任务，丢失 34 个，p < 0.001）。

尽管训练时完全没有开启 thinking，它却是我们评估过的开启 thinking 模式里最强的模型。与同等强度开启 thinking 的基座模型相比，它在六个组合中赢下五个、在第六个上打平（平均 55.5% → 63.5%；新解出 67 个，丢失 37 个，p = 0.004）。增益最大的是 SWE-bench Pro：hermes 下 +16 分，opencode 下 +20 分。在 pi 的 SWE-bench Pro 上，单靠 thinking 就已经达到 74%，两者打平。

关闭 thinking 时，就该用专用 harness 适配器。每个 harness 自己的适配器在六个组合中的四个上领先，其中 pi 下领先最多（SWE-bench Pro 上 64.0% 对 46.0%，Terminal-Bench 上 56.5% 对 48.2%）。把一个模型摊到三个 harness 上，pi 损失的增益最多。如果你只用一种 harness，并且保持 thinking 关闭，那就用它对应的专用适配器。

super adapter 的效率也高得多。在基座模型和 super-adapter 都能解出的任务上，关闭 thinking 时，它每任务的工具调用少 53–73%、生成的 token 少 44–60%，在 130 个任务中有 111 个的工具调用更少。开启 thinking 时，它在 SWE-bench Pro 上仍能把工具调用减少 31–48%、token 减少 24–43%；在 Terminal-Bench 上，工具调用减少 19–25%，token 数基本持平。

½ 这个权重是在 Terminal-Bench 2.1 上用第 120 步的适配器选出来的，所以 Terminal-Bench 上的数字略偏乐观；SWE-bench Pro 并没有参与这次选择。完整的配对结果见 [super-adapter 的模型卡](https://huggingface.co/harness-hub/Qwen3.8-27B-super-adapter)。

## 最终结果

本节先讲训练期间发生了什么，再讲适配器在自身 harness 内外的留出基准上得分如何。

### 训练结果

训练累计跑了 598 步，一共训练了 78,114 个样本，正好相当于 167M 个训练 token。

训练期间有一个很明确的信号：模型学会用越来越少的步数解出任务，而且没有明显的饱和迹象。训练正确率虽然偶尔有明显上升，但总体看起来是持平的。这可以解释为：模型在训练中不断遇到新任务，而随着轨迹变短，一步的 token 预算里能装下的组数翻了一倍还多。准确率的提升体现在下一节的留出基准上。

另一方面，safeagents 也拦下了多次可疑尝试。三次训练运行中，一共检查了 1.3M 次工具调用，拦下 647 次。

### 评估结果

本节涵盖评估设置、harness 内的结果、跨 harness 的迁移，以及一项分布外检查。

#### 评估设置

我们把每个适配器都放在它自己训练所用的 harness 里评估，用的是两个 agentic coding 基准：完整的 89 个 [Terminal-Bench 2.1](https://huggingface.co/datasets/harborframework/terminal-bench-2.1) 任务（每任务 1 小时、100 个 agent 步），以及 SWE-bench Pro 最难的 51 个任务（2 小时、100 个 agent 步）。每任务的 token 上限设为 131072。我们不调整 agent 设置，所有 harness 都用默认配置。举个例子，Pi 不保留之前的推理轮次，而 OpenCode 和 Hermes 会保留，这主要会影响 SWE-bench Pro 的结果，因为上下文会很快溢出。因此你不能跨 harness 横向比较（用 Pi 不一定就比 Hermes 或 OpenCode 结果更好），但在同一个 harness 内部比较并下结论是公平的。

每次 rollout 都走与训练相同的 Harbor 和 OpenEnv 栈，在 HF sandbox 中运行，每任务一次尝试，温度 0.8，关闭 thinking。每个 LoRA checkpoint 都会合并进基座权重，单独用单卡 vLLM 提供服务，并发数与基座模型评估时相同。

对所有评估基准，我们既报告 pass@1，也报告工具调用次数和总轮数，并且都分全部任务与已解出任务两组。

为了公开透明，最终评估的全部模型轨迹都推送到了这个公共 bucket：[harness-hub/harness-adapters-trajectories](https://huggingface.co/buckets/harness-hub/harness-adapters-trajectories)。

#### 最终评估结果

三个专用适配器在各自的 harness 下、在两个基准上都胜过基座模型。在 SWE-bench Pro（困难 51）上，pi 从 39.2% 升到 64.7%（+25.5 分：新解出 15 个任务，丢失 2 个，p = 0.002），hermes 从 29.4% 到 43.1%，opencode 从 35.3% 到 51.0%。在完整的 Terminal-Bench 2.1 上，pi 提升 +16.3 分（16 对 2，p = 0.001），hermes 提升 +14.1（19 对 7，p = 0.03）。Opencode 总体提升 +6.0，在未参与其 checkpoint 选择的 66 个任务上提升 +13.6（12 对 3，p = 0.035）。

适配器解题的效率也高得多：在它们与基座模型都能解出的任务上，SWE-bench Pro 上每任务的工具调用少 56–72%，Terminal-Bench 2.1 上少 53–70%。单一的 super-adapter 在三个 harness 下同样都胜过基座模型（SWE-bench Pro 上 +6 到 +18 分，Terminal-Bench 2.1 上 +5 到 +10），工具调用的削减幅度也一样大（53–73%）。关闭 thinking 时，它保住的各专用适配器增益比较少，其中 pi 下最少；但开启 thinking 时，它在六个 harness–基准组合中的五个上，都胜过同等强度的基座模型 thinking（见 [super-adapter 一节](https://huggingface.co/blog/harness-adapters-at-scale#super-adapter-merging-all-adapters-into-one)）。每个模型卡里都有完整的配对结果。

#### 效率与性能能否跨 harness 迁移？

为了回答这个问题，我们还把 pi harness 适配器放到 Hermes Agent 和 OpenCode 下做了评估。

在 OpenCode 下，它在 Terminal-Bench 2.1 上与 OpenCode 自己的专用适配器相当（44.8% → 54.0%，对方是 46.4% → 52.4%）。在 Hermes 下，它保住了专用适配器约三分之二的增益（46.3% → 56.1%，对方是 44.7% → 58.8%），两者工具调用的削减幅度都约为 45%。这么看，新学到的能力似乎是可以跨 harness 迁移的。

#### 在分布外任务与配置上的评估

如果把评估放到分布外任务、放到适配器训练时没碰过的 harness 之外，会发生什么？

我们让五个模型都在 300 个 [AutomationBench 任务](https://github.com/zapier/AutomationBench)上跑了一遍。这批任务由业务自动化工作流评估组成，用的是 AutomationBench 自己的 agent 循环，而不是 Pi、Hermes 或 OpenCode。这样我们可以交叉验证两个不同的问题：模型能否解决 SWE 相关之外的问题？把模型放到它训练时所用 harness 之外，又会发生什么？

结果显示，适配器与基座模型相差不大。Pi 和 OpenCode 略占优（27.0% 和 25.3% 的 pass@1，基座是 23.0%），合并适配器基本持平（23.7%），Hermes 落后几分（17.7%）。除 Hermes 之外，差异都在噪声范围内。所以，harness 内的 RL 既没有明显迁移到这个差别很大的场景，也没有把模型搞坏。

| --- | --- | --- | --- | --- |
| base | 23.0% |  | 62.2% |  |
| pi 160 | 27.0% | +4.0 | 66.2% | +4.0 |
| opencode 150 | 25.3% | +2.3 | 65.2% | +3.0 |
| merged | 23.7% | +0.7 | 60.6% | −1.6 |

## 开放问题：模型究竟学会了做什么？

我们很感谢用户和社区的反馈。社区最初的测试和结果总体上非常积极，我们也希望未来继续沿着这个方向做下去。我们也看到了一些意外的结果，比如有用户反馈 [harness 适配器在 Qwen3.8 的衍生模型（例如 Swift-1.5）上效果很好](https://huggingface.co/harness-hub/Qwen3.8-27B-opencode-adapted-GGUF/discussions/2)。

这个问题是我们在发布之后一直在想的开放问题。仔细检查评估基准生成的轨迹之后可以看出，模型在非 thinking 模式下，倾向于在提出工具调用之前先写一小段文字，而基座模型几乎不铺垫任何文字，直接就发出工具调用。

这种现象可以看作一种“推理泄漏”：模型学会了通过生成一些有时候看起来像推理痕迹的文字（例如 ..wait? ..let me see 之类），从它的非 thinking 版本“逃逸”到 thinking 版本。[最近的一篇论文](https://huggingface.co/papers/2610.14270)也很好地描述了 LLM 在 RL 阶段的行为。

这是否让我们的模型失效了？我们不这么看，因为最终结果依然成立：在完全相同的条件下（固定的 token 预算），我们的适配器确实（远远）优于基座的非 thinking 模型，并且追平 thinking 版本的表现，同时 token 效率高得多。社区给出的正面反馈也进一步印证了这一点。

不过这提示我们需要一项正式的后续工作：我们会尝试把同一套流水线用到纯 thinking 模型上，并探索 thinking / 非 thinking 混合训练，以更好地理解 RL 训练在混合 thinking 模型上的行为。等拿到确凿的结论，我们会把后续的发现（以及 harness 适配器）分享给社区。

## 结语与未来方向

通过这项工作我们证明了：在目标 harness 内对模型做 RL 训练，在相同条件下评估时能得到更高效、因而也更准确的最终模型。这个观察与 Hugging Face 团队此前的多项工作一脉相承，比如 [multi-harness-RL](https://huggingface.co/spaces/FineEnvs/multi-harness-rl) 或者 [harness 适配器的早期版本](https://huggingface.co/blog/harness-hub/harness-adapters)。

未来，我们会把这套配方用到更多模型上，同时更深入地研究 thinking / 非 thinking 混合模型的训练策略。

我们也会把完整的配方和流水线公开分享给社区，方便复现全部流程，并邀请每个人从自己的代码库或任何相关材料出发，构建自己的 RL 任务，然后把同样的训练配方和思路用到自己最喜欢的模型和 harness 上，得到更高效的 agentic 模型。我们希望这篇博客能成为构建者今后构建并分享自己的 harness 适配器的起点。
