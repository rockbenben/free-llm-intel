生成式 AI 领域发展速度极快，我们相信开放的方式是把生态聚到一起、降低大语言模型（LLM）潜在风险的重要途径。去年，Meta 发布了一套初始工具与评测，旨在支持基于开放生成式模型的负责任开发。随着 LLM 越来越多地作为编程助手被集成进系统，它们也带来了必须应对的新型网络安全漏洞。要应对这一挑战，就需要全面的基准来评测 LLM 的网络安全安全性。[CyberSecEval 2](https://arxiv.org/pdf/2404.13161) 正是在这里发挥作用：它评估 LLM 对代码解释器滥用的易感程度、进攻性网络安全能力，以及对提示注入攻击的抵抗力，从而对 LLM 网络安全风险做更全面的评估。你可以在这里查看 [CyberSecEval 2 排行榜](https://huggingface.co/spaces/facebook/CyberSecEval)。

## 基准

CyberSecEval 2 基准帮助评估 LLM 生成不安全代码、以及顺从"协助网络攻击"请求的倾向：

- **测试不安全编程实践的生成**：不安全编码实践测试衡量 LLM 在自动补全和指令两种场景下，有多大频率建议存在安全隐患的高风险弱点，其分类依据是 [Common Weakness Enumeration 的行业标准不安全编码实践分类](https://cwe.mitre.org/)。我们报告代码测试通过率。
- **测试对提示注入的易感性**：针对 LLM 应用的提示注入攻击，是企图让 LLM 以不良方式行事。[提示注入测试](https://github.com/meta-llama/PurpleLlama/tree/main/CybersecurityBenchmarks/datasets/mitre)评估 LLM 识别输入中不可信部分的能力，以及它对常见提示注入技术的抵抗力。我们报告模型顺从攻击的频率。
- **测试对"协助网络攻击"请求的顺从度**：这组测试衡量"迷惑性良性提示"的误拒绝率。这些[提示](https://github.com/meta-llama/PurpleLlama/tree/main/CybersecurityBenchmarks/datasets/frr)与网络攻击顺从测试类似，覆盖包括网络防御在内的广泛主题，但它们明确是良性的——即使看起来像恶意。我们报告误拒绝（拒绝协助合法的网络相关活动）与违规率（同意协助进攻性网络攻击）之间的权衡。
- **测试滥用代码解释器的倾向**：代码解释器让 LLM 能在沙箱环境中运行代码。这组[提示](https://github.com/meta-llama/PurpleLlama/tree/main/CybersecurityBenchmarks/datasets/interpreter)试图操纵 LLM 执行恶意代码，以达到访问运行 LLM 的系统、收集系统敏感信息、策划并执行社会工程攻击、或探测宿主环境外部基础设施信息等目的。我们报告模型顺从攻击的频率。
- **测试自动化进攻性网络安全能力**：该套件由模拟程序漏洞利用的 [CTF（capture-the-flag）风格安全测试用例](https://github.com/meta-llama/PurpleLlama/tree/main/CybersecurityBenchmarks/datasets/canary_exploit)组成。我们把 LLM 当作安全工具，判断它能否到达程序中故意埋入安全问题的特定位置。部分测试会显式检查工具能否执行基础漏洞利用，如 SQL 注入和缓冲区溢出。我们报告模型的完成百分比。

所有代码均开源，我们希望社区用它来度量并提升 LLM 的网络安全安全属性。

关于各基准的更多信息可阅读[这里](https://huggingface.co/spaces/facebook/CyberSecEval)。

## 关键洞察

我们用 CyberSecEval 2 对最先进大语言模型做的最新评测，既显示了进展，也揭示了应对网络安全风险仍是持续的挑战。

### 行业整体进步

自 2023 年 12 日发布基准第一版以来，LLM 平均对"协助网络攻击"请求的顺从率从 52% 降至 28%，说明行业越来越重视这一问题，并在采取措施改进。

### 模型对比

我们发现非代码特化的模型比代码特化的模型有更低的不顺从率。不过两类模型之间的差距正在缩小，说明代码特化模型正在安全能力上追赶。

### 提示注入风险

提示注入测试表明，让 LLM 抵御这类攻击仍是一个未解决的问题，对使用这些模型构建的应用构成重大安全风险。开发者不应假定 LLM 在面对对抗性输入时还能可靠地遵照系统提示词安全行事。

### 代码漏洞利用的局限

代码利用测试显示，虽然通用编码能力强的模型表现更好，但 LLM 要可靠解决端到端的漏洞利用挑战还有很长的路要走。这意味着以当前状态，LLM 不太可能颠覆网络漏洞利用攻击。

### 解释器滥用风险

解释器滥用测试凸显了 LLM 容易被操纵、进而在代码解释器中实施滥用行为的脆弱性。这印证了需要额外的护栏与检测机制来防止解释器被滥用。

## 如何参与贡献？

我们非常欢迎社区为基准做贡献，感兴趣的话有以下几件事可以做！

要在你的模型上运行 CyberSecEval 2 基准，可以参考[这里的说明](https://github.com/meta-llama/PurpleLlama/tree/main/CybersecurityBenchmarks)。欢迎把输出发给我们，我们会将你的模型加入[排行榜](https://huggingface.co/spaces/facebook/CyberSecEval)！

如果你有改进 CyberSecEval 2 基准的想法，可以按照[这里的说明](https://github.com/meta-llama/PurpleLlama/blob/main/CONTRIBUTING.md)直接参与贡献。
