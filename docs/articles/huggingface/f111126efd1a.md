### 引言

尽管来自 PyTorch 和 JAX 的竞争日益加剧，TensorFlow 仍是 [使用最广泛的深度学习框架](https://twitter.com/fchollet/status/1478404084881190912?lang=en)。它也在一些非常重要的方面与那两个库不同。尤其地，它与自己的高层 API `Keras` 以及数据加载库 `tf.data` 集成得很紧。

PyTorch 工程师有一种倾向（想象我隔着开放式办公室阴郁地盯着这边），把这视为一个要克服的问题；他们的目标是想方设法让 TensorFlow 别碍事，好让他们能用自己习惯的低层训练和数据加载代码。这完全是接触 TensorFlow 的错误方式！Keras 是一个很棒的高层 API。如果在一个超过几个模块的项目里把它推开，你最终会在意识到自己需要它时，重新实现它大部分功能。

作为精锐、受人尊敬且极具魅力的 TensorFlow 工程师，我们想用前沿模型那惊人的能力和灵活性，但我们想用我们熟悉的工具和 API 来处理它们。这篇博客将谈我们在 Hugging Face 为此所做的取舍，以及作为 TensorFlow 程序员对该框架应有什么预期。

### 插曲：30 秒了解 🤗

有经验的用户可以随意略读或跳过这一节，但如果这是你第一次接触 Hugging Face 和 `transformers`，我应该先给你一个库的核心思想概览：你只要按名字要一个预训练模型，一行代码就拿到。最简单的方式是直接用 `TFAutoModel` 类：

```
from transformers import TFAutoModel

model = TFAutoModel.from_pretrained("bert-base-cased")
```

这一行会实例化模型架构并加载权重，给你一个与原始著名 [BERT](https://arxiv.org/abs/1810.04805) 模型完全一致的复制品。不过这个模型单靠自己没什么用——它缺一个输出头和一个损失函数。实际上它是神经网络的"干"，刚好停在最后一个隐藏层之后。那怎么给它加输出头？很简单，用另一个 `AutoModel` 类即可。这里我们加载 [Vision Transformer (ViT)](https://arxiv.org/abs/2010.11929) 模型并加一个图像分类头：

```
from transformers import TFAutoModelForImageClassification

model_name = "google/vit-base-patch16-224"
model = TFAutoModelForImageClassification.from_pretrained(model_name)
```

现在我们的 `model` 有了一个输出头，以及（可选地）一个适配新任务的损失函数。如果新输出头与原始模型不同，那么它的权重会被随机初始化。其余权重都从原始模型加载。但我们为什么这么做？为什么用一个已有模型的"干"，而不干脆从零搭一个我们需要的模型？

事实证明，在大量数据上预训练的大模型，对几乎任何 ML 问题来说，都比简单的随机初始化权重这种标准方法要好得多的起点。这叫 **迁移学习**，而如果你想想，它是有道理的——把一个文本任务做好需要对语言有一些知识，把一个视觉任务做好需要对图像和空间有一些知识。没有迁移学习时 ML 如此吞数据的原因很简单：每个问题都得从头重学这些基础领域知识，这就需要海量训练样本。而用了迁移学习，原本可能需要一百万样本才能解决的问题，一千个样本就能解决，而且往往最终准确率更高。关于这个主题的更多内容，看看 [Hugging Face 课程](https://www.youtube.com/watch?v=BqqfQnyjmgg) 的相关章节！

然而使用迁移学习时，让输入按训练时的处理方式被处理非常重要。这样当我们把模型知识迁移到新问题时，模型需要重学的就尽可能少。在 `transformers` 里，这种预处理通常由 **分词器（tokenizers）** 处理。分词器可以像模型一样用 `AutoTokenizer` 类加载。务必加载与你要使用的模型匹配的分词器！

```
from transformers import TFAutoModel, AutoTokenizer

# Make sure to always load a matching tokenizer and model!
tokenizer = AutoTokenizer.from_pretrained("bert-base-cased")
model = TFAutoModel.from_pretrained("bert-base-cased")

# Let's load some data and tokenize it
test_strings = ["This is a sentence!", "This is another one!"]
tokenized_inputs = tokenizer(test_strings, return_tensors="np", padding=True)

# Now our data is tokenized, we can pass it to our model, or use it in fit()!
outputs = model(tokenized_inputs)
```

这当然只是库的一点滋味——想要更多，可以查看我们的 [notebooks](https://huggingface.co/docs/transformers/notebooks) 或 [代码示例](https://github.com/huggingface/transformers/tree/main/examples/tensorflow)。还有若干其他 [库实际使用的示例在 keras.io 上](https://keras.io/examples/#natural-language-processing)！

此刻你已经理解了 `transformers` 里一些基础概念和类。我上面写的一切都是框架无关的（除了 `TFAutoModel` 里的 "TF"），但当你实际要训练和部署模型时，各框架之间就会开始分道。这就把我们引向本文的主焦点：作为一个 TensorFlow 工程师，你对 `transformers` 应有什么期待？

#### 理念 #1：所有 TensorFlow 模型都应是 Keras Model 对象，所有 TensorFlow 层都应是 Keras Layer 对象。

对一个 TensorFlow 库这几乎不言而喻，但仍值得强调。从用户视角，这个选择最重要的影响是你可以直接在我们的模型上调用 `fit()`、`compile()` 和 `predict()` 等 Keras 方法。

例如，假设你的数据已经准备好并分词，那么用 TensorFlow 从序列分类模型拿预测就这么简单：

```
model = TFAutoModelForSequenceClassification.from_pretrained(my_model)
model.predict(my_data)
```

而如果你想训练那个模型，也只是：

```
model.fit(my_data, my_labels)
```

不过这种便利并不意味着你被限制在我们开箱支持的任务上。Keras 模型可以作为层组合进其他模型里，所以如果你有一个把五个不同模型拼接在一起的宏大银河大脑构想，没有什么能阻止你，除了也许你那点 GPU 显存。也许你想把一个预训练语言模型和一个预训练视觉 transformer 合并成一个混合体，像 [Deepmind 最近的 Flamingo](https://arxiv.org/abs/2204.14198)，或者你想打造下一个病毒式文生图爆款，像 Dall-E Mini [Craiyon](https://www.craiyon.com/)？下面是用 Keras [子类化](https://www.tensorflow.org/guide/keras/custom_layers_and_models) 做一个混合模型的示例：

```
class HybridVisionLanguageModel(tf.keras.Model):
  def __init__(self):
    super().__init__()
    self.language = TFAutoModel.from_pretrained("gpt2")
    self.vision = TFAutoModel.from_pretrained("google/vit-base-patch16-224")

  def call(self, inputs):
    # I have a truly wonderful idea for this
    # which this code box is too short to contain
```

#### 理念 #2：默认提供损失函数，但可以轻松更换。

在 Keras 里，训练模型的标准方式是创建模型，然后用优化器和损失函数 `compile()`，最后 `fit()`。用 transformers 加载模型很容易，但设置损失函数可能很棘手——即便是标准语言模型训练，你的损失函数也可能出奇地不直观，而一些混合模型有极其复杂的损失。

我们的解法很简单：如果你 `compile()` 时不带损失参数，我们会给你你大概想要的那个。具体地，我们给出一个既匹配你的基座模型又匹配输出类型的损失——如果你对基于 BERT 的掩码语言模型 `compile()` 而不带损失，我们会给你一个正确处理 padding 和 masking、只对被损坏的 token 计算损失、与原始 BERT 训练过程完全一致的掩码语言建模损失。如果出于某种原因你真的、真的不想让模型编译时带任何损失，那就在编译时显式指定 `loss=None`。

```
model = TFAutoModelForQuestionAnswering.from_pretrained("bert-base-cased")
model.compile(optimizer="adam")  # No loss argument!
model.fit(my_data, my_labels)
```

但同样、而且非常重要的是，一旦你想做更复杂的事，我们就想别碍事。如果你对 `compile()` 指定了损失参数，模型就会用那个而不是默认损失。而且当然，如果你做一个自己的子类化模型，比如上面的 `HybridVisionLanguageModel`，你就通过自己编写的 `call()` 和 `train_step()` 方法对模型功能的每个方面拥有完全控制。

#### 理念实现细节 #3：Labels 很灵活

过去一个让人困惑的点是标签到底该怎样传给模型。把标签传给 Keras 模型的标准方式是作为单独的参数，或作为 (inputs, labels) 元组的一部分：

```
model.fit(inputs, labels)
```

过去，在使用默认损失时我们反而请用户在输入字典里传标签。原因是计算该特定模型损失的代码包含在 `call()` 前向方法里。这能用，但对 Keras 模型而言绝对是非标准的，并引起若干问题，包括与标准 Keras 指标的不兼容，更不用说一些用户的困惑。所幸，这不再必要了。我们现在推荐按标准 Keras 方式传标签，尽管出于向后兼容，旧方法仍然可用。总的来说，很多过去繁琐的事情现在对我们的 TensorFlow 模型"能用就行"——试一下！

#### 理念 #4：你不该非得自己写数据流水线，尤其是对常见任务

除了 `transformers`（一个巨大的预训练模型开放仓库），还有 🤗 `datasets`，一个巨大的数据集开放仓库——文本、视觉、音频及更多。这些数据集能轻松转换为 TensorFlow Tensor 和 Numpy 数组，便于用作训练数据。下面是一个快速示例，展示我们如何对一个数据集分词并转成 Numpy。一如既往，确保你的分词器与你要训练的模型匹配，否则事情会变得很奇怪！

```
from datasets import load_dataset
from transformers import AutoTokenizer, TFAutoModelForSequenceClassification
from tensorflow.keras.optimizers import Adam

dataset = load_dataset("glue", "cola")  # Simple text classification dataset
dataset = dataset["train"]  # Just take the training split for now

# Load our tokenizer and tokenize our data
tokenizer = AutoTokenizer.from_pretrained("bert-base-cased")
tokenized_data = tokenizer(dataset["text"], return_tensors="np", padding=True)
labels = np.array(dataset["label"]) # Label is already an array of 0 and 1

# Load and compile our model
model = TFAutoModelForSequenceClassification.from_pretrained("bert-base-cased")
# Lower learning rates are often better for fine-tuning transformers
model.compile(optimizer=Adam(3e-5))

model.fit(tokenized_data, labels)
```

这种方法能用时很好，但对更大的数据集你会发现它开始成为问题。为什么？因为分词后的数组和标签必须全部加载进内存，而 Numpy 不处理"参差"数组，所以每个分词样本都必须填充到整个数据集里最长样本的长度。这会让你的数组更大，而所有那些 padding token 也会拖慢训练！

作为 TensorFlow 工程师，这正是你通常转向 `tf.data` 做一个流水线、从存储流式加载而非全部载入内存的地方。但那很麻烦，所以我们替你办好了。首先，用 `map()` 方法把分词器的列加到数据集。记住我们的数据集默认是磁盘存放的——在你把它们转成数组之前不会载入内存！

```
def tokenize_dataset(data):
    # Keys of the returned dictionary will be added to the dataset as columns
    return tokenizer(data["text"])

dataset = dataset.map(tokenize_dataset)
```

现在我们的数据集有了想要的列，但我们如何在其上训练？很简单——用一个 `tf.data.Dataset` 包装它，所有问题就都解决了——数据即时加载，而 padding 只施加到批次而非整个数据集，这意味着我们需要少得多的 padding token：

```
tf_dataset = model.prepare_tf_dataset(
    dataset,
    batch_size=16,
    shuffle=True
)

model.fit(tf_dataset)
```

为什么 [prepare_tf_dataset()](https://huggingface.co/docs/transformers/main/en/main_classes/model#transformers.TFPreTrainedModel.prepare_tf_dataset) 是你模型上的一个方法？简单：因为你的模型知道哪些列是有效的输入，并会自动过滤掉不是有效输入名的数据集列！如果你宁愿对正在创建的 `tf.data.Dataset` 有更精确的控制，可以用更底层的 [Dataset.to_tf_dataset()](https://huggingface.co/docs/datasets/main/en/package_reference/main_classes#datasets.Dataset.to_tf_dataset)。

#### 理念 #5：XLA 很棒！

[XLA](https://www.tensorflow.org/xla) 是 TensorFlow 和 JAX 共享的即时编译器。它把线性代数代码转换成运行更快、用内存更少的优化版本。它真的很酷，我们尽量确保支持它。它对让模型在 TPU 上运行极其重要，但即便对 GPU 乃至 CPU 也能提速！要使用它，只需在 `compile()` 模型时带 `jit_compile=True` 参数（这对所有 Keras 模型都有效，不只是 Hugging Face 的）：

```
model.compile(optimizer="adam", jit_compile=True)
```

最近我们在这一领域做了若干重大改进。最显著的是，我们更新了 `generate()` 代码以使用 XLA——这是一个从语言模型迭代生成文本输出的函数。这带来了巨大的性能提升——我们旧的 TF 代码比 PyTorch 慢得多，但新代码比它快得多，速度上与 JAX 相当！更多信息请看 [我们关于 XLA 生成的博客](https://huggingface.co/blog/tf-xla-generate)。

XLA 除了生成之外也很有用！我们也做了若干修复以确保你能用 XLA 训练模型，结果是我们的 TF 模型在语言模型训练等任务上达到了 JAX 级别的速度。

需要讲清楚 XLA 的主要局限：XLA 期望输入形状是静态的。这意味着如果你的任务涉及可变序列长度，你需要为传给模型的每个不同输入形状重新做一次 XLA 编译，这会抵消性能收益！你可以在我们的 [TensorFlow notebooks](https://huggingface.co/docs/transformers/notebooks) 以及上面的 XLA 生成博客中看到我们如何处理这个问题的若干示例。

#### 理念 #6：部署和训练一样重要

TensorFlow 拥有丰富的生态，尤其围绕模型部署，这是其他更偏研究的框架所缺乏的。我们正在积极让你能用这些工具部署整个模型做推理。我们特别有兴趣支持 `TF Serving` 和 `TFX`。如果这对你有意义，请看 [我们关于用 TF Serving 部署模型的博客](https://huggingface.co/blog/tf-serving-vision)！

然而部署 NLP 模型的一个主要障碍是输入仍然需要分词，这意味着光部署模型还不够。对 `tokenizers` 的依赖在很多部署场景里很烦人，所以我们正在努力让把分词嵌入模型本身成为可能，让你只部署单个模型产物就能处理从输入字符串到输出预测的整条流水线。目前我们只支持最常见的模型如 BERT，但这是一个活跃的工作方向！如果你想试试，可以用这样的代码片段：

```
# This is a new feature, so make sure to update to the latest version of transformers!
# You will also need to pip install tensorflow_text

import tensorflow as tf
from transformers import TFAutoModel, TFBertTokenizer


class EndToEndModel(tf.keras.Model):
    def __init__(self, checkpoint):
        super().__init__()
        self.tokenizer = TFBertTokenizer.from_pretrained(checkpoint)
        self.model = TFAutoModel.from_pretrained(checkpoint)

    def call(self, inputs):
        tokenized = self.tokenizer(inputs)
        return self.model(**tokenized)

model = EndToEndModel(checkpoint="bert-base-cased")

test_inputs = [
    "This is a test sentence!",
    "This is another one!",
]
model.predict(test_inputs)  # Pass strings straight to model!
```

#### 结论：我们是一个开源项目，而这意味着社区就是一切

做了一个很酷的模型？分享它！一旦你 [创建账号并设置好凭证](https://huggingface.co/docs/transformers/main/en/model_sharing)，就简单到：

```
model_name = "google/vit-base-patch16-224"
model = TFAutoModelForImageClassification.from_pretrained(model_name)

model.fit(my_data, my_labels)

model.push_to_hub("my-new-model")
```

你也可以用 [PushToHubCallback](https://huggingface.co/docs/transformers/main_classes/keras_callbacks#transformers.PushToHubCallback) 在更长的训练运行中定期上传检查点！无论哪种方式，你都会得到一个模型页和一张自动生成的模型卡，而最重要的是，其他任何人都能用你的模型获取预测，或作为进一步训练的起点，使用与他们加载任何已有模型时完全相同的 API：

```
model_name = "your-username/my-new-model"
model = TFAutoModelForImageClassification.from_pretrained(model_name)
```

我觉得"著名的基础模型"和"单个用户微调出的模型"之间没有区别这一事实，体现了 Hugging Face 的核心理念——用户建造伟大事物的力量。机器学习从来不该是少数几家公司在闭源模型里涓滴出的成果；它应当是一组开放的工具、产物、实践和知识的集合，不断被扩充、测试、批评和在之上构建——是集市，不是大教堂。如果你灵光一现有了一个新想法、新方法，或者你训练出一个表现很棒的新模型，告诉所有人！

而同样地，有没有你缺少的东西？Bug？烦心事？本该直观却直观不起来的东西？告诉我们！如果你愿意拿一把（比喻意义的）铲子开始修，那就更好，但即便你没有时间或技能栈去亲自改进代码库，也别羞于发声。很多时候，正因用户不提出问题，核心维护者才会漏掉问题，所以别假设我们一定知道某件事！如果它困扰着你，请在 [论坛](https://discuss.huggingface.co/) 上提问，如果你相当确信那是一个 bug 或缺了一个重要特性，就 [提一个 issue](https://github.com/huggingface/transformers)。

这些东西里很多是小细节没错，但造一个（相当笨拙的）短语来说，伟大的软件是由上千个小提交做出来的。正是在用户和维护者持续不断的集体努力下，开源软件才得以改进。机器学习将成为 2020 年代一个重大的社会议题，而开源软件和社区的力量将决定它成为一个开放、民主、可被批评和重新评估的力量，还是被那些巨型黑盒模型所主宰——它们的拥有者不容许局外人，即便是那些被模型做出决策的人，去窥见他们宝贵的专有权重。所以别害羞——如果有东西不对，如果你有办法让它做得更好，如果你想贡献却不知从何下手，告诉我们！

（而且如果你的炫酷新特性被合入之后，还能做一个梗图去调侃 PyTorch 团队，那就再好不过了。）
