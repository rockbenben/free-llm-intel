## 概述

AI 评估影响着人们构建、采用和信任哪些系统。一项评估会向系统布置任务、检查它的回答或动作,并给出一个分数。因此,构建和维护一套有用的评估是实打实的工作:定义能体现领域专业性的任务、可靠地给它们打分,并核查结果是否支撑所提出的主张。当方法、代码和数据都留在私有状态时,别人要审视这些工作、或者在其上继续搭建,都会更难。

开源提供了一条路径,让我们能构建更强、更新更频繁、也更可比的评估,以及围绕它们的配套基础设施。既有的任务、环境和工具给构建者一个起点,这样他们的精力就能花在领域专业性和验证上。把一项评估是怎么建起来的分享出来——包括哪里搞错了——能让别人发现错误、改进它、复用它。

Hugging Face Hub 是 AI 评估的家园:我们托管着大约 3500 个评估排行榜,过去一年 Hub 上的[评估数据集增长了约 16 倍](https://huggingface.co/spaces/huggingface/hub-stats),达到约 17000 个。近几个月,我们还加入了对与评估相关的 agentic 抽象的支持。例如,[Traces](https://huggingface.co/docs/hub/en/agent-traces)以易于审阅和分享的方式保存 agent 的工作过程;[Benchmarks](https://huggingface.co/datasets?benchmark=benchmark%3Aofficial)突出展示用于配合排行榜评估模型的数据集;[Environments](https://huggingface.co/blog/rl-environments)则展示被用作 agentic RL 环境或评估环境的数据集。

本指南涵盖四件事:

- [**评估的三个时代**](https://huggingface.co/blog/agentic-evals#1-introduction-how-evaluation-design-has-changed)(第 1 节)。评估从检查答案,发展到检查 agent 做了什么,再发展到检查一组 agent 共同产出了什么。每前进一步,都会多出一层可能改变分数的软件。
- [**agentic 评估的各个步骤**](https://huggingface.co/blog/agentic-evals#2-building-an-eval-what-to-reuse-adapt-and-validate)(第 2 节)。我们带着一个任务走完八个步骤,从主张一路走到报出的分数。带命令的完整演练见[附录 A](https://huggingface.co/blog/agentic-evals#appendix-a-practical-example-agentic-deployment-in-a-physics-lab)。
- [**当基准出错时**](https://huggingface.co/blog/agentic-evals#3-bitter-lessons-when-a-benchmark-is-wrong)(第 3 节)。任务和评分器里的错误很常见。我们来看看它们是怎么被发现和纠正的。
- [**哪些该有策略地开放,以及为什么**](https://huggingface.co/blog/agentic-evals#4-open-sourcing-an-evaluation-strategically)(第 4 节)。一张表按组件逐项列出:什么可以分享,什么可以继续保持受保护。

> 在研究社区里,AI 评估的术语出了名地不统一。文末的术语表定义了我们使用的每个术语,并注明了你可能遇到的其他叫法。

## 1. 引言:评估设计如何演变

随着语言模型能力增强、能承担更复杂的工作,AI 评估设计演化出三种形态:问答、agentic,以及团队与群体(teams/swarms)。[MMLU](https://huggingface.co/papers/2009.03300)(2020)和 [GPQA](https://huggingface.co/papers/2311.12022)(2023)这类问答型基准,通过模型给出的答案来衡量知识与推理能力。当模型具备了规划和调用工具的能力后,[SWE-bench](https://huggingface.co/papers/2310.06770)和 [WebArena](https://huggingface.co/papers/2307.13854)这类 agentic 基准把范围扩展到解决软件问题、以及在网站上完成任务。这些任务要求评估设置能够考虑系统运行所处的环境,以及它对环境造成的改动。

最近,多 agent 系统的研究开始加入另一个维度:agent 之间如何协同,以及它们共同达成了什么。这包括[去中心化的群体(swarms)](https://huggingface.co/papers/2505.04364)、[由编排器管理的团队](https://aclanthology.org/2026.findings-emnlp.662/),以及[在科学工作中协作的专用 agent](https://arxiv.org/abs/2610.07763)。图 1 粗略勾勒了这三个评估时代的时间线。

*图 1. 语言模型评估的三种类型。问答型基准拿回答对照标准答案。agentic 基准检查 agent 在环境中改动了什么。团队与群体基准则对一组 agent 的产出打分。*

本文聚焦 agentic 评估,原因有两个。第一,由于用户和企业对 agentic 部署兴趣浓厚,它正日益成为[模型发布公告](https://claude.ai/artifact/22cBPJt6Aos6bYpjmB1BHw#distribution)中最主流的类型。第二,它为了解评估设计如何影响模型表现提供了一个有用的起点。团队与群体评估会因 agent 之间的交互引入更多复杂度,这部分我们不在本指南讨论范围内。一旦 agent 用工具完成任务,周边软件的每一个部分都可能影响它的分数。举例来说,在一项[对 Terminal-Bench 的审计](https://icml.cc/virtual/2026/82793)中,研究者固定模型不变、只更换 agent harness,准确率变化最高达到 29.9 个百分点。要理解这样的差异,我们得剖析一项 agentic 评估的构造,并跟踪一个任务:从 agent 收到的指令,一直到判定它是否通过的检查。

### agentic 评估的构造

*图 2. agentic 评估的各个组成部分。*

一项 agentic 评估由多个部分组成。任务(task)把指令交给 agent。agent harness 把模型和它的工具包在一起,让它在锁定版本的环境里工作。在一次 rollout 中,agent 从头到尾尝试完成任务:它可能运行若干条命令、查看输出,在停下来之前再试一次。评估 harness 会为每个任务运行多次 rollout。rollout 结束时,校验器(verifier)对环境的最终状态打分。每次 rollout 还会留下一份 trace,而 trace 与分数一起构成最终公布的证据。每个部分都可以单独发布、单独审阅、单独复用。

### 为什么基准的发布决策很重要

对独立评估的需求正在增长。政策制定者、企业和研究者都想要他们能够核验的评估,而今天他们大多做不到:[98.2% 的模型-基准分数只有一方在报告](https://huggingface.co/papers/2606.09809),研究者也已论证过[内部自评并不够](https://huggingface.co/papers/2503.16861)。

与此同时,越来越多的基准选择暂不公开一部分测试条目,以减少污染(contamination):也就是问题或解答进入训练数据,使分数可能反映的是此前的接触而非能力。Artificial Analysis 表示,其 2026 年 10 月发布的 [Intelligence Index v5 中有 60%](https://x.com/ArtificialAnlys/status/2115265133467635877)建立在带有私有测试集或留出答案的评估之上。Google DeepMind 最近试点了[双盲评估](https://deepmind.google/blog/piloting-the-worlds-first-double-blind-ai-evaluations/):由一个安全飞地(secure enclave)对模型提供方隐藏外部评估者的测试提示词,同时对评估者隐藏模型的权重。这确实能减少污染,但仅靠保密并不保证质量,而扣住支撑材料会让专家审阅变得更难。我们认为,构建者可以、也应该继续分享基础设施、评分方法和关于任务设计的证据。要有人来审视,就得给别人质疑这套测量、纠正错误的途径——在公开不合适的地方,至少要有受控的审阅。

## 2. 构建评估:复用什么、改造什么、验证什么

有了这幅构造图,我们来为一个真实场景构建一项 agentic 评估:一个为物理实验室分析测量数据的 agent。我们没有从零开始,而是改造一个公开任务,这样大部分精力都花在领域专业性和验证上。

我们依次走完八个步骤:[定义主张](https://huggingface.co/blog/agentic-evals#step-1-define-the-claim)、[找到一个任务](https://huggingface.co/blog/agentic-evals#step-2-find-a-starting-task)、[原样运行它](https://huggingface.co/blog/agentic-evals#step-3-run-the-task-unchanged)、[改造它](https://huggingface.co/blog/agentic-evals#step-4-adapt-the-task)、[检查评估本身](https://huggingface.co/blog/agentic-evals#step-5-check-the-evaluation)、[阅读 trace](https://huggingface.co/blog/agentic-evals#step-6-run-it-and-read-the-traces)、[报告分数](https://huggingface.co/blog/agentic-evals#step-7-report-the-score)、[比较模型](https://huggingface.co/blog/agentic-evals#step-8-compare-models)。最后我们盘点复用了什么。完整演练在[附录 A](https://huggingface.co/blog/agentic-evals#appendix-a-practical-example-agentic-deployment-in-a-physics-lab)。图 3 把这八个步骤以及它们在我们示例中各自的产出对应起来。

*图 3. 构建一项 agentic 评估的八个步骤。左栏依次高亮每个步骤,右栏展示该步骤在我们的示例中涉及什么。黄色步骤作用于评估本身,橙色步骤运行模型并读取结果。*

### 方法

**主张。** 设想一个物理实验室,希望 agent 对拉曼光谱中的峰进行拟合。拉曼光谱是一种测量,它的峰揭示了材料的性质,这里是石墨烯。agent 要做的是普通的编码工作:读取数据文件,对每个峰拟合一条曲线,保存结果(附录 A 图 5)。就本文而言,我们的主张刻意收窄:拟合指定的峰、计算所要求的 D/G 比(一个峰相对于另一个峰的强度,可以指示材料中的缺陷;我们也称它为缺陷比),并稳定地保存准确的结果。审阅一整份实验报告需要额外的能力和证据。

**起始任务与基线。** 我们复用了 [Harbor](https://docs.harborframework.com/)的任务格式和 Terminal-Bench 的 [raman-fitting](https://hub.harborframework.com/tasks/terminal-bench/raman-fitting)任务。Harbor 是一个开源评估 harness,Terminal-Bench 则是一个公开基准,其中的任务由 agent 在终端里完成。我们首先运行了任务的参考解,它通过了;随后用 [Terminus-2](https://docs.harborframework.com/agents/pre-integrated-agents)(一个终端 agent harness)和 [gpt-oss-120b](https://huggingface.co/openai/gpt-oss-120b)(OpenAI 的一个开放权重模型)把原始任务跑了三次。Harbor 运行在 HF Job 里,每次 rollout 使用自己的 HF Sandbox,模型回复由 Inference Providers 提供。复用 runner 和任务格式,让我们能把精力集中在物理、评分和审阅上。只有 agent harness 无需任何新工作。其他每一个组件都需要核查或有新工作,我们逐项列在[附录 A 的末尾](https://huggingface.co/blog/agentic-evals#how-we-reused-existing-open-components)。

**改造。** 我们构建了 [raman-lab](https://huggingface.co/datasets/burtenshaw/raman-lab):八条合成光谱,参数已知,噪声与缺陷水平各不相同。改造后的任务拟合三个峰而不是两个,并报告缺陷比。我们用 agent 协助生成光谱,再人工审阅,并新写了指令、参考拟合和输出检查。新指令明确写出了原任务略去的单位与参数定义。这八个任务是开发集(development set),即在构建评估过程中使用的任务;更广的覆盖面应当跟随真实测量的变化。

**检查。** 在跑更多模型之前,我们先测试评估本身。我们运行了参考解、一个什么都不做的 agent,以及一个跳过必需工作的捷径方案。参考解应当通过每个任务,另外两个应当失败。我们的捷径方案直接从数据里读出每个峰的高度、再猜出峰的宽度。它在八个任务上都给出了预期的缺陷比,却根本没有拟合光谱,于是我们在拟合本身上加了检查。

**捷径。** 我们还测试了一个捷径方案,用来检查评估对作弊的鲁棒性。这个捷径是一小段脚本,跳过真正的拟合:它直接从数据里读出每个峰的最高点,猜出峰宽,再用 D 峰高度除以 G 峰高度。即便如此,它在八个任务上都给出了预期的缺陷比,所以一个只看比值的评分器会给它满分。我们为每个拟合峰都加了检查,最终的校验器会拒绝它。

### 结果

*图 4. 在构建评估过程中,我们从测量不同侧面学到的东西。(A)用捷径方案测试评分器,说明只查比值的检查会被骗过。(B)阅读 gpt-oss-120b 的 trace 发现,它的大多数失败来自过早停止。(C)运行其他模型说明这些任务是可以解出来的。*[*附录 A*](https://huggingface.co/blog/agentic-evals#appendix-a-practical-example-agentic-deployment-in-a-physics-lab)*有详细结果:图 7(gpt-oss-120b 的尝试如何结束)、图 8(全部六个模型)、图 9(各模型在什么时候说自己完成了)。*

**基线。** 在原始任务上,gpt-oss-120b 在 3 次 rollout 中通过 0 次。有两次,它在观察到相关输出之前就宣告完成;第三次,它读不了数据文件——该文件使用小数逗号,参考解会在加载前先做转换。单看分数,无法把这类失败与拟合错误区分开。trace 可以。

**trace 与分数。** 在八个改造后的任务上,每个任务跑三次 rollout。改造后的设置通过了 24 次 rollout 中的 11 次。有 19 次,模型在第一个回复里就调用了 `mark_task_complete`;其中 11 次没有产出结果文件。这些当中有几次的开头就是脚本失败,原因是缺少 NumPy 或 SciPy——而任务本来就指望 agent 自己安装。因此大多数失败来自过早停止或缺少软件包,13 次失败中只有两次栽在拟合检查上(附录 A 图 7)。我们的 pass@3 是 7/8:七个任务至少成功过一次。pass^3 是 1/8:只有一个任务每次都成功。有人审阅输出时,重试是可以接受的;无人值守的处理需要一致性,所以第二个指标更重要。平均通过率为 0.46,按任务对 rollout 聚类后,标准误约为 0.11。重跑一次通过了 24 次中的 10 次。只有八个开发任务,我们会谨慎对待把任一结果推广到新光谱上。

**模型比较。** 接着我们在同样的八个任务上比较了六个模型(图 4)。同一开放权重模型可能由多家提供方以不同的量化和上下文上限来服务,所以我们为每个模型锁定一家提供方。把 DeepInfra 锁定为提供方后,gpt-oss-120b 通过了 24 次 rollout 中的 13 次,而先前那轮使用默认提供方时是 24 次中的 11 次。只有 gpt-oss-120b 在第一个回复里就宣告完成——24 次 rollout 中有 22 次如此。其余五个模型在任何一次 rollout 中都没有这样做(附录 A 图 9)。这项比较也暴露了开发集的局限。[Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B)、[DeepSeek-V4.1-Flash](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash) 和 [MiniMax-M3.1-Flash](https://huggingface.co/MiniMaxAI/MiniMax-M3.1-Flash)通过了 raman-lab 全部 24 次 rollout,所以这些任务无法给它们排位。那需要更难的任务。

## 3. 苦涩的教训:当基准出错时

我们的捷径方案没有拟合任何光谱,却给出了预期的缺陷比。一个只看比值的校验器,会在八个任务上全给它满分。我们是怎么发现的:故意用一个明知不完整的解去攻破评分器,然后为拟合出的光谱加上检查([附录 A 第 5 步](https://huggingface.co/blog/agentic-evals#step-5-check-the-evaluation))。

这个捷径靠错误的理由拿到了正确答案,就像一个只抄最终数字、不写过程的学生。我们得到的教训是:要检验输出究竟证明了什么。更快但同样有效的方法应当通过;跳过必需技能的方法则不该通过。领域专家可以协助设定容差,让校验器接受其他正确的拟合方式,同时不接受偏离任务本意的成果。

这类错误很常见,而且对分数影响不小。一篇[对 agentic 基准的综述](https://huggingface.co/papers/2507.02825)发现,任务设置或奖励设计上的缺陷,可以使测得的性能在相对意义上浮动最高 100%。

### 公开审阅是纠正基准的关键

公开审阅能暴露出基准构建者漏掉的指令与测试错误。Terminal-Bench 2.1 在用户反馈后修复了[89 个任务中的 28 个](https://www.tbench.ai/news/terminal-bench-2-1),其中包括一个测试要求 Spark SQL、而指令却要求 PostgreSQL 的任务;在整个纠正过程中,[agent 排名保持稳定](https://icml.cc/virtual/2026/82793)。

能否拿到证据,也决定外部审计要花多少工夫。CritPt 的参考解不公开,所以[审计它的物理学家们](https://arxiv.org/abs/2609.13009)必须先把题目自己解一遍,才能在他们审阅的 56 道题中发现 21 道有错。作者随后发布了[修订版](https://artificialanalysis.ai/evaluations/critpt-v2)。OpenAI 对 [SWE-bench Verified](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/) 的审计,从任何人都能读到的任务与测试入手,在它检查的 138 道题中发现了 59.4% 存在实质性问题。对构建者而言,外部审视是验证的一部分:把审阅者质疑任务所需的东西公开出来,给他们反馈问题的渠道,并记录下改了什么。

SWE-bench Pro 也暴露出类似缺陷。2026 年 7 月,OpenAI [估计约 30% 的 SWE-Bench Pro 任务是有问题的](https://openai.com/index/separating-signal-from-noise-coding-evaluations/),并撤回了采用它的建议。基准验证需要在发布之后继续下去。

### 既要查代码,也要查主张

一致的分数仍然可能测错了东西。[Measuring what Matters](https://huggingface.co/papers/2511.04703)由 29 位专家审阅者回顾了 445 个 LLM 基准,发现任务与指标中反复出现某些模式,损害了构念效度(construct validity)——即任务和指标是否真的支撑关于目标能力的结论。

例如,拟合合成光谱并不能证明 agent 会审阅实验报告。后者可能还需要识别出测量质量不佳,或者主动求助。如果每个任务都提供一份可用的光谱,测试就无法显示 agent 是否知道在什么情况下不该做拟合。

[Harder Than the Task](https://arxiv.org/abs/2611.03494)把这种担忧延伸到组织性工作中——在那里,权限、分散的知识和依赖关系都可能决定成败。作者发现,在知名基准中,宣称覆盖了其中任何一类维度的不到四分之一。agent 可能需要另一个团队的校准数据,或者需要获得更换测量方式的许可,而一开始就把一切都备齐,恰好抹掉了这些困难。如果这些困难对主张重要,它们就该出现在评估里;如果不重要,说明它们未被测试就够了。

每个错误都值得留一份简短记录:哪个假设不成立、它是怎么被发现的、改了什么。记录还应写明受影响的版本,并说明此前的分数是否仍可比。

### 污染与饱和

前面提到的 SWE-bench Verified 审计还发现了污染:受测的每一个前沿模型,都能对某些任务复现出参考补丁或逐字的问题细节。SWE-bench 的公开仓库和广泛使用让任务暴露给了训练。让坏测试得以被审视的那种开放性,同时也让条目更容易在评估之前被遇到。

然而,如果在训练期间能仔细控制污染,单靠隐藏测试集并不能阻止饱和。一项[对 60 个语言模型基准的研究](https://huggingface.co/papers/2602.16763)在公开基准和私有基准上都发现了相近的饱和程度,并得出结论:一个基准一旦被广泛采用,隐藏测试数据并不能阻止饱和——也就是说,好基准会因为饱和而被弃用,而开发者却无法从中学习、在其上继续搭建。真正与更低饱和相关的是专家策展和更大的测试集。

这就留下一个实际发布问题:我们能在保护现役测试条目的同时,公开哪些内容供审阅?

## 4. 有策略地开源评估

在污染风险与饱和之间取得平衡,需要对「哪些内容公开」采取有策略的做法。基准创建者不必把开放当成全有或全无的抉择,而是可以逐个部分决定发布什么:既保护现役测试任务不被数据泄漏,又分享底层基础设施、评分方法,以及能让外部研究者审计并在此之上继续构建的参考示例。

现有基准展现了不同的开放程度。[ARC-AGI-2](https://arcprize.org/arc-agi/2)公开一个训练集和一个含 120 个任务的评估集,同时保留各含 120 个任务的半私有集与私有集。[AILuminate](https://mlcommons.org/ailuminate/faq/)对官方提示词保密,公开其方法与分类体系,并把底层证据保留给经授权的审计者和可信研究者做受控审阅。Terminal-Bench 公开其任务,并在文件中标上[canary string](https://huggingface.co/datasets/harborframework/terminal-bench-2.1/blob/main/tasks/raman-fitting/solution/solve.sh),请求它们不要进入训练语料。公开审阅者无法检查受保护的条目,所以任何保持封闭的部分,都需要有自己的审阅通路。

我们自己的示例就遵循这一做法。我们把 raman-lab 作为[数据集发布到 Hub](https://huggingface.co/datasets/burtenshaw/raman-lab)。它包含八条 Harbor 任务格式的合成石墨烯光谱,每条都带有自己的环境、参考拟合、校验器和容差。结果背后的原始 rollout 作为[单独的数据集](https://huggingface.co/datasets/burtenshaw/raman-lab-runs)共享,其中包含全部六个模型的 Harbor trial 目录、轨迹和校验器输出。光谱生成器、分析代码与结果放在配套的 [GitHub 仓库](https://github.com/burtenshaw/raman-lab-evals)里,因此 agent harness 和评估 harness 都可以被查看和重跑。

在更敏感的领域,一项临床评估可以公开它的环境定义、harness、工具接口和评分框架,并提供合成病例供开发使用。病历和参考答案则留在受控访问之下,同时让经授权的审阅者查看有争议的判定。每一项限制都应当附带一个重新审视它的条件。

### 有策略地开源:检查清单

我们推荐一份简短的清单,部分取自更全面的 [Agentic Benchmark Checklist](https://huggingface.co/papers/2507.02825)。在发布或停用一项评估之前,请检查另一个构建者是否能够:

- 说清它测的是什么、预期用途是什么,以及它忽略了哪些条件。
- 找到可复用的产物、它们的许可证与版本,以及反馈问题的渠道。
- 看到空操作 agent 得多少分,并在可能时,看到人类专家得多少分。
- 连同不确定性一起读懂每个分数,并了解已知缺陷对它意味着什么。
- 了解发现了哪些缺陷、它们是如何处理的,以及它们可能让结果偏移多远。
- 知道任务将以何种方式、在何时更新,以抑制污染与过拟合。

当基准不再能区分它原本要比较的系统时,这些发布决策同样决定了还能留下什么有用的东西。

## 5. 结语:让评估在退役后仍有用处

基准是有生命周期的。它们被构建、被采用、被针对性地优化,最终不再能区分它们原本要比较的系统。第 3 节提到的[饱和研究](https://huggingface.co/papers/2602.16763)把 60 个语言模型基准中的 29 个评为高度饱和,且比例随基准年龄上升。饱和本身并不是失败,因为它可能意味着这项能力真的到位了。

一个基准能留下什么,取决于它有多开放。只发布分数,后人能运行或改造的东西就所剩无几。当任务、环境、校验器和 trace 都开放时,即使排行榜停更,每一部分仍在继续发挥作用。一个已被解出的任务,会成为新 harness 的回归检查;它的环境和校验器可以催生一个更难的继任者。开放的基准还会被修复和再版:MMLU 的题目变成了 [MMLU-Redux](https://huggingface.co/datasets/edinburgh-dawg/mmlu-redux-2.0),Terminal-Bench 2.0 借助社区贡献变成 [2.1](https://www.tbench.ai/news/terminal-bench-2-1)。我们自己的演练就是这样的「身后生命」:raman-lab 最初只是为通用终端工作构建的基准里的一个任务。

这就是公开构建评估所承诺的东西。投入一项评估的工作可以比基准本身活得更久,为他人打下基础,去提出新问题、测试新能力、改进前人的成果。我们分享的所建与所学越多,每一项新评估需要从零开始的部分就越少。

如果你好奇这在实践中是什么样子,就跟着我们的实例走一遍。

## 附录 A. 实例:物理实验室中的 agentic 部署

设想一个物理实验室,希望 agent 拟合拉曼光谱中的峰。拉曼光谱法把激光照在样品上,测量散射光频率的位移;由此得到的峰揭示了材料的性质。对于石墨烯——一层原子厚的碳片——位于 1580 和 2700 cm⁻¹ 附近的 G 峰和 2D 峰[可以确定层数](https://arxiv.org/abs/cond-mat/0606284)。当晶格无序时会出现第三个峰 D,它相对于 G 的强度[可以指示缺陷](https://arxiv.org/abs/1306.5856)。图 5 展示了这套设置。

### 第 1 步. 定义主张

一个好的起点是一条*主张*:一句关于 agent 能做什么的平实陈述,而评估正是为支撑它而存在。「这个 agent 能拟合拉曼光谱」是一条主张,「这个 agent 能处理实验报告」也是。从这里,你可以把主张拆成更小的技能,逐个检查,比如读取文件、定位峰、写出输出。

就本文而言,我们的主张刻意收窄:拟合指定的峰、计算所要求的 D/G 比,并稳定地保存准确的结果。审阅一整份实验报告需要额外的能力和证据。

领域专家在这里能帮上忙。我们建议请他们挑选贴近现实的噪声水平、容差和可用软件,然后独立给示例打分,并追查分歧。至此,你可以把主张拆成可检查的部分,再把每个部分对应到每个任务实际测试的内容。

### 第 2 步. 找一个起始任务

针对你自己的领域,Hugging Face Hub 是个好去处,可以看它的 Benchmark 和 Environment 数据集类型。找到候选之后,值得检查它的指令、环境、[参考解](https://huggingface.co/datasets/harborframework/terminal-bench-2.1/blob/main/tasks/raman-fitting/solution/solve.sh)和测试。即便是模型已经能解出的任务,也可能提供有用的基础设施。我们从 raman-fitting 继承了一套可用的任务格式。不过它只有一条光谱,而实验室的测量是变化的,所以我们按第 4 步的说明进一步扩展了这个任务。

### 第 3 步. 原样运行任务

在运行任何模型之前,先跑一遍参考解(也叫 oracle)会有帮助。如果它失败了,问题出在任务、环境或校验器上,需要先修好,然后才谈得上解读模型的失败。之后,你可以在不改动设置的情况下把模型跑几次。

我们把 Harbor 跑在一个 [HF Job](https://huggingface.co/docs/hub/jobs-overview)里,由它提供 runner 所需的算力。每次 rollout 使用自己的 [HF Sandbox](https://huggingface.co/docs/huggingface_hub/guides/sandbox)来执行命令和存放文件,模型回复由 [Inference Providers](https://huggingface.co/docs/inference-providers/index)提供。在安装 Harbor 的 `hf-sandbox` extra 并设置 `HF_TOKEN` 之后,下面这些命令先测试 oracle,然后用 [Terminus-2](https://docs.harborframework.com/agents/pre-integrated-agents)(一个终端 agent harness)和 [gpt-oss-120b](https://huggingface.co/openai/gpt-oss-120b)(OpenAI 的一个开放权重模型)跑三次 rollout。

```
harbor run -t terminal-bench/raman-fitting \
  -a oracle -e hf-sandbox

OPENAI_API_KEY="$HF_TOKEN" harbor run \
  -t terminal-bench/raman-fitting -k 3 -e hf-sandbox \
  -a terminus-2 -m openai/openai/gpt-oss-120b \
  --ak api_base=https://router.huggingface.co/v1
```

在这些命令里,`-t` 指定任务,`-a` 指定 agent,`-e` 指定环境,`-m` 指定模型,`-k` 指定每个任务的 rollout 次数。

模型在 3 次 rollout 中通过 0 次。有两次,它在观察到相关输出之前就宣告完成;第三次,它读不了数据文件——该文件使用小数逗号,参考解会在加载前先做转换。单看分数,无法把这类失败与拟合错误区分开。trace 可以。

### 第 4 步. 改造任务

我们构建了 [raman-lab](https://huggingface.co/datasets/burtenshaw/raman-lab):八条合成光谱,参数已知,噪声与缺陷水平各不相同。改造后的任务拟合三个峰而不是两个,并报告缺陷比。我们用 agent 协助生成光谱,再人工审阅,并新写了指令、参考拟合和输出检查。这八个任务是开发集,即在构建评估过程中使用的任务;更广的覆盖面应当跟随真实测量的变化。

D/G 强度比可以指示缺陷,但它的解读[取决于激光激发能量和无序程度](https://pubmed.ncbi.nlm.nih.gov/21696186/)。一项要求「缺陷比」的评估必须说明:用哪两个峰、强度指的是峰高还是积分面积,以及结果如何检查。

原始的 [instruction.md](https://huggingface.co/datasets/harborframework/terminal-bench-2.1/blob/main/tasks/raman-fitting/instruction.md)说明了这类定义为什么重要:它要求 x0、gamma、amplitude 和 offset,却没有定义它们或它们的单位。参考解把它们理解为峰中心、半高半宽、扣背景后的峰高和背景水平,并把 x 轴从纳米换算为拉曼位移。我们把诸如此类的选择写进了改造后的指令,好让校验器的要求一目了然。图 6 把两个文件并排放置。

*图 6.* [*raman-fitting*](https://huggingface.co/datasets/harborframework/terminal-bench-2.1/blob/main/tasks/raman-fitting/instruction.md) *和* [*raman-lab*](https://huggingface.co/datasets/burtenshaw/raman-lab/blob/main/graphene-s01/instruction.md)*的 `instruction.md` 文件并排对照。高亮的新增部分覆盖了主张中新增的内容:D 峰、缺陷比,以及二者在保存结果中的体现。剩下的部分——处理变化的测量——存在于数据里:八个 raman-lab 任务共用这份指令,改变的只有光谱及其噪声与缺陷水平。*

校验器遵循三条规则:

- 给 agent 实际产出的东西打分:检查保存下来的输出,而不是它自称完成了。[τ-bench](https://huggingface.co/papers/2406.12045)的做法是把最终的数据库状态与标注好的目标状态作比较。
- 在指令里写明每一个会被检查的事实,包括单位、参数约定、容差和必填字段。
- 用已知参数生成合成数据,使参考答案可得,然后再审阅这些示例是否代表了要考的问题。

共用格式可以保持不变,只让数据和检查发生变化。下面这条命令创建一个任务脚手架:

```
harbor task init my-org/task-01 -p datasets/my-evals
```

### 第 5 步. 检查评估

在跑更多模型之前,先测试评估本身。这里 `datasets/my-evals` 存放改造后的任务。

```
harbor run -p datasets/my-evals -a oracle -e hf-sandbox
harbor run -p datasets/my-evals -a nop -e hf-sandbox
```

- oracle 应当通过每个任务,也就是说,已知的解必须能在给定的环境里跑通。
- 空操作 agent 什么都不做,所以它应当在每个任务上都失败。交白卷不该通过。一篇[对 agentic 基准的综述](https://huggingface.co/papers/2507.02825)发现,有一个基准把空回复算作了成功。
- 跳过必需工作的捷径方案应当失败。一种测试方法是用一个刻意偷懒的解,比如不做实际工作、只输出一个看似合理的答案,看校验器是否会接受。也要试一试看似合理的错误答案和其他正确的解法,以便同时抓出误判通过和误判失败。

我们的捷径方案在八个任务上都给出了预期的缺陷比,却没有拟合光谱,于是在拟合本身上加了检查。第 3 节解释了这对校验器设计意味着什么。

### 第 6 步. 运行并阅读 trace

成功和失败的 rollout 都值得读。Harbor 使用共享的 trace 格式 [ATIF](https://docs.harborframework.com/agents/atif),把消息、工具调用和观察记录在 `agent/trajectory.json`。按原因给失败分组,模式会更容易看出来:解析数据、执行工具、过早停止,或者给输出评分。

改造后的设置通过了 24 次 rollout 中的 11 次。有 19 次,模型在第一个回复里就调用了 `mark_task_complete`;其中 11 次没有产出结果文件。

*图 7. 在 24 次尝试中,有 19 次 agent 在第一个回复里就调用了 `mark_task_complete`。其中 11 次没有产出结果文件,7 次通过,1 次栽在拟合检查上。剩余的 5 次尝试中,4 次通过,1 次栽在拟合检查上。*

有几次「缺文件」的失败是从缺少 NumPy 或 SciPy 开始的。发布的任务指望 agent 自己安装;它的参考解开头就是一条 pip install。而一项「用给定工具做拟合」的实验室评估,可以预先安装并锁定这些包。依赖还会漂移:Terminal-Bench 2.1 [修复了九个任务](https://www.tbench.ai/news/terminal-bench-2-1),原因是它们的外部依赖在发布之后发生了变化。

预装会改变评估条件,所以在比较这两种设置时,要把模型、harness、任务和 rollout 次数都固定住。

最后,我们调整设置、重做第 5 步的检查,再跑一遍。Harbor 的 [trace 导出器](https://github.com/harbor-framework/harbor/blob/26106c6d9c66848a1440faf5724d336affac52aa/docs/content/docs/training-workflows/sft.mdx)可以准备好记录,供在 Hub 上分享。分享之前值得先检查其中有没有受保护的内容,并且成功与失败都要保留,好让别人能追查结果。

### 第 7 步. 报告分数

正确的指标取决于你需要做出的决策:

- [pass@k](https://huggingface.co/papers/2107.03374)问的是 k 次 rollout 中是否至少有一次成功。我们的 pass@3 是 7/8:七个任务至少成功过一次。
- [pass^k](https://huggingface.co/papers/2406.12045)问的是 k 次 rollout 是否全部成功。我们的 pass^3 是 1/8:只有一个任务每次都成功。

有人审阅输出时,重试是可以接受的;无人值守的处理需要一致性,所以第二个指标更重要。

平均值配上它的不确定性才更有用。同一光谱的多次 rollout 共享同等的难度,因此彼此并不独立,标准误应当[按任务聚类](https://huggingface.co/papers/2411.00640)。聚类后得到的平均成功率为 0.46,标准误约 0.11。重跑一次通过了 24 次 rollout 中的 10 次,而第一次是 24 次中的 11 次。只有八个开发任务,我们会谨慎对待把任一结果推广到新光谱上。

Harbor 为每次 rollout 写一个 `result.json`;它把一次 rollout 称作一次 trial。我们按任务把这些文件分组,确认每个任务都有三次 rollout,并记录错误或排除项。在分数旁边同时报告 token 数、耗时和工具调用次数,能让读者比较那些以不同成本达到相近结果的设置。

### 第 8 步. 比较模型

当单个模型在某个任务上失败时,仅凭那一次运行说不出哪里出了问题。可能是模型、agent harness,也可能是评估本身。在同一批任务上多跑几个模型,有助于缩小可能性。当多个模型都在同一个任务上失败时,去检查指令、环境和校验器,找出共同原因。当某个模型反复以某种独特方式失败时,把它的 trace 与成功的尝试对照。

Inference Providers 通过同一个 router 服务许多开放权重模型,所以每多一个模型,只是给 `-m` 多一个取值。同一模型可能由多家提供方以不同的量化和上下文上限来服务,所以最好用 `:deepinfra` 这样的后缀锁定一家,并在分数旁边记录下来。

```
OPENAI_API_KEY="$HF_TOKEN" harbor run -p datasets/my-evals -k 3 \
  -e hf-sandbox -a terminus-2 -m openai/Qwen/Qwen3.8-27B:deepinfra \
  --ak api_base=https://router.huggingface.co/v1
```

图 8 展示了各模型在 raman-lab 上的结果。

*图 8. 各模型在 raman-lab 上的结果,含 pass@3、pass^3,以及带聚类标准误的平均通过率。点选方块可以查看那次 rollout。*

这项比较让 gpt-oss-120b 的一个模式更清楚了:它常常在没看到命令输出之前就宣告完成。在这次锁定 DeepInfra 为提供方的单独运行中,它在 24 次 rollout 里有 22 次在第一个回复中就调用 `mark_task_complete`,而其余五个模型一次都没有这样做(图 9)。第 6 步那次运行用的是 router 的默认提供方,记录到 24 次里有 19 次这样的提前完成。它通过了 24 次 rollout 中的 11 次,而 DeepInfra 那次是 24 次中的 13 次。两者用的是同一个判定:模型是否在第一个回复里调用了 `mark_task_complete`。

*图 9. 按 agent 宣告完成的时机划分的 raman-lab rollout 结果。左:agent 先观察了命令输出。右:它在第一个回复里就调用了 `mark_task_complete`。*

这项比较也暴露了开发集的局限。[Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B)、[DeepSeek-V4.1-Flash](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash) 和 [MiniMax-M3.1-Flash](https://huggingface.co/MiniMaxAI/MiniMax-M3.1-Flash)通过了 raman-lab 全部 24 次 rollout,所以这些任务无法给它们排位。那需要更难的任务。

按 router 的标价计算,六个模型的推理总成本不到 5 美元。raman-lab 的中位 rollout 中,gpt-oss-120b 用了约 6,000 个 token,MiniMax-M3.1-Flash 约 90,000 个。配套[仓库](https://github.com/burtenshaw/raman-lab-evals)里有[trace](https://huggingface.co/datasets/burtenshaw/raman-lab-runs)、逐次 rollout 的结果,以及添加另一个模型的脚本。

### 我们如何复用已有的开放组件

复用 runner 和任务格式,让我们能专注于物理、评分和审阅。之所以能复用,是因为 Harbor 和 Terminal-Bench 公开了它们的代码和任务。

- **任务:** 我们复用了 Harbor 的任务格式和 Terminal-Bench 的 raman-fitting 任务。新工作是收窄的主张、技能覆盖,以及为 raman-lab 编写的指令。
- **任务数据:** 原始光谱作为起始示例。我们为八条已知参数的光谱构建了生成器,并人工审阅。
- **环境:** 由 Harbor 的环境支持和 HF Sandbox 承载任务运行。我们核对了软件包需求,并诊断了缺失依赖。
- **agent harness 与工具:** 带 shell 访问权的 Terminus-2,模型回复由 Inference Providers 提供。这部分不需要新工作。
- **rollout 与 trace:** Harbor 的 rollout 记录与 ATIF 捕获了每次运行。我们审阅了成功与失败,并按原因分组。
- **参考解:** 我们沿用运行 `solution/solve.sh` 的约定,并为每个新任务写了参考拟合。
- **评估 harness:** Harbor 运行在 HF Job 里。我们配置了运行,并按任务对结果分组。
- **校验器:** 我们复用了 `tests/test.sh` 入口及其把分数写入文件的方式。新工作是拟合检查与比值检查,以及针对捷径方案和错误输出的测试。

## 术语表

**Agent harness:** 模型周边的软件,把模型的回复转成动作,例如 shell 命令。本文中的 agent harness 是 Terminus-2。

**Agentic evaluation(agentic 评估):** 对 agent 在环境中改动了什么进行打分的评估,而不只是看它返回的文本。

**ATIF:** Agent Trajectory Interchange Format,一种用于记录 agent 的消息、工具调用和观察的共享格式。

**Canary string:** 基准文件中的一个唯一标记,便于模型训练方找到它们并将之排除在训练数据之外。

**Clustered standard error(聚类标准误):** 把同一任务的多次 rollout 视为相关的标准误;相比把每次 rollout 当作独立样本,它给出的误差范围更宽,也更诚实。

**Container image(容器镜像):** 操作系统、文件和软件的一个固定打包,使每次 rollout 都从相同的环境开始。

**Contamination(污染):** 测试题或解答出现在训练数据中,使分数可能反映记忆而非能力。

**Context limit(上下文上限):** 模型在一次请求中能读入的最大文本量,以 token 计。

**D、G 与 2D 峰:** 石墨烯拉曼光谱中的特征。G 与 2D 指示层数,D 在碳晶格存在缺陷时出现。

**Defect ratio(缺陷比):** D 峰强度除以 G 峰强度,用于指示石墨烯中的缺陷。也称 D/G 比。

**Development set(开发集):** 构建和调试评估期间使用的任务,与留作最终打分的测试集相对。

**Environment(环境):** agent 在完成任务时所处的软件、文件与资源。

**Evaluation harness(评估 harness):** 运行任务、重复 rollout、收集 trace 并汇总分数的软件。本文中的评估 harness 是 Harbor。

**Gated dataset(门控数据集):** 只有所有者批准访问请求后才能下载的 Hugging Face 数据集。

**Harbor:** 一个面向 agentic 任务的开源评估 harness。

**HF Job:** Hugging Face 上运行脚本的计算资源。本文中它跑的就是 Harbor。

**HF Sandbox:** 一个隔离的 Hugging Face 环境,单次 rollout 在其中执行命令、存放文件。

**Held-out test set(留出测试集):** 保持私密的测试条目,使模型无法在其上训练或调参。

**Inference Providers:** Hugging Face 的一项服务,通过一个 API(称为 router)把模型请求路由给第三方提供方。

**Lorentzian(洛伦兹线型):** 一种常用于建模光谱峰形的数学曲线。

**No-op agent:** 什么都不做的 agent。健全的评估应当给它零分。

**Open-weight model(开放权重模型):** 训练好的参数公开发布、任何人都可以下载和运行的模型。

**Oracle:** 运行参考解的 agent,用于检查每个任务都能在给定的环境中被解出。

**pass@k:** k 次 rollout 中至少有一次成功的任务占比。

**pass^k:** k 次 rollout 全部成功的任务占比。

**Pinning(固定版本):** 锁定软件、镜像或模型提供方的确切版本,使一次运行可以被重复。

**Quantization(量化):** 用更低的数值精度存储模型权重,以更快、更省地运行,但可能轻微改变输出。

**Raman shift(拉曼位移):** 激光与样品散射光之间的频率差,以 cm⁻¹ 计。

**Raman spectroscopy(拉曼光谱法):** 一种把激光照在样品上、测量散射光位移以辨识材料性质的技术。

**Reference solution(参考解):** 完成任务的一种已知正确做法,与任务一起存放。

**Rollout:** agent 对某个任务的一次尝试。Harbor 把它称作一次 trial。

**Run record(运行记录):** 记录分数背后实际运行了什么:确切的任务、环境、模型配置和代码版本。

**Saturation(饱和):** 大多数模型在一个基准上都拿到接近顶部的分数、基准不再能区分它们的那个时点。

**Synthetic data(合成数据):** 由已知参数生成的数据,因此正确答案事先已知。

**Terminal-Bench:** 一个公开基准,其中的任务由 agent 在计算机终端里完成。

**Terminus-2:** 本文使用的终端 agent harness。它把模型接到 shell 命令上。

**Token:** 模型读写文本的单位,大致相当于一个短词或词的一部分。

**Trace:** 一次 rollout 的完整记录:模型的消息、工具调用,以及每条命令返回了什么。也称 trajectory。

**Verifier(校验器):** 通过检查保存的输出或环境的最终状态来给 rollout 打分的代码。
