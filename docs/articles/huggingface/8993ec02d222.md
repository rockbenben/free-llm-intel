# CodeAgents + 结构化：执行操作的更优方式

今天我们分享一项连接 AI 智能体设计两大范式的研究：基于代码动作（code-based actions）的表达力，与结构化生成（structured generation）的可靠性。我们的发现表明：强制 **CodeAgent** 以结构化 JSON 格式同时生成思考与代码，可以在多个基准上显著超越传统做法。

[![accuracy.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/structured-codeagent/accuracy.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/structured-codeagent/accuracy.png) 图 1：三种方法在 [SmolBench（GAIA、MATH、SimpleQA 和 Frames）](https://huggingface.co/datasets/akseljoonas/smolbench)上的准确率对比：Structured CodeAgent（蓝）、CodeAgent（橙）、ToolCallingAgent（灰）。误差棒为 95% 置信区间。

## **🤔 智能体动作的演化**

AI 智能体需要在世界中采取行动——调用 API、处理数据、或推理复杂问题。智能体表达这些动作的方式经历了几种范式：

**传统 JSON Agent**：智能体生成结构化 JSON 来调用工具。

```
{"tool": "get_weather", "arguments": {"city": "Paris"}}
```

这类智能体从预定义工具列表中选择，并生成 JSON 格式的调用。这种工具调用方式因 OpenAI 的 [function calling API](https://openai.com/index/function-calling-and-other-api-updates/) 而流行，此后一直是用得最多的工具调用方法。

它很可靠，但受制于：

- **有限的动作集**：智能体能做的动作只能通过预定义工具表达，功能受限。
- **缺乏可组合性**：任务若需要组合多个来源的信息，JSON agent 会很吃力，因为它不支持跨工具调用维护中间状态。尽管一些模型支持并行工具调用，但当一个工具的输出决定下一步动作、或结果需要放在一起比较处理时，它们难以胜任。
- **结构僵化**：当工具与要做的事不完全匹配时，能处理的范围非常有限。

**Code Agent**：智能体利用自己天生的编程能力，直接写可执行的 Python 代码。

```
# We can get the average temperature in 3 cities in 1 model call.
temperature_sum = 0
for city in ["Paris", "Tokyo", "New York"]:
    temp = get_weather(city)
    temperature_sum += temp
    
print(f"Average temperature: {temperature_sum / 3:.1f}°C")
```

这一转变最早在论文 "[Executable Code Actions Elicit Better LLM Agents](https://arxiv.org/abs/2402.01030)" 中以 CodeAct 之名提出，让 AI 智能体在工具调用之外获得了编写任意可执行 Python 代码的灵活性。

关键洞见是：**工具直接在代码内部被调用**，变量与状态管理因此可靠得多。智能体可以在循环、函数、条件语句里调用工具——本质上每次动作都在生成一张动态的工具执行图！

使用 [CodeAgent](https://github.com/huggingface/smolagents/blob/6a12ebdf210207eec22d5940157f522463fc1c59/src/smolagents/agents.py#L1344) 的优点：

- **聪明的工具使用**：智能体根据当下情况决定用哪些工具。
- **无限的灵活性**：可以用任何 Python 功能达成目标。
- **能够检验想法**：智能体可以提出假设并验证，动作更灵活。

然而，从 markdown 里解析代码容易出错，于是有了这个提议：为什么不用结构化生成来产出代码动作呢？

### **➡️ 给 Code Agent 加上结构化输出**

有了结构化输出，你可以强制 LLM 把显式思考与代码一起生成为一个 JSON 块：

```
// The "code" block gets parsed into executable Python
{
  "thoughts": "I want to find the average temperature across 3 cities.",
  "code": "temperature_sum = 0\nfor city in [\"Paris\", \"Tokyo\", \"New York\"]:\n    temp = get_weather(city)\n    temperature_sum += temp\n\nprint(f\"Average temperature: {temperature_sum / 3:.1f}°C\")"
}
```

关键区别在于生成是被强制的：现在不只是被*提示*要输出思考然后代码，而是用[结构化输出](https://huggingface.co/docs/text-generation-inference/en/conceptual/guidance)强制它遵守这个结构。

这一方法把结构化生成的可靠性加到代码执行的灵活性上，兼得两者之长。

- **显式推理**：`thoughts` 字段强迫智能体在行动前先把理由想清楚。
- **可靠解析**：JSON 结构消灭了 markdown 解析错误。
- **完整的代码表达力**：`code` 字段保留代码智能体的全部灵活性。
- **更好的分离**：规划与执行界限分明。

## 🧪 **基准结果**

我们在 GAIA、MATH、SimpleQA、Frames 等多个基准上比较了这三种范式。结果呈现清晰的规律：**代码动作 + 结构化生成，对能力足够的模型有一致的提升**。

在多数能力强的模型上，结构化方法平均比常规 CodeAgent 高出 2-7 个百分点。

- **OpenAI 模型**：从结构化中获益最大，尤其在重推理的任务上。
- **Claude 模型**：受益于结构化，Claude 3.7 Sonnet 表现尤其突出。
- **Qwen 模型**：整体上结构化有提升，但小模型开始出现「结构税」（见下节）。

## **💡 为什么结构化（大体上）有帮助**

### **解析问题是真实存在的**

我们在 [smolagents 里的 CodeAgent 实现](https://github.com/huggingface/smolagents/blob/6a12ebdf210207eec22d5940157f522463fc1c59/src/smolagents/agents.py#L1344)从 LLM 输出中提取 Python 代码，以下情形会失败：

- markdown 中的代码块不完整或格式不对
- 一个回复里出现多个代码块

结构化生成靠可靠的 JSON 解析消除了这些问题。

为了理解结构化生成为什么重要，我们分析了基准上的 15,724 条智能体轨迹。结果触目：

- **2.4%** 的轨迹在第一次调用就出现解析错误
- **有**首次解析错误的轨迹：成功率 **42.3%**
- **没有**首次解析错误的轨迹：成功率 **51.3%**

**没有解析错误的智能体轨迹，成功率比有错误的多 21.3%。**

这不只是方便与否——解析错误会引发连锁失败，显著拖累智能体整体表现。当智能体因为代码格式不对而无法执行第一个动作时，它往往很难恢复，导致次优的解题路径。

[![parsing error.png](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/structured-codeagent/parsing_error.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/structured-codeagent/parsing_error.png) 图 2：第一步的解析错误使智能体成功率下降 21.3%，平均步数从 3.18 升到 4.63。

**此外：强制的推理过程**

结构化生成和显式 `thoughts` 不只是*提示*智能体，而是*强迫*它在行动前把推理讲出来。这带来：

- **更好的规划**：智能体更系统地思考问题。
- **更强的可靠性**：显式推理能及早发现逻辑错误。

### **结构税**

我们的结果也揭示了一个清晰的能力门槛：模型需要足够的指令遵循能力、以及预训练数据中足够的 JSON 覆盖，才能从结构化生成中获益。这说明结构化方法最适合：

- 大型、充分训练的模型
- 指令遵循能力强的模型
- 在结构化生成上做过微调的模型

#### **结构化翻车的真实示例**

当一个小模型（比如 `mistralai/Mistral-7B-Instruct-v0.3`）尝试生成结构化代码时会发生什么——认知负载超出了它：

```
{
  "thought": "I need to find the height...",
  "code": "web_search(query=\"Eiffel Tower height\")\", "
}
```

模型生成了语法坏掉的 Python：`web_search(query="Eiffel Tower height")",` ——注意多出来的引号和逗号。这直接导致 SyntaxError 和执行失败。

这就是「结构税」：小模型很难同时应付 JSON 格式、Python 语法和真正的解题逻辑。结构化生成的认知开销，会压垮那些用简单的基于 markdown 的代码生成原本表现尚可的模型。

## **🚀 什么时候该用 Structured CodeAgent**

**✅ 适合使用 Structured CodeAgent 的场景：**

- 使用能力强的模型（32B+ 参数或前沿模型）
- 任务需要复杂推理与代码执行
- 你需要可靠解析智能体输出

**⚠️ 考虑其他方案的场景：**

- 用难以应付结构化生成的小模型
- 简单、预定义的工作流已经够用

### 如何在 smolagents 中使用

超级简单！加一个 `use_structured_outputs_internally:` 开关即可：

```
from smolagents import CodeAgent, InferenceClientModel, GoogleSearchTool

# Configure agent for structured generation
agent = CodeAgent(
    tools=[GoogleSearchTool(provider="serper")],
    model=InferenceClientModel("Qwen/Qwen3-235B-A22B", provider='nebius'),
    use_structured_outputs_internally=True # Enable structured output
)

result = agent.run("Calculate the time for a cheetah to run across the Golden Gate Bridge")
```

LLM 会生成类似这样的东西：

```
{
  "thoughts": "I need to find the length of the Golden Gate Bridge and the top speed of a cheetah, then calculate the time.",
  "code": "bridge_info = web_search('Golden Gate Bridge length meters')\ncheetah_speed = web_search('Cheetah top speed') ..."
}
```

然后 "code" 部分照常被智能体执行——这就是标准 CodeAgent，但现在解析可靠性是 100%！

### **实现建议**

- **清晰的提示**：确保 prompt 明确说明期望的 JSON 结构
- **模型选择**：选结构化生成能力强的模型
- **选对提供商：** 一些 API 提供商如 OpenAI 或 Anthropic 开箱支持结构化生成。如果你通过 Hugging Face 使用推理提供商，各提供商对结构化生成的支持不一。支持结构化生成的提供商列表见：[Structured generation support for Models in smolagents‣](https://www.notion.so/Structured-generation-support-for-Models-in-smolagents-1f51384ebcac8074a051e6dd03d1fe1d?pvs=21)

## **更大的图景——接下来？**

这项研究表明，我们正在走向对智能体架构更细腻的理解。问题不只是"智能体能做什么"，而是"智能体应该如何思考它正在做的事"。

也许是让推理过程更显式有助于模型不跑偏，也许只是解析更容易。无论如何，这是赢面。

但这只是开始，还有很多问题值得探索：

- 还有哪些结构性改进能帮上忙？
- 如何让它对不同模型架构、尤其是小模型工作得更好？
- 这对 AI 推理的本质告诉我们什么？

目前，如果你在用 smolagents（或在构建自己的 CodeAgent 系统），不妨试试结构化输出。你的解析错误会感谢你，而且你很可能会看到一轮漂亮的性能提升！
