# 改进 Hugging Face Hub 上的 Parquet 去重

Hugging Face 的 Xet 团队正在致力于提升 Hub 存储架构的效率，让用户存储和更新数据与模型更简单、更快捷。Hugging Face 托管的数据集接近 11PB，其中 Parquet 文件就占了 2.2PB 以上，因此优化 Parquet 存储的优先级相当高。

大多数 Parquet 文件是各种数据分析管道或数据库的批量导出，往往以全量快照而非增量更新的形式出现。当用户希望定期更新数据集时，数据去重对效率至关重要。只有去重，我们才能尽可能紧凑地存储所有版本，而无需每次更新都重新上传全部内容。理想情况下，对于一个不断增长的数据集，我们应该只需比其最大版本略多一点的空间，就能存储它的每一个版本。

我们的默认存储算法使用字节级 [Content-Defined Chunking (CDC)](https://joshleeb.com/posts/content-defined-chunking.html)，通常能很好地针对插入和删除去重，但 Parquet 的布局带来了一些挑战。我们做了一系列实验，看看一些简单改动在 Parquet 文件上的表现。实验使用来自 [FineWeb](https://huggingface.co/datasets/HuggingFaceFW/fineweb/tree/main/data/CC-MAIN-2013-20) 数据集的一个 2GB、含 1,092,000 行的 Parquet 文件，并用我们的[去重估计器](https://github.com/huggingface/dedupe_estimator)生成可视化。

## 背景

Parquet 表的运作方式是把表切分成行组（row group），每组包含固定数量的行（例如 1000 行）。行组内每一列被压缩后存储：

![Parquet Layout](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/improve_parquet_dedupe/layout.png)

直观上，这意味着不扰动行分组的操作——如修改或追加——应该能很好地去重。让我们验证一下！

## 追加（Append）

这里我们向文件追加 10,000 行新数据，并与原始版本比较结果。绿色表示全部被去重的块，红色表示全部新块，中间的颜色表示不同的去重程度。

![Visualization of dedupe from data appends](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/improve_parquet_dedupe/1_append.png)

可以看到，我们确实几乎去重了整个文件，只是文件末尾出现了变化。新文件 99.1% 被去重，只需额外 20MB 存储。这与我们的直觉相当吻合。

## 修改（Modification）

考虑到这种布局，我们本以为行修改会相当局部化，但事实显然并非如此。这里我们对第 10000 行做了一个小改动，发现虽然文件大部分能去重，但出现了许多小的、间隔规律的新数据段！

![Visualization of dedupe from data modifications](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/improve_parquet_dedupe/2_mod.png)

快速浏览 [Parquet 文件格式](https://parquet.apache.org/docs/file-format/metadata/)可以发现，绝对文件偏移量是 Parquet 列头的一部分（见 ColumnChunk 和 ColumnMetaData 结构）！这意味着任何修改都可能重写所有列头。因此，尽管数据本身去重良好（几乎全绿），每个列头却都产生了新字节。

在这种情况下，新文件只有 89% 被去重，需要额外 230MB 存储。

## 删除（Deletion）

这里我们删除文件中间的一行（注意：插入的行为应类似）。由于这会重新整理整个行组布局（每个行组 1000 行），我们看到前半部分文件能去重，而剩余文件的块则完全是新的。

![Visualization of dedupe from data deletion](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/improve_parquet_dedupe/3_delete.png)

这主要是因为 Parquet 格式对每一列进行了激进压缩。如果关闭压缩，我们就能更激进地去重：

![Visualization of dedupe from data deletion without column compression](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/improve_parquet_dedupe/4_delete_no_compress.png)

不过，不压缩存储时文件大小接近原来的 2 倍。

能否同时享受去重与压缩的好处？

## 内容定义行组（Content Defined Row Groups）

一个潜在方案是不仅在字节级使用 CDC，还把它应用到行级：行组的切分不依据绝对行数（1000 行），而依据所提供 "Key" 列的哈希。换句话说，每当 key 列的哈希 % [目标行数] = 0 时就切出一个行组，同时对行组大小设最小值和最大值作为容限。

我在这里 hack 了一个快速而低效的实验性演示：[gist](https://gist.github.com/ylow/db38522fb0ca69bdf1065237222b4d1c)。

借助这个方法，即使删除一行，我们也能在压缩的 Parquet 文件之间高效去重。这里可以清楚看到代表被重写行组的大红块，随后是每个列头的小幅变化。

![Visualization of dedupe from data deletion with content defined row groups](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/improve_parquet_dedupe/5_content_defined.png)

# 为可去重性优化 Parquet

基于这些实验，我们可以考虑从几个方向改进 Parquet 文件的去重能力：

- 对文件结构数据使用相对偏移而非绝对偏移。这会让 Parquet 结构位置无关、便于 "memcpy" 搬移，但这是牵一发动全身的文件格式改动，可能难以落地。
- 支持在行组上做内容定义切块。格式实际上今天就允许这一点，因为它并不要求行组大小一致，因此改动面很小。只需更新 Parquet 格式的写入器。

虽然我们会继续探索提升 Parquet 存储性能的方法（例如：上传前可选地重写 Parquet 文件？上传时剥离绝对文件偏移、下载时恢复？），但我们很希望能与 Apache Arrow 项目合作，看看是否有兴趣在 Parquet / Arrow 代码库中实现这些想法。

在此期间，我们也在探索数据去重过程对其他常见文件类型的表现。欢迎试用我们的[去重估计器](https://github.com/huggingface/dedupe_estimator)并告诉我们你的发现！
