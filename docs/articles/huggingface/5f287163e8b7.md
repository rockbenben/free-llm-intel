我们最近发布了一个由 [Gemma 4 E2B](https://huggingface.co/google/gemma-4-E2B) 驱动的 Transformers.js 浏览器扩展 demo，帮助用户浏览网页。

在构建过程中，我们收集到一些关于 Manifest V3 运行时、模型加载与消息传递的实用观察，值得分享。

## 本文适合谁

本指南面向想在 Chrome 扩展中、于 Manifest V3 约束下用 Transformers.js 运行本地 AI 功能的开发者。

读完后，你将拥有与本项目相同的架构：托管模型的后台 service worker、侧边栏聊天 UI，以及负责页面级操作的 content script。

## 我们将构建什么

在本指南中，我们将以已发布的扩展为参照、以开源代码库为实现地图，重现 **Transformers.js Gemma 4 Browser Assistant** 的核心架构。

- 线上扩展：[Chrome Web Store](https://chromewebstore.google.com/detail/transformerjs-gemma-4-bro/dhaknnnkcdkjhcclchmnfdhddoehoool)
- 源代码：[github.com/nico-martin/gemma4-browser-extension](https://github.com/nico-martin/gemma4-browser-extension)
- 最终成果：后台托管的 Transformers.js 引擎、侧边栏聊天 UI，以及负责页面提取与高亮的 content script。

## 1）Chrome 扩展架构（MV3）

深入之前，先说明范围：我不会详谈 React UI 层或 Vite 构建配置。这里的重点是高层架构决策：每种 Chrome 运行时里跑什么、这些部分如何被编排。

如果 Manifest V3 对你还是新东西，先读这篇简短概述：[What is Manifest V3?](https://developer.chrome.com/docs/extensions/develop/migrate/what-is-mv3)。

### 1.1 运行时上下文与入口点

在 MV3 中，你的架构从 [`public/manifest.json`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/public/manifest.json) 开始。本项目定义了三个入口点：

- `background.service_worker = background.js`，由 [`src/background/background.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/background/background.ts) 构建。
- `side_panel.default_path = sidebar.html`，由 [`src/sidebar/index.html`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/sidebar/index.html) 构建。
- `content_scripts[].js = content.js`，`matches: http(s)://*/*`、`run_at: document_idle`，由 [`src/content/content.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/content/content.ts) 构建。

后台 service worker 还处理 `chrome.action.onClicked`，为活动标签页打开侧边栏。另一个值得知道的入口点：popup 可以用 `action.default_popup` 定义，很适合快捷操作。本项目用侧边栏承载持久聊天，但编排模式是一样的。

### 1.2 什么跑在哪里

关键设计决策是：把重型编排放在后台，让 UI/页面逻辑保持薄。

- 后台（[`src/background/background.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/background/background.ts)）是控制平面：agent 生命周期、模型初始化、工具执行，以及特征提取等共享服务。
- 侧边栏（[`src/sidebar/*`](https://github.com/nico-martin/gemma4-browser-extension/tree/main/src/sidebar)）是交互层：聊天输入/输出、流式更新与设置控制。
- Content script（[`src/content/content.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/content/content.ts)）是页面桥：DOM 提取与高亮操作。

这一分工的一个实际结果是：对话历史也放在后台（`Agent.chatMessages`）：UI 发送 `AGENT_GENERATE_TEXT` 这类事件，后台追加消息、运行推理，再把 `MESSAGES_UPDATE` 发回侧边栏。

这种拆分避免了重复加载模型，让 UI 保持响应灵敏，也尊重 Chrome 关于 DOM 访问的安全边界。

### 1.3 消息契约

运行时一旦分离，消息传递就成了骨架。在本项目中，所有消息都通过 [`src/shared/types.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/shared/types.ts) 中的枚举做类型化。

- 侧边栏 -> 后台（`BackgroundTasks`）：`CHECK_MODELS`、`INITIALIZE_MODELS` `AGENT_INITIALIZE`、`AGENT_GENERATE_TEXT`、`AGENT_GET_MESSAGES`、`AGENT_CLEAR` `EXTRACT_FEATURES`
- 后台 -> 侧边栏（`BackgroundMessages`）：`DOWNLOAD_PROGRESS`、`MESSAGES_UPDATE`
- 后台 -> content（`ContentTasks`）：`EXTRACT_PAGE_DATA`、`HIGHLIGHT_ELEMENTS`、`CLEAR_HIGHLIGHTS`

编排规则很简单：后台是唯一的协调者；侧边栏与 content script 是专职的请求动作、渲染结果的工作者。

典型的请求流程：

- 侧边栏发送 `AGENT_GENERATE_TEXT`。
- 后台追加到 `Agent.chatMessages` 并运行模型/工具步骤。
- 后台发出 `MESSAGES_UPDATE`。
- 侧边栏根据更新后的消息列表重新渲染。

## 2）Transformers.js 集成细节

### 2.1 模型与职责

在 [`src/shared/constants.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/shared/constants.ts) 中，这个扩展使用两种模型角色：

- TextGeneration / LLM：[`onnx-community/gemma-4-E2B-it-ONNX`](https://huggingface.co/onnx-community/gemma-4-E2B-it-ONNX)（`text-generation`、`q4f16`）
- VectorEmbeddings：[`onnx-community/all-MiniLM-L6-v2-ONNX`](https://huggingface.co/onnx-community/all-MiniLM-L6-v2-ONNX)（`feature-extraction`、`fp32`）

这种拆分是刻意的：Gemma 4 负责推理与工具决策，MiniLM 则为 `ask_website` 与 `find_history` 中的语义相似度搜索生成向量 embedding。

### 2.2 推理在哪里跑

所有推理都在后台运行（[`src/background/background.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/background/background.ts)）：

- 文本生成用 `pipeline("text-generation", ...)`，并通过我们新的 `DynamicCache` 类一致地启用 KV Caching
- embedding 用 `pipeline("feature-extraction", ...)` 加向量归一化

这为所有标签页/会话提供了一个单一的模型宿主，避免内存重复占用，也让侧边栏 UI 保持流畅。由于模型是从后台 service worker 加载的，产物被缓存在扩展来源（`chrome-extension://<extension-id>`）之下，而不是按网站来源分别缓存——整个扩展安装共享一份缓存。

MV3 生命周期提示：service worker 可能被挂起并重启，因此模型运行时状态应视为可恢复、必要时重新初始化。

### 2.3 下载与缓存生命周期

模型生命周期是显式的：

- `CHECK_MODELS` 检查已缓存的内容并估算剩余下载量。
- `INITIALIZE_MODELS` 下载/初始化模型并向 UI 发出 `DOWNLOAD_PROGRESS`。
- 设置完成后复用长生命周期实例：生成 pipeline 在 [`src/background/agent/Agent.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/background/agent/Agent.ts)，embedding pipeline 在 [`src/background/utils/FeatureExtractor.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/background/utils/FeatureExtractor.ts)

权限与隐私是架构的一部分，而不是最后的勾选项。在本项目中，[`public/manifest.json`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/public/manifest.json) 申请了 `sidePanel`、`storage`、`scripting`、`tabs`，外加 `http(s)://*/*` 的 `host_permissions`：

- `sidePanel`：打开与控制侧边栏 UX 所必需。
- `storage`：跨会话持久化工具/设置状态所必需。
- `tabs` + `scripting`：标签页感知的工具与页面级操作所必需。
- 对 `http(s)://*/*` 的 `host_permissions`：因为页面内容提取/高亮被设计为在任意网站上工作。

为什么要保持狭窄：权限定义了用户信任与 Chrome Web Store 审核风险。只申请功能真正需要的权限，并明确说明推理在扩展运行时内本地进行，让用户理解他们的数据在哪里被处理。

## 3）Agent 与工具执行循环

### 3.1 工具调用基础（这层为何存在）

在执行循环之前，先理解模型的工具调用如何工作（一切 agentic 工作流的基础）。你传入消息加工具 schema（`name`、`description` 和 `parameters`），Transformers.js 用模型的 chat template 从这些输入格式化出真正的 prompt。由于 chat template 因模型而异，具体的工具调用格式取决于你用的模型。在 Gemma-4 风格的模板下，模型在决定调用某个工具时会输出一个特殊的工具调用 token 块。

```
import { pipeline } from "@huggingface/transformers";

const generator = await pipeline(
  "text-generation",
  "onnx-community/gemma-4-E2B-it-ONNX",
  {
    dtype: "q4f16",
    device: "webgpu",
  },
);

const messages = [{ role: "user", content: "What's the weather in Bern?" }];

const output = await generator(messages, {
  max_new_tokens: 128,
  do_sample: false,
  tools: [
    {
      type: "function",
      function: {
        name: "getWeather",
        description: "Get the weather in a location",
        parameters: {
          type: "object",
          properties: {
            location: {
              type: "string",
              description: "The location to get the weather for",
            },
          },
          required: ["location"],
        },
      },
    },
  ],
});
```

在生成时，模型可能输出类似：

```
<|tool_call>call:getWeather{location:<|"|>Bern<|"|>}<tool_call|>
```

这正是本项目需要一个归一化层（`webMcp`）和一个解析器（`extractToolCalls`）的原因：模型输出必须被转换成确定性的工具执行。

### 3.2 本项目的工具接口

[`src/background/agent/webMcp.tsx`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/background/agent/webMcp.tsx) 把扩展工具归一化为对模型友好的形状：

- `name`、`description`、`inputSchema`、`execute`

示例工具包括 `get_open_tabs`、`go_to_tab`、`open_url`、`close_tab`、`find_history`、`ask_website` 与 `highlight_website_element`。

### 3.3 循环设计（`Agent.runAgent`）

这里的核心设计选择，是把模型内部消息与面向 UI 的聊天消息分开：

- 内部模型记录（`messages`）：system/user/tool/assistant 轮次，用于 `generator(...)` 的消息。
- UI 记录（`chatMessages`）：用户所见的内容，包括流式的助手文本、工具执行元数据（`tools`）与性能指标。

执行流程：

- 把用户输入加入 `chatMessages`，创建一条占位的助手消息并流式输出 token。
- 用 [`extractToolCalls.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/background/agent/extractToolCalls.ts) 把流式/最终的模型输出解析为 `{ message, toolCalls }`。
- 用户可见的助手消息保持纯文本，工具调用在后台执行。
- 把工具结果追加到助手的工具元数据中，并把结果作为下一轮 prompt 喂回模型。
- 重复直到没有工具调用，然后定稿助手内容与指标。

这让用户侧的交流保持干净，同时在后台维持一个确定性的工具循环。

## 4）数据边界与持久化

状态放哪里，是 MV3 中另一个影响重大的架构决策。在这个实现中，状态按生命周期与访问模式拆分：

- 对话状态：后台内存（`Agent.chatMessages`），用于快速的逐轮编排。
- 工具偏好：`chrome.storage.local`，让设置在会话间持久。
- 语义历史向量：IndexedDB（`VectorHistoryDB`），用于更大的本地检索数据。
- 提取的页面内容：后台缓存（`WebsiteContentManager`），以活动 URL 为键。

如 1.2 节所述，把对话历史放后台，让 UI 各处更新共享一份权威状态。这让短生命周期状态留在内存、持久设置放扩展存储、重型检索数据放本地数据库。

## 5）构建与打包注意事项

你不需要复杂的构建配置，但 MV3 要求每个运行时的输出可预测。

- [`vite.config.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/vite.config.ts) 中的多入口构建：[`src/sidebar/index.html`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/sidebar/index.html) [`src/background/background.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/background/background.ts) [`src/content/content.ts`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/src/content/content.ts)
- 确保输出名/路径与 manifest 对齐（`sidebar.html`、`background.js`、`content.js`）。
- 让 content script 保持自包含的输出，避免运行时 chunk 加载问题。

目标很简单：每个 Chrome 入口点一个产物，放在 [`public/manifest.json`](https://github.com/nico-martin/gemma4-browser-extension/blob/main/public/manifest.json) 期望的确切位置。

## 最后的要点

解锁整个项目的架构选择，就是清晰的关注点分离：后台拥有编排与模型执行，UI 表面保持薄，content script 处理页面访问。

本项目使用侧边栏，但同样的思路适用于其他形态：

- Popup 优先的助手：用 `action.default_popup` 做快捷交互，后台拥有对话状态与模型执行。
- 侧边栏副驾：把长对话放在持久面板里，后台处理工具循环与缓存。
- 每标签页 agent：当每个标签页需要自己的上下文时，在后台按 `tabId` 各保存一份 agent 状态。
- 混合 UI（popup + 侧边栏 + 选项页）：所有 UI 入口点都对话同一个后台协调者，复用同一套消息契约。

实用规则很简单：决定状态放在哪里（全局、按 tabId 还是按站点），把该状态和模型推理留在后台（本质上是后台服务），让 UI/content 运行时充当专注的客户端。
