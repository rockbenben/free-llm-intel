*根据 272 次生产运行，预测共享 GPU 集群上的端到端微调时间。*

**这是我们即将发表的论文 *Predicting End-to-End Fine-Tuning Time for Generative Language Models* 的预览。完整版很快会在 arXiv 上发布。**

GPU 是当下 AI 领域最贵也最紧俏的资源之一。任何在跑共享集群的人，每天都要决定哪些作业上哪些 GPU、按什么顺序上。而这个排期计划的好坏，取决于对每个作业耗时的估计。作业早完工几个小时，GPU 就空转着等下一个人来派活；晚几个小时，后面排队的一切都跟着顺延，实验要等，交付日期要改。

更准的时长估计能把这件事从猜测变成规划：跑什么、什么时候跑、用多少张 GPU，中间的空闲容量更少。可大多数团队用的估计，不过是拿 FLOP 随手一算。它说九小时，结果作业第二天下午才结束。

我们想知道这套算式到底偏了多少，以及能不能在作业派发之前就估得更准。于是我们从生产环境里 NVIDIA H200 的 GPU 池中取出 272 个真实的监督微调（SFT）作业，合计约 7,382 GPU 小时，把解析式估计与学习型预测器做了对比。

先说结论：常见的基于 FLOP 的估计几乎解释不了我们观察到的结果（R² = 0.31，MAE 12.41 h）。而一个只看派发前信息的 CatBoost 回归器，在 5 折交叉验证中达到 **R² = 0.98，平均绝对误差 1.71 h，中位误差 0.51 h**。差距来自两件闭式估计做不到的事：回归器能看到更多与训练相关的信号，比如评估节奏、checkpoint 策略、单 GPU 负载和微调方式；它还能从历史运行中学到这些信号之间的非线性交互。

## 大家常用的估计只算计算量

对稠密 Transformer 来说，训练开销大致是 6·P·D 次浮点运算，其中 P 是参数量，D 是训练 token 数。把它除以你的 GPU 能提供的算力，就得到训练循环时间：

```
T_theoretical = (6 · P · D) / (N_GPU · FLOPS_peak · MFU)
```

这里 N_GPU 是 GPU 数量，FLOPS_peak 是单张 GPU 规格书上的峰值吞吐，MFU（Model FLOPs Utilization，模型 FLOP 利用率）是训练实际达到的峰值比例。真实作业从来跑不到峰值——内存访问、通信和 kernel 效率都会拖后腿，所以 MFU 通常落在 30% 到 60% 之间，而且某个具体作业该取多少，事先并不知道。

对优化循环来说，这是个不错的描述。但一个作业并不只有循环。第一步之前有环境准备、模型下载与加载、tokenization；训练过程中有周期性评估和 checkpoint 上传；结束时最终模型要写进对象存储。在多租户集群上，这些环节还都要和其他作业抢网络与存储 I/O。

这些开销取决于配置，而且不会随工作负载或 GPU 数量整齐地缩放。两个名义计算量相同的作业，完工时间可能差好几个小时。

为了让比较公平，我们测试的 FLOP 基线把排定的评估 token 与训练 token 一并计入，并且在大范围内扫描 MFU。

## 我们做了什么

我们把端到端时长当作一个有监督回归问题：给定由作业配置和模型元数据构成的特征向量，预测从作业拿到 GPU 到作业完成之间的 wall-clock 时间。排队时间不计入。

两个设计选择决定了这项工作：

- **所有信息都在派发前已知。** 每个输入都来自提交的配置：超参数、数据集大小、模型标识、GPU 分配。不看运行时日志，不看中途进度。正因如此，这个预测才能用于调度。
- **用特征把开销暴露出来。** 在原始配置之外，我们还派生了一些量，例如 `num_eval_data`（所有评估轮次累计处理的样本数）、`num_saves` 与 `num_params_saved`（checkpoint I/O），以及单 GPU 的 token 量。FLOP 估计本身（MFU 固定为 0.45）作为又一个特征（`baseline_time`）输入，于是模型从纯计算数字出发，去学那些修正项。

我们比较了 Linear Regression、Ridge、XGBoost 和 CatBoost。特征选择结合了相关性过滤、互信息和排列重要性，覆盖 18 组候选特征集，随后以 MAE 为准则做网格搜索。最终的 CatBoost 模型使用 24 个特征。

## 数据

- **272 次 SFT 运行**，来自某企业生产环境的运维日志，覆盖多个模型系列、参数规模最高到 150 亿，既有 LoRA 也有全量微调，数据集大小和超参数分布很宽。
- **共享基础设施。** 作业在 1、2 或 4 张 GPU 上运行，GPU 取自跨 1 到 4 个节点、共 8 到 32 张 H200 的池子，并与其他训练和推理工作负载共存。测得的时间包含真实的资源争用。
- **时长从 1.6 到 172.4 小时**，均值 23.43 h，中位数 15.29 h。
- **技术栈：** Hugging Face Transformers 和 Unsloth。我们把技术栈建模为一个分类特征，不对两者之间的固定加速比做任何假设。

## 结果

所有数字都来自分层 5 折交叉验证。前四行是解析式结果，不涉及拟合。

| 模型 | R² | RMSE (h) | MAE (h) |
| --- | --- | --- | --- |
| FLOP 基线（MFU 30%） | 0.31 | 20.45 | 12.41 |
| FLOP 基线（MFU 45%） | 0.18 | 22.38 | 13.01 |
| FLOP 基线（MFU 60%） | 0.01 | 24.56 | 14.62 |
| Calculon | −0.51 | 30.40 | 20.36 |
| Linear Regression | 0.69 ± 0.14 | 13.52 ± 4.23 | 7.52 ± 0.49 |
| Ridge | 0.73 ± 0.09 | 12.72 ± 3.70 | 7.23 ± 0.68 |
| XGBoost | 0.97 ± 0.01 | 4.18 ± 1.17 | 1.95 ± 0.32 |
| **CatBoost** | **0.98 ± 0.01** | **3.52 ± 0.78** | **1.71 ± 0.33** |

有几处值得注意。

**没有任何单一 MFU 取值能修正 FLOP 基线。** 我们把 MFU 从 0.25 扫到 0.65。最好的设置是 30%，但对于平均时长 23 小时的作业，平均误差仍在 12 小时以上。

**更精细的解析模型也补不上这个缺口。** 作为第二个基线，我们采用了 Calculon（Isaev 等，SC '23），这是以往工作中面向 LLM 训练的解析性能模型。它会构建显式的层图，并把计算、内存访问和设备间通信都算进去。我们把公开实现扩展到支持 LoRA、grouped-query attention、fused attention、bfloat16 和 SwiGLU。它的估计值中位数仍只对应实测 wall-clock 时间的 11%。这并不是说 Calculon 不行——它是为 step 级别的分析而设计的工具，本来就是这个用途。它说明的是一个生产作业有多大比例发生在优化步之外。

**线性模型有帮助，然后就走不动了。** Ridge 把 MAE 降到 7.23 h。配置与时长之间的关系，纯线性模型捕捉得并不好。

**梯度提升承担了主要工作。** CatBoost 和 XGBoost 在每一项指标上都落在一个标准差之内。我们最终选用 CatBoost，因为它的平均误差整体最低。

## 预测器依赖什么

CatBoost 的特征重要性集中在少数几个特征上。模型与工作负载变量如预期地出现了，但评估和 checkpoint 相关的变量同样在列。`num_eval_data`——作业生命周期内评估累计处理的样本总数——排第一，其后是 `num_trainable_params`、`batch_eval_size_percent`、`num_all_params` 和 `num_gpus*batch_train_percent`，`num_params_saved` 紧随其后。SHAP 值讲的是同一个故事：评估量越大，预测时长越是被推高；可训练参数量则是非线性影响，只有最大的那些模型才会明显放大。

[![fig-feature-importance](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/MHyGZSFJZ6HXmwAUCTAnF.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/MHyGZSFJZ6HXmwAUCTAnF.png)

*CatBoost 模型在各折上的平均特征重要性（PredictionValuesChange）。*

特征重要性不等于因果关系。不过这个模式与作业实际把时间花在哪里是吻合的。你多久评估一次、评估集有多大、存多少个 checkpoint，都会左右 wall-clock 时间，与模型和数据集的规模并列。而这些，往往是人们写训练配置时按习惯随手定下的选择。

读图时有一点要留意：更大的 GPU 分配对预测时长是正贡献。在我们的数据里，分到更多 GPU 的往往也是更大的作业，所以 `num_gpus` 在某种程度上充当了作业规模的代理变量。它并不意味着多加 GPU 会让作业变慢。

## 误差有多大，错在哪里

看全部 272 个折外预测，绝对误差中位数为 0.51 h。80% 的预测误差在 2.20 h 以内，90% 在 4.31 h 以内。按作业时长拆开看：

| 作业时长（h） | 运行次数 | 绝对误差中位数（h） | P90（h） |
| --- | --- | --- | --- |
| 1.56 至 5 | 60 | 0.30 | 1.55 |
| 5 至 10 | 63 | 0.18 | 1.27 |
| 10 至 30 | 69 | 0.73 | 4.17 |
| 30 至 60 | 67 | 1.06 | 5.50 |
| 60 至 175 | 13 | 5.19 | 18.51 |

在 60 小时以内，误差中位数保持在一小时上下或更低。长尾是模型吃力之处，而超过 60 小时的运行只有 13 次，我们把这看作数据量的限制。

[![fig-error-by-duration](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/gQbjzLv37ag5kX7nZuuMh.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/gQbjzLv37ag5kX7nZuuMh.png)

*折外绝对误差对实际时长，按时长区间着色。误差在 60 h 以内保持低位，在稀疏的长尾里放大。*

更多数据应该仍有帮助。在固定的 20% 留出集上，训练分区从 85% 提到 100%，MAE 从 1.63 h 降到 1.50 h，尚未看到明显的平台。

## 它有什么用

实际使用中，这个预测器能在作业开始前给调度器一个可据以规划的时长：哪些作业可以凑一起跑、GPU 什么时候腾出来、某次运行能否赶上截止时间。

## 局限

- **仅限 SFT。** 我们没有纳入 RLHF、DPO、RLVR 等其他训练与对齐策略。
- **单一 GPU 型号。** 所有运行都用 H200。拟合出的模型是针对这套基础设施校准的，不能指望不重新训练就把数值迁移到其他代际的 GPU 上。要做混合 GPU 池的预测器，还需要硬件描述符，例如算力吞吐、显存容量与带宽、互连拓扑。
- **超长运行样本太少。** 60 小时以上误差会放大。

能迁移的是方法本身：开销感知的特征、考虑多重共线性的选择流程，以及比较协议。完整论文会逐一给出特征公式、选择流程、搜索空间和最终超参数，使得这套 pipeline 能在任何结构相似的执行日志数据集上重建。

我们接下来的计划是：面向特定硬件的描述符、在其他 GPU 型号上的验证、面向观测样本很少的配置的迁移学习、其他训练目标，以及更多长时运行的数据。
