# 智能体能力够强吗？在你自己的工具上为开放模型跑基准测试

Lysandre (lysandre)

Pedro Cuenca (pcuenq)

[![Benchmarking transformers revisions across different metrics](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_6.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_6.png)

*在不同指标下对 transformers 各版本做基准测试*

> 这是一篇人写的、聚焦 agent 的博客。

编码智能体（coding agent）越来越多地替我们与软件打交道：描述一个任务，agent 自己选库、写调用、跑代码、调试自己的错误。当库碍事时，它会毫不犹豫地绕过它、从头重写逻辑。这给库开发带来了一个新概念：代码不仅要正确、快，还要设计得让 agent 能高效驾驭。别扭的 API 或过时的文档过去只是烦我们开发者，现在还会把 agent 引上一条更长、更贵的路。

多数基准只看最终答案。我们想要的是整个过程：不光看 agent 答对没有，还看走到答案花了多少功夫，以及这在不同模型、库版本和任务之间如何变化。我们度量的正是这些，案例研究对象是 `transformers`。

这里我们介绍一类关注"答案是怎么找到的"的特定工具基准，并给出这样一个 harness（测试台架）的简单实现：完全由 [pi](https://www.npmjs.com/package/@mariozechner/pi-coding-agent) 编码智能体驱动的开放模型运行，完整的模型 × 版本 × 任务扫描铺开到 [Hugging Face Jobs](https://huggingface.co/docs/huggingface_hub/guides/jobs) 上，保证每次运行看到的硬件完全相同。

但是，***如何为 agent 优化软件？***

我们坚信以下两条软件原则：

- 没测试过的东西，就是不能用的
- 没文档的东西，就是不存在的

在面向 agent 优化的工具领域，这两条同样成立，而且难得的是，这一次两者直接绑定在一起。

你想让你的工具对 agent "存在"：它就得可发现。API 要清晰，文档要详尽，结构要能让 agent 快速访问到有用的文件和示例。你想让工具对 agent 好用，就应该按 agent 使用场景去测试它。

## 面向 agent 使用的软件测试

全文以 `transformers` 为例：指 agent *使用*它来解决 ML 任务（文本分类、图像描述、语音转写），而不是给它贡献代码；不过这个 harness 的设计可用于任何能从命令行操作的工具。

我们对 `transformers` 的直觉是：几个改动就能大幅简化用法——一个 CLI、一个 Skill（技能包）、以及自包含的、按任务组织的示例。这与最近给 [`hf` CLI 重新设计成 agent 优先](https://huggingface.co/blog/hf-cli-for-agents)用的是同一配方——那个改动让 agent 少用了 1.3–1.8 倍（最多 6 倍）的 token。我们想知道这种收益能否泛化，对 transformers 是否同样有用。

直觉是很强大的工具，但在给 `transformers` 这样被广泛使用的代码库提增加几千行代码的 PR 之前，我们想要更多证据。于是我们着手度量"成功长什么样"。

### 成功与成功并不等价

两个 agent 都可能对情感分类任务给出正确标签，但一个：

- 写了 40 行 Python 脚本，import `transformers`，调试一个 shape 错误，重跑两遍，最后打印答案；

而另一个

- 敲了一句 `transformers classify --model ... --text "..."`，一次调用收工。

两者都得到 `POSITIVE (0.9999)`，以下是 agent 在这个完全相同的任务上真实走过的两条路径：

```
# Task: classify the sentiment of "I absolutely loved the movie, it was fantastic!"

- # one agent: pipe a script into python and parse the output
- python - <<'PY'
- from transformers import AutoTokenizer, AutoModelForSequenceClassification
- import torch
- import torch.nn.functional as F
-
- model = AutoModelForSequenceClassification.from_pretrained("distilbert/distilbert-base-uncased-finetuned-sst-2-english")
- tokenizer = AutoTokenizer.from_pretrained("distilbert/distilbert-base-uncased-finetuned-sst-2-english")
- inputs = tokenizer("I absolutely loved the movie, it was fantastic!", return_tensors="pt")
- with torch.no_grad():
-     logits = model(**inputs).logits
- probs = F.softmax(logits, dim=1)
- idx = torch.argmax(probs, dim=1).item()
- print(model.config.id2label[idx], probs[0][idx].item())
- PY

+ # the other agent: one command
+ transformers classify \
+   --model distilbert/distilbert-base-uncased-finetuned-sst-2-english \
+   --text "I absolutely loved the movie, it was fantastic!"
```

殊途同归，但两者在**成本、延迟、token 用量、失败率**上的画像天差地别。

如果你的评估只看最终字符串，你就看不到这些，也看不到你往库里做的改动（CLI 改进、更好的报错信息、一个 Skill）是否真的帮到了 agent。

我们做这个 harness 的目标，就是评估 agent 完成给定任务要花多少功夫，以及库的改动是否提升了表现。

### 我们怎么做评估？

先说说这里如何评估 agent。

每个任务都在三种变体（"tier"，层级）下跑——agent 接近 `transformers` 的三种不同方式：

```
bare     pip install transformers，其他什么都没有
clone    完整 transformers 源码，签出到工作目录
skill    一个打包好的 Skill：CLI 文档 + 任务示例，加载进上下文
```

它们不是嵌套关系：`skill` 不包含 `clone`（它带的是精编文档而非源码树），两者也不互相包含，各自给 agent 的帮助类型不同。后文会看到，有时模型在 `clone` 上反而比 `skill` 做得更好。

还有几个选择：

- 目前我们只聚焦能给出精确匹配（exact match）的确定性任务，它们是极好的实验土壤。对其他任务，Model-as-a-judge 等方案是明显的下一步。
- 每次运行都是独立的 Hugging Face Job：每个（模型 × 版本 × 任务）一个，整个扫描在相同硬件上并行跑，大规模下对比依然公平。
- 结果和 trace 存进 Hugging Face Bucket：快、不需要版本管理、能扛极高并发写入。

### 用哪些模型做基准？

驱动 agent 的模型并不都一样，它们的差异决定了你跑测试时该看什么。

*大型开放模型*

一端是最大最强的开放模型。在相当常见的任务上，它们早晚能拿到正确答案。对它们来说，任务完成率会饱和到接近 100%，对你的工具就说明不了什么了；更有意义的基准是 agent 走到答案花了多大力气：用了多少轮、多少 token、多少秒，走的是干净路径还是踩了你已弃用的 API。

*本地模型*

本地模型体积差异巨大，能力也各异。对它们，**"match %"** 这类指标比大模型更相关，你能看到模型规模/能力如何影响你自己工具上的结果。

这个 harness 不仅为库维护者提供"如何改进仓库以适应 agent 交互"的指导，也能评估不同 agent 和模型在用户关心的任务上的表现。

harness 会在多个轴上给每次运行打分，让你对每类模型都能问到真正要紧的问题：

- **match %**：最终回答是否包含预期结果（按任务判定，大小写不敏感的子串/正则/精确匹配，报告里都写明）；
- **中位时间**和**中位 token 数**（新输入 vs 缓存 vs 生成）；
- **出错运行 %**：还包括一个保护规则，专门标记那些*什么都没产出*的运行（0 输出 token、无工具调用、无答案），不让静默失败冒充成"0"；
- **marker 采纳率**：工具定义的行为标记，是什么见下文解释。

所有这些都汇总进一份可直接查看的报告：

*实时报告：Overview、Coverage 和 Results，全部客户端渲染。*

而且由于它保存了每次运行的原生 agent trace，数字只是开始：你可以逐命令阅读 agent 到底做了什么。trace 可以通过 Hub 的 [agent-traces viewer](https://huggingface.co/docs/hub/agent-traces) 分享：

![A run rendered in the Hub's agent-traces viewer: MiniMax-M2.7 on the answer-question task](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_11.png)
 *Hub 的 agent-traces viewer 中渲染的一次运行：MiniMax-M2.7 做 answer-question 任务。*
 [**在 Hub 上打开这条 trace ↗**](https://huggingface.co/buckets/lysandre/transformers-agentic-use/tree/traces/22404f7951/pi/MiniMaxAI--MiniMax-M2.7/bare__answer-question__run1.jsonl)

看结果之前，快速回顾一下设置。每次运行变化四个东西：驱动 agent 的**模型**、运行所针对的 **`transformers` 版本**、**任务**、以及**层级**（`bare` / `clone` / `skill`）。如前所述，两类模型我们看不同指标。

### 大型开放模型：固定模型，变化版本

大开放模型通常能走到正确结果，所以你真正测的是它为此花了多少力气。是十轮还是一轮？它是否因为相信过时文档走了你已弃用的 API 路径？它是否撞上你没预料到的错误？

天然的实验是锁定一个强模型、变换工具版本：即我们测试的 `transformers` 各 git 版本，从 `v5.8.0`、`v5.9.0` 这样的发布标签，到引入 CLI 和 Skill 的那个具体 commit。我们想观察它施加给 agent 的负担是升是降。我们用 harness 在 `transformers` 上验证：加入专属 CLI 和 Skill 到底有没有减轻 agent 的工作量。

对我们使用的三个大模型，全部任务的平均耗时表明：Skill commit 使任务耗时更少：

![Median time per revision, by tier](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_13.png)
 *每个版本的中位耗时，按层级：skill commit（绿点）最快。*

另一方面，在我们克隆仓库的实验里，能看到引入 CLI 和示例的那个 commit 造成 token 消耗显著上升，马上就会看到。

![Median new tokens per revision, by tier](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_12.png)
 *每个版本的中位新 token 数，按层级：CLI 进入仓库后 clone 变体跳升。*

读 clone 变体的 trace 就知道为什么。该 commit 加了一个命令，但同时把 CLI 的实现和一整套 `cli/agentic/*.py` 使用示例直接放进了仓库。

在 `clone` 变体下，agent 面前是完整的 transformers 检出版，约三分之一的运行会先去读这些新面（`/cli/` 目录和示例脚本）学习接口再调用。这把中位输入从约 4k token 抬到约 6.4k。

于是两张图是一体两面的权衡：这个 commit 换来大模型更少的时间（它们转向 CLI 而不是调试 Python），代价是更多 token（它们读了教会它们用 CLI 的代码）。合并 PR 之前值得知道这种取舍。

不过有一点其实对 CLI 有利，目前还没被基准覆盖：读 CLI 的成本会随连续运行摊薄。我们的设置是为一次性实验设计的，每次运行都是全新 agent 从零重新发现 CLI，所以每次都付出发现成本。真实使用中，agent 学一次接口，然后在同一会话里连续解决一个又一个任务，成本被摊到很多请求上。我们这里测到的 token 上升更接近最坏情况，而不是用户日常会看到的。

### 小模型：固定版本，变化模型

开放模型让我们对这里最要紧的变量有精细控制：规模、配置、量化、提供商、训练，以及模型之间的一切差异。它们也最能体现好的工具面的价值：一个被要求"用 `transformers` 做 X"的小模型，在 `bare` 环境里可能猜一个几个版本前就变过的 API，可能做多余的工具调用，还可能答错。

所以这里的实验与上面相反：锁定版本、扫描模型。这能看出哪些模型真正能胜任任务——不只是按 token 数和时间，而是细到哪些模型无法可靠地发起工具调用。我们的直觉是模型越小，工具使用和任务都越难；我们跨一批模型规模跑了 harness 来验证：

![Match % across models, by tier](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_14.png)
 *跨模型的 match %，按层级：skill 层级抬高了较大模型，却压低了较小模型。*

这看起来也与摄入的 token 数相关

![Median new tokens across models, by tier](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_15.png)
 *跨模型的中位新 token 数，按层级。*

## 调整工具：markers 与结果

这里两件事汇到一起：如何越过"agent 成没成功"看到它做了什么、怎么做的；以及我们从 harness 里挖出的第一批结果。

### marker 是什么？

match %、token、时间告诉你一次运行的成本，但对内部发生了什么说得不多。

这就是我们引入 marker 概念的原因。marker 是一个具名模式，由 profile（每个工具的小插件，教 harness 如何构建并驱动给定库）对运行做匹配。

它就是你关心的某个行为的一行标签，匹配对象可以是 agent 执行的 shell 命令、写的代码、读的文件或最终回答。一次运行可以命中多个 marker 或一个都不中；报告会显示每个 marker 在各模型、各版本上的命中率。

对 `transformers` 我们声明了一些，这里只看最相关的两个：

- **`cli`**：agent 调用了 `transformers` 命令行工具（如 `transformers classify …`），而不是写 Python。
- **`pipeline`**：它伸手用了高层 Python API `pipeline(...)`。

我们盯着这些 marker，看改动是否真的改变了 agent 的行为。有意思的是：模型越大，越倾向于利用新上下文而不是自身记忆；因此也越会用新引入的 CLI。

![CLI adoption by tier across models](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_16.png)
 *跨模型的 CLI 采纳率，按层级：只有 skill 层级会用它，而且模型越大用得越多。*

CLI 采纳是新鲜事：CLI 在单个 commit 里落地，不在任何模型的训练数据里，文档也只有寥寥几笔。效果很清晰：真正带 CLI 文档的 Skill 变体才会去用它，采纳率 55.3%。

### CLI + Skill commit 有用吗？

跨模型规模比较该 commit，CLI + Skill 帮到大模型：在 `skill` 层级，Kimi 和其他大 agent 转向 CLI，用更少轮次完成。（在 `clone` 上它们反而先花*更多*输入 token 读新 CLI 代码——前面看到的那样——所以收益体现在时间和轮次，而不是原始 token。）

![Kimi-K2.6, GLM-5.1, and MiniMax-M2.7 across revisions](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_5.png)
 *Kimi-K2.6、GLM-5.1 和 MiniMax-M2.7 跨版本对比*

但在一些小模型设置里，它似乎反而伤害了表现。一个合理的小模型解释是：小模型依赖记住的 API 模式，复现训练数据里见过的 `pipeline(...)` 片段。新概念对它们反而是更大的"可犯错面"。你可以直接在 harness 上看：match % 更低、重试更多、`cli` marker 几乎不亮。在 Qwen3-4B 上尤其明显：Skill 几乎没改变它的 match 率，但其成本分布受到显著影响。

这几乎全部来自 `clone` 层级。检出版现在包含 CLI 的实现和 `cli/agentic/*.py` 示例，4B agent 成批地读它们：中位新 token 从约 2.4k 跳到约 23k，时间和输出同步飙升，准确率却毫无收益。

![Qwen3-4B cost distributions across revisions: elapsed, new tokens, repeat tokens, out tokens](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_7.png)
 *Qwen3-4B 跨版本对比。CLI + Skill commit 把成本分布完全摊开：在 `clone` 层级，agent 成批读取新打包的 CLI 源码（新 token 约 10 倍），match % 毫无收益。（`repeat tokens` 保持平稳：该设置未用 prompt caching。）*

不过有时，Skill 会直接把正确性搞崩。读 trace 能看到是怎么发生的，例如 Qwen3-14B：加 Skill 使其整体 match 率从 67%（bare）跌到 43%，而在最简单的任务上崩塌非常明显：`classify-sentiment` 从 `clone` 变体的 100% 跌到带 Skill 的 **0%**。

![Qwen3-14B classify-sentiment match % by tier across revisions](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_17.png)
 *Qwen3-14B 在 `classify-sentiment` 上按层级的表现：`clone`（蓝）跨版本稳定 100%，而 Skill 变体（绿）在 CLI + Skill 版本上崩到 0%。*

看 trace，模型把 CLI 误当成了*可以直接调用的工具*（像 agentic harness 里的 web-search 那种工具）。Skill **不是**可执行工具：它是加载进 agent 上下文的文档，而 `transformers` CLI 只应该从 shell（经 `bash`）运行；所以这行不通。

Qwen3-14B 读了 Skill 之后，在 56 次 Skill 运行里有 39 次，要么发出 `transformers(command="classify", ...)` 的工具调用（一个从未注册过的工具），要么在它的 `read`/`bash`/`edit`/`write` 工具里找不到类似的，就断定自己*不能*运行模型然后放弃。无论哪种，它宁愿宣布任务不可能，也不肯退回在 `clone` 检出版上拿过 100% 的那一行 `pipeline(...)`。

![Qwen3-14B gives up on classify-sentiment under the Skill variant](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/is-it-agentic-enough/img_10.png)
 *Qwen3-14B 在 classify-sentiment（Skill 变体）上的表现：它推理说 read/bash/edit/write 跑不了模型，然后放弃了。*

这正是我们构建 harness 要抓的问题：让大模型提速的同一个改动，最终搞坏了小模型——我们起初觉得这有点反直觉，很可能原样就合并了。给维护者的启示：**面向 agent 的 API 要跨模型规模评估，因为新的便利可能减少强模型的工作量，同时给小模型增加歧义。** 它还暗示了一种修法：与其手写一个 Skill 再事后检查，不如一开始就针对弱模型生成并验证 Skill。

这正是 [Upskill](https://huggingface.co/blog/upskill) 做的事：只有当强模型的解法对小模型有可度量的帮助时，才把它变成 Skill。

## 自己动手试

harness 就是一个 CLI：`agent-eval`。装上它，跑一套测试，在 HF Jobs 上铺开模型 × 版本的扫描，把报告发布成 Hugging Face Space。

> 仅限受信本地使用。harness 以绕过权限的方式运行编码智能体，并会执行你指向的任意版本里的代码，trace 可能包含提示词、输出和本地路径。在指向你未编写的代码或分享结果之前，请阅读 SECURITY.md。

## 结语

检查最终答案只能告诉你 agent *能不能*用你的库，不告诉你代价：轮次、token、错误，以及它走过的路径。这个 harness 度量的正是这些，覆盖你选的版本和模型。

在 `transformers` 上，它抓到了一个我们凭直觉就会合并的问题：CLI + Skill 帮助最大的开放模型，伤害最小的那些。合并前值得知道！

它基于 profile，设计上易于适配：指向你自己的库，定义几个任务和预期答案，得到同样的报告。代码和任务在[仓库](https://github.com/huggingface/is-it-agentic-enough)里，trace 在 Hub 上。如果你在自己的项目里用了，请告诉我们！
