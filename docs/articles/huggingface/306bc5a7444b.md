# Jupyter Agents：用 notebook 训练 LLM 推理

Baptiste Colle (baptistecolle)

Hanna Yukhymenko (hannayukhymenko)

Leandro von Werra (lvwerra)

过去一年的主旋律，是给 LLM 更多工具和自主权，去解决更复杂、更开放的任务。**Jupyter Agent** 的目标，是把终极工具交给模型：代码执行。

把多步代码执行和推理一起呈现，最自然的方式就是 Jupyter Notebook——由代码单元和 markdown 单元组成。所以我们构建了 Jupyter Agent：一个能直接在 Jupyter notebook 里执行代码、并用这个环境解决数据分析与数据科学任务的 agent。可以把它想象成 *Cursor*，只不过原生嵌在你的数据科学工作流里。
我们用 **Qwen-3 Coder**（目前最强的编码模型之一）做了一个体现这一理念的 [demo](https://huggingface.co/spaces/lvwerra/jupyter-agent-2)。这是我们早期 [jupyter-agent (v1)](https://huggingface.co/spaces/lvwerra/jupyter-agent) 工作的延续。

大模型已经开始展现出有用的行为，但关键问题是如何继续提升它们。为此我们专注于增强小模型，让它们在 agentic 数据科学任务上表现出色——目前它们还难以与大模型竞争。

这个项目的目标是搭一条 pipeline：先合成高质量训练数据，再微调一个现有小模型，最后评估模型在相关基准上的表现是否提升。

让我们从最后一步开始：为评估数据科学任务模型选一个强基准。

## 🏁 预备知识：DABStep 基准

要判断我们在"更好的数据科学 agent"这条路上是否取得进展，需要一个能度量这种能力的基准。去年，我们与 [Adyen](https://huggingface.co/adyen) 合作推出了 **[DABStep 基准](https://huggingface.co/blog/dabstep)**：用现实任务评估数据科学 agent 的方法。设置很简单：给 LLM 提供数据集，让它回答不那么简单/data 问题。

示例任务：

| 问题 | 答案 |
| --- | --- |
| 2023 年平均欺诈率最高的卡组织是哪家？ | SwiftCharge |
| 就 2023 年、商户 *Crossfit Hanna* 而言，如果鼓励用户切换到另一个 Authorization Characteristics Indicator，哪个选项最划算？ | E:346.49 |

这个基准对当今的 LLM 仍然很难——比如开箱表现最好的模型是 Claude 4 Sonnet，在 hard 任务上准确率也不到 20%。
实时排行榜见[这里](https://huggingface.co/spaces/adyen/DABstep)。

## 🎯 第一个基线

找到好基准后，就可以开始往上爬了！我们的目标是构建一个微调数据集，让**小数据 agent 模型**也能在 DABStep 上表现出色。

我们的第一个选择是 [**Qwen3-4B-Thinking-2507**](https://huggingface.co/Qwen/Qwen3-4B-Thinking-2507)：极小（迭代快、易运行），但又足够强，能在 agentic 场景里行动。

基线结果：

- *Easy 任务：* **44.4%**
- *Hard 任务：* **2.1%**

不算好——但作为起点很有希望，因为提升空间很大。来看看怎么改进！

## 🔧 脚手架（Scaffolding）预备知识

agent 区别于纯聊天模型的核心，是围绕模型搭建、用来引导其行为的脚手架（scaffolding）。比如 DABStep 的评估脚本用 [smolagents](https://github.com/huggingface/smolagents) 执行代码，Smolagents 自带预定义行为、提示词结构和预期格式。

我们还研究了 [**Qwen-Agent**](https://github.com/QwenLM/Qwen-Agent) 代码库，作者为模型量身打造了脚手架。这很合理：比如 Claude Code 与 Claude Sonnet 配合得惊人地好，正是因为它们的脚手架是对齐的。

于是我们重构了自己的脚手架：

- 精简到约 200 行代码。
- 无外部依赖。
- 受 [**tiny-agents**](https://huggingface.co/blog/tiny-agents) 精神的启发。

👉 代码在这里：[utils.py](https://huggingface.co/spaces/lvwerra/jupyter-agent-2/blob/main/utils.py)。

**结果：** 准确率从 **44.4% → 59.7%（easy split）**。🚀

**我们的循环：**

- 一个 while 循环配两个工具：*code execution* 用于运行代码，*final_answer* 用于返回最终答案。
- 与 Qwen-Agent 不同，我们显式加了 **final_answer** 工具——测试表明它提升了性能。
- 与 smolagents 相比，我们删掉大量提示词和工具，把脚手架做了简化。Smolagents 采用 ReACT 框架，也把很多假设硬编码进了模型。

## 🏃‍♂️ 训练 Pipeline

有了简化版脚手架，我们专注于针对**数据科学 agentic 任务**微调 Qwen3-4B。

## ⚙️ 数据集 Pipeline

想让模型在某个任务或某种行为上变强，配方就是用尽可能贴近该任务的数据来训练。一个天然的起点是看真实的 Jupyter Notebook，找到与我们要对付的任务——数据分析——高度契合的 notebook。

Kaggle notebook 是一座高质量数据分析 notebook 的宝库，由 Kaggle 提供：

**数据集：**

- **Kaggle Notebooks dataset**：约 2TB 的 notebook。
- **Kaggle Datasets**：约 5TB 的 kaggle 数据集，由我们手动下载并与 notebook 关联。
- 每个 notebook 都有丰富的元数据（作者、所用数据集等）。

有了基座模型的好结果，是时候构建能让我们更进一步的数据集了。我们用 [Datatrove](https://github.com/huggingface/datatrove) 设计了一条多阶段 pipeline，规模化地清洗和准备 Kaggle notebook。

每一步的做法如下：

### 1. 大规模去重

我们从约 2TB 的 Kaggle notebook 开始，复用 BigCode 项目的成果缩减到约 250GB。作为 StarCoder2 训练数据处理的一部分，这些 notebook（不含输出单元）已经被去过重。大多数 Kaggle notebook 只是小改动或近乎相同的副本，所以这一步必不可少。
*关键发现：* 约 90% 的原始 notebook 是重复的，不过滤会严重带偏训练。

### 2. 下载关联数据集

多数 Kaggle notebook 通过 Kaggle 元数据引用外部数据集。为确保 notebook 里的代码真能跑，我们搭了一条自动抓取这些关联数据集的 pipeline。这一步至关重要，否则很多 notebook 会不完整或无法执行。

我们用 **kagglehub** 包下载了数千个数据集——总共约 **5TB**。为了可控且相关：

- 过滤掉包含模型检查点、大型多模态语料或 LLM 相关文件的图集。
- 排除超过 10GB、放不进我们用于执行的 [E2B sandboxes](https://e2b.dev/) 的超大数据集。

最终我们得到了一个"可执行 notebook + 配套数据集"的丰富合集，为在真实可运行环境中训练 agent 打下基础。

### 3. 教育评分（Edu scoring）

我们用 [Qwen3-32B](https://huggingface.co/Qwen/Qwen3-32B) 按教育质量给 notebook 打分。实践表明整篇 notebook 一起打分并不理想，因为其中不少包含琐碎或坏的代码。教育评分方法详见 edu_scoring.py。

**TL;DR：** 按清晰度、完整性和教育价值给每个 notebook 打 1–5 分，只保留高于选定阈值的。这一步过滤掉了约 70% 的 notebook。

这与 BeyondWeb 论文的发现类似：使用高质量数据更利于合成数据生成——我们在 QA（问答）生成这一步正是这样做的。这让模型从"高质量"notebook 而非噪声 notebook 中学习。

### 4. 过滤无关 notebook

我们排除了关于训练 LLM 的、或与数据分析无关的 notebook。还通过一个基于 LLM 的自动过滤流程（使用 Qwen3-32B），移除了实际没有使用数据集的 notebook。过滤实现见 [`extract_packages_and_files.py`](https://github.com/huggingface/jupyter-agent/blob/main/data/pipelines/extract_packages_and_files.py)。

**TL;DR：** 我们提示 Qwen3-32B 识别并移除两类 notebook：(1) 与数据分析无关的，或 (2) 实际没用数据集的。这一步去掉了约 20% 的 notebook。

这保证我们只用相关的数据科学任务数据训练。

### 5. QA 生成

利用清洗后的 notebook，我们用 [Qwen3-32B](https://huggingface.co/Qwen/Qwen3-32B) 生成问答对。问题和答案都锚定在真实的 notebook 轨迹上，因此 QA 对基于真实的代码执行结果。**提示词设计：** 我们要求 LLM 产出对数据集来说真实可问的自然问题，然后验证 notebook 是否给出了正确答案。

*挑战：* 要得到更高难度的问题，我们试了很多 prompt，因为 LLM 倾向于生成"数据集有多大"这类琐碎问题。
*经验：* 我们把它拆成两步，因为 LLM 倾向于幻觉答案：

- 生成问题和答案。
- 让另一个 LLM（可以访问该 notebook）检查答案是否正确。

完整的提示词策略和实现见 [`generate_qa.py`](https://github.com/huggingface/jupyter-agent/blob/main/data/pipelines/generate_qa.py)。

### 6. 轨迹生成

最后我们想生成干净的代码执行轨迹，因为即便是处理后的原始 notebook 也常常开放、冗长、夹杂大量无关部分。而我们要让 Jupyter Agent 高效地直达结果。为生成用于训练的更干净 notebook 轨迹，我们基于原 notebook 合成了轨迹。
我们提示 [Qwen-3-Coder-480B](https://huggingface.co/Qwen/Qwen3-Coder-480B-A35B-Instruct) 模型生成一段 jupyter notebook 代码，回答此前合成的 QA 对中的问题。轨迹记录了逐步的代码执行，包括中间输出——这对 agent 训练至关重要。

我们用 [E2B](https://e2b.dev/) 让 agent 解这些合成的 QA 对；为了让代码真能跑，需要通过 E2B 拉取 Kaggle 数据集。

*挑战 1：* 很多数据集不可用。
*技巧：* 既然 LLM 擅长代码且有相当的世界模型，当数据集缺失时，我们提示它们**扮演代码解释器**。

提示词开头：

```
You are a stateful Python code interpreter that executes code in a persistent environment. Your role is to execute Python code while maintaining state across multiple code cells, similar to a Jupyter notebook environment.
[REST OF THE PROMPT]
```

*挑战 2：* [Qwen3-Coder-480B-A35B](https://huggingface.co/Qwen/Qwen3-Coder-480B-A35B-Instruct) 模型不支持 thinking 模式——怎么提取代码注释？默认它往往只输出一句简短注释加几步代码执行。但我们希望每个单元之间都有推理或注释。*技巧：* 从 [Qwen3-32B](https://huggingface.co/Qwen/Qwen3-32B) 切换到 [Qwen3-Coder-480B-A35B](https://huggingface.co/Qwen/Qwen3-Coder-480B-A35B-Instruct) 时，我们注意到输出消息内容经常为空。这原来是 Qwen3-Coder 模型的一个已知怪癖：使用 tool calling 时模型不会返回空的 assistant 响应。我们通过工具调用强制附带文字注释——在代码执行工具的调用里把 'comment' 设为必填字段。这样，用非推理模型生成代码单元时，它默认会输出一些第一人称的动作描述，模拟 thinking 轨迹的结构。

**注意：** notebook 中生成的最终答案可能与 QA 对里指定的答案不一致。原因是 agent 模型可能使用与原 Kaggle notebook 不同的数据预处理方法和步骤，而合成的问题通常不会指定这些。这种差异是正常的，也为一个有趣的新研究方向打下基础：语言模型如何看待数据分析，以及它们的做法是否与人类不同。为了完全透明，我们同时保留 LLM 生成的最终答案和真实 Kaggle notebook 的原始答案，作为模型表现的信号。欢迎社区尝试不同的数据配比，看看能把性能推到多高。

### 7. 最终整理

我们截断过长的输出、过滤琐碎轨迹，以避免内容长度问题，只保留高质量轨迹。
保留了非平凡、多轮、与 DABStep 风格任务对齐的轨迹。
产出的 [Jupyter Agent Dataset](https://huggingface.co/datasets/jupyter-agent/jupyter-agent-dataset) 成为在 Qwen3-4B 上做 SFT 的基础，包含 5.1 万个合成 notebook 和近 2 亿 token。

有了这个数据集，下一步自然是检验它能否真正让我们的模型变成更强的数据科学 agent。接着看训练 pipeline 和评估影响！

## 🏃‍♂️ 训练 Pipeline

数据集整理就绪，我们转向核心问题：**这些数据真的能帮助模型更好地解决数据分析任务吗？** 为了验证，我们搭了一条简单的微调 pipeline，跑实验测量在合成 notebook 上训练带来的影响。

一些训练步骤特别有意思，给了我们有用的启发：

- 轨迹生成时，我们用 LLM 生成 QA 对，得到一个**可验证的环境**。
- 最后用 [TRL](https://huggingface.co/docs/trl) 微调 **Qwen3-4B**。使用 `assistant_loss_only=True` → 小幅性能提升。全参数多轮训练时加入 neftune 噪声 → 避免过拟合。

**挑战：**

- 用提示词让模型做 tool calling 很讲究：不同 prompt 的性能并不一样（[Qwen 文档](https://qwen.readthedocs.io/en/latest/framework/function_call.html#vllm)）。
- 我们不得不逐个手动测试，找出效果最好的。
- tool calling 的响应格式没有标准化，模型之间切换很麻烦。
- Qwen 原生的 generation prompt 不适配 TRL 的 `assistant_loss_only=True` 训练模式（该模式默认要求有 generation tokens）。因此我们改编了原始 chat template，把 assistant 回复部分包进 generation 标签。
- 用短推理文本训练 thinking 模型可能破坏模型能力 → 这种情况下全参数训练比 PEFT 效果更好。

完整的训练实现，包括超参配置和模板适配，都在我们仓库的 [finetuning 目录](https://github.com/huggingface/jupyter-agent/tree/main/finetuning)。

## 📊 结果

首先，我们用 [Qwen3-Coder-480B-A35B](https://huggingface.co/Qwen/Qwen3-Coder-480B-A35B-Instruct) 生成了最终数据集，其中包含高质量代码和简短的类推理轨迹。随后开始训练，尝试了各种配置：PEFT/adapter 对全参数微调、学习率、训练轮数、加噪声等。我们发现全参数微调让模型学得更好，能复制 [Qwen3-Coder-480B-A35B](https://huggingface.co/Qwen/Qwen3-Coder-480B-A35B-Instruct) 的行为响应质量：更短的辅助注释更贴合数据分析任务，没有不必要的冗长推理。

我们做了一个小型消融研究，考察训练轮数的影响：

| 模型 | 训练轮数 | DABstep (Easy) |
| --- | --- | --- |
| Qwen-3-4B-Instruct-2507（基座） | 0 | 38.67% |
| Qwen-3-4B-Instruct-2507（我们的脚手架） | 0 | 52.78% |
| Qwen-3-4B-Instruct-2507 | 2 | 63.89% |
| Qwen-3-4B-Instruct-2507 | 3 | 73.61% |
| Qwen-3-4B-Instruct-2507 | 5 | **75%** |
| Qwen-3-4B-Instruct-2507 | 7 | 70.83% |

我们观察到，SFT 时用比平常略多的轮数、更低的学习率和更高的 neftune 噪声（7）是有益的。最后，我们把训练好的模型搭配实现的脚手架一起对比，以确定训练数据集的纯粹影响。总之，相比基座/带脚手架模型，DABStep easy 分数最高提升 36%/22%：

还可以看到，尽管我们的数据集聚焦较简单的问题，hard 分数也能提升：

从上面的数字可以明显看到，新脚手架和在合成 notebook 上调优双双带来可观影响。这让 Qwen-4B（配合我们的 pipeline + 脚手架）成为 DABStep 上小模型 agent 的 SOTA。

实际使用中，模型现在能以稳定的执行解决大量真实的 Kaggle 风格数据分析任务。
面对最难的问题它还不够强，但我们已经证明：只要数据和对的脚手架，小模型也能成为强大的 agent。

按照 Qwen 文档的代码即可使用调优后的 Jupyter Agent Qwen 模型：

```
from transformers import AutoModelForCausalLM, AutoTokenizer

model_name = "jupyter-agent/jupyter-agent-qwen3-4b-instruct"

# load the tokenizer and the model
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype="auto",
    device_map="auto"
)

# prepare the model input
prompt = "Give me a short introduction to large language model."
messages = [
    {"role": "user", "content": prompt}
]
text = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
)
model_inputs = tokenizer([text], return_tensors="pt").to(model.device)

# conduct text completion
generated_ids = model.generate(
    **model_inputs,
    max_new_tokens=16384
)
output_ids = generated_ids[0][len(model_inputs.input_ids[0]):].tolist() 

content = tokenizer.decode(output_ids, skip_special_tokens=True)

print("content:", content)
```

对于 Thinking 模型，可以用下面的代码分别解码思考内容和正文：

```
from transformers import AutoModelForCausalLM, AutoTokenizer

model_name = "jupyter-agent/jupyter-agent-qwen3-4b-thinking"

# ...use same processing code from above...
try:
    # index finding 151668 (</think>)
    index = len(output_ids) - output_ids[::-1].index(151668)
except ValueError:
    index = 0

thinking_content = tokenizer.decode(output_ids[:index], skip_special_tokens=True).strip("\n")
content = tokenizer.decode(output_ids[index:], skip_special_tokens=True).strip("\n")
```
