[Transformers v5](https://huggingface.co/blog/transformers-v5) 重新设计了分词器的工作方式。[大规模 tokenizers 重构](https://github.com/huggingface/transformers/pull/40936/files)把分词器的设计与训练得到的词表分离开来（正如 PyTorch 把神经网络架构与学习到的权重分离）。结果是：分词器现在可以被*检查*、*定制*，甚至低摩擦地*从零训练*。

> TL;DR：本博客解释分词在 Transformers 中如何工作、为什么 v5 是一次大改版——内部机制更清晰、类层级干净、单一快速后端。这是一份实用指南，适合想理解、定制或训练模型专属分词器，而不是把它们当黑盒的人。

## 什么是分词？

语言模型不读原始文本。它们消费的是通常称为 **token ID 或 input ID** 的整数序列。分词就是把原始文本转换成这些 token ID 的过程。（可以在[这个分词 playground](https://huggingface.co/spaces/Xenova/the-tokenizer-playground) 里可视化体验分词。）

分词是贯穿自然语言处理和文本处理的广泛概念。本文聚焦于使用 [`transformers`](https://github.com/huggingface/transformers) 和 [`tokenizers`](https://github.com/huggingface/tokenizers) 库为大语言模型（LLM）做的分词。

```
from transformers import AutoTokenizer
tokenizer = AutoTokenizer.from_pretrained("HuggingFaceTB/SmolLM3-3B")

text = "Hello world"
tokens = tokenizer(text)

print(tokens["input_ids"])
# [9906, 1917]

print(tokenizer.convert_ids_to_tokens(tokens["input_ids"]))
# ['Hello', 'Ġworld']
```

> Ġworld（上面）是一个单独的 token，代表带空格的字符序列 " world"。

**token** 是模型看到的最小字符串单元。它可以是一个字符、一个词，或像 "play"、"##ing" 这样的子词块（"##" 是一种模式，现在不完全理解也没关系 🤗）。**词表（vocabulary）**把每个唯一 token 映射到 token ID。

```
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("HuggingFaceTB/SmolLM3-3B")
print(tokenizer.vocab)

# {'ÎĹÎľ': 106502, 'ĠPeel': 89694, '.languages': 91078, ...}
```

好的分词器会把文本*压缩*成尽可能少的 token。token 更少，就意味着在不增大模型的前提下能用更多上下文。训练分词器归根到底是为目标数据集找到最好的压缩规则。比如处理中文语料时，有时会有[非常惊喜的发现 😉](https://x.com/suchenzang/status/1697862650053660721)。

## 分词管线

分词分阶段进行。每个阶段变换文本后传给下一个：

| 阶段 | 作用 | 示例 |
| --- | --- | --- |
| **Normalizer（规范化器）** | 标准化文本（小写化、unicode 规范化、空白清理） | `"HELLO World"` → `"hello world"` |
| **Pre-tokenizer（预分词器）** | 把文本切成初步块 | `"hello world"` → `["hello", " world"]` |
| **Model（模型）** | 应用分词算法（BPE、Unigram 等） | `["hello", " world"]` → `[9906, 1917]` |
| **Post-processor（后处理器）** | 添加特殊 token（BOS、EOS、padding） | `[9906, 1917]` → `[1, 9906, 1917, 2]` |
| **Decoder（解码器）** | 把 token ID 转回文本 | `[9906, 1917]` → `"hello world"` |

每个组件都是*独立的*。你可以换 [normalizer](https://huggingface.co/docs/tokenizers/en/api/normalizers) 或改[算法](https://huggingface.co/docs/tokenizers/en/api/models)，而不必重写其他任何东西。

> 可以通过 _tokenizer 访问基于 Rust 的分词器。本节会深入讲这一点。

```
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("google/gemma-3-270m-it")

print(f"{tokenizer._tokenizer.normalizer=}")
# Replace(...)

print(f"{tokenizer._tokenizer.pre_tokenizer=}")
# Split(...)

print(f"{tokenizer._tokenizer.model=}")
# BPE(...)

print(f"{tokenizer._tokenizer.post_processor=}")
# TemplateProcessing(...)

print(f"{tokenizer._tokenizer.decoder=}")
# Sequence(decoders=[Replace(...), ByteFallback(), Fuse()])
```

## 分词算法

现代语言模型分词器以以下几种算法为主：

- **字节对编码（BPE）**：迭代合并出现频率最高的字符对。该算法是确定性的、应用最广。（延伸阅读：[BPE](https://huggingface.co/learn/llm-course/en/chapter6/5)）

```
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("openai/gpt-oss-20b")
print(tokenizer._tokenizer.model)

# BPE(...)
```

- **Unigram**：走概率路线，从一个很大的初始词表中选出最可能的切分。相比严格的 BPE 更灵活。（延伸阅读：[Unigram](https://huggingface.co/learn/llm-course/en/chapter6/7)）

```
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("google-t5/t5-base")
print(tokenizer._tokenizer.model)

# Unigram(...)
```

- **WordPiece**：类似 BPE，但合并准则基于似然。（延伸阅读：[WordPiece](https://huggingface.co/learn/llm-course/en/chapter6/6)）

```
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("bert-base-uncased")
print(tokenizer._tokenizer.model)

# WordPiece(...)
```

## 通过 transformers 访问 tokenizers

[`tokenizers`](https://github.com/huggingface/tokenizers) 库是一个基于 Rust 的分词引擎：快、高效、完全与语言模型无关。它负责把文本变成 token ID、再变回来的机制。`tokenizers` 是通用工具，实现了分词算法，但没有实现"把算法接到具体语言模型上"的那些约定。

看看直接用 `tokenizers` 配 [`SmolLM3-3B`](http://hf.co/HuggingFaceTB/SmolLM3-3B) 模型会发生什么：

```
from tokenizers import Tokenizer

tokenizer = Tokenizer.from_pretrained("HuggingFaceTB/SmolLM3-3B")
text = "Hello world"
encodings = tokenizer.encode(text)

print(encodings.ids)
# [9906, 1917]
print(encodings.tokens)
# ['Hello', 'Ġworld']
```

输出是原样分词结果：token ID 和它们对应的字符串片段，仅此而已。

再想想缺了什么。`SmolLM3-3B` 是一个*对话模型*。与它交互时，输入通常组织成带 "user"、"assistant" 等角色的对话，语言模型期望有特殊格式 token 来标示这些角色。原始的 `tokenizers` 库完全没有这些概念。

### 如何弥合原始分词与模型需求之间的鸿沟？

`transformers` 库就是这座桥。它以"模型定义库"著称，但同时提供了一层分词器抽象，把原始 `tokenizers` 后端包起来，加上面向模型的功能。

用 `transformers` 的包装做同样的分词：

```
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("HuggingFaceTB/SmolLM3-3B")

# Format a conversation using the model's chat template
prompt = "Give me a brief explanation of gravity in simple terms."
messages = [{"role": "user", "content": prompt}]
text = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
)

print(text)

# <|im_start|>system
# ...
# <|im_start|>user
# Give me a brief explanation of gravity in simple terms.<|im_end|>
# <|im_start|>assistant

model_inputs = tokenizer([text], add_special_tokens=False, return_tensors="pt")
```

注意，`<|im_start|>` 和 `<|im_end|>` 等特殊 token 在分词之前就已经插入 prompt 中。这有助于模型学习一段新序列从哪里开始、在哪里结束。

`transformers` 的 tokenizer 补齐了底层库缺少的功能：

- **应用对话模板。** `apply_chat_template` 按模型预期的格式组织对话，插入正确的特殊 token 和分隔符。
- **自动插入特殊 token。** 在模型预期的位置加入序列起始和结束 token。
- **按上下文长度截断。** 指定 `truncation=True` 后，tokenizer 会遵守模型的最大序列长度。
- **批量编码与 padding。** 可以一次编码多个输入，并按正确的 padding token 和方向把它们补到相同长度。
- **返回格式选项。** 可以请求返回 PyTorch tensor（`return_tensors="pt"`）、NumPy 数组等格式。

> transformers 实现了整个 ML 社区最常用的分词 API，包括 encode、decode、convert_tokens_to_ids 等。

## Transformers 中的 tokenizer 类层级

`transformers` 库用类层级组织 tokenizer。最上层是定义公共接口的基类。其下是后端类，负责调用不同的引擎实现分词。最下层是面向具体模型的类，为各自的模型配置这些后端。

| --- |
| transformers 库中的 tokenizer 类层级 |

### `PreTrainedTokenizerBase` 定义公共接口

[`PreTrainedTokenizerBase`](https://github.com/huggingface/transformers/blob/7f52a2a4ea8ab49b7f069df7fac58a5b280d4919/src/transformers/tokenization_utils_base.py#L964C7) 是 Transformers 中所有 tokenizer 的抽象基类，定义了它们共有的接口。

基类负责所有与分词后端无关的功能：

- **特殊 token 属性。** `bos_token`、`eos_token`、`pad_token` 和 `unk_token` 等属性让调用方可以访问模型的特殊标记。
- **编码接口。** `__call__`、`encode` 和 `encode_plus` 都接收文本输入并返回编码结果。
- **解码接口。** `decode` 和 `batch_decode` 将 token 转回文本。
- **序列化。** `save_pretrained` 和 `from_pretrained` 负责加载正确的文件、读取词表信息等工作。
- **对话模板支持。** `apply_chat_template` 方法定义在这里，使用 tokenizer 配置中保存的 Jinja 模板。

无论底层分词引擎是什么，`transformers` 中每个 tokenizer 最终都继承自这个类。因此，调用方可以始终使用同一套 API。

### `TokenizersBackend` 封装 `tokenizers` 库

[`TokenizersBackend`](https://github.com/huggingface/transformers/blob/7f52a2a4ea8ab49b7f069df7fac58a5b280d4919/src/transformers/tokenization_utils_tokenizers.py#L80C7) 是现代 tokenizer 的主要后端。它继承自 `PreTrainedTokenizerBase`，并封装基于 Rust 的 `tokenizers` 库。

这个类在内部保存 Rust tokenizer 对象：

```
class TokenizersBackend(PreTrainedTokenizerBase):
    def __init__(self, tokenizer_object, ...):
        self._tokenizer = tokenizer_object  # The Rust tokenizer
        ...
```

调用 `TokenizersBackend` 上的编码方法时，类会把实际分词交给 Rust 后端：

```
def _batch_encode_plus(self, batch_text_or_text_pairs, ...):
    encodings = self._tokenizer.encode_batch(batch_text_or_text_pairs, ...)
    ...
```

由于实际分词在 Rust 中执行，`TokenizersBackend` 提供了高性能的分词能力。Python 封装层负责对话模板、特殊 token 管理、padding 和截断等模型相关行为。

许多面向具体模型的类都继承自 `TokenizersBackend`，例如：

- `LlamaTokenizer`
- `GemmaTokenizer`

这些面向具体模型的类会为各自的模型配置后端、特殊 token 和归一化设置。

### `PythonBackend` 提供纯 Python mixin

[`PythonBackend`](https://github.com/huggingface/transformers/blob/7f52a2a4ea8ab49b7f069df7fac58a5b280d4919/src/transformers/tokenization_python.py#L400) 继承自 `PreTrainedTokenizerBase`，用纯 Python 实现分词。它的别名是 [`PreTrainedTokenizer`](https://github.com/huggingface/transformers/blob/7f52a2a4ea8ab49b7f069df7fac58a5b280d4919/src/transformers/tokenization_python.py#L1400C1)。

纯 Python 后端有两种用途：

- **自定义分词逻辑。** 有些模型需要标准 `tokenizers` 流水线不支持的行为。
- **旧版兼容。** 早期模型的实现可能依赖 Python 特有的行为。

> Python 后端比 Rust 后端慢。大多数场景优先使用基于 Rust 的 TokenizersBackend。

一些较早或面向特殊用途的 tokenizer 继承自 `PythonBackend` 或其别名 `PreTrainedTokenizer`，例如：

- `CTRLTokenizer`
- `CanineTokenizer`

### `SentencePieceBackend` 处理 SentencePiece 模型

[`SentencePieceBackend`](https://github.com/huggingface/transformers/blob/7f52a2a4ea8ab49b7f069df7fac58a5b280d4919/src/transformers/tokenization_utils_sentencepiece.py#L46) 继承自 `PythonBackend`，集成了 Google 的 [SentencePiece](https://github.com/google/sentencepiece) 库。SentencePiece 是一个独立的分词库，许多模型都在使用它，尤其是 Google 训练的模型。

这个后端封装了一个 SentencePiece processor：

```
class SentencePieceBackend(PythonBackend):
    def __init__(self, vocab_file, ...):
        self.sp_model = spm.SentencePieceProcessor()
        self.sp_model.Load(vocab_file)
        ...
```

使用 SentencePiece 分词的模型继承自这个后端，例如：

- `SiglipTokenizer`
- `BartphoTokenizer`

SentencePiece 后端与 `PythonBackend` 共享许多接口以及 padding 和截断逻辑，因此继承自 `PythonBackend`，无须直接继承 `PreTrainedTokenizerBase`。

## AutoTokenizer 自动选择正确的 tokenizer 类

[`AutoTokenizer`](https://github.com/huggingface/transformers/blob/7f52a2a4ea8ab49b7f069df7fac58a5b280d4919/src/transformers/models/auto/tokenization_auto.py#L531) 是加载 tokenizer 的主要入口。它根据模型配置自动确定并实例化正确的 tokenizer 类。

```
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("gpt2")
```

调用 `AutoTokenizer.from_pretrained("model-name")` 时，内部流程如下：

- **下载 tokenizer 配置。** `from_pretrained` 从 Hub 或本地目录获取 `config.json` 文件。
- **识别模型类型。** 配置中包含[标明模型类型的元数据](https://huggingface.co/openai-community/gpt2/blob/main/config.json#L12)，例如 `"gpt2"`、`"llama"` 或 `"bert"`。
- **查找 tokenizer 类。** `AutoTokenizer` 维护一个叫 [`TOKENIZER_MAPPING_NAMES`](https://github.com/huggingface/transformers/blob/7f52a2a4ea8ab49b7f069df7fac58a5b280d4919/src/transformers/models/auto/tokenization_auto.py#L64) 的映射表，将模型类型映射到 tokenizer 类名：

```
TOKENIZER_MAPPING_NAMES = {
    "gpt2": "GPT2Tokenizer",
    "llama": "LlamaTokenizer",
    "bert": "BertTokenizer",
    ...
}
```

- **实例化正确的类。** `AutoTokenizer` 导入对应的类，调用其 `from_pretrained()` 方法，并把分词文件和配置传入。
- **返回可用的 tokenizer。** 返回结果是模型对应的 tokenizer 类实例，例如 `GPT2Tokenizer` 或 `LlamaTokenizer`。

> 使用 AutoTokenizer 时，无需事先知道模型使用哪个 tokenizer 类。无论模型使用 LlamaTokenizer、GPT2Tokenizer 还是其他类，同一个 `AutoTokenizer.from_pretrained("model-name")` 调用都能加载它。

`transformers` 的分词系统分为以下几层：

| 层级 | 组件 | 职责 |
| --- | --- | --- |
| 入口 | `AutoTokenizer` | 自动选择并实例化正确的 tokenizer 类 |
| 模型层 | `LlamaTokenizer`、`GPT2Tokenizer` 等 | 配置归一化器、预分词器、分词模型、后处理器、解码器 |
| 后端层 | `TokenizersBackend`、`SentencePieceBackend`、`PythonBackend` | 封装分词引擎，实现公共行为 |
| 引擎层 | Rust（`tokenizers`）、SentencePiece、纯 Python | 执行实际分词 |
| 基类 | `PreTrainedTokenizerBase` | 定义所有 tokenizer 的公共接口 |

## v5 将 tokenizer 架构与训练所得词表分开

Transformers v5 最重要的变化是设计思路的转变。**Tokenizer 现在像 PyTorch 的 `nn.Module` 一样工作**：先定义架构，再填入学习得到的参数。

### v4 的问题：tokenizer 不透明，组件紧耦合

在 v4 中，tokenizer 是和预训练 checkpoint 紧耦合的黑盒。载入 `LlamaTokenizerFast` 后，很难直接回答以下问题：

- 它用的是 BPE 还是 Unigram？
- 它如何归一化文本？
- 它使用哪种预分词策略？
- 它有哪些特殊 token，分别放在什么位置？

`__init__` 方法没有提供多少信息。必须查看序列化文件或外部文档，才能弄清 tokenizer 实际做了什么。

| [![v4 Llama](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/tokenizers/v4-llama.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/tokenizers/v4-llama.png) |
| --- |
| v4 `transformers` 中的 `LlamaTokenizerFast` |

v4 还为每个模型并行维护两套实现：

- “慢速” Python tokenizer（`LlamaTokenizer` 继承自 `PreTrainedTokenizer`）
- “快速” Rust tokenizer（`LlamaTokenizerFast` 继承自 `PreTrainedTokenizerFast`）

这带来了几个问题：

- **代码重复。** 两套 tokenizer 分别放在 `tokenization_llama.py` 和 `tokenization_llama_fast.py` 中。
- **行为差异。** 快速和慢速版本存在细微差别，容易引入 bug。
- **用户难以选择。** 用户需要知道什么时候选慢速或快速版本，也要理解 `use_fast` 参数。
- **维护负担。** 测试套件里有多个测试专门验证慢速和快速版本的行为一致。

更麻烦的是，你无法创建空的 tokenizer 架构。如果想用自己的数据训练 LLaMA 风格的 tokenizer，很难先实例化一个“空白”的 `LlamaTokenizer`，再填入词表和合并规则。Tokenizer 以已加载的 checkpoint 形式存在，无法充当可配置模板。

### v5 的方案：分开定义架构与参数

v5 把 tokenizer 架构（归一化器、预分词器、模型类型、后处理器、解码器）和学习得到的参数（词表、合并规则、特殊 token ID）分开。这沿用了 PyTorch 将模型架构与学习所得权重分开管理的做法。

**用 `nn.Module` 时，先定义各层：**

```
from torch import nn

model = nn.Sequential(
    nn.Embedding(vocab_size, embed_dim),
    nn.Linear(embed_dim, hidden_dim),
)
# Architecture defined; weights initialized randomly or loaded later
```

**v5 tokenizer 采用同样的方式：**

```
from transformers import LlamaTokenizer

# Instantiate the architecture
tokenizer = LlamaTokenizer()

# Train on your own data to fill in vocab and merges
tokenizer.train(files=["my_corpus.txt"])
```

Tokenizer 类现在显式声明自身结构。查看 v5 的 `LlamaTokenizer` 就能立即看出：

- 它的分词模型[使用 **BPE**](https://github.com/huggingface/transformers/blob/0a8465420eecbac1c6d7dd9f45c08dd96b8c5027/src/transformers/models/llama/tokenization_llama.py#L92)
- 它可以添加**前缀空格**
- 它的特殊 token（`unk`、`bos`、`eos`）在指定位置插入
- 它[**不对输入文本做归一化**](https://github.com/huggingface/transformers/blob/0a8465420eecbac1c6d7dd9f45c08dd96b8c5027/src/transformers/models/llama/tokenization_llama.py#L121)
- 它的[解码器](https://github.com/huggingface/transformers/blob/0a8465420eecbac1c6d7dd9f45c08dd96b8c5027/src/transformers/models/llama/tokenization_llama.py#L122)把 metaspace 字符 `▁` 替换成空格

| --- |
| v5 `transformers` 中的 `LlamaTokenizer` |

在 v4 中，和快速版本等效的信息藏在序列化文件里。现在这些信息可以直接在类定义中查看。

### 每个模型一个文件、一套后端、一条推荐路径

v5 把原来的两文件系统*合并为每个模型一个文件*。`LlamaTokenizer` 现在封装 `TokenizersBackend`，后者再封装 Rust 库 `tokenizers`。Rust 后端原先由单独的 `LlamaTokenizerFast` 使用，现在成为默认实现。

这一变更消除了以下问题：

- 慢速与快速实现之间的代码重复
- `Tokenizer` 和 `TokenizerFast` 的命名混淆

早期的“慢速” Python 实现通过显式的 `PythonBackend` 提供。需要 SentencePiece 时也仍可使用 `SentencePieceBackend`。默认优先使用 Rust 后端。

现在只有一个入口、一个类名和一条推荐路径。有特定需求的高级用户仍可访问更底层的组件，日常用法则更容易理解。

### 现在可以从头训练面向特定模型的 tokenizer

假设你希望训练一个架构与 LLaMA 完全相同的 tokenizer，保留相同的归一化、预分词、BPE 模型类型和解码方式，使用自己的词表。在 v4 中，这意味着要在目标语言或领域重新实现 LLaMA 的分词流程。现在可以直接实例化该架构并在自己的语料上训练：

```
from transformers import LlamaTokenizer
from datasets import load_dataset

# Initialize blank tokenizer
tokenizer = LlamaTokenizer()

dataset = load_dataset("wikitext", "wikitext-2-raw-v1", split="train")

def get_training_corpus():
    batch = 1000
    for i in range(0, len(dataset), batch):
        yield dataset[i : i + batch]["text"]

trained_tokenizer = tokenizer.train_new_from_iterator(
    text_iterator=get_training_corpus(),
    vocab_size=32000,
    length=len(dataset),
    show_progress=True,
)

trained_tokenizer.push_to_hub("my_custom_tokenizer")

tokenizer = LlamaTokenizer.from_pretrained("my_custom_tokenizer")
```

生成的 tokenizer 会使用你的自定义词表和合并规则，并在空格处理、特殊 token 约定和解码等方面保持标准 LLaMA tokenizer 的行为。

| 维度 | v4 | v5 |
| --- | --- | --- |
| 每个模型的文件数 | 两个（`tokenization_X.py`、`tokenization_X_fast.py`） | 一个（`tokenization_X.py`） |
| 默认后端 | Python 为慢速，Rust 为快速 | Rust（`TokenizersBackend`）优先 |
| 架构可见性 | 藏在序列化文件中 | 在类定义中显式声明 |
| 从头训练 | 需要手动搭建流程 | `tokenizer.train(files=[...])` |
| 组件检查 | 难以判断实际用了哪些组件 | 直接访问 `tokenizer.normalizer` 等属性 |
| 父类 | `PreTrainedTokenizer`、`PreTrainedTokenizerFast` | `TokenizersBackend`（或 `SentencePieceBackend`、`PythonBackend`） |

从“作为已加载 checkpoint 的 tokenizer”转向“作为可配置架构的 tokenizer”，使这个库更模块化、更透明，也更贴合开发者构建 ML 系统的思路。

## 总结

Transformers v5 对分词带来了三项改进：

- **每个模型一个文件**，将慢速和快速实现合在一起。
- **架构可见**，可以直接查看归一化器、预分词器和解码器。
- **可训练的模板**，可以从头构建与任意模型设计相匹配的自定义 tokenizer。

`tokenizers` 与 Transformers 之间的封装层依然不可或缺。它处理模型相关逻辑、上下文长度、对话模板和特殊 token，而底层的分词引擎并不处理这些信息。v5 让这层封装更清晰，也更容易定制。
