# 介绍 **HELMET**：全面评估长上下文语言模型

Howard Yen（hyen，princeton-nlp）、Tianyu Gao（gaotianyu1350，princeton-nlp）、Minmin Hou（houminmin，Intel）、Ke Ding（kding1，Intel）、Daniel Fleischer（danf，Intel）、Moshe Wasserblat（moshew，Intel）、Danqi Chen（cdq10131，princeton-nlp）

联系：[hyen@cs.princeton.edu](mailto:hyen@cs.princeton.edu)
论文：[https://arxiv.org/abs/2410.02694](https://arxiv.org/abs/2410.02694)
网站：[https://princeton-nlp.github.io/HELMET](https://princeton-nlp.github.io/HELMET)
代码与数据：[https://github.com/princeton-nlp/HELMET](https://github.com/princeton-nlp/HELMET)

自去年 10 月我们首次发布 HELMET 以来，长上下文语言模型领域的发展比以往任何时候都多，我们看到社区对 HELMET 的采用——比如 [Microsoft 的 Phi-4](https://arxiv.org/abs/2412.08905) 和 [AI21 的 Jamba 1.6](https://www.ai21.com/blog/introducing-jamba-1-6/)——非常高兴。初次发布之后，我们又向评估套件加入了更多模型，并做了额外分析。我们很高兴分享新的结果，并在 ICLR 2025 上展示 HELMET！

在这篇博客里，我们会介绍 HELMET 的构建、我们的关键发现，以及从业者在未来的研究和应用中如何用 HELMET 区分各种 LCLM。最后，我们会以一份在 HuggingFace 上使用 HELMET 的快速上手指南收尾。

## 评估长上下文语言模型很有挑战，但很重要

从摘要海量法律文档，到即时学习新任务，长上下文语言模型（LCLM）有巨大潜力改变我们使用和与语言模型交互的方式。语言模型一直受其上下文窗口限制，大约在 2K 到 8K token（例如 [ChatGPT](https://openai.com/index/chatgpt/)、[Llama-2/3](https://arxiv.org/abs/2407.21783)）。近期，模型开发者不断扩充模型的上下文窗口，像 [GPT-4o](https://openai.com/index/hello-gpt-4o/)、[Claude-3](https://www.anthropic.com/news/claude-3-family) 和 [Gemini-1.5](https://blog.google/technology/ai/google-gemini-next-generation-model-february-2024/#ethics-safety) 这样的新模型支持多达数百万 token 的上下文窗口。

图 1：现有基准呈现出违反直觉的趋势，比如小模型反而胜过大模型（例如 Llama-3.1 8B > 70B）。

然而，随着上下文窗口变长，之前的自然语言基准（例如 [Scrolls](https://arxiv.org/abs/2201.03533)）不再适合评估 LCLM。于是困惑度（perplexity）和合成任务（如大海捞针 needle-in-a-haystack）成了近期 LCLM 最常用的评估指标，但它们往往**不能反映真实性能**。模型开发者也可能在其他任意的数据集上评估，这让模型对比变得复杂。此外，现有的 LCLM 基准有时会给出令人困惑、违反直觉的结果，让人难以理解不同模型的强弱（图 1）。

在这项工作中，我们提出 HELMET（How to Evaluate Long-Context Models Effectively and Thoroughly），一个评估 LCLM 的全面基准，在多个方面改进了现有基准——*多样性、可控性和可靠性*。我们评估了 59 个近期 LCLM，发现要在多样化应用上评估模型才能理解其能力，而前沿 LCLM 在复杂任务上仍然受限。

## 现有评估过度依赖合成任务

随着 LCLM 在工业界和开源社区同时发展，拥有一个可靠的评估和对比这些模型的方法至关重要。然而，当前模型*常常在不同的基准上被评估*（表 1）。

表 1：模型开发者常常在不同数据集集合上评估。

♭

：Base 模型。NQA：NarrativeQA，Qspr：Qasper，QALT：QuALITY，SQALT：SQuALTY。

评估长上下文语言模型的一个常见做法是用困惑度或合成任务，比如大海捞针（NIAH）。但近期研究表明，困惑度与下游性能并不太相关（[Fang et al., 2024](https://arxiv.org/abs/2410.23771)）。在图 2 里我们展示，像 NIAH 这样的合成任务与真实性能并不相关，但更复杂的合成任务与真实任务有更高的相关性。

图 2：简单合成任务（如 NIAH）与下游任务（如摘要或带引用的生成）相关性不高。更复杂的变体（如 RULER MV）相关性更高。

在那些有真实应用的现有基准中，如 ZeroScrolls（[Shaman et al., 2023](https://arxiv.org/abs/2308.14508)）、LongBench（[Bai et al., 2024](https://arxiv.org/abs/2308.14508)）和 InfiniteBench（[Zhang et al., 2024](https://arxiv.org/abs/2402.13718)），仍存在关键局限：

- 下游任务覆盖不足：往往聚焦特定领域
- 测试前沿 LCLM 的长度不够：旧的 QA 数据集常常限于 <32K token（例如 [QASPER](https://arxiv.org/abs/2105.03011)、[QuALITY](https://arxiv.org/abs/2112.08608)）
- 指标不可靠：像 ROUGE 这样的 N-gram 匹配指标噪声很大——它们与人类判断不相关（[Goyal et al., 2023](https://arxiv.org/abs/2209.12356)），也无法区分模型
- 与 base 模型不兼容：需要指令微调，意味着它们无法用于 base 模型开发

因此，我们提出 HELMET 来应对这些局限，提供对 LCLM 的全面评估。

## 为 LCLM 打造多样、可控、可靠的评估

我们按以下诉求设计 HELMET：

- 对下游任务的多样覆盖
- 可控的长度与复杂度
- 对 base 和指令微调模型都可靠的评估

### 相较现有基准的关键改进

***多样覆盖***：HELMET 包含一组多样的任务，如基于真实检索段落的检索增强生成、带引用的生成，以及摘要。我们精心挑选那些具有自然长上下文、能反映真实应用的数据集。这些数据集配合可靠的评估设置，如基于模型的评估和人类研究。

***可控的长度与难度***：评估 LCLM 时要考虑的一个重要维度是输入长度，因为更长的输入既能提供更多信息，也会考验模型处理噪声上下文的能力。在我们的任务里，我们可以通过改变检索段落的数量（RAG、Cite、Re-rank）、示例 demonstrations 的数量（ICL），或输入文档的长度（LongQA、Summ）来控制输入长度。尽管 LongQA 和 Summ 不易扩展到更长的上下文，我们有意选择了自然文档长度远超 100K token 的数据集，使它们仍能用于评估前沿 LCLM。

***可靠的评估***：许多现有基准尽管与人类判断相关性很差（[Goyal et al., 2023](https://arxiv.org/abs/2209.12356)），仍在用基于 n-gram 的指标，比如 ROUGE。我们采用基于模型的评估，它在区分不同模型和不同输入长度上表现更好（图 3）。此外，我们的人类研究表明我们的指标与人类判断有很高的一致性。

图 3：ROUGE 无法区分模型和长度，而基于模型的评估更善于分离不同容量规模的模型。

***稳健的提示***：现有长上下文基准常要求模型遵循指令，但许多模型开发围绕 base 模型展开，而 base 模型只能依赖合成任务或困惑度来评估。因此，我们通过 in-context learning 示例为我们的一部分任务支持 base 模型。这显著提升了 base 模型的性能，也更贴近真实应用。

## 在真实任务上，LCLM 仍有很长的路要走

我们的实验和分析包含一组全面的 59 个 LCLM。据我们所知，这是对长上下文模型在多样应用上最详尽、最受控的对比。这些模型涵盖了领先的闭源和开源模型，我们也考虑了不同架构的模型（如全注意力 transformer、混合架构）和位置外推技术。本节我们会着重指出实验中一些关键发现。

### 评估长上下文能力需要多样化评估

长上下文基准常常是针对特定应用构建的，比如摘要或问答，这限制了对 LCLM 在更 broadly 背景下的理解。我们考察模型在众多真实任务上的表现，发现不同类别之间并不总是相关（图 4）。

图 4：不同类别彼此相关性不好。

虽然有些任务由于都基于检索而中等相关（如 RAG 和 MS-MARCO），其他则几乎没有相关性（如 Summ 和 Cite）。值得注意的是，ICL 与其他任务的相关性最低，这表明它是一个独特的任务，需要模型不同的能力。因此，模型开发者应沿这些不同的维度进行评估，从而对模型能力形成更全面的图景。

### 随长度和任务复杂度增加，模型性能会退化

我们给出前沿闭源模型以及若干开源模型在 HELMET 上的结果。更多结果可在论文和网站找到。

图 5：在选定指令微调模型上，跨任务和输入长度的 HELMET 结果。

首先，我们观察到**开源模型在复杂任务上落后于闭源模型**。虽然在 Recall 这类较简单的任务上差距看起来不大，但在 Cite 这类更复杂的任务上差距会拉大。

此外，**性能随长度增加而退化是类别相关的**。即便是最先进的模型，如 GPT-4o 和 Gemini，在像 re-ranking 这样的任务上也会经历性能的显著下降。这种性能变化单看合成任务表现是观察不到的。

最后，**没有一个在所有类别上都明确胜出的模型**，这就呼吁沿不同维度做评估。更多分析，比如不同位置外推方法的性能和"迷失在中间（lost-in-the-middle）"现象，可在论文中找到。

## 用 HELMET 推动未来发展

### 如何运行 HELMET

用 HELMET 很简单！只需克隆我们的 [GitHub 仓库](https://github.com/princeton-nlp/HELMET)，配置好环境之后就一切就绪！

我们提供许多不同的模型加载方式，可以在配置文件里配置：

- 用 HuggingFace 的 `transformers` 库
- 用 HuggingFace 的 TGI 在你机器上启动一个模型端点
- 用 HuggingFace 的 Inference Endpoints 启动一个远程模型端点
- 用 vllm 在你机器上启动一个模型端点。注意：你可以在 Intel Gaudi 加速器上启动 vllm 端点。
- 用模型提供商的 API

#### 选项 1. 使用 HuggingFace 的 `transformers` 库

直接用我们仓库里的 config yaml，并用下面的命令运行这些评估

```
python eval.py --config configs/rag.yaml --model_name_or_path <model_name>
```

底层使用的是 HuggingFace 的 `transformers` 库，本地和远程模型都自动支持。

#### 选项 2. 使用 HuggingFace 的 TGI

首先，按照 [TGI github](https://github.com/huggingface/text-generation-inference) 上的说明启动一个模型端点。然后在你的配置文件里指定端点 URL。例如，你可以用下面这样的 config.yaml

```
input_max_length: 131072
datasets: kilt_nq
generation_max_length: 20
test_files: data/kilt/nq-dev-multikilt_1000_k1000_dep6.jsonl
demo_files: data/kilt/nq-train-multikilt_1000_k3_dep6.jsonl
use_chat_template: true
max_test_samples: 100
shots: 2
stop_new_line: true
model_name_or_path: tgi:meta-llama/Llama-3.1-8B-Instruct # need to add "tgi:" prefix
use_tgi_serving: true # add this line in your config
```

然后用下面的命令运行基准

```
export LLM_ENPOINT=<your-tgi-endpoint> # example: "https://10.10.10.1:8080/v1"
python eval.py --config configs/config.yaml --endpoint_url $LLM_ENDPOINT
```

#### 选项 3. 使用 HuggingFace 的 Inference Endpoints

首先按照[这里的说明](https://huggingface.co/inference-endpoints/dedicated)搭建一个端点。获取端点 URL 和你的 API key。然后用上面选项 2 里展示的同样 config yaml，并运行下面的命令。

```
export LLM_ENPOINT=<your-hf-inference-endpoint> # example: "https://XXXX.us-east-1.aws.endpoints.huggingface.cloud/v1"
export API_KEY=<your-hf-api-key>
python eval.py --config configs/config.yaml --endpoint_url $LLM_ENDPOINT --api_key $API_KEY
```

#### 选项 4. 使用 VLLM

你可以在你的系统上用 vllm 启动一个模型端点，包括 Intel Gaudi2 和 Gaudi3 加速器。关于如何在 Intel Gaudi 加速器上用 vllm 运行 HELMET，见[这里的说明](https://github.com/princeton-nlp/HELMET/tree/main#run-on-intel-gaudi)。

你可以使用和选项 2 里一样的示例 config.yaml，只是有两行改动如下：

```
model_name_or_path: meta-llama/Llama-3.1-8B-Instruct # no prefix needed
use_vllm_serving: true # use vllm instead of tgi
```

然后用下面的命令运行基准

```
export LLM_ENPOINT=<your-vllm-endpoint>
python eval.py --config configs/config.yaml --endpoint_url $LLM_ENDPOINT
```

#### 选项 5. 使用模型提供商的 API

我们支持 OpenAI、Anthropic、Google 和 TogetherAI 的 API。请参考我们 [repo](https://github.com/princeton-nlp/HELMET/tree/main) 里的说明。

### 更快开发

我们建议在模型开发期间用 Recall 和 RAG 任务做快速迭代。这些任务在快速评估与对其他真实任务的相关性之间取得了良好平衡。你可以很容易地用以下命令跑这些评估

```
python eval.py --config configs/rag.yaml --model_name_or_path <model_name>
```

### 与现有模型快速对比

要跑所有基线来评估 LCLM 往往很昂贵，在长上下文下尤其如此，因为其计算和内存成本很高。例如，在一个 70B 模型上、在所有长度上跑 HELMET 需要一个配备 8 张 80GB GPU 的节点、数百个 GPU 小时，这可能成本不菲。通过在 HELMET 上评估，研究者只需参照我们的结果就能把自己的模型与现有模型直接对比，而我们的结果涵盖了 59 个不同规模和架构的模型。你可以在我们的[网站](https://princeton-nlp.github.io/HELMET)找到排行榜。

### 展望未来

HELMET 是朝更全面评估长上下文语言模型迈出的一步，但 LCLM 仍有许多令人兴奋的应用。例如，我们最近发布了 [LongProc](https://arxiv.org/abs/2501.05414)，一个用于评估 LCLM 在*长文本生成*和*遵循流程*上的基准——这两点对生成数万 token 思考步骤的推理模型至关重要。尽管摘要任务已有较长的输出（最多 1K token），LongProc 聚焦于更长的输出，多达 8K token。和 HELMET 一样，LongProc 也设计有可靠的评估设置和多样的任务。我们正在把 LongProc 集成进 HELMET 的评估套件，希望这能为 LCLM 在长文本任务上提供更全面的评估。
