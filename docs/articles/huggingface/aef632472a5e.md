**实时预测、异常检测与优化，由下载量超过 5,000 万次的 IBM 时间序列模型驱动。如今已原生支持 Confluent，云端与本地皆可部署，运行在 CPU 上。**

每家企业都在持续产生一份变化记录：一次机器读数、一笔支付、一次销售、一张订单，或者一次库存变动。这些观测构成时间序列，而其中携带的信号可以帮助团队预判接下来会发生什么。

难点在于趁这些信号仍然有价值时把它们变成决策。一次生产批次跑完、一次缺货、一次支付授权之后才送达的预测，也许依然准确，却已来不及影响结果。

IBM 与 Confluent 正让时间序列基础模型更贴近流动中的数据。借助 Apache Flink，团队可以用 SQL 对流式数据施加预测、异常检测与语义智能，让模型输出直达负责下一步动作的应用和人员。

基础模型改变了组织处理文本、图像与文档的方式。时间序列基础模型把类似的思路延伸到数值数据：先从多样化的历史数据中学习通用模式，再把这份知识用于新的序列与任务。这类模型可以提供一个起点，团队无需为每一条序列单独训练模型。视任务与部署方式而定，团队还可以对模型做 fine-tuning，或把模型的输出与其他数据和业务逻辑结合。

如今，时间序列基础模型以内置函数的形式原生运行在 Confluent 之内，云端与本地皆可。在 Confluent Cloud 中它们完全托管，无需部署任何东西（[文档](https://docs.confluent.io/cloud/current/ai/builtin-functions/forecast.html)）。在本地，模型可以借助 Confluent Platform for Apache Flink 跑在你自己的基础设施里。（[文档](https://docs.confluent.io/cp-flink/current/jobs/sql-statements/ai/set-up-ai-functions.html)）。这些模型运行在 CPU 上，不需要 GPU。

这些模型可以支撑一系列关键业务场景：从帮助生产线保持在规格之内、发现门店异常活动，到改进单品层面的规划。它们还能提供信号来评估卡片支付，并预测交易量以协助下达大额订单。这些构件可以通用于制造业、零售、银行与航空业，把洞察带到离决策更近的地方。

## Streamhouse：agentic 时代的实时数据与智能

企业的运营从不间断。订单在更新，付款在到账，货运在延误，库存一天之内反复变动。然而这些事件背后的信息往往散落在不同系统里，各系统更新节奏不一，或者依赖周期性的批处理。当应用与 AI agent 依据过时或不一致的信息行动时，就可能做出不再反映当下实况的决策。

Streamhouse 通过持续捕获、处理、治理并提供当前的业务上下文来解决这个问题。Confluent 的 Data Streaming Platform 把 connect、stream、process、govern、query 五项能力汇于一处，让这份上下文可供应用、分析与 agent 使用。Apache Flink 在数据流动过程中完成转换与增强，Lightning Tables 则提供对当前状态的低延迟访问。

[![Confluent 上的 Streamhouse](https://cdn-uploads.huggingface.co/production/uploads/64e8143f6de557454220921e/M2Rn5ft2uBCZcTkyUxNfx.png)](https://cdn-uploads.huggingface.co/production/uploads/64e8143f6de557454220921e/M2Rn5ft2uBCZcTkyUxNfx.png)

*图 2. Confluent 上的 Streamhouse：从既有数据源到当前的业务上下文，供 agent、应用、分析与 lakehouse 在任何地方使用。*

时间序列模型为这套架构补上预测能力。Flink 可以准备数据、调用预测与异常检测，并让结果与产生它的事件一并可用。其他模型——包括大型语言模型、统计模型和专用机器学习系统——也能在合适的位置参与进来。

[![Streamhouse 的各层：agentic 体验、端到端解决方案、流原生智能，以及 Streamhouse 本身](https://cdn-uploads.huggingface.co/production/uploads/64e8143f6de557454220921e/ELIbCPJpgpZn1X58rxs7p.png)](https://cdn-uploads.huggingface.co/production/uploads/64e8143f6de557454220921e/ELIbCPJpgpZn1X58rxs7p.png)

这种做法可以在四个方面帮到团队：

-**扩大模型开发的规模**。一个预训练模型可以为众多时间序列提供共同的起点，减少为每一条序列单独开发并维护模型的需要。

-**随数据变化刷新预测**。预测可以在流式工作流中纳入最近的观测，具体取决于模型的要求与 pipeline 的配置。

-**让信号离决策更近**。预测与异常可以更早地路由到运营类应用，团队在那里把它们与业务上下文、规则和人工判断结合。

-**在 CPU 上运行紧凑模型。** 这些模型足够小，可以与流式 pipeline 一起跑在标准 CPU 上，云端或本地皆可，从而减少对专用 GPU 基础设施的依赖，并简化部署。

## 真实企业中的关键业务场景

以下场景展示了组织可以如何把时间序列模型、流式数据与应用逻辑组合起来。

### 用例 1 | 生产优化：每一桶都合乎规格

冰淇淋生产线的质量取决于 overrun——也就是搅打进混合料里的空气量。目前，工艺工程师和操作员依赖 QA 实验室在桶装完成之后所做的测量。如果换了一批新奶油，或者遇上温暖潮湿的天气而让工艺发生变化，等到团队看到结果时，可能已有数小时的产品需要返工。

为了提前应对这个问题，一个预训练的 TTM 模型每 10 分钟读取一次 SCADA 遥测数据与 QA 测量值。它预测未来四小时内预计合乎规格的桶装比例，并给出一个可能区间。

当预测值低于工厂目标时，优化流程会评估冷冻机抽气温度与风量的各种组合。由于模型把这些控制变量作为输入，它可以在产线做任何改动之前就为每个选项打分。操作员批准推荐的设定点，而常规调整可以在预设的护栏范围内自动执行。

结果是流程变得更主动：返工更少、每吨能耗更低、质量更稳定。同样的方法也适用于烤箱、干燥机、窑炉和研磨机。

### 用例 2 | 异常检测：从一条标记到正确的处置

某门店运营团队要监控数百家门店、数千种商品的销售。固定阈值常常把可预期的周末高峰标出来，却漏掉更安静的变化，比如某件商品卖得比预期少。警报越积越多，团队反而越来越难判断该把注意力放在哪里。

AI_DETECT_ANOMALIES 依据每条销售序列的近期历史给出一个预期区间。每个新读数都会按团队选定的置信水平与该区间比对，无需为每个商品和门店单独训练模型。

当销售落到预期区间之外时，这个信号可以与库存和门店数据结合，帮助找出可能的原因并建议下一步——例如检查货架或补货。同样的方法也适用于机器传感器、API 遥测、电表读数和支付量。

### 用例 3 | 供应链规划：每个 SKU、每家门店、每个小时

品类规划师与补货团队需要让每家门店都不断货，同时又不背上多余库存。但预测可能一周才刷新一次，而且往往只覆盖畅销品，长尾商品则靠更简单的规则管理。一旦销售模式在两个规划周期之间发生变化，就可能一家门店断货、另一家库存过剩。

借助 AI_FORECAST，一个预训练模型可以跨商品、跨门店预测需求。在这个例子里，它产出带 P10–P90 区间的 28 天预测，并随着新销售数据的到来而刷新。规划应用把预测与库存、提前期以及规划师选定的服务水平结合起来，计算出再订货点。

当预计库存将跌破该点时，agent 可以起草一份采购订单供审阅。同样的方法也能支撑备件、人员排班、ATM 现金和能源需求的规划。

### 用例 4 | 欺诈与安全：每张卡都有自己的常态

欺诈团队早已依靠复杂的规则与模型来评估交易。一个持续的难题是：套用于众多持卡人的统一阈值，未必能反映每个人平常的消费方式。

时间序列信号可以补上这层个体上下文。在这个例子里，每笔支付都会与基于该卡近期历史得出的预期消费区间比对。落在区间之外的交易，会连同其他信号与业务规则一起，作为额外输入送给银行现有的反欺诈系统。

随后银行可以决定是批准这笔支付、要求追加认证，还是进一步调查。决策及其背后的信号都可以留存备查。

### 用例 5 | 交易：让下单节奏跟随行情

执行台需要把一笔大单拆成多笔较小的交易，同时控制它对市场的影响。历史成交量曲线能提供起点，但当下的交易活跃度可能与均值相去甚远。

在每一根一分钟 bar 上，PatchTST-FM 预测未来 30 分钟的成交量，并给出 P10–P90 区间。执行算法用这份预测，在交易台设定的参与率上限内安排下单节奏。

如果新闻事件改变了市场活跃度，算法可以暂停并重新规划。如果交易比预期清淡，它可以缩小每一笔切分的规模，并提示该订单可能需要更长时间才能完成。每一次预测以及由此产生的执行决策，都可以留在审计轨迹里。

### 用例 6 | 语义搜索：找出每一个长得像它的信号

一位可靠性工程师在调查某个异常传感器模式时，可能想知道工厂其他地方是否出现过类似的行为。

TSPulse 可以生成时间序列窗口的表示，用来支撑相似度检索。在一个另行搭建的应用中，这些表示可以被索引，用于跨设备召回历史模式。工程师可以按形状检索，比如尖峰后回落、缓慢上升或阶跃变化，然后再查看相关的维护记录与运行工况。

这个应用需要一条 embedding pipeline、一个索引，以及对相关上下文的访问权限。相似度能帮调查收窄范围，但它本身并不确立根因。

## 行业特定应用

同样的模型与构件可以支撑不同行业中的不同工作流：

- **工业 AI：从传感器到设定点。** 工厂经理希望每一批都合乎规格，也没有哪条产线被意外停机。SCADA、QA 实验室和电表的数据流在到达时即被预测。质量开始漂移时，生产优化会调整设定点；异常检测会标出任何规则都没写过的读数；语义搜索会找出故障前出现过同样模式的每一台泵。设定点、工单和警报在周期之内就抵达车间，而不是等下一份交接班报告。

[![13-twin-plant](https://cdn-uploads.huggingface.co/production/uploads/64e8143f6de557454220921e/q8GaODH5na0inQAQ5NsSy.webp)](https://cdn-uploads.huggingface.co/production/uploads/64e8143f6de557454220921e/q8GaODH5na0inQAQ5NsSy.webp)

*图 11. 工厂数字孪生，从传感器到设定点。一批新奶油让 overrun 偏离目标。预测读取产线状态，agent 提出新的抽气温度与风量，操作员批准，桶装产品重回规格。模拟数据。*

- **零售：一家门店与它的供应链。** 门店经理希望周六货架是满的，周一又不要压货。销售、天气与促销数据流会针对每家门店的每个商品做出预测。供应链规划确定订单，异常检测捕捉空货架或漏送的到货，欺诈与安全模块拦下可疑的卡。订单、门店任务和拦截指令在货架空掉之前就发出去了。

[![14-twin-store](https://cdn-uploads.huggingface.co/production/uploads/64e8143f6de557454220921e/H2fM8uPxwgGowSbE81se3.webp)](https://cdn-uploads.huggingface.co/production/uploads/64e8143f6de557454220921e/H2fM8uPxwgGowSbE81se3.webp)

*图 12. 门店数字孪生，一家门店与它的供应链。燕麦奶即将促销。预测把促销计入并设定再订货点，agent 提出采购订单，规划师批准，促销当天货架是满的。模拟数据。*

- **银行：支付与交易台。** 反欺诈负责人想在不误伤好客户的前提下阻止卡测试，交易员想在不推动价格的情况下完成大额订单。每一张卡、每一个标的都按各自的预期模式逐事件打分。欺诈与安全模块在授权前拦下异常刷卡，异常检测发现异常的资金流，交易模块用预测成交量安排每笔订单的节奏。
- **航空：枢纽运营、机队与航线网络。** 运行控制部门希望在还来得及行动的时候就看到扰动来临。发动机、登机口与网络数据流被实时预测和核查。异常检测捕捉漂移的发动机读数，生产优化重新平衡登机口与机组，供应链规划把备件放到飞机将要去的地方。

在每个行业里，Streamhouse 做的都是同一件事：Flink 运行 Granite 模型来做预测、检测与优化，Streaming Agents 基于实时上下文采取行动，而人来批准例外。
