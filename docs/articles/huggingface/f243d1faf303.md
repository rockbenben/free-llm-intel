# Hugging Face 上最被低估的 5 个工具

Derek Thomas（[derek-thomas](https://huggingface.co/derek-thomas)）

tl;dr Hugging Face Hub 上有很多常被忽视的工具和集成，它们能让构建各类 AI 方案变得更轻松

Hugging Face Hub 拥有超过 85 万个公开模型，每月新增约 5 万个，而且这个数字还在持续攀升。我们还提供 Enterprise Hub 订阅，解锁[合规](https://huggingface.co/docs/hub/en/storage-regions#regulatory-and-legal-compliance)、[安全](https://huggingface.co/docs/hub/en/security#security)和[治理](https://huggingface.co/docs/hub/en/enterprise-hub-resource-groups)功能，为生产级推理提供额外的推理端点算力，并为 Spaces 演示提供更多硬件选项。

Hugging Face Hub 之所以能广泛使用，是因为你有多样化的硬件，而且几乎可以在 [Docker Spaces](https://huggingface.co/docs/hub/en/spaces-sdks-docker) 里运行任何东西。我注意到我们有一批"无名英雄"级别的功能（见下）。在 Hugging Face hub 上构建一个语义搜索应用的过程中，我正是用这些功能搭起了方案的各个部分。虽然我认为最终的应用（详见 [reddit-tools-HF](https://huggingface.co/reddit-tools-HF) 这个组织）已经很有说服力，但更想借这个例子展示如何把它们用到你自己的项目里。

- [ZeroGPU](https://huggingface.co/blog/unsung-heroes#zerogpu) - 怎么免费用上 GPU？
- [多进程 Docker](https://huggingface.co/blog/unsung-heroes#multi-process-docker) - 怎么在一个 space 里同时解决 2（n）个问题？
- [Gradio API](https://huggingface.co/blog/unsung-heroes#gradio-api) - 怎么让多个 space 协同工作？
- [Webhooks](https://huggingface.co/blog/unsung-heroes#webhooks) - 怎么根据 hub 上的变化触发 space 里的事件？
- [Nomic Atlas](https://huggingface.co/blog/unsung-heroes#nomic-atlas) - 功能丰富的语义搜索（可视化 + 文本）

## 用例

> 免费搭建一个自动更新、带可视化的、面向动态数据源的语义搜索

这个场景在很多地方都有用：

- 电商平台想基于商品描述或用户反馈来管理海量商品
- 律所和合规部门需要翻阅大量法律文档或法规
- 研究人员要跟进最新进展，找到自己领域相关的论文或文章

我的演示是用一个 subreddit 作为数据源，剩下的全部由 Hub 来支撑。实现方式有很多种。我可以把一切塞进 1 个 space，但那会很乱；反过来，组件太多也有自己的麻烦。最终，**我选了一个能突出 Hub 上这些"无名英雄"、并示范如何高效使用它们的设计**。架构见*图 1*，完全托管在 Hugging Face 上，以 spaces、datasets 和 webhooks 的形式存在。我用到的每个功能都是免费的，保证最大程度的可及性。等你的服务需要扩容时，可以考虑升级到 [Enterprise Hub](https://huggingface.co/enterprise)。

## ZeroGPU

现代模型的一个普遍挑战是需要 GPU 或其他重型硬件才能跑起来。这些硬件不仅笨重，往往还要签一年期合约，价格昂贵。Spaces 可以让你低成本用上想要的硬件，但它不会自动扩缩容（当然你可以自己写脚本实现！）。[ZeroGPU](https://huggingface.co/zero-gpu-explorers) 是 Spaces 的一种新型硬件。免费用户有一定配额，[PRO 用户](https://huggingface.co/pricing#pro)配额更高。

它有两个目标：

- 为 Spaces 提供**免费**的 GPU 访问
- 让 Spaces 能跑在多个 GPU 上

| [![Zero Spaces](https://cdn-uploads.huggingface.co/production/uploads/5f17f0a0925b9863e28ad517/naVZI-v41zNxmGlhEhGDJ.gif)](https://cdn-uploads.huggingface.co/production/uploads/5f17f0a0925b9863e28ad517/naVZI-v41zNxmGlhEhGDJ.gif) |
| --- |
| 图 2：ZeroGPU 幕后原理 |

它的实现方式是让 Spaces 按需高效地占用和释放 GPU（区别于始终绑定一块 GPU 的传统 GPU Space）。ZeroGPU 底层使用 Nvidia A100 GPU（每个工作负载可用 40GB vRAM）。

### 实际应用

我用 ZeroGPU 在**嵌入模型 Space** 里托管了非常出色的 nomic 嵌入模型。这特别方便，因为我只需要偶尔做增量推理，并不需要专用 GPU。

用起来**极其**简单。唯一的改动是把所有 GPU 代码放进一个函数，然后给它加上 `@spaces.GPU` 装饰器。

```
import spaces

model = SentenceTransformer("nomic-ai/nomic-embed-text-v1.5", trust_remote_code=True, device='cuda')

@spaces.GPU
def embed(document: str):
    return model.encode(document)
```

| --- |
| 图 3：数据处理 Space |

企业客户最常见的诉求之一就是"我想要功能 X，或者集成工具 Y"。Hugging Face Hub 最好的地方之一，就是我们有一套[强得离谱的 API](https://huggingface.co/docs/huggingface_hub/main/en/index)，基本能和任何东西集成。第二种解决思路通常在 spaces 里。这里我用了一个空白的 [docker space](https://huggingface.co/docs/hub/spaces-sdks-docker)，它可以按你选的硬件跑任意 docker 容器（我这里用免费 CPU）。

我主要的痛点是：想在同一个 space 里跑两件完全不同的事。大多数 space 只有单一身份，比如[展示一个 diffusers 模型](https://huggingface.co/spaces/stabilityai/stable-diffusion)，或者[生成音乐](https://huggingface.co/spaces/facebook/MusicGen)。看看 **Dataset Creator Space**，我需要：

- 跑一段代码，从 Reddit 拉数据并存入**原始数据集** 这是一个几乎不可见的过程 由 `main.py` 负责
- 把上面代码的日志可视化出来，好让我清楚发生了什么（见*图 3*） 由 `app.py` 负责

注意这两件事应该在独立进程中运行。我遇到过很多场景，日志可视化其实非常有用且重要——它是很好的调试工具，而且在没有天然 UI 的场景下，观感也好得多。

### 实际应用

我借助 [supervisord](http://supervisord.org) 库实现了多进程 Docker 方案，它是一个流程控制系统。用它可以干净地控制多个独立进程。Supervisord 让我能在单个容器里干多件事，这在 Docker Space 里非常实用。注意 Spaces 只允许暴露一个端口，这会影响你的方案选型。

安装 Supervisor 很简单，它就是个 python 包。

```
pip install supervisor
```

你需要写一个 `supervisord.conf` 文件来指定配置。我的完整示例在[这里](https://huggingface.co/spaces/reddit-tools-HF/dataset-creator-reddit-bestofredditorupdates/blob/main/supervisord.conf)，基本不言自明。注意我不想要 `program:app` 的日志，因为 `app.py` 只是用来展示日志的、不产生日志，所以我把它的日志路由到 `/dev/null`。

```
[supervisord]
nodaemon=true

[program:main]
command=python main.py
stdout_logfile=/dev/stdout
stdout_logfile_maxbytes=0
stderr_logfile=/dev/stderr
stderr_logfile_maxbytes=0
autostart=true

[program:app]
command=python app.py
stdout_logfile=/dev/null
stdout_logfile_maxbytes=0
stderr_logfile=/dev/stderr
stderr_logfile_maxbytes=0
autostart=true
autorestart=true
```

最后，启动我们的 `supervisord.conf`，真正跑起这 2 个进程。在我的 [Dockerfile](https://huggingface.co/spaces/reddit-tools-HF/dataset-creator-reddit-bestofredditorupdates/blob/main/Dockerfile) 里只需运行：

```
CMD ["supervisord", "-c", "supervisord.conf"]
```

## Gradio API

在**数据处理 Space** 里我需要为帖子生成嵌入，而一旦把嵌入模型抽象到另一个 space，就带来一个问题：怎么调用它？

当你构建一个 [Gradio 应用](https://www.gradio.app)时，默认情况下任何交互都可以当作 API 调用来处理。这意味着 Hub 上那些[很酷的 spaces](https://huggingface.co/spaces) 都自带配套 API（如果作者开启，Spaces 里用 API 调用 Streamlit 或 Docker space 也没问题）！更棒的是，我们还为这个 API 提供了一个[易用客户端](https://www.gradio.app/docs/python-client/client)。

### 实际应用

我在**数据处理 Space** 里用这个客户端，从部署在**嵌入模型 Space** 的 nomic 模型获取嵌入。具体用在 [utilities.py](https://huggingface.co/spaces/reddit-tools-HF/processing-bestofredditorupdates/blob/main/src/utilities.py) 文件里，我把相关部分摘出来：

```
from gradio_client import Client

# Define the Client
client = Client("reddit-tools-HF/nomic-embeddings")

# Create an easy to use function (originally applied to a dataframe)
def update_embeddings(content, client):
    # Note that the embedding model requires you to add the relevant prefix
    embedding = client.predict('search_document: ' + content, api_name="/embed")
    return np.array(embedding)

# Consume 
final_embedding = update_embeddings(content=row['content'], client=client)
```

现在甚至还有一个非常酷的

API 录制器

，让你在 GUI 里操作，同时把每一步录成 API 交互。

[Webhooks](https://huggingface.co/docs/hub/en/webhooks) 是 MLOps 相关功能的基础设施。它们让你能监听特定仓库、或某个用户/组织名下全部仓库的变化（不只是你自己的仓库，任何仓库都行）。

你可以用它们自动转换模型、构建社区机器人、给你的模型、数据集和 Spaces 搭 CI/CD，以及更多玩法！

### 实际应用

在我的用例里，我希望每次更新**原始数据集**时都重建**处理后数据集**。完整代码见[这里](https://huggingface.co/spaces/reddit-tools-HF/processing-bestofredditorupdates/blob/main/app.py#L73-L139)。为此我要加一个 webhook，在**原始数据集**更新时触发，并把它的 payload 发给**数据处理 Space**。更新有多种类型，有的发生在其他分支上，有的在 discussions 标签页。我的触发条件是：`README.md` 文件和另一个文件同时在仓库主分支上被更新，因为数据集有新 commit 推送时正是这样变的（[看这个例子](https://huggingface.co/api/datasets/reddit-tools-HF/dataset-creator-reddit-bestofredditorupdates/compare/984759c734ab6d01c43739ac7eb46870eacf304b..adcc0f523c8fabe0f04448139fc7f72befa5428e?raw=true)）。

```
# Commit cleaned up for readability
T 1807	M	README.md
T 52836295	M	data/train-00000-of-00001.parquet
```

把这套方案移植到你的用例时，需要仔细定义自己的触发条件

首先，你要在设置里创建 webhook。最好按[这份指南](https://huggingface.co/docs/hub/en/webhooks#create-your-webhook)来操作，并确保端点名保持一致（我这里用 `/dataset_repo`）。

另外注意，webhook url 是在 *Direct URL* 后面追加 `/webhooks`。*Direct URL* 可以通过点击 space 上方的三个点并选择 `Embed this Space` 找到。我还在**数据处理 Space** 里设置了 [webhook secret](https://huggingface.co/docs/hub/en/webhooks#webhook-secret)，保证安全。

我的 webhook 创建输入长这样。别把我的 secret 告诉别人 😉。

Target Repositories: `datasets/reddit-tools-HF/dataset-creator-reddit-bestofredditorupdates`

Webhook URL: `https://reddit-tools-hf-processing-bestofredditorupdates.hf.space/webhooks/dataset_repo`

Secret (optional): `Float-like-a-butterfly`

接下来你要在 space 里消费这个 webhook。我会分两部分讲：

- 如何搭建 webhook 服务器
- 如何只选择性触发我们关心的更新 必须是 `repo` 级别的变更 必须发生在 main 分支：`refs/heads/main` 必须是除 `README.md` 之外还有别的文件在变化

#### 如何搭建 webhook 服务器

首先要消费 payload。[huggingface_hub](https://huggingface.co/docs/huggingface_hub/index) 库里内置了一个方便的[消费 webhook payload](https://huggingface.co/docs/huggingface_hub/main/en/guides/webhooks#custom-server) 的方式。可以看到我用 `@app.add_webhook` 定义了一个与创建 webhook 时一致的端点，然后写上我的函数。

注意你必须在 30 秒内响应 payload 请求，否则会收到 `500` 错误。这就是为什么我用一个 async 函数先响应、再把真正的处理任务扔出去，而不是在 `handle_repository_changes` 函数里直接做处理。更多信息参见 [background task 文档](https://fastapi.tiangolo.com/tutorial/background-tasks/)。

```
from huggingface_hub import WebhookPayload, WebhooksServer

app = WebhooksServer(ui=ui.queue(), webhook_secret=WEBHOOK_SECRET)

# Use /dataset_repo upon webhook creation
@app.add_webhook("/dataset_repo")
async def handle_repository_changes(payload: WebhookPayload, task_queue: BackgroundTasks):

    ###################################
    # Add selective trigger code here #
    ###################################

    logger.info(f"Webhook received from {payload.repo.name} indicating a repo {payload.event.action}")
    task_queue.add_task(_process_webhook, payload=payload)
    return Response("Task scheduled.", status_code=status.HTTP_202_ACCEPTED)


def _process_webhook(payload: WebhookPayload):
    #do processing here
    pass
```

#### 选择性触发

由于我关心的是仓库级别的任何变化，可以用 `payload.event.scope.startswith("repo")` 判断这个 incoming payload 是否与我相关。

```
# FILTER 1: Don't trigger on non-repo changes
if not payload.event.scope.startswith("repo"):
    return Response("No task scheduled", status_code=status.HTTP_200_OK)
```

分支信息可以通过 `payload.updatedRefs[0]` 拿到

```
# FILTER 2: Dont trigger if change is not on the main branch
try:
    if payload.updatedRefs[0].ref != 'refs/heads/main':
        response_content = "No task scheduled: Change not on main branch"
        logger.info(response_content)
        return Response(response_content, status_code=status.HTTP_200_OK)
except:
    response_content = "No task scheduled"
    logger.info(response_content)
    return Response(response_content, status_code=status.HTTP_200_OK)
```

检查哪些文件变了就更复杂一点。我们能在 `commit_files_url` 里看到一些 git 信息，但需要解析。它长得有点像 `.tsv`。
步骤：

- 获取 commit 信息
- 解析成 `changed_files`
- 按我的条件决定要不要行动

```
from huggingface_hub.utils import build_hf_headers, get_session

# FILTER 3: Dont trigger if there are only README updates
try:
    commit_files_url = f"""{payload.repo.url.api}/compare/{payload.updatedRefs[0].oldSha}..{payload.updatedRefs[0].newSha}?raw=true"""
    response_text = get_session.get(commit_files_url, headers=build_hf_headers()).text
    logger.info(f"Git Compare URl: {commit_files_url}")

    # Splitting the output into lines
    file_lines = response_text.split('\n')

    # Filtering the lines to find file changes
    changed_files = [line.split('\t')[-1] for line in file_lines if line.strip()]
    logger.info(f"Changed files: {changed_files}")

    # Checking if only README.md has been changed
    if all('README.md' in file for file in changed_files):
        response_content = "No task scheduled: its a README only update."
        logger.info(response_content)
        return Response(response_content, status_code=status.HTTP_200_OK)
except Exception as e:
    logger.error(f"{str(e)}")
    response_content = "Unexpected issue :'("
    logger.info(response_content)
    return Response(response_content, status_code=status.HTTP_501_NOT_IMPLEMENTED)
```

## Nomic Atlas

我们在客户/合作伙伴那里看到的常见痛点之一，是数据理解和协作都很困难。理解数据往往是解决任何 AI 用例的第一步。我最喜欢的做法是可视化，但在语义数据方面，我常觉得没有称手的工具。所以发现 [Nomic Atlas](https://docs.nomic.ai/index.html) 时我非常惊喜。它提供了数据探索所需的一系列关键能力：

- 用 [nomic-ai/nomic-embed-text-v1.5](https://huggingface.co/nomic-ai/nomic-embed-text-v1.5) 做语义搜索（目前处于 beta）
- 功能丰富的筛选
- 关键词搜索
- 套索搜索（我能手画边界！！）

### 实际应用

我在**数据处理 Space** 里构建了 nomic Atlas。在这个流程里，**处理后数据集**已经建好，剩下的只是把它可视化。如何用 nomic 构建可以查看 [build_nomic.py](https://huggingface.co/spaces/reddit-tools-HF/processing-bestofredditorupdates/blob/main/src/build_nomic.py)。和之前一样，我把与本篇相关的部分摘出来：

```
from nomic import atlas
from nomic.dataset import AtlasClass
from nomic.data_inference import NomicTopicOptions

# Login to nomic with a Space Secret
NOMIC_KEY = os.getenv('NOMIC_KEY')
nomic.login(NOMIC_KEY)

# Set because I do want the super cool topic modeling
topic_options = NomicTopicOptions(build_topic_model=True, community_description_target_field='subreddit')

identifier = 'BORU Subreddit Neural Search'
project = atlas.map_data(embeddings=np.stack(df['embedding'].values),
                         data=df,
                         id_field='id',
                         identifier=identifier,
                         topic_model=topic_options)
print(f"Succeeded in creating new version of nomic Atlas: {project.slug}")
```

按照 nomic 的工作方式，每次运行 `atlas.map_data` 都会在你的账户下创建一个新的 Atlas 数据集。我想持续更新同一个数据集。目前最好的做法是删掉旧数据集。

```
ac = AtlasClass()

ac._delete_project_by_id(atlas_id)
logger.info(f"Succeeded in deleting old version of nomic Atlas.")
```

中间布满圆点的主区域展示的是每篇嵌入后的文档。两个文档离得越近，相关性越高。具体表现取决于多种因素（嵌入器对你的数据适配得好不好、从高维压缩到 2D 表示的损失等），所以要谨慎解读。左侧可以搜索和查看文档。

在*图 5* 的**红框**里可以看到 5 个输入框，用不同方式搜索。每个筛选都是逐步叠加的，所以这是"[一口一口啃下大象](https://philipchircop.wordpress.com/2012/07/03/chip-it-away/)"的绝佳方式。比如先按日期或其他字段筛，再做文本搜索。最酷的是*最左边*那个——神经搜索，有三种用法：

- Query Search - 给一段简短描述，去匹配嵌入过的（长）文档
- Document Search - 给一整篇长文档，去匹配嵌入文档
- Embedding Search - 直接用嵌入向量搜索

我在探索自己上传的文档时一般用 Query search。

在*图 5* 的**蓝框**里，可以看到我上传数据集的每一行都被漂亮地可视化了。我很喜欢的一个功能是它会渲染 HTML，所以你可以控制展示效果。Reddit 帖子是 markdown 格式，转成 HTML 来展示很容易。

## 伦理考量

这一切的数据源包含标记为 Not Suited For Work（NSFW，不适合工作场合）的内容，类似于我们的 Not For All Audiences（NFAA）标签。我们不在 Hub 上禁止这类内容，但确实要妥善处置。另外，近期研究表明，从互联网不加甄别获取的内容存在包含儿童性虐待材料（CSAM）的风险，尤其是未经筛选、性内容高发的数据。

在本次数据集构建的语境下评估这些风险，可以先看源数据的收集流程。原始故事（在聚合之前）会先经过版主审核，更新内容往往也发在有版主的 subreddit 里。偶尔，更新会被传到原帖主的个人主页。最终版本发布到 [r/bestofredditorupdates](https://www.reddit.com/r/BestofRedditorUpdates/)，那里审核非常严格——因为他们更容易被群体围攻（brigading），所以必须严。综上，至少有 2 道审核，通常是 3 道，其中一道以严格著称。

写作本文时，共有 69 个故事被标记为 NSFW。经我人工逐条检查，其中没有 CSAM 内容。我也对包含 NFAA 材料的数据集做了访问限制。为了让 nomic 可视化更易用，我在创建 atlas 时会过滤掉 dataframe 中包含 "NSFW" 的内容，生成一个过滤后的数据集。
