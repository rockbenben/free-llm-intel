# Text Generation Inference 基准测试

本文另有[简体中文](https://huggingface.co/blog/zh/tgi-benchmarking)版本。

在这篇博客中，我们将探索 [Text Generation Inference](https://github.com/huggingface/text-generation-inference)（TGI）的"小兄弟"——[TGI 基准测试工具](https://github.com/huggingface/text-generation-inference/blob/main/benchmark/README.md)。它将帮助我们理解如何在简单吞吐之外为 TGI 做性能画像，更好地理解各种权衡，从而根据你的需求调优部署。如果你曾觉得 LLM 部署太贵，或者想调优部署以提升性能，这篇博客就是为你写的！

我会演示如何在一个方便的 [Hugging Face Space](https://huggingface.co/spaces) 里完成这一切。你可以把得到的结果用到 [Inference Endpoint](https://huggingface.co/inference-endpoints/dedicated) 或相同硬件的其他副本上。

## 动机

为了更好地理解为什么需要做性能画像，先谈一些背景。

大语言模型（LLM）在根本上是低效的。基于[解码器的工作方式](https://huggingface.co/learn/nlp-course/chapter1/6?fw=pt)，生成每个解码 token 都需要一次新的前向传播。随着 LLM 规模增大、[企业采用率激增](https://a16z.com/generative-ai-enterprise-2024/)，AI 行业在创造新优化和性能提升技术方面做得非常出色。

LLM 服务化的方方面面已有数十项改进：我们见证了 [Flash Attention](https://huggingface.co/docs/text-generation-inference/en/conceptual/flash_attention)、[Paged Attention](https://huggingface.co/docs/text-generation-inference/en/conceptual/paged_attention)、[流式响应](https://huggingface.co/docs/text-generation-inference/en/conceptual/streaming)、[批处理改进](https://huggingface.co/docs/text-generation-inference/en/basic_tutorials/launcher#maxwaitingtokens)、[投机解码](https://huggingface.co/docs/text-generation-inference/en/conceptual/speculation)、各种[量化](https://huggingface.co/docs/text-generation-inference/en/conceptual/quantization)、[Web 服务器改进](https://github.com/huggingface/text-generation-inference?tab=readme-ov-file#architecture)、采纳[更快的语言](https://github.com/search?q=repo%3Ahuggingface%2Ftext-generation-inference++language%3ARust&type=code)（抱歉了 Python 🐍）等等。还有像 [structured generation](https://huggingface.co/docs/text-generation-inference/en/conceptual/guidance) 和 [watermarking](https://huggingface.co/blog/watermarking) 这样的用例级改进，如今也在 LLM 推理世界占据一席之地。问题在于，快速高效的实现需要越来越专精的技能才能落地 [[1]](https://huggingface.co/blog/tgi-benchmarking#1)。

[Text Generation Inference](https://github.com/huggingface/text-generation-inference) 是 Hugging Face 出品的高性能 LLM 推理服务器，旨在拥抱并发展改进 LLM 部署与消费的最新技术。得益于 Hugging Face 的开源合作生态，大多数（如果不是全部）主要开源 LLM 在发布当天即可在 TGI 上使用。

通常，用户根据用例需求会有非常不同的诉求。考虑 **RAG 用例**中的 prompt 与生成：

- 指令/格式通常很短，<200 token
- 用户查询通常很短，<200 token
- 多个文档中等大小，每文档 500-1000 token，文档数 N<10
- 输出答案中等大小，约 500-1000 token

在 RAG 中，拿到正确的文档才能得到高质量回复，而增大包含更多文档的 N 可以提高这个概率。这意味着 RAG 往往试图把 LLM 的上下文窗口塞满以提升任务表现。相比之下，想想基础聊天。典型的**聊天场景**的 token 数远少于 RAG：

- 多轮对话 2×T×50-200 token，T 为轮数；2 倍是因为用户与助手双方

既然场景如此不同，我们就必须根据哪个场景更相关来相应配置 LLM 服务器。Hugging Face 有一个[基准测试工具](https://github.com/huggingface/text-generation-inference/blob/main/benchmark/README.md)可以帮助我们探索哪些配置最合理，我将演示如何在一个 [Hugging Face Space](https://huggingface.co/docs/hub/en/spaces-overview) 上做这件事。

## 前置概念

在深入工具之前，先确保我们对几个关键概念有一致理解。

### 延迟与吞吐

|  |
| --- |
| *Figure 1: Latency vs Throughput Visualization* |

- Token 延迟——处理并发送 1 个 token 给用户所需的时间
- 请求延迟——完整响应一个请求所需的时间
- 首 token 时间（TTFT）——从最初请求到返回第一个 token 给用户的时间，是处理 prefill 输入加生成单个 token 的时间总和
- 吞吐——服务器在固定时间内能返回的 token 数（此例中为每秒 4 个）

延迟是个棘手的度量，因为它不能说明全貌。你可能生成了很长或很短的内容，这并不能告诉你服务器真实性能如何。

重要的是理解吞吐和延迟是两个正交的度量，根据我们对服务器的不同配置，可以为其中之一优化。我们的基准测试工具将通过数据可视化帮助我们理解这一权衡。

### 预填充与解码

| [![Prefilling vs Decoding](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/tgi-benchmarking/prefilling_vs_decoding.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/tgi-benchmarking/prefilling_vs_decoding.png) |
| --- |
| *Figure 2: Prefilling vs Decoding inspired by [[2]](https://huggingface.co/blog/tgi-benchmarking#2)* |

这是 LLM 生成文本的简化视图。模型（通常）每次前向传播生成一个 token。对橙色的 **pre-filling 阶段**，完整 prompt（What is.. of the US?）被送入模型，生成一个 token（Washington）。在蓝色的 **decoding 阶段**，生成的 token 被追加到之前的输入后面，然后这段（... the capital of the US? Washington）再次经过模型做一次前向传播。在模型生成结束序列 token（<EOS>）之前，这个过程会一直持续：把输入送入模型、生成一个 token、把 token 追加回输入。

思考题：为什么 pre-filling 只需一次传播，即便我们提交了多个未见过的 token？

点击查看答案

我们不需要生成"What is the"之后的内容，我们从用户那里已经知道它是"capital"。

我举的这个例子很短，仅为说明用途。但请记住：pre-filling 只需模型的一次前向传播，而解码可能需要数百次甚至更多。即使在我们这个短例子里，蓝色箭头也比橙色多。我们现在明白为什么 LLM 的输出如此耗时了！解码往往是我们花更多时间思考的环节，因为它有很多次传播。

## 基准测试工具

### 动机

我们都见过各种工具、新算法或模型的吞吐对比。吞吐固然是 LLM 推理故事的重要部分，但缺少一些关键信息。至少（当然你还可以更深入）我们需要同时知道吞吐和延迟，才能做出好的决策。TGI 基准测试工具的主要优势之一正是具备这一能力。

另一个重要的思路是思考你想给用户什么样的体验。你更在乎服务尽可能多的用户，还是希望每个进入系统的用户都能获得快速响应？你想要更好的 Time To First Token（TTFT），还是不介意第一个 token 晚一点、但之后 token 飞速涌现？

以下是一些可能的取舍思路。记住没有免费的午餐。但只要有足够的 GPU 和恰当的配置，你几乎想吃什么菜就有什么菜。

| **I care about…** | **I should focus on…** |
| --- | --- |
| Handling more users | Maximizing Throughput |
| People not navigating away from my page/app | Minimizing TTFT |
| User Experience for a moderate amount of users | Minimizing Latency |
| Well rounded experience | Capping latency and maximizing throughput |

### 环境搭建

基准测试工具随 TGI 一起安装，但你需要能访问服务器才能运行它。有鉴于此，我提供了这个 [Space](https://huggingface.co/spaces/derek-thomas/tgi-benchmark-space)（derek-thomas/tgi-benchmark-space），把 TGI docker 镜像（锁定最新版）和一个 jupyter lab 工作空间结合起来。它被设计为供你复制（duplicate），所以如果它在休眠不要惊讶。它允许我们部署自选模型，并方便地通过 CLI 运行基准测试工具。我加了几个 notebook，方便你按步骤操作。欢迎查看 [Dockerfile](https://huggingface.co/spaces/derek-thomas/tgi-benchmark-space/blob/main/Dockerfile) 了解构建方式，尤其是如果你想调整它。

### 理解基准测试工具

| [![Benchmarking Tool Charts](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/tgi-benchmarking/TGI-benchmark-screenshot.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/tgi-benchmarking/TGI-benchmark-screenshot.png) |
| --- |
| *Figure 4: Benchmarking Tool Charts* |

如果你用的硬件和设置与我相同，你应该会得到与图 4 非常接近的图。基准测试工具展示了在我们启动 TGI 时给定的当前设置和硬件下，不同批大小（用户请求数量，与启动 TGI 时的说法略有差异）对应的吞吐和延迟。理解这一点很重要，因为我们应该根据基准工具得到的发现来更新 TGI 的启动设置。

**组件 3** 的图表在有像 RAG 这样更长 prefill 时往往更有意思。它会影响 TTFT（显示在 X 轴上），这是用户体验的重要部分。记住，即使需要从零构建 KV cache，我们的输入 token 也可以在一次前向传播中推过去。因此在很多情况下，每 token 的 prefill 比解码更快。

**组件 5** 是解码时的图。来看看数据点形成的形状。可以看到 batch size 1-32 时形状几乎垂直于约 5.3s 处——非常好，意味着延迟不劣化的同时可以显著提升吞吐！64 和 128 时发生了什么？可以看到吞吐在增加的同时，我们开始牺牲延迟。

对同样的取值，来看看 **组件 3** 的图上发生了什么。batch size 32 时我们的 TTFT 仍约 1 秒。但从 32 → 64 → 128 可以看到线性增长：2 倍批大小带来 2 倍延迟，而且吞吐没有增益！这意味着这种权衡基本没带来什么好处。

思考题：

- 如果增加更多采样点，你预期这些曲线会呈现什么形状？
- 如果 token 更多（prefill 或解码），你预期这些曲线会如何变化？

如果你的批大小处于垂直区域，那太好了——你可以免费获得更多吞吐、服务更多用户。如果批大小处于水平区域，说明你已经算力受限，增加用户只会拖累所有人而吞吐没有好处。这时你应该改进 TGI 配置或扩容硬件。

现在我们已经了解了 TGI 在各种场景下的行为，可以尝试不同的 TGI 设置再做基准。最好在决定一个好的配置前把这一循环走几轮。如果有足够多的人感兴趣，也许我们可以写第二篇，深入聊天或 RAG 这类用例的优化。

### 收尾

跟踪真实用户行为很重要。当我们估计用户行为时总得从某个起点出发、做有依据的猜测，而这些数字选择会大大影响性能画像的结果。好在 TGI 能在日志里告诉我们这些信息，记得也去查看。

探索结束后，记得停掉所有东西以免产生额外费用。

- 在 `TGI-launcher.ipynb` notebook 中终止正在运行的 cell
- 在终端中按 `q` 停止性能剖析工具
- 在 space 设置中点击 pause

## 结论

LLM 笨重且昂贵，但有不少方法可以降低成本。只要我们善用其能力，像 TGI 这样的 LLM 推理服务器已经替我们做了大部分工作。第一步是搞清楚现状、理解你能做哪些权衡。我们已经看到如何用 TGI 基准测试工具做到这一点，并可以把结果用于 AWS、GCP 或 Inference Endpoints 上任何同等硬件。
