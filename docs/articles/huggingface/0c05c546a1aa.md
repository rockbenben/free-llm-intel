# Diffusers 中开放视频生成模型的现状

去年 OpenAI 的 Sora 演示标志着 AI 生成视频的一次惊人跃迁，让我们提前看到了视频生成模型的潜力。影响立竿见影：自那次演示以来，视频生成领域竞争愈发激烈，大厂和初创公司纷纷拿出各自强大的模型——Google 的 Veo2、Haliluo 的 Minimax、Runway 的 Gen3 Alpha、Kling、Pika，以及 Luma Lab 的 Dream Machine。

开源阵营也迎来了一波视频生成模型的爆发：CogVideoX、Mochi-1、Hunyuan、Allegro 和 LTX Video。视频社区会迎来自己的"Stable Diffusion 时刻"吗？

本文将简要梳理视频生成模型的现状、我们在开放视频生成模型上的位置，以及 Diffusers 团队如何规划大规模支持它们的落地。

具体会讨论：

- 视频生成模型的能力与局限
- 视频生成为什么难
- 开放的视频生成模型
- 用 Diffusers 做视频生成：推理与优化、微调
- 展望

**局限**：

- **资源需求高**：产出高质量视频需要大型预训练模型，开发和部署的算力成本都很高。这些成本来自数据集收集、硬件要求、大量训练迭代与实验。如此代价让"做开源免费模型"很难自圆其说。虽然没有详细技术报告披露 Sora 的训练资源，[这篇文章](https://www.factorialfunds.com/blog/under-the-hood-how-openai-s-sora-model-works)给出了一些还算靠谱的估计。
- **泛化**：不少开放模型泛化能力有限，达不到用户预期。模型可能需要特定方式的提示、LLM 风格的提示词，或者无法泛化到分布外数据——这些都是大规模用户采用的障碍。例如 LTX-Video 这类模型常常需要用非常详细、具体的提示才能获得高质量生成。
- **延迟**：视频生成的高计算与内存需求导致生成延迟显著。对本地使用而言这常常是拦路虎。大多数新的开放视频模型，在没有大量内存优化和量化手段（这些手段又同时影响推理延迟和生成质量）的情况下，社区硬件根本跑不动。

## 视频生成为什么难？

我们希望在视频中看到并控制的要素有不少：

- 对输入条件的遵从（如文本提示词、起始图像等）
- 真实感
- 美学
- 运动动态
- 时空一致性与连贯性
- FPS
- 时长

对图像生成模型，我们通常只关心前三项。而对视频生成，还要考虑运动质量、时间维度上的连贯与一致，可能还是多主体。要在合适的数据、正确的归纳偏置和训练方法之间找到平衡以满足这些额外要求，被证明比其他模态更具挑战。

## 开放的视频生成模型

[![diagram](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/video_gen/diagram.jpg)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/video_gen/diagram.jpg)

文生视频模型的组件与文生图模型类似：

- 文本编码器，为输入文本提示提供丰富表示
- 一个去噪网络
- 一个编码器与解码器，负责像素空间与潜空间之间的转换
- 一个非参数的调度器（scheduler），负责管理所有与时间步相关的计算和去噪步骤

最新一代视频模型有一个共同核心特征：去噪网络处理同时捕捉空间与时间信息的 3D 视频 token。负责生成并解码这些 token 的视频编码-解码系统同时做空间和时间压缩。虽然解码潜变量通常最吃内存，但这些模型提供了逐帧解码选项来降低内存占用。

文本条件的注入方式要么用联合注意力（joint attention，由 [Stable Diffusion 3](https://arxiv.org/abs/2403.03206)引入），要么用交叉注意力（cross-attention）。T5 已成为多数模型的首选文本编码器，Hunyuan 是例外——同时使用 CLIP-L 和 LLaMa 3。

去噪网络本身基于 [William Peebles 和 Saining Xie](https://arxiv.org/abs/2212.09748) 开发的 DiT 架构，同时融入了来自 [PixArt](https://arxiv.org/abs/2310.00426) 的多种设计元素。

## 用 Diffusers 生成视频

对视频模型，生成大致分三大类：

- 文本到视频
- 图像或图像控制条件 + 文本到视频
- 视频或视频控制条件 + 文本到视频

从文本（及其他条件）到视频只需几行代码。下面演示如何用 [Lightricks 的 LTX-Video 模型](https://huggingface.co/Lightricks/LTX-Video)做文生视频。

```
import torch
from diffusers import LTXPipeline
from diffusers.utils import export_to_video

pipe = LTXPipeline.from_pretrained("Lightricks/LTX-Video", torch_dtype=torch.bfloat16).to("cuda")

prompt = "A woman with long brown hair and light skin smiles at another woman with long blonde hair. The woman with brown hair wears a black jacket and has a small, barely noticeable mole on her right cheek. The camera angle is a close-up, focused on the woman with brown hair's face. The lighting is warm and natural, likely from the setting sun, casting a soft glow on the scene. The scene appears to be real-life footage"
negative_prompt = "worst quality, inconsistent motion, blurry, jittery, distorted"

video = pipe(
    prompt=prompt,
    negative_prompt=negative_prompt,
    width=704,
    height=480,
    num_frames=161,
    num_inference_steps=50,
).frames[0]
export_to_video(video, "output.mp4", fps=24)
```

### 内存需求

任何模型的内存需求可以由两部分相加得到：

- 权重所需内存
- 存储中间激活状态所需最大内存

权重所需内存可以通过量化、降到低精度 dtype 或卸载（offload）到 CPU 来降低。激活状态内存也能压缩，但过程更复杂，超出本文范围。

用极低的内存运行任何视频模型是可能的，但代价是推理耗时增加。如果某种优化技术引入的时间开销超出用户可接受的合理范围，推理就不可行。Diffusers 提供了许多此类优化，都是选择启用的，并且可以串联使用。

下表给出三个流行视频模型在合理默认设置下的内存需求：

| **模型名** | **内存（GB）** |
| --- | --- |
| HunyuanVideo | 60.09 |
| CogVideoX (1.5 5B) | 36.51 |
| LTX-Video | 17.75 |

这些数字在 80GB A100 上用以下设置测得（完整脚本见[这里](https://gist.github.com/sayakpaul/2bc49a30cf76cea07914104d28b1fb86)）：

- `torch.bfloat16` dtype
- `num_frames`: 121，`height`: 512，`width`: 768
- `max_sequence_length`: 128
- `num_inference_steps`: 50

这些需求相当惊人，让消费级硬件难以运行。在 Diffusers 里，用户可以选择不同优化来降低内存。下表是 HunyuanVideo 开启各种优化（只在质量和耗时上做最小妥协）后的内存需求。

我们选 HunyuanVideo 做这项研究，因为它足够大，能逐步展示优化的收益。

| **设置** | **内存** | **耗时** |
| --- | --- | --- |
| BF16 基础 | 60.10 GB | 863s |
| BF16 + CPU 卸载 | 28.87 GB | 917s |
| BF16 + VAE tiling | 43.58 GB | 870s |
| 8-bit BnB | 49.90 GB | 983s |
| 8-bit BnB + CPU 卸载* | 35.66 GB | 1041s |
| 8-bit BnB + VAE tiling | 36.92 GB | 997s |
| 8-bit BnB + CPU 卸载 + VAE tiling | 26.18 GB | 1260s |
| 4-bit BnB | 42.96 GB | 867s |
| 4-bit BnB + CPU 卸载 | 21.99 GB | 953s |
| 4-bit BnB + VAE tiling | 26.42 GB | 889s |
| 4-bit BnB + CPU 卸载 + VAE tiling | 14.15 GB | 995s |
| FP8 升精度计算 | 51.70 GB | 856s |
| FP8 升精度计算 + CPU 卸载 | 21.99 GB | 983s |
| FP8 升精度计算 + VAE tiling | 35.17 GB | 867s |
| FP8 升精度计算 + CPU 卸载 + VAE tiling | 20.44 GB | 1013s |
| BF16 + Group offload（blocks=8）+ VAE tiling | 15.67 GB | 925s |
| BF16 + Group offload（blocks=1）+ VAE tiling | 7.72 GB | 881s |
| BF16 + Group offload（leaf）+ VAE tiling | 6.66 GB | 887s |
| FP8 升精度计算 + Group offload（leaf）+ VAE tiling | 6.56 GB^ | 885s |

*`bitsandbytes` 的 8-bit 模型不像 4-bit 那样可以从 GPU 移回 CPU。
^内存无法再降，因为峰值来自注意力和前馈网络的计算。使用 [Flash Attention](https://github.com/Dao-AILab/flash-attention) 和 [Optimized Feed-Forward](https://github.com/huggingface/diffusers/pull/10623) 可以把这一需求降到约 5 GB。

我们沿用与上相同的设置取得这些数字。另请注意，由于数值精度损失，量化会影响输出质量——这种影响在视频里比在图像里更明显。

下面几节会更详细地介绍这些优化，并附上可用代码。如果你已经按捺不住，我们鼓励直接看[官方指南](https://huggingface.co/docs/diffusers/main/en/using-diffusers/text-img2vid)。

### 优化套件

视频生成在资源受限设备上相当困难，即便在更强的 GPU 上也很耗时。Diffusers 提供一整套工具来优化这些模型的运行时与内存消耗。这些优化分几类：

- **量化**：把模型权重量化到低精度数据类型，降低显存需求。Diffusers 目前支持三种量化后端：[bitsandbytes](https://huggingface.co/docs/diffusers/main/en/quantization/bitsandbytes)、[torchao](https://huggingface.co/docs/diffusers/main/en/quantization/torchao) 和 [GGUF](https://huggingface.co/docs/diffusers/main/en/quantization/gguf)。
- **卸载（Offloading）**：模型的各层可以在需要计算时按需加载到 GPU，用完再卸回 CPU，推理期间能省下大量内存。通过 `enable_model_cpu_offload()` 和 `enable_sequential_cpu_offload()` 支持卸载。详情见[这里](https://huggingface.co/docs/diffusers/main/en/optimization/memory#model-offloading)。
- **分块推理（Chunked Inference）**：沿输入潜张量的非嵌入维度切分推理，可以减少中间激活状态带来的内存开销。常见用法是编码器/解码器的切片/分块。Diffusers 中的分块推理通过 [feed-forward chunking](https://huggingface.co/docs/diffusers/main/en/api/pipelines/text_to_video#tips)、解码器 tiling 与 slicing、[split attention inference](https://huggingface.co/docs/diffusers/main/en/api/pipelines/animatediff#freenoise-memory-savings) 支持。
- **复用注意力与 MLP 状态**：在特定算法满足某些条件时，可以跳过部分去噪步的计算、复用之前的状态，以最小质量损失加速生成。

下面列几个仍在开发中、即将合并的进阶优化技术：

- [Layerwise Casting](https://github.com/huggingface/diffusers/pull/10347)：让用户以更低精度（如 `torch.float8_e4m3fn`）存储参数，以更高精度（如 `torch.bfloat16`）执行计算。
- [Group offloading](https://github.com/huggingface/diffusers/pull/10503)：让用户按内部 block 级或 leaf 级模块分组做卸载。好处是只有需要计算的部分被加载到 GPU。此外还支持用 CUDA streams 让数据传输与计算重叠，消除多次层装卸带来的大部分额外开销。

下面是给 HunyuanVideo 同时应用 4bit 量化、VAE tiling、CPU 卸载和 layerwise casting 的例子，把运行 `121 x 512 x 768` 分辨率视频所需显存降到约 6.5 GB。据我们所知，这是所有可用实现中运行 HunyuanVideo 的最低内存需求，且不牺牲速度。

想试用这些特性请从源码安装 Diffusers！部分实现与具体模型无关，很容易应用到其他后端——值得看看！

```
pip install git+https://github.com/huggingface/diffusers.git
```

```
import torch
from diffusers import (
    BitsAndBytesConfig,
    HunyuanVideoTransformer3DModel,
    HunyuanVideoPipeline,
)
from diffusers.utils import export_to_video
from diffusers.hooks import apply_layerwise_casting
from transformers import LlamaModel

model_id = "hunyuanvideo-community/HunyuanVideo"
quantization_config = BitsAndBytesConfig(
    load_in_4bit=True, bnb_4bit_compute_dtype=torch.bfloat16
)

text_encoder = LlamaModel.from_pretrained(model_id, subfolder="text_encoder", torch_dtype=torch.float16)
apply_layerwise_casting(text_encoder, storage_dtype=torch.float8_e4m3fn, compute_dtype=torch.float16)

# Apply 4-bit bitsandbytes quantization to Hunyuan DiT model
transformer = HunyuanVideoTransformer3DModel.from_pretrained(
    model_id,
    subfolder="transformer",
    quantization_config=quantization_config,
    torch_dtype=torch.bfloat16,
)

pipe = HunyuanVideoPipeline.from_pretrained(
    model_id, transformer=transformer, text_encoder=text_encoder, torch_dtype=torch.float16
)

# Enable memory saving
pipe.vae.enable_tiling()
pipe.enable_model_cpu_offload()

output = pipe(
    prompt="A cat walks on the grass, realistic",
    height=320,
    width=512,
    num_frames=61,
    num_inference_steps=30,
).frames[0]
export_to_video(output, "output.mp4", fps=15)
```

优化同样可以用在训练上。对视频模型最著名的两项技术是：

- **时间步蒸馏（Timestep distillation）**：教模型以递归方式用更少推理步更快去噪潜变量。例如一个模型原本需要 32 步生成好视频，可以让它尝试只用 16 步、8 步甚至 2 步预测最终输出！用的步数越少，质量损失可能越大。时间步蒸馏模型的例子包括 [Flux.1-Schnell](https://huggingface.co/black-forest-labs/FLUX.1-schnell/) 和 [FastHunyuan](https://huggingface.co/FastVideo/FastHunyuan)。
- **引导蒸馏（Guidance distillation）**：[Classifier-Free Guidance](https://arxiv.org/abs/2207.12598) 是扩散模型广泛使用的提升生成质量的技术，但它每个推理步要做两次完整前向传播再加一次插值，导致生成时间翻倍。通过教模型用一次前向传播直接预测两次前向加插值之后的输出，这个方法能大幅加速生成。引导蒸馏模型的例子包括 [HunyuanVideo](https://huggingface.co/docs/diffusers/main/api/pipelines/hunyuan_video) 和 [Flux.1-Dev](https://huggingface.co/black-forest-labs/FLUX.1-dev)。

关于视频生成和 Diffusers 当前能做什么的详细解读，请参阅[这份指南](https://huggingface.co/docs/diffusers/main/en/using-diffusers/text-img2vid)。

### 微调

我们创建了 [`finetrainers`](https://github.com/a-r-r-o-w/finetrainers)——一个让你轻松微调最新一代开放视频模型的仓库。例如用 LoRA 微调 CogVideoX 的做法：

```
# Download a dataset
huggingface-cli download \
  --repo-type dataset Wild-Heart/Disney-VideoGeneration-Dataset \
  --local-dir video-dataset-disney

# Then launch training
accelerate launch train.py \
  --model_name="cogvideox" --pretrained_model_name_or_path="THUDM/CogVideoX1.5-5B" \
  --data_root="video-dataset-disney" \
  --video_column="videos.txt" \
  --caption_column="prompt.txt" \
  --training_type="lora" \
  --seed=42 \
  --mixed_precision="bf16" \
  --batch_size=1 \
  --train_steps=1200 \
  --rank=128 \
  --lora_alpha=128 \
  --target_modules to_q to_k to_v to_out.0 \
  --gradient_accumulation_steps 1 \
  --gradient_checkpointing \
  --checkpointing_steps 500 \
  --checkpointing_limit 2 \
  --enable_slicing \
  --enable_tiling \
  --optimizer adamw \
  --lr 3e-5 \
  --lr_scheduler constant_with_warmup \
  --lr_warmup_steps 100 \
  --lr_num_cycles 1 \
  --beta1 0.9 \
  --beta2 0.95 \
  --weight_decay 1e-4 \
  --epsilon 1e-8 \
  --max_grad_norm 1.0

# ...
# (Full training command removed for brevity)
```

## 展望

我们预计 2025 年视频生成模型将持续取得重大进展，输出质量和模型能力都会有大的提升。我们的目标是让这些模型用起来简单、人人可及。我们会继续发展 `finetrainers` 库，并计划加入更多功能：Control LoRA、蒸馏算法、ControlNet、Adapter 等等。一如既往，欢迎社区贡献 🤗

我们将继续与模型发布者、研究人员和社区成员合作，确保视频生成的最新创新对每个人触手可及。
