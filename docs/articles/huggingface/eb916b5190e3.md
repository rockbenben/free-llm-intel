# 欢迎 RL 环境（RL Environments）入驻 Hub

强化学习（Reinforcement Learning）环境为 agentic AI 系统带来新的能力，也是衡量并改进你的 agent 性能的好办法。因此，Hugging Face Hub 现在为 RL Environments 专门留了一个位置。

一个环境会给 agent 一个任务，用 observation 回应它的动作，并对结果打分。由此产生的 reward 既能在评估阶段衡量 agent 的表现，也能在训练阶段提供学习信号。关于这个交互循环的入门介绍，见我们[关于环境的博客](https://huggingface.co/spaces/AdithyaSK/rl-environments-guide)。在环境内部，agent 要完成的那一组任务是以数据集的形式表示的，所以环境大致可以分成两部分：tasksets（任务集）和 runtimes（运行时）。这次发布我们聚焦在 tasksets 上。

Hub 上的一个 RL 环境就是一个数据集仓库，它会出现在新的 [RL Environments 过滤器](https://huggingface.co/datasets?other=rl-environment)里。**Use this dataset** 按钮会给你在该框架下运行它的命令。没有新增的仓库类型，没有注册中心，也不需要注册。Harbor、Verifiers 和 NVIDIA NeMo Gym 里已经有环境了。

## 别再自建环境注册中心

每篇 RL 论文、每个框架都用自己的方式去找环境：自建 hub、运行时注册中心、独立的任务数据集，或者一份 GitHub 上的任务清单配一个自定义 loader。结果是很多已发布的环境彼此隔离：如果你为某一个框架发布了环境，另外三个框架的用户加载不了。想用另一个框架或某篇新论文里的环境来训练，就得手工把它移植过来。

我们认为这个形态是错的。一个环境就是任务、测试、容器加一条 reward 规则——本质是数据，上面再叠一个运行时。Hub 已经在存储数据、做版本管理、做访问门槛、做预览，并把它们分发给数百万人。它不需要第二套系统来存放环境，它需要的是某种表达"这份数据是一个环境，这是它的运行方式"的办法。

任务数据放在 Hub 上。运行时配置和 verifier 代码可以放在仓库里，也可以放在框架里。

框架继续做它们擅长的事。Hub 做它擅长的事，也就是托管、发现和版本管理。没人需要去拥有那份目录。事实上，目录也可以跑在其他平台上，由 hub 来提供底层支撑。

数据集仓库托管你的环境文件，框架则在本地或某个受支持的云端后端运行它们。[Hugging Face Jobs](https://huggingface.co/docs/hub/en/jobs) 可以运行云端工作负载，而基于 Jobs 构建的 [Hugging Face Sandboxes](https://huggingface.co/docs/huggingface_hub/main/guides/sandbox) 提供交互式命令执行。标签描述兼容性并据此生成加载命令；添加一个标签并不会启动 job 或 sandbox。

## 已经上线了什么

**RL Environments 过滤器。** 打开 [huggingface.co/datasets?other=rl-environment](https://huggingface.co/datasets?other=rl-environment)，凡是带 `rl-environment` 标签的数据集都会出现在那里，无论它适配哪个框架。

**框架标签。** 有四个环境框架被注册为数据集库：

| 标签 | 框架 |
| --- | --- |
| `harbor` | [Harbor](https://github.com/harbor-framework/harbor) |
| `verifiers` | [Verifiers](https://github.com/PrimeIntellect-ai/verifiers) |
| `openenv` | [OpenEnv](https://github.com/huggingface/OpenEnv) |
| `nemo-gym` | [NeMo Gym](https://github.com/NVIDIA-NeMo/Gym) |

每个框架标签都会在数据集页面上展示该框架的图标，并在 **Use this dataset** 中加上一段自动生成的代码片段。

一个数据集可以同时带多个框架标签，这正是设计的用意所在。标签描述的是兼容性，而兼容性并不互斥。被列出的每个框架都必须真的支持仓库里的文件；加一个标签并不会把它们转换过去。

## 运行一个环境并查看它的 reward

选对应你框架的那个示例，在独立的 Python 环境中按下文列出的前置条件运行。

### Harbor：运行参考解法

[Harbor](https://www.harborframework.com/docs/datasets) 可以从 Hub 仓库加载任务目录。oracle agent 会执行该任务的参考解法，然后由 verifier 给结果打分，它不会调用任何模型。

```
uv tool install --python 3.13 'harbor==0.21.0'
harbor run \
    --repo https://huggingface.co/datasets/harborframework/terminal-bench-2.1 \
    --dataset terminal-bench-2.1@2.1.0 \
    --include-task-name '*regex-log' \
    --agent oracle --env docker --jobs-dir results/harbor
harbor view results/harbor
```

查看器会显示任务的 reward、verifier 输出和日志。这能让你在试模型 agent 之前，先把任务和它的参考解法检查一遍。

### Verifiers：用模型跑同一个任务

[verifiers v1](https://www.primeintellect.ai/blog/verifiers-v1) 的 Harbor 集成可以在不同运行时（比如 Docker）中运行同一批任务目录，也支持不同的 harness，包括一个极简的 bash harness。

```
uvx --python 3.13 --from 'verifiers[harbor]' eval harbor \
    --env.taskset.repo https://huggingface.co/datasets/harborframework/terminal-bench-2.1 \
    --env.taskset.dataset terminal-bench-2.1@2.1.0 \
    --env.taskset.tasks '["regex-log"]' \
    --env.agent.runtime.type docker \
    --env.agent.harness.id bash \
    --model "$MODEL" \
    --client.base-url "$LLM_URL"
```

这里的 repo 是完整的 Hugging Face Git URL，而 dataset 是该仓库 registry.json 里的名称和版本。这个 loader 沿用 Harbor 的注册约定，所以单凭一个 Hub 仓库 ID 无法同时替代这两个值。

### OpenEnv：运行 agent 并查看它的 reward

[OpenEnv 的 Harbor 集成](https://huggingface.co/docs/openenv/main/environments/harbor) 可以用 OpenCode 这样的 agent 运行同一批任务目录，并在返回 agent trace 的同时给出 verifier 的 reward。

```
pip install "openenv[harbor]==0.7.0"

openenv harbor rollout \
    --llm-url "$LLM_URL" \
    --model "$MODEL" \
    --dataset harborframework/terminal-bench-2.1 \
    --task-index 0 \
    --harness opencode \
    --sandbox docker \
    --out rollout.json
```

这条命令会下载数据集的 `tasks/` 目录，在 Docker 里运行其中一个任务，并写出结果。默认连接使用一个临时的 Gradio 隧道，好让沙箱里的 agent 能够访问 OpenEnv 的模型代理。读取 verifier 结果和模型调用次数：

```
import json
from pathlib import Path

result = json.loads(Path("rollout.json").read_text())[0]
print("Reward:", result["reward"])
print("Model calls:", result["n_turns"])
print("Error:", result["error"])
```

reward 为 `None` 表示 verifier 没有产出 reward；在把这次运行判读成模型失败之前，先看 `error`。这条路径要求使用 Harbor 的任务目录。

### NeMo Gym：生成回答并查看 reward

[NeMo Gym](https://github.com/NVIDIA-NeMo/Gym) 同时支持评估和 RL 训练：它的环境负责采集轨迹并计算 reward，而训练框架负责更新模型权重。举个例子，[Structured Outputs 数据集](https://huggingface.co/datasets/nvidia/Nemotron-RL-instruction_following-structured_outputs) 把 prompt 与 JSON schema 配对，它的 verifier 只针对是否遵循 schema 给 reward，并不检查生成内容在事实上是否正确。

最出色的一点是，这带来了一个仓库和一个讨论区，人们在其中报告来自所有主要框架的坏任务。于是当作者修好一个坏测试，每个框架在下一次 pull 时都能拿到这个修复。

## 给你的环境打标签

打开你的数据集卡片，在 YAML 头部加上这些：

```
---
pretty_name: Terminal-Bench 2.0
tags:
- rl-environment
- harbor
- verifiers
---
```

集成要做的就这些。保留 `rl-environment`，然后列出所有能加载你这些文件的框架。如果你的环境能跑在我们还没注册的框架上，请向[受支持库列表](https://github.com/huggingface/huggingface.js/blob/main/packages/tasks/src/dataset-libraries.ts)提一个 PR。

完整参考见[文档](https://huggingface.co/docs/hub/datasets-cards#declare-an-rl-environment-dataset)。

## 已经在 Hub 上的环境

我们已经提了一批 PR，为人们本来就在训练的一些环境加上标签。如果你是其中某个环境的维护者，合并那个 PR，你的环境就会出现在过滤器里。

**Harbor**

- [BeyondSWE](https://huggingface.co/datasets/AweAI-Team/BeyondSWE-harbor/discussions/1)：把 BeyondSWE 基准整理成 Harbor 任务目录，每个实例一个文件夹。
- [Terminal-Lego](https://huggingface.co/datasets/Lego-X/Terminal-Lego-15k/discussions/1)：基于真实 StackOverflow issue 构建的 Terminal-Bench 风格任务，只有通过 Docker 往返验证的才保留下来。
- [Harbor-Mix](https://huggingface.co/datasets/harborframework/harbor-mix/discussions/2)：从 Harbor adapters 池中挑出的 100 个高难度 agentic 任务，比跑完整的多基准扫一遍更省钱。
- [NatureBench](https://huggingface.co/datasets/FrontisAI/NatureBench-Harbor/discussions/2)：为 Harbor 预先构建好的 90 个 NatureBench 任务。

**Verifiers**

- [Reverse-Text-RL](https://huggingface.co/datasets/PrimeIntellect/Reverse-Text-RL/discussions/2)：prime-rl 在 CI 里用来调试 RL 训练的那个小型反转任务。
- [Multi-SWE-RL-Verified](https://huggingface.co/datasets/PrimeIntellect/Multi-SWE-RL-Verified/discussions/2)：Multi-SWE-RL 的 4,703 条数据中通过 gold-patch 校验的 2,232 条，覆盖 C、Go、Java、JavaScript、Rust 和 TypeScript。
- [R2E-Gym-Subset-Verified](https://huggingface.co/datasets/PrimeIntellect/R2E-Gym-Subset-Verified/discussions/1)：经过验证的 R2E-Gym 子集。
- [Scale-SWE-Verified](https://huggingface.co/datasets/PrimeIntellect/Scale-SWE-Verified/discussions/2)：20,181 个 Python 修 issue 任务中，端到端能给出干净 reward 信号的 17,202 个。

**NeMo Gym**

- [Workplace Assistant](https://huggingface.co/datasets/nvidia/Nemotron-RL-agent-workplace_assistant/discussions/3)：一个多步工具使用沙箱，含五个数据库、26 个工具和 690 个业务任务。
- [Structured Outputs](https://huggingface.co/datasets/nvidia/Nemotron-RL-instruction_following-structured_outputs/discussions/2)：带结构化输出的指令遵循。
- [CFBench](https://huggingface.co/datasets/nvidia/Nemotron-RL-CFBench-v1/discussions/2)：多语言约束遵循。
- [SysBench](https://huggingface.co/datasets/nvidia/Nemotron-RL-SysBench-v1/discussions/1)：多轮 system message 遵循。

## 接下来

更大的目标是让框架打标在各处都自动化。OpenEnv 已经在上传环节自动做了这件事。如果你维护 Harbor、Verifiers、Nemo Gym 或任何其他环境框架，把打标签加进你的 push 流程。只需几行代码，你的用户发布的每一个环境就能被其他所有人看到。

如果你训练 agent，去[过滤器](https://huggingface.co/datasets?other=rl-environment)里逛逛。如果你构建环境，就把它们发布出来并打上标签，无论它们覆盖的是编程、工具使用、游戏、机器人还是别的任务。请把文件、一条能跑通的运行命令、以及产出 reward 的规则一起提供，好让其他人也能用。如果你的框架还没被收录，欢迎把它贡献到[受支持库列表](https://github.com/huggingface/huggingface.js/blob/main/packages/tasks/src/dataset-libraries.ts)。
