# 在 🤗 Transformers 中用受约束的 beam search 引导文本生成

## **引言**

本文假设读者已经熟悉使用 beam search 各种变体进行文本生成的方法，相关内容见博客文章：[《如何生成文本：为 Transformers 的语言生成使用不同的解码方法》](https://huggingface.co/blog/how-to-generate)

与普通的 beam search 不同，**受约束的（constrained）** beam search 让我们能够对文本生成的输出施加控制。这很有用，因为我们有时确切地知道输出里想要什么。例如，在神经机器翻译任务中，借助词典查询我们可能知道最终译文里必须包含哪些词。有时，对于语言模型来说概率几乎相当的生成结果，因为特定的上下文，对最终用户而言未必同样令人满意。这两种情况都可以通过让用户告诉模型最终输出中必须包含哪些词来解决。

### **为什么这件事很难**

然而，这其实是一个非常不平凡的问题。因为这项任务要求我们在最终输出中的*某个位置*、在生成过程中的*某个时刻*，强制生成某些子序列。

假设我们要生成一个句子 `S`，它必须按顺序包含短语 p_1 = {t_1, t_2}（其中 token t_1、t_2 需保持先后顺序）。我们把期望的句子 S 定义为：

S_{expected} = {s_1, s_2, ..., s_k, t_1, t_2, s_{k+1}, ..., s_n}

问题在于 beam search 是*逐 token* 生成序列的。虽然不完全准确，但可以把 beam search 看作一个函数 B(s_{0:i}) = s_{i+1}，它会查看当前从 0 到 i 已生成的 token 序列，然后预测 i+1 处的下一个 token。可这个函数在任意一个 i < k 的步上，怎么可能知道这些 token 必须在未来某个 k 步生成呢？而当它走到 i = k 这一步时，又怎么能确定这里是强制生成这些 token 的最佳位置，而不是未来的某个 i > k 步呢？

[![Why constraints are hard](https://raw.githubusercontent.com/huggingface/blog/main/assets/53_constrained_beam_search/why_constraints_are_hard.png)](https://raw.githubusercontent.com/huggingface/blog/main/assets/53_constrained_beam_search/why_constraints_are_hard.png)

那如果你有多个约束、且要求各不相同呢？如果你想同时强制短语 p_1 = {t_1, t_2} *和* 短语 p_2 = {t_3, t_4, t_5, t_6} 呢？如果你想让模型在**两个短语之间二选一**呢？如果我们想强制短语 p_1，同时在短语列表 {p_21, p_22, p_23} 中只强制其中一个呢？

上面这些例子其实都是非常合理的用例，下文将会说明这一点，而新的受约束 beam search 功能对它们全都支持！

本文将先快速介绍新的 ***受约束的 beam search*** 功能能为你做什么，然后再深入讲解它在底层是如何工作的。

## **示例 1：强制生成一个词**

假设我们要把 `"How old are you?"` 翻译成德语。

`"Wie alt bist du?"` 是非正式场合的说法，而 `"Wie alt sind Sie?"` 是正式场合的说法。

根据上下文不同，我们可能更想要其中一种正式程度而非另一种，但我们该怎么告诉模型这一点呢？

### **传统 beam search**

在***传统的 beam search 设定***下，我们做文本翻译的方式如下。

```
!pip install -q git+https://github.com/huggingface/transformers.git
```

```
from transformers import AutoTokenizer, AutoModelForSeq2SeqLM

tokenizer = AutoTokenizer.from_pretrained("t5-base")
model = AutoModelForSeq2SeqLM.from_pretrained("t5-base")

encoder_input_str = "translate English to German: How old are you?"

input_ids = tokenizer(encoder_input_str, return_tensors="pt").input_ids

outputs = model.generate(
    input_ids,
    num_beams=10,
    num_return_sequences=1,
    no_repeat_ngram_size=1,
    remove_invalid_values=True,
)

print("Output:\n" + 100 * '-')
print(tokenizer.decode(outputs[0], skip_special_tokens=True))
```

```
Output:
----------------------------------------------------------------------------------------------------
Wie alt bist du?
```

### **使用受约束的 beam search**

但如果我们事先就知道想要正式的输出而非非正式的输出呢？如果我们凭先验知识就知道生成结果必须包含什么，并且能把这个要求*注入*到生成过程中呢？

现在，通过 `model.generate()` 的 `force_words_ids` 关键字参数就能做到下面这些：

```
tokenizer = AutoTokenizer.from_pretrained("t5-base")
model = AutoModelForSeq2SeqLM.from_pretrained("t5-base")

encoder_input_str = "translate English to German: How old are you?"

force_words = ["Sie"]

input_ids = tokenizer(encoder_input_str, return_tensors="pt").input_ids
force_words_ids = tokenizer(force_words, add_special_tokens=False).input_ids

outputs = model.generate(
    input_ids,
    force_words_ids=force_words_ids,
    num_beams=5,
    num_return_sequences=1,
    no_repeat_ngram_size=1,
    remove_invalid_values=True,
)


print("Output:\n" + 100 * '-')
print(tokenizer.decode(outputs[0], skip_special_tokens=True))
```

```
Output:
----------------------------------------------------------------------------------------------------
Wie alt sind Sie?
```

可以看到，我们借助关于期望输出的先验知识引导了生成。以前，我们得先生成一大批可能的输出，再筛选出符合要求的那些；现在我们在生成阶段就能做到这一点。

## **示例 2：析取约束（Disjunctive Constraints）**

上面我们提到过一种用例：我们知道自己希望最终输出里包含哪些词。一个例子就是在神经机器翻译过程中使用词典查询。

但如果我们不知道该用哪种*词形*呢——我们希望像 `["raining", "rained", "rains", ...]` 这样的输出具有同等的可行性？更一般地说，总会有一些场景，我们并不想要*逐字逐字母一模一样的那个词*，也对其他相关的形式持开放态度。

允许这种行为的约束叫做***析取约束（Disjunctive Constraints）***，它让用户输入一个词列表，其目的是引导生成，使得最终输出必须包含该词列表中的*至少一个*。

下面这个例子把上面两类约束混合使用：

```
from transformers import GPT2LMHeadModel, GPT2Tokenizer

model = GPT2LMHeadModel.from_pretrained("gpt2")
tokenizer = GPT2Tokenizer.from_pretrained("gpt2")

force_word = "scared"
force_flexible = ["scream", "screams", "screaming", "screamed"]

force_words_ids = [
    tokenizer([force_word], add_prefix_space=True, add_special_tokens=False).input_ids,
    tokenizer(force_flexible, add_prefix_space=True, add_special_tokens=False).input_ids,
]

starting_text = ["The soldiers", "The child"]

input_ids = tokenizer(starting_text, return_tensors="pt").input_ids

outputs = model.generate(
    input_ids,
    force_words_ids=force_words_ids,
    num_beams=10,
    num_return_sequences=1,
    no_repeat_ngram_size=1,
    remove_invalid_values=True,
)


print("Output:\n" + 100 * '-')
print(tokenizer.decode(outputs[0], skip_special_tokens=True))
print(tokenizer.decode(outputs[1], skip_special_tokens=True))
```

```
Setting `pad_token_id` to `eos_token_id`:50256 for open-end generation.


Output:
----------------------------------------------------------------------------------------------------
The soldiers, who were all scared and screaming at each other as they tried to get out of the
The child was taken to a local hospital where she screamed and scared for her life, police said.
```

可以看到，第一个输出用了 `"screaming"`，第二个输出用了 `"screamed"`，而两者都原样用到了 `"scared"`。可供选择的列表 `["screaming", "screamed", ...]` 不一定非得是词形；它可以满足任何"只需从一组词里取一个"的用例。

## **传统 beam search**

下面是传统 **beam search** 的一个例子，取自之前的一篇[博客文章](https://huggingface.co/blog/how-to-generate)：

[![Beam search](https://raw.githubusercontent.com/patrickvonplaten/scientific_images/master/beam_search.png)](https://raw.githubusercontent.com/patrickvonplaten/scientific_images/master/beam_search.png)

与贪心搜索不同，beam search 通过保留更长的候选假设列表来工作。在上图中，我们在生成的每个可能步骤上展示了三个下一个可能的 token。

对于上面的例子，换一种方式来看 beam search 的第一步，这里 `num_beams=3`：

[![Beam search step 1](https://raw.githubusercontent.com/huggingface/blog/main/assets/53_constrained_beam_search/beam_1.jpg)](https://raw.githubusercontent.com/huggingface/blog/main/assets/53_constrained_beam_search/beam_1.jpg)

beam search 不会像贪心搜索那样只选 `"The dog"`，而是允许*进一步考虑* `"The nice"` 和 `"The car"`。

在下一步，我们对上一步创建的那三个分支，分别考虑各自下一个可能的 token。

[![Beam search step 2](https://raw.githubusercontent.com/huggingface/blog/main/assets/53_constrained_beam_search/beam_2.jpg)](https://raw.githubusercontent.com/huggingface/blog/main/assets/53_constrained_beam_search/beam_2.jpg)

虽然我们最终*考虑*的输出远多于 `num_beams` 个，但我们会在每一步结束时把它们缩减到 `num_beams` 个。我们不能一直分叉下去，否则对于 n 步，需要跟踪的 `beam` 数量将达到 beams^n，这很快就会变得极大（10 条 beam 经过 10 步就是 10,000,000,000 条 beam！）。

对于剩下的生成过程，我们重复上述步骤，直到满足终止条件，比如生成了 `<eos>` token 或达到了 `max_length`。分叉、排序、缩减，然后重复。

## **受约束的 beam search**

受约束的 beam search 会在生成的每一步*注入*所需的 token，从而尝试满足约束。

假设我们想在生成的输出中强制出现短语 `"is fast"`。

在传统的 beam search 设定中，我们在每个分支上找出概率最高的前 `k` 个下一个 token，并把它们追加进去以供考虑。在受约束的设定中，我们同样这么做，但还会追加那些能让我们*更接近满足约束*的 token。下面是一个演示：

[![Constrained Beam Search Step 1](https://raw.githubusercontent.com/huggingface/blog/main/assets/53_constrained_beam_search/cbeam_1.jpg)](https://raw.githubusercontent.com/huggingface/blog/main/assets/53_constrained_beam_search/cbeam_1.jpg)

在 `"dog"`、`"nice"` 这类通常的高概率下一个 token 之上，我们强制加入 token `"is"`，以便让我们更接近满足 `"is fast"` 这个约束。

对于下一步，下面分叉出来的候选大多与传统 beam search 相同。但和上面的例子一样，受约束的 beam search 会在每个新分支上强制施加约束，从而在已有候选的基础上追加候选：

[![Constrained Beam Search Step 2](https://raw.githubusercontent.com/huggingface/blog/main/assets/53_constrained_beam_search/cbeam_2.jpg)](https://raw.githubusercontent.com/huggingface/blog/main/assets/53_constrained_beam_search/cbeam_2.jpg)

### **Bank（束组）**

在讲下一步之前，我们需要先想想上面那一步中可以看到的那种不良结果行为。

天真地只是在输出中强制想要的短语 `"is fast"`，问题在于大多数时候你会得到像上面 `"The is fast"` 这样毫无意义的输出。这恰恰是它成为一个不平凡问题的原因。关于解决这一问题复杂性的更深入讨论，可以在 `huggingface/transformers` 里提出的[原始功能请求 issue](https://github.com/huggingface/transformers/issues/14081#issuecomment-1004479944) 中找到。

Bank 通过在满足约束和生成合理输出之间达成一种*平衡*来解决这个问题。

第 n 个 Bank（Bank n）指的是***在满足约束方面已经推进了 n 步的 beam 列表***。把所有可能的 beam 归入各自对应的 Bank 并排序后，我们做一次轮询（round-robin）选择。以上面的例子来说，我们会先选出 Bank 2 中最可能的输出，再选出 Bank 1 中最可能的，然后从 Bank 0 选一个，接着是 Bank 2 中第二可能的、Bank 1 中第二可能的，依此类推。因为我们用的是 `num_beams=3`，所以只需把上述过程做三次，最终得到 `["The is fast", "The dog is", "The dog and"]`。

这样一来，即使我们*强制*模型去考虑那个手动追加了所需 token 的分支，我们仍然在跟踪其他概率很高、很可能更有意义的序列。虽然 `"The is fast"` 完全满足了我们的约束，但它并不是一个很有意义的短语。幸运的是，还有 `"The dog is"` 和 `"The dog and"` 供我们在未来的步骤中使用，希望它们随后能带来更有意义的输出。

这一行为在上面示例的第三步中得到了展示：

[![Constrained Beam Search Step 3](https://raw.githubusercontent.com/huggingface/blog/main/assets/53_constrained_beam_search/cbeam_3.jpg)](https://raw.githubusercontent.com/huggingface/blog/main/assets/53_constrained_beam_search/cbeam_3.jpg)

注意，`"The is fast"` 不再需要手动追加任何约束 token，因为它已经满足了约束（即它已经包含了短语 `"is fast"`）。另外，注意像 `"The dog is slow"` 或 `"The dog is mad"` 这样的 beam 其实位于 Bank 0，因为尽管它包含了 token `"is"`，它必须从头重新开始才能生成 `"is fast"`。通过在 `"is"` 后面追加 `"slow"` 之类的词，它实际上*重置了自己的进度*。

最后注意，我们最终得到了一个既合理又包含约束短语的输出：`"The dog is fast"`！

我们起初之所以担心，是因为盲目地追加所需 token 会导致像 `"The is fast"` 这样毫无意义的短语。然而，通过使用从各个 Bank 轮询选择这一方式，我们不知不觉间就摒弃了毫无意义的输出，转而得到更有意义的输出。

## **更多关于 `Constraint` 类与自定义约束的内容**

从上面的讲解中可以得出的主要结论可以概括如下：在每一步，我们不断"催促"模型去考虑那些满足我们约束的 token，同时始终跟踪那些不满足约束的 beam，直到我们最终得到概率相当高、且包含所需短语的序列。

因此，设计这一实现的一个有原则的方式，就是把每个约束都表示成一个 `Constraint` 对象，它的目的是跟踪自己的进度，并告诉 beam search 下一个该生成哪些 token。虽然我们为 `model.generate()` 提供了 `force_words_ids` 关键字参数，但后端实际发生的其实是下面这样：

```
from transformers import AutoTokenizer, AutoModelForSeq2SeqLM, PhrasalConstraint

tokenizer = AutoTokenizer.from_pretrained("t5-base")
model = AutoModelForSeq2SeqLM.from_pretrained("t5-base")

encoder_input_str = "translate English to German: How old are you?"

constraints = [
    PhrasalConstraint(
        tokenizer("Sie", add_special_tokens=False).input_ids
    )
]

input_ids = tokenizer(encoder_input_str, return_tensors="pt").input_ids


outputs = model.generate(
    input_ids,
    constraints=constraints,
    num_beams=10,
    num_return_sequences=1,
    no_repeat_ngram_size=1,
    remove_invalid_values=True,
)


print("Output:\n" + 100 * '-')
print(tokenizer.decode(outputs[0], skip_special_tokens=True))
```

```
Output:
----------------------------------------------------------------------------------------------------
Wie alt sind Sie?
```

你也可以自己定义一个约束，并把它传入 `constraints` 关键字参数，从而设计出你独特的约束。你只需要创建 `Constraint` 抽象接口类的一个子类，并遵循它的要求即可。更多信息见[这里](https://github.com/huggingface/transformers/blob/main/src/transformers/generation/beam_constraints.py)的 `Constraint` 定义。

一些独特的想法（尚未实现；也许你可以来试一试！）包括 `OrderedConstraints`、`TemplateConstraints` 这类约束，它们日后可能会加入。目前，只要把相应的序列包含进输出的任意位置，生成就算满足了约束。例如，前面的例子中一个序列是 scared -> screaming，另一个是 screamed -> scared。`OrderedConstraints` 则可以让用户指定这些约束被满足的先后顺序。

`TemplateConstraints` 可以让这一功能用于更小众的场景，其目标可以是类似这样的东西：

```
starting_text = "The woman"
template = ["the", "", "School of", "", "in"]

possible_outputs == [
   "The woman attended the Ross School of Business in Michigan.",
   "The woman was the administrator for the Harvard School of Business in MA."
]
```

或者：

```
starting_text = "The woman"
template = ["the", "", "", "University", "", "in"]

possible_outputs == [
   "The woman attended the Carnegie Mellon University in Pittsburgh.",
]
impossible_outputs == [
  "The woman attended the Harvard University in MA."
]
```

或者，如果用户并不在意两个词之间可以插入多少个 token，那么直接用 `OrderedConstraint` 就可以了。

## **结语**

受约束的 beam search 给了我们一种灵活的手段，把外部知识和要求注入文本生成。以前，要告诉模型去 1. 包含一个序列列表，其中 2. 有些是可选的、有些是必需的，并且 3. 这些序列要在序列中的*某个位置*、各自合理的位置上被生成，是没有简单办法的。现在，借助不同 `Constraint` 对象子类的混合使用，我们可以完全掌控自己的生成了！

这一新功能主要基于以下几篇论文：

- [Guided Open Vocabulary Image Captioning with Constrained Beam Search](https://arxiv.org/pdf/1612.00576.pdf)
- [Fast Lexically Constrained Decoding with Dynamic Beam Allocation for Neural Machine Translation](https://arxiv.org/abs/1804.06609)
- [Improved Lexically Constrained Decoding for Translation and Monolingual Rewriting](https://aclanthology.org/N19-1090/)
- [Guided Generation of Cause and Effect](https://arxiv.org/pdf/2107.09846.pdf)

和上面这些一样，许多新的研究论文都在探索如何利用外部知识（例如知识图谱 KG、知识库 KB）来引导大型深度学习模型的输出。希望这一受约束的 beam search 功能能成为实现该目标的又一种有效途径。
