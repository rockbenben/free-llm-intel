**更新（2024/02）：性能进一步提升！查看我们的[最新基准测试](https://huggingface.co/docs/optimum-neuron/benchmarks/inferentia-llama2)。**

在[Hugging Face 博客上一篇文章](https://huggingface.co/blog/accelerate-transformers-with-inferentia2)中，我们介绍了 [AWS Inferentia2](https://aws.amazon.com/ec2/instance-types/inf2/)——第二代 AWS Inferentia 加速器，并解释了你如何使用 [optimum-neuron](https://huggingface.co/docs/optimum-neuron/index) 在 AWS Inferentia 2 实例上快速部署用于标准文本和视觉任务的 Hugging Face 模型。

作为与 [AWS Neuron SDK](https://github.com/aws-neuron/aws-neuron-sdk) 集成的进一步步骤，现在可以使用 🤗 [optimum-neuron](https://huggingface.co/docs/optimum-neuron/index) 在 AWS Inferentia2 上部署用于文本生成的 LLM 模型。

而对于这一演示，没有比 [Llama 2](https://huggingface.co/meta-llama/Llama-2-13b-hf)——[Hugging Face 中心](https://huggingface.co/models)上最受欢迎的模型之一——更合适的选择了。

## 在你的 Inferentia2 实例上配置 🤗 optimum-neuron

我们的建议是使用 [Hugging Face Neuron Deep Learning AMI](https://aws.amazon.com/marketplace/pp/prodview-gr3e6yiscria2)（DLAMI）。DLAMI 已为你预先打包好所有必需的库，包括 Optimum Neuron、Neuron 驱动、Transformers、Datasets 和 Accelerate。

或者，你可以使用 [Hugging Face Neuron SDK DLC](https://github.com/aws/deep-learning-containers/releases?q=hf&expanded=true) 部署到 Amazon SageMaker。

*注：敬请留意一篇专门讲 SageMaker 部署的后续文章。*

最后，这些组件也可以按照 `optimum-neuron` 的[安装说明](https://huggingface.co/docs/optimum-neuron/installation)在一个全新的 Inferentia2 实例上手动安装。

## 将 Llama 2 模型导出到 Neuron

如 [optimum-neuron 文档](https://huggingface.co/docs/optimum-neuron/guides/export_model#why-compile-to-neuron-model)所述，模型在 Neuron 设备上运行之前，需要被编译并导出为一种序列化格式。

幸运的是，🤗 `optimum-neuron` 提供了一个[极其简单的 API](https://huggingface.co/docs/optimum-neuron/guides/models#configuring-the-export-of-a-generative-model)，可将标准的 🤗 [transformers 模型](https://huggingface.co/docs/transformers/index)导出为 Neuron 格式。

```
>>> from optimum.neuron import NeuronModelForCausalLM

>>> compiler_args = {"num_cores": 24, "auto_cast_type": 'fp16'}
>>> input_shapes = {"batch_size": 1, "sequence_length": 2048}
>>> model = NeuronModelForCausalLM.from_pretrained(
        "meta-llama/Llama-2-7b-hf",
        export=True,
        **compiler_args,
        **input_shapes)
```

这一点值得稍作解释：

- 使用 `compiler_args`，我们指定希望模型部署在多少个核心上（每个 neuron 设备有两个核心），以及采用哪种精度（这里是 `float16`），
- 使用 `input_shape`，我们设置模型的静态输入和输出维度。所有模型编译器都需要静态形状，neuron 也不例外。请注意，`sequence_length` 不仅约束输入上下文的长度，也约束 KV cache 的长度，因而也约束输出长度。

根据你选择的参数和 inferentia 主机，这可能需要几分钟到一个多小时不等。

幸运的是，你只需要做一次，因为你可以保存模型并在之后重新加载。

```
>>> model.save_pretrained("a_local_path_for_compiled_neuron_model")
```

更好的是，你可以把它推送到 [Hugging Face 中心](https://huggingface.co/models)。

```
>>> model.push_to_hub(
        "a_local_path_for_compiled_neuron_model",
        repository_id="aws-neuron/Llama-2-7b-hf-neuron-latency")
```

## 在 AWS Inferentia2 上用 Llama 2 生成文本

模型导出后，你可以使用 transformers 库来生成文本，正如在[这篇先前的文章中详细描述的](https://huggingface.co/blog/how-to-generate)那样。

```
>>> from optimum.neuron import NeuronModelForCausalLM
>>> from transformers import AutoTokenizer

>>> model = NeuronModelForCausalLM.from_pretrained('aws-neuron/Llama-2-7b-hf-neuron-latency')
>>> tokenizer = AutoTokenizer.from_pretrained("aws-neuron/Llama-2-7b-hf-neuron-latency")

>>> inputs = tokenizer("What is deep-learning ?", return_tensors="pt")
>>> outputs = model.generate(**inputs,
                             max_new_tokens=128,
                             do_sample=True,
                             temperature=0.9,
                             top_k=50,
                             top_p=0.9)
>>> tokenizer.batch_decode(outputs, skip_special_tokens=True)
['What is deep-learning ?\nThe term “deep-learning” refers to a type of machine-learning
that aims to model high-level abstractions of the data in the form of a hierarchy of multiple
layers of increasingly complex processing nodes.']
```

*注：当向模型传入多个输入 prompt 时，得到的 token 序列必须用一个结束符 token 在左侧补齐。随导出模型保存的 tokenizer 已相应配置好。*

支持以下生成策略：

- 贪心搜索（greedy search），
- 带 top-k 和 top-p 的多项式采样（带 temperature）。

大多数 logits 预处理/过滤器（如重复惩罚）都受到支持。

## 用 optimum-neuron 管线实现一体化

对于喜欢简单的人来说，还有一种更简单的方式，即使用 [optimum-neuron 管线](https://huggingface.co/docs/optimum-neuron/guides/pipelines)在 AWS inferentia 2 上使用 LLM 模型。

使用它们就像这样简单：

```
>>> from optimum.neuron import pipeline

>>> p = pipeline('text-generation', 'aws-neuron/Llama-2-7b-hf-neuron-budget')
>>> p("My favorite place on earth is", max_new_tokens=64, do_sample=True, top_k=50)
[{'generated_text': 'My favorite place on earth is the ocean. It is where I feel most
at peace. I love to travel and see new places. I have a'}]
```

## 基准测试

但在 Inferentia2 上文本生成究竟有多高效？让我们来一探究竟！

我们已在中心上上传了 LLama 2 7B 和 13B 模型采用不同配置的预编译版本：

| 模型类型 | num cores | batch_size | Hugging Face Hub 模型 |
| --- | --- | --- | --- |
| Llama2 7B - B（budget，预算型） | 2 | 1 | [aws-neuron/Llama-2-7b-hf-neuron-budget](https://huggingface.co/aws-neuron/Llama-2-7b-hf-neuron-budget) |
| Llama2 7B - L（latency，延迟型） | 24 | 1 | [aws-neuron/Llama-2-7b-hf-neuron-latency](https://huggingface.co/aws-neuron/Llama-2-7b-hf-neuron-latency) |
| Llama2 7B - T（throughput，吞吐型） | 24 | 4 | [aws-neuron/Llama-2-7b-hf-neuron-throughput](https://huggingface.co/aws-neuron/Llama-2-7b-hf-neuron-throughput) |
| Llama2 13B - L（latency，延迟型） | 24 | 1 | [aws-neuron/Llama-2-13b-hf-neuron-latency](https://huggingface.co/aws-neuron/Llama-2-13b-hf-neuron-latency) |
| Llama2 13B - T（throughput，吞吐型） | 24 | 4 | [aws-neuron/Llama-2-13b-hf-neuron-throughput](https://huggingface.co/aws-neuron/Llama-2-13b-hf-neuron-throughput) |

*注：所有模型都以最大序列长度 2048 编译。*

`llama2 7B` 的“budget（预算型）”模型意在部署在只有一个 neuron 设备、且有足够 `cpu` 内存来加载模型的 `inf2.xlarge` 实例上。

所有其他模型都编译为充分利用 `inf2.48xlarge` 实例上可用的全部核心。

*注：有关可用实例的详情，请参阅 [inferentia2 产品页](https://aws.amazon.com/ec2/instance-types/inf2/)。*

我们为 `llama2 7B` 和 `llama2 13B` 模型创建了两个以“延迟（latency）”为导向的配置，它们一次只能服务一个请求，但以全速运行。

我们还创建了两个以“吞吐（throughput）”为导向的配置，以并行服务多达四个请求。

为评估模型，我们生成 token 直到总序列长度达到 1024，从 256 个输入 token 开始（也就是我们生成 256、512 和 768 个 token）。

*注：“budget（预算型）”模型的数据有报告，但为了可读性未纳入图表。*

### 编码时间

编码时间是处理输入 token 并生成第一个输出 token 所需的时间。这是一个非常重要的指标，因为它对应于用户在流式生成 token 时直接感知到的延迟。

我们测试随上下文尺寸增大的编码时间，256 个输入 token 大致对应典型的问答（Q/A）用法，而 768 则更典型于检索增强生成（RAG）用例。

“budget（预算型）”模型（`Llama2 7B-B`）部署在 `inf2.xlarge` 实例上，而其他模型部署在 `inf2.48xlarge` 实例上。

编码时间以**秒**表示。

| 输入 token | Llama2 7B-L | Llama2 7B-T | Llama2 13B-L | Llama2 13B-T | Llama2 7B-B |
| --- | --- | --- | --- | --- | --- |
| 256 | 0.5 | 0.9 | 0.6 | 1.8 | 0.3 |
| 512 | 0.7 | 1.6 | 1.1 | 3.0 | 0.4 |
| 768 | 1.1 | 3.3 | 1.7 | 5.2 | 0.5 |

[![Llama2 inferentia2 encoding-time](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/169_inferentia-llama2/encoding-time.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/169_inferentia-llama2/encoding-time.png)

我们可以看到，所有部署的模型都表现出出色的响应时间，即便是长上下文也是如此。

### 端到端延迟

端到端延迟对应于达到 1024 token 序列长度所需的总时间。

因此它包含编码和生成时间。

“budget（预算型）”模型（`Llama2 7B-B`）部署在 `inf2.xlarge` 实例上，而其他模型部署在 `inf2.48xlarge` 实例上。

延迟以**秒**表示。

| 新 token | Llama2 7B-L | Llama2 7B-T | Llama2 13B-L | Llama2 13B-T | Llama2 7B-B |
| --- | --- | --- | --- | --- | --- |
| 256 | 2.3 | 2.7 | 3.5 | 4.1 | 15.9 |
| 512 | 4.4 | 5.3 | 6.9 | 7.8 | 31.7 |
| 768 | 6.2 | 7.7 | 10.2 | 11.1 | 47.3 |

[![Llama2 inferentia2 end-to-end latency](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/169_inferentia-llama2/latency.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/169_inferentia-llama2/latency.png)

所有部署在高端实例上的模型都表现出良好的延迟，即使是那些实际配置为优化吞吐的模型。

“budget（预算型）”部署模型的延迟明显更高，但仍然可以接受。

### 吞吐量

我们采用与其他基准测试相同的约定来评估吞吐量，即用端到端延迟除以输入和输出 token 之和。换句话说，我们用端到端延迟除以 `batch_size * sequence_length` 以得到每秒生成的 token 数。

“budget（预算型）”模型（`Llama2 7B-B`）部署在 `inf2.xlarge` 实例上，而其他模型部署在 `inf2.48xlarge` 实例上。

吞吐量以 **token/秒** 表示。

| 新 token | Llama2 7B-L | Llama2 7B-T | Llama2 13B-L | Llama2 13B-T | Llama2 7B-B |
| --- | --- | --- | --- | --- | --- |
| 256 | 227 | 750 | 145 | 504 | 32 |
| 512 | 177 | 579 | 111 | 394 | 24 |
| 768 | 164 | 529 | 101 | 370 | 22 |

[![Llama2 inferentia2 throughput](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/169_inferentia-llama2/throughput.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/169_inferentia-llama2/throughput.png)

同样，部署在高端实例上的模型都有非常好的吞吐量，即使是那些为延迟优化的模型。

“budget（预算型）”模型的吞吐量要低得多，但考虑到一个普通读者大约每秒读 5 个词，它对流式用例而言仍然可以接受。

## 结论

我们演示了如何使用 🤗 [optimum-neuron](https://huggingface.co/docs/optimum-neuron/index)，从 [Hugging Face 中心](https://huggingface.co/models)将 `llama2` 模型轻松部署到 [AWS Inferentia2](https://aws.amazon.com/ec2/instance-types/inf2/) 上。

所部署的模型在编码时间、延迟和吞吐量方面都展现出非常好的性能。

有趣的是，所部署模型的延迟对 batch size 并不太敏感，这为它们在并行服务多个请求的推理端点上的部署开辟了道路。

不过仍有大量改进空间：

- 在当前实现中，提升吞吐量的唯一方式是增大 batch size，但它目前受限于设备内存。诸如流水线（pipelining）之类的其他方案正在集成之中，
- 静态序列长度限制了模型编码长上下文的能力。看看 attention sinks 是否可能是解决此问题的有效方案，将会很有意思。
