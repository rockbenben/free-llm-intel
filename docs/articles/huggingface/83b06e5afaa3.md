# Xet 上线 Hub

想跳过细节，直接体验更快的大文件上传下载？

[点击这里](https://huggingface.co/blog/xet-on-the-hub#ready-xet-go)阅读如何加入 Xet 等待名单（或[直接前往立即加入](https://huggingface.co/join/xet)）。

过去几周，Hugging Face 的 [Xet 团队](https://huggingface.co/xet-team)迈出了关键一步：[把第一批模型和数据集仓库从 LFS 迁移到了 Xet 存储](https://huggingface.co/posts/jsulz/911431940353906)。

这是[实现 Hugging Face 对 Hub 愿景](https://huggingface.co/blog/xethub-joins-hf)的诸多步骤之一——让 AI 构建者在超大规模模型和数据集上更高效地构建、迭代和协作。如果想更深入地了解技术本身，可以看看这些文章：

- [From Files to Chunks: Improving Hugging Face Storage Efficiency](https://huggingface.co/blog/from-files-to-chunks)
- [Rearchitecting Hugging Face Uploads and Downloads](https://huggingface.co/blog/rearchitecting-uploads-and-downloads)
- [From Chunks to Blocks: Accelerating Uploads and Downloads on the Hub](https://huggingface.co/blog/from-chunks-to-blocks)

但这篇不是讲核心技术，而是 Xet 上 Hub 的幕后故事——从概念验证一路讲到首批仓库迁移。

这次迁移把 Hub 约 6% 的下载流量切到了 Xet 基础设施上，验证了若干核心组件，并测试了与访问仓库的各种方式（本地开发环境、不同的库、CI 系统、云平台等）的集成。近两百万开发者在两百万多个公开仓库上工作——真实使用才是终极试炼场。工程化 Xet 存储这样复杂的系统是一种平衡艺术：你要为规模、性能和可靠性做规划，但字节真的开始流动之后，挑战才会浮现。诀窍在于知道什么时候该从设计和理论转入实战。

## Xet 的不同之处

[LFS](https://huggingface.co/docs/hub/en/repositories-getting-started#requirements)——当今仓库背后的存储系统——把大文件存在仓库外部的独立对象存储里。LFS 在文件级别去重：哪怕极小的编辑，也会产生一个需要完整上传的新版本；对 Hub 仓库里常见的那些多 GB 文件来说，这非常痛苦。

相比之下，Xet 存储用[内容定义分块（CDC）](https://huggingface.co/blog/from-files-to-chunks)在字节层面去重（约 64KB 的数据块）。如果你在 Parquet 文件里改一行，或调整 GGUF 模型里一小段元数据，网络上只传那些变化的块。

这为大文件传输带来巨大好处。举个例子，Xet 团队内部维护一个约 5 GB 的 SQLite 数据库，支撑一个指标看板。用 LFS 时，追加 1 MB（大约是目前平均每次更新的量）就得重传整个 5 GB 文件；用 Xet 存储，我们只推送新数据。

Comparison of two recent runs with the

dedupe_estimator

(a tool for estimating the chunk-level deduplication available between files). Red chunks indicate what needs to be uploaded when using Xet.

这意味着看板的上传只要十分之一秒（50Mb/s 下），而如果数据库放在 LFS 上要 13 分钟。

要让这一切运转，需要以下组件协同：

- Xet 感知的客户端——把数据切成约 64 KB 的块；本地对相同块去重，并把它们聚合成约 64 MB 的块再上传。
- Hugging Face Hub——接收客户端请求并路由到正确的仓库；提供认证和安全保证。
- 内容寻址存储（CAS）——对上传和下载强制执行基于块的去重；内置一个 LFS Bridge 服务旧的、非 Xet 的客户端，像传统 LFS 服务器一样工作，为下载提供单一 URL。
- Amazon S3——存储文件内容（[blocks](https://huggingface.co/blog/from-chunks-to-blocks#scaling-deduplication-with-aggregation)）和文件重建元数据（[shards](https://huggingface.co/blog/from-chunks-to-blocks#scaling-deduplication-with-aggregation)）；作为 CAS 引用的最终数据持久层。

## 迁移后的挑战

没有一次上线是不交学费的。系统平滑扛住了负载，迁移也没出大乱子，但随着字节流过各个组件，我们开始看到一些趋势。

### 块格式带来的下载开销

迁移后复查网络吞吐，我们发现 CAS 下载的数据量是它返回给客户端数据量的四倍：

黄色为下载量 (rx)，绿色为发送给客户端的量 (tx)。

进一步排查发现，绝大多数对 CAS 的请求是文件内 10MB 范围的数据。这些请求来自用 `hf_transfer` 加速大文件下载的用户。请求的范围并不对齐块边界，而块格式又没有提供未压缩的块长度信息，无法直接跳到块内目标数据。于是 CAS 只能从块头开始流式读取，一直读到找齐请求的数据为止。

假设块平均 60MB，且同一块内有多个部分范围的请求，开销就会累积：为交付 60MB，CAS 读了 210MB，下载与发送之比是 3.5:1。在规模下，面对大小不一的块和跨多个块的请求范围，4:1 的比例就出现了。

老话讲，一图胜千言：

红色块是被不必要流式传输的内容，绿色块是 CAS 真正请求并最终发送的数据。

为解决这个问题，我们更新了块格式，存入块长度元数据，让 CAS 每个请求只下载真正需要的部分。这次格式改动需要跨多个层面协同更新：

- CAS API
- 块元数据格式
- S3 上的 `2^16 + 1` 个块（我发誓纯属巧合）

全程零停机。改动后，CAS 下载与返回数据的比例恢复了平衡，GET 延迟也整体降低了约 35%。

下载与发送数据恢复平衡，各请求吞吐同步下降。

### Pod 负载不均

与此同时，我们还发现 CAS 集群出现意外的负载不均：某个 pod 的活跃上传数飙到几百，其他 pod 却只有一位数。把负载均衡器的[路由算法](https://docs.aws.amazon.com/elasticloadbalancing/latest/userguide/how-elastic-load-balancing-works.html#routing-algorithm)[从轮询换成最少未完成请求](https://medium.com/dazn-tech/aws-application-load-balancer-algorithms-765be2eca158)，再增加节点，当时都收效甚微。

深挖之后我们意识到：上传时，CAS 会先写一个临时文件做校验再上传，且不调用 `fsync`，这允许操作系统把写入缓冲在页缓存里。当一波上传洪峰到来，未刷盘的页缓存会造成内存压力升高。

操作系统试图把页缓存刷到磁盘时，pod 会因[块存储](https://aws.amazon.com/ebs/)的吞吐限流而出现上传延迟上升。上传处理变慢的同时，新请求源源不断进来，继续往磁盘堆。这形成恶性循环，导致上传积压，也就是迁移期间看到的负载不均：

Balanced view of downloaded and sent data with reduced throughput across the board.

为防止 pod 进入这种状态，我们给每台机器设置了并发上传上限，达到上限就拒绝新请求，把请求推给集群中其他 pod。如果整个集群的 pod 都进入该状态，自动伸缩策略就会介入。更长期的方案可能包括强制磁盘同步、去掉磁盘缓冲，或换成吞吐更好的临时存储。

### 迁移启示

这两个问题带来了重要的架构改进，但迁移后的几周里团队处理的挑战远不止这些。我们还修了其他性能问题、一个内存泄漏（已修复但仍无法定根因），并采纳 AWS 建议，把 LFS Bridge 从[应用负载均衡器](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html)（ALB）迁到[网络负载均衡器](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/introduction.html)（NLB），以改善流量突增时的可扩展性。

#### 经验教训

- **生产就是生产（There is nothing like PROD）**：任何测试环境都无法模拟真实规模下的用户行为。即使经过周密的集成工作、Hugging Face 成员测试基础设施数月之久，角落案例仍只有在真实用量涌入系统时才暴露。
- **迁移本身就是真实流量演练**：通过分阶段灰度迁移，在更多流量进入基础设施前先把问题挖出来，我们避免了停机与扰动。管理一小部分流量和存储，比起整个 Hub 从第一天就压在 Xet 上，要容易得多。
- **让学习复利**：基础设施和系统设计经过数周迭代被不断加固。未来在 Xet 上的每一次字节传输、每一个网络请求，都会受益于这些教训。

简言之，真实负载对暴露这些挑战至关重要，增量式迁移让我们能安全地逐个解决。我们正是以此确保 Xet 支撑的仓库能为整个 Hugging Face 社区可靠扩展——一路更快的上传、更少的瓶颈、最小的扰动。

## 各就各位。Xet。跑。

首批迁移完成后，Xet 正式上线 Hugging Face Hub。

![Xet speed](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/xet-on-the-hub/migration.gif)

我们正在敲定与 `huggingface_hub` 的正式集成——你将获得 Xet 的全部好处，而无需对现有工作流做任何重大改动。要开始：

- **加入等待名单**——用你的用户或组织账号（需有 admin/write 权限）在[这里报名](https://huggingface.co/join/xet)。一旦获批，你的新仓库会自动使用 Xet 存储。我们也会逐步迁移已有仓库，不错过更快的传输。
- **继续用你熟悉的工具**——`hf_xet` Python 包即将进入 `huggingface_hub`。如果你用 `transformers` 或 `datasets` 库，它们本身就在用 `huggingface_hub`，只需在同一环境安装 `hf_xet` 即可。安装步骤和文档在路上。大文件的下载上传命令一切照旧。
- **坐享其成**——上传下载少等待，大文件迭代更迅速。团队里每个人都应升级到 `hf_xet` 才能拿满收益，但旧客户端会通过 LFS Bridge 保持兼容。
