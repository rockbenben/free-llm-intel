[VAKRA 数据集](https://huggingface.co/datasets/ibm-research/VAKRA) | [排行榜](https://ibm-research-vakra.hf.space/) | [发布博客](https://www.ibm.com/new/announcements/introducing-vakra-benchmark) | [GitHub](https://github.com/IBM/vakra) | [提交到排行榜](https://github.com/IBM/vakra?tab=readme-ov-file#submitting-to-the-live-leaderboard)

我们最近发布了 **VAKRA**——一个基于工具、可执行的基准，用于评估 AI 智能体在企业级环境中推理和行动的能力。

不同于测试孤立技能的传统基准，VAKRA 度量的是**跨 API 与文档的组合推理**能力，用完整执行轨迹来评估智能体能否可靠完成多步工作流。

**VAKRA** 提供可执行环境，智能体在其中与 **8000 多个本地托管 API** 交互，这些 API 背后是覆盖 **62 个领域**的真实数据库，并配有领域对齐的文档集合。任务可能要求 **3-7 步的推理链**，把结构化的 API 交互与非结构化的检索结合起来，还要满足自然语言描述的工具使用约束。

如下所示，模型在 VAKRA 上表现很差——本文中我们补充了 VAKRA 任务的额外[数据集细节](https://huggingface.co/blog/ibm-research/vakra-benchmark-analysis#task-description)，并给出我们对不同任务上观察到的[故障模式分析](https://huggingface.co/blog/ibm-research/vakra-benchmark-analysis#evaluation-framework)。

## 任务描述

如下所示，**VAKRA** 基准由四个任务组成，各测试不同的一组*能力*。

#### 能力 1：使用商业智能 API 的 API 链式调用

这一能力包含 54 个领域的 2,077 个测试实例，要求使用 SLOT-BIRD 和 SEL-BIRD 工具集合中的工具（[Elder et al., 2026](https://arxiv.org/pdf/2506.11266)）。与 Elder et al. 的设置相比，SLOT-BIRD 和 SEL-BIRD 的工具宇宙通过纳入更多领域得到了扩展。每个领域限定使用一个工具集合，任务需要串联 1-12 次工具调用才能得出最终答案。

```
{
  "query": "Which football team has a build-up play speed of 31, build-up plan dribbling of 53, and build-up play passing of 32?",
  "tool_calls":[
      {
        "name": "get_data",
        "arguments":{"tool_universe_id="486ea46224d1-aeb8037c5e78"},
        "label": "retrieved_data_1"
      },
      {
        "name": "select_data_equal_to",
        "arguments":{"data_label":"retrieved_data_1","key_name":"play_speed","value":31},
        "label": "FILTERED_DF_0"
      },
      {
        "name": "select_data_equal_to",
        "arguments":{"data_label":"FILTERED_DF_0","key_name":"play_dribble","value":53},
        "label": "FILTERED_DF_1"
      },
      {
        "name": "select_data_equal_to",
        "arguments":{"data_label":"FILTERED_DF_1","key_name":"play_passing","value":32},
        "label": "FILTERED_DF_2"
      },
      {"name":{get_team_name},"arguments":{"data_label":"FILTERED_DF_2","n":1}}}],
  "answer": "FC Barcelona"
}
```

图 2：SEL-BIRD 集合的数据样例

如上所示，每个实例都关联一个 JSON 数据源，答案必须从中推导。支持该任务的 MCP 服务器包含一个特殊工具 `get_data(tool_universe_id=id)`，必须在每个实例开始时调用。该工具初始化数据源，返回数据的轻量预览（见下方图 3），并把完整数据集存到服务端以避免大体积传输，从而避免通过 MCP 协议低效地传大数据。这次调用还会配置 MCP 服务器，让它依据 `tool_universe_id` 暴露相应的工具集，并把数据源与该实例的领域专属数据库对齐。

SLOT-BIRD 集合提供一套全局的 7 个工具，用于通用数据操作（如过滤、排序），灵感来自 [Tableau](https://help.tableau.com/current/api/rest_api/en-us/REST/rest_api_concepts_filtering_and_sorting.htm) 和 [Google Analytics](https://developers.google.com/analytics/devguides/reporting/data/v1/rest/v1beta/FilterExpression) 这类系统。SEL-BIRD 集合在此基础上引入更专门化的工具：有些与 SLOT-BIRD 共享，另一些是把类别参数摊平成独立函数得到的（例如 `sort_data` 带参数 ascending: `bool = False`，被拆成 `sort_data_ascending` 和 `sort_data_descending`）。此外，SLOT-BIRD 里的通用函数（`retrieve_data`）被替换为查询专属的 getter。给定实例数据的每个键都有对应的 get 函数（`get_KEY_NAME`），平均每个实例有 4 个 get 函数。

```
{
  "handle": "retrieved_data_1",
  "num_records": 2,
  "key_details": [
    {"name": "team_name", "dtype": "str", "first_3_values": ["FC Barcelona", "Manchester City"]},
    {"name": "play_speed", "dtype": "int32", "first_3_values": [31, 40]},
    {"name": "play_dribble", "dtype": "int32", "first_3_values": [53, 30]},
    {"name": "play_passing", "dtype": "int32", "first_3_values": [32, 16]}
  ]}
```

图 3：`get_data` 函数返回的数据预览

#### 能力 2：使用仪表盘 API 的工具选择

这一能力包含 17 个领域的 1,597 个实例，要求使用扩展后的 REST-BIRD 集合中的工具（[Elder et al.](https://arxiv.org/pdf/2506.11266)）。这些工具采用端点式接口，提供与查询高度对齐、把大部分计算封装在内部的专门端点。它们以 REST API 形式运行在 FastAPI 服务器上，外面包一层 MCP 服务器。该任务要求从领域专属工具集中选对 API（见[图 1](https://huggingface.co/blog/ibm-research/vakra-benchmark-analysis/#task-description)中的示例）。每个领域最少 6 个、最多 328 个工具（平均 116 个）。与上一个任务类似，`get_data` 工具会配置 MCP 服务器，使其只暴露相关的领域专属 API。

OpenAI API 规范限制工具列表输入最多 128 个工具。这个限制要求使用该 API 的智能体构建者通过筛选（shortlisting）机制直接管理工具列表长度。我们仓库中的基线智能体用一个简单的[筛选能力](https://github.com/IBM/vakra/blob/main/agents/components/tool_shortlister.py)应对这一挑战。

#### 能力 3：使用仪表盘 API 的多跳推理

基准的能力 3 部分有 869 个测试实例，取自 38 个主题领域。这些实例同样依赖 REST-BIRD API 集合，但在此之上加入了多跳推理挑战（参见[图 1](https://huggingface.co/blog/ibm-research/vakra-benchmark-analysis/#task-description)示例）。多跳问题需要抽取并组合多条支撑证据才能得出答案。本部分实例回答一个查询需要 1 到 5 个逻辑跳。测试数据集内问题类型分布如下图 4 所示。

#### 能力 4：多跳、多源推理与策略遵从

能力 4 包含 41 个领域的 644 个实例，同样基于 REST-BIRD API 构建。上面的图 4 展示了无策略的测试查询的混合跳分布。它包含最复杂的查询，具有下列特征：

**多源（Multi-Source）**：这部分为每个领域增加了文档索引。本能力的查询可能同时需要这些文档索引和 API 调用的信息。与能力 3 类似，该任务也包含多跳查询。信息来源要求在"每一跳"层面生效，例如一个问题可能包含三跳，来源依次是：API - RAG（文档检索）- API。为保证推理正确，数据生成时对各来源做了去污染，即某一跳所需的信息只存在于一个来源中。例如，若某一跳要用 API 回答，构建文档索引时就会剔除可能包含答案信息的文档。

**多轮（Multi-Turn）**：这部分数据还加入了多轮对话。每个实例是一场多轮对话。数据以"上下文-回复"对的形式发布，上下文编码当前对话历史，智能体只负责回答当前轮次。

**工具使用策略**：这些实例的一部分附带了智能体必须遵守的工具使用策略。策略以纯文本指令形式描述智能体允许访问哪些知识来源、在什么条件下访问。例如：

```
If a user's query pertains to Technology & Software, which is/are about Topics focusing on codebases,
software platforms, applications, and user interactions in tech, make sure you try answering them by
only using document retrievers. Do not use other types of tools.
```

项目仓库里的基线智能体通过在提示词中简单追加一句来强制遵守策略：`"You are a helpful assistant with access to tools.\n Tool Usage Constraint: {additional_instructions}."`。当然，智能体构建者可以自由选择任何约束执行机制。

## 评估框架

VAKRA 在工具环境中评估智能体，成功既取决于执行连贯多步工作流的能力，也取决于答案的正确性。我们引入了一个**以执行为中心的评估框架**，不仅评估最终输出，还评估完整的工具执行轨迹，包括工具调用、输入和中间结果。

#### 评估指标

[VAKRA Evaluator](https://github.com/IBM/vakra/tree/main/evaluator) 对每个样本使用两类关键输入：**预测的最终回复**和对应的**工具调用轨迹**。预测轨迹中的工具调用会在与真值相同的环境中执行，以校验中间工具输出。

评估遵循**瀑布式管道**（图 6），后面的阶段以前面的成功为条件：

- 对能力 4 的任务，先以程序化方式校验**策略遵从**（此步骤不适用于其他能力）。
- 然后把**预测的工具调用序列**与真值序列比较。
- 只有**轨迹有效**的样本才进入最终回复评估。

图 6：瀑布式评估管道

![](https://cdn-uploads.huggingface.co/production/uploads/677629b4931b3b2eb8d5820a/LP13FH1OviGtRUGs6OSqF.png)

**工具序列比较** 由于存在可执行环境，智能体可以探索环境，有时会用与我们识别出的 API 不同的一组 API 返回答案。为了支持不同但合法的工具调用与推理路径，正确性的判定方式是执行每个预测的工具，并把工具响应集合与真值的响应集合比对（而不是强制逐步骤严格匹配）。

具体来说，我们先做程序化检查：验证真值工具响应中包含的全部信息是否都被预测工具响应恢复出来。这种检查在部分匹配、语义等价或表示差异（如顺序、聚合、格式）的情况下可能无法定论。这时我们采用第二级**基于 LLM 的评估**——改编自 CRAG 框架 [Yang et al., 2024](https://arxiv.org/html/2406.04744v1)——判定预测轨迹是否在结构不同的情况下仍取回了所有必需信息。这一步使用改自 [CRAG 的 prompt 模板](https://github.com/facebookresearch/CRAG/blob/main/prompts/templates.py)。

**最终回复评估** 对通过前面检查的轨迹，用基于 LLM 的评审来评估最终回复。这一步确保回复 (i) **锚定在预测的工具输出上**，并且 (ii) **与真值答案事实一致**，同时考虑措辞或结构上的可能差异。

这一设计保证智能体不仅因给出正确答案获得奖励，还因为通过有效且完整的推理过程得到答案而获得认可。

**评分**

四个能力等权重，得到最终排行榜得分：

Leaderboard_Score = (1/4) Σ_{n=1}^{4} Capability_n

能力 1-3 内部，每个样本等权重：

Capability_{1-3} = (# correct queries) / (# total queries)

对能力 4，异构查询权重更高：

Capability_4 = (# correct multi-source × 2 + # correct API-only or RAG-only) / (# total multi-source × 2 + # total API-only or RAG-only)

## 错误分析

接下来给出对 VAKRA 四个能力的详细错误分析。为便于分析，我们采用**按阶段归类错误**的方式，把每次失败归到第一个出问题的点。具体按顺序评估：(i) 是否选对了工具；(ii) 是否提供了所需参数，无遗漏也无幻觉；(iii) 参数值是否正确；(iv) 最终回复是否既准确又扎根于工具输出。

#### 故障阶段隔离

由于单个样本可能在不同步骤上出现多种错误，我们把每个实例顺序归类到最早失败的阶段（例如工具选择错误优先于参数错误）。这样避免重复计数，使各错误类别可以解读为数据集中互斥的比例。虽然可以做更细的指标（如工具使用的精确率/召回率）（Elder et al., 2026），但我们发现这种形式提供了简单、可解释的智能体失败拆解。

[![bi_apis_error_plot](https://cdn-uploads.huggingface.co/production/uploads/677629b4931b3b2eb8d5820a/cTXZ1LmNP-tkPIe5ghj_t.png)](https://cdn-uploads.huggingface.co/production/uploads/677629b4931b3b2eb8d5820a/cTXZ1LmNP-tkPIe5ghj_t.png)

基准这一部分的实例需要为单个任务选择并排列多个工具，本能力共 2077 个样本。这对所有模型都很难，但 GPT-OSS-120B 在这一段表现最好。

- **GPT-OSS-120B** 大幅领先其他模型，主要得益于对工具 schema 更好的理解。
- 这部分的工具参数量很大，其中不少是可选参数；与其他模型相比，GPT-OSS-120B 在选对要填哪些参数上尤其稳健。
- 总体而言，在这部分基准里，把所有工具调用正确执行之后再综合出正确答案反而不太难——很可能是因为工具调用需要排序，使得工具选择问题不像[仪表盘 API 能力](https://huggingface.co/blog/ibm-research/vakra-benchmark-analysis#analysis-figure)那样可以靠猜蒙对。

图 7：SEL-BIRD 与 SLOT-BIRD 错误类型分析

[![sel_vs_slot_error_plot_v2](https://cdn-uploads.huggingface.co/production/uploads/677629b4931b3b2eb8d5820a/Ckd7lRTEYbTM9gVXUvwDI.png)](https://cdn-uploads.huggingface.co/production/uploads/677629b4931b3b2eb8d5820a/Ckd7lRTEYbTM9gVXUvwDI.png)

商业智能（BI）API 能力包含来自 SLOT-BIRD 和 SEL-BIRD 工具集合的两套 API。基准中 SEL 部分有 600 个样本，SLOT 部分有 1477 个样本。两个集合归在 BI API 能力下，但特性略有不同。SLOT-BIRD 的通用工具数量较少，但要填大量参数值；SEL-BIRD 工具集更大、每个工具的参数更少。模型在这两个工具集合上的相对错误恰好体现了这种侧重。

- 使用 SLOT-BIRD 时，除 GPT-OSS-120b 外所有模型在正确生成工具参数名上都犯了大量错误。这基本就是 GPT-OSS-120b 在本段基准整体表现出色的原因。
- 由于要填的参数变少，同样的模型在用 SEL-BIRD 工具集合时几乎不犯这类错误，但在选对工具上错误多得多——反映了从更大（且动态）工具集中做选择的难度上升。

- 如上所示，在工具选择能力的 1597 个样本中，Gemini-3-flash-preview 在所有错误类别上都优于其他被测模型。
- 如预期，由于仪表盘 API 实例要求模型从大量工具选项中选择，而每个工具只需少量参数，错误大量集中在工具选择和参数值选择上。
- 幻觉或漏填必需参数的问题似乎不大。然而，即便所有工具调用都正确，模型（尤其是 Gemini-3-flash-preview 和 Claude-Sonnet-4-5）仍难以从工具响应中综合出正确答案——图表最右侧的大幅掉量证明了这一点。

#### 多跳推理：跳数深度对模型表现的影响

图 8：按跳数深度对比各模型准确率

[![multihop_hop_depth_acc](https://cdn-uploads.huggingface.co/production/uploads/677629b4931b3b2eb8d5820a/JGR1iJ0DgZulV_gQ4Wx-Z.png)](https://cdn-uploads.huggingface.co/production/uploads/677629b4931b3b2eb8d5820a/JGR1iJ0DgZulV_gQ4Wx-Z.png)

多跳推理把原任务难度抬高了一层：模型要成功回答多个隐式耦合的小问题，每一问都要选对并调对 API。如预期，所有模型在只有一个逻辑跳的问题上表现最好，2 跳时出现下滑，3+ 跳时再度下滑。

#### 多跳多源推理：混合跳对模型表现的影响

图 9：按交互类型（API、文档检索器、混合）的模型准确率

[![question_type_acc](https://cdn-uploads.huggingface.co/production/uploads/677629b4931b3b2eb8d5820a/d8Cqz2tApdRe6ePcaZbYf.png)](https://cdn-uploads.huggingface.co/production/uploads/677629b4931b3b2eb8d5820a/d8Cqz2tApdRe6ePcaZbYf.png)

数据集最后一部分在其他部分已有的工具/API 来源之外加入了文档来源。于是实例可能要求：单次或多次 API 调用、单次或多次文档检索，或两者的组合。

- 和之前一样，只需一次 API 调用（1-hop API）的实例与需要多次 API 调用（2-hop API）的实例表现差异明显；加入文档检索器会让任务更有挑战（RAG Hops 和 Hybrid）。
- 有趣的是，我们发现对于只需一次文档检索器调用（1-hop RAG）的问题，GPT-OSS-120B 会试图直接从参数化知识给出答案；而当问题*看起来*需要多跳时，它反倒会老老实实去调工具。我们猜测：1-hop RAG 的问题非常围绕维基百科式实体，模型因此跳过了工具调用（在 1-hop API 上看不到这个问题，因为那类问题里往往会出现后端数据库特有的实体/事实）。
- 同样有趣的是，Gemini-3-flash-preview 在 2-hop API-RAG 上的表现比其他混合跳模式高出一截。这很可能与它在仪表盘 API（工具选择能力）上的相对强表现有关——一旦通过工具调用确定了正确的中间答案，检索查询就更可能成功。

#### 策略对模型表现的影响

图 10：按策略类型的模型准确率

[![policy_acc](https://cdn-uploads.huggingface.co/production/uploads/677629b4931b3b2eb8d5820a/P5L7b-vzkQKYqO63EHccb.png)](https://cdn-uploads.huggingface.co/production/uploads/677629b4931b3b2eb8d5820a/P5L7b-vzkQKYqO63EHccb.png)

策略在多跳、多源推理之上又加了一层难度。当策略与回答所需的信息来源一致、即不影响模型回答所需的工具列表时，我们称之为"不改变答案（No Updates to Answer）"。如图 10 所示，除 Granite-4.0-h-Small-32B 外，所有模型在"策略改变了答案"（即限制访问最相关信息源）的约束下性能都明显下降。

总体上我们发现，模型要么违反约束、要么取不到足够信息——有时它们理解了策略却无法正确回答问题，有时则表现出前面分析过的某种故障模式。

概言之，受工具使用策略约束的设定表明：模型虽然能对工具和来源进行推理，却难以把外部约束纳入推理——而这恰恰是真实世界可靠部署的关键要求之一。

## 结论

VAKRA 暴露了一个关键缺口：表面的工具能力与端到端的智能体可靠性相去甚远。尽管现代模型越来越会选 API、能执行孤立的工具调用，VAKRA 表明这些能力本身不足以支撑真实部署。实践中，模型在执行约束下进行组合推理——横跨 API、文档、对话上下文和策略要求——时常常崩溃。
