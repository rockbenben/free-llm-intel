# 在 modern CPU 上扩展 BERT 类模型推理（第 1 部分）

作者：Morgan Funtowicz（mfuntowicz）

## 1. 背景与动机

早在 2019 年 10 月，我的同事 Lysandre Debut 发布了一篇全面的（*在当时而言*）[推理性能基准测试博客 (1)](https://medium.com/huggingface/benchmarking-transformers-pytorch-and-tensorflow-e2917fb891c2)。

自那以后，[🤗 transformers (2)](https://github.com/huggingface/transformers) 迎来了大量新架构，[🤗 hub (3)](https://huggingface.co/models) 上也新增了数千个模型，截至 2021 年第一季度已超过 9,000 个。

随着 NLP 领域在生产中越来越多地采用 BERT 类模型，如何高效部署并大规模运行这些架构依然充满挑战。这正是我们最近推出 [🤗 Inference API](https://api-inference.huggingface.co/docs/python/html/index.html) 的原因：让你专注于为用户和客户创造价值，而不必深究运行这类模型的所有高度技术化的细节。

本博客是一系列文章的第一篇，将涵盖更好地利用 CPU 跑 BERT 模型推理的大部分硬件和软件优化。

作为这个系列的首篇，我们将讲硬件部分：

- 设置基线 - 开箱即用的结果
- 在 CPU 密集型任务中使用现代 CPU 时的实用与技术考量
- 核数扩展 - 增加核心数真的能带来更好性能吗？
- 批大小扩展 - 用多个并行且独立的模型实例提升吞吐

我们决定以最著名的 Transformer 架构 [BERT (Devlin & al. 2018) (4)](https://arxiv.org/abs/1810.04805v1) 为主线。虽然为了控制篇幅本文只聚焦 BERT 类模型，但所描述的所有技术都可以应用到 Hugging Face 模型仓库上的任何架构。本文不打算详细讲解 Transformer 架构——想了解的话，我强烈推荐 Jay Alammar 的 [Illustrated Transformer 博客 (5)](https://jalammar.github.io/illustrated-transformer/)。

今天的目标是让你了解：从开源视角看，我们在 PyTorch 和 TensorFlow 上用 BERT 类模型做推理处于什么水平，以及你可以轻松利用哪些手段来加速推理。

## 2. 基准测试方法论

当涉及到从 Hugging Face 模型仓库使用 BERT 类模型时，有很多可以调节的"旋钮"让事情更快。
此外，为了量化"更快"意味着什么，我们依赖一些广泛采用的指标：

- **延迟（Latency）**：单次模型执行（即一次 forward 调用）所花的时间
- **吞吐（Throughput）**：在固定时间内完成的执行次数

这两个指标将帮助我们在本文中理解各种收益与权衡。

基准测试方法论是从零重新实现的，以便集成 transformers 的最新特性，也让社区能以**更简便的方式**运行和分享基准结果。整个框架现在基于 [Facebook AI & Research 的 Hydra 配置库](https://hydra.cc/)，使我们能在运行基准时轻松报告和跟踪所有涉及的项目，从而提升整体可复现性。项目的完整结构在[这里](https://github.com/huggingface/tune)。

在 2021 版中，我们保留了像上一篇博客 [(1)](https://medium.com/huggingface/benchmarking-transformers-pytorch-and-tensorflow-e2917fb891c2) 那样通过 PyTorch 和 TensorFlow 运行推理负载的能力，也包括它们的 traced 对应版本 [TorchScript (6)](https://pytorch.org/docs/stable/jit.html) 和 [Google Accelerated Linear Algebra (XLA) (7)](https://www.tensorflow.org/xla)。同时，我们决定加入对 [ONNX Runtime (8)](https://www.onnxruntime.ai/) 的支持，因为它提供了许多专门针对 transformers 模型的优化，是讨论性能时绕不开的强候选。

最后同样重要的是，这个新的统一基准环境将让我们能轻松为不同场景跑推理，例如 [Quantized Models (Zafrir & al.) (9)](https://arxiv.org/abs/1910.06188)，使用精度更低的数值表示（`float16`、`int8`、`int4`）。这种被称为**量化**的方法已被所有主要硬件厂商广泛采用。在不久的将来，我们希望集成 Hugging Face 正在积极研发的额外方法，即蒸馏（Distillation）、剪枝（Pruning）和稀疏化（Sparsification）。

## 3. 基线

以下所有结果都运行在 [Amazon Web Services (AWS) c5.metal 实例](https://aws.amazon.com/ec2/instance-types/c5)上，使用 Intel Xeon Platinum 8275 CPU（48 核/96 线程）。选择该实例是因为它提供了所有有助于加速深度学习负载的 CPU 特性：

- AVX512 指令集（*各框架不一定能开箱即用地产出利用*）
- Intel Deep Learning Boost（也叫 Vector Neural Network Instruction - VNNI），为运行量化网络（*使用 int8 数据类型*）提供专用 CPU 指令

选择 *metal* 实例是为了避免使用云厂商时可能出现的任何虚拟化问题。这让我们对硬件拥有完全控制权，尤其是针对 NUMA（Non-Unified Memory Architecture）控制器时——后文会讲到。

*操作系统为 Ubuntu 20.04 (LTS)，所有实验基于 Hugging Face transformers 4.5.0、PyTorch 1.8.1 和 Google TensorFlow 2.4.0 完成*

## 5. 扩展 BERT 推理以提升现代 CPU 上的整体吞吐

### 5.1. 引言

改善 BERT 推理这类任务的延迟和吞吐有多种方式。优化和调参可以在多个层面进行：从启用操作系统特性、替换为性能更好的依赖库、仔细调整框架属性，到最后一条——利用并行化逻辑把 CPU 的所有核心都用起来。

本文余下部分聚焦最后一种，即所谓的 **Multiple Inference Stream（多推理流）**。

思路很简单：**分配同一模型的多个实例**，并把每个实例的执行绑定到 **CPU 核心一个专属、互不重叠的子集**上，从而获得真正并行的实例。

### 5.2. 现代 CPU 上的核心与线程

在优化 CPU 推理、更好利用 CPU 核心的路上，你可能已经见过——*至少过去 20 年一直如此*——现代 CPU 规格表里的 "cores" 与 "hardware threads"，或 "physical" 与 "logical" 数字。这些概念对应的机制叫 **同步多线程（Simultaneous Multi-Threading，SMT）**，在 Intel 平台上称为 **超线程（Hyper-Threading）**。

举例说明：设想两个任务 **A** 和 **B**，各自在自己的软件线程上并行执行。在某个时刻，这两个任务很可能要等待某些资源从主存、SSD、HDD 甚至网络中取回。如果这些线程被调度到不同的物理核心上且没有超线程，那么在这些等待期间，执行任务的核处于 **Idle** 状态干等资源到达，实际上什么也没干……也就没有被充分利用。

而有了 **SMT**，**任务 A 和 B 的两个软件线程**可以被调度到**同一个物理核心**上，使它们在该物理核心上交错执行：

任务 A 和任务 B 在物理核心上同时执行，当一个任务停顿等待时，另一个任务仍可在该核心上继续执行，从而提升核心的利用率。

图 3. Intel 超线程技术（SMT）示意

上面的图 3 简化了情形，假设的是单核设置。如果想了解 SMT 在多核 CPU 上如何工作、要看更深入的技术解释，请参考这两篇文章：

- [Intel® Hyper-Threading Technology - Technical User Guide (12)](http://www.cslab.ece.ntua.gr/courses/advcomparch/2007/material/readings/Intel%20Hyper-Threading%20Technology.pdf)
- [Introduction to Hyper-Threading Technology (13)](https://software.intel.com/content/www/us/en/develop/articles/introduction-to-hyper-threading-technology.html)

回到我们的模型推理负载……你想一下，在一个完全优化的理想世界里，计算占据了大部分时间。在这种场景下，使用逻辑核心不会带来任何性能收益，因为两个逻辑核心（硬件线程）要竞争该核心的执行资源。因此，对于以通用矩阵乘法为主的任务（*[gemm (14)](https://en.wikipedia.org/wiki/Basic_Linear_Algebra_Subprograms#Level_3)*），它们天生就是 CPU 密集型的，**不会从 SMT 获益**。

### 5.3. 利用多路服务器与 CPU 亲和性

如今的服务器提供大量核心，有些还支持多路（multi-socket）配置（*即主板上有多颗 CPU*）。
在 Linux 上，`lscpu` 命令会报告系统上所有 CPU 的规格和拓扑：

```

```

在我们的例子里，这台机器有 **2 个 socket**，每个 socket 提供 **24 个物理核心**、每核 **2 个线程**（SMT）。
另一个值得关注的概念是 **NUMA** 节点（0、1），它描述了核心与内存在系统上的映射方式。

非一致性内存访问（**NUMA**）与一致性内存访问（**UMA**）相反：UMA 下全部内存池由所有核心通过 socket 与主存之间单一统一的总线访问；而 **NUMA** 把内存池拆分，每颗 CPU socket 负责寻址一部分内存，从而缓解总线拥堵。

图 5. UMA 与 NUMA 架构差异示意

（来源 (15)）

要充分发挥这样一台性能强悍的机器的潜力，我们必须确保模型实例被正确地分发到所有 socket 的**物理**核心上，同时强制内存分配"NUMA 感知"。

在 Linux 上，可以通过 [`numactl`](https://linux.die.net/man/8/numactl) 调整 NUMA 的进程配置。它提供了把进程绑定到一组 CPU 核心的接口（称为 **Thread Affinity，线程亲和性**）。
它还能调整内存分配策略，确保为进程分配的内存尽可能靠近这些核心所在的内存池（称为 **显式内存分配指令**）。

*注意：同时设置核心亲和性和内存亲和性很重要。如果在 socket 0 上计算、内存却分配在 socket 1，系统就得跨 socket 共享总线交换内存，带来不必要的开销。*

### 5.4. 调整线程亲和性与内存分配策略

现在我们已经掌握了控制模型实例资源分配所需的全部"旋钮"，接下来看看如何实际部署它们，以及对延迟和吞吐的影响。我们循序渐进，体会每条命令和参数各自的影响。

首先，不做任何调优直接启动推理模型，观察计算是如何分发到 CPU 核心上的（*左图*）。

```
python3 src/main.py model=bert-base-cased backend.name=pytorch batch_size=1 sequence_length=128
```

然后用 `numactl` 指定核心和内存亲和性，使用全部 **物理**核心、每个核心只用一个线程（线程 0）（*右图*）：

```
numactl -C 0-47 -m 0,1 python3 src/main.py model=bert-base-cased backend.name=pytorch batch_size=1 sequence_length=128
```

图 6. Linux htop 命令对比：设置线程亲和性之前与之后

可以看到，不做任何调优时，PyTorch 和 TensorFlow 把工作分发在单个 socket 上，占用该 socket 的全部逻辑核心（24 个核的双线程）。
另外，正如前面强调的，我们的场景不想利用 **SMT** 特性，所以把进程的线程亲和性设为每个物理核只针对 1 个硬件线程。

*注意，这是本次运行的具体情况，因环境而异。因此建议针对每个具体用例检查线程亲和性设置。*

在这里花点时间说明我们用 `numactl` 做了什么：

- `-C 0-47`：告诉 `numactl` 线程亲和性范围（核心 0 到 47）。
- `-m 0,1`：告诉 `numactl` 在两个 CPU socket 上都分配内存。

如果你好奇为什么把进程绑定到核心 [0...47]，需要回看 `lscpu` 的输出。其中有 `NUMA node0` 和 `NUMA node1` 部分，格式为 `NUMA node<X> <logical ids>`。

在我们的例子中，每个 socket 是一个 NUMA 节点，共 2 个 NUMA 节点。每个 socket（每个 NUMA 节点）有 24 个物理核心，每核 2 个硬件线程，即 48 个逻辑核心。对 NUMA node 0，0-23 是硬件线程 0，24-47 是 socket 0 上 24 个物理核的硬件线程 1。同理，对 NUMA node 1，48-71 是硬件线程 0，72-95 是 socket 1 上 24 个物理核的硬件线程 1。

由于如前所述我们每个物理核只针对 1 个线程，所以每个核只选线程 0，即逻辑处理器 0-47。既然我们两个 socket 都用，内存分配也要相应绑定（0,1）。

*请注意，同时使用两个 socket 未必总是最优，尤其对问题规模较小时。跨 socket 通信开销可能抵消甚至反转使用两个 socket 全部算力带来的收益。*

## 6. 核数扩展 - 更多核心真的能提升性能吗？

思考如何提升模型推理性能时，最直觉的方案可能是"砸更多资源干同样的活"。
在本系列的其余部分，我们会把这种方式称为 **Core Count Scaling（核数扩展）**，即只改变完成任务所用的系统核心数量。这在 HPC 领域也常称为强扩展（Strong Scaling）。

此时你可能会问：既然追求最低延迟，为什么不把全部马力都砸上去，而只分配一部分核心？

确实，取决于问题规模，投入更多资源可能效果更好；也可能对小问题来说，更多的 CPU 核心并不能改善最终延迟。

为了说明这一点，下图 6 取了不同的问题规模（`batch_size = 1, sequence length = {32, 128, 512}`），报告了 PyTorch 和 TensorFlow 在不同计算核心数下的延迟。

限制参与计算的资源数量，是通过限制 **intra** 操作内部的计算核心数实现的（***intra** 指算子（也称 "kernel"）内部的计算*）。

可通过以下 API 实现：

- PyTorch：`torch.set_num_threads(x)`
- TensorFlow：`tf.config.threading.set_intra_op_parallelism_threads(x)`

图 7. 延迟测量

可以看到，取决于问题规模，参与计算的线程数对延迟测量有正面影响。

对小规模和中等规模问题，只用一个 socket 性能最好。对大规模问题，跨 socket 通信开销被计算成本摊薄，因此能受益于两个 socket 的全部核心。

## 7. 多流推理 - 并行运行多个实例

如果你读到这里，应该已经具备在 CPU 上搭建并行推理负载的能力了。
接下来，我们将展示手中强大硬件提供的一些可能性，通过调节前面描述的"旋钮"，让推理尽可能线性扩展。

下一节我们将探索另一种扩展方案 **Batch Size Scaling（批大小扩展）**。但在那之前，先看看如何利用 Linux 工具分配线程亲和性，实现真正的模型实例并行。

核数扩展是往任务里加更多核心，而现在的做法是：加更多模型实例。每个实例在硬件资源的一个子集上独立运行，真正并行地各占一部分 CPU 核心。

### 7.1. 如何分配多个独立实例

先从简单的开始：如果要启动 2 个实例，每个 socket 上一个、各分配 24 核：

```
numactl -C 0-23 -m 0 python3 src/main.py model=bert-base-cased batch_size=1 sequence_length=128 backend.name=pytorch backend.num_threads=24
numactl -C 24-47 -m 1 python3 src/main.py model=bert-base-cased batch_size=1 sequence_length=128 backend.name=pytorch backend.num_threads=24
```

从这里开始，每个实例与另一个互不共享资源，从硬件角度看一切都在以最高效率运行。
延迟测量与单实例达到的一致，但吞吐实际上是 2 倍，因为两个实例是真正并行工作的。

我们可以进一步增加实例数量，同时降低每个实例分配的核心数。
运行 4 个独立实例，每个实际绑定 12 个 CPU 核心。

```
numactl -C 0-11 -m 0 python3 src/main.py model=bert-base-cased batch_size=1 sequence_length=128 backend.name=pytorch backend.num_threads=12
numactl -C 12-23 -m 0 python3 src/main.py model=bert-base-cased batch_size=1 sequence_length=128 backend.name=pytorch backend.num_threads=12
numactl -C 24-35 -m 1 python3 src/main.py model=bert-base-cased batch_size=1 sequence_length=128 backend.name=pytorch backend.num_threads=12
numactl -C 36-47 -m 1 python3 src/main.py model=bert-base-cased batch_size=1 sequence_length=128 backend.name=pytorch backend.num_threads=12
```

结论不变：我们的 4 个实例真正并行运行。
延迟会比上一个例子（核心数少一半）略高，但吞吐又会翻倍。

### 7.2. 智能分发 - 为不同问题规模分配不同模型实例

这种配置的另一个可能性是：为各种问题规模精心配置多个实例。
配合智能分发机制，可以把进来的请求重定向到对应配置，针对不同请求负载获得最佳延迟。

```
# Small-sized problems (sequence length <= 32) use only 8 cores (on socket 0 - 8/24 cores used)
numactl -C 0-7 -m 0 python3 src/main.py model=bert-base-cased batch_size=1 sequence_length=32 backend.name=pytorch backend.num_threads=8

# Medium-sized problems (32 > sequence <= 384) use remaining 16 cores (on socket 0 - (8+16)/24 cores used)
numactl -C 8-23 -m 0 python3 src/main.py model=bert-base-cased batch_size=1 sequence_length=128 backend.name=pytorch backend.num_threads=16

# Large sized problems (sequence >= 384) use the entire CPU (on socket 1 - 24/24 cores used)
numactl -C 24-37 -m 1 python3 src/main.py model=bert-base-cased batch_size=1 sequence_length=384 backend.name=pytorch backend.num_threads=24
```

## 8. 批大小扩展 - 用多个并行独立模型实例提升吞吐和延迟

扩展推理的另一个非常有趣的方向是：在增加模型实例数量的同时，成比例减少每个实例实际接收的负载。

这种方法同时改变了问题规模（*批大小*）和参与计算的资源（*核心数*）。

举例：假设你有一台 `C` 核的服务器，想跑一个包含 B 个样本、每个 S 个 token 的负载。
可以把这个负载表示为形状 `[B, S]` 的张量，B 是批大小，S 是 B 个样本中的最大序列长度。

对所有实例（`N` 个），每个实例运行在 `C / N` 个核心上，接收任务的一个子集 `[B / N, S]`。

每个实例收到的不是全局批，而是它的一个子集 `[B / N, S]`，因此得名 **Batch Size Scaling（批大小扩展）**。
为了突出这种扩展方法的收益，下面的图表既展示了随模型实例扩展的延迟，也展示了对吞吐的影响。

看结果时，聚焦延迟和吞吐两个方面：

一方面，我们取实例池中所有实例的最大延迟，来反映处理完整个批样本所需的时间。换句话说，由于实例是真正并行的，收齐所有实例的批分片所花时间，取决于池中耗时最长的实例完成其分片的时间。

## 9. 结论

本文中，我们介绍了从 PyPI 简单安装、不做任何额外调优时，PyTorch 和 TensorFlow 上 BERT 开箱即用的推理性能。
需要强调的是，这里的结果反映的是框架的开箱即用配置，因此未必是绝对最佳性能。我们决定不在本文中纳入优化，而聚焦硬件与效率。优化会在第二部分讨论！🚀

随后，我们讲解并细化了设置线程亲和性的影响与重要性，以及目标问题尺寸与所需核心数之间的权衡。
优化部署时，明确使用**哪种标准**（*即延迟 vs 吞吐*）也很重要，因为最终配置可能完全不同。

更一般地看，小问题规模（*短序列和/或小批量*）达到最佳延迟所需的核心数，可能远少于大问题（*超长序列和/或大批量*）。

在思考最终部署平台时，把这些方面都考虑进去会很有意思，因为它可能大幅削减基础设施成本。
例如，我们的 48 核机器收费 **4.848 美元/小时**，而一个只有 8 核的小实例把成本降到 **0.808 美元/小时**，相当于**成本降低 6 倍**。

最后，本文中讨论的许多"旋钮"都可以通过一个 [launcher 脚本](https://github.com/huggingface/tune/blob/main/launcher.py)自动调优，其灵感主要来自 Intel 的原始脚本（见[这里](https://github.com/intel/intel-extension-for-pytorch/blob/master/intel_pytorch_extension_py/launch.py)）。launcher 脚本能自动以正确的线程亲和性启动你的 Python 进程（们），把资源有效地拆分到各实例，并包含许多其他性能技巧！我们会在第二部分详细讲解这些技巧 🧐。
