今天我们发布 [**Olmo-core 3**](https://github.com/allenai/olmo-core)——我们的大语言模型开发框架的重大升级，核心是一个重新设计的开放 mixture-of-experts（MoE）训练系统。

Olmo-core 3 的设计目标是在保留计算效率的同时，把 MoE 训练扩展到万亿参数区间。它是下一代 Olmo 背后的核心系统之一，也是我们「把每个新模型背后的工具与训练基础设施开放出来」这一长期承诺的一部分。

训练大型 AI 模型需要大量算力，推高成本和能耗，让许多学术研究者和小型实验室无法开展前沿模型开发。MoE 模型提供更高效的路子——它们可以包含多得多的学习组件（参数），而不要求每个输入用到全部参数。但完整模型仍需存放在 GPU 显存中并在训练中更新，而且在整个集群上把输入路由到合适的专家——MoE 内部的专门组件——会带来自身的通信与协调成本。随着 MoE 变大，这些成本会侵蚀「每个输入只用部分模型」带来的大部分计算优势。

Olmo-core 3 正是为弥合这一差距而建。在一个基准中，我们把专家池从 8 个扩大到 128 个，而每个 token 仍只选取四个专家——token 是语言模型处理的小文本单元——使每个 token 的活跃参数数量基本固定在约 3.2B。总参数容量从 4.6B 增至 47B，而训练吞吐量下降不到 5%。

同一套基础设施已在超过一万亿总参数的规模上做过基准测试。

## **围绕 MoE 的真实运作方式构建训练栈**

Olmo-core 随每一代 Olmo 演进。

我们对稀疏模型的工作可以追溯到 [OlmoE](https://allenai.org/blog/olmoe-an-open-small-and-state-of-the-art-mixture-of-experts-model-c258432d0514)，它使用带 64 个路由专家的 MoE 架构。相比之下，[Olmo 3](https://allenai.org/blog/olmo3) 使用稠密架构，即对每个 token 模型几乎全部处于活跃状态，其训练栈也围绕该设计构建。Olmo-core 3 用一个为更大 MoE 模型设计的训练系统扩展了这个框架。

Olmo-core 早期的 MoE 实现使用全分片数据并行（FSDP），配置成每收到一小批训练数据就收集再重新分片模型权重。Olmo-core 3 切换到基于[分布式数据并行（DDP）](https://narrative.allen.ai/scaling-up-training#data-parallelism)的系统：专家常驻 GPU，把相关数据路由过去，避免了反复的权重收集。

NVIDIA 的 Megatron-Core 是训练大型 MoE 的成熟选项。Olmo-core 3 则把一套集成式 MoE 训练栈带进 Olmo 背后的框架，其重新设计相较早期基于 FSDP 的实现提升了吞吐量。在 8 块 NVIDIA B300 GPU 上的初步测试中，一个 470 亿参数的 MoE 用新栈达到每 GPU 每秒 52,000 token，而早期实现为 19,400——约为 2.7 倍吞吐。

## **扩展并优化 MoE 训练**

Olmo-core 3 把多种「将大型 MoE 分布到 GPU 集群」的技术，与「让路由和计算更高效」的优化结合在一起。

三项技术决定模型及其训练状态如何切分到硬件上：

- **[专家并行（Expert parallelism）](https://narrative.allen.ai/scaling-up-training#expert-parallelism)**把专家分布到各 GPU，每块 GPU 只存储完整专家池的一部分。
- **[流水线并行（Pipeline parallelism）](https://narrative.allen.ai/scaling-up-training#pipeline-parallelism)**把模型的层——依次变换输入的若干阶段——切分到 GPU 组，减少每块 GPU 需要驻留的模型部分。
- **分布式优化器**把优化器状态——训练中用于计算和应用更新的额外数据——分布到各 GPU，而不是每块 GPU 存一整份。

这些技术合起来，让 MoE 能够扩展，而不要求每块 GPU 在内存中保存整个模型及其训练状态。

Olmo-core 3 还降低了把数据路由到合适专家并运行其计算的成本。*Rowwise expert parallelism* 把路由后的数据直接放进专家输入缓冲区，尽量减少重排所需的额外工作。*GPU-resident routing* 让路由元数据留在 GPU 上，CPU 因此可以排队派发工作，而不必等这些信息被拷回。*Grouped GEMM* 把许多小的专家计算合并起来，让 GPU 更高效地执行。

最后，Olmo-core 3 支持 **MXFP8**——一种用更少的 bit 表示某些值的低精度数字格式。只要这些节省能超过数字格式之间转换的成本，它就能减少计算量并减少 GPU 之间传输的数据量。

我们在 4 块 NVIDIA B300 GPU 上的受控基准中测量了 MXFP8 对端到端训练吞吐的影响，工作在专家间均匀分布。在系统中收益最大的部分启用 MXFP8 后，训练吞吐比我们用作基线的高精度格式 BF16 高约 21%，同时峰值活跃内存从 103 GiB 降到 95 GiB。大部分收益来自前馈计算和专家间数据搬运，而不只是 attention。

这些技术与优化必须协同工作。加速训练的一部分会在别处造成成本：更快的计算可能需要更多数据搬运，而如果转换数据耗时太久，搬运更少的 bit 也无济于事。Olmo-core 3 围绕整个训练流程中的这些取舍构建，让我们——也使用这套开放栈的研究者——能够掌控各部分如何组合。

## **扩展到万亿参数区间**

我们在 NVIDIA B300 GPU 上对一系列配置做了 Olmo-core 3 的基准测试，包括一个 1.2 万亿参数的模型——每 token 活跃 58.36B 参数——跑在 512 块 GPU 上。观测到的最高吞吐为 858 TFLOP/s/GPU，即每块 GPU 每秒有效的模型计算量。这些测试采用随机路由来度量系统性能，而非训练质量。

我们还尝试了 DeepEP v2——一种处理跨 GPU 专家间通信的替代方案，达到了 2.38 万亿总参数的配置。这是一次短促的容量测试而非完整训练 run，所以它展示的是 Olmo-core 3 能到达的规模，而非持续训练性能。

在这样的规模上，系统性能只是图景的一部分。我们的技术报告还记录了一系列实验，它们影响了我们训练 MoE 和度量其表现的方式。例如：

- 一个本意是鼓励均衡路由的分数，可能在真实负载变得*更*不均衡时反而变好。我们把这种失败称为 *token gerrymandering*（token 杰利蝾螈）。
- 因为专家处理的 token 更少而调低其学习率（训练更新的步长），在我们测试的模型家族中并未改善结果。
- 即使矩阵维度相同，当被处理的数值变化时，GPU 计算也会耗时不同。因此性能比较不仅要形状匹配，输入数值也要匹配。
- 在不同 GPU 流上重叠通信与计算，并不总能加快训练。某些测试中它反而拖慢了端到端执行——提醒我们更多重叠未必等于更高吞吐。

报告在解释这些发现的同时，也给出了我们测试过并最终未采用的路线。

## **为下一代 Olmo 而建，向所有人开放**

Olmo-core 3 是我们下一步工作的基石。我们的下一代 Olmo 将采用 MoE 架构，目标是成为迄今最强的 Olmo——在我们最大的数据集上训练，拥有我们最长的上下文窗口。

新的训练栈让我们在超越以往 MoE 工作的同时，拥有更大的灵活性，随模型和硬件演进调整训练。而且它完全开放——研究者和开发者可以用 Olmo-core 3 训练自己的 MoE、适配不同硬件，并在路由、并行及系统其他部件上做实验。

这正是我们思考开放模型开发的方式之一：当模型权重背后的基础设施与训练决策同样开放时，权重才更有价值。
