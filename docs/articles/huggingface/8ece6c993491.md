# 通过 DeepSpeed 和 FairScale 用 ZeRO 装载更多、训练更快

**Hugging Face fellow Stas Bekman 的客座博客**

近年机器学习模型的增长速度远超新显卡增加的显存量，许多用户既没法训练、甚至根本加载不了那些巨型模型。虽然一直有人致力于把这些大模型蒸馏到更易管理的尺寸——但蒸馏出的模型既不够快、也不够小。

2019 年秋，Samyam Rajbhandari、Jeff Rasley、Olatunji Ruwase 和 Yuxiong He 发表论文 [ZeRO: Memory Optimizations Toward Training Trillion Parameter Models](https://arxiv.org/abs/1910.02054)，里面充满了巧妙的新想法，告诉你如何让硬件干出远超想象的活。不久后 [DeepSpeed](https://github.com/microsoft/deepspeed) 发布，开源实现了论文中的大部分思想（少数想法仍在开发中）；几乎同时，Facebook 的团队发布了 [FairScale](https://github.com/facebookresearch/fairscale/)，也实现了 ZeRO 论文的一些核心思想。

如果你用 Hugging Face Trainer，从 `transformers` v4.2.0 起就已经实验性支持 DeepSpeed 和 FairScale 的 ZeRO 特性。新的 `--sharded_ddp` 和 `--deepspeed` 命令行 `Trainer` 参数分别集成 FairScale 和 DeepSpeed。[完整文档在这里](https://huggingface.co/transformers/master/main_classes/trainer.html#trainer-integrations)。

这篇博客会讲清楚：无论你只有一块 GPU 还是一整摞 GPU，都能从 ZeRO 中受益。

## 多 GPU 环境下的巨大加速

我们做个小规模微调实验——翻译任务，用 `t5-large` 模型和 `finetune_trainer.py` 脚本（在 `transformers` GitHub 仓库的 [`examples/seq2seq`](https://github.com/huggingface/transformers/tree/master/examples/seq2seq) 下）。

测试机有 2 块 24GB（Titan RTX）GPU。

这只是概念验证性质的基准测试，肯定还能继续优化。所以我们取小样本：训练 2000 条、评估 500 条来做对比。评估默认做宽度为 4 的 beam search，同样条数下比训练更慢，所以测试里评估条数只用了训练的四分之一。

我们基线的关键命令行参数如下：

```
export BS=16
python -m torch.distributed.launch --nproc_per_node=2 ./finetune_trainer.py \
--model_name_or_path t5-large --n_train 2000 --n_val 500 \
--per_device_eval_batch_size $BS --per_device_train_batch_size $BS \
--task translation_en_to_ro [...]
```

基线只用 `DistributedDataParallel`（DDP），没有做任何额外的性能优化。batch size（BS）最多开到 16 就撞 Out of Memory（OOM）了。

注意，为简单易懂，我只列出了与本次演示相关的命令行参数。完整命令见[这个帖子](https://github.com/huggingface/transformers/issues/8771#issuecomment-759248400)。

接下来，我们每次重跑基准都加上下面一项：

- `--fp16`
- `--sharded_ddp`（fairscale）
- `--sharded_ddp --fp16`（fairscale）
- `--deepspeed`（不带 CPU offload）
- `--deepspeed`（带 CPU offload）

由于这些技术的关键优化是把 GPU 显存用得更高效，我们会不断调大 batch size，期望训练和评估更快完成（同时保持指标稳定甚至更好，不过这里不关注这些）。

要记住，训练和评估阶段截然不同：训练时模型权重在更新、梯度在计算、优化器状态要存储；评估时这些都不发生。但这个翻译任务里模型要搜索最佳假设，必须多跑几轮才罢休，所以本身不快，模型一大就更慢。

看看这六轮测试的结果：

| 方法 | 最大 BS | 训练时间 | 评估时间 |
| --- | --- | --- | --- |
| baseline | 16 | 30.9458 | 56.3310 |
| fp16 | 20 | 21.4943 | 53.4675 |
| sharded_ddp | 30 | 25.9085 | 47.5589 |
| sharded_ddp+fp16 | 30 | 17.3838 | 45.6593 |
| deepspeed w/o cpu offload | 40 | **10.4007** | 34.9289 |
| deepspeed w/ cpu offload | **50** | 20.9706 | **32.1409** |

很明显，FairScale 和 DeepSpeed 相比基线都有大幅提升——训练评估总时长和 batch size 都改善了。截稿时 DeepSpeed 施展的魔法更多，短期看是赢家，但 FairScale 部署更省心。用 DeepSpeed 你得写一个简单的配置文件并更换命令行的 launcher；用 FairScale 只需加 `--sharded_ddp` 参数，所以不妨先试它——这是最容易摘的果子。

按 80:20 法则，我只在这些基准上花了几小时，没有去精雕命令行和配置、榨干每一个 MB 和每一秒，因为从这张简单的表里已经足够明显下一步该试什么。当你面对一个要跑几小时甚至几天的真实项目时，请务必多花时间把超参调到最优，让任务更快、成本更低地完成。

想自己动手复现这个基准，或了解所用硬件软件的更多细节，请看[这个帖子](https://github.com/huggingface/transformers/issues/8771#issuecomment-759248400)。

## 把巨型模型塞进一块 GPU

FairScale 只在多 GPU 时才发威，DeepSpeed 则连单 GPU 用户都有礼物。

我们来试试"不可能"：在 24GB 的 RTX-3090 上训练 [t5-3b](https://huggingface.co/t5-3b)。

先按常规单 GPU 设置尝试微调巨大的 `t5-3b`：

```
export BS=1
CUDA_VISIBLE_DEVICES=0 ./finetune_trainer.py \
--model_name_or_path t5-3b --n_train 60 --n_val 10 \
--per_device_eval_batch_size $BS --per_device_train_batch_size $BS \
--task translation_en_to_ro --fp16 [...]
```

没饼吃：即使 BS=1 也会得到：

```
RuntimeError: CUDA out of memory. Tried to allocate 64.00 MiB (GPU 0; 23.70 GiB total capacity;
21.37 GiB already allocated; 45.69 MiB free; 22.05 GiB reserved in total by PyTorch)
```

和前面一样，我只展示关键部分，完整命令在[这里](https://github.com/huggingface/transformers/issues/8771#issuecomment-759176685)。

现在把 `transformers` 升级到 v4.2.0 或更高，然后安装 DeepSpeed：

```
pip install deepspeed
```

再来一次，这次在命令行加上 DeepSpeed：

```
export BS=20
CUDA_VISIBLE_DEVICES=0 deepspeed --num_gpus=1 ./finetune_trainer.py \
--model_name_or_path t5-3b --n_train 60 --n_val 10 \
--per_device_eval_batch_size $BS --per_device_train_batch_size $BS \
--task translation_en_to_ro --fp16 --deepspeed ds_config_1gpu.json [...]
```

看吧！batch size 20 顺利训练。我大概还能再往上推，到 `BS=30` 才 OOM。

相关结果如下：

```
2021-01-12 19:06:31 | INFO | __main__ |   train_n_objs = 60
2021-01-12 19:06:31 | INFO | __main__ |   train_runtime = 8.8511
2021-01-12 19:06:35 | INFO | __main__ |   val_n_objs = 10
2021-01-12 19:06:35 | INFO | __main__ |   val_runtime = 3.5329
```

没法跟基线比——基线连启动都做不到，直接 OOM。

太惊人了！

我故意用极小的样本，因为我最关心的是：这个平时塞不进 24GB GPU 的巨型模型，到底能不能训练和评估。

想自己复现或了解更多软硬件细节，请看[这个帖子](https://github.com/huggingface/transformers/issues/8771#issuecomment-759176685)。

## ZeRO 背后的魔法

`transformers` 只是集成了这些出色的方案，发明并非我们所为，所以这里分享一些能让你自己深挖细节的资源。但先给出几个速览，帮你理解 ZeRO 如何做到这些惊艳表现。

ZeRO 的关键特性，是在大家熟悉的数据并行训练概念上加上分布式数据存储。

每块 GPU 上的计算与数据并行训练完全相同，但参数、梯度和优化器状态以分布式/分区的方式存放在所有 GPU 上，只在需要时取用。

下面这张图来自[这篇博客](https://www.microsoft.com/en-us/research/blog/zero-deepspeed-new-system-optimizations-enable-training-models-with-over-100-billion-parameters/)，展示了其工作原理：

[![ZeRO Partitioning](https://huggingface.co/blog/assets/11_zero_deepspeed_fairscale/zero-partitioning.png)](https://huggingface.co/blog/assets/11_zero_deepspeed_fairscale/zero-partitioning.png)

ZeRO 的巧妙之处是把参数、梯度和优化器状态均匀切分到所有 GPU，每块 GPU 只持有一个分区（也叫 shard）。这样 GPU 之间的数据存储零重叠。运行时，每块 GPU 现用现拼每层的数据：向持有缺失信息的 GPU 索要即可。

这个 idea 可能不好消化，我在[这里](https://github.com/huggingface/transformers/issues/8771#issuecomment-758418429)尝试做了一个解释。

截至发稿，FairScale 和 DeepSpeed 只对优化器状态和梯度做分区（分片）。模型参数分片据说很快会在 DeepSpeed 和 FairScale 中到来。

另一个强力特性是 ZeRO-Offload（[论文](https://arxiv.org/abs/2101.06840)）。它把部分计算和内存压力卸载到宿主机 CPU，从而让 GPU 装下更多东西。你在 24GB GPU 上跑 `t5-3b` 的成功，已经见识了它戏剧性的效果。

PyTorch 论坛上大家抱怨很多的另一个问题是 GPU 显存碎片。你经常见到这样的 OOM 错误：

```
RuntimeError: CUDA out of memory. Tried to allocate 1.48 GiB (GPU 0; 23.65 GiB total capacity;
16.22 GiB already allocated; 111.12 MiB free; 22.52 GiB reserved in total by PyTorch)
```

程序想分配约 1.5GB，GPU 明明还有 6-7GB 没用，但连续可用空间只剩约 100MB，于是 OOM。原因是不同大小的内存块被反复分配、释放，时间久了就挖出一个个"洞"，形成显存碎片——空闲总量很大，却没有目标大小的连续块。上面这个例子里，程序或许能拿到 100MB 连续内存，但显然拿不到 1.5GB 的整块。

DeepSpeed 直接自管 GPU 显存来对付这个问题，让长生命周期分配与短生命周期分配不混在一起，从而大幅减少碎片。论文没展开细节，但[源码](https://github.com/microsoft/DeepSpeed)开源，可以研究 DeepSpeed 是怎么做到的。

ZeRO 全称 Zero Redundancy Optimizer（零冗余优化器），从表现来看名副其实。

## 未来

除了期待中的模型参数分片支持，DeepSpeed 已经发布了一些我们还没探索的新特性，包括 DeepSpeed Sparse Attention 和 1-bit Adam，它们应该会降低内存用量、大幅削减 GPU 间通信开销，让训练更快、支持的模型更大。

我相信 FairScale 团队也会持续送出礼物，听说他们也在做 ZeRO stage 3。

更兴奋的是，[ZeRO 正在被集成进 PyTorch](https://github.com/pytorch/pytorch/pull/46750)。

## 部署

如果本文的结果让你心动，请移步[这里](https://huggingface.co/transformers/master/main_classes/trainer.html#trainer-integrations)了解如何在 `transformers` Trainer 中使用 DeepSpeed 和 FairScale。

当然，你也可以按各项目的说明修改自己的训练器来集成 DeepSpeed 和 FairScale，或者"抄近路"看看我们在 `transformers` Trainer 里是怎么做的——选后者的话，在源码里 `grep` `deepspeed` 和/或 `sharded_ddp` 就能找到线索。

好消息是：ZeRO 不需要修改模型，需要改的只有训练代码。
