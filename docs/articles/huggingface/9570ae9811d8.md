# 不要重复自己*

##### *为现代机器学习设计开源库*

## 🤗 Transformers 的设计哲学

*「不要重复自己」（Don't repeat yourself）*，即 **DRY**，是软件开发中一条广为人知的原则。这条原则出自《The pragmatic programmer》，是代码设计领域被阅读最多的书之一。它传达的信息简单却不言自明：别处已经存在的逻辑，不要再重写一遍。这样能保证代码保持同步，让维护更容易、代码更健壮。对这一逻辑模式做出的任何改动，都会一致地影响到它所有的依赖。

乍看之下，Hugging Face 的 Transformers 库的设计与 DRY 原则再背道而驰不过了。注意力机制的代码在不同模型文件中差不多被复制了 50 多次。有时整个 BERT 模型的代码会被复制到别的模型文件里。当新的模型贡献和已有模型完全相同——只差一点小的逻辑改动——我们常常要求贡献者把现有代码整份复制过来。我们为什么要这么做？是因为我们太懒，或者忙得无暇把所有逻辑部分集中到一处吗？

不，我们不是懒——这是一个非常审慎的决定：不在 Transformers 库中应用 DRY 这条设计原则。相反，我们选择采纳另一条设计原则，我们愿意称之为***单一模型文件（single model file）* 策略**。*单一模型文件*策略的意思是：一个模型前向传播所需的全部代码都放在唯一的、也是唯一一个文件里，即模型文件。如果读者想弄明白 BERT 是如何做推理的，她只需要去看 BERT 的 `modeling_bert.py` 这一个文件。我们通常会拒绝任何把不同模型中相同的子组件抽象到一个新的集中位置的尝试。我们不希望存在一个 `attention_layer.py`，里面装着所有可能的注意力机制。那么，我们为什么要这么做？

简而言之，理由有：

- **1. Transformers 由开源社区共建，也为开源社区而建。**
- **2. 我们的产品是模型，我们的客户是阅读和改动模型代码的用户。**
- **3. 机器学习这一领域演进极快。**
- **4. 机器学习模型是静态的。**

### 1. 由开源社区共建，也为开源社区而建

Transformers 的构建目标之一就是主动激励外部贡献。一次贡献通常要么是一个 bug 修复，要么是一个新模型的贡献。如果在某个模型文件里发现了 bug，我们希望尽可能让发现它的人容易地把它修好。没有什么比修好一个 bug 之后却发现它导致其他 100 个模型失败更让人泄气的了。

由于每个模型的代码都独立于其他所有模型，一个只理解她正在使用的那一个模型的人就能把它修好，这相当容易。同样，如果只新增一个模型文件，添加新的建模代码并 review 相应的 PR 也就更容易。贡献者不必费神去想如何在一个中心化的注意力机制里加入新功能而不破坏现有模型；review 的人也能轻松确认没有任何现有模型被破坏。

### 2. 建模代码就是我们的产物

我们认为，Transformers 库中有相当一部分用户不仅读文档，也会去查看真正的建模代码，甚至可能动手修改它。Transformers 库被 fork 超过 10,000 次、Transformers 论文被引用超过一千次，都印证了这一假设。因此，让第一次阅读 Transformers 建模代码的人能够轻松理解并有可能加以改造，就至关重要。把所有必要的逻辑组件按顺序放进单个建模文件，对提升可读性和可改造性帮助很大。此外，我们非常在意合理的变量/方法命名，宁要表达清晰、可读性好的代码，也不要节省字符的代码。

### 3. 机器学习以令人窒息的速度演进

机器学习领域——尤其是神经网络——的研究演进极快。一年前还是 state-of-the-art 的模型，今天可能就已经过时。我们并不知道一年之后哪种注意力机制、位置嵌入或架构会是最好的。因此，我们无法定义出适用于所有模型的标准逻辑模式。

举个例子，两年前我们或许会把 BERT 的自注意力层定义为所有 Transformers 模型都使用的标准注意力层。从逻辑上讲，一个「标准」注意力函数本可以被移进一个中心的 `attention.py` 文件。但随后就出现了在每层注意力中加入相对位置嵌入的注意力层（T5）、多种不同形式的分块注意力（Reformer、Longformer、BigBird），以及为位置嵌入和词嵌入分别使用不同注意力机制的做法（DeBERTa），如此等等……每出现一次，我们都得问自己：是应该改造那个「标准」注意力函数，还是往 `attention.py` 里新增一个注意力函数更好？可那样的话我们又该如何命名它？`attention_with_positional_embd`？`reformer_attention`？`deberta_attention`？

给机器学习模型的逻辑组件起通用化的名字是危险的，因为人们对这个组件代表什么的理解可能很快发生变化或变得过时。例如，「分块注意力」到底对应的是 GPTNeo 的、Reformer 的还是 BigBird 的分块注意力？一个注意力层是自注意力层、交叉注意力层，还是两者都包含？反过来，如果我们按模型的名字来给注意力层命名，那就应该直接把那个注意力函数放进对应的建模文件里。

### 4. 机器学习模型是静态的

Transformers 库是一个统一而经过打磨的机器学习模型集合，这些模型由不同的研究团队创造。每个机器学习模型通常都配有一篇论文和它官方的 GitHub 仓库。而一个机器学习模型一旦发表，之后很少再被改动或调整。

相反，研究团队倾向于在前人模型的基础上发布新模型，而很少对已经发布的代码做重大修改。这是在确定 Transformers 库设计原则时一个很重要的认识。它意味着，一旦某个模型架构被加入 Transformers，这个模型的基本组件就不再变化了。人们会不断发现并修复 bug，方法和变量可能被重命名，模型的输入或输出格式也可能略有调整，但模型的核心组件不再改变。于是，对 Transformers 中所有模型施加全局性改动的需求大大减少；既然每种逻辑模式很少被改动，保证它只存在一处也就没那么重要了。

第二个认识是，模型之间**并不**存在双向依赖。更晚发表的模型可能依赖已有模型，但显然，一个已有模型不可能在逻辑上依赖它的后继。例如 T5 部分建立在 BERT 之上，因此 T5 的建模代码可以在逻辑上依赖 BERT 的建模代码，但 BERT 不可能以任何方式在逻辑上依赖 T5。所以，去重构 BERT 的注意力函数以便同时也能配合 T5 的注意力函数工作，在逻辑上就是站不住的——一个通读 BERT 注意力层代码的人不应该需要了解任何关于 T5 的事情。这同样是不赞成把注意力层这类组件中心化到所有模型都能访问的模块里的理由。

另一方面，后继模型的建模代码完全可能在逻辑上依赖其前驱模型。例如，DeBERTa-v2 的建模代码在某种程度上确实逻辑上依赖 DeBERTa 的建模代码。通过确保 DeBERTa-v2 的建模代码与 DeBERTa 保持同步，可维护性会显著提升：在 DeBERTa 里修复一个 bug，理想情况下也应同时修掉 DeBERTa-v2 里的同一个 bug。那么，我们如何在坚持*单一模型文件*策略的同时，让后继模型与其前驱模型保持同步？

现在可以解释我们为什么在 *"Repeat Yourself"*（重复自己）后面加上那个星号 * {}^{\textbf{*}} * 了。即使看起来像，我们也不会盲目地把已有的建模代码全部复制粘贴。Transformers 的核心维护者之一 [Sylvain Gugger](https://github.com/sgugger) 找到了一个极妙的机制，它既尊重*单一文件策略*，又把维护成本控制在合理范围内。这个机制被宽泛地称为*"copying mechanism"（复制机制）*，它允许我们用 `# Copied from <predecessor_model>.<function>` 这样的语句标记某个逻辑组件，比如一个注意力层函数，从而强制被标记的代码与 `<predecessor_model>` 的 `<function>` 保持完全一致。例如，[DeBERTa-v2 这个 class 中的一行](https://github.com/huggingface/transformers/blob/21decb7731e998d3d208ec33e5b249b0a84c0a02/src/transformers/models/deberta_v2/modeling_deberta_v2.py#L325) 就强制整个 class 与 [DeBERTa 的 class](https://github.com/huggingface/transformers/blob/21decb7731e998d3d208ec33e5b249b0a84c0a02/src/transformers/models/deberta/modeling_deberta.py#L336) 完全相同，除了 `DeBERTav2` 这个前缀。这样，复制机制让建模代码依旧非常好懂，同时显著降低了维护量。如果前驱模型某个函数里的代码被改动，而后继模型中有函数引用了它，那么已有工具会自动修正后继模型的那个函数。

### 缺点

显然，单一文件策略也有缺点，这里我们简要提两个。

Transformers 的一个主要目标是为所有模型提供统一的推理和训练 API，让用户可以在自己的环境中快速切换不同模型。但如果建模文件不允许使用抽象后的逻辑模式，要保证 API 统一就困难得多。我们解决这个问题的办法是运行**大量**测试（写下这篇博客时，每天大约运行 20,000 个测试），以确保模型遵循一致的 API。在这种情况下，单一文件策略要求我们在 review 模型与测试的新增内容时极其严格。

第二个问题是，有大量研究只针对机器学习模型中的单个组件。*例如*，研究团队会探索一种新的注意力机制形式，并希望它适用于所有现有的预训练模型，[Rethinking Attention with Performers](https://arxiv.org/abs/2009.14794) 就是这么做的。这样的研究我们该如何纳入 Transformers 库？这确实是个难题。难道要修改所有现有模型？这会与上面写的第 3、4 点相违背。难道要新增 100 多个建模文件，每个都以 `Performer...` 作为前缀？这看起来很荒谬。这种情况下并没有好的解决方案，我们只能选择不把这篇论文收进 Transformers。如果这篇论文获得了远更多的关注、并包含了很强的预训练 checkpoint，我们大概就会为最重要的那几个模型新增建模文件，比如提供 `modeling_performer_bert.py`。

### 结论

总而言之，在 🤗 Hugging Face，我们坚信*单一文件策略*就是 Transformers 合适的编码哲学。
