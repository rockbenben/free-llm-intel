# 用 KVPress 掌控 LLM 长上下文

> TL;DR：KVPress 打包了最新的 KV cache 压缩技术，让长上下文 LLM 省显存。🚀

大语言模型（LLM）的关键特性之一是**上下文窗口**——单次请求能处理的最大 token 数。随着 LLM 演进，上下文窗口越做越大。

更大的上下文窗口解锁了惊人的可能：

- 上下文内检索：在一次查询中无缝引用海量文本。
- 上下文内学习：在同一会话里根据具体示例调整行为。
- 长链推理：处理非常长的思维链而不断上下文。

然而这些扩展的窗口是有代价的——长上下文在 KV Cache 中占用的内存变得难以管理。例如，用 float16 的 Llama 3-70B 处理 100 万 token，KV Cache 就需要 **330GB**，让很多应用望而却步。

这篇博客介绍一个解决办法：**压缩 KV Cache** 以更高效的生成。我们会讲：

- KV Cache 是什么、为什么重要。
- KVPress——NVIDIA 打造、用于高效压缩 KV Cache 的强大工具包。
- KVPress 的内部机制，以及它如何实现压缩。

## KV Cache 是什么，为什么重要？

[![KV Cache](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/kvpress/cache.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/kvpress/cache.png) 图 1：注意力模块内部的 Key-Value cache（来源：NVIDIA）

在自回归模型中，文本生成是**逐 token** 进行的，每一次预测都依赖前面所有 token 提供上下文。例如：

- 要生成第 1000 个 token，模型必须考虑 token 1 到 999 的表示。
- 要生成第 1001 个 token，同样的信息（token 1 到 999）又得处理一遍，再加上 token 1000。

随着序列变长，这种重复计算变得低效，对大模型尤其如此。KV Cache 的优化思路是把注意力层产生的中间结果——key（K）和 value（V）——存下来，后续 token 直接复用而不是重算。

## 问题：KV Cache 与其线性膨胀的负担

KV Cache 虽强，却有一个大缺点——它随上下文窗口大小线性增长。听起来也许不吓人，拆开算一算就知道这为什么会成为严重瓶颈。

### KV Cache 的大小

KV Cache 存的值来自模型用到的所有注意力块。因此它的大小取决于模型架构——架构决定了注意力头的数量。具体地说，KV Cache 的内存用量由下式决定：

Size(KV)=2×precision×nlayers×nheads×d×ntokens \text{Size}(\text{KV}) = 2 \times \text{precision} \times n_{layers} \times n_{heads} \times d \times n_{tokens} Size(KV)=2×precision×nlayers​×nheads​×d×ntokens​

每个因子都在助推内存的爆炸。为了更直观，算一个具体例子——Llama 3-70B 以 `bfloat16` 精度运行（[模型作者](https://huggingface.co/meta-llama/Llama-3.3-70B-Instruct)推荐的精度），上下文 100 万 token：

Size(KV)=2×2×80×8×128×1M=327.6GB \text{Size}(\text{KV}) = 2 \times 2 \times 80 \times 8 \times 128 \times 1M = 327.6 \text{GB} Size(KV)=2×2×80×8×128×1M=327.6GB

bfloat16 每个参数 2 字节，仅模型权重就要 140 GB（70B x 2 字节）。也就是说，用 100 万 token 上下文跑这个模型大约需要 470 GB 内存，其中 KV cache 独占高达 70%。

## KVPress：KV Cache 压缩工具包

如上所述，KV Cache 既是长上下文 LLM 部署的关键使能者，也是重大瓶颈。解决线性膨胀的内存问题需要创新的压缩技术，这正是 [KVPress](https://github.com/nvIDIA/kvpress) 的用武之地。

KVPress 由 NVIDIA 开发，是一个 Python 工具包，通过提供一整套[最先进的压缩](https://github.com/NVIDIA/kvpress?tab=readme-ov-file#available-presses)技术来化解大 KV Cache 的内存难题。它还能与其他方法组合使用，比如 **KV Cache 量化**——transformers 库内置的降低内存用法的手段（上面公式里的 precision 项），进一步扩大实用性（[详情](https://huggingface.co/blog/kv-cache-quantization)）。

对专攻压缩的**研究者**，KVPress 提供灵活、模块化的框架，容易理解、也容易加入新方法。对**开发者**，KVPress 简化了部署这些前沿技术的过程，可以快速高效地集成进真实应用。

## KVPress 实战

KVPress 的核心是 [**presses**](https://github.com/NVIDIA/kvpress/tree/main/kvpress/presses)——专为缩减 KV Cache 内存足迹设计的高级压缩算法。

许多 press 依赖一个分数，在每个头内部用它来剪掉最不重要的 KV 对。例如 KnormPress 剪掉 key 值范数最低的 KV 对（[论文](https://arxiv.org/abs/2406.11430)），SnapKVPress 剪掉与最新查询的注意力权重较低的 KV 对（[论文](https://arxiv.org/abs/2404.14469)）。

这些 press 通过 forward hook 无缝集成进模型的注意力层。

[![KV Press 实战](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/kvpress/kvpress.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/kvpress/kvpress.png) 图 2：KV 压缩可视化（来源：NVIDIA）

在文本生成期间，它们动态压缩 KV Cache，在不损害模型生成连贯、准确输出能力的前提下降低内存用量。每个 press 都有一个 `compression_ratio` 属性，决定对 KV Cache 施加的压缩程度。

这些 press 与定制的 `transformers` pipeline 无缝集成，方便应用和实验。

下面示范如何用 KVPress 里的 `ExpectedAttentionPress`（众多 press 之一）。这个 press 剪掉对未来查询的预期注意力权重最低的 KV 对。

```
from transformers import pipeline
from kvpress import ExpectedAttentionPress

pipe = pipeline(
"kv-press-text-generation",
model="meta-llama/Llama-3.1-8B-Instruct",
device="cuda",
model_kwargs={"attn_implementation": "sdpa"}
)

context = "A very long text you want to compress once and for all"
question = "\nA question about the compressed context"  # optional

press = ExpectedAttentionPress(compression_ratio=0.5)
answer = pipe(context, question=question, press=press)["answer"]
```

直接在这个 [Hugging Face space](https://huggingface.co/spaces/nvidia/kvpress) 或这份 [Google colab notebook](https://colab.research.google.com/drive/1JNvaTKuuAHrl49dYB9-mdEH_y52Ib-NP?usp=drive_link) 里试试！

KVPress 瞄准**预填充（pre-filling）阶段**发力，在 cache 最大的时候把它压下来——帮助数万个乃至数百万 token 的序列降低内存开销。

下图展示了随提示词变长，KVPress 压缩带来的 GPU 内存节省。短提示时，内存大头是模型权重——Llama 3.1 8B 以 bfloat16 约 15GB。但随着提示变长，KV cache 成为内存消耗大户。对 128k 上下文，用 50% 压缩率的 KVPress 把峰值内存从 45GB 降到 37GB。更小的 KV cache 还提升了解码速度——A100 GPU 上从 11 tokens/s 提到 17 tokens/s（[来源](https://github.com/NVIDIA/kvpress/blob/main/notebooks/speed_and_memory.ipynb)）。

# 基准测试

研究社区一直在开发 KV cache 压缩的各种技术。KVPress 鼓励研究者贡献自己的方法，目前已经提供了十几种 press。

为评估这些 press 的表现，KVPress 内置了一个简单的 CLI，可在 RULER、InfiniteBench、Loogle 等标准长上下文数据集上做基准。下图用 4k 上下文长度、不同压缩率对 9 种 press 在 RULER 数据集上做了基准。该数据集上表现最好的 press 是 `AdaKVPress`（[论文](https://arxiv.org/abs/2407.11550)）与 `ExpectedAttentionPress` 的组合——后者是 KVPress 作者新发明的、尚未发表的剪枝技术（更多信息见[这里](https://github.com/NVIDIA/kvpress/blob/main/notebooks/expected_attention.ipynb)）。

# 结论

LLM 不断增大的上下文窗口开启了新可能，也带来了 KV Cache 线性膨胀的严峻内存挑战。KVPress 通过在关键的预填充阶段压缩 cache 来应对。

虽然 KVPress 改善了内存效率，但正如基准图所示，更高的压缩率可能影响模型准确度。还需要更多研究来开发能最小化这种取舍的更优压缩算法。

凭借与 transformers 库的无缝集成和模块化设计，KVPress 让研究者和开发者能高效处理长上下文 LLM、并设计新的压缩技术。它是扩展 LLM 而不被内存压垮的务实方案——让模型继续长大的同时，创新保持触手可及。
