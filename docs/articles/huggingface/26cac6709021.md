# 超越 LoRA：你能击败最受欢迎的微调技术吗？

Benjamin Bossan（BenjaminB）、Sayak Paul（sayakpaul）、Marian Tietz（hubnemo）、Kashif Rasul（kashif）

![Is LoRA the best PEFT technique?](https://huggingface.co/datasets/peft-internal-testing/peft-blog-assets/resolve/main/peft-beyond-lora/lora-celebration.png)

# 当你打算以参数高效的方式微调一个模型时，想想 LoRA 之外的可能

如果你想在自己的数据上微调一个开放模型，你多半会对所谓的参数高效微调（parameter-efficient fine-tuning，简称 *PEFT*）感兴趣。这个术语描述的是一类显著降低微调所需内存的技术。虽然有几十种这样的技术，几乎所有人都选一个叫 "LoRA" 的。在这篇博客里，我们探讨 LoRA 是否真的是最佳选择、有哪些工具能帮你做知情决策，以及把视野拓展到 LoRA 之外你能如何受益。

# 什么是 PEFT，什么时候需要它

有无数的开放模型可用，但它们对你的用例往往不够好。提示词工程或许有帮助，但通常不够。与其从零训练一个新模型，你应当考虑微调一个现有的。

然而微调很费内存：你通常要有足够的内存把整个模型容纳好几份。量化能降低模型的内存占用，但量化后的模型无法直接微调。于是一类用于削减微调所需内存的技术出现了，即"参数高效微调"，PEFT。

有了 PEFT，你能只用一小部分内存来微调模型，甚至能微调量化后的模型。它还有其他优势，比如极小的 checkpoint 体积、更强的抗灾难性遗忘能力，以及用同一基座模型服务多个微调结果的能力。

在 Hugging Face，我们开发 [`PEFT` 库](https://github.com/huggingface/peft)，它在统一的 API 后实现了许多 PEFT 技术，并与生态良好集成，例如 [`Transformers`](https://huggingface.co/docs/transformers/main/en/peft) 和 [`Diffusers`](https://huggingface.co/docs/diffusers/main/en/api/loaders/peft)。它还支持[多种量化方法](https://huggingface.co/docs/peft/developer_guides/quantization)，让参数高效微调更易得。无论你想在自己的数据上微调，还是在研究一种新的 PEFT 方法，`PEFT` 都是一个不错的起点。

# LoRA：微调技术的女王 👑

有一个较早涌现、并被证明相当有效的参数高效微调技术，叫"Low Rank Adaptation"，简称 ["LoRA"](https://huggingface.co/papers/2106.09685)。它的做法是在基座模型之上加少量参数、冻结基座模型权重、只训练那些少量参数。

在所有 PEFT 技术中，LoRA 遥遥领先地最受欢迎。这里给几个估计：

- 在抽样自 [Hugging Face Hub 上的 20,834 个模型卡](https://huggingface.co/datasets/librarian-bots/model_cards_with_metadata)（恰好提及一种 PEFT 技术）中，20,509 个提及 LoRA（98.4%）。
- 我们也检查了在一个外部站点上图像生成领域哪些 PEFT 技术流行。用 10,000 个 checkpoint 的样本，我们发现 7,111 个是 LoRA。其他被识别的 PEFT 技术是 LoCon（363）和 DoRA（11，可谓一种 LoRA 变体）。这意味着 95.0% 的 PEFT checkpoint 是 LoRA。
- 在 GitHub 上搜索代码片段 `from peft import <PEFT CONFIG>`（[示例 GH query](https://github.com/search?q=%22from+peft+import+LoraConfig%22&type=code)），71.3% 的结果是 LoRA。紧随其后的是 LoHa（3.7%）和 AdaLoRA（3.5%）。

尽管这些估计不完美，但结论仍是 LoRA 几乎可以肯定是迄今为止最常见的 PEFT 技术。

这可能只意味着 LoRA 对每个人都最好，并且这一事实反映在它的使用统计里。不过还有另一种可能：LoRA 是较早流行的 PEFT 技术之一。所以也许它的使用是自我强化的：LoRA 有最高的可见度、最多的教程/示例，在下游包里也有最好的支持。于是 LoRA 的热度自我滋养。

这一切引出问题：*我们是否因为排斥更好的技术而把性能留在了桌上？*毕竟，有无数的研究者，他们的论文声称自己的技术胜过 LoRA。这难道不足以证明我们应当超越 LoRA、转向更新的技术吗？

# 基于论文结果选择 PEFT 技术是有问题的

有几十篇论文研究 LoRA 之外的微调技术。仅在 `PEFT` 库里，撰写本文时就有 40 多种不同的 PEFT 技术（若算上 PEFT 技术的变体则更多）。对其中几乎所有技术，你都能找到研究者声称在他们的基准上该技术胜过 LoRA。

这些声明的问题在于，研究者面临压力，必须给出击败现有基准的结果。即便没有恶意，这也会让结果有偏，比如对替代技术花的时间比对研究者所提技术花的时间少。[一项研究](https://arxiv.org/abs/2602.04998) 就发现，仅通过调学习率，LoRA 就能匹敌所谓更好的 PEFT 技术。

另一个麻烦是，每篇论文选择用于对比的 PEFT 技术集合不同，运行的基准集合也不同。而且即便在同一基准上比较同一技术，代码常常拿不到、或不容易自己跑，使得结果难以复现。

总体而言，只查论文结果很难弄清楚哪种 PEFT 技术最适合你。因此你很容易被诱惑去直接选默认的 LoRA。

# 我们在 `PEFT` 里如何做基准测试

在 Hugging Face，我们思考如何帮助用户就使用哪种 PEFT 技术做出知情决策。通过 `PEFT` 库，我们已经提供一个实现了许多 PEFT 技术、并用同一 API 暴露它们的包。下一步是提供基准，为讨论的问题揭示更多。

我们早就有一个[在数学数据集上微调 LLM 的基准](https://github.com/huggingface/peft/tree/main/method_comparison/MetaMathQA)。这个基准拿一个 LLM，在链式思维推理上微调它，用一个未经指令微调的基座模型产出数学题的答案。因此该基准检查模型能否学会做数学推理，以及把生成的输出调整到期望格式。

为把我们的发现扩展到另一种模态，我们还加了一个[图像生成基准](https://github.com/huggingface/peft/tree/main/method_comparison/image-gen)。这个测试模型能否被微调以学一个新概念——一个 [cat plushy](https://huggingface.co/datasets/peft-internal-testing/cat-image-dataset)——并在新语境中生成它而不遗忘已有概念。

所有 PEFT 技术都在完全相同的条件下评估：同样的基座模型、同样的数据集、同样的训练和评估代码、同样的硬件。由于不同用户需求不同，我们追踪的不止是测试性能。除显存使用外，我们还追踪遗忘/漂移、运行时间、checkpoint 体积等指标。结果被设计成能在消费级硬件上跑，而添加一个新实验只需加一个新的 `PEFT` 配置并运行一个脚本。

由于我们让所有 PEFT 技术站在同一起跑线、且不偏袒任何一方，我们相信这些基准能对不同 PEFT 技术的工作好坏给出客观图景。我们认为，如果你有自己数据集，可以采用类似方法、利用 `PEFT` 库来评估多种 PEFT 技术。

# 我们的发现：LoRA 表现不错，但不一定是最佳选择

跑完基准后我们发现，虽然 LoRA 工作得很好，但其他 PEFT 方法能在一个或多个维度上击败它，因此应当被纳入考量。看看下面这张比较 LoRA 和其他五种 PEFT 技术性能的图。

| ![](https://huggingface.co/datasets/peft-internal-testing/peft-blog-assets/resolve/main/peft-beyond-lora/benchmark-highlights.png) |
| --- |
| *基准的一些结果。在测试性能和内存使用上，LoRA 不一定是最佳选择。左：MetaMathQA 基准；右：图像生成基准。查看这个 [Space](https://huggingface.co/spaces/peft-internal-testing/PEFT-method-comparison) 获取最新结果。* |

解读结果的一种方式是从权衡的角度思考，比如：模型在测试集上表现多好 vs 训练它需要多少内存？如果某个 PEFT 技术无法被任何其他技术在两个指标上同时击败，它就在*帕累托前沿*上。换句话说：想要更好的测试准确率，就需要更多内存；想要更省内存，就得放弃一些准确率。

我们细看 LLM 数学数据集基准的结果。在测试准确率对内存上，我们发现 LoRA 确实在帕累托前沿上。它达到 53.2% 测试准确率，峰值需要 22.6 GB 显存。然而帕累托前沿上也有其他 PEFT 技术。例如 [BEFT](https://huggingface.co/docs/peft/main/en/package_reference/beft) 达到 32.9% 测试准确率，最多只需 20.2 GB 内存。另一端，我们有 [Lily](https://huggingface.co/docs/peft/main/en/package_reference/lily)，达到 54.9% 测试准确率但需要 25.6 GB 内存。根据你更看重什么，你可能得出结论：LoRA 对你并非最佳权衡。

| ![](https://huggingface.co/datasets/peft-internal-testing/peft-blog-assets/resolve/main/peft-beyond-lora/metamath-pareto.png) |
| --- |
| *微调 `meta-llama/Llama-3.2-3B` 并在 GSM8K 上评估的测试准确率对内存使用的权衡。LoRA 表现不错，但其他 PEFT 技术也是。* |

同样值得注意的是，虽然 LoRA 在这个任务上表现好，但我们说的不是原版 LoRA。一端是带 [rank stabilized initialization](https://huggingface.co/papers/2312.03732) 的 LoRA，这是一种以不同于默认初始化的方式缩放 LoRA 贡献的技术，给出非常好的测试准确率（53.2%）。另一端是 [LoRA-FA](https://huggingface.co/papers/2308.03303)，它用一种专为 LoRA 定制的优化器，冻结 LoRA 权重的一部分，因而更省内存（20.2 GB）。普通 LoRA 在 22.5 GB 内存下只达到 48.1% 准确率，因此应避免、转向这些替代方案。

| --- |
| *用 LoRA 微调 `FLUX.2-klein-base-4B` 生成的 cat plushy 图像。* |

对这个任务，主要指标是 "dino similarity"，衡量生成图像与留出测试数据集中图片的相似程度，值越高越好。照例，我们也想留意内存使用。把这两个指标的帕累托前沿画出来后，我们发现 LoRA 落在前沿之下。给具体数字：LoRA 达到 0.697 的相似度分数，而 [OFT](https://huggingface.co/docs/peft/package_reference/oft) 达到 0.708；内存上 LoRA 需要 9.97 GB，OFT 需要 9.01 GB。因此在这些指标上 OFT 严格支配 LoRA。

当然，你也应当检查那些接近帕累托前沿的其他 PEFT 方法，因为指标可能因随机性而有小幅波动。你也应当探索其他指标：运行时间对你重要吗，或你在意 checkpoint 的大小？从下拉框选择相关指标，图景可能大变。对图像生成基准，请检视生成的示例图像，感受微调后模型的能力。

# 局限

> 异议：但这些基准偏袒某一种方法！

对 `PEFT` 基准的一种批评是，超参的选择可能偏袒某一种技术。这是事实，用这么多技术做彻底而公平的超参搜索很难。然而，任何人都很容易给 `PEFT` 贡献自己的实验：如果你相信某种 PEFT 技术可以通过改超参来改进，就发一个 PR！我们加了[如何这样做的说明](https://github.com/huggingface/peft/tree/main/method_comparison#creating-new-experiments)。同样，如果你想贡献一个全新的基准，联系我们讨论你的想法。

基准的另一个问题是，它们可能不完全反映某种 PEFT 技术的能力。我们让你能沿许多不同维度比较技术，并按这些权衡发现最佳的。但不可能用这种方式捕捉所有面向。例如，一种叫 [Cartridges](https://huggingface.co/docs/peft/package_reference/cartridges) 的 PEFT 技术是为压缩长提示词而开发的，这不在基准的测量之内。其他因素也会影响选择，比如：

- 取决于 PEFT 技术，只有某些层类型能被修改。
- 并非所有 PEFT 技术都支持量化基座模型（但我们在 `PEFT` 里积极扩展支持）。
- 有些 PEFT 技术允许[合并适配器](https://huggingface.co/docs/peft/main/en/developer_guides/model_merging)以降低运行开销，有些则不行。

基准无法完全替你做研究的这份责任，但它们可以是合理的指引。

> 异议：但 llama.cpp/vLLM/... 只支持 LoRA

使用 LoRA 之外的 PEFT 技术的一个局限，是它们得不到 LoRA 在下游包里享有的广泛支持。例如，如果你想用 vLLM 服务模型，只有 LoRA checkpoint 能被加载。好在 `PEFT` 现在支持[把其他适配器转换为 LoRA](https://huggingface.co/docs/peft/main/en/package_reference/lora_conversion)。这样你可以把一个非 LoRA checkpoint 转成 LoRA，并在 vLLM 或其他下游包里使用。

为测试这一点，我们把一个用 GraLoRA 技术训练出的图像适配器转换成了 LoRA checkpoint。转换后测试分数几乎相同（相似度 0.702 → 0.694，0.260 → 0.269）。下面是为提示词 "sks cat at the beach" 生成的测试图像：

# 结论，以及*你*能做什么

在做 `PEFT` 包的过程中，我们注意到 LoRA 有大量势能，即便其他 PEFT 技术可能更好。因此，我们着手给 PEFT 加上基准，为不同 PEFT 技术在不同指标上的表现勾勒更客观的图景。

鉴于我们得到的结果，可以自信地得出结论：LoRA 完全不算差的选择，但可能有更好的选择。尤其在看图像生成基准时，LoRA 被其他技术击败。我们讨论了除指标外，选择合适 PEFT 技术时还须考虑其他方面。但即便如此，我们也在推进 `PEFT`，以实现 LoRA 与其他这些技术之间的功能对等。

我们的路还远未走完；我们要扩展和改进现有基准，也计划在未来加入更多基准。我们确保社区很容易贡献，所以如果你想这么做，请在 [`PEFT` 仓库](https://github.com/huggingface/peft/issues) 上开一个 issue，告诉我们你想如何贡献。

如果你从这篇文章只带走一点，那就是：为你的用例选 PEFT 技术时，LoRA 不该是自动的默认选择。鉴于 `PEFT` 提供的统一 API，从一种 PEFT 技术换到另一种，只需在代码里改一个配置那么简单。而即便你坚持用 LoRA，也看看 `PEFT` 支持的所有变体：DoRA、rs-LoRA、LoRA-FA 等等。试试这些其他技术，你或许会惊喜。

示例：用 `PEFT` 从 LoRA 换到 OFT：

```
from transformers import AutoModelForCausalLM
-from peft import LoraConfig, get_peft_model
+from peft import OFTConfig, get_peft_model

base_model = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.2-3B", dtype="bfloat16")
-config = LoraConfig(target_modules=["q_proj", "v_proj"])
+config = OFTConfig(target_modules=["q_proj", "v_proj"])
model = get_peft_model(base_model, config)
```
