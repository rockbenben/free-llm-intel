# 用 Strands Agents、LeRobot 与 Hugging Face Storage Buckets 在一处完成录制、训练与部署

*Strands Robots 流式数据环（streaming data loop）的完整走查——一个代理循环，录制机器人演示、直接从 Hub 读取数据在其上训练，并把策略部署回硬件；全程数据集都保持同一种磁盘上的 LeRobot 格式。*

你已经有一个能把演示录制并推送到 [Hugging Face Hub](https://huggingface.co/) 的代理。现在你想让这个循环持续运转：白天不断采集 episode，在持续增长的数据集上训练策略、部署它，再把下一批采集的数据收回来继续改进。跑一遍这个循环，每个环节都能工作；但每天都跑，你就开始为同样的字节传输反复付费：上传的录制文件不断膨胀，每次训练开始前都要把整个数据集复制到 GPU，每个新 checkpoint 发出去的同时下一批录制又收回来。

[本系列第一篇](https://huggingface.co/blog/amazon/strands-lerobot-hub-to-hardware)介绍了 [Strands Robots](https://github.com/strands-labs/robots)——AWS 的开源 SDK（[Apache 2.0](https://www.apache.org/licenses/LICENSE-2.0)），它把机器人抽象、仿真和 [LeRobot](https://github.com/huggingface/lerobot) 技术栈封装成 AgentTool，供你组合进单个 Strands 代理。那篇讲到了 `Robot()` 工厂、在仿真中录制演示、运行策略，以及把同样的代理代码部署到物理 SO-101。该工厂按名字解析一个涵盖机械臂、人形机器人、移动底座和灵巧手的注册表，所以本文通篇使用的 SO-100 只是众多支持的具身形态之一。[机器人目录](https://strands-labs.github.io/robots/robots/)列出了工厂认识的所有机器人。LeRobot 的数据集格式已被 Hub 上来自 8,000 多个发布者的 90,000 多个数据集和模型使用（[LeRobot Project Pulse](https://huggingface.co/spaces/imstevenpmwork/lerobot-adoption-dashboard)）。Strands Robots 的录制只是其中又一份，所以任何能读 LeRobot 数据的工具无需转换即可读取它。如果你是初次接触 Strands Robots，请从那篇开始；本文以那套配置为前提。

上一篇沿一个方向追踪了代理循环：从 Hub 数据集到物理机器人。这一篇则反向追踪数据：从录制的第一帧画面回到部署的策略，全程借助 [Hugging Face Storage Buckets](https://huggingface.co/docs/hub/storage-buckets)——一种可变的、无版本管理的、基于 [Xet](https://huggingface.co/blog/from-files-to-chunks) 的对象存储仓库类型，[于 2026 年 3 月发布](https://huggingface.co/blog/storage-buckets)。bucket 与你的数据集仓库并列在同一个 `hf://` 命名空间中，使用的就是你已有的 `hf` CLI，于是它成了你的数据层：存放你从录制那天到训练那天之间的数据。

总得有人决定：保留哪些 episode、场景何时漂移到了要重录的程度、今天这批数据是否够训练、哪个 checkpoint 替换机械臂上现有的那个。在一场采集活动中，每个这样的决定都要出现几十次，而且每一次都需要先查看回收回来的东西，才能下发下一条命令。这正是代理该干的活。本文带你走过单个代理内部的数据环：把演示录制进一个 Storage Bucket、以"每次同步只上传发生变化的字节"的方式存储、直接从 Hub 流式读取数据集来训练而不下载，最后只改一个关键字参数就把 checkpoint 部署回硬件。本文的可运行配套文件位于 [`examples/notebooks/05_streaming_data_loop.ipynb`](https://github.com/strands-labs/robots/blob/main/examples/notebooks/05_streaming_data_loop.ipynb)。

## 你将构建什么

第一篇是录制数据集并推送到 Hub，而这里你构建的代理从一句自然语言 prompt 录制 LeRobotDataset、同步进一个 Storage Bucket，再把同一份数据集逐帧流式读回、实时解码相机视频，全程没有本地副本。你在写入它的同一个进程里读回它：录制数据集的同一个 Strands Robots `Robot()` 也来流式读取它。随后你训练好的 checkpoint 只改一个关键字参数就部署回这同一个 `Robot()`，而它在硬件上录制的演示又回到同一个 bucket。

**图 1。** *四个阶段共享同一个后端。* `Robot("so100")` *通过共享的* `DatasetRecorder` *录制 LeRobotDataset；* `sync_dataset_to_bucket(...)` *把它同步进 Storage Bucket；* `stream_dataset(...)` *经 Hub 读回，无需完整下载；训练好的 checkpoint 以* `mode="real"` *部署到同一个* `Robot`*。磁盘格式始终保持 LeRobot 写出的原样。*

由于同一个 `Robot()` 既能录制数据集又能读回它，采集数据和训练数据就变成同一后端上同一对象的两个方法。代理决定跑一次 episode 并调用一个工具；随后 rollout 以机器人的控制频率持续推进，直到 episode 结束，期间每个动作都由训练好的策略产生。整个循环，寥寥数行：

```
from strands import Agent
from strands_robots import Robot

sim = Robot("so100")                 # mode="sim" (default - safe, no hardware)
agent = Agent(tools=[sim])

# Record a demonstration and sync it to a bucket.
agent("Record a pick-the-cube demo and sync it to my-org/robot-fave.")

# Stream it back from the bucket to train, without downloading it first.
for batch in sim.stream_dataset("my-org/robot-fave/cube_pick", repo_type="bucket").dataloader(batch_size=64):
    ...
```

接下来我们逐步拆解这个循环内部真正发生的事情。

## 前置条件

#### 最小配置（默认仿真路径）

- Python 3.12+，运行于 Linux 或 macOS（MuJoCo 后端支持 Apple Silicon）。
- 一个与 Strands 兼容、供代理推理的模型 provider。[Amazon Bedrock](https://aws.amazon.com/bedrock/)（配 AWS 凭证）、[Anthropic API](https://docs.anthropic.com/)、OpenAI，或本地运行的 [Ollama](https://ollama.com/)。
- 带数据集 extras 的 Strands Robots：`uv pip install -U "strands-robots[sim-mujoco,lerobot]>=0.5.1"`。`lerobot` extra 会拉取 LeRobot（>=0.6.1）、`datasets`、`av` 和 `torchcodec`，因此录制与视频解码都无需再做额外配置。参见[安装指南](https://strands-labs.github.io/robots/getting-started/installation/)。

就这些。本文的每个阶段用这三样就能在笔记本上运行。跑起来的是循环本身，而不是一个可用的策略：默认路径使用 mock 策略，它能录制结构合法的数据集，但没有实用价值。

#### 进阶配置（bucket、硬件、真实策略）

- 一个拥有写权限的 Hugging Face 账户和 token，以及用于创建 bucket 和同步数据集的 `hf` CLI：`pip install -U "huggingface-hub>=1.6.0,<2.0.0"`，然后 `hf auth login`。
- 硬件路径：一对 SO-101 follower 和 leader，或任何其他 LeRobot 支持的机器人，且 `~/.cache/huggingface/lerobot/calibration/` 下有校准文件。
- 本地视觉-语言-动作（VLA）推理：一块 NVIDIA GPU。规模化训练：一个从 Hub 读取的 GPU 集群。
- 要运行训练步骤：`uv pip install "lerobot[training]"`。录制和流式读取不需要它。如果跳过安装，`trainer.train()` 会返回错误结果而不是 checkpoint。[排障指南](https://strands-labs.github.io/robots/troubleshooting/)会指出该错误以及能修复它的安装命令。

## 第 1 步 - 把演示录制进 bucket

你白天不断录制新 episode，每个 episode 都是相机画面与关节状态-动作遥测的连续流。LeRobot 把它们写成一小批会随录制增长的大文件。把这些推进一个带版本管理的数据集仓库，每次追加都变成一次 commit，每个修订版本都会保留。而采集工作想要的恰恰相反：一个能写数据并能就地覆盖的地方。这就是 [Storage Bucket](https://huggingface.co/docs/hub/storage-buckets)，它就在你的 Hugging Face 工作空间内，复用你已有的权限体系。没有 IAM 角色要配置，没有 CORS 规则，也不用自己维护上传服务。

你的代理以 LeRobot 在硬件上写入的相同格式录制 LeRobotDataset。先录制 episode，再把完成的数据集同步进 bucket。下面这句 prompt 要求使用 mock 策略——一个无需训练模型即可产生关节动作的替身——让你在还没有 checkpoint 可跑时就能把整个循环跑通：

```
from strands import Agent
from strands_robots import Robot, sync_dataset_to_bucket

sim = Robot("so100")                 # mode="sim" by default
agent = Agent(tools=[sim])
# One prompt drives scene setup, cameras, policy, and recording.
agent(
    "Create a world with the so100 robot, add a red cube and a front camera, "
    "start recording (repo_id='local/cube_pick', root='/tmp/cube_pick', fps=30, "
    "overwrite=True, task='pick up the red cube'), run the mock policy for "
    "60 steps, then stop recording."
)
# Sync the finished on-disk dataset into the bucket (no live recording session needed).
sync_dataset_to_bucket("/tmp/cube_pick", "my-org/robot-fave")
# -> {"status": "success", "bucket_uri": "hf://buckets/my-org/robot-fave/cube_pick"}
```

同步写入 `hf://buckets/{bucket}/{run_id}`，其中 `run_id` 默认取数据集目录名。第 3 步的流式读取同样要指定 run：id 的前两段是 bucket，之后的所有内容都是 bucket 内的路径。

`sync_dataset_to_bucket(root, bucket, run_id=...)` 会校验数据集并通过 `hf` CLI 同步，与录制生命周期解耦。如果你直接驱动一个打开着的录制器，同样的能力在 `DatasetRecorder.sync_to_bucket(bucket, run_id=...)` 上；`stop_recording(bucket=...)` 则在你停止一次活跃录制的瞬间执行同步。bucket 是你白天持续写入的工作层；要得到带版本管理的、可发布的产物，你仍然调用 `push_to_hub()`。两者承载同一种格式。

episode 的结构是完整的，但动作是占位的，所以它并不是你想要的训练数据。换上 `create_policy("<hf_repo>")` 加载真实策略就能真正抓取；prompt、格式和 bucket 同步保持完全不变。

#### 在硬件上录制

要在物理 SO-101 上录制，[LeRobot 的 record CLI](https://huggingface.co/docs/lerobot/il_robots) 负责 leader-follower 的启动：

```
lerobot-record \
  --robot.type=so101_follower --robot.id=my_follower \
  --teleop.type=so101_leader  --teleop.id=my_leader \
  --dataset.repo_id=my_user/cube_picking \
  --dataset.single_task='Pick up the red cube'
```

落盘的数据集与仿真录制格式相同，因此同一个同步调用就能把它带进 bucket：`sync_dataset_to_bucket("./recordings", "my-org/robot-fave", run_id="run-021")`（或它封装的 `hf sync ./recordings hf://buckets/my-org/robot-fave/run-021` CLI）。采集活动统一追加进同一个地方，而你发布的仓库只拿到你选择发布的版本。

## 第 2 步 - 用字节级去重存储

数据集进了 bucket，问题是下一次同步要花你多少。让两枚固定相机对着一只机械臂清理同一张桌子拍八小时，你录下的大多是早已拥有的像素：同样的光照、同样的机身、同样的背景，横跨上千个 episode。在带版本管理的仓库上情况更糟，因为改动一个数 GB 视频分片中的一帧，就会重传整个文件。

bucket 由 [Xet](https://huggingface.co/blog/from-files-to-chunks) 支撑，它使用内容定义分块（content-defined chunking）在字节级对你的上传去重。分块边界跟随内容，因此插入几个字节只影响它落入的那个块，而不会让之后的所有边界都平移。按 Hugging Face 自己的测量（[HF Storage](https://huggingface.co/storage)），内容定义分块使全站的每次上传数据传输量降低约四倍，而 Enterprise 套餐的计费依据是去重后的占用量。他们的 [bucket 基准测试](https://huggingface.co/spaces/h-m-t/hf-buckets-benchmark)展示了单文件上的效果：从一个 500 MB 的上传出发，改动 1% 的字节再上传只传输了 5.5 MB，改动 5% 传输 27.5 MB，改动 10% 传输 55 MB。没有块级去重时，覆盖一个对象就意味着重新发送它的每一个字节，无论有没有变化。

这能省多少取决于文件布局，而 Strands Robots 录制器使用的是 LeRobot 的布局。Episode 写入 Parquet 分片（`data/chunk-000/file-000.parquet`）和每相机 MP4 分片（`videos/observation.images.front/chunk-000/file-000.mp4`），只有当前文件写满才滚动到新文件，按 LeRobot 默认值：数据 Parquet 为 100 MB，视频 MP4 为 200 MB。因此录一天之后的同步只上传新的尾部分片以及那个增长中的半满分片，而不是整个数据集。明天再同步同一个 bucket，Xet 会处理去重。

[![fig2_xet_dedup](https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/mPnNR7MlxV9SeRoFqGIyv.png)](https://cdn-uploads.huggingface.co/production/uploads/6a1dc0f2b4238bb17ff94794/mPnNR7MlxV9SeRoFqGIyv.png)

**图 2。** *一次同步只上传发生变化的部分。全新数据集的首次同步上传所有块；录了更多 episode 之后，由于 Xet 的内容定义分块，下一次同步只上传新增的块，跳过已存储的部分。*

## 第 3 步 - 从 Hub 流式训练

要训练，你得把 GPU 对准数据集。先下载的话，GPU 就干等着几百 GB 复制完。直接从 Hub 流式读取在这里行得通，靠的正是第 2 步的分片布局：一个 batch 变成对大分片的几次字节范围读取，而不是上千次小请求。LeRobot 的 `StreamingLeRobotDataset` 把它变成一个即插即用的 torch iterable，Strands Robots 通过 `stream_dataset()` 暴露它：

**图 3。** *流式，而不是下载。下载路径先把整个数据集复制到本地磁盘，GPU 只能等待；* `stream_dataset()` *直接从 bucket 读取 batch，本地磁盘上不落任何东西，GPU 从第一个 batch 就能开始训练。*

```
reader = sim.stream_dataset("my-org/robot-fave/cube_pick", repo_type="bucket",
    shuffle=False, max_num_shards=1, buffer_size=1,  # one episode, in capture order
)

print(reader.num_episodes, reader.num_frames, reader.fps)
for frame in reader:
    frame["observation.images.front"]   # (3, H, W) tensor, decoded on the fly from the MP4 shard
    frame["observation.state"]           # joint vector, from the Parquet shard
    frame["action"]
    break
```

除了包含 schema、统计信息和 episode 索引的小型 `meta/` 目录，没有任何东西落到本地磁盘。相机帧在你迭代时从远端 MP4 分片解码；state 和 action 来自 Parquet 分片。上面这个循环一次只读一帧，适合查看某个 episode。要训练，把 reader 传给 `DataLoader` 按 batch 迭代。流式数据集通过一个有界的 reservoir 缓冲在内部做 shuffle，因此视频解码可以在多个 worker 进程间并行，而训练步骤本身就是普通的 PyTorch 循环：

```
# policy here is a LeRobot policy you constructed, such as ACTPolicy.
for batch in reader.dataloader(batch_size=64, num_workers=4):
    loss, _ = policy(batch)   # lerobot ACTPolicy.forward returns (loss, loss_dict)
    loss.backward()
```

如果你根本不想写这个循环，LeRobot 自家的 trainer 也通过同一个引擎读取，你的代理采集的数据集不需要一行新代码就能训练。它用与进程内 reader 相同的关键字参数接收 bucket：

```
lerobot-train --policy.type=act \
  --dataset.repo_id=my-org/robot-fave/cube_pick \
  --dataset.repo_type=bucket \
  --dataset.streaming=true \
  --num_workers=4
```

bucket 只支持流式，因此 `--dataset.repo_type=bucket` 必须搭配 `--dataset.streaming=true`，否则配置会拒绝这个组合。当你想在自己进程里拿到这个循环时再用 `stream_dataset()`：验证一个 episode、在仿真中回放它，或喂给自定义评估循环。如果只想流式读取本体感知数据，`drop_videos=True` 会完全跳过视频解码，这也是它能在没有 `torchcodec` wheel 的边缘设备上工作的原因。[录制与数据集指南](https://strands-labs.github.io/robots/recording/)记录了该参数及其必需的 `delta_timestamps` map。

运行策略和训练策略共用 provider 名字。`create_trainer("lerobot_local")` 返回一个用法类似 `create_policy()` 的 `Trainer`，一个 [`TrainSpec`](https://strands-labs.github.io/robots/recording/) 描述这次训练运行；于是录制-训练-部署循环几行就能闭环：

```
import os
os.environ["STRANDS_TRUST_REMOTE_CODE"] = "1"   # create_policy loads with trust_remote_code=True

from strands_robots import create_policy
from strands_robots.training import TrainSpec, create_trainer

trainer = create_trainer("lerobot_local", device="cuda")
spec = TrainSpec(dataset_root="/tmp/cube_pick", output_dir="/tmp/cube_pick_ft",
                 base_model="", steps=500, extra={"policy_type": "act"})
result = trainer.train(spec)                    # train ACT on the streamed dataset
policy = create_policy(result.checkpoint_dir)   # load the checkpoint straight back
```

在单块 NVIDIA L4（`g6.4xlarge`）上，对一个 120 帧的 episode 跑 500 个优化步的 [ACT](https://tonyzhaozh.github.io/aloha/)（5,160 万参数，有效 batch size 8）耗时 133 秒，写出的 checkpoint 可以由 `create_policy()` 通过运行任何其他策略的同一入口直接加载。训练时间随数据集大小、batch size 和步数变化，请把它当作一个实测配置而非基准。`"groot"` 和 `"cosmos3"` provider 面向同样的 `TrainSpec` 和 `Trainer` 生命周期，因此外围循环不变；每个 provider 会先校验自己必需的字段——GR00T 运行需要 `base_model` 和 `embodiment` 标签，Cosmos 3 运行需要 `base_model` 和一份 SFT 配方。在 `train()` 之前调用 `trainer.validate(spec)`，它会精确返回某个后端缺少的字段列表。

Hugging Face 的预加热（pre-warming）缓存会把 bucket 数据放到靠近你作业运行所在云和区域的边缘节点，于是你的集群就近读取，dataloader 始终跑在 GPU 前面。在 Hugging Face 的 [bucket 基准测试](https://huggingface.co/spaces/h-m-t/hf-buckets-benchmark)中，在 `us-east-1` 的 `m5dn.24xlarge` 上实测：10 GB 载荷经温暖的 CDN 读取约 1,086 MB/s（冷缓存为 780 MB/s），100 GB 时约 1,124 MB/s。与普通对象存储的完整对比（上传和下载）都在那个 dashboard 上。选择数据存放地点是 Team 和 Enterprise 套餐上的 [Storage Regions](https://huggingface.co/docs/hub/en/storage-regions) 设置，截至本文撰写支持美国和欧盟，已宣布亚太地区与海湾合作委员会（GCC）区域即将加入；这些套餐之外的仓库存于美国。

在 macOS 上，`import strands_robots` 会自动把 Homebrew 的 `ffmpeg` 加进 loader 路径，因此 `torchcodec` 无需额外配置就能解码流式视频。

## 第 4 步 - 部署策略并让数据回到循环

在这一步，你拿着刚训练好的 checkpoint，在物理机器人上运行它，并用它录制下一轮演示。这就是[第一篇](https://huggingface.co/blog/amazon/strands-lerobot-hub-to-hardware)里的同一份代理代码，只把一个关键字参数改成 `mode="real"`：

```
robot = Robot("so100", mode="real", port="/dev/ttyACM0",
              cameras={"front": {"type": "opencv", "index_or_path": "/dev/video0", "fps": 30}})
agent = Agent(tools=[robot])
agent("Pick up the red cube.")
```

checkpoint 跑在真实的机械臂上，而这台机械臂录下的演示会以你起步时同样的 LeRobot 格式保存到磁盘，随时可以同步回 bucket 供下一轮训练。

如果你的数据已经在 [Amazon Simple Storage Service（Amazon S3）](https://aws.amazon.com/s3/)上，本文所有的格式工作都不必改变。LeRobotDataset 就是一个由 Parquet 和 MP4 分片组成的目录，存到 Amazon S3 与存在别处一样，录制、训练和部署各步骤无论在哪儿都能读取这种格式。bucket 增加的是 Hub 原生路径：`sync_dataset_to_bucket` 和 `stream_dataset(repo_type="bucket")` 直接面向 `hf://`，于是你拿到同步和流式读取，不必接线一条单独的存储路径。两条路径跑的是同一个循环：数据本来就在那里就用 Amazon S3，想要不先开通存储就能同步和流式读取，就用 bucket。

明天再跑一遍这个循环，你就已经在向那个 bucket 录制、只同步发生变化的字节，并把这些字节流式喂给 GPU 而不必等下载。数据从未离开 LeRobot 格式，也从未离开 Hub。

## 安全考量

这里的代码片段只是 Strands Robots 数据循环的"hello world"。当你用真实数据跑起来后，有五件事会发生变化。

- **Prompt 注入。** 向代理供给不可信数据可能导致 prompt 注入——不可信的上下文被当成 LLM 指令执行。这些代理会驱动机器人，现在还读写共享存储，因此这是必须跟踪的重要风险。只向代理喂来自可信来源的数据。如果无法保证所有输入可信，就限制代理可用的工具，使其不能执行安全关键动作或覆盖 bucket 内容。
- **训练数据是一个信任边界。** 能写入采集 bucket 的代理，也能写出某个策略随后要用于训练的 episode，而那个策略驱动着一条物理机械臂。把写入采集数据的凭证与训练作业读取用的凭证分开；每次 run 用自己的 `run_id` 同步，使每个 episode 都能追溯到产生它的 run 并能单独移除；把带版本管理的数据集仓库当作经过审查的产物，因为 bucket 不保留可供审计的修订版本。
- **Bucket 凭证与作用域。** `sync_dataset_to_bucket(...)`、`stop_recording(bucket=...)` 和 `sync_to_bucket` 通过 `hf` CLI 上传，使用 `hf auth login` 的 token。请使用限定到具体命名空间的 token；采集数据优先使用 `--private` bucket；并保持 bucket 与你 `push_to_hub` 并共享的带版本管理数据集仓库相区分。
- **就地覆盖不保留修订。** bucket 就地覆盖且不保留修订版本，这既使它成为合适的工作层，也意味着重复的 `run_id` 会替换已存放在那里的 run。为每次采集活动传入显式的 `run_id`，如 `sync_dataset_to_bucket("./recordings", "my-org/robot-fave", run_id="run-021")`。凡是你需要能回滚到的内容，`push_to_hub()` 到带版本管理的数据集仓库——那里每个修订都会被保留。
- **只使用可信的 Hugging Face 组织。** 本地推理路径以 `trust_remote_code=True` 加载 Hugging Face 模型。设置 `STRANDS_TRUST_REMOTE_CODE=1` 选择启用，且只从你信任的组织加载 checkpoint。从 Hub 加载预训练权重时（例如通过 `pretrained_name_or_path`），先确认组织可信再加载。模型权重可能携带任意代码（基于 pickle 的 checkpoint）。尽可能优先选择 safetensors 格式的 checkpoint。

## 清理

这个循环会留下一个 bucket、`/tmp` 下的数据集和磁盘上的 checkpoint。bucket 内容会计入你的存储量，请删除不再需要的东西：

```
hf buckets rm my-org/robot-fave/cube_pick/ --recursive --dry-run  # lists, removes nothing
hf buckets rm my-org/robot-fave/cube_pick/ --recursive            # --yes skips the prompt
hf buckets delete my-org/robot-fave                               # takes everything in it
rm -rf /tmp/cube_pick /tmp/cube_pick_ft /tmp/nb5_dataset /tmp/nb5_ft
```

停掉任何仍占用 GPU 实例的训练进程，并停止该实例。如果你跑的是 notebook，把其中的 `RUN_ID`（默认为 `nb5_demo`）替换进 `cube_pick` 的位置。凡是用 `push_to_hub()` 发布过的内容都在带版本管理的仓库里，不受影响。

## 下一步去向

[Strands Robots 文档](https://strands-labs.github.io/robots/)深入介绍机器人目录、仿真、策略 provider、录制和网格。[录制与数据集指南](https://strands-labs.github.io/robots/recording/)完整记录了 `DatasetRecorder` API、`sync_dataset_to_bucket` / `sync_to_bucket` 和 `stream_dataset`。

如果你从多台机器人采集，给每台一个自己的 `run_id`，它们就会并行写入同一个 bucket。[多机器人网格](https://strands-labs.github.io/robots/mesh/)把一个代理扇出到这些机器人，于是同一个循环变成一支白天持续采集、写入共享存储的舰队。流式 reader 一次读一个 run。[录制与数据集指南](https://strands-labs.github.io/robots/recording/)描述了如何跨多个 run 训练。

如果你想要比 ACT 更大的策略，第 3 步的 `TrainSpec` 和 `Trainer` 生命周期以各自的 provider 名覆盖 GR00T 和 Cosmos 3，因此在你刚流式读取的数据集上微调一个 VLA，只是同样的调用换一个 provider 字符串并指定 base model。运行结果的部署路径开始分叉：VLA checkpoint 要部署到硬件，而不是你训练时用的仿真器。若要用更重的仿真生成这些数据，Newton（`sim-newton`）和 Isaac Sim（`isaac`）后端位于同一个 `Robot()` 工厂背后，随着规模增长代理代码不变。

bucket 流式读取由 Strands Robots 与 LeRobot 两个团队共同贡献，直接上游进了 LeRobot 本体，所以你的代理采集的数据集能被该生态里的每个工具读取。这也是双向的：第 3 步的 reader 可以打开 Hub 上已发布的任何 LeRobot 数据集，因此代理在录制自己的演示之前，可以先针对既有演示做回放和评估。

欢迎在 Apache 2.0 下贡献代码。如果你用这个循环构建了什么东西，请开个 issue 告诉我们哪里好用、哪里不好用。
