在长序列上训练大语言模型，已成为构建有能力的 AI 系统的必备能力。随着模型越来越多地用于文档分析、代码理解、复杂推理和 RAG 负载等任务，处理数十万乃至数百万 token 序列的需求急剧增长。打个比方，一本普通书大约 25 万 token，所以在多文档上下文或整本书长度的输入上训练，需要处理的序列远超单块 GPU 所能容纳。然而用这样长的上下文训练会带来显著的内存挑战：注意力计算的开销随序列长度平方增长，对超过数万 token 的上下文很快就会超出 GPU 显存。

Ulysses 序列并行（属于 Snowflake AI Research 的 [Arctic Long Sequence Training（ALST）协议](https://huggingface.co/papers/2506.13996) 的一部分）通过注意力头并行把注意力计算分布到多块 GPU 上，提供了一个优雅的解法。在本文里，我们将探索 Ulysses 如何工作、以及它如何被集成进 Hugging Face 生态——从 Accelerate 到 Transformers Trainer 再到 TRL 的 SFTTrainer。

## 长序列训练的挑战

transformer 里的注意力机制随序列长度平方增长。对一个长度为 n n n 的序列，标准注意力需要 O(n2) O(n^2) O(n2) FLOPs 和 O(n2) O(n^2) O(n2) 内存来计算并存储注意力分数矩阵。像 [FlashAttention](https://huggingface.co/papers/2205.14135) 这样的优化实现通过分块计算、从不实体化完整注意力矩阵，把 **内存** 降到 O(n) O(n) O(n)——但 O(n2) O(n^2) O(n2) 的计算仍在。对超长序列（32k+ token），即便有 FlashAttention，训练仍会把单 GPU 显存逼到极限。

看看这些必须做长上下文训练的场景：

- **文档理解**：处理整本书、法律文件或研究论文
- **代码分析**：理解含多个互联文件的大型代码库
- **推理任务**：模型"分步思考"可能在推理时生成数千 token
- **检索增强生成**：把大量检索到的段落纳入上下文

传统数据并行在这里帮不上忙——每块 GPU 在注意力块内仍需处理完整序列。我们需要一种把序列本身切分到多个设备上的方式。

## Ulysses 如何工作

Ulysses 序列并行（SP），在 [DeepSpeed Ulysses 论文](https://huggingface.co/papers/2309.14509) 中提出，采用了一个巧妙的做法：除了沿序列维度切分，它还把注意力头分配到各 GPU 上。

Ulysses 沿序列维度切分输入序列，并用 all-to-all 通信交换键值对，让每块 GPU 计算注意力头的一个子集。（

来源：

Snowflake 工程博客

）

工作原理如下：

- **序列分片**：输入序列沿序列维度在 P P P 块 GPU 上切分。每块 GPU i i i 持有 token [i⋅n/P,(i+1)⋅n/P) [i \cdot n/P, (i+1) \cdot n/P) [i⋅n/P,(i+1)⋅n/P)。
- **QKV 投影**：每块 GPU 为它本地的序列块计算查询、键和值投影。
- **All-to-All 通信**：一次 all-to-all 集合操作重新分配数据，使每块 GPU 在投影之后持有 *所有* 序列位置，但只针对注意力头的一个子集。
- **本地注意力**：每块 GPU 用标准注意力机制（FlashAttention 或 SDPA）为其分配到的头计算注意力。
- **All-to-All 通信**：另一次 all-to-all 操作反转这次重新分配，回到序列分片格式。
- **输出投影**：每块 GPU 为它本地的序列块计算输出投影。

关键洞察在于注意力头彼此独立——每个头可以单独计算。通过把序列局部性换成头局部性，Ulysses 以相对较低的通信开销实现了高效并行。

### 通信复杂度

Ulysses 每个注意力层需要两次 all-to-all 操作，每块 GPU 的总通信量为 O(n⋅d/P) O(n \cdot d / P) O(n⋅d/P)，其中：

- n n n 是序列长度
- d d d 是隐藏维度
- P P P 是并行度

Ring Attention 每块 GPU 通信 O(n⋅d) O(n \cdot d) O(n⋅d)——多了 P P P 倍——通过沿环的 P−1 P-1 P−1 次顺序点对点传输。Ulysses 还受益于更低的延迟，因为 all-to-all 能在单个集合步骤里利用全部二分带宽，而 Ring Attention 在 P−1 P-1 P−1 跳上串行。

## 与 Accelerate 集成

Accelerate 通过其 [`ParallelismConfig`](https://huggingface.co/docs/accelerate/concept_guides/sequence_parallelism#alstulysses-sp-backend-configuration) 类和 DeepSpeed 集成，为 Ulysses 序列并行打下基础。

### 配置

```
from accelerate import Accelerator
from accelerate.utils import ParallelismConfig, DeepSpeedSequenceParallelConfig

parallelism_config = ParallelismConfig(
    sp_backend="deepspeed",
    sp_size=4,  # Split across 4 GPUs
    dp_shard_size=1,  # Must satisfy: dp_replicate × dp_shard × sp_size = num_processes
    sp_handler=DeepSpeedSequenceParallelConfig(
        sp_seq_length=None,  # None for variable-length sequences
        sp_seq_length_is_variable=True,
        sp_attn_implementation="flash_attention_2",  # or "sdpa"
    ),
)

accelerator = Accelerator(parallelism_config=parallelism_config)
```

### 关键参数

| 参数 | 说明 |
| --- | --- |
| `sp_size` | 用于序列并行的 GPU 数量 |
| `sp_backend` | Ulysses 必须设为 `"deepspeed"` |
| `sp_seq_length_is_variable` | 各批次序列长度不同则设为 `True` |
| `sp_attn_implementation` | `"flash_attention_2"`、`"flash_attention_3"` 或 `"sdpa"` |

### 使用 Accelerator

当你调用 `accelerator.prepare()` 时，Ulysses 会自动设置好：

```
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.1-8B")
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-5)

# This registers the model with Ulysses and wraps the dataloader
model, optimizer, dataloader = accelerator.prepare(model, optimizer, dataloader)
```

`prepare()` 调用会：

- 把模型注册到 DeepSpeed 的 `UlyssesSPAttentionHF`
- 用 `UlyssesSPDataLoaderAdapter` 包装数据加载器以处理序列分片
- 自动注入 `shift_labels` 以保证损失计算正确

### 损失聚合

用 Ulysses 时，每块 GPU 在序列的不同部分计算损失。损失必须按每个 rank 的有效 token 数加权地正确聚合。如果你用 Transformers 的 `Trainer` 或 TRL 的 `SFTTrainer`，这会自动处理——下面这段代码只在你写自定义 Accelerate 训练循环时才需要：

```
sp_size = parallelism_config.sp_size
if sp_size > 1:
    from deepspeed.utils import groups

    sp_group = groups._get_sequence_parallel_group()

    # Gather losses and token counts from all SP ranks
    losses_per_rank = torch.distributed.nn.functional.all_gather(loss, group=sp_group)
    good_tokens = (batch["shift_labels"] != -100).view(-1).sum()
    good_tokens_per_rank = torch.distributed.nn.functional.all_gather(good_tokens, group=sp_group)

    # Weighted aggregation
    total_loss = sum(
        losses_per_rank[i] * good_tokens_per_rank[i]
        for i in range(sp_size)
        if good_tokens_per_rank[i] > 0
    )
    loss = total_loss / max(sum(good_tokens_per_rank), 1)

accelerator.backward(loss)
```

> 加权损失聚合确保在 token 不均衡地分布到各 rank 时（例如某些 rank 只含 padding 或被掩码的提示 token）梯度仍正确。

> Ulysses 和 Ring Attention 在训练期间都用 position_ids 而非 attention_mask 做因果掩码。在这些序列长度上，一个 4D 注意力掩码会和注意力分数本身一样令人却步——在 128k token 时那是又一个约 1TB 的张量。Position IDs 用 O(n) O(n) O(n) 内存实现同样的因果行为，而不是 O(n2) O(n^2) O(n2)。在评估/推理期间，DeepSpeed 的 SP 注意力层可以完全绕过 SP 操作（通过 disable_in_eval）并回退到模型的默认注意力实现。

## 与 Transformers Trainer 集成

Transformers 的 [`Trainer`](https://huggingface.co/docs/transformers/main_classes/trainer) 通过 [`TrainingArguments.parallelism_config`](https://huggingface.co/docs/transformers/main_classes/trainer#transformers.TrainingArguments.parallelism_config) 提供无缝的 Ulysses 集成。它自动处理所有 SP 相关细节——数据加载器包装、序列分片和损失聚合——所以你不需要写上面那段自定义损失代码。

### 配置

只要把上面同样的 `parallelism_config` 传进 `TrainingArguments`：

```
from transformers import TrainingArguments

training_args = TrainingArguments(
    parallelism_config=parallelism_config,  # same ParallelismConfig as above
    per_device_train_batch_size=1,
)
```

### Trainer 自动处理的事项

- **数据加载器包装**：模型准备之后，Trainer 用 `UlyssesSPDataLoaderAdapter` 包装数据加载器
- **损失计算**：`compute_loss` 方法检测 SP 模式并路由到专门的 `_deepspeed_sp_compute_loss`，它负责：跨 SP rank 收集损失、计算每个 rank 的有效 token 数、加权损失聚合
- **批大小计算**：有效数据并行 world size 会考虑 SP：`dp_world_size = world_size // sp_size `
- **数据加载器长度调整**：训练步数计算会针对 SP 对迭代次数的影响做调整

### 启动命令

用一个 accelerate 配置文件或命令行参数：

```
accelerate launch \
    --config_file deepspeed_ulysses.yaml \
    train.py \
    --per_device_train_batch_size 1
```

## 与 TRL SFTTrainer 集成

TRL 的 [`SFTTrainer`](https://huggingface.co/docs/trl/sft_trainer) 建立在 Transformers Trainer 之上，并为长序列的监督微调加了专门的优化。

### 配置

```
from trl import SFTConfig, SFTTrainer
from accelerate.utils import ParallelismConfig, DeepSpeedSequenceParallelConfig

parallelism_config = ParallelismConfig(
    sp_backend="deepspeed",
    sp_size=2,
    dp_shard_size=2,  # 2D parallelism: SP × DP = 4 GPUs
    sp_handler=DeepSpeedSequenceParallelConfig(
        sp_seq_length_is_variable=True,
        sp_attn_implementation="flash_attention_2",
    ),
)

training_args = SFTConfig(
    ...,
    parallelism_config=parallelism_config,
    max_length=32768,
    pad_to_multiple_of=2,  # Must equal sp_size
    per_device_train_batch_size=1,
)

trainer = SFTTrainer(
    model=model,
    args=training_args,
    train_dataset=dataset,
)
trainer.train()
```

### 用于 Ulysses 的关键 SFTConfig 参数

| 参数 | 说明 |
| --- | --- |
| `pad_to_multiple_of` | 必须等于 `sp_size` 以确保序列可整除 |
| `max_length` | 全局序列长度（在切分到各 GPU 之前） |
| `packing` | 与 SP 配合良好——打包减少 padding 浪费，尤其对变长序列 |

### Accelerate 配置文件

创建 `alst_ulysses_4gpu.yaml`：

```
compute_environment: LOCAL_MACHINE
distributed_type: DEEPSPEED
mixed_precision: bf16
num_processes: 4
deepspeed_config:
  zero_stage: 3
  seq_parallel_communication_data_type: bf16
parallelism_config:
  parallelism_config_sp_size: 2
  parallelism_config_sp_backend: deepspeed
  parallelism_config_dp_shard_size: 2
  parallelism_config_sp_seq_length_is_variable: true
  parallelism_config_sp_attn_implementation: flash_attention_2
```

### 完整训练命令

```
accelerate launch --config_file alst_ulysses_4gpu.yaml \
    trl/scripts/sft.py \
    --model_name_or_path meta-llama/Llama-3.1-8B \
    --dataset_name trl-lib/Capybara \
    --max_length 32768 \
    --packing \
    --pad_to_multiple_of 2 \
    --per_device_train_batch_size 1
```

### Shift Labels 处理

启用 Ulysses 时，SFTTrainer 会自动处理预先偏移的标签：

```
# When using SP, labels are pre-shifted by the dataloader adapter
# The trainer detects this and uses shift_labels directly
labels = inputs["labels"] if "shift_labels" not in inputs else None

# Loss computation uses the pre-shifted labels
if "shift_labels" in inputs:
    shift_logits = outputs.logits.contiguous()
    shift_labels = inputs["shift_labels"]
else:
    shift_logits = outputs.logits[..., :-1, :].contiguous()
    shift_labels = labels[..., 1:].contiguous()
```

## 对比 Ulysses 与 Ring Attention

Ulysses 和 Ring Attention 都能实现长上下文训练，但特性不同：

| 方面 | Ulysses（DeepSpeed） | Ring Attention（FSDP2） |
| --- | --- | --- |
| **并行方法** | 注意力头划分 | 基于环的 KV 交换 |
| **后端** | DeepSpeed ZeRO | PyTorch FSDP2 |
| **注意力支持** | FlashAttention 2/3、SDPA | 仅 SDPA |
| **通信** | 每层两次 `all-to-all` | P2P 环通信 |
| **每 GPU 通信量** | O(total_seq x hidden / sp_size) | O(total_seq x hidden) |
| **序列可整除性** | `sp_size` | `cp_size * 2` |
| **头数约束** | `num_heads >= sp_size` | 无 |

### 何时选 Ulysses 还是 Ring Attention

由于两者之间切换只需改 accelerate 配置，我们建议在你具体环境上两种都试试，比较性能和内存占用。主要约束是 Ulysses 要求 `num_heads >= sp_size`，而 Ring Attention 没有这个限制。

## 最佳实践

### 1. 序列长度可整除性

始终确保序列长度能被 `sp_size` 整除：

```
training_args = SFTConfig(
    pad_to_multiple_of=4,  # For sp_size=4
    max_length=32768,  # Must be divisible by 4
)
```

### 2. 使用 Flash Attention

Flash Attention 2 比 SDPA 输出更干净、性能更好：

```
parallelism_config = ParallelismConfig(
    sp_handler=DeepSpeedSequenceParallelConfig(
        sp_attn_implementation="flash_attention_2",
    ),
)
```

在 Hopper 上用 Flash Attention 3，并留意为 Blackwell 发布的 Flash Attention 4（FA2 在 Blackwell 上相当慢）。

### 3. 与 DeepSpeed ZeRO 结合

对非常大的模型，把 Ulysses 与 ZeRO Stage 3 结合：

```
deepspeed_config:
  zero_stage: 3
  offload_optimizer:
    device: cpu
```

如果模型巨大，你还可以把参数也卸载出去，在上面加：

```
  offload_param:
    device: cpu
```

### 5. 使用对内存碎片友好的 PyTorch 分配器

这个环境变量能让你用更长的序列长度：

```
export PYTORCH_ALLOC_CONF=expandable_segments:True
```

### 6. 二维并行配置

为你的 GPU 数量平衡 SP 和 DP：

| GPU 数 | `sp_size` | `dp_shard_size` | 用例 |
| --- | --- | --- | --- |
| 4 | 2 | 2 | 吞吐与序列长度均衡 |
| 4 | 4 | 1 | 最大序列长度 |
| 8 | 2 | 4 | 中等序列长度下更高吞吐 |
| 8 | 4 | 2 | 中等吞吐下更长序列 |

记住：`dp_replicate_size × dp_shard_size × sp_size = num_processes`

### 7. Liger-Kernel

如果你想要的模型架构被 [Liger-Kernel](https://github.com/linkedin/Liger-Kernel) 支持，它与 Ulysses SP 完全兼容，可用一个标志启用：

```
training_args = SFTConfig(
    use_liger_kernel=True,
)
```

主要的内存节省来自 `FusedLinearCrossEntropy`，它避免了在损失计算时实体化完整的 logits 张量。在更长的序列、logits 张量更大的情况下节省更多。

此外，你可以启用 [`TiledMLP`](https://www.deepspeed.ai/tutorials/ulysses-alst-sequence-parallelism/#tiled-mlp-computation) 以进一步延长序列长度——和 `FusedLinearCrossEntropy` 一样，它通过分块大矩阵运算来节省工作内存。

### 8. 各 rank 间的 token 分布

你不必手动把 token 均衡到各 SP rank——损失聚合代码能优雅地处理不均衡分布（包括有效 token 为零的 rank）。在一个合理规模的数据集上随机分批，分布在训练中会在统计上趋于均衡。

## 基准

为量化 Ulysses SP 的收益，我们用 TRL 的 SFTTrainer 在 [Gutenberg English](https://huggingface.co/datasets/sedthh/gutenberg_english) 流式数据集上训练 [Qwen3-4B](https://huggingface.co/Qwen/Qwen3-4B)。所有实验在 H100 80GB GPU 上运行，使用 DeepSpeed ZeRO-3、CPU 优化器卸载、梯度检查点，注意力后端为 flash-attn2。

### 设置

| 配置 | GPU 数 | SP | DP | 序列长度 | Grad Acc | 全局批大小 |
| --- | --- | --- | --- | --- | --- | --- |
| 基线 | 1 | 1 | 1 | 8K | 8 | 8 |
| SP=4 | 4 | 4 | 1 | 8K | 8 | 8 |
| SP=4 | 4 | 4 | 1 | 32K | 8 | 8 |
| SP=4 | 4 | 4 | 1 | 64K | 8 | 8 |
| SP=4 | 4 | 4 | 1 | 96K | 8 | 8 |

上表中的基准运行使用相同的全局批大小（8 个微批）、余弦学习率调度和种子，因此这些损失的曲线可直接比较。

### 损失曲线匹配诊断（4 GPU）

为验证 SP 与 DP 的损失等价性，我们在相同种子、模型、优化器、学习率调度和数据顺序下做了受控的 4-GPU A/B 实验。

#### 公平 DP vs SP 比较的方法

比较的设置：

- `DP=4, SP=1, GAS=1`（基线）
- `DP=1, SP=4, GAS=4`（Ulysses SP）

为了公平比较，`GAS` 必须随 `SP` 缩放：

- Ulysses SP 把序列分到 `SP` 个 rank，所以每个 SP rank 每个微步大约只看到 `1/SP` 的序列 token。
- 如果 `GAS` 不变，SP 中每个优化器步聚合的总 token 会少于 DP 基线。
- 设置 `GAS=SP` 能保持每个优化器步的有效 token 数匹配：DP tokens/step：`dp_world_size * micro_batch * seq_len * GAS = 4 * B * L * 1` SP tokens/step：`dp_world_size * micro_batch * (L/SP) * GAS * SP_ranks = 1 * B * (L/4) * 4 * 4 = 4 * B * L`

在 Gutenberg 文本上（20 步），规范损失在

DP=4,SP=1,GAS=1

和

DP=1,SP=4,GAS=4

之间在日志精度内匹配。

在受控等价性测试台上，4 GPU 跑 20 步实测：

| 测试台 | 指标 | DP vs SP 设置 | 平均绝对差 | 最大绝对差 |
| --- | --- | --- | --- | --- |
| `Trainer` | `loss` | DP=4, SP=1 vs DP=1, SP=4 | 0.0054 | 0.0131 |
| `SFTTrainer` | 日志 `loss` | DP=4, SP=1 vs DP=1, SP=4 | 0.0811 | 0.0812 |
| `SFTTrainer` | 规范 NLL | DP=4, SP=1 vs DP=1, SP=4 | 0.000004 | 0.000005 |

结论：在匹配的 token 预算下，SP 与非 SP 在规范 token 归一化损失上匹配。剩余差异在 trainer 报告的日志（`loss`）上，而非底层交叉熵目标。

### 内存降低

在相同序列长度下，SP=4 把每 GPU 内存降低到 1/3.3，从而能在 4× H100 80GB 上训练到 96K token。在 128K 时模型 OOM。

| 配置 | 序列长度 | 峰值内存 | 备注 |
| --- | --- | --- | --- |
| DP=4（4 GPU） | 8K | 22.4 GB | 基线——无 SP |
| SP=4（4 GPU） | 8K | 22.8 GB | 相同序列长度下内存相近 |
| SP=4（4 GPU） | 32K | 35.0 GB | 比 DP 基线长 4 倍 |
| SP=4（4 GPU） | 64K | 50.5 GB | 比 DP 基线长 8 倍 |
| SP=4（4 GPU） | 96K | 66.0 GB | **比 DP 基线长 12 倍** |
| SP=4（4 GPU） | 128K | OOM | 超过 80 GB 限制 |

在 8K token 时，DP=4 和 SP=4 每 GPU 用差不多内存（用 ZeRO-3 约 22 GB）。SP 的优势在于它扩展到长得多的序列：在 96K token（长 12 倍）时，峰值内存为 66 GB——仍在 H100 的 80 GB 容量内。到 128K 时模型 OOM，确立了该配置的实际上限。不带 SP 的 DP=4 对这个模型无法超过 8K。

### 吞吐

用 SP 的更长序列能显著处理更多 token/秒。64K 下的 SP=4 达到了基线 3.7 倍的吞吐。

| 配置 | 序列长度 | Tokens/s | vs 基线 |
| --- | --- | --- | --- |
| 基线（1 GPU） | 8K | 3,633 | — |
| SP=4（4 GPU） | 8K | 3,933 | ~1x |
| SP=4（4 GPU） | 32K | 7,733 | **2.1x** |
| SP=4（4 GPU） | 64K | 13,396 | **3.7x** |

在相同序列长度（8K）下，SP=4 与单 GPU 基线吞吐相当——在 NVLink 互联的 GPU 上 all-to-all 通信开销很小。真正的收益来自更长序列：随着序列长度增长，平方级的注意力计算会在通信和其他开销之上占据主导，使每一步训练越来越高效。每一步也处理按比例更多的 token，所以吞吐随序列长度扩展。在 64K 时，SP=4 处理 13,396 token/秒——是基线的 3.7 倍。

> 这些结果只用 4 块 GPU、SP=4。用 8 块 GPU（SP=8）你可以推到更长的序列——最高 256K+ token——或者用二维并行（SP=4, DP=2）把长上下文训练与数据并行吞吐结合起来。
