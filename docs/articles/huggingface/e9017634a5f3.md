随着 Arm 近期[发布 SME2](https://newsroom.arm.com/blog/arm-sme2-android-mobile-apps)，[Arm KleidiAI](https://www.arm.com/products/development-tools/embedded-and-software/kleidi-libraries) 的角色愈发清晰：它就是 Arm 面向下一波 AI 的加速器层。通过嵌入 XNNPack、[MediaPipe](https://newsroom.arm.com/blog/kleidiai-integration-mediapipe)、[MNN](https://newsroom.arm.com/blog/arm-kleidi-alibaba-mnn-framework-multimodal-ai)、[ONNX Runtime](https://newsroom.arm.com/blog/arm-microsoft-kleidiai-onnx-runtime) 乃至 llama.cpp 等广泛使用的 Edge AI 框架，KleidiAI 在开发者无需改动任何代码的情况下带来了显著的[性能提升](https://newsroom.arm.com/blog/stability-ai-arm-kleidi-text-to-audio-generation)。这一基础直接通向下即将发布的 ExecuTorch 0.7 beta——届时 KleidiAI 将默认启用——为基于最新 Arm CPU 架构的设备，以及庞大的基于较早代际设备存量，带来自动加速。

Android 与跨平台开发者——无论第一方还是第三方——都能通过 ExecuTorch 和 XNNPack 即时获得 KleidiAI 的 AI 性能优化。结果是什么？更快的模型启动、更低的延迟、更精简的内存占用——而且没有集成障碍。过去需要定制调优才能得到的东西，如今是开箱即用的性能。这种效率解锁了新的可能——不仅面向最新的高端设备，也面向远为广泛的硬件。

说到在移动设备上运行生成式 AI（GenAI），我们很容易想到那些搭载强大 CPU、GPU 和 NPU 的最新旗舰智能手机。但如果我们告诉你，像运行大语言模型（LLM）这样的 GenAI 体验也能带到 3 年、4 年甚至 5 年前的设备上呢？甚至带到大树莓派——Raspberry Pi 5 上呢？

这已经不再只是愿景，而是切实的现实。这要归功于 Arm 的 SDOT CPU 特性——它自 2015 年起就已存在于 Arm CPU 中。

# 什么是 SDOT？

SDOT（Signed Dot Product，有符号点积）指令引入于 Armv8.2 架构及其后续 CPU，能够对 8-bit 有符号整数向量执行高效的点积运算。下图展示了 Arm CPU 上这样一条 SDOT 指令的行为：[![image/png](https://cdn-uploads.huggingface.co/production/uploads/6682a9252200824e2ddc667f/guiinfFqKwgqUAz6UFS6R.png)](https://cdn-uploads.huggingface.co/production/uploads/6682a9252200824e2ddc667f/guiinfFqKwgqUAz6UFS6R.png)

如上图所示，该指令产生四个 32-bit 整数输出，每个输出都来自左操作数（LHS）与右操作数（RHS）向量寄存器中对应四人一组的 int8 元素的点积。

在使用 Int8 或更低精度格式（如 Int4）时，这条指令可以用来加速矩阵乘法例程——每一个 LLM 背后的核心计算负载。这类运算通常涉及大量点积：左矩阵的每一行与右矩阵对应的列逐对做点积。

SDOT 指令已经在极为多样的设备上获得广泛支持，为 GenAI 用例触达远为庞大的手机人群打开了大门。截至目前，约 30 亿台基于 Arm 的设备中的 Arm CPU 已具备这一能力——让大多数用户都能获得强大的设备端 GenAI 体验。事实上，如今 72% 的设备都支持这条指令。

多亏 ExecuTorch，我们现在能让 Llama 3.2 这类模型在多数 Android 设备以及 Raspberry Pi 5 等边缘设备上高效运行。

# KleidiAI + ExecuTorch：把一切聚合起来

在去年量化版 Llama 3.2 1B 的发布中，ExecuTorch 与 KleidiAI 团队合作，利用自 Armv8.6 架构起提供的 I8MM 特性，为 Arm CPU 上的 Int4 矩阵乘法做了优化。正如此前一篇博客所述，在 Galaxy S24+ 上，带 KleidiAI 的 ExecuTorch 的 prefill 性能比不带 KleidiAI 的内核高出 20% 以上。

换算下来，prefill 阶段超过每秒 350 个 token，decode 阶段超过每秒 40 个 token。这样的性能足以支撑设备端任务，例如总结未读消息——仅用 Arm CPU 就能带来流畅的用户体验。作为参照，总结约 50 条未读消息通常需要处理大约 600 个 token。

今年，ExecuTorch 与 KleidiAI 团队的重点是利用 SDOT 指令优化 Int4 矩阵乘法性能，以推动更广泛的采用。

[查看 GitHub 上的 XNNPack PR](https://github.com/google/XNNPACK/pull/8604)

虽然只有 SDOT 扩展的 Arm CPU 上的 LLM 性能比不上最新旗舰智能手机，但它依然能支撑令人印象深刻的设备端生成式 AI 能力。事实上，在很多场景里，decode 阶段的速度比人类的平均阅读速度还快——这说明即便是较早的 Arm CPU 也能支撑实用而有意义的 GenAI 用例。

例如，与语音转文本和文本转语音模型组合后，这样的本地 LLM 可以打造完全私密的智能助手：全程离线运行，免除数据隐私之忧，同时提供丰富的语音交互。这样的设备可以与你的智能家居设备无缝互动，让用户对自己的数据安枕无忧。

运行 Llama 3.2 1B 的另一个诱人用例是本地文本编辑器中的上下文感知补全。你一边打字，模型一边提供智能的实时建议，让写作或编码工作流更顺畅——全程无需联网。

这些只是几个例子，设备端 GenAI 的可能性远不止于此。

# 结语：人人可用的 GenAI

凭借 SDOT、KleidiAI 与 ExecuTorch 的合力，我们正在拓展可能性的边界。把生成式 AI 带出高端旗舰设备，让它能在数十亿已在使用的 Arm 设备上触手可及。
