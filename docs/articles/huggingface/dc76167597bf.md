# 引言

每天超过十亿次：这是对 ChatGPT 日请求量的一个保守估计，而且这个数字短期内不会下降。每一次请求、每一个生成的 token，我们都在运行一个数十亿参数模型的推理。这正是为什么每一层的模型优化都至关重要：到了这种规模，哪怕 1% 的延迟或功耗改善都能带来巨大的节省。

但这份收益可能来自哪里？模型架构已经很成熟，热门模型的权重也早就量化过了。不过还有一个可以优化模型推理的关键层级：内核（kernel）层。内核是网络中执行任何运算时真正跑起来的算法：有矩阵乘法内核、卷积内核、批归一化内核等等。内核是底层、高度优化的算法，通常针对运行它的设备量身定制。出了名的又长又难写，需要对 GPU 内部工作机制有很好的理解。

内核是神经网络运算的基础——没有内核，一个运算实际上就没法用。正因如此，新创新往往带着一个"day 0"内核发布，而且通常只为最新的 Nvidia 硬件做过优化。这排除了大量其他设备，尤其是 AMD GPU——尽管规格相当甚至更好，却常常被内核开发者忽视。Hugging Face 与 AMD 合作，在 AMD 平台交付最先进（state-of-the-art）的性能，让开源社区受益。作为合作的一部分，我们与 AMD 决定聚焦于交付开源的优化内核，提升在 8 张 MI300X 组成的单节点上用 VLLM 以 FP8 服务 [Llama 3.1 405B](https://huggingface.co/meta-llama/Llama-3.1-405B) 的性能。

本文将探讨我们如何为 MI300X 优化性能、逐个内核做精调。但先看我们用定制内核取得了多少性能收益。把下面三个优化内核组合起来：

- 残差连接、RMS norm 与 FP8 转换的融合内核
- SwiGLU 激活与 FP8 转换的融合内核
- Skinny GEMM（瘦高矩阵乘法）内核

我们在 MI300X 节点上运行 VLLM 时获得了显著加速。

[![Latency gains](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/results_figure.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/results_figure.png)

测量时输入长度为 1、输出长度为 128，以模拟解码场景。解码延迟取 30 次迭代的中位数。

这些性能收益是在 VLLM 中测得的，但内核也可以单独使用，方法见后文"How to"一节。

# 优化过程

我们先快速回顾一下所用设备——MI300X 的架构，然后看看优化前模型推理的现状，据此定位瓶颈、确定需要写哪些定制内核。之后逐个介绍我们写的内核，并从多个角度展示内核优化是怎么开展的。

## MI300X 快速入门

在动手优化 GPU 代码之前，得先了解 GPU 是怎么工作的。网上已经有很多把 GPU 内部机制讲得很清楚的好资料，这里直接放链接：[这里](https://tinkerd.net/blog/machine-learning/cuda-basics/)、[这里](https://siboehm.com/articles/22/CUDA-MMM)、[这里](https://www.youtube.com/watch?v=OUIkkAPaw4M)。我们还是快速过一遍 GPU 的各个层级，当作温习。想跳过温习直接看定制内核细节，点[这里](https://huggingface.co/blog/mi300kernels#rms-norm-kernel)！

### 线程（Threads）

GPU 上最小的工作单元是**线程（thread）**。GPU 上任何工作的发生，都是因为某个线程执行了一条指令。指令都是些基本操作：加法、乘法、数据类型转换、load/store 等。每个线程都有自己的、只有自己能访问的内存，即寄存器（register，或称 VGPR）。一个线程最多 256 个寄存器，每个 32 位宽。下图表示一个线程及其 256 个 VGPR。

[![Representation of a thread](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/thread_global.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/thread_global.png)

除了 load/store 指令，线程只能对自己的寄存器执行指令。例如要把两个向量 A 和 B 相加，每个线程要：1) 从 A 加载一个元素进寄存器，2) 再加载一个 B 的元素，3) 执行加法并把结果存入另一个寄存器，4) 把该寄存器的值写回内存。总共 4 条指令。

### 波前（Warps）

下一个工作单元是 warp：每个 warp 由 64 个线程组成。warp 没有自己的内存，但对我们很重要，因为同一 warp 内的所有线程必须在同一时刻执行相同的指令。这既是保证，也是约束。

[![Representation of a warp](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/warp_global.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/warp_global.png)

warp 还允许线程之间交换各自寄存器里的数据。虽然同一 warp 内不同线程访问的数据不同，但由于它们必须执行相同指令，写内核时你需要以 warp 级行为为单位去思考。

### 计算单元（Compute units）

warp 被打包成**线程块（thread block）**：线程块是软件抽象，运行在一个叫**计算单元（compute unit, CU）**的硬件组件上。单个计算单元可以同时运行多个线程块，但最多只放得下 16 个 warp。每个计算单元有专属的 L1 缓存和共享内存。L1 缓存无法控制也无法分配，它帮助 CU 上所有 warp 复用数据。共享内存则相反，可以分配，用作所有 warp 共享的存储。例如当我们想让一个计算单元里的所有 warp（也就是所有线程）访问同一块缓冲区时，就把它分配到共享内存。共享内存和 L1 缓存访问都很快，因为它们离线程很"近"。

[![Representation of a compute unit](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/cu_global.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/cu_global.png)

线程块还提供内部所有线程同步的能力：这在处理涉及共享内存的操作时非常有用，比如把共享内存里的数组初始化为零、做归约操作。一般来说，写内核时线程块是需要考虑的最高层级：不同线程块之间几乎无法同步，也无法以任何方式交互。内核吞吐量与 GPU 上计算单元数量紧密相关：CU 越多，能同时运行的线程块越多——只要你能用满所有 CU，吞吐就会提升。

### XCD

计算单元再被分组进**加速器复合芯粒（accelerator complex dies, XCD）**，每个 XCD 有 38 个计算单元。CU 之间虽不能互相交互，但共享一个 L2 缓存。L2 缓存你控制不了，但在数据复用时仍然有用。比如访问内存时，如果两个 CU 位于同一个 XCD 并访问相同数据，加载延迟会大幅降低。L2 缓存相当大：4MB；而共享内存 64kB，L1 缓存 32kB。

[![Representation of a XCD](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/xcd.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/xcd.png)

### 整块 GPU（MI300X）

把 8 个 XCD 拼起来（8 × 38 = 304 个 CU），再加一级缓存（infinity cache，256MB）和海量显存（192GB），就是 MI300X。

[![Representation of a MI300](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/mi300x.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/mi300x.png)

所有 XCD（也就是所有线程）都能访问 VRAM，但访问相当慢。离线程层级越远，内存访问越慢，但容量越大、作用范围越广，服务的线程越多。优化内核时，永远要在"多做运算"和"多加载数据"之间找平衡；但总体而言，你要尽可能少地访问 VRAM（通常称为全局内存，global memory）。

看着这张图，就能明白 GPU 为什么被称作"大规模并行"：这里有 304 个计算单元，每个能运行 16 个 warp，每个 warp 64 个线程。也就是最多 311,296 个线程同时在跑，各自执行各自的指令。别忘了"指令"只是加法这种基本操作，所以像牛顿法这种简单迭代，对单个线程来说都可能跑得很长。GPU 不是为"单条指令跑得快"（低延迟）优化的——那是延迟导向设备；GPU 是为"海量线程一起吞吐大量数据"优化的：它是吞吐导向设备。所以给 GPU 优化内核时，思路要跟着变：让一个算法在很多线程上各跑少量指令，好过让少数线程跑大量指令。这也是为什么把跑在 GPU 上的算法称为"并行"算法。

挡在这些算法高效运行路上的有三样东西：要加载的数据太多（memory bound，访存受限）、要执行的运算太多（compute bound，计算受限），以及线程需要协作（同步开销）。

## Day 0 性能分析

优化一个负载时，写第一行代码之前先要 profile 当前状态。我们的做法是给 VLLM 中的模型推理做 profile，了解每个操作耗时多少，从而定位主要瓶颈、确定先攻哪些内核能拿到最大加速。例如 batch size 为 32 时的耗时分布：

[![Disk plot ok kernels latency](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/disk_figure.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/disk_figure.png)

每一块扇形对应网络的不同部分：

- "Attention*"：我们把 RoPE、注意力和 KV 缓存内核归在一起；
- "Attention GEMMs"：包括 QKV 和 Output 两个投影；
- "Communications"：由两次 all-reduce 组成，一次在 Attention 块后、一次在 MLP 块后，因为我们在张量并行（TP8）下工作；
- "MLP GEMMs"：包括 MLP 中的两个投影，Gate / Up 和 Down；
- "RMS norm" 和 "SwiGLU"：各一个内核——注意每个 block 里 RMS norm 内核会被调用两次，Attention 前一次、MLP 前一次；
- "Other"：影响较小、未归入更大类别的内核。

已经能看出大部分延迟来自 GEMM 和通信，而注意力及其周边操作对延迟的贡献并不大。这或许令人意外，因为很多论文都聚焦注意力、设法降低它的开销。但 KV 缓存加上 FlashAttention（VLLM 中已优化过）的组合，可能让这部分不再是头号优先级。出人意料的是，"RMS norm" 内核的两次调用相当昂贵，优化它的收益可能很大。它和 SwiGLU 内核合计占总延迟的 15%，不容忽视。总的来说，攻这两个内核、再设法给 GEMM 拿到一点加速，是最优路线。为确认这个耗时分布不是巧合，可以再看看其他 batch size：

[![Latency distribution over batch sizes](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/bs_latency_figure.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/bs_latency_figure.png)

batch size 32 呈现的规律在其他 batch size 上也成立，只是 GEMM 和通信的延迟占比随 batch size 增大而上升。另外，batch size 32 在 GEMM 延迟上是个离群点：可能因为 batch size 32 时选用的 GEMM 经过手动调优，或 32 的内存对齐模式更好，所以比 batch size 24 或 28 时更快。

热点已经定位，来看我们写的第一内核：RMS norm 内核。

## RMS norm 内核

每个 decoder block 有两个主要部分：注意力块和 MLP 块。两者都从两个输入的残差连接开始：当前隐状态 x 和残差 r。二者形状相同：n 行（与 token 数相同）、d 列。相加之后，对 x 施加按行的均方根（RMS）归一化；由于模型是 FP8 的，还要用缩放因子 s 把 x 量化为 FP8。光是把这三个操作融合进一个内核，就能带来可观的性能提升。数学上要做的事情如下：

(1) x ← x + r；r ← x　(2) V = Σ_{i=1}^{d} x_i²　(3) x ← x / √(V + ε)；x_Q = Q_fp8(s * x * w)

其中 w 是长度为 d 的权重向量。步骤 (1) 和 (3) 很基本。步骤 (1) 只需让每个线程定位到张量中不同的位置，加载 x 和 r 的一些元素，相加后写回 r。步骤 (3) 中每个线程做若干标量运算（加法、开方、除法）和一次 FP8 转换。这些线程各自就能完成，天然契合 GPU 的并行性。要小心的是步骤 (2)：要对 d 求和——要么每个线程遍历全部 d 列，要么线程之间交换数据。d 越大，第一种方案要加载的数据越多，就越不可行。我们选第二种：在线程块层面同步，用共享内存交换数据。每个线程先各自累加 V 的一部分，再在整个线程块上把这些部分加起来，这就是所谓的归约（reduction）。由于 V 是按整行计算的，我们给每一行分配一个线程块。

与开箱即用的 PyTorch 相比，这个内核的原始版本已经带来约 10 倍加速。但还不够：上面还能叠加很多优化。

### 优化：内存相关

就延迟而言，最昂贵的操作之一是访问 VRAM，即**全局内存**。好在有一些容易遵循的原则能大幅降低数据加载成本。

首先，看单个线程一条指令能加载多少数据：查 MI300X 指令指南可知，从全局内存一次加载最宽 128 位。我们加载的是 FP16 数据，所以每次加载 128b / 16b = 8 个元素；若是 fp32，则对应 4 个元素。

其次，确保访存是合并的（coalesced）。每个线程都属于某个 warp，一个线程到达 "load" 指令时，warp 内其他线程也到达。为效率计，这些 "load" 指令会在整个 warp 上打包，warp 集体取数，各线程拿到自己所需的数据。当 warp 取回的是中间没有空隙的整块数据时效率最高，即**连续（contiguous）**数据。当需要加载的数据超过一条 load 指令的容量时就会出现下面的问题。

[![Two loading scenarios](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/coalesced.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/coalesced.png)

在这个假想场景中，同一 warp 里有两个线程，需要共同加载 16 个 fp32 元素，不限制哪个线程加载哪个元素——这是典型的"归约"情形。由于一个线程一条指令只能加载 4 个 fp32 元素，至少有两种读法，即场景 (a) 和 (b)。判断哪个更好，要站在 warp 视角而不是线程视角。场景 (a) 中，第一次加载取元素 0,1,2,3,8,9,10,11：数据不连续，元素 3 和 8 之间有空隙。场景 (b) 中，第一次加载取元素 0,1,2,3,4,5,6,7：加载的是连续数据，第二次同理。所以**场景 (b) 更好**。尽管场景 (a) 里每个线程最终也有 8 个连续元素，但那不重要：重要的是 **warp** 加载的数据是否连续。原因：如果 warp 一个周期只能加载 8 个连续元素，那场景 (a) 的每次加载要两个周期，而场景 (b) 一次加载只需一个周期。

第三，减少 store 次数：看步骤 (1) 和 (3)，其实只需要两次存储——一次存 r，一次存 x_Q。步骤 (1) 之后就可以把 r 存掉、完成。但步骤 (2) 之后仍需访问修改过的 x。办法有二：把修改后的 x 存到全局内存，步骤 (2) 结束后重新加载，依赖缓存命中；或者，如果 x 足够小，把修改后的 x 存进共享内存——x 是 FP16 且每个 CU 只跑一个线程块时，每块线程可在共享内存存 64KB / 2B = 32 × 1024 个元素。对 Llama 405B 而言 d = 16384，装得下。相比依赖缓存命中，用共享内存能带来不错的加速，尤其在多个线程块同时活跃时：如果 L1 缓存装不下整个 x，就得依赖由 38 个 CU 共享的 L2 缓存。

访存之外还可以优化计算效率，但那留到下一个内核细说，两者思路类似。

输入是 [X, 16384] 形状的 FP16 张量。我们内核的最基础版本（"Pointwise"）没有任何访存优化，但已经对 torch 至少有 4 倍加速；它不如 VLLM 的实现，但我们的 "Vectorized" 版本同时超过 "Pointwise" 和 VLLM。"Vectorized" 实现了合并的 128 位加载，只有 "Vectorized + SMEM"（SMEM 即共享内存）版本比它更快——后者在低 batch 和高 batch 下的加速比都明显优于 VLLM。

## SwiGLU 内核

在 MLP 块中，紧跟在上面说的内核之后的，是我们之前一直称为 "Gate / Up" 的投影。之所以这么叫，是因为 "Gate / Up" 投影实际上是以同一输入做的两个投影 "Gate" 和 "Up" 的拼接。因此把 "Gate / Up" 投影的结果 x 写成 x = x_G | x_U，其中 | 是沿列轴的拼接运算符。x_G 和 x_U 维度相同。需要这两个投影，是因为紧随其后的 SwiGLU 激活函数，其结果 y 由公式 (4) 定义。SwiGLU 激活之后是 "Down" 投影，在我们的场景里它是 FP8 的，所以还要按公式 (5) 量化 y：

(4) y = σ(x_G) · x_U　(5) y_Q = Q_FP8(s * y)

其中 σ 是 sigmoid 函数：σ(x) = e^{-x} / (1 + x)。我们要写一个融合内核把这一切都处理掉。对这个内核，前面 RMS 内核说的优化依然适用，除了共享内存缓冲区那条。这里聚焦计算相关的优化。

### 优化：计算相关

我们准备用两种方式提高内核速度：增加每条指令完成的工作量，以及使用更快的指令。

要增加每条指令的工作量，可以使用**打包（packed）指令**。当同一种算子要作用在多个元素上时，打包指令很有用：不是每个元素执行一条指令，而是对一组元素执行一条指令。在 CPU 上，打包（向量化）指令是单线程优化的看家本领，AVX 指令家族就是明证。GPU 上的打包指令不多，但在合适的地方非常有用。MI300X 上有（除其他之外）FP16 加法和乘法的打包指令，两个步骤我们都会用上。还有从 FP32 到 FP8 的打包转换，相比非打包转换能带来可观的性能提升。事实上，除了 FP32 之外没有其他类型能直接转 FP8，所以 RMS norm 内核和这个内核都必须先回到 FP32 精度再转 FP8。

不过在这个内核里这不是问题：sigmoid 函数 σ 需要计算指数，而指数运算非常受益于 FP32 精度。同时这里恰好能用更快的指令优化计算：不用 `exp` 指令，而是把输入乘以 log(2) 后用 `exp2` 指令——后者快得多。精度损失几乎可以忽略，延迟却降了下来。

## Skinny GEMM 内核

如前所见，模型推理约 60% 的延迟来自投影，而投影依赖 GEMM 内核。GEMM 内核在专用库（AMD 上的 hipBLASLT、rocBLAS）中已被高度优化，想写出全面超越它们的定制内核相当难。但如果聚焦于对我们重要的某些边界情况，专门针对这些情况写 GEMM 内核，我们的定制内核就有机会快过专用库。

无论 prefill 还是解码，网络任意投影的输入行数都等于正在处理的 token 数。而解码阶段处理的 token 数就等于 batch size。所以解码时所有 GEMM 内核的输入行数等于 batch size，在我们的场景中范围是 1 到 256。我们重点关注很小的 batch size。当 GEMM A * B = C 中的 A 行很少、列很多时，我们称这个 GEMM 是**瘦高的（skinny）**。之所以给这类 GEMM 专门起名，是因为它们不适合 GPU 上经典的 GEMM 算法。通常 GEMM 内核的效率来自**分块（tiling）**：把结果矩阵切成许多子矩阵（tile），每个 tile 分配给一个不同的计算单元（CU）。tile 多，就能用很多 CU，GPU 利用率高。下图说明了这一点。

[![Classic GEMM dimensions](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/classic_gemm.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/classic_gemm.png)

但如果输入 A 的行非常少，只能形成很少的 tile，结果就是只有少量 CU 在干活，GPU 利用率很低：

[![Skinny GEMM dimensions](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/skinny_gemm.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/skinny_gemm.png)

Skinny GEMM 对 GPU 天生不友好。下一节看看如何通过一个假定 skinny GEMM 场景的定制内核让它们变得友好。

### 优化：split-K

Skinny GEMM 的主要问题是使用的计算单元太少，所以第一件事是想办法多用 CU。我们可以利用下面这个"烧脑"公式：

c_ij = Σ_{k=1}^{K} a_ik b_kj = ( Σ_{k=1}^{K/2} a_ik b_kj ) + ( Σ_{k=1+K/2}^{K} a_ik b_kj )

得益于加法的结合律，我们可以沿共享轴（通常称 **K 轴**）把主 GEMM 切开，用几个并发执行的子 GEMM 替代一个 GEMM。每个子 GEMM 用到的 CU 数和原来的主 GEMM 一样，所以使用的 CU 总数乘以了 K 轴被切分的次数。下图展示了这一点：

[![Split-K algorithm](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/split_k.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/split_k.png)

这里我们设 split K = 2，一次使用的 CU 数量翻倍。由于得到的是部分结果，两个子 GEMM 完成后需要把它们加起来。看似反直觉：我们明明加了一个操作（对部分结果求和），却声称降低了整体延迟。但每个 CU 本来要遍历整条 K 轴才能算出结果，我们把它切成两半，每个 CU 的工作量也减半。如果这样省下的工作量能够抵消求和增加的工作量，整体就是优化。只要 K 足够大、原 GEMM 用不到 50% 的 GPU，这个条件一般都能满足。

### 优化：去掉填充（padding）

假设通过 split-K 大多数 CU 都在忙于各自的 tile，我们就可以把优化的焦点收拢到计算单元层面。来看看矩阵乘法实际是怎么做的、如何加速。

在 MI300X 这种先进 GPU 上，矩阵乘法由一个叫张量核心（tensor core）的专用硬件单元处理。张量核心只做矩阵乘法，但速度极快。张量核心指令的格式是 `mfma_MxNxK...`，其中 `mfma` 表示 matrix fused multiply-add（矩阵融合乘加），`M` 是左矩阵的行数，`N` 是右矩阵的列数，`K` 是两者的共享维度。下面用假想指令 `mfma_2x2x4` 图解：

[![MFMA dense version](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/MFMA_full.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/MFMA_full.png)

张量核心指令种类不多，但对任何 `MxNxK` 组合，用张量核心专用指令都比其他任何方式快得多。张量核心指令还分两种形态："dense"（稠密）和 "sparse"（稀疏）。稠密指令对应标准矩阵乘法。稀疏指令假定左矩阵 A 具有 4:2 结构化稀疏模式，即沿矩阵 K 轴每 4 个元素中有 2 个为零。数学上说，对任意满足 a_{i, 4j+3} 是 A 中元素的 i, j，(a_{i,4j}, a_{i,4j+1}, a_{i,4j+2}, a_{i,4j+3}) 中至少有两个零。下面是一个稀疏矩阵示例。

[![A 4:2 sparse matrix](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/sample_sparse.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/sample_sparse.png)

回到我们的模型：FP8 的 Llama 405B。FP8 下只有两条稠密张量核心指令：`16x16x32` 和 `32x32x16`，以及一条 `16x16x64` 的稀疏指令。对于 8 行的输入，即便用最小的稠密指令 `16x16x32`，也要给输入补 8 行填充——浪费计算资源。你可能会想：能不能改用稀疏指令？毕竟，一个 16 行矩阵如果有一半按 4:2 稀疏，就能用一个 8 行稠密矩阵完整描述它的所有非零系数。反过来，一个 8 行稠密矩阵的数据也能全部装进一个 4:2 稀疏的 16 行矩阵。而稀疏指令的好处显而易见：稠密指令 `K=32`，稀疏指令 `K=64`。同样的周期数，稀疏指令的深度翻倍。下图用 1 行输入、`2x2x4` 稠密指令和对应的 `2x2x8` 稀疏指令演示这个稀疏化技巧。

[![Using sparsity for skinny inputs](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/sparsity_trick.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/sparsity_trick.png)

用这个技巧，对行数不超过 8 的任何输入，我们都能显著加速 GEMM，从而降低请求数少于 8 的任何解码批次的单 token 延迟。

### 优化：warp 专职化与异步执行

前面说过，skinny GEMM 中行数少限制了输出 tile 的数量，进而限制 GPU 利用率。但行数少同时限制了每个输出 tile 的行数，进而降低所谓**算术强度（arithmetic intensity）**。简单说，算术强度 = 完成的工作量 ÷ 为完成它加载的数据量。对比两个例子：

s_n = Σ_{i=1}^{n} x_i　　t_n = Σ_{i=1}^{n} y^i = y (1 + t_{n-1})

其中 x 是长度为 n 的向量，y 是标量。计算 s_n 要加载 n 个元素、执行 n−1 次加法；计算 t_n 只需加载 1 个元素、执行 2n−1 次加法和乘法。于是 s_n 的"算术强度"是 (n−1)/n，t_n 则是 2n−1：t_n 的计算比 s_n 更"算术密集"。由此可见：**算术强度越低，完成工作所需加载的数据就越多**。

这为什么和我们有关？前面看到，从 VRAM 加载数据的延迟成本很高，对 GPU 很不友好。换句话说，低算术强度的负载不适合 GPU，而 skinny GEMM 的算术强度恰好比非 skinny GEMM 低。看下面的图就直观了：数据量除以二时，由于 GEMM 维度的二次性质，输出系数数量除以 4。

[![The arithmetic intensity of two GEMMs](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/gemm_AI.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/gemm_AI.png)

skinny GEMM 中输出 tile 的行数受限，算术强度也随之受限。这意味着为了算出一个输出 tile 需要加载大量数据。而且由于使用 FP8 算术，计算相当快，我们无法靠计算时间来掩盖数据加载延迟。理想状态是：负责加载数据的线程多于负责计算结果的线程。

为此我们使用**warp 专职化（warp specialization）**技术。不再让线程块中所有 warp 执行相同指令，而是指派一些 warp 专门加载数据、另一些专门计算结果。负责加载数据的 warp 称为**生产者（producers）**，负责计算的称为**消费者（consumers）**。生产者和消费者异步工作：生产者先从 VRAM 加载数据（慢），把它存入共享内存缓冲区供消费者使用；在数据就绪前，消费者处于空闲；数据就绪后，消费者从共享内存加载（快）并计算结果。生产者与消费者的协调通过一个存放在共享内存中的队列完成：生产者把数据写入缓冲区 i 后，把队列第 i 个变量的状态改为"数据可用"；消费者盯着这个状态，看到后就加载数据；加载完成后把第 i 个变量改为"缓冲区 i 可被覆写"。下图展示了一个简单异步 GEMM 的各个步骤：一个生产者、一个消费者、一个长度为 2 的队列。

[![Async GEMM mechanism](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/async_work.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mi300kernels/async_work.png)

整个流程能运转的关键在于：生产者填满缓冲区 0 后，无需等消费者取走缓冲区 0 的数据，就可以开始填缓冲区 1。目标是队列长度足以让生产者始终在填缓冲区、消费者始终在取数据。队列长度受共享内存大小的限制。

还需要调校生产者与消费者的比例。前面说过我们的算术强度低，需要为相对快的计算加载大量数据，因此会用很多生产者 warp（通常 8 到 10 个）配少数消费者 warp（大概 2 到 3 个）。此外还能利用 GEMM 瘦高的特性，为输入（瘦矩阵）和权重（非瘦矩阵）分别设置独立的生产者。为了让输出 tile 在不受限的维度（即列维度）上更大，我们给权重分配更多生产者。

想更深入地了解异步 GEMM，推荐阅读[这篇博客](https://cudaforfun.substack.com/p/outperforming-cublas-on-h100-a-worklog)。不过其中很多内容不适用于我们的场景：MI300X 没有 warp 级屏障，只有单一的线程块级屏障。这带来了一些"有趣"的操作，比如用 ASM 确保 warp 在屏障处等待、在检查屏障状态之前先完成共享内存的 load/store、以及小心处理队列的取模性质。这些细节这里就不展开了，欢迎去看[代码](https://github.com/huggingface/hf-rocm-kernels)或在评论区提问。关于异步处理的深度剖析未来可能会另文详谈。

通过 warp 专职化和异步工作，我们让内核适配了低算术强度负载。但光这样能反超 hipBLASLT 这类库吗？答案是：某些情况下可以。
