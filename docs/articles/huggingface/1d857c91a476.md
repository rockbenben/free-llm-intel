## 现代 OCR 简史

光学字符识别（OCR）是计算机视觉中最早、也最长跑的挑战之一。AI 最早的一批实用应用，很多都聚焦于把印刷文本变成数字形式。

随着[视觉-语言模型](https://huggingface.co/blog/vlms)（VLM）浪潮，OCR 取得了长足进步。最近许多 OCR 模型是在既有 VLM 上微调而来的。但今天的能力早已远超 OCR：你可以按查询检索文档，或者直接回答关于文档的问题。得益于更强的视觉特征，这些模型还能处理低质量扫描件、解读表格/图表/图像等复杂元素，并把文本与视觉融合起来，跨文档回答开放式问题。

### 模型能力

#### 转写

近年的模型能把文本转写成机器可读格式。
输入可以包括：

- 手写文本
- 拉丁、阿拉伯、日文等各种文字系统
- 数学公式
- 化学式
- 图像/版式/页码标签

OCR 模型把它们转换成机器可读文本，形式可以是 HTML、Markdown 等多种格式。

#### 处理文档中的复杂组件

除文本外，一些模型还能识别：

- 图像
- 图表
- 表格

有些模型知道图像在文档中的位置，会提取其坐标并恰当地插入文本之间。另一些模型会为图像生成字幕并插入其出现的位置。如果你要把机器可读输出喂给 LLM，这尤其有用。例子包括 [AllenAI 的 OlmOCR](https://huggingface.co/allenai/olmOCR-7B-0825) 或 [PaddlePaddle 的 PaddleOCR-VL](https://huggingface.co/PaddlePaddle/PaddleOCR-VL)。

不同模型使用不同的机器可读输出格式，例如 **DocTags**、**HTML** 或 **Markdown**（下一节*输出格式*会解释）。模型处理表格和图表的方式，往往取决于它所用的输出格式。一些模型把图表当作图片：原样保留。另一些模型把图表转成 markdown 表格或 JSON，例如一张柱状图可以这样转换。

[![Chart Rendering](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/ocr/chart-rendering.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/ocr/chart-rendering.png)

表格也类似：单元格被转换为机器可读格式，同时保留标题行和列的上下文。

[![Table Rendering](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/ocr/table-rendering.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/ocr/table-rendering.png)

#### 输出格式

不同 OCR 模型有不同的输出格式。简单概括一下现代模型常用的输出格式。
**DocTag：** DocTag 是一种类 XML 的文档格式，表达位置、文本格式、组件级信息等。下面是一篇论文被解析成 DocTags 的示意。开放模型 Docling 就使用这种格式。

[![DocTags](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/ocr/doctags_v2.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/ocr/doctags_v2.png)

- **HTML：** HTML 是文档解析中最常用的输出格式之一，能完整编码结构与层级信息。
- **Markdown：** Markdown 是人类最易读的格式。它比 HTML 简单，但表达力稍弱——比如无法表示分栏表格。
- **JSON：** JSON 不是模型用来输出整篇文档的格式，但可以用来表示表格或图表中的信息。

选哪个模型，取决于你打算怎么用它的输出：

- **数字化重建**：要数字重建文档，选保留版式的格式（如 DocTags 或 HTML）。
- **作为 LLM 输入或做问答**：如果要把输出喂给 LLM，选输出 Markdown 和图像字幕的模型，它们更接近自然语言。
- **程序化使用**：如果要把输出接入程序（比如数据分析），选能生成 JSON 这类结构化输出的模型。

#### 位置感知

文档结构可能很复杂：多栏文本块、浮动图表。老一代 OCR 模型先识别词，再在后处理中人工推断页面版式、让文本按阅读顺序排列——非常脆弱。而现代 OCR 模型内嵌版式元数据来帮助保持阅读顺序与准确性，这类元数据称为"锚点"（anchor），可以是边界框。这个过程也叫"grounding/anchoring"（定位/锚定），因为它有助于减少幻觉。

#### 模型提示词

OCR 模型可以接受图像以及可选的文本提示词，具体取决于模型架构和预训练设置。
一些 OCR 模型支持基于提示词的任务切换，例如 [granite-docling](https://huggingface.co/ibm-granite/granite-docling-258M)：用提示词 "Convert this page to Docling" 可以解析整页，也可以用 "Convert this formula to LaTeX" 这样的提示词配合满是公式的页面。
另一些模型则只训练了解析整页，并通过系统提示词来设定这一行为。
例如 [AllenAI 的 OlmOCR](https://huggingface.co/collections/allenai/olmocr-67af8630b0062a25bf1b54a1) 使用一段很长的条件化提示词。和许多模型一样，OlmOCR 技术上是一个 VLM（这里是 Qwen2.5VL）的 OCR 微调版，所以你也可以提示它做别的任务，只是表现远不如其 OCR 能力。

## 前沿开放 OCR 模型

过去一年涌现了惊人的新模型潮。因为大量工作在开放环境下进行，各家彼此构建、彼此受益。一个很好的例子是 AllenAI 发布 OlmOCR：不仅释出模型，还释出了训练所用的数据集。有了这些，其他人就能在其上开拓新方向。这个领域异常活跃，但用哪个模型并不总是显而易见。

### 模型评估

#### 基准测试

没有绝对的最好的模型，因为每个问题的需求都不同。表格应该渲染成 Markdown 还是 HTML？该提取哪些元素？如何量化文本准确率与错误率？👀
虽然评估数据集和工具很多，但大多回答不了这些问题。所以我们建议用以下基准：

- [**OmniDocBenchmark**](https://huggingface.co/datasets/opendatalab/OmniDocBench)**：** 这个被广泛使用的基准以文档类型多样见长：书籍、杂志、教科书。评估指标设计精良，表格接受 HTML 和 Markdown 两种格式。其新颖的匹配算法评估阅读顺序，公式在评估前先做归一化。多数指标依赖编辑距离或树编辑距离（表格）。值得注意的是，用于评估的标注并非全人工产出，还借助了 SOTA VLM 或传统 OCR 方法。
- [**OlmOCR-Bench**](https://huggingface.co/datasets/allenai/olmOCR-bench)：OlmOCR-Bench 走的是另一条路：把评估当作一组单元测试。例如表格评估是通过检查给定表格中选定单元格之间的关系。他们从公开来源取 PDF，标注则由一系列闭源 VLM 完成。这个基准在英语评估上相当成功。
- [**CC-OCR（多语言）**：](https://huggingface.co/datasets/wulipc/CC-OCR)与前两个基准相比，CC-OCR 在选型时不太受青睐，因为文档质量和多样性较低。但它是唯一包含英语和中文之外评估的基准！虽然评估远非完美（图像是词数很少的照片），做多语言评估你能用到的最好选择仍是它。

在测试不同 OCR 模型时，我们发现不同文档类型、语言等之间的性能差异很大。你的领域未必被现有基准充分覆盖！要高效利用这一代基于 VLM 的 OCR 模型，我们建议你收集一份代表自己任务领域的示例数据集，并测试多个模型对比表现。

#### 成本效率

多数 OCR 模型都很小，参数在 3B 到 7B 之间；你甚至能找到不足 1B 参数的模型，如 PaddleOCR-VL。但成本还取决于是否有针对专业推理框架的优化实现。例如 OlmOCR-2 自带 vLLM 和 SGLang 实现，每百万页成本 178 美元（按 H100 每小时 $2.69 计算）。DeepSeek-OCR 在单块 40GB 显存的 A100 上每天可处理 20 万页以上。粗略一算，每百万页成本与 OlmOCR 大致相当（取决于你的 A100 供应商）。如果你的用例不受影响，也可以选择模型的量化版本。跑开源模型的成本很大程度取决于实例的每小时单价和模型自带的优化，但在更大规模上，它肯定比市面上许多闭源模型便宜。

#### 开放 OCR 数据集

过去一年开放 OCR 模型激增，但开放的训练/评估数据集并没有同步跟上。例外是 AllenAI 的 [olmOCR-mix-0225](https://huggingface.co/datasets/allenai/olmOCR-mix-0225)，它至少已被用于训练 [Hub 上的 72 个模型](https://huggingface.co/models?dataset=dataset:allenai/olmOCR-mix-0225)——实际可能更多，因为并非所有模型都记录了训练数据。

分享更多数据集可以为开放 OCR 模型解锁更大的进展。创建这类数据集有几个很有前景的方向：

- **合成数据生成**（例如 [isl_synthetic_ocr](https://huggingface.co/datasets/Sigurdur/isl_synthetic_ocr)）
- **VLM 生成的转写**，通过人工或启发式规则过滤
- **用现有 OCR 模型**为新模型（特定领域可能更高效的模型）生成训练数据
- **利用已有的经过校订的数据集**，例如[英国藏印度历史记录数据集](https://huggingface.co/NationalLibraryOfScotland)，其中包含对历史文档大量人工校正过的 OCR 结果

值得注意的是，许多这样的数据集已经存在但无人使用。把它们整编成"训练就绪"的数据集，对开源社区是相当大的潜在财富。

## 运行模型的工具

我们收到很多关于 OCR 模型如何上手的问题，这里给出几条路径：本地推理工具和 Hugging Face 远程托管。

### 本地运行

多数前沿模型都支持 vLLM 和 transformers。各模型的服务方式请看模型自身的模型卡。为方便起见，这里演示用 vLLM 本地推理。具体代码因模型而异，但大多数模型都类似下面这样。

```
vllm serve nanonets/Nanonets-OCR2-3B
```

然后可以用 OpenAI 客户端等发起查询。

```
from openai import OpenAI
import base64

client = OpenAI(base_url="http://localhost:8000/v1")

model = "nanonets/Nanonets-OCR2-3B"

def encode_image(image_path):
    with open(image_path, "rb") as image_file:
        return base64.b64encode(image_file.read()).decode("utf-8")

def infer(img_base64):
    response = client.chat.completions.create(
        model=model,
        messages=[
            {
                "role": "user",
                "content": [
                    {
                        "type": "image_url",
                        "image_url": {"url": f"data:image/png;base64,{img_base64}"},
                    },
                    {
                        "type": "text",
                        "text": "Extract the text from the above document as if you were reading it naturally.",
                    },
                ],
            }
        ],
        temperature=0.0,
        max_tokens=15000
    )
    return response.choices[0].message.content

img_base64 = encode_image(your_img_path)
print(infer(img_base64))
```

**Transformers**

Transformers 提供标准的模型定义，便于推理和微调。Hub 上的 transformers 模型要么有官方实现（库内的模型定义），要么是"remote code"实现。后者由模型所有者定义，以便模型能直接装进 transformers 接口，你不用自己实现模型。下面是用 transformers 实现加载 Nanonets 模型的例子。

```
# make sure to install flash-attn and transformers
from transformers import AutoProcessor, AutoModelForImageTextToText

model = AutoModelForImageTextToText.from_pretrained(
    "nanonets/Nanonets-OCR2-3B", 
    torch_dtype="auto", 
    device_map="auto", 
    attn_implementation="flash_attention_2"
)
model.eval()
processor = AutoProcessor.from_pretrained("nanonets/Nanonets-OCR2-3B")

def infer(image_url, model, processor, max_new_tokens=4096):
    prompt = """Extract the text from the above document as if you were reading it naturally. Return the tables in html format. Return the equations in LaTeX representation. If there is an image in the document and image caption is not present, add a small description of the image inside the <img></img> tag; otherwise, add the image caption inside <img></img>. Watermarks should be wrapped in brackets. Ex: <watermark>OFFICIAL COPY</watermark>. Page numbers should be wrapped in brackets. Ex: <page_number>14</page_number> or <page_number>9/22</page_number>. Prefer using ☐ and ☑ for check boxes."""
    image = Image.open(image_path)
    messages = [
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": [
            {"type": "image", "image": image_url},
            {"type": "text", "text": prompt},
        ]},
    ]
    text = processor.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
    inputs = processor(text=[text], images=[image], padding=True, return_tensors="pt").to(model.device)
    
    output_ids = model.generate(**inputs, max_new_tokens=max_new_tokens, do_sample=False)
    generated_ids = [output_ids[len(input_ids):] for input_ids, output_ids in zip(inputs.input_ids, output_ids)]
    
    output_text = processor.batch_decode(generated_ids, skip_special_tokens=True, clean_up_tokenization_spaces=True)
    return output_text[0]

result = infer(image_path, model, processor, max_new_tokens=15000)
print(result)
```


### 远程运行

**用 Inference Endpoints 做托管部署**
你可以把兼容 vLLM 或 SGLang 的 OCR 模型部署到 Hugging Face Inference Endpoints——既可以从模型仓库的 "Deploy" 选项进入，也可以直接用 [Inference Endpoints 界面](https://endpoints.huggingface.co/)。Inference Endpoints 在完全托管的环境中服务这些前沿模型：GPU 加速、自动扩缩容、监控，全都不用你手动管理基础设施。

这里是用 vLLM 作为推理引擎部署 `nanonets` 的简单方法。

- 进入模型仓库 [`nanonets/Nanonets-OCR2-3B`](https://huggingface.co/nanonets/Nanonets-OCR2-3B)
- 点击 "Deploy" 按钮，选择 "HF Inference Endpoints"

[![Inference Endpoints](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/ocr/IE.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/ocr/IE.png)

- 几秒钟内完成部署配置

[![Inference Endpoints](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/ocr/IE2.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/ocr/IE2.png)

- endpoint 创建完成后，用上一章给出的 OpenAI 客户端代码片段调用即可。

了解更多请看[这里](https://huggingface.co/docs/inference-endpoints/engines/vllm)。

**用 Hugging Face Jobs 做批量推理**

很多 OCR 应用需要高效的批量推理——在成千上万张图像上尽可能便宜高效地跑模型。一个好办法是使用 vLLM 的离线推理模式。如前所述，许多最新的基于 VLM 的 OCR 模型都受 vLLM 支持，它能高效地对图像做批处理、规模化生成 OCR 结果。

为了更进一步省事，我们创建了 [uv-scripts/ocr](https://huggingface.co/datasets/uv-scripts/ocr)——一套可直接运行的 OCR 脚本文集，配合 Hugging Face Jobs 使用。这些脚本让你在任意数据集上跑 OCR，完全不需要自备 GPU。把脚本指向你的输入数据集即可，它会：

- 用多个不同的开放 OCR 模型处理数据集中某列的所有图像
- 把 OCR 结果作为新的 markdown 列加入数据集
- 把带 OCR 结果的更新数据集推送到 Hub

例如，对 100 张图像跑 OCR：

```
hf jobs uv run --flavor l4x1 \
  https://huggingface.co/datasets/uv-scripts/ocr/raw/main/nanonets-ocr.py \
  your-input-dataset your-output-dataset \
  --max-samples 100
```

脚本自动处理所有 vLLM 配置和批处理，让批量 OCR 在零基础设施的情况下人人可及。

### 超越 OCR

如果你对文档 AI 感兴趣（而不只是 OCR），这里有一些我们的推荐。

#### 视觉文档检索器

视觉文档检索，就是给定一个文本查询，检索出最相关的前 k 个文档。如果你之前用过检索模型，不同之处在于：你直接在成堆的 PDF 上检索。除了单独使用，你还可以把它们与视觉语言模型结合，搭建多模态 RAG 流水线（做法见[这里](https://huggingface.co/merve/smol-vision/blob/main/ColPali_%2B_Qwen2_VL.ipynb)）。[Hugging Face Hub 上都能找到](https://huggingface.co/models?pipeline_tag=visual-document-retrieval&sort=trending)。

视觉文档检索器分两类：单向量模型与多向量模型。单向量模型更省内存但性能较弱；多向量模型更耗内存但性能更强。这些模型大多配有 vLLM 和 transformers 集成，因此你既可以用它们给文档建索引，也能配合向量数据库轻松检索。

#### 用视觉语言模型做文档问答

如果你的任务只需要基于文档回答问题，可以直接用那些训练任务中包含文档类任务的视觉语言模型。我们观察到有用户先把文档转成文本、再把输出交给 LLM——但如果你的文档版式复杂，转换输出里有 HTML 渲染的图表之类，或者图像字幕写错了，LLM 就会漏掉信息。更好的做法：把文档和查询直接喂给像 [Qwen3-VL](https://huggingface.co/collections/Qwen/qwen3-vl-68d2a7c1b8a8afce4ebd2dbe) 这样的先进视觉语言模型，不遗漏任何上下文。
