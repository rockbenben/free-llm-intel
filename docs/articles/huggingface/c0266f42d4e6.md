## 今天的 Accelerate 是什么？

3.5 年前，[Accelerate](https://github.com/huggingface/accelerate) 还只是一个简单的框架，旨在通过低层抽象简化*原生* PyTorch 训练循环，让多 GPU 与 TPU 系统上的训练更容易：

[![Sylvain's tweet announcing accelerate](https://raw.githubusercontent.com/muellerzr/presentations/master/talks/ai_dev_2024/sylvain_tweet.JPG)](https://raw.githubusercontent.com/muellerzr/presentations/master/talks/ai_dev_2024/sylvain_tweet.JPG)

自那以后，Accelerate 已扩展为一个多面手库，着手解决大规模训练与大模型的众多常见问题——在一个 4050 亿参数（Llama）成为新语言模型尺寸的时代。这包括：

- [一个灵活的低层训练 API](https://huggingface.co/docs/accelerate/basic_tutorials/migration)，可在六种不同的硬件加速器（CPU、GPU、TPU、XPU、NPU、MLU）上训练，同时保留你原始训练循环的 99%
- 一个易用的[命令行界面](https://huggingface.co/docs/accelerate/basic_tutorials/launch)，用于在不同硬件配置上配置和运行脚本
- [Big Model Inference](https://huggingface.co/docs/accelerate/usage_guides/big_modeling)（即 `device_map="auto"`）的发源地——不仅让用户能在多设备上对 LLM 做推理，现在还借助参数高效微调（PEFT）等技术，助力在小算力上训练 LLM

这三个侧面让 Accelerate 成为 **Hugging Face 几乎每个包的基石**，包括 `transformers`、`diffusers`、`peft`、`trl` 等等！

由于该包已经稳定近一年，我们兴奋地宣布：从今天起，我们发布了 **Accelerate 1.0.0 的首个候选版本（release candidate）**！

本博客将详述：

- 我们为什么决定做 1.0？
- Accelerate 的未来是什么？我们如何看待 PyTorch 整体的走向？
- 有哪些破坏性变更和弃用？如何轻松迁移？

## 为什么是 1.0？

发布 1.0.0 的计划酝酿了一年以上。API 大致已经到达我们期望的状态：以 `Accelerator` 为核心，简化大量配置并让它更可扩展。但我们知道，在把 `Accelerate` 的「基础」称为「功能完备」之前，还缺几块拼图：

- 集成 MS-AMP 和 `TransformersEngine` 的 FP8 支持（更多见[这里](https://github.com/huggingface/accelerate/tree/main/benchmarks/fp8/transformer_engine)和[这里](https://github.com/huggingface/accelerate/tree/main/benchmarks/fp8/ms_amp)）
- 支持使用 DeepSpeed 时多模型的编排（[Experimental](https://huggingface.co/docs/accelerate/usage_guides/deepspeed_multiple_model)）
- 为大模型推理 API 提供 `torch.compile` 支持（需要 `torch>=2.5`）
- 把 `torch.distributed.pipelining` 集成[为一种替代的分布式推理机制](https://huggingface.co/docs/accelerate/main/en/usage_guides/distributed_inference#memory-efficient-pipeline-parallelism-experimental)
- 把 `torchdata.StatefulDataLoader` 集成[为一种替代的 dataloader 机制](https://github.com/huggingface/accelerate/blob/main/examples/by_feature/checkpointing.py)

随着为 1.0 所做的这些改动，accelerate 已准备好在保持面向用户 API 稳定的同时，去接纳新技术集成。

## Accelerate 的未来

1.0 如今接近完成，我们可以把精力转向社区中不断涌现的新技术，并找到它们进入 Accelerate 的集成路径——因为我们预见 PyTorch 生态很快会发生根本性的变化：

- 在多模型 DeepSpeed 支持的工作中我们发现，DeepSpeed 当前的使用方式*大体上*可行，但为支持「为任意多模型训练场景准备模型」的简单封装，最终可能需要对整体 API 做较重的改动。
- 随着 [torchao](https://github.com/pytorch/ao) 和 [torchtitan](https://github.com/pytorch/torchtitan) 渐入佳境，它们暗示了整个 PyTorch 的未来。目标是更原生的 FP8 训练支持、新的分布式分片 API，以及对新版 FSDP（FSDPv2）的支持。我们预计，随着这些框架慢慢稳定，Accelerate 的许多内部实现和一般用法 API 都需要（希望改动不至于太剧烈）变化以满足这些需求。
- 顺着 `torchao`/FP8 的浪潮，许多新框架对「如何让 FP8 训练可用且稳定」带来了各自的想法和实现（`transformer_engine`、`torchao`、`MS-AMP`、`nanotron` 等等，仅举几例）。我们在 Accelerate 中的目标，是把这些实现收拢于一处、配以简单配置，让用户自由探索和测试每一种，从中找到最终最稳定、最灵活的方案。这个领域的研究正在飞速加速（双关语不请自来）——尤其是 NVIDIA 的 FP4 训练支持即将到来——我们要确保不仅支持每一种方法，还打算**为每种方法提供可靠的基准**，展示它们开箱即用（ minimal 调整）相对原生 BF16 训练的倾向。

我们对 PyTorch 生态分布式训练的未来无比兴奋，也希望 Accelerate 一路相伴，为这些新技术提供更低的入门门槛。借此，我们希望社区继续一起实验、一起学习，去寻找在更复杂计算系统上训练和扩展更大模型的最佳方法。

## 如何试用

今天想试用 Accelerate 的首个候选版本，请使用以下任一方式：

- pip：

```
pip install --pre accelerate
```

- Docker：

```
docker pull huggingface/accelerate:gpu-release-1.0.0rc1
```

有效的 release 标签有：

- `gpu-release-1.0.0rc1`
- `cpu-release-1.0.0rc1`
- `gpu-fp8-transformerengine-release-1.0.0rc1`
- `gpu-deepspeed-release-1.0.0rc1`

## 迁移帮助

以下是本次发布所执行的全部弃用细节：

- 向 `Accelerator()` 传入 `dispatch_batches`、`split_batches`、`even_batches` 和 `use_seedable_sampler`，现在应改为创建 `accelerate.utils.DataLoaderConfiguration()` 并把它传给 `Accelerator()`（`Accelerator(dataloader_config=DataLoaderConfiguration(...))`）
- `Accelerator().use_fp16` 和 `AcceleratorState().use_fp16` 已移除；应改用 `accelerator.mixed_precision == "fp16"` 检查
- `Accelerator().autocast()` 不再接受 `cache_enabled` 参数。取而代之，应使用 `AutocastKwargs()` 实例来处理这一标志（及其他标志），并把它传给 `Accelerator`（`Accelerator(kwargs_handlers=[AutocastKwargs(cache_enabled=True)])`）
- `accelerate.utils.is_tpu_available` 应替换为 `accelerate.utils.is_torch_xla_available`
- `accelerate.utils.modeling.shard_checkpoint` 应替换为 `huggingface_hub` 库中的 `split_torch_state_dict_into_shards`
- `accelerate.tqdm.tqdm()` 不再接受 `True`/`False` 作为第一个参数，`main_process_only` 应作为命名参数传入
- `ACCELERATE_DISABLE_RICH` 不再是有效的环境变量；应通过设置 `ACCELERATE_ENABLE_RICH=1` 手动启用 `rich` traceback
- FSDP 设置 `fsdp_backward_prefetch_policy` 已被 `fsdp_backward_prefetch` 取代
