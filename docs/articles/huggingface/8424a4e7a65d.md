# 在 Hugging Face 上部署 Speech-to-Speech

## 简介

[Speech-to-Speech (S2S)](https://github.com/huggingface/speech-to-speech) 是 Hugging Face 一个令人兴奋的新项目，它把多个先进模型组合起来，创造出一种无缝、近乎神奇的体验：你开口说话，系统用合成的声音回答你。

这个项目实现了一个级联式流水线，使用的都是 Transformers 库在 Hugging Face hub 上提供的模型。流水线由以下组件构成：

- 语音活动检测（Voice Activity Detection，VAD）
- 语音转文本（Speech to Text，STT）
- 语言模型（Language Model，LM）
- 文本转语音（Text to Speech，TTS）

不仅如此，S2S 还支持多语言！目前支持英语、法语、西班牙语、中文、日语和韩语。你可以让流水线以单语言模式运行，也可以用 `auto` 标志做自动语言检测。更多细节见 [repo](https://github.com/huggingface/speech-to-speech)。

```
> 👩🏽‍💻: That's all amazing, but how do I run S2S?
> 🤗: Great question!
```

运行 Speech-to-Speech 需要相当可观的算力。即使在高端笔记本上你也可能遇到延迟问题，尤其是使用最先进的模型时。强力 GPU 可以缓解这些问题，但并不是每个人都有条件（或意愿！)自备硬件。

这时就该轮到 Hugging Face 的 [Inference Endpoints (IE)](https://huggingface.co/inference-endpoints) 出场了。Inference Endpoints 允许你租用一台配备 GPU（或其他你需要的硬件）的虚拟机，只为系统运行的时间付费——对于部署 Speech-to-Speech 这类性能密集型应用，这是理想的解决方案。

在这篇博客中，我们将一步步指导你把 Speech-to-Speech 部署到 Hugging Face Inference Endpoint。内容包括：

- 认识 Inference Endpoints，快速了解搭建 IE 的几种方式，包括自定义容器镜像（正是 S2S 需要的）
- 为 S2S 构建自定义 docker 镜像
- 把自定义镜像部署到 IE，然后愉快地玩转 S2S！

## Inference Endpoints

Inference Endpoints 提供了一种可伸缩、高效的机器学习模型部署方式。它让你以极少的配置把模型作为服务提供，并使用多种强力硬件。对于需要高性能和高可靠、却不想自己管理底层基础设施的应用，Inference Endpoints 非常合适。

以下是几个关键特性，更多内容请务必查阅官方文档：

- **简单** - 得益于 IE 对 Hugging Face hub 上模型的直接支持，几分钟就能跑起来。
- **可伸缩** - 不用担心规模问题，IE 会自动伸缩，包括缩容到零，以应对波动的负载并节约成本。
- **可定制**：你可以自定义 IE 的配置来处理新任务，下面详细展开。

Inference Endpoints 支持所有 Transformers 和 Sentence-Transformers 任务，也支持自定义任务。IE 的搭建选项有：

- **预置模型（Pre-built Models）**：直接从 Hugging Face hub 快速部署模型。
- **自定义处理器（Custom Handlers）**：为更复杂的流水线定义自定义推理逻辑。
- **自定义 Docker 镜像（Custom Docker Images）**：用你自己的 Docker 镜像打包全部依赖和自定义代码。

对较简单的模型，选项 1 和 2 最为理想，让 IE 部署异常简单。但对 S2S 这样的复杂流水线，你需要选项 3 的灵活性：用自定义 Docker 镜像部署 IE。

这种方式不仅更灵活，还能通过优化构建过程、预先备好必要数据来提升性能。如果你在处理复杂的模型流水线，或想优化应用部署，本指南会给你有价值的思路。

## 在 Inference Endpoints 上部署 Speech-to-Speech

开始动手！

### 构建自定义 Docker 镜像

要从零开始创建自定义 Docker 镜像，我们先克隆 Hugging Face 默认的 Docker 镜像仓库。它是部署推理任务机器学习模型的绝佳起点。

```
git clone https://github.com/huggingface/huggingface-inference-toolkit
```

### 为什么克隆默认仓库？

- **稳固的基础**：仓库提供了一个专为推理工作负载预优化的基础镜像，是可靠的起点。
- **兼容性**：该镜像与 Hugging Face 的部署环境对齐构建，确保你部署自定义镜像时顺利集成。
- **易于定制**：仓库提供了干净、结构清晰的环境，方便按应用的具体需求定制镜像。

你可以[在这里查看我们的全部改动](https://github.com/andimarafioti/speech-to-speech-inference-toolkit/pull/1/files)

### 为 Speech-to-Speech 应用定制 Docker 镜像

克隆仓库后，下一步是定制镜像以支持我们的 Speech-to-Speech 流水线。

- 加入 Speech-to-Speech 项目

为了顺利集成，我们把 speech-to-speech 代码库和所需数据集作为 submodule 加进来。这样做版本控制更好，确保构建 Docker 镜像时代码和数据的版本永远精确可用。

把数据直接打进 Docker 容器，就不用每次实例化 endpoint 时重新下载，大幅缩短启动时间，也让系统可复现。数据存储在 Hugging Face 仓库中，便于追踪和版本管理。

```
git submodule add https://github.com/huggingface/speech-to-speech.git
git submodule add https://huggingface.co/andito/fast-unidic
```

- 优化 Docker 镜像

接下来，我们修改 Dockerfile 以适配需求：

- **给镜像瘦身**：移除与我们用例无关的包和依赖，缩小镜像体积，减少推理时的多余开销。
- **安装依赖**：把 `requirements.txt` 的安装从入口点挪进 Dockerfile。这样依赖在构建镜像时就装好了，部署更快，运行时不再需要安装这些包。

- 部署自定义镜像

改好之后，我们构建自定义镜像并推送到 Docker Hub：

```
DOCKER_DEFAULT_PLATFORM="linux/amd64" docker build -t speech-to-speech -f dockerfiles/pytorch/Dockerfile . 
docker tag speech-to-speech andito/speech-to-speech:latest 
docker push andito/speech-to-speech:latest
```

镜像构建并推送完成后，就可以用在 Hugging Face Inference Endpoint 里了。使用这个预构建镜像，endpoint 启动更快、运行更高效，因为所有依赖和数据都已预先打包在镜像里。

## 配置 Inference Endpoint

使用自定义 docker 镜像只需要稍有不同的配置，欢迎查阅[文档](https://huggingface.co/docs/inference-endpoints/en/guides/custom_container)。下面分别介绍 GUI 和 API 两种方式。

前置步骤

- 登录：[https://huggingface.co/login](https://huggingface.co/login)
- 申请访问 [meta-llama/Meta-Llama-3.1-8B-Instruct](https://huggingface.co/meta-llama/Meta-Llama-3.1-8B-Instruct)
- 创建一个 Fine-Grained Token：[https://huggingface.co/settings/tokens/new?tokenType=fineGrained](https://huggingface.co/settings/tokens/new?tokenType=fineGrained) [![Fine-Grained Token](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/s2s_endpoint/fine-grained-token.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/s2s_endpoint/fine-grained-token.png) 勾选对 gated repo 的访问权限。如果使用 API，记得授予 Manage Inference Endpoints 权限

### Inference Endpoints GUI

- 打开 [https://ui.endpoints.huggingface.co/new](https://ui.endpoints.huggingface.co/new)
- 填写相关信息 Model Repository - `andito/s2s` Model Name - 不喜欢自动生成的名字可以改，比如 `speech-to-speech-demo`，保持小写、简短   选择 Cloud 和 Hardware - 我们用了 `AWS` `GPU` `L4`，每小时只要 `$0.80`，跑这些模型绰绰有余   Advanced Configuration（点击展开箭头 ➤）Container Type - `Custom` Container Port - `80` Container URL - `andito/speech-to-speech:latest` Secrets - `HF_TOKEN`|`<your token here>`

Click to show images

![New Inference Endpoint](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/s2s_endpoint/new-inference-endpoint.png)

![Advanced Configuration](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/s2s_endpoint/advanced-configuration.png)

3. 点击 `Create Endpoint`

> 由于模型是在容器创建阶段指定并下载的，Model Repository 其实并不重要；但 Inference Endpoints 要求填一个模型，随便挑个轻量的即可。

> 必须指定 HF_TOKEN，因为容器创建阶段要下载 gated 模型。如果你用的模型不是 gated 或私有的，就不需要这一步。

> 当前的 huggingface-inference-toolkit 入口点默认使用 5000 端口，但 inference endpoint 期望 80 端口，Container Port 要与它保持一致。我们的 dockerfile 里已经配好，但你从头自建时要多加留意！

### Inference Endpoints API

这里介绍用 API 创建 endpoint 的步骤，直接在你的 Python 环境里运行以下代码。

确保版本 `0.25.1` 或更高

```
pip install huggingface_hub>=0.25.1
```

使用一个可以写入 endpoint 的 [token](https://huggingface.co/docs/hub/en/security-tokens)（Write 或 Fine-Grained）

```
from huggingface_hub import login
login()
```

```
from huggingface_hub import create_inference_endpoint, get_token
endpoint = create_inference_endpoint(
    # Model Configuration
    "speech-to-speech-demo",
    repository="andito/s2s",
    framework="custom",
    task="custom",
    # Security
    type="protected",
    # Hardware
    vendor="aws",
    accelerator="gpu",
    region="us-east-1",
    instance_size="x1",
    instance_type="nvidia-l4",
    # Image Configuration
    custom_image={
        "health_route": "/health",
        "url": "andito/speech-to-speech:latest", # Pulls from DockerHub
        "port": 80
    },
    secrets={'HF_TOKEN': get_token()}
)

# Optional
endpoint.wait()
```

## 总览

[![Overview](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/s2s_endpoint/overview.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/s2s_endpoint/overview.png)

主要组件

- [Speech To Speech](https://github.com/huggingface/speech-to-speech/tree/inference-endpoint)：这是 Hugging Face 的一个库，我们把一些 inference-endpoint 专用的文件放在 `inference-endpoint` 分支上，不久会合并到 main。
- andito/s2s 或任意其他仓库。对我们来说这并非必需——模型已在容器创建阶段就位——但 inference-endpoint 要求指定一个模型，所以我们传了一个轻量仓库。
- [andimarafioti/speech-to-speech-toolkit](https://github.com/andimarafioti/speech-to-speech-inference-toolkit)：从 [huggingface/huggingface-inference-toolkit](https://github.com/huggingface/huggingface-inference-toolkit) fork 而来，帮助我们按自己的需求构建自定义容器。

### 搭建 webserver

要使用这个 endpoint，我们需要构建一个小型 webservice。相关代码一部分在 [speech_to_speech 库](https://github.com/huggingface/speech-to-speech)的 `s2s_handler.py`（客户端使用），一部分在 [speech_to_speech_inference_toolkit](https://github.com/huggingface/speech-to-speech-inference-toolkit) 的 `webservice_starlette.py`（用于构建 docker 镜像）。通常 endpoint 只需要一个自定义 handler，但因为我们追求极低延迟，webservice 也做成了支持 websocket 连接而非普通请求。听起来唬人，其实这个 webservice 只有 32 行代码！

![Webservice code](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/s2s_endpoint/webservice.png)

这段代码会在启动时运行 `prepare_handler`，初始化所有模型并预热。之后每条消息都由 `inference_handler.process_streaming_data` 处理。

![Process streaming code](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/s2s_endpoint/process_streaming.png)

这个方法接收客户端的音频数据，切成小块交给 VAD，再提交到处理队列。然后检查输出处理队列（模型说出来的回答！），有结果就返回。所有内部处理都由 [Hugging Face 的 speech_to_speech 库](https://github.com/huggingface/speech-to-speech)完成。

### 自定义 handler 与自定义客户端

webservice 收发音频。但还缺一大块：怎么录制和播放音频？为此我们写了[一个客户端](https://github.com/huggingface/speech-to-speech/blob/inference-endpoint/audio_streaming_client.py)连接服务。最容易的理解方式，是把分析拆成"连接 webservice"和"录制/播放音频"两部分。

![Audio client code](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/s2s_endpoint/client.png)

初始化 webservice 客户端时，要为所有消息设置一个 header，携带我们的 Hugging Face Token。初始化客户端时，还要指定常见消息（open、close、error、message）的处理动作，决定服务器发来消息时客户端的行为。

![Audio client messages code](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/s2s_endpoint/messages.png)

可以看到，各消息的处理都很直接，只有 `on_message` 稍复杂。这个方法能判断服务器何时说完，然后转回"聆听"用户的状态；否则就把服务器数据放进播放队列。

![Client's audio record and playback](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/s2s_endpoint/client-audio.png)

客户端音频部分有 4 个任务：

- 录制音频
- 提交录制的音频
- 接收服务器的音频响应
- 播放音频响应

音频在 `audio_input_callback` 方法里录制，它只是把所有数据块塞进队列，随后由 `send_audio` 方法发给服务器。这里如果没有音频可发，我们仍然提交一个空数组，以便收到服务器的响应。服务器的响应由前文见过的 `on_message` 方法处理。音频响应的播放则由 `audio_output_callback` 方法处理——这里只需确保音频在预期范围内（可不想因为某个有问题的包把人的耳膜搞坏！），并确保输出数组的大小符合播放库的期望。
