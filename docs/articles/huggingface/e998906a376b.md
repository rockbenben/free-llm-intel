## Kernels——一种新的仓库类型

我们在 Hub 上新增了一种名为 ["kernel"](https://huggingface.co/kernels) 的仓库类型。这让我们能更好地服务有算力相关需求的用户。例如，用户可以直观了解某个内核支持哪些加速卡、操作系统和后端版本：

Kernel 页面：

kernels-community/flash-attn3

所有可用的 kernels 可以在这里浏览：[https://huggingface.co/kernels](https://huggingface.co/kernels)。

让内核成为 Hub 的一等公民，也让 AI 生态受益。用户现在可以观察内核、模型以及使用它们的应用之间的趋势，内核也因此更容易被用户发现。

## 安全性改进

内核运行的是原生代码，权限与加载它的 Python 进程相同，所以一个恶意内核可以造成真实危害。因此，安全一直是 Kernels 项目的重中之重。

这也是我们很早便聚焦可复现性的原因：你应该能自己重新编译一个内核，并验证它与公开源码一致。我们用 Nix 来实现这一点——它通过构建配方的密封（hermetic）求值与强隔离沙箱，保证构建的纯净。我们还把源码的 Git SHA1 嵌入内核本身，进一步强化溯源。

近几个月，我们又加了几层防线：受信内核发布者（trusted publishers）和代码签名。

### 受信内核发布者

伴随新的仓库类型，我们引入了"受信发布者"。由于内核在与 Python 进程相同权限下执行代码，攻击者可能通过上传恶意内核并诱使你使用它来攻破机器。为帮你避开这类恶意内核，kernels 包现在默认只加载*受信发布者*的内核。所谓受信发布者，是被社区信任、会善意行事的组织。

我们仍然支持加载来自非受信组织或用户的内核，但你必须在从 Hub 加载内核时显式通过 `trust_remote_code` 参数选择加入：

```
from kernels import get_kernel

kernel_module = get_kernel(  
   “Atlas-Inference/gdn”, version=1, trust_remote_code=True  
)  
```

默认情况下，用户不能在 Hub 上发布内核仓库，需要先申请成为内核发布者。用户和组织可以在账号设置里提交申请，这会让我们有时间逐一审核这些请求。

### 内核签名

我们添加的另一层安全机制是代码签名。代码签名防范这样一种场景：攻击者窃取了某个受信发布者账号的 Hub 凭证，然后向其内核仓库上传恶意内核。代码签名中，内核由只有内核开发者掌握的私钥签名，再用公开可得的公钥验证。在 Hub 被入侵的场景下，攻击者没有签名所需的私钥，就无法给恶意内核签名。

为进一步提升安全性，我们使用 Sigstore 的 cosign 以临时私钥签名。这些签名密钥只在有限时间内有效，即使泄露，攻击者通常也无法利用。我们还会验证内核确实由受信 GitHub 仓库中受信的 GitHub workflow 签名。

`kernel-builder` 已经支持内核签名，我们提供了 `kernels verify-signature` 来验证一个内核。Kernels 在加载内核时暂未自动校验签名——我们希望在全面推广前再多测试这一新功能。为自己的内核配置代码签名的初步说明见 kernels 0.16.0 的发布说明：[https://github.com/huggingface/kernels/releases/tag/v0.16.0](https://github.com/huggingface/kernels/releases/tag/v0.16.0)。

## 全新 CLI

此前，大量工具能力交织在 `kernels` 和 `kernel-builder` 之间。我们为两者的 CLI 建立了更清晰的关注点分离。心智模型是：`kernels` 是用于加载内核并为其使用做准备的库，因此不应包含任何与"构建"内核相关的内容。

结果是，`kernels` 和 `kernel-builder` 都变得更精简、更有针对性。详情参见文档：

- [`kernels` CLI](https://huggingface.co/docs/kernels/en/cli)
- [`kernel-builder` CLI](https://huggingface.co/docs/kernels/en/builder-cli)

改进后的 CLI 体验也让我们能更好地适应智能体（agentic）内核开发的兴起。这一点[稍后](https://huggingface.co/blog/revamped-kernels#foundation-for-agentic-kernel-development)再谈。

## 更广的框架与后端覆盖

我们扩展了对框架的支持，最显见的变化有：

- kernels 和 kernel-builder 新增了对 Torch Stable ABI 的支持。Torch Stable ABI 让内核开发者可以瞄准某个特定 Torch 版本，或其后大约两年内发布的任意版本。例如，针对 Torch 2.9 Stable ABI 的内核支持 Torch >= 2.9。
- Apache TVM FFI 是继 Torch 之后首个获得支持的框架。TVM FFI 是一种标准化的内核 ABI，可与 PyTorch、Jax、CuPy 等其他框架互操作，让开发者写出能跨框架运行的内核。

## 智能体内核开发的基础

`kernel-builder` 和 `kernels` 与智能体内核开发的兴起相辅相成——在这类开发中，智能体被用来从零产出（优化过的）内核。两者共同支撑了一条智能体可以搭脚手架、构建、跑基准并迭代优化内核的工作流。

智能体内核开发仍处于早期，合适的开发循环还会持续演化。正因如此，简单清晰的基座尤为重要——工具应当容易被组合进人们选择的任意智能体工作流或框架中。

`kernel-builder` 帮助强制一种结构：内核源码应如何搭脚手架、如何用于可复现构建。这为智能体提供了可预期的项目布局和可重复的工作流。它的 CLI 也是按[智能体优先](https://huggingface.co/blog/is-it-agentic-enough)设计的，例如非交互式命令、输出便于智能体以编程方式解读。为此我们还提供了[后端专属 skills](https://huggingface.co/docs/kernels/en/cli-skills)，帮助智能体驾驭不同后端的各种特性。这些 skills 会记录后端专属的工具链、编译路径和性能考量。

成功构建内核并不是唯一目标，我们还要确保它在目标硬件上相对基线真正提速。因此成功构建只是第一个验证步骤。目标硬件通常包含许多不同的加速卡，甚至同一加速卡的不同代际。

这使得跨硬件厂商、必要时跨代际地评估结果非常重要。我们与 HF Jobs 的深度[集成](https://huggingface.co/docs/kernels/en/builder/github-actions)能让这一基准测试过程变得简单。智能体可以利用该集成运行基准套件、收集性能结果，并与设定基线对比。

这样，智能体就能在不同硬件配置上跑测试，对生成内核的性能获得可靠反馈，明确下一步该做什么。这些反馈随后会指导下一轮优化迭代。

## 杂项

### 环境搭建

用 `kernel-builder` 构建内核的环境搭建可能让人头大。为方便用户，我们现在提供了一个[安装脚本](https://huggingface.co/docs/kernels/en/builder/writing-kernels#quick-install)，一键配好环境。如果你偏好使用临时实例，可以参考我们的 [Terraform 配置指南](https://github.com/huggingface/kernels/tree/main/terraform)。

### 内核的 system card

内核构建完成后，我们会为每个内核生成一份 system card，暴露有用信息，包括使用方法和对外接口。当内核推送到 Hub 时，这份 system card 就成了该内核的 front matter：

### 我的系统上能用这个内核吗？

这是为做规划时人们会反复询问的问题。可以用 [`has_kernel()`](https://huggingface.co/docs/kernels/main/en/api/kernels#kernels.has_kernel) 方法：

```
from kernels import has_kernel

print(has_kernel("kernels-community/activation", version=1))  
```

它返回一个 `bool`。如果你想知道某个内核不被支持的更多原因，请用 [`get_kernel_variants()`](https://huggingface.co/docs/kernels/main/en/api/kernels#kernels.get_kernel_variants)：

```
 from kernels import get_kernel_variants, VariantAccepted

for decision in get_kernel_variants("kernels-community/activation", version=1):  
    name = decision.variant.variant_str  
    if isinstance(decision, VariantAccepted):  
        print(f"{name}: compatible")  
    else:  
        print(f"{name}: rejected ({decision.reason})")  
```

应输出如下内容（取决于你所在的机器）：

```
torch212-cxx11-cu130-aarch64-linux: compatible  
torch210-cu128-x86_64-windows: rejected (CPU (x86_64) does not match system CPU (aarch64))  
torch211-cu128-x86_64-windows: rejected (CPU (x86_64) does not match system CPU (aarch64))  
torch212-metal-aarch64-darwin: rejected (OS (darwin) does not match system OS (linux))  
torch211-metal-aarch64-darwin: rejected (OS (darwin) does not match system OS (linux))  
torch210-metal-aarch64-darwin: rejected (OS (darwin) does not match system OS (linux))  
torch29-metal-aarch64-darwin: rejected (OS (darwin) does not match system OS (linux))  
…  
```

### 改进的 manylinux_2_28 支持

kernel-builder 几乎从一开始就以 `manylinux_2_28` 为目标。此前我们用一个以 glibc 2.28 编译的现代 gcc 工具链来达成 manylinux 目标，并且为避免与老版本 `libstdc++` 的兼容问题，静态链接了 libstdc++。

但这个做法最近引发了一些问题。某些 `libstdc++` 功能会使用全局初始化。当多个 `libstdc++` 版本同时存在时——例如 PyTorch 动态链接的那份和内核静态链接的那份——就可能导致数据损坏。最近的一些内核用到了会触发全局初始化的功能（如 C++ 正则），造成数据损坏，进而导致段错误等问题。

为了解决这个问题，内核现在动态链接 `libstdc++`。为保证与老版本 `libstdc++` 的兼容性，我们改用官方 `manylinux_2_28` 工具链编译内核。

## 结论

Kernels 项目的目标是同时服务好内核开发者和自定义内核的使用者。我们始终乐于接收社区关于如何改进它的反馈。欢迎贡献！
