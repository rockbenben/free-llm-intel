# 构建深度研究代理：我们如何做到 SOTA

研究代理（research agent）正迅速成为 AI 最重要的应用之一。研究是一项基础性的知识工作任务：收集、阅读和综合信息，支撑着从写作、决策到编码本身的一切。然而由人主导的研究受限于记忆、阅读速度和时间。相比之下，AI 研究代理可以处理海量信息、即时综合洞见，并轻松实现规模化。正因如此，研究代理正在成为当今 AI 的顶级用例，并且很快就会成为内容生成、编码、销售等更广泛代理工作流中的核心子组件。在这篇文章中，我们分享构建**最先进（state-of-the-art）研究代理**过程中学到的技术与理念层面的经验，以及我们对该领域走向的判断。

## 为未来而构建

### 代理框架（Agent Harness）

构建 [agent harness](https://www.vtrivedy.com/posts/claude-code-sdk-haas-harness-as-a-service?ref=blog.langchain.com) 的任务，是创造一个软件层，通过上下文管理、工具调用、循环控制、编排和错误处理来增强模型的运行时执行。然而，在快速迭代的模型之上构建应用是一个现代工程挑战。我们如何设计今天的软件，使其能吸收未来模型发布带来的性能增益？

这要求我们预判模型的演化方向、对其进步保持乐观、少做假设，并避免手工定制的优化。

七个月前我们用惨痛代价学到了这一点：当时我们不得不放弃第一版 deep research，把整个系统从零重建。第一版架构复杂而精巧（我们当时以为这是好事），但当下一代模型到来时，它的各种假设都成了瓶颈。

### 模型

过去七个月里，模型能力在悄无声息中有了实质性演进（尤其是工具调用能力）。正是这一优化焦点把我们从 workflow 推向了 agent。我们相信未来的模型会被训练去解决当前代理开发者的痛点。每个模型最终都要被某个 harness 消费，因此模型的演进应当服务于 harness。我们希望看到模型在高召回摘要（用于上下文压缩）、工具调用可靠性和写作简洁性方面继续提升。

### 工具

同样，工具的演进应当支持 LLM 和广泛采用的代理 harness。最好的工具应当在工具侧完成一部分 context engineering，对代理透明封装。它们应当只返回最相关的数据，而不是把海量 token 倾倒进上下文窗口。作为一家工具提供商，我们在[高级搜索](https://docs.tavily.com/documentation/api-reference/endpoint/search#body-search-depth)功能上投入巨大，其内建了 context engineering。这反过来降低了下游代理流程的幻觉率和延迟。

### 要点

要让代理随时间不断变强，我们遵循了几条指导原则：

- 简化编排逻辑，拥抱自主性。
- 密切关注模型和工具被优化的方向，并利用它们新出现的能力。
- 专注于 context engineering（下一节详述）。

## Context Engineering——一场精选的艺术

长周期研究任务暴露了当前代理设计中的一个根本挑战：如何随时间维护一个干净、优化的上下文窗口。如果工程师不把上下文的精选当作头等大事，代理几乎注定失败。以下是我们在深度研究领域对这一概念的思考。

### 上下文受控的网页检索

使用 Tavily 的 Advanced Search 是应对这一挑战的自然第一步：它抽象掉了原始网页内容的处理过程，只从每个来源返回最相关的内容块。借助这一能力，我们让 Tavily Search 承担重活，Tavily Research 从中受益，以低延迟高效的方式获取最有价值的内容。

确保代理不过拟合于单一研究线索，是构建高效上下文收集流水线的下一步。正因如此，全局状态持久化和来源去重至关重要，在我们的场景中它带来了三方面的好处：

- 确保代理只接触新鲜信息。
- 让工程师能够识别信息范围正在收窄的时机，并提示代理去探索尚未触及的相关领域。
- 有助于在后续生成过程中进行有效的来源归因。

对 Tavily 来说，与网页打交道是我们的看家本领。为深度研究精心设计的网页检索系统，是我们整个深度研究代理设计的基础构件之一。

### 建模人与网页的交互

人类的研究天然是非结构化、迭代的。我们先定义任务：想要完成什么、需要什么信息。然后从各种来源收集数据，提炼关键洞见并暂存于短期记忆，让这些精炼后的思考指导接下来的行动。

这个循环不断重复：收集信息、提炼、决定下一步做什么。只有当我们积累了足够的理解、可以产出最终交付物时，我们才会回到原始来源，把它们作为参考来组装成品。

我们认为深度研究代理也应当以类似方式设计：工具输出应被提炼为反思（reflection），而**只**把历史反思的集合用作工具调用模型的上下文。与人类一样，只有当代理开始准备最终交付物时，才必须把原始信息作为上下文提供，以确保没有信息损失。

### 少即是多

这种方式不同于 ReAct 代理架构中的传统上下文组织。通常情况下，工具调用及其输出会在工具调用循环中不断传递，此前检索/生成的 token 在每次后续迭代中都会留在上下文窗口里。这一模式可以在 [LangChain 的 Open Deep Research](https://github.com/langchain-ai/open_deep_research) 代理实现中看到；从 token 消耗的角度，它可以用如下二次级数建模，其中 n n n 是每次工具调用迭代时调用工具模型的 token 数，m m m 是工具调用的迭代次数。

n+2n+3n+⋯+mn = n⋅m(m+1)2n + 2n + 3n + \cdots + mn \;=\; n \cdot \frac{m(m+1)}{2}n+2n+3n+⋯+mn=n⋅2m(m+1)​

[![Group 29](https://cdn-uploads.huggingface.co/production/uploads/691cbf41fd922ec2d851f771/zBVSQrGwtMnMVOZwaRRhh.png)](https://cdn-uploads.huggingface.co/production/uploads/691cbf41fd922ec2d851f771/zBVSQrGwtMnMVOZwaRRhh.png)

相反，我们提出的 context engineering 方法去掉了这种 token 传递（因为知识蒸馏的产物即使累计起来，与从网页获取的 token 量相比也可忽略不计），可以用如下线性级数建模。

n+n+n+⋯+n = nmn + n + n + \cdots + n \;=\; nmn+n+n+⋯+n=nm

[![Group 30](https://cdn-uploads.huggingface.co/production/uploads/691cbf41fd922ec2d851f771/1W0Y8YDgXIYhcRuH3ZDwv.png)](https://cdn-uploads.huggingface.co/production/uploads/691cbf41fd922ec2d851f771/1W0Y8YDgXIYhcRuH3ZDwv.png)

对比两种方法，每个代理节省的 token 达到 m+12 \frac{m+1}{2} 2m+1​ 倍；把这一点外推到多代理系统、并考虑规模化消耗后，节省的 token 绝对数量更加可观。

借助这套方法论，我们在 [DeepResearch Bench](https://huggingface.co/spaces/muset-ai/DeepResearch-Bench-Leaderboard) 上取得 SOTA 的同时，**将 token 消耗降低了 66%**（与 Open Deep Research 相比）——质量与效率的统一体现得淋漓尽致。

## 代理的生产化——一个进行中的挑战

构建生产级代理是一种平衡艺术。我们拥抱自主性以最大化性能和质量，同时仍要满足对延迟、成本和可靠性的严苛要求。

### 与非确定性共处

LLM 天生是非确定性的，我们发现给予它们有护栏的自由去推理和迭代，能产生最强的结果。自主性一旦失控，可能导致代理行为脱轨：工具可能被错误调用、LLM 可能过拟合到某个子话题、预期的推理模式可能失效。没有任何单一保障手段能捕获所有这些问题。

工程思维需要转变：把失效模式当作核心设计考量，而不是事后补丁。简单的护栏——如工具调用重试或模型级联——有帮助，但真正让长时间运行的代理达到生产级的，是主动预判异常、在提示词中强化正确模式，以及边缘用例测试。

### 最优工具——少即是多

根据我们的经验，向代理暴露一个精小的核心工具集，好过一个庞大复杂的工具集。我们曾受到诱惑去过度工程化，添加许多理论上看起来有用的工具，但实践中这带来了新的失效模式，让 LLM 更难稳定选对工具并有效迭代。

### 评估（Evals）

我们用 evals 来引导开发流程，但也清楚它们的局限。LLM-as-a-judge 式评估很难被信任：当前模型是非确定性的、推理过程不可解释，而且可能成为瓶颈——对长时间运行的代理尤其如此，单个实验可能要跑好几天。

我们没有为基准分数做优化，而是为方向性反馈做优化。核心问题始终是：这次改动让代理在实践中更可靠、更有用了吗？Evals 成了验证方向的工具，而不是优化目标。直觉加上细致的代理 trace 监控，提供的信号始终比任何一个评估分数更高。总体而言，最好的结果很少是那个最高数字分数。对生产系统来说，token 用量降低、可靠性提升、延迟下降、失败更少这类改进，比 eval 上高出一分更有价值。
