# 使用 TF Serving 在 Kubernetes 上部署 🤗 ViT

在[上一篇文章](https://huggingface.co/blog/tf-serving-vision)中，我们演示了如何用 TensorFlow Serving 在本地部署 🤗 Transformers 的 [Vision Transformer (ViT)](https://huggingface.co/docs/transformers/main/en/model_doc/vit) 模型。内容涵盖在 Vision Transformer 模型内部嵌入预处理与后处理操作、处理 gRPC 请求等主题！

本地部署虽然是很好的起步，能快速做出有用的东西，但真实项目往往需要能服务大量用户的部署方式。本文将教你如何用 Docker 和 Kubernetes 把上一篇文章中的本地部署扩展开。因此，我们假设你对 Docker 和 Kubernetes 有一定了解。

本文建立在[上一篇文章](https://huggingface.co/blog/tf-serving-vision)之上，强烈建议先阅读那篇。本文讨论的全部代码都在[这个仓库](https://github.com/sayakpaul/deploy-hf-tf-vision-models/tree/main/hf_vision_model_onnx_gke)中。

## 为什么选 Docker 和 Kubernetes？

扩展我们这类部署的基本工作流包括以下步骤：

- **容器化应用逻辑**：应用逻辑即对外提供服务的模型，它能处理请求并返回预测结果。容器化方面，Docker 是行业标准选择。
- **部署 Docker 容器**：这里有多种选项。最常用的是把 Docker 容器部署在 Kubernetes 集群上。Kubernetes 提供了大量利于部署的特性（例如自动扩缩容和安全）。你可以用 [Minikube](https://minikube.sigs.k8s.io/docs/start/) 这类方案在本地管理 Kubernetes 集群，或者用 [Elastic Kubernetes Service (EKS)](https://docs.aws.amazon.com/eks/latest/userguide/what-is-eks.html) 这类无服务器方案。

你可能会问：在有了 [Sagemaker](https://aws.amazon.com/sagemaker/)、[Vertex AI](https://cloud.google.com/vertex-ai) 这些开箱即用地提供 ML 部署特性的平台时代，为什么还要搭这样一套显式的架构？这个疑问很合理。

上述工作流在业界被广泛采用，许多组织从中受益，并且已经历多年实战检验。它在把复杂部分抽象掉的同时，让你对部署保留更细粒度的控制。

本文使用 [Google Kubernetes Engine (GKE)](https://cloud.google.com/kubernetes-engine) 来开通和管理 Kubernetes 集群。如果用的是 GKE，我们假设你已经有一个开通了计费的 GCP 项目。另外注意，需要配置 [`gcloud`](https://cloud.google.com/sdk/gcloud) 工具才能在 GKE 上执行部署。但本文讲的概念同样适用于你决定使用 Minikube 的情况。

**注意**：只要配置好了 `gcloud` 工具以及 Docker 和 `kubectl`，本文的代码片段都可以在 Unix 终端上直接执行。更多说明见[配套仓库](https://github.com/sayakpaul/deploy-hf-tf-vision-models/tree/main/hf_vision_model_onnx_gke)。

## 用 Docker 容器化

可服务模型能够直接处理字节形式的原始图像输入，并具备预处理和后处理能力。

本节演示如何用 [TensorFlow Serving 基础镜像](http://hub.docker.com/r/tensorflow/serving/tags/)把该模型容器化。TensorFlow Serving 使用 [`SavedModel`](https://www.tensorflow.org/guide/saved_model) 格式的模型。回想一下，我们在[上一篇文章](https://huggingface.co/blog/tf-serving-vision)里已经得到了这样一个 `SavedModel`。这里假设 `SavedModel` 已压缩为 `tar.gz` 格式；以防万一，你也可以从[这里](https://huggingface.co/deploy-hf-tf-vit/vit-base16-extended/resolve/main/saved_model.tar.gz)获取。然后 `SavedModel` 需要放入 `<MODEL_NAME>/<VERSION>/<SavedModel>` 这一特殊目录结构中，TensorFlow Serving 正是靠它同时管理多个不同版本模型的部署。

### 准备 Docker 镜像

下面的 shell 脚本把 `SavedModel` 放到父目录 models 下的 `hf-vit/1` 中。制作 Docker 镜像时会把其中的所有内容拷贝进去。本例只有一个模型，但这是更通用、可扩展的做法。

```
$ MODEL_TAR=model.tar.gz
$ MODEL_NAME=hf-vit
$ MODEL_VERSION=1
$ MODEL_PATH=models/$MODEL_NAME/$MODEL_VERSION

$ mkdir -p $MODEL_PATH
$ tar -xvf $MODEL_TAR --directory $MODEL_PATH
```

下面展示我们环境中 `models` 目录的结构：

```
$ find /models
/models
/models/hf-vit
/models/hf-vit/1
/models/hf-vit/1/keras_metadata.pb
/models/hf-vit/1/variables
/models/hf-vit/1/variables/variables.index
/models/hf-vit/1/variables/variables.data-00000-of-00001
/models/hf-vit/1/assets
/models/hf-vit/1/saved_model.pb
```

自定义的 TensorFlow Serving 镜像应在[基础镜像](http://hub.docker.com/r/tensorflow/serving/tags/)之上构建。做法有多种，我们按照[官方文档](https://www.tensorflow.org/tfx/serving/serving_kubernetes#commit_image_for_deployment)的方式，通过运行 Docker 容器来完成。先在后台模式启动 `tensorflow/serving` 镜像，然后把整个 `models` 目录拷贝进运行中的容器，如下所示。

```
$ docker run -d --name serving_base tensorflow/serving
$ docker cp models/ serving_base:/models/
```

我们以 TensorFlow Serving 官方 Docker 镜像为基础，但你也可以用[从源码构建](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/g3doc/setup.md#building-from-source)的镜像。

**注意**：TensorFlow Serving 能从硬件优化中获益，例如利用 [AVX512](https://en.wikipedia.org/wiki/AVX-512) 之类的指令集，这些指令集可以[加速深度学习模型推理](https://huggingface.co/blog/bert-cpu-scaling-part-1)。因此，如果你知道模型将部署在什么硬件上，通常会受益于获取 TensorFlow Serving 镜像的优化构建版并全程使用它。

现在运行中的容器已按正确的目录结构放好了所有必需文件，接下来需要创建一个包含这些变更的新 Docker 镜像。用下面的 [`docker commit`](https://docs.docker.com/engine/reference/commandline/commit/) 命令即可完成，你会得到名为 `$NEW_IMAGE` 的新 Docker 镜像。有一点很重要：需要把 `MODEL_NAME` 环境变量设置为模型名，本例即 `hf-vit`。这告诉 TensorFlow Serving 要部署哪个模型。

```
$ NEW_IMAGE=tfserving:$MODEL_NAME

$ docker commit \ 
    --change "ENV MODEL_NAME $MODEL_NAME" \ 
    serving_base $NEW_IMAGE
```

### 在本地运行 Docker 镜像

最后，在本地运行新构建的 Docker 镜像，确认一切正常。下面是 `docker run` 命令的输出。由于输出冗长，我们做了精简以突出关键信息。另外值得注意的是，它开放了 `8500` 和 `8501` 端口，分别用于 gRPC 和 HTTP/REST 端点。

```
$ docker run -p 8500:8500 -p 8501:8501 -t $NEW_IMAGE &


---------OUTPUT---------
(Re-)adding model: hf-vit
Successfully reserved resources to load servable {name: hf-vit version: 1}
Approving load for servable version {name: hf-vit version: 1}
Loading servable version {name: hf-vit version: 1}
Reading SavedModel from: /models/hf-vit/1
Reading SavedModel debug info (if present) from: /models/hf-vit/1
Successfully loaded servable version {name: hf-vit version: 1}
Running gRPC ModelServer at 0.0.0.0:8500 ...
Exporting HTTP/REST API at:localhost:8501 ...
```

### 推送 Docker 镜像

这里的最后一步是把 Docker 镜像推送到镜像仓库。我们使用 [Google Container Registry (GCR)](https://cloud.google.com/container-registry) 来完成。以下几行代码即可搞定：

```
$ GCP_PROJECT_ID=<GCP_PROJECT_ID>
$ GCP_IMAGE=gcr.io/$GCP_PROJECT_ID/$NEW_IMAGE

$ gcloud auth configure-docker
$ docker tag $NEW_IMAGE $GCP_IMAGE
$ docker push $GCP_IMAGE
```

由于用的是 GCR，需要在 Docker 镜像 tag 前加 `gcr.io/<GCP_PROJECT_ID>` 前缀（[注意](https://cloud.google.com/container-registry/docs/pushing-and-pulling)，还有其他格式）。Docker 镜像准备好并推送到 GCR 后，就可以继续在 Kubernetes 集群上部署了。

## 部署到 Kubernetes 集群

在 Kubernetes 集群上部署需要：

- 开通一个 Kubernetes 集群，本文使用 [Google Kubernetes Engine](https://cloud.google.com/kubernetes-engine)（GKE）完成。当然你也可以选用 EKS 或 Minikube 等其他平台和工具。
- 连接到 Kubernetes 集群以执行部署。
- 编写 YAML manifest。
- 用工具 [`kubectl`](https://kubernetes.io/docs/reference/kubectl/) 配合 manifest 执行部署。

逐步来看。

### 在 GKE 上开通 Kubernetes 集群

可以用这样一个 shell 脚本（见[这里](https://github.com/sayakpaul/deploy-hf-tf-vision-models/blob/main/hf_vision_model_tfserving_gke/provision_gke_cluster.sh)）：

```
$ GKE_CLUSTER_NAME=tfs-cluster
$ GKE_CLUSTER_ZONE=us-central1-a
$ NUM_NODES=2
$ MACHINE_TYPE=n1-standard-8

$ gcloud container clusters create $GKE_CLUSTER_NAME \
    --zone=$GKE_CLUSTER_ZONE \
    --machine-type=$MACHINE_TYPE \
    --num-nodes=$NUM_NODES
```

GCP 提供多种机型供你按需配置部署。建议查阅[文档](https://cloud.google.com/sdk/gcloud/reference/container/clusters/create)了解更多。

集群开通后，需要连接到集群才能执行部署。由于这里用的是 GKE，还需要完成身份认证。可以用这样一个 shell 脚本一次完成两件事：

```
$ GCP_PROJECT_ID=<GCP_PROJECT_ID>

$ export USE_GKE_GCLOUD_AUTH_PLUGIN=True

$ gcloud container clusters get-credentials $GKE_CLUSTER_NAME \
    --zone $GKE_CLUSTER_ZONE \
    --project $GCP_PROJECT_ID
```

`gcloud container clusters get-credentials` 命令同时负责连接集群和身份认证。完成后就可以编写 manifest 了。

### 编写 Kubernetes manifest

Kubernetes manifest 以 [YAML](https://yaml.org/) 文件编写。虽然可以用单个 manifest 文件完成部署，但拆成多个文件通常更有助于职责分离。常见做法是使用三个 manifest 文件：

- `deployment.yaml` 定义 Deployment 的期望状态：Docker 镜像名称、运行 Docker 镜像时的附加参数、对外开放的端口以及资源限制。
- `service.yaml` 定义外部客户端与 Kubernetes 集群内部 Pod 之间的连接。
- `hpa.yaml` 定义伸缩 Deployment 所含 Pod 数量的规则，例如 CPU 利用率百分比。

本文相关的 manifest 见[这里](https://github.com/sayakpaul/deploy-hf-tf-vision-models/tree/main/hf_vision_model_tfserving_gke/.kube/base)。下面是这些 manifest 被消费方式的图示。

[![](https://huggingface.co/blog/assets/94_tf_serving_kubernetes/manifest_propagation.png)](https://huggingface.co/blog/assets/94_tf_serving_kubernetes/manifest_propagation.png)

接下来逐个看每个 manifest 的关键部分。

**`deployment.yaml`**：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: tfs-server
  name: tfs-server
...
spec:
  containers:
  - image: gcr.io/$GCP_PROJECT_ID/tfserving-hf-vit:latest
    name: tfs-k8s
    imagePullPolicy: Always
    args: ["--tensorflow_inter_op_parallelism=2", 
           "--tensorflow_intra_op_parallelism=8"] 
    ports:
    - containerPort: 8500
      name: grpc
    - containerPort: 8501
      name: restapi
    resources:
      limits:
        cpu: 800m
      requests:
        cpu: 800m
...
```

`tfs-server`、`tfs-k8s` 这些名称可以按你的喜好任意配置。在 `containers` 下指定部署要使用的 Docker 镜像 URI。通过设置容器 `resources` 的允许范围来监控当前资源使用情况，它可以让 Horizontal Pod Autoscaler（后文讨论）决定容器的扩缩容。`requests.cpu` 是运维人员设定的容器正常运行所需的最小 CPU 资源量。这里 800m 表示整个 CPU 资源的 80%。因此，HPA 会监控所有 Pod 之间基于 `requests.cpu` 总和的平均 CPU 利用率来做出伸缩决策。

除了 Kubernetes 相关配置，还可以在 `args` 中指定 TensorFlow Serving 的专有选项。这里是两个：

- `tensorflow_inter_op_parallelism`，设置并行执行相互独立操作的线程数，推荐值为 2。
- `tensorflow_intra_op_parallelism`，设置并行执行单个操作内部工作的线程数，推荐值等于部署所用 CPU 的物理核心数。

关于这些选项（及其他选项）及其调优技巧，可在[这里](https://www.tensorflow.org/tfx/serving/performance)和[这里](https://github.com/IntelAI/models/blob/master/docs/general/tensorflow_serving/GeneralBestPractices.md)了解更多。

**`service.yaml`**：

```
apiVersion: v1
kind: Service
metadata:
  labels:
    app: tfs-server
  name: tfs-server
spec:
  ports:
  - port: 8500
    protocol: TCP
    targetPort: 8500
    name: tf-serving-grpc
  - port: 8501
    protocol: TCP
    targetPort: 8501
    name: tf-serving-restapi
  selector:
    app: tfs-server
  type: LoadBalancer
```

我们把服务类型设为 'LoadBalancer'，这样端点会对外暴露到 Kubernetes 集群之外。它通过指定端口选择 'tfs-server' Deployment 与外部客户端建立连接。我们开放 '8500' 和 '8501' 两个端口，分别用于 gRPC 和 HTTP/REST 连接。

**`hpa.yaml`**：

```
apiVersion: autoscaling/v1
kind: HorizontalPodAutoscaler
metadata:
 name: tfs-server

spec:
 scaleTargetRef:
   apiVersion: apps/v1
   kind: Deployment
   name: tfs-server
 minReplicas: 1
 maxReplicas: 3
 targetCPUUtilizationPercentage: 80
```

HPA 是 **H**orizontal **P**od **A**utoscaler（水平 Pod 自动伸缩器）的缩写，用于设定决定目标 Deployment Pod 数量伸缩的条件。Kubernetes 内部自动伸缩算法的详情见[这里](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale)。

这里你指定 Kubernetes 应如何处理自动伸缩。具体地，定义伸缩所依据的副本上下界——`minReplicas` 和 `maxReplicas`——以及目标 CPU 利用率。`targetCPUUtilizationPercentage` 是自动伸缩的关键指标。下面这段话精确概括了它的含义（取自[这里](https://stackoverflow.com/a/42530520/7636462)）：

> CPU 利用率是某一 deployment 中所有 Pod 过去一分钟的平均 CPU
> 用量除以该 deployment 请求的 CPU。如果各 Pod CPU 利用率的均值
> 高于你设定的目标，你的副本数就会被调整。

回想一下我们在 deployment manifest 中指定的 `resources`。正是因为指定了 `resources`，Kubernetes 控制平面才开始监控相关指标，`targetCPUUtilization` 才能生效。否则 HPA 根本不知道 Deployment 的当前状态。

你可以根据需求试验并设置这些数值。但要注意，自动伸缩还取决于你在 GCP 上的可用配额，因为 GKE 底层使用 [Google Compute Engine](https://cloud.google.com/compute) 来管理这些资源。

### 执行部署

manifest 就绪后，用 [`kubectl apply`](https://kubernetes.io/docs/reference/generated/kubectl/kubectl-commands#apply) 命令把它们应用到当前连接的 Kubernetes 集群。

```
$ kubectl apply -f deployment.yaml
$ kubectl apply -f service.yaml
$ kubectl apply -f hpa.yaml
```

用 `kubectl` 逐个应用 manifest 完成部署没问题，但如果你有很多不同的 manifest，事情会很快变复杂。这时 [Kustomize](https://kustomize.io/) 这类工具就派上用场了。只需再定义一个名为 `kustomization.yaml` 的配置文件，如下：

```
commonLabels:
  app: tfs-server
resources:
- deployment.yaml
- hpa.yaml
- service.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
```

然后一行命令就能完成实际部署：

```
$ kustomize build . | kubectl apply -f -
```

完整说明见[这里](https://github.com/sayakpaul/deploy-hf-tf-vision-models/tree/main/hf_vision_model_tfserving_gke)。部署完成后，我们可以这样获取端点 IP：

```
$ kubectl rollout status deployment/tfs-server
$ kubectl get svc tfs-server --watch

---------OUTPUT---------
NAME        TYPE          CLUSTER-IP   EXTERNAL-IP  PORT(S)                        AGE
tfs-server  LoadBalancer  xxxxxxxxxx   xxxxxxxxxx   8500:30869/TCP,8501:31469/TCP  xxx
```

记下可用的外部 IP。

至此，在 Kubernetes 上部署模型所需的全部步骤就讲完了！Kubernetes 优雅地为自动伸缩、集群管理等复杂环节提供了抽象，让你专注于部署模型时真正该关心的关键方面，例如资源利用率、安全（本文未涉及）、以及延迟等性能指标。

## 测试端点

bytes_inputs = tf.io.read_file(image_path)
b64str = base64.urlsafe_b64encode(bytes_inputs.numpy()).decode("utf-8")
data = json.dumps(
    {"signature_name": "serving_default", "instances": [b64str]}

json_response = requests.post(
    "http://<ENDPOINT-IP>:8501/v1/models/hf-vit:predict",

## 关于不同 TF Serving 配置的说明

TensorFlow Serving [提供](https://www.tensorflow.org/tfx/serving/serving_config)了多种选项，可根据你的应用场景定制部署。下面简要介绍其中几个。

**`enable_batching`** 启用批处理推理能力：在一定时间窗口内收集进来的请求，将它们汇聚成一个批次，执行一次批量推理，再把每个请求的结果返回给对应客户端。TensorFlow Serving 提供了丰富的可配置项（如 `max_batch_size`、`num_batch_threads`）来定制你的部署需求。详情见[这里](https://github.com/tensorflow/serving/blob/master/tensorflow_serving/batching/README.md)。批处理特别适合不需要即时获得模型预测的应用。这类场景下，你通常会把多个待预测样本攒成批次再统一送进模型。幸运的是，启用批处理能力后，TensorFlow Serving 可以自动配置这一切。

**`enable_model_warmup`** 用虚拟输入数据预热一些延迟实例化的 TensorFlow 组件。这样你可以确认一切已正确加载完毕，真正对外服务时不会有卡顿。
