# Swarms、Flocks、Gangs：如何构建、训练与评估多智能体系统







*第一部分：理解 swarm，并训练它们相互通信*

这是一个写给有抱负读者的、同样有抱负的博客系列。我们（我们、社区、你）想构建自己的 agent swarm，因为它们令人兴奋、富有挑战，而且能力越来越强。更进一步，如果我们能训练自己的 agent 在 swarm 中协作，那会极其酷。如果这些 swarm 用的还是小型、可负担的模型，那酷的程度还会指数级上升。

这就是本系列要做的事！每篇博客都会包含一些构建 swarm 的背景，以及可以在 Hugging Face Jobs 上运行的可复现示例。本文的示例在两块 H200 上大约需要五个小时，成本约为 $50。

多智能体系统很难真正跑通。增加 agent 会改变 agent 的上下文、预算，进而改变整个系统的复杂度。通过通信把各 agent 的上下文混在一起，相对于单个 agent 并不是一种内生的性能提升。模型需要通过训练学会通信。我们如何定义模型应该学什么？而当我们要处理许多 agent 时，又该更新哪些模型权重？

在本系列中，我们将通过教学式的概览和实际示例来逐个处理这些问题。每篇文章都会提出一个问题、搭建一个小系统，并考察发生了什么以及你如何复现它。第一个示例从四个 agent、一个共享语言模型和一个简单的可验证任务开始。它非常适合你自己实现、动手折腾并从中学习。

首先，我们先从一些关于 swarm 的背景讲起。

## swarm 的兴起

过去几个月里，我们听到很多关于 swarm 的消息，有好有坏。今年 9 月，[OpenAI 宣布](https://openai.com/index/navier-stokes-solution/)一个由约 10,000 个 agent 组成的 swarm 在三维 Navier-Stokes 方程中找到了一个奇点，而这是千禧年大奖难题之一。一个规模更小、约 100 个 agent 的团队此前已经否证了无外力三维 Euler 方程的正则性，这是一个与之密切相关的开放问题。

但 swarm 并不总是去做我们希望它们做的问题。[METR 对 Hugging Face 事件的调查](https://metr.org/blog/2026-08-26-openai-hugging-face-incident-investigation/)发现，约 1,200 个本应相互隔离的 OpenAI agent 找到了交换超过 70,000 条消息和文件的办法。其中约 700 个在寻找办法欺骗其 benchmark 评分器的过程中，参与了对 Hugging Face 的攻击——并没有任何人指示它们这样做。

一个庞大的 swarm 本身并不能证明协作帮上了忙。[Noam Brown 估计](https://www.dwarkesh.com/p/noam-brown)，Navier-Stokes 那项成果中来自多智能体协作的部分不到 10%。在 [Anthropic 的漏洞发现实验](https://www.anthropic.com/research/multiagent-systems)中，协同的 agent 比独立的 agent 找到了更多 bug，但也搜索了更多代码、消耗了更多 token。当比较被限制在相同的目录上时，每百万 token 的产出大致相当。

## 协作帮上了忙，还是我们只是花了更多？

从最简单的情形说起。如果四个 agent 各自独立尝试一个任务，那么至少有一个做对的概率会高于单次尝试——前提是我们能判断哪个答案是正确的。这为多智能体系统提供了一个有用的基线，但它并不能说明各 agent 之间互相帮助了。它们可能只是多试了几次。

四次尝试的成本也是四倍。因此更公平的比较是在同等预算下进行：如果四个 agent 各分到总 token 的四分之一，它们还能胜过把这全部 token 都花掉的单个 agent 吗？我们只能通过实测才知道答案，因为这取决于任务、模型以及工作如何划分。

> 本系列会一直追问同一个问题：当 agent 之间通信时，它真的有用吗，还是我们只是花了更多算力？

我们通过下面这个简单的预期来理解那个问题。

图 1。我们想要检验的预期示意：在匹配的预算下比较相互通信的 agent 与独立的 agent。

我们会把 agent 数量当作一个 scaling 维度，与 token 数和模型规模并列。有时增加 agent 会有帮助，有时协调会消耗掉我们本想省下的预算。关键是把两者都测出来。我们不会从 10,000 个 agent 起步，而是从一个小编队、一个我们能轻松校验的任务开始。

## 多智能体系统与强化学习

早在语言模型被称作 swarm 之前，多智能体强化学习就已经在研究合作与竞争了。

单个 agent 的任务是一个马尔可夫决策过程：观测、行动、获得奖励。在团队中，所有人共享奖励，但每个 agent 只看到世界的一部分。这就是一个去中心化的部分可观测马尔可夫决策过程：是队友，但没人看得到全貌。

这带来三个实际问题。第一，在每个 agent 学习的过程中，队友一直在变。第二，信用分配：当团队成功时，哪些动作应得这份功劳？一支获胜的团队里可能包含糟糕的动作，而我们最终可能会奖励它们。第三，一条消息会改变其他 agent 观测到的东西，因此通信是我们正在训练的策略的一部分。

一种常见的解决方案是集中式训练、分散式执行：训练时使用整个团队的信息，但每个 agent 只依据自己的观测行动。我们的第一个示例就采用这一模式，并配以共享的团队奖励。

agent 也可以有不同的组织方式。两个有用的起点是：

- **层级结构。** 一个 lead agent 把工作分配给 worker，并收集它们的结果。Anthropic 的 Research 系统就是这样运作的，每个 worker 拥有独立的上下文。Kimi K2.5 的 PARL 只训练 orchestrator，让 subagent 保持冻结，因此训练一个多智能体系统并不意味着要更新每一个组件。参见 [Anthropic 的系统说明](https://www.anthropic.com/research/multi-agent-research-system) 和 [Kimi 的技术博客](https://www.kimi.com/en/blog/kimi-k2-5)。
- **分布式团队。** 对等节点互相发送消息，并自行决定何时读取收件箱。没有 lead agent 来分配动作。这就是我们在这里要用的设置，沿用 [s³: Simple Scaling of Swarms via Cooperative Multi-agent RL](https://huggingface.co/papers/2611.08615) 中的信息聚合任务。

## 我们的第一个实验：四个 agent 给数字排序

我们将复现 [Simple Scaling of Swarms](https://huggingface.co/papers/2611.08615) 中的信息共享任务，因为它可解释、实现起来也直接。四个 agent 共享一个小语言模型，并学习把各自掌握的信息汇聚起来。

每个 agent 收到一个 1 到 99 之间的整数。它知道自己的分配值和队友的名字，但一开始并不知道其他 agent 的数字。例如，四个私有的分配值可能是 “five”、“twenty-six”、“five” 和 “seventy-eight”。重复值会留在列表里，因此正确的最终答案是：

```
#### [5, 5, 26, 78]
```

当**至少有一个 agent 提交了完整且排序正确的列表**时，团队即成功。一个正确答案就足够了；成功并不要求四个 agent 都答对。在没有队友信息的情况下，一个 agent 无法可靠地推断出其他私有的分配值。

这意味着该任务还没有直接检验图 1。每个 agent 都持有其他人需要的信息，因此单个 agent、或者一个不通信的团队，无论重试多少次都无法成功。相反，这个任务检验的是图 1 背后的前提：一个小的共享策略究竟能否学会通信，以及这要花多少 token？后续文章会转向一个单个 agent 就能独立解决的任务，在那里，同等预算的比较才有意义。

主要的通信工具是 `message(to, text)`、`read_messages()` 和 `check_notifications()`。通知告诉 agent 存在未读消息；读取收件箱后，其内容才可获取。agent 可以发送直接消息，也可以向所有人广播。

我们使用**一个共享的 Qwen3-0.6B 策略**定义了一个四 agent 系统，各 agent 拥有独立的上下文和私有的输入。我们并不是在训练四个不同的模型。prompt 说明了任务和工具，包括分享各自分配值的必要性。

图 2。任务与训练循环。这些私有数字展示的是一个可能成功的 episode；此图不是一段真实记录的对话，也不是关于第 75 次更新时所学协议的主张。

### 团队奖励与每个问题的八次尝试

在本文中，*team* 指一个 episode：四个 agent 对一个问题尝试一次。成功的 team 会获得一份奖励，并按它消耗的 token 数扣减。失败的 team 得到零：

```
team allowance = 4 × (8,192 work tokens + 1,024 final-answer tokens)
               = 36,864 tokens

reward = success × (1 − 0.25 × min(1, generated team tokens / 36,864))
```

举例说明，一个正确的 team 若用掉一半额度，得到 0.875。发送消息没有单独的奖励。激励在于：在解决任务的同时使用更少的生成 token。

对每一个训练问题，我们收集八次独立的 team 尝试。它们的奖励在该组内做归一化。表现优于组内平均的尝试得到正优势值；表现更差的得到负优势值。同一个 team 中的每个 agent 都会收到该 team 的优势值，包括自己最终答案错误的 agent。

在 [TRL](https://github.com/huggingface/trl) 中，每个 agent 采样出的 token 构成一个训练行。它收到的消息和工具结果提供上下文。loss 先在每个 team 内平均，再在各 team 之间平均，因此更长的对话不会让某个 team 获得更大的权重。

> 我们的结果来自原始实验，该实验每次更新使用 256 次 team 尝试（32 个问题 × 每个问题八次尝试）。下面的操作演练使用 TRL 的默认值 --teams-per-update 128，折算下来每次更新约 150 次 team 尝试。

### 我们的结果

在 75 步之内，训练成功率从 **6.6% 升到 82.3%**（比较最初五次与最后五次更新）。在 checkpoint 75，四 agent 团队解决了 **32 个 held-out 问题中的 26 个（81.25%）**。[论文](https://huggingface.co/papers/2611.08615)报告在 200 次更新后四 agent 成功率为 93.2%。

团队每次尝试使用的 token 也**减少了 37.4%**，从约 13k 降到 8k。这一改善伴随着更活跃的信息共享：尽管总 token 用量下降，每个 team 的广播次数从 2.38 增加到 5.73。

图 3。蓝色曲线描述的是每次更新前收集的、包含 256 次 team 尝试的训练 batch。橙色点是所示更新之后的 held-out 检查结果。

在训练后期，团队使用的 token 也更少。对比最初五次更新与第 71–75 次更新：

| **训练指标** | **第 1–5 次更新，均值** | **第 71–75 次更新，均值** |
| --- | --- | --- |
| 成功率 | 6.56% | 82.34% |
| 每个 team 的生成 token 数 | 12,826.9 | 8,026.0 |
| 每个 team 的消息数 | 3.48 | 6.28 |
| 每个 team 的广播数 | 2.38 | 5.73 |
| 每个 agent 发一次广播的 team 占比 | 4.06% | 18.20% |

也就是说，在这两个窗口之间，**每个训练 team 的生成 token 数减少了 37.4%**。在第 75 个 batch 本身，每个 team 的均值为 7,624 个 token。这些是训练侧的测量；我们没有为训练后的 checkpoint 保留 held-out 的 token 效率测量。

注意，token 更少并不意味着消息更少。更多 agent 开始参与，但变得更常见的是广播，而不是直接消息。生成 token 既包括消息正文，也包括推理和工具调用，所以单看消息数量无法告诉我们这个 team 到底产出了多少文本。

图 4。上：训练 token 用量及其五次更新的滑动均值。下：基于已发送消息事件的互斥通信类别。team 的分类顺序是：先看是否有某个 agent 从不发送，再看是否出现任何直接消息，然后看是否每个 agent 都恰好发送一次广播；剩下的 team 属于重复广播。

### 更多重试，还是一个训练过的团队？

没有哪个 agent 能单独解决这个问题，所以与“单个 agent 加上更多重试”最接近的等价物，就是未训练的 team 加上更多重试。训练数据里已经包含了这个比较。每次更新都会为每个问题收集八次尝试，而该任务的答案很容易校验，因此只要八次尝试中有任意一次成功，我们就可以把这个题算作已解决。在训练早期，这个计数给出了未训练 team 的 best-of-8 成功率：

|  | **成功率** | **每个问题的生成 token 数** |
| --- | --- | --- |
| 未训练的 team，8 次尝试取最佳（第 1–5 次更新） | 37.5% | 约 103,000 |
| 训练后的 team，单次尝试（第 71–75 次更新） | 82.3% | 约 8,000 |

有八次重试时，未训练的 team 解决不到一半的问题，却花掉约相当于训练后 team 单次尝试 13 倍的 token。请把这当作一个估计值来读。两行用的都是训练问题而不是 held-out 问题，而且第 2–5 次更新时采样的已经是一个经过些许训练的 policy 了。

### 基础设施

模型很小，但 rollout 并不小。每次更新都会在最高 40k token 的上下文下生成数百万 token 的 agent 对话。我们用一个 H200 做训练器，用七个 H200 运行 vLLM rollout 引擎以快速跑完这些 rollout，并把每个 worker 的八次尝试保持在一起。下面的操作演练在两块 GPU 上运行同一个任务。以下是基础设施细节：

| **设置** | **记录的实验** |
| --- | --- |
| 共享 policy | Qwen3-0.6B |
| 每个 team 的逻辑 agent 数 | 4 |
| 每次更新的问题数 | 32 |
| 每个问题的 team 尝试数 | 8 |
| 每个 agent 的工作 / 最终答案 token | 8,192 / 1,024 |
| 学习率 / temperature | 5e-7 / 1.0 |
| 训练问题池 | 1,024 个生成的问题 |
| 汇报端点 | 保留的 checkpoint 75 |
| 执行 | 1 块训练 GPU + 7 块 rollout GPU |

## 实践示例：训练你自己的 swarm

上面的图表描述的是我们原始的 75 次更新实验。在这次操作演练中，我们将在 Hugging Face Jobs 上运行 [TRL 的 swarm 示例](https://github.com/huggingface/trl/tree/main/examples/async_grpo_s3_aggregation)。一块 H200 用 vLLM 提供共享的 Qwen3-0.6B 策略，第二块 H200 负责训练它。

### 1. 为这次运行创建一个 bucket

用一个能够运行 Jobs 并创建 bucket 的 Hugging Face 账号登录。把 `YOUR_USERNAME` 替换为你的 Hub 用户名。

> 每次运行都使用一个新的 bucket，这样此前的测量结果仍然可用。

```
uv tool install 'huggingface_hub==2.4.0'
hf auth login
BUCKET="YOUR_USERNAME/swarm-trl-$(date -u +%Y%m%d-%H%M%S)"
hf buckets create "$BUCKET"
```

### 2. 在 Hugging Face Jobs 上运行 TRL 示例

把下面的脚本保存为你当前目录中的 `train-swarm.sh`。

`train-swarm.sh`

```
set -eu
git clone --depth 1 https://github.com/huggingface/trl /tmp/trl
cd /tmp/trl
example=examples/async_grpo_s3_aggregation
if [ ! -f "$example/async_grpo_s3_aggregation.py" ]; then
  git fetch --depth 1 origin refs/pull/8424/head
  git checkout --detach FETCH_HEAD
fi
git rev-parse HEAD > /results/trl-revision.txt
python -m pip install -e ".[vllm,kernels]" "vllm==0.32.0" datasets httpx trackio

base=Qwen/Qwen3-0.6B
url=http://127.0.0.1:8000
export TRACKIO_DIR=/tmp/trackio
serve() {
  CUDA_VISIBLE_DEVICES=0 VLLM_SERVER_DEV_MODE=1 vllm serve "$@" \
    --host 127.0.0.1 --max-model-len 40960 --max-num-seqs 512 --enable-prefix-caching &
  server=$!
  until curl -fs "$url/health" >/dev/null; do kill -0 "$server"; sleep 5; done
}
evaluate() {
  python "$example/evaluate.py" --url "$url" --model "$1" --name "$2" \
    --episodes 192 --concurrency 64 --out "/results/$2.jsonl"
}

serve "$base" --logprobs-mode processed_logprobs --weight-transfer-config "{\"backend\":\"nccl\"}"
evaluate "$base" base
CUDA_VISIBLE_DEVICES=1 accelerate launch --num_processes 1 --mixed_precision bf16 \
  "$example/async_grpo_s3_aggregation.py" --vllm-url "$url" \
  --updates 50 --teams-per-update 128 --concurrent-teams 128 \
  --report-to trackio --output-dir /tmp/swarm
cp -r "$TRACKIO_DIR" /tmp/swarm/checkpoint-50 /results/
kill "$server"
wait "$server" || true
serve /tmp/swarm/checkpoint-50 --logprobs-mode processed_logprobs
evaluate /tmp/swarm/checkpoint-50 trained
```

下面的命令会把它的内容发送到 job。在 job 内部，vLLM 在 GPU 0 上提供共享策略。GPU 1 借助 Trackio 运行 TRL 的 `async_grpo_s3_aggregation.py`，共 50 次更新。TRL 的 `evaluate.py` 在同样的 192 个 held-out 问题上给基座模型和 checkpoint 50 打分。这比我们结果中 32 个问题的检查规模更大，误差棒也更紧。这个 job 会把两个分数、checkpoint、Trackio 数据以及确切的 Git commit 保存到你的 bucket。

```
hf jobs run --detach --flavor h200x2 --timeout 12h \
  --volume "hf://buckets/$BUCKET:/results" \
  -- vllm/vllm-openai:v0.32.0 bash -c "$(cat train-swarm.sh)"
```

一次 TRL rollout 包含一整个 team 对话。训练器会比较对同一个问题的八次尝试，并把同一个优势值给一次尝试中的全部四个 agent。每次更新大约使用 150 次 team 尝试。TRL 按 token 数而不是按 team 来打包 micro-batch，所以 `--teams-per-update 128` 这个设置是近似的。`--report-to trackio` 标志会在每次更新时记录训练指标。

这次更短的运行比我们原始实验便宜，也在学习曲线上更早停下。TRL 运行这个示例在两块 H100 上花了大约 4.8 小时，在 checkpoint 50 达到 60.9% 的 held-out 成功率。

> 要更接近我们的原始实验，请把训练参数改为 --updates 75 --teams-per-update 256 --concurrent-teams 256，把脚本中的 checkpoint-50 换成 checkpoint-75，并把 job 的 --timeout 提高到 24h。那是三倍的 rollout 量。两套代码在 system prompt 等细节上仍然不同，所以请期待相近的结果，而不是精确复现。

### 3. 读取结果

job 完成后，把 bucket 同步到本地文件夹。里面有那两个评估文件、Trackio 数据、TRL 版本，以及 checkpoint-50 的权重——后者是最大的一笔下载。在 dashboard 中，对比训练过程中的 `team/success`、`team/messages` 和 `team/tokens`。job 日志也会给出基座模型和 checkpoint 50 的 held-out 成功率。`base.jsonl` 或 `trained.jsonl` 的每一行记录其中一次评估尝试。

```
hf buckets sync "hf://buckets/$BUCKET" ./swarm-results
TRACKIO_DIR="$PWD/swarm-results/trackio" uvx trackio show
```

## 我们接下来会尝试什么

这第一个示例给了我们一个小环境、一个共享奖励，以及一个在汇聚私有信息上不断改进的策略。它也说明了为什么成功率、token 用量和通信结构需要放在一起读。在 75 次更新时，团队已经能解决大多数被检查的问题，但它还没有收敛到最干净的通信模式。

在接下来的示例中，我们会从训练退后一步，看看我们如何评估和分析 swarm。

目前，我们已有一些具体的东西可作基础：四个小 agent、一个可训练的策略、一个可校验的任务，以及一种可复现的方式来考察这个团队学到了什么。
