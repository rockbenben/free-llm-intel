*第一部分：理解 swarm 并训练其通信*

这是一个面向有抱负读者的、同样有抱负的博客系列。我们（我们、社区、你）想构建自己的 agent swarm，因为它们令人兴奋、富有挑战性，而且能力越来越强。更进一步，如果我们能训练自己的 agent 在 swarm 中协作，那会极其酷。如果这些 swarm 使用的还是小而经济的模型，那酷的程度还会指数级上升。

这就是我们在本系列中要做的事！每篇博客都会包含一些关于构建 swarm 的背景，以及可在 Hugging Face Jobs 上运行的可复现示例。本文的示例在两块 H200 上大约需要五小时，成本约为 $50。

多智能体系统很难真正跑通。增加 agent 会改变 agent 的上下文、预算，进而改变整个系统的复杂度。通过通信把各 agent 的上下文混合在一起，相比单个 agent 并不是内在的性能提升。模型需要通过训练学会通信。我们如何定义模型应该学什么？当我们面对许多 agent 时，又该更新哪些模型权重？

在本系列中，我们将通过教学性概览和实践示例来逐个处理这些问题。每篇文章都会提出一个问题、构建一个小系统，并考察会发生什么以及你如何复现它。第一个示例从四个 agent、一个共享语言模型和一个简单的可验证任务开始。它非常适合你自己实现、动手折腾并从中学习。

首先，我们会从一些关于 swarm 的背景开始。

## swarm 的崛起

过去几个月里，我们听到了很多关于 swarm 的消息，有好有坏。今年九月，[OpenAI 宣布](https://openai.com/index/navier-stokes-solution/)，一个约 10,000 个 agent 组成的 swarm 在三维 Navier-Stokes 方程中找到了一个奇点，这是千禧年大奖难题之一。一个由近 100 个 agent 组成的更小团队已经否证了无外力三维 Euler 方程的正则性，这是一个密切相关的开放问题。

但 swarm 并不总是会去解决我们希望它们解决的问题。[METR 对 Hugging Face 事件的调查](https://metr.org/blog/2026-08-26-openai-hugging-face-incident-investigation/)发现，约 1,200 个本应被隔离的 OpenAI agent 找到了交换超过 70,000 条消息和文件的方法。大约 700 个 agent 在寻找办法欺骗其 benchmark 评分器的过程中，参与了对 Hugging Face 的攻击，而它们并没有被指示这样做。

一个大型 swarm 本身并不能证明合作起了作用。[Noam Brown 估计](https://www.dwarkesh.com/p/noam-brown)，Navier-Stokes 成果中来自多智能体合作的部分不到 10%。在 [Anthropic 的漏洞发现实验](https://www.anthropic.com/research/multiagent-systems)中，协调后的 agent 比独立 agent 发现了更多 bug，但也搜索了更多代码、使用了更多 token。当比较被限制在相同目录时，每百万 token 的结果大致相同。

## 合作有帮助，还是我们只是花了更多？

从最简单的情况开始。如果四个 agent 各自独立尝试一个任务，那么只要我们能判断哪个答案正确，至少有一个 agent 答对的概率就高于单次尝试。这为多智能体系统提供了一个有用的基线，但它并不能表明 agent 之间互相帮助了。它们可能只是有了更多次尝试。

四次尝试的成本也是四倍。因此，更公平的比较是在相同预算下进行：如果四个 agent 各获得总 token 的四分之一，它们还能击败一个花掉全部 token 的 agent 吗？我们只能通过测试来找出答案，因为这取决于任务、模型以及工作如何划分。

> 本系列一直在问一个问题：当 agent 通信时，这真的有帮助吗，还是我们只是花了更多算力？

我们通过下面这个简单的预期来理解这个问题。

图 1. 我们想要检验的预期示意图：在匹配预算下比较相互通信的 agent 与独立 agent。

我们会把 agent 数量视为一个扩展维度，与 token 数和模型规模并列。有时增加 agent 会有帮助。有时协调会消耗掉我们原本希望节省的预算。关键在于把两者都测量出来。我们不会从 10,000 个 agent 开始。我们会从一个小团队和一个容易检查的任务开始。

## 多智能体系统与强化学习

早在语言模型被称为 swarm 之前，多智能体强化学习就已经在研究合作与竞争。

单个 agent 的任务是一个马尔可夫决策过程：观察、行动、获得奖励。在一个团队中，所有人共享奖励，但每个 agent 只能看到世界的一部分。这是一个去中心化部分可观测马尔可夫决策过程：彼此是队友，但没有人能看到全貌。

这带来了三个实际问题。第一，在每个 agent 学习的同时，队友一直在变化。第二，信用分配：当团队成功时，哪些行动应获得功劳？一支获胜的队伍可能包含较弱的行动，而我们最终可能会奖励它们。第三，一条消息会改变其他 agent 的观察，因此通信是我们正在训练的策略的一部分。

一种常见的解决方案是集中式训练、分散式执行：训练使用整个团队的信息，但每个 agent 仅根据自己的观察行动。我们的第一个示例采用这种模式，并使用共享的团队奖励。

agent 也可以通过不同方式组织。两个有用的起点是：

- **层级结构。** 一个 lead agent 把工作分配给 worker 并收集它们的结果。Anthropic 的 Research 系统就是这样工作的，每个 worker 有独立的上下文。Kimi K2.5 的 PARL 只训练 orchestrator，并保持 subagent 冻结，因此训练多智能体系统并不意味着要更新每个组件。参见 [Anthropic 的系统描述](https://www.anthropic.com/research/multi-agent-research-system)和 [Kimi 的技术博客](https://www.kimi.com/en/blog/kimi-k2-5)。
- **分布式团队。** 同伴之间互相发送消息，并决定何时读取自己的收件箱。没有 lead agent 分配动作。这就是我们在这里将采用的设置，它沿用了 [s³: Simple Scaling of Swarms via Cooperative Multi-agent RL](https://huggingface.co/papers/2611.08615)中的信息聚合任务。

## 我们的第一个实验：四个 agent 对数字排序

我们将复现 [Simple Scaling of Swarms](https://huggingface.co/papers/2611.08615)中的信息共享任务，因为它可解释且易于实现。四个 agent 共享一个小型语言模型，并学习汇集它们各自知道的信息。

每个 agent 会收到一个 1 到 99 的整数。它知道自己的分配值以及队友的名字。它最初不知道其他 agent 的数字。例如，四个私有分配值可能是“五”、“二十六”、“五”和“七十八”。重复值会保留在列表中，因此正确的最终答案是：

```
#### [5, 5, 26, 78]
```

当**至少一个 agent 提交完整且排序正确的列表**时，团队即成功。一个正确答案就足够了；成功不要求四个 agent 全部答对。在没有队友信息的情况下，一个 agent 无法可靠地推断出其他私有分配值。

这意味着该任务还没有直接检验图 1。每个 agent 都掌握着其他人需要的信息，因此单个 agent，或者一个不发送消息的团队，无论重试多少次都无法成功。相反，该任务检验的是图 1 背后的前提：一个小型共享策略究竟能否学会通信，以及这需要花费多少 token？后续文章会转向一个单个 agent 可以独立解决的任务，在那里，匹配预算的比较才有意义。

主要的通信工具是 `message(to, text)`、`read_messages()` 和 `check_notifications()`。通知会告诉 agent 存在未读消息；读取收件箱后，消息内容就可供使用。agent 可以发送私信，也可以向所有人广播。

我们定义了一个四 agent 系统，使用**一个共享的 Qwen3-0.6B 策略**，每个 agent 有独立的上下文和私有输入。我们并不是在训练四个不同的模型。prompt 说明了任务和工具，包括共享分配值的必要性。

图 2. 任务与训练循环。私有数字展示了一个可能的成功 episode；此图不是一段录制的对话，也不是对第 75 次更新时所学协议的主张。

### 团队奖励与每个问题八次尝试

在本文中，*team* 指一个 episode：四个 agent 对一个问题尝试一次。成功的团队会获得奖励，但奖励会因其使用的 token 而减少。失败的团队获得零奖励：

```
team allowance = 4 × (8,192 work tokens + 1,024 final-answer tokens)
               = 36,864 tokens

reward = success × (1 − 0.25 × min(1, generated team tokens / 36,864))
```

举例来说，一个正确使用其额度一半的团队会得到 0.875。发送消息没有单独奖励。激励是在使用更少生成 token 的同时解决任务。

对于每个训练问题，我们收集八个独立的团队尝试。它们的奖励在该组内归一化。表现优于组平均的尝试获得正 advantage；表现较差的尝试获得负 advantage。同一团队中的每个 agent 都会获得该团队的 advantage，包括自身最终答案错误的 agent。

在 [TRL](https://github.com/huggingface/trl) 中，每个 agent 采样的 token 构成一行训练数据。它接收到的消息和工具结果提供上下文。loss 先在每个团队内平均，然后在团队之间平均，因此较长的对话不会让某个团队获得更高权重。

> 我们的结果来自原始实验，该实验每次更新使用 256 次团队尝试（32 个问题，每个问题八次尝试）。操作演练使用 TRL 默认的 --teams-per-update 128，折算下来每次更新大约有 150 次团队尝试。

### 我们的结果

在 75 个 step 中，对比最初五次和最后五次更新，训练成功率从 **6.6% 上升到 82.3%**。在 checkpoint 75，四 agent 团队解决了 **32 个 held-out 问题中的 26 个（81.25%）**。[论文](https://huggingface.co/papers/2611.08615)报告称，经过 200 次更新后，四 agent 成功率为 93.2%。

该团队每次尝试使用的 token 也**减少了 37.4%**，从约 13k 降至 8k。这一改进伴随着更活跃的信息共享：每个团队的广播次数从 2.38 增加到 5.73，尽管总 token 使用量下降了。

图 3. 蓝色曲线描述每次更新前收集的、包含 256 次团队尝试的训练批次。橙色点是指示更新之后的 held-out 检查结果。

团队在训练后期也使用了更少的 token。对比最初五次更新与第 71–75 次更新：

| **训练指标** | **第 1–5 次更新，均值** | **第 71–75 次更新，均值** |
| --- | --- | --- |
| 成功率 | 6.56% | 82.34% |
| 每个团队生成的 token | 12,826.9 | 8,026.0 |
| 每个团队的消息数 | 3.48 | 6.28 |
| 每个团队的广播数 | 2.38 | 5.73 |
| 每个 agent 发送一次广播的团队占比 | 4.06% | 18.20% |

这意味着在这两个窗口之间，**每个训练团队生成的 token 减少了 37.4%**。在 batch 75 本身，每个团队的均值是 7,624 个 token。这些是训练测量值；我们没有保留训练后 checkpoint 的 held-out token 效率测量值。

注意，更少的 token 并不意味着更少的消息。更多 agent 开始参与，但广播变得比直接发消息更常见。生成的 token 既包括消息正文，也包括推理和工具调用，因此仅凭消息数量并不能告诉我们团队生成了多少文本。

图 4. 上：训练 token 使用量及过去五次更新的滑动均值。下：基于已发送消息事件的互斥通信类别。团队的分类顺序是：首先看是否有某个 agent 从不发送消息，然后看是否出现任何直接消息，再看是否每个 agent 恰好发送一次广播；剩余团队则重复广播。

### 更多重试，还是训练过的团队？

没有 agent 能独自解决该问题，因此与“带更多重试的单个 agent”最接近的对应物，是带更多重试的未训练团队。训练数据已经包含这一比较。每次更新会为每个问题收集八次尝试，而任务的答案很容易检查，因此只要八次尝试中有任何一次成功，我们就可以把该问题计为已解决。在训练早期，这个计数给出了未训练团队的 best-of-8 成功率：

|  | **成功率** | **每个问题生成的 token** |
| --- | --- | --- |
| 未训练团队，8 次尝试中的最佳（第 1–5 次更新） | 37.5% | 约 103,000 |
| 训练后团队，一次尝试（第 71–75 次更新） | 82.3% | 约 8,000 |

在八次重试下，未训练团队解决的问题不到一半，并且花费的 token 约为训练后团队单次尝试的 13 倍。请将此视为估计值。两行使用的都是训练问题而非 held-out 问题，而且第 2–5 次更新已经是从略微训练过的策略中采样。

### 基础设施

模型很小，但 rollout 规模不小。每次更新都会在最高 40k token 的上下文中生成数百万 token 的 agent 对话。我们使用一块 H200 作为 trainer，七块 H200 运行 vLLM rollout 引擎来快速完成这些 rollout，并把每个 worker 的八次尝试放在一起。下面的演练在两块 GPU 上运行同样的任务。以下是基础设施细节：

| **设置** | **记录的实验** |
| --- | --- |
| 共享策略 | Qwen3-0.6B |
| 每个团队的逻辑 agent 数 | 4 |
| 每次更新的问题数 | 32 |
| 每个问题的团队尝试数 | 8 |
| 每个 agent 的工作 / 最终答案 token 数 | 8,192 / 1,024 |
| 学习率 / temperature | 5e-7 / 1.0 |
| 训练问题池 | 1,024 个生成问题 |
| 报告 endpoint | 保留的 checkpoint 75 |
| 执行 | 1 块 trainer GPU + 7 块 rollout GPU |

## 实践示例：训练你自己的 swarm

上面的图表描述了我们最初的 75 次更新实验。在本演练中，我们将在 Hugging Face Jobs 上运行 [TRL 的 swarm 示例](https://github.com/huggingface/trl/tree/main/examples/async_grpo_s3_aggregation)。一块 H200 用 vLLM 服务共享的 Qwen3-0.6B 策略，第二块 H200 训练它。

### 1. 为本次运行创建一个 bucket

使用能够运行 Jobs 并创建 bucket 的 Hugging Face 账户登录。将 `YOUR_USERNAME` 替换为你的 Hub 用户名。

> 每次运行都使用一个新的 bucket，以便先前的测量结果仍然可用。

```
uv tool install 'huggingface_hub==2.4.0'
hf auth login
BUCKET="YOUR_USERNAME/swarm-trl-$(date -u +%Y%m%d-%H%M%S)"
hf buckets create "$BUCKET"
```

### 2. 在 Hugging Face Jobs 上运行 TRL 示例

将下面的脚本保存为当前目录中的 `train-swarm.sh`。

`train-swarm.sh`

```
set -eu
git clone --depth 1 https://github.com/huggingface/trl /tmp/trl
cd /tmp/trl
example=examples/async_grpo_s3_aggregation
if [ ! -f "$example/async_grpo_s3_aggregation.py" ]; then
  git fetch --depth 1 origin refs/pull/8424/head
  git checkout --detach FETCH_HEAD
fi
git rev-parse HEAD > /results/trl-revision.txt
python -m pip install -e ".[vllm,kernels]" "vllm==0.32.0" datasets httpx trackio

base=Qwen/Qwen3-0.6B
url=http://127.0.0.1:8000
export TRACKIO_DIR=/tmp/trackio
serve() {
  CUDA_VISIBLE_DEVICES=0 VLLM_SERVER_DEV_MODE=1 vllm serve "$@" \
    --host 127.0.0.1 --max-model-len 40960 --max-num-seqs 512 --enable-prefix-caching &
  server=$!
  until curl -fs "$url/health" >/dev/null; do kill -0 "$server"; sleep 5; done
}
evaluate() {
  python "$example/evaluate.py" --url "$url" --model "$1" --name "$2" \
    --episodes 192 --concurrency 64 --out "/results/$2.jsonl"
}

serve "$base" --logprobs-mode processed_logprobs --weight-transfer-config "{\"backend\":\"nccl\"}"
evaluate "$base" base
CUDA_VISIBLE_DEVICES=1 accelerate launch --num_processes 1 --mixed_precision bf16 \
  "$example/async_grpo_s3_aggregation.py" --vllm-url "$url" \
  --updates 50 --teams-per-update 128 --concurrent-teams 128 \
  --report-to trackio --output-dir /tmp/swarm
cp -r "$TRACKIO_DIR" /tmp/swarm/checkpoint-50 /results/
kill "$server"
wait "$server" || true
serve /tmp/swarm/checkpoint-50 --logprobs-mode processed_logprobs
evaluate /tmp/swarm/checkpoint-50 trained
```

下面的命令会将其内容发送到 job。在 job 内部，vLLM 在 GPU 0 上服务共享策略。GPU 1 使用 Trackio 运行 TRL 的 `async_grpo_s3_aggregation.py`，进行 50 次更新。TRL 的 `evaluate.py` 会在相同的 192 个 held-out 问题上为基座模型和 checkpoint 50 打分。这比我们结果中的 32 问题检查集更大，因此误差棒更紧。该 job 会把两个分数、checkpoint、Trackio 数据以及确切的 Git commit 保存到你的 bucket。

```
hf jobs run --detach --flavor h200x2 --timeout 12h \
  --volume "hf://buckets/$BUCKET:/results" \
  -- vllm/vllm-openai:v0.32.0 bash -c "$(cat train-swarm.sh)"
```

一次 TRL rollout 包含一整段团队对话。trainer 会比较针对同一问题的八次尝试，并给一次尝试中的全部四个 agent 相同的 advantage。每次更新使用约 150 次团队尝试。TRL 按 token 数而非按团队打包 micro-batch，因此 `--teams-per-update 128` 设置是近似值。`--report-to trackio` 标志会在每次更新时记录训练指标。

这次较短的运行比我们的原始实验更便宜，并且在学习曲线上更早停止。TRL 运行此示例时，在两块 H100 上耗时约 4.8 小时，并在 checkpoint 50 达到 60.9% 的 held-out 成功率。

> 若要更接近我们的原始实验，请将训练标志改为 --updates 75 --teams-per-update 256 --concurrent-teams 256，将脚本中的 checkpoint-50 替换为 checkpoint-75，并将 job 的 --timeout 提高到 24h。这样 rollout 数量会变成三倍。两个代码库在 system prompt 等细节上仍然不同，因此预期会得到相似结果，而不是精确复现。

### 3. 读取结果

job 完成后，将 bucket 同步到本地文件夹。其中包含两个评估文件、Trackio 数据、TRL revision 以及 checkpoint-50 权重，后者是最大的下载项。在 dashboard 中，对比训练过程中的 `team/success`、`team/messages` 和 `team/tokens`。job 日志还会给出基座模型和 checkpoint 50 的 held-out 成功率。`base.jsonl` 或 `trained.jsonl` 的每一行记录其中一次评估尝试。

```
hf buckets sync "hf://buckets/$BUCKET" ./swarm-results
TRACKIO_DIR="$PWD/swarm-results/trackio" uvx trackio show
```

## 我们接下来会尝试什么
