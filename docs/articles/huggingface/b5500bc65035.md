# 用 TRL 和 OpenEnv 训练编码模型画水彩

8 月 23 日，[Surya Narreddi](https://x.com/kickingkeys/status/2091570990048276897) 发布了一段漂亮的视频：一个语言模型画出的水彩画。模型通过 [p5.brush](https://github.com/acamposuribe/p5.brush)——一个「为 p5.js 添加自然绘画工具」的库——写 JavaScript。视频很快火了，写作本文时已经超过 150 万播放。

视频配了[一篇博客](https://surya.website/rling-qwen-to-paint-with-code)，讲解项目更早、更窄阶段（特写花朵，而非视频里的完整构图）背后的训练，遗憾的是当时还没有开放工件。他的网站说完整技术报告在路上，记得关注他。原始想法来自他，出自艺术与设计一侧——[那方面的技能远在我之上](https://x.com/kickingkeys/status/2094901433149612118)。我的尝试在工程一侧：用完全开放、每一件工件都发布的方式复现那份配方。

> 注：想了解项目背景（Surya 本人讲述），可以看他毕业论文的这段视频。

本文尝试用 [TRL](https://huggingface.co/docs/trl) 和 [OpenEnv](https://github.com/huggingface/OpenEnv) 复现他的想法。参考池数据集、RL 环境、训练脚本和训练出的模型，全部开放。

整条流水线端到端跑在 Hugging Face 上：

- 训练在 [Jobs](https://huggingface.co/docs/huggingface_hub/guides/jobs) 上
- RL 环境和打分模型作为 [Spaces](https://huggingface.co/docs/hub/spaces)
- 成对评审（pairwise judge）经由 [Inference Providers](https://huggingface.co/docs/inference-providers)
- 所有工件都在 Hub 上，收集在[一个 collection](https://huggingface.co/collections/HuggingEnvs/paint-with-code-6a955b79d63f67f1631d9be6) 里

两个 Space 起好后，配方就是一条命令。复制[环境](https://huggingface.co/spaces/HuggingEnvs/watercolour-env)和[打分模型](https://huggingface.co/spaces/HuggingEnvs/watercolour-hpsv3)，设置两个环境变量控制奖励配比，然后开跑：

```
hf jobs uv run train/watercolour_grpo.py --flavor h200 --timeout 48h --secrets HF_TOKEN -- \
  --env-url https://<you>-watercolour-env.hf.space \
  --model Qwen/Qwen3.5-35B-A3B --lora --all-linear --bf16 --gradient-checkpointing \
  --subject 'a peach hibiscus' --references 4 \
  --top-p 0.95 --top-k 20 \
  --lr 5e-5 --lr-scheduler constant_with_warmup --warmup-steps 5 \
  --scale-rewards none \
  --steps 110 --n-episodes 240 --num-generations 8 \
  --per-device-batch-size 1 --gradient-accumulation-steps 8 \
  --max-completion-length 8192 \
  --run-tag my-run --out <you>/watercolour-grpo --push-to-hub
```

本文余下部分是走到这一步的故事，[每个部件都在 repo 里](https://github.com/adithya-s-k/HuggingEnvs/tree/main/02-watercolour)。

我一步步跟随原始博客，只在严格必要时才做改动。我自己的每个想法都进了清单而不是实验，那份清单成了文末的「我接下来会尝试什么」，紧挨着完整的已发布工件清单。如果你已经读过他的文章，框架和奖励设计会很眼熟。新增的内容是开放实现、手工评分的池子，以及训练并对比的三种奖励配比——从[你需要构建的 RL 环境](https://huggingface.co/blog/train-to-paint-with-code#the-rl-environment-you-need-to-build)开始。

三次运行，每种奖励配比一次，并行演进。每一帧展示的是一步的中位数画作。现在还不需要分辨它们，文章会说明哪条曲线对应哪次运行。

## 人们为什么喜欢它

这些画看起来松弛、不完美、手作感十足——恰是在图像模型产出完美（统计意义上的平均） pictures 的时刻。我猜这种反差是视频爆火的重要原因。它让我想起生成式 AI 艺术的早期年代，那时重点在于探索媒介本身。[DeepDream](https://research.google/blog/inceptionism-going-deeper-into-neural-networks/)（2015）是个被人们玩成艺术的调试工具；[Edmond de Belamy](https://en.wikipedia.org/wiki/Edmond_de_Belamy)（2018）这类作品来自艺术家对 GAN 能力边界的试探；像 [Mario Klingemann](https://quasimondo.com) 这样的艺术家，那些年用神经网络创作[如梦似幻的肖像](https://artsandculture.google.com/asset/memories-of-passerby-i-mario-klingemann/aAHG7iV3aXme8g)。

这个项目更接近那些早期时光。Surya 在论文里描述了通到这里的路径。他最初是给文生图模型写提示词——提示词是唯一能拉的杆，细节换来越多的控制，但到某个点就到头了。训练模型本身能走得更远。想法的另一半是媒介：模型写一个约 150 行 JavaScript 的程序来画出图像。模型输出是代码，你可以读它、编辑它、重新运行它，每一笔背后的决策都看得见。而风格来自一个限制：模型只被允许使用*库的十个方法*。细节下面讲。

同一时期，[Anna Ridler](https://annaridler.com/works/myriad-tulips) 拍摄了数千朵郁金香、逐张手工标注、把数据集本身作为艺术品展出，之后又在其上训练了模型。我是在构建本项目时 AI agent 带回来的参考文献里发现她的作品的，很喜欢——因为这个项目做的事非常相似：手工策展一组图像，然后对着它们训练。

## 对品味做 RL

近期针对语言模型的 RL 工作大多使用可验证的奖励。例如有标准答案的数学题、能通过测试的代码，或判断对错、运行便宜的评分器。这个项目更接近那个老牌的例外——RLHF：模型从人类偏好中学习一个奖励模型。

这里的奖励是审美偏好。没有*正确*答案。项目真正的问题是：你能不能对品味做 RL。

奖励的定义沿用他博客，也即我构建的 RL 环境所实现的版本：

| 项 | 权重 | 衡量什么 |
| --- | --- | --- |
| `gate` | 0.05 | 草稿能编译、画出了东西、没有作弊 |
| `length` | 0.05 | 向更长的代码片段轻轻推一把 |
| 成对评审 | 0.60 | 风格——与从池子抽取的参考图比较 |
| [HPSv3](https://huggingface.co/MizzenAI/HPSv3) | 0.30 | 渲染结果上的审美偏好 |

[HPSv3](https://huggingface.co/MizzenAI/HPSv3) 是一个开源的 7B 偏好模型。给它一张图和一段文本描述，它返回一个人会有多偏好这张图的分数。它在大规模「成对图像之间的人类选择」数据上训练，所以它的分数是许多人品味的平均。成对评审则是 [Qwen3-VL-30B-A3B-Instruct](https://huggingface.co/Qwen/Qwen3-VL-30B-A3B-Instruct)——一个通过 HF Inference Providers 调用的通用视觉模型。成对评审把候选画作与池中随机抽取的四张参考图并排看，由一段书面描述引导它权衡什么（洇染、透明罩染、柔和边缘），每次比较都按两种呈现顺序各来一遍，它的分数是候选赢下的比较占比。它唯一的标尺就是这个池子，所以它的分数就是我的品味——编码在那些评分里的品味。

奖励函数的四项里有两项是模型。两者都是某个人品味的代理。

这些权重是 Narreddi 收敛出来的。在这里，池子定义了品味。这把工作重心从调超参数移到了构建「决定什么是美」的那个集合。

我用这个奖励训练了三次运行。它们只在两个模型评审之间的权重分配上不同：

| 运行 | 成对评审 | HPSv3 | 角色 |
| --- | --- | --- | --- |
| `judge-led` | 0.60 | 0.30 | 原始配比，停在第 110 步 |
| `hps-led` | 0.30 | 0.60 | 中间点，停在第 110 步 |
| `hps-only` | 0.00 | 0.90 | 验证运行，停在第 60 步 |

我先跑 `hps-only`，验证这条流水线到底能不能学。当奖励开始上升、指标健康之后，没有理由继续跑它，于是我改为启动两个更长的运行。更长的运行提出的问题是：你能把多少 HPSv3 的话语权交给成对评审？评审权重越大，奖励就越意味着*我的*品味而非所有人的品味，爬升应该越难。顺带一提，如果推得足够远、或者你的风格离平均太远，模型可能会彻底停下。

幸运的是它没有停，两个开着成对评审的运行也都学会了。至少从指标和最终画作看，手工评分的池子能够牵引策略。数字在下面。

> 免责声明。如果我们用前沿模型，它本来就能从提示词直接生成画水彩的 JavaScript 代码——那是起点。这里的工作是教会一个更小的模型做到这一点，并融合一个人的艺术偏好。

## 你需要构建的 RL 环境

环境包裹着模型与奖励之间的一切，包括模型用来绘画的 JavaScript 库、限制它的系统提示词、渲染每份草稿的无头 Chromium，以及拒绝作弊的门控（gate）。

这个库干的活比看上去多。[p5.brush](https://github.com/acamposuribe/p5.brush)（作者 [@acamposuribe](https://x.com/acamposuribe)）模拟的是一种媒介而不是画形状：颜料会洇出填充边缘、纸张有纹理、笔触有质量、流场会拖拽笔迹。当模型调用 `brush.fillBleed(0.25)`，它是在决定墨水洇多远。

> 注。p5.brush 的作者在任何这一切之前很久就想教机器画画。2022 年他做了一个生成艺术系列，藏着一本关于教 p5.js 像孩子一样画画的日记：「它几乎连蜡笔都用不好……简单的指令也听不懂。今天到此为止，太令人抓狂了。」这个系列本应有三件作品，他做了两件。Surya 的视频爆火时，他转发了它，分享那本日记，说这件作品就是自己到来的第三件。

p5.brush 暴露 47 个方法。提示词只允许 10 个：`scaleBrushes`、`noStroke`、`fill`、`noFill`、`fillBleed`、`fillTexture`、`beginShape`、`vertex`、`endShape` 和 `circle`。其余三十七个会加的东西——线条、排线、自定义笔刷——会破坏水彩的观感。有了这十个，模型只能画填充形状，而库会给每一个形状加上洇染。

一次 rollout 的部分 draw() 与它的渲染结果。注释是模型自己写的。奖励 0.864，129 行，第 22 步。每幅画的完整源码都在 rollouts 数据集里。

他的博客帮我省了大量时间——否则我可能在迭代提示词上白白浪费。冗长的 API 参考会让模型发明不存在的方法，而他的 200 轮 GEPA 迭代收敛到了一个不带任何文档的严格 allowlist。我见到了同样的失败，然后手写了 allowlist。我对那份配方唯一的增补是一句话：每片花瓣画两到三遍，先大笔一层，再在里面叠一笔更小、更浓的。这个小改动让我的输出色彩鲜艳了很多。

> 注。如果你是第一次听说 GEPA：它是一个自动提示词优化器。语言模型用自然语言反思当前提示词哪里失败、提出更好的版本，循环往复。

门控是最后一块。草稿必须能编译、必须使用这个库而不是直接调 p5、必须在画布上落下真实颜料、不能试图骗过打分器——例如在画布上写文字。

## 池子就是奖励函数

池子由 [178 幅画](https://huggingface.co/datasets/HuggingEnvs/watercolour-reference-pool)组成，按我的个人偏好分成两档：`love` 和 `okay`。它们其实全部由模型生成。四个开放权重模型（通过 Inference Providers 调用）写 p5.brush 草稿，每一份都以 iNaturalist 上一张真实、开放许可的木槿花照片为蓝本。视觉模型对每份草稿给出书面反馈，经过三轮精修。每一张最终渲染再由我逐张评分，178 张入围。

| 生成模型 | 画作数量 |
| --- | --- |
| [GLM-5.2](https://huggingface.co/zai-org/GLM-5.2) | 64 |
| [Kimi-K3](https://huggingface.co/moonshotai/Kimi-K3) | 57 |
| [Qwen3-Coder-Next](https://huggingface.co/Qwen/Qwen3-Coder-Next) | 35 |
| [Qwen3.5-122B-A10B](https://huggingface.co/Qwen/Qwen3.5-122B-A10B) | 22 |

这里我特意选了四个不同的模型家族，检验它们不同的风格。这四个是在快速可靠性检查中每次都能产出有效草稿的开放模型，另外两个候选因未通过而被淘汰。如果你想构建自己的池子，你也许会选别的。

两档画作真实的样子。不同意评分是合理的——某个人的判断如今就是奖励函数。

这两档在奖励中真的起作用。成对评审抽四张参考时，一半来自 `love`、一半来自 `okay`，策略因此总会面对一些它有时能赢的对手，而且赢任意一档的回报相同。这是我少数几个有意为之的改动之一：原始方案只与其最高档比较，我把较容易的那档留在抽签里，让弱小的早期策略也能拿到信号。

池子里没有一幅人类创作的画，这是实实在在的限制。p5.brush 是个小众库，其中有人类作品、且代码可及的只有寥寥几件，远达不到训练语料的需要——他的博客也指出了这一点。

这里有意思的想法——我之前也讨论过——是模型会学会模仿池子里装的东西。如果把环境指向另一个数据集，奖励就会自动改变，一行代码都不用动。对我生成并开放共享的数据集，我还附上了源草稿。

凑近看两个评审，它们回答的是不同的问题。HPSv3 判断的是「这是不是一朵花」，成对评审判断的是「它是否按我选的风格画得好」。

## 再来一次 yolo 跑

在一切跑通之前，是漫长的奖励曲线平坦期。如果你尝试复现过没有开放工件的论文/博客，大概能感同身受。每次运行都在检验我当时觉得合理的某个「哪里出了问题」的理论。一次运行耗时很长，所以我总是在翻上一次结果的时候就把下一次排进队列。和往常一样，答案是从一个更简单、能工作的东西出发，再在其上往上盖。一个没有浏览器、没有评审的简单对照任务，是第一个能学习的尝试，原因则是我的学习率实在太低了。

对奖励做了三个实验，三条平线。我换了池子、去掉了渲染器噪声、关掉了成对评审，哪个都没让曲线动起来。真正动起来的那次改的是 trainer 配置——所以差异在 trainer，不在奖励配比。

另一个花了不少时间才找到的改动，是正确调整 LoRA 参数。惯用的 `target_modules` 列表假设的是稠密模型，而 [`Qwen/Qwen3.5-35B-A3B`](https://huggingface.co/Qwen/Qwen3.5-35B-A3B) 是混合专家模型，大部分投影层的命名都不同，于是适配器只训练了四十层里的十层。我把它改成 `all-linear` 解决了这个问题——它覆盖所有线性层。这个架构里的路由专家是 even `all-linear` 也会冻结的融合张量，但其他所有层都拿到了适配器，这就够学会了。

修复是 TRL [`GRPOTrainer`](https://huggingface.co/docs/trl/grpo_trainer) 里的四个改动：

| 设置 | 从 | 到 | 原因 |
| --- | --- | --- | --- |
| 学习率 | 2e-5 | **5e-5** | *LoRA Without Regret* 用于 GRPO 的上限 |
| 调度器 | `linear` | **`constant_with_warmup`** | linear 衰减在运行中途就烧掉了大部分学习率，奖励始终起不来 |
| `scale_rewards` | `group` | **`none`** | 一次 gate 拒绝把组里其他所有优势都压缩了 |
| `target_modules` | 手写列表 | **`all-linear`** | 覆盖每一个线性层 |

这四个改动解锁了第一次成功的运行（`hps-only`），奖励明显提升。

用这个配置，三次运行都学会了。两个评审运行本来要跑 200 步，停在 110 步——奖励仍在缓慢爬升。一步要十五到十八分钟，且配比之间的对比已经稳定，所以我停掉两者以节省算力。每次运行前三分之一与后三分之一的组平均奖励：

| 运行 | 步数 | 前三分之一 | 后三分之一 | Δ |
| --- | --- | --- | --- | --- |
| `hps-only` | 60 | 0.58 | 0.71 | +0.13 |
| `judge-led` | 110 | 0.45 | 0.72 | +0.27 |
| `hps-led` | 110 | 0.57 | 0.82 | +0.24 |

三条曲线与「我的品味占多大权重」的排序一致。评审权重越大，起点越低、爬升越嘈杂。`judge-led` 前三十步几乎平坦才开始动。这和解调试时的招数是同一个：把问题缩小到有东西能学，再把难的部件一件件加回去。

成对评审项本身在两个使用它的运行中都在上升。随着训练推进，模型对池子赢得更多比较——这正是 `hps-only` 无法做出的声明。任何运行的任何组都没有坍缩到相同奖励（那个会杀死梯度的 GRPO 失败模式）。好奇的话，各指标曲线（HPSv3、颜料覆盖率、熵）以 CSV 形式存在[仓库里](https://github.com/adithya-s-k/HuggingEnvs/tree/main/02-watercolour/results)。

完整的启动命令、硬件，以及把配方变成另外两次运行的那两个环境变量，都在[配方](https://github.com/adithya-s-k/HuggingEnvs/tree/main/02-watercolour)里。

## 它到底学到了什么

**每次运行中，模型最先学会的都是停止产出烂画**——那种总奖励 0.3 以下的近乎空白的画布和无定形的淡彩。在 `hps-only` 里，组均值上涨的四分之三来自烂画变罕见。在评审运行里坍缩更陡：`judge-led` 的前后三分之一之间，低于 0.3 的 rollout 从 99 降到 16；`hps-led` 从 37 降到 4。

这就是为什么那个最直观的视觉指标——每步最好的画——在 `hps-only` 里几乎看不出差别。它整个运行只动 **+0.034**，而中位数动了 **+0.155**。学习体现在分布的中段。

**成对评审改变的是头部。** 在 `hps-only` 里，画作变得更可靠，但没有变好。好画的品质只给组均值加了 +0.03；一旦 HPSv3 看到围绕中心的瓣和一根茎，它就不再要求更多颜料。开着评审时，故事的另一半出现了。这里的*更好*意味着更接近池子——也就是更接近我评过「好」或更喜欢的东西。这部分给 `judge-led` 加了 +0.12、给 `hps-led` 加了 +0.16；每步最好的画也涨了；两个运行的颜料覆盖率都翻倍（0.11 到 0.23、0.13 到 0.30），而 `hps-only` 几乎没推动它。有一幅参考图要超越时，一幅好画仍然可以更好，模型开始因为使用更多颜料而获得奖励。

还有一个发现。模型无视一条明确指令，而且它无视得对。系统提示词要求画十五到三十个填充形状。看真实均值，其实只有 7 到 9 之间；而且 `n_shapes` 与奖励在任何运行里都几乎不相关（+0.000、−0.14、+0.07）。策略不会因为服从那句话得到奖励，所以它不服从。

`hps-only` 这条路也有天花板。如果每次 rollout 都达到它的好水平，该运行的均值也只能到 0.771。更多的步数能否打破它，还是未知数。

画作还展示了表格看不出的东西。在同一运行内，它们彼此都很像。随着训练推进，每个组内部的奖励越来越接近，开篇视频里的中位数画作看起来像同一朵花的多个取景。这就是 GRPO 对着「单一主体的池子」干它设计上会干的事。池子决定什么算多样性，就像它决定什么算品质。如果奖励只为「匹配一朵花」付费，模型就学会只画那一朵花。更多样的输出需要更多样的池子，而建池子是更多的策展工作。Surya 更新的构图就是一个例子。[Alex Yango 的动物画](https://x.com/alexyango/status/2091696296931574217)是同一个配方、池子里换了不同的选择。审美奖励和数学评分器之间最大的区别正在这里：数字背后是一件非常人类的工作——决定什么该进奖励集合。[Jason Liu 关于品味的文章](https://x.com/jxnlco/status/2073819508729684462)一句话讲明了普遍版本：AI 把瓶颈从「制作」挪到了「看见」。

Surya 用他一些心头好收尾他的博客。我不挑我的了——下面是一面墙，装着两次评审运行中奖励评分最高的 178 幅画，和参考池的数量恰好相同，不分先后。打开它，挑你自己的。

奖励在两次评审运行中的 178 幅最爱，乱序排列。现在挑你的。

要挑选，你就看了很多、留下一些——这恰恰是构建本项目奖励的那份工作。每次运行的每一幅画，连同草稿和奖励，都在 rollouts 数据集中，也可以在[这个画廊](https://huggingface.co/spaces/HuggingEnvs/watercolour-gallery)浏览。

每次运行最后一步的中位数画作，顺序与开篇视频相同。同样的基座模型、同样的池子、三种奖励配比、三种风格。

既然奖励部分基于我的品味，以一个观者的身份给出结论也算公平。在我看来，`judge-led` 是最终最多姿、也最具艺术趣味的一次。`hps-led` 画出了令人信服的水彩，但它最好的那些共享一种湿润柔和的湿画法观感，几乎自成一派。`hps-only` 收敛得最狠，大多数画都落在同样的颜色里。你可以在[画廊](https://huggingface.co/spaces/HuggingEnvs/watercolour-gallery)里自己评判——每次运行的每幅画都在，可按步数和奖励排序。

## 基础设施很难

这个项目大半是基础设施。一次运行需要 trainer、两个 Space、一个推理路由器、一条 websocket 连续健康运行好几个小时，而每一个安静失败的部件都会在别处变成一个错误的数字。一半的工作是确认你读到的数字与真实发生过的事相符。

**基础设施故障曾以零分混进奖励。** 渲染超时或打分器没应答，得分和一幅烂画一样——组内的 0.0。在我全部运行里这约占 rollout 的 1.5%，最差的那次达到 5.2%。这会让模型在噪声上训练，所以这些路径现在返回 `None`，rollout 被排除出该组。

**我还发现了 OpenEnv 的一个 bug，并把修复提交上游。** 客户端保持一条持久 websocket，被对端关闭的 socket 会留在缓存里，导致之后每次调用都失败——哪怕环境本身是健康的。我花了两趟跑废一半的运行才找到它。修复已[提交上游](https://github.com/huggingface/OpenEnv/pull/1103)，用上了它的后续运行一直干净至今。

`judge-led` 运行连续两步、各取最好四幅。第 12 步的画是否看起来差了半分，交由你来判断。

**一步的奖励取决于它抽到哪些参考。** 成对评审每步抽四张参考，所以每一步面对的对手集合都不同，有些签就是更难。GRPO 本身大体安全，因为优势是在组内计算的，难签会把整个组一起挪动。我读的那条曲线可不安全——有些看起来是「糟糕的一步」，其实只是难签。上面那张图就是一个例子：第 12 步比第 11 步低了半分，主要因为它抽到了整个运行里最难的参考，而画本身看起来差不多。

## 花了多少钱

取整数字，且只算跑完的运行。

| 部件 | 需要什么 |
| --- | --- |
| trainer | 1 块 H200。60 步约 **18 小时**，110 步约 **34** |
| HPSv3 | 一个 `a100-large` Space，整个运行期间在线 |
| 环境 | 一个 `cpu-upgrade` Space，渲染从容跟得上 |
| 成对评审 | `Qwen/Qwen3-VL-30B-A3B-Instruct` 的 Inference Providers 配额 |
| 池子（一次性） | iNaturalist 开放许可的照片、四个生成模型的 Inference Providers 配额，评分则是你自己的时间 |

一步是八个 rollout，耗时十五到十八分钟，其中 **70-80% 是渲染**。单次渲染 69 到 96 秒，而截止线是 90 秒。一部分在预料之中：Space 没有 GPU，Chromium 用软件渲染 WEBGL 画布，p5.brush 的洇染和纹理是重像素活。即便如此，我本以为会更快，而且我还没找到全部原因。

打分器可能比用它来训练的东西更贵：HPSv3 在整个运行期间必须在线，所以运行结束后请把 Space 暂停，或设置它的休眠计时器。

四个付费服务必须同时健康。只有 Hub 和 trackio 会活得比运行久。

一切都跑在 [HF Jobs](https://huggingface.co/docs/huggingface_hub/guides/jobs) 上，环境是一个 [Docker Space](https://huggingface.co/docs/hub/spaces-sdks-docker)，指标进 [trackio](https://huggingface.co/docs/trackio)。

## 我接下来会尝试什么

本项目的纪律是：以全开放资源复现配方，而不是改进它——于是沿途攒了一堆没试的想法。这些是我真会去试的，按证据强度排序。

**多步，并让模型看见自己画的东西。** 这是我会试的第一件事。原始博客训练的是单轮，我也就训练了单轮；在这个设定里，模型是闭着眼睛画画的。没有任何图像输入，它得到的唯一反馈是一个数字。反馈循环有效性的证据就是池子本身：参考画作来自模型在视觉评论家下迭代三轮，越往后的轮次越好。定义奖励的材料是用一个策略永远拿不到的循环做出来的。

**更小的模型。** 有证据表明 35B 超出了所需。在我的旁路实验里，4B 已经能写出通过门控的有效草稿。如果 4B 能学会这个，实验成本降低一个数量级。

清单上的其他想法还有：RL 之前先在池子源数据上做 SFT、显式奖励颜料用量、随着运行推进把评审的参考配比从易挪到难直到只剩 `love`、放宽十方法 allowlist 以获得更多视觉变化（我的这类尝试崩掉更多草稿、还破坏了水彩观感），以及把同一张图打分两次来检验成对评审到底有多一致。

而且这个方法并不专门用于花。[Alex Yango 用同一机制画了动物](https://x.com/alexyango/status/2091696296931574217)，[Brendan Hogan 对着手工评分的动画片段池训练了 canvas 动画](https://x.com/brendanh0gan/status/2092650655789855222)。我之前也用 [Simon Willison 的鹈鹕基准](https://huggingface.co/blog/sergiopaniego/pelican-env-openenv)玩过类似的东西——代码被渲染成图像并打分。

在所有这一切底下，躺着这个项目无法闭环的问题。**178 幅由模型画的画，定义了这个被训练模型眼中的美。**池子是瓶颈，也是整条流水线里唯一没有原则性答案的部分。

## 我对原版改了什么

给想复现的人：与 Narreddi 配方有两处刻意的分歧，都在前文论证过：

- 成对评审的参考一半抽自 `love`、一半抽自 `okay`，而不是只与最高档比较——这样弱小的早期策略仍能拿到信号。
- 提示词里加了一句关于手艺的小小的话：每片花瓣画两到三遍，先大笔一层，再在里面叠一笔更小、更浓的。

其余——LoRA 用 `all-linear`、基础设施故障返回 `None` 而不是 0.0、评审运行停在第 110 步——都是因为他博客没有写明、我不得不沿途自行拍板的决定。他的实现没有发布，我无法判断这些是与他的选择一致还是相左。
