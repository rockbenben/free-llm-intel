# 一天之内构建领域专用嵌入模型

如果你在构建 RAG（检索增强生成）系统，很可能撞过这堵墙：一切运行良好……直到它不灵了。通用嵌入模型是为理解互联网而训练的，不是为了理解你的合同、生产日志、专有化学配方或内部分类体系。它们能捕捉宽泛的语义相似性，却不懂你领域里那些至关重要的细微差别。当现成模型无法有效捕捉领域特有语义时，微调嵌入模型可以提升检索流水线的表现。尽管嵌入对 RAG 性能如此关键，这一流程却出奇地割裂：所需技能很专门，时间投入也吓人。

只要一块 GPU、不到一天的训练时间，你就能把一个通用嵌入模型变成真正懂你领域的模型——完全不需要手工标注。为了帮你快速起步，我们还发布了一份即用型[合成训练数据集](https://huggingface.co/datasets/nvidia/Retrieval-Synthetic-NVDocs-v1)，正是用这条流水线从 NVIDIA 公开文档生成的。用这份数据和这套配方，我们在 Recall@10 和 NDCG@10 上都看到了超过 10% 的提升。[Atlassian](https://www.atlassian.com/) 把这套配方用于他们的 [JIRA 数据集](https://zenodo.org/records/15719919/files/2025-06-23%20ThePublicJiraDataset.zip?download=1)做微调，Recall@60 从 0.751 提升到 0.951——提升 26%——而且是单卡完成的。

## ⚙️ 环境准备

本教程微调的基础模型是 [Llama-Nemotron-Embed-1B-v2](https://huggingface.co/nvidia/llama-nemotron-embed-1b-v2)——一个在质量与推理成本之间取得平衡的 10 亿参数嵌入模型。开始之前，请按照这份[设置指南](https://github.com/NVIDIA-NeMo/Nemotron/blob/main/docs/nemotron/embed/README.md)操作。

## 📚 第 1 步：从文档生成训练数据

微调嵌入模型需要数千个（查询，相关文档）对。大多数场景并没有现成的这类数据。手工制作既贵又慢，还常被标注者个人对"相关"的理解带偏。

与其手工标注，不如用一个 LLM（nvidia/nemotron-3-nano-30b-a3b）阅读你的文档，自动合成高质量的问答对。

```
nemotron embed sdg -c default corpus_dir=./data/my_domain_docs
```

### 它是怎么工作的？

幕后运行的是一条由 [NeMo Data Designer](https://github.com/NVIDIA-NeMo/DataDesigner) 驱动的四阶段合成数据生成（SDG）流水线：

[![sdg_pipeline](https://cdn-uploads.huggingface.co/production/uploads/662a9c2154a9f1037104a075/84IMYChKX4twWnC4U6iCQ.png)](https://cdn-uploads.huggingface.co/production/uploads/662a9c2154a9f1037104a075/84IMYChKX4twWnC4U6iCQ.png)

### 输出长什么样？

**源文档片段：**

The thermal design power (TDP) of the H100 GPU is 700W in SXM form factor. The cooling solution must maintain junction temperature below 83°C under sustained workloads. Liquid cooling is recommended for dense deployments exceeding 4 GPUs per node, as air cooling cannot dissipate sufficient heat in standard 2U chassis configurations.

**生成的 QA 对：**

```
{
  "question": "What cooling approach is recommended when deploying more than 4 H100 GPUs per server node?",
  "answer": "Liquid cooling is recommended for dense deployments exceeding 4 GPUs per node, as air cooling cannot dissipate sufficient heat in standard 2U chassis configurations.",
  "query_type": "contextual",
  "reasoning_type": "factual",
  "question_complexity": 3,
  "segment_ids": [1],
  "quality_score": 8.5
}
```

```
{
  "question": "How does the 700W TDP of the H100 SXM constrain the choice between air and liquid cooling in multi-GPU configurations?",
  "answer": "The 700W TDP generates substantial heat that must be dissipated to keep junction temperatures below 83°C. In dense configurations exceeding 4 GPUs per node, air cooling in standard 2U chassis cannot handle this thermal load, making liquid cooling necessary.",
  "query_type": "multi_hop",
  "reasoning_type": "causal",
  "question_complexity": 4,
  "segment_ids": [1, 2],
  "hop_count": 2,
  "quality_score": 9.0
}
```

注意区别：第一个问题是简单的事实查找，第二个需要多跳因果推理。流水线两种都会生成，复杂度和跳数可配置（复杂度 2–5、跳数 1–3）。每个 QA 对随后会经过质量评估，获得相关性、准确性、上下文支撑度和清晰度四个子分数及总分。只有达到阈值的对才会纳入训练。

## ⛏️ 第 2 步：挖掘困难负样本（以及它为何重要）

如果只用正样本对（查询 + 正确文档）训练嵌入模型，它只能学会区分明显不同的文档，碰到困难样本就失效——那些*看起来*相关但其实不是答案的段落。在真实检索系统里，正是这些"差一点"的文档导致糟糕的回答。困难负样本挖掘把这些令人混淆的段落找出来，让模型学会分辨它们。

```
nemotron embed prep -c default
```

上面的命令会自动执行三个子步骤：

### 2a. 训练/验证/测试划分

生成的 QA 对被划分为训练集（80%）和测试集（20%）。测试集按 [BEIR](https://github.com/beir-cellar/beir) 兼容的基准格式组织，供第 5 步做标准化评估。

### 2b. 困难负样本挖掘

使用基础嵌入模型，流水线：

- 把每个查询和语料库中每个段落编码成向量。
- 计算每个查询与所有段落的相似度。
- 屏蔽掉每个查询已标注的正样本。
- 应用边界过滤器：任何得分*高于*正样本最低分 95% 的非正文档被淘汰。这个排除区防止伪负样本——有些未标注段落与正样本近到可能确实是相关的。
- 在幸存候选中，挑选得分最高的 top-k 文档作为困难负样本（默认每个查询 5 个）。

结果：困难负样本是最相似、同时又安全地落在正样本得分上限之下的非正段落。它们是当前模型认为高度相关、却不是标注答案的段落。

**为什么有效**：用简单负样本（完全不相关的段落）训练，模型学不到新东西；用困难负样本训练，则迫使它学习你领域中真正重要的细微差别。例如在医学语料库中，关于"二甲双胍治疗 2 型糖尿病的剂量"的问题，其困难负样本可能是"二甲双胍的副作用"或"1 型糖尿病的胰岛素剂量"——接近但有本质区别。95% 的边界上限防止挖掘器选中离正样本太近的段落——它们可能是 SDG 时漏标的正确答案。

### 2c. 多跳展开（Unrolling）

多跳问题会引用多个正文档。例如问题 *"3.2 节中的热管理系统与 5.1 节描述的功耗约束有什么关联？"* 就有两个正样本段落。

展开操作为每个（查询，正文档）对生成一条训练样本，使对比损失能独立看到每个正样本。一个有 2 个正文档的问题变成 2 条训练样本，各自使用相同的困难负样本、但正样本不同。

最终输出是一份可直接用于训练的 JSON 文件：

```
{
  "question_id": "q42_0",
  "question": "How does the thermal management system in Section 3.2 relate to the power constraints described in Section 5.1?",
  "pos_doc": [{"id": "Section 3.2"}],
  "neg_doc": [{"id": "d_x7y8z9"}, {"id": "d_m4n5o6"}, {"id": "d_p1q2r3"}, {"id": "d_s4t5u6"}, {"id": "d_v7w8x9"}]
}, 
{
  "question_id": "q42_1",
  "question": "How does the thermal management system in Section 3.2 relate to the power constraints described in Section 5.1?",
  "pos_doc": [{"id": "Section 5.1"}],
  "neg_doc": [{"id": "d_x7y8z9"}, {"id": "d_m4n5o6"}, {"id": "d_p1q2r3"}, {"id": "d_s4t5u6"}, {"id": "d_v7w8x9"}]
}
```

## 🔍 第 3 步：理解多跳问题及其为何改善检索

标准的嵌入微调为每个段落生成一个问题，训练模型把二者匹配起来。这对简单事实查找管用，但真实用户会提出横跨多个文档或章节的复杂问题。如果模型只见过单跳训练数据，遇到这类复杂查询就难以检索*所有*相关段落。

SDG 流水线默认生成 1 到 3 跳的问题：

- **1 跳：**"H100 SXM 的 TDP 是多少？"——单个段落即可回答。
- **2 跳：**"H100 的 TDP 与高密度部署的散热要求有什么关联？"——需要连接两个段落的信息。
- **3 跳：**"综合 TDP、散热约束和机架密度限制，一个标准数据中心列最多能部署多少块 H100 GPU？"——综合三个段落。

每一跳都带有自己的上下文摘要和段 ID，因此训练数据保留了完整的推理链。展开（第 2c 步）之后，每个（问题，相关段落）对都成为独立的训练信号，教会模型：对于多跳查询，*所有*这些段落都是相关的。

微调后的模型学会检索上下文相关的文档，而不仅是词面相似的文档。

## 🧠 第 4 步：微调嵌入模型

```
nemotron embed finetune -c default
```

### 对比学习如何工作

训练采用**双塔架构（biencoder）**加**对比损失**。

[![contrastive_learning](https://cdn-uploads.huggingface.co/production/uploads/662a9c2154a9f1037104a075/ntYmgzatUK_Sfn35GCdve.png)](https://cdn-uploads.huggingface.co/production/uploads/662a9c2154a9f1037104a075/ntYmgzatUK_Sfn35GCdve.png)

温度设为 0.02 是有意为之的激进选择，它产生非常尖锐的概率分布。这样可行是因为第 2 步挖出的困难负样本质量很高：它们是真正令人混淆的段落，模型需要强梯度才能学会区分。

### 关键超参数

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| Epochs | 3 | **默认值是针对小规模示例数据集调的；真实数据通常 1–2 个 epoch 就够了**，以免过拟合。 |
| 学习率 | 1e-5 | 调优建议：试默认值的两倍和一半 |
| 学习率预热步数 | 5 | 设为微调总步数的 5-10%，让训练早期更稳定 |
| 全局批量大小 | 128 |  |
| 每个查询的段落数 | 5 | 1 个正样本 + 4 个困难负样本 |

### 检查点频率

如果配置中省略 `ckpt_every_steps`，检查点频率会自动设定：

- **Map 式数据集**（长度已知）：默认每个 epoch 一次。
- **Iterable 数据集**（长度未知）：默认训练期间两次。

这意味着你可以先用小语料（50–100 篇文档）快速做个概念验证，之后再扩容，无需手动调检查点设置。

## 📈 第 5 步：量化提升

微调真的有帮助吗？在保留的测试集上，用标准化评估把基础模型和微调检查点对比一下：

```
nemotron embed eval -c default
```

评估使用 [BEIR 框架](https://github.com/beir-cellar/beir)，在 k = 1、5、10、100 处计算四项标准信息检索指标：

- nDCG@k：排序质量——最好的文档是否排在最前？
- Recall@k：覆盖率——前 k 条结果中出现了多少比例的相关文档？
- Precision@k：准确率——前 k 条结果中真正相关的占多少？
- MAP@k：所有查询的平均精度

一次成功的微调，通常在不到 1 天内带来 nDCG@10 和 Recall@10 约 10% 的提升。

**使用 Retrieval Synthetic NVDocs 的结果：**

```
📊 Comparison (Base -> Fine-tuned)
============================================================
  NDCG:
    NDCG@1: 0.55178 → 0.60796 (+0.05618, +10.2%)
    NDCG@5: 0.51894 → 0.57689 (+0.05795, +11.2%)
    NDCG@10: 0.55506 → 0.61559 (+0.06053, +10.9%)
    NDCG@100: 0.60617 → 0.66567 (+0.05950, +9.8%)
  Recall:
    Recall@1: 0.28478 → 0.31547 (+0.03069, +10.8%)
    Recall@5: 0.54486 → 0.60288 (+0.05802, +10.6%)
    Recall@10: 0.62979 → 0.69296 (+0.06317, +10.0%)
    Recall@100: 0.81421 → 0.87020 (+0.05599, +6.9%)
```

### 如果数字没有提升怎么办？

流水线让迭代很容易：

- **SDG 质量分低？** 检查文档质量——干净、排版良好的文本产生更好的合成数据。换一个更大更强的 LLM 试试。
- **训练数据不够？** 往语料里加更多文档，重跑 Stage 0。
- **过拟合？** 默认 3 个 epoch 是为小示例数据集校准的；对大多数真实数据，**1–2 个 epoch 就够**。也可以考虑提高质量阈值，只保留最佳训练样本。
- **学习率不对？** 试默认学习率的两倍或一半。

这套配方已由 Atlassian 在真实企业数据上验证。他们按上述同样的阶段，把这条流水线用于在[公开 Jira 数据集](https://zenodo.org/records/15719919/files/2025-06-23%20ThePublicJiraDataset.zip?download=1)上微调 Llama-Nemotron-Embed-1B-v2，只用一块 NVIDIA A100 80GB GPU。

## 🚀 第 6 步：导出与部署

PyTorch 检查点适合评估，但用于生产太慢。最后两个阶段把模型转换格式并以 API 形式提供出去。

### 导出为 ONNX / TensorRT

```
nemotron embed export -c default
```

这会把微调后的检查点导出为 ONNX（opset 17）。还可以选择编译 TensorRT 引擎以获得最大推理吞吐，并为批量大小（1–64）和序列长度（3–256）配置优化 profile：

```
# ONNX only (runs anywhere)
nemotron embed export -c default export_to_trt=false

# FP8 quantization for further speedup
nemotron embed export -c default quant_cfg=fp8
```

### 用 NVIDIA NIM 部署

导出的模型被部署进一个 [NVIDIA NIM](https://developer.nvidia.com/nim) 容器——生产就绪的推理微服务，暴露 OpenAI 兼容的 /v1/embeddings 端点：

```
nemotron embed deploy -c default
```

服务起来后，任何客户端都可以调用：

```
curl -X POST http://localhost:8000/v1/embeddings \
  -H "Content-Type: application/json" \
  -d '{"input": ["What cooling is needed for 8 H100 GPUs in a 2U chassis?"],
       "model": "custom",
       "input_type": "query"}'
```

由于 NIM 提供的是 OpenAI 兼容 API，任何使用 embeddings API 格式的现有 RAG 流水线都能直接接入——无需改代码。

### 验证部署精度

流水线包含一个 NIM 精度验证步骤，对已部署的端点跑同一套 BEIR 评估：

```
nemotron embed eval -c default eval_nim=true eval_base=false
```

这能发现 ONNX/TensorRT 转换带来的任何精度损失。指标在容差内一致（@1 为 0.03，@5 及以上为 0.01）标记通过；超出转换噪声的偏差会被标红。

## 把一切串起来

从原始文档到部署完成的模型，整条嵌入微调流水线只需六条命令。

```
# 1. Generate synthetic training data from your documents
nemotron embed sdg -c default corpus_dir=./data/my_docs

# 2. Prepare the training data (split data, mine hard negatives, unroll)
nemotron embed prep -c default

# 3. Fine-tune the embedding model
nemotron embed finetune -c default

# 4. Evaluate the base vs. fine-tuned model
nemotron embed eval -c default

# 5. Export the optimized model
nemotron embed export -c default

# 6. Deploy the model
nemotron embed deploy -c default
```

| 阶段 | 需要 GPU？ | 预计时长 | 说明 |
| --- | --- | --- | --- |
| SDG | 否（用 API） | 约 1 小时 | 视语料规模和 API 限速而定 |
| 数据准备 | 是（40 GB 显存） | 约 5 分钟 | 困难负样本挖掘在 GPU 上进行 |
| 微调 | 是（80 GB 显存） | 约 1 小时 | 视数据集规模和 epoch 数而定 |
| 评估 | 是（40 GB 显存） | 约 5 分钟 |  |
| 导出 | 是（40 GB 显存） | 约 5 分钟 | TensorRT 需要 NGC 容器 |

**合计：不到一天，其中大部分时间是可以撒手的训练。** 小语料（约 500 篇文档）整条流水线约 2–3 小时即可跑完。

流水线可以端到端运行，也可以根据你的起点单独执行每个阶段。例如，如果你手头有原始文档，可以从合成数据生成（SDG）开始；已经包含困难负样本的数据集可以跳过前面的步骤，直接微调。由于每个阶段都使用 JSON、BEIR、ONNX 等标准格式，集成自定义组件或在其他工作流中复用中间产物都很容易。配方的运行方式同样灵活：支持本地机器、Docker 容器或基于 Slurm 的集群。
