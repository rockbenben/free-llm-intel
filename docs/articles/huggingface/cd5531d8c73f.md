# Bamba：推理高效的混合 Mamba2 模型 🐍

作者：Linsong Chu、Divya Kumari、Tri Dao、Albert Gu、Raghu Ganti 等（IBM / Princeton / CMU / UIUC 联合团队）

![Bamba](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/bamba/bamba.jpeg)

## TL;DR

我们发布 **Bamba-9B**，一个由 IBM、Princeton、CMU 和 UIUC 在**完全开放的数据**上训练出来的推理高效 Hybrid Mamba2（混合 Mamba2）模型。在推理时，相比 vLLM 中的标准 transformer，该模型带来了 2.5 倍的吞吐提升和 2 倍的延迟加速。为了促进社区实验，模型已可立即在 `transformers`、`vLLM`、`TRL` 和 `llama.cpp` 中使用。我们还发布了调优、训练和扩展预训练配方，以及一个有状态的数据加载器，并邀请社区继续改进这个模型。让我们一起攻克 KV-cache 瓶颈！

## 动机 🌟

Transformer 模型在真实应用中的使用越来越多，但它们在推理时面临内存带宽瓶颈，尤其在长上下文模型的逐 token 解码阶段。降低精度、层剪枝、压缩等技术可以缓解问题，但没有解决根因——随着上下文长度增加，KV-cache 所需的内存量也在持续增长。[Mamba](https://huggingface.co/papers/2312.00752)、[Griffin](https://huggingface.co/papers/2402.19427)、[DeltaNet](https://huggingface.co/papers/2406.06484) 等新架构通过让 KV-cache 大小保持恒定来消除这一瓶颈。Mamba 架构近期在社区中获得了广泛关注。例如，[Jamba](https://huggingface.co/papers/2403.19887) 和 [Samba](https://huggingface.co/papers/2406.07522) 将 Mamba 层与 transformer 层交错，探索由此产生的混合 Mamba 模型。[Codestral Mamba](https://mistral.ai/news/codestral-mamba/) 是一个纯 Mamba2 模型，在编码任务上展示了 SOTA（业界领先）成绩；NVIDIA 的混合 Mamba2 模型也在长上下文和传统 LLM 基准上取得了有竞争力的表现。近期的创新，如 [Falcon Mamba](https://huggingface.co/collections/tiiuae/falconmamba-7b-66b9a580324dd1598b0f6d4a) 和 [Falcon 3 Mamba](https://huggingface.co/tiiuae/Falcon3-Mamba-7B-Base)，在发布时都登上了 [Hugging Face 榜单](https://huggingface.co/spaces/open-llm-leaderboard/open_llm_leaderboard)的 SOTA 排名。

我们发布 Bamba-9B——一个在 2.2T token 上训练的混合 Mamba2 模型——进一步验证了这些新架构。这次 IBM、Princeton、CMU 和 UIUC 的合作提供了完整的训练脉络、模型 checkpoint 和预训练代码，以支持可复现性和实验。已发布 checkpoint 的训练数据集不包含任何与基准对齐的指令数据（FLAN 除外），以保留扩展预训练和微调的灵活性。我们的目标是展示混合 Mamba2 架构的潜力——在中低规模模型（7B-10B）上拿出强劲性能——并为社区提供完全可复现、用开放数据集训练出来的 checkpoint。

为了促进社区实验，我们还发布了分布式无状态 shuffle 数据加载器，并让混合 Mamba2 架构在 `transformers`、`TRL`、`vLLM`、`llama.cpp` 等开源库中可用。我们希望这些努力能推动 Mamba 架构的采用、缓解 KV-cache 瓶颈，并缩小与 SOTA 开源模型的差距。

### 在 transformers 中使用 🤗

要在 transformers 中使用 Bamba，你可以使用熟悉的 `AutoModel` 类和 `generate` API。更多细节请参考 [Bamba GitHub](https://github.com/foundation-model-stack/bamba/) 中的说明。

```
from transformers import AutoModelForCausalLM, AutoTokenizer

model = AutoModelForCausalLM.from_pretrained("ibm-fms/Bamba-9B")
tokenizer = AutoTokenizer.from_pretrained("ibm-fms/Bamba-9B")

message = ["Mamba is a snake with following properties  "]
inputs = tokenizer(message, return_tensors='pt', return_token_type_ids=False)
response = model.generate(**inputs, max_new_tokens=64)
print(tokenizer.batch_decode(response, skip_special_tokens=True)[0])
```

## 评估 📊

我们把评估分成三部分：

- 与 SoTA transformer 模型对比
- 与 token 预算相近的 transformer 模型对比
- 与其他 Mamba 变体对比

> 评估设置 ⚙️ 🖥️：
> 除 NVIDIA Mamba2 Hybrid 模型外，我们按照此处的设置和脚本重跑了所有基准测试。NVIDIA Mamba2 Hybrid 模型无法跑基准，因为其权重不是 Hugging Face transformers 兼容格式，因此我们引用原论文的数值。对于 v2 榜单结果，我们做了归一化并报告归一化后的结果。除特别注明外，所有评估中数值越高越好。

### TL;DR 评估

Bamba-9B 证明了混合 Mamba 模型与 transformer 模型相比具有竞争力。它在数学基准和 MMLU 分数上有差距（MMLU、GSM8K、MMLU-PRO、MATH Lvl 5），但若剔除这些基准，其平均表现与 Meta Llama 3.1 8B 基本持平（Llama 为 44.68，Bamba 为 45.53）——而后者用了*多 7 倍*的数据训练。这些差距可以通过以下途径弥补：(a) 用更多 token 扩展预训练（MMLU 分数在训练过程中稳步提升），(b) 在预训练/退火阶段加入高质量数学数据。后续计划包括使用 Olmo2 mix 等更新的数据集，并用与基准对齐的混合数据集（如 Dolmino mix）做退火。

Bamba-9B 的结果也缓解了人们对 NVIDIA 混合 Mamba2 模型在榜单基准上得分偏低的担忧。NVIDIA 研究的目标是在完全相同的条件下对比架构。与他们的发现一致，Bamba-9B 再次确认：混合 Mamba2 架构能提供与 transformer 模型相当的性能，同时带来最高 5 倍的推理效率。

### 与 SoTA transformer 模型对比

我们把 Bamba-9B 与同等规模的 SoTA transformer 模型对比（[Meta Llama 3.1 8B](https://huggingface.co/meta-llama/Llama-3.1-8B)、[IBM Granite v3 8B](https://huggingface.co/ibm-granite/granite-3.0-8b-base)、[Olmo2 7B](https://huggingface.co/allenai/OLMo-2-1124-7B) 和 [Gemma 2 9B](https://huggingface.co/google/gemma-2-9b)）。我们观察到，虽然存在明显的基准差距，但这些差距并不清楚是否指向 Mamba/Mamba2 模型的缺陷。事实上，仔细分析表明，差距主要源于训练所用的数据量，以及在退火阶段加入了与基准对齐的指令数据集。例如，我们做过一次小规模实验，加入 `metamath` 后 `GSM8k` 分数从 `36.77` 提升到 `60.0`。我们将在即将发表的论文中发布详细分析和发现。

Mamba/Mamba2 对比

### 与基于 Mamba/Mamba2 架构的语言模型对比

过去 6 个月涌现出多个基于 Mamba/Mamba2 架构的模型（如 NVIDIA hybrid Mamba2、Codestral Mamba、Falcon Mamba 和 [Zamba 7B v1](https://huggingface.co/Zyphra/Zamba-7B-v1)），不断提升这类架构的性能，展示了它们出色的推理性能，并缩小了与 transformer 模型在基准结果上的差距。我们在 Bamba-9B、NVIDIA hybrid Mamba2、Zamba 和 Falcon Mamba 之间对比了 8 个关键基准。

Falcon Mamba 是纯 Mamba 模型；Zamba 是每 6 个 Mamba 层共享一个注意力层；Bamba-9B 和 NVIDIA 都是完整注意力层与 Mamba2 层交错的混合模型。Falcon Mamba 训练到了 5.5T token，整体表现最好，但在长上下文任务上它的表现如何仍是未知数——而那恰恰是 Mamba 系架构在推理性能上真正发光的地方。Zamba 训练的 token 更少（1T），但采用了不同的混合架构，并使用了与基准对齐的指令数据集，包括由更强语言模型生成的数据。Bamba-9B 和 NVIDIA hybrid Mamba2 彼此相当相似（差异细节在模型架构一节汇总），但 Bamba-9B 训练到 2.2T token，而 NVIDIA Hybrid Mamba 训练到 3.5T token。

## 推理效率 ⚡🏎️

KV-cache 瓶颈是大型语言模型的一大挑战，由此催生了量化、剪枝以及 Mamba2、Linear Transformer、RetNet 等新架构方案。即使使用标准 transformer，要在规模化场景中实现推理效率，往往也需要定制 kernel。Bamba-9B 借助社区在 kernel 供给上的势头，并通过与 vLLM 模型服务框架的集成进一步提升了性能。

我们在 vLLM 集成方面的进展通过[这个 PR](https://github.com/vllm-project/vllm/pull/10909)跟踪，基准测试在 NVIDIA H100 80GB GPU 上对比 Bamba-9B 与 Meta Llama 3.1 8B。输入长度取 1K token，输出长度从 2K 到 64K，覆盖多种批大小，我们测量了吞吐（tokens/second）和延迟。结果显示，随着批大小和序列长度增加，Bamba-9B 相比 transformer 模型可实现最高 2-2.5 倍的吞吐和延迟优势。这些增益有助于实时应用和 GPU 利用率——吞吐比（>1）越高、延迟比（<1）越低越好。

我们的分析表明，在 H100 NVIDIA GPU 上，当推理转为内存瓶颈时（生产环境通常如此），预期可获得 5 倍加速——参见关于**算术强度（Arithmetic Intensity）**的附录。但由于三个主要原因，我们在 vLLM 中尚未实现这一加速：

- Bamba 及任何基于 Mamba2 的架构不支持分块预填充（chunked pre-fill）
- 内存分配仍按标准 transformer 的 KV-cache 假设
- Mamba2 kernel 尚未针对 H100 GPU 优化

这些问题在[这里](https://github.com/foundation-model-stack/bamba/issues/3)跟踪。

## 模型架构

我们的模型架构基于 NVIDIA hybrid Mamba2，并做了以下改动。

| 参数 | Bamba 9B | NVIDIA hybrid Mamba2 8B |
| --- | --- | --- |
| 总层数 | 32 | 29 |
| 注意力层数 | 3 | 4 |
| Mamba2 层数 | 29 | 25 |
| MLP 扩展系数 | 3.5 | 4 |
| 词表大小 | 128k | 256k |
| 非嵌入参数 | 8.8B | 8.6B |
| RoPE | 是 | 否 |
| Gated linear units | 是 | 否 |

Mamba2 层共有 8B 参数，完整注意力层 800M，嵌入层 1B。隐藏维度为 4K，完整注意力使用 GQA（8 个 KV-head、32 个头），Mamba2 层的 head 维度为 64，卷积核大小为 4。两个模型之间最显著的改动是把完整注意力层从 NVIDIA hybrid Mamba2 的 4 层减少到 Bamba-9B 的 3 层，并引入了 RoPE 位置编码。

## 数据

自 The Pile 数据集问世以来，开源数据已经进步很多。我们开始训练这个模型时，最好的开源数据是 Dolma v1.7——通过 [Olmo 模型](https://allenai.org/olmo)以及 Hugging Face 数据团队的[消融实验](https://huggingface.co/spaces/HuggingFaceFW/blogpost-fineweb-v1)证明其效果很好。此后又发布了多个更高质量的开源数据集，如 [DCLM](https://www.datacomp.ai/dclm/)、[FineWeb-2](https://huggingface.co/collections/HuggingFaceFW/fineweb2-6755657a481dae41e8fbba4d) 和 [Olmo2 mix](https://huggingface.co/datasets/allenai/olmo-mix-1124)。

我们在训练的第一阶段使用 Dolma v1.7，选定的数据混合如下图。训练的第二阶段使用 [Fineweb-edu](https://huggingface.co/datasets/HuggingFaceFW/fineweb-edu) 和 [Cosmopedia](https://huggingface.co/datasets/HuggingFaceTB/cosmopedia)。这些数据集以原始形式下载，并用运行在内部大规模 [Red Hat Open Shift](https://www.redhat.com/en/technologies/cloud-computing/openshift) 集群上的 [Ray 框架](https://github.com/ray-project/ray)进行 tokenization。我们计划不久后发布 tokenized 并格式化好的 parquet 数据，以便复现。

## 预训练

Bamba 的预训练是分阶段进行的。我们在 1.8B 模型规模、100B token 上做了大量消融实验来确定合适的学习率。基于该研究的积极结果，我们用 Dolma mix 训练了更大规模的模型——3B 训练到 2T token。我们还按 Meta Llama 架构、用相同数据混合训练了一个 3B transformer 模型，观察到 Bamba 模型性能相当或更好，这与同期 NVIDIA 研究得出的结论一致。最后，我们设计了 9B 模型架构并在相同混合上重新训练。所有模型都用 PyTorch FSDP 训练。

> 训练细节：
> 我们使用余弦学习率调度，峰值学习率 3e−4，前 2000 步二次 warmup，衰减系数 0.033，在 2T token 内结束学习率为 1e−5。使用 AdamW 优化器，β1 为 0.9、β2 为 0.95。权重衰减 0.1，序列长度 4096，全局批大小 1.5M token/批。我们用 IBM Cloud Vela 生产集群的 192 块 A100 GPU，耗时 2 个月训练了这个模型。该集群由 Red Hat OpenShift 管理。期间我们遇到 3 次任务中断，原因分别是任务部署错误和硬件故障；硬件相关的任务故障由 autopilot 自动检测。
> 我们还使用 Hugging Face FineWeb-edu 和 Cosmopedia 的高质量数据做了第二阶段训练，额外训练了 200B token。我们用 2e−5 的学习率和余弦调度对模型做退火，这帮助提升了分数。我们目前正在尝试更多高质量数据，并将作为开源承诺的一部分发布后续 checkpoint。

## 数据加载器

训练高质量语言模型有很多方面，数据加载器是重要的一环。过去 18 个月，我们一直在打磨一个能满足大规模分布式训练需求的数据加载器。我们把它开源，方便其他人配合自己选择的框架使用。我们已在 Bamba 模型训练中使用了它，并将其集成进了 [Torch Titan](https://github.com/pytorch/torchtitan/)。据我们所知，这是目前唯一一个提供丰富功能集的开源数据加载器。

该数据加载器提供以下关键特性：

- **有状态、可 checkpoint**，确保能在 epoch 中途无缝恢复
- **自动重缩放**以适应变化的负载和 GPU 分配
- 数据**流式**处理，shuffle **零开销**
- **异步分布式**运行，无需点对点通信
- 支持**动态数据混合**与即时 tokenization
- PyTorch 原生，**模块化**、**可扩展**

这个数据加载器经过数百个训练任务的实战检验，并在数月持续运行中不断优化。主要代码在本仓库的[这里](https://github.com/foundation-model-stack/fms-fsdp/blob/main/fms_fsdp/utils/dataset_utils.py)，我们也与 Torch Titan 团队合作使其可用，见[这里](https://github.com/pytorch/torchtitan/pull/376)。我们正在与 Meta PyTorch 团队合作，把这个数据加载器贡献进 PyTorch 核心。

## 量化

我们近期开源了一个模型[量化框架](https://github.com/foundation-model-stack/fms-model-optimizer/)。通过该框架，我们利用 [llm-compressor](https://github.com/vllm-project/llm-compressor) 把 Bamba checkpoint 量化为 `fp8`。在 OpenLLM 榜单的所有基准上，我们观察到精度损失极小：具体到 Bamba 9B，V1 平均分只有 `0.1` 的微小差异（从 `62.31` 到 `61.5`），V2 平均分下降 `0.9`（`10.91` 到 `10.04`）。这些量化 checkpoint 也随 `bf16` 版本一同发布。这也验证了 Bamba 模型和 SoTA transformer 模型一样适合量化。

我们正在为该模型启用 vLLM 中的 `fp8` 推理，这需要更新 kernel。线性层和完整注意力容易处理，但 Mamba2 层需要更新 Triton/CUDA kernel 以支持 `fp8`。

## 上下文长度扩展

我们目前正在探索多种长上下文扩展方案，首先是在完整注意力层上应用 [LongRope](https://github.com/microsoft/LongRoPE/tree/main)。以 PhoneBook 检索为任务的初步结果表明 LongRoPE 可以应用于该模型。我们把 Bamba-9B 的上下文长度扩展 4 倍和 8 倍，并将上下文扩展后的 Bamba-9B 与 Meta Llama 的三个版本——Llama2、Llama3、Llama3.1（训练上下文长度分别为 4K、8K、128K）对比。结果如下图所示。

![Datamix](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/bamba/phonebook.png)

我们观察到，上下文扩展后的 Bamba-9B 在不做任何微调的情况下，16K 上下文长度内表现非常出色，大幅超过原版 Bamba-9B、Llama2-7B 和 Llama3-8B，并与 Llama3.1-8B 表现相当。在 32K 序列长度上，Llama3.1 取得最佳成绩。我们计划在长上下文扩展模型就绪后发布。

## 总结 🎯

Bamba-9B 由 IBM、Princeton、CMU 和 UIUC 联合开发，是一个性能强劲的混合 Mamba2 模型。模型完全在开放数据集上训练，我们发布了中间和最终 checkpoint。为了促进社区实验，模型已可立即在 `transformers`、`vLLM`、`TRL` 和 `llama.cpp` 中使用。我们还发布了调优、训练和扩展预训练配方以及有状态数据加载器，并邀请社区继续改进这个模型。

关键要点：

- **推理效率**：Bamba-9B 在吞吐和延迟上有显著提升，增强了实时应用的性能。在 vLLM 中与 Llama 3.1 8B 的基准测试显示 2.5 倍吞吐和 2 倍延迟的改善，后续还会更好！
- **有竞争力的基准成绩**：Bamba-9B 与 Meta Llama 3.1 8B 等业界领先（SoTA）的 transformer 模型相比表现有竞争力。剔除数学和 MMLU 任务后，其平均基准成绩与它们相当，这些差距可以通过延长训练和使用数学向数据集来弥补。
- **开放协作**：模型的开发全部使用开放数据，推动了 AI 社区内的透明度和可复现性。

更多细节及模型与相关资源访问，请前往 [Bamba GitHub 仓库](https://github.com/foundation-model-stack/bamba)。

## 附录：算术强度

使用以下符号：
$b$：批大小
$s$：序列长度
$h$：隐藏维度大小（4096）
$d$：head 维度（128）
$l$：总层数（32）
$l_{attn}$：注意力层数（3）
$l_{ssd}$：SSD 层数（29）

注意力模型和 Bamba 模型都配置了 4:1 的 GQA（在注意力层中）、MLP 扩展比 3.5，并在 MLP 块中使用 GLU。Bamba 的 SSD 层配置为：状态维度 $d$，head 维度 $d/2$，head 数量 = $4h/d$。不含嵌入层的模型规模为：

| 模型类型 | 模型规模 |
| --- | --- |
| attention | $13h^2l$ |
| Bamba | $15.5h^2l$ |

在预填充阶段，模型带来的计算与内存（读 + 写）需求为：

| 模型类型 | 计算 Prefill | 内存 Prefill |
| --- | --- | --- |
| attention | $26bsh^2l + 4bs^2hl$ | $13h^2l + 0.5bshl$ |
| Bamba | $31bsh^2l + 4bs^2hl_{attn} + 4bsdhl_{ssd}$ | $15.5h^2l + 0.5bshl_{attn} + 4bdhl_{ssd}$ |

在解码阶段，模型带来的计算与内存（读 + 写）需求为：

| 模型类型 | 计算 Decode | 内存 Decode |
| --- | --- | --- |
| attention | $26bh^2l + 4bshl$ | $13h^2l + 0.5bshl$ |
| Bamba | $31bh^2l + 4bshl_{attn} + 4bdhl_{ssd}$ | $15.5h^2l + 0.5bshl_{attn} + 4bdhl_{ssd}$ |

下图对比了 Bamba 与 LLaMa 模型在预填充阶段的计算 flops 与解码阶段的内存（读+写）大小。注意，比值小于 1 才是有利的。由于推理吞吐主要受解码阶段瓶颈限制，Bamba 相对 LLaMa 在长序列（> 16K）下有 5 倍的潜在加速。当前实测（在 vLLM 上）约为 2.5 倍，我们预计不久后会进一步提升。
