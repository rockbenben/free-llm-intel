## GAIA：对 Agents 来说很硬核的基准

**什么是 agent？**

一句话：agent 是指任何基于 LLM 的系统，它可以根据当前用例的需要调用外部工具或不调用，并基于 LLM 的输出继续迭代后续步骤。工具可以是任何东西，从 Web 搜索 API 到 Python 解释器。

> 用一个视觉化的类比：所有程序都可以描述为图。先做 A，再做 B。if/else 分支是图中的叉口，但不改变图的结构。我们把 agent 定义为「LLM 输出会改变图结构」的系统。Agent 决定调用工具 A、工具 B 还是什么都不调，决定再运行一步还是停止——这些都会改变图的结构。你可以把 LLM 嵌入一个固定工作流（如 LLM 评审），那不算 agent 系统，因为 LLM 的输出不会改变图的结构。

下面用两个执行[检索增强生成](https://huggingface.co/learn/cookbook/en/rag_zephyr_langchain)的不同系统做示意：一个是经典版本，图是固定的；另一个是 agentic 版本，图中的一个循环可以按需重复。

![Classical vs Agentic RAG](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/beating_gaia/classical_vs_agentic_rag.png)

Agent 系统赋予 LLM 超能力。更多细节，阅读[我们早前关于 Transformers Agents 2.0 发布的博客](https://huggingface.co/blog/agents)。

[GAIA](https://huggingface.co/datasets/gaia-benchmark/GAIA) 是最全面的 agent 基准。GAIA 的问题非常难，凸显了基于 LLM 系统的若干难点。

来看一个刁钻的问题示例：

> Which of the fruits shown in the 2008 painting "Embroidery from Uzbekistan" were served as part of the October 1949 breakfast menu for the ocean liner that was later used as a floating prop for the film "The Last Voyage"? Give the items as a comma-separated list, ordering them in clockwise order based on their arrangement in the painting starting from the 12 o'clock position. Use the plural form of each fruit.

可以看出这个问题包含多个难点：

- 以受约束的格式作答。
- 需要多模态能力，从图像中读出水果。
- 需要收集多条信息，其中一些依赖于另一些：画中的水果；用作「The Last Voyage」浮动布景的那艘远洋客轮的身份；上述客轮 1949 年 10 月的早餐菜单。
- 以上迫使正确的求解轨迹使用多个环环相扣的步骤。

解这道题既需要高层规划能力，又需要严谨的执行——而这两点恰恰是 LLM 的短板。

因此，它是 agent 系统的绝佳测试集！

在 GAIA 的[公开排行榜](https://huggingface.co/spaces/gaia-benchmark/leaderboard)上，GPT-4-Turbo 平均分不到 7%。榜首提交（曾是）一个基于 Autogen、利用 OpenAI tool calling 函数的复杂多智能体方案，得分 40%。

## 打造合适的工具 🛠️

我们用了三个主要工具来解决 GAIA 问题：

**a. 网页浏览器**

网页浏览方面，我们主要复用了 [Autogen 团队提交方案](https://github.com/microsoft/autogen/tree/gaia_multiagent_v01_march_1st/samples/tools/autogenbench/scenarios/GAIA/Templates/Orchestrator)中的 Markdown 网页浏览器。它包含一个存储当前浏览器状态的 `Browser` 类，以及若干网页导航工具，如 `visit_page`、`page_down` 或 `find_in_page`。该工具返回当前视口的 markdown 表示。用 markdown 会大幅压缩网页信息，相比截图+视觉模型等其他方案可能导致一些遗漏。但我们发现这个工具整体表现不错，而且用起来、改起来都不复杂。

注：我们认为未来改进此工具的一个好方法是用 selenium 包而非 requests 加载页面。这样可以加载 JavaScript（很多页面没有 JS 无法正常加载），并接受 cookies 以访问某些页面。

**b. 文件检查器**

许多 GAIA 问题依赖类型多样的附件，如 `.xls`、`.mp3`、`.pdf` 等。这些文件需要正确解析。同样地，我们用了 Autogen 的工具，因为它非常好用。

非常感谢 Autogen 团队开源了他们的工作。用这些工具让我们的开发进程提前了数周！🤗

**c. 代码解释器**

我们不需要这个——因为我们的 agent 天然会生成并执行 Python 代码：详见下文。

## Code Agent 🧑‍💻

### 为什么是 Code Agent？

正如 [Wang et al. (2024)](https://huggingface.co/papers/2402.01030) 所示，让 agent 用代码表达行动，相比 JSON 这类字典式输出有多个优势。对我们来说，最主要的优势是**代码是表达复杂动作序列的一种极其优化的方式**。可以说，如果存在比现有编程语言更严谨地表达细致动作的方式，它早就成为一门新的编程语言了！

看论文中给的这个例子：

它凸显了用代码的若干优势：

- 代码动作比 JSON **简洁得多**。需要运行 4 条并行、每条 5 个连续动作的流程？用 JSON，你得生成 20 个 JSON blob，各自占一个步骤；用代码，只需 1 步。论文平均而言，Code 动作比 JSON 少 30% 的步骤，等价于生成 token 数减少 30%。由于 LLM 调用往往是 agent 系统的成本决定维度，这意味着你的 agent 运行便宜约 30%。
- 代码能复用常见库里的工具。
- 在基准上，用代码性能更好，原因有二：它是更直觉的行动表达方式；LLM 的训练数据里有大量代码，这可能让它们写代码比写 JSON 更流畅。

我们在 [agent_reasoning_benchmark](https://github.com/aymeric-roucher/agent_reasoning_benchmark) 上的实验印证了这些观点。

从构建 transformers agents 的最新实验中，我们还观察到额外的优势：

- 在代码里把元素存成具名变量容易得多。例如，需要保存某个工具生成的岩石图像稍后使用？在代码里完全没问题：`rock_image = image_generation_tool("A picture of a rock")` 会把变量存在变量字典的 `"rock_image"` 键下。之后 LLM 在任何代码 blob 里重新引用 `rock_image` 就能用到它的值。而在 JSON 里，你得做一番复杂体操来为这张图像创建一个存储名，好让 LLM 之后知道怎么再次访问。比如把所有图像生成工具的输出存成 `image_{i}.png`，然后指望 LLM 之后能理解 image_4.png 就是记忆中它前面那次工具调用的输出？还是让 LLM 额外输出一个 `output_name` 键来自选变量名，从而把你 action JSON 的结构变得更复杂？
- Agent 日志的可读性大幅提升。

### Transformers Agents 的 CodeAgent 实现

LLM 生成代码的问题在于：原样执行可能非常不安全。如果你让 LLM 在没有护栏的情况下写代码并执行，它可能幻觉出任何事：比如认为你所有个人文件都需要被《沙丘》设定的副本清除掉，或者你清唱《冰雪奇缘》主题曲的录音需要发到你的博客上！

所以对我们的 agent 来说，必须把代码执行做安全。常规做法是自顶向下：「用一个功能完整的 Python 解释器，但禁止某些操作」。

为了更安全，我们更愿意反其道而行，**从零构建一个 LLM 安全的 Python 解释器**。给定 LLM 提供的 Python 代码 blob，我们的解释器从 [ast](https://docs.python.org/3/library/ast.html) python 模块给出的代码[抽象语法树表示](https://en.wikipedia.org/wiki/Abstract_syntax_tree)出发，按树结构逐个执行树节点，遇到任何未被显式授权的操作就停下。

例如，一条 `import` 语句会先检查该 import 是否在用户定义的 `authorized_imports` 列表中被显式提及：若不在，就不执行。我们内置了一个标准 Python 函数的默认授权列表，包含 `print`、`range` 等。列表之外的一切，除非用户显式授权，否则不会被执行。例如 `open`（如 `with open("path.txt", "w") as file:`）不在授权之列。

遇到函数调用（`ast.Call`）时，如果函数名是用户定义的工具之一，就用调用的参数调用该工具。如果是此前已定义且被允许的其他函数，则正常执行。

我们还做了一些便利 LLM 使用该解释器的微调：

- 我们限制执行的总操作数，防止 LLM 生成代码中的问题导致的死循环：每步操作递增计数器，达到阈值即中断执行。
- 我们限制 print 输出的行数，避免垃圾内容淹没 LLM 的上下文长度。例如 LLM 读取了一个 100 万行的文本文件并决定逐行打印，输出到某个点会被截断，agent 的记忆不会因此爆炸。

## 基础的多智能体编排

网页浏览是信息量极大的活动，但取回的大部分内容其实并无用处。例如上面那道 GAIA 问题，唯一重要的信息是画作 "Embroidery from Uzbekistan" 的图像。它周围的一切——比如我们找到它的博客页面的内容——对整体解题通常是没用的。

为解决这个问题，使用多智能体步骤是合理的！例如，我们可以创建一个 manager agent 和一个 web 搜索 agent。manager agent 负责解决高层任务，并把具体的搜索任务指派给 web 搜索 agent。web 搜索 agent 只返回其搜索中有用的输出，manager 就不必被无用信息塞满。

我们的工作流程里正是这样构建多智能体编排的：

- 顶层 agent 是一个 [ReactCodeAgent](https://huggingface.co/docs/transformers/main/en/main_classes/agent#transformers.ReactCodeAgent)。它天生处理代码——其 action 以 Python 表达并执行。它可以访问这些工具：`file_inspector` 读取文本文件，带一个可选的 `question` 参数，用于不返回文件全部内容、只返回基于内容对该具体问题的回答；`visualizer` 专门回答关于图像的问题；`search_agent` 浏览网页。更具体地说，这个 Tool 只是对一个 Web 搜索 agent 的包装，该 agent 是一个 JSON agent（JSON 在严格顺序任务上依然好用，比如网页浏览——向下滚动、再跳转到新页面，如此循环）。而这个 agent 又能访问网页浏览工具：`informational_web_search`、`page_down`、`find_in_page`……（完整列表见[这一行](https://github.com/aymeric-roucher/GAIA/blob/a66aefc857d484a051a5eb66b49575dfaadff266/gaia.py#L107)）

把一个 agent 嵌入为工具是一种朴素的多智能体编排，但我们想看看能把它推到多远——结果发现能推得很远！

## 规划组件 🗺️

如今[已有整整一座动物园](https://arxiv.org/pdf/2402.02716)的规划策略，我们选择了一种相对简单的提前规划（plan-ahead）工作流。每 N 步生成两样东西：

- 一份事实总结：我们知道或可以从上下文推出的事实，以及需要去发现的事实
- 一份基于最新观察与上述事实总结的、如何解决该任务的分步计划

参数 N 可以为目标用例调优以获得更好性能：manager agent 我们选 N=2，web 搜索 agent 选 N=5。

一个有趣的发现是：如果不把计划的旧版本作为输入提供，分数反而上升。直觉的解释是：LLM 通常强烈偏向利用上下文中出现的任何相关信息。如果计划的旧版本在 prompt 里，LLM 很可能大量复用它，而不是重新评估方法并在需要时重新生成计划。

事实总结与计划随后都作为额外上下文用于生成下一个 action。规划之所以能帮 LLM 选择更好的轨迹，是因为它面前摆着达成目标的全部步骤和当前局势。

## 结果 🏅

[这是我们提交所用的最终代码。](https://github.com/aymeric-roucher/GAIA)

我们在验证集上得到 44.2%：这意味着 Transformers Agent 的 ReactCodeAgent 现在总排名第 1，领先第二名 4 个百分点！**在测试集上我们得到 33.3%，排名第 2，排在 Microsoft Autogen 的提交之前，并且我们在最硬核的 Level 3 问题上取得平均最高分。**

这为一个论点提供了数据支撑：[Code actions 效果更好](https://huggingface.co/papers/2402.01030)。鉴于其高效，我们相信 Code actions 不久将取代 JSON/OAI 格式，成为 agent 表达行动的标准。

据我们所知，LangChain 和 LlamaIndex 都开箱不支持 Code actions；Microsoft 的 Autogen 有一些支持（在 [docker 容器](https://github.com/microsoft/autogen/blob/57ec13c2eb1fd227a7976c62d0fd4a88bf8a1975/autogen/code_utils.py#L350)中执行代码），但看起来只是 JSON actions 的附属。所以 Transformers Agents 是唯一把这个格式放到中心位置的库！
