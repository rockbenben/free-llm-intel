# 支撑 Hugging Face 生产基础设施的三大强力告警

Jeremy Udit (jcudit)

Hugging Face 基础设施团队很高兴分享一篇"幕后花絮"，带你看 Hugging Face 生产基础设施的内部运作——我们有幸参与建设和维护它。团队专注于设计和实现健壮的监控与告警系统，这对保障平台的稳定性和可扩展性起到了关键作用。我们时刻感受到：告警直接影响我们"在潜在问题演变成重大事故之前发现并响应它"的能力。

本文将深入介绍三个强力告警，它们在支撑生产基础设施时各有各的角色，并看看它们如何帮我们维持社区依赖的高性能与高可用。

### NAT 网关高吞吐

在云计算架构中，数据在私有网络和公有网络之间流动，部署 NAT（网络地址转换）网关是久经验证的最佳实践。这个网关像一位战略性门神，监控并转发所有去往公网的出站流量。通过把出口流量集中起来，NAT 网关提供了一个全局可见性的战略制高点。我们的团队可以轻松查询和分析这些流量，在处理安全、成本优化或各种调查场景时，它是无价的资产。

成本优化是云基础设施管理的关键一环，理解定价机制尤为重要。数据中心里，定价结构通常区分东西向流量（一般是同一机架或同一楼宇内的通信）和南北向流量（与更远的私有网络或互联网的通信）。通过监控网络流量规模，Hugging Face 获得对这些流量模式的宝贵洞察，从而就基础设施配置与架构做出有依据的决策，避免产生不必要的成本。

我们的一个关键告警，是在网络流量超过预设阈值时通知我们。这个告警有多重用途：首先，它是预警系统，提醒我们注意任何可能意味着潜在问题或意外行为的异常流量峰值；其次，它促使我们定期复盘流量趋势，确保紧跟基础设施的增长与演进需求。这个告警采用静态阈值，我们随时间不断微调，保证其相关性和有效性。它触发时，往往正逢我们重构基础设施的阶段。

例如，在集成第三方安全和自动扩缩容工具时，我们观察到节点的遥测数据外发增加，触发告警，推动我们优化配置。

另一次，我们对基础设施的某项调整导致流量错误地绕过了产品专属基础设施之间的私有低成本路径（例如 Space 访问仓库数据发往 Hub 的流量）。展开讲讲：我们发现对成本影响最大的工作负载是访问对象存储的那类。对 LFS 仓库存储而言，直接拉取对象比我们 CDN 托管资源的定价更便宜，而且相比抵达我们"正门"的公网请求，也不需要 WAF 提供的同等安全措施。借助 DNS 覆写在私有网络路径和公网路径之间切换流量，已成为我们的一项宝贵技术，实现基于 [CDKTF AWS provider](https://github.com/cdktf/cdktf-provider-aws)。

```
new Route53ResolverFirewallRule(
  stack,
  `dns-override-rule-${key}-${j}`,
  {
    provider: group?.provider!,
    name: `dns-override-${dnsOverride.name}-${rule[0]}`,
    action: 'BLOCK',
    blockOverrideDnsType: 'CNAME',
    blockOverrideDomain: `${rule[1]}.`,
    blockOverrideTtl: dnsOverride.ttl,
    blockResponse: 'OVERRIDE',
    firewallDomainListId: list.id,
    firewallRuleGroupId: group!.id,
    priority: 100 + j,
  },
);
```

最后一点：虽然我们有 configuration-as-code 保证期望状态始终生效，但在其外面再加一层告警，可以在用代码表达期望状态出错时兜底。

### Hub 请求日志归档成功率

Hugging Face 的日志基础设施是一套精密系统，用于收集、处理和存储应用与服务产生的海量日志数据。系统的核心是 Hub 应用日志管道——一个架构良好的方案，确保高效捕获、富化并存储 Hub 模型使用数据，供报表和归档使用。管道起点是 [Filebeat](https://github.com/elastic/beats)，一个轻量级日志发送器，以 daemonset 形式与每个 Kubernetes 集群中的应用 pod 并排运行。Filebeat 的职责是从各种来源（包括应用容器）收集日志，并转发到管道下一站。

日志被 Filebeat 收集后发送到 [Logstash](https://github.com/elastic/logstash)——一个强大的日志处理工具。Logstash 是数据处理的劳模，对进来的日志做一系列修改与转换：用 GeoIP 数据富化日志以支持地理位置洞察、按预定义条件把日志路由到特定 Elasticsearch 索引、增删改字段格式以保证一致性和易分析性。Logstash 处理完后，日志被转发到 Elasticsearch 集群。

[Elasticsearch](https://github.com/elastic/elasticsearch)——分布式搜索与分析引擎——是我们日志存储与分析平台的核心。它接收 Logstash 的日志，并通过 Elasticsearch pipelines 应用自己的一套处理规则。这些管道只做轻量处理，比如添加表示处理时刻的时间戳字段，这对日志分析和关联至关重要。Elasticsearch 提供了可扩展、灵活的存储方案，让我们能把日志缓冲起来用于运维和实时分析。

为管理 Elasticsearch 内日志的生命周期，我们采用健壮的存储与生命周期管理策略：日志在 Elasticsearch 中保留固定周期，供运维和排障快速访问；保留期结束后，日志卸载到长期归档存储。归档过程由一个自动化工具完成——从 Elasticsearch 索引读取日志、格式化为 Parquet 文件（高效的列式存储格式）、写入对象存储系统。

日志管道的最后一站是 AWS 数据仓库服务。这里用 AWS Glue crawler 发现和分类对象存储中的数据，自动生成 Glue Data Catalog，形成统一的元数据中心。Glue 表结构定期刷新，确保跟得上日志数据结构的演进。与 AWS Glue 的集成让我们能用 Amazon Athena（无服务器交互式查询服务）查询归档日志。Athena 可以直接对对象存储里的数据跑 SQL，为日志分析和历史数据探索提供了性价比极高且可扩展的方案。

这条日志管道虽然设计考究，也有挑战和潜在故障点。最关键的脆弱点在系统的弹性，特别是 Elasticsearch 集群。作为分布式系统，Elasticsearch 在多种场景下可能遭遇背压（backpressure）：高入口流量、密集查询、或分片迁移等内部操作。背压一旦发生，可能在整个管道引发连锁问题。比如集群不堪重负时，可能开始拒绝或延迟日志写入，导致 Logstash 甚至 Filebeat 积压，最终丢日志或处理延迟。

另一个脆弱点是 Elasticsearch 的自动 schema 检测机制。它本为适应日志结构变化而生，但当应用日志字段类型发生大改动时可能失效。若 schema 检测认不出新字段类型，Logstash 写 Elasticsearch 就会失败，造成日志处理瓶颈和潜在数据不一致。这凸显了主动管理日志 schema 和健全监控的重要性——要及时发现并处理这类问题。

内存管理也是管道稳定性的关键。日志处理层（包括 Logstash 和 Filebeat）为控制成本，内存资源有限。背压发生时，这些组件——尤其在系统变慢时——容易出现 OOM（Out-of-Memory）。随着日志积压、背压升高，这些进程的内存占用不断逼近极限，不及时处置就会导致进程崩溃或进一步恶化背压。

负责把日志从 Elasticsearch 转移到对象存储的归档作业也遇到过麻烦。有时这些作业资源消耗很大，性能对节点大小和可用内存很敏感。当垃圾数据或异常巨大的日志条目穿过管道时，归档过程会吃紧，可能因内存耗尽或节点容量限制而失败。这说明要在管道更上游做数据校验和过滤，避免这类问题流到归档阶段。

为了缓解这些潜在故障，我们实现了一个独特的强力告警：校验端到端日志流。该告警**比较 Application Load Balancer（ALB）收到的请求数与成功归档的日志数**，提供整条管道日志数据流的全景视图。这让我们能快速发现任何意味着日志丢失或处理问题的差异。

告警机制基于一个简单却有效的比较：打到 ALB 的请求数（即进入系统的日志总量）对比成功归档到长期存储的日志数。监控这个比值，我们就能确保"进去的必须出来"，为日志基础设施的健康提供扎实校验。告警触发意味着可能不匹配，需要立即排查和修复。

实践中，这个告警被证明非常有用，尤其是在基础设施重构期间。例如把 ALB 迁移到 VPC origin 时，正是这个告警帮我们定位并处理了随之而来的日志流差异。它也在不那么显眼的场景里救过场：比如归档作业因意外问题未能运行，告警立刻发现归档日志缺失，让我们及时调查解决，赶在影响日志分析与保留流程之前。

这个告警虽然强大，也只是我们整体监控策略的一环。我们持续改进日志基础设施，以应对日志数据不断增长的数量和复杂度。通过主动监控、高效资源管理和对系统行为的深入理解，Hugging Face 确保日志管道保持韧性、可靠，能支撑平台的成长与演进需求。这个告警是我们对健壮、透明日志系统承诺的写照，它让各团队拿到保障 Hugging Face 平稳运行所需的洞察。

### Kubernetes API 请求错误与限流

运行云原生应用和基于 Kubernetes 的基础设施时，即使是看似微小的问题，放着不管也可能演变成重大宕机。对 Kubernetes API 尤其如此——它是 Kubernetes 集群的中枢神经，编排容器的创建、管理和网络。在 Hugging Face，我们吃过经验教训：监控 Kubernetes API 错误率和限流指标是关键实践，能防患于未然。

Hugging Face 的基础设施与 Kubernetes 深度集成，[`kube-rs`](https://github.com/kube-rs/kube) 库在高效构建和管理这一生态上居功至伟。`kube-rs` 提供了以 Rust 为中心的 Kubernetes 应用开发方式，给开发者一套熟悉而强大的工具包。其核心引入三个关键概念：reflector（反射器）、controller（控制器）和 custom resource interface（自定义资源接口）。Reflector 保证 Kubernetes 资源的实时同步，让应用能迅速响应变化。Controller 是决策者，持续调和资源的期望状态与实际状态，让 Kubernetes 自愈。自定义资源接口扩展了 Kubernetes，允许开发者定义应用专属资源以获得更好的抽象。

此外 `kube-rs` 还提供 watcher（观察者）和 finalizer（终结器）。Watcher 监视特定资源的变化，并据事件触发动作；Finalizer 通过定义自定义逻辑确保正确的清理与资源终止。通过为这些 Kubernetes 概念提供 Rust 抽象，`kube-rs` 让开发者构建健壮高效的应用，在保持 Rust 开发方式的同时发挥 Kubernetes 平台的威力与灵活性。这一集成简化了构建和管理复杂 Kubernetes 应用的流程，是 Hugging Face 基础设施中的宝贵工具。

Hugging Face 与 Kubernetes 的集成是我们基础设施的基石，`kube-rs` 在管理这一生态中扮演关键角色。`kube::api::` 模块对自动化各种任务至关重要，比如管理我们 Spaces 产品自定义域名的 HTTPS 证书。通过以程序化方式处理证书生命周期，我们保障服务的安全与可达，给用户无缝体验。此外，在面向用户功能之外，我们在日常维护中也用这个模块执行节点排空与终止，在基础设施更新期间保持集群稳定。

`kube::runtime::` 模块同样关键，让我们得以开发部署自定义控制器，增强基础设施的自动化与韧性。例如我们在托管服务中实现了账单管理控制器，通过对客户 pod 的 watcher 和 finalizer 确保资源追踪与计费的准确。这种程度的定制让我们能把 Kubernetes 调整到自身需求上。

借助 `kube-rs`，Hugging Face 在云原生应用上达成了高效率、高可靠和强控制力。库的 Rust 中心设计与我们的工程哲学一致，让我们能发挥 Rust 的优势来管理 Kubernetes 资源。通过自动化关键任务和构建自定义控制器，我们打造了可扩展、自愈的基础设施，满足用户与企业客户多样演进的需求。这一集成体现了我们的承诺：释放 Kubernetes 的全部潜力，同时保持贴合自身独特需求开发方式。

我们的基础设施很少遇到 Kubernetes API 相关问题，但我们始终保持警惕，尤其是在部署期间和之后。Kubernetes API 对我们用 `kube::runtime::` 管理客户 pod 和云网络资源至关重要。API 通信的任何中断或低效都可能对我们服务产生级联影响，导致宕机或性能下降。

监控这些 API 指标的重要性，可以从其他 Kubernetes 用户的经历得到印证。例如 OpenAI 分享过一次[状态更新](https://status.openai.com/incidents/ctrsv3lwd797)，详述 DNS 可用性问题如何导致重大宕机。虽然与 Kubernetes API 无直接关系，但他们的经历凸显了基础设施各组件的相互关联和级联故障的可能。正如 DNS 可用性对应用可达性至关重要，健康、响应迅速的 Kubernetes API 对我们管理和编排容器化负载不可或缺。

作为最佳实践，我们把这些 API 指标接入监控告警系统，确保任何异常或趋势都被及时拉到眼前。这让我们能主动出击，在影响客户之前调查处理问题。有一次，某个集群开始对 Kubernetes API 请求限流。我们追查到是一个第三方工具踩了 bug，在节点已经排空后仍反复请求排空该节点。我们得以在用户感受到明显劣化之前把这个故障任务从系统中清除。这个例子很好地说明：告警场景并不只发生在部署自定义控制器新版本之后——bug 可能需要一段时间才表现为生产问题。

总之，虽然我们的基础设施健壮、架构良好，但我们深知保持警惕和主动监控是维持其健康稳定的必要条件。紧盯 Kubernetes API 错误率和限流指标，我们在守护托管服务、保障客户体验、坚守对可靠性与性能的承诺。这印证了我们的信念：在云原生技术世界里，每个组件，无论多小，都在平台的整体韧性与成功中扮演重要角色。

### 彩蛋告警：新集群指标为零

读到这里，送一个彩蛋告警！

在 Hugging Face，实验从未停歇，为特定用途定制的集群随功能与产品迭代不断起起停停。再加上增长这个变量让熵继续增加——集群扩展到极限就会像减数分裂一样一分为二以维持平衡。要在这样动态的环境里导航，既不硬编码也不额外引入集群发现层，我们设计了一个能自适应这些变化的巧妙告警。

```
(
  (sum by (cluster) (rate(container_network_transmit_packets_total{pod="prometheus"}[1h] ) ) > 0)
or
  (-1 * (sum by (cluster) (rate(container_network_transmit_packets_total{pod="prometheus"}[1h] offset 48h) ) > 0))
) < 0
```

查询使用的指标是 **`container_network_transmit_packets_total`**，代表容器发出的报文总数。查询筛选的是每个集群本地 Prometheus 实例的指标——该实例负责指标采集以及向我们的中心指标存储 Grafana Mimir 远程写入。报文发送量近似反映了远程写入的健康度，而保证所有活跃集群的远程写入健康正是我们的目标。

查询第一部分做当前速率检查。第二部分做历史速率检查：用与当前速率相同的计算，加一个 **`offset 48h`** 子句。**`-1 *`** 用来翻转结果——这样如果历史速率大于 0，结果就小于 0。

**`or`** 把两部分合起来。满足以下任一条件查询就返回**正值（大于 0）**：

- 某集群当前报文发送速率大于 0。
- 某集群 48 小时前的历史报文发送速率大于 0。

外层 **`< 0`** 条件检查 `or` 的结果是否小于 0。这意味着只有两个条件都不满足时查询才触发——即某集群从来没发过任何指标（当前和历史速率都为 0）。

查询触发有两种情形：

- **新集群无指标**：新集群加了进来，但还没发过任何指标。此时当前和历史速率都是 0，查询触发。
- **从未发过指标的集群**：某集群存在超过 48 小时，但从未发过任何指标。此时历史速率为 0，当前速率也为 0，触发查询。

两种情形下，查询都能发现该集群没在发送指标并触发告警。

这个简单而有效的方案会在我们的指标基础设施崩溃、集群搭建中、以及集群销毁时触发，为基础设施健康提供及时洞察。它也许不是我们武器库里最关键的告警，但因为诞生于协作而格外珍贵——它是严格 code review 中团队力量的写照，离不开 Hugging Face 基础设施团队同事们专业与乐于助人的精神 🤗
