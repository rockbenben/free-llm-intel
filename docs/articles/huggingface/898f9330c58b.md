## 为什么用嵌入？

嵌入是自然语言处理中用途最广的工具之一，支撑着大量场景和用例。本质上，嵌入是把更复杂的对象（文本、图像、音频等）表示成数值向量，即对象被表示成 n 维向量。

完成这种转换之后，计算相应嵌入的相似度就能知道对象之间的相似度！这对许多用例至关重要：推荐系统、检索、one-shot 或 few-shot 学习、异常检测、相似搜索、复述检测、聚类、分类等等，背后都靠它。

### 嵌入可能难以扩展

但嵌入在生产用例中可能很难扩展，导致方案昂贵、延迟高。目前很多最先进（state-of-the-art）模型产出 1024 维的嵌入，每一维用 `float32` 编码，即每维需要 4 字节。要对 2.5 亿个向量做检索，你将需要大约 1TB 内存！

## 改善可扩展性

应对嵌入扩展挑战有几种思路。最常见的是降维，比如 [PCA](https://en.wikipedia.org/wiki/Principal_component_analysis)。但经典的降维方法（PCA 之类）[用在嵌入上表现往往不佳](https://arxiv.org/abs/2205.11498)。

最近的新事物是 [Matryoshka Representation Learning](https://arxiv.org/abs/2205.13147)（[博客](https://huggingface.co/blog/matryoshka)）（MRL，套娃表示学习），[OpenAI](https://openai.com/blog/new-embedding-models-and-api-updates) 也在用，同样能让嵌入更便宜。MRL 只使用嵌入的前 `n` 个维度。一些开源模型已经采用这个思路，如 [nomic-ai/nomic-embed-text-v1.5](https://huggingface.co/nomic-ai/nomic-embed-text-v1.5) 和 [mixedbread-ai/mxbai-embed-2d-large-v1](https://huggingface.co/mixedbread-ai/mxbai-embed-2d-large-v1)（对 OpenAI 的 `text-embedding-3-large`，压缩 12 倍仍能保留 93.1% 的性能；nomic 的模型压缩 3 倍保留 95.8%、压缩 6 倍保留 90%）。

不过还有另一条新路，它不减维度，而是压缩嵌入中每个数值本身的体积：**量化（Quantization）**。我们的量化实验会表明：可以在大幅加速计算、节省内存、存储和成本的同时，保留绝大部分性能。来看细节！

### 二进制量化

模型量化指的是降低权重精度，而嵌入量化不同——它是对嵌入本身做后处理。具体说，二进制量化是把嵌入中的 `float32` 数值转换为 1 bit 的值，带来 32 倍的内存与存储空间缩减。

要把 `float32` 嵌入二值化，只需对归一化后的嵌入以 0 为阈值截断：

检索这些二进制嵌入可以用汉明距离（Hamming Distance）高效完成：它是两个二进制嵌入中比特不同的位置数。汉明距离越小，嵌入越接近，文档越相关。汉明距离的巨大优势在于 2 个 CPU 周期就能算完，性能快得飞起。

[Yamada et al. (2021)](https://arxiv.org/abs/2106.00882) 提出了一个称为 *rerank* 的重新打分（rescore）步骤来提升性能。他们建议用 `float32` 查询嵌入与二进制文档嵌入做点积比较。实践上，先用二进制查询嵌入和二进制文档嵌入检索 `rescore_multiplier * top_k` 条结果（即双二进制检索的前 k 个结果列表），再用 `float32` 查询嵌入对这批二进制文档嵌入重新打分。

应用这个新奇的重新打分步骤后，我们能保留高达约 96% 的总检索性能，同时内存和磁盘占用缩减 32 倍、检索速度最高同样提升 32 倍。不用重新打分的话，大约能保留 92.5% 的总检索性能。

#### Sentence Transformers 中的二进制量化

把一个 1024 维的嵌入量化成二进制，得到的是 1024 个 bit。实践中按字节存比特更常见，所以量化为二进制嵌入时，我们用 `np.packbits` 把比特打包进字节。

因此，一个 1024 维的 `float32` 嵌入量化后得到一个 128 维的 `int8` 或 `uint8` 嵌入。下面给出用 [Sentence Transformers](https://sbert.net/) 生成量化嵌入的两种方式：

```
from sentence_transformers import SentenceTransformer

# 1. Load an embedding model
model = SentenceTransformer("mixedbread-ai/mxbai-embed-large-v1")

# 2a. Encode some text using "binary" quantization
binary_embeddings = model.encode(
    ["I am driving to the lake.", "It is a beautiful day."],
    precision="binary",
)
```

或者

```
from sentence_transformers import SentenceTransformer
from sentence_transformers.quantization import quantize_embeddings

# 1. Load an embedding model
model = SentenceTransformer("mixedbread-ai/mxbai-embed-large-v1")

# 2b. or, encode some text without quantization & apply quantization afterwards
embeddings = model.encode(["I am driving to the lake.", "It is a beautiful day."])
binary_embeddings = quantize_embeddings(embeddings, precision="binary")
```

### 标量（int8）量化

我们用标量量化过程把 `float32` 嵌入转换为 `int8`：把 `float32` 的连续值域映射到离散的 `int8` 取值集合（-128 到 127，共可表示 256 个级别），如下图所示。做法是使用一大批校准（calibration）嵌入数据，计算这些嵌入的范围，即每个嵌入维度的 `min` 和 `max`，再算出用于归类每个值的步长（桶）。

要进一步提升检索性能，还可以对二进制嵌入一样应用可选的重新打分步骤。需要注意，校准数据集会显著影响性能，因为它决定了量化桶的划分。

![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/embedding-quantization/scalar-quantization.png) *来源：[https://qdrant.tech/articles/scalar-quantization/](https://qdrant.tech/articles/scalar-quantization/)*

标量量化到 `int8` 是把原 `float32` 嵌入的精度降低，每个值用一个 8 bit 整数表示（小 4 倍）。注意这与二进制量化不同——那边每个值只用 1 bit（小 32 倍）。

#### Sentence Transformers 中的标量量化

把 1024 维嵌入量化成 `int8` 得到 1024 字节。实践中可以选 `uint8` 或 `int8`，通常取决于你的向量库/数据库支持哪种。

实践上，建议给标量量化提供以下三者之一：

- 一大批需要一次性量化的嵌入，或
- 每个嵌入维度的 `min` 和 `max` 范围，或
- 一大批校准嵌入，从中可以计算出 `min` 和 `max` 范围。

都不满足的话，你会收到类似这样的警告：`Computing int8 quantization buckets based on 2 embeddings. int8 quantization is more stable with 'ranges' calculated from more embeddings or a 'calibration_embeddings' that can be used to calculate the buckets.`

下面是用 [Sentence Transformers](https://sbert.net/) 生成标量量化嵌入的方式：

```
from sentence_transformers import SentenceTransformer
from sentence_transformers.quantization import quantize_embeddings
from datasets import load_dataset

# 1. Load an embedding model
model = SentenceTransformer("mixedbread-ai/mxbai-embed-large-v1")

# 2. Prepare an example calibration dataset
corpus = load_dataset("nq_open", split="train[:1000]")["question"]
calibration_embeddings = model.encode(corpus)

# 3. Encode some text without quantization & apply quantization afterwards
embeddings = model.encode(["I am driving to the lake.", "It is a beautiful day."])
int8_embeddings = quantize_embeddings(
    embeddings,
    precision="int8",
    calibration_embeddings=calibration_embeddings,
)
```

- [`quantize_embeddings`](https://sbert.net/docs/package_reference/quantization.html#sentence_transformers.quantization.quantize_embeddings)

### 二进制与标量量化组合使用

把二进制与标量量化组合起来，就能兼得两者之长：二进制嵌入的极致速度，加上标量嵌入配合重新打分的出色性能保持。见[演示](https://huggingface.co/blog/embedding-quantization#demo)——涉及 4,100 万条 Wikipedia 文本的真实实现。该方案的流水线如下：

- 查询用 [`mixedbread-ai/mxbai-embed-large-v1`](https://huggingface.co/mixedbread-ai/mxbai-embed-large-v1) SentenceTransformer 模型转为嵌入。
- 查询用 `sentence-transformers` 库的 [`quantize_embeddings`](https://sbert.net/docs/package_reference/quantization.html#sentence_transformers.quantization.quantize_embeddings) 函数量化为二进制。
- 用量化后的查询在二进制索引（4,100 万条二进制嵌入；内存/磁盘 5.2GB）中检索 top 40 文档。
- 这 top 40 文档随时从磁盘上的 int8 索引中加载（4,100 万条 int8 嵌入；内存 0 字节，磁盘 47.5GB）。
- 用 `float32` 查询和 int8 嵌入对这 top 40 文档重新打分，得到 top 10 文档。
- top 10 文档按分数排序并展示。

用这个方案，索引只需要 5.2GB 内存和 52GB 磁盘。相比常规检索所需的 200GB 内存加 200GB 磁盘，省下太多。规模越大，延迟和成本的下降就越明显。

从量化实验结果可以看出若干关键趋势和收益。不出所料，维度更高的嵌入模型每算一次存储成本更高，但性能也最好。但令人意外的是，仅量化到 `int8` 就能让 `mxbai-embed-large-v1` 和 `Cohere-embed-english-v3.0` 以更低存储占用超过维度更小的 base 模型的性能。

看二进制量化的结果时，量化的好处更加明显。此时 1024 维模型仍然胜出现在存储成本高 10 倍的 base 模型，而且 `mxbai-embed-large-v1` 在资源需求缩减 32 倍后仍保有 96% 以上的性能。对这个模型而言，从 `int8` 进一步量化到 binary 几乎没有额外损失。

有趣的是，我们也可以看到 `all-MiniLM-L6-v2` 在二进制量化下的表现反而强于 `int8`。一个可能的解释是校准数据的选择。在 `e5-base-v2` 上，我们观察到[维度坍缩](https://arxiv.org/abs/2110.09348)（dimension collapse）的影响：该模型只使用潜空间的一个子空间，做量化时整个空间进一步坍缩，导致性能大幅损失。

这说明量化并非对所有嵌入模型都通用。参考已有基准结果并亲自实验来确认某个模型是否适合量化，依然非常关键。

### 重新打分（Rescoring）的影响

这一节考察重新打分对检索性能的影响。结果基于 [mxbai-embed-large-v1](https://huggingface.co/mixedbread-ai/mxbai-embed-large-v1) 评估。

#### 二进制重新打分

二进制嵌入下，[mxbai-embed-large-v1](https://huggingface.co/mixedbread-ai/mxbai-embed-large-v1) 在 MTEB 检索上保住了 92.53% 的性能。仅加上重新打分（不多检索样本）就能把性能推到 96.45%。我们试了 `rescore_multiplier` 从 1 到 10，但没有看到性能继续提升。这说明 `top_k` 检索已经拿到了头部候选，重新打分只是把这些好候选重新排到位。

#### 标量（Int8）重新打分

我们也评估了 [mxbai-embed-large-v1](https://huggingface.co/mixedbread-ai/mxbai-embed-large-v1) 配合 `int8` 重新打分，因为 Cohere 展示了 [Cohere-embed-english-v3.0](https://txt.cohere.com/introducing-embed-v3/) 在 `int8` 量化下最高能达到 `float32` 模型 100% 的性能。这组实验里 `rescore_multiplier` 取 [1, 4, 10]，结果如下：

![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/embedding-quantization/rescoring-influence.png)

从图上可见，rescore multiplier 越高，量化后性能保持越好。根据我们的结果外推，这个关系很可能是双曲线型的：rescore multiplier 持续增大，性能趋近 100%。`int8` 下 4-5 的 rescore multiplier 就已带来高达 99% 的性能保持。

#### 检索速度

我们在 Google Cloud Platform `a2-highgpu-4g` 实例上测量检索速度，使用 1024 维的 [mxbai-embed-large-v1](https://huggingface.co/mixedbread-ai/mxbai-embed-large-v1) 嵌入跑完整的 MTEB 检索。int8 用 [USearch](https://github.com/unum-cloud/usearch)（2.9.2 版），binary 用 [Faiss](https://github.com/facebookresearch/faiss)（1.8.0 版）。全部在 CPU 上做精确检索。

| 量化方式 | 最低 | 平均 | 最高 |
| --- | --- | --- | --- |
| `float32` | 1x（基线） | **1x**（基线） | 1x（基线） |
| `int8` | 2.99x 加速 | **3.66x** 加速 | 4.8x 加速 |
| `binary` | 15.05x 加速 | **24.76x** 加速 | 45.8x 加速 |

如表所示，相比满尺寸 `float32` 嵌入，`int8` 标量量化平均加速 3.66x；二进制量化平均加速 24.76x。无论标量还是二进制，最坏情形也相当快。

### 性能总结

量化在资源占用、检索速度和检索性能上的实验结果可以总结如下：

|  | float32 | int8/uint8 | binary/ubinary |
| --- | --- | --- | --- |
| **内存与索引大小节省** | 1x | 恰好 4x | 恰好 32x |
| **检索速度** | 1x | 最高 4x | 最高 45x |
| **相对默认性能百分比** | 100% | ~99.3% | ~96% |

### 未来工作

我们期待二进制量化继续演进。举几个潜在改进方向：我们猜测标量量化还有比 `int8` 更小的空间，例如用 128 或 64 个桶代替 256 个。

另外让我们兴奋的是，嵌入量化与 Matryoshka Representation Learning（MRL）完全正交。换句话说，你可以把 MRL 嵌入例如从 1024 维缩到 128 维（通常只损失约 2% 性能），然后再施加二进制或标量量化。我们猜测这能让检索加速最高至 32x 而质量仅降约 3%，或最高 256x 而降约 10%。

最后，我们也认识到基于嵌入量化的检索还可以与独立的重排（reranker）模型结合。我们设想的三步流水线——二进制检索、标量（int8）重新打分、cross-encoder 重排——能以低延迟、低内存、低磁盘占用和低成本实现最先进的检索性能。
