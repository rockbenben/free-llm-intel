# 用 Sentence Transformers 训练与微调多向量嵌入模型

[Sentence Transformers](https://sbert.net/) 是一个用于使用和训练嵌入与重排序模型的 Python 库，服务于检索增强生成、语义搜索、语义文本相似度等广泛应用。它的 v6.0 更新引入了第四种模型类型：`MultiVectorEncoder`，支持 ColBERT 风格的后期交互（late interaction）检索，并配套一套完整的训练方法。在这篇博客里，我将演示如何用它微调一个在你的数据上超越通用检索器的多向量模型。这套方法也能从零训练出强大的新多向量模型。下文所有内容只需 `pip install -U "sentence-transformers[train]"` 即可运行。

微调多向量模型涉及多个组件：模型本身、数据集、损失函数、训练参数、评估器和 Trainer 类。我会逐个介绍这些组件，并辅以实用示例，展示如何微调出强大的多向量模型。

最后，在[评估](https://huggingface.co/blog/train-multi-vector-encoder#evaluation)一节我会展示：我微调的 [multi-vector-encoder/mLateOn-medical](https://huggingface.co/multi-vector-encoder/mLateOn-medical) 模型——在单张 RTX 3090 上训练 14.5 小时、与这篇博客同步完成——在我的医学检索评估中轻松超越我能找到的每一个通用检索模型：稠密、稀疏、词法、多向量，概莫能外。

[![NDCG@10 on MIRIAD versus active parameters: the finetuned mLateOn-medical reaches the top at a fraction of the size of the strongest general-purpose models](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/train-multi-vector-encoder/mve_medical_model_size_ndcg.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/train-multi-vector-encoder/mve_medical_model_size_ndcg.png)

如果你感兴趣的是微调稠密嵌入模型、稀疏嵌入模型或重排序模型，可以看我之前的[《训练与微调嵌入模型》](https://huggingface.co/blog/train-sentence-transformers)、[《训练与微调稀疏嵌入模型》](https://huggingface.co/blog/train-sparse-encoder)和[《训练与微调重排序模型》](https://huggingface.co/blog/train-reranker)三篇博客。

## 什么是多向量模型？

稠密嵌入模型把整段文本压缩成单个向量，相似度就是两个摘要向量的一次点积。多向量模型（也叫后期交互或 ColBERT 风格模型）跳过这一步压缩：它为**每个 token 保留一个小向量**，用 MaxSim 算子给查询与文档打分——每个查询 token 找到与其最匹配的文档 token，得分求和。token 级匹配保住了单个向量不得不平均掉的细粒度信号，通常意味着更强的检索，代价是更大的索引。

姊妹篇[《多向量嵌入模型》](https://huggingface.co/blog/multi-vector-encoder)详细讲了架构、编码、打分与索引，所以这一节我们从简，直奔训练。

[![Dense embedding versus multi-vector late interaction](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/multi-vector-encoder/maxsim_explainer.gif)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/multi-vector-encoder/maxsim_explainer.gif)

## 为什么要微调？

在特定领域上微调多向量模型能显著提升检索性能：词汇、查询风格、相关性的定义，在网页搜索、法律取证、代码搜索、科学文献综述之间都不一样。由于查询和文档是按 token 逐一匹配的，多向量模型能捕捉单向量模型往往平均掉的细粒度领域信号，而且对哪怕小规模的领域内微调数据都有非常好的响应。

除此之外，多数已发布的检索模型是为短段落配置的。经典的 ColBERT 检查点把文档截断在 180 或 300 token，许多流行的稠密模型是 256 或 512——因为它们的 MS MARCO 风格训练数据很少超过这个长度。如果你的文档很长，这些模型会在打分前悄悄丢掉文档的大部分。在我的医学评估里（段落平均 941 token），我测得这种截断最多损失 0.24 的 NDCG@10——远比任何模型架构之间的差异大。自己训练模型时，你可以按*你的*数据需要来配置文档长度。

LightOn 在代码检索上遇到了同样的情况：通用的 [LateOn](https://huggingface.co/lightonai/LateOn) 不够用，于是他们训练了 [LateOn-Code](https://huggingface.co/lightonai/LateOn-Code)。你的领域——无论是医疗、法律、金融还是公司内部文档——不会有官方模型。这篇博客教你自己动手，几个小时、一张消费级 GPU 搞定。

## 模型

多向量训练给了你一个真正的起点选择——而这个选择比你可能预期的重要得多。

### 微调现有多向量模型

如果要在一个现有多向量模型上继续微调，架构完全不用操心：

```
from sentence_transformers import MultiVectorEncoder

# Loading in fp32 is preferred for training if your memory can handle it
model = MultiVectorEncoder(
    "lightonai/mLateOn-unsupervised",
    model_kwargs={"torch_dtype": "float32"},
    processor_kwargs={"model_max_length": 8192},  # the tokenizer-level token limit
)
```

检查点自带它的配方：查询和文档标记 token、投影头、打分跳名单（skiplist）。微调时一般保留这一切，只改数据要求改的。首先检查长度配置——许多已发布检查点把文档限制在 180 到 512 token（见[为什么要微调？](https://huggingface.co/blog/train-multi-vector-encoder#why-finetune)），而我的医学段落长达 1400 token。mLateOn 家族已经能用满骨干的 8192 token 上下文，但如果你起步的检查点带着上限，把它们解开：

```
# Let the model read full documents instead of the caps it was trained with,
# e.g. GTE-ModernColBERT-v1 ships with query_length=48 and document_length=300
model[0].query_length = None
model[0].document_length = None
```

任务级上限解除后，截断行为回落到分词器的 `model_max_length`——这就是我在加载时配置该上限的原因。

我还做了另一处改动：加了一个标点跳名单，把标点 token 从文档侧打分和存储中排除。在 4 组消融（无、标点、停用词、两者）中，它以小幅优势胜出，而且免费把文档索引缩小 9.6%：

```
import string

# model[2] is the MultiVectorMask module
model[2].skiplist_words = list(string.punctuation)
model[2].resolve_with_tokenizer(model.tokenizer)  # token ids are cached, so re-resolve after changing
```

### 从基础 transformer 构建

你也可以把 `MultiVectorEncoder` 指向任意基础 transformer，它会自动为你追加一个全新的、随机初始化的 token 级投影：

```
from sentence_transformers import MultiVectorEncoder

model = MultiVectorEncoder("answerdotai/ModernBERT-base", model_kwargs={"torch_dtype": "float32"})
# MultiVectorEncoder(
#   (0): Transformer({..., 'architecture': 'ModernBertModel'})
#   (1): Dense({'in_features': 768, 'out_features': 128, 'bias': False, ...})
#   (2): MultiVectorMask({'skiplist_words': [], 'skiplist_tasks': ['document'], ...})
#   (3): Normalize({...})
# )
```

这就是经典 ColBERT 流水线：`Transformer` 产出上下文化的 token 嵌入；token 级 `Dense` 把每个嵌入投影到 128 维；`MultiVectorMask` 决定哪些 token 参与打分；token 级 `Normalize`。投影一开始是随机的，所以这个模型必须训练才有用。有趣的是，这也适用于强稠密嵌入骨干。在 [Alibaba-NLP/gte-modernbert-base](https://huggingface.co/Alibaba-NLP/gte-modernbert-base) 上装一个全新投影，仅凭投影本身加 2.5 万训练对，在我的实验里就逼近了现成检查点起点的 0.03 以内。

经典 ColBERT 的分词技巧（`[MASK]` 查询扩展、`[Q]`/`[D]` 前缀 token、文档长度上限、标点跳名单）默认全部关闭、皆可配置。完整清单见[创建自定义模型](https://sbert.net/docs/multi_vector_encoder/usage/custom_models.html)。顺便说一句，我在领域微调中用四种配置测了 `[MASK]` 查询扩展，没有一种带来可测量的差别——所以不必非得采用经典配方。

### 该选哪个起点？

写这篇博客时我直接测了这件事：取 6 个起点，在 [MIRIAD](https://huggingface.co/datasets/tomaarsen/miriad-4.4M-split) 的 2.5 万条医学"问题-段落"对上用完全相同的配方训练，然后在 1000 道留出的问题上、对 5 万段落语料做评估：

| 起点 | Zero-shot NDCG@10 | 2.5 万对之后 | 差值 |
| --- | --- | --- | --- |
| [lightonai/mLateOn-unsupervised](https://huggingface.co/lightonai/mLateOn-unsupervised) | 0.9087 | **0.9398** | **+0.0311** |
| [lightonai/mLateOn](https://huggingface.co/lightonai/mLateOn) | 0.9277 | 0.9319 | +0.0042 |
| [lightonai/LateOn-unsupervised](https://huggingface.co/lightonai/LateOn-unsupervised) | 0.9026 | **0.9206** | **+0.0180** |
| [lightonai/LateOn](https://huggingface.co/lightonai/LateOn) | 0.9185 | 0.9105 | -0.0080 |
| [lightonai/GTE-ModernColBERT-v1](https://huggingface.co/lightonai/GTE-ModernColBERT-v1) | 0.9198 | 0.9007 | -0.0191 |
| gte-modernbert-base 上新装投影 | - | 0.9177 | - |

结果让我意外，而且在两个模型家族上都得到了复现。*`-unsupervised` 检查点适应新领域的能力远胜于它们的成品兄弟，尽管起点更低却最终反超。这些检查点处在大规模对比预训练之后、通用检索监督微调之前，因此带有全部后期交互结构，却没有领域训练不得不先拆掉再重建的通用调优。相反，成品检查点几乎没动甚至倒退——在我尝试的所有学习率下都是如此。

所以，如果你看中的模型家族发布了"监督前"检查点，从那里开始。如果没有，在强检索预训练骨干上装新投影是很接近的第二选择。从一个完整成品检查点继续，是领域适配中最弱的选项——尽管它感觉上最自然。

### 数据集格式

重要的是让数据集格式与损失函数匹配（或者选一个匹配你数据格式的损失函数）。核对某数据格式是否适用于某损失函数只需两步：

- 如果损失函数按[损失总览](https://sbert.net/docs/multi_vector_encoder/loss_overview.html)表需要*标签*，那么数据集必须有**名为 "label" 或 "score" 的列**，该列会被自动作为标签。
- 所有未命名为 "label" 或 "score" 的列按[损失总览](https://sbert.net/docs/multi_vector_encoder/loss_overview.html)表被视为*输入*。剩余列数必须与你所选损失的有效输入数一致。这些列的名称**无关紧要**，**只有顺序重要**。

在此之上还有两条多向量专属约定：

- 按位置分配查询与文档：第一列作为*查询*嵌入，其后所有列作为*文档*，与列名无关。该默认行为可通过标准的 `router_mapping` 训练参数按列覆盖。
- 知识蒸馏格式：每个候选文档一列，即 `(query, document_1, ..., document_N, scores)`，其中 `scores` 是每行 N 个教师分数构成的列表。对于把查询和文档 *ID* 与独立文本数据集分开存放的 KD 数据集（如 [lightonai/ms-marco-en-bge](https://huggingface.co/datasets/lightonai/ms-marco-en-bge)），可用 [`resolve_ids`](https://sbert.net/docs/package_reference/util.html#sentence_transformers.util.dataset.resolve_ids) 在线把 ID 解析为文本。

## 损失函数

损失函数量化模型在给定数据批次上的表现，让优化器可以更新模型权重以获得更理想（即更低）的损失值。适合你任务的损失函数取决于你手上的数据和目标。完整选项见[损失总览](https://sbert.net/docs/multi_vector_encoder/loss_overview.html)。

对常见的"问题-答案"或"问题-段落"对，主力方案是带批内负样本（in-batch negatives）训练的 [`MultiVectorMultipleNegativesRankingLoss`](https://sbert.net/docs/package_reference/multi_vector_encoder/losses.html#multivectormultiplenegativesrankingloss)：batch 里其他每个文档都充当每个查询的负样本。batch 越大负样本越多、训练越强，所以实践中要用它的 GradCache 变体 [`CachedMultiVectorMultipleNegativesRankingLoss`](https://sbert.net/docs/package_reference/multi_vector_encoder/losses.html#cachedmultivectormultiplenegativesrankingloss)——它把有效批量与 GPU 装得下的批量解耦：

```
from sentence_transformers import MultiVectorEncoder
from sentence_transformers.multi_vector_encoder.losses import CachedMultiVectorMultipleNegativesRankingLoss

model = MultiVectorEncoder("lightonai/mLateOn-unsupervised", model_kwargs={"torch_dtype": "float32"})

loss = CachedMultiVectorMultipleNegativesRankingLoss(
    model=model,
    mini_batch_size=16,  # how many documents to encode per chunk: bounds memory, not quality
)
```

`mini_batch_size` 通过按该大小分块编码文档来约束内存，而有效的对比批量（我下面这次运行是 128；消融实验表明更大批量也无增益）仍然是自由选择。GradCache 保证无论分块大小结果都相同，所以显存小的 GPU 可以放心调低它，只损失一点墙钟时间。当文档长度差异很大时，考虑它的姊妹参数 `mini_batch_num_tokens`：把每块打包到总 token 预算而非文档数，异常长的文档永远不会让某块冲爆内存（我"每文档约 940 token、mini_batch_size=16"大致相当于 `mini_batch_num_tokens=15_000`）。

多向量的一个专属陷阱：对比损失的默认值是 `scale=1.0`，而稠密嵌入的对应值是 `scale=20.0`。20.0 的存在是因为余弦相似度是 [-1, 1] 内的单个值——对尖锐的 softmax 来说范围太窄。而 MaxSim 分数把每个查询 token 的最佳匹配相似度求和，天然跨度约 [0, query_length]：32 token 的查询最高可到 32。所以不要把 `scale=20.0` 从稠密训练脚本里抄过来——那会让 softmax 饱和、梯度消失。

想从更强的教师模型做蒸馏（最强的通用后期交互模型正是这样训练的），见 [`MultiVectorDistillKLDivLoss`](https://sbert.net/docs/package_reference/multi_vector_encoder/losses.html#multivectordistillkldivloss) 和[训练总览](https://sbert.net/docs/multi_vector_encoder/training_overview.html#trainer)文档中的 Knowledge Distillation 标签页。

## 训练参数

用 [`MultiVectorEncoderTrainingArguments`](https://sbert.net/docs/package_reference/multi_vector_encoder/training_args.html) 类自定义训练过程。该类可以调整影响训练速度的参数，并帮你理解训练中发生了什么。

关于最有用的训练参数，请查阅 [Multi-Vector Encoder > Training Overview > Training Arguments](https://sbert.net/docs/multi_vector_encoder/training_overview.html#training-arguments)。值得通读，以便榨干你的训练。

一个示例，用的就是我真实训练运行的取值：

```
from sentence_transformers import MultiVectorEncoderTrainingArguments
from sentence_transformers.base.sampler import BatchSamplers

args = MultiVectorEncoderTrainingArguments(
    # Required parameter:
    output_dir="models/mLateOn-medical",
    # Optional training parameters:
    num_train_epochs=1,
    per_device_train_batch_size=128,  # the effective contrastive batch, thanks to GradCache
    per_device_eval_batch_size=16,
    learning_rate=1e-4,
    warmup_steps=0.05,
    prompts={"question": "[Q] ", "passage_text": "[D] "},  # the checkpoint's markers, keyed by training column
    fp16=False,  # Set to True if you have a GPU that supports FP16
    bf16=True,  # Set to True if you have a GPU that supports BF16
    batch_sampler=BatchSamplers.NO_DUPLICATES,  # in-batch negatives benefit from no duplicates
    # Optional tracking/debugging parameters:
    eval_strategy="steps",
    eval_steps=0.1,
    save_strategy="steps",
    save_steps=0.05,
    logging_steps=0.01,
    run_name="mLateOn-medical",  # Will be used in e.g. Trackio, W&B, etc.
)
```

有几点值得说明：

- `prompts`：训练不会自动应用模型里存的提示词，所以要显式映射到训练列上。这里把检查点的 `[Q] ` 标记配给 question 列、`[D] ` 配给 passage 列，保持训练与推理一致。
- `max_length`（故意没设）：这个参数只在*训练时*给分词设上限，适合你希望训练比模型完整服务长度更省钱的场合。我在这份数据上量过这个捷径的代价：512 token 训练大约损失 0.015 NDCG@10、换来约 2 倍速度——而且数据越多亏空也不会缩小，因为模型根本没见过被切掉的部分。除非速度比质量更重要，否则别设它，让训练与推理一致。
- `learning_rate=1e-4`：在 5e-6 到 2e-4 的扫描后，这个高于常规的数值效果最好。

## 评估器

要跟踪模型训练中的表现，可以给 trainer 传 `eval_dataset` 得到评估损失，但具体的检索指标信息量大得多。Sentence Transformers 为多向量模型内置了这些评估器：

| 评估器 | 所需数据 |
| --- | --- |
| [`MultiVectorInformationRetrievalEvaluator`](https://sbert.net/docs/package_reference/multi_vector_encoder/evaluation.html#multivectorinformationretrievalevaluator) | 查询、语料库和相关文档映射 |
| [`MultiVectorNanoBEIREvaluator`](https://sbert.net/docs/package_reference/multi_vector_encoder/evaluation.html#multivectornanobeirevaluator) | 无需数据 |
| [`MultiVectorTripletEvaluator`](https://sbert.net/docs/package_reference/multi_vector_encoder/evaluation.html#multivectortripletevaluator) | (anchor, positive, negative) 三元组 |
| [`MultiVectorRerankingEvaluator`](https://sbert.net/docs/package_reference/multi_vector_encoder/evaluation.html#multivectorrerankingevaluator) | `{'query': '...', 'positive': [...], 'negative': [...]}` 字典列表 |
| [`MultiVectorDistillationEvaluator`](https://sbert.net/docs/package_reference/multi_vector_encoder/evaluation.html#multivectordistillationevaluator) | 查询加候选文档与教师分数 |

对领域微调，用你自己留出数据构建的 [`MultiVectorInformationRetrievalEvaluator`](https://sbert.net/docs/package_reference/multi_vector_encoder/evaluation.html#multivectorinformationretrievalevaluator) 才是关键。构建时的一个提示：语料要足够难，才能区分模型高下。就我而言，MIRIAD 的问题由其源段落生成，检索异常容易——只在 1 万条金段落上，几乎所有模型的 NDCG@10 都超过 0.97。如果你的评估也饱和成这样，就往里加*干扰*段落（我用训练划分里去重后的段落），直到分数拉开：

```
from datasets import load_dataset
from sentence_transformers.multi_vector_encoder.evaluation import MultiVectorInformationRetrievalEvaluator

dataset = load_dataset("tomaarsen/miriad-4.4M-split")

# Gold: 1,000 evaluation questions, each mapping to its own passage, with the
# eval split's full ~10k unique passages as the initial corpus
corpus = {}
queries = {}
relevant_docs = {}
passage_to_id = {}
for idx, row in enumerate(dataset["eval"]):
    if row["passage_text"] not in passage_to_id:
        passage_to_id[row["passage_text"]] = f"p{len(passage_to_id)}"
        corpus[passage_to_id[row["passage_text"]]] = row["passage_text"]
    if idx < 1_000:
        queries[f"q{idx}"] = row["question"]
        relevant_docs[f"q{idx}"] = {passage_to_id[row["passage_text"]]}

# Distractors: unique train passages that make the haystack realistic
seen = set(passage_to_id)
for row in dataset["train"]:
    if len(corpus) >= 200_000:
        break
    if row["passage_text"] not in seen:
        seen.add(row["passage_text"])
        corpus[f"d{len(corpus)}"] = row["passage_text"]

evaluator = MultiVectorInformationRetrievalEvaluator(
    queries=queries,
    corpus=corpus,
    relevant_docs=relevant_docs,
    name="miriad-dev",
    batch_size=16,
)
# results = evaluator(model)
```

## Trainer

[`MultiVectorEncoderTrainer`](https://sbert.net/docs/package_reference/multi_vector_encoder/trainer.html) 是所有组件汇合的地方。下面是训练出 [multi-vector-encoder/mLateOn-medical](https://huggingface.co/multi-vector-encoder/mLateOn-medical)——引言里那个模型——的完整脚本：

```
import logging
import string
import traceback

from datasets import load_dataset

from sentence_transformers import (
    MultiVectorEncoder,
    MultiVectorEncoderModelCardData,
    MultiVectorEncoderTrainer,
    MultiVectorEncoderTrainingArguments,
)
from sentence_transformers.base.sampler import BatchSamplers
from sentence_transformers.multi_vector_encoder.evaluation import MultiVectorInformationRetrievalEvaluator
from sentence_transformers.multi_vector_encoder.losses import CachedMultiVectorMultipleNegativesRankingLoss

logging.basicConfig(format="%(asctime)s - %(message)s", datefmt="%Y-%m-%d %H:%M:%S", level=logging.INFO)


def main():
    # 1. Load the starting checkpoint: contrastively pretrained, not yet supervised
    # Loading in fp32 is preferred for training if your memory can handle it
    model = MultiVectorEncoder(
        "lightonai/mLateOn-unsupervised",
        model_kwargs={"torch_dtype": "float32"},
        processor_kwargs={"model_max_length": 8192},
        model_card_data=MultiVectorEncoderModelCardData(
            language="en",
            license="apache-2.0",
            model_name="mLateOn finetuned on MIRIAD medical retrieval",
        ),
    )

    # 2. Lift the per-task length caps so training and inference see full medical passages
    model[0].query_length = None
    model[0].document_length = None

    # 3. Skip punctuation tokens during scoring: a small quality win and a 9.6% smaller index
    model[2].skiplist_words = list(string.punctuation)
    model[2].resolve_with_tokenizer(model.tokenizer)

    # 4. Load 1 million medical question-passage pairs
    train_dataset = load_dataset("tomaarsen/miriad-4.4M-split", split="train").select(range(1_000_000))

    # 5. In-batch negatives with GradCache: large effective batch, memory-bounded chunks
    loss = CachedMultiVectorMultipleNegativesRankingLoss(model=model, mini_batch_size=16)

    # 6. A light dev evaluator to watch progress during training: 500 held-out questions
    # against the eval split's ~10k unique passages. The full 200k protocol runs afterwards.
    eval_split = load_dataset("tomaarsen/miriad-4.4M-split", split="eval")
    corpus, queries, relevant_docs, passage_to_id = {}, {}, {}, {}
    for idx, row in enumerate(eval_split):
        if row["passage_text"] not in passage_to_id:
            passage_to_id[row["passage_text"]] = f"p{len(passage_to_id)}"
            corpus[passage_to_id[row["passage_text"]]] = row["passage_text"]
        if idx < 500:
            queries[f"q{idx}"] = row["question"]
            relevant_docs[f"q{idx}"] = {passage_to_id[row["passage_text"]]}
    dev_evaluator = MultiVectorInformationRetrievalEvaluator(
        queries=queries, corpus=corpus, relevant_docs=relevant_docs, name="miriad-dev", batch_size=16
    )

    # 7. Training arguments, as discussed above
    run_name = "mLateOn-medical"
    args = MultiVectorEncoderTrainingArguments(
        output_dir=f"models/{run_name}",
        num_train_epochs=1,
        per_device_train_batch_size=128,
        per_device_eval_batch_size=16,
        learning_rate=1e-4,
        warmup_steps=0.05,
        prompts={"question": "[Q] ", "passage_text": "[D] "},
        fp16=False,  # Set to True if you have a GPU that supports FP16
        bf16=True,  # Set to True if you have a GPU that supports BF16
        batch_sampler=BatchSamplers.NO_DUPLICATES,
        eval_strategy="steps",
        eval_steps=0.1,
        save_strategy="steps",
        save_steps=0.05,
        logging_steps=0.01,
        run_name=run_name,
    )

    # 8. Create a trainer & train
    trainer = MultiVectorEncoderTrainer(
        model=model,
        args=args,
        train_dataset=train_dataset,
        loss=loss,
        evaluator=dev_evaluator,
    )
    trainer.train()

    # 9. Save the trained model
    model.save_pretrained(f"models/{run_name}/final")

    # 10. (Optional) Push it to the Hugging Face Hub
    try:
        model.push_to_hub(run_name)
    except Exception:
        logging.error(f"Error uploading model to the Hugging Face Hub:\n{traceback.format_exc()}")


if __name__ == "__main__":
    main()
```

这就是完整配方：一个"监督前"检查点、百万领域数据对、批内负样本、完整文档长度，加上高于常规的学习率。这次训练在我单张 RTX 3090 上耗时 14.5 小时，峰值显存 17.5 GB——而上面每个选择都是实测对比的胜出者，不是拍脑袋。

预算更紧的读者可以参考：我的扩展实验显示 10 万数据对（75 分钟训练）与百万对全程训练只差 0.012 NDCG@10。大部分收益在第一个小时就到手了。

### 回调

MultiVectorEncoder 的 trainer 支持各种 [`transformers.TrainerCallback`](https://huggingface.co/docs/transformers/main_classes/callback#transformers.TrainerCallback) 子类，包括：

- [`WandbCallback`](https://huggingface.co/docs/transformers/en/main_classes/callback#transformers.integrations.WandbCallback)：若安装了 `wandb`，把训练指标记录到 W&B
- [`TensorBoardCallback`](https://huggingface.co/docs/transformers/en/main_classes/callback#transformers.integrations.TensorBoardCallback)：若 `tensorboard` 可用，把训练指标记录到 TensorBoard
- [`CodeCarbonCallback`](https://huggingface.co/docs/transformers/en/main_classes/callback#transformers.integrations.CodeCarbonCallback)：若安装了 `codecarbon`，跟踪训练期间的碳排放

通过 `report_to` 训练参数启用，例如在装好依赖后 `report_to=["wandb", "codecarbon"]`。默认值是 `"none"`；`report_to="all"` 会激活所有依赖已安装的平台。

关于这些回调及如何编写自定义回调，参见 [Transformers 回调文档](https://huggingface.co/docs/transformers/en/main_classes/callback)。

### 多数据集训练

通常，顶级通用模型是在多个数据集上同时训练的。但由于各数据集格式不一，这条路并不好走。好在 [`MultiVectorEncoderTrainer`](https://sbert.net/docs/package_reference/multi_vector_encoder/trainer.html) 允许你在多个数据集上训练而不要求统一格式，还能给不同数据集施加不同损失函数。多数据集训练步骤：

- 把 `train_dataset`（以及可选的 `eval_dataset`）设为 [`datasets.Dataset`](https://huggingface.co/docs/datasets/main/en/package_reference/main_classes#datasets.Dataset) 实例的字典（或 [`datasets.DatasetDict`](https://huggingface.co/docs/datasets/main/en/package_reference/main_classes#datasets.DatasetDict)）。
- （可选）把损失函数做成"数据集名 → 损失"的字典。只有当你想给不同数据集用不同损失时才需要。

每个训练/评估 batch 只会包含来自单一数据集的样本。从多个数据集采样 batch 的顺序由 [`MultiDatasetBatchSamplers`](https://sbert.net/docs/package_reference/sentence_transformer/sampler.html#sentence_transformers.training_args.MultiDatasetBatchSamplers) 枚举定义，通过 `multi_dataset_batch_sampler` 传给 [`MultiVectorEncoderTrainingArguments`](https://sbert.net/docs/package_reference/multi_vector_encoder/training_args.html)。可选值：

- `MultiDatasetBatchSamplers.ROUND_ROBIN`：各数据集轮转采样，直到某一方耗尽。这种策略下每个数据集被等概率采样，但很可能用不完每个数据集的全部样本。
- `MultiDatasetBatchSamplers.PROPORTIONAL`（默认）：按数据集大小比例采样。每个数据集的全部样本都会被用到，更大的数据集被采样得更频繁。

## 评估

架构层面的规律同样清晰：榜单头部清一色是后期交互。在长文档上，每 token 一个向量胜过每文档一个向量——即便训练数据和骨干相同。DenseOn 和 LateOn 共享训练数据与架构，只有头部不同，后期交互的兄弟高出 +0.12；多语言对（mDenseOn 和 mLateOn）以 +0.13 复现了这一点。堆规模也救不了单向量：[Qwen3-Embedding-4B](https://huggingface.co/Qwen/Qwen3-Embedding-4B) 是最强的稠密模型、激活（非 embedding）参数约为我的 33 倍，仍差 0.13；8B 版本反而比 4B 更低。

### 优化索引

对多向量检索最公平的质疑是索引大小，而这个领域几乎是最坏情况。每 token 存一个向量，我的模型每条段落要存约 878 个向量，20 万段落的语料在 fp16 下约需 45 GB——稠密模型则远不到 1 GB。正是文档长度拉开了这个差距。[姊妹篇](https://huggingface.co/blog/multi-vector-encoder)中 Natural Questions 的段落平均只有约 125 个 token 向量，少 7 倍，短段落语料起步就小得多。[`HierarchicalTokenPooling`](https://sbert.net/docs/package_reference/multi_vector_encoder/modules.html#hierarchicaltokenpooling) 模块正是为此压缩而生：对每个文档的 token 嵌入做聚类、存簇均值，大致保留 `1 / pool_factor` 的向量：

```
from sentence_transformers.multi_vector_encoder.modules import HierarchicalTokenPooling

pooling = HierarchicalTokenPooling(pool_factor=4)
document_embeddings = model.encode_document(passages, token_pooling=pooling)
```

我是在训练完成后的模型上做的事后测量，没有配合池化训练——而在长文档上，它的代价低得惊人。

[![Embedding size for the 200,000-passage corpus versus NDCG@10, with the token pooling trajectory sweeping the multi-vector index into dense-model territory](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/train-multi-vector-encoder/mve_medical_index_size_ndcg.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/train-multi-vector-encoder/mve_medical_index_size_ndcg.png)

实线圆点是未压缩的嵌入——这样每个家族的计算方式一致、都用精确搜索打分。但实际你不会按那样部署任何一种：稠密索引惯用 int8 或二值量化加重打分，稀疏索引会压缩 postings，多向量索引则用 PLAID 风格的残差压缩。别把实线点理解成你要买的磁盘容量，它们只是相对存储成本。

Token pooling 是那条实线。向量数减半只花 0.0033 NDCG@10、rank-1 准确率纹丝不动；只保留四分之一（11.2 GB）仍有 0.8991。曲线还在往下走（我测到十分之一的向量，仍有 0.8765），但一旦量化进入选项，就没必要把池化推那么远——这正是下面那条虚线的事。

虚线展示的是真实部署的可能样子。我提前把模型和基准给了 Omar Khattab，他用 [fast-plaid](https://github.com/lightonai/fast-plaid) 在 1-bit 残差量化下测了这些配置：用紧凑的 17-bit 簇心 ID 和 18-bit 文档 ID 替代通常的 64-bit 未打包整数，并加上文档侧剪枝：

| 配置 | 保留向量 | 索引 | NDCG@10 |
| --- | --- | --- | --- |
| 1-bit PLAID，全部向量 | 100% | 3.37 GB | 0.8984 |
| 1-bit PLAID + 剪枝 | 65% | 2.23 GB | 0.8830 |
| 1-bit PLAID + 剪枝 | 42% | 1.45 GB | 0.8642 |

第一行比原始嵌入小 13 倍，代价只有 0.0155 NDCG@10——比池化曲线上任何点都划算。量化缩小每个向量，池化和剪枝削减向量数量，两者可以叠加——而量化该是首选。继续推进，最后一行落在 1.45 GB，*比* [Qwen3-Embedding-8B](https://huggingface.co/Qwen/Qwen3-Embedding-8B) 的 fp16 嵌入（1.64 GB）还小，分数却高出 0.0895。"多向量索引太大"这个反对意见，在一个配置得当的索引面前站不住脚。

这里的剪枝很粗糙，只为确立"token 削减可以在量化之上再叠加"，所以把最后两行当作下限而不是前沿来读。如果你完全不想手动调量化，姊妹篇的[索引](https://huggingface.co/blog/multi-vector-encoder#indexing)一节介绍了 fast-plaid、Qdrant、Weaviate 和 Vespa。

多向量检索的开销只取决于它的索引。这份语料的原始嵌入是 45 GB，而配置得当的索引至少小 7 倍、精度几乎不变。索引值得你花和检查点一样多的心思。
