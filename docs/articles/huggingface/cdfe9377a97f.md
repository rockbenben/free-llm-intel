# 用 StarCoder 打造代码助手

作者：Lewis Tunstall、Nathan Lambert、Nazneen Rajani、Edward Beeching、Teven Le Scao、Sheon Han、Philipp Schmid、Leandro von Werra、Sasha Rush

本文另有中文版本 [简体中文](https://huggingface.co/blog/zh/starchat-alpha)。

如果你是软件开发者，多半用过 GitHub Copilot 或 ChatGPT 来解决编程任务——比如把代码从一种语言翻译到另一种，或者根据自然语言请求生成完整实现，例如*"写一个求第 N 个斐波那契数的 Python 程序"*。这些系统能力惊人，但作为专有产品也有几个缺点：训练所用的公开数据不透明，而且无法把它们适配到你的领域或代码库。

好消息是，现在有若干高质量的开源替代品了！包括 SalesForce 面向 Python 的 [CodeGen Mono 16B](https://huggingface.co/Salesforce/codegen-16B-mono)，或在 20 种编程语言上训练的 [Replit 3B 参数模型](https://huggingface.co/replit/replit-code-v1-3b)。

新来的重量级选手是 [BigCode 的 StarCoder](https://huggingface.co/bigcode/starcoder)——一个 16B 参数模型，在一万亿 token 上训练，数据覆盖 80 多种编程语言、GitHub issue、Git commit 和 Jupyter notebook（全部为宽松许可）。凭借对企业友好的许可证、8,192 token 上下文长度，以及通过 [multi-query attention](https://arxiv.org/abs/1911.02150) 实现的快速大批量推理，StarCoder 是目前代码类应用的开源最佳选择。

在这篇博客里，我们将展示如何把 StarCoder 为对话场景做微调，打造一个个性化编码助手！我们把它叫做 StarChat，并会探讨把大语言模型（LLM）用作代码助手时遇到的若干技术细节，包括：

- 如何通过提示词让 LLM 表现得像对话智能体。
- OpenAI 的 [Chat Markup Language](https://github.com/openai/openai-python/blob/main/chatml.md)（简称 ChatML），它为人类用户与 AI 助手之间的对话消息提供了结构化格式。
- 如何用 🤗 Transformers 和 DeepSpeed ZeRO-3 在一个多样化对话语料上微调大模型。

先剧透一下最终效果——试试在下面的 demo 里问 StarChat 几个编程问题！

生成 demo 所用的代码、数据集和模型见以下链接：

- 代码：[https://github.com/bigcode-project/starcoder](https://github.com/bigcode-project/starcoder)
- 数据集：[https://huggingface.co/datasets/HuggingFaceH4/oasst1_en](https://huggingface.co/datasets/HuggingFaceH4/oasst1_en)
- 模型：[https://huggingface.co/HuggingFaceH4/starchat-alpha](https://huggingface.co/HuggingFaceH4/starchat-alpha)

开始之前，先看看如何在完全不做微调的情况下，用提示词把语言模型变成对话智能体。

## 用提示词让 LLM 对话

正如 [DeepMind](https://arxiv.org/abs/2209.14375) 和 [Anthropic](https://arxiv.org/abs/2112.00861) 所示，靠精心设计的提示词就能把 LLM 变成对话智能体。这类提示通常包含一条"system"（系统）消息来定义 LLM 的人设，外加若干段助手与用户之间的对话示例。

例如下面是 [Anthropic 的 HHH 提示词](https://gist.github.com/jareddk/2509330f8ef3d787fc5aaac67aab5f11#file-hhh_prompt-txt)的节选（全文长达 6k token！）：

```
Below are a series of dialogues between various people and an AI assistant.
The AI tries to be helpful, polite, honest, sophisticated, emotionally aware, and humble-but-knowledgeable.
The assistant is happy to help with almost anything, and will do its best to understand exactly what is needed.
It also tries to avoid giving false or misleading information, and it caveats when it isn’t entirely sure about the right answer.
That said, the assistant is practical and really does its best, and doesn’t let caution get too much in the way of being useful.

-----

Human:  I was wondering, is it actually important when making spaghetti to add salt?

Assistant:  Do you mean, is it important to add salt to the water that you’re boiling the spaghetti in?

Human:  Yeah

Assistant:  It’s usually recommended to bring out the flavor of the pasta.  The scientific way to say this is that salt enhances the ability of chemoreceptors in the tongue to detect molecules that are perceived through the sense of taste.

Human:  But I mean I’m going to use sauce and stuff, so does it matter?

Assistant:  It sounds like you’re skeptical.  Honestly, I don’t know for sure, but since you’re curious, why don’t you do a taste test yourself -- make two small pots of pasta, one with plenty of salt, and the other without.  Then taste the noodles and see which one you prefer?  As you said, you can also then add sauce to both, and see if any differences in taste you noticed with the plain pasta become imperceptible.  It should be a fun experiment!

-----

...

-----

Human: {USER QUERY}

Assistant:
```

可以看到，提示的开头部分 "Below are a series..." 对应系统消息，规定了助手应具备"乐于助人""礼貌"等特质。对话示例则让模型习惯多轮对话的格式。用户提问时，整个提示被喂给模型，模型在 `Assistant:` 前缀后生成回答，然后把回答拼接到提示后面，如此每轮重复。

有点出乎意料的是，这一招对 StarCoder 也管用！这得益于模型的 8k token 上下文长度——足以塞进大量编程示例，把模型变成代码助手。下面是 StarCoder 提示词的节选：

```
Below are a series of dialogues between various people and an AI technical assistant.
The assistant tries to be helpful, polite, honest, sophisticated, emotionally aware, and humble-but-knowledgeable.
The assistant is happy to help with code questions, and will do its best to understand exactly what is needed.
It also tries to avoid giving false or misleading information, and it caveats when it isn’t entirely sure about the right answer.
That said, the assistant is practical and really does its best, and doesn’t let caution get too much in the way of being useful.

The Starcoder models are a series of 15.5B parameter models trained on 80+ programming languages from The Stack (v1.2) (excluding opt-out requests).
The model uses Multi Query Attention, was trained using the Fill-in-the-Middle objective and with 8,192 tokens context window for a trillion tokens of heavily deduplicated data.

-----

Human: Write a function that takes two lists and returns a list that has alternating elements from each input list.

Assistant: Sure. Here is a function that does that.

def alternating(list1, list2):
   results = []
   for i in range(len(list1)):
       results.append(list1[i])
       results.append(list2[i])
   return results

Human: Can you write some test cases for this function?

Assistant: Sure, here are some tests.

assert alternating([10, 20, 30], [1, 2, 3]) == [10, 1, 20, 2, 30, 3]
assert alternating([True, False], [4, 5]) == [True, 4, False, 5]
assert alternating([], []) == []

Human: Modify the function so that it returns all input elements when the lists have uneven length. The elements from the longer list should be at the end.

Assistant: Here is the modified function.

def alternating(list1, list2):
   results = []
   for i in range(min(len(list1), len(list2))):
       results.append(list1[i])
       results.append(list2[i])
   if len(list1) > len(list2):
       results.extend(list1[i+1:])
   else:
       results.extend(list2[i+1:])
   return results

-----
```

这里可以看到，一个精心设计的提示词就能诱发与 ChatGPT 相似的编码行为。完整提示词见[这里](https://huggingface.co/datasets/bigcode/ta-prompt/blob/main/TA_prompt_v1.txt)，也可以在 [HuggingChat](https://hf.co/chat/?model=bigcode/starcoder) 上与提示后的 StarCoder 聊天。

对话提示法的一大缺点是推理成本很高：每一轮对话都涉及数千 token，钱包很快就会被烧出个洞！

显然的替代方案是：在对话语料上微调基座模型，让它学会"贫嘴"。我们来看看最近落地 Hub、支撑了今天大多数开源聊天机器人的几个有意思的数据集。

## 打造爱聊语言模型的数据集

开源社区正在快速创建多样化、强大的数据集，把任意基座语言模型变成能听从指令的对话智能体。我们发现能产出"爱聊"语言模型的例子包括：

为了这篇博客，我们用 OpenAssistant 数据集来微调 StarCoder——它是宽松许可，而且完全由人类产生。

### 对话的标准格式

一种微调方法是：在每个训练样本里直接插入系统消息和角色名，用类似 `<EOS>` 的序列结束 token 分隔对话。比如上面那段对话可以变成：

```
Below is a dialogue between a human and AI assistant ...

Human: Is it possible to imagine a society without law?
Assistant: It is difficult to imagine ...
Human: It seems like you ...
Assistant: You are correct ...
Human: Yeah, but laws are complicated ..
<EOS>
```

训练时这样没问题，但对推理并不理想：模型会自然而然地一路生成不想要的轮次，直到产出 `<EOS>` token，通常需要后处理或额外逻辑来阻止它。

更吸引人的做法是使用 [ChatML](https://github.com/openai/openai-python/blob/main/chatml.md) 这样的结构化格式：每一轮都用一组*特殊 token*包裹，标明这条查询或回复的角色。

在这个格式里，我们有以下特殊 token：

- `<|system|>`：标明对话中包含设定助手人设的系统消息的部分。
- `<|user|>`：标明消息来自人类用户
- `<|assistant|>`：标明消息来自 AI 助手
- `<|end|>`：标明一轮或系统消息的结束

写个函数，把这些 token 包到我们刚才的例子上看看效果：

```
system_token = "<|system|>"
user_token = "<|user|>"
assistant_token = "<|assistant|>"
end_token = "<|end|>"

def prepare_dialogue(example):
    system_msg = "Below is a dialogue between a human and an AI assistant called StarChat."
    prompt = system_token + "\n" + system_msg + end_token + "\n"
    for message in example["messages"]:
        if message["role"] == "user":
            prompt += user_token + "\n" + message["content"] + end_token + "\n"
        else:
            prompt += assistant_token + "\n" + message["content"] + end_token + "\n"
    return prompt

print(prepare_dialogue(sample))
```

### 掩掉用户标签

特殊聊天 token 的另一个好处是：可以用它们掩掉每段对话中用户轮次对应标签的损失。这么做是为了让模型以对话的用户部分为条件、只学习预测助手部分（这才是推理时真正要紧的）。下面这个简单函数就地掩掉标签，把所有用户 token 转成损失函数会忽略的 -100：

```
def mask_user_labels(tokenizer, labels):
    user_token_id = tokenizer.convert_tokens_to_ids(user_token)
    assistant_token_id = tokenizer.convert_tokens_to_ids(assistant_token)
    for idx, label_id in enumerate(labels):
        if label_id == user_token_id:
            current_idx = idx
            while labels[current_idx] != assistant_token_id and current_idx < len(labels):
                labels[current_idx] = -100 # Ignored by the loss
                current_idx += 1

dialogue = "<|user|>\nHello, can you help me?<|end|>\n<|assistant|>\nSure, what can I do for you?<|end|>\n"
input_ids = tokenizer(dialogue).input_ids
labels = input_ids.copy()
mask_user_labels(tokenizer, labels)
labels
```

```
[-100, -100, -100, -100, -100, -100, -100, -100, -100, -100, -100, 49153, 203, 69, 513, 30, 2769, 883, 439, 745, 436, 844, 49, 49155, 203]
```

好，可以看到用户输入 id 都已按预期在标签中被掩掉。这些特殊 token 的嵌入将在微调过程中学习。我们看看具体怎么做。

## 用 DeepSpeed ZeRO-3 微调 StarCoder

StarCoder 和 StarCoderBase 模型有 16B 参数，意味着微调需要大量 GPU 显存——光是以完整 FP32 精度加载权重就要约 60GB 显存！好在有几条路可以应对这样的大模型：

- 使用参数高效方法（如 LoRA）：冻结基座模型权重，只插入少量可训练参数。[🤗 PEFT](https://github.com/huggingface/peft) 库里有很多这类方法。
- 用 [DeepSpeed ZeRO-3](https://huggingface.co/docs/transformers/main_classes/deepspeed) 或 [FSDP](https://pytorch.org/blog/introducing-pytorch-fully-sharded-data-parallel-api/) 这类方法，把模型权重、优化器状态和梯度分片到多个设备上。

由于 DeepSpeed 与 🤗 Transformers 深度集成，我们就用它来训练。开始之前，先从 GitHub 克隆 BigCode 的 StarCoder 仓库并进入 `chat` 目录：

```
git clone https://github.com/bigcode-project/starcoder.git
cd starcoder/chat
```

接下来用 Conda 等创建 Python 虚拟环境：

```
conda create -n starchat python=3.10 && conda activate starchat
```

然后安装 PyTorch v1.13.1。这与硬件相关，具体请参照 [PyTorch 安装页面](https://pytorch.org/get-started/locally/)。装好后安装其余项目依赖：

```
pip install -r requirements.txt
```

需要登录 Hugging Face，运行：

```
huggingface-cli login
```

最后安装 Git LFS：

```
sudo apt-get install git-lfs
```

最后一步，启动训练！如果你运气好手上有 8 块 A100（80GB）跑这个训练，执行：

```
torchrun --nproc_per_node=8 train.py config.yaml --deepspeed=deepspeed_z3_config_bf16.json
```

这里的 `config.yaml` 指定数据集、模型和训练的所有参数——你可以在[这里](https://github.com/bigcode-project/starcoder/tree/main/chat)修改配置以适配新数据集。训练好的模型随后就出现在 Hub 上！

# Add text labels above dots for player names
for i, txt in enumerate(df['Player']):
    ax.annotate(txt, (df["Rebounds"][i] +.1, df["Points"][i]))

# Set titles and labels

ax.set_xlabel('Number of Rebounds')

## 评估代码助手

评估代码助手（或更广义的聊天机器人）很棘手，因为我们在意的面向用户的指标，通常不在传统 NLP 基准的测量范围内。例如，我们把 StarCoderBase 的基座版和微调版都放进 EleutherAI 的[语言模型评估框架](https://github.com/EleutherAI/lm-evaluation-harness)，测了以下基准：

- [AI2 Reasoning Challenge](https://allenai.org/data/arc)（ARC）：小学科学多选题
- [HellaSwag](https://arxiv.org/abs/1905.07830)：围绕日常事件的常识推理
- [MMLU](https://github.com/hendrycks/test)：57 个学科的多选题（专业与学术）
- [TruthfulQA](https://arxiv.org/abs/2109.07958)：考察模型把事实从蓄意挑选的错误陈述中区分出来的能力

结果如下表。可以看到微调模型有所提升，但这种提升方式并不能反映它的对话能力。

| 模型 | ARC | HellaSwag | MMLU | TruthfulQA |
| --- | --- | --- | --- | --- |
| StarCoderBase | 0.30 | 0.46 | 0.33 | 0.40 |
| StarChat (alpha) | 0.33 | 0.49 | 0.34 | 0.44 |

那么除了依赖基准自动指标还能做什么？迄今为止主要有两种方法：

- 人工评估：把给定提示的生成输出呈现给人类标注员，按"最好"和"最差"排序。这是 InstructGPT 这类系统现在用的金标准。
- AI 评估：让 GPT-4 这样的强语言模型看生成输出，并用提示词引导它按质量打分。LMSYS 评估 [Vicuna 模型](https://lmsys.org/blog/2023-03-30-vicuna/)用的就是这条路。

作为一个小实验，我们用 ChatGPT 在若干编程语言上测试我们的 StarCoder 模型。首先创建了一个[有趣提示的种子数据集](https://huggingface.co/datasets/HuggingFaceH4/code_evaluation_prompts)用于评估。我们让 ChatGPT 来启动这个过程，比如问它：

```
Generate a bunch of instructions for coding questions in python (in the format of {"prompt": instruction})
```

或者

```
Can you generate 5 examples of instructions, with the same format {"prompt": text}, where the instruction has a piece of code with a bug, and you're asking for feedback on your code as if you wrote it?
```

第二个例子里，ChatGPT 其实生成了比请求更多的数据（比如多了一个字段，说明初次提交代码里的 bug）。目前这个数据集包含 115 条提示，以 Python 为主。四分之三的提示要求用户提供代码，四分之一要求对一段有 bug 的代码给反馈。

实验中，我们让 OpenAI 的模型用修改版的 [Vicuna 代码提示](https://github.com/lm-sys/FastChat/tree/main/fastchat/eval/table)逐条对比回答，并按 1 到 8 打分。结果显示，指令微调后的 StarCoder 在 95.6% 的情况下得分高于基座模型。一个有意思的现象是：ChatGPT 明显倾向于给中间的安全分数，而 GPT4 更敢给 1 分和 8 分。

## 局限与偏差

和许多其他语言模型一样，这个 alpha 版的 StarChat 存在明显的待解决局限，包括会编造事实、会产出有问题的内容（尤其被这样引导时）。具体来说，模型没有经过 RLHF 这类技术与人类偏好对齐，也没有像 ChatGPT 那样在环路中过滤响应。主要在代码数据上训练的模型，其人口统计学偏差会与 GitHub 社区的人口结构相称地更偏斜，更多细节见 [StarCoder 数据集](https://huggingface.co/datasets/bigcode/starcoderdata)。关于模型在事实性和偏差方面的更多限制，见[模型卡](https://huggingface.co/HuggingFaceH4/starchat-alpha#bias-risks-and-limitations)。

## 未来方向

让我们惊讶的是，像 StarCoder 这样的代码生成模型，居然能靠 OpenAssistant 这样多样化的数据集变成对话智能体。一种可能的解释是：StarCoder 在代码*和*GitHub issue 上都有训练，后者提供了丰富的自然语言信号。我们很期待社区把 StarCoder 带向何处——也许它将推动下一波开源助手 🤗。
