# 将 fairseq wmt19 翻译系统移植到 transformers

##### Stas Bekman guest 投稿

本文试图记录 [fairseq wmt19 翻译系统](https://github.com/pytorch/fairseq/tree/master/examples/wmt19)是如何被移植到 [`transformers`](https://github.com/huggingface/transformers/) 的。

我当时正想找一个有意思的项目做，[Sam Shleifer](https://github.com/sshleifer) 建议我尝试[移植一个高质量翻译器](https://github.com/huggingface/transformers/issues/5419)。

我读了那篇短文：[Facebook FAIR 的 WMT19 新闻翻译任务提交](https://arxiv.org/abs/1907.06616)，了解了原始系统，决定试一试。

起初我完全不知道该如何下手这个复杂项目，Sam 帮我[把它拆解成小任务](https://github.com/huggingface/transformers/issues/5419)，这帮助极大。

移植时我选择先处理 `en-ru`/`ru-en` 预训练模型，因为我两种语言都会说。如果做 `de-en`/`en-de` 对会难得多——我不会德语。能在移植后期直接读输出、判断翻译质量，帮我省了大量时间。

另外，由于我最初是用 `en-ru`/`ru-en` 模型做移植的，我当时完全不知道 `de-en`/`en-de` 模型用的是合并词表，而前者用的是两个大小不同的独立词表。所以当我啃下了支持两个独立词表这块硬骨头之后，让合并词表工作就变得轻而易举。

第一步当然是"抄近道"。能少费劲何必多费劲。我写了一个[短 notebook](https://github.com/stas00/porting/tree/master/transformers/fairseq-wmt19/nbs/cheat.ipynb)，用几行代码提供了一个通往 `fairseq` 的代理，并模拟 `transformers` 的 API。

如果只需要基本翻译，这就够了。但我们当然想要完整移植，所以这个小胜利之后，我转向了更难的部分。

## 翻译系统是如何工作的

先简短介绍一下当今计算机如何翻译文本。

计算机读不了文本，只能处理数字。所以处理文本时，我们必须把一个或多个字母映射成数字，交给程序；程序完成后返回的也是数字，我们再把它们转回文本。

从俄英两个句子开始，给每个词分配唯一编号：

```
я  люблю следовательно я  существую
10 11    12            10 13

I  love therefore I  am
20 21   22        20 23
```

10 开头的编号把俄语词映射为唯一数字，20 开头的对英语词做同样的事。即使不懂俄语，也能看出 `я`（意为"我"）在句中出现了两次，编号都是 10；`I`（20）同样出现了两次。

翻译系统分以下阶段工作：

```
1. [я люблю следовательно я существую] # 把句子切分成词
2. [10 11 12 10 13]                    # 在输入词典中查词并转成 id
3. [黑盒]                               # 机器学习系统的魔法
4. [20 21 22 20 23]                    # 在输出词典中查数字并转回文本
5. [I love therefore I am]             # 把 token 去分词、合并成句子
```

如果把前两阶段、后两阶段合并，就得到 3 个阶段：

- **编码输入**：把输入文本切成 token，构建 token 词典（vocab），把每个 token 重映射为词典中的唯一 id。
- **生成翻译**：输入数字，过一遍预训练机器学习模型得到最佳翻译预测，返回输出数字。
- **解码输出**：拿输出数字去目标语言词典查回文本，再把 token 合并成翻译后的句子。

第二阶段可能返回一种或多种可能的译文；若是多种，调用方可挑最合适的那个。本文会提到[束搜索算法](https://en.wikipedia.org/wiki/Beam_search)（beam search），它是搜寻多种可能结果的方法之一；束宽（beam size）指返回结果的数量。

如果只要一个结果，模型会选似然概率最高的；如果要多结果，则按概率排序返回。

注意，同样的思路适用于绝大多数 NLP 任务，不只是翻译。

## 分词

早期系统把句子切成单词和标点。但许多语言有数十万词，维护超大词表非常吃力——会急剧增加算力需求和任务耗时。

截至 2020 年，已有不少分词方法，但近年主流都基于子词（sub-word）分词——现代分词器不再按单词切分输入文本，而是把文本切成词段和字母，通过某种训练获得最优切分。

看看这种方法如何降低内存与计算需求。假设输入词表有 6 个常用词：go、going、speak、speaking、sleep、sleeping——按词级分词会得到 6 个 token。但若把它们切成 go、go-ing、speak、speak-ing 等，词表就只剩 4 个 token：go、speak、sleep、ing。这一个简单改动就带来 33% 的改善！当然，子词分词器不用语法规则，而是在海量文本上训练找这类切分。这里用简单语法规则是为了好理解。

这种方法的另一个重大优势是处理词表外的输入词。比如系统遇到词表里没有的 `grokking` (*)。如果把它切成 `grokk'-'ing'`，机器学习模型也许不知道如何对待前半部分，但能捕捉到 'ing' 表示进行时这一有用信息，从而给出更好的翻译。这种情况下，分词器会把未知片段继续拆成它认识的更小编段，最坏情况拆到单个字母。

- 脚注：to grok 由 Robert A. Heinlein 在 1961 年的《Stranger in a Strange Land》中造词：凭直觉或共情理解（某事物）。

现代分词方法远胜简单词级分词的原因还有很多，不在本文范围内。多数系统的切分机制比上面演示的简单 'ing' 切分复杂得多，但原理类似。

## 分词器移植

第一步移植分词器的编码（encoder）部分——把文本转成 id。解码部分要到最后才需要。

### fairseq 分词器的工作原理

先搞懂 `fairseq` 的分词器怎么工作。

`fairseq` (*) 使用[字节对编码](https://en.wikipedia.org/wiki/Byte_pair_encoding)（BPE）算法做分词。

- 脚注：下文提到 `fairseq` 时，指的是[这个具体的模型实现](https://github.com/pytorch/fairseq/tree/master/examples/wmt19)——`fairseq` 项目本身有几十种不同模型的不同实现。

看看 BPE 做了什么：

```
import torch
sentence = "Machine Learning is great"
checkpoint_file='model4.pt'
model = torch.hub.load('pytorch/fairseq', 'transformer.wmt19.en-ru', checkpoint_file=checkpoint_file, tokenizer='moses', bpe='fastbpe')

# encode step by step
tokens = model.tokenize(sentence)
print("tokenize ", tokens)

bpe = model.apply_bpe(tokens)
print("apply_bpe: ", bpe)

bin = model.binarize(bpe)
print("binarize: ", len(bin), bin)

# compare to model.encode - should give us the same output
expected = model.encode(sentence)
print("encode:   ", len(expected), expected)
```

得到：

```
('tokenize ', 'Machine Learning is great')
('apply_bpe: ', 'Mach@@ ine Lear@@ ning is great')
('binarize: ', 7, tensor([10217,  1419,     3,  2515,    21,  1054,     2]))
('encode:   ', 7, tensor([10217,  1419,     3,  2515,    21,  1054,     2]))
```

可以看到 `model.encode` 就是 `tokenize+apply_bpe+binarize` 的组合——输出一模一样。

步骤是：

- `tokenize`：通常会转义撇号、做其他预处理；这个例子里只是原样返回输入句子
- `apply_bpe`：BPE 按分词器提供的 `bpecodes` 文件把输入切成词与子词——得到 6 个 BPE 块
- `binarize`：把上一步的 BPE 块重映射为词表（也是随模型下载的）中对应的 id

更多细节可参考[这个 notebook](https://github.com/stas00/porting/tree/master/transformers/fairseq-wmt19/nbs/tokenizer.ipynb)。

一番调查后发现：词表文件里的 id 并不是模型使用的 id，模型内部在加载词表后会把它们重映射成新 id。幸运的是，我不必弄清具体怎么映射。我直接用了 `fairseq.data.dictionary.Dictionary.load` 来加载词典 (*)——它做了所有重映射——然后保存最终词典。我是靠调试器单步走 `fairseq` 代码发现这个 `Dictionary` 类的。

- 脚注：移植模型和数据集做得越多，我越意识到：让原始代码为我所用，而不是尝试复刻它，能省大量时间；更重要的是那些代码早已被测试过——自己重写很容易漏掉什么，日后才发现大问题。毕竟最终，这些转换代码本身都无所谓，被 `transformers` 和最终用户使用的是它生成的数据。

转换脚本的相关部分：

```
from fairseq.data.dictionary import Dictionary
def rewrite_dict_keys(d):
    # (1) remove word breaking symbol
    # (2) add word ending symbol where the word is not broken up,
    # e.g.: d = {'le@@': 5, 'tt@@': 6, 'er': 7} => {'le': 5, 'tt': 6, 'er</w>': 7}
    d2 = dict((re.sub(r"@@$", "", k), v) if k.endswith("@@") else (re.sub(r"$", "</w>", k), v) for k, v in d.items())
    keep_keys = "<s> <pad> </s> <unk>".split()
    # restore the special tokens
    for k in keep_keys:
        del d2[f"{k}</w>"]
        d2[k] = d[k]  # restore
    return d2

src_dict_file = os.path.join(fsmt_folder_path, f"dict.{src_lang}.txt")
src_dict = Dictionary.load(src_dict_file)
src_vocab = rewrite_dict_keys(src_dict.indices)
src_vocab_size = len(src_vocab)
src_vocab_file = os.path.join(pytorch_dump_folder_path, "vocab-src.json")
print(f"Generating {src_vocab_file}")
```

## 移植核心翻译功能

## 移植分词器解码器

当移植后的 `generate` 函数输出与 `fairseq` 的 `generate` 已经相当接近后，下一步是完成最后的解码——把输出变成人类可读文本。这样我就能用眼睛快速比较翻译质量——对着输出 id 可做不到。

解码与编码过程相反。

步骤：

- 把输出 id 转成文本字符串
- 去掉 BPE 编码
- 去分词（detokenize）——处理转义字符等

调试后，我不得不改变 `tokenization_xlm.py` 中处理 BPE 的原始方式，并把输出过一遍 `moses` 去分词器。

```
     def convert_tokens_to_string(self, tokens):
         """ Converts a sequence of tokens (string) in a single string. """
-        out_string = "".join(tokens).replace("</w>", " ").strip()
-        return out_string
+        # remove BPE
+        tokens = [t.replace(" ", "").replace("</w>", " ") for t in tokens]
+        tokens = "".join(tokens).split()
+        # detokenize
+        text = self.moses_detokenize(tokens, self.tgt_lang)
+        return text
```

一切就绪。

## 手动测试

到这里为止，我主要用自己的脚本做测试。

翻译器可以工作后，我转换了反向的 `ru-en` 模型，然后写了两个改述（paraphrase）脚本：

- [fseq-paraphrase](https://github.com/stas00/porting/tree/master/transformers/fairseq-wmt19/scripts/fseq-paraphrase.py)
- [fsmt-paraphrase](https://github.com/stas00/porting/tree/master/transformers/fairseq-wmt19/scripts/fsmt-paraphrase.py)

它们把源语言句子翻成另一语言，再把结果翻回原语言。由于不同语言表达同一件事的方式不同，这一过程通常会得到一个改述版本。

借助这些脚本，我又发现去分词器还有一些问题，调试器单步排查后，让 fsmt 脚本产出的结果与 `fairseq` 版本完全一致。

此时无束搜索已基本产出相同结果，但束搜索仍有出入。为了揪出特殊案例，我写了 [fsmt-port-validate.py](https://github.com/stas00/porting/tree/master/transformers/fairseq-wmt19/scripts/fsmt-port-validate.py) 脚本：以 `sacrebleu` 测试数据为输入，让 `fairseq` 和 `transformers` 都跑一遍翻译，只报告不一致的样本。它很快暴露了剩下的几个问题，观察规律后我把它们都修好了。

## 移植其他模型

接着我去移植 `en-de` 和 `de-en` 模型。

意外发现它们构建方式不一样：每个模型用合并词典。有那么一瞬间我很绝望，以为又要做大改造来支持它。但结果是不需要任何改动——合并词典天然适配。我只需把同一个词典用两份——一份当源、一份复制当目标。

我又写了一个脚本测试所有已移植模型的基本功能：[fsmt-test-all.py](https://github.com/stas00/porting/tree/master/transformers/fairseq-wmt19/scripts/fsmt-test-all.py)。

## 测试覆盖

下一步非常关键——要为移植的模型准备充分的测试。

在 `transformers` 测试套件中，大多数涉及大模型的测试被标记为 `@slow`，它们不会在 CI（持续集成）里常规运行——因为它们确实慢。所以我还需要一个"微型模型"：结构与正常预训练模型相同，但要非常小、权重可以是随机的。这个微型模型可用于测试移植的功能，只是不能用于质量测试——它只有很少的权重，实际什么也干不了。[fsmt-make-tiny-model.py](https://github.com/stas00/porting/tree/master/transformers/fairseq-wmt19/scripts/fsmt-make-tiny-model.py) 可以创建这样的微型模型。生成的模型连同词典和配置文件总共只有 3MB。我用 `transformers-cli upload` 传到 `s3`，然后就能在测试套件里使用了。

和写代码一样，我先复制 `tests/test_modeling_bart.py`，改成使用 `FSMT`，再针对新模型逐条调整。

然后把我手动测试用的几个脚本转成单元测试——很容易。

`transformers` 有一套庞大的公共测试，每个模型都要过一遍——我又做了些调整让 `FSMT` 能跑通这些测试（主要是适配双词典设置），并覆盖了少数因该模型独特性无法运行、只能跳过的测试。结果见[这里](https://github.com/huggingface/transformers/blob/129fdae04033fe4adfe013b734deaec6ec34ae2e/tests/test_tokenization_fsmt.py)。

我加了一个做轻量 BLEU 评估的测试——对 4 个模型各用 8 条文本输入测 BLEU 分数。[测试在这里](https://github.com/huggingface/transformers/blob/129fdae04033fe4adfe013b734deaec6ec34ae2e/examples/seq2seq/test_fsmt_bleu_score.py)，[生成数据的脚本在这里](https://github.com/huggingface/transformers/blob/129fdae04033fe4adfe013b734deaec6ec34ae2e/examples/seq2seq/test_data/fsmt/build-eval-data.py)。

## SinusoidalPositionalEmbedding

`fairseq` 的 `SinusoidalPositionalEmbedding` 实现与 `transformers` 用的略有不同。我最初照搬了 `fairseq` 版。但跑测试套件时，`torchscript` 测试怎么都过不去。`SinusoidalPositionalEmbedding` 的写法本意是不进入 `state_dict`、不随模型权重一起保存——该类生成的所有权值都是确定性的、不参与训练。`fairseq` 的取巧做法是：权值既不设为参数也不设为 buffer，然后在 `forward` 时把权重切换到正确设备。`torchscript` 不接受这套——它要求第一次 `forward` 之前所有权值就位于正确设备。

我只能重写实现：改成正常的 `nn.Embedding` 子类，再增加功能：`save_pretrained()` 时不保存这些权重，而 `from_pretrained()` 在加载 `state_dict` 找不到这些权重时也不报错。

## 评估

根据我拿大量文本做手动测试的经验，我知道移植模型表现不错，但不知道它相对原版的分数如何。于是到了评估环节。

翻译任务的评估指标是 [BLEU 分数](https://en.wikipedia.org/wiki/BLEU)。`transformers` 有个评估脚本 [run_eval.py](https://github.com/huggingface/transformers/blob/129fdae04033fe4adfe013b734deaec6ec34ae2e/examples/seq2seq/run_eval.py%60)。

`ru-en` 方向的评估如下：

```
export PAIR=ru-en
export MODEL=facebook/wmt19-$PAIR
export DATA_DIR=data/$PAIR
export SAVE_DIR=data/$PAIR
export BS=64
export NUM_BEAMS=5
export LENGTH_PENALTY=1.1
mkdir -p $DATA_DIR
sacrebleu -t wmt19 -l $PAIR --echo src > $DATA_DIR/val.source
sacrebleu -t wmt19 -l $PAIR --echo ref > $DATA_DIR/val.target
PYTHONPATH="src:examples/seq2seq" python examples/seq2seq/run_eval.py $MODEL \
$DATA_DIR/val.source $SAVE_DIR/test_translations.txt --reference_path $DATA_DIR/val.target \
--score_path $SAVE_DIR/test_bleu.json --bs $BS --task translation --num_beams $NUM_BEAMS \
--length_penalty $LENGTH_PENALTY --info $MODEL --dump-args
```

运行几分钟后返回：

```
{'bleu': 39.0498, 'n_obs': 2000, 'runtime': 184, 'seconds_per_sample': 0.092, 
'num_beams': 5, 'length_penalty': 1.1, 'info': 'ru-en'}
```

可以看到 BLEU 分数为 `39.0498`，用的是 `sacrebleu` 提供的 `wmt19` 数据集中的 2000 条测试输入。

别忘了，我用不了模型集成，所以还要找出表现最好的检查点。为此我写了脚本 [fsmt-bleu-eval-each-chkpt.py](https://github.com/stas00/porting/tree/master/transformers/fairseq-wmt19/scripts/fsmt-bleu-eval-each-chkpt.sh)：逐个转换检查点、跑评估、报告最佳。结果：4 个可用检查点中 `model4.pt` 表现最好。

我得到的 BLEU 分数与原论文报告的不一致，于是需要确认双方用的是同样的数据和同样的工具。通过在 `fairseq` 的 issue 里求助，我拿到了 `fairseq` 开发者用来计算 BLEU 的代码——见[这里](https://github.com/stas00/porting/tree/master/transformers/fairseq-wmt19/scripts/fseq-reproduce-bleu.sh)。但可惜，他们的方法使用了未公开的重排序（re-ranking）手段；而且他们是在去分词之前的输出上做评估，不是真实输出——据说这样分数更高。总之——我们的计分方式不一样 (*)。

- 脚注：论文 [A Call for Clarity in Reporting BLEU Scores](https://arxiv.org/abs/1804.08771) 呼吁开发者统一指标算法（简言之：用 `sacrebleu`）。

目前这个移植模型因为不使用模型集成，BLEU 分数略逊于原版；但在双方采用相同测量方法之前，具体差距无从判断。

## 移植更多模型

把 4 个 `fairseq` 模型[上传](https://huggingface.co/models?filter=facebook&tag=fsmt)后，又有人建议移植 AllenAI 的 3 个 `wmt16` 和 2 个 `wmt19` 模型（[Jungo Kasai 等](https://github.com/jungokasai/deep-shallow/)）。移植过程轻松愉快，唯一的难题是把源文件凑齐——它们散落在好几个不相干的压缩包里。一旦搞定，转换一气呵成。

移植后我发现唯一的问题：BLEU 分数比原版低。这些模型的作者 Jungo Kasai 非常热心地指出，他们使用了自定义超参数 `length_penalty=0.6`——一旦换上这个值，结果立刻好多了。

这个发现催生了新脚本：[run_eval_search.py](https://github.com/huggingface/transformers/blob/129fdae04033fe4adfe013b734deaec6ec34ae2e/examples/seq2seq/run_eval_search.py%60)，可用于搜索能让 BLEU 最优的各种超参数。用法示例：

```
# search space
export PAIR=ru-en
export DATA_DIR=data/$PAIR
export SAVE_DIR=data/$PAIR
export BS=32
mkdir -p $DATA_DIR
sacrebleu -t wmt19 -l $PAIR --echo src > $DATA_DIR/val.source
sacrebleu -t wmt19 -l $PAIR --echo ref > $DATA_DIR/val.target
PYTHONPATH="src:examples/seq2seq" python examples/seq2seq/run_eval_search.py stas/wmt19-$PAIR \
$DATA_DIR/val.source $SAVE_DIR/test_translations.txt --reference_path $DATA_DIR/val.target \
--score_path $SAVE_DIR/test_bleu.json --bs $BS --task translation \
--search="num_beams=5:8:11:15 length_penalty=0.6:0.7:0.8:0.9:1.0:1.1 early_stopping=true:false"
```

它会遍历 `num_beams`、`length_penalty` 和 `early_stopping` 所有可能的组合。

运行结束后报告：

```
bleu  | num_beams | length_penalty | early_stopping
----- | --------- | -------------- | --------------
39.20 |        15 |            1.1 |              0
39.13 |        11 |            1.1 |              0
39.05 |         5 |            1.1 |              0
39.05 |         8 |            1.1 |              0
39.03 |        15 |            1.0 |              0
39.00 |        11 |            1.0 |              0
38.93 |         8 |            1.0 |              0
38.92 |        15 |            1.1 |              1
[...]
```

可以看到在 `transformers` 中 `early_stopping=False` 效果更好（`fairseq` 用的是等效于 `early_stopping=True` 的行为）。

对 5 个新模型，我用这个脚本找出最佳默认参数，并在转换模型时写入。用户调用 `generate()` 时仍可覆盖这些参数，但何不提供更优的默认值呢。

5 个已移植的 AllenAI 模型在[这里](https://huggingface.co/models?filter=allenai&tag=fsmt)。

## 收尾思考

- 虽然我没能移植模型集成（`transformers` 不支持），但好处是最终的 `facebook/wmt19-*` 模型下载体积只有 1.1GB，而不是原版的 13GB。不知为何，原版模型把优化器状态也保存在模型里——对只想下载模型直接翻译的用户来说，白白多了近 9GB（4x2.2GB）的死重。
- 虽然移植工作看起来挑战巨大——毕竟我对 `transformers` 和 `fairseq` 的内部构造都不了解——但回头看，其实没那么难。这主要归功于 `transformers` 各处已有几乎所有现成组件：我*"只需"*找到需要的部分（大量借用其他模型的代码），再调整它们以满足需求。代码和测试都是如此。换个说法——移植确实难——但如果一切从零写起只会难得多。而且找到正确的部件本身也不轻松。

### Jupyter Notebook 自动打印所有表达式

我的 jupyter notebook 配置为自动打印所有表达式，不必显式写 `print()`。默认行为只打印每个 cell 的最后一个表达式。所以如果你读到我 notebook 里的输出，可能与你自己运行时看到的不一样——除非你有相同配置。

你可以在 jupyter notebook 环境中启用自动打印，在 `~/.ipython/profile_default/ipython_config.py`（没有就创建一个）中加入：

```
c = get_config()
# Run all nodes interactively
c.InteractiveShell.ast_node_interactivity = "all"
# restore to the original behavior
# c.InteractiveShell.ast_node_interactivity = "last_expr"
```

然后重启 jupyter notebook 服务器。
