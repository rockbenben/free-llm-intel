# 释放连续批处理中的异步能力

[![标题图](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/banner.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/banner.png)

*TL;DR：我们讲清楚如何把 CPU 与 GPU 的负载拆开，为推理带来大幅性能提升。*

*这是高效 LLM 推理系列的第二篇。[第一篇](https://huggingface.co/blog/continuous_batching)从第一性原理讲了连续批处理（continuous batching），引入了本篇要沿用的几个概念：KV cache、FlashAttention、注意力掩码等。*

一张 H200 在 [Inference Endpoints](https://endpoints.huggingface.co/) 上大约 $5/小时。一小时听着不贵，但跑上一天就要 $120。既然花了这个钱，你就希望 GPU 被榨到最满。

我们已经知道连续批处理通过安排紧密的批次来提高 GPU 利用率，算力不再浪费在 padding 上。但还有第二重浪费是连续批处理没有解决的：它默认是同步的。也就是说 CPU 和 GPU 轮流出工：GPU 在算的时候 CPU 闲着；CPU 在准备下一批的时候 GPU 闲着。在一个每秒跑几百步的循环里，这些空隙会不断累积——如我们将展示的，它们能占到总运行时间的近四分之一。要让 GPU 100% 的时间都在计算，就得把这些空隙消掉。

办法是**异步批处理（asynchronous batching）**：把 CPU 侧的批次准备与 GPU 侧的批次计算解耦，让二者并行，GPU 时刻保持生产力 🔥

## 同步批处理

朴素的同步批处理是这样：

[![同步批处理](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/synchronous_batching.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/synchronous_batching.png)

CPU 准备新批次时，挑选要纳入哪些请求、更新 KV cache 表、驱逐上一轮已完成的请求、再放入新请求填满腾出的空间。全部弄好后，把准备好的输入搬到 GPU。GPU 跑一次前向，并为每个请求采样（即选择）一个新 token。结果回到 CPU，CPU 由此知道每个请求刚产出了什么 token，然后整个循环再来一遍。

注意图右侧的红色标注：GPU 算完之后进入空闲。下一个批次要等 CPU 完成它的更新步骤（采样输出 token、更新请求状态、重新排批）才能开始。

这就是同步批处理的核心低效：CPU 和 GPU 轮流干活。GPU 计算时 CPU 闲着，CPU 更新时 GPU 闲着。任何时刻两个都干不了有用的事。单次前向这似乎代价不大，但连续批处理循环每秒跑几百步，这些空隙会累积成实打实的吞吐损失。

为了展示这一点，我们用 8B 模型、batch size 32 生成 8K token，分别剖析 CPU 与 GPU 的耗时：

[![CPU 与 GPU 活动时间线](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/cpu_gpu_phases_sync.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/cpu_gpu_phases_sync.png)

*如果你想做出同款图，可以在连续批处理代码里埋点导出 CPU/GPU 活动时间跨度，然后[用这个脚本](https://gist.github.com/remi-or/8de44738629c4d3c72451aa01df1a2ab)。*

时间线在绿色（GPU 忙、CPU 闲）和红色（CPU 忙、GPU 闲）之间交替：两者从不重叠。总生成时间 300.6 秒，其中 24.0% 的时间 GPU 空闲、在等 CPU 干完。从 GPU 的角度看，近四分之一的生成时间被浪费了。这是悲观的看法。

乐观的看法是：如果能彻底消除 CPU 开销，生成时间就能从 300 秒降到 228 秒（白捡 24% 加速！）。这不需要任何新 kernel 或模型改动，只需要精细地协调硬件。

根本思路很简单：想办法在批次 N 计算的同时准备批次 N+1。但这个简单想法藏着几个技术难点：

- 怎样把活儿丢给 GPU 之后，把控制权交还给 CPU？
- 怎样保证每个任务（无论 CPU 还是 GPU）启动时它需要的数据已经就绪？
- 如果批次 N+1 依赖批次 N 的预测结果，怎么提前准备批次 N+1？

回答这三个问题的过程，就是我们从零构建异步批处理的过程。我们在 [transformers](https://github.com/huggingface/transformers) 库里把这套东西实现进了连续批处理，走的也是同样的步骤，欢迎对照代码比较！

## 制造并发

我们的最终目标是让 CPU 和 GPU 操作**并发**执行。需要一种给操作分类的手段，让机器知道哪些操作可以并行。CUDA stream（流）可以办到。

### 什么是 CUDA stream？

要理解 CUDA 如何编排它的操作，就得说说 **CUDA streams**。一个 stream 是一个有序 GPU 操作队列（kernel 启动、内存拷贝、同步屏障），按提交顺序执行。每个 GPU 操作必然归属于某个 stream。同一 stream 内的操作是串行的：前一个不完成，GPU 不开始下一个。*不同* stream 之间的操作互不相干，可以并发执行。举例：你在 3 个不同 stream 上各启动 1 个操作，执行起来是这样：

[![CUDA stream 并发](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/stream_concurrency.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/stream_concurrency.png)

三个操作同时开始。这是个小小的简化：每个 GPU 操作终究由 CPU 发起，而发起本身要花一点时间——找对 kernel、发出调用、把命令从 CPU 传到 GPU 等等，这就是 **CPU launch overhead（CPU 启动开销）**。更写实的图长这样：

[![更写实的 CUDA stream 并发](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/realistic_concurrency.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/realistic_concurrency.png)

操作依然并发，但起始时间被每次 CPU 启动的成本错开了。后文我们会一直画出这些 CPU 启动事件，因为它们真实耗时，也帮我们跟踪「什么活儿是什么时候发出去的」——进入异步流程后这点很重要。例如我们会经常检查某个 stream 是否已 **flush**（冲刷完毕）：意思是该 stream 里的所有操作都已执行。

### 默认流与非默认流

如果你以前没在 PyTorch 里显式用过 CUDA stream，你可能会惊讶它们居然存在。典型的 PyTorch 脚本从不提它们，你也不*觉得* GPU 操作是异步的——CPU 看起来总在等 GPU 干完才往下走。这个感觉没错，来源就是**默认流（default stream）**。

调用 PyTorch 操作却不指定 stream 时，它就落在默认流上。默认流有个特殊属性：**同步性**。排在默认流上的操作会等**所有其他 stream 都 flush**——GPU 上的全部工作结束，默认流上的这个操作才能开始。反过来也成立：任何操作，无论在哪个 stream，都要等默认流 flush 完才启动。

所以如果你要把默认流操作的结果拷回 CPU，哪怕用的是理论上不阻塞 CPU 的拷贝，CPU 依然会一直阻塞到所有 GPU 操作完成——因为那些操作排在了默认流上。这会直接摧毁你构建并发的一切努力。

这就是为什么必须用非默认流。把 kernel 启动或非阻塞内存拷贝排进队列后，控制权立刻回到 CPU。GPU 在后台跑这个操作，但 CPU 不等。第一个问题就此解决：要在启动 GPU 工作后拿回 CPU 控制权，就用非默认流。

[![阻塞与非阻塞传输](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/block_or_not.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/block_or_not.png)

本文余下部分，我们假设所有跨设备内存传输都是非阻塞的，因此需要我们自己做同步。

### 回到连续批处理

我们已经确定：任何 GPU 操作都不该落在默认流上。但问题还在：不用默认流的话，该用哪些流？回到同步批处理那张图：

[![同步批处理](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/synchronous_batching.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/synchronous_batching.png)

可以识别出三个不同的 GPU 操作：

- 输入从 CPU 传到 GPU
- GPU 上的计算
- 输出从 GPU 传回 CPU

也就是说我们需要三个流：一个计算流、一个 CPU 到 GPU 传输流、一个 GPU 到 CPU 传输流。两类传输互不依赖，没有理由串行化，各拿一个流。

> 命名说明：谈 CPU 和 GPU 时，CUDA 文档的惯例是把 CPU 称为 host（主机）、GPU 称为 device（设备）。下文沿用该惯例。CPU→GPU 的传输叫 host-to-device（H2D），GPU→CPU 的叫 device-to-host（D2H）。于是三个流就是 H2D 流、计算流、D2H 流。

现在试试只用流来异步地把一个批次发到 GPU 并拿回 CPU 控制权。从 CPU 出发做这几步：

- 在 CPU 上准备好批次输入数据（无流，纯 CPU 操作）
- 把它传输到 GPU（用 H2D 流）
- 在 GPU 上跑计算（用计算流）
- 取回批次输出（用 D2H 流）
- 查看结果（无流）

如果只靠 CUDA stream 就这么干，结果几乎是瞬间返回的——而且是错的。为什么？看看实际发生了什么：

[![失败的异步批处理](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/failed_async.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/failed_async.png)

因为流彼此独立，三个 GPU 操作几乎同时启动。计算流没有等 H2D 传完，前向传播就地取材、算了 GPU 显存里原本躺着的东西。D2H 流没有等计算完成，把还没算出来的结果搬了回来。第 5 步瞬间返回，因为没有任何东西阻塞 CPU：没有默认流可同步。

每步操作单独看都在正确执行。问题是我们从没告诉这些流要互相等待。我们明知计算必须在 H2D 之后开始、D2H 必须在计算之后开始，却没有把顺序强制下来。我们需要一种跨流边界的机制，能说出「那个没做完，这个不许开始」。

## 强制同步

要在流之间强制顺序，我们请出 **CUDA events（事件）**。

### 什么是 CUDA event？

CUDA event 是可以记录进某个流的一个标记。GPU 执行经过这个标记时，就把事件置为完成。其他流则可以被告知：等这个事件完成再进行下一个操作。具体就两个操作：`stream.record(event)` 在当前插入标记，`stream.wait(event)` 让该流被阻塞直到事件置完成。注意，`wait` 阻塞的是*流*，不是 CPU、也不影响并行运行的其他流：CPU 调用立即返回，只有等待的那个流被扣住。

[![CUDA 事件](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/events.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/events.png)

上图是单个事件同步两个流。CPU 连续发出三个操作（三个小块）：在流 1 上启动输入准备、在流 1 上记录事件、然后让流 2 等这个事件。之后 CPU 立刻继续干活。流 1 执行它的操作，完成后事件被置起。流 2 全程被扣在 wait 标记处，直到事件完成才开始计算。这一切 CPU 都没有参与：顺序完全由 GPU 侧强制。

### 在连续批处理中使用事件

应用到我们的场景，改法很直接。H2D 传输入队之后，调用 `h2d_stream.record(h2d_done)`：传输完成时该事件才被置完成。前向传播入队之前，调用 `compute_stream.wait(h2d_done)`，计算流就会等 `h2d_done` 置起才开始。计算与 D2H 之间同理：`model.forward` 发出后调用 `compute_stream.record(compute_done)`，再在输出传输入队前调用 `d2h_stream.wait(compute_done)`。得到一条顺序显式的流水线：

- H2D 传输在 `h2d_stream` 上跑
- `compute_stream` 等 `h2d_done`，然后跑前向
- `d2h_stream` 等 `compute_done`，然后把输出传回来

CPU 把这一切依次入队然后就走人，全程不阻塞。GPU 靠事件来强制顺序，三个流在各自依赖满足的那一刻全部活跃。

[![成功的异步批处理](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/success_async.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/success_async.png)

上图展示了全过程。CPU 准备好批次后迅速把所有 GPU 工作入队：H2D 传输、前向、D2H 传输，每级之间插入 `record` 和 `wait`。之后 CPU 就自由了。GPU 接管，按事件置起的顺序逐流执行。注意右侧的绿色标注：D2H 传输一完成，CPU 回来读结果。这最后一次同步是整步中 CPU 唯一阻塞的地方。实现方式是：在输出传输之后对 D2H 流再记录第三个事件，然后在 CPU 侧调用 `d2h_done_event.synchronize()`。`synchronize` 会阻塞 CPU，直到 D2H 流到达那个标记。

这正是与同步批处理的关键区别：以前 CPU 在每个操作后都要阻塞，现在 GPU 干活时 CPU 可以自由地做「某件事」。

至于这个「某件事」是什么，还得我们来定——因为到目前为止 GPU 利用率并没有任何变化。

## 填空

CPU 可用的窗口位于「发出批次 N」和「发出批次 N+1」之间。天然的用途就是准备批次 N+1 的输入，好把它们发往 GPU、在批次 N 算完时恰好就绪。看怎么做。

准备批次 N+1 可以复用准备批次 N 的那些 CPU 侧对象：当前请求列表、cache 状态、host 侧张量缓冲等。但要注意两件事：

- 数据损坏（data corruption）：批次 N+1 的设备侧输入缓冲不能和批次 N 用同一块——GPU 还在读，写了就会损坏数据
- 数据传递（data transmission）：若某请求同时出现在批次 N 和 N+1 中，且它在批次 N 的输出里产出了一个新 token，那这个 token 是批次 N+1 输入所需要的

数据损坏和数据传递这两个问题，下面两节分别解决。

### 竞态条件

先解决数据损坏。

假设批次 N 和 N+1 共享同一组设备侧输入缓冲，而 N+1 的 H2D 传输在 N 还在计算时就开始。CPU 可能往 GPU 仍在读取的内存里写 N+1 的输入，GPU 就可能读到被部分覆盖的数据，结果损坏。这就是**竞态条件（race condition）**。host 侧也有同样风险：N 的 H2D 拷贝还在途时复用同一个拷贝源，就会损坏传输。

解法是准备两组张量交替使用。GPU 在槽位 A 上处理批次 N 时，CPU 用批次 N-1 的结果更新请求状态，接着在输入槽位 B 上准备批次 N+1。下一步两者互换。下图展示了这一点：

[![输入 / 输出槽位](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/slots.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/slots.png)

当然这有代价：存放输入输出张量的 RAM 和 VRAM 都翻倍。这是可接受的折衷，尤其配合 [FlashAttention](https://github.com/Dao-AILab/flash-attention) 用时——它不需要注意力掩码，而掩码正是最大的那个输入张量。

但两个槽位又带来一个新问题。推理中我们通常用 **CUDA graph** 降延迟。简单说，[CUDA graph](https://pytorch.org/blog/accelerating-pytorch-with-cuda-graphs/) 是一段预先录好的 CUDA 操作序列，录制时绑定了具体的内存地址：为槽位 A 捕获的 graph 不能对槽位 B 的缓冲重放。所以我们需要两张 graph。而两张 graph 各配一套内存缓冲的话，VRAM 又要翻倍。

解法是**内存池（memory pool）**：两张 graph 共同分配的一块共享内存缓冲。唯一约束是同一池里的两张 graph 绝不可并发执行。而批次 N 必须先于 N+1 结束，这个条件天然总是成立。实测两张 graph 加起来用的 VRAM 和一张几乎一样——只是初始化时付了两次捕获的时间。我们可以在同一个池里创建任意数量的 CUDA graph，总内存用量仍以单张 graph 的最大值封顶。下图展示了这一点。

[![CUDA graph 内存池](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/memory_pool.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/memory_pool.png)

现在知道怎么防数据损坏了，接着解决第二个问题：把批次 N 的输出 token 送进批次 N+1 的输入。

### Carry-over（传递）

考虑一个同时出现在批次 N 和 N+1 的请求。它在批次 N 里产出一个新 token，这个 token 就是它在 N+1 的输入。麻烦在于：我们准备 N+1 的输入缓冲时，那个 token 还不存在——批次 N 还在跑。对策是：构建 N+1 时先放一个占位 token。我们用 0 作占位符，原因后面会明朗。等批次 N 算完、N+1 开始前向之前，再把占位符替换掉。这一步我们叫 **carry-over（传递）**，因为我们把新 token 从批次 N 传递到 N+1。思路如下图：

[![Carry over 原理](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/carry_over_idea.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/carry_over_idea.png)

执行 carry-over 只需要三样东西：批次 N 的输出 token ids、批次 N+1 的输入 token ids、以及一个描述如何 carry-over 的指令张量——我们叫它 **carry-over mask**。它包含需要传递的 token 的目标位置，不需要传递的位置填 -1。下图给出一种表示：

[![Carry over mask](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/carry_over_mask.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/carry_over_mask.png)

carry-over 本身由四个操作构成：

- 从批次 N 的输出中选出要传递的 token，放进新张量 T
- 把 T 中不需要传递的位置清零
- 把 T 截断到与批次 N+1 的输入长度一致
- 把 T 加到批次 N+1 的输入 ids 上（这就是占位符取值为 0 的原因）

这四个操作都很便宜，所以我们在每个新批次开始时执行，并把 carry-over 一并捕获进 CUDA graph。若 carry-over mask 全是 -1（-1 表示该位置不传递），最后一步就退化为加一个零张量。这种情况不常发生，因为跨批次的解码请求通常被调度在相邻批次里。

## 完整的异步循环

把一切拼起来，走一遍前两步。

第 0 步是冷启动：没有上一个批次在跑，CPU 在槽位 A 上准备批次 0，照同步批处理的样子直接发出。还没有重叠。

[![异步流程回顾](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/async_recap_1.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/async_recap_1.png)

第 1 步是异步循环真正开始的地方。GPU 正在槽位 A 上跑批次 0，CPU 空出来了。它立刻在槽位 B 上准备批次 1：驱逐已完成的请求、放入新请求、更新 KV cache 路由表、构建 carry-over mask。这一切与 GPU 完全重叠地运行。批次 1 的输入就绪后，CPU 依次入队：发出槽位 B 的 H2D 传输、为计算流和 D2H 流记录并等待事件，然后继续前进。

[![异步流程回顾](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/async_recap_2.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/async_recap_2.png)

此刻 GPU 上有两件事并行。槽位 A 上，GPU 跑完计算并置起 `compute_done`，放行批次 0 输出的 D2H 传输。槽位 B 上，批次 1 输入的 H2D 传输正在进行。它一完成，`h2d_done` 事件被置起，批次 1 的计算开始。从批次 0 到批次 1 的 carry-over 属于这轮计算的一部分：在常规前向之前执行。槽位 A 和槽位 B 彼此独立，所有环节自由重叠。

[![异步流程回顾](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/async_recap_3.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/async_recap_3.png)

与此同时，CPU 阻塞在 `d2h_done_event.synchronize()` 上，直到批次 0 的输出落地。然后它处理输出、更新批次 0 中所有请求的状态、开始调度批次 2。循环已经转起来了，后续每一步都严格重复同一模式。

[![异步流程回顾](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/async_recap_4.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/async_recap_4.png)

只要批次 N 结束时批次 N+1 的输入已在 GPU 上就绪，GPU 就不会在批次之间空闲。唯一悬念是 CPU 能否赶在 GPU 算完之前干完它的活。通常能：模型还在不断变大，而批次调度始终相对便宜，所以瓶颈在 GPU 计算，不在 CPU。

## 真的有效吗？

验证一下：重跑之前那个实验——8K token、batch size 32、8B 模型。

[![CPU 与 GPU 活动时间线](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/cpu_gpu_phases_async.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/continuous_async/cpu_gpu_phases_async.png)

时间线几乎整条是深绿色：CPU 和 GPU 同时在跑。偶尔出现的浅绿片段是 GPU 在忙而 CPU 已备完、正在等的时刻。几乎看不见的红色刻度是批次之间的同步点——CPU 阻塞以采样批次 N 的输出。GPU 在总运行时间中的活跃比例为 99.4%，此前是 76.0%。总生成时间从 300.6s 降到 234.5s，加速 22%。我们预测彻底消除 CPU 开销能到 24%，剩下的微小差距就是那个不可消除的同步点。没有新 kernel、没有模型改动：只是让 CPU 和 GPU 同时干活。

## 结论

我们从一个 CPU 和 GPU 先后串行、两边都用不满的同步负载出发。通过把依赖关系从「按计划排程」换成「按数据流」并打磨同步点，我们成功解开了 CPU 与 GPU 的负载纠缠，让两种硬件得以并行执行。由此 GPU 工作队列被填满、保持常转，最终在保持模型精度的同时大幅提升生成速度。可以说是满堂彩。

完整实现在 [transformers](https://github.com/huggingface/transformers) 库里。想看这套东西如何落到真实代码，连续批处理的总入口是 [continuous_batching.py](https://github.com/huggingface/transformers/blob/main/src/transformers/generation/continuous_batching/continuous_api.py)，更偏异步的代码在 [ContinuousBatchingAsyncIOs](https://huggingface.co/transformers/blob/5042bb7eb64b69efd351482a05b3803c48955cb4/src/transformers/generation/continuous_batching/input_outputs.py#L609) 类里。

异步批处理让我们离为 16K+ 长生成（比如强化学习场景）解锁 SOTA 吞吐更近一步。但还有若干件较小的事也少不了。下一篇我们就讲这些：请求 offload、解码专用 kernel、细粒度编译等等。敬请期待！
