企业需要的是能在自家环境里把活干好的 agent。它们交给这些 agent 的工作，由所用系统、所遵循的规则以及数据状态共同塑造。一个模型可能普遍能力很强，却在某个特定环境里表现挣扎：某条流程它处理得不好，某一组工具它用错，或者某条约束它没能遵守。而这些正是企业需要改进的短板。

难点在于把这些短板变成训练数据。单一个失败确实能说明一些东西，但训练一个模型需要许多新任务，在不同情境下锻炼同一种能力。这些任务还必须在该环境里能够完成，看起来像某人真会提出的那种工作，并且有一种可靠的方式来检查 agent 是否成功。

在 ServiceNow CoreAI，我们构建了 AutoSynthData，把这些能力缺口变成训练数据。它利用目标模型的失败与更强的 teacher 的成功来决定模型下一步该学什么，然后生成并校验能锻炼这些能力的新任务。随着模型进步，课程会转向它仍然觉得困难的部分。我们用 EnterpriseOps Gym（[Malay et al., 2026](https://arxiv.org/abs/2603.13594)）来说明这条流水线，并使用[已发布的数据集](https://huggingface.co/datasets/ServiceNow-AI/EnterpriseOps-Gym)。我们先描述 agent 运作其中的环境，以及一个任务凭什么对训练有用。

## 什么样的 agentic 任务才有用

agentic 环境定义了 agent 运作于其中的那个世界：它能观察和修改的状态、它能调用的工具与 API，以及它的动作所产生的状态转移。

任务是在这个环境里被实例化的。我们采用如下抽象：

```
task = (system specification, user prompt, verifier)
```

### 系统规范

系统规范定义了 agent 运作所受的限制，包括系统指令、环境政策，以及在适用时的任务专属初始化，比如预置好的数据库状态或一批 knowledge article。

规范必须与环境中的工具、状态和支持的动作相兼容。它的指令应当清晰，避免仅仅为了制造难度而引入的任意限制。

### 面向 agent 的任务

用户 prompt 说明用户希望 agent 完成什么，以及任何用户层面的限制。生成出的任务应当满足三条性质。

**可行性。** 在当前环境里，应当至少存在一条轨迹，既满足用户 prompt，又遵守系统规范。这就排除了那些依赖不可得的工具、无法访问的知识、不可能的状态转移，或被政策禁止的动作的任务。

**真实性。** 用户 prompt 应当像一个用户会在目标环境里合理提出的请求。可执行行为的空间通常远大于真实工作流的空间。

**难度。** 用于训练时，任务应当暴露当前 agent 的一处短板。那些已经能被稳定解决的任务几乎不提供新的训练信号。因此有用的区域是那些可行且真实、但尚未被稳定解决的任务。

### 校验器

校验器判定最终得到的那条轨迹是否成功完成了任务。它应当满足三条性质。

**一致性。** 它应当与用户 prompt、系统规范以及任务专属的环境状态相一致。

**健全性。** 它应当拒绝那些未满足任务或违反相关限制的轨迹。

**完备性。** 它应当接受所有有效的解，而不是把某一条特定的参考轨迹写死进去。

这些性质在训练期间有直接影响：宽松的校验器可能给错误行为发奖励，而过于苛刻的校验器则可能惩罚有效的解。

## 概览

给定一个环境和一个目标模型，AutoSynthData 生成由系统规范、用户 prompt 和校验器组成的训练任务。生成的任务扎根于该环境，并被挑选出来以给当前模型提供有用的训练信号。

[![figure-01](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/sM50frTSx9Q7Yyh6UNcGz.png)](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/sM50frTSx9Q7Yyh6UNcGz.png)

AutoSynthData 先用诊断性任务在该环境中评测目标模型，并识别它在完成时比较吃力的任务中存在哪些模式。一个更强的 teacher 帮助刻画这些任务里哪些是可解的、成功的行为长什么样。AutoSynthData 把由此得到的能力缺口转成新的可执行任务，在环境中逐一检查每个任务，并把被接受的样本用于 post-training。对更新后的模型再做评测，能揭示还剩下哪些缺口，并可以为下一轮生成提供指引。

[![figure-02](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/huMlVCBcc-IseCIk5uEIJ.png)](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/huMlVCBcc-IseCIk5uEIJ.png)

## 从模型失败到课程

AutoSynthData 利用在目标环境中的评测运行来识别模型下一步需要学什么。在我们的 EnterpriseOps Gym 实验里，我们让目标模型和一个更强的 teacher 都跑这些评测任务。我们检查这些运行，以识别：

- 被考察的能力；
- 涉及的工具与工作流结构；
- 目标模型在哪里失败，teacher 又是如何成功的；
- 正确的最终状态必须满足的性质；
- 在不改变所考察能力的前提下可以变化的维度。

我们把这些发现提炼成清洗过的能力规范卡片。评测任务指引模型该学什么，但生成器不会收到它们原始的 prompt、实体、轨迹或校验器细节。它收到的是卡片，并用它们来创建带有不同 prompt、状态和求解路径的新任务。

[![figure-03](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/ZwShYC2FDYFXU9yR9yz1t.png)](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/ZwShYC2FDYFXU9yR9yz1t.png)

## 生成任务并规模化

识别出一个能力缺口只告诉我们要教什么，但训练需要许多各不相同、又能锻炼该能力的任务。AutoSynthData 用规范卡片来生成这些任务。

假设目标模型在完成下面这条工作流的任务上很吃力：

[![figure-04](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/UCTRFFZ7ttq6JEXZr5_Qi.png)](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/UCTRFFZ7ttq6JEXZr5_Qi.png)

生成器会创建锻炼这条工作流的新任务，改变实体、初始环境状态、工作流组成、工具组合、措辞和难度。更强的 teacher 随后为每个任务演示一条成功轨迹。就 supervised fine-tuning（SFT）而言，这些演示教会目标模型如何在新情境中运用这项能力。

AutoSynthData 分两个阶段构建数据集：先生成并校验核心样本，再把它们扩展为全新的变体。

### Target

target 阶段依据能力规范生成训练样本的核心集合。多个 worker 并行生成彼此独立的任务，做完一个就接下一个新的 target。每个候选都要经过校验、执行、solver 评测和修复才会被接受。产出的是一批围绕「目标模型需要学什么」构建、经过把关的样本。

### Multiply

multiply 阶段通过为已接受的 target 样本创建全新变体来扩充数据集。每个变体都有自己的用户请求、环境状态、实体配置、参考轨迹和校验器，并且必须通过同样的校验与执行检查。一个 multiply 出来的样本不能作为另一个 multiply 样本的种子。这把扩张锚定在经过把关的 target 集合上，并限制了跨世代的漂移。

### 实现细节

为了支撑这两个阶段，AutoSynthData 把生成控制与环境专属的执行分离开。一个共享的 controller 协调生成、质量控制、覆盖率与数据集构建；一个 adapter 则负责环境执行、任务与状态管理、参考轨迹回放、确定性校验、solver 执行和任务画像。

并行的 target 生成与 multiply 合起来，提供了一条通往训练规模数据的路径。它们的用处取决于施加在每个候选上的检查：任务必须可执行，解法必须行得通，校验器必须能区分成功与失败。

[![figure-05](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/zUTtl1ILl-fTtA-0RZdgV.png)](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/zUTtl1ILl-fTtA-0RZdgV.png)

## 高质量合成数据不止靠生成

生成一个看起来合理的请求，还不足以产出有用的训练数据。某个任务在目标环境里可能根本不可能完成，它的参考解在执行时可能失败，或者它的校验器可能给错误的最终状态发奖励。AutoSynthData 在接受一个任务用于训练之前会检查这些性质。

AutoSynthData 在两个层面审查质量：单个候选必须通过校验，批次则必须提供有用的覆盖率与多样性。

### 样本级校验与修复

每个候选在进入训练数据集之前，都要过一道质量控制循环。我们从 solver 评测开始，用它来度量难度。在本文采用的配置里，我们偏向这样的任务：目标模型在三次尝试中至多解出一次，而更强的 solver 在三次尝试中至少解出两次。候选还要经过正向与负向校验，以及一个次数有上限的修复流程。

[![figure-06](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/r3nXamYF6OEI2ezj7MX78.png)](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/r3nXamYF6OEI2ezj7MX78.png)

#### 正向校验

正向闸门问的是：预设的解法能解掉生成出来的这个任务吗？

流水线在目标环境里执行参考轨迹，并把得到的状态与候选的校验器做比对检查。这能暴露 prompt、初始状态、解法和成功判据之间的不匹配。

#### 负向校验

负向闸门问的是：相关的错误结果会不通过吗？

例如，它可以改动预期结果的若干部分，并确认那些状态不再能通过校验。这能揪出那些不要求预期行为就给成功的弱校验器。

#### 批评与修复

失败的候选在被丢弃之前会先交给一个 critic。critic 检查这个样本以及它的失败，寻找不一致的状态、不可能完成的流程、错误的任务构造、糟糕的参考轨迹、薄弱的校验逻辑，或者与目标能力不符之处。critic 的发现用于指导修复，重试次数设有固定上限：

```
candidate
↓
failure
↓
critique / diagnosis
↓
targeted repair
↓
run the gates again
↓
accept or retry
```

修复后的任务必须重新通过相关检查。诊断指向的是对既有候选的修复，而不是要求从头重新生成。

通过这些检查让一个样本具备进入训练的资格，但单个都合格的样本仍然可能组成一个重复或失衡的数据集。因此 AutoSynthData 也在批次层面审查生成。

### 批次级审查

一个批次可能过度呈现某几个简单的任务族、漏掉某项能力，或者反映出把过多生成精力花在了低产出的模式上。

一次元审查会检查每个批次里被接受与被拒绝的样本，以及整体的生成行为。它要问：

- 哪些任务族占比过高，哪些能力维度缺失？
- 是不是同一类样本在反复出现？
- 是否某些特定的 target 一直在生成失败？
- 批评中是否出现了系统性的问题？
- 下一批应当改变哪些指引？

controller 跟踪已接受数据集中的覆盖情况，减少在过度呈现区域的生成，把更多工作导向缺口。当某个区域反复产出糟糕的候选时，批评与元审查会指引生成策略的调整。这些调整在可用的生成预算与数据集规模要求之内，平衡有用的学习信号、任务质量、覆盖率、多样性与低冗余。

这些反馈循环合起来，既改善单个任务，也改善它们所构成的数据集：样本级检查指导候选修复，批次级审查则指引后续的生成。

## 推动训练前沿

有用的训练分布会随着模型进步而变化。AutoSynthData 把合成数据生成看成一次搜索：寻找靠近目标模型能力边界的任务——难到足以暴露短板，但又可解到足以让 teacher 提供可靠的演示。

post-training 之后，我们在同一个环境里评测更新后的模型。它现在能够稳定解决的任务，对下一轮训练的价值就较低；持续的失败则指向仍然需要关注的能力。这些结果可以指引下一轮生成。

[![figure-07](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/ONKQXJ1u9buDLEa-AuXMo.png)](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/ONKQXJ1u9buDLEa-AuXMo.png)

我们的实验聚焦 SFT，但同一套机制也能支撑强化学习（RL）：生成那些挑战当前 policy、同时又能提供可靠学习信号的任务，训练，然后让生成目标随更新后的 policy 一起移动。我们计划在 SFT 之外检验这条不断移动、按难度校准的前沿。

## EnterpriseOps Gym 实验

我们用 EnterpriseOps Gym 来检验这套方法能否提升模型在有状态企业环境任务上的表现。我们在 Gym 的 Hybrid 和 ITSM 环境中生成训练任务，用被接受的样本对目标模型做 fine-tune，并评测得到的 checkpoint。

### Hybrid

我们在 EnterpriseOps Gym 的 Hybrid 领域上测试了这条流水线，用 [Gemma-4-26B-A4B-it](https://huggingface.co/google/gemma-4-26B-A4B-it) 作为目标模型，用 [Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B) 作为 teacher。

AutoSynthData 在约 18 小时内生成了 2,000 个合成训练样本。我们在这个数据集上对 Gemma 做了 fine-tune，并在基准上评测得到的 checkpoint。最好的 checkpoint 是 epoch 5。

### Hybrid 结果

合成数据 SFT 得到的 checkpoint 把平均 Pass@1 提高了 7.2 个百分点，即 35% 的相对提升，并把校验器通过率从 63.01% 提升到 68.55%。它补上了 Gemma 与参照模型之间原本 Pass@1 差距的 59%。

[![figure-08](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/D2CdcykJInh82mYAMGz3I.png)](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/D2CdcykJInh82mYAMGz3I.png)

这些训练任务是从能力规范新生产出来的；生成器没有收到原始的评测任务。该结果展示的是在 EnterpriseOps Gym Hybrid——也就是本次实验所用的环境——上的提升。

### ITSM

我们也把 AutoSynthData 用在 EnterpriseOps Gym 的 ITSM 领域，目标模型是 Gemma-4-26B-A4B-it，teacher 是 [DeepSeek-V4.1-Flash](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash)。AutoSynthData 在 66 小时内生成了 1,994 个合成训练样本。生成耗时比上文描述的那次在其之后进行的 Hybrid 运行更长，主要是因为 ITSM 那次运行用了更大的 teacher 模型，而且它发生在那些提升吞吐量的流水线优化之前。

在 ITSM 上，合成数据 SFT 把平均 Pass@1 从 18.77% 提升到 27.18%，说明这套方法在第二个领域同样能提升性能。

[![figure-09](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/3G6bJhA0JKZMJdiwfeHYs.png)](https://cdn-uploads.huggingface.co/production/uploads/66a41f3c1d52bffc13c285a5/3G6bJhA0JKZMJdiwfeHYs.png)

## 闭环

对训练最有用的任务同时取决于环境，以及在其中工作的模型。AutoSynthData 用模型的失败来选择该生成什么，依据环境校验新任务，并让这些任务可用于 post-training。我们在 EnterpriseOps Gym 上的结果在一个受控设置中展示了这一做法的价值。随着模型变化，同一套流程可以把焦点放在仍然剩下的缺口上。
