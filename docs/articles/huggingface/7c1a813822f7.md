# AWS 上基础模型训练与推理的构建模块

长期以来，基础模型领域的"scaling（规模化）"基本只有一个含义：在预训练上投入更多算力，能力自然水涨船高。这一直觉得到了 [Kaplan et al. (2020)](https://arxiv.org/abs/2001.08361) 等实证工作的支持——他们报告了随**模型参数**、**数据集规模**和**训练算力**增大，损失呈可预测的幂律下降。在实践中，这些趋势支撑了对大规模加速卡容量以及配套分布式基础设施的持续投入，以保持其高效利用率。但前沿已经演进——scaling 不再是单条曲线。NVIDIA 的"从一个到三个 scaling law"的说法很好地强调了这一点：除预训练外，性能越来越多地通过**后训练**（如监督微调 SFT 和基于强化学习 RL 的方法）以及**测试时算力**（"长思考"、搜索/验证、多样本策略）获得规模化。

[![3-Scaling-Laws-Chart-1280x720](https://cdn-uploads.huggingface.co/production/uploads/64d6b270c2eedf9af82baa23/X5ZiXBoPmJzcDhaiL_Zkf.jpeg)](https://cdn-uploads.huggingface.co/production/uploads/64d6b270c2eedf9af82baa23/X5ZiXBoPmJzcDhaiL_Zkf.jpeg)

> 图：改编自 "AI's Three Scaling Laws, Explained"（NVIDIA Blog）。

合在一起，这些 scaling 机制让基础模型生命周期——预训练、后训练、推理——走向趋同的基础设施需求：紧耦合的加速卡算力、高带宽低延迟网络、分布式存储后端。它们也抬升了两类东西的重要性：资源管理的编排调度，以及应用级与硬件级的可观测性——用以维持集群健康、在规模化环境下诊断性能病灶。

另一个关键趋势是，基础模型生命周期越来越依赖一个横跨模型开发框架、集群资源管理和运维工具的开源软件（OSS）生态。在集群层，资源管理通常由 [Slurm](https://slurm.schedmd.com/documentation.html) 和 [Kubernetes](https://kubernetes.io/docs/) 这类系统承担。模型开发与分布式训练通常实现在 [PyTorch](https://pytorch.org/) 和 [JAX](https://jax.readthedocs.io/) 等框架中。监控与可视化——也就是可观测性——通常用 [Prometheus](https://prometheus.io/docs/introduction/overview/) 采集指标、用 [Grafana](https://grafana.com/docs/grafana/latest/) 做可视化和告警，作为坐落在基础设施与资源管理之上的运维层。图 1 展示了这种分层架构：硬件基础设施支撑资源编排，资源编排进而使能 ML 框架，可观测性贯穿所有层。

[![Building Blocks Intro](https://cdn-uploads.huggingface.co/production/uploads/64d6b270c2eedf9af82baa23/QSBYRirLS8pkgJK3rvqMF.png)](https://cdn-uploads.huggingface.co/production/uploads/64d6b270c2eedf9af82baa23/QSBYRirLS8pkgJK3rvqMF.png)

*图 1：基础模型训练与推理开源软件栈的分层架构*

本文面向参与基础模型训练与推理、尤其关注基于 OSS 框架构建工作流的 ML 工程师与研究者。它分析 AWS 基础设施——多节点加速卡算力、高带宽低延迟网络、分布式共享存储及相关托管服务——如何在基础模型全生命周期中与常见 OSS 技术栈互动。首要目标是提供理解系统瓶颈与规模化特性的技术基础，覆盖预训练、后训练与推理。作为开篇，本文呈现总体系统架构，重点放在 AWS 基础设施组件与支撑大规模分布式训练/推理的 OSS 工具之间的集成点上。

## AWS 构建模块

本系列的后续内容考察这一分层架构在 AWS 上如何实现，依次覆盖基础设施、资源编排、ML 软件栈和可观测性。以下小节预览每一层。

### 基础设施：计算、网络与存储

如图 1 所示，基础设施由三个耦合的构建模块支撑：大显存的加速计算、用于集合通信的宽带互连，以及面向数据与 checkpoint 的可扩展分布式存储。

加速计算是大规模基础模型预训练、后训练与推理的底座。AWS 提供多代 NVIDIA GPU，即 [Amazon EC2 加速计算实例](https://aws.amazon.com/ec2/instance-types/accelerated-computing/)，包括 Amazon EC2 P 实例系列。[P5 实例系列](https://aws.amazon.com/ec2/instance-types/p5/)含 8 张 [NVIDIA H100](https://www.nvidia.com/en-us/data-center/h100/) 的 p5.48xlarge、面向小规模负载单卡 H100 的 p5.4xlarge，以及配备 [NVIDIA H200](https://www.nvidia.com/en-us/data-center/h200/) 的 p5e.48xlarge/p5en.48xlarge 变体。[P6 实例系列](https://aws.amazon.com/ec2/instance-types/p6/)引入 [NVIDIA Blackwell B200](https://www.nvidia.com/en-us/data-center/dgx-b200/) 架构的 p6-b200.48xlarge 和 [Blackwell Ultra B300](https://developer.nvidia.com/blog/inside-nvidia-blackwell-ultra-the-chip-powering-the-ai-factory-era/) 的 p6-b300.48xlarge。纵观这些代际，主要的规模化维度是峰值 Tensor 吞吐、HBM 容量与带宽，以及互连带宽（节点内与节点间）。

随着模型规模变大，单步耗时往往由集合通信和内存搬运而非原始算力吞吐主导，因此需要显式统计 scale-up 与 scale-out 带宽。在多卡实例中，GPU 通信横跨两种体制。**内部 scale-up（NVLink/NVSwitch）**提供节点内高带宽、低延迟的 GPU 到 GPU 连接，使 all-reduce、all-gather 等集合操作无需经过主机网络栈。**外部 scale-out（EFA）**提供跨节点的 OS-bypass 网络，AWS 用它作为构建 [Amazon EC2 UltraClusters](https://aws.amazon.com/ec2/ultraclusters/) 的积木——通信密集的集合操作可横跨数千台实例。下表汇总这些实例类型的关键规格：

| [p5.4xlarge](https://aws.amazon.com/ec2/instance-types/p5/) | H100 | 1 | 80 GB HBM3 | — | — | v2 | 12.5 GB/s |

| [p5en.48xlarge](https://aws.amazon.com/ec2/instance-types/p5/) | H200 | 8 | 1,128 GB HBM3e | 第4代 | 7.2 TB/s | v3 | 400 GB/s |

Elastic Fabric Adapter（EFA）是 Amazon EC2 的一种网络接口，使用 [Scalable Reliable Datagram（SRD）](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html)协议提供 OS-bypass 远程直接内存访问（RDMA）能力。通过让应用经 Libfabric API 直接与网络设备通信、绕过操作系统内核，EFA 降低了延迟、提升了分布式训练中集合操作的吞吐。

不同实例系列提供多代 EFA。Amazon EC2 P5 与 P5e 实例配备 EFA 第 2 代（EFAv2）。[P5en 实例上的 EFA 第 3 代（EFAv3）较 EFAv2 将包延迟降低约 35%](https://aws.amazon.com/blogs/aws/new-amazon-ec2-p5en-instances-with-nvidia-h200-tensor-core-gpus-and-efav3-networking/)。[P6 实例上的 EFA 第 4 代（EFAv4）在 EFAv3 基础上再将集合通信性能提升 18%](https://aws.amazon.com/blogs/machine-learning/aws-ai-infrastructure-with-nvidia-blackwell-two-powerful-compute-solutions-for-the-next-frontier-of-ai/)。

在规模化下，分布式训练（流式读取语料、写入数 TB checkpoint）与大规模推理（暂存权重、管理 KV cache 增长）都需要分层存储体系：本地 NVMe SSD 放热数据，Lustre 提供共享高吞吐访问，[Amazon S3](https://aws.amazon.com/s3/) 负责持久化。

在本系列主打的多卡实例中，本地 NVMe 以**实例存储（临时性）**提供，**原始容量 30.72 TB（8 × 3.84 TB NVMe SSD）**；参见 [EC2 加速计算实例存储规格](https://docs.aws.amazon.com/ec2/latest/instancetypes/ac.html#ac_instance-store)。

[Lustre](https://www.lustre.org/about/) 是开源、POSIX 兼容的分布式文件系统，在高性能计算（HPC）中广泛使用，为众多客户端提供共享命名空间和高聚合吞吐。[Amazon FSx for Lustre](https://aws.amazon.com/fsx/lustre/) 以全托管服务形式提供 Lustre，作为并行文件系统可达每秒 TB 级吞吐、百万级 IOPS 和亚毫秒延迟。Data Repository Association 特性支持与 [Amazon S3](https://aws.amazon.com/s3/) 集成，实现训练数据集的懒加载和 checkpoint 自动导出以获得持久性。

在集群规模上，这些实例部署于 [Amazon EC2 UltraClusters](https://aws.amazon.com/ec2/ultraclusters/)：在单个可用区内部署数千台加速实例为一个位置紧密的集群，并用 PB 级无阻塞网络互联。

对于每步通信强度高的负载（如 MoE 模型的专家并行，all-to-all 的 token 分发横跨大量 GPU），NVLink 域的大小可能成为一阶约束。作为内部 scale-up 轴的延伸，扩大 NVLink 域能减少性能关键通信被迫离开 NVLink 结构的频率。

[Amazon EC2 UltraServers](https://aws.amazon.com/ec2/ultraservers/) 通过专用加速卡互连把多台组件实例连接起来，将 NVLink 域扩展到单台 EC2 实例之外。AWS 报告 [P6e-GB200 UltraServers](https://aws.amazon.com/about-aws/whats-new/2025/07/amazon-p6e-gb200-ultraservers-gpu-performance-ec2/) 基于 [NVIDIA GB200 NVL72](https://www.nvidia.com/en-us/data-center/gb200-nvl72/) 平台构建，在一个 NVLink 域内最多暴露 72 颗 Blackwell GPU 和 13.4 TB 聚合 HBM3e。在更大规模时，跨 UltraServer 作业仍以 EFA 作为跨节点网络结构，但增加域内 GPU 数量可以减少性能关键通信需要离开 NVLink 结构的频率。

这些系统由 NVIDIA Grace–Blackwell 超级芯片构成，通过缓存一致的 [NVLink-C2C](https://developer.nvidia.com/blog/nvidia-grace-hopper-superchip-architecture-in-depth/) 将 Grace CPU 内存与 Blackwell GPU 的 HBM 耦合，可以跨 CPU 挂载内存和 GPU 挂载内存直接访问，无需显式的主机-设备拷贝。实践中，这能扩展 GPU 工作负载的可用内存（例如把较冷的模型状态或 KV cache 放进 CPU 挂载内存），同时避免 PCIe 量级的拷贝开销——尽管其延迟高于、带宽低于本地 HBM。

P6e-GB200 UltraServers 的组件实例类型是 [`p6e-gb200.36xlarge`](https://aws.amazon.com/ec2/instance-types/p6/)，提供 4 颗 GPU 和 Elastic Fabric Adapter (EFA) v4 网络。下表汇总单实例与整 UltraServer 配置。

### 资源编排：Slurm 与 Kubernetes

当训练横跨数百乃至数千加速卡时，手工资源管理变得不可行。例如一个需要 512 块 GPU 的训练任务必须同时联合调度 64 台八卡节点（P 实例），并在完成或失败时原子性地释放资源。[Slurm](https://slurm.schedmd.com/) 和 [Kubernetes](https://kubernetes.io/) 都以控制平面架构解决这一挑战：集中式调度器维护集群状态并做出分配决策，工作节点执行被分派的工作负载。

[![slurm-k8s-highlevel-arch](https://cdn-uploads.huggingface.co/production/uploads/64d6b270c2eedf9af82baa23/rYM10isubva2wx3jIVeZm.png)](https://cdn-uploads.huggingface.co/production/uploads/64d6b270c2eedf9af82baa23/rYM10isubva2wx3jIVeZm.png)

*图 2：AWS 上基于 Slurm 与基于 Kubernetes 资源编排的高层架构*

[Slurm](https://slurm.schedmd.com/)（Simple Linux Utility for Resource Management）是 HPC 中占主导地位的工作负载管理器，建立在模块化插件架构之上，调度算法、拓扑模型、资源类型和记账后端都可独立配置。其调度模型把资源组织为分区（partition，节点的逻辑分组），通过 `sbatch` 接收作业提交，通过 `srun` 在分配到的节点上同步启动并行任务。对分布式训练至关重要的是，Slurm 以作业粒度调度——整个多节点作业被原子分配后才启动任何任务。[回填调度器（backfill scheduler）](https://slurm.schedmd.com/sched_config.html)在空闲槽位启动低优先级作业而不拖延高优先级作业；[多因子优先级](https://slurm.schedmd.com/priority_multifactor.html)系统权衡公平份额用量、作业等待时长和 QOS 档位来决定跨租户排队顺序。Slurm 还支持[拓扑感知放置](https://slurm.schedmd.com/topology.html)，通过建模网络交换机层次的插件实现——在 AWS 上即编码 EFA 网络结构拓扑，让作业落在交换机跳数最少的节点上——以及经由 Generic Resource（GRES）接口的原生 [GPU 调度](https://slurm.schedmd.com/gres.html)，可追踪 GPU 类型并强制设备亲和性。

AWS 为 Slurm 编排提供多种部署选择。[AWS ParallelCluster](https://github.com/aws/aws-parallelcluster) 是开源集群管理工具，自动化在 EC2 上部署 Slurm 集群，处理头节点开通、计算舰队扩缩容和共享存储集成。[AWS Parallel Computing Service (PCS)](https://aws.amazon.com/pcs/) 则提供托管控制平面。针对分布式训练负载，[Amazon SageMaker HyperPod](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod.html) 支持 Slurm 模式并附加为大规模训练定制的能力，例如[持续节点健康监控](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-resiliency-slurm-cluster-health-check.html)和[作业自动恢复](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-resiliency-slurm-auto-resume.html)。

[Kubernetes](https://kubernetes.io/) 采用声明式、API 驱动的方式：用户通过资源清单（manifest）声明期望状态，控制器把实际状态调整到与之一致。Kubernetes 在模型部署上表现出色，但其原生调度模型在紧耦合分布式训练上存在几个缺口。Kubernetes 以 pod 粒度调度；没有作业级原子性，多节点训练作业可能部分启动——一些 rank 在跑、另一些卡在 Pending——浪费 GPU 或造成死锁。原生 Kubernetes 也缺乏带优先级回填的批处理队列语义，缺乏对网络结构拓扑（NVLink 域、EFA 互联）的内建感知来放置通信密集的集合操作。

若干 Kubernetes 原生项目在不同层面填补这些缺口。[Kueue](https://kueue.sigs.k8s.io/) 作为默认调度器之上的准入控制器，负责作业级 gang 准入、带层级公平共享的多租户配额和基于优先级的抢占——同时把 pod 放置交给底层调度器。[Volcano](https://volcano.sh/) 和 [NVIDIA KAI Scheduler](https://github.com/NVIDIA/KAI-Scheduler) 走另一条路，替换或增强默认调度器，把 gang 调度与拓扑感知 pod 放置直接整合——Volcano 是通用批调度器，KAI Scheduler 则对 NVLink/NVSwitch 有深度感知、为 GPU 优化的放置。这些层是互补的：Kueue 管理准入与配额策略，同时把准入后的作业交给拓扑感知调度器做放置。

在 AWS 上做基于 Kubernetes 的编排，[Amazon Elastic Kubernetes Service (EKS)](https://aws.amazon.com/eks/) 提供托管 Kubernetes，通过 [NVIDIA device plugin](https://github.com/NVIDIA/k8s-device-plugin) 实现 GPU 调度。Amazon SageMaker HyperPod 也支持 [EKS 模式](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks.html)，把 Kubernetes 编排与 HyperPod 的训练特有能力结合。HyperPod EKS 在 EKS 之上扩展了为大规模基础模型训练设计的特性。[任务治理（Task governance）](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-eks-operate-console-ui-governance-policies.html)提供跨团队的算力分配与策略执行，集成托管的 [Kueue](https://kueue.sigs.k8s.io/) 做准入控制、[Karpenter](https://karpenter.sh/) 做即时节点开通。[Checkpointless training](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-eks-checkpointless.html)解决了传统基于 checkpoint 容错的恢复延迟。它不再周期性地把模型状态序列化到共享存储，而是维持 GPU 之间点对点的持续状态复制。发生故障时，存活节点通过 EFA 通信重建丢失的状态，而不是从 FSx for Lustre 或 S3 读取数 TB 的 checkpoint。[弹性训练（Elastic training）](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-eks-elastic-training.html)让作业根据资源可用性自动扩缩。当更多加速卡可用（例如其他作业完成或新开通容量），弹性作业可扩展利用它们；当更高优先级负载需要资源时，作业可收缩且保持训练进度不丢。

### ML 软件栈

分布式训练和推理涉及多个必须正确配置并协同的软件层。一个有用的模型是把运行时栈分为五层，从贴近硬件的组件（它们必须先工作正常，上层才有的跑）到框架级抽象（它们决定程序员生产力和模型吞吐）：硬件使能、加速卡运行时与数学库、通信基座、ML 框架、分布式训练/推理框架。

#### 硬件使能：内核驱动

在最底层，Linux 内核驱动提供直接硬件访问。NVIDIA GPU 驱动暴露算力并支持 [GPUDirect RDMA](https://docs.nvidia.com/cuda/gpudirect-rdma/index.html)，实现 GPU 与网卡之间的直接数据传输。[GDRCopy](https://github.com/NVIDIA/gdrcopy) 驱动（`gdrdrv`）支持低延迟的 CPU 发起的 GPU 内存双向拷贝，被 NCCL 用于小消息传输。[EFA 驱动](https://github.com/amzn/amzn-drivers)通过 [libfabric](https://github.com/ofiwg/libfabric) API 提供 OS-bypass 网络，[Lustre 客户端](https://www.lustre.org/)驱动则提供对 FSx for Lustre 并行文件系统的 POSIX 访问。

#### 加速卡运行时、编译器与 kernel 库

[CUDA](https://developer.nvidia.com/cuda-toolkit) 平台提供 GPU 计算的编程模型与运行时。基于 CUDA 编译的应用可以在 NVIDIA GPU 上启动 kernel、管理设备内存并协调多设备执行。当前版本为 CUDA Toolkit 13.x，支持 Blackwell 架构（计算能力 10.x）。

现代训练与推理性能越来越多地由专门的优化库和自定义 kernel 驱动，而非仅靠厂商的通用原语。[FlashAttention](https://github.com/Dao-AILab/flash-attention) 这类 kernel 把注意力融合成单次内存高效的遍历，削减 HBM 流量、提升吞吐。许多团队还针对自己的确切模型编写形状与精度特化的融合 kernel（如 layernorm/残差/激活、量化 GEMM、MoE 分发、KV-cache 操作）。这得益于可编程工具链，如 [Triton](https://triton-lang.org/)（Python GPU kernel 编译器）和 NVIDIA 的 [CuTe](https://github.com/NVIDIA/cutlass/blob/1d9e1f6d7a1e820a884765cf3dcfda05c95f39d1/media/docs/cpp/cute/00_quickstart.md)（张量布局与 warp 级 DSL），而 [CUTLASS](https://github.com/NVIDIA/cutlass) 等库提供高度优化的 GEMM 与融合构件。实践中，这层 kernel 与编译器往往与 ML 框架同等程度地决定端到端性能。

#### 通信基座：NCCL 与传输插件

多 GPU 训练依赖高效的集合通信。[NVIDIA Collective Communications Library (NCCL)](https://developer.nvidia.com/nccl) 实现集合操作——all-reduce、all-gather、reduce-scatter、all-to-all、broadcast 以及点对点收发——采用拓扑感知算法：节点内走 NVLink，节点间走网络传输。NCCL 动态探测通信拓扑，按消息大小与可用带宽选择环形或树形算法。数据并行与张量并行策略主要依赖 all-reduce 和 all-gather；而带专家并行的混合专家（MoE）模型依赖 all-to-all 集合在各 GPU 之间路由 token：dispatch all-to-all 把每个 token 发给承载其分配专家的 GPU，combine all-to-all 把专家输出送回原发 GPU（[NVIDIA Developer Blog](https://developer.nvidia.com/blog/accelerating-large-scale-mixture-of-experts-training-in-pytorch/)）。由于专家并行组内每块 GPU 都要与其他所有 GPU 交换数据，all-to-all 通信量随专家数增长，在高度专家并行时可能成为主导瓶颈。

在 AWS 上，NCCL 的节点间通信由 [aws-ofi-nccl](https://github.com/aws/aws-ofi-nccl) 插件启用，它把 NCCL 的传输 API 映射到 [libfabric](https://github.com/ofiwg/libfabric) 接口。这样 NCCL 无需应用改动即可利用 EFA 的 OS-bypass 与 Scalable Reliable Datagram (SRD) 协议。

对推理负载，集合操作并不能涵盖所有通信模式。分离式（disaggregated）推理架构——把 prefill 与 decode 阶段拆到不同 GPU 池——需要高效的点对点数据搬运，尤其是跨实例传输 KV cache 状态。[NVIDIA Inference Xfer Library (NIXL)](https://github.com/ai-dynamo/nixl) 针对这一需求，提供跨内存层级（HBM、DRAM、NVMe、分布式存储）和互连（NVLink、InfiniBand、Ethernet）点对点传输的统一 API。NIXL 与 NVIDIA Dynamo 等推理框架集成，支持 UCX、GPUDirect Storage 等后端。

#### ML 框架：PyTorch

基础模型开发两大主流框架是 [PyTorch](https://pytorch.org/) 和 [JAX](https://jax.readthedocs.io/)。JAX 通过 XLA 走 SPMD（Single Program Multiple Data）路线：同一程序跨设备执行，自动做数据分布与集合原语降级。本文聚焦 PyTorch——它在开源生态中采用更广，也是下文讨论的分布式训练/推理框架的基础。

PyTorch 提供带 GPU 加速的张量计算、自动微分和灵活的 eager 执行模型。对分布式负载，PyTorch 的 `torch.distributed` 模块提供核心原语：集合通信用的进程组，以及分布式数据并行抽象，包括 [Distributed Data Parallel (DDP)](https://docs.pytorch.org/docs/stable/nn.html#torch.nn.parallel.DistributedDataParallel) 和 [Fully Sharded Data Parallel (FSDP2)](https://docs.pytorch.org/docs/stable/distributed.fsdp.fully_shard.html)。DDP 把模型复制到各 GPU 并通过 all-reduce 同步梯度；FSDP2 借鉴 ZeRO 算法，把参数、梯度和优化器状态分片到各 worker，使超过单卡显存的模型也能训练。

#### 分布式训练与推理框架

最顶层是在 PyTorch 之上构建、为规模化分布式训练与推理提供更高级抽象的框架。训练方面，三类框架占据复杂度-性能权衡的不同点位。举几个例子：

[Hugging Face Transformers](https://huggingface.co/docs/transformers/) 提供 `Trainer` 类，通过 [Accelerate](https://huggingface.co/docs/accelerate/) 内建分布式训练支持，把 DDP、FSDP、DeepSpeed 都抽象掉。这条路线以易用性和广泛的模型兼容为先，适合配置简单性比极限吞吐更重要的微调与中等规模训练。

[NVIDIA Megatron Core](https://developer.nvidia.com/megatron-core) 瞄准规模下的最大效率，实现 3D 并行（张量、流水线、专家并行），并包含经 Transformer Engine 的 FP8 混合精度等优化。[NeMo Framework](https://docs.nvidia.com/nemo-framework/user-guide/latest/) 构建在 Megatron Core 之上，提供预训练与微调的端到端工作流。

对于人类反馈强化学习（RLHF）及相关后训练方法，[veRL](https://github.com/volcengine/verl)（Volcano Engine Reinforcement Learning）提供了一个灵活框架，实现了 PPO、GRPO、REINFORCE++ 等算法。veRL 的 HybridFlow 架构允许在同一作业中混用训练后端（FSDP2、Megatron）与推理引擎（vLLM、SGLang），通过 actor 与 rollout 组件在内存中共享模型权重，避免权重同步开销。

推理服务方面，[vLLM](https://github.com/vllm-project/vllm) 实现了 PagedAttention，把 KV cache 按分页虚拟内存管理，减少碎片、支持更大批。[SGLang](https://github.com/sgl-project/sglang) 进一步带来 RadixAttention 实现跨请求的前缀自动复用、把 CPU 调度与 GPU 计算重叠的零开销批调度器，以及按预测缓存命中率路由请求的缓存感知负载均衡器。两个框架都支持张量并行以托管超出单卡显存的模型，也都与 [NVIDIA Dynamo](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/) 集成，支持把 prefill 与 decode 分离的分离式服务架构。

### 可观测性

可观测性是大规模调试和运维分布式训练系统的前提。当训练作业停滞或吞吐下滑时，从业者需要看清根因是硬件故障、网络拥塞、存储瓶颈还是应用层低效。在本讨论的基础设施规模下——数千 GPU、PB 级互连带宽、TB 级 checkpoint 数据——挑战从简单监控转向系统化的遥测采集、存储与分析。可观测性覆盖三类遥测：基础设施指标（GPU、网络、存储）、工作负载指标（训练吞吐、队列延迟），以及用于主动故障检测的告警。

#### 核心栈：Prometheus 与 Grafana

Kubernetes 与 HPC 环境可观测性的事实标准，是 [Prometheus](https://prometheus.io/docs/introduction/overview/) 采集指标配合 [Grafana](https://grafana.com/docs/grafana/latest/) 做可视化与告警。Prometheus 采用拉取模型，周期性抓取各指标导出器（exporter）暴露的 HTTP 端点。采集的指标存入时序数据库（TSDB），通过 PromQL 查询——一门用于聚合、过滤和告警规则求值的灵活查询语言。Grafana 以 Prometheus 为数据源，渲染仪表盘并基于 PromQL 表达式触发告警。

生产部署方面，[Amazon Managed Service for Prometheus (AMP)](https://docs.aws.amazon.com/prometheus/latest/userguide/what-is-Amazon-Managed-Service-Prometheus.html) 提供全托管、Prometheus 兼容的时序数据库，可扩展到每秒摄取数百万样本，运维者无需管理存储、复制或高可用。[Amazon Managed Grafana (AMG)](https://docs.aws.amazon.com/grafana/latest/userguide/what-is-Amazon-Managed-Service-Grafana.html) 提供托管 Grafana 工作区，原生集成 AMP，并通过 IAM Identity Center 使用 AWS 认证。这两个服务消除了运维开销，同时保留与现有 Prometheus exporter 和 Grafana 仪表盘的兼容性。

#### GPU、网络与应用遥测

[DCGM-Exporter](https://github.com/NVIDIA/dcgm-exporter) 以 Prometheus 格式暴露 NVIDIA GPU 指标，包括利用率、显存占用、功耗、温度和 ECC 错误、XID 事件等硬件健康指标。对训练负载，SM 活跃度（`DCGM_FI_PROF_SM_ACTIVE`）通常比基础利用率指标更准确地反映算力效率。

EFA 暴露驱动级统计量（字节数、包数、重传、超时），有助于诊断分布式训练中集合操作的瓶颈。[aws-ofi-nccl](https://github.com/aws/aws-ofi-nccl) 插件把 NCCL 桥接到 libfabric 接口，运维者可以把 EFA 计数器与 NCCL 诊断信息（`NCCL_DEBUG=INFO`）结合，隔离网络层问题。

[Amazon FSx for Lustre](https://aws.amazon.com/fsx/lustre/) 暴露吞吐、元数据延迟等客户端指标；应用级指标（训练侧的 step time、每秒 token 数、loss；推理侧的 TTFT、token 间延迟）可以通过 Prometheus 客户端库导出。

#### GPU 健康监控与告警

主动故障检测能防止硬件问题扩散成训练长时间中断。典型流程是监控 DCGM 健康指标，当错误计数越过阈值就告警。ECC 单比特错误（SBE）少量出现或可容忍，但 SBE 速率加速往往预示双比特错误（DBE）或其他故障。XID 63（行重映射失败）、XID 64（GPU 掉卡）、XID 94/95（已遏制/未遏制错误）通常意味着要立刻替换节点。

[GPU Health - Cluster 仪表盘](https://grafana.com/grafana/dashboards/21645-gpu-health-cluster/)（Grafana 仪表盘 ID 21645）为常见 GPU 错误模式提供了参考可视化。该仪表盘聚合全集群节点的 ECC 错误、XID 事件、温度违规和行重映射状态，让运维者在故障硬件影响训练作业之前就把它揪出来。

## 结语

从单一预训练 scaling law 转向预训练、后训练、测试时算力三个互补机制，并没有分裂基础设施需求——反而强化了它。三种机制都要求紧耦合的加速卡算力、高带宽低延迟网络和可扩展的分布式存储，差别主要在工作负载画像与资源调度模式。

本文呈现了在 AWS 上满足这些需求的四层架构：基础设施构建模块（EC2 P 实例、EFA 网络、分层存储）、资源编排（Slurm 与 Kubernetes，配 SageMaker HyperPod）、ML 软件栈（从内核驱动、CUDA 到 NCCL 再到 PyTorch），以及可观测性（Prometheus、Grafana 与 GPU 健康监控）。每一层都既约束又支撑上层——一个配错的驱动或一条饱和的网络链路，完全能和一套欠优的并行策略一样，把训练拖垮。

理解这些集成点，是在基础模型生命周期中诊断性能瓶颈、做出明智扩容决策的基础。
