# nanoVLM 中从零实现 KV Cache

## TL;DR

## 引言

自回归语言模型*一次采样一个 token* 来生成文本。推理时，模型处理给定输入序列、预测下一个 token、把它追加到序列末尾，如此重复直到满足某个停止条件：

[![diagram for autoregression](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/kv-cache/autoregression.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/kv-cache/autoregression.png)

这种逐步生成天然是串行的：

- 要生成 token t_{i+1}，模型必须考虑从 t_0 到 t_i 的整个序列。上面例子的第一次迭代中，t_{i+1} 会是 `the`，而此前的所有 token t_0 到 t_i 是 `[What, is, in]`。
- 虽然 transformer 内部是并行的，但每一次新预测都要过一遍全部 transformer 层的完整前向，代价是关于序列长度平方级的内存/计算。

这种重复还带来了计算**冗余**。本文我们探索 **KV 缓存**——一种缓解该低效的优化技术。

## 回顾 Transformer 架构

在深入研究缓存之前，先回顾 transformer 模型中注意力是怎么运作的。一个 Transformer 语言模型由堆叠的层组成，每层包含：

- 多头自注意力
- 前馈网络（MLP）
- 残差连接与层归一化

要理解**KV 缓存帮在哪里**，我们聚焦**自注意力**机制，具体到单个注意力头。

用一段简单的 PyTorch 实现走一遍关键计算。

```
import torch

input_seq_length = 5
dim_model = 10

input_ids_emb = torch.randn(input_seq_length, dim_model)
W_q = torch.randn(dim_model, dim_model)
W_k = torch.randn(dim_model, dim_model)
W_v = torch.randn(dim_model, dim_model)

Q = input_ids_emb @ W_q
K = input_ids_emb @ W_k
V = input_ids_emb @ W_v
```

### 自注意力计算

对 T 个输入嵌入组成的序列 X ∈ R^{T×D}，自注意力这样计算：

- Q = X·W_Q，其中 W_Q ∈ R^{D×D_q}
- K = X·W_K，其中 W_K ∈ R^{D×D_k}
- V = X·W_V，其中 W_V ∈ R^{D×D_v}
- 因果掩码 M，防止访问未来的 token

最终输出：

Attention(X;Q,K,V)=softmax(QK⊤⋅M/√dk)⋅V \text{Attention}(X; Q, K, V) = \text{softmax}\left( \frac{QK^\top \cdot M}{\sqrt{d_k}} \right)V Attention(X;Q,K,V)=softmax(dk​​QK⊤⋅M​)V

下面是等价的极简 PyTorch 实现（带因果掩码）：

```
import torch.nn.functional as F
import math

d_k = K.shape[-1]
attention_scores = (Q @ K.T) / math.sqrt(d_k)

# Lower triangular mask to prevent future token access
causal_mask = torch.tril(torch.ones(input_seq_length, input_seq_length))
masked_scores = attention_scores.masked_fill(causal_mask == 0, float('-inf'))

attention_weights = F.softmax(masked_scores, dim=-1)
output = attention_weights @ V
```

## 冗余从哪里冒出来

自回归生成一次产出 token，每一步都会对**整个序列**重新计算 Q、K、V——哪怕前面的 token 根本没变。

```
new_token_emb = torch.randn(1, dim_model)
extended_input = torch.cat([input_ids_emb, new_token_emb], dim=0)

Q_ext = extended_input @ W_q
K_ext = extended_input @ W_k
V_ext = extended_input @ W_v

# (output_ext would be computed using Q_ext, K_ext, V_ext + masking)
```

验证这个冗余：

```
torch.testing.assert_close(K, K_ext[:input_seq_length]) # test pass
torch.testing.assert_close(V, V_ext[:input_seq_length]) # test pass
```

这些检查说明：除最新 token 外，K 和 V 与之前算过的值完全相同。

```
Original (5×5):         Extended (6×6):
■ ■ ■ ■ ■              ■ ■ ■ ■ ■ □
■ ■ ■ ■ ■              ■ ■ ■ ■ ■ □
■ ■ ■ ■ ■    →         ■ ■ ■ ■ ■ □
■ ■ ■ ■ ■              ■ ■ ■ ■ ■ □
■ ■ ■ ■ ■              ■ ■ ■ ■ ■ □
                       □ □ □ □ □ □
```

- **■** = 已计算并复用
- **□** = 不必要地重算

大部分注意力计算都被无谓地重复了。序列越长，这越贵。

## KV 缓存如何修好它

为了消除这个低效，我们用 **KV 缓存**：

- 处理完初始提示后，把每层算出的 key（K）和 value（V）**缓存**起来
- 生成时，**只为新 token 计算** K **和** V，并**追加**到缓存
- 对当前 token 计算 Q，与**缓存的 K 和 V** 一起得到输出

这把生成从"整序列重算"变成轻量的增量更新。

> ✅ 实践中，这个缓存是每层一个字典，键为 "key" 和 "value"，形状各为 (batch_size, num_heads, seq_len_cached, head_dim)。

这正是现代 LLM 能高效生成长序列输出的基础。

## nanoVLM 中的 KV 缓存：从理论到实践

懂了 KV 缓存的原理，来看它在我们的 [nanoVLM](https://github.com/huggingface/nanoVLM) 仓库里怎么落地。这是个理想的试验田——代码极其精简、自包含。

KV 缓存的启用涉及模型的三个关键组件：

- **注意力块**：使用并更新 KV 缓存
- **语言模型**：按层跟踪缓存
- **生成循环**：分离 **prefill**（对输入提示的首次完整前向）与逐次 **decode** 两个阶段

### 1. 在注意力块中更新 KV 缓存

在 `LanguageModelGroupedAttention` 类里，我们修改 `forward`，让它接收并更新 key/value 缓存（`block_kv_cache`）。

以前模型每个生成步都重算 K 和 V。现在只对当前 token 计算 K_new、V_new，并追加到已缓存的值上。

```
def forward(self, x, cos, sin, attention_mask=None, block_kv_cache=None):
    is_prefill = block_kv_cache is None
    B, T_curr, C = x.size()

    # Project inputs to Q, K, V
    q_curr, k_curr, v_curr = project_current_tokens(x)
    q, k_rotated = apply_rotary_pos_embd(q_curr, k_curr, cos, sin)

    if not is_prefill and block_kv_cache['key'] is not None:
        # Append new keys and values to the cache
        k = torch.cat([block_kv_cache['key'], k_rotated], dim=2)
        v = torch.cat([block_kv_cache['value'], v_curr], dim=2)
    else:
        # First pass (prefill) — no cache
        k, v = k_rotated, v_curr

    block_kv_cache = {'key': k, 'value': v}
    return attention_output, block_kv_cache
```

### 2. 跨层跟踪缓存

在 `LanguageModel` 类里，我们引入**逐层缓存跟踪**。`start_pos` 参数帮模型为新产生的 token 计算正确的**旋转位置编码**。

```
def forward(self, x, kv_cache=None, start_pos=0):
    T_curr = x.size(1)
    position_ids = torch.arange(start_pos, start_pos + T_curr, device=x.device)
    cos, sin = self.rotary_embd(position_ids)

    for i, block in enumerate(self.blocks):
        # Pass per-layer KV cache
        x, kv_cache[i] = block(x, cos, sin, attention_mask, kv_cache[i])

    return x, kv_cache
```

- `kv_cache`：一个字典列表，每个 transformer 层一个，存之前的 key 和 value。
- `start_pos`：保证旋转嵌入与当前生成位置对齐。

### 3. 生成循环中的 Prefill 与 Decode

最大的架构改动在 `VisionLanguageModel` 的 `generate()` 方法。

我们把**生成拆成两个阶段**：

- **PREFILL 阶段：** 编码完整 prompt，构建初始缓存。
- **DECODE 阶段：** 用缓存的 key/value 逐个生成 token。

```
PREFILL PHASE (cache construction)
[Prompt: "What is"] → [Transformer] → [Cache: K, V for all layers]

DECODE PHASE (token-by-token)
[Token: "the"] → [Q("the") + cached K/V] → [next token: "?"] → ...
```

对应代码：

```
# PREFILL: Process the input prompt, fill the cache
prompt_output, kv_cache_list = self.forward(
    inputs,
    kv_cache=None,
    start_pos=0
)

# DECODE: Generate one token at a time using cached K/V
for i in range(max_new_tokens):
    next_token = sample_from(prompt_output)

    decode_output, kv_cache_list = self.forward(
        next_token,
        kv_cache=kv_cache_list,
        start_pos=current_position  # updated with each step
    )

    prompt_output = decode_output
```

> 通过分离这两个阶段，我们避免了冗余计算，推理显著提速——长 prompt 下尤其明显。

### 改动总结

| 模块 | 原行为 | 新行为 |
| --- | --- | --- |
| `LanguageModelGroupedAttention.forward` | 每步重算 Q、K、V | 使用并更新 KV 缓存 |
| `LanguageModel.forward` | 没有历史状态记忆 | 跟踪逐层 KV 缓存，处理 `start_pos` |
| `VisionLanguageModel.generate` | 单阶段生成循环 | 拆为 **prefill** 与 **decode** 两阶段 |

## 总结：为什么 KV 缓存重要

| 收益 | 解释 |
| --- | --- |
| **增量增长** | 缓存每来一个新 token 只多一行 |
| **位置感知的解码** | `start_pos` 保证位置编码计算正确 |
| **效率** | 把每 token 推理从平方级降到 O(`seq len`) |

KV 缓存消除了自回归生成中不必要的计算，让推理更快更高效——长序列和实时应用里尤其如此。这是速度与内存之间的权衡，代价是更复杂的代码，以及会限制一些更花哨的推理方案（比如 beam search 等）。KV 缓存是加速 LLM 推理的主流方法，让模型在消费级硬件上跑起来成为可能——现在你也知道它是怎么工作的了！
