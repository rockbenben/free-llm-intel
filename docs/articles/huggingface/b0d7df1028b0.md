# 借助 AI、开放工具与人在回路，每周发布 huggingface_hub

`huggingface_hub` 是 Hugging Face 生态底座的那个 Python 客户端。`transformers`、`datasets`、`diffusers`、`sentence-transformers` 以及几十个其他库都依赖它来和 Hub 对话。我们每不发布一个新版本，就是有一整周的修复和新特性堵在 `main` 上。

很长一段时间里，我们每 4 到 6 周发一版。现在，我们从一个单一的 GitHub Actions workflow 每周发一版。我们用开源工具和开放权重模型构建了它，并在唯一需要判断力的地方保留了人在回路。本文没有任何一处需要厂商合同、闭源模型、或你自己跑不起来的基建。这从一开始就是设计目标——我们想要一个其他维护者可以拿走并改造的工作流。

读完本文，你将获得构建你自己工作流所需的一切。

## 起点

旧流程一部分自动化，大部分靠人。

已经在 CI 里的：

- 推 tag 之后发布到 PyPI。
- 在下游库里开测试分支，pin 住 release candidate。

仍然全靠手工、每一次都是：

- 创建发布分支、改 `__init__.py` 里的版本号、提交、打 tag、推送。
- 盯着下游 CI 跑完并排查失败。
- 通读上一版以来合并的每一条 PR、手写发布说明：按主题分组、带上上下文、语气不能像 `git log` 倾倒。
- RC 期结束后切出稳定版。
- 起草内部 Slack 公告和社交帖子。
- 开发布后的 PR，把 `main` 升到下一个 `dev0`。

给新版本写好说明是重头戏——要聚合几十条主题各异的 PR。技术上没什么难的，但需要几个小时的高度专注。再算上公告，一个 minor 版本轻松耗掉分散在好几天的半天工作量。

## 两类工作

于是我们决定把整个流程理顺。看那张清单，工作分成两半。

有些步骤纯机械，可以自动化：改版本号、提交、打 tag、推送、开下游测试分支、开发布后的 PR。这些不需要任何人思考，只需要每次按正确顺序发生——这正是 CI workflow 擅长的。

剩下的不同。写发布说明、决定突出什么、为人类读者措辞一段公告——这是动脑的活。正是这类判断力让发布多年来保持手工。AI 在这里登场：几秒钟内把一张白纸变成扎实初稿。这里也是我们必须小心的地方——一份看起来自信、实则 subtly 出错的草稿，比没有草稿更糟。

## 设计原则：开放的部件，任何人都可复用

决定修这个问题时，我们先立了一条约束：每个活动部件都必须是任何维护者自己就能跑的东西。不能有不我们能替换的 API 背后的闭源模型，不能有专有发布平台，不能有秘方。

整个技术栈如下：

| 部件 | 作用 |
| --- | --- |
| **GitHub Actions** | 编排整个发布 |
| **[OpenCode](https://opencode.ai/)** | 驱动模型的 agent 运行时 |
| **一个开放权重模型**（目前是 Z.ai 的 [GLM-5.2](https://huggingface.co/zai-org/GLM-5.2)） | 起草发布说明和 Slack 公告 |
| **[HF Inference Providers](https://huggingface.co/docs/inference-providers/index)** | 提供模型服务 |
| **[PyPI Trusted Publishing](https://docs.pypi.org/trusted-publishers/)** | 发布包 |

第二条原则：模型起草，人类定夺。语言模型擅长把三十条简短的 PR 标题变成可读的发布说明，但它不擅长「被无条件信任」。所以整个工作流是人类监督的：模型做第一遍，确定性脚本检查它的产出，任何东西上线前由人审校编辑（下文详述）。

## 流水线导览

完整 workflow 是一个单文件 [`.github/workflows/release.yml`](https://github.com/huggingface/huggingface_hub/blob/main/.github/workflows/release.yml)，由人在 Actions UI 里手动触发。它恰好只接受一个输入：

```
on:
  workflow_dispatch:
    inputs:
      release_type:
        type: choice
        options:
          - minor-prerelease   # cut an RC from main
          - minor-release      # promote the RC to final
          - patch-release      # bugfix on an existing release branch
```

从这里开始，各 job 大体按此顺序执行：

- **Prepare。** 计算下一个版本号，创建或复用发布分支，改 `__version__`，提交、打 tag、推送。
- **Publish to PyPI。** 构建并上传 `huggingface_hub`。并行地，把 `hf` CLI 作为独立 PyPI 包构建上传。
- **Release notes。** 对比自上个 tag 以来的提交范围，从 GitHub API 拉 PR 元数据，让模型起草结构化的 changelog（[这是一份近期的例子](https://github.com/huggingface/huggingface_hub/releases/tag/v1.20.0)）。以*草稿* GitHub release 保存。
- **Downstream test branches。** 对 RC，在 `transformers`、`datasets`、`diffusers`、`sentence-transformers` 里各开一个 pin 住 RC 的分支，让它们的 CI 快速告诉我们有没有破坏东西。
- **Slack announcement。** 阅读发布说明，以我们团队的语气产出内部公告。
- **Archive notes。** 把原始 AI 草稿和人工编辑版并排上传到一个 Hugging Face Bucket。
- **Post-release bump。** 稳定版发布后，在 `main` 上开 PR 升到下一个 `dev0`。
- **Comment on shipped PRs。** 对本次发布包含的每一条 PR 留一条「this shipped in vX.Y.Z」评论。
- **Sync CLI docs。** 向我们 [skills](https://github.com/huggingface/skills) 仓库开 PR，同步重新生成的 `hf` CLI skill 文档。
- **Report to Slack。** 每一步把状态发到 thread 回复；最后一个 job 把根消息更新为 ✅ 或 ❌。

剩下的手工步骤是：审校并发布草稿 release 说明，审校并发送内部 Slack 消息。这两步就是我们想要人在回路的位置。

## 信任但验证：人在回路的核心

大家都担心的 AI 生成发布说明的失败模式在这里：模型悄悄漏掉一条 PR，或凭空捏造一条不属于本次发布的。差不多对的 changelog 比没有 changelog 更糟，因为没人会再去核对。

我们不相信生成出的发布说明第一次就完整，而是确定性地验证它。模型运行之前，一个 Python 脚本取回属于本次发布的所有 PR，存为 ground truth。

```
# Deterministic: extract PR numbers from squash-merge commits in the range.
PR_NUMBER_PATTERN = re.compile(r"\(#(\d+)\)$")

pr_numbers = [
    int(m.group(1))
    for commit in commits_since_last_tag
    if (m := PR_NUMBER_PATTERN.search(commit.title))
]
save_manifest(pr_numbers)  # the source of truth
```

然后模型基于清单起草说明。完成后，把它的输出与最初的 PR 列表比对：

```
expected = set(load_manifest())          # what should be there
found    = extract_pr_refs(notes_md)     # what the model wrote (#1234 -> 1234)

missing = expected - found               # silently dropped
extra   = found - expected               # belongs to a different release
```

如果有缺失或多余，我们不失败也不发布错误文件。我们把差异交还给 agent，要求它精确修复那些 PR：

```
for _ in range(MAX_ITERATIONS):
    missing, extra = validate(notes)
    if not missing and not extra:
        break  # matches the manifest exactly
    run_agent_fix(missing_prs=missing, extra_prs=extra)
```

这就是让整套东西可信的模式：不确定性模型包在确定性护栏里。模型擅长写 prose，不擅长做到详尽无遗。所以我们让它写，让代码来强制一致性。

## 给模型接地，别让它瞎编

完整性是一半，准确性是另一半。只凭标题总结 PR 的模型，会愉快地编出一段和真实 API 对不上的代码示例。

为了防止这一点，我们拉取 PR 元数据时，同时抓取每条 PR 里真实的文档 diff：该 PR 触碰过的 `docs/` 下任何 `.md` 文件的 unified diff。

```
def fetch_doc_diffs(pr):
    return [
        {"filename": f.filename, "status": f.status, "patch": f.patch}
        for f in pr.get_files()
        if f.filename.startswith("docs/") and f.filename.endswith(".md") and f.patch
    ]
```

这些 diff 进入模型上下文，所以当它写「这是新的 CLI 命令」时，引用的是 PR 作者真正写进文档里的示例。逻辑与前面一致：给模型真实素材和一个收窄的任务。

提示词本身以 [Skills](https://github.com/huggingface/huggingface_hub/tree/main/.opencode/skills/hf-release-notes) 形式存在：签入仓库的小型 Markdown 文件（`SKILL.md` 加参考模板）。release-notes skill 写清了怎么选亮点、怎么组织章节、何时加文档链接等等。它读起来像新人入职指引——这正是合适的心智模型。

## 人类检查点

RC 发布后，草稿 GitHub release 就放在那里，里面是 AI 的第一稿。这时候人上场：

- 审阅者读草稿，为语气和重点做编辑，修正模型高估或低估的任何内容。
- 之后才触发 `minor-release` 运行，把 RC 提升为正式版。

审阅者的时间花在打磨上——半天的写作变成十五分钟的编辑。

我们还保留书面痕迹以便持续改进：两个文件并排存档到 Hugging Face Bucket——原始 AI 草稿在 RC 时上传（还没被任何人碰过），人工编辑版在正式 release 切出时上传。

```
# at RC time: straight from the model, untouched
hf cp release_notes_raw.txt    "hf://buckets/huggingface/releases/huggingface_hub/${V}/release_notes_raw.txt"

# at release time: after the human review
hf cp release_notes_edited.txt "hf://buckets/huggingface/releases/huggingface_hub/${V}/release_notes_edited.txt"
```

每周积累两份，我们就有了一份不断成长的「模型写了什么」vs「我们希望它写什么」的数据集，可以拿来更新 agent 的 skill。

## 开放且安全的管道

重造发布流程正好是收紧安全的机会，尤其是针对供应链攻击。

**不用 PyPI token。** 发布使用 [Trusted Publishing](https://docs.pypi.org/trusted-publishers/)：PyPI 校验由 GitHub 为这条精确 workflow 铸造的短时 OIDC token，并为每个工件出具 [PEP 740](https://peps.python.org/pep-0740/) attestations / Sigstore provenance。没有长期密钥需要泄露或轮换。

```
permissions:
  id-token: write       # mint the OIDC token for PyPI
  attestations: write   # generate Sigstore provenance
# ...
- uses: pypa/gh-action-pypi-publish@v1.14.0
  with:
    attestations: true  # no password, no API token, just OIDC
```

**Agent 运行时被 pin 住并校验。** 我们不会 `curl | bash` 最新版 OpenCode 然后祈祷。我们 pin 版本，并在运行前检查它的 SHA256：

```
curl -fsSL https://opencode.ai/install | bash -s -- --version "${OPENCODE_VERSION}"
echo "${OPENCODE_SHA256}  $(which opencode)" | sha256sum -c -
```

开放的工具不等于粗心的工具。

## 所以，花了多少钱？

几乎为零。一次完整发布（发布说明加 Slack 公告，跨 20-40 条 PR、几轮提示词）在 Inference Providers 上大约花 **$0.25**。用开放权重模型按量计费，每周唯一真正要问的问题是「有没有值得发布的东西？」——总有。

## 实践中的变化

节奏从 4-6 周一版变成一周一版。次级效应才是有意思的部分：

- **说明变好了，不是变差。** 永远有一份初稿，审阅时间就都用在了打磨上。分组更一致，遗漏更少。
- **破坏更早暴露。** 每个 RC 都跑下游测试分支，集成问题在候选窗口期就被抓住。
- **贡献者闭环缩短。** 自动化的「shipped in vX.Y.Z」评论比我们预期的更有意义。当有人已在关闭的 PR 上报 issue，所有人立刻能看到修复进了哪个版本。以前这是手动翻 tag 的活。

## 变成你自己的

这是我们最在意的部分。Workflow 按 `huggingface_hub` 定型，但结构是通用的。

**几乎原样可复用：**

- 触发与版本递增逻辑（`minor-prerelease` 然后 `minor-release` 然后 `patch-release`）。
- 信任但验证循环：确定性清单、模型起草、校验、再提示。这是可迁移的思想，与你在生成什么无关。
- OIDC Trusted Publishing、pin 住并校验 checksum 的运行时、Slack 线程汇报。
- 基于 skill 的提示词：换模板，留结构。

**我们专属的：**

- 下游仓库列表及其依赖 pin 的格式。
- Skill 里具体的章节分类和语气。
- Slack 和 bucket 的目的地。

要适配它：fork [workflow 文件](https://github.com/huggingface/huggingface_hub/blob/main/.github/workflows/release.yml)和[脚本](https://github.com/huggingface/huggingface_hub/tree/main/utils/release_notes)，指向你的包，按你项目的语气重写 [skill Markdown](https://github.com/huggingface/huggingface_hub/blob/main/.opencode/skills/hf-release-notes/SKILL.md)，设置两个仓库变量（模型 ID 和 OpenCode 版本），在 PyPI 上配好 Trusted Publishing，如果你没有下游就删掉 downstream-testing job。信任但验证循环是值得原样复用的部分——它决定了生成出的工件能不能安全发布。

## 接下来

- **自动分诊下游失败。** 今天 workflow 只开测试分支、由人来读 CI。明显下一步是检查失败日志，把它们汇报进内部 Slack 消息。
- **扩展这个模式。** 其中大部分是通用的。我们预计会把它的大块内容复用到我们生态的其他 Python 库里。

## 要点

发布中过去需要半天人类专注工作的部分（写说明、拟公告、协调下游检查），恰恰是模型擅长起草的部分。其余全是机械活，塞进一个 YAML 文件就行。诀窍从来不只是「让 AI 来做」，而是：让模型起草、让确定性代码验证、让人来定夺。整套东西完全由开放工具和开放权重构建，于是成本约等于零，谁都能跑起来。

完整 workflow 文件是公开的。如果你维护一个 Python 库，去 [fork 它](https://github.com/huggingface/huggingface_hub/blob/main/.github/workflows/release.yml)、改造它，然后告诉我们进展如何！
