许多 ML 从业者对如何让模型跑得快有些直觉，但很少有人知道如何分析模型为什么慢。在本系列的第 1 部分中，你将会学到如何系统地分析推理性能，并找出时间花在了哪里。

本文从零开始，假设你没有任何性能剖析经验。整个演练使用 AWS Trainium——一款专为深度学习训练和推理工作负载打造的 AI 芯片——以及它开源的 PyTorch 原生后端 [TorchNeuron](https://github.com/aws-neuron/torch-neuronx)。TorchNeuron 在 Trainium 上支持标准 PyTorch 工作流，包括 eager 执行、`torch.compile` 和标准 PyTorch API，且代码改动极小。此外，TorchNeuron 与 [Neuron Kernel Interface（NKI）](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/index.html) 集成，可为 Trainium 硬件启用自定义算子与性能优化。读到最后，你应当了解：

- 如何为 `torch.profiler` 配置 Neuron 后端，并抓取一份干净的 trace。
- 如何阅读 `key_averages()` 表格，找出哪些操作消耗了 Neuron 设备时间，并比较它们的 Self CPU 时间。
- 如何通过 Neuron Explorer 追踪一个操作，从框架派发、运行时调度，一直到在 NeuronCore 上的硬件执行。
- 同一个操作的三种实现下，这些信号会如何变化。

## Neuron 作为 PyTorch 后端

在剖析某个工作负载之前，先了解 [Neuron](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/index.html) 如何与 PyTorch 集成的机制会有帮助。

Neuron 后端使用 PyTorch 的 `PrivateUse1` 扩展点。该机制让加速器无需新增 `cuda` 这类专用派发键，就能与框架集成。`torch_neuronx` 包与上游 PyTorch 配合，把 Neuron 注册为 PyTorch 代码的原生后端。关于这一扩展机制的细节，见 [Facilitating New Backend Integration by PrivateUse1](https://docs.pytorch.org/tutorials/advanced/privateuseone.html)。

## 配置 profiler

剖析 Neuron 工作负载要用到两个对象：

- `NeuronConfig` 控制要抓取哪些 Neuron 数据流与 NeuronCore，以及把输出写到哪里。你以 `experimental_config` 的形式把它传给 `torch.profiler.profile`。
- `NeuronProfiler` 接收一个 `NeuronConfig`，并提供 `export_trace` 回调。该回调会把框架 trace（`trace.json`）与 Neuron 系统 trace 一起写出。

```
nc = NeuronConfig(
    modes=[ProfileMode.DEVICE, ProfileMode.RUNTIME],
    profile_output_dir=OUTPUT_DIR,
    capture_enabled_for_nc='0',
    correlate_device_time=True,
)
exporter = NeuronProfiler(nc)
```

`modes` 参数选择要抓取的数据流，例如设备指令和运行时 trace。`capture_enabled_for_nc` 参数选择要追踪的 NeuronCore。设置 `correlate_device_time=True` 会把设备时间从 trace 传播到 `key_averages()` 表格中，便于你在那里比较 CPU 时间与 Neuron 设备时间。完整的参数参考与可用的 `ProfileMode` 取值，见 NeuronConfig 的 [Profile Modes 文档](http://awsdocs-neuron.readthedocs-hosted.com/en/latest/tools/neuron-explorer/how-to-profile-workload.html#neuronconfig-profile-modes)。

## 工具：Neuron Explorer

Neuron Explorer 是一个基于浏览器的查看器，用于查看系统 trace、设备时间线和按引擎拆分的明细。你可以通过 SSH 隧道或 Visual Studio Code 扩展访问它。在本文中，你用 Explorer 来确认 `key_averages()` 以数字报告的内容，并检视派发之间发生了什么。

剖析结束后，输出目录中包含系统 trace；当你抓取了设备数据，还会有配对的 `.neff` 与 `.ntff` 文件。Neuron Executable File Format（NEFF）包含编译后的 Neuron 可执行文件，而配对的 NTFF 包含其硬件指令 trace。两个文件共享一个数字哈希，用以标识它们是一对。要在 Neuron Explorer 中打开 profile：若为系统 profile 或组合 profile，请上传完整输出目录；若为仅有设备的 profile，请分别上传配对的 `.neff` 与 `.ntff` 文件。UI 与命令行说明见 [Step 5: Upload your profile](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/tools/neuron-explorer/get-started.html#step-5-upload-your-profile)。

## 剖析 RMSNorm

在第一次分析中，你剖析 RMSNorm——一个规模很小、算术与归约操作序列清晰的操作。

你剖析同一操作的三种实现：

- 用单个 PyTorch 操作拼出的朴素 RMSNorm：乘法、求均值、加法、平方根倒数，再乘法。
- `torch.rms_norm()`，即 PyTorch 内置实现，会被 lower 成单个融合的 Neuron kernel。
- 配合 `torch.compile` 的朴素 RMSNorm，使用与第一种实现相同的操作。

这些脚本使用相同的输入、profiler 配置与调度，因此结果可以直接比较。

复现本文工作的所有脚本都在 `torch-neuronx` 的 [examples 目录](https://github.com/aws-neuron/torch-neuronx/tree/main/examples/hf_profiling_blog_pt1) 中。

## 剖析 1：朴素的 PyTorch 操作

先直接用一个个 PyTorch 操作来写 RMSNorm。每一行都对应一个或多个 ATen 操作，并可能产生中间张量。

```
device = torch.device('neuron')

x = torch.randn(4, 512, dtype=torch.bfloat16, device=device)
weight = torch.ones(512, dtype=torch.bfloat16, device=device)

def rms_norm_fn(t):
    x_sq = t * t                                    # square
    mean_sq = x_sq.mean(dim=-1, keepdim=True)       # mean of squares
    rms = torch.rsqrt(mean_sq + 1e-6)               # 1 / sqrt(mean_sq + eps)
    return t * rms * weight                         # normalize + scale
```

调用 profiler 时，Neuron 后端需要两个参数：

- 包含 `ProfilerActivity.PrivateUse1`，以收集 Neuron 设备上的活动。
- 把 `NeuronConfig` 作为 `experimental_config` 传入，以启用 Neuron 专属的 Kineto 特性。

这里的调度在四次 `prof.step()` 调用中使用 `wait=2`、`warmup=1`、`active=1`。这样会记录一次热身之后的迭代，且不包含初始化设置的开销。

在 profiler 循环内调用 `torch.neuron.synchronize()`。若没有这次同步，profiler 可能在设备完成之前就导出，从而使 Neuron 时间列留空。

```
with torch.profiler.profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.PrivateUse1],
    experimental_config=nc,
    record_shapes=False,
    on_trace_ready=exporter.export_trace,
    schedule=torch.profiler.schedule(wait=2, warmup=1, active=1),
) as prof:
    for step in range(4):
        with torch.no_grad():
            _ = rms_norm_fn(x)
        torch.neuron.synchronize()
        prof.step()
```

剖析结束后，检查 `key_averages()` 表格。按 `self_privateuse1_time_total` 排序，可把设备开销最高的操作排在前面。这里展示的表格已筛选为报告了 Neuron 设备时间的 RMSNorm 操作。完整的 `key_averages()` 输出还包含 CPU 侧事件，例如内存分配和 host-to-device 拷贝。

```
print(prof.key_averages().table(sort_by="self_privateuse1_time_total", row_limit=4))
```

这张表显示了哪些 ATen 操作运行过、运行了多少次，以及它们在 CPU 和 Neuron 设备上各花了多少时间。`aten::mul` 的设备总时间最高，因为该函数执行了三次乘法。

| 名称 | 调用次数 | Self CPU | Self NEURON | % NEURON |
| --- | --- | --- | --- | --- |
| aten::mul | 3 | 60.9 μs | 1,164.5 μs | 49.5% |
| aten::add | 1 | 26.6 μs | 434.6 μs | 18.5% |
| aten::rsqrt | 1 | 15.6 μs | 415.0 μs | 17.6% |
| aten::mean | 1 | 21.1 μs | 340.8 μs | 14.5% |

*Self NEURON 总计：2.355 ms*

每一行都直接对应函数里的操作。`aten::mul` 对应 `x * x`、`x * rms` 以及最后与 `weight` 相乘。`aten::mean` 对最后一维做归约。`aten::add` 加上 epsilon 值，并触发一次 host-to-device 拷贝，因为这个标量最初在 CPU 上。`aten::rsqrt` 计算平方根倒数。

### 在 Explorer 中阅读 trace

在 Explorer 中，时间从左向右流动，事件生命周期从上到下展开。每个 ATen 操作都遵循同样的模式：在框架泳道中创建，在运行时泳道中作为 `nrta_execute_schedule` 被调度，在硬件泳道中作为 `nc_exec_running` 执行。

系统 trace 视图把事件组织成若干泳道。在默认分组模式下，标签遵循 instance/PID/subsystem/identifier 的模式：

| 泳道 | 标签后缀 | 展示内容 |
| --- | --- | --- |
| 框架派发 | `framework/TID:<id>` | 算子派发事件（PrivateUse1 运行时），按线程 ID 分组。 |
| 框架设备 | `framework/Stream:<n>` | 设备交互事件（PrivateUse1 驱动），按 stream 编号分组。 |
| Neuron 运行时 | `neuron_rt/NC:<n>` | Neuron Runtime API 调用，按逻辑 NeuronCore 分组。 |
| Neuron 硬件 | `neuron_hw/NC<n>:<id>` | 硬件执行事件，按物理 NeuronCore 分组。 |

在 eager 模式下，每个操作独立运行。用依赖链查看器追踪 `aten::mul.Tensor`，看它如何从框架层经过运行时调度走到设备执行。

## 剖析 2：torch.rms_norm

把单个操作换成 PyTorch 内置的 `rms_norm` 函数。Neuron 会把这个操作 lower 成一个融合 kernel：

```
def rms_norm_fn(t):
    return torch.rms_norm(t, [512], weight)
```

[![融合后的 RMSNorm 在 key averages 表中表现为一个设备操作。](https://cdn-uploads.huggingface.co/production/uploads/6ac67ea29579ea34f1f7e470/uYhQmUtuUp1LYPOu8f9bf.png)](https://cdn-uploads.huggingface.co/production/uploads/6ac67ea29579ea34f1f7e470/uYhQmUtuUp1LYPOu8f9bf.png)

*融合后的 RMSNorm 在 key averages 表中表现为一个设备操作。*

| 名称 | 调用次数 | Self CPU | Self NEURON | % NEURON |
| --- | --- | --- | --- | --- |
| aten::_fused_rms_norm | 1 | 47.6 μs | 403.3 μs | 100% |

*Self NEURON 总计：403.3 μs*

[![融合后的 RMSNorm 只走一条从框架到硬件的路径，而不是把每个算术操作分别派发。](https://cdn-uploads.huggingface.co/production/uploads/6ac67ea29579ea34f1f7e470/OfM6vRT9iPBG42s8iWK1V.png)](https://cdn-uploads.huggingface.co/production/uploads/6ac67ea29579ea34f1f7e470/OfM6vRT9iPBG42s8iWK1V.png)

*融合后的 RMSNorm 只走一条从框架到硬件的路径，而不是把每个算术操作分别派发。*

### 对比 lower 路径

在朴素实现中，每个操作都独立跨越派发边界，各自走一条从框架到运行时再到硬件的路径。在融合实现中，一次 Python 调用就覆盖了整个计算。trace 中只有一次派发和一个硬件事件，组成操作之间没有空隙。

## 剖析 3：配合 torch.compile 的朴素 PyTorch

最后一个例子，用 `torch.compile` 编译原来的朴素 RMSNorm 函数。

通过 `@torch.compile(backend="neuron")`，TorchDynamo 把 Python 字节码捕获为 FX 图，AOTAutograd 再把它 lower 成 ATen 操作。Neuron 后端拿到的是完整的图，而不是逐个派发每个操作。它会融合操作、优化内存访问，并把图编译成单个 NEFF 产物。该产物作为一次硬件派发运行。

```
@torch.compile(backend='neuron', fullgraph=True)
def naive_compiled(t):
    x_sq = t * t
    mean_sq = x_sq.mean(dim=-1, keepdim=True)
    rms = torch.rsqrt(mean_sq + 1e-6)
    return t * rms * weight
```

| Torch-Compiled Region: 0/0 | 1 | 98.4 μs | 375.5 μs | 100% |

*Self NEURON 总计：375.5 μs*

表格显示只有一次设备执行，与剖析 2 相同，但代码走的路径不同。它不是去调用专门构建的融合操作，而是由编译器从原始 Python 函数中发现可融合之处。在这次运行中，Neuron 时间与 `torch.rms_norm` 相当：375 μs 对 403 μs。

## 并排对比总结

| 变体 | NEURON 时间 | Self CPU 时间 | 算子调用次数 |
| --- | --- | --- | --- |
| 朴素操作 | 2,355 µs | ~125 µs | 6 |
| torch.rms_norm | 403 µs | ~48 µs | 1 |
| 朴素 + torch.compile | 376 µs | ~98 µs | 1 |

`torch.rms_norm` 与 `torch.compile` 都把 RMSNorm 融合成一次 kernel 派发。在这些运行中，两种做法的设备时间都约为朴素实现的六分之一。融合消除了硬件执行之间的空隙，也避免了在分别派发的操作之间实际生成 `x_sq`、`mean_sq` 这类中间值。

## 结论

`key_averages()` 显示哪些操作消耗了设备时间，其完整输出还会揭示 CPU 侧的初始化设置与传输开销。Explorer 提供对应的可视化 trace。你可以追踪一个操作从框架派发、运行时调度到硬件执行的全过程，并看到融合消除了哪些空隙。

同样的工作流也能用在大模型上：先在表格里找到热点，再到 trace 中核实，然后判断融合操作或 `torch.compile` 能否降低其开销。

在第 2 部分，我们将进入设备级 profile。你会打开 NEFF，检查 TensorEngine、VectorEngine 与直接内存访问（DMA）的明细，并把 kernel 放到 roofline 图上，判断它受限于计算还是受限于内存。
