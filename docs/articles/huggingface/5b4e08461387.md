许多机器学习从业者对如何使模型运行得更快有一定的直觉，但很少有人知道如何分析模型运行缓慢的原因。在本系列的第 1 部分中，您将学习如何系统地分析推理性能并确定时间花在哪里。

这篇文章从头开始，假设之前没有分析经验。本演练使用 AWS Trainium（一种用于深度学习训练和推理工作负载的专用 AI 芯片）及其开源原生 PyTorch 后端 [TorchNeuron](https://github.com/aws-neuron/torch-neuronx)。 TorchNeuron 支持 Trainium 上的标准 PyTorch 工作流程，包括即时执行、“torch.compile”和标准 PyTorch API，只需最少的代码更改。此外，TorchNeuron 与 [Neuron 内核接口 (NKI)](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/index.html) 集成，可为 Trainium 硬件启用自定义运算符和性能优化。到最后，你应该知道：

- 如何使用 Neuron 后端配置 `torch.profiler` 并捕获干净的跟踪。
- 如何读取“key_averages()”表来识别哪些操作消耗 Neuron 设备时间并比较它们的自身 CPU 时间。
- 如何通过 Neuron Explorer 跟踪一项操作，从框架调度到运行时调度再到 NeuronCore 上的硬件执行。
- 这些信号在同一操作的三种实现中如何变化。

## Neuron 作为 PyTorch 后端

在分析工作负载之前，了解 [Neuron](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/index.html) 如何与 PyTorch 集成会有所帮助。

Neuron 后端使用 PyTorch 的“PrivateUse1”扩展点。这种机制允许加速器与框架集成，而无需添加专用的调度密钥，例如“cuda”。 `torch_neuronx` 包与上游 PyTorch 配合使用，将 Neuron 注册为 PyTorch 代码的本机后端。有关此扩展机制的详细信息，请参阅 [通过 PrivateUse1 促进新后端集成](https://docs.pytorch.org/tutorials/advanced/privateuseone.html)。

## 设置分析器

您使用两个对象来分析 Neuron 工作负载：

- `NeuronConfig` 控制要捕获哪些 Neuron 数据流和 NeuronCore 以及将输出写入何处。您将其作为“experimental_config”传递给“torch.profiler.profile”。
- `NeuronProfiler` 采用 `NeuronConfig` 并提供 `export_trace` 回调。回调将框架跟踪“trace.json”与 Neuron 系统跟踪一起写入。
```
nc = NeuronConfig(
    modes=[ProfileMode.DEVICE, ProfileMode.RUNTIME],
    profile_output_dir=OUTPUT_DIR,
    capture_enabled_for_nc='0',
    correlate_device_time=True,
)
exporter = NeuronProfiler(nc)
```
“modes”参数选择要捕获的数据流，例如设备指令和运行时跟踪。 `capture_enabled_for_nc` 参数选择要跟踪的 NeuronCore。设置“correlate_device_time=True”会将设备时间从跟踪传播到“key_averages()”表中，您可以在其中比较 CPU 和 Neuron 设备时间。有关完整的参数参考和可用的“ProfileMode”值，请参阅 NeuronConfig [配置文件模式文档](http://awsdocs-neuron.readthedocs-hosted.com/en/latest/tools/neuron-explorer/how-to-profile-workload.html#neuronconfig-profile-modes)。

## 工具：神经元浏览器

Neuron Explorer 是一个基于浏览器的查看器，用于查看系统跟踪、设备时间线和每个引擎的故障。您可以通过 SSH 隧道或 Visual Studio Code 扩展来访问它。在本文中，您将使用 Explorer 来确认 key_averages() 报告的数字内容并检查调度之间发生的情况。

分析后，输出目录包含系统跟踪，并且当您捕获设备数据时，会匹配“.neff”和“.ntff”文件。 Neuron 可执行文件格式 (NEFF) 包含已编译的 Neuron 可执行文件，而匹配的 NTFF 包含其硬件指令跟踪。这些文件共享一个数字哈希，将它们标识为一对。要在 Neuron Explorer 中打开配置文件，请上传系统或组合配置文件的完整输出目录。对于仅限设备的配置文件，请分别上传匹配的“.neff”和“.ntff”文件。有关 UI 和命令行说明，请参阅[步骤 5：上传您的个人资料](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/tools/neuron-explorer/get-started.html#step-5-upload-your-profile)。

## 配置文件 RMSNorm

对于第一个分析，您将分析 RMSNorm，这是一个具有清晰的算术和归约运算序列的小运算。

您分析同一操作的三个实现：

- Naive RMSNorm 具有单独的 PyTorch 运算：乘法、均值、加法、倒数平方根和乘法。
- `torch.rms_norm()`，PyTorch 内置降低为单个融合神经元内核。
- 使用“torch.compile”的 Naive RMSNorm，使用与第一个实现相同的操作。

这些脚本使用相同的输入、分析器配置和计划，因此结果可以直接比较。

重现这项工作的所有脚本都可以在 `torch-neuronx` [示例目录](https://github.com/aws-neuron/torch-neuronx/tree/main/examples/hf_profiling_blog_pt1) 中找到。

## 配置文件 1：朴素的 PyTorch 操作

首先使用单独的 PyTorch 操作编写 RMSNorm。每条线映射到一个或多个 ATen 操作，并可以创建中间张量。
```
device = torch.device('neuron')

x = torch.randn(4, 512, dtype=torch.bfloat16, device=device)
weight = torch.ones(512, dtype=torch.bfloat16, device=device)

def rms_norm_fn(t):
    x_sq = t * t                                    # square
    mean_sq = x_sq.mean(dim=-1, keepdim=True)       # mean of squares
    rms = torch.rsqrt(mean_sq + 1e-6)               # 1 / sqrt(mean_sq + eps)
    return t * rms * weight                         # normalize + scale
```
使用 Neuron 后端所需的两个参数调用探查器：

- 包含“ProfilerActivity.PrivateUse1”以从 Neuron 设备收集活动。
- 将 `NeuronConfig` 作为 `experimental_config` 传递以启用 Neuron 特定的 Kineto 功能。

该计划在四个“prof.step()”调用中使用“wait=2”、“warmup=1”和“active=1”。这记录了一次热迭代，不包括初始设置开销。

在分析器循环内调用“torch.neuron.synchronize()”。如果没有这种同步，分析器可以在设备完成之前导出并将神经元时间列留空。
```
with torch.profiler.profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.PrivateUse1],
    experimental_config=nc,
    record_shapes=False,
    on_trace_ready=exporter.export_trace,
    schedule=torch.profiler.schedule(wait=2, warmup=1, active=1),
) as prof:
    for step in range(4):
        with torch.no_grad():
            _ = rms_norm_fn(x)
        torch.neuron.synchronize()
        prof.step()
```
分析完成后，检查“key_averages()”表。按“self_privateuse1_time_total”排序，将设备成本最高的操作放在前面。此处显示的表已过滤为报告 Neuron 设备时间的 RMSNorm 操作。完整的“key_averages()”输出还包括 CPU 端事件，例如分配和主机到设备的传输。
```
print(prof.key_averages().table(sort_by="self_privateuse1_time_total", row_limit=4))
```

### 读取资源管理器中的跟踪

在资源管理器中，时间从左到右流动，事件生命周期从上到下流动。每个 ATen 操作都遵循相同的模式：在框架通道中创建，在运行时通道中调度为“nrta_execute_schedule”，以及在硬件通道中作为“nc_exec_running”执行设备。

系统跟踪视图将事件组织到通道中。在默认分组模式下，标签遵循模式实例/PID/子系统/标识符：

|车道 |标签后缀|它显示了什么 |
| --- | --- | --- |
|框架调度 | `框架/TID：<id>` |操作员调度事件（PrivateUse1 运行时），按线程 ID 分组。 |
|框架装置| `框架/流：<n>` |设备交互事件（PrivateUse1 驱动程序），按流编号分组。 |
|神经元运行时 | `neuron_rt/NC:<n>` | Neuron 运行时 API 调用，按逻辑 NeuronCore 分组。 |
|神经元硬件 | `neuron_hw/NC<n>:<id>` |硬件执行事件，按物理 NeuronCore 分组。 |

在 Eager 模式下，每个操作独立运行。使用依赖链查看器跟踪“aten::mul.Tensor”从框架层到运行时调度到设备执行。

## 配置文件 2：torch.rms_norm

将各个操作替换为 PyTorch 的内置“rms_norm”函数。 Neuron 将操作降低到一个融合内核：
```
def rms_norm_fn(t):
    return torch.rms_norm(t, [512], weight)
```

### 比较下降路径

在简单的实现中，每个操作独立地跨越调度边界，并遵循其自己的框架到运行时到硬件的路径。在融合实现中，一个 Python 调用涵盖了完整的计算。该跟踪包含一项调度和一项硬件事件，组件操作之间没有间隙。

## 配置文件 3：带有 torch.compile 的 Naive PyTorch

对于最后一个示例，使用“torch.compile”编译原始的 RMSNorm 函数。

使用 @torch.compile(backend="neuron")`，TorchDynamo 将 Python 字节码捕获为 FX 图形，AOTAutograd 将其降低为 ATen 操作。 Neuron 后端接收完整的图，而不是单独分派每个操作。它融合了操作，优化了内存访问，并将图编译成单个 NEFF 工件。该工件作为一个硬件调度运行。
```
@torch.compile(backend='neuron', fullgraph=True)
def naive_compiled(t):
    x_sq = t * t
    mean_sq = x_sq.mean(dim=-1, keepdim=True)
    rms = torch.rsqrt(mean_sq + 1e-6)
    return t * rms * weight
```

## 并排总结

|变体 |神经元时间|自CPU时间|接线员电话 |
| --- | --- | --- | --- |
|天真的操作 | 2,355 µs |约 125 µs | 6 |
|火炬.rms_norm | 403 微秒 | ~48 µs | 1 |
|天真的+ torch.compile | 376 微秒 | ~98 µs | 1 |

`torch.rms_norm` 和 `torch.compile` 都将 RMSNorm 融合到一个内核调度中。在这些运行中，任何一种方法都花费大约六分之一的简单实现的设备时间。 Fusion 消除了硬件执行之间的间隙，并避免在单独分派的操作之间具体化中间值，例如“x_sq”和“mean_sq”。

## 结论

`key_averages()` 显示哪些操作消耗设备时间，而其完整输出还揭示了 CPU 端设置和传输。 Explorer提供了相应的视觉轨迹。您可以跟踪从框架调度到运行时调度再到硬件执行的一项操作，并查看融合消除的差距。

您可以在较大的模型上使用相同的工作流程：在表中找到热点，在跟踪中验证它，然后确定融合操作或“torch.compile”是否可以降低其成本。

在第 2 部分中，我们将进入设备级配置文件。您打开 NEFF，检查 TensorEngine、VectorEngine 和直接内存访问 (DMA) 故障，并将内核放在屋顶线上以确定它是受计算限制还是受内存限制。
