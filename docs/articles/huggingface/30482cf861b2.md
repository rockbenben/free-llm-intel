# 重新架构 Hugging Face 的上传与下载

Banerjee (port8080, xet-team)

Jared Sulzdorf (jsulz, xet-team)

Ann Huang (erinys, xet-team)

作为 Hugging Face Xet 团队[改进 Hub 存储后端](https://huggingface.co/blog/xethub-joins-hf)工作的一部分，我们分析了 Hugging Face 上传请求的 24 小时窗口，以更好理解访问模式。2024 年 10 月 11 日当天：

- 上传来自 88 个国家
- 820 万次上传请求
- 传输数据量 130.8 TB

下面这张地图可视化了这些活动，国家按每小时上传字节数着色。

![Animated view of uploads](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/rearchitecting-uploads-and-downloads/animated-uploads-choropleth.gif)

目前，上传内容存储在 **`us-east-1`** 的 [S3 bucket](https://aws.amazon.com/s3/) 中，并用 [S3 Transfer Acceleration](https://aws.amazon.com/s3/transfer-acceleration/) 优化。下载通过 [AWS Cloudfront](https://aws.amazon.com/cloudfront/) 作为 CDN 缓存和分发。Cloudfront 的 [400 多个便利边缘节点](https://aws.amazon.com/blogs/networking-and-content-delivery/400-amazon-cloudfront-points-of-presence/)提供了全球覆盖和低延迟传输。但和多数 CDN 一样，它针对 Web 内容优化，有 50GB 的文件大小上限。

这个大小限制对一般互联网文件传输来说合理，但模型和数据集仓库中不断膨胀的文件尺寸带来了挑战。例如 [meta-llama/Meta-Llama-3-70B](https://huggingface.co/meta-llama/Meta-Llama-3-70B) 的权重合计 131GB，为满足 Hub 推荐的[按 20 GB 分段](https://huggingface.co/docs/hub/en/repositories-recommendations#recommendations)切分权重要求，被拆成了 30 个文件。此外，要在上传和下载两侧都启用高级去重或压缩技术，也需要重新构想文件传输的处理方式。

## 为上传与下载设计自定义协议

为了把 Hugging Face 基础设施推到当前极限之外，我们正在重新设计 Hub 的上传与下载架构。计划把[内容寻址存储（CAS，content-addressed store）](https://en.wikipedia.org/wiki/Content-addressable_storage)插为内容分发的第一站。这让我们得以构建一个遵循***笨读巧写（dumb reads and smart writes）***指导哲学的自定义协议。与把文件当作不透明 blob 的 Git LFS 不同，我们的方法在字节层面分析文件，为模型和数据集仓库里那些超大文件挖掘提速空间。

读路径追求简单快捷，保证高吞吐、低延迟。文件请求被路由到 CAS 服务器，由其提供重建信息。数据本身仍存放在 **`us-east-1`** 的 S3 bucket，AWS CloudFront 继续作为下载的 CDN。

写路径更复杂，目标是优化上传速度并提供额外安全保障。与读一样，上传请求也路由到 CAS 服务器，但不按文件查询，而是[按 chunk 操作](https://huggingface.co/blog/from-files-to-chunks)。找到匹配时，CAS 服务器指示客户端（如 [huggingface_hub](https://github.com/huggingface/huggingface_hub)）只传输必要的（新）chunk。chunk 先经 CAS 验证再上传到 S3。

还有很多实现细节待处理，如网络约束和存储开销，以后另文展开。先看现在读是怎么走的。下面第一张图展示当前的读写路径：

左侧是读，右侧是写。注意写是直接进 S3，没有任何中间层。

新的写路径：CAS 加速并验证上传，S3 继续提供底层存储。

在字节层面管理文件，让我们能针对不同文件格式适配优化。比如，我们已经探索过[提升 Parquet 文件的去重能力](https://huggingface.co/blog/improve_parquet_dedupe)，现在在研究压缩 tensor 文件（如 [Safetensors](https://github.com/huggingface/safetensors)），有望把上传速度提升 10-25%。随着新格式涌现，我们处于独特的位置，可以继续开发改进 Hub 上开发体验的增强项。

该协议还为企业客户和高级用户带来显著提升。为文件传输插入控制层，提供了额外保障，确保恶意或无效数据无法上传。运维上，上传不再是黑盒：增强的遥测提供审计轨迹和详细日志，让 Hub 基础设施团队能快速高效地定位和解决问题。

## 面向全球访问的设计

为支撑这一自定义协议，需要确定 CAS 服务的最优地理分布。我们最初考虑 [AWS Lambda@Edge](https://aws.amazon.com/lambda/edge/)，因为它全球覆盖广，有助于最小化往返时延。但它依赖 Cloudfront 触发器，与我们更新后的上传路径不兼容。最终我们选择在 AWS 的 34 个 region 中挑选少数几个部署 CAS 节点。

细看那 24 小时的 S3 PUT 请求，我们识别出揭示 Hub 数据上传分布的全球流量模式。如预期，多数活动来自北美和欧洲，全天持续高量上传。数据还显示亚洲强劲且增长的存在。聚焦这些核心区域，我们就能布置 CAS 的[接入点（PoP）](https://docs.aws.amazon.com/whitepapers/latest/aws-fault-isolation-boundaries/points-of-presence.html)，在平衡存储与网络资源的同时最小化延迟。

![Pareto chart of uploads](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/rearchitecting-uploads-and-downloads/pareto-chart.png)

AWS 虽有 34 个 region，我们的目标是在保持优质体验的同时把基础设施成本控制在合理范围。这次快照涉及 88 个国家，上面的帕累托图显示：前 7 个国家贡献了 80% 的上传字节，前 20 个国家贡献了 95% 的总上传量和请求数。

美国是上传流量的最大来源，必须在此区域设 PoP。欧洲的活动集中在中东欧和西欧国家（如卢森堡、英国、德国），非洲也有一些需要兼顾的额外活动（特别是阿尔及利亚、埃及、南非）。亚洲的上传流量主要由新加坡、香港、日本和韩国驱动。

用简单启发式分配流量，可把 CAS 覆盖划分为三大区域：

- **`us-east-1`**：服务南北美洲
- **`eu-west-3`**：服务欧洲、中东和非洲
- **`ap-southeast-1`**：服务亚洲和大洋洲

结果相当有效：美国和欧洲占上传字节的 78.4%，亚洲占 21.6%。

![New AWS mapping](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/rearchitecting-uploads-and-downloads/aws-regions.png)

这一区域划分让三个 CAS PoP 的负载均衡，**`ap-southeast-1`** 还留有增长余量，**`us-east-1`** 和 **`eu-west-3`** 也能按需扩容。

按预期流量，我们计划这样分配资源：

- **`us-east-1`**：4 节点
- **`eu-west-3`**：4 节点
- **`ap-southeast-1`**：2 节点

## 验证与评估

虽然部分用户的第一跳距离变长了，但对 Hub 整体带宽的影响有限。估算显示：所有上传的累计带宽将从 48.5 Mbps 降至 42.5 Mbps（减少 12%），但这个性能损失会被系统其他优化反超。

我们正在推进基础设施于 2024 年底进入生产，届时先在 **`us-east-1`** 上单个 CAS 起步。随后把内部仓库复制到新存储系统以基准测试传输性能，再把 CAS 复制到上述更多 PoP 继续测试。根据结果持续优化方案，确保明年存储后端全面就位时一切顺畅。

## 字节之外

随着分析深入，更深刻洞察的机会不断涌现。Hugging Face 托管着开源机器学习社区最大的数据集合之一，是观察驱动全球 AI 发展的模态与趋势的独特视角。

例如，未来的分析可以按用途对 Hub 上的模型分类（NLP、计算机视觉、机器人、大语言模型等），并考察 ML 活动的地域趋势。这些数据不仅指导我们的基础设施决策，也是观察机器学习版图演进的透镜。
