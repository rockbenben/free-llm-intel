We built ThinkingBox to catch agents that say they are done when they are not.

Each of its 507 tasks in ThinkingBox-Bench (our benchmark dataset) hands an agent a real backend and a set of tools, lets it work, then checks what really changed in the database. [In the first post](https://huggingface.co/blog/microsoft/thinkingbox), we caught a model closing a customer's ticket as **resolved** while the carrier exception behind it was still open. Nine competent-looking tool calls, one **wrong** database row.

Then we noticed what we had built. For most tasks, an executable check can return 1 or 0 directly from the final database state. That is not just a grader. **This can be a reward function.**+

So we constructed a training pool from ThinkingBox-format tasks outside the benchmark and used their executable outcomes as rewards. The catch was choosing **which** tasks are suitable for agent training: most tasks are either already solved or hopeless for the model in front of you, and both teach it nothing.

> Difficulty is policy-relative: a task is hard for the current model only until that model learns it.

We call this **offline policy-relative difficulty**. We estimated each task's success probability once using the base policy before training and kept the selected training pool fixed throughout the run.

### What happened after training

We used offline policy-relative difficulty to build the training pool, then fine-tuned Qwen3.8-27B with GRPO for 50 steps. To recap, we evaluate each of the 507 benchmark tasks 20 times. pass@1 measures average success across all 10,140 attempts. pass@20 measures the share of tasks solved at least once. Observed 20/20 measures the share of tasks that pass every recorded attempt.

*Table 1. Qwen3.8-27B results before and after 50 steps of GRPO on the offline-selected training pool.*

| Metric | Base |  | RL fine-tuned | Change |
| --- | --- | --- | --- | --- |
| **Observed 20/20** | 38 (7.50%) | → | **107 (21.10%)** | **+69 tasks** |
| pass@1 (successful attempts) | 5,242 (51.70%) | → | **6,163 (60.78%)** | **+9.08 pt** |
| pass@20 (tasks solved at least once) | 453 (89.35%) | → | **446 (87.97%)** | **−7 tasks** |

Training sharply **increased** repeatable success, with a small decline in at-least-once coverage. The rest of the post explains how we selected practice tasks, built the reward loop, and measured that tradeoff.

**What does that improvement look like on one task?** A traveler requests a room downgrade, but company policy requires manager approval first. Before training, the agent changed the booking and issued refunds without approval in 15 of 20 attempts. After RL fine-tuning, it preserved the booking and payment state in all 20.

## What the benchmark found, in sixty seconds

[ThinkingBox-Bench](https://huggingface.co/datasets/microsoft/ThinkingBox-Bench) grades agents on the database records they leave behind. Each of its 507 tasks starts a real backend, hands the agent a set of MCP tools and a simulated LLM user with private context, and at the end runs executable checks against the terminal database state. Checks are against the backend record that needs to be correct, not the specific tool calls. This incentivizes the model to discover possibly new solution paths rather than “rediscover” the human-backed solution, that might be suboptimal albeit correct.

[In our first post](https://huggingface.co/blog/microsoft/thinkingbox) we ran eighteen models through that benchmark twenty times each and reported a gap that headline accuracy hides. Kimi-K3 solved 93.89% of tasks *at least once* but completed only 68 of 507 tasks (13.41%) on **all twenty recorded attempts**. Claude Opus 5 inverted it: narrower coverage, far more consistency.

And bigger or better model did not close it. Claude Opus 5.5 scored 0.66 percentage points higher than Claude Opus 5 on pass@1, yet passed **exactly the same number of tasks, 241**, on all twenty attempts. That gain in headline accuracy bought zero additional dependability.

If you are choosing a model for work that touches production database records, pass@1 should not be read alone. Observed 20/20 shows which tasks succeed on every attempt, which is closer to what production reliability requires.

The executable terminal-state verdict was also the training reward. Before unpacking the training loop, here is what changed on the sealed benchmark.

**The headline result is the observed-20/20 row in Table 1.** A **27B model** that initially completed 38 (7.5%) of ThinkingBox-Bench on every attempt now completes 107 (21.1%) on every attempt, almost thrice. For comparison, observed 20/20 for Kimi-K3 is 68, GPT-5.4 with 128, GPT-6 Astra has 231, and Claude Opus 5.5 leads with 241.

**Average success and repeatability produce different orderings.** In Table 2, we notice that GPT-5.6 Sol scored slightly higher on pass@1 than the RL fine-tuned Qwen3.8-27B (61.91% versus 60.78%) but passed fewer tasks on all 20 recorded attempts: 82 versus 107. Claude Sonnet 4.6 scored lower on pass@1, at 59.19%, yet passed nearly the same number of tasks every time, at 102. Neither metric alone captures the full picture.

The observed pattern is consistent with sharpening: repeatable success rose while at-least-once coverage fell slightly. This is in-line with [prior work](https://arxiv.org/abs/2504.13837). One explanation is that probability distribution moved toward trajectories that work repeatedly while some low-probability paths disappeared.

> Overall, the model did not become broader. It became more repeatable. The next question is where those gains landed.

## What dependability costs

The [first post](https://huggingface.co/blog/microsoft/thinkingbox) priced consistency using simple math: divide the **estimated cost of the full 20-run campaign** by the number of tasks the model passed every single time.

> Cost per dependable task = estimated cost of the 507 × 20 campaign ÷ tasks passing 20/20

Applying the same cost math to the fine-tuned checkpoint's measured token usage:

*Table 3. Estimated evaluation cost and dependability for base and RL fine-tuned Qwen3.8-27B. Cost per successful attempt divides total estimated campaign cost (507 x 20) by the number of passing attempts.*

| Measure | Base |  | RL fine-tuned | Change |
| --- | --- | --- | --- | --- |
| Campaign cost, 20 runs | $925.80 | → | **$855.58** | **−7.6%** |
| Cost per successful attempt | $0.177 | → | **$0.139** | **−21.4%** |
| Tasks passing 20/20 | 38 | → | **107** | **2.8× as many** |
| **Cost per dependable task** | $24.36 | → | **$8.00** | **−67.2%** |

At $8.00 per dependable task, the fine-tuned model came close to GPT-5.4 ($6.80), GPT-6 Astra ($7.45), and Claude Opus 5.5 ($7.80) in the companion comparison.

These results tell us what moved. The next sections explain the training loop and why selecting the right tasks matters the most.

## The training loop

[![fig4-training-overview](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/ZaqyG8RtqCRsxGdxUQMfi.png)](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/ZaqyG8RtqCRsxGdxUQMfi.png)

*Figure 5. The six stages, now in context: candidate tasks feed in, the first three run once offline, the last three repeat for every group in the training run. The trained checkpoint is evaluated against ThinkingBox-Bench.*

Selection runs once, offline, against the base policy model, i.e in this case Qwen3.8 27B; training then uses that fixed pool that has been curated. The dashed amber arrow in Figure 5 marks the path we did not take: re-probing difficulty during the training run.

Every rollout is a complete episode, not a text completion. It gets a fresh backend, an isolated MCP session, and GPT-5 Chat as the simulated user. Most rewards come from deterministic terminal-state checks; a minority of narrow rubric requirements can invoke the configured judge (GPT-5 Chat).

**Training and evaluation must interpret Qwen output identically.** That includes reasoning extraction, tool calls, argument typing, rendering, and isolated task state. Otherwise the reward measures a different agent from the one evaluated. The shared interpretation code is in [`trainer/core/tb_interpret.py`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/trainer/core/tb_interpret.py).

For the reference run, we ran full-parameter RL fine-tuned Qwen3.8-27B on 187 tasks using token-mean GRPO. Each update generated 18 groups of 8 rollouts, or 144 episodes, across 24 H100s. Training ran synchronously with parameter and optimizer offload; AdamW used a `1e-6` learning rate and zero weight decay. We ran the training for 50 steps.

Zero-variance groups were replaced [DAPO-style](https://arxiv.org/abs/2503.14476) during training. System errors were handled separately: a backend timeout is not an incorrect agent outcome, so affected groups were refilled rather than scored as failures.

That explains how retained tasks were trained. The remaining question is which tasks entered the training pool.

## Offline policy-relative difficulty

Before diving deep into the selection of training tasks, a disclaimer:

> No ThinkingBox-Bench task was included in the RL training pool. The benchmark was reserved for evaluation.

ThinkingBox-Bench is out-of-distribution relative to the RL training pool: its domains, databases, policies, and most tools were not encountered during RL training. The two sets still share the ThinkingBox framework, simulated-user machinery, executable terminal-state grading, a few common tools, and a similar task style. These shared elements limit the scope of the transfer claim.

Why selection matters comes down to one arithmetic fact about GRPO. If all eight rollouts fail, the reward vector is `[0, 0, 0, 0, 0, 0, 0, 0]`. If all eight succeed, it is `[1, 1, 1, 1, 1, 1, 1, 1]`. In either case, centering within the group produces no task-reward advantage because no trajectory did better than another.++

A mixed group such as `[0, 0, 0, 1, 1, 1, 1, 1]` supplies the contrast GRPO can learn from. That distinction is expensive for a stateful agent: every rollout provisions an isolated backend, runs a real tool session, and calls a separate model to play the user.

The question that shaped this work was therefore not only *which model or optimizer?* It was: **which candidate tasks should enter the fixed training pool?**

We used an offline pass-rate filter on the posterior to select the training pool. It estimates which tasks are likely to produce contrasting terminal rewards under the base policy.

So we probe. Each candidate task is run repeatedly against the **base policy** model. The plain-language rule is simple: tasks the model always fails are unlikely to teach it yet; tasks it always passes are already learned; **tasks it solves sometimes are where outcomes can provide contrast.**

### Estimating difficulty from limited probes

Each candidate task is run *n* times, producing *k* successes. We model its latent success probability with Jeffreys posterior probability:

> success probability | k successes in n probes  ~  Beta(k + ½, n − k + ½)

[![fig5-policy-relative-difficulty](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/eR45y7Dl0VFFK3HinwDYg.png)](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/eR45y7Dl0VFFK3HinwDYg.png)

*Figure 6. Offline policy-relative difficulty is estimated from repeated base-policy probes and used to retain tasks likely to produce contrasting rewards.*

We partition the unit interval into five buckets with boundaries at 0.08, 0.40, 0.60, and 0.90, chosen as hyperparameters for these runs. Each task is assigned to the bucket containing the greatest posterior mass:

- **Rarely solved [0, 0.08):** drop
- **Difficult [0.08, 0.40):** keep
- **Intermediate [0.40, 0.60):** keep
- **Frequently solved [0.60, 0.90):** keep for full-parameter RLFT
- **Nearly always solved [0.90, 1]:** drop

Further details are in [Appendix C.4 of our ThinkingBox paper](https://arxiv.org/pdf/2608.19741).

### One task, end to end

[![fig6-worked-example](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/IBBkNpYKQRK6jBLSusMXw.png)](https://cdn-uploads.huggingface.co/production/uploads/64b8491203124195cd795cad/IBBkNpYKQRK6jBLSusMXw.png)

*Figure 7. Zooming in, one task through all six stages: GPT-5.4 screening, base-model probes, difficulty classification, a rollout group, terminal-state grading, and a GRPO update.*

Figure 7 follows one candidate task that can potentially enter the training pool. For the Qwen3.8 27B full-parameter pool, GPT-5.4 first served as a solvability screen. The base policy then succeeded on few of the probes e.g 3 of 8, producing a Beta(3.5, 5.5) posterior. Its largest mass, 54.0%, fell in the Difficult band.

When sampled for training, the task produced the mixed reward group `[0, 0, 0, 0, 1, 1, 1, 1]`. Successful trajectories therefore received above-mean task advantage and failed trajectories below-mean advantage, giving GRPO contrast to learn from. A different policy model could place the same task in a different difficulty band.

The final Qwen3.8-27B curated training pool contained 187 tasks.

## What earns a reward

Nothing about the trajectory. The reward is the task's own executable verdict.

When an episode ends, the sandbox extracts what actually changed in the backend and runs the task's deterministic checks against the terminal state. Any trajectory that produces the correct end state passes. Wrong, missing, or extra side effects fail. The reward is 1 or 0.

In the benchmark, the database grader can be thought of as the “examiner”: it caught agents that reported success and left the wrong record. In training, the same kind of check can be seen as the “teacher” on a different, disjoint set of tasks.

> Two reward paths, one binary verdict
> 
> Executable check (the large majority). When the required outcome is represented in terminal state or side effects, a deterministic test accepts or rejects it; no LLM judge call is needed.
> Judge-assisted check (a minority). When a narrow requirement cannot be determined cleanly from database state, the configured LLM judge answers a binary rubric question used by the executable test.

## Run the training stack

We release the data-selection, rollout, reward, and Verl integration used to train Qwen3.8-27B in [microsoft/thinkingbox-training](https://github.com/microsoft/thinkingbox-training). The repository README is the entry point. The detailed guides are:

- [`docs/data-preparation.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/data-preparation.md) for task hydration, policy probes, benchmark exclusion, and train/validation splitting;
- [`docs/reference-q38-run.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/reference-q38-run.md) for the validated 24-H100 Qwen3.8 configuration;
- [`docs/evaluation.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/evaluation.md) for merging a checkpoint and running ThinkingBox-Bench 507 x 20.

### Before you start

Tested on Linux and WSL with Python 3.12 and [uv](https://docs.astral.sh/uv/). You need NVIDIA GPUs with a compatible CUDA/NCCL stack, a local Qwen3.8-27B checkpoint, and OpenAI-compatible endpoints for the simulated user and judge. The validated reference configuration uses 3 nodes x 8 H100 GPUs; smaller custom configurations depend on model size, context length, and rollout concurrency.

The public sample task list exercises the interface. It is not the private 187-task training pool used for the reported run. Supply an authorized training source that remains disjoint from the public benchmark.

### Install

Keep the three repositories side by side:

```
mkdir -p ~/thinkingbox-workspace
cd ~/thinkingbox-workspace

git clone https://github.com/microsoft/thinkingbox.git
git clone https://github.com/microsoft/thinkingbox-data.git
git clone --branch main https://github.com/microsoft/thinkingbox-training

git -C thinkingbox checkout 892964e7226044e5463ad188da119df838f4bec1
git -C thinkingbox-data checkout thinkingbox-bench-v1.0
```

### Create the validated environment

The released stack targets Linux, Python 3.12, Verl 0.9.0, and the pinned package lock:

```
cd ~/thinkingbox-workspace/thinkingbox-training

uv venv --python 3.12
source .venv/bin/activate

uv sync --frozen --extra fast --extra tracking --extra eval-proxy
uv pip install -e ../thinkingbox
uv pip install --config-settings editable-mode=compat \
  -e ../thinkingbox-data/servers/thinkingbox_tools
uv pip install --config-settings editable-mode=compat \
  -e ../thinkingbox-data/servers/tb_business_ops_servers_202606

python scripts/prepare_verl.py --dest .deps/verl --install
python scripts/verify_verl_install.py
uv pip check
```

The final two commands should report a verified patched Verl checkout and no broken requirements. Do not run another automatic package sync afterward: it can replace the patched source installation with the vanilla Verl wheel.

### Prepare the training data

Start with the publicly provided samples, or add your own authorized dataset in ThinkingBox format. Then run the repository's preparation script:

```
cd ~/thinkingbox-workspace/thinkingbox-training
source .venv/bin/activate
python data/prepare_data.py --help
```

The script aggregates policy probes, applies offline policy-relative difficulty filters and benchmark exclusions, and writes the selected `train.yaml` and `test.yaml` files. [`docs/data-preparation.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/data-preparation.md) documents the input fields, loader contract, and complete command.

### Configure and inspect the launch

Follow [`docs/reference-q38-run.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/reference-q38-run.md) to start Typesense and the MCP servers, configure the simulated user and judge, set the model, task-list, checkpoint, and topology variables, and prepare the Ray cluster. Keep credentials in runtime secret injection rather than committed files or shell history.

Before allocating a training job, use the guide's dry-run command:

```
DRY_RUN=true ./scripts/run_train.sh \
  trainer.total_training_steps=50 \
  trainer.save_freq=5
```

It must exit zero without starting Ray or allocating GPUs. Read the emitted `python -m verl.trainer.main_ppo` command and every resolved override before launching the run.

### Train

The launcher configures training; it does not provision hosts. On the reference three-node topology, export the same environment on every node, mount `CHECKPOINT_DIR` at the same absolute path, then start Ray:

```
# head node
ROLE=head NODE_IP="$HEAD_IP" GPUS_PER_NODE=8 \
  ./scripts/start_ray.sh

# each worker node
ROLE=worker NODE_IP="$WORKER_IP" \
  HEAD_ADDRESS="$HEAD_IP:6379" GPUS_PER_NODE=8 \
  ./scripts/start_ray.sh
```

After `ray status` reports all 24 GPUs, launch once from the head node:

```
export RAY_ADDRESS=auto
export GPUS=0,1,2,3,4,5,6,7

./scripts/run_train.sh \
  trainer.project_name=thinkingbox-training \
  trainer.experiment_name=q38-full-rlft \
  trainer.total_training_steps=50 \
  trainer.save_freq=5
```

### Evaluate the checkpoint through OpenEnv

The [first ThinkingBox post](https://huggingface.co/blog/microsoft/thinkingbox#run-it-yourself) covers Typesense, the MCP Session Proxy, and OpenEnv setup. Merge the trained checkpoint following [`docs/evaluation.md`](https://github.com/microsoft/thinkingbox-training/blob/8c04db18da362357dc8a2d4ab187f44a8d63e20a/docs/evaluation.md), then serve it with vLLM.

From the OpenEnv repository root, set `MERGED_MODEL` to the merged model directory and `THINKINGBOX_DATA` to the pinned benchmark checkout. The historical checkpoint evaluation used this eight-A100 serving configuration:

```
vllm serve "$MERGED_MODEL" \
  --served-model-name q38-rlft \
  --host 127.0.0.1 \
  --port 8001 \
  --tensor-parallel-size 8 \
  --dtype bfloat16 \
  --max-model-len 262144 \
  --gpu-memory-utilization 0.85 \
  --max-num-seqs 16 \
  --max-num-batched-tokens 8192 \
  --language-model-only \
  --enable-chunked-prefill \
  --enable-prefix-caching \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_xml
```

## Where this goes next

The useful part of this work is not one Qwen3.8-27B checkpoint. It is the training loop and training data curation that turns executable outcomes into rewards.

If you are training or evaluating an agent that touches real database records:

- **Probe before you train.** Take your own agent task set, run the base policy against it *n* times, and look at the band histogram. In our experience teams often have not inspected this distribution, and it is usually more lopsided than expected.
- **Check your parity.** Replay the same recorded model output through the training and evaluation parsers, and verify that both extract identical tool names and arguments. Otherwise, training may reward behavior that evaluation interprets differently.
- **Report both coverage and repeatability.** State how many tasks pass at least once in *k* attempts and how many pass all *k*. A model that occasionally finds a solution is not necessarily one that repeats it consistently.
