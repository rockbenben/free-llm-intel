从历史上看，tokenizer 并不是 ML 工作流里的瓶颈。就计算量而言，与流水线其余环节里繁重的建模相比，tokenization 很轻。但在某些情况下，它已经迅速成为加速（或拖慢）你机器学习工作的关键。

随着模型变得更快、工作负载不断扩展，这种平衡开始发生变化。在海量数据集上训练、服务大量并发请求，或反复处理长输入，都可能给 tokenizer 施加足够大的压力，以至于它让模型因为拿不到数据而空等。

这正是我们在即将到来的 tokenizers version 1 中把重心大量压在性能上的原因。tokenization 应当是轻量的，并且应当随你的工作流一起扩展。你的 GPU 绝不该因为 CPU 还在完成 tokenization 而闲置等待。

在本文中，我们来看是什么让 v1 比 v0.23 更快——而且往往快上数十倍。

这项工作完全得益于生态系统的其余部分。tokenization 是一个非常活跃的开源领域，[gigatoken](https://github.com/marcelroed/gigatoken)、[tiktoken](https://crates.io/crates/tiktoken-rs)、[kitoken](https://crates.io/crates/kitoken)、[tokie](https://crates.io/crates/tokie)、[fastokens](https://crates.io/crates/fastokens)、[wordchipper](https://crates.io/crates/wordchipper) 和 [ai-tokenizer](https://www.npmjs.com/package/ai-tokenizer) 等库，以及许多其他项目，各自都在推进"一个快速的 tokenizer 究竟能有多快"这件事。我们读过这些工作，下面有好几个想法之所以来到我们面前，是因为另一个项目已经证明它们值得一试。

在这次重构之前，tokenizers 远没有达到它本可达到的性能，所以为它贡献代码看起来可能并不划算。通过这次重构，我们希望清楚地表明：我们打算让 tokenizers 成为一个值得贡献的库。

我们还要感谢 IBM、NVIDIA 以及 ExecuTorch 团队贡献补丁，并帮助我们在很宽的硬件范围内进行测试，以拓宽平台支持。

## 结果

我们展示 tokenizers v1 的 release candidate 相对其他广泛使用的替代方案的结果。内容涵盖单线程、多线程、跨线程扩展、逐模型对比、逐语言对比、延迟、decode 吞吐、内存堆，以及 crate 体积。

这些是在 [tokbench](https://github.com/huggingface/tokbench) 仓库里跑出来的，我们还提供了一条命令，如果你愿意，可以在自己的硬件上重新运行这些 benchmark。

## V1 是什么

v1 会产出与 v0.23 完全相同的 token ID。目标是保留输出、API、词表和 merge rank，并把一切**能够**改进的地方都改进。这也包括覆盖面。这个库在各个 tokenizer 家族之间保持通用，而不是只针对 BPE 做特化，所以 v0.23 能加载的东西 v1 都能加载。

tokenizer 把文本转换成模型所读取的整数列表。tokenizers 分四个阶段完成这一转换。Normalization 对原始文本应用小写化或 Unicode normalization 之类的操作。Pre-tokenization 把文本切分为更小的片段，称为 pre-token。model 阶段把每个 pre-token 变成 token，并把它们映射到词表里的 ID。Post-processing 补上模型所期望的任何 special token。

本文所描述的绝大部分工作都发生在 model 阶段。本文测量的十个 model 家族里，有八个使用 byte pair encoding，也就是 BPE。BPE 从一个 pre-token 的字节出发，反复合并 rank 最高的相邻 pair，直到不再存在带 rank 的 pair。这个排序在 tokenizer 训练时学得，并随它一起分发，所以同样的文本永远产出同样的 ID。一次 merge 绝不会跨越 pre-token 的边界。剩下两个家族使用 WordPiece 和 Unigram，即这个库支持的另外两种 model 类型。

[tokenization pipeline](https://huggingface.co/docs/tokenizers/pipeline) 页面记录了这四个阶段。[Tokenization algorithms](https://huggingface.co/docs/transformers/tokenizer_summary) 记录了 BPE、WordPiece 和 Unigram。

每个阶段都被动过。以下是真正起作用的改动：

| 改动 | 作用 |
| --- | --- |
| workspace 拆分 | 一个 crate 变成一个 workspace：`tk-encode` 是必需的运行时，而 `tk-serialize`、`tk-convert` 和 `tk-train` 只在应用需要时才链接 |
| 无分配的 model | merge 的工作集存放在调用方持有的 scratch buffer 里；循环完全不触碰分配器 |
| bitcannon | 切分模式变成对位流（bitstreams）的布尔运算，用 SIMD 指令来找切分点，而不是靠 regex 引擎 |
| merge 循环重写 | 参与合并的各个 piece 在一块预分配缓冲区内组成一条侵入式双向链表，于是一次合并只需更新两个索引，而不必搬动数据 |
| word cache | 一份线程本地的 memo，从 pre-token 的字节映射到最终的 ids，于是重复出现的词只合并一次 |
| 原生并行 | 一个共享的 tokenizer 可以同时被许多线程 encode；每个线程从自己的子池里取用它的 scratch buffer 和 word cache，于是线程不再在单一把锁上排队（[#2365](https://github.com/huggingface/tokenizers/pull/2365)） |

### 切分：用位流取代 regex

BPE model 使用一条正则表达式把输入文本切分成更小、更易处理的块，称为 pre-token。合并发生在 pre-token 内部，绝不跨越两个 pre-token 之间的边界，所以这次切分决定了流水线其余部分看到什么。

那条正则表达式是 model 的一个固定参数。它随 tokenizer 一起分发，运行时从不改变，因此没必要在每次 encode 时都让一个通用 regex 引擎去解释它。针对某个 model 实际使用的那条模式，人工手写一个等价的切分函数就可以了，而且只需写一次。

手写函数随后可以利用现代 CPU 的 SIMD 指令（single instruction, multiple data），它们一次就把同一个操作施加在许多字节上，很适合 UTF-8 文本。bitcannon 把输入的字节看作并行的比特流，于是边界是从对整个寄存器的布尔运算里直接得出的，而不是一次只前进一个字符的扫描。它每个寄存器操作就能判定 64 个字节。同样的思路也驱动着用于文本处理的 [Parabix](https://www.cs.sfu.ca/~ashriram/papers/2012_HPCA_Parabix.pdf) 和用于 JSON 的 [simdjson](https://arxiv.org/abs/1902.08318)。

这取决于能否识别出那条模式。少数几种语法就覆盖了大多数 byte-level BPE model，而模式不在其中的 tokenizer 会保留 regex 路径，这份加速一点都得不到。这正是上面的收益为何差异如此之大。

### Word Cache

真实文本里有大量重复的词。由于 BPE 对给定的 pre-token 永远产出相同的 token ID，v1 可以在处理一次之后就把结果存下来。一份线程本地缓存把每个 pre-token 的字节映射到它的 token ID，让后来再次出现的同一个词跳过整个合并过程。

很自然，随着输入变长，唯一词的数量可能比词的总数增长得更慢。于是重复词在输入中所占的比重不断上升。但仍然会有新词出现，这也解释了下面动画里偶尔的未命中。

用这条命令复现 shared-prefix 的结果：

```
tokbench measure prefix-sharing \
  --engine pipeline \
  --engine hf-tokenizers \
  --compare-to pipeline-no-cache \
  --corpus agentic_swe
```

缓存最适合包含重复 pre-token 的输入。重复 pre-token 很少的输入可能付出了查找的开销，却换不来多少次命中。

### merge 循环

下一个主要开销来自 BPE 的 merge 循环。对每个 pre-token，循环反复找出优先级最高的相邻 pair 并把它合并。此前的实现每次调用都要分配新的内存，并为每个 pre-token 建一个新的优先队列。

v1 复用由调用方持有的 scratch buffer，去掉了那些重复分配。它把符号存放在一个扁平数组里，并用符号在该数组中的位置来链接相邻符号，这使得合并过程中的更新更便宜。它还把一批 pre-token 放在一次 model 调用里处理。

每个候选 pair 也被打包进单个 64 位值中，merge rank 放在高位。于是比较两个候选就是比较两个整数，而"这里没有可合并的"就是最大可能值，所以循环不需要分支就能找到下一次合并。

## 方法

benchmark 设计上的细小差别，就可能让 tokenizer 的性能表现出现巨大差异。我们用以下规则来保持各引擎之间比较的一致性。

| 规则 | 原因 |
| --- | --- |
| 一条计时循环 | 每个引擎跑完全相同的循环；不给任何引擎单独准备 fast path |
| 不计入加载 | 词表加载单独计时，绝不放进 encode 里面计时 |
| id 哈希校验 | 对输出 ids 做 FNV-1a，必须与基线完全一致 |
| 只取公共单元格 | 中位数只在每个引擎都跑过并校验过的单元格上计算 |
| 每个进程跑完整扫描 | 每次 repeat 都在新进程里开始，并保留所有单元格 |
| 物理核心绑核 | worker 绑定在八个不同的物理核心上，绝不使用同一核心的 SMT 兄弟线程 |
| 独立 Jobs | 用分开的 Jobs 来测量主机之间的波动 |

在同一个 build 上，反复 encode 同一份文档可能比 encode 一串各不相同的文档更快。第一种做法测量的是整份文档已经存在于缓存中时的性能。第二种测量的是在新输入上的性能，同时允许此前见过的 pre-token 留在缓存里。

这两种条件有时都被描述为"暖机（warm）"，尽管它们测量的是不同的工作负载。我们的头条结果使用的是各不相同的文档，而且完整语料太大，装不进缓存。tokenizer benchmark 应当说明自己用的是哪种工作负载，因为这个选择可能完全左右结果。

## 这些加起来意味着什么

在 v1 的 encode 路径所覆盖的十个 model 家族上，单线程在 Apple M4 Max 上 encode 文本比 v0.23 快 **3 到 30 倍**。低端是 t5-base，高端是 gpt2。八个 worker 时它扩展到线性加速的 **76%**。贯穿所有这些改动，v1 产出的 token ID 与已发布的库完全一致。

整体提升来自若干改动的协同：一个取代 regex 引擎的手写切分器，一个能在重复词出现时直接给出答案而不必重新合并它的缓存，一个绝不触碰分配器的 merge 循环，以及对每批 pre-token 发起一次 model 调用而不是每个 pre-token 一次。每一项都在流水线的不同位置减少所做的事。

下一个优先级是支持更多 model 家族。我们会在 `1.0.0` 之前把更多 model 迁到新的 merge 循环上。一旦 release candidate 稳定下来，下一步就是把这份改进带到依赖 tokenizers 库的 transformers 库以及其余生态中。

本文根据 [tokbench](https://github.com/huggingface/tokbench) 的结果生成，并会随着支持范围的扩大而更新。

## 如何获取

v1 的 release candidate 已经在 crates.io 上。你调用的 API 就是你已经在调用的那一个，所以唯一变化的是你安装哪个 build。

就是寻常的安装方式：

```
cargo add tokenizers --pre
```

训练功能藏在一个默认开启的 feature 之后，它还会连带拉进一个 C++ 依赖。如果你只需要 encode，把它关掉即可排除训练实现：

```
cargo add tokenizers --pre --no-default-features --features http
```

encode 没有任何变化：同样的调用，同样的 ids。

```
use tokenizers::tokenizer::{Result, Tokenizer};

fn main() -> Result<()> {
    let tokenizer = Tokenizer::from_pretrained("deepseek-ai/DeepSeek-V4-Flash", None)?;

let encoding = tokenizer.encode("The tokenizer is no longer the bottleneck.", false)?; println!("{:?}", encoding.get_ids()); // [671, 17840, 9160, 344, 1119, 5827, 270, 111127, 16] println!("{:?}", encoding.get_tokens()); // ["The", "Ġtoken", "izer", "Ġis", "Ġno", "Ġlonger", "Ġthe", "Ġbottleneck", "."]

Ok(()) } ```

对于批量数据，`encode_batch` 才是跨核心扩展的那个调用。上面那个扩展性视图测量的就是它。

```rust
let encodings = tokenizer.encode_batch(documents, false)?;
```

本文里的每一个数字都是针对这个 crate 测量的。Python bindings 封装的是同一套代码，从 `bindings/python` 构建，但它们会带来每次调用的额外开销，而这些测量都不包含这部分开销。

## 迈向 V1 的进展

本文的 benchmark 覆盖前面列出的已完成的 release-candidate 工作。其余小节说明 `1.0.0` 还需要做什么，以及我们之后打算探索什么。

### Release Candidate：已实现

这些工作都在 crates.io 上的 Rust 预发布版本里：

```
cargo add tokenizers --pre
```

- workspace 拆分：把单个 crate 拆成 `tk-encode`、`tk-serialize`、`tk-convert` 和 `tk-train`，于是应用只链接它用到的东西
- bitcannon：用位流运算取代 encode 路径上的 regex 切分，覆盖 GPT-2、cl100k、o200k、Tekken 和 DeepSeek。这取代了最初随版本发布的有限状态机 [#2201](https://github.com/huggingface/tokenizers/pull/2201) [#2317](https://github.com/huggingface/tokenizers/pull/2317)
- WordCache：复用此前已处理过的 pre-token 的 token ID [#2262](https://github.com/huggingface/tokenizers/pull/2262)，`af5a3e3`
- 更快的查找与合并结构：加入 FlatCache、MPHF RankStore、增量式合并，以及 BucketVocabStore [#2190](https://github.com/huggingface/tokenizers/pull/2190) [#2188](https://github.com/huggingface/tokenizers/pull/2188)
- 可复用的 model 内存：把临时的 model 状态挪进 scratch buffer，于是 tokenization 不必每次调用都分配 [#2175](https://github.com/huggingface/tokenizers/pull/2175) [#2183](https://github.com/huggingface/tokenizers/pull/2183)
- 流水线 post-processing：把 post-processing 作为 `STAGE_POST` 流水线阶段暴露出来 [#2182](https://github.com/huggingface/tokenizers/pull/2182)
- 批量 model 调用：在一次调用中处理多个 pre-token span [#2304](https://github.com/huggingface/tokenizers/pull/2304)
- 更快的 decode：把解码出的字节直接写入一个可复用的缓冲区，避免中间字符串和拷贝，加速 token 查找，支持带缓冲的流式输出，并并行 decode 批量数据
- `role_to_token` 支持 [#2343](https://github.com/huggingface/tokenizers/pull/2343)
- Node.js bindings [#2281](https://github.com/huggingface/tokenizers/pull/2281)

### 1.0.0

- 单一的 encode 实现：在训练校验期间使用 `tk-encode`，让训练和推理不可能产出不同的 tokenization 结果
- 可选的 offsets 和 masks：只有被请求时才计算这份元数据，把它挡在只取 token ID 的路径之外
- 重做 normalizer
- bitnorm 支持，建立在 atomnorm 之上 [#2209](https://github.com/huggingface/tokenizers/pull/2209)
- spm 预编译
- 更简洁的 Python bindings：减少加锁、包装类型和手写的 dispatch 代码，同时保留子类化、序列化、自定义 decoder、mutating 行为，以及对 free-threaded CPython 的支持
- 仅供推理的 C 与 C++ bindings，面向 ExecuTorch 和 llama.cpp，之后可能跟进 JVM、Swift 和 Go 的 bindings

### 1.0.0 之后

- tok-devices：探索 GPU encode 与批量 decode，同时把文本和 token ID 留在设备上。decoder 会一次性上传词表，并行计算输出位置，并在 GPU 上收集对应的字节。这将是一个可选组件，面向大批量场景，还需进一步做原型和测量。
