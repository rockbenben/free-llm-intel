`hf` 是 Hugging Face Hub 官方命令行入口。凡是用 Python SDK 能在 Hub 上做的一切，你现在都能在终端里完成：下载和上传模型、数据集与 Space；创建和管理仓库、分支、标签与 pull request；在 HF 基础设施上运行 Jobs；管理 Buckets、Collections、webhooks 与 Inference Endpoints。

多年来 `hf` CLI 主要为用户而建。但它如今正被越来越多的 **coding agent** 使用：Claude Code、Codex、Cursor 等等。于是我们重构了它，让两类受众同时好用。这篇博文总结了我们做了什么、以及我们如何对其做了基准测试。我们发现，在复杂的多步任务上，无 CLI 基线（agent 手写 `curl` 或 Python SDK）消耗的 token 多达 `hf` CLI 的 **6 倍**。

## Hub 上的 AI agent 流量

我们从 2026 年 4 月开始追踪 Hub 上的 agent 使用情况。`hf` CLI（以及它所基于的 `huggingface_hub` Python SDK）通过读取 agent 设置的环境变量来检测是否由 coding agent 驱动：Claude Code 的 `CLAUDECODE`/`CLAUDE_CODE`、Codex 的 `CODEX_SANDBOX`，加上 Cursor、Gemini、Pi，以及通用的 `AI_AGENT`。这一个信号起到两个作用：它影响 CLI 的输出（下文详述），并给每个 Hub 请求打上 `agent/<name>` 的 user-agent 标签，使我们能把流量归因到驱动它的 agent。按独立用户数排名前两位的是 **Claude Code 和 Codex**，遥遥领先其他，也正是本文后文基准测试的两个 agent。

图中条形统计每个 agent 的独立用户数，请求量标在副标签上。仅 Claude Code 就约有 4 万用户、近 4,900 万请求，Codex 紧随其后。这些还是早期数字（我们从 2026 年 4 月才开始归因 agent 流量），但规模已经可观。随着 coding agent 成为使用 Hub 的标准方式，我们预计它还会持续增长。

## 为人类和 agent 而造

人类和 coding agent 对同样的 `hf` 命令期待不同的输出。人想要丰富的终端输出：ANSI 颜色、补齐并对齐到屏宽后截断的表格、成功时绿色的 ✅、布尔值的 `✔`、进度条、文字提示。agent 想要的恰好相反：没有 ANSI、不截断、每个值都完整——因为 agent 能消化远比人密集的输出，同时保持紧凑结构化以节省 token。它也无法回答交互式 CLI 提示，超时后会乐呵呵地重跑命令。本节余下内容就是 `hf` 如何各取所需。我们在 `hf` v1.9.0 引入了 agent 模式输出，并在之后的版本中逐步把 CLI 其余部分迁移过来。

### 一条命令，多种渲染

当 `hf` 自动检测到 agent 使用（通过上述环境变量），它会对**同一条命令**做不同渲染。无需加 flag，就能针对人或 agent 优化输出格式：

```
# human (default in a terminal): aligned table, truncated to fit, with a hint
> hf models ls --author Qwen --sort downloads --limit 3
ID                       CREATED_AT DOWNLOADS LIBRARY_NAME LIKES PIPELINE_TAG    PRIVATE TAGS
------------------------ ---------- --------- ------------ ----- --------------- ------- -------------------------
Qwen/Qwen3-0.6B          2025-04-27  21156913 transformers  1285 text-generation         transformers, safetens...
Qwen/Qwen2.5-1.5B-Ins... 2024-09-17  15143953 transformers   725 text-generation         transformers, safetens...
Qwen/Qwen3-4B            2025-04-27  14808352 transformers   625 text-generation         transformers, safetens...
Hint: Use `--no-truncate` or `--format json` to display full values.

# agent (auto-detected): TSV, full ids + ISO timestamps + every tag, nothing truncated
$ hf models ls --author Qwen --sort downloads --limit 3
id      created_at      downloads       library_name    likes   pipeline_tag    private tags
Qwen/Qwen3-0.6B 2025-04-27T03:40:08+00:00       21156913        transformers    1285    text-generation False   ['transformers', 'safetensors', 'qwen3', 'text-generation', 'conversational', 'arxiv:2505.09388', 'base_model:Qwen/Qwen3-0.6B-Base', 'base_model:finetune:Qwen/Qwen3-0.6B-Base', 'license:apache-2.0', 'text-generation-inference', 'endpoints_compatible', 'deploy:azure', 'region:us']
```

**人类**得到对齐的表格、按终端宽度截断，外加一条如何查看更多内容的提示，并有颜色状态提示（成功绿色 `✓`，错误红色）。**agent** 得到 TSV 形式的完整记录：完整仓库 id、完整 ISO 时间戳、所有标签、无 ANSI 码、无截断，好解析且省 token。

实践中，我们实现了 `.table(...)`、`.result(...)`、`.json()` 等日志方法，它们接收原始数据并负责格式化。除人和 agent 模式外，我们还引入了 `--json` 和 `--quiet` 选项，方便把命令串联管道。默认模式根据上下文自动选择，但用户始终可以用 `--format human | agent | json | quiet` 强制指定格式。

### 下一步命令提示

CLI 命令很少孤立运行：一步通常意味着下一步（先 `git add` 再 `git commit`）。许多 `hf` 命令现在以一个**提示**结尾：要运行的下一条确切命令，并预填你刚用过的 ID，用户或 agent 可以直接衔接下一步，而不必从零推导。后台启动一个 Job，它会指向日志；创建一个 Space，它会指向启动状态：

```
$ hf jobs run --detach python:3.12 python train.py
✓ Job started
  id: 6f3a1c2e9b
  url: https://huggingface.co/jobs/celinah/6f3a1c2e9b
Hint: Use `hf jobs logs 6f3a1c2e9b` to fetch the logs.
```

对人这是便利；对 agent 这是轨道：下一个动作被点名、带上正确的 id 参数、随时可跑，agent 因此不用花步骤去想该做什么。错误也照样处理——指出修法而不是仅仅失败：

```
Error: Not logged in. Run `hf auth login` first.
```

提示、警告与错误全部走 stderr，数据走 stdout，因此这些引导不会污染 agent 正在解析的输出。

### 不阻塞、可安全重试

`hf` 绝不会卡在交互式提示上等一个 agent 按不了的键。破坏性命令仍会请人类确认，但在 agent 模式下它会*快速失败*，并把解决办法写进消息（`Use --yes to skip confirmation.`），`-y`/`--yes` 可跳过确认。而且由于 agent 会在超时或上下文丢失后重试，所有操作都被设计为可安全重复执行：仓库已存在时 `hf repos create --exist-ok` 是空操作，重跑上传也能干净地重新 commit。另外，搬运真实数据的命令都提供 `--dry-run`，在执行前精确展示将要传输的内容——这对人和 agent 都很方便，谁都不用贸然开始一次长下载或盲目同步：

```
# agent mode: a destructive command without --yes refuses, with the fix in the message
$ hf repos delete my-org/old-model
Error: You are about to permanently delete model 'my-org/old-model'. Proceed? Use --yes to skip confirmation.

# commands that move data take --dry-run to preview the transfer first
$ hf download deepseek-ai/DeepSeek-V4-Pro config.json --dry-run
[dry-run] Will download 1 files (out of 1) totalling 1.8K.
file         size
config.json  1.8K
```

### 可发现、可预测的命令

`hf` 生来就欢迎试探：运行 `hf` 查看资源分组，对你需要的分组跑 `--help`，每个 `--help` 都以真实的、可复制粘贴的示例结尾（agent 匹配示例远比解析描述文字来得快）：

```
$ hf models ls --help
...
Examples
  $ hf models ls --sort downloads --limit 10
  $ hf models ls --search "qwen" --author Qwen
  $ hf models ls Qwen/Qwen3-4B --tree
```

命令树是一致的**资源 + 动词**结构，配以显然的别名（`hf models ls`、`hf repos create`、`hf jobs ps`、`hf collections delete`；`list`/`ls`、`remove`/`rm`），agent 学会一条命令就能推断其余。输出也可组合：`-q` 每行输出一个 id 以便管道给下一条命令，`--json` 给你可交给 [`jq`](https://jqlang.org/) 的内容。

```
$ hf models ls --author Qwen -q | head -3
Qwen/Qwen3-0.6B
Qwen/Qwen2.5-1.5B-Instruct
Qwen/Qwen3-4B
```

## 面向 Coding Agent 的 hf CLI 基准测试

为了弄清 `hf` CLI 对 agent 是否真的更高效，我们做了测量。我们搭建了一个小型评估 harness，把同一批 Hub 任务用每种与 Hub 交互的方式反复运行，并对照线上 Hub 为每次运行评分。在讲方法之前先给结论：在两个 agent 上，`hf` CLI 全面领先——在复杂多步任务上最明显，token 用量显著更少。

| agent | tool | success score | token usage | self-report error |
| --- | --- | --- | --- | --- |
| **Claude Code (Sonnet 4.6)** | `hf` CLI | **0.94** | baseline | **2 / 163** |
|  | curl / Python SDK | 0.84 | **1.3-1.6× tokens** | 11 / 163 |
| **Codex (GPT-5.5)** | `hf` CLI | **0.93** | baseline | **3 / 163** |
|  | curl / Python SDK | 0.92 | **1.6-1.8× tokens** | 10 / 163 |

*（self-report error = agent 在 17 个可解任务上报告成功、但 Hub 状态并不如此。`hf` CLI 各行是安装了其 skill 的 CLI；skill 在裸 CLI 之上带来的增益（主要是更少的工具调用）在下文 [skill 一节](https://huggingface.co/blog/hf-cli-for-agents#the-hf-cli-skill)单独拆出。有代表性的对话记录发布在[这个 bucket](https://huggingface.co/buckets/celinah/hf-cli-agent-benchmark) 中。）*

### 实验设置

我们定义了 **18 个非平凡的 Hub 任务**。不是「下载一个文件」，而是你实际会提的需求：汇总一个趋势 org 的模型、查看仓库文件及其大小、按 include/exclude 规则上传文件夹、删除文件、跨仓库复制文件、开一个添加 license 的 PR、创建带分支和标签的仓库、同步并清理 bucket、构建 collection。每个任务交给一个全新的 coding agent，并限定恰好**一种**与 Hub 对话的方式：

- `hf` CLI，或
- **curl / Python SDK**：完全没有 `hf` CLI，agent 只能退回对 REST API 用 `curl`，或使用 `huggingface_hub` Python 库。

`hf` CLI 以两种配置运行：带其 skill 与不带 skill（一份自动生成的命令参考，留待[它自己的小节](https://huggingface.co/blog/hf-cli-for-agents#the-hf-cli-skill)再讲）。但下面的头条对比就是单纯的 **`hf` CLI vs curl / SDK**；skill 的增量效应很小，我们单独拆出，不挤进主结果。

配置刻意保持干净：每次运行全新实例，没有自定义 MCP server，没有 `CLAUDE.md` 或 `AGENTS.md`，上下文里没有任何引导行为的元素。任务与工具写进同一个 prompt，agent 以 `TASK_COMPLETE` 或 `TASK_FAILED` 标记收尾，但我们不信任该标记（agent 会为根本没落地的工作报告成功），因此每次运行都独立**重新查询线上 Hub** 来评分：分支真的建了吗？文件真的删了吗？bucket 真的存在吗？由于 coding agent 是非确定性的，每个「任务 × 工具」组合跑 **10 次**，每个 agent 约 **520 次运行**（18 任务 × 3 工具 × 10 次，减去一个会计费的 Jobs 任务设的上限），总共约 1,000 次评分运行。整个实验跑了两遍，用两个最流行的 coding agent（**Claude Code** + Sonnet 4.6 与 **OpenAI Codex** + GPT-5.5）。

### 结果

下面两张图拆解上面的表格。首先是 **Sonnet 上的任务成功率**——curl 和 SDK 在它上面挣扎最多的 agent：

没有 CLI 时，curl 和 SDK 落后十个点，因为在 Sonnet 上它们就是完不成工作的某些部分（多半是写操作），而 `hf` CLI 能全部跨过。

第二张图展示 **GPT-5.5 上的 token 影响**，按任务拆解。每根条是同一任务上 curl/SDK 的 token 数除以 CLI 的 token 数，所以 `2.4×` 表示非 hf 版本做了同样的事却烧掉了 2.4 倍 token：

在一次读取型任务（数数据集行数、批量元数据）上，curl 和 SDK 没问题，有时甚至更省。但任务越复杂、涉及越多相互依赖的步骤，agent 就得手写整条 REST 调用链（或翻找 SDK），成本爆炸：在「创建带分支与标签的仓库」「删除文件」「跨仓库复制」「同步 bucket」这类任务上是 **CLI 的 2.4 到 6 倍**。`hf` CLI 让 agent 用几条高层命令就能表达任务，而不必编排复杂工作流。

### 关键发现

- **`hf` CLI 比 curl 或 SDK 省得多。** 同一任务、成功率持平或更好的情况下，curl 和 SDK 烧掉**约 1.3 到 1.8 倍的 token**。简单读取上它们没问题，但真正的多步工作上要付出 **2 到 6 倍**：CLI 把一串 REST 调用合成几条高层命令，而 curl 或 SDK 每次运行都要手工重新推导整条链。
- **在更强的模型上，curl 和 SDK 能用但仍然浪费。** 在 Sonnet 上它们完不成部分工作（多为写操作）；在 GPT-5.5 上大体成功——手写 REST 调用（或用 SDK）是正确的——但 token 账单依然远高于 CLI。

## hf-cli skill

`hf` 自带一个 **skill**：一份覆盖整个命令面的紧凑参考，agent 将其加载为上下文。它从活动的 `hf` 命令树**自动生成**，每条命令一行（签名、一行描述、以及重要 flags），按资源分组，附一个常用选项小词典。它有意省略不言自明的 flags 以保持简短省上下文，且每个版本都会重新生成。运行 `hf skills preview` 打印它，或用以下命令安装：

```
# for Codex, Cursor, OpenCode, Pi and other agents that load skills from `.agents/skills`
hf skills add
# includes the above + Claude Code
hf skills add --claude
```

它能给你带来什么？最主要是 agent 不再瞎猜。最直观的一个视角是每次运行消耗多少条命令——有 skill 与没有：

在两个 agent 上，都是每任务约十次命令降到约七次，工具调用大约减少 30%。这是因为 agent 不再靠试探 `--help` 来找正确的命令和参数。skill 不会削减你的 token 账单，因为它往上下文里前置一块固定信息，同一任务的 token 数大致持平或略增。skill 也不会让 CLI 更可靠，但它能让 agent 把时间花在执行你的任务上，而不是研究工具怎么用。在配合本地模型使用 `hf` 时，这一点可能尤其有帮助。

我们每个任务都在全新会话中运行，所以 skill 的上下文成本每个任务都要付一次。在真实的多任务会话里，该成本会被摊薄（agent 一次学会命令面），token 图景大概率会更好；我们没有测量这种情况。

## 自己动手试试

我们之所以对这一切做基准，是因为我们认为它重要。Agent 正在成为 Hub 的真实用户：它们训练模型、构建和清洗数据集、把 demo 作为 Space 上线——几乎总是代表某个人在做。对 agent 好用的 Hub，对使用 agent 的人也是更好用的 Hub。agent 的工具越好，它能为你做的事就越多。

如果你的 agent 要与 Hugging Face Hub 交互，我们推荐把 `hf` CLI 交给它：

```
# macOS / Linux
curl -LsSf https://hf.co/cli/install.sh | bash

# Windows (PowerShell)
powershell -ExecutionPolicy ByPass -c "irm https://hf.co/cli/install.ps1 | iex"
```

然后把 skill 也交给它，让它从第一轮对话起就知道整个命令面：

```
hf skills add            # Codex, Cursor, OpenCode, Pi and other agents that load skills from .agents/skills
hf skills add --claude   # the above + Claude Code
```

接着让 agent 面向 Hub、放手去干。确保已登录（`hf auth login`），然后给它一个类似这样的 prompt：

```
Use `hf` to list my Hugging Face Hub models, datasets, and Spaces.
Take a look at how I am currently using the Hub and suggest a few ways you could help me.
```

它会自己想办法组合命令，并带回有用的结果。

完整命令参考在 [`hf` CLI 指南](https://huggingface.co/docs/huggingface_hub/guides/cli)。

## 注册你的 agent harness

在构建 agent harness？**把它注册了！** `hf` 就是这样学会检测它的，Hub 也是这样把它的流量归因到你的 harness。只需开一个小 PR，在 [`agent-harnesses.ts`](https://github.com/huggingface/huggingface.js/blob/main/packages/tasks/src/agent-harnesses.ts) 里添加一条目。详情阅读 [Register your agent harness](https://huggingface.co/docs/hub/agents-overview#register-your-agent-harness) 指南。
