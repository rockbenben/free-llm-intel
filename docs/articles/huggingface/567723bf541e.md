Hugging Face 已成为规模化推进 AI 的代名词。Hub 上有超过 400 万构建者在部署模型，平台的快速增长促使我们重新思考敏感配置数据——密钥（secrets）——的管理方式。

去年，工程团队着手改进密钥与凭证的处理。在评估了 HashiCorp Vault 等工具后，他们最终选择了 [Infisical](https://infisical.com/)。

本案例研究详述了他们向 Infisical 的迁移、如何集成其强大功能，以及它如何让工程师更高效、更安全地工作。

## 背景

随着 Hugging Face 的基础设施从纯 AWS 演进为包含 Azure 和 GCP 的多云环境，工程团队需要一种更敏捷、更安全、更集中的密钥管理方式。他们没有改造遗留系统，也没有采用 HashiCorp Vault 这类重型方案，而是选择了 Infisical——因为它对开发者友好的工作流、多云抽象以及扎实的安全能力。

他们面临的关键挑战包括：

- 各环境管理不一致，导致「[密钥蔓延（secret sprawl）](https://infisical.com/blog/what-is-secret-sprawl)」风险上升。
- 团队扩张后权限管理复杂，需要与组织 SSO（Okta）集成的严格基于角色的访问控制（RBAC）。
- 本地开发棘手：传统 [.env 文件](https://infisical.com/blog/stop-using-env-files)既损害安全性又拖累开发效率。
- 手动密钥轮换负担沉重——一起涉及凭证泄露的安全事件让这点痛彻领悟。

此外，团队需要一个遵循基础设施即代码实践、支持按项目管理密钥、并在部署时于自动化与手动控制之间平滑权衡的解决方案。

## 实施

Infisical 灵活的架构是理想的解法。工程团队借此机会重新审视内部项目结构，把项目拆分为独立的基础设施域与应用域。这让他们能实现更清晰的关注点分离，并标准化密钥轮换实践——在近期安全事件的余波中，这是重中之重。

借助此前用于从 AWS 配置创建 Kubernetes secret 的 Terraform，他们发现迁移到 Infisical Kubernetes Operator 格外顺滑。这次集成在标准化所有环境的密钥管理的同时，带来了安全性的提升。

### Kubernetes 集成

Kubernetes 是 Hugging Face 生产环境的核心，Infisical 的 [Kubernetes Operator](https://infisical.com/docs/integrations/platforms/kubernetes) 在密钥更新自动化上功不可没。Operator 持续监控 Infisical 中任何密钥的变化，确保这些更新传播到对应的 Kubernetes 对象。检测到变化时，它可以自动重载依赖的 Deployment，确保容器始终运行最新的密钥。

**示例：**

Kubernetes 中运行的应用需要一个新密钥。可以通过 Infisical 的 CLI 或 Web UI 创建密钥，然后开发者在 Kubernetes 中创建一个 `InfisicalSecret` 资源，指定要同步 Infisical 中的哪个密钥：

```
apiVersion: infisical.com/v1alpha1
kind: InfisicalSecret
metadata:
  name: my-app-secret
  namespace: production
spec:
  infisicalSecretId: "123e4567-e89b-12d3-a456-426614174000"
  targetSecretName: "my-app-k8s-secret"
```

CRD 应用后，Infisical Operator 持续监听更新。当 Infisical 中检测到变化，Operator 会自动更新 Kubernetes secret（`my-app-k8s-secret`）。

用 Infisical 管理密钥的流程：Infisical 平台上的密钥更新后，Infisical Operator 自动把变更同步到所引用的 Kubernetes secret，进而供应用使用。

更好的是，由于应用的 Deployment 把 `my-app-k8s-secret` 作为环境变量来源或挂载卷引用，Operator 可以在密钥变化时自动触发容器重载。

实践中，尽管 Operator 能自动触发容器重启，Hugging Face 工程师仍倾向于等待手动重新部署。这个决定源于对部署的精确定位控制需求——尤其当流量高达每分钟千万级请求、副本数量众多时。

### 本地开发

本地开发方面，[Infisical CLI](https://infisical.com/docs/cli/usage) 把密钥直接注入开发环境，简化了工作流。这消除了不安全的本地 .env 文件，让本地配置对齐生产标准，并减少上手的摩擦。

## 安全与访问管理

安全改进是这次迁移的脊梁。把 Infisical 与 Okta 等既有身份提供商集成后，Hugging Face 建立了细粒度 RBAC 系统。权限自动从 Okta 组映射而来：开发者保留对其项目的管理权限，而前端与后端团队获得适当受限的读或写权限。

此外，[密钥共享](https://infisical.com/docs/documentation/platform/secret-sharing)功能让 Hugging Face 的 ML/AI 研究者们能安全共享凭证。中心化的 Infisical 平台还简化了审计与密钥轮换管理——此前几起安全事件正凸显了这一必要性。

## CI/CD 与基础设施集成

与 CI/CD 流水线的无缝集成进一步增强了整体安全态势。Infisical 通过 GitHub Actions 嵌入部署流水线，使用 [OIDC 认证](https://infisical.com/docs/documentation/platform/identities/oidc-auth/github)和 Terraform 集成。在安全环境内运行自托管 runner，使每次部署都符合生产级安全标准。这种一体化方式最小化了风险，并确保从本地开发到云端部署的一致体验。

## 技术成果与洞见

用 Infisical 集中密钥管理带来了实实在在的改进：

- 工程师不再需要花费宝贵时间手动配置环境密钥。自助式工作流加速了入职与日常开发循环。
- 自动化审计与细粒度访问控制实现了快速事件响应，并推动了安全的「左移（shift left）」实践。
- 跨云厂商、Kubernetes 集群与 CI/CD 流水线的统一集成消除了密钥管理的不一致，从而加固了基础设施的安全性与可靠性。

正如 Hugging Face 基础设施负责人 Adrien Carreira 所说：

> "Infisical 提供了我们提升安全态势、节省工程时间所需的全部功能与安全设置。无论你是在本地工作、在生产中运行 Kubernetes 集群，还是在 CI/CD 流水线中操作密钥，Infisical 都有无缝的预制工作流。"

## 结论

Hugging Face 向 Infisical 的迁移表明：以技术驱动、工程为中心地管理跨多云平台的密钥，能带来显著收益。面对类似挑战，使用 Infisical 是在保持安全强度的同时更高效工作的务实之选。

当安全的路径成为最轻松的路径，团队就能专注于构建创新产品，而不必担心密钥管理。
