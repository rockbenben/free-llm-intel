# 让 Token 持续流动：16 个开源 RL 库的经验

> TL;DR —— 给没时间读 5000 字异步 RL 管道细节的你（我们懂，你还要训模型）：
> 
> 问题：在同步 RL（强化学习）训练中，数据生成（用模型推理来创造数据样本）主导了墙钟时间——在 32B（320 亿参数）模型上跑一批 32K token 的 rollout 可能要几个小时，而用于训练的 GPU 全程空闲。
> 大家不约而同的解法：把推理和训练解耦（分离）到不同的 GPU 池，用 rollout 缓冲区（暂存模型输出的地方）连接两者，并异步（不互相等待）地传输权重，这样谁也不用等谁。
> 我们调研了 16 个实现这一模式的开源库，并在 7 个维度上做了对比：编排原语、缓冲区设计、权重同步协议、陈旧度管理、部分 rollout 处理、LoRA 支持、分布式训练后端。
> 关键发现：Ray 在编排上占统治地位（调研的 16 个分布式计算库中有 8 个使用 Ray）。NCCL（NVIDIA Collective Communications Library）广播是传输模型权重的默认方式。陈旧度管理指如何处理过时的数据样本，范围从直接丢弃旧样本到使用高级重要性采样校正。LoRA（Low-Rank Adaptation）训练的支持很稀疏。分布式 MoE（Mixture of Experts）支持是新兴的差异化点。
> 
> 如果你想直奔重点，这里是完整的对比表（不用读任何东西，我们不做道德评判）。
> 但说真的，留下来待一待，你或许能学到一两手——比如为什么你的 GPU 有 60% 的时间在闲着。

## 1. 动机：从同步 RL 训练到异步架构

异步 RL 训练已成为规模化后训练的主导范式。现代后训练中的几个趋势，让同步训练循环几乎无法扩展：

- **推理模型的长 rollout。** 思维链训练会产生非常长的 rollout，单个同步生成批次在一块 GPU 上可能要几个小时才能完成。在此期间，训练 GPU 完全空闲。
- **像 GRPO 这样不带价值函数的训练器**使用组相对优势。这意味着每个 prompt 要生成多至 G 倍的 rollout，而且整个批次被组内最慢的那个 completion 卡住。
- **Agentic RL 训练的兴起。** 当模型在多轮轨迹中与工具、沙箱和外部环境交互时，rollout 的长度和延迟变得高度可变。一个简单的 API 调用可能秒级返回，而一个带工具调用的复杂推理链可能运行几分钟甚至几小时。MiniMax 的 [Forge](https://www.minimax.io/news/forge-scalable-agent-rl-framework-and-algorithm) 框架（用于训练 MiniMax-M2.5）展示了实践中达到的规模：上下文长度最高 200K token、超过十万种不同的 agent scaffold 和环境、日吞吐量达到百万级样本。在这个量级下，生成与训练之间的任何同步屏障都会成为严重瓶颈。仅掉队者（straggler）问题（一小撮慢 rollout 卡住整批）就能让数百块 GPU 闲置。

开源生态对一个共同的架构回应达成了共识：把推理与训练解耦到独立的 GPU 池，用 rollout 缓冲区连接两者，让两边并发运行。

我们正在为 [TRL](https://github.com/huggingface/trl)——使用最广的后训练库之一——开发一个新的异步训练器。为了指导设计，我们调研了 **16 个从零开始围绕异步训练构建的开源库**，并在 **7 个维度**上做了对比：编排原语、缓冲区设计、权重同步协议、陈旧度管理、部分 rollout 处理、LoRA 支持、分布式训练后端。本文提炼了我们从这次调研中提取的设计原则。

在 RL 之外，对异步基础设施的需求也日益明显。例如，**on-policy distillation（在线策略蒸馏）**——学生模型生成序列、教师模型为其打分——结构与 GRPO 相同，只是把奖励函数换成了教师的前向传播。认识到这种结构上的相似性，本调研的一切结论同样适用于异步蒸馏。我们会在 5.5 节回到这个更宏观的观点。

### 1.1 TRL 目前的 RL 训练方式

TRL 当前的 `GRPOTrainer` 把完整的 GRPO 循环（prompt 采样、生成、奖励打分、优势计算、梯度更新、权重同步）实现在单个同步的 `training_step()` 调用里。这个设计简单且正确，但它无法让生成与训练重叠，把大量 GPU 利用率丢在了桌上。

看 `GRPOTrainer`，每个训练步内依次有以下阶段：

- **Prompt 采样：** 从数据集抽一批 prompt。没啥玄机，继续。
- **生成**，调用 `model.generate()`（或把请求转发给 vLLM 服务器）为每个 prompt 生成 G 个 completion。这是自回归过程，主导墙钟时间。
- **奖励打分：** 用一到多个奖励函数评估每个 completion。
- **优势计算**
- **前向与反向传播：** 计算截断策略梯度损失并反向传播。
- **优化器步**，更新模型权重。
- **权重同步**，把更新后的权重推给推理引擎（vLLM），让下一轮生成使用新策略。

TRL 提供了 `steps_per_generation` 配置项，让同一批 rollout 复用于多个梯度步（时间复用），摊薄生成开销。但生成本身仍然是完全同步、阻塞的；在批次里每个 completion 结束之前，训练器不能开始梯度计算。

该库也支持把 vLLM 以 `server` 模式作为独立进程运行。这在生成期间释放了训练 GPU，但仍有两道硬同步屏障：**HTTP 调用要等到所有 completion 返回**，且权重同步在传输期间同时阻塞训练器和 vLLM。

### 1.2 Colocated 与 Disaggregated 训练

在讨论异步训练之前，必须先理解使用独立推理引擎做 RL 训练的两种部署拓扑：

- **Colocated 模式**把推理和训练放在**同一组 GPU** 上。单块 GPU（或 TP 组）同时持有训练模型（在 FSDP 或 ZeRO 下）和推理引擎（vLLM 或 SGLang）。同一时刻只有一个角色在工作：生成期间，训练模型的参数可能被换出（offload）或重切成适合推理的布局（例如从 FSDP 分片切到 vLLM 的张量并行布局）；训练期间，推理引擎被暂停或休眠。权重「同步」基本免费；至多是同一块 GPU 上的原地重切，不是网络传输。Colocated 模式的优势是简单和省成本——需要的 GPU 总数更少。根本性限制是**推理和训练无法重叠**。例如，这是 `colocate_mode` 下 TRL 配 vLLM 的情形：

- **Disaggregated 模式**把推理和训练放在**独立的 GPU 池**。推理池持续运行 vLLM 或 SGLang；训练池持续运行优化器。两个池通过权重同步协议（NCCL 广播、文件系统 checkpoint、HTTP 等）和数据传输机制（Ray object store、Redis 流、共享内存等）通信。

Disaggregated 模式最大的优势是**推理和训练可以并发**。当训练器在对批次 N 计算梯度时，推理池已经在为批次 N+K 生成 rollout 了，异步训练由此成为可能。不过这份收益有代价：需要额外的 GPU。

并发（concurrency）、异步（asynchronicity）和并行（parallelism）是经常被混为一谈的三个不同概念。在本文中，当我们说「**异步训练**」时，指的是一个很具体的东西：**生成和训练并行运行、且有效重叠**；推理池在产出下一批 rollout 的同时，训练池在对当前批次计算梯度。这本质上是 disaggregated 模式才有的能力。Colocated 模式可以借助 sleep/wake 内存管理或快速的原地重切等优化来加速推理，但做不到真正的同时重叠；推理和训练在同一组 GPU 上依然要轮流来。本次调研中所有实现有意义异步重叠的库，都以 disaggregated 模式为基础。

### 1.3 生成瓶颈

在推理模型的 RL 训练里，**自回归生成主导墙钟时间**。单个数学或编程任务的 rollout 可以产生 8K–64K token 的思维链推理（参见 [QED-Nano rollout 长度](https://huggingface.co/spaces/lm-provers/qed-nano-blogpost#outcome-reward-rl-with-long-response-lengths)）。

为了把这件事说得具体，看看 [vLLM 在单块 H100 80GB GPU 上的基准](https://www.databasemart.com/blog/vllm-gpu-benchmark-h100)（bf16、无量化、离线吞吐模式）。**7B 模型**（DeepSeek-R1-Distill-Qwen-7B）达到约 6,300 输出 token/s 的聚合吞吐；**32B 模型**（DeepSeek-R1-Distill-Qwen-32B）掉到约 1,200 输出 token/s。这些是所有并发请求的*总*吞吐——推理引擎每秒能推过去的量，不管有多少条序列在共享这块 GPU。

再考虑一个典型的 GRPO 训练步：**每个 prompt 8 个 completion（G=8）× 每批 64 个 prompt = 512 条 rollout**。生成要花多长时间？

| 每条 rollout 的输出长度 | 总输出 token 数（512 条 rollout） | 1×H100 上的耗时（7B @ ~6K tok/s） | 1×H100 上的耗时（32B @ ~1.2K tok/s） |
| --- | --- | --- | --- |
| 2K token（短 CoT） | 约 100 万 token | **约 3 分钟** | **约 14 分钟** |
| 8K token（中等 CoT） | 约 400 万 token | **约 11 分钟** | **约 56 分钟** |
| 32K token（长 CoT） | 约 1600 万 token | **约 45 分钟** | **约 3.7 小时** |

即使在短的一端（7B 模型生成 2K token），仅生成就消耗每个训练步好几分钟。而在长的一端——前沿推理模型日益在这个区间工作——单个生成阶段在一块 GPU 上要花*几个小时*。扩展到 8 块推理 GPU 可以把这些时间大致除以 8（假设吞吐线性扩展），但即便如此，32B 模型的 32K token rollout 每步仍需约 28 分钟。

**掉队者问题**让这一切更糟。在 GRPO 这类基于组的算法中，每个 prompt 采样 G 个 completion。在*最慢*的那个 completion 结束之前，批次无法推进。思维链输出长度 variability 极大；同一个 prompt 的 completion 可能从 1K 到 32K token 不等。批次被最长的 completion 卡住，而 continuous batching 只能部分缓解：短序列释放槽位给新任务，但 GRPO 组里的*最后*一条序列仍然会阻塞该组的奖励计算和训练步。

### 1.4 核心洞见

本次调研中的每个库都各自独立地收敛到同一条架构原则：**在物理上把推理 GPU 与训练 GPU 分开，并异步推送权重**，这样生成永不停、训练永不等。

推理池持续运行，把完成的 rollout 喂进缓冲区。训练池从缓冲区取数据、计算梯度更新，并周期性地把新权重推回推理池以保持同步。两个循环按各自的节奏运行，由缓冲区解耦。

这套结构扩展性极好，但也引入了一类新问题：陈旧度（rollout 是旧策略生成的）、权重同步开销、部分 rollout 处理等等。本文余下部分将详细剖析当前开源库如何解决这些问题。

## 3. 对比框架：七个维度

为了厘清快速扩张的异步 RL 库生态，我们提出七个正交的对比维度。每个维度都捕捉了一个根本性的设计决策，塑造着库的性能、复杂度和权衡。

- **维度 1 – 编排与并发原语：** 分布式组件如何被协调（Ray actor、asyncio、发布/订阅、HTTP）。
- **维度 2 – Rollout 缓冲区设计：** rollout 如何从推理流向训练。
- **维度 3 – 权重同步协议：** 更新后的权重如何到达推理服务器，以及系统是必须暂停下来接收它们还是可以继续生成。
- **维度 4 – 陈旧度管理：** 离策略（off-policy）rollout 如何处理：版本拒绝、深度限定，还是重要性采样校正。
- **维度 5 – 部分 Rollout 处理：** 当权重更新在序列中途到达时，正在进行的生成会怎样。
- **维度 6 – LoRA 训练支持：** LoRA 的通用支持程度，以及能否训练并同步仅适配器（adapter-only）的参数，从而实现亚毫秒级的权重传输。
- **维度 7 – 分布式训练后端与并行策略：** 训练使用什么并行策略，这限制了最大模型规模。

### 维度 1：编排与并发原语

*系统如何协调它的分布式组件？*

编排框架的选择决定了编程模型、失败语义和可扩展性上限。我们不再逐库罗列实现细节，整个版图可以干净地分解为四种**编排类型**——它们在抽象层级、故障模型和部署需求上各不相同的基本协调范式：

| 编排类型 | 是什么 | 库 | 权衡 |
| --- | --- | --- | --- |
| **分布式 Actor 模型** | 组件是*actor*：带邮箱的、隔离的有状态进程，由运行时统一管理调度、资源放置、容错和对象传输。通信通过异步 RPC / futures / object store。 | **Ray：** verl、SkyRL、NeMo-RL、SLIME、MILES、ROLL、OAT、open-instruct。**Monarch：** TorchForge。 | 抽象最丰富；调度和容错开箱即用。但引入了不轻的运行时依赖和框架特有的调试负担。 |
| **Python 原生并发** | 组件是线程、协程（`asyncio`）、`threading` 原语、`multiprocessing` 子进程和队列。没有外部编排运行时。 | verifiers-rl、PipelineRL（池内）、ART（`asyncio` + 子进程代理）、AReaL（基于 `asyncio` 的事件循环） | 依赖极少、易调试、完全掌控。单节点之外的场景需要额外 IPC（Redis、HTTP、NCCL）来实现多节点通信。 |
| **发布/订阅消息总线** | 组件是解耦的生产者与消费者，通过仅追加（append-only）流或消息队列通信。这算不上编排，而是独立运行的池之间的*数据传输层*。 | PipelineRL（池间：多节点用 Redis `XADD`/`XREAD` 流，单节点用仅追加的 JSONL 文件） | 跨池边界解耦干净且无需 RPC。但不管理进程生命周期、调度或故障恢复，必须与另一种编排类型配合。 |
| **HTTP 微服务** | 组件是通过 REST API 通信的独立服务。语言无关、解耦到极致。 | Atropos | 任意推理服务器、任意语言、零共享状态。延迟最高（若不用 NCCL）；没有共享对象存储；容靠用户自己负责。 |

> 关于 Tunix 的说明：Tunix（Google）使用 JAX 原生的 mesh 模型，以 ThreadPoolExecutor 实现异步重叠、以 jax.device_put 实现跨 mesh 权重传输。它的架构与 PyTorch 生态差异大到在编排上做直接对比没有意义；它活在 XLA/TPU 世界里，有自己的协调原语。

上表揭示了一个显著规律：**调研的十六个库中有八个把 Ray 作为编排骨干**。这不是巧合；它反映了 actor 模型与 RL 训练结构之间的深度契合。[Anyscale 的一份调研](https://www.anyscale.com/blog/open-source-rl-libraries-for-llms)（Ray 背后的公司）对面向 LLM 的开源 RL 库的调研证实了这种收敛。大规模 RL 训练涉及根本异构的组件（推理引擎、训练引擎、环境、奖励模型），它们必须跨集群编排，往往运行在不同硬件类型上、有着不同的扩展需求和故障模式。Ray 的 actor 模型可以直接映射到这一点：

- **Actor 隔离与异构资源。** 每个 RL 组件（vLLM 推理服务器、FSDP 训练器、奖励模型、环境池）成为一个有自己的资源需求（`num_gpus`、`num_cpus`、`memory`）的 Ray actor。Placement group 让你对 GPU 亲和性做细粒度控制，无需手动 SSH/torchrun 编排。
- **调度与自动扩缩容。** Ray 的调度器处理把异构 actor 放到集群各处的组合优化问题。当生成需要比训练多 8 倍的 GPU 小时，你只要告诉 Ray 独立扩缩你的推理 actor 即可。
- **容错。** 长达数天乃至数周的 RL 训练容易受 GPU 故障、OOM 查杀和网络分区影响。Ray 的 actor 重启策略和对象存储副本提供了弹性，用裸 `asyncio` 和 `multiprocessing` 要达到同等效果需要大量定制基础设施。容错的一个具体例子：`open-instruct` 就依赖 Ray 的 actor 监督来从 rollout 中途的 vLLM 引擎崩溃中恢复。
- **用于零拷贝数据传输的对象存储。** Rollout 数据可能很大——超长上下文推理每个批次几十 GB。Ray 的共享内存 object store 支持同节点 actor 之间的零拷贝传输，避免了 `multiprocessing.Queue` 方式通常带来的序列化开销。
- **生态成熟度。** Ray 自 2017 年起就在大规模场景久经考验，在生产环境上千块 GPU 上有部署。调试开销确实存在（Ray Dashboard、分布式堆栈跟踪、placement group 失败），但替代方案——从零搭一套等效的协调机制——在多节点规模下更糟。话虽如此，Ray 是个重依赖：它会带进自己的调度器、对象存储和 dashboard，增加并非每个团队都需要的运维复杂度。这正是 PRIME-RL、PipelineRL、AReaL 这类库选择轻量 Python 原生协调（asyncio、threading、Redis 流）的原因——当你掌控全栈且部署拓扑固定时，原生 Python 的简单与可调试性往往胜过 Ray 提供的便利。

代价是硬依赖一个不轻的运行时。这个权衡通常值得，尤其对于生产级训练（64+ GPU、跨天运行、复杂的奖励计算）。

虽然 Ray 的 actor 模型是场上的主角，[Monarch](https://github.com/meta-pytorch/monarch) 作为 Meta 推出的面向 GPU 工作负载的 PyTorch 原生分布式 actor 框架崭露头角。与 Ray 一样，Monarch 基于 actor 模型：组件是带邮箱、通过消息通信的独立 actor，但它从第一行代码起就是为 PyTorch/CUDA 生态设计的，而不是通用分布式运行时。

Monarch 提供了若干与异步 RL 特别相关的能力。一份 [Monarch 异步 RL 示例实现](https://allenwang28.github.io/monarch-gpu-mode/05_rl_intro.html)（来自 GPU Mode 讲座系列）展示了这个架构：生成器、replay buffer 和训练器都建模为 Monarch actor，replay buffer 吸收掉队 rollout 带来的延迟方差，RDMA 权重同步把更新后的参数推给生成器而不阻塞训练。这个模式在结构上与基于 Ray 的设计（verl、SkyRL、open-instruct）完全一致，只是用纯 PyTorch 原生原语实现。

### 维度 2：Rollout 缓冲区设计

*生成的 rollout 如何从推理流向训练？流水线有多深？*

缓冲区是坐落在生成与训练之间的数据结构。它的深度控制着异步程度的上限，也因此控制着陈旧度的上限。

| 模式 | 深度 | 库 | 特征 |
| --- | --- | --- | --- |
| **无缓冲区**（同步） | 0 | TRL（当前）、**ART**（先收齐再训练） | 生成和训练严格轮流；零陈旧度，最大空闲时间 |
| **双缓冲**（提前一步） | 1 | verifiers-rl、SLIME（async 模式）、MILES、OAT | 在第 N 个训练步开始时提交第 N+1 批生成；恰好重叠一个批次 |
| **有界异步队列** | 2–K | SkyRL、verl（fully async）、NeMo-RL、ROLL、PRIME-RL、TorchForge、Tunix、**open-instruct**（`async_steps`）、**AReaL**（`max_head_offpolicyness`） | 多个批次同时在途；陈旧度受队列容量约束 |
| **无界 / 流** | 无限 | PipelineRL（Redis 流）、SLIME（fully async 模式）、Atropos | 持续生成；陈旧度仅靠显式版本控制来约束 |

[双缓冲模式](https://en.wikipedia.org/wiki/Multiple_buffering)是从同步到异步训练最简单的升级：它恰好让一次生成与一个训练步重叠，最多引入一步的策略滞后！

更深的队列能提高吞吐，但需要陈旧度管理来配合。

缓冲区控制着有多少数据在途。但数据只是方程的一半。另一半是赶在这些 rollout 变陈旧之前，把更新的权重*送回去*给推理服务器。这就轮到权重同步出场了！

### 维度 3：权重同步协议

*梯度更新之后，新的模型权重如何到达推理服务器？*

> 范围说明：本维度聚焦 disaggregated 模式——推理和训练运行在不同 GPU 池上——因为这才是异步重叠（进而权重同步设计）真正有意义的部署拓扑。Colocated 部署（两种角色共享同一组 GPU）本质上是同步的，不涉及下面讨论的传输/中断权衡。

这是架构上后果最重的维度。协议决定了同步延迟、中断粒度和部分 rollout 是否可行。

这里必须做一个关键区分：**传输机制**与**中断模型**。大多数库在一个粗粒度边界——一个 HTTP 请求、一个完整批次、甚至一整个训练步——暂停生成，然后启动权重传输。PipelineRL 是个例外：它根本从不停止生成。

**传输机制：**

| 机制 | 延迟 | 库 |
| --- | --- | --- |
| **NCCL 广播** | 约 100–500ms | PipelineRL、SkyRL、SLIME、MILES、ROLL、OAT、NeMo-RL、PRIME-RL、open-instruct、AReaL |
| **NCCL + 分桶** | 约 20ms | verl |
| **KV + 共享内存** | 低 | TorchForge |
| **文件系统 + HTTP** | 中 | PRIME-RL、AReaL、ART |
| **CUDA IPC（零拷贝）** | 极低 | NeMo-RL、MILES |
| **JAX 跨 mesh** | 低 | Tunix |
| **HTTP PUT** | 高 | verifiers-rl |
| **文件系统 + 重启** | 极高 | Atropos |

**中断模型：生成什么时候停下来接收新权重？**

这正是 PipelineRL 与其他所有库根本分道扬镳的地方。与其逐库列举，整个版图可以归纳为五个概念层级，按中断粒度从细到粗排列：

| 中断粒度 | 发生什么 | 库 |
| --- | --- | --- |
| **永不**（每次前向传播在途处理） | 序列从不停止。权重切换发生在 token 解码步之间（约 1-10ms 的间隙）。运行中的序列无缝地用新权重继续。 | PipelineRL、open-instruct（可选开启） |
| **每个 HTTP 请求**（中止 + 重同步） | 在途的 HTTP 请求被中止。部分 token 通过前缀续跑（prefix-resume）机制重新提交，或回收用于重试。 | SkyRL、SLIME、MILES |
| **软暂停**（排空在途） | 不再接受新的生成请求，进行中的自然完成。排空后同步权重，生成恢复。 | PRIME-RL、AReaL、open-instruct（默认）、verl（async） |
| **每个训练步 / 批次**（阻塞） | 生成必须完全结束。训练器和推理引擎互相阻塞、轮流工作。 | NeMo-RL、ROLL、OAT、TorchForge、Tunix、verifiers-rl、Atropos |

「永不停止」层级与其他所有层级有质的不同：PipelineRL 直接钩进推理引擎，锁*按每次 transformer 前向传播*（一条序列的一个 token 步）获取和释放。权重更新最多等待一次前向传播（几毫秒），换完所有参数，生成立即恢复。其他每个库都在更粗的边界暂停生成，从单个 HTTP 请求（约几百毫秒）到整个批次边界（约几秒）不等。

权重同步控制*何时*新权重到达。但异步训练意味着 rollout 永远是在*某个*策略版本下生成的，而那个*正在生成*的策略可能落后训练器好几个梯度步。库如何处理这种策略滞后，就是陈旧度管理。

### 维度 4：陈旧度管理

*系统如何处理「生成的 rollout 可能来自比当前训练策略更旧的策略」这一事实？*

一旦生成与训练重叠，样本就变成了 off-policy。管理这种陈旧度出现了三种**正交**策略，多数生产系统会组合使用其中不止一种：

**策略 1：逐样本版本拒绝。** 每个样本都带上生成它的整数策略版本标签。训练时，版本落后当前策略超过阈值的样本在进入损失计算之前被硬性丢弃。简单且正确，但白白浪费了生成被丢弃样本所花的算力。

**策略 2：深度限定。** 生成与训练之间的队列或缓冲区有界容量（或有显式的陈旧度门），从架构上限制任何样本最多能落后多远。范围从 depth=1（提前一步的双缓冲，其陈旧度在构造上不可能存在）到与版本差距挂钩的显式容量公式。不需要逐样本版本追踪；界限由系统流水线深度强制。

**策略 3：IS 加权损失校正。** 到达训练器的陈旧样本按重要性采样比率 π∗θ(a∣s)π∗old(a∣s)\frac{\pi*{\theta}(a \mid s)}{\pi*{\text{old}}(a \mid s)}π∗old(a∣s)π∗θ(a∣s)​ 重新加权，通常会被截断（Truncated IS）。一些库还会应用 OPSM（对优势为负的 off-policy 样本置零损失）。这保住了吞吐——不丢弃样本——但代价是 IS 比率带来的梯度方差。

这些策略彼此正交：系统可以只用版本拒绝、只用深度限定、只用 IS 校正，或任意组合。同步系统则通过不让生成与训练重叠而彻底回避这个问题。

| 库 | 版本拒绝 | 深度限定 | IS 校正 | 关键配置 / 备注 |
| --- | --- | --- | --- | --- |
| **AReaL** | ❌ | ✅ | ⚠️ | `max_head_offpolicyness` 容量公式；可选 `use_decoupled_loss` 加上限为 5.0 的 IS 权重 |
| **ART** | — | — | — | 同步；所有 rollout 收齐后才训练；设计上无陈旧度 |
| **Atropos** | ❌ | ✅ | ❌ | `max_batches_offpolicy`，对缓冲批次数的上限 |
| **MILES** | ❌ | ❌ | ✅ | TIS + OPSM |
| **NeMo-RL** | ✅ | ❌ | ❌ | `max_trajectory_age_steps`，逐样本版本丢弃 |
| **OAT** | ❌ | ❌ | ✅ | 截断 TIS 比率 |
| **open-instruct** | ❌ | ✅ | ⚠️ | `async_steps` 上限（默认 1，生产用 8）；可选 `--truncated_importance_sampling_ratio_cap ρ` 加上截断 TIS |
| **PipelineRL** | ✅ | ❌ | ❌ | `max_lag`，逐样本整数版本标签；年龄超阈值即丢弃 |
| **PRIME-RL** | ✅ | ✅ | ✅ | 全混合：`max_async_level` 版本差距 + `max_off_policy_steps` 取消 + IPO trust-region IS |
| **ROLL** | ❌ | ❌ | ✅ | 最丰富的 IS 套件：TIS、TOPR、CISPO、Kimi15，六种 off-policy 损失变体 |
| **SkyRL** | ❌ | ✅ | ❌ | `max_staleness_steps`，容量门超限时阻止新 rollout |
| **SLIME** | ❌ | ❌ | ✅ | TIS + OPSM（对部分 rollout 做 off-policy 掩码） |
| **TorchForge** | ✅ | ❌ | ❌ | `max_policy_age`，逐样本版本标签；硬性丢弃 |
| **Tunix** | ❌ | ✅ | ❌ | 有界队列 + 每步同步；陈旧度在结构上受限 |
| **verl** | ❌ | ❌ | ✅ | 截断 TIS 比率；可选 OPSM |
| **verifiers-rl** | ❌ | ✅ | ❌ | Depth=1 FIFO + 每步同步；陈旧度在构造上不可能 |

> ✅ = 有，❌ = 无，⚠️ = 可选 / 可配置，— = 不适用（同步）

- **版本拒绝**简单且正确，但大量样本被丢弃时浪费算力。
- **IS 校正**以梯度方差为代价保住吞吐。
- **深度限定**是最粗的机制，但它完全避免了逐样本记账。

生产系统（PRIME-RL、AReaL、open-instruct）的趋势是走向**混合方案**：深度限定加上可选 IS 校正，兼得有界队列的架构简单性和重要性加权在损失层面的安全网，以获得稳定训练。

陈旧度管理处理的是在旧策略下已经生成的数据。但当权重更新落地时数据*还在生成中*，那怎么办？

### 维度 5：部分 Rollout 处理

*当权重更新到达时，正在进行的生成会怎样？*

这对单次 rollout 可能花费数分钟的长上下文任务至关重要。有四种策略：

| 策略 | 库 | 描述 |
| --- | --- | --- |
| **隐式续跑** | PipelineRL | 序列从不中断。权重在前向传播之间切换；序列 simply 用新权重继续。存储的 logprobs 仍然有效，因为训练使用的是*记录的* π_old\pi\_{\text{old}}π_old，而非重新计算的值。 |
| **中止 + 带前缀重试** | SkyRL、SLIME | 活动序列被中止。部分 token 被累积，然后用新权重通过前缀续跑机制重新提交。 |
| **显式保存/续跑** | verl（fully async） | rollout worker 把部分 token ID 和 logprobs 存入缓冲区，等同步完成，再从保存的前缀继续。 |
| **组取消（生成继续）** | PRIME-RL | 陈旧 rollout 组的异步任务被取消；推理服务器继续服务在途 HTTP 请求，但其结果被丢弃。权重同步在 HTTP 请求之间触发，不打断请求中途的生成。 |
| **不支持部分 rollout** | verifiers-rl、OAT、Atropos、Tunix | 权重同步只在批次边界进行。在途生成必须先完成才能开始同步。 |
| **软暂停，在途序列完成** | **AReaL** | 暂停信号阻止新的 KV-cache 分配，但不中止进行中的序列。任务调度器停止提交新任务；运行中的任务跑到完成。权重同步后，生成调度恢复。 |
| **完全休眠，同步时无在途** | **ART** | 设计上，训练只在所有 rollout 收齐后才开始。触发休眠时从不存在进行中的序列。一级休眠（存在进行中请求）把 KV cache 换出到 CPU；二级休眠则整个丢弃。 |
| **排空或在途（可配置）** | **open-instruct** | 默认：停止标志门控新预取；权重更新等待活动任务排空。开启 in-flight 更新后，跳过排空，在 token 仍在生成时广播权重；进行中的序列以新旧权重混合继续。 |

到此，每个维度都假定了全参数训练。但在 LoRA 训练中，你只训练几百万个适配器参数而不是几十亿个，权重同步问题几乎消失。来看看这些库如何支持 LoRA 训练。

### 维度 6：LoRA 训练支持

*库是否通过 LoRA 适配器支持参数高效训练，支持哪些模式，是否利用仅适配器的权重同步？*

对于 GPU 预算有限的团队，LoRA 可以说是最有实际影响的维度。它把可训练参数量减少 99% 以上，将峰值激活内存减半，并且当推理服务器支持 LoRA 时，可以实现*仅适配器的权重同步*：不是广播 7B+ 模型的每个参数（NCCL 约 100–500ms），只把适配器增量推给 vLLM——在 rank 32 下大约 50 MB，亚毫秒传输。

| 库 | 支持 LoRA | 模式限制 | LoRA 后端 | 仅适配器同步 |
| --- | --- | --- | --- | --- |
| **AReaL** | ✅ 支持 | 仅 FSDP2（不支持 Megatron/Archon） | HF `peft` | ✅ 支持（基于磁盘的同步；只传输可训练参数；vLLM 适配器热切换） |
| **ART** | ✅ 支持（核心设计） | 两种均可（共享 GPU + 专用 GPU） | Unsloth/`peft`（默认）；定制 Megatron LoRA | ✅ 支持（只保存/加载适配器；进程内或 HTTP 适配器热切换；基础权重从不动） |
| **Atropos** | ✅ 支持 | Disaggregated | HF `peft` | ✅ 支持（`lora_only` / `lora_restart` 模式） |

**三个 LoRA 实现流派：**

- **HuggingFace `peft`**（PipelineRL、SkyRL/FSDP、verifiers-rl、ROLL、OAT、Atropos）：最常见的选择。标准 checkpoint 格式（`adapter_model.safetensors`），兼容任何 HF Transformers 训练循环。与 ZeRO-3 的交互需要小心：例如 OAT 需要禁用融合 LM head；ROLL 必须整个关闭梯度检查点。
- **Megatron-Bridge**（verl/Megatron、SkyRL/Megatron、MILES）：3D 并行训练（TP × PP × DP）的必选项。支持多种 LoRA 类型：`lora`、`canonical_lora`（把合并的 QKV 拆成独立的 Q/K/V 适配器）、`vlm_lora` 和 `dora`。`canonical_lora` 变体避开 QKV 合并，从而提高训练稳定性。MILES 同时以 HF `peft` 格式和 Megatron 原生 per-rank 格式保存 checkpoint。
- **自定义实现**（NeMo-RL、PRIME-RL、Tunix/qwix）：库专属的 LoRA 模块，与 `peft` checkpoint 不互通。PRIME-RL 独家支持单次运行中多个并行适配器，用于多实验并行。Tunix 使用 Google 的 `qwix` JAX 库，自带 QLoRA（NF4 量化）和 TPU 原生梯度路由。NeMo-RL 使用定制的 DTensor 兼容模块，可选 Triton 融合 kernel。

**仅适配器权重同步的机会（与维度 3 的交互）：**

十三个库中有八个支持**只把 LoRA 适配器增量**推给推理服务器。这彻底改变了权重同步问题（维度 3）的性质。全参数训练时，中断模型（逐前向传播锁 vs 逐请求中止 vs 逐批次暂停）决定了 NCCL 广播期间浪费多少生成。而 LoRA 加仅适配器同步时，传输小到几乎任何中断模型都能给出等效吞吐！连 Atropos 粗暴的 HTTP 热切换都变得可行了。

训练后端对异步 RL 库设计有直接影响：

**权重同步速度是训练后端的直接函数，而更快的同步意味着更少的陈旧度。**

在 disaggregated 异步配置下，权重同步*不一定*会 stall 推理。关键设计决策是**权重更新如何与在途生成交互**；存在四种策略，按干扰从小到大排列：

- **原子切换，不中断。** 整个权重更新以单次阻塞 RPC 派发给推理引擎。每次前向传播看到的要么全是旧权重要么全是新权重，绝不会混合。生成最多暂停一个前向传播间隙（约几毫秒）。（PipelineRL）
- **逐参数流式传输，不中断。** 每个参数作为独立 RPC + NCCL 广播发送。前向传播在单个参数更新之间穿插进行，因此在途序列确实会在不同层看到新旧权重混合。重叠最大化，但一致性最弱。（open-instruct，inflight 模式）
- **调度门控，排空在途，再同步。** 新请求被拦住，进行中的序列自然完成；流水线排空后才广播权重。不浪费 token，但同步气泡长度与最长的在途序列成正比。（PRIME-RL、AReaL、open-instruct 默认、verl fully-async）
- **硬暂停或中止。** 推理被暂停，或在途请求在权重传输开始前被中止。一致性最干净，算力浪费最大。（verl、SkyRL）

但即使在推理持续运行的库里，**同步越慢，推理跑在陈旧权重上的时间就越长**。训练器与推理池之间的策略版本差距随同步时长增长。这是需要考虑的因素。

**随着领域转向稀疏模型，MoE 支持成为日益重要的差异化点。**
趋势很清楚：前沿模型是稀疏的（DeepSeek-V3、Qwen3-MoE、Mixtral、DBRX），开放权重 MoE 正在成为后训练的默认起点。训练这些模型需要专家并行（EP）——把不同专家分发到不同 rank——而多数异步 RL 库并不支持。只有基于 Megatron 的库（verl、SLIME、MILES、ROLL、NeMo-RL）和 PRIME-RL 的 FSDP2+EP 路径能正确处理 EP。基于 ZeRO 的库（PipelineRL、verifiers-rl、OAT、open-instruct）可以*加载* MoE 的 HuggingFace 模型类，但没有 EP 时每个专家会被分片到所有 ZeRO-3 rank 上，而不是放到专用 rank；每次前向传播都要对每个专家做 AllGather，稀疏性优势被完全抵消。EP 也让权重同步变复杂：在向 vLLM/SGLang 广播之前（它们通常由单个 TP 组服务所有专家），训练器必须从每个 EP rank AllGather 专家参数，这是 O(N∗experts×E∗size) O(N*{\text{experts}} \times E*{\text{size}}) O(N∗experts×E∗size) 的通信量（其中 E_size E\_{\text{size}} E_size 是每个专家的参数量），稠密模型不存在这个问题。对一个有 256 个专家的 235B MoE，这是可观的同步成本。想在下一代开放 MoE 模型的后训练中保持相关性的库，需要 EP 感知的训练*和* EP 感知的权重同步。

**MoE LoRA 是一个新兴需求，而且很难缠。**
稠密模型上的 LoRA 已被充分理解（维度 6）：把适配器挂到注意力投影上、训练它们、只同步适配器增量。MoE LoRA 更难，因为天然的挂载目标是*专家 FFN 层*，也就是每个专家都有自己的适配器。对一个有 64 个专家、每个专家的 gate/up/down 投影都上 rank-32 LoRA 的模型，适配器数量从约 20（稠密）跳到约 200+（MoE），且适配器分布在各个 EP rank 上。权重同步必须先从每个 EP rank 收集适配器，再推给推理服务器——这是稠密 LoRA 不存在的协调难题。在训练侧，**ART** 显式实现了 MoE 专家 LoRA 层（Megatron EP 路径，逐专家 LoRA 加手动 allreduce），**MILES** 通过 Megatron-Bridge 支持 LoRA 且可以瞄准专家层，**PRIME-RL** 也支持[通过定制 `MultiMoELoRA` 模块实现 MoE LoRA](https://github.com/PrimeIntellect-ai/prime-rl/blob/main/src/prime_rl/trainer/models/layers/lora/multi_moe.py)。verl 的 Megatron-Bridge 路径支持包含 `vlm_lora` 在内的 LoRA 类型，但 MoE 专属的专家 LoRA 未见文档。在推理侧，**vLLM** 已经通过融合 Triton kernel [支持 MoE 的逐专家 LoRA 加载与服务](https://github.com/vllm-project/vllm/blob/2488a82f89b15ad2ebed12160dcc423d44210db2/vllm/lora/ops/triton_ops/fused_moe_lora_op.py#L158)有好几个 release 了，而 **SGLang** 有一个[为 MoE 添加 LoRA 支持的开放 PR](https://github.com/sgl-project/sglang/pull/14105)。据我们所知，vLLM 和 SGLang 都在开发 MoE LoRA 配合专家并行的推理支持。随着 MoE 模型成为后训练的默认选择，带高效仅适配器同步的 MoE LoRA 将是一个需要补齐的关键能力缺口。

七个维度到此讲完，每个维度捕捉的是同一个底层问题的不同侧面。合在一起，它们给了我们一副对比这些库的完整透镜。现在把一切铺在一页纸上。

## 5. 下一波浪潮：设计启示

下面列出的趋势不是新技术的目录清单；每一个都会对今天的基础设施和算法选择构成具体压力。问题不是「前沿是什么」，而是「如果这个趋势赢了，我当前的技术栈里什么会坏掉？」

### 5.1 无 Critic 算法：内存省了，权重同步压力大了

PPO 的价值网络让任何训练节点的内存占用翻倍。领域正收敛到无 critic 变体（GRPO、REINFORCE++、Online DPO），原因恰恰是长 CoT 推理让这份开销在 8K–64K 上下文长度下高不可攀。

**这解锁了什么：** 去掉 critic 释放约 50% 的训练 GPU 内存。这份余量可以重新分配给：(a) 更大的 rollout 批次，直接缓解掉队者方差问题；或 (b) 把推理和训练 colocate 到同一组 GPU 上，从而完全不需要独立的 NCCL 权重同步进程组。

**它没解决什么：** 无 critic 方法仍需要向推理服务器频繁推送权重。事实上它们可能*加大*同步压力：没有价值网络提供稳定基线，GRPO 系算法需要更大的组规模（G=8–32）来获得低方差的优势估计，这意味着每步更多 rollout、策略漂移更快。只在粗边界（每训练步或每 K 步）同步的库，会在无 critic 训练下看到陈旧度增长得更快。

**非对称轨迹筛选**（GRPO-RoC：过采样 rollout、严格筛选正样本、均匀下采样负样本；DeepSeek-V3.2 和 MiniMax-M1 中 CISPO/DAPO 风格的非对称截断）对陈旧度的影响更微妙。问题不在于批次本身变小，而在于幸存批次的*构成*。正样本轨迹（简单 prompt 的正确解法）收敛更快且被优先保留；较难的 prompt 产出的多为负样本轨迹而被丢弃。结果是：通过筛选存活的样本系统性地比缓冲区里 rollout 的平均水平*更旧*，因为它们解决的简单 prompt 是在训练更早期发出的。一个装满了名义上「新鲜」rollout 的缓冲区，其存活的正样本可能横跨很宽的策略版本范围。只在批次层级追踪陈旧度的准入控制（例如 SkyRL 的 `max_staleness_steps` 容量门、Atropos 的 `max_batches_offpolicy`）无法察觉这种批次内的版本散布。在这种机制下，逐样本版本标签（维度 4）不再是可选项；训练器必须能够拒绝或 IS 校正策略版本偏离过远的单个样本——哪怕它们所在的批次刚刚才被准入。

无 critic 方法简化了训练侧。但*打分*侧即将变得更贵：过程奖励模型（PRM）对中间推理步骤而非最终答案打分，这引入了一个全新的同步瓶颈。

### 5.2 过程奖励：新的同步屏障

结果奖励是标量且便宜的——rollout 结束时调用一次验证器即可。过程奖励模型（PRM）对中间步骤打分，要么需要 (a) 对完整推理轨迹跑一次独立的 PRM 前向传播，要么需要 (b) 在生成期间逐 token 计算的在线效用函数。

**PRPO**（熵尖峰切段 + 逐段 PRM 打分）和 **DEEP-GRPO**（通过在线效用函数识别枢轴点）都会在*生成与训练之间*引入计算开销。在当前的库版图中，这个阶段别扭地映射到预处理器池（PipelineRL），或需要一个额外的 Ray actor（verl、NeMo-RL）。两者都不是为它设计的。

**关键启示：** 基于 PRM 的信用分配打破了「奖励计算很便宜」这一假设。7B 模型对一条 32K token 推理轨迹跑 PRM 前向传播可能非常昂贵。在每 prompt 生成 G=8 个 completion 的情况下，奖励计算可能占据相对于生成本身不可忽略的墙钟时间。两个后果：

- **异步奖励流水线成为必需。** PRIME-RL 在其全异步的 Orchestrator-Trainer 流水线中将奖励打分与训练并发执行：Orchestrator 负责打分，Trainer 独立进行反向传播和优化器步骤。对基于 PRM 的方法，这种流水线化的奖励计算不是可选项；同步奖励打分会主导训练墙钟时间。
- **独立的预处理器池成为必需**。把参考 logprobs 计算和 PRM 打分放在专用 GPU 层级上运行——例如流水线在生成与训练之间——是稠密信用分配的正确架构。

**DEEP-GRPO 的枢轴重采样**引入了介于标准 rollout 与部分 rollout 续跑之外的第三种生成模式：*从序列中间状态的局部重采样*。这需要在枢轴点保存 KV cache 状态，而**当前没有任何异步库开箱支持**。枢轴边界处的权重同步可能成为新的正确性要求：如果枢轴生成与局部重采样之间权重发生了变化，优势估计就被污染了。当然，我们可以用一次 prefill 重算 KV-cache，但那会浪费训练中宝贵的算力。

### 5.3 多智能体共同进化：掉队者问题雪上加霜

单智能体 GRPO 训练一个策略，每个 prompt 生成 G 个 completion。新兴的多智能体自我博弈意味着有效的「组」横跨多个模型调用、顺序串联。奖励只有在链中所有模型都完成后才可得。

**掉队者动态发生质变。** 单智能体 GRPO 中，掉队者是组内最长的 completion——单峰长度分布中的一个尾部事件。多智能体流水线中，掉队者是两个或更多长度分布的*乘积*。在 Proposer/Solver 多智能体架构中，如果各自的第 90 百分位完成时间是中位数的 5 倍，联合的第 90 百分位大约是中位数的 25 倍。

**对 agent 集群做 RL 意味着新的工作单元。** 今天，每个库里的原子单元是单个 (prompt, completion, reward) 三元组。多智能体训练中，原子单元变成一个*episode*——一个由回合、工具调用和跨 agent 消息构成的有向图。缓冲区设计、陈旧度追踪和优势计算都需要在 episode 上运作。重放或分叉 episode 也可能变得必要。

至少模型内部自洽时，跨 agent 的掉队者问题已经够糟了。有了 MoE 架构，连单个模型都可能在推理和训练框架之间「自相矛盾」，这给 RL 训练带来了一组新的涌现问题。

### 5.4 训练-推理不一致：DeepSeek-V3.2 MoE 案例研究

训练-推理不一致问题在异步 RL 中无处不在：只要 rollout 数据在 π∗old\pi*{\text{old}}π∗old 下生成、而梯度更新在 π∗θ\pi*{\theta}π∗θ 下计算，两个策略就会发散。多数库用 IS 校正或硬性版本拒绝来应对。但 DeepSeek-V3.2 的生产经验揭示了 IS 校正修不了的**两个结构性**不一致来源。

**来源 1：MoE 专家路由不一致。** Mixture-of-Experts 模型对每个 token 激活一个稀疏的专家子集。推理框架（vLLM、SGLang）和训练框架（Megatron、FSDP）各自独立实现 router，门控函数里浮点舍入的差别会导致*相同输入选出不同的专家*。当专家路由发散时，活跃参数子空间发生不连续变化；一个假设专家 A 活跃而计算出的梯度步，被应用到了专家 B 下才活跃的权重上。DeepSeek-V3.2 发现这「会诱发活跃参数子空间的突变，使优化失稳并加剧 off-policy 问题」。

他们的方案 **Keep Routing** 保留采样（推理）时使用的确切专家路由路径，并在训练前向传播中强制执行这些路径。这要求推理框架在返回 token logprobs 的同时记录并返回路由决策，训练框架接受并执行它们。当前没有任何开源异步 RL 库实现这一点。对任何训练 MoE 模型（DeepSeek-V3 级别、Mixtral、未来的开放 MoE）的团队来说，这是正确性问题，不是性能问题。

**来源 2：采样截断掩码不一致。** Top-p 和 top-k 采样在生成时截断词表，把低概率 token 排除在采样分布之外。训练时，完整词表对 π∗θ\pi*{\theta}π∗θ 可见。这违反了重要性采样恒等式：π∗old\pi*{\text{old}}π∗old（截断的）与 π∗θ\pi*{\theta}π∗θ（完整的）动作空间不同，因此对采样时被掩码的 token，IS 比率 π∗θ(o∗t)/π∗old(ot)\pi*{\theta}(o*t) / \pi*{\text{old}}(o_t)π∗θ(o∗t)/π∗old(ot​) 无定义。

DeepSeek-V3.2 的 **Keep Sampling Mask** 方案：在采样时记录截断掩码，并在训练前向传播中将其应用到 π_θ\pi\_{\theta}π_θ 上，让两个策略在同一片词表子集上运作。这要求把掩码从推理服务器回传给训练器——同样，当前没有任何库基础设施支持。

**对库设计的启示：** Keep Routing 和 Keep Sampling Mask 都要求推理服务器在 token logprobs 之外返回*额外元数据*——路由决策和采样掩码。推理服务器（vLLM、SGLang）与训练器之间当前的 API 契约是 `(token_ids, logprobs, finish_reason)`。把它扩展到 `(token_ids, logprobs, finish_reason, expert_routing, sampling_mask)` 是对每个库数据流的破坏性变更。

### 5.5 蒸馏：换了个名字的同一套异步问题

On-policy 蒸馏——学生模型生成序列、教师模型用逐 token logprobs 打分——在结构上与 GRPO 的异步协调问题相同。

本调研的每一个设计维度——rollout 缓冲区、权重同步协议、陈旧度管理、部分 rollout 处理——都原样适用于蒸馏。生成池产出学生 rollout，教师为其打分（取代验证器），训练器用带优势修正的 GRPO 损失或独立的 KL 目标计算反向传播。自蒸馏再加一条协调要求：教师是学生第 *N−k* 步的冻结快照，因此系统必须周期性 checkpoint 策略并热切换教师服务器而不扰乱流水线——这个原语没有任何库实现了完全自动化。

**对库设计的实际启示是：异步 RL 基础设施不应被建成 GRPO 专属系统。** 生成-打分-训练流水线是一个通用模式，覆盖带结果奖励的 RL、带过程奖励的 RL、on-policy 蒸馏和自蒸馏。**SLIME、MILES、PRIME-RL、AReaL 和 NeMo-RL** 这类库之所以已经同时支持 GRPO 和 on-policy 蒸馏，正因为它们的异步脚手架把奖励/打分期当作可插拔组件，而非硬编码的验证器调用。任何以通用性为目标的异步训练器都应如此：把打分期定义为一个接口（一个 HTTP 端点、一个 Ray actor 或一个共址前向传播），让缓冲区、陈旧度和权重同步机制无论其中填什么都以同样的方式运作。

## 6. TRL 异步训练器的设计选择

survey 完整个版图——编排模型、缓冲区设计、权重同步协议、陈旧度策略和部分 rollout 处理——我们现在可以列出 TRL 异步训练器的具体设计选择，以及我们打算探索的面向未来的方向。

### 设计原则：编排保持轻量

当前 TRL 实现的一个优点是它不依赖重型编排系统来管理训练生命周期。库内部的数据保持为原生 Python 对象，不被外部库染色。我们希望保持这一点：编排应尽可能简单，不依赖重量级外部框架。

### 1. 带逐 token `model_version` 的有界队列（不用双缓冲）

我们不走「先双缓冲、再升级更细粒度」的路线，而是直接上**有界队列，每个 token 都带上产生它的 `model_version` 标签**。这从一开始就是最低可能的粒度；它支持 token 级的重要性采样校正、支持简单的准入门控（丢弃或降权超过陈旧度阈值的 token），并避免日后往批次级缓冲区上补造 token 级出处信息这种架构债。

### 2. 带打包传输的 NCCL 权重同步

NCCL 进程组是刚需，我们也已经在用。下一步应该加上分桶：vLLM 的 [`NCCLWeightTransferEngine`](https://github.com/vllm-project/vllm/blob/f3c6c9c9d794fac5e74b59bc75da6e9d1921eeac/vllm/distributed/weight_transfer/nccl_engine.py) 配 `packed=True` 直接支持分桶广播：它把参数打包进可配置大小的 `uint8` 缓冲区（默认 1 GB，跨 CUDA 流双缓冲），并通过独立于训练进程组的专用 NCCL communicator 广播。这消除了支配朴素广播的逐参数调用开销，带来巨大的同步提速。

在 vLLM 内置引擎之外，我们将探索面向更高要求场景的高性能权重打包库：

- **[Awex](https://github.com/inclusionAI/asystem-awex)**（inclusionAI），一个面向 RL 训练的专用权重同步框架，处理跨引擎传输这个硬骨头：训练引擎（Megatron、DeepSpeed）和推理引擎（SGLang、vLLM）使用完全不同的并行策略和张量布局。Awex 把这一点抽象在统一的转换层和确定性的 P2P 传输计划之后。同时支持 GPU 分离与共址（CUDA IPC）两种模式。
- **[Mooncake Transfer Engine](https://github.com/kvcache-ai/Mooncake)**，SGLang 一直在朝集成 Mooncake Transfer Engine 作为其高性能传输层的方向推进，集成范围横跨 PD 分离、分层 KV 缓存和弹性专家并行。具体到权重同步，配套的 **[checkpoint-engine](https://github.com/MoonshotAI/checkpoint-engine)** 项目使用 Mooncake 的 RDMA P2P 传输，在约 16–17 秒内更新万亿参数模型（Kimi-K2，256×H20 GPU）。Mooncake 现已加入 PyTorch Ecosystem，同时作为 [NVIDIA 的 NIXL 传输库](https://github.com/ai-dynamo/nixl)的后端插件。

### 3. 面向 Agentic 工作负载的部分 Rollout 支持

复杂环境中的多轮工具使用任务，单次 rollout 可能要几分钟。若没有在权重更新期间处理在途 rollout 的机制，同步窗口就会变成流水线停顿。我们大概会用实验探索两种策略：

- **前缀续跑（Prefix-resume）**：权重在 rollout 中途更新时，保存 KV cache 前缀，在新策略下从断点继续生成。这保住了已完成的部分工作，但要求推理引擎支持序列中途的权重切换。
- **中止重试（Abort-and-retry）**：丢弃超过陈旧度阈值的在途 rollout，把 prompt 重新排队。实现更简单，但按中止时的平均 rollout 长度成比例地浪费算力。
