# 将你的 GitHub CI 迁移到 Hugging Face Jobs

如果你有一个 GitHub 仓库并启用了 GitHub Actions，那你多半在用 GitHub 托管的 runner 跑 CI。很多项目默认就是这么做的，因为它简单：加一个 workflow，写上 `runs-on: ubuntu-latest`，GitHub 就给你一台机器。

这个默认方案很方便，但也有局限。GitHub Actions 可能很慢，或者在维护期间宕机；托管机器是通用配置；GPU 访问更不是大多数开源项目随手就能打开的功能。对 [Trackio](https://github.com/gradio-app/trackio) 来说，这些局限开始成为问题：我们既需要可靠的 CPU CI 来跑基础单元测试和前端检查，也需要 GPU CI 来跑必须在真实 CUDA 硬件上执行的测试。

所以我们搭了一套替代方案：让 GitHub Actions 继续掌管 CI，但把任务跑在 [Hugging Face Jobs](https://huggingface.co/docs/hub/en/jobs-overview) 上。

结果：Trackio 的 CI 现在运行在 Hugging Face Jobs 上，并实时回传日志，**CPU 任务的 CI 时间缩短约 30%，还让我们启用了一整套在 GPU 机器上运行的新测试**！

本文一步步讲解如何把你的 GitHub 仓库也配成同样的方案。如果你在用智能体（agent），可以直接把它指向这篇文章，因为我们除了给人看的浏览器操作说明，也提供了 CLI 指令。

先来快速了解一下 Hugging Face Jobs！

## 什么是 Hugging Face Jobs？

[Hugging Face Jobs](https://huggingface.co/docs/hub/en/jobs-overview) 让你在 Hugging Face 的无服务器基础设施上运行命令或脚本，硬件型号几乎随便挑。一个 Job 本质上就是：

- 一条要运行的命令
- 一个 Docker 镜像，来自 Docker Hub 或某个 Hugging Face Space
- 一种硬件规格，比如 CPU 或 `t4-small`、`h200` GPU
- 可选的环境变量和密钥

例如，你可以运行：

```
hf jobs run python:3.12 python -c "print('Hello world')"
```

或者

```
hf jobs uv run --flavor a10g-small "https://raw.githubusercontent.com/huggingface/trl/main/trl/scripts/sft.py" 
```

这让 Jobs 天然适合 CI。CI 任务本来就是命令驱动的、本来就跑在干净环境里，而且常常受益于精确选择最合适的硬件。对 ML 库来说，GPU 场景尤其有吸引力：你可以在真实 GPU 硬件上跑测试套件，而无需维护自己的常驻 runner。

关键一步是把 GitHub Actions 连到 HF Jobs，下面就来描述。

## 架构

为了这套方案，我们创建了 [`huggingface/jobs-actions`](https://github.com/huggingface/jobs-actions)——一个小型桥接器，把一个 GitHub Actions 任务变成运行在 HF Job 内部的临时自托管 runner。

完整流程如下：

- 一个 pull request 触发 GitHub Actions workflow。
- GitHub 会把 `runs-on` 标签不可用的任务排进队列，例如 `hf-jobs-cpu-upgrade` 或 `hf-jobs-t4-small`，并通过 GitHub App 向 dispatcher 发送签名的 `workflow_job.queued` webhook。
- dispatcher Space 校验 webhook，检查是否存在 `hf-jobs-*` 标签，铸造一个短时效的 GitHub runner 注册 token，并在匹配的硬件上启动一个 HF Job。
- 该 HF Job 启动一个临时 GitHub Actions runner，用一次性 token 把它注册到仓库。
- GitHub 把排队的 workflow 任务分配给这个 runner；runner 执行 CI 任务、把状态回报给 GitHub，然后退出。

从 GitHub 的视角看，这只是一个自托管 runner。从 Hugging Face 的视角看，这只是一个启动容器、运行仓库里 GitHub Actions workflow 步骤的 Job。

## 步骤 1：复制 dispatcher Space

首先需要的是 dispatcher。这是一个小型 Docker Space，负责接收 GitHub 的 `workflow_job` webhook 事件并相应启动 HF Job。

先创建它，因为 GitHub App 需要一个 webhook URL，而这个 URL 来自 Space。这个 Space 应当位于你自己的命名空间，或你有写权限的 Hugging Face 组织之下。

#### 网页方式

打开 [`huggingface/jobs-actions-dispatcher`](https://huggingface.co/spaces/huggingface/jobs-actions-dispatcher) 并点击 **Duplicate this Space**。

使用：

```
Owner: your HF user or org
Name: jobs-actions-dispatcher
Hardware: cpu-upgrade
```

正式的 CI 请用 `cpu-upgrade`，这样 dispatcher 能一直在线等待 GitHub webhook。`cpu-basic` 用于测试没问题，大概率也能工作，但它可能在闲置后休眠；如果 GitHub 的 webhook 恰好在其唤醒过程中到达，workflow 可能会一直排队。

构建完成后，打开复制出的 Space。你会看到一节"Required Space secrets"，现在可以先忽略。首页应该会显示下一步你需要的 GitHub App webhook URL，形如：

```
https://YOUR-HF-NAMESPACE-jobs-actions-dispatcher.hf.space/webhook
```

#### CLI 方式

如果你更想用智能体或 CLI 工作流来配置 dispatcher Space：

```
export HF_NAMESPACE=your-hf-user-or-org
export SPACE_ID="$HF_NAMESPACE/jobs-actions-dispatcher"

hf repo duplicate huggingface/jobs-actions-dispatcher "$SPACE_ID" \
  --type space \
  --flavor cpu-upgrade \
  --exist-ok
```

然后设置：

```
export DISPATCHER_URL="https://${HF_NAMESPACE}-jobs-actions-dispatcher.hf.space"
```

## 步骤 2：创建并安装 GitHub App

接下来，直接从 dispatcher Space 创建并安装 GitHub App。这个 App 需要权限来监听排队的 workflow 任务，并创建临时自托管 runner 的注册 token。

### 网页方式

打开你复制出的 dispatcher Space：

```
https://YOUR-HF-NAMESPACE-jobs-actions-dispatcher.hf.space
```

在配置表单中，输入希望把 CI 跑在 HF Jobs 上的 GitHub 仓库：

```
YOUR-GITHUB-ORG/YOUR-REPO
```

然后点击创建 GitHub App 的按钮。GitHub 会让你为 App 取名字；名字随意，只要在你的 GitHub 账号或组织内可用即可。提交后，最后的界面会明确告诉你如何用 `hf` CLI 把 App 凭证上传到 dispatcher Space。

**重要提示**：你需要提供一个有启动 Jobs 权限的 [Hugging Face token](https://huggingface.co/settings/tokens)，对应你的个人账号或应承担 Jobs 费用的组织。这个 token 应以 `HF_TOKEN` secret 保存在 dispatcher Space 中。

最后，把 App 安装到你在 Space 中输入的同一个 GitHub 仓库。在 Trackio 的配置中，我们把它装在了 `gradio-app/trackio` 上。

### 智能体辅助方式

GitHub App manifest 流程仍然在浏览器中完成，但智能体可以跟着同样的 Space 驱动路径：

```
export HF_NAMESPACE=your-hf-user-or-org
export GITHUB_REPO=YOUR-GITHUB-ORG/YOUR-REPO
open "https://${HF_NAMESPACE}-jobs-actions-dispatcher.hf.space"
```

把 `$GITHUB_REPO` 粘贴进 Space，点击 GitHub App 创建按钮，任选一个可用的 App 名称，然后按 GitHub 生成的指引操作。

App 创建之后，从 App 设置页面把它安装到你的仓库。对 GitHub 组织，安装设置位于：

```
https://github.com/organizations/YOUR-GITHUB-ORG/settings/installations
```

## 步骤 3：dispatcher 收尾配置

此时 dispatcher Space 应该已经配置完毕。GitHub App 的配置流程已经生成了把 App 凭证、webhook secret 和 Hugging Face token 上传到 Space 的命令。

默认情况下，HF Jobs 会在与 dispatcher Space 相同的命名空间下启动。如果你想把 Jobs 费用记到另一个 Hugging Face 用户或组织，可选地设置 `HF_NAMESPACE` 为 Space 变量：

```
export SPACE_ID=YOUR-HF-NAMESPACE/jobs-actions-dispatcher
hf spaces variables add "$SPACE_ID" -e HF_NAMESPACE=your-billing-namespace
hf spaces restart "$SPACE_ID"
```

步骤 2 中设置的 token 应对应于这个命名空间。

## 步骤 4：修改 `runs-on`

workflow 本身的改动很小。把

```
runs-on: ubuntu-latest
```

换成 dispatcher 能处理的某个标签：

```
runs-on: hf-jobs-cpu-upgrade
```

要跑 GPU 测试，就用 GPU 标签：

```
runs-on: hf-jobs-t4-small
```

对任何你想跑在 HF Jobs 上的 GitHub Action，这一行改动就是全部！

## 步骤 5：试跑一下

从 CLI 添加一个最小冒烟测试 workflow：

```
mkdir -p .github/workflows
cat > .github/workflows/hf-jobs-test.yml <<'EOF'
name: HF Jobs Test

on:
  pull_request:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  test:
    runs-on: hf-jobs-cpu-upgrade
    steps:
      - uses: actions/checkout@v4
      - run: echo "Hello from Hugging Face Jobs"
EOF

git add .github/workflows/hf-jobs-test.yml
git commit -m "Run CI on Hugging Face Jobs"
git push
```

从 CLI 验证：

```
gh run list --repo YOUR-GITHUB-ORG/YOUR-REPO --limit 5
hf jobs ps --namespace "$HF_NAMESPACE"
hf spaces logs "$SPACE_ID"
```

你应该能像普通 GitHub Action 一样看到日志——例如在这个 [Trackio PR #565](https://github.com/gradio-app/trackio/pull/565) 中。

就这样，全部搞定！

*关于选择合适 Docker 镜像的提示*

我们最初的 CPU 配置用的是 `ubuntu:22.04`，每次运行时都安装缺失的系统包。这能用，但比必要的慢。GitHub 的 `ubuntu-latest` 镜像默认带了很多开发者工具，而裸 Ubuntu 镜像没有。

对 Trackio 来说，UI 测试需要 Playwright 浏览器、Node、ffmpeg、sqlite、git 和常规 Linux 构建依赖。Hugging Face Jobs 支持使用任意 [Docker 镜像](https://huggingface.co/docs/hub/jobs-popular-images)，于是我们换成了 Microsoft Playwright 镜像，效果很好：

```
mcr.microsoft.com/playwright:v1.60.0-jammy
```

GPU 任务我们用了：

```
nvidia/cuda:12.4.0-runtime-ubuntu22.04
```

## 结果

以下是 Trackio CI 的数据：

| Runner 配置 | 运行时间 | 对比 GitHub 平均值 |
| --- | --- | --- |
| GitHub `ubuntu-latest` 基线 | `1m40s` | 基线 |
| HF Jobs CPU，Playwright 镜像 | `1m10s` | `-30s`，约快 `30%` |
| HF Jobs GPU，`t4-small` 标签 | `45s` | 没有 GitHub 托管 GPU 基线 |

最大的收获是 GPU CI。Trackio 的 GPU 检查在 HF Jobs 上运行，`45s` 通过，按 `t4-small` 的单价算花费不到一美分。

CPU 的结果同样令人鼓舞。用对了镜像，Linux 测试任务比 GitHub 托管基线还快。这说明 HF Jobs 可以是一个实用的 CI 后端，对需要定制镜像或加速器的 ML 项目尤其如此。

日志也是意外之喜。GitHub Actions 的日志很有用，但网页 UI 处理大日志时比较笨重。HF Jobs 的日志用 CLI 一行就能拉下来：

```
hf jobs logs <job_id> > logs.txt
```

这让你很容易用本地工具或编码智能体检查日志。在我们的桥接器里，我们还把 GitHub Actions 的任务日志镜像到 HF Job 日志中，这样两边系统都有足够信息来排查一次运行。

最后，虽然 Trackio 的 CI 用不到，HF Jobs 还[支持挂载 volume](https://huggingface.co/docs/huggingface_hub/en/guides/jobs#mount-a-volume)。如果你需要在 CI 中快速加载 Hugging Face 上的数据集或模型，这会非常有用。

希望这篇文章给足了你把 HF Jobs 用于 GitHub Actions 的全部信息！
