# 用 Optimum Intel 和 fastRAG 实现 CPU 优化嵌入

嵌入模型（embedding model）在检索、重排序、聚类和分类等众多应用中很有价值。近年来，研究社区在嵌入模型上取得了长足进展，让所有基于语义表示的应用都得到显著提升。[BGE](https://huggingface.co/BAAI/bge-large-en-v1.5)、[GTE](https://huggingface.co/thenlper/gte-small) 和 [E5](https://huggingface.co/intfloat/multilingual-e5-large) 等模型位列 [MTEB](https://github.com/embeddings-benchmark/mteb) 基准前茅，某些表现甚至超过专有嵌入服务。Hugging Face 模型库中有各种规模的模型，从轻量级（1-3.5 亿参数）到 7B 模型（如 [Salesforce/SFR-Embedding-Mistral](http://Salesforce/SFR-Embedding-Mistral)）。基于 encoder 架构的轻量模型，非常适合在 CPU 后端上做优化并用于语义搜索类应用，比如检索增强生成（[RAG](https://en.wikipedia.org/wiki/Prompt_engineering#Retrieval-augmented-generation)）。

在这篇博客中，我们将展示如何在基于 Xeon 的 CPU 上获得显著的性能提升，并演示如何用 [fastRAG](https://github.com/IntelLabs/fastRAG/) 把优化后的模型轻松集成到现有 RAG 流水线中。

## 用嵌入模型做信息检索

嵌入模型把文本数据编码为稠密向量，捕捉语义与上下文含义。这让信息检索更准确——词与文档的关系得以用更贴合上下文的方式表示。通常，语义相似度用嵌入向量之间的余弦相似度来度量。

稠密向量是否总是信息检索的最优选择？两种主流方法各有取舍：

- 稀疏检索（Sparse retrieval）匹配 n-gram、短语或元数据，可以高效、大规模地搜索大集合。但因查询与文档之间存在词汇鸿沟，可能漏掉相关文档。
- 语义检索（Semantic retrieval）把文本编码成稠密向量，比词袋更好地捕捉上下文与含义。即使词汇不匹配，它也能检索到语义相关的文档。但它计算量大、延迟更高，相比 BM25 这类词汇匹配方法需要更复杂的编码模型。

### 嵌入模型与 RAG

嵌入模型在 RAG 应用中承担多重关键职责：

- 离线流程：在索引/更新检索文档库（索引）时，把文档编码成稠密向量。
- 查询编码：在查询时，把输入查询编码成稠密向量表示用于检索。
- 重排序：初始检索后，可以把检索到的文档编码为稠密向量并与查询向量比较，从而重排序。这允许对原本缺少稠密表示的文档进行重排序。

对 RAG 流水线中的嵌入模型部分做优化是非常值得的，能带来更高效率的体验，具体而言：

- 文档索引/更新：更高吞吐量意味着在初始构建或定期更新时，能更快地编码并索引大规模文档集合。
- 查询编码：更低的查询编码延迟对实时响应的检索至关重要。更高吞吐量可以高效编码大量并发查询，支撑扩展。
- 重排序检索到的文档：初始检索后，嵌入模型需要快速编码待重排的候选文档。对时间敏感的应用而言，低延迟可实现快速重排序；高吞吐量则可并行重排更大的候选集，让重排序更全面。

## 用 Optimum Intel 和 IPEX 优化嵌入模型

[Optimum Intel](https://github.com/huggingface/optimum-intel) 是一个开源库，可以在 Intel 硬件上加速用 Hugging Face 库构建的端到端流水线。Optimum Intel 包含多种模型加速技术，如低比特量化、模型权重剪枝、知识蒸馏，以及一个加速运行时。

[Optimum Intel](https://github.com/huggingface/optimum-intel) 的运行时和优化技术利用了 Intel CPU 上的 Intel® Advanced Vector Extensions 512（Intel® AVX-512）、Vector Neural Network Instructions（VNNI）和 Intel® Advanced Matrix Extensions（Intel® AMX）。具体来说，每个核心都内置 [BFloat16](https://en.wikipedia.org/wiki/Bfloat16_floating-point_format)（`bf16`）和 `int8` GEMM 加速器，可加速深度学习训练与推理工作负载。AMX 加速推理在 PyTorch 2.0 和 [Intel Extension for PyTorch](https://github.com/intel/intel-extension-for-pytorch)（IPEX）中引入，此外还有针对各种常用算子的优化。

借助 Optimum Intel，对预训练模型做优化非常轻松；许多简单示例可在[这里](https://huggingface.co/docs/optimum/main/en/intel/optimization_inc)找到。

## 示例：优化 BGE 嵌入模型

本博客聚焦 [北京智源人工智能研究院](https://arxiv.org/pdf/2309.07597.pdf) 研究人员近期发布的嵌入模型，因为他们在广泛使用的 [MTEB](https://github.com/embeddings-benchmark/mteb) 排行榜上表现颇具竞争力。

### BGE 技术细节

双塔模型（Bi-encoder）是基于 Transformer 的编码器，训练目标是最小化两个语义相似文本向量之间的相似度度量（如余弦相似度）。例如，常见嵌入模型以 BERT 作为预训练基座并为其微调成文档嵌入模型。表示已编码文本的向量由模型输出构造而来，例如可以取 [CLS] token 的向量，或所有 token 向量的平均值。

与更复杂的嵌入架构不同，双塔编码器每次只编码单个文档，因而缺少编码实体之间（如查询-文档、文档-文档）的上下文交互。但最先进的双塔嵌入模型依然有很有竞争力的表现，而且由于结构简单，速度极快。

我们聚焦 3 个 BGE 模型：[small](https://huggingface.co/BAAI/bge-small-en-v1.5)、[base](https://huggingface.co/BAAI/bge-base-en-v1.5) 和 [large](https://huggingface.co/BAAI/bge-large-en-v1.5)，参数量分别为 4500 万、1.1 亿、3.55 亿，编码出的向量维度分别为 384/768/1024。

需要注意，下面展示的优化流程是通用的，也可以用于其他嵌入模型（包括双塔、cross-encoder 等）。

### 分步教程：用量化做优化

下面给出一份分步指南，用于提升嵌入模型的性能——重点是降低延迟（批量为 1）并提高吞吐量（以每秒编码文档数计）。本方案用 `optimum-intel` 和 [Intel Neural Compressor](https://github.com/intel/neural-compressor) 对模型量化，并用 [IPEX](https://github.com/intel/intel-extension-for-pytorch) 在 Intel 硬件上获得优化运行时。

##### 第 1 步：安装依赖包

安装 `optimum-intel` 和 `intel-extension-for-transformers`，运行：

```
pip install -U optimum[neural-compressor] intel-extension-for-transformers
```

##### 第 2 步：训练后静态量化

训练后静态量化需要一个校准集来确定权重和激活的动态范围。校准的做法是让一批有代表性的数据样本过一遍模型、收集统计信息，然后基于收集到的信息进行量化，把精度损失降到最低。

量化代码片段如下：

```
def quantize(model_name: str, output_path: str, calibration_set: "datasets.Dataset"):
    model = AutoModel.from_pretrained(model_name)
    tokenizer = AutoTokenizer.from_pretrained(model_name)

    def preprocess_function(examples):
        return tokenizer(examples["text"], padding="max_length", max_length=512, truncation=True)

    vectorized_ds = calibration_set.map(preprocess_function, num_proc=10)
    vectorized_ds = vectorized_ds.remove_columns(["text"])

    quantizer = INCQuantizer.from_pretrained(model)
    quantization_config = PostTrainingQuantConfig(approach="static", backend="ipex", domain="nlp")
    quantizer.quantize(
        quantization_config=quantization_config,
        calibration_dataset=vectorized_ds,
        save_directory=output_path,
        batch_size=1,
    )
    tokenizer.save_pretrained(output_path)
```

在校准过程中，我们使用了 [qasper](https://huggingface.co/datasets/allenai/qasper) 数据集的一个子集。

##### 第 3 步：加载并运行推理

加载量化后的模型只需：

```
from optimum.intel import IPEXModel

model = IPEXModel.from_pretrained("Intel/bge-small-en-v1.5-rag-int8-static")
```

把句子编码为向量的方式与我们熟悉的 [Transformers](https://github.com/huggingface/transformers) 库一致：

```
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("Intel/bge-small-en-v1.5-rag-int8-static")
inputs = tokenizer(sentences, return_tensors="pt")

with torch.no_grad():
    outputs = model(**inputs)
    # get the [CLS] token
    embeddings = outputs[0][:, 0]
```

### 用 MTEB 评估模型

把模型权重量化到更低精度会引入精度损失，因为从 `fp32` 权重转到 `int8` 会有损失。因此，我们用两个 [MTEB](https://github.com/embeddings-benchmark/mteb) 任务，将优化后的模型与原始模型对比来验证精度：

- **Retrieval（检索）**——把语料库编码，然后给定查询在索引中搜索并生成排序列表。
- **Reranking（重排序）**——给定查询，对检索结果重新排序以获得更好的相关性。

### 速度与延迟

我们将优化模型的性能与另外两种常见的模型使用方式对比：

- 用 PyTorch 和 Huggingface Transformers 库并以 `bf16` 运行。
- 用 [Intel extension for PyTorch](https://intel.github.io/intel-extension-for-pytorch/#introduction)（IPEX）运行时以 `bf16` 运行，并用 torchscript 追踪模型。

实验设置说明：

- 硬件（CPU）：第 4 代 Intel Xeon 8480+，双路插槽，每路 56 核。
- PyTorch 模型在 1 个 CPU 插槽的 56 核上评测。
- IPEX/Optimum 设置用 ipexrun 在 1 个 CPU 插槽上评测，核心数在 22-56 之间。
- 所有运行都安装了 TCMalloc 并设为环境变量。

### 我们是怎么跑评测的？

我们写了一个脚本，用模型的词表生成随机样例。分别加载原始模型和优化的模型，比较在上述两种场景下编码这些样例所花的时间：批量为 1 时测延迟，批量编码时测吞吐量。

- 基线 PyTorch 和 Hugging Face：

```
import torch
from transformers import AutoModel

model = AutoModel.from_pretrained("BAAI/bge-small-en-v1.5")

@torch.inference_mode()
def encode_text():
    outputs = model(inputs)

with torch.cpu.amp.autocast(dtype=torch.bfloat16):
    encode_text()
```

- IPEX torchscript 加 `bf16`：

```
import torch
from transformers import AutoModel
import intel_extension_for_pytorch as ipex


model = AutoModel.from_pretrained("BAAI/bge-small-en-v1.5")
model = ipex.optimize(model, dtype=torch.bfloat16)

vocab_size = model.config.vocab_size
batch_size = 1
seq_length = 512
d = torch.randint(vocab_size, size=[batch_size, seq_length])
model = torch.jit.trace(model, (d,), check_trace=False, strict=False)
model = torch.jit.freeze(model)

@torch.inference_mode()
def encode_text():
    outputs = model(inputs)

with torch.cpu.amp.autocast(dtype=torch.bfloat16):
    encode_text()
```

- Optimum Intel 配 IPEX 和 `int8` 模型：

```
import torch
from optimum.intel import IPEXModel

model = IPEXModel.from_pretrained("Intel/bge-small-en-v1.5-rag-int8-static")

@torch.inference_mode()
def encode_text():
    outputs = model(inputs)

encode_text()
```

可以看到，量化模型整体延迟最佳：small 和 base 模型低于 10 ms，large 模型低于 20 ms。与原始模型相比，量化模型的延迟提速最高达 4.5 倍。

### 吞吐量性能

吞吐量评测中，我们寻找的是文档编码的峰值性能（每秒文档数）。我们把文本长度设为 256 token——这是 RAG 流水线中平均文档长度的合理估计——并用不同批量大小（4、8、16、32、64、128、256）评测。

结果显示，量化模型达到了比其他模型更高的吞吐量，并在批量 128 时达到峰值。整体而言，在所有模型规模上，量化模型相对基线 `bf16` 模型在各种批量大小下都有最高 4 倍的提升。

## 用 fastRAG 使用优化后的嵌入模型

[ ![](https://github.com/IntelLabs/fastRAG/raw/main/assets/fastrag_header.png) ](https://github.com/IntelLabs/fastRAG/)

举个例子，我们将演示如何把优化后的检索/重排序模型集成到 [fastRAG](https://github.com/IntelLabs/fastRAG)（同样可以轻松集成到其他 RAG 框架，如 Langchain 和 LlamaIndex）。

[fastRAG](https://github.com/IntelLabs/fastRAG) 是由 [Intel Labs](https://www.intel.com/content/www/us/en/research/overview.html) 开发的研究框架，用于高效、优化的检索增强生成流水线，集成了最先进的大语言模型与信息检索技术。fastRAG 与 [Haystack](https://haystack.deepset.ai/) 完全兼容，并包含面向 Intel 硬件高效部署的新型、高效 RAG 模块。想上手 fastRAG，请参考[安装说明](https://github.com/IntelLabs/fastRAG#round_pushpin-installation)，并用我们的[指南](https://github.com/IntelLabs/fastRAG/blob/main/getting_started.md)开始使用。

我们把优化的双塔嵌入模型集成到了两个模块：

- [`QuantizedBiEncoderRetriever`](https://github.com/IntelLabs/fastRAG/blob/main/fastrag/retrievers/optimized.py#L17)——用于从稠密索引中索引和检索文档。
- [`QuantizedBiEncoderRanker`](https://github.com/IntelLabs/fastRAG/blob/main/fastrag/rankers/quantized_bi_encoder.py#L17)——在精细的检索流水线中，作为其中一个环节用嵌入模型对文档列表重排序。

### 用优化 Retriever 快速索引

我们用一个基于优化嵌入模型的稠密检索器来创建稠密索引。

首先创建文档存储：

```
from haystack.document_store import InMemoryDocumentStore

document_store = InMemoryDocumentStore(use_gpu=False, use_bm25=False, embedding_dim=384, return_embedding=True)
```

然后添加一些文档进去：

```
from haystack.schema import Document

# example documents to index
examples = [
   "There is a blue house on Oxford Street.",
   "Paris is the capital of France.",
   "The first commit in fastRAG was in 2022"  
]

documents = []
for i, d in enumerate(examples):
    documents.append(Document(content=d, id=i))
document_store.write_documents(documents)
```

加载一个使用优化双塔嵌入模型的 Retriever，并把文档存储中所有文档编码：

```
from fastrag.retrievers import QuantizedBiEncoderRetriever

model_id = "Intel/bge-small-en-v1.5-rag-int8-static"
retriever = QuantizedBiEncoderRetriever(document_store=document_store, embedding_model=model_id)
document_store.update_embeddings(retriever=retriever)
```

### 用优化 Ranker 重排序

下面示例演示把优化模型加载为一个 ranker 节点，它在给定查询时从索引中检索并编码、重排序所有文档：

```
from haystack import Pipeline
from fastrag.rankers import QuantizedBiEncoderRanker

ranker = QuantizedBiEncoderRanker("Intel/bge-large-en-v1.5-rag-int8-static")

p = Pipeline()
p.add_node(component=retriever, name="retriever", inputs=["Query"])
p.add_node(component=ranker, name="ranker", inputs=["retriever"])
results = p.run(query="What is the capital of France?")

# print the documents retrieved
print(results)
```

完成！创建的流水线可用于从文档存储中检索文档，并用（另一个）嵌入模型对检索到的文档重排序。更完整的示例见这个 [notebook](https://github.com/IntelLabs/fastRAG/blob/main/examples/optimized-embeddings.ipynb)。

想了解 RAG 相关的更多方法、模型和示例，欢迎阅读 [fastRAG/examples](https://github.com/IntelLabs/fastRAG/tree/main/examples) 中的 notebook。
