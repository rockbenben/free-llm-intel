# 在现代 CPU 上扩展类 BERT 模型推理 - 第 2 部分

## 引言：用 Intel 软件在 CPU 上优化 AI 效率

正如我们在[上一篇博客](https://huggingface.co/blog/bert-cpu-scaling-part-1)中详述的，Intel Xeon CPU 提供了一整套专为 AI 工作负载设计的能力，例如 AVX512 和 VNNI（Vector Neural Network Instructions，向量神经网络指令），可以高效地用整数化量化神经网络做推理，并配有额外的系统工具确保以最有效的方式完成工作。在这篇博客中，我们将聚焦软件优化，让你对 Intel 新一代 Ice Lake Xeon CPU 的性能有一个直观感受。目标是给你一幅软件侧全貌，帮你把 Intel 硬件的潜力榨干。和上一篇一样，我们用基准测试结果和图表展示性能，并介绍让所有这些调优项和能力易于使用的新工具。

今年四月，Intel 发布了[最新一代 Intel Xeon 处理器](https://www.intel.com/content/www/us/en/products/details/processors/xeon/scalable.html)，代号 Ice Lake，瞄准更高效、更高性能的 AI 工作负载。更准确地说，与上一代 Cascade Lake Xeon 处理器相比，Ice Lake Xeon CPU 可以在多种 NLP 任务上实现最高快 75% 的推理。这是硬件与软件改进共同作用的结果——[比如新指令](https://en.wikichip.org/wiki/x86/avx512_vnni)以及全新 Sunny Cove 架构上支持机器学习和深度学习负载的 PCIe 4.0。最后同样重要的是，Intel 针对 various 框架做了专门优化，如今这些框架都带有 Intel 的定制版本，如 [Intel's Extension for Scikit Learn](https://intel.github.io/scikit-learn-intelex/)、[Intel TensorFlow](https://www.intel.com/content/www/us/en/developer/articles/guide/optimization-for-tensorflow-installation-guide.html) 和 [Intel PyTorch Extension](https://www.intel.com/content/www/us/en/developer/articles/containers/pytorch-extension.html)。

这些能力都位于数据科学家和机器学习工程师日常工具栈的很底层。绝大多数场景下，人们更常依赖更上层的框架和库来处理多维数组操作，比如 [PyTorch](https://pytorch.org) 和 [TensorFlow](https://www.tensorflow.org/)，并使用高度调优的数学算子来做计算部分，比如 [BLAS (Basic Linear Algebra Subroutines)](http://www.netlib.org/blas/)。

在这个领域，Intel 扮演关键角色：它在 oneAPI 大伞下提供软件组件，让使用者可以非常方便地用上高效的线性代数例程——Intel [oneMKL (Math Kernel Library)](https://www.intel.com/content/www/us/en/develop/documentation/oneapi-programming-guide/top/api-based-programming/intel-oneapi-math-kernel-library-onemkl.html)；更上层的并行化框架——Intel OpenMP 或 [Threading Building Blocks (oneTBB)](https://www.intel.com/content/www/us/en/developer/tools/oneapi/onetbb.html)。此外 oneAPI 还提供一些领域专用库，如 Intel [oneDNN](https://www.intel.com/content/www/us/en/developer/tools/oneapi/onednn.html) 提供深度神经网络基元（ReLU、全连接等），以及 [oneCCL](https://www.intel.com/content/www/us/en/developer/tools/oneapi/oneccl.html) 提供集合通信——在使用分布式环境跨多台主机做高效 all-reduce 操作时尤其有用。

这些库中的一些，尤其是 MKL 和 oneDNN，已经原生集成进 PyTorch 和 TensorFlow（[自 2.5.0 起](https://medium.com/intel-analytics-software/leverage-intel-deep-learning-optimizations-in-tensorflow-129faa80ee07)），让终端用户开箱即得全部性能提升。当需要针对非常具体的硬件能力时，Intel 提供了常见软件的定制版本，为 Intel 平台做了深度优化。比如 TensorFlow，[Intel 为其提供定制、高度调优和优化的版本](https://www.intel.com/content/www/us/en/developer/articles/guide/optimization-for-tensorflow-installation-guide.html)；再比如 Intel PyTorch Extension（IPEX）框架，可以看作上游化到 PyTorch 之前的特性实验室。

## 深入：利用高级 Intel 特性提升 AI 性能

### 性能调优项

如上所述，我们将介绍一组新的可调项来改善 AI 应用性能。从高层视角看，每个机器学习和深度学习框架都由同样的原料构成：

- 在内存中表示数据的结构化方式（向量、矩阵等）
- 数学算子的实现
- 在目标硬件上对计算的高效并行化

*除了上面几点，深度学习框架还提供表示数据流和依赖关系以计算梯度的方式。这超出本文范围，并且用到的还是上面列出的那些组件！*

### 1. 内存分配与管理库

本文有意跳过第一点（数据表示），因为它相当依赖具体框架。作为参考，PyTorch 使用自己的实现 [ATen](https://github.com/pytorch/pytorch/tree/master/aten/src)，而 TensorFlow 依赖开源库 [Eigen](https://eigen.tuxfamily.org/index.php?title=Main_Page) 来实现这一点。

虽然对不同对象结构和布局应用通用优化很复杂，但有一个方面我们可以发力：内存分配。简单回顾一下，这里的内存分配指以编程方式向操作系统申请一块动态（事先未知）的系统区域，用于存放条目，比如 C 里的 malloc 及其衍生函数、C++ 里的 new 运算符。内存效率——无论速度还是碎片化——是一个庞大的科学与工程课题，针对不同任务和底层硬件有多种解法。过去几年这个领域的工作越来越多，代表性的有：

- [jemalloc](http://jemalloc.net/)（Facebook - 2005）
- [mimalloc](https://microsoft.github.io/mimalloc/)（Microsoft - 2019）
- [tcmalloc](https://abseil.io/blog/20200212-tcmalloc)（Google - 2020）

它们各自提出不同思路，以改进各类软件在内存分配与管理上的不同方面。

### 2. 计算的高效并行化

有了高效的数据表示方式，接下来需要把可用计算硬件的潜力用到极致。有意思的是，在推理上，CPU 相对 GPU 有一个潜在优势：CPU 无处不在，而且不需要专门的应用组件和运维人员来操作它。

现代 CPU 拥有众多核心和复杂的机制来提升软件的总体性能。然而，正如我们在[第一篇博客](https://hf.co/blog/bert-cpu-scaling-part-1)中强调的，它们也有一些可以根据目标负载类型（CPU 密集型还是 I/O 密集型）调整的特性，进一步为你的应用提升性能。

话虽如此，实现并行算法可能不是「堆核心就能干活」那么简单。很多因素——所用的数据结构、并发数据访问、CPU 缓存失效——都可能让你的算法快不起来。作为入门参考，我们推荐 [**Scott Meyers: CPU Caches and Why You Care**](https://www.youtube.com/watch?v=WDIkqP4JbkE) 这场演讲，如果你想更深入这个主题。

好在有库能让这类并行算法的开发过程更轻松、更不易出错。最常见的并行库包括 OpenMP 和 TBB（Threading Building Blocks），它们作用于不同层面，从 C/C++ 编程 API 到环境变量调优和动态调度。在 Intel 硬件上，建议使用 Intel 对 OpenMP 规范的实现（常被称为 "IOMP"），它包含在 [Intel oneAPI 工具包](https://www.intel.com/content/www/us/en/developer/tools/oneapi/overview.html)中。

### 3. 优化的数学算子

覆盖了设计高效数据结构和并行算法所需的构件之后，最后一块拼图就是实际跑计算的部分——实现各种数学算子和神经网络层、做我们最爱之事（设计神经网络）的那个部分！😊

在每个程序员的工具箱里，提供数学运算支持的层次有好几个，可以依据不同因素做不同优化：数据存储布局（连续内存、分块、打包等）、表示每个标量元素的数据格式（Float32、Integer、Long、Bfloat16 等），当然还有处理器支持的各种指令。

如今几乎所有处理器都支持标量模式（一次单个元素）或向量化模式（在同一条 CPU 指令内对多个元素操作，即 SIMD「Single Instruction Multiple Data」）的基本数学运算。著名的 SIMD 指令集有 SSE2、AVX、AVX2，以及 Intel 最新几代 CPU 上的 AVX-512——单个 CPU 时钟内可对 16 字节内容做运算。

大多数时候，你不用太操心两条向量做逐元素相加时实际生成的汇编；但如果你真操心，也有库能让你比直接编写调用 CPU 特定 intrinsic 的代码再高一层，实现高效的数学 kernel。Intel 的 MKL「Math Kernel Library」就是这方面的代表，连同著名的 BLAS「Basic Linear Algebra Subroutines」接口，实现了线性代数的所有基础操作。

在此之上，还能找到一些领域专用库，比如 Intel 的 oneDNN，它带来实现神经网络层所需的最常用、最基础的构件。Intel MKL 和 oneDNN 原生集成在 PyTorch 框架中，可以在某些操作（如 Linear + ReLU 或卷积）上带来性能提升。TensorFlow 一侧，oneDNN 可以通过设置环境变量 `TF_ENABLE_ONEDNN_OPTS=1`（*TensorFlow >= 2.5.0*）启用，底层机制类似。

如前所述，基线由两种配置组成：- 开箱即用：原样运行负载，不做任何调优 - 优化版：应用[博客 #1](https://hf.co/blog/bert-cpu-scaling-part-1#2-benchmarking-methodology)中的各种调优项

#### 基线：Eager 框架的延迟

以 eager 模式运行的框架通常在执行期间才发现实际的图。更准确地说，实际计算图事先未知，你逐步（*eagerly*）执行一个算子，它的输出成为下一个算子的输入，依此类推，直到叶子节点（输出）。

这些框架通常在算法实现上提供更高的灵活性，代价是更高的运行时开销，以及为反向传播保留所有所需元素而可能略多的内存占用。

最后同样重要的一点：在这类框架上通常难以启用图优化，比如算子融合。例如，many 深度学习库（如 oneDNN）对 Convolution + ReLU 有优化的 kernel，但你需要在执行图之前就知道这个模式会出现在操作序列中——而按定义，eager 框架做不到这一点。

总体趋势凸显了核心数对观测延迟的积极影响。多数情况下，增加核心数能缩短不同负载规模的计算时间。但堆核心并不产生单调递减的延迟，负载大小与分配资源数量之间总有权衡。

从上面的图表可以看到，一个很常见的模式出现在拥有多 CPU（多 socket）的系统中使用全部核心时。跨 socket 通信会引入显著的延迟开销，导致总体延迟几乎没有改善。

而且，随着负载变大，跨 socket 通信的开销会变得越来越不敏感，也就是说大负载使用全部计算资源时能从所有可用核心受益。在这个领域，PyTorch（图 1）和 Intel TensorFlow（图 4）的并行支持似乎略好——在序列长度 384 和 512 上，使用全部核心仍能降低观测延迟。

### 调优内存分配器：会影响观测到的延迟吗？

每个动态分配内存的程序所依赖的关键组件之一就是内存分配器。如果你熟悉 C/C++ 编程，这个组件提供 malloc/free 或 new/delete 的底层实现。大多数时候你不用太操心它，默认的分配器（比如大多数 Linux 发行版上的 glibc）开箱就能给出很不错的性能。但某些场景下它未必是最高效的，因为这些默认分配器通常按「大多数时候够用」设计，并非针对特定负载或并行度精调。

那么替代品有哪些、什么时候比默认方案更合适？嗯，还是取决于你软件的运行上下文。

可能的情况包括：分配/释放次数极多导致时间推移下的碎片化、运行软件的特定硬件和/或架构，最后是应用的并行程度。

猜到方向了吗？深度学习乃至所有重计算应用都是重度多线程的——PyTorch、TensorFlow 以及任何面向机器学习负载的框架等软件库也是如此。

默认内存分配策略往往依赖全局内存池，操作时需要同步原语，加大系统整体压力，降低应用性能。Google、Facebook、Microsoft 等公司近期的工作提供了替代的内存分配策略，实现为可轻松集成进软件组件的定制内存分配器库，也可通过动态共享库预加载（preload）来替换执行分配/释放的库。

这些库包括 [tcmalloc]()、[jemalloc]() 和 [mimalloc]()。

### OpenMP

上一节我们谈了机器学习软件（以 CPU 密集负载为主）中的内存管理。这类软件常依赖 PyTorch 或 TensorFlow 等中间层做深度学习，它们通常把所有底层高度并行化的算子实现全部抽象掉。

编写这样高度并行、高度优化的算法是真正的工程挑战，需要对 CPU 实际参与运算的所有元素（同步、内存缓存、缓存有效性等）有非常底层的理解。在这种场景下，能够借助原语来实现强大算法非常重要——相比从零实现所有内容，可以大幅缩短交付时间和计算时间。

市面上有不少库提供这种更高层的能力来加速算法开发。最常见的包括 OpenMP、Thread Building Blocks，以及面向较新标准的 C++ 直接实现。在本文余下部分，我们限定在 OpenMP，特别是把 GNU 的开源社区实现与 Intel OpenMP 实现做对比。后者专门面向 Intel CPU，作为 GNU OpenMP 的即插即用替代时，能提供一流性能。

OpenMP 暴露了[许多环境变量](https://www.openmp.org/spec-html/5.0/openmpch6.html)来自动配置计算所涉及的底层资源，例如用于派发计算的线程数（intra-op 线程）、系统调度器应如何把这些线程绑定到 CPU 资源（线程、核心、socket），以及其他给用户更多控制权的变量。Intel OpenMP 暴露的[环境变量更多](https://www.intel.com/content/www/us/en/develop/documentation/cpp-compiler-developer-guide-and-reference/top/compilation/supported-environment-variables.html)，让用户在调整软件性能时有更大的灵活度。

如上所述，当你试完所有其他系统级调优项之后，可以开始调 OpenMP。只需设置一个环境变量，它就能为你的模型带来最后一波加速。

另外要注意，调优 OpenMP 库只在内部使用 OpenMP API 的软件中生效。具体地，现在只有 PyTorch 和 TorchScript 真正使用 OpenMP，因此能受益于 OpenMP 后端调优。

这也解释了为什么我们只报告这两个框架的延迟。

## 自动性能调优：用 Intel SigOpt 做贝叶斯优化

如上所述，要在 Intel CPU 上改善延迟和吞吐有很多可调项，但正因为太多，逐一调优以达到最优性能可能很繁琐。例如在实验中，我们调了以下这些项：

- 核心数：虽然通常「核心全用上」是好主意，但并不总产生最佳性能，因为这意味着线程间更多通信。而且，更少核心反而更快的情况很有用——它允许同时运行多个实例，延迟和吞吐同时变好。
- 内存分配器：默认 malloc、Google 的 tcmalloc、Facebook 的 jemalloc 中哪个给出最佳性能？
- 并行库：GNU OpenMP 与 Intel OpenMP 哪个给出最佳性能？
- 透明大页（Transparent Huge Pages）：在系统上启用 THP 是否带来更好性能？
- KMP block time 参数：设置线程在完成一个并行区域执行后、进入睡眠前应等待的毫秒数。

当然，暴力法——把所有组合试一遍——会给出达到最优性能所需的最佳调优项取值，但搜索空间大小为 `N x 3 x 2 x 2 x 2 = 24N`，可能要花很长时间：在一台 80 物理核心的机器上，这意味着最多要试 `24 x 80 = 1920` 种配置！😱

幸运的是，Intel 的 [SigOpt](https://sigopt.com/) 通过贝叶斯优化，让这些调优实验既更快又更容易分析，同时提供与暴力法相近的性能。

当我们分析绝对最优延迟与 SigOpt 给出的结果之间的相对差距时，注意到虽然 SigOpt 往往略逊于暴力法（这个特定案例中除序列长度 = 512 外），但给出的性能非常接近，图中最大差距为 **8.6%**。
