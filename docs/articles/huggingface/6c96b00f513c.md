# BigCodeBench：下一代 HumanEval

[HumanEval](https://github.com/openai/human-eval) 是评估大语言模型（LLM）代码生成能力的标杆基准，它让紧凑的函数级代码片段评估变得简单。但人们越来越担心它评估 LLM 编程能力的有效性，主要顾虑是 HumanEval 的任务过于简单，可能无法代表真实世界的编程任务。与 HumanEval 偏算法导向的任务相比，真实软件开发往往涉及五花八门的库和函数调用。此外，LLM 在 HumanEval 上的表现受[数据污染与过拟合问题](https://arxiv.org/abs/2403.07974)影响，用它评估 LLM 的泛化能力并不那么可靠。

虽然已有一些工作试图解决这些问题，但它们要么局限于特定领域，要么是确定性的，要么以智能体为中心（抱歉了 [DS-1000](https://github.com/HKUNLP/DS-1000)、[ODEX](https://github.com/zorazrw/odex) 和 [SWE-bench](https://github.com/princeton-nlp/SWE-bench) 💔）。我们认为社区仍然缺一个易用的、能广泛评估 LLM 编程能力的基准，这正是我们发力的方向。

我们高兴地宣布 BigCodeBench 发布。它在无污染的前提下，评估 LLM 解决实用且有挑战性编程任务的能力。具体来说，BigCodeBench 包含 1,140 个函数级任务，要求 LLM 理解指令并把来自 139 个库的多个函数调用当作工具来组合使用。为了严格评估 LLM，每个编程任务平均包含 5.6 个测试用例，平均分支覆盖率 99%。

准备好深入 BigCodeBench 了吗？开始吧！🚀

## BigCodeBench 的任务长什么样？🕵️‍♂️

BigCodeBench 为每个任务配备了复杂、面向用户的指令，包括清晰的功能描述、输入/输出格式、错误处理和经过验证的交互示例。我们刻意不写分步式的任务说明——因为我们相信有能力的 LLM 应该能从用户视角出发，以开放的方式理解并解决任务。我们用测试用例来验证具体功能点。

```
# We elaborate the above task with some test cases:

# Requirements SetUp
import unittest
from unittest.mock import patch
import http.client
import ssl
import socket

# Start the test
class TestCases(unittest.TestCase):

    # Mock the successful connection and assess the response content
    @patch('http.client.HTTPSConnection')
    def test_response_content(self, mock_conn):
        """ Test the content of the response. """
        mock_conn.return_value.getresponse.return_value.read.return_value = b'Expected Content'
        result = task_func('www.example.com', 443, '/content/path')
        self.assertEqual(result, 'Expected Content')

    # Mock the failed connection and assess the error handling
    @patch('socket.create_connection')
    @patch('http.client.HTTPSConnection')
    def test_ssl_handshake_error_handling(self, mock_conn, mock_socket):
        """ Test handling of SSL handshake errors. """
        mock_socket.side_effect = ssl.SSLError('SSL handshake failed')
        with self.assertRaises(ssl.SSLError):
            task_func('badssl.com', 443, '/test/path')

    # More test cases...
```

BigCodeBench 的任务会用到流行库中丰富的函数调用。我们不限制 LLM 可以使用哪些函数调用，期望它们自行选择合适的函数并灵活组合来完成任务。测试用例被设计成测试框架（test harness），在运行时检验预期的程序行为。

评估 LLM 性能时，我们使用贪心解码下的 Pass@1，度量靠精心设计的测试用例一次性生成正确代码解决任务的比例。这与 [HumanEval](https://github.com/openai/human-eval)、[MBPP](https://github.com/google-research/google-research/tree/master/mbpp) 等基准的做法一致。针对 LLM 倾向于跳过长代码提示词的问题，我们在 Pass@1 评估时补齐缺失的设置代码（如 import 语句、全局常量），称为校准后的 Pass@1（calibrated Pass@1）。

为了更好地理解实现复杂度与工具使用多样性，我们把 BigCodeBench 的任务与一系列代表性基准做了对比，包括 [APPS](https://github.com/hendrycks/apps)、[DS-1000](https://github.com/HKUNLP/DS-1000)、[ODEX](https://github.com/zorazrw/odex)、[APIBench](https://github.com/ShishirPatil/gorilla/tree/main/data/apibench)、[MBPP](https://github.com/google-research/google-research/tree/master/mbpp)、[NumpyEval](https://github.com/microsoft/PyCodeGPT/tree/main/cert/pandas-numpy-eval)、[PandasEval](https://github.com/microsoft/PyCodeGPT/tree/main/cert/pandas-numpy-eval)、[HumanEval](https://github.com/openai/human-eval) 和 [TorchDataEval](https://github.com/microsoft/PyCodeGPT/tree/main/apicoder/private-eval)。我们发现 BigCodeBench 需要更复杂的推理和解决问题的能力才能实现完整功能。

如任务示意图所示，主要目标场景是代码补全（即 `BigCodeBench-Complete`），要求 LLM 根据 docstring 中的详细指令完成函数实现。但考虑到多轮对话等下游应用，用户描述需求时可能更口语化、更简略。这正是指令微调 LLM 的用武之地——它们受过遵循自然语言指令并据此生成代码的训练。为了检验模型是否真的能理解人类意图并转化为代码，我们创建了 `BigCodeBench-Instruct`——一个更具挑战性的 BigCodeBench 变体，专门评估指令微调 LLM。

## 任务从哪里来？🤔

我们通过系统化的"人机协作流程"保证 BigCodeBench 任务的质量。我们从 [ODEX](https://github.com/zorazrw/odex) 这个"种子数据集"出发，其中包含来自 Stack Overflow 的短小但真实的人类意图和对应的 Python 单行代码。我们用 GPT-4 把这些单行代码扩展成完整的函数级任务。

接下来，20 位人类专家——多数有 5 年以上 Python 编程经验——在基于执行的沙箱中自愿引导 GPT-4，不断指示它打磨合成的任务并添加测试用例。任务与测试用例随后在本地环境中检查、在其他 LLM 上预评估，并由另外 7 位人类专家交叉核对，以确保质量。

为验证整体质量，作者抽样了若干任务交给 11 位人类专家解答，人类平均表现达到 97%。

## LLM 在 BigCodeBench 上表现如何？📊

我们在 [Hugging Face Space](https://huggingface.co/spaces/bigcode/bigcodebench-leaderboard) 和 [GitHub Pages](https://bigcode-bench.github.io/) 上都托管了 BigCodeBench 排行榜。这里以 Hugging Face 排行榜为例。

有趣的是，我们观察到 GPT-4 这类指令微调 LLM 会在 `BigCodeBench-Complete` 的长提示词中省略必要的 import 语句，导致任务因缺少模块和常量而失败。这种行为被称为"模型偷懒（model laziness）"，[社区](https://community.openai.com/t/why-i-think-gpt-is-now-lazy/534332)也有讨论。

与人类表现相比，LLM 在 `BigCodeBench-Complete` 上的表现明显更低，在 `BigCodeBench-Instruct` 上甚至更低。最好的模型（GPT-4o）在 `BigCodeBench-Complete` 上的 calibrated Pass@1 为 61.1%，在 `BigCodeBench-Instruct` 上为 51.1%。此外，闭源与开源 LLM 之间存在明显的性能差距。

Pass@1 虽是衡量总体表现的好指标，但不足以细粒度地直接对比模型。受 [Chatbot Arena](https://lmsys.org/blog/2023-05-03-arena/) 启发，我们在 `BigCodeBench-Complete` 上用 Elo 等级分给模型排名。这个方法 originally 用于国际象棋，根据对局表现给棋手排名。我们把它适配到编程任务上：每个任务是一局比赛，每个模型是一名选手。Elo 更新基于对局结果和预期，使用任务级的 calibrated Pass@1（0% 或 100%）并剔除平局。初始 Elo 设为 1000，用最大似然估计拟合，再用 500 次 bootstrap 迭代得到最终分数。我们发现 GPT-4o 大幅领先其他模型，DeepSeekCoder-V2 处于第二梯队。

为了帮助社区理解模型在每个任务上的表现，我们用 calibrated Pass@1 跟踪解决率。在 `BigCodeBench-Complete` 上，有 149 个任务所有模型都解不出，只有 6 个任务被全部解决；在 `BigCodeBench-Instruct` 上，有 278 个任务所有模型都解不出，只有 14 个任务被所有模型完全解决。大量的未解任务和极少的全解任务表明，BigCodeBench 对 LLM 来说是很有挑战性的基准。

## 太好了！我该怎么在 BigCodeBench 上评估我的模型？🛠️

我们提供了一个简单易用的评估框架，让社区能轻松用上 BigCodeBench，可通过 [PyPI](https://pydigger.com/pypi/bigcodebench) 下载。评估框架的原型基于 HumanEval+ 和 MBPP+ 基准的 [EvalPlus](https://github.com/evalplus/evalplus)。但由于我们的基准任务库依赖比 EvalPlus 多样得多，我们搭建了资源限制更小的执行环境，并适配了 BigCodeBench 测试框架中的 `unittest`。

为方便评估，我们提供了预构建的 Docker 镜像，分别用于[*代码生成*](https://hub.docker.com/r/bigcodebench/bigcodebench-generate)和[*代码执行*](https://hub.docker.com/r/bigcodebench/bigcodebench-evaluate)。更多评估框架的使用细节请看我们的 [GitHub 仓库](https://github.com/bigcode-project/bigcodebench)。

### 安装

```
# Install to use bigcodebench.evaluate
pip install bigcodebench --upgrade
# If you want to use the evaluate locally, you need to install the requirements
pip install -I -r https://raw.githubusercontent.com/bigcode-project/bigcodebench/main/Requirements/requirements-eval.txt

# Install to use bigcodebench.generate
# You are strongly recommended to install the [generate] dependencies in a separate environment
pip install bigcodebench[generate] --upgrade
```

### 代码生成

建议使用 `flash-attn` 来生成代码样本。

```
pip install -U flash-attn
```

从一个模型生成代码样本，可用如下命令：

```
bigcodebench.generate \
    --model [model_name] \
    --subset [complete|instruct] \
    --greedy \
    --bs [bs] \
    --temperature [temp] \
    --n_samples [n_samples] \
    --resume \
    --backend [vllm|hf|openai|mistral|anthropic|google] \
    --tp [gpu_number] \
    [--trust_remote_code] \
    [--base_url [base_url]]
```

生成的代码样本会存放在名为 `[model_name]--bigcodebench-[instruct|complete]--[backend]-[temp]-[n_samples].jsonl` 的文件中。

### 代码后处理

LLM 生成的文本未必是可编译的代码——可能包含自然语言行或不完整的附加代码。我们提供 `bigcodebench.sanitize` 工具来清洗代码：

```
# 💡 If you want to store calibrated code in jsonl:
bigcodebench.sanitize --samples samples.jsonl --calibrate
# Sanitized code will be produced to `samples-sanitized-calibrated.jsonl`

# 💡 If you do without calibration:
bigcodebench.sanitize --samples samples.jsonl
# Sanitized code will be produced to `samples-sanitized.jsonl`

# 💡 If you are storing codes in directories:
bigcodebench.sanitize --samples /path/to/vicuna-[??]b_temp_[??]
# Sanitized code will be produced to `/path/to/vicuna-[??]b_temp_[??]-sanitized`
```

### 代码评估

强烈建议使用 [docker](https://docs.docker.com/get-docker/) 这类沙箱：

```
# Mount the current directory to the container
docker run -v $(pwd):/app bigcodebench/bigcodebench-evaluate:latest --subset [complete|instruct] --samples samples-sanitized-calibrated

# ...Or locally ⚠️
bigcodebench.evaluate --subset [complete|instruct] --samples samples-sanitized-calibrated

# ...If the ground truth is working locally (due to some flaky tests)
bigcodebench.evaluate --subset [complete|instruct] --samples samples-sanitized-calibrated --no-gt
```

## 接下来做什么？

我们分享了一份长期路线图，以解决 BigCodeBench 的局限，并与社区持续共建。我们的目标是为社区提供最开放、可靠、可扩展的评估，真正理解 LLM 编程的基础能力，并找到释放其潜力的途径。具体来说，我们计划加强 BigCodeBench 以下几个方面：

- **多语言**：目前 BigCodeBench 仅支持 Python，难以直接扩展到其他编程语言。由于函数调用大多与语言强相关，在 Python 之外的语言中寻找功能相同的包或库很有挑战性。
- **严谨性**：虽然 BigCodeBench 的参考解实现了很高的测试覆盖率，但这并不能保证*所有* LLM 生成的代码方案都能被现有测试用例正确评判。此前的工作如 EvalPlus 尝试通过 LLM 和变异策略增广输入-输出对来扩充有限的测试用例，但把 EvalPlus 适配到 BigCodeBench 的测试框架并不轻松。EvalPlus 侧重输入-输出断言，而 BigCodeBench 的大多数测试框架需要不简单的配置（如 mock patching）才能在运行时检验预期的程序行为。
- **泛化性**：一个关键问题是"模型对未见过的工具和任务泛化得如何？"目前 BigCodeBench 覆盖的是常见库和日常编程任务。让模型在使用 [transformers](https://github.com/huggingface/transformers)、[langchain](https://github.com/langchain-ai/langchain) 等新兴库的编程任务上做基准测试会更有意思。
- **演化**：库会过时也会被更新，意味着模型训练用的源代码数据在不断演变。模型可能记不住已废弃库版本的函数调用，这对任何依赖工具库的编程基准都是挑战——不周期性更新就无法正确检验模型能力。与之相关的另一个担忧是训练数据变化带来的测试集污染。
- **交互性**：近期的关注点在 *LLM 即智能体（LLMs as Agents）* 这一概念上，它被视为通向通用人工智能的路径。具体来说，LLM 将落地到约束更少的沙箱环境中，可以操作浏览器、终端等应用。这样的环境有助于解锁 [self-debugging](https://arxiv.org/pdf/2304.05128)（自我调试）和 [self-reflection](https://arxiv.org/abs/2303.11366)（自我反思）等能力。

我们期待社区的反馈与贡献，一起长期把 BigCodeBench 建好 🤗
