# 不让任何 GPU 掉队：借助 TRL 中同址 vLLM 释放效率

作者：Mert Toslali、Yu Chin Fabian Lim、Quentin Gallouédec、Ed Snible、Raghu Ganti、Mudhakar Srivatsa（ibm-ai-platform）

## 🚀 引言

TRL 支持用 GRPO 训练 LLM——这是 [*DeepSeekMath* 论文](https://huggingface.co/papers/2402.03300)中提出的在线学习算法。GRPO 里，模型从自己的输出中学习：训练时生成回答、接收反馈、再用反馈持续自我改进。

这让生成成为训练环路中的关键环节——也是主要瓶颈。为了加速生成，TRL 集成了 vLLM。这个组合让你在 GRPO 设定下更高效地训练强模型。不过，有个坑。

## 🧨 问题

在 TRL v0.18.0 之前，vLLM 只支持 **server 模式**：作为独立进程跑在与训练任务不同的 GPU 上，通过 HTTP 与训练脚本通信。这让部署模块化、易于使用——但也引入了 GPU 低效。

事情的经过是：

- 训练期间，模型需要频繁生成补全。
- 训练器向 vLLM 服务器发请求，vLLM 在自己的 GPU 上跑。
- vLLM 生成时，**训练 GPU 闲置**干等。
- 生成完成后，**vLLM 的 GPU 转为闲置**，训练再继续。

这种训练与生成之间的"乒乓"导致：

- 两边都在浪费 GPU 时间
- 需要**额外 GPU** 纯粹用来跑推理
- 整体**吞吐下降、成本上升**

在 GRPO 这类在线学习方法里——生成持续不断——这种低效更加刺眼。硬件多花了钱，性能却不如预期。

**于是关键问题来了：*能不能让训练和生成共用同一批 GPU，而不是把它们分开？***

## 💡 机会

核心问题是训练和推理跑在不同 GPU 上，造成空闲时间和利用率不足。自然的解法？让两者跑在同一批 GPU 上。与其让 vLLM 作为独立进程、独立设备上的独立服务器，不如让 vLLM 和训练代码并肩运行，加入同一个分布式进程组。这样就能启动一个分布式任务，训练和推理共享同一批设备，在两种任务间高效切换、不浪费资源。

这个方案就是我们说的**同址（colocation）**。训练与推理同址部署在同一批 GPU 上，通过同一进程组协调，平滑地轮流使用设备——不需要额外硬件。

此前这在 TRL 里做不到——它依赖把 vLLM 作为外部 HTTP 服务器。我们的 [PR #3394](https://github.com/huggingface/trl/pull/3394) 改变了这一点：新增了对 vLLM external launcher 的支持，让 vLLM 真正集成进训练进程。

### 这带来什么

- **统一执行**：把 vLLM 嵌入同一进程组后，训练与推理任务共享同一批 GPU，轮流用而不是互相干等。空闲时间减少，整体效率提升。
- **省掉 HTTP 通信**：不需要 REST API 调用和网络——vLLM 内联在训练循环里，没有额外开销和延迟。
- **Torchrun 兼容**：与 `torchrun` 无缝协作，只需少量配置改动即可跨节点扩展。
- **TP 与 DP 支持**：兼容张量并行（Tensor Parallelism）和数据并行（Data Parallelism），适合大规模训练。
- **SPMD 执行模式**：采用单程序多数据（SPMD）模型，每块 GPU 同步运行自己的引擎实例。非常适合分布式多 GPU、多节点环境。
- **部署更简单**：不再需要维护单独的服务器脚本——vLLM 直接在训练任务内部启动和控制。
- **吞吐增强**：避免 GPU 空闲、消除进程间通信，系统训练和生成都更快——这在 GRPO 这类在线学习设定下尤为重要。
- **更稳健的进程间通信**：因为避开了 server 模式中"在独立进程之间搭建分布式进程组"的复杂性，这种方式更稳健。

多亏这个特性，同址训练与推理不再是个 hack——现在是**一等公民、可扩展、生产可用**。

## 🧩 设计：从分离服务器到共享 GPU

从 server 模式 TRL 到同址 TRL 的转变，核心是让 GPU 用得更聪明。下图展示了差异：

[![gpus-design](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-colocate/gpus-design.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-colocate/gpus-design.png)

### Server 模式 TRL（上排）

server 模式的 TRL 里，训练和推理跑在不同 GPU 上。例如：

- GPU 0 到 2 用于训练。
- GPU 3 完全专门跑 vLLM 服务器。

训练步期间，**GPU 3 闲置**。生成步（推理）期间，GPU 3 在生成输出，而 **GPU 0–2 闲置**。

这导致：

- GPU 使用低效，设备经常互相干等
- 要额外配置专门跑推理的 GPU
- 成本和复杂度上升

### 同址 TRL（下排）

相比之下，同址 TRL 把训练和 vLLM 跑在**同一批 GPU** 上。每块 GPU：

- 运行训练循环
- 在**同一进程**内启动一个 vLLM 引擎

训练与推理**轮流**使用 GPU 资源——不需要专用设备或独立进程。

这个设计：

- 减少空闲时间
- 把进程间和 HTTP 通信降到最低
- 充分利用可用的 GPU 显存和算力
- 在不增加硬件的情况下带来**更快的吞吐**

## 🛠️ 实现说明

不再是把 vLLM 作为服务器启动，[训练器现在以**进程内**方式启动 vLLM](https://github.com/huggingface/trl/blob/fef915e36f12f759b384e4ab6f650208130aa232/trl/trainer/grpo_trainer.py#L647-L658)，使用 external launcher，如下所示：

```
self.llm = LLM(
    model=model.name_or_path,
    tensor_parallel_size=args.vllm_tensor_parallel_size,
    gpu_memory_utilization=self.vllm_gpu_memory_utilization,
    max_num_seqs=self.args.per_device_train_batch_size
        * self.vllm_tensor_parallel_size
        * self.args.gradient_accumulation_steps,
    max_model_len=self.max_prompt_length + self.max_completion_length,
    distributed_executor_backend="external_launcher",
    # Feed identical seed for tp groups to ensure sampling results are the same across workers
    seed=self.accelerator.process_index // self.vllm_tensor_parallel_size,
)
```

同址 vLLM 遵守 torch.distributed 的进程组与 rank 结构。这让 vLLM 可以和训练一起初始化而不冲突，TP/DP 配置也能顺畅工作：

```
if self.vllm_tensor_parallel_size > 1:
    # Create subgroups of ranks for TP, each group with `vllm_tensor_parallel_size` ranks.
    self.tp_group, _ = torch.distributed.new_subgroups_by_enumeration(
        [
            list(range(i * self.vllm_tensor_parallel_size, (i + 1) * self.vllm_tensor_parallel_size))
            for i in range(self.accelerator.num_processes // self.vllm_tensor_parallel_size)
        ]
    )
```

同址 vLLM 不再依赖 REST API——它直接在内存中运行，用原生 Python 调用通信：

```
if self.vllm_tensor_parallel_size > 1:
    orig_size = len(prompts_text)
    gathered_prompts = [None for _ in range(self.vllm_tensor_parallel_size)]
    torch.distributed.all_gather_object(gathered_prompts, prompts_text, group=self.tp_group)
    all_prompts_text = [p for sublist in gathered_prompts for p in sublist]
else:
    all_prompts_text = prompts_text

with profiling_context(self, "vLLM.generate"):
    all_outputs = self.llm.generate(all_prompts_text, sampling_params=sampling_params, use_tqdm=False)

completion_ids = [output.token_ids for outputs in all_outputs for output in outputs.outputs]

if self.vllm_tensor_parallel_size > 1:
    local_rank_in_group = torch.distributed.get_rank(group=self.tp_group)
    tp_slice = slice(local_rank_in_group * orig_size, (local_rank_in_group + 1) * orig_size)
    completion_ids = completion_ids[tp_slice]
```

要用这套配置，只需在 GRPO 配置里设置 vllm_mode="colocate"：

```
training_args = GRPOConfig(
    ...,
    use_vllm=True,
    vllm_mode="colocate",
)
```

> 注：根据模型大小和训练的整体显存需求，你可能需要调整 GRPOConfig 里的 vllm_gpu_memory_utilization 参数，以避免利用率不足或 OOM。

## 📊 实测：同址 vs 普通 TRL 性能

为量化同址的影响，我们做了一系列实验，对比传统 **server 模式**（vLLM 作为独立服务器跑在单独 GPU 上）与新的 **colocate 模式**（训练与推理共享同一批 GPU）。

**server 模式**下，只有 7 块 GPU 用于训练，因为 1 块 GPU 完全 dedicated 给 vLLM 推理服务器。

**colocate 模式**下，8 块 GPU 全部用于训练——默认也就增大了有效批大小。

为保证公平对比，我们把 server 模式的吞吐**按 8/7 做了归一化**。这个调整考虑了 colocate 模式更高的训练容量，让两种配置在同等训练条件下可比。

### 实验 1：1.5B 模型 —— 不同批大小

- 随着批大小增加，两种配置的吞吐都提升。
- **同址配置在最大批大小下达到 1.43 倍加速**。
- 更大的批次让同址模式的共享显存利用得更好。[![small-b](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-colocate/small-b.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-colocate/small-b.png)

### 实验 2：1.5B 模型 —— 不同张量并行度（TP）

- 同址配置中，提高 TP 反而**降低性能**。
- 更多分片带来更多通信开销——**对小模型并不理想**。
- **要点**：小模型在同址模式下别过度分片。[![small-tp](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-colocate/small-tp.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-colocate/small-tp.png)

### 实验 3：7B 模型 —— 不同批大小

- 同样，colocate 模式**随批大小扩展得更好**。
- 最大测试批下增益达 **1.35 倍加速**。[![med-b](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-colocate/med-b.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-colocate/med-b.png)

### 实验 4：7B 模型 —— 不同张量并行度（TP）

- 与 1.5B 模型趋势相反。
- 7B 时，**更高 TP 提升吞吐**，最高达 **1.73 倍加速**。
- **大模型在同址配置下受益于分片**。[![med-tp](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-colocate/med-tp.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-colocate/med-tp.png)

## 📊 扩展到 72B 模型

训练 **Qwen2.5-Math-72B** 这样的大模型时，用对策略很重要——要让训练在大量 GPU 和节点间高效、可扩展、稳定。我们的配置把**同址 vLLM** 与几项关键优化结合起来。

### vLLM 的休眠模式（Sleep Mode）

同址训练时，显存管理至关重要——训练和推理要在同一批设备上顺畅运行。为支持这一点，我们把 vLLM 的 `sleep()` API 加进了 GRPO 训练循环。

`sleep()` 函数临时挂起 vLLM 引擎并释放 GPU 显存。它支持两个级别：

- **Level 1**：把模型权重从 GPU 卸载（保留在 CPU 内存），并清空 KV cache。适合很快会复用同一模型的场景。
- **Level 2**：把模型权重和 KV cache 全部卸载。最适合模型将更换、或不会马上复用的场景。

GRPO 每一步之后模型都会更新——所以我们用 **Level 2 休眠**。

Level 2 休眠的好处：

- **最大化训练可用的空闲显存**
- **避免训练与生成之间的显存争用**
- 即便像 Qwen2.5-72B 这样的大模型，同址依然高效

这个小小的添加，为实现顺畅、可扩展的同址训练带来了**巨大差别**。

### DeepSpeed 优化

训练 Qwen2.5-72B 这样的大模型，我们依赖 **DeepSpeed ZeRO Stage 3**——与普通 TRL 相同的配置。

ZeRO 通过把内存分布到多 GPU 上来扩展大模型。Stage 3 更进一步，把以下内容都做了切分：

- 模型权重
- 梯度
- 优化器状态

这对单卡装不下的模型不可或缺。有了 ZeRO Stage 3，每块 GPU 只承载模型的一部分。

我们还启用了以下选项：

- `"offload_optimizer": {"device": "cpu"}`：把优化器状态挪到 CPU，释放 GPU 显存——对同址配置至关重要。
- `"overlap_comm": true`：让通信与计算重叠，加速训练。
- `"contiguous_gradients": true`：把梯度分配在单一内存块中，改善内存访问、减少碎片。

这些优化帮助**高效训练 72B 模型**，并确保同址在紧张显存约束下保持稳定。

### Accelerate 集成

按照 TRL 的推荐，我们使用 **Accelerate**——一个简化分布式训练的轻量库。它负责：

- 多 GPU、多节点任务启动
- 数据并行
- 梯度累积
- 分布式数据加载

这让配置干净、可扩展、易维护。

## 🎓 挑战、经验与下一步

在把 GRPO 训练扩展到同址 vLLM 的工作中，我们遇到了几个关键挑战，也在大模型训练的效率、灵活性和系统设计上学到了重要一课。

### 挑战

- **vLLM ≥ 0.8.0 的张量并行 Bug。** TP 配合 external_launcher 在 vLLM 0.8.0 及之后版本失效。该问题跟踪于 Issue [#15895](https://github.com/vllm-project/vllm/issues/15895)。为定位破坏点，我们采用了 vLLM 开发者[博客](https://blog.vllm.ai/2025-01-10/dev-experience.html)里描述的方法（它为每个 commit 提供 wheel）。二分之后，我们锁定破坏 commit 是 [cc10281](https://github.com/vllm-project/vllm/commit/cc10281498fc2a6eb804274dcf22e6cb766f7aa7)。根因是确定性——新版本要求显式设置随机种子。设了 seed 之后，问题消失。
- **Level 2 休眠的 Buffer Bug。** 最初，尝试用 load_weights 重新加载权重时 level 2 休眠不能正常工作。问题跟踪在 [Issue #16564](https://github.com/vllm-project/vllm/issues/16564)：模型的 buffers（如 BatchNorm 的 running mean/var）在从休眠唤醒后没有被恢复。修复来自 PR [#16889](https://github.com/vllm-project/vllm/pull/16889)，它加入了从 level 2 休眠唤醒时显式恢复 buffers 的逻辑。我们现在保留原始 buffers 的副本，加载新权重后手动重新应用。
- **退出时的段错误。** vLLM 休眠在训练结束、关闭进程时会导致段错误，这个问题仍未解决（Issue [#16993](https://github.com/vllm-project/vllm/issues/16993)）。崩溃发生在关闭阶段，不影响训练本身，所以我们能完成本博客分享的全部 demo 和实验。但在把 sleep() 完整并入 TRL 上游之前，我们在等官方修复。

这些挑战都不是拦路虎，但需要仔细调试、版本控制，以及对 vLLM 底层内存与并行管理的更深入理解。

### 经验教训

- 同址推理显著提升 GPU 利用率。让训练和生成共享同一批 GPU，我们消除了空闲时间、降低了硬件需求——即便 GPU 更少也能达到更高吞吐。
- vLLM 的 sleep() 特性对大规模同址不可或缺。它实现对内存使用的精细控制，让训练在生成步之间完全收回 GPU 显存——这是 Qwen2.5-72B 这类模型得以同址的关键。
- DeepSpeed ZeRO Stage 3 对训练大模型不可或缺。它通过把权重、梯度、优化器状态分布到多 GPU，让超大模型装得进内存。我们的经验是：启用 contiguous_gradients 有助于减少显存碎片，把优化器卸载到 CPU 释放了关键显存——这在同址配置下尤其有用。
- 同址很强大，但有取舍。它在显存被精心管理时效果最好，常常需要手动调节 vllm_gpu_memory_utilization 等参数。虽然有明确的吞吐收益、减少 GPU 空闲，但对显存预算很紧或碎片控制不好的模型，同址未必合适。做得好的话，它能释放巨大的效率收益。
- TP/DP 兼容、Accelerate 和 torchrun 支持让部署丝滑。尽管底层架构复杂，整个系统可以用标准分布式工具启动和扩展。
- 同址训练能保持模型质量。在多个基准（Math500、AIME24）上，同址与普通配置结果相当，证实没有为效率牺牲性能。

## ✅ 结论

本文探讨了把 vLLM 与 GRPO 训练同址部署，如何在大语言模型（包括 Qwen2.5-72B 这么大的模型）训练中释放显著的效率收益。

传统上 TRL 只支持 vLLM 的 server 模式——推理需要独立进程和独立 GPU，导致算力浪费和空闲时间。随着 vLLM external launcher 的引入和 TRL 的同址 [PR #3394](https://github.com/huggingface/trl/pull/3394)，我们现在可以在同一个分布式进程组、同一批 GPU 上运行训练与推理，完整支持 TP、DP 和 Accelerate。

尽管仍有挑战——比如特定版本的 vLLM bug 和 sleep() 之类的边界情况——总体结果表明同址 GRPO 是训练大模型高效、务实、可扩展的解法。我们很兴奋继续打磨这套配置、集成 FSDP 等特性、冲击大模型训练的极限——让下一代 LLM 的构建者训练得更快、更便宜、更普惠。

```
from datasets import load_dataset
from trl import GRPOConfig, GRPOTrainer

# Load dataset
dataset = load_dataset("trl-lib/tldr", split="train")

# Define the reward function
def reward_len(completions, **kwargs):
    return [-abs(20 - len(completion)) for completion in completions]

# Define training arguments
training_args = GRPOConfig(
    output_dir="Qwen2-0.5B-GRPO",
    logging_steps=1,
    use_vllm=True,
    vllm_mode="colocate",
    vllm_tensor_parallel_size=1,
    vllm_gpu_memory_utilization=0.3,
    max_prompt_length=512,
    max_completion_length=1024,
    max_steps=2,
    num_generations=4,
    num_train_epochs=1,
    per_device_train_batch_size=4,
    push_to_hub=False,
    report_to=None
)

# Create and run the trainer
trainer = GRPOTrainer(
    model="Qwen/Qwen2-0.5B-Instruct",
    reward_funcs=reward_len,
    args=training_args,
    train_dataset=dataset,
)

trainer.train()
```
