# Few-shot 学习实战：GPT-Neo 与 🤗 Accelerated Inference API

在许多机器学习应用中，可用标注数据的数量是产出高性能模型的障碍。NLP 的最新进展表明，可以通过在推理时为大语言模型提供少量示例来克服这一限制——这就是所谓的 Few-Shot Learning（小样本学习）。在这篇博客中，我们会解释 Few-Shot Learning 是什么，并探索如何使用名为 GPT-Neo 的大语言模型和 🤗 Accelerated Inference API 来生成你自己的预测。

## 什么是 Few-Shot Learning？

Few-Shot Learning 指用极少量训练数据引导机器学习模型预测的做法，例如在推理时给出几个例子；与之相对的是标准微调技术——它需要相对大量的训练数据，让预训练模型准确适配目标任务。

这项技术过去主要用在计算机视觉，但借助一些最新的语言模型，如 [EleutherAI GPT-Neo](https://www.eleuther.ai/research/projects/gpt-neo/) 和 [OpenAI GPT-3](https://openai.com/blog/gpt-3-apps/)，我们现在可以把它用于自然语言处理（NLP）。

在 NLP 中，Few-Shot Learning 可以配合大语言模型使用——这些模型在大规模文本数据集预训练期间已经隐式地学会了执行大量任务，使模型能够仅凭少量示例就泛化理解相关但从未见过的任务。

NLP 的 few-shot 示例由三个主要部分组成：

- **任务描述（Task Description）**：对模型该做什么的简短描述，例如 "Translate English to French"
- **示例（Examples）**：几个展示模型预期预测内容的例子，例如 "sea otter => loutre de mer"
- **提示（Prompt）**：新示例的开头部分，模型应通过生成缺失文本把它补全，例如 "cheese => "

构造这些 few-shot 示例可能颇有讲究，因为你需要通过它们把希望模型执行的「任务」表达清楚。一个常见问题是：模型（尤其是较小的模型）对示例的写法非常敏感。

一种在生产环境中优化 Few-Shot Learning 的思路是：为一个任务学习通用表示，再在其上训练任务特定的分类器。

OpenAI 在 [GPT-3 论文](https://arxiv.org/abs/2005.14165)中展示了 few-shot prompting 能力随语言模型参数规模增长而提升。

## GPT-Neo 是什么？

GPT⁠-⁠Neo 是 [EleutherAI](https://www.eleuther.ai/projects/gpt-neo/) 基于 GPT 架构推出的一系列 transformer 语言模型。[EleutherAI](https://www.eleuther.ai) 的首要目标是训练一个与 GPT⁠-⁠3 规模相当的模型，并以开放许可证向公众开放。

目前所有可用的 GPT-Neo checkpoint 都用 Pile 数据集训练——这是一个大型文本语料，在（[Gao et al., 2021](https://arxiv.org/abs/2101.00027)）中有详尽记录。因此，在与训练文本分布匹配的文字上它的表现预期会更好；设计示例时请牢记这一点。

## 🤗 Accelerated Inference API

[Accelerated Inference API](https://huggingface.co/inference-api) 是我们的托管服务，通过简单的 API 调用即可对 🤗 Model Hub 上公开可用的 10,000 多个模型或你自己的私有模型执行推理。该 API 在 CPU 和 GPU 上提供加速，相比 Transformers 的裸部署可获得[高达 100 倍的提速](https://huggingface.co/blog/accelerated-inference)。

要把 `GPT-Neo` 的 Few-Shot Learning 预测集成进你自己的应用，你可以用下面的代码片段调用 🤗 Accelerated Inference API。你的 API Token 在[这里](https://huggingface.co/settings/token)获取；还没有账号的话，从[这里](https://huggingface.co/pricing)开始。

```
import json
import requests

API_TOKEN = ""

def query(payload='',parameters=None,options={'use_cache': False}):
    API_URL = "https://api-inference.huggingface.co/models/EleutherAI/gpt-neo-2.7B"
        headers = {"Authorization": f"Bearer {API_TOKEN}"}
    body = {"inputs":payload,'parameters':parameters,'options':options}
    response = requests.request("POST", API_URL, headers=headers, data= json.dumps(body))
    try:
      response.raise_for_status()
    except requests.exceptions.HTTPError:
        return "Error:"+" ".join(response.json()['error'])
    else:
      return response.json()[0]['generated_text']

parameters = {
    'max_new_tokens':25,  # number of generated tokens
    'temperature': 0.5,   # controlling the randomness of generations
    'end_sequence': "###" # stopping sequence for generation
}

prompt="...."             # few-shot prompt

data = query(prompt,parameters,options)
```

## 实践心得

以下一些实践经验，能帮你上手 `GPT-Neo` 和 🤗 Accelerated Inference API。

由于 `GPT-Neo`（2.7B）大约比 `GPT-3`（175B）小 60 倍，它对 zero-shot 问题的泛化不如后者，需要 3—4 个示例才能达到好效果。当你提供更多示例时，`GPT-Neo` 能理解任务并顾及 `end_sequence`，这让我们可以相当好地控制生成文本。

[![insights-benefit-of-examples](https://huggingface.co/blog/assets/22_few_shot_learning_gpt_neo_and_inference_api/insights-benefit-of-examples.png)](https://huggingface.co/blog/assets/22_few_shot_learning_gpt_neo_and_inference_api/insights-benefit-of-examples.png)

超参数 `End Sequence`、`Token Length` 和 `Temperature` 可以用来控制模型的 `text-generation`，你可以借此解决你的任务。`Temperature` 控制生成的随机性：较低温度带来较不随机的生成，较高温度带来更随机的生成。

[![insights-benefit-of-hyperparameter](https://huggingface.co/blog/assets/22_few_shot_learning_gpt_neo_and_inference_api/insights-benefit-of-hyperparameter.png)](https://huggingface.co/blog/assets/22_few_shot_learning_gpt_neo_and_inference_api/insights-benefit-of-hyperparameter.png)

从这个例子可以看到，定义好你的超参数多么重要——它们决定了你是完成任务，还是惨烈失败。

## 负责任的使用

Few-Shot Learning 是一项强大的技术，但也有其独特的陷阱，在设计用例时必须考虑。为此举个例子：考虑 widget 中默认提供的 `Sentiment Analysis` 设置。在看过三个情感分类示例后，模型在 temperature 设为 0.1 时，有 4/5 的次数做出如下预测：

> Tweet: "I'm a disabled happy person"Sentiment: Negative

这会出什么问题？想象你用情感分析聚合在线购物网站的商品评论：一个可能的结果是对残障人士有用的商品被自动降权——这是一种自动化歧视。关于这一具体问题，推荐阅读 ACL 2020 论文 [Social Biases in NLP Models as Barriers for Persons with Disabilities](https://www.aclweb.org/anthology/2020.acl-main.487.pdf)。由于 Few-Shot Learning 更直接依赖从预训练中学到的信息和关联，它对这类失败更为敏感。

如何把危害风险降到最低？以下是一些实践建议。

### 负责任使用的最佳实践

- 让用户知道他们的体验中哪些部分依赖该 ML 系统的输出
- 如果可能，赋予用户退出的能力
- 提供机制让用户对模型决策给出反馈，并予以推翻
- 监控反馈——特别是模型失败——关注可能受到不成比例影响的用户群体

最需要避免的是：用模型替用户或关于用户自动做决策，而不给人工介入提供输入或纠正输出的机会。包括欧洲 [GDPR](https://gdpr-info.eu/) 在内的一些法规要求，对自动做出的涉及用户的决策必须向用户提供解释。
