开始之前，先快速回顾两个我们反复用到的概念：

- GPU **kernel** 是在 GPU 大量线程上并行运行的程序。
- CPU 负责**调度并 launch** 这些 kernel。profiler trace 里看到的大部分 PyTorch 开销都是这种调度工作。

## 从 matmul-add 到 Linear

`nn.Linear` 只是把我们在[第 1 部分](https://huggingface.co/blog/torch-profiler)已经剖析过的矩阵乘法加法包成了模块。唯一区别是它把 weight 和 bias 作为参数持有，并暴露 PyTorch 用户熟悉的 `forward` 方法。

```
# bias=True would truly emulate the multiplication and addition
# operations we have seen in part 1 of the series
linear_layer = nn.Linear(in_dim, out_dim, bias=True)
y = linear_layer(x)
```

当前这个运算可以写成：

```
y = x @ w.T + b
```

其中 `x` 是输入，`w` 是权重，`b` 是偏置。我们跑一下 [`02_linear.py`](https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/02_linear.py) 看看 profile。

```
uv run 02_linear.py --batch 1024 --in_dim 32 --out_dim 64
uvx trace-util -f traces -b <hf_uname>/traces
```

> trace-util 是一个工具，会把你的 trace 同步到 Hugging Face 存储桶，然后在终端给出 Perfetto URL。

### transpose 在干什么？

| [![Zoomed in CPU dispatch chain showing the aten::t transpose op nested before aten::addmm inside aten::linear, with no matching activity on the GPU lane](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/transpose-cpu-dispatch.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/transpose-cpu-dispatch.png) |
| --- |
| 图 2：transpose 的 CPU 行 |

放大 trace（如图 2），会注意到 `aten::addmm`（乘加）之前有一个 `aten::t`（transpose）算子。可以猜到：`nn.Linear` 会先转置权重参数，再与输入相乘——这就是 `aten::t` 的来源。

一个重要的点是：`aten::t` 实际上**不复制、不重排数据**——它只在 CPU 上重写 tensor 的元数据（shape 和 stride）来表示转置后的矩阵，并不在 GPU 上 launch kernel。可以从两处验证：看 trace 的 GPU 泳道，或看 profiler 表中 `aten::t` 行在 CUDA 上花费的时间。

### 为什么没有独立的 `mul` 和 `add` kernel？

| [![Profiler trace of the linear layer with the dispatch chain highlighted, showing aten::linear, aten::t and aten::addmm but no separate aten::add op](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/no-aten-add.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/no-aten-add.png) |
| --- |
| 图 3：linear 层的 profile 中没有 `aten::add` |

如图 3，linear 层的调度链里没有 `aten::add`（偏置加法）。原因是偏置加法被*折叠*进了矩阵乘法 kernel——用所谓 **epilogue（结尾旁路计算）**。

**epilogue** 是 GEMM（GEneral Matrix Multiply，通用矩阵乘）kernel 在写回结果到 HBM（High Bandwidth Memory，GPU 主存）之前顺手做的一小步计算。加偏置、套激活、乘常数都是典型的 epilogue。epilogue 的意义在于避免第二次读写 HBM——访存才是让运算昂贵的元凶。

`nn.Linear` 调用 `torch.nn.functional.linear`，后者调用 `aten::linear`。`aten::linear` 检查输入，发现有 bias，于是直接分发 `aten::addmm(bias, x, weight)`，而不是分别做 matmul 和 add。`addmm` 计算：

```
out = x @ weight.T + bias
```

GPU 上运行的 cuBLAS GEMM kernel 自带 bias-add 变体，`aten::addmm` 选中的正是它。加法永远不会作为独立 kernel 出现，因为它**就是 matmul kernel 写回的一部分**——这正是 epilogue 的含义。

这里要意识到一个微妙的点：你在[第 1 部分 `--compile` 下看到的 kernel](https://huggingface.co/blog/torch-profiler#did-we-fuse-the-matmul-and-add-kernels-into-one)（`addmm`）就是 eager `nn.Linear` 本来就在用的 kernel。这里没有留给 `torch.compile` 融合的东西——接下来我们就来验证这一点。

### `--compile` 对单个 Linear 有帮助吗？

我们把 forward 调用编译一下，再看 trace（trace 可视化见[下一节](https://huggingface.co/blog/torch-mlp-fusion#where-did-the-transpose-go-kernel-layouts-and-pre-ops)）。

```
uv run 02_linear.py --batch 1024 --in_dim 32 --out_dim 64 --compile
uvx trace-util -f traces -b <hf_uname>/traces
```

对比单个 `nn.Linear` forward 的 eager 与 compiled trace，你会发现：

- GPU 上是同一个 cuBLAS GEMM kernel。
- CPU 上是同一个 `aten::addmm` 算子。
- CPU 泳道多了几行只有 compile 才有的内容。

这一点值得记牢。常见的条件反射是"模型感觉慢就掏 `torch.compile`"。但对单个带 bias 的 GEMM，compile 几乎无事可做。这不是 bug——只是 compile 需要至少两个运算才可能有东西可融。我们来看 [MLP](https://huggingface.co/blog/torch-mlp-fusion#stacking-two-linears-the-mlp) 证明这一点。

### transpose 去哪了？kernel 布局与 pre-ops

细心对比两份 trace（eager vs compile）会发现：eager 的 CPU 调度链内容比 compiled 的更多。

| [![Eager CPU dispatch chain with the aten::t transpose and aten::addmm boxed separately under aten::linear](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/eager.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/eager.png) |
| --- |
| 图 4：eager 调度链，`aten::linear` 依次走 `aten::t`（transpose）再 `aten::addmm` |

| [![Compiled CPU dispatch chain showing a Torch-Compiled Region and a single aten::addmm call, with no transpose op](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/compile.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/compile.png) |
| --- |
| 图 5：compiled 调度链，直接调用 `aten::addmm`，没有 transpose |

eager 模式下 `aten::linear` 内部的调度链是 `aten::t` 接 `aten::addmm`（图 4）。要弄清 `aten::t` 到底做了什么，得先绕道讲一下 *stride* 和 *view（视图）*。

tensor 在内存里以一段扁平、连续的数字存储。`shape` 和 `stride` 是叠在其上的元数据，告诉 PyTorch 如何遍历：stride 为 `(s0, s1)` 意味着"移动一行跨过 `s0` 个元素，移动一列跨过 `s1` 个元素"。改动元数据就得到同一份原始数据的一个新*视图*，无需复制：

```
>>> M = torch.tensor([[0, 1],
...                   [2, 3],
...                   [4, 5]])
>>> M.shape, M.stride()
(torch.Size([3, 2]), (2, 1))   # two steps per row, one step per column

>>> T = M.t()                  # transpose
>>> T.shape, T.stride()
(torch.Size([2, 3]), (1, 2))   # shape and stride swapped, data untouched
>>> T
tensor([[0, 2, 4],
        [1, 3, 5]])
>>> T.flatten()                # forced to materialize, so the data is reordered
tensor([0, 2, 4, 1, 3, 5])
```

`M.t()` 一个数字都没搬。它返回了一个 stride 交换后的新视图，于是按行读取时以转置顺序遍历原始缓冲区 `0, 1, 2, 3, 4, 5`。底层数据完全相同，只是元数据不同。

linear 层里的 `aten::t` 正是如此：不分配新 tensor、不复制数据，只产出一个重写 stride 的权重*视图*。

如图 5 所见，compile 并没有去掉某个 GPU kernel——它去掉的是调度这个视图的 *CPU 开销*。Inductor 在编译期追踪了整条 view 链，一次性算出最终 stride，然后直接生成一个把这些 stride 硬编码进去的 `aten::addmm` 调用。几微秒的 CPU 工作消失了，GPU 上的数学完全一样。

不出意料，如果输入数据违反了编译器预计算的 stride，就会抛错。

看两份 trace 的 GPU 泳道，每次 forward 都恰好一个 kernel，而且是*同一个* kernel：

```
cutlass_80_wmma_tensorop_bf16_s161616gemm_bf16_32x32_32x1_tn_align8
```

既然没有 transpose kernel 运行，是谁教会 GEMM 按转置顺序读权重的？答案在 kernel 名字里。看后缀：

```
cutlass_80_wmma_tensorop_bf16_s161616gemm_bf16_32x32_32x1_tn_align8
                                                          ^^
```

那个 `tn` 就是布局描述符。cuBLAS 和 CUTLASS 会为每种输入布局组合*分别预编译一个独立的 kernel 二进制*。

`n`（非转置）与 `t`（转置）描述 kernel 在内层循环里如何遍历其输入。dispatcher 的工作就是查看输入 stride，判断哪个后缀组合匹配，挑出正确的预编译 kernel。

> profiler trace 中的 kernel 名是 kernel 身份的哈希式转储。两次运行显示相同 kernel 名，说明 GPU 干的是同样的活。如果名字不同（比如 _tn_ 对 _nn_、bf16 对 fp16、s16816gemm 对 s161616gemm），说明 GPU 干的活不同，dispatcher 走了不同的分支。学会读这个名字，是对比 trace 时最有用的习惯之一。

## 叠三个 Linear：MLP

本节我们要剖析一个多层感知机（MLP）。为了更有趣一点，我们剖析带 GeGLU 激活变体的前馈网络（实践中用得很多）。这也是我们向深度学习研究史上最伟大句子之一致敬的方式（图 6）。

| [![Conclusions section of the GLU Variants Improve Transformer paper, with the closing sentence attributing the architectures' success to divine benevolence highlighted](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/geglu-paper.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/geglu-paper.png) |
| --- |
| 图 6：[GLU Variants Improve Transformer](https://arxiv.org/abs/2002.05202) 论文的结论部分。 |

```
class SimpleGeGLUMLP(nn.Module):
    def __init__(self, dim, hidden):
        super().__init__()
        self.gate_proj = nn.Linear(dim, hidden, bias=False)
        self.up_proj = nn.Linear(dim, hidden, bias=False)
        self.down_proj = nn.Linear(hidden, dim, bias=False)

    def forward(self, x):
        g = self.gate_proj(x)
        u = self.up_proj(x)
        h = F.gelu(g, approximate="tanh")
        m = h * u
        y = self.down_proj(m)
        return y
```

完整脚本在这里：[`03_simple_mlp.py`](https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/03_simple_mlp.py)。这样执行：

```
uv run 03_simple_mlp.py --batch 64 --seq 128 --dim 768 --hidden 3072
uvx trace-util -f traces -b <hf_uname>/traces
```

在打开 trace 之前，我们先一起想想应该看到什么。`forward` 做了不少计算，但绝大部分我们已经熟悉。

我们应该预期三次 `aten::linear` 调度（每个 `nn.Linear` 一次），还应看到两次 pointwise kernel launch：一次 GeLU、一次乘法。在查看之前先形成预期，是剖析之路上最有用的单一习惯：你读 trace 是为了*证实或打破*一个猜测，而不是从零形成猜测。

从图 7 看，我们可以得意地拍拍自己的背——直觉是对的。每次 forward（一个 `mlp_fwd`），GPU 恰好跑 5 个 kernel。图 8 高亮了 linear 投影层 CPU 泳道上的"occupancy query"。

| 运算 | CPU 算子 | GPU kernel | launches |
| --- | --- | --- | --- |
| `gate_proj` | `aten::linear` | `ampere_bf16_s16816gemm_bf16_128x128_...` | occupancy query + cudaLaunchKernel |
| `up_proj` | `aten::linear` | `ampere_bf16_s16816gemm_bf16_128x128_...` | occupancy query + cudaLaunchKernel |
| `gelu` | `aten::gelu` | `vectorized_elementwise_kernel<4, GeluCUDAKernelImpl...>` | cudaLaunchKernel |
| `h * u` | `aten::mul` | `vectorized_elementwise_kernel<4, ...MulFunctor...>` | cudaLaunchKernel |
| `down_proj` | `aten::linear` | `ampere_bf16_s16816gemm_bf16_128x256_...` | occupancy query + cudaLaunchKernel |

三个 GEMM 在 launch 前各多做一次 `cudaOccupancyMaxActiveBlocksPerMultiprocessor` 调用。第 1 部分有专门一节讲这个，[见这里](https://huggingface.co/blog/torch-profiler#why-does-matmul-have-an-extra-cuda-runtime-call)。那是 cuBLAS 在给 grid 定尺寸。pointwise 运算（GeLU 和 mul）直接 launch，没有 occupancy query。所以"一个 linear"实际是 query + launch，而"一个 pointwise 运算"只是 launch。

| --- |
| 图 9：表格显示某些算子 launch 了零个 kernel |

`aten::t`、`aten::transpose`、`aten::reshape`、`aten::view`、`aten::as_strided` 和 `aten::_unsafe_view` 这些算子不 launch 任何 kernel。它们在表格中显示 CUDA 时间 `0.000us`（图 9），因为它们在 CPU 上只重写 tensor 元数据（shape 与 stride）。粗读表格会看到每个 linear 名下约有六个算子，但只有其中一个（`mm`）真正到达 GPU。

### 为什么会有两种 GEMM kernel？

MLP 为了做 matmul 把 `[batch, seq, dim]` 压平成 `[batch * seq, dim]`。我们的命令行用了 batch=64、seq=128，所以下面的 `8192`（`batch * seq = 64 * 128`）是这么来的。

从 trace 看：

| Linear | `aten::mm` 输入维度 | M·K·N | cuBLAS kernel | 平均 CUDA 时间 |
| --- | --- | --- | --- | --- |
| `gate_proj` | `[8192,768] x [768,3072]` | `8192·768·3072` | `…128x128…stages_32x5_tn` | 0.19ms |
| `up_proj` | `[8192,768] x [768,3072]` | `8192·768·3072` | `…128x128…stages_32x5_tn` | 0.19ms |
| `down_proj` | `[8192,3072] x [3072,768]` | `8192·3072·768` | `…128x256…stages_64x3_tn` | 0.17ms |

三个 GEMM 的 FLOP 数相同，各约 `2·8192·768·3072 ≈ 38.7 GFLOP`，但 `down_proj` 快约 `10%`。同样的工作量、不同的形状（`N=768` 而非 `3072`），于是 cuBLAS 选了不同的 tile（`128×256`，配更深的 `stages_64x3` 流水线），对该形状的复用率更高。

> 想深入了解 tiling，这里有一个很好的入门资源。

这正是为什么表格里有两行 GEMM（图 9）：`128x128` 行是 gate+up，`128x256` 行是 down。

### torch.compile 做了什么？

在编译 `forward` 并可视化之前，照例做一次思维实验：我们期待在 trace 里看到什么。这是个有趣也重要的练习——每次自己剖析时都值得重复。始终建立在直觉之上，一旦有出入，就停下来弄明白为什么。

```
uv run 03_simple_mlp.py --batch 64 --seq 128 --dim 768 --hidden 3072 --compile
uvx trace-util -f traces -b <hf_uname>/traces
```

| [![Profiler trace of the compiled GeGLU MLP showing three aten::mm calls and one fused triton kernel on the CPU lane, labelled mm, mm, fused, mm](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/simple-mlp-compile-trace.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/simple-mlp-compile-trace.png) |
| --- |
| 图 10：编译后 GeGLU MLP 的 profiler trace |

在 eager 模式下，每个 `nn.Linear` 被展开成一串 dispatcher 算子（`aten::linear` → `aten::t` → `aten::transpose` → `aten::matmul` → `aten::reshape` → `aten::mm`）。它们是 ATen 在到达真正 GEMM 之前经过的高层包装。`torch.compile` 拿掉了这条链。

到编译图运行时，没有 linear、没有 matmul、没有 transpose 和 reshape——那些元数据算子都被折叠进了 `mm` 的调用方式里。我们看到三次裸的 `aten::mm` 外部调用（图 10）。证明它们还是同一批 GEMM 的，是 kernel 名与 eager 逐字节一致：gate 和 up 是 `...128x128...stages_32x5_tn`，down 是 `...128x256...stages_64x3_tn`。

### 融合的 Triton kernel

| [![Compiled MLP trace with the triton_poi_fused__unsafe_view_gelu_mul_0 kernel boxed on the CPU lane, replacing the separate gelu and mul kernels from the eager run](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/fused.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/fused.png) |
| --- |
| 图 11：融合的 Triton kernel |

这是整堂 compile 课的头条新闻。eager 的两个 pointwise kernel（GeLU 和 mul）加上一个 reshape，塌缩成了一个 kernel：`triton_poi_fused__unsafe_view_gelu_mul_0`（图 11）。来解读一下名字：

- `triton`：由 Inductor 的 Triton 后端生成（不是 cuBLAS，也不是 ATen）。
- `poi`：pointwise（Inductor 给 pointwise kernel 标 `poi`，归约标 `red`，持久化归约标 `per`）。
- `fused__unsafe_view_gelu_mul`：它合并的算子——`_unsafe_view`（reshape）、GeLU 和 mul。
- `0`：图内的唯一编号。

为什么这是收益？在 eager 模式下，中间结果 `h = gelu(g)` 是一个完整的 `[8192, 3072]` bf16 tensor（约 50 MB）：GeLU kernel 把它写进 HBM，mul kernel 又马上读回来。融合让中间结果留在寄存器里（芯片内部、比 HBM 更近的存储）。这个 Triton kernel 读一次 `g` 和 `u`，算出 `gelu(g) * u`，写一次结果。整个中间量在全局内存里的一来一回没了。

## 上手写调优的 kernel

到目前为止，kernel 都是 PyTorch（eager）或编译器（`torch.compile`）帮我们挑的。现在我们接入一个人类专家手写、手工调优的 kernel。用的是 `LigerGEGLUMLP` 层，可以从 [Hugging Face Hub](https://huggingface.co/kernels/kernels-community/liger-kernels) 用 `kernels` 库轻松取到。

```
from kernels import get_kernel

kernels_layers = get_kernel("kernels-community/liger-kernels", version=1).layers
kernels_geglu_mlp = kernels_layers.LigerGEGLUMLP(Config()).to(device, dtype=torch.bfloat16).eval()
```

完整脚本在这里：[`03_kernels_mlp.py`](https://huggingface.co/datasets/ariG23498/profiling-pytorch/blob/main/03_kernels_mlp.py)。

```
uv run 03_kernels_mlp.py --batch 64 --seq 128 --dim 768 --hidden 3072
uvx trace-util -f traces -b <hf_uname>/traces
```

### 为什么要用 kernels 库

用 Triton 或 CUDA 写 kernel 是一个问题，把它们*发布出去*是另一个问题。kernel 必须针对你的 GPU 架构、CUDA 版本、PyTorch 版本这一精确组合编译。通常正是这一步崩掉（"在我机器上能跑"、缺 `nvcc`、Triton 版本不对）。

[`kernels`](https://github.com/huggingface/kernels) 库把这个构建步骤挪出你的机器。`get_kernel("kernels-community/liger-kernels", version=1)` 从 Hugging Face Hub 下载一个**预构建、版本锁定**的 kernel 包并缓存到本地（这里是 `~/.cache/...kernels-community--liger-kernels`）。好处是：

- kernel 在 CI 中针对多种架构与版本组合编译一次。你下载合适的二进制，而不是自己编译。
- `version=1` 锁定精确构建，每个人跑你的脚本拿到的都是同一个 kernel。不存在"更新某个包之后变慢了"。
- 包暴露一个 `.layers` 属性，内含可即插即用的 `nn.Module`（如 `LigerGEGLUMLP`）。把你的模块换成它的，模型其他部分不用动。

### 为什么调优过的 kernel 更好

我们说"调优"，指两个具体的东西，而且都能在 trace 里看到。

| [![Compiled MLP trace with the TorchDynamo, prologue and guard pre-ops boxed on the CPU lane before the compiled graph runs](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/compile-preops.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/compile-preops.png) |
| --- |
| 图 13：编译运行在任何 GEMM 之前要付出 pre-ops 成本（Dynamo、guards、prologue） |

| [![LigerGEGLUMLP trace with an empty box where the compile pre-ops would be, showing the hand-written kernel has no Dynamo or guard overhead](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/no-preops.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/torch-mlp-fusion/no-preops.png) |
| --- |
| 图 14：Liger kernel 没有 pre-ops——本该有它们的那个框是空的 |

- **融合是写死的。** [`LigerGEGLUMLP`](https://huggingface.co/kernels/kernels-community/liger-kernels/blob/v1/build/torch-cuda/layers.py#L307) 的 forward 是 `down_proj(LigerGELUMulFunction.apply(gate_proj(x), up_proj(x)))`。[`LigerGELUMulFunction`](https://huggingface.co/kernels/kernels-community/liger-kernels/blob/v1/build/torch-cuda/geglu.py#L130) 只跑一个 Triton kernel——[`_geglu_tanh_forward_kernel`](https://huggingface.co/kernels/kernels-community/liger-kernels/blob/v1/build/torch-cuda/geglu.py#L97)——一次遍历就算出 `gelu(gate) * up`。这正是我们从 `torch.compile` 看到的效果：中间量不再往返 HBM。而这里**不依赖编译器**就能拿到，见图 13 与图 14（没有 Dynamo guards、没有编译延迟、没有重编译风险）。
- **启动参数是为硬件挑的。** kernel 不会瞎猜 block size。Liger 的 [`calculate_settings`](https://huggingface.co/kernels/kernels-community/liger-kernels/blob/v1/build/torch-cuda/geglu.py#L95) 依据列数来选。

这里的权衡值得坦诚，因为裸数字会误导人。Liger kernel 用时 **92.8 µs**，而 compile 运行中 Inductor 的融合 kernel 是 **89.4 µs**。乍看手写的还略慢，但这个比较掩盖了让它物有所值的成本。

`torch.compile` 是针对**静态形状**特化的。Inductor 那个 `89.4 µs` 的 kernel 之所以快，恰恰因为它是为*这一个确切的* `[8192, 3072]` 问题生成的。换个 batch size、seq 长度或 hidden 维度，Dynamo 就得重新追踪，你重新付出编译成本换来一个新的特化 kernel。

所以真正的选择不是"慢的手写 kernel vs 快的编译 kernel"，而是**一个快的通用 kernel vs 一个为某个特定输入形状特化的 kernel**。Liger kernel 用一组启动参数为*任意*形状服务，无需重编译。它放弃了按形状特化可能换来的最后几微秒，换来了对形状变化的鲁棒性。

## 结论

下表汇总了每一步在 GPU 上改变了什么、什么保持原样。

| 设置 | 改变了什么 | 什么没变 |
| --- | --- | --- |
| Eager `nn.Linear` | 基线：偏置加法本来就被折叠进 GEMM epilogue（`addmm`），所以是*一个* cuBLAS kernel，而不是 matmul 加 add | — |
| Compiled `nn.Linear` | 一些 CPU 调度算子（`aten::t` 视图记账）消失 | 同一个 cuBLAS GEMM kernel，逐字节一致。Compile 无事可融 |
| Eager MLP | 5 个 GPU kernel：3 个 GEMM + GeLU + mul。`[8192, 3072]` 中间量完整往返一次 HBM | 每个 GEMM 仍是与独立 linear 相同的无 bias cuBLAS kernel |
| Compiled MLP | GeLU + mul + reshape 塌缩为**一个**融合 Triton kernel；中间量留在寄存器。代价是 compile pre-ops（Dynamo、guards） | 3 个 GEMM 原封不动，cuBLAS kernel 名一致 |
| Liger MLP | 同样的融合，但烘焙进人工调优启动参数的 Triton kernel，**没有** Dynamo、guards 或编译延迟 | 3 个 GEMM 仍是同样的 cuBLAS kernel |

如果要带走一个习惯，那就是我们在每次看 trace 前练习的那个：**先猜，再看。** 说出你预期 trace 里会有什么，打开它，把任何不一致当作屏幕上最有意思的东西。
