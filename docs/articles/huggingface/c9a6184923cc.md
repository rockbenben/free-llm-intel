Reflection 的 Beam 已经在 Hugging Face 上发布！它是 Reflection 这家新成立的美国实验室的首个模型，而且是开放的！它是一个 501B 参数的 mixture-of-experts（MoEs）模型（每个 token 激活 23B），支持文本作为输入，拥有 **1M token 的上下文窗口**，并以 Apache 2.0 许可证发布。

Beam 专注于 *编码* 和 *智能体* 用例。它面向这样的团队：想要在自己的硬件、基础设施或云上跑一个前沿规模的模型，并且想按自己的用例对它做定制。Beam 自带一个专属的开源 Rust 实现 harness（执行框架），能把这个模型的性能发挥到最好。

Beam 有原生的 transformers 实现，vLLM 和 SGLang 这样的下游库同样支持。我们与 Reflection 团队合作，为你带来了推理、SFT（有监督微调）和 RL（强化学习）的配方（recipe），方便你基于这个模型按自己的需求去构建。除了 transformers、SGLang 和 vLLM 的 day-0 支持，这篇文章还会告诉你如何运行它、如何对它做后训练，以及我们用它做了些什么。

**太长不看**

> 501B 参数的 MoEs LLM，每个 token 激活 23B。52 层，每个 MoE 层 256 个专家，每个 token 路由到 8 个。
> 文本进、文本出，上下文窗口 1M token。
> Checkpoint 格式：BF16、FP8 和 NVFP4
> 推理过程可以跨轮次留在上下文里（preserve_thinking），并配有专用语法的工具调用。该模型支持五个 reasoning 取值："low"、"medium"（默认）、"high"、"xhigh" 和 "max"。
> tokenizer 内置 response template（响应模板）。
> 带 DFlash2 的投机解码 drafter 模型。
> day-0 支持的库：transformers、SGLang、vLLM。用 Miles 做全参数 RL。
> 自带一个基于 Rust 的定制 harness。
> Apache 2.0。

## Beam 是什么？

Beam 是一个纯文本模型，为长上下文（1M 上下文长度）推理与智能体工作而打造。它是一个稀疏 MoE 模型，每个 token 只由网络的一小部分来计算，因此它能以一个远小得多的模型的速度运行，同时保有大模型的容量。

### 注意力

解码器有 52 层，hidden size 为 5,120。多数层使用滑动窗口注意力，只看之前的 512 个 token；每第六层以及最后一层则关注完整上下文。这样得到 43 个滑动窗口层和 9 个全局层。

*注意力块内部（两种层都是如此）*

两类层对位置的处理方式不同。滑动窗口层使用 RoPE，因为在很短的窗口内相对位置最重要。**全局层不使用任何位置编码**。取而代之的是，每个 query 会乘上一个随可见 token 数量缓慢增长的缩放系数，`(1 + (pos + 1) / 2048) ** 0.1`。它起到温度的作用：上下文变长时 softmax 仍保持其精度，而不会变得平坦。实现中把这称为 scalable-softmax query scaling。

注意力使用分组查询注意力，48 个 query 头和 8 个 key-value 头，query 与 key 上做 RMSNorm。一个由层输入计算得到的可学习 sigmoid 门控，会在输出投影之前对每个头的每个通道做缩放。

### Mixture of Experts

前 3 层使用稠密的 SwiGLU MLP。其余 49 层把它换成一个由 256 个专家组成的 Mixture-of-Experts 块，每个专家是一个 intermediate size 为 2,560 的 SwiGLU MLP，约 39M 参数。专家占据了模型 98.4% 的参数。

router 沿用 DeepSeek-V3 的分组受限方案。它用 sigmoid 对全部 256 个专家打分，把它们分成 8 组、每组 32 个，保留最好的 4 组（按每组前两个得分之和排名），然后在这些组内选出得分最高的 8 个专家。Beam 使用的分组大小与 DeepSeek-V3 相同，但没有共享专家。专家输出用归一化后的 router 权重组合，并乘以 2.5 缩放。

每个 token 只运行 8 个专家，所以模型每个 token 大约用 23B 参数计算。全部 256 个专家都要留在内存里，因此部署需要 501B 模型的内存，却跑出了 23B 模型的速度。BF16 checkpoint 以 safetensors 格式约 1 TB。NVFP4 checkpoint 把大部分参数以 4-bit 精度存放，面向 NVIDIA Blackwell GPU，部分参数为保精度仍保留 BF16。Hub 上还有 FP8 checkpoint，适合 Hopper 和 Ampere 系列芯片。

如果你想自己部署 Beam，可以看看下面的 vLLM 或 SGLang 配方。

### 残差流

残差连接是它最有特色的部分。标准 transformer 把每个子层的输出以权重 1 加到残差流上，所以这个流会随深度增长。

Beam 把输入 embedding 算作第 1 步。在第 `k` 步，它以 `1/sqrt(k)` 的权重加上子层输出，并以 `sqrt((k-1)/k)` 的权重保留已有的流。两个权重的平方和为 1，所以从第一层到最后一层，这个流始终保持恒定的尺度。在全部 104 次相加之后，每个子层的输出和输入 embedding 在最终 hidden state 中携带的权重相同。

每个子层前后也都做了归一化，最终 logits 要经过一个 ±30 的 tanh softcap，以 FP32 计算。实现固定了哪些地方用 FP32 计算：router、SwiGLU 的乘积、各个 norm、RoPE、query 缩放以及 softcap。

### 长上下文

混合注意力很适合长上下文。每层每个 token 缓存 2 x 8 个 KV 头 x 128 维 = 2,048 个值。如果 52 层都保留每一个 token，缓存会按每个 token 208 KiB 增长。只有 9 个全局层保留整个序列。43 个滑动窗口层各自只保留固定的 512 token 窗口，不再增长。于是缓存按每个 token 36 KiB 增长，大约是朴素速率的六分之一。

| 上下文 | 若 52 层全部是全局层 | Beam |
| --- | --- | --- |
| 32K token | 6.5 GiB | 1.2 GiB |
| 128K token | 26 GiB | 4.6 GiB |
| 完整上下文（1M） | 208 GiB | **36.08 GiB** |

这些数字是每条序列、BF16 精度下、使用 transformers 动态缓存得到的。

## 硬件需求

最实用的部署方式是服务 NVFP4 checkpoint，它保留了 BF16 checkpoint 的大部分质量。NVFP4 把部分权重存成 4 bit，这样一来，501B 参数在 BF16 下的 1 TB 就缩小到约 280 GB。Blackwell GPU 原生运行 NVFP4，但比 Blackwell 更早的 GPU（比如 H200）不支持。FP8 checkpoint 适合比 Blackwell 更早的 GPU。

一张 B200 有 180 GB HBM3e，所以两张（360 GB）就能装下 Beam 的权重，但留给激活值和 KV cache 的空间很少。请按四张 B200（720 GB）来规划，这会为长上下文和并发请求留下充足空间。你也可以在一整个 8xB200 节点上部署，或者用两张各 288 GB 的 B300，甚至 8xRTX Pro 6000。如果你没有 Blackwell 硬件，可以用 Inference Providers（serverless）来测试 Reflection。

## 推理支持

Beam 在 transformers、SGLang 和 vLLM 上都有 day-0 支持。

### Transformers

安装最新版本的 transformers。

```
pip install -U "transformers>=5.20.1"
```

运行 Beam 最简单的方式是文本生成 pipeline：

```
from transformers import pipeline

pipe = pipeline(
    "text-generation", model="reflection/Beam-1.0-501B-A23B", device_map="auto"
)

messages = [
    {"role": "user", "content": "Write a limerick about Python exceptions."}
]
output = pipe(messages, max_new_tokens=2000)
output[0]["generated_text"][-1]
```

pipeline 会返回整段对话。最后一条消息就是 Beam 的回复，已经由 response template 解析过了。

再往下走一层，使用 `AutoModelForCausalLM` 和 `AutoTokenizer`。

```
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "reflection/Beam-1.0-501B-A23B"
tokenizer = AutoTokenizer.from_pretrained(model_id)

model = AutoModelForCausalLM.from_pretrained(
    model_id, dtype="auto", device_map="auto"
)
```

#### 聊天

```
messages = [
    {"role": "system", "content": "You should only answer with a number."},
    {"role": "user", "content": "What is 17 * 23?"},
]

inputs = tokenizer.apply_chat_template(
    messages,
    add_generation_prompt=True,
    tokenize=True,
    return_dict=True,
    return_tensors="pt",
    reasoning_effort="medium" # by default
).to(model.device)

input_len = inputs["input_ids"].shape[-1]

outputs = model.generate(**inputs, max_new_tokens=2000)

tokenizer.parse_response(
    outputs[0][input_len:], prefix=inputs["input_ids"][0]
)
```

Beam 的 tokenizer 携带了一份 response template。`parse_response` 会读取它，把原始输出变成一个 message dict，其中推理、回答以及任何工具调用分别放在独立的字段里。这样就免掉了平时用来把推理、回答和工具调用拆开的正则表达式。而且这些规则随 tokenizer 一起发布，所以解析出的结构与 Beam 训练时要产出的格式一致。聊天模板可能会预先写出助手轮次的一部分，而解析器需要看到这部分内容。

#### 工具调用

完整的工具调用示例

```
def get_weather(city: str, unit: str = "celsius"):
    """
    Get the current weather for a city.

    Args:
        city: The city to look up.
        unit: Temperature unit, "celsius" or "fahrenheit".
    """
    ...

tools = [get_weather]
messages = [
    {"role": "user", "content": "I land in Paris tonight. Do I need a coat?"}
]

inputs = tokenizer.apply_chat_template(
    messages,
    tools=tools,
    add_generation_prompt=True,
    tokenize=True,
    return_dict=True,
    return_tensors="pt",
).to(model.device)

input_len = inputs["input_ids"].shape[-1]
outputs = model.generate(**inputs, max_new_tokens=1000)

message = tokenizer.parse_response(
    outputs[0][input_len:], prefix=inputs["input_ids"][0], tools=tools
)
message.get("tool_calls")
```

`tools` 也要一并传给 `parse_response`。Beam 会用它自己的 XML 风格语法把工具调用参数内联写出来，所以一个光秃秃的 `7` 既可能是数字也可能是字符串。有了 tool schema，解析器就能把每个参数转换成它声明的类型。

#### 多 GPU 与多节点

Beam 的 config 定义了一个专家并行方案。专家并行把每个专家放到一个设备上；注意力、稠密层、embedding 和 LM head 则在每个设备上都有副本。这部分是 8B 参数，即 BF16 下 16 GB。用 `DistributedConfig` 加载模型：

```
import os

from transformers import AutoModelForCausalLM
from transformers.distributed import DistributedConfig

model = AutoModelForCausalLM.from_pretrained(
    "reflection/Beam-1.0-501B-A23B",
    distributed_config=DistributedConfig(
        tp_size=int(os.environ["WORLD_SIZE"]), ep_size=int(os.environ["WORLD_SIZE"]), tp_plan={}
    ),
)
```

用 `torchrun` 跨 16 张 H200 GPU 启动脚本。这样每张卡持有 78 GB 权重。若只有 8 张卡，每张就要持有 139 GB，在 141 GB 的 H200 上留不出余地。设备数量必须能整除专家数量，也就是 256。

### vLLM

Beam 在 vLLM 中有 day-0 支持。下面的命令以张量并行跨 16 张 GPU（两个 8x H200 节点）服务 BF16 checkpoint，并暴露一个 OpenAI 兼容的 API：

```
vllm serve reflection/Beam-1.0-501B-A23B --tensor-parallel-size 16 --served-model-name beam
```

想要更快的生成，可以加上 DFlash2 投机解码。一个小的 drafter 模型最多提前提议 15 个 token，而 Beam 在一次前向传播中把它们全部校验，因此每一步可以接受多个 token。代价是为 drafter 多占一点显存：

```
vllm serve reflection/Beam-1.0-501B-A23B \
  --tensor-parallel-size 16 \
  --speculative-config '{ "method": "dflash", "model": "reflection/dflash2-drafter-preview", "num_speculative_tokens": 15 }'
```

两条命令都会启动一个 OpenAI 兼容的服务端，所以你可以把任何 OpenAI 客户端指向 `http://localhost:8000/v1`。更多服务配置，见[为 vLLM 提交的 Beam 配方](https://github.com/vllm-project/recipes/pull/1132)。

### SGLang

Beam 在 SGLang 中同样有 day-0 支持。我们推荐配合 DFlash2 投机解码来服务它，下面两条命令都已开启。在 Blackwell 上，NVFP4 checkpoint 可以放进 4 张 B300：

```
python -m sglang.launch_server \
--model-path reflection/Beam-1.0-501B-A23B-NVFP4 \
--served-model-name beam \
--tp 4 \
--attention-backend trtllm_mha \
--page-size 64 \
--context-length 1048576 \
--mem-fraction-static 0.85 \
--enable-unified-memory \
--speculative-algorithm DFLASH \
--speculative-draft-model-path reflection/Beam-1.0-501B-A23B-DFlash2 \
--speculative-dflash-block-size 8 \
--tool-call-parser beam --reasoning-parser beam \
--host 0.0.0.0 --port 30000
```

在 Hopper GPU 上，改用 8 张 H200 来跑 FP8 checkpoint。只有三个 flag 会变：checkpoint、张量并行大小（8 而不是 4），以及注意力后端（fa3 而不是 trtllm_mha，后者需要 Blackwell）：

```
python -m sglang.launch_server \
--model-path reflection/Beam-1.0-501B-A23B-FP8 \
--served-model-name beam \
--tp 8 \
--attention-backend fa3 \
--page-size 64 \
--context-length 1048576 \
--mem-fraction-static 0.85 \
--enable-unified-memory \
--speculative-algorithm DFLASH \
--speculative-draft-model-path reflection/Beam-1.0-501B-A23B-DFlash2 \
--speculative-dflash-block-size 8 \
--tool-call-parser beam --reasoning-parser beam \
--host 0.0.0.0 --port 30000
```

## 后训练 Beam

你可以为自家用例微调 Beam。这里我们分享 TRL 和 Miles 中的一些例子，帮你入门有监督微调与强化学习。

### 用 TRL 做 SFT

把 Beam 适配到你自己的数据上，最快的方式是用 TRL 的 SFTTrainer 做有监督微调。为了把显存控制在可管理的范围内，我们用 PEFT 训练 LoRA adapter，而不是更新全部 501B 参数：我们用 TRL 的 `SFTTrainer` 让 Beam 朝一个简单的目标做适配——用用户请求的语言来推理。我们在 [Multilingual-Thinking](https://huggingface.co/datasets/HuggingFaceH4/Multilingual-Thinking) 上用 LoRA 做了微调，它只训练一小部分 adapter 权重，同时把基座模型冻结。

这套配置把加载时的模型分片、专家并行、FlashAttention 4 和序列打包结合在了一起。LoRA SFT 能放进单台 8 张 B300 GPU 的节点，达到约每秒 19,000 token。对应的 H100 配置需要四个节点。

在 Multilingual-Thinking 上训练完一个 epoch 之后，Beam 在 16 个留出的提示词中有 16 个用所要求的语言进行推理，而基座模型只有 3 个。这个小规模评测衡量的是语言遵循度，而不是推理本身是否正确。

*训练损失（左）与平均 token 准确率（右），来自另一次在 open-r1/Mixture-of-Thought 的推理子集上用一台 8 GPU 的 B300 节点跑的 500 步运行。这些训练指标出自官方的 [TRL 示例 PR](https://github.com/huggingface/trl/pull/7629)。*

### 用 Miles 做 GRPO

Reflection 和 RadixArk 做了一套配方，用 Miles 以 BF16 通过 GRPO 训练这个模型。你可以更新整个模型，也可以用 LoRA 训练 adapter 同时冻结基座权重。Megatron 负责训练，SGLang 生成 rollout，Miles 在每次更新之后把新权重发布给各个 rollout 引擎。我们审阅了这套配方。

| 工作负载 | 参考配置 |
| --- | --- |
| 推理 / 评测，BF16 | 每个引擎 16x H200 |
| 全参数 GRPO，BF16（Miles） | 96x H200：64 训练，32 rollout。或者 64x H200 共置。 |
| LoRA GRPO，BF16（Miles） | 32x H200：16 训练，16 rollout。 |
| 全参数 GRPO，BF16，128-token 上下文（Miles） | 48x H200：32 训练，16 rollout。这是 Reflection 和 RadixArk 最初在真实 checkpoint 上验证过的配置。 |

这套配方在 DAPO-Math-17K 上运行 GRPO，并在 AIME25 上评测。构建镜像、下载数据，然后把作业提交给一个由十二台 8x H200 节点组成的 Ray 集群：

```
docker build -f docker/Dockerfile.beam -t miles-beam .

python scripts/run_beam.py prepare \
  --model-id reflection/Beam-1.0-501B-A23B \
  --model-dir /root/models/Beam \
  --data-dir /data/datasets

export MASTER_ADDR=10.0.0.1
export RAY_ADDRESS=http://${MASTER_ADDR}:8265

python scripts/run_beam.py execute \
  --model-dir /root/models/Beam \
  --data-dir /data/datasets \
  --output-dir /root/shared_data/beam-run \
  --num-rollout 100
```

一次 rollout 里发生了什么：

**采样：** 32 个提示词传给模型，每个生成 8 个响应。两个 SGLang 引擎各用 16 张 GPU 来服务这些 rollout。

**打分：** 把 boxed 答案与标签核对，并对接近长度上限的响应施加软性惩罚。

**更新：** 对全部 256 个样本走一次优化器步。组相对优势配合截断重要性采样，没有 KL 也没有熵惩罚。

**并行训练：** 张量并行 8，专家并行 8，数据并行 8，并带序列并行与全量重算。

**优化器：** Adam，学习率恒定为 1e-6。梯度用 BF16，主权重用 FP32，动量用 BF16。优化器状态经由节点本地 NVMe 流式读写，所以每个训练节点需要 2 TB 暂存空间。

**评测：** 每五次 rollout 做一次 AIME25，每题八个采样。每二十次保存一个 checkpoint。

下一次 rollout 在当前这次训练进行的同时生成，因此响应总是落后一次更新。加上 `--resume` 可以从最后一个 checkpoint 继续。`execute-colocate` 在八台节点上运行同一套配方，每张 GPU 轮流训练与提供服务。

### 用 LoRA 训练

你也可以在四台 8× H200 节点上用 LoRA 跑 GRPO：16 张 GPU 用于训练，16 张用于 rollout。这套配方在 Beam 的注意力、稠密 MLP 和专家层上训练 rank-16 的 adapter，同时保持基座权重冻结。只有 adapter 权重会与 SGLang 同步，而优化器状态留在 GPU 显存里，从而省掉了把优化器状态卸载到 NVMe 的需要。

```
python scripts/run_beam_lora.py execute \
  --model-dir /root/models/Beam \
  --data-dir /data/datasets \
  --output-dir /root/shared_data/beam-run \
  --num-rollout 100
```

## 用 Beam 构建：Demos

如果你用 Beam 做出了什么东西，就把它分享在 Hub 上，即有机会赢得 $10,000。你要做的只是建好一个 space、model 或 dataset 仓库，并在[模型仓库页面](https://huggingface.co/reflection/Beam-1.0-501B-A23B/discussions/5)上分享它。为了给你一点灵感，这里是我们做出的几个东西。

### 嘿 Beam，构建一个原生本地 MacOS 应用！

在 Hugging Face 我们喜欢能原生跑在自己硬件上的开放本地模型，但在 Mac 上构建原生应用可能很难！我们来看看 Beam 能不能帮上忙。

我们请 Beam 构建一个把语音转成文字、并顺手把它送到你光标处的 MacOS 原生应用。我们想用 MLX 把我们 Mac 上 Metal 的性能榨到极致，并用 Parakeet Model 获得出色的语音转文字效果。

```
Build BeamSpeak, a native macOS menu bar dictation app with a compact recording pill and no main window or account.

Use ⌘⇧Space to start and stop microphone recording, showing elapsed time, microphone level, and transcription status. Run speech recognition entirely locally using a Hugging Face model, preferably Parakeet v3 through MLX, and keep the model loaded between recordings. Paste the transcript into the original app if it remains focused and Accessibility permission is granted; otherwise copy it to the clipboard, preserving newer clipboard changes and never pressing Enter. Handle permissions, cancellation, silence, errors, a two-minute recording limit, and temporary audio cleanup. Deliver source code, a runnable BeamSpeak.app, setup instructions, and verification of offline transcription, the physical shortcut, microphone capture, and text delivery.
```

我们用了 Beam 加 Pi coding harness 来构建最初的这个原生 macOS 菜单栏应用，用 MLX 跑 Parakeet。保存下来的运行记录里包含后续的提示词；最终源码还包含了之后的 Codex 修复。上面那条提示词是构建需求的一份精简版本。

你可以查看 Beam 在 pi 里如何构建这个项目的[智能体轨迹](https://huggingface.co/buckets/burtenshaw/beamspeak-demo/tree/trace/beam-build.sanitized.jsonl)。如果你想试试这个 demo，可以下载[源码](https://huggingface.co/buckets/burtenshaw/beamspeak-demo/resolve/beamspeak-source.zip)或阅读[运行说明](https://huggingface.co/buckets/burtenshaw/beamspeak-demo/resolve/RUNNING.md)。

### 嘿 Beam，如何在多个智能体上扩展？

我们想看看 Beam 能否把一项编程任务拆给多个智能体从而更快推进。我们把 Beam 与开源的 Pi coding agent 配对，并比较了三种配置：1. 一个智能体独自工作，2. 五个常驻同伴通过一个共享的 Git 仓库协作，3. 一个 lead 智能体把工作委派给异步的子智能体。harness 跑在 Hugging Face jobs 上，推理通过 Reflection 的平台 API。

任务方面我们用了 ProgramBench：智能体必须从编译好的可执行文件和文档还原出一个程序，而不能看到它的源码或评测器的测试。每种配置在每个任务上都有同样的 8M API-token 上限和两小时求解时限，由其全部智能体共享。我们保存了实现快照，并用 [ProgramBench-Tests 数据集](https://huggingface.co/datasets/programbench/ProgramBench-Tests) 中固定的隐藏测试套件来评测它们。

我们的[得分与延迟图](https://burtenshaw-beam-pi-programbench.hf.space/study)展示的是通过的测试的平均比例。时间轴用的是模型 token 的固定参考速率加上实测的工具时间，而不是实际流逝的墙钟时间。我们最初跑了五个任务。当前图表展示的是事后选取的子集：jq、xsv、FIGlet 和 hexyl；ripgrep 在三种配置中都被排除，因为给它保存下来的产物评分太慢。公开的结果保留了全部 15 个原始 episode。

你可以在 [Trackio 仪表盘](https://burtenshaw-beam-pi-programbench.hf.space/?project=beam-pi-programbench-20261009)里查看这些运行，浏览[公开的结果数据](https://huggingface.co/spaces/burtenshaw/beam-pi-programbench/tree/main/results/beam-pi-programbench-20261009)，并复用[这套 study harness](https://huggingface.co/spaces/burtenshaw/beam-pi-programbench/tree/main/source)。

### 嘿 Beam，为我的代码库微调一个决策模型！

决策模型此刻正流行，因为它们超级快，而且对许多用例都很实用。我们先在 Pi 里用 Beam，等 Beam 的额度用完之后，转而训练并评测一个面向开发者事故分诊的定制决策模型。

我们想看看一个编码智能体能否把一份事故分诊策略变成一个小而快的决策模型。任务是读懂一起开发者事故，选出负责的团队、它的严重程度，以及是否需要立刻呼叫某人。借助 Unsloth，我们微调了 Qwen3.5-0.8B 来直接给这些选择打分。

首先，这套工作流构建了一个包含 2.3k 起事故的合成数据集，按事故聚类划分为训练、校准和测试。我们训练了一个 LoRA adapter 和一个决策头，跑三个 epoch，主干用 4-bit 量化，在 Science Slurm 集群的一台 H100 80GB 上完成。

作为基线，我们把完整的分诊策略和工单一起提示未做适配的模型、不给任何示例，让它把这三个决策生成为 JSON。在同一批 320 个合成测试工单上，微调后的决策模型三项全对的比例为 76.25%，而提示式 zero-shot 只有 4.69%。单个工单的平均延迟从 1,218.06 ms 降到 102.58 ms，即 11.9× 的提速。

如果你想自己试这个实验，可以看看这个[产物 bucket](https://huggingface.co/buckets/burtenshaw/qwen35-incident-triage-reproduction)，里面包含数据、代码、checkpoint 和结果。
