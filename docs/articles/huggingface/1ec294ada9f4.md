# Foundry Managed Compute 上的 Hugging Face 模型

在 Microsoft Build 2026 上，我们发布了 **Foundry Managed Compute** 和 **Foundry 上的 Hugging Face 模型**——一个精选的开放权重模型目录，来自 Hugging Face 生态、每周更新，可一键部署到 Foundry Managed Compute。模型权重预置在 Azure 中，运行时由 Microsoft 构建并扫描，Collection 中的每个模型都享有与 Foundry 上其他模型相同的企业级安全、治理、可观测性与计费。

## 平台：Microsoft Foundry 与 Managed Compute

Microsoft Foundry 是构建和运行智能体（agentic）AI 应用的平台。Foundry 始于任何云上最宽的模型选择——来自 Microsoft、OpenAI、Anthropic、Meta、Mistral、DeepSeek、Hugging Face 等的模型，横跨前沿模型、开源模型和自定义权重——全部通过单一端点和同一套 Python、C#、JavaScript、Java SDK 访问。

在这些模型之上是 **Foundry Agent Service**：多智能体编排、内置记忆、通过 Foundry IQ 的知识锚定（grounding），以及通过 agentic 协议接入的工具目录，让智能体能处理企业数据。智能体跑起来之后，Foundry 提供端到端追踪、实时监控、持续评估，还有一个根据评估结果改进智能体行为的提示词优化器——可观测性与质量闭环是平台的一部分。

除此之外，开发者还能获得：

- 内容安全过滤器
- 任务遵循护栏（task-adherence guardrails）
- 用于对抗性测试的 AI Red Teaming Agent
- 统一 RBAC
- 私有网络
- 平台内直接集成 Azure Policy

除了按 token 计费（上手摩擦最低的路径）和预配吞吐量（前沿模型上可预测、高性能的生产负载）之外，**Foundry Managed Compute** 是 Foundry 的第三种部署选项：面向开源与自定义模型的托管 GPU 平台即服务（PaaS）。

你按工作负载真正关心的维度来描述要部署的模型实例——参数量、上下文长度、想优化延迟还是吞吐量——Foundry 在底层处理 GPU 拓扑，不管实例落在单块加速卡还是多块上，让你完全以模型为单位思考和规划。

机器的事交给 Microsoft：在受支持的运行时——**vLLM、SGLang、TensorRT-LLM、NIM、TEI、llama.cpp**——上，容器更新、运行时升级和安全补丁自动完成，无需重新部署模型；而模型配置、部署行为和路由仍由你掌握。

这种一致性贯穿整个开发者体验——按 token 计费、预配吞吐量和 Managed Compute 共享：

- 单一端点
- 相同的 SDK
- 相同的认证
- 相同的可观测性
- 一张账单

开源模型接入 Foundry Agents 的方式与前沿模型完全相同，你可以在单个智能体里混用不同类型的模型，不需要单独的集成路径。

Managed Compute 提供：

- **全局部署（Global deployments）**——最广的容量、最优的价格
- **数据区部署（Data Zone deployments）**——数据驻留与主权

同样的代码，同样的工作流。配额按加速卡家族对齐，今天在 H100 家族上做的规划，会随着新硬件世代上线而自然延续。

## 为什么是 Hugging Face

Hugging Face 是开放 AI 的公共广场：**1500 万构建者、40 万个组织、超过 300 万个已发布的开放模型**，智能体编程、视频分割、语音、嵌入等前沿能力每周都在涌现。它是开放模型界的 GitHub——社区在这里发布权重、撰写模型卡、对比评测、拉取模型做实验。

开放模型已在一个又一个基准上追平专有模型，还解锁了专有端点做不到的事：

- **最先进水平如今是开放的。** 领先的开放权重模型在最常用基准上已足以与顶级封闭前沿模型竞争。
- **深度定制。** 完整权重让微调、蒸馏、量化、LoRA 适配成为可能——把模型调到贴合你的领域、你的数据，以及你的延迟和成本目标。
- **你的模型，你做东。** 权重运行在你租户内、你控制的基础设施上，在你自己的推理端点、身份体系和网络边界之后。
- **成本塑形。** 按小时付费加速卡、空闲时缩到零、为具体模型匹配 GPU 规格——对于按 token 定价难以预测的稳定、大流量或延迟敏感型负载很实用。
- **版本控制。** 锁定具体模型版本，评估它、部署它，按自己的发布节奏前进或回滚。

难点一直都在运营层：发现、许可证审查、安全筛查、运行时选型、GPU 定容、镜像构建、CVE 补丁，以及把模型架进企业级端点之后。仅靠 Hugging Face 本身并不是一个企业级服务平台。**Foundry 上的 Hugging Face 模型，就是由 Microsoft 来运营的这一层。**

## Foundry 上的 Hugging Face 模型

Hugging Face Collection 把一批精选模型直接带进 Foundry Model Catalog：

- **每周更新**——随着社区不断发布，Hugging Face 生态的热门模型持续加入。
- **覆盖所有模态**——文本、视觉、音频与多模态：用于聊天和智能体的 LLM/VLM、ASR 与语音翻译、嵌入、分割、图像生成。
- **仅 Safetensors、不运行不可信代码**——Collection 中每个模型都经过安全筛查，以 SafeTensors 权重格式发布，除非经过严格评审，否则没有 `trust_remote_code` 执行路径。
- **为模型选对运行时**——LLM 用 vLLM 和 SGLang，适用之处用 TensorRT-LLM 和 NIM，嵌入用 TEI，CPU 用 llama.cpp——Foundry 为模型匹配对应引擎。

从你的角度看，Hugging Face Collection 里的开放权重模型与 Foundry Model Catalog 中的其他模型看起来、用起来一模一样，而 Collection 里的每个模型在现身目录之前，都已通过一套多阶段发布流水线。

### 整编流水线

Hugging Face 与 Microsoft 协作，通过系统化的整编流程，把 Hugging Face 生态中最受欢迎的开放权重模型带到 Microsoft Foundry——面向企业环境、生产可用：

- **识别生态中的热门模型**——基于社区信号、合作伙伴请求和客户需求，挑选具备企业就绪条件的候选。
- **合规与安全筛查**——按 Microsoft 企业分发政策审查模型许可证（许可证元数据会被捕获并保留在目录模型卡上），并检查仓库中的 `trust_remote_code` 模式和自定义可执行代码；凡在加载时需要执行第三方 Python 的模型，要么整改、要么排除。
- **构建、扫描并发布运行时**——Microsoft 在受支持运行时（vLLM、SGLang、TensorRT-LLM、NIM、TEI、llama.cpp）上构建推理容器镜像，做 CVE 扫描，签名后发布到 Microsoft 托管的容器注册表。
- **把权重上传到安全的 Azure 存储**——模型权重从 Hugging Face 一次性拉取，对照已发布的模型卡做校验，然后存入提供该模型区域中 Microsoft 托管的 Azure 存储。
- **验证并发布到目录**——每个"模型 + 运行时 + 加速卡"组合都要通过 API 一致性（chat completions、embeddings、rerank 等）与性能（延迟、吞吐量、首 token 时间、token 间解码时间）测试，随后这个已验证的模型（连同其模板、运行时镜像和权重）发布到 Foundry Model Catalog，附带一键部署到 Managed Compute 的路径。

因为权重预置在 Azure 存储、运行时镜像位于 Microsoft 托管注册表，你的部署不需要对 Hugging Face Hub 的出站网络访问——你可以在私有网络内部署到生产。

## 模型运行时

Foundry 上的 Hugging Face 模型由一组多元的、社区构建的开源推理运行时驱动——每个运行时都经过挑选和调优以适配 Foundry Managed Compute，并与最擅长的模型架构配对。在所有运行时上，系统化的整编流程意味着新版本和补丁很快到达 Foundry，现有模型部署会自动升级——无需你重新部署。

- **vLLM**——开放大语言模型默认的高吞吐服务引擎，为生产 GPU 负载调优。由于 Hugging Face 是 vLLM 的直接贡献者，Transformers 库中的任何模型都能开箱即用地跑在 vLLM 上——所以当一个新模型登陆 Hugging Face，它当天就能在 Foundry 上提供服务，无需等待定制集成。
- **SGLang**——服务于语言与多模态模型的服务引擎，对结构化输出（JSON、正则、语法约束生成）支持很强，而这正是智能体和工具调用负载所依赖的。Hugging Face 与 SGLang 团队为 SGLang 构建了 Transformers 后端集成，因此 Transformers 库中任何模型都开箱即用地运行在 SGLang 上——模型登陆 Hugging Face 的当天就能到达 Foundry。
- **Text Embeddings Inference (TEI)**——嵌入、重排序和序列分类模型的运行时。针对不同加速卡的专用镜像自带为 Foundry 支持的每类 GPU 和 CPU 编译的内核，让 RAG 与语义搜索负载的嵌入热路径保持精干。
- **llama.cpp**——GGUF 量化模型在 CPU 与小 GPU 上的路径。适合成本优化的部署、较小模型和纯 CPU 区域，拥有与 vLLM、SGLang 相同的 OpenAI 兼容 API。
- **TensorRT-LLM 与 NIM**——用于 NVIDIA 硬件，在 NVIDIA 优化内核与基于 Triton 的服务能带来明显更好延迟或吞吐的特定模型家族上使用。
- **hf-serve**——Hugging Face 自家的多模型推理服务器，用于 LLM 和嵌入快速路径之外的模型架构（视觉、音频、分割及其他 Transformers 原生流水线），让 Collection 能以一致的服务层覆盖所有模态。

## 部署与调用一个开放权重模型

入口是 Foundry Model Catalog 中的 Hugging Face Collection，部署共五步：

- **浏览目录并选择模型**——部署向导同时会显示你用 SDK 或 REST 脚本化部署时所需的模型 id、部署模板 id 和 `acceleratorType`。
- **选择部署模板**——延迟优化还是吞吐优化、加速卡家族、上下文长度、量化方式。
- **配置实例数量**——通过增加模型实例来扩展吞吐量。
- **部署**——从门户、CLI、SDK 或 REST 均可。
- **调用（Score）**——用你已有的 SDK 通过统一的 Foundry 端点访问。

### 部署模板

部署模板就是第二步的选择单元：一个有名字、有版本的资产，固定了运行时、加速卡家族与数量、上下文长度，以及把模型服务好的运行时专属调优——所以选模板就是你对"我想让模型怎么跑"做的唯一调节。

例如 `qwen3-32b` 附带四个模板，部署向导会并排展示：

| 模板 | 运行时 | 加速卡 | 上下文 |
| --- | --- | --- | --- |
| `qwen–qwen3-32b–40k-nvidia-a100` | vLLM | 1 × A100 80 GB | 40K |
| `qwen–qwen3-32b–40k-nvidia-h100` | vLLM | 1 × H100 80 GB | 40K |
| `qwen–qwen3-32b–128k-nvidia-2xa100` | vLLM | 2 × A100 80 GB | 128K |
| `qwen–qwen3-32b–128k-nvidia-2xh100` | vLLM | 2 × H100 80 GB | 128K |

每个模板都针对模型预先调优——运行时设置、工具调用与推理解析器、调用路径、健康探测、请求并发，以及模型特有的上下文扩展设置，全部由 Microsoft 配好，任何取舍都在模板描述中就地说明。当你脚本化部署时，只需引用模板，剩下的交给 Foundry。

### 部署——Python SDK

```
from azure.identity import DefaultAzureCredential
from azure.mgmt.cognitiveservices import CognitiveServicesManagementClient

client = CognitiveServicesManagementClient(DefaultAzureCredential(), SUBSCRIPTION_ID)

deployment = client.managed_compute_deployments.begin_create_or_update(
    resource_group_name=RESOURCE_GROUP,
    account_name=ACCOUNT_NAME,
    deployment_name="qwen3-32b",
    resource={
        "sku": {"name": "GlobalManagedCompute", "capacity": 1},
        "properties": {
            "model": "azureml://registries/azure-huggingface/models/qwen--qwen3-32b/versions/1",
            "deploymentTemplate": "azureml://registries/azure-huggingface/deploymenttemplates/qwen--qwen3-32b--40k-nvidia-h100/labels/latest",
            "acceleratorType": "H100_80GB",
        },
    },
).result()
```

### 调用——OpenAI SDK

部署可通过统一的 Foundry 端点、用 OpenAI SDK 访问——`model` 字段填你刚创建的部署名：

```
from openai import OpenAI

api_key  = client.accounts.list_keys(RESOURCE_GROUP, ACCOUNT_NAME).key1
endpoint = f"https://{ACCOUNT_NAME}.services.ai.azure.com/openai/v1"

openai_client = OpenAI(base_url=endpoint, api_key=api_key)

completion = openai_client.chat.completions.create(
    model=deployment.name,
    messages=[{"role": "user", "content": "What is the capital of France?"}],
)

print(completion.choices[0].message)
```

### 在智能体中使用

Collection 中的 chat-completions 模型可以作为管理员连接的模型直接嵌入 Foundry Agents，并通过统一的 OpenAI SDK 经 Foundry Responses API 调用——同样的认证、同样的端点、同样的可观测性。

## 现在有什么

**现已开放预览：** Microsoft Foundry Model Catalog 中的 Hugging Face Collection——覆盖所有模态的数千个模型，每周更新，可部署到 Foundry Managed Compute，支持 NVIDIA A100、NVIDIA H100 或 AMD MI300X 加速卡，Global 与 Data Zone 两种范围，统一 Foundry 端点之后配有 Playground 支持、一流的 Azure Monitor 指标、按部署的计费标签，以及自动应用到你的部署的精选运行时升级与 CVE 补丁。

**路线图上：** 更广泛地覆盖 Hugging Face 生态、更多加速卡家族，以及 Bring Your Own Weights——微调与专有变体通过同样的模板和治理部署，与 Collection 模型一致。

Hugging Face 是开放模型发布与被发现的地方。Microsoft Foundry 是企业把它们运营起来的地方——在 Azure 托管的、经许可证筛查与安全筛查的精选权重之上；在社区构建、经 CVE 扫描的运行时之上；在单一端点之后，还叠有企业身份、网络、可观测性与智能体集成。开源生态的广度，加上 Microsoft 在底下运营的支撑层。想深入了解 Foundry Managed Compute——定价、加速卡 SKU、数据驻留、企业就绪、可观测性，以及完整的 Responses API + 记忆模式——请看 [Managed Compute 发布博客](https://devblogs.microsoft.com/foundry/announcing-foundry-managed-compute/)。
