大型语言模型（LLM）非常擅长生成文本。我们用它们回答问题、编写代码、对问题做推理，以及做很多别的事。*但并非每个问题都需要生成文本。*

设想一个客服系统收到下面这条消息：

“我的订阅被重复扣费了。我今天需要退款。”

系统需要判断该由哪个团队处理这条请求、紧急程度如何，以及客户是否在要求退款。

我们可以让 LLM 返回一个包含这些答案的 JSON 对象。

```
llama cli -hf ggml-org/gemma-4-e4b-it-GGUF:Q4_0

> We have the following customer support ticket, "I was charged twice for my subscription. I need a refund today.", which team should handle the request, how urgent it is, and whether the customer is requesting a refund. Give the answers in JSON.

[Start thinking]
...
[end thinking]
```json
{
  "team_to_handle": "Billing",
  "urgency": "High",
  "request_refund": true
}
```

但如果模型能直接评估可选项，并返回在这些选项上的概率分布，*而不生成任何文本*呢？

```
from transformers import pipeline

decide = pipeline("decision", model="autotrust/GEV-26B-Decide")
decision = decide(
    {
        "state": "I was charged twice for my order and want a refund.",
        "questions": {
            "department": {
                "type": "choice",
                "instructions": "Which team should handle this?",
                "criteria": {
                    "billing": "Payments and refunds",
                    "technical": "Bugs and technical issues",
                    "sales": "Pricing and subscriptions"
                }
            },
        }
    }
)

# {
#   'department': {
#       'type': 'choice',
#       'choice': 'billing',
#       'confidence': 0.9974000453948975,
#       'probabilities': {
#         'billing': 0.9982666969299316,
#         'technical': 0.0010246571619063616,
#         'sales': 0.0007087149424478412
#       }
#     }
# }
```

这正是**决策模型**背后的核心思路。

## 什么是决策模型？

决策模型接收一段输入上下文（state），用一组预先定义好的候选答案（primitive）来评估一个问题，并返回带概率的结构化决策。我们不让模型逐 token 生成答案，而是让它为应用已经理解的那些答案分配概率。

[![决策模型的 state 与原语](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/decision/decision-models.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/decision/decision-models.png)

[TypeSafe AI 推出了 Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev)，把它描述为一种 [*System One model*](https://en.wikipedia.org/wiki/Thinking,_Fast_and_Slow)。这个名字的灵感来自快速、直觉的思维（System 1）与较慢、审慎的思维（System 2）之间的区分。

> 社区已逐渐统一使用 decision model 这一术语，因为它描述的是模型的计算角色，而不是援引某种特定的认知理论。在本文余下部分，我们把这类模型称为「decision model」而不是「system one model」。（一次在 twitter 上决定该如何称呼这类模型的投票）

对决策模型而言，最基本的接口是：

```
State + Questions + Allowed Answers → Decisions + Probabilities
```

## 为什么不让 LLM 包办一切？

我们大可以直接 prompt LLM，让它返回包含决策结果的 JSON 对象。事实上，许多应用本来就是这样用语言模型来做分类、路由及其他结构化任务的。

不过，这种做法有几个问题。

- LLM 并不保证遵循指定的 schema：即便给出明确指令，模型也可能产出无效 JSON、冒出意料之外的键，或返回不在允许选项内的答案。
- 约束解码有帮助，但并不能消除计算开销：[Outlines](https://github.com/dottxt-ai/outlines) 和 [XGrammar](https://github.com/mlc-ai/xgrammar) 这类库通过限制模型每一步可以生成哪些 token，来强制遵循语法或 JSON schema。这能保证输出符合支持的结构约束，但也带来了额外的工作。
- 何必生成整段回答：LLM 是为开放式生成而设计的，可当应用只需在预定义答案之间做选择时，自回归解码就可能是多余的功。

## 决策模型与分类模型有何不同？

在理解决策模型的接口之前，有必要先回顾两种密切相关的方法：传统分类和零样本分类。

### 传统分类

假设我们训练一个分类器，把客服请求路由到三个部门：

- Billing
- Technical support
- Sales

传统的分类模型学习的是从输入到一组预定义标签的映射。训练时，模型从样本中学习预测这些标签。分类头通常为每个类别输出一个 logit，再由 softmax 把这些 logit 转成概率分布。

这里的局限在于***输出类别被固化进了模型的分类头***。

如果引入第四个部门，比如 Legal，现有分类器并不会自动获得一个对应的输出类别。我们可能得改动分类头、收集训练数据，并**重新训练**或调整模型。

### 零样本分类

[零样本分类](https://huggingface.co/tasks/zero-shot-classification)在一定程度上解决了这个局限。它不要求分类器针对每个输出类别专门训练，而是在推理时提供候选标签。

例如：

```
from transformers import pipeline

classifier = pipeline(
    "zero-shot-classification",
    model="facebook/bart-large-mnli",
)

classifier(
    "My payment was deducted twice.",
    candidate_labels=["billing", "technical support", "sales"],
)

# {'sequence': 'My payment was deducted twice.',
#  'labels': ['billing', 'sales', 'technical support'],
#  'scores': [0.8466812372207642, 0.0962134450674057, 0.05710534751415253]}
```

与固定标签的传统分类器不同，这里的类别可以随请求而变。我们再加一个部门，比如“Legal”，看看模型的输出。

```
from transformers import pipeline

classifier = pipeline(
    "zero-shot-classification",
    model="facebook/bart-large-mnli",
)

classifier(
    "My payment was deducted twice.",
    candidate_labels=["billing", "technical support", "sales", "legal"],
)

# {'sequence': 'My payment was deducted twice.',
#  'labels': ['billing', 'sales', 'technical support', 'legal'],
#  'scores': [0.8185835480690002, 0.09302053600549698, 0.05521026626229286, 0.03318570926785469]}
```

一种常见实现用的是为自然语言推理（NLI）训练的模型。每个候选标签被转成一个假设，模型再衡量输入在多大程度上蕴含该假设。

这听起来已经和决策模型很像了。在很多方面，确实如此。

### 决策模型的不同之处

决策模型把这一思路往前推了一步，不只是把输入归到某个类别。它可以针对同一个 state 接收多个带名字的 question，各自有不同的答案类型。类型可以是在若干备选项中做选择（choice）、在有序量表上打分（score），或估计某个陈述为真的概率（noul）。

更重要的是，它的接口是围绕**可能决策上的概率分布**来设计的。

来看这三种方法：

| 属性 | 分类 | 零样本分类 | 决策模型 |
| --- | --- | --- | --- |
| 选项上的概率 | 是 | 是 | 是 |
| 推理时定义标签 | 否 | 是 | 是 |
| 多个带类型的问题 | 否 | 否 | 是 |
| 有序打分与是/否决策 | 视任务而定 | 经适配可做到 | 原生原语 |

决策模型的优势并不在于它发明了运行时定义标签或概率化分类，而在于把这些能力组织成一套一致的接口，背后还可以由专门针对决策优化过的架构和训练流程来支撑。

## 决策模型的接口

一次决策模型请求包含下面两个组成部分：

- state
- questions

### State

state 是模型要评估的信息。它可以是字符串、结构化的 JSON 对象，或者对受支持的全模态模型而言的其他模态。

例如：

```
{
  "customer_message": "I was charged twice. Please refund me today.",
  "subscription": "pro",
  "previous_tickets": 2
}
```

### Questions 及其原语

questions 描述我们想了解的关于 state 的内容。在决策模型的接口中，三种基本原语代表不同形式的决策：

- **Choice：** 从若干可能答案中选一个。
- **Score：** 在有序量表上评估某事物。
- **Noul：** 以概率方式回答是/否问题。

我们逐个来看。

#### Choice：选项上的概率分布

Choice 是最直观的原语，也最接近传统分类。

假设我们问：

> 该由哪个部门处理这条客户请求？

可选项是 Billing、Technical support 和 Sales。

```
from transformers import pipeline

decide = pipeline("decision", model="autotrust/GEV-26B-Decide")
decision = decide(
    {
        "state": "I was charged twice for my order and want a refund.",
        "questions": {
            "department": {
                "type": "choice",
                "instructions": "Which team should handle this?",
                "criteria": {
                    "billing": "Payments and refunds",
                    "technical": "Bugs and technical issues",
                    "sales": "Pricing and subscriptions"
                }
            },
        }
    }
)

# {
#   'department': {
#     'type': 'choice',
#     'choice': 'billing',
#     'confidence': 0.9974000453948975,
#     'probabilities': {
#       'billing': 0.9982666969299316,
#       'technical': 0.0010246571619063616,
#       'sales': 0.0007087149424478412
#     }
#   }
# }
```

模型为每个选项分配一个 logit。对于各 logit（$z_1,\ldots,z_K$，共 K 个类别），可以用 softmax 求出概率：

pi=exp⁡(zi/T)∑j=1Kexp⁡(zj) p_i=\frac{\exp(z_i/T)}{\sum_{j=1}^{K}\exp(z_j)}

这里，(K) 是选项的数量。

看这个示意性的分布：

| 选项 | 概率 |
| --- | --- |
| Billing | 0.998 |
| Technical support | 0.001 |
| Sales | 0.001 |

这些概率之和为 1：

∑i=1Kpi=1. \sum_{i=1}^{K}p_i=1.

模型选择概率最大的那个选项：

y^=arg⁡max⁡ipi \hat y=\arg\max_i p_i

这里选中的是 Billing，概率为 0.998，但其余概率同样有用：它们告诉我们模型如何在各备选项之间分配自己的置信。

#### Score：有序分布的期望

当存在若干彼此不同的备选项时，Choice 很合用。可如果我们想在有序量表上衡量某样东西呢？

看这个问题：

> 这条客户请求有多紧急？

我们定义三个等级：

- 0：低紧急度
- 1：中紧急度
- 2：高紧急度

```
from transformers import pipeline

decide = pipeline("decision", model="autotrust/GEV-26B-Decide")
decision = decide(
    {
        "state": "I was charged twice for my order and want a refund.",
        "questions": {
            "urgency": {
                "type": "score",
                "instructions": "How urgent is the request?",
                "criteria": ["low", "medium", "high"]
            },
        }
    }
)

# {
#   'urgency': {
#     'type': 'score',
#     'score': 1.7053890228271484,
#     'legend': {
#       '0': 'low',
#       '1': 'medium',
#       '2': 'high'
#     },
#     'confidence': 0.5580834252759814,
#     'probabilities': {
#       '0': 0.014908230863511562,
#       '1': 0.26479458808898926,
#       '2': 0.7202972173690796
#     }
#   }
# }
```

模型同样给出一个概率分布：

| 等级 | 概率 |
| --- | --- |
| 0 — Low | 0.01 |
| 1 — Medium | 0.26 |
| 2 — High | 0.72 |

Score 原语并不只返回最可能的等级，而是计算**等级索引的期望值**。

对表示等级的随机变量 (X)，期望为：

E[X]=∑i=0K−1ipi \mathbb{E}[X]=\sum_{i=0}^{K-1}ip_i

对我们的例子：

E[X]=0(0.01)+1(0.26)+2(0.72)=1.7 \mathbb{E}[X] = 0(0.01)+1(0.26)+2(0.72)=1.7

因此报告出来的 score 是 `1.7`。

这并不是说模型选了一个介于 medium 和 high 之间的虚构等级，而是说它的概率分布的期望是 1.7。

#### Noul：一次 Bernoulli 决策

第三种原语是 Noul，表示一个二值问题。

例如：

> 客户是在要求退款吗？

```
from transformers import pipeline

decide = pipeline("decision", model="autotrust/GEV-26B-Decide")
decision = decide(
    {
        "state": "I was charged twice for my order and want a refund.",
        "questions": {
            "refund": {
                "type": "noul",
                "instructions": "Is the customer requesting a refund?"
            }
        }
    }
)

# {
#   'refund': {
#     'type': 'noul',
#     'noul': 0.9947046637535095
#   }
# }
```

我们不定义一串选项，而是让模型返回答案为真的概率。可以用 Bernoulli 分布来理解这一点（noul 就来自 Bernoulli）。

令 (Y) 表示一个二值结果：

Y∼Bernoulli⁡(p) Y\sim\operatorname{Bernoulli}(p)

其中

P(Y=1)=p,P(Y=0)=1−p. P(Y=1)=p,\qquad P(Y=0)=1-p.

如果模型返回：

```
{"type": "noul", "noul": 0.92}
```

它给 Yes 分配 `0.92` 的概率，给 No 分配 `0.08`。

模型在这里并不是随机采样一个二值答案，而是直接返回概率参数本身，把如何据此行动留给应用去决定。

#### Confidence：模型有多确定？

到目前为止，我们已经从模型那里拿到了概率分布。不过决策模型的接口还会为 Choice 和 Score 返回一个名为 `confidence` 的字段。

完整分布里可能包含若干个可能答案，把模型置信的集中程度概括出来会很有用，`confidence` 正是干这个的。

对有 (K) 个选项的 Choice，confidence 为：

pmax⁡−1K1−1K \frac{p_{\max}-\frac{1}{K}}{1-\frac{1}{K}}

其中（$p_{\max}$）是最大的预测概率。

这里的直觉是：

- 均匀分布的 confidence 为 0（$p_{\max} = \frac{1}{K}$）。这意味着模型认为所有选项等可能。
- 完全集中在某一个选项上的分布，confidence 为 1（$p_{\max} = 1$）
- 相对均匀分布而言，获胜概率越大，confidence 越高。

在前面那个三选项的例子里，Billing 的概率是 0.80：

C=3(0.99)−12=0.98 C=\frac{3(0.99)-1}{2}=0.98

注意，获胜概率是 0.99，但报告出来的 confidence 是 0.98。confidence 会把最大概率相对可用选项数做归一化。相比之下，有序的 Score 例子里 confidence 只有 0.558。

## Hugging Face 生态中的决策模型

决策模型是个年轻又快速变化的领域。每个模型在底层做决策的方式都不一样（对整个 schema 联合打分的头、架在 LLM 骨架之上的独立读出层、边缘设备尺寸和多模态变体，等等）。这种多样性是好事，但也有代价：如果每个模型都暴露自己的接口，围绕它的每个工具就得做针对模型的适配。

我们在 Hugging Face 的目标是就一套共同的**接口**达成一致，而不强求共同的**实现**。决策模型内部想怎么运作都可以，只要它接收同样的 state 和 questions、返回同样带类型的决策。这份契约一旦存在，生态里的其他部分就能一次性地基于它来构建：

- llama.cpp 这类推理引擎可以通过同一套 API 服务任意决策模型
- Hub 可以用统一的方式打包和呈现它们
- 训练工具可以面向共享的原语，而不是逐个架构

本节余下部分逐一讲这几块。

### 1. 用 Transformers 提供服务

Transformers 现已支持 `DecisionPipeline`、`AutoModelForDecision` 和 `DecisionConfig` 类。它们沿用了 `transformers` 里 pipeline 与模型类的整体结构，但专为决策模型量身打造。

```
from transformers import pipeline

decide = pipeline("decision", model="autotrust/GEV-26B-Decide")
print(decide)

# DecisionPipeline: {'model': 'JevForDecision', 'dtype': 'bfloat16', 'device': 'cuda', 'input_modalities': 'text'}
```

也可以像这样查看配置和模型：

```
from transformers import AutoModelForDecision, DecisionConfig

model_id = "autotrust/GEV-26B-Decide"
config = DecisionConfig.from_pretrained(model_id)
model = AutoModelForDecision.from_pretrained(model_id)
```

[Transformers 也支持 `/v1/systemone` endpoint](https://huggingface.co/docs/transformers/main/en/serve-cli/serving#v1systemone)。

    "refund":{
      "type":"noul",
      "noul":0.9953224062919617
    }
  },
  "usage":{"input_tokens":148,"output_tokens":0}
}
```

> 一个有意思的细节是：上面这些 API 同样适用于兼容的自回归语言模型。Transformers 会构造决策 prompt，在一次批量前向里评估答案标签的 logit，再套用 softmax，而不生成回答文本。这意味着我们不必非得训练一个新模型，就能试验决策接口。

### 2. 用 llama.cpp 提供服务

[llama.cpp 也支持决策模型](https://huggingface.co/blog/ggml-org/decision-models-in-llamacpp)，用的是同一套 `/v1/systemone` API。

例如，可以从 Hub 启动一个 GGUF 决策模型：

```
llama serve -hf ggml-org/Kev-4B-GGUF
```

默认服务器跑在 9931 端口。

接着可以用 `http://localhost:9931/v1/systemone` 发送包含同样 state 和 questions 的请求。模型已由服务器选定，请求里可以省略 `model` 字段。

有用之处在于接口兼容。

```
curl http://localhost:9931/v1/systemone \
  -H "Content-Type: application/json" \
  -d '{
    "model": "ggml-org/Kev-4B-GGUF",
    "state": "I was charged twice. Please refund me today.",
    "questions": {
      "department": {
        "type": "choice",
        "instructions": "Which team should handle this?",
        "criteria": {
          "billing": "Payments and refunds",
          "technical": "Bugs and technical issues",
          "sales": "Pricing and subscriptions"
        }
      },
      "urgency": {
        "type": "score",
        "instructions": "How urgent is the request?",
        "criteria": ["low", "medium", "high"]
      },
      "refund": {
        "type": "noul",
        "instructions": "Is the customer requesting a refund?"
      }
    }
  }'
```

### 3. 在 Hugging Face Hub 上发现模型

Hugging Face 引入了专门的 [`decision-model` 标签](https://huggingface.co/models?other=decision-model&sort=trending)，用来发现兼容的模型。这很有用，因为决策模型不必共用同一个骨架或架构。

例如，生态里既有基于 ModernBERT 这类编码器架构的模型，也有从更大的生成式语言模型骨架衍生出来的模型。

### 4. 用 Hugging Face 工具训练决策模型

弄清推理之后，下一个问题是能否对决策模型做适配。既然决策模型已经集成进 transformers，就可以用 `Trainer` API 来 fine-tune 它们。

下面是一个玩具示例，用 `JEV-9B` 做客服请求路由的 fine-tune。它故意写得很小，但把关键部分都展示了出来：

- 每个样本都是一次决策请求（一个 `state` 加 `questions`），配上标准答案。
- `model.decision_config.prepare_inputs` 把请求转成模型输入，和推理时完全一样。
- 模型为每个选项返回一个 logit，因此 `choice` 问题用普通的、在选项上的交叉熵损失来训练。

```
import os; os.environ["CUDA_VISIBLE_DEVICES"]="2"
import torch
import torch.nn.functional as F
from transformers import AutoTokenizer, AutoModelForDecision, Trainer, TrainingArguments

checkpoint = "autotrust/JEV-9B"
tokenizer = AutoTokenizer.from_pretrained(checkpoint)
model = AutoModelForDecision.from_pretrained(checkpoint)

examples = [
    ("I was charged twice. Please refund me.", "refund"),
    ("My package has not arrived.", "shipping"),
    ("The application crashes when I open it.", "technical"),
    ("I want my money back.", "refund"),
    ("Where is my delivery?", "shipping"),
    ("I cannot log into my account.", "technical"),
]

options = {
    "refund": "Billing issues and refunds",
    "shipping": "Orders and deliveries",
    "technical": "Software and account issues",
}

def preprocess(text, label):
    request = {
        "state": text,
        "questions": {
            "category": {
                "type": "choice",
                "instructions": "Classify the support request.",
                "criteria": options,
            }
        },
    }
    (inputs, questions), = model.decision_config.prepare_inputs(
        request, tokenizer
    )
    inputs["marks"] = inputs["marks"].unsqueeze(0)
    inputs["num_options"] = torch.tensor([[len(questions[0].options)]])
    inputs["question_type_ids"] = torch.tensor([[1]])  # choice
    inputs["labels"] = torch.tensor(
        [questions[0].options.index(label)]
    )
    return inputs

dataset = [preprocess(text, label) for text, label in examples]


class DecisionTrainer(Trainer):
    def compute_loss(self, model, inputs, return_outputs=False, **kwargs):
        inputs = inputs.copy()
        labels = inputs.pop("labels")
        logits = model(**inputs)

        logits = logits.unsqueeze(0)  # [3] -> [1, 3]
        loss = F.cross_entropy(logits.float(), labels)

        return (loss, logits) if return_outputs else loss


trainer = DecisionTrainer(
    model=model,
    args=TrainingArguments(
        output_dir="./decision-toy",
        max_steps=30,
        per_device_train_batch_size=1,
        learning_rate=1e-3,
        logging_steps=5,
        save_strategy="no",
        report_to="none",
        remove_unused_columns=False,
    ),
    train_dataset=dataset,
    data_collator=lambda batch: batch[0],
)

trainer.train()
```

训练决策模型的一流支持也即将进入 TRL（[huggingface/trl#8040](https://github.com/huggingface/trl/pull/8040)），到时候就不必手写这些管道代码了。撰文时，这个 PR 仍然开着。

如果想更进一步，把生成式 LLM 改造成决策模型，[Unsloth 提供了一份配方](https://unsloth.ai/docs/basics/train-your-own-decision-model-with-unsloth)，用 LoRA 和决策打分头对 Qwen 这类模型做 fine-tune。

## 结语

决策模型之所以有意思，不是因为分类这件事新鲜，而是因为它让**决策与概率成为软件的一等输出**。

传统分类器本来就会输出概率，零样本分类器本来也允许在运行时定义类别。决策模型把这些思路收进一套带类型的接口：多种问题原语、非生成式的打分，以及通过专门训练得到可靠、校准过的决策的可能。
