向一个前沿模型要一份幻灯片，你会拿到一份不错的。要十份，它们就开始长得像了：同样是那种有品位的默认样式，同样是同一套自家风格，还带一点淡淡的「AI 生成的幻灯片」味。在你想让幻灯片长得像*你自己的*模板之前，这都没关系。前沿模型有它的自家风格，再多 prompt 也拦不住它们漂回去。而且有时候内容是机密的，压根不能离开你的系统。

这两件事都指向一个你自己拥有的模型：开放权重、跑在你自己的基础设施上、在你自己的设计语言上训练过。麻烦在于，小尺寸的开放模型，也就是你真会自建托管的那一类，在这件事上*很差*。它们做出来的幻灯片是坏的：标题隐进背景里看不见了，文字冲出页面，形状一个压一个叠着。

**Palette** 押的是一个赌注：一个小的开放权重模型，用你设计语言上的合成数据训练、再由一套 harness 把关，可以在你保留成果所有权的同时与前沿系统竞争。我们对一个 20B 模型做了 fine-tuning，让它像人一样做幻灯片：一个设计师负责规划整份幻灯片，一个编码者负责画每一页。它的训练数据遵循 [IBM Design Language](https://www.ibm.com/design/language/resources/)，而在 [PresentBench](https://huggingface.co/datasets/PresentBench/PresentBench) 上，我们测的三个领域里它有两个排第一。本文会讲我们怎么合成数据、怎么训练模型，以及在它外面怎么搭这套 harness。

## 为什么幻灯片对小模型很难

一份幻灯片看起来简单，但做一份要求模型完成三件小模型不擅长的事。

**它看不见自己正在排的版。** 模型并不画幻灯片，它写代码，把每个元素放到某个 x、y、宽度和字号上。一个 75 字符的标题在 56pt 下能不能排进两行，是模型在脑子里算的算术，而要等代码渲染出来，它才知道自己算错了。小模型经常在这里出错，形状互相重叠、文字冲出页面就是这么来的。

**它同时要下两类判断。** 决定每页说什么、怎么呈现（用图表还是表格？砍掉什么？）是编辑上的判断；把它精确地摆好是几何。一趟生成就得在 10–20 页里同时把两件事都做了，还要让配色、字体和版式保持一致。

**没有数据展示幻灯片是怎么做出来的。** 成品幻灯片多得是，但设计选择背后的理由、以及产出它们的那些代码，并不存在。

## 像人一样构建：一个设计师加一个编码者

没有人能一趟就做出一份幻灯片。你先定故事（多少页、每页说什么、哪一页用图表哪一页用表格），然后才去做每一页。Palette 也这样分工，拆成两个角色，由同一个 LoRA adapter 承担：

- 设计师读规划，写出一份结构化的 JSON brief：配色、字体体系，以及每一页的版式、确切内容和一句设计理由。
- 编码者从 brief 里取出一页的规格，写出画出这一页的 [pptxgenjs](https://gitbrent.github.io/PptxGenJS/) JavaScript，并在前面附上自己的推理。

现在每个角色只下一类判断：设计师管编辑上的取舍，编码者管几何。它们之间的 brief 既可读也可改，所以一个人或一个 agent 都能在不重新生成整份幻灯片的情况下改掉某一页的版式。而且因为每一页的上下文在任何代码写出来之前就已经定死，编码者的调用可以并行跑，一页一个，这让编码阶段快了大约 6–7 倍。

我们用 LoRA 而不是全量 fine-tuning 来训练这个 adapter：它在一个足够强的底座之上教一种格式和一项技能，而不去扰动底座已经会的东西，而且它让每次实验都很便宜。一个教训：编码者的样本比设计师的样本长约 5 倍，所以简单地混在一起会让设计师训练不足，直到我们把设计师的样本过采样 5 倍。

## 合成幻灯片以及它们的推理

关于规划、设计决策和逐页代码，并没有公开的语料，所以我们用一个大的开放 teacher 生成了一份。每份幻灯片都从一份 recipe 开始，它设定体裁、长度、版式和任何用户指令，于是我们能控制数据覆盖到什么范围。规划从整齐的大纲到原样倾倒出来的内容堆都有，所以模型会学会删减和压缩。我们生成了大约 1000 份幻灯片，覆盖大约 10,000 页。

每个样本还带着它背后的推理，而且写成一个反事实：这段轨迹会掂量另一个方案，并说明它为什么被否掉，于是模型学到的是一个选择背后的规则，而不只是选择本身。设计师对内容和形式做推理。例如：

> “四个季度的营收，有一条明确向上的趋势。我考虑过用表格，但这一页的重点是趋势而不是具体数字，所以柱状图能让人一眼看出来。”

编码者对几何做推理：

> “标题有 62 个字符。用 44pt 它会折成三行并压到下面的图表上，所以我把它设成 36pt，正好排进两行，还在图表上方留出了空间。”

单靠 teacher 并不能让数据变好，围着它的那个循环才行。每一份合成出来的幻灯片都会被渲染，并由 harness 在推理时用的同一个 checker 检查重叠和溢出。坏掉的页面会被修复，而它们的推理会被重写成同一类反事实，说清楚原来的版式错在哪里、修好之后为什么就对了。checker 抓到的每一个错误，都变成一个更好的训练样本。

最难的问题是忠实度。最糟的失败是一页幻灯片上出现了输入里并没有的事实，而我们发现一条 prompt 规则挡不住它。如果 brief 要一张六行五列的表格，却只带了三条要点，编码者就得把剩下的编出来。

真正解决它的是参照幻灯片，不是规则：把参照修好，几乎总会改变 teacher 的输出，而加一条规则很少有用。teacher 在 prompt 里看到几份参照幻灯片，它照抄参照的程度远超过听指令的程度。

## 用平实的英语引导一份幻灯片

用户常常想对具体的设计选择做更细粒度的控制：用图表而不是表格、某个特定的颜色、更暗一点的封面。Palette 让他们用 *directives* 提这些要求——直接写进规划里、用 `[[ ]]` 包起来的一句短指令：

```
## Rollout plan
- March: pilot with two teams
- May: security review complete
- July: rollout to all of engineering
- September: company-wide launch
- November: first adoption review
[[make this a timeline]]
```

设计师把每条 directive 都做进 brief，编码者画这一页时照它执行。没有这条 directive，模型把这些里程碑做成表格是合理的选择；有了它，模型改画成一条时间线。

模型会遵循 directive，是因为它就是这么训练的。数据 recipe 里包含 12 个类别的 directive，下面展示其中几个，每一类都配了好几种不同的说法，所以模型学到的是意图而不是某个固定短语。

| 类别 | 示例 directive |
| --- | --- |
| 版式 | `[[make this a timeline]]` |
| 语气 | `[[be candid, no spin]]` |
| 受众 | `[[this is for the board]]` |
| 顺序 | `[[lead with the ask]]` |
| 省略 | `[[no pricing]]` |
| 强调 | `[[highlight the headline number]]` |

## 搭建一套检查与修复的 harness

即使训练得很好的模型，有时也会产出一页坏掉的东西：标题和背景一个颜色，或者两个方框叠在一起。所以 Palette 不会直接把模型的输出交给你，每份幻灯片都要先过一遍 harness。

[![Palette 的流水线：plan → designer → coder → check & repair → deck](https://cdn-uploads.huggingface.co/production/uploads/63890e3843d8b0797a0ad606/PZoiyAFg_nrWRryQhjGN_.png)](https://cdn-uploads.huggingface.co/production/uploads/63890e3843d8b0797a0ad606/PZoiyAFg_nrWRryQhjGN_.png) *图 2。设计师起草 brief，编码者并行写出每一页的代码，在把幻灯片交回之前，harness 会逐页检查并修复。*

首先，一些简单的规则修掉已知的错误，比如一个畸形的颜色代码——不然它会把每一页都变成黑色。然后每一页会被渲染并测量：一个几何 checker 会标记出重叠、被裁切或冲出页面的文字。被标记的页面交给另一个独立的 editor 模型，由它重写这一页的代码。

关键的规则是：只有 checker 确认这一页确实变好了，重写才会被保留，否则原样留着。这让 harness 可以放心地跑在每一份幻灯片上。它能修好一页，但不会把一页改得更糟。

[![修复前后：重叠的卡片被修成一个整齐的网格](https://cdn-uploads.huggingface.co/production/uploads/63890e3843d8b0797a0ad606/iZzBRJXOUxncecFIEgw-B.png)](https://cdn-uploads.huggingface.co/production/uploads/63890e3843d8b0797a0ad606/iZzBRJXOUxncecFIEgw-B.png) *图 3。一次修复的示意。刚生成时（左），每张卡片的标题都叠在它的描述之上；harness 检测到重叠，把卡片重排成一个 2×2 的网格（右）。*

为了衡量它的效果，我们把每份 PresentBench 幻灯片各生成一次，再分别在带 harness 和不带 harness 的情况下打分。在 131 份幻灯片上，harness 平均加 3.5 分。

## 评测

我们在 [PresentBench](https://huggingface.co/datasets/PresentBench/PresentBench) 上做评测，它按五项标准给生成的幻灯片打分：基本功、视觉设计、完整性、正确性和忠实度。PresentBench 提供的是源文档而不是规划，所以在这些跑测里，由一个单独的前沿模型先从相应的文档起草出每份规划，Palette 再据这份规划做幻灯片。我们报告三个领域；基线数字来自 PresentBench 论文。

[![按领域划分的 PresentBench 得分](https://cdn-uploads.huggingface.co/production/uploads/63890e3843d8b0797a0ad606/QiWVeHtadoTFYsfdPjkDr.png)](https://cdn-uploads.huggingface.co/production/uploads/63890e3843d8b0797a0ad606/QiWVeHtadoTFYsfdPjkDr.png) *图 4。按领域划分的 PresentBench 得分。Palette（蓝色）对阵 NotebookLM、Manus 1.6 和另外五个系统（灰色）。Palette 在 Economics 与 Education 上排第一，在 Talk 上排第三，三个领域的均值上排第二。*

在结构化内容和数字准确度决定得分的地方，Palette 表现最好，在 Economics 与 Education 上排名第一。在 Talk 这种以叙事、以讲稿驱动的幻灯片上，两个闭源系统得分更高，Palette 排第三。三个领域合起来它排第二，落后 NotebookLM 1.1 分（59.7 对 60.8），排在其余系统之前——而它是一个单一的 20B 开放权重模型。

PresentBench 衡量的是一份幻灯片好不好，但不衡量它是否遵循某一套具体的设计语言。我们没有发现任何一个做这件事的基准，而这正是我们希望帮忙补上的缺口。

## 下一步

harness 已经在计算一些便宜、可校验的信号：这一页能不能渲染出来、有没有东西重叠或溢出、每一条事实是否都能回溯到 brief。今天我们用它们在生成之后修复输出。下一步，我们想把同一套检查用作强化学习的 reward，让模型从一开始就不再犯这些错。因为编码者一次只做一页，每一页都是一段很短、可以独立校验的 rollout，天生适合 GRPO 风格的训练。

我们也想补上图表密集的幻灯片这个短板：从源文档里抽取图表（例如用 [Docling](https://github.com/docling-project/docling)），再借助 harness 把它们摆放好。我们还在探索一种更轻的自带模板的办法：拿你现有的一两个 `.pptx` 文件的产出重新换皮，而不需要再训练。

## 我们学到了什么

构建 Palette 教会了我们几条有效的方法，它们可以自然地推广到别的任务上——只要那个任务的产出有一种能用代码校验的结构，从图表、示意图到 UI 布局都算：

- 把推理放进数据里。训练时带上一个选择为什么被做出、包括什么被否掉了，教给模型的远比只给选择本身多。
- 先修样本，再考虑加规则。teacher 出错的时候，我们的第一反应是往它的 prompt 里加规则，而那很少有用。teacher 照抄参照幻灯片的程度远超过遵循指令，所以真正改变它输出的是把参照修好。
- 让修复默认安全。一个只在可度量地有帮助时才被保留的修复，可以跑在每一个产出上。
- 先把 checker 做出来。它才是让数据可信、让产出敢交付的东西。
