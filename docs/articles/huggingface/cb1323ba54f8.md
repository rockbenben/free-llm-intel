我们于 2025 年 11 月发布了 OlmoEarth（v1）。此后，合作伙伴们把它应用于各种各样的任务：从跟踪红树林变化、分类森林退化的驱动因素，到在数天内产出国家尺度的作物类型地图，部署规模扩展到国家、大洲乃至全球。每一次发布都让我们更接近使命：把最先进的 AI 带给那些致力于保护人类和地球的组织与社区。

当 [OlmoEarth](https://olmoearth.allenai.org/) 处理卫星影像、在数万到数十万平方公里范围上做预测时，效率决定了什么是可行的。在运行 OlmoEarth 的整个生命周期——数据导出、预处理、推理、后处理——中，算力是迄今为止最大的成本。更高的效率意味着我们能在 OlmoEarth 平台上支持更多伙伴，也意味着任何自行运行 OlmoEarth 的人都能更快、更便宜地利用这项技术。

这就是我们构建 **[OlmoEarth v1.1](https://huggingface.co/collections/allenai/olmoearth)** 的原因：一个新的模型家族，把算力成本最多降低 **3 倍**，同时在研究基准和与合作伙伴共同构建的任务组合上保持 OlmoEarth v1 的性能。

### 用更短的序列提升效率

OlmoEarth 模型是基于 transformer 的模型——当今机器-learning 的主流架构之一。为了处理遥感数据，我们首先把它转换为模型可以摄入的 *token* 序列。

基于 transformer 的模型有两个控制效率的重要杠杆：**模型大小**（这就是我们发布一个模型家族的原因，用户可以挑选适合自己计算预算的规模）和 **token 序列长度**。计算成本随 token 序列长度二次增长，因此即便小幅缩短也能显著降低运行模型的成本。

[![bench-capture-2026-05-18T14-40-39](https://cdn-uploads.huggingface.co/production/uploads/638e39b249de7ae552d977b5/E_EJ2q5ZLbGn2dZ4j92r_.png)](https://cdn-uploads.huggingface.co/production/uploads/638e39b249de7ae552d977b5/E_EJ2q5ZLbGn2dZ4j92r_.png)

### 设计 token

这对基于 transformer 的遥感模型引出一个重要问题：**一个 token 应该表示什么？**

以 Sentinel-2 影像为例——这是我们处理的常见模态。一个 Sentinel-2 输入是一个带有高和宽的张量（H、W 表示纬向和经向像素）、一个时间维度 T，以及 12 个 Sentinel-2 通道（[H, W, T, D=12]）。

[![OlmoEarth v11 blog copy - Google Docs-image-3](https://cdn-uploads.huggingface.co/production/uploads/638e39b249de7ae552d977b5/mPjOTX0JVZij1-6q2DFLY.png)](https://cdn-uploads.huggingface.co/production/uploads/638e39b249de7ae552d977b5/mPjOTX0JVZij1-6q2DFLY.png)

目前，我们按*基于分辨率的 patch* 切分数据。具体来说，就是选取某个空间 patch 尺寸 p，把整幅 Sentinel-2 图像切分成 p x p 大小的 patch：

[![OlmoEarth v11 blog and social copy - Google Docs-image-4](https://cdn-uploads.huggingface.co/production/uploads/638e39b249de7ae552d977b5/-OzFWBJPTKBDXOJR2Iguw.png)](https://cdn-uploads.huggingface.co/production/uploads/638e39b249de7ae552d977b5/-OzFWBJPTKBDXOJR2Iguw.png)

对每个 patch，我们按每个时间步、每种分辨率各建一个 token。因此一个有 2 个时间步的 Sentinel-2 输入，每个 patch 会产出 6 个 token（2 个时间步 × 3 种分辨率：10m、20m 和 60m）。

总体上一个 [H, W, T, D=12] 的 Sentinel-2 输入会产生 H/p × W/p × T × 3 个 token。

为每种分辨率使用独立的 token 是处理 Sentinel-2 数据的常见技术——[Galileo](https://arxiv.org/abs/2502.09356) 和 [SatMAE](https://arxiv.org/abs/2207.08051) 都采用此法，且 SatMAE 显示这样做结果显著更好。但这并非普适规则：[CROMA](https://arxiv.org/abs/2311.00566) 就是所有波段只用单个 token 的模型，不管分辨率如何。由于 token 数量以乘法方式叠加，把各分辨率折叠为单个 token 能产出**少 3 倍的 token**，并在预训练、微调和推理上带来实实在在的节省。

朴素地这样合并 token 会导致明显的性能下降，包括在 m-eurosat kNN（遥感模型的常见基准任务）上掉 10 个百分点。我们假设，把 Sentinel-2 各波段分开成不同 token，让 OlmoEarth 更容易建模重要的跨波段关系。

要在**不**影响性能的前提下合并 token，我们必须修改预训练方案。这些改动在论文中有详细描述。

### 面向开发者

产出的是一个「以更少做更多」的模型家族。在每一个尺寸上，OlmoEarth v1.1 的运行成本最多比 OlmoEarth v1 便宜三倍，让每个运行 OlmoEarth 的团队都更负担得起对行星尺度地图的高频更新。如果你在用最初 OlmoEarth 家族中的模型，试试 OlmoEarth v1.1。它在只需三分之一算力的情况下提供与 OlmoEarth v1 相似的性能，尽管我们观察到某些任务有所退步（详见技术报告）。如果它适合你的任务，你应该能在微调和推理中看到显著提速。

### 面向研究者

预训练遥感模型有太多自由度，这使其难以研究。当性能发生变化时，是架构、数据集还是预训练算法的作用？

OlmoEarth v1.1 与 OlmoEarth v1 在同一数据集上训练，因此两者之间的任何差异都能隔离出方法学改动的影响。我们希望这能推进「为遥感预训练模型」背后的科学原理的理解。
