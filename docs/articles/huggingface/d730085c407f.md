# 那本你会亲手提交的 PR

*用一个 Skill 和测试工装，让 transformers 模型在 mlx-lm 中即刻可用*

## TL;DR

我们提供一个 **Skill** 和一套**测试工装（test harness）**，帮助把语言模型从 transformers 移植到 mlx-lm，让它们在进入 transformers 的瞬间（几乎）立刻可用。这个 Skill 的定位是辅助贡献者与审稿人的"副手"，而非自动化工具。我们将解释为什么这么做、怎么做的，并谈谈在 agent 时代如何有意义地参与开源贡献。

## 代码 agent 的到来

2026 年，代码 agent 开始真正可用了。过去编辑器旁边的自动补全，如今变成了能根据简短规格一次性产出合理解决方案的系统。生成的代码通常开箱即用、覆盖你要的需求，并对未指明的细节做出合理假设。这很好。正如 Jensen Huang 所说，[我们已让世界从 3000 万程序员瞬间变成 10 亿](https://www.youtube.com/watch?v=vif8NQcjVf0&t=7324s)。创造力被释放了。

但这迫使我们重新思考开源。

以 transformers 库为例。它有数百名贡献者，被数千个项目使用，下载量超过十亿次。突然之间，任何有 agent 的人都可以让它找一个 open issue、修复并提交 PR。这正是正在发生的事。这些人很开心，因为他们觉得自己为一个伟大的库做了贡献——但可悲的事实是，多数时候他们并没有，只是自己没意识到。

为什么不算？agent 生成的 PR 通常漏掉了两个前提。

- **像 transformers 这样的代码库极其在意代码本身。**做一个"代码长什么样无所谓"的项目当然很酷，但 transformers 不是这样的项目。作为被数千人使用的库，transformers 首先是一种人与人之间通过代码交流的方式。模型文件要能从上到下顺畅阅读，因为我们希望实践者不必穿透复杂抽象就能看懂。这一理念[贯穿整个库的设计](https://huggingface.co/spaces/transformers-community/Transformers-tenets)，也是我们偏好扁平层次结构等原因所在。
- **Agent 没有这个上下文。**因为设计决策未被显式记录，agent 会按"最佳实践"提出重构来"改进"代码库，却没意识到它们破坏了库与用户之间的隐性契约。它们啰嗦、过早抽象、注意不到改动波及其他区域、引入隐蔽 bug、破坏性能。它们还阿谀奉承，把任何想法都当作好主意并认真执行——包括那些维护者本会用一句话直接驳回的想法。

仍只有少数维护者需要阅读每个 PR、理解它、判断设计方向是否正确、识别副作用并写下反馈。PR 数量涨了十倍，但维护者人数没涨（也不可能涨，因为团队协调无法扩展）。

## 这和 MLX 有什么关系？

因为体量巨大，transformers 是最早感受到这种压力的项目之一，但同样的动态到处都在发生。来自另一个领域的例子：App Store 审核人员被淹没了，因为现在任何人都能构建并提交应用，于是很多人真的这么干了。

同样的逻辑也适用于 MLX：其维护者非常在意代码质量，并仔细阅读每个 PR。我们想看看 agent 能否*帮助贡献者*快速落地高质量的模型移植，同时*支持审稿人*的工作。我们不仅力求产出看起来出自细心人类之手的 PR，还提供额外工件来增强信号：生成示例、数值对比，以及一套独立的、非 agent 的测试工装用于可复现验证。

![Transformers as the source of truth](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/transformers-to-mlx/transformers-thumbnail.png)

transformers 与 MLX 的另一层联系是：多数时候，mlx-lm 的模型就是从 transformers 实现移植来的。由于 transformers 追求清晰可读，它已[成为模型定义的权威来源](https://huggingface.co/blog/transformers-model-definition)。下游贡献者会等 transformers 的实现就绪后再移植到其他框架。副作用是，这对 agent 来说是绝佳环境，因为它天然限制了范围：agent 不必从零创造实现，而是以 transformers 代码为权威来源。

这种方式契合我们的目标：一个模型进入 transformers 后，应该很快在 MLX 上可用。

## 我们做了什么

我们构建了一个 mlx-lm 贡献者可用的 Skill，用于把模型从 transformers 移植到 MLX。给定像"把 olmo_hybrid 架构转换到 MLX"这样的 prompt，Skill 会搭建工作用的虚拟环境、从 Hub 发现并下载相关模型、阅读 transformers 的建模代码、编写 MLX 实现，并运行一整套测试。如果结果看起来不对，它会调试并迭代，在满意之前不会宣告成功。

我们把它设计成对审稿人同样有用。

**对贡献者**，Skill 当然处理了所有脚手架工作：在 Hub 上寻找模型变体、diff 它们的 config 以发现随变体变化的参数、下载 checkpoint、为 mlx-lm 和 transformers 设置可编辑安装。但它也处理更困难的建模任务。它关注关键的架构细节，并核验像 RoPE 配置这类容易埋下隐蔽 bug 的敏感区域。它能发现 config 未声明 dtype 并从 safetensors 元数据头推断。它逐层对比 transformers 与 MLX，精确定位分歧出现在哪里。这些只有具备移植经验的人才会想到去做。

**对审稿人**，Skill 生成的 PR 会坦诚说明是 agent 辅助完成的，但看起来确实像一份细心的人类提交。审稿人会看到代码遵循 mlx-lm 约定：使用惯用解法、没有多余注释、没有投机式抽象、未经明确许可不改动共享工具函数。鉴于代码是 agent 辅助的，我们尽量放入*比一般 PR 更多*的数据，提供尽可能强的信号：PR 正文包含一份报告，其中有各变体及其架构差异汇总、生成示例、数值对比、dtype 校验、相对 transformers 基线的逐层对比。PR 始终披露 agent 辅助身份，且在贡献者确认结果之前，Skill 不会提交它。

**对验证**，Skill 会生成一份测试清单，交给一套独立的、非 agent 的测试工装——后者在设计上易于复现，且不受 LLM 幻觉或自满影响（[下文详述](https://huggingface.co/blog/transformers-to-mlx#the-test-harness)）。

## 我们怎么做的

Skill 是 agent 的"菜谱"：用简单文本文件写下指引，引导模型完成复杂任务。它不是魔法；靠 prompting 加迭代也能达到同样效果。但 Skill 提供*一致性*（每次运行遵循同一流程，而不同的人 prompt 方式会不同）、把歧义降到最低，同时充当文档：任何人都可以阅读 Skill 来理解它在做什么、发现遗漏场景并提出改进。

我们的 Skill 是靠亲手移植一个模型引导出来的——在与 Claude 的对话中完成。我让 Claude 把 GLM 4.7 从 transformers 移植到 mlx-lm，按平时协作的方式下达指令。有个技巧：我让 Claude 指向一份 mlx-lm 检出，其中已存在实现被我删掉了，这样就能把输出与 ground truth 对比。经过几轮迭代，我得到了可用的实现、一段揭示 Claude 解题思路的对话，以及 Skill 的第一稿（由 Claude 按流程摘要生成）。我对它做了大量编辑，并融入了 [@gabegoodhart](https://huggingface.co/gabegoodhart) 的经验——他慷慨地分享了自己[移植另一个模型的对话](https://github.com/ml-explore/mlx-lm/pull/442#issue-3399360107) 🙌。

我们把这个循环重复了很多遍，Skill 不断成长。技术层面，我们覆盖了诸如 [RoPE bug](https://x.com/Prince_Canuma/status/1982913823888814334)（会产出看似合理、但长序列上逐渐劣化的输出）、悄然摧毁推理速度的 float32 精度污染（这些事情的发生频率会出乎你意料）、实现必须处理的跨变体差异的 config 字段，以及单机放不下的超大模型的分布式推理。我们教会它调用 `hf` CLI 来发现和下载模型。最重要的是，我们要求它执行资深移植者会跑的那些测试，测试通过前不得宣告成功。

![It's always RoPE](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/transformers-to-mlx/rope.png) *Source: [@Prince_Canuma](https://x.com/Prince_Canuma/status/1982913823888814334)*

文化层面，我们覆盖了*更软性*的特性，解释了让 PR 易于审阅的约定：不要用注释解释代码（审稿人得同时解析注释*和*代码 🤦‍♂️）、绝不要顺手提议重构、未经询问不要动共享工具函数。这些规则对 agent 毫无成本，却为审稿人省下大量时间。

最终效果：贡献者输入一条 prompt，Skill 就产出像[这个](https://github.com/ml-explore/mlx-lm/pull/1023)这样的 PR，外加一份供外部测试工装使用的测试清单。

## 测试工装

Skill 会把完整的结果报告作为 PR 的一部分公开。这些都来自 agent 在转换过程中运行的测试，但我们不希望审稿人"凭信仰"接受它们。更进一步，我们创建了一套独立的、非 agent 的测试工装，对转换后的代码进行系统化测试。这带来几个好处：

- 排除对 LLM 幻觉结果或过于自满的不确定性。
- 保证可复现：任何人都能下载测试工装仓库并运行测试。
- 文档与透明。所有结果按不同层级保存：[汇总报告](https://github.com/pcuenca/mlx-lm-tests/blob/main/results/pr-5/2026-04-14T122120-7ce7a68/summary.md#layers--ran)、[逐模型细节](https://github.com/pcuenca/mlx-lm-tests/blob/main/results/pr-5/2026-04-14T122120-7ce7a68/summary.md#allenaiolmo-hybrid-instruct-sft-7b)、保存为 JSON 文件的[原始输入/输出](https://github.com/pcuenca/mlx-lm-tests/tree/main/results/pr-5/2026-04-14T122120-7ce7a68/allenai--Olmo-Hybrid-Instruct-SFT-7B)。[测试脚本](https://github.com/pcuenca/mlx-lm-tests/tree/main/results/pr-5/2026-04-14T122120-7ce7a68/scripts)也会复制到结果目录，即使将来工装改动，我们仍知道当时跑的是什么。

测试工装不是 CI 门禁。有些检查很直接（输出 dtype 是否正确？），但多数检查是定性的。预训练模型在长序列上重复自己正常吗？相对 transformers 基线 4% 的 logits 相对差异可以接受吗？这些是基于同类架构经验做出的判断。工装提供有用的信号，但拍板的仍是审稿人和贡献者。

## 如何使用这个 Skill

该 Skill 是为那些已经在给 mlx-lm 提交模型 PR、或本来就会手动提交的人设计的。它不面向大众化批量使用——因为投给 mlx-lm 的 PR 很少被一眼通过。典型循环是：贡献者提交 PR，审稿人指出改进点，双方迭代直到达到质量标准。专家级提交尚且如此，agent 辅助的提交也不会例外。

如果你不准备参与这个循环，那你可能本就不该提交 PR。审稿人会努力理解你的代码（即使知道是 agent 辅助的），你也应如此。对代码负责，准备好采纳他们的反馈。尤其不要把审稿人的评论原样丢回给 agent 然后照搬它的回复。LLM 会在自己的决定上加倍下注、跑偏、且不会有效地反驳。一旦你与审稿人交流，这就变成了人与人的对话，该由你来讨论，并尊重对方投入的时间。

你也可以用 Skill 来学习——在信心和经验积累起来之前不需要提交任何东西。阅读 Skill 以发现你不知道的问题区域：它在 skill 文件、参考文档和工具脚本中包含了近 1.5 万字。把它指向你自己的 mlx-lm fork、试着转换一个模型，等官方仓库收录了认可的实现后与你的输出对比。这样重复几次，你会对 transformers、MLX 和语言模型架构学到很多。

如果你准备好了：

```
uv run https://raw.githubusercontent.com/huggingface/transformers-to-mlx/main/install_skill.py
uvx hf skills add --claude
```

我们在 Claude Code 上开发并测试了这个 Skill。同样的思路也适用于 Codex 或其他 coding agent，但我们尚未测试。如果你在别的环境尝试了这个 Skill，欢迎告诉我们效果如何！

## 下一步与已知不足

该 Skill 对 mlx-lm 中的 LLM 效果很好，但还有大量成长空间。

### 接下来

- **mlx-vlm**。视觉语言模型住在[另一个仓库](https://github.com/Blaizzy/mlx-vlm)里，约定不同。除建模代码外，mlx-vlm 还需要*处理器（processors）*在 LLM 看到输入前处理图像。我们期待与 [Prince Canuma](https://huggingface.co/prince-canuma) 合作，帮他把擅长的事情做得更好。
- **llama.cpp**。部分同样的挑战存在。处理器要求图像处理算法用 C++ 复刻，数值差异不可避免。这是范围收得很窄的 agent 可能帮上忙的领域。
- **测试工装**。我们希望扩充测试项目，并探索安全的自动化，在我们的基础设施上自动运行测试。

### 还不行的部分

- **mlx-lm 的共享工具函数**。mlx-lm 在"抽取公共模式到共享函数"方面不如 transformers 严格。Skill 刻意偏向自包含的模型文件（和 transformers 一样），但审稿人经常要求把重复代码重构进共享模块。
- **VLM 及其他架构**，如上所述。
- **量化模型上传**。Skill 会测试量化，但不会把量化模型上传到 Hub。我们认为在 PR 审阅期间上传并不合理，但可以做一个稍后上传的流程。
- **Thinking 测试**。尚未设计专门针对 thinking 的测试。Skill 会转换并验证这类模型的生成，但不会校验 thinking 的结构。

## 结论

开源的瓶颈不是打字速度，而是理解代码库、在不破坏与用户的显式与隐性契约的前提下改动它。只要我们教给 agent 什么重要，它们就能在这个过程中帮忙。我们在 mlx-lm 的场景里探索了这会长成什么样，希望对贡献者和审稿人更快落地高质量模型转换有用！
