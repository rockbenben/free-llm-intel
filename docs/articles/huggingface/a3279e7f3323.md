*警告：本文主题是红队测试（red-teaming），因此包含一些可能令人不适或冒犯的模型生成示例。*

在海量文本数据上训练的大型语言模型（LLM）非常擅长生成逼真的文本。但这些模型常常表现出不期望的行为，例如泄露个人信息（如社会保障号）、生成虚假信息、偏见、仇恨或有毒内容。比如，早期版本的 GPT3 就被已知存在性别歧视行为（见下图）以及[针对穆斯林的偏见](https://dl.acm.org/doi/abs/10.1145/3461702.3462624)。

![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/red-teaming/gpt3.png)

一旦我们在使用 LLM 时发现这类不期望的结果，就可以开发策略把它从这些行为上引开，例如用 [Generative Discriminator Guided Sequence Generation (GeDi)](https://arxiv.org/pdf/2009.06367.pdf) 或 [Plug and Play Language Models (PPLM)](https://arxiv.org/pdf/1912.02164.pdf) 来引导 GPT3 的生成。下面是同一个提示词在 GeDi 控制 GPT3 生成下的效果示例。

![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/red-teaming/gedi.png)

即便是近期版本的 GPT3，在被提示词注入（prompt injection）攻击时也会产出类似冒犯性文本，而这会成为下游应用的安全隐患，[这篇博客](https://simonwillison.net/2022/Sep/12/prompt-injection/)有相关讨论。

**红队测试（Red-teaming）** *是一种通过诱发模型脆弱性来发现可能导致不期望行为的评估形式。* 越狱（jailbreaking）是红队测试的另一种说法，指通过操纵让 LLM 突破其安全护栏。微软 2016 年上线的 [Chatbot Tay](https://blogs.microsoft.com/blog/2016/03/25/learning-tays-introduction/)，以及更近期的 [Bing 聊天机器人 Sydney](https://www.nytimes.com/2023/02/16/technology/bing-chatbot-transcript.html)，都是真实世界案例，说明不对底层 ML 模型做充分的红队测试后果可以有多严重。红队这一概念的起源可以追溯到军队进行的假想敌模拟和兵棋推演。

对语言模型做红队测试的目标，是构造一个能诱导模型生成可能造成伤害的文本的提示词。红队测试与 ML 领域更广为人知的评估形式*对抗攻击（adversarial attacks）*有相似也有不同。相似之处在于两者都以"攻击"或"欺骗"模型、让它在真实用例中产出不期望内容为共同目标。但对抗攻击对人类来说可能无法理解，例如在每条提示词前面加上字符串 "aaabbbcc"，因为它会恶化模型表现。这类攻击在各种 NLP 分类与生成任务上的大量例子在 [Wallace et al., '19](https://arxiv.org/abs/1908.07125) 中有讨论。而红队测试的提示词看起来就是普通的自然语言提示词。

红队测试能暴露模型的局限——这些局限可能造成令人不快的用户体验，或帮助有恶意意图的用户施加暴力或从事其他违法活动从而酿成危害。红队测试的产出（和对抗攻击一样）通常用于训练模型，使其更不容易造成伤害、或使其偏离不期望的输出。

由于红队测试需要对模型可能的失败方式进行创造性思考，它的问题搜索空间非常大，因而很消耗资源。一种变通方案是给 LLM 配一个分类器，预测给定提示词是否包含可能引发冒犯性生成的话题或短语；如果分类器判定该提示词可能产生冒犯文本，就回复预设的固定话术。这种策略会倾向保守。但那样也过于死板，会导致模型频繁顾左右而言他。于是，模型要*有用*（遵循指令）与要*无害*（或至少不容易助长伤害）之间就存在张力。

红队既可以是人在回路（human-in-the-loop），也可以是用一个 LM 来测试另一个 LM 的有害输出。对那些已经做过安全与对齐微调（例如通过 RLHF 或 SFT）的模型设计红队提示词，需要以*角色扮演攻击（roleplay attacks）*的形式进行创造性思考——即指示 LLM 扮演一个恶意角色[如 Ganguli et al., '22](https://arxiv.org/pdf/2209.07858.pdf)。此外，指示模型用代码而不是自然语言作答，也能暴露模型学到的偏见，例如下面的例子。

对 LLM 做红队测试仍是一个新兴研究领域，前面提到的策略可能依然能成功越狱这些模型，或者已经帮助了大规模 ML 产品的落地。随着模型伴随涌现能力（emerging capabilities）变得越来越强大，开发能够持续适应的红队方法将变得至关重要。红队测试需要建立的一些最佳实践包括：模拟寻求权力（资源等）的场景、说服他人的场景（例如诱使人伤害自己或他人）、以及拥有能对物理世界施加影响的自主能力的场景（例如通过 API 在线订购化学品）。我们把这类可能产生物理后果的情形称为*关键威胁场景（critical threat scenarios）*。

评估 LLM 这类恶意行为有一个前提性难题：我们并不知道它们能做什么，因为它们并没有被显式训练去表现出这些行为（这正是"涌现能力"一词的由来）。因此，随着 LLM 越来越强大，要真正知道它们 capable 了什么，唯一的办法就是模拟所有可能导向恶性结果的场景，并逐一评估模型在这些场景中的行为。也就是说，我们模型的安全表现，取决于我们红队测试方法的强度。

鉴于红队测试的这一持久难题，各组织之间在数据集和最佳实践上协作（可能涉及学术、工业和政府实体）就有了充分的动力。一套结构化的信息共享流程，可以让发布模型的较小实体也能在发布前对自己的模型做红队测试，从而整体上带来更安全的用户体验。

**红队测试的开源数据集：**

- Meta 的 [Bot Adversarial Dialog dataset](https://github.com/facebookresearch/ParlAI/tree/main/parlai/tasks/bot_adversarial_dialogue)
- Anthropic 的 [red-teaming attempts](https://huggingface.co/datasets/Anthropic/hh-rlhf/tree/main/red-team-attempts)
- AI2 的 [RealToxicityPrompts](https://huggingface.co/datasets/allenai/real-toxicity-prompts)

**过往 LLM 红队测试工作的发现**（来自 [Anthropic 的 Ganguli et al. 2022](https://arxiv.org/abs/2209.07858) 和 [Perez et al. 2022](https://arxiv.org/abs/2202.03286)）

- 具备"有用、诚实、无害"行为的 few-shot 提示 LM，红队难度并不比普通 LM 更高。
- 除 RLHF 模型随规模增长变得更难红队之外，攻击成功率随模型规模扩大没有明显趋势。
- 模型可能靠"回避"来学会无害，有用性与无害性之间存在权衡。
- 人类对"什么算攻击成功"整体上缺乏共识。
- 成功率的分布随伤害类别不同而不同，非暴力类的成功率更高。
- 众包红队会产出模板化提示词（例如"给出一个以 X 开头的骂人词"），导致彼此冗余。

**未来方向：**

- 目前还没有面向代码生成的开源红队数据集——例如通过代码越狱模型、生成实现 DDOS 或后门攻击的程序。
- 针对关键威胁场景设计并实现 LLM 红队测试策略。
- 红队测试很消耗资源——算力和人力都是——因此从共享策略、开源数据集乃至直接协作中受益，协作还能提高成功率。
- 评估"回避"与"有用"之间的权衡。
- 基于上述权衡枚举各种选择，并探索红队测试的帕累托前沿（类似于 [Anthropic 的 Constitutional AI](https://arxiv.org/pdf/2212.08073.pdf) 的工作）。

这些局限与未来方向清楚地表明：红队测试是现代 LLM 工作流中一个极重要但尚未被充分探索的环节。本文是一次行动号召——邀请 LLM 研究者和 Hugging Face 开发者社区为营造安全友好的世界协作起来 :)
