# 使用 Diffusers 和 PEFT 实现 Flux 的快速 LoRA 推理

Sayak Paul（sayakpaul）、Benjamin Bossan（BenjaminB）

LoRA 适配器为各种形状的模型提供了大量定制能力。就图像生成而言，它们能让模型获得[不同的风格、不同的人物等等](https://huggingface.co/spaces/multimodalart/flux-lora-the-explorer)。有时它们还能被用来[降低推理延迟](https://huggingface.co/ByteDance/Hyper-SD/)。因此它们的重要性至关重要，尤其是在定制和微调模型时。

在本文里，我们拿用于文本到图像生成的 [Flux.1-Dev 模型](https://huggingface.co/black-forest-labs/FLUX.1-dev)来做示例——因为它广为流行和被采用，以及在使用 LoRA 时如何优化它的推理速度（约 2.3 倍）。在它上面训练了超过 3 万个适配器（[如 Hugging Face Hub 平台上所报告](https://huggingface.co/models?other=base_model:adapter:black-forest-labs/FLUX.1-dev)）。因此它对社区意义重大。

注意，尽管我们用 Flux 演示加速，我们相信我们的方法足够通用，也能应用到其他模型上。

如果你迫不及待想上手代码，请查看配套的[代码仓库](https://github.com/huggingface/lora-fast)。

# 优化 LoRA 推理的障碍

在服务 LoRA 时，常见做法是热交换（把不同 LoRA 换入换出）。一个 LoRA 会改变基座模型的架构。此外，LoRA 之间可以各不相同——每一个都可能有不同的 rank 和不同的、被适配所针对的层。考虑到 LoRA 这些动态特性，我们必须采取必要措施，确保我们所应用的优化足够稳健。

例如，我们可以在一个加载了特定 LoRA 的模型上应用 `torch.compile`，以获得推理延迟上的加速。然而，一旦我们把它换出成另一个 LoRA（可能配置不同），就会遇到重编译问题，导致推理变慢。

有人也可能把 LoRA 参数融合进基座模型参数、运行编译，并在加载新 LoRA 时再解融合。但由于潜在的架构级变更，这种方式同样会在每次运行推理时遇到重编译问题。

我们的优化配方考虑了上面提到的这些情形，尽可能贴近现实。下面是我们优化配方的关键组件：

- Flash Attention 3（FA3）
- `torch.compile`
- 来自 TorchAO 的 FP8 量化
- 热交换就绪（Hotswapping-ready）

注意，上述这些里 FP8 量化是有损的，但常常提供最强的速度-内存权衡。尽管我们主要用 NVIDIA GPU 测试这套配方，它在 AMD GPU 上也应当可用。

# 优化配方

在我们之前的博客（[第 1 篇](https://pytorch.org/blog/presenting-flux-fast-making-flux-go-brrr-on-h100s/)和[第 2 篇](https://pytorch.org/blog/torch-compile-and-diffusers-a-hands-on-guide-to-peak-performance/)）中，我们已经讨论过使用前三个组件的好处。逐个应用它们只需几行代码：

```
from diffusers import DiffusionPipeline, TorchAoConfig
from diffusers.quantizers import PipelineQuantizationConfig
from utils.fa3_processor import FlashFluxAttnProcessor3_0
import torch

# quantize the Flux transformer with FP8
pipe = DiffusionPipeline.from_pretrained(
    "black-forest-labs/FLUX.1-dev",
    torch_dtype=torch.bfloat16,
    quantization_config=PipelineQuantizationConfig(
        quant_mapping={"transformer": TorchAoConfig("float8dq_e4m3_row")}
    )
).to("cuda")

# use Flash-attention 3
pipe.transformer.set_attn_processor(FlashFluxAttnProcessor3_0())

# use torch.compile()
pipe.transformer.compile(fullgraph=True, mode="max-autotune")

# perform inference
pipe_kwargs = {
    "prompt": "A cat holding a sign that says hello world",
    "height": 1024,
    "width": 1024,
    "guidance_scale": 3.5,
    "num_inference_steps": 28,
    "max_sequence_length": 512,
}

# first time will be slower, subsequent runs will be faster
image = pipe(**pipe_kwargs).images[0]
```

*FA3 processor 来自[这里](https://github.com/huggingface/lora-fast/blob/main/utils/fa3_processor.py)。*

当我们试图在不触发重编译的情况下，把 LoRA 换入换出一个已编译的扩散 transformer（`pipe.transformer`）时，问题就开始浮现。

通常，加载和卸载 LoRA 都需要重编译，这会抵消编译带来的任何速度优势。好在有一种方法可以避免重编译。通过传入 `hotswap=True`，diffusers 会保持模型架构不变，只交换 LoRA 适配器自身的权重，这不需要重编译。

```
pipe.enable_lora_hotswap(target_rank=max_rank)
pipe.load_lora_weights(<lora-adapter-name1>)
# compile *after* loading the first LoRA
pipe.transformer.compile(mode="max-autotune", fullgraph=True)
image = pipe(**pipe_kwargs).images[0]
# from this point on, load new LoRAs with `hotswap=True`
pipe.load_lora_weights(<lora-adapter-name2>, hotswap=True)
image = pipe(**pipe_kwargs).images[0]
```

*（提醒一下，第一次调用 `pipe` 会慢，因为 `torch.compile` 是一个即时编译器。不过后续调用应当快得多。）*

这通常允许在不重编译的情况下交换 LoRA，但有局限：

- 我们需要提前提供所有 LoRA 适配器中的最大 rank。因此如果有一个 rank 为 16 的适配器和一个为 32 的，我们需要传 `max_rank=32`。
- 被热交换进来的 LoRA 适配器只能针对第一个 LoRA 所针对的相同层、或其子集。
- 暂不支持针对文本编码器的适配。

关于 Diffusers 中热交换及其局限的更多信息，请访问[文档的热交换一节](https://huggingface.co/docs/diffusers/main/en/tutorials/using_peft_for_inference#hotswapping)。

当我们看不使用"带热交换的编译"时的推理延迟，这套流程的好处就显而易见了。

| 选项 | 时间(s) ⬇️ | 加速（对比基线）⬆️ | 说明 |
| --- | --- | --- | --- |
| baseline | 7.8910 | – | 基线 |
| optimized | 3.5464 | 2.23× | 热交换 + 编译，无重编译卡顿（默认开 FP8） |
| no_fp8 | 4.3520 | 1.81× | 同 optimized，但禁用 FP8 量化 |
| no_fa3 | 4.3020 | 1.84× | 禁用 FA3（flash-attention v3） |
| baseline + compile | 5.0920 | 1.55× | 开编译，但受间歇性重编译停顿影响 |
| no_fa3_fp8 | 5.0850 | 1.55× | 禁用 FA3 和 FP8 |
| no_compile_fp8 | 7.5190 | 1.05× | 禁用 FP8 量化和编译 |
| no_compile | 10.4340 | 0.76× | 禁用编译：最慢的设置 |

**关键要点**：

- "regular + compile" 选项相对 regular 选项提供了不错的加速，但它会引入重编译问题，从而增加总体执行时间。在我们的基准里，我们不展示编译时间。
- 当通过热交换消除重编译问题（即"optimized"选项）时，我们取得最高的加速。
- 在"optimized"选项里，FP8 量化被启用，这可能导致质量损失。即便不用 FP8，我们也能获得可观的加速（"no_fp8"选项）。
- 出于演示目的，我们用一个由两个 LoRA 组成的池来做带编译的热交换。完整代码请参考配套的[代码仓库](https://github.com/huggingface/lora-fast)。

我们迄今讨论的优化配方假设能访问像 H100 这样强大的 GPU。但如果我们只能用像 RTX 4090 这样的消费级 GPU 呢？我们来看看。

# 在消费级 GPU 上做优化后的 LoRA 推理

Flux.1-Dev（不带任何 LoRA）使用 Bfloat16 数据类型运行需要约 33GB 内存。取决于 LoRA 模块的大小，在不用任何优化时，这一内存占用还会进一步增大。许多消费级 GPU 如 RTX 4090 只有 24GB。本节其余部分我们把一台 RTX 4090 机器作为测试平台。

首先，要让 Flux.1-Dev 端到端执行，我们可以应用 CPU 卸载，把执行当前计算不需要的组件卸载到 CPU，腾出更多加速器内存。这样做让我们能在 RTX 4090 上以约 22GB 运行整条 pipeline，用时 **35.403 秒**。启用编译可把延迟降到 **31.205 秒**（1.12 倍加速）。代码上只是几行：

```
pipe = DiffusionPipeline.from_pretrained(
    "black-forest-labs/FLUX.1-dev", torch_dtype=torch.bfloat16,
)
pipe.enable_model_cpu_offload()
# Instead of full compilation, we apply regional compilation
# here to take advantage of `fullgraph=True` and also to reduce
# compilation time. More details can be found here:
# https://hf.co/docs/diffusers/main/en/optimization/fp16#regional-compilation
pipe.transformer.compile_repeated_blocks(fullgraph=True)
image = pipe(**pipe_kwargs).images[0]
```

注意，我们这里没应用 FP8 量化，因为它和 CPU 卸载加编译不兼容（见[支持 issue 讨论](https://github.com/pytorch/pytorch/issues/141548)）。因此，单对 Flux Transformer 应用 FP8 量化也不足以缓解内存耗尽问题。这一回我们决定把它去掉。

因此，要利用 FP8 量化方案，我们需要找到不依赖 CPU 卸载的做法。对 Flux.1-Dev，如果我们额外把量化应用到 T5 文本编码器上，我们应该就能在 24GB 内加载并运行完整 pipeline。下面对比了量化与不量化 T5 文本编码器的结果（[`bitsandbytes`](https://huggingface.co/docs/diffusers/main/en/quantization/bitsandbytes) 的 NF4 量化）。

[![te_quantized_results](https://huggingface.co/datasets/sayakpaul/sample-datasets/resolve/main/lora-fast/image_1_lora_fast.png)](https://huggingface.co/datasets/sayakpaul/sample-datasets/resolve/main/lora-fast/image_1_lora_fast.png)

如我们在上面图中注意到的，量化 T5 文本编码器不会引入太多质量损失。把量化的 T5 文本编码器和 FP8 量化的 Flux Transformer 结合 `torch.compile`，给了我们还算合理的结果——从 32.27 秒降到 **9.668 秒**（约 3.3 倍加速），且没有明显的质量下降。

[![quantized_compiled_results](https://huggingface.co/datasets/sayakpaul/sample-datasets/resolve/main/lora-fast/image_2_lora_fast.png)](https://huggingface.co/datasets/sayakpaul/sample-datasets/resolve/main/lora-fast/image_2_lora_fast.png)

即使不量化 T5 文本编码器，也能用 24GB 显存生成图像，但那会让我们的生成 pipeline 稍微复杂一点。

现在我们有一种方式，可以在 RTX 4090 上用 FP8 量化运行整个 Flux.1-Dev pipeline。我们可以在同一硬件上应用先前建立的优化配方来优化 LoRA 推理。由于 FA3 在 RTX 4090 上不受支持，我们坚持用以下优化配方，并新加入 T5 量化：

- FP8 量化
- `torch.compile`
- 热交换就绪
- T5 量化（用 NF4）

下面表格里，我们展示了应用上述组件不同组合时的推理延迟数字。

| 选项 | 关键参数标志 | 时间(s) ⬇️ | 加速（对比基线）⬆️ |
| --- | --- | --- | --- |
| baseline | `disable_fp8=False disable_compile=True` `quantize_t5=True offload=False` | 23.6060 | – |
| optimized | `disable_fp8=False disable_compile=False` `quantize_t5=True offload=False` | 11.5715 | 2.04× |

**简要说明**：

- 编译相对基线提供了巨大的 2 倍加速。
- 其他选项即便开启了卸载也会 OOM 报错。

## 热交换的技术细节

要启用热交换而不触发重编译，需要迈过两道坎。第一，LoRA 缩放因子必须从浮点数转换为 torch 张量，这很容易做到。第二，LoRA 权重的形状需要 padding 到所需的最大形状。这样就能替换权重里的数据，而不必重新赋值整个属性。这就是上面讨论的 `max_rank` 参数至关重要的原因。因为我们用零来 padding 数值，结果保持不变，尽管计算会因 padding 大小而稍微变慢。

由于不会添加新的 LoRA 属性，这也要求第一个之后的每个 LoRA 只能针对第一个 LoRA 所针对的相同层、或其子集。因此，请明智地选择加载顺序。如果多个 LoRA 针对不相交的层，那可以创建一个针对所有目标层并集的虚拟 LoRA。

要看这个实现的细枝末节，请访问 PEFT 里的 [`hotswap.py` 文件](https://github.com/huggingface/peft/blob/92d65cafa51c829484ad3d95cf71d09de57ff066/src/peft/utils/hotswap.py)。

# 结论

本文勾勒了一套用于 Flux 快速 LoRA 推理的优化配方，展示了显著的加速。我们的方法结合 Flash Attention 3、`torch.compile` 和 FP8 量化，同时确保具备热交换能力而不引入重编译问题。在像 H100 这样的高端 GPU 上，这套优化后的配置相对基线提供了 2.23 倍加速。

对于消费级 GPU，特别是 RTX 4090，我们通过引入 T5 文本编码器量化（NF4）并利用区域编译来应对内存限制。这套完整配方取得了可观的 2.04 倍加速，使 Flux 上的 LoRA 推理即便在有限显存下也切实可行且高效。关键洞见在于：通过审慎地管理编译和量化，LoRA 的好处能够在不同硬件配置上被充分发挥。

希望本文的配方能激励你去优化自己基于 LoRA 的用例，受益于高速推理。
