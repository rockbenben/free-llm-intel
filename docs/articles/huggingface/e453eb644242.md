## 引言

在这篇博客里，我们来看看如何用 PyTorch FSDP 及相关最佳实践微调 Llama 2 70B。我们会用到 Hugging Face Transformers、Accelerate 和 TRL，还会学习如何在 SLURM 中使用 Accelerate。

全分片数据并行（Fully Sharded Data Parallelism，FSDP）是一种将优化器状态、梯度和参数分片到各设备上的范式。前向传播时，每个 FSDP 单元执行一次 *all-gather 操作*拿到完整权重，完成计算后丢弃来自其他设备的分片。前向传播结束后计算损失，再进入反向传播。反向传播时，每个 FSDP 单元同样先 all-gather 拿到完整权重并计算出本地梯度；这些本地梯度通过 *reduce-scatter 操作*在设备间求平均并分片，使每个设备更新自己那份分片的参数。关于 PyTorch FSDP 的更多信息，请参考这篇博客：[Accelerate Large Model Training using PyTorch Fully Sharded Data Parallel](https://huggingface.co/blog/pytorch-fsdp)。

[![FSDP Workflow](https://huggingface.co/blog/assets/62_pytorch_fsdp/FSDP_workflow.png)](https://huggingface.co/blog/assets/62_pytorch_fsdp/FSDP_workflow.png)

（来源：[链接](https://pytorch.org/blog/introducing-pytorch-fully-sharded-data-parallel-api/)）

## 微调 LLaMa 70B 的挑战

我们用 FSDP 微调 LLaMa 70B 时遇到了三个主要挑战：

- FSDP 是在加载预训练模型之后再包装模型的。如果节点内每个进程/rank 都加载 Llama-70B 模型，就需要 70*4*8 GB ≈ 2TB 的 CPU RAM——4 是每个参数的字节数，8 是每个节点的 GPU 数。这会导致 CPU 内存耗尽、进程被杀。
- 用 `FULL_STATE_DICT` 并在 rank 0 上做 CPU 卸载来保存完整的中间 checkpoint 非常耗时，还经常因广播无限挂起而报 NCCL Timeout 错误。但训练结束时，我们确实想要整个模型的 state dict，而不是只有 FSDP 兼容的分片 state dict。
- 我们需要提升速度、降低显存占用，从而更快训练、节省算力成本。

下面看看如何解决这些挑战、把一个 70B 模型微调起来！

## 微调

### 解决挑战 1

PR [huggingface/transformers#25107](https://github.com/huggingface/transformers/pull/25107) 和 [huggingface/accelerate#1777](https://github.com/huggingface/accelerate/pull/1777) 解决了第一个挑战，用户侧无需改任何代码。它做了这些事：

- 在所有 rank 上用 `meta` 设备创建无权重模型。
- 只在 rank==0 上加载 state dict，并用它设置 rank 0 的模型权重。
- 其余 rank 对 `meta` 设备上的每个参数执行 `torch.empty(*param.size(), dtype=dtype)`。
- 于是 rank==0 持有加载了正确 state dict 的模型，其他 rank 是随机权重。
- 设置 `sync_module_states=True`，让 FSDP 对象在训练开始前把它们广播到所有 rank。

### 解决挑战 2

解决办法是在创建 FSDP 配置时选择 `SHARDED_STATE_DICT` 这种 state dict 类型。`SHARDED_STATE_DICT` 为每张 GPU 单独保存分片，这让从中间 checkpoint 保存或恢复训练都很快。而使用 `FULL_STATE_DICT` 时，第一个进程（rank 0）会在 CPU 上收集整个模型，再以标准格式保存。

用下面命令创建 accelerate 配置：

```
accelerate config --config_file "fsdp_config.yaml"
```

[![fsdp_config](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/160_ram_efficient_fsdp/fsdp_config.jpg)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/160_ram_efficient_fsdp/fsdp_config.jpg)

生成的配置文件在这里：[fsdp_config.yaml](https://github.com/pacman100/DHS-LLM-Workshop/blob/main/chat_assistant/training/configs/fsdp_config.yaml)。这里分片策略是 `FULL_SHARD`。自动包装（auto wrap）策略用 `TRANSFORMER_BASED_WRAP`，它借助 `_no_split_module` 找到 Transformer block 名称以便嵌套 FSDP 自动包装。中间 checkpoint 和优化器状态用 `SHARDED_STATE_DICT` 按 PyTorch 团队推荐的格式保存。记得像上一段"解决挑战 1"说的那样，启用训练开始时从 rank 0 广播模块参数。我们启用了 `bf16` 混合精度训练。

关于最终 checkpoint 保存为整个模型 state dict，使用如下代码片段：

```
if trainer.is_fsdp_enabled:
    trainer.accelerator.state.fsdp_plugin.set_state_dict_type("FULL_STATE_DICT")

trainer.save_model(script_args.output_dir) # 或者 trainer.push_to_hub()，前提是完整 ckpt 小于 50GB——Hub 上 LFS 单文件限制是 50GB
```

### 解决挑战 3

要实现更快训练并降低显存占用以支撑微调、节省算力成本，Flash Attention 和梯度检查点（gradient checkpointing）都是必需的。代码库目前使用 monkey patch，实现在 [chat_assistant/training/llama_flash_attn_monkey_patch.py](https://github.com/pacman100/DHS-LLM-Workshop/blob/main/chat_assistant/training/llama_flash_attn_monkey_patch.py)。

[FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness](https://arxiv.org/pdf/2205.14135.pdf) 提出了一种精确计算注意力的方式，同时更快、更省显存——它利用了对底层硬件/GPU 存储层级的认知：内存带宽/速度越高，容量就越小，因为它更贵。

顺着博客 [Making Deep Learning Go Brrrr From First Principles](https://horace.io/brrr_intro.html) 的思路，我们能看出在当前硬件上 `Attention` 模块是`内存受限/带宽受限`的。原因在于注意力**主要由逐元素操作（elementwise operations）构成**，如下左图所示。可以看到，掩码、softmax 和 dropout 这些操作占据了大头时间，而不是贡献大部分 FLOPs 的矩阵乘法。

[![Attention Bottlenecks](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/160_ram_efficient_fsdp/attention_bottleneck.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/160_ram_efficient_fsdp/attention_bottleneck.png)

（来源：[链接](https://arxiv.org/pdf/2205.14135.pdf)）

Flash Attention 解决的正是这个问题。思路是**消除冗余的 HBM 读写**：所有东西留在 SRAM 里，完成全部中间步骤，最后才把结果写回 HBM——也就是所谓的**内核融合（Kernel Fusion）**。下图示意它如何突破内存受限瓶颈。 [![kernel_fusion](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/160_ram_efficient_fsdp/kernel_fusion.webp)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/160_ram_efficient_fsdp/kernel_fusion.webp)

（来源：[链接](https://gordicaleksa.medium.com/eli5-flash-attention-5c44017022ad)）

前向和反向传播中使用**分块（Tiling）**，把 NxN 的 softmax/得分计算切成块，以突破 SRAM 容量限制；为支持分块使用了在线 softmax（online softmax）算法。反向传播中使用**重算（Recomputation）**，避免在前向时保存整个 NxN 的 softmax/得分矩阵，从而大幅降低内存消耗。

想对 Flash Attention 有既简化又深入的理解，请参考博客 [ELI5: FlashAttention](https://gordicaleksa.medium.com/eli5-flash-attention-5c44017022ad) 和 [Making Deep Learning Go Brrrr From First Principles](https://horace.io/brrr_intro.html)，以及原论文 [FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness](https://arxiv.org/pdf/2205.14135.pdf)。

## 把它们串起来

要用 SLURM 配合 `Accelerate` 启动器运行训练，请参考该 gist [launch.slurm](https://gist.github.com/pacman100/1cb1f17b2f1b3139a63b764263e70b25)。下面是等效的 `Accelerate` 启动命令。注意我们覆盖了 `fsdp_config.yaml` 里的 `main_process_ip`、`main_process_port`、`machine_rank`、`num_processes` 和 `num_machines` 取值。另有一个要点：所有节点共享同一存储。

```
accelerate launch \
    --config_file configs/fsdp_config.yaml \
    --main_process_ip $MASTER_ADDR \
    --main_process_port $MASTER_PORT \
    --machine_rank \$MACHINE_RANK \
    --num_processes 16 \
    --num_machines 2 \
    train.py \
    --seed 100 \
    --model_name "meta-llama/Llama-2-70b-chat-hf" \
    --dataset_name "smangrul/code-chat-assistant-v1" \
    --chat_template_format "none" \
    --add_special_tokens False \
    --append_concat_token False \
    --splits "train,test" \
    --max_seq_len 2048 \
    --max_steps 500 \
    --logging_steps 25 \
    --log_level "info" \
    --eval_steps 100 \
    --save_steps 250 \
    --logging_strategy "steps" \
    --evaluation_strategy "steps" \
    --save_strategy "steps" \
    --push_to_hub \
    --hub_private_repo True \
    --hub_strategy "every_save" \
    --bf16 True \
    --packing True \
    --learning_rate 5e-5 \
    --lr_scheduler_type "cosine" \
    --weight_decay 0.01 \
    --warmup_ratio 0.03 \
    --max_grad_norm 1.0 \
    --output_dir "/shared_storage/sourab/experiments/full-finetune-llama-chat-asst" \
    --per_device_train_batch_size 1 \
    --per_device_eval_batch_size 1 \
    --gradient_accumulation_steps 1 \
    --gradient_checkpointing True \
    --use_reentrant False \
    --dataset_text_field "content" \
    --use_flash_attn True \
    --ddp_timeout 5400 \
    --optim paged_adamw_32bit 
```

微调约 13.5 小时完成，下面是训练损失曲线。

## 结论

我们在解决诸多挑战后，成功在多节点多 GPU 环境下用 PyTorch FSDP 微调了 70B 的 Llama 模型。我们看到了 🤗 Transformers 和 🤗 Accelerate 如今支持用更高效的 FSDP 大模型初始化方式，克服 CPU 内存耗尽问题；随后介绍了保存/加载中间 checkpoint 的推荐实践，以及以"拿来就能用"的方式保存最终模型的方法。为实现更快训练并降低 GPU 显存占用，我们强调了 Flash Attention 与梯度检查点的重要性。总而言之，可以看到仅靠 🤗 Accelerate 的一份简单配置，就能让这类超大模型在多节点多 GPU 环境下完成微调。
