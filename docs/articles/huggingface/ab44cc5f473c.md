**TL;DR** — [Falcon Perception](https://huggingface.co/tiiuae/Falcon-Perception) 是一个 **0.6B 参数**的早期融合（early-fusion）Transformer，用于根据自然语言提示词做开放词汇的定位（grounding）与分割。模型在一个序列中同时处理**图像块 + 文本**，使用混合注意力掩码，并以一个小型结构化 token 接口和轻量输出头产出数量可变的实例。在 **SA-Co** 上，Falcon Perception 达到 **68.0 Macro-F1**（SAM 3 为 **62.3**），主要剩余差距在于存在性校准（presence calibration，MCC **0.64** vs **0.82**）。我们还发布了 [**PBench**](https://huggingface.co/datasets/tiiuae/PBench)——一个诊断性基准，按能力维度（属性、OCR 引导消歧、空间约束、关系）以及稠密长上下文拥挤场景拆分性能。

我们同时发布了 [Falcon OCR](https://huggingface.co/tiiuae/Falcon-OCR)，一个 **0.3B 参数**模型，在 olmOCR 基准和 OmniDocBench 上分别拿到 80.3 和 88.6 分，同时是吞吐量最高的开源 OCR 模型。

本文简要、务实地记录我们做了什么、为什么这样设计，以及过程中的收获。

## 问题：为什么感知系统最终都变成了流水线？

许多开放词汇感知系统是按模块化流水线搭的：一个（通常冻结的）视觉骨干抽取特征，独立的融合/解码阶段将其与语言结合，再由额外组件负责匹配与后处理。这一类设计在很多场景下工作得很好，但代价是：难以干净地扩展、难以把改进归因到正确的组件，而且每发现一种失败模式就加一个新补丁，复杂度很容易越堆越高。

我们问了一个更简单的问题：**如果选对注意力模式、输出接口和训练信号，单个早期融合 Transformer 骨干能否同时承担感知与语言建模？**

实验给出的答案基本是"能"。下文介绍主要设计决策及其依据。

## 架构：早期融合、混合注意力与高效的稠密接口

[![falcon_inference](https://cdn-uploads.huggingface.co/production/uploads/69c985bf83862cf48855c45d/kRjlfyqAZxX2LDebkdMWf.gif)](https://cdn-uploads.huggingface.co/production/uploads/69c985bf83862cf48855c45d/kRjlfyqAZxX2LDebkdMWf.gif)

*单个自回归 Transformer 处理由图像块、文本和任务 token 组成的统一序列。模型按固定顺序预测物体属性：`<coord>` → `<size>` → `<seg>`。边界框坐标与尺寸由专用输出头解码，并以傅里叶特征形式重新注入序列。高分辨率分割掩码由 `<seg>` token 与上采样图像特征做点积生成。*

### 一个骨干，两种行为

Falcon Perception 的核心是一个稠密 Transformer，从第一层起就在**共享参数空间**中处理图像块和文本 token。我们没有"独立视觉骨干 + 后期融合解码器"，而是保留单一骨干，依靠掩码和轻量输出接口让稠密预测问题变得可解。

图像和文本的结构不同：像素是二维的，受益于双向上下文；而预测接口天然是顺序的。我们用**混合注意力掩码**解决这一点：

- **图像 token** 对所有其他图像 token **双向**注意，构建全局视觉上下文（类似视觉编码器的做法）。
- **文本与任务 token** 对其之前的一切**因果**注意——完整的视觉前缀加前文文本。

这样同一个骨干在图像 token 上表现得像双向视觉编码器，同时又能在任务 token 上支持自回归预测。

### Chain-of-Perception：面向稠密输出的由粗到细监督

稠密感知不是固定规模的预测问题：一张图里可能有零个实例，也可能有上百个。自回归生成提供了干净的变长接口，但完全自回归的稠密生成（例如逐 token 生成多边形或高分辨率掩码）很快会变得很贵。

我们用一个小型结构化接口 **Chain-of-Perception**，把每个实例分解为三步：

```
<coord> → <size> → <seg>
```

- **坐标 token**：模型先预测实例的中心——确定"说的是哪个物体"。
- **尺寸 token**：然后是空间范围——确定"有多大"。
- **分割 token**：最后是一个嵌入向量，与上采样图像特征做点积即可产出全分辨率二值掩码。

这个顺序是刻意的。先锁定几何信息能减少歧义（"是哪个实例？"），也让掩码预测这一步更接近"在已确定的物体基础上做像素精修"。

### 专用输出头，极低开销

骨干是共享的，解码则使用按输出类型定制的轻量头：

- **坐标与尺寸头**采用**傅里叶特征编码**：通过随机高斯投影把连续坐标映射到高维正弦空间。这克服了神经网络的频谱偏置（spectral bias），比单纯离散分箱定位更精准。解码出的坐标会重新注入序列，作为后续 token 的条件。
- **分割头**计算 `<seg>` token 隐藏状态与内容感知上采样图像特征的**点积**。由于 `<seg>` token 在几何信息之后产生、且能访问早期融合的视觉上下文，我们得以避开基于解码器的实例分割训练里常见的独立 mask-query 机制和匈牙利匹配。

## PBench：为定位"缺什么"而设计的基准

像 RefCOCO 这样的现有指代表达（referring-expression）基准已经饱和——模型轻松达到 90%+——而且混淆了*到底哪里出了错*。模型失败是因为不会读文字？不懂空间关系？还是应付不了人群？

我们发布 **PBench**，一个诊断性基准，按样本所需的主导能力分类：

| 级别 | 能力 | 示例提示词 |
| --- | --- | --- |
| **L0** | 简单物体 | "car" |
| **L1** | 属性与子类 | "red car"、"broken fence" |
| **L2** | OCR 引导识别 | "Diet Coke bottle"、"Nike shoes" |
| **L3** | 空间理解 | "car on the left"、"third window from left" |
| **L4** | 关系与交互 | "person holding umbrella"、"tallest building" |
| **Dense** | 拥挤度压力测试 | 每张图数百个实例 |

每个样本只针对**一种**主导能力：OCR 提示词不带空间限定词，空间提示词不用图内文字消歧。这样得到的是一份能力*画像*而不是单一黑箱分数，也更容易判断下一步该往哪里投入（数据、训练课程，还是后训练）。

## 训练：蒸馏、大规模数据与三阶段配方

### 多教师蒸馏

Falcon Perception 不从随机权重开始训练（消融实验显示那样做分割不稳定），而是通过**多教师蒸馏**初始化。两个强视觉教师提供互补信号：

- **DINOv3**（ViT-H）：分割所需的高质量局部特征
- **SigLIP2**：面向开放词汇理解的语言对齐特征

蒸馏初始化在 ImageNet-1k 上达到 74.25% 零样本准确率、在 Pascal VOC 上达到 85.11% 线性探测 mIoU，在进入感知专项训练之前就打下了扎实的视觉地基。

### 数据：5400 万图像、1.95 亿正样本表达、4.88 亿困难负样本

训练集通过多阶段流水线构建：

- 基于 DINOv3 嵌入对网络抓取图像做**层次聚类**，保证概念覆盖均匀。
- **VLM 驱动的清单生成**为每张图产出稠密的物体描述，并按 PBench 复杂度分级（60% 基础、40% 进阶）。
- **负样本挖掘**生成语义、视觉和细粒度三类困难负样本，对抗幻觉。
- **集成共识**——SAM 3、Qwen3-VL-30B 与 Moondream3 必须一致（IoU > 0.8）才能自动通过。
- **人工核验**——有分歧的样本交给标注员，挽回那些让自动系统困惑的疑难样本。

我们严格保持正负样本 1:1 的比例。这把存在性校准变成一等训练目标：模型不仅要敢于画掩码，更要可靠地说"没有"。

### 三个阶段（总计 700 GT）

**阶段 1——上下文内清单（In-Context Listing，450 GT）：** 模型学习自回归地罗列场景清单——同时预测文本表达*及其*位置。查询之间的全因果注意力让模型学到物体共现（"fork，然后 knife，然后 plate"）。这一步建立广泛的场景理解。

**阶段 2——任务对齐（225 GT）：** 修改注意力掩码，让各查询不能再互相看见，以模拟推理时的独立查询。文本 token 上的损失被 mask 掉，梯度信号全部集中在存在性分类和定位上。这一阶段完成从"理解场景"到"回答这个具体问题"的过渡。

**阶段 3——长上下文微调（10 GT）：** 一个简短阶段，把掩码上限提到每个表达 600，并使用极小的恒定学习率。这让模型适应极端拥挤密度，同时不遗忘之前的能力。

经消融验证的关键设计选择：

- 专用头使用 **Muon 优化器**（对比 AdamW）——SA-Co 检测 +4.8 分
- 实例采用 **Raster 排序**（对比随机/按尺寸）——SA-Co 上比随机排序 +10 分
- **Gram 特征正则**——防止偏离蒸馏特征，分割 +1.5 分
- 跨 rank 的**全局损失归一化**——纠正 FSDP 中变长打包序列带来的偏差

## 结果

### SA-Co：掩码质量同类最佳

在 SA-Co 开放词汇分割基准上，Falcon Perception（0.6B 参数）取得 **68.0 Macro-F1**，SAM 3 为 **62.3**；在属性密集（+8.2）、餐饮食物（+12.2）和运动器材（+4.0）子集上提升显著。同时，Falcon Perception 在存在性校准上落后 SAM 3（MCC：0.64 vs 0.82），这是最明确的待改进维度。

### PBench：随提示词复杂度扩展

早期融合设计的最大差异正体现在这里：

| 能力 | SAM 3 | Falcon Perception | 差距 |
| --- | --- | --- | --- |
| L0：简单物体 | 64.3 | 65.1 | +0.8 |
| L1：属性 | 54.4 | 63.6 | **+9.2** |
| L2：OCR 引导 | 24.6 | 38.0 | **+13.4** |
| L3：空间 | 31.6 | 53.5 | **+21.9** |
| L4：关系 | 33.3 | 49.1 | **+15.8** |
| Dense | 58.4 | 72.6 | **+14.2** |

简单物体上差距不大。随着提示词变得更组合化——需要 OCR 引导消歧、空间约束或关系绑定——差距不断拉大。

在 PBench Dense 子集上，Falcon Perception（0.6B）大幅超越通用 VLM 基线（在我们的评测设置下，72.6 对比 Qwen3-VL-30B 的 8.9），并在空间和关系层级上追平或超过 8B 模型。

#### 定性结果：OCR、空间、关系与稠密场景

随着提示词越来越组合化——需要 OCR 引导消歧、空间约束、关系绑定，或扩展到数百个实例——早期融合的优势在视觉上清晰可见：

- OCR 引导定位（Level 2）：当区分信号是*物体上印刷的文字*时，Falcon Perception 能正确读出来，而 SAM 3 无法区分。
- 空间理解（Level 3）：当提示词指定空间关系时，Falcon Perception 能构建连贯的 2D 场景地图。
- 关系推理（Level 4）：当目标由*交互*而非外观定义时，Falcon Perception 理解场景图。
- 稠密场景：扩展到数百个实例：自回归接口在场景极度拥挤时特别有用——固定查询数量的解码器会先撞上实际上限。

## Falcon OCR：把早期融合扩展到文档理解

现代 OCR 早已超越"从干净扫描件提取文字"。今天的系统必须一次处理多栏排版、数学公式、表格、图表和多语言内容。多数有竞争力的 OCR VLM 用的是熟悉的配方：视觉编码器接一个独立文本解码器，再配上任务专属的粘合模块。这些系统能用，但往往很大（1B–3B+ 参数）。

我们走了不同的路：**复用 Falcon Perception 的同一个早期融合稠密 Transformer**，但从头专门训练一个更小的 **0.3B 参数** OCR 变体。结果就是 **Falcon OCR**——单一骨干，在共享参数空间中处理图像块与文本 token，使用同样的混合注意力掩码（图像 token 双向、文本 token 因果），并且靠提示词而非额外模块来切换任务。

我们选择从零训练（不做多教师蒸馏），因为 OCR 需要的视觉特征——细粒度的字形识别、笔画级区分——与分割需要的物体级特征差别很大。从头开始能让骨干自底向上发展出针对文本优化的表示。

### 训练

我们在一个精挑细选的英文数据混合上训练，覆盖三大核心任务：通用文档文本解析（数字 PDF、老扫描件、打字机文档）、数学与科学公式识别、表格结构识别。混合数据还包含手写体、真实场景文字，以及由 LaTeX 和 HTML 源渲染生成的合成样本。训练目标就是纯粹的结构化文本 next-token prediction。

训练分两个阶段：先以恒定学习率做漫长的**预训练**，让模型学会覆盖所有元素类型的核心 OCR 能力；随后做简短的**余弦衰减微调**，把学习率退火到接近零。

### 基准结果

我们在 **olmOCR**（跨多样输入的二元正确性检查）和 **OmniDocBench**（整页解析上的连续指标）上评测。所有对比模型都明显更大，和/或使用专有基础设施。在仅有 0.3B 参数的情况下，Falcon OCR 在 olmOCR 上拿到 80.3%，与最强系统仅差 1.7 分，并在**多栏排版**（87.1%）和**表格**（90.3%）上领先所有模型。在 OmniDocBench 上综合得分 88.64，超过 DeepSeek OCR v2、GPT 5.2 和 Mistral OCR 3。

### 服务吞吐量

0.3B 参数意味着 Falcon OCR 大约比 0.9B 级别的 OCR VLM **小 3 倍**，这直接转化为更高的服务吞吐量。在单张 A100-80GB 上用 vLLM、高并发场景实测：

| 模式 | tok/s | img/s | 说明 |
| --- | --- | --- | --- |
| **Layout + OCR** | 5,825 | 2.9 | 完整流水线：版面检测 → 裁剪 → 逐区域 OCR |

紧凑的体积加上 vLLM 集成（continuous batching、PagedAttention、优化 CUDA kernel），让它在需要处理数百万页面的大规模文档数字化场景中切实可用。

### 结果说明了什么

更宏观地看，这些结果说明：对于 OCR，"早期融合的单栈 Transformer"是"视觉编码器 + 文本解码器"配方一个可行的替代。一个骨干、一个共享参数空间、一个解码接口——靠更好的数据和训练信号取胜，而不是把流水线越堆越复杂。希望这能鼓励更多朝这个方向的工作。

## 推理：快速、实用、开源

发布内容包含一套基于 **PyTorch FlexAttention** 的推理栈——用它来表达自定义注意力模式、高效服务打包后的变长序列，非常实际。

### Paged 推理引擎

- 带虚拟页表的 **Paged KV cache**（不再有 padding 浪费显存）
- **Continuous batching**：新序列可在生成中途加入，完成的立即释放页
- 解码循环使用 **CUDA graph capture**
- **后台分词**与 GPU 计算重叠
- **HR 特征缓存**：带锁页内存缓冲的 LRU 缓存，用于把上采样图像特征异步在 GPU-CPU 间传输——同一张图的后续查询可跳过昂贵的上采样步骤

在我们的设置下（H100），典型延迟约为：prefill ~100ms、上采样 ~200ms（缓存命中则 0ms）、数个实例的解码 ~50ms。（这些数字取决于分辨率、序列长度和预测实例数量。）

### Falcon-OCR 的 Docker 与 MLX 集成

对于 Falcon-OCR 模型，我们还提供了用于快速部署的 [vLLM docker server](https://huggingface.co/blog/tiiuae/ghcr.io/tiiuae/falcon-ocr:latest)，以及面向 Apple-Silicon 的 [MLX](https://github.com/Blaizzy/mlx-vlm) 集成。

细节请查看 [GitHub 仓库](https://github.com/tiiuae/Falcon-Perception)。

## 更大的图景：感知领域的"Bitter Lesson"

Falcon Perception 是刻意做得极简的：一个骨干、一族目标函数，只在输出是连续、稠密的地方使用小头。我们的工作是建立在这样一个假设上：**大部分收益应来自数据、算力和训练信号**，而不是不断用专门模块去扩张流水线。

这一架构不阻碍任何明显的扩展路径：想要更好的定位，就加更多图像和更难提示词；想要更好的语言能力，就混入纯文本数据；想要应对更密场景，就加长上下文。它始终只是一个序列模型。

*Falcon Perception 由阿联酋阿布扎比技术创新研究所（TII）的 Falcon Vision Team 开发。*
