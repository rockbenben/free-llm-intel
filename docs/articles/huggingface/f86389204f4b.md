# 发布 Outlines-core 0.1.0：Rust 与 Python 中的结构化生成

dottxt 和 Hugging Face 高兴地宣布，我们一直在协作开发 [outlines-core](https://github.com/dottxt-ai/outlines-core)——[outlines](https://github.com/dottxt-ai/outlines) 结构化生成核心算法的 Rust 移植版。除了用 outlines 从 LLM 获得可靠输出，这一 Rust 移植还为用户带来额外好处：

- 速度：用户可预期索引编译获得 2 倍提速。
- 关注点分离：现在更容易把结构化生成融入其他库，`outlines-core` 非常轻量。
- 可移植性：核心算法用 Rust 实现，使其可以绑定到 Python 以外的语言。

这些改进不仅会提升现有 `outlines` 用户的性能，还会极大地拓展用户把结构化生成融入 LLM 工作流的方式。`outlines-core` 现已公开、集成进 `outlines`，Python 绑定的 `0.1.0` 版本也已发布。仓库在[这里](https://github.com/dottxt-ai/outlines-core)。

## 结构化生成快速入门 🧑‍🎓

### 它是如何工作的

结构化生成意味着保证你的 LLM 遵循期望的格式。这可以是 JSON、Pydantic 模型、正则表达式或上下文无关文法。关键在于：结构化生成禁止生成"错误"的 token。

看一个极简例子。LLM 应当生成一个布尔值——"true" 或 "false"，仅此而已。为了便于说明，假设 LLM 逐字符生成而非逐 token。第一个字符是 `"`，我们可以直接跳过前向计算。第二个字符不需要在所有可能字符中采样——LLM 只需在 `t` 或 `f` 之间选择。

![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/outlines-core/graph.png)

在那之后，无论走哪条路径，合法的下一个字符都只有一个。如果 LLM 第二个字符选了 `t`，接下来必须是 `r`、`u`、`e`；选了 `f` 则跟 `a`、`l`、`s`、`e`。最后无论哪条路径都会选择 `"` 作为结尾字符。背后当然还有更多内容，想更深入了解推荐阅读这篇 [dottxt 博客](https://blog.dottxt.co/coalescence.html)和 [arxiv 上的相关论文](https://arxiv.org/abs/2307.09702)。

### 为什么它很重要

你可能一时看不出结构化生成有多惊艳。很多人首先想到的用例是"不错，我的 LLM 现在能返回合法 JSON，我可以把它当 API、可靠地序列化/反序列化 JSON 了"。但这只是冰山一角。仔细想想，结构无处不在，甚至在你最意想不到的地方，比如 [GSM8K 基准](https://blog.dottxt.co/performance-gsm8k.html)。

以下只是结构化生成所能实现的[几个例子](https://dottxt-ai.github.io/outlines/cookbook/)：

- 生成[合成数据](https://dottxt-ai.github.io/outlines/latest/cookbook/dating_profiles/)（还有[与 Distilabel 的集成](https://distilabel.argilla.io/dev/sections/pipeline_samples/examples/llama_cpp_with_outlines/)）
- 从文档和图像中抽取信息。
- 函数[调用/构建 agent](https://blog.dottxt.co/oss-v-gpt4.html)
- [思维链 Chain of Thought](https://dottxt-ai.github.io/outlines/latest/cookbook/chain_of_thought/)
- 确保你的 LLM 输出一个[合法的井字棋棋盘](https://x.com/dottxtai/status/1840826952577421646)
- 甚至[生成虚拟世界！](https://github.com/dottxt-ai/demos/tree/main/lore-generator)

也许更令人惊讶的是，它还能降低评估对[具体所用 prompt](https://huggingface.co/blog/evaluation-structured-outputs)和[few-shot 数量](https://blog.dottxt.co/prompt-efficiency.html)的敏感性。除了结构带给你的这些妙用，它还更快。dottxt 博客有很多带性能基准的好文章。

## 为什么用 Rust 重写？🦀

### 速度

听到"用 Rust 重写"，你首先想到的多半是性能。没错，`outlines-core` 也是如此。仍有几个关键部分尚未迁到 Rust，尽管如此，我们已经看到[编译速度平均提升 2 倍](https://github.com/dottxt-ai/benchmarks)。

在 Rust 移植之前，Outlines 用 Numba 加速索引构建。Numba 虽然快（运行时性能可与 Rust 相比），但 Numba 函数的 JIT 编译在首次运行时增加了延迟，令许多用户抓狂。用 Rust 意味着我们可以提前编译索引构建函数，首次运行零延迟。虽然这在生产场景不重要（首次运行反正可以作为部署的一部分完成），但在实验阶段可能带来巨大差别！

### 安全与可靠

用 Rust 重写 Outlines 的主要原因之一，是 Rust 带来的对安全与可靠的强调。Rust 强大的静态类型加上所有权模型，消除了整类 bug——如空指针解引用和并发代码中的数据竞争。这导向更健壮、更安全的软件。

在 Outlines 的语境中，安全至关重要。结构化生成常涉及复杂数据结构与操作，尤其在面对高性能推理引擎时。借助 Rust 的安全保证，我们降低了内存管理不当导致的运行时错误与未定义行为风险。

此外，Rust 的编译期检查促使开发者编写更干净、更可维护的代码。这既改善了当前代码库，也让未来开发更高效。新贡献者能更快上手，代码也更易审计和验证正确性。

### 关注点分离

Outlines 的设计目标不止于提供结构化生成的核心算法。它还包含对 `transformers` 等其他库的集成，这意味着这个库打包了大量依赖。把核心算法与 Outlines 库分离，意味着想加入结构化生成的其他库只需导入一个非常轻量的库。因此可以预见，`transformers`、`llama-cpp-python` 这类库在不久的将来直接集成结构化生成。这也能让 dottxt 团队专注于核心算法。

### 可移植性

大多数 LLM 训练代码用 Python 编写，但推理略有不同：它发生在各种设备、专用服务器上，并使用多种编程语言。这就是为什么可移植性对结构化生成同样重要。把 `outlines` 的核心功能用 Rust 写就后，我们现在可以为其他语言创建绑定。

例如，这个移植让与 [text-generation-inference](https://github.com/huggingface/text-generation-inference) 的集成顺畅得多。TGI 的服务器逻辑用 Rust 编写，而我们尽可能避免调用 Python 代码。这也意味着像 `mistral.rs` 这样的库或用 [candle](https://github.com/huggingface/candle) 实现的模型都能受益于 Outlines 的性能与能力。

未来我们计划探索 JS/TS 绑定，让 outlines 能用于 transformers-js；或可能的 Swift 绑定，让 outlines 在 Apple 设备上原生可用。但目前的重点是 Python 绑定，并通过扩展对 JSON Schema 规范的支持，让 `outlines-core` 的功能集更加完备。
