# 我们如何为 🤗 API 客户把 transformer 推理提速 100 倍

🤗 Transformers 已成为全球数据科学家探索最先进 NLP 模型、构建新 NLP 功能的默认库。它提供超过 5,000 个预训练和微调模型，覆盖 250 多种语言，是一个丰富的试验场，无论你使用哪个框架都能轻松上手。

虽然在 🤗 Transformers 里试验模型很容易，但把这些大模型以最高性能部署到生产环境，并管理成能随用量扩展的架构，对任何机器学习工程师来说都是一个**艰难的工程挑战**。

正是这 100 倍的性能提升与内建的可扩展性，让我们的托管 [Accelerated Inference API](https://huggingface.co/pricing) 的订阅客户选择在其之上构建自己的 NLP 功能。要拿到**最后那 10 倍的性能**提升，优化必须足够底层、与具体模型以及目标硬件紧密绑定。

本文分享我们为客户榨干每一滴算力的一些做法。🍋

## 拿到第一个 10 倍加速

优化之旅的第一段是最容易触及的，全部围绕与目标硬件无关地、组合使用 [Hugging Face 库](https://github.com/huggingface/)所提供的最佳技术。

我们使用 Hugging Face 模型 [pipelines](https://huggingface.co/transformers/main_classes/pipelines.html) 内建的高效方法，减少每次前向传播中的计算量。这些方法与模型的架构和目标任务具体相关，例如在 GPT 架构上做一次文本生成任务，我们通过聚焦于每轮中最后一个 token 的新注意力，来降低注意力矩阵计算的维度：

分词（Tokenization）往往是推理效率的瓶颈。我们使用 [🤗 Tokenizers](https://github.com/huggingface/tokenizers/) 库中最高效的方法，结合模型分词器的 Rust 实现与智能缓存，将整体延迟最高提速 10 倍。

借助 Hugging Face 库的最新特性，相对于开箱即用的部署，我们在给定的模型/硬件组合上都能稳定实现 10 倍加速。由于 Transformers 和 Tokenizers 通常每月都有新版本发布，API 客户无需不断去适配新的优化机会，他们的模型只会持续跑得更快。

## 编译万岁：难拿的那 10 倍

现在到了真正棘手的地方。为了获得尽可能最佳的性能，我们需要修改模型并针对具体的推理硬件进行编译。硬件本身的选择既取决于模型（内存占用大小），也取决于需求特征（请求批处理）。即使是基于同一个模型提供预测，有些 API 客户更适合从 Accelerated CPU 推理中获益，而有些则更适合 Accelerated GPU 推理，各自应用不同的优化技术和库。

一旦针对用例选定了计算平台，我们就可以开工了。以下是一些可在静态图上应用的 CPU 专属技术：

- 优化计算图（移除未使用的分支）
- 层融合（使用特定的 CPU 指令）
- 量化各种运算

直接调用开源库的开箱函数（例如把 🤗 Transformers 配合 [ONNX Runtime](https://github.com/microsoft/onnxruntime) 使用）不会产生最佳结果，或者可能带来明显的精度损失，尤其是在量化时。没有银弹，最佳路径对每种模型架构都不相同。但深入钻研 Transformers 源码和 ONNX Runtime 文档，就能让各项条件对齐，从而再拿到一个 10 倍加速。

这一趋势给机器学习工程师在部署最新模型到生产环境时带来了令人却步的挑战。虽然 100 倍加速是一个很高的门槛，但要在面向消费者的实时应用中以可接受的延迟提供预测，恰恰就需要这么多。
