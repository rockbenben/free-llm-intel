# 用 Hub Bucket 运送万亿参数：TRL 中的权重增量同步

> TL;DR，因为你知道自己还要训模型，我们尊重这一点：
> 
> 异步 RL 有个不光彩的秘密：每一步，训练器都得把整个模型运给推理引擎。7B 模型以 bf16 算是 14 GB。一个前沿级 1T 模型的 checkpoint 则是 TB 量级。每一步都是如此。
> 结果发现根本不必这样。相邻两个 RL 优化步之间，约 99% 的 bf16 权重逐位相同（最坏情况也不低于 98%）。真正的增量很小。
> 我们落地了一个 TRL PR：只把变化的元素编码成稀疏 safetensors 文件，上传到一个 Hugging Face Bucket，再告诉 vLLM 去取。在 Qwen3-0.6B 上，每步载荷从 1.2 GB 降到 20–35 MB。
> 点睛之笔：我们跑了一次完全分离式训练——训练器在一台机器，vLLM 住在一个 Hugging Face Space，Wordle 环境住在另一个 Space，权重流经一个 Hub bucket。没有共享集群，没有 RDMA，没有 VPN。
> 
> 异步 RL 突然便宜了很多。请往下看。

运送同一份权重的两种方式。红色是没有 token 在生成的墙钟时间。

## 1. 一太字节问题

如果你读过我们上一篇关于[异步 RL 训练版图](https://huggingface.co/blog/async-rl-training-landscape)的文章，已经知道包袱底了。每个异步 RL 库——无论它把 "actor model" 拼成什么、NCCL 后端涂成什么颜色——最后都会绊倒在同一个根子上：**权重同步**。

推理引擎说的是第 N 步的 policy，训练器刚跑完第 N+1 步。新权重必须在推理引擎彻底跑偏到 off-policy 之前从一边送到另一边。无论你跑同步还是异步，这条传输都在关键路径上：一次阻塞的传输就是*白白浪费的空闲算力*——GPU 没在生成 token。有了稀疏增量路径，你把这段空闲压缩到几秒，而且训练器甚至不用等推理引擎就绪：优化步一完成就发布"权重已就绪"、把权重上传到共享 bucket，推理引擎按自己的节奏取。

Fireworks 在他们那篇 [Frontier RL Is Cheaper Than You Think](https://fireworks.ai/blog/frontier-rl-is-cheaper-than-you-think) 里给出了一个令人难忘数字：前沿级 1T 参数 checkpoint 以 fp8（他们的设定），一份完整快照是 **1024 GiB**——按传统说法，你每次更新 rollout 舰队都得运这个量级。这个数字会让人开始画巨型集群、RDMA  fabrics、专线跨区域的架构图。而他们实测相邻 checkpoint 间的平均增量是 **20.3 GiB，占完整模型的 1.98%**，并且"bf16 格式下超过 98% 的权重在相邻 checkpoint 间逐位等价"。

Cursor 的 [Composer 2 报告](https://huggingface.co/papers/2603.24477)讲了个平行故事。他们把训练和推理放在不同区域，用一个**共享 S3 bucket**（原话）缝合：训练器*每个训练步*把压缩后的权重差分上传进去，各集群独立下载、从共享差分链重建，"无需与训练集群直接连通"。两边从不就参数直接对话。bucket 就是那根线。

两篇论文在三件事上是一致的，我们想慢慢重复一遍，因为本文余下的部分基本就是它的忠实开源转译：

- 相邻两个 RL 步之间，大部分权重其实没变。
- 只发送变化部分，带宽账单直接缩大约两个数量级。
- 把这些小差分路由过共享对象存储，训练器和推理集群就不必住在同一个数据中心。

唯一缺的，是一个你能 `pip install` 的版本。于是我们写了一个。

## 2. 为什么 bf16 RL 权重几乎总是稀疏的

在接线之前，值得先弄明白为什么这场游戏可赢。"98% 权重不变"听起来像那种 demo 里成立、实战散架的数字。它不是。它来自 bf16 算术在 RL 所用学习率下的行为方式。

bf16 有 7 位尾数。在两个相邻 2 的幂之间恰好有 2^7 = 128 个可表示值，所以在 ∣w∣ 附近，相邻 bf16 数的间隔约为 ∣w∣⋅2⁻⁷。当一次更新小于*半个*间隔，即 ∣Δw∣ < ∣w∣/256 时，它会被 bf16 的类型转换吸收——这就是 PULSE 论文图 3 画的"bf16 可见阈值"。

再看 Adam 做什么。在 RL 学习率比如 3×10⁻⁶ 下，单个权重的更新是：Δw = −η⋅m̂/(√v̂+ϵ)。

归一化步长 m̂/(√v̂+ϵ) 大致是一阶量，所以 ∣Δw∣ ≈ η ≈ 3×10⁻⁶。对多数权重，∣w∣ 大约在 10⁻² 到 10⁻¹ 之间（PULSE 报告的有代表性 LLM 权重中位数是 0.019）。这个量级下 ∣w∣/256 的阈值约为 4×10⁻⁵ 到 4×10⁻⁴，*大于*更新量。

换句话说：优化器在耳语，bf16 听不见。更新被舍入吸收，w 的字节表示没有变，从推理引擎的角度看这个权重根本没动。乘以几亿个参数，你就免费得到 >99% 的稀疏率，零近似。

这正是 PULSE 论文（[Mihai & Belilovsky, 2026](https://huggingface.co/papers/2602.03839)）形式化的论证。他们定义了两个阈值：**吸收界** 10η 是对 Adam 更新的保守最坏情况，**有效界** η 是你实际所处的区间。**bf16 可见阈值**是 ∣w∣/256。只要更新低于可见阈值，就被吸收，bf16 字节不变。他们的图 3 把两个界画在一片有代表性的 LLM 权重云上，结论毫无歧义：η=3×10⁻⁶ 时，吸收界本身对模型中几乎所有权重已经低于可见阈值。他们在 Qwen2.5（0.5B/1.5B/7B）、Llama-3.2-3B、Gemma-3-4B 上实测，稳定得到每步平均稀疏率 **~99%，400 个训练步内标准差 0.2–0.4%**。最坏的一步也高于 98%。所以"<1% 变化"不是幸运测量，是算术保证。

我们不必用解析方法预测这件事（我们的确试过从 Adam 的 m 和 v 统计量预测变化掩码，召回率惨到 30%，后文详述）。只需要**观察哪些字节翻了**。这是一个每参数一个的小型布尔张量，就在优化步前后算出来。

把学习率拖到 RL 的区间，看回写 bf16 的标记如何贴回原来的刻度。左下 256 格小方阵是一个微型模型上的聚合效果。

## 3. HF Buckets 与架构

故事的第二块在这里进场，本文也在这里不再是对 Fireworks/Cursor 的转译，而变成 Hugging Face 的东西。

### 3.1 什么是 Bucket？

**Bucket** 是 Hub 上为高频对象存储设计的仓库类型。没有 commit 仪式，没有 PR 流程，没有 LFS 的怪癖。你加文件、列文件、下载文件。Python 接口就两个函数：

```
from huggingface_hub import batch_bucket_files, download_bucket_files

# Trainer side
batch_bucket_files("my-org/wordle-deltas", add=[(buffer, "deltas/step_000042.safetensors")])

# Inference side
download_bucket_files("my-org/wordle-deltas", files=[("deltas/step_000042.safetensors", local_path)])
```

就这样。两个函数调用，权重就上路了。

底层，bucket 由 **Xet**——Hub 的内容定义分块存储层——支撑。Xet 看你上传的每个文件，按实际内容（而非固定偏移）切片，并与 bucket 中已有内容去重。在这个语境下有个令人愉悦的实际效果：哪怕我们懒到不写稀疏编码、每步上传完整锚点，Xet 也*仍然*只传输变化的块。稀疏编码 + Xet 叠加：变化的部分我们付一次钱，只付一次。

这就是 Fireworks 和 Cursor 都伸手去拿的"共享 S3 bucket"的开源等价物——只是存储层本来就懂内容哈希，你的 HF token 本来就有权限，而且它与整个栈（Spaces、数据集、模型）天然组合。

### 3.2 三台机器

完整架构恰好三台机器加一个共享底座：

- **训练器。** 随便哪。一块 GPU、八块 GPU、一台插着 USB H100 的笔记本，我们不评判。它拥有模型权重、跑优化器、发出稀疏增量。
- **HF Bucket。** 一个仓库，两个前缀：`anchors/` 存偶尔的完整快照，`deltas/` 存其间的稀疏补丁。这是双方唯一达成共识的东西。
- **vLLM rollout 服务器。** 随便哪——关键是*不必和训练器在一处*。从 bucket 拉取、应用增量、提供 rollouts。
- **环境。** 按常规挂在 rollout 服务器旁边（HTTP、函数调用，环境会说什么都行）。

要内化的性质——Cursor 论文用力推销、在这里逐字成立的那条：**训练器和 rollout 服务器从不就权重互相通信**。它们只交换一个携带 `{"repo_id": ..., "filename": ...}` 的小 POST，这就是整个控制面。真正的字节传输发生在各方与 bucket 之间，并行、无共享网络结构。

为什么这在实践中重要：

- rollout 服务器可以在另一个区域、另一朵云、甚至藏在一个 Hugging Face Space 的 NAT 后面。它无所谓。
- N 个推理副本可以从同一个 bucket 拉同一份增量，Xet 会在所有副本之间去重字节。
- 训练器永远不需要知道存在几个推理副本、在哪里、有没有哪个刚崩了。

训练器写。副本读。Hub 做管道。

## 4. 协议

现在可以打开引擎盖了。协议四部分：一个传输格式、一个 bucket 布局、一个 30 行的 vLLM 扩展、一个训练器侧的变化检测器。老实说代码量没听起来多。

### 4.1 用 Safetensors 做传输格式

我们选 [safetensors](https://github.com/huggingface/safetensors) 作为磁盘和传输格式。它本来就是 Hub 上的标准 checkpoint 格式，所有正经框架都能读它，头部还携带任意字符串元数据。协议就藏在这个元数据字段里。

bucket 里有两种文件。

**锚点（Anchors）**看起来就是普通 checkpoint：每参数一个张量、完整 bf16 权重，每 N 次同步写一份（默认 N=10）。

```
anchors/step_000010.safetensors
  ├── model.layers.0.self_attn.q_proj.weight   (bf16, full)
  ├── model.layers.0.self_attn.k_proj.weight   (bf16, full)
  └── ...
metadata:
  sparse=False, model_version=10, sparsity=0.0
```

**增量（Deltas）**才是有意思的部分。对每个真正变化的参数，存两个条目：一个扁平 int32 的元素索引张量，和一个这些位置上取值的 bf16 张量。

```
deltas/step_000011.safetensors
  ├── model.layers.0.self_attn.q_proj.weight.indices   (int32, [num_changed])
  ├── model.layers.0.self_attn.q_proj.weight.values    (bf16,  [num_changed])
  ├── model.layers.0.mlp.gate_proj.weight.indices
  ├── model.layers.0.mlp.gate_proj.weight.values
  └── ...
metadata:
  sparse=True, model_version=11, sparsity=0.9938, changed_params=[...]
```

这个选择不小的妙处：

- 增量就是*一个文件*。你可以用 Python 的 `safe_open(...)` 打开它、逐个检查张量。没有私有封帧、没有长度前缀、没有版本握手。
- 元数据自描述。接收方读 `sparse=True/False` 然后分支。没有单独的清单。
- 推理侧通过 mmap 零拷贝——当你每几秒做一遍这个时，这很重要。

节奏很简单：每第 N 步一个锚点，其余增量。两者都落在同一个 bucket 的 `anchors/` 和 `deltas/` 前缀下。新的推理副本只需抓最近的锚点，然后重放其后的增量。

十个训练步。第 1 步和第 6 步放锚点（完整快照），其余每步都是稀疏增量。文件在你眼前落进 bucket。

### 4.2 训练器侧：从优化器 hook 得到布尔掩码

训练器需要知道哪些 bf16 元素真的翻了。我们用一个小小的 `BF16ChangeDetector`，在优化器上注册步前/步后 hook：

```
class BF16ChangeDetector:
    def __init__(self, model, optimizer):
        self._pre_step_bf16: dict[str, torch.Tensor] = {}
        self._validated_masks: dict[str, torch.Tensor] = {}
        optimizer.register_step_pre_hook(self._pre_step_hook)
        optimizer.register_step_post_hook(self._post_step_hook)

    def _pre_step_hook(self, opt, args, kwargs):
        for p in self._params:
            self._pre_step_bf16[name_of(p)] = p.detach().to(torch.bfloat16).cpu().clone()

    def _post_step_hook(self, opt, args, kwargs):
        for p in self._params:
            self._validated_masks[name_of(p)] = (
                p.detach().to(torch.bfloat16).cpu() != self._pre_step_bf16[name_of(p)]
            )
```

PR 里的实际代码多了些管道（用 `data_ptr()` 把优化器参数对象对回模型参数，因为 Accelerate 把它们包装成不同的 Python 对象），但思路写在餐巾纸上都够：快照、步进、求差。

这是 ground truth。我们*试过*更优雅的路——直接用 bf16 ULP 阈值从 Adam 的 m 和 v 统计量预测掩码。原理上可行。实际召回率约 30%，意味着我们的增量会漏掉三分之二的真实更新。Adam 的归一化足够乱，解析阈值并不紧。所以我们直接比对字节。代价是训练器侧多一份模型的 bf16 CPU 快照，这个钱我们愿意付。

新 `_sync_weight` 流程的四个阶段：

- **推理照常运行，同时上传。** 训练器把掩码选中的元素编码进 safetensors 缓冲，推到 bucket。这整段时间 vLLM 仍在愉快地服务旧 policy。
- **暂停 vLLM。** 一次短 HTTP 调用，几百毫秒。
- **发信号 `/update_weights`。** 传 bucket 坐标。vLLM 下载、应用、返回。
- **恢复。** vLLM 重新上线。

日志行讲清了故事：

```
Delta: 1234567/200000000 elements changed (sparsity=99.38%)
[delta_engine] uploaded user/wordle-deltas/deltas/step_000042.safetensors (27.4 MB, ...)
Weight sync: done. Total 9.4s (inference paused 1.1s)
```

要紧的是括号里那句。推理只暂停了 **1.1 秒**。其余 9.4 秒花在上传——发生在 rollout 服务器仍在生成 token 的时候。以前用 NCCL，整个同步时长都是暂停时长。现在它只是背景时间。

一次同步的端到端过程。在「bucket 走增量」与「NCCL 广播」之间切换，试试副本数开关看扇出效果。

### 4.3 vLLM 侧：30 行扩展

vLLM 有一个干净的抽象叫 `WeightTransferEngine`。我们实现了一个 `DeltaWeightTransferEngine`，其 `receive_weights` 方法的精神是：

```
def receive_weights(self, update_info, load_weights):
    download_bucket_files(update_info.repo_id, files=[(update_info.filename, local_path)])
    with safe_open(local_path, framework="pt", device="cpu") as f:
        meta = PatchMetadata.from_metadata_dict(f.metadata())
        if not meta.sparse:
            # Anchor: feed every tensor and snapshot for future deltas
            for name in f.keys():
                tensor = f.get_tensor(name)
                self._bf16_snapshot[name] = tensor.clone()
                load_weights([(name, tensor)])
        else:
            # Delta: apply (indices, values) to snapshot, hand full tensor to vLLM
            for name in json.loads(meta.changed_params):
                indices = f.get_tensor(f"{name}.indices").long()
                values = f.get_tensor(f"{name}.values")
                snap = self._bf16_snapshot[name].flatten()
                snap[indices] = values
                self._bf16_snapshot[name] = snap.reshape(self._bf16_snapshot[name].shape)
                load_weights([(name, self._bf16_snapshot[name])])
```

我们通过 vLLM 的 `--worker-extension-cls` 参数注册它，意思是**不需要 fork vLLM**。把 TRL 装进 vLLM 同一镜像，CLI 指向我们的类，就完事了。

值得一提：vLLM 自己也有进行中的工作要把稀疏权重传输原生化，[vllm-project/vllm#40096](https://github.com/vllm-project/vllm/pull/40096)。它在 `WeightTransferEngine` 基类上直接加了 `receive_sparse_weights()` 和 `trainer_send_sparse_weights()`，补丁以 `(indices, values)` 编码、用 `index_copy_()` 原地应用，完全省去 GPU/CPU 校验往返。该 PR 报告在 Qwen3-1.7B 上，一个稀疏补丁传输 **0.16 MB 只花 0.40 ms**，而完整稠密发送是 **942 MB、192 ms**。

对我们推理侧实现的一个诚实提醒：为了从稀疏 `(indices, values)` 补丁重建完整张量，我们在 CPU 上保持了一份模型的 bf16 快照——因为今天 vLLM 的 `load_weights` 要求完整张量。等 [#40096](https://github.com/vllm-project/vllm/pull/40096)（或其继任者）落地、暴露原地的稀疏 `load_weights` 路径，我们就能直接在 GPU 上应用索引、扔掉快照！

## 5. 真的把它架到 Spaces 上

这是我们得意洋洋的部分。前面描述的一切在你笔记本上也能跑，但把权重路由过 Hub bucket 的意义恰恰在于：训练器和 rollout 服务器不必待在彼此附近。于是我们用三台机器跑了一次完全分离式训练，它们互不共享网络：

- 一台带单 GPU 的机器跑**训练器**。
- 一个 **Hugging Face Space**（Docker SDK、L4 GPU）跑带我们扩展类的 **vLLM**。
- 第二个 **Hugging Face Space**（CPU）跑 **Wordle 环境**服务器，支持 256 并发会话。
- 中间一个 **Hub bucket**。

搭建真的就是几个 `hf` CLI 调用。vLLM Space 的 `Dockerfile` 基本就是上游 vLLM 镜像加上 `pip install trl@...` 加上 entrypoint：

```
FROM vllm/vllm-openai:latest
RUN pip install "trl @ git+https://github.com/huggingface/trl.git@delta-weight-sync"
ENV VLLM_SERVER_DEV_MODE=1
EXPOSE 7860
ENTRYPOINT ["vllm", "serve", "Qwen/Qwen3-1.7B", \
    "--host", "0.0.0.0", "--port", "7860", \
    "--worker-extension-cls", "trl.experimental.async_grpo.delta_engine.DeltaWorkerExtension", \
    "--weight-transfer-config", "{\"backend\":\"nccl\"}", \
    "--max-model-len", "32768", \
    "--gpu-memory-utilization", "0.8"]
```

部署为 Space：

```
hf repos create $USER/vllm-wordle-inference \
    --type space --space-sdk docker --flavor l4x1 \
    --secrets HF_TOKEN=$HF_TOKEN
hf upload $USER/vllm-wordle-inference examples/scripts/openenv/vllm_space/ --type space
```

然后从世界上任何能发 HTTPS 的地方启动训练：

```
python examples/scripts/openenv/async_wordle.py \
    --vllm-server-url https://$USER-vllm-wordle-inference.hf.space \
    --env-url https://openenv-wordle.hf.space \
    --delta-sync-repo-id $USER/wordle-deltas \
    --model Qwen/Qwen3-1.7B
```

训练器从不开放端口。Space 从来看不到训练器的 IP。Wordle 环境不知道它们俩的存在。它们全都只和 Hub 说话。训练先通过了 immediate-EOS 的健全性检查，然后在真实的 Wordle rollouts 上收敛：reward 上升，增量载荷稳定在 20–35 MB 区间，每次同步的推理暂停窗口约一秒。完整运行日志见配套 PR 的链接。

## 6. 这到底解锁了什么？

有几件事，而且我们觉得是大事。

**没有集群的异步 RL 训练。** 只要你有一块 GPU 和一个 Hugging Face 账户，现在就能做真正的分离式训练。训练器在 GPU 上，rollout 舰队住在 Spaces 里，环境住在另一个 Space，权重流经一个 bucket。这以前要么需要 colocated 部署（带来一堆吞吐妥协），要么需要一套有共享网络的真实集群。现在都不需要了。

**免费的多副本推理。** 立两个 vLLM Space，或十个。它们都从同一个 bucket 拉取。Xet 的内容寻址存储让相邻锚点在存储层共享数据块（让你的 bucket 不会爆炸），Hub 的边缘缓存让同一文件的重复下载很好服务。想要一个全球分布的 rollout 舰队？那现在是一回小型 DevOps 练习，而不是研究课题。

**一个能用你现有工具调试的传输格式。** 增量就是一个 safetensors 文件。你可以在 notebook 里 `safe_open` 它、列 key、查索引、自己算稀疏度。我们花够了在 tcpdump 里盯着不透明 NCCL 流的夜晚，深知这一点的好。

**一条通往前沿规模的路。** 20–35 MB 是 Qwen3-0.6B 的数字。有意思的是把旋钮拧大之后曲线长什么样。我们做餐巾纸数学。

拿 Llama-3.1-405B 来说。bf16 下磁盘上是 **810 GB**。PULSE 在 RL 学习率下测到每步平均 ~99% 稀疏，所以真实增量约为参数的 1%。他们部署实测的编码是 **7B 模型上 108 MB**，即 PULSE 报告的 **~130×** 缩减。线性外推到 405B，增量落在约 **6 GB/步**。

这在墙钟上买到什么？NCCL 在集群内确实快。假设一个慷慨的 100 GB/s 聚合广播带宽（多节点、RDMA、全套）。完整同步 = `810 GB / 100 GB/s ≈ 8 秒`的推理暂停，每一步。用增量路径，训练器在生成继续运行的同时*后台*流 6 GB 到 bucket，rollout 服务器真正的暂停窗口只剩应用补丁那一步——在这个规模约几秒。所以还没出集群，增量已把可见暂停砍 4 倍、把线上字节砍约 130 倍。

现在离开集群。NCCL 跨云根本不通。一旦你想在 `us-east` 放一支 rollout 舰队、`eu-west` 放一支、也许再来一个 Hugging Face Space，基于 bucket 的路径是*唯一*路径。按 1 GB/s 的可用互联网带宽，一次完整广播要 13 分钟；增量只要 6 秒。

按 Fireworks 口径的 1TB 级模型，他们自己的实测显示 **20.3 GiB 增量对 1024 GiB 完整快照**，约 50× 缩减。PULSE 更紧的稀疏编码会推得更高（外推每份增量约 15 GB，接近 ~65×）。无论如何，你进入了一个区域：通过商品化对象存储运送权重不再是个 hack，而是唯一讲得通的架构。

## 7. 我们桌上还摆着什么

我们不会假装这事做完了。诚实清单如下：

- **两份 CPU bf16 快照，多了一份。** 训练器保留一份（给变化检测器），rollout 服务器保留一份（给 vLLM 的 `load_weights` 重建完整张量）。前者我们只能先背着，直到有人找到紧的解析掩码——这比看起来难。后者等 vLLM 有稀疏 `load_weights` API 就会消失。PR 在路上。
- **固定的锚点节奏。** 目前每 N 步 dump 一个完整锚点。自适应策略（"累计漂移超过 X 时才放锚点"）会在长跑中削减锚点成本。
- **多节点 FSDP2 训练器。** `BF16ChangeDetector` 围绕进程内优化器 hook 构建。它应该能干净地推广到 FSDP2，但我们还没在多节点规模测过。PR 里有个写着我们名字的 `TODO`。
- **挂钩进优化器。** 我们试图只从 (m, v) 预测掩码，召回很低——说明解析的 bf16 阈值做的事比教科书公式微妙得多。谁破解过这个，欢迎告诉我们。
- **与传输压缩叠加。** 稀疏 safetensors 和逐块 gzip 是正交的。我们还没试结合。不过我们也不指望 huge 的压缩收益。
