# FineVideo：幕后花絮

作者：Miquel Farré、Andres Marafioti、Lewis Tunstall、Leandro von Werra、Pedro Cuenca、Thomas Wolf

本文另有中文版本 [简体中文](https://huggingface.co/blog/zh/fine-video)。

开放视频数据集很稀缺，因此拖慢了开源视频 AI 的发展。为此我们构建了 [FineVideo](https://huggingface.co/spaces/HuggingFaceFV/FineVideo-Explorer)——一个包含 4.3 万个视频、总时长 3.4k 小时的数据集，附带丰富的描述、叙事细节、场景切分和 QA 对标注。

FineVideo 收录了高度多样的视频和元数据，是训练视频理解模型、用文本描述生成视频的扩散模型，或以其结构化数据为输入训练计算机视觉模型的好原料。

还没见过 FineVideo？来通过[数据集浏览器页面](https://huggingface.co/spaces/HuggingFaceFV/FineVideo-Explorer)看看。

## 构建原始数据集

旅程始于 [YouTube-Commons](https://huggingface.co/datasets/PleIAs/YouTube-Commons)：一个收录以 CC-By 许可分享的 YouTube 视频语音转录的合集。该项目由 [PleIAs](https://pleias.fr/) 创建和维护，是其语料库收集项目的一部分。

### 下载视频

拿到 190 万个视频的目标清单后，我们成功下载了 180 万个（一些被频道主删除，一些改了权限）。

我们探索了两种分布式下载方案。

**方案 1：Video2dataset**

video2dataset 是一个开源项目（[链接](https://github.com/iejMac/video2dataset)），专注分布式视频下载、转换和打包成不同数据集格式。项目原生支持 Slurm Workload Manager，因此能在我们的 CPU 集群上跑。

（来源：Video2Dataset GitHub 页面）

由于集群所有实例共用同一个公网 IP 访问互联网，我们为该项目贡献了"可指定代理"的功能以便下载视频。该特性还没合并，可以用我们的 PR（[链接](https://github.com/iejMac/video2dataset/pull/350)）给 video2dataset 打上代理能力的补丁。

**方案 2：云批处理任务**

多数云厂商都支持批处理任务：只需定义执行每个任务的实例类型、定义队列、提供包含待执行代码的容器。

我们用 Google Cloud 和 AWS 跑一个自制的 Docker 容器，用 [ytdlp](https://github.com/yt-dlp/yt-dlp) 下载视频和元数据，并把结果推到 S3。

构建该 Docker 容器的文件见[这里](https://github.com/mfarre/fineVideo/tree/main/rawdataset/ytdlps3)。

**我们的结论**

Video2Dataset 配上代理可以工作，还能做额外处理步骤，但走代理的每秒请求数成了瓶颈。这让我们转向云批处理任务。

## 保留动态内容

我们在寻找最好的视频，把选择收窄到"既有画面动作、又有人以中快速度讲话"的内容。实现手段是词密度过滤与视觉动态性过滤。

### 词密度过滤

我们把视频中的词密度当作音频动态性的代理。词密度定义为：

`Word density = Number of words in closed captions / Total video length in seconds`

通过采样并在不同密度阈值下人工评估内容质量，我们决定移除所有词密度低于 0.5 词/秒的视频。

示例：

| **词密度** | **示例** |
| --- | --- |
| 0.25 |  |
| 0.5 |  |
| 0.75 |  |
| 1.0 |  |

按词密度过滤并浏览示例的代码见[这里](https://github.com/mfarre/fineVideo/blob/main/dynamicfilters/worddensityfiltering.py)

### 视觉动态性过滤

我们改造了 FFMPEG 的 [Freezedetect 滤镜](https://ffmpeg.org/ffmpeg-filters.html#freezedetect)来评判视频动态性。这个滤镜本用于识别视频中的冻结片段（多帧相同画面连续排列），但把 `noise` 参数调到非常高的值，也能识别出低运动的片段。

我们没有对整个视频跑 freezedetect，而是按时间分段分析，再根据被判为静态的分段数量投票决定是否算静态视频。经人工评估设定阈值：若分析分段中 40% 低运动，就丢弃该视频。

这一轮过滤后丢弃的几类内容：

| **类型** | **示例** |
| --- | --- |
| 静态图片配音乐 |  |
| 演示文稿录屏 |  |
| 非常静态的对镜头讲话 |  |

按动态性分类视频的 DockerFile 和代码见[这里](https://github.com/mfarre/fineVideo/tree/main/dynamicfilters/videodynamismfiltering)

180 万个视频分析完，这一步后保留 60 万个动态视频。到这一步，我们深入视频内容——这将是保证数据集多样性的关键。

## 视频分类

为了实现多样化的内容选择，我们用隐藏字幕和 YouTube 元数据对过滤后的 60 万个素材做分类。为了掌控分类过程，我们创建了分类体系（taxonomy），并引导标注 adhering（贴合）该体系。

### 自建分类体系

我们用 GPT4-o 自举生成自建分类体系，再由一位信息科学家审校调整。该体系含 126 个细分品类，按多层级聚合。这种多层设计让 FineVideo 用户能按需切片，匹配自己的用例。

[![taxonomy](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/finevideo/taxonomy.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/finevideo/taxonomy.png)

分类体系也提供 JSON 版（[链接](https://github.com/mfarre/fineVideo/blob/main/videocategorization/content_taxonomy.json)）

有了初版分类体系后我们开始内容标注；再结合信息科学家的帮助，根据标注结果反过来调整分类体系。

### 内容标注

我们用通过 Text Generation Inference [TGI](https://github.com/huggingface/text-generation-inference) 服务的 Llama 3.1 70B 给视频分类（[代码](https://github.com/mfarre/fineVideo/tree/main/videocategorization)）。

提示词经过多轮迭代，才确保答案严格是我们体系中的一个类别。在提示词评估中我们发现：从提示里去掉 YouTube 的标签和分类后，结果质量大幅提升——YouTube 的元数据会把 Llama 3.1 生成的文本带偏到 YouTube 提供的某类别上。

```
prompt_template = """
Given those categories: {leaves}
Classify a youtube video given its closed captioning and some metadata details. RETURN ONLY the selected category and nothing else!
Title: {title}
Description: {description}
Channel: {channel}
Closed Caption: {closed_caption}
"""
```

### 分类体系与内容标注的反馈闭环

内容分类过程中对分类体系的调整

信息科学家的职责之一，就是长期维护分类体系：需要时新增类别、或增加额外的区分度。

用 LLM 给内容分类，把调整分类体系的周期从几个月/几年压缩到了几小时。另外，某些情况下我们专门创建类别来丢弃敏感视频，例如落入 `Firearms & Weapons` 和 `Substance Use & Drugs` 的内容。

## 贡献描述性元数据

到这一步，视频级元数据有三个来源：

- 视频类别（用 Llama 3.1 推断）
- YouTube 元数据（标题、描述）
- 来自 YouTube-Commons 的转录

为了推进视频理解领域，我们决定深入到时间码级的元数据——例如活动、物体、叙事和剪辑方面。人工标注我们也考虑过，作为主动学习设置的一部分：一个或多个模型提出标注、人做质检。但如下文所述，Gemini 是个不错的方案，尤其是当我们限制输入视频长度和输出格式时。

### 长视频与 Gemini 1.5 Pro

我们深入研究 Gemini 1.5 Pro，反复迭代提示词并用不同内容长度测试。

它的限制是 1M token，大约相当于约 1 小时视频，我们不得不丢弃超过 1 小时的视频。一个想法是：对超过 1 小时的视频做加速，从而塞进 Gemini 的上下文。

（探索：加速视频以在 Gemini 上下文中装下更多内容）

表面上可行，但细看之后我们发现：只有视频前几分钟被准确标注。

既然长视频质量下滑，我们不禁自问：这个问题是否影响其余视频？通过采样不同长度的视频并检查标注对视频的覆盖度，我们发现超过 10 分钟的视频质量下降。

与我们"把高质量数据带回社区"的目标一致，我们丢弃了 10 分钟以上的视频。

### 内容选择

既然用 Gemini 标注每小时视频成本超过 5 美元，过滤后剩下的视频不可能全标。因此我们要保证所有主题的良好覆盖，在内容多样性（面向后期预训练/微调任务）和预算之间找平衡。我们把规模约束定为 4K 小时视频。

为了从 60 万视频压到 4K 小时，我们准备了一个算法，平衡内容类别、用户参与度和频道代表性，以达到目标时长。

*算法流程图*

### 内容选择算法的几个关键部分：

- **活跃度分数（Activity Score）**：用评论、播放、点赞数按加权组合计算每个视频的参与度指标。这个分数帮助优先选择更受观众欢迎的视频。
- **视频选择**：该步骤迭代选择视频以满足目标时长，同时保证多样性。它在高参与度内容与不同类别、频道的代表性之间平衡，并用惩罚机制避免单一频道占比过高。
- **最终调整**：对选择结果做微调，尽量贴近目标时长且不超出。把已选视频按时长排序，逐个加入最终清单，直到总时长最接近目标值。

代码见仓库（[链接](https://github.com/mfarre/fineVideo/blob/main/contentselection/oracle.py)）。

### 用 Gemini 1.5 Pro 标注并用 GPT4o 做结构化输出

**为什么要结构化数据？**

FineVideo 的目标之一是提供结构化数据来赋能社区：如果你在做多模态 LLM，可以切片数据、决定哪些类别适合你的预训练或微调配比；如果你更偏计算机视觉，可以直接用数据集训练分类器——FineVideo 自带数值型类别，如动态性分数、场景边界、音视频相关性分数。

**结构化数据与 Gemini 1.5**

Gemini 1.5 Pro 支持给定 JSON schema 的输出。我们试了这个特性，很快发现两个问题：

- 我们的 schema 高度复杂，塞不进 Gemini
- 换稍简单的 schema（仍然相当复杂）时，Gemini 的结果质量大幅下降：大多数场景类数据（人物、活动、道具）被丢掉了。我们尝试把提示拆成多个、分别对应 schema 的不同部分，效果也不理想。

我们的观察与其他研究者的经历完全吻合：加上具体的 schema 约束可能降低性能。（[Let Me Speak Freely? A Study on the Impact of Format Restrictions on Performance of Large Language Models](https://huggingface.co/papers/2408.02442)）

我们的方案是：用 Gemini 1.5 生成自由文本，再加一个处理步骤，把 Gemini 的结果对齐到我们的 schema。

我们使用的 Gemini 提示词如下：

```
Study the video and provide the following details about the video and the semantic scenes that compose it:

- characterList: a list of characters that appear in the whole video and a visual description that should allow me to identify them just seeing an image of them.
- scenes: a list of the scenes with the following properties:
  - start/end timestamps of the scene
  - list of all the characters that appear in the scene
  - list of all activities and their timestamps
  - list of all props and their timestamps
  - list of all video editing details and their start/end timestamps. Details include transitions, effects, music as well as suggestions like segments of the scene that could be removed and why 
  - scene mood with notes on how the visuals, audio and context contribute to it. Use the following taxonomy returning only the name in your answer {"moods":{"Positive":[{"name":"Happy","description":"Feeling joyful, content, or delighted."},{"name":"Excited","description":"Feeling enthusiastic, energetic, or eager."},{"name":"Calm","description":"Feeling peaceful, relaxed, or serene."},{"name":"Grateful","description":"Feeling appreciative or thankful."},{"name":"Proud","description":"Feeling satisfied with one's achievements or the achievements of others."}],"Negative":[{"name":"Sad","description":"Feeling down, unhappy, or sorrowful."},{"name":"Angry","description":"Feeling irritated, frustrated, or furious."},{"name":"Anxious","description":"Feeling nervous, worried, or uneasy."},{"name":"Lonely","description":"Feeling isolated, disconnected, or abandoned."},{"name":"Bored","description":"Feeling uninterested, disengaged, or restless."}],"Neutral":[{"name":"Indifferent","description":"Feeling neither particularly positive nor negative."},{"name":"Content","description":"Feeling satisfied but not overly excited."},{"name":"Curious","description":"Feeling interested or inquisitive without strong emotion."},{"name":"Confused","description":"Feeling uncertain or unclear but without strong negative feelings."},{"name":"Pensive","description":"Feeling thoughtful or reflective without strong emotional engagement."}]}}
    - specific  mood changing moments inside the scene, report the timestamp and what we transition from/to in any of the dimensions (visual / auditive)
  - scene narrative progression and plot development
    - specific narrative moments inside the scene. Report the timestamp and what happened
  - character interaction and dynamics descriptions and their start/end timestamps
  - specific thematic elements and descriptions
  - specific relevant happenings to create deeper meanings and subtexts not explicitly stated that contribute to the richness and depth of the content, timestamp and descriptions
  - dynamism score of the scene. Score between 0 and 1. 1 is highly dynamic
  - audio - visual correlation score. Score between 0 and 1. 0 what we see is not correlated with the speech and 1 is highly correlated

- storylines: a list of the different storylines found and which scenes belong to it. 
  - Specify where is the climax (scene and timestamp) and if the content is being presented a narrative story, or is it more like a collection of facts or non-narrative information
  - if there are scenes not matching storylines, explain how those scenes contribute to the video
- looking at the overall video and the storylines, which segments of the video could be trimmed to make it more dynamic?
- q&a: a list of 5 questions/answers about the video that focus on fine details (objects and or activities), overall story reasoning and mood. Focus on Q&A aspects captured on the audio and the video whenever possible difficult to get only by looking at the transcription.
```

**加入 Instructor**

Gemini 处理完结果后，我们用 [Instructor](https://github.com/jxnl/instructor/) 解析：一个基于 Pydantic 的库，给定 schema 就能得到结构化输出。示例见下面的表格对照。

Instructor 让我们能试验不同模型，把 Gemini 的自由文本转成我们在 Pydantic 里定义的 schema。我们试了 Gemini 和 GPT4o，最终选择 GPT4o，因为成功率更高。

## 精细对齐与异常过滤

视频标注完、数据也对齐到 schema 后，我们检查数据的时域，确保它与视频对齐：Gemini 1.5 以每秒 1 帧读视频，而视频帧率常常是 25-29 帧/秒。在精细对齐（Fine Alignment）中，我们确保 Gemini 1.5 给出的场景边界对应到视频中正确的帧。

我们还利用这个时间对齐来丢弃那些 Gemini 停止输出有用数据、导致部分视频被错误标注的情况。注意，得益于管线早前就丢掉了 10 分钟以上的内容，质量差数据的视频数量可以忽略（低于 0.5%）。

精细元数据——把视频场景边界与镜头对齐，作为剔除离群值的机制。
