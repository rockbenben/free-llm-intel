## tl;dr

你是该微调自己的模型，还是用 LLM API？自建模型让你拥有完全控制权，但需要数据采集、训练和部署的专业知识。LLM API 用起来省事得多，却逼你把数据交给第三方，并对 LLM 提供商形成昂贵的依赖。这篇博客展示如何把 LLM 的便利与定制模型的控制力和效率结合起来。

## 1. 问题：你的用例没有数据

想象老板让你给公司做一个情绪分析系统。你会在 Hugging Face Hub 上找到 10 万多个数据集，其中约 450 个标题里带 "sentiment"——覆盖 Twitter 情绪、诗歌情绪、希伯来语情绪等等。这很好，但如果你在一家金融机构工作、需要跟踪组合中特定品牌的情绪，这些数据集一个都用不上。企业可以用机器学习解决的任务有百万种，已经有人恰好为你的公司要解决的那个用例收集并发布了数据，这种事不太可能发生。

面对这种任务级数据和模型的稀缺，很多人转向通用 LLM。这些模型大到足够通用，开箱就能以惊艳的准确率解决大多数任务。它们易用的 API 免去了微调和部署的专业知识。主要缺点是规模和掌控力：数千亿甚至万亿参数让这些模型效率低下，而且只能跑在少数公司掌控的算力集群上。

## 2. 解法：用合成数据教出高效的学生模型

2023 年，一项进展从根本上改变了机器学习版图：LLM 开始追平人类数据标注员。现在有大量证据表明，最好的 LLM 胜过众包工人、在制造高质量（合成）数据上正追平专家（例如 [Zheng et al. 2023](https://arxiv.org/pdf/2306.05685.pdf)、[Gilardi et al. 2023](https://arxiv.org/pdf/2303.15056.pdf)、[He et al. 2023](https://arxiv.org/pdf/2303.16854.pdf)）。这一进展的重要性再怎么强调都不为过。打造定制模型的关键瓶颈，一直是招募和协调人类工人生产定制训练数据所需的金钱、时间和专业知识。随着 LLM 达到人类水平，高质量标注劳动力如今通过 API 即可获得；可复现的标注指令可以作为提示词发送；合成数据几乎即时返回，唯一的瓶颈只剩算力。

2024 年，这条路将具备商业可行性，并放大开源对大小企业的价值。2023 年大部分时间里，把 LLM 商用做标注会被 LLM API 提供商的限制性条款挡住。随着 [Mistral](https://mistral.ai/) 的 [Mixtral-8x7B-Instruct-v0.1](https://huggingface.co/mistralai/Mixtral-8x7B-Instruct-v0.1) 这类模型出现，LLM 标注劳动力和合成数据现在对商用开放了。[Mixtral 的表现与 GPT3.5 相当](https://huggingface.co/spaces/lmsys/chatbot-arena-leaderboard)，而且凭借 Apache 2.0 许可证，它的合成数据输出可以作为训练数据用于商业场景下更小、更专业的模型（"学生"）。这篇博客给出一个实例：这将显著加快你定制模型的产出，同时大幅削减长期推理成本。

## 3. 案例研究：监控金融情绪

假设你是一家大型投资公司开发者，负责监控财经新闻对你投资组合中公司的情绪。在前不久，你只有两个主要选项：

- 自己微调模型。这要写标注说明、搭标注界面、招募（众包）工人、上质检措施来应对低质量数据、在这份数据上微调模型、再部署。
- 或者把你的数据连同样例发给 LLM API。完全跳过微调和部署，把数据分析过程缩减为编写指令（提示词），发给 API 背后的"LLM 标注员"。这种情况下，LLM API 就是你的最终推理方案，LLM 的输出直接用于分析。

选项 2 推理更贵、还要求把敏感数据交给第三方，但搭建比选项 1 容易太多，所以很多开发者都在用。

2024 年，合成数据提供了第三个选项：把选项 1 的成本优势和选项 2 的易用性结合。简单说，用 LLM（"老师"）替你标注一小份样本，再拿这些数据微调一个更小、更高效的 LM（"学生"）。这套方法几步就能落地。

### 3.1 提示 LLM 为你的数据打标

我们用 [financial_phrasebank](https://huggingface.co/datasets/financial_phrasebank) 情绪数据集作贯穿示例，但代码可以改成任何用例。financial_phrasebank 是三分类任务：16 位专家把芬兰公司财经新闻中的句子从投资者视角标成 "positive" / "negative" / "neutral"（[Malo et al. 2013](https://arxiv.org/pdf/1307.5336.pdf)）。例如数据集中有句 "For the last quarter of 2010, Componenta's net sales doubled to EUR131m from EUR76m for the same period a year earlier"，标注员从投资者视角将其分为 "positive"。

接下来我们为 `financial_phrasebank` 任务写一段简短标注说明，并格式化成 LLM 提示词。这相当于平时发给众包工人的说明。

```
prompt_financial_sentiment = """\
You are a highly qualified expert trained to annotate machine learning training data.

Your task is to analyze the sentiment in the TEXT below from an investor perspective and label it with only one the three labels:
positive, negative, or neutral.

Base your label decision only on the TEXT and do not speculate e.g. based on prior knowledge about a company. 

Do not provide any explanations and only respond with one of the labels as one word: negative, positive, or neutral

Examples:
Text: Operating profit increased, from EUR 7m to 9m compared to the previous reporting period.
Label: positive
Text: The company generated net sales of 11.3 million euro this year.
Label: neutral
Text: Profit before taxes decreased to EUR 14m, compared to EUR 19m in the previous period.	
Label: negative

Your TEXT to analyse:
TEXT: {text}
Label: """
```

在把提示词发给 API 之前，还需要加些格式。如今大多数 LLM 都用特定的聊天模板微调过。模板由特殊 token 组成，让 LLM 能区分用户指令、系统提示，以及它在聊天历史里的回复。虽然这里我们不是把模型当聊天机器人用，省略聊天模板仍会悄悄导致性能下降。可以用 `tokenizer` 自动加上模型聊天模板的特殊 token（相关阅读[见这里](https://huggingface.co/blog/chat-templates)）。示例中我们使用 `Mixtral-8x7B-Instruct-v0.1` 模型。

```
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("mistralai/Mixtral-8x7B-Instruct-v0.1")

chat_financial_sentiment = [{"role": "user", "content": prompt_financial_sentiment}]

prompt_financial_sentiment = tokenizer.apply_chat_template(chat_financial_sentiment, tokenize=False)

# The prompt now includes special tokens: '<s>[INST] You are a highly qualified expert ...  [/INST]'
```

格式化后的标注指令（提示词）现在可以传给 LLM API 了。我们使用免费的 Hugging Face [serverless Inference API](https://huggingface.co/docs/api-inference/index)。它很适合测试热门模型。注意：免费 API 由大量用户共享，发太多数据可能遇到限流。大工作负载我们建议创建[专用 Inference Endpoint](https://huggingface.co/docs/inference-endpoints/index)。专用 Inference Endpoint 本质上是你自己的付费专属 API，可以随时开关。

我们用 `huggingface_hub` 库登录，轻松安全地处理 API token。也可以把 token 定义为环境变量（见[文档](https://huggingface.co/docs/huggingface_hub/quick-start#authentication)）。


然后定义一个简单的 `generate_text` 函数，把提示词和数据发给 API。

```
import os
import requests

# Choose your LLM annotator
# to find available LLMs see: https://huggingface.co/docs/huggingface_hub/main/en/package_reference/inference_client#huggingface_hub.InferenceClient.list_deployed_models
API_URL = "https://api-inference.huggingface.co/models/mistralai/Mixtral-8x7B-Instruct-v0.1"

# docs on different parameters: https://huggingface.co/docs/api-inference/detailed_parameters#text-generation-task
generation_params = dict(
    top_p=0.90,
    temperature=0.8,
    max_new_tokens=128,
    return_full_text=False,
    use_cache=False
)

def generate_text(prompt=None, generation_params=None):
    payload = {
        "inputs": prompt, 
        "parameters": {**generation_params}
    }
    response = requests.post(
        API_URL, 
        headers={"Authorization": f"Bearer {huggingface_hub.get_token()}"}, 
        json=payload
    )
    return response.json()[0]["generated_text"]
```

由于 LLM 的输出格式不一定每次都完全统一，我们还定义一个简短的 `clean_output` 函数，把 LLM 的字符串输出映射到三个候选标签。

```
labels = ["positive", "negative", "neutral"]

def clean_output(string, random_choice=True):
    for category in labels:
        if category.lower() in string.lower():
            return category
    # if the output string cannot be mapped to one of the categories, we either return "FAIL" or choose a random label
    if random_choice:
        return random.choice(labels)
    else:
        return "FAIL"
```

现在可以把文本逐条发给 LLM 标注。下面的代码把每条文本发给 LLM API 并把输出映射到三个清洗后的类别。注意：逐条迭代并分别发请求在实践中效率很低。API 可以并发处理多条文本，通过异步发送批次能显著加速。优化后的代码见本文的[复现仓库](https://github.com/MoritzLaurer/synthetic-data-blog/tree/main)。

```
output_simple = []
for text in dataset["sentence"]:
    # add text into the prompt template
    prompt_formatted = prompt_financial_sentiment.format(text=text)
    # send text to API
    output = generate_text(
        prompt=prompt_formatted, generation_params=generation_params
    )
    # clean output
    output_cl = clean_output(output, random_choice=True)
    output_simple.append(output_cl)
```

基于这份输出，我们可以计算指标，看模型在未训练的情况下把任务做对了多少。

```
from sklearn.metrics import classification_report

def compute_metrics(label_experts, label_pred):
    # classification report gives us both aggregate and per-class metrics 
    metrics_report = classification_report(
        label_experts, label_pred, digits=2, output_dict=True, zero_division='warn'
    )
    return metrics_report

label_experts = dataset["label_text"]
label_pred = output_simple

metrics = compute_metrics(label_experts, label_pred)
```

就凭这个简单提示词，LLM 正确分类了 91.6% 的文本（准确率 0.916、F1 macro 0.916）。考虑到它从没为这个特定任务训练过，很不错了。

还可以用两个简单提示技巧进一步提升：思维链（Chain-of-Thought, CoT）和自洽性（Self-Consistency, SC）。CoT 让模型先推理正确标签、再做标签决定，而不是立刻下结论。SC 是把同一个文本连同同一个提示词发给同一个 LLM 多次。SC 相当于给 LLM 每条文本多次不同推理路径的机会：如果它两次答 "positive"、一次答 "neutral"，我们就取多数票（"positive"）作为正确标签。下面是更新后的 CoT+SC 提示词：

```
prompt_financial_sentiment_cot = """\
You are a highly qualified expert trained to annotate machine learning training data.

Your task is to briefly analyze the sentiment in the TEXT below from an investor perspective and then label it with only one the three labels:
positive, negative, neutral.

Base your label decision only on the TEXT and do not speculate e.g. based on prior knowledge about a company. 

You first reason step by step about the correct label and then return your label.

You ALWAYS respond only in the following JSON format: {{"reason": "...", "label": "..."}}
You only respond with one single JSON response. 

Examples:
Text: Operating profit increased, from EUR 7m to 9m compared to the previous reporting period.
JSON response: {{"reason": "An increase in operating profit is positive for investors", "label": "positive"}}
Text: The company generated net sales of 11.3 million euro this year.
JSON response: {{"reason": "The text only mentions financials without indication if they are better or worse than before", "label": "neutral"}}
Text: Profit before taxes decreased to EUR 14m, compared to EUR 19m in the previous period.	
JSON response: {{"reason": "A decrease in profit is negative for investors", "label": "negative"}}

Your TEXT to analyse:
TEXT: {text}
JSON response: """

# we apply the chat template like above
chat_financial_sentiment_cot = [{"role": "user", "content": prompt_financial_sentiment_cot}]
prompt_financial_sentiment_cot = tokenizer.apply_chat_template(chat_financial_sentiment_cot, tokenize=False)
# The prompt now includes special tokens: '<s>[INST] You are a highly qualified expert ...  [/INST]'
```

这是一个 JSON 提示词，我们要求 LLM 返回结构化 JSON 字符串，"reason" 和 "label" 各为一个键。JSON 的主要好处是可以解析成 Python 字典再取 "label"；想看 LLM 为什么选这个标签，也可以把 "reason" 取出来。

`process_output_cot` 函数解析 LLM 返回的 JSON 字符串；如果 LLM 没返回有效 JSON，就退回用前面定义的 `clean_output` 做简单字符串匹配找标签。

```
import ast 

def process_output_cot(output):
    try: 
        output_dic = ast.literal_eval(output) 
        return output_dic
    except Exception as e:
        # if json/dict parse fails, do simple search for occurrence of first label term
        print(f"Parsing failed for output: {output}, Error: {e}")
        output_cl = clean_output(output, random_choice=False)
        output_dic = {"reason": "FAIL", "label": output_cl}
        return output_dic
```

现在可以复用上面的 `generate_text` 函数配新提示词，用 `process_output_cot` 处理 JSON 思维链输出，并且每条提示词多次发送以实现自洽性。

```
self_consistency_iterations = 3

output_cot_multiple = []
for _ in range(self_consistency_iterations):
    output_lst_step = []
    for text in tqdm(dataset["sentence"]):
        prompt_formatted = prompt_financial_sentiment_cot.format(text=text)
        output = generate_text(
            prompt=prompt_formatted, generation_params=generation_params
        )
        output_dic = process_output_cot(output)
        output_lst_step.append(output_dic["label"])

    output_cot_multiple.append(output_lst_step)
```

对每条文本，我们的 LLM 标注员现在各有三次不同推理路径的机会来确定正确标签。下面的代码从三次结果中取多数标签。

```
import pandas as pd
from collections import Counter

def find_majority(row):
    # Count occurrences
    count = Counter(row)
    # Find majority
    majority = count.most_common(1)[0]
    # Check if it's a real majority or if all labels are equally frequent
    if majority[1] > 1:
        return majority[0]
    else: # in case all labels appear with equal frequency
        return random.choice(labels)

df_output = pd.DataFrame(data=output_cot_multiple).T

df_output['label_pred_cot_multiple'] = df_output.apply(find_majority, axis=1)
```

现在可以把改进后的 LLM 标签与专家标签对比并计算指标。

```
label_experts = dataset["label_text"]
label_pred_cot_multiple = df_output['label_pred_cot_multiple']

metrics_cot_multiple = compute_metrics(label_experts, label_pred_cot_multiple)
```

CoT 和 SC 把性能提升到 94.0% 准确率、0.94 F1 macro。通过给模型"思考标签决策的时间"和多次尝试，我们提升了表现。注意 CoT 和 SC 会多花算力——本质上是用算力换标注精度。

### 3.2 把开源模型与闭源模型对比

用开源 Mixtral 造数据的主要优势是：数据完全可以商用、没有法律不确定性。例如，OpenAI API 生成的数据受 [OpenAI 商业条款](https://openai.com/policies/business-terms)约束，明确禁止用模型输出训练与其产品或服务竞争模型。这些条款的法律效力和含义并不明确，但它们给"用 OpenAI 模型的合成数据训练商用模型"引入了法律不确定性。任何基于合成数据训练的小而高效的模型，都可能被视为竞争——因为它降低了对 API 服务的依赖。

Mistral 开源的 `Mixtral-8x7B-Instruct-v0.1` 与 OpenAI 的 GPT3.5、GPT4 相比，合成数据质量如何？我们用 `gpt-3.5-turbo-0613` 和 `gpt-4-0125-preview` 跑了完全相同的管线和提示词，结果在下表中。对这个任务，Mixtral 表现优于 GPT3.5，视提示词类型与 GPT4 持平。（这里不展示更新的 gpt-3.5-turbo-0125 的结果，因为不知为何该模型表现比旧的默认版本 gpt-3.5-turbo-0613 更差。）

这并不意味着 Mixtral 永远胜过 GPT3.5、追平 GPT4——GPT4 在多个基准上仍然更强。关键信息是：开源模型如今已能制造高质量合成数据。

### 3.3 理解并验证你的（合成）数据

这在实践中意味着什么？到目前为止，结果只是某个黑盒 LLM 标出的数据。我们之所以能算指标，是因为示例数据集里有专家标注作参照。在真实场景里没有专家标注时，怎么相信 LLM 的标注？

实践中，不管你用什么标注员（人类还是 LLM），只有亲自验证过的数据才可信。指令/提示词总有一定程度的歧义。即便再聪明的标注员，面对常常有歧义的真实数据也会犯错、也要做模糊判断。

好在过去几年开源工具让数据验证变得容易多了：[Argilla](https://argilla.io/) 提供免费界面来验证和清洗非结构化 LLM 输出；[LabelStudio](https://labelstud.io/) 支持多模态数据标注；[CleanLab](https://cleanlab.ai/) 提供结构化数据的标注与自动清洗界面；简单快速的验证，直接在 Excel 里标标也行。

花点时间亲手标注一些文本、体会数据和其中的歧义，非常必要。你很快就会知道模型犯过哪些错，也会发现若干正确答案本就含糊的例子，还有一些文本你反而更认同 LLM 的判断而不是数据集原作者。这类错误和歧义是数据集制作的常态。事实上，真实任务中人类专家基线能达到 100% 一致性的情况极少。"人类数据是有缺陷的黄金标准"是个老观点，近年被机器学习文献"重新发现"（[Krippendorf 2004](https://books.google.de/books/about/Content_Analysis.html?id=q657o3M3C8cC&redir_esc=y)、[Hosking et al. 2024](https://arxiv.org/pdf/2309.16349.pdf)）。

在标注界面里花了不到一小时，我们加深了对数据的理解并修正了一些错误。不过为了保证可复现性、展示纯合成数据的质量，下一步我们继续使用未清洗的 LLM 标注。

### 3.3 用 AutoTrain 微调你的高效专业模型

到目前为止，这还只是"通过 API 提示 LLM 并验证输出"的标准流程。接下来是带来重大资源节省的一步：在 LLM 的合成数据上微调一个更小、更高效、更专业的 LM。这个过程也叫"蒸馏"（distillation）——用大模型（"老师"）的输出训练小模型（"学生"）。听起来玄，本质就是把数据集里原始的 `text` 拿来、把 LLM 的预测当作微调的 `labels`。如果你训练过分类器就知道，用 `transformers`、`sklearn` 或任何库训练分类器，只需要这两列。

我们用 Hugging Face 的 [AutoTrain](https://huggingface.co/autotrain) 方案让这一步更省事。AutoTrain 是无代码界面：上传带标签的 `.csv`，服务就自动帮你微调出模型。不需要写代码，也不需要深入的微调专业知识。

在 Hugging Face 网站上，先点顶部 "Spaces"，再点 "Create new Space"。选择 "Docker" > "AutoTrain"，挑一块小的 A10G GPU（每小时 $1.05）。AutoTrain 的 Space 会自行初始化。然后通过界面上传合成训练数据和专家测试数据，调整各个字段（如下方截图）。一切填好后点 "Start Training"，在 Space 日志里跟进训练过程。用仅 1811 条数据训练一个小的 RoBERTa-base 模型（约 0.13B 参数）非常快，几分钟就完成。训练结束后模型会自动上传到你的 HF 个人主页。Space 在训练结束后停止，整个过程至多 15 分钟、花费不到 $1。

![autotrain](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/176_synthetic-data-save-costs/autotrain.png)

愿意的话，也可以完全在本地硬件上用 AutoTrain，见[文档](https://huggingface.co/docs/autotrain/index)。高级用户当然尽可以写自己的训练脚本，但用这些默认超参，AutoTrain 的结果对很多分类任务已经够用。

我们产出的微调后约 0.13B 参数 RoBERTa-base 模型，和那些大得多的 LLM 比表现如何？下面的柱状图显示：在 1811 条文本上微调出的定制模型达到 94% 准确率——与它的老师 Mixtral 和 GPT4 一样！小模型开箱永远比不过更大的 LLM，但拿高质量数据微调后，在它专精的任务上就能达到同一水平。

![fig_mixtral_gpt_roberta](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/176_synthetic-data-save-costs/fig_mixtral_gpt_roberta.png)

### 3.4 各方案的利弊

开头讨论的三种方案各自的总利弊是什么：(1) 手工制作自己的数据和模型，(2) 只用 LLM API，(3) 用 LLM API 造合成数据来训练定制模型？下表展示各因素的权衡，下面结合示例数据集讨论具体指标。

![table_pros_cons](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/176_synthetic-data-save-costs/table_pros_cons.png)

先看任务性能。如上所示，定制模型与远大于它的 LLM 打平。微调出的模型只能做我们训练它做的那一件任务，但把它做得很好。要造更多训练数据让模型适应新领域或更复杂任务也轻而易举。多亏 LLM 合成数据，"因缺少专业数据而性能不行"已不再是问题。

第二，算力成本与推理速度。实践中的主要算力成本在推理——模型训练完之后跑它的开销。假设生产用例需要在一段时间内处理 100 万条句子。我们微调后的 RoBERTa-base 模型在小型 T4 GPU（16GB RAM）上高效运行，[Inference Endpoint](https://ui.endpoints.huggingface.co/) 上每小时 $0.6，延迟 0.13 秒，`batch_size=8` 时每秒吞吐 61 句。处理 100 万句总成本 $2.7。

对 GPT 系列可以按 token 计推理成本。处理 100 万句子的 token，GPT3.5 约 $153，GPT4 约 $3061。这些模型的延迟和吞吐更复杂——随时段服务器负载变化。任何用过 GPT4 的人都知道，延迟经常高达数秒还被限流。注意速度快不起来是所有 LLM（含开源 LLM）的通病：很多生成式 LLM 就是大到快不起来。

训练算力成本通常没那么要紧：LLM 常常开箱可用无需微调，小模型的微调成本也相对低（微调 RoBERTa-base 不到 $1）。只有极少数情况需要投入从零预训练。当你要微调一个较大的生成式 LLM 使其专精于某个生成任务时，训练成本才变得重要。

第三，时间与专业知识的投入。这是 LLM API 的最大强项：向 API 发指令，比手工收集数据、微调定制模型并部署要省事得多。而这正是"用 LLM API 造合成数据"变得重要的地方——生产好的训练数据大幅变简单，微调和部署则交给 AutoTrain 和专用 Inference Endpoint 这类服务。

第四，掌控力。这大概是 LLM API 的主要短板。LLM API 从设计上就让你依赖提供商：你得把敏感数据发到别人的服务器，无法控制系统可靠性和速度。训练自己的模型，部署方式和地点由你选。

最后是环境影响。要估算 GPT4 这类闭源模型的能耗和碳排放非常困难——模型架构和硬件信息都是黑箱。我们找到的[最好（也非常粗略）的估计](https://towardsdatascience.com/chatgpts-energy-use-per-query-9383b8654487)认为每次 GPT4 查询耗电约 0.0017 到 0.0026 度。分析 100 万句大约要 1700-2600 度电。按 [EPA CO2 等效计算器](https://www.epa.gov/energy/greenhouse-gas-equivalencies-calculator)，约等于 0.735-1.1 公吨 CO2，相当于普通轿车开 1885-2883 英里。实际排放随 LLM 所在算力区域的能源结构变化很大。而自家模型的估算容易得多：定制模型处理 100 万句在 T4 GPU 上约需 4.52 小时，在 AWS 美东（北弗吉尼亚）服务器上约产生 0.12 kg CO2（见 [ML CO2 Impact 计算器](https://mlco2.github.io/impact/)）。跑一个（号称）8x220B 参数的通用 LLM 如 GPT4，与一个约 0.13B 参数的定制模型相比，是荒谬的低效。

## 结论

我们展示了"用 LLM 造合成数据训练更小更高效模型"的巨大红利。虽然这里只处理了投资者情绪分类，同一管线可以套用到许多其他任务：其他分类任务（如客户意图识别、有害内容检测）、token 分类（如命名实体识别、PII 检测）、生成任务（如摘要、问答）。

2024 年，企业自造高效模型、掌控自己的数据和基础设施、减少碳排放、节省算力和时间而不在精度上妥协，从未如此容易。
