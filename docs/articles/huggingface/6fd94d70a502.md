# 欢迎 OpenAI 全新开源模型家族 GPT OSS！

GPT OSS 是 OpenAI 万众期待的开放权重发布，面向强大推理、智能体（agentic）任务以及多样的开发者使用场景。它包含两个模型：一个 117B 参数的大模型（[gpt-oss-120b](https://hf.co/openai/gpt-oss-120b)）和一个 21B 参数的小模型（[gpt-oss-20b](https://hf.co/openai/gpt-oss-20b)）。两者都是混合专家模型（MoE），并采用 4-bit 量化方案（MXFP4），从而在保持低资源占用的同时实现快速推理（得益于更少的激活参数，细节见下文）。大模型能塞进单块 H100 GPU，小模型则可在 16GB 内存内运行，非常适合消费级硬件和端侧应用。

为了让它对社区更有价值、影响更大，模型采用 **Apache 2.0 许可证**，并附一条极简的使用政策：

> 我们希望我们的工具被安全、负责、大众化地使用，同时把怎么用最大程度上交给你。使用 gpt-oss 即表示你同意遵守所有适用法律。

按 OpenAI 的说法，这次发布是他们对开源生态承诺的重要一步，与其"让 AI 的益处广泛可及"的使命一致。很多场景依赖私有和/或本地部署，我们 Hugging Face 特别高兴欢迎 [OpenAI](https://huggingface.co/openai) 加入社区。我们相信这些模型会长久地启发并影响大家。

## 能力与架构总览

- 总参数 21B 和 117B，*激活*参数分别为 3.6B 和 5.1B。
- 采用 [mxfp4](https://www.opencompute.org/documents/ocp-microscaling-formats-mx-v1-0-spec-final-pdf) 格式的 4-bit 量化方案，仅作用于 MoE 权重。如前所述，120B 可以装进单张 80GB GPU，20B 可以装进单张 16GB GPU。
- 推理（reasoning）、纯文本模型；带思维链和可调的推理努力（reasoning effort）档位。
- 支持指令遵循与工具使用。
- 已有 transformers、vLLM、llama.cpp 和 ollama 的推理实现。
- 推荐使用 [Responses API](https://platform.openai.com/docs/api-reference/responses) 进行推理。
- 许可证：Apache 2.0，附加一条简短的补充使用政策。

**架构**

- token 选择式 MoE，激活函数为 SwiGLU。
- 计算 MoE 权重时，对被选中的专家做 softmax（softmax-after-topk）。
- 每个注意力层使用 RoPE，上下文 128K。
- 注意力层交替：全上下文层与 128 token 滑动窗口层。
- 注意力层使用每头的*学习型 attention sink（注意力汇聚点）*，即在 softmax 分母上附加一个可学习值。
- 与 GPT-4o 及其他 OpenAI API 模型使用同一个 tokenizer。为兼容 Responses API，加入了一些新 token。

（OpenAI GPT OSS 模型的基准测试结果，与 o3 和 o4-mini 对比。来源：OpenAI。）

## 通过 Inference Providers 访问 API

OpenAI GPT OSS 模型可以通过 Hugging Face 的 [Inference Providers](https://huggingface.co/docs/inference-providers/en/index) 服务访问，用同样的 JavaScript 或 Python 代码向任何受支持的提供商发送请求。这正是 OpenAI 在 [gpt-oss.com](http://gpt-oss.com) 上官方 demo 背后的基础设施，你完全可以把它用于自己的项目。

下面是一个用 Python 和超快的 Cerebras 提供商的示例。更多信息和更多代码片段，请看[模型卡中的 inference providers 一节](https://huggingface.co/openai/gpt-oss-120b?inference_api=true&inference_provider=auto&language=python&client=openai)以及我们为这批模型[专门编写的指南](https://huggingface.co/docs/inference-providers/guides/gpt-oss)。

```
import os
from openai import OpenAI

client = OpenAI(
    base_url="https://router.huggingface.co/v1",
    api_key=os.environ["HF_TOKEN"],
)

completion = client.chat.completions.create(
    model="openai/gpt-oss-120b:cerebras",
    messages=[
        {
            "role": "user",
            "content": "How many rs are in the word 'strawberry'?",
        }
    ],
)

print(completion.choices[0].message)
```

Inference Providers 还实现了与 OpenAI 兼容的 Responses API——OpenAI 面向聊天模型最接口的接口，为更灵活直观的交互而设计。
下面是用 Fireworks AI 提供商配合 Responses API 的示例。更多细节请看开源的 [responses.js](https://github.com/huggingface/responses.js) 项目。

```
import os
from openai import OpenAI

client = OpenAI(
    base_url="https://router.huggingface.co/v1",
    api_key=os.getenv("HF_TOKEN"),
)

response = client.responses.create(
    model="openai/gpt-oss-20b:fireworks-ai",
    input="How many rs are in the word 'strawberry'?",
)

print(response)
```

## 本地推理

### 使用 Transformers

你需要安装最新的 `transformers` 版本（v4.55.1 或更高），以及 `accelerate` 和 `kernels`。我们还建议安装 triton 3.4 或更好版本，它能在 CUDA 硬件上解锁 `mxfp4` 量化支持：

```
pip install --upgrade transformers kernels accelerate "triton>=3.4"
```

模型权重以 `mxfp4` 格式量化。该格式原本只在 Hopper 或 Blackwell 系列 GPU 上可用，现在也支持更早的 CUDA 架构（包括 Ada、Ampere 和 Tesla）。安装 triton 3.4 并配合 `kernels` 库，就能在首次使用时下载优化过的 `mxfp4` kernel，大幅节省内存。有了这些组件，你就能在 16GB 显存的 GPU 上跑 20B 模型——包括很多消费级显卡（3090、4090、5080），还有 Colab 和 Kaggle！

如果上述库没装好（或你的 GPU 不兼容），加载模型会回退到 `bfloat16`——从量化权重中解包而来。

下面的代码片段展示 20B 模型的简单推理。如前所述，用 `mxfp4` 时它能在 16GB GPU 上跑，用 `bfloat16` 则需要约 48GB。

```
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "openai/gpt-oss-20b"

tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    device_map="auto",
    torch_dtype="auto",
)

messages = [
    {"role": "user", "content": "How many rs are in the word 'strawberry'?"},
]

inputs = tokenizer.apply_chat_template(
    messages,
    add_generation_prompt=True,
    return_tensors="pt",
    return_dict=True,
).to(model.device)

generated = model.generate(**inputs, max_new_tokens=100)
print(tokenizer.decode(generated[0][inputs["input_ids"].shape[-1]:]))
```

#### Flash Attention 3

这些模型使用了 *attention sinks*，vLLM 团队让这项技术与 Flash Attention 3 兼容。我们把他们的优化 kernel 打包集成进了 [`kernels-community/vllm-flash-attn3`](https://huggingface.co/kernels-community/vllm-flash-attn3)。撰写本文时，这个超快 kernel 已在 Hopper 卡上用 PyTorch 2.7 和 2.8 测试过。预计接下来几天覆盖会进一步扩大。如果你在 Hopper 卡（例如 H100 或 H200）上运行模型，需要先 `pip install --upgrade kernels`，然后在代码里加上这一行：

```
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "openai/gpt-oss-20b"

tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    device_map="auto",
    torch_dtype="auto",
+    # Flash Attention with Sinks
+    attn_implementation="kernels-community/vllm-flash-attn3",
)

messages = [
    {"role": "user", "content": "How many rs are in the word 'strawberry'?"},
]

inputs = tokenizer.apply_chat_template(
    messages,
    add_generation_prompt=True,
    return_tensors="pt",
    return_dict=True,
).to(model.device)

generated = model.generate(**inputs, max_new_tokens=100)
print(tokenizer.decode(generated[0][inputs["input_ids"].shape[-1]:]))
```

这段代码会从 `kernels-community` 下载优化过、预编译的 kernel 代码，正如我们在[上一篇博文](https://huggingface.co/blog/hello-hf-kernels)中解释的那样。transformers 团队已经构建、打包并测试了代码，你可以放心使用。

#### 其他优化

如果你的 GPU 支持 `mxfp4`，我们推荐用它。如果你还能用 Flash Attention 3，那就尽管开！

> 如果你的 GPU 与 mxfp4 不兼容，那我们推荐用 MegaBlocks MoE kernels 来提提速。只需像这样调整你的推理代码：

```
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "openai/gpt-oss-20b"

tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    device_map="auto",
    torch_dtype="auto",
+    # Optimize MoE layers with downloadable` MegaBlocksMoeMLP
+    use_kernels=True,
)

messages = [
    {"role": "user", "content": "How many rs are in the word 'strawberry'?"},
]

inputs = tokenizer.apply_chat_template(
    messages,
    add_generation_prompt=True,
    tokenize=True,
    return_tensors="pt",
    return_dict=True,
).to(model.device)

generated = model.generate(**inputs, max_new_tokens=100)
print(tokenizer.decode(generated[0][inputs["input_ids"].shape[-1]:]))
```

> MegaBlocks 优化 MoE kernel 要求模型跑在 bfloat16 上，所以内存消耗会比 mxfp4 高。我们建议能用 mxfp4 就用，否则通过 use_kernels=True 启用 MegaBlocks。

#### AMD ROCm 支持

OpenAI GPT OSS 已在 AMD Instinct 硬件上通过验证，我们很高兴宣布 kernels 库初步支持 AMD 的 ROCm 平台，为 Transformers 后续推出的 ROCm 优化 kernel 铺路。MegaBlocks MoE kernel 加速已在 AMD Instinct（例如 MI300 系列）上对 OpenAI GPT OSS 可用，带来更好的训练与推理性能。用上面同样的推理代码就能体验。

AMD 还准备了一个 Hugging Face [Space](https://huggingface.co/spaces/amd/gpt-oss-120b-chatbot)，让用户在 AMD 硬件上体验模型。

#### 可用优化汇总

撰写本文时，下表基于 GPU 兼容性和我们的测试总结了我们的*推荐*。预计 Flash Attention 3（带 sink attention）将兼容更多 GPU。

|  | mxfp4 | Flash Attention 3（带 sink attention） | MegaBlocks MoE kernels |
| --- | --- | --- | --- |
| Hopper GPU（H100、H200） | ✅ | ✅ | ❌ |
| 16GB 以上显存的 CUDA GPU | ✅ | ❌ | ❌ |
| 其他 CUDA GPU | ❌ | ❌ | ✅ |
| AMD Instinct（MI3XX） | ❌ | ❌ | ✅ |
| *如何启用* | triton 3.4 + kernels 库 | 使用 kernels-community 的 vllm-flash-attn3 | `use_kernels` |

虽然 120B 模型（用 `mxfp4`）能装进单块 H100，你也可以用 `accelerate` 或 `torchrun` 轻松在多 GPU 上运行它。Transformers 提供了默认的并行化方案，而且你同样能用上优化的注意力 kernel。以下代码片段可以在 4 GPU 的系统上用 `torchrun --nproc_per_node=4 generate.py` 运行：

```
from transformers import AutoModelForCausalLM, AutoTokenizer
from transformers.distributed import DistributedConfig
import torch

model_path = "openai/gpt-oss-120b"
tokenizer = AutoTokenizer.from_pretrained(model_path, padding_side="left")

device_map = {
    "tp_plan": "auto",    # Enable Tensor Parallelism
}

model = AutoModelForCausalLM.from_pretrained(
    model_path,
    torch_dtype="auto",
    attn_implementation="kernels-community/vllm-flash-attn3",
    **device_map,
)

messages = [
     {"role": "user", "content": "Explain how expert parallelism works in large language models."}
]

inputs = tokenizer.apply_chat_template(
    messages,
    add_generation_prompt=True,
    return_tensors="pt",
    return_dict=True,
).to(model.device)

outputs = model.generate(**inputs, max_new_tokens=1000)

# Decode and print
response = tokenizer.decode(outputs[0])
print("Model response:", response.split("<|channel|>final<|message|>")[-1].strip())
```

OpenAI GPT OSS 模型经过了大量训练以在其推理过程中利用工具使用。我们为 transformers 打造的对话模板提供了很多灵活性，请看[本文后文的专门章节](https://huggingface.co/blog/welcome-openai-gpt-oss#tool-use-with-transformers)。

### Llama.cpp

Llama.cpp 自 day-0 发布起就原生支持带 Flash Attention 的 MXFP4，在 Metal、CUDA、Vulkan 等各种后端上提供最佳性能。

安装方法参见 [llama.cpp GitHub 仓库](https://github.com/ggml-org/llama.cpp/blob/master/docs/install.md)的指南。

```
# MacOS
brew install llama.cpp

# Windows
winget install llama.cpp
```

推荐通过 llama-server 使用：

```
llama-server -hf ggml-org/gpt-oss-120b-GGUF -c 0 -fa --jinja --reasoning-format none

# Then, access http://localhost:8080
```

### vLLM

如前所述，vLLM 开发了支持 sink attention 的优化 Flash Attention 3 kernels，所以在 Hopper 卡上效果最好。Chat Completion 和 Responses API 都支持。可以用以下代码安装并启动服务器（假定使用 2 块 H100 GPU）：

```
vllm serve openai/gpt-oss-120b --tensor-parallel-size 2
```

或者在 Python 里直接使用：

```
from vllm import LLM
llm = LLM("openai/gpt-oss-120b", tensor_parallel_size=2)
output = llm.generate("San Francisco is a")
```

## 评估模型

GPT OSS 是推理模型：因此评估时所需的生成长度（最大新 token 数）很大，因为生成内容会先包含推理、再是最终回答。生成长度设得太小有风险把预测拦腰截断在推理中途，造成假阴性。计算指标前还应把推理轨迹从模型回答中移除，以避免解析错误，尤其在数学或指令遵循（instruct）评测中。

下面是用 lighteval 评估模型的示例（需要从源码安装）。

```
git clone https://github.com/huggingface/lighteval
pip install -e .[dev] # make sure you have the correct transformers version installed!
lighteval accelerate \
    "model_name=openai/gpt-oss-20b,max_length=16384,skip_special_tokens=False,generation_parameters={temperature:1,top_p:1,top_k:40,min_p:0,max_new_tokens:16384}" \ 
    "extended|ifeval|0|0,lighteval|aime25|0|0" \
    --save-details --output-dir "openai_scores" \
    --remove-reasoning-tags --reasoning-tags="[('<|channel|>analysis<|message|>','<|end|><|start|>assistant<|channel|>final<|message|>')]" 
```

对 20B 模型，这应该给出 IFEval（strict prompt）69.5（±1.9）、AIME25（pass@1）63.3（±8.9）——对这一规模的推理模型来说都在预期区间内。

如果你想自己写评估脚本，注意要正确过滤推理标签，需在 tokenizer 中使用 `skip_special_tokens=False`，以便拿到模型输出的完整轨迹（然后用与上面示例相同的字符串对来过滤推理）——原因下文就会揭晓。

## 对话与对话模板

OpenAI GPT OSS 在输出中使用"channel（通道）"的概念。大多数时候，你会看到一个"analysis"通道，装着不打算发给终端用户的内容（比如思维链），以及一个"final"通道，装着真正要展示给用户的信息。

假设没有使用工具，模型输出的结构看起来像这样：

```
<|start|>assistant<|channel|>analysis<|message|>CHAIN_OF_THOUGHT<|end|><|start|>assistant<|channel|>final<|message|>ACTUAL_MESSAGE
```

大多数时候，除 **<|channel|>final<|message|> 之后的文本，其他都该忽略。只有这段文本应该作为助手消息追加到对话中，或展示给用户。这条规则有两个例外：**训练**时你可能需要把 **analysis** 消息保留在历史里；或者当模型**调用外部工具时**。

**训练时**：如果你在构造训练样本，通常希望把思维链放进最终消息。正确的做法是用 **thinking** 键。

```
chat = [
    {"role": "user", "content": "Hi there!"},
    {"role": "assistant", "content": "Hello!"},
    {"role": "user", "content": "Can you think about this one?"},
    {"role": "assistant", "thinking": "Thinking real hard...", "content": "Okay!"}
]

# add_generation_prompt=False is generally only used in training, not inference
inputs = tokenizer.apply_chat_template(chat, add_generation_prompt=False)
```

在早期轮次或推理（而非训练）时，你尽可以带上 **thinking** 键，但它们通常会被忽略。对话模板只会纳入最近一次思维链，而且仅在训练时（`add_generation_prompt=False` 且最后一轮是 assistant 轮）。

我们这么做的原因有点微妙：OpenAI gpt-oss 模型是在多轮数据上训练的，其中除最后一条以外的思维链都被丢弃了。这意味着当你要微调一个 OpenAI `gpt-oss` 模型时，也应该照此办理。

- 让对话模板丢弃除最后一条外的所有思维链
- 对除最后一个 assistant 轮以外的所有轮次屏蔽（mask）标签，否则你会在没有思维链的历史轮次上训练它，教它输出不带 CoT 的回答。这意味着不能把整段多轮对话当成一个样本训练；而要拆成每个 assistant 轮一个样本，每次只保留最后一个 assistant 轮不被屏蔽，让模型能从每一轮学习，同时每次都只在最后一条消息上看到思维链。

### System 与 Developer 消息

OpenAI GPT OSS 很特别：它区分对话开头的"system"消息和"developer"消息，而大多数其他模型只有"system"。在 GPT OSS 中，system 消息遵循严格的格式，包含当前日期、模型身份、应使用的推理努力档位等信息；"developer"消息更自由，这使得它（非常令人困惑地）类似于其他模型的"system"消息。

为了让 GPT OSS 更贴合标准 API 的使用习惯，对话模板会把 "system" 或 "developer" 角色的消息当作 **developer** 消息处理。如果你想修改真正的 system 消息，可以给对话模板传 **model_identity** 或 **reasoning_effort** 这两个特定参数：

```
chat = [
    {"role": "system", "content": "This will actually become a developer message!"}
]

tokenizer.apply_chat_template(
    chat, 
    model_identity="You are OpenAI GPT OSS.",
    reasoning_effort="high"  # Defaults to "medium", but also accepts "high" and "low"
)
```

### 在 transformers 中使用工具

GPT OSS 支持两类工具：**内置（builtin）**工具 **browser** 和 **python**，以及用户自定义工具。要启用内置工具，把名字以列表形式传给对话模板的 **builtin_tools** 参数，如下所示。要传自定义工具，既可以用 JSON schema，也可以用带类型提示和 docstring 的 Python 函数，通过 tools 参数传入。详见[对话模板工具文档](https://huggingface.co/docs/transformers/en/chat_extras)，或者直接改下面的示例：

```
def get_current_weather(location: str):
    """
    Returns the current weather status at a given location as a string.

    Args:
        location: The location to get the weather for.
    """
    return "Terrestrial."  # We never said this was a good weather tool

chat = [
    {"role": "user", "content": "What's the weather in Paris right now?"}
]

inputs = tokenizer.apply_chat_template(
    chat, 
    tools=[weather_tool], 
    builtin_tools=["browser", "python"],
    add_generation_prompt=True,
    return_tensors="pt"
)
```

如果模型选择调用某个工具（以 `<|call|>` 结尾的消息为标志），你应该把这次工具调用加入对话、执行工具、把工具结果加入对话，然后重新生成：

```
tool_call_message = {
    "role": "assistant",
    "tool_calls": [
        {
            "type": "function",
            "function": {
                "name": "get_current_temperature", 
                "arguments": {"location": "Paris, France"}
            }
        }
    ]
}
chat.append(tool_call_message)

tool_output = get_current_weather("Paris, France")

tool_result_message = {
    # Because GPT OSS only calls one tool at a time, we don't
    # need any extra metadata in the tool message! The template can
    # figure out that this result is from the most recent tool call.
    "role": "tool",
    "content": tool_output
}
chat.append(tool_result_message)

# You can now apply_chat_template() and generate() again, and the model can use
# the tool result in conversation.
```
