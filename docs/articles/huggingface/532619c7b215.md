# 通过键值缓存量化解锁更长的生成

Raushan Turganbay (RaushanTurganbay)

在 Hugging Face，我们很高兴向大家分享一个能把语言模型带上新台阶的新特性：*KV Cache 量化（键值缓存量化）*。

TL;DR：KV Cache 量化能在对质量影响极小的情况下，降低 LLM 长上下文文本生成的内存占用，并提供内存效率与生成速度之间可定制的权衡。

你有没有试过让语言模型生成一篇长文，结果被讨厌的内存限制卡住？随着语言模型越来越大、能力越来越强，支持更长的生成开始吃掉大量内存。这是常见的痛点，尤其在资源有限的时候。这时 KV cache 量化就来救场了。

那么 KV cache 量化到底是什么？不熟悉这个词也没关系！我们把它拆成两块：*kv cache* 和 *量化*。

键值缓存（key-value cache，kv cache）是优化自回归模型生成所必需的——这类模型逐个 token 预测文本。这个过程可能很慢，因为模型一次只能生成一个 token，且每个新预测都依赖之前的上下文。也就是说，要生成第 1000 个 token，你需要前面 999 个 token 的信息——这表现为对这些 token 表示做一系列矩阵乘法。而要生成第 1001 个 token，除了前 999 个 token 的同样信息，还需要第 1000 个 token 的额外信息。KV cache 正是用来优化这一顺序生成过程的：保存之前的计算结果供后续 token 复用，避免重新计算。

更具体地说，KV cache 相当于自回归生成模型的"记忆库"：模型保存自注意力层为此前处理过的 token 计算出的键值对。在 transformer 架构中，自注意力层通过 query 乘 key 计算注意力分数，再对 value 向量加权求和得到输出。保存这些信息后，模型就能避免冗余计算，直接从缓存里取回之前 token 的 key 和 value。要直观理解这个概念，可以看看下图如何展示 KV cache 的工作方式。计算第 `K+1` 个 token 的注意力分数时，我们不必重算之前所有的 key 和 value，而是从缓存取出、与当前向量拼接。这通常让文本生成更快、更高效。

再说第二个词：量化不过是"降低数值精度以节省内存"的花哨说法。量化时每个数值会被舍入或截断到更低的精度格式里，可能带来信息损失。不过仔细选择量化参数和技术，可以把损失压到很小，仍取得令人满意的表现。量化方法有很多种，想深入了解可以读我们之前的[博客](https://huggingface.co/blog/4bit-transformers-bitsandbytes)。

虽然 kv cache 加速了自回归生成，但在长上下文或大 batch 下它会成为内存瓶颈。让我们估算一下：对一个 7B 的 Llama-2 模型，为长度 10000 token 的输入保存 kv cache 需要多少内存。单个 token 的 kv cache 内存大约是 `2 * 2 * num_layers * num_key_value_heads * head_dim`——第一个 `2` 是 key 和 value，第二个 `2` 是所需字节数（假设模型以 `float16` 加载）。所以 10000 token 的上下文需要

`2 * 2 * 32 * 32 * 128 * 10000 ≈ 5GB`

的内存只用来存键值缓存——几乎是以半精度存模型参数所需内存的三分之一。

因此，把 kv cache 压缩成更紧凑的形式可以省下大量内存，让我们在消费级 GPU 上跑更长上下文的生成。实验中，我们通过把 kv cache 量化到更低精度格式，在不过多牺牲质量的前提下显著降低了内存占用。有了这个量化新特性，我们可以支持更长的生成而不耗尽内存——意味着你可以放大模型的上下文长度，不用担心撞上内存约束。

## 实现细节

Transformers 中的键值缓存量化很大程度上受 [KIVI: A Tuning-Free Asymmetric 2bit Quantization for kv Cache](https://arxiv.org/abs/2402.02750) 论文启发。该论文为大语言模型提出了不降质量的 2bit 非对称量化。KIVI 对 key 缓存按通道（per-channel）量化、对 value 缓存按 token 量化——因为他们证明对 LLM 而言，key 在部分通道上有更大的离群值幅度，而 value 没有这种模式。所以 key 按通道、value 按 token 量化时，量化精度与原始精度之间的相对误差更小。

在我们集成进 Transformers 的方法里，key 和 value 都按 token 量化。按 token 量化的主要瓶颈是：每加入一个新 token（即每个生成步）都要重新量化/反量化 key 和 value，可能拖慢生成。为了克服这一点，我们保留一个固定大小的残差缓存（residual cache），以原始精度存 key 和 value。当残差缓存达到容量上限时，把其中存的 key 和 value 量化并丢弃缓存内容。这个小技巧也有助于保持精度——最近的一部分 key/value 始终以原始精度保存。主要考量是设定残差缓存长度时内存与效率的权衡：残差缓存以原始精度存数据，可能推高总体内存占用。我们发现残差长度取 128 作为基线效果不错。

具体来说，给定形状为 `batch size, num of heads, num of tokens, head dim` 的 key 或 value，我们把它分组为 `num of groups, group size`，然后做仿射量化：

`X_Q = round(X / S) - Z`

其中，

- X_Q 是量化后的张量
- S 是 scale，计算方式 `(maxX - minX) / (max_val_for_precision - min_val_for_precision)`
- Z 是 zeropoint，计算方式 `round(-minX / S)`

目前 kv 量化支持 [quanto](https://github.com/huggingface/quanto) 后端的 `int2` 和 `int4` 精度，以及 [`HQQ`](https://github.com/mobiusml/hqq/tree/master) 后端的 `int2`、`int4` 和 `int8` 精度。关于 `quanto` 的信息见之前的[博客](https://huggingface.co/blog/quanto-introduction)。虽然我们暂不支持更多量化后端，但欢迎社区贡献来集成它们——特别是那些无需校准数据、可以动态即时计算低比特张量的量化方法，很容易接进来。另外，你可以在 config 里指定常用的量化参数，从而自由调整量化过程，例如根据你的场景决定做按通道还是按 token 量化。

## fp16 与量化 cache 的性能对比

视觉胜于言语，我们准备了一些对比图，直观展示量化与 FP16 精度的差距——看看调整 kv cache 精度设置后模型生成质量的表现。我们用以下量化参数计算了 [Llama2-7b-chat](https://huggingface.co/meta-llama/Llama-2-7b-chat-hf) 模型在 [`PG-19`](https://huggingface.co/datasets/emozilla/pg19-test) 数据集上的困惑度：`nbits=4, group_size=64, resildual_length=128, per_token=True`

可以看到，`int4` cache 在两种后端上的表现都与原始 `fp16` 精度几乎一致，而使用 `int2` 时质量会有所下降。复现结果的脚本在[这里](https://gist.github.com/zucchini-nlp/a7b19ec32f8c402761d48f3736eac808)。

在 [LongBench](https://huggingface.co/datasets/THUDM/LongBench) 基准上计算性能并与 KIVI 论文结果对比后，结论相同。`Int4 quanto` 的精度与 `fp16` 相当，甚至在下表所有数据集上略胜一筹（越高越好）。

| 数据集 | KIVI f16p | KIVI int2 | Transformers fp16 | Quanto int4 | Quanto int2 |
| --- | --- | --- | --- | --- | --- |
| TREC | 63.0 | 67.5 | 63.0 | 63.0 | 55.0 |
| SAMSum | 41.12 | 42.18 | 41.12 | 41.3 | 14.04 |
| TriviaQA | NA | NA | 84.28 | 84.76 | 63.64 |
| HotPotQA | NA | NA | 30.08 | 30.04 | 17.3 |
| Passage_retrieval_en | NA | NA | 8.5 | 9.5 | 4.82 |

再谈谈内存节省与速度之间的取舍。把模型的 kv cache 量化后，内存需求更小，但有时要付出一点生成速度的代价。把 cache 量化到 `int4` 大约能带来 2.5 倍的内存节省，但 batch size 越大，生成速度越低。你得自己决定：用量化 kv cache、可能牺牲一点速度，换可观的内存效率提升是否值得。一切都取决于找到最适合你场景与优先级的方案。

想知道把权重量化也加进来会怎样？当然，两项技术结合可以进一步瘦身模型的内存占用，但也有坑——可能让速度更慢。实际上我们的实验显示，权重量化与 kv cache 量化叠加会导致速度降至三分之一。不过我们一直在琢磨让这套组合丝滑运行的办法。虽然 `quanto` 库中目前没有优化过的 kernel，但我们欢迎社区贡献来提升计算效率。我们的目标是让你的模型跑顺畅，同时保持高延迟表现（低延迟）和高精度。

另外值得注意：对输入 prompt 的初次处理（即 pre-fill 阶段）仍需要一次性算出整个输入的键值矩阵，对长上下文来说是另一个内存瓶颈。这就是生成第一个 token 的延迟往往高于后续 token 的原因。还有别的策略可以通过优化注意力计算阶段来降低 pre-fill 阶段的内存负担，例如 [Local Windowed Attention](https://arxiv.org/abs/2004.05150) 或 [Flash-Attention](https://arxiv.org/abs/2307.08691)。如果 pre-fill 阶段内存不够，你可以在 🤗 Transformers 中把 `FlashAttention` 与 kv cache 量化一起用，在长输入 prompt 上进一步压低内存占用。详见[文档](https://huggingface.co/docs/transformers/main/en/perf_infer_gpu_one#flashattention-2)。

如果好奇把内存推到极限能塞下多少 token：量化 kv cache 配合 Flash Attention，在 80GB A100 上最多可支持 128k token；半精度 cache 的上限则是 40k token。

## 如何在 🤗 Transformers 中使用量化 kv cache

要在 🤗 Transformers 中使用 kv cache 量化，先运行 `pip install quanto` 装外部依赖。要激活 kv cache 量化，只需传 `cache_implementation="quantized"`，并在字典格式的 cache config 里指定量化参数。这就够了。而且由于 quanto 与设备无关，无论 CPU/GPU/MPS（Apple Silicon）都可以量化并运行模型。

这里有一份简短的 [Colab notebook](https://colab.research.google.com/drive/1YKAdOLoBPIore77xR5Xy0XLN8Etcjhui?usp=sharing)，包含使用示例。

```
>>> import torch
>>> from transformers import AutoTokenizer, AutoModelForCausalLM

>>> tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-2-7b-chat-hf")
>>> model = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-2-7b-chat-hf", torch_dtype=torch.float16, device_map="cuda:0")
>>> inputs = tokenizer("I like rock music because", return_tensors="pt").to(model.device)

>>> out = model.generate(**inputs, do_sample=False, max_new_tokens=20, cache_implementation="quantized", cache_config={"backend": "quanto", "nbits": 4})
>>> print(tokenizer.batch_decode(out, skip_special_tokens=True)[0])
I like rock music because it's loud and energetic. It's a great way to express myself and rel

>>> out = model.generate(**inputs, do_sample=False, max_new_tokens=20)
>>> print(tokenizer.batch_decode(out, skip_special_tokens=True)[0])
I like rock music because it's loud and energetic. I like to listen to it when I'm feeling
```

## 结论

减小键值缓存内存占用的方法远不止一种，包括 [MultiQueryAttention](https://arxiv.org/abs/1911.02150)、[GroupedQueryAttention](https://arxiv.org/abs/2305.13245)，以及最近的 [kv cache 检索](https://arxiv.org/abs/2403.09054)方法。有些方法与模型架构的选择绑定，另一些可以在训练后应用。量化正是这样一种训练后优化技术，从这篇简短的博客可以得出以下结论：

- **内存与速度的权衡**：把 kv cache 量化到更低精度可显著降低内存占用，让更长的文本生成不再撞上内存约束。但用户要自行判断牺牲一点生成速度是否适合自己的场景。
- **精度保持**：尽管精度降低了，`int4` 的 kv cache 量化仍能相当程度保住模型精度，生成的文本在上下文上保持相关且连贯。
- **灵活性**：用户可以按需求在不同精度格式间选择，适配不同场景与优先级。
- **进一步优化的潜力**：kv cache 量化本身就很有价值，还可以与权重量化等其他优化技术结合，进一步提升内存效率与计算速度。
