# Transformers 中的专家混合机制（MoE）

## 引言

过去几年，扩展稠密（dense）语言模型驱动了 LLM 的大部分进步。从最早的 [ULMFiT](https://nlp.fast.ai/classification/2018/05/15/introducing-ulmfit.html)（约 3000 万参数）或 GPT-2（1.5B 参数，当年还被认为是"危险到不敢发布"🧌），直到今天千亿参数的系统，配方很简单：

> 更多数据 + 更多参数 = 更好性能。

[缩放定律](https://huggingface.co/papers/2001.08361)强化了这一趋势，但稠密扩展有实际极限：

- 训练越来越贵。
- 推理延迟增长。
- 部署需要大量内存和硬件。

这就是混合专家（Mixture of Experts，MoE）登场的地方。

> 如果你已经熟悉 MoE、想直接看 transformers 里的工程工作，可以直达「Transformers 与 MoEs」一节。

## 从稠密到稀疏：MoE 是什么？

MoE 模型保留 Transformer 主干，但把某些稠密前馈层换成一组**专家（experts）**。「专家」不是按主题专精的模块（没有什么"数学专家""代码专家"），它就是一个可学习的子网络。对每个 token，一个**路由器（router）**选出少量专家来处理它。

| [![MoE 路由示意图](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/moe_routing.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/moe_routing.png) |
| --- |
| 图 1：4 个专家中激活了专家 1（来源：[Maarten Grootendorst](https://newsletter.maartengrootendorst.com/p/a-visual-guide-to-mixture-of-experts)） |

不同 token 根据其隐藏表示激活不同专家。

> 模型容量取决于总参数量，而推理速度取决于激活参数量。

这就是核心思想。

举个例子，[`gpt-oss-20b`](https://huggingface.co/openai/gpt-oss-20b)：总参数 21B，但每个 token 从 32 个专家里激活 4 个。算上共享部分加激活的专家，该模型每个 token 约 3.6B 激活参数。在 M3 Ultra Mac（内存带宽约 800 GB）上跑这个模型，可以按 `800 / (3.6 * 2)` 估算 `bfloat16` 的生成速度（每个参数 2 字节），约 **111 tokens/s**。我们实测约 115 tok/s，和这个拍脑袋估算非常接近。

你的浏览器不支持 video 标签。

这个惊人的速度印证了模型工作起来大约像个 3.6B 参数模型，但容量（质量）与 21B 参数模型相当。

*（注：如果用该模型原生 mxfp4 量化的专用 kernel，速度还会更快。）*

MoE 的吸引力在于：

- **更高的算力效率** 给定固定训练 FLOP 预算，MoE 常常胜过稠密对应物。    [![MoE vs Dense 训练曲线](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/faster_training.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/faster_training.png)   图 2：稠密 vs MoE 训练曲线（来源：[OLMoE: Open Mixture-of-Experts Language Models](https://huggingface.co/papers/2409.02060)）      这意味着更快的迭代和更好的扩展效率。
- **天然的并行化维度** 专家在计算图中提供了结构性边界。既然不同 token 使用不同专家，就可以跨专家并行（后文[专家并行](https://huggingface.co/blog/moe-transformers#expert-parallelism)详谈）。
- **产业采纳** 过去几周发布的重量级开源 MoE 就包括 [Qwen 3.5](https://huggingface.co/collections/Qwen/qwen35)、[MiniMax M2](https://huggingface.co/collections/MiniMaxAI/minimax-m2)、[GLM-5](https://huggingface.co/collections/zai-org/glm-5)、[Kimi K2.5](https://huggingface.co/collections/moonshotai/kimi-k25)。 这一趋势在 [DeepSeek R1](https://huggingface.co/deepseek-ai/DeepSeek-R1) 于 2025 年 1 月大获成功后明显加速，而它又建立在 [DeepSeek V2](https://huggingface.co/deepseek-ai/DeepSeek-V2) 等更早系统之上。更早期的 MoE 还有 2023 年 12 月发布的 [Mixtral-8x7B](https://huggingface.co/mistralai/Mixtral-8x7B-v0.1)。    [![transformers 包近两年 MoE 模型新增时间线](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/moe_2y_timeline.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/moe-transformers/moe_2y_timeline.png)   图 3：`transformers` 库近两年新增 MoE 模型的时间线。DeepSeek R1 是明显的拐点。      闭源实验室同样在用 MoE。ChatGPT 一直[*有传闻*](https://x.com/soumithchintala/status/1671267150101721090)采用稀疏架构，而开源的 [gpt-oss 模型](https://huggingface.co/collections/openai/gpt-oss)确实用了。

> 想更全面了解 MoE，强烈建议读这篇博客（指[混合专家模型详解](https://huggingface.co/blog/moe)），并观看我们最近的关于路由的 YouTube 视频。

## Transformers 与 MoEs

生态里的大多数工具——模型加载、设备放置、量化、后端执行——最初都是为**稠密**模型设计的。MoE 对这些假设构成挑战。

让 MoE 在 `transformers` 里成为**一等公民**，意味着重新设计加载流水线、执行模型和分布式抽象的一部分，而不只是新增模型类。下面聚焦 `transformers` 库如何演进以支持稀疏架构：

- [权重加载重构](https://huggingface.co/blog/moe-transformers#weight-loading-refactor)
- [专家后端](https://huggingface.co/blog/moe-transformers#expert-backend)
- [专家并行](https://huggingface.co/blog/moe-transformers#expert-parallelism)
- [用 transformers 训练 MoE](https://huggingface.co/blog/moe-transformers#training-moes-with-transformers)

## 权重加载重构

[`AutoModelForCausalLM.from_pretrained("model_id")`](https://huggingface.co/docs/transformers/main/en/model_doc/auto#transformers.AutoModelForCausalLM.from_pretrained) 负责下载模型权重并加载进 PyTorch 模型。对稠密模型，加载相对直接：checkpoint 中每个张量与运行时模块里的参数一比一对应。

对 MoE 就复杂了。多数 MoE checkpoint 中，每个专家是独立序列化的。偷看一眼 [DeepSeek-V3 的 checkpoint 索引](https://huggingface.co/deepseek-ai/DeepSeek-V3/raw/main/model.safetensors.index.json)，会看到这样的 key：

```
model.layers.3.mlp.experts.0.gate_proj.weight
...
model.layers.3.mlp.experts.255.gate_proj.weight
```

每个专家有自己的一套权重矩阵，本质上是 256 个（以 DeepSeek-V3 为例，0 到 255）小前馈网络并排存放。但运行时 GPU 执行的是优化过的 kernel。现代 MoE kernel，如 [grouped GEMM 与融合 MoE 实现](https://huggingface.co/kernels-community/megablocks)，是为*单个操作处理全部专家*而设计的，不是一个个专家轮流循环。

要高效做到这一点，需要把专家权重打包进一个**连续张量**。

于是出现了错配：

- **Checkpoint：** 256 个独立张量
- **运行时：** 1 个打包张量

系统性地弥合这个鸿沟，正是[权重加载重构](https://github.com/huggingface/transformers/pull/41580)带来的能力。

随着通用 [WeightConverter](https://huggingface.co/docs/transformers/main/en/weightconverter) 的引入，心智模型从：

> checkpoint 本来就与我的运行时布局一致，加载基本就是逐个 key 拷贝。

转变为：

> checkpoint 只是张量的序列化来源。加载是一条转换流水线，把它们变成我们想要的运行时布局。

### 用 `WeightConverter` 做动态权重加载

这次重构引入的中心抽象，是通过 [`WeightConverter`](https://huggingface.co/docs/transformers/main/en/weightconverter) 实现的**动态权重加载**。

`WeightConverter` 允许我们定义：

```
source key patterns → target key(s) + operations
```

基础操作（chunk、concatenate 等）可以组合。对 MoE 特别有用的两个：

- [`MergeModulelist`](https://github.com/huggingface/transformers/blob/main/src/transformers/core_model_loading.py) 把一串张量合并成一个张量。例如把 `MergeModulelist` 与 `Concatenate` 组合，就能把 MoE 的各专家堆叠打包成单个张量。`WeightConverter( ["block_sparse_moe.experts.*.w1.weight", "block_sparse_moe.experts.*.w3.weight",], "mlp.experts.gate_up_proj", operations=[ MergeModulelist(dim=0), Concatenate(dim=1), ], ) `
- [`SplitModulelist`](https://github.com/huggingface/transformers/blob/b71de73468429eb02da18caa50e9b5200400a4ed/src/transformers/core_model_loading.py#L208) 把一个张量拆回一串张量。例如把堆叠的专家拆回单个专家。`WeightConverter( "mlp.experts.down_proj", "block_sparse_moe.experts.*.w2.weight", operations=[SplitModulelist(dim=0)], ) `

### 张量的惰性实体化

重构不仅改进了*有哪些*转换，还改进了转换*怎么调度*。

加载器只扫一遍 checkpoint key，与 converter 的模式匹配，按 converter 归组张量。一旦某个 key 被确认需要，就登记为一个 *future*，通过线程池实体化。转换操作只在依赖就绪后才执行。例如 `MergeModulelist` 会等某一层的全部专家都加载完。

这避免了反复扫描，也降低了内存峰值。

### 基准测试：权重加载流水线的改进

为评估新权重加载流水线的收益，我们对 `transformers` v4 与 v5 做了基准。重点是大型 MoE 模型的加载速度——它常是训练和推理的瓶颈。

基准用的分支：

- v4 分支：[https://github.com/ariG23498/transformers/tree/bench-v4](https://github.com/ariG23498/transformers/tree/bench-v4)
- v5 分支：[https://github.com/ariG23498/transformers/tree/bench-v5](https://github.com/ariG23498/transformers/tree/bench-v5)

示例：

```
from transformers import AutoModelForCausalLM

model_id = "Qwen/Qwen1.5-110B-Chat"
model = AutoModelForCausalLM.from_pretrained(model_id)
```

两个相关环境变量：

- `HF_ENABLE_PARALLEL_LOADING`：启用线程并行加载分片。
- `HF_DEACTIVATE_ASYNC_LOAD`：关闭新的异步流水线（v5 的逃生舱）。

### 量化如何接入

有了这次重构，我们可以先构造运行时模块结构，再把权重转换进这个结构。量化现在可以选择性地挂在转换流水线里，成为权重加载流水线本身的一环。这很关键，因为「按专家量化」只有当专家以可预期的打包布局存在时才有意义。

这条端到端流水线过去做不到，现在作为公开 API 交到用户手里。

## 专家后端

专家被打包进单个运行时张量后，又冒出一个问题：

> 实际怎么高效地路由穿过它们？

在 MoE 模型里，每个 token 被路由到不同专家。这意味着运行时必须把 token 分发给选中专家的权重、高效执行投影、应用路由权重，再收集并还原结果顺序。

这正是[专家后端系统](https://huggingface.co/docs/transformers/experts_interface)（[PR #42697](https://github.com/huggingface/transformers/pull/42697) 引入）解决的问题。专家后端提供了一个**可插拔的执行架构**，把专家计算与模型实现解耦。系统不再在每个 MoE 模型里硬编码一种分发策略，而是让专家层在运行时动态选择后端。

实现方式是装饰器模式：

```
@use_experts_implementation
```

装饰器包住专家类，自动把计算分发给选定的后端。

目前提供三个后端：

- `eager`：循环遍历被选中的专家、逐个应用投影。用于正确性参照和调试。
- `batched_mm`：使用 [`torch.bmm`](https://docs.pytorch.org/docs/stable/generated/torch.bmm.html) API。把选中专家的权重按 token 复制，做一次批量 GEMM。非常适合 batch 小、GPU 富余且内存充足的场景。
- `grouped_mm`：使用 [`torch._grouped_mm`](https://docs.pytorch.org/docs/stable/generated/torch.nn.functional.grouped_mm.html) API。先按专家 ID 给 token 排序、分组，再做一次分组 GEMM。这个后端在大 batch 或内存受限的场合表现出色。

## 专家并行

MoE 模型可以有数千亿参数（远超单张 GPU 的容量）。专家并行（EP）通过把专家分布到多个设备来解决。每个设备只加载分给它的专家子集、计算这些专家的结果，然后参与结果汇总。这样模型规模可以扩到远超单卡能容纳的参数量，而计算成本并不增加——因为每个 token 只激活少量专家。

专家并行通过 `enable_expert_parallel` 启用：

```
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from transformers.distributed.configuration_utils import DistributedConfig

distributed_config = DistributedConfig(enable_expert_parallel=True)

model = AutoModelForCausalLM.from_pretrained(
    "openai/gpt-oss-120b",
    dtype="auto",
    distributed_config=distributed_config,
)
```

启动命令：

```
torchrun --nproc-per-node N script.py
```

其中 `N` 要能整除专家总数，最好与你节点的 GPU 数一致。

当 `enable_expert_parallel=True` 时，模型从标准张量并行（TP）计划切换到专家并行（EP）计划，使用专门的分片策略。

EP 的核心组件：

- [`GroupedGemmParallel`](https://github.com/huggingface/transformers/blob/b71de73468429eb02da18caa50e9b5200400a4ed/src/transformers/integrations/tensor_parallel.py#L934)：沿专家维度（`dim=0`）切分专家权重。每个设备只加载 `num_experts / num_devices` 个。
- [`RouterParallel`](https://github.com/huggingface/transformers/blob/b71de73468429eb02da18caa50e9b5200400a4ed/src/transformers/integrations/tensor_parallel.py#L977)：把全局专家索引重映射为本地索引，掩掉未分配给当前 rank 的专家，确保每个设备只用自己的本地专家计算，最后用 all-reduce 合并各设备的部分输出。

## 用 Transformers 训练 MoE

MoE 很适合扩展推理，但训练它们要复杂得多。

MoE 参数量巨大、分布式专家通信复杂，还有路由不稳定问题要处理。为此我们与 **Unsloth** 合作，让 MoE 训练显著提速：

- MoE 训练快约 12×
- VRAM 降低超 35%
- 上下文长约 6×
- 相比 v4 整体加速 12-30×

我们利用专家后端抽象，统一围绕 PyTorch 的 `torch._grouped_mm` API，并使用定制的 Triton grouped-GEMM + LoRA kernel。Unsloth 在 Transformers（和 TRL）的优化之上继续压榨性能。
