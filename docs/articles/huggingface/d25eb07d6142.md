本文亦有[简体中文](https://huggingface.co/blog/zh/the_n_implementation_details_of_rlhf_with_ppo)版本。

RLHF / ChatGPT 近来是热门研究方向。为了更深入研究 RLHF，本博客尝试复现 OpenAI 2019 年的原版 RLHF 代码库 [*openai/lm-human-preferences*](https://github.com/openai/lm-human-preferences)。尽管它还带着"tensorflow-1.x 味儿"，OpenAI 的原版代码库经过了充分的评估和基准测试，是研究 RLHF 实现工程细节的好去处。

我们的目标是：

- 在风格类（stylistic）任务上复现 OAI 的结果，并让学习曲线与 [*openai/lm-human-preferences*](https://github.com/openai/lm-human-preferences) 尽量吻合。
- 给出一份实现细节清单，精神同 [*The 37 Implementation Details of Proximal Policy Optimization*](https://iclr-blog-track.github.io/2022/03/25/ppo-implementation-details/) 和 [*Debugging RL, Without the Agonizing Pain*](https://andyljones.com/posts/rl-debugging.html)。
- 提供一个易读的、最小化的 RLHF 参考实现；

本工作仅用于教育/学习目的。对于需要更多特性（例如用 PEFT 跑更大模型）的高级用户，[*huggingface/trl*](https://github.com/huggingface/trl) 是很好的选择。

- 在[匹配学习曲线](https://huggingface.co/blog/the_n_implementation_details_of_rlhf_with_ppo#matching-learning-curves)一节，我们展示主要贡献：建立一个能复现 OAI 风格类任务结果、且学习曲线与 [*openai/lm-human-preferences*](https://github.com/openai/lm-human-preferences) 高度吻合的代码库。
- 随后深入讲解与复现 OAI 工作相关的实现细节。在[通用实现细节](https://huggingface.co/blog/the_n_implementation_details_of_rlhf_with_ppo#general-implementation-details)我们谈基础细节，如 reward/value 如何生成、回复如何生成；在[奖励模型实现细节](https://huggingface.co/blog/the_n_implementation_details_of_rlhf_with_ppo#reward-model-implementation-details)谈奖励归一化等细节；在[策略训练实现细节](https://huggingface.co/blog/the_n_implementation_details_of_rlhf_with_ppo#policy-training-implementation-details)谈拒绝采样、奖励"白化"等细节；在 [**Adam 优化器数值问题对 RLHF 的影响（PyTorch vs TensorFlow）**](https://huggingface.co/blog/the_n_implementation_details_of_rlhf_with_ppo#pytorch-adam-optimizer-numerical-issues-wrt-rlhf)一节，我们指出 TensorFlow 与 PyTorch 在 Adam 上一个非常有意思的实现差异，它会在训练早期造成过激的参数更新。
- 接着，我们考察在奖励标签由 `gpt2-large` 产生的前提下，训练不同基座模型（如 gpt2-xl、falcon-1b）的效果差异。
- 最后以局限性和讨论收尾。

### 关于运行 openai/lm-human-preferences 的一点说明

为了直接对比，我们运行了 [*openai/lm-human-preferences*](https://github.com/openai/lm-human-preferences) 的原版 RLHF 代码，它能提供有价值的指标来帮助验证和诊断我们的复现。我们成功把这份 TensorFlow 1.x 老代码跑了起来，但它的环境要求苛刻到令人发指：

- OAI 的数据集部分已损坏/丢失（所以我们用类似的 HF 数据集做了替换，替换是否造成性能差异不得而知）。具体说，它的书籍数据集在 OpenAI 从 GCP 向 Azure 迁移期间丢了（https://github.com/openai/lm-human-preferences/issues/17#issuecomment-1044051496 ）。我们用 Hugging Face 的 `bookcorpus` 数据集替换，原则上它就是 OAI 当年用的东西。
- 它没法在单张 V100 上跑，因为它没实现梯度累积。它用的是大 batch，把一个 batch 拆到 8 张 GPU 上，单卡会 OOM。
- 它没法在 8x A100 上跑，因为它用 TensorFlow 1.x，与 CUDA 8+ 不兼容。
- 它没法在 8x V100（16GB）上跑，会 OOM。
- 它只能在 8x V100（32GB）上跑，而这种配置只有 AWS 的 `p3dn.24xlarge` 实例提供。

## 通用实现细节

本节深入讲解与复现 OAI 工作相关的实现细节。我们先谈基础细节，如 reward/value 如何生成、回复如何生成。以下细节排名不分先后：

- **奖励模型和策略的 value head 的输入是 `query` 与 `response` 的拼接**  奖励模型和策略的 value head 看的*不只*是 response，而是把 `query` 和 `response` 拼成 `query_response`（[lm_human_preferences/rewards.py#L105-L107](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/rewards.py#L105-L107)）。举例：若 `query = "he was quiet for a minute, his eyes unreadable"`，`response = "He looked at his left hand, which held the arm that held his arm out in front of him."`，那么奖励模型和策略的 value 就是对 `query_response = "he was quiet for a minute, his eyes unreadable. He looked at his left hand, which held the arm that held his arm out in front of him."` 做前向传播，产出形状为 `(B, T, 1)` 的奖励和 value，其中 `B` 是 batch size，`T` 是序列长度，`1` 是奖励头的维度 1（[lm_human_preferences/rewards.py#L105-L107](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/rewards.py#L105-L107)，[lm_human_preferences/policy.py#L111](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/policy.py#L111)）。  `T` 意味着每个 token 都关联着一个奖励以及它的上文。例如 `eyes` 这个 token 的奖励对应的是 `he was quiet for a minute, his eyes`。
- **用特殊 padding token 填充，并截断输入。**   OAI 给查询设定了固定长度 `query_length`：过短的序列用 `pad_token` **填充**（[lm_human_preferences/language/datasets.py#L66-L67](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/datasets.py#L66-L67)），过长的序列**截断**（[lm_human_preferences/language/datasets.py#L57](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/datasets.py#L57)）（关于 padding/truncation 概念的介绍见[这里](https://huggingface.co/docs/transformers/pad_truncation)）。填充输入时，OAI 用的是词表之外的一个特殊 token（[lm_human_preferences/language/encodings.py#L56](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/encodings.py#L56)）。  **关于 HF transformers 的 padding token 的说明**：根据（[transformers#2630#issuecomment-578159876](https://github.com/huggingface/transformers/issues/2630#issuecomment-578159876)），GPT 和 GPT-2 预训练时不使用 padding token，因此 transformers 里的 gpt2 模型没有官方配套的 padding token。常见做法是 `tokenizer.pad_token = tokenizer.eos_token`，但为了对齐 OAI 的原始设置，本工作中我们把这两个特殊 token 区分开，即使用 `tokenizer.add_special_tokens({"pad_token": "[PAD]"})`。   注意，没有 padding token 是解码器模型的默认状态，因为它们预训练时用"打包（packing）"：许多序列被拼接在一起、以 EOS token 分隔，预训练时把固定最大长度的切片喂给模型。  把所有内容合起来看一个例子   `import transformers tokenizer = - **回复生成时采样固定长度且不 padding。**  生成回复时，OAI 使用 `top_k=0, top_p=1.0`，直接对整个词表做类别采样（categorical sample）（[lm_human_preferences/language/sample.py#L43](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/sample.py#L43)），并且会一直采样直到生成固定长度的回复（[lm_human_preferences/policy.py#L103](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/policy.py#L103)）。注意即使遇到 EOS（end-of-sequence）token 也继续采样。  **关于 HF transformers 的说明——采样可能在 `eos_token` 处停止**：在 `transformers` 里，生成可能在 `eos_token` 处停止（[src/transformers/generation/utils.py#L2248-L2256](https://github.com/huggingface/transformers/blob/67b85f24def79962ce075353c2627f78e0e53e9f/src/transformers/generation/utils.py#L2248-L2256)），与 OAI 的设置不同。为了对齐，需要设置 `pretrained_model.generation_config.eos_token_id = None, pretrained_model.generation_config.pad_token_id = None`。注意 `transformers.GenerationConfig(eos_token_id=None, pad_token_id=None, ...)` 是不行的，因为 `pretrained_model.generation_config` 会覆盖并重新设置 `eos_token`。`import torch import transformers tokenizer = transformers.AutoTokenizer.from_pretrained("gpt2", padding_side="right") tokenizer.add_special_tokens({"pad_token": "[PAD]"}) pad_id = tokenizer.pad_token_id query = torch.tensor([ [pad_id, pad_id, 23073], ]) response = torch.tensor([ [11, 339, 561], ]) response_length = 4 temperature = 0.7 pretrained_model = transformers.AutoModelForCausalLM.from_pretrained("gpt2") pretrained_model.generation_config.eos_token_id = None # - **不同进程使用不同的种子**  在启动 8 个 GPU 进程做数据并行时，OAI 给每个进程设置了不同的随机种子（[lm_human_preferences/utils/core.py#L108-L111](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/utils/core.py#L108-L111)）。实现上是 `local_seed = args.seed + process_rank * 100003`。种子不同，模型产出的回复和得分也就不同。注：我们认为数据集洗牌（shuffling）有个 bug——数据集莫名其妙地用了相同的种子洗牌（[lm_human_preferences/lm_tasks.py#L94-L97](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/lm_tasks.py#L94-L97)）。

## 奖励模型实现细节

本节讨论奖励模型专属的实现细节，如奖励归一化和层初始化。以下细节排名不分先后：

- **奖励模型只在最后一个 token 上输出值。**  注意：对 `query` 与 `response` 拼接做前向传播后拿到的奖励形状为 `(B, T, 1)`，其中 `B` 是 batch size，`T` 是序列长度（在本设定下恒定不变：风格类任务中 `query_length + response_length = 64 + 24 = 88`，见 [launch.py#L9-L11](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/launch.py#L9-L11)），`1` 是奖励头的维度 1。出于 RLHF 目的，原代码库只取最后一个 token 的奖励（[lm_human_preferences/rewards.py#L132](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/rewards.py#L132)），于是奖励形状变成 `(B, 1)`。  注意更新的代码库 [*openai/summarize-from-feedback*](https://github.com/openai/summarize-from-feedback) 里，OAI 遇到 EOS token 会停止采样（[summarize_from_feedback/utils/experiment_helpers.py#L19](https://github.com/openai/summarize-from-feedback/blob/8af822a428c93432aa80ffbe5b065a8f93895669/summarize_from_feedback/utils/experiment_helpers.py#L19)）。提取奖励时，它会先定位 `last_response_index`——EOS token 之前的那个索引（[#L11-L13](https://github.com/openai/summarize-from-feedback/blob/8af822a428c93432aa80ffbe5b065a8f93895669/summarize_from_feedback/reward_model.py#L11-L13)），并提取该位置的奖励（[summarize_from_feedback/reward_model.py#L59](https://github.com/openai/summarize-from-feedback/blob/8af822a428c93432aa80ffbe5b065a8f93895669/summarize_from_feedback/reward_model.py#L59)）。但本工作保持原代码库的设置。
- **奖励头层的初始化**  奖励头的权重按 N(0,1/(√(d_model+1))) \mathcal{N}\left(0,1 /\left(\sqrt{d_{\text {model }}+1}\right)\right) N(0,1/(dmodel ​+1​)) 初始化（[lm_human_preferences/language/model.py#L368,](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/model.py#L368) [lm_human_preferences/language/model.py#L251-L252](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/model.py#L251-L252)）。这与 Stiennon et al., 2020 的设定一致（[summarize_from_feedback/query_response_model.py#L106-L107](https://github.com/openai/summarize-from-feedback/blob/8af822a428c93432aa80ffbe5b065a8f93895669/summarize_from_feedback/query_response_model.py#L106-L107)）（顺便说，Stiennon et al., 2020 在第 17 页有个笔误，把分布写成了 N(0,1/(dmodel+1)) \mathcal{N}\left(0,1 /\left(d_{\text {model }}+1\right)\right) N(0,1/(dmodel ​+1))，漏掉了平方根）。奖励头的 bias 设为 0（[lm_human_preferences/language/model.py#L254](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/model.py#L254)）。
- **奖励模型训练前后的归一化**  论文里 Ziegler et al. (2019) 提到："为了让奖励模型的尺度在训练期间保持一致，我们把它归一化，使其在 x∼D,y∼ρ(⋅∣x) x \sim \mathcal{D}, y \sim \rho(·|x) x∼D,y∼ρ(⋅∣x) 下均值为 0、方差为 1。" 执行归一化时，代码先构造 `reward_gain` 和 `reward_bias`，奖励按 `reward = reward * reward_gain + reward_bias` 计算（[lm_human_preferences/rewards.py#L50-L51](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/rewards.py#L50-L51)）。  归一化过程先设定 `reward_gain=1, reward_bias=0`（[lm_human_preferences/train_reward.py#L211](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/train_reward.py#L211)），然后从目标数据集（如 `bookcorpus, tldr, cnndm`）采样查询、生成回复、评估奖励。接着计算已评估奖励的**经验均值与标准差**（[lm_human_preferences/train_reward.py#L162-L167](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/train_reward.py#L162-L167)），据此求解 `reward_gain` 和 `reward_bias` 应该取多少。  用 μD \mu_{\mathcal{D}} μD​ 表示经验均值，σD \sigma_{\mathcal{D}} σD​ 表示经验标准差，g 表示 `reward_gain`，b 表示 `reward_bias`，μT=0 \mu_{\mathcal{T}} = 0 μT​=0 为**目标均值**，σT=1 \sigma_{\mathcal{T}}=1 σT​=1 为**目标标准差**。于是有下面这个公式。 g∗N(μD,σD)+b=N(g∗μD,g∗σD)+b=N(g∗μD+b,g∗σD)=N(μT,σT)g=σT/σD b=μT−g∗μD \begin{aligned}g*\mathcal{N}(\mu_{\mathcal{D}}, \sigma_{\mathcal{D}}) + b &= \mathcal{N}(g*\mu_{\mathcal{D}}, g*\sigma_{\mathcal{D}}) + b\\&= \mathcal{N}(g*\mu_{\mathcal{D}} + b, g*\sigma_{\mathcal{D}}) \\&= \mathcal{N}(\mu_{\mathcal{T}}, \sigma_{\mathcal{T}}) \\g &= \frac{\sigma_{\mathcal{T}}}{\sigma_{\mathcal{D}}} \\b &= \mu_{\mathcal{T}} - g*\mu_{\mathcal{D}}\end{aligned} g∗N(μD​,σD​)+bgb​=N(g∗μD​,g∗σD​)+b=N(g∗μD​+b,g∗σD​)=N(μT​,σT​)=σD​σT​​​=μT​−g∗μD​​ 归一化在奖励模型训练**前**和训练**后**都会应用（[lm_human_preferences/train_reward.py#L232-L234](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/train_reward.py#L232-L234)，[lm_human_preferences/train_reward.py#L252-L254](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/train_reward.py#L252-L254)）。注意用于归一化的回复 y∼ρ(⋅∣x) y \sim \rho(·|x) y∼ρ(⋅∣x) 来自预训练语言模型 ρ\rho ρ。ρ\rho ρ 固定作为参考模型，在奖励学习中不更新（[lm_human_preferences/train_reward.py#L286C1-L286C31](https://github.com/openai/lm-human-preferences/blob/master/lm_human_preferences/train_reward.py#L286C1-L286C31)）。

## 策略训练实现细节

本节深入层初始化、数据后处理、dropout 设置等细节，还会探讨拒绝采样、奖励"白化"（whitening）和自适应 KL 等技术。以下细节排名不分先后：

- **用采样温度缩放 logits。**   计算回复的对数概率时，模型先输出回复中各 token 的 logits，然后把 logits 除以采样温度（[lm_human_preferences/policy.py#L121](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/policy.py#L121)），即 `logits /= self.temperature`。一次非正式测试中我们发现，不做这个缩放，KL 会比预期上升得更快，性能也会变差。
- **Value head 层的初始化**  value head 的权重按 N(0,0)\mathcal{N}\left(0,0\right)N(0,0) 初始化（[lm_human_preferences/language/model.py#L368,](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/model.py#L368) [lm_human_preferences/language/model.py#L251-L252](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/model.py#L251-L252)。 value head 的 bias 设为 0（[lm_human_preferences/language/model.py#L254](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/model.py#L254)）。
- **选择以句号开头和结尾的查询文本**  这是数据预处理的一部分：尽量从 `start_text="."` 之后选取文本（[lm_human_preferences/language/datasets.py#L51](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/datasets.py#L51)）；尽量选取在 `end_text="."` 之前的文本（[lm_human_preferences/language/datasets.py#L61](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/datasets.py#L61)）；然后对文本做 padding（[lm_human_preferences/language/datasets.py#L66-L67](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/language/datasets.py#L66-L67)）   运行 `openai/lm-human-preferences` 时，OAI 的数据集部分已损坏/丢失（[openai/lm-human-preferences/issues/17#issuecomment-104405149](https://github.com/openai/lm-human-preferences/issues/17#issuecomment-1044051496)），所以我们用类似的 HF 数据集替换，是否引起性能差异未知。  书籍数据集我们用了 [https://huggingface.co/datasets/bookcorpus](https://huggingface.co/datasets/bookcorpus)。我们发现没必要再抽取"以句号开头结尾"的句子，因为该数据集已经按这种方式预处理过了（例如 `"usually , he would be tearing around the living room , playing with his toys ."`）。因此在 `sentiment` 和 `descriptiveness` 任务上我们设置 `start_text=None, end_text=None`。
- **关闭 dropout**  Ziegler et al. (2019) 提到："策略训练不使用 dropout。"代码里也确实这么做（[lm_human_preferences/policy.py#L48](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/policy.py#L48)）。

- **逐 token 的 KL 惩罚**  代码给奖励加了逐 token 的 KL 惩罚（[lm_human_preferences/train_policy.py#L150-L153](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/train_policy.py#L150-L153)），以阻止策略偏离原始策略太远。以 `"usually, he would"` 为例，它被分词为 `[23073, 11, 339, 561]`。假设用 `[23073]` 作 query、`[11, 339, 561]` 作 response。那么在默认 `gpt2` 参数下，参考策略对响应 token 的对数概率为 `logprobs=[-3.3213, -4.9980, -3.8690]` 。在第一次 PPO 更新 epoch 和 minibatch 更新时，主动策略的对数概率与之相同 `new_logprobs=[-3.3213, -4.9980, -3.8690]`，因此逐 token KL 惩罚为 `kl = new_logprobs - logprobs = [0., 0., 0.,]`。 然而第一次梯度反向传播之后，可能出现 `new_logprob=[-3.6528, -5.0406, -3.2339]`，于是逐 token KL 惩罚变成 `kl = new_logprobs - logprobs = [-0.3315, -0.0426, 0.6351]`。然后 `non_score_reward = beta * kl`，其中 `beta` 是 KL 惩罚系数 β\betaβ，它被加到从奖励模型获得的 `score` 上构成训练用的 `rewards`。`score` 只在回合结束时给出，比如可以是 `[0.4,]`，于是 `rewards = [beta * -0.3315, beta * -0.0426, beta * 0.6351 + 0.4]`。

- **Value function 的裁剪（clipped value function）**  与原始 PPO 一致（[baselines/ppo2/model.py#L68-L75](https://github.com/openai/baselines/blob/ea25b9e8b234e6ee1bca43083f8f3cf974143998/baselines/ppo2/model.py#L68-L75)），value function 也以类似策略目标的方式被裁剪（[lm_human_preferences/train_policy.py#L343-L348](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/train_policy.py#L343-L348)）。
- **自适应 KL**  KL 散度惩罚系数 β\betaβ 会根据当前策略与上一策略之间的 KL 散度自适应调整。如果 KL 散度超出了预设目标范围，就调整惩罚系数，使其回到目标范围（[lm_human_preferences/train_policy.py#L115-L124](https://github.com/openai/lm-human-preferences/blob/cbfd210bb8b08f6bc5c26878c10984b90f516c66/lm_human_preferences/train_policy.py#L115-L124)）。实现如下：`class AdaptiveKLController: def __init__(self, init_kl_coef, hparams): self.value = init_kl_coef self.hparams = hparams def update(self, current, n_steps): target = self.hparams.target proportional_error = np.clip(current / target - 1, -0.2, 0.2) mult = 1 + proportional_error * n_steps / self.hparams.horizon self.value *= mult `  本工作考察的 `sentiment` 和 `descriptiveness` 任务使用 `init_kl_coef=0.15, hparams.target=6, hparams.horizon=10000`。

### **Adam 优化器的数值问题对 RLHF 的影响（PyTorch vs TensorFlow）**

- 这个实现细节有趣到值得单独成节。
- PyTorch 的 Adam 优化器（[torch.optim.Adam.html](https://pytorch.org/docs/stable/generated/torch.optim.Adam.html)）与 TensorFlow 的 Adam 优化器（TF1 Adam 见 [tensorflow/v1.15.2/adam.py](https://github.com/tensorflow/tensorflow/blob/v1.15.2/tensorflow/python/training/adam.py)，TF2 Adam 见 [keras/adam.py#L26-L220](https://github.com/keras-team/keras/blob/v2.13.1/keras/optimizers/adam.py#L26-L220)）实现不同。特别是，**PyTorch 遵循 Kingma 和 Ba 的 Adam 论文的 Algorithm 1**（[arxiv/1412.6980](https://arxiv.org/pdf/1412.6980.pdf)），而 **TensorFlow 使用论文 2.1 节之前紧邻的公式**，其在此处称为 `epsilon` 的量对应论文中的 `epsilon hat`。用伪代码对比：

```
### pytorch adam implementation:
bias_correction1 = 1 - beta1 ** step
bias_correction2 = 1 - beta2 ** step
step_size = lr / bias_correction1
bias_correction2_sqrt = _dispatch_sqrt(bias_correction2)
denom = (exp_avg_sq.sqrt() / bias_correction2_sqrt).add_(eps)
param.addcdiv_(exp_avg, denom, value=-step_size)

### tensorflow adam implementation:
lr_t = lr * _dispatch_sqrt((1 - beta2 ** step)) / (1 - beta1 ** step)
denom = exp_avg_sq.sqrt().add_(eps)
param.addcdiv_(exp_avg, denom, value=-lr_t)
```

- 来对比 pytorch 风格和 tensorflow 风格 adam 的更新方程。沿用 Adam 论文（[Kingma and Ba, 2014](https://arxiv.org/abs/1412.6980)）的记号，pytorch adam（论文 Algorithm 1）与 tensorflow 风格 adam（论文 2.1 节之前紧邻公式）的梯度更新规则如下：

pytorch adam :θt=θt−1−α⋅m^t/(v^t+ε)=θt−1−α[mt/(1−β1t)]⏟=m^t/[vt/(1−β2t)⏟=v^t+ε]=θt−1−α[mt/(1−β1t)]1−β2tvt+ε1−β2t\begin{aligned}\text{pytorch adam :}\quad \theta_t & =\theta_{t-1}-\alpha \cdot \hat{m}_t /\left(\sqrt{\hat{v}_t}+\varepsilon\right) \\& =\theta_{t-1}- \alpha \underbrace{\left[m_t /\left(1-\beta_1^t\right)\right]}_{=\hat{m}_t} /\left[\sqrt{\underbrace{v_t /\left(1-\beta_2^t\right)}_{=\hat{v}_t} }+\varepsilon\right]\\& =\theta_{t-1}- \alpha\left[m_t /\left(1-\beta_1^t\right)\right]\frac{\sqrt{1-\beta_2^t}}{\sqrt{v_t}+\color{green}{\varepsilon \sqrt{1-\beta_2^t}}}\end{aligned}pytorch adam :θt​​=θt−1​−α⋅m^t​/(v^t​​+ε)=θt−1​−α=m^t​[mt​/(1−β1t​)]​​/​=v^t​vt​/(1−β2t​)​​​+ε​=θt−1​−α[mt​/(1−β1t​)]vt​​+ε1−β2t​​1−β2t​​​​

tensorflow adam:θt=θt−1−αtmt/(vt+ε^)=θt−1−[α1−β2t/(1−β1t)]⏟=αtmt/(vt+ε^)=θt−1−α[mt/(1−β1t)]1−β2tvt+ε^\begin{aligned}\text{tensorflow adam:}\quad \theta_t & =\theta_{t-1}-\alpha_t m_t /\left(\sqrt{v_t}+\hat{\varepsilon}\right) \\& =\theta_{t-1}-\underbrace{\left[\alpha \sqrt{1-\beta_2^t} /\left(1-\beta_1^t\right)\right]}_{=\alpha_t} m_t /\left(\sqrt{v_t}+\hat{\varepsilon}\right) \\& =\theta_{t-1}- \alpha\left[m_t /\left(1-\beta_1^t\right)\right] \frac{\sqrt{1-\beta_2^t}}{\sqrt{v_t}+\color{green}{\hat{\varepsilon}}} \end{aligned}tensorflow adam:θt​​=θt−1​−αt​mt​/(vt​​+ε^)=θt−1​−=αt​[α1−β2t​​/(1−β1t​)]​​mt​/(vt​​+ε^)=θt−1​−α[mt​/(1−β1t​)]vt​​+ε^1−β2t​​​​

- 上面的方程表明，pytorch 与 tensorflow 实现的区别在于它们的**归一化项**：ε1−β2t\color{green}{\varepsilon \sqrt{1-\beta_2^t}}ε1−β2t​​ 与 ε^\color{green}{\hat{\varepsilon}}ε^。如果设 ε^=ε1−β2t\hat{\varepsilon} =\varepsilon \sqrt{1-\beta_2^t}ε^=ε1−β2t​​，两个版本是等价的。然而在 pytorch 和 tensorflow 的 API 里，我们只能通过 `eps` 参数分别设置 ε\varepsilonε（pytorch）和 ε^\hat{\varepsilon}ε^（tensorflow），于是更新方程出现差异。如果让 ε\varepsilonε 和 ε^\hat{\varepsilon}ε^ 取同样的值，比如 1e-5？那么对 tensorflow adam，归一化项 ε^=1e-5\hat{\varepsilon} = \text{1e-5}ε^=1e-5 就是个常数。但对 pytorch adam，归一化项 ε1−β2t{\varepsilon \sqrt{1-\beta_2^t}}ε1−β2t​​ 随时间变化。关键在于：时间步 ttt 较小时这一项远小于 1e-5，随后随着时间步增大逐渐逼近 1e-5。下面这张图对比了两个归一化项随时间步的变化：  [![norma_const_comparison.png](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/rlhf_implementation_details/norma_const_comparison.png)](https://huggingface.co/datasets/trl-internal-testing/example-images/resolve/main/rlhf_implementation_details/norma_const_comparison.png)
- 上图说明：如果给 pytorch adam 和 tensorflow adam 设同样的 `eps`，那么训练早期 pytorch-adam 的归一化项比 tensorflow-adam 小得多。换句话说，**pytorch adam 在训练早期会做更激进的梯度更新**。我们的实验支持这一发现，下面来展示。

- **PyTorch 的 `Adam` 产出了更激进的更新**，原因见上文。证据如下：  **PyTorch `Adam` 的 `logprob_diff_var` 高 6 倍**。这里 `logprobs_diff = new_logprobs - logprobs` 是训练两个 epoch 后初始策略与当前策略之间 token 对数概率的差。`logprob_diff_var` 更大意味着对数概率变化的幅度比 OAI 的 TF1 Adam 更大。**PyTorch 的 `Adam` 的 ratio 最大/最小值更极端**。这里 `ratio = torch.exp(logprobs_diff)`。`ratio_max=1.8121057748794556` 意味着对某些 token，当前策略下采样到该 token 的概率变为 1.8 倍，而 OAI 的 TF1 Adam 只有 1.2 倍。**更大的 `policy/approxkl` 和 `policy/clipfrac`。** 由于更新过激，ratio 被裁剪的频率高 **4.4 倍**，近似 KL 散度大 **6 倍**。这种激进更新很可能引发后续问题。例如，`logprob_diff_mean` 在 PyTorch 的 `Adam` 中大 1.7 倍，对应下一次奖励计算中 KL 惩罚也大约 1.7 倍；这个效应会不断叠加。事实上这可能和著名的 KL 散度问题有关——KL 惩罚比应有的更大，模型可能更加在意它、优先优化它，进而导致负 KL 散度。
- **越大的模型受影响越严重。** 我们在 `gpt2` 和 `gpt2-xl` 上对比了 PyTorch 的 `Adam`（代号 `pt_adam`）和我们自定义的 TensorFlow 风格 Adam（代号 `tf_adam`）。发现 `gpt2` 下性能大体相似；而 `gpt2-xl` 上观察到更激进的更新，也就是说更大的模型受这个问题影响更大。  `gpt2-xl` 初期策略更新更激进时，训练动态随之受影响。例如 `pt_adam` 下 `objective/kl` 和 `objective/scores` 出现大得多的尖峰，`sentiment` 任务尤其明显——某个随机种子里最大 KL 高达 17.5，说明出现了不想要的过度优化。而且由于 KL 更大，许多其他训练指标也连带受影响，例如 `clipfrac`（`ratio` 被 PPO 目标裁剪系数 0.2 裁剪的频率）和 `approxkl` 都大得多。

## 局限

注意本工作没有尝试复现 CNN DM 或 TL;DR 的摘要任务。因为我们发现这类训练耗时且脆弱。

我们跑的那次训练 GPU 利用率很低（约 30%），所以一次训练要接近 4 天，成本极高（只有 AWS 卖 p3dn.24xlarge，每小时 31.212 美元）。

此外训练很脆弱。虽然奖励在上升，我们却难以复现 Ziegler et al. (2019) 报告的"聪明复印机（smart copier）"行为。下面是一些输出样例——显然智能体以某种方式过拟合了。更完整的日志见 [https://wandb.ai/openrlbenchmark/lm-human-preferences/runs/1ab47rqi/logs](https://wandb.ai/openrlbenchmark/lm-human-preferences/runs/1ab47rqi/logs?workspace=user-costa-huang)。

## 结论

本工作中我们深入研究了 OAI 的原始 RLHF 代码库，整理出一份实现细节清单。在数据集和超参数受控的条件下，我们建立的最小基座复现出了与 OAI 原始 RLHF 代码库相同的学习曲线。我们还发现了些出人意料的实现细节，比如 Adam 优化器的设置会在 RLHF 训练早期造成过激更新。
