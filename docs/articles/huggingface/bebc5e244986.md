# 构建 Hugging Face MCP Server

> TL;DR：Hugging Face 官方 MCP Server 为访问 Hub 的 AI 助手提供了独特的定制化选项，并通过一个简单的 URL 就能访问数千个 AI 应用。我们采用了 MCP 的「Streamable HTTP」传输方式进行部署，本节将详细剖析服务器开发者面临的权衡。
> 过去一个月里，我们在构建一个有用的 MCP server 方面学到了很多——这里讲讲我们的历程。

## 引言

Model Context Protocol（MCP）正在兑现它的承诺：成为连接 AI 助手与外部世界的标准。

对 Hugging Face 而言，通过 MCP 开放 Hub 访问是显而易见的选择。本文分享我们开发 [`hf.co/mcp`](https://hf.co/mcp) MCP Server 的经验。

## 设计选择

社区把 Hub 用于研究、开发、内容创作等等。我们希望人们能按自己的需求定制服务器，也能轻松访问 Spaces 上可用的数千个 AI 应用。这意味着要让 MCP Server 保持动态——随时调整用户的工具。

Hugging Face MCP 设置页，用户可以在这里配置自己的工具。

我们还希望让访问足够简单，避免复杂的下载和配置，因此「通过一个简单 URL 远程访问」是必选项。

## 远程服务器

构建远程 MCP Server 时，第一个决策是客户端如何连接它。MCP 提供了几种传输选项，各有取舍。**TL;DR：** 我们的开源代码支持全部变体，但生产环境我们选了最现代的那个。本节详细过一遍各选项。

自 2024 年 11 月发布以来，MCP 演进飞快，9 个月内出了 3 个协议修订版。期间 SSE 传输被 Streamable HTTP 取代，授权机制也经历了引入和重做。

这些快速变化意味着不同客户端对 MCP 特性和修订版的支持程度参差不齐，给我们的设计选择增添了额外挑战。

下面是 Model Context Protocol 及配套 SDK 提供的传输选项简表：

| 传输 | 说明 |
| --- | --- |
| `STDIO` | 通常用于 MCP Server 与客户端运行在同一台电脑上的情形。需要时可访问本地资源，如文件。 |
| `HTTP with SSE` | 用于经 HTTP 的远程连接。在 MCP 2025-03-26 版本中被标记弃用，但仍有使用。 |
| `Streamable HTTP` | 更灵活的远程 HTTP 传输，部署选项比即将退场的 SSE 版本更多 |

`STDIO` 和 `HTTP with SSE` 默认都是全双工的——客户端和服务器保持一条开放连接，可随时互发消息。

> SSE 指「Server Sent Events」——HTTP 服务器保持连接开放、按请求发送事件的一种方式。

#### 理解 Streamable HTTP

设置 Streamable HTTP 传输时，MCP 服务器开发者面临大量选择。

主要有 3 种通信模式可选：

- **直接响应（Direct Response）**——简单的请求/响应（类似标准 REST API）。适合直来直去的无状态操作，比如简单搜索。
- **请求级流（Request Scoped Streams）**——与单个请求关联的临时 SSE 流。当工具调用耗时较长（例如视频生成）时，适合用它发送[进度更新](https://modelcontextprotocol.io/specification/2025-06-18/basic/utilities/progress)。此外服务器可能需要通过 [Elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation) 向用户请求信息，或发起 Sampling 请求。
- **服务器推送流（Server Push Streams）**——长期存活的 SSE 连接，支持服务器主动发起的消息。这让 Resource、Tool 和 Prompt 列表变更通知，或即时的 Sampling 和 Elicitation 成为可能。这类连接需要额外的管理，例如[keep-alive](https://modelcontextprotocol.io/specification/2025-06-18/basic/utilities/ping) 和重连时的消息续传机制。

> 在使用官方 SDK 的请求级流时，请通过 RequestHandlerExtra 参数提供的 sendNotification() 和 sendRequest() 方法（TypeScript）或设置 related_request_id（Python）把消息发到正确的流上。

另一个要考虑的因素是 MCP 服务器本身是否需要为每个连接维护状态。这由服务器在客户端发来 Initialize 请求时决定：

|  | 无状态（Stateless） | 有状态（Stateful） |
| --- | --- | --- |
| **Session ID** | 不需要 | 服务器回复 `mcp-session-id` |
| **含义** | 每个请求相互独立 | 服务器维护客户端上下文 |
| **扩展** | 简单水平扩展：任何实例都能处理任何请求 | 需要会话亲和或共享状态机制 |
| **续传** | 不需要 | 可能对断线连接重放消息 |

下表总结 MCP 特性与支持的通信模式：

| MCP 特性 | 服务器推送 | 请求级流 | 直接响应 |
| --- | --- | --- | --- |
| Tools、Prompts、Resources | Y | Y | Y |
| Sampling/Elicitation | 服务器随时主动发起 | 关联到客户端发起的请求 | N |
| Resource 订阅 | Y | N | N |
| Tool/Prompt 列表变更 | Y | N | N |
| Tool 进度通知 | - | Y | N |

使用请求级流时，Sampling 和 Elicitation 请求需要有状态连接，这样才能用 `mcp-session-id` 关联响应。

> Hugging Face MCP Server 是开源的——支持 STDIO、SSE 和 Streamable HTTP 部署，且都支持直接响应和服务器推送两种模式。使用服务器推送流时，你可以配置 keep-alive 和最后活动时间超时。它还内置一个可观测性 dashboard，帮助你理解不同客户端如何管理连接、如何处理 Tool 列表变更通知。

### 生产部署

生产环境，我们决定以无状态、直接响应的 Streamable HTTP 配置上线 MCP Server，理由如下：

**无状态**：对匿名用户，我们提供一套标准的 Hub 使用工具加一个图像生成器。对已认证用户，状态就是其[所选工具](https://huggingface.co/settings/mcp)和选定的 Gradio 应用。我们还会确保用户账号的 ZeroGPU 配额被正确应用。这通过请求时查询提供的 `HF_TOKEN` 或 OAuth 凭证来管理。我们现有工具都不需要在请求之间维护任何其他状态。

> 你可以在 MCP Server 地址后加 ?login 来使用 OAuth 登录——例如 https://huggingface.co/mcp?login. claude.ai 的远程集成支持最新 OAuth 规范，我们可能把它设为默认。

**直接响应**的部署资源开销最低——我们目前没有工具在执行中需要 Sampling 或 Elicitation。

**未来支持**：上线之初，「HTTP with SSE」仍是许多 MCP 客户端的默认远程传输。但由于它即将弃用，我们不想在维护它上投入过多。幸运的是，主流客户端已经开始了切换（VSCode 和 Cursor），上线一周内 `claude.ai` 也加上了支持。如果你确实需要用 SSE 连接，欢迎在 [FreeCPU Hugging Face Space](https://huggingface.co/new-space) 上部署一份我们服务器的副本。

#### Tool 列表变更通知

未来，我们希望在用户更新 Hub 设置时支持实时的 Tool List Changed 通知。但这引出两个实际问题：

第一，用户倾向于把常用的 MCP Server 配置进客户端然后一直开着。这意味着客户端在应用打开期间始终保持连接。要发通知，就得维持与当前活跃客户端数量一样多的开放连接——不管它们是否真的在用——只为防备用户随时可能更新其工具配置。

第二，大多数 MCP 服务器和客户端在一段时间不活动后会断开，需要时再重连。这必然导致即时推送通知会被错过——通知通道那时已经关了。实践中，由客户端按需刷新连接和 Tool 列表要简单得多。

除非你对客户端/服务器这对组合有相当的控制力，否则在公共部署里使用**服务器推送流**会带来大量复杂度——而刷新 Tool 列表明明存在更省资源的方案。

#### URL 用户体验

上线前，[`@julien-c`](https://huggingface.co/julien-c) 提交了一个 PR，为访问 `hf.co/mcp` 的用户提供友好的说明。这极大改善了用户体验——否则默认响应只是一段不友好的 JSON。

最初，我们发现这产生了巨量流量。调查之后我们发现问题在于：当返回网页而不是 HTTP 405 错误时，VSCode 会每秒轮询该端点多次！

[`@coyotte508`](https://huggingface.co/coyotte508) 给出的修复方案是正确检测浏览器、只在这种情况下返回页面。也要感谢 VSCode 团队迅速[修好了它](https://github.com/microsoft/vscode/pull/251288/files)。

虽然规范没有明说——以这种方式返回页面*看起来*确实符合 MCP 规范。

#### MCP 客户端行为

MCP 协议在初始化期间会发送多个请求。典型连接序列是：`Initialize`、`Notifications/Initialize`、`tools/list`，然后是 `prompts/list`。

考虑到 MCP 客户端在打开期间会不断连接和重连，加上用户会周期性调用，我们发现大约每 1 次 Tool 调用对应 100 条 MCP 控制消息。

一些客户端还会发送与我们无状态、直接响应配置不搭调的请求——比如 Ping、Cancellation 或尝试列出 Resources（这不是我们当前声明的能力）。

2025 年 7 月第一周，访问我们服务器的客户端多达惊人的 164 种。有意思的是，最受欢迎的工具之一是 [`mcp-remote`](https://github.com/geelen/mcp-remote)。大约一半的客户端用它作为桥接来连接我们的远程服务器。
