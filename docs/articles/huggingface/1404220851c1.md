# VibeGame：探索 Vibe 编码游戏

## 问题

人们正在尝试用 vibe coding 做游戏。一开始，它还真行。但随着项目变大，事情开始分崩离析。为什么？我们能怎么办？

下面谈谈这个问题、我是怎么修的，以及接下来往哪走。

## 什么是 "Vibe Coding"？

先说什么是 vibe coding。这个词最早出自 Andrej Karpathy 的一条[爆款推文](https://x.com/karpathy/status/1886192184808149383)，定义是"完全交给感觉、拥抱指数级增长、忘掉代码的存在"。

但从那以后，这个词被拿来描述很多不同的东西，从泛泛的"用 AI 写代码"一直到"完全不思考代码本身"。在这篇博客里，我把它定义为：**把 AI 当作一门高级编程语言来构建东西**。和其他编程语言一样，理解底层发生了什么会有好处，但不是必需。

按这个理解，你不懂代码也能做游戏——当然，懂点基础仍然有帮助。

## 上下文管理

前面我说"项目一大，事情就开始崩"。这是因为有[证据](https://huggingface.co/blog/helmet)表明：上下文窗口填满后，模型性能会开始退化。游戏开发尤其如此——上下文可能又大又快地膨胀。

应对这个问题，有很多个人化的临时方案：比如把 LLM 专用的上下文直接写进项目文件，或者更系统的大型上下文管理方案，如 [Claude Code Development Kit](https://github.com/peterkrueck/Claude-Code-Development-Kit)。

我找不到一个轻量、易上手、且不依赖大量领域知识的方案，于是自己做了一个：🧅 [Shallot](https://github.com/dylanebert/shallot)——一个简单、轻量、不带立场的 Claude Code 上下文管理系统。它只依赖两条基本命令：

- `/peel [prompt]`：对话开始时加载上下文
- `/nourish`：对话结束时更新上下文

从体感上看，这很好用。不过它在项目保持精简、组织良好时效果最佳——这样所有相关上下文才能轻松装进模型的上下文窗口。这里用的是 Claude Code，但同样的原理适用于其他模型。

除了上下文管理工具，平台选择也至关重要。理想平台应该用高级抽象天然保持项目精简，同时也是 AI 模型熟悉的领域。那么，现有平台里哪些最适合 vibe coding？

## 初步探索

我最初尝试了 3 条 vibe coding 游戏路线：Roblox MCP、Unity MCP 和 Web。每条路线我都用 Claude Code 做一个受 [Grass Cutting Incremental](https://roblox-grass-cutting-incremental.fandom.com/wiki/Roblox_Grass_Cutting_Incremental_Wiki) 启发的简单放置类游戏。

结果如下：

### 尝试 1：Roblox MCP

Roblox 的[官方 MCP 服务器](https://github.com/Roblox/studio-rust-mcp-server)。它让 AI 通过发送执行代码的命令与 Roblox Studio 交互。

优点：

- 抽象层次出色，内置游戏机制
- AI 能非常轻松理解语法、把指令转成代码

缺点：

- 没有文件，只能用代码读数据，严重限制上下文管理
- AI 可获得的运行时信息非常有限
- 专有围墙花园

Roblox 提供了出色的抽象层，代码库保持精简可控，完美契合 vibe coding。但围墙花园加上上下文缺失，让它在 Roblox 内部之外几乎不可行。

### 尝试 2：Unity MCP

Unity 的[非官方 MCP 服务器](https://github.com/CoplayDev/unity-mcp)。它让 AI 与 Unity Editor 交互：读控制台、管理资产、校验脚本。

优点：

- 完整的文件系统访问

缺点：

- Unity 里每件事都有很多做法，且随版本频繁变化，AI 容易犯迷糊
- 需要相当多的领域知识告诉 AI *怎么做*，而不是*做什么*
- AI 表现不稳定、不可靠
- 专有引擎（虽然比 Roblox 透明得多）

Unity 是一个功能强大的引擎。但引擎的复杂与多变，让用户不给足领域知识，AI 就很难稳定产出好结果。

### 尝试 3：Web 技术栈

开放的 Web 平台：[three.js](https://threejs.org/) 做 3D 渲染，[rapier](https://rapier.rs/) 做物理，[bitecs](https://github.com/NateTheGreatt/bitECS) 做游戏逻辑。

优点：

- AI 熟练度远超游戏引擎——很可能得益于海量训练数据
- 完整的文件系统访问
- 全开源技术栈，完全掌控、完全透明

缺点：

- 库偏底层，基本要先造引擎再做游戏
- 缺少高质量 3D 游戏生态；Web 更常见的是 2D 游戏和简单 3D 体验

这条路 AI 表现好得多——大概是训练时见过的 Web 开发数据太多了。但库太底层，意味着我得先造一个游戏引擎才能做游戏本身。造好之后，我们就能像在 Roblox 里那样，在更高的抽象层上工作。

虽然要先造引擎，但这是在用户没有深厚领域知识时，唯一产出有趣结果的路。

### 对比总结

| 平台 | AI 表现 | 抽象层次 | 上下文管理 | 开源 |
| --- | --- | --- | --- | --- |
| Roblox | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐ | ❌ |
| Unity | ⭐ | ⭐⭐ | ⭐⭐⭐ | ❌ |
| Web | ⭐⭐⭐⭐⭐ | ⭐ | ⭐⭐⭐⭐⭐ | ✅ |

## 解决方案：VibeGame

这些实验之后，图景很清晰：Web 栈 AI 表现优秀但太底层，Roblox 抽象完美但不开放、缺上下文管理。

那么，把两者的优点合起来怎么样？

介绍 [VibeGame](https://github.com/dylanebert/vibegame)：一个构建在 three.js、rapier 和 bitecs 之上的高层声明式游戏引擎，专为 AI 辅助游戏开发设计。

### 设计理念

VibeGame 的设计有三个关键决策：

- **抽象：** 高层抽象，内置物理、渲染和常见游戏机制，保持代码库精简可控。灵感来自 Roblox、Fortnite UEFN、Minecraft 这类流行的沙盒游戏/游戏"引擎"。
- **语法：** 定义游戏对象及其属性的声明式类 XML 语法，让 AI 容易理解并生成代码。这和 AI 模型本就熟练的 HTML/CSS 类似。
- **架构：** 采用实体-组件-系统（ECS）架构保证可扩展与灵活。ECS 把数据（组件）和行为（系统）分离，促使项目变大时依旧模块化和有序——天然适合 vibe coding 和上下文管理。

一个基础游戏长这样：

```
<world canvas="#game-canvas" sky="#87ceeb">
  <!-- Ground -->
  <static-part pos="0 -0.5 0" shape="box" size="20 1 20" color="#90ee90"></static-part>

  <!-- Ball -->
  <dynamic-part pos="-2 4 -3" shape="sphere" size="1" color="#ff4500"></dynamic-part>
</world>

<canvas id="game-canvas"></canvas>

<script type="module">
  import * as GAME from 'vibegame';
  GAME.run();
</script>
```

在 [JSFiddle](https://jsfiddle.net/keLsxh5t/) 或 [Live Demo](https://huggingface.co/spaces/dylanebert/VibeGame) 看效果。

这会创建一个带地面和下落小球的最简场景。玩家、相机和光照自动创建。所有部分都是模块化的、可替换的。需要时可以随意添加自定义组件和系统。

引擎附带一份 [llms.txt](https://raw.githubusercontent.com/dylanebert/VibeGame/refs/heads/main/llms.txt) 文档文件，专为 AI 编写的引擎说明，放进它的系统提示词或初始上下文。

## 它真的管用吗？

管。

嗯，基本上吧。

[这个游戏](https://huggingface.co/spaces/dylanebert/grass_cutting_game)就是我用 VibeGame 加 Claude Code 做的测试——一个收集草的简单放置游戏。效果很好，实现核心玩法几乎不需要领域知识。

[![Grass Cutting Game](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vibegame/grass_cutting_game.gif)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vibegame/grass_cutting_game.gif)

但仍有一些重大前提：

- 引擎支持范围内它很好用——比如简单平台游戏或只靠基础物理与渲染的游戏。
- 但对引擎还没实现的更复杂的东西——交互、背包、多人、战斗等——就力不从心。

所以，如果 vibe coding 的定义是一次性"给我做个游戏"，那它不行。但如果按"把 vibe coding 当作一门高级编程语言"的定义，它很好用——前提是用户理解引擎的能力边界。

## 自己动手试

想马上体验：我做了一个在浏览器里用 VibeGame 配 [Qwen3-Next-80B-A3B-Instruct](https://huggingface.co/Qwen/Qwen3-Next-80B-A3B-Instruct) 直接开发游戏的 demo：[Hugging Face 在线演示](https://huggingface.co/spaces/dylanebert/VibeGame)。

你也可以在本地配合 Claude Code 这样的前沿模型测试：

```
npm create vibegame@latest my-game
cd my-game
npm run dev  # or bun dev
```

然后把随附 `llms.txt` 的全部内容粘贴到 `CLAUDE.md` 里，给 AI 提供完整的引擎文档（或让你的上下文管理系统指向它）。其他模型也同样适用。

## 接下来？

引擎目前非常简陋，只支持很基础的机制（除非你自己从零写）。但初步成果令人鼓舞。

下一步包括：

- 充实引擎、增加更多内置机制，向 Roblox / UEFN 早期版本看齐。包括：

- 交互
- 背包/道具
- 多人
- 带精选资源库的蒙皮网格/动画
- 带精选资源库的音频

- 改进 AI 引导系统，让新手有更好的体验。包括：

- 关于引擎能力/限制清晰的信息
- 常见任务的引导式提示词
- 更多例子和模板
- 教育资源

同样值得探索的是：vibe coding 游戏如何借力更成熟的引擎。例如在 Unity 或虚幻引擎之上搭高层沙盒游戏编辑器（类似虚幻编辑器之于 Fortnite 的关系），既能利用成熟引擎的能量，又给 AI 一个更可控的工作环境。

预计我们也会看到更多大厂自研的方案。
