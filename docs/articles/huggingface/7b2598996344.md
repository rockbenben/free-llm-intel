# 10 亿次分类

模型优化好了，流水线也跑得顺了。结果云账单飞天了。每天 10 亿+ 次分类或嵌入，不只是技术挑战——更是财务挑战。怎么在这个规模下处理数据还不把预算炸掉？无论你是在做大规模文档分类，还是为检索增强生成（RAG）批量跑嵌入流水线，都需要高性价比、高吞吐的推理才能让这事可行——而这来自一套调优到位的配置。

这类任务常用的是[编码器模型](https://huggingface.co/learn/nlp-course/en/chapter1/5)，比现代 LLM 小得多，但在 10 亿+ 推理请求的规模下，依然是个不轻松的任务。说直观一点：那相当于 [英文维基百科](https://en.wikipedia.org/wiki/Wikipedia:Size_of_Wikipedia) 的 144 倍。我没怎么见过"以成本为前提该怎么做"的资料，所以想亲自动手解决。**这篇博客拆解如何计算大规模分类和嵌入的成本与延迟**。我们会分析不同的模型架构，在不同硬件选项上比较成本，并给你一个清晰的框架来优化你自己的配置。另外如果你不想亲自跑一遍这个流程，看完也能建立一些直觉。

你可能有几个问题：

- 处理 10 亿输入，最便宜的配置是什么？（批量推理）
- 同时考虑延迟的话怎么做？（重度使用）

## 方法

要评估成本和延迟，我们需要 4 个关键组件：

- **硬件选项**：一批可供比价的硬件
- **部署工具**：按我们的设定部署模型的方式
- **压测**：发送请求并度量性能的方式
- **推理服务器**：在选定硬件上高效跑模型的方式

**硬件选项**我用了 [Inference Endpoints](https://huggingface.co/inference-endpoints/dedicated)，因为它让我在[很广](https://huggingface.co/docs/inference-endpoints/pricing#gpu-instances)的硬件范围内选择。你也可以换成自己考虑的任何 GPU。**部署工具**用的是永远好使的 [Hugging Face Hub 库](https://huggingface.co/docs/huggingface_hub/guides/inference_endpoints#inference-endpoints)，它能以编程方式轻松部署模型。

**推理服务器**我也用了 [Infinity](https://github.com/michaelfeil/infinity/)——一个为编码器模型（现在还支持更多！）服务的出色库。我之前[已经写过](https://huggingface.co/learn/cookbook/automatic_embedding_tei_inference_endpoints) [TEI](https://huggingface.co/docs/text-embeddings-inference/en/index)，它同样是了不起的库。面对你的用例当然值得考虑 TEI，不过本文聚焦方法论而非框架对比。Infinity 有几个关键优势：支持多模态嵌入、面向不同硬件（AMD、Nvidia、CPU 和 Inferentia）、能运行任何包含 remote code、尚未并入 huggingface transformer 库的新模型。对我来说最重要的是：大多数模型默认就兼容。

**压测**用的是 Grafana 家的 [k6](https://k6.io)——一个用 Go 编写、JS 接口的开源压测工具。配置容易，性能高，开销低。它内置大量极其有用的[执行器（executors）](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/)。它还会预分配虚拟用户（VUs），比你自己随手攒一个测试要真实得多。

### 压测参数

VUs 和 Batch Size 很重要，因为它们决定我们把 GPU 上所有可用算力用到多好。足够大的 Batch Size 确保 Streaming Multiprocessors 和显存被充分使用。有些场景显存还有余，但带宽成本会阻止吞吐继续上升——所以实验能帮我们。VUs 则确保我们把可用的批大小真正喂满。
以下是我要测的主要参数：

- `INFINITY_BATCH_SIZE`：一个批次里有多少文档在同一次模型前向传播中处理。太低就吃不满 GPU；太高 GPU 扛不住大输入
- `VUs`：发给 K6 的、模拟并发客户端请求的虚拟用户数。要模拟大量用户不容易，且取决于机器
- GPU：Inference Endpoints 上有[多种](https://huggingface.co/docs/inference-endpoints/pricing#gpu-instances)GPU 可用，我优先选性能/成本比最好的
- CPU：我把它们略过了，因为 Nvidia-T4 太便宜，轻测之下 CPU 没什么吸引力。不过留了测试代码，感兴趣的用户可以自己跑！

根据你的模型，你可能还想考虑：

- 用哪个 Docker 镜像。[`'michaelf34/infinity:0.0.75-trt-onnx'`、`'michaelf34/infinity:0.0.75'`]。[Infinity 镜像](https://github.com/michaelfeil/infinity?tab=readme-ov-file#specialized-docker-images)有多种，支持不同后端。应选择最匹配你硬件/模型/配置的那个
- `INFINITY_COMPILE`：要不要用 `torch.compile()` [文档](https://pytorch.org/tutorials/intermediate/torch_compile_tutorial.html)
- `INFINITY_BETTERTRANSFORMER`：要不要让 torch 使用 [Better Transformer](https://huggingface.co/docs/optimum/en/bettertransformer/overview)

### K6

K6 好用在于它能预分配 VUs，避免一些阴险的 bug；发请求的方式也很灵活。我选择了一种特定用法。

调用 k6 实验时，我主要想知道请求的吞吐和平均延迟，并对所选压测参数做几个健全性检查。我还想做参数扫描，这意味着很多次实验。

我用 `shared-iterations` 执行器（[文档](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/shared-iterations/)），即 K6 在各 VU 之间分摊迭代次数，k6 执行完所有迭代即结束。这样既能有合理超时，又发够请求，让我有信心在扫描中区分不同压测参数的选择。与其他执行器相比，这种方式能确保每个 VU 都在拼命模拟客户端，从而告诉我最便宜的选项是什么。

我用 `10_000` 个请求†，单次实验最长 `1 分钟`。10_000 请求如果 1 分钟内跑不完，这次实验就算结束。

```
export const options = {
    scenarios: {
        shared_load_test: {
            executor: 'shared-iterations',
            vus: {{ pre_allocated_vus }}, 
            iterations: 10000, 
            maxDuration: '1m',
        },
    },
};
```

#### 统计量

- P95†† 与平均延迟
- 吞吐

#### 健全性检查

- 准确率（仅分类）
- 测试时长
- 成功请求数
- 格式校验

† 视觉嵌入用例我用了更少的请求上限，因为吞吐低得多，图片也重。
†† P95 指 95% 的请求在此时间内完成，代表多数用户的最坏情况延迟。

## 分类

### 引言

[文本分类](https://huggingface.co/docs/transformers/en/tasks/sequence_classification)在规模下有各种用例，比如邮件过滤、预训练数据集的毒性检测等。老牌经典架构是 BERT，随后很快出现了许多其他架构。注意：与流行的解码器模型不同，这些模型需要先在你的任务上微调才能使用。我认为当今最值得关注的**架构**†有：

- [DistilBERT](https://huggingface.co/docs/transformers/model_doc/distilbert)：任务表现好，工程表现也好。它对原始 BERT 做了些架构改动，做分类时与 TEI 不兼容
- [DeBERTa-v3](https://huggingface.co/microsoft/deberta-v3-base)：任务表现优秀。工程表现††很慢，因为它独特的注意力机制难以优化
- [ModernBERT](https://huggingface.co/blog/modernbert)：使用序列打包和 Flash-Attention-2。任务表现和工程表现††都优秀

† 对这些模型，*通常*需要在你的数据上微调才能有好表现
†† 我用"工程表现"指代预期的延迟/吞吐

## 嵌入

### 引言

文本嵌入是一种比较宽泛的说法，指的是把文本输入投影到一个语义空间：距离近的点含义相似，距离远的点含义不同（示例见下）。它在 RAG 里大量使用，也是 AI 搜索的重要组成（有人[挺喜欢](https://yellow-apartment-148.notion.site/AI-Search-The-Bitter-er-Lesson-44c11acd27294f4495c3de778cd09c8d)的）。
[![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/billion-classifications/embedding.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/billion-classifications/embedding.png)

兼容的架构非常多，性能最强的可以在 [MTEB 排行榜](https://huggingface.co/spaces/mteb/leaderboard)上看到。

### 实验

ModernBERT 是自 2020 年 DeBERTa 之后最令人兴奋的编码器发布。它把一堆*咳咳*现代技巧内置进了一个古老又眼熟的架构里。它很适合拿来做实验——远没有别的架构被探索得那么透，潜力还大。速度和性能上有不少改进，但对用户最显眼的很可能是 8k 上下文窗口。想更透彻了解请看这篇[博客](https://huggingface.co/blog/modernbert)。

重要说明：Flash Attention 2 受计算能力要求限制，只在较新的 GPU 上可用，所以我略过 T4 直接用 L4。至于"大力出奇迹"档，H100 在这里也会非常能打。

## 视觉嵌入

### 引言

ColQwen2 是一个视觉检索器，基于 [Qwen2-VL-2B-Instruct](https://huggingface.co/Qwen/Qwen2-VL-2B-Instruct)，对文本和图像采用 ColBERT 风格的多向量表示。可以看出，相比我们前面探索的编码器，它的架构复杂得多。

[![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/billion-classifications/qwen2_vl.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/billion-classifications/qwen2_vl.png)

有不少用例可能从大规模这种能力中受益，比如电商搜索、多模态推荐、企业多模态 RAG 等

ColBERT 风格与前面的嵌入用例不同：它把输入拆成多个 token，每个 token 返回一个向量，而不是整个输入一个向量。Jina AI 有一篇极好的教程，在[这里](https://jina.ai/news/what-is-colbert-and-late-interaction-and-why-they-matter-in-search/)。这能带来更优秀的语义编码和更好的检索，但也更慢、更贵。

这个实验我很期待，因为它探索了两个相对少见的概念：视觉嵌入和 ColBERT 风格嵌入†。关于 ColQwen2/VLM 有几点要注意：

- 2B 比本文其他模型大约大 15 倍
- ColQwen2 架构复杂，包含多个模型，其中还有比编码器更慢的解码器
- 图像很容易吃掉大量 token
- API 成本：通过 API 传图比传文本慢。如果在云上，还会遇到更高的出口流量费用

†如果这对你新颖有趣，请看看这篇[更详细的博客](https://danielvanstrien.xyz/posts/post-with-code/colpali-qdrant/2024-10-02_using_colpali_with_qdrant.html)。

## 结论

扩展到每天 10 亿+ 次分类或嵌入绝非易事，但优化得当就能做到有性价比。从我的实验里，浮现出几个关键模式：

- 硬件很关键——NVIDIA L4（$0.80/小时）在性能和成本之间持续提供最佳平衡，现代负载下优于 T4。CPU 在规模下没有竞争力。
- Batch Size 至关重要——最佳批大小因任务而异，但总体上，在不触顶 GPU 显存和带宽的前提下把批开大，是效率的关键。分类的最佳值是 64；嵌入是 32。
- 并行度是关键——找到合适的虚拟用户数（VUs）才能保证 GPU 被完全利用。指数递增 + 二分搜索的办法帮我们高效收敛到最佳 VU 设置。
- ColBERT 风格视觉嵌入很贵——每 10 亿嵌入超过 $44,000，图像检索比文本任务贵了 2 个数量级。

你的数据、硬件、模型等可能都不同，但我希望这套方法和[代码](https://github.com/datavistics/encoder-analysis)对你有用。想要靠谱的估算，最好的方式就是用自己的任务、自己的配置跑一遍。去探索吧！

### 健全性检查

复杂度上升时，健全性检查也要跟着升级。由于我们是用 `subprocess` 和 `jinja` 去调用 `k6`，离实际测试有点远，所以我设了几道检查。

#### 任务表现

任务表现检查的目标是：某个具体配置下，我们的表现符合预期。任务表现在不同任务里含义不同。分类我选了准确率，嵌入则跳过了——也可以看平均相似度之类的指标。ColBERT 风格每个请求返回多个向量，就更复杂些。

虽然 58% 对某些三分类任务不算差，但这并不重要。**目标是要确认我们得到了预期的任务表现。**如果看到显著变化（升高或降低），就该警惕并弄清楚原因。

下面是一个分类用例的绝佳例子——分布极其紧凑，只有一个离群点。进一步排查后，离群点是因为发出的请求量太少。[![](https://github.com/datavistics/encoder-analysis/blob/main/media/classification-accuracy.png?raw=true)](https://github.com/datavistics/encoder-analysis/blob/main/media/classification-accuracy.png?raw=true)

#### 失败请求检查

我们应该预期零失败请求，因为 Inference Endpoints 有队列可以消化多出来的请求。这对三个用例都适用：分类、嵌入和视觉嵌入。

`sum(df.total_requests - df.successful_requests)` 可以让我们看是否有失败请求。

#### 单调序列——VUs 试够了吗？

如前所述，我们用指数递增加二分搜索来找最佳 VU 数。但怎么知道试的 VUs 够多了？如果更高的 VUs 数量下吞吐还在涨呢？那就表现为 VUs 与吞吐之间单调递增的关系，我们需要继续跑更多测试。

#### 成本 vs 延迟

这是一张关键图表，因为很多用例存在用户可感知的最大延迟上限。通常，如果允许延迟上升，吞吐也能上升，于是形成权衡场景。在我考察的所有用例里都是如此。有一条 pareto 曲线，能很好地可视化这个权衡在哪。

#### 成本 vs VUs 和 Batch Size 的等高线图

最后，建立"不同设置下发生了什么"的直觉很重要。我们会得到漂亮的理想化图表吗？会看到意外的梯度吗？某个区域需要更多探索吗？我们的设置会不会有问题，比如环境不隔离？这些都是好问题，有些还不好回答。

等高线图由在这个三维空间（VUs、batch_size、成本）定义的空间内插中间点构成。有几个现象值得理解：

- 颜色渐变：表示成本水平，颜色越深成本越高，越浅越低。
- 等高线：代表成本水平，帮助识别性价比区域。
- 等高线密集簇：说明 batch size 或 VUs 的微小调整会让成本剧烈变化。

### 其他经验教训

- 我试过在同一张 GPU 上部署多个模型，尽管显存和算力都有富余，也没看到明显改善——很可能是处理大批次的带宽成本所致
- 让 K6 处理图片一度很折磨，直到我发现了 [SharedArrays](https://grafana.com/docs/k6/latest/javascript-api/k6-data/sharedarray/)
- 图像数据真的很难伺候
- 当你用脚本生成 K6 测试时，调试的关键是手动跑一次 K6 并看输出。
