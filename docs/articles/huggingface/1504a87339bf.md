# 从零到 GPU：构建与扩展生产级 CUDA 内核指南

> 自本文发布以来，我们已对 Kernels 项目进行了改版。
> 更新内容见这里。

自定义 CUDA 内核（kernel）能给你的模型带来显著的性能优势，但要为真实场景构建它们可能令人望而生畏。怎样才能超越一个简单 GPU 函数，打造健壮、可扩展的系统，而不被无尽的编译时间和依赖噩梦拖垮？

我们为此创建了 [`kernel-builder` 库](https://github.com/huggingface/kernels)。你可以在本地开发自定义内核，然后为多种架构构建，并发布给全世界使用。

本指南将带你从零构建一个完整的现代 CUDA 内核，然后直面开发与部署中的棘手挑战，借鉴真实工程实践，教你构建既快又高效、还易维护的系统。

```

## 第一部分：现代 CUDA 内核的解剖

我们来做一个实用的内核：把图像从 RGB 转为灰度。这个例子使用 PyTorch 的现代 C++ API，把我们的函数注册为一个原生的、一等公民的算子（operator）。

### 第 1 步：项目结构

清晰、可预期的结构是好项目的地基。Hugging Face Kernel Builder 期望你的文件按如下组织：

```
img2gray/
├── build.toml
├── csrc
│   └── img2gray.cu
├── flake.nix
└── torch-ext
    ├── torch_binding.cpp
    ├── torch_binding.h
    └── img2gray
        └── __init__.py
```

- **`build.toml`**：项目清单文件，是构建流程的大脑。
- **`csrc/`**：原始 CUDA 源代码，GPU 的魔法在这里发生。
- **`flake.nix`**：完美可复现构建环境的钥匙。
- **`torch-ext/img2gray/`**：原始 PyTorch 算子的 Python 封装。

### 第 2 步：`build.toml` 清单

这个文件指挥整个构建过程，告诉 `kernel-builder` 编译什么、各部分如何连接。

```
# build.toml
[general]
name = "img2gray"
universal = false

# Defines the C++ files that bind to PyTorch
[torch]
src = [
  "torch-ext/torch_binding.cpp",
  "torch-ext/torch_binding.h"
]

# Defines the CUDA kernel itself
[kernel.img2gray]
backend = "cuda"
depends = ["torch"] # This kernel depends on the Torch library for the `Tensor` class.
src = [
    "csrc/img2gray.cu",
]
```

### 第 3 步：`flake.nix` 可复现性文件

为了确保任何人、在任何机器上都能构建你的内核，我们使用 `flake.nix` 文件。它锁定 `kernel-builder` 及其依赖的精确版本，杜绝"在我机器上是好的"这类问题。

```
# flake.nix
{
  description = "Flake for img2gray kernel";

  inputs = {
    kernel-builder.url = "github:huggingface/kernels";
  };

  outputs =
    {
      self,
      kernel-builder,
    }:
    kernel-builder.lib.genFlakeOutputs {
      path = ./.;
      rev = self.shortRev or self.dirtyShortRev or self.lastModifiedDate;
    };
}
```

### 第 4 步：编写 CUDA 内核

轮到 GPU 代码了。在 **`csrc/img2gray.cu`** 中，我们定义一个使用二维线程网格的内核——对图像处理来说自然又高效。

```
// csrc/img2gray.cu
#include <cstdint>
#include <torch/torch.h>

// This kernel runs on the GPU, with each thread handling one pixel
__global__ void img2gray_kernel(const uint8_t* input, uint8_t* output, int width, int height) {
    int x = blockIdx.x * blockDim.x + threadIdx.x;
    int y = blockIdx.y * blockDim.y + threadIdx.y;

    if (x < width && y < height) {
        int idx = (y * width + x) * 3; // 3 channels for RGB
        uint8_t r = input[idx];
        uint8_t g = input[idx + 1];
        uint8_t b = input[idx + 2];

        // Luminance conversion
        uint8_t gray = static_cast<uint8_t>(0.21f * r + 0.72f * g + 0.07f * b);
        output[y * width + x] = gray;
    }
}

// This C++ function launches our CUDA kernel
void img2gray_cuda(torch::Tensor const &input, torch::Tensor &output) {
    const int width = input.size(1);
    const int height = input.size(0);

    // Define a 2D block and grid size for image processing
    const dim3 blockSize(16, 16);
    const dim3 gridSize((width + blockSize.x - 1) / blockSize.x, (height + blockSize.y - 1) / blockSize.y);

    img2gray_kernel<<<gridSize, blockSize>>>(
        input.data_ptr<uint8_t>(),
        output.data_ptr<uint8_t>(),
        width,
        height
    );
}
```

### 第 5 步：注册原生 PyTorch 算子

这是最重要的一步。我们不只是绑定到 Python，而是把函数注册为原生 PyTorch 算子，让它成为 PyTorch 生态中的一等公民，在 `torch.ops` 命名空间下可见。

注册工作由 **`torch-ext/torch_binding.cpp`** 完成。

```
// torch-ext/torch_binding.cpp
#include <torch/library.h>
#include "registration.h" // included in the build
#include "torch_binding.h" // Declares our img2gray_cuda function

TORCH_LIBRARY_EXPAND(TORCH_EXTENSION_NAME, ops) {
  ops.def("img2gray(Tensor input, Tensor! output) -> ()");
  ops.impl("img2gray", torch::kCUDA, &img2gray_cuda);
}

REGISTER_EXTENSION(TORCH_EXTENSION_NAME)
```

简单说，`TORCH_LIBRARY_EXPAND` 让我们以未来易于扩展或修改的方式定义算子。

#### 为什么这很重要

这种做法有两个关键原因：

- **兼容 `torch.compile`**：这样注册内核后，`torch.compile` 能"看见"它。PyTorch 因此可以把你的自定义算子融合进更大的计算图，最小化开销、最大化性能。这是让你的自定义代码无缝融入 PyTorch 整体性能生态的关键。
- **针对硬件的差异化实现**：这套系统允许你为同一个算子提供不同后端。你可以再加一个 `TORCH_LIBRARY_IMPL(img2gray, CPU, ...)` 块指向一个 C++ CPU 函数。PyTorch 的调度器（dispatcher）会根据输入张量所在设备自动调用正确的实现（CUDA 或 CPU），让你的代码既强大又可移植。**配置 `__init__.py` 封装**

在 `torch-ext/img2gray/` 中需要一个 `__init__.py` 文件，把这个目录变成 Python 包，并以友好的方式暴露我们的自定义算子。

> _ops 模块由 kernel-builder 从模板自动生成，为你注册的 C++ 函数提供标准命名空间。

```
# torch-ext/img2gray/__init__.py
import torch

from ._ops import ops


def img2gray(input: torch.Tensor) -> torch.Tensor:
    # we expect input to be in CHW format
    height, width, channels = input.shape
    assert channels == 3, "Input image must have 3 channels (RGB)"

    output = torch.empty((height, width), device=input.device, dtype=input.dtype)
    ops.img2gray(input, output)

    return output
```

### 第 6 步：构建内核

内核和绑定都就绪了，该构建了。`kernel-builder` 工具让这一步很简单。

你可以用一条命令 `nix build . -L` 构建内核；但作为开发者，我们会想要更快、可迭代的开发流程。为此，我们用 `nix develop` 命令进入一个预装全部依赖的开发 shell。

更具体地说，我们可以挑选要使用的精确 CUDA 和 PyTorch 版本。例如，要为 PyTorch 2.7 + CUDA 12.6 构建内核，可以使用如下命令：

#### 进入 Nix Shell

```
# Drop into a Nix shell (an isolated sandbox with all dependencies)
nix develop .#devShells.torch28-cxx11-cu128-x86_64-linux
```

注意，上面 `devShell` 的名字可以这样解读：

```
nix develop .#devShells.torch27-cxx11-cu126-x86_64-linux
                        │       │         │       │
                        │       │         │       └─── Architecture: x86_64 (Linux)
                        │       │         └────────── CUDA version: 12.6
                        │       └──────────────────── C++ ABI: cxx11
                        └──────────────────────────── Torch version: 2.7
```

此时我们已身处安装了所有依赖的 Nix shell 中，可以为这个特定架构构建内核并测试它。多架构和最终分发的问题稍后处理。

#### 生成构建产物

```
build2cmake generate-torch build.toml
# this creates: torch-ext/img2gray/_ops.py, pyproject.toml, torch-ext/registration.h, setup.py, cmake/hipify.py, cmake/utils.cmake, CMakeLists.txt
```

这条命令会创建一批用于构建内核的文件：`CMakeLists.txt`、`pyproject.toml`、`setup.py` 以及一个 `cmake` 目录。`CMakeLists.txt` 是 CMake 构建内核的主入口。

#### 创建 Python 虚拟环境

```
python -m venv .venv
source .venv/bin/activate
```

现在你可以以可编辑模式安装内核了。

#### 编译内核并安装 Python 包

```
pip install --no-build-isolation -e .
```

🙌 太棒了！我们现在有了一个自定义构建的内核：遵循 PyTorch 绑定的最佳实践，构建流程完全可复现。

#### 开发循环

为确保一切正常，我们可以跑一个简单的测试，检查内核是否注册成功、行为是否符合预期。如果不对，就编辑源文件、重复构建，复用刚创建的 nix 环境即可。

```

### 第 7 步：分享给全世界

内核能用了，是时候分享给其他开发者了！

分享之前，先要做一件小事：清理构建过程产生的所有开发产物，避免上传不必要的文件。

```
build2cmake clean build.toml
```

#### 为所有 PyTorch 和 CUDA 版本构建内核

之前我们只为某个特定 PyTorch 和 CUDA 版本构建了内核。要让更广泛的用户群能使用它，就要为所有受支持版本构建。`kernel-builder` 工具可以帮忙。

这也是 `compliant kernel`（合规内核）概念登场之处。合规内核指可以为所有受支持的 PyTorch 和 CUDA 版本构建并运行的内核。通常需要自定义配置，但在我们的例子里，`kernel-builder` 会自动完成这个过程。

```
# Outside of the dev shell, run the following command
# if you are inside of the sandbox you can leave with `exit`
nix build . -L
```

> 这个过程可能耗时较久，因为它要为所有受支持的 PyTorch 和 CUDA 版本构建内核。输出在 result 目录中。

> kernel-builder 团队积极维护受支持的构建变体，使其跟上最新的 PyTorch 与 CUDA 发布，同时支持相邻版本以获得更广泛的兼容性。

最后一步是把结果移动到约定的 `build` 目录（`kernels` 库会在这里查找它们）。

```
mkdir -p build
rsync -av --delete --chmod=Du+w,Fu+w result/ build/
```

## 第二部分：从一个内核到一堆内核：解决生产挑战

有了可用的内核之后，还有一些事情可以让部署更轻松。我们会讨论如何用版本管理这个工具来修改 API 而不破坏下游使用，最后展示如何为你的内核制作 Python wheel。

### 内核版本

你可能过一阵子就想更新内核：发现了提升性能的新办法，或者想扩展内核功能。有些改动会要求你修改内核 API，比如新版本给某个公开函数新增了必填参数。这对下游用户很不方便——在他们加上这个新参数之前，代码就是坏的。

内核的下游用户可以通过把所用内核固定（pin）到某个特定版本来避免这种破坏。例如，每个 Hub 仓库同时也是 Git 仓库，可以用 git commit 短哈希把内核锁定到某个版本：

```
from kernels import get_kernel
img2gray_lib = get_kernel("drbh/img2gray", revision="4148918")
```

用 Git 短哈希能降低破坏概率；但它难以解读，也不支持在版本范围内的平滑升级。因此我们建议 Hub 内核采用大家熟悉的[语义化版本](https://semver.org/)（semantic versioning）体系。给内核加版本很简单：只需添加形如 `vx.y.z` 的 Git 标签，其中 *x.y.z* 就是版本号。例如，如果内核当前版本是 1.1.2，就打标签 `v1.1.2`。之后就可以用 `get_kernel` 获取该版本：

```
from kernels import get_kernel
img2gray_lib = get_kernel("drbh/img2gray", revision="v1.1.2")
```

配合版本边界，版本管理会更加强大。按语义化版本规则，`1.y.z` 系列中任何后续 `x` 和 `y` 的公开 API 都不得有向后不兼容的改动。所以，如果你写代码时内核版本是 `1.1.2`，你可以要求版本至少为 `1.1.2`、但小于 `2.0.0`：

```
from kernels import get_kernel
img2gray_lib = get_kernel("drbh/img2gray", version=">=1.1.2,<2")
```

这样代码总能获取 `1.y.z` 系列的最新内核。版本边界可以用 Python 风格的[版本说明符](https://packaging.pypa.io/en/stable/specifiers.html)。

你可以用 `huggingface-cli` [打标签](https://huggingface.co/docs/huggingface_hub/en/guides/cli#tag-a-model)：

```
$ huggingface-cli tag drbh/img2gray v1.1.2
```

#### 锁定内核

在大项目中，你可能希望在全项目范围协调内核版本，而不是散落在每个 `get_kernel` 调用里。此外，锁定内核往往很有用——让所有用户使用相同的内核版本，有助于处理 bug 报告。

`kernels` 库提供了一种在项目级管理内核的好方法。做法是把 `kernels` 包加入项目 `pyproject.toml` 的 build-system 依赖，然后在 `tools.kernels` 部分声明项目的内核需求：

```
[build-system]
requires = ["kernels", "setuptools"]
build-backend = "setuptools.build_meta"

[tool.kernels.dependencies]
"drbh/img2gray" = ">=0.1.2,<0.2.0"
```

版本可以用与 Python 依赖相同类型的版本说明符指定。这也是版本标签（`va.b.c`）发挥作用的另一个地方——`kernels` 会用仓库的版本标签查询有哪些可用版本。在 `pyproject.toml` 中声明内核后，可以用 `kernels` 命令行工具把它锁定到具体版本。该工具是 `kernels` Python 包的一部分：

```
$ kernels lock .
```

这会生成一个 `kernels.lock` 文件，记录与 `pyproject.toml` 中所指定边界兼容的最新内核版本。`kernels.lock` 应提交到项目的 Git 仓库，这样每个用户都会得到锁定版本的内核。有新内核版本发布时，再次运行 `kernels lock` 更新锁文件即可。

距离完整落地锁定内核还差最后一步。`get_locked_kernel` 是 `get_kernel` 对应使用锁定内核的版本。所以要使用锁定内核，把每一处 `get_kernel` 替换成 `get_locked_kernel`：

```
from kernels import get_kernel
img2gray_lib = get_locked_kernel("drbh/img2gray")
```

搞定！项目中每次调用 `get_locked_kernel("drbh/img2gray")` 都会使用 `kernels.lock` 中指定的版本。

### 预下载锁定的内核

`get_locked_kernel` 在内核不在本地 Hub 缓存中时会去下载。对于不希望运行时下载二进制的应用来说这并不理想。例如构建应用的 Docker 镜像时，你通常希望内核与应用一起存进镜像。这只需两个简单步骤。

首先，用 `load_kernel` 函数代替 `get_locked_kernel`：

```
from kernels import get_kernel
img2gray_lib = load_kernel("drbh/img2gray")
```

顾名思义，这个函数只会加载内核，*永远*不会尝试从 Hub 下载。如果内核在本地不可用，`load_kernel` 会抛出异常。那么如何让内核在本地可用？`kernels` 工具已经想到了！运行 `kernels download .` 会下载 `kernels.lock` 中指定的内核。例如，在 Docker 容器里你可以加一个步骤：

```
RUN kernels download /path/to/your/project
```

内核就会被烘焙进你的 Docker 镜像。

> 内核使用标准的 Hugging Face 缓存，所有 HF_HOME 缓存规则同样适用。

### 制作传统 Python Wheel

我们强烈推荐使用 `kernels` 包从 Hub 下载内核，好处很多：

- `kernels` 支持在同一个 Python 进程中加载同一内核的多个版本。
- `kernels` 会自动下载与你环境中 CUDA 和 Torch 版本兼容的内核版本。
- 你将获得 Hub 的全部好处：分析、issue 跟踪、pull request、fork 等。
- Hub 和 `kernel-builder` 提供了溯源与可复现性：用户可以查看内核的源码历史，并在同一构建环境中重建以做验证。

话虽如此，有些项目可能仍需要以 wheel 形式部署内核。`kernels` 工具提供了一个简单方案：一条命令就能把任何 Hub 内核转换成一组 wheel：
