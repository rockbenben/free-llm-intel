## Mixture-of-Experts 语言模型中专家的高阶剪枝

### 引言

Mixture-of-Experts（MoE）模型让最先进的 LLM 得以扩展到数千亿参数，但也带来一个根本性且代价高昂的附带条件：每个专家 MLP 在推理时都必须占用内存，尽管对任何给定 token 而言，绝大多数专家都处于闲置状态。例如，Qwen3.5-122B 的 48 个 MoE 层中每层有 256 个专家，其约 250 GB 参数内存占用的 95% 完全由这些专家 MLP 占据。然而，对任何给定 token，每层实际只使用 8 个专家。

**Expert pruning** 是缓解这一内存瓶颈最直接的手段之一，即永久删除最没用的专家。剪枝避免了让专家动态加载/卸载变得不切实际的延迟问题；它不需要任何训练；而且[可以与量化组合使用](https://arxiv.org/abs/2510.13999)。鉴于这些诱人的好处和想法本身的简洁性，不难理解为什么 expert pruning 已成为压缩 MoE 的首选方法。难点在于判断*哪些*专家删除起来最安全。

现有的剪枝方法独立地给每个专家打分，为每个专家赋予一个标量重要性分数（基于校准数据集），然后剔除最不重要的专家（每层独立进行）。这些是**一阶**方法，因为它们假设每个专家的贡献与其他所有专家无关。而实际上，专家会形成协作小组。我们在自己的实验中观察到一致的共激活专家簇，独立研究也表明[专家协作是 MoE 的稳定属性](https://arxiv.org/abs/2505.20225)，并且[对模型性能很重要](https://arxiv.org/abs/2510.16411)。忽略这些交互会导致次优的剪枝，在激进剪枝率下尤其如此。

[我们最新的论文](https://arxiv.org/abs/2609.18916)提出了 **HOPE**（Higher-Order Pruning of Experts），这是一种**二阶**方法，考虑了专家之间的成对交互。在 50% 剪枝时，HOPE 取得了所有方法中最佳的平均排名，在 agentic coding 任务上相对次优剪枝方法最高提升 +6.1%。

在这篇文章中，我们解释 HOPE 的工作原理，展示它在哪些方面优于现有方法，并逐步介绍如何在自己的模型上使用它。不熟悉 MoE 架构的读者，请参阅 [Mixture of Experts (MoEs) in Transformers](https://huggingface.co/blog/moe-transformers)。

### 专家不是单打独斗

在标准 MoE 中，每层有 EE 个专家，每个输入 token xx 被独立路由到 KK 个这样的专家（K=8 K = 8 是典型选择）。路由由单个层完成，它为每个专家 kk 生成经 softmax 归一化的门控权重 gk(x)g_{k}(x)，其中门控权重最高的 KK 个专家被选中，构成活跃专家集合 T(x)⊂{1,..,E}T(x) \subset\{1,..,E\}。该层的输出于是为 ∑k∈T(x)gk(x)fk(x)\sum\limits_{k\in T(x)}g_{k}(x)f_{k}(x)，其中 fk(x)f_{k}(x) 是专家 kk 对 token xx 的输出。

![pruning_cartoon](https://cdn-uploads.huggingface.co/production/uploads/6ab2f79bd8000a811c648a32/ZTLrZSA4pDn81OVRHtCXq.png)

*左：典型的 MoE 层，每个 token 被路由到 top-K 专家。右：一阶方法基于标量重要性分数对专家排序并删除，但最好的剪枝决策还会考虑专家之间交互的强度。*

重要的是，被选中集合 T(x)T(x) 中的专家并非相互独立。专家会形成稳定的协作小组，持续地一起被共激活。这一点[在文献中早有观察](https://arxiv.org/abs/2505.20225)：专家共同选择模式在训练早期就出现，并在整个过程中保持稳定。

这意味着，当我们从 MoE 层中剪掉专家时，剪枝决策需要考虑这些专家之间的高阶效应。单独看，删除专家 A 似乎没问题，但如果专家 B——它经常与 A 协作并依赖 A——非常重要，那么删除 A 就会仅凭一次删除拆散一个协作小组。一阶方法完全忽略了这一点，因为它们对 A 和 B 分别打分。

这种效应在高剪枝率下会叠加放大。当我们删除多达 50% 的专家时，就有可能破坏许多协作链路。这正是二阶剪枝优势最大的地方。

### HOPE 如何确定剪枝集合

*（HOPE 目标函数的完整推导见[我们对应的论文](https://arxiv.org/abs/2609.18916)附录 A）*

当我们从某个 MoE 层删除一组 PP 个专家时，被选中的专家集合 T(x)T(x)（对任何 token xx）都可能改变。那些*本来会*被选中的被剪专家，由门控权重次高的专家替补。由此导致的层输出变化就是**剪枝误差**。我们的目标是找到剪枝集合 PP（在某个预定义剪枝预算 ∣P∣\vert P\vert 下），使由此产生的剪枝误差*最小化*（在我们校准集的 token xx 上）。

遗憾的是，直接对 PP 最小化剪枝误差是不可解的。剪枝误差取决于替补专家的身份，而替补专家又取决于剪枝集合 PP 本身。HOPE 通过定义一个可处理的替代量 ZZ 绕开了这个问题，它对剪枝误差的主导分量构成严格上界：

Z=[∑j∈P∩T(x)gj(x)∥fj(x)∥2]2≥true errorZ = \bigl[\sum\limits_{j \in P\cap T(x)} g_{j}(x)\Vert f_j(x)\Vert_{2}\bigr]^{2} \geq \text{true error}

由于 ZZ 是一个和的平方，展开它自然会产生专家对之间的交叉项 gi(x)gj(x)∥fi(x)∥2∥fj(x)∥2g_{i}(x)g_{j}(x)\Vert f_{i}(x)\Vert_{2}\Vert f_{j}(x)\Vert_{2}。这些正是一阶方法丢弃的交互项。

为了找到最优剪枝集合，HOPE 在校准集上最小化 E[Z]\mathbb{E}[Z]，这可以重新表述为如下二次规划：

P∗=arg min⁡p p⊤Fps.t.p∈{0,1}E,∑k=1Epk=∣P∣P^{*} = \argmin_{p}\; p^{\top}Fp \quad \text{s.t.} \quad p \in \{0,1\}^{E}, \sum\limits_{k=1}^{E}p_{k} = \vert P\vert

其中 F∈RE×EF\in\mathbb{R}^{E\times E} 定义为：

Fi,j=1∣Xi,j∣∑x∈Xi,jgi(x)gj(x)∥fi(x)∥2∥fj(x)∥2whereXi,j={x:i,j∈T(x)}F_{i,j} = \frac{1}{\vert \mathcal{X}_{i,j}\vert} \sum\limits_{x\in\mathcal{X}_{i,j}} g_{i}(x)g_{j}(x)\Vert f_{i}(x)\Vert_{2}\Vert f_{j}(x)\Vert_{2}\quad\text{where}\quad \mathcal{X}_{i,j} = \{x: i,j \in T(x)\}

这个 F 矩阵在校准数据集上收集，最优剪枝集合通过连续松弛求解所得的二次规划（QP）获得（然后舍入为二值解）。每个条目 Fi,jF_{i,j} 捕捉专家 ii 和 jj 在两者共激活的 token 上的平均门控加权输出乘积。对角线 Fk,kF_{k,k} 度量的是*单个*专家的重要性，而非对角线条目（i≠ji\neq j 时的 Fi,jF_{i,j}）度量的是成对的*协作*贡献。

FF 在实践中长什么样？它展示了专家协作的结构，而这种结构取决于层：

![fmatrix](https://cdn-uploads.huggingface.co/production/uploads/6ab2f79bd8000a811c648a32/xyjeUqqFm2FtQtKVdZhwq.png)

*GLM-4.5-Air（每层 128 个专家，总计 1,060 亿参数）在三个代表性层（早期、中期、晚期）的交互矩阵 F 可视化。专家经过聚类以揭示块状结构。对角线上的亮块表示具有强成对交互分数的专家组。*

就实际成本而言，HOPE 需要的校准过程与其他任何 expert-pruning 方法相同（对校准数据做一次前向传播）。唯一新增的是求解二次规划，它是非凸的，但可以通过标准 QP 求解器高效求解（每层 1–2 秒）。与一阶方法相比，总的额外开销可以忽略不计，因为校准时间占主导。

#### 与 REAP 的联系

值得注意的是，HOPE 与 [Router-weighted Expert Activation Pruning (REAP)](https://arxiv.org/abs/2510.13999) 有很强的联系，后者是最先进的一阶 expert-pruning 方法。HOPE 的 F 矩阵在对角线上编码单个专家的重要性分数，这条对角线实际上恢复了 REAP 用于独立给专家排序以进行剪枝的分数（仅相差专家贡献的方差）。FF 的对角线几乎完美地恢复了 REAP 的专家排名（Spearman ρ=0.988\rho = 0.988）。因此，HOPE 相对 REAP 取得的任何改进，都归功于 FF 矩阵非对角线条目中的二阶交互项。

### 结果

我们用 3 个模型（Qwen3.5-122B、Qwen3.5-35B 和 GLM-4.5-Air）、2 个校准数据集（Evol-CodeAlpaca 和 SWE-Bench Verified 轨迹）评估了 HOPE 作为一种 expert pruning 方法的表现。我们使用 Tulu3 套件和 SWE-Bench Pro（agentic coding）测试所得的剪枝后模型，在 10% 到 50% 的剪枝率范围内，将 HOPE 与 4 个一阶基线（[REAP](https://arxiv.org/abs/2510.13999)、[MAN](https://arxiv.org/abs/2606.15716)、[EAN](https://arxiv.org/abs/2504.05586) 和 Frequency）进行比较。

![results](https://cdn-uploads.huggingface.co/production/uploads/6ab2f79bd8000a811c648a32/5ArwjL0FoYK6nW1eazSzF.png)

*HOPE 在所有条件下取得最佳总体排名，并在激进剪枝率下占据主导。左：所有模型、校准集和基准上的平均排名（越低越好）。右：Qwen3.5-35B 上的 SWE-Bench Pro 表现。*

在所有条件下，HOPE 取得了最佳平均排名（5 个方法中为 **2.07**），夺得第一的比例最高（**39%** 的条件），进入前二的比例为 **67%**。在逐一对比中，HOPE 在大多数条件下都击败其他每个基线。

不出所料，**HOPE 的优势在更高剪枝率下会扩大。**随着更多专家被删除，更多协作链路被破坏，FF 的非对角项变得更加重要。在 50% 剪枝时，HOPE 的平均排名提升至 **1.58**（次优方法 REAP 为 **2.42**）。这也是与部署最相关的设置，此时内存节省足以容纳更长的上下文、更深入的推理和更多的工具调用。

HOPE 的优势在 **SWE-Bench Pro** 上最为显著，这是一个 agentic coding 基准，模型必须自主解决真实的 GitHub issue。这些问题涉及多轮中组合多样的任务（如编码、工具调用、推理等），很可能调用多样的专家组合——正是保留协作结构最重要的场景。在 Qwen3.5-35B-A3B 上以 50% 剪枝时，HOPE 在 SWE-Bench Pro 上取得 **42.3**，与未剪枝模型的 **41.8** 相当（而 REAP 跌至 **36.2**，回退 13%）。

值得注意的是，剪枝后的模型偶尔能追平甚至超过未剪枝基线，这可能是因为删除低相关性专家减少了目标任务上的噪声。这种效应并非 HOPE 独有，[在各类剪枝方法中都有观察到](https://arxiv.org/abs/2504.06792)。此外，我们的实验表明，任何剪枝方法（包括 HOPE）使用聚焦代码的校准都不会严重降低非编码基准的表现，而且无论使用哪个校准集，HOPE 在整个 Tulu3 套件上都表现良好。

#### HOPE 保留更多协作专家

![exp_interaction_breakdown](https://cdn-uploads.huggingface.co/production/uploads/6ab2f79bd8000a811c648a32/S2fm99InMXuhOUFqEbI_2.png)

*与保留专家的协作平均强度（以 F 矩阵的值度量），按 HOPE 与 REAP 存在分歧的专家划分。*

HOPE 的优势源于在整个交互矩阵 FF 上进行优化。为了理解这在实践中如何影响剪枝决策，我们考察 HOPE 与 REAP 存在分歧的专家。对每个有争议的专家，我们计算其*协作分数*（即它与其他保留专家的平均 F 值）。仅被 HOPE 保留的专家，其*协作分数*始终高于仅被 REAP 保留的专家。换句话说，作为 QP 优化的一部分，HOPE 牺牲了一些单独得分高的专家，以换取保留协作簇。基准性能上的收益（如上所示）验证了这种权衡是有利的。

### 如何运行 HOPE

![pipeline](https://cdn-uploads.huggingface.co/production/uploads/6ab2f79bd8000a811c648a32/b8EewrlBWbGA0DlrBKa2E.png)

我们创建了一个基础的[包](https://github.com/awslabs/HOPE)来运行 HOPE。它有三个步骤：1) calibrate；2) solve；3) prune。我们的包已在 Qwen3、Qwen3-Next、Qwen3.5 和 GLM-4.5 上测试过。

#### 步骤 1：Calibrate

```
hope calibrate \
    --model-path Qwen/Qwen3.5-35B-A3B \
    --prompts calibration_prompts.txt \
    --out-path observations.h5
```

校准步骤对校准数据运行一次前向传播，无论是 agentic rollout 还是单轮轨迹。它使用 HuggingFace `transformers` 钩入每个 MoE 层各自的前向传播。对每个 token，记录哪些专家被选中、它们的门控权重、输出范数以及成对共激活统计。这一步的输出是 F 矩阵，存储在一个 HDF5 文件中。

#### 步骤 2：Solve QP

```
hope solve \
    --obs-path observations.h5 \
    --prune-frac 0.50 \
    --out-path pruneset.json
```

该命令将 F 矩阵具体化，并通过连续松弛求解二值二次规划。每层耗时几秒，输出是一个包含剪枝集合的 JSON 文件。严格来说，这就是 HOPE 算法的最终输出。

#### 步骤 3：Prune

```
hope prune \
    --model-path Qwen/Qwen3.5-35B-A3B \
    --pruneset-path pruneset.json \
    --out-path ./Qwen3.5-35B-A3B-pruned-50
```

为了完成整个流水线，我们运行这条命令，从剪枝集合实际创建更小的模型 checkpoint。剪枝后的模型是一个标准的 HuggingFace checkpoint，在磁盘和内存中都更小（无需修改 vLLM 或 SGLang 的模型定义）。

我们还发布了一个更紧凑的 Python API：

```
from hope.calibrate import calibrate
from hope.solve import solve
from hope.prune import prune_model

calibrate("Qwen/Qwen3.5-35B-A3B", calibration_prompts, "observations.h5")
solve("observations.h5", prune_frac=0.50, out_path="pruneset.json")
prune_model("Qwen/Qwen3.5-35B-A3B", "pruneset.json", "./Qwen3.5-35B-A3B-pruned-50")
```

### HOPE 的局限

HOPE 的优势在较高剪枝率（40–50%）下最为显著。在较低剪枝率（10–20%）下，REAP 和 MAN 等一阶方法有时也有竞争力，HOPE 的优势会缩小。此外，与大多数 expert-pruning 算法一样，HOPE 独立地剪每一层，不考虑跨层交互。在我们的论文中，我们提出了跨层 HOPE 的理论框架，但结果仍是初步的。最后，HOPE 捕捉的是成对交互，但更高阶的交互（三元组及以上）可能提供额外信号，尽管它们在组合上难以估计。
