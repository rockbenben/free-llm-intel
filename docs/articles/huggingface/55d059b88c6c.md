## 混合专家语言模型中专家的高阶剪枝

### 简介

专家混合 (MoE) 模型使最先进的 LLM 能够扩展到数千亿个参数，但它们有一个基本且昂贵的警告：每个专家 MLP 都必须在推理时占用内存，即使绝大多数对于任何给定的令牌来说都是空闲的。例如，Qwen3.5-122B 的 48 个 MoE 层中的每一层都有 256 个专家，其约 250 GB 参数内存占用量的 95% 完全由这些专家 MLP 占用。然而，对于任何给定的代币，实际上每层仅使用 8 个专家。

**专家修剪**是解决此内存瓶颈的最直接方法之一。即永久删除最无用的专家。修剪避免了延迟问题，避免了专家的动态加载/卸载变得不切实际；它不需要任何培训； [它由量化组成](https://arxiv.org/abs/2510.13999)。考虑到这些诱人的好处和简单的想法，很容易理解为什么专家修剪已成为缩小 MoE 的首选方法。困难在于决定删除“哪些”专家是最安全的。

现有的修剪方法对每个专家独立评分，为每个专家分配标量重要性得分（基于校准数据集），并剔除最不重要的专家（在每层中独立）。这些是**一阶**方法，因为它们假设每个专家的贡献独立于所有其他专家。事实上，专家们组成了合作小组。我们在自己的实验中观察到一致的共同激活专家集群，独立工作表明[专家合作是 MoE 的稳定属性](https://arxiv.org/abs/2505.20225)并且[对于模型性能很重要](https://arxiv.org/abs/2510.16411)。忽略这些相互作用会导致修剪效果不佳，尤其是在激进的修剪速度下。

[我们的最新论文](https://arxiv.org/abs/2609.18916) 推导了**HOPE**（专家的高阶剪枝），这是一种解释成对专家交互的**二阶**方法。在 50% 修剪时，HOPE 实现了所有方法中最好的平均排名，与次佳修剪方法相比，在代理编码任务上的增益高达 +6.1%。

在这篇文章中，我们将解释 HOPE 的工作原理，展示它在哪些方面优于现有方法，并逐步介绍如何将它用于您自己的模型。对于不熟悉 MoE 架构的读者，请参阅 [Transformers 中的专家混合 (MoE)](https://huggingface.co/blog/moe-transformers)。

### 专家不会单独工作

在标准 MoE 中，每一层都有 EE 专家，每个输入令牌 xx 独立路由到 KK 这样的专家（K=8 K = 8 是典型的选择）。路由由单层执行，为每个专家 kk 生成 softmax 归一化门权重 gk(x)g_{k}(x)，其中选择具有最高门权重的 KK 专家来形成活动专家集 T(x)⊂{1,..,E}T(x) \subset\{1,..,E\}。该层的输出为 Σk∈T(x)gk(x)fk(x)\sum\limits_{k\in T(x)}g_{k}(x)f_{k}(x)，其中 fk(x)f_{k}(x) 是专家 kk 对令牌 xx 的输出。

![pruning_cartoon](https://cdn-uploads.huggingface.co/product/uploads/6ab2f79bd8000a811c648a32/ZTLrZSA4pDn81OVRHtCXq.png)

*左：典型的 MoE 层，其中每个代币都被路由到前 K 个专家。右图：一阶方法根据标量重要性得分对专家进行排名和删除，但最佳修剪决策还将考虑专家之间交互的强度。*

重要的是，所选集合 T(x)T(x) 中的专家不是独立的。专家们形成了稳定的合作团体，并始终共同活跃起来。 [之前的文献](https://arxiv.org/abs/2505.20225)也观察到了这一点：专家共同选择模式在训练的早期就出现并在整个过程中保持稳定。

这意味着当我们从 MoE 层修剪专家时，修剪决策需要考虑这些专家之间的高阶效应。删除专家 A 本身似乎没问题，但如果经常与 A 合作并依赖 A 的专家 B 非常重要，那么删除 A 就可以通过一次删除来解散一个合作组。一阶方法完全忽略了这一点，因为它们分别对 A 和 B 进行评分。

这种效果在高修剪率下会加剧。当我们撤掉多达 50% 的专家时，我们就面临着破坏许多合作链接的风险。这是二阶剪枝最有利的地方。

### HOPE 如何识别修剪集

*（有关 HOPE 目标的完整推导，请参阅[我们相应论文](https://arxiv.org/abs/2609.18916)中的附录 A)*

当我们从某个 MoE 层删除一组 PP 专家时，所选的专家组 T(x)T(x)（对于任何代币 xx）可能会发生变化。 “本来”被选择的被修剪的专家将被具有次高门权重的专家所取代。层输出的最终变化是**剪枝误差**。我们的目标是找到剪枝集 PP（某些预定义的剪枝预算 ∣P∣\vert P\vert），以*最小化*产生的剪枝误差（针对我们校准集中的标记 xx）。

不幸的是，直接最小化 PP 上的剪枝误差是很困难的。剪枝误差取决于替换专家的身份，而替换专家的身份又取决于剪枝集并程本身。 HOPE 通过定义一个易于处理的代理 ZZ 来回避这个问题，它严格限制了剪枝误差的主要成分的上限：

Z=[Σj∈P∩T(x)gj(x)∥fj(x)∥2]2≥true errorZ = \bigl[\sum\limits_{j \in P\cap T(x)} g_{j}(x)\Vert f_j(x)\Vert_{2}\bigr]^{2} \geq \text{真误差}

因为 ZZ 是平方和，所以展开它自然会在专家对之间产生交叉项 gi(x)gj(x)∥fi(x)∥2∥fj(x)∥2g_{i}(x)g_{j}(x)\Vert f_{i}(x)\Vert_{2}\Vert f_{j}(x)\Vert_{2}。这些是一阶方法丢弃的交互项。

为了找到最佳剪枝集，HOPE 在校准集上最小化 E[Z]\mathbb{E}[Z]，可以将其重新表述为以下二次规划：

P*=arg min⁡p p⊤Fps.t.p∈{0,1}E,Σk=1Epk=∣P∣P^{*} = \argmin_{p}\; p^{\top}Fp \quad \text{s.t.} \quad p \in \{0,1\}^{E}, \sum\limits_{k=1}^{E}p_{k} = \vert P\vert

其中 F∈RE×EF\in\mathbb{R}^{E\times E} 定义为：

Fi,j=1∣Xi,j∣Σx∈Xi,jgi(x)gj(x)∥fi(x)∥2∥fj(x)∥2其中Xi,j={x:i,j∈T(x)}F_{i,j} = \frac{1}{\vert \mathcal{X}_{i,j}\vert} \sum\limits_{x\in\mathcal{X}_{i,j}} g_{i}(x)g_{j}(x)\Vert f_{i}(x)\Vert_{2}\Vert f_{j}(x)\Vert_{2}\quad\text{其中}\quad \mathcal{X}_{i,j} = \{x: i,j \in T(x)\}

该 F 矩阵收集在校准数据集上，并通过连续松弛（然后舍入为二元解）求解所得二次规划 (QP) 来获得最佳剪枝集。每个条目 Fi,jF_{i,j} 捕获专家 ii 和 jj 的平均门加权输出乘积，跨越两个共同激活的令牌。对角线 Fk,kF_{k,k} 衡量*个人*专家的重要性，而非对角线条目（Fi,jF_{i,j} for i≠ji\neq j）衡量成对*合作*贡献。

FF在实践中是什么样子的？它显示了专家合作的结构，该结构取决于层：

![fmatrix](https://cdn-uploads.huggingface.co/product/uploads/6ab2f79bd8000a811c648a32/xyjeUqqFm2FtQtKVdZhwq.png)

*GLM-4.5-Air（每层 128 个专家，总共 106B 个参数）在三个代表性层（早期、中期、晚期）的交互矩阵 F 的可视化。专家们齐聚一堂，揭示区块结构。沿对角线的明亮块表示具有较强配对交互得分的专家组。*

就实际成本而言，HOPE 需要与任何其他专家修剪方法相同的校准过程（对校准数据进行一次前向传递）。唯一的补充是求解二次规划，它是非凸的，但可以通过标准 QP 求解器有效求解（每层 1-2 秒）。与一阶方法相比，总的额外开销可以忽略不计，因为校准时间占主导地位。

#### 连接至 REAP

值得注意的是，HOPE 与[路由器加权专家激活修剪（REAP）]（https://arxiv.org/abs/2510.13999）有很强的联系，这是一种最先进的一阶专家修剪方法。 HOPE 的 F 矩阵对对角线上的各个专家重要性分数进行编码，并且该对角线有效地恢复了 REAP 用于独立排名专家进行剪枝的分数（仅因专家贡献的方差而不同）。 FF 的对角线几乎完美地恢复了 REAP 的专家排名（Spearman ρ=0.988\rho = 0.988）。因此，HOPE 相对于 REAP 所取得的任何改进都可归因于 FF 矩阵的非对角线项中的二阶相互作用项。

### 结果

我们使用 3 个模型（Qwen3.5-122B、Qwen3.5-35B 和 GLM-4.5-Air）以及 2 个校准数据集（Evol-CodeAlpaca 和 SWE-Bench Verified 轨迹）对 HOPE 作为专家剪枝方法进行了评估。我们使用 Tulu3 套件和 SWE-Bench Pro（代理编码）来测试生成的修剪模型，将 HOPE 与 4 个一阶基线进行比较（[REAP](https://arxiv.org/abs/2510.13999)、[MAN](https://arxiv.org/abs/2606.15716)、 [EAN](https://arxiv.org/abs/2504.05586) 和频率)，修剪率范围从 10% 到 50%。

![结果](https://cdn-uploads.huggingface.co/product/uploads/6ab2f79bd8000a811c648a32/5ArwjL0FoYK6nW1eazSzF.png)

*HOPE 在各种条件下实现了最佳总体排名，并在激进的修剪率下占据主导地位。左：所有模型、校准集和基准的平均排名（较低=更好）。右：SWE-Bench Pro 在 Qwen3.5-35B 上的性能。*

在所有条件下，HOPE 均取得了最佳平均排名（5 种方法中的**2.07**），获得前 1 名的完成率最高（条件的**39%**）和前 2 名的完成率（**67%**）。在面对面的比较中，HOPE 在大多数情况下都击败了所有其他基线。

正如预期的那样，**HOPE 的优势随着剪枝率的提高而增长。** 随着更多的专家被移除，更多的合作链接被破坏，FF 的非对角项变得更加重要。在修剪 50% 时，HOPE 的平均排名提高到 **1.58**（而次佳方法 REAP 的 **2.42**）。这也是与部署最相关的设置，其中节省的内存足以容纳更长的上下文、更深入的推理和更多的工具调用。

HOPE 的优势在 **SWE-Bench Pro** 上最为明显，这是一个代理编码基准，模型必须自主解决真正的 GitHub 问题。这些问题涉及多轮组合上不同的任务（例如编码、工具调用、推理等），并且可能会运用不同的专家组合——这正是保持合作结构最重要的机制。在 Qwen3.5-35B-A3B 上，修剪 50% 时，HOPE 在 SWE-Bench Pro 上达到 **42.3**，与未修剪模型的 **41.8** 相匹配（而 REAP 下降至 **36.2**，回归 13%）。

值得注意的是，修剪后的模型有时可以匹配或超过未修剪的基线，这可能是因为删除低相关性专家减少了目标任务的噪音。这种效果并非 HOPE 所独有，并且[已在各种修剪方法中观察到](https://arxiv.org/abs/2504.06792)。此外，我们的实验表明，使用任何修剪方法（包括 HOPE）进行以代码为中心的校准都不会严重降低非编码基准，并且无论校准集如何，HOPE 在整个 Tulu3 套件中都表现良好。

#### HOPE保留更多合作专家

![exp_interaction_breakdown](https://cdn-uploads.huggingface.co/product/uploads/6ab2f79bd8000a811c648a32/S2fm99InMXuhOUFqEbI_2.png)

*与保留专家的平均合作强度（以 F 矩阵值衡量），按 HOPE 和 REAP 不同意的专家划分。*

HOPE 的优势源于对整个交互矩阵 FF 的优化。为了了解这如何影响实践中的修剪决策，我们研究了 HOPE 和 REAP 意见不一致的专家。对于每个有争议的专家，我们计算其*合作分数*（即其与其他保留专家的平均 F 值）。仅由 HOPE 保留的专家始终比仅由 REAP 保留的专家拥有“更高的合作分数”。换句话说，作为 QP 优化的一部分，HOPE 牺牲了一些单独的高分专家以支持保留合作集群。基准性能的提升（如上所示）证实了这种权衡是有利的。

### 如何运行希望

![管道](https://cdn-uploads.huggingface.co/product/uploads/6ab2f79bd8000a811c648a32/b8EewrlBWbGA0DlrBKa2E.png)

我们创建了一个基本的[包](https://github.com/awslabs/HOPE)来运行HOPE。它分为三个步骤：1）校准； 2）解决； 3）修剪。我们的软件包已在 Qwen3、Qwen3-Next、Qwen3.5 和 GLM-4.5 上进行了测试。

#### 第 1 步：校准
```
hope calibrate \
    --model-path Qwen/Qwen3.5-35B-A3B \
    --prompts calibration_prompts.txt \
    --out-path observations.h5
```
校准步骤对校准数据运行一次前向传递，无论是代理推出还是单轮跟踪。这使用 HuggingFace “transformers” 来连接到每个单独 MoE 层的前向传递。对于每个令牌，这会记录选择的专家、他们的门权重、输出规范和成对共激活统计数据。此步骤的输出是 F 矩阵，存储在 HDF5 文件中。

#### 第 2 步：求解 QP
```
hope solve \
    --obs-path observations.h5 \
    --prune-frac 0.50 \
    --out-path pruneset.json
```
该命令具体化 F 矩阵并通过连续松弛求解二元二次规划。每层需要几秒钟的时间，输出是一个包含剪枝集的 JSON 文件。从技术上讲，这是 HOPE 算法的最终输出。

#### 第三步：修剪
```
hope prune \
    --model-path Qwen/Qwen3.5-35B-A3B \
    --pruneset-path pruneset.json \
    --out-path ./Qwen3.5-35B-A3B-pruned-50
```
为了完成管道，我们运行此命令以实际从修剪集创建较小的模型检查点。修剪后的模型是标准 HuggingFace 检查点，它在磁盘和内存中较小（无需更改 vLLM 或 SGLang 模型定义）。

我们还发布了更紧凑的 Python API：
```
from hope.calibrate import calibrate
from hope.solve import solve
from hope.prune import prune_model

calibrate("Qwen/Qwen3.5-35B-A3B", calibration_prompts, "observations.h5")
solve("observations.h5", prune_frac=0.50, out_path="pruneset.json")
prune_model("Qwen/Qwen3.5-35B-A3B", "pruneset.json", "./Qwen3.5-35B-A3B-pruned-50")
```
### 希望的局限性

HOPE 的优势在较高修剪率 (40–50%) 时最为明显。在较低的剪枝率（10-20%）下，像 REAP 和 MAN 这样的一阶方法有时具有竞争力，HOPE 的优势会缩小。此外，与大多数专家剪枝算法一样，HOPE 独立地剪枝每一层，并且不考虑跨层交互。在我们的论文中，我们提出了跨层 HOPE 的理论框架，但结果仍处于初步阶段。最后，HOPE 捕获成对相互作用，但即使是更高阶的相互作用（三元组及更高阶）也可以提供额外的信号，尽管它们在组合上很难估计。
