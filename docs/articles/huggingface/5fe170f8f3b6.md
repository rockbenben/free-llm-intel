我们想对 transformers 支持的每种量化方案的优缺点给出清晰总览，帮你决定该选哪一种。

目前，量化模型主要用于两个目的：

- 在更小的设备上运行大模型推理
- 在量化模型之上微调适配器（adapters）

迄今为止，有两项集成工作是**原生**受 transformers 支持的：*bitsandbytes* 与 *auto-gptq*。注意 [🤗 optimum 库](https://github.com/huggingface/optimum)还支持一些额外的量化方案，但不在本篇范围内。

想深入了解每种受支持的方案，请看下面的资源，也请看文档中的相应章节。

另请注意，以下细节只对 `PyTorch` 模型有效，Tensorflow 与 Flax/JAX 模型目前不在讨论范围内。

## 对比 bitsandbytes 与 auto-gptq

本节讨论两种量化各自的优缺点。注意这些基于社区反馈，并可能随时间演进——因为部分特性在各库的路线图上。

### bitsandbytes 的好处是什么？

**简单**：bitsandbytes 仍然是量化任意模型最简单的方式，因为它不需要用输入数据校准量化模型（也称 zero-shot 量化）。只要模型包含 `torch.nn.Linear` 模块，就能开箱即用地量化。每当 transformers 加入新架构，只要它能用 accelerate 的 `device_map="auto"` 加载，用户就能立刻用上 bitsandbytes 量化，性能退化极小。量化在模型加载时完成，无需任何后处理或准备步骤。

**跨模态互操作**：由于量化的唯一条件是模型含有 `torch.nn.Linear` 层，量化对任何模态都开箱即用，使 Whisper、ViT、Blip2 等模型也能直接以 8-bit 或 4-bit 加载。

**合并适配器零性能退化**：（若不熟悉适配器与 PEFT，可先读[这篇博客](https://huggingface.co/blog/peft)）。如果你在量化基座模型之上训练适配器，为部署可以把适配器合并到基座模型上，推理性能零退化。你还可以把适配器[合并](https://github.com/huggingface/peft/pull/851/files)到反量化后的模型上！GPTQ 不支持这一点。

### autoGPTQ 的好处是什么？

**文本生成快**：相比 bitsandbytes 量化模型，GPTQ 量化模型在[文本生成](https://huggingface.co/docs/transformers/main_classes/text_generation)上更快。速度对比我们放到专门的章节讲。

**n-bit 支持**：GPTQ 算法可以把模型量化到低至 2 bits！不过这可能伴随严重质量退化。推荐位数是 4——就目前而言这是 GPTQ 的最佳折衷。

**易于序列化**：GPTQ 模型支持任意位数的序列化。加载 TheBloke 命名空间的模型：[https://huggingface.co/TheBloke](https://huggingface.co/TheBloke)（找以 `-GPTQ` 结尾的）开箱即用，只要你装好了所需的包。bitsandbytes 支持 8-bit 序列化，但目前不支持 4-bit 序列化。

**AMD 支持**：该集成应可在 AMD GPU 上开箱即用！

### bitsandbytes 可能的改进空间？

**文本生成比 GPTQ 慢**：使用 [`generate`](https://huggingface.co/docs/transformers/main_classes/text_generation) 时，bitsandbytes 4-bit 模型相比 GPTQ 更慢。

**4-bit 权重不可序列化**：目前 4-bit 模型无法序列化。这是社区的常见诉求，我们相信 bitsandbytes 维护者很快会处理——它已在路线图上！

### autoGPTQ 可能的改进空间？

**校准数据集**：需要校准数据集可能让一些用户对 GPTQ 望而却步。此外，量化模型可能要花数小时（例如按[论文](https://arxiv.org/pdf/2210.17323.pdf)第 2 节，175B 规模模型需 4 GPU 小时）。

**目前只适用于语言模型**：目前，用 auto-GPTQ 量化模型的 API 只为语言模型设计。理论上可以用 GPTQ 算法量化非文本（或多模态）模型，但原论文和 auto-gptq 仓库都未详述这一过程。如果社区对此话题热情高涨，未来也许会考虑。

## 深入速度基准

我们决定对 bitsandbytes 与 auto-gptq 在不同硬件上的推理与适配器微调做详尽基准。推理基准让用户了解各推理方案的速度差异；适配器微调基准则让用户在「于 bitsandbytes 和 GPTQ 基座模型上微调适配器该选哪种方案」时有清晰判断。

我们使用如下设置：

- bitsandbytes：4-bit 量化，`bnb_4bit_compute_dtype=torch.float16`。请用 `bitsandbytes>=0.41.1` 以获得快速 4-bit kernel。
- auto-gptq：4-bit 量化并使用 exllama kernel。需要 `auto-gptq>=0.4.0` 才能使用 ex-llama kernel。

### 推理速度（仅前向传播）

该基准只测 prefill 步骤，对应训练时的前向传播。基准在单张 NVIDIA A100-SXM4-80GB GPU 上运行，prompt 长度 512。模型为 `meta-llama/Llama-2-13b-hf`。

batch size = 1：

| quantization | act_order | bits | group_size | kernel | Load time (s) | Per-token latency (ms) | Throughput (tok/s) | Peak memory (MB) |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| fp16 | None | None | None | None | 26.0 | 36.958 | 27.058 | 29152.98 |
| gptq | False | 4 | 128 | exllama | 36.2 | 33.711 | 29.663 | 10484.34 |
| bitsandbytes | None | 4 | None | None | 37.64 | 52.00 | 19.23 | 11018.36 |

batch size = 16：

| quantization | act_order | bits | group_size | kernel | Load time (s) | Per-token latency (ms) | Throughput (tok/s) | Peak memory (MB) |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| fp16 | None | None | None | None | 26.0 | 69.94 | 228.76 | 53986.51 |
| gptq | False | 4 | 128 | exllama | 36.2 | 95.41 | 167.68 | 34777.04 |
| bitsandbytes | None | 4 | None | None | 37.64 | 113.98 | 140.38 | 35532.37 |

从基准看，bitsandbytes 与 GPTQ 大致相当，GPTQ 在大 batch size 下略快。更多细节见这个[链接](https://github.com/huggingface/optimum/blob/main/tests/benchmark/README.md#prefill-only-benchmark-results)。

### 适配器微调（前向 + 反向）

无法对量化模型做纯粹训练。但你可以借助参数高效微调方法（PEFT）训练适配器，从而微调量化模型。微调方法依赖一种近期流行的方法「低秩适配器」（LoRA）：不必微调整个模型，只需微调这些适配器并在模型内正确加载它们。来对比一下微调速度！

基准在 NVIDIA A100 GPU 上运行，使用 Hub 上的 `meta-llama/Llama-2-7b-hf` 模型。注意对 GPTQ 模型我们必须禁用 exllama kernel，因为微调不支持 exllama。

[![Benchmark A100 finetuning](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/163_overview-quantization-transformers/A100_finetuning.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/163_overview-quantization-transformers/A100_finetuning.png)

由结果我们得出结论：微调上 bitsandbytes 比 GPTQ 快。

## 结论与最后的话

在这篇博文中，我们在多种设置下对比了 bitsandbytes 与 GPTQ 量化。我们看到 bitsandbytes 更适合微调，而 GPTQ 更适合生成。基于这一观察，要得到更好的合并模型，可以：

- (1) 用 bitsandbytes 量化基座模型（zero-shot 量化）
- (2) 添加并微调适配器
- (3) 把训练好的适配器合并到基座模型或[反量化模型](https://github.com/huggingface/peft/pull/851/files)上！
- (4) 用 GPTQ 量化合并后的模型并用于部署
