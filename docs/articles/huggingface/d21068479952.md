*一篇技术导览：我们如何构建 Granite 4.2 推理模型家族。*

**作者：** Granite Team, IBM

**TL;DR：** Granite 4.2 是我们首个稠密、仅解码器（decoder-only）的推理 LLM 家族，发布三个尺寸：**3B、8B 和 30B**。这些模型从 [Granite-4.1](https://huggingface.co/collections/ibm-granite/granite-41-language-models) 基座模型做后训练（post-trained）而来。[Granite-4.1](https://huggingface.co/collections/ibm-granite/granite-41-language-models) 基座模型是在约 15T token 上从零开始预训练的，采用五阶段策略，把上下文窗口扩展到 512K token；随后在思维链（chain-of-thought）、推理和智能体轨迹（agentic-trajectory）数据上做监督微调（SFT）；最后用**多阶段强化学习流水线**进行后训练。这条流水线包含智能体 RL（agentic RL）——8B 和 30B 模型在真实的沙箱环境中学会带着工具行动。每个模型都有一个**思考/不思考**开关、一种在简单问题上只花少量推理预算的**低开销（low-effort）**思考模式，以及原生工具调用（tool calling）。所有 Granite 4.2 模型均以 Apache 2.0 许可证发布。

- [GitHub 仓库](https://github.com/ibm-granite/granite-4.2-language-models)
- [Granite 文档](https://www.ibm.com/granite/docs/)

## 概览

Granite 4.2 是 Granite 语言模型家族中主打推理的版本。早前的 Granite 版本是出色的指令跟随助手；Granite 4.2 加上了显式推理。每个模型都可以在给出答案前生成一条思维链，并根据任务需要多少斟酌来决定运行在**思考**还是**不思考**模式。**低开销**模式介于两者之间，在简单问题上只花少量推理预算。

三个尺寸（**3B、8B、30B**）共享同一套架构设计，走同一条训练流水线（基座模型、SFT，然后多阶段 RL），只是各自规模不同。三者都是强推理者和指令跟随者。能力上最明显的分岔出现在后训练：**8B 和 30B** 额外经过一个**智能体 RL**环节，教会它们像智能体一样运作：调用工具、编辑并运行代码、操作终端、在真实环境里搜索网页。所有模型都支持原生工具调用。通过 OpenAI 兼容端点服务（例如用 vLLM）时，模型按 OpenAI function-calling 格式发出工具调用，无需额外胶水即可接入各种智能体框架（agentic harness）。Granite 4.2 也受 SGLang 支持，可直接使用的部署配方见 [SGLang cookbook](https://docs.sglang.io/cookbook/autoregressive/IBM/Granite-4.2)。

下文逐步讲清整个构建过程：架构、预训练、监督微调、多阶段 RL 流水线，以及结果。

## 模型架构

Granite 4.2 模型基于仅解码器的稠密 transformer 架构构建，核心组件如下：

- **注意力：** 分组查询注意力（GQA），40 个注意力头、8 个 KV 头
- **位置嵌入：** 旋转位置编码（RoPE），θ = 10,000,000
- **前馈：** 使用 SwiGLU 激活的 MLP
- **归一化：** RMSNorm（ε = 1e-5）
- **嵌入：** 输入/输出嵌入相互独立（不共享权重）
- **精度：** bfloat16

| 组件 | 3B Dense | 8B Dense | 30B Dense |
| --- | --- | --- | --- |
| 嵌入维度 | 2560 | 4096 | 4096 |
| 层数 | 40 | 40 | 64 |
| 注意力头大小 | 64 | 128 | 128 |
| 注意力头数 | 40 | 32 | 32 |
| KV 头数 | 8 | 8 | 8 |
| MLP 隐藏层大小 | 8192 | 12800 | 32768 |
| MLP 激活 | SwiGLU | SwiGLU | SwiGLU |
| 序列长度 | 131072 | 131072 | 131072 |
| 位置嵌入 | RoPE | RoPE | RoPE |
| 参数量 | 3B | 8B | 30B |

## 预训练

Granite 4.2 模型从 [Granite-4.1](https://huggingface.co/collections/ibm-granite/granite-41-language-models) 基座模型后训练而来。[Granite-4.1](https://huggingface.co/collections/ibm-granite/granite-41-language-models) 基座模型在约 **15 万亿 token** 上以五阶段训练策略从零训练。阶段 1-2 专注基础预训练，阶段 3-4 做中期训练（mid-training）并逐步用更高质量的数据退火（annealing），阶段 5 引入长上下文训练，把上下文窗口扩展到 **512K token**。每个阶段使用不同的数据混合与学习率调度，从广泛的网络级数据逐步转向更精选、更高质量的来源。

预训练配方与上一代基本一致；数据混合、阶段调度、长上下文扩展的细节见 [Granite 4.1 博客](https://huggingface.co/blog/ibm-granite/granite-4-1)。

## SFT：数据准备与质量控制

监督微调（SFT）把基座模型变成可靠的指令跟随、推理、会用工具的助手。SFT 数据混合包含智能体（31.6%）与非智能体（68.4%）两类数据，合计约 720 万个样本、约 1000 亿 token，其中可训练 token 约 650 亿。

**智能体语料**覆盖多个领域，包括软件工程（SWE，69%）、工具调用（12.1%）、终端使用（8.0%）、数学（3.5%）、搜索（0.8%）和行动（action，0.2%）。这些样本与轨迹由一系列多样的智能体脚手架和框架生成，包括 OpenHands、OpenCode、Terminus-2、SWE-agent、OpenResearcher、MiniSWE、OpenSeeker、EnvScaler、Gemini CLI、Hermes、Codex 和 Goose。智能体数据兼收开源数据集样本和我们自己在合成 RL 环境中生成的数据，涵盖多种智能体-框架组合。

**非智能体语料**由几大类组成：指令跟随（18.8%）、编程（18.8%）、数学（14.6%）、多语言（7.0%）、科学（5.4%）、推理（3.0%）和安全（0.8%）。

### 数据质量控制

一个样本进入最终 SFT 混合前，要经过多道质控。首先，来自不同来源的数据被规范化并重排为统一的 OpenAI Chat 格式，使对话结构和工具交互在所有数据集和脚手架之间保持一致。

然后我们用 GPT-OSS-120B 和 Gemma 4 作为基于 LLM 的评审（judge）评估样本质量。低分样本被移除，含幻觉或编造信息、无效工具交互、或调用工具清单中未定义函数的样本也被移除。此外还按数据集特点应用一些针对性的启发式规则，进一步提升质量、去除已知噪声源。

最后进行局部和全局去重。去重基于对 `tools` 和 `messages` 字段组合计算的 SHA-256 哈希，既清除单个数据源内部的重复样本，也清除整个 SFT 混合之间的重复。

### SFT 训练细节

完整语料先做全局洗牌（shuffle），以减少顺序效应、确保训练时各域样本充分混合。洗牌后的语料被切成等大的 `.parquet` 分片，用模型的 tokenizer 和 chat template 做分词，并为大规模分布式训练做好准备。

在启动最终的大规模训练前，我们先在代表性配置上调超参数，扫学习率调度、初始学习率和 warm-up 比例，找到在各种模型尺寸下都能稳定训练的设定。最终训练配置汇总如下：

| 参数 | 值 |
| --- | --- |
| 算力 | 32-128 节点（按模型尺寸），每节点 4x Grace/GB200 |
| 序列长度（打包） | 131,072 (128K) |
| 全局批大小 | 128 |
| 学习率 | 1.0e-5，warm-up 后恒定；Phase 2 用 3.0e-6 |
| LR warm-up | `train_iters` 的 2.5% |
| 训练时长 | 约 2 个 epoch |
| 并行策略 | TP=2, PP=1, CP=4 或 CP=2 |

### 30B 模型的 Phase 2 SFT

对 30B 模型，我们额外做了第二阶段 SFT，专门聚焦智能体编程。这一阶段把智能体、SWE 和编程数据上采样（upsample），提高它们在训练分布中的有效占比，同时保留原 SFT 语料约 16% 作为回放（replay）数据。

随后以 3.0e-6 的较低学习率再微调约 1 个 epoch。这个针对性的第二阶段增加了模型接触智能体编程轨迹的量，又不丢弃初始 SFT 阶段获得的能力。

## 强化学习：多阶段、多环境流水线

SFT 之后，我们应用一条**多阶段、多环境强化学习流水线**。不是单次 RL 跑完，而是跑一串针对性强的*阶段*，覆盖许多环境：数学、代码、科学、指令跟随、工具使用、结构化输出，然后是软件工程、终端使用和网页搜索。每个阶段是一次独立的 RL 运行，只针对一种能力，并从上一阶段的 checkpoint 热启动（warm-start）。

*图 1。分阶段 RL 课程。基础 RL（可验证奖励 + 技能增强器）对所有尺寸运行；智能体 RL 环节（SWE → Terminal → Search）只对 8B 和 30B 运行。每个模型最后都以 RLHF 收尾。每个阶段是一次独立的 GRPO 运行，从前一 checkpoint 热启动。*

### 训练方法

每个阶段都用**异步 GRPO**（[Group Relative Policy Optimization](https://arxiv.org/abs/2402.03300)）训练，使回路的生成（generator）与训练（trainer）两半永不互相阻塞。一批生成 worker 持续采样回答，把完成的轨迹投进共享缓冲区；缓冲区攒够一个 step 的量，trainer 就取走这批、做一次优化器 step，并把更新后的参数流式推回生成 worker，全程不停下它们。刷新可能落在某次 rollout 进行到一半时，于是单条轨迹会被两个相邻策略版本"缝合"起来。我们允许这种情况而不是花钱去避免它：worker 复用现有 KV 缓存，无需每次刷新后重建；唯一的护栏是一个上限，禁止它们落后 trainer 超过一个更新，从而界定任何样本最多能偏离当前策略多远。跨过这条线仍然存在的失配，由目标函数中的*截断重要性采样（truncated importance sampling）*处理——把"训练时对数概率 / 生成时对数概率"的比值钳制在固定上限内，使少量过期 token 无法左右整个更新。

优势（advantage）采用组相对（group-relative）的**留一法基线（leave-one-out baseline）**：每个回答与同一提示词下*其他*样本的平均奖励比较，从而无需单独的价值网络。说具体点，看 **RLVR**——第一个也是跑得最久的阶段：每个 step 用 **256 个提示词**配**每个 16 个采样回答**，组成 **4,096** 个样本的批，trainer 在下一个 rollout 开始前用一次优化器 step 全部消化。后续阶段保持这套机制不变，只调整各阶段的形状（shape），见下文。

#### RL 训练配置

流水线在所有阶段保留一套共同的超参数主干，让课程更易于运行和比较。几个旋钮全局固定：

| 参数 | 值（各阶段共享） |
| --- | --- |
| 算法 | GRPO（无价值网络；组相对优势） |
| 训练栈 | NeMo-RL（Megatron-Core + vLLM），配 NeMo-Gym 环境 |
| 比值裁剪（min / max） | 0.2 / 0.28 |
| 微批大小 | 1 |
| 并行策略 | 张量并行 2-4；不用流水线并行和上下文并行 |

阶段之间变化的是每次运行的*形状*：每个 step 的提示词数和生成数、上下文长度、是否运行智能体回路、以及把策略往参考模型拉回的力度。下表给出 **30B** 链条逐阶段的确切设定：

| 阶段 | 提示词/step | 每提示词生成数 | 最大序列长度 | Rollout 轮数 | KL | LR |
| --- | --- | --- | --- | --- | --- | --- |
| RLVR（×3） | 256 | 16 | 64K | 1 | 0 | 5e-7 |
| IF 增强器 | 256 | 16 | 64K | 1 | 0 | 5e-7 |
| Code 增强器 | 64 | 16 | 64K | 1 | 0.05 | 5e-7 |
| SWE 1 | 64 | 16 | 128K | 1 | 0.01 | 5e-7 |
| SWE 2 | 32 | 16 | 128K | **128** | 0 | 5e-7 |
| Terminal | 8 | 32 | 64K | **64** | 0.01 | **1e-6** |
| Search | 32 | 16 | 128K | **64** | 0.01 | 5e-7 |
| RLHF | 128 | 16 | 48K | 1 | 0.05 | 5e-7 |

*表中为 30B 模型参数。全局批大小 = 提示词/step × 每提示词生成数（如 RLVR：256 × 16 = 4096）。3B 和 8B 使用相同的配方和超参数，但**阶段更少**（见[三个尺寸的差异](https://huggingface.co/blog/ibm-granite/granite-4-2#how-the-three-sizes-differ)）；变的是阶段清单，不是旋钮。*

**KL 调度**跟着奖励类型走：奖励客观可验证的地方自由探索（RLVR 和 SWE 2 以 KL 0 运行），目标出于偏好、安全或窄技能嫁接的地方贴近参考策略（RLHF 和代码增强器用 KL 0.05）。**Rollout 轮数**一列统计的是 *GRPO 本身*每次 rollout 看到的与环境交互次数。无论哪种情况，模型都基于完整、真实环境的轨迹来训练。

### 分阶段课程

每个阶段是一次独立 RL 运行，只有一个目标、一套自己的奖励信号。跑完后，其策略导出为 Hugging Face 格式，成为下一阶段的基座模型，所以整条流水线是一串热启动：

```
SFT ─▶ RLVR ─▶ Skill boosters ─▶ SWE agent ─▶ Terminal ─▶ Search ─▶ RLHF
      └──────── foundational RL ────────┘   └──────── agentic RL (8B / 30B) ────────┘
```

**8B 和 30B** 模型走完全部阶梯。**3B** 走缩短路线：基础 RL 加对齐，不含智能体环节。

### 奖励信号

一个阶段很大程度上由*它如何给奖励*定义。整条流水线有三种奖励类型，单个阶段可以并用多种：

| 奖励类型 | 衡量什么 | 用在 |
| --- | --- | --- |
| **可验证（Verifiable）** | 精确匹配、单元测试、格式检查器、基于真值的规则检查器 | RLVR · 增强器 · SWE |
| **奖励模型 / LLM 评审** | 开放式质量、偏好、安全、回答正确性 | RLVR · Search · RLHF |
| **智能体结果（Agentic outcome）** | 模型在真实环境中是否真的解决了任务？ | SWE · Terminal · Search |

可验证奖励客观、难以钻空子，所以流水线把它们前置。评审型和偏好型奖励负责那些任何检查器都无法表达的开放品质。智能体结果奖励最稀疏：常常是长长的工具使用轨迹终点的一个比特。

### 基础 RL：练出技能

#### RLVR：可验证奖励 RL

RLVR 是基础阶段，也是流水线中数据混合最广的一站：单个混合数据集横跨许多可验证领域。

- **数学：** 带框式答案（boxed-answer）检查的思维链，加上 **Lean** 形式化证明
- **竞技编程：** 解答在沙箱中对照隐藏测试检查
- **STEM / 研究生级科学 MCQA** 与通识
- **指令跟随：** 结构化输出与逆指令（inverse-instruction）任务
- **工具 / 函数调用：** 单步工具使用
- **推理解谜**与**弃答（abstention）**（知道何时该拒绝）

每类任务都有自己的验证器，所以奖励逐样本落到实处。RLVR 在 3B 和 8B 上跑**两轮**，在 30B 上跑**三轮**。每轮都是在公开数据与内部精选 RL 数据的重新加权混合上的一次全新热启动运行。

#### 技能增强器：针对性拔高

RLVR 之后，几个简短的**增强器（booster）**阶段针对以下领域集中训练、拔高特定能力：

- **指令跟随（IF）：** 多轮对话、inverse-IFEval、结构化输出
- **代码：** 只练竞技编程

增强器是小而集中的运行。轻微的 KL 惩罚让模型贴近当前行为，同时推动单项技能。

### 智能体 RL：学会行动（8B / 30B）

在智能体阶段，模型学会**行动**：调用工具、观察结果、在真实环境里迭代，奖励取决于任务是否真正解决。这些阶段共享同一形状：多轮工具使用、真实（非模拟）环境、稀疏的结果奖励、GRPO，从代码增强后的 checkpoint 热启动。顺序为：**SWE → Terminal → Search**。

[![智能体 RL 环境](https://cdn-uploads.huggingface.co/production/uploads/65cc2c288ebd392213e58899/FxSMYasHnR4vpv263_DAL.png)](https://cdn-uploads.huggingface.co/production/uploads/65cc2c288ebd392213e58899/FxSMYasHnR4vpv263_DAL.png)

*图 2。三个智能体 RL 环境。每个都由真实框架 + 真实环境 + 稀疏的结果奖励构成。3B 模型不跑其中任何一个。*

- **SWE 智能体（软件工程）。** 每个任务是各自沙箱里的真实仓库。由 [OpenHands](https://github.com/All-Hands-AI/OpenHands) 框架驱动，模型读代码、改文件、在大量内部轮次中运行测试套件。奖励可验证：隐藏测试是否通过？任务取自开源 SWE 数据集，每个实例都配套一个按仓库构建的容器镜像。
- **终端智能体（终端 / 操作系统操作）。** 在活跃 shell 中执行多步任务，通过 Harbor / [Terminus-2](https://www.harborframework.com/docs/agents/terminus-2) 智能体框架运行。模型规划一串命令、观察输出、从错误中恢复。任务成功完成才给奖励。这是唯一一个在 GRPO 层面驱动多轮智能体回路的阶段，rollout 最多跨越 64 个环境轮次。
- **搜索智能体（深度研究）。** 模型在浏览智能体回路中用实时网页搜索工具调用回答困难的多跳问题：跨跳收集证据、对其推理、给出答案。由于这里的正确性是开放式的，奖励是对最终答案的 LLM 评审。

### 对齐：RLHF

每个模型的最后一个阶段是**面向人类偏好与安全的 RLHF。** 它针对一个生成式奖励模型（GenRM）的偏好信号，外加覆盖越狱抵抗与恰当拒绝的安全奖励进行优化。这一阶段使用流水线中最高的 KL 惩罚，在不侵蚀先前阶段能力的前提下对齐语气与安全。除人类偏好与安全对齐之外，该阶段还施加推理长度惩罚，抑制早期阶段染上的过度冗长推理倾向。

### 三个尺寸的差异

方法与基础设施相同，区别在于每个模型沿阶梯爬多高。

| 阶段 | 3B | 8B | 30B |
| --- | --- | --- | --- |
| **RLVR**（可验证） | ×2 | ×2 | ×3 |
| **技能增强器** | code | IF · GPQA · code | IF · code |
| **SWE 智能体** | — | ✓ | ✓ |
| **终端智能体** | — | ✓ | ✓ |
| **搜索智能体** | — | ✓ | ✓ |
| **RLHF**（偏好 + 安全） | ✓ | ✓ | ✓ |

3B 是扎实的基础 RL 模型；8B 和 30B 在其上叠加智能体 RL 环节，学会在真实环境中带着工具行动。

## 面向可扩展 RL 的智能体 AI 基础设施

这种规模的强化学习，需要能同时驱动训练回路和一整支实时环境集群的基础设施。这在智能体阶段最为关键——每个训练样本都是一次多轮 rollout，要改代码、跑命令或浏览网页。Granite 4.2 的 RL 跑在两个开源组件上：训练侧的 **[NeMo-RL](https://github.com/NVIDIA-NeMo/RL)** 与 rollout 侧的 **[NeMo-Gym](https://github.com/NVIDIA-NeMo/gym)**。

[![NeMo-RL + NeMo-Gym 系统架构](https://cdn-uploads.huggingface.co/production/uploads/65cc2c288ebd392213e58899/ceRxgjK0m0kVHp1iJ7P34.png)](https://cdn-uploads.huggingface.co/production/uploads/65cc2c288ebd392213e58899/ceRxgjK0m0kVHp1iJ7P34.png)

*图 3。RL 系统。NeMo-RL 驱动 GRPO 回路（Megatron-Core 训练后端、vLLM 生成，以及负责 HF⇄Megatron 权重转换的 Megatron-Bridge）。NeMo-Gym 编排 rollout，并把工具、沙箱、奖励/验证器调用作为可插拔的 **Resources** 托管起来。*

分工如下：

- **NeMo-RL（训练侧）。** [Megatron-Core](https://github.com/NVIDIA/Megatron-LM) 是训练后端；[vLLM](https://github.com/vllm-project/vllm) 负责生成 rollout；**Megatron-Bridge** 在 Megatron 与 Hugging Face 格式之间转换权重，使每个阶段都能导出一个干净的 HF checkpoint 给下一阶段用。
- **NeMo-Gym（rollout 侧）。** 它把每个环境以一组 **Resources**（验证器、工具、沙箱和奖励模型）的形式统一到同一个接口后面。这正是智能体阶段的插口：SWE 仓库沙箱、终端框架、网页搜索工具都挂在这里，而在训练回路眼中，它们和一个简单的数学验证器长得一模一样。

这种统一性才让上面的分阶段课程切实可行：增强器的规则检查器和一个完整的 SWE 沙箱向 GRPO 呈现的是同一个接口。

这种拆分也让前述**异步**训练回路在物理上成为可能：生成与策略更新分处不同 GPU 池，昂贵的生成集群（包括实时智能体环境）因此保持忙碌，不必干等优化器 step。

## 量化

我们还发布了 Granite 4.2 模型的四种量化变体，用于 vLLM 推理。模型用 LLM Compressor 转换为 FP8、NVFP4 和 MXFP4，并用 llama.cpp 框架转成 GGUF 格式，面向低内存部署。

### FP8

FP8 版本采用动态逐通道（per-channel）权重与逐 token（per-token）激活量化，不使用校准。

### FP4

NVFP4 和 MXFP4 版本用 GPTQ 量化，以从 SFT 数据集抽取的 2K 样本做校准。校准时最大上下文长度为 2K。

### GGUF

Granite 4.2 模型到 GGUF 的转换由官方的 llama.cpp 工具完成，做法见 <https://github.com/IBM/gguf#gguf-conversion--quantization>。

提供了多种 GGUF 格式：

- Q8_0
- Q6_K
- Q5_K_S
- Q5_K_M
- Q5_1
- Q5_0
- Q4_K_S
- Q4_K_M
- Q4_1
- Q4_0
- Q3_K_S
- Q3_K_M
- Q3_K_L
- Q2_K

## 基础设施

### 硬件

我们在 CoreWeave 托管的 NVIDIA GB200 NVL72 集群上训练 Granite 4.2 语言模型，该集群具备：

- 一个 72 GPU 的 NVLink 域，实现机架内高速通信
- 一张无阻塞 Fat-Tree NDR 400 Gb/s InfiniBand 网络，提供全带宽的机架间互联
- 集群规模下数千块 GPU 同时运行

这套基础设施提供了大规模分布式训练所需的高带宽、低延迟通信。

### 软件栈

训练软件栈打包成 `.sqsh` 容器镜像，让每次运行都有一个可复现、可移植的环境，其 SBSA 兼容的 CUDA 目标、Linux aarch64 的 Python wheel 和 GPU 专用二进制都被锁定。大规模 SFT 运行基于 NGC PyTorch 基础镜像（Ubuntu 22.04、CUDA 12.8、Python 3.12）；RL 软件栈运行在自己的 NeMo-RL 容器中。

### 基础推理（思考模式）

```
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

model_path = "ibm-granite/granite-4.2-30b"
tokenizer = AutoTokenizer.from_pretrained(model_path)
model = AutoModelForCausalLM.from_pretrained(model_path, device_map="cuda", torch_dtype=torch.bfloat16)
model.eval()

messages = [
    {"role": "user", "content": "How many r's are in the word 'strawberry'?"},
]

text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True, enable_thinking=True)
inputs = tokenizer(text, return_tensors="pt").to(model.device)

with torch.no_grad():
    output = model.generate(**inputs, max_new_tokens=8192, temperature=1.0, top_p=0.95, do_sample=True)

print(tokenizer.decode(output[0][inputs.input_ids.shape[-1]:], skip_special_tokens=False))
```
