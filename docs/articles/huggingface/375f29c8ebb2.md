# huggingface_hub v1.0：五年筑就开放机器学习基石

这篇文章也有中文版 [简体中文](https://huggingface.co/blog/zh/huggingface-hub-v1)。

**太长不看：** 经过五年开发，`huggingface_hub` 迎来 v1.0——这是一个里程碑，标志着这套库作为支撑 **20 万个依赖库** 的 Python 包已经成熟，为访问超过 200 万个公开模型、50 万个公开数据集和 100 万个公开 Space 提供核心功能。本次发布引入了一批面向未来十年开放机器学习的破坏性变更，背后是一个近 300 名贡献者和数百万用户的全球社区。

**🚀 我们强烈建议升级到 v1.0，以享受大幅性能改进和新能力。**

```
pip install --upgrade huggingface_hub
```

本次发布的主要变化包括：迁移到 `httpx` 作为后端库；彻底重新设计的 `hf` CLI（取代已弃用的 `huggingface-cli`），采用基于 Typer 的界面、功能集大幅扩展；以及全面启用 `hf_xet` 做文件传输，取代老的 `hf_transfer`。**[完整发布说明见这里](https://github.com/huggingface/huggingface_hub/releases/tag/v1.0.0)**。

> 我们下了很大功夫确保 huggingface_hub v1.0.0 保持向后兼容。实践中，大多数 ML 库在 v0.x 和 v1.x 下都应该无缝工作。主要的例外是 transformers：其 v4 版本明确要求 huggingface_hub v0.x，即将发布的 v5 则要求 v1.x。各库的详细兼容性对照，请参考该 issue 中的表格。

## 库背后的故事

每个大库都有一个故事。对 `huggingface_hub` 来说，它始于一个简单的想法：**如果分享机器学习模型能像在 GitHub 上分享代码一样容易，会怎样？**

在 Hugging Face Hub 的早期，研究者和实践者面临共同的痛点。训练一个前沿模型需要大量算力和专业知识；而训练完成后，这些模型往往孤立地躺在本地机器上，靠（失效的）Google Drive 链接分享。AI 社区在重复劳动、浪费资源、错过协作机会。

Hugging Face Hub 正是这一挑战的答案。最初它主要用来分享与 `transformers` 库兼容的 checkpoint。与 Hub 交互的全部 Python 代码都活在 transformers 库内部，其他库无法复用。

2020 年末，我们发布了 `huggingface_hub` [v0.0.1](https://github.com/huggingface/huggingface_hub/releases/tag/v0.0.1)，使命很简单：把内部逻辑从 `transformers` 中抽出来，做成一个专门的库，统一在 Hugging Face Hub 上访问和分享机器学习模型与数据集的方式。最初这个库简单得就是一个下载文件、管理仓库的 Git 封装。五年、35+ 个版本之后，`huggingface_hub` 早已超越出身。

让我们回顾这段旅程。

### 奠基岁月（2020-2021）

早期版本确立了基础。[0.0.8](https://github.com/huggingface/huggingface_hub/releases/tag/v0.0.8) 引入了我们最早的 API，把 Git 命令封装起来与仓库交互。[0.0.17](https://github.com/huggingface/huggingface_hub/releases/tag/v0.0.17) 带来了基于 token 的认证，让私有仓库的安全访问和上传成为可能。开局虽然简陋，却为之后的一切打下了地基。

### 大转向：从 Git 到 HTTP（2022）

2022 年 6 月，[0.8.1](https://github.com/huggingface/huggingface_hub/releases/tag/v0.8.1) 标记了一个转折点：我们引入了 HTTP Commit API。用户不再需要安装 Git 和 Git LFS，可以直接通过 HTTP 请求上传文件。新的 `create_commit()` API 极大简化了工作流，尤其对用 Git LFS 很笨重的大模型文件。此外还引入了带 Git 感知的缓存文件布局，所有库（不仅是 transformers，第三方库也一样）从此共享同一份缓存，支持显式版本管理和文件去重。

这不只是技术改进，更是一次理念转向。我们不再是为 transformers 做 Git 封装，而是在为机器学习制品构建专用基础设施，可以为整个 ML 生态里的任何库供能。

### 持续扩张的 API（2022–2024）

随着 Hub 从一个模型仓库成长为完整平台，`huggingface_hub` 也以不断扩张的 API 面积跟进。仓库核心原语逐步成熟：列目录树、浏览 ref 和 commit、读取文件、同步文件夹、管理标签、分支和发布周期。仓库元数据和 webhook 补齐了整套能力，让团队可以实时响应变化。

同期，[Spaces](https://huggingface.co/docs/huggingface_hub/guides/manage-spaces) 兴起——一种简单但强大的方式，直接在 Hub 上托管和分享交互式 ML demo。随着时间推移，`huggingface_hub` 获得了对 Spaces 的完整程序化控制（硬件申请、secrets、环境配置、上传）。为了把模型部署到生产级基础设施，[Inference Endpoints](https://huggingface.co/docs/huggingface_hub/guides/inference_endpoints) 也被集成进来。最后，[Jobs API](https://huggingface.co/docs/huggingface_hub/guides/jobs) 在稍后（2025 年三季度）上线，补全了我们的算力版图。

社交和社区层也成了头等公民：从 [pull request 和评论](https://huggingface.co/docs/huggingface_hub/guides/community)的 API，到用户与组织信息、仓库点赞、关注与粉丝，再到用于策划和分享相关资源合集的 [Collections](https://huggingface.co/docs/huggingface_hub/guides/collections)。日常体验也在进步：Colab 中的无缝认证、断点续传下载、大规模文件夹的可靠上传等等。

然后是 [0.28.0](https://github.com/huggingface/huggingface_hub/releases/tag/v0.28.0) 和 [Inference Providers](https://huggingface.co/docs/huggingface_hub/guides/inference) 生态。我们不再只用单一推理后端，而是与多家 serverless 服务商合作（Together AI、SambaNova、Replicate、Cerebras、Groq 等），用一个 API 配合透明路由。我们采用了按请求付费的推理架构，正好匹配人们实际希望的工作方式。

### Ready. Xet. Go!（2024-2025）

[0.30.0](https://github.com/huggingface/huggingface_hub/releases/tag/v0.30.0) 引入了 Xet——一种在 Git 仓库中存储大对象的开创性新协议。与按文件去重的 Git LFS 不同，Xet 在块（chunk）级别工作（64KB 块）。当你更新数据集或模型里的大文件时，只上传或下载发生变化的块，而不是整个文件。

[迁移规模巨大](https://huggingface.co/spaces/jsulz/ready-xet-go)，从 50 多万个仓库里的 20PB 起步。但整个过程透明完成，完全向后兼容。一年后，**600 万+ 仓库**中全部 **77PB+** 数据都已迁移到 Xet 后端，带来更快（也更聪明！）的上传下载。全程无需用户干预，也不打断现有工作流 🔥

[![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/huggingface-hub-v1/xet_progress.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/huggingface-hub-v1/xet_progress.png)

## 衡量增长与影响

衡量一个开源库的增长和影响是件棘手的事，但数字自会讲述故事：

- **月下载量 1.135 亿次**，累计 **16 亿次**（2025 年 10 月）。
- 支撑访问 **200 万+** 公开模型、**50 万+** 公开数据集、**100 万+** 公开 Space；算上私有仓库大约是两倍。
- 每天 **6 万+** 用户、每月 **55 万+** 用户在使用。
- 从创业公司到财富 500 强，**20 万+ 家企业**信赖它。

但真正的规模要看生态。`huggingface_hub` 是 GitHub 上 **20 万+ 仓库**和 PyPI 上 **3,000 个包**的**依赖**，支撑着从 Keras、LangChain、PaddleOCR、ChatTTS、YOLO、Google Generative AI、Moshi、NVIDIA NeMo、Open Sora 等主要第三方框架，到 ML 领域数不胜数的更小库和工具。我们自己的生态（transformers、diffusers、datasets、sentence-transformers、lighteval、gradio、peft、trl、smolagents、timm、lerobot 等）同样受益于这块基石。

了不起的是？大多数第三方集成都是自然发生的，我们没有参与。Hugging Face Hub 以无数方式赋能 ML 社区，而它已经走多远、被用多广，始终让我们心怀谦卑。

## 为下一个十年而构建

1.0 版本不只是为了到达一个里程碑，而是**为开放机器学习的下一个十年打地基**。我们做的破坏性变更不是随意的，而是战略性决策：让 `huggingface_hub` 能随 AI 的爆炸性增长一起扩展，同时保持数百万开发者赖以生存的可靠性。

### 用 httpx 与 hf_xet 现代化 HTTP 基础设施

v1.0 最重要的架构变化是从 `requests` 迁移到 [`httpx`](https://www.python-httpx.org/)。这不是简单的换依赖，而是把库带入现代 HTTP 时代的根本升级。

**为什么是 httpx？** 收益是实打实的：原生 HTTP/2 支持带来更好的连接效率，真正的线程安全让连接可以跨多线程安全复用。最重要的是，`httpx` 为同步和异步操作提供了统一 API，消除了我们同步与异步推理客户端之间曾经存在的微妙行为差异。

这次迁移被设计得尽可能透明。大多数用户不需要改动任何东西。对使用自定义 HTTP 后端的人，我们提供了清晰的迁移路径：从 `configure_http_backend()` 到 `set_client_factory()` 和 `set_async_client_factory()`。

此外，`hf_xet` 现在是上传下载 Hub 文件的默认包，取代了此前可选的 `hf_transfer`——后者已被彻底移除。

### 用 MCP 和 Tiny-Agents 让智能体变简单

[0.32.0](https://github.com/huggingface/huggingface_hub/releases/tag/v0.32.0) 引入了 **Model Context Protocol（MCP）集成**和 **tiny-agents**，从根本上改变了开发者构建 AI 智能体的方式。过去需要复杂框架集成的事，现在大约 70 行 Python 就能完成。

[`MCPClient`](https://huggingface.co/docs/huggingface_hub/package_reference/mcp) 为 AI 智能体与工具交互提供了标准化方式，而 `tiny-agents` CLI 让你直接运行 Hub 上的智能体。连接本地或远程 MCP 服务器，把任意 Gradio Space 当作工具，构建自然、响应灵敏的对话式智能体。

这一切都构建在我们现有的 `InferenceClient` 及其支持的数十家 Inference Providers 之上。我们坚信智能体是未来，而 `huggingface_hub` 要做的，就是提供让 AI 构建者们玩转智能体的积木。

### 面向现代工作流的完整 CLI

CLI 已经从简单的命令行工具进化成**覆盖 ML 操作的全面界面**。精简的 `hf` 命令取代老式 `huggingface-cli`，采用现代的「资源-动作」模式：

- `hf auth login` 认证
- `hf download` 和 `hf upload` 传输文件
- `hf repo` 管理仓库
- `hf cache ls` 和 `hf cache rm` 管理缓存
- `hf jobs run` 使用云计算

CLI 附带[沙箱化安装器](https://huggingface.co/docs/huggingface_hub/installation#install-the-hugging-face-cli)，升级时不会破坏现有开发环境：

```
# On macOS or Linux
curl -LsSf https://hf.co/cli/install.sh | sh

# or on Windows
powershell -ExecutionPolicy ByPass -c "irm https://hf.co/cli/install.ps1 | iex"
```

加上自动补全支持和跨平台安装器，CLI 如今的手感已媲美任何现代开发者工具。

### 为大扫除未来

1.0 版本移除了拖累我们的历史包袱。基于 Git 的 `Repository` 类已成为过去。基于 HTTP 的方法如 `upload_file()` 和 `create_commit()` 更简单、更可靠、更适合现代工作流。`HfFolder` 的 token 管理被显式的 `login()`、`logout()` 和 `get_token()` 函数取代。老的 `InferenceApi` 类被功能更完整的 `InferenceClient` 替代。`hf_transfer` 已被 `hf_xet` 二进制包全面取代。

这些改变都不是轻率做出的。大部分弃用都提前数月公告，附带清晰警告和迁移指南。结果是一个更干净、更易维护的代码库，可以把精力放在面向未来的功能上，而不是支撑已废弃的模式。

### 迁移指南

我们理解破坏性变更会带来冲击。这就是为什么我们投入大量精力让迁移尽可能平滑。我们的[完整迁移指南](https://huggingface.co/docs/huggingface_hub/concepts/migration)为每一项变更提供分步说明，并解释为什么每项变更是必要的。

最重要的是，我们尽可能保持了向后兼容。例如 `HfHubHttpError` 同时继承旧的 `requests` 和新的 `httpx` 基类 `HTTPError`，确保错误处理跨版本继续工作。通过这次发布，我们全面拥抱未来：将只专注 v1.0 及之后，确保交付社区与 Hugging Face Hub 交互所需的性能、功能和工具。此前的 `v0.*` 版本仍会在 PyPI 上保留，但只会收到漏洞修复更新。

> 我们下了很大功夫确保 huggingface_hub v1.0.0 保持向后兼容。实践中，大多数 ML 库在 v0.x 和 v1.x 下都应该无缝工作。主要的例外是 transformers：其 v4 版本明确要求 huggingface_hub v0.x，即将发布的 v5 则要求 v1.x。各库的详细兼容性对照，请参考该 issue 中的表格。
