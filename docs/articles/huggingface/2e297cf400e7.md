# 在 Transformers.js 中试验拟议的跨源存储 API

（本文由 Google Chrome 团队的 Developer Relations Engineer [Thomas Steiner](https://blog.tomayac.com/) 投稿。）

Transformers.js 为 Web 开发者提供了一种简单的方式，通过面向具体任务的 pipeline 在 Web 应用里用上 transformer 的能力。要在浏览器里做推理，开发者创建一个 [`pipeline()`](https://huggingface.co/docs/transformers.js/en/api/pipelines) 实例，并指定想让它处理的任务。举个具体例子，下面的代码片段演示了如何搭建一个自动语音识别（ASR）pipeline。

```
import { pipeline } from 'https://cdn.jsdelivr.net/npm/@huggingface/transformers@4.2.0';

const asr = await pipeline(
  'automatic-speech-recognition',
  'Xenova/whisper-tiny.en',
  { device: 'webgpu' },
);
const result = await asr('jfk.wav');
console.log(result);
```

[![自动语音识别 pipeline 的一个极简示例。](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cross-origin-storage/87a91qnbicf.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cross-origin-storage/87a91qnbicf.png)

## 缓存难题

你会在源码里注意到我把模型指定为 [`Xenova/whisper-tiny.en`](https://huggingface.co/Xenova/whisper-tiny.en)，对于常见的英文自动语音识别任务，这是个相当不错的选择。事实上，根据 Transformers.js 的[默认模型解析](https://github.com/huggingface/transformers.js/blob/main/packages/transformers/src/pipelines/index.js)，它甚至是*默认*模型，见所链接的[代码摘录](https://github.com/huggingface/transformers.js/blob/bc9cf7400f4f2c8695016699f879e31026ff0313/packages/transformers/src/pipelines/index.js#L151-L158)。

### 模型资源

当你在[浏览器里运行这个示例](https://googlechrome.github.io/samples/transformersjs-automatic-speech-recognition/index.html)时，Transformers.js 会自动负责下载并缓存相关的模型资源和 Wasm 文件。下面这张截图展示了访问应用之后 Chrome DevTools 的 [Cache storage](https://developer.chrome.com/docs/devtools/storage/cache) 区域。当你重新加载页面时，资源会从 [Cache API](https://developer.mozilla.org/en-US/docs/Web/API/Cache) 提供，模型几乎能立刻返回结果。

[![Chrome DevTools Cache storage 区域，展示了访问应用之后的 Whisper AI 模型资源和 Wasm 运行时文件。](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cross-origin-storage/otd8tt1gusb.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cross-origin-storage/otd8tt1gusb.png)

然而，`Xenova/whisper-tiny.en` 是个很受欢迎的模型（而且如上所述，还是 Transformers.js 里的*默认* ASR 模型），不难想象你访问的应用里不会只有一个用它。为了模拟这种情形，这里有和前面一样的示例应用，但它是从一个[不同的源](https://rawcdn.rawgit.net/GoogleChrome/samples/c4192bd7a3c66fc288a7b22b77acb935df00b8a1/transformersjs-automatic-speech-recognition/index.html)提供的。当你访问这个不同源的应用时，浏览器无法让它几乎立刻可用，而是必须把所有模型资源重新下载并缓存一遍，即便它们和之前逐字节完全相同。就算在这个玩具示例里，这也带来了 177 MB 的重复下载和存储，你可以在 Chrome DevTools [Application 面板](https://developer.chrome.com/docs/devtools/application#open_the_application_panel)的 **Storage** 区域查看。可以想象，这会很快积少成多。

[![Chrome DevTools Storage 概览，显示已用存储达 177 MB。](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cross-origin-storage/9byoniem0pw.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cross-origin-storage/9byoniem0pw.png)

### Wasm 运行时资源

但更糟的还在后面。我们给这个玩具示例再加一个 pipeline：情感分析。情感分析[默认](https://github.com/huggingface/transformers.js/blob/bc9cf7400f4f2c8695016699f879e31026ff0313/packages/transformers/src/pipelines/index.js#L65)使用 [`Xenova/distilbert-base-uncased-finetuned-sst-2-english`](https://huggingface.co/Xenova/distilbert-base-uncased-finetuned-sst-2-english) 模型。只要不指定模型，Transformers.js 的默认模型解析就会自动帮你选好。

```
const classifier = await pipeline('sentiment-analysis');
const sentiment = await classifier(result.text);
console.log(sentiment);
```

[![image](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cross-origin-storage/le7l1km7o4g.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cross-origin-storage/le7l1km7o4g.png)

两个完全不同的 AI 模型，却都依赖同一个 4,733 kB 的 `ort-wasm-simd-threaded.asyncify.wasm` WebAssembly（Wasm）运行时文件——它[来自底层的 ONNX Runtime 库](https://onnxruntime.ai/docs/api/js/interfaces/Env.WasmFilePaths.html#wasm)，Transformers.js 正是构建在其之上。打开[在另一个源上的扩展演示](https://rawcdn.rawgit.net/GoogleChrome/samples/d47114a15637383015c274e7bdcd81e1a17b0ccf/transformersjs-automatic-speech-recognition/index2.html)，你会在 [**Network** 标签](https://developer.chrome.com/docs/devtools/network#load)里注意到，连 Wasm 运行时也被重新下载并缓存了一遍。

[![Chrome DevTools Network 面板，显示正在下载 Wasm 运行时资源。](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cross-origin-storage/pz12g20fqeg.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cross-origin-storage/pz12g20fqeg.png)

所以，哪怕你运行的应用并不共享同一批 AI 模型，浏览器仍然会为你已经拥有的共享 Wasm 资源发起冗余请求，并且还会把它们再缓存一遍，从而占用你的磁盘空间。

### 缓存隔离

#### AI 模型资源的提供

默认情况下，**AI 模型资源**来自 [Hugging Face Hub](https://huggingface.co/docs/hub/en/models-the-hub)，最终来自 Hugging Face CDN。浏览器会请求像 [`https://huggingface.co/Xenova/distilbert-base-uncased-finetuned-sst-2-english/resolve/main/config.json`](https://huggingface.co/Xenova/distilbert-base-uncased-finetuned-sst-2-english/resolve/main/config.json) 这样的资源，然后被重定向到最终的 CDN URL，本例中就是 [`https://huggingface.co/api/resolve-cache/models/Xenova/distilbert-base-uncased-finetuned-sst-2-english/0b6928efcb76139cae2c6881d49cda67fe119f42/config.json?%2FXenova%2Fdistilbert-base-uncased-finetuned-sst-2-english%2Fresolve%2Fmain%2Fconfig.json=&etag=%223c36342ef1f74de2797d667c68c6b7b988d0b87c%22`](https://huggingface.co/api/resolve-cache/models/Xenova/distilbert-base-uncased-finetuned-sst-2-english/0b6928efcb76139cae2c6881d49cda67fe119f42/config.json?%2FXenova%2Fdistilbert-base-uncased-finetuned-sst-2-english%2Fresolve%2Fmain%2Fconfig.json=&etag=%223c36342ef1f74de2797d667c68c6b7b988d0b87c%22)。

#### Wasm 运行时资源的提供

**Wasm 运行时资源**默认由 [jsDelivr CDN](https://www.jsdelivr.com/) 提供。例如，截至本文撰写时，`ort-wasm-simd-threaded.asyncify.wasm` 来自 [`https://cdn.jsdelivr.net/npm/onnxruntime-web@1.26.0-dev.20260416-b7804b056c/dist/ort-wasm-simd-threaded.asyncify.wasm`](https://cdn.jsdelivr.net/npm/onnxruntime-web@1.26.0-dev.20260416-b7804b056c/dist/ort-wasm-simd-threaded.asyncify.wasm)。

你可能会说，既然不同的应用尽管运行在不同的源上，最终却从相同的 CDN URL 提供资源，那么只要最终 URL 一致，缓存就不该是个问题。遗憾的是，浏览器里的缓存机制长期并非如此运作。这篇文章 [Gaining security and privacy by partitioning the cache](https://developer.chrome.com/blog/http-cache-partitioning) 讲了所有细节，但本质上，**缓存是按源进行隔离的**，用以防范时序攻击：一个网站响应 HTTP 请求所花的时间，可能暴露浏览器过去访问过同一资源这一事实，这会让浏览器面临安全和隐私泄露的风险。

#### Chrome 的实现

具体实现因浏览器而异，但在 Chrome 中，缓存资源除了用**资源 URL** 之外，还会用一个 Network Isolation Key（网络隔离键）来作为键。Network Isolation Key 由**顶层站点（top-level site）**和**当前帧站点（current-frame site）**组成。以托管在 `https://googlechrome.github.io` 和 `https://rawcdn.rawgit.net` 上的前面那些玩具示例为例。如果它们都使用来自 `https://cdn.jsdelivr.net/npm/onnxruntime-web@1.26.0-dev.20260416-b7804b056c/dist/ort-wasm-simd-threaded.asyncify.wasm` 的 Wasm 运行时，它们的缓存键会如下表所示。

| Network Isolation Key | **Resource URL** |  |
| --- | --- | --- |
| **Top-level site** | **Current-frame site** |  |
| https://googlechrome.github.io | https://googlechrome.github.io | https://cdn.jsdelivr.net/npm/onnxruntime-web@1.26.0-dev.20260416-b7804b056c/dist/ort-wasm-simd-threaded.asyncify.wasm |
| https://rawcdn.rawgit.net | https://rawcdn.rawgit.net | https://cdn.jsdelivr.net/npm/onnxruntime-web@1.26.0-dev.20260416-b7804b056c/dist/ort-wasm-simd-threaded.asyncify.wasm |

所以，即便资源 URL 完全一致，由于 Network Isolation Key 不匹配，缓存无法命中，这就意味着重复下载和重复存储。这正是 Cross-Origin Storage 提案要解决的难题。

## 登场：Cross-Origin Storage API

> 💡 注意：Cross-Origin Storage API 是一个早期阶段的提案，尚未定稿。虽然拟议的 API 目前还没有在任何浏览器中原生实现，但你不必干等就能试验它。安装 Cross-Origin Storage 扩展，即可在所有页面上注入 `navigator.crossOriginStorage` polyfill，测试完整流程。

拟议的 **[Cross-Origin Storage](https://github.com/WICG/cross-origin-storage)（COS）API** 引入了一个专门的 `navigator.crossOriginStorage` 接口，Web 应用可以通过它在源边界之间存取大文件，而识别文件的不是 URL，而是一个加密哈希。

最后这点——用加密哈希——是关键所在。因为 COS 是按**哈希**而非 URL 或源来识别文件的，你在访问 `https://googlechrome.github.io` 时下载的那个 `ort-wasm-simd-threaded.asyncify.wasm` Wasm 运行时，会被识别为与 `https://rawcdn.rawgit.net` 即将请求的那个完全相同，无论这两个源各自是从哪里获取它的。下面这段代码演示了基本流程。

```
const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};

try {
  const handle = await navigator.crossOriginStorage.requestFileHandle(hash);
  // Cache hit! Get the file as a Blob and use it directly.
  const fileBlob = await handle.getFile();
} catch {
  // Cache miss. Download from network, then store for next time.
  const fileBlob = await fetch('https://cdn.jsdelivr.net/.../ort-wasm-simd-threaded.asyncify.wasm')
    .then(r => r.blob());
  const handle = await navigator.crossOriginStorage.requestFileHandle(
    hash,
    { create: true, origins: '*' },
  );
  const writableStream = await handle.createWritable();
  await writableStream.write(fileBlob);
  await writableStream.close();  
}
```

如果资源在 COS 里，你会拿到一个 [`FileSystemFileHandle`](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle)，可以通过 [`getFile()`](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/getFile) 直接读出 blob（返回的 [`File`](https://developer.mozilla.org/en-US/docs/Web/API/File) 继承自 [`Blob`](https://developer.mozilla.org/en-US/docs/Web/API/Blob)）。如果资源不在 COS 里，就回退到网络，并把资源写入 COS，留给下一个需要它的应用——可能是你自己的应用，也可能是另一个完全无关、甚至在不同源上的应用。

这个 API 是刻意参照 [File System Standard](https://fs.spec.whatwg.org/) 里的 [`FileSystemDirectoryHandle.getFileHandle()`](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemDirectoryHandle/getFileHandle) 来设计的，你大概已经在 [Origin Private File System](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)（OPFS）API 里熟悉它了。`hash` 参数扮演的角色和 OPFS 里的 `name` 参数一样：唯一标识一个资源。`options.create` 标志的工作方式也一样：缺省或 `false` 表示只读访问，`true` 表示你要写入。

### 控制谁能读什么

并非所有资源都应全局共享。COS 让开发者通过存储文件时的 `origins` 选项精确控制可见性。

- 设置 `origins: '*'` 会让文件**全局可用**，任何源都能按哈希找到它。对于 Transformers.js 示例里的 AI 模型资源或 Wasm 运行时，这是正确的选择——要点就在于让 Web 上每个应用都从同一份缓存副本中受益。
- 传入一个具体的源列表，比如 `origins: ['https://write.example.com', 'https://calculate.example.com']`，会把访问**限制**在这些站点内。这很适合在一家公司自有产品之间共享、但不希望被其他人发现的专有资源，例如一款商业办公套件里用的专有校对 AI 模型。
- 完全不写 `origins`，则文件只对 **[同源站点（same-site）](https://web.dev/articles/same-site-same-origin#same-site-cross-site) 源**可用。对于在组织所有子域名之间共享、但无意跨越组织边界的资源，这是个合理的默认。

有一条重要规则：可见性可以升级，但绝不能降级。如果一个文件已经全局可用，之后试图用受限的 `origins` 列表再存一次会被静默忽略。这可以防止恶意行为者把公共资源重新存一遍、从而收窄其可用性。反过来则可行：最初用受限 `origins` 列表存储的文件，之后可以改得更宽松。任何站点——不只是最初的存储者——都可以对同一哈希（哈希并非秘密）调用 `requestFileHandle()`，传入 `create: true` 和更宽的 `origins` 值，浏览器在验证哈希匹配后，资源从此就对更广的受众可用。注意，升级可见性的站点**必须**仍然通过返回的 handle 写入完整的文件。这一要求是为了防止站点把升级路径当成侧信道，用来探测某个文件是否已经存进 COS。

### 设计即保证完整性

COS 一个微妙但重要的性质是，浏览器在你写入文件时会**校验哈希**。如果你写入的数据与声明的哈希不符，写入就会失败并报错。这让完整性校验自动化了：从 COS 读文件的应用可以放心，它拿到的正是预期的那些字节——和它在网络下载后自己计算一遍哈希所能得到的保证是一样的。

在 Transformers.js 场景里，这一点其实双重有用。如今，下载模型权重之后，大多数应用并没有实际可行的方法去验证 CDN 提供的字节是否正确。有了 COS，存储里的每个文件在写入时都会被隐式校验，无论它来自官方 Hugging Face CDN 还是某个随机站点的自建镜像。

### 不牺牲实用性的隐私

当然，一个跨源共享缓存会引出与分区 HTTP 缓存相反的问题：如果任何站点都能按哈希探测某文件是否存在，攻击者岂不就是否缓存了某个游戏引擎的 Wasm 模块来了解用户的浏览历史？

COS 通过两个互补机制来应对：

- 首先是 `origins` 字段：那些不该被全局探测的专有资源，简单地不要用 `origins: '*'` 存储即可——通过**开发者教育**，鼓励开发者在合适的时候考虑这一点。
- 其次是**可用性门控（availability gating）**：即便对声明为全局的文件，如果浏览器没有在足够多的不同源上遇到过它，也可能不确认它的存在。一个只出现在一两个站点上的文件仍可能充当跨站标识符，因此浏览器可能返回一个错误，就好像文件根本不存在一样，无论磁盘上实际有没有。在 Chrome 团队，我们清楚不常见资源可能造成的隐私泄露，总体计划通过限制哪些具体资源可以被缓存来缓解。具体的缓解措施仍在完善中。

关键在于，这意味着报错并不是一个确定性的答案。它可能表示"未存储"，也可能表示"已存储，但浏览器不打算告诉你"。应用应当始终以同样的方式处理：回退到网络。

### 这对 Transformers.js 示例意味着什么

回到前面那些玩具示例：`ort-wasm-simd-threaded.asyncify.wasm` 运行时大小为 4,733 kB，被每一个基于 Transformers.js 的应用共享，无论它用哪个 AI 模型。有了 COS，第一个加载它的应用只需下载一次，并以 SHA-256 哈希加上 `origins: '*'` 存下来。之后每个应用——无论在 `https://googlechrome.github.io`、`https://rawcdn.rawgit.net` 还是其他源上——都能在 COS 里立刻找到它。那 177 MB 的重复 Whisper 模型权重呢？同样的故事：`Xenova/whisper-tiny.en` 只下载一次，第二次靠哈希被识别出来，随即从 COS 以毫秒级提供。当然，`Xenova/distilbert-base-uncased-finetuned-sst-2-english` 也是如此。

Transformers.js 本身已经在库层面试点 COS API。[Pull request #1549](https://github.com/huggingface/transformers.js/pull/1549) 在一个可选开启的标志后面引入了实验性的 COS 缓存后端。启用它只需在你搭建 pipeline 之前加一行：

```
import { env, pipeline } from "https://cdn.jsdelivr.net/npm/@huggingface/transformers@4.2.0";

// 👇 Opt in to the experimental Cross-Origin Storage cache backend.
env.experimental_useCrossOriginStorage = true;

const asr = await pipeline('automatic-speech-recognition', 'Xenova/whisper-tiny.en', { device: 'webgpu' });
const result = await asr('jfk.wav');
console.log(result);
```

注意标志上的 `experimental_` 前缀，这是有意为之，它表明底层的浏览器 API 尚未标准化，可能会在不升大版本号的情况下变更。设置该标志后，Transformers.js 会逐个为每个 [Xet 跟踪](https://huggingface.co/docs/hub/en/xet/index)的模型文件（那些大型的 ONNX 权重文件）解析 SHA-256 哈希——做法是拉取原始的 Xet 指针（[示例原始指针文件](https://huggingface.co/Xenova/whisper-tiny.en/raw/main/onnx/decoder_model.onnx)）并提取其 `oid sha256:` 字段，然后把这个哈希用作 `navigator.crossOriginStorage` 的键。如果模型已经在 COS 里（因为别的站点先存了），就即时提供，无需一次网络往返；否则回退到常规下载，并把结果存入 COS 供下一个调用者使用。在这个玩具示例里，实际的好处是：`Xenova/whisper-tiny.en` 和 `Xenova/distilbert-base-uncased-finetuned-sst-2-english`（当然还有 `ort-wasm-simd-threaded.asyncify.wasm`）无论被多少个不同源请求，都只需要穿过网络一次。

### 模型灵活性

玩具示例用 `Xenova/whisper-tiny.en` 跑得好好的，但显然，如果用户已经在 COS 缓存里有[其他任意 Whisper 变体](https://huggingface.co/Xenova/models?search=whisper)，你多半也不会拒绝。例如，用户可能已经有了 [`Xenova/whisper-large-v3`](https://huggingface.co/Xenova/whisper-large-v3)，顾名思义，它比 tiny 版要大得多。Transformers.js 的 [Model Registry](https://huggingface.co/docs/transformers.js/en/api/utils/model_registry) 让对模型保持灵活成为可能。如果你知道应用的需求可以由 `Xenova/whisper-tiny.en`、`whisper-medium.en` 或 `Xenova/whisper-large-v3` 中的任意一个来满足，就可以去注册表里查每个模型关联的文件，探测它们在 COS 缓存里的存在情况（其中可能部分或完整地包含你需要的模型资源），然后再最终决定选哪个模型。[`ModelRegistry.is_pipeline_cached()`](https://huggingface.co/docs/transformers.js/en/api/utils/model_registry#modelregistryispipelinecachedtask-modelid-options--promise--boolean-) API 直接与 COS（当然也和 Cache API）集成，所以这个操作非常顺手。

### 现在就试试

COS API 尚未在任何浏览器中原生实现，但你不必干等就能试验它。安装 [Cross-Origin Storage 扩展](https://chromewebstore.google.com/detail/cross-origin-storage/denpnpcgjgikjpoglpjefakmdcbmlgih)，即可在所有页面上注入 `navigator.crossOriginStorage` polyfill 并测试完整流程。查看该[扩展的源码](https://github.com/web-ai-community/cross-origin-storage-extension)，并按[使用说明](https://github.com/web-ai-community/cross-origin-storage-extension?tab=readme-ov-file#usage)开始。

[![Chrome Web Store 上的 Cross-Origin Storage 扩展页面。](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cross-origin-storage/0q3rowmy67ta.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/cross-origin-storage/0q3rowmy67ta.png)

装好扩展后，现在就能体验完整的端到端流程：打开第一个[启用了 COS 的玩具示例](https://googlechrome.github.io/samples/transformersjs-automatic-speech-recognition/index3.html)，让它加载 `Xenova/whisper-tiny.en`，然后打开[来自第二个源、启用了 COS 的玩具示例](https://rawcdn.rawgit.net/GoogleChrome/samples/1e4f2b8c10adc394352c6ec8327bb503bac7aba1/transformersjs-automatic-speech-recognition/index3.html)。模型不再是之前你看到的 177 MB 重新下载，而是从 COS 以毫秒级提供。打开扩展的弹窗，你就能看到 COS 在起作用。选择 **View by Resource**，你能看到 SHA-256 哈希为 `950978b1dbcbf250335358c1236053ba19a7f7849b33dc777f4421b72b7626fa` 的资源在 `https://googlechrome.github.io` 和 `https://rawcdn.rawgit.net` 之间共享。这也许不明显，但你可以对照 Hugging Face 上的 SHA-256 哈希来验证——你看到的是 [`https://huggingface.co/Xenova/whisper-tiny.en/blob/main/onnx/decoder_model_merged.onnx`](https://huggingface.co/Xenova/whisper-tiny.en/blob/main/onnx/decoder_model_merged.onnx)。现阶段，这个扩展主要面向像你这样的高级用户。等浏览器实现之后，会在浏览器的 **Settings** 页面提供更友好的集成。下面这张截图展示了扩展弹窗里激活的 **View by Resource** 标签，你可以在那里看到带哈希的共享资源，以及把它存入各自 COS 缓存的那两个源。

## 行动号召

如果你正在搭建自己的 Transformers.js 应用，行动号召很简单：在第一次 `pipeline()` 调用之前加上 `env.experimental_useCrossOriginStorage = true`，安装扩展，然后看着 Network 标签里的重复下载消失。每个选择启用的站点，都会让其他站点的用户体验更快、更省。启用它完全没有风险：如果因为用户没装 COS 扩展而不支持 COS API，代码就会回退到默认路径（[Cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache) API）。

在试验 COS 的不止 Transformers.js。[WebLLM](https://webllm.mlc.ai/)（可选启用，见[文档](https://webllm.mlc.ai/docs/user/advanced_usage.html#using-cross-origin-storage-cache)）和 [wllama](https://github.com/ngxson/wllama)（自动，见 [PR](https://github.com/ngxson/wllama/pull/248)）同样对这个拟议 API 很兴奋。

在 Chrome 团队，我们[正在考虑在浏览器中原生实现 COS API](https://chromestatus.com/feature/5163371507875840)。作为一个早期提案，我们欢迎对这个 API 以及提案本身形态的反馈。[Cross-Origin Storage 仓库](https://github.com/WICG/cross-origin-storage)是提 issue、[表达支持](https://github.com/WICG/cross-origin-storage/labels/expression%20of%20support) 或开 PR 的地方。
