## 太长不看（TL;DR）

NVIDIA Kumo Relational 是一个预训练的关系型基础模型，直接在企业数据库上做预测。给定一个预测查询，它会把最多 10,000 条历史样本作为上下文收集起来，并在一次前向传播中预测流失、需求或欺诈等结果。它不需要任务专属训练，不需要特征工程，也不需要把表打平。Kumo Relational 是首个在常见关系型基准上超越监督式机器学习的 few-shot 基础模型。在 15 个数据库的 41 个任务上，它击败了监督式关系深度学习模型和由专家手工设计特征的梯度提升树流水线；在 SAP SALT 企业基准上，它的平均倒数排名（MRR）比 AutoGluon 集成高出 8%。它可以扩展到 500B+ 行的数据库，并且既服务人、也服务 agent：既可通过 NVIDIA 开源、GPU 原生的 structured-data-models 库使用，也可作为 NVIDIA NIM 使用。

- **论文：** [https://arxiv.org/abs/2604.12596](https://arxiv.org/abs/2604.12596)
- **文档：** [https://docs.nvidia.com/sdgm/rfm/overview](https://docs.nvidia.com/sdgm/rfm/overview)

## 转向结构化数据基础模型

基础模型早已重写了语言与视觉领域的玩法。不久前，生产环境的 NLP 还意味着每个任务一个专用模型，各自配一套分词、词形还原和 n-gram 流水线。LLM 让这套栈基本过时了，原因有三：它们比最好的任务专属模型更准确、投入生产要简单得多，而且足够灵活，开启了一个 agent 应用的新时代。

同样的转变如今正在结构化数据上发生。关系型数据库支撑着世界上最重要的商业决策，但在其上做预测建模仍然需要数周的特征工程、任务专属训练和调优过的流水线。结构化数据基础模型出于同样的三个原因改变了这一点：

**当下更好的准确率：** 作为可直接替换的方案，这些模型已经胜过许多生产流水线，尤其是 XGBoost。在 RelBench V1 的分类任务上，Kumo Relational 在专家手工特征上比梯度提升树平均高出近 4 个 AUROC 点。在 SAP SALT 上，它在手工特征上开箱即比 XGBoost 高出 7 个 MRR 点，微调后高出 13 个 MRR 点。这些结果有力地支持了用 Kumo Relational 替换生产环境中的 XGBoost 流水线。

**简单与敏捷：** 一个预训练模型取代了针对各个任务的独立流水线。一次新的预测变成一条查询，而不是一个项目，于是 ML 团队终于可以在组织的各个层面承接那些传统 ML 做起来过于费力的用例。

**能预测的 agent：** LLM 让 agent 能够读写与推理。结构化数据基础模型则让它们能够预判接下来会发生什么，比如哪个客户会流失，并据此行动。Kumo Relational 本身就被设计成可供 agent 调用，它的 Predictive Query Language（PQL）为 agent 提供了一个提出预测式问题的简单接口。

今天，我们推出 **Kumo Relational**（[论文](https://arxiv.org/abs/2604.12596)、[文档](https://docs.nvidia.com/sdgm/rfm/overview)），这是一个把该范式带到关系型数据上的预训练基础模型。连接一个数据库，描述要预测什么，就能在一次前向传播中得到预测结果。无需训练。

## Kumo Relational 如何工作

多数面向结构化数据的基础模型都是在单张扁平表上运行的。而真实世界的数据存在于关系型数据库中：用户关联到订单，订单关联到产品，它们都在随时间演进。通过手工聚合（*例如*“过去 30 天的平均订单金额”）把这些关系压平成一行，会丢失细粒度的结构信号，而且需要大量人力。

Kumo Relational 是一个*关系型基础模型*（Relational Foundation Model），它直接在数据库上运行，尊重其中的表、外键和时间戳。它只需在反映真实世界数据集的合成关系数据上预训练一次，并通过*上下文学习*（in-context learning）适应每个新任务，在推理时读取最多 10,000 条上下文样本。每条样本都把某个实体在某一时点周围的局部子图与其真实标签配对（*例如*“这个用户流失了”或“这个商品卖出了 142 件”）。

![NVIDIA Kumo Relational 系统概览：(a) 数据库集成，(b) 把自然语言转成预测查询的提示接口，(c) 自动生成上下文并喂给 NVIDIA Kumo Relational 模型，该模型可跨租户横向扩展。][![kumo-relational-architecture](https://cdn-uploads.huggingface.co/production/uploads/6ad8e88370f69967fafc8703/FY-lkWrNmBYRFrosRD2Le.png)](https://cdn-uploads.huggingface.co/production/uploads/6ad8e88370f69967fafc8703/FY-lkWrNmBYRFrosRD2Le.png)

*图 1. Kumo Relational 系统概览。连接数据库、指定预测查询，其余交给 Kumo Relational，从上下文生成到模型推理。*

要做出预测，Kumo Relational 必须做三件事：**(1)** 理解每张表里的值，**(2)** 把跨表的记录关联起来，**(3)** 把带有已知标签的上下文样本与被预测的实体关联起来。具体做法如下：

![Kumo Relational 架构：(a) 带任务、users、orders 和 items 表的上下文输入；(b) 表内的列注意力和行注意力，并注入了上下文标签；(c) 跨表的图注意力和跨样本注意力。][![kumo-relational-system-overview](https://cdn-uploads.huggingface.co/production/uploads/6ad8e88370f69967fafc8703/OFX2a7xwBTfUEcbedTsfe.png)](https://cdn-uploads.huggingface.co/production/uploads/6ad8e88370f69967fafc8703/OFX2a7xwBTfUEcbedTsfe.png)

*图 2. Kumo Relational 架构：(a) 上下文输入，(b) 表内推理，(c) 跨表推理。*

**自动上下文生成：** 任务用 [Predictive Query Language（PQL）](https://arxiv.org/abs/2602.09572)书写，这是一种声明式接口，你只需说明要预测什么，而不是怎么预测。对于时序任务，Kumo Relational 会重放历史数据库状态：它以某个锚点时间戳为界采样以实体为中心的子图，并根据该时间戳之后的事件计算每个标签，同时只向模型提供该时间戳之前的数据。这样可以防止数据泄漏。

**表内推理：** 一个轻量网络独立处理每张表，交替进行列注意力（关联同一列内的值）和行注意力（关联同一行内的特征）。模型会学习哪些列和行对当前预测重要，并在噪声扩散之前将其过滤掉。

**跨表推理：** 一个更大的网络通过在主键/外键关系上的图注意力，把行嵌入沿着关系结构分发，并与跨上下文样本的跨样本注意力交替进行。关系推理就发生在这里，比如把用户的画像与其交易历史关联起来。由于这一阶段处理的是行嵌入，而不是每张表的每一个单元格，该设计避免了二次方开销，并能扩展到较大的上下文和更深的子图。

## Kumo Relational 是如何构建的

Kumo Relational 完全在合成的关系数据上预训练，这些数据模拟了带有多种预测查询的真实世界关系型数据库。预训练分阶段进行，从单表逐步过渡到越来越复杂的关系结构。

预训练所需的多样化关系型数据库很少公开，因此合成数据填补了这一空白。Kumo Relational 的生成器建立在 [PluRel](https://arxiv.org/abs/2602.04029)（Kothapalli 等，ICML 2026）的方法之上，后者把单表数据生成器扩展到完整的关系型数据库。Kumo 团队成员参与开发了 PluRel，也是原论文的共同作者。PluRel 分三个阶段生成每个数据库：一个 schema；行与行之间的外键连接，这些行像真实数据那样聚簇；以及来自结构因果模型（Structural Causal Models）的列值，带有时间趋势和跨表依赖。生成过程很轻量，因此预训练数据实际上是无限的；PluRel 论文还表明，随着合成数据库的增加，预训练损失遵循幂律，而且这些收益能迁移到真实数据库上。

通过这样的预训练，模型学会跨表过滤、关联和聚合信息，而不是依赖固定的聚合。当最高准确率至关重要时，Kumo Relational 还可以在特定数据集和任务上微调。

## 性能

在论文中，我们在来自 RelBench V1 与 V2、SAP SALT 和 4DBInfer 的 15 个关系型数据库上的 41 个基准上评估了 Kumo Relational，覆盖电商、医疗、企业、社交和学术领域。这些数据集都没有在预训练中出现过。Kumo Relational 在分类和回归上都优于最强的监督模型，包括关系深度学习模型和由专家手工设计的表格集成。在 [RelArena-α](https://arxiv.org/abs/2608.16319) 排行榜（在 RelBench V1 上比较关系模型与系统）上，它开箱即位于准确率-效率的帕累托前沿：

![RelArena-α 排行榜的散点图：跨任务的相对准确率（以 Elo 表示，y 轴）对每 1,000 个样本的中位推理时间（x 轴，对数刻度）。Kumo Relational 位于帕累托前沿，约 17 秒、Elo 1,842。得分最高的条目 rt-plurel 在约 7,300 秒时达到 Elo 1,878，大约慢 430 倍。其它每个基础模型、特征工程系统和监督模型的得分都更低、运行也更慢。][![relarena-alpha-leaderboard](https://cdn-uploads.huggingface.co/production/uploads/6ad8e88370f69967fafc8703/9ITlubGvqGVnoy7j_NZDi.png)](https://cdn-uploads.huggingface.co/production/uploads/6ad8e88370f69967fafc8703/9ITlubGvqGVnoy7j_NZDi.png)

*图 3. RelArena-α 排行榜：跨任务的 Elo 对每 1,000 个样本的中位推理时间（对数刻度）。在相近准确率下，Kumo Relational 比得分最高的条目快约 430 倍。*

论文还报告，在 SAP SALT 企业基准上，Kumo Relational 的平均倒数排名（MRR）比大型 AutoGluon 集成高 8%，比近期的表格基础模型高约 25%，而微调可把它对 AutoGluon 的领先扩大到 16%。它在苛刻条件下同样站得住：只用 0.2% 的训练数据作为上下文也能表现良好；即使移除了多达 75% 的外键连接仍然稳定；加入大量噪声列时性能也几乎不退化。

## 局限性

Kumo Relational 在具有有意义关系和时序动态的数据上表现最好，比如随时间变化的用户行为。在训练集非常大的任务上，任务专属的监督模型仍可能胜过上下文预测——在我们的基准中，上下文最多使用了 10,000 条样本。对基础模型进行微调正是为这种情况设计的。此外，预测信号必须在有限跳数内可达，因此建议先针对少数相关表提出一个聚焦的查询，再按需扩展图。

## 演示

Kumo Relational 原生地在数据库上做上下文学习：可以在内存中运行，也可以通过数据库与数仓连接器，或者通过一个自定义图引擎——后者借助内存映射 I/O 以最高 5 GB/s 的速度处理 500B+ 行数据。它已在 NVIDIA 新发布的 GPU 原生 structured-data-models 库中提供，这也是支撑我们姊妹模型 [Kumo Tabular](https://huggingface.co/blog/nvidia/kumo-tabular) 的同一个开源库。该库会在首次使用时从 Hugging Face Hub 下载权重，因此你可以在一个带 GPU 的 notebook 里加载模型并直接预测。下面的代码把上下文样本、待预测实体及其相关表传给模型：

```
# pip install structured-data-models
import sdm

model = sdm.models.KumoRelational(device="cuda")
pred = model(
    # In-context training table (fkeys/timestamps/targets):
    x_context=...,
    y_context=...,
    # Prediction examples (fkeys/timestamps):
    x_query=...,
    # Multi-table information for context/prediction entities:
    related_context_tables=...,
    related_query_tables=...,
)
```

完整的 RelBench 与 SAP SALT 流水线请见该库的[关系型示例](https://github.com/NVIDIA/structured-data-models/tree/main/examples/relational)，其中也包括如何为每个实体采样相关表。

如果想把模型作为独立服务运行，可以把它部署成 NVIDIA NIM，并在 notebook 中让开源的 [structured-data-models-client](https://github.com/NVIDIA/structured-data-models-client) 指向它。你用 PQL 写出预测，客户端会收集上下文样本和相关表，然后发送请求：

```
# pip install 'structured-data-models-client[relational]'
import sdm_client

client = sdm_client.SDMClient(url="http://localhost:8001")  # NIM URL
query = sdm_client.PredictiveQuery(
    # Prediction task in Predictive Query Language (PQL):
    "PREDICT COUNT(orders.*, 0, 30, days) FOR EACH users.user_id",
    # Multi-table data as pandas DataFrames (keys/links inferred):
    {"users": ..., "orders": ...},
)
pred = client.predict(
    # Context examples and related tables for the entities to predict:
    query.materialize(indices=[1, 2, 3]),
    model=sdm_client.KumoRelational(),
)
```

针对本地 NIM 以及在 Databricks 上的端到端运行，请见客户端的[示例 notebook](https://github.com/NVIDIA/structured-data-models-client/tree/main/examples)。
