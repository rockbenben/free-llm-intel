本文带你了解幕后故事：我们如何打造驱动 bloom 的高效推理服务器——即支撑 [https://huggingface.co/bigscience/bloom]() 的推理服务器。

我们在数周内实现了 5 倍的延迟降低（以及高出 50 倍的吞吐）。我们想把这一路经历的挣扎与辉煌胜利都分享给大家。

有很多人在很多阶段参与其中，所以并非所有内容都能在此覆盖。也请多包涵：某些内容可能已经过时甚至完全错误，因为我们仍在学习如何优化超大规模模型，而大量新硬件特性和新知识也在持续涌现。

如果你钟爱的优化流派没有被讨论或被描述得不准确，我们深表歉意——请分享给我们，我们非常乐意尝试新东西并纠正错误。

## 打造 BLOOM

不言而喻，如果这个大模型一开始就无法被使用，就根本没有理由为它优化推理。这是一项由许多人共同领导的非凡工程。

为了在训练时榨干 GPU，团队探索了多种方案，最终选择了 [Megatron-Deepspeed](https://github.com/bigscience-workshop/Megatron-DeepSpeed) 来训练最终模型。这意味着现有代码未必与 `transformers` 库兼容。

## 移植到 transformers

由于原始的训练代码，我们着手做一件我们常做的事：把已有模型移植到 `transformers`。目标是从训练代码中提炼相关部分并在 `transformers` 内实现。这项工作由 [Younes](https://huggingface.co/ybelkada) 承担。这绝非小工程——几乎花了一个月、[200 个 commit](https://github.com/huggingface/transformers/pull/17474/commits) 才达成。

有几件事需要注意，后面还会再提到：

我们需要更小的模型 [bigscience/bigscience-small-testing](https://huggingface.co/bigscience/bigscience-small-testing) 和 [bigscience/bloom-560m](https://huggingface.co/bigscience/bloom-560m)。这极其重要，因为它们更小，所以一切处理都快得多。

首先，你要放弃「最终 logits 逐字节完全一致」的幻想。PyTorch 版本会更换 kernel、引入微妙差异，而不同硬件可能因架构不同产生不同结果（出于成本考虑你大概也不想一直在 A100 GPU 上开发）。

***为所有模型构建一套严格的好测试套件真的非常重要***

我们发现最好的测试是固定一组提示词：已知提示词、已知必须确定的（因此贪心解码的）补全。如果两次生成完全一致，你基本可以忽略微小的 logits 差异。一旦出现漂移（drift），就要调查。可能是你的代码没有做它该做的事，也可能你其实超出了该模型的分布域（out of domain），模型因此对噪声更敏感。如果你有多个提示词、并且提示词足够长，就不太可能对所有提示词都偶然触发该现象。提示词越多越好，越长越好。

第一个模型（small-testing）和大型 bloom 一样用 `bfloat16`，所以一切应该非常相似，但它没怎么训练过、或者就是表现不好，输出波动很大。这意味着我们在生成测试上遇到了麻烦。第二个模型更稳定，但它是用 `float16` 而非 `bfloat16` 训练和保存的，两者之间的误差空间更大。

说句公道话，`bfloat16` -> `float16` 的转换在推理模式下看起来没问题（`bfloat16` 主要为处理大梯度而存在，而推理中不存在大梯度）。

在这一步中，我们发现并实现了一个重要的权衡。因为 bloom 在分布式环境下训练，部分代码在 Linear 层上做张量并行（Tensor parallelism），这意味着在单张 GPU 上把同一运算作为单一操作执行会得到[不同的结果](https://github.com/huggingface/transformers/blob/main/src/transformers/models/bloom/modeling_bloom.py#L350)。我们花了些时间才定位到这一点：要么追求 100% 一致、模型会慢得多；要么接受生成上的微小差异，但运行快得多、代码也更简单。我们选择做成可配置的开关。

## 第一次推理（PP + Accelerate）

```
Note: Pipeline Parallelism (PP) means in this context that each GPU will own
some layers so each GPU will work on a given chunk  of data before handing
it off to the next GPU.
```

现在我们有了一个可用的、干净的 `transformers` 版本，可以开始运行它了。

Bloom 是一个 352GB 的模型（176B 参数，bf16），至少需要这么多 GPU RAM 才放得下。我们短暂探索过在小机器上卸载（offload）到 CPU，但推理速度慢了数个数量级，于是放弃了。

接着我们基本上想直接用到 [pipeline](https://huggingface.co/docs/transformers/v4.22.2/en/pipeline_tutorial#pipeline-usage)。这算吃自己的狗粮，而且 API 在底层一直用的就是它。

不过 `pipelines` 并不感知分布式（这也不是它的目标）。短暂讨论方案后，我们最终用上 [accelerate](https://github.com/huggingface/accelerate/) 新创建的 `device_map="auto"` 来管理模型的切分。我们排查了几个 bug，并修改了 `transformers` 代码以帮助 `accelerate` 正确工作。

其原理是把 transformer 的各层拆开，将模型的一部分分给每张 GPU。GPU0 先干活，然后交接给 GPU1，依此类推。

最终，在上面架一个小型 HTTP 服务器，我们就开始为 bloom（大模型）提供服务了！！

## 起点

但我们甚至还没开始谈优化！

实际上我们已经攒了不少东西，整个过程是一座纸牌屋。做优化时我们要修改底层代码，确保没有以这样或那样的方式「杀死」模型非常重要——而且这比你想象的更容易做到。

我们现在处于优化的最初阶段，需要开始测量、并持续测量性能。因此要考虑我们在乎什么。对于一个支持众多选项的开放推理服务器，我们预期用户会发送各种参数的查询，我们在乎的是：

我们能同时服务多少用户（吞吐量）？平均一个用户要多久才能得到服务（延迟）？

我们用 [locust](https://locust.io/) 写了一个测试脚本，正是这个：

```
from locust import HttpUser, between, task
from random import randrange, random


class QuickstartUser(HttpUser):
    wait_time = between(1, 5)

    @task
    def bloom_small(self):
        sentence = "Translate to chinese. EN: I like soup. CN: "
        self.client.post(
            "/generate",
            json={
                "inputs": sentence[: randrange(1, len(sentence))],
                "parameters": {"max_new_tokens": 20, "seed": random()},
            },
        )

    @task
    def bloom_small(self):
        sentence = "Translate to chinese. EN: I like soup. CN: "
        self.client.post(
            "/generate",
            json={
                "inputs": sentence[: randrange(1, len(sentence))],
                "parameters": {
                    "max_new_tokens": 20,
                    "do_sample": True,
                    "top_p": 0.9,
                    "seed": random(),
                },
            },
        )
```

**注意：这不是最好也不是唯一的负载测试，但它总是最先跑的那个，以便在各种方案之间公平比较。在这个基准上最好并不意味着它就是最佳方案。除了真实世界性能之外，还必须使用其他更复杂的场景。**

在这个基准上，最初的表现为（GCP 上的 16xA100 40GB——全程使用的机器）：

Requests/s：0.3（吞吐量） Latency：350ms/token（延迟）

这些数字并不好看。开工之前，先估算我们能想象的最好结果。运算量公式为 `24Bsh^2 + 4𝐵s^2h24Bsh^2 + 4𝐵s^2h`，其中 `B` 是 batch 大小，`s` 是序列长度，`h` 是隐藏维度。

算一下，得到单次前向传播 `17 TFlop`。看 A100 的[规格](https://www.nvidia.com/en-us/data-center/a100/)，单卡标称 `312 TFLOPS`。也就是说单张 GPU 理论上能跑到 `17 / 312 = 54ms/token`。我们用了 16 张，整机即 `3ms/token`。这些数字请大方地加盐看待（当作粗略估计）——这些数字永远达不到，现实性能很少与规格匹配。而且如果计算不是你的瓶颈，这也不是你能达到的下限。知道离目标还有多远是好习惯。本例中我们差了 2 个数量级，相当遥远。此外，这个估算把所有 flops 都用在降低延迟上，意味着一次只能处理一个请求（没关系，因为你已在最大化机器性能，别的也做不了什么；但我们可以通过更易实现的 batching 用更高延迟换回吞吐量）。

## 探索多条路线

```
Note: Tensor Parallelism (TP) means in this context that each GPU will own
part of the weights, so ALL gpus are active all the time and do less work.
Usually this comes with a very slight overhead that some work is duplicated
and more importantly that the GPUs regularly have to communicate to each other
their results to continue the computation
```

在清楚了解现状之后，到了干活的时候。

基于人手和各自的知识，我们尝试了许多不同的东西。

所有尝试都值得单独写一篇博客，所以我只列出来、讲几句最终的收获，并只详细展开目前服务器上实际采用的方案。从流水线并行（PP）转向张量并行（TP）是对延迟影响巨大的一项有趣改变：每张 GPU 持有一部分参数，所有 GPU 同时工作，所以延迟应大幅下降，代价是通信开销——因为 GPU 之间需要频繁互传结果。

值得指出的是，这是一张非常宽泛的方法光谱，我们的初衷就是深入了解每个工具，以及它们日后如何派上用场。

### 把代码移植到 JAX/Flax 以在 TPU 上运行：

- 预期并行方式的选择更容易，因此 TP 应更容易测试。这是 Jax 设计的好处之一。
- 硬件更受限，TPU 上的性能很可能优于 GPU，但 TPU 的供应商选择更少。
- 缺点：需要再一次移植。不过我们的库里反正也会欢迎它。

结果：

- 移植并非易事，一些条件和 kernel 很难足够正确地复现。但总体尚可控。
- 移植完成后，并行化相当容易搞定。向 Jax 致敬，此言不虚。
- Ray/与 TPU worker 通信对我们来说是真正的痛苦。我们不知道是工具、网络，还是纯粹因为我们经验不足，但它拖慢实验和工作的程度远超预期。我们会启动一个 5 分钟能跑完的实验，等 5 分钟毫无动静，10 分钟后依然没有——原来某个 worker 挂了/没响应，我们得手动登录、查清状况、修复、重启、再重跑，半小时就这么没了。如此重复若干次，损失的天数很快累积起来。要强调这未必是对所用工具的批评，但我们主观体验确实如此。
- 无法控制编译。事情跑起来后，我们尝试了多种设置，以找出最适合我们要做的推理的设置。结果发现很难从设置猜出延迟/吞吐量会发生什么。例如，batch_size=1（每个请求/用户单独处理）时是 0.3 rps，延迟 15ms/token（别和本文其他数字过多对比——那台机器性能画像完全不同），延迟很漂亮，但总体吞吐并不比旧代码好多少。于是我们决定加 batching。BS=2 时延迟涨了 5 倍，吞吐却只翻倍。进一步调查发现，batch_size 直到 16 之前每个 batch_size 的延迟曲线都一样。也就是说我们能用 5 倍延迟换来 16 倍吞吐。不算差，但看看数字，我们真心希望有更精细的控制。我们追求的数字源自 [100ms、1s、10s、1mn](https://www.nngroup.com/articles/response-times-3-important-limits/) 法则。

### 使用 ONNX/TRT 或其他编译型方案

- 它们据说能接手大部分优化工作
- 缺点：并行通常需要手动处理。

结果：

- 事实证明，为了能够 trace/jit/export，我们需要改造部分 PyTorch，这样它就容易与纯 PyTorch 方案融合。总体上我们发现，留在 PyTorch 世界里就能获得我们想要的大部分优化，既保留灵活性，又不必付出太多编码代价。另外值得注意的是，由于我们在 GPU 上运行，而文本生成有大量前向传播，我们需要张量留在 GPU 上。有时很难把你的张量发给某个库、拿回结果、在外部计算 logits（如 argmax 或采样）再喂回去。把循环放进外部库意味着像 Jax 那样失去灵活性，因此不在我们用例的设想之内。

### DeepSpeed

- 这是支撑训练的技术，用它做推理似乎顺理成章
- 缺点：它此前从未被用于/准备用于推理。

结果：

- 我们很快得到令人印象深刻的结果，大致与我们目前在跑的最后一轮迭代相当。
- 我们必须发明一种方式，把 Web 服务器（要处理并发）架在 DeepSpeed 之上——后者本身就有多个进程（每个 GPU 一个）。好在有出色的库 [Mii](https://github.com/microsoft/DeepSpeed-MII)。它不符合我们极其灵活的目标，但我们会大概一开始就在它之上构建（当前方案在后面讨论）。
- 我们在 DeepSpeed 上遇到的最大问题是缺乏稳定性。在 CUDA 11.4 上运行针对 11.6 构建的代码时出现问题；而始终未能真正解决的长期问题是会出现频繁的 kernel 崩溃（Cuda illegal access、维度不匹配等）。我们修复了一堆，但在我们 Web 服务器的压力下始终无法完全稳定。即便如此，我要为帮助过我们的微软同事们喝彩：我们进行了一次非常好的交流，加深了对问题机理的理解，并为后续工作提供了真正的洞见。
- 我认为的一个痛点是：我们团队主要在欧洲，而微软在加州，协作在时间上很棘手，我们可能因此损失了大量时间。这与技术无关，但承认「协作的组织层面同样重要」是有益的。
- 另一点：DeepSpeed 依赖 `transformers` 来注入其优化，而我们几乎持续在更新代码，这让 DeepSpeed 团队很难在我们的 `main` 分支上保持一切可用。很抱歉让事情变难了，我猜这就是「bleeding edge（前沿尖端）」的含义。

### Web 服务器思路

- 既然我们要运行一台免费服务器，用户会发长文本、短文本、要几个 token 或一整份菜谱，各带不同参数——这里必须做点什么。

结果：

- 我们借助出色的绑定 [tch-rs](https://github.com/LaurentMazare/tch-rs) 用 `Rust` 重写了全部。选 Rust 不是为了性能提升，而是为了对并行（线程/进程）有更精细的控制，并在 Web 服务器并发与 PyTorch 并发之间做更精细的调度。Python 出了名难处理底层细节，都怪 [GIL](https://realpython.com/python-gil/)。
- 结果发现痛苦主要来自移植本身，移植之后实验就一帆风顺了。我们发现在对循环有足够控制的前提下，即使在请求属性非常多样的场景里也能为所有人取得出色性能。好奇者可看[代码](https://github.com/Narsil/bloomserver)，但没有任何支持或漂亮文档。
- 它当了几个周的生产方案，因为它对并行更宽松，我们可以更高效地利用 GPU（请求 1 用 GPU0 时，GPU1 正在处理请求 0）。吞吐从 0.3 RPS 升到约 2.5 RPS 而延迟不变。理想情况本可把吞吐提高 16 倍，但这里的数字是真实负载测量，所以已经不错。

### 纯 PyTorch

- 直接修改现有代码使其更快：去掉 `reshape` 之类的操作、使用更优化的 kernel，等等。
- 缺点：我们要自己写 TP，而且有个约束——代码（大体上）仍要契合我们的库。

结果

- 见下一章。

## 最终路线：PyTorch + TP + 1 个自定义 kernel + torch.jit.script

### 编写更高效的 PyTorch

清单上的第一项是去掉最初实现中不必要的操作。只看代码就能发现一些明显的缺陷：

- Bloom 用 Alibi 添加位置嵌入，而它被计算了太多次。我们可以只算一次，并且算得更高效。

旧代码：[link](https://github.com/huggingface/transformers/blob/ca2a55e9dfb245527b5e1c954fec6ffbb7aef07b/src/transformers/models/bloom/modeling_bloom.py#L94-L132) 新代码：[link](https://github.com/huggingface/transformers/blob/main/src/transformers/models/bloom/modeling_bloom.py#L86-L127)

这是 10 倍提速，而且最新版本还处理了 padding！由于这一步只计算一次，实际速度并不重要，但总体减少操作和张量创建是好方向。

其他部分在你开始做 [profiling](https://pytorch.org/tutorials/recipes/recipes/profiler_recipe.html) 后会更清晰地浮现，我们 extensively 使用了 [tensorboard 扩展](https://pytorch.org/tutorials/intermediate/tensorboard_profiler_tutorial.html)

它能提供这类给出洞见的图像：

Attention 耗时很长。当心，这是 CPU 视图，长条不代表时间长，而是 CPU 在等待上一步 GPU 的结果。

在 `baddbmm` 之前看到许多 `cat` 操作。

大量移除 reshape/transpose。例如我们发现：- attention 是热路径（意料之中，但验证总是好的）。- attention 内部很多 kernel 实际上是拷贝，源于大量的 reshape。- 我们**可以**通过重构权重本身和 past 来移除 reshape。这是一个 breaking change，但确实显著提升了性能！

### 支持 TP

好，我们摘掉了大部分低垂的果实，在 PP 下延迟从大约 350ms/token 降到 300ms/token。即延迟降低 15%，实际上不止，但最初我们测量不够严格，就以这个数字为准。

然后我们着手做 TP 实现。结果比我们预期的快得多——单个（有经验的）开发者半天就实现完了。成果在[这里](https://github.com/huggingface/transformers/tree/thomas/dirty_bloom_tp/src/transformers/models/bloom)。我们还能复用其他项目的代码，帮了大忙。

延迟直接从 300ms/token 降到 91ms/token，用户体验巨大改善。一个简单的 20 token 请求从 6 秒降到 2 秒，从「慢」的体验变成略有延迟。

吞吐量也大涨到 10 RPS。吞吐提升的原因是：batch_size=1 跑一个查询与 batch_size=32 耗时相同，此时吞吐量几乎不花延迟成本，基本上是*免费*的。

### 低垂的果实

有了 TP 实现，我们可以重新开始 profiling 和优化。这是足够大的转变，以至于我们得从头来过。

最先跳出来的是：同步（ncclAllReduce）开始成为负载中占比很大的部分。这在意料之中——它就是同步部分，而且**确实**要花时间。我们从没尝试查看和优化它，因为它已经在用 `nccl`，但也许仍有改进空间。我们假设很难做得更好了。

第二件事是 `Gelu` 算子启动了大量逐元素 kernel，总体占据了比预期更大的计算份额。

我们做了如下改动，从：

```
def bloom_gelu_forward(x):
    return x * 0.5 * (1.0 + torch.tanh(0.79788456 * x * (1 + 0.044715 * x * x)))
```

改为

```
@torch.jit.script
def bloom_gelu_forward(x):
    return x * 0.5 * (1.0 + torch.tanh(0.79788456 * x * (1 + 0.044715 * x * x)))
```

这把多个小型逐元素 kernel（及随之而来的张量拷贝）合并为单一 kernel 操作！

就在这里，延迟从 91ms/token 到 81ms/token，直接提升 10%！

但请当心，这不是可以到处乱扔的魔法黑盒：kernel 融合不一定会发生，或者所用操作本身已经极其高效。

我们发现有效的场景：

- 你有大量小型/逐元素操作
- 你有个热点，其中有几个难以移除的 reshape、拷贝
- 融合确实发生时。

### 史诗级翻车

我们也有过难堪的时刻：测试期间，我们一直看到 Rust 服务器的延迟稳定比 Python 低 25%。这相当诡异，但因为测量结果一致，而且移除 kernel 确实有加速，我们 impression 是也许甩掉 Python 开销能带来可观提升。

我们启动了一个 3 天的活儿，重新实现 `torch.distributed` 的必要部分以在 Rust 世界跑起来（[nccl-rs](https://github.com/Narsil/nccl-rs)）。版本能跑了，但生成结果与其 Python 对应版本相比有些不对。排查问题的过程中我们发现……**原来我们在 PyTorch 的测量里忘了移除 profiler**……

这就是史诗级翻车：去掉 profiler 后 25% 回来了，两套代码速度完全一致。这才是我们最初的预期——Python 不应该是性能拖累，因为它主要在执行 torch cpp 的代码。3 天不算世界末日，将来也许还有用，但还是很糗。做优化时进行错误或具误导性的测量，结果令人失望甚至有害于整体产品，这是很常见的。正因如此，小步迭代、尽早对结果建立预期，有助于控制这类风险。

另一个必须格外小心的地方，是最初的前向传播（无 past）与后续的前向传播（有 past）。如果你优化前者，几乎肯定会拖慢更重要的后者——后者占据大部分运行时间。另一个常见元凶是测量的是 CPU 时间而非真正的 CUDA 时间，所以你需要在运行时调用 `torch.cuda.synchronize()` 以确保 kernel 已完成。

### 自定义 kernel

到这里，我们在没有任何 PyTorch 之外自定义代码的情况下，逼近了 DeepSpeed 的性能！相当漂亮。而且我们不必为运行时 batch 大小的灵活性做任何妥协！

但鉴于 DeepSpeed 的经验，我们想试试写一个自定义 kernel，把热路径上 `torch.jit.script` 无法为我们融合的几个操作融合起来。 essentially 就是下面两行：

```
attn_weights = attention_scores.masked_fill_(attention_mask, torch.finfo(attention_scores.dtype).min)
attention_probs = F.softmax(attn_weights, dim=-1, dtype=torch.float32).to(input_dtype)
```

第一个 masked fill 创建了一个新张量，它存在的意义只是告诉 softmax 算子忽略那些值。另外，softmax 需要在 float32 上计算（为了稳定性），但在自定义 kernel 内，我们可以把必要的向上转换（upcast）限制在实际的求和与累积处。

代码在[这里](https://github.com/huggingface/transformers/blob/thomas/add_custom_kernels/src/transformers/models/bloom/custom_kernels/fused_bloom_attention_cuda.cu)。请记住：我们只需针对单一 GPU 架构，所以能专注于此；而且我们（还）不是写 kernel 的专家，所以可能有更好的做法。

这个自定义 kernel 又带来 10% 的延迟改善，从 81ms/token 降到 71ms/token，同时保持我们的灵活性。

之后，我们还研究和探索了其他方案：融合更多算子、移除其他 reshape、或把它们挪到别处。但没有任何尝试产生足够大的影响进入最终版本。

### Web 服务器部分

与 Rust 版本一样，我们必须实现对不同参数请求的 batching。既然在 `PyTorch` 世界里，我们对发生的一切有近乎完全的控制。因为在 Python 中，限制因素是 `torch.distributed` 必须运行在多个进程而非线程上，这意味着进程间通信稍难一些。最终，我们选择通过 Redis pub/sub 传输原始字符串，把请求一次性分发给所有进程。由于在不同进程里，这样做比传输张量（大得多）更容易。

然后我们不得不弃用 [generate](https://huggingface.co/docs/transformers/v4.22.2/en/main_classes/text_generation#transformers.generation_utils.GenerationMixin.generate)，因为它把参数应用到 batch 的所有成员，而我们实际想应用不同的参数组。好在我们可以复用更底层的组件，例如 [LogitsProcessor](https://huggingface.co/docs/transformers/internal/generation_utils#transformers.LogitsProcessor)，省下大量工作。

于是我们重建了一个接收参数列表的 `generate` 函数，把各参数应用到 batch 的每个成员。

最终 UX 的另一个至关重要的方面是延迟。既然不同请求有不同参数组，可能出现：

一个请求要 20 个 token，另一个要 250 个。按 75ms/token 的延迟算，一个请求要 1.5s，另一个要 18s。如果一路全部 batch 在一起，那个只要 20 token 的用户也得等 18s，在他眼里我们就像在以 900ms/token 的速度运行——相当慢！

由于我们身处拥有极致灵活性的 PyTorch 世界，我们可以改为：一旦生成了前 20 个 token，就把第一个请求从 batch 中抽出，在要求的 1.5s 内返回给那位用户！我们还顺带节省了 230 个 token 的计算量。

所以，灵活性**确实**是取得最佳延迟表现的关键。

## 最后的笔记与疯狂点子

优化是没有尽头的工作，和任何项目一样，20% 的投入通常产出 80% 的成果。后期我们形成了一套小测试策略：先评估某个想法的潜在收益，如果测试没有显著收益就放弃它。1 天换 10% 提升值得做，2 周换 10 倍值得做，但 2 周换 10% 就不太划算。

### 你们试过……吗？

我们知道存在但没有采用的东西，各有原因：可能觉得不适配我们的用例、工作量太大、收益不够有前景，或者单纯是选项太多、没时间而略过了某些，没有特别理由。以下排名不分先后：

- [Cuda graphs](https://developer.nvidia.com/blog/cuda-graphs/)
- [nvFuser](https://pytorch.org/tutorials/intermediate/nvfuser_intro_tutorial.html)（这就是 `torch.jit.script` 背后的引擎，所以我们确实用了它。）
- [FasterTransformer](https://github.com/NVIDIA/FasterTransformer)
- [Nvidia's Triton](https://developer.nvidia.com/nvidia-triton-inference-server)
- [XLA](https://www.tensorflow.org/xla)（Jax 也在用 xla！）
- [torch.fx](https://pytorch.org/docs/stable/fx.html)
- [TensorRT](https://developer.nvidia.com/blog/accelerating-inference-up-to-6x-faster-in-pytorch-with-torch-tensorrt/)

如果你钟爱的工具不在其中，或者你觉得我们遗漏了某个重要的、可能有用的东西，欢迎随时联系我们！

### Flash attention

我们简要研究过集成 flash attention：虽然它在第一次前向传播（无 `past_key_values`）上表现出色，但在使用 `past_key_values` 运行时并没有带来同样大的改进。由于需要改造它以把 `alibi` 张量纳入计算，我们决定暂不做这个工作（至少现在不做）。

### OpenAI Triton

[Triton](https://github.com/openai/triton) 是一个用 Python 构建自定义 kernel 的优秀框架。我们想更多地使用它，但目前还没有。我们很期待看看它是否比我们的 Cuda kernel 更快。当时权衡下来，直接写 Cuda 似乎是我们目标的最短路径。

### Padding 与 Reshape

正如全文所说，每次张量拷贝都有代价，而生产环境的另一项隐性成本是 padding。当两个查询长度差异很大时，必须用 padding（占位 token）把它们凑成矩形，这会导致大量不必要的计算。[更多信息](https://huggingface.co/docs/transformers/v4.22.2/en/main_classes/pipelines#pipeline-batching)。

理想情况下，我们希望能完全*不做*这些计算，也永远不需要 reshape。Tensorflow 有 [RaggedTensor](https://www.tensorflow.org/guide/ragged_tensor) 的概念，PyTorch 有 [Nested tensors](https://pytorch.org/docs/stable/nested.html)。两者看起来都不如常规张量那样顺畅，但也许能减少计算——少算永远是赢。

在理想世界里，整个推理都用 CUDA 或纯 GPU 实现来写。考虑到我们融合操作时取得的性能提升，这令人向往。但它究竟能做到什么程度，我们心里没数。如果更懂 GPU 的人有想法，我们洗耳恭听！
