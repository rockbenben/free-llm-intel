# 借助 NVIDIA NeMo AutoModel 加速 Transformers 微调

Hugging Face Transformers 已成为开源 AI 生态的基石，而最近的 [Transformers v5](https://github.com/huggingface/transformers/releases/tag/v5.0.0) 发布为它补上了一等公民级的 Mixture-of-Experts（MoE，混合专家）模型支持——MoE 如今是[前沿模型](https://www.nvidia.com/en-us/glossary/frontier-models/)的主流架构。v5 带来了 MoE 的地基：专家后端（expert backends）、动态权重加载、分布式执行，让 MoE 可扩展、易在其上构建。

[NVIDIA NeMo AutoModel](https://github.com/NVIDIA-NeMo/Automodel) 是 [NVIDIA NeMo 框架](https://github.com/NVIDIA-NeMo)下的一个开源库，用于大规模构建自定义生成式 AI 模型。NeMo AutoModel 干净地构建在 v5 之上，加入专家并行（Expert Parallelism）、DeepEP 融合 all-to-all 调度以及 TransformerEngine kernels，并借助 v5 的动态权重加载把这些优化带给广泛且不断增长的模型家族。收益是：在微调 MoE 模型时，相比原生 Transformers v5，**训练吞吐高 3.4-3.7 倍**、**GPU 显存省 29-32%**，而用的还是同一个 from_pretrained() API——只改一行 import，其他代码完全不动。

本博客详细说明这套组合如何工作，以及用户如何在不改 API 的情况下更快微调 MoE 模型。

# 背景

MoE 模型的兴起给高效训练带来了新挑战：把 token 路由到数百个专家、把专家矩阵乘融合进单个 kernel、把权重分片到多块 GPU、让通信与计算重叠——这些都需要通用库开箱能力之外的基础设施。

[Transformers v5](https://github.com/huggingface/transformers/releases/tag/v5.0.0)（"v5"）引入了一等公民的 MoE 支持，例如[专家后端](https://huggingface.co/docs/transformers/en/experts_interface)、[动态权重加载](https://huggingface.co/docs/transformers/en/weightconverter)，以及用于分布式执行的张量并行方案。此外，v5 把 PyTorch 的 DeviceMesh 直接集成进 from_pretrained()，使分布式训练成为一等公民。

[NeMo AutoModel](https://github.com/NVIDIA-NeMo/Automodel) 在 v5 之上通过子类化 AutoModelForCausalLM 构建，加入专家并行（EP）、DeepEP 融合 all-to-all 调度和 TransformerEngine kernels。DeepEP 正是 v5 还没有的一块：它让通信与专家计算重叠。而且因为 NeMo AutoModel 复用 v5 可逆的权重转换来加载每个模型，它可以把工程精力集中在这些可复用的核心算子上，而不是逐个模型做 checkpoint 管道对接；同时 save_pretrained() 仍产出标准 HF checkpoint，vLLM、SGLang 等工具都能加载。

下一节梳理两者如何协同，以及我们测得的性能提升——从跨 16 个节点全参数微调 [NVIDIA Nemotron 3 Ultra 550B A55B](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Ultra-550B-A55B-BF16)，到单节点的 Qwen3-30B-A3B、[Nemotron 3 Nano 30B A3B](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16)。

## NeMo AutoModel：同样的 API，更强的性能

NeMo AutoModel 的目标之一是与 HuggingFace Transformers 的 API 兼容，以拥抱开源社区。NeMoAutoModelForCausalLM 子类化自 AutoModelForCausalLM，因此任何适用于 HF 模型的代码同样适用于 AutoModel。

下面是两种加载模型的对照。改变的只有 import：

[![nemo_and_hf](https://cdn-uploads.huggingface.co/production/uploads/690d0a6c2c5acfe0e1f4777d/VTPq2Wp-RrEcP1eGUJxao.png)](https://cdn-uploads.huggingface.co/production/uploads/690d0a6c2c5acfe0e1f4777d/VTPq2Wp-RrEcP1eGUJxao.png)

这一行 import 干了非常多的活。对 Qwen3、[NVIDIA Nemotron](https://developer.nvidia.com/nemotron)、GPT-OSS、DeepSeek V3 等主流 MoE 架构，NeMo AutoModel 内置了[手工调优的实现](https://github.com/NVIDIA-NeMo/Automodel/blob/main/nemo_automodel/_transformers/registry.py)：TransformerEngine 注意力、融合线性层和定制专家 kernel。对其余模型，它回落到原生 HF，但仍会应用 [Liger kernel](https://github.com/linkedin/Liger-Kernel) 打补丁等优化。而无论走哪条路，得到的模型都随时可以扩展：传入一个 device_mesh，无需再改任何代码就能多 GPU 训练。

NeMo AutoModel 真正发光的场景，是把 MoE 模型扩展到多 GPU 训练。想在 8 块 GPU 上用专家并行训练 [Nemotron 3 Nano 30B A3B](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16)，只需加上分布式 mesh 配置：

```
import os
import torch
import torch.distributed as dist
from nemo_automodel import NeMoAutoModelForCausalLM
from nemo_automodel.recipes._dist_utils import create_distributed_setup_from_config

dist.init_process_group(backend="nccl")
torch.manual_seed(0)
torch.cuda.set_device(int(os.environ.get("LOCAL_RANK", 0)))

dist_setup = create_distributed_setup_from_config(
    {
        "strategy": "fsdp2",
        "ep_size": 8,
    },
)

model = NeMoAutoModelForCausalLM.from_pretrained(
    "nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16",
    dtype=torch.bfloat16,
    distributed_setup=dist_setup,
)

dist.destroy_process_group()
```

一次 from_pretrained() 调用，就同时拿到了 FSDP2 带来的速度、可扩展性与内存优化，以及专家并行、TransformerEngine kernels 和 DeepEP 调度。

## 性能对比

我们在两种场景下评估 NeMo AutoModel：跨 16 个节点全参数微调一个前沿规模的 550B 模型，以及在单节点训练两个 30B MoE 模型。550B 的结果说明为什么规模一大专家并行就不可或缺；30B 的结果量化了相对 Transformers v5 的单 GPU 加速。

### Nemotron 3 Ultra 550B A55B（全参数微调，多节点）

[Nemotron 3 Ultra 550B A55B](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Ultra-550B-A55B-BF16) 是一个 550B 参数的混合模型，带 Mamba2、LatentMoE 和 Multi-Token Prediction（MTP，多 token 预测）。我们基准测试的是**全参数微调**：每个参数都更新，Adam 优化器状态完整落地——在这个规模下要横跨 **16 个 H100 节点（128 块 GPU）**。

**实验设置：**

| 参数 | 值 |
| --- | --- |
| 硬件 | 16x H100 80GB（128 GPUs） |
| 专家并行 | EP=64 |
| 局部 batch size | 2 |
| 序列长度 | 4,096 |
| 特性 | MTP、activation checkpointing、融合 linear cross-entropy |
| Kernels | DeepEP 调度 + torch_mm 专家 + TransformerEngine |

| 指标 | NeMo AutoModel (EP=64) |
| --- | --- |
| TPS/GPU（均值） | 815 |
| TFLOP/s/GPU | ~293 |
| 峰值内存 | 58.2 GiB |

**为什么没有 Transformers v5 一列。** Transformers v5 在这个规模下直接 OOM，所以没有 v5 数字可报。AutoModel 的专家并行把专家分片到各 GPU，使占用回到预算之内，全参数微调因此得以运行。下面的 30B 对比展示的是 v5 装得下时同样的优势。

### 单节点 30B MoE 基准

我们在单节点 8x H100 80GB 上对比三种方案：HF Transformers v4（hub 代码）、HF Transformers v5（用上可用的最佳优化）、NeMo AutoModel（EP=8 + 定制 kernels）。

**实验设置：**

| 参数 | 值 |
| --- | --- |
| 硬件 | 8x H100 80GB（单节点） |
| 序列长度 | 4,096 |
| 局部 batch size | 1 |

**关于路由 gate 的说明。** 下面 NeMo AutoModel 的数字使用了平衡路由 gate，强制 token 均匀分布到各专家。这是在模拟 MoE 被训练趋向的*理想*工作点：训练良好的模型其负载均衡损失会把专家利用率推向接近均匀，所以平衡路由反映真实负载收敛到的稳态（也消除了随机 dummy token 否则注入专家并行的掉队者噪声）。v4/v5 则用其原生 router 跑同样的 dummy tokens。因此平衡 gate 衡量的是 NeMo AutoModel 在其目标 MoE 工作点上的表现，而 v4/v5 列体现的是开箱行为。

[![nemo_automodel_blog_chart_mockup_v5](https://cdn-uploads.huggingface.co/production/uploads/690d0a6c2c5acfe0e1f4777d/rbCVgV6a18c4UcDsiWfZN.png)](https://cdn-uploads.huggingface.co/production/uploads/690d0a6c2c5acfe0e1f4777d/rbCVgV6a18c4UcDsiWfZN.png)

### Qwen3-30B-A3B

| 指标 | v4 | v5 (FA2 + grouped_mm) | NeMo AutoModel (EP=8) | v5 → NeMo AutoModel |
| --- | --- | --- | --- | --- |
| TPS/GPU（均值） | 死锁 | 3,075 | 11,340 | **3.69x** |
| 峰值内存 | — | 68.2 GiB | 48.1 GiB | **-29%** |
| 平均前向+损失 | — | 582 ms | 194 ms | 3.00x |
| 平均反向 | — | 758 ms | 178 ms | 4.26x |

**v4 为什么死锁：** Transformers v4 把 Qwen3 的 MoE 专家存成一个 ModuleList，内含 128 个独立 MLP 模块，每个分别被 FSDP 包裹。前向使用数据依赖的循环，只遍历收到 token 的专家。各 rank 数据不同，跳过的专家就不同，导致 FSDP 的 AllGather/ReduceScatter 集合通信不匹配，永久挂起。Transformers v5 通过把专家存为融合的 3D 参数张量（无逐专家模块、无逐专家 FSDP 集合通信）修复了这一点。

### Nemotron 3 Nano 30B A3B

| 指标 | v4（hub 代码） | v5 (FA2 + grouped_mm + Mamba CUDA) | NeMo AutoModel (EP=8) | v5 → NeMo AutoModel |
| --- | --- | --- | --- | --- |
| TPS/GPU（均值） | 1,807 | 4,583 | 15,421 | **3.36x** |
| 峰值内存 | 61.9 GiB | 62.1 GiB | 42.5 GiB | **-32%** |
| 平均前向+损失 | 1,024 ms | 283 ms | 109 ms | 2.60x |
| 平均反向 | 1,246 ms | 611 ms | 157 ms | 3.89x |

**v4 配置：** trust_remote_code=True（NVIDIA 的 hub 建模代码）。hub 代码的专家循环对 FSDP 安全（无论 token 如何分配都遍历全部专家），所以不会像 Qwen3 v4 那样死锁。

### 加速来自哪里

NeMo AutoModel 相对 Transformers v5 的 3.4-3.7 倍加速来自三个方面：

- **专家并行降低内存压力。** EP=8 把专家权重分布到各 GPU，单 GPU 的 MoE 占用降为 1/8。对 Qwen3，峰值内存从 68.2 GiB 降到 48.1 GiB（-29%）；对 Nemotron Nano，从 62.1 GiB 降到 42.5 GiB（-32%），腾出空间可以用更大 batch 或更长序列。
- **DeepEP 把通信与计算融合。** 专家路由不再用独立的 AllGather/ReduceScatter 集合通信，DeepEP 把 token 的分发与合并融合进优化的 GPU kernel，让通信与专家计算重叠。
- **TransformerEngine kernels 加速核心运算。** TE 的融合注意力、线性层和 RMSNorm 实现在所有层类型（不只 MoE 层）上相对 PyTorch/Flash Attention 等价实现都有一致的加速。

## NeMo AutoModel 用到的 Transformers v5 特性

### 专家后端

Transformers v5 最有影响力的特性之一是 [experts_implementation](https://huggingface.co/docs/transformers/en/experts_interface) 参数，包含三种专家后端：

| 后端 | 说明 | 适用 |
| --- | --- | --- |
| eager | 对被选中的专家做 for 循环 | 调试、兼容性、正确性。v4 也可用。 |
| batched_mm | 复制专家参数，用 torch.bmm 做单次批量 GEMM | 小输入，配合 torch.compile 很快。v5 新增 |
| grouped_mm | 按专家给 token 排序，用 torch.nn.functional.grouped_mm 做单次分组 GEMM | 训练（内存高效，无需复制参数）。v5 新增。 |

grouped_mm 后端是训练优化的关键：不再逐个循环专家，而是按所分配的专家给 token 排序，执行一次融合的分组矩阵乘法。

NeMo AutoModel 把它推得更远。对有自定义实现的模型，它使用 DeepEP 融合 all-to-all 调度，配合分组 GEMM kernel 和 TransformerEngine 线性层。演进路线是：

```
v4 (eager for-loop) → v5 (grouped_mm) → NeMo AutoModel (DeepEP + GMM + TE)
```

在 NeMo AutoModel 中，专家后端通过 BackendConfig 配置：

```
from nemo_automodel.components.models.common.utils import BackendConfig

backend = BackendConfig(
    attn="te",           # TransformerEngine attention
    linear="te",         # TransformerEngine linear layers
    experts="torch_mm",  # Grouped expert matmul
    dispatcher="deepep", # DeepEP fused all-to-all
)
```

## 专家并行与 DeepEP

Transformers v5 也自带一条[专家并行路径](https://huggingface.co/docs/transformers/en/expert_parallelism)，把专家权重分片到各 GPU。[GroupedGemmParallel](https://github.com/huggingface/transformers/blob/v5.10.2/src/transformers/integrations/tensor_parallel.py#L1078) 样式只加载每台设备的本地专家，[RouterParallel](https://github.com/huggingface/transformers/blob/v5.10.2/src/transformers/integrations/tensor_parallel.py#L1123) 负责路由 token 并用 all_reduce 合并结果。它巧妙地建立在 v5 现有的张量并行机制上。启用后，模型的 tp_plan 会返回其[专家方案](https://github.com/huggingface/transformers/blob/v5.10.2/src/transformers/modeling_utils.py#L1448)，于是专家并行与数据并行共享设备预算（ep × dp = world_size）。在本文的单节点 30B 基准中，我们发现纯数据并行的 v5（dp=8、ep=1）是最快的 v5 配置，所以报告的 v5 就是这套设置。

NeMo AutoModel 采取的是针对多 GPU MoE 训练调优的互补路线。它把 EP 做成独立的并行维度——一条专用的 moe_mesh，与数据并行 mesh 并列（而不是从后者中切出来），使用 PyTorch 的 DTensor 配合 Shard(0)。因为专家 mesh 与数据并行正交，两者可以在同一批设备上组合：在 8 块 GPU 上，NeMo AutoModel 同时跑 ep=8 和 dp=8，每块 GPU 在自己的数据分片上训练，却只持有 1/8 的专家。专家权重沿专家维度在物理上分片到各 GPU。

```
# From nemo_automodel/components/moe/parallelizer.py
from torch.distributed.tensor import Shard, distribute_tensor

# Each GPU holds only 1/ep_size of the expert weights
distribute_tensor(param, device_mesh, [Shard(0)])
```

在 8 块 GPU 上设 ep_size=8，每块 GPU 只持有 1/8 的专家参数。对 Nemotron-3-Nano-30B-A3B 这种专家权重约 55 GiB 的模型，EP 把单 GPU 专家占用从约 55 GiB 压到约 6.8 GiB，让纯 FSDP 方案会 OOM 的场景变得可训。

在 EP 之上，NeMo AutoModel 集成了 [DeepEP](https://github.com/deepseek-ai/DeepEP)，把 token 路由融合进优化的 GPU kernel；与分组 GEMM 的分组专家计算结合时带来显著加速。在我们的[大规模 MoE 基准](https://github.com/NVIDIA-NeMo/Automodel/discussions/916)中，DeepEP + 分组 GEMM 相比 all-gather + 循环专家的基线，在完整 DeepSeek V3 671B 模型上把每次迭代成本降低了 47%。

### 动态权重加载

Transformers v5 还通过 WeightConverter 和 WeightRenaming 引入了[动态权重加载](https://huggingface.co/docs/transformers/en/weightconverter)系统，使 MoE checkpoint 能以融合的 3D 张量存储，运行更高效。WeightConverter 在 from_pretrained() 过程中对 checkpoint 张量就地施加可组合的变换操作。

NeMo AutoModel 是这一 v5 API 的直接使用方。超过 [20 种模型类型](https://github.com/NVIDIA-NeMo/Automodel/blob/main/nemo_automodel/components/checkpoint/conversion_mapping.py)通过 MODELS_REQUIRING_TENSOR_MERGING 使用该机制，包括 Mixtral、Qwen2 MoE、Qwen3 MoE、DeepSeek V2/V3、OLMoE 等。转换完全可逆：save_pretrained() 产出标准 HF 格式 checkpoint，任何下游工具都能加载。

## 结论

NVIDIA NeMo AutoModel 是 HuggingFace 用户扩大训练规模时自然的下一步。直接构建在 Transformers v5 之上，AutoModel 提供了一条零摩擦升级路径：改一行 import，模型实例快三倍以上。

在 Qwen3-30B-A3B 和 Nemotron 3 Nano 30B A3B 上，相比最佳 Transformers v5 配置，它带来 3.4-3.7 倍训练吞吐和 29-32% 的显存节省。而因为真正的专家并行把专家分片到各 GPU，同一条路径可以一路扩展到跨 16 个节点全参数微调 Nemotron 3 Ultra 这样的 550B 模型——在那个规模，专家并行成为把模型装进内存的必需。由于 NeMo AutoModel 的 checkpoint 是标准 HF 格式 safetensors，你可以把它们部署到 vLLM、SGLang 等推理框架上。
