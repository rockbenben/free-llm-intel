# 通用辅助生成：用任意助手模型加速解码

本文另有[简体中文](https://huggingface.co/blog/zh/universal_assisted_generation)版本。

*TL;DR*：许多 LLM（如 `gemma-2-9b` 和 `Mixtral-8x22B-Instruct-v0.1`）缺少可供 [assisted generation](https://huggingface.co/blog/assisted-generation) 使用的更小型版本。在这篇博客中，我们介绍 *Universal Assisted Generation*（通用辅助生成，UAG）——由 Intel Labs 与 Hugging Face 开发的方法，把 assisted generation 扩展到可与**任意模型家族**的小语言模型配合使用 🤯。由此，现在可以用几乎零开销的方式让*任何* decoder 或 [Mixture of Experts](https://huggingface.co/blog/moe) 模型的推理提速 **1.5x-2.0x** 🔥🔥🔥。开始深入吧！

## 引言

如今，最强的开放权重 LLM 通常有数十亿到数千亿参数（你好 Llama-3.1-405B 👋），把这些"巨兽"部署到生产环境带来一系列工程挑战。其中之一是这些大模型生成文本很*慢*，这促使社区发展了大量加速解码过程的技术。Assisted generation（也称 [speculative decoding](https://arxiv.org/abs/2211.17192)）是一个非常流行且实用的、在不损失精度的前提下加速 LLM 推理的方法。在这篇博客中，我们回顾 assisted generation 的原理，并分享我们把这一方法扩展到 Hugging Face Hub 上 [14 万个语言模型](https://huggingface.co/models?pipeline_tag=text-generation&sort=trending)中*任意*模型的研究 🚀！

## Assisted Generation

Assisted generation 的核心思想是使用一对模型，称为 *target*（目标）模型和 *assistant*（助手）模型。助手模型是目标模型更小、更高效的版本，例如用 [`Llama-3.2-1B`](https://huggingface.co/meta-llama/Llama-3.2-1B) 作为更大 [`Llama-3.1-70b`](https://huggingface.co/meta-llama/Llama-3.1-70b) 目标模型的助手。Assisted generation 是一个迭代过程：每一轮，助手模型以自回归方式逐个生成一串 token；随后目标模型用一次前向传播验证序列中所有助手 token。提速来自目标模型每次前向传播确认多个 token，而不是一次只产出一个。更详细的解释见原始[博客](https://huggingface.co/blog/assisted-generation)。结合最近引入的 [Dynamic Speculation](https://huggingface.co/blog/dynamic_speculation_lookahead) 策略，assisted generation 依任务和模型不同可将文本生成加速 1.5x-3x。

Assisted generation 的显著提速伴随着一个重大缺点：目标模型与助手模型必须共享同一个 tokenizer，也就是说它们需要来自同一模型家族。然而，许多广泛使用的模型缺少既足够小又足够准、能带来可观延迟下降的小版本。根据我们的经验，只有当助手模型比目标模型小至少 50-100 倍时，提速才有意义。例如 [`CodeLlama-13b`](https://huggingface.co/meta-llama/CodeLlama-13b-Instruct-hf) 没有更小的版本，而 [`gemma-2-9b`](https://huggingface.co/google/gemma-2-9b) 只有 `2b` 变体，仍不够小/快，无法取得显著性能提升。

## Universal Assisted Generation

为缓解这一痛点，Intel Labs 与 Hugging Face 的朋友共同开发了 Universal Assisted Generation（UAG）。UAG 允许选择任意目标/助手模型组合，无论其 tokenizer 是否一致。例如，可以用 `gemma-2-9b` 作为目标模型，用微小的 [`vicuna-68m`](https://huggingface.co/double7/vicuna-68m) 作为助手。

我们提出方法的核心思想是双向 tokenizer 翻译。助手模型完成一轮生成后，助手 token 被转换回文本，再用目标模型的 tokenizer 重新 tokenize 生成目标 token。验证步骤之后，目标 token 同样被转回助手 token 格式，追加到助手模型的上下文中，然后开始下一轮迭代。

由于助手与目标 tokenizer 使用不同词表，必须处理二者间的差异。为了准确重编码新生成的助手 token，需要前置一个由若干历史 token 组成的上下文窗口。随后把整个序列重编码成目标 token 格式，与最近的目标 token 对齐，从而精确定位新生成 token 应追加的位置。这一过程在下方的视频中演示。

虽然视频里没有展示，从目标到助手的 token 重编码也遵循类似过程。不过，必须把不匹配的 token 从助手模型的 key-value（KV）缓存中丢弃，以确保数据一致性。

## 基准测试

下表展示了目标模型与使用不同 tokenizer 的助手模型配对时观察到的延迟改善。

| Target model | Assistant model | Dataset | Task | Speedup |
| --- | --- | --- | --- | --- |
| `codellama/CodeLlama-13b-Instruct-hf` | `bigcode/tiny_starcoder_py` | [`openai/humaneval`](https://huggingface.co/openai/humaneval) | code generation | **1.90x** |
| [`mistralai/Mixtral-8x22B-Instruct-v0.1`](https://huggingface.co/blog/mistralai/Mixtral-8x22B-Instruct-v0.1) | `double7/vicuna-68m` | [`cnn_dailymail`](https://huggingface.co/cnn_dailymail) | summarization | **1.52x** |
| `google/gemma-2-9b` | `double7/vicuna-68m` | [`cnn_dailymail`](https://huggingface.co/cnn_dailymail) | summarization | **1.76x** |
| `mistralai/Mixtral-8x22B-Instruct-v0.1` | `Qwen/Qwen2-0.5B-Instruct` | [`tau/scrolls`](https://huggingface.co/tau/scrolls) | long-context summarization | **1.78x** |
| `meta-llama/Llama-3.1-70B` | `Qwen/Qwen2-0.5B-Instruct` | [`tau/scrolls`](https://huggingface.co/tau/scrolls) | long-context summarization | **1.78x** |
| `microsoft/Phi-3-medium-128k-instruct` | `Qwen/Qwen2-0.5B-Instruct` | [`tau/scrolls`](https://huggingface.co/tau/scrolls) | long-context summarization | **1.91x** |

注意，上述目标模型都没有适合用标准 assisted generation 加速的（10 亿参数以下）小变体。

每个实验在随机抽取的 100 个样本上进行。以 `Llama` 和 `Mixtral` 为目标模型的实验分别使用 2 块和 4 块 A100 GPU；其余实验均在单块 A6000 GPU 上进行。

## 代码

Universal assisted generation 已集成进 🤗 Transformers 的 [4.46.0](https://github.com/huggingface/transformers/releases/tag/v4.46.0) 版本。

使用时，把 `tokenizer` 和 `assistant_tokenizer` 传给 `generate()`：

```
>>> from transformers import AutoModelForCausalLM, AutoTokenizer

>>> prompt = "Alice and Bob"
>>> checkpoint = "google/gemma-2-9b"
>>> assistant_checkpoint = "double7/vicuna-68m"

>>> assistant_tokenizer = AutoTokenizer.from_pretrained(assistant_checkpoint)
>>> tokenizer = AutoTokenizer.from_pretrained(checkpoint)
>>> inputs = tokenizer(prompt, return_tensors="pt")

>>> model = AutoModelForCausalLM.from_pretrained(checkpoint)
>>> assistant_model = AutoModelForCausalLM.from_pretrained(assistant_checkpoint)
>>> outputs = model.generate(**inputs, assistant_model=assistant_model, tokenizer=tokenizer, assistant_tokenizer=assistant_tokenizer)
>>> tokenizer.batch_decode(outputs, skip_special_tokens=True)
['Alice and Bob are sitting in a bar. Alice is drinking a beer and Bob is drinking a']
```

## 未来方向

虽然标准 assisted generation 在传入 `do_sample=True` 时使用 speculative sampling 算法（[论文中的 Algorithm 1](https://arxiv.org/pdf/2211.17192.pdf)），UAG 目前只支持多项式采样（multinomial sampling）。在多项式采样下，如果目标模型采样出的 token 与助手不同，该 token 会被自动拒绝——speculative sampling 则不然。实际上，这意味着 `do_sample=True` 时 UAG 的吞吐低于助手与目标共享 tokenizer 的情况。未来我们计划为 UAG 增加 speculative sampling 支持。此外，我们打算把 UAG 集成进 🤗 Transformers pipelines，以获得更简洁流畅的用法。
