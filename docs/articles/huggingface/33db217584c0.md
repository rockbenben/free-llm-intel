## 1. 引言

我对让 LLM 解决什么大问题不感兴趣，恰恰相反。我希望它们处理杂活，如果一次没做对，我用一句简单的英语提示就能让它改对。简而言之，我想要一个助手，就像老科幻片里的[电脑](https://en.wikipedia.org/wiki/HAL_9000)那样——当然要去掉"[对不起 Dave，我不能那样做](https://youtu.be/ARJ8cAGm6JE?si=LnI39hH7EhiXunw6)"那段 😅。

[这篇论文](https://arxiv.org/abs/2411.03562)探索了面向编码的此类工具。先抛开吸引眼球的标题结论（不，[AI 还没打败 Kaggle 大师](https://x.com/martin_gorner/status/1857042235524632894)），论文作者做的事情是：手动把各种 Kaggle 问题拆成微任务，让 LLM 为它们生成代码，然后不断迭代直到单元测试通过。一个微任务的例子：对图像分类问题，让模型"搞清楚输入数据的格式，并把它重排成含 'id'、'image_filename' 和 'class' 列的 CSV"。

我喜欢这个思路，因为这正是我未来希望与 AI 协作做项目的方式：让 AI 生成数据重排之类的无聊代码，我专注于有趣的部分——正确定义问题、设计通向方案的步骤。

但这个交互式编码助手必须能听懂 plain English 的反馈，并修正代码里的错误。凭借 LLM 从知识和上下文推断信息的能力，这可以成为非常高效的计算机界面。但如果 LLM 的毛病——幻觉、缺乏形式逻辑——碍了事，我们得到的可能不是人工智能，而是"人工智障"。

于是我决定用当今的 LLM 跑一个小测试。一个极度简化的测试，看看当你把错误指出来时，LLM 修正错误的效率有多高。

## 2. 实验设计

场景如下：

系统提示词：

> You are a helpful vocal assistant on a mobile device. Your job is to translate user requests into API calls using this Python API:
> action.add_calendar_entry(title, date="YYYY-MM-DD", time="HH:MM", duration=m) # duration in minutes
> action.remove_calendar_entry(title, date, time)
> 
> You can use 30 minutes as the default duration for new events. Respond to every request with a single line of executable code.

| 对话提示词 | 预期输出 |
| --- | --- |
| **Add a meeting with Fred on Nov 11 at 5PM**（添加 11 月 11 日 5 点与 Fred 的会议） | `action.add_calendar_entry("Meeting with Fred", date="2023-11-11", time="17:00", duration=30)` |
| **The current year is 2024.**（今年是 2024 年。） | `action.add_calendar_entry("Meeting with Fred", date="2024-11-11", time="17:00", duration=30)` |
| **I'm going to a rock concert in the evening of the same day at 8pm. Add a calendar entry for that.**（当天晚上 8 点我要去看摇滚演唱会，给这个也加条日程。） | `action.add_calendar_entry("Rock Concert", date="2024-11-11", time="20:00", duration=30)` |
| **Set the duration to 3 hours.**（时长设为 3 小时。） | `action.add_calendar_entry("Rock Concert", date="2024-11-11", time="20:00", duration=60*3)` |
| **Add a meeting with Paul on the next day at 8am. 1/2h.**（第二天早上 8 点添加与 Paul 的会议，半小时。） | `action.add_calendar_entry("Meeting with Paul", date="2024-11-12", time="08:00", duration=30)` |
| **Cancel the meeting with Fred.**（取消与 Fred 的会议。） | `action.remove_calendar_entry("Meeting with Fred", "2024-11-11", "17:00")` |

就这么简单。确实很简单，但 LLM 能搞定吗？它们犯错时，你能否直接指出错误并期待它改好？

为了测试这个，我需要一个能快速同时与多个聊天bot交互的环境，下面是我的搭建方式。

## 3. Keras 聊天机器人竞技场的技术栈：Spaces、Gradio、TPU、JAX 和 Keras

为了实验这个场景，我需要同时进行两场对话、对接不同 LLM，并且能在让其中一个改正输出错误时暂停另一方。效果如下。它用 Spaces 上的 Gradio 构建，底层是 Keras、JAX 和 TPU：

[![screenshot](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/keras-chatbot-arena/screenshot.png)](https://huggingface.co/spaces/huggingface/keras-chatbot-arena)

在我们回到"和 LLM 闲聊"这件正事之前，先说几句构建细节。

### 3.1 为什么用 TPU？

因为推理快、内存大。一块 [TPU v5e 2x4](https://cloud.google.com/tpu/docs/v5e) 有 8 个核心，每核 16GB RAM，合计 128GB 内存。有了这么多内存，只要把模型分片到所有核心上，就能同时加载多个 LLM，并在 UI 里随意切换。在这次实验中，我加载了五个约 8B 参数的模型（再多加一个就 OOM）加三个约 2B 的模型，一共 7 个 LLM 同时在内存里，全部为 bfloat16 格式。

### 3.2 为什么用 JAX 和 Keras？

得益于强大的 XLA 编译器，JAX 是 TPU 上的首选 ML 环境。Keras 现在原生跑在 JAX（以及 PyTorch 和 TensorFlow）之上，是我最喜爱的建模环境，其姊妹库 KerasHub 还有一批不错的预训练 LLM。它甚至能加载 Hugging Face 上部分非 Keras 检查点，这对做对比很有用。我之前写过相关内容：[Llama 3.2 in Keras](https://huggingface.co/blog/keras-llama-32)。

### 3.3 模型分片（Sharding）？

我选 Keras 还有一个原因：它的模型并行 API 是最好用的，没有之一。这里我想在 TPU 内存里同时装入尽可能多的模型。为此模型必须分片到全部 8 个 TPU 核心的内存上。好在大多数模型都自带一个正好干这件事的默认 layout map。例如：

```
layout_map = keras_hub.models.Llama3Backbone.get_layout_map(device_mesh)
```

完整的加载代码和模型并行的更多背景，见我[之前的这篇文章](https://developers.googleblog.com/en/fine-tuning-gemma-2-with-keras-hugging-face-update/)。那篇文章里还有一段代码，可以可视化模型加载后实际生效的分片情况，调试时非常有用。是的，调试和若干 layout map 调整[在所难免](https://huggingface.co/spaces/huggingface/keras-chatbot-arena/blob/c16851db4f6aaac90c2d06d8bdb06890a86e24e7/models.py#L34)。

### 3.4 用了哪些模型？

这次实验我选了 10B 参数以下的 LLM，主要图它们实用——很多可以同时加载。另外，实验测试的内容相当简单，本该在这些小模型的能力范围内。所有模型都经过指令微调，因此可以进行对话。你可以在 [demo 的实现里看到它们的 chat template](https://huggingface.co/spaces/huggingface/keras-chatbot-arena/blob/main/chatstate.py)。需要给自己的 Keras 聊天bot 时欢迎直接复制代码。模型来自 Gemma、Llama3、Mistral 和 Vicuna 家族。完整清单见下面的结果表格。

### 4.3 更多的错误修复测试

有些模型一路轻松过关，错误很少，也就没什么机会修正错误、挣西兰花 🥦。借助 [Keras 聊天机器人竞技场](https://huggingface.co/spaces/huggingface/keras-chatbot-arena) UI，我们可以拿其他 LLM 犯过的错 🍄 来考它们，看能不能修好。

## 5. 总结

开始测试前我也不知道会是什么结果。模型要用的 API 简单得不真实，就两个调用：'add_calendar_entry' 和 'remove_calendar_entry'。所以我原以为这对模型应该超级简单，稍微加一点纠正提示就能每次都满分。另一方面，我也知道 LLM 是概率推理机器，并不真的"听"你说什么。提示词只是改变输出的概率分布，有些输出就是很难得到。
