如果您在 Mac 上运行模型或使用 MPS 作为主要计算加速工具，那么 PyTorch 2.15 有很多值得期待的功能！ FP8 到达 MPS，语言模型解码通过线性层和 softmax 获得更快的路径，新的 Metal 内核解决了音频、视频和训练工作负载中一些极其昂贵的部分。

简单介绍一下我们是谁：我们是 Hugging Face 的 PyTorch 团队。我们在 PyTorch 上做出贡献，我们的重点领域之一是 MPS 后端，其目标是使您的 Mac 成为运行和训练 PyTorch 模型的一流场所。 2026 年初，即使在 MPS 上运行小型模型也通常意味着要解决不受支持的操作、性能悬崖和意外的内存增长。因此，我们通过 Hugging Face Hub 跨语言、图像和视频运行真实模型，找到 MPS 的不足之处，并在 PyTorch 上游修复它，越来越多地通过用专用 Metal 内核替换 MPSGraph 来解决。这篇文章的大部分内容都是与 PyTorch 维护者和社区贡献者共同完成的工作成果。

## 长篇大论；博士

- **FP8 登陆 Mac：** 将 `float8_e4m3fn` 值存储在 BF16 一半的空间中，并使用缩放矩阵乘法和 CUDA/CPU 支持的所有其他运算！
- **MoE 模型的解码速度比 2.14 快 5-6.5 倍：** Qwen3.6-35B-A3B 在 M3 Ultra 上从 9.4 个令牌/秒增加到 61.3 个令牌/秒，这要归功于具有专用解码路径的本机分组 matmul、更少的 GPU-CPU 同步和更快的 top-k 路由。
- **每个LLM的每个标记的时间更少：**单行线性层使用专门的矩阵向量内核，并且词汇表上的softmax大约快8倍。
- **GPU 上的更多线性代数：** 复杂的 LU 和三角求解、更快的小矩阵逆以及更快的 QR 分解。
- **音频、视频和训练也受到关注：** 更快的卷积、填充、丢失、向后插值和缩减路径。 Wan2.2 的视频 VAE 解码现在内存峰值为 8 GiB，而不是 270 GiB。
- **来自 Python 的更多控制：** 公共 MPS 流和更可靠的事件计时。
- **更新的要求：** MPS 现在需要 **macOS 15 或更高版本**； PyTorch 2.15 需要 **Python 3.11 或更高版本**。
- **浏览 2.16：** 完全关注 Metal、更多 MPSGraph 到 Metal 的迁移以及更快的 LLM 解码。

## 这对您意味着什么

如果您使用 Transformer、Diffuser 或 ComfyUI 等工具在 Mac 上运行模型，那么 2.15 在实践中发生了以下变化：

- **更快的本地 LLM。** 专家混合模型的解码速度比 2.14 快 5-6.5 倍：在带有“torch.compile”的 M3 Ultra 上，Qwen3.6-35B-A3B 从 9.4 到 61.3 个令牌/秒，LFM2.5-8B-A1B 从 23.6 到 123.6 个令牌/秒。密集模型也受益于更快的线性层和快 8 倍的 softmax 采样。 ([更多](https://huggingface.co/blog/mps-pytorch-2-15#faster-language-model-decoding))
- **适合内存的视频生成。** 使用 Wan2.2 的平铺 VAE 解码视频，用于将驱动程序内存推至 270 GiB；现在峰值约为 8 GiB。 ([更多](https://huggingface.co/blog/mps-pytorch-2-15#a-much-smaller-memory-footprint-for-video-decoding))
- **使用 Qwen-Image-2.1 正确编辑图像。** 在 2.14 上，Qwen-Image-2.1 VAE 编码器会默默地损坏 MPS 上的图像，破坏图像编辑工作流程（[ComfyUI 中报告](https://github.com/Comfy-Org/ComfyUI/issues/16433)）。 [相同的填充更改](https://github.com/pytorch/pytorch/pull/195368) 修复了这个问题：编码-解码往返现在与 CPU 匹配的 PSNR 为 29.95 dB，高于 10.06 dB。
- **Mac 上的 FP8 权重。** FP8 张量占用 BF16 的一半内存，并且“F.scaled_mm”直接在 GPU 上将它们相乘。 （[更多](https://huggingface.co/blog/mps-pytorch-2-15#fp8-comes-to-mps))

您需要一台配备 **macOS 15 或更高版本** 和 **Python 3.11 或更高版本** 的 Apple 芯片 Mac（请参阅 [2.15 兼容性矩阵](https://github.com/pytorch/pytorch/blob/release/2.15/RELEASE.md#release-compatibility-matrix)）。如果您的操作系统太旧或没有可用的 Metal GPU，MPS 可用性检查现在会告诉您原因。

要在单独的环境中尝试候选版本：
```

```
## FP8 来到 MPS

FP8 为您提供了另一种节省 Mac 内存的方法。 PyTorch 2.15 在 MPS 上添加了 [`torch.float8_e4m3fn`](https://github.com/pytorch/pytorch/pull/194074) 张量：每个值一个字节，存储量是 FP16 或 BF16 的一半。

您可以将这些张量与 [`F.scaled_mm`](https://github.com/pytorch/pytorch/pull/196916) 相乘，它支持张量和行缩放。这是一个小例子，每个张量一个尺度：
```
import torch
import torch.nn.functional as F

def quantize_fp8(x):
    limit = torch.finfo(torch.float8_e4m3fn).max
    scale = x.abs().amax().clamp_min(1e-12) / limit
    return (x / scale).to(torch.float8_e4m3fn), scale

x = torch.randn(1, 1024, device="mps", dtype=torch.float32)
weight = torch.randn(1024, 1024, device="mps", dtype=torch.float32)
x_fp8, x_scale = quantize_fp8(x)
w_fp8, w_scale = quantize_fp8(weight)

y = F.scaled_mm(
    x_fp8,
    w_fp8.t(),
    scale_a=x_scale,
    scale_recipe_a=F.ScalingType.TensorWise,
    scale_b=w_scale,
    scale_recipe_b=F.ScalingType.TensorWise,
    output_dtype=torch.bfloat16,
)
print(y.shape, y.dtype)
```
## 更快的语言模型解码

每个法学硕士都有预填充阶段和解码阶段。在解码期间，每个新标记作为单行通过模型，因此大矩阵乘法变成矩阵向量乘积。 PyTorch 2.15 加速了主导此步骤的两种层：密集线性层和专家混合层。

### 线性层

自 2.14 起，MPS 就为“torch.mm”提供了 GEMV 内核，但“F.线性”仍然通过 MPSGraph。 PyTorch 2.15 [将它们连接到“F.线性”](https://github.com/pytorch/pytorch/pull/198721)，因此常见的“[1, 1,hidden_​​size]”解码输入直接使用它们，并融合了合格的偏差添加。在来自真实模型的 96 个 BF16 层形状中，这是 **1.23× 几何平均加速**。最大的胜利在于小投影，例如 MoE 模型中的门，其中旧路径未使用大部分内存带宽。大层和 LM 头已经接近带宽限制，因此它们保持在 1 倍附近。

### 混合专家层

专家混合层向每个专家发送不同数量的令牌。分组 matmul 在单个操作中处理这些不均匀的组，2.15 为 MPS 提供了[本机实现](https://github.com/pytorch/pytorch/pull/194933)。

在 2.14 中，分组 matmul 将组偏移量复制到 CPU 并循环遍历组。新的 Metal 内核直接在 GPU 上读取偏移量，使用可用的 Metal 性能基元以及其他地方的单独 Metal 路径。小团体（解码过程中的常见情况）也获得[自己的内核](https://github.com/pytorch/pytorch/pull/198725)。

例如，64 个令牌可以分为 16、32 和 16 组：
```
import torch
import torch.nn.functional as F

tokens = torch.randn(64, 64, device="mps", dtype=torch.bfloat16)
weights = torch.randn(3, 128, 64, device="mps", dtype=torch.bfloat16)
ends = torch.tensor([16, 48, 64], device="mps", dtype=torch.int32)

out = F.grouped_mm(tokens, weights.transpose(-2, -1), offs=ends)
print(out.shape)  # torch.Size([64, 128])
```
解码内核直接显示在令牌吞吐量中。在带有 `torch.compile`** 的 **M3 Ultra 上，MoE 模型每秒生成大约 **1.3 倍的令牌**：

[![使用 torch.compile 在 M3 Ultra 上进行 MoE 解码吞吐量的条形图。 Qwen3.6-35B-A3B 在上下文 512 处从 38.7 令牌/秒变为 51.7 个令牌/秒，在上下文 2048 处从 36.8 令牌/秒变为 48.7； LFM2.5-8B-A1B 从 77.1 升至 103.2，从 74.9 升至 98.7令牌/s。](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mps-pytorch-2-15/moe-decode-throughput.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mps-pytorch-2-15/moe-decode-throughput.png)

## 线性代数得到提升

### 复值计算

使用复杂的张量变得更加容易。 `complex64` [LU 分解](https://github.com/pytorch/pytorch/pull/188473)、[LU 求解](https://github.com/pytorch/pytorch/pull/195369) 和 [三角求解](https://github.com/pytorch/pytorch/pull/195861) 现在在 MPS 上运行，这也解锁了基于它们构建的操作和梯度，例如作为复杂的决定因素。这是一个直接在 GPU 上求解的小型系统：
```
import torch

a = torch.randn(8, 8, device="mps", dtype=torch.complex64)
a = a + 8 * torch.eye(8, device="mps", dtype=torch.complex64)
b = torch.randn(8, 2, device="mps", dtype=torch.complex64)

lu, pivots = torch.linalg.lu_factor(a)
x = torch.linalg.lu_solve(lu, pivots, b)
print((a @ x - b).abs().max().item())
```
### 小矩阵和大求解

小矩阵也可以获得快速内核。对于相机几何和图像转换，高达 **4 × 4** 的批量 FP32 矩阵[在单个 Metal 内核中反转](https://github.com/pytorch/pytorch/pull/195944)，结合了分解和求解。更大的问题也受到关注：[QR 使用阻塞更新](https://github.com/pytorch/pytorch/pull/198732) 和[三角求解](https://github.com/pytorch/pytorch/pull/196241) 将大部分工作转化为高效的矩阵乘法。

门控 DeltaNet 工作负载获得[专用快速路径](https://github.com/pytorch/pytorch/pull/196900)，用于批量**16 × 16、32 × 32 和 64 × 64 FP32 三角形系统**（至少有八个右侧边）。

SVD 在数值极值情况下也更加稳健。它现在可以正确处理[非常小的奇异值](https://github.com/pytorch/pytorch/pull/200920)、[非常大或非常小的输入幅度](https://github.com/pytorch/pytorch/pull/201037)和[使用 `full_matrices=True` 进行基础补全](https://github.com/pytorch/pytorch/pull/201198)，其中转使得伪逆和最小二乘结果更加可靠。

## 卷积、填充和训练

音频模型、视频解码器和训练循环都有自己昂贵的操作。此版本为其中一些人提供了通过 Metal 的新途径：

|运营| 2.15 有何变化 |
| --- | --- |
| [`conv1d` 转发](https://github.com/pytorch/pytorch/pull/198878) |专用内核取代了 MPSGraph，加上用于短输出的 im2col-plus-matmul 路径。对于音频和流模型形状很有用。 |
| [恒定填充](https://github.com/pytorch/pytorch/pull/195368) |转向 Metal 内核，修复了平铺视频 VAE 解码中驱动程序内存失控的增长（更多内容见下文）。 |
| [反射和复制填充](https://github.com/pytorch/pytorch/pull/196985) |新的 Metal 实现速度更快并修复了向后正确性。 |

| [向后上采样](https://github.com/pytorch/pytorch/pull/199687) | Metal Gather 内核取代了 MPSGraph 调整大小梯度路径。 |
| [通道-最后一个 `conv2d` 向后](https://github.com/pytorch/pytorch/pull/193623) |保持在高效的通道最后路径上，而不是具有昂贵的跨步访问的 NCHW 图。 |

## Softmax 和缩减

令牌采样在 2.15 中也变得更快。 [`softmax`](https://github.com/pytorch/pytorch/pull/196071) 和 [`log_softmax`](https://github.com/pytorch/pytorch/pull/195441) 现在在专用 Metal 内核上运行，大词汇量受益最多：在 `[1, 128256]` 行 logits 上的 FP32 softmax 从 **57 µs 下降到7 µs**，比 MPSGraph 版本快大约 **8 倍**。这种加速适用于其他常见的词汇量：

## 通过 MPS 流进行更多控制

现在，您可以直接从 Python 选择运行您的工作的 MPS 流。 [`torch.mps.Stream` 和 `torch.mps.stream` 上下文管理器](https://github.com/pytorch/pytorch/pull/191415) 提供接口，[`Tensor.record_stream`](https://github.com/pytorch/pytorch/pull/193464) 让分配器跟踪张量在另一个流上的使用情况。

这是一个小示例，它将工作发送到单独的流并在读取结果之前进行同步：
```
import torch

x = torch.randn(1024, device="mps")
torch.mps.synchronize()
worker = torch.mps.Stream()

with torch.mps.stream(worker):
    y = x.square()
    x.record_stream(worker)

del x
worker.synchronize()
print(y.cpu().shape)
```
## MPS 上的更多操作

现在在 MPS 上运行了更多操作：[`torch.frexp`](https://github.com/pytorch/pytorch/pull/194110)、[`torch.logspace`](https://github.com/pytorch/pytorch/pull/190495)、[`torch.take` 和`Tensor.put_`](https://github.com/pytorch/pytorch/pull/192980)、[`torch.heaviside`](https://github.com/pytorch/pytorch/pull/195265)、[`torch.special.laguerre_polynomial_l`](https://github.com/pytorch/pytorch/pull/195225) 和[无符号整数比较](https://github.com/pytorch/pytorch/pull/198860)。 `logspace` 尚不支持具有多个元素的整数或布尔输出。

注意力也得到了正确性修复：缩放点积注意力的 MPS 数学实现现在[正确处理批量和头部广播](https://github.com/pytorch/pytorch/pull/189631)。

## PyTorch 2.16 预览

2.16 的工作已经在顺利进行中。以下一些更改已发布在“main”上，并且可以在夜间播放中使用；其他部分仍在审查中，因此细节在发布之前可能会发生变化。

### 更快的 LLM 解码

一旦模型的解码路径不再包含任何 MPSGraph 操作，GPU 仅在 CPU 完成对其所有内核的编码后才在令牌上启动。 PyTorch 2.16 [每 16 个内核提交一次命令缓冲区](https://github.com/pytorch/pytorch/pull/200181)，因此 GPU 开始工作，而 CPU 仍在对其余部分进行编码。对于 2048 个令牌上下文中编译的 BF16 解码：

|型号|之前 |之后|改变 |
| --- | --- | --- | --- |
| LFM2.5-8B-A1B | 108.8 代币/秒 | 126.0 代币/秒 | +16% |

### 注意力完全运行在 Metal 上

缩放点积注意力[完全放弃 MPSGraph](https://github.com/pytorch/pytorch/pull/201526)：每个形状都将在 Metal 内核上运行，具有用于解码的专用矢量内核和用于在较新的 macOS 版本上进行半精度预填充的 Metal 性能基元。过去回归 MPSGraph 的形状受益最多。在 M5 Pro 上，使用分组查询注意力（32 个查询头、8 KV 头、head dim 80、4K 上下文）进行解码从 465 µs 降至 65 µs，而 head dim 40 的 4K × 4K 预填充从 42 ms 降至 6 ms。

### 更多 MPSGraph 到 Metal 迁移

远离 MPSGraph 的趋势仍在继续。批量归一化[向前](https://github.com/pytorch/pytorch/pull/201361)和[向后](https://github.com/pytorch/pytorch/pull/201411)正在进行中，而[MSE损失](https://github.com/pytorch/pytorch/pull/201351)(小输入时速度提高12倍)，[`std_mean`和`var_mean`](https://github.com/pytorch/pytorch/pull/201310)（速度提高了 4 倍）和 [`bincount`](https://github.com/pytorch/pytorch/pull/201045) 已经落地。 “bincount”是最戏剧性的：当大多数值落入一个容器时，计算 400 万个整数过去需要 6.8 秒，现在只需要半毫秒。

### 较小的安装

捆绑的着色器将[默认为 Metal 3.1 构建](https://github.com/pytorch/pytorch/pull/197529)，仅为需要它们的内核编译 Metal 4 版本。这将“libtorch_cpu.dylib”缩小了约 25%，从 384 MiB 缩小到 287 MiB，并为具有更快 matmul 和本机 FP8 矩阵乘法的 Metal 4.1 着色器奠定了基础。

## 总结

PyTorch 2.15 为 Mac 带来了 FP8、针对密集模型和 MoE 模型的更快的 LLM 解码、GPU 上更多的线性代数以及从 MPSGraph 转移到专用 Metal 内核的一长串操作。尝试一下候选版本！

### 我们的下一步是什么

- **更多 MPS：** 2.16 将完全关注 Metal，我们将继续将操作移出 MPSGraph。
- **`torch.compile`：**我们正在努力消除图表中断，以便更多模型进行端到端编译。
- **您的想法：** 我们还应该在 PyTorch 中做什么？如果 MPS 或其他任何地方出现缓慢、丢失或损坏的情况，请[在 GitHub 上提出问题](https://github.com/pytorch/pytorch/issues) 并告知我们。
