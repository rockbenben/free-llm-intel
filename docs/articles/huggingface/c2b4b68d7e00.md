如果你在 Mac 上运行模型，或者把 MPS 作为主要的计算加速手段，那么 PyTorch 2.15 有不少值得期待的东西！FP8 来到 MPS；语言模型解码通过线性层与 softmax 获得了更快的路径；新的 Metal kernel 则攻克了音频、视频和训练工作负载中一些出奇昂贵的部分。

先简单说明我们是谁：我们是 Hugging Face 的 PyTorch 团队。我们在 PyTorch 的多个方向上做贡献，其中一个重点领域是 MPS 后端，目标是让你的 Mac 成为运行和训练 PyTorch 模型的一等场所。2026 年初，哪怕只是在 MPS 上运行小模型，也往往意味着要绕开不支持的操作、性能悬崖和意料之外的内存增长。于是我们拿 Hugging Face Hub 上真实的语言、图像和视频模型来跑，找出 MPS 的短板并在 PyTorch 上游修掉，而且越来越多地用专用 Metal kernel 取代 MPSGraph。本文的很多内容正是这项工作与 PyTorch 维护者、社区贡献者共同完成的成果。

## 太长不看（TL;DR）

- **FP8 来到 Mac：** 用 BF16 一半的空间存储 `float8_e4m3fn` 数值，并使用缩放矩阵乘法以及 CUDA/CPU 上支持的所有其他算子！
- **MoE 模型解码比 2.14 快 5–6.5 倍：** 借助带专用解码路径的原生 grouped matmul、更少的 GPU-CPU 同步以及更快的 top-k 路由，Qwen3.6-35B-A3B 在 M3 Ultra 上从 9.4 tokens/s 提升到 61.3 tokens/s。
- **每个 LLM 的每个 token 耗时更少：** 单行线性层使用专门的矩阵-向量 kernel，而词表上的 softmax 大约快了 8 倍。
- **GPU 上更多的线性代数：** 复数 LU 与三角求解、更快的小矩阵求逆，以及更快的 QR 分解。
- **音频、视频和训练同样得到关注：** 卷积、padding、dropout、插值反向和归约都有了更快的路径。Wan2.2 的视频 VAE 解码现在内存峰值是 8 GiB，而不是 270 GiB。
- **从 Python 获得更多控制：** 公开的 MPS stream，以及更可靠的事件计时。
- **更新的要求：** MPS 现在需要 **macOS 15 或更高版本**；PyTorch 2.15 需要 **Python 3.11 或更高版本**。
- **提前一瞥 2.16：** attention 完全跑在 Metal 上、更多从 MPSGraph 到 Metal 的迁移，以及更快的 LLM 解码。

## 这对你意味着什么

如果你在 Mac 上用 transformers、diffusers 或 ComfyUI 之类的工具运行模型，以下是 2.15 在实践中带来的变化：

- **本地 LLM 快得多。** 专家混合模型（MoE）的解码速度比 2.14 快 5–6.5 倍：在开启 `torch.compile` 的 M3 Ultra 上，Qwen3.6-35B-A3B 从 9.4 tokens/s 提升到 61.3 tokens/s，LFM2.5-8B-A1B 从 23.6 tokens/s 提升到 123.6 tokens/s。密集模型同样受益，来自更快的线性层和用于采样的、快 8 倍的 softmax。（[更多](https://huggingface.co/blog/mps-pytorch-2-15#faster-language-model-decoding)）
- **装得下内存的视频生成。** 以前用 Wan2.2 的 tiled VAE 解码视频会把驱动内存推到 270 GiB；现在峰值约为 8 GiB。（[更多](https://huggingface.co/blog/mps-pytorch-2-15#a-much-smaller-memory-footprint-for-video-decoding)）
- **用 Qwen-Image-2.1 正确地编辑图像。** 在 2.14 上，Qwen-Image-2.1 的 VAE 编码器会在 MPS 上悄悄损坏图像，导致图像编辑工作流失败（[已在 ComfyUI 中报告](https://github.com/Comfy-Org/ComfyUI/issues/16433)）。[同一处 padding 改动](https://github.com/pytorch/pytorch/pull/195368)修复了它：一次编码-解码往返现在与 CPU 的结果达到 29.95 dB PSNR，而此前只有 10.06 dB。
- **Mac 上的 FP8 权重。** FP8 张量只占 BF16 一半的内存，而 `F.scaled_mm` 直接在 GPU 上完成相乘。（[更多](https://huggingface.co/blog/mps-pytorch-2-15#fp8-comes-to-mps)）

## FP8 来到 MPS

FP8 为你在 Mac 上节省内存提供了另一种方式。PyTorch 2.15 在 MPS 上新增了 [`torch.float8_e4m3fn`](https://github.com/pytorch/pytorch/pull/194074) 张量：每个值占一个字节，存储量是 FP16 或 BF16 的一半。

你可以用 [`F.scaled_mm`](https://github.com/pytorch/pytorch/pull/196916) 相乘这些张量，它同时支持按张量（tensorwise）和按行（rowwise）缩放。下面是一个每个张量一个 scale 的小例子：

```
import torch
import torch.nn.functional as F

def quantize_fp8(x):
    limit = torch.finfo(torch.float8_e4m3fn).max
    scale = x.abs().amax().clamp_min(1e-12) / limit
    return (x / scale).to(torch.float8_e4m3fn), scale

x = torch.randn(1, 1024, device="mps", dtype=torch.float32)
weight = torch.randn(1024, 1024, device="mps", dtype=torch.float32)
x_fp8, x_scale = quantize_fp8(x)
w_fp8, w_scale = quantize_fp8(weight)

y = F.scaled_mm(
    x_fp8,
    w_fp8.t(),
    scale_a=x_scale,
    scale_recipe_a=F.ScalingType.TensorWise,
    scale_b=w_scale,
    scale_recipe_b=F.ScalingType.TensorWise,
    output_dtype=torch.bfloat16,
)
print(y.shape, y.dtype)
```

## 更快的语言模型解码

每个 LLM 都有 prefill 阶段和 decode 阶段。在 decode 阶段，每个新 token 都以单行形式经过模型，因此大矩阵乘法变成了矩阵-向量乘法。PyTorch 2.15 加速了这一环节中占主导的两类层：密集线性层和专家混合层。

### 线性层

自 2.14 起，MPS 已经为 `torch.mm` 提供了 GEMV kernel，但 `F.linear` 仍然走 MPSGraph。PyTorch 2.15 [把它们接到了 `F.linear` 上](https://github.com/pytorch/pytorch/pull/198721)，于是常见的 `[1, 1, hidden_size]` 解码输入可以直接使用这些 kernel，并把符合条件的 bias 加法融合进去。在来自真实模型的 96 种 BF16 层形状上，这带来了 **1.23 倍的几何平均加速**。收益最大的是小型投影，比如 MoE 模型中的 gate，旧路径在那里浪费了大部分内存带宽。大层和 LM head 本来就已接近带宽上限，因此基本维持在 1 倍附近。

### 专家混合层

专家混合层会把数量不等的 token 发给每个专家。grouped matmul 用一次操作处理这些不规整的分组，而 2.15 为 MPS 提供了[原生实现](https://github.com/pytorch/pytorch/pull/194933)。

在 2.14 中，grouped matmul 会把分组偏移量拷贝到 CPU，再在分组上循环。新的 Metal kernel 直接在 GPU 上读取这些偏移量，在有条件时使用 Metal Performance Primitives，其余情况走单独的 Metal 路径。解码期间常见的小分组还额外获得了[自己的 kernel](https://github.com/pytorch/pytorch/pull/198725)。

例如，64 个 token 可以被拆成 16、32 和 16 三组：

```
import torch
import torch.nn.functional as F

tokens = torch.randn(64, 64, device="mps", dtype=torch.bfloat16)
weights = torch.randn(3, 128, 64, device="mps", dtype=torch.bfloat16)
ends = torch.tensor([16, 48, 64], device="mps", dtype=torch.int32)

out = F.grouped_mm(tokens, weights.transpose(-2, -1), offs=ends)
print(out.shape)  # torch.Size([64, 128])
```

解码 kernel 直接体现在 token 吞吐上。在 **开启 `torch.compile` 的 M3 Ultra** 上，MoE 模型每秒生成的 token 数大约**提升 1.3 倍**：

[![M3 Ultra 上开启 torch.compile 时 MoE 解码吞吐的柱状图。Qwen3.6-35B-A3B 在上下文 512 时从 38.7 提升到 51.7 tokens/s，在上下文 2048 时从 36.8 提升到 48.7；LFM2.5-8B-A1B 则从 77.1 提升到 103.2、从 74.9 提升到 98.7 tokens/s。](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mps-pytorch-2-15/moe-decode-throughput.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mps-pytorch-2-15/moe-decode-throughput.png)

## 线性代数得到增强

### 复数值计算

处理复数张量变得更轻松了。`complex64` 的 [LU 分解](https://github.com/pytorch/pytorch/pull/188473)、[LU 求解](https://github.com/pytorch/pytorch/pull/195369)和[三角求解](https://github.com/pytorch/pytorch/pull/195861)现在都能在 MPS 上运行，这也解锁了建立在它们之上的算子与梯度，比如复数行列式。下面是一个直接在 GPU 上求解的小型方程组：

```
import torch

a = torch.randn(8, 8, device="mps", dtype=torch.complex64)
a = a + 8 * torch.eye(8, device="mps", dtype=torch.complex64)
b = torch.randn(8, 2, device="mps", dtype=torch.complex64)

lu, pivots = torch.linalg.lu_factor(a)
x = torch.linalg.lu_solve(lu, pivots, b)
print((a @ x - b).abs().max().item())
```

### 小矩阵与更大规模的求解

小矩阵也获得了快速 kernel。对于相机几何和图像变换，批量最大到 **4 × 4** 的 FP32 矩阵现在[在单个 Metal kernel 中求逆](https://github.com/pytorch/pytorch/pull/195944)，该 kernel 把分解和求解合并在一起。更大的问题同样得到关注：[QR 使用分块更新](https://github.com/pytorch/pytorch/pull/198732)，而[三角求解](https://github.com/pytorch/pytorch/pull/196241)把大部分工作转化成高效的矩阵乘法。

Gated DeltaNet 工作负载获得了一条[专用的快速路径](https://github.com/pytorch/pytorch/pull/196900)，适用于批量 **16 × 16、32 × 32 和 64 × 64 的 FP32 三角方程组**，且右端项至少有 8 个。

SVD 在数值极端情况下也更加稳健。它现在能正确处理[非常小的奇异值](https://github.com/pytorch/pytorch/pull/200920)、[极大或极小的输入量级](https://github.com/pytorch/pytorch/pull/201037)以及 [`full_matrices=True` 时的基补全](https://github.com/pytorch/pytorch/pull/201198)，这反过来让伪逆和最小二乘的结果更可靠。

## 卷积、padding 与训练

音频模型、视频解码器和训练循环各自都有开销高昂的算子。本次发布为其中若干算子提供了经由 Metal 的新路径：

| 算子 | 2.15 中的变化 |
| --- | --- |
| [`conv1d` 前向](https://github.com/pytorch/pytorch/pull/198878) | 专用 kernel 取代 MPSGraph，另外为短输出提供 im2col 加 matmul 的路径。适用于音频和流式模型的形状。 |
| [常量 padding](https://github.com/pytorch/pytorch/pull/195368) | 迁移到 Metal kernel，修复了 tiled 视频 VAE 解码中失控的驱动内存增长（详见下文）。 |
| [反射与复制 padding](https://github.com/pytorch/pytorch/pull/196985) | 新的 Metal 实现更快，并修复了反向传播的正确性。 |
| [out-of-place dropout](https://github.com/pytorch/pytorch/pull/195011) | `nn.Dropout` 和 `F.dropout` 现在使用已有的融合 kernel。 |
| [上采样反向](https://github.com/pytorch/pytorch/pull/199687) | 用 Metal gather kernel 取代 MPSGraph 的 resize 梯度路径。 |
| [channels-last `conv2d` 反向](https://github.com/pytorch/pytorch/pull/193623) | 保持在高效的 channels-last 路径上，而不是退回到带昂贵跨步访问的 NCHW 图。 |

## Softmax 与归约

token 采样在 2.15 中也变快了。[`softmax`](https://github.com/pytorch/pytorch/pull/196071) 和 [`log_softmax`](https://github.com/pytorch/pytorch/pull/195441) 现在运行在专用 Metal kernel 上，大词表收益最大：对一行 `[1, 128256]` 的 logits 做 FP32 softmax，耗时从 **57 µs 降到 7 µs**，约比 MPSGraph 版本**快 8 倍**。这一加速在其它常见词表大小上同样成立：

[![五种词表大小（从 128,256 到 201,088）下，单行 logits 的 FP32 softmax 耗时柱状图。MPSGraph 需要 50 到 74 微秒；Metal kernel 需要 7 到 10 微秒，加速 7.1 倍到 8.0 倍。](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mps-pytorch-2-15/softmax-sampling.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mps-pytorch-2-15/softmax-sampling.png)

## 视频解码的内存占用大幅缩小

本次发布中最亮眼的结果之一来自常量 padding 的改动。`Wan-AI/Wan2.2-TI2V-5B-Diffusers` 中的 VAE 解码在完整的 28 个 tile 解码过程中发起了 **8,764 次 padding 调用**。把 padding 放到 Metal 上之后，驱动内存峰值从约 **270 GiB 降到 8 GiB**：

[![Wan2.2 tiled VAE 解码期间驱动内存峰值的堆叠柱状图。使用 MPSGraph padding 时，分配器保留的 8.07 GiB 加上分配器之外的 262 GiB 合计 270.1 GiB；使用 Metal padding 时总量为 8.1 GiB。](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mps-pytorch-2-15/wan-vae-memory.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mps-pytorch-2-15/wan-vae-memory.png)

## 用 MPS stream 获得更多控制

你现在可以直接在 Python 里指定由哪个 MPS stream 来执行你的工作。[`torch.mps.Stream` 与 `torch.mps.stream` 上下文管理器](https://github.com/pytorch/pytorch/pull/191415)提供了这套接口，而 [`Tensor.record_stream`](https://github.com/pytorch/pytorch/pull/193464)让分配器能够追踪某个张量在另一个 stream 上的使用情况。

下面是一个小例子，把工作发到单独的 stream，并在读取结果前做同步：

```
import torch

x = torch.randn(1024, device="mps")
torch.mps.synchronize()
worker = torch.mps.Stream()

with torch.mps.stream(worker):
    y = x.square()
    x.record_stream(worker)

del x
worker.synchronize()
print(y.cpu().shape)
```

## 更多算子在 MPS 上可用

又有若干算子在 MPS 上可用： [`torch.frexp`](https://github.com/pytorch/pytorch/pull/194110)、[`torch.logspace`](https://github.com/pytorch/pytorch/pull/190495)、[`torch.take` 和 `Tensor.put_`](https://github.com/pytorch/pytorch/pull/192980)、[`torch.heaviside`](https://github.com/pytorch/pytorch/pull/195265)、[`torch.special.laguerre_polynomial_l`](https://github.com/pytorch/pytorch/pull/195225) 以及[无符号整数比较](https://github.com/pytorch/pytorch/pull/198860)。`logspace` 目前尚不支持多元素的整数或布尔输出。

attention 也获得了一处正确性修复：MPS 的 scaled dot-product attention 数学实现现在[能正确处理 batch 与 head 的广播](https://github.com/pytorch/pytorch/pull/189631)。

## PyTorch 2.16 抢先看

2.16 的工作已经在稳步推进。下面某些改动已经进入 `main` 并可在 nightly 中试用；另一些仍在评审，因此细节可能在发布前发生变化。

### 更快的 LLM 解码

一旦模型的 decode 路径不再包含任何 MPSGraph 算子，GPU 就要等 CPU 把所有 kernel 编码完毕才开始处理一个 token。PyTorch 2.16 [每 16 个 kernel 就提交一次 command buffer](https://github.com/pytorch/pytorch/pull/200181)，这样 GPU 在 CPU 仍在编码其余部分时就能开始工作。对于 2048 token 上下文下的编译版 BF16 解码：

| 模型 | 之前 | 之后 | 变化 |
| --- | --- | --- | --- |
| LFM2.5-8B-A1B | 108.8 tokens/s | 126.0 tokens/s | +16% |
| Qwen3.6-35B-A3B | 52.9 tokens/s | 62.8 tokens/s | +19% |
| Qwen3.8-27B | 12.1 tokens/s | 12.6 tokens/s | +4% |

### Attention 完全运行在 Metal 上

scaled dot-product attention 正在[彻底摆脱 MPSGraph](https://github.com/pytorch/pytorch/pull/201526)：所有形状都将运行在 Metal kernel 上，解码使用专用向量 kernel，在较新的 macOS 版本上，半精度 prefill 使用 Metal Performance Primitives。过去回退到 MPSGraph 的那些形状受益最大。在一台 M5 Pro 上，使用 grouped-query attention 解码（32 个 query head、8 个 KV head、head dim 80、4K 上下文）耗时从 465 µs 降到 65 µs，而 head dim 为 40 的 4K × 4K prefill 从 42 ms 降到 6 ms。

### 更多从 MPSGraph 到 Metal 的迁移

离开 MPSGraph 的步伐仍在继续。batch norm 的[前向](https://github.com/pytorch/pytorch/pull/201361)和[反向](https://github.com/pytorch/pytorch/pull/201411)正在进行中，而 [MSE loss](https://github.com/pytorch/pytorch/pull/201351)（小输入上最高快 12 倍）、[`std_mean` 与 `var_mean`](https://github.com/pytorch/pytorch/pull/201310)（最高快 4 倍）以及 [`bincount`](https://github.com/pytorch/pytorch/pull/201045)已经落地。`bincount` 最为惊人：当大多数值落在同一个 bin 里时，统计 400 万个整数过去要 6.8 秒，现在只需半毫秒。

### 更小的安装体积

内置 shader 将[默认按 Metal 3.1 构建](https://github.com/pytorch/pytorch/pull/197529)，只为需要它们的 kernel 编译 Metal 4 版本。这让 `libtorch_cpu.dylib` 缩小约 25%，从 384 MiB 降到 287 MiB，并为使用更快 matmul 和原生 FP8 矩阵乘法的 Metal 4.1 shader 打下基础。

## 总结

PyTorch 2.15 把 FP8 带到 Mac，为密集模型和 MoE 模型带来更快的 LLM 解码，把更多线性代数放到 GPU 上，并把一长串算子从 MPSGraph 迁移到专用 Metal kernel。不妨试试这个候选版本！

### 我们接下来做什么

- **更多 MPS 工作：** 2.16 将让 attention 完全运行在 Metal 上，我们也会继续把算子迁出 MPSGraph。
- **`torch.compile`：** 我们正在努力消除 graph break，让更多模型能够端到端编译。
- **你的想法：** 我们接下来还应该在 PyTorch 里做些什么？如果有哪里慢、缺失或坏掉，无论是在 MPS 还是别处，[在 GitHub 上开一个 issue](https://github.com/pytorch/pytorch/issues)告诉我们。
