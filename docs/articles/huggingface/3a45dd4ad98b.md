## [阶段 2] 朴素填充

我们第一次训练用的是最直观（也非常常见）的做法：

- 找到每个 batch 里最长的序列

## [阶段 3] 受限填充

下一步动作很简单：设一个全局最大长度并严格遵守。样本太长就直接丢掉。

[![Constrained Padding](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mmdp/03.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mmdp/03.png)

你可能已经注意到这个 batch 少了一个样本，这是过滤造成的。这有帮助，但我们仍然把所有内容 pad 到同一个固定长度，不管实际内容多少。比之前好，但依然浪费。

## [阶段 4]：用背包问题更聪明地打包

现在我们可以彻底重新思考 batching 了。padding 是敌人，我们需要一种策略：在最小化 padding 的同时最大化每个 batch 能装下的数据。请出计算机科学里的经典——[**背包问题**（knapsack problem）](https://en.wikipedia.org/wiki/Knapsack_problem)，它正好合适。

想象你要为徒步打包背包：载重有限，你想尽量多塞有用的东西。在我们的场景里：

- **背包**是一个有最大 token 上限（`max_length`）的训练 batch。
- 每件**物品**是一个序列（一个 tokenized 的 prompt-response 对），它的**重量**是 token 数。
- 目标是把尽可能多的序列装进 batch 且不超 token 上限，让浪费的空间最小。

为了验证这个想法，我们先从玩具数据集开始：一个 1 到 25 的数字列表，每个数字代表一个序列长度。这样不用处理图像和文本的复杂性就能做实验。

### 切换到 Iterable Dataset

多数 PyTorch 数据集是 *map-style*（用 `dataset[i]` 访问）。但动态 batching 需要更灵活的东西。于是我们通过继承 `torch.utils.data.IterableDataset` 做了一个 *iterable-style* 数据集。这让我们可以即时生成 batch，还能处理"把数据分片（sharding）给多个 worker"这类技巧：

```
def _get_data_range(self):
    worker_info = get_worker_info()
    if worker_info is None:  # single worker, return the entire dataset
        return self.start, self.end
    else:  # multiple workers, split the data load
        per_worker = int(
            math.ceil((self.end - self.start) / worker_info.num_workers)
        )
        worker_id = worker_info.id
        iter_start = self.start + worker_id * per_worker
        iter_end = min(iter_start + per_worker, self.end)
        return iter_start, iter_end
```

### 生产者-消费者的妙用

打包序列可能很慢，尤其涉及排序或打乱时。为了让流程保持顺畅，我们用 [Python 队列](https://docs.python.org/3/library/queue.html)实现了一个**生产者-消费者**（producer-consumer）模式：

```
def _producer(self, data_iter, queue, stop_signal):
    if self.strategy == "greedy":
        for pack in self._greedy_packing(data_iter):
            queue.put(pack)
    elif self.strategy == "binpack":
        while True:
            buffer = list(itertools.islice(data_iter, self.buffer_size))
            if not buffer:
                break
            knapsacks = self._bin_packing(buffer)
            for pack in knapsacks:
                queue.put(pack)
    queue.put(stop_signal)
```

生产者线程负责打包 batch 并放进队列，主线程按需取走。这种重叠让管道流畅运转。

### 贪心打包

先试一个简单的**贪心打包**（greedy packing）策略：

```
def _greedy_packing(self, iterator):
    pack, pack_sum = [], 0
    for item in iterator:
        if item > self.max_length:
            continue
        if pack_sum + item <= self.max_length:
            pack.append(item)
            pack_sum += item
        else:
            yield pack
            pack = [item]
            pack_sum = item
    if pack:
        yield pack
```

它顺序遍历数据，不断把物品装进当前包，装满就开一个新包。速度很快但不完美。batch 长这样：

```
=== Strategy: GREEDY ===
[tensor([1]), tensor([2]), tensor([3]), tensor([4]), tensor([5]), tensor([6]), tensor([7]), tensor([8]), tensor([9]), tensor([10]), tensor([11]), tensor([12]), tensor([13])]
[tensor([14]), tensor([15]), tensor([16]), tensor([17]), tensor([18]), tensor([19])]
[tensor([20]), tensor([21]), tensor([22]), tensor([23])]
[tensor([24])]
```

[![Greedy Knapsack](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mmdp/greedy.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mmdp/greedy.png)

注意到越靠后的 batch 越稀疏吗？我们在留空隙。

### 用 Bin-Packing 装得更紧

试试更聪明的方法：**装箱打包**（bin-packing），具体是 First Fit Decreasing：

```
def _bin_packing(self, buffer: List[int]):
    buffer = sorted(buffer, reverse=True)
    knapsacks = []
    for item in buffer:
        for pack in knapsacks:
            if sum(pack) + item <= self.max_length:
                pack.append(item)
                break
        else:
            knapsacks.append([item])
```

它按长度对序列排序（最长的先放），试着把每个塞进第一个有位置的包里；放不下就新开一个包。结果是：

```
=== Strategy: BINPACK ===
[tensor([24]), tensor([23]), tensor([22]), tensor([21]), tensor([10])]
[tensor([20]), tensor([19]), tensor([18]), tensor([17]), tensor([16]), tensor([9]), tensor([1])]
[tensor([15]), tensor([14]), tensor([13]), tensor([12]), tensor([11]), tensor([8]), tensor([7]), tensor([6]), tensor([5]), tensor([4]), tensor([3]), tensor([2])]
```

[![Tight](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mmdp/tight.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/mmdp/tight.png)

这些 batch *紧密*得多，浪费的空间更少。就像拿数据玩俄罗斯方块，把每一块都严丝合缝地拼上。

## [阶段 5] 多模态数据的背包

现在来真的：把背包打包应用到我们的*多模态*数据集。

我们回到图像、prompt 和回答，需要在遵守 token 上限*和*图像预算的前提下高效打包。图像预算是为了让每个样本的图像数量保持均衡。我们不希望出现某个 GPU 要处理的图像比另一个多很多的情况。

新的 [`ConstantLengthDataset`](https://github.com/ariG23498/mmdp/blob/main/src/mmdp/advanced_torch_datasets.py#L13) 类承担了重活。与阶段 4 对比，它的工作方式如下：

| 概念 | 阶段 4（玩具数据） | 阶段 5（多模态数据） | 函数 |
| --- | --- | --- | --- |
| **物品** | 整数（序列长度） | 完整样本（图像、prompt、回答） | `VQADataset.__getitem__` |
| **重量** | 整数本身 | token 数（`len(input_ids)`） | — |
| **背包** | 总和 ≤ `max_length` 的整数批 | token 长度 ≤ `seq_length` 且不超图像上限的样本批 | `_balanced_greedy_knapsack` |
| **打包策略** | 贪心或 Binpack | 带 token 与图像约束的贪心打包 | `_balanced_greedy_knapsack` |
| **生产者-消费者** | 生产者填充队列 | 与玩具示例相同，但装的是多模态样本 | `_producer`, `__iter__` |
| **样本过滤** | 跳过 > `max_length` 的整数 | 跳过 token 或图像过多的样本 | `_producer` |
| **分片（Sharding）** | 切分整数区间 | 按数据集索引分片 | `make_base_iterator()` |
| **组 batch** | 整数分组 | 拼接并对齐 token/图像 | `_pack_one_group` |
| **输出** | 整数列表 | 含 `input_ids`、`labels`、`attention_mask`、`images` 的 dict | `__iter__` 中的 `yield` |

`ConstantLengthDataset` 一手包办：

- 读取样本（图像和文本）。
- 过滤掉过长或图像过多的样本。
- 用贪心背包策略把样本打包成 batch，同时平衡 token 数和图像数。
- 把最终 batch pad 到固定长度，但 padding 比之前*少得多*。

## 结论

这一切始于一个简单的"训练为什么这么慢？"调查，最后演变成对我们处理多模态数据方式的彻底重构。

数据管道中的均衡背包策略来自 NVIDIA 的论文 [Eagle 2: Building Post-Training Data Strategies from Scratch for Frontier Vision-Language Models](https://arxiv.org/abs/2501.14818)。

**关键经验：**

- 全部 pad 到最长序列是一个不错的初步做法（但浪费）
- 把 batching 想成一个装箱问题
- 考虑你所有的约束（文本长度、图像显存等）
- 先用玩具数据验证你的方法
