[知识蒸馏](https://arxiv.org/abs/1503.02531)——训练一个更小的学生模型去匹配更大教师模型的性能——是机器学习中一门为人熟知的技术。随着近期开源大语言模型的浪潮，如 [gpt-oss](https://huggingface.co/openai/gpt-oss-120b)、[Qwen](https://huggingface.co/collections/Qwen/qwen35)、[GLM](https://huggingface.co/zai-org/GLM-5.2)、[Kimi](https://huggingface.co/moonshotai/Kimi-K3)，它重新成为主流研究课题。部署这些超大规模模型很贵：最近的 [Kimi-K3 模型](https://huggingface.co/moonshotai/Kimi-K3)有 2.8 万亿参数，仅加载就需要约 3TB 显存。因此，把它们压缩成更小的模型、再靠知识蒸馏找回原始能力，已经成为标准操作——Nvidia（[Nemotron 3 Puzzle 75B](https://huggingface.co/nvidia/NVIDIA-Nemotron-Labs-3-Puzzle-75B-A9B-NVFP4)）和 Multiverse Computing（[Hypernova 60B](https://huggingface.co/MultiverseComputingCAI/Hypernova-60B-2605)）最近都发布了高质量的压缩模型。

蒸馏这一步决定了最终质量的大半，但它通常也是整条流水线中最贵的部分。同时把教师和学生加载在内存里，并对每个 token 在整个词表上产出概率分布，需要海量显存——通常只有几百块 GPU 加上精细的 tensor-parallelism 策略才可行。我们最新的论文 [Efficient Knowledge Distillation for LLMs: Offline Top-K Logits and a Fused Chunked KL Loss](https://huggingface.co/papers/2608.03796) 用两项系统层面的改动来处理这个问题：把教师的 top-K logits 一次性缓存下来，教师就再也不用和学生同驻内存；以及一个新的、内存高效的 KL 散度损失，它从不真正实例化「词表大小 × 序列长度」的完整矩阵，从而把显存用量压到远低于 [PyTorch](https://pytorch.org) 或 [NVIDIA Megatron-Bridge](https://github.com/NVIDIA-NeMo/Megatron-Bridge) 等库默认实现所能达到的水平。这两项改动合在一起，把训练成本削减到足以在单块 GPU 上做长上下文 healing（疗愈），也便宜到大规模实验可以放手去做。

## 蒸馏恢复为什么昂贵

标准做法是用 [Kullback-Leibler 散度损失](https://docs.pytorch.org/docs/2.13/generated/torch.nn.KLDivLoss.html)（KL loss）的*在线（online）*蒸馏，教师和学生同时驻留在内存。每个训练步，教师都要跑一次完整的前向传播产出输出分布，学生则被训练去匹配它。这是表达力最强的设置——完整教师分布随时可用——但也是最耗内存、耗计算的：每个 token 位置要持有两个完整词表张量，而且教师每一步都要重新计算，尽管它的行为在整个训练过程中从不改变。

举个实际的例子：gpt-oss-120b 的词表有 201,088 个 token。在 32K 序列长度、batch size 4 下，仅教师概率张量的形状就是 `4 × 201,088 × 32,768`；用 bfloat16，这一个张量就已约 50GB 显存。再加上梯度、激活、模型权重和优化器状态，蒸馏的一次训练迭代可以峰值冲到约 250GB 显存——比一块 H200 或 B200 能提供的还多。在这篇博文里，我们会展示：把 KL loss 重写为分块（chunk）处理数据，可以把这个成本压到几乎为零。

[![Peak GPU memory over one training iteration at 32K context, comparing dense KL against the fused chunked KL loss](https://cdn-uploads.huggingface.co/production/uploads/668e37fd9c9aa124a3c867e8/-whmAUit96bo1Yy0vLPis.png)](https://cdn-uploads.huggingface.co/production/uploads/668e37fd9c9aa124a3c867e8/-whmAUit96bo1Yy0vLPis.png) *Dense KL 飙到约 250GB，超过单块 H200 的 141GB 容量。fused chunked loss 从不形成这个尖峰，峰值约 128GB。来源：论文 Figure 1。*

## 两项系统改动

**离线（Offline）蒸馏。** 我们不在每一步重算教师，而是只计算一次它的输出，缓存每个位置最可能的 top-100 个 token，然后让学生对着这份缓存训练。教师在训练期间从不需要驻留内存，缓存一旦存在也不必再跑——同一份缓存可以在大量 ablation 实验中反复复用。

**一个 fused、chunked 的 KL loss。** 要看损失本身为什么贵，想象它实际构建了什么东西：对序列中的每个 token 位置和词表中的每个词，损失都需要一个数字来描述学生的预测与教师的预测相差多少。如果铺成一张网格，那就是每个词表条目一行、每个序列位置一列——词表 10 万+、序列又长，这张网格巨大无比，而默认计算 KL loss 的方式是在产出任何一个数字之前把整张网格全部建出来。

我们对比计算同一损失的三种方式——它们在数学上完全等价：

- **Dense KL** 是教科书做法。它从缓存的 top-100 logits 重建一个完整的稠密教师概率网格，与学生自己的稠密 log-概率网格做比较。这是最接近在线蒸馏已有方式的版本，所以我们拿它做正确性基线；但它要把完整的词表 × 序列网格在内存中保存两份。
- **Forward-chunked KL** 让教师保持稀疏（只有每个位置缓存的 top-100 logits，从不展开成稠密网格），并一块一块地计算损失，一次处理一段序列位置。这消除了稠密教师和稠密比较，在我们的基准中是三种方法里最快的。不过它仍有一个盲区：学生自己的 logits——模型输出层产生的那张网格——仍然是完整计算并保留用于反向传播的，所以内存仍随序列长度陡峭增长。
- **Fused chunked KL** 是我们的主要贡献，它更进一步，把模型的输出投影直接融合进损失计算。它从不产出学生的完整 logits 网格：一次端到端地处理一段序列，把该段的 hidden states 投影成 logits、折入累计损失，然后在移到下一段之前丢弃该段。反向传播对每一段即时重算而不是存储。代价是那个投影要做两遍——前向一遍、反向一遍——但换来的是峰值内存只随序列长度线性增长，而不再随完整的词表 × 序列体积出现尖峰。

下面这张 GIF 展示了 dense 与 fused-chunked 两种方式的差异：一个构建完整的比较网格并全部握住不放，另一个一次构建并丢弃一片，因此内存永远不会超过一个 chunk。

## 在实践中这改变了什么

下表把四种设置正面对决：在线蒸馏，以及刚描述的三种离线损失实现。在单块 H200 GPU 上，以 [Llama 3.1 8B Instruct](https://huggingface.co/meta-llama/Llama-3.1-8B-Instruct) 为教师、一个 3.2B 的 Llama 模型为学生，在 8K token 上下文下比较，四种方法都收敛到几乎相同的训练损失——尽管离线训练只是对着每个 token 缓存的 top-100 logits 学习。

| 方法（8K 上下文，单块 H200） | 峰值内存 | 迭代耗时 | 吞吐量 |
| --- | --- | --- | --- |
| Online distillation | 102.8 GB | 25.9 s | 237 TFLOP/s |
| Offline, dense KL | 78.3 GB | 18.5 s | 331 TFLOP/s |
| Offline, forward-chunked KL | 61.8 GB | 18.4 s | 335 TFLOP/s |
| Offline, fused chunked KL | 58.3 GB | 20.2 s | 304 TFLOP/s |

[![Training loss, iteration time and throughput, and peak GPU memory breakdown for online distillation versus the three offline loss implementations, at 8K context on a single H200](https://cdn-uploads.huggingface.co/production/uploads/668e37fd9c9aa124a3c867e8/hV9Hu8he7f1kZJy_SS9X6.png)](https://cdn-uploads.huggingface.co/production/uploads/668e37fd9c9aa124a3c867e8/hV9Hu8he7f1kZJy_SS9X6.png)

四种方法的损失曲线几乎完全重合，证明用 top-100 缓存 logits 的离线蒸馏相对在线蒸馏是无损的。来源：论文 Figure 2。在这个序列长度下，fused chunked loss 还不是最快的选项——它反向传播里多做的投影牺牲了一点速度——但它的真正优势要到上下文变长才显现，下一节会展示。

### 扩展到长上下文

为了更鲜明地看到扩展规律，我们在一个玩具级的输出投影网络上（没有 transformer 主体，只有损失 kernel）跑了隔离基准。在 32K token 时，峰值内存从 dense loss 的 85.2 GiB 降到 fully-chunked 版本的 5.45 GiB，缩小 15.6 倍；而 dense loss 从 64K token 起直接失败。在 256K token 时，fully-chunked loss 用 11.6 GiB，次优的 chunked 变体要 134.2 GiB，且每迭代快约 3.3 倍。

[![Peak VRAM usage by loss](https://cdn-uploads.huggingface.co/production/uploads/614a1ebb8f82f1df64d55126/jsYblMP3R5futGF9Y8Kl1.png)](https://cdn-uploads.huggingface.co/production/uploads/614a1ebb8f82f1df64d55126/jsYblMP3R5futGF9Y8Kl1.png)

在对 GPT-OSS 20B 模型做 32,768 token 上下文的蒸馏时，fused loss 省下的内存让整个设置从四个 GPU 节点缩小到一个。单步时间从 57.0 秒降到 12.23 秒，约快 5 倍；每块 GPU 的吞吐量从 74.2 TFLOP/s 升到 345.7 TFLOP/s。

## 由此而来的学生模型

正是这套高效的离线方案，让大规模蒸馏运动第一次变得负担得起。由此得到的紧凑学生模型——从 Llama 3.1 8B Instruct 蒸馏到约 3.2B 参数——在 BoolQ 和 HellaSwag 上保留了教师的大部分准确率，在 MMLU 上与教师相差不到约九个百分点，而参数量不到一半。

[![Short-context accuracy of the compact 3.2B student against the Llama 3.1 8B Instruct teacher on BoolQ, WinoGrande, MMLU, HellaSwag, and GSM8K](https://cdn-uploads.huggingface.co/production/uploads/614a1ebb8f82f1df64d55126/e0VvKmFktQCyoOhhOTD4n.png)](https://cdn-uploads.huggingface.co/production/uploads/614a1ebb8f82f1df64d55126/e0VvKmFktQCyoOhhOTD4n.png) *学生在不到一半的体积下保留了教师大部分的短上下文准确率。来源：论文 Figure 6。*

这项工作属于 [Multiverse Computing](https://multiversecomputing.com) 持续推进的[让蒸馏与疗愈可规模化运行](https://multiversecomputing.com/compactifai)的研究——不只是一份一次性的配方，而是团队可以低成本反复迭代的东西。论文还涵盖了额外的 ablation，例如损失函数的选择和 sequence packing 如何影响恢复质量。
