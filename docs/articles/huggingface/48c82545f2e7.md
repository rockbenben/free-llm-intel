LLM 已成为构建软件的必备工具。但对 Apple 开发者而言，集成它们仍然痛苦得不必要。

构建 AI 应用的开发者通常采取混合方案，组合使用以下几种方式：

- 使用 Core ML 或 MLX 的本地模型，以获得隐私与离线能力
- 使用 OpenAI 或 Anthropic 等云服务商，以获得前沿能力
- 使用 Apple 的 Foundation Models 作为系统级兜底

每种方式的 API 不同、要求不同、集成模式也不同。事情很多，而且迅速累积。当我访谈开发者关于构建 AI 应用的经历时，模型集成的摩擦立刻被反复提及。一位开发者的话说得很直白：

> 我以为我能快速用官方的 demo 做个测试、也许再搭个糙快猛的构建，
> 结果浪费了太多时间。
> 快把我逼疯了。

试错成本很高，这让开发者很难发现：本地开源模型其实可能非常适合他们的用例。

今天我们发布 [AnyLanguageModel](https://github.com/mattt/AnyLanguageModel)，这是一个 Swift 包，为 Apple 的 Foundation Models 框架提供了支持多种模型提供商的直接替换（drop-in replacement）。我们的目标是降低在 Apple 平台上使用 LLM 的摩擦，让采用本地运行的开源模型更容易。

## 解决方案

核心思想很简单：换一行 `import` 语句，保持同样的 API。

```
- import FoundationModels
+ import AnyLanguageModel
```

实际用起来是这样的。先从 Apple 内置模型开始：

```
let model = SystemLanguageModel.default
let session = LanguageModelSession(model: model)

let response = try await session.respond(to: "Explain quantum computing in one sentence")
print(response.content)
```

再试试通过 [MLX](https://huggingface.co/docs/hub/en/mlx) 在本地运行的开源模型：

```
let model = MLXLanguageModel(modelId: "mlx-community/Qwen3-4B-4bit")
let session = LanguageModelSession(model: model)

let response = try await session.respond(to: "Explain quantum computing in one sentence")
print(response.content)
```

AnyLanguageModel 支持一系列提供商：

- **Apple Foundation Models**：与 Apple 系统模型的原生集成（macOS 26+ / iOS 26+）
- **Core ML**：运行转换后的模型，享有 Neural Engine 加速
- **MLX**：在 Apple Silicon 上高效运行量化模型
- **llama.cpp**：通过 llama.cpp 后端加载 GGUF 模型
- **Ollama**：通过 Ollama 的 HTTP API 连接本地托管的模型
- **OpenAI、Anthropic、Google Gemini**：用于对比和兜底的云服务商
- **Hugging Face Inference Providers**：由世界级[推理提供商](https://huggingface.co/docs/inference-providers/en/index)驱动的数百个云端模型。

重点是你可以从 [Hugging Face Hub](https://huggingface.co/docs/hub/) 下载的本地模型。纳入云服务商是为了降低上手门槛并提供一条迁移路径。先让它跑起来，再做正确的事。

## 为什么以 Foundation Models 作为基础 API

设计 AnyLanguageModel 时我们面临一个选择：造一个新抽象试图囊括一切，还是建立在既有 API 之上。我们选了后者，以 [Apple 的 Foundation Models 框架](https://developer.apple.com/documentation/FoundationModels)为模板。

这看起来可能违反直觉。为什么要绑定 Apple 的选择？理由有几点：

- Foundation Models 确实设计得很好。它利用 Swift 的宏等特性带来顺手的人机工学体验，其围绕会话（session）、工具（tools）与生成的抽象与 LLM 的实际工作方式很好地对应。
- 它是有意受限的。Foundation Models 大致代表了语言模型能力的最低公分母。我们不把这看作弱点，而是把它当作稳定的地基（*hyuk hyuk*）。每个面向 Apple 平台的 Swift 开发者都会接触到这个 API，直接在其上构建意味着更少的概念负担。
- 它让我们保持脚踏实地。每多一层抽象，就离你真正要解决的问题更远。抽象很强大，但堆叠太多本身就成了问题。

结果是：切换提供商只需极少的代码改动，而核心抽象保持干净、可预测。

## Package Traits：只引入你需要的部分

多后端库的一个挑战是依赖膨胀。如果你只想运行 MLX 模型，就不该被迫拉进 llama.cpp 以及*它*的全部依赖。

AnyLanguageModel 用 Swift 6.1 的 package traits 解决这个问题。你只为需要的后端选择加入：

```
dependencies: [
    .package(
        url: "https://github.com/mattt/AnyLanguageModel.git",
        from: "0.4.0",
        traits: ["MLX"]  // Pull in MLX dependencies only
    )
]
```

可用的 traits 包括 `CoreML`、`MLX` 和 `Llama`（用于 llama.cpp / [llama.swift](https://github.com/mattt/llama.swift)）。默认不包含任何重量级依赖。你得到基础 API 加云服务商，后者只需要标准的 `URLSession` 网络能力。

对于 Xcode 项目（目前尚不支持直接声明 trait），你可以创建一个内部的小型 Swift 包，按所需的 traits 依赖 AnyLanguageModel，再把这个包作为本地依赖加入。[README](https://github.com/mattt/AnyLanguageModel#using-traits-in-xcode-projects) 中有详细说明。

## 图像支持（以及 API 设计的取舍）

[视觉语言模型](https://huggingface.co/blog/vlms-2025)非常强大且应用广泛。它们可以描述图像、从截图中提取文字、分析图表、回答关于视觉内容的问题。遗憾的是，Apple 的 Foundation Models 框架目前不支持在提示中附带图像。

建立在既有 API 之上，就意味着接受它的限制。Apple 未来版本很可能会加入图像支持（也许是 iOS 27？），但视觉语言模型太有用了，等不起。所以我们在 Foundation Models 目前提供的能力之外做了扩展。

下面是一个向 Claude 发送图像的示例：

```
let model = AnthropicLanguageModel(
    apiKey: ProcessInfo.processInfo.environment["ANTHROPIC_API_KEY"]!,
    model: "claude-sonnet-4-5-20250929"
)

let session = LanguageModelSession(model: model)
let response = try await session.respond(
    to: "What's in this image?",
    image: .init(url: URL(fileURLWithPath: "/path/to/image.png"))
)
```

这里我们承担了一个经过计算的风险；我们设计的接口可能与 Apple 将来的实现冲突。但弃用警告就是为此存在的。有时候，你必须为一个还不存在的框架先把 API 写出来。

这个应用包括：

它的定位是一个起点：fork 它、扩展它、换用不同的模型。看看各个部分如何拼装，并按你的需求改造。

## 下一步

AnyLanguageModel 目前还处于 1.0 之前。核心 API 是稳定的，但我们正积极把 Foundation Models 的完整特性集带到所有适配器上，具体包括：

- 覆盖所有提供商的**工具调用（tool calling）**
- 面向工具与征求输入（elicitations）的 **MCP 集成**
- 用于结构化输出的**引导生成（guided generation）**
- 本地推理的性能优化

这个库是迈向更大目标的第一步。统一的推理 API 为在 Apple 平台上构建无缝的 agent 工作流提供了必要的脚手架——让模型可以使用工具、访问系统资源、完成复杂任务。更多内容很快见。🤫
