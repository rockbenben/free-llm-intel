## TL;DR

本文介绍 [ModernBERT](https://huggingface.co/collections/answerdotai/modernbert-67627ad707a4acbf33c41deb)——一族 SOTA 的 encoder-only（仅编码器）模型，相比上一代编码器全面升级：**8192** 序列长度、更好的下游任务表现、快得多的处理速度。

ModernBERT 可以直接作为任何 BERT 类模型的 *slot-in*（即插即用）替代品，有 **base**（1.49 亿参数）和 **large**（3.95 亿参数）两种规格。

点击查看如何用 transformers 使用这些模型

ModernBERT 将随 `transformers` v4.48.0 发布。在此之前需要先从 main 分支安装 transformers：

```
pip install git+https://github.com/huggingface/transformers.git
```

ModernBERT 是掩码语言模型（MLM），你可以用 `fill-mask` pipeline，或通过 `AutoModelForMaskedLM` 加载。想把 ModernBERT 用于分类、检索、QA 等下游任务，按标准 BERT 微调流程微调即可。

**⚠️ 如果你的 GPU 支持，我们推荐搭配 Flash Attention 2 使用 ModernBERT 以获得最高效率。安装方式如下，之后正常使用模型即可：**

```
pip install flash-attn
```

使用 `AutoModelForMaskedLM`：

```
from transformers import AutoTokenizer, AutoModelForMaskedLM

model_id = "answerdotai/ModernBERT-base"
tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForMaskedLM.from_pretrained(model_id)

text = "The capital of France is [MASK]."
inputs = tokenizer(text, return_tensors="pt")
outputs = model(**inputs)

# To get predictions for the mask:
masked_index = inputs["input_ids"][0].tolist().index(tokenizer.mask_token_id)
predicted_token_id = outputs.logits[0, masked_index].argmax(axis=-1)
predicted_token = tokenizer.decode(predicted_token_id)
print("Predicted token:", predicted_token)
# Predicted token:  Paris
```

使用 pipeline：

```
import torch
from transformers import pipeline
from pprint import pprint

pipe = pipeline(
    "fill-mask",
    model="answerdotai/ModernBERT-base",
    torch_dtype=torch.bfloat16,
)

input_text = "He walked to the [MASK]."
results = pipe(input_text)
pprint(results)
```

**注意：**与现代某些 BERT 模型不同，ModernBERT 不使用 token type IDs。除可以省略 `token_type_ids` 参数外，大多数下游用法与 Hugging Face Hub 上的标准 BERT 模型完全相同。

## 引言

[BERT](https://huggingface.co/papers/1810.04805) 发布于 2018 年（按 AI 纪年已经是几千年前了！），但至今仍被广泛使用：事实上，它目前是 [HuggingFace hub](https://huggingface.co/models?sort=downloads) 上下载量第二高的模型，月下载量超过 6800 万次，仅次于[另一个为检索微调过的编码器模型](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2)。这是因为它的*仅编码器架构*特别适合每天遇到的那类现实问题：检索（比如 RAG）、分类（比如内容审核）、实体抽取（比如隐私与监管合规）。

终于，6 年后，替代品来了！今天，我们在 [Answer.AI](http://Answer.AI) 和 [LightOn](https://www.lighton.ai/)（以及朋友们！）发布 ModernBERT。ModernBERT 是一个全新模型系列，在**速度**和**准确率**上对 BERT 及其后辈做出了帕累托改进（Pareto improvement，全面占优）。这个模型吸收了近年大语言模型（LLM）研究中的几十项进展，把它们应用到 BERT 风格的模型上，包括架构和训练过程的更新。

[![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/modernbert/modernbert_pareto_curve.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/modernbert/modernbert_pareto_curve.png)

我们预期 ModernBERT 会在使用仅编码器模型的众多应用中成为新标准，比如 RAG（检索增强生成）管道和推荐系统。

除了更快、更准，ModernBERT 还把上下文长度提高到 8k token（多数编码器只有 512），并且是第一个在训练数据中包含大量代码的仅编码器模型。这些特性打开了此前开源模型无法触及的新应用领域：大规模代码搜索、新的 IDE 功能，以及基于整文档检索（而非小碎片）的新型检索管道。

不过要讲清楚我们做了什么，得先回头看看我们从哪里来。

## 仅解码器模型

近年备受瞩目的 LLM 进展发生在 [GPT](https://huggingface.co/openai-community/openai-gpt)、[Llama](https://huggingface.co/meta-llama)、[Claude](https://www.anthropic.com/claude) 这类模型上。它们是*仅解码器模型*，也就是生成式模型。它们生成类人内容的能力催生了生成艺术、交互式聊天等惊人的 GenAI 新应用。这些引人注目的应用吸引了大量投资、支撑了蓬勃的研究、带来了快速的技术进步。我们做的事情，本质上就是把这些进展移植回一个仅编码器模型。

为什么？因为很多实际应用需要**精干**又**强悍**的模型！而且它不必是生成式模型。

更直白点：对很多工作来说，仅解码器模型*太大*、*太慢*、*闭源*、*太贵*。想想最初的 [GPT-1](https://huggingface.co/openai-community/openai-gpt) 只有 1.17 亿参数，而 [Llama 3.1](https://huggingface.co/meta-llama/Llama-3.1-405B) 有 4050 *亿*参数，其技术报告里的数据合成与整理配方复杂昂贵到多数公司无法复制。所以要用上这样的模型（比如 ChatGPT），你得按美分付费、按秒等待，从你控制不了的重型服务器拿回一个 API 响应。

当然，这些巨型生成模型的开放能力意味着紧急情况下也能把它们按进非生成式的*判别式*任务，比如分类。因为你可以用 plain English 描述一个分类任务，然后……直接让模型分类就行。但这个工作流适合做原型，量产阶段谁也不想付原型的价格。

围绕 GenAI 的喧嚣掩盖了*仅编码器模型*的角色。它们才是实际语言处理的主力，是此时此刻众多科研与商业应用真正跑在生产负载上的模型。

## 仅编码器模型

仅编码器模型的输出是一列数值（一个*嵌入向量*，embedding vector）。可以说，编码器模型不用文本回答，而是把"答案"原样*编码*成这种压缩的数值形式。这个向量是模型输入的压缩表示，所以仅编码器模型有时也被称为*表示型模型*（representational models）。

虽然仅解码器模型（如 GPT）也能干仅编码器模型（如 BERT）的活，但它们被一个关键约束捆住了手脚：作为*生成式模型*，它们在数学上"不许""偷看"后面的 token，只能*向后看*。这与仅编码器模型相反——后者**从训练之初就让每个 token 可以同时向前*和*向后看（双向）**。它们就是为这个而造的，所以干起这活来特别高效。

基本上，OpenAI 的 O1 这样的前沿模型就像一辆法拉利 SF-23。它是显而易见的工程胜利，生来为赢比赛，所以我们才谈论它。但光换轮胎就得一支专门的维修团队，而且你有钱也买不到一辆。相比之下，BERT 模型像一辆本田思域。它*也*是工程胜利，只是更低调——*它*的设计目标是买得起、省油、可靠、极其有用。所以它们无处不在。

从好几个角度都能看到这一点。

***支撑生成式模型***：理解表示型模型（仅编码器）有多普及的一个角度，是看它们与仅解码器模型配合构建安全高效系统的频率。

最明显的例子是 RAG。系统不依赖训练进 LLM 参数里的知识，而是用文档库为 LLM 提供与查询相关的信息。但这当然只是把问题往前推了一步：如果 LLM 不知道哪些文档与查询相关，那系统得靠别的流程来挑选文档。它需要一个足够快、足够便宜的模型，把让 LLM 有用所需的海量信息编码起来——这个模型往往就是 BERT 类的仅编码器模型。

另一个例子是监督架构（supervision architectures）：用一个便宜的分类器确保生成文本不违反内容安全要求。

总之，每当你看到一个仅解码器模型上线部署，大概率有一个仅编码器模型也是系统的一部分。反过来则不成立。

***基于编码器的系统***：在 GPT 出现之前，社交媒体和 Netflix 这样的平台就有内容推荐；这些地方以及搜索等场景里有广告投放定向；还有用于垃圾检测、滥用检测等的内容分类。这些系统不是建立在生成式模型上，而是建立在表示型模型——仅编码器模型上。而这些系统至今仍在，仍在以巨大规模运行。想象一下全世界每秒有多少广告被定向投放！

***下载量***：在 HuggingFace 上，基于 BERT 的领先模型之一 [RoBERTa](https://huggingface.co/FacebookAI/roberta-base) 的下载量超过了 HuggingFace 上最受欢迎的 10 个 LLM 之和。事实上，当前仅编码器模型每月合计下载量超过 10 亿次，几乎是仅解码器模型（3.97 亿月下载）的三倍。更具体地说，`fill-mask` 模型类别——由 ModernBERT 这类可供下游微调的编码器"基座模型"组成——是下载量最大的模型类别。

***推理成本***：上面这些说明，按单次推理计，每年在仅编码器模型上跑的推理次数比仅解码器/生成式模型多好几倍。一个有趣的例子是 [FineWeb-Edu](https://huggingface.co/spaces/HuggingFaceFW/blogpost-fineweb-v1)，需要对 15 万亿 token 做基于模型的质量过滤。FineWeb-Edu 团队选择用仅解码器模型 [Llama-3-70b-Instruct](https://huggingface.co/meta-llama/Meta-Llama-3-70B-Instruct) 生成标注，而用[一个微调过的基于 BERT 的模型](https://huggingface.co/HuggingFaceFW/fineweb-edu-classifier)执行绝大部分过滤。这次过滤花了 6000 个 H100 小时，按 [HuggingFace Inference Endpoints](https://huggingface.co/pricing) 每小时 10 美元的价格，总共 6 万美元。另一方面，把 15 万亿 token 喂给热门的仅解码器模型，即使选最便宜的 [Google Gemini Flash（推理成本低至每百万 token 0.075 美元）](https://ai.google.dev/pricing#1_5flash)，也要超过 100 万美元！

## 性能

### 概览

下面是 ModernBERT 与其他模型在一系列任务上的准确率快照，以标准学术基准衡量——可以看到，ModernBERT 是唯一一个**在每个类别都拿最高分**的模型，这让它成为你的所有编码器任务可以共用的那一个模型：

[![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/modernbert/modernbert_accuracy_table.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/modernbert/modernbert_accuracy_table.png)

如果你参加过 [Kaggle](https://www.kaggle.com/) 上的 NLP 比赛，就会知道 [DeBERTaV3](https://huggingface.co/microsoft/deberta-v3-base) 多年来是冠军们的首选。但现在不了：ModernBERT 不仅是第一个在 GLUE 上击败 DeBERTaV3 的 base 规模模型，内存占用也不到 DeBERTa 的 **1/5**。

当然，ModernBERT 很快。它的速度是 DeBERTa 的**两倍**——在更常见的混合长度输入情况下，实际上快达 **4 倍**。在长上下文推理上，它的速度接近 [NomicBERT](https://huggingface.co/nomic-ai/nomic-bert-2048) 和 [GTE-en-MLM](https://huggingface.co/Alibaba-NLP/gte-en-mlm-base) 等其他高质量模型的 **3 倍**。

ModernBERT 8192 token 的上下文长度是现有大多数编码器的 **16 倍**以上。这非常关键，比如在 RAG 管道中，上下文太小会让切片小到无法承载语义理解。配合 [ColBERT](https://huggingface.co/colbert-ir/colbertv2.0)，ModernBERT 也是长上下文检索的 SOTA，比其他长上下文模型高 9 个百分点。更 impressive 的是：这个训练非常赶、只为对比骨干（backbone）而调优的模型，在长上下文任务上甚至超过了广泛使用的检索模型！

代码检索方面，ModernBERT 是独一份。真的没什么可对比的，因为从来没有一个像它这样在大量代码数据上训练过的编码器模型。例如在 [StackOverflow-QA 数据集（SQA）](https://www.kaggle.com/datasets/imoore/60k-stack-overflow-questions-with-quality-rate)——一个代码与自然语言混合的数据集——上，ModernBERT 专业的代码理解能力和长上下文能力让它成为此任务上唯一得分超 80 的骨干模型。

这意味着很可能有全新的应用将建立在这一能力上。比如，想象一个 AI 联网的 IDE，用 ModernBERT 嵌入索引整个企业代码库，在所有仓库中快速进行跨仓库代码的长上下文检索。或者一个代码聊天服务，解释一个横跨数十个项目的功能是如何工作的。

与主流模型相比，ModernBERT 在检索、自然语言理解、代码检索三大任务类别上几乎全面更强。虽然在一个领域（自然语言理解）略逊于 [DeBERTaV3](https://huggingface.co/microsoft/deberta-v3-base)，但速度快得多。请注意，ModernBERT 和其他基座模型一样，开箱只能做掩码词预测。要执行其他任务，应像这些[模板代码](https://github.com/AnswerDotAI/ModernBERT/tree/main/examples)里那样微调基座模型。

与专用模型相比，ModernBERT 在多数任务上不相上下或更强。而且 ModernBERT 在多数任务上比多数模型更快，能处理最长 8192 token 的输入，比主流模型长 16 倍。

### 效率

以下是 ModernBERT 与其他 decoder 模型在 NVIDIA RTX 4090 上的内存（最大 batch size，BS）和推理（千 token/秒）效率结果：

[![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/modernbert/modernbert_efficiency_table.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/modernbert/modernbert_efficiency_table.png)

你可能首先注意到，我们是在一块买得起的消费级 GPU 上分析效率，而不是最新最难抢的网红硬件。**ModernBERT 首先关注的是实用性，不是炒作。**

这一取向也意味着我们确保 ModernBERT 在真实应用中表现良好，而不只是刷榜。这类模型通常只在其最擅长的单一尺寸——最大上下文长度——上测试，这就是表中"fixed"列显示的内容。但现实世界中输入长度是变化的，所以我们努力优化的正是这种性能——"variable"列。可以看到，对于变长输入，ModernBERT 比其他所有模型都快得多。

对于长上下文输入——我们相信这是未来最有价值应用的基石——ModernBERT 比速度第二快的模型快 **2-3 倍**。并且从"实用性"维度看：ModernBERT 不需要额外的笨重依赖 [xformers](https://github.com/facebookresearch/xformers)，只依赖如今已普及的 [Flash Attention](https://github.com/Dao-AILab/flash-attention)。

此外，得益于 ModernBERT 的效率，它能用几乎比其他任何模型都大的 batch size，能有效运行在更小更便宜的 GPU 上。base 规模的效率尤其可能催生直接在浏览器、手机上运行的新应用。

## ModernBERT 凭什么"Modern"？

前面我们论证了为什么**应该**给编码器模型更多关爱。作为可靠但被低估的苦力，它们自 2018 年 BERT 以来的更新少得惊人！

更惊讶的是：自 RoBERTa 以来，没有任何编码器能在不做取舍（即所谓 "***帕累托改进***"）的情况下提供全面进步：DeBERTaV3 的 GLUE 和分类性能更好，但牺牲了效率和检索。其他模型，如 [AlBERT](https://huggingface.co/albert/albert-base-v2)，或较新的 GTE-en-MLM，都只在某些方面超过原版 BERT 和 RoBERTa，在另一些方面反而退步。

然而自这对组合最初发布以来，我们关于如何构建更好的语言模型已经学到了太多。如果你用过 LLM，你一定深有体会：*帕累托改进*在解码器的世界里是常态——模型在方方面面持续变强——而在编码器的世界里却很罕见。而且如我们所见：模型进步一小半是魔法，一大半是工程。

所以（但愿名副其实）ModernBERT 项目的目标相当简单：把现代工程带给编码器模型。我们从三个核心方面入手：

- **现代化的 transformer 架构**
- **对效率的格外关注**
- **现代化的数据规模与来源**

### New Transformer, Same as the Old Transformer

Transformer 架构已经一统天下，如今绝大多数模型都在用它。但要记住，*Transformer* 不止一种。它们的共同点是深信 attention is indeed all you need，并围绕注意力机制构建各种改进。

ModernBERT 大量借鉴了 Transformer++（这个说法源自 [Mamba](https://arxiv.org/abs/2312.00752)），最早由 [Llama2 模型家族](https://arxiv.org/abs/2307.09288)使用。具体来说，我们把 BERT 类的老组件换成其改进版：

- 把老式位置编码替换为["旋转位置嵌入"](https://huggingface.co/blog/designing-positional-encoding)（RoPE）：让模型更好地理解词与词之间的位置关系，并允许我们扩展到更长的序列。
- 把旧的 MLP 层换成 GeGLU 层，优于原版 BERT 的 GeLU 激活函数。
- 精简架构，去掉不必要的 bias 项，把参数预算花在刀刃上。
- 在嵌入之后增加一层归一化，帮助稳定训练。

### 给本田思域做赛道改装

前面说过：编码器不是法拉利，ModernBERT 也不例外。但这不代表它不能快。上高速时，你一般不去换一辆赛车，而是希望日常可靠的座驾能舒舒服服跑满限速。

事实上，对我们上面提到的所有应用场景，速度都至关重要。编码器常用于两种情形：要么处理海量数据——哪怕一点点提速都会迅速累积成巨大收益；要么延迟极其敏感——RAG 就是如此。很多场景下编码器甚至在 CPU 上运行，这时要想在合理时间内拿到结果，效率就更重要了。

和研究中的多数事情一样，我们站在巨人的肩膀上构建，大量借力 Flash Attention 2 的速度提升。我们的效率改进依赖三大支柱：**交替注意力**（Alternating Attention）提升处理效率、**去填充与序列打包**（Unpadding and Sequence Packing）减少计算浪费、**硬件感知的模型设计**（Hardware-Aware Model Design）最大化硬件利用率。

#### 全局注意力与局部注意力

ModernBERT 最有影响力的特性之一是**交替**注意力，而非全程全局注意力。技术上讲，我们的注意力机制每 3 层才对完整输入做一次全局注意（**global attention**，全局注意力），其余各层使用滑动窗口，每个 token 只关注离它最近的 128 个 token（**local attention**，局部注意力）。
由于注意力的计算复杂度随 token 数不断膨胀，这意味着 ModernBERT 处理长输入序列的速度比任何其他模型都快不少。

实际效果是这样：
[![](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/modernbert/modernbert_alternating_attention.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/modernbert/modernbert_alternating_attention.png)

从概念上讲，这招有效的原因很简单：想象你在读书。读的每一个句子，你真的需要时刻掌握整本书的剧情才能理解吗（**全全局注意力**）？还是了解当前章节通常就够了（**局部注意力**），只需要偶尔回想它与主线的关联（**全局注意力**）？绝大多数情况下是后者。

#### 去填充与序列打包

另一个支撑 ModernBERT 效率的核心机制是去填充（Unpadding）与序列打包（Sequence packing）。

要让更多序列在同一 batch 内处理，编码器模型要求它们*长度相同*，以便并行计算。传统做法靠 **padding**：找出最长的那句，把其他序列都用无意义 token（*padding token*）补齐。

padding 解决了问题，但解决得不优雅：大量算力被花在不对语义做任何贡献的 padding token 上。

padding 与序列打包对比。序列打包（"去填充"）避免在 padding token 上浪费算力，并且每个 batch 的有效 token 数更稳定。样本仍通过精心设计的 mask 被独立处理。

**去填充**解决了这个问题：我们不再保留 padding token，而是全部移除，把序列拼接成 batch size 为 1 的小批次，避免一切不必要的计算。如果你在用 Flash Attention，我们的去填充实现甚至比以前的方法更快——以往方法严重依赖序列在模型各层间反复去填充再填充：我们更进一步，引入了自己的去填充实现，深度依赖 Flash Attention 在 RoPE 支持上的最新进展。这让 ModernBERT 只需去填充一次，处理完可以选择性地重新填充，比之前的方法快 10-20%。

为了让预训练更快，去填充在我们模型中并不孤单——它还配合了**序列打包**。序列打包是顺理成章的下一步：既然我们在把输入拼接成单个序列，而 GPU 极擅长并行化，就要榨干单次前向计算能提供的计算效率。为此我们用贪心算法把单个序列分组拼接，让拼接结果尽可能贴近模型的最大输入长度。

#### 关注硬件

最后，ModernBERT 效率的第三块是硬件设计。

我们试图平衡此前研究强调的两个洞见：

- *深而窄 vs 宽而浅*：[研究表明](https://arxiv.org/abs/2109.10686)，层数更深、每层更窄的模型往往比层数少但更宽层的浅模型表现更好。但这是把双刃剑：模型越深，可并行度越低，同等参数量下跑得越慢。
- *硬件效率*：模型维度需要与 GPU 硬件良好对齐才能达到最佳性能，而不同的目标 GPU 会带来不同的约束。

遗憾的是，没有让同一个模型在各种 GPU 上都跑得同样好的神奇配方，但有一本绝佳的食谱——[*The Case for Co-Designing Model Architectures with Hardware*](https://arxiv.org/abs/2401.14489)，其中细致列出了针对特定 GPU 优化模型架构的方法。我们提出一个启发式，把他们的方法扩展到一组 GPU，同时满足给定的约束。合乎逻辑的第一步是先定义约束，对我们来说是：

- 目标 GPU 定义为常见推理卡（RTX 3090/4090、A10、T4、L4）
- 目标模型规模大致为 ModernBERT-Base 1.3-1.5 亿参数、ModernBERT-Large 3.5-4.2 亿参数。
- 最终嵌入维度必须与原 BERT 一致（base 为 768、large 为 1024），以最大化向后兼容性
- 设置在这组 GPU 上通用的性能约束

之后，我们通过受限网格搜索试验了多种模型设计，调整层数和层宽。一旦确定似乎最高效的形状，我们验证启发式与真实 GPU 性能相符，最终敲定模型设计。

*把那个经典场面在脑子里过一遍，把 Developers 换成 Data*

编码器落后的另一个大方面是训练数据。这通常被理解为训练数据**规模**的问题，但实际并非如此：以前的编码器，如 DeBERTaV3，训练时间足够长，甚至可能已经突破了万亿 token 大关！

真正的问题在训练数据的**多样性**：许多老模型只在有限语料上训练，通常就是 Wikipedia 和 Wikibooks。这些数据配比**单一文本模态**得非常明显：里面只有高质量自然文本。

相比之下，ModernBERT 训练数据来自多样的英文来源，包括网页文档、代码和科学论文。它在 **2 万亿 token** 上训练，其中大部分是唯一的，而不是以往编码器常见的重复 20-40 遍。

影响立竿见影：在所有现有开源编码器中，ModernBERT 在编程相关任务上独一档。我们特别期待这会带来哪些下游应用，尤其是在改进编程助手方面。

#### 流程

我们沿用原版 BERT 的训练配方，并参考后续工作做了小幅升级：移除 Next-Sentence Prediction 目标（后来的研究证明它只增加开销、没有明显收益），并把掩码率从 15% 提高到 30%。

两个模型都按**三阶段流程**训练。首先以 1024 序列长度训练 1.7 万亿 token。然后进入长上下文适应阶段，以 8192 序列长度训练 2500 亿 token，通过降低 batch size 让每个 batch 的总 token 数大致保持一致。最后在另行采样的 500 亿 token 上做退火（annealing），遵循 [ProLong](https://arxiv.org/abs/2410.02660) 推荐的长上下文扩展理想配比。

三阶段训练是我们确保模型全面在线的方式，结果也印证了这点：它在长上下文任务上有竞争力，同时丝毫不牺牲短上下文处理能力……

……还有另一个好处：前两个阶段在 warmup 结束后使用恒定学习率，只在最后 500 亿 token 上做学习率衰减，采用梯形（即 Warmup-Stable-Decay）学习率。而且：受 [Pythia](https://arxiv.org/abs/2304.01373) 启发，我们将发布这些稳定阶段的每一个中间检查点。这么做的主要原因是支持未来的研究与应用：**任何人都可以从我们的任意退火前检查点重新继续训练，并按其用途在合适领域的数据上做退火**！

#### 技巧，全靠技巧！

读到这里，你应该已经习惯了：当然，我们在提速上也有技巧。准确说，我们有两个主要技巧。

先看第一个，挺常见的：由于训练初期更新的是随机权重，我们采用 **batch size warmup（批大小预热）**：一开始用小 batch size，让同样数量的 token 更频繁地更新模型权重，然后逐步增大到最终训练规模。这显著加速了模型学习语言基本认知的初始阶段。

第二个技巧就罕见得多：**大模型通过平铺（tiling）做权重初始化**，灵感来自微软的 [Phi](https://azure.microsoft.com/en-us/products/phi) 模型家族。依据的是这个领悟：既然有一套现成的（我们自夸一点）ModernBERT-base 权重闲着，为什么要用随机数初始化 ModernBERT-large 的初始权重？

事实上，把 ModernBERT-base 的权重平铺到 ModernBERT-large 上确实比从随机权重初始化更好。它还有一个额外好处：与 batch size warmup 叠加，让初始训练更快。

本文介绍了 ModernBERT 模型——一族全新 SOTA 的小型高效仅编码器模型，终于给了 BERT 一次急需的重制机会。

ModernBERT 证明仅编码器模型可以用现代方法做得更好。它们在某些任务上持续提供非常强的表现，拥有极具吸引力的规模/性能比。
