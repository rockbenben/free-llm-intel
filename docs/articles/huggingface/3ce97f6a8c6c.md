# 原生速度的 vLLM Transformers 建模后端

Harry Mellor (hmellor)

Lysandre (lysandre)

**TL;DR**：transformers 的 vLLM 后端如今在许多 LLM 架构上已经和 vLLM 自定义实现一样快（甚至更快）。模型作者可以直接让自己的 transformers 实现自动获得极速的 vLLM 推理，而且零成本。

```
# Upgrade the vllm pip package
uv pip install --upgrade vllm --torch-backend auto
```

transformers 库已成为机器学习的**参考建模库**。它通过一致的 API 支持 450 多种架构，设计上最重要的目标是模型实现要*自包含*、*易于理解*。读 transformers 代码让人容易搞懂一个架构如何工作，然后再把它移植到 vLLM、SGLang、MLX、llama.cpp 等其他框架。

我们完全承担起了这一生态角色，并投入大量精力让这件事更容易。朝着这个方向迈出的重要一步，是去年把 transformers 集成为 vLLM 的建模后端。这让模型作者可以把 transformers 模型（LLM 和 VLM 都行）跑在 vLLM 里，什么都不用移植：transformers 提供建模代码，vLLM 提供极致优化的推理技术，如连续批处理（continuous batching）和自定义注意力 kernel。

这个集成现在更好了 🚀！

## 实测展示

我们把 vLLM 的 transformers 建模后端与 vLLM 手写的原生实现正面对比，覆盖三个差异很大的 Qwen3 模型：

- 4B 稠密模型，单 GPU
- 32B 稠密模型，张量并行（tensor parallelism）
- 2350 亿参数 FP8 MoE（Mixture-of-Experts，专家混合）模型，在同一个 8×H100 节点上数据并行 + 专家并行

| [![Pre and Post PR benchmarks with trasnformers vllm backend](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-backend/pre-post-pr.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-backend/pre-post-pr.png) |
| --- |
| 结果：transformers 建模后端在每一项测试中都**追平或超过**了原生实现的吞吐。 |

通过 transformers 建模后端运行任意* Hugging Face 模型只需一个标志——`--model-impl transformers`。它与常规的并行选项可以自由组合，你的服务部署方式完全不用变：

```
# Qwen3-4B dense, single GPU
vllm serve Qwen/Qwen3-4B --model-impl transformers

# Qwen3-32B dense, tensor-parallel across 2 GPUs
vllm serve Qwen/Qwen3-32B --model-impl transformers --tensor-parallel-size 2

# Qwen3-235B-A22B-FP8 MoE, data-parallel + expert-parallel across 8 GPUs
vllm serve Qwen/Qwen3-235B-A22B-FP8 --model-impl transformers --data-parallel-size 8 --enable-expert-parallel
# add --max-model-len 8192 if your node is memory constrained
```

**使用线性注意力（linear attention）的模型目前尚不支持，但很快会支持！代码托管在 Hub 仓库里的自定义模型大概率无法工作，因为其代码未必按合规方式编写。*

### 我们怎么测的

每个模型在三种条件下对比，除代码路径外其他设置完全相同：

- **native** — `--model-impl vllm`，vLLM 手写模型（要对标的标杆）
- **after** — `--model-impl transformers` *带*该 PR
- **before** — `--model-impl transformers` *不带*该 PR

完整、可复现的运行脚本以 gist 形式提供：[`benchmark.sh`](https://huggingface.co/datasets/ariG23498/useful-scripts/blob/main/transformers-backend-vllm-benchmark.sh)

## 那么，新在哪？

vLLM 的 transformers 建模后端过去只关注*注意力*——把它当作推理瓶颈。通过在运行时接入 vLLM 的注意力实现，我们能让 transformers 模型高效跑在 vLLM 引擎里。但影响部署性能的维度很多，只有自定义移植才能逐一施展以榨取最大推理性能：跨 GPU 并行化、编译、融合 kernel 等等，都会影响你能从硬件中挖出的推理速度上限。

| 过去新模型要为 transformers 集成一次，再为 vLLM 用自定义优化实现一次 |

模型作者想要极致性能时，仍然得自己写 vLLM 的自定义实现。

| [![New model integrates to transformers, and is immediately available to vLLM](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-backend/current-pipeline.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/vllm-backend/current-pipeline.png) |

vLLM 的 transformers 建模后端最新版本会在运行时动态施加推理专用的层融合（layer fusion），以追平自定义代码实现的速度——前提是架构兼容。

## 它是怎么工作的？

vLLM 的 transformers 建模后端现在使用 `torch.fx` 对模型计算图做静态分析。这一过程会搜索可优化的已知模式，识别出模式后，用 ast（抽象语法树，abstract syntax tree）操纵源代码，就地重写部分操作。

**这能带来什么？**

- 多对一映射到（超）优化 vLLM kernel 的融合操作，例如 Mixture-of-Experts（MoE）模型专家并行（EP）所用的 kernel。
- 其余主要融合操作是 vLLM 的 `MergedColumnParallelLinear` 和 `QKVParallelLinear`。这些模块让我们能推断出张量并行（TP）的并行方案。若 decoder 层列表易于识别，还能推断出流水线并行（PP）方案。
- 被改写后的模型仍然完全可 (torch) 编译——照常经过 `torch.compile` 和 CUDA Graphs，与专门的 vLLM 模型实现无异。
- 与 vLLM 模型实现不同，Transformers 模型实现可以用于**训练**。所以同一套模型代码可以用于训练/评估/RL rollout。

如上所示，这让兼容模型直接获得 vLLM 原生推理速度，而无需为推理优化写一行代码。
