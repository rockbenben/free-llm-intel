# 用机器学习帮助幸存者并与时间赛跑

merve

Alara Dirik（adirik）

2023 年 2 月 6 日，土耳其东南部发生 7.7 级和 7.6 级地震，波及 10 座城市；截至 2 月 21 日，已造成超过 42000 人遇难、12 万人受伤。

地震发生几小时后，一群程序员建起了一个 Discord 服务器，着手推出一个名为 *afetharita*（字面意思"灾害地图"）的应用。这个应用服务于搜救队和志愿者，帮他们找到幸存者并送去救助。之所以需要这样的应用，是因为幸存者们在社交媒体上发帖——截图里写着自己的地址和需求（包括求救信息）；也有人直接发推说明自己需要什么，好让亲人知道自己还活着、需要救援。要从这些推文里抽取信息，我们开发了多个应用把它们变成结构化数据，在与时间赛跑中完成开发和部署。

我被拉进 Discord 服务器时，关于志愿者如何运作、要做什么都还相当混乱。我们决定协作训练模型，于是需要一个模型和数据集的登记处。我们开通了 Hugging Face 组织账号，通过 pull request 协作，构建基于 ML 的信息接收与处理应用。

[![organization](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/org.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/org.png)

其他团队的志愿者告诉我们，现在需要一个应用：能发布截图、从截图里提取文字、把文字结构化，再把结构化信息写进数据库。我们开始开发这样一个应用：接收图片、先提取文字，再从文字中抽取姓名、电话和地址，写入最终要交给官方的数据库。试了各种开源 OCR 工具后，OCR 部分选用了 `easyocr`，界面用 `Gradio` 搭建。期间我们又受托为 OCR 单独做一个应用，于是从界面里开出了 API 端点。OCR 输出的文本由一个基于 transformers 微调的 NER 模型解析。

[![OCR](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/ocr-app.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/ocr-app.png)

为了协作改进这个应用，我们把它托管在 Hugging Face Spaces 上，并拿到了一份 GPU 赞助让应用持续运行。Hugging Face Hub 团队还给我们配了一个 CI 机器人，提供临时环境，让我们能看到每个 PR 会对 Space 产生什么影响，在 PR review 时帮了大忙。

之后，我们拿到了来自渠道（如 twitter、discord）的已标注内容，包含幸存者求助的原始推文，以及从中抽取的地址和个人信息。我们一方面尝试对闭源模型做 few-shot 提示，一方面用 transformers 微调自己的 token 分类模型。token 分类的基座模型选了 [bert-base-turkish-cased](https://huggingface.co/dbmdz/bert-base-turkish-cased)，做出了第一个地址抽取模型。

[![NER](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/deprem-ner.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/deprem-ner.png)

这个模型后来被 `afetharita` 用于抽取地址：解析出的地址会发给地理编码 API 换取经纬度，位置随后显示在前端地图上。推理方面我们用了 Inference API——一个托管模型做推理的 API，模型推到 Hugging Face Hub 上就自动启用。用它来做服务，省掉了拉模型、写应用、构建镜像、配置 CI/CD、部署到云端实例这一整套——对 DevOps 和云团队来说这本来是额外负担。Hugging Face 团队还给了我们更多副本（replicas），保证零停机，让应用足以扛住大流量。

[![backend_pipeline](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/production_pipeline.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/production_pipeline.png)

后来我们又接到需求：能否从一条推文里抽取幸存者需要什么？拿到的数据是多标签的——一条推文可能有多种需求，比如庇护所、食物或物流（当地天寒地冻）。我们先尝试用 Hub 上的开源 NLI 模型做 zero-shot，再用闭源生成模型端点做 few-shot。试过的模型有 [xlm-roberta-large-xnli](https://huggingface.co/joeddav/xlm-roberta-large-xnli) 和 [convbert-base-turkish-mc4-cased-allnli_tr](https://huggingface.co/emrecan/convbert-base-turkish-mc4-cased-allnli_tr)。NLI 模型特别好用：可以直接拿候选标签做推断，数据漂移时换标签即可；生成模型则可能凭空造标签，给后端返回时造成不匹配。最初我们没有标注数据，所以什么方案都得能跑。

最终我们决定微调自己的模型，因为在单张 GPU 上微调 BERT 的分类头大约只要三分钟。为训练它，我们组织了一轮标注做出数据集。实验结果都记录在模型卡的 metadata 里，之后我们据此搭了一个排行榜，用来决定该把哪个模型部署到生产。基座模型方面，试过 [bert-base-turkish-uncased](https://huggingface.co/loodos/bert-base-turkish-uncased) 和 [bert-base-turkish-128k-cased](https://huggingface.co/dbmdz/bert-base-turkish-128k-cased)，发现它们比 [bert-base-turkish-cased](https://huggingface.co/dbmdz/bert-base-turkish-cased) 表现更好。排行榜在[这里](https://huggingface.co/spaces/deprem-ml/intent-leaderboard)。

[![intent_model](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/model-repo.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/model-repo.png)

考虑到任务本身和数据类别的不平衡，我们把重点放在消除假负例上，并建了一个 Space 来对所有模型的召回率和 F1 做基准。为此我们给所有相关模型仓库加上 metadata 标签 `deprem-clf-v1`，用这个标签自动抓取记录的 F1 和 recall 分数并给模型排名。我们还准备了独立的基准集，避免对训练集造成数据泄漏，并持续为模型做基准；同时对每个模型逐一测试，找出部署时每个标签的最佳阈值。

我们希望 NER 模型也能被评估，于是众包了这个工作——因为标注团队正忙着给我们产出更好、更新的意图数据集。为了评估 NER 模型，我们用 `Argilla` 和 `Gradio` 搭了一个标注界面：人们可以输入一条推文，把模型输出标记为正确/错误/存疑。

[![active_learning](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/active-learning.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/active-learning.png)

之后这份数据集被去重，用于对我们的后续实验做基准。

机器学习的另一个团队则用生成模型（在受控 API 后面）把具体需求以自由文本形式提取出来（因为标签太宽泛），再把这段文本作为附加上下文写进每条发布内容。为此他们做了提示词工程，把 API 端点包装成另一个独立 API 部署在云上。我们发现，在数据快速漂移的情况下，借助 LLM 做 few-shot 提示能很好适配细粒度需求——要调整的只有提示词本身，而且不需要任何标注数据。

这些模型目前已在生产环境中使用，生成下面这张热力图里的点位，供志愿者和搜救队把物资送到幸存者手中。

[![afetharita](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/afetharita.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/afetharita.png)

我们深切体会到：没有 Hugging Face Hub 和整个生态，我们不可能这么快完成协作、原型和部署。下面是地址识别与意图分类模型的 MLOps 管线。

[![mlops](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/pipeline.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/pipeline.png)

这个应用和它的各个组件背后，是数十位志愿者，他们彻夜未眠，才在这么短的时间内把它做出来。

## 遥感应用

另有团队从事遥感应用，评估建筑与基础设施受损情况，为搜救行动指明方向。震后头 48 小时停电、移动通信网络不稳定，加上道路塌毁，让评估灾情范围和确定救援重点变得极其困难。由于通讯和交通不畅，倒塌和受损建筑的误报也严重干扰了搜救行动。

为解决这些问题、并为未来沉淀可复用的开源工具，我们从 Planet Labs、Maxar 和 Copernicus Open Access Hub 收集了受灾区域的震前与震后卫星影像。

[![input_satellite](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/output_satellite.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/output_satellite.png)

最初的做法是快速为卫星影像做目标检测和实例分割标注，只设"建筑"一个类别。思路是对比同一区域震前震后影像中仍然存立的建筑数量，从而评估损毁程度。为了让模型更好训练，我们先把 1080x1080 的卫星图裁成 640x640 的小块。接着为建筑检测微调了 [YOLOv5](https://huggingface.co/spaces/deprem-ml/deprem_satellite_test)、YOLOv8 和 EfficientNet 模型，为建筑的语义分割微调了 [SegFormer](https://huggingface.co/spaces/deprem-ml/deprem_satellite_semantic_whu) 模型，并把这些应用部署为 Hugging Face Spaces。

[![app](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/app.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/app.png)

依然是数十位志愿者参与标注、准备数据、训练模型。除了个人志愿者，像 [Co-One](https://co-one.co/) 这样的公司也志愿为卫星数据做标注，对建筑和基础设施给出更细的标签，包括 *no damage*（无损）、*destroyed*（摧毁）、*damaged*（受损）、*damaged facility*（受损设施）和 *undamaged facility*（完好设施）。我们当前的目标是发布一个大规模开源数据集，未来能在全球范围内加快搜救行动。

[![output_satellite](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/processed_satellite.jpeg)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/disaster-assets/processed_satellite.jpeg)

## 写在最后

在这个极端场景里，我们必须快，必须在分类指标上抠到 1% 的提升都值得争取。过程中有过许多伦理讨论——连"优化哪个指标"本身都是一个伦理问题。我们亲眼看到开源机器学习和"技术平权"如何让个人也能做出救命的产品。感谢 Hugging Face 背后的社区发布这些模型和数据集，也感谢 Hugging Face 团队在基础设施和 MLOps 上的支持。
