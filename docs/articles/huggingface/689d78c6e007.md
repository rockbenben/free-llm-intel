**我们正在加入在 transformers 中高效运行 GGUF 模型的支持**，这样你就能通过熟悉的 transformers API 使用按笔记本内存大小挑选的 checkpoint。从 Hub 上挑一个 GGUF，用 `from_pretrained` 加载它，就能在你自己的机器上开始生成。

在笔记本上跑 AI 模型已经容易了很多，[llama.cpp](https://github.com/ggml-org/llama.cpp) 在其中扮演着重要角色。它的推理引擎为 Ollama、LM Studio、Jan 这类本地 AI 工具提供支撑。和 [MLX](https://github.com/ml-explore/mlx) 这样的项目一起，它们让本地推理成了日常可用的一种务实选择。

**GGUF** 由 llama.cpp 团队开发，是本地推理中使用广泛的格式。该团队也在 Hub 上以 [ggml-org](https://huggingface.co/ggml-org) 的名义分享量化 checkpoint。[Unsloth](https://huggingface.co/unsloth)、[LM Studio Community](https://huggingface.co/lmstudio-community) 和 [bartowski](https://huggingface.co/bartowski) 等发布者也提供覆盖多种量化程度、开箱即用的 GGUF checkpoint，用户可以挑出适合自己机器的那个版本。GGUF 模型已被下载数百万次。

我们也想让「用 transformers 在本地跑这些模型」同样轻松。只有跑起来顺手的模型，兼容性才有意义。为了把性能做到接近 llama.cpp，我们通过 [`kernels`](https://huggingface.co/docs/kernels/index) 库复用它底层的 ggml kernel，并降低 `generate` 的开销。我们最初的重心是 Apple Silicon 上的本地推理，从 Qwen3.5 架构起步。

## GGUF 文件格式是什么

[GGUF](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md) 把模型权重和元数据——包括 tokenizer 信息以及一个可选的 chat template——打包进一个文件。它支持不同的量化等级，让你用一部分精度换取更小的内存占用。`Q4_K_M` 这类变体会混合张量精度，大部分权重用 4-bit，同时把敏感的张量保留在更高精度。

量化对 [Unsloth 的 Qwen3.5-4B](https://huggingface.co/unsloth/Qwen3.5-4B-GGUF/tree/main) 文件大小的影响如下：

| GGUF 变体 | 文件大小 | 取舍 |
| --- | --- | --- |
| `BF16` | 8.42 GB | 未量化的参照 |
| `Q6_K` | 3.53 GB | 精度高于更小的变体 |
| `Q5_K_M` | 3.14 GB | 大小与精度之间的折中 |
| `Q4_K_M` | 2.74 GB | 本地推理一个实用的起点 |

我们建议从 `Q4_K_M` 起步，如果你有更多可用内存，再试 `Q5_K_M` 或 `Q6_K`。更激进的量化能让更大的模型塞得下，但质量上的取舍取决于模型和任务。请在你的模型实际要做的工作上评测它。[Hub 的 GGUF 文档](https://huggingface.co/docs/hub/gguf#quantization-types)描述了可用的量化类型。

## 用 transformers 加载 GGUF

开始之前你需要：

- **一台 Apple Silicon Mac**。
- **一个被已发布的 [ggml-quantization kernel 构建](https://huggingface.co/kernels/ggml-org/ggml-quantization) 所支持的 PyTorch 版本**，通常是最近的两个 PyTorch 发行版。
- **最新版本的 transformers（在下一次发布之前暂时用 main 分支）以及兼容版本的 `kernels`**。

```
pip install -U "git+https://github.com/huggingface/transformers.git" kernels
```

要加载一个 GGUF 模型，把它的 Hub `model_id` 和文件名作为 `gguf_file` 传给 `from_pretrained`。

不需要额外配置：当权重以打包形式留在 Metal 上时，transformers 会自动加载兼容的 ggml/Metal 层 kernel，并用 `ggml-org/ggml-attn` 作为 attention 实现。如果那个 kernel 拉取不到，模型会带警告地退回 `"sdpa"`；你也始终可以通过显式传入 `attn_implementation="sdpa"` 来强制使用 `"sdpa"`。更多加载选项见 [GGUF 文档](https://huggingface.co/docs/transformers/main/en/quantization/gguf)。

```
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "unsloth/Qwen3.5-4B-GGUF"
filename = "Qwen3.5-4B-Q4_K_M.gguf"

tokenizer = AutoTokenizer.from_pretrained(model_id, gguf_file=filename)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    gguf_file=filename
)
```

这是唯一一步 GGUF 特有的操作。之后的都是标准 transformers API：

```
messages = [{"role": "user", "content": "Explain why the sky is blue in a few sentences."}]
inputs = tokenizer.apply_chat_template(
    messages,
    tokenize=True,
    add_generation_prompt=True,
    return_dict=True,
    return_tensors="pt",
).to(model.device)

with torch.inference_mode():
    outputs = model.generate(**inputs, max_new_tokens=256)

print(tokenizer.decode(outputs[0], skip_special_tokens=True))
```

> 若没有兼容的量化 kernel，加载器会退回到把模型反量化，从而占用更多内存。

## 用你偏好的接口对外提供 GGUF 服务

你也可以用 [`transformers serve`](https://huggingface.co/docs/transformers/main/en/serve-cli/serving) 使用同一个 checkpoint，它对外暴露一个 OpenAI 兼容的 API：

```
pip install -U "transformers[serving] @ git+https://github.com/huggingface/transformers.git" kernels

transformers serve "unsloth/Qwen3.5-4B-GGUF:Qwen3.5-4B-Q4_K_M.gguf"
```

模型参数使用 `<model_id>:<filename>.gguf` 形式：冒号之前是 Hub 仓库（`unsloth/Qwen3.5-4B-GGUF`），之后是要加载的文件（`Qwen3.5-4B-Q4_K_M.gguf`）。这用于在可能含有多个量化版本的仓库里选定某一个具体量化。

对于 chat template 支持 thinking 的模型，加上 `--reasoning off` 可跳过它，加上 `--reasoning on` 可启用它。默认值 `--reasoning auto` 沿用 chat template 的默认设置。细节见 [reasoning 选项](https://huggingface.co/docs/transformers/main/en/serve-cli/serving#enable-reasoning-on-the-server)。

你可以把 [Jan](https://www.jan.ai/docs/desktop/remote-models/custom-endpoint) 或 [Pi](https://pi.dev) 这类客户端连上来：新增一个自定义的 OpenAI 兼容 provider，并使用这些设置：

| Setting | Value |
| --- | --- |
| Base URL | `http://localhost:8000/v1` |
| Model ID | `unsloth/Qwen3.5-4B-GGUF:Qwen3.5-4B-Q4_K_M.gguf` |

transformers 在你的 Mac 上运行模型，客户端则提供对话界面。其他支持这一 API 的客户端也可以用同一个 endpoint。

## 与 llama.cpp 的基准对比

本地推理性能的参照对象是 llama.cpp。下面的对比聚焦三个 GGUF checkpoint：一个小的 dense 模型、一个更大的 dense 模型，以及一个 mixture-of-experts 模型。

llama.cpp 那一列来自 [`llama-bench`](https://github.com/ggml-org/llama.cpp/tree/master/tools/llama-bench) 工具（构建 `5f55650a7`，发行版 b10200，Metal backend 来自 ggml 0.18.0），以 `llama-bench -m <file> -p 0 -n 128 -r 3` 运行，报告的是 `tg128`：在 128 个解码 token 上的 token 生成速率，取三次重复的平均值，不含 prompt 处理。transformers 那一列是 `generate` 从一个 12 token 的 prompt 生成同样 128 个 token，取三次预热运行中最好的一次，并且包含 prefill。

测量环境：MacBook Pro M2 Max，32 GB 统一内存，macOS 26.6，PyTorch 2.12.1，kernels 0.17.0，插电运行。

基准脚本

```
import time
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id, filename = "unsloth/Qwen3.5-4B-GGUF", "Qwen3.5-4B-Q4_K_M.gguf"

model = AutoModelForCausalLM.from_pretrained(model_id, gguf_file=filename)
tokenizer = AutoTokenizer.from_pretrained(model_id, gguf_file=filename)
inputs = tokenizer("The capital of France is Paris. The capital of Germany is", return_tensors="pt")
inputs = inputs.to(model.device)


with torch.inference_mode():
    model.generate(**inputs, max_new_tokens=8, min_new_tokens=8, do_sample=False)  # warm up
    torch.mps.synchronize()
    for _ in range(3):
        time.sleep(90)  # let the machine cool: back-to-back runs decay by 10% or more
        start = time.perf_counter()
        model.generate(**inputs, max_new_tokens=128, min_new_tokens=128, do_sample=False)
        torch.mps.synchronize()
        print(f"{128 / (time.perf_counter() - start):.1f} tok/s")
```

另一列则用：

```
llama-bench -hf unsloth/Qwen3.5-4B-GGUF:Q4_K_M -p 0 -n 128 -r 3
```

[![与 llama.cpp 对比的 GGUF 生成吞吐量](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/transformers-llama-cpp-quants/benchmark-comparison.svg)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/transformers-llama-cpp-quants/benchmark-comparison.svg)

## transformers 与 llama.cpp

在 [GGML 与 llama.cpp 加入 Hugging Face](https://huggingface.co/blog/ggml-joins-hf) 时，我们描述过两者互补的角色：llama.cpp 为本地推理提供底座，transformers 为模型定义提供底座。GGUF 支持让这两者靠得更近。

**当你的首要目标是高效的本地推理时，llama.cpp 仍然是我们推荐的引擎。**它专属的 runtime、内存管理以及对广泛硬件的支持都是围绕这个目标构建的。这次集成为开发者提供了一条在 transformers 里使用同一批 GGUF checkpoint 的便捷途径：

- **在 Python 和 PyTorch 里试验 GGUF。**用 hook 检查中间激活，修改模型的 forward pass，或者用熟悉的 PyTorch 工具为自定义 layer 做原型。
- **评测 GGUF 模型。**用你现有的 transformers 评测流程来度量量化 checkpoint 的质量。
- **校验 GGUF 转换。**对我们这些开发者来说，在 transformers 里同时加载原始 checkpoint 和它转换出的 GGUF，更容易确认权重被正确转换，并把量化误差算在内。
- **尝试新的解码思路。**给 `generate` 配上自定义的 logits processor 和停止准则，或者用 Python 写你自己的生成循环。
- **从 GGUF checkpoint 开始 fine-tuning。**把权重反量化，然后按标准 transformers 训练流程继续。

最后这种情况，使用 `GgufConfig(dequantize=True)`：

```
import torch
from transformers import AutoModelForCausalLM, GgufConfig

model = AutoModelForCausalLM.from_pretrained(
    "unsloth/Qwen3.5-4B-GGUF",
    gguf_file="Qwen3.5-4B-Q4_K_M.gguf",
    quantization_config=GgufConfig(dequantize=True),
    dtype=torch.bfloat16,
)
```

## 走出 GGUF：用 ggml kernel 覆盖更多模型

**更大的机会在于把 ggml 的性能带给 llama.cpp 并不支持的模型。**

transformers 已经提供了这些架构的 PyTorch 实现。有了在 PyTorch 中可用的 ggml kernel 和量化方案，我们可以着手加速它们已支持的操作，而不必先把整个模型在 llama.cpp 里实现一遍。这对新架构、研究模型和自定义变体尤其有用——它们也许永远不会有一个专门的 llama.cpp 实现。

这个机会并不局限于 GGUF 格式本身。kernel 作用在张量上，它并不要求整个模型都来自一个 GGUF 文件。同样的积木可以被集成进其他 transformers 模型和加载流程。这也为其他模态开出了一条路：计算机视觉模型、音频模型和多模态模型都可以复用兼容的 attention、normalization 与矩阵乘法 kernel，而不必先在 llama.cpp 里有完整实现。每个架构仍然需要集成与验证；本文最初这些 GGUF 示例覆盖的是文本生成。

## 用 Python 和 PyTorch 做快速的本地推理

我们还想展示：在把模型和生成循环都留在 Python 里的前提下，我们能走多远。**配上合适的 kernel 和高效的生成循环，Python 和 PyTorch 也能给出很强的本地推理性能。**kernel 承担繁重的计算，生成循环则通过避免不必要的同步让 GPU 一直有活可干。

我们的重心是让 eager 执行在不要求 `torch.compile` 的情况下也足够快。就交互式使用而言，我们希望启动快、token 稳定流出，没有编译造成的停顿，也没有输入形状变化时的重新编译。这项工作主要有两块：kernel，以及 `generate` 本身。

### 复用 ggml 的 Metal kernel

kernel 就是在 GPU 上执行某个操作的小程序。PyTorch 提供的是通用实现；一个专门的 kernel 可以做更少的工作、把若干操作合并，或者按存储格式直接读取量化后的权重。

`kernels` 库让我们把 ggml 的 Metal kernel 的兼容构建分发在 Hub 上，并从 transformers 调用它们。这就把 ggml 的成果带进 PyTorch 模型，而不需要用一套独立的推理 runtime 把模型替换掉。

| Kernel | 作用 |
| --- | --- |
| [`ggml-quantization`](https://huggingface.co/kernels/ggml-org/ggml-quantization) | 为矩阵运算读取打包的量化权重，包括 MoE 模型中选中的 expert。它避免了在每次解码操作之前把整个权重矩阵展开。 |
| [`ggml-norm`](https://huggingface.co/kernels/ggml-org/ggml-norm) | 融合 normalization 操作，包括 Qwen3.5 与 Qwen3.8 使用的零居中 RMSNorm。 |
| [`ggml-attn`](https://huggingface.co/kernels/ggml-org/ggml-attn) | 为 prompt 处理和 token 解码提供 ggml 的 Metal flash attention。 |
| [`ggml-gated-delta-net`](https://huggingface.co/kernels/ggml-org/ggml-gated-delta-net) | 加速 Qwen3.5 与 Qwen3.8 混合架构中 linear-attention 层所用的 gated delta network。 |
| [`topk`](https://huggingface.co/kernels/transformers-community/topk) | 为 MoE 模型中每个 token 挑选 expert，把 softmax 与 top-k 路由合为一体。这是我们自己的 Metal 实现。 |

前四个包都建立在 ggml 的 kernel 之上；top-k kernel 处理的是 MoE 路由中另一个独立的瓶颈。它们一起降低了每生成一个 token 所需的 GPU 工作量。

为了说明层 kernel 的贡献，我们在启用与不启用它们两种情况下对比同一批打包的 GGUF checkpoint。量化 kernel 在两种配置里都保持启用：把它关掉同时也会改变权重的表示方式，那测量的就是另一种取舍了。

[![层 kernel 带来的吞吐量提升](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/transformers-llama-cpp-quants/layer-kernel-benchmark.svg)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/transformers-llama-cpp-quants/layer-kernel-benchmark.svg)

### 让 CPU 和 GPU 持续协同工作

只有当 GPU 有活可干时，更快的 kernel 才有帮助。生成过程中，CPU 负责调度 GPU 操作，并控制产出下一个 token 的循环。从 GPU 读回结果可能迫使 CPU 等待到排队的操作完成。哪怕每个 token 只多等很小一会儿，也会明显拉低吞吐量。

`generate` 里有两处改动针对这一点，它们给所有 transformers 模型都带来提升（不只是在跑 GGUF 文件时）：

- **[尽早丢弃多余的 attention mask（#48814）](https://github.com/huggingface/transformers/pull/48814)。**当某个受支持的 decoder-only 输入不含 padding 时，那份全 1 的 padding mask 可以在生成开始时就移除。下游 attention 代码不再需要反复检查这份 mask 来判断它是否可以跳过。causal attention 依然保留。
- **[推迟停止检查（#47975）](https://github.com/huggingface/transformers/pull/47975)。**在受支持的路径上，`generate` 异步复制停止判定，并在下一步消费它。GPU 运行时 CPU 可以继续调度工作。流式输出 token 采用同样的做法，越过停止条件的那一步会从结果中被剔除。

这些改动改善的是模型外围的生成循环，所以它们的用处不限于 GGUF。它们与 kernel 工作互为补充：kernel 降低一次操作的成本，而更少的同步点让 CPU 调度与 GPU 执行得以重叠。

[![生成循环改动带来的吞吐量提升](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/transformers-llama-cpp-quants/generation-loop-benchmark.svg)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/transformers-llama-cpp-quants/generation-loop-benchmark.svg)

这些测量把所有层 kernel 都保持在启用状态；图中的柱形只隔离出生成循环那部分的改动。

## 当前限制与后续步骤

最初的目标是 Apple Silicon 上的单场交互式对话。有几个边界需要留意：

- **打包推理路径目前仅支持 MPS。**通过反量化导入 GGUF 仍然是一个独立的选项；支持这个文件格式，并不意味着打包 kernel 在每种设备上都可得。
- **padding 与批量处理仍有待改进。**未做 padding 的输入能受益于上文描述的 mask 优化。带 padding 的批次无法走同样的捷径，性能可能更低。我们希望把这项工作扩展到 MPS 上的 `generate_batch`。
- **架构覆盖有限。**打包加载器目前覆盖 Qwen3.5 的 dense 与 MoE 架构，包括兼容的 Qwen3.8 checkpoint。为其他架构添加支持相对直接，我们会逐步扩大覆盖面。

如果你有一个想在 transformers 里使用的 GGUF 模型，请[提一个 issue](https://github.com/huggingface/transformers/issues)，附上该 checkpoint 和你的使用场景。这会帮助我们安排优先级，先支持人们正在本地运行的那些模型。
