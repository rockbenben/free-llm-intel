# 在考虑 ACE？我们可以用更少的 token 做到

*ALTK-Evolve 和 ACE 都让智能体从自己的轨迹中学习。区别在于它们如何运用学到的东西——而这一点决定了 token 账单。*

给 LLM 智能体一个真实的多步任务——拆分账单、找一首歌、在九个模拟应用间核对一张订单——它失败时，通常不是因为缺乏知识。它会把 API 翻页翻错、认错人、或在没人要求的情况下返回一个值。模型是懂这些 API 的；它没有内化的是*如何可靠地使用它们*。而这恰恰可以从智能体自己的历史中学到。

最近的两个系统做的正是这件事，作用在同一种智能体上：[**ACE**](https://arxiv.org/abs/2510.04618)（Agentic Context Engineering）和我们的 **ALTK-Evolve**（[介绍见这里](https://huggingface.co/blog/ibm-research/altk-evolve)）。两者都是**智能体记忆（agentic memory）**的一种形式——把智能体过去的轨迹转化为可复用的**经验教训（lessons）**，在推理时回灌，无需更新权重、无需人工标注。它们甚至对难点的判断都一致。分道扬镳的地方是*交付方式*。

先说明一下用词，因为两个系统的命名不同：我们把智能体学到的原始东西称为一条 **lesson（经验教训）**。ACE 把它的 lessons 组织进一份全面、不断演化的 **playbook（行动手册）**；我们则把自己的整合成一条条可独立检索的 **guidelines（准则）**。同样的 lessons，两种容器。

## 我们的共识

两个系统都拒绝压缩。

ACE 精准地点名了失败模式：**简洁偏差（brevity bias）**——优化过程坍缩向简短、泛化的指令；以及**上下文崩塌（context collapse）**——被要求每步重写全部上下文的模型会把细节摘要掉。它的解法是保留一份丰富的、逐条罗列的 playbook，每个条目带有益/有害计数器，让模型在读取时自行提炼相关性。

我们从另一个方向得出同样结论。每条不同的 guideline 都带一个 **support count（支持计数）**——它由多少个独立 episodes 产生——我们从不把整个记忆库摘要成寥寥几条规则。被五个不同任务各自发现的 lesson，和只出现过一次的 lesson 是两个不同的对象，都值得保留。

所以在核心问题上——*该不该把智能体辛苦换来的 lessons 压缩成一份整洁的摘要？*——ACE 和 ALTK-Evolve 给出同一个答案：**不。数着它们，别塌缩它们。**ACE 的逐条计数器和我们的 support counts 是同一思想的不同写法。

## 我们的分歧

分歧在两处：记忆如何**构建**，以及如何**交付**——而体现在 token 账单上的，正是交付方式的差异。

**整合（记忆库如何构建）。** ACE 通过 **Generator → Reflector → Curator** 循环生长出一份 playbook，施加增量 delta 更新、按 embedding 去重。我们则把近似重复的 lessons 聚簇并在簇*内部*合并，**支持计数守恒（support-conserving）**——多条 lesson 合并时，幸存条目继承它们的合并计数，于是记忆库变小却不丢失"每条 guideline 背后有多少经验"的记录。我们还抽取*带类型*的 guidelines——策略（strategy）、恢复（recovery）、优化（optimization）——带因果归因和回指来源轨迹的出处，并做到子任务粒度，使在一个应用上学到的 lesson 能迁移到另一个应用。

**交付（推理时送到模型面前的是什么）。** 这才是驱动数字的那一项。ACE 每一步都注入**整本 playbook**，不论模型、不论任务都一样。我们把交付做成一个可调的旋钮而不是常数：一小簇固定高支持度的核心 guidelines，再为当前任务补充挑选出的少量条目（cosine 或 LLM 引导、按优先级加权）——或者，当模型有余力利用时，交付整合后的完整集合。同样的 lessons 对两个智能体都*可用*；区别在于 ACE 永远全量发送，而我们发送某个模型实际能用上的数量。

## 为什么重要

在 AppWorld 上，用*同一个*基座 ReAct 智能体，两个系统都由我们在内部复跑：

| 模型 |  | TGC / SGC | Tokens/任务 |
| --- | --- | --- | --- |
| **DeepSeek-V3.2** | ACE | 80.4 / 73.2 | 634K |
|  | **ALTK-Evolve** | **89.3 / 80.4** | **263K** |
| **gpt-oss-120b** | ACE | 54.8 / 35.7 | 777K |
|  | **ALTK-Evolve** | **56.0 / 37.5** | **116K** |

在强模型上，我们在两项指标上都更好，而推理成本只有 **ACE 的约 40%**。在弱模型上，我们以 56.0 对 54.8 险胜 ACE——接近于**准确率平手**（我们重跑一次得到 54.8，几乎与 ACE 完全一致，在这类基准的单次运行波动范围内）——而成本约为**七分之一**。

关于成本要说句公道话：ACE 自己的效率叙事是关于*构建*上下文的低成本。我们在另一条轴上——*服务（serving)*。每任务检索少量 guidelines，而不是每一步注入整本 playbook，token 就是这么省下来的，这正是上面交付差异的直接结果。

准确率从哪来？按难度拆开看，是两个不同的故事：

[![image](https://cdn-uploads.huggingface.co/production/uploads/6435a1131860001f144239ea/RlNmW6Vps10XLGW4DuJQh.png)](https://cdn-uploads.huggingface.co/production/uploads/6435a1131860001f144239ea/RlNmW6Vps10XLGW4DuJQh.png)

*图 1. 加入记忆后按难度划分的 Task Goal Completion，我们 vs. ACE。在 DeepSeek-V3.2（右）上我们赢下 Easy、Hard 和 Overall；ACE 只在 Medium 略优。在 gpt-oss-120b（左）上 ACE 领先 easy 和 medium，但按任务选择在 hard 任务上胜出——也包括总分。两个系统都相对各自的无记忆基线有提升（见下方 Method notes 里的按难度参照表）。*

两个模型各讲各的故事。在 gpt-oss-120b 上，ACE 的整本 playbook 在 Easy 和 Medium 上占优——任务里有足够多的部分靠泛化指令跟随就能解决，全面的提示帮忙多于干扰。但在 Hard 任务上，模型必须挑出*对的* lesson 而不能全部硬翻，精心检索开始领先——而这一档恰恰决定总分。在 DeepSeek-V3.2 上故事反转：更强的模型能良好吸收 ACE 的整本 playbook，在 Medium 上略胜我们，但我们在 Easy、Hard、Overall 领先——容量更富余时，更多的 lessons（以我们的方式交付）持续帮忙，而不是互相挤兑。

我们给每个模型配其**最佳配置**——强模型用整合后的完整集合，弱模型用选择性检索，因为大上下文对弱模型是淹没而非帮助。（到底该注入*多少*、它如何随能力谱系伸缩，是我们[**后续文章**](https://huggingface.co/blog/ibm-research/altk-evolve-hmm/)的主题。）

## 同样的 lessons，不同的交付

两个系统都拒绝把智能体辛苦积累的经验压缩成整洁摘要——这一点我们是一致的。区别在于交付是固定的还是校准过的：ACE 无论如何每一步发送整本 playbook；我们发送某个模型实际能用上的 guideline 数量。正是这种校准买来了上面的数字——以 ACE 一小部分的推理成本换同等甚至更好的准确率——而在较弱模型上，它决定了指导是帮忙还是添乱。

## 方法说明

AppWorld `test_normal`，168 个任务。一个 ReAct 代码智能体（每步写 Python，环境返回输出）。**TGC** = Task Goal Completion；**SGC** = Scenario Goal Completion，要求场景的*每个*变体都通过。记忆仅从 **train/dev** 挖掘；结果为单次运行（pass@1），这是该基准的惯例。

ACE 的数字是我们自己运行 ACE 智能体的结果，在与 ALTK-Evolve 相同的 AppWorld 切分和相同基座模型（DeepSeek-V3.2 和 gpt-oss-120b）上内部评估。ACE 论文报告用的是另一个基座模型（DeepSeek-V3.1），因此我们自己复跑能让模型与运行框架保持一致。两个系统是*同一个* ReAct 智能体，仅在提示模板上有差异——这也是为什么两个无记忆基线不同（TGC 72.0 vs 79.8）；我们的比较不建立在这个基线差上，只建立在改提示无法触及的结论上：以一小部分的 token 达到同等或更好的准确率。
