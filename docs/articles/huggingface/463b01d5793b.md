# vLLM V0 到 V1：在 RL 中先谈正确性，再谈纠正

[PipelineRL](https://huggingface.co/blog/ServiceNow-AI/github.com/ServiceNow/PipelineRL/) 使用 vLLM 作为 rollout 生成的推理引擎。推理引擎采样 token 并返回 token logprob；训练器用这些 logprob 来计算策略比率、KL、裁剪率、熵和奖励。这些 logprob 计算方式上的任何差异都可能改变训练动态。这就是我们在 vLLM V0 到 V1 迁移期间需要消除的训练-推理失配。

**TL;DR。** 在修复了四样东西之后，vLLM V1 匹配上了我们的 vLLM V0 参考：处理后的 rollout logprob、V1 特有的运行时默认值、inflight 权重更新路径，以及用于最终投影的 fp32 `lm_head`。我们在改动 RL 目标之前先修复了后端行为。

参考运行使用 vLLM `0.8.5`；V1 运行使用 vLLM `0.18.1`。图 1 展示了最终结果。红色运行是初次 V1 尝试，绿色运行是在下述修复之后的最终 V1 运行。

图 1. vLLM V0 参考（蓝色）、初次 vLLM V1 尝试（红色），以及经过我们修复（含 fp32 lm_head）后的最终 vLLM V1 运行（绿色）的训练器侧指标。最终 V1 运行在裁剪率、KL、熵和奖励上都回到了接近 V0 轨迹的位置。

## 迁移目标

vLLM V1 是对 V0 引擎的一次大规模重写。因此我们的迁移目标刻意保持狭窄：

- 验证 V1 以训练器期望的形式返回 rollout logprob
- 针对 V0 参考重新运行同一负载
- 仅在后端对等性恢复之后才评估目标级的改动

最初可见的症状出现在：

- `clamp_log_ratio_new_old_indicator`
- `kl_new_old`
- `entropy`
- `reward`

这些指标来自一次 GSPO 训练运行，即本实验所用的目标。同一类失配也可能出现在 PPO、GRPO，或任何把 rollout 侧 logprob 当作优化目标一部分的在线 RL 系统中。

初次 V1 运行清楚地暴露了问题。训练器侧的 logprob 和奖励在训练早期就偏离了 V0 参考。

图 2. 训练器在更新期间计算的当前策略 logprob（左）和奖励（右）。初次 vLLM V1 运行（红色）从 vLLM V0 参考（蓝色）分离开来。

同样的模式出现在训练器指标中。裁剪率是初次对比中最容易解读的信号。

图 3. vLLM V0 参考（蓝色）和初次 vLLM V1 尝试（红色）的训练器侧指标。裁剪率跟踪 rollout/训练器策略之间的差距；熵和奖励展示了这一差距如何传播进训练。

## 失败模式

我们把可能的原因分成三层：

- **语义失配**：后端返回的 logprob 相对于训练器所期望的具有不同含义。
- **推理路径失配**：后端对缓存、调度或请求处理使用不同的运行时默认值，使得相同的提示走了一条不同的执行路径。
- **目标失配**：RL 目标需要针对剩余的陈旧度或后端失配量做纠正。

我们一开始过早就怀疑了第三类。有用的诊断来自把前两类当作后端行为问题并先行排除它们。

## V1 后端修复

### Logprob 语义

第一个问题是语义层面的。vLLM V1 默认从原始模型输出返回 logprob，即在 logits 后处理（例如温度缩放、惩罚、top-k/top-p 过滤）之前。PipelineRL 期望的是采样器所用的处理后分布的 logprob。

所需的设置是：

- `logprobs-mode=processed_logprobs`

这消除了 rollout logprob 中明显的均值偏移。训练曲线相对已知良好的参考仍有差距，所以下一个问题必定在推理路径上。

策略比率图直接展示了这一点。一旦为 V1 打开 `processed_logprobs`，均值策略比率在所有三次运行中都保持在极接近 `1.0` 的中心位置。这就确立了均值偏差的修复。剩余的失配体现在裁剪率、KL、熵以及下游训练行为上。

图 4. 对 vLLM V0 参考（蓝色）、初次 vLLM V1 运行（红色）和修正后的 vLLM V1 运行（绿色），rollout/训练器策略比率相对 1.0 的逐步偏差，乘以 10000 缩放。

### 运行时默认值

早期的 V1 运行把引擎版本与 V1 运行时默认值混在了一起：

- 前缀缓存（prefix caching），在早期运行中未设置，因而 vLLM `0.18.1` 的默认值生效
- 异步调度（async scheduling），在早期运行中未设置，因而 vLLM `0.18.1` 的默认值生效
- 一个临时的 `disable-cascade-attn` 覆盖，通过启动时的 kwarg 透传设置，位于已提交配置的对等配方之外

对于对等运行，我们把这些选择显式化：

```
vllm_config:
  use_v1: true
  vllm_kwargs:
    logprobs-mode: processed_logprobs
    enable-prefix-caching: false
    async-scheduling: false
```

前缀缓存值得单独一提。对于固定的模型状态，它通常是一个保持正确性的推理优化。在这个在线 RL 设置中，它是一项相对 V0 参考路径而言 V1 独有的、关于缓存生命周期和复用的差异。而且 actor 还在处理重复前缀、并发请求、异步调度和 inflight 权重更新。

当缓存策略忽略权重更新边界时，一次前缀缓存命中可能复用在权重更新之前计算的状态。禁用前缀缓存从对等比较中移除了一个 V1 独有的自由度。

### Inflight 权重更新

权重同步也必须匹配在线 RL 的更新模型。一个选项是让 V1 比 V0 更严格，在每次更新时排空请求并清空缓存。那会回答另一个问题。我们首先需要验证 V1 能否匹配现有的 V0 行为。

V0 实际所做的更接近于：

- 在引擎边界阻塞执行
- 加载新权重
- 不进行显式缓存状态失效地恢复

最接近的 V1 对应做法是：

```
await engine.pause_generation(mode="keep", clear_cache=False)
await engine_client.collective_rpc_async(
    "receive_weight_update",
    args=(request.model_dump_json(),),
)
await engine.resume_generation()
```

两个细节重要：

- `mode="keep"` 比 `wait` 或 `abort` 更紧密地匹配旧的 inflight 更新模型
- `clear_cache=False` 匹配 V0 包装器行为，它在更新时保留缓存状态不变

滞后（lag）是一个有用的运行时诊断。初次 V1 路径在训练后期比修正后的 V1 运行携带更多持续滞后。

## 剩余的差距：fp32 lm_head

上述 V1 后端修复消除了明显的迁移问题，但最终对等性仍要求匹配用于计算 logits 的数值路径。训练器使用一个 fp32 `lm_head` 做最终投影。rollout 后端必须匹配这一行为。

一个密切相关的问题出现在 [MiniMax-M1 技术报告](https://arxiv.org/abs/2506.13585)中：他们的 RL 运行显示出一种训练/推理的 token 概率失配，他们把它追溯到 LM 输出头，并通过以 fp32 计算该头来修复。

这很重要，因为 RL 更新直接消耗 token logprob。logits 的微小变化可能在策略比率、KL 和裁剪中变得可见。因此最终投影精度是在线 RL 正确性面的一部分。[ScaleRL 论文](https://arxiv.org/abs/2510.13786)后来在其 RL 配方中纳入了 fp32 logits/头计算作为一部分，并将它作为一个对大规模 RL 有用的设计选择做了消融。

在纳入 fp32 `lm_head` 路径之后，奖励给出最终对等结果的一个紧凑视图。在图 6 中，最终 V1 运行跟踪 V0 参考；初次 V1 尝试产生了一条明显不同的奖励曲线。

## 消融

负面结果很重要，因为它们排除了常见的解释。

- **仅 `processed_logprobs`**：修复了语义 logprob 的 bug；训练失配依然存在。
- **批不变性（batch invariance）**：在一个独立测试中失配依然存在，且伴随更高滞后、更高裁剪率和 NCCL 上的麻烦。
- **把初次 V1 运行当作公平基线**：初次 V1 运行启用了多个 V1 独有默认值，因此它是一个被混淆的迁移比较。

## 为什么我们先修复后端正确性

目标侧的纠正——例如截断重要性采样、重要性比率重加权及相关方法——是有用的工具。如果 rollout 是刻意陈旧的、异步生成的，或由一个无法保证与训练器侧策略等价的后端生成的，那么某种形式的纠正通常是该加的东西。

这里的首要问题是推理正确性。迁移到 V1 之后，rollout 后端返回破坏了训练器假设的 logprob 和运行时行为。在彼时添加一个目标侧纠正会把两个问题混在一起：

- 推理后端是否在产出正确的 logprob？
- 给定正确的 logprob，目标是否仍需要一个离策略或异步的纠正？

这些问题需要被分开。否则一个目标侧纠正可能掩盖了坏掉的推理后端行为，这让训练曲线更难解读。

当前目标仍可改善。在推理对等性恢复之后，下一个改进是常规的异步/离策略清理：

- 保留来自 rollout 时刻的显式行为策略 logprob
- 在优化时刻重算训练器侧旧策略 logprob
- 把后端失配纠正与策略更新比率分离开
- 在聚合训练器指标之外，为纠正项追踪诸如 ESS 之类的诊断

这次迁移的主要教训更狭窄：先修复后端正确性，然后针对剩余的失配添加纠正。
