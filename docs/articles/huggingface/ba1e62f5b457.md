# 发布 Swift Transformers：在 Apple 设备上运行端侧 LLM

我对 iOS/Mac 开发者怀有深深的敬意。2007 年我就开始给 iPhone 写 app——那时连 API 和文档都没有。新设备在约束空间里做出了一些不熟悉的取舍：功耗、屏幕面积、UI 语汇、网络访问、持久化、延迟，都和我们以前习惯的不同。然而这个社区很快就创造出了与新范式浑然一体的一流应用。

我相信 ML 是一种构建软件的新方式，我也知道很多 Swift 开发者想把 AI 能力做进他们的 app。ML 生态已经成熟了很多，有数千个模型能解决各种各样的问题。而且近来，LLM 几乎成了通用工具——只要我们的任务能建模成对文本或类文本数据的处理，LLM 就能适配到新领域。我们正见证计算史上的一个标志性时刻：LLM 正在走出实验室，成为人人均可使用的计算工具。

但是，在 app 里使用一个像 Llama 这样的 LLM 涉及若干任务，很多人是独自面对、独自解决的。我们一直在探索这个方向，很希望能继续和社区一起推进。我们的目标是做出一套工具和构件，帮开发者更快地构建。

今天，我们发布这份指南，走一遍用 Core ML 在你的 Mac 上运行 Llama 2 这类模型所需的步骤。同时我们还发布 alpha 版的库和工具来支持开发者的这段旅程。我们号召所有对 ML 感兴趣的 Swift 开发者——*所有* Swift 开发者吧？——来贡献 PR、bug 报告或观点，一起把它打磨好。

开始吧！

*视频：Llama 2 (7B) chat 模型在 M1 MacBook Pro 上用 Core ML 运行。*

## 今日发布

- [`swift-transformers`](https://github.com/huggingface/swift-transformers)：一个开发中的 Swift 包，在 Swift 里实现类 transformers API，聚焦文本生成。它是 [`swift-coreml-transformers`](https://github.com/huggingface/swift-coreml-transformers) 的演进，目标更宏大：Hub 集成、任意 tokenizer 支持、可插拔模型。
- [`swift-chat`](https://github.com/huggingface/swift-chat)：一个简单 app，演示如何使用该包。
- 更新版 [`exporters`](https://github.com/huggingface/exporters)：面向 transformers 模型的 Core ML 转换包。
- 更新版 [`transformers-to-coreml`](https://huggingface.co/spaces/coreml-projects/transformers-to-coreml)：基于 `exporters` 构建的无代码 Core ML 转换工具。
- 一些已转换好的模型，如 [Llama 2 7B](https://huggingface.co/coreml-projects/Llama-2-7b-chat-coreml) 或 [Falcon 7B](https://huggingface.co/tiiuae/falcon-7b-instruct/tree/main/coreml)，可直接配合这些文本生成工具使用。

## 任务总览

当我发推展示在 Mac 上跑的 [Falcon](https://twitter.com/pcuenq/status/1664605575882366980) 或 [Llama 2](https://twitter.com/pcuenq/status/1681404748904431616) 时，收到很多开发者问怎么把这些模型转成 Core ML——因为他们也想在自己的 app 里用。转换是关键一步，但只是拼图的第一块。我写这些 app 的真正原因，是去踩其他开发者同样会踩的坑，找出我们能在哪些地方帮上忙。下面本文会过一遍这些任务，说明我们有（和还没有）哪些工具能帮上忙。

- [转换到 Core ML](https://huggingface.co/blog/swift-coreml-llm#conversion-to-core-ml)。我们用 Llama 2 作为真实案例。
- [优化](https://huggingface.co/blog/swift-coreml-llm#optimization)技术，让你的模型（和 app）跑得快、省内存。这是贯穿整个项目方方面面的领域，没有一劳永逸的银弹。
- [`swift-transformers`](https://huggingface.co/blog/swift-coreml-llm#swift-transformers)：我们的新库，帮忙处理一些常见任务。[Tokenizers](https://huggingface.co/blog/swift-coreml-llm#tokenizers)。分词是把文本输入转成模型实际处理的数字集合（再把生成预测转回文本）的方式。这比听起来复杂得多，因为有很多不同的选项和策略。[模型与 Hub 包装器](https://huggingface.co/blog/swift-coreml-llm#model-and-hub-wrappers)。要支持 Hub 上的海量模型，我们不能硬编码模型设置。我们做了一个简单的 `LanguageModel` 抽象和各种从 Hub 下载模型与 tokenizer 配置文件的小工具。[生成算法](https://huggingface.co/blog/swift-coreml-llm#generation-algorithms)。语言模型被训练来预测文本序列之后下一个 token 的概率分布。生成文本需要多次调用模型、每步选一个 token。怎么选下一个 token，有很多种方法。[支持的模型](https://huggingface.co/blog/swift-coreml-llm#supported-models)。并非所有模型家族都已（暂时）得到支持。
- [`swift-chat`](https://huggingface.co/blog/swift-coreml-llm#swift-chat)。一个小 app，纯粹演示如何在项目里使用 `swift-transformers`。
- [缺失部分 / 即将到来](https://huggingface.co/blog/swift-coreml-llm#missing-parts--coming-next)。一些重要但还没有的东西，作为未来工作的方向。
- [资源](https://huggingface.co/blog/swift-coreml-llm#resources)。所有项目和工具的链接。

## 转换到 Core ML

Core ML 是 Apple 的机器学习原生框架，同时也是其文件格式的名字。把模型从（比如）PyTorch 转成 Core ML 后，就能在 Swift app 中使用。Core ML 框架会自动挑选最适合运行你模型的硬件：CPU、GPU，或叫 Neural Engine 的专用张量单元。根据你系统的特性和模型细节，还可以组合使用多个计算单元。

要看看现实中转换模型长什么样，我们以新发布的 Llama 2 为例。过程有时可能曲折，但我们提供了一些工具来帮忙。这些工具不保证总能用——新模型不断涌现，我们需要做调整和修改。

我们推荐的方式是：

- 使用 [`transformers-to-coreml`](https://huggingface.co/spaces/coreml-projects/transformers-to-coreml) 转换 Space：

这是基于 `exporters`（见下）构建的自动化工具，对你的模型要么能用、要么不能用。它不需要写代码：填入 Hub 上的模型标识，选择你打算用模型做的任务，点击 apply。如果转换成功，你可以把 Core ML 权重推到 Hub，完事！

你可以[访问这个 Space](https://huggingface.co/spaces/coreml-projects/transformers-to-coreml)，或在这里直接使用：

- 使用 [`exporters`](https://github.com/huggingface/exporters)：基于 Apple `coremltools` 构建的 Python 转换包（见下）。

这个库给转换任务提供更多配置选项。此外，它允许你创建自己的[转换配置类](https://github.com/huggingface/exporters#overriding-default-choices-in-the-configuration-object)，用于更强的控制或绕开转换问题。

- 使用 [`coremltools`](https://github.com/apple/coremltools)：Apple 官方的转换包。

这是最底层的方式，因此控制力最强。某些模型（尤其新模型）仍可能失败，但你总可以钻进源码去搞清楚为什么。

关于 Llama 2 的好消息是：我们提前做了功课，用以上任何一种方法都能转换成功。坏消息是：它发布时*转换失败*，我们修了一些东西才支持它。我们在[附录](https://huggingface.co/blog/swift-coreml-llm#appendix-converting-llama-2-the-hard-way)里简要回顾当时发生了什么，让你尝尝出问题时该怎么办。

### 学到的重要经验

我跟进了几个近期模型的转换过程（Llama 2、Falcon、StarCoder），并把学到的东西应用到 `exporters` 和 `transformers-to-coreml` Space 上。部分要点总结如下：

- 如果不得不使用 `coremltools`，请用最新版 `7.0b1`。虽然名义上是 beta，我用了几周，非常好：稳定、包含大量修复、支持 PyTorch 2，还有高级量化工具等新特性。
- `exporters` 在转换文本生成任务时不再对输出施加 softmax。我们意识到这对某些生成算法是必要的。
- `exporters` 现在默认对文本模型使用固定序列长度。Core ML 有一种方式指定「灵活形状」，让输入序列可以是 1 到（比如）4096 token 之间的任意长度。我们发现灵活输入只能跑在 CPU 上，跑不到 GPU 或 Neural Engine。更多调查即将发布！

我们会持续把这些最佳实践加进我们的工具，免得你重新踩一遍同样的坑。

## 优化

如果模型在目标硬件上跑不快、不尊重系统资源，转换就毫无意义。本文提到的模型对本地使用来说相当大，我们是有意选它们来试探当前技术的极限、弄清瓶颈在哪。

我们识别出几个关键优化领域。它们对我们非常重要，也是当前和后续工作的主题。包括：

- 缓存先前生成过程中 attention 的 key 和 value，就像 PyTorch 实现中的 transformers 模型那样。attention 分数的计算需要对已生成的整个序列进行，但所有历史 key-value 对在之前的运行中已经算过。目前我们*没有*为 Core ML 模型使用任何缓存机制，但正在计划！
- 使用离散形状，而不是很小的固定序列长度。不用灵活形状的主要原因是它们与 GPU 或 Neural Engine 不兼容。次要原因是：由于没有上面提到的缓存，序列长度增长时生成会越来越慢。使用一组离散固定形状，配合 key-value 缓存，应当能支撑更大的上下文、带来更自然的聊天体验。
- 量化技术。我们在 Stable Diffusion 模型上已经探索过，对其为语言模型带来的选项非常兴奋。例如，[6-bit 调色板化](https://huggingface.co/blog/fast-diffusers-coreml)能减小模型体积、节省资源。[混合位量化](https://huggingface.co/blog/stable-diffusion-xl-coreml)这个新技术可以在对模型质量影响很小的情况下实现（平均）4-bit 量化。我们也计划把这些用到语言模型上！

对生产应用，考虑先用小模型迭代（尤其在开发期），再运用优化技术选出你的用例能承受的最小模型。

## `swift-transformers`

[`swift-transformers`](https://github.com/huggingface/swift-transformers) 是一个开发中的 Swift 包，力求为 Swift 开发者提供类 transformers API。我们看看它有什么、缺什么。

### Tokenizers

分词解决两个互补的任务：把文本输入适配成模型使用的张量格式，以及把模型的结果转回文本。这个过程很有讲究，例如：

- 用词、字符、字符组还是字节？
- 大小写字母怎么处理？需要处理这个区别吗？
- 重复字符（比如空格）要删除吗，还是它们很重要？
- 模型词表里没有的词怎么办？

有几种通用的分词算法，以及大量影响模型有效使用的归一化和预处理步骤。transformers 库决定把所有这些操作抽象进同一个库（`tokenizers`），并以配置文件形式表示这些决策、与模型一起存放在 Hub 上。例如，下面是描述 Llama 2 tokenizer 配置中*仅归一化步骤*的节选：

```
  "normalizer": {
    "type": "Sequence",
    "normalizers": [
      {
        "type": "Prepend",
        "prepend": "▁"
      },
      {
        "type": "Replace",
        "pattern": {
          "String": " "
        },
        "content": "▁"
      }
    ]
  },
```

读作：归一化是按顺序执行的一串操作。先给输入串`Prepend`（前置）字符 `▁`。然后把所有空格替换成 `▁`。潜在操作有一个巨大的列表，可以作用于正则匹配，而且必须按非常特定的顺序执行。`tokenizers` 库的代码为 Hub 上的所有模型处理好了这些细节。

相比之下，在其他领域使用语言模型的项目（比如 Swift app）通常把这些决策硬编码进 app 源码。一两个模型还好，但想换一个不同模型就很困难，而且很容易出错。

我们在 `swift-transformers` 里做的，是在 Swift 中复刻这些抽象——写一次，人人可用。我们刚刚起步，覆盖还很有限。欢迎在 repo 开 issue 或来贡献你自己的实现！

具体地说，我们目前支持 BPE（Byte-Pair Encoding）tokenizer——当下使用的三大家族之一。GPT 系列、Falcon 和 Llama 都用这个方法。Unigram 和 WordPiece 的支持稍后会有。我们还没有移植所有可能的 normalizer、pre-tokenizer 和 post-processor——只移植了在转换 Llama 2、Falcon 和 GPT 模型过程中遇到的那些。

在 Swift 中使用 `Tokenizers` 模块的方式是：

```
import Tokenizers

func testTokenizer() async throws {
    let tokenizer = try await AutoTokenizer.from(pretrained: "pcuenq/Llama-2-7b-chat-coreml")
    let inputIds = tokenizer("Today she took a train to the West")
    assert(inputIds == [1, 20628, 1183, 3614, 263, 7945, 304, 278, 3122])
}
```

不过通常你不需要自己 tokenize 输入文本——[`Generation` 代码](https://github.com/huggingface/swift-transformers/blob/17d4bfae3598482fc7ecf1a621aa77ab586d379a/Sources/Generation/Generation.swift#L82)会代劳。

### 模型与 Hub 包装器

如上所述，`transformers` 大量使用存放在 Hub 上的配置文件。我们准备了一个简单的 `Hub` 模块从 Hub 下载配置文件，用于实例化 tokenizer 和获取模型元数据。

关于模型，我们创建了一个简单的 `LanguageModel` 类型作为 Core ML 模型的包装，聚焦文本生成任务。借助 protocol，我们可以用同一套 API 查询任何模型。

要获取你所用模型的恰当元数据，`swift-transformers` 依赖几个自定义元数据字段——转换模型时必须写入 Core ML 文件。`swift-transformers` 会用这些信息从 Hub 下载所有必需的配置文件。这些就是我们在用的字段，在 Xcode 的模型预览中呈示如下：

[![截图：Core ML 模型元数据字段](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/swift-transformers/coreml-model-metadata.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/swift-transformers/coreml-model-metadata.png)

`exporters` 和 `transformers-to-coreml` 会自动帮你加上这些字段。如果你手动用 `coremltools`，请一定记得自己添加。

### 生成算法

语言模型被训练来预测输入序列续写下个 token 的概率分布。要组成回答，我们需要多次调用模型，直到模型产生特殊的*终止* token，或达到我们想要的长度。决定下一个最佳 token 有很多方法。我们目前支持两种：

- 贪心解码。最直白的算法：选概率最高的 token，追加到序列，重复。对相同输入序列总是产生相同结果。
- top-k 采样。选出 `top-k`（`k` 是参数）个概率最高的 token，然后用 `temperature` 这类参数从中随机*采样*——temperature 会提高多样性，代价是模型可能跑题、丢失对内容的跟踪。

「nucleus sampling」等其他方法稍后会来。我们推荐[这篇博客](https://huggingface.co/blog/how-to-generate)（最近有更新），它对生成方法及原理有出色的综述。像 [assisted generation](https://huggingface.co/blog/assisted-generation) 这样的高级方法在优化上也可能非常有用！

## `swift-chat`

`swift-chat` 是基于 `swift-transformers` 的简单 demo app。它的主要目的是示范如何在你的代码里用 `swift-transformers`，但也能当模型测试工具。

[![Swift Chat UI](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/swift-transformers/swift-chat-ui.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/swift-transformers/swift-chat-ui.png)

使用时，从 Hub 下载一个 Core ML 模型或自己创建一个，然后在 UI 里选择。所有相关的模型配置文件会从 Hub 下载，利用元数据信息识别这是哪种模型。

第一次加载新模型会花一些时间准备。这个阶段，CoreML 框架会编译模型，并根据你的机器规格和模型结构决定在哪些计算设备上运行。这些信息会被缓存，供后续运行复用。

这个 app 刻意保持简单，以便可读、精炼。它也缺一些功能，主要受限于当前模型上下文大小。例如，它完全没有考虑「system prompt」——而 system prompt 是[用来指定语言模型行为](https://huggingface.co/blog/llama2#how-to-prompt-llama-2)乃至个性的有用机制。

## 缺失部分 / 即将到来

如前所述，我们刚刚起步！接下来的优先级包括：

- 编码器-解码器模型，如 T5 和 Flan。
- 更多 tokenizer：支持 Unigram 和 WordPiece。
- 更多生成算法。
- 支持 key-value 缓存用于优化。
- 转换时使用离散的序列形状。配合 key-value 缓存，这将允许更大的上下文。

告诉我们你觉得下一步该做什么，或者去 repos 找 [Good First Issues](https://github.com/huggingface/swift-transformers/issues?q=is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22) 练练手！

### *附录：硬核方式转换 Llama 2*

除非你正被 Core ML 转换问题折磨、并且准备好战斗 :)，否则这一节可以放心跳过。

以我的经验，PyTorch 模型用 `coremltools` 转 Core ML 失败，常见原因有两个：

- 不支持的 PyTorch 操作或操作变体

PyTorch 有*海量*操作，每个操作都要映射到中间表示（[MIL](https://apple.github.io/coremltools/source/coremltools.converters.mil.mil.ops.defs.html)，即 *Model Intermediate Language*），MIL 再转成原生 Core ML 指令。PyTorch 的操作集合不是静态的，所以新操作也得不断加进 `coremltools`。而且有些操作非常复杂，还能以奇特的参数组合工作。最近加入的一个复杂操作例子是 PyTorch 2 引入的*scaled dot-product attention*。部分支持的操作例子是 `einsum`：并非所有可能的方程都能翻译成 MIL。

- 边角案例与类型不匹配

即使 PyTorch 操作受支持，也很难保证翻译过程在所有输入类型的所有可能输入上都工作。要记住，单个 PyTorch 操作可能针对不同设备（cpu、CUDA）、输入类型（整型、浮点）或精度（float16、float32）有多个后端实现。所有组合的数量是惊人的，而有时某个模型使用 PyTorch 代码的方式会触发一条从未被考虑或测试过的翻译路径。

我第一次尝试用 `coremltools` 转换 Llama 2 时正是这样：

[![Llama 2 转换错误](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/swift-transformers/llama-conversion-error.png)](https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/blog/swift-transformers/llama-conversion-error.png)

通过对比 transformers 的不同版本，我能看出问题始于[这一行代码](https://github.com/huggingface/transformers/blob/d114a6b71f243054db333dc5a3f55816161eb7ea/src/transformers/models/llama/modeling_llama.py#L52C5-L52C6)被引入之时。它是 `transformers` 近期重构的一部分，为了更好地处理*所有*使用 causal mask 的模型，所以这对其他模型也是大问题，不只是 Llama。

错误截图告诉我们的是：填充 mask 张量时发生了类型不匹配。问题出在这一行里的 `0`：它被解释成 `int`，而要填充的张量装的是 `float`，翻译过程拒绝使用不同类型。在这个具体案例里，我给 `coremltools` 提了一个[补丁](https://github.com/apple/coremltools/pull/1915)，但幸运的是很少需要做到这一步。很多时候你可以给代码打补丁（在 `transformers` 的本地副本里改成 `0.0` 就行），或创建一个「special operation」来处理这个例外。我们的 `exporters` 库对自定义特殊操作支持很好：见一个缺少 `einsum` 方程的[例子](https://github.com/huggingface/exporters/blob/f134e5ceca05409ea8abcecc3df1c39b53d911fe/src/exporters/coreml/models.py#L139C9-L139C18)，或在新版 `coremltools` 发布前让 `StarCoder` 模型能跑的[这个变通](https://github.com/huggingface/exporters/blob/f134e5ceca05409ea8abcecc3df1c39b53d911fe/src/exporters/coreml/models.py#L208C9-L208C18)。

好在 `coremltools` 对新操作的覆盖不错，团队反应也很快。
