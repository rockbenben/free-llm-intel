Hugging Face 的模型和数据集仓库很适合发布最终产物。但生产环境的 ML 会持续产生中间文件（检查点、优化器状态、处理后的分片、日志、trace 等）——它们频繁变化、多个任务同时写入，而且几乎不需要版本控制。

**存储桶（Storage Buckets）**正是为此而生：可在 Hub 上浏览、用 Python 脚本操作、用 `hf` CLI 管理的可变更 S3 式对象存储。而且因为底层是 [Xet](https://huggingface.co/docs/hub/en/xet)，文件之间有大量共享内容的 ML 产物存起来尤其高效。

## 我们为什么要做存储桶

当你面对这些情况时，Git 很快就会显得是个错误的抽象：

- 训练集群在整个训练过程中持续写检查点和优化器状态
- 数据管线迭代式地处理原始数据集
- Agent 存储 trace、记忆和共享知识图谱

这些场景的存储需求是一样的：快速写入、需要时覆盖、同步目录、清理过期文件，让流程保持运转。

存储桶是 Hub 上的一个非版本化存储容器。它归属于某个用户或组织命名空间，使用标准的 Hugging Face 权限体系，可以私有也可以公开，有自己的网页可以直接在浏览器打开，也可以用 `hf://buckets/username/my-training-bucket` 这样的句柄编程式访问。

## 为什么 Xet 很重要

存储桶构建在 [Xet](https://huggingface.co/docs/hub/en/xet)——Hugging Face 的基于分块（chunk）的存储后端——之上，这点比看上去更重要。

Xet 不把文件当作整块 blob，而是拆分成 chunk 并跨 chunk 去重。上传一个和原始数据高度相似的已处理数据集？很多 chunk 已经存在。存连续的检查点、其中大部分模型参数是冻结不变的？同样如此。存储桶会跳过已经存在的字节，也就是更少带宽、更快传输、更高存储效率。

这对 ML 工作负载是天然契合。训练管线不断产出一族族相关的产物——原始与处理后数据、连续的检查点、Agent trace 及其派生摘要——而 Xet 就是为利用这种重叠而设计的。

对企业客户，计费基于去重后的存储量，共享 chunk 会直接降低计费体积。去重同时带来速度和成本上的收益。

## 预热（Pre-warming）：把数据搬到算力旁边

存储桶住在 Hub 上，默认即全球存储。但并非所有工作负载都能忍受从数据所在之地拉取——对分布式训练和大规模管线来说，存储位置直接影响吞吐。

预热功能可以把热点数据搬到你的算力所在的云提供商和区域附近。数据不再需要每次读取都跨区流动——你声明需要它在哪里，存储桶就会确保任务启动时它已经就位。这对需要快速访问大数据集或检查点的训练集群、以及管线不同部分跑在不同云上的多区域架构特别有用。

我们先与 AWS 和 GCP 合作，未来会接入更多云提供商。

## 快速上手

用 `hf` CLI，两分钟内就能跑起来一个存储桶。第一步是安装并登录：

```
curl -LsSf https://hf.co/cli/install.sh | bash
hf auth login
```

为你的项目创建一个存储桶：

```
hf buckets create my-training-bucket --private
```

假设你的训练任务把检查点写在本地 `./checkpoints`，把这个目录同步进存储桶：

```
hf buckets sync ./checkpoints hf://buckets/username/my-training-bucket/checkpoints
```

大文件传输时，你可能想在真正动手前先看看会发生什么。`--dry-run` 会打印执行计划但不做任何事：

```
hf buckets sync ./checkpoints hf://buckets/username/my-training-bucket/checkpoints --dry-run
```

也可以把计划存进文件，先审查、之后再生效：

```
hf buckets sync ./checkpoints hf://buckets/username/my-training-bucket/checkpoints --plan sync-plan.jsonl
hf buckets sync --apply sync-plan.jsonl
```

完成后，用 CLI 查看存储桶：

```
hf buckets list username/my-training-bucket -h
```

或直接在 Hub 上浏览：`https://huggingface.co/buckets/username/my-training-bucket`。

这就是完整闭环：建一个桶，把工作数据同步进去，需要时查看，等某个东西值得发布了再存进版本化仓库。零散操作用 `hf buckets cp` 复制单个文件，用 `hf buckets remove` 清理过期对象。

## 在 Python 中使用存储桶

上面的一切也能通过 [`huggingface_hub`](https://github.com/huggingface/huggingface_hub) 在 Python 里完成（自 [v1.5.0](https://github.com/huggingface/huggingface_hub/releases/tag/v1.5.0) 起提供）。API 遵循同样的模式：创建、同步、查看。

```
from huggingface_hub import create_bucket, list_bucket_tree, sync_bucket

create_bucket("my-training-bucket", private=True, exist_ok=True)

sync_bucket(
    "./checkpoints",
    "hf://buckets/username/my-training-bucket/checkpoints",
)

for item in list_bucket_tree(
    "username/my-training-bucket",
    prefix="checkpoints",
    recursive=True,
):
    print(item.path, item.size)
```

这让把存储桶集成进训练脚本、数据管线或任何编程管理产物的服务变得非常直接。Python 客户端还支持批量上传、选择性下载、删除，以及桶的迁移，提供更细粒度的控制。

JavaScript 也可用：[`@huggingface/hub`](https://www.npmjs.com/package/@huggingface/hub)（自 v2.10.5 起）支持存储桶，Node.js 服务和 Web 应用同样能集成。

## 文件系统集成

存储桶也能通过 `HfFileSystem` 使用——`huggingface_hub` 里兼容 [fsspec](https://filesystem-spec.readthedocs.io/) 的文件系统。也就是说你可以用标准文件系统操作对桶内容执行列表、读、写、glob——任何支持 fsspec 的库都能直接访问存储桶。

```
from huggingface_hub import hffs

# List files in a bucket directory
hffs.ls("buckets/username/my-training-bucket/checkpoints", detail=False)

# Glob for specific files
hffs.glob("buckets/username/my-training-bucket/**/*.parquet")

# Read a file directly
with hffs.open("buckets/username/my-training-bucket/config.yaml", "r") as f:
    print(f.read())
```

因为 fsspec 是 Python 远程文件系统的标准接口，pandas、Polars、Dask 等库可以直接用 `hf://` 路径读写存储桶，无需额外配置：

```
import pandas as pd

# Read a CSV directly from a Bucket
df = pd.read_csv("hf://buckets/username/my-training-bucket/results.csv")

# Write results back
df.to_csv("hf://buckets/username/my-training-bucket/summary.csv")
```

这让存储桶能无缝插入现有数据工作流，你的代码读写文件的方式完全不用变。

## 从存储桶到版本化仓库

存储桶是产物"还在运动中"时居住的快速、可变的场所。一旦某个东西成为稳定的交付物，它通常就该进一个版本化的模型或数据集仓库。

在路线图里，我们计划支持存储桶与仓库之间的双向直接传输：把最终检查点权重"晋升"进模型仓库，或在管线完成后把处理好的分片提交进数据集仓库。工作层与发布层保持分离，但能拼成一条连续的 Hub 原生工作流。

## 结论与资源

存储桶为 Hub 补上了一层缺失的存储。它为 ML 可变、高吞吐的那一面提供了 Hub 原生的家：检查点、已处理数据、Agent trace、日志，以及在"变成最终产物"之前所有有用的东西。

因为构建在 Xet 上，存储桶不只是比硬塞进 Git 更好用——对 AI 系统时刻产出的相关产物族，它也更快。这意味着更快传输、更好的去重；在企业版套餐上，计费还能直接受益于去重后的体积。

如果你已经在用 Hub，存储桶让你的大部分工作流留在同一个地方；如果你来自 S3 式存储，它提供熟悉的模型、与 AI 产物更好的契合，以及一条通往 Hub 最终发布的清晰路径。

存储桶已包含在现有的 [Hub 存储套餐](https://huggingface.co/docs/hub/en/storage-limits#storage-plans)中。免费账号自带起步存储空间，PRO 和 Enterprise 套餐提供更高上限。细节见[存储页面](https://huggingface.co/storage)。
