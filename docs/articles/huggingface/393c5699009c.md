# Google Cloud C4 联合 Intel 和 Hugging Face 为 GPT OSS 带来 70% 的 TCO 改善

Intel 与 Hugging Face 合作，验证了升级到 Google 最新一代运行 Intel® Xeon® 6 处理器（代号 Granite Rapids，GNR）的 `C4` 虚拟机（VM）在现实场景中的价值。我们专门对 OpenAI GPT OSS 大语言模型（LLM）的文本生成性能做了基准测试，以衡量改进幅度。

结果出炉，令人印象深刻：相比上一代 Google `C3` VM 实例，总拥有成本（TCO）改进 *1.7 倍*。Google Cloud `C4` VM 实例还带来了：

- 1.4x 到 1.7x 的 TPOT 吞吐/vCPU/美元
- 比 `C3` VM 更低的小时单价

## 背景介绍

GPT OSS 是 OpenAI 发布的一个开源混合专家（MoE）模型的统称。MoE 模型是一种深度神经网络架构，使用专门的「专家」子网络和一个「门控网络」来决定对给定输入调用哪些专家。MoE 模型让你能高效扩展模型容量，而不必线性扩展算力成本；同时支持专业化分工——不同的「专家」学到不同技能，从而适应多样的数据分布。

即便参数规模非常大，每个 token 也只激活一小部分专家，这使得 CPU 推理变得可行。

Intel 与 Hugging Face 合作合入了一项专家执行优化（PR [#40304](https://github.com/huggingface/transformers/pull/40304)），进入 transformers 库，消除了「每个专家处理所有 token」造成的冗余计算。这项优化让每个专家只在其被路由到的 token 上运行，去除了 FLOPs 浪费，提高了利用率。

## 基准测试范围与硬件

我们在受控、可重复的生成负载下对 GPT OSS 进行基准测试，以隔离架构差异（GCP 上运行 Intel Xeon 6（GNR）的 `C4` VM vs GCP 上运行第四代 Intel Xeon（SPR）的 `C3` VM）以及 MoE 执行效率。测试聚焦稳态解码（每 token 延迟），以及在序列长度固定的情况下，随 batch size 增长而端到端归一化的吞吐量。所有运行都使用静态 KV cache 和 SDPA 注意力以保证确定性。

### 配置概览

- 模型：[unsloth/gpt-oss-120b-BF16](https://huggingface.co/unsloth/gpt-oss-120b-BF16)
- 精度：bfloat16
- 任务：文本生成
- 输入长度：1024 token（左侧填充）
- 输出长度：1024 token
- Batch sizes：1、2、4、8、16、32、64
- 启用特性：静态 KV cache，SDPA 注意力后端
- 上报指标：吞吐量（整个 batch 内每秒生成 token 总数的聚合）

### 被测硬件

| 实例 | 架构 | vCPU 数 |
| --- | --- | --- |
| `C3` | 第四代 Intel Xeon 处理器（SPR） | 172 |
| `C4` | Intel Xeon 6 处理器（GNR） | 144 |

## 基准测试流程

对每个 batch size，我们：

- 构造一个固定长度 1024 token 的左填充 batch。
- 先跑一轮 warm-up。
- 设置 `max_new_tokens=1024` 并测量总延迟，然后计算吞吐量 throughput=(OUTPUT_TOKENS∗batch_size)/total_latencythroughput = (OUTPUT\_TOKENS * batch\_size) / total\_latencythroughput=(OUTPUT_TOKENS∗batch_size)/total_latency。

对下面的代码运行 `numactl -l python benchmark.py`。

```
import os
import time
import torch
from datasets import load_dataset
from transformers import AutoModelForCausalLM, AutoTokenizer

INPUT_TOKENS = 1024
OUTPUT_TOKENS = 1024

def get_inputs(tokenizer, batch_size):
    dataset = load_dataset("ola13/small-the_pile", split="train")
    tokenizer.padding_side = "left"
    selected_texts = []
    for sample in dataset:
        input_ids = tokenizer(sample["text"], return_tensors="pt").input_ids
        if len(selected_texts) == 0 and input_ids.shape[-1] >= INPUT_TOKENS:
            selected_texts.append(sample["text"])
        elif len(selected_texts) > 0:
            selected_texts.append(sample["text"])
        if len(selected_texts) == batch_size:
            break

    return tokenizer(selected_texts, max_length=INPUT_TOKENS, padding="max_length", truncation=True, return_tensors="pt")

def run_generate(model, inputs, generation_config):
    inputs["generation_config"] = generation_config
    model.generate(**inputs) # warm up
    pre = time.time()
    model.generate(**inputs)
    latency = (time.time() - pre)
    return latency

def benchmark(model, tokenizer, batch_size, generation_config):
    inputs = get_inputs(tokenizer, batch_size)
    generation_config.max_new_tokens = 1
    generation_config.min_new_tokens = 1
    prefill_latency = run_generate(model, inputs, generation_config)
    generation_config.max_new_tokens = OUTPUT_TOKENS
    generation_config.min_new_tokens = OUTPUT_TOKENS
    total_latency = run_generate(model, inputs, generation_config)
    decoding_latency = (total_latency - prefill_latency) / (OUTPUT_TOKENS - 1)
    throughput = OUTPUT_TOKENS * batch_size / total_latency

    return prefill_latency, decoding_latency, throughput


if __name__ == "__main__":
    model_id = "unsloth/gpt-oss-120b-BF16"
    tokenizer = AutoTokenizer.from_pretrained(model_id)
    model_kwargs = {"dtype": torch.bfloat16}
    model = AutoModelForCausalLM.from_pretrained(model_id, **model_kwargs)
    model.config._attn_implementation="sdpa"
    generation_config = model.generation_config
    generation_config.do_sample = False
    generation_config.cache_implementation="static"

    for batch_size in [1, 2, 4, 8, 16, 32, 64]:
        print(f"---------- Run generation with batch size = {batch_size} ----------", flush=True)
        prefill_latency, decoding_latency, throughput = benchmark(model, tokenizer, batch_size, generation_config)
        print(f"throughput = {throughput}", flush=True)
```

## 结果

### 归一化每 vCPU 吞吐量

在直到 64 的各个 batch size 上，搭载 Intel Xeon 6 处理器的 `C4` 始终优于 `C3`，每 vCPU 吞吐高出 1.4x 到 1.7×。计算公式为：

normalized_throughput_per_vCPU=throughput_C4/vCPUs_C4throughput_C3/vCPUs_C3 \text{normalized\_throughput\_per\_vCPU} = \frac{\text{throughput\_C4} / \text{vCPUs\_C4}} {\text{throughput\_C3} / \text{vCPUs\_C3}} normalized_throughput_per_vCPU=throughput_C3/vCPUs_C3throughput_C4/vCPUs_C4​

![throughput-gpt-oss-per-vcpu](https://huggingface.co/datasets/Intel/blog/resolve/main/gpt-oss-on-intel-xeon/throughput-gpt-oss-per-vcpu.png)

### 成本与 TCO

在 batch size 为 64 时，`C4` 提供 `C3` 的 1.7× 每 vCPU 吞吐；而两者每 vCPU 价格基本相当（小时成本与 vCPU 数量线性相关），因此带来 1.7× 的 TCO 优势（要生成同样的 token 量，`C3` 需要多花 1.7× 的钱）。

每 vCPU 吞吐比：throughput_C4/vCPUs_C4throughput_C3/vCPUs_C3=1.7⇒TCO_C3TCO_C4≈1.7 \frac{\text{throughput\_C4} / \text{vCPUs\_C4}}{\text{throughput\_C3} / \text{vCPUs\_C3}} = 1.7 \Rightarrow \frac{\text{TCO\_C3}}{\text{TCO\_C4}} \approx 1.7 throughput_C3/vCPUs_C3throughput_C4/vCPUs_C4​=1.7⇒TCO_C4TCO_C3​≈1.7

## 结论

由 Intel Xeon 6 处理器（GNR）驱动的 Google Cloud `C4` VM，相比上一代 Google Cloud `C3` VM（第四代 Intel Xeon 驱动），在大型 MoE 推理上同时带来了亮眼的性能提升和更好的成本效率。对于 GPT OSS 的 MoE 推理，我们观察到吞吐量更高、延迟更低、成本下降的叠加效果。这些结果说明：得益于 Intel 和 Hugging Face 针对性的框架优化，大型 MoE 模型可以在新一代通用 CPU 上高效服务。
