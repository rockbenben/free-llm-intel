## 没有 MLOps 团队，如何在生产环境扩展与维护 ML 模型

我们创建了 [Rocket Money](https://www.rocketmoney.com/)（前身是 Truebill 的个人理财应用），帮助用户改善财务健康。用户把银行账户关联到应用后，应用会对交易进行分类归档、识别周期性模式，为其个人财务生活提供一个整合、全面的视图。交易处理的关键环节是检测已知商户与服务——其中一些 Rocket Money 可以帮会员取消并议价。这一检测始于把那些简短、常被截断、格式晦涩的交易字符串转换成可用于丰富产品体验的类别。

## 迈向新系统的旅程

最初，我们用基于正则表达式的规范化器从交易中提取品牌与产品，并配合一张不断复杂的决策表把字符串映射到对应品牌。这套体系在头四年里运转良好——那时类别只绑定我们支持取消和议价的产品。但随着用户规模增长、订阅经济爆发、产品范围扩大，我们既要跟上类别新增的速度，又要不停调 regex、防止冲突与重叠。为此我们尝试了多种传统机器学习方案，包括词袋模型加每类一个模型的架构。这套系统维护困难、性能不佳，最终被封存。

我们决定从零开始，组建新团队、确立新使命。第一项任务是积累训练数据并从零构建内部系统。我们用 Retool 搭建标注队列、金标准验证数据集和漂移检测监控工具。我们探索了多种模型拓扑，最终选择 BERT 系列模型来解决文本分类问题。大部分初期的模型测试与评估都在 GCP 数据仓库中离线完成。在这里，我们设计并构建了用于衡量 4000+ 类别模型性能的遥测与系统。

## 与 Hugging Face 合作化解领域挑战与约束

我们在自己的领域面临一系列独特挑战，包括商户、支付处理公司、机构差异以及用户行为变化注入的熵。设计并构建高效的模型性能告警、以及贴近现实的基准数据集，是一场持续的硬仗。另一道大坎是确定系统的最佳类别数量——每个类别的创建与维护都意味着可观的投入，因此必须权衡它对用户和我们业务的价值。

模型在离线测试中表现良好、ML 工程团队人数不多，我们随即面临新挑战：把这个模型无缝集成进生产流水线。既有 regex 系统每月处理超过 1 亿笔交易，且负载高度突发，因此我们必须拥有一个高可用、能按负载动态扩缩的系统，既要维持流水线的整体低延迟，又要对所服务模型做计算优化。当时我们还是家小创业公司，选择外购而非自建模型服务方案。我们没有内部的模型运维专长，需要把 ML 工程师的精力集中在提升模型在产品中的表现上。带着这些考虑，我们踏上寻觅之旅。

起初，我们试用了一套为原型开发而手写的内部模型托管方案，并与 AWS SageMaker 以及 Hugging Face 新推出的模型托管 Inference API 作对比。鉴于我们用 GCP 做数据存储、用 Google Vertex Pipelines 训练模型，把模型导出到 AWS SageMaker 既别扭又 bug 频出。值得庆幸的是，Hugging Face 的搭建快速简单，一周内就能承接一部分流量。Hugging Face 一上来就运转正常，这份低摩擦让我们放心沿这条路走下去。

在长达三个月的评估期后，我们选定 Hugging Face 托管我们的模型。期间我们逐步提高向其托管模型导流的交易量，并按最坏情况的容量跑了大量模拟负载测试。这一过程让我们得以微调系统、监控性能，最终对推理 API 承载交易富化负载的能力充满信心。

除技术能力外，我们还与 Hugging Face 团队建立了很好的默契。我们发现他们不只是服务提供商，而是真正投入我们目标与成果的伙伴。合作早期我们就建了共享 Slack 频道，事后证明极其宝贵。他们对问题的快速响应和主动解决问题的方式令我们印象深刻。他们的工程师和客户成功经理（CSM）始终展现出对我们成功的投入和把事情做对的执着。到了最终抉择时刻，这给了我们又一层信心。

## 集成、评估与最终选择

#### 「总体而言，与 Hugging Face 携手推进模型部署的经历让我们团队受益匪浅，也给了我们推动更大规模的信心」——Nicolas Kuzak，Rocket Money 资深 ML 工程师

合同签订后，我们开始迁移：逐步脱离 regex 系统，把越来越多的关键路径流量导向 transformer 模型。内部我们需要为模型与生产数据监控构建新的遥测体系。鉴于这个系统位于产品体验的最前端，模型结果的任何不准确都可能显著影响业务指标。我们做了一个大规模实验：把新用户平均分流到旧系统和新模型，同时结合更大的业务指标（如付费用户留存与活跃度）来评估模型表现。ML 模型在留存上明显胜出，让我们有信心果断扩展系统——先对新用户、再对存量用户，两个月内爬坡到 100%。

模型完全就位到交易处理流水线后，可用性与延迟成了头号关切。我们的许多下游流程依赖分类结果，任何故障都会造成数据延迟或富化不完整，两者都会损害用户体验。

Rocket Money 与 Hugging Face 合作的首年并非一帆风顺。但两个团队都展现出非凡的韧性与共同解决问题的决心。有一次我们在第二个生产模型中扩充类别数量，不幸引发了一次宕机。尽管遭遇挫折，团队坚持不懈，此后成功避免了同类问题重演。另一次小插曲是切换到新模型时，由于 Hugging Face 侧的缓存问题，我们仍收到旧模型的结果。该问题被迅速解决且未再发生。总体而言，与 Hugging Face 携手推进模型部署的经历让我们团队受益匪浅，也给了我们推动更大规模的信心。

说到规模：随着模型流量显著增长，我们看清推理成本将超出预算。于是在推理调用前加了一层缓存，大幅降低交易基数并复用既往推理结果。我们的问题理论上可达 93% 的缓存命中率，但生产环境中最高只到 85%。在模型承担 100% 预测的同时，我们在 Rocket Money 侧也迎来几个里程碑——模型扩展到了每月超过 10 亿笔交易的运行速率，并在我们冲上应用商店理财类第一、总榜第七时驾驭了流量激增，同时保持了低延迟。

## 协作与未来计划

#### 「Hugging Face Inference API 的可用性与给我们的信心，让我们能把精力放在模型产生的价值上，而不是管道和日常运维」——Nicolas Kuzak，Rocket Money 资深 ML 工程师

上线之后，Rocket Money 内部团队现在的重心是模型的类别与性能调优，以及更自动化的监控与训练标签体系。我们每天新增标签，也遭遇模型生命周期管理的种种有趣挑战——包括公司更名，以及 2021 年底 Rocket Companies 收购 Truebill 之后不断涌现的新公司、新产品这类独特情况。

我们持续审视模型拓扑是否契合问题。虽然 LLM 近来热度很高，但目前我们还没找到在速度与成本上都能超越我们专用 transformer 分类器的落地方式。在长尾服务（如夫妻小店）上使用 LLM 的早期结果让我们看到了希望——留意未来版本 Rocket Money 里的这个方向！Hugging Face Inference API 的可用性与带给我们的信心，让我们能把精力放在模型创造的价值上，而不是管道与日常运维。在 Hugging Face 的帮助下，我们承接了模型内部更大的规模与复杂度，以及它创造价值的更多形态。他们的客户服务与支持超出我们的预期，是我们旅程中名副其实的良伴。
