# gradio.Server：用 Gradio 后端搭配任意自定义前端

几周前，我们写过[用 `gr.HTML` 一次性构建完整 Web 应用](https://huggingface.co/blog/gradio-html-one-shot-apps)：完全在 Gradio 内部使用自定义 HTML、CSS 和 JavaScript 构建丰富、可交互的前端。这打开了很多可能。但如果这还不够呢？

如果你想**完全使用自己的前端框架**——React、Svelte，甚至纯 HTML/JS——同时仍然享受 Gradio 的排队系统、API 基础设施、MCP 支持以及 Spaces 上的 ZeroGPU 呢？

这正是 **`gradio.Server`** 要解决的问题。它改变了 Gradio 与 Hugging Face Spaces 的可能性边界。

## 我们想构建什么

**[Text Behind Image](https://huggingface.co/spaces/ysharma/text-behind-image)**：一个编辑器——上传照片后，用 ML 模型去除背景，然后你可以把艺术化文字放置在前景主体与背景*之间*，让文字看起来位于图中人物或物体的后面。

这需要：

- 一个带分层渲染（背景 → 文字 → 前景）的**拖放画布**
- 一个**富控制面板**：字号、字重、字间距、颜色、不透明度、描边、阴影、3D 挤出、透视变换等滑块
- 一个**后端 ML endpoint**：运行背景移除模型并返回透明 PNG
- **客户端导出 PNG**

这样的 UI 无法用 Gradio 组件表达。它是一个完整的 Web 应用。但我们仍然想要 Gradio 的后端能力：排队、并发管理、ZeroGPU 支持，以及无基础设施烦恼的 HF Spaces 托管。

## 有请 `gradio.Server`

`gradio.Server` 扩展自 FastAPI。它给你 FastAPI 的全部能力（自定义路由、中间件、文件上传、任意响应类型），同时在其上叠加 Gradio 的 API 引擎：排队、SSE 流式传输、并发控制以及 `gradio_client` 兼容。

下面是 Text Behind Image 的完整后端：

```
import os
import torch
from PIL import Image
from torchvision import transforms
from transformers import AutoModelForImageSegmentation
from gradio import Server
from gradio.data_classes import FileData
from fastapi.responses import HTMLResponse
import spaces

torch.set_float32_matmul_precision("high")

birefnet = AutoModelForImageSegmentation.from_pretrained(
    "ZhengPeng7/BiRefNet", trust_remote_code=True
)
birefnet.to("cuda")
birefnet.float()

transform_image = transforms.Compose([
    transforms.Resize((1024, 1024)),
    transforms.ToTensor(),
    transforms.Normalize([0.485, 0.456, 0.406], [0.229, 0.224, 0.225]),
])

app = Server()


@spaces.GPU
def segment(image: Image.Image) -> Image.Image:
    """Run BiRefNet segmentation to produce a transparency mask."""
    image_size = image.size
    input_images = transform_image(image).unsqueeze(0).to("cuda")
    with torch.no_grad():
        preds = birefnet(input_images)[-1].sigmoid().cpu()
    pred = preds[0].squeeze()
    mask = transforms.ToPILImage()(pred).resize(image_size)
    image.putalpha(mask)
    return image


@app.api(name="remove_background")
def remove_background(image_path: FileData) -> FileData:
    """Remove background from an image. Returns transparent PNG."""
    im = Image.open(image_path["path"]).convert("RGB")
    result = segment(im)
    out_path = image_path["path"].rsplit(".", 1)[0] + ".png"
    result.save(out_path)
    return FileData(path=out_path)


@app.get("/", response_class=HTMLResponse)
async def homepage():
    html_path = os.path.join(os.path.dirname(os.path.abspath(__file__)), "index.html")
    with open(html_path, "r", encoding="utf-8") as f:
        return f.read()


app.launch(show_error=True)
```

就这些。约 50 行 Python。模型在启动时加载，`@spaces.GPU` 负责 ZeroGPU 分配，`gradio.Server` 管理排队与并发。我们来拆解其中发生了什么。

### 为什么用 `@app.api()` 而不是普通 FastAPI 路由？

如果这是一个普通 FastAPI 应用，你会为去背景定义一个 `@app.post()` 路由。这可行——直到两个用户同时访问。没有并发管理，两个请求会争抢 GPU，应用要么崩溃要么返回垃圾数据。

`@app.api()` 解决了这一点。它用 Gradio 的排队引擎包装你的函数：请求被序列化、并发被控制；在 ZeroGPU Spaces 上，GPU 分配通过 `@spaces.GPU` 自动处理。额外的好处是，任何 `@app.api()` endpoint 都可以通过 `gradio_client` 调用，因此其他应用或脚本可以以编程方式使用你的 Space：

```
from gradio_client import Client, handle_file
client = Client("ysharma/text-behind-image")
result = client.predict(
      image_path=handle_file("photo.jpg"),
      api_name="/remove_background"
  )
```

与此同时，`@app.get("/")` 是一个标准的 FastAPI 路由，用于提供 HTML 页面。两者能自然共存，因为 `Server` *本身*就是一个 FastAPI 应用。

### 前端：纯 HTML/CSS/JS

本例中的 `index.html` 是一个自包含的约 1300 行 Web 应用。没有 React，没有构建步骤，没有打包器。就是原生 HTML，包含：

- **三层画布**：背景图 → 文字层 → 前景（透明 PNG），用 CSS `z-index` 堆叠
- 基于指针事件的**拖放文字定位**
- 一个**控制面板**，含 20 多个参数：字体（25+ 种）、字号、字重、间距、颜色、不透明度、背景填充、描边、阴影、3D 挤出的深度与角度、旋转、斜切，以及完整的 CSS 透视变换
- 使用 `<canvas>` 合成的**客户端 PNG 导出**

前端通过 [Gradio JS Client](https://www.gradio.app/guides/getting-started-with-the-js-client) 与后端通信：

```
import { Client, handle_file } from "https://cdn.jsdelivr.net/npm/@gradio/client/dist/index.min.js";

const client = await Client.connect(window.location.origin);
const result = await client.predict("/remove_background", {
    image_path: handle_file(file),
});
foregroundLayer.src = result.data[0].url;  // transparent PNG
```

这是关键：前端使用 Gradio JS 客户端而非裸 `fetch()` 调用，请求就会走 Gradio 的队列。也就是说并发被管理、GPU 请求不会相撞，你甚至可以向用户展示排队位置或进度。其余一切——文字渲染、图层合成、导出——都发生在浏览器里。

## 这解锁了什么

以下是 `gradio.Server` 出现之前**做不到**的事：

| Before | After |
| --- | --- |
| 自定义 UI 意味着彻底离开 Gradio | 自定义 UI *配上* Gradio 的后端引擎 |
| 无法从 Gradio 应用提供静态 HTML | `@app.get("/")` 可以服务任何内容 |
| `gradio_client` 只能配合 Gradio 组件应用 | `@app.api()` endpoints 兼容 client |
| 在 Gradio 的基础设施与设计自由之间二选一 | 两者兼得 |

有了 `gradio.Server`，**Gradio 兼具后端框架的角色：想要它的 UI 系统就用，不想要就带自己的前端。**

想要 Gradio 的 UI，可以用 `gr.Blocks`、`gr.Interface`、`gr.ChatInterface`。想要自己的 UI，就用 `gradio.Server`，搭配任何你喜欢的前端。无论哪种方式，你都拥有 Spaces 托管、API 排队、`gradio_client` 访问、完整 HF 生态等等。
