# 🤗 Hub 上的超强搜索

Zachary Mueller（muellerzr）

`huggingface_hub` 库是一个轻量接口，为探索 Hugging Face 提供的托管端点（模型、数据集和 Spaces）提供了一种编程方式。

到目前为止，通过这个接口在 Hub 上搜索很难搞定，用户有太多方面需要"自己去摸索"和习惯。

在这篇文章里，我们会看看 `huggingface_hub` 新增的几个令人兴奋的特性，它们帮助降低了门槛，让用户能在不离开 Jupyter 或 Python 界面的情况下，用一个友好的 API 搜索想用的模型和数据集。

> 开始之前，如果你的系统上还没有最新版 huggingface_hub 库，请运行下面这个单元格：

```
!pip install huggingface_hub -U
```

## 定位问题：

首先，我们来想象你所处的场景。你想找到 Hugging Face Hub 上所有用于文本分类、在 GLUE 数据集上训练、且兼容 PyTorch 的模型。

你大可直接打开 [https://huggingface.co/models](https://huggingface.co/models) 用上面的小部件。但这需要你离开 IDE 去浏览结果，所有这些都 Requires 点几下按钮才能拿到你需要的信息。

如果有种方案能让你不离开 IDE 就解决这个呢？有了编程接口，它还能轻松地在探索 Hub 的工作流里被集成。

这正是 `huggingface_hub` 大显身手的地方。

熟悉这个库的人可能已经知道，我们可以搜索这类模型。然而，把查询写对是一个痛苦的试错过程。

我们能简化它吗？我们看看！

## 找到我们需要的东西

我们先导入 `HfApi`，它是一个帮助我们与 Hugging Face 后端托管交互的类。我们可以通过它与模型、数据集等交互。同时，我们导入几个辅助类：`ModelFilter` 和 `ModelSearchArguments`

```
from huggingface_hub import HfApi, ModelFilter, ModelSearchArguments

api = HfApi()
```

这两个类能帮我们把上面的问题搭出一个方案。`ModelSearchArguments` 类是一个类似命名空间的对象，里面包含了我们能搜索的每一个有效参数！

我们看一眼：

```
>>> model_args = ModelSearchArguments()

>>> model_args
```

```
Available Attributes or Keys:
 * author
 * dataset
 * language
 * library
 * license
 * model_name
 * pipeline_tag
```

我们看到一系列可用的属性（关于这个"魔法"如何做到，后面再说。）。如果我们要归类想要的东西，大致可以这样分开：

- `pipeline_tag`（或任务）：Text Classification
- `dataset`：GLUE
- `library`：PyTorch

有了这个划分，我们去我们声明的 `model_args` 里找到它们是合情合理的：

```
>>> model_args.pipeline_tag.TextClassification
```

```
'text-classification'
```

```
>>> model_args.dataset.glue
```

```
'dataset:glue'
```

```
>>> model_args.library.PyTorch
```

```
'pytorch'
```

我们开始注意到的是这里做的一些便捷封装。`ModelSearchArguments`（以及配套的 `DatasetSearchArguments`）有一个人类可读的界面，把输出格式化成 API 想要的样子，比如 GLUE 数据集应当用 `dataset:glue` 来搜索。

这一点很关键，因为没有这份"如何书写某些参数"的小抄，你在用 API 搜索模型时很容易陷入沮丧！

现在我们知道了正确的参数，就能轻松搜索 API：

```
>>> models = api.list_models(filter = (
>>>     model_args.pipeline_tag.TextClassification, 
>>>     model_args.dataset.glue, 
>>>     model_args.library.PyTorch)
>>> )
>>> print(len(models))
```

```
    140
```

我们发现**140** 个匹配的模型符合我们的条件！（撰写本文时。）如果我们仔细看其中一个，会发现它确实对得上：

```

```

## 更进一步

我们看到如何用 `ModelSearchArguments` 和 `DatasetSearchArguments` 来去掉在 Hub 上搜索时的猜测，但如果你有一个非常复杂、杂乱的查询呢？

比如：我想搜索所有为 `text-classification` 和 `zero-shot` 分类两者训练的、在 Multi NLI 和 GLUE 数据集上训练的、且同时兼容 PyTorch 和 TensorFlow 的模型（一个更精确、用来命中上面那个模型的查询）。

要设置这个查询，我们会用 `ModelFilter` 类。它就是为处理这类情况而设计的，这样我们不必绞尽脑汁：

```
>>> filt = ModelFilter(
>>>     task = ["text-classification", "zero-shot-classification"],
>>>     trained_dataset = [model_args.dataset.multi_nli, model_args.dataset.glue],
>>>     library = ['pytorch', 'tensorflow']
>>> )
>>> api.list_models(filt)
```


## 魔法是什么？

简短说说背后那个给出这种类枚举-字典数据类型的魔法，即 `AttributeDictionary`。

它深受 [fastcore](https://fastcore.fast.ai/basics.html#AttrDict) 库里 `AttrDict` 类的启发，总体思路是拿一个普通字典，通过为字典里的每个键提供 tab 补全来为*探索式编程*强力升级。

如我们前面所见，当我们可以逐层探索嵌套字典时它更强大，比如 `model_args.dataset.glue`！

> 对熟悉 JavaScript 的人而言，我们模仿了 object 类的运作方式。

这个简单的工具类，在探索嵌套数据类型、试图理解里面有什么（比如一个 API 请求的返回！）时，能提供更以用户为中心的体验。

如前所述，我们在几个关键方面扩展了 `AttrDict`：

- 你可以用 `del model_args[key]` *或* `del model_args.key` 删除键
- 我们之前看到的那个干净的 `__repr__`

不过有一个很重要的概念要注意：如果一个键包含数字或特殊字符，它**必须**按字典索引，而*不是*按对象。

```
>>> from huggingface_hub.utils.endpoint_helpers import AttributeDictionary
```

一个很简短的例子是，如果我们有一个键为 `3_c` 的 `AttributeDictionary`：

```
>>> d = {"a":2, "b":3, "3_c":4}
>>> ad = AttributeDictionary(d)
```

```
>>> # As an attribute
>>> ad.3_c
```

```
 File "<ipython-input-6-c0fe109cf75d>", line 2
    ad.3_c
        ^
SyntaxError: invalid token
```

```
>>> # As a dictionary key
>>> ad["3_c"]
```

```
4
```
