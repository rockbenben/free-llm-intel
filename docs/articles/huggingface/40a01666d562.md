*为某个领域或任务专门化模型时，我们通常是在 Qwen、Gemma 等通用开源模型上做微调，于是它继承了为众多领域和通用应用而构建的词表。*

*在我们投入生产运行的一个作文评分器中，这套词表把模型最常写的文本切成了很多 token。本文抢先披露 VocabX 论文的部分结果（论文即将发布）：我们没有按词频、而是按每个 token 的成本来专门化词表，在不更换基础模型的前提下，把实测推理成本降低了 77%。*

[![同一句话，更少的 token：基础 tokenizer 是 14 个 token，VocabX 是 4 个](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/TYOhAFobnI4ss3UnNqMHc.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/TYOhAFobnI4ss3UnNqMHc.png)

tokenizer 通常被当作基础模型的一项固定属性，继承下来就不去动它。但对于专门服务于单一领域的模型，它可能是最大的成本杠杆之一，而且它在任何训练步骤之前就已经确定。

我们在生产环境运行的系统之一，是一个基于 Qwen3-4B 构建的葡萄牙语作文自动评分器。它接收作文、题目和支持文本，返回一份 JSON 评估，其中包含总分以及每项能力的评语。

这个模型本身已经很小，只有 40 亿参数，而且已经针对该任务训练过。然而它的 tokenizer 仍然是 Qwen3-4B 原本那套，为多种语言和多种文本而构建。在评分器中，它只用于一种语言（葡萄牙语）和一种响应格式。这带来两项成本：评分器每次请求写出的文本占用了超过所需的 token；而模型每生成一个 token，都要在一个 151,669 条的词表上打分，其中许多条目这个任务几乎从不使用。

我们用一种称为 VocabX 的方法重建了这套词表，基础模型、数据和训练配方都保持不变。本文中的数字来自论文的当前版本（仍在评审中），在正式发表前可能变化。

## 为所有人打造的词表

主流语言模型以 token 读写，而 tokenizer 决定文本如何变成 token。主流通用模型的 tokenizer 是在来自众多领域和语言的大规模文本集合上训练的，从源代码到合同再到中文。对一个通用模型而言，这个选择是合理的。

但对只用于单一领域的模型，它同时制造了两类浪费。

第一类是碎片化。tokenizer 恰恰把该领域重复最多的内容切成许多片段。在评分器中，每条响应都以相同的 JSON 外壳、相同的能力名称、相同的评语短语开头。在合同里，这些是样板条款；在代码里，是标识符。这些序列每一个都要花掉本该只需一个 token 的好几个 token，而模型在每次请求时都要为它们一一付费。

[![评分器在每条响应中写出的这一段，在基础 tokenizer 下是 12 个 token，VocabX 下是 1 个](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/K5De-hfTaOl9vUJItSijj.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/K5De-hfTaOl9vUJItSijj.png)

第二类是冗余。词表里带着成千上万个该领域从不使用的条目，而模型每生成一个 token 都要为所有条目计算分数。一个被调去评美国中学生物试卷的模型几乎永远不会写中文，却要在每一步计算每个中文 token 的概率。词表把该领域重复最多的内容切成许多片段，同时又带着该领域从不使用的条目。

[![基础 tokenizer 有 151,669 个词表条目，VocabX 是 64,767 个](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/Inl5L1IDqWUBbD0Xlq-JB.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/Inl5L1IDqWUBbD0Xlq-JB.png)

## 读便宜，写昂贵

自然的反应是数 token、想办法减少数量。但数量并不是账单。

要理解为什么生成的 token 更贵，先看看推理是如何运作的。它有两个阶段。在 *prefill* 阶段，模型通过网络单次前向处理整个输入：从 GPU 内存读取的每个权重都会被所有输入 token 复用，瓶颈是算力。在 *decode* 阶段，模型一次生成一个 token 的响应，每个 token 都需要一次完整的前向。每次读取的权重只用上几次，GPU 大部分时间都在等数据从内存送达：瓶颈变成了内存带宽。

这一效应在我们所处的场景中最强：以小到中等 batch 服务的小模型。把请求批处理可以把权重的读取分摊到多个请求上、缓解问题，但并没有解决它。在每个 decode 步骤，模型还要读取 KV cache，即保存已处理上下文、并随上下文增长的注意力内存。在我们测量的案例（评分器）中，生成一个 token 的成本是读取一个 token 的 7.4 倍，但这个比例会随硬件、问题、batch 大小、上下文长度等因素变化，而且可能更大。总体而言，方向是成立的：生成比读取更贵。

[![在我们测量的案例中，写一个 token 的成本是读一个的 7.4 倍](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/q-GjdgYd6GgXnv3-wJQsY.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/q-GjdgYd6GgXnv3-wJQsY.png)

想象一家物流公司按箱收费，但寄出的箱子比寄入的箱子贵七倍。减少箱子总数有帮助，减少寄出的箱子则带来七倍的帮助。一种对输入和输出同等压缩的方法，会错过大部分可节省的空间。

账单的第三个组成部分是词表本身。模型的最后一层，也就是 LM head，把内部状态转换成每个可能 token 的分数。为此，它为每个词表条目持有一行参数。在 Qwen3-4B 这个规模的模型里，这个矩阵占了近 10% 的参数。大模型可以毫无察觉地吸收这个比例，但它会压垮小模型。

而且这项成本不只付一次。输入层只查被读取 token 的那一行，但 LM head 对每个生成的 token 都要读取并乘以整个矩阵。由于 decode 本来就受内存带宽限制，每多一行，就意味着每一步要多搬运一份数据。一个该领域从不使用的条目，与一个高频条目成本完全相同。这就是为什么增加 token 可能同时降低数量、抬高账单。VocabX 没有把这一项放进它的选择准则，但它分两步控制词表规模：子词合并用更小的、领域专属词表替换基础词表，而 macro 在固定预算下进入。在评分器中，输出层从约 152,000 行降到约 65,000 行。

## 为什么现有方案不够好

调整模型的词表并不是新想法。文献中的参考方法，例如 fast vocabulary transfer（FVT）、multi-word tokenization（MWT）以及 Liquid AI 的[原位 tokenizer 扩展](https://www.liquid.ai/blog/tokenizer-expansion)（in-place BPE，即在原词表基础上继续训练 BPE），已经能减少碎片化。当我们在自己的问题上测试它们时，发现了两个局限。

**它们按频率而不是按成本挑选 token。** 一个在输入中经常出现的表达，对它们来说比一个在响应中出现较少的表达更有价值，哪怕后者服务起来更昂贵。

**它们只作用于单一层面。** 它们要么调整词如何被切成片段，要么把整段短语合并成一个 token。这三者没有一个在同一准则下同时做这两件事。而评分器最大的浪费恰恰在于冗长且重复的片段，比如 JSON 外壳，子词方法只能通过逐个合并各部分才能触及它。

## 我们如何解决

VocabX 同时应对这两个局限，外加第三个问题——它在解决第一个问题的最直白路径上就会出现。

**首先，我们换了问题。** 我们不再问某个候选能省下多少个 token，而是问它能省下多少成本和时间。每个被消除的 token 都乘以它所在字段的价格：system prompt、用户消息或模型响应。在我们测量过的案例（评分器）中，响应里省下的一个 token 价值是输入里省下的一个 token 的 7.4 倍，词表也据此构建。

**其次，我们同时作用于两个层面。** 回到那家物流公司：你可以把每件物品包得更好来减少箱子，也可以意识到同一套十二件工具包每周都要寄一次，于是把整套工具装进一个箱子。VocabX 两者都做。在子词层面，它重建领域词汇被切成片段的方式。在多词层面，它寻找重复出现的整段片段，从简短表达一直到整行文本和 JSON 外壳，把每一段变成一个 token，我们称之为 macro token。两个层面都在同一成本准则下挑选，各有各的预算。

[![十二个箱子变成一个，7 个 token 变成一个 macro token](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/B5Wig-4nTEutpFZlGQ6sk.gif)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/B5Wig-4nTEutpFZlGQ6sk.gif)

为了找到这些片段，我们使用了五个 miner，也就是在语料中自动搜索重复片段的机制，每个专攻一类重复：长词、整行、表达式、完整句子，以及带标点的结构，例如 JSON 和标签。在八个语料上平均来看，最后一个贡献最大，而在代码上它单独就贡献了 17.5 个点。缺少这五个中的任何一个，评分器上的 token 缩减率都会下降 55.6 个点。

[![两个层面，一个成本准则](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/_EdPyU7R3xdomvFxuadPY.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/_EdPyU7R3xdomvFxuadPY.png)

**第三，我们估计样本看不到的部分。** 按成本挑选 token，需要知道每个候选在已被选中的 token 之后还能省下多少。精确测量这一点，意味着每次选择之后都要重新处理整个语料，而这要做上万次。在大规模场景下常见的做法是在文档样本上测量，但这样一来，不在样本中的候选得到的增益是零。

一个在 50,000 篇文档中出现 37 次的表达，在 400 篇文档的样本里大约只有 26% 的概率出现。在一个合同语料中，只有 16.6% 的候选出现在 400 篇文档的样本里，其余的从未被评估。

[![37 次出现没有一次落进这 400 篇文档的样本](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/zxfdAxNxsvfBCBNeUThx5.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/zxfdAxNxsvfBCBNeUThx5.png)

一个候选的增益有两部分。一部分是它在整个语料上能省多少，这部分可以精确统计，不需要样本。另一部分是这份节省中有多少还未被已选中的 token 覆盖，只有这部分需要估计。对于样本看不到的候选，我们根据可见候选的行为做统计估计，而不是直接记为零。一个在样本中罕见但在语料中高频的候选，因此重新回到候选之列。

仅这一处改动，在同样的样本和同样的预算下，把合同语料上的 token 缩减率从 44.7% 提升到 52.8%。

[![用估计代替零：token 缩减率从 44.7% 提升到 52.8%](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/PxGLMRrjTPVYDW8rlDuBd.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/PxGLMRrjTPVYDW8rlDuBd.png)

## 评分器上发生了什么变化

为了衡量真实效果，我们用相同的基础模型、相同的数据、相同的配方和相同的随机种子训练了七个版本的评分器。它们之间唯一的差别是 tokenizer。七个版本都在同一台测试机上跑同样的 500 个请求，机器配有 RTX 5090 GPU 和 vLLM 推理服务器，成本按实测运行时间计算。

[![评分器结果：成本降低 77.0%，bench 分数从 0.703 提升到 0.810](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/7CKshmOEsUkemfgL9Mopn.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/7CKshmOEsUkemfgL9Mopn.png)

模型的响应平均从 350 个 token 降到 101 个 token。成本下降 77.0%。质量以 bench 分数衡量（该分数综合了评分准确率，以及筛除跑题或违规作文的准确率），从 0.703 提升到 0.810。

为此我们经历了一次路线修正。词表的第一个版本把每项能力的分数与周围的 JSON 融合成单个 macro token。那是最紧凑的方案，但质量下降了：bench 分数为 0.689，低于生产评分器的 0.703。把分数放进 macro 之后，分数与结构的每种组合都变成了同一个 token 的不同变体，模型在一步之内同时做出了这两个选择。让分数拥有自己的 token，每条响应多花 2 个 token，bench 分数提升到 0.810，而且在测量中还更便宜：降低 77.0%，而融合版本是 73.3%。

这个教训不只适用于评分器。当被压缩的片段承载的正是模型存在的意义所在的那个决策时，压缩是有代价的。目标不是尽可能便宜的词表，而是在保住真正重要的 token 的前提下最便宜的词表。

## 超越评分器

为了弄清这一收益是否只适用于我们的场景，我们在五个公开领域（合同、医学论文、科学论文、新闻和 Python 代码）和三个模型家族（Qwen3、Llama-3.1 和 Gemma-3）上，把 VocabX 与三种参考方法做了比较。所有方法使用相同的挖掘文档和测试文档，以及相同的词表上限。

在全部十五种组合中，VocabX 的压缩幅度都超过最强的参考方法，领先 1.2 到 9.3 个点。在估算推理成本上，裁剪版 VocabX 同样在十五种组合中全部领先，在 Qwen3 上平均领先 10.2 个点、Llama-3.1 上 7.5 个点、Gemma-3 上 13.6 个点。在合同上，裁剪版以 113,426 个词表条目达到 62.6% 的 token 缩减率，而最佳 in-place BPE 配置是 61.8%，后者用了 207,803 个条目。

[![VocabX 的平均领先：+10.2（Qwen3）、+7.5（Llama-3.1）、+13.6（Gemma-3）个点](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/bCCQQjpY6tU5ZAD3hXOeN.png)](https://cdn-uploads.huggingface.co/production/uploads/6a725daa5ca641a21ab61956/bCCQQjpY6tU5ZAD3hXOeN.png)

## 只为真正重要的 token 付费

VocabX 并不会让模型更聪明。它只是让模型不再为那些本不需要逐段写出的文本付费，也不再为一个永远用不上的词表打分。在我们的评分器中，这在同样的基础模型和同样的训练配方下，把实测推理成本降低了 77%。

专门化通常从数据和权重开始。它也可以从更早的一层开始，也就是词表。

完整方法、每个实验的表格以及被舍弃的干预措施，都将收录在即将发布的 VocabX 论文中。
