# 将 Trainium3 带上赛道：用 LTX-2.5 生成视频










得益于我们与 AWS 的合作，我们有幸获得了一台 Trainium3 机器（[trn3.48xlarge](https://aws.amazon.com/ec2/instance-types/trn3/)，64 个 NeuronCore）为期一个月的使用权。这个月的大部分时间，我们都在这台机器上测试 Hugging Face 模型，并让更多模型跑通。

还剩五天时，我允许自己找点乐子。当你拥有一辆法拉利，总会时不时想把它开上赛道。于是我自问：不如试试生成视频？

我选了 Lightricks 的 [LTX-2.5](https://huggingface.co/Lightricks/LTX-2.5-Diffusers)，它能同时生成视频和声音。到最后，在模型加载完成之后，在机器一半的算力上，生成一段带声音的 10 秒片段需要 22 到 23 秒。结果如下。

*一只海豹梦见温暖的沙滩。完全在 Trainium3 上生成。*

## 两个目标

我有两个目标。第一个是看看在 Trainium3 上用 [diffusers](https://github.com/huggingface/diffusers) 生成视频有多容易。不是示例里那种简单片段：我想按脚本制作短片，更接近真实用例，就像给一部电影打草稿。第二个是性能。我想接近用 CUDA、或用 LTX 自家 API 所能达到的水平。

关于 CUDA，我没能找到真正可对比的数字。唯一的数字是 LTX 的说法：在四块 B200 GPU 上，一段 10 秒 720p 片段耗时 6.8 秒，但没有说明它是如何测得的。于是我把 CUDA 放到一边，改为与 LTX 的在线 API 比较；[LTX 称](https://venturebeat.com/technology/ltx-2-5-can-generate-a-10-second-ai-video-from-an-image-in-just-6-8-seconds-on-nvidia-superchips-and-its-open-weights)，它能在 23.7 秒内生成一段 10 秒 1080p 片段。最终，这套配置与之持平，甚至快了约一秒：在模型加载完成后，在机器一半的算力上，一段 2048×1024 的 10 秒片段耗时 22 到 23 秒。考虑到我用来优化 pipeline 的时间少得可怜，这已经不错了。

## 工作原理

输入就是一部影片：一个 JSON 形式的镜头列表，每个镜头有一个名称和一个 prompt，很像分镜脚本。LTX-2.5 对长 prompt 效果更好，因此每个 prompt 都是一段文字，分别描述风格、主体、运动、镜头、光线和声音。下面是海豹影片的文件，其中 prompt 已缩短：

```
[
  {"name": "dream", "prompt": "Style: cinematic, realistic, shallow depth of field. A plump seal ... is fast asleep on warm golden sand under palm trees ...",
   "seed": 3},
  {"name": "nap", "prompt": "Style: cinematic, realistic, wide-angle lens. ... a plump grey seal is fast asleep on a small ice floe ...",
   "seed": 1, "to": {"shot": "iceberg", "frames": 9}},
  {"name": "iceberg", "prompt": "Style: cinematic, realistic, wide-angle lens. ... the whole iceberg slowly rolls over ... and washes over the seal. ..."},
  {"name": "shake", "prompt": "Style: cinematic, realistic, wide-angle lens. ... It slowly shakes its head and body ... and flops down on its belly on the floe, ...",
   "from": {"shot": "iceberg", "frames": 25}}
]
```

每个镜头都有一个 `name` 和一个 `prompt`，还可以有一个 `seed`，用来保留我从多个 take 里挑中的那一条。镜头之间用两个键串联起来。这种串联正是关键所在，因为仅凭 prompt 无法让主体从一个镜头延续到下一个镜头：

- `from`：该镜头从较早镜头的最后几帧开始。从较早镜头的最后一帧开始，可以让主体在剪辑点两侧保持外观一致；从它的最后 25 帧（1 秒）开始，还能延续运动。
- `to`：该镜头结束在较晚镜头的开头几帧上，从而过渡到该镜头。

镜头还可以裁剪，或在上面绘制字幕。

用镜头制作影片的方式类似做动画，有两条路可走。一是连续动作法（straight ahead）：每个镜头紧接着前一个镜头往下做。二是关键姿势法（pose to pose）：先制作关键镜头，直到做出你满意的一个；然后让它之前的镜头结束在它的开头几帧（`to`）上，让它之后的镜头从它的最后几帧（`from`）开始。当一部影片层层铺垫推向一个高潮（payoff，即一切都指向的那一刻），这个高潮就是关键镜头。我是靠反复试错找到这个顺序的，并按关键姿势法制作海豹影片，起点是 `iceberg`。

高潮是 `iceberg`：冰山翻了过来，它掀起的浪浇透了海豹。`nap` 是睡觉的海豹，它结束在 `iceberg` 的开头 9 帧（`to`）上，这样海豹、浮冰和冰山一直延续到高潮都保持一致。`shake` 从 `iceberg` 的最后 25 帧开始（`from`）：湿淋淋的海豹抖掉身上的水，扑通趴到浮冰上。`dream` 是单独制作的，再用一个剪辑把它与其余部分衔接起来。

海豹影片的镜头链。作为高潮的 `iceberg` 最先制作；`nap` 结束在它的开头 9 帧上，`shake` 从它的最后 25 帧开始，因此海豹、浮冰和冰山保持一致。

在 diffusers 这一侧，三条 pipeline 共享 [LTX-2.5](https://huggingface.co/Lightricks/LTX-2.5-Diffusers) 的模型。`LTX2Pipeline` 仅凭 prompt 制作镜头，`LTX2ConditionPipeline` 制作从其他镜头的帧开始或结束的镜头。这两条 pipeline 遵循模型卡里的两阶段蒸馏配方：先走 8 步，然后由第三条 pipeline `LTX2LatentUpsamplePipeline` 把 latent 上采样 ×2，再走最后 3 步。

生成全部由 diffusers 的 pipeline 完成。影片部分是在此之上约 160 行 Python 代码：读取影片文件，对镜头排序，让每个关键帧都在需要它的镜头之前就位，并切出要交接的帧；然后裁剪、加字幕、平衡声音并组装影片。代码在 [dacorvo/video-generation](https://github.com/dacorvo/video-generation)。我保留的影片放在 [dacorvo/video-generation](https://huggingface.co/buckets/dacorvo/video-generation/tree/entertainment) bucket 里，并附有各自的 JSON 文件：海豹、狐狸和山羊；其中山羊影片裁剪了两个镜头，并在它的高潮画面上画了字幕。

*狐狸影片：雪中漫步，按“连续动作法”制作：每个镜头紧接着前一个镜头往下做。*

*山羊影片：两个被裁剪的镜头，以及在高潮画面上绘制的字幕。*

## 在 Trainium3 上运行

开箱即用时，模型无法在 NeuronCores 上运行：transformer 放不进一个 NeuronCore，而 diffusers 也没有拆分它的方案。第一次跑通的尝试（模型卡里的 pipeline，把 transformer 拆到 4 个核上，外加少量补丁）为一段 10 秒片段耗时约 **5 分 20 秒**，而其中 NeuronCores 实际计算的时间只有约 45 秒。更何况，目标分辨率还遥不可及。

五天后：

| 带声音的 10 秒片段 | NeuronCores | 实际耗时 | 在 NeuronCores 上的时间 | 对比第一次尝试 |
| --- | --- | --- | --- | --- |
| 第一次尝试，960×544 | 4 | 5 分 20 秒 | 45 秒 | 1× |
| 优化后，2048×1024（像素约多 4×） | 32 | 22 到 23 秒 | 15 秒 | 14× |

做到这一步花了三类功夫：让模型能在 NeuronCores 上运行（需要张量并行），把它拆分到更多 NeuronCore 上（序列并行），以及让主机跟得上它们。

TP-4 × SP-8：一个片段用上 32 个核。权重按 4 路拆分，每个核分到每一层的一个条带；视频 token 按 8 路拆分，每颗芯片分到片段的一段。

下面大多数修复都在设备侧，大部分精力也花在那里。而端到端最大的节省来自主机：这是最容易摘的果子，因为浪费显然就出在那里。

### 让它跑起来做了哪些工作

| 问题 | 变通方案 | 结果 |
| --- | --- | --- |
| transformer 放不进一个 NeuronCore，而 diffusers 没有针对它的张量并行方案 | 一个[方案](https://github.com/dacorvo/video-generation/blob/main/parallel.py#L50)，以及一个在单个 rank 的注意力头上运行的[注意力处理器](https://github.com/dacorvo/video-generation/blob/main/parallel.py#L65) | transformer 在 4 个核上运行 |
| 文本编码器无法和 transformer 一起放进一个 NeuronCore，因此它跑在 CPU 上。diffusers 支持这样拆分 pipeline，但它的 LTX-2 pipeline 会在 NeuronCores 上给文本编码器提供输入 | 把 pipeline 固定在主机上，并把 transformer 的输入搬到核上、输出搬回来 | pipeline 跑起来了，且 transformer 在核上 |
| 把 transformer 作为一个图编译时，它在某个尺寸下返回 NaN；而且即使所有图都在缓存里，每个新进程仍会重新追踪它 | 用 `compile_repeated_blocks` 编译单个 block | 输出为有限值，追踪时间从 388 秒降到 18 秒 |
| torch-neuronx 完全用 bf16 计算 bf16 GELU，连常量也不例外（[#1049](https://github.com/aws-neuron/torch-neuronx/issues/1049)） | 改用 fp32 计算 GELU | transformer 相对 fp32 的误差：0.297 → 0.158（CPU bf16：0.160） |
| 在 2048×1024 下，按 4 路拆分的 transformer block 图加载失败 | 在此之上把视频 token 再按 8 路拆分（序列并行）：在 diffusers 的 `set_attn_processor` 钩子上挂两个自定义注意力处理器，每个处理器在各自的集合通信调用前后做几次张量 reshape（[代码](https://github.com/dacorvo/video-generation/blob/main/parallel.py#L141)） | 第 2 阶段在 4 × 8 = 32 个核上运行，每步 3.0 秒 |
| 从帧开始的镜头每个视频 token 各有一个 timestep，其 block 图加载失败 | 只嵌入两个 timestep，再为每个 token 选一个（[代码](https://github.com/dacorvo/video-generation/blob/main/timesteps.py)） | 从帧开始的镜头耗时与从 prompt 开始的镜头大致相当 |

### 让它变快做了哪些工作

| 问题 | 变通方案 | 收益 |
| --- | --- | --- |
| 每个 rank（每个 NeuronCore 一个进程）都运行整个 pipeline，而且它们都在同一个 socket 的 CPU 上编码 prompt | 只在 rank 0 上运行 pipeline，并把每次调用的参数发送给其他 rank | prompt 编码：约 205 秒 → 7.5 秒 |
| torch-neuronx 的分配器让大部分内存段闲置未用（[#1052](https://github.com/aws-neuron/torch-neuronx/issues/1052)） | 把参数打包进不超过 1 GiB 的缓冲区 | 每个核的内存：22.96 GiB → 10.2 GiB |
| 除非序列长度是 128 个 token 的整数倍，注意力会以普通算子运行 | 以 1024×512（每帧 512 个 token）生成，并设置 `NEURON_LOGICAL_NC_CONFIG=2` | transformer 单步：4.3 秒 → 3.0 秒 |
| 视频解码在 CPU 上很慢，而增加 CPU 核也没有用 | 在 NeuronCores 上按帧拆分解码，再通过共享内存把帧传给 rank 0 | 2048×1024 下的解码：357 秒 → 1.6 秒 |
| 复制到设备上的跨步切片（strided slice）会由设备上一次缓慢的拷贝来填充（[#1050](https://github.com/aws-neuron/torch-neuronx/issues/1050)） | 复制前先调用 [`.contiguous()`](https://github.com/dacorvo/video-generation/blob/main/parallel.py#L231-L235) | 16 个核上的单步：5.6 秒 → 1.0 秒 |
| 只有 rank 0 运行 pipeline 的 CPU 阶段（文本编码器、上采样器、声码器），但每个 rank 都会拿到一个节点范围的 torch 线程池，31 个 rank 会把它饿死 | 把 rank 0 的线程固定到其他 rank 不用的 CPU 上，并把其他 rank 的线程数限制在各自应得的份额（[代码](https://github.com/dacorvo/video-generation/blob/main/generate.py#L330)） | prompt 编码：7.4 秒 → 3.3 秒。第 1 阶段单步：0.9 秒 → 0.6 秒 |
| pipeline 会把 prompt 填充到 1024 个 token，而 CPU 上的文本编码器连填充部分也一起编码 | 只对 prompt 本身的 token 运行文本编码器 | prompt 编码：3.4 秒 → 1.4 秒 |

有三个问题始终没有得到解释：transformer 作为单个图编译时会在某个尺寸下返回 NaN；第一个以关键帧结束的镜头在每个新进程里都很慢（即使所有图都在缓存中）；latent 上采样器无法与 transformer 一起加载，因此它留在了 CPU 上。

其中一些问题正在上游修复。[diffusers#15420](https://github.com/huggingface/diffusers/pull/15420)（仍未合并）修复 LTX-2 的 pipeline，这将使上面的第二个变通方案不再必要。[diffusers#14725](https://github.com/huggingface/diffusers/pull/14725)（至今仍未合并）把张量并行与上下文并行统一进一个 `ParallelConfig`，并且计划为 LTX-2.5 提供一个 `_tp_plan`。

## 经验教训

- **两边都降得很猛：主机与设备。** 跑起来之后，一个片段的主机时间从约 280 秒降到约 8 秒（约 35×），在 NeuronCores 上的时间从 45 秒降到 15 秒（3×，且像素数是四倍，还多了一个第一次尝试根本加载不了的第二阶段）。
- **序列并行才是一个片段用上整台机器的办法。** 张量并行是被内存逼出来的（transformer 放不进一个核），并受 32 个注意力头的上限约束。把序列拆分到更多核上，才让 64 个 NeuronCore 中的 32 个投入到单个片段，也才让 2048×1024 真正成为可能——办法是缩小每个核的图，直到它能加载。
- **在 Trainium 上，要为图的大小做好规划。** 形状决定注意力是否走快速 kernel，而过大的图会加载失败。
- **先拿 CPU 做对照。** 模型的每一种拆分都先在 CPU 上检查，再放到设备上运行；正是与 CPU 的对比发现了 GELU 问题。
- **让被追踪的代码保持稳定。** 在我用的那个构建里，torch-neuronx 的缓存键包含每个被追踪算子的文件名与行号，因此一次编辑就可能触发每个图长达 30 分钟的重新编译。这个问题我之前已经报告过（[aws-neuron/torch-neuronx#1027](https://github.com/aws-neuron/torch-neuronx/issues/1027)），现在该 issue 已关闭。
- **一部影片需要的不仅是 prompt。** 仅靠 prompt 无法让一个角色、或一座山，从一个镜头延续到下一个镜头，因此镜头会从其他镜头的帧开始或结束。每个镜头也保持在一个地点：狐狸影片早期版本里，有一个镜头把狐狸从森林带到湖边时，模型叠化成了另一只狐狸。
- **每个镜头多拍几个 take。** 模型经常把某个细节弄错：同一个 prompt 在 4 个 take 里有 3 个给山羊生成了滑稽的角。我为每个新镜头都做 4 个 take，再挑一个。

## 专业用例

性能方面，模型加载完成后，一段带声音的 10 秒 2048×1024 片段需要 22 到 23 秒。在实例一半的算力上，这已可与 LTX 的付费 API 匹敌。真正的服务会让进程常驻，因为加载模型约需 3 分钟，第一个片段还要再花 80 秒。

功能方面，diffusers 具备为一部电影打草稿所需的能力。镜头来自 prompt，并通过从其他镜头的帧开始或结束，让主体从一个镜头延续到下一个镜头。不同 take 靠 seed 区分，影片文件会记住我选中的那一个。用同样的代码和影片文件重跑，你会逐字节拿回同一部影片。镜头也可以从一张图开始，例如分镜帧或角色设定图；条件 pipeline 会像对待帧一样处理它（我没有在影片里试过这一招）。

让它还停留在草稿阶段的原因：

- 模型仍会把细节弄错，所以每个新镜头都需要多拍几个 take。
- 每个镜头各自生成声音。影片会把背景音量拉平，但声音不会从一个镜头延续到下一个镜头。
- 一个镜头最长 20 秒，这是模型的极限。

## 从影片到世界模型

LTX 称 LTX-2.5 为世界模型，机器人技术是其中新兴的用途。机器人、汽车和无人机从摄像头所见内容的视频中学习，而世界模型可以生成更多这类视频，包括那些太罕见或拍摄风险太高的事件。所以我也用同样的代码在真实素材上试了一把：一个镜头可以从真实摄像头片段的第一秒开始，并虚构接下来发生的事。只给一帧不够，因为模型无法从一帧判断物体运动得多快。

下面是一台 Fourier GR1-T2 人形机器人头部摄像头的画面（片段来自 NVIDIA 的 [GR1-100](https://huggingface.co/datasets/nvidia/PhysicalAI-Robotics-GR00T-GR1)），镜头俯视一张桌子。在真实的 6 秒片段里，机器人的左手从盘子里拿起一个橙子，丢进托盘中。模型只看到该片段的第一秒（双手抬起，什么都还没动），其余部分全靠自己虚构。真实发生的情况，与它的虚构并排如下：

*来自 GR1-T2 人形机器人头部摄像头的真实素材，以及 LTX-2.5 根据其第一秒虚构出的后续。*

同样的场景，同样的抓取：模型自行虚构出了抓取动作，并让桌子、双手和水果与真实素材保持一致。更有意思的是那些没有发生的事件。从同一秒开始，只改动 prompt，一个人俯身也去抓那个橙子，然后人手和机器人的手一起把它送到托盘里。五个 take，先是真实素材：

*真实片段，然后是五个生成的 take，内容是一个人帮机器人搬橙子。*

在不同 take 里，这个人的手势和时机各不相同，而机器人的手臂会随之调整。这正是它对训练的吸引力：不是片段的一个延续，而是一组延续的分布，每一个都能从其影片文件和 seed 复现。

该 bucket 的 [robotics](https://huggingface.co/buckets/dacorvo/video-generation/tree/robotics) 文件夹里有这五个 take 及其 JSON 文件，还有一个来自暴风雪中汽车前视摄像头的第二个示例（[Boreas](https://www.boreas.utias.utoronto.ca/)）；在那里，替代事件是一辆路过的卡车把雪泥甩到镜头上。当要求模型改成让汽车加速时，它保持了原速：prompt 并不能推翻第一秒素材已经暗示的内容。

这些视频遵循的是 prompt，而不是机器人或汽车的指令：若要用于训练，生成需要以这些动作为条件。为此，团队会用自己的机器人的帧和动作，微调 [LTX-2.5 的预训练 checkpoint](https://huggingface.co/Lightricks/LTX-2.5-Pre-Trained)。

这辆法拉利只用了一半的气缸，就跑完了赛道。
