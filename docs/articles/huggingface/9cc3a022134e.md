随着用户寻找可以高效部署、又足够能干的模型，小型语言模型正变得越来越重要。社区已经产出了一批引人入胜的强大小模型，每一个都在推进这个规模下可能性的边界。借 SmolLM3，我们很高兴贡献一个全新的、完全开放的 3B 竞品模型：

- 基座模型：[https://hf.co/HuggingFaceTB/SmolLM3-3B-Base](https://hf.co/HuggingFaceTB/SmolLM3-3B-Base)
- 指令与推理模型：[https://hf.co/HuggingFaceTB/SmolLM3-3B](https://hf.co/HuggingFaceTB/SmolLM3-3B)

**SmolLM3 正处于效率的甜点位置。** 我们的 3B 模型超过了 Llama-3.2-3B 和 Qwen2.5-3B，同时与更大的 4B 替代方案（Qwen3 与 Gemma3）不相上下。除了性能数字，我们还完整公开了如何用公开数据集和训练框架构建它的过程。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(17).png)

模型概要：

- **3B 模型**，在 11T 词元上训练，是 3B 规模的最先进水平，并且可与 4B 模型竞争
- **指令模型**具备**双模式推理**，支持 `think`/`no_think` 模式
- **多语言支持**覆盖 6 种语言：英语、法语、西班牙语、德语、意大利语和葡萄牙语
- **长上下文**支持到 128k，采用 NoPE 并使用 YaRN

**完整配方：** 我们随 SmolLM3 一并公布工程蓝图。它包含架构细节、精确的数据配比（展示我们如何在三阶段预训练中逐步提升各领域性能），以及构建混合推理模型的方法论。通常，要拿到这样的结果得花上几个月做逆向工程。而我们直接给出完整方法。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/smollm3-whiteprint.png)

无论你是要训练自己的模型，还是想理解是什么在这个规模下驱动性能，这份蓝图都会揭示竞争力 3B 表现背后的工程故事。

我们来看看预训练阶段。

# 预训练

SmolLM3 相对前代同时改变了架构和数据配比。我们先看架构与训练配置！

## **架构与训练细节**

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(18).png)

SmolLM3 遵循与 SmolLM2 类似的、带词嵌入绑定的 Transformer 解码器架构，基于 Llama 架构并针对效率和长上下文性能做了几处关键改动。

**分组查询注意力（GQA）：** 我们用 4 组的分组查询注意力替换了多头注意力。在一个用 [FineWeb-Edu](https://huggingface.co/datasets/HuggingFaceFW/fineweb-edu) 的 100B 词元训练的 3B 模型上做的消融实验显示，GQA 与多头注意力性能相当，同时显著缩小了推理时的 KV cache 大小。

**NoPE：** 我们实现了来自 "[RoPE to NoRoPE and Back Again: A New Hybrid Attention Strategy](https://huggingface.co/papers/2501.18795)"（Yang et al., 2025）的 NoPE，有选择地从每第 4 层移除旋转位置编码。消融证实，这种方式在不影响短上下文能力的前提下改善了长上下文性能。

**文档内掩码（Intra-Document Masking）：** 按照 "[Analysing The Impact of Sequence Composition on Language Model Pre-Training](https://huggingface.co/papers/2402.13991)"，训练时我们用注意力掩码确保同一训练序列里来自不同文档的词元不会相互注意。与 Llama 3 类似，这有助于更快、更稳定的长上下文训练，同时保持短上下文性能。

**训练稳定性：** 按照 OLMo 2，我们从嵌入层移除权重衰减以提升训练稳定性。这一改动带来了更稳定的训练动态——消融显示，嵌入范数在训练过程中自然稳定到健康的数值，且不影响整体性能。

以上所有改动都通过相同 3B 架构、在 FineWeb-Edu 的 100B 词元上的消融实验验证，确保每个改动要么提升性能，要么保持性能同时带来其他好处。

训练配置：我们使用 2.36M 词元的全局批大小、4096 序列长度、2e-4 学习率、AdamW 优化器（beta1: 0.9, beta2: 0.95）、权重衰减 0.1、梯度裁剪 1。我们使用 WSD（预热-稳定-衰减）调度器，2000 步预热，最后 10% 训练步线性衰减到 0。训练用 [nanotron](https://github.com/huggingface/nanotron) 框架，数据处理用 [datatrove](https://github.com/huggingface/datatrove)，评估用 [lighteval](https://github.com/huggingface/lighteval)。模型在 384 块 H100 GPU 上训练了 24 天。分布式训练设置见下图。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(19).png)

除了架构改动，我们还消融并改进了训练配方。我们来细看。

## **数据配比与训练阶段**

延续 SmolLM2 的多阶段方法，我们以三阶段训练策略在 11.2T 词元上训练 SmolLM3，混合网页、数学和代码数据并让比例不断演进。我们在 50B 到 100B 词元训练的 3B 模型上做了大量消融，以确定数据配比和各部分比例。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(20).png)

预训练由以下阶段构成，也见上图：

- **阶段 1：稳定期（0T → 8T 词元）** 这一基础阶段用我们的核心数据配比建立稳健的通用能力：网页 85%（其中 12% 多语言）——FineWeb-Edu、DCLM、FineWeb2 和 FineWeb2-HQ；代码 12%——The Stack v2（16 种编程语言）、StarCoder2 的 pull request、Jupyter 和 Kaggle notebook、GitHub issue 和 StackExchange；数学 3%——FineMath3+ 和 InfiWebMath3+。
- **阶段 2：稳定期（8T → 10T 词元）** 我们引入更高质量的数学和代码数据集，同时维持良好的网页覆盖：网页 75%（其中 12% 多语言）；代码 15%——加入 Stack-Edu；数学 10%——引入 FineMath4+、InfiWebMath4+ 和 MegaMath（含 Qwen 问答、Pro 合成改写，以及文本与代码交织块）。
- **阶段 3：衰减期（10T → 11.1T 词元）** 最后阶段进一步上采样数学和代码数据：网页 63%（其中 12% 多语言）；代码 24%——上采样高质量代码数据；数学 13%——上采样数学数据并引入指令与推理数据集，如 OpenMathReasoning。

凭借这些阶段和配比，基座模型取得了非常有竞争力的表现，详情见评估部分。带精确数据权重的 nanotron 训练配置见[这里](https://huggingface.co/datasets/HuggingFaceTB/smollm3-configs)。我们还会公开训练日志和中间检查点。

主预训练之后，我们在一个中期训练阶段针对长上下文和推理对模型做了改进。

# 中期训练

我们把长上下文适配和推理适配称为"中期训练"。它们比主预训练短得多，但仍然是相对通用、旨在改善这两个领域的方式。我们先看长上下文训练。

## **长上下文扩展**

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(21).png)

主预训练之后，我们又在额外的 100B 词元上训练 SmolLM3 以扩展上下文长度。我们分两阶段顺序扩展上下文窗口，各 50B 词元：先从 4k 过渡到 32k，把 RoPE theta 增到 1.5M；再从 32k 到 64k，把 RoPE theta 增到 5M。两阶段都上采样了数学、代码和推理数据。消融中我们发现，除了配比里本来就长的样本之外，再专门上采样长上下文数据（如代码仓库、书籍、长网页）并不会进一步提升 RULER 和 HELMET 基准上的表现。使用 NoPE，并在更长的序列、更大的 RoPE theta 值的衰减配比数据上训练，就足以达到直至 64k 都有竞争力的长上下文性能。

沿用 Qwen2.5，我们用 YARN 外推到超出训练上下文的长度。推理时，模型可以处理直至 128k 的上下文（在 64k 训练长度上扩展 2 倍）。

## **推理中期训练**

扩展上下文长度之后，我们在中期训练阶段融入推理能力。中期训练与预训练、后训练阶段的主要区别在于：我们瞄准的是一种通用能力，而尚未聚焦到特定领域。就我们而言，我们希望训练模型进行推理，而不针对数学或代码这样的特定领域。

我们的中期训练数据集包含 35B 词元，来自 Open Thought 的 [OpenThoughts3-1.2M](https://huggingface.co/datasets/open-thoughts/OpenThoughts3-1.2M) 以及 NVIDIA 的 [Llama-Nemotron-Post-Training-Dataset-v1.1](https://huggingface.co/datasets/nvidia/Llama-Nemotron-Post-Training-Dataset) 中带 R1 推理轨迹的一个子集。我们使用 ChatML 聊天模板和[带包裹的打包](https://huggingface.co/docs/trl/main/en/reducing_memory_usage#packing)，以免给模型提供太多结构。我们把模型训练了 4 个 epoch（约 140B 词元），并把该检查点用于后续 SFT 阶段。

# 后训练

[DeepSeek R1](https://arxiv.org/abs/2501.12948) 和 [Qwen3](https://arxiv.org/abs/2505.09388) 这类推理模型的发布证明了，当模型能进行显式推理时会涌现出强大能力。然而，社区仍然缺少完全开放、使用公开数据集来构建同时支持推理与非推理模式的双指令模型的配方。现有大多数方法涉及复杂的强化学习流程和专有数据集，让研究者难以复现和在此基础上继续构建。

本节说明我们如何攻克这些挑战，并分享构建双指令模型的完整配方。我们详述如何通过一个精心设计的训练管线在推理与非推理模式之间平衡性能——该管线包括面向通用推理能力的中期训练、用合成数据生成的监督微调，以及使用锚定偏好优化（Anchored Preference Optimization，APO）——一种近期的 DPO 变体——进行的对齐。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(22).png)

## **构建聊天模板**

在进入训练方法之前，先确立用户如何与我们的双模式模型交互很关键。聊天模板是让用户在推理与非推理模式之间无缝切换的接口，它的设计直接影响我们的训练数据格式和模型行为。SmolLM3 的聊天模板允许用户在对话过程中控制推理模式。用户可以在系统提示词中加入 `/think` 和 `/no_think` 标记，分别激活推理或非推理模式。在非推理模式下，我们像 Qwen3 那样用空的 think 区块预填充模型回复，以确保直接作答而不显式推理。

SmolLM3 支持工具调用，其聊天模板为工具描述设置了两个不同的区块：XML Tools 和 Python Tools。在我们实验中，这种区分有利于模型准确解读每种格式下的工具定义。

聊天模板为两种推理模式都提供了默认系统消息，并附带一个元数据区块，包含日期、知识截止日期和当前推理模式。用户可以通过提供带 `system` 角色的消息来替换默认系统消息。元数据区块可以通过在系统提示词中使用 `/system_override` 标记来排除，为特定用例提供灵活性。

## **监督微调**

在推理中期训练阶段（我们用 140B 词元的通用推理数据训练模型）之后，我们进行监督微调（SFT），在推理与非推理模式下融入数学、代码、通用推理、指令遵循、多语言和工具调用等能力。训练双模式模型要求精心平衡数据配比，以在所有目标领域的两种模式上都保持强劲表现。为评估 SmolLM3 在整个训练过程中的表现，我们跟踪了以下领域：数学、代码、通用推理、指令遵循和多语言。

我们在构建推理模式数据集时遇到的主要挑战，是某些领域缺少含推理轨迹的数据集。为弥补这一空缺，我们用现有非推理数据集中的提示词去以推理模式提示 [Qwen3-32B](https://huggingface.co/Qwen/Qwen3-32B)，从而生成合成数据。这让我们能够提升模型在推理模式下起初表现不佳的领域的性能，例如多轮对话、多语言和日常对话。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(23).png)

我们最终的数据配比是大量消融的结果，研究了推理与非推理词元的最佳比例以及每种模式内部的组成。得到的 SFT 数据集包含 1.8B 词元：非推理模式 1B、推理模式 0.8B，由 12 个非推理数据集和 10 个含推理轨迹的数据集组成。我们训练了 4 个 epoch（约 8B 词元），使用 [BFD（最优递减拟合）打包](https://github.com/huggingface/trl/pull/3521)，并对用户轮次和工具调用结果掩蔽损失。

我们将公开这份数据配比以及完整训练脚本，好让社区能复现并在我们的工作上继续构建。

## **用锚定偏好优化（APO）做离线策略对齐**

SFT 之后，我们做了一轮模型对齐：非推理模式用组合的 [Tulu3 偏好数据集](https://huggingface.co/datasets/allenai/llama-3.1-tulu-3-8b-preference-mixture)，推理模式用我们从 Qwen3-32B 和 Qwen3-0.6B 生成的新合成偏好对。为了确保非思考数据集覆盖所有领域，我们生成了与之配套的思考模式偏好对。我们选取 Qwen3-32B 的生成作为"chosen"，Qwen3-0.6B 的回复作为"rejected"，用于锚定偏好优化。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(24).png)

[锚定偏好优化](https://arxiv.org/abs/2408.06266)（APO）是[直接偏好优化](https://arxiv.org/abs/2305.18290)（DPO）的一个变体，能提供更稳定的优化目标。在 DPO 中，奖励函数 r_θ(x,y) 衡量训练期间序列概率相对训练开始时模型（即参考模型）的对数比值：

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(25).png)

其中 β 控制被优化模型相对参考模型能改变多少。DPO 损失优化由提示词 x、被选回复 y_w 和被拒回复 y_l 组成的三元组：

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(26).png)

APO 目标已被证明更稳定，我们在内部消融中也观察到更高的下游性能。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(27).png)

虽然下游评估显示在数学、科学、指令遵循、编码、对话和多语言任务上都有提升，但我们也观察到 RULER 这类长上下文基准上的性能下降。我们把这种下降追溯到推理中期训练阶段——那里对推理能力的侧重影响了长上下文表现。此外，APO 训练数据受限于 24k 词元，因为我们绝大部分推理数据集都短于这个长度。

为缓解这一性能下降，我们探索了模型合并作为解决方案。

## **模型合并**

模型合并是一种流行而强大的技术，可以在不带来集成计算开销、也不需要额外训练的情况下结合不同模型的优势。我们用 [MergeKit](https://github.com/arcee-ai/mergekit) 库来做模型合并，因为它包含多种合并方法，包括线性和非线性合并。

我们的合并配方分两步：

- 取每个 APO 检查点，合成一个模型"汤"（model soup）。
- 把模型汤与一个在长内容上表现强劲的中期训练检查点结合。用 APO 模型汤与中期训练检查点权重分别为 0.9 和 0.1 的线性合并取得了最佳效果。我们把基座模型的 RULER 分数恢复到了直至 128k 词元的上下文。

得到的模型就是我们今天要发布的检查点。它在广泛的任务上保持了性能。那我们来看看这个模型以及基座模型的评估结果。

# 评估

我们评估基座模型，以及推理与非推理两种模式下的指令模型。先来看基座模型的表现！

## **基座模型**

下图展示 SmolLM3 在 12 个考察知识、推理、数学和编码能力的流行基准上的胜率。SmolLM3 持续胜过其他 3B 模型，并与更大的 4B 模型（含 Qwen3-4B 和 Gemma3-4B）竞争激烈。

用于胜率计算的评估基准：HellaSwag、ARC、Winogrande、CommonsenseQA、MMLU-CF、MMLU Pro CF、PIQA、OpenBookQA、GSM8K、MATH、HumanEval+、MBPP+

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(28).png)

SmolLM3 在知识和推理基准（HellaSwag、ARC、BoolQ）上取得第一或第二名，在这些核心能力上表现强劲。数学和编码性能在 3B 档位内富有竞争力。Ruler 64k 上的长上下文性能显示模型能有效处理超长序列。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(33).png)

在涵盖 Global MMLU、MLMM HellaSwag、Flores-200、Belebele 等考察知识、常识推理、文本理解和翻译的多语言基准上评估时，模型在五种主要欧洲语言上展示了强劲的多语言性能。这说明 SmolLM3 在英语之外也保持一致的表现。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(30).png)

总之，基座模型在许多领域都表现非常出色。我们看看这如何转化为指令模型的表现。

## **双指令 / 推理模型**

由于 SmolLM3 同时具备指令模式和推理模式，我们需要在两种模式下评估，并与具备相同能力的模型对比。

### 非扩展思考评估

我们把 SmolLM3 与其他 3B 非推理模型对比，并在多个基准上把它与 Qwen3 推理模型在无思考模式下比较。如性能图所示，SmolLM3 胜过了其他 3B 非推理模型（包括 Llama3.2 3B Instruct 和 Qwen2.5 3B Instruct），并且处于推理模型之间的效率甜点位置——以更低计算成本显著超过 Qwen3 1.7B，同时逼近 4B 模型的性能。

![](https://huggingface.co/datasets/HuggingFaceTB/images/resolve/main/smollm3/image%20(31).png)

所以指令模型正好落在性能与成本的帕累托前沿上。我们再看看推理模型表现如何！

### 扩展思考评估

在启用扩展思考评估 SmolLM3 的推理能力时，相比它的非推理对应体，模型在大多数基准上都有显著提升。我们在 AIME 2025（36.7% 对 9.3%）、LiveCodeBench 上的竞技编程（30.0% 对 15.2%）以及 GPQA Diamond 上的研究生级推理（41.7% 对 35.7%）等高难度任务上观察到明显增益。

虽然 Qwen3 4B 通常在思考与非思考两种模式下都取得最高分，但 SmolLM3 在 3B 参数档位内展示了有竞争力的表现，尤其在数学推理和复杂问题解决任务上表现出色。模型的双模式能力允许用户在"不做推理的快速推断"和"用扩展思考做更彻底分析"之间选择。

那么最后的问题是：如何使用这个模型？

# 如何本地运行

SmolLM3 的建模代码已在 transformers `v4.53.0` 中提供，所以请确保升级你的 transformers 版本。你也可以用最新的 `vllm` 加载模型（它以 transformers 作为后端）。

`pip install -U transformers`

```
from transformers import AutoModelForCausalLM, AutoTokenizer

model_name = "HuggingFaceTB/SmolLM3-3B"
device = "cuda" # for GPU usage or "cpu" for CPU usage

# load the tokenizer and the model
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
).to(device)

# prepare the model input
prompt = "Give me a brief explanation of gravity in simple terms."
messages_think = [
    {"role": "user", "content": prompt}
]

text = tokenizer.apply_chat_template(
    messages_think,
    tokenize=False,
    add_generation_prompt=True,
)
model_inputs = tokenizer([text], return_tensors="pt").to(model.device)

# Generate the output
generated_ids = model.generate(**model_inputs, max_new_tokens=32768)

# Get and decode the output
output_ids = generated_ids[0][len(model_inputs.input_ids[0]) :]
print(tokenizer.decode(output_ids, skip_special_tokens=True))
```

> 我们建议在采样参数中设置 temperature=0.6 和 top_p=0.95。

### **启用与禁用扩展思考模式**

我们默认启用扩展思考，所以上面的例子会带着推理轨迹生成输出。要在启用与禁用之间选择，你可以通过系统提示词提供 `/think` 和 `/no_think` 标记，如下面这段禁用扩展思考的片段所示。生成带扩展思考回复的代码与之相同，只是系统提示词要用 `/think` 而不是 `/no_think`。

```
prompt = "Give me a brief explanation of gravity in simple terms."
messages = [
    {"role": "system", "content": "/no_think"},
    {"role": "user", "content": prompt}
]

text = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=True,
)
```

### **智能体用法**

SmolLM3 支持工具调用！只需把你的工具列表通过参数 `xml_tools`（标准工具调用）或 `python_tools`（在 `<code>` 片段中像调用 Python 函数一样调用工具）传入。

```
from transformers import AutoModelForCausalLM, AutoTokenizer

checkpoint = "HuggingFaceTB/SmolLM3-3B"

tokenizer = AutoTokenizer.from_pretrained(checkpoint)
model = AutoModelForCausalLM.from_pretrained(checkpoint)

tools = [
    {
        "name": "get_weather",
        "description": "Get the weather in a city",
        "parameters": {"type": "object", "properties": {"city": {"type": "string", "description": "The city to get the weather for"}}}}
]

messages = [
    {
        "role": "user",
        "content": "Hello! How is the weather today in Copenhagen?"
    }
]

inputs = tokenizer.apply_chat_template(
    messages,
    enable_thinking=False, # True works as well, your choice!
    xml_tools=tools,
    add_generation_prompt=True,
    tokenize=True,
    return_tensors="pt"
)

outputs = model.generate(inputs)
print(tokenizer.decode(outputs[0]))
```
