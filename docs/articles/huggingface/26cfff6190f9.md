# BigCode 背后的大规模近重复数据去重

Chenghao Mou（chenghao）

本文另有中文版本 [简体中文](https://huggingface.co/blog/zh/dedup)。

## 目标读者

对大规模文档级近重复去重感兴趣，并且对哈希、图与文本处理有一定了解的人。

## 动机

在把数据喂给模型之前先照料好数据很重要——至少在我们这里的大语言模型是这样，正所谓"垃圾进，垃圾出"。尽管当那些赚足眼球的模型（或者该叫 API）营造出"数据质量不那么重要了"的错觉时，想这么做越来越难。

在 BigScience 和 BigCode 里，我们在数据质量上面对的问题之一就是重复，包括可能的基准污染。已有研究表明，当存在大量重复时，模型倾向于逐字输出训练数据 [[1]](https://huggingface.co/blog/dedup#1)（尽管在某些其他领域还不那么明确 [[2]](https://huggingface.co/blog/dedup#2)），这还会让模型更容易遭受隐私攻击 [[1]](https://huggingface.co/blog/dedup#1)。此外，去重的一些典型好处还包括：

- 高效训练：你可以用更少的训练步数达到相同的、有时甚至更好的性能 [[3]](https://huggingface.co/blog/dedup#3) [[4]](https://huggingface.co/blog/dedup#4)。
- 防止可能的数据泄漏和基准污染：非零的重复会让你的评测失真，并可能把所谓的"改进"变成虚假声明。
- 可及性。我们大多数人都没法反复下载或传输几千 GB 的文本，更别说用它训练模型了。去重能让一个固定规模的数据集更便于研究、传输和协作。

## 从 BigScience 到 BigCode

先允许我分享一下我是如何踏上这条近重复去重之路的、成果是如何一步步推进的，以及一路上学到了什么。

一切始于 BigScience 已经启动几个月后 LinkedIn 上的一次对话。Huu Nguyen 注意到我在 GitHub 上的个人项目，来问我是否有兴趣为 BigScience 做去重。当然，我的回答是"愿意"，当时完全不知道仅凭数据体量本身就要付出多少工作量。

那段时间既有趣又充满挑战。挑战在于，我对如此规模的数据其实没什么研究经验，而大家仍然很包容、还把价值数千美元的云端算力预算托付给你。是的，我有过好几次不得不从睡梦中惊醒，去确认自己是否关掉了那些机器。结果我只能在一次次的试错中学，这最终为我打开了一种新的视角——若非 BigScience，我大概永远不会有。

时间往前推一年，我如今把学到的东西反哺进 [BigCode](https://www.bigcode-project.org/)，处理更大的数据集。除了为英语训练的 LLM [[3]](https://huggingface.co/blog/dedup#3)，我们确认过去重也能改进代码模型 [[4]](https://huggingface.co/blog/dedup#4)，而且用的是小得多的数据集。现在，我把学到的东西分享给你，我亲爱的读者，希望你能透过去重这个视角，对 BigCode 幕后发生些什么有个感知。

## MinHash 逐走一通

本节里，我们会覆盖 MinHash 的每一步——也就是 BigCode 所用的那一套——以及潜在的规模化问题和解决方案。我们用三个英文文档的一个例子来演示工作流：

| doc_id | content |
| --- | --- |
| 0 | Deduplication is so much fun! |
| 1 | Deduplication is so much fun and easy! |
| 2 | I wish spider dog [[17]](https://huggingface.co/blog/dedup#17) is a thing. |

MinHash 的典型工作流如下：

- Shingling（分词）和指纹化（MinHashing），把每个文档映射成一组哈希。
- 局部敏感哈希（LSH）。这一步是为了通过把相似 band 的文档分到一组来减少比较次数。
- 重复移除。这一步决定哪些重复文档保留、哪些移除。

### Shingles

和大多数涉及文本的应用一样，我们要从分词开始。常使用 N-gram，也叫 shingles。在我们的例子里，使用词级的三元组（tri-gram），不带任何标点。至于 ngram 大小如何影响性能，我们在后面一节再回头讲。

| doc_id | shingles |
| --- | --- |
| 0 | {"Deduplication is so", "is so much", "so much fun"} |
| 1 | {'so much fun', 'fun and easy', 'Deduplication is so', 'is so much'} |
| 2 | {'dog is a', 'is a thing', 'wish spider dog', 'spider dog is', 'I wish spider'} |

这个操作的时间复杂度为 O(NM) \mathcal{O}(NM) O(NM)，其中 N N N 是文档数量，M M M 是文档长度。换句话说，它线性依赖于数据集的大小。这一步很容易通过多进程或分布式计算的并行化来扩展。

### 指纹计算

在 MinHash 中，每个 shingle 通常要么 1) 用不同的哈希函数哈希多次，要么 2) 用一个哈希函数置换多次。这里我们选择对每个哈希置换 5 次。MinHash 的更多变体可见 [MinHash - Wikipedia](https://en.wikipedia.org/wiki/MinHash?useskin=vector)。

| shingle | permuted hashes |
| --- | --- |
| Deduplication is so | [403996643, 2764117407, 3550129378, 3548765886, 2353686061] |
| is so much | [3594692244, 3595617149, 1564558780, 2888962350, 432993166] |
| so much fun | [1556191985, 840529008, 1008110251, 3095214118, 3194813501] |

取每个文档每一列的最小值——也就是"MinHash"里的"Min"部分——就得到该文档最终的 MinHash：

| doc_id | minhash |
| --- | --- |
| 0 | [403996643, 840529008, 1008110251, 2888962350, 432993166] |
| 1 | [403996643, 840529008, 1008110251, 1998729813, 432993166] |
| 2 | [166417565, 213933364, 1129612544, 1419614622, 1370935710] |

技术上，我们不一定非得取每列的最小值，但最小值是最常见的选择。其他顺序统计量，如最大值、第 k 小或第 k 大，也可以使用 [[21]](https://huggingface.co/blog/dedup#21)。

在实现上，你可以用 `numpy` 把这些步骤轻松向量化，并预期时间复杂度为 O(NMK) \mathcal{O}(NMK) O(NMK)，其中 K K K 是你的置换数量。代码基于 [Datasketch](https://github.com/ekzhu/datasketch) 修改。

```
def embed_func(
    content: str,
    idx: int,
    *,
    num_perm: int,
    ngram_size: int,
    hashranges: List[Tuple[int, int]],
    permutations: np.ndarray,
) -> Dict[str, Any]:
    a, b = permutations
    masks: np.ndarray = np.full(shape=num_perm, dtype=np.uint64, fill_value=MAX_HASH)
    tokens: Set[str] = {" ".join(t) for t in ngrams(NON_ALPHA.split(content), ngram_size)}
    hashvalues: np.ndarray = np.array([sha1_hash(token.encode("utf-8")) for token in tokens], dtype=np.uint64)
    permuted_hashvalues = np.bitwise_and(
        ((hashvalues * np.tile(a, (len(hashvalues), 1)).T).T + b) % MERSENNE_PRIME, MAX_HASH
    )
    hashvalues = np.vstack([permuted_hashvalues, masks]).min(axis=0)
    Hs = [bytes(hashvalues[start:end].byteswap().data) for start, end in hashranges]
    return {"__signatures__": Hs, "__id__": idx}
```

如果你熟悉 [Datasketch](https://github.com/ekzhu/datasketch)，也许会问：我们何必费劲把库提供的那些好用的高层函数都拆掉？不是为了少加依赖，而是我们想在并行化时尽量榨干 CPU 算力。把若干步骤融合进一个函数调用，能让我们更好地利用计算资源。

由于一个文档的计算不依赖其他任何东西，一个好的并行化选择是用 `datasets` 库的 `map` 函数：

```
embedded = ds.map(
    function=embed_func,
    fn_kwargs={
        "num_perm": args.num_perm,
        "hashranges": HASH_RANGES,
        "ngram_size": args.ngram,
        "permutations": PERMUTATIONS,
    },
    input_columns=[args.column],
    remove_columns=ds.column_names,
    num_proc=os.cpu_count(),
    with_indices=True,
    desc="Fingerprinting...",
)
```

指纹计算之后，一个特定文档被映射成一整列整数值。要搞清楚哪些文档彼此相似，我们需要按这些指纹把它们分组。于是 **局部敏感哈希（LSH）** 登场。

### 局部敏感哈希

LSH 把指纹数组切分成 band，每个 band 含相同数量的 row。如果有剩余的哈希值，会被忽略。我们用 b=2 b=2 b=2 个 band、r=2 r=2 r=2 个 row 来分组这些文档：

| doc_id | minhash | bands |
| --- | --- | --- |
| 0 | [403996643, 840529008, 1008110251, 2888962350, 432993166] | [0:[403996643, 840529008], 1:[1008110251, 2888962350]] |
| 1 | [403996643, 840529008, 1008110251, 1998729813, 432993166] | [0:[403996643, 840529008], 1:[1008110251, 1998729813]] |
| 2 | [166417565, 213933364, 1129612544, 1419614622, 1370935710] | [0:[166417565, 213933364], 1:[1129612544, 1419614622]] |

如果两个文档在某个特定位置（band 索引）的 band 里共享相同的哈希，它们会被聚到同一个桶里，被视为候选。

| band index | band value | doc_ids |
| --- | --- | --- |
| 0 | [403996643, 840529008] | 0, 1 |
| 1 | [1008110251, 2888962350] | 0 |
| 1 | [1008110251, 1998729813] | 1 |
| 0 | [166417565, 213933364] | 2 |
| 1 | [1129612544, 1419614622] | 2 |

对 `doc_ids` 列里的每一行，我们可以通过把其中每两个配对来生成候选对。从上表可以生成一个候选对：`(0, 1)`。

### 不止于重复对

很多论文或教程里对去重的描述到这里就停了。我们还剩下"拿这些候选对怎么办"的问题。一般有两种走法：

- 由于 MinHash 是估算性质，去核实它们实际的 Jaccard 相似度，即计算它们的 shingle 重叠。两个集合的 Jaccard 相似度定义为交集大小除以并集大小。而且现在这比计算所有对之间的相似度可行得多，因为我们只需要关注簇内的文档。这也是我们最初在 BigCode 里的做法，效果相当不错。
- 把它们都当作真阳性。你可能已经注意到这里的问题：Jaccard 相似度不具备传递性，意味着 A A A 与 B B B 相似、B B B 与 C C C 相似，但 A A A 与 C C C 未必相似。不过我们在 The Stack 上的实验表明，把它们全部当作重复处理，下游模型性能反而最好。于是我们逐渐转向这种方法，它同时也省时间。但要把它应用到你的数据集上，我们仍然建议你通读自己的数据集、看看你的重复项，然后做一个数据驱动的决定。

从这些对——无论是否经过核实——出发，我们现在可以把这些对作为边来构造一张图，重复项会被聚成社区或连通分量。在实现上，遗憾的是，到了这里 `datasets` 就帮不上什么忙了，因为现在我们需要的是一种类似 `groupby` 的东西，好让我们能基于文档的 *band offset* 和 *band values* 来聚类文档。以下是我们试过的一些选项：

**选项 1：按老办法迭代数据集并收集边，然后用一个图库做社区检测或连通分量检测。**

这在我们的测试里扩展性不好，原因有多方面。首先，迭代整个数据集在大规模下又慢又费内存。其次，流行的图库如 `graphtool` 或 `networkx` 在建图上有不少开销。

**选项 2：使用流行的 Python 框架如 `dask`，以实现更高效的 `groupby` 操作。**

但你仍然摆脱不了迭代慢、建图慢的问题。

**选项 3：迭代数据集，但用并查集（union find）数据结构来聚类文档。**

这给迭代增加的开销微乎其微，在中等规模数据集上表现得不错。

```
for table in tqdm(HASH_TABLES, dynamic_ncols=True, desc="Clustering..."):
    for cluster in table.values():
        if len(cluster) <= 1:
            continue
        idx = min(cluster)
        for x in cluster:
            uf.union(x, idx)
```

**选项 4：对大规模数据集，用 Spark。**

我们已经知道，直到 LSH 那一步都可以并行化，而这在 Spark 里也能做到。除此之外，Spark 开箱支持分布式 `groupBy`，实现像 [[18]](https://huggingface.co/blog/dedup#18) 那样的连通分量检测算法也很直接。如果你好奇我们为什么不用 Spark 自带的 MinHash 实现，答案是：我们至此的所有实验都源自 [Datasketch](https://github.com/ekzhu/datasketch)，它的实现与 Spark 完全不同，而我们希望把从那里学到的经验和洞见延续下来，而不是再跳进另一个消融实验的兔子洞。

```
edges = (
    records.flatMap(
        lambda x: generate_hash_values(
            content=x[1],
            idx=x[0],
            num_perm=args.num_perm,
            ngram_size=args.ngram_size,
            hashranges=HASH_RANGES,
            permutations=PERMUTATIONS,
        )
    )
    .groupBy(lambda x: (x[0], x[1]))
    .flatMap(lambda x: generate_edges([i[2] for i in x[1]]))
    .distinct()
    .cache()
)
```

一个基于 [[18]](https://huggingface.co/blog/dedup#18) 在 Spark 里实现的简单连通分量算法。

```
a = edges
while True:
    b = a.flatMap(large_star_map).groupByKey().flatMap(large_star_reduce).distinct().cache()
    a = b.map(small_star_map).groupByKey().flatMap(small_star_reduce).distinct().cache()
    changes = a.subtract(b).union(b.subtract(a)).collect()
    if len(changes) == 0:
        break

results = a.collect()
```

此外，多亏云服务商，我们可以借助 GCP DataProc 这样的服务轻松搭建 Spark 集群。**最终，我们可以在每小时 15 美元的预算下，不到 4 小时就从容地跑完程序，对 1.4 TB 数据做去重。**

## 质量才是关键

把梯子架得再高也到不了月球。正因如此，我们需要确认方向是对的、并且用得对。

早期，我们的参数很大程度上沿袭自 CodeParrot 的实验，而我们的消融实验表明这些设置确实提升了模型的下游表现 [[16]](https://huggingface.co/blog/dedup#16)。随后我们进一步探索这条路，可以确认 [[4]](https://huggingface.co/blog/dedup#4)：

- 近重复去重以显著更小的数据集（6 TB 对 3 TB）改进了模型的下游表现
- 我们还没摸清上限，但更激进的去重（6 TB 对 2.4 TB）能进一步提升性能：降低相似度阈值；增大 shingle 大小（unigram → 5-gram）；放弃假阳性核查，因为我们承受得起损失一小部分假阳性

[![A violin chart showing unigram impact in different settings](https://huggingface.co/datasets/chenghao/dedup_blog_assets/resolve/main/data/violin_chart_1.png)](https://huggingface.co/datasets/chenghao/dedup_blog_assets/resolve/main/data/violin_chart_1.png) [![A violin chart showing unigram impact in different settings](https://huggingface.co/datasets/chenghao/dedup_blog_assets/resolve/main/data/violin_chart_2.png)](https://huggingface.co/datasets/chenghao/dedup_blog_assets/resolve/main/data/violin_chart_2.png)

图：两张展示相似度阈值和 shingle 大小影响的图，第一张用 unigram，第二张用 5-gram。红色虚线表示相似度截止线：低于它的文档会被视为假阳性——它们与同簇内其他文档的相似度低于阈值。

这些图能帮我们理解为什么对 CodeParrot 和 The Stack 早期版本有必要复核假阳性：用 unigram 会产生很多假阳性；它们也表明，把 shingle 大小增大到 5-gram 时，假阳性比例显著下降。如果我们想保持去重的激进程度，就需要一个更小的阈值。

额外的实验还表明，降低阈值会移除更多拥有高相似度对的文档，也就是说在我们真正最想移除的那部分里召回率提高了。

## 规模化

这不是你能找到的最严谨的规模化证明，但在给定固定算力预算下，去重时间与数据集的物理大小实际上呈线性。当你细看处理 JSON 数据集（Stack 里最大的子集）时的集群资源使用，会发现 MinHash + LSH（阶段 2）占据了总实际计算时间（阶段 2 + 3）的绝大部分，而从我们前面的分析看，它是 O(NM) \mathcal{O}(NM) O(NM)——与数据集物理体量线性相关。

## 谨慎前行

去重并不能让你免于彻底的数据探查和分析。此外，这些去重发现对 The Stack 成立，但并不意味着它就能照搬到其他数据集或语言。它是构建更好数据集的良好第一步，而数据质量过滤（如漏洞、毒性、偏见、生成模板、PII）之类的进一步研究仍然十分必要。

我们仍然鼓励你在训练前对自己的数据集做类似分析。例如，如果你的时间和算力预算很紧，做去重可能没多大帮助：[@geiping_2022](http://arxiv.org/abs/2212.14034) 提到子串去重并没有改善他们模型的下游表现。已有的数据集在使用前也可能需要彻底检查，例如 [@gao_2020](http://arxiv.org/abs/2101.00027) 说他们只确保 Pile 本身及其各个 split 被去重，而不会主动为任何下游基准去重，把那个决定留给读者。

就数据泄漏和基准污染而言，仍有大量值得探索之处。我们不得不重新训练我们的代码模型，因为 HumanEval 被发布在 Python 的某个 GitHub 仓库里。早期的近重复去重结果也表明，MBPP [[19]](https://huggingface.co/blog/dedup#19)——最流行的编码基准之一——与许多 Leetcode 题有大量相似之处（例如，MBPP 的 task 601 基本就是 Leetcode 646，task 604 ≃ Leetcode 151。）。而我们都清楚 GitHub 从不缺这些编程题和解法。如果有人居心不良，把所有基准以 python 脚本或其他更不显眼的方式上传、从而污染你所有的训练数据，那会更棘手。

## 未来方向

- 子串去重。尽管它对英语显示了一些益处 [[3]](https://huggingface.co/blog/dedup#3)，是否也应把同样方法用到代码数据上还不清楚；
- 重复：在一篇文档里被重复多次的段落。[@rae_2021](http://arxiv.org/abs/2112.11446) 分享了一些关于如何检测并移除它们的有趣启发式。
- 用模型嵌入做语义去重。那是另一个完整的研究问题，涉及规模化、成本、消融实验，以及与近重复去重的权衡。这方面有一些耐人寻味的成果 [[20]](https://huggingface.co/blog/dedup#20)，但我们仍需要更多具体证据来下结论（例如，[@abbas_2023](http://arxiv.org/abs/2303.09540) 唯一的文本去重参照是 [@lee_2022a](http://arxiv.org/abs/2107.06499)，而后者主要主张是"去重有帮助"，而非"力求做到 SOTA"）。
- 优化。总有优化空间：更好的质量评估、规模化、下游性能影响分析等。
- 还有一个看待问题的方向：近重复去重到什么程度开始损害性能？为了多样性，相似度在多大程度上是必要的，而非被当作冗余？
