#### TL;DR

检索增强生成（RAG）、语义搜索、重排序（reranking）、推荐、意图分类、去重、聚类——生产环境中极大的 AI 份额最终归结为一个原语：把文本变成向量，让相关的东西彼此靠近、不相关的东西彼此远离。

这个向量空间的质量，就是建在其上的一切系统的天花板。一个再优秀的 reranker 也救不回从未召回正确文档的检索器；RAG 流水线也无法引用一篇它没能检索到的判例。于是问题变成：**如何为你的领域获得尽可能好的 embedding？**

在这篇文章中，我们给出一套实用、低成本（<$10）的方案：在 Fireworks 平台用对比学习（contrastive）微调，把通用 embedding LLM（Qwen3-Embedding-8B）适配到特定领域——并在两个高难度的真实检索任务上度量结果。简版结论：一次短暂的微调就能让检索质量相对基座模型大幅提升（例如法律引证检索 **+36% nDCG@10**），同时保持模型通用能力不倒退。

## **为什么要微调一个 LLM 来做 Embedding 模型？**

文本 embedding 已被研究了十多年，可追溯到 [word2vec](https://arxiv.org/abs/1301.3781) 及其后继者——它们首次证明文本的意义可以被压缩进稠密向量。今天获取一个领域 embedding 有三条大路，其中只有一条既高质量又便宜：

- **直接拿来一个基座 LLM embedding 模型用。**
- **从零训练一个 embedding 模型。**
- **微调一个基于 LLM 的 embedding 模型（本文）。**

逐条权衡利弊。

**方案 1 —— 直接拿来基座 embedding 模型。** 源自 LLM 的现代 embedding 模型（Qwen3-Embedding、E5-Mistral、NV-Embed……）是出色的通才：在海量互联网语料上训练，对日常文本能产出强向量。但在专业化语料上，「通才」恰恰是局限。基座模型不知道在美国判例法中 36 So. 3d 84 与 Reed v. State 指的是同一权威，也不知道哪些入组标准能让一位患者匹配某项临床试验。它抓得住通用文本，抓不住领域语义。后文会展示：在法律引证检索任务上，基座模型只有 **0.43 nDCG@10**——能用，但远低于该语料允许的上限。

**方案 2 —— 从零训练 embedding 模型。** 过去十年里大部分时间，搜索、推荐、广告的 embedding 系统都是从零训练的（[DSSM](https://www.microsoft.com/en-us/research/publication/learning-deep-structured-semantic-models-for-web-search-using-clickthrough-data/)、[Facebook 搜索中基于 embedding 的检索](https://arxiv.org/abs/2006.11632)）——通常是贴合域内数据训练的专用 BERT 风格编码器，可以工作得还不错。但对大多数团队来说这是个陷阱：以可获得的中等规模标注数据，从零训练的模型会过拟合训练分布，并**丢掉让 embedding 保持稳健的广泛语言能力**。它记住你的训练配对，然后在生产里遇到的换述、错字和新奇表达上跌跤——你扔掉了数十亿 token 的预训练，去追几千个标注对。此外，从零训练 embedding 模型通常是 AI 实验室和拥有研究专长、大规模数据集与训练基座模型所需算力基础设施的机构的领域。一般只有当现有 embedding 模型无法充分表达高度专业化的领域，或者需要对模型架构与优化目标拥有完全控制权时，才值得这么做。对多数公司而言，使用或微调一个 SOTA embedding 模型能以一小部分成本和复杂度获得相当的性能。这正是方案 3 的思路。

**方案 3 —— 微调一个基于 LLM 的 embedding 模型（本文）。** 从一个强预训练 embedding LLM（[BERT](https://arxiv.org/abs/1810.04805)、[Don't Stop Pretraining](https://arxiv.org/abs/2004.10964)）出发，用你领域内的配对数据以对比目标轻量适配它。这是两全其美：

- •**保住泛化能力。**基座模型已经理解语言、句法、实体和世界知识。微调只是把向量空间的几何往你的领域方向推，而不是重建——几百步就能专业化模型而不发生灾难性遗忘。
- •**获得领域能力。**模型学到你的相关性定义：一段被遮盖的法条段落应该检索出它所引用的判例，一份患者摘要应该检索出他们符合入组条件的试验。
- •**成本低。**因为你是在适配而非预训练，一次有用的运行约 150 个优化步——在 Fireworks 上只是几分钟的训练时间，可选全参数更新或一个很小的 LoRA 适配器。

这与[把 LLM 变成分类器](https://fireworks.ai/blog/Finetuning-LLMs-as-Classifiers)一文的经验一致：制胜一手是**适配你已有的模型**、复用同一套训练与推理基础设施，而不是外挂一个新架构或从零开始。

## **Embedding 微调如何工作：批内负样本与 InfoNCE**

embedding 模型把一段文本映射为单个向量。对 Qwen3-Embedding 这样基于 LLM 的编码器，我们把文本送过 transformer，取**最后一个 token** 的最终隐藏状态作为 embedding（因果注意力掩码意味着最后一个位置「看过」整个序列），然后做 L2 归一化。两段文本的相似度就是其向量的点积（余弦相似度）。

要教会模型一个领域的相关性概念，我们需要形如 **(query, positive) 对**的训练数据——一个查询与一个应为它被检索的文档。在我们的法律任务中，查询是一段把引证遮掉的法院段落，positive 是它引用的判例。对临床试验，查询是患者摘要，positive 是他们符合资格的试验。

目标是**对比的（contrastive）**：把每个查询拉近它的 positive，推远其他一切。让这件事高效的巧妙技巧是**批内负样本（in-batch negatives）**。在一个含 B 个 (query, positive) 对的训练批次里，每个查询已经恰好有一个正确文档——同一批次里其余 B−1 个文档就是免费的负样本。（值得指出，更高级的困难负样本挖掘和跨批负样本可以进一步提升性能，我们留到下一篇。）眼下先聚焦只用批内负样本的基础设定。

具体地说，对一个批次我们计算完整的 `B × B` 相似度矩阵 `S`，其中 `S[i][j]` 是查询 `i` 与文档 `j` 的余弦相似度。对角线元素是真正的正样本，所有非对角元素都是负样本。然后应用 **InfoNCE** 损失——一个 softmax 交叉熵，要求每个查询在全部 B 个候选中把最高相似度给到自己的 positive：

B×B 批内负样本相似度矩阵：对角线是真正的 (query, positive) 对，其余每个格子都是从批内免费抽到的负样本。

```
123L_q2d = cross_entropy(S / τ, targets = diag)   # each query picks its positiveL_d2q = cross_entropy(Sᵀ / τ, targets = diag)  # each doc picks its queryL     = ½ (L_q2d + L_d2q)                       # bidirectional / symmetric
```

两个细节要紧：

- •**温度 τ**（我们用 0.02）把 softmax 变尖锐，迫使模型让 positive 赢得明确，而不是险胜。
- •**双向损失**——我们在两个方向（query→doc 与 doc→query）都施加 InfoNCE 并取平均。这种对称形式同时训练检索关系的两侧，比单向损失更稳定。

## **实验结果**

我们在两个高难度、领域特定的检索基准上评估，对比**基座** Qwen3-Embedding-8B 与同一模型的**微调**版本。两种情况我们都全参数训练 150 步，batch size 64（下述长上下文 case→case 运行用 batch 8，因为只装得下 8 条 16k token 序列），学习率 1e-5，温度 0.02——这套配方只需几分钟训练时间。评估使用训练期间模型从未见过的**保留查询**，所有指标都用标准 pytrec_eval 库（MTEB 同款）。为让表格可读，我们报告 **nDCG@100**（排序质量）和 **Recall@100**（覆盖率）；其余标准指标——nDCG@10、Recall@10、MRR、MAP@100——也全部显著提升。

### **实验 1：法律引证检索（LegalBench）**

任务：给定一个法律问题，检索答案中应被引用的法院意见书。我们这样构建：把 legal-bench 引证检索问题与 Caselaw Access Project 中被引案件的全文相连接——4,899 个问题，语料库为 6,061 篇真实美国法院意见书，每个查询平均约 19 篇相关判例。我们按源案件切分，使评估查询来自训练中从未见过的案件。问题来自 [phalanetwork/legal-bench_cat1_cite_retrieval](https://huggingface.co/datasets/phalanetwork/legal-bench_cat1_cite_retrieval)，我们把每个问题与其引用案件在 [Caselaw Access Project](https://case.law) 中的意见书全文配对。(query, positive) 对长这样：

> Query: "In Florida, I'm advising a county clerk's office on managing pro se prisoner petitions after the Pray v. Forman decision. … What specific administrative protocols should we implement to comply with recent court standards?"

> Positive (被引意见书): Pettway v. State, Supreme Court of Florida — "John Everett Pettway, Petitioner, v. State of Florida, Respondent … "

| 指标 | Base | Fine-tuned | 相对提升 |
| --- | --- | --- | --- |
| 指标 | Base | Fine-tuned | 相对提升 |
| nDCG@100 | 0.462 | 0.644 | +39% |
| Recall@100 | 0.540 | 0.758 | +40% |

微调大幅抬升检索质量——**nDCG@100 +39%、Recall@100 +40%**（其他指标同样改善：nDCG@10 +36%、Recall@10 +43%、MRR +17%、MAP@100 +61%）——因为基座模型虽在通用文本上很强，在「把法律问题匹配到它所依赖的判例」这一专业任务上仍有实实在在的上升空间。几分钟的对比微调补上了其中大部分差距。

### **实验 2：临床试验匹配（TREC Clinical Trials）**

任务：给定一份患者病例描述，检索患者可能符合资格的临床试验（TREC Clinical Trials，约 6.3 万条试验语料）。这是另一个领域、结构非常不同——长而结构化的入排文档、每位患者有许多相关试验——很适合检验这套配方能否泛化到法律文本之外。训练查询只有约 130 条，这是一个刻意数据稀缺的设定。查询来自 [TREC Clinical Trials track](https://www.trec-cds.org/)（2021–2023）的患者 "topics"；语料来自 [ClinicalTrials.gov](https://clinicaltrials.gov) 的试验记录。(query, positive) 对长这样：

> Query (患者): "Patient is a 45-year-old man with a history of anaplastic astrocytoma of the spine, complicated by severe lower-extremity weakness and urinary retention … on high-dose steroids …"

> Positive (符合资格的试验): Radiation Therapy With or Without Chemotherapy in Treating Patients With Anaplastic Oligodendroglioma (NCT00002569) — inclusion: histologically proven supratentorial anaplastic oligodendroglioma; age ≥ 18 …

| 指标 | Base | Fine-tuned | 相对提升 |
| --- | --- | --- | --- |
| 指标 | Base | Fine-tuned | 相对提升 |
| nDCG@100 | 0.495 | 0.556 | +12% |
| Recall@100 | 0.303 | 0.352 | +16% |

即便训练集极小，一次简短微调也改善了所有指标——这正是临床试验匹配工作流在意的：临床医生想要所有看似合理的可入组试验都被浮出，而不只是单个最佳项。

### **实验 3：欧盟判例引证检索（LegalPincite）**

第二个法律引证任务，这次来自 [theresiavr/legalpincite](https://huggingface.co/datasets/theresiavr/legalpincite) 的欧洲法院判决书。查询是判决中把某条引证**遮掉**的段落，模型必须检索出被引内容。数据集有两种粒度，讲的是不同的故事。

> 段落 → 段落——从约 59.4 万段落的语料中检索被引段落。查询和文档都短，因此按标准 512 token 上下文评估。(query, positive) 对如下（被遮掉的引证以 ___ 表示）：

> Query (citation masked): "68 In addition, as the General Court noted in ___ of the order under appeal, that reasoning applies with the same force in a situation in which lawyers are employed by an entity connected to the party they represent (judgment of ___ Prezes ___)."

> Positive (the cited paragraph): "25. That reasoning applies with the same force in a situation such as that of the legal advisers in issue in the present dispute, in which the lawyers are employed by an entity connected to the party they represent. …"

| 指标 | Base | Fine-tuned | 相对提升 |
| --- | --- | --- | --- |
| 指标 | Base | Fine-tuned | 相对提升 |
| nDCG@100 | 0.548 | 0.584 | +7% |
| Recall@100 | 0.833 | 0.866 | +4% |

提升真实但有限：基座模型在这里已经很强（nDCG@100 0.55），因为把一段短法律段落匹配到它引用的短段落，已经很接近一般语义相似度——没什么空间。（其他指标走势类似：nDCG@10 0.501→0.540，MRR 0.501→0.536，MAP@100 0.446→0.481。）

**案件 → 案件**——检索被引案件，即整份判决书。(query, positive) 对——两者都是完整判决书，此处大幅截断展示：

**Query (citation masked, 约 37k 字符):** "1 By their appeals, PJ and PC seek to set aside the order of the General Court of the European Union of 30 May 2018, ___ (PJ v EUIPO — Erdmann & Rossi), 'the order under appeal', by which the General Court … "

**Positive (the cited case, 约 23k 字符):** "1 By application lodged at the Court Registry on 4 October 1979, Australian Mining & Smelting Europe Limited ('AM & S Europe'), which is based in the United Kingdom, instituted proceedings … " ——关于律师-客户特权的里程碑式 AM & S Europe 判决。

这些文档很长（查询的中位数约 8.7k token），所以对比必须在长上下文下进行。**在匹配的 16k token 窗口上公平评估**——并且微调训练也用 16k 窗口：

| 指标 | Base | Fine-tuned | 相对提升 |
| --- | --- | --- | --- |
| 指标 | Base | Fine-tuned | 相对提升 |
| nDCG@100 | 0.484 | 0.778 | +61% |
| Recall@100 | 0.653 | 0.881 | +35% |

这里微调把排序质量**几乎翻倍**（nDCG@10 0.40→0.72，MRR 0.62→0.89）。我们吃过苦头学到的教训是：一个在 512 token 短窗口上训练的微调版本，在长上下文评估下几乎赢不过基座——模型必须在它将来服务的上下文长度上训练。把训练与评估窗口都对齐到文档长度，回报是巨大的。

> 可复现性。上述数字来自 Fireworks 生产训练器。我们还提供了一个独立的单 GPU 复现套件（开源 sentence-transformers、全参数、同一配方），结果与本文数字相差约 0.03 nDCG@100 以内：LegalBench（0.639 对微调 0.644 nDCG@100）和 LegalPincite 段落→段落（0.601 对 0.584）表现出高可复现性；LegalPincite 案件→案件达到 0.747 对 0.778（小量残差来自独立训练器与生产训练器之差）。Clinical Trials 因评估框架差异在 base 和 fine-tuned 上都有约 0.05 nDCG@100 的一致偏移（复现 0.449→0.510 对本文 0.495→0.556），但绝对提升同为约 +0.06。简言之，用开源工具在每个任务上微调增益都能复现。

## **我们还发现了什么**

除了两个头条结果，我们还跑了一系列扫描（sweep）。细节超出本文范围，但结论值得一说：

- •**微调的增益跟随基座模型的余量。**基座已经强的地方，增益就小；基座吃力的地方，增益就大。我们在另外三个领域看到同一模式——代码搜索（[CoSQA](https://huggingface.co/datasets/CoIR-Retrieval/cosqa-queries-corpus)）、开发者问答（[StackOverflow-QA](https://huggingface.co/datasets/CoIR-Retrieval/stackoverflow-qa-queries-corpus)）、电商产品搜索（[Amazon ESCI](https://huggingface.co/datasets/mteb/ESCIReranking)）：ESCI 提升明显，本已接近天花板的 StackOverflow-QA 提升很小，CoSQA 基本持平。
- •**约 150 步是甜点。**训到 300 步没有改善，有时头部排名指标还轻微回退——一次短适配足以让几何 specialize 而过拟合。
- •**LoRA 几乎追平全参数微调。**rank-32 的 LoRA 适配器在每个指标上都落在全参数微调约 1 个点以内，成本只有其一小部分——作为便宜、可热插拔的领域适配器是很好的默认选项。
- •**更大的 batch 在这里没用。**把批内负样本从 63（B=64）提到 255（B=256），在这些任务上没有增益，而且慢得多——64 已经足够。
- •**上下文长度可能比微调更要紧。**在整份判决书（case 级）变体上，一个在 512 token 窗口微调的模型在长上下文评估下几乎赢不了基座；改成在 8k–16k 窗口训练则让 nDCG 与 MRR **几乎翻倍**。当文档超出编码器的窗口时，瓶颈是截断而不是模型质量，所以请按你数据的长度来训练和评估。

### **微调推不动的情况**

不是每个数据集都有提升。最明确的「无效果」来自基座模型已经很强、或「相关性」接近纯语义/词法相似度的任务：

| 数据集 | 问的是什么 | Base nDCG@10 | Fine-tuned nDCG@10 |
| --- | --- | --- | --- |
| 数据集 | 问的是什么 | Base nDCG@10 | Fine-tuned nDCG@10 |
| CoSQA | 自然语言查询 → 代码片段 | 0.439 | 0.433（持平） |
| StackOverflow-QA | 问题 → 回答帖 | 0.944 | 0.967（已近天花板） |
| FiQA2018 | 金融问题 → 回答 | 0.645 | 0.638（无增益） |
| NFCorpus | 健康问题 → PubMed 文档 | 0.414 | 0.419（可忽略） |

这些无效果的情况落入两类：

- **任务其实并非领域特化。**当「相关性」可归约为一般语义或词法相似度时，基座模型已经能处理，没有专门信号可加。CoSQA——把自然语言查询匹配到回答它的代码片段——接近一般语义搜索；StackOverflow-QA 的回答帖与问题在词法上几乎相同（base nDCG@10 0.94，近天花板）。微调无事可学。
- **基准太流行、已被基座模型饱和。**FiQA（金融）和 NFCorpus（医疗）看着领域特化，但它们是广泛使用的公开 IR 基准，其文档与相关性模式几乎肯定在基座模型的预训练数据里。模型实际上已经见过这个任务，所以在其一小片上微调加不了东西（FiQA 甚至略降）。

合起来，这些结果精炼了假设：**只有当任务携带基座模型尚未内化的特化相关性信号时，微调才带来大增益**——不是仅仅领域词汇就行，在基座模型已经吸收的公开基准上也不行。大赢家——LegalBench 引证检索（nDCG@10 +36%）和整份判决书匹配（约 2 倍）——恰恰出现在「相关」的含义由领域来定义（哪个判例管辖这个问题、哪个试验患者符合资格）而一般预训练从未教过的地方。

## **开始上手**

如果你的产品依赖在专业语料上的搜索、RAG、重排序或推荐，基座 embedding 模型正在把质量留在桌上——而从零训练会牺牲泛化。对 embedding LLM 做对比微调，是既捕获你领域的相关性、又保住模型通用能力的便宜中间路线。

- •从你的领域收集几千个 `(query, positive)` 对。
- •用上面的配方微调 Qwen3-Embedding-8B（约 150 步，几分钟训练时间）。
- •在保留查询上用 nDCG / Recall / MRR 做前后对比评估。
- •通过同一 embeddings API 部署，并重建语料索引。

### **Fireworks 三种训练模式：灵活性与效率的取舍**

现已开放预览，Fireworks 把这套对比微调循环以三种模式提供，在**灵活性**（你能多自由地定义损失）与**训练效率**（驱动循环的客户端与持有模型的训练器之间必须搬运多少数据）之间取舍。它们优化同一族目标；差别在于损失算在哪、什么要跨过客户端↔训练器边界。

`embedding` —— 最灵活，最低效。训练器跑前向并返回原始 embedding 向量，损失由你自己在客户端用任何你喜欢的函数计算——InfoNCE、triplet、自定义 margin、多正样本方案，都行。这是最通用的选项：你不限于任何内建目标。代价是带宽。整个 embedding 矩阵（batch × hidden dim——如 4096 维）在前向时从训练器发给客户端，对应梯度在反向时发回。对大批次和 8B 模型宽大的隐藏状态来说，来回搬运这些张量支配了单步时间。

`cos_similarity_matrix` —— 中间地带。训练器计算成对余弦相似度矩阵并返回其行；你仍在客户端定义损失，但作用在远小于 N×D embedding 的 N×N 相似度矩阵上。当批次大小 N 小于 embedding 维度 D（通常如此），这比 embedding 模式搬运的数据少得多，同时仍让你自定义任何可用相似度表达的损失——InfoNCE 变体、温度调度、自定义掩码。代价是：完整矩阵必须在单一设备上组装，所以该模式要求单数据并行（DP=1）的训练器。

`contrastive_loss` —— 最不灵活，最高效。双向 InfoNCE 损失完全在训练器上以单次往返计算：没有 embedding 或梯度跨越边界——批数据进，标量损失出。这是最快的选项，当你想要的就是 InfoNCE 时它是正确的默认——对检索来说几乎总如此。你放弃插入任意损失的能力，换来最小的通信开销。

| 模式 | 损失算在哪 | 跨过客户端↔训练器边界的内容 | 灵活性 | 效率 | 约束 |
| --- | --- | --- | --- | --- | --- |
| 模式 | 损失算在哪 | 跨过客户端↔训练器边界的内容 | 灵活性 | 效率 | 约束 |
| embedding | 客户端 | embedding + 梯度 (N×D) | 任意自定义损失 | 最低 | — |
| cos_similarity_matrix | 客户端 | 相似度矩阵 (N×N) | 任意基于相似度的损失 | 中 | DP=1（单 GPU） |
| contrastive_loss | 训练器 | 数据进、标量损失出 | 仅内建 InfoNCE | 最高 | — |

经验法则：标准检索微调从 **`contrastive_loss`** 开始；想自定义基于相似度的损失又不愿付全量 embedding 传输成本时选 **`cos_similarity_matrix`**；需要对目标函数的完全自由时用 **`embedding`**。（上面的实验使用 embedding 模式。）
