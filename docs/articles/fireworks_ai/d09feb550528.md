上周，Fireworks 发布了最新的 [DeepSeek-V4.1-Flash](https://fireworks.ai/models/deepseek-ai/deepseek-v4p1-flash)。在跑完一整套基准测试后，结果显示它在质量、速度、成本等关键权衡上划出了新的 Pareto 前沿。在 DeepSWE 上，它以每任务 1/15 的价格达到了 GPT-6 Astra 级别的编码准确率。

开发者常问我们怎么选对模型。现实是，一个模型只是地图上的一个点，而你的应用是一整个系统。AI 能力是参差不齐的，意思是能把一个任务做得很漂亮的模型，可能在另一个任务上吃力。由于没有哪个单一模型能在所有场景中胜出，工作负载设计归根结底是把对的模型配给对的任务——无论你需要的是低延迟处理，还是复杂推理所需的深度计算。

## 深入内部：新的拆分激活架构

DeepSeek-V4.1-Flash 是 DeepSeek 新架构家族中最小的模型，带来了一些新的架构增强。

它由 552B 参数的 MoE 组成，采用新的编码器—解码器拆分架构。在这种架构里，模型不再为整个前向传播设一份激活预算，而是把它拆成输入侧 8B 激活参数、输出侧 16B**。**这样的设计更高效，于是 token 开销也更经济。

这种不对称正对应 coding agent 的工作方式。一条典型的 agent 轨迹非常偏输入：coding agent 经常反复读文件、反复读自己的草稿、反复读工具输出，最后只吐出一个相对很小的 patch。在我们的 DeepSWE 运行中，模型每个任务消耗 36.9M 输入 token，对应 211K 输出 token，比例 174:1。这个架构让开发者在输入侧只花一半的计算，而输入侧通常正是 token 占比更大的地方。

相比上一代 DeepSeek V4，DeepSeek 提升了 DeepSeek-V4.1-Flash 的 KV Cache 利用率，只消耗 ¼ 的 HBM，以及 ⅛ 的 SSD 存储。

## HLE 与一次 oracle router 评测

我们跑了第三个基准任务：Humanity’s Last Exam，也就是 HLE。这是一个多模态基准，用来测量 LLM 在研究生水平各学科上的能力极限。在这轮测试中，我们还用 oracle router 做了一些基准测试，类似我们在 [Kimi K3](https://fireworks.ai/blog/kimik3-fable) 和 [DeepSeek V4 Pro](https://fireworks.ai/blog/DeepSeekV4Pro-Fable5) 上做过的。快速回顾一下：oracle routing 是一种测量理论最佳表现的方法——把任务分别交给每个模型跑，然后挑出成本最优的正确选项，以此确立成本与性能的上限。

在 HLE 上，单独运行时 DeepSeek-V4.1-Flash 落后于 Astra。这说明 DeepSeek 更适合 DeepSWE 这类 agentic coding 任务，而不是 HLE 这类推理任务。如果你的工作负载只是高难度的科学推理，这可能不是合适的选择。

这里有意思的结果是 oracle router，它说明了路由和多模型系统的重要性。Astra 加 DeepSeek V4.1 的 oracle router 表现优于单独的 GPT-6 Astra。这 4.4% 的差距，只有在 V4.1-Flash 正确回答了 Astra 答错的一批有分量的问题时才可能实现。34.52% 并不是 50.40% 的子集；两个模型在不同的问题上失败。需要考虑的是，oracle router 是你的应用所能达到的上限。真实的路由器未必能吃满这 4.4 个百分点的差距，但 oracle router 展示了由多个模型组成的系统有可能做得比单独的 Astra 模型更好。
