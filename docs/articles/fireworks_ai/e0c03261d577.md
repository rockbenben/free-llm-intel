## Training API，现已正式可用

我们与全球 ML 团队合作，了解现有训练工作流哪里不给力：模型与方法选择受限、参数与训练循环控制有限、算力僵化且利用率不足、训练与 rollout 基础设施割裂导致成本膨胀、同步开销与数值漂移。这些伙伴关系塑造了我们的 Training API。

Fireworks Training API 把你的自定义训练循环连到 Fireworks 管理的分布式训练与 rollout 基础设施。你在任意选择的地方用 Python 编排循环，对你的损失或奖励、数据与环境拥有完全控制。Fireworks 管理高性能算力：计算梯度并更新模型的训练器，以及从训练后的模型采样的 rollout 部署。Fireworks 还管理这两者之间的交互——从权重同步、失败切换恢复，到训练- rollout 对齐。这一切让你专注于打磨学习信号，而不是基础设施难题。

## 团队为什么在 Fireworks 上训练

Fireworks 是前沿实验室之外少数在超过 10,000 块 GPU 上运行过强化学习（RL）的机构之一。RL 把训练与推理变成一个持续耦合的系统：每一步都从当前策略的 rollout 开始、更新权重、再把权重送回推理做下一轮采样。在前沿规模上，算法只是挑战的一部分。有效的 RL 取决于三项要求：正确性、性能效率与开发速度。

### 正确性：训练与推理对齐

要在 RL 训练中保证正确，rollout 引擎与训练器需要共享同一套数值定义。小数值漂移就能腐蚀学习信号——从 token 截断到奖励崩塌——而表面上一切都在正常运转。在 Fireworks，

- •**数值格式端到端一致。**训练与推理之间精度或量化的差异会改变模型计算出的值，哪怕权重相同。Fireworks 对齐训练器与 rollout 的数值格式（如 BF16、block-wise FP8 与 NVFP4），让训练器保存的那个模型就是 rollout 部署运行的那个。
- •**kernel 也要一致。**同样的数值格式不保证同样的计算。浮点归约、kernel 选择与并行方式即使在完全相同的精度下也会产生不同的数，所以 Fireworks 对齐两条路径的底层实现。
- •**MoE 执行保持一致。**微小的数值差异能改变哪些专家被激活，让 token 走上不同的计算路径。Fireworks 用 Router Replay 在 rollout 与反向传播之间保持专家选择，并配合批不变 kernel 与确定性归约，覆盖所支持的前沿 MoE。

Fireworks 直接验证这种对齐：把同样的序列分别送过 rollout 引擎与训练器，测量训练-推理 KL 散度（KLD）。所有在 Fireworks training 上线的模型都持续接受验证，确保 KLD 被压到最低。

### 性能效率：在 RL 循环内最大化吞吐

在规模上，RL 很大程度上是一个生成问题。大部分墙钟时间花在产出 rollouts 而非更新权重，因此 rollout 吞吐与 GPU 利用率成为训练时间与成本的首要决定因素。完成长度还差异极大，这意味着僵化的批处理会让 GPU 空转，等少数几条长轨迹跑完。

Fireworks 可以跑异步 RL：让 rollout 收集与训练重叠，而不是强迫循环的两侧顺序执行。rollout GPU 可以在训练器更新上一批的同时开始生成下一批，并在算法允许更多重叠时提供有界的权重陈旧度。目标很简单：让 GPU 一直做有用的工作，而不是在同步屏障前等待。

一旦循环完成一个训练步，更新后的模型必须传输并加载进 rollout 部署。Fireworks 不必在每一步之后拆掉 rollout 部署、重载整个模型，而是把新权重热加载进正在运行的部署。对全参数 checkpoint，我们使用新的压缩技术降低权重传输的带宽与存储需求：在当前与先前权重之间计算 XOR Diff，并用 zstd 压缩缩小负载。这让传输带宽最多降低 10 倍，显著加速训练循环。

### 开发速度：压缩迭代周期

到生产的瓶颈往往不是训练作业本身，而是两次迭代之间的间隔。在割裂的技术栈里，每个循环都意味着把 checkpoint 在训练与推理系统之间搬运、重新部署、对账差异、跑评估、再来一遍。

Fireworks 把这个过程变成一个连续的开发循环：在同一平台上训练 → 部署 → 评估 → 重训。checkpoint 直接进入服务，而生产轨迹、评估与反馈喂给下一次训练。而且由于我们处理 GPU 开通、容量与配置，客户跳过了拖慢迭代与上市时间的采购、模型启用和基础设施定容工作。团队报告同样的训练预算下迭代次数多 2–4 倍，把模型开发从数周压到数小时，加速投产。
