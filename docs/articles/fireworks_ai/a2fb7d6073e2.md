Kimi K3 现已通过 **Fireworks Serverless Training** 开放 Multi-LoRA 服务与训练的内测（private preview）。

Kimi K3 是一个庞大的混合专家（MoE）模型，总参数约 2.8 万亿，是第一个达到 3T 参数规模的开放权重模型。训练这样一个巨型模型过去是个大工程。而从今天起，它在 Fireworks 上只是一行代码的改动。

秘诀是什么？LoRA 适配器：训练便宜、服务便宜，而且强大到足以对 K3 做有意义的后训练。有了 Fireworks Training，你可以把世界上最好的开源模型拿来，花小钱教会它精准完成你的任务——不必付前沿模型的价格，也不必碰 GPU 集群。

## **先快速科普一下**

**LoRA（Low-Rank Adaptation，低秩适配）**

- •不去训练模型的每一个参数，而是在模型之上训练一小组挂载权重（称为**适配器，adapter**）。
- •这是最便宜的训练方式，而且易于存储：适配器只有几兆字节。
- •最擅长行为与风格：人设、语气、格式、结构化输出、新目标函数、工具调用循环。
- •复杂度由适配器的**秩（rank, r）**决定。即便是一个 rank-1 适配器——单一方向的改变——也能显著引导行为，这就是 LoRA 以小博大的原因。

**在 Fireworks 上服务一个 LoRA**

训练完成后，适配器会加载进一个推理部署中用于评估或生产。我们提供两种方式：

- **Live merge** 在部署时把单个适配器折叠进模型，因此以完整基座模型速度运行、零开销。
- **Multi-LoRA** 在一个部署上托管多个适配器，并把每个请求路由到对应的那一个。

无论哪种方式，基座权重在内存中只驻留一份，所以在其上叠很多适配器时，每新增一个微调的边际成本接近于零。参见[部署 LoRA 指南](https://docs.fireworks.ai/fine-tuning/deploying-loras)。

## **规模化的成本效率：按 token 计费训练与灵活服务**

微调一个前沿模型是真的难。它横跨三个层面的工作：研究本身、训练器实现与优化、基础设施与 GPU 管理。Fireworks 上的 serverless 训练就是你的新基础设施团队，把这三层全部折叠，让一个研究员无需专属基础设施团队在后也能独立作战。

没有训练器要拉起，也没有预留 GPU 集群要预订。循环归你：你的代码调用 forward_backward、step 优化器，并在同一会话里用你最新的权重采样。Fireworks 在一个共享 GPU 池上执行这些操作。你保留训练逻辑，我们处理硬件。无需启动，无需拆除。无需启动，无需拆除。

> “在 HUD，我们在数千个并发环境中运行智能体，为世界上最苛刻的一些实验室产出最好的后训练数据。这意味着底下的训练层必须是一流的。我们的训练也是爆发式的——我们在环境和奖励上不断迭代，最不想做的事就是守着集群或为两次运行之间的闲置 GPU 付费。Fireworks serverless 训练同时满足这两个要求：我们把训练循环指向一个端点，几秒内接入预热池，按 token 付费而不是按预留小时付费。我们按工作负载需要随意伸缩，不用去操心 GPU 集群，让团队专注于环境和奖励质量——那才是真正的工作所在。”

> Lorenss Martinsons，HUD 创始人兼联合 CEO

调整 rank（r）让适配器的容量匹配你的任务，然后迭代。内测账户最多可跑 8 个并发训练任务且速率限制宽松，因此你可以并行验证多个想法。

## **为什么选 Fireworks Serverless Training**

你按 token 付费。一次小型强化学习运行，大约 20 步、86 万训练 token，总花费约 $65——训练加采样都算在内——根据池子负载在 30 到 60 分钟内完成。强化学习是主要用例：从适配器采样、用你的奖励打分、走一步、重复。而且由于完整的 KV 缓存感知，多轮智能体运行的成本要低得多，因为重复上下文的计费只有标准 prefill 费率的 20%。详见 [serverless 训练指南](https://docs.fireworks.ai/fine-tuning/training-api/serverless)。

当你成长到超出共享池，同一套 SDK 可以跑在[专用训练](https://docs.fireworks.ai/fine-tuning/training-api/dedicated)上——同样这条路径支持全参数训练、DPO、持续 RL，以及对 checkpoint、部署和生命周期的显式控制。

我们还[保证训练与推理之间数值一致性对齐](https://fireworks.ai/blog/when-faster-not-identical-moe-numerics)，serverless 和专用皆可，因此训练 rollout 里看到的就是你在生产里得到的。模型就绪后，一键直接部署到推理，无需换平台、无需交接。

## **LoRA 如何为你的任务学会可靠性**

要看 LoRA 的实战效果，我们挑了两个像人们真正会交付的工作的任务。然后我们在 K3 上各训练一个小的适配器，看它学习。没有全参数运行，没有触碰基座权重。只有一个小的适配器加几十步练习。

### **任务 1：教 K3 一个新目标（Countdown）**

人们微调模型的常见原因之一，是教会模型用它已有的知识高效达成一个目标。

**Countdown**（倒计时算术）任务给模型几个数字（45、14、39）和一个目标数（20）。模型必须用算术命中目标（45 - 39 + 14 = 20）。评分看模型最终结果与目标的距离：接近有部分分，命中拿满分。模型本来就会加法和乘法，它要学的是目标本身：不断组合数字直到落在目标上，然后停下来。

K3 起步就不差，大多数情况下能完成到目标的约 80%，但它还能更好。它只需要学会这个新目标——大约十步之内就锁定，并保持在接近完美的解出率。这个任务告诉我们：当任务主要是学行为而非记事实时，一个小适配器能很快掌握。

你可以花几分钟复现它。代码在文末。

### **任务 2：教 K3 一步步解决问题（Frozen Lake）**

人们转向微调的另一个常见原因，是教他们的工具调用智能体高效使用工具集来达成目标。

**Frozen Lake**（冰湖）任务把智能体放到网格上，要求它从起点格走到目标格，且不能掉进洞里。每一回合，K3 观察网格、调用一个移动工具（上/下/左/右）、观察发生了什么、再决定下一步。就这样一回合接一回合，直到到达目标或失败。

这正是真实智能体背后的循环：观察、行动、再观察、重复。奖励同样现实。与 Countdown 不同，模型不能靠朝正确方向瞎逛拿部分分——只有抵达目标才得满分，失败则一分不得。

这一次，K3 起步接近掷硬币，因为模型得把「移动-检查-决策」的整个循环学下来。仅仅几次尝试之后它就逼近顶部，训练结束时几乎每次运行都能到达目标。

## **你的模型好不好，全看你的奖励好不好**

LoRA 把训练变得如此便宜，以至于挑战已不再是「训练你跑不跑得起」，而是「到底该奖励什么」。想让 LoRA 训练得好，仍然需要常规功夫：调学习率、调 rank，直到运行健康。但奖励才是决定模型瞄准什么的杠杆——在上面两个例子中，它对曲线的塑造超过其他任何因素。

Countdown 给部分分，所以模型越接近就越有得分。这个信号是稠密的（dense），曲线上升快而平滑。Frozen Lake 只为到达目标付费。这个信号是稀疏的（sparse）、更嘈杂，所以奖励花更久才开始攀升。模型越接近目标就得分越多，因此信号是**稠密的**，曲线上升快而平滑。Frozen Lake 只为到达目标付费。信号是**稀疏的**、更嘈杂，因此奖励花更久才顺畅攀升。

同一个基座模型、同一类适配器，两条迥异的学习曲线，主要是因为我们选择了不同的任务计分方式。这才是当今后训练真正的技艺所在。设计奖励的方法有很多，稀疏的、稠密的都有，训练曲线可以长得很不一样，但目标始终如一：把「完成且正确」定义得足够清晰，让小适配器能够可靠地追逐它。搞砸这一点，即便全参数训练也救不了你。

## **LoRA 之外**

对于单一的、边界明确的行为任务，几乎总存在一个 rank 值能让你到位。对很多任务而言，微调是教模型如何组合它已具备的能力，而像 K3 这样的前沿模型已经具备很多能力。大多数时候你只是教它一种表层形式（surface form），LoRA 对此足够好。

当目标变得宽泛或真正新颖时——同时训练许多不相关的任务、大范围蒸馏、继续预训练、或一门新语言/新领域——全参数训练仍有其一席之地。而且如果一次全参数微调确实胜出，原因未必显而易见，所以先跑一次 LoRA 往往是值得的。

**真正的优势出现在训练与服务同驻一个平台时**。训练一个适配器，用一次 API 调用把它部署到自动伸缩的端点，在生产中监控延迟、准确率与成本，收集反馈、失败案例和边缘情况，然后在新数据上触发一轮新的训练。每一圈都产出一个更聪明的模型。

这就是飞轮。LoRA 让第一圈便宜到任何人今天就能启动，而由于每个循环都在喂养下一个循环，专用智能会复利累积，形成一条越跑越宽的护城河。
