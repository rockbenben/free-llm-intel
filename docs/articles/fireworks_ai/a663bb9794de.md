## **TL;DR**

- •数值不一致能让训练脱轨：在 Fireworks 的 GLM 5.2 实验中，同一算法与数据在未对齐时奖励崩塌，在对齐后 25 步内保持稳定。
- •训练 MoE 模型给对齐增添了复杂性：我们的 Qwen3.5-MoE 调查发现，专家输出组合方式的差异会导致分歧——即便其中一个实现用了更高的精度。
- •这些分歧会扭曲训练更新，看上去却像数据、奖励或学习率的问题，把团队引入一轮轮昂贵的实验，而根因始终未解。
- •前沿训练需要训练与推理协同优化：Fireworks 把训练器与 rollout 引擎放在一起开发和验证，让团队能在数值、kernel 与 MoE 全对齐的前提下扩展强化学习。

## **规模化 RL 是一个系统问题**

rollout 生成可以占据强化学习（RL）大部分时间。ML 团队常用一个独立的推理引擎来高效生成 rollout。但那个引擎使用的 kernel、精度、批处理和并行方式可能与训练器不同。于是策略就有了两个实现：一个负责生成 token，一个负责计算梯度。即便权重完全相同，它们也可能给同一个 token 赋予不同的概率。

如果训练算法不考虑这种不一致，就可能扭曲更新、 destabilize 学习。在混合专家（MoE）模型中，这种不一致还可能翻转路由决定。当路由器分数几乎打平时，一个舍入差异就能改变哪些专家被激活。同一个 token 于是走了模型内不同的计算路径。

我们的实验展示了数值差异在哪里产生、为什么仅有 router replay 不够，以及弥合差距需要什么。

## **我们的实验揭示了什么**

### **数值不一致能让学习脱轨**

在 [Fireworks 的一项实验](https://fireworks.ai/blog/frontier-lab-training-infrastructure-as-a-service)中，我们在 GLM 5.2 上把同一个 RL 任务跑了两遍：一个 countdown 推理题，同一算法、同一训练数据。唯一的变量是训练器与 rollout 引擎计算 token 概率的方式是否一致。

当两者不一致时，运行分崩离析。两套系统的分歧达到约 0.013 的 KL，而标准保护机制为了维持训练稳定，几乎要丢弃每个 batch 的 45%。即便如此还不够。奖励爬到约 0.9，随后在第 20 步左右崩到 0.2 以下——模型在追逐一个与它自己生成内容已不再匹配的目标。数值对齐后，KL 为零，什么都没丢，奖励在整个运行中保持稳定。

> Fireworks GLM 5.2 countdown 实验：无数值对齐时奖励崩塌，对齐后在 25 个训练步中保持稳定。KL 为零的结论适用于所测的 LoRA 配置。

数值实现改变了结果，而算法和数据都没动。这让「训练器与 rollout 引擎的一致性」成为在修改训练配方并投入更多运行之前一项要紧的检查。

### **混合专家模型更难对齐**

有了路由专家，很多「数学上等价」的优化会产生数值上不同的结果。[Fireworks 一个针对 Qwen3.5-MoE 的训练实验](https://fireworks.ai/blog/when-faster-not-identical-moe-numerics)把一个重大数值分歧追到了专家输出的组合方式上。

在图像 token 上，训练路径与 Hugging Face 参考实现的偏差达到 k3 为 0.296——约为我们用来的判定两条路径等价的 0.001 阈值的 300 倍。在这个量级上，模型的两份副本之间的分歧，差不多相当于两个不同模型之间的分歧。

团队通过只把 MoE 块换成 Hugging Face 的参考模块、其余技术栈原封不动，把差距定位到 MoE 聚合。文本与图像 token 的 k3 值都降到了零。进一步调查确定了加权与求和专家输出所用精度上的差异。

这一发现说明为什么只匹配专家选择并不够：组合其输出所用的数值精度与执行顺序也必须对齐。

> Fireworks 的 Qwen3.5-MoE 实验，比较三条专家输出聚合路径及每一步所用的精度。

GLM 实验展示了数值不一致对学习意味着什么：一次烧着算力、奖励却在崩塌的运行。Qwen 调查展示了这种不一致多么容易躲过逐层检查。对研究者来说，其症状酷似数据、奖励或学习率的问题，于是引出更多修改配方却不触及根因的运行。

## **数值差异如何扰乱学习**

### **概率不匹配会扭曲更新**

训练与推理软件常用不同的数值精度层级，或以不同的顺序执行操作。由于中间结果会被舍入，`(a + b) + c` 可能与 `a + (b + c)` 不同。跨模型的整个计算，这些差异会改变赋予同一 token 的概率。浮点加法不满足结合律，而 RL 是发现这一点最昂贵的方式。

许多 RL 算法用概率比来引导更新。rollout 引擎与训练器之间未被计入的差异，能在任何学习发生之前就改变这些比率。这可能改变 token 对更新的影响强度，或因执行差异触发截断（clipping）。[verl rollout 校正文档](https://verl.readthedocs.io/en/latest/algo/rollout_corr.html)解释了校正如何处理这一缺口。

即便训练器对其 token 赋予不同概率，rollout 看上去仍可以像模像样。只检查生成的文本不会暴露这种分歧。在相同权重下比较概率能暴露它；训练-推理 KL 度量的正是这种分歧。

### **MoE 路由会放大不一致**

在混合专家模型里，一个小的数值差异还能改变哪些专家处理某个 token。当路由分数几乎打平时，舍入就能把选择推向另一个专家。token 于是经过不同的权重，并可能在后续层中把分歧进一步放大。

[R3 的研究者](https://arxiv.org/abs/2510.11370)证明了一致的路由对 RL 稳定性的影响。他们的 router replay 方法在 rollout 生成期间记录路由决定，并在训练期间复用。这在他们测试的设定中稳定了训练。

Router replay 让专家选择保持一致，但其输出如何计算与组合上的差异仍可能存在。让 rollout 与训练器的概率对齐，需要横跨两个实现（包括 kernel、精度与执行顺序）的工程。这项工作正是可靠运行一套训练配方所需基础设施的一部分。

## **Fireworks 让训练循环保持一致**

Fireworks 将训练器与 rollout 引擎一并开发，承担让快速 rollout 生成与训练保持一致所需的复杂工程。这降低了昂贵的运行因实现差异而报废的风险，把更多训练预算留给有前景配方的测试与扩展。

我们的方法包含三个关键要素：

**数值对齐：让计算一致。**对齐覆盖模型在两套系统中的执行方式，包括注意力、专家计算、聚合，以及跨 GPU 的操作。

**Router replay：用同样的专家。**[Router replay 支持](https://docs.fireworks.ai/guides/rollout-inference#moe-router-replay)为使用自有训练器的团队提供 rollout 生成期间记录的专家选择。把这些记录集成进训练，训练器就能复用同样的选择。

**验证：在全模型范围内度量一致性。**在相同权重下比较 token 概率，能暴露单个操作检查会漏掉的分歧。持续验证使用训练-推理 KL，在 Fireworks Training 上线的模型上、不同 batch 条件下度量一致性。上文的 GLM 对比就是一个公开案例。
