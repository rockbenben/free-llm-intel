## 摘要（TL;DR）

- Fireworks 通过把训练、rollout 生成与策略更新放在一起优化，让强化学习在 Kimi K3 的 2.8T 参数上变得切实可行，训练更快、更稳定。
- 在本报告中，我们详述了用于降低迭代开销的自定义 kernel、长上下文缓存与压缩权重传输，以及保持训练稳定的数值对齐与 Router Replay。
- Fireworks 无服务器训练让团队可以通过 Fireworks Training API 在 Kimi K3 上测试自己的任务与奖励函数，共享训练与 rollout 容量，无需自行准备专用 GPU。

让一个前沿模型走向专精，意味着把它的行为适配到特定领域的任务、工具与成功标准。[强化学习（RL）](https://aclanthology.org/2025.findings-emnlp.970/) 通过一个反复循环实现这一点：模型生成轨迹——一连串动作与观测——评估器赋予奖励，训练器更新策略，让成功的行为更可能出现。

在 Kimi K3 的规模上，实用的 RL 需要整条训练循环都高效执行。rollout 生成与训练必须维持高吞吐，更新后的策略必须能快速可用，训练与推理之间的数值对齐也必须保持。为了做实验，系统还必须支持彼此独立的运行，而不必为每个实验准备专用基础设施。

本报告介绍 Fireworks 在 Kimi K3 上支撑 RL 的系统，涵盖全参数训练与 rollout 生成、训练—推理一致性，以及无服务器 LoRA 训练。我们考察这些组件如何降低迭代开销，帮助团队更高效地开发与评估专用策略。

## 训练

[Kimi K3](https://arxiv.org/abs/2607.24653) 是一个 **2.8T 参数模型，上下文窗口 1M token**。在这一规模下，模型状态与长序列激活会挤压显存容量，而其混合架构又带来独特的计算与通信瓶颈。

组件

Kimi K3

注意力

69 层 Kimi Delta Attention（KDA）+ 24 层 Multi-head Latent Attention（MLA）

Latent MoE

896 个专家；top-16；latent 维度 3,584

专家激活

SiTU

路由专家量化

Group-32 MXFP4 权重；group-128 FP8 激活

Attention Residuals

对层输出做分块注意力

Fireworks 用专门的 mixture-of-experts（MoE）、Kimi Delta Attention（KDA）与 Attention Residual kernel 来应对这些瓶颈，并以面向长序列的分布式训练作为支撑。

### MoE Mega Kernel

K3 的 [LatentMoE](https://arxiv.org/abs/2607.24653) 把 FP4 专家分布到多张 GPU 上，需要在专家计算前后做 all-to-all dispatch 与 combine。[DeepEP](https://github.com/deepseek-ai/DeepEP) 加速了这些传输，但暴露在外的通信仍可能让 tensor core 空转。类似的通信—计算重叠已在 [Mixture-of-Kittens](https://arxiv.org/abs/2609.36070)、[COMET](https://arxiv.org/abs/2502.19811) 与 [FlashMoE](https://arxiv.org/abs/2506.04667) 中发表。

我们自研的 **MoE Mega Kernel** 把这些通信—计算重叠技术适配到 K3 的路由专家前向与反向传播：

- **环形缓冲区约束 dispatch 暂存。** 随着工作推进复用 token 缓冲区的槽位，限制 dispatch 所需的工作区。
- **微批处理构成连续流水线。** 跨 microbatch 重叠 dispatch、专家计算与结果返回；反向同样把梯度通信与计算重叠起来。
- **把量化融进暂存阶段。** 将 FP8 激活与 scale 直接写入通信缓冲区，消除中间拷贝，同时保持 K3 的量化契约。

![MoE Mega Kernel FWD：重叠与缓冲区复用](https://cdn.sanity.io/files/pv37i0yn/horizon/19bead5726417c879c48f36fd58cf2a0269d72d3.svg)

前向与反向的调度示意图；底部条带为实测的 16K token/rank 计时。收益包括减少暂存与数据搬运，以及重叠。

相对于**经过优化的原生 DeepEPv2** 基线，在**每 rank 1K-128K token** 范围内，它带来**前向 1.87-2.61×**、**反向 1.31-2.13× 的加速**。对比中包含 Normal EP，以展示在已经优化过的通信后端之上还能获得的额外增益。

8× B300，EP=8；优化后的 DeepEPv2 = 1×。路由专家前向/反向分别测量，包含通信；不是全模型吞吐。

### KDA：从循环记忆到高效的 GPU 执行

[Kimi Delta Attention（KDA）](https://arxiv.org/abs/2607.24653) 是一种线性注意力机制，用逐通道门控去更新一个紧凑的循环状态，使计算量随序列长度线性增长，解码状态大小固定。高效的训练必须并行化 chunk 内的局部工作，同时限制循环依赖与中间数据搬运带来的停顿。

我们构建了一个针对 Blackwell 优化的**自研 KDA kernel**，它融合相关运算并减少中间显存流量。相比 [FLA 的 KDA 实现](https://github.com/fla-org/flash-linear-attention/tree/main/fla/ops/kda)，在 **4K-128K token** 的序列长度上带来**前向 1.49-1.58×**、**反向 1.49-1.51× 的加速**。

B300，无 CP；FLA Triton = 1×。仅 KDA 核心，包含 Q/K 归一化与 gate scan。

### Attention Residuals：更低内存，更快训练

[Attention Residuals](https://arxiv.org/abs/2607.24653) 在模型深度方向上组合各层表示。在长序列下，用于归一化、加权与梯度计算的中间张量会占用可观的显存与带宽，挤占原本可用于训练的容量。

我们的 kernel 融合归一化与加权求和运算，减少前向与反向过程中的中间张量物化与数据搬运。

相比 [K3 布局下的 FLA](https://github.com/fla-org/flash-linear-attention/tree/main/fla/ops/attnres)，该实现跨 **1K-256K 本地 token** 带来**前向+反向合计 1.75-2.50× 的加速**。在 128K 时，实测峰值分配显存从 **63.02 降到 35.03 GiB**——**降低 44%**，为周边训练负载留出更多可用显存。

共享 B300，BF16；算子前向 + 反向，FLA = 1×。由于 GPU 共享下会 OOM，64K 以上的 PyTorch 结果被略去。

### 分布式训练

在 **2.8T 参数**下，全参数训练需要把权重、梯度与优化器状态分片到多张 GPU 上。接近 **1M token** 的序列还会带来激活显存压力，以及 MLA 层中二次方复杂度的注意力计算。我们组合三种并行策略，同时应对模型规模与序列长度：

- [**完全分片数据并行（FSDP）**](https://arxiv.org/abs/2304.11277)。分片参数、梯度与优化器状态。预取会把即将进行的 weight all-gather 与 gradient reduce-scatter 和当前层的计算重叠起来。
- [**上下文并行（CP）**](https://arxiv.org/abs/2405.07719)。把长序列切分到多张 GPU，为 KDA 的循环状态传播保留连续的 token 区间，同时平衡 MLA 因果注意力的负载。
- [**专家并行（EP）**](https://www.jmlr.org/papers/volume23/21-0998/21-0998.pdf)。把路由专家分布到多张 GPU，并将 EP 与 FSDP 结合以控制专家权重的常驻工作集。我们的 **MoE Mega Kernel** 在把 token dispatch 与 combine 和计算流水化的同时保持专家 GEMM 高效，减少暴露出来的 all-to-all 延迟。

我们的 **Kernel Bricks** 库提供感知拓扑与载荷的集合通信实现，降低各种训练配置下的通信延迟。例如 AllReduce 相比 PyTorch Distributed 取得 **1.67-3.31×** 的加速。

## Rollout

Fireworks 支持面向全参数强化学习的 Kimi K3 rollout 推理。这类负载与普通的聊天服务不同：数千条轨迹反复从共享 prompt 分叉，在生成与工具调用之间交替，并逐步长成很长的多轮历史。rollout 引擎必须让这些历史保持可复用，并高效执行一个 2.8 万亿参数的混合 MoE 模型。

本节说明在 GB300 系统上让这一切成为可能的 rollout 侧技术。

### 一个模型，两种缓存状态

[KV cache](https://arxiv.org/abs/2309.06180) 存储继续生成所需的注意力状态，避免重算整个 prompt。[K3](https://arxiv.org/abs/2607.24653) 把逐 token 保留 KV 历史的 MLA，与用紧凑循环状态概括历史 token 的 KDA 结合起来。复用一段对话前缀，需要这两份历史都代表对话中的同一个位置——尤其当 RL 轨迹从共享 prompt 分叉、或在工具调用之后继续时。

Fireworks 协调 MLA 与 KDA 的历史，使两种缓存状态始终代表同一个前缀。这样在对话变长、并发轨迹变多时仍能保住可复用的工作，减少重复 prefill，同时每条分支都维持独立而一致的状态。

MLA KV 历史与 KDA 状态一起复用，而每条轨迹各自独立推进。

在我们的长上下文、多轮 rollout 基准中，Fireworks 达到约 **99% 的缓存命中率**，几乎全部 prompt token 都能从缓存中复用。

### 不破坏循环状态的投机解码

[投机解码（Speculative decoding）](https://proceedings.mlr.press/v202/leviathan23a.html) 用较小的 draft 模型提出候选 token，再由目标模型并行验证。Fireworks 为 Kimi K3 训练了一个 speculator；在两个引擎的 draft 长度都取 3 时，我们的 replay 基准显示每个验证步产出的 token 比 SGLang DSpark 基线最多多 12%。

K3 的循环 KDA 状态在被拒绝的 token 之后必须保持一致。我们集成 [ReplaySSM](https://tridao.me/blog/2026/replayssm/)，从已提交的检查点重放被接受 token 的紧凑状态更新输入，避免为每个候选保存全量状态快照。

ReplaySSM 只让 KDA 状态沿着被接受的前缀推进。

我们评估了**八类任务上的 322 个 replay 请求**，每个引擎使用 **16 张 GB300 GPU**，SGLang v0.5.18。**接受长度**统计每个验证步推进的 token 数，包含被验证的目标 token（draft 长度 3 时最大为 **4**）；结果按验证步数加权。

- **跨任务：** 通用聊天达到 **2.80 对 2.51 token（+12%）**，竞赛编程 **3.09 对 2.92（+6%）**，仓库 issue 修复 **3.47 对 3.29（+5%）**。其他 agent 任务提升 **1-3%**，基于技能的 agent 基本持平（**3.24 对 3.25**）。
- **跨上下文长度：** 增益在 **2-9%** 之间。最大的桶 **10-20K token（190 个请求）** 达到 **3.37 对 3.31（+2%）**；**60K+** 达到 **3.43 对 3.27（+5%）**。请求数少于 30 的桶，其准确度约为 ±0.3 token。

热缓存 replay，关闭思考，温度 0，最大输出 512；更新于 2026 年 9 月 29 日。上下文分桶聚合的是不同请求；接受长度的增益并不是端到端吞吐增益。

### 缩短通信关键路径

张量并行推理需要 GPU 先合并部分结果，计算才能继续。这些反复的同步会限制 K3 的生成速度，尤其是在解码 batch 较小时。

Fireworks 的 AllReduce 库采用感知拓扑与载荷的实现，减少暂存与通信延迟。这让依赖它的计算更早开始，缩短通信关键路径。

Fireworks 的 AllReduce 库按载荷大小与硬件拓扑选择集合通信路径。

### 选择内联 prefill 还是分离式 rollout 服务

这里描述的配置使用**内联 prefill**：prefill 与 decode 共用同一个 GPU 副本。这适合长时间运行的多轮 rollout，因为后续轮次可以复用保留的历史，只对新增的后缀做 prefill。内联服务也免去了把 MLA KV 与相匹配的 KDA 循环状态交给独立 decode 池的步骤。

[分离式服务（Disaggregated serving）](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin) 把 decode 与 prefill 隔离开，让每个池自行选择拓扑与容量。当未命中缓存的 prefill 体量很大，或严格的 token 时延足以支持这种拆分时，它很有吸引力。但对 K3 而言，每次交接都必须传递一致的 MLA KV 以及 KDA 的循环与卷积状态，在目标缓存里找到空间，并保持当前生效的 RL 策略版本。

内联服务也有自己的代价：prefill 会与正在进行的解码争抢 GPU 时间。正确的选择取决于 prompt 体量、生成长度、前缀复用、传输带宽与时延目标。比较两者需要相同的工作负载与相同的总 GPU 预算；这里描述的被测系统使用的是内联服务。

### 在宽专家组内协调 prefill

下面的基准采用 TP4 / DP4 / EP16 的混合布局：张量并行保持在快速的节点内互联之内，四个注意力组各自独立处理请求，专家并行跨越 16 张 GPU 的整组。这是一个测量配置，而不是通用的生产放置配方。

这就带来一个调度问题。只要一个注意力组开始 prefill，共享专家组里的每张 GPU 都必须参与，哪怕其他组手上并没有可用的 prefill。不均匀的 RL 轨迹因此会把许多小 prefill 变成反复的 padding 工作和解码中断。

Fireworks 的 DP prefill 配对给兄弟组一个短窗口去对齐有用的 prefill 工作，与此同时活跃请求继续解码。待处理的 prefill 会在所有组就绪或超时之后一起执行，用有界的等待换取更大的 batch 与更少的 padding。这与 [AMD 的 ATOM](https://rocm.blogs.amd.com/software-tools-optimization/atom-optimiztion/README.html) 中发表的通用有界延迟思路一致。

共用一个专家组的注意力组协同进行 prefill 准入；超时机制保证在到达持续不均衡时仍能推进。

### 历史增长时的吞吐

在一个合成的长上下文、多轮 rollout 负载上，**16 张 GB300 GPU（TP4 / DP4 / EP16）** 服务了 128 条并发轨迹、每条 50 轮，在整个计时运行期间（包含爬坡与排空）平均达到 2,834 输出 token/s。

每个点表示一分钟满并发窗口内的总输出吞吐，横轴是该窗口的平均 prompt 长度。

单独消融测得：使用 EAGLE3 时整轮吞吐提高 **49.37%**，使用 ReplaySSM 时提高 **65.05%**。ReplaySSM 的收益包含 GPU 缓存容量增加带来的部分。

### 合在一起

K3 的 rollout 性能来自把模型当作一个完整系统来对待。协同的 MLA 与 KDA 缓存保住了可复用的对话历史。ReplaySSM 让投机解码对循环状态也是安全的。Fireworks 的 AllReduce 库缩短了集合通信。内联服务与 DP prefill 配对把异步的 RL 轨迹转化为高效的 GPU 工作。

这些技术合在一起，让 Fireworks 能以高吞吐维持 K3 长而分叉的多轮 rollout，同时保持模型所要求的状态正确性。

## RL：快速迭代，稳定训练

### 用 XOR delta 做权重同步

同步 K3 的 **2.8T 参数**让全量检查点传输变得昂贵。我们把每次更新编码为按字节的[**XOR delta**](https://fireworks.ai/blog/frontier-rl-is-cheaper-than-you-think)，`Δ = W_new XOR W_base`，并用 Zstandard 压缩。未变化的字节变成零，压缩后的载荷随之变小。rollout worker 解压 delta 并应用 `W_base XOR Δ`，**逐比特**重建新的检查点。

在 [Fireworks 公开的负载](https://fireworks.ai/blog/frontier-rl-is-cheaper-than-you-think) 中，一个 **1,024 GiB** 的检查点产生了平均 **20.3 GiB 的 delta**——**每次 delta 更新少了 98% 的字节**。把周期性的全量检查点也算进去，50 步内总传输量下降了 **94%**。

![XOR 权重同步：很小的 delta，同样新的权重](https://cdn.sanity.io/files/pv37i0yn/horizon/01a9d2689430deecbb245cb408cefa6b842ca36a.svg)

### RL 稳定性与数值

#### 确定性

训练与 rollout 之间的[数值漂移](https://fireworks.ai/blog/when-faster-not-identical-moe-numerics)即使两边权重完全相同，也会扭曲 RL 的重要性比率。这与 policy staleness 不同：后者的 rollout 数据来自 learner 更新权重之前的旧策略。两种效应如果不去测量和控制，都会让策略更新变得不稳定。

我们在 K3 的前向过程中强制确定性执行，覆盖主要 kernel 与归约，使固定的权重、输入与执行配置产生一致的输出。

包括 **RMSNorm** 在内的关键 kernel 也支持 batch 无关（batch-invariant）的执行。对 RMSNorm 而言，固定的归约顺序让结果在不同 batch 大小下保持一致，同时保留 K3 的舍入边界可以减少[训练—推理漂移](https://fireworks.ai/blog/when-faster-not-identical-moe-numerics)。

#### Router replay（R3）

即使权重完全相同，微小的数值差异也可能改变 top-k 专家选择，让训练与 rollout 的 log-probability 出现分歧。**Fireworks RL 平台**支持[**Router Replay（R3）**](https://arxiv.org/abs/2510.11370)：learner 复用 rollout 时的专家选择，同时用当前参数重算门控权重与专家输出。

有了这些数值对齐措施，在这一配置下，同步 [**LoRA**](https://arxiv.org/abs/2106.09685) 的 train-rollout 分歧低至 **0.0008**。我们用按 token 平均的 [Schulman k3 估计器](http://joschu.net/blog/kl-approx.html)报告估计的 KL 散度；结果取决于序列长度与执行配置。

## 开始使用 Kimi K3 无服务器训练

![用无服务器 Kimi K3 更快地做实验](https://cdn.sanity.io/files/pv37i0yn/horizon/fc5b24f6ecdd823cea67cd6d3b5ef2a173669430.svg)

一个新的奖励函数、一份不同的数据集、一个更好的学习率：强化学习的进步来自尝试想法并衡量哪些有效。Fireworks 无服务器训练让这些实验在 Kimi K3 上变得可行，训练与 rollout 容量以共享方式通过 Python API 提供。

你的实验连接到一个已经在运行的训练器与 rollout worker 池。无需为每次运行准备专用 GPU 分配、启动 trainer 作业，或单独拉起一套 rollout 部署。使用现成的池把基础设施准备从实验搭建中抹掉，缩短从想法到训练循环的路径。

[多 LoRA](https://arxiv.org/abs/2106.09685) 的 trainer 与推理引擎让不同的运行与策略快照共享同一份基座权重。推理侧，adapter 异步加载，[multi-LoRA kernel](https://arxiv.org/abs/2310.18547) 减少重复的准备与数据搬运。训练侧，调度器把相容的请求合并成批，在 adapter 局部性与公平性之间取得平衡。优化器状态被卸载，并随会话调度异步暂存，为更长的上下文和更多的活跃 adapter 留出 GPU 显存。

![CSGMV：高效的 adapter 计算](https://cdn.sanity.io/files/pv37i0yn/horizon/87ccbafbbeaea0d2f1903e4b5953392c0945a707.svg)

rollout 生成通常占掉 RL 迭代时间的大头。高吞吐既需要 adapter 并发，也需要足够的缓存容量来容纳长而分叉的历史。Fireworks 采用分层的 adapter 与缓存管理：可复用的 KV 与 KDA 状态可以挪到主机内存，活跃 adapter 占用 GPU 槽位，不活跃的快照异步加载。缓存复用严格限定在正确的 adapter 与策略版本之内，使就绪的 rollout 继续推进，又不让状态在实验之间混淆。

![准备 adapter，让 rollout 持续运转。](https://cdn.sanity.io/files/pv37i0yn/horizon/e10007a4bb183e296257c3ed31556385d895a282.svg)

### 一个真实案例：Visual ToolBench

在一次无服务器 Kimi K3 实验中，面向带图像工具的多轮 [VisualToolBench](https://arxiv.org/abs/2510.12712) 任务，在固定的 50 个任务的评估集上，经过 **20 次训练更新**后，评估奖励从 **0.314 升到 0.451**。可参见 Fireworks cookbook 中的[完整可运行示例](https://github.com/fw-ai/cookbook/blob/main/training/examples/serverless_rl/visual_toolbench_rl.py)。

[用 Fireworks 无服务器训练开始一个 Kimi K3 实验](https://docs.fireworks.ai/fine-tuning/training-api/serverless)。带上你的任务、环境与奖励函数，用共享的训练与 rollout 工作流测试你的下一个想法。
