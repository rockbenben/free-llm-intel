## 长篇大论；博士

- Fireworks 通过优化训练、部署生成和策略更新，使强化学习在 Kimi K3 的 2.8T 参数上变得实用，以实现更快、更稳定的训练。
- 在本报告中，我们详细介绍了可减少迭代开销的自定义内核、长上下文缓存和压缩权重传输，以及保持训练稳定的数值对齐和路由器重放。
- Fireworks 无服务器训练让团队可以通过 Fireworks Training API 在 Kimi K3 上测试自己的任务和奖励功能，并共享训练和部署容量，无需配置专用 GPU。

专业化前沿模型意味着使其行为适应特定领域的任务、工具和成功标准。 [强化学习 (RL)](https://aclanthology.org/2025.findings-emnlp.970/) 通过重复循环来实现这一点：模型生成轨迹（行动和观察序列），评估者分配奖励，训练者更新策略以提高成功行为的可能性。

在 Kimi K3 的规模上，实用的强化学习需要在整个训练循环中高效执行。推出生成和训练必须维持高吞吐量，必须快速提供更新的策略，并且必须保持训练和推理之间的数值一致性。对于实验，系统还必须支持独立运行，而不需要为每个实验提供专用基础设施。

本报告介绍了 Fireworks 在 Kimi K3 上支持强化学习的系统，涵盖全参数训练和部署生成、训练推理一致性以及无服务器 LoRA 训练。我们研究这些组件如何减少迭代开销并帮助团队更有效地开发和评估专门策略。

[Kimi K3](https://arxiv.org/abs/2607.24653) 是一个 **2.8T 参数模型，具有 1M 代币上下文窗口**。在这种规模下，模型状态和长序列激活会对内存容量造成压力，而其混合架构则引入了明显的计算和通信瓶颈。

Fireworks 通过专门的专家混合 (MoE)、Kimi Delta Attention (KDA) 和 Attention Residual 内核来解决这些瓶颈，并由长序列的分布式训练提供支持。

### 教育部超级内核

K3 的 [LatentMoE](https://arxiv.org/abs/2607.24653) 将 FP4 专家分布在 GPU 上，需要围绕专家计算进行全面调度和组合。 [DeepEP](https://github.com/deepseek-ai/DeepEP) 加速了这些传输，但暴露的通信仍然会使张量核心闲置。类似的通信计算重叠已在 [Mixture-of-Kittens](https://arxiv.org/abs/2609.36070)、[COMET](https://arxiv.org/abs/2502.19811) 和 [FlashMoE](https://arxiv.org/abs/2506.04667) 中发布。

我们的内部 **MoE Mega Kernel** 将这些通信计算重叠技术适应 K3 的路由专家前向和后向传递：

- **环形缓冲区绑定调度暂存。** 随着工作进展重复使用令牌缓冲区插槽，限制调度工作空间。
- **微批处理实现了连续的管道。**跨微批的重叠调度、专家计算和结果返回；向后类似地将梯度通信与计算重叠。
- **将量化融合到分段中。** 将 FP8 激活和缩放直接写入通信缓冲区，消除中间副本，同时保留 K3 的量化契约。

![MoE Mega Kernel FWD：重叠和缓冲区重用](https://cdn.sanity.io/files/pv37i0yn/horizon/19bead5726417c879c48f36fd58cf2a0269d72d3.svg)

前向和后向调度示意图；底部条显示测量的 16K 令牌/排名计时。收益包括减少分期和数据移动以及重叠。

相对于 **优化的本机 DeepEPv2** 基准，它在 **每等级 1K-128K 代币** 上提供 **1.87-2.61× 前向** 和 **1.31-2.13× 后向加速**。该比较包括正常 EP，以显示超出已优化通信后端的额外增益。

8×B300，EP=8；优化的 DeepEPv2 = 1×。 Routed-expert前向/后向单独测量，包括通信；不是全模型吞吐量。

### KDA：从循环内存到高效的 GPU 执行

[Kimi Delta Attention (KDA)](https://arxiv.org/abs/2607.24653) 是一种线性注意机制，它使用通道门控来更新紧凑的循环状态，从而提供具有序列长度和固定大小解码状态的线性计算缩放。高效的训练必须并行化块本地工作，同时限制循环依赖和中间数据移动造成的停顿。

我们构建了一个针对 Blackwell 进行优化的**内部 KDA 内核**，它融合了相关工作并减少了中间内存流量。相对于 [FLA 的 KDA 实现](https://github.com/fla-org/flash-linear-attention/tree/main/fla/ops/kda)，它在 **4K-128K 令牌**的序列长度上提供 **1.49-1.58× 前向** 和 **1.49-1.51× 后向加速**。

B300，无CP； FLA 海卫一 = 1×。仅 KDA 核心，包括 Q/K 归一化和门扫描。

### 注意力残差：内存更低，训练更快

[注意力残差](https://arxiv.org/abs/2607.24653) 结合了模型深度的表示。在长序列长度下，用于归一化、加权和梯度计算的中间张量可能会消耗大量内存和带宽，从而减少可用于训练的容量。

我们的内核融合了归一化和加权和运算，以减少向前和向后过程中的中间张量具体化和数据移动。

与 [K3 布局中的 FLA](https://github.com/fla-org/flash-linear-attention/tree/main/fla/ops/attnres) 相比，此实现在 **1K-256K 本地令牌**上提供 **1.75-2.50× 组合的前向和后向加速**。在 128K 时，测得的峰值分配内存从 **63.02 GiB** 下降到 35.03 GiB** — **降低了 44%**，为周围的训练工作负载留下了更多可用内存。

共用B300、BF16；向前+向后算子，FLA = 1×。由于 GPU 共享下的 OOM，64K 以上的 PyTorch 结果被省略。

### 分布式训练

在**2.8T 参数**下，全参数训练需要跨 GPU 分片权重、梯度和优化器状态。接近 **1M 令牌**的序列会增加 MLA 层中的激活记忆压力和二次注意力计算。我们结合三种并行策略来解决模型规模和序列长度问题：

- [**完全分片数据并行性 (FSDP)**](https://arxiv.org/abs/2304.11277)。分片参数、梯度和优化器状态。预取将即将到来的权重全收集和梯度减少分散与当前层的计算重叠。
- [**上下文并行性 (CP)**](https://arxiv.org/abs/2405.07719)。在 GPU 之间对长序列进行分区，为 KDA 的循环状态传播保留连续的标记范围，同时平衡 MLA 的因果注意力工作负载。
- [**专家并行性 (EP)**](https://www.jmlr.org/papers/volume23/21-0998/21-0998.pdf)。将路由专家分布在 GPU 上，并将 EP 与 FSDP 结合起来，以控制专家权重工作集。我们的 **MoE Mega Kernel** 保持专家 GEMM 的高效，同时管道化令牌调度和计算组合，减少暴露的所有延迟。

我们的 **Kernel Bricks** 库提供了拓扑和有效负载感知的集体实现，可以减少训练配置之间的通信延迟。例如，AllReduce 比 PyTorch Distributed 实现了 **1.67-3.31× **加速。

## 推出

Fireworks 支持 Kimi K3 推出全参数强化学习推理。工作负载与普通的聊天服务不同：数千条轨迹从共享提示中反复分支，在生成和工具使用之间交替，并成长为漫长的多轮历史。推出引擎必须保持这些历史记录可重用，并有效执行 2.8 万亿参数的混合 MoE 模型。

本节介绍了在 GB300 系统上实现这一点的转出端技术。

### 一种模型，两种缓存状态

[KV 缓存](https://arxiv.org/abs/2309.06180) 存储继续生成所需的注意力状态，而无需重新计算完整的提示。 [K3](https://arxiv.org/abs/2607.24653) 将 MLA 与 KDA 结​​合起来，MLA 保留了逐个令牌的 KV 历史记录，KDA 以紧凑的循环状态总结了先前的令牌。重用对话前缀需要两个历史记录代表对话中的同一点，尤其是当 RL 轨迹从共享提示分支或在工具调用后恢复时。

Fireworks 协调 MLA 和 KDA 历史记录，因此两个缓存状态始终表示相同的前缀。随着对话的增长和更多轨迹同时运行，这可以保留可重用的工作，减少重复的预填充，同时每个分支保持独立、一致的状态。

MLA KV 历史和 KDA 状态一起重用，而每个轨迹独立继续。

在我们的长上下文、多轮部署基准测试中，Fireworks 实现了大约 **99% 的缓存命中率**，允许从缓存中重用几乎所有提示令牌。

### 推测解码而不破坏循环状态

[推测性解码](https://proceedings.mlr.press/v202/leviathan23a.html) 使用较小的草稿模型来提议令牌，并使用目标模型来并行验证它们。 Fireworks为Kimi K3培养了一名投机者；当两个引擎都使用 3 的草稿长度时，我们的重放基准显示每个验证步骤的令牌比 SGLang DSpark 基准多出 12%。

在拒绝令牌后，K3 的循环 KDA 状态必须保持一致。我们集成 [ReplaySSM](https://tridao.me/blog/2026/replayssm/) 来重放来自已提交检查点的已接受令牌的紧凑状态更新输入，从而避免每个候选者的全状态快照。

ReplaySSM 仅通过接受的前缀推进 KDA 状态。

我们评估了**八种任务类型**的 322 个重播请求，**每个引擎 16 GB300 GPU** 和 SGLang v0.5.18。 **接受长度**计算每个验证步骤前进的令牌，包括已验证的目标令牌（草稿长度为 3 时最大 **4**）；结果通过验证步骤进行加权。

- **跨任务：**一般聊天达到 **2.80 与 2.51 代币 (+12%)**，竞争性编程 **3.09 与 2.92 (+6%)**，以及回购问题修复 **3.47 与 3.29 (+5%)**。其他代理任务提高了 **1-3%**，而基于技能的代理基本没有变化（**3.24 与 3.25**）。
- **跨上下文长度：**增益范围为**2-9%**。最大的存储桶，**10-20K 令牌（190 个请求）**，达到 **3.37 与 3.31 (+2%)**； **60K+** 达到 **3.43 与 3.27 (+5%)**。请求数少于 30 个的存储桶报告的准确度约为 ±0.3 个令牌。

热缓存重放，思考，温度0，最大输出512； 2026 年 9 月 29 日更新。上下文桶聚合不同的请求；接受度增益不是端到端吞吐量增益。

### 缩短沟通关键路径

张量并行推理需要 GPU 在继续计算之前组合部分结果。这些重复的同步会限制 K3 的生成速度，尤其是在解码批量较小的情况下。

Fireworks 的 AllReduce 库使用拓扑和负载感知实现来减少分段和通信延迟。这使得相关计算可以更快地开始并缩短通信关键路径。

Fireworks 的 AllReduce 库根据有效负载大小和硬件拓扑选择集体路径。

### 选择内联或分类推出服务

此处描述的配置使用**内联预填充**：预填充和解码共享相同的 GPU 副本。这适合长时间运行的多轮部署，因为稍后的轮次可以重用保留的历史记录并仅预填充其新后缀。内联服务还避免将 MLA KV 和匹配 KDA 循环状态交给单独的解码池。

[分类服务](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin) 将解码与预填充隔离，并允许每个池选择自己的拓扑和容量。当未缓存的预填充量或严格的令牌延迟证明分离合理时，它很有吸引力。然而，对于 K3，每次切换必须传输一致的 MLA KV 加上 KDA 循环和卷积状态，在目标缓存中找到空间，并保留活动的 RL 策略版本。

内联服务有其自身的成本：预填充与主动解码竞争 GPU 时间。正确的选择取决于提示量、生成长度、前缀重用、传输带宽和延迟目标。比较两者需要相同的工作负载和总 GPU 预算；这里描述的测量系统使用内联服务。

### 在广泛的专家组中协调预填充

下面的基准测试使用混合 TP4 / DP4 / EP16 布局：张量并行性保持在快速节点内结构内，四个注意力组独立处理请求，专家并行性跨越 16-GPU 组。这是一种测量配置，而不是通用的生产布局方案。

这就产生了调度问题。如果一个注意力组开始预填充，则共享专家组中的每个 GPU 都必须参与，即使其他组没有准备好有用的预填充。因此，不均匀的强化学习轨迹可能会将许多小的预填充变成重复的填充工作和解码中断。

Fireworks DP 预填充配对为同级组提供了一个短窗口，以便在活动请求继续解码时对齐有用的预填充工作。一旦所有组准​​备就绪或超时到期，挂起的预填充就会运行，交易有界等待更大的批次和更少的填充。这遵循 [AMD 的 ATOM](https://rocm.blogs.amd.com/software-tools-optimization/atom-optimiztion/README.html) 中发布的相同通用有界延迟方法。

共享一个专家组的关注小组协调预填入学；当到达保持不对称时，超时可以保证进度。

### 吞吐量随着历史的增长而增长

在合成的长上下文、多轮部署工作负载中，**16 GB300 GPU (TP4 / DP4 / EP16)** 在每个轮次超过 50 个轮次的情况下为 128 个并发轨迹提供服务，在整个定时运行（包括启动和耗尽）期间平均每秒输出 2,834 个令牌。

每个点都显示一分钟完全并发窗口期间的总输出吞吐量，根据该窗口中的平均提示长度绘制。

单独的消融测量表明，**EAGLE3** 的完整运行吞吐量提高了 49.37%，而 ReplaySSM** 的完整运行吞吐量提高了 65.05%。 ReplaySSM 的好处包括增加 GPU 缓存容量。

### 把它放在一起

K3 的推出性能来自于将模型视为一个完整的系统。协调的 MLA 和 KDA 缓存可保留可重用的对话历史记录。 ReplaySSM 使推测解码对于循环状态来说是安全的。 Fireworks 的 AllReduce 库缩短了集体通信。内联服务和 DP 预填充配对将异步 RL 轨迹转化为高效的 GPU 工作。

这些技术共同使 Fireworks 能够以高吞吐量维持长时间、分支、多轮 K3 部署，同时保持模型所需的状态正确性。

## RL：快速迭代，稳定训练

### 与 XOR 增量的权重同步

同步 K3 的 **2.8T 参数** 会使全检查点传输变得昂贵。我们将每个更新编码为字节 [**XOR delta**](https://fireworks.ai/blog/frontier-rl-is-cheaper-than-you-think)，`Δ = W_new XOR W_base`，并使用 Zstandard 对其进行压缩。未更改的字节变为零，从而减少了压缩的有效负载。 Rollout 工作人员解压缩增量并应用“W_base XOR Δ”来重建新的检查点**逐位**。

在 [Fireworks 发布的工作负载](https://fireworks.ai/blog/frontier-rl-is-cheaper-than-you-think) 中，**1,024 GiB** 检查点产生 **20.3 GiB 平均增量** — **每次增量更新减少 98% 的字节**。包括定期的完整检查点，总传输量在 50 个步骤中下降了 **94%**。

![异或权重同步：一个小增量，相同的新权重](https://cdn.sanity.io/files/pv37i0yn/horizo​​n/01a9d2689430deecbb245cb408cefa6b842ca36a.svg)

### RL 稳定性和数值

#### 决定论

即使两个系统使用相同的权重，训练和部署之间的[数值漂移](https://fireworks.ai/blog/when-faster-not-identical-moe-numerics)也会扭曲 RL 重要性比率。这与策略陈旧不同，在策略陈旧中，在学习器更新其权重后，推出数据来自较旧的策略。如果不加以衡量和控制，这两种效应都会破坏政策更新的稳定性。

我们在 K3 的前向传递中强制执行确定性执行，包括主要内核和缩减，因此固定权重、输入和执行配置会产生匹配的输出。

关键内核，包括 **RMSNorm**，也支持批处理不变执行。对于 RMSNorm，固定的缩减顺序可以在批量大小之间保持一致的结果，同时保留 K3 的舍入边界可以减少[训练推理漂移](https://fireworks.ai/blog/when-faster-not-identical-moe-numerics)。

#### 路由器重播 (R3)

即使在相同的权重下，小的数值差异也可能会改变 top-k 专家的选择，从而导致训练和推出对数概率出现分歧。 **Fireworks RL 平台**支持 [**路由器重放 (R3)**](https://arxiv.org/abs/2510.11370)：学习器重用 rollout 专家选择，同时根据当前参数重新计算门权重和专家输出。

通过这些数值对齐措施，在此配置中同步 [**LoRA**](https://arxiv.org/abs/2106.09685) 训练部署散度低至 **0.0008**。我们使用令牌平均 [Schulman k3 估计器](http://joschu.net/blog/kl-approx.html) 报告估计的 KL 散度；结果取决于序列长度和执行配置。

## Kimi K3 无服务器培训入门

![使用无服务器 Kimi K3 进行更快的实验](https://cdn.sanity.io/files/pv37i0yn/horizon/fc5b24f6ecdd823cea67cd6d3b5ef2a173669430.svg)

新的奖励函数、不同的数据集、更好的学习率：强化学习的进步来自尝试想法和衡量有效的方法。 Fireworks 无服务器训练使这些实验在 Kimi K3 上变得实用，并通过 Python API 提供共享训练和部署能力。

您的实验连接到已经运行的培训师和推广工作人员池。无需配置专用 GPU 分配、启动训练器作业，也无需为每次运行进行单独的部署部署。使用现有池可以从实验设置中删除基础设施配置，从而缩短从想法到培训循环的路径。

[multi-LoRA](https://arxiv.org/abs/2106.09685) 训练器和推理引擎让不同的运行和策略快照共享相同的基本权重。据推断，适配器异步加载，并且[多LoRA内核](https://arxiv.org/abs/2310.18547)减少了重复的准备和数据移动。在训练时，调度程序会批量处理兼容的请求，并公平地平衡适配器局部性。优化器状态会随着会话的调度而被卸载和异步暂存，从而为更长的上下文和更活跃的适配器保留 GPU 内存。

![CSGMV：高效适配器计算](https://cdn.sanity.io/files/pv37i0yn/horizon/87ccbafbbeaea0d2f1903e4b5953392c0945a707.svg)

Rollout 生成通常占用大部分 RL 迭代时间。高吞吐量需要适配器并发性和足够的缓存容量来支持长期的分支历史记录。 Fireworks 使用分层适配器和缓存管理：可重用的 KV 和 KDA 状态可以移动到主机内存，活动适配器占用 GPU 插槽，非活动快照异步加载。缓存重用的范围仍然限于正确的适配器和策略版本，因此准备好的部署可以继续进行，而无需在实验之间混合状态。

![准备适配器。继续推出。](https://cdn.sanity.io/files/pv37i0yn/horizon/e10007a4bb183e296257c3ed31556385d895a282.svg)

### 真实示例：Visual ToolBench

在使用图像工具对多轮 [VisualToolBench](https://arxiv.org/abs/2510.12712) 任务进行的无服务器 Kimi K3 实验中，在固定的 50 个任务评估集上测量，在 **20 次训练更新**后，评估奖励从 **0.314 增加到 0.451**。请参阅 Fireworks 说明书中的[完整的可运行示例](https://github.com/fw-ai/cookbook/blob/main/training/examples/serverless_rl/visual_toolbench_rl.py)。

[使用 Fireworks 无服务器训练开始 Kimi K3 实验](https://docs.fireworks.ai/fine-tuning/training-api/serverless)。带上您的任务、环境和奖励函数，并使用共享的培训和部署工作流程来测试您的下一个想法。
