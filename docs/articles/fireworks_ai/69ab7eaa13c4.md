## 底层原理：全新的分裂激活架构

DeepSeek-V4.1-Flash 是 DeepSeek 新架构家族中最小的模型，并带来了一些新的架构增强。

它是一个 552B 参数的 MoE，采用全新的编码器-解码器分裂架构。在这种架构中，模型不再为整次前向传播使用一个激活预算，而是把它拆成输入侧 8B 激活参数、输出侧 16B。这带来了更高效的设计，也让 token 开销更省。

这种不对称恰好契合编码智能体的工作方式。典型的智能体轨迹是严重输入密集的。编码智能体经常重读文件、重读自己的草稿板、重读工具输出，最后只产出一个相对很小的补丁。在我们的 DeepSWE 运行中，模型每任务消耗 3690 万输入 token，而输出仅 21.1 万 token，比例为 174:1。这一架构让开发者可以在输入侧少花一半的算力——而输入侧恰恰是 token 占比最大的地方。

## KV 缓存优化

与前一代 DeepSeek V4 相比，DeepSeek 在 DeepSeek-V4.1-Flash 上改进了 KV 缓存利用率，HBM 只消耗四分之一，SSD 存储只消耗八分之一。

图 2：DeepSeek-V4.1-Flash 上的 KV 缓存

这套新的 KV 缓存优化为你的编码智能体解锁了更好的经济性。从 DeepSWE 运行中，我们得到如下成本结构：

| 成本项 | 每任务 Token 数 | 单价 | 每任务成本 | 占比 |
| --- | --- | --- | --- | --- |
| 成本项 | 每任务 Token 数 | 单价 | 每任务成本 | 占比 |
| 未缓存输入 | 148,741 | $0.22/M | $0.0327 | 7.6% |
| 缓存命中输入 | 36,744,586 | $0.007/M | $0.2572 | 59.9% |
| 输出 | 211,513 | $0.66/M | $0.1396 | 32.5% |
| 合计 |  |  | $0.4295 |  |

**这次运行中 99.6% 的输入 token 是缓存命中，而缓存命中的计费占了账单的 60%。**

大多数人以为智能体的成本主要来自为模型生成的内容付费。然而在长时运行的智能体循环中，大部分开销来自反复重读同一段上下文。正是这种因重复任务产生的持续支出，让 KV 缓存内存 4 倍的削减对 token 花费产生了更大的影响。它直接命中智能体设计中最大的成本驱动项，把 74% 档位的 DeepSWE 得分对应的成本压低 15 倍。SSD 开销 8 倍的削减则与 HBM 优化形成互补，让长轨迹下的缓存命中率保持在约 99%。

## HLE 与 oracle 路由器评测

我们跑了第三个基准任务：Humanity's Last Exam，即 HLE。这是一个多模态基准，用于衡量 LLM 在研究生学科学术问题上的极限。在这轮测试中，我们还做了带 oracle 路由器的基准对比，做法与我们此前对 [Kimi K3](https://fireworks.ai/blog/kimik3-fable) 和 [DeepSeek V4 Pro](https://fireworks.ai/blog/DeepSeekV4Pro-Fable5) 的评测类似。快速回顾：oracle 路由是一种测量理论上最佳性能的方法——让每个模型都跑一遍任务，然后挑选成本最优的正确答案，从而确定成本与性能的上界。

| 配置 | HLE 得分 |
| --- | --- |
| 配置 | HLE 得分 |
| DeepSeek-V4.1-Flash | 34.52% |
| GPT-6-Astra | 50.40% |
| Oracle 路由器（GPT-6-Astra + DeepSeek-V4.1-Flash 取最优） | 54.80% |

在 HLE 上，单独运行的 DeepSeek-V4.1-Flash 落后于 Astra。这说明 DeepSeek 单独使用时更适合 DeepSWE 这样的智能体编码任务，而非 HLE 这样的推理任务。如果你的工作负载只有高难度科学推理，它可能不是正确选择。

真正有意思的结果是 oracle 路由器，它揭示了路由和多模型系统的重要性。Astra 加 DeepSeek V4.1 的 oracle 路由器表现优于单独使用 GPT-6 Astra。这 4.4% 的差距只有在 V4.1-Flash 答对了一批 Astra 答错的问题时才可能实现——34.52% 并不是 50.40% 的子集，两个模型失败在不同的题目上。需要注意的一点是：oracle 路由器代表你的应用可能达到的上界。真实路由器未必能吃到全部 4.4 个百分点的差距，但 oracle 路由器证明了模型系统超越单独的 Astra 模型的可能性。
