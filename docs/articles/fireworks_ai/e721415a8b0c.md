如果 coding agent 为每个任务都使用最佳模型，它能强多少？

最好的单一模型 GPT-6 Astra 解决 74.1% 的 DeepSWE 任务，每个任务 $6.52。为每个任务挑对模型，同样的十八个模型能达到 97.6%，每个任务 $1.88。高出 23 个百分点，成本却不到三分之一。

这个数字来自事后视角（hindsight）。我们先让全部十八个模型跑遍每个任务，再为每个任务挑出胜者。它衡量的是已经存在于这个池子里的能力，只不过这些能力分散在没有人会一起使用的模型上。

把它们组合起来是 router 的工作。它在工作开始之前就决定由哪个模型处理哪个任务，而"开始之前"才是难的部分。回头看，很容易指着某个任务说出哪个模型本来会做得更好。router 必须在看到结果之前就做选择，而选错的代价远不止它省下的那几美元。

## 模型池里已经有多少能力？

我们分析了 [DeepSWE v1.1](https://deepswe.datacurve.ai/)，这是一个 agentic coding benchmark，其中工作的单位是一个工程任务：agent 必须理解 issue、检查 repo、使用工具、修改代码、执行它，并让任务通过。

策略刻意保持简单：在任务开始时选定一个模型，并贯穿整轮运行，会话中途不切换。

然后我们按实测 pass rate 为每个任务命名胜者，成本相同时用成本打破平局。这就是 oracle router，与我们在 [Kimi K3 和 Fable 分析](https://fireworks.ai/blog/kimik3-fable)中使用的方法相同。

oracle 在它自己挑选模型的同一批 113 个任务上打分，每个模型-任务对使用四次 rollout，而在 18 个带噪声的估计上取最大值会让它的分数偏高。

最好的模型得分在 70% 左右，达到这个水平每个任务要花 $6.46 到 $13.41：

- GPT-6 Astra：74.1%，每个任务 $6.52
- Claude Opus 5：73.8%，$11.84
- GPT-5.6 Sol：72.6%，$6.46
- Claude Fable 5：69.9%，$13.41

这就是固定模型策略能做到的最好结果。现在改为按任务选择：

覆盖全部十八个模型的 oracle router 达到 **97.6%，每个任务 $1.88**。这比 GPT-6 Astra 高 23 个百分点，成本不到它的三分之一。如果只限**开放权重模型**（DeepSeek V4 Flash 和 Pro、GLM-5.3 和 GLM-5.3 Flash、Kimi K3、Qwen3.8 Max），它仍能达到 **90.3%，每个任务 $1.45**，比这里每一个闭源模型都高 16 个百分点，而花费不到 Astra 的四分之一。

这些结果让"开放 vs 闭源"变成一个没那么有意思的争论。正在浮现的竞赛，是从理论上的 oracle router 走向构建一个模型系统，让它的集体智能超过任何单一模型。原则上，一个开放模型系统已经可以远远超越闭源前沿。

**池子里存在的能力，远远多于任何单一模型所展现的。**

## 你很少需要最贵的模型

在此前的工作中，我们发现[**不同的模型在不同任务上就足够（甚至表现出色）**](https://fireworks.ai/blog/kimik3-fable)。DeepSWE 的分析让成本含义变得具体。在 97.6% 这个点上，oracle 仍然把 **113 个任务中的 94 个**交给**成本低于 $3 的模型**。

这个领域里最贵的三款模型（每个任务都在 $11.50 以上），在**仅仅三个任务**上是唯一的最佳选择。

在 **113 个任务中的 79 个**上，这些昂贵模型中至少有一个并列最高分，仅仅因为在价格上落败。一个强大的通用模型可以在很广的分布上都很出色，却不必在大多数单个任务上是唯一必需的。

固定模型策略为每个任务都支付广泛能力的成本。而一个系统可以问一个更窄的问题：

**这个**任务究竟需要什么能力？

## 少数几个模型就能走很远

要抓住这种效果，需要多少个模型？

最佳双模型组合比最佳单模型高出 **13.1 个百分点**，最佳三模型组合达到 91.2%。从三个模型扩展到全部十八个，只再增加 6.4 个百分点。有用的对象不是包含数百个几乎可互换模型的目录，而是一个覆盖互补的 portfolio。

**价值在于能力覆盖，而不是模型数量。**

[LLMRouterBench](https://aclanthology.org/2026.findings-acl.1881/) 在 33 个模型和超过 400,000 个实例上评估路由。它发现少数几个模型就覆盖了全集能做的大部分事情，而如果没有精心筛选，更大的池子带来的增益很小。

## 难的部分是预测该用哪个模型

oracle 招人喜欢是因为它永远不会错。而生产环境的 router 会出错。我们严格地衡量它：使用 pass@1，即单次尝试通过的概率，而不是"这个模型在四次尝试中是否有任何一次成功"的规则。后一种规则会让上限看起来更惊艳，但含义要小得多。

这个差距是一个产品问题，文献对此说得很直白。LLMRouterBench 发现，包括商业方案在内的几种近期路由方法都无法稳定胜过简单基线，并把很大一部分原因归到 model recall 上：即使池子里存在具备正确能力的模型，router 也必须能识别出何时该去用它。

所以，坚持用一个你熟悉的模型并不保守，而是理性的：一个稳定的错误分布，胜过会不可预测地选错专家的 router。对路由系统的要求是，让模型专业化变得足够可预测，使得更换模型**能改进系统，而不会让它的行为变得更不可信**。

## FireRouter 是如何做到的

路由通常被当作成本优化来介绍：把简单的工作交给更省钱的模型，把贵的留给困难的工作，然后留下差价。在 [Fireworks](https://fireworks.ai/nexus)，我们的看法更宽。

**如果不同模型确实是互补的，那么在它们之间做选择会让你沿能力曲线向上移动，而不只是沿成本曲线向左移动。**

这正是 FireRouter 的用途。它在任务级别跨开放与闭源模型进行路由，并且具备缓存感知能力，因此切换模型不会悄悄丢掉你已经付过费的上下文。

在我们自己四周的生产 coding 流量中，经 FireRouter 路由的会话成本为 $7.42，而单用 Opus 5 为 $15.81，在 2,334 个会话上降低了 53%。

AI 工作的有用单位已经大于单次模型调用。一个 coding agent 是 harness 里的模型，harness 提供上下文、工具、执行、测试、状态和反馈。

一旦多个模型拥有互补的优势，选择策略就成为[系统的一个组件](https://www.faros.ai/blog/open-models-vs-frontier-models)，与上下文、工具和测试并列。挑选并组合这些组件就是工作本身。这就是 AI engineering。

我们的实验只衡量了这个系统最简单的版本：在任务开始时选一个模型，然后就不动它。选择策略是我们真正可以构建的那部分。

我们在生产环境中提供每一个前沿开放模型，对每个模型优势的真正理解正来自这里。你无法从 benchmark 平均值里学到某个模型独特擅长什么。你要在真实工作上、在大规模下把它们全部跑一遍才能学到。FireRouter 的模型选择就来自这里，而我们打算跨过的正是这道门槛。后续文章中我们会深入讲[我们自己的 router](https://docs.fireworks.ai/ecosystem/firerouter/overview)，以及如何在[你自己的专业化智能](https://fireworks.ai/training)上做爬山式优化。

**在 [FireRouter](https://app.fireworks.ai/fire-router) 上定义你的前沿。**

**关于成本。** 本分析中的所有成本数据都来自 DeepSWE 排行榜公布的按模型数值。公开 trials 文件里的原始 cost_usd 与榜单显示的数值并不一致，对 DeepSeek 家族来说相差数倍，因此我们对每个模型的单任务成本做了缩放，使其均值与公布数值一致。准确率来自每个任务-模型对的四次原始 rollout，成本则来自榜单。
