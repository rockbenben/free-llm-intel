[MiniMax M3.1 Flash](https://fireworks.ai/models/fireworks/minimax-m3p1-flash) 在哪些场景下能以可接受的成本和速度提供有用的性能？[Specialized Intelligence Index](https://fireworks.ai/specialized-intelligence-index/)（SII）通过由从业者构建的领域特定基准，帮助团队回答这个问题。我们利用这些评估，把 M3.1 Flash 与 Claude Sonnet 5.5、GPT-6 Luna、Gemini 3.8 Flash 等闭源模型做比较，并探讨把它与另一个模型搭配使用能否改善结果。

编码场景的收益最明显。M3.1 Flash 完成的 DeepSWE 任务比 Gemini 更多，模型成本却低得多；而在与 Luna 对比时，额外完成的任务需要付出更高成本。网络研究方面的结果则更复杂：相比 Sonnet，成本更低，但等待时间更长，或者得分更低，具体取决于所用的评估。

编码方面的发现也不止于逐个模型对比。在一项模拟中，先用 M3.1 Flash 尝试，再把失败的尝试交给 Claude Opus 5.5，相比只用 Opus，以更低的模型成本完成了更多遗留代码任务。这说明评估一个模型时，也要考虑它与其他模型配合时能扮演的角色。

## 我们评估了什么

本研究用 DeepSWE v1.1 和 Factory 的 Legacy-Bench 覆盖软件工程，用 Nimble 的 Web Context、Exa 的 ATLAS 和 Parallel 的 Search Capability Leaderboard 覆盖网络研究。Sierra 的 τ³-Banking、Doximity 的 Bedside Bench 和 Column Tax 的 TaxCalcBench 分别提供银行支持、临床问题和税务准备方面的对比。我们在数据可得时考察质量、模型成本和执行时间，然后利用单次运行结果模拟重试与模型组合。Rogo 的 Big Finance Benchmark（测试金融研究）也用于分析工作负载分配。

## 编码：M3.1 Flash 完成的任务多于 Gemini 3.8 Flash 和 GPT-6 Luna

DeepSWE v1.1 测试 agent 能否解决跨 91 个仓库的 113 个任务中的软件问题。agent 会浏览代码库、修改文件并提交 patch。随后用对 agent 保密的测试检查该 patch 是否解决了问题。

![在 DeepSWE v1.1 上，M3.1 Flash 以每任务 $0.35 的模型成本完成 73.2% 的任务，而 Gemini 3.8 Flash 为每任务 $4.24、完成 61.7%，GPT-6 Luna 为每任务 $0.19、完成 66.4%](https://fireworks.ai/_next/image?url=https%3A%2F%2Fcdn.sanity.io%2Fimages%2Fpv37i0yn%2Fhorizon%2Fb7f050129d1864e4bcf2699a702bf207854ffc83-1412x1248.png%3Fauto%3Dformat&w=3840&q=75)

对使用 Gemini 3.8 Flash 的团队来说，在这次评估中，M3.1 Flash 以约低 92% 的模型成本带来更高的完成率。而与 GPT-6 Luna 相比，它的成本约高 84%，每轮 113 个任务大约多完成 8 个任务，模型支出多 $18。

在这套设置下，M3.1 Flash 平均每个任务约 20 分钟，与 Gemini 和 Luna 大致相当。它在此处的优势是完成率，成本收益则取决于它替代的是哪个模型。

### 重试 M3.1 Flash 把编码覆盖率从 73% 提升到 90%

有些任务 M3.1 Flash 一次尝试没做出来，下一次却成功了。在三次记录的运行中，它至少一次解决了 113 个任务中的 102 个，而平均每次运行约解决 83 个。

我们模拟了最多允许三次尝试、首次成功即停止的策略。平均每个提交任务的模型支出从约 $0.35 升到 $0.50，换算为每个已解决任务约 $0.55。每次重试都从零开始，不带上次失败的任何反馈。

![允许最多三次尝试后，M3.1 Flash 的 DeepSWE 覆盖率从约 83/113 个任务（73%）提升到 102/113 个（90%），每个提交任务的模型成本从 $0.35 升到 $0.50](https://fireworks.ai/_next/image?url=https%3A%2F%2Fcdn.sanity.io%2Fimages%2Fpv37i0yn%2Fhorizon%2F7a69cfa4248ae446aba39d37e9a45c6531e5146b-1412x1184.png%3Fauto%3Dformat&w=3840&q=75)

只要应用能可靠地检查每个 patch 是否修复了问题，重试就能帮助 M3.1 Flash 解决更多编码任务。该模拟使用隐藏的基准测试来决定何时停止；在生产工作流中，验证成本和时间同样重要。

## 网络研究：节省多少取决于你需要怎样的质量与速度

在三个网络研究评估中，M3.1 Flash 呈现出不同的取舍。在 Nimble 的 Web Context 基准上，它以更低的模型成本取得比 Claude Sonnet 5.5 更高的分数，但耗时明显更长。在 Exa 的 ATLAS 和 Parallel 的 Search Capability Leaderboard 上，成本节省伴随的是更低的分数。

### Web Context 上更高的分数伴随更长的等待

Nimble 的 Web Context 测试 agent 收集公司与创作者信息、找出符合指定条件的实体，以及撰写研究报告的能力。它把报告中的事实与来源页面对照核实，并对准确性和完整性分别打分。

M3.1 Flash 得分 74.7，Claude Sonnet 5.5 为 67.2，GPT-6 Luna 为 67.9。在该基准的三个垂直领域——go-to-market、金融和社交媒体——它的得分也都高于这两者。

在 Web Context 上，M3.1 Flash 以低 33% 的模型成本取得高于 Sonnet 的分数，但耗时接近后者的八倍。这使它更适合后台研究，而不是用户正等着结果的交互场景。与 Luna 相比，更高的分数同时伴随着更高的支出和更长的执行时间。

对使用更昂贵模型的团队来说，M3.1 Flash 同样值得评估：Claude Opus 5.5 得分为 71.8，GPT-6 Astra 为 72.6，模型成本约为它的七倍和十八倍。这些小幅分差并不构成可靠的质量优势。

### 更低的搜索成本可能伴随更低的分数

Exa 的 ATLAS 测试 agent 能否构建出与请求相符的完整实体表格。M3.1 Flash 得分为 22.0，而 Claude Sonnet 5.5 为 46.8。Web Context 也包含实体查找任务，因此这些汇总结果无法单独解释两个模型相对表现为何变化。

Parallel 的 Search Capability Leaderboard 评估 300 个问题，涵盖多步研究、专业知识和商业研究。模型使用搜索与页面抽取工具来回答这些问题。

M3.1 Flash 得分为 68.8，Sonnet 为 74.1；包含预估搜索费用后，每道题的成本分别为 $0.04 和 $0.80。也就是成本约低 95%，分数低 5.3 分。若研究成本是你最在意的因素，可以评估 M3.1 Flash，同时确认它满足你的工作流在答案质量、完整性和响应时间方面的要求。

## 银行、临床与税务评估更青睐被对比的替代模型

M3.1 Flash 的编码优势并不能延伸到所有工作负载。在 Sierra 的 τ³-Banking 上——该基准测试通过银行政策和账户管理工具处理客户请求——它解决了 34.0% 的尝试，而 Gemini 3.8 Flash 为 51.4%，GPT-6 Luna 为 37.7%。

我们考察了 38 个至少四分之三的受评模型都能解决的对话。在每个对话四次尝试中，M3.1 Flash 失败了 57 次。其中 23 次失败里，它完成了所有必需步骤，但同时也做了一次未被要求的账户变更。在一个例子中，它正确地拒绝了提高信用额度的请求，随后又发放了一笔账单抵扣来缓和这次拒绝。对于会改动账户的工作流，只检查请求是否被完成，就会漏掉这些额外操作。

临床与税务结果同样更青睐被对比的替代模型。Doximity 的 Bedside Bench 评估对医生所写临床问题的回答。M3.1 Flash 得分为 75.3，Gemini 为 86.5，Luna 为 87.2。Column Tax 的 TaxCalcBench 测试根据纳税人文档准备完整的联邦和州税务申报表。M3.1 Flash 在正确报告工资和已预扣税款方面接近 Luna，但在减少应税收入的扣除项和免税额方面准确度较低。因此，这些基础数字上的准确性并不等于一份正确的申报表。

## 将 M3.1 Flash 与其他模型组合可以改善质量与成本的权衡

### 将 M3.1 Flash 与 Gemini 3.8 Flash 搭配，以更低成本完成更多任务

前面的对比显示，M3.1 Flash 在编码上较强，在银行支持上较弱。能否让 M3.1 Flash 的编码优势改善整体结果，同时由另一个模型处理它更擅长的工作负载？

我们模拟了在四类工作负载上按模型分工：修复软件问题、维护较旧的代码库、处理银行支持请求，以及回答金融研究问题。

对每一种搭配，我们都把每类工作负载分配给记录完成率更高的模型，完成率相同时用成本来决胜。每个任务只由一个模型尝试一次，不重试，也不回退给另一个模型。

与 Gemini 3.8 Flash 搭配时，M3.1 Flash 负责代码仓库中的编码任务和遗留代码维护，Gemini 负责银行支持。在这 307 个基准任务上，该搭配平均完成 188 个，而单用 Gemini 为 172 个，同时模型支出从 $661 降到 $108。

这 84% 的节省大部分来自 DeepSWE，在那里 M3.1 Flash 每个任务成本 $0.35，而 Gemini 为 $4.24。节省比例取决于工作负载构成：银行任务更多、编码任务更少的应用，看到的节省比例会更小。

其他搭配说明了对比模型为何重要。把 M3.1 Flash 加入 GPT-6 Luna 后，以更高成本换来了更多完成量。与 Claude Opus 5.5 或 GPT-6.1 Sol 搭配降低了支出，但在验证检查中，完成的任务并不总是多于这些模型单独使用。

我们还检查了这些模型选择在未被用于做选择的那些任务上是否依然成立。在 500 次随机切分中，我们用一半任务为每类工作负载选定模型，再在另一半任务上评估这些选择。与单独使用 Gemini 相比，与 Gemini 的搭配仍然取得了更高的平均完成量和更低的支出。

### 让 M3.1 Flash 先尝试、再交给 Opus 5.5，能以更低成本提升完成量

按工作负载分配模型是一种选择。另一种是让一个模型先尝试任务，再把失败任务交给第二个模型。我们用 M3.1 Flash 先试、Claude Opus 5.5 处理失败尝试的方式测试了这种策略。

在测试旧代码库维护的 Factory Legacy-Bench 上，这一模拟序列解决了 97 个共有任务中的约 71%，而单用 Opus 为 64%。包含失败尝试在内，平均每任务模型支出从 $0.51 降到 $0.42，约低 18%。

M3.1 Flash 解决了 Opus 漏掉的一些任务，而 Opus 也挽回了 M3.1 Flash 的一些失败。由 M3.1 Flash 解决的任务还省去了那次 Opus 尝试的成本。正是这种组合，解释了该序列为何能同时改善完成量和支出。

![先用 M3.1 Flash、再把失败任务升级给 Claude Opus 5.5，可解决 97 个 Legacy-Bench 任务中的约 71%，每任务成本 $0.42；单用 Opus 则为 64%，每任务 $0.51](https://fireworks.ai/_next/image?url=https%3A%2F%2Fcdn.sanity.io%2Fimages%2Fpv37i0yn%2Fhorizon%2Fe852242051f4343658b00ad83549cc32d6d8bc02-1412x1950.png%3Fauto%3Dformat&w=3840&q=75)

该模拟使用隐藏的基准测试来识别失败。应用这一方法需要可靠的检查；所报告的成本不含验证与编排环节，端到端执行时间也未测量。

## 一个模型不必包揽所有任务，也能创造价值

M3.1 Flash 的编码结果说明，一个模型可以在已有模型旁边赢得一个受限的角色。这使采用问题从「是否要彻底替换某个模型」变成「把一部分工作分配给它，或让它先尝试，能否改善整体结果」。答案取决于已有的模型、工作负载构成，以及在升级模式下可靠识别失败的能力。

在 [**Specialized Intelligence Index**](https://fireworks.ai/specialized-intelligence-index/) 中查看这些基准对比，或了解 [**Fireworks Nexus**](https://fireworks.ai/product/nexus)，用它对开源与闭源模型做集成。

## 方法与局限

### 数据来源、评分与成本

结果使用本研究 2026 年 11 月 7 日和 11 月 11 日的快照。分数遵循各基准自身的评分规则。模型成本使用记录的使用量与评估定价，包括 Gemini 3.8 Flash 的入门定价。Parallel 和 Exa 包含搜索费用；评分器成本不计入。每任务成本包含未成功的尝试。

### DeepSWE 与重试

M3.1 Flash 在 91 个仓库的 113 个任务上完成了三次运行；全部 339 次尝试都计入。10 月 29 日的运行使用专用 Fireworks 部署，成本按 serverless 费率计算：未缓存输入 token 每百万 $0.15，缓存输入 token 每百万 $0.015，输出 token 每百万 $0.60。

重试估算对记录尝试的所有可能顺序求平均，在第一次经基准验证成功或达到尝试上限时停止。重复尝试不被假定为彼此独立。

### 工作负载分配与升级

期望完成量由各任务在记录尝试上取平均的通过率求和得出。全集路由结果在同一批数据上选择并评估工作负载分配。另一项检查使用 500 次切分，在一半任务上选择分配方案，在另一半任务上评估。

Legacy-Bench 的路由与升级使用所有参与对比的运行都能构建的 97 个任务。M3.1 Flash 后续环境中额外可用的三个 Java 7 任务被排除在外。

### 任务级分析与覆盖范围

银行子集包含 38 个由至少四分之三受评模型解决的对话，每个对话有四次 M3.1 Flash 尝试。「57 次中的 23 次」这一发现描述的是该子集内的失败情况。

税务对比对两个模型都使用不搜索的运行设置。M3.1 Flash 接收从 PDF 中抽取的 OCR 文本。工资/预扣与扣除/免税这两类，是分析师对申报表行项目的自定义分组。

各模型的运行覆盖范围不同。M3.1 Flash 在某些基准上记录的运行次数较少，包括 Legacy-Bench 和 Bedside Bench，这使得小幅分差难以支撑结论。只有一项基准与 MiniMax M3 共有，因此本研究并不能得出通用的升级建议。
