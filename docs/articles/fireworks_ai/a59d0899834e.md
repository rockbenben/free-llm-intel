[**Specialized Intelligence Index（SII）**](https://fireworks.ai/specialized-intelligence-index/) 是你探索开源、闭源和专用模型在特定领域基准上表现的一站式目的地。每个基准都反映由从业者设计的真实世界任务。今天，我们上线了七个初始领域的基准：医疗健康、法律、网络安全、金融、客户支持、生产力和软件。更多领域即将推出。

## 衡量真实工作

公开基准提供了追踪进展和比较模型的共同参照点，但它们不是衡量真实工作的好尺度。这些 eval 使用有界任务、固定数据集和标准化评分。真实工作要乱得多：它涉及不完整的信息、变化的工作范围、业务约束、复杂的判断、多步工作流和协作。

这个区别对想要判断一个模型是否好到能替代人工任务的组织很重要。一个可接受的结果，必须满足那些对真实结果负责的真实的人的标准。今年早些时候，[METR](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/) 把这个差异量化了出来。在他们的工作中，4 位维护者审阅了来自 3 个 SWE-bench Verified 仓库的 296 个 AI 生成的 pull request（PR）。维护者的接受率平均比自动化基准分数低 24.2 个百分点。用他们自己的话说：“许多通过 SWE-bench 的 PR 根本不会被合并进 main。”

要把基准用到真实工作上，我们需要明确一个分数衡量的是什么、这个评估有多贴近预期的工作、以及更好的表现是否带来有用的运营结果。

**这个测试衡量的是它声称的那项能力吗？**

这是构念效度（construct validity）的问题：这个评估是否支持附加在其分数上的那种解释。[Bean 及同事](https://arxiv.org/abs/2511.04703) 考察了 445 个 LLM 基准，找出了研究者想测量的现象、他们的任务和他们的评分方法之间反复出现的缺口。举例来说，一个本意是测推理的任务，可能同时也依赖背下来的知识。这就很难判断高分反映的到底是推理、是记忆，还是两者都有。

**这个测试代表了我们真正关心的工作吗？**

代表性关乎任务集的覆盖面和构成。[Wang 及同事](https://arxiv.org/abs/2603.01203) 研究了 43 个 agent 基准，发现它们集中在计算机和数学类工作上——在他们的分析中，这一类只占美国就业的 7.6%。管理和法律类工作被低估，各职业普遍需要的人际能力同样被低估。真实工作基准必须代表它针对的那个领域。

于是，在真实工作上评估模型遵循一条合乎逻辑的递进，每一步都需要更多证据：

**基准分数 → 能力主张 → 业务结果**

分数记录的是在特定协议下、在既定任务集上的表现。能力主张需要证据，证明系统能可靠地执行相关类别的工作，包括没见过的情形。业务结果则需要证据，证明这种表现能在可接受的质量和成本下带来期望的结果。

depthfirst 的 dfbench 评估开放式防御性安全工作。访问 SII 探索覆盖各行业的基准。

### 由从业者开发，为从业者服务

真实工作 eval 由从业者定义，他们帮着勾勒工作内容、约束条件和验收条件。设计真实工作 eval 通常包括这些步骤：

**1. 定义这项工作及其价值。**明确任务、目标用户和人工监督的程度。设定质量阈值以及时间和成本上限。为当前工作流建立基线，然后在试点或受控部署中检验分数提升是否预示着更好的结果。

**2. 反映真实工作。**从目标场景中抽取常规任务和困难案例。纳入贴近现实的信息、工具、权限和政策约束。为后果严重的失败加入压力测试，但当其发生频率与常规使用不同时，要单独报告。一个刻意做难的测试集，不应该被当成对日常表现的估计。

**3. 与从业者共同设定验收标准。**把专业标准转化成可观察的结果和明确的评分细则。把轻微缺陷与导致输出不可接受的失败区分开。既要评估最终结果，也要评估任何重要的动作，比如在改动受保护资源之前先申请批准。

**4. 验证评分器。**把自动判断与专家评审做比较。检查误接受、误拒绝以及评审者之间的分歧。在那些分歧暴露出歧义的地方，改进评分细则或评分方法。随着系统变化，持续抽样输出交给专家评审。

**5. 检验泛化与可靠性。**把开发用案例和留出案例分开，检查是否存在数据污染，并随着工作变化刷新评估。重复运行并报告不确定性、按任务类别的表现以及关键失败率。记录模型、提示词、agent harness、工具、资源上限和评分器版本，让比较始终保持可解释。

## SII 亮点一览

### 医疗健康

**Doximity 的 BedsideBench v0.2.0** 在 500 个经医生验证的临床案例上评估前沿 AI 模型，覆盖医学推理、计算、用药安全、指南依从性、幻觉、诊断安全性和治疗方案规划。

**Mercor 的 APEX-1: General Practitioner (MD) Benchmark** 衡量前沿 AI 模型在真实的初级保健医生任务上表现如何，涵盖诊断、检查评估和安全升级。

**HealthBench Professional** 评估前沿 AI 模型能否对临床医生编写的难题给出准确、有用且安全的回答。

### 法律

**Harvey 的 Legal Agent Benchmark（LAB）** 衡量前沿 AI 模型在真实法律工作上的表现，覆盖 24 个执业领域，要求模型浏览文件并产出工作成果，再按专家评分细则在事实准确性、法律分析和格式上打分。

**Harvey 的 LAB Contracts** 测试 AI agent 能否在 500 个起草、审阅和谈判任务中把合同谈判往前推进。要成功完成每个任务，agent 必须在业务和交易的约束下处理所有变更和未决问题，推动合同前进。

**Mercor 的 APEX Agents: Corporate Law** 评估多步公司法任务，涵盖链式工具使用、检索和文件起草。执业公司法律师按律所会接受的成果标准给输出打分。

**RedlineBench** 评估 AI agent 以内聘律师身份、对贴近现实的合同进行多轮批注修订的表现。

### 金融

**Rogo 的 Big Finance Bench** 用跨估值模型、财务报表分析、预测以及其他关键金融工作流的问题来评估 AI agent，由从业者编写的评分细则来评判 agent 如何查找信息、如何应用财务定义与引用、以及如何进行计算。

### 网络安全

**depthfirst dfbench v1** 针对防御性安全，覆盖漏洞检测、验证和差分分析。depthfirst 自家的 dfs-large1 模型在 Fireworks 上基于 GLM 5.2 用 RL 做了后训练，在其评估中达到了新的 Pareto 前沿。该模型的提升归因于带工作量惩罚的 RL reward shaping、软性的发现预算惩罚，以及在漏洞检测与验证上的联合训练。这一结果由 [depthfirst](https://depthfirst.com/research/dfbench) 报告。

**Novee 的 PWNBench-v0.1** 在真实 Web 应用的 agentic 灰盒渗透测试上评估前沿 AI 模型，覆盖完整的发现—利用—报告流程。它在统一的精简 harness 下衡量 recall、precision、F0.5 和 API 成本。

### 客户支持

**Decagon 的 DuetBench-Diagnosis** 回放真实的 Duet 客户支持调查，并在结果、调查过程、工具使用和沟通这几个维度上对模型回答做头对头评分。

**Sierra 的 τ-Banking** 在银行任务上评估客户支持 agent，这些任务需要在横跨 21 个产品类别的 698 份文档知识库中检索、应用政策，并在维持一段持续客户对话的同时执行多步工具调用。

**Sierra 的 τ-Voice** 评估语音 agent 能否在零售、航空和电信场景中完成客户服务任务，同时应对打断、背景噪声和不同口音。

### 生产力

**Genspark Slides Benchmark** 在去标识化的真实用户任务上评估 AI 生成的演示文稿，从任务完成度、内容质量、视觉设计和过程质量给成品 deck 打分，并对版式缺陷、编造内容和被忽略的指令扣分。

### 软件

**Traversal 的 ORCA-Bench** 是一个站点可靠性工程基准，它从模糊的报告、遥测数据和源代码出发，评估生产环境式的根因分析（RCA）。Hard RCA 准确率是头条分数；Medium RCA 和事故幻觉则作为单独的 native 指标保留。

**Proximal 的 FrontierSWE V2** 是一个代码生成基准，评估 34 个处在人类专家能力边缘的软件工程任务：用 OpenGL 写一个飞行模拟渲染器、把 Git 移植到 Zig、仅靠视觉驱动一个赛车 bot。每个模型在每个任务上有 5 次尝试，每次最长 20 小时。每次尝试都获得分级奖励而不是通过或失败，所以一次走完了大半路程的运行仍然算数。

**Mercor 的 APEX-SWE** 在 200 个软件工程任务上评估 AI 模型，这些任务要求集成云服务和业务应用，或者利用日志、仪表盘和不完整的上下文来调试生产故障。

**Datacurve 的 DeepSWE v1.1** 在 91 个仓库、五种语言的 113 个原创长程工程任务上评估 coding agent，在隔离环境中检验它们提交的代码行为是否正确。

**Macroscope 的 MacroscopeBench** 评估模型在代码审阅上的表现，衡量审阅者发现真实已知 bug 的能力，同时不发出错误的评论。它跑在来自开源仓库的 195 个 commit 上，其中 144 个引入了维护者后来不得不修的真实 bug，51 个是干净的对照。

训练开源模型能带来更好的结果，包括在前沿级质量下更低的单任务成本。以下是 Genspark 在自家专业智能上的结果。

## 方法论概览

**不做人为汇总。**SII 不对排名取平均，不把质量与成本或时长加权，也不生成跨领域的综合分。结果停留在基准和领域层面，配以覆盖矩阵以及分数对成本、分数对时长的视图，让用户自己套用自己愿意接受的取舍。

**来源。**基准结果可能由合作方、Fireworks 或两者共同在多个模型上报告；具体实现方式会相应说明或给出链接。发布遵循基准所有者的政策；分数会公开，而 eval 集、提示词、评分逻辑、轨迹和合作方的原始输出保持私密，除非所有者另有选择。

**可复现性。**每个基准都会标注谁能复现它：任何人、Fireworks 与基准所有者，或仅限合作方。可复现性来自带版本的方法论和钉死的执行快照，其中记录了 harness、采样参数、超时、快照 ID、执行器以及任何未决问题。

**模型选择。**模型是否入选，取决于一个组织能否把它真正部署到生产规模，价格是重要考量。新的前沿模型会自动进入资格审核流程，只有通过这道门槛后才会出现在 Index 上。

关于 harness、推理、沙箱、运行协议、置信度、可靠性以及成本和时长指标的更多细节，[参见 Fireworks 方法论](https://fireworks.ai/specialized-intelligence-index/#methodology)。

## 贡献一个基准或一个模型

如果你为某个特定领域跑生产级 eval，它可能就属于 Index。Fireworks Lab 帮助组织设计自己的基准和专用模型。

要向 Index 提交，合作方需以 Harbor 兼容的格式提供任务和数据。Fireworks 会审阅任务的多样性和校准情况，免费在多模型名单上请求并运行 eval，并在合作方批准后发布分数。
