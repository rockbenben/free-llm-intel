这个模型是为智能体而构建的。它为「always-on」常驻智能体而设计，而不仅仅是简单的聊天交互。它能跨多轮管理大量顺序工具调用。它具备从失败与重试中恢复的能力，而不会在某次工具调用失败或返回意外结果时停摆。

## **Muse Glimmer 架构内部**

Muse Glimmer 是一个 30B 稠密模型，由 52 个 transformer 层组成，采用 grouped-query attention（32 个 query 头、2 个 KV 头）和 SwiGLU 前馈层。一个约 1.8B 的感知编码器让它在文本之外原生理解图像，并支持 128K+ token 上下文窗口。

Meta 构建它时以装进 24 GB 为目标。同样的设计——小 KV 足迹、滑动窗口注意力——正是让它在高并发下服务得起的原因。而且权重以 Apache 2.0 发布，路径是对称的：在工作站上用量化版本做原型，需要服务数千会话时把同一个模型部署到 Fireworks。

对智能体最要紧的细节是注意力模式：大多数层在 2,048 个 token 上做滑动窗口注意力，每第四层放一个全局完整注意力层。配上仅两个 KV 头，这让 KV 缓存保持在很小的规模——这正是让长上下文智能体在高并发下经济可服务的原因。这一架构效率让智能体管理 10 万 token 的累积工具输出，比同规模稠密模型更省钱，而且节省随并发会话数放大。

该模型还支持 DFlash 投机解码（speculative decoding）以降低生成延迟。

## **这个模型擅长什么**

从端到端的客服工单解决，到长时间的自主研究，这个模型为深度多步推理、大规模并行和严苛智能体工作流下的可靠性而生。它理想适配以下负载：

- •**面向客户的支持智能体：**端到端解决工单的智能体会拉取账户状态、查库存、起草退款待审批、跨几十次工具调用与用户确认状态。Meta 建议对不可逆操作要求人工确认；我们附和：把模型的权限限定在读取、规划与暂存，写操作设卡把关。失败恢复在这里至关重要，因为工作流中途超时不该把客户晾在那里。
- •**长时研究与监控智能体：**向多个信息源铺开、把发现保持在上下文里、几小时后带着综合结论回来的智能体。Muse Glimmer 在 DeepSearch QA（74.6）和 MCP Atlas（75.5）上领先其体量级别——这两个基准最贴近这种工作形态。原生图像输入意味着图表和文档与文本走同一个循环——Muse Glimmer 在 CharXiv Reasoning（78.8）上领跑同类。注意 2026 年 1 月 4 日的知识截止日期，任何时效性内容都必须经由工具获取。
- •**仓库规模的编码智能体：**读仓库、规划改动、跑测试、在失败上迭代的智能体。Muse Glimmer 在 SWE-Bench Pro（51.2）和 SciCode（43.6）上领先同类。

## **今天在 Fireworks 上开始使用**

Muse Glimmer 已在 Fireworks 上线，支持 serverless 与按需部署。我们比别人晚一天发布，是故意的。我们多花了一天来上线，因为我们想把它做对：这意味着修正模型出厂的生成配置，并把 reasoning-effort 控制一路打通到模型内部。好模型配得上好的执行。质量是我们的最高优先级，我们想确保你从第一天起就得到期望的确切性能、控制与可靠性。

- •无需采购 GPU。从一次 API 调用开始；无需容量规划即可扩展到生产。
- •为突发智能体流量而造。智能体负载会不可预测地尖峰。Fireworks 自动伸缩以匹配，你不必按峰值配置。

**跑好的建议：**Meta 建议使用以下设置。

temperature = 1.0, top_p = 0.95, top_k = 64

Reasoning effort 在系统提示词中以 `Reasoning strength: <value>` 设置，可选 low、medium、high、xhigh——智能体与编码工作用 high 或 xhigh。上表中所有基准数字均为 high 档。
