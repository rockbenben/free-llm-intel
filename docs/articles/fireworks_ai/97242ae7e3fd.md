这个模型在构建时就考虑了 agent。它面向"永远在线"的 agent 设计，而不只是简单的聊天交互。它能够在多轮对话中管理大量连续的 tool call。当 tool call 失败或返回意外结果时，它具备从失败中恢复并重试的能力，而不是直接停住。

## Muse Glimmer 的架构内幕

Muse Glimmer 是一个 30B 稠密模型，由 52 个 transformer 层、带 32 个 query head 和 2 个 KV head 的 grouped-query attention 以及 SwiGLU 前馈层组成。一个约 1.8B 的感知编码器让它具备原生的图像理解能力，与文本并列，并支持 128K+ token 的上下文窗口。

Meta 把它做到可以装进 24 GB。同样的设计——小的 KV 占用、sliding-window attention——正是它能在并发下低成本 serving 的原因。而且因为权重以 Apache 2.0 发布，路径是对称的：在工作站的量化版本上做原型，需要服务数千个会话时，把同一个模型部署到 Fireworks 上。

对 agent 来说最重要的细节是注意力模式：大多数层上是覆盖 2,048 个 token 的 sliding-window attention，每第四层有一个完整的全局注意力层。再配合仅仅两个 KV head，KV cache 就能保持很小——这正是长上下文 agent 能在高并发下经济地 serving 的原因。这个模型的架构效率让 agent 能比同类稠密模型更经济地管理累积的 100K token 工具输出，而且节省会随并发会话一起放大。

该模型还支持 DFlash 推测解码，以获得更低延迟的生成。

## 这个模型擅长什么

从端到端的支持工单处理到长时自主研究，这个模型专为深度多步推理、大规模并行，以及在苛刻 agentic 工作流中的可靠性而构建。它非常适合以下工作负载：

- **面向客户的支持 agent：** 端到端解决工单的 agent，会在数十次 tool call 中拉取账户状态、检查库存、起草退款以供审批，并与用户确认状态。Meta 建议对不可逆操作进行人工确认；我们也认同：把模型的范围限定为读取、规划和暂存，并对写入加上闸门。失败恢复在这里至关重要，因为工作流中途超时不应该把客户晾在那里。
- **长时间运行的研究与监控 agent：** 在多个来源之间分发、把发现保存在上下文中，并在数小时后返回一份综述的 agent。Muse Glimmer 在同尺寸级别中领先 DeepSearch QA（74.6）和 MCP Atlas（75.5），这两个 benchmark 最贴近这类工作形态。原生图像输入意味着图表和文档与文本走同一个循环——Muse Glimmer 在 CharXiv Reasoning 上领先同级（78.8）。注意知识截止时间是 2026 年 1 月 4 日，任何对时间敏感的信息都需要通过工具获取。
- **repo 级 coding agent：** 阅读 repo、规划改动、运行测试并针对失败迭代的 agent。Muse Glimmer 在同级中领先 SWE-Bench Pro（51.2）和 SciCode（43.6）。

## 今天就在 Fireworks 上开始

Muse Glimmer 已在 Fireworks 上线，serverless 和按需部署都可用。我们比其他人晚一天上线，这是有意的。我们多花了一天来发布，因为想把这件事做对。这意味着修正模型自带的生成配置，并把 reasoning-effort 控制一路打通到模型本身。好的模型值得好的执行。质量是我们的最高优先级，我们希望确保你从第一天起就得到你所期待的性能、控制和可靠性。

- 无需采购 GPU。从一次 API 调用开始；扩展到生产也无需容量规划。
- 为突发的 agent 流量而建。agent 工作负载会不可预测地尖峰。Fireworks 会自动扩缩以匹配，所以你不用为峰值预留。

**用好它：** Meta 建议使用以下设置。

temperature = 1.0, top_p = 0.95, top_k = 64

reasoning effort 在 system prompt 中以 Reasoning strength: <value> 设置，可选 low、medium、high 和 xhigh——agentic 与 coding 工作请用 high 或 xhigh。上表中所有 benchmark 数字都是在 high 下取得的。
