## TL;DR

- 用专业智能训练属于你自己的模型，意味着掌握住让公司与众不同的东西
- 通向专业智能的路可以从租用闭源前沿模型开始，但最终不可避免地会走向训练开源模型
- 至于公司为什么转向训练自己的模型，已经浮现出几种常见的模式

> 这是“专业智能”系列的第一篇，面向正在浅尝训练、或好奇到底要付出什么的工程师。

## 通向专业智能之路

团队决定训练自己的模型，原因无非几个：

- 担心某家闭源前沿实验室会闯进自己的领域
- 通用模型在自己所处的垂直领域达不到的质量门槛
- 为了实际需要的智能水平而支付的 API 账单太高

这些理由底下是同一个本能：把定义自己业务的那种专业智能握在自己手里。本文讲的就是通向那里的路。

你先租用能拿到的最强（通常也是最贵）的闭源 LLM，围绕这个模型搭建专门的 harness、系统和组件，以提升它在你的任务上的表现。等这些组件做到头，你再迁移到更便宜但仍然有效的开源模型，在最大化效用的同时压低成本。最后，如果这个问题确实是你独有的，你就决定通过训练一个定制模型，彻底拥有这份智能。

## 阶段 1：租用闭源前沿模型

几乎所有人都是从 API 背后的闭源前沿模型开始的。这很合理**：**那些厂商不惜重金在一切能触达的地方推销自己的模型**，**想把你拉上船。这些模型很强大，而且因为训练和服务的成本由别人承担，你按用量通过 token 费用付费。

缺点很深，但你可能碰上的主要有三个：

模型过于通用，必须在上面再加提示词，才能在某个专门方向上做点事。它好用是好用，但这个模型是别人为所有人塑造出来的。

闭源 API 在每一种意义上都是租用。你不控制模型权重、价格、延迟和下线时间表，而且在多数情况下，你并不控制自己的数据。

你付的 token 溢价和你发给团队的企业订阅，为这一切买单：你从没碰过的基础设施、营销活动、为这些活动出谋划策的顾问，以及让实验室维持在前沿的研发。你在补贴一台你不拥有、也无法操控的机器。

在厂商为自家模型投入了那么多功夫之后，闭源前沿 LLM 确实很强大，但它们从货架上拿下来时也过于通用了，必须不断喂相关的上下文，才能在日常工作中派上用场。于是 AI 工程登场了。

## 阶段 2：AI 工程——提示词、上下文与 harness，天哪！

过去几年 AI 工程的演进是一条清晰的升级路线，每一层都是为了让那个我们从货架上租来的模型多榨出一点东西。先是 **prompt engineering**：few-shot 示例和 chain-of-thought 表明，改变提问的方式能引出更强、更一致的行为。随着我们往上下文窗口里塞进越来越多东西（通常是为了 retrieval-augmented generation，RAG），让模型跟上不断变化的信息，这就变成了 **context engineering**。等提示词和上下文都安排妥当，agent 又来了，用一轮轮工具调用把同一个窗口填满，于是我们转向 **harness engineering**：对话压缩、工具优化、MCP 等等，把上下文窗口当成一份预算，而不是一个桶。

整条弧线就是人类在替一个永远不会改变的模型补上工程上的缺口。

这是大多数认真做事的团队会长期停留的阶段，也是你第一次真正觉得自己在拥有自己的 AI。提示、工具调用和 RAG 能把你带得相当远；但存在天花板。你 harness 里的每个模型，仍然是它上架时的那同一个模型。你的提示词和 harness 只是引导模型，什么也没教给它。而 harness 关于你业务所知道的一切，都要在每一次请求里用你付钱的 token 重新解释一遍，塞进一个你反复粘贴的提示词，交给一个可能下周就被下线的模型。

每个 AI 系统实际上都沿着三个轴被优化：**质量**（够不够好？）、**成本**（规模化之后还付得起吗？）和**延迟**（够不够快？）。AI 工程就是在不碰模型本身的前提下把这三点都往前推，而在撞上任何一条轴的天花板之前，它能带你走很远。攻克性能天花板很难，所以大多数人先去优化成本和延迟，而最有效的做法之一就是掺入开源模型。

## 阶段 3：把开源模型掺进来

如今，前沿开源模型往往能以闭源前沿模型一小部分的成本把活干完，而且视任务而定，质量差距很小甚至不存在。

这个阶段的定义因素是**单位经济性与控制权**，而不是意识形态。到了这一步，你要决定模型跑在哪里、响应多快、你的数据会怎样、以及你为每个 token、每个任务付多少钱。要挑对模型（开源或闭源），你可以依赖公开的基准测试成绩，更好的做法是在自己的任务上评估候选模型。

基准测试并不总能代表你实际在做的工作。也许你的 fintech 用例比基准里的样例更小众，或者你的法律问题横跨十几个领域、理念各不相同。基准测试是缩小候选范围的好办法；你自己的 **evals**（针对你自己的任务、系统性自建的 AI 系统测试）永远是性能的最佳指标。

假设你在做这样的 agent：它们需要操作 UI 来提取信息、与屏幕上的元素交互，或者干脆回答问题。这叫作 **computer use**，它有自己的基准测试。比如，如果你看 [**OSWorld 2.0**](https://osworld-v1.xlang.ai/) 的排行榜——这是一个面向多模态 computer use 的基准（也就是说 AI 要真的用眼睛看浏览器、真的去导航它来完成一个任务）——GPT 5.6 Sol 只比 Kimi K3 高几个百分点。你完全可以认为两者打平，然后选更便宜的 Kimi K3，但总还能再深挖一层。

再拿另一个 computer use 数据集举例。它叫 [**MacPaw UIPad**](https://huggingface.co/datasets/macpaw-research/UiPad)，里面有 1,000 多个样例，每个都是截图配上问题以及问题的答案。这个数据集不是常见的基准，但它作为公开可用的 computer use 测试集而存在。我在这个数据集上跑 K3 和 Sol 时，两者在 UIPad 上得分相同，但 Sol 跑完整个数据集花了 115 美元，而 K3 花了 56 美元（便宜 2 倍多）。

到这里，结果看起来和 OSWorld 一样。两个模型表现不相上下，但有一个更便宜：决定做完了。不过这个数据集有意思的地方在于：它被分成四个类别，如果逐个类别深挖，会出现一些有趣的东西：

- **yes/no** 类问题——K3 胜
- 答案是**数字**的问题——K3 胜
- 答案是自然语言的问题——打平
- **坐标**类问题，即 AI 必须在被问到的目标周围画一个框——Sol 胜

在 UIPad 测试集上，K3 和 Sol 总体以 87.7 打平，但类别的拆分是偏的：K3 在四类中赢下或打平三类，而 Sol 在坐标类上领先 13 个百分点。这个差距就是支持路由的论据。

如果事先就知道 K3 在 3/4 的类别上打平或取胜、而且更便宜，你就可以把坐标类任务路由给 Sol，其余全部交给 K3，最终得到整体更强也更便宜的系统。

能自由地在全球最强的 AI 模型上做实验、把系统工程做到最强，确实令人陶醉，但还是那句话：有天花板。AI 工程只是自有智能的创可贴，不是真正的解法。

## 阶段 4：训练——拥有你自己的专业智能

到了某个阶段，你的业务逻辑、你的分类体系、你内部的写作风格、你客户的怪癖，本身就是产品。这时那三个动机，以及它们底下的占有本能，不再只是考虑训练的理由，而成了动手训练的理由。**训练**（也就是 fine-tuning，就地改变一个模型的智能）让你不必在每次请求里重新说明这些东西，而是把它们搬进你控制的模型权重里。模型不再是你按 token 租来的通用工具，而变成你拥有的资产。

在实践中，训练模型会以五种常见模式出现。这些模式都以「现成的 AI 模型已经具备基础智能」为前提，把一个模型的智能塑造成专属于你的数据和工作流。

### “教模型我们的分类体系”

这是最宽泛、涵盖最多的模式。一般来说，我们需要模型从对任务的通用理解（通常用公开基准测试来测）走到更具体的任务版本（用内部测试集上的 eval 来测）。

分类和抽取是两个经典例子。想象把一张支持工单归到 17 个主题中的 1 个（这是分类）、升级给正确的团队（也是分类）、读一张收据做报销记账（这是抽取）。这些听起来简单，但模型不知道你的决策边界，也不知道两个主题之间只有你才懂的细微差别。你可以尽情地加提示词、做 few-shot，但那些 token 你要一直付钱，而且在灰色地带仍然是在赌。给模型几百到几千个「输入 → 我们实际使用的标签」的例子，它就不再猜你的分类体系，而是开始真的知道它。

我们的 UIPad 例子也属于这个模式。它既不是抽取也不是分类，但我们想让模型理解我们这个特定版本的任务。那就来测一测（test 这个词是双关，故意的）。计划如下：

- 把 UIPad 数据集切成训练集 / 测试集。这样我们更有信心模型能把从训练集学到的东西泛化到测试集上未见过的数据
- 在测试集上跑 Kimi K3 和 GPT 5.6 Sol，拿到基线分数。先说明一下，我之前给你看的是**整个**数据集的分数，并没有切分，所以需要重做一遍才能公平比较
- 在训练集上训练 K3，**不**在测试集上训练。我用的是 Fireworks 的 [Serverless Training API](https://docs.fireworks.ai/fine-tuning/training-api/serverless)，把我们的 [cookbook 训练 skill](https://github.com/fw-ai/cookbook) 文件指给我的 coding agent，剩下的交给它做
- 用训练后的新模型在同一个测试集上跑，拿到最终分数

在留出测试集上，基座 K3 落后于 Sol；经过大约三小时训练，调优后的 K3 超过了它。

就是这样！我们调优后的 K3 模型现在**只训练了 3 小时就比 GPT 5.6 Sol 更好。**这只是把独有数据和现成模型结合起来、造出真正具备专业智能的模型的一个例子。

### “用我们写作的方式写作”

如果你用 AI 写营销简报、临床记录、法律文书草稿、博客文章这类东西，你可能会注意到 AI 的输出未必真的错，但就是不像你会写出的记录，也不像你所里组织简报的方式。风格是一种行为，不是一个事实；提示词可以在短程内把风格撑住，但在长程上它会漂移。

举例来说，[Heidi](https://fireworks.ai/blog/Heidi-Health) 为每个医学专科训练不同的模型，因为精神科记录和骨科记录即使来自同一个事实来源，也属于不同的写作文类。我们在法律（[Harvey](https://fireworks.ai/blog/post-training-kimi-k3-with-harvey-for-long-horizon-legal-work)、Legora）和监管文书起草（Ritivel）中观察到同样的文体模式：知识是共享的，但形式是专门的，而你要训练进模型里的正是这个形式。

### “大模型能用，我们只是在规模化时用不起”

也许你一路读到这里，心想「呼，我的模型对我来说已经够好了，哪怕是闭源的」。如果是这样，那很好！如果一个前沿模型已经达到你的质量门槛，真正难受的是账单和延迟，那你该走的路可能是**蒸馏**：用那个大的前沿模型去指导和训练一个更小的模型，以低得多的成本和延迟复现它的质量。

你已经知道自己的质量门槛和账单，所以可以在花出第一块训练费用之前先估算回报——说实话这并不总是容易，但最后的评估**确实**更容易，因为「小模型能追平大模型吗？」比「这东西抽象地看算好吗？」要好回答得多。

### “让 agent 真的把活干完”

agent 是如今 LLM 最常见的应用形态，远超其他。大多数人要么在用现成的 agent harness，要么为了更有竞争力而自建一套、针对自己的业务调优。要让多步工具调用的 agent 可靠地端到端跑完，我们常常求助于**强化学习**：让 agent 在模拟任务和环境里跑，然后按结果（答案对不对？）、轨迹（路径是否高效？）和行为（有没有守规矩？）给它打分。

这类训练已被证明能灌输各种不同的行为，在某些情况下甚至能传授知识。难怪越来越多的公司转向强化学习，以抬高自家 agent 能做到的上限。当 agent 执行的任务可以被程序化检查时，这项工作尤其可行：单元测试通过、查询返回正确的行、工单被解决。我们与 [Vercel](https://fireworks.ai/blog/vercel) 的合作就是一个很好的例子，我们的 cookbook 里也正好有这类工作的配方（链接在文末）。

### “我们的领域变化频繁”

在上面这些模式里，任务空间通常变化得没那么快，不至于要求持续重训。举例来说，如果我们训练一个模型去操作某一组特定的 UI，而这套 UI 并不经常变，那你把训练好的模型放一阵子也没问题，不必太担心性能漂移。

最后这个模式是一种运营模式，不是一次性项目。漂移这个概念在 AI 里已经存在了几十年：你训练一次模型，效果很好，但它周围的数据一直在变。ICD 编码会修订，客户会问新问题，支付方政策会变，新药会进入市场。如果你的智能是租来的，你最多只能等别人的模型追上来。如果你拥有它，你可以搭一个持续训练的闭环并保持领先——这个好处值得在最后单独用一个词来说。

## 迈出通向专业智能的第一步

租用前沿模型是正确的起点，开源还是闭源都行。AI 工程能把你带得很远，尤其是在开源模型上。Fine-tuning 则是把你业务里独有的东西（数据、专业能力）变成你自己拥有的智能的方式。

但真正的回报不是单个训练好的模型，而是那个闭环。当你拥有模型、拥有配方、拥有训练闭环时，你的专业智能就不再是一张会衰减的快照，而变成会复利累积的东西：你领域里的每一次变化、线上每一次新的失败、每一个更好的基座模型，都会成为下一轮迭代的燃料，而不是让你等待别人路线图的理由。这才是拥有智能真正换来的东西。租来的版本永远只能追赶；拥有的版本才有机会保持领先。

现在我们有了一张如何拥有自己专业智能的地图。本系列余下的部分会一路驶过各个补给站、路边景点，最终抵达终点线。我们会看到如何诊断你的 AI 系统里真正坏掉的是什么、如何判断到底要不要训练，以及在准备好之后在哪里训练。一路上，我们还会看到端到端训练 LLM 和 agent 的完整实例。
