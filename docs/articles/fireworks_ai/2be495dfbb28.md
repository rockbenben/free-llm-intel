K3 是一个以一小部分成本达到前沿质量的开源模型。更重要的是，它与 Fable 形成可预测的互补，这使得通过路由任务获得最高质量的智能成为可能。

🧭 **tl;dr：** 我们在约 1,000 个智能体任务上让 Kimi K3（开源）对阵 Fable 5（闭源），发现：

- **我们在 K3 与 Fable 之间路由达到了 93% 准确率。**
- **在长智能体循环上，结果比单用 Fable 成本效益高约 50 倍**，并且在每个用例上成本都持续更低。

## 我们如何度量

我们汇总了**各自面向不同种类工作的基准**，让 K3 与 Fable 5 通过同一个 harness。总计约 1,030 个任务，全部在真实智能体循环中运行。

| 家族 | 测试内容 | 任务数 |
| --- | --- | --- |
| 家族 | 测试内容 | 任务数 |
| SWE | 真实仓库 bug 修复（SWE-bench 风格） | 460 |
| Terminal | 长周期智能体运维：安全、密码学、逆向工程、系统管理 | 89 |
| Algorithmic | LeetCode / AtCoder 风格题目 | 100 |
| Multi-Language | 跨六种语言的实现 | 225 |
| Legal | 法律智能体基准（律师评分任务） | 120 |

在进入结果之前先给一个快速定义。**Oracle 路由**是一种测量理论最佳性能的方法：让每个模型都跑一遍任务，然后挑出成本最低的正确选项（即成本/性能上限）。在实用路由器中，你不可能拿多个模型各跑一遍任务。路由器只能预测哪个模型在成本与质量上权衡最好，而说到底那只是个猜测。

在本研究中，oracle 路由在 72-96% 的任务中选择 K3。这暗示一个近乎完美的路由器或许是可以实现的——只要学会区分日常任务与真正处于前沿长尾的工作。但要下定论，还需要多一个数量级的路由数据和真实世界表现。

## K3 是一个好模型。

从一万英尺高空看，两个模型摆在一起很容易把正面对决判成平局。例如看 SWE 这个头条基准，K3 得 **92.4%**，Fable 得 **92.6%**。在我们基准测试的五类任务上，两个模型通常都咬在几分之内，Fable 在其编程语言广度（Multi-lang）上略占上风。

图 1 · 按类别的任务解出率。总平均几乎相同；底下各有所长。

到此为止说一句“大致打平”很容易。真正的新闻是：它们在不同任务类型上各有各的明显更强之处。

## 两个模型胜过一个

如果你往单个基准内部看，能看到的远不止头条准确率。拿 SWE 来说，两者整体上不分伯仲。若把 SWE 按问题领域拆开，你能看清各模型的闪光之处。K3 在符号数学与开发工具链上最锋利；Fable 赢在 Web 与数据可视化工作。同样的模式贯穿多语言集——Fable 的广度覆盖 Java、Python 和 C++，而 K3 在 JavaScript 和 Rust 上扳平。

图 2 · 按 SWE 领域的得分差（K3 减 Fable）。基准整体打平，两者仍逐领域各有专精。

在终端上的长周期工作——几十轮驱动 shell、摆弄系统——K3 显出了真本事。它清掉了一批 Fable 始终没攻下的任务：7z 哈希、FEAL 密码分析、泄露的密钥、一个真实漏洞、失控的异步作业。

图 3 · 89 个终端任务中，K3 有 11 个独占胜利，Fable 有 7 个，并且整体拿下安全与密码学集群。

## K3 在 Fireworks 上成本最多可低 50 倍。🫳🎤

质量上高水平打平，价格上却相去甚远。

图 4 · 每任务成本优势。背后有两个因素：token 定价，以及哪个模型跑得更久取决于任务。

这么大的价差从哪来？token 定价、prompt 缓存和每任务的 effort。以 SWE 为例，K3 比 Fable 卖力得多：每任务约 55 轮、130 万 token，对应 Fable 的 21 轮、13 万。在长终端任务上则反过来：Fable 才是那个兜圈子的，跑到 64 轮、150 万 token（有时直接撞进超时）。

图 5 · 每任务的轮数（线性轴）与 token 数（对数轴）。没有哪个模型全面更精简：K3 的额外功课在 SWE，Fable 在终端任务。注意 token 图的纵轴是任务解出率。

prompt 缓存把这些 effort 转化为 K3 价格优势的工作做得最多：即便 K3 读十倍的 token，靠缓存命中，SWE 的运行的总成本仍低于 Fable。这中间有取舍。轮数更多的任务通常意味着每次运行墙钟时间更长，即更慢。如果你需要两秒内出答案，这很重要；如果你在后台大规模跑智能体，一张小得多的账单要重要得多。

## 别选模型。要路由。

如果你把每个任务发给最胜任它的那个模型，你不会落在两个模型之间，而是落在两者之上。

逐任务路由总是胜过任何单模型运行：

图 6 · 逐任务 oracle 路由 vs 单独每个模型。绿色标签 = 该类别上相对最佳单模型赢得的分数点。

oracle 路由器在 72-96% 的任务流量中选择 K3。以这种方式架构路由器，你得到的整体质量高于任何单用模型，而成本接近只用那个成本优化的模型。

图 7 · oracle 路由器把每类任务发往何处。像 K3 这样强而成本优化的模型成为默认；高端模型是例外，不是常规。

## K3 在所有工作类型上都是成本优化的

把质量与成本放到同一张图上。蓝色的 K3 在全部五个任务家族中都落在红色 Fable 的左边（成本效益更高的一侧）。准确率你来我往：Fable 在多语言上领先，K3 在终端与法律上领先，其余大致持平。

图 8 · 各家族成本（对数轴）vs 准确率。K3 在全部五项中都位于 Fable 左侧、成本更低。垂直间距显示哪个模型在何处更强。

## 单模型是浪费的，也不再是 SoTA

Kimi K3 + Fable 一起路由，以最优价格解锁了两者最好的品质。

单模型供应商、堆 token 的日子正在走向尽头。任务级数据显示，这些模型是价格迥异的专家。最好的 AI 不再出自单一实验室，而是一个模型的混合体。

这在实践中的含义：

- **开源作为默认。** 像 K3 这样成本低 50 倍的开源模型应该是你的基准选项——反正 oracle 会把大多数流量发给它。
- **路由器就是你的护城河。** 路由器必须为你的工作负载量身定制，持续学习任务/模型的分工，是你保持领先的最大机会。
