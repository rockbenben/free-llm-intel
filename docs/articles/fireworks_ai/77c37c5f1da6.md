## TL;DR

- •Fireworks 全新的 ARCv3 压缩器缩小了从训练器发往强化学习（RL）rollout 生成机器的 BF16 权重更新的体积。
- •在 1,000 个生产环境 RL 权重更新增量（delta）上，ARCv3 生成的负载比 ARCv2 小近 50%，且能无损还原训练器精确的 BF16 权重。
- •更小的传输帮助 rollout 集群更紧地贴住当前策略（policy），让跨地域使用算力变得更可行，而不必依赖一个巨大的同址集群。
- •ARCv3 已随 [Fireworks Training API](https://docs.fireworks.ai/fine-tuning/training-api/introduction) 提供，以 `fireworks-delta-compression` 包的形式服务于「自带训练器 + Fireworks rollout」的团队。

随着越来越多团队推进强化学习、训练自己前沿规模的模型，两件事变得空前重要：获得训练算力的途径，以及优化在训练机器之间搬运数据的管道。RL 对这些管道的要求格外苛刻。一个前沿模型可能有数万亿参数，而训练器需要在训练推进过程中，持续不断地把它的更新版本推送给生成 rollout 的机器集群。

当管道跟不上时，团队就被逼向唯一的选择：一个把所有东西布在同一物理机房里、全互联的巨型集群。那很贵、很难拿到，并把小玩家挡在门外。在 Fireworks，我们穷尽一切可行路径，不让它成为唯一选项。否则，我们最终会面对一个只有少数几家公司进得了的训练市场。

在此前的文章[《前沿 RL 比你想象的便宜》](https://fireworks.ai/blog/frontier-rl-is-cheaper-than-you-think)中，我们讲过如何让跨区域 RL 真正落地。核心观察是：在我们考察的 RL 工作负载中，相邻 checkpoint 之间只有约 2% 的 BF16 权重发生变化。因此，我们不必在训练器每走一步时就把完整的 1 TB checkpoint 发往每台 rollout 机器，而是发送一个紧凑的 delta——一份「变了什么」的压缩描述——并在另一端重建更新后的模型。正是这一点让一次训练运行在三个或四个区域之间保持同步，而不需要集群之间的专用高带宽网络。

这个 delta 的大小决定了该方案在实践中效果如何。更小的 delta 让 rollout 集群更新更快、更贴近当前策略，并能拉取跨地域的可用算力。更大的 delta 则意味着训练器开始跑赢 rollout、集群数据过时，多区域架构相对单一巨型集群的优势也开始瓦解。

> ARCv3 delta 如何从训练器到达 rollout：每个训练器分片（shard）并行地把压缩后权重增量的自己那一份上传到共享对象存储（S3）。随后 Fireworks API 通知每个区域有新更新可用，各 rollout 区域拉取自己需要的部分并在本地重建更新后的模型。训练器从不直接与 rollout 集群通信——这正是全球分布式推理集群能靠普通网络链路保持同步的原因。

我们发布 ARCv3，即我们用于构建这些 delta 的压缩器的最新版本。这些改进适用于 BF16 权重：ARCv3 生成的负载约为上一版本的一半，平均 delta 负载约为原始 BF16 权重大小的 0.19%，低于此前的 0.36%（越低越好）。压缩是无损的：rollout 端重建出的模型与训练器产出的逐比特一致。ARCv3 已随 Fireworks Training API 提供，以 `fireworks-delta-compression` 包的形式服务于「自带训练器 + Fireworks rollout」的团队。

## ARCv3 内部机制：更新与更新并不平等

改进源自 BF16 权重在训练步之间变化方式的一个特定属性。

我们运行生产 RL 训练会话并观察 checkpoint 之间实际发生的事情，发现了一种强烈的不对称。在给定步上发生变化的大约 2% 的 BF16 权重中，绝大多数只是尾数（mantissa）移位，而指数（exponent）和符号（sign）保持不动。触及指数的更新很少见，翻转符号的更新更罕见。换句话说，大多数权重更新是轻推，不是跳跃。

ARCv3 把这种不对称直接编码进去。未变化的权重值从负载中省略；仅尾数变化的贡献只有它的尾数位；较罕见的更新（指数移位或符号翻转）被单独打包，每个更新的变更字段作为一个整体块一起编码。在 rollout 端，两个流都应用到上一个 checkpoint 上，并把结果与训练器的原始值做校验和（checksum）比对，以验证重建一致。

> ARCv3 如何编码一个权重块。每对 prev/next 做 XOR，并按哪些字段真正变了来分类。未变化的权重值（XOR 为零）从输出中省略。仅尾数变化（常见情形）只贡献其尾数位（图中高亮）。较罕见的更新——指数移位或符号翻转——连同变更字段作为一个块打包。输出流的形状由「变了什么」决定，而不是由输入格式的固定宽度决定。

对模型中的每个张量（tensor），ARCv3 还并行运行多种通用压缩算法，保留输出最小的那一个。这比预先选定单一算法更耗 CPU，但训练器机器上 GPU 在做实际训练时通常有闲置的 CPU 周期，所以花掉它们是划算的。

## ARCv3 与业界方案对比

我们在来自生产 RL 工作负载的 1,000 个真实权重更新 delta 上，把 ARCv3 与三种替代方案做了基准对比。所有更新都是 BF16，四个压缩器都无损运行，因此我们比较的是纯负载大小：描述同一个权重更新，每个压缩器需要多少字节。

ARCv3 的对照方案是：

- •**ARCv2**，我们自己压缩器的上一版本。
- •**PULSESync**，来自论文 [Understanding and Exploiting Weight Update Sparsity for Communication-Efficient Distributed RL](https://arxiv.org/abs/2602.03839)（Miahi & Belilovsky, 2026）的权重同步算法。PULSESync 同样利用 BF16 权重更新的稀疏性，采用稀疏补丁（sparse-patch）设计。
- [**Hugging Face TRL 中的 delta 压缩实现**](https://huggingface.co/blog/delta-weight-sync?utm_source=chatgpt.com)。

| 压缩器 | 压缩后 / 原始 BF16 权重比 |
| --- | --- |
| 压缩器 | 压缩后 / 原始 BF16 权重比 |
| ARCv3 | 0.19% |
| PULSESync | 0.35% |
| ARCv2 | 0.36% |
| HF TRL（草案） | 0.67% |

这里越低越好，ARCv3 在本次基准中产生最小负载。在被测的 BF16 权重张量上，ARCv3 把压缩后的 delta 缩到次优方案的大约一半。每个 rollout 区域拉取自己需要的 delta 分片，重建出与训练器逐比特一致的 BF16 权重。这帮助全球分布的 rollout 集群更贴近当前策略——这正是跨区域 RL 能规模化的原因。

## 使用 ARCv3

如果你为了 rollout 使用 Fireworks Trainer SDK，什么都不用做，因为 ARCv3 已经是默认选项。你的 rollout 集群会自动获得更小的传输，无需改动任何代码。

如果你自带训练器并使用 Fireworks 做 rollout，可以通过 `fireworks-delta-compression` 包直接集成 ARCv3。完整集成流程见 [Fireworks rollout 文档](https://docs.fireworks.ai/fine-tuning/rl-rollout-integration)。

## 让分布式算力为 RL 服务

RL 的权重更新是有结构的，而压缩器可以利用这种结构。把罕见的指数变化与常见的尾数更新分开处理，再在其上让几种通用编解码器同场竞技——这让我们以相对较低的额外 CPU 成本，获得了较我们自己上一版本近乎翻倍的压缩率。

我们在这条路上持续用力，是因为从 delta 上省下的每一个字节，都是在训练步中不必跨越大洲搬运的一个字节。这让我们更接近于让「跨三个四个区域集群训练」感觉像在同一栋楼里训练。它帮助更多团队在想法上竞争，而不是在能买到多少同址算力上竞争。

对于构建专用模型的团队，回报是扩展 RL 时更灵活的方式。Fireworks 负责跨 rollout 区域的权重分发与同步。

ARCv3 是我们目前到达的位置。我们会继续推进。
