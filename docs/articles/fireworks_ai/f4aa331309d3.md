## Training API 现已正式可用

我们与全球各地的 ML 团队合作，弄清现有训练工作流到底短在哪里：模型与方法选择受限，对参数和训练循环的控制有限，算力僵化且利用率不足，训练与 rollout 基础设施割裂——这推高成本、产生同步开销并引入数值漂移。这些合作塑造了我们的 Training API。

Fireworks Training API 将你的自定义训练循环连接到 Fireworks 托管的分布式训练与 rollout 基础设施。你可以从任意位置用 Python 编排循环，完全掌控自己的 loss 或 reward、数据和环境。Fireworks 管理高性能算力：负责计算梯度并更新模型的 trainer，以及从训练后的模型生成样本的 rollout 部署。Fireworks 还管理两者之间的交互，从权重同步到 swap 失败恢复，以及训练与 rollout 的对齐。这一切让你专注于打磨学习信号，而不是基础设施难题。

## 为什么团队选择在 Fireworks 上训练

Fireworks 是少数在前沿实验室之外、在超过 10,000 块 GPU 上运行过强化学习（RL）的组织之一。RL 把训练和推理变成一个持续耦合的系统；每一步都从当前策略的 rollout 开始，更新权重，再把这些权重送回推理进行下一轮采样。在前沿规模下，算法只是挑战的一部分。有效的 RL 取决于三项要求：正确性、性能效率和开发速度。

### 正确性：训练与推理对齐

要让 RL 训练保持正确，rollout 引擎和 trainer 必须共享同一套数值定义。即便一切看上去都在正常工作，微小的数值漂移也可能破坏学习信号，从 token clipping 一直到 reward 崩塌。在 Fireworks 上，

- **数值格式端到端一致。** 训练与推理之间精度或量化的差异，即使权重相同，也会改变模型算出的值。Fireworks 对齐 trainer 与 rollout 的数值格式（例如 BF16、分块 FP8 和 NVFP4），因此 trainer 保存的模型就是 rollout 部署所运行的模型。
- **kernel 也一致。** 相同的数值格式并不能保证相同的计算。浮点归约、kernel 选择和并行方式即使在完全相同的精度下也可能产生不同的数值，因此 Fireworks 对齐两条路径上的底层实现。
- **MoE 执行保持一致。** 微小的数值差异可能改变哪些 expert 被激活，让同一个 token 走上不同的计算路径。Fireworks 使用 Router Replay 在 rollout 与反向传播之间保留 expert 选择，并为受支持的前沿 MoE 配备 batch-invariant kernel 和确定性归约。

Fireworks 直接验证这种对齐：让相同的序列分别经过 rollout 引擎和 trainer，并测量训练-推理 KL 散度（KLD）。所有在 Fireworks 训练上发布的模型都会持续校验，确保 KLD 最小化。

### 性能效率：最大化整个 RL 循环的吞吐

在大规模下，RL 很大程度上是一个生成问题。大部分 wall-clock 时间花在产出 rollout 而不是更新权重上，所以 rollout 吞吐和 GPU 利用率成为训练时间与成本的主要决定因素。completion 长度也差异巨大，这意味着僵化的 batching 会让 GPU 在少数长轨迹跑完之前一直空闲。

Fireworks 可以运行异步 RL，让 rollout 收集与训练重叠，而不是强迫循环的两端串行执行。rollout GPU 可以在 trainer 更新上一批的同时开始生成下一批，在算法允许多一些重叠时还可以接受有界的权重陈旧度（weight staleness）。目标很简单：让 GPU 做有用的工作，而不是在同步屏障处等待。

循环完成一个训练步之后，更新后的模型必须传输并加载进 rollout 部署。Fireworks 不会在每一步之后拆掉 rollout 部署并重载完整模型，而是把新权重热加载进正在运行的部署。对于全参数 checkpoint，我们使用新颖的压缩技术来降低权重传输的带宽和存储需求：计算当前权重与上一版权重之间的 XOR Diff，再用 zstd 压缩缩小这份 payload 的体积。这让传输带宽最多降低 10 倍，显著加快训练循环。

### 开发速度：压缩迭代周期

通往生产的瓶颈往往不是训练任务，而是两次迭代之间的时间。在割裂的技术栈里，每个周期都意味着在训练与推理系统之间搬运 checkpoint、重新部署、对齐差异、跑评估，然后再从头开始。

Fireworks 把这个过程变成一个持续开发循环：在一个平台上 训练 → 部署 → 评估 → 再训练。checkpoint 直接进入 serving，而生产 trace、评估和反馈喂给下一轮训练。又因为我们负责 GPU 开通、容量和配置，客户省去了采购、模型启用和基础设施容量测算这些拖慢迭代与上市时间的工作。团队反馈在同样的训练预算下迭代次数提升 2–4 倍，把模型开发从数周压缩到数小时，加快了走向生产的速度。
