# 用 MCP 结合代码执行：构建更高效的 agent

发布于 2025 年 11 月 4 日

直接工具调用会为每个定义和结果消耗上下文。让 agent 转而通过写代码来调用工具，能更好地扩展。下面讲它在 MCP 下如何工作。

[Model Context Protocol（MCP）](https://modelcontextprotocol.io/)是一个把 AI agent 连到外部系统的开放标准。把 agent 连到工具和数据，传统上需要为每一对组合做定制集成，造成碎片化和重复劳动，使真正互联的系统难以扩展。MCP 提供一个通用协议——开发者在 agent 里实现一次 MCP，就解锁了整一生态的集成。

自 2024 年 11 月发布 MCP 以来，采用速度飞快：社区构建了数以千计的 [MCP 服务器](https://github.com/modelcontextprotocol/servers)，[SDK](https://modelcontextprotocol.io/docs/sdk) 覆盖了所有主流编程语言，业界也已把 MCP 采纳为把 agent 连到工具和数据的实际标准。

如今开发者常常构建能访问数十个 MCP 服务器上数百乃至数千个工具的 agent。然而，随着所连工具数量增长，把所有工具体定义预先加载、并把中间结果经由上下文窗口传递，会拖慢 agent、增加成本。

在这篇博客里，我们会探讨代码执行如何让 agent 更高效地与 MCP 服务器交互、用更少的 token 处理更多的工具。

## **工具带来的过度 token 消耗让 agent 效率变低**

随着 MCP 使用规模化，有两种常见模式会增加 agent 的成本和延迟：

- 工具体定义使上下文窗口超载；
- 中间工具结果消耗额外的 token。

### **1. 工具体定义使上下文窗口超载**

多数 MCP 客户端把所有工具体定义预先直接加载进上下文，用一种直接工具调用语法把工具暴露给模型。这些工具体定义可能长这样：

```
gdrive.getDocument
     Description: Retrieves a document from Google Drive
     Parameters:
                documentId (required, string): The ID of the document to retrieve
                fields (optional, string): Specific fields to return
     Returns: Document object with title, body content, metadata, permissions, etc.
```

```
salesforce.updateRecord
    Description: Updates a record in Salesforce
    Parameters:
               objectType (required, string): Type of Salesforce object (Lead, Contact,      Account, etc.)
               recordId (required, string): The ID of the record to update
               data (required, object): Fields to update with their new values
     Returns: Updated record object with confirmation
```

工具描述占据更多上下文窗口空间，增加响应时间和成本。在 agent 连到数千个工具的情形里，它们在读一个请求之前就要处理几十万个 token。

### **2. 中间工具结果消耗额外的 token**

多数 MCP 客户端允许模型直接调用 MCP 工具。例如，你可能对 agent 说：「从 Google Drive 下载我的会议记录文本，并把它附到 Salesforce 线索上。」

模型会做出这样的调用：

```
TOOL CALL: gdrive.getDocument(documentId: "abc123")
        → returns "Discussed Q4 goals...\n[full transcript text]"
           (loaded into model context)

TOOL CALL: salesforce.updateRecord(
			objectType: "SalesMeeting",
			recordId: "00Q5f000001abcXYZ",
  			data: { "Notes": "Discussed Q4 goals...\n[full transcript text written out]" }
		)
		(model needs to write entire transcript into context again)
```

每个中间结果都必须经由模型传递。在这个例子里，完整的会议文本流过了两次。对一场两小时的销售会议，这可能意味着多处理 50,000 个 token。更大的文档甚至可能超出上下文窗口限制，破坏工作流。

面对大文档或复杂数据结构时，模型在工具调用之间复制数据时更容易犯错。

MCP 客户端把工具体定义加载进模型的上下文窗口，并编排一个消息循环，其中每个工具调用和结果在操作之间都经由模型传递。

## **MCP 结合代码执行提升上下文效率**

随着代码执行环境对 agent 越来越普及，一种解法是把 MCP 服务器作为代码 API、而非直接工具调用来呈现。agent 于是可以写代码来与 MCP 服务器交互。这种做法同时应对了两个挑战：agent 可以只加载它们需要的工具，并在把结果回传给模型之前、于执行环境里处理数据。

有多种方式可以做到这一点。一种是从已连接的 MCP 服务器生成一棵所有可用工具的文件树。这里是一个用 TypeScript 的实现：

```
servers
├── google-drive
│   ├── getDocument.ts
│   ├── ... (other tools)
│   └── index.ts
├── salesforce
│   ├── updateRecord.ts
│   ├── ... (other tools)
│   └── index.ts
└── ... (other servers)
```

然后每个工具对应一个文件，类似：

```
// ./servers/google-drive/getDocument.ts
import { callMCPTool } from "../../../client.js";

interface GetDocumentInput {
  documentId: string;
}

interface GetDocumentResponse {
  content: string;
}

/* Read a document from Google Drive */
export async function getDocument(input: GetDocumentInput): Promise<GetDocumentResponse> {
  return callMCPTool<GetDocumentResponse>('google_drive__get_document', input);
}
```

上面我们那个 Google Drive 到 Salesforce 的例子，就变成了代码：

```
// Read transcript from Google Docs and add to Salesforce prospect
import * as gdrive from './servers/google-drive';
import * as salesforce from './servers/salesforce';

const transcript = (await gdrive.getDocument({ documentId: 'abc123' })).content;
await salesforce.updateRecord({
  objectType: 'SalesMeeting',
  recordId: '00Q5f000001abcXYZ',
  data: { Notes: transcript }
});
```

agent 通过浏览文件系统来发现工具：列出 `./servers/` 目录找到可用的服务器（如 `google-drive` 和 `salesforce`），然后阅读它需要的具体工具文件（如 `getDocument.ts` 和 `updateRecord.ts`）来理解每个工具的接口。这让 agent 只加载当前任务所需的定义。这把 token 用量从 150,000 降到 2,000——时间和成本上节省了 98.7%。

Cloudflare [发布了类似的发现](https://blog.cloudflare.com/code-mode/)，把 MCP 结合代码执行称作「Code Mode」。核心洞见相同：LLM 擅长写代码，开发者应当利用这一长处，构建与 MCP 服务器更高效交互的 agent。

## **MCP 结合代码执行的好处**

MCP 结合代码执行能让 agent 更有效地使用上下文——按需加载工具、在数据抵达模型前过滤它、并在单个步骤里执行复杂逻辑。用这种做法在安全和状态管理上也有好处。

### 渐进式披露

模型擅长浏览文件系统。把工具作为文件系统中的代码来呈现，能让模型按需阅读工具体定义，而不是预先读取全部。

或者，可以给服务器添加一个 `search_tools` 工具来查找相关定义。例如，在使用上面那个假设的 Salesforce 服务器时，agent 搜索「salesforce」并只加载当前任务所需的那些工具。在 `search_tools` 里包含一个详细程度参数、让 agent 选择所需详细度（例如仅名字、名字和描述、或带 schema 的完整定义），也能帮 agent 节省上下文、高效地查找工具。

### 上下文高效的工具结果

处理大数据集时，agent 能在回传结果前在代码里过滤并转换它。考虑拉取一张 10,000 行的电子表格：

```
// Without code execution - all rows flow through context
TOOL CALL: gdrive.getSheet(sheetId: 'abc123')
        → returns 10,000 rows in context to filter manually

// With code execution - filter in the execution environment
const allRows = await gdrive.getSheet({ sheetId: 'abc123' });
const pendingOrders = allRows.filter(row => 
  row["Status"] === 'pending'
);
console.log(`Found ${pendingOrders.length} pending orders`);
console.log(pendingOrders.slice(0, 5)); // Only log first 5 for review
```

agent 看到的是五行而不是 10,000 行。类似的模式也能用于聚合、跨多数据源连接、或提取特定字段——全都不撑爆上下文窗口。

#### **更强大、更上下文高效的控制流**

循环、条件、错误处理可以用熟悉的代码模式来做到，而不是串接一个个工具调用。例如，如果你需要在 Slack 里得到一条部署通知，agent 可以写：

```
let found = false;
while (!found) {
  const messages = await slack.getChannelHistory({ channel: 'C123456' });
  found = messages.some(m => m.text.includes('deployment complete'));
  if (!found) await new Promise(r => setTimeout(r, 5000));
}
console.log('Deployment notification received');
```

这种做法比在 agent 循环里交替发起 MCP 工具调用和 sleep 命令更高效。

此外，能写出一个会被执行的条件树，也节省了「首 token 时间」延迟：agent 不必等模型去求值一个 if 语句，而可以让代码执行环境来做这件事。

### 保护隐私的操作

当 agent 用 MCP 结合代码执行时，中间结果默认留在执行环境里。这样一来，agent 只能看到你显式 log 或 return 的东西，意味着你不想与模型共享的数据能流过你的工作流、而从不进入模型的上下文。

对于更敏感的工作负载，agent harness 可以自动给敏感数据做令牌化。想象一下你需要把客户联系人详情从一张电子表格导入 Salesforce，agent 写：

```
const sheet = await gdrive.getSheet({ sheetId: 'abc123' });
for (const row of sheet.rows) {
  await salesforce.updateRecord({
    objectType: 'Lead',
    recordId: row.salesforceId,
    data: { 
      Email: row.email,
      Phone: row.phone,
      Name: row.name
    }
  });
}
console.log(`Updated ${sheet.rows.length} leads`);
```

MCP 客户端在数据抵达模型前就拦截它、并对 PII 做令牌化：

```
// What the agent would see, if it logged the sheet.rows:
[
  { salesforceId: '00Q...', email: '[EMAIL_1]', phone: '[PHONE_1]', name: '[NAME_1]' },
  { salesforceId: '00Q...', email: '[EMAIL_2]', phone: '[PHONE_2]', name: '[NAME_2]' },
  ...
]
```

然后，当数据在另一个 MCP 工具调用里被共享时，它经由 MCP 客户端里的一次查找被还原为明文。真实的邮箱、电话号码和姓名从 Google Sheets 流向 Salesforce，但从不经过模型。这防止了 agent 意外记录或处理敏感数据。你也可以用这个来定义确定性的安全规则，选择数据能流向何处、从何而来。

### 状态持久化与 skills

带文件系统访问的代码执行让 agent 能跨操作维持状态。agent 可以把中间结果写入文件，从而能够恢复工作、跟踪进度：

```
const leads = await salesforce.query({ 
  query: 'SELECT Id, Email FROM Lead LIMIT 1000' 
});
const csvData = leads.map(l => `${l.Id},${l.Email}`).join('\n');
await fs.writeFile('./workspace/leads.csv', csvData);

// Later execution picks up where it left off
const saved = await fs.readFile('./workspace/leads.csv', 'utf-8');
```

agent 也能把自己写的代码持久化为可复用的函数。一旦 agent 为某任务写出了可用的代码，它就能把那个实现保存下来供日后使用：

```
// In ./skills/save-sheet-as-csv.ts
import * as gdrive from './servers/google-drive';
export async function saveSheetAsCsv(sheetId: string) {
  const data = await gdrive.getSheet({ sheetId });
  const csv = data.map(row => row.join(',')).join('\n');
  await fs.writeFile(`./workspace/sheet-${sheetId}.csv`, csv);
  return `./workspace/sheet-${sheetId}.csv`;
}

// Later, in any agent execution:
import { saveSheetAsCsv } from './skills/save-sheet-as-csv';
const csvPath = await saveSheetAsCsv('abc123');
```

这与 [Skills](https://docs.claude.com/en/docs/agents-and-tools/agent-skills/overview) 的概念紧密相关——一组可复用的指令、脚本和资源的文件夹，供模型提升其在专门任务上的表现。给这些被保存的函数加一个 SKILL.md 文件，就创建了一个结构化 skill，供模型引用和使用。随时间推移，这让你的 agent 构建起一个更高层能力的工具箱，演进它高效工作所需的脚手架。

请注意，代码执行引入了它自己的复杂性。运行 agent 生成的代码需要一个安全的执行环境，配合恰当的[沙箱](https://www.anthropic.com/engineering/claude-code-sandboxing)、资源限额和监控。这些基础设施要求会增加运营负担、以及直接工具调用本可避免的安全考量。代码执行的好处——降低 token 成本、更低延迟、更好的工具组合——应与这些实现成本相权衡。

## **总结**

MCP 为 agent 连接众多工具和系统提供了一套基础协议。然而，一旦连接了太多服务器，工具体定义和结果就可能消耗过多 token，降低 agent 效率。

虽然这里的许多问题感觉新颖——上下文管理、工具组合、状态持久化——但它们在软件工程里早有众所周知的解法。代码执行把这些成熟的模式应用到 agent 上，让它们能用熟悉的编程构件更高效地与 MCP 服务器交互。如果你实现了这种做法，我们鼓励你把自己的发现分享给[MCP 社区](https://modelcontextprotocol.io/community/communication)。
