# 医疗机构如何使用 Claude Tag

Insight Health、Tennr 和 Medallion 如何借助 Claude Tag 构建人机协作的团队。

- 类别：[企业 AI](https://claude.com/blog/category/enterprise-ai)
- 产品：[Claude Tag](https://claude.com/product/tag)
- 日期：2026 年 9 月 14 日
- 阅读时长：5 分钟

- 作者：Camy Pearson、Maria Howe、Araba Koomson

医疗机构正使用 [Claude Tag（beta）](https://support.claude.com/en/articles/15594475-what-is-claude-tag)——它把 Claude 作为[一位队友](https://academy.claude.com/courses/building-effective-human-agent-teams)带入 Slack——来帮助他们分类生产告警、维护内部工具，以及回答关于支付方规则的问题。虽然 Claude Tag 尚未纳入 Anthropic 的[业务伙伴协议](https://support.claude.com/en/articles/8114513-business-associate-agreements-baa-for-commercial-customers)（BAA）范围，但已有多家医疗机构如今就在从不触及受保护健康信息（PHI）的频道、搭配从不触及 PHI 的连接器使用它。

在频道里 @-提及 @Claude，它就会阅读讨论串、使用你已连接的工具、完成工作并向回汇报。它记得每个频道里发生了什么，因此长时间运行的工作从不需要反复解释；在你允许的情况下，它还能关注一个频道、在恰当时机主动介入。

管理员决定 Claude Tag 在哪里工作、能触达什么，因此医疗团队可以让 Claude Tag 避开那些存有 PHI 的频道和系统：

- Claude Tag 可以默认关闭，仅在 **获批准的频道中启用**，禁用私信，并按频道**划定连接器范围**。
- Claude Tag 不会读取整个 Slack——相反，它只看到一名工作区成员所看到的内容。虽然它能读取并按时键词搜索工作区的公开频道，但无法访问那些未被邀请进入的私有频道。
- **访问包（Access bundles）** 让一个团队能在某个频道里一次性连接其代码库和问题跟踪器等数据源，同时让 EHR、临床系统和患者通讯保持不可访问。了解更多关于 Claude Tag [agent 身份访问模型](https://claude.com/blog/agent-identity-access-model)及其完整架构的内容，见[安全与数据处理文档](https://claude.com/docs/claude-tag/concepts/security-and-data?open_in_browser=1)；关于医疗机构最佳实践的更多内容，见[此处](https://claude.com/docs/claude-tag/admins/healthcare)。

启用 Claude Tag 并将其链接到 GitHub 的企业组织可获得 25,000 美元的 Claude Tag 额度（拥有 10 个及以上席位的 Team 组织为 2,500 美元）；请注意这些额度于 2026 年 10 月 1 日到期。额度详情见[此处](https://support.claude.com/en/articles/15575654-claude-tag-launch-promo-for-claude-team-and-enterprise)。

以下是 Insight Health、Tennr 和 Medallion 如今如何使用 Claude Tag 构建[人机协作团队](https://claude.com/blog/building-effective-human-agent-teams)。

#### **在 Insight Health 运行事故响应**

Insight Health 打造了 MagicDocs——一款面向专科医疗机构的 AI 转诊协调器。MagicDocs 读取传入的患者文档（传真、转诊单、事前授权请求、化验单和病历），提取临床细节，把每份文档匹配到正确的患者，并把结构化数据写入 EHR。该公司服务横跨 56 个专科的 1,100 多家诊所。

随着 Insight Health 客户群的增长，生产告警分类一直在蚕食其精干工程团队本愿投入更高价值工作的时间。因此过去三个月，该公司在不含 PHI 的工程和支持频道里运行 Claude Tag，由它调查生产告警、开单并去重、审阅 PR，并把上下文从一个讨论串带到下一个。

在他们高吞吐的生产告警频道里，他们把 Claude Tag 与第二个 agent——Zeus（由 Insight Health 基于 Claude Agent SDK 构建）——搭配起来，把一起事故从首次通知一路推进到经过测试的修复。两个 agent 的访问权限被刻意区分：Claude Tag 能看到代码库和 Linear，因此它了解代码模式和工单历史；Zeus 运行在公司受 BAA 覆盖的 Claude API 组织上，因此它能查询生产数据，并在数据进入 Slack 之前对 PHI 做脱敏。当一条告警到达时，两个 agent 会调查它——查询生产数据、对照代码和近期部署检查、与过往工单比对——全程在 Slack 讨论串里汇报进度。一旦它们确定根因，就开一个草稿 PR 并监控测试，最后由工程师审阅并合并。Claude Tag 的频道记忆在这里很有价值：它能把一个新抱怨识别为一个修复待定的已知问题、记起数周前的调查，并在不受提示的情况下遵循常设指令。

Insight Health 联合创始人兼 CTO Saran Siva 表示：「Slack 频道里的每个人都能看到两个 agent 的推理，以及它们如何分工。这种透明建立了信任，也教会团队如何从 agent 身上榨取最大价值。」自 Claude Tag 上线以来，Insight Health 关键告警频道里 97% 的告警在无需工程师介入的情况下就被关闭了，让团队得以专注于核心产品工作。

除事故之外，Insight Health 团队还用 Claude Tag 做招聘、供应商谈判准备、合同审阅（对照通话记录核查条款）以及一般业务运营。

#### **在 Tennr 维护内部工具**

Tennr 是一个患者调度平台，通过自动化接待、文档、授权和排期这些本会拖延护理的工作，帮助医疗服务提供者更快地把患者送进合适的护理环境。Claude Tag 栖身于其内部工具中，帮助非技术团队搭建并维护定制的内部应用。

在像 Tennr 这样高速成长的公司，内部工具的消亡和建成一样快，因为没人有余力去维护。2026 年 7 月，Tennr 在构建内部工具时采取了一种不同做法。它上线了 recruiting.tennr.com——一个用 Claude Code 构建的内部 offer 呈递门户——并通过一个专用 Slack 频道把 Claude Tag 设为主维护者。如今，真正使用这个工具的人（招聘人员、人事团队成员、招聘经理和 RevOps）用平实易懂的英语 @-提及 Claude 提要求，Claude 就交付代码变更、部署它并回报。他们可以直接在这个工具上迭代，而不必把工程师从产品工作上抽调出来。

大约一个月里，团队以这种方式交付了 15 个以上的工单：从一个上传的 PDF 一页纸构建的福利深度剖析板块、一个链接到 Dropbox Sign 的「在此签署你的 offer」横幅、目标奖金字段，以及自助管理控制。当一处被公开暴露的 copy API 被标记时，Claude 当天就把它锁了起来。当一个 Ashby 导入 bug 不断重置已上线 offer 的股权时，Claude 修好了 bug 并传播了修正后的值。当另一个 bug 短暂地错误地向候选人显示变动薪酬时，Claude 未经请求就在频道里发布了一条通知，说明受影响的时间窗口和补救措施。它还撰写了这个工具的上手文档，并处理其权限管理。

团队在频道里教会了 Claude 自己的运维惯例，包括一套 emoji 状态图例，以及一个含编号工单、请求者、commit 链接、截图和实时测试链接的工单格式。Claude 从今往后采用了它们。招聘人员用自然语言提的其实是工程工单，有时就是一张截图，却在一小时内就拿回了生产变更。Tennr 业务运营与战略副总裁 Abe Griffiths 表示：「正是 Claude Tag 让内部工具得以成立。借助 Claude 通过一个 Slack 渠道担任工具的守护者，真正使用工具的人就能直接在上面迭代，而不必把工程师从产品工作上抽调出来。」

推广之所以迅速，是因为 groundwork 已经就绪。Tennr 只允许 PHI 存在于有限的若干私有频道，因此广泛添加 Claude Tag 并未引入新的数据问题。让 Claude Tag 易于点头的，是按频道划定范围的能力。

Griffiths 说：「在 offer 工具频道里，我们希望 Claude 主动出击：修复问题、修改代码、跳过 PR 审查并交付。这种姿态显然不适合，比如一个产品或工程频道——在那里 Claude 的角色更接近信息收集或让我们保持条理。能够逐条频道地划出这些界限，意味着我们可以在低风险处赋予 Claude 真正的自主权，而不必到处授予它。」

#### **在 Medallion 积累支付方专业知识**

Medallion 为医疗机构自动化提供者的资质认证、执业许可和支付方注册。这些工作很大程度上依赖晦涩、缺乏文档的规则：某个支付方在一个团体注册前要求最少有多少名认证提供者、州级的特定法规，以及工程师在把一个流程编码进产品之前需要回答的数十个类似问题。历来，这些答案掌握在少数几位内部医疗领域专家手中，为核心产品开发决策造成了一道持续存在的人力瓶颈。

如今 Claude Tag 坐进了这个回路，打破了知识孤岛。当工程师在 Slack 里问一个支付方规则问题时，Claude Tag 从过往专家回复、历史数据和非结构化内部资源中作答。专业知识在频道里累积，而不是在某一个人脑子里。

CTO Armaan Sarkar 表示：「当它没有把握时，会 @ 进对口的专家，而专家的回复就成了未来相关话题回答的基础。」

是什么让他们放心推广 Claude Tag？Sarkar 归因于选对不含 PHI 的工作流、专家审阅和自动化校验。Claude Tag 在政策层面运作：问题关乎支付方规则和流程，而非个体患者或服务提供者。它并非独自作答：专家提供监督和更正，每一次交流都发生在公司任何人都可审计的 Slack 频道里。而且输出会在下游被核查，因为 Medallion 的系统用这些政策去执行那些本身会被审计和验证的动作。

#### **如何开始**

上述这些团队都起步于同一个地方：工程、产品、运营或招聘频道，配上一两个连接器，在公开的讨论串而非私信里工作，好让整个团队都能审阅并承接上下文。

查阅面向医疗机构的 Claude Tag 最佳实践，见[此处](https://claude.com/docs/claude-tag/admins/healthcare)，然后从一个频道开始。把 Claude Tag 在一个告警或支持工程频道上开启，连接 GitHub，让团队与它共事两周后再扩大允许清单。
