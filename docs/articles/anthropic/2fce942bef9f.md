在过去的几个月里，我们看到了永远在线的客服人员的复兴。

永远在线的代理是有状态的、主动的，这意味着它们管理跨会话的上下文并在没有直接监督的情况下采取行动。在下面，它们与其他代理运行在相同的[核心循环](https://www.anthropic.com/research/building- effective-agents)上。不同之处在于周围的架构，它是由控制代理何时唤醒、运行之间延续的内容以及它们的工作如何到达用户的原语构建的。

这种复兴很大程度上归功于最近模型的进步，这使得永远在线的代理运行起来更加实用。首先，最新的模型有更好的判断力：它们在理解用户意图和知道何时检查方面更可靠。其次，情报变得越来越便宜，长期任务受益最多。例如，在[一个长期编码基准](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)上，Opus 5.5 每解决任务的成本比 Opus 5 低 78%，而典型工作负载则低 40%。

客户已经开始询问我们如何将这种体验融入到他们自己的产品中。一些公司希望让现有的代理更加积极主动，而另一些公司则希望从头开始建立代理。

这篇文章详细分析了永远在线代理背后的原语，并介绍了它们如何组合在一起。

## 永远在线代理背后的循环

永远在线的代理实际上并不是“永远在线”。这只是对用户体验的描述。

实际上，代理大部分时间都在睡觉，定期醒来去做工作。每一段工作都称为“运行”：代理接收事件，完成其任务，然后保存有关所发生情况的信息。运行在 **会话** 内进行，它是消息和工具调用的记录。一旦运行完成，代理就会重新进入睡眠状态，并且循环无限地重复。

![永远在线的代理时间线的动画图：长时间睡眠，没有花费任何代币，被短暂的运行打断。每次运行都有四个步骤：事件到达、会话启动、代理循环运行，以及运行写回到运行之间延续的存储状态。](https://assets.claude.com/5dc803bf06d6e92e4aecae762da096626e2fa9ec.gif)

## 核心原语

永远在线代理的外围架构有五个核心原语：事件收件箱、计时器、内存、权限和发件箱。让我们逐一看一下。

### 活动收件箱

大多数人工智能代理仅在用户发送消息时运行。相比之下，永远在线的代理可以由多种类型的事件触发，包括 Webhook、计划任务和后台作业。

一种诱人的方法是让每个事件源直接调用代理，但这有一些失败模式。例如，同时到达的两个事件可能会开始竞争运行，而崩溃可能会完全丢失一个事件。

这就是事件收件箱发挥作用的地方。每个源都将事件发送到收件箱，然后由工作人员接收该事件，而不是调用代理。

最简单的版本包含三个组件：

- 持久的事件列表，通常是数据库表；
- 处理程序，通常是 HTTP 端点，用于将事件写入列表；和
- 从列表中读取的工作者，通常是后台服务。

收件箱应跟踪每个事件的状态，并且可以根据源的唯一标识符对事件进行重复数据删除。关系数据库非常适合收件箱，每个事件都作为新行附加。我们建议从每个用户一个收件箱开始，但如果您需要更多并行性，可以进一步拆分。

![活动收件箱图。处理程序（HTTP 端点）将每个事件写入收件箱（一个跟踪状态并删除重复项的数据库表），并唤醒工作人员。工作线程读取待处理的内容，开始运行，等待其完成，并将事件标记为已完成。](https://assets.claude.com/bb08543a505cea3a24c88c718ceec4405e9c0a79.png)

当新事件到来时，处理程序将事件写入收件箱并唤醒工作人员。工作人员读取待处理的内容并开始运行。继续早期工作的事件（例如用户的回复）将恢复现有会话，而其他所有事件都会启动新会话。

从那里，工作人员将事件传递到代理循环，等待运行完成，并将相应的事件标记为已完成。实施细节可能会很棘手，因此这里有一些最佳实践：

- **处理程序应快速确认事件**。某些来源（例如 Webhook 提供商）将缓慢的响应视为失败。处理程序仍然可以运行轻量级检查，但任何更深入的验证（例如检查提示注入）都应该在运行期间完成。
- **收件箱应该是真相的来源**。当工作线程被唤醒时，它应该首先从收件箱中提取最新的事件。这样，如果工作人员在运行中死亡，新的工作人员可以拾取相同的事件并重试。
- **收件箱一次只能有一名活跃工作人员**。这可以防止两次运行重复工作或相互覆盖。当新事件在运行中出现时，您可以将其推送到下一次运行、将其折叠到当前运行中，或者中断并重新启动。
- **工作人员应将待处理事件一起批处理。** 例如，如果用户连续发送多条消息，工作人员可以将它们合并到一次运行中，因此代理只需回复一次。

### 计时器

计时器与事件收件箱一起，让永远在线的座席保持主动。计时器通常分为两类之一：后续或时间表。后续行动是代理为自己设定的截止日期，例如检查回复。另一方面，时间表是按已知节奏发生的重复任务，例如每日新闻通讯。

计时器存在于自己的持久存储中，通常是另一个数据库表，与收件箱分开。收件箱应该只保存准备好处理的事件。后续行动和计划可以共享类似的模式，但计划也需要跟踪其重复发生。

![定时器图。运行在数据库表中设置一个计时器，可以是代理设置的后续操作，也可以是用户设置的计划。调度程序找到到期的事件并将事件添加到事件收件箱，从而开始下一次运行。](https://assets.claude.com/c16694e6d979a2ace84d03da0544297b7245c0a8.png)

计时器不会自行启动运行。相反，调度程序（通常是后台服务）以固定的时间间隔轮询存储并触发任何到期的内容。在每次传递中，调度程序：

- 扫描商店并找到到期的计时器。
- 根据类别更新每个计时器。后续操作应标记为已完成。计划应将其到期时间更新为下一次发生。
- 将事件添加到收件箱并唤醒工作人员。

对于调度程序，您可以构建自己的服务或使用持久的执行引擎。

＃＃＃ 记忆

始终在线的代理可以在许多脱节的运行中工作，并依靠内存来保持连续性。

与事件收件箱和计时器类似，内存应该有自己的存储。在我们的产品中，例如 Claude Code 的[自动记忆](https://code.claude.com/docs/en/memory) 和 Messages API 的[记忆工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)，这是作为文件目录实现的。对于始终在线的代理，目录应映射到持久存储，通常是数据库或对象存储。这样，记忆就比工人更长寿。

根据经验，内存应该只保存代理无法再次查找的内容。如果某些东西已经存在于另一个系统中，例如问题跟踪器，您应该保存一个指针。以下是永远在线代理应存储的内存类型的详细信息：

- **用户说明：** 用户有关代理行为的任何说明都应保存在自己的文件中，并在每次运行开始时加载。用户不会总是在指导代理，因此指令必须在运行之间延续。
- **用户注释：** 代理应该保存所了解的有关用户的信息，例如他们的角色、他们的偏好或他们给出的任何更正。您可以从一个文件开始，然后随着笔记的增长移动到多个小文件。在后一种情况下，每次运行开始时仅加载索引，但代理可以在需要更多详细信息时将各个文件拉入上下文中。
- **过去的消息：** 代理应该跟踪已经告诉用户的内容，这样就不会重复任何内容。它可以将其存储在每次运行开始时加载的单独文件中，或者让工作人员加载代理与用户的最后几条消息。
- **任务进度：** 对于每项正在进行的任务，代理应保留一个进度文件，其中涵盖已完成的任务和剩余的任务。然后，任何新的运行都可以读取该文件并从上一次运行停止的地方继续。与用户注释类似，每次运行开始时仅加载索引，但代理可以在需要更多详细信息时将各个文件拉入上下文中。

下图显示了一个示例设置。

![作为文件目录的内存设置示例图。 instructions.md、index.md 和reported.md 在每次运行开始时加载，而notes/ 和progress/ 文件夹则在需要时读取。代理在运行期间写入内存。](https://assets.claude.com/e5d209d7ef9b3455dec8a27b777dc12bdf806699.png)

以上所有内容都描述了运行期间保存的内存。您还可以添加梦想，回顾过去的课程来整理记忆。梦想可以取代过时的条目，并找到只在多次运行中出现的模式。如果您有兴趣了解更多信息，我们的[关于代理记忆的帖子](https://www.anthropic.com/research/components-of-agent-memory) 对此进行了更详细的介绍。

#### 在上下文窗口内

在执行任何工作之前，代理会加载系统提示、工具定义和内存文件。每次运行中都包含初始上下文“开销”，因此我们建议保持精简并使用[提示缓存](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)来降低成本。

新会话仅以该上下文开销和触发运行的事件启动。另一方面，现有会话会带回其早期运行中的消息和工具调用。

如果会话变得太长，您可以[压缩旧消息](https://platform.claude.com/docs/en/build-with-claude/compaction) 或启动新会话。这两种方法都会丢失细节，因此任何需要保留的内容都应该一路保存到内存中。

![随时间变化的上下文动画图表。每次运行时都会出现系统提示、工具和内存的固定范围。现有会话会带回其整个记录并不断增长，直到压缩将旧记录转换为摘要。](https://assets.claude.com/48757f0a147acfe841c943674c6214d34ed4405a.gif)

### 权限

权限是永远在线的代理带来最大风险的地方。运行保留了用户的访问权限，并且按照设计，可以在无人值守的情况下运行。对于每个工具调用，代理需要决定是自行继续、阻止还是等待批准。

权限组件与其他代理使用的组件相同：

- **凭证存储：** 始终在线的代理通常需要敏感的用户凭证（例如密码或访问令牌）才能发挥作用。 [推荐模式](https://code.claude.com/docs/en/agent-sdk/secure-deployment#credential-management)是代理环境之外的代理，它将凭据添加到传出请求中。代理发送没有凭据的请求，代理在转发之前注入真实的凭据。
- **自动模式：** 始终在线的代理应该能够在没有持续用户输入的情况下工作。我们已经在 Claude Code 中使用[自动模式](https://www.anthropic.com/research/claude-code-auto-mode)解决了这个问题的一个版本。自动模式使用分类器来审查高风险操作并阻止他们识别为危险的操作，以便 Claude 可以找到更安全的方法。然而，对于最重要的决策来说，用户审查仍然是必要的。
- **推迟工具调用：** 在 Claude Code 中，[钩子可以推迟工具调用](https://code.claude.com/docs/en/hooks#defer-a-tool-call-for-later) 并等待用户的其他输入。同样的模式适用于始终在线的代理，在采取某些操作之前可能需要澄清或批准。当呼叫延迟时，运行结束并在呼叫中保存会话。该请求会显示给用户（例如，通过使用 [MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview) 构建的交互式卡），并且他们的答案作为收件箱中的事件返回。该事件启动新的运行，从而使用用户的输入恢复保存的会话。当延迟调用等待响应时，工作人员可以拾取其他事件，因此代理不会被阻止。

### 发件箱

对于大多数人工智能代理来说，响应在生成时会流式传输给用户，因此他们可以跟随 Claude 推理问题、调用工具并编写答案。

另一方面，永远在线的代理在后台完成大部分工作。用户获得结果和一些细节，而不是整个逐步分解。

![发件箱图。运行结束时无话可说，发送工具调用或询问用户的延迟工具调用。消息发送到发件箱、数据库表，然后调度程序将消息传递给用户。延迟的请求可以通过发件箱或显示在您自己的界面中。](https://assets.claude.com/700b5f3a446f22493c0307ec65751b6b2f82ccb7.png)

跑步可以通过以下三种方式之一结束：

- 代理将消息发送到发件箱，
- 代理决定不需要发送任何内容，或者
- 代理使用延迟的工具调用来请求权限或附加输入。

大多数始终在线的代理可以使用“发送”工具将消息直接传递给用户。仅当您想要调整代理的消息速度或允许代理从错误中恢复时，您才需要正式的发件箱。

发件箱是一个单独的传出消息表，类似于事件收件箱。还有一个调度程序，通常是后台服务，类似于工作人员。调度程序读取待处理的消息，决定传送什么内容，并将其发送给用户。来自延迟工具调用的请求可以通过发件箱或直接显示在界面中。

除了传递之外，调整代理发送的消息数量也很重要。发送太多的代理会变得嘈杂，而发送不足的代理会错过用户需要知道的信息。我们建议构建评估以找到适当的平衡。在实践中，代理最好一开始保持安静，然后随着时间的推移赢得更多用户的注意力。

## 一切如何组合在一起

以下是这五个基元如何组合在一起的：

![五个基元如何组合在一起的动画图。计时器和事件收件箱启动运行，运行使用会话内的内存和权限，发件箱将消息传递给用户，用户的答案作为事件返回。](https://assets.claude.com/9f8df7b2dcc9d4637d27f37dae6e40a2a5851c8a.gif)

每次运行都以收件箱中的事件开始，无论是用户消息、Webhook 还是计时器。当工作线程接收到事件时，它会开始运行并在新的或现有的会话中唤醒代理。代理读取其内存以获得基线，在其权限范围内工作以采取操作，然后用所学到的任何内容更新其内存。运行完成后，代理将一行推送到发件箱，调度程序将消息传递给用户。

Together, these form a cycle.运行可以设置一个计时器，稍后再次唤醒代理，当用户回复消息时，他们的答案会作为收件箱中的事件返回。每次运行都很短暂，但循环会无限期地持续下去，这就是让代理感觉它一直在运行的原因。
