Block 构建帮助企业和个人参与经济活动的工具，包括面向卖家的 Square 和面向消费者的 Cash App。Bradley Axen 领导 Block 的 AI 能力工作，他的团队端到端地构建 AI 产品，其中包括 Buzz——一个为 [human-agent 团队（在新标签页打开）](https://claude.com/blog/building-effective-human-agent-teams) 打造的开源工作空间——并与 Square 和 Cash App 团队协作构建面向客户的 AI 功能。Brad 与 Anthropic 谈了谈 Claude Opus 5、Claude Fable 5 这样的前沿模型如何重塑了「做一名工程师」意味着什么，Block 如何用 Fable 应用 agent 编排模式，以及当每位员工都能用上前沿模型时安全防护该扮演什么角色。

## **前沿模型在 2026 年取得了实质性进展。这项技术如何影响了你们的工作方式？**

在 Block，AI 对我们工作最大的影响在于我们怎么造东西，这一点再怎么强调都不为过。2025 年我们就看到了它的开端，那是 Claude Code 这类工具，而当时还需要大量人工介入。随着模型变得更智能，设计与工程工作转向了设计迁移方案本身、审查 agent 的行为，以及构建更多面向客户的功能——而这从来就是我们的目标。

下一阶段是通过 Block 的产品把这些变革性的技术带给客户。AI 同样能为小企业处理好那些它们不愿花时间去打理的后端运营，或帮一位 Cash App 用户管理自己的财务，创造等量的价值。有了 Claude，我们手里多了一根全新的技术杠杆，它能改变人们对「软件能为自己做什么」的期待。想象一下，如果 AI 能响应客户需求、即时构建新的界面会怎样？我认为我们的产品会越来越由 AI 按需构建，去解决具体问题。

## **随着前沿智能的演进，你的团队如今能做到哪些几个月前还做不到的事？**

Claude 新一代前沿模型带来的最大变化，是我们构建软件的规模。写代码仍然是核心环节，但现在我们会用 AI 做全公司范围的迁移。这个梦想我们都有很久了，而在 2025 年它很少能成真。在 Claude Fable 5 之前，你得有一个形状特别好的问题，前沿模型才能真正大放异彩。

2026 年，AI 已经是我们运行所有大规模代码迁移的主要方式。对我们来说，一次迁移可能意味着跨多个 repo 的成百上千个独立 pull request，以及数百万行代码。过去必须由人来协调这些工作，而模型一次只能承担一个或几个 PR。有了 Fable，我们看到它跨多个 session 编排整个工作。人类工程师负责掌舵，Fable 专注更高层的设计工作：数据模型、API spec、算法。随后它指挥多达数十个更小、更划算的模型（如 Opus 或 Sonnet）去完成具体任务，比如实际的文件编辑和跑测试。

这套账算下来很划算。早期结果显示，orchestrator 用前沿 token 做复杂的前期规划，之后把更高比例的 token 交给更小的 worker 模型，而质量没有下降。整套配置都跑在 Buzz 上——我们的开源协作工作空间，人类和 AI agent 在共享的 channel 和 thread 里并肩工作。它让我们对团队的进展有很好的可见性。

在任何一次迁移中，我们都可能合入上千个由 Fable 编排的 pull request。这让工程师能专注于困难的设计决策，而不是机械性工作。

## **什么时候你会选 Claude Fable 模型而不是其他选项？**

自那以后很多模型都开始缩小差距，Opus 也非常出色，但 Fable 发布的那一刻，你一次能接手多大的问题就发生了一次阶跃式变化。Block 的各团队被它吸引，并开始摸索再上一个抽象层级、再上一个规模层级意味着什么。

现在我们大量的讨论都在讲模型效率。这正是模型编排的用武之地：Fable 的前沿智能在你用它攻克大问题时最有价值，之后我们让更小的模型去补上代码改动里的许多细节。这是我记得的、自打我们用 LLM 写代码以来第一次，答案不再只是「100% 的时间都用最前沿的模型」。

模型编排是今天我们要造东西的一大组成部分，这也意味着我们需要新工具。有些工具非常以单次对话为中心，界面跟不上你随时有 45 个 agent 在和你一起工作。这是 Buzz 发挥作用的另一个地方。我们在 Buzz 里有多 agent 工作流，我们真的认为未来是多人同时与许多 agent 对话，由组织为例行任务挑选高效模型、为更大的问题挑选前沿模型。

## **你丢给 Fable 的最难的问题是什么？**

第一是大规模迁移：数千个 PR 级别的迁移，由 Fable 编排完成这项工作的整个系统。

第二是拿一个大型代码库——大概百万行代码的量级——然后确保它不会每天都在增加技术债。我们正在发布比以往任何时候都多的 PR。大家发布的功能和改动都多了很多，于是我们的系统积累技术债的速度前所未有，而我们一直缺少那件能提升维护速度的对应能力。这件事终于成了。我们有 agent 每天或每周对整个代码库做一遍巡检，问：「这里情况怎么样？我们需要清理和合并些什么？」

## **在广泛开放访问权限的情况下，你们如何推动高效地使用前沿模型？**

我们把最前沿模型的完整访问权限给到任何技术岗位的人，因为我们战略的一大部分就是始终在可能性的边缘上工作。

用 Fable 去改 README 里的一个拼写错误，是非常糟糕的资源使用。所以我们需要更好的系统来建议给定任务该用哪个模型。为此我们一直在构建一个自动选择器，帮员工决定什么时候用哪个模型。我们由更大与更小的前沿模型混合驱动的 multi-agent 系统也有帮助。

作为公司，我们目标的一大部分是默认就把运营做得高效，而这正是我们现在要培养的能力。我们有大量优秀的模型可选。如果每个人都擅长为合适的任务挑合适的模型，我们的成本效益就能走得更远，同时又不会拖慢速度。

## **你们会建议具体的优化策略吗，比如 effort level？**

哪怕我整天和 LLM 打交道，我几乎觉得同一个模型开 xhigh effort 就像换了一个模型，和它开 medium 判若两者。我不把 effort level 看成一条可以沿着走的谱线。Fable 开 low 可能反而比另一个模型开 xhigh 更好。所以我把它看成一张更大的网格，我们需要在其中做优化。我们基准测试的每一个用例，都不只测每个模型，而是测每个模型的每一档 effort level。

作为一个集中负责「我们怎么做 AI」的人，我需要非常明确的建议，比如：「这类任务默认用这个模型、开 high。」我们必须让工具尽可能自动地把这件事做掉，然后让专家想探索时再去探索。

## **你们如何考虑把安全防护融入今天的前沿模型使用之中？**

有些东西关键到你需要确定性保证，而我们还没准备好让 LLM 在我们的代码库里撒开跑。合入 main、部署到生产，以及 feature flag 这类相关改动，我们一律交给人来决定。agent 可以改代码，但这些改动必须通过我们的安全检查，然后要有两名人类批准这次部署。这层双重审批让 LLM 不可能自行推送这类改动。

在更低的层级上，如果员工不留神，他们能在自己笔记本上做出的事情多得惊人——那些你以为人类不会做的事，因为人类知道不该做。这把我们推向了一些有趣的方向。我认为未来的工作有很大一块是远程工作站，因为它们更容易加固安全（而且它们还能解决 LLM 带来的其他问题，比如把磁盘空间占满）。我们安全工作的很大一部分是构建默认即安全的系统：用网络 allow list 而不是 deny list 之类的做法，把最糟糕那类问题挡在外面。

我们也尽量把更多东西挪出模型回路。我们很多安全护栏都是非常便宜、高效的检查，运行时不需要模型参与。我们把它们内置到人们用来干活的界面里。有时候它就是一条 regex。越来越常见的还有更小的 classifier 也成为这套体系的一部分。

然后在日常工作中，有一整类你为了让人高效而必须放开的事情，拦截它们并不划算。我们有意让模型开 PR、审代码、查询我们的日志系统和分析型数据库，全都是为了帮人们走得更快。

这正是模型内置安全防护真正关键的地方。我指的是 Fable 和其他前沿模型被调校成不参与危险活动的那种方式，加上 [Anthropic 自己的安全 classifier（在新标签页打开）](https://www.anthropic.com/news/claude-fable-5-mythos-5)。在我们的测试里，即使有人让 Claude 去「绕开」我们的双重审批系统，它也拒绝尝试绕过。这也是我们做基准测试的一项内容。

## **对于其他与前沿模型协作的工程团队，你有什么建议？**

我们有数千名与 AI 协作的人，正在把 AI 能力的边界不断往前推。他们作为个体在学习什么有效，同时在改进自己周围的系统。比如我笔记本上装了一堆本地 skill，让我能在我们的 Square web 前端里干活，尽管我的本行并不是前端开发。当所有这些上下文和组织知识被记在系统层面而不是个人层面时，才谈得上组织的成熟。

我们的目标是把从做事的人那里学到的一切记录下来，放进一个所有人都能受益的系统，这样你每一次运行 agent，都知道它握有可为你的工作做贡献的最佳可用上下文。
