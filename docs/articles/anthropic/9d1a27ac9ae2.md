*在我们的**现场笔记**系列中，Anthropic 前沿部署工程师分享了受真实客户部署启发的最佳实践。在本文中，我们分享管理大型代码现代化项目的经验。*

[代码现代化](https://claude.com/resources/articles/how-ai-helps-break-cost-barrier-cobol-modernization)曾经被视为多年的、全体员工的努力现在可以在几个月（或[几周](https://claude.com/resources/articles/ai-code-migration)）内完成，但双方的组织工作通常保持不变。

例如，对关键银行系统的每次变更都必须经过变更管理、审查和批准。这是一个稳健的流程，因为监管机构、审计师和企业都需要它。

这些流程使关键系统值得信赖，它们是建立在人类编写每个更改并且人类会审查每个差异的假设之上的。一旦代理加速编写变更，瓶颈就会从产生变更转变为动员围绕变更的组织。

本文介绍了企业在进行现代化之前必须做的工作：定义完成的含义、变更必须携带哪些证据、经过认证的变更将如何进入生产，以及必须进行哪些阶段才能开始运行。

我们将这个过程分为六个步骤：

- **定义目标：**现代化代码必须具备的技术堆栈和行为。
- **创建证书：**更改必须满足的条件才能在目标状态下被视为正确。
- **设置促销政策：**经过认证的变更以其产生的速度进入生产的路径。
- **满足先决条件：**环境、CI/CD、审核能力和批准。
- **构建和完善代理工作流程：**自定义 Claude Code [动态工作流程](https://claude.com/resources/articles/introducing-dynamic-workflows-in-claude-code)，将现代化分布到许多产生更改的较小并行子代理工作流中。这是围绕目标、证书和促销政策建立的。
- **运行现代化：** 在代码库的一个小分区上端到端地证明工作流程，然后进行扩展。

## **第 1 步：定义目标**

**目标**是现代化的最终状态。所需的最终状态决定了您正在执行三种现代化中的哪一种，详细信息如下表所示。

### **确定现代化类型**

|类型 |它是什么 |选择何时 |目标是|
| --- | --- | --- | --- |
| **提升** |相同堆栈版本提升（例如，C++11 → C++20）。 |堆栈很好，但版本已经落后：生命周期结束、未修补的安全问题、无法再升级的依赖项。 |运行时版本和包集。 |
| **转变** |保持行为固定的跨堆栈重写（例如，COBOL → Java）。 |堆栈是要解决的问题并且行为是可信的。 |升级所需的一切，以及新代码必须遵循的语言、框架和架构约定。 |
| **重新想象** | Greenfield 重建了一个具有修改行为的新架构。 |行为需要与代码一起更改。 |转换所需的一切，加上新系统的书面行为规范。 |

组织内部经常就确定进行哪种类型的现代化进行争论。根据我们的经验，最接近生产的人希望在行为保持不变的情况下交换堆栈以遏制风险（转型现代化）。另一方通常是那些与代码库共存并希望通过现代化来偿还技术债务的工程师，以及其他希望借此机会提出新需求（重新构想现代化）的业务利益相关者。

这两种立场都是合理的，但如果问题没有得到解决，它会在稍后重新出现，作为关于给定更改是否“正确”的争论。就采取哪条路径达成共识会增加最初的摩擦，但会简化整个项目。

### **映射代码库并创建行为规范**

了解当前系统通常是定义目标的良好第一步。提取旧代码的实际功能并创建当前行为的清单，可以轻松决定是否应更改或删除某些部分，从而确定现代化是转型还是重新构想。这也经常揭示未知的业务逻辑和边缘情况。

Claude可以通过[映射依赖关系并记录没人记得构建的工作流程](https://claude.com/resources/articles/how-ai-helps-break-cost-barrier-cobol-modernization) 来完成大部分发现工作。 [代码现代化插件](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization) 的 *assess、map、*和 *extract-rules* 命令通过源引用挖掘业务规则，然后工程师可以对其进行审查。

然而，仅Claude的发现可能无法捕捉到遗留系统的完整行为方式。与业务用户和开发人员的访谈以及内部文档可以填补这些空白。上下文收集可能需要一些时间，但上下文的质量会影响工作流程稍后做出的每个决策。

对于重新构想，定义目标需要额外的工作：应写下详细的行为规范并与用户组达成一致。

### **确立项目的理由和目标**

除了定义目标之外，组织还应该考虑为什么现代化值得进行。对遗留系统进行现代化改造可以减少持续的维护和运营成本，但是，根据我们的经验，降低成本并不是大多数现代化项目的驱动目标。

> “降低风险往往是最重要的现代化效益。在讨论是否进行该项目时，请考虑不进行现代化改造的风险。”

例如，带有未修补漏洞的系统可能意味着网络漏洞或中断，严重程度足以使企业本身面临风险。不受支持的运行时间或了解系统的工程师数量不断减少都会加剧风险。

像 Claude Code 这样的代理编码工具缩短了现代化的时间，但预算仍然难以估计，这导致了惰性。我们已经公布了一些[大规模现代化](https://claude.com/resources/articles/ai-code-migration) 的成本，[其他](https://claude.com/customers/lg-cns) 也一样。这些可以作为粗略的基准，我们在本指南的底部提供了有关预算预测的额外指导。

启动这些项目的主要挑战通常是建立拥有该系统的团队以及依赖该系统的团队的内部共识和承诺。构建业务案例并设定项目目标（通常是在领导层）使这部分过程变得更容易。这也有助于在随后的证书和促销政策中进行权衡。当利益相关者对变革可能带来多大风险存在分歧时，不现代化的风险就是平衡因素。

## **步骤 2：定义证书**

**证书**是每次现代化变革都必须满足的一组条件或测试。选择能够提供最强累积证据的条件，证明更改对于目标而言是正确的。

每个条件都应该可以在没有人工参与的情况下进行检查，因此代理工作流程可以迭代更改，直到满足证书要求，或者如果不能满足要求，则将其标记为供人工审核。

证书中包含的内容取决于目标，但通常会从此列表中提取：

- 原始测试套件通过
- Claude编写的现代化期间编写的测试全部通过
- 测试覆盖率达到商定的阈值
- 绩效基准保持在商定的范围内
- Claude 的独立对抗性审查，每个审查都在一个新的上下文窗口中进行，没有发现任何阻塞问题
- 对于用户界面，Claude驱动的计算机使用没有发现回归
- 当前版本和目标版本从相同的输入产生相同的输出，可以是实时的、录制的或Claude生成的
- 当前版本和目标版本之间的持续状态和线路格式往返
- 更改在约定的时间内在暂存中运行，错误率、延迟或警报不会回归
- 静态分析和安全扫描没有显示新发现
- 对于已编译的目标，构建是干净的并且类型检查通过

> “与将审查变更并将其推广到生产中的人员一起编写证书。引入现在依赖于代码库的开发人员、用户组和业务主管，而证书和代理工作流程仍在设计中。”

他们的专业知识决定了证书的衡量标准，而他们的早期参与则在变更进入审核时赢得了他们的支持。对完成的证书的一个很好的检查是他们是否愿意单独合并证书的证据。如果他们在里面看到了自己的酒吧，那么第3步的促销政策就可以宽松一些。

证书检查的内容以及检查方式取决于现代化类型。

- **对于提升现代化**，奇偶校验是针对原始代码库的，原始测试套件可以是证书的核心。
- **对于转换现代化，**奇偶校验也针对原始代码库，但原始测试套件很少在新堆栈上运行。生产流量的重放、新旧之间的差异测试以及产品并行部署可以完成大部分工作。
- **为了重新构想现代化**，证书锚定在行为规范中。这是最难的情况。规范不如现有系统客观，因此涉及更大程度的模型判断，这可能导致更多可变的结果。在这里，该证书依赖于根据规范编写的测试、Claude（Claude）根据秒检查每个更改的独立对抗性审查，以及新系统保留旧系统行为的差异检查。随着规范的澄清，预计会修改证书：规范中的差距首先出现在此处。

较旧的系统通常测试覆盖范围较薄、测试不稳定且遥测很少。定义证书的一部分就是识别这些差距。如果很难支持强大的证书，那么这一步要做的最有用的事情之一就是使用 Claude 来构建缺失的证据，无论是建立产品并行设置、构建重放工具还是编写更多测试。

## **第三步：制定促销政策**

代理产生变更的速度远远快于任何人类团队逐一审查它们的速度。晋升政策是一种分层审查路径——提前写下并商定——它设定了变更的人工审查深度，以便现代化可以在可接受的时间表上完成。

与证书一样，与审阅者一起执行此步骤，并尽可能将其融入组织现有的变更管理流程中。细节因组织及其面临的风险权衡而异，但有一些规则在任何地方都适用：

- **根据爆炸半径和代理信心进行等级更改。** 使用您的组织自己的更改或风险分类（如果有）。对关键路径进行全面的人工审查。
- **在源头修复重复出现的标志。 **随着时间的推移对标记的变化进行分组和分析。当同一类型的标志不断重复出现时，请在代理工作流程或证书中修复原因，而不是逐一检查。
- **与审阅者一起设计输出格式。 **同意哪些信息和格式可以使审核速度最快，以及哪些信号比其他信号更有信心。让他们查看第 5 步中的早期示例输出。
- **有效分配中小企业时间**。中小企业不会阅读每一个最终的差异，但他们的判断仍然是稀缺的输入。让他们可以轻松地直接查看最高风险层中的更改以及每个层中标记的代理决策，而无需费力处理巨大的差异。然后，少量的专家时间涵盖了风险最大的变更。

其中许多规则通过让 SME 尽早参与项目来提前加载 SME 时间。在全面现代化开始之前，他们的反馈会调整证书和代理工作流程。

他们对样本的签字也进一步证明了在高置信度的情况下采用更轻松的审查路径的理由。这与传统的非代理模式相反，传统的非代理模式是在最后进行审查。

促进政策还应反映现代化在速度和审查深度之间的位置。现代化进程必须在严格的截止日期前进行，例如运行时失去支持，需要更快的策略、更少的人工审查以及明确的协议来接受每次更改的更多风险。

较长时间上的现代化可以承受更深入的人工审查和更慢的切换。利益相关者将根据他们的风险偏好和约束条件，选择不同的点，因此值得在工作开始之前锁定。

在受监管的环境中，对任何变化采取更轻松的人工审查路径可能会引起真正的不适。个人审批者犹豫是否批准，因为他们面临着糟糕变革的风险，而领导层则面临着系统老化的更大风险。

根据我们的经验，晋升政策的指示最好来自组织高层。最好事先达成一致，这样对进入生产的错误的责任是共同承担的，而不是归咎于批准变更的人。

> “所有这一切仍然取决于足够详细的证书来作为真正的证据，以及审阅者充分了解 Claude 如何实现更改并足以信任它。”

## **第 4 步：满足先决条件**

此步骤的大部分内容是通过现代化之外的团队进行的：主机的平台或基础设施、测试能力的质量保证或发布工程、批准的安全性和合规性。每个团队通常都有自己的待办事项或审批流程，因此一旦确定了需求，就尽早开始对话，通常是在步骤 1 到步骤 3 仍在进行时。

### **环境**

- 专用远程主机，用于使用代码库和 Claude 可访问的其他相关源运行工作流程
- 证书要求的测试能力
- 任何增强证书的内容：生产遥测、产品并行设置或用于重放的生产数据

### **代码库和 CI/CD**

- 代码库的依赖关系图，以构建和编译日志为基础；进口分析；或运行时痕迹。注意：插件的 *map* 命令是一个很好的起点，但根据代码库的大小和年龄，可能需要完成更广泛的前期工作
- 作为目标定义的一部分，有计划地处理任何依赖项或包
- 如果需要，可以添加到 CI/CD 的兼容性检查
- 如果您要进行现代化改造，则需要商定的代码冻结政策
- 针对活跃开发人员的沟通计划，涵盖任何代码冻结和新的兼容性要求

### **团队和审查**

- 其他团队根据代码库参与方式达成的协议，例如签署证书或根据促销政策进行审核，并留出审核时间

### **安全性与合规性**

- 批准用于源代码的 Claude Code 的模型访问路径
- 代理工作流程的最低权限访问：仅写入现代化分支，无生产凭据
- 现代化分支中的秘密和 PII 被清除或掩盖
- 每项变更均可追踪，并与代理成绩单和证书证据相关联
- 对新依赖项的许可证和漏洞检查

## **步骤 5：构建和完善代理工作流程**

使用 Claude Code 开发自定义的[动态工作流程](https://claude.com/resources/articles/introducing-dynamic-workflows-in-claude-code) 以实现代码库的现代化。

我们建议从[代码现代化插件](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization) 开始，并将工作流程可能需要的所有内容放在文件系统或 MCP 上，以便 Claude 可以访问它。这包括目标、证书、升级策略、代码库、文档以及证书所需的任何数据源或工具。您也可以将这篇文章提供给 Claude 作为上下文。这构成了该项目的中心知识库。

有了这些，[构建现代化工作流程](https://claude.com/resources/articles/ai-code-migration) 就很容易了。让中小企业根据需要审查 Claude 的工作，包括任何特定于代码库的技能或在下游依赖它之前提取的规则。

通过将其应用到代码库的一小部分来优化您所构建的内容，并由中小企业审查其产生的更改、代理的流程以及满足证书的证据。

> “当问题出现时，您应该修改工作流程，而不是每次更改。我们的目标是相信，一旦扩展，更改将几乎在所有地方都满足证书要求，并且审阅者将在升级政策下轻松合并。”

## **第 6 步：运行现代化**

首先，对一小部分代码库进行端到端的现代化改造，包括通过推广政策来审查和落地变更。在价格仍然便宜的情况下修复任何不起作用的问题，重复该过程直到您有信心为止，然后扩展到完整的代码库。

虽然转型和重新构想现代化涉及在现有系统旁边构建目标并在完成后进行切换，但提升还有第二种选择：在继续开发的同时在实时代码库上进行现代化。

当系统无法停机，或者代码库变化如此之快以至于很难保持单独的现代化副本最新时，这是通常的选择。在这种情况下，我们看到的工作是将代码库从叶子向内分割成逻辑分区；一次冻结和现代化一个分区；并控制 CI/CD，以便新的提交在现代化后无法撤消分区。

## **关于成本的说明**

我们经常被问到这样的现代化需要花费多少代币。每项现代化工作都是不同的，但主要成本驱动因素包括：

- 需要读取多少代码库以及需要更改多少代码库；
- 证书的参与程度（在受监管的环境中，验证而不是写入更改通常占较大份额）；
- 证书需要多少新的测试编写和测试修复；和
- 在运行过程中，有多少协调工作来自于您周围合并的其他团队。

> “当完成一小部分代码库的现代化时，测量代币使用情况，并用它来推断运行的其余部分。将飞行员看不到的任何东西（例如实时代码库上的协调）视为未知数。通过这种方式，您可以估算全面现代化的成本底线。”

试点的测量结果还显示了在哪里优化代理工作流程以降低成本。找到工作流程中消耗最多令牌的部分，并考虑如何提高它们的效率。将计算量大的验证信号移到更便宜的门后面，这样它们只有在更简单的检查通过后才运行。

考虑使用 Sonnet 等模型来平衡证书全面检查的机械、大批量工作的成本和能力。保留更智能的模型来进行硬转换和验证正确性的对抗性评论。

当较便宜的模型无法满足证书要求时，您还可以升级到更昂贵的模型，但在试点时要仔细分析重试率，因为几次便宜的尝试可能比一次昂贵的尝试花费更多。如果您授予 Claude 访问工作流程和试点数据的权限，它可以与您一起完成大部分分析工作。

## **超越现代化**

现代化的代码库是一种输出。其他的是产生它的工作流程、一份关于什么是正确的书面证书、您的变更管理流程已经接受的升级政策，以及每个落地变更的证据跟踪。将剧本编码为可重用资产，以便该模式已就位以供下次升级或重写。
