*在我们的 **Notes from the Field **系列中，Anthropic 的 forward deployed engineers 分享来自真实客户部署的最佳实践。本文中，我们分享管理大型代码现代化项目的经验。*

[代码现代化](https://claude.com/resources/articles/how-ai-helps-break-cost-barrier-cobol-modernization)项目过去往往被规划为耗时数年、全员投入的工作，现在几个月（甚至[几周](https://claude.com/resources/articles/ai-code-migration)）就能完成，但组织层面的工作往往还是一样多。

例如，对关键银行系统的每一次变更都必须经过变更管理、评审和批准。这是一个稳健的流程，因为监管机构、审计人员和企业本身都要求如此。

正是这些流程让关键系统值得信任，而它们建立在一个假设之上：每一项变更都由人编写，每一个 diff 都由人评审。一旦 agent 加速了变更的编写，瓶颈就从产出变更转移到围绕变更调动组织。

本文讨论企业在现代化真正开始之前必须完成的工作：定义“完成”意味着什么、一项变更必须附带哪些证据、已认证的变更如何进入生产，以及必须提前准备好哪些条件，让整个流程得以启动。

我们把这一过程拆成六步：

- **定义目标：** 现代化后的代码必须具备的技术栈和行为。
- **创建证书：** 变更要达到什么条件，才算在目标状态下是正确的。
- **设定晋级策略：** 已认证的变更按产出速度进入生产的路径。
- **准备好前置条件：** 环境、CI/CD、评审能力和审批。
- **构建并完善 agentic 工作流：** 自定义的 Claude Code [动态工作流](https://claude.com/resources/articles/introducing-dynamic-workflows-in-claude-code)，它把现代化工作分散到许多更小的并行子 agent 工作流中，由它们产出变更。这个工作流围绕目标、证书和晋级策略构建。
- **执行现代化：** 先在代码库的一小部分上端到端验证工作流，然后再扩大规模。

## **第 1 步：定义目标**

**目标**是现代化的最终状态。期望的最终状态决定了你是在做三类现代化中的哪一类，详见下表。

### **确定现代化类型**

| 类型 | 是什么 | 何时选择 | 目标是 |
| --- | --- | --- | --- |
| **Uplift** | 同技术栈内的版本升级（例如 C++11 → C++20）。 | 技术栈本身没问题，但版本已经落后：运行时已到 end-of-life、安全问题未修补、依赖无法再升级。 | 一个运行时版本和一套软件包集合。 |
| **Transform** | 跨技术栈重写，保持行为不变（例如 COBOL → Java）。 | 技术栈是待解决的问题，而行为是可信的。 | uplift 所需的全部内容，再加上新代码必须遵循的语言、框架和架构约定。 |
| **Reimagine** | 在新架构上从零重建，并改变行为。 | 行为需要随代码一起改变。 | transform 所需的全部内容，再加上一份为新系统编写的行为规格。 |

该做哪一类现代化，往往会在组织内部引发争论。以我们的经验，最贴近生产的人希望只替换技术栈、行为保持不变，以控制风险（transform 现代化）。另一方通常是长期与这套代码库打交道的工程师，他们希望借现代化偿还技术债；还有一些业务相关方，希望趁这个机会提出新需求（reimagine 现代化）。

两种立场都有道理，但如果这个问题悬而未决，它之后会重新浮现，变成对某项变更是否“正确”的争论。就选哪条路径达成共识，会增加前期的摩擦，但会让整个项目更顺畅。

### **梳理代码库并编写行为规格**

理解当前系统，通常是定义目标的一个不错的起点。把旧代码实际做了什么提取出来，并建立一份当前行为清单，就能更容易判断哪些部分应当修改或舍弃，从而确定这次现代化是 transform 还是 reimagine。这一步也常常会暴露出此前未知的业务逻辑和边缘情况。

Claude 可以完成其中大部分探查工作，比如[梳理依赖关系，并为那些没人记得是谁搭建的工作流补上文档](https://claude.com/resources/articles/how-ai-helps-break-cost-barrier-cobol-modernization)。[code modernization plugin](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization) 的 *assess*、*map* 和 *extract-rules* 命令会挖掘业务规则并附上源码引用，供工程师复核。

不过，仅靠 Claude 的探查可能无法完整还原一个遗留系统的全部行为。与业务用户和开发人员的访谈，以及内部文档，可以补上这些空白。前期收集上下文可能需要一些时间，但上下文的质量会影响工作流之后做出的每一个决定。

如果是 reimagine，定义目标还需要额外的工作：应当写下一份详细的行为规格，并与用户组达成一致。

code modernization plugin 中的一个交互式依赖关系图示例。

### **确立项目的立项依据和目标**

在定义目标的同时，组织还应该考虑这项现代化到底为什么值得做。改造遗留系统可以降低持续维护和运营成本，但以我们的经验，削减成本并不是大多数现代化项目的主要驱动力。

> “风险降低往往是现代化最重要的收益。在讨论要不要开展这个项目时，请考虑不做现代化会带来哪些风险。”

例如，一个系统带着未修补的漏洞，可能意味着一次网络入侵，或一次严重到让企业本身陷入危险的中断。运行时已不受支持，或者了解这套系统的工程师越来越少，都会加剧这种风险。

像 Claude Code 这样的 agentic 编码工具缩短了现代化的时间线，但预算仍然难以估算，这导致组织倾向于拖延。我们已经公开过一些[大规模现代化](https://claude.com/resources/articles/ai-code-migration)的成本，[其他公司](https://claude.com/customers/lg-cns)也做过同样的事。这些可以作为粗略的基准，本指南末尾还提供了关于预算预测的更多建议。

启动这类项目时，主要的挑战通常是在组织内部建立共识，并获得系统归属团队和依赖该系统的团队的承诺。把商业论证做扎实，并设定项目目标——这往往由领导层来做——能让这部分工作更容易。这也有助于为后续证书和晋级策略中的取舍定好锚点。当相关方对一项变更能承担多少风险有分歧时，不做现代化的风险就是与之对冲的砝码。

## **第 2 步：定义证书**

**证书**是每一项现代化变更都必须满足的一组条件或测试。挑选那些能提供最强累积证据、证明变更相对于目标而言是正确的条件。

每个条件都应该能在没有人工介入的情况下检查，这样 agentic 工作流就能反复迭代一项变更，直到满足证书；如果满足不了，就把它标记出来交给人工评审。

证书里包含什么取决于目标，但通常会从下面这份清单中选取：

- 原有测试套件全部通过
- 现代化过程中由 Claude 编写的测试全部通过
- 测试覆盖率满足约定阈值
- 性能基准保持在约定范围内
- 由 Claude 在各自全新的上下文窗口中做的独立对抗性审查未发现阻塞性问题
- 对于用户界面，由 Claude 驱动的 computer use 未发现回归
- 当前版本与目标版本对相同输入产生相同输出，输入可以是实时流量、录制流量或 Claude 生成的输入
- 持久化状态与传输格式在当前版本和目标版本之间可以双向往返
- 变更在 staging 中运行约定的一段时间，错误率、延迟或告警均无回归
- 静态分析和安全扫描未发现新问题
- 对于编译型目标，构建干净、类型检查通过

> “请与将来负责评审和把变更推进到生产的人一起编写证书。在证书和 agentic 工作流仍在设计阶段时，就把依赖这套代码库的开发人员、用户组和业务负责人拉进来。”

他们的专业判断会影响证书衡量什么，而他们的早期参与，正是日后变更进入评审时他们愿意认可的基础。检验一份证书是否合格的一个好办法是：他们是否愿意仅凭证书给出的证据就合并变更。如果他们能从中看到自己认可的标准，第 3 步的晋级策略就可以更轻量。

证书以什么为基准、如何检查，取决于现代化类型。

- **对于 uplift 现代化**，一致性的基准是原始代码库，原有测试套件可以作为证书的核心。
- **对于 transform 现代化，** 一致性的基准同样是原始代码库，但原有测试套件很少能在新技术栈上运行。取而代之的主要手段是生产流量回放、新旧版本之间的差分测试，以及与生产并行的部署。
- **对于 reimagine 现代化**，证书以行为规格为锚点。这是最难的一类。规格不像现有系统那样可以客观地做 diff，因此会涉及更大程度的模型判断，结果也可能更不稳定。这种情况下，证书依赖根据规格编写的测试、由 Claude 做的独立对抗性审查（逐项检查变更是否符合规格），以及在新系统保留旧系统行为之处做的差分检查。要做好随着规格逐步明确而修订证书的准备：规格中的空白会首先在这里暴露出来。

老旧系统往往测试覆盖薄弱、测试不稳定、遥测数据很少。定义证书的一部分工作就是识别这些缺口。如果很难支撑一份强证书，这一步最有用的做法之一，就是用 Claude 补齐缺失的证据——无论是搭建与生产并行的环境、构建回放 harness，还是编写更多测试。

## **第 3 步：设定晋级策略**

Agent 产出变更的速度，会远远超过任何人类团队逐个 diff 评审的速度。晋级策略是一条分层的评审路径——提前写下来并达成一致——它规定了一项变更需要多深的人工评审，从而让现代化能在可接受的时间内完成。

和证书一样，这一步要和评审人员一起做，并尽可能嵌入组织现有的变更管理流程。具体细节会因组织和它面临的风险取舍而不同，但有几条规则普遍适用：

- **按影响范围和 agent 置信度对变更分层。** 如果组织有自己的变更分类或风险分类，就用它。关键路径上保留完整的人工评审。
- **从源头修复反复出现的标记。** 对一段时间内被标记的变更进行归类和分析。当同一类标记反复出现时，去修复 agentic 工作流或证书中的根因，而不是逐条评审。
- **与评审人员一起设计输出格式。** 共同商定哪些信息、什么格式能让评审最快完成，以及哪些信号比其他信号更能增强信心。让他们在第 5 步提前评审样例输出。
- **有效分配 SME 时间**。SME 不会阅读每一份最终 diff，但他们的判断仍然是稀缺的输入。要让他们能直接跳到最高风险层级的变更，以及其中每一项被标记的 agent 决策，而不必在大量 diff 中跋涉。这样少量专家工时就能覆盖风险最高的那部分变更。

上述许多规则都会在项目早期就投入 SME 的时间。他们的反馈会在全面现代化开始之前调整证书和 agentic 工作流。

他们对样例的签字确认，也会成为高置信度场景下采用更轻量评审路径的进一步依据。这与传统的非 agentic 模式正好相反——那种模式下评审发生在最后。

一项变更从生成到生产的路径。

晋级策略还应该反映这项现代化在速度与评审深度之间的位置。一项赶着硬性截止日期（例如运行时即将失去支持）的现代化，需要更快的策略、更轻的人工评审，并明确同意为每项变更承担更多风险。

时间线更长的现代化则可以承受更深的人工评审和更慢的切换。相关方会根据各自的风险偏好和约束，落在这一区间的不同位置上，因此值得在开工之前就把这一点确定下来。

在受监管的环境中，对任何变更采用更轻的人工评审路径都可能引起切实的不适。具体审批人会犹豫要不要签字，因为他们要为一次糟糕的变更承担风险；而领导层承担的则是系统老化的更大风险。

以我们的经验，最好是让晋级策略的指令来自组织最高层。最好也提前就达成一致，这样当某个缺陷流入生产时，责任是共担的，而不是被归到批准那次变更的人头上。

> “所有这些仍然取决于一份足够详细、能作为真实证据的证书，以及真正理解 Claude 是如何得出某项变更、从而能信任它的评审人员。”

## **第 4 步：准备好前置条件**

这一步的很多工作要由现代化之外的团队完成：平台或基础设施团队负责主机，QA 或发布工程团队负责测试能力，安全与合规团队负责审批。这些团队通常各有自己的待办队列或审批流程，所以要尽早开启沟通——一旦确定了需求就去找他们，往往在第 1 到第 3 步还在进行时就开始了。

### **环境**

- 一台专用的远程主机，用来运行工作流，并让 Claude 能够访问代码库及其他相关来源
- 证书所要求的测试能力
- 一切能增强证书的东西：生产遥测、与生产并行的环境，或用于回放的生产数据

### **代码库与 CI/CD**

- 一份基于构建日志和编译日志、import 分析或运行时追踪得到的代码库依赖关系图。注意：plugin 的 *map* 命令是一个不错的起点，但取决于代码库的规模和年代，可能需要预先做更多工作
- 作为目标定义的一部分，规划好如何处理任何依赖或软件包
- 需要时可供加入 CI/CD 的兼容性检查
- 如果是在原地进行现代化，需要一份达成一致的代码冻结政策
- 面向在职开发者的沟通计划，涵盖任何代码冻结和新的兼容性要求

### **团队与评审**

- 与依赖该代码库的其他团队就他们如何参与达成一致，例如为证书签字确认，或在晋级策略下参与评审，并预留评审人时间

### **安全与合规**

- 一条为 Claude Code 获批、可用于源代码的模型访问路径
- 为 agentic 工作流配置最小权限：只能写入现代化分支，不得持有生产凭证
- 从现代化分支中清除或遮蔽密钥和 PII
- 每一项变更都可追溯，PR 关联到 agent 执行记录和证书证据
- 对新增依赖做许可证与漏洞检查

## **第 5 步：构建并完善 agentic 工作流**

用 Claude Code 为代码库的现代化开发一个定制的[动态工作流](https://claude.com/resources/articles/introducing-dynamic-workflows-in-claude-code)。

我们建议从 [code modernization plugin](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization) 开始，并把工作流可能需要的一切放到文件系统上或通过 MCP 暴露出来，让 Claude 能够访问。这包括目标、证书、晋级策略、代码库、文档，以及证书所需的任何数据源或工具。你也可以把本文交给 Claude 作为上下文。这就形成了项目的中心知识库。

有了这些，[构建现代化工作流](https://claude.com/resources/articles/ai-code-migration)就是容易的部分。让 SME 按需评审 Claude 的工作，包括任何针对特定代码库的 skills 或提取出的规则，之后才能让下游依赖它们。

把已经搭好的东西应用到代码库的小部分区域上加以打磨：让 SME 评审它产出的变更、agent 的过程，以及证书已满足的证据。

> “当问题出现时，你应该修改工作流，而不是逐项修改变更。目标是确信：在扩大规模之后，变更几乎在任何地方都能满足证书，评审人员也愿意在晋级策略下合并。”

## **第 6 步：执行现代化**

首先，在代码库的一小部分上端到端完成现代化，包括通过晋级策略评审并落地这些变更。趁着成本还低，修好任何跑不通的地方，重复这个过程直到你有信心，然后再扩展到整个代码库。

transform 和 reimagine 现代化需要一边在现有系统旁构建目标系统，完成后再切换；而 uplift 还有第二种选择：在开发继续的同时，在现网代码库上原地进行现代化。

当系统不能停机，或者代码库变化太快、难以让一份独立的现代化副本保持最新时，这通常是常规选择。在这种情况下，我们见过可行的做法是把代码库从叶子节点向内拆成多个逻辑分区；一次冻结并现代化一个分区；并对 CI/CD 设卡，使新提交无法撤销已经完成现代化的分区。

## **关于成本**

我们经常被问到，这样一次现代化要花多少 token。每一次现代化的具体情况都不同，但主要的成本驱动因素包括：

- 代码库中有多少需要阅读、有多少需要修改；
- 证书的复杂程度（在受监管的环境中，验证通常比编写变更占更大比重）；
- 证书要求编写多少新测试、修复多少测试；
- 运行期间其他团队在你周围合并代码，带来多少协调工作。

> “在代码库的一小部分上完成现代化时，测量 token 用量，并用它来推算剩余部分。把试点看不到的东西，例如在现网代码库上的协调工作，当作未知项。这样你就能得到完整现代化的成本下限估计。”

试点的测量结果还能指出 agentic 工作流在哪些地方可以优化成本。找出工作流中消耗 token 最多的部分，考虑如何让它们更高效。把计算密集型的验证信号放到更便宜的关卡之后，让它们只在更容易的检查通过后才运行。

对于证书能够完整检查的机械性、大批量工作，可以考虑使用像 Sonnet 这样兼顾成本与能力的模型。把更智能的模型留给困难的转换，以及验证正确性的对抗性评审。

当较便宜的模型无法满足证书时，你也可以升级到更贵的模型，但在试点期间要仔细分析重试率，因为多次便宜尝试的成本可能超过一次昂贵尝试。如果你让 Claude 同时访问工作流和试点数据，它可以和你一起完成其中大部分分析。

## **现代化之外**

现代化后的代码库只是产出之一。其他产出还包括：产出它的那套工作流、一份写明何为正确的书面证书、一份已经被你的变更管理流程接受的晋级策略，以及每一次落地变更的证据链。把这套打法固化为可复用的资产，这样下一次升级或重写时，模式已经就位。

我们的 forward deployed engineers 会与客户一起，在他们最关键的系统上走完这些步骤。如果你正在准备一次现代化，[请联系我们的团队](https://claude.com/contact-sales)。
