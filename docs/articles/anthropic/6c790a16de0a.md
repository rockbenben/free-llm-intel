# 揭秘 AI agent 的评测

发布于 2026 年 1 月 9 日

让 agent 有用的那些能力，也让它们难以被评估。在各部署中奏效的策略，用多种技术的组合来匹配它们所衡量系统的复杂性。

## 引言

好的评估能帮助团队更有信心地交付 AI agent。没有它们，很容易陷入被动循环——在生产环境里才抓到问题，而修复一处失败又制造了其他问题。评估让问题和行为变化在影响用户之前变得可见，而它们的价值在 agent 的生命周期上不断累积。

正如我们在[构建高效的 agent](https://www.anthropic.com/engineering/building-effective-agents)中所描述的，agent 跨多轮运作：调用工具、修改状态、并基于中间结果适应。正是让 AI agent 有用的那些同样能力——自主性、智能和灵活性——也让它们更难评估。

通过我们的内部工作、以及与站在 agent 开发前沿的客户，我们学会了如何为 agent 设计更严谨、更有用的评估。以下是在一系列 agent 架构和真实部署用例中行之有效的方法。

## 评估的构造

一个**评估**（「eval」）是对一个 AI 系统的测试：给 AI 一个输入，然后对其输出施加打分逻辑来衡量成功。在本文里，我们聚焦于能在开发期间、无需真实用户运行的**自动化评估**。

**单轮评估**很直白：一个 prompt、一个响应、一套打分逻辑。对较早的 LLM，单轮、非 agentic 的评估是主要的评估方法。随着 AI 能力进步，**多轮评估**变得越来越常见。

在一个简单评估里，agent 处理一个 prompt，评审员检查输出是否符合预期。对更复杂的多轮评估，一个编码 agent 收到工具、一个任务（在本例里是构建一个 MCP 服务器）和一个环境，执行一个「agent 循环」（工具调用和推理），并把实现更新到环境里。打分随后用单元测试来验证那个可用的 MCP 服务器。

**Agent 评估**要复杂得多。Agent 跨多轮使用工具、修改环境中的状态并边做边调整——这意味着错误会传播并叠加。前沿模型也能找到超越静态评估极限的创造性解法。例如，Opus 4.5 通过[发现](https://www.anthropic.com/news/claude-opus-4-5)政策中的一个漏洞，解决了一道关于订机票的 [𝜏2-bench](https://github.com/sierra-research/tau2-bench) 问题。按字面它「失败」了评估，但实则为用户想出了一个更好的解法。

在构建 agent 评估时，我们用以下定义：

- 一个**任务**（亦称**问题**或**测试用例**）是一项有定义输入和成功标准的单一测试。
- 对任务的每次尝试是一个**试验（trial）**。因为模型输出在运行之间会变化，我们跑多个试验以产出更一致的结果。
- 一个**评分器（grader）**是给 agent 表现某方面打分的逻辑。一个任务可以有多个评分器，每个含多个断言（有时叫**检查（check）**）。
- 一个**文字记录（transcript）**（也叫 trace 或 trajectory）是一次试验的完整记录，包括输出、工具调用、推理、中间结果，以及任何其他交互。对 Anthropic API，这是一次评估运行结束时完整的 messages 数组——含评估期间对 API 的所有调用和所有返回的响应。
- 一个**结果（outcome）**是试验结束时环境里的最终状态。一个订机票的 agent 可能在文字记录末尾说「你的机票已订好」，但结果在于环境的 SQL 数据库里是否存在一条预订。
- 一个**评估 harness** 是端到端运行评估的基础设施。它提供指令和工具、并发运行任务、记录所有步骤、给输出打分、并汇总结果。
- 一个**agent harness**（或 scaffold）是让模型能作为 agent 行动的系统：它处理输入、编排工具调用、并返回结果。当我们评估「一个 agent」时，我们评估的是 harness *和* 模型协同工作。例如，[Claude Code](https://claude.com/product/claude-code) 是一个灵活的 agent harness，我们通过 [Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 使用它的核心原语，来构建我们的[长时间运行 agent harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。
- 一个**评估套件**是一组旨在衡量特定能力或行为的任务集合。套件里的任务通常共享一个宽泛的目标。例如，一个客服评估套件可能测试退款、取消和升级。

## 为什么要构建评估？

当团队初次开始构建 agent 时，靠手动测试、[内部试用](https://en.wikipedia.org/wiki/Eating_your_own_dog_food) 和直觉的组合，它们能意外地走得很远。更严谨的评估甚至可能像是拖慢交付的负担。但在早期原型阶段之后、一旦 agent 上了生产并开始规模化，无评估构建就开始崩解。

崩解点常出现在用户反馈说 agent 在改动后变差了、而团队「蒙眼飞行」、除了猜测和检查别无验证之途。没有评估，调试是被动的：等抱怨、手动复现、修 bug、并希望别处没回归。团队无法区分真实的回归与噪声，无法在交付前对数百个场景自动测试改动，也无法衡量改进。

我们见过这一演进反复上演。例如，Claude Code 起初基于 Anthropic 员工和外部用户的反馈快速迭代。随后我们加入了评估——先是针对简洁和文件编辑这类窄领域，然后是像过度设计这类更复杂的行为。这些评估帮助识别问题、指导改进、并聚焦研究-产品协作。与生产监控、A/B 测试、用户研究等结合，评估为 Claude Code 在规模化时持续改进提供了信号。

在 agent 生命周期的任何阶段，写评估都有用。早期，评估迫使产品团队明确 agent 的成功意味着什么；后期，它们帮助维持一致的质量门槛。

[Descript](https://www.descript.com/) 的 agent 帮用户编辑视频，于是他们围绕一次成功编辑工作流的三个维度构建评估：别搞坏东西、按我说的做、把它做好。他们从手动打分演进到由产品团队定义标准、并定期做人工校准的 LLM 评分器，如今定期跑两套独立的套件，分别用于质量基准和回归测试。[Bolt](https://bolt.new/) 的 AI 团队起步构建评估较晚，在他们已有一个广泛使用的 agent 之后。在 3 个月里，他们建了一套评估系统：运行他们的 agent 并用静态分析给输出打分、用浏览器 agent 测试应用、并为像指令遵循这类行为使用 LLM 评审员。

有些团队在开发之初就创建评估；另一些则在规模化时、评估成为改进 agent 的瓶颈时才加上。评估在 agent 开发之初尤其有用，因为它显式地编码了期望行为。两位工程师读同一份初始规格，可能对 AI 该如何处理边缘情形得出不同的理解。一套评估套件能消除这种歧义。无论它们何时创建，评估都帮助加速开发。

评估也塑造你采用新模型的速度。当更强的模型出现时，没有评估的团队会面临数周的测试，而有评估的竞争对手能迅速判定模型的长处、打磨他们的 prompt、并在几天内升级。

一旦评估存在，你就免费获得基线和回归测试：延迟、token 用量、每任务成本和错误率都能在一个静态的任务库上被跟踪。评估也能成为产品和研究团队之间带宽最高的沟通渠道，定义研究者可据以优化的指标。显然，评估的收益远超跟踪回归和改进。它们的复利价值容易被忽视，因为成本在前、而收益在后累积。

## 如何评估 AI agent

我们看到今天被规模化部署的若干常见 agent 类型，包括编码 agent、研究 agent、computer use agent 和对话式 agent。每一类都可能部署在五花八门的行业里，但可以用相似的技术来评估。你不必从零发明一种评估。下面几节描述了对若干 agent 类型被验证过的技术。把这些方法当作基础，再扩展到你的领域。

### agent 评估器的类型

agent 评估通常结合三种评估器：基于代码的、基于模型的和人类的。每个评估器衡量文字记录或结果中的某一部分。有效评估设计的一个要素，是为这份工作选对评估器。

基于代码的评估器

| **方法** | **长处** | **短处** |
| --- | --- | --- |
| • 字符串匹配检查（精确、正则、模糊等）• 二元测试（fail-to-pass、pass-to-pass）• 静态分析（lint、类型、安全）• 结果核验 • 工具调用核验（用了哪些工具、参数）• 文字记录分析（用了多少轮、token 用量） | • 快 • 便宜 • 客观 • 可复现 • 易于调试 • 验证特定条件 | • 对不完全匹配预期模式的有效变化很脆弱 • 缺乏细腻 • 在评估某些更主观的任务上受限 |

基于模型的评估器

| **方法** | **长处** | **短处** |
| --- | --- | --- |
| 基于评分标准的打分、自然语言断言、成对比较、基于参考的评估、多评审员共识 | 灵活、可扩展、捕捉细腻、处理开放式任务、处理自由格式输出 | 非确定、比代码更贵、准确性需要与人类评估器校准 |

人类评估器

| **方法** | **长处** | **短处** |
| --- | --- | --- |
| 领域专家评审、众包判断、抽查采样、A/B 测试、标注者间一致性 | 金标准的品质、契合专家用户的判断、用于校准基于模型的评估器 | 昂贵、慢、常常需要大规模接触人类专家 |

对每个任务，打分可以被加权（各评估器分数的组合必须达到一个阈值）、二元（所有评估器必须通过）、或二者混合。

### 能力评估 vs. 回归评估

**能力或「质量」评估**问：「这个 agent 擅长做什么？」它们应当以低通过率起步，瞄准 agent 吃力的任务、给团队一座可攀登的山。

**回归评估**问：「agent 是否仍处理它过去能做的所有任务？」且应有接近 100% 的通过率。它们防止倒退，因为分数下降意味着某处坏了、需要改进。当团队在能力评估上攀登时，重要的是同时跑回归评估，确保改动不在别处引发问题。

在 agent 发布并优化之后，高通过率的能力评估可以「毕业」，变成一套持续运行以捕捉任何漂移的回归套件。那些曾经衡量「我们究竟能不能做这个」的任务，转而衡量「我们还能可靠地做这个吗」。

### 评估编码 agent

**编码 agent** 编写、测试和调试代码，浏览代码库、运行命令，很像一位人类开发者。对现代编码 agent 有效的评估，通常依赖规格清晰的任务、稳定的测试环境、以及对生成代码的彻底测试。

确定性评估器对编码 agent 是天然的，因为软件大体上评估起来直截了当：代码能跑吗？测试通过吗？两个广泛使用的编码 agent 基准——[SWE-bench Verified](https://www.swebench.com/SWE-bench/) 和 [Terminal-Bench](https://www.tbench.ai/)——都遵循这一方法。SWE-bench Verified 给 agent 来自热门 Python 仓库的 GitHub issue，并通过运行测试套件给解法打分；一个解法只有在修复了失败的测试、又不破坏现有测试时才通过。LLM 仅一年之内就在这一评估上从 40% 进步到 >80%。Terminal-Bench 走一条不同的路：它测试端到端的技术任务，例如从源码构建一个 Linux 内核或训练一个 ML 模型。

一旦你有了一组通过与否的测试来验证编码任务的关键*结果*，通常对文字记录也打分也有帮助。例如，基于启发式的代码质量规则可以依据超过通过测试的标准来评估生成的代码，而带清晰评分标准的基于模型的评估器，可以评估像 agent 如何调用工具或如何与用户交互这类行为。

**示例：对编码 agent 的一种理论评估**

考虑一个编码任务，agent 必须修复一个认证绕过漏洞。如下面这份说明性的 YAML 文件所示，你可以同时用评估器和指标来评估这个 agent。

```
task:
  id: "fix-auth-bypass_1"
  desc: "Fix authentication bypass when password field is empty and ..."
  graders:
    - type: deterministic_tests
      required: [test_empty_pw_rejected.py, test_null_pw_rejected.py]
    - type: llm_rubric
      rubric: prompts/code_quality.md
    - type: static_analysis
      commands: [ruff, mypy, bandit]
    - type: state_check
      expect:
        security_logs: {event_type: "auth_blocked"}
    - type: tool_calls
      required:
        - {tool: read_file, params: {path: "src/auth/*"}}
        - {tool: edit_file}
        - {tool: run_tests}
  tracked_metrics:
    - type: transcript
      metrics:
        - n_turns
        - n_toolcalls
        - n_total_tokens
    - type: latency
      metrics:
        - time_to_first_token
        - output_tokens_per_sec
        - time_to_last_token
```

请注意，这个例子为演示而展示了所有可用评估器的全貌。在实践中，编码评估通常依赖单元测试做正确性核验、一份 LLM 评分标准做整体代码质量评估，只在需要时才添加额外的评估器和指标。

### 评估对话式 agent

**对话式 agent** 在支持、销售或教练等领域与用户交互。与传统聊天机器人不同，它们维持状态、使用工具、并在对话中途采取行动。虽然编码和研究 agent 也可能涉及与用户的多轮交互，对话式 agent 呈现出一个独特的挑战：交互本身的质量就是你在评估的一部分。对对话式 agent 有效的评估，通常依赖可验证的终态结果，以及既捕捉任务完成、也捕捉交互质量的评分标准。与多数其他评估不同，它们常常需要第二个 LLM 来模拟用户。我们在[对齐审计 agent](https://alignment.anthropic.com/2025/automated-auditing/)中用这一方法，通过长时的对抗性对话对模型做压力测试。

对话式 agent 的成功可以是多维的：工单是否解决了（状态检查）、是否在 <10 轮内完成（文字记录约束）、语气是否恰当（LLM 评分标准）？两个纳入多维度的基准是 [𝜏-Bench](https://arxiv.org/abs/2406.12045) 及其后继 [τ2-Bench](https://arxiv.org/abs/2506.07982)。它们模拟零售支持、订机票等领域里的多轮交互，其中一个模型扮演一个用户人设，而 agent 导航真实场景。

**示例：对对话式 agent 的一种理论评估**

考虑一个支持任务，agent 必须为一位沮丧的客户处理一笔退款。

```
graders:
  - type: llm_rubric
    rubric: prompts/support_quality.md
    assertions:
      - "Agent showed empathy for customer's frustration"
      - "Resolution was clearly explained"
      - "Agent's response grounded in fetch_policy tool results"
  - type: state_check
    expect:
      tickets: {status: resolved}
      refunds: {status: processed}
  - type: tool_calls
    required:
      - {tool: verify_identity}
      - {tool: process_refund, params: {amount: "<=100"}}
      - {tool: send_confirmation}
  - type: transcript
    max_turns: 10
tracked_metrics:
  - type: transcript
    metrics:
      - n_turns
      - n_toolcalls
      - n_total_tokens
  - type: latency
    metrics:
      - time_to_first_token
      - output_tokens_per_sec
      - time_to_last_token
```

如同我们编码 agent 的例子，这个任务为演示而展示了多种评估器类型。在实践中，对话式 agent 评估通常用基于模型的评估器来评估沟通质量和目标完成，因为许多任务——例如回答一个问题——可能有多个「正确」解法。

### 评估研究 agent

**研究 agent** 收集、综合并分析信息，然后产出像答案或报告这样的输出。与单元测试提供二元通过/失败信号的编码 agent 不同，研究质量只能相对于任务来评判。什么算「全面」、「来源可靠」甚至「正确」都取决于上下文：一次市场扫描、一项收购的尽调、一份科学报告，各自要求不同的标准。

研究评估面临独特的挑战：专家可能就一份综合是否全面而意见不一、随着参考内容不断变化而事实标准也在变动、更长更开放的输出为犯错留下了更多空间。例如像 [BrowseComp](http://arxiv.org/abs/2504.12516) 这样的基准，测试 AI agent 能否在开放网络上大海捞针——那些设计成易于验证却难以解决的问题。

一种构建研究 agent 评估的策略是组合多种评估器类型。依据性检查核验论断是否被检索到的来源支持，覆盖度检查定义一份好答案必须包含的关键事实，来源质量检查确认所查阅的来源是权威的、而非仅仅是最先检索到的。对有客观正确答案的任务（「X 公司的 Q3 营收是多少？」），精确匹配管用。一个 LLM 能标记无依据的论断和覆盖度上的缺口，同时也能验证那份开放式综合的连贯性和完整性。

鉴于研究质量的主观性质，基于 LLM 的评分标准应当频繁地对专家的人类判断做校准，才能有效地评估这些 agent。

### Computer use agent

**Computer use agent** 通过与人类相同的界面——截图、鼠标点击、键盘输入和滚动——而非通过 API 或代码执行来与软件交互。它们能使用任何有图形用户界面（GUI）的应用，从设计工具到遗留企业软件。评估需要在真实或沙箱环境里运行 agent，让它能使用软件应用、并检查它是否达到了预期结果。例如，[WebArena](https://arxiv.org/abs/2307.13854) 测试基于浏览器的任务，用 URL 和页面状态检查来验证 agent 是否正确地导航，并配合后端状态核验来确认那些修改数据的任务（确认订单确实被下了，而不仅仅是确认页面出现了）。[OSWorld](https://os-world.github.io/) 把它扩展到完整的操作系统控制，评估脚本在任务完成后检查多样的产物：文件系统状态、应用配置、数据库内容和 UI 元素属性。

浏览器使用 agent 需要在 token 效率和延迟之间取得平衡。基于 DOM 的交互执行快但消耗很多 token，而基于截图的交互更慢但更 token 高效。例如，当请 Claude 总结一篇 Wikipedia 时，从 DOM 提取文本更高效。当在 Amazon 上找一个新笔记本内胆包时，截图更高效（因为提取整个 DOM 很费 token）。在我们的 Claude for Chrome 产品里，我们开发了评估来检查 agent 是否在按上下文选择正确的工具。这让我们能更快、更准确地完成基于浏览器的任务。

### 如何看待 agent 评估中的非确定性

无论 agent 类型如何，agent 行为在运行之间都会有变化，这使得评估结果比乍看更难解读。每个任务有它自己的成功率——也许一个任务 90%，另一个 50%——而一次评估运行里通过的任务，下一次可能失败。有时，我们想衡量的是 agent 对某任务成功得*多频繁*（占试验的多大比例）。

两个指标有助于捕捉这一细腻：

[**pass@k**](https://proceedings.neurips.cc/paper/2019/file/7298332f04ac004a0ca44cc69ecf6f6b-Paper.pdf) 衡量 agent 在 *k* 次尝试中至少得到一个正确解法的可能性。随 *k* 增大，pass@k 分数上升：更多「射门机会」意味着至少 1 次成功的更高几率。50% pass@1 意味着模型在其首次尝试上对一半的 eval 任务成功。在编码里，我们通常最感兴趣的是 agent 第一次尝试就找到解法——pass@1。在其他情形里，只要有一个管用，提出许多解法是有效的。

[**pass^k**](https://arxiv.org/abs/2406.12045) 衡量*所有 k* 次试验都成功的概率。随 *k* 增大，pass^k 下降，因为要求跨更多试验的一致性是一道更难跨过的门槛。如果你的 agent 有每次试验 75% 的成功率、而你跑 3 次试验，三次全过的概率是 (0.75)³ ≈ 42%。这个指标对期望每次都有可靠行为的面向客户的 agent 尤其重要。

pass@k 和 pass^k 随试验增加而分道扬镳。在 k=1 时它们相同（都等于每次试验的成功率）。到 k=10，它们讲述相反的故事：pass@k 逼近 100%，而 pass^k 跌到 0%。

两个指标都有用，用哪个取决于产品要求：对一个成功即算数的工具用 pass@k，对一个一致性至关重要的 agent 用 pass^k。

## 从 0 到 1：通往出色 agent 评估的路线图

本节铺排我们从无评估到有可信评估的务实、经实战检验的建议。把它当作一份评估驱动的 agent 开发路线图：早早定义成功、清晰地衡量它、并持续迭代。

### 收集任务作为初始评估数据集

**第 0 步。尽早开始**

我们看到团队推迟构建评估，因为它们以为需要数百个任务。实际上，从真实失败中抽取的 20-50 个简单任务就是一个很好的起点。毕竟，在早期 agent 开发中，对系统的每次改动往往都有清晰、可察觉的影响，而这种大的效应量意味着小样本就足够。更成熟的 agent 可能需要更大、更难的评估来检测更小的效应，但起初最好采用 80/20 的做法。你拖得越久，评估就越难构建。早期，产品需求会自然地转化为测试用例。拖太久，你就在从一套活着的系统逆向工程成功标准。

**第 1 步。从你已经在手动测试的东西开始**

从你在开发中跑的手动检查开始——那些你在每次发布前会验证的行为、以及终端用户常试的常见任务。如果你已在生产，看你的 bug 跟踪器和支持队列。把用户报告的失败转成测试用例，能确保你的套件反映真实的用量；按用户影响排序，帮你把精力投在关键处。

**第 2 步：撰写带参考解的、无歧义的任务**

把任务质量做对比看上去更难。一个好的任务，是两位领域专家会独立地得出相同通过/失败裁定的任务。他们自己能通过任务吗？如果不能，任务需要打磨。任务规格中的歧义会变成指标中的噪声。这同样适用于基于模型评估器的标准：含糊的评分标准会产出不一致的判断。

每个任务都应当对一个正确遵循指令的 agent 是可通过的。这一点可能很微妙。例如，审计 Terminal-Bench 时我们揭示：如果一个任务要求 agent 写一个脚本却不指定文件路径，而测试假定脚本有一个特定的文件路径，agent 可能因非己之过而失败。评估器检查的一切都应当从任务描述里清晰可见；agent 不该因含糊的规格而失败。面对前沿模型，跨许多试验 0% 的通过率（即 0% pass@100）多半是一个坏任务的信号，而非一个无能 agent 的信号，也是一个该复查你任务规格和评估器的征兆。对每个任务，创建一个参考解是有用的：一份已知可用、能通过所有评估器的输出。这证明任务可解，并核验评估器配置正确。

**第 3 步：构建平衡的问题集**

既要测一个行为*应该*发生的情形，也要测它*不该*发生的情形。单边的评估制造单边的优化。例如，如果你只测试 agent 该不该在应当时搜索，你可能最终得到一个几乎什么都搜的 agent。尽量避免[类别不平衡](https://developers.google.com/machine-learning/crash-course/overfitting/imbalanced-datasets)的评估。我们在为 [Claude.ai](http://claude.ai/redirect/website.v1.aca40ed7-d416-48d1-9b17-e70903f6ff1e) 的网络搜索构建评估时亲身学到了这一点。挑战在于防止模型在不该搜时搜、同时在恰当的时候保留它做广泛研究的能力。团队构建了覆盖两个方向的评估：模型应当搜索的查询（例如找天气）和它应当凭已有知识回答的查询（例如「谁创立了 Apple？」）。在欠触发（该搜不搜）与过触发（不该搜却搜）之间取得恰当平衡很难，并对 prompt 和评估做了很多轮打磨。随着更多示例问题出现，我们持续把它们加入评估，以改善我们的覆盖度。

### 设计评估 harness 和评估器

**第 4 步：构建一个带稳定环境的稳健评估 harness**

至关重要的是，评估中的 agent 功能上与生产中所用的 agent 大体一致，且环境本身不引入更多噪声。每次试验都应通过从一个干净环境启动来做「隔离」。运行之间不必要的共享状态（残留文件、缓存数据、资源耗尽）可能因基础设施抖动而非 agent 性能造成相关失败。共享状态也可能人为地虚增性能。例如，在一些内部评估里我们观察到 Claude 通过检查以往试验的 git 历史，在某些任务上获得了不公平的优势。如果多个不同试验因环境的同一局限（如有限的 CPU 内存）而失败，这些试验并非独立，因为它们受同一因素影响，而评估结果对衡量 agent 性能就变得不可靠。

**第 5 步：周密地设计评估器**

如上所述，出色的评估设计涉及为 agent 和任务选择最佳的评估器。我们建议尽可能选择确定性评估器、在必要时或为额外灵活性使用 LLM 评估器、并审慎地使用人类评估器做额外核验。

有一种常见的本能，是去检查 agent 是否按正确顺序走了一系列工具调用这样的特定步骤。我们发现这种方法太死板、导致过于脆弱的测试，因为 agent 经常找到评估设计者未曾预料的可行解法。为了不不必要地惩罚创造力，通常最好是给 agent 产出了什么打分，而不是它所走的路径。

对有多个组件的任务，内建部分学分。一个正确识别问题并核验了客户、却未能处理退款的客服 agent，比一个立即失败的 agent 有意义地更好。在结果里呈现这一成功的连续谱很重要。

模型打分常常需要周密迭代以验证准确性。LLM-as-judge 评估器应与人类专家紧密校准，以获得对「人类打分与模型打分之间几乎没有分歧」的信心。为避免幻觉，给 LLM 一个退路，例如提供一条指令：当它没有足够信息时返回「Unknown」。创建清晰、结构化的评分标准、对任务的每个维度分别打分，然后用一个独立的 LLM-as-judge 为每个维度打分、而不是用一个来评所有维度，也会有帮助。一旦系统稳健起来，偶尔用人工审阅就够了。

有些评估有微妙的失败模式，即便 agent 表现良好也会得低分，因为 agent 因打分 bug、agent harness 限制或歧义而未能解决任务。即便是资深团队也会漏掉这些问题。例如，[Opus 4.5 最初在 CORE-Bench 上得 42%](https://x.com/sayashk/status/1996334941832089732?s=46&t=c5pEvnVdVbMkcR_rcCHplg)，直到一位 Anthropic 研究者发现了多个问题：僵硬的打分——在预期「96.124991…」时惩罚「96.12」、含糊的任务规格、以及无法精确复现的随机任务。在修复 bug 并使用一个约束更少的 scaffold 之后，Opus 4.5 的分数跳到了 95%。类似地，[METR 发现](https://x.com/metr_evals/status/2001473506442375645?s=46)其时间跨度基准里有若干配置错误的任务，要求 agent 优化到一个声明的分数阈值，但打分却要求超过那个阈值。这惩罚了像 Claude 这样遵循指令的模型，而忽视声明目标的模型反得了更好的分。仔细复查任务和评估器能帮助避免这些问题。

让你的评估器对绕过或取巧有抵抗力。agent 不应能轻易「作弊」评估。任务和评估器的设计应使通过它真正地要求解决问题，而非利用非预期的漏洞。

### 长期维护并使用评估

**第 6 步：检查文字记录**

除非你阅读许多试验的文字记录和打分，否则你不会知道你的评估器是否工作得好。在 Anthropic，我们投资于查看评估文字记录的工具，并定期花时间阅读它们。当一个任务失败时，文字记录会告诉你 agent 是犯了一个真正的错误、还是你的评估器拒绝了一个有效的解法。它也常常浮现关于 agent 和评估行为的关键细节。

失败应当显得公平：agent 弄错了什么、以及为什么，一目了然。当分数不攀升时，我们需要信心，那是由于 agent 表现、而非评估。阅读文字记录，是你核实你的评估是否在衡量真正要紧的东西的方式，也是 agent 开发的一项关键技能。

**第 7 步：监控能力评估饱和**

一个处于 100% 的评估跟踪回归、却不为改进提供信号。**评估饱和**发生在 agent 通过了所有可解的任务，没有改进的余地时。例如，SWE-Bench Verified 分数今年年初起步于 30%，而前沿模型如今正逼近 >80% 的饱和。当评估接近饱和时，进步也会放慢，因为只剩最难的任务。这会让结果具有欺骗性，因为大的能力改进表现为分数的小幅提升。例如，代码审查初创 [Qodo](https://www.qodo.ai/) 起初对 Opus 4.5 不以为然，因为它们一次性编码评估没能捕捉到在更长、更复杂任务上的增益。作为回应，他们开发了一套新的 agentic 评估框架，提供了对进步更清晰的图景。

作为一条规则，在别人深挖评估细节、阅读一些文字记录之前，我们不会把评估分数当作表面价值。如果打分不公平、任务含糊、有效解法被惩罚、或 harness 约束了模型，评估就应当被修订。

**第 8 步：通过开放贡献和维护长期保持评估套件的健康**

一套评估套件是一个需要持续关注、并有清晰归属才能保持有用的活的产物。

在 Anthropic，我们试验了各种评估维护方法。最有效的，是设立专门的评估团队来拥有核心基础设施，而领域专家和产品团队贡献多数评估任务、并亲自来跑评估。

对 AI 产品团队，拥有并迭代评估应当像维护单元测试一样例行。团队可能在那些早期测试里「管用」、却未能满足一套设计良好的评估本会早早暴露的未声明期望的 AI 功能上浪费数周。定义评估任务，是压力测试产品需求是否足够具体、可以开始构建的最佳方式之一。

我们建议实践评估驱动的开发：在 agent 能满足某些能力之前，构建评估来定义那些被规划的能力，然后迭代直到 agent 表现出色。在内部，我们常构建今天「够好」地工作、但押注在几个月后模型能做些什么的功能。那些以低通过率起步的能力评估让这一点变得可见。当一款新模型出炉，跑一遍套件会迅速揭示哪些押注兑现了。

最贴近产品需求和用户的人，最有资格定义成功。以当前的模型能力，产品经理、客户成功经理或销售员能用 Claude Code 把一个评估任务作为 PR 贡献进来——让他们做！或者，更好的是，主动赋能他们。

创建一套有效评估的过程。

## 评估如何与其他方法配合，对 agent 形成全貌理解

自动化评估能在数千个任务上对一个 agent 运行，而不部署到生产或影响真实用户。但这只是理解 agent 性能的诸多方式之一。一幅完整的图景包括生产监控、用户反馈、A/B 测试、手动文字记录审阅和系统化的人类评估。

理解 AI agent 性能各方法的概览

| 方法 | 优点 | 缺点 |
| --- | --- | --- |
| **自动化评估** *无需真实用户地程序化运行测试* | 更快迭代、完全可复现、无用户影响、可每次提交运行、无需生产部署即可规模化测试场景 | 构建需要更多前置投入、随产品和模型演进而需要持续维护以避免漂移、若不与真实用量匹配则可能制造虚假的信心 |
| **生产监控** *在实时系统里跟踪指标和错误* | 大规模揭示真实用户行为、捕捉合成评估漏掉的问题、就 agent 实际表现提供事实标准 | 被动；问题在你知道之前就触达用户；信号可能噪声大；需要在插桩上投入；打分缺乏事实标准 |
| **A/B 测试** *用真实用户流量比较变体* | 衡量真实的用户结果（留存、任务完成）、控制混淆因素、可扩展且系统化 | 慢；要达到显著性需要数天或数周、且需要足够流量；只测试你部署的改动；在无法彻底审阅文字记录时，对指标变化背后的根本「为什么」信号较少 |
| **用户反馈** *像点踩或 bug 报告这样的显式信号* | 浮现你未曾预料的问题、附带来自真实人类用户的真实示例、反馈常与产品目标相关 | 稀疏且自我选择、偏向严重问题、用户很少解释*为什么*某样东西失败、非自动化、主要依赖用户来抓问题可能有负面的用户影响 |
| **手动文字记录审阅** *人类通读 agent 对话* | 建立对失败模式的直觉、捕捉自动检查漏掉的微妙质量问题、帮助校准「好」长什么样并把握细节 | 费时、不可扩展、覆盖不一致、审阅者疲劳或不同审阅者会影响信号质量、通常只给定性信号而非清晰的量化打分 |
| **系统化人类研究** *由受过训练的评审员对 agent 输出做结构化打分* | 来自多位人类评审的金标准品质判断、处理主观或含糊任务、为改进基于模型的评估器提供信号 | 相对昂贵、周转慢、难频繁运行、评审员间分歧需要调和、复杂领域（法律、金融、医疗）需要人类专家来开展研究 |

这些方法映射到 agent 开发的不同阶段。自动化评估在发布前和 CI/CD 里尤其有用，在每次 agent 改动和模型升级时运行，作为抵御质量问题的第一道防线。生产监控在发布后介入，检测分布漂移和未预料的真实世界失败。A/B 测试在你有足够流量后验证重要变化。用户反馈和文字记录审阅是填补空档的持续实践：不断对反馈做分类、每周抽样阅读文字记录、并在需要时深挖。把系统化人类研究保留用来校准 LLM 评估器，或在人类共识充当参考标准之处评估主观输出。

就像安全工程里的瑞士奶酪模型，没有单层评估能抓住每一个问题。通过组合多种方法，从一层溜过的失败会被另一层抓住。

最有效的团队组合这些方法：自动化评估用于快速迭代，生产监控用于事实标准，周期性人工审阅用于校准。

## 结论

没有评估的团队会陷入被动循环——修一处失败、造另一处、无法区分真实回归与噪声。尽早投入的团队则发现相反：开发加速，因为失败变成测试用例、测试用例预防回归、指标取代猜测。评估给整个团队一座清晰的攀登之山，把「agent 感觉变差了」变成可执行的东西。它的价值会复利，但前提是你把评估当作核心组件、而非事后补丁。

模式因 agent 类型而异，但这里描述的根本是不变的。尽早开始，别等完美的套件。从你所见的失败中取材、构建真实的任务。定义无歧义、稳健的成功标准。周密地设计评估器并组合多种类型。确保问题对模型足够难。在评估上迭代以改善它们的信噪比。阅读文字记录！

AI agent 评估仍是一个新兴、快速演进的领域。随着 agent 承担更长的任务、在多 agent 系统中协作、并处理日益主观的工作，我们将需要调整我们的技术。我们会随着学到更多而持续分享最佳实践。

## 附录：评估框架

有几个开源和商业框架能帮助团队实现 agent 评估，而不必从零构建基础设施。合适的选择取决于你的 agent 类型、现有栈，以及你是否需要离线评估、生产可观测性、或两者。

[Harbor](https://harborframework.com/) 为在容器化环境里运行 agent 而设计，带有跨云提供商规模化运行试验的基础设施、以及定义任务和评估器的标准格式。像 Terminal-Bench 2.0 这样的热门基准通过 Harbor 注册库交付，使运行成熟的基准连同自定义评估套件都变得容易。

[Braintrust](https://www.braintrust.dev/) 是一个把离线评估与生产可观测性和实验跟踪结合起来的平台——对那些既需要在开发期迭代、又需要在生产监控质量的团队很有用。它的 `autoevals` 库包含针对事实性、相关性及其他常见维度的预置打分器。

[LangSmith](https://docs.langchain.com/langsmith/evaluation) 提供 trace、离线和在线评估、以及数据集管理，与 LangChain 生态紧密集成。[Langfuse](https://langfuse.com/) 作为自托管的开源替代品，为有数据驻留要求的团队提供类似能力。

[Arize](https://arize.com/) 提供 Phoenix，一个用于 LLM trace、调试和离线或在线评估的开源平台，以及 AX，一个扩展 Phoenix 以实现规模、优化和监控的 SaaS 产品。

许多团队组合多个工具、自研评估框架、或只用简单的评估脚本起步。我们发现，虽然框架可以是加速进步和标准化的宝贵方式，但它们只如你通过它们运行的评估任务一样好。通常最好是快速挑一个契合你工作流的框架，然后把你的精力通过在高品质的测试用例和评估器上迭代，投入到评估本身。
