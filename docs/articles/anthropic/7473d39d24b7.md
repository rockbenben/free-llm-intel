*这是我们关于构建人类—agent 团队系列文章的第三篇。[第一篇](https://claude.com/resources/articles/building-effective-human-agent-teams) 分享了我们在 Anthropic 实践 multiplayer AI 的收获。[第二篇](https://claude.com/resources/articles/turning-conversation-into-knowledge-how-slack-builds-human-agent-teams) 介绍了 Slack 如何把职场对话变成 agents 所需的上下文。这一篇来看看，当 agents 与团队在同一个平台上工作时，会发生哪些变化。*

早在推出 AI agents 的多年以前，Asana 的团队就在不断摸索，想办法把结构和责任制编码进团队协作的方式里。他们最终打造出了 W*ork Graph*® 模型，它把每一项任务、项目、目标和对话都映射到一张关系网上，并明确各自的负责人、贡献者和依赖关系。

在开始构建 AI agents 时，他们决定不为 AI 另加一套上下文结构，而是让 agents 在这同一个模型中运作。它们会有明确的角色，被分配任务，读写消息，并与人类协作者一起出现在动态流中——同时在 agents 能访问什么、能分享什么上，附加额外的防护措施。

我们与 Asana 首席产品官 Arnab Bose 聊了聊 Asana 自己的团队如何使用 Claude、如何与这些 agents 并肩工作（其中复杂任务由 Claude 模型驱动）：每个 agent 如何获得自己的角色和访问权限、由谁来训练它、工作如何对所有人保持可见，以及 agents 在 Asana 的人类—agent 团队里承担哪些类型的工作。

## 在 agents 动手之前，先想清楚并组织好你的工作

对 Asana 员工来说，Claude 是默认的 AI 工具，它连接着员工日常使用的平台，包括 Google Drive、Slack，当然还有 Asana。

"一个人要理清自己的一天，得把非结构化数据——一个想法、Slack 里的一段对话、Zoom 里的一场会议录音、一份 Databricks 报告、来自 Google Docs 的信息——拿来消化，”Arnab 说。“他们和 Claude 把事情聊一遍，然后就能把这一切都灌进 Asana 用项目和任务提供的结构里。"结构一旦就位，agents 就能在此基础上行动，依靠的是我们在本系列第一篇 [*Building effective human agent teams*](https://claude.com/resources/articles/building-effective-human-agent-teams) 中描述的三项能力：持久记忆、自己的凭据，以及共享上下文。

**如何付诸实践：**

- **从你自己的想法开始。**把你一天里零散的片段——一个想法、一段 Slack 对话，或散落在各份文档里的笔记——带到 Claude 面前。
- **和 Claude 辩论、讨论。**把它当作思考伙伴：把想法聊透，直到下一步清晰起来。
- **把可执行的事项记录到 Work Graph。**把可执行的内容移进项目和任务里，agents 和同事就能接着处理。

## 给每个 agent 一个角色，以及它需要的工具和访问权限

Asana 员工可以在任何项目里与 AI agents 协作，就像和人类同事协作一样。团队由人来设计；每位员工都会拿到一份推荐 agents 列表，用来帮助团队达成目标。

agents 围绕角色或工作类型来构建，例如内容写作者、洞察分析师、项目经理、工作受理专员、活动分析师或活动协调员。每个 agent 都带有预置的 skills，这些 skills 基于 Asana 对客户如何开展此类工作的研究；它还带有角色所需的各种集成，比如 Hubspot 或某个文档盘。

![](https://assets.claude.com/71e5b66591e4a02d83db7fa47acf7ef214d4146e.png)

每个 agent 还有一个资料页，列出它的名称与用途、可以使用它的人、管理员、指令、skills、集成和权限。Asana 提供的工具让你能有意识地授予访问权限。“Asana 是一个有边界的工作面，”Arnab 说。“你可以选择只授予某一组项目而不是全部，或者只授予某一组文档，也可以是文档和应用的组合。”

和人类用户一样，agents 也受明确的访问控制约束，但还多一层保护：Asana 表示，一个 agent 的实际访问范围以触发它那个人的权限为界。这样 agents 可以广泛访问公开内容，同时把任何人访问到 agent 在私有上下文中获知的信息的风险降到最低。

**如何付诸实践：**

- **在创建 agent 之前先定义角色。**想清楚 agents 能在你的团队里承担哪些类型的工作，然后写下这个 agent 的用途、指令，以及它负责哪些具体工作——就像为新员工规划第一个季度那样。
- **划定访问范围。**决定这个 agent 可以读取哪些项目和文档、可以访问哪些应用，以及可以执行哪些操作。
- **把使用者和管理员分开指定。**很多人可以和同一个 agent 协作，但只应由一个规模很小、点名指定的群体来管理它能访问什么、表现如何。

## 把与 agent 协作和训练 agent 分开

Asana 把这些 agents 称作 AI teammates，它们的一个关键特性是共享记忆：agent 能保留此前指令中的信息，让多个用户可以复用这份记忆，更快完成任务或工作。“AI teammates 可以像团队里的一个人那样被指导和训练，”Arnab 说。

共享记忆的运作有一项基于角色的限制。任何人都可以就某个任务向 agent 提供反馈，但只有管理员和编辑者才能把反馈写入永久记忆，也才能撤销或删除记忆中的内容。对其他所有人来说，他们给出的反馈只作用于当前任务。

Arnab 说，这种划分是刻意为之。Asana 的传播团队负责把握公司的口吻和语调，因此一个负责写作的 agent，其编辑者和管理员就该是他们。Arnab 可以用它起草，但不能修改它的行为。而大多数人根本不需要接触这套机制："团队里不是每个人都需要理解 skills、行为和记忆这些概念。团队里有一两个人成为专家，把它正确设置好，团队里其他所有人往后都能得到同样的好处。"

**如何付诸实践：**

- **决定由谁训练每个 agent、由谁与它协作。**找出业务内部能够帮助构建团队所用 agents 的主题专家。其他人可以在任务上提供反馈，但不能改写这个 agent。
- **让编辑者与专业能力相匹配。**哪个团队掌握着 agent 所应用的标准（比如品牌语调或规划惯例），就由哪个团队拥有（或管理）这个 agent。
- **在工作中积累记忆。**反馈能让 agent 随时间不断改进。让 agent 记住值得保留的决定，或者删掉那些已经不再相关或不再属实的决定。

## 把 agent 的工作放在所有人都看得见的地方

与 [Slack 中的 agents 在频道里透明发帖](https://claude.com/resources/articles/turning-conversation-into-knowledge-how-slack-builds-human-agent-teams) 类似，当一个任务被分配给 AI teammate 时，所有人都能看到是某个 agent 在做这件事，以及它做了什么。agent 会把活动发布出来，包括它的研究计划和采取的步骤，这样所有能访问该任务的人都能读到它做了什么、发表评论，并把它引向自己想要的结果。

当 Asana 的传播团队请 Arnab 审阅一份演讲活动的简报文档时，他在任务里 @ 了那个 agent，并要求它把自己早先一次演讲的讲述思路也考虑进去。这条消息很简短，因为他已经用过那个 agent 很多次，而他引用的材料早已在 Work Graph 里。传播团队的一位同事能看到他的请求和 agent 的回复，并同时与这个 agent 来回沟通。

"如果你对 AI 非常熟练，你大概能从一对一的 AI agent 那里拿到质量很高的回复，把文档导出来，再贴回 Slack 或 Asana，"Arnab 说。"但到那一步，其他评审这份内容的人并不知道 prompt 是什么、来回沟通了什么。如果他们不同意你给出的某些指导，他们根本没办法和你对齐。"而在共享任务里，请求、反驳和产出都在同一个地方，评审产出的人也能修改产生这份产出的指令。

**如何付诸实践**

- **把 agents 引入团队评审工作的环节。**这样，请求、agent 的步骤和结果都在同一个地方，评审者可以修改指令或产出。
- **让 agent 的工作明确看得出是 agent 做的。**这样，人们就会知道这项工作是由 AI agent 而不是人类同事完成的。
- **让评审者能够指导 agent 的工作。**Asana 的 agents 会在共享任务中发布自己的计划和步骤，其他评审者因此可以提供进一步的指令或反馈。

## Asana 交给 agents 的三类工作

在 Asana，任何生成文档或执行复杂任务的 agentic 工作都由 Claude 驱动。以下是来自公司不同团队的三个例子：

### **在 Slack 频道里回答产品问题**

Asana 每推出新功能，销售和客户成功人员就可以在一个共享 Slack 频道里提问。在 AI teammates 出现之前，同样的问题会被反复发布，每次都要 @ 主题专家。Arnab 说，做一个可搜索的知识库并不是个可行的方案，因为答案很微妙，而且会变化。"关于产品当前处于什么状态，你多少得有点把关和判断，"他说。

这些问题仍然会发到 Slack，因为那是一线人员提问最方便的地方。现在，频道里的一个 Asana 应用会把每个问题转成 Asana 任务，再由某个 agent 接手。如果存在已获批准的指导内容，agent 会附上来源链接作答。如果没有已获批准的答案，且问题指向产品的一处缺口，agent 会在产品团队的受理项目中创建一个任务，并把它加进 backlog。而如果同一个问题反复出现、agent 反复贴出同一条记录，它就会为 enablement 团队创建一个任务，去更新培训材料和文档。

这个过程为 enablement 团队腾出了宝贵时间，让他们专注于战略性、优先级更高的工作，同时也为业务的其他领域提供了信息。比如，如果围绕某个新产品的某一主题出现大量问题，这就提示 enablement 团队应当投入额外培训或资料来重点处理它。

### **向高管汇报有风险的续约**

Asana 首席客户官 Josh Abdulla 过去每周要为高管团队制作一份有风险的续约简报，内容是汇总客户成功经理（CSM）的更新——CSM 会标记有风险的续约，并在情况变化时更新客户记录。全球有数千家客户，更新量之大，如果没有专人做综合整理，根本不可能跟上最新情况；这项工作枯燥乏味，也让整个流程变成被动反应。"Josh 是在领导告诉他时才知道出了问题，而不是在数据第一次显示问题时就知道，"Arnab 说。

客户体验组织在 Asana 里构建了一个名为 At-Risk Renewal 的 agent AI teammate。它会读取全球客户组合中每一个有风险的续约任务，包括每位 CSM 的更新、状态说明和评论，并生成一份结构化的每日摘要，分成三类：正向势头、负向势头和建议的后续动作。它先给出全球视图，再按区域拆分，每天早晨自动把摘要推送给首席客户官、首席营收官和每一位区域客户成功负责人。由于摘要落在共享空间里，这些负责人可以追问，比如某个客户流失预测背后的领先指标是什么，还可以指导 agent 记住一些内容供下次运行使用，从而让报告每天早晨都更完善。

"他们大概可以让 Claude 给自己生成一份报告，"Arnab 说。"但怎么才能做到报告有统一标准、有共享工作空间，而且每运行一次就变得更好一点呢？"

### **用 Command 规划工程周期**

当 Asana 在自己的产品上跑自动化编码循环时，周期时间和发布开始拖后，因为循环被自动生成的改动撑得越来越臃肿。这种循环本身在软件公司里已经变得很常见：从各个渠道收集客户反馈，做综合提炼，再触发编程 agents 把它变成 pull request（PR）。"代码生成现在不再是瓶颈了，"Arnab 说。"瓶颈在于规划、决策和打磨。"Asana 的工程组织现在运行在 Command by Asana 上——这是一款用于管理大型工程团队的产品——并用它来管理这个循环。

在 Command 中，一个团队空间容纳一组 10 到 12 名工程师，共同负责一个产品。agents 会把从客户反馈和团队 Slack 反馈频道评论中提取的工单，放进团队的未规划看板。由人来决定看板上哪些内容进入周期，Command 则用乐观、平衡和保守三种估算，预测该周期的完成时间。

一个工单可以分配给一个人，也可以分配给一个编程 agent；由于周期数据都集中在一处，管理者可以在聊天里问某个发布为什么偏离了计划，以及做哪些取舍能把它拉回来。Command 会基于数据作答，说明是什么在驱动这一信号、该在哪些改动上做取舍。这一切都通过 Asana 的 MCP server 暴露出来——这条连接让 Claude 这样的助手可以读取它，于是像 Arnab 或他对标的 CTO 这样的人，无需打开 Command，就能问 Claude 哪些事情在正轨上。

"当团队能够毫不费力地协作时，人类就能蓬勃发展；而今天，每个团队都是一部分人、一部分 agent，"Arnab 说。"这正是我们设计的工作方式：一个人类和 agents 都能使用的共享上下文；每个 agent 都有独立身份，它的贡献和访问权限都可以被审计；还有一份 agent 能学到什么的持久记录，让团队的知识不断累积，而不是蒸发掉。"
