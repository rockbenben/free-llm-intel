作为一名销售负责人，我不得不承认：不久之前，想为公司采购 Claude 的人，并不能足够快地拿到他们需要的答案。他们填好了我们的 Contact Sales 表单，却要等很久才收到回复，有时要等上好几天。他们的问题大多很简单：某个套餐要多少钱、有没有最低席位要求，或者我们能否满足 HIPAA 的合同要求。答案就在我们的文档和支持文章里，但客户希望有人能快速地带他们走一遍。

于是我们在 Claude Managed Agents（beta）上构建了一个购买 agent，把潜在客户从“我想给公司买 Claude”一路带到完成购买。现在，这个购买 agent 每天要承接数千次对话，回答客户最紧迫的问题，并帮助他们走完结账流程。它升级给我们团队的客户，来的时候已经了解了情况、更接近做出购买决定：这些线索转化成商机的频率是旧表单线索的两倍多，成交速度也快大约五天。我们有意把这个体验设为选择加入（opt-in），也就是说，客户在开始时可以根据自己的偏好，选择与 agent 对话还是与销售代表对话。

![](https://assets.claude.com/b67a0e1a023590767c2fd9b4cbb9a94aba1cc82d.png)

## **为什么旧的入站流程失效了**

在构建购买 agent 之前，我们的入站流程相当直接。买家填一张表，线索被转给一位业务拓展代表（BDR），由他做资格审核，再交给客户经理。当团队能够与每一位对产品感兴趣的人交谈时，这套流程依然运转良好。

我们每月有数万条入站请求，负责入站的 BDR 团队根本跟不上。销售代表整天都在回答文档里已经写过的问题，而我们也没有有效的方式触及队列里的所有客户。这不是我们希望给客户的体验。

我们希望每一位客户在任何时间、用任何语言都能得到一个专业的答案，并且能按自己喜欢的方式购买——这往往意味着不用和销售代表交谈。我们希望销售代表把时间花在那些能改变结果走向的对话上。

## **一个补上缺口的购买 agent**

我们把 agent 部署在客户本来就在提问的地方：[Contact Sales](https://claude.com/contact-sales) 和 [Pricing](https://claude.com/pricing#team-&-enterprise) 页面、产品内部，以及我们的邮件里。任何客户都可以在 [Claude.ai](http://claude.ai) 产品中找到这个购买 agent，它是一个简单的聊天体验，帮助客户弄明白哪种套餐最适合自己。客户描述团队的需求，agent 问几个追问，然后回答关于价格、安全和数据的疑问，最后推荐套餐与席位数。每段对话以三种方式之一结束：

- **购买。** 买家直接进入结账。
- **转接。** 对于更大或更复杂的单子，agent 会把买家连同完整的对话详情一起转给销售代表。
- **快速得到答案。** 有时候客户需要的就只有这个。

我们让这个 agent 遵循销售代表同样的工作方式，也就是理解客户想解决什么、他们目前使用 Claude 的情况如何，以及我们怎样能最好地帮到他们。

![](https://assets.claude.com/7c281bb3ea8a03950ee0130275034a17b32b111a.png)

## **为什么选用 Claude Managed Agents？**

在底层，这个购买 agent 很简单：一段 prompt、几个工具，以及跑在 Claude Managed Agents 上的 Claude。因为平台接管了托管、会话管理和工具编排，我们的工程师可以把时间花在与销售团队一起设计购买体验上，而不是去搭基础设施。

最终我们选择 Managed Agents，理由如下：

- **上线快。** 一位工程师只用了短短几周，就在 Managed Agents 上做出了最初的购买 agent。
- **技术与非技术同事都能参与。** 工程团队负责代码，但销售与内容负责人可以直接在 Console 里审阅和修改 system prompt。改动先进入 staging agent，所以任何人都能在改动触达客户之前先试一试。
- **专注业务领域，而不是 harness。** Managed Agents 负责跑 agent loop、会话和托管。我们把时间花在 prompt、工具和知识库上——这三样才是销售场景特有的。
- **版本管理让迭代更便宜。** agent 的每次改动都会保存为独立版本。内部测试大约一周时我们已经到了 v7，发布之后仍然每周发布 prompt 改动。需要时，我们可以轻松把新会话指回之前的版本。
- **灵活支持更多用例。** 今天，客户在我们的网站上认识这个 agent。Managed Agents 支持定时运行（scheduled runs），这给了我们一条探索其他类型客户互动的路径。

## **构建购买 agent 过程中学到的经验**

**给 Claude 一个目标，而不是规则。** 讲清 agent 的目标，比给一份详尽的指令清单更有效。例如，像“你的目标是了解客户需求、对潜在客户做资格审核，并推荐最合适的套餐”这样简单的一句话，就比把每一条资格审核要求都列进流程图更管用。

**少即是多。** 我们试过长短、复杂度和结构各不相同的 prompt，发现“少即是多”这条准则效果最好。如今的模型能理解复杂而微妙的目标，并从中倒推。落到实践上，这意味着不要挡着 Claude 的路，而是给它成功所需的知识与上下文，比如按席位定价覆盖哪些内容、账单周期何时结算。

**让领域专家进入开发闭环。** 在 agent 编码不断加速开发周期的今天，这一点正变得越来越有价值。借助 Managed Agents 和 Claude Code 省下来的时间，我们的工程师能花更多时间与销售团队一起打磨以客户为中心的体验。我们得以尽早、频繁地测试 agent，从而实现快速迭代。

**以什么对客户最合适为准。** agent 经常把小团队引向我们的 Team 套餐而不是 Enterprise，因为在某些情况下那对他们才是正确答案。我们认为这是一个特性。落在正确套餐上的买家，与被强行向上销售相比，更有可能留下来并获得更好的体验。

**把每一次 agent 转接销售代表都当成反馈。** 每当 agent 把买家交给销售代表，它都会说明原因。早期，这些原因大多是客户当时还无法通过我们的自助式产品自行完成的事情。这些原因塑造了我们改进体验的方式，而需要人来帮忙才能成单的对话占比已经下降了大约一半。

## **客户侧的变化**

现在，agent 每天 24 小时承接数千次对话。客户能立刻得到问题的答案，而不必等一个预约通话，或来回邮件折腾好几天。实际上，很多客户更喜欢和 agent 而不是真人对话，因为问题一出现，它就能给出快速且信息充分的回答。我们的许多新自助式 Enterprise 客户在购买前都会先与购买 agent 交谈，我们发现，事先与 agent 交流过的客户更清楚自己买的是什么。

## **agent 如何改变了我们的销售组织**

agent 改变了销售代表度过一天的方式。现在，我们能够把团队大部分时间和精力放在在购买旅程更早的阶段教育客户、进行更多实时客户对话，以及到线下活动现场。

影响最大的变化是：销售代表现在拿到的是信息更充分的线索，线索转化成销售机会的频率高于旧的联系表单，成交速度也快大约五天。销售代表开始对话时，就已经知道客户需要什么、已经被告知了什么，以及我们怎样能最好地帮到他们。

例如，我们的一位内部销售代表 Ojas，过去成单大约要来回 10 封邮件，现在大约 6 封。购买 agent 上线后，他把已赢单的产出提高到 2.5 倍，因为他可以专注于那些已经充分了解情况、只差人帮一把就能过关的客户。

不久前，入站还是一支我们跟不上的队列。现在，它是任何买家在任何时间都能开启的一段对话，而我们的销售代表也能更高效地使用时间。购买 agent 是我们迈向覆盖整个客户关系全流程的 agent 的第一步。
