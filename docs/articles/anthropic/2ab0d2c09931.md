# 设计抗 AI 的技术评测

发布于 2026 年 1 月 21 日

从一份 Claude 总能击败、反复迭代三版的性能工程带回家测试中，我们学到了什么。

*本文由 Tristan Hume 撰写，他是 Anthropic 性能优化团队的一名负责人。Tristan 设计——并重新设计——了这份帮助 Anthropic 招聘了几十名性能工程师的带回家测试。*

随着 AI 能力提升，评估技术候选人变得越来越难。一份今天能在人类技能水平之间做出区分的带回家测试，明天可能就被模型轻易解掉——从而在评估上失去作用。

自 2024 年初起，我们的性能工程团队一直使用一份带回家测试：候选人为一个模拟的加速器优化代码。超过 1,000 名候选人完成了它，如今有数十人在此工作，其中包括把我们 Trainium 集群带起来、并发布了自 Claude 3 Opus 以来每一款模型的工程师。

但每一款新的 Claude 模型都迫使我们重新设计这份测试。在同样的时限下，Claude Opus 4 的表现超过了大多数人类申请者。那仍容我们区分出最强的候选人——但接着 Claude Opus 4.5 连那些也追平了。在不限时间时，人类仍能超越模型，但在带回家测试的约束下，我们再也没有办法在我们顶尖候选人的输出与我们最强模型之间做出区分。

我如今已把我们的带回家迭代了三版，试图确保它仍然携带信号。每一次，我都对什么让评测对 AI 辅助保持稳健、什么不稳健，学到了新东西。

本文描述最初的带回家设计、每款 Claude 模型如何击败它，以及我为了确保测试保持在我们顶尖模型能力之前，不得不采取的那些越来越不寻常的办法。尽管我们所做的工作随模型一同演进，我们仍然需要更多强工程师——只是需要越来越有创意地去找到他们。

为此，我们把最初的带回家作为一项公开挑战发布，因为在不限时间时，最佳人类表现仍超过 Claude 所能达到的。如果你能胜过 Opus 4.5，我们很乐意收到你的消息——详情见本文底部。

## 这份带回家的由来

2023 年 11 月，我们正着手训练并发布 Claude Opus 3。我们拿到了新的 TPU 和 GPU 集群，我们的大型 Trainium 集群即将到来，我们在加速器上的花销比以往都大得多，但我们的性能工程师不足以匹配新规模。我在 [Twitter 上发帖](https://x.com/trishume/status/1730386529997238605?s=20)请大家给我们发邮件，这带来的有潜力候选人多到我们无法用标准面试流程评估——而那套流程要消耗员工和候选人大量时间。

我们需要一种更高效评估候选人的方式。于是，我花两周设计了一份带回家测试，能够恰当地捕捉这份职位的要求、并识别最有能力的申请者。

### 设计目标

带回家测试名声不佳。它们通常塞满工程师觉得无聊、作为过滤器效果也很差的通用问题。我的目标不同：创造一种真正引人入胜的东西，让候选人兴奋地参与、并让我们以高解析度捕捉他们的技术能力。

这种形式在评估性能工程技能上，相比现场面试也有优势：

**更长的时间视野：** 工程师编码时极少面对少于一小时的期限。一个 4 小时的窗口（后来缩减为 2 小时）更贴合这份工作的实际性质。它仍比多数真实任务短，但我们需要拿这点与它的负担程度做权衡。

**真实的环境：** 没有人在旁观看或期待你边做边解说。候选人在自己无干扰的编辑器里工作。

**理解与构建工具的时间：** 性能优化需要理解既有系统，有时还要构建调试工具。两者都很难在一次常规的 50 分钟面试里真实评估。

**与 AI 辅助的兼容性：** Anthropic 的[通用候选人指南](https://www.anthropic.com/candidate-ai-guidance)要求候选人在没有另作说明时不使用 AI 完成带回家。对这份带回家，我们明确另作说明。

更长视野的问题对 AI 来说更难彻底解决，所以候选人可以使用 AI 工具（正如他们在工作中那样），同时仍需展示自己的能力。

除了这些形式专属的目标，我还把设计任何面试时所用的同样原则应用到了带回家上：

**真实工作的代表性：** 问题应让候选人尝到这份工作实际涉及什么。

**高信号：** 带回家应避免依赖单一洞见的问题，并确保候选人有很多次机会展示其全部能力——尽量把成败交给运气的成分降到最低。它还应有宽广的打分分布，并确保足够的深度，让连很强的候选人也无法完成一切。

**不要求特定领域知识：** 基础扎实的人能在工作中学习细节。要求狭窄的专长会不必要地限制候选人池。

**有趣：** 快速的开发循环、有深度的有趣问题，以及发挥创意的空间。

### 模拟机器

我为一个带有 TPU 特征的假加速器写了一个 Python 模拟器。候选人在优化运行在这台机器上的代码，使用一个热重载的 [Perfetto](https://perfetto.dev/) trace，它会显示每一条指令，类似[我们在 Trainium 上所用的工具](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/tools/neuron-explorer/overview-device-profiles.html)。

这台机器包含了让加速器优化变得有趣的特性：手动管理的暂存器内存（scratchpad，不同于 CPU，加速器常需要显式内存管理）、VLIW（多个执行单元每周期并行运行，要求高效的指令打包）、SIMD（每条指令对多个元素做向量操作），以及多核（把工作分发到各核）。

任务是一次并行树遍历，刻意不带深度学习味道，因为多数性能工程师当时还没做过深度学习、而能在工作中学习领域细节。这道问题的灵感来自无分支（branchless）的 SIMD 决策树推理——一个作为对过去致敬的经典 ML 优化挑战，此前只有极少数候选人接触过。

候选人从一个完全串行的实现起步，逐步利用机器的并行性。热身是多核并行，然后候选人选择去攻克 SIMD 向量化还是 VLIW 指令打包。最初的版本还包含一个 bug，候选人需要先调试它，以锻炼其构建工具的能力。

## 早期结果

最初的带回家效果很好。Twitter 那批人里有一位得分远高于其他所有人。他在二月初入职，比我们标准流程招来的首批人晚两周。这份测试被证明有预测力：他一开始就着手优化 kernel，并找到一个绕过某个涉及张量索引数学溢出 32 位的、阻塞启动的编译器 bug 的办法。

在接下来一年半里，约 1,000 名候选人完成了带回家，它帮助我们招到了目前性能工程团队的多数人。它对纸面经验有限的候选人尤其有价值：我们几位表现最好的工程师直接从本科而来，但在带回家上展示了足以让我们有信心录用的能力。

反馈是正面的。许多候选人超过了 4 小时的时限还在做，因为他们乐在其中。最强的不限时间提交包括完整的优化迷你编译器，以及若干我没预料到的巧妙优化。

### 然后 Claude Opus 4 击败了它

到 2025 年 5 月，Claude 3.7 Sonnet 已悄悄逼近到这样的程度：超过 50% 的候选人如果干脆把工作全权交给 Claude Code 反而会更好。随后我在带回家上测试了一个 Claude Opus 4 的预发布版。它在 4 小时限制内得出的优化方案，比几乎所有人类都要好。

这不是我第一次有面试被 Claude 模型击败。我在 2023 年专门设计了一道现场面试题，因为当时我们的问题都是围绕常见任务，而早期 Claude 模型对这些有大量知识、因而能轻松解决。我试图设计一道更考验问题求解能力而非知识、且仍基于一个我在工作中解决过的真实（但小众）问题。Claude 3 Opus 击败了那道题的第 1 部分；Claude 3.5 Sonnet 击败了第 2 部分。我们仍在使用它，因为我们的其他现场题同样不抗 AI。

对这份带回家来说，有一个直接的修法。那道问题的深度远超任何人能在 4 小时里探索的，所以我用 Claude Opus 4 找出它开始吃力的地方。那成了第 2 版的新起点。我写了更干净的起始代码、添加了新机器特性以提供更多深度，并移除了多核（Claude 已经解决了它，而它只会拖慢开发循环、却不增加信号）。

我还把时限从 4 小时缩短为 2 小时。我当初选 4 小时，是基于候选人反馈说他们偏好万一在一个 bug 或困惑上卡一会儿时、沉没风险更小，但排期开销正在让我们的流程拖出数周延迟。2 小时更容易塞进一个周末。

第 2 版强调巧妙的优化洞见，而非调试和代码量。它为我们服务得很好——有好几个月。

### 然后 Claude Opus 4.5 击败了那个

当我测试一个 Claude Opus 4.5 的预发布 checkpoint 时，我看着 Claude Code 在问题上下了 2 小时的功、逐步改进它的解法。它解决了最初的瓶颈、实现了所有常见的微优化，并在不到一小时内达到了我们的及格线。

随后它停了下来，确信自己撞上了一个不可逾越的内存带宽瓶颈。大多数人类会得出同样的结论。但有一些巧妙的技巧，能利用问题的结构绕开那个瓶颈。当我告诉 Claude 有可能达到的周期数后，它思考了一会儿，找到了那个技巧。然后它调试、调优，并实现了更多优化。到 2 小时处，它的得分追平了该时限内最佳的人类表现——而那个人类大量使用了带引导的 Claude 4。

为了更严格，我们在内部测试时算力 harness 上试了它，确认它既能在 2 小时内击败人类、又能随时间继续爬升。发布后我们甚至以一种通用方式改进了我们的 harness、拿到了更高的分数。

我遇上了麻烦。我们即将发布一款模型，在它上面，我们在带回家上的最佳策略会是把工作全权交给 Claude Code。

## 权衡各选项

一些同事建议禁用 AI 辅助。我不想这么做。除了执行的挑战，我有一种感觉：既然人们在我们的工作中继续扮演至关重要的角色，我应该能想出 *某种* 办法，让 *在有 AI 的* 环境里、他们仍能像在工作中那样脱颖而出。我还不想屈服于那种 [想法](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/)：人类只在比几小时更长的任务上才有优势。

其他人建议把标准提高到「大幅超越 Claude Code 独自所能达到的」。这里的顾虑是 Claude 干活很快。人类通常要花 2 小时里的一半去读题、理解问题，然后才开始优化。一个试图引导 Claude 的人类，很可能会不断落后、只能在事后理解 Claude 做了什么。占优的策略可能变成坐壁上观。

如今 Anthropic 的性能工程师仍有很多活要做，但它更像是艰苦的调试、系统设计、性能分析、想办法验证我们系统的正确性，以及想办法让 Claude 的代码更简洁优雅。不幸的是，这些东西若没有大量时间或共同上下文，很难客观地测试。设计能代表工作的面试从来都难，如今它比以往更难。

但我也担心：如果我投入去设计一份新的带回家，要么 Claude Opus 4.5 也解了它，要么它会变得太难、人类根本不可能在两小时内完成。

### 尝试 1：一个不同的优化问题

我意识到 Claude 能帮我快速实现我设计的任何东西，这激励我去试着开发一份更难的带回家。我选了一道基于我在 Anthropic 做过的、更棘手的 kernel 优化之一的问题：在 2D TPU 寄存器上做一次高效的数据[转置（transposition）](https://en.wikipedia.org/wiki/Transpose)，同时避免[存储体冲突（bank conflicts）](https://feldmann.nyc/blog/smem-microbenchmarks)。我把它蒸馏成模拟机器上一个更简单的问题，并让 Claude 在不到一天内实现了改动。

Claude Opus 4.5 找到了一个我连想都没想到的极佳优化。通过仔细分析，它意识到它可以转置整个计算、而非想法子转置数据，并据此重写了整个程序。

在我的真实情形里，这行不通，所以我打了补丁移除那条路径。Claude 随后有进展，但找不到最高效的解。看起来我有了我的新问题，现在我只需希望人类候选人能足够快搞出来。但我有些挥之不去的疑虑，于是我用 Claude Code 的「ultrathink」功能、配合更长的思考预算又核查了一遍……它解出来了。它甚至知道修复存储体冲突的技巧。

事后看来，这不是该试的正确问题。许多平台上的工程师都曾为数据转置和存储体冲突苦苦挣扎，所以 Claude 有大量训练数据可借鉴。虽然我凭第一性原理找到了我的解，Claude 却能从一个更大的经验工具箱里取材。

### 尝试 2：走得更怪

我需要一道问题，在那里人类推理能胜过 Claude 更大的经验基础：某种足够分布外（out of distribution）的东西。不幸的是，这与我「要能认出像这份工作」的目标相冲突。

我想了想我最享受的那些最不寻常的优化问题，落到了 [Zachtronics 游戏](https://www.zachtronics.com/)上。这些编程解谜游戏使用不寻常、高度受限的指令集，迫你用非传统方式编程。例如，在 [Shenzhen I/O](https://www.zachtronics.com/shenzhen-io/) 里，程序被拆到多个相互通信的芯片上，每个只持有约 10 条指令、带一两个状态寄存器。巧妙的优化常常涉及把状态编码进指令指针或分支标志。

我设计了一份新的带回家，由若干谜题组成，使用一个微小、高度受限的指令集，以最小指令数来优化解法。我实现了一个中等难度的谜题，并在 Claude Opus 4.5 上测试。它失败了。我又填上更多谜题，并让同事核实：不像我那样浸淫于该问题的人，仍能胜过 Claude。

不同于 Zachtronics 游戏，我刻意不提供任何可视化或调试工具。起始代码只检查解是否有效。构建调试工具正是被考察的一部分：你要么精心插入 print 语句，要么让一个编码模型在几分钟内生成一个交互式调试器。关于如何投入工具建设的判断，本身就是信号的一部分。

我对这份新带回家相当满意。它可能比原来的方差更低，因为它由更多独立的子问题组成。早期结果令人鼓舞：得分与候选人过往工作的水准相关性良好，而我最有能力的同事之一得分超过了迄今任何一位候选人。

放弃原来那份的真实感和多样深度，我仍感惋惜。但真实感或许是我们已不再拥有的奢侈品。原版之所以奏效，是因为它像真实工作。替代品之所以奏效，是因为它模拟新颖的工作。

## 一项公开挑战

我们发布最初的带回家，供任何人在不限时间下尝试。在足够长的时间视野上，人类专家[保持着](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/)对当前模型的优势。有史以来提交的最快人类解，大幅超过了 Claude 即便带着大量测试时算力所达到的。

发布的版本从零开始（像第 1 版），但使用第 2 版的指令集和单核设计，因此周期数可与第 2 版比较。

性能基准（以模拟机器的时钟周期计）：

- **2164 周期**：Claude Opus 4 在测试时算力 harness 里跑了很久之后
- **1790 周期**：Claude Opus 4.5 在一次随意的 Claude Code 会话中，约与 2 小时内最佳人类表现持平
- **1579 周期**：Claude Opus 4.5 在我们的测试时算力 harness 里跑了 2 小时之后
- **1548 周期**：Claude Sonnet 4.5 在远超 2 小时的测试时算力之后
- **1487 周期**：Claude Opus 4.5 在 harness 里跑了 11.5 小时之后
- **1363 周期**：Claude Opus 4.5 在一个改进的测试时算力 harness 里跑了很久之后

[在 GitHub 上下载](https://github.com/anthropics/original_performance_takehome)。如果你优化到 1487 周期以下、击败了 Claude 发布时的最佳表现，请发邮件到 [performance-recruiting@anthropic.com](mailto:performance-recruiting@anthropic.com)，附上你的代码和一份简历。

或者你可以[通过我们的常规流程申请](https://www.anthropic.com/careers/jobs)，那会使用我们（如今）抗 Claude 的带回家。我们很好奇它还能撑多久。
