# 为 agent 编写高效的工具——借助 agent

发布于 2025 年 9 月 11 日

agent 的有效性，取决于我们给它们的工具。我们分享如何编写高质量的工具和评估，以及如何借助 Claude 为它自己优化工具来提升性能。

[Model Context Protocol（MCP）](https://modelcontextprotocol.io/docs/getting-started/intro)能给 LLM agent 赋予多达数百个工具来解决真实世界任务。但我们如何把这些工具做到极致有效？

在本文里，我们描述我们在各种 agentic AI 系统上提升性能最有效的技术 1。

我们先讲你如何能：

- 构建并测试你工具的原型
- 与 agent 一起创建并运行对你工具全面的评估
- 与像 Claude Code 这样的 agent 协作，自动提升你工具的性能

我们以我们在过程中识别出的、编写高质量工具的几条关键原则作结：

- 选择该实现（以及不该实现）哪些正确的工具
- 给工具做命名空间化，以界定功能的清晰边界
- 从工具返回有意义的上下文给 agent
- 为 token 效率优化工具响应
- 对工具描述和规格做 prompt 工程

构建一个评估能让你系统地衡量你工具的性能。你可以用 Claude Code 对照这个评估自动优化你的工具。

## 什么是工具？

在计算里，确定性系统给定相同输入每次都产出相同输出，而*非确定性*系统——像 agent——即便从相同起点也能生成多样的响应。

当我们传统地编写软件时，我们在确定性系统之间确立一份契约。例如，一个像 `getWeather(“NYC”)` 的函数调用，每次被调用时都会以完全相同的方式去取纽约市的天气。

工具是一种新型软件，它反映的是确定性系统与非确定性 agent 之间的一份契约。当用户问「我今天该带伞吗？」，一个 agent 可能调用天气工具、凭一般知识作答、甚至先就地点问一个澄清问题。偶尔，一个 agent 可能产生幻觉、或甚至未能领会如何使用一个工具。

这意味着在给 agent 编写软件时，我们要从根本上重构我们的方法：不是按我们为他开发者或系统编写函数和 API 那样去写工具和 [MCP 服务器](https://modelcontextprotocol.io/)，我们需要为 agent 设计它们。

我们的目标是扩大 agent 能有效运作的覆盖面——让它们通过工具、采用多种成功策略来解决广泛的任务。幸运的是，以我们的经验，对 agent 最「符合人体工学」的工具，作为人类理解起来也出奇地直观。

## 如何编写工具

在本节，我们描述你如何与 agent 协作，既编写又改进你给它们的工具。先快速搭起你工具的原型并在本地测试。然后，跑一次全面的评估来衡量后续改动。与 agent 并肩工作，你可以重复评估并改进你工具的过程，直到你的 agent 在真实任务上取得强劲表现。

### 构建一个原型

若不动手自己试，很难预判 agent 会觉得哪些工具符合人体工学、哪些不会。先快速搭起你工具的原型。如果你用 [Claude Code](https://www.anthropic.com/claude-code) 写你的工具（可能一次性成型），给 Claude 提供任何软件库、API 或 SDK 的文档会有帮助（包括你的工具所依赖的 [MCP SDK](https://modelcontextprotocol.io/docs/sdk)）。LLM 友好的文档通常能在官方文档站的扁平 `llms.txt` 文件里找到（这里是[我们 API 的](https://docs.anthropic.com/llms.txt)）。

把你的工具包进一个[本地 MCP 服务器](https://modelcontextprotocol.io/docs/develop/connect-local-servers)或[桌面扩展](https://www.anthropic.com/engineering/desktop-extensions)（DXT），会让你能在 Claude Code 或 Claude 桌面应用里连接并测试你的工具。

要把你的本地 MCP 服务器连到 Claude Code，运行 `claude mcp add <name> <command> [args...]`。

要把你的本地 MCP 服务器或 DXT 连到 Claude 桌面应用，分别前往 `Settings > Developer` 或 `Settings > Extensions`。

工具也能被直接传入 [Anthropic API](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview) 调用做程序化测试。

自己测试工具以发现任何毛刺。从用户处收集反馈，为你期待工具所促成的用例和 prompt 建立直觉。

### 运行一次评估

接下来，你需要通过跑一次评估来衡量 Claude 使用你工具的优劣。先生成大量基于真实用途的评估任务。我们建议与一个 agent 协作，帮你分析结果并决定如何改进你的工具。在我们[工具评估 cookbook](https://platform.claude.com/cookbook/tool-evaluation-tool-evaluation)里端到端地看这一过程。

**生成评估任务**

有了你早期的原型，Claude Code 能快速浏览你的工具并创建数十个 prompt 与响应配对。Prompt 应当受真实用途启发、并基于真实的数据源和服务（例如内部知识库和微服务）。我们建议你避免过于简单或肤浅的「沙盒」环境，那没有用足够的复杂性来压力测试你的工具。强的评估任务可能需要多个工具调用——可能几十个。

下面是一些强任务的例子：

- 下周约 Jane 开个会，讨论我们最新的 Acme Corp 项目。附上我们上次项目规划会议的笔记，并预订一间会议室。
- 客户 ID 9182 报告他们为一次购买尝试被扣了三次费。找出所有相关的日志条目，并判定是否有其他客户受同一问题影响。
- 客户 Sarah Chen 刚提交了一个取消请求。准备一份挽留方案。判定：(1) 他们为什么离开，(2) 什么挽留方案最具吸引力，(3) 在提出方案前我们应留意的任何风险因素。

而下面是一些较弱的任务：

- 下周与 jane@acme.corp 约个会。
- 在支付日志里搜索 `purchase_complete` 和 `customer_id=9182`。
- 找到客户 ID 45892 的取消请求。

每个评估 prompt 应当与一个可验证的响应或结果配对。你的验证器可以简单到真实答案与采样响应之间的精确字符串比较，也可以高级到请 Claude 来评判响应。避免那种因格式、标点或有效的不同措辞这类无关差异而拒绝正确响应的、过于严格的验证器。

对每个 prompt-响应配对，你也可以选择性地指定你期待 agent 为解决任务而调用的工具，以衡量 agent 在评估期间是否成功领会了每个工具的用途。然而，因为可能有通往正确解任务的多条有效路径，尽量避免过度规定或过拟合到策略。

**运行评估**

我们建议用直接的 LLM API 调用来程序化地运行你的评估。使用简单的 agentic 循环（包裹交替的 LLM API 和工具调用的 `while` 循环）：每个评估任务一个循环。每个评估 agent 被给予单个任务 prompt 和你的工具。

在你评估 agent 的系统 prompt 里，我们建议指示 agent 不仅输出结构化响应块（用于验证），也输出推理和反馈块。指示 agent 在工具和响应块*之前*输出这些，可以通过触发思维链（CoT）行为来提升 LLM 的有效智能。

如果你用 Claude 运行评估，你可以开启[交错思考](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking)，「现成地」获得类似功能。这会帮你探明 agent 为何调用或不调用某些工具、并凸显工具描述和规格里具体的改进之处。

除了顶层准确率，我们建议收集其他指标，像单个工具调用和任务的总运行时间、工具调用总数、token 总消耗、以及工具错误。跟踪工具调用能帮助揭示 agent 所追求的常见工作流、并为工具的整合提供一些机会。

**分析结果**

Agent 是你发现问题的得力伙伴，能在从相互矛盾的工具描述、到低效的工具实现、再到令人困惑的工具 schema 的一切事情上提供反馈。然而，要记着 agent 在其反馈和响应中所省略的，往往比它们所包含的更重要。LLM 并不总能[言其所想](https://www.anthropic.com/research/tracing-thoughts-language-model)。

观察你的 agent 在何处卡壳或困惑。通读你评估 agent 的推理和反馈（或 CoT）以识别毛刺。查看原始文字记录（包括工具调用和工具响应）以捕捉任何 agent 的 CoT 里未明确描述的行为。读懂字里行间；要记着你的评估 agent 未必知道正确的答案和策略。

分析你的工具调用指标。大量冗余的工具调用，可能提示对分页或 token 限制参数做一番恰当的缩放是必要的；大量因无效参数导致的工具错误，可能提示工具可以用更清晰的描述或更好的示例。当我们发布 Claude 的[网络搜索工具](https://www.anthropic.com/news/web-search)时，我们识别到 Claude 在多余地往工具的 `query` 参数后追加 `2025`，使搜索结果产生偏见并降低性能（我们通过改进工具描述把 Claude 引上正路）。

### 与 agent 协作

你甚至能让 agent 替你分析结果并改进工具。只需把你评估 agent 的文字记录拼接起来、粘贴进 Claude Code。Claude 是分析文字记录并一次性重构大量工具的专家——例如，确保工具实现和描述在新改动发生时仍保持自洽。

事实上，本文的大部分建议都来自我们反复用 Claude Code 优化内部工具实现。我们的评估建立在我们内部工作区之上，映照我们内部工作流的复杂性，包括真实的项目、文档和消息。

我们依赖留出测试集，以确保我们不对「训练」评估过拟合。这些测试集揭示：我们能榨取额外的性能提升，甚至超出我们以「专家」工具实现所达到的——无论那些工具是我们研究人员手写的、还是 Claude 自己生成的。

## 编写高效工具的原则

在本节，我们把我们的所学凝练成几条编写高效工具的指导原则。

### 为 agent 选择正确的工具

更多的工具并不总是带来更好的结果。我们观察到的一个常见错误，是那些仅仅包裹现有软件功能或 API 端点的工具——无论它们是否适合 agent。这是因为 agent 与传统软件有截然不同的「可供性（affordances）」——也就是说，它们对能用那些工具采取什么动作，有不同的感知方式。

LLM agent 有有限的「上下文」（即它们一次能处理的信息有上限），而计算机内存既便宜又充足。考虑在通讯录里搜一个联系人这一任务。传统软件程序能高效地逐个存储并处理一长串联系人，在继续前逐一检查。

然而，如果一个 LLM agent 用一个返回所有联系人、然后不得不逐 token 通读的工具，它就是在把有限的上下文空间浪费在无关信息上（想象通过从上到下逐页读来在你的通讯录里搜一个联系人——即暴力搜索）。更好、也更自然的方式（对 agent 和人类都一样）是先跳到相关那一页（也许按字母顺序找到它）。

我们建议先构建几个针对特定高影响力工作流、契合你评估任务的深思熟虑的工具，然后从那里扩展。在通讯录这个例子里，你会选择实现一个 `search_contacts` 或 `message_contact` 工具，而不是一个 `list_contacts` 工具。

工具可以整合功能，在底层处理潜在的*多个*离散操作（或 API 调用）。例如，工具可以在响应里加上相关的元数据来丰富之，或把常链在一起的多步任务在单个工具调用里处理掉。

下面是一些例子：

- 与其实现 `list_users`、`list_events` 和 `create_event` 工具，不如考虑实现一个 `schedule_event` 工具，它找到空闲时间并排定会议。
- 与其实现一个 `read_logs` 工具，不如考虑实现一个 `search_logs` 工具，它只返回相关的日志行和一点周边上下文。
- 与其实现 `get_customer_by_id`、`list_transactions` 和 `list_notes` 工具，不如实现一个 `get_customer_context` 工具，它一次性汇编一个客户所有近期且相关的信息。

确保你构建的每个工具有清晰、独特的用途。工具应当使 agent 能以与人类在访问相同底层资源时相同的方式去细分并解决任务，同时减少那些本会被中间输出消耗掉的上下文。

太多工具或重叠的工具也会让 agent 偏离高效策略。对你所构建（或不构建）的工具做审慎、有选择性的规划，回报颇丰。

### 给你的工具做命名空间化

你的 AI agent 可能会访问数十个 MCP 服务器和数百个不同工具——包括其他开发者的。当工具在功能上重叠或用途含糊时，agent 会对该用哪个感到困惑。

命名空间化（把相关工具归到公共前缀下）能帮着在很多工具之间划出边界；MCP 客户端有时会默认这么做。例如，按服务给工具做命名空间化（如 `asana_search`、`jira_search`）以及按资源做（如 `asana_projects_search`、`asana_users_search`），能帮助 agent 在正确的时间选对工具。

我们发现，在前缀式与后缀式命名空间化之间做选择，对我们的工具使用评估有不可忽略的影响。影响因 LLM 而异，我们鼓励你根据自己的评估选一种命名方案。

agent 可能调错工具、用错的参数调对工具、调用太少的工具、或错误地处理工具响应。通过有选择地实现那些名字反映任务自然细分的工具，你同时减少了加载进 agent 上下文的工具和工具体描述的数量、并把 agentic 计算从 agent 的上下文卸载回工具调用本身。这降低了 agent 整体犯错的风险。

### 从你的工具返回有意义的上下文

出于同样的精神，工具实现应当注意只把高信号的信息返回给 agent。它们应当把上下文相关性置于灵活性之上，并避免低层的技术标识符（例如 `uuid`、`256px_image_url`、`mime_type`）。像 `name`、`image_url` 和 `file_type` 这样的字段，更可能直接为 agent 的下游动作和响应提供信息。

agent 也往往能远比处理晦涩标识符更成功地拿捏自然语言的名字、术语或标识符。我们发现，仅仅把任意的字母数字 UUID 解析为更具语义、更可解释的语言（或甚至一个 0 起始的 ID 方案），就通过减少幻觉显著提升了 Claude 在检索任务上的精确度。

在某些情形里，agent 可能要求同时与自然语言和技术标识符输出交互的灵活性，哪怕只是为触发下游工具调用（例如 `search_user(name='jane')` → `send_message(id=12345)`）。你可以通过在你工具里暴露一个简单的 `response_format` 枚举参数来同时支持两者，让你的 agent 控制工具返回 `“concise”` 还是 `“detailed”` 响应（图见下）。

你可以添加更多格式以获得更大灵活性，类似 GraphQL，你可以选择究竟想要接收哪些信息。下面是一个控制工具响应冗长度的 ResponseFormat 枚举示例：

```
enum ResponseFormat {
   DETAILED = "detailed",
   CONCISE = "concise"
}
```

### 为 token 效率优化工具响应

优化上下文的质量很重要。但优化工具响应返回给 agent 的上下文*数量*同样重要。

我们建议对任何可能消耗大量上下文的工具响应，实现分页、范围选择、过滤和/或截断的某种组合，并配以合理的默认参数值。对 Claude Code，我们默认把工具响应限制在 25,000 token。我们预期 agent 的有效上下文长度会随时间增长，但对上下文高效工具的需求会持续。

如果你选择截断响应，务必用有用的指令来引导 agent。你可以直接鼓励 agent 采用更 token 高效的策略，例如对一个知识检索任务做多次小而精准的搜索，而不是一次宽泛的搜索。同样，如果一次工具调用抛出一个错误（例如在输入验证期间），你可以对你的错误响应做 prompt 工程，清晰传达具体、可执行的改进，而不是晦涩的错误码或 traceback。

### 对你的工具描述做 prompt 工程

我们如今来到提升工具最有效的方法之一：对你的工具描述和规格做 prompt 工程。因为它们被加载进你的 agent 上下文，它们能集体地把 agent 引向高效的工具调用行为。

在编写工具体描述和规格时，想象你会如何向团队里一位新入职者描述你的工具。考虑你或许会隐含带上的上下文——专门的查询格式、小众术语的定义、底层资源之间的关系——并把它显式化。通过清晰描述（并用严格的数据模型强制执行）预期的输入和输出来避免歧义。特别地，输入参数应当被无歧义地命名：与其用一个名为 `user` 的参数，不如用一个名为 `user_id` 的参数。

有了评估，你能更有信心地衡量你 prompt 工程的影响。即便对工具体描述的小小打磨也能带来戏剧性的提升。在[我们对工具体描述做了精确打磨](https://www.anthropic.com/engineering/swe-bench-sonnet)之后，Claude Sonnet 3.5 在 SWE-bench Verified 评估上达到了最先进的表现，显著降低了错误率并改善了任务完成。

我们[开发者指南](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#best-practices-for-tool-definitions)里有关于工具体定义的其他最佳实践。如果你在构建给 Claude 的工具，我们也建议阅读工具如何被动态加载进 Claude 的[系统 prompt](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#tool-use-system-prompt)。最后，如果你在为某个 MCP 服务器写工具，[工具体注释](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)有助于披露哪些工具需要开放世界访问或会做破坏性更改。

## 展望未来

要为 agent 构建高效的工具，我们需要把我们的软件开发实践从可预测的、确定性的模式，转向非确定性的模式。

通过我们在本文里描述的、迭代式、评估驱动的过程，我们识别出了工具为何成功的恒常模式：有效的工具被刻意而清晰地定义、审慎地利用 agent 上下文、能在多样的工作流里彼此组合、并让 agent 能直观地解决真实世界任务。

未来，我们预期 agent 与世界交互的具体机制会演化——从对 MCP 协议的更新，到底层 LLM 本身的升级。通过对为 agent 改进工具采取一种系统化、评估驱动的方法，我们能确保随着 agent 变得更有能力，它们所使用的工具也随之演进。
