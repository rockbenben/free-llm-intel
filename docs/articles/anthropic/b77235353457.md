Claude Code 是一个 agentic 编码环境。不同于一个回答问题然后等着的聊天机器人，Claude Code 能读你的文件、运行命令、做出更改，并在你旁观、redirect 或干脆走开的情况下自主地推进问题的解决。

这改变了你的工作方式。与其自己写代码、再请 Claude 审阅，不如描述你想要的、让 Claude 想办法去构建它。Claude 会探索、规划并实现。

但这种自主性仍伴随着一条学习曲线。Claude 在某些你需要理解的约束内工作。

本指南涵盖的那些模式，已被 Anthropic 内部团队、以及跨各种代码库、语言和环境使用 Claude Code 的工程师证明有效。关于 agentic 循环如何运作，见「How Claude Code works」。

多数最佳实践都基于一条约束：Claude 的上下文窗口填得很快，而随着它填满，性能会下降。

Claude 的上下文窗口装着你的整个对话，包括每一条消息、Claude 读的每一个文件、每一条命令输出。然而这能很快填满。一次调试会话或一次代码库探索，就可能生成并消耗数以万计的 token。

这之所以要紧，是因为 LLM 性能随上下文填满而下降。当上下文窗口将满时，Claude 可能开始「忘记」早先的指令或犯更多错误。上下文窗口是最需要管理的资源。要看一次会话在实践中如何被填满，可观看一段「startup 时加载了什么、每次文件读取花多少」的交互式讲解；用一条自定义状态栏持续跟踪上下文用量；并见「Reduce token usage」了解减少 token 用量的策略。

## [​](https://code.claude.com/docs/en/best-practices#give-claude-a-way-to-verify-its-work)给 Claude 一个验证其工作的途径

给 Claude 一个它能跑的检查：测试、一次构建、一张用来比对的截图。这正是「你要盯着的会话」与「你能走开的会话」之间的区别。

Claude 在工作看起来完成时停下。没有它能跑的检查，「看起来完成」就是唯一可用的信号，而你就成了验证回路：每个错误都要等你去注意到它。给 Claude 一个能产出通过或失败的东西，回路就自行闭合。Claude 做工作、跑检查、读结果，并迭代直到检查通过。

这个检查可以是任何能返回一个 Claude 能在对话里读到的信号的东西：一套测试、一个构建退出码、一个 linter、一个把输出对照 fixture 做 diff 的脚本，或一张对照设计比对的浏览器截图。在 Claude 的检查通过后，自己跑 /verify 来对照运行的应用确认这一改动。

| 策略 | 之前 | 之后 |
| --- | --- | --- |
| **提供验证标准** | *"实现一个验证邮箱地址的函数"* | *"写一个 validateEmail 函数。示例测试用例：[user@example.com](mailto:user@example.com) 为 true，invalid 为 false，[user@.com](mailto:user@.com) 为 false。实现后运行测试"* |
| **可视化地验证 UI 改动** | *"让仪表盘好看点"* | *"[粘贴截图] 实现这个设计。给结果截一张图并对照原图。列出差异并修掉"* |
| **处理根因而非症状** | *"构建失败了"* | *"构建带着这个错误失败：[粘贴错误]。修好它并验证构建成功。处理根因，别压制这个错误"* |

一旦检查存在，决定它把「停」把关得多严：

- **在一次 prompt 里**：请 Claude 在同一条消息里跑检查并迭代，如上表所示。
- **跨一次会话**：把检查设成一个 [`/goal` 条件](https://code.claude.com/docs/en/goal)。一个独立的评估者在每轮之后重查它，而 Claude 一直工作直到目标达成。若 Claude 停滞，Claude Code 最终会在目标仍设着的情况下停止运行——见 [/goal 评估如何运作](https://code.claude.com/docs/en/goal#how-evaluation-works)。
- **作为一道确定性闸门**：一个 [Stop hook](https://code.claude.com/docs/en/hooks#stop) 把你的检查作为脚本运行、并拦截这一轮结束直到它通过。[Stop 输入](https://code.claude.com/docs/en/hooks#stop-input)说明了连续拦截的上限。
- **借助第二意见**：一个[验证子 agent](https://code.claude.com/docs/en/sub-agents)，或一个检查自身发现的[动态工作流](https://code.claude.com/docs/en/workflows)，会让一个新模型去试图反驳该结果，好让做工作的 agent 不是给自身打分的那个。

每一步都拿设置换注意力。prompt 版本今天对任何任务都管用。/goal 和 Stop hook 版本，则让一次无人值守的运行能在没有你的情况下正确地收尾。

让 Claude 展示证据、而非断言成功：测试输出、它跑了什么命令并返回了什么、或结果的一张截图。审阅证据比你自己重跑验证更快，也适用于你未曾盯着的会话。

## [​](https://code.claude.com/docs/en/best-practices#explore-first-then-plan-then-code)先探索，再规划，再编码

把研究与规划和实现分开，以避免解决了错误的问题。

让 Claude 直接跳到编码，可能产出解决错误问题的代码。用 plan 模式把探索与执行分开。

推荐的工作流有四个阶段：

1 探索

按 Shift+Tab 直到状态栏显示「⏸ plan mode on」，或用一个 `claude --permission-mode plan` 开始会话，就进入了 plan 模式。Claude 读文件并回答问题，而不做任何更改。

```
read /src/auth and understand how we handle sessions and login.
also look at how we manage environment variables for secrets.
```

2 规划

请 Claude 创建一份详细的实现计划。

```
I want to add Google OAuth. What files need to change?
What's the session flow? Create a plan.
```

按 Ctrl+G 在你的文本编辑器里打开这份计划，在 Claude 继续之前直接编辑它。

3 实现

通过批准计划或按 Shift+Tab 切出 plan 模式，然后让 Claude 编码，并对照它的计划做验证。

```
implement the OAuth flow from your plan. write tests for the
callback handler, run the test suite and fix any failures.
```

4 提交

请 Claude 用一个描述性的信息提交、并创建一个 PR。

```
commit with a descriptive message and open a PR
```

plan 模式很有用，但也增加开销。对于范围清晰、改动很小（如修一个拼写、加一行日志、或重命名一个变量）的任务，直接请 Claude 做。

规划最有用的时候，是你对方法拿不准、改动涉及多个文件、或你不熟悉被修改的代码时。如果你能用一句话描述这个 diff，就跳过规划。

## [​](https://code.claude.com/docs/en/best-practices#provide-specific-context-in-your-prompts)在 prompt 里提供具体的上下文

你的指令越精确，需要的更正就越少。

Claude 能推断意图，但它读不了你的心。引用具体的文件、提及约束、并指向示例模式。

| 策略 | 之前 | 之后 |
| --- | --- | --- |
| **界定任务范围。** 指定哪个文件、什么场景、以及测试偏好。 | *"给 foo.py 加测试"* | *"给 foo.py 写一个测试，覆盖用户已登出这一边缘情形。避免 mock。"* |
| **指向来源。** 把 Claude 导向那个能回答问题的来源。 | *"为什么 ExecutionFactory 有个这么怪的 api？"* | *"翻阅 ExecutionFactory 的 git 历史，总结它的 api 是怎么变成这样的"* |
| **引用已有的模式。** 把 Claude 指向你代码库里的模式。 | *"加一个日历组件"* | *"看看首页上已有组件是怎么实现的以理解模式。HotDogWidget.php 是个好例子。照着那个模式实现一个新的日历组件，让用户能选月份并向前向后翻页来选年份。除代码库已用的库外，从零构建。"* |
| **描述症状。** 提供症状、可能的位置、以及「修好」长什么样。 | *"修登录 bug"* | *"用户报告会话超时后登录失败。检查 src/auth/ 里的认证流程，特别是 token 刷新。写一个能复现问题的失败测试，然后修好它"* |

当你在探索、且能负担得起纠偏时，含糊的 prompt 可能很有用。像 "what would you improve in this file?" 这样的 prompt，能浮现出你本不会想到去问的东西。

### [​](https://code.claude.com/docs/en/best-practices#provide-rich-content)提供丰富的内容

用 `@` 引用文件、粘贴截图/图像，或直接把数据管道进来。

你可以通过若干方式向 Claude 提供丰富的数据：

- **用 `@` 引用文件**，而不是描述代码在哪。Claude 会在回应前读那个文件。
- **直接粘贴图像**。复制/粘贴或拖放图像到 prompt 里。
- **给出 URL** 用于文档和 API 参考。用 `/permissions` 把常用的域名列入允许清单。
- **管道输入数据**，通过运行 `cat error.log | claude -p "explain this error"` 直接把文件内容送进去。
- **让 Claude 自行抓取它所需的。** 告诉 Claude 用 Bash 命令、MCP 工具或读文件自己去拉上下文。

## [​](https://code.claude.com/docs/en/best-practices#configure-your-environment)配置你的环境

几个设置步骤能让 Claude Code 在你所有会话里显著更有效。关于扩展功能及何时用每一项的完整概览，见「Extend Claude Code」。

### [​](https://code.claude.com/docs/en/best-practices#write-an-effective-claude-md)写一份有效的 CLAUDE.md

运行 `/init`，基于你当前的项目结构生成一份起始的 CLAUDE.md 文件，然后随时间打磨它。

CLAUDE.md 是一份特殊文件，Claude 在每次对话开始时读它。纳入 Claude 猜不到的 Bash 命令、代码风格和工作流规则。这给 Claude 一份它无法仅从代码推断出来的持久上下文。

CLAUDE.md 文件没有要求的格式，但把它保持得短而人类可读。例如：

```
# Code style
- Use ES modules (import/export) syntax, not CommonJS (require)
- Destructure imports when possible (eg. import { foo } from 'bar')

# Workflow
- Be sure to typecheck when you're done making a series of code changes
- Prefer running single tests, and not the whole test suite, for performance
```

运行 `/context` 确认 Claude 加载了这个文件。CLAUDE.md 每次会话都被加载，所以只纳入那些广泛适用的东西。对于有时才相关的领域知识或工作流，改用 skills。Claude 按需加载它们，而不给每次对话增加负担。

保持精炼。对每一行，问：「删掉这行会让 Claude 犯错吗？」如果不会，就砍掉。臃肿的 CLAUDE.md 文件会让 Claude 忽略你真正的指令！

| ✅ 纳入 | ❌ 排除 |
| --- | --- |
| Claude 猜不到的 Bash 命令 | 任何 Claude 能通过读代码弄清的东西 |
| 与默认不同的代码风格规则 | Claude 已知晓的标准语言惯例 |
| 测试说明和首选的测试运行器 | 详细的 API 文档（改为放一个文档链接） |
| 仓库礼仪（分支命名、PR 约定） | 频繁变化的信息 |
| 你项目特有的架构决策 | 冗长的解释或教程 |
| 开发环境的怪癖（所需的环境变量） | 逐文件的代码库描述 |
| 常见的坑或不明显的行为 | 像「写干净的代码」这样不言自明的实践 |

如果 Claude 尽管有一条针对某事的规则却仍一直做你不想要的，那文件大概太长了、规则正被淹没。如果 Claude 问你那些在 CLAUDE.md 里已有答案的问题，那措辞可能含糊。把 CLAUDE.md 当作代码来对待：在出问题时审阅它、定期修剪它、并通过观察 Claude 的行为是否真的改变来测试改动。对于一份已提交的 CLAUDE.md，运行 /doctor，Claude 会为那些它能从代码库推导出的内容提议删减。

如果 Claude 一直跳过某一条指令，就单独给那一行加强调，比如「IMPORTANT」。如果你强调很多行，就没有一行能凸显。把 CLAUDE.md 提交进 git，好让你的团队能贡献。这份文件的价值随时间复利。

CLAUDE.md 文件可以用 `@path/to/import` 语法导入额外文件。关于导入规则以及 CLAUDE.md 文件能放在何处，见「CLAUDE.md files」。

### [​](https://code.claude.com/docs/en/best-practices#configure-permissions)配置权限

要在不放弃掌控的情况下得到更少的提示，用 `/permissions` 预先批准你信任的工具，并让沙箱化的命令无需询问就运行，用 `/sandbox`。当你想自己批准编辑和命令时，切到 Manual 模式。

从 Claude Code v2.1.283 起，auto 模式是交互式终端和 VS Code 会话内建的起始许可模式：一个独立的分类器模型替你审阅多数动作、只拦截那些看起来有风险的东西，例如范围升级、未知基础设施、或由敌意内容驱动的动作。在更早的版本上，auto 模式仅在 Pro、Max 和 Team 套餐上是内建的起始许可模式。

在 Manual 模式下，Claude Code 在那些可能修改你系统的动作前询问：文件写入、Bash 命令、MCP 工具。那安全但繁琐。到第十次批准时，你是在一路点击而非审阅。两个工具在 Manual 模式下削减这些打断、在 auto 模式下也适用：

- **权限允许清单**：许可你确知安全的具体工具，如 `npm run lint` 或 `git commit`
- **沙箱化**：启用 OS 级的隔离，限制文件系统和网络访问，让 Claude 能在定义好的边界内更自由地工作

更多关于许可模式、权限规则和沙箱化的内容见对应文档。

### [​](https://code.claude.com/docs/en/best-practices#use-cli-tools)使用 CLI 工具

在与外部服务交互时，告诉 Claude Code 使用像 `gh`、`aws`、`gcloud` 和 `sentry-cli` 这样的 CLI 工具。

CLI 工具是与外部服务交互最上下文高效的方式。如果你用 GitHub，安装 `gh` CLI。Claude 知道如何用它创建 issue、开 pull request、读评论。没有 `gh`，Claude 仍能用 GitHub API，但未认证的请求常撞到速率限制。

Claude 对于学习它尚不认识的 CLI 工具也很在行。试试像 `Use 'foo-cli-tool --help' to learn about foo tool, then use it to solve A, B, C.` 这样的 prompt。

### [​](https://code.claude.com/docs/en/best-practices#connect-mcp-servers)连接 MCP 服务器

用 `claude mcp add` 加一个服务器名和 URL 或命令，来连接像 Notion、Figma 或你的数据库这样的外部工具。例如：`claude mcp add --transport http notion https://mcp.notion.com/mcp`。

有了 MCP 服务器，你可以请 Claude 从 issue 跟踪器实现功能、查询数据库、分析监控数据、集成 Figma 的设计、并自动化工作流。

### [​](https://code.claude.com/docs/en/best-practices#set-up-hooks)设置 hook

对那些每次都必须发生、零例外地使用 hook。

Hook 在 Claude 工作流的特定点自动运行脚本。不同于带建议性质的 CLAUDE.md 指令，hook 是确定性的、保证动作发生。

Claude 能替你写 hook。试试像「Write a hook that runs eslint after every file edit」或「Write a hook that blocks writes to the migrations folder.」这样的 prompt。直接编辑 `.claude/settings.json` 来手工配置 hook，并运行 `/hooks` 来浏览已配置了什么。

### [​](https://code.claude.com/docs/en/best-practices#create-skills)创建 skill

在 `.claude/skills/` 里创建 `SKILL.md` 文件，给 Claude 领域知识和可复用的工作流。

Skills 用那些专属于你项目、团队或领域的信息来扩展 Claude 的知识。Claude 在相关时自动应用它们，或者你能用 `/skill-name` 直接调用它们。

通过在 `.claude/skills/` 里添加一个带 `SKILL.md` 的目录来创建 skill：

```
---
name: api-conventions
description: REST API design conventions for our services
---
# API Conventions
- Use kebab-case for URL paths
- Use camelCase for JSON properties
- Always include pagination for list endpoints
- Version APIs in the URL path (/v1/, /v2/)
```

Skills 也能定义你可直接调用的可重复工作流：

```
---
name: fix-issue
description: Fix a GitHub issue
disable-model-invocation: true
---
Analyze and fix the GitHub issue: $ARGUMENTS.

1. Use `gh issue view` to get the issue details
2. Understand the problem described in the issue
3. Search the codebase for relevant files
4. Implement the necessary changes to fix the issue
5. Write and run tests to verify the fix
6. Ensure code passes linting and type checking
7. Create a descriptive commit message
8. Push and create a PR
```

运行 `/fix-issue 1234` 来调用它。对那些有副作用、你想手动触发的工作流，用 `disable-model-invocation: true`。

### [​](https://code.claude.com/docs/en/best-practices#create-custom-subagents)创建自定义子 agent

在 `.claude/agents/` 里定义专门的助手，Claude 可以把孤立的任务委派给它们。

子 agent 在它们自己的上下文里运行，有它们自己的一套允许工具。它们对那类要读很多文件、或需要专门聚焦而不愿弄乱你主对话的任务很有用。

```
---
name: security-reviewer
description: Reviews code for security vulnerabilities
tools: Read, Grep, Glob, Bash
model: opus
---
You are a senior security engineer. Review code for:
- Injection vulnerabilities (SQL, XSS, command injection)
- Authentication and authorization flaws
- Secrets or credentials in code
- Insecure data handling

Provide specific line references and suggested fixes.
```

明确地让 Claude 使用子 agent：「Use a subagent to review this code for security issues.」

### [​](https://code.claude.com/docs/en/best-practices#install-plugins)安装插件

运行 `/plugin` 浏览市场。插件无需配置就能添加 skill、工具和集成。

插件把 skill、hook、子 agent 和 MCP 服务器打包进一个来自社区和 Anthropic 的可安装单元。如果你用一种带类型的语言，安装一个代码智能（code intelligence）插件，给 Claude 精确的符号导航和编辑后自动的错误检测。

关于在 skill、子 agent、hook 和 MCP 之间如何选择，见「Extend Claude Code」。

## [​](https://code.claude.com/docs/en/best-practices#communicate-effectively)有效地沟通

向 Claude 提出你会问另一位工程师的问题，而对更大的功能，让 Claude 先采访你、并在你开始实现前写一份规格。

### [​](https://code.claude.com/docs/en/best-practices#ask-codebase-questions)问代码库问题

向 Claude 提出你会问一位资深工程师的问题。

在入职一个新代码库时，用 Claude Code 做学习和探索。你可以向 Claude 提出你会向另一位工程师提的那类问题：

- 日志是怎么工作的？
- 我如何新建一个 API 端点？
- `foo.rs` 第 134 行的 `async move { ... }` 做了什么？
- `CustomerOnboardingFlowImpl` 处理哪些边缘情形？
- 为什么这段代码在第 333 行调用 `foo()` 而不是 `bar()`？

这样用 Claude Code 是一种有效的入职工作流，改善上手时间、减轻其他团队的负担。无需特别的 prompt：直接提问即可。

### [​](https://code.claude.com/docs/en/best-practices#let-claude-interview-you)让 Claude 采访你

对更大的功能，先让 Claude 采访你。从一个最小的 prompt 开始，请 Claude 用 AskUserQuestion 工具采访你。

Claude 会问那些你可能还没考虑到的东西，包括技术实现、UI/UX、边缘情形和权衡。在发 prompt 之前把 [brief description] 换成你的功能。

```
I want to build [brief description]. Interview me in detail using the AskUserQuestion tool.

Ask about technical implementation, UI/UX, edge cases, concerns, and tradeoffs. Don't ask obvious questions, dig into the hard parts I might not have considered.

Keep interviewing until we've covered everything, then write a complete spec to SPEC.md.
```

一旦规格完成，开一个新会话去执行它。新会话带着专注实现的干净上下文，而你有一份可参考的书面规格。

最有用的规格是自包含的：它们点名所涉的文件和接口、声明什么超出范围、并以一个端到端的验证步骤收尾，证明功能可行。花在做准规格上的时间，比花在盯着实现上的时间回报更高。

## [​](https://code.claude.com/docs/en/best-practices#manage-your-session)管理你的会话

对话是持久且可回退的。善加利用这一点！

### [​](https://code.claude.com/docs/en/best-practices#course-correct-early-and-often)尽早且频繁地纠偏

在你注意到 Claude 跑偏的第一时间纠正它。

最好的结果来自紧密的反馈回路。尽管 Claude 偶尔会一次就完美地解决问题，但快速纠正它通常更快地产出更好的解法。

- **`Esc`**：用 `Esc` 键在 Claude 动作中途停下它。上下文被保留，于是你能 redirect。
- **`Esc + Esc` 或 `/rewind`**：按两次 `Esc` 或运行 `/rewind` 打开回退菜单，恢复先前的对话和代码状态，或从选中的一条消息开始做摘要。
- **"Undo that"**：让 Claude 回退它的改动。
- **`/clear`**：在不相关的任务之间重置上下文。冗长的会话带着无关上下文会降低性能。

如果你在一次会话里就同一问题纠正了 Claude 超过两次，上下文里已塞满了失败的做法。运行 `/clear`，带一份把你所学纳入其中的、更具体的 prompt 重新开始。一份干净会话配更好的 prompt，几乎总是胜过带着累积更正的冗长会话。

### [​](https://code.claude.com/docs/en/best-practices#manage-context-aggressively)积极地管理上下文

在不相关的任务之间运行 `/clear` 来重置上下文。

当你接近上下文极限时，Claude Code 会自动压缩对话历史，保留重要的代码和决策同时腾出空间。

在长会话期间，Claude 的上下文窗口会填满无关的对话、文件内容和命令。这会降低性能、有时会让 Claude 分心。

- 在任务之间频繁使用 `/clear` 来彻底重置上下文窗口
- 当自动压缩触发时，Claude 会总结最重要的东西，包括代码模式、文件状态和关键决策
- 为了更多控制，运行 `/compact <instructions>`，例如 `/compact Focus on the API changes`
- 要只压缩对话的一部分，用 `Esc + Esc` 或 `/rewind`，选一个消息检查点，然后选 **Summarize from here** 或 **Summarize up to here**。前者把该点之后的消息浓缩、同时保留更早的上下文；后者把更早的消息浓缩、同时完整保留最近的。见回退菜单的摘要选项。
- 在 CLAUDE.md 里用像 `"When compacting, always preserve the full list of modified files and any test commands"` 这样的指令来定制压缩行为，确保关键上下文在摘要中存活
- 对于那些不需要留在上下文里的问题，用 [`/btw`](https://code.claude.com/docs/en/interactive-mode#side-questions-with-%2Fbtw)。答案从不进入对话历史，于是你能在不增长上下文的情况下查一个细节。

### [​](https://code.claude.com/docs/en/best-practices#use-subagents-for-investigation)用子 agent 做调查

用 "use subagents to investigate X" 委派研究。它们在单独的上下文里探索，让你的主对话为实现保持干净。

因为上下文是你的根本约束，用子 agent 把研究挡在它之外。当 Claude 研究一个代码库时，它会读很多文件，全都消耗你的上下文。子 agent 在单独的上下文窗口里运行、并回报摘要：

```
Use subagents to investigate how our authentication system handles token
refresh, and whether we have any existing OAuth utilities I should reuse.
```

你也可以在 Claude 实现了某样东西之后用子 agent 做验证。见「添加一个对抗性审阅步骤」。

### [​](https://code.claude.com/docs/en/best-practices#rewind-with-checkpoints)用检查点回退

你发出的、开启一轮的每条 prompt 都创建一个检查点。你能把对话、代码或两者都恢复到任何先前的检查点。

Claude 在每次更改前自动为文件打快照，好让一个检查点能恢复它们。双击 Escape 或运行 `/rewind` 打开回退菜单。你能只恢复对话、只恢复代码、两者都恢复、或从选中的一条消息开始做摘要。详见 Checkpointing。

与其周密地计划每一步，不如让 Claude 去试有风险的东西。如果不成，回退并换一种办法。检查点随对话一起保存，于是你能关掉终端、稍后恢复会话、仍能回退。

检查点只追踪通过 Claude 文件编辑工具做出的改动。通过 Bash 命令或外部进程做出的改动不被捕获。这不是 git 的替代品。

### [​](https://code.claude.com/docs/en/best-practices#resume-conversations)恢复对话

用 `/rename` 给会话命名，并把它们当作分支来对待：每条工作线都有它自己的持久上下文。

Claude Code 在本地保存对话，于是当一项任务横跨多次落座时，你不必重新解释上下文。运行 `claude --continue` 从你上次停下的地方接续，或 `claude --resume` 从一个列表里挑。给会话起一个描述性的名字如 `oauth-migration`，好让你日后能找到。恢复、分支和命名控制的完整集合见 Manage sessions。

## [​](https://code.claude.com/docs/en/best-practices#automate-and-scale)自动化与扩展

一旦你在一个 Claude 上手足有效，就用并行会话、非交互模式和扇出（fan-out）模式来倍增你的产出。

### [​](https://code.claude.com/docs/en/best-practices#run-non-interactive-mode)运行非交互模式

在 CI、pre-commit hook 或脚本里用 `claude -p "prompt"`。加上 `--output-format stream-json --verbose` 以获得流式 JSON 输出。

用 `claude -p "your prompt"`，你能非交互地运行 Claude，不带一个交互式提示。这次运行仍会创建一个可恢复的会话，除非你传 `--no-session-persistence`。

非交互模式是你把 Claude 集成进 CI 流水线、pre-commit hook 或任何自动化工作流的方式。输出格式让你能程序化地解析结果：纯文本、JSON 或流式 JSON。

```
# One-off queries
claude -p "Explain what this project does"

# Structured output for scripts
claude -p "List all API endpoints" --output-format json

# Streaming for real-time processing
claude -p "Analyze this log file" --output-format stream-json --verbose
```

第一条命令打印纯文本。`json` 格式返回一个带 `result` 字段的单一 JSON 对象。`stream-json` 格式每行打印一个 JSON 对象，以一个 init 事件开头。

### [​](https://code.claude.com/docs/en/best-practices#run-multiple-claude-sessions)运行多个 Claude 会话

并行运行多个 Claude 会话，以加速开发、运行隔离的实验、或启动复杂的工作流。

挑一种契合你想自己做多少协调的并行方式，并在会话需要互相传递发现时加上消息传递：

- [Worktrees](https://code.claude.com/docs/en/worktrees)：在隔离的 git 签出里跑独立的 CLI 会话，使编辑不相互冲突
- [跨会话消息](https://code.claude.com/docs/en/cross-session-messaging)：让你自己运行的会话把发现互相传递
- [桌面应用](https://code.claude.com/docs/en/desktop#work-in-parallel-with-sessions)：可视地管理多个本地会话，可选地每个在它自己的 worktree 里
- [在云端使用 Claude Code](https://code.claude.com/docs/en/claude-code-on-the-web)：默认在 Anthropic 管理的基础设施上运行会话
- [Agent view](https://code.claude.com/docs/en/agent-view)：研究预览。运行 `claude agents` 派发保持后台运行的会话，并从一屏监视它们
- [Agent teams](https://code.claude.com/docs/en/agent-teams)：实验性、默认禁用。对多个会话带共享任务、消息和一位团队领导的自动化协调

除了并行化工作，多个会话还能赋能以质量为重的工作流。一个新鲜上下文能改善代码审查，因为 Claude 不会偏向它刚写的代码。

例如，用一种作者/审阅者（Writer/Reviewer）模式：

| 会话 A（作者） | 会话 B（审阅者） |
| --- | --- |
| `Implement a rate limiter for our API endpoints` |  |
|  | `Review the rate limiter implementation in @src/middleware/rateLimiter.ts. Look for edge cases, race conditions, and consistency with our existing middleware patterns.` |
| `Here's the review feedback: [Session B output]. Address these issues.` |  |

你可以在测试上做类似的事：让一个 Claude 写测试，另一个写代码去通过它们。

### [​](https://code.claude.com/docs/en/best-practices#fan-out-across-files)跨文件扇出

用一个调用 `claude -p` 的循环来逐任务处理。用 `--allowedTools` 为批处理操作预先批准工具。

对大型迁移或分析，你能把工作在许多并行的 Claude 调用之间分发。运行 `/batch <instruction>` 让 Claude 把改动拆到 5 到 30 个子 agent。每个子 agent 在它自己的 worktree 里工作。要反过来从你自己的脚本来驱动扇出，循环调用 `claude -p`：

1 生成一个任务清单

让 Claude 把需要迁移的文件列表写进一个文件，好让下一步的循环读它，用一个像 `list all 2,000 Python files that need migrating and save the list to files.txt` 的 prompt。

2 写一个脚本去遍历这个清单

```
for file in $(cat files.txt); do
  claude -p "Migrate $file from Python 2 to Python 3. Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)" \
    --permission-mode dontAsk
done
```

3 先在几个文件上测试，然后全量运行

根据头 2-3 个文件出的错来打磨你的 prompt，然后在全集上运行。`--allowedTools` 标志预先批准迁移所需的工具，而 `--permission-mode dontAsk` 拒绝任何其他需要批准的东西——在你无人值守地运行时，这一点很重要。

你也能把 Claude 集成进已有的数据/处理流水线：

```
claude -p "<your prompt>" --output-format json | your_command
```

### [​](https://code.claude.com/docs/en/best-practices#run-autonomously-with-auto-mode)用 auto 模式自主运行

要在带后台安全检查的无中断执行下运行，用 auto 模式。一个分类器模型在命令运行前审阅它们，拦截范围升级、未知基础设施和敌意内容驱动的动作，同时让常规工作无需提示地进行。

```
claude --permission-mode auto -p "fix all lint errors"
```

当分类器在一个带 `-p` 标志的非交互运行里反复拦截动作时，Claude Code 不会停止运行。见「当 auto 模式回退时」了解届时会发生什么以及那些阈值。

### [​](https://code.claude.com/docs/en/best-practices#add-an-adversarial-review-step)添加一个对抗性审阅步骤

在你把任务算作完成之前，让一个子 agent 在一个新鲜上下文里审阅这个 diff 并报告缺口。

Claude 无人值守地工作得越久，在你把这工作算作完成之前，一个独立的检查就越重要。一个跑在新鲜子 agent 上下文里的审阅者，只看到这个 diff 和你给它的标准、而看不到产生这个改动的推理，于是它按自身标准来评估结果。

要做一次正确性检查，运行内建的 `/code-review` skill，它在一个新鲜的子 agent 里审阅当前 diff 找 bug、并把发现返回给会话。要反过来对照你的计划检查 diff，就自己写审阅 prompt。点名要检查的工作、用来对照的计划，以及什么算一条发现：

```
Use a subagent to review the rate limiter diff against PLAN.md. Check that
every requirement is implemented, the listed edge cases have tests, and
nothing outside the task's scope changed. Report gaps, not style preferences.
```

因为审阅者作为子 agent 运行，实现的那个会话会直接收到缺口、并能在你和我不在多个窗口间复制发现的情况下修复它们并再次审阅。

一个被 prompt 去发现缺口的审阅者，即便工作稳健，也通常会上报一些缺口，因为这正是它被要求做的。追着每一条发现会导致过度工程：额外的抽象层、防御性代码、以及为不可能发生的情形写测试。告诉审阅者只标记那些影响正确性或所声明需求的缺口，其余当作可选。

## [​](https://code.claude.com/docs/en/best-practices#avoid-common-failure-patterns)避免常见的失败模式

这些是常见的错误。早早认出它们能省下时间：

- **一锅炖的会话。** 你从一个任务开始，然后问 Claude 一个不相关的东西，再回到第一个任务。上下文塞满了无关信息。**修复**：在不相关的任务之间 `/clear`。
- **反复纠正。** Claude 做错了什么，你纠正，它还是错，你再纠正。上下文被失败的做法污染。**修复**：两次纠正失败后，`/clear` 并写一份把你所学纳入其中的、更好的初始 prompt。
- **过度规定的 CLAUDE.md。** 如果你的 CLAUDE.md 太长，Claude 会忽略一半，因为重要规则淹没在噪声里。**修复**：无情地修剪。如果 Claude 不带那条指令也正确地做某事，删掉它或把它转成一个 hook。
- **信任却未验证的鸿沟。** Claude 产出一个看起来合理、却不处理边缘情形的实现。**修复**：始终提供验证（测试、脚本、截图）。如果你无法验证它，就别发布它。
- **无界的探索。** 你请 Claude「调查」某样东西而不界定它。Claude 读几百个文件，把上下文填满。**修复**：把调查范围界定得很窄，或用子 agent，让探索不消耗你的主上下文。

## [​](https://code.claude.com/docs/en/best-practices#develop-your-intuition)培养你的直觉

本指南里的这些模式并非一成不变。它们是通常管用的起点，但未必对每种情形都最优。

有时你**应该**让上下文累积，因为你正深陷一个复杂问题、而那份历史很有价值。有时你应该跳过规划、让 Claude 去搞定，因为任务带有探索性。有时一个含糊的 prompt 恰恰正确，因为你想先看看 Claude 如何在约束它之前解读问题。

留意什么管用。当 Claude 产出出色的输出时，注意你做了什么：prompt 结构、你提供的上下文、你所处的模式。当 Claude 吃力时，问为什么。是上下文太嘈杂？prompt 太含糊？还是任务太大、一次处理不了？

随时间推移，你会培养出任何指南都无法捕捉的直觉。你会知道何时该具体、何时该开放，何时该规划、何时该探索，何时该清空上下文、何时该让它累积。
