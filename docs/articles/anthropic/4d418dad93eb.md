# 「think」工具：让 Claude 在复杂工具使用情境中停下来思考

发布于 2025 年 3 月 20 日

一个提升 Claude 复杂问题求解性能的新工具

- 扩展思考更新 2025 年 12 月 15 日：自初次发布以来，扩展思考能力已有所改进，以至于在多数情况下我们建议使用该功能，而非专门的 think 工具。扩展思考提供类似的好处——给 Claude 空间去推理复杂问题——且集成度和性能更好。实现细节见我们的扩展思考文档。

在我们持续增强 Claude 复杂问题求解能力的过程中，我们发现了一种特别有效的办法：一个在复杂任务中为结构化思考创造专用空间的「think」工具。

这个简单却强大的技术——正如我们下面会解释的，它不同于 Claude 的新「[扩展思考](https://www.anthropic.com/research/visible-extended-thinking)」能力（[扩展思考实现细节](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)见此处）——让 Claude 的 agentic 工具使用能力取得了显著改善。这包括遵循政策、做出一致的决策、处理多步骤问题，而实现开销极小。

在本文里，我们会探讨在不同应用上如何实现「think」工具，基于可验证的基准结果分享面向开发者的实用指南。

### 什么是「think」工具？

借助「think」工具，我们赋予 Claude 在其得出最终答案的过程中纳入一个额外思考步骤的能力——带它自己专用的一块空间。

它听起来与扩展思考相似，却是一个不同的概念。扩展思考关乎的是 Claude 在开始生成响应*之前*做什么。在扩展思考下，Claude 在行动之前会深入考虑并迭代它的计划。「think」工具则是给 Claude 用的，一旦它开始生成响应，用来添加一个步骤去停下来、思考它是否已具备前进所需的全部信息。这在执行长工具调用链、或在与用户的长多步对话中时尤其有帮助。

这让「think」工具更适合那些 Claude 无法仅凭用户查询就掌握撰写响应所需全部信息、而需要处理外部信息（如工具调用结果里的信息）的情形。Claude 用「think」工具所做的推理，不如扩展思考所能得到的那样全面，而更聚焦于模型所发现的*新*信息。

我们建议对更简单的工具使用场景用扩展思考，例如非顺序的工具调用或直白的指令遵循。扩展思考在对无需 Claude 调用工具的用例，如编码、数学、物理，也很有用。「think」工具则更适合当 Claude 需要调用复杂工具、在长工具调用链里仔细分析工具输出、在有详细指南的政策密集型环境中导航、或在每步都建立在前一步之上、犯错代价高昂的顺序决策中时。

下面是一个用来自 [τ-Bench](https://arxiv.org/abs/2406.12045)、采用标准工具体规格格式的实现示例：

```
{
  "name": "think",
  "description": "Use the tool to think about something. It will not obtain new information or change the database, but just append the thought to the log. Use it when complex reasoning or some cache memory is needed.",
  "input_schema": {
    "type": "object",
    "properties": {
      "thought": {
        "type": "string",
        "description": "A thought to think about."
      }
    },
    "required": ["thought"]
  }
}
```

### 在 τ-Bench 上的性能

我们用 τ-bench（tau-bench）评估「think」工具——一个全面的基准，旨在测试模型在真实客服场景中使用工具的能力，而「think」工具是该评测标准环境的一部分。

τ-bench 评估 Claude 在以下方面的能力：

- 与模拟用户导航真实的对话
- 始终如一地遵循复杂的客服 agent 政策指南
- 使用多种工具来访问和操作环境数据库

τ-bench 使用的主要评估指标是 pass^*k*，它衡量给定任务的所有 *k* 次独立任务尝试都成功的概率，并在所有任务上取平均。与在其他 LLM 评测中常见的 pass@*k* 指标（它衡量 *k* 次尝试中至少一次成功的与否）不同，pass^*k* 评估一致性和可靠性——这对必须始终如一地遵守政策的客服应用是至关重要的品质。

#### 性能分析

我们的评估比较了几种不同的配置：

- 基线（无「think」工具、无扩展思考模式）
- 仅扩展思考模式
- 仅「think」工具
- 带优化 prompt 的「think」工具（针对航空领域）

结果显示，当 Claude 3.7 在基准的「航空」和「零售」两个客服领域里有效使用「think」工具时，取得了显著的改善：

- **航空领域**：带优化 prompt 的「think」工具在 pass^1 指标上达到 0.570，而基线只有 0.370——相对提升 54%；
- **零售领域**：仅用「think」工具就达到 0.812，而基线为 0.783。

Claude 3.7 Sonnet 在 Tau-Bench 评估「航空」领域下四种不同配置中的表现。

在航空领域取得的最佳表现，来自把「think」工具与一个优化 prompt 配对，后者给出在分析客户请求时应使用何种推理方式的示例。下面是优化 prompt 的一个示例：

```
## Using the think tool

Before taking any action or responding to the user after receiving tool results, use the think tool as a scratchpad to:
- List the specific rules that apply to the current request
- Check if all required information is collected
- Verify that the planned action complies with all policies
- Iterate over tool results for correctness 

Here are some examples of what to iterate over inside the think tool:
<think_tool_example_1>
User wants to cancel flight ABC123
- Need to verify: user ID, reservation ID, reason
- Check cancellation rules:
  * Is it within 24h of booking?
  * If not, check ticket class and insurance
- Verify no segments flown or are in the past
- Plan: collect missing info, verify rules, get confirmation
</think_tool_example_1>

<think_tool_example_2>
User wants to book 3 tickets to NYC with 2 checked bags each
- Need user ID to check:
  * Membership tier for baggage allowance
  * Which payments methods exist in profile
- Baggage calculation:
  * Economy class × 3 passengers
  * If regular member: 1 free bag each → 3 extra bags = $150
  * If silver member: 2 free bags each → 0 extra bags = $0
  * If gold member: 3 free bags each → 0 extra bags = $0
- Payment rules to verify:
  * Max 1 travel certificate, 1 credit card, 3 gift cards
  * All payment methods must be in profile
  * Travel certificate remainder goes to waste
- Plan:
1. Get user ID
2. Verify membership level for bag fees
3. Check which payment methods in profile and if their combination is allowed
4. Calculate total: ticket price + any bag fees
5. Get explicit confirmation for booking
</think_tool_example_2>
```

特别有意思的是不同方法之间的对比。把「think」工具与优化 prompt 一起使用，取得了显著优于扩展思考模式的结果（后者的表现与未经 prompt 的「think」工具类似）。单用「think」工具（不加 prompt）相比基线提升了表现，但仍不及优化后的方案。

「think」工具与优化 prompt 的结合以显著优势交付了最强表现，这可能归因于基准中[航空政策](https://github.com/sierra-research/tau-bench/blob/main/tau_bench/envs/airline/wiki.md)部分的高复杂性——在那里，模型从被给予「如何思考」的示例中获益最多。

#### 来自 τ-Bench 分析的关键洞见

我们详细的分析揭示了若干能帮你有效实现「think」工具的模式：

- **在困难领域，prompt 至关重要。** 仅仅让「think」工具可用可能略微提升表现，但把它与优化 prompt 配对，在困难领域带来了显著更好的结果。然而，较容易的领域或许只靠能用上「think」就能获益。
- **跨尝试的一致性提升。** 使用「think」带来的提升在 pass^k 上一直保持到 k=5，表明该工具帮助 Claude 更有效地处理边缘情形和不寻常场景。

### 在 SWE-Bench 上的性能

在评估 Claude 3.7 Sonnet 时，我们把一个类似的「think」工具加入了 SWE-bench 配置，促成了所取得的 0.623 的最先进（state-of-the-art）得分。改造后的「think」工具体定义见下：

```
{
  "name": "think",
  "description": "Use the tool to think about something. It will not obtain new information or make any changes to the repository, but just log the thought. Use it when complex reasoning or brainstorming is needed. For example, if you explore the repo and discover the source of a bug, call this tool to brainstorm several unique ways of fixing the bug, and assess which change(s) are likely to be simplest and most effective. Alternatively, if you receive some test results, call this tool to brainstorm ways to fix the failing tests.",
  "input_schema": {
    "type": "object",
    "properties": {
      "thought": {
        "type": "string",
        "description": "Your thoughts."
      }
    },
    "required": ["thought"]
  }
}
```

我们的实验（*n*=30 个带「think」工具的样本，*n*=144 个不带工具样本）显示，仅纳入这个工具就让平均表现提升了 1.6%（Welch *t* 检验：*t*(38.89) = 6.71，*p* < .001，*d* = 1.47）。

### 何时使用「think」工具

基于这些评估结果，我们识别出了 Claude 从「think」工具中获益最多的特定场景：

- **工具输出分析。** 当 Claude 需要在行动前仔细处理先前工具调用的输出、且可能需要在其方法上回头修正时；
- **政策密集型环境。** 当 Claude 需要遵循详细指南并核验合规时；以及
- **顺序决策。** 当每个动作都建立在前一个之上、且犯错代价高昂时（常见于多步骤领域）。

## 实现最佳实践

要在使用 Claude 时把「think」工具用到极致，我们基于 τ-bench 实验推荐以下实现实践。

#### 1. 带领域专用示例的战略性 prompt

最有效的方法是就何时、如何使用「think」工具提供清晰的指令，例如 τ-bench 航空领域所用的那一种。提供契合你特定用例的示例，能显著提升模型使用「think」工具的效力：

- 推理过程中所期待的详细程度；
- 如何把复杂指令拆解成可执行的步骤；
- 处理常见场景的决策树；以及
- 如何检查是否已收集齐所有必要信息。

#### 2. 把复杂指南放在系统 prompt 里

我们发现，当这些关于「think」工具的指令冗长或复杂时，把它们放进系统 prompt 比放进工具体描述本身更有效。这种做法提供了更广的上下文，帮助模型把思考过程更好地融入其整体行为。

### 何时*不*使用「think」工具

虽然「think」工具能提供可观的提升，但它并不适用于所有工具使用用例，且确实以 prompt 变长和输出 token 增多为代价。具体说，我们发现「think」工具在以下用例中不带来任何提升：

- **非顺序的工具调用。** 如果 Claude 只需发起一次工具调用、或多次并行调用即可完成任务，那么添加「think」不太可能带来提升。
- **简单的指令遵循。** 当没有太多 Claude 必须遵守的约束、且它的默认行为已足够好时，额外的「思考」不太可能带来收益。

### 如何开始

「think」工具是你 Claude 实现中一个直截了当的补充，只需几步就能带来有意义的提升：

- **在 agentic 工具使用场景上测试。** 从有挑战的用例开始——那些 Claude 目前在长工具调用链的政策合规或复杂推理上还吃力的用例。
- **添加工具体定义。** 实现一个契合你领域的「think」工具。它只需极少代码，却能促成更结构化的思考。也可以考虑就何时、如何使用该工具、并附上契合你领域的示例，把指令加进系统 prompt。
- **监控并打磨。** 观察 Claude 在实践中如何使用该工具，并调整你的 prompt 以鼓励更有效的思考模式。

最好的地方在于，添加这个工具在性能结果上几乎没有下行。除非 Claude 决定使用它，它不改变外部行为，也不干扰你已有的工具或工作流。

### 结论

我们的研究证明，「think」工具能显著提升 Claude 3.7 Sonnet 在需要政策遵从、以及长工具调用链中推理的复杂任务上的表现 1。「Think」不是一刀切的解药，但它为正确的用例提供了可观的好处，而实现复杂度极低。

我们期待看到你如何用「think」工具，与 Claude 一起构建更有能力、更可靠、更透明的 AI 系统。

1. 虽然我们的 τ-Bench 结果聚焦于带「think」工具的 Claude 3.7 Sonnet 的提升，但我们的实验显示 Claude 3.5 Sonnet（新版）也能在与 3.7 Sonnet 相同的配置下取得表现增益，表明这一提升也能推广到其他 Claude 模型。
