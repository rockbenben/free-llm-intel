# 用一队并行的 Claude 构建一个 C 编译器

发布于 2026 年 2 月 5 日

我们让 Opus 4.6 用 agent 团队去构建一个 C 编译器，然后（基本上）走开了。这教会了我们关于自主软件开发未来的什么。

*本文由我们安全防护团队的研究员 Nicholas Carlini 撰写。*

我一直在试验一种监督语言模型的新方法，我们称之为「agent 团队」。

在 agent 团队里，多个 Claude 实例在没有人类主动干预的情况下，并行工作在一个共享代码库上。这种做法极大地拓展了 LLM agent 所能成就的范围。

为了对它做压力测试，我指派 16 个 agent 从零开始编写一个基于 Rust 的 C 编译器，要能编译 Linux 内核。在近 2,000 次 Claude Code 会话、20,000 美元 API 成本之后，这支 agent 团队产出了一个 100,000 行的编译器，能在 x86、ARM 和 RISC-V 上构建 Linux 6.9。

[这个编译器本身就是一件有趣的产物](https://github.com/anthropics/claudes-c-compiler)，但我在此聚焦于我为长时间运行自主 agent 团队设计 harness 所学到的：如何编写能在无人监督下让 agent 保持正轨的测试、如何组织工作让多个 agent 能并行推进，以及这种做法在何处触顶。

## 让 Claude 能长时间运行

像 Claude Code 这样的现有 agent 脚手架，需要一个操作员在线、能一同协作。如果你要求一个漫长而复杂问题的解法，模型可能解决其中一部分，但最终会停下来等待继续输入——一个提问、一次状态更新，或一次澄清请求。

为了引出持续、自主的进展，我搭了一个把 Claude 塞进一个简单循环的 harness（如果你见过 Ralph-loop，这看着会很眼熟）。当它完成一个任务，就立刻拾起下一个。*（这要跑在容器里，别在你的真机上跑。）*

```
#!/bin/bash

while true; do
    COMMIT=$(git rev-parse --short=6 HEAD)
    LOGFILE="agent_logs/agent_${COMMIT}.log"

    claude --dangerously-skip-permissions \
           -p "$(cat AGENT_PROMPT.md)" \
           --model claude-opus-X-Y &> "$LOGFILE"
done
```

在 agent prompt 里，我告诉 Claude 要解决什么问题，并请它把问题拆成小块、追踪它正在做什么、弄清楚下一步该做什么、以及有效地继续直到完美为止。（在最后这一点上，Claude 别无选择。这个循环永远运行——尽管有一次，我确实见到 Claude 意外地 `pkill -9 bash`，从而杀死了自己、结束了循环。哎呀！）

## 并行运行 Claude

并行运行多个实例能解决单 agent harness 的两个弱点：

- 一个 Claude Code 会话一次只能做一件事。尤其当项目范围扩大时，并行调试多个问题要高效得多。
- 运行多个 Claude agent 允许专业化。虽然少数 agent 被指派去解决眼前的实际问题，其他专门的 agent 可以被调用来（例如）维护文档、盯着代码质量，或解决专门的子任务。

我对并行 Claude 的实现很简陋。会新建一个空的 git 仓库，并为每个 agent 拉起一个 Docker 容器，把仓库挂载到 `/upstream`。每个 agent 克隆一份本地副本到 `/workspace`，完成时从自己的本地容器推送到 upstream。

为防止两个 agent 同时试图解决同一个问题，harness 用一个简单的同步算法：

- Claude 通过在 current_tasks/ 里写一个文本文件来给一个任务上「锁」（例如，一个 agent 可能锁 current_tasks/parse_if_statement.txt，而另一个锁 current_tasks/codegen_function_definition.txt）。如果两个 agent 试图认领同一任务，git 的同步会迫使第二个 agent 挑一个不同的。
- Claude 处理任务，然后从 upstream 拉取、合并其他 agent 的改动、推送它的改动，并移除锁。合并冲突很频繁，但 Claude 足够聪明能搞定它。
- 那个无限 agent 生成循环会在新容器里拉起一个新的 Claude Code 会话，然后循环往复。

这是一个非常早期的研究原型。我还没有实现 agent 之间通信的任何其他方法，也不强制任何管理高层目标的流程。我不使用编排 agent。

相反，我把每个 Claude agent 该如何行动的决定权留给它自己。在多数情况下，Claude 会拾起「下一个最明显的」问题。卡在一个 bug 上时，Claude 常会维护一份记录失败做法和剩余任务的活动文档。在项目的 [git 仓库](https://github.com/anthropics/claudes-c-compiler)里，你可以通读历史，看它给各种任务上锁。

## 用 Claude agent 团队编程的教训

脚手架让 Claude 在一个循环里运行，但只有当 Claude 能判断如何推进时，这个循环才有用。我大部分精力都花在围绕 Claude 设计环境上——测试、环境、反馈——好让它能在没有我的情况下给自己定向。这些是我在编排多个 Claude 实例时觉得最有用的做法。

### 编写极高质量的测试

Claude 会自主工作来解决我交给它的任何问题。所以任务验证器近乎完美就至关重要，否则 Claude 会去解决错误的问题。改进测试脚手架需要找到高质量的编译器测试套件、为开源软件包编写验证器和构建脚本、观察 Claude 所犯的错误，然后在我识别出那些失败模式时设计新测试。

例如，在项目接近尾声时，Claude 每实现一个新功能，就开始频繁地破坏现有功能。为解决这一点，我搭了一条持续集成流水线，并实施了更严格的强制，让 Claude 能更好地测试自己的工作，使新提交无法破坏现有代码。

### 设身处地为 Claude 着想

我不得不不断提醒自己：我是在为 Claude 而非为我自己写这份测试脚手架，这意味着要重新思考我许多关于测试该如何传达结果的假设。

例如，每个 agent 被丢进一个没有上下文的全新容器，会花相当多的时间给自己定向，在大项目上尤甚。甚至还没到测试之前，为了帮 Claude 自助，我加入了要维护详尽 README 和进度文件的指令，这些应频繁更新当前状态。

我也记着语言模型有固有局限这一事实，在这个情形里需要绕开它们来设计。这些包括：

- **上下文窗口污染：** 测试脚手架不该打印成千上万无用的字节。最多它应打印几行输出，并把所有重要信息记录到一个文件里，好让 Claude 在需要时能找到。日志文件应易于自动处理：如果有错误，Claude 应写下 ERROR 并把原因放在同一行，好让 grep 找到它。预先算好聚合的汇总统计会有帮助，免得 Claude 反复重算。
- **时间盲：** Claude 看不出时间，独自待着时它会乐呵呵花上几个小时跑测试而不推进。harness 不频繁地打印增量进度（以免污染上下文），并包含一个默认的 `--fast` 选项，运行 1% 或 10% 的随机样本。这个子样本对每个 agent 是确定的，但跨 VM 是随机的，所以 Claude 仍覆盖所有文件，而每个 agent 能精确地识别回归。

### 让并行变得容易

当有许多不同的失败测试时，并行化是琐碎的：每个 agent 挑一个不同的失败测试去处理。当测试套件达到 99% 通过率后，每个 agent 转去把不同的小型开源项目（如 SQlite、Redis、libjpeg、MQuickJS、Lua）编译成功。

但当 agent 开始编译 Linux 内核时，它们卡住了。与有数百个独立测试的测试套件不同，编译 Linux 内核是一个巨型任务。每个 agent 都会撞上同一个 bug、修好那个 bug、然后互相覆盖对方的改动。有 16 个 agent 在跑并没帮助，因为每个都卡在解决同一个任务上。

解决办法是用 [GCC](https://gcc.gnu.org/) 作为一个在线的已知良好编译器神谕（oracle）来做对比。我写了一个新的测试脚手架，它随机地用 GCC 编译内核的大部分、只用 Claude 的 C 编译器编译剩余的文件。如果内核能用，那么问题不在 Claude 的那部分文件里。如果它坏了，那么它可以再把其中一些文件用 GCC 重新编译来进一步收敛。这让每个 agent 能并行工作，在不同文件里修不同的 bug，直到 Claude 的编译器最终能编译所有文件。（在这奏效之后，仍需应用 delta 调试技术，去找那些一起失败、但各自独立能用的文件对。）

### 多个 agent 角色

并行也催生专业化。LLM 编写的代码经常重新实现已有功能，所以我指派一个 agent 去合并它所发现的任何重复代码。我把另一个负责改进编译器本身的性能，第三个负责输出高效的编译代码。我请一个 agent 从 Rust 开发者的视角批判项目的设计，并对项目做结构性改动以提升整体代码质量，还有一个去做文档。

## 压力测试 agent 团队的极限

这个项目被设计为一个能力基准。我有兴趣去压力测试 LLM 今天能*勉强*达到的极限，以帮助我们为模型未来能可靠达到什么做准备。

我一直把 C 编译器项目当作跨越整个 Claude 4 模型系列的基准。和我对先前项目所做的一样，我起初草拟了我想要的：一个从零开始、无依赖的优化编译器，GCC 兼容，能编译 Linux 内核，并被设计成支持多个后端。虽然我指定了设计的某些方面（例如它应有一个 SSA IR 以启用多个优化 pass），但我没有在如何做到上给出任何细节。

早先的 Opus 4 模型勉强能产出一个可用的编译器。Opus 4.5 是第一个越过某个门槛的，让它能产出一个能通过大型测试套件的可用编译器，但它仍无法编译任何真正的大型项目。我在 Opus 4.6 上的目标，是再次测试极限。

### 评估

在横跨两周、近 2,000 次 Claude Code 会话里，Opus 4.6 消耗了 20 亿输入 token、生成了 1.4 亿输出 token，总成本刚不到 20,000 美元。与最贵的 Claude Max 套餐相比，这都是一个极其昂贵的项目。但这个总额，只是我自己产出这东西本会花费的一小部分——更别说一整支团队了。

这是一次洁净室实现（Claude 在其开发期间任何时刻都没有互联网访问）；它只依赖 Rust 标准库。这个 100,000 行的编译器能构建一个可启动的 Linux 6.9，在 x86、ARM 和 RISC-V 上。它也能编译 QEMU、FFmpeg、SQlite、postgres、redis，并在多数编译器测试套件上包括 [GCC torture 测试套件](https://gcc.gnu.org/onlinedocs/gccint/Torture-Tests.html) 有 99% 的通过率。它还通过了一个开发者的终极试金石：它能编译并运行 Doom。

然而，这个编译器并非没有局限。这些包括：

- 它缺少从实模式启动 Linux 所必需的 16 位 x86 编译器。为此它转而去调 GCC（x86_32 和 x86_64 编译器是它自己的）。
- 它没有自己的汇编器和链接器；这些正是 Claude 最后才开始自动化、且仍有些 bug 的部分。演示视频是用 GCC 汇编器和链接器制作的。
- 编译器成功构建了许许多多项目，但不是全部。它还无法作为真正编译器的即插即用替代品。
- 生成的代码效率不算高。即便启用所有优化，它输出的代码也比*禁用*所有优化的 GCC 更不高效。
- Rust 代码质量合理，但远不及一个资深 Rust 程序员所能产出的质量。

最终得到的编译器几乎触及了 Opus 能力的极限。我（努力！）试图修复上面若干局限，但没有完全成功。新功能和 bug 修复经常破坏现有功能。

作为一个尤其具有挑战的例子，Opus 无法实现启动进 16 位实模式所需的 16 位 x86 代码生成器。虽然编译器能通过 66/67 操作码前缀输出正确的 16 位 x86，但由此编译出的输出超过 60kb，远超 Linux 强制的 32k 代码限制。于是，Claude 在这里干脆取巧、为这一阶段转去调 GCC（这仅适用于 x86。对 ARM 或 RISC-V，Claude 的编译器能完全自行编译。）

[编译器的源码已可获取](https://github.com/anthropics/claudes-c-compiler)。下载它、通读代码，在你喜爱的 C 项目上试一试。我一直发现，理解语言模型能做什么的最好方式，就是把它们推到极限，然后研究它们在何处开始崩解。接下来几天，如果你愿意跟进 Claude 为应对这些局限而做的持续尝试，我会继续让 Claude 推送新改动。

## 展望未来

每一代语言模型都开启了与它们协作的新方式。早期模型对 IDE 里的标签补全有用。不久之后，模型就能从函数体的文档字符串把它补全。Claude Code 的发布把 agent 带入了主流，并让开发者能与 Claude 结对编程。但这些产品都运作在一个假设之下：用户定义一个任务，一个 LLM 运行几秒或几分钟并返回一个答案，然后用户提供一次追问。

agent 团队展示了自主实现整个复杂项目的可能性。这让我们作为这些工具的用户，能对目标更有雄心。

我们仍处于早期，而完全自主的开发伴随着真实的风险。当一个人类在开发期间与 Claude 坐在一起时，他们能确保一致的质量、实时捕获错误。对自主系统，很容易看到测试通过就假设工作完成了，而事实很少如此。我过去做渗透测试，利用大公司产品里的漏洞，而程序员部署他们从未亲自验证过的软件这一想法，是一个切实的担忧。

所以，虽然这个实验让我兴奋，它也让我感到不安。构建这个编译器是我近来最有趣的事之一，但我没料到在 2026 年这么早这会近乎可能。语言模型以及我们用来与它们交互的脚手架的快速进展，打开了一扇门，通往书写巨量新代码。我预期正面应用会盖过负面的，但我们正进入一个需要新策略来安全导航的新世界。
