# 构建高效的 agent

发布于 2024 年 12 月 19 日

我们已与跨行业构建 LLM agent 的数十个团队合作。始终一贯地，最成功的实现用的是简单、可组合的模式，而非复杂的框架。

*注：本文描述的工具格局自 2024 年 12 月以来已大有变化。关于我们的当前方法，参见[**我们如何构建 Claude Managed Agents**](https://www.anthropic.com/engineering/managed-agents)* *和 [**Managed Agents 文档**](https://platform.claude.com/docs/en/managed-agents/overview)。*

过去一年，我们已与跨行业构建大语言模型（LLM）agent 的数十个团队合作。一贯地，最成功的实现并不使用复杂的框架或专门的库。相反，它们用简单、可组合的模式来构建。

在本文里，我们分享从与客户共事、以及我们自己构建 agent 中学到的经验，并为开发者提供构建高效 agent 的实用建议。

## 什么是 agent？

「agent」可以有多种定义。一些客户把 agent 定义为完全自主的系统，能独立运行很长时间、使用各种工具完成复杂任务。另一些人用这个词描述遵循预定义工作流的更具规定性的实现。在 Anthropic，我们把这些所有变体都归类为 **agentic 系统**，但在 **工作流** 和 **agent** 之间划出一条重要的架构区分：

- **工作流（Workflows）** 是 LLM 和工具通过预定义代码路径被编排的系统。
- **Agent** 则是 LLM 动态指挥自身流程和使用工具、并对如何完成任务保持控制的系统。

下面，我们会详细探讨这两类 agentic 系统。在附录 1（「agent 实践」）里，我们描述了客户发现使用这类系统尤其有价值的两个领域。

## 何时（以及何时不）使用 agent

在构建 LLM 应用时，我们建议找到尽可能简单的方案，只在必要时才增加复杂度。这可能意味着根本不构建 agentic 系统。agentic 系统常常拿延迟和成本换取更好的任务表现，你应当考量这种权衡何时划算。

当更复杂的方案确有必要时，工作流为定义良好的任务提供可预测性和一致性，而当在规模上需要灵活性和模型驱动的决策时，agent 是更好的选择。不过，对许多应用而言，用检索和上下文内示例优化单次 LLM 调用通常就够了。

## 何时以及如何使用框架

有许多框架让 agentic 系统更易实现，包括：

- [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)；
- AWS 的 [Strands Agents SDK](https://strandsagents.com/latest/)；
- [Rivet](https://rivet.ironcladapp.com/)，一款拖放式 GUI LLM 工作流构建器；以及
- [Vellum](https://www.vellum.ai/)，另一款用于构建和测试复杂工作流的 GUI 工具。

这些框架通过简化像调用 LLM、定义和解析工具、把调用串起来这样的标准底层任务，让上手变得容易。然而，它们常常制造额外的抽象层，可能掩盖底层的 prompt 和响应，使其更难调试。它们也容易让人在一个更简单的配置就够用时，忍不住去增加复杂度。

我们建议开发者先直接使用 LLM API：许多模式几行代码就能实现。如果你确实使用框架，确保你理解底层代码。关于内部运作的不正确假设，是客户错误的常见来源。

有关一些示例实现，参见我们的 [cookbook](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)。

## 构件、工作流与 agent

在本节，我们会探讨在生产中我们见过的 agentic 系统常见模式。我们从我们的基础构件——增强型 LLM——开始，逐步增加复杂度，从简单的组合式工作流到自主 agent。

### 构件：增强型 LLM

agentic 系统的基本构件，是一个被检索、工具和记忆等增强手段所强化的 LLM。我们当前的模型能主动使用这些能力——生成自己的搜索查询、选择合适的工具、并决定要保留哪些信息。

增强型 LLM

我们建议聚焦于实现的两个关键方面：让这些能力契合你的特定用例，并确保它们为你的 LLM 提供一个易用、文档良好的接口。虽然有许多方式来实现这些增强，一种做法是通过我们最近发布的 [Model Context Protocol](https://www.anthropic.com/news/model-context-protocol)，它让开发者能用一个简单的[客户端实现](https://modelcontextprotocol.io/tutorials/building-a-client#building-mcp-clients)，与一个不断壮大的第三方工具生态集成。

在本文余下部分，我们假设每次 LLM 调用都能访问这些增强能力。

### 工作流：prompt 链

prompt 链把一个任务分解为一系列步骤，每次 LLM 调用处理上一次的输出。你可以对任何中间步骤添加程序化检查（见下图中的「gate（闸门）」），以确保流程仍在正轨上。

prompt 链工作流

**何时使用这一工作流：** 这一工作流最适合能轻松干净地分解为固定子任务的情形。主要目标是拿延迟换更高准确率，让每次 LLM 调用成为一个更容易的任务。

**prompt 链有用的例子：**

- 生成营销文案，然后把它翻译成另一种语言。
- 写一份文档的大纲，检查大纲是否符合某些标准，然后据大纲撰写文档。

### 工作流：路由

路由对一个输入做分类，并把它导向一个专门的后续任务。这一工作流允许关注点分离、并构建更专门的 prompt。没有这一工作流，针对某一类输入的优化可能损害其他输入的表现。

路由工作流

**何时使用这一工作流：** 对于有各自更适合分别处理的、清晰类别的复杂任务，且分类能由 LLM 或更传统的分类模型/算法准确处理时，路由效果很好。

**路由有用的例子：**

- 把不同类型的客服查询（一般问题、退款请求、技术支持）导向不同的下游流程、prompt 和工具。
- 把简单/常见问题路由到更小、更经济的模型（如 Claude Haiku 4.5），把困难/不寻常的问题路由到更强的模型（如 Claude Sonnet 4.5），以优化最佳表现。

### 工作流：并行化

LLM 有时能同时处理一个任务，并通过程序聚合它们的输出。这一工作流——并行化——表现为两个关键变体：

- **分段（Sectioning）**：把一个任务拆成独立子任务并行运行。
- **投票（Voting）**：多次运行同一任务以获得多样的输出。

并行化工作流

**何时使用这一工作流：** 当被拆分的子任务能为速度而并行、或为更高置信的结果需要多视角或多次尝试时，并行化很有效。对于有多重考量的复杂任务，当每个考量都由一次独立的 LLM 调用处理、从而能对每个具体方面给予专注注意力时，LLM 通常表现更好。

**并行化有用的例子：**

- **分段**：实现护栏，其中一个模型实例处理用户查询，另一个则筛查不当内容或请求。这通常比让同一个 LLM 调用既处理护栏又处理核心响应表现更好。为评估 LLM 性能而自动化评测，其中每次 LLM 调用评估模型在给定 prompt 上表现的某一不同方面。
- **投票**：审查一段代码的漏洞，其中几个不同的 prompt 各自审查、若发现问题就标记出来。评估一段内容是否不当，其中多个 prompt 评估不同方面或要求不同的投票阈值，以平衡误报和漏报。

### 工作流：编排者-工作者

在编排者-工作者工作流中，一个中央 LLM 动态地分解任务、把它们委派给工作者 LLM、并综合它们的结果。

编排者-工作者工作流

**何时使用这一工作流：** 这一工作流很适合你无法预测所需子任务的复杂任务（在编码里，例如需要改动多少文件、每个文件改动的性质很可能取决于任务）。尽管它在拓扑上与并行化类似，与并行化的关键区别在于它的灵活性——子任务不是预定义的，而是由编排者基于具体输入来确定的。

**编排者-工作者有用的例子：**

- 每次都向多个文件做复杂改动的编码产品。
- 涉及从多个来源收集并分析信息以寻找可能相关内容的搜索任务。

### 工作流：评估者-优化者

在评估者-优化者工作流中，一次 LLM 调用生成响应，而另一次在一个循环里提供评估和反馈。

评估者-优化者工作流

**何时使用这一工作流：** 当我们有清晰的评估标准、且迭代改进能带来可衡量的价值时，这一工作流特别有效。契合的两点标志是：第一，当人类表达其反馈时，LLM 响应能被明显改进；第二，LLM 能提供这样的反馈。这类似于人类作者在产出一份精美文档时所经历的迭代写作过程。

**评估者-优化者有用的例子：**

- 文学翻译，其中有些细微差别翻译 LLM 起初可能捕捉不到，但评估 LLM 能提供有用的批评。
- 需要多轮搜索和分析来收集全面信息的复杂搜索任务，其中评估者决定是否需要进一步搜索。

### Agent

随着 LLM 在关键能力上成熟——理解复杂输入、进行推理和规划、可靠地使用工具、从错误中恢复——agent 正在生产中涌现。agent 以来自人类用户的命令或与人类的交互讨论开始其工作。一旦任务清晰，agent 便独立地规划并运作，可能为了进一步的信息或判断返回人类。在执行期间，agent 在每一步从环境获取「事实根据（ground truth）」（如工具调用结果或代码执行）以评估其进展，这一点至关重要。agent 随后可以在检查点处或遇到阻碍时为人类反馈而暂停。任务常在完成时终止，但也常见地会加入停止条件（如最大迭代次数）以维持控制。

agent 能处理复杂的任务，但它们的实现往往很直接。它们通常就是在一个循环里基于环境反馈使用工具的 LLM。因此，清晰而周密地设计工具集及其文档至关重要。我们在附录 2（「为你的工具做 prompt 工程」）里展开工具开发的最佳实践。

自主 agent

**何时使用 agent：** agent 可用于开放式问题——难以或不可能预测所需步数，且你无法硬编码一条固定路径。LLM 可能会运作很多轮，而你必须对其决策保持一定程度的信任。agent 的自主性使它们成为在受信任环境里扩展任务的理想选择。

agent 的自主本质意味着更高的成本、以及错误累积的潜在可能。我们建议在沙箱环境里广泛测试，并配合恰当的护栏。

**agent 有用的例子：**

以下例子来自我们自己的实现：

- 我们的[「computer use」参考实现](https://github.com/anthropics/anthropic-quickstarts/tree/main/computer-use-demo)，其中 Claude 使用一台计算机来完成任务。

## 组合并定制这些模式

这些构件并非规定性的。它们是开发者可以塑造、组合以契合不同用例的常见模式。成功的关键，与任何 LLM 功能一样，在于衡量性能并对实现进行迭代。再强调一遍：你应当*只*在复杂度能可证明地改善结果时才考虑添加它。

## 总结

在 LLM 领域的成功，不在于构建最复杂的系统。而在于为你的需求构建*合适*的系统。从简单的 prompt 开始，用全面的评估优化它们，只在更简单方案力有不逮时才添加多步 agentic 系统。

在实现 agent 时，我们尽量遵循三条核心原则：

- 在 agent 的设计上保持**简单**。
- 通过明确展示 agent 的规划步骤，优先保证**透明**。
- 通过周密的工具**文档与测试**，精心打磨你的 agent-计算机接口（ACI）。

框架能帮你快速上手，但当你进入生产时，不要犹豫去削减抽象层、用基础组件构建。遵循这些原则，你能创造出不仅强大、而且可靠、可维护、受用户信赖的 agent。

## 附录 1：agent 实践

我们与客户的共事揭示了两个特别有前景的 AI agent 应用，它们展示了上述模式的实际价值。两个应用都说明了：agent 对那些既需要对话又需要行动、有清晰成功标准、能促成反馈回路、并融入有意义的人类监督的任务，能增添最大价值。

### A. 客户支持

客户支持把熟悉的聊天机器人界面，与通过工具集成而增强的能力相结合。这对更开放式的 agent 是天然的契合，因为：

- 支持交互自然地沿一个对话流程进行，同时要求访问外部信息和采取行动；
- 可以集成工具来拉取客户数据、订单历史和知识库文章；
- 诸如发放退款、更新工单这类动作可以被程序化处理；以及
- 成功可以通过用户定义的解决情况来清晰衡量。

一些公司已通过按使用计费的模式证明了这一方法的可行性——只对成功解决收费，显示了它们对自家 agent 有效性的信心。

### B. 编码 agent

软件开发领域展现出了 LLM 功能的非凡潜力，能力从代码补全演进到自主问题求解。agent 尤其有效，因为：

- 代码解能通过自动化测试得到验证；
- agent 能以测试结果作为反馈对解进行迭代；
- 问题空间定义良好且结构化；以及
- 输出质量能被客观衡量。

在我们自己的实现中，agent 如今仅凭 pull request 的描述，就能解决 [SWE-bench Verified](https://www.anthropic.com/research/swe-bench-sonnet) 基准里真实的 GitHub issue。然而，尽管自动化测试有助于验证功能，人类审阅对于确保解与更广泛的系统要求保持一致，仍至关重要。

## 附录 2：为你的工具做 prompt 工程

无论你构建哪种 agentic 系统，工具很可能都是你 agent 的重要组成部分。[工具](https://www.anthropic.com/news/tool-use-ga)让我们能在 API 里通过指定它们确切的结构和定义，使 Claude 与外部服务和 API 交互。当 Claude 响应时，如果它打算调用一个工具，它会在 API 响应里包含一个[工具使用块](https://docs.anthropic.com/en/docs/build-with-claude/tool-use#example-api-response-with-a-tool-use-content-block)。工具定义和规格应当被给予和你整体 prompt 同等分量的 prompt 工程关注。在这个简短的附录里，我们讲述如何为你的工具做 prompt 工程。

对同一个动作，往往有几种指定方式。例如，你可以通过写一个 diff、或重写整个文件来指定一次文件编辑。对于结构化输出，你可以把代码返回在 markdown 里或 JSON 里。在软件工程里，这些差异是表面性的，可以在彼此之间无损转换。然而，有些格式对 LLM 来说比另一些更难写。写一个 diff，需要在写新代码之前就精确知道 chunk 头部声明改了多少行。（与 markdown 相比）把代码写在 JSON 里，需要对换行和引号做额外转义。

我们对决定工具格式的建议如下：

- 在模型把自己写进死角之前，给它足够的 token 来「思考」。
- 让格式接近模型在互联网文本中天然见到的样子。
- 确保没有格式上的「负担」，例如必须精确计数数千行代码，或对它写下的任何代码做字符串转义。

一条经验法则是，想想人机界面（HCI）上投入了多少功夫，并计划投入同等功夫去打造良好的*agent*-计算机界面（ACI）。这里是一些关于如何做到的思考：

- 设身处地为模型着想。基于描述和参数，使用这个工具是否一目了然，还是你需要仔细琢磨？如果是后者，那对模型来说大概也如此。一个好的工具定义常常包括示例用法、边缘情形、输入格式要求，以及与其他工具清晰划界。
- 你能如何更改参数名或描述，让事情更一目了然？把这当作给你们团队一位初级开发者写一份精彩的文档字符串。当使用许多相似工具时，这一点尤其重要。
- 测试模型如何使用你的工具：在我们的[工作台](https://console.anthropic.com/workbench)里跑许多示例输入，看模型会犯什么错，并迭代。
- 对你的工具做防呆（poka-yoke）。更改参数，让犯错变得更难。

在构建我们用于 [SWE-bench](https://www.anthropic.com/research/swe-bench-sonnet) 的 agent 时，我们实际上在优化工具上花的时间，比在整体 prompt 上花的还多。例如，我们发现当 agent 移出根目录后，它会在使用相对路径的工具上犯错。为修复这一点，我们把工具改成总是要求绝对路径，而我们发现模型完美无误地用了这个方法。
