# 长时间运行 agent 的有效 harness

发布于 2025 年 11 月 26 日

Agent 在跨多个上下文窗口工作时仍面临挑战。我们向人类工程师寻求灵感，为长时间运行的 agent 打造了更有效的 harness。

随着 AI agent 变得更有能力，开发者日益要求它们承担需要跨越数小时甚至数天工作的复杂任务。然而，让 agent 在多个上下文窗口之间取得一致的进展，仍是一个未解难题。

长时间运行 agent 的核心挑战在于，它们必须在离散的分段会话里工作，而每个新会话开始时对之前发生了什么毫无记忆。想象一个由轮班工程师组成的软件项目，每位新工程师到岗时都对上一班发生了什么毫无记忆。因为上下文窗口是有限的，又因为多数复杂项目无法在单个窗口内完成，agent 需要一种在编码会话之间架桥的办法。

我们开发了一套双管齐下的方案，让 [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 能在许多上下文窗口之间有效工作：一个在首次运行时搭建环境的**初始化 agent**，以及一个被指派在每次会话里取得增量进展、同时为下一次会话留下清晰成果物的**编码 agent**。你可以在配套的 [quickstart](https://github.com/anthropics/claude-quickstarts/tree/main/autonomous-coding) 中找到代码示例。

## 长时间运行 agent 问题

Claude Agent SDK 是一个强大的、通用的 agent harness，擅长编码，也擅长其他要求模型使用工具来收集上下文、规划和执行的任务。它具备像压缩这样的上下文管理能力，使 agent 能在不耗尽上下文窗口的情况下处理任务。理论上，有了这套配置，agent 应该能持续地做任意长时间的有用工作。

然而，压缩还不够。开箱即用时，即便是像 Opus 4.5 这样的前沿编码模型，在 Claude Agent SDK 上跨多个上下文窗口循环运行，若只给它一个高层 prompt（例如「构建一个 [claude.ai](http://claude.ai/redirect/website.v1.149f6d93-8934-407f-a58d-77445d6c3082) 的克隆」），也无法造出一个生产质量的 web 应用。

Claude 的失败表现为两种模式。首先，agent 倾向于一次做太多——本质上是想一次性搞定整个应用。这常常导致模型在实现中途耗尽上下文，让下一次会话开始时一个功能只实现了一半、且没有文档。随后 agent 不得不猜测发生了什么，并花大量时间试图让基础应用重新能跑。这即便有压缩也会发生，而压缩并不总能给下一个 agent 传递足够清晰的指令。

第二种失败模式常在项目后期出现。在一些功能已经构建之后，一个较晚的 agent 实例会环顾四周、看到已有进展，就宣布工作完成了。

这把问题分解成两部分。第一，我们需要搭建一个初始环境，为给定 prompt 所要求的*全部*功能打下基础，从而让 agent 能一步步、一个功能一个功能地工作。第二，我们应当 prompt 每个 agent 在其目标上取得增量进展，同时在会话结束时把环境留在一个干净状态。所谓「干净状态」，指的是那种适合合并到主分支的代码：没有重大 bug，代码有序且有良好文档，总体上，一个开发者能轻松地开始一个新功能的工作，而不必先清理一堆无关的烂摊子。

在内部实验时，我们用一个两部分方案解决了这些问题：

- 初始化 agent：第一个 agent 会话使用一个专门的 prompt，要求模型搭建初始环境：一个 `init.sh` 脚本、一个记录 agent 都做了什么日志的 claude-progress.txt 文件，以及一个显示添加了哪些文件的初始 git 提交。
- 编码 agent：每个后续会话都要求模型取得增量进展，然后留下结构化的更新。1

这里的关键洞见，是找到一种让 agent 在从一个全新上下文窗口开始时能快速理解工作状态的方法，这靠 claude-progress.txt 文件连同 git 历史来实现。这些实践的灵感，来自于了解有效软件工程师每天都在做什么。

## 环境管理

在更新的 [Claude 4 提示指南](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/claude-4-best-practices#multi-context-window-workflows)里，我们分享了多上下文窗口工作流的一些最佳实践，包括一种使用「对第一个上下文窗口用不同 prompt」的 harness 结构。这个「不同的 prompt」请求初始化 agent 搭建一个环境，其中包含未来编码 agent 有效工作所需的全部上下文。这里，我们对这样一个环境的若干关键组件做更深入的展开。

### 功能清单

为解决 agent 一次性搞定整个应用、或过早认为项目已完成的问题，我们 prompt 初始化 agent 去写一份对用户初始 prompt 加以扩展的全面功能需求文件。在 [claude.ai](http://claude.ai/redirect/website.v1.149f6d93-8934-407f-a58d-77445d6c3082) 克隆的例子里，那意味着 200 多个功能，例如「用户可以新开一个聊天、输入一个查询、按下回车、并看到 AI 回复」。这些功能起初全部被标为「failing（未通过）」，好让后来的编码 agent 对完整功能长什么样有一个清晰的轮廓。

```
{
    "category": "functional",
    "description": "New chat button creates a fresh conversation",
    "steps": [
      "Navigate to main interface",
      "Click the 'New Chat' button",
      "Verify a new conversation is created",
      "Check that chat area shows welcome state",
      "Verify conversation appears in sidebar"
    ],
    "passes": false
  }
```

我们 prompt 编码 agent 只能通过更改一个 passes 字段的状态来编辑这份文件，并使用像「删除或编辑测试是不可接受的，因为这可能导致缺失或带 bug 的功能」这样措辞强硬的指令。经过一些实验，我们最终选定了用 JSON，因为相比 Markdown 文件，模型不太可能不当更改或覆盖 JSON 文件。

### 增量进展

有了这套初始环境脚手架，编码 agent 的下一个迭代被要求一次只处理一个功能。这种增量方法最终成为解决 agent 一次做太多倾向的关键。

一旦增量地工作，模型在做出代码改动后把环境留在干净状态仍然至关重要。在我们的实验中，我们发现引出这种行为最好的方式，是要求模型把它的进展用描述性的提交信息提交到 git，并在一份进度文件里写下它进展的摘要。这让模型能用 git 回滚糟糕的代码改动、恢复代码库的可用状态。

这些做法也提高了效率，因为它们消除了 agent 去猜测发生了什么、并花时间试图让基础应用重新能跑的需要。

### 测试

我们观察到的最后一个主要失败模式，是 Claude 倾向于在没有妥善测试的情况下就把一个功能标记为完成。在没有明确 prompt 时，Claude 倾向于做出代码改动、甚至用单元测试或对开发服务器跑 `curl` 命令来做测试，却识别不出这个功能并没有端到端地工作。

就构建一个 web 应用而言，一旦被明确 prompt 使用浏览器自动化工具、并像人类用户那样做所有测试，Claude 在端到端验证功能上大体做得不错。

Claude 在测试 claude.ai 克隆时通过 Puppeteer MCP 服务器截取的截图。

给 Claude 提供这类测试工具显著提升了性能，因为 agent 能识别并修复那些单从代码看不出来的 bug。

一些问题仍在，比如 Claude 视觉的局限、以及浏览器自动化工具的局限，使识别每种 bug 都很困难。例如，Claude 通过 Puppeteer MCP 看不到浏览器原生的 alert 模态框，依赖这些模态框的功能因此往往更带 bug。

## 快速上手

在这一切就位之后，每个编码 agent 都被 prompt 跑一系列步骤来弄清状况，有些相当基本但仍有帮忙：

- *运行 `pwd` 看你工作在哪个目录。你只能编辑这个目录里的文件。*
- *阅读 git 日志和进度文件，弄清楚最近在处理什么。*
- *阅读功能清单文件，并选择一个尚未完成的功能里优先级最高的去处理。*

这种方法在每个会话里给 Claude 省下了些 token，因为它不必去琢磨如何测试代码。同样有帮助的，是请初始化 agent 写一个能运行开发服务器的 init.sh 脚本，然后在实现新功能前跑一遍基本的端到端测试。

在 claude.ai 克隆的例子中，这意味着 agent 总是启动本地开发服务器，并用 Puppeteer MCP 新开一个聊天、发一条消息、收到一个回复。这确保了 Claude 能快速识别应用是否被留在了损坏状态、并立即修复任何现有 bug。如果 agent 反而开始实现一个新功能，它很可能会让问题更糟。

有了这一切，一个典型的会话以下面这些 assistant 消息开场：

```
[Assistant] I'll start by getting my bearings and understanding the current state of the project.
[Tool Use] <bash - pwd>
[Tool Use] <read - claude-progress.txt>
[Tool Use] <read - feature_list.json>
[Assistant] Let me check the git log to see recent work.
[Tool Use] <bash - git log --oneline -20>
[Assistant] Now let me check if there's an init.sh script to restart the servers.
<Starts the development server>
[Assistant] Excellent! Now let me navigate to the application and verify that some fundamental features are still working.
<Tests basic functionality>
[Assistant] Based on my verification testing, I can see that the fundamental functionality is working well. The core chat features, theme switching, conversation loading, and error handling are all functioning correctly. Now let me review the tests.json file more comprehensively to understand what needs to be implemented next.
<Starts work on a new feature>
```

Agent 失败模式与解决方案

| **问题** | **初始化 Agent 的行为** | **编码 Agent 的行为** |
| --- | --- | --- |
| Claude 过早对整个项目宣布胜利。 | 搭建一个功能清单文件：基于输入规格，搭建一个含端到端功能描述列表的结构化 JSON 文件。 | 在会话开头读取功能清单文件。选择单个功能开始处理。 |
| Claude 把环境留在带 bug 或无文档进展的状态。 | 写下一个初始 git 仓库和进度笔记文件。 | 通过阅读进度笔记文件和 git 提交日志开始会话，并在开发服务器上跑一个基本测试以捕捉任何无文档的 bug。通过写一个 git 提交和进度更新结束会话。 |
| Claude 过早地把功能标记为已完成。 | 搭建一个功能清单文件。 | 自验证所有功能。只在仔细测试后才把功能标记为「passing」。 |
| Claude 不得不花时间琢磨如何运行应用。 | 写一个能运行开发服务器的 `init.sh` 脚本。 | 通过阅读 `init.sh` 开始会话。 |

## 未来的工作

这项研究展示了长时间运行 agent harness 中使模型能在许多上下文窗口之间取得增量进展的一组可能方案。然而，仍有未解的问题。

最值得注意的是，单个通用的编码 agent 是否在各情境下表现最佳、还是通过多 agent 架构能取得更好表现，仍不清楚。看起来合理的是，像测试 agent、质量保证 agent 或代码清理 agent 这样专门的 agent，能在软件开发生命周期中的子任务上做得更好。

此外，这个演示为全栈 web 应用开发做了优化。一个未来方向是把这些发现推广到其他领域。很可能，这些经验中部分或全部可以应用到例如科学研究或金融建模中那种需要长时间运行 agentic 任务上。
