# 为 AI agent 做有效的上下文工程

发布于 2025 年 9 月 29 日

上下文对 AI agent 是一种关键但有限的资源。在本文里，我们探讨如何有效编排和管理为它们提供动力的上下文。

在「prompt 工程」成为应用 AI 界关注焦点数年之后，一个新词开始走红：**上下文工程**。用语言模型构建，正越来越少地关乎为你的 prompt 找到恰当的措辞，而更多地关乎回答一个更宏观的问题——「什么样的上下文配置，最有可能生成我们模型所期望的行为？」

**上下文（Context）** 指的是从大语言模型（LLM）采样时所包含的那组 token。当下的**工程**问题，是针对 LLM 的固有约束优化这些 token 的效用，从而稳定地达成一个期望结果。驾驭 LLM 常常需要*以上下文的方式思考*——换句话说：考虑 LLM 在任何给定时刻可用的整体状态，以及该状态可能引出的潜在行为。

在本文里，我们会探索上下文工程这门正在形成的艺术，并为构建可控、高效的 agent 提供一个精炼的心智模型。

## 上下文工程 vs. prompt 工程

在 Anthropic，我们把上下文工程视为 prompt 工程的自然演进。Prompt 工程指的是为最优结果而撰写和组织 LLM 指令的方法（概览和有用的 prompt 工程策略见[我们的文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)）。**上下文工程**指的是在 LLM 推理期间编排和维护最优 token 集（信息）的一套策略，包括 prompt 之外可能落入其中的所有其他信息。

在早期用 LLM 做工程的日子里，写 prompt 是 AI 工程工作中最大的组成部分，因为日常聊天交互之外的大多数用例，都需要为一次性分类或文本生成任务优化的 prompt。顾名思义，prompt 工程的首要焦点是如何撰写有效的 prompt，尤其是系统 prompt。然而，当我们朝着更有能力的、跨多轮推理和更长时间跨度运作的 agent 做工程时，我们需要管理整个上下文状态（系统指令、工具、[Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro)（MCP）、外部数据、消息历史等）的策略。

一个在循环里运行的 agent 会产出越来越多、对下一轮推理*可能*相关的数据，而这些信息必须被循环地打磨。上下文工程，就是从那个不断演化的、可能信息构成的宇宙里，编排什么会进入有限上下文窗口的[艺术与科学](https://x.com/karpathy/status/1937902205765607626?lang=en)。

与撰写一个 prompt 这种离散任务相反，上下文工程是迭代式的，而编排环节每次发生在我们决定传给模型什么的时候。

## 为什么上下文工程对构建有能力的 agent 很重要

尽管它们很快、且能管理越来越大的数据量，我们观察到 LLM 和人一样，在某个点会失去专注或陷入困惑。关于「大海捞针」式基准的研究揭示了一个叫[上下文腐烂（context rot）](https://research.trychroma.com/context-rot)的概念：随着上下文窗口里 token 数增加，模型从该上下文准确回忆信息的能力下降。

虽然某些模型比其他模型表现出更温和的退化，这一特性在所有模型上都会出现。因此，上下文必须被当作一种边际收益递减的有限资源来对待。就像拥有[有限工作记忆容量](https://journals.sagepub.com/doi/abs/10.1177/0963721409359277)的人类，LLM 在解析大量上下文时会动用它们的「注意力预算」。每引入一个新 token 都会消耗掉这个预算一定额度，从而加大对 LLM 可用 token 仔细编排的需要。

这种注意力稀缺源自 LLM 的架构约束。LLM 基于 [transformer 架构](https://arxiv.org/abs/1706.03762)，它让每个 token 都能[关注其他每一个 token](https://huggingface.co/blog/Esmail-AGumaan/attention-is-all-you-need)跨越整个上下文。这对 n 个 token 产生 n² 的两两关系。

随着上下文长度增加，模型捕捉这些两两关系的能力被拉得越来越薄，在上下文大小与注意力专注之间造成一种天然的张力。此外，模型从训练数据分布中发展它们的注意力模式，其中较短序列通常比较长序列更常见。这意味着模型对跨上下文的依赖经验更少、专门的参数也更少。

像[位置编码插值](https://arxiv.org/pdf/2306.15595)这样的技术，让模型能把更长的序列适配到原本训练的小上下文上来处理，尽管在 token 位置理解上会有一些退化。这些因素形成一个性能梯度而非一道硬悬崖：模型在长上下文上仍保持高能力，但相比它们在短上下文上的表现，在信息检索和长程推理上可能精度降低。

这些现实意味着，周密的上下文工程对构建有能力的 agent 至关重要。

## 有效上下文的构造

鉴于 LLM 受限于一个有限的注意力预算，*好的*上下文工程意味着找到*尽可能小的*一组高信号 token，使某个期望结果的可能性最大化。落实这一实践说起来容易做起来难，但在下面几节，我们会在上下文的各个组件上勾勒这一指导原则在实践中意味着什么。

**系统 prompt** 应当极为清晰，用简单、直接的语言，以*恰当的抽象高度*呈现想法。恰当的抽象高度，处在两种常见失败模式之间的「黄金分割区」。在一个极端，我们看到工程师在 prompt 里硬编码复杂脆弱的逻辑，以引出确切的 agentic 行为。这种做法制造脆弱性、并随时间增加维护复杂度。在另一个极端，工程师有时提供含糊的高层指导，未能给 LLM 关于期望输出的具体信号，或错误地假设了共享上下文。最佳高度取得一种平衡：足够具体以有效引导行为，又足够灵活以给模型提供引导行为的强启发式规则。

在光谱的一端，是脆弱的、if-else 硬编码的 prompt；另一端是过于宽泛、或错误假设共享上下文的 prompt。

我们建议把 prompt 组织成清晰的章节（如 `<background_information>`、`<instructions>`、`## Tool guidance`、`## Output description` 等），并使用像 XML 标签或 Markdown 标题这样的技术来划分这些章节，尽管随着模型变得更强大，prompt 的确切格式可能越来越不重要。

无论你决定如何组织你的系统 prompt，你都应致力于找到能完整勾勒你期望行为的最小信息集。（注意，最小不一定意味着短；你仍需给 agent 足够的前置信息，以确保它遵从期望行为。）最好先用一个最小的 prompt 配合当前可用的最强模型来测试、看它在你的任务上表现如何，然后基于初次测试中发现的失败模式添加清晰的指令和示例以提升表现。

**工具**让 agent 能与其环境运作、并在工作时拉入新的额外上下文。因为工具定义了 agent 与其信息/动作空间之间的契约，让工具促进效率——既通过返回 token 高效的信息，也通过鼓励高效的 agent 行为——就极其重要。

在[为 AI agent 编写工具——借助 AI agent](https://www.anthropic.com/engineering/writing-tools-for-agents)里，我们讨论了构建被 LLM 良好理解、且功能重叠最少的工具。就像设计良好的代码库的函数那样，工具应当自包含、对错误稳健、并在其预期用途上极为清晰。输入参数也应当同样具描述性、无歧义，并发挥模型固有的长处。

我们见到的最常见失败模式之一，是覆盖太多功能、或导致关于该用哪个工具的决策点含糊不清的臃肿工具集。如果一个人类工程师都无法确切说出在某个情形下该用哪个工具，就不能指望一个 AI agent 做得更好。正如我们稍后会讨论的，为 agent 编排一个最小可行工具集，也能促成跨长交互更可靠的维护和上下文裁剪。

提供示例——aka few-shot prompt——是一条众所周知的最佳实践，我们继续强烈建议采用。然而，团队常常把一堆杂乱边缘情形塞进 prompt，试图阐明 LLM 在某个特定任务上应遵循的每一条规则。我们不建议这样做。相反，我们建议致力于编排一组多样、典范的示例，有效地刻画 agent 的期望行为。对一个 LLM 来说，示例就是胜过千言万语的「图像」。

我们对上下文各个组件（系统 prompt、工具、示例、消息历史等）的总体建议是：审慎而为，让你的上下文信息丰富、却又精炼。现在让我们深入到运行时动态检索上下文。

## 上下文检索与 agentic 搜索

在[构建高效的 AI agent](https://www.anthropic.com/research/building-effective-agents)里，我们强调了基于 LLM 的工作流与 agent 之间的区别。自我们写了那篇文章以来，我们倾向于对 agent 采用一个[简单的定义](https://simonwillison.net/2025/Sep/18/agents/)：LLM 在循环里自主使用工具。

与我们的客户并肩工作，我们看到整个领域正在收敛到这个简单的范式。随着底层模型变得更强大，agent 的自主程度可以随之扩展：更聪明的模型让 agent 能独立导航微妙的问题空间并从错误中恢复。

我们现在看到工程师在为 agent 设计上下文的方式上发生转变。如今，许多 AI 原生应用采用某种形式的、基于嵌入的推理前检索，来浮现供 agent 推理的重要上下文。随着该领域转向更 agentic 的方法，我们越来越多地见到团队用「即时（just in time）」上下文策略来增强这些检索系统。

用「即时」方法构建的 agent，不预先处理所有相关数据，而是维护轻量标识符（文件路径、存储的查询、网络链接等），并用这些引用在运行时通过工具把数据动态加载进上下文。Anthropic 的 agentic 编码方案 [Claude Code](https://www.anthropic.com/claude-code) 就用这一方法对大型数据库执行复杂数据分析。模型能编写有针对性的查询、存储结果、并利用像 head 和 tail 这样的 Bash 命令来分析大量数据，而从不把完整的数据对象加载进上下文。这种做法映照了人类认知：我们通常不会记住整部语料的信息，而是引入外部组织和索引系统——如文件系统、收件箱、书签——按需检索相关信息。

除了存储效率，这些引用的元数据还提供了一种机制，有效地打磨行为，无论是显式提供还是直觉上的。对一个在文件系统中运作的 agent，`tests` 文件夹里一个名为 `test_utils.py` 的文件的存在，暗示着一个不同于 `src/core_logic/` 里同名文件的目的。文件夹层级、命名惯例和时间戳都提供了重要信号，帮助人类和 agent 理解如何、何时使用信息。

让 agent 自主导航和检索数据，也促成渐进式披露——换句话说，允许 agent 通过探索逐步发现相关上下文。每次交互都产出为下一个决策提供信息的上下文：文件大小暗示复杂性；命名惯例提示目的；时间戳可以是相关度的代理。agent 能一层层地组装理解，只在工作记忆里保留必要的东西，并利用记笔记策略做额外持久化。这种自管理的上下文窗口让 agent 专注于相关子集，而不是淹没在详尽但可能无关的信息中。

当然，这里有一个权衡：运行时探索比检索预计算的数据更慢。而且，需要有主见、周密的工程来确保 LLM 拥有正确的工具和启发式规则去有效导航其信息版图。没有恰当的指导，agent 会因误用工具、追死胡同、或未能识别关键信息而浪费上下文。

在某些设定里，最有效的 agent 可能采用一种混合策略，为速度预先检索部分数据，并自行 pursuit 更进一步的自主探索。对于「恰当」自主程度的决策边界取决于任务。Claude Code 是一个采用这种混合模型的 agent：CLAUDE.md 文件被朴素地预先放入上下文，而像 glob 和 grep 这样的原语让它即时地导航其环境和检索文件，有效地绕过了陈旧索引和复杂语法树的问题。

混合策略或许更适合内容不那么动态的上下文，例如法律或金融工作。随着模型能力提升，agentic 设计会趋向于让聪明的模型聪明地行动，配以日益减少的人工编排。鉴于该领域快速推进，对建立在 Claude 之上构建 agent 的团队，「做能奏效的最简单的事」很可能仍是我们最好的建议。

### 长时段任务的上下文工程

长时段任务要求 agent 在动作序列上维持连贯性、上下文和目标导向的行为，而其 token 数超出 LLM 的上下文窗口。对于跨越几十分钟到多小时的连续工作、像大型代码库迁移或综合性研究项目这样的任务，agent 需要专门的技术来绕开上下文窗口大小的限制。

等待更大的上下文窗口看起来是个显而易见的策略。但在可预见的未来，各种大小的上下文窗口很可能都会受上下文污染和信息相关性之困——至少在追求最强 agent 表现的那些情形里。为让 agent 能在更长的时间跨度上有效工作，我们开发了几项直接应对这些上下文污染约束的技术：压缩、结构化记笔记，和多 agent 架构。

**压缩**

压缩是这样一种实践：把一个接近上下文窗口极限的对话取其内容做摘要，并用该摘要重新初始化一个新的上下文窗口。压缩通常是上下文工程中驱动更好长期连贯性的第一个杠杆。其核心，压缩以高保真的方式提炼一个上下文窗口的内容，让 agent 能以最小的性能退化继续下去。

例如在 Claude Code 里，我们实现这一点，是通过把消息历史交给模型去总结并压缩最关键的细节。模型会保留架构决策、未解决的 bug 和实现细节，同时丢弃冗余的工具输出或消息。agent 随后能带着这份压缩后的上下文，加上最近访问的五个文件继续。用户获得了连续性而无需担心上下文窗口的限制。

压缩的艺术，在于选择保留什么 versus 丢弃什么，因为过于激进的压缩会导致丢失微妙但关键的上下文，而其重要性要到后来才显现。对于实现压缩系统的工程师，我们建议仔细调优你在复杂 agent trace 上的 prompt。先最大化召回，确保你的压缩 prompt 捕捉 trace 里每一条相关信息，然后通过剔除多余内容来迭代提升精确度。

一个唾手可得的多余内容的例子，就是清除工具调用和结果——当一个工具已在消息历史深处被调用过，agent 为何还需要再看一次原始结果？最安全、最轻触的形式之一的压缩，就是工具结果清除，最近作为[一项功能在 Claude Developer Platform 上发布](https://www.anthropic.com/news/context-management)。

**结构化记笔记**

结构化记笔记，或 agentic 记忆，是一种 agent 定期把笔记写到上下文窗口之外的持久记忆里的技术。这些笔记会在之后被拉回上下文窗口。

这种策略以最小开销提供了持久记忆。就像 Claude Code 创建一个待办清单，或你的自定义 agent 维护一个 NOTES.md 文件，这个简单的模式让 agent 能跨复杂任务跟踪进度，维持那些否则会在数十次工具调用之间丢失的关键上下文和依赖。

[Claude 玩宝可梦](https://www.twitch.tv/claudeplayspokemon)展示了记忆如何在非编码领域转变 agent 的能力。该 agent 在上千游戏步中维持精确的计数——跟踪诸如「过去 1,234 步我一直在 1 号道路训练我的宝可梦，Pikachu 已经朝着 10 级的目标升了 8 级」这样的目标。在对记忆结构没有任何 prompt 的情况下，它绘制已探索区域的地图、记住它已解锁了哪些关键成就，并维护战斗策略的战略性笔记，帮助它学会哪些攻击对不同对手最有效。

在上下文重置之后，agent 读它自己的笔记，继续多小时的训练序列或地牢探索。这种跨摘要步骤的连贯性，促成了把全部信息仅保持在 LLM 上下文窗口里时所不可能实现的长时段策略。

作为我们 [Sonnet 4.5 发布](https://www.anthropic.com/effective-context-engineering-for-ai-agents)的一部分，我们在 Claude Developer Platform 上以公开 beta 发布了一个[记忆工具](http://anthropic.com/news/context-management)，通过一个基于文件的系统，让存储和查阅上下文窗口之外的信息变得更容易。这让 agent 能随时间构建知识库、跨会话维持项目状态，并在不把一切保持在上下文里的前提下引用先前的工作。

**子 agent 架构**

子 agent 架构提供了另一种绕开上下文限制的方法。与其让一个 agent 试图跨整个项目维持状态，专门的子 agent 能用干净的上下文窗口处理聚焦的任务。主 agent 用一个高层计划协调，而子 agent 做深度技术工作或使用工具查找相关信息。每个子 agent 可能大量探索，用上数万乃至更多 token，但只返回它工作的一份精炼、蒸馏的摘要（通常 1,000-2,000 token）。

这种方式取得了一种清晰的关注点分离——详细的搜索上下文保持在各子 agent 内部隔离，而主 agent 专注于综合并分析结果。这一模式在[我们如何构建多 agent 研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)里有讨论，它在复杂研究任务上展示了相对单 agent 系统的显著提升。

这些方法之间的选择取决于任务特性。例如：

- 压缩为那些需要大量往返的任务维持对话流程；
- 记笔记在里程碑清晰的迭代式开发上表现出色；
- 多 agent 架构处理并行探索能带来回报的复杂研究和分析。

即便模型持续改进，跨更长交互维持连贯性的挑战，仍将是构建更有效 agent 的核心。

## 结论

上下文工程代表着我们如何用 LLM 构建的一次根本转变。随着模型变得更强大，挑战不仅仅是打磨一个完美的 prompt——而是审慎地编排每一步什么信息进入模型有限的注意力预算。无论你是为长时段任务实现压缩、设计 token 高效的工具、还是让 agent 即时探索其环境，指导原则始终如一：找到那组尽可能小的、能最大化你期望结果可能性的、高信号的 token。

我们勾勒的这些技术会随着模型改进而持续演化。我们已经看到更聪明的模型需要更少规定性的工程，让 agent 以更多自主性运作。但即便能力随之扩展，把上下文当作一种珍贵、有限的资源来对待，仍将处于构建可靠、有效 agent 的核心。
