# Anthropic 的一位市场人员如何用 Claude Code 向每位销售发去每周个性化更新

*Adam Ward 身处 Anthropic 的市场团队，他分享了如何用 Claude 把一份每周销售报告，转成为他支持的每位客户主管（AE）个性化定制的周一简报。*

作为市场人员，我面临的最大挑战之一，就是让销售团队随时了解一线正在发生的各种情况。大多数市场人员都熟悉那种走廊偶遇的对话：一位销售说「哦，我从没听说过那个活动」（或那份新白皮书、那场网络研讨会），于是你意识到自己错失了一次把最新工作分享给销售、进而分享给客户的机会。

我最初的解决方案是许多市场人员都会认出的一种：周一早上跟销售团队开一个 15 分钟的站会。我把周日晚上的时间用来汇总全业务线的更新，做成可展示的幻灯片，然后在会上现场交付，并把这叠幻灯片发到 Slack 上。工作完成了，对吧？并不完全是：有了 Claude 之后，这一切显得过于手动；随着我们团队壮大、我开始支持多个销售团队，我的幻灯片流程再也跟不上。这些更新也变得没那么有用了，因为我不再有时间去为每个团队挑出适合他们的机会。

我希望 Claude 来做这项工作，为每位销售打造一个更好的「产品」：一份贴合其客户、并与我们市场营销里一切动态相匹配的每周摘要。

幸运的是，我们组织了一场市场黑客松：一段专门用来用 Claude Code 重建可复用流程和工作的时间。我和团队凑在一起，为这个问题投入了一个小时，而这带来了决定性的差别。这类随意的、常由同事主导的学习机会（比如黑客松），让你得以进行日常中本不会特意腾出时间去做的实验和探索，我们团队也不例外。

## **你不需要会写代码，你需要会讲清楚**

我从同行市场人员那里得到的最大问题之一是：「我该如何上手 AI？」我的做法——尤其是在 Claude Code 上——是先用一个 prompt 开场，向 Claude 说明：虽然我不懂技术，但我有这个具体挑战；请把我当作一个深刻理解业务问题的产品经理，与我一步步协作。我会边想边说，所以我常常录下自己解释问题的声音，把文字稿给 Claude；这样 Claude 就拥有了全部业务上下文。

以我们团队的每周 AE 摘要为例，我先向 Claude 勾勒出目标：给每位销售发一条每周 Slack 消息，说明市场营销里正在发生什么、以及它将如何帮助他们的客户。然后我写了一份假的每周更新，给 Claude 一个要照着做的模板。我知道销售是行动导向的，所以我从「本周三件最重要的事」清单起步，列出三条行动项——比如即将举行的活动或最新发布的内容——供他们分享给客户。我还为经理的汇总单独写了一个模板，因为经理通常想要的是其团队的整体视图，而非仅仅是逐个客户。

接下来，我通过 MCP 把 Claude 连到 BigQuery；BigQuery 是我们市场团队的事实来源（source of truth），能对来自 HubSpot、Clay 和 Salesforce 的数据提供细粒度洞察。我想从简单起步，所以先从我们活动和网络研讨会的事实来源开始。为了把每条更新个性化，我让 Claude 从我们的 CRM 里拉取该销售的辖区，以及在 Slack 中传达的任何相关客户更新。这样，Claude 就能把这两者一起解析，生成一份个性化的每周更新。

随着时间推移，我与市场里其他团队协作来丰富数据，因此这份简报如今纳入了博客文章、电子书、客户案例、网络研讨会等新内容，甚至包括我们合作伙伴生态的活动。

## **用户反馈才是真正的 prompt 工程**

要向一线推广，我先从一支同意充当测试组的销售团队起步。发给一个 10 人的小组让我没那么发怵，以防出现错误；而这个小组也承诺会提供反馈。在最初那次发送后，我做了些调整。

有些问题纯粹是错误。例如，某个活动在源表里没有 URL，Claude 就编了一个看起来很合理、实则哪也去不了的地址。我们立刻把它写成 prompt 里的一条硬规则：绝不编造 URL。如今，一个链接只有在地址逐字符来自源表时才会渲染。后来的版本干脆把没有链接的活动从简报里完全剔除，因为我们意识到，我们的销售谁也无法为其报名的活动只是噪声。

到第一周结束时，这个 prompt 已容纳九条内容规则，每条都追溯自某位销售或某位经理的一条反馈。一位销售指出，某位工程副总裁被推荐去参加一个面向知识工作者的工作坊，于是现在联系人的职务会对照活动的目标受众做校验，不匹配的就悄悄略去。一道行业闸门会把零售客户挡在金融晚餐邀请之外，而还没有客户的极新销售会收到一封简短的欢迎信，而不是一条空白消息。

另一些问题是数据问题。市场营销里的任何人都知道维持一个事实来源有多难。比如，一线活动表在六周里被重新排列过三次列。为应对这一点，我们把 prompt 改成每次运行开头都先读表头行、并在撰写任何内容之前校验列映射。指令不再是硬编码「看 C 列」，而更像是「看含有活动 URL 的那一列」。

## **把摘要推广到整个业务**

在最初几次运行之后，我把这份摘要扩展到我所支持的每一个团队，现在一线市场为整个销售运行它。每周周一早上，跨 Anthropic 多个销售板块的客户主管打开 Slack，就能看到一条私信，列着本周三项优先行动、为其客户安排的一线活动、已报名参加即将举行网络研讨会的联系人、值得分享的相关市场内容，以及其他跟进建议。

每条消息都是根据收件人自己的客户列表生成的，所以没有两条消息是一样的。这份摘要在起作用：我们最近在一周内让一场高管晚餐的报名量翻了一倍，纯粹是因为对的销售在周一早上看到了对的活动。

当 Anthropic 的业务拓展代表（BDR）想要他们自己版本的摘要时，我们为他们复制了 prompt，只改动了一个字段，因为 BDR 在我们的 CRM 里通过不同于客户主管的关系映射到客户。prompt 结构和内容规则原封不动地沿用，BDR 在两天内就上线了。此后我也为客户成功团队和联盟团队做了同样的事，还为销售以外的其他跨职能合作方提供所有市场活动的总览。

无论业务推进得多快，我的团队和我在 Claude 的帮助下，确保销售们在周一开始时确切知道本周发生什么、该优先处理哪些客户和活动。每周一的发送都被完整归档，所以我能调出任何一位销售在任何日期收到的确切内容，而经理们能在一份汇总里看到整个团队的推荐。我仍然会阅读发出的内容，只是系统不再等待我的批准。几周前我休假时，周一的发送照常自行发出，毫无差错。

一份周一简报长什么样的示例，以界面模拟图呈现，其中的合成数据并不代表真实公司或个人。

## **上手 Claude 的最佳实践**

下面，我分享一些源自我自己使用 Claude Code 经验得到的技巧：

- **从小处起步，从你已经手动在做的事起步。** 当关于人们用 AI 在做什么的噪声如此之多时，起步可能很难。我的建议是：挑一个你花最多亲力亲为时间的重复任务，请 Claude 重建它。这样你就能判断输出，因为你已经知道好的样子是什么。如果问题仍然显得太大，就把 Claude 当作思考伙伴，把它拆成步骤。如果这是你要与他人分享的东西，先把早期运行发给你自己，好让你在别人之前抓到错误。
- **用平实的语言写指令，并给每份文档做版本。** 像给新同事交代那样向 Claude 说明，其余的交给 Claude。指示 Claude 把每次更新保存为一个带编号的版本，附一行说明改了什么，这样你就有了一份记录，记着每次过往运行是由哪个 prompt 产生的。我们的是一份 markdown 文件，我的同事为自己的板块运行它；我们从一份共享 Google Doc 起步，等到更多人需要编辑时就迁到了 GitHub。
- **用一个小的、有承诺的群体做试点。** 我们最初的一批测试，是找了几位我们明知愿意花时间给我们反馈、并长期改进报告的客户主管来跑的，他们帮我们检测错误，或就如何扩展或个性化覆盖范围提建议。
- **用反馈来改进你的 prompt，把每一处更正折叠成一条显式规则。** 当收件人开始与我们分享反馈、每一处更正都变成给 Claude 的一条显式规则时，这份市场简报才真正变得有用。

Claude 把我过去每周日要花上数小时的手动流程自动化了，但借这个项目，我和我的团队收获的东西远胜于时间：我们的产出如今更个性化、更有用、更可衡量。你能用 Claude 改进哪个市场流程？
