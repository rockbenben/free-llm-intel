# 推出 Contextual Retrieval（上下文检索）

发布于 2024 年 9 月 19 日

要让一个 AI 模型在特定情境中有用，它往往需要访问背景知识。

要让一个 AI 模型在特定情境中有用，它往往需要访问背景知识。例如，客服聊天机器人需要关于其所服务的具体业务的知识，而法律分析机器人需要了解大量过往案例。

开发者通常用检索增强生成（RAG）来增强 AI 模型的知识。RAG 是一种从知识库检索相关信息、并把它附加到用户 prompt 上的方法，从而显著增强模型的响应。问题在于，传统的 RAG 方案在编码信息时会把上下文抹除，这常常导致系统无法从知识库中检索到相关信息。

在本文里，我们概述一种能显著改善 RAG 中检索步骤的方法。该方法叫「Contextual Retrieval（上下文检索）」，使用两个子技术：Contextual Embeddings（上下文嵌入）和 Contextual BM25（上下文 BM25）。这一方法能把检索失败次数减少 49%，与重排序（reranking）结合时减少 67%。这些是检索精度上的显著提升，直接转化为下游任务上更好的性能。

你可以借助[我们的 cookbook](https://platform.claude.com/cookbook/capabilities-contextual-embeddings-guide)，轻松地用 Claude 部署你自己的上下文检索方案。

### 关于直接用更长 prompt 的一条说明

有时最简单的方案就是最好的。如果你的知识库小于 200,000 token（约 500 页材料），你可以干脆把整个知识库放进你给模型的 prompt 里，不需要 RAG 或类似方法。

几周前，我们为 Claude 发布了 [prompt 缓存](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)，让这种方法显著更快、更具成本效益。开发者如今能在 API 调用之间缓存常用 prompt，把延迟降低 > 2 倍、成本降低多达 90%（读我们的 [prompt 缓存 cookbook](https://platform.claude.com/cookbook/misc-prompt-caching) 可看它如何运作）。

然而，随着你的知识库增长，你会需要一个更可扩展的解法。这就是上下文检索的用武之地。

## RAG 入门：扩展到更大的知识库

对于放不下上下文窗口的更大知识库，RAG 是典型的解法。RAG 通过以下步骤预处理一个知识库：

- 把知识库（文档「语料」）拆解成更小的文本块，通常不超过几百 token；
- 用一个嵌入模型把这些块转成编码含义的向量嵌入；
- 把这些嵌入存储到一个可按语义相似度搜索的向量数据库里。

在运行时，当用户向模型输入一个查询，向量数据库被用来基于与查询的语义相似度找到最相关的块。然后，最相关的块被加进发给生成模型的 prompt。

虽然嵌入模型在捕捉语义关系上出色，它们却可能错过关键的字面匹配。幸好，有一项更老的技术能在这些情形里施以援手。BM25（Best Matching 25）是一种使用字面匹配来找精确词或短语匹配的排序函数。它对包含唯一标识符或技术术语的查询尤其有效。

BM25 建立在 TF-IDF（词频-逆文档频率）概念之上运作。TF-IDF 衡量一个词对语料库中某份文档有多重要。BM25 通过考虑文档长度、并对词频施加一个饱和函数来精炼这一点，从而有助于防止常见词主导结果。

下面是 BM25 能在语义嵌入失败之处成功的方式：假设用户在一个技术支持数据库里查询「Error code TS-999」。一个嵌入模型可能找到关于错误码的一般内容，却可能错过精确的「TS-999」匹配。BM25 会寻找这个特定的文本串来识别相关文档。

RAG 方案可以通过以下步骤结合嵌入和 BM25 技术，用如下方式更准确地检索最适用的块：

- 把知识库（文档「语料」）拆解成更小的文本块，通常不超过几百 token；
- 为这些块创建 TF-IDF 编码和语义嵌入；
- 用 BM25 基于精确匹配找到顶级块；
- 用嵌入基于语义相似度找到顶级块；
- 用排名融合技术合并并对 (3) 和 (4) 的结果去重；
- 把 top-K 块加进 prompt 以生成响应。

通过同时借力 BM25 和嵌入模型，传统 RAG 系统能提供更全面、准确的结果，在精确的术语匹配与更广的语义理解之间取得平衡。

一个使用嵌入和 Best Matching 25（BM25）来检索信息的标准检索增强生成（RAG）系统。TF-IDF（词频-逆文档频率）衡量词的重要性并构成 BM25 的基础。

这种方法让你能具成本效益地扩展到庞大的知识库，远超单个 prompt 所能容纳的。但这些传统 RAG 系统有一个重大局限：它们常常破坏上下文。

### 传统 RAG 中的上下文难题

在传统 RAG 中，文档通常被切成更小的块以便高效检索。虽然这种方法对许多应用管用，但当单个块缺乏足够上下文时可能引发问题。

例如，想象你知识库里嵌着一组财务信息（比如美国 SEC 备案文件），你收到如下问题：*"ACME Corp 在 2023 年第二季度的营收增长是多少？"*

一个相关的块可能含有文本：*"该公司的营收较上一季度增长了 3%。"* 然而，这个块本身没有指明它说的是哪家公司、或相关的时间段，使得检索正确的信息、或有效使用信息都很困难。

## 推出 Contextual Retrieval

上下文检索通过在某块被嵌入（「Contextual Embeddings」）和创建 BM25 索引（「Contextual BM25」）之前，把该块专属的说明性上下文前置到每个块上，来解决这一问题。

让我们回到我们那个 SEC 备案文件集合的例子。下面是一个块如何被转换的示例：

```
original_chunk = "The company's revenue grew by 3% over the previous quarter."

contextualized_chunk = "This chunk is from an SEC filing on ACME corp's performance in Q2 2023; the previous quarter's revenue was $314 million. The company's revenue grew by 3% over the previous quarter."
```

值得一提的是，过去也有人提出过利用上下文来改进检索的其他方法。其他提议包括：[给块加上通用的文档摘要](https://aclanthology.org/W02-0405.pdf)（我们做了实验、只见到极有限的增益）、[假设性文档嵌入](https://arxiv.org/abs/2212.10496)，以及[基于摘要的索引](https://www.llamaindex.ai/blog/a-new-document-summary-index-for-llm-powered-qa-systems-9a32ece2f9ec)（我们做了评估、只见低性能）。这些方法与本文所提议的不同。

### 实现 Contextual Retrieval

当然，手动标注一个知识库里成千甚至上百万个块，工作量大得离谱。为实现上下文检索，我们求助 Claude。我们写了一个 prompt，指示模型提供简洁、针对该块的上下文，用整篇文档的语境来解释这个块。我们用下面的 Claude 3 Haiku prompt 为每个块生成上下文：

```
<document> 
{{WHOLE_DOCUMENT}} 
</document> 
Here is the chunk we want to situate within the whole document 
<chunk> 
{{CHUNK_CONTENT}} 
</chunk> 
Please give a short succinct context to situate this chunk within the overall document for the purposes of improving search retrieval of the chunk. Answer only with the succinct context and nothing else. 
```

所得的上下文文本，通常 50-100 token，会在嵌入它之前、也在创建 BM25 索引之前被前置到块上。

### 用 Prompt 缓存降低 Contextual Retrieval 的成本

上下文检索在 Claude 上能以低成本独特地实现，多亏了我们上面提到的那个专门的 prompt 缓存特性。借助 prompt 缓存，你不必为每个块都传入参考文档。你只需把文档加载进缓存一次，然后引用先前缓存的内容。假设 800 token 的块、8k token 的文档、50 token 的上下文指令、每块 100 token 的上下文，**生成上下文化块的单次成本为每百万文档 token 1.02 美元**。

#### 实现考量

在实现上下文检索时，有几点要留心：

- **块边界：** 考虑你如何把文档拆成块。块大小、块边界和块重叠的选择都会影响检索性能 1。
- **嵌入模型：** 尽管上下文检索在我们测试的所有嵌入模型上都改进了表现，某些模型可能获益更多。我们发现 [Gemini](https://ai.google.dev/gemini-api/docs/embeddings) 和 [Voyage](https://www.voyageai.com/) 嵌入尤其有效。
- **定制的上下文化器 prompt：** 虽然我们提供的通用 prompt 工作得很好，你或许能用契合你特定领域或用例的 prompt 达到甚至更好的结果（例如，纳入一份关键术语词汇表，而这些术语只在知识库里的其他文档中被定义）。
- **块的数量：** 把更多块加入上下文窗口，会增加你纳入相关信息的机会。然而，更多信息对模型而言会分散注意力，所以这里有一个上限。我们试了交付 5、10、20 个块，发现用 20 个是这几个里性能最佳的（比较见附录），但值得在你自己的用例上做实验。

**永远跑评测：** 通过把上下文化的块传给响应生成、并区分什么是上下文、什么是块，响应生成可以被改进。

## 用重排序进一步提升性能

在最后一步，我们可以把上下文检索与另一项技术结合，带来更多性能提升。在传统 RAG 中，AI 系统搜索其知识库以找到可能相关的信息块。对大知识库，这一初始检索常常返回大量——有时数百个——相关度和重要性不一的块。

重排序是一种常用的过滤技术，以确保只有最相关的块被传给模型。重排序提供更好的响应、并降低成本和延迟，因为模型处理的信息更少。关键步骤是：

- 执行初始检索以找到 top 可能相关的块（我们用了 top 150）；
- 把 top-N 块连同用户的查询一起通过重排序模型；
- 用一个重排序模型，基于相关度和对 prompt 的重要性给每个块打分，然后选出 top-K 块（我们用了 top 20）；
- 把 top-K 块作为上下文传给模型以生成最终结果。

结合 Contextual Retrieval 和重排序以最大化检索精度。

### 性能提升

市场上有几个重排序模型。我们用 [Cohere reranker](https://cohere.com/rerank) 跑了我们的测试。Voyage [也提供一个重排序器](https://docs.voyageai.com/docs/reranker)，尽管我们没来得及测试。我们的实验显示，在各领域，加入一个重排序步骤能进一步优化检索。

具体地，我们发现重排序的 Contextual Embedding 和 Contextual BM25 把 top-20 块检索失败率降低了 67%（5.7% → 1.9%）。

重排序的 Contextual Embedding 和 Contextual BM25 把 top-20 块检索失败率降低 67%。

#### 成本与延迟考量

关于重排序，一个重要的考量是对延迟和成本的影响，尤其是在重排序大量块时。因为重排序在运行时加了一个额外步骤，它不可避免地增加一点延迟，尽管重排序器并行地为所有块打分。在「重排序更多块以换取更好性能」与「重排序更少块以换取更低延迟和成本」之间存在一种固有的权衡。我们建议在你自己的用例上尝试不同设置，找到恰当的平衡。

## 结论

我们跑了大量测试，比较上述所有技术的不同组合（嵌入模型、BM25 的使用、上下文检索的使用、重排序器的使用、以及总共 top-K 检索结果数），全都跨多种不同的数据集类型。下面是我们的发现概要：

- 嵌入 + BM25 优于单独使用嵌入；
- Voyage 和 Gemini 在我们测试的之中嵌入最佳；
- 把 top-20 块传给模型比只传 top-10 或 top-5 更有效；
- 给块加上下文能大幅改善检索精度；
- 重排序优于不重排序；
- **这些好处全部叠加**：为最大化性能提升，我们可以结合上下文嵌入（来自 Voyage 或 Gemini）与上下文 BM25，再加一个重排序步骤，并把 20 个块加进 prompt。
