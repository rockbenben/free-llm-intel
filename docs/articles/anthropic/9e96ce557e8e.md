了解 Warp 如何设计出一种任何人都能用来创建自我改进 agent 的简单开发模式。

Agent 需要可靠且高效地处理重复性任务。一个能答对 80% 任务的初版 prompt，会给用户造成嘈杂而恼人的体验。Warp 是吃过苦头才学到这一点的，并据此塑造它的产品策略，为全球近 100 万开发者打造了改进后的体验。

Warp——这款 AI 驱动的终端和 agentic 开发环境——构建在 Claude Platform 之上。团队在其内部代码审查 agent 上撞上了这个「嘈杂体验」问题。工程师抱怨他们的 agent 会留下没用的评论、产出低质量的输出。

团队起初试过权宜之计，比如根据观察到的代码审查失败手动重写 prompt。这让输出更好用，但无法扩展。改进 AGENTS.md 这类上下文文件也有帮助，但远非彻底的解决方案。

最终，他们意识到，真正的问题在于：给到一个 agent 的反馈——无论它的目的是什么——通常会在会话结束时消失，把关键上下文从 agentic 回路中抽走。他们的解法是：一个基于 [Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) 的框架，用来创建自我改进的 agent，让反馈随时间累积，持续打磨并增强 agent 的输出。

请继续阅读，了解他们如何在 Claude Platform 之上用 skills 构建它。

## **建立在 skills 之上的 agent 自我改进回路**

核心技巧是一个使用 [**skills**](https://support.claude.com/en/articles/12512176-what-are-skills) 的自我改进回路——skills 是以文件形式编码的知识，把指令与原始 prompt 隔离开。Warp 演化出一套由两个 skill 组成、中间夹着人类反馈的自我改进 agent 架构。

**内层/基础 skill** 承载功能性的领域知识和指令。例如，当一个 PR 被打开时，Warp 的代码 agent 使用那个基础 skill 和上下文来执行、产出它的审查。

关于 agent 输出的**人类反馈**是自我改进回路的关键组成部分。对于代码审查，这可以简单到一个点赞，但越明确越好。

Warp 创始人 Zach Lloyd 解释道：「人可以肯定地说『这是一条好的、有用的评论』，但人也可以给出详细的原因，说明某次代码审查为什么不好。像『你建议重命名这个变量，但我们的代码库惯例是这类全局变量使用这个特定的命名上下文』这样的具体信息，能告诉 agent 下次该怎么做对。」

**外层/改进器 skill** 充当一个观察 agent，按调度而非按任务运行。它拉取累积的人类反馈，把 agent 的建议与人类的回应做对比，并对基础 skill 提出一个小的、聚焦的编辑。

因为 skills 就是纯文件，agent 极擅于更新它们。这些可审阅、可批准、可合并的更新，能走一套普通的 PR/代码审查工作流；一旦合并，内层 skill 的下一次运行就继承了这一改进。

Warp 如今在其整个开源仓库上运行这一模式，配有各自的规格撰写、审查和分类 agent，每个都带着自己的自我改进回路。

Zach 说：「基于文件的 skills 是一种为 agent 编码知识的方式，而不把那些知识直接放进 prompt——它成了 agent 在做事过程中可以随手查阅的东西。这个框架其实非常简单：有一个基础的领域专用 skill，然后有一个改进器 skill 去精炼那个领域专用 skill。这种简单正是这一方法的美妙之处。」

## **如何为 agent 编写自我改进的 skill**

下面是 Warp 团队为 agentic 回路编写自我改进 skill 的一些屡试不爽的技巧：

- **写原则，而不是规则。** Zach 说：「构造 skill 时，要像在给一个聪明人做指导，而不是像在编程一台计算机。」在 skill 里包含诸如『留意重复代码』这样的方向，比穷举变量命名规则能提供更好的指导。
- **解释为什么。** 给出规则背后的理由，能让 agent 去推理问题，而非死板地遵循指令，从而再次带来更好的泛化。
- **让反馈易于给出。** 在人们已经工作的地方捕获它，比如直接在 PR 或 issue 上评论。同时让它自动发生，不需要额外的提交步骤。Zach 指出：「低摩擦才让信号持续流动。如果你做得太难，你就拿不到反馈，也就无法改进 skill。」
- **保持 skill 精简，并渐进式披露。** [一个好的 skill](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) 文件并不大；它引用资源文件和脚本，而不是把一切都一次性倒入上下文。
- **反馈质量 > 数量，但数量也有帮助。** 一位资深工程师少量而详尽、领域专用的反馈，可能胜过大量粗略反馈，因为简单的点赞/点踩并说不出*为什么*。Zach 继续道：「即使样本量相对小，只要它是围绕领域知识、由一个人给出的非常详细的反馈——那种 agent 本无从获得的知识——你也能得到非常好的信号。话虽如此，优质信号的语料越大越好。在 Warp，我们用回路来管理我们的整个开源仓库。我们有数百人在贡献，我们在做数千次代码审查。」
- **在改进器 skill 上多下功夫。** 在编写改进器 skill（观察 agent）上多下功夫，其回报超出眼前的 agent 回路，因为改进器 skill 在不同用例间非常可复用。「除了领域专用知识那一块，这是一个相当可复用的机制——代码审查 agent 的改进器 skill，与任何其他 agent 的改进器 skill 差别不大。」

## **回路的实际运作：Warp 的 issue 分类 agent**

[Warp 的 issue 分类 agent](https://github.com/warpdotdev/warp-agents-demo-github-issue-triage) 展示了这套自我改进 agent skills 框架。只要有有人提一个新的 GitHub issue，这个模式就被触发：一个 GitHub Action 拉起一个 agent，它分析 issue 的复杂性和可行性、贴上标签，并建议一个修复方向。那个分类 agent 靠一个内层 skill 文件运行，里面持有关于每个标签意味着什么、以及在行动前如何研究代码库的领域知识。

在一个示例 issue 上，第一阶段的内层 skill 干得不错，但漏了一个标签——ready to spec，它标示一位贡献者可以开始针对该 issue 撰写产品和技术规格。Warp 团队的一位维护者发现了这个缺口，直接在 issue 上留下反馈，就在工作进行的地方。关键在于，他既解释了他期望什么、也解释了他为什么这么期望：这是一条对 agent 日后易于吸收的、可执行的反馈。

外层改进器 skill 在 [Oz——Warp 的 agent 编排平台](https://docs.warp.dev/)上运行，作为一个定时的「更新分类」agent。该 agent 认证到 GitHub，运行一个随 skill 打包的 Python 脚本来拉取带反馈的近期 issue，把它们汇总成一个 JSON 文件，并读回上下文。这个打包的脚本本身就是一条最佳实践；skill 可以引用资源文件，而不是每次运行都重写新代码。

从那里出发，agent 识别出维护者评论里那些具体的反馈信号，并提出能捕捉它们的最小编辑。它开了一个编辑内层 skill 的 PR：当一个 issue 描述了一个真实问题、尽管确切的 UI 或 UX 形态尚未定义时，就贴上「ready to spec」标签。

因为整个更新就是一个 skill 文件，它走的是普通的代码审查工作流。这个 PR 附带一段描述，解释是哪些信号促成了改动、它改了什么。人类审阅、批准并合并，分类 skill 的下一次运行就继承了这份新知识。最后这一步人类把关，闭合了回路，并让一个人掌控实际发生的变化。

这同一套机制，就是 Warp 如今在其开源仓库上规模化运行的：规格撰写 agent、审查 agent 和分类 agent 各自带着自己的自我改进回路。

任何 agent，无论它的任务是什么，只要你从一开始就在它里面构建这样一个回路来捕获人类反馈信号、把它们变成 skill 更新，并把 agent 从一次性的助手扩展为在你组织里不断累积能力的系统，它都会随时间变得更好。

| 来自 Warp 团队的最佳实践 |  |
| --- | --- |
| 你是否把 skills 与 memory 混为一谈？ | Skills 是程序性且稳定的——「如何做 X」，与运行无关，被刻意修改。Memory 是 agent 在推理时自动写入的，从不停止变化。 |
| 你需要一个改进器回路，还是每个 agent 一个？ | 折中：一个模板化的基础回路捕捉你各 agent 之间的重叠，再叠上领域专用的权重。 handful 几个改进器可以各自独占一个；上百个就应当共享。 |
| 当反馈是错的时会怎样？ | 假定它会发生。不要让 agent 盲目接受反馈——给它上下文去做合理性检查，过滤谁的输入算数，并在过滤环节或终审环节把人类留在回路里。 |
| 你的领域可验证吗？ | 先构建验证框架，再让 agent 针对它调优：生成一份参考语料、把输出与参考比对、修正、重复。 |
| 如果领域不可验证呢？ | 凡存在黄金输出的地方，就依靠对它们的确定性评测。凡必须使用人类反馈之处，把它限定给领域专家——不要开闸放水。 |
| 你怎么知道整个系统在改进？ | 跟踪人类已经在目视的全局指标——合并耗时、贡献者数量、成本——并把它们反馈进改进器 agent。在部署上「爬-走-跑」。 |
