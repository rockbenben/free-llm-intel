# Cresta 如何将 CX 专业知识转变为 Claude Agent SDK 上的代理构建器

*在本系列 **How startups build with Claude** 中，我们审视 AI 产品背后的决策。这一篇我们来探索 [Cresta](https://cresta.com/) 如何把它在构建 AI 原生客户体验上的专长，带进 [Conductor](https://cresta.com/blog/cresta-conductor-the-agent-for-ai-agent-development)——一个帮助开发者构建并改进其他 agent 的 agent。*

| 一句话介绍 |  |
| --- | --- |
| 名称 | Cresta |
| 成立时间 | 2017 |
| CEO | Ping Wu |
| 增长 | 融资超过 2.7 亿美元。ARR 超过 1 亿美元。帮助 United Airlines、CVS Health、Marriott 这样的组织交付出色的客户体验 |

为客户体验用例构建企业级 AI agent，需要理解散布在大量客户交互之中的上下文。例如，客户可能会：

- 要求退款，却不说明自己指的是哪一笔购买，
- 在同一条消息里同时反馈账单问题和登录问题，或
- 在退货窗口已经关闭之后申请退款。

要正确应对，agent 可能需要查看客户买了什么、退款政策、他们的账户历史，或者付款状态。

Cresta 以规模化体量处理着这些交互。它的平台支撑着客户体验：AI agent 独自处理对话、为与它们协同工作的人工坐席提供实时指引，并呈现出对话智能，告诉业务该在哪里改进。

构建并维护客户体验 agent，要求组织就运行需求做出关键决策：agent 需要知道什么、必须访问哪些系统，以及它的行为哪里应当柔性、哪里应当确定。Cresta 希望把这种判断力交给更多团队，而不必每个团队都从零开始。

Conductor 就是这件事的结果：一个自然语言 agent 构建器，帮助团队把复杂的业务上下文转化为可用于生产的 agent。用户描述自己想构建什么，Conductor 就把这项工作从一份立足实际的蓝图，一路引导过实现、评估和优化。

Cresta 最初使用 Claude Sonnet 和 Claude Opus 构建了 Conductor 的早期版本，用来帮助内部团队支持客户部署。悬而未决的问题是，Cresta 能否把这套系统变成一款产品，让客户可以直接*在平台内部*用它来构建 agent。

为了承担开放式的开发工作，Conductor 把 Claude Agent SDK 当作一个通用 harness 来使用，收集上下文、使用工具、编写并运行代码，并根据结果做出调整。

“我们在内部把 Claude Code 当作开发工具来使用，因为它在构建 agent 的软件工程层面非常有效，”Cresta Conductor 的工程负责人 Renjie Li 说。“Claude Agent SDK 让我们可以用编程的方式调用同一个 agentic 开发 harness。在 Conductor 里，我们把它与 Cresta 深厚的对话智能、CX 专长、评估和运行时连接起来，为用户呈现出我们希望从第一天就拥有的那种 agent 构建体验。”

Cresta 反馈，在 Cresta 及其合作伙伴的早期用例中，Conductor 把初次部署所需的时间大致削减了一半。

## **帮助构建下一个 agent 的元 agent**

Conductor 是一个自我改进的元 agent，建立在 CX agent 开发的既有最佳实践之上。随着团队用它构建并打磨更多 agent，他们也沉淀下自己被验证过的模式、工作流和专家判断。这会形成一个知识飞轮，让后续的开发更快、更一致。

上线之后，生产中的交互、工作流结果和反馈，会变成下一轮改进的新信号。

Conductor 帮助构建者把从一个 agent 构建项目中学到的东西，转化为一份可复用的记忆产物，沉淀其中的模式、业务规则和评估方法。随后他们可以把它作为一项 skill 分享给团队里的其他人，让别人也能基于同一套经过验证的实践来构建。

### **让重要的决策更容易做**

写下第一版 prompt 只是构建有用 agent 的一部分。更难做的判断之一，是对话哪里该保持柔性、哪里需要显式的业务规则和受控的工具行为。

“你不会想要做得太过确定性，否则你会造出一棵巨大的决策树，试图穷举每一条可能的分支……但有些企业级关键工作流是你必须保证任何时候都能跑通的，尤其是在风险容忍度极低的受监管行业，”Renjie 说。“Conductor 会帮助发现并加固那些确定性的要求以及相应的实现，同时保留改善整体体验所需的柔性。”

Conductor 借助历史对话，帮助团队识别哪些地方应当让人类留在回路之中、哪些地方可以给模型留出自行适应的空间。一旦这些边界确定下来，开发者仍然需要针对所要执行的约束去测试那些确定性部分，并在底层业务规则变化时修订这些测试。

## **Cresta 如何评估 Conductor**

对 Conductor 的衡量标准是它把 agent 构建得有多好。为此，Cresta 让 Conductor 走一遍一组构建任务：

- 构建一个新 agent
- 为一个 agent 编写测试用例
- 修改一个已经存在的 agent
- 执行根因分析

完成任务并不是唯一的门槛。团队还会看结果本身、Conductor 是怎么走到那一步的，以及它途中用到了什么。

| 评估维度 | 它回答的问题 |
| --- | --- |
| 结果 | Conductor 是否产出了所要求的、可用的产物？ |
| 执行路径 | 它是否使用了合适的工具和所需的上下文？ |
| 质量 | 结果与一份精选的参考答案相比如何？ |
| 资源消耗 | 这项任务需要多少时间和模型用量？ |

同一批任务也起到安全网的作用。当新的 Claude 模型发布、或者 Conductor 框架得到更新时，Cresta 会重跑它的评估。它用同样的任务和同样的评分，在任何人正式采纳这项变更之前，识别出哪些改好了、哪些仍然需要打磨。

同一套评估纪律也被内置进 Conductor，让它的用户能够检查自己的 agent 是否按预期表现。Conductor 把构建阶段捕获到的需求和边界情况，转换成其评估模块里的测试。

随后，当政策、接入的系统和对话模式发生变化时，团队可以持续监控那些每次都必须跑通的工作流。这给了他们一条务实的路径：随着业务变化去更新 agent，同时不丢失他们已经加固好的那些工作流的可靠性。

## **在 Claude Agent SDK 上构建 Conductor**

Cresta 把 Conductor 设计成面向 agent 开发的、CX 专用的控制面。它把对话数据、领域专长和开发实践汇聚在一起，然后通过策略、可观测性、验证以及反馈驱动的改进来治理每一次 agent 运行。

Claude Agent SDK 位于 Conductor 之下，充当一个通用的执行 harness。它负责管理收集上下文、调用工具、编写并运行代码这些工作；Conductor 则在它之上叠加 Cresta 的 CX 工作流、工具和领域上下文。

团队对照 Conductor 需要完成的工作来评估这个 SDK：多步骤、上下文量大、并且反复调用工具的任务。他们的审查覆盖了数据隐私、租户架构、组织级的 key 分发、控制项，以及贯穿整个实现的可观测性。

“Anthropic 给了我们一个扎实、通用的 agentic 软件开发底座。这让我们能把工程投入放在 Cresta 创造最持久客户价值的地方，”Cresta 工程副总裁 Xiangru Chen 说。

## **把 Cresta 的工程专长直接交到客户手里**

Conductor 起步于 Cresta 内部，帮助它自己的前线部署团队搞清楚哪些开发任务可以变得可重复、上下文在哪些地方最为关键、构建者途中需要检查些什么。它在那份内部工作上的成功，给了团队把同样的能力带给客户与合作伙伴的信心。

对于那些自定义 agent 的部署速度已经超过工程师手工搭建速度的团队来说，Cresta 的做法是一个有用的参照点：无论是 agent 还是元 agent，初次构建之后的工作往往才是最难的部分。

| 来自 Cresta 团队的最佳实践 |  |
| --- | --- |
| 自用你的产品 | Conductor 先作为内部工具运行，只有当它的产出比得上一位具备深厚 AI 专长的工程师的产出时，它才成为一款产品。 |
| 聚焦你独有的优势 | Cresta 在自己唯一能提供的专长（他们的对话数据和对客户体验的理解）与可以从 Agent SDK 直接拿来即用的东西之间划了一条硬线，并拒绝构建任何踩在错误一侧的东西。 |
| 你的 agent 哪些部分需要是确定性的 | 把绝不能出错的企业级关键工作流加固好，其余部分保留柔性，否则你最终得不到你想要的那种交互式 agentic 体验。 |
| 上生产反而是容易的部分 | 初次构建只占大约 20% 的工作量，另外 80% 是随之而来的测试、优化和持续改进，所以要围绕迭代回路而不是上线去设计你的工具。 |
