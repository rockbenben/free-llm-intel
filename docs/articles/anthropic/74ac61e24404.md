## 代码不再是瓶颈

各组织已经开始用 AI 以一年前难以想象的速度编写代码，但围绕代码的流程并没有以同样的节奏改变。

许多工程团队仍然沿用同样的审批关卡、评审、交接和策略，把使用 [Claude Code](https://claude.com/product/claude-code) 这类 agentic 编码方案所带来的生产力增益又拖了回去。

软件开发生命周期（SDLC）是把软件从想法带到生产的流程。大多数组织跑的都是同样六个阶段的某个版本，覆盖软件的规划、设计、构建、测试、部署和维护。传统上，每个阶段都是由不同角色负责的独立环节：产品经理编写需求，技术架构师把需求变成设计，工程师按设计构建，受监管企业的 QA 团队做验证，发布团队负责上线，运维团队监控正在运行的东西。工作通过文档、工单和签核在各环节之间流转。

传统的软件开发生命周期（SDLC）流程繁重，目的是在每一步都保证可追责与控制。但传统 SDLC 是在「编写和实现代码是最耗时、最昂贵的环节」那个年代为追求效率最大化而设计的，而这一点如今已不再成立。PRD、估算仪式、产品安全评审，都是为了在可能长达数周、数月甚至数个季度的开发工作中强制对齐而存在的。

传统 SDLC 的控制措施同样假设每一步都由人来执行。而创造出最多价值的组织，已经围绕 agentic AI 现在能做的事重构了自己的流程，同时确保人始终留在环内。在本指南中，我们会梳理我们 Applied AI 团队的多项最佳实践——它们源自与我们的客户合作时积累的经验，做法是在 SDLC 的每个阶段内部整合 Claude，以加速开发并让流程跑得更快。

当代码不再是瓶颈、构建阶段跑得比传统 SDLC 所能容许的速度更快时，三件事会成立：

- 瓶颈移动到构建阶段左右两侧的步骤上。这主要是 Plan、review/test 和 Deploy，它们仍然以人的速度在跑。
- 控制措施开始与现实脱节，变得难以为继。逐行人工评审在代码由人手写下时是合理的，但一旦大部分 diff 由 agent 写出，它就跟不上了。
- 治理成本上升，因为例外情况仍然要经由每周或每月才开一次的会议和委员会来走流程。

构建不再是约束——围绕它的那些人速环节才是。构建被压缩到几小时，而人速阶段的长度保持不变。

以安全瓶颈为例。安全团队的规模是按人的产出配置的，所以当 agent 把代码产出成倍放大时，要么评审队列堆积，要么代码在未充分评审的情况下发布。受监管的组织两种结果都不能接受，因此它的安全与策略检查必须跟得上 agent 的节奏。

为了更好地兑现 agentic AI 的生产力增益并保障其安全，传统的 SDLC 需要经历一场与实现阶段已经发生的变革同等程度的改造。

## 什么是 AI 原生 SDLC？

AI 原生 SDLC 是一种重新构想的流程，它把旧的控制目标与新的执行手段结合在一起。流程不再是线性的，而变成一个环，AI 嵌入在每一个节点上。AI 原生 SDLC 推动自动化的交接与后续打法的触发，有助于解决传统 SDLC 各阶段之间那种手工、笨拙的交接问题。

你也会听到这种转变被称为 agentic SDLC、AI SDLC，或者干脆叫 agentic 软件开发——叫法不同，但描述的是同一件事。

### AI 原生 SDLC 六个阶段上的转变

下表突出的是由 Claude 支撑的、传统 SDLC 与 AI 原生 SDLC 这条光谱的两端。大多数组织位于这两列之间的某个位置。

| 阶段 | 传统 SDLC | AI 原生 SDLC |
| --- | --- | --- |
| Plan | 需求由委员会收集，经过工作坊和签核提炼，再手工写成文档 | Claude 直接从源头综合出痛点，并把它记录在 `intent.md` 里，既可被人读，也可被机器执行 |
| Design | 规格由分析师撰写，由设计师再解读一遍 | 需求与设计压缩进一次与 agent 一起完成的工作会话，由编码成 skills 的标准来引导，并版本化地存在 git 里 |
| Build | 测试和代码都是手写的，文档要在主要开发完成之后才补写 | 测试和代码由 AI 生成，机构知识以带版本、机器可读的 `CLAUDE.md` 文件和 skills 的形式维护 |
| Test | QA 卡在阶段边界上 | continuous evals 贯穿实现过程 |
| Deploy | 人逐行评审每一行代码，治理在评审周期里进行，且常常不一致 | 分层的 agentic 评审，把人工评审留给受监管的和关键的代码。治理在 AI 行动时强制执行，用 hooks 作为审批关卡 |
| Maintain | 人盯着生产环境找 bug | agent 监控在线部署。任何被突破的控制区间都会被诊断，并作为新的 `intent.md` 写回这个环 |

贯穿右边那一列的主线是「已提交的产出物」。每个阶段都以把一份产出物写入版本控制作为结束（包括 `intent.md`、`spec.md`、`plan.md`、diff 及其测试、带着评审发现的 PR，以及事故记录），下一个阶段则以读取它作为开始。在早期阶段，.md 文件是主要的产出物，因为产品负责人和 agent 都能读同一个文件、并在其上行动。从 Build 往后，产出物就是代码及其记录。提交链同时也是审计轨迹：谁提出了什么要求，agent 产出了什么，谁批准了它。

凡是需要判断的决策，责任仍然在人身上。在 agentic SDLC 的世界里，人的注意力会随着必须评审的产出物一起移动。

每个阶段都提交一份下一阶段能读到的产出物。intent、spec、plan、diff 和评审发现合在一起，就是审计轨迹。

## 打法（Plays）

这些打法是本行动手册的核心，被分到六个非线性阶段（Plan、Design、Build、Test、Deploy、Maintain）中，合起来覆盖完整的生命周期。

每条打法都包含：

- 改变了什么；
- 如何上手；
- 具体的实施步骤；
- 治理考量；以及
- 你如何衡量它是否奏效。

这些步骤是模块化的，组织可以根据自己的独特需求，选择在不同时间优先改造不同的阶段。每条打法都在「Prerequisites（前置条件）」下列出它的依赖，依赖图对此有更进一步的说明。

一个阶段以提交一份产出物结束，而这次提交又启动下一个阶段。一份被接受的 `intent.md` 触发需求与设计这一轮，一个被批准的 `spec.md` 触发 plan mode，一次合并的 PR 触发流水线，而生产环境里一次被突破的控制区间则写下下一份 `intent.md`，如此循环往复。

一开始，你手工提示每一个步骤；最终形态是一个环，其中每一份被接受的产出物都会点燃下一个关卡。人的注意力集中在关卡上，评审 agent 标记出来的东西，而不是从零开始启动每个阶段。

打法按阶段列出；箭头给出的是采纳它们的顺序，这两者并不相同。从任意一条 clay 打法开始——没有任何箭头指向它，所以它不需要先具备什么。对于其他任何打法，指向它的箭头就是在它之前要先采纳的打法。

01

## Plan（规划）

想法不必再等着别人把它们写下来。意图只被记录一次，用的是提出者自己的话，作为一份带版本控制的产出物，下一个阶段可以直接在它上面行动。

### 记录为 intent.md

启动软件开发流程的 `intent.md`，可以从不同路径进来。一个人有了想法，有人提了一张工单，或者一起事故由告警暴露出来（见 Stage 6: Maintenance）。

当一个人有了想法，他与 Claude 一起头脑风暴，产出一份 markdown 的 proto-spec。在传统 SDLC 里，同一个人接着得说服产品团队的某位成员，和他一起把这个想法写下来、或者代他写下来。

Claude 生成的 proto-spec 人可读、有版本控制，并且能立刻被下一个阶段消费。这份 proto-spec 就存为 `intent.md`。

无论意图来自事件触发还是来自 agent，步骤都一样：在提交之前，由产品负责人审阅并修正 agent 写出的 `intent.md`。

传统方式

一个想法要经过待办条目、用户故事、故事点和细化会议，别人才有可能对它采取行动。每交接一次，归属权就转移一次，所以最终交到工程团队手里的东西，离提出者原本的意思已经隔了好几层。

AI 原生

提出者与 Claude 一起头脑风暴，并把结果写成

intent.md

，一份用提出者自己的语言表述的 proto-spec。这份产出物包含想要什么、为什么、以及在什么约束之下。重复性的流程通过 skills 编码。

如何上手

前置条件

无。

基础设施

非工程师人员的 Claude 访问权限（claude.ai 或

Cowork

）；一份约定好的

intent.md

模板；一个由产品负责人看管的、用于存放 intent 的共享版本控制空间。对单一产品来说，最简单的存放处就是产品仓库里的一个

intent/

目录。这样配置能让产出物链紧挨着由它派生出的代码。只有当 intent 横跨许多仓库时，专门开一个 intent 仓库才值得那点额外开销；而在 monorepo 里，它就是一个目录。Stage 3: Build 的侧栏讲了这个存放处与已经在持有记录的 Jira 或需求工具之间是什么关系。

搭建这件事对平台或工程团队来说是一次性的任务。需要有一位技术团队成员把存放 intent 的空间建起来，并决定谁可以向它写入，因为贡献者会来自组织的各个部门。

仓库建好之后，没有 git 经验的贡献者并不需要直接使用 git。取而代之的是连到版本控制系统（例如 GitHub）的连接器，它让 Claude 代他们在 claude.ai 或 Cowork 里提交 markdown 文件。

#### 如何执行它

- 提出者用自己的话向 Claude 描述问题。提出者可以描述自己今天做不到什么、这个想法影响到谁、更好的状态长什么样、以及什么不在范围内。不需要正式的语言。
- 头脑风暴，直到想法变得具体。Claude 会问分析师该问的那些问题：范围、用户、约束，以及成功是什么样子。
- 让 Claude 用组织的模板把结果写成 `intent.md`。模板能由技术团队成员配置成一个 skill、并经负责人签核，内容覆盖问题、建议的结果、受影响的用户与系统、约束，以及尚未解决的问题。
- 提出者纠正 Claude 理解错的地方。
- 把 `intent.md` 提交到共享空间。作者和时间戳一起进入记录，产品负责人从那里接手这个想法。

```
# Intent: claims status self-service
Author: J. Ortiz (claims operations). Status: draft.

## Problem
Customers phone the contact center to ask where their claim is.
Handlers spend roughly a third of call time on status-only queries.

## Proposed outcome
Customers see claim status, next step and expected date in the portal.

## Affected users and systems
Claims handlers, portal team, claims-core API.

## Constraints
No new PII in the portal session. Existing authentication only.

## Open questions
Do third-party loss adjusters need access too?
```

#### 治理考量

证据就是提交了的 `intent.md`，它列出了作者、时间戳和完整的修订历史，记录在 intent 空间的 git 历史里。由产品负责人批准；而这个把 intent 送进 Stage 2: Design 的接受或拒绝决定，则记录为那次合并、或那次关闭时的评审。

如何衡量

先导指标

从第一次对话到有一份

intent.md

被提交所花的时间，从 intent 空间的 git 历史里读取，那里记录了作者和时间戳。预期是从一个持续数周的需求挖掘与细化周期降到几小时。

滞后指标

存活率，也就是产品负责人接受进 Stage 2: Design 而不是关闭掉的

intent.md

文件占比。接受或拒绝的决定记录为该产出物的合并或那次已关闭的评审。此外还有：对

intent.md

做出的改动次数，即针对同一个变更、发生在第一份

spec.md

提交之后的那些改动。

02

## Design（设计）

需求与设计坍缩成一次会话。策略在撰写 spec 的同时就被应用，而不是几周后在评审里才被发现。

### 需求与设计

产品负责人批准之后，Claude 拿过这份被接受的 `intent.md`，产出一份需求与设计规格。这一过程由组织针对品牌、安全、合规和 UX 写成的 [skills](https://code.claude.com/docs/en/skills) 来引导。

产品负责人评审那份 spec，但并不撰写它。这个流程的目标是产出一份工程团队可以据此规划的 spec，并把令人担忧的地方标记出来。

前端工作是最清楚的例子。一旦 `intent.md` 被接受，产品负责人就在 [Claude Design](https://claude.com/product/design)（beta）里从这份 `intent.md` 出发把设计做成 mock，对 mock 迭代，然后导出到 Claude Code 去构建。

传统方式

需求与设计是由不同团队执行的两个独立阶段。分析师把想法形式化为需求，设计师再把这些需求解读回设计。这种分隔是为了可追责，但它又慢又有信息损失。

AI 原生

两个阶段发生在同一次提示出来的会话里。Claude 拿过

intent.md

，产出一份需求与设计规格，受组织 skills 的约束，并标记出令人担忧之处。

如何上手

前置条件

写一份

intent.md

文件，并把品牌、安全、合规和 UX 策略写成 skills。

基础设施

一位有 Claude 访问权限的产品负责人。不需要工程技能。

#### 如何执行它

- 产品负责人开启一个会话，组织的 skills 在该会话中可用，并附上 `intent.md`。
- 产品负责人的 prompt 指向 `intent.md`，点明约束，并要求标出令人担忧之处。先手工跑，然后把它固化为组织级的斜杠命令。再往后，把 intent 空间里 `intent.md` 被接受这件事作为触发器：一个在合并时触发的非交互任务，加载组织的 skills 跑这一轮，并把 `spec.md` 作为一个 pull request 提交（Stage 5: Deploy 里的 CI/CD 打法讲这套管道怎么搭）。到那时，产品负责人第一次介入就是评审。
- 同一位产品负责人对照原来的想法来评审这份 spec。spec 是否解决了陈述的问题？`intent.md` 里未解决的问题是被回答了，还是被继续往下带？
- 先处理标记出来的担忧点，它们正是分析师会向上升级的那些点。在工程看到这份 spec 之前，产品负责人与每个担忧点对应的策略负责人一起把它解决掉。
- 把 `spec.md` 与 `intent.md` 一起提交。这两个文件构成的对儿记录了要的是什么、定下来的是什么。
- 由产品负责人决定 spec 与 intent 是否推进到构建；凡是组织归类为更高风险的东西，会咨询一位技术负责人。这个判断始终由一位人类同事做出，而接受这份 spec 就是启动 Stage 3: Build 里 plan mode 打法的动作。

#### 具体长什么样（the prompt）

```
Read the attached intent.md and produce a requirements and design spec for integrating it into our existing codebase. Apply the skills available to you so the plan conforms to our brand guidelines, security policies and UX standards. Document the spec fully as spec.md, ready to hand to the engineering team. Describe clearly any areas of concern, especially where you cannot satisfy contradicting policies.
```

#### 治理考量

策略不再等到几周后的评审里才被发现，而是在撰写 spec 的同时就被读取和应用。组织的 skills 作为对 spec 的约束被施加。spec、产出它的 prompt，以及当时生效的 skill 版本，全都记录在版本控制里。产品负责人对 spec 签核，并把标记出的担忧点转给具名的策略负责人。

如何衡量

先导指标

同一个变更的

intent.md

提交与

spec.md

提交之间的耗时（两个 git 时间戳），与过去「需求加设计」那个周期做比较。

滞后指标

构建开始之后的需求返工。统计

spec.md

的提交中，日期晚于同一个变更第一份

plan.md

提交的那些。git log 可以直接给出这个数。

03

## Build（构建）

没有一份被批准的 plan，什么都不实现。机构知识变成 agent 会读的文件，护栏则以代码而非习惯的方式运行。

### 以 Claude Code plan mode 作为默认起点

工程师在 [plan mode](https://code.claude.com/docs/en/permission-modes) 下开启 Claude Code 会话，把 Stage 2: Design 产出的、已批准的 `spec.md` 交给 Claude，让它来访谈自己，并反复迭代这份 plan，直到工程师满意为止。

传统方式

工程师读完设计就开始写代码。这次改动打算怎么做、动到哪些文件、写哪些测试，只留在工程师的脑子里，充其量写在一句工单评论里。别人没法评审它。评审者看到的第一个东西就是写完的 diff，到那时候返工已经很慢。

AI 原生

工作从一份成文的 plan 开始，它由 Claude 在 plan mode 下产出——在这个模式下它能读代码库但不改任何东西。工程师在写下代码之前修正这份 plan，而被批准的版本作为

plan.md

提交，供后续阶段对照检查。

如何上手

前置条件

intent 产出物（

intent.md

或

spec.md

），如果有；而

CLAUDE.md

文件也会有帮助。

基础设施

有仓库访问权限的 Claude Code。

#### 如何执行它

- 工程师在 plan mode 下与 Claude 开启会话。
- 工程师把 `intent.md` 和 `spec.md` 给 Claude，要求一份实现计划，点名要改的文件、工作的顺序，以及证明它成立的测试。
- 追问这份 plan：这次改动可能弄坏什么、哪一步风险最大、Claude 没有采用的其他选项是什么。
- 反复迭代，直到一位从没看过这段对话的工程师也能只凭这份 plan 完成这次改动。
- 把批准了的 plan 作为 `plan.md` 提交。plan 进入审计轨迹，而 PR 评审打法（Stage 5: Deploy）会拿最终的 diff 与它对照。
- 接受这份 plan，让 Claude 去实现。有了扎实的 plan，实现往往一遍就过。
- 当实现偏离了 plan，在同一次提交里更新 `plan.md`。可以考虑用一个 hook 来强制两者保持同步。

#### 具体长什么样（plan.md）

```
# Plan: claims status self-service (from intent.md 2026-06-02)

## Files that change
portal/src/claims/StatusPanel.tsx (new), claims-api/routes/status.py,
claims-api/tests/test_status.py

## Order of work
1. Add the status endpoint behind existing auth.
2. Panel against the endpoint.
3. Wire into the portal nav.

## Risks
The claims-core API rate-limits at 50 rps; the panel must cache.

## Proof
test_status.py covers the four claim states; screenshot matches the
approved mock.
```

#### 治理考量

设计评审发生在任何代码生成之前，那时改方向还只是改一份文档的事。plan mode 自身就在强制这一点：在工程师接受 plan 之前，Claude 不能编辑文件。plan 及其修订都被记录下来，连同是谁批准的。常规改动由工程师自己批准，凡是组织归为更高风险的，交给技术负责人或架构师。

如何衡量

先导指标

一次实现就合并成功的变更占比，以及从 plan 批准到 PR 合并的耗时；所需数据都在 PR 的元数据里。

滞后指标

每个变更的返工轮次，同样取自 PR 元数据；以及合并的 diff 与提交了的

plan.md

仍然吻合的频率。

### Claude Code 的 auto mode

Claude Code 也可以跑在 auto mode 下：工程师批准 plan，在 plan 被反复迭代到满意之后，Claude 应用每一处改动时不再逐条编辑提示。随着后面几条打法的护栏成熟（调校过的 `CLAUDE.md`、把策略编码成的 skills、拦下不安全动作的 hooks，以及一套 Claude 能跑的测试），auto-accept 就成了常规工作的默认方式：一份紧凑的 `spec.md`、小的影响面，以及测试已经覆盖到的代码。

重心于是从「用户看着 agent 做编辑、逐条评审它的动作」，转移到较长的自主会话结束之后对产出物的评审。auto-accept 模式配合 worktrees，还能在个人和团队两个层面进一步放大并行度，它是 Stage 6: Maintenance 所描述的自主运行 SDLC、把闭环合上的基础。

侧栏

### 遗留系统与事实来源

适用于本流程产出的每一份产出物。

现有的 SDLC 流程很可能已经在跟踪产出物了，只不过不是用 markdown 文件。工作项可能在 Jira 里，需求在一个自带监管可追溯性的工具里，设计在 Figma 里，变更审批在 change board 那里。这些系统很难被取代，因为审计方和监管方已经认可它们，别的团队也依赖它们，所以 AI 原生 SDLC 必须围绕既有的东西来安排。

在向 AI 原生 SDLC 迁移时，对本流程产出的每一份产出物，都要指定一个系统作为事实来源（source of truth），其余地方只放副本或指向原件的链接。下面几种配置都能做到单一事实来源，具体选哪种可以按产出物分别决定：

仓库作为事实来源。

markdown 产出物是权威记录，遗留系统引用提交里的文件。对以工程为主导的组织来说，这可能是最干净的配置之一，因为所有记录都活在一个工具里、共用一个时间戳权威。

遗留系统作为事实来源。

Jira、ServiceNow 或需求工具持有权威记录，markdown 产出物是工作副本。Claude 在会话开始时读取记录，并在产出 spec 或 plan 的同一次会话里，通过一个

MCP

连接器把结果写回去。

以互链作为最低标准。

所有产出物都标注记录 ID，所有遗留记录都包含 markdown 文件的提交 SHA。在迁移到 AI 原生 SDLC 时，互链是一个好的起点，代价是承认存在两个事实来源。

遗留体系与 markdown 优先的体系可以共存，只要两者之间有链接，或者明确宣告其中一个为事实来源。

### CLAUDE.md

[`CLAUDE.md`](https://code.claude.com/docs/en/memory) 给 Claude 提供一位新人需要的上下文，涵盖约定、命令、架构，以及团队最常看到的那些错误。过去装在人们脑子里、写在 wiki 上的知识，变成一份 agent 每次会话开始都会读的文件，由整个团队共同维护，每当出一次错就迭代一次。

如何上手

前置条件

无。

基础设施

一个仓库、装好的 Claude Code，和一位很熟悉这个代码库的工程师。

#### 如何执行它

- 在仓库里运行 `/init`。Claude 根据它扫到的内容生成一份起始的 `CLAUDE.md`。
- 把生成的文件删减到一位新人在第一天真正需要的东西。保留 build、test 和 lint 命令，真正重要的约定，以及 Claude 一再弄错的事情。
- 把 `CLAUDE.md` 提交进仓库根目录的 git，让整个团队共享同一个版本，改动像评审代码一样被评审。
- 这里有一条可操作的规则：当 Claude 第二次犯同一个错，纠正就写进 `CLAUDE.md`。
- 把它控制在一页以内，因为 Claude 在会话开始时会把它全部读进来，任何过时的内容都是在白白占用上下文。

#### 具体长什么样（CLAUDE.md）

```
# Payments service

## Commands
- Build: make build
- Test: make test (unit), make itest (integration, needs docker)
- Lint: make lint (runs in CI; fix before pushing)

## Conventions
- Java 21, Spring Boot 3. No new Lombok.
- Money is always BigDecimal, never double.
- Every endpoint needs an integration test in src/itest.

## Architecture
- api/ holds REST controllers, core/ holds domain logic,
  adapters/ talks to external systems.
- Kafka events are defined in schemas/; never edit generated classes.

## Things Claude gets wrong
- Do not bump dependency versions; the platform team owns them.
- The legacy v1/ package is frozen; changes go in v2/.
```

#### 治理考量

`CLAUDE.md` 有版本控制，所以 agent 据以工作的指令是可评审、可审计的。团队约定通过这个文件来落实，对它的改动记录在 git 历史里，由 code owner 在 PR 评审中批准。

如何衡量

先导指标

Claude 多大比例地重复了本该由

CLAUDE.md

拦住的错误。对

CLAUDE.md

所做的纠正或改动应当在 git 历史里可追踪。

滞后指标

从 PR 历史看，一位团队新成员第一次有 PR 被合并所花的时间。

### skills 作为机构知识

skills 是组织把机构知识变成可执行之物的方式。这些指令是明确的、有版本控制的、被广泛应用的，并在策略变化时集中更新。经验法则是：必须被一致应用的机构知识就写成 skill；属于 `CLAUDE.md` 或 prompt 的组成部分就不要写成 skill。

如何上手

前置条件

没有强制要求。有一份

CLAUDE.md

会有帮助，因为它把 agent 的工作知识留在仓库里，但 skill 并不依赖它。

基础设施

一条有具名负责人、且有成文事实来源的策略。

#### 如何执行它

- 挑一件如今执行得不一致的知识。它可以是一条安全标准、一个 API 设计约定，或一条品牌规则。
- 把它写成 skill：一个包含 `SKILL.md` 的文件夹，其 frontmatter 说明它在什么时候触发，正文说明该做什么。由一位工程师依据策略负责人的成文事实来源来写，让 Claude 帮忙。
- 把 skill 放进仓库的 `.claude/skills/<name>/`，让它随代码一起分发；或者通过 [plugin](https://code.claude.com/docs/en/plugin-marketplaces) 在整个组织范围内分发。
- 测试这个 skill 会不会触发。用不同的说法让 Claude 做相关的任务，确认每次都加载了它。
- 策略变化时，改这个 skill，并让策略负责人签核这次改动。
- 工程师在下一次会话里自动拿到新版本。

#### 具体长什么样（.claude/skills/secure-api-review/SKILL.md）

```
---
name: secure-api-review
description: Apply the API security standard. Use whenever creating or
  modifying an external-facing endpoint, reviewing API code, or
  generating an OpenAPI spec.
---
# Secure API review

When you create or change an API endpoint:
1. Authentication: every endpoint requires the gateway JWT;
   no anonymous routes outside /health.
2. Input validation: validate request bodies against the OpenAPI
   schema and reject unknown fields.
3. Audit: every state-changing endpoint emits an audit event with
   actor, action, entity and timestamp.
4. Data classification: fields tagged pii in the schema must never
   appear in logs or error messages.

Run scripts/check-endpoints.sh and include its output in your summary.
```

#### 治理考量

skill 是一种控制，但只是建议性的。它让 Claude 很可能在写代码的同时应用策略，但没有任何东西强制一次会话遵守它。一条必须始终成立的策略，需要在 skill 背后有确定性的东西兜着，比如拦下该动作的 hook，或者在 PR 上重新核查该策略的一轮评审。skill 让违规变得罕见，hook 则让违规几乎不可能发生。skill 的调用会记录在会话轨迹里，策略负责人像评审代码一样评审 skill 的改动。

如何衡量

先导指标

从策略负责人批准一项策略变更，到更新后的 skill 合并所花的时间，取自该 skill 文件夹上的 PR。

滞后指标

PR 评审中引用该策略的发现项。一旦 skill 在写代码的过程中就把策略落地，这类发现项应当趋近于零。如果没有趋近于零，那要么是 skill 没有触发，要么是它的文本已经偏离了正式策略。

### hooks 作为构建期护栏

skill 是建议性的控制，而 [hook](https://code.claude.com/docs/en/hooks) 是它背后的确定性层。Claude 的大部分动作是实现过程中的文件编辑和 shell 命令，所以构建阶段是 hooks 最可能频繁触发的地方。

构建阶段的 hooks 可以：

- 拦住对受保护路径的编辑，例如生成的类或一个冻结的 package；
- 在文件编辑之后运行 formatter 和 linter，让偏移从不累积；
- 把凭证挡在 diff 之外。

凡是策略必须毫无例外成立的 skill，都要有东西在后面兜住。hook 会在每个与它匹配的动作上运行，所以构建阶段的 hook 要快，作用域限定在发生改动的那个文件上。更重的检查，比如完整测试套件，应当放在提交或 PR 那一层。

需要向人请求批准的 hook，属于 Stage 5: Deploy 里的那些关卡，因为在构建过程中弹一个审批提示，会把人重新放回所有并行会话的关键路径上。

### 并行会话与 subagents

一位工程师可以同时驱动好几条工作流。

一个并行会话就是另一个完整的 Claude Code 实例，在它自己的 [git worktree](https://code.claude.com/docs/en/worktrees) 里做另一件任务。每个独立会话都不知道其他会话的存在，它们唯一共享的是操控它们的那位工程师。

一个 [subagent](https://code.claude.com/docs/en/sub-agents) 运行在单次会话之内，是一个有明确作用域的助手，有自己的上下文窗口和工具限制，适合在多个任务里重复出现的工作，例如验证应用是否按预期运行。

并行会话提高了工程师可以同时推进的任务数量，而 subagents 让每个会话专注于自己的任务。工程师的工作是驾驭和评审它们全部。

传统方式

一位工程师一次做一件任务，一天或一周里有相当大的一部分时间花在构建、测试和等评审上。等待的时候在任务之间切换是可行的，但上下文切换累人到很少有人真的愿意这么做。

AI 原生

一位工程师同时跑好几个 Claude 会话，每个都在自己的 worktree 里做自己的任务。重复出现的工作变成带着自己上下文和工具限制的 subagents。工程师的工作转向编排，并最终转向搭建和监控这些循环。

如何上手

前置条件

那份

CLAUDE.md

，因为所有会话都会读这个文件。反馈回路（Stage 4: Test）在这里也有帮助，因为当一次会话能自行验证自己的工作时，需要工程师监督的地方就更少了。

基础设施

一个 git 仓库；隔离来自 worktrees，还需要调校权限设置，让会话不必为了组织认为安全的命令而卡在审批提示上。

#### 如何执行它

- 工程师把工作拆成触及不同文件的任务，用 plan mode 打法（Stage 3: Build）产出的 plan 来看清哪些工作是相互独立的。共享文件的任务在同一个会话里一件接一件地做。
- 每件并行任务有自己的 worktree，例如一个终端里 `claude --worktree feature-auth`，另一个终端里 `claude --worktree fix-rate-limit`。worktree 就是一个在自己分支上的独立 checkout，它能避免会话之间在文件上相互冲撞。
- 两到三个会话是合理的起点。实际上限是一个人能认真评审多少条并行工作流，所以只在评审跟得上的时候增加会话。
- 把重复出现的工作变成 subagents：它们定义在 `.claude/agents/` 下的 markdown 文件里，每个都有自己的名字、一段说明何时使用的描述，以及它可以触及的工具。例子包括：在主 agent 完成后剥掉多余复杂度的 code simplifier；运行应用并检查行为的 verifier；探查代码库并回报、但不把主上下文淹掉的 researcher。把这些定义提交进 git，让整个团队共享它们。

#### 具体长什么样（.claude/agents/verifier.md）

```
---
name: verifier
description: Runs the app and checks the change works before the session
  reports done
tools: Bash, Read
---
Start the app with make run. Exercise the changed behavior and the two
nearest neighboring flows. Report what you ran, what you saw, and any
behavior that does not match plan.md. Do not fix anything; report only.
```

#### 治理考量

会话更多意味着产出更多，所以控制必须来自仓库里的配置。那里的 hooks 和权限设置适用于所有会话，而每个会话做了什么都会被记录，并归属到运行它的工程师名下。

如何衡量

先导指标

在保证评审质量的前提下，每位工程师的并发会话数，从 OpenTelemetry 导出数据统计；以及一天之中用于驾驭而非等待的时间占比。

滞后指标

每位工程师每周合并的变更数，并与从 PR 历史得出的返工率放在一起看。

## Test（测试）

每个会话都在被人看到之前先检查自己的工作，而那份驱动 agent 的配置也像它写出的代码一样做回归测试。

### 给 Claude 一条反馈回路

始终给 Claude 一个能验证自己工作的方式，无论是测试、一次构建，还是截图 diff。一次会话在工程师看到错误之前就自己检查工作、自己修掉自己的错误。

不要把反馈回路和 verifier subagent（Stage 3: Build）混为一谈。反馈回路贯穿整个任务，工作做多少轮它就跑多少轮。而 verifier subagent 是把最后一次检查打包起来的其中一种方式：当会话认为工作已完成时，它在一个全新的上下文窗口里跑一次。这样一来，结论就不会被那些产生这段代码的假设所染指。

传统方式

「代码能跑」这个信号来得很晚。CI 是几分钟后，测试人员是几天后，生产环境是几周后。当代码由 agent 产出时，信号来得晚就意味着必须有一个人去检查它全部的产出，而那个人就成了瓶颈。

AI 原生

会话在被人看到之前就被给了一个检查自己工作的方法。跑测试、跑构建、截屏。Claude 反复迭代直到检查通过，所以交到工程师手上的东西已经通过了检查。把这条回路搭起来是运行该会话的工程师的事，下面的步骤就是写给他们看的。

如何上手

前置条件

无。

基础设施

一套测试套件和一个构建，各自一条命令就能在本地跑起来。对于 UI 工作，让 Claude 能看到结果的方式至关重要——可以是通过 MCP 接进来的浏览器工具，也可以是截图工具。

#### 如何执行它

- 如果今天检查一次工作需要一连串命令外加一些环境知识，就把它包进一个单一 target，例如 "make test" 或 "npm test"，失败时以非零退出码退出。
- 在 `CLAUDE.md` 的 Commands 一节里，逐条列出每个命令，并附上一个健康输出的样例。
- 给出一个可量化的目标，让 Claude 不用问你就能检查工作，例如："test_status.py 里的所有测试都通过"、"截图与附上的 mock 一致"，或者"endpoint 返回 200 并带上新的字段"。
- 修 bug 时先写那个会失败的测试。让 Claude 把这个 bug 复现成一个测试，运行它，并确认它确实因为你预期的原因失败。把那个测试提交。之后才让 Claude 在不修改这个测试的前提下让它通过，最后一步里的 test-file hook 会强制这个限制。一个在修复之前就存在、且 agent 无法改写的测试，就是 bug 已除的证据。
- UI 工作要用视觉检查把回路闭合。给 Claude 一个浏览器或截图工具，把 mock 给它，让它迭代：实现、截图、比对、调整。两三轮是正常的，而且结果每轮都应当更好。
- 把验证变成「完成」定义的一部分。这条指令写在 `CLAUDE.md` 里：在报告任务完成之前先跑测试，并展示输出。
- 最后，回路本身需要被保护，因为一个在修代码的 agent 绝不能有能力削弱对它正在修的代码的检查。一个在修复任务期间拦住对测试文件编辑的 hook 就能做到这一点。替代方案是在评审时检查 diff，拒绝任何动到测试的改动。

#### 具体长什么样（CLAUDE.md 的验证区块）

```
## Verifying your work

- Build: make build (must finish with "Build succeeded")
- Test: make test (all green; never skip or delete a failing test)
- Lint: make lint (zero warnings)

Run all three before reporting any task complete, and paste the output.
If a test fails, fix the code, not the test.
```

治理考量

被强制的是什么

任务被报告完成之前必须先验证；以及禁止 agent 在修复过程中编辑测试文件。在组织要求有保证的地方，这两条都以 hooks 实现。

证据是什么

"make test" 的原始输出、构建日志，或者 Claude 跑出来并贴上的截图 diff——所以证据来自工具链本身。

记录在哪里

会话转录里（OpenTelemetry 导出会把它转发到组织的可观测性栈），以及 PR 的 check run 里——评审者和日后任何审计方都能看到它。

谁来批准

评审该 PR 的 code owner。因为机械性的证据已经附在上面，他可以把注意力集中在意图和风险上。

如何衡量

先导指标

由 agent 写出的变更首次就跑通 CI 的成功率，CI 系统本身就支持这个指标。

滞后指标

每个 PR 的评审时长（取自 PR 元数据）——当测试能抓到过去由评审者抓到的东西之后，这个时间应当下降；以及来自事故跟踪系统的变更失败率。

### CI 中的 continuous evals

evals 是阶段关卡式 QA 在 AI 原生世界的对应物。落到实操上，它意味着一套只要 agent 的配置发生变化就会运行的套件。当换上一个新模型、或者重写了一个 prompt，eval 套件会告诉你 agent 是否仍以同样的标准完成工作。

evals 应当被看作一套活的套件。随着模型进步，曾经有区分度的用例不再具备区分度，而必须补充新的用例——它们来自持续的监控。

视具体用例，有些团队可能更愿意按固定节奏离线跑这些 evals，而不是每次改动都跑。下面的步骤是针对持续评估的。

如何上手

前置条件

那份

CLAUDE.md

，以及反馈回路（Stage 4: Test）。

基础设施

能非交互地运行 Claude Code 的 CI，以及一个有预算额度、用于跑 eval 的 API key。

#### 如何执行它

- 平台工程师从近期工作中收集 20 到 50 个真实任务，连同它们的预期/已接受的结果。
- 把每个任务写成一个 eval，也就是 prompt 加上定义「可接受」的那些检查（测试通过、lint 干净、行为未变、策略被遵守）。
- 这个套件在 CI 里以非交互方式按计划运行，并且在 `CLAUDE.md`、skills 或 hooks 有任何变化时运行——因为那份配置在驱动 agent，理应享受代码所享有的回归测试。
- 用结果来把关配置变更。一项导致通过率下降的 skill 改动，在合并之前要先经过评审。
- 每一起生产事故都要有一条 eval，由负责该事故的团队撰写，并作为回归测试留在套件里。

#### 具体长什么样（.github/workflows/agent-evals.yml）

```
name: Agent evals
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']
  schedule:
    - cron: '0 2 * * *'
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g @anthropic-ai/claude-code
      - name: Run eval suite
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          for eval in evals/*.json; do
            claude -p "$(jq -r '.prompt' $eval)" \
              --allowedTools "Read,Edit,Bash(make test)" \
              --output-format json > result.json
            ./evals/check.sh "$eval" result.json
          done
```

#### 治理考量

evals 让 QA 有了一道能跟上 agent 产出速度的关卡。通过率阈值作为合并检查强制执行；每次运行都被记录，以便随时间比对结果；而由拥有该配置变更的团队来批准它。

如何衡量

先导指标

随时间变化的 eval 通过率（套件每次运行都会报告），以及一起生产事故变成一条永久 eval 需要多久。

滞后指标

在 CI 里拦住的回归，与在生产环境发现的回归（取自事故跟踪系统）做对比。

05

## Deploy（部署）

评审双向进行，治理在 agent 行动的同时被强制执行。agent 做生产关卡之前的一切，绝不越过它。

### AI 进入 PR 评审回路

Claude 既给出评审也接受评审。它按组织的策略评审进来的 PR，也处理别人在它自己 PR 上留下的评审意见。这让工程师可以把 PR 评审的精力放在行为上——归结起来就是判断意图与风险。

传统方式

评审产能是按人的产出来规划的。一个 PR 要等评审者把它全部读完；评审质量随评审者的负载起伏；而作者一路追着评审，积压还在增长。

AI 原生

所有 PR 都得到同样一组评审轮次，发现项按严重程度排序。人的注意力上移一层，去看这次改动是否做到了 plan 想要的东西，以及风险是否可以接受。

如何上手

前置条件

来自 Stage 3: Build 的、更新过的

CLAUDE.md

文件；如果评审轮次要执行成文的策略，就需要 skills；已定义的 subagents。

基础设施

装好 Claude 集成的仓库。二选一：由管理员开启的托管版

Code Review

（research preview）服务，或者跑在你自己 CI 里的

claude-code-action

，必要时通过 AWS Bedrock、Google Vertex 或 Microsoft Foundry 走模型调用（CI/CD 打法覆盖了这些部署选项）。此外，要求 code owner 批准的分支保护策略也很值得配置。

#### 如何执行它

- 托管的 Code Review 服务是最快的起步方式。由管理员开启它并挑选仓库。当你需要掌控流水线，或希望 API 调用走自己的云协议时，就用 claude-code-action 在你自己的 CI 里跑评审（CI/CD 打法讲了这套管道怎么搭）。
- 技术负责人把评审策略写成仓库根目录下的 `REVIEW.md`，按组织关心的轮次划分：bug 与逻辑错误；安全与漏洞；对照 spec（需求打法里的 `spec.md`）、实现计划（plan mode 打法里的 `plan.md`）与设计原则做合规检查。`REVIEW.md` 还定义什么算 Important、什么只是 Nit，以及什么应当跳过。
- 技术负责人设定人工介入的门槛。发现项本身不批准也不阻断 PR，分支保护仍然要求 code owner 的批准。想要用发现项来把住合并关的平台工程师，可以读取该 check run 以机器可读形式发布的严重度计数。
- 当评审者或作者在某条评审意见上标记 `@claude`，Claude 会处理这条意见并推送修复。PR 讨论串同时记录下请求与改动。这个修复回路通过 claude-code-action 运行。在托管服务里，评论 `@claude review` 请求的是一次全新的评审。对于 Claude 自己开的 PR，更进一步：让 Claude 一路把 PR 照看到合并。团队会把这条回路包进一个自定义斜杠命令：扫一遍 PR 上未解决的评审意见和失败的检查，逐条处理并推送修复，直到 PR 全绿、只等 code owner 批准。
- 评审发现回流到 `CLAUDE.md`。当一次评审第二次标出同一个错误，纠正就作为那次评审的一部分写进 `CLAUDE.md`；因为评审会读 `CLAUDE.md`，这个错误从下一个 PR 起就会被抓住。评审也会指出某次改动是否让 `CLAUDE.md` 变得过时。
- 技术负责人每月调校一次这套配置：给发现项打分，让评审器持续改进，并在 `REVIEW.md` 里给 Nit 的数量设上限。生成的路径以及 CI 已经在强制的东西都排除在外。

#### 具体长什么样（REVIEW.md）

```
# Review instructions

## Passes
Run three passes and tag each finding with its pass:
- Bugs: logic errors, broken edge cases, subtle regressions
- Security: injection risks, authentication gaps, PII in logs
- Compliance: the change matches spec.md, plan.md and our design principles

## What Important means here
Reserve Important for findings that would break behavior, leak data
or breach a policy. Style and naming are nits.

## Cap the nits
Report at most five nits per review; summarize the rest as a count.

## Do not report
Generated files under src/gen/ and anything CI already enforces.
```

#### 治理考量

职责分离得以保留，因为写代码的那个 agent 没有任何途径批准自己的代码。`REVIEW.md` 里的评审策略适用于所有 PR，而发现项、修复、打分和批准都记录在 PR 历史里，所以 PR 本身就是审计记录。批准来自人，通过分支保护完成，并以发现项为依据。

关于这些控制在生产规模下如何组合起来，参见 [Anthropic 如何保障 AI 原生 SDLC 的安全](https://claude.com/resources/articles/how-anthropic-secures-its-ai-native-software-development-lifecycle)。

如何衡量

先导指标

到首次评审的时间，应当降到几分钟量级；以及不需要人碰这个分支就被解决掉的评审意见占比——数据直接存在 Git 上。

滞后指标

从 PR 历史和事故跟踪系统看：在合并之前被拦住的缺陷与漏洞，对比那些逃逸到生产环境的。

### hooks 作为审批关卡

构建阶段把 hooks 当护栏用，在没有人参与的情况下放行或拦下动作（Stage 3: Build）。hook 也可以「发问」：把动作暂停下来，直到某个指定的人批准——这正是发布关卡所需要的。

这条打法放在 Stage 5: Deploy，是因为发布关卡是最清楚的场景，但 hooks 并不专属于部署：Claude 在任何地方行动，它们就在哪里运行。例如，在 Stage 3: Build 期间，hooks 可以在没有变更工单的情况下拦住对 migrations 和基础设施的编辑；在 Stage 4: Test 里，也可以阻止 agent 在修复任务中编辑测试文件。

如何上手

前置条件

无。

基础设施

一份成文清单，列出变更流程要求的那些审批。

#### 如何执行它

- 工程负责人会同变更管理和合规，列出必须保留下来的人工审批关卡，例如变更管理的签核、发布授权，以及对受保护路径的编辑。
- 平台工程师把每个关卡表达成一个 hook——一段在 Claude 行动之前运行的脚本，它可以 allow、ask 或 block。
- 团队级的 hooks 放进 git 里的 `.claude/settings.json`；不可协商的 hooks 放进由平台或 IT 管理员持有的 managed settings，在那里单个工程师无法把它们关掉。
- 一个 block 应当说明理由，所以当 hook 停下某个动作时，原因和取得审批的路径会出现在 Claude 的输出里。

#### 具体长什么样（.claude/settings.json）

```
{
    "hooks": {
      "PreToolUse": [
        {
          "matcher": "Bash",
          "hooks": [
            { "type": "command",
              "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/production-gate.sh" }
          ]
        }
      ]
    }
}
```

#### 以及关卡本身（.claude/hooks/production-gate.sh）

```
#!/bin/bash
# Production deploys require a named release authorization
cmd=$(jq -r '.tool_input.command' < /dev/stdin)
if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
   if [ -z "$RELEASE_APPROVAL" ]; then
     echo "Production deploys need a release authorization." >&2
     exit 2 # exit 2 blocks the action; the message goes to Claude
   fi
fi
exit 0
```

#### 治理考量

hooks 就是审批关卡。关卡条件对每个人、每一次都强制执行。allow 和 block 的判定都带时间戳记录。关卡还定义了什么叫作批准——是一张已批准的变更工单，还是发布经理的签核。

示例

### 受监管企业的 managed settings

由平台团队通过 MDM 或管理控制台下发；工程师无法编辑或覆盖其中任何一项。

{
  "permissions": {
     "deny": [
        "Read(.env*)", "Read(./secrets/**)",
        "WebFetch", "Bash(curl *)", "Bash(wget *)"
     ],
     "allow": [
        "Bash(git *)", "Bash(make build)",
        "Bash(make test)", "Bash(make lint)"
     ],
     "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true,
  "sandbox": {
     "enabled": true,
     "failIfUnavailable": true,
     "allowUnsandboxedCommands": false,
     "network": { "allowedDomains": ["git.internal.example.com",
"registry.npmjs.org"] },
     "credentials": {
        "files": [
          { "path": "~/.ssh", "mode": "deny" },
          { "path": "~/.aws/credentials", "mode": "deny" }
        ],
        "envVars": [ { "name": "GITHUB_TOKEN", "mode": "deny" } ]
     }
  },
  "allowManagedHooksOnly": true,
  "disableSideloadFlags": true,
  "allowManagedMcpServersOnly": true,
  "strictKnownMarketplaces": [
     { "source": "github", "repo": "example-corp/approved-plugins" }
  ],
  "requiredMinimumVersion": "2.1.193"
}

从控制的角度看，每一行换来什么

permissions.deny

把密钥挡在 agent 的上下文之外，并阻止通过工具任意对外发网络请求；

permissions.allow

预先批准安全的内循环，这样 deny 列表不至于变成 prompt 疲劳。

disableBypassPermissionsMode

加上

allowManagedPermissionRulesOnly

意味着没有任何工程师、项目文件或命令行标志能放宽这些规则。

sandbox

补上 permissions 补不了的缺口。工具层面对 WebFetch 的 deny 拦不住一条 shell 命令去访问网络；而 OS 层面的域名 allowlist 直接阻断对外连接。

failIfUnavailable

和

allowUnsandboxedCommands

把 sandbox 变成一道关卡：当 sandbox 无法初始化时，Claude Code 拒绝启动；在 sandbox 内失败的命令也不能拿到外面去重试。

credentials

补上 deny 规则留下的缺口。

permissions.deny

管的是 Claude 的文件工具，但一条被沙箱包裹的 shell 命令默认仍然可能读到

~/.ssh

或

~/.aws/credentials

；这个区块拒绝这些读取，并把具名的密钥从每一条沙箱命令的环境变量里剥掉。

allowManagedHooksOnly

意味着本打法里的审批关卡是唯一会运行的 hooks；任何本地配置都无法在其上添加或将其替换。

disableSideloadFlags

和

strictKnownMarketplaces

意味着工程师机器上的每一个 skill、agent、hook 和 MCP server 都是经由组织批准的 plugin marketplace 装进来的，绝不来自某个 home 目录。

allowManagedMcpServersOnly

让 agent 的工具面变成一份由平台团队持有的 allowlist。

requiredMinimumVersion

拒绝在低于核准下限的版本上启动，于是这些控制是由一个组织确实评估过的构建来强制执行的。

把上面这份配置当作按需裁剪的起点，而不是一份照抄的建议。每一条 deny 都是拿能力换来的，正确的平衡点取决于仓库的数据分级。设置参考文档记录了每一个 key，包括那些 managed-only 的：

code.claude.com/docs/en/settings

如何衡量（针对 hooks 本身）

先导指标

在每个审批关卡上等待的时间。每一次 hook 判定都会带着时间戳和 allow 或 block 的结论写入 OpenTelemetry 导出，于是每个关卡的等待都看得见。

滞后指标

从事故跟踪系统看：上了 hooks 之前与之后，仍有关卡违规进入生产环境的数量。

### CI/CD 集成与部署

在 CI/CD 流水线里以非交互方式运行 Claude Code；把执行放进 sandbox，让长时间运行的 agent 安全地跑；通过 MCP 集成把部署能力暴露出去；并在 agent 真正需要回滚之前先把回滚路径演练过。

传统方式

流水线跑的是确定性脚本，凡是需要判断的事都等人。例如给 flaky 测试做分类、写 changelog，或者弄清楚构建为什么挂了。部署和回滚则是人在压力下去照着执行的 runbook。

AI 原生

Claude 以非交互方式跑在流水线里，负责那些需要判断的步骤，运行在带有受限凭证的 sandbox 中。部署工具通过 MCP 暴露给 agent，于是那条写下并测试了这次改动的工作流，也能把它发布出去、把它回滚回来——前提是待在组织按环境定义的关卡之内。

如何上手

前置条件

PR 评审回路里的 Claude，以及作为审批关卡的 hooks，因为在自动化能通过关卡加速任何东西之前，关卡必须先存在。

基础设施

装好 claude-code-action 的 CI 平台，或任何能调用

claude -p

的 runner；通过 API 访问模型，或者在流量必须留在组织的云协议之内时用 Bedrock、Foundry 或 Vertex；面向部署目标的 MCP servers；一份给 agent 作业用的 sandbox 配置，其中不放常备的生产凭证。

#### 如何执行它

- 平台工程师从只读的判断类步骤起步。在流水线作业里用 `claude -p` 给失败的构建做分类、总结一个 flaky 测试，或者起草 changelog。
- 把写入类步骤加在既有的关卡后面，用于修 lint、更新生成的文档，或者通过 `@claude` 提及来处理评审意见这类作业。agent 写入的一切都作为 PR 抵达，走分支保护，而 agent 没有向 main 直接推送的路径。
- 执行是沙箱化的。agent 作业运行在容器里，受网络策略约束，使用短时效的受限 token，默认不持有生产凭证。
- 通过 MCP 暴露部署能力。部署、状态、回滚变成工具，按环境限定作用域，于是 agent 的部署能力是一份 allowlist，而不是一个带着凭证的 shell 脚本。
- 按环境分层设置自主度。在开发环境，agent 可以自由部署。在生产环境，agent 准备好发布，由发布经理授权，而一个 hook 来强制这道生产关卡。Staging 处在两者之间的某个位置。
- 回滚应当是流水线里演练得最充分的一条路径：一条 agent 能执行的命令，并且定期在 staging 中演练。闭环打法（Stage 6: Maintenance）在控制区间被突破时就会调用这个回滚，所以它必须提前被验证过。

#### 具体长什么样（流水线步骤）

```
- name: Triage failed build
  if: failure()
  run: >
    claude -p "Read the build log at out/build.log. Identify the most
    likely cause, say whether the failure looks flaky or real, and write a
    three-line summary for the PR thread." >> triage.md
```

#### 治理考量

总原则是：agent 可以在生产关卡之前行动，但不能越过它。下面的控制来强制这一原则。

- 分支保护把 agent 写入的任何东西变成 PR，没有通向 main 的直接路径。
- 生产部署 hook 会拦住发布，直到具名的发布经理授权。每一次非交互运行都以 agent 自己的身份行动，于是流水线日志能把 agent 做了什么与触发它的工程师做了什么区分开。
- 按环境的权限层级设定 agent 在通往关卡的路上能做到多少事。

如何衡量

先导指标

从 CI/CD 流水线日志看：流水线失败中，无需呼人（paging）就完成分类的占比。

滞后指标

DevOps Research and Assessment（DORA）指标——CI 系统和部署工具本来就在输出这些。

06

## Maintain（维护）

环就此闭合。一个触发器调用 Claude，调用链路上没有人的参与，而它发现的东西作为

intent.md

重新进入流水线。

### 维护与闭环

到目前为止，我们讨论的是如何把 Claude 加入 SDLC 流程的每个阶段，而每个阶段都需要人来启动最初的步骤。这一阶段则把重点转向让 Claude 自主运行，把闭环合上。

举例来说，一个持续运行的监控 agent 可以在一张 bug 工单被提出之后，创建一份 `intent.md`，并让它流经需求、规划、构建、测试和评审这些环节。Stage 6: Maintenance 以 headless 方式运行，阶段之间有一道独立的信心关卡——一个确定性检查，或者一个对抗式的评审 agent——来决定上一阶段的产出是继续往下走，还是升级到人那里。

传统方式

维护是一个被动响应的阶段。所有工单或事故都在等某个人去处理、去重启流程。凌晨 3 点的一条告警可能被漏掉；一张工单可以在待办堆里躺着直到有人认领；而如果另一把火先烧起来，复盘行动项可能根本没走到代码库里。

AI 原生

一个触发器——控制区间被突破、一张工单、频道里的一条消息，或一个定时计划——调用 Claude，链路上没有人。Claude 做诊断，只通过有关卡的路径行动，并把它发现的东西写成

intent.md

，随后走上面描述过的那些阶段。人对它的工作做分类和评审，而不必再亲手启动它。

### 闭环

一个确定性脚本盯着生产环境，当控制区间被突破时调用 Claude。对突破的监控是「环自主运行」这一模式很好的一例，而本阶段末尾的 [Claude Tag](https://claude.com/product/tag)（public beta）一节讲的是从别的渠道进来的工作。

如何上手

前置条件

Intent.md

它给这个环提供一份结构化的产出物来重启。Claude 加速过的 PR 评审、作为行动边界的 hooks，以及一条供 CI/CD 使用的回滚路径（最高自主度层级会调用它）。

基础设施

一个检测脚本可以查询的指标存储（Prometheus、CI 系统的 API 或等价物）；仓库的读权限；在 CI 里非交互运行 Claude Code 的方式；或者一个

Agent SDK

，用于一个接收 webhook 的服务。

#### 如何执行它

- 服务负责人或平台工程师挑一个滚动基线稳定的指标，例如 CI 测试失败率、部署后的 5xx 率，或 PR 周期时间。
- 他们写检测脚本：通常是在滚动窗口上算均值和标准差，配合规则（Western Electric 或类似的），让区间既能抓到缓慢的漂移也能抓到突刺。脚本有版本控制、有单元测试，而检测本身完全确定性，不涉及任何模型。
- 响应层级定义在有版本控制的配置里（下面的 `bands.yaml`）。在 1σ 时脚本只记录日志；2σ 时它调用只读模式的 Claude 来诊断；3σ 时 Claude 可以行动，但只能通过开一个进入评审关卡的 PR，或触发一条预先批准的 runbook。
- 触发层可以是 GitHub 或 GitLab 里的定时工作流、来自现有监控栈的 webhook，或网络内部的一个 Cron Job。Claude 以无状态方式运行：要么作为 CI runner 上的一个非交互步骤，要么作为沙箱容器里的一个 Agent SDK 服务，部署与模型访问的选项由 CI/CD 打法覆盖。因为每一次运行都是无状态、非交互的，一个循环可以在没人启动的情况下开始和结束。
- agent 把它的诊断按 Stage 1: Plan 的格式写成 `intent.md`，内容覆盖这个异常及其证据、一个建议的结果、受影响的系统，以及尚未明确的问题。从这里开始，这个发现就和别的东西一样走流水线。
- 服务负责人或 on-call 工程师对这个队列做分类，把面向产品的发现转给产品负责人：现在修、排期修，还是驳回。驳回可以调校这些区间，也有助于降噪。
- 一次修复发布之后，为这起事故补一条 eval（continuous evals 打法），确保今后同类问题都被防住。

#### 具体长什么样（例如一个监控 CI 测试失败率的 bands.yaml）

```
metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose,
            tools: "Read,Grep,Bash(gh run view *)" }
  3sigma: { action: propose,
            routes: [pull_request, runbook:rollback-deploy] }
```

#### 治理考量

层级边界由有版本控制的配置来强制执行，permissions 和 managed settings 则拒绝生产环境的访问。调用、发现和分类决定都带时间戳记录。由服务负责人对发现做分类和批准；由此产生的改动走正常的 PR 评审关卡；agent 可以触发的那些 runbook 则是事先批准过的。

如何衡量

先导指标

从区间被突破，到分类队列里出现一份

intent.md

的时间，与过去从事故到复盘行动项的时间做对照。检测脚本的日志里有突破发生的时间戳和事件所属的层级。

滞后指标

发现项最终变成被合并修复的占比（分类队列对照真实的 PR 历史），以及同类事故的重复次数——随着修复不断往 eval 套件里补用例，这个数应当下降。

#### 例子

- 当 CI 测试失败率突破 3σ，agent 隔离那个 flaky 测试，或者开一个 revert PR，由评审关卡来定。
- 当部署后的 5xx 率在窗口内有一次部署的情况下突破 3σ，agent 触发既有的回滚流水线。
- 当 PR 周期时间触发了某条漂移规则，agent 为工程负责人写一份报告——这说明这套 harness 对流程指标同样有效，而不只适用于生产指标。

检测始终保持确定性。区间一旦被突破才调用 Claude，而层级决定了它能做什么。

### 周期性的代码库扫描

一次安全扫描是「在某个特定模型下、就某个时刻的代码库」作出的陈述，而这两半都会过时：代码每周都在变，而每一代模型都能发现上一代漏掉的漏洞。AI 原生的答案是按时间表运行扫描，调用链路上没有人，并把它发现的东西像代码库任何其他改动一样送过同样的关卡。

[Claude Security](https://claude.com/product/claude-security) 是定时扫描的托管形态。连上一个 GitHub 仓库，扫描就在 Anthropic 的基础设施上、由 Claude Mythos 5 运行；每一条发现都先经过验证才上报，并附上一个信心评分。建议的补丁在 Claude Code on the web 里评审和应用。组织拿到的是发现本身，并不需要访问模型。

传统方式

安全扫描是一桩「事件」：发布或审计之前发起一次扫描。报告进跟踪系统，积压靠人工一条条消化，直到下一次事件。中间写出来的代码能被覆盖多少，全看 PR 评审抓到了什么。

AI 原生

扫描按时间表对所有已连接的仓库运行，用的是当下最有能力的模型，而发现有人在读之前就已验证过。每条发现都按处理被突破的控制区间的方式来处理：一个 PR 装得下的修复走评审关卡，更大的东西则变成一份

intent.md

。覆盖度的日期是从最近一次运行算起，而不是从第一次

如何上手

前置条件

PR 评审关卡和作为审批关卡的 hooks（

Stage 5: Deploy

），好让发现像其他任何改动一样经过评审。还有

intent.md

的格式，来自

Stage 1: Plan

，用于超出单个 PR 承载能力的发现。

基础设施

Claude Security 以 public beta 形式向 Claude Enterprise 组织开放。它需要在目标仓库（云端托管的 github.com）安装 Anthropic GitHub App；启用 Claude Code on the Web；打开 Extra Usage 并设好支出上限；给运行扫描的人配 premium 席位；并由管理员在

claude.ai/admin-settings/claude-code

把这个功能打开。扫描按消耗以 Mythos 5 的费率计费，所以支出上限应当与仓库的体量和数量相匹配。

#### 如何执行它

- 安全负责人把仓库接进来，并按仓库、服务或团队组织成项目，好让发现的归属从一开始就清楚。
- 对最关键的仓库跑第一次全量扫描，包括那些过去被别的工具或更早的模型扫过的仓库。把第一次扫描当作基线。第一次扫描很可能会在原本被认为干净的代码里翻出发现。
- 按项目设定时间表。对活跃开发的服务，每周是合理的默认值；仓库很大或内容混杂时，把扫描范围限定到某个目录或分支。
- 拿着信心评分对发现做分类。驳回时要给理由，这样这次驳回会被记录，同一条发现也不会在下一次运行时又当作新东西回来。
- 对一条范围明确的发现，在 Claude Code on the Web 里打开建议的补丁，评审它，然后像其他任何改动一样走 PR 评审关卡。提出这个修复的 agent 没有批准它的途径。
- 比一个补丁更宽的东西，例如架构层面的弱点，或跨多个服务重复出现的某个模式，就按 Stage 1 的格式写成 `intent.md`，从 Plan 起跑。
- 一个修复发布到生产之后，为这个漏洞类别往 continuous evals 打法的那套套件里补一条 eval，从此之后，驱动 agent 的那份配置就会被针对这一类别做测试。
- 把发现导出为 CSV 或 Markdown，或者使用 webhook，让组织现有的跟踪系统和审计系统继续作为记录系统——审计方本来就期待在那里看到它们。

#### 治理考量

扫描在组织的管控之下运行：哪些仓库被连进来、谁持有扫描席位、支出上限是多少，都是集中设定的。每条发现都有验证结果和信心评分，每次驳回都有理由，所以扫描历史本身就是一份记录了「发现了什么、修了什么、又有意接受了什么」的审计材料。

修复是通过 PR 评审关卡和分支保护抵达生产环境的，而不是由扫描本身直接落地。Claude Security 是对既有静态分析和依赖扫描的补强。确定性的检查留在 CI 里，而由模型驱动的扫描覆盖那些确定性检查本来不打算发现的、依赖上下文的漏洞。

如何衡量

先导指标

已连接仓库中按时间表扫描的占比；以及从一条发现被上报，到它的补丁进入 PR 评审关卡的时间，分别取自扫描历史和 PR 元数据。

滞后指标

由定时扫描发现的漏洞，对比在生产环境或由外部报告发现的（取自事故跟踪系统）；以及已经跑过几轮的仓库里每次扫描发现数的趋势——随着修复和 evals 的积累，这个数应当下降。

### Claude Tag 让 Claude 值班

事故也可以通过别的途径进来，例如 Slack 或 Teams 这类办公沟通应用。一次事故可能表现为晚上 10 点 incident 频道里一条要求紧急修复的 Slack 消息，而现在它可以被立即处置。Claude Tag（public beta，目前支持 Slack）让 Claude 以自己的身份成为那些频道的一员，于是每一场新的事故都有一个第一响应者，而响应本身也成为这个环的一部分，并沉淀为未来事故的记忆。

对话和机构知识都留在频道里，频道里的任何人都能引导并执行响应。任何团队成员都可以验证假设、探索新选项、实时展开调查，而频道的历史记录进一步增强了可审计性。借助对 MCP 的访问，Claude 会确认指标是否已回到基线并在线程里给出确认，把复盘写进一份有版本控制的 lessons 文件，供未来的调查阅读。

事故并不是 Claude Tag 接的唯一工作。在工单上通过 MCP 标记它，或是在频道里问它，Claude 都用同样的方式对工作进行分类。一个范围清晰的小修复会以 PR 的形式通过评审关卡抵达，更大的东西则写成 `intent.md`，交给 Stage 1: Plan——到这个点上，这个环就开始自己喂自己了。参见：[Claude Tag 在 Anthropic 如何承担 CI/CD 的值班](https://claude.com/resources/articles/ai-ci-cd-on-call)。

频道就是审计轨迹：请求、诊断、人的授权和修复，全都留在处理这场事故的地方。

## 结语

模型和 harness 都已经变得更先进，这让组织得以改变的不只是生产代码的方式，而是整个软件开发生命周期。

这场变革把人的判断保持在流程的中心，同时兼顾大型企业组织在治理与监管上的要求。

本指南汇集了我们 Applied AI 团队在为客户日常执行的大量真实最佳实践，我们希望它对你是一份实用、可落地的资料。

环持续运转。人的判断始终在它之上。
