我们估计，对于按 token 计费的典型工作负载，Claude Opus 5.5 的运行[成本比 Opus 5 低约 40%](https://www.anthropic.com/claude-opus-5-5)。对开发者来说，这些节省究竟*如何*累积起来才是关键。

如果你按 token 付费，那么运行时间更长、上下文更高的会话会看到最大的成本差异——正是过去六个月里越来越普遍的 Claude Code 会话类型。

本文会深入剖析：是什么让 Opus 5.5 对开发者今天（很可能也是明天）的编码方式来说具备成本效益。

## **Claude Code 的趋势**

我们汇总了 2026 年 3 月到 9 月开发者使用 Claude Code 的聚合数据。随着模型能力提升，开发者部署 agent 的方式越来越精细。每个会话的 prompt 数量保持稳定，但我们发现了一些有趣的行为：

- 对每个 prompt，Claude 的工作时长是原来的 3.3 倍，每个 prompt 的模型调用次数多 40% 以上，中断次数少 68%。
- 开发者连接 tool server 或使用 skill 的可能性约为原来的两倍，往 prompt 里粘贴文本的可能性则少了三分之一。
- 每个请求的上下文增长了 2.6 倍。输入与输出的 token 比例从 189:1 变为 324:1。

![](https://assets.claude.com/809e6884c05cc2a142d34ee57456120a550ef6d1.png)

这一切都指向：开发者正把更勤奋、信息更充分的 Claude 投向更大、更开放的任务。对这类会话来说，context engineering 的经济影响会被放大。

简单说，Claude 读的 token 更多了。你需要确保[你提供的所有上下文都是必要的](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)，并且[尽可能多的上下文从缓存读取](https://claude.com/resources/articles/maximizing-the-value-of-your-claude-code-sessions)。

## **是什么让 Opus 5.5 在长而上下文密集的会话中具备成本效益**

有三项改动让长时间运行、上下文密集的会话更具成本效益：定价、模型行为以及 Claude Code harness 的改动。我们逐项来看。

### **缓存很便宜**

对于按 token 计费的用量，我们把输入和输出 token 的成本降低了 20%，并且*把读取缓存 token 的价格降低了 60%*。后一项降价意义重大，因为缓存读取构成了 agentic 和编码工作成本的大部分。

正如我们刚才讨论的，每个请求的上下文在六个月内增长了约 2.6 倍，这意味着节省正朝着正确的方向走。同样的价格调整，对按 token 计费的用户来说，在今天的 Claude Code 流量上比六个月前省得更多，因为账单中重新读取的上下文占比更高了。

截至本文发布之日，Opus 5.5 的缓存 token 成本是竞品模型的五分之一，同时性能优于它们。

![](https://assets.claude.com/dda0a2bf9ba0614e6be7598a1be52d1871292742.png)

### **Claude Code 更善于利用缓存**

这一点与 Opus 5.5 关系不大，更多是我们过去六个月新增的许多 Claude Code 功能带来的结果。考虑到我们刚才讨论的编码会话趋势，你可能会预期缓存未命中的比例上升，但事实恰恰相反。**未命中缓存的输入减少了 50% 以上。**

例如，对于刷新登录这类小摩擦，我们让缓存更难被意外破坏；对于更大的操作，比如在对话中途添加指令或按需加载工具，我们也让缓存更难被破坏。对 Opus 5.5 和 Fable 5.1 这样的新模型，你现在可以在会话中切换 effort 级别，而不必重置缓存。

我们还让缓存对长时间运行和委派出去的会话更有用。使用 API key 和云提供商的开发者现在可以设置一小时的缓存生命周期（订阅用户此前已有此能力），fork 出的 subagent 会从父级的缓存起步，而不必为同一份上下文再付一次钱。

### **同样的任务，更少的轮次**

完成同样的任务，Opus 5.5 可能比其他模型需要更少的轮次。Zeta Labs 发现，与 Opus 5 相比，每个任务的轮次和工具调用都更少，成本却只有近一半，而他们最难的任务完成数量翻了一倍。

这并非对每个任务都成立。在[《Opus 5.5 上任务的成本》](https://claude.com/blog/what-a-task-costs-on-opus-5-5)一文中，Addy 写道：“对于范围明确的任务，两个模型完成的轮次大致相同，降价就是你得到的全部好处。差距最大的应该是开放型任务，模型可能在一个错误想法上耗掉很多轮。没有任何一个数字适用于所有代码库，所以要实际测量。”

换句话说，简单、短小、机械的任务所需轮次相同，而更长、更难的任务中，Opus 5.5 更有机会避免在错误路线上烧 token。省下一轮，比省下一个缓存 token 更划算。

同样值得注意——尤其是当 Claude 无人值守或长时间不间断工作时——Opus 5.5 生成输出的速度比 Opus 5 快 30% 以上。这不会提高缓存命中率，也不会减少 token 用量，但意味着长任务等待更少。

## **保护好你的缓存读取**

随着 agentic 编码走向成熟，各组织的要求已从「不惜一切代价扩展」转向「高效扩展」。在 Claude Code 里运行 /usage，看看你的用量中有多少是缓存读取。然后守住这个数字：

- 在会话开始时选好模型，而不是中途切换；
- 离开之前先 compact，而不是回来之后再 compact；
- 如果你使用 API key 或云提供商，为长会话设置[一小时的缓存生命周期](https://code.claude.com/docs/en/prompt-caching#choose-the-ttl-yourself)。

把 Opus 5.5 用在那些开放型、上下文密集、这些习惯会复利的工作上，并查看[《Opus 5.5 上任务的成本》](https://claude.com/blog/what-a-task-costs-on-opus-5-5)里算好的数字。
