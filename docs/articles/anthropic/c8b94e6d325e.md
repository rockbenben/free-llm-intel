我们估计，对于按代币计费的典型工作负载，Claude Opus 5.5 [运行成本比 Opus 5 低约 40%](https://www.anthropic.com/claude-opus-5-5)。对于开发人员来说，这些节省的具体效果如何叠加很重要。

如果您通过代币付款，您将看到运行时间较长、上下文较高的会话的最大成本差异 - 这正是过去六个月中变得更加流行的 Claude Code 会话类型。

这篇文章将深入探讨 Opus 5.5 对于开发人员今天（也可能是明天）的编码方式具有成本效益的机制。

## **Claude Code趋势**

我们提取了有关开发人员从 2026 年 3 月到 9 月如何使用 Claude Code 的汇总数据。随着模型功能的改进，开发人员已经以越来越复杂的方式部署代理。每个会话的提示数量一直稳定，但我们发现了一些有趣的行为：

- Claude 在每个提示上的工作时间延长了 3.3 倍，每个提示的模型调用量增加了 40% 以上。中断减少了 68%。
- 开发人员连接工具服务器或使用技能的可能性约为两倍，而将文本粘贴到提示中的可能性则降低三分之一。
- 每个请求的上下文增长了 2.6 倍。输入与输出代币比率从 189:1 变为 324:1。

![](https://assets.claude.com/809e6884c05cc2a142d34ee57456120a550ef6d1.png)

所有这些都表明，开发人员的目标是让Claude更加努力、更加了解情况，以完成更大、更开放的任务。对于这些类型的会议，背景工程的经济影响是复杂的。

简单地说，Claude读取了更多的令牌。您需要确保[您提供的所有上下文都是必要的](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5- Generation-models)，并且[尽可能多的上下文是从缓存中读取的](https://claude.com/resources/articles/maximizing-the-value-of-your-claude-code-sessions)。

## **是什么让 Opus 5.5 对于长时间、上下文密集的会话具有成本效益**

通过三项更改，可以使长时间运行、上下文较多的会话更具成本效益：定价、模型行为和 Claude 代码工具的更改。让我们逐一看看。

### **缓存很便宜**

对于按令牌计费的使用量，我们将输入和输出令牌的成本降低了 20%，并且*我们将读取缓存令牌的价格降低了 60%*。后者的减少是显着的，因为缓存读取占据了代理和编码工作成本的大部分。

正如我们刚刚讨论的那样，每个请求的上下文在六个月内增加了大约 2.6 倍，这意味着节省趋势正朝着正确的方向发展。对于那些按代币计费的价格，同样的价格变化比六个月前节省了更多的Claude Code流量，因为现在更多的账单是重新读取的上下文。

截至发布日期，Opus 5.5 上的缓存代币成本仅为竞争模型的五分之一，但性能却优于竞争对手。

![](https://assets.claude.com/dda0a2bf9ba0614e6be7598a1be52d1871292742.png)

### **Claude Code更擅长使用缓存**

这并不是 Opus 5.5 特有的，更多的是我们在过去六个月中添加的许多 Claude Code 功能的结果。鉴于我们刚刚讨论的编码会话趋势，您可能会期望缓存未命中率更高，但事实恰恰相反。 **未命中缓存的输入减少了 50% 以上。**

例如，我们通过较小的剪纸（例如刷新登录）来提高无意中破坏缓存的难度。我们还加大了破坏更大操作的难度，例如在对话中添加说明或按需加载工具。对于 Opus 5.5 和 Fable 5.1 等较新的模型，您现在可以在会话期间更改工作量级别，而无需重置缓存。

我们还使缓存对于运行时间较长和委派的会话更加有用。 API 密钥和云提供商的开发人员现在可以设置一小时的缓存生命周期（订阅者已经拥有），并且分叉的子代理从父级的缓存开始，而不是再次为相同的上下文付费。

### **同样的任务，但回合数更少**

Opus 5.5 完成相同任务所需的转动次数比其他型号少。 Zeta Labs 每项任务的轮次和工具调用量比 Opus 5 少，但成本却只有 Opus 5 的一半，完成的最困难任务的数量是 Opus 5 的两倍。

这并不适用于所有任务。在 [Opus 5.5 上的任务成本](https://claude.com/blog/what-a-task-costs-on-opus-5-5) 中，Addy 写道，“在范围明确的任务中，两个模型完成的轮数大致相同，而降价就是你所能得到的。开放式任务中的差距应该是最大的，其中模型可能会在错误的想法上花费很多轮。没有一个数字适用于每个代码库，因此请衡量它。”

换句话说，简单、简短和机械的任务将需要相同的轮数，而较长、较难的任务则更有潜力让 Opus 5.5 避免因错误的方法而销毁代币。减少轮次甚至比缓存令牌更具成本效益。

另外值得注意的是，特别是当 Claude 在无人值守或不间断的情况下工作更长时间时，Opus 5.5 生成输出的速度比 Opus 5 快 30% 以上。虽然这不会提高缓存命中率或使用更少的令牌，但这意味着长时间运行时的等待时间更少。

## **保护您的缓存读取**

随着代理编码的成熟，组织已经从要求开发人员不惜一切代价进行扩展转变为要求开发人员高效扩展。在 Claude Code 中运行 /usage 以查看有多少使用量是缓存读取。然后保护该号码：

- 在会话开始时选择您的模型，而不是中途切换，
- 在离开之前而不是离开之后进行压缩，并且
- 如果您使用 API 密钥或云提供商，请为长时间会话设置 [一小时缓存寿命](https://code.claude.com/docs/en/prompt-caching#choose-the-ttl-yourself)。

将 Opus 5.5 放在那些习惯复合的开放式、上下文密集的工作中，并参阅 [Opus 5.5 上的任务成本是多少](https://claude.com/blog/what-a-task-costs-on-opus-5-5) 了解工作数据。
