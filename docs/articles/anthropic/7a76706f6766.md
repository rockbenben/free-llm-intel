# 用 Claude Platform 降低成本并提升性能

调优 prompt 缓存、指令和努力（effort），可以在不牺牲应用性能的前提下降低 Claude 的成本。

***更新：*** *本博客文章最初发布于 2026 年 9 月 8 日，其中的基准反映了使用 Opus 5 和 Sonnet 5 的成本与性能。此后我们重跑了几项基准，以纳入或突出 2026 年 9 月 22 日发布的 Opus 5.5。*

性能与成本常被视为一种权衡：要少花钱，就得接受更差的结果。在实践中，我们发现许多使用 Claude Platform 的应用可以通过三处修正来削减成本而又不放弃性能：把 prompt 缓存命中率最大化、在升级到前沿 Claude 模型时移除 prompt 里的反模式，以及把 effort 校准到任务。我们把这份指南放进了 [`claude-api`](https://github.com/anthropics/skills/tree/main/skills/claude-api) skill。在本文里，我们展示 Claude Code 配合 `claude-api` 如何往往能找到既降低成本、又维持或提升性能的办法。

## **Prompt 缓存**

在 Claude 生成回复之前，它先把你的 prompt 处理成一个内部工作状态。这一步称为 *prefill（预填充）*，是处理输入中最昂贵的部分。Prompt 缓存会保存那个状态（键-值，即 KV 缓存）：当一个请求以相同前缀开始时，Claude 会回读它而不是重新计算。缓存读取的[计费](https://platform.claude.com/docs/en/about-claude/pricing)只是完整输入价格的一小部分。

要有效使用 prompt 缓存，有几个实际考量。第一，prompt 缓存钉在特定模型上。第二，prompt 缓存读取必须在整个 prompt 跨度上 *逐字节精确*。最后，prompt 缓存有[有限的存活时间](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#ttl-support)（TTL）。

牢记这几点后，有以下几条实用技巧：

- **避免在对话中途改变 effort 或 thinking 设置。** 这些设置会渲染到你内容之前的 prompt 里，因此它们是被缓存前缀的一部分。特别是在 Claude Opus 5 和 Fable 5.1 上，你可以[在对话中途更新 effort](https://platform.claude.com/docs/en/build-with-claude/effort#changing-effort-mid-conversation) 而不破坏缓存。

- **把易变的值留在前缀之外。** 系统 prompt 里一个动态时间戳或 ID，会跨模型调用发生变化，从而破坏缓存。

- **避免自行重排的工具体定义。** 使用 Claude Messages API 时，[prompt 按固定顺序组装](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#structuring-your-prompt)，工具体定义渲染在最顶部。任何对工具体定义的改动都会破坏缓存。

- **分叉对话时要小心。** 子 agent 和分支只有在分叉的前缀逐字节相同、在同一模型上、且使用相同 effort 时，才共享父级的缓存。

- **避免超过缓存 TTL 而存活的同步工具调用和子 agent。** 如果一个 agent 阻塞在一个长时间运行的工具调用或子 agent 上，缓存可能在结果返回之前就过期了。下一轮就得重写缓存，按 1.25 倍的普通输入价（1 小时缓存为 2 倍）计价，而不是廉价的读取价。

### 如何修复

我们在 prompt 缓存管理上[积累了](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)几条经验：

- **仔细监控你的 prompt 缓存命中率。** [Claude Console](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics) 提供 prompt 缓存诊断，包括缓存未命中的原因（图 1）。如果命中数意外下降，[缓存诊断 API](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics) 会精确告诉你两个请求在何处产生了分歧。

图 1。Claude Console 能通过比较连续请求、精确识别 prompt 前缀在何处产生分歧，来诊断意外的 prompt 缓存未命中。

- **推迟不常用的工具。** 一开始就声明你所有的工具，但把不常用的标记为 [defer_loading](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching#defer-loading-and-cache-preservation)：它们留在缓存前缀之外，只有当 Claude 通过工具搜索查找它们时才被追加进对话，从而保住了缓存。

- **把系统 prompt 的更新当作消息来施加。** [Claude Platform](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages#when-to-use-a-mid-conversation-system-message) 让你在对话中途把一条系统指令作为消息加入，而不是去编辑系统 prompt，从而保住缓存。

- **把请求布局安排成稳定部分保持稳定。** 先加静态上下文（工具体定义和系统 prompt），把不断增长的对话放在其后（图 2）。

图 2。组织 prompt，以确保动态内容被追加到一个稳定前缀的末尾。

- **在 prompt 缓存反正已经被破坏时，再去改动模型或 effort。** 某些操作，如[压缩（compaction）](https://platform.claude.com/docs/en/build-with-claude/compaction)，本就会重写大部分缓存（即对话）。那正是[切换模型或 effort 的好时机](https://cognition.com/blog/devin-fusion)，反正你已经在为一次未命中买单。

- **随对话增长移动缓存断点。** 借助 Claude Platform，你可以设置[自动缓存](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#automatic-caching)，把缓存断点自动施加到最后一个可缓存块上。

- **预热缓存。** 为降低延迟，发送一个 `max_tokens: 0` 且带显式缓存断点的请求。这会把 prompt 处理一遍并写入缓存，而不生成任何东西。如果你在会话开始时（例如用户正在输入时）运行它，第一次真正的请求就会命中一个热缓存。

- **不要超出 prompt 缓存 TTL。** 5 分钟的缓存 TTL 从请求开始计时。如果一个 agent 阻塞在超过 5 分钟的工具调用或子 agent 请求上，父级的缓存会在结果返回前过期。在这种情况下，考虑对前缀[设置一个 1 小时的 TTL](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)。

## **指令**

Prompt 会累积一些用来打补丁式弥补模型弱点的指令。这些指令相对于[最新 Claude 模型](https://x.com/trq212/status/2080710971228918066)的能力会发生漂移。以下是一些妨碍前沿 Claude 模型、并可能无意间增加成本的常见 prompt「反模式」：

- **验证仪式。** 像「*仔细检查你的工作*」或「*回答前先验证两遍*」这样的指令，常被前沿模型按字面执行，可能浪费 token。

- **详尽与强调增强词。** 「*要尽可能详尽*」「*关键：你必须始终……*」在处理前沿模型时会导致冗长和额外的工具调用。

- **强制流程与 scratchpad 脚手架。** 固定的步骤流程（例如「*在 scratchpad 里一步步思考*」）或推理模板，是前沿模型并不需要的仪式。这类脚手架会叠加到原生推理之上，用掉不必要的 token。

- **过时的示例。** 针对某个旧模型失败模式调优的 few-shot 示例，可能教前沿模型在本不需要的请求上模仿长篇推理链。

- **相互矛盾的规则。** 前沿模型更擅长遵循指令。相互矛盾的指令（「始终在政策内退款」对「绝不在升级之前退款」）会被前沿模型更按字面地遵循，导致性能下降。

- **过时的配置。** 为某一代旧 Claude 编写的设置（如手动的 thinking 预算），在升级到前沿模型时可能被 Claude Platform 拒绝。

### **如何修复**

我们更新了 `claude-api` skill，加入一个新命令来提防这些反模式。在 Claude Code 里，对你的 prompt、skills 或工具体描述运行 `/claude-api prompt-audit`。这项审计涵盖你工作目录里的任何内容，包括调用 Claude API 的应用代码以及 Claude Code 自身的配置（如 [CLAUDE.md](http://claude.md) 或 skills）。

例如，我们在一个客户支持基准上测试了一次从 Opus 4.8 到 Opus 5.5 的模型迁移。我们从一份干净的 prompt 起步，一次种入一个反模式（一个已弃用的 thinking 设置、一对相互矛盾的退款规则、一个手动 scratchpad、「验证两遍」、「尽可能详尽」，以及一个强制的六步流程），得到六份遗留 prompt。

我们分别在 Opus 4.8 上、在 Opus 5.5 上（只改了模型 ID）、以及在 Opus 5.5 上对每份 prompt 各运行一次 `/claude-api prompt-audit` 后，分别跑了它们（图 3 展示六者的平均）。

图 3 | 从 Opus 4.8 迁移到 Opus 5.5 期间 prompt 反模式的影响。

从 Opus 4.8 到 Opus 5.5 的迁移把成本降了约 18%。这是因为 Opus 5.5 的[输入 token 和 prompt 缓存读取](https://platform.claude.com/docs/en/about-claude/pricing)比 Opus 4.8 更便宜。

在 Opus 5 上，验证仪式（「*验证两遍*」）通过对每一笔退款重复订单查询而用掉不必要的 token。强调增强词（「*尽可能详尽*」）变成了几十次并不需要的知识库搜索。

运行 `/claude-api prompt-audit` 移除了这些反模式，又额外降低了 9% 的成本。成本下降是因为多余的调用和重复的推理被消除了。准确率上升了约 2 个百分点，原因有三。那个已弃用的 thinking 设置让 API 直接拒绝每一次路由请求。相互矛盾的退款规则导致 Opus 5.5 在本应向客户应退的四笔退款上、却要客户确认时 withhold 了。而那个手动 scratchpad 与 Opus 5.5 内建的 thinking 相冲突：在三张工单上，它把工具调用写进了推理里、却从未执行。

## **Effort**

[Effort](https://platform.claude.com/docs/en/build-with-claude/effort) 告诉 Claude「要用多大力气」。在低 effort 下，Claude 通常更快得出结论。在高 effort 下，Claude 会斟酌、验证，并在回答前探索替代方案。

在单一模型上，各 effort 级别的成本-性能会有差异。例如，Claude Fable 5 在 FrontierCode Diamond（最难的 50 个任务）上，低 effort 得 11.5%、每任务 5.35 美元。在最高 effort 下，Fable 5 得 30.9%、每任务 19.00 美元；改 effort 把分数提升约 2.7 倍（+19 分），代价约为 3.5 倍的成本（图 4）。

在 Claude Fable 5.1 上，Humanity's Last Exam（不带工具）呈现出一条陡峭、最后一步收益递减的曲线。它在低 effort 下得约 53%、每题约 0.30 美元，在最高 effort 下得约 61%、每题约 2.23 美元；最后一步升到最高只加约半分，却多花 46% 的成本。那点增益落在基准的逐次运行噪声之内，所以你多付了钱却换不来可衡量的收益。

图 4。Fable 5 在 FrontierCode Diamond 上、跨 effort 级别的性能对成本。

Effort 可能在任一方向上失准：

- **假设越高越好。** 高 effort 会导致*过度*思考。Claude 花在斟酌上的时间超出任务所需，增加了成本/延迟，还可能降低答案质量。斟酌只在仍有证据可寻时才有帮助。

- **偏向低 effort。** 设得太低，Claude 会在证据不足时就停下。它做出更少的工具调用，因此可能凭第一个搜索结果而不是第三个来作答。它在难步骤上想得更少，并跳过它本来会自己跑的那道检查。答案看起来完成了，但它建立在部分信息之上。

### **如何修复**

有一些有用的 effort 校准方法：

- **在更低 effort 下测试更强的模型。** 一个更强的模型在低 effort 下，可能比一个拼命工作（高 effort）的较弱模型更便宜。例如，在 CursorBench 3.2 上，Claude Fable 5.1 在低 effort 下[匹敌](https://www-cdn.anthropic.com/0339e6a7c5c7b87f5c07798616dc32c215d14235/Claude%20Fable%205.1%20&%20Claude%20Mythos%205.1%20System%20Card.pdf) Fable 5 在高 effort 下的性能，而成本只有三分之一（图 5）。有两点让更新的模型更便宜：在低 effort 下它每个任务做的功更少，而且 Fable 5.1 的 prompt 缓存读取定价为每百万 token 0.25 美元，而 Fable 5 为 1.00 美元。即便按 Fable 5 的价格，Fable 5.1 在低 effort 下也会便宜约 40%。

图 5。Fable 5 与 Fable 5.1 在 CursorBench 3.2 上跨 effort 级别的比较。

- **理解你的任务形态。** 在[一系列 effort 级别](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence#tune-effort)上测量应用性能，是理解你特定任务成本-性能权衡的有用方式。在一个未饱和的评测上，跨 effort 级别呈现一条平坦的性能-成本曲线，说明该任务并不受思考算力约束；增加 effort 无益。

这种校准通常涉及跨模型、跨 effort 级别跑一次评测。在 Claude Code 里，`/claude-api hillclimb` 会替你进行这项搜索：它把你的评测拆成训练集和测试集，提出配置改动，并读取失败的训练样例来修正它所发现的问题。

我们在一个客户支持基准上运行它，从 Opus 4.8 及其默认（高）effort 起步。爬山器首先尝试 Opus 5 的低 effort，施加 prompt-audit 来移除强制工具调用仪式、scratchpad 步骤和相互矛盾的规则。这在 98.9% 的训练准确率下越过了 Opus 4.8 的基线，并把成本降到每票 2.6 美分。

图 6。爬山通过更新模型选择、effort 和 prompt，改善了成本与性能。

随后它下探到 Sonnet 5 的低 effort，每票 1 美分、更便宜，但准确率跌到 88.9%。阅读那些失败的训练工单，Claude 往 prompt 里加了路由规则和一道退款上限交叉引用，把 Sonnet 5 以同样的成本拉回到 98.9%。

在搜索从未见过的 14 张留出工单上，最终配置得 90.5%，而原始设置为 78.6%，成本约只有五分之一。

## **自动化成本削减**

Prompt 缓存、指令和 effort 是降本的常见杠杆。我们的[文档](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence#cut-spend-without-losing-quality)涵盖了更多。要对使用 Claude API 的应用代码做一次全面的成本审计，我们加入了 `/claude-api cost-optimize`：它剖析你的支出流向何处、施加成本削减，并（若你提供一份评测）展示节省与性能之间的取舍。

`cost-optimize` 先从找出你的 token 去向开始：若你有 Claude Admin API 密钥，则来自你组织的[用量与成本报告](https://platform.claude.com/docs/en/manage-claude/usage-cost-api)；若你的应用记录了每个 API 响应上的 usage 对象，则来自那里；若两者皆无，则通过阅读你构建请求的代码来估算。

随后它把可用的节省排序，从 prompt 缓存开始、精简每个请求所携带的内容（包括一次 prompt-audit）、界定输出，以及用[批处理](https://platform.claude.com/docs/en/build-with-claude/batch-processing)处理无人值守的工作。若你提供一份评测，它会更进一步，跨 effort 级别和模型选择计算成本与性能。

我们在四个公开基准上运行了它，以 Opus 5.5 作为基线起步（图 7）：

- **LegalBench**（成本低约 67%）：`cost-optimize` 找到一个缓存 prompt 一部分的机会，设低 effort，并通过成本更低的 [Batch API](https://platform.claude.com/docs/en/about-claude/pricing) 处理任务。思考 token 降了约 84%，准确率变动不到一分，成本降了约 67%。

- **tau2-bench retail**（成本低约 73%）：`cost-optimize` 发现约 93% 的 prompt 可被缓存，在不改变通过率的情况下把支出削减约 73%。

- **OfficeQA Pro**（成本低约 72%）：`cost-optimize` 应用了 [Batch API](https://platform.claude.com/docs/en/about-claude/pricing)，并把超大的文档精简到最相关的章节，在分数无显著变化的情况下把成本降低约 72%。

- **SWE-bench Verified**（成本低约 24%）：`cost-optimize` 发现 prompt 缓存已经应用，因此节省来自把 effort 设为 medium，并把 agent 的输出约束为几句简洁的话。两者合起来把成本降低了约 24%。

图 7 | 用 /claude-api cost-optimize 跨基准的成本与性能变化。

## **如何开始**

当你已经迁移到一个前沿 Claude 模型、想对照它检查你现有的 prompt 时，从 `/claude-api prompt-audit` 开始。它扫描你工作目录里的 prompt、skills 和工具体描述。这可以是调用 Claude API 的应用代码，或 Claude Code 的配置（CLAUDE.md、skills）。它会移除妨碍前沿模型的常见反模式。

当你的应用使用 Claude API、你想要一份成本审计时，用 `/claude-api cost-optimize`。它剖析 token 支出，然后测试不同的杠杆：它应用 prompt-audit，同时也检查通过 prompt 缓存、批处理无人值守工作或界定输出来降本的办法。若你提供一份评测，它会衡量 effort 和模型选择的取舍。

最后，用 `/claude-api hillclimb` 对成本和性能做迭代搜索。给定一份评测，Claude 把它拆成训练集和测试集，然后提出旨在降低成本、同时保持基线性能的应用更新。Claude 读取失败的训练案例来引导搜索，最终配置在留出的测试集上评分。
