# 长时段应用开发的 harness 设计

发布于 2026 年 3 月 24 日

在 agentic 编码的前沿，harness 设计是性能的关键。以下是我们如何让 Claude 在前沿设计、以及长时段自主软件工程上更进一步。

*本文由我们 [Labs](https://www.anthropic.com/news/introducing-anthropic-labs) 团队的成员 Prithvi Rajasekaran 撰写。*

过去几个月，我一直在处理两个相互关联的问题：让 Claude 产出高质量的前沿设计，以及让它在无人干预下构建完整应用。这项工作源自我们早先在[前端设计 skill](https://github.com/anthropics/claude-code/blob/main/plugins/frontend-design/skills/frontend-design/SKILL.md)和[长时段编码 agent harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)上的努力——我和我的同事通过 prompt 工程和 harness 设计，把 Claude 的性能提升到了远超基线的水平——但两者最终都撞了墙。

要突破，我寻找在两个相当不同的领域之间都能成立的新 AI 工程方法——一个由主观品味定义，另一个由可验证的正确性和可用性定义。受[生成对抗网络](https://en.wikipedia.org/wiki/Generative_adversarial_network)（GAN）启发，我设计了一个带**生成器**和**评估器** agent 的多 agent 结构。构建一个能可靠地——且带品味地——给输出打分的评估器，意味着先要发展出一套能把「这个设计好吗？」这类主观判断转化为具体、可打分措辞的标准。

随后我把这些技术用到长时段自主编码上，沿用我们早先 harness 工作的两条经验：把构建分解成可处理的块，以及用结构化产物在会话之间交接上下文。最终成果是一个三 agent 架构——规划者、生成器、评估器——能在长达数小时的自主编码会话中产出丰富的全栈应用。

## 为什么朴素实现力有不及

我们此前已展示过，harness 设计对长时段 agentic 编码的有效性有重大影响。在早先一个[实验](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)里，我们用一个初始化器 agent 把产品规格分解成任务清单，以及一个编码 agent 一次实现一个功能、在交接产物时携带跨会话的上下文。更广泛的开发者社区也收敛到类似的洞见，像「[Ralph Wiggum](https://ghuntley.com/ralph/)」方法用 hook 或脚本让 agent 保持持续迭代循环。

但有些问题始终存在。对更复杂的任务，agent 随时间仍会脱轨。在分解这一问题时，我们观察到 agent 执行这类任务时有两种常见失败模式。

首先是模型在长任务上容易随上下文窗口填满而失去连贯（见我们关于[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)的文章）。有些模型还表现出「上下文焦虑」，即当它们接近自己认为的上下文极限时，会开始提前收尾工作。上下文重置——彻底清空上下文窗口、起一个新 agent，配合一个把上一 agent 的状态和下一步带过来的结构化交接——能同时应对这两个问题。

这不同于压缩（compaction），后者就地把对话较早的部分做摘要，让同一个 agent 能靠一段缩短的历史继续。虽然压缩维持了连续性，它却没有给 agent 一块干净的板子，这意味着上下文焦虑仍会残留。重置则提供一块干净的板子，代价是交接产物得带足够的上下文，让下一个 agent 能干净地接手工作。在我们早先的测试中，我们发现 Claude Sonnet 4.5 表现出的上下文焦虑之强，单靠压缩不足以支撑强劲的长任务表现，于是上下文重置成了 harness 设计的关键所在。这解决了核心问题，但给每次 harness 运行增添了编排复杂性、token 开销和延迟。

第二个我们此前未曾处理的问题，是自我评估。当被要求评估自己产出的工作时，agent 往往以自信地称赞该工作来回应——即便在一位人类观察者看来，质量显然平庸。这一问题是对于像设计这样主观的任务尤为突出，那里没有等价于可验证软件测试的二元检查。一个布局感觉精致还是泛泛，是一个判断问题，而 agent 在给自己的工作打分时会可靠地偏向正面。

然而，即便在那些确有可验证结果的任务上，agent 有时仍表现出会阻碍其完成任务时性能的糟糕判断。把做工作的 agent 与评判它的 agent 分开，被证明是应对这一问题的一大杠杆。这种分离本身并不能立刻消除那种宽纵；评估器终究还是一个对 LLM 生成输出倾向于宽容的 LLM。但把一个独立的评估器调优得怀疑，比起让一个生成器对自己工作持批判态度要容易处理得多，而一旦那份外部反馈存在，生成器就有了一个具体的东西去迭代。

## 前端设计：让主观质量可打分

我从前端设计上做实验入手，那里自我评估的问题最可见。在没有任何干预下，Claude 通常会倒向安全、可预测的布局——技术上管用、视觉上却平淡无奇。

有两个洞见塑造了我前端设计所建的 harness。第一，虽然审美无法被完全化约为一个分数——个人品味总会不同——但它们能用编码了设计原则和偏好的打分标准来改进。「这个设计美吗？」难以一致地回答，但「它遵循我们关于好设计的原则吗？」给了 Claude 一个具体的东西去对照打分。第二，通过把前端生成与前端评分分离，我们能创造一个驱动生成器走向更强输出的反馈回路。

牢记这一点，我写了四条打分标准，并把它们给到生成器和评估器 agent 的 prompt 里：

- **设计质量：** 这个设计是否感觉像一个连贯的整体，而非一堆零件的拼凑？这里的强工作意味着色彩、字体排印、布局、图像和其他细节共同营造出一种独特的气质和身份。
- **原创性：** 是否有定制决策的证据，还是这是模板布局、库默认值和 AI 生成套路？一位人类设计师应能认出刻意的创意选择。未经改动的现成组件——或 AI 生成的典型标志，如白卡片上的紫色渐变——在这里不及格。
- **工艺：** 技术执行：字体层次、间距一致性、色彩和谐、对比度。这是一项能力检查，而非创造力检查。多数合理的实现默认在这里做得不错；不及格意味着基础崩坏。
- **功能性：** 独立于美学的可用性。用户能否理解界面做什么、找到主操作、并在不猜的情况下完成任务？

我在工艺和功能性之上强调了设计质量和原创性。Claude 默认在工艺和功能性上得分就不错，因为所需的技术能力往往对模型来说是自然而然的。但在设计和原创性上，Claude 常常产出至多乏味的输出。这些标准明确惩罚高度泛泛的「AI 套路」模式，并通过对设计和原创性赋予更高权重，把模型推向更有冒险性的审美。

我用带详细分数细分的 few-shot 示例来校准评估器。这确保了评估器的判断与我的偏好对齐，并减少跨迭代的分数漂移。

我在 [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 上构建这个循环，它把编排保持得简明。一个生成器 agent 先根据用户 prompt 创建一个 HTML/CSS/JS 前端。我给评估器配了 Playwright MCP，让它能在给每条标准打分、并撰写详细批评之前，直接与实时页面交互。实践中，评估器会自行浏览页面、截图并仔细研究这个实现，然后产出它的评估。那份反馈作为下一次迭代的输入流回生成器。我为每次生成跑 5 到 15 次迭代，每一次迭代通常随着生成器回应评估器的批评，把它推向更有辨识度的方向。因为评估器在主动浏览页面、而非给一张静态截图打分，每个循环都要花真实的时钟时间。完整运行最长拖到四个小时。我还指示生成器在每次评估后做一个战略性决定：若分数走势向好就打磨当前方向，若那套办法行不通就转向一种完全不同的美学。

跨各次运行，评估器的评估在趋于平缓之前随迭代改善，仍有空间。有些生成是渐进地打磨。另一些在迭代之间来了一次审美的急转弯。

标准的措辞以我未曾完全预料的方式引导着生成器。纳入像「最好的设计是博物馆级的」这样的短语，把设计推向某种视觉上的趋同，表明与标准相关的 prompt 直接塑造了输出的性格。

虽然分数通常随迭代提升，模式并不总是干净的线性。后来的实现在整体上往往更好，但我常看到我更喜欢中间某次迭代而非最后一次的情形。实现的复杂性也倾向于跨轮增加，生成器为回应评估器的反馈而伸手去取更有雄心的解法。即便在第一次迭代上，输出也比完全无 prompt 的基线明显更好，这表明标准及其相关语言本身，就在评估器反馈带来进一步打磨之前，就把模型从泛泛的默认值上引开了。

在一个值得注意的例子中，我 prompt 模型为一家荷兰艺术博物馆创建一个网站。到第九次迭代，它为一个虚构博物馆产出了一个干净、暗色调的落地页。页面视觉精致，但大体不出我的预期。然后，在第十个循环，它彻底推翻了那套做法、把网站重新构想成一种空间体验：一间带棋盘格地板、用 CSS 透视渲染的 3D 房间，画作以自由形式挂在墙上，以及画廊房间之间基于门口的导航，而非滚动或点击。那是我此前从未在一次成型生成中见过的创意飞跃。

## 扩展到全栈编码

有了这些发现，我把这一 GAN 启发的模式应用到全栈开发上。生成器-评估器循环天然映射到软件开发生命周期，那里代码审查和 QA 扮演着与设计评估器相同结构性的角色。

### 架构

在我们早先的[长时段 harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)里，我们用初始化器 agent、一次做一个功能的编码 agent、以及会话之间的上下文重置，解决了连贯的多会话编码。上下文重置是一个关键的解锁：那个 harness 用了 Sonnet 4.5，它表现出前面提到的「上下文焦虑」倾向。创建一个能跨上下文重置良好工作的 harness，是让模型保持专注任务的关键。Opus 4.5 在很大程度上自行消除了那一行为，于是我得以从这个 harness 里彻底去掉上下文重置。agent 作为贯穿整个构建的一个连续会话来运行，由 [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 的自动压缩处理一路上的上下文增长。

对这项工作，我在原 harness 的基础上构建了一个三 agent 系统，每个 agent 应对我在先前运行中观察到的一个特定缺口。系统含以下 agent 人设：

**规划者：** 我们先前的长时段 harness 要求用户事先提供一份详细规格。我想自动化那一步，于是创建了一个规划者 agent，它把简单的 1-4 句 prompt 扩展成一份完整的产品规格。我 prompt 它对范围要有雄心，并聚焦在产品上下文和高阶技术设计上，而非细致的技术实现。这一强调是出于这样一种顾虑：如果规划者试图事先指定细粒度的技术细节并且出了错，规格里的错误会级联进下游实现。更聪明的做法似乎是约束 agent 于要交付的成果物、让它们在工作中自行找出路径。我也请规划者寻找把 AI 功能织入产品规格的机会。（示例见文末附录。）

**生成器：** 早先 harness 里一次做一个功能的方法对范围管理很奏效。我在这里应用了类似的模型，指示生成器按 sprint 工作，每次从规格里挑一个功能。每个 sprint 用一个 React、Vite、FastAPI 和 SQLite（后来 PostgreSQL）的技术栈实现应用，而生成器被指示在交给 QA 之前、于每个 sprint 末尾自我评估它的工作。它也有 git 做版本控制。

**评估器：** 早先 harness 的应用看起来惊艳，但当你真去用时仍有真实的 bug。为抓住这些，评估器用 Playwright MCP 像用户那样点击穿过运行中的应用，测试 UI 功能、API 端点和数据库状态。随后它对照它发现的 bug、以及一组仿照前端实验而在此改编以覆盖产品深度、功能性、视觉设计和代码质量的标准，为每个 sprint 打分。每条标准都有一个硬阈值，若任何一条低于它，该 sprint 失败，生成器会得到关于哪里出错的详细反馈。

在每个 sprint 之前，生成器和评估器协商一份 sprint 契约：在任何代码写之前就为那个工作块商定「完成」长什么样。它的存在是因为产品规格是刻意高阶的，而我想有一步来弥合用户故事与可测试实现之间的缺口。生成器提议它要建什么、成功如何被验证，评估器审阅那份提议以确保生成器在建正确的东西。两者迭代直到它们达成一致。

沟通经由文件处理：一个 agent 写一个文件，另一个 agent 读它、或在那份文件里、或用上一 agent 会转而阅读的新文件来回应。生成器随后对照商定好的契约来构建、再把工作交接给 QA。这让工作忠于规格、又不过早地把实现规定得太细。

### 运行 harness

对于这个 harness 的第一个版本，我用 Claude Opus 4.5，拿用户 prompt 同时跑完整 harness 和单 agent 系统做对比。我用 Opus 4.5，因为在我开始这些实验时它是最好的编码模型。

我写了下面这道 prompt 来生成一个复古游戏制造器：

> 创建一个 2D 复古游戏制造器，带有关卡编辑器、精灵编辑器、实体行为和一个可玩的测试模式等功能。

下面的表展示 harness 类型、它运行了多久、以及总成本。

| **Harness** | **时长** | **成本** |
| --- | --- | --- |
| 单干 | 20 分钟 | 9 美元 |
| 完整 harness | 6 小时 | 200 美元 |

harness 贵了 20 倍以上，但输出质量的差别一目了然。

我期待的是一个界面，我能在其中构建一个关卡及其组成部件（精灵、实体、瓦片布局），然后点播放真正去玩那个关卡。我从打开单干运行的输出来开始，初始应用似乎符合那些预期。

然而随着我点穿各页，问题开始浮现。布局浪费空间，固定高度的面板把大部分视口留着空着。工作流死板。试图填充一个关卡时，它提示我先创建精灵和实体，但界面里没有任何东西引导我去向那个顺序。更关键的是，那个实际的游戏是坏的。我的实体出现在屏幕上，却没有任何东西响应输入。深入代码发现，实体定义与游戏运行时之间的接线是断的，没有任何界面迹象指出断在哪。

评估完单干运行后，我把注意力转向 harness 运行。这次运行从同一句 prompt 起步，但规划步骤把那句 prompt 扩展成一份横跨十个 sprint、含 16 个功能的规格。它远超单干运行所尝试的。除了核心编辑器和播放模式，规格还要求一套精灵动画系统、行为模板、音效和音乐、一个 AI 辅助的精灵生成器和关卡设计器，以及带可分享链接的游戏导出。我给了规划者访问我们[前端设计 skill](https://github.com/anthropics/claude-code/blob/main/plugins/frontend-design/skills/frontend-design/SKILL.md)的权限，它读了并用来在规格里为应用创建一种视觉设计语言。对每个 sprint，生成器和评估器协商一份契约，定义该 sprint 具体的实现细节、以及将被测试以验证完成的可测试行为。

应用立刻展现出比单干运行更多的精致和平滑。画布用满了视口，面板尺寸合理，界面有一种追踪规格里设计方向的连贯视觉身份。我在单干运行里看到的一些笨拙仍在——工作流仍没把「应先建精灵和实体、再去填充关卡」说清楚，我不得不靠摸索去搞明白。这读起来是底层模型产品直觉上的缺口，而非 harness 被设计来应对的东西，尽管它确实指出了在 harness 内部做有针对性迭代能进一步改善输出质量的一个地方。

穿过各编辑器，新运行相对单干的优势愈发明显。精灵编辑器更丰富、功能更全，有更干净的工具面板、更好的拾色器和更可用的缩放控制。

因为我请规划者把 AI 功能织进规格，应用也自带一个 Claude 集成，能让我通过 prompt 生成游戏的不同部分。这显著加快了工作流。

最大的差别在播放模式。我实际能移动我的实体、玩游戏了。物理有一些粗糙之处——我的角色跳上一个平台、却最终与它重叠，这在直觉上感觉不对——但核心的东西能用了，这是单干运行没能做到的。移动了一会儿后，我遇到了 AI 关卡构建的一些局限。有一堵我没能跳过的大墙，于是我被困住了。这表明有一些常识性的改进和边缘情形，是 harness 能处理、以进一步打磨应用的。

通读日志，很清楚评估器让实现保持在规格之内。每个 sprint，它穿过 sprint 契约的测试标准、并用 Playwright 演练运行中的应用，对任何偏离期望行为的东西提 bug。契约很细——光 Sprint 3 就有 27 条标准覆盖关卡编辑器——而评估器的发现足够具体、不需额外调查即可行动。下面的表展示了我们评估器识别出的若干问题例子：

| **契约标准** | **评估器发现** |
| --- | --- |
| 矩形填充工具允许点击拖拽以用选中的瓦片填充一个矩形区域 | **FAIL** — 工具只在拖拽的起点/终点放置瓦片，而非填充区域。`fillRectangle` 函数存在但在 mouseUp 时未被正确触发。 |
| 用户能选择并删除已放置的实体生成点 | **FAIL** — `LevelEditor.tsx:892` 处的 Delete 键处理器要求 `selection` 和 `selectedEntityId` 都被设置，但点击一个实体只设了 `selectedEntityId`。条件应为 `selection \|\| (selectedEntityId && activeLayer === 'entity')`。 |
| 用户能通过 API 重排动画帧 | **FAIL** — `PUT /frames/reorder` 路由定义在 `/{frame_id}` 路由之后。FastAPI 把 'reorder' 当作一个 frame_id 整数来匹配并返回 422：「无法把字符串解析为整数」。 |

要让评估器达到这一水准的运作，费了一番功夫。开箱即用，Claude 是一个糟糕的 QA agent。在早期运行里，我看着它识别出合理的问题，然后说服自己那些没什么大不了、照单批准了工作。它也倾向于肤浅地测试、而非探查边缘情形，于是更微妙的 bug 常溜过。调优循环就是读评估器的日志、找它判断与我分歧的例子、并更新 QA 的 prompt 来解决那些问题。这一开发循环转了好几轮，评估器才以我认可合理的方式打分。即便如此，harness 输出仍显示出模型 QA 能力的局限：小的布局问题、某些地方感觉不直观交互、以及评估器没彻底演练过的更深层嵌套功能里未被发现的 bug。还有明显的验证空间可用进一步调优来榨取。但和单干运行相比——那里应用的核心功能干脆不能用——这一提升显而易见。

### 迭代 harness

第一组 harness 结果令人鼓舞，但也笨重、慢、昂贵。下一个合逻辑的步骤，是找到在不劣化其性能的前提下简化 harness 的办法。这部分是常识、部分是一个更普适原则的体现：harness 里的每个组件都编码了一个关于模型独自做不到的假设，而那些假设值得压力测试，既因为它们可能是错的，也因为随着模型改进它们会很快变得陈旧。我们的博客文章[构建高效的 agent](https://www.anthropic.com/research/building-effective-agents)把这一底层思想表述为「找到尽可能简单的解法，只在需要时才增加复杂度」，而对任何维护 agent harness 的人来说，这一模式都会不断重现。

在我简化第一版的尝试中，我把 harness 大幅削减并试了几样有创意的新点子，但我没能复现原版的表现。也变得难以判断 harness 设计里哪些部件实际上是承重的、以何种方式承重。基于那经验，我转向更有条理的方法，一次移除一个组件、并检视它对最终结果的影响。

在我跑这些迭代循环的同时，我们也发布了 Opus 4.6，它为削减 harness 复杂性提供了进一步的动机。有充分的理由预期 4.6 会比 4.5 需要更少的脚手架。从我们的[发布博客](https://www.anthropic.com/news/claude-opus-4-6)：「[Opus 4.6] 更周密地规划、把 agentic 任务维持得更久、能在更大的代码库里更可靠地运作，并有更好的代码审查和调试技能来抓住自己的错误。」它在长上下文检索上也有大幅改进。这些全都是 harness 曾被建来补足的能力。

### 移除 sprint 构造

我从彻底移除 sprint 构造开始。sprint 结构曾帮助把工作分解成模型能连贯工作的块。鉴于 Opus 4.6 的改进，有充分的理由相信模型能原生地胜任这一工作、而不需要这种分解。

我保留了规划者和评估器，因为各自持续增添明显的价值。没有规划者，生成器会低估范围：拿原始 prompt，它会不先给工作做规格就开建、最终建出一个功能不如规划者所产那么丰富的应用。

移除 sprint 构造后，我把评估器改为运行末尾的一次性处理、而非按 sprint 打分。既然模型能力强得多，它改变了评估器在某些运行上的承重程度，其有用性取决于任务相对于模型能可靠独力做到的处于何处。在 4.5 上，那条边界很近：我们的构建处在生成器能独力做好的边缘，而评估器在构建各处捕捉有意义的问题。在 4.6 上，模型的原始能力提升了，于是那条边界向外移。过去需要评估器检查才能被连贯实现的任务，如今常常落在生成器独力就能做好的范围内，而在那条边界之内的任务上，评估器成了不必要的开销。但对于构建里仍在生成器能力边缘的那些部分，评估器持续给予真正的提升。

实际的含义是：评估器不是一个固定的是或否决定。当任务处在当前模型独力做不稳的范畴之外时，它值那点成本。

在结构简化的同时，我也加了 prompt 来改进 harness 如何把 AI 功能构建进每个应用，特别是让生成器构建一个能通过工具驱动应用自身功能的像样 agent。那需要真正的迭代，因为相关的知识足够新，Claude 的训练数据对它覆盖稀薄。但经过足够调优，生成器正确地构建了 agent。

### 更新 harness 的结果

为检验更新的 harness，我用下面这道 prompt 生成一个数字音频工作站（DAW），一个用于作曲、录音和混音的音乐制作程序：

> 用 Web Audio API 在浏览器里构建一个功能齐全的 DAW。

这次运行仍然漫长而昂贵，约 4 小时、124 美元 token 成本。

多数时间花在了构建器上，它在没有 Opus 4.5 所需的 sprint 分解的情况下连贯地运行了两个小时以上。

| **Agent 与阶段** | **时长** | **成本** |
| --- | --- | --- |
| 规划者 | 4.7 分钟 | 0.46 美元 |
| 构建（第 1 轮） | 2 小时 7 分钟 | 71.08 美元 |
| QA（第 1 轮） | 8.8 分钟 | 3.24 美元 |
| 构建（第 2 轮） | 1 小时 2 分钟 | 36.89 美元 |
| QA（第 2 轮） | 6.8 分钟 | 3.09 美元 |
| 构建（第 3 轮） | 10.9 分钟 | 5.88 美元 |
| QA（第 3 轮） | 9.6 分钟 | 4.06 美元 |
| **V2 harness 总计** | **3 小时 50 分钟** | **124.70 美元** |

与先前的 harness 一样，规划者把一行 prompt 扩展成一份完整规格。从日志看，我能看到生成器模型很好地规划了应用和 agent 设计、把 agent 接好线、并在交给 QA 之前测试了它。

话虽如此，QA agent 仍抓住了真实的缺口。在它第一轮的反馈里，它指出：

> 这是一个设计保真度出色、AI agent 扎实、后端不错的强应用。主要的失败点在功能完整性上——虽然应用看起来惊艳、AI 集成也好用，但几个核心 DAW 功能是仅显示而无交互深度的：clip 无法在时间轴上拖拽/移动，没有乐器 UI 面板（合成旋钮、鼓垫），也没有可视的效果器编辑器（EQ 曲线、压缩表）。这些不是边缘情形——它们是让一个 DAW 可用的核心交互，而规格明确要求它们。

在它第二轮的反馈里，它又一次抓住了若干功能缺口：

> 遗留缺口：- 音频录制仍是桩函数（按钮会切换但不采集麦克风）- clip 边缘拖拽缩放和 clip 切分未实现- 效果可视化是数字滑块，而非图形（没有 EQ 曲线）

当放任自流时，生成器仍会漏掉细节或对功能写桩函数，而 QA 在抓住那些最后一公里的问题让生成器修复上，仍在增添价值。

基于这道 prompt，我期待的是一个我能创作旋律、和声、鼓点、把它们排列成一首歌、并在过程中得到集成 agent 帮助的程序。下面的视频展示了结果。

但最终应用有了一个可用音乐制作程序的所有核心部件：一个在浏览器里工作的编排视图、混音器和走带控制。在那之外，我能够完全靠 prompt 拼出一小段歌曲片段：agent 设定了速度和调、铺下一条旋律、建了一轨鼓、调了混音器电平、并加了混响。歌曲作曲的核心原语都在，而 agent 能自主地驱动它们，用工具从头到尾做一个简单的制作。你可以说它尚未音准完美——但它正朝那里去。

## 接下来

随着模型持续改进，我们大体可以预期它们能工作更久、处理更复杂的任务。在某些情形里，那意味着围绕模型的脚手架随时间不那么重要，开发者可以等下一款模型、看着某些问题自行解决。而在另一些情形里，模型越好，就有越多空间去开发能完成超出模型基线能力之复杂任务的 harness。

牢记这一点，这项工作里有几条值得带下去的经验。用你所构建针对的那个模型做实验、读它在真实问题上的 trace、并调优它的表现以达成你想要的结果，永远是好的实践。在处理更复杂的任务时，通过分解任务、并把专门的 agent 应用到问题的各个方面，有时会有空间。而当一款新模型落地，通常的好实践是重新审视 harness，剥除那些不再承重的部件、并加入新部件以获得此前或许无法企及的更大能力。

从这项工作，我的信念是：有趣的 harness 组合空间并不随模型改进而收缩。相反，它会移动，而对 AI 工程师来说有趣的工作，是不断找到下一个新颖的组合。
