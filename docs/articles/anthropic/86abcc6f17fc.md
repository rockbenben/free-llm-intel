## AI 正在演化 CI

Anthropic 的工程师平均每季度提交的代码量，是 2021-2025 年的 [8 倍](https://www.anthropic.com/institute/recursive-self-improvement)。Claude 撰写了[其中 80% 的代码](https://www.anthropic.com/institute/recursive-self-improvement)，并在[审阅和批准 PR 上也扮演重要角色](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)。

写代码不再是要害，而一旦 PR 审阅被加速，CI 就开始感受到压力。

除此之外，我们代码库里的测试数量增长了 10 倍，而新增工程师只是名义上的。这一切导致六个月内 CI 任务增长 25 倍（如果你在试图算这笔账：并非每个测试都会在每个 PR 上运行，我稍后会解释）。

这几次威胁到要把我们的测试影响分析服务压垮。为了避免成为下一个瓶颈，我们把整个东西推倒重来、重新想象了这个服务的架构长什么样。但走到那一步是一条颠簸的路，始于三次快速修复，它们分别只维持了 70 天、29 天，然后不到一天。

随着 agent 持续加速代码生成和审阅，扩展 CI 是更多工程团队可能很快会面临的挑战。我预计水平扩展的测试选择架构会成为行业标准，因为运行 agent 的团队会同时造出更多 PR 和更多测试。

在本文里，我会讨论我们如何在 Anthropic 扩展测试影响分析服务，以及我吃过的苦头换来的教训：永远为指数曲线做规划。具体的扩展技术——买更大的机器、把进程并行化、或重启服务（是的，这招至今仍出奇地管用）——都很常见，**而它们并不是本文真正要传达的洞见。**

要点是：这些技术里每一种买到的时间，都只是它们一年前所能买到的一小部分。另一方面，彻底翻新并完全重新设计一个服务，如今也只花费一小部分时间、也更可持续，因为写代码不再是瓶颈了。

你越能预判这种压力、并规划你的架构将如何随之演化，你就越少在半吊子措施上浪费时间。

## 测试影响分析的架构

我的许多同行所在的组织，至今仍会在每次变更上运行**每一个**测试。这在一定程度上管用，但无法扩展：CI 关卡变得越来越长、越来越贵、越来越不可信。

此外，人类很擅长判断哪些测试失败与自己无关，而 agent 需要更多上下文和指导。当它们拿到一组特定的有效测试时，就能更有效地自我验证和迭代。

在 Anthropic，我们构建了一个确定性的测试影响分析、或测试选择服务，它基于过往表现和包相关性来决定每次变更上运行哪些测试。这并非罕见做法，有一类供应商在这个领域提供产品。

我们的服务依赖于两个确定性组件保持同步：

- 一个「监听器（listener）」，记录每一次 CI 运行的测试结果。
- 一个「选择器（selector）」，读取测试结果历史，并决定哪些测试在哪些打开的 PR 上运行。

这很有效，但当每秒有多个 CI 任务在运行时，监听器就开始越来越落后于 PR 队列。对一个 [AI 原生的 SDLC](https://claude.com/blog/the-ai-native-sdlc-playbook) 而言，一点延迟都可能造成巨大影响。例如，20 分钟的监听器延迟，可能意味着数以万计的测试更新没被应用到选择器上。

- **如果一个坏变更被合并**，那么一个测试就会开始对所有其他人失败，引发多次不必要的调查。
- **如果一个依赖开始抖动（flaky）**，那么抖动的红灯就开始阻塞合并。
- **如果一个测试被修好或新增了一个**，在监听器赶上之前它不会运行，从而冒回归的风险。

这一切作为单个进程运行，因为要为每个测试维持一份连续的历史，就需要单个写入者来应用结果。这个 v0 设计使我们无法做水平分片。

## 通往重建的颠簸之路

到去年十月，这个服务已经显示出吃力的迹象，我们连续两天被呼叫。

### 补丁 1：一台更大的机器

第一个修复很简单：我们把运行服务的核心数翻倍。我们也知道这会转瞬即逝。

对话基于真实事件重现。

即使趋势线一目了然，归属却模糊不清。没人愿意再认领一块基础设施。而且 CI 团队有更大的鱼要煎。

### 补丁 2：分片

到这一步，我们经常因为这个服务监听器累积的延迟而被呼叫。为了推动一些长期修复，我在一个内部版本的 Claude Tag 里开了一个长时运行的会话，专门监控这个服务。每当监听器落后超过 50,000 个任务，Claude 就会 ping 我、并把我们就下一步的对话继续下去。

这持续了好几个月，而不必反复向它提醒过去的努力或上下文，这很有帮助。Claude 常常主张大改，但我们通常还是定在另一个补丁上。

在内部版本 Claude Tag 上的逐字对话，做了一些删减。

二月，CI 任务的指数增长开始再次让这个服务吃力。这次我们决定并行化。

监听器并不需要单个写入者来正确给测试结果排序，它需要每个包一个写入者，来正确为我们代码库每一部分的测试结果排序。Claude 为我们生成了代码，把每个包的状态切进一个带自己 worker 的 shard。

我们也知道这个修复会转瞬即逝，但我们没料到它只能给我们买 29 天。

### 补丁 3：每日重启

三月，这个进程在多数工作日午后就达到了内存上限。同样，我们寻找快速修复，但：

- 我们只找到了四个 bug。
- 把内存分配器换掉作为权宜之计毫无作用。我们试图优化垃圾回收，但那并不是真正的解法。
- 我们不想冒在一个已重载的单例上做内存分析的风险。
- 重启给我们买的不足一天。

我们还发现，每日重启导致服务逐渐越落越远。当它落后超过一小时——这发生了好几次——大量任务结果没被监听器记录。

需要澄清的是，这并不意味着 CI 从未在那些 PR 上运行，或未经测试的代码被推上了生产。它的意思是监听器没拾取到某些结果，意味着我们的测试选择组件在用陈旧数据来决定 PR 上什么该跑、什么不该跑。多数情况下，这转化为我们去运行那些本已极度抖动、或普遍全线失败的测试。

### 重新设计

是（早就）时候重新设计这个服务了，我们采纳了 Claude 的建议：给测试选择服务一个数据库——准确说是一个内存数据存储。通过这样做，我们有效地把单例过去所做的一大块内存处理卸载了出去。

现在，任何监听器 worker 都能处理任何结果，把它追加到内存存储里的一份日志（journal）中，然后继续，而不在内存里持有任何东西——无状态，因而可水平扩展。一个独立的小型消费者进程每几秒把日志汇总进按测试的历史，而选择器能迅速查找到相关的结果历史。

这种分布式架构运行起来更贵，但相比一个摇摇欲坠的单例，它扩展和内存分析都容易得多。这个项目单个工程师花了三周。一年前它会接近一个季度。

排队、未处理的任务结果事件，每小时峰值。此前：积压多数日子都在形成、并逐周增长。切换并调优之后：持平。

有一些微调（日志的大小和 worker 的数量），Claude 大体自主完成了，但我们的服务自此一直保持稳定。

## 我会做的不同之处

如果把我送回 2025 年 10 月，用我现在知道的东西，我会用不同的方式处理这个以及其他项目。

第一个不同是，我会把 AI 的指数曲线考虑进来。随着每位工程师平均 agent 数上升、随着加速的 PR 批准变得更成熟，CI 任务呈指数增长。

这随时间在 Anthropic 改变了 PR 的形态，因为 Claude 偏好更小、更细粒度的 PR（又一个不要对每个 PR 跑每个测试的好理由）。这转化为一天里更多 CI 任务。而且，随着 agent 在夜间和周末推送，活动量的下限被抬高了，但它仍是阵发性的，因为人类工程师仍驱动和批准了相当多的 PR。

我给工程团队的建议是，无论你是自建还是外购，假设你的架构在两个季度内就会处在 25 倍的负载下。「过度设计」这个概念开始略微褪色，或者至少门槛正被抬得高得多。现在你可以在 v0 设计里开始考虑你感知规模的 10-20 倍——只要你的预算允许。

给你的服务装上仪表，让它们充当 Claude 的眼睛和耳朵。它能让 Claude 比我们手动地更好地、更快地爬山式增量修复问题。特别要确保：进来的 CI 任务数量，与出去的数量相等。

从一开始就把状态留在进程之外。我也会避免把任何关键服务作为单实例运行——除非你能度量它以及任何金丝雀变更。CI 演化得太快，不容用别的方式推进。
