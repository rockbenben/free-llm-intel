# 关于近期 Claude Code 质量报告的更新

发布于 2026 年 4 月 23 日

我们把近期关于 Claude Code 质量问题的报告，追溯到了三项独立的改动。这里发生了什么、以及我们要做什么改变。

过去一个月，我们一直在调查关于 Claude 对某些用户的回复有所恶化的反馈。我们把这些报告追溯到了三项独立改动，它们分别影响了 Claude Code、Claude Agent SDK 和 Claude Cowork。API 未受影响。

截至 4 月 20 日（v2.1.116），全部三个问题都已解决。

在本文里，我们解释我们发现了什么、修好了什么，以及我们会做哪些不同的事，以确保类似问题再发生的概率大大降低。

我们极其认真地对待关于质量下降的报告。我们从不故意降低模型质量，而且我们得以立刻确认我们的 API 和推理层未受影响。

经调查，我们定位了三个不同的问题：

- 3 月 4 日，我们把 Claude Code 的默认推理 effort 从 `high` 改为 `medium`，以降低某些用户在 `high` 模式下看到的极长延迟——长到让界面看起来像卡死。这是个错误的权衡。4 月 7 日我们回滚了这一改动，因为用户告诉我们，他们宁愿默认更高智能、对简单任务主动选择更低 effort。这影响了 Sonnet 4.6 和 Opus 4.6。
- 3 月 26 日，我们上线了一项改动：从闲置超过一小时的会话里清除 Claude 较早的思考，以降低用户恢复这些会话时的延迟。一个 bug 导致它在会话余下的每一轮都持续发生，而不是一次，这让 Claude 显得健忘而重复。我们于 4 月 10 日修复。这影响了 Sonnet 4.6 和 Opus 4.6。
- 4 月 16 日，我们往系统 prompt 里加了一条降低冗长度的指令。它与其他 prompt 改动结合起来，损害了编码质量，并于 4 月 20 日被回滚。这影响了 Sonnet 4.6、Opus 4.6 和 Opus 4.7。

因为每项改动在不同时间以不同方式影响不同比例的流量，综合起来看起来像广泛而不一致的质量下降。虽然我们三月初就开始调查这些报告，起初它们很难与用户反馈的正常波动区分开，而我们的内部使用和评测一开始都无法复现那些被识别出的问题。

这不是用户应从 Claude Code 得到的体验。截至 4 月 23 日，我们正在重置所有订阅者的用量限制。

## 对 Claude Code 默认推理 effort 的一项改动

二月我们在 Claude Code 里发布 Opus 4.6 时，把默认推理 effort 设为 `high`。

不久之后，我们收到用户反馈：高 effort 模式下的 Claude Opus 4.6 偶尔会思考太久，导致界面看起来卡死、并给这些用户带来不成比例的延迟和 token 用量。

一般而言，模型想得越久，输出越好。effort 级别就是 Claude Code 让用户设定这一权衡的方式——更多思考，对更低延迟和更少触及用量限制。在我们为模型校准 effort 级别时，我们会把这一权衡纳入考量，以便在测试时算力曲线上挑出给人们最佳选择区间的那些点。在产品层，我们随后选择曲线上哪个点作为我们的默认，并把该值作为 effort 参数发给 Messages API；然后我们通过 `/effort` 提供其他选项。

在我们的内部评测和测试中，medium effort 在智能上略低，但对多数任务延迟显著更低。它也不受偶尔思考长尾延迟的那些问题影响，并帮助最大化用户的用量限制。结果，我们推出了把 medium 设为默认 effort 的改动，并通过产品内的对话框解释了理由。

推出后不久，用户开始反馈 Claude Code 显得不那么智能了。我们上线了好几个设计迭代，把当前 effort 设置做得更清晰，以便提醒人们他们可以更改默认（启动时的通知、一个内联的 effort 选择器、以及重新带回 ultrathink），但多数用户仍保留了 medium effort 默认。

在听到更多客户反馈后，我们于 4 月 7 日推翻了这一决定。所有用户如今对 Opus 4.7 默认 `xhigh` effort，对其余所有模型默认 `high` effort。

## 一项丢弃先前推理的缓存优化

当 Claude 通过推理处理一个任务时，那部分推理通常会保留在对话历史里，因此在随后每一轮，Claude 都能看到它为什么做了那些编辑和工具调用。

3 月 26 日，我们上线了一项本意是针对该功能的效率改进。我们用 prompt 缓存让连续背靠背的 API 调用对用户更便宜更快。Claude 在发起 API 请求时把输入 token 写入缓存，然后在一段不活跃之后，该 prompt 被从缓存中赶出，为其他 prompt 腾出空间。缓存利用率是我们仔细管理的某样东西（更多关于我们的[方法](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)）。

设计本该很简单：如果一个会话闲置超过一小时，我们可以通过清除旧的思考板块来降低用户恢复该会话的成本。既然反正请求会是一次缓存未命中，我们可以在请求里剔除不必要的消息，以减少发给 API 的未缓存 token 数量。随后我们本会恢复发送完整的推理历史。为此我们使用了 `clear_thinking_20251015` API 头，配合 `keep:1`。

实现里有一个 bug。它不是一次清除思考历史，而是在会话余下的每一轮都清除。一旦某个会话越过一次闲置阈值，该进程余下的每个请求都告诉 API 只保留最近一段推理、丢弃它之前的一切。这会叠加：如果你在 Claude 正处于工具调用中途时发一条追问，那会在损坏的标志下开启新一轮，于是连当前轮的推理也被丢弃。Claude 会继续执行，但越来越不记得它为什么选择做它正在做的事。这就表现为人们所报告的健忘、重复和奇怪的工具选择。

因为这会持续丢弃后续请求里的思考块，那些请求也导致了缓存未命中。我们相信这就是单独那些「用量限制比预期消耗更快」报告的驱动原因。

两个互不相关的实验起初让我们难以复现这个：一个内部专有的、与消息排队相关的服务端实验；以及一个在如何显示思考方面、与之正交的改动，它在多数 CLI 会话里抑制了这个 bug，以至于我们即便测试外部构建时也没抓到它。

这个 bug 正处于 Claude Code 上下文管理、Anthropic API 和扩展思考的交汇处。它所引入的改动，通过了多道人工和自动代码审查，也通过了单元测试、端到端测试、自动验证和内部试用。加上它只在一个边缘情形（陈旧会话）里发生、以及复现该问题的难度，我们花了一个多星期才定位并确认根因。

作为调查的一部分，我们用 Opus 4.7 对肇事 pull request 回测了[代码审查](https://code.claude.com/docs/en/code-review)。当提供收集完整上下文所必需的代码仓库时，Opus 4.7 找到了这个 bug，而 Opus 4.6 没有。为防止这种事再次发生，我们如今正在为代码审查落地对额外仓库作为上下文的支持。

我们于 4 月 10 日在 v2.1.101 里修复了这个 bug。

## 一项降低冗长度的系统 prompt 改动

我们最新的模型 Claude Opus 4.7，相对其前身有一个值得注意的行为怪癖：正如我们发布时[所写的](https://www.anthropic.com/news/claude-opus-4-7)，它往往相当冗长。这让它在难题上更聪明，但也产出更多输出 token。

在发布 Opus 4.7 前几周，我们开始为此准备而调优 Claude Code。每个模型的行为都略有不同，我们在每次发布前花时间针对它优化 harness 和产品。

我们有许多降低冗长度的工具：模型训练、提示，以及改进产品里的思考 UX。最终我们全都用了，但系统 prompt 里的一处新增对 Claude Code 的智能造成了过大的影响：

> 「长度限制：工具调用之间的文本保持在 ≤25 词。最终回复保持在 ≤100 词，除非任务需要更多细节。」

在数周的内部测试、且我们所跑的一组评测无回归之后，我们对这项改动有信心，并于 4 月 16 日随 Opus 4.7 一起上线。

作为本次调查的一部分，我们用一组更广的评测跑了更多消融（从系统 prompt 移除某些行，以理解每一行的影响）。其中一个评测对 Opus 4.6 和 4.7 都显示出 3% 的下降。我们随即作为 4 月 20 日发布的一部分回滚了该 prompt。

## 展望未来

我们会做几件不同的事以避免这些问题：我们会确保更大比例的内部员工使用与公众完全相同的 Claude Code 构建版本（而非我们用来测试新功能的那个版本）；并且我们会改进我们内部使用的[代码审查](https://code.claude.com/docs/en/code-review)工具、并把这版改进后的工具交付给客户。

我们也在为系统 prompt 改动加上更严格的控制。我们会对 Claude Code 的每一处系统 prompt 改动跑一套广泛的、按模型的评测，持续做消融以理解每一行的影响，并且我们构建了新工具，使 prompt 改动更易被审阅和审计。我们还额外在 CLAUDE.md 里加入了指南，确保按模型的改动被门控到它们所针对的特定模型。对任何可能与智能相权衡的改动，我们会加入浸泡期、更广的评测套件和逐步推广，以便更早发现问题。

我们最近在 X 上创建了 @ClaudeDevs，好给我们空间去深入解释产品决策及其背后的理由。我们会在 GitHub 上集中的讨论串里分享同样的更新。

最后，我们要感谢我们的用户：那些用 `/feedback` 命令向我们分享问题的人（或是在网上发布具体、可复现示例的人），最终正是他们让我们得以识别并修复这些问题。今天，我们正在重置所有订阅者的用量限制。

我们对你们的反馈和你们的耐心，深怀感激。
