# 我们如何构建多 agent 研究系统

发布于 2025 年 6 月 13 日

我们的 Research 功能使用多个 Claude agent 来更有效地探索复杂主题。我们分享构建这套系统时遇到的工程挑战和学到的经验。

Claude 如今拥有 [Research 能力](https://www.anthropic.com/news/research)，能让它跨越网络、Google Workspace 和任何集成进行搜索，以完成复杂任务。

这套多 agent 系统从原型走向生产的历程，教会了我们关于系统架构、工具设计和 prompt 工程的关键一课。一个多 agent 系统由多个协同工作的 agent（LLM 在循环里自主使用工具）组成。我们的 Research 功能涉及一个 agent：它基于用户查询规划一个研究流程，然后用工具创建并行 agent，同时搜索信息。多 agent 系统引入了在 agent 协调、评估和可靠性方面的新挑战。

本文拆解对我们奏效的原则——希望你在构建自己的多 agent 系统时也能用上它们。

### 多 agent 系统的好处

研究工作涉及开放式问题，在那里事先预测所需步骤非常困难。你无法为探索复杂主题硬编码一条固定路径，因为这一过程本质上是动态且路径依赖的。当人们做研究时，他们往往基于发现持续更新自己的方法，追随调查过程中浮现的线索。

这种不可预测性使 AI agent 尤其适合研究任务。研究要求在调查展开时灵活地转向或探索旁支关联。模型必须自主运作许多轮，就基于中间发现该追求哪个方向做出决策。一条线性的、一次成型的流水线无法处理这些任务。

搜索的本质是压缩：从海量语料中提炼洞察。子 agent 通过各自拥有独立的上下文窗口、并行运作来促成压缩，在为主研究 agent 浓缩最重要的 token 之前，同时探索问题的不同方面。每个子 agent 也带来关注点的分离——不同的工具、prompt 和探索轨迹——减少路径依赖，并促成彻底、独立的调查。

一旦智能达到某个阈值，多 agent 系统就成为一种扩展性能的重要方式。例如，尽管过去十万年里个体人类变得更聪明了，人类社会却由于我们的*集体*智能和协调能力，在信息时代变得*指数级*更有能力。即便是通才 agent 作为个体运作时也会遇到限制；agent 群体能成就多得多的事情。

我们的内部评估显示，多 agent 研究系统在尤其适合那些涉及同时追求多个独立方向的广度优先查询。我们发现，一个以 Claude Opus 4 作为主 agent、Claude Sonnet 4 作为子 agent 的多 agent 系统，在我们内部研究评测上比单 agent 的 Claude Opus 4 高出 90.2%。例如，当被要求识别信息技术标普 500 成分公司的所有董事会成员时，多 agent 系统通过把它拆成给子 agent 的任务找到了正确答案，而单 agent 系统用缓慢的顺序搜索没能找到答案。

多 agent 系统之所以奏效，主要因为它们帮助花足够多的 token 去解决问题。在我们的分析中，[BrowseComp](https://openai.com/index/browsecomp/) 评测（测试浏览 agent 定位难以找到信息的能力）里有三个因素解释了 95% 的性能方差。我们发现 token 用量本身就解释了 80% 的方差，另两个解释因素是工具调用次数和模型选择。这一发现印证了我们的架构——把工作分散到拥有独立上下文窗口的各 agent 上，以增加并行推理的容量。最新的 Claude 模型是 token 使用上的大号效率倍增器，因为升级到 Claude Sonnet 4 比在 Claude Sonnet 3.7 上把 token 预算翻倍带来的性能增益还大。多 agent 架构有效地为那些超出单 agent 极限的任务扩展了 token 用量。

有一个下行：在实践中，这些架构烧 token 很快。在我们的数据里，agent 通常比聊天交互多用约 4 倍 token，多 agent 系统比聊天多用约 15 倍 token。要具经济可行性，多 agent 系统要求任务的价值高到足以偿付提升的性能。此外，某些要求所有 agent 共享同一上下文、或 agent 之间有很多依赖的领域，如今并不适合多 agent 系统。例如，多数编码任务比研究包含更少真正可并行的任务，而 LLM agent 尚不擅长实时协调和委派给其他 agent。我们发现，多 agent 系统在那些需要重度并行化、信息超出单个上下文窗口、并要与众多复杂工具打交道的、有价值的任务上表现出色。

### Research 的架构概览

我们的 Research 系统使用一个带编排者-工作者（orchestrator-worker）模式的多 agent 架构，一个主 agent 协调流程，同时把工作委派给并行运作的专门子 agent。

实际运作中的多 agent 架构：用户查询流经一个主 agent，后者创建专门的子 agent 并行搜索不同方面。

当用户提交一个查询，主 agent 分析它、制定一个策略、并派出子 agent 同时探索不同方面。如上面图中所示，子 agent 充当智能过滤器，通过迭代地使用搜索工具收集信息——这里是 2025 年的 AI agent 公司——然后把一份公司列表返回给主 agent，以便它汇编出最终答案。

使用检索增强生成（RAG）的传统方法用静态检索。也就是说，它们抓取某组与输入查询最相似的块、并用这些块生成响应。相较之下，我们的架构使用一个多步搜索，动态地找到相关信息、适应新发现、并分析结果以形成高质量答案。

展示我们多 agent Research 系统完整工作流的流程图。当用户提交一个查询，系统创建一个 LeadResearcher agent，它进入一个迭代研究流程。LeadResearcher 先思考其方法、并把计划保存到 Memory 以持久化上下文，因为若上下文窗口超过 200,000 token 就会被截断，而保留计划很重要。随后它用具体的研究任务创建专门的子 agent（这里画了两个，但可以是任意数量）。每个子 agent 独立执行网页搜索，用交错思考（interleaved thinking）评估工具结果，并把发现返回给 LeadResearcher。LeadResearcher 综合这些结果并决定是否还需要更多研究——若需要，它可以创建更多子 agent 或打磨其策略。一旦收集到足够信息，系统就退出研究循环、把所有发现交给一个 CitationAgent，它处理文档和研究报告以识别具体的引用位置。这确保所有论断都被恰当地归属于其来源。最终的研究结果连同引用一起被返回给用户。

### 研究 agent 的 prompt 工程与评估

多 agent 系统与单 agent 系统有关键差异，包括协调复杂度的快速增长。早期 agent 会犯诸如为简单查询派出 50 个子 agent、无休止地在网上搜不存在的来源、用过度的更新相互干扰这类错误。由于每个 agent 都由 prompt 引导，prompt 工程是我们改进这些行为的主要杠杆。下面是我们在给 agent 做 prompt 时学到的一些原则：

- **像你的 agent 那样思考。** 要迭代 prompt，你必须理解它们的效果。为帮我们做到这一点，我们用系统中的确切 prompt 和工具，在我们的 [Console](https://console.anthropic.com/) 上构建模拟，然后一步步看着 agent 工作。这立刻揭示了失败模式：agent 在已有足够结果时仍继续、用过于冗长的搜索查询、或选错工具。有效的 prompt 依赖于培养一个关于 agent 的准确心智模型，它能让最有影响的变化一目了然。
- **教编排者如何委派。** 在我们的系统里，主 agent 把查询分解成子任务并向子 agent 描述它们。每个子 agent 需要一个目标、一个输出格式、关于该用哪些工具和来源的指导、以及清晰的任务边界。没有详细的任务描述，agent 会重复劳动、留下空档、或找不到必要的信息。我们从让主 agent 给出简单、短小的指令起步，比如「研究半导体短缺」，却发现这些指令常常含糊到让子 agent 误解任务、或做出与其他 agent 完全相同的搜索。例如，一个子 agent 探索 2021 年汽车芯片危机，而另外两个重复调查当前 2025 年供应链的工作，没有有效的分工。
- **把工作强度缩放到查询复杂度。** agent 难以判断不同任务该花多少力气，所以我们在 prompt 里嵌入了缩放规则。简单的事实查找只需 1 个 agent、3-10 次工具调用，直接比较可能需要 2-4 个子 agent、每个 10-15 次调用，而复杂研究可能用超过 10 个职责清晰分明的子 agent。这些显式指南帮助主 agent 高效分配资源、防止在简单查询上过度投入——这是我们早期版本中一个常见的失败模式。
- **工具的设计与选择至关重要。** agent-工具接口之于 agent，就像人机界面之于人一样关键。用对工具是高效的——很多时候它甚至是必需的。例如，一个 agent 去搜网络找那些只存在于 Slack 里的上下文，从一开始就注定失败。借助让模型能访问外部工具的 [MCP 服务器](https://modelcontextprotocol.io/introduction)，这一问题会叠加，因为 agent 会遇到质量参差不齐、前所未见的工具。我们给 agent 显式的启发式规则：例如，先审视所有可用工具、把工具使用与用户意图匹配、对广泛的外部探索用网页搜索、或优先专门工具而非通用工具。糟糕的工具描述会把 agent 引上完全错误的路径，所以每个工具都需要一个独特的用途和清晰的描述。
- **让 agent 自我改进。** 我们发现 Claude 4 模型能成为出色的 prompt 工程师。当被给定一个 prompt 和一个失败模式时，它们能诊断 agent 为何失败并建议改进。我们甚至创建了一个工具测试 agent——给定一个有缺陷的 MCP 工具，它会尝试使用该工具、然后重写工具描述以避免失败。通过几十次测试该工具，这个 agent 发现了关键的细微之处和 bug。这个改进工具人体工学的过程，使得使用新描述的后续 agent 任务完成时间减少了 40%，因为它们能避开大多数错误。
- **先铺开，再收窄。** 搜索策略应当映照有专长的人类研究：先钻探之前先勘察地形。agent 常常默认用过长、过于具体的查询，返回很少结果。我们通过 prompt agent 从短、宽的查询开始、评估有什么可用、然后逐步收窄焦点，来对抗这一倾向。
- **引导思考过程。** [扩展思考模式](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking)会让 Claude 在可见的思考过程里输出额外的 token，可以充当一块可控的草稿纸。主 agent 用思考来规划其方法，评估哪些工具契合任务、判定查询复杂度和子 agent 数量、并定义每个子 agent 的角色。我们的测试显示，扩展思考改善了指令遵循、推理和效率。子 agent 也做规划，然后在工具结果之后用[交错思考](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking)来评估质量、识别缺口、打磨其下一个查询。这让子 agent 在任何任务上都更有效地适应。
- **并行工具调用改变速度和性能。** 复杂研究任务天然涉及探索许多来源。我们早期的 agent 顺序执行搜索，那慢得难受。为求速度，我们引入了两种并行化：(1) 主 agent 并行而非串接地派出 3-5 个子 agent；(2) 子 agent 并行使用 3 个以上工具。这些改动把复杂查询的研究时间削减了多达 90%，让 Research 能在几分钟而非几小时内做更多工作，同时覆盖比其他系统更多的信息。

我们的 prompt 策略聚焦于灌输良好的启发式规则，而非死板的规则。我们研究有专长的人如何做研究任务，并把这些策略编码进我们的 prompt——例如把难题分解成更小的任务、仔细评估来源质量、基于新信息调整搜索方法、以及识别何时该聚焦于深度（详查一个主题）versus 广度（并行探索多个主题）。我们还通过设定显式护栏来主动预防意外的副作用，防止 agent 失控外溢。最后，我们聚焦于一个带可观测性和测试用例的快速迭代循环。

### agent 的有效评估

好的评估对构建可靠的 AI 应用至关重要，agent 也不例外。然而，评估多 agent 系统带来了独特的挑战。传统评估常常假设 AI 每次都遵循相同步骤：给定输入 X，系统应遵循路径 Y 产出输出 Z。但多 agent 系统并非如此运作。即便起点相同，agent 也可能走完全不同的有效路径抵达目标。一个 agent 可能搜索三个来源而另一个搜索十个，或它们用不同的工具找到同一个答案。因为我们并不总是知道正确的步骤是什么，通常不能只检查 agent 是否遵循了我们事先规定的「正确」步骤。相反，我们需要灵活的评估方法，判断 agent 是否取得了正确结果、同时遵循了一个合理的过程。

**从小样本立即开始评估。** 在早期 agent 开发中，变化往往带来巨大影响，因为有大量唾手可得的好处。一次 prompt 微调可能把成功率从 30% 提到 80%。有这么大的效应量，仅几个测试用例你就能发现变化。我们从约 20 条代表真实使用模式的查询开始。测试这些查询往往能让我们清楚地看到改动的影响。我们经常听到 AI 开发团队推迟创建评估，因为他们认为只有包含数百测试用例的大型评估才有用。然而，最好立刻用几个示例从小规模测试开始，而不是拖延到你能构建更彻底的评估。

**做得好时，LLM-as-judge 评估能扩展。** 研究产出难以程序化地评估，因为它们是自由格式的文本、很少有一个唯一正确答案。LLM 是为产出打分的天生之选。我们用一个 LLM 评审员，对照评分标准里的准则评估每个输出：事实准确性（论断是否与来源相符）、引用准确性（被引用的来源是否与论断相符）、完整性（是否覆盖了所有要求的方面）、来源质量（它用的是原始来源还是低质量的二手来源）、以及工具效率（它是否以合理的次数用了正确的工具）。我们试验了多个评审员来评估每个组件，却发现一次带单一 prompt、输出 0.0-1.0 分数和一个通过/失败等级的 LLM 调用最稳定、与人类判断最契合。当评估测试用例*确实*有一个清晰答案、而我们可以用 LLM 评审员简单地检查答案是否正确时（例如它是否准确列出了研发预算最高的前三大制药公司？），这种方法尤其有效。用 LLM 做评审员让我们能可扩展地评估数百个输出。

**人类评估能捕捉自动化漏掉的东西。** 测试 agent 的人会发现评估漏掉的边缘情形。这些包括不寻常查询上的幻觉答案、系统失败、或微妙的来源选择偏见。就我们的情形，人类测试者注意到我们早期的 agent 一贯选择 SEO 优化的内容农场，而非权威但排名较低的来源，如学术 PDF 或个人博客。在 prompt 里加入来源质量启发式规则帮助解决了这一问题。即便在一个自动化评估的世界里，手动测试仍然必不可少。

多 agent 系统有涌现行为，它们在没有专门编程的情况下产生。例如，对主 agent 的小改动会不可预测地改变子 agent 的行为。成功需要理解交互模式，而不仅是单个 agent 的行为。因此，这些 agent 最好的 prompt 不只是严格的指令，而是协作的框架——定义分工、问题求解方法和工作强度预算。做好这一点依赖于周密的 prompt 和工具设计、扎实的启发式规则、可观测性，以及紧密的反馈回路。参见[我们 Cookbook 里开源的 prompt](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)获取我们系统的示例 prompt。

### 生产可靠性与工程挑战

在传统软件里，一个 bug 可能破坏一个功能、劣化性能或造成宕机。在 agentic 系统里，微小变化会级联成大的行为变化，这使得为那些必须在长时间运行流程里维持状态的复杂 agent 写代码异常困难。

**agent 是有状态的、错误会叠加。** agent 能长时间运行，跨许多次工具调用维持状态。这意味着我们需要持久地执行代码、并在途中处理错误。没有有效的缓解，小的系统失败对 agent 可能是灾难性的。当错误发生时，我们不能从头重启：重启既昂贵又让用户沮丧。相反，我们构建能从 agent 出错时所在位置恢复的系统。我们也用模型的智能来妥善地处理问题：例如，让 agent 知道某个工具正在失败、并让它去适应，效果出奇地好。我们把基于 Claude 构建的 AI agent 的适应性，与确定性的保护措施（如重试逻辑和定期检查点）结合起来。

**调试受益于新方法。** agent 做出动态决策、且在运行之间非确定，即便 prompt 相同。这让调试更难。例如，用户会反馈 agent「找不到明显的信息」，但我们看不到为什么。是 agent 在用糟糕的搜索查询吗？选差的来源吗？还是遇到工具失败？添加完整的生产 trace 让我们能诊断 agent 为何失败、并系统地修复问题。除了标准的可观测性，我们监控 agent 的决策模式和交互结构——全都不监控单个对话的内容，以维护用户隐私。这种高层可观测性帮助我们诊断根因、发现意外行为、并修复常见失败。

**部署需要周密协调。** agent 系统是由 prompt、工具和执行逻辑构成的、几乎持续运行的高状态网络。这意味着每当我们部署更新，agent 可能处在流程的任何位置。因此我们需要防止我们善意的代码改动破坏已有的 agent。我们无法在同一时刻把所有 agent 更新到新版本。相反，我们使用[彩虹部署](https://brandon.dimcheff.com/2018/02/rainbow-deploys-with-kubernetes/)来避免扰乱运行中的 agent，通过逐渐把流量从旧版本迁移到新版本、同时让两者并行运行。

**同步执行造成瓶颈。** 目前，我们的主 agent 同步地执行子 agent，等待每一批子 agent 完成后再继续。这简化了协调，却在 agent 之间的信息流里造成了瓶颈。例如，主 agent 无法引导子 agent，子 agent 无法相互协调，而整个系统在等单个子 agent 完成搜索时会被阻塞。异步执行会带来额外的并行性：agent 并发工作、并在需要时创建新的子 agent。但这种异步性在结果协调、状态一致性和子 agent 之间的错误传播上增加了挑战。随着模型能处理更长、更复杂的研究任务，我们预期性能增益会证明这种复杂性是值得的。

### 结论

在构建 AI agent 时，最后一公里常常变成旅程的大头。在开发者机器上能跑通的代码库，需要大量工程才能变成可靠的生产系统。agentic 系统里错误的复合本质，意味着对传统软件无足轻重的小问题可能彻底让 agent 脱轨。一步失败可能导致 agent 去探索完全不同的轨迹，引发不可预测的结果。出于本文描述的所有原因，原型与生产之间的鸿沟往往比预想的更宽。

尽管有这些挑战，多 agent 系统已证明对开放式研究任务很有价值。用户说 Claude 帮他们找到了此前未曾考虑的商业机会、驾驭复杂的医疗选项、解决棘手的技术 bug，并通过揭示他们独自不会找到的研究关联，省下多达数天的工作。多 agent 研究系统能在精心工程、全面测试、细致的 prompt 和工具设计、稳健的运营实践，以及对当前 agent 能力有深刻理解的研究、产品和工程团队之间紧密协作下，可靠地规模化运作。我们已经看到这些系统正在改变人们解决复杂问题的方式。

一张 Clio 嵌入图，展示人们今天使用 Research 功能最常见的方式。最主要的使用用例类别是：跨专门领域开发软件系统（10%）、开发与优化专业和技术内容（8%）、开发业务增长和创收策略（8%）、协助学术研究和教学材料开发（7%）、以及研究并核实关于人、地点或组织的信息（5%）。

## 附录

下面是关于多 agent 系统的一些额外的杂项建议。

**对跨多轮改变状态的 agent 做终态评估。** 评估那些在多轮对话中修改持久状态的 agent，带来了独特的挑战。与只读的研究任务不同，每个动作都可能改变后续步骤的环境，造成了传统评估方法难以应对的依赖。我们发现聚焦于终态评估、而非逐轮分析，能取得成功。不是判断 agent 是否遵循了某个特定过程，而是评估它是否达到了正确的最终状态。这种做法承认 agent 可能找到通往同一目标的替代路径，同时仍确保它交付预期的结果。对复杂工作流，把评估拆成若干离散的、应已发生特定状态变化的检查点，而不是试图验证每一个中间步骤。

**长时段对话管理。** 生产 agent 常常参与跨越数百轮、需要周密上下文管理策略的对话。随着对话延展，标准的上下文窗口变得不够用，需要有智能的压缩和记忆机制。我们实现的模式是：agent 在进入新任务前，把已完成的工作阶段做摘要、并把关键信息存到外部记忆里。当接近上下文限制时，agent 可以派出带干净上下文的新子 agent，并通过周密的交接维持连续性。此外，它们能像从记忆中取回研究计划这样的存储上下文，而不是在触及上下文极限时丢失先前的工作。这种分布式方法在防止上下文溢出的同时，维持了跨长交互的对话连贯性。

**让子 agent 输出到文件系统，以最小化「传话游戏」。** 对某些类型的结果，子 agent 的直接输出可以绕过主协调者，改善保真度和性能。与其要求子 agent 通过主 agent 传达一切，不如实现一种产物系统，让专门的 agent 创建能独立持久化的输出。子 agent 调用工具把其工作存储到外部系统，然后把轻量引用回传给协调者。这防止了多阶段处理期间的信息丢失、并减少了把大输出经由对话历史复制所带来的 token 负担。这种模式对那些结构化输出（如代码、报告或数据可视化）尤其奏效，因为子 agent 的专门 prompt 比经由通用协调者过滤能产出更好的结果。
