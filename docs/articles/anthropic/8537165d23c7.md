# 扩展 Managed Agents：把「大脑」与「双手」解耦

发布于 2026 年 4 月 8 日

Harness 会编码一些假设，而这些假设随着模型进步会过时。Managed Agents——我们面向长时段 agent 工作的托管服务——围绕在 harness 变化时仍能保持稳定的接口构建。

*想开始使用 Claude Managed Agents，请遵循我们的 [文档](https://platform.claude.com/docs/en/managed-agents/overview)。*

工程博客上持续热议的话题，是如何 [构建高效的 agent](https://www.anthropic.com/engineering/building-effective-agents)、如何为 [长时段工作](https://www.anthropic.com/engineering/harness-design-long-running-apps) [设计 harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。贯穿这些工作的一条共同主线是：harness 会编码关于「Claude 独自做不到什么」的假设。然而，这些假设需要被频繁地质疑，因为随着模型进步它们会 [过时](http://www.incompleteideas.net/IncIdeas/BitterLesson.html)。

仅举一例，在之前的工作里我们 [发现](https://www.anthropic.com/engineering/harness-design-long-running-apps)，Claude Sonnet 4.5 会在察觉自身接近上下文极限时提前收尾任务——这种行为有时被称为「上下文焦虑」。我们通过在 harness 里加入上下文重置来应对。但当我们在 Claude Opus 4.5 上使用同一个 harness 时，发现这一行为消失了。那些重置变成了无用负担。

我们预期 harness 会持续演进。于是我们构建了 Managed Agents：Claude Platform 上的一项托管服务，通过一小组旨在比任何特定实现（包括我们今天所用的那些）更持久存在的接口，代你在后台运行长时段 agent。

构建 Managed Agents 意味着要解决计算领域的一个老问题：如何为「[尚未被构想出来的程序](http://www.catb.org/esr/writings/taoup/html/ch03s01.html)」设计一个系统。数十年前，操作系统通过把硬件虚拟化为抽象——*进程、文件*——解决了这个问题，其通用性足以覆盖当时尚不存在的程序。这些抽象比硬件更长寿。`read()` 命令并不关心它访问的是 1970 年代的磁盘组还是现代的 SSD。上层抽象保持稳定，而底层实现可以自由更换。

Managed Agents 遵循同样的模式。我们把 agent 的组件做了虚拟化：会话（session，记录所发生一切的仅追加日志）、harness（调用 Claude 并把 Claude 的工具调用路由到相应基础设施的那个循环），以及沙箱（sandbox，Claude 运行代码和编辑文件的执行环境）。这使得每个组件的实现可以在不扰动其他组件的情况下被更换。我们对这些接口的 *形态* 有主张，但对其背后运行什么没有主张。

## 别养宠物

我们一开始把所有 agent 组件放进单个容器，这意味着会话、agent harness 和沙箱共享同一个环境。这种做法有好处——文件编辑是直接的 syscall，也没有服务边界需要设计。

但把所有东西耦合进一个容器，我们撞上了一个老的基础设施问题：我们 *养了一只宠物*。在「宠物 vs 牲口」的类比里，宠物是你输不起、需要精心照料的个体，而牲口是可以替换的。在我们的情形里，服务器就变成了那只宠物：容器一坏，会话就丢了；容器一失去响应，我们就得把它护理回健康。

护理容器意味着要调试失去响应的卡死会话。我们唯一的窗口是 WebSocket 事件流，但它无法告诉我们故障 *源自何处*，这意味着 harness 里的一个 bug、事件流里的一次丢包，或一个容器下线，全都呈现为同样的样子。要弄清出了什么问题，工程师得在容器里开一个 shell，但由于那个容器往往还存有用户数据，这种做法实际上意味着我们缺乏调试能力。

第二个问题是，harness 假设了 Claude 所操作的一切都与它同处一个容器里。当客户要求我们把 Claude 连到他们的虚拟私有云时，他们要么把自己的网络与我们对等互联，要么在我们的环境之外运行我们的 harness。一个被烙进 harness 的假设，在我们想把它连到不同基础设施时就变成了问题。

## 把大脑与双手解耦

我们最终找到的解法，是把我们所称的「大脑」（Claude 及其 harness）与「双手」（执行动作的沙箱和工具）以及「会话」（会话事件的日志）都解耦开来。三者各自成为一个接口，对其他几乎不做假设，且每一者都可以独立失败或被替换。

**harness 离开容器。** 把大脑与双手解耦意味着 harness 不再栖身于容器之内。它调用容器的方式，就像调用任何其他工具一样：`execute(name, input) → string`。容器就此变成了牲口。如果容器死了，harness 会把这次失败当作一次工具调用错误捕获，并回传给 Claude。如果 Claude 决定重试，就可以用一个标准配方 `provision({resources})` 重新初始化一个新容器。我们再也不必把故障容器护理回健康。

**从 harness 故障中恢复。** harness 也变成了牲口。由于会话日志位于 harness 之外，harness 里没有任何东西需要在崩溃中幸存。当某个 harness 故障时，可以用 `wake(sessionId)` 重启一个新 harness，用 `getSession(id)` 取回事件日志，并从最后一个事件处继续。在 agent 循环期间，harness 通过 `emitEvent(id, event)` 写入会话，以保持一份对事件的持久记录。

**安全边界。** 在耦合式设计里，Claude 生成的任何不受信任代码都与凭证跑在同一个容器中——于是一次提示注入只需说服 Claude 去读取它自己的环境变量即可。一旦攻击者拿到那些 token，就能生成全新的、不受限的会话并把工作委派给它们。收窄作用域是一个显而易见的缓解手段，但它编码了关于「Claude 拿着受限 token 做不到什么」的假设——而 Claude 正变得越来越聪明。结构性的解决办法，是确保凭证 token 永远无法从 Claude 生成代码所在的沙箱中被触及。

我们用了两种模式来保证这一点。认证凭证要么与某个资源捆绑在一起，要么保存在沙箱之外的保险库（vault）里。对于 Git，我们在沙箱初始化期间用每个仓库的访问 token 克隆仓库，并把它接入本地的 git remote。从沙箱内部 `push` 和 `pull` 都能正常工作，而 agent 自始至终不经手这个 token。对于自定义工具，我们支持 MCP 并把 OAuth token 存放在安全保险库里。Claude 通过一个专用代理调用 MCP 工具；该代理接收一个与会话关联的 token。代理随后可以从保险库取出对应的凭证，并向外部服务发起调用。harness 永远不会知晓任何凭证。

## 会话不是 Claude 的上下文窗口

长时段任务往往超出 Claude 上下文窗口的长度，而应对这一点的所有标准方法，都涉及关于「保留什么」的不可逆决策。我们在上下文工程的 [先前工作](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 中探讨过这些技术。例如，压缩（compaction）让 Claude 保存其上下文窗口的一份摘要，而 memory 工具让 Claude 把上下文写入文件，从而实现跨会话学习。这可以与上下文裁剪（context trimming）配合使用，后者会选择性移除 token，例如旧的工具结果或思考块。

但那些选择性保留或丢弃上下文的不可逆决策可能导致失败。我们很难知道未来的轮次会需要哪些 token。如果消息被一个压缩步骤转换，harness 会把已被压缩的消息从 Claude 的上下文窗口移除，而它们只有在被存储的情况下才可恢复。先前工作 [探讨了](https://arxiv.org/pdf/2512.24601) 一种做法，即把上下文作为一个位于上下文窗口 *之外* 的对象来存储。例如，上下文可以是 REPL 里的一个对象，由 LLM 通过编写代码来过滤或切片以编程式访问。

在 Managed Agents 中，会话提供了同样的好处，充当一个位于 Claude 上下文窗口之外的上下文对象。但它不存储在沙箱或 REPL 里，而是持久存储在会话日志中。接口 `getEvents()` 让大脑通过选取事件流的位置切片来盘问上下文。这个接口可灵活使用，让大脑能从上次停止读取之处继续、往前倒回某个特定时刻前的事件以查看铺垫，或重读某个特定动作之前的上下文。

任何取回的事件在传给 Claude 的上下文窗口之前，也可以在 harness 中先行转换。这些转换可以完全由 harness 编码，包括为达到高 prompt cache 命中率而做的上下文组织，以及上下文工程。我们把「可恢复的上下文存储在会话中」与「任意的上下文管理在 harness 中」分离，是因为我们无法预测未来的模型需要什么样的具体上下文工程。这些接口把上下文管理的职责推向 harness，只保证会话是持久的、可供盘问的。

## 众多大脑，众多双手

**众多大脑。** 把大脑与双手解耦解决了我们最早的客户投诉之一。当团队希望 Claude 针对其自身 VPC 里的资源工作时，唯一的途径是把他们的网络与我们的对等互联，因为装着 harness 的容器假设了每个资源就在它旁边。一旦 harness 不再在容器里，这个假设就消失了。同一改动还带来了性能回报。当我们最初把大脑放进容器时，意味着众多大脑需要众多容器。对每个大脑而言，在容器被分配好之前无法进行任何推理；每个会话都要预先付出完整的容器启动成本。每个会话——哪怕是永远不碰沙箱的那些——都得克隆仓库、启动进程、从我们的服务器拉取待处理事件。

那段空等时间体现在首 token 时间（TTFT）上，它衡量一个会话从接受工作到产出第一个响应 token 之间要等多久。TTFT 是用户最真切 *感受到* 的延迟。

把大脑与双手解耦意味着容器由大脑通过一次工具调用 `(execute(name, input) → string)` 按需分配。所以不需要立即用容器的会话就不必等待容器。推理可以在编排层从会话日志拉取待处理事件后立刻开始。采用这一架构后，我们的 p50 TTFT 下降了约 60%，p95 下降了超过 90%。扩展到大脑众多，仅仅意味着启动众多无状态 harness，并且只在需要时才把它们连到双手。

**众多双手。** 我们还希望有能力把每个大脑连到众多双手。实际上，这意味着 Claude 必须推理众多执行环境并决定把工作送往何处——这是一项比在单个 shell 中操作更难的认知任务。我们最初把大脑放在单个容器里，是因为更早的模型做不到这一点。随着智能提升，单个容器反而成了局限：那个容器一旦故障，我们就丢失了大脑正在触及的每一只双手的状态。

把大脑与双手解耦让每只双手成为一个工具，`execute(name, input) → string`：传入一个名字和输入，返回一个字符串。这个接口支持任何自定义工具、任何 MCP 服务器，以及我们自己的工具。harness 并不关心沙箱究竟是一个容器、一部手机，还是一个宝可梦模拟器。而且由于没有任何双手与任何大脑耦合，大脑之间可以把双手互相传递。

## 结论

我们面临的挑战是一个老问题：如何为「尚未被构想出来的程序」设计一个系统。操作系统通过把硬件虚拟化为对尚不存在的程序足够通用的抽象，延续了数十年。借助 Managed Agents，我们旨在设计一个能够容纳围绕 Claude 的未来 harness、沙箱或其他组件的系统。

Managed Agents 是同一精神上的一个元 harness（meta-harness），对 Claude 未来将需要 *哪个* 具体 harness 没有主张。不如说，它是一个拥有通用接口、允许多种不同 harness 的系统。例如，Claude Code 是我们广泛用于各类任务的一个出色 harness。我们也展示了特定任务的 agent harness 在狭窄领域里表现出色。Managed Agents 能够容纳其中任何一种，并随时间匹配 Claude 的智能水平。

元 harness 设计意味着对围绕 Claude 的接口要有主张：我们预期 Claude 将需要操作状态（会话）和执行计算（沙箱）的能力。我们也预期 Claude 将需要扩展到大脑众多、双手众多的能力。我们设计这些接口，使得这些能力能在长时间跨度上被可靠且安全地运行。但我们不对 Claude 所需大脑或双手的数量或位置做任何假设。
