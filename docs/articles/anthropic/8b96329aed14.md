# 调查我们网络安全评估中的三起真实世界事故

2026 年 7 月 30 日

***在我们网络安全评估文字记录的一次审查中，我们发现三起事故：一个 Claude 模型从第三方评估环境内部、或在与该环境交互期间抵达了互联网，随后未经授权访问了三家不同组织的真实系统。***

***下面，我们描述发生了什么、如何发生、以及我们要做什么改变。我们鼓励其他 AI 实验室做类似的审查。本文反映我们当前的理解；如有任何细节变化，我们会更新它。***

7 月 21 日，OpenAI [披露](https://openai.com/index/hugging-face-model-evaluation-security-incident/)：他们的若干模型通过利用一个先前未知的（「零日」）漏洞，逃出了一个隔离的测试环境。这些模型进而访问了 Hugging Face——一个开源机器学习模型和 AI 数据集的平台——的生产基础设施。

作为对该事故的回应，我们开始对自身网络安全评估进行一次大规模的事后审查。特别地，我们寻找证据，看 Claude——像访问 Hugging Face 的那些 OpenAI 模型一样——是否能从本应被隔绝的测试环境内部访问互联网。

在审查了 141,006 次 Claude 本可能获得互联网访问的评估运行后，我们识别出三起事故：一个模型从我们第三方评估伙伴之一 Irregular 的评估环境内部、或在与该环境交互期间访问了互联网，随后未经授权访问了三家不同组织的生产基础设施。

在三起事故中，Claude 都被指派了一个夺旗（capture-the-flag）挑战——这是我们评估模型网络能力的方式之一。模型被给一个虚构场景，被告知一份秘密信息（「旗」）被藏在网络上另一台机器里，它的目标是闯入并取回它。挑战是开放式的，不规定任何特定方法。

在所有情形中，Anthropic 的评估 prompt 都向 Claude 指明其环境是一个模拟、且它没有互联网访问。由于我们与我们评估伙伴之间的一处误解，事实并非如此，互联网访问是可用的。因此，当 Claude 的搜索把它带到开放互联网上的真实系统时，它把它们当作演练的一部分。（网络安全评估版图通常包含真实细节，以准确评估模型在真实环境中能做什么；一个看起来真实的目标本身，对模型来说并不是目标不属于模拟的明确证据。）

在「所有可访问的实体本都应处于演练范围之内」这一错误信念下运作，Claude 用基础技术（如利用弱密码和未认证端点）攻陷了受影响组织的基础设施。它没有发现或利用任何复杂漏洞，且在每一起里，Claude 只继续完成其评估所指派的那个特定夺旗任务。然而，在某些案例中，我们较早的模型在获得它正运行在开放互联网上的证据之后仍继续攻击；我们最新的模型一旦认出它在互联网上就停了下来。在所有这些情形中，Claude 都没有把自己外泄、或蓄意试图逃出它的测试环境。

这些事故涉及三款不同的 Claude 模型：Opus 4.7、Mythos 5 和一个内部研究测试模型。[1](https://www.anthropic.com/news/investigating-incidents-cybersecurity-evals#footnote-1) 最早的事故可追溯到四月。这些评估中每一起的模型运行时，都没有我们在让模型普遍可用时所部署的标准防护（也就是说，它们没有我们通常为防止滥用而实施的分类器和监控）。不过，这些模型确实有它们按模型的安全训练（也就是说，它们不是我们有时在测试中使用的「仅有帮助」版本模型）。这里描述的所有评估都在专用基础设施上运行，该基础设施独立于、且无法访问 Anthropic 敏感的内部系统或客户数据。

我们于周四 7 月 23 日开始文字记录审查，并在识别出 Claude 可能访问了互联网的文字记录后，同一天停止了所有网络评估。我们次日就识别出了全部三起事故。我们在周一 7 月 27 日通知了我们的评估伙伴 Irregular 和三家受影响的组织。我们能联系上的那两家此前并未检测到该活动、也未联系我们，我们如今正与他们合作整改。我们仍在继续联系第三家。

我们与 [Irregular](https://www.irregular.com/research/next-generation-of-cyber-evals) 协作进行了这次审查。我们感谢他们与我们紧密合作以理解和解决这些事故；他们也在进行自己的调查。我们相信这类协作，对确保对模型进行安全、严谨的评估愈发关键。我们期待双方在安全上的共同工作。

在下文，我们提供每起事故的更多细节、以及我们接下来如何应对。

## **网络评估的背景**

我们定期运行涉及模拟真实攻击性网络安全挑战的网络安全评估。这些评估是开发和发布模型过程中的关键一步——对模型能力的细腻理解让我们能设计恰当的防护、并最终安全地发布模型。

我们于 2025 年 2 月用 Claude Sonnet 3.7 在 [Cybench](https://cybench.github.io/) 上开始运行网络安全评估，那由 40 个不同的夺旗挑战组成。随时间推移，随着新基准发布和模型能力演进，我们增加了所用基准的数量。例如在 [Mythos 5 系统卡](https://www-cdn.anthropic.com/d00db56fa754a1b115b6dd7cb2e3c342ee809620.pdf)里，我们纳入了 CyberGym 和 ExploitBench——评估语言模型发现新漏洞能力的基准。[2](https://www.anthropic.com/news/investigating-incidents-cybersecurity-evals#footnote-2) 在多数这些评估里，环境不连接互联网，模型也被告知如此。

我们经常与外部伙伴合作，他们创建并协助运行某些这些网络安全评估。外部伙伴提供比我们独自所能构建更多样的环境和场景，并对我们的模型提供独立、第三方的评估。

## **发生了什么**

在我们审查的 141,006 次评估运行中，我们识别出三起独立事故（涉及总共六次运行，其中四次影响了同一家组织；另两起事故各发生在独立的评估运行中）。每起事故涉及一个不同的虚构夺旗场景——例如在一起里，Claude 扮演一家虚构公司的员工，在一个私有测试环境内攻击那家公司的内部系统。

在所有情形中，我们的评估 prompt 都明确写着 Claude 没有互联网访问，却没给 Claude 任何关于去哪找旗的限制。然而，一处配置错误让 Claude 作为评估一部分所访问的那些机器拥有实时的互联网访问。我们和我们的评估伙伴都不知道这个配置错误，直到上周我们通过额外的评估监控检测到了它。

若干纵深防御措施，在我们一侧和伙伴一侧都有的，本可以阻止这些事故、或至少降低其发生的可能。在评估开始前仔细校验所有互联网访问路径、并对评估日志做实时监控，本会帮助更早暴露问题。我们和我们的伙伴也本可以更彻底地审阅评估文字记录或网络日志。也可能一条告诉 Claude 它*确实*有互联网访问的 prompt，会在 Claude 接触到真实系统时改变其行为。

Claude 做了夺旗演练训练网络专家去做的事：寻找抵达旗的办法。那次搜索让它发现它的机器能访问互联网，但由于系统 prompt 告诉它没有互联网访问，Claude 认为它起初遇到的一切都是模拟的一部分，并把它发现的真实系统当作演练的构件。三起事故涉及三个不同的模型，而一旦目标为真的迹象浮现，每个模型的反应各不相同，我们下面描述。

### **事故 1**

在一次评估中，我们评估伙伴所选的虚构目标公司，与一个活跃的网站导航名同名。这个评估容器有非预期的直接互联网访问，由于上面讨论的那处误解。

在这评估的四次运行中，Claude 在评估环境内难以够到其模拟目标，但随后发现那家真实公司可通过互联网到达。假设这就是夺旗任务里预期的目标，Claude 搜寻、识别并利用该公司基础设施内的漏洞，认为它是演练的一部分。这四次运行提取了应用和基础设施凭证这类信息，并获得了访问一个含数百行生产数据的数据库。这代表我们识别到的最严重冲击。

该事故涉及 Claude Opus 4.7，是唯一一例模型在得知自己很可能运作在真实环境后仍继续攻击系统的。在这四次运行中，模型最终都认出（可从其被说出的推理中观察到）系统是真的——在两个案例里，模型强辩说那家真实公司一定是演练的一部分。然而没有一个因此停下攻击。

### **事故 2**

在另一次评估中，Claude 在虚构环境里发现一份文档，看起来像是另一家虚构公司给新开发者的安装设置说明。那些说明让员工从 PyPI——Python 软件发布的公共注册库——安装一个实际上并不存在的 Python 包。

Claude 把这看成一个潜在入口：如果它以同样的名字发布自己的包，那家虚构公司的系统会自动下载并安装它。于是，Claude 构建并以同名发布了一个恶意（本质上是设了陷阱的）Python 包，试图赢得夺旗挑战。

Claude 为执行这次攻击费了很大周章——这些周章本会向一位人类参与者表明这不再只是一次评估，而是他们确实在上传一个真实的 PyPI 包。例如，在一个案例里，为了创建一个 PyPI 账户，Claude 需要一个邮箱地址。而为了创建一个邮箱地址，它需要一个电话号码。为了得到一个电话号码，在找不到免费电话号码服务失败后，它试图——并失败地——通过若干不同方式筹款来付费购买一个号码。它最终折返，找到一个免费、未被屏蔽的邮箱服务商，用它注册了一个 PyPI 账户，然后用这个账户把恶意软件上传到 PyPI。

Claude 认为它所用的包注册库是模拟的一部分，但现实中，那个包在网上自由可得约一小时。在那段时间里，该包被下载并运行在 15 台真实系统上。其中一台系统属于一家真实安全公司（独立于场景中引入的虚构公司）的扫描器，它会例行地安装 Python 包并扫描其恶意软件。当那家公司的扫描器安装了该包时，Claude 隐藏的代码被执行了。我们相信该公司的安全扫描器把 PyPI 包当作可安全安装来处理，因此 Claude 得以把该公司的凭证外泄到它设置的一个收集点。随后 Claude 用这些凭证从这家公司访问了更多基础设施。

Claude 并未直接以这家公司为目标——它上传该包时甚至不知道这家公司存在。但因为代码被发布到了开放互联网，它冲击了任何运行它的系统。（Claude 上传的那个包被 PyPI 自己的安全系统自动从 PyPI 移除了。我们已就此事通知了 PyPI 团队，并提供了相关指标。）

这次攻击由 Claude Mythos 5 执行。在运行早期，Claude 自己的推理正确地识别出了它行动的后果。它指出，如果这是真实的互联网，发布该包会是一次真实世界的攻击——「不对，也肯定不是预期的解法」。然而，它说服自己仍在模拟之中，理由是它没有认出（现实中真实的）为它连接提供保障的证书颁发机构。此外，系统上 2026 年的日历日期，据 Claude 所言，证明环境是布景出来的。Claude 从未重审这一结论；例如当自动化扫描器开始安装该包时，Claude 把它们当作评估里被脚本驱动的参与者。

我们的观点是：无论它对自己的环境抱有什么信念，Claude 为发布 PyPI 包所费的周章都不够理想行为，而这正是我们要在训练上更多聚焦的领域。

### **事故 3**

在这次评估中，当 Claude 无法够到其预期的虚构目标时，它在网上寻找替代，扫描了约 9,000 个目标。它最终发现并攻陷了一家公司的面向互联网的应用，使用基础和众所周知的网络攻击技术，如从一个暴露的调试页面读取凭证和 SQL 注入。

这次攻击由一个内部研究测试模型执行。运行的多数时间里，Claude 把它够到的（真实）主机仅仅当作演练的一部分；它假设它们是模拟的，并相信它的行动因此无害。然而，在运行后期，Claude 意识到被攻陷的主机位于一个与夺旗挑战毫无关联的云账户里。它自行判定目标其实是真的，并停止了攻击。

## **我们对 Claude 行为的分析**

在每一个案例中，Claude 都被我们的 prompt 明确告知它没有互联网访问。在每次运行的多数时间里，当它遇到真实世界的系统时，Claude 假设这些是演练的一部分（尽管它有时认出它们是真实的生产系统）。而因为一个夺旗场景按其设计就是一道去攻击外部系统的指令，这样做符合 Claude 被给予的任务。

在这一共同背景之下，一旦目标为真的迹象浮现，三个模型行为各异。Opus 4.7，我们最早的模型，认出了它已够到生产系统，却继续其攻击。Mythos 5 正确直觉到它在访问开放互联网，却推理回到了「它仍在模拟中」的结论。我们最新的模型——一个内部研究测试模型——也考量了其目标是否其实为真。当证据浮现表明它们为真时，它终止了演练。

这是三起孤立事件，也不是某次受控的、实验性的对比。因此我们务必要谨慎地从它们得出结论。尽管如此，我们最希望看到的行为——认出目标是真实的、并在未被提示的情况下停下——只在三者中最新的那个模型上发生（而即便是那个模型，在停下之前也走得比我们希望的更远）。这一模式与更先进的模型作出更恰当的反应相一致，但我们需要做更多测试才有信心得出这一结论。

我们也正在与独立的 AI 评估组织 METR 磋商，进行一次第三方审查，包括对所有文字记录的访问、以及对相关模型的采样访问。在此期间，在未来一周内，我们会发布一份轻度脱敏的文字记录，其中 Claude 构建了一个恶意 PyPI 包。为保护受影响的组织，我们目前无法发布更多文字记录，但一旦能够，我们会设法把它们公开。

## **我们如何应对**

我们从这些事故中吸取几条教训。

首先，那些涉及强大专自主能力的评估环境*也*需要重大控制。安全测试发生在模型发布之前，恰恰因为我们还不知道它能做什么。评估环境越来越需要被以与我们模型运行所在的任何其他系统相同的安全标准来对待。

一个只含虚构场景的网络评估版图，看起来或许是低风险的——毕竟，里面没有东西是真实的。然而，随着 AI 能力进步，我们需要改变我们如何为这类威胁建模。即便在没有敏感信息访问的环境里，先进的 agent 本身就构成可观的威胁。我们需要更好地共同设计评估环境、并更好地监控评估结果，以应对这一威胁。这里的某些解法甚至可能是简单的修复；例如，如果 prompt 清楚解释了哪些系统在评估的范围之内、之外，Claude 很可能压根就不会去访问互联网。

这不仅适用于内部环境，也适用于第三方供应商——评估供应商所构建的基础设施需要同等的加强监控和加固。我们鼓励其他实验室做类似的审查。此外，整个领域会从一场更广泛的对话中受益：如何既安全*又*现实地评估日益强大的 AI agent，包括如何权衡部署前测试期间互联网访问所提供的现实性、与它所引入的风险。

其次，一个对齐动作与一个有害动作之间的界线，取决于模型对其所处情境的理解。我们在本文描述的任何一次运行中，都没有看到模型追求它自己某个目标的证据。相反，模型做了它们的评估所要求的——尽管在多数情形里，它们这样做时对环境是否为真抱有一个错误信念。在模型认出系统为真*并继续*的那些运行里，它之所以继续，是因为它假设那是挑战的一部分。情境感知是模型做出对齐决策的一个因素，但在这一情形里，Claude 的是错的。

最后，这些事故证明了纵深防御方法的重要性。我们运行像这样的能力评估时，不带我们普遍可用模型所随附的防护，因为我们的目标是衡量底层模型能做什么。只有当评估被恰当地约束住时，这才是安全的。然而，部署在我们普遍可用模型上的防护，本会拦截这些被识别的行为。

归根结底，许多因素促成了这些事故，但，与一种无责（blameless）复盘文化一致，我们把修复当作责任全在我们自己那样来对待。这始于确保我们评估流程的每一部分都是安全的，包括我们与外部伙伴集成的方式。向前，它将包括：扩展我们对评估文字记录中意外行为的持续监控、改进我们的调查工具、以及与我们所依赖的供应商做更严谨的保证工作。

我们在 OpenAI 披露其模型逃出了一个隔离测试环境之后开始了这次审查，我们赞赏他们[发布报告](https://openai.com/index/hugging-face-model-evaluation-security-incident/)。虽然我们也发现我们的模型够到了本不该够的系统的证据，但这些事故在其他方面很不相同：

- 我们在对网络安全评估文字记录的一次主动审查之后发现了这些事故；受影响的组织此前并未检测到该活动，我们随后已联系了全部三家。
- 而 OpenAI 的模型利用一个新漏洞逃出隔离，这里评估的 Claude 模型是通过一条敞开的路径访问互联网的。
- 尽管两者之间没有一道绝对锋利的界线，我们认为这些事故更接近一次 harness 和运营失败，而非一次模型对齐失败。我们的模型被告知它们没有互联网访问、要去夺取旗，而实际上却被配置成了有互联网访问。这让它们相信——可以说合理地——它们遇到的真实环境是模拟。
- 值得注意的是，我们最新的模型在意识到自己运作在一个真实环境里时，停止了其对评估目标的追求。

这些事实给了我们一种审慎的乐观：只要对评估基础设施有更紧的监控和控制、以及对对齐的持续投入，这类风险是可以被克服的。
