*如果您在 Claude Platform 中构建了一个包含多个子代理的代理，请查看使用我们的[迁移工具包](https://github.com/anthropics/single-agent-loop-kit)将哪些子代理合并到主代理循环中。它运行引导式工作流程来识别您的模式、评估替代方案并验证最佳方法。它包括一个演示，您可以在代理上运行之前在模拟系统上尝试。*

子代理——具有自己的上下文窗口、工具和指令的代理，由协调员精心编排——是代理设计的核心组件。它们在验证、并行工作和模块化许可方面非常有效。我们在使用 Claude Platform 构建的许多自己的代理中使用它们，例如我们的[多代理研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)。

然而，最近应用人工智能团队发现了一种企业代理部署模式，该模式受益于将路由器、规划器和域子代理折叠到主代理循环中。在[我们对多个企业部署的比较](https://claude.com/blog/the-anatomy-of- effective-commerce-agents#:~:text=In%20our%20comparisons%20across%20several%20enterprise%20deployments,latency%20per%20task)中，具有技能的单个代理的性能经常优于一提示所有设计和子代理设计注重质量，并且通常每个任务的成本和延迟都较低。

例如，一家公司发现其面向客户的代理中有数十个专业子代理，这使得一致的品牌体验难以维持，并且增加了延迟，从而损害了用户体验。

我们还经常看到提出的代理设计遵循熟悉的流程：意图分类器、固定的多步骤推理管道、用户细分存储桶、单独的推荐分支以及顶部的多代理协调器。

在这些情况下，反馈通常是该结构的大部分正在执行模型不再需要完成的工作，并且一个清晰的系统提示、4-5 个精简数据工具和牢固的输出护栏将覆盖大部分用例。

![子代理设计](https://assets.claude.com/a7cb2cf08bfcef461166310c0c55f28b72c33b0d.gif)

需要明确的是，子代理仍然占有一席之地，包括在研究前沿。在以下情况下使用它们：

- 单个代理循环会因上下文膨胀而导致可测量的性能下降，或者
- 需要使用新的上下文窗口并行处理多个任务，任务完成后可以将其丢弃，或者
- 单个代理难以选择合适的工具，或者系统提示中存在冲突的指令。

但我们经常看到企业为每个团队或问题类型提供自己的子代理，代理架构成为其组织结构图的副本（康威定律在起作用）。

这篇文章解释了何时考虑将子代理合并到主代理循环中，以及我们从大型组织中构建代理中学到的最佳实践。

## 大型组织的代理构建失败模式

公司通常希望建立一个代理，将多种产品和功能整合到一个客户界面中。

通常，每个功能都由一个单独的团队拥有，因此公司首先让每个单独的团队构建自己的代理，然后中央平台团队在顶部构建一个协调器。这可以采用多种结构，包括协调器子代理或具有作为 MCP 工具公开的特定代理的单个代理。

这看起来是最简单的解决方案，但会带来直接的复杂性：

- **上下文管理：**您需要决定在代理之间交换什么上下文，并且经常会在来回中丢失详细信息。
- **子代理蔓延**：每个团队都有自己的子代理，因此公司最终会出现数百个重叠的子代理，没有强制标准，也没有特定的所有者。
- **弗兰肯提示**：每个团队都会在系统提示中添加一句话，导致规则相互冲突，声音不一致。
- **未经审查、过度本地化的评估**：每个人都添加自己的评估，这些评估针对其子任务过度优化。没有人拥有或维护整个集合，领导层根据淡化的、过于本地化的分数做出决策。
- **延迟**：多代理架构的复杂性增加了延迟。一位客户根据单代理循环评估了多代理工具，发现后者的运行时间大约快了 2 倍。

## 使用渐进式披露的代理循环

上述协调器-子代理设计是协调跨团队构建的专家的合理方法，但通常更有效的方法可以是**通过技能逐步公开上下文**和**通过工具搜索逐步公开工具**。换句话说，代理会看到技能和工具的简短描述，仅在需要时才完全加载。

这种方法之所以有意义有以下三个原因：

- **共享上下文产生更好的答案：**对于运行时间较长的代理，我们希望来自多个不同任务的上下文位于主上下文窗口中。看到每个早期步骤结果的代理可以将它们连接起来，这比子代理传回的一组摘要会产生更丰富的输出和更好的见解。它还意味着[更少的上下文窗口和更少的有损切换](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)。
- **渐进式披露可防止上下文膨胀：**此技术允许团队构建可以完成各种任务的单个代理，而不需要将所有上下文立即加载到一个长系统提示中。这消除了团队之前在子代理之间分配工作的主要原因。事实上，我们[将 Claude Code 对更高级模型的系统提示减少了 80% 以上](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5- Generation-models/)，其中包括与逐步公开技能和工具相关的削减。
- **模型的能力更强：**从 Opus 4.5 开始，模型能够在单个循环中管理比大多数团队预期的更多内容。你无法停止对 Opus 5.5 和 Fable 5.1 的思考，最近的模型越来越多地叙述他们的进展并检查他们的工作，这使得一些线束元素变得多余。每个新模型都可以让您将更多决策从线束中转移到模型本身中。更简单的循环也更容易移动到下一个模型；在迁移过程中，我们为客户提供了帮助，严格的多代理结构通常会阻止新模型完成更多工作。

单代理循环设计需要纪律：精心管理的系统提示、在正确时间触发的技能和工具描述，以及对上下文窗口、内存和笔记的精心处理。本文将在后续部分中深入探讨迁移和设计注意事项。

一个中央团队应该负责端到端的质量和系统提示，在每一个新工具发布之前对其进行审查和评估。保持中心团队规模较小有助于快速迭代并降低大型组织的协调成本。

如果您采用多代理路线，请从最简单的可行模式（生成器-验证器、协调器-子代理或其他）开始。通过**除以上下文来有效地分解边界：为每个子代理提供一项几乎不需要系统其余部分的工作，并让它返回一个紧凑的结果**（好的候选者是独立的研究路径、具有干净接口的单独组件或黑盒验证）。当座席按问题类型划分时，他们会参与“电话游戏”，在每次切换时来回传递信息，从而降低保真度。

## 如何将子代理折叠到主代理循环中

许多团队已经在生产中拥有一名协调员和一组专业代理。以下是我们建议的单循环设计：

- 一个模型和一个上下文窗口运行一个开放式工具循环，并在线束中设置限制（转弯和成本预算、写入门）。
- 每回合，模型都会发出一批工具调用。线束并行运行它们并将原始结果返回到同一模型，该模型决定下一步：另一个批次、向用户提出问题或答案。
- 当模型回答或达到[预算](https://platform.claude.com/docs/en/build-with-claude/task-budgets)时，循环停止。目标或验证者检查可以选择在答案之后运行。
- 该模型在第一轮就根据上下文编写其计划，并在结果到达时对其进行修改。这是协调器和专家代理设置的主要变化：编写计划的模型也是执行计划的模型，因此它可以在中间更改计划。
- 上下文仍然被加载，并由代理本身管理：不再需要从规则目录重写计划的代码步骤，因为模型决定了每个步骤。排序和域过程移至**技能。**硬限制（验证、批准门）和对话中出现的任何其他内容（例如内存查找）移至**工具。**代码仍然可用于加载任何廉价且几乎总是相关的内容（例如实体解析）步骤），并处理循环调用的工具内的任何机械部分（有效负载构造、流解析、恢复说明）。

这种单循环设计还有助于实现许多团队正在努力实现的最终状态（一个了解用户的高级目标并代表他们采取行动的代理），因为它将代理所学到的所有内容都保留在一个上下文中。

下面的建议是团队如何分阶段从多代理系统过渡到单代理循环，以及多个团队如何在此过程中继续为该代理做出贡献。

### 任务完成评估

第一步是创建一个评估集，它可以帮助您确定是否应该将子代理折叠到主代理循环中。我们所看到的评估结构是一个共享的端到端集，由一个中心团队拥有，较小的评估集由拥有它的团队随每项技能一起提供。即使一组 10 个黄金示例也足以开始。

根据评分标准对座席的最终消息进行评分是跟踪答案质量的良好起点。虽然您仍然拥有协调器，但您还应该跟踪路由准确性（它是否选择了正确的子代理？）。一旦子代理被合并，请检查代理是否加载了正确的技能或调用了正确的工具。随着时间的推移，努力评估任务完成情况是有帮助的，因为这在比较架构时最重要。

在内部系统难以重放且用户参与难以模拟的环境中，这可能会很复杂。在我们内部有效的一种方法是记录重要事件的时间戳，以便稍后可以重播它们以作为目标评估运行。

### 随着时间的推移减少子代理

向单代理循环演进涉及将子代理折叠成工具和技能。这可以通过合并域子代理、将它们称为工具或用技能和工具替换它们来完成。

![折叠在子代理中](https://assets.claude.com/ed6bd97496ffdab88763806d9e14f1ec61ed9255.gif)

### 组合域代理

在第一次合并之前构建一个小型的端到端评估。然后**从最常用的子代理开始按共享上下文折叠。**

[合并专家](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them) 链接彼此的输出，接触相同的数据，或者经常被一起调用。例如，如果生产流量的很大一部分是一位专家，其次是一位专家，那么这就是一对紧密耦合的专家，这使得它成为合并到一个域代理的候选者。

### 子代理被称为工具

当上述三个条件之一适用并且您保留子代理时，让主代理将子代理作为工具调用是有效的，以便它可以继续与用户进行对话。

我们仅建议在需要直接与用户对话时进行完全切换，即子代理接管对话。其他一切都可以是主循环中的技能加工具。

这将允许您为子代理定义共享响应模式，使用主代理根据真实数据验证结论，并修剪任何最终综合步骤的输入。这是一个很好的第一步，因为您不需要**重写**子代理。在决定将任何子代理合并到主代理之前，它还为您提供了任务完成评估的**基线**。

然而，一些故障模式仍然存在：

- 每个专家都有自己的提示、背景、所有者团队和评估
- 每次调用仍然返回有损摘要
- 每个调用都是一个嵌套模型循环，会增加延迟

### 通过技能和工具将子代理折叠到主代理中

通过将每个子代理的提示转化为技能并将 API 调用转化为 MCP 工具，将子代理一次合并到主代理中。比较使用和不使用子代理的评估性能。然后决定保留哪一个。

当你进行比较时，不要只检查最终分数，还要看看哪些任务发生了翻转。当我们在示例支持代理上对此进行测试时，将一个子代理折叠到另一个降低的延迟中，但也破坏了已经通过的进程。主代理拿着订单查找工具自行回答，没有向运输专员询问交货日期。

在每次更改之前，请确保您的评估对在生产中一起运行的每个代理链都有一项任务，并且对于代理不得破坏的每条规则，并多次运行每个任务，因为像这样的破坏只会出现在两次运行中的一次。

## 多个团队如何为单个代理做出贡献

领域推理可以从知识库、技能和 MCP 工具中检索。各个团队可以将其所有权从代理转移到技能和工具，由一个小型中央团队保持对系统及时性和端到端质量的所有权。这涉及到在发布新技能、工具和评估之前对其进行审查。

### MCP 工具

当代理需要采取行动、从系统读取实时数据或以固定形式返回结果时，工具是正确的选择。您还可以使用工具在迁移时继续调用子代理。我们建议按用户意图分组工具（不是每个 API 一个工具），因为一旦系统提示中的工具定义超过 30-50 个，工具选择往往会降低。

使用带有延迟加载的[工具搜索](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)，限制硬性前提条件，并将任何需要的条件移至工具中。例如，如果 Y 需要 X 的输出，Y 的工具会检查它并返回模型可以执行的指令。每用户权限的工作方式相同。每个工具都会检查调用用户可能看到或执行的操作，并返回模型可以读取的简单拒绝，因此一个循环可以为具有不同访问权限的用户提供服务，而无需每个权限级别使用单独的代理。

### 技能

当座席需要了解团队如何工作时，技能是正确的选择，例如专家子座席提示所用的步骤、规则和判断呼叫。

我们发展技能库的方法是将维护工作交还给编写技能的人员。克劳德可以利用可以构建、测试和修剪其他技能的技能来完成繁重的工作。

为了防止技能蔓延，您可以让每个团队的 DRI 拥有自己的技能，并确保它们精心设计、独特并附带适当的评估。

- **/skill-creator** 允许您编写格式良好的新技能，并审核现有技能以修剪、删除重复和重组它们。
- **/skill-doctor** 允许您查看库中每项技能的成本以及实际使用的频率，并删除自重。

### 知识库

知识库非常适合代理仅在某些时候需要的参考材料。事实和参考材料（政策、指标定义、产品规格）可以位于模型调用的搜索或查找工具后面，或者作为技能内的参考文件提供。避免[代码检索此上下文并将其粘贴到提示中](https://claude.com/blog/seeing-like-an-agent)。

## 加速这项工作的工具

我们最近[发布了](https://code.claude.com/docs/en/commands)一套 Claude API 技能，可以帮助完成上述大部分工作。我们的[迁移套件](https://github.com/anthropics/single-agent-loop-kit)将这些技能链接在一个指导工作流程中，用于评估多代理系统并将其移动到单个代理循环。它包含一个演示，您可以在实际运行之前尝试一下：

- **/claude-api build-eval:** 可以帮助创建中央团队拥有的第一个端到端集合或每个团队以其技能提供的小型评估
- **/claude-api提示审计：**可以在提示、技能和工具描述中标记为旧模型编写的指令，并建议修复作为差异。这可以在您的系统提示上运行，以查找为早期模型添加的任何规则，这些规则现在使代理速度更慢或更严格。每个团队的 DRI 也可以根据自己的技能和工具描述来运行。
- **/claude-api hillclimb：**可以根据现有评估迭代改进应用程序。这可用于“折叠与保留”比较（将一个子代理折叠成技能加工具后，让它迭代技能和工具描述，看看折叠版本是否匹配或击败子代理）以及系统提示。
- **/claude-api 成本优化：**分析您的调用的去向，并建议通过提示缓存、修剪不需要的输入和输出令牌、工作量和模型选择等选项来节省费用，一次一项更改。这有助于降低给定设计的成本和延迟。

随着模型的发展，我们对如何最好地使用它们的理解以及最佳实践的指导也在不断发展。这使得任何一种架构都不如其背后的原则重要：衡量、一次改变一件事，并保留坚持的东西。

这是其中之一。随着模型的能力越来越强，代理的运行时间越来越长，更多的子代理可以成为技能和工具。不过，您不必一步到位。构建一个小型端到端评估，折叠一个子代理，仅当折叠版本得分较差时才将其保留为子代理，然后冲洗并重复。
