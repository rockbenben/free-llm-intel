# 管理成本并展示 Google Cloud 上 Claude Code 的投资回报率

随着组织把越来越多的工作交给 Claude Code，支出也随之增长，平台团队需要一种既能控制成本、又能理解影响的方式。受近期与 Google Cloud 共同举办的一场[网络研讨会](https://www.anthropic.com/webinars/how-to-control-costs-and-show-roi-for-claude-code-on-google-cloud)启发，我们分享使用 Claude Code 的组织如何在 Google Cloud 上更好地跟踪和优化这些考量，包括三个核心杠杆：控制、跟踪和证明。

## 管理 Claude Code 支出的控制措施

Google Cloud 上的 Claude 采用基于用量的定价，因此你的账单就是开发者在你的 Google Cloud 环境中使用 Claude 多少的读数。采用会推动用量；用量是你付费的对象，也是价值显现之处。

你的 Claude Code 账单是任务消耗多少 token 与处理这些任务的模型的乘积。token 消耗随任务复杂度和对话长度而增长。Chat 是一问一答的对话。像 Claude Code 这样的 agent 工具相对 chat 而言每个任务会消耗更多 token，因为它在做多步骤工作：读取文件、运行工具，并在整个任务范围内推理。与此同时，每个模型都有各自的每 token 价格，因此[让模型与任务相匹配](https://claude.com/blog/claude-model-and-effort-level-in-claude-code)是另一项主要的成本控制手段。

通过 [Claude apps gateway](https://claude.com/blog/introducing-the-claude-apps-gateway) 和 Google Cloud 服务，可以了解每月影响组织账单的 token 与模型选择。你可以通过三个独立的杠杆来治理支出、管理成本：

- **控制**。建立护栏来引导用量，而不过度限制访问、意外地挡住人。
- **跟踪**。在账单到来之前，细粒度地掌握支出发生在哪里，以及接下来还会流向哪里。
- **证明**。识别组织从这些 token 支出中获得了什么价值，并精确归因价值来自何处。

以下是如何将这套 control → track → prove 框架应用到你自己在 Google Cloud 上的 Claude Code 部署。

### 治理工具箱

Google Cloud 上的 Claude 附带用于控制、跟踪和证明支出价值的工具与能力。

![展示 Google Cloud 原生能力与 Claude Code + Claude apps gateway 附加能力的图示](https://assets.claude.com/b3266f5cebd6e2613593339d21200b3a7c034b9a.png)

Google Cloud 已经提供了许多原生能力，可用于跟踪和控制你的 Claude 支出：

- **按项目计费**。允许你为 Claude Code 托管一个专用项目，作为跟踪成本的干净方式。
- **账单预算与提醒**。允许你设置预算提醒，并在实际支出越过你设定的阈值时收到通知。
- **支出上限（预览）**。允许你为 Google Cloud 服务级支出强制设定预算，并可手动解除上限。
- **BigQuery 导出**。让你可以把 Claude 支出与其余云成本一起分析。
- **配额**。Google Cloud 上的 Claude 模型对每个模型家族和 endpoint 位置的请求数、输入 token 和输出 token 都有每分钟限制。
- **预置吞吐量**。为预留容量支付固定费用，而不是按量付费。

Claude Code 和 Claude apps gateway 增加了各自的跟踪与控制能力。gateway 是一项自托管服务，随开发者已经在使用的同一个 `claude` 二进制文件一同交付，运行在你的 Google Cloud 项目中，位于 Claude Code 与 Google Cloud 上的 Claude 之间。开发者通过你的身份提供商（例如 Google Workspace）登录，因此每个请求都携带经过验证的身份。这让你可以按 IdP 组设置模型允许清单，并按天、周或月设置按用户、IdP 组或组织的支出上限。

以下是如何选择并组合这些能力，来管理衡量组织在 Google Cloud 上用 Claude 所做 AI 投资的成本与 ROI 的三个杠杆：

#### 杠杆 1：控制

控制杠杆的核心是提供护栏，引导开发者使用 Claude Code，而不是用任意的上限去限制他们。

引导而非限制之所以重要，是因为高成本会话不一定就是坏事——事实上，它们往往价值很高，在 Claude Code 中尤其如此。这些会话通常来自你的重度用户，他们处在最前沿，使用新的工作流，从 Claude 获得很多价值，也完成了大量工作。

浪费往往出现在高支出者的长尾中段。例如，他们用 Fable 处理 Sonnet 轻松就能应付的日常事务。又或者，他们忘了某个已经不再关心的定时任务，但它仍在自动运行。

有四项功能可以为你提供护栏，去引导用户而不是限制用户：

- **[支出限额](https://code.claude.com/docs/en/claude-apps-gateway-spend-limits)**。Claude apps gateway 允许你按天、周或月设置按用户、按 IdP 组或组织范围的支出上限。组和组织上限是每位开发者继承的默认值，而不是共享池。
- **阈值提醒**。与 Claude apps gateway 一起使用时，Google Cloud 上的 Claude Code 会在开发者接近上限时提醒他们，第一次是超过 75%，再次是超过 95%。这些是面向开发者的 CLI 内提醒，而 Google Cloud Billing 的提醒是给管理员的。达到上限时，gateway 会返回 429，直到周期重置或管理员提高上限；你也可以通过 gateway 的管理 API 用脚本提高上限。
- **模型默认值与允许清单**。通过 Claude apps gateway 按 IdP 组指定哪些模型可用，gateway 会在服务端对每个请求强制执行允许清单。我们发现设置模型默认值效果非常好，因为大多数人会沿用默认模型；如果他们想切换模型，通常是有原因的。你可以在模型允许清单之外额外使用模型默认值，也可以用模型默认值代替它。
- **Gateway Admin API**。gateway 提供用于[支出限额的管理 API](https://code.claude.com/docs/en/claude-apps-gateway-spend-limits)，因此你可以用程序设置和更改上限，例如使用工单工作流。

![展示支出上限生命周期各阶段的图示](https://assets.claude.com/d1ded8cd5410c90e62905f650bf2a4e09df4cdce.png)

把这些能力组合起来控制你的总体账单，但请记住控制只是第一个杠杆。每 token 的价格并不能给你全貌。最重要的指标是每个任务的成本，而它可以通过跟踪这些用量来监控和分析。

#### 杠杆 2：跟踪

这个杠杆的核心是看清支出流向哪里、如何被使用。好消息是，你可以跟踪整个组织中 Claude Code 的用量、成本和工具活动。主要的跟踪策略包括：

- **用量与成本可观测性**。[Claude Code 的 OpenTelemetry 指标与事件](https://code.claude.com/docs/en/monitoring-usage)会报告用量与估算成本，并按技能、插件、agent 和 MCP server 拆分。通过 OpenTelemetry 收集器，或经由 Claude apps gateway 中转（用于集中式 OpenTelemetry 配置），用 OpenTelemetry Protocol（OTLP）把它们发送到你已经在运行的工具，例如 Google Cloud Monitoring。
- **终端用户用量视图**。开发者在 Claude Code 内就能看到自己的支出，并在触及上限之前收到用量警告。
- **导出数据到你现有的系统**。Google Cloud Billing 导出到 BigQuery 后，你可以按模型和 token 类型筛选 Claude SKU，把 Claude 支出与其余云和 AI 支出放在一起。OTel 数据流向你的可观测性（O11y）技术栈，而 gateway 的管理 API 可以把支出限额状态直接送入你的工单系统。

![展示 Google Cloud 上 Claude Code 遥测的图示](https://assets.claude.com/f2ab59204d683994ef32ddc5b4e6f1167389a800.png)

Claude Code 无论运行在开发者机器还是云工作站上，一经启用即可导出 OpenTelemetry 数据，包括会话、活跃时间、代码行数、提交、pull request、token 与成本，并按用户、团队和模型拆分。Claude Code 最近的版本还按技能、插件、agent 和 MCP server 拆解用量，因此你不仅能看到 Claude Code 的整体用量，还能看到组织内部哪些技能和插件被采用。使用 Claude apps gateway 时，你无需配置每台机器。在 gateway 上设置一个遥测目标，它就会为已登录的开发者开启遥测。它还会为每次导出打上开发者登录时经过验证的邮箱和 IdP 组，而不是客户端上配置的值。

要把用量归因到你自己的成本中心和部门，请设置 OTEL_RESOURCE_ATTRIBUTES 环境变量（例如 department=engineering,cost_center=eng-123）。Claude Code 会把这些标签加到每个指标和事件上，因此你可以按它们筛选和聚合。指标会带着这些自定义属性进入 Google Cloud Monitoring（或 Grafana、Splunk 等其他监控方案）。

Cloud Monitoring 中的 Claude Code 用量仪表盘，基于 Claude Code 的 OpenTelemetry 指标构建。使用示例数据做的示意性重现。

典型的采用情况视图会显示活跃开发者、过去 24 小时的会话数以及消耗的 token 总量。橙色方框显示开发者触及 gateway 强制执行的支出上限时被阻止的请求。该指标与你现有的工单系统配合得很好，可形成一套允许开发者申请提高上限的工作流。

关于现成的 Cloud Monitoring 仪表盘，请参考 [Claude Code Monitoring 模板](https://github.com/GoogleCloudPlatform/monitoring-dashboard-samples/tree/master/dashboards/claude-code)，它把 Claude Code 的 OpenTelemetry 指标汇成采用情况、编码活动、token 用量与估算支出的单一视图，让你在 Google Cloud 上推广 Claude Code 的过程中按用户和模型跟踪用量与成本。你可以直接在 Cloud Monitoring 控制台内复制这个模板。

要在 Google Cloud 上设置自定义的 Claude Code 遥测，请从 [Claude Code OTel 快速入门](https://github.com/Google-Cloud-AI/partner-ai-anthropic/tree/main/01-quickstart/otlp-to-telemetry-api)开始。用它来配置 Claude Code，把 OpenTelemetry 直接导出到 Google Cloud Observability 套件，包括 Cloud Logging 和 Cloud Monitoring。该快速入门还会把日志路由到分区 BigQuery 表，每种事件类型一张表（API 请求、工具决策、工具结果、助手响应和已完成的 hook 执行），并附带 SQL 查询，用于按开发者/模型的支出、工具成功率与延迟、hook 等待时间、按轮次和按会话的分析。

#### 杠杆 3：证明

控制杠杆治理并分配用量与成本；跟踪杠杆让你把支出可视化。证明杠杆则是你把用量映射为 Google Cloud 上 Claude Code 的 ROI 的方式。

平台工程师在 Claude Code 中最关心的度量指标包含在三个维度中：用量、开发者满意度和影响。

**采用与用量**指标衡量人们如何在你的组织中使用 Claude，包括已激活用户及其每周和每日用量。这些指标揭示使用深度、用户留存随时间的变化，以及谁是 Claude Code 的重度用户。这些指标全部来自 Claude Code 的 OTel 数据。

**满意度**指标监测你的工程师的用户体验，包括他们对 Claude Code 的满意程度、感知到的时间节省、对输出的信心，以及他们可能遇到的任何摩擦。满意度指标来自推广前后各一次简短调查，以及持续的用户回访。

**影响**指标评估 Claude 如何带来可衡量的工程成果，把吞吐量、周期时间和评审速度与基线对比，并对具体工作体做定性衡量。

### 一组起步的影响指标

以下是一组起步的影响指标，分为三个领域：时间、投入和产出量。

**时间**衡量工作交付的速度：PR 从开启到合并的周期时间，以及代码评审的周转时间。

**投入**衡量每个变更需要多少工作：每个 PR 的评审迭代次数、每个 PR 的评审意见与返工。

**产出量**衡量释放出的产能带来了什么：每位工程师的 PR 数、部署频率，以及点名的工作体——你的团队用释放出的产能交付的具体 backlog 事项。这些在计数之外增加了定性视角。

这些是指引性的参考点，不是规则，但它们是衡量 Claude Code 在你组织中影响的一个良好起点。你所需要的基线已经存在：源代码管理和工单中的交付历史。

### 定义你的工作单元

这些指标大多在数 PR，但修正一个拼写错误和发布一个功能都算一个 PR。因此，改为统计某一已定义类别的已合并 PR：Claude 打开 PR，由人来决定它是否上线。hotfix 或 feature release 这样的标签、工单 ID，以及 Claude 是否参与其中，能让这些 PR 在你已经运行的系统里容易被找到。并非每个工作单元都是 PR；服务切换，或在根因层面关闭的一次事故，都是例子。适用同样的规则：数一件完成的事，以它落地的地方为准。

## Claude Code 原生遥测

在把成本治理和用量跟踪落实到位之后，下一步是把它们映射到 ROI。Claude Code 的原生遥测帮助你获取贡献与生产力指标，用以记录组织正在获得的价值。

![展示 Claude Code 原生遥测的图示，分三列：用量、成本、贡献 / 生产力。](https://assets.claude.com/5d1a4e740237e04f4524c9ff169e0f70def7c5ab.png)

Claude Code 的 OTel 指标让你可以跟踪或推导代码建议接受率、修改的代码行数、创建的提交、创建的 PR、每单位产出的成本，以及每位用户的 PR 数。

所有这些原生指标都提供有用且可行动的信息。当这些信息与记录下来的事件（如用户 prompt 和工具决策）配对时，会变得更有价值，这些事件可通过 [Google Cloud 上的 Claude Code 遥测](https://docs.google.com/document/d/1LezclyuvbRQ9tInAet0loCEPiNIITB8eLHvzNik9IBs/edit?tab=t.nr7gi1cdf1oi#heading=h.vdcj39wwyv9f)捕获。例如，记录用户 prompt 是了解你的用户群想构建什么的好方法，因为并非每个工作单元都必然是 PR。请注意，由于内容可能敏感，用户 prompt 不会被自动记录；你必须专门选择开启。

举一个例子：如果你是 SRE，可以用 Claude Code 排查一次事故；如果你是售前工程师，可以用它为现场演示生成示例数据。这些会话不会产生 PR，但确实加速了这些团队的工作流。请记住，Claude Code 的 PR 指标统计的是 Claude Code *创建*的 PR，而不是最终合并的数量。你的源代码管理和工单系统仍然是「上线了什么」的记录，因此要把 Claude Code 遥测与 GitHub 或 GitLab 以及你的工单跟踪系统关联起来，才能得到全貌。

以下是部分 Google Cloud 上的 Claude 客户使用 Claude Code 所取得的可衡量影响。

- [Delivery Hero](https://claude.com/customers/delivery-hero) 有一个团队对 100 个 UI 组件的设计系统做了全面改造。Claude Code 在几分钟内完成了通常需要一名工程师一周时间的工作。
- [Shopify](https://claude.com/customers/shopify)的工程师用 Claude Code 构建得更快，但非工程师也在几分钟内而不是几天内构建内部工具。Claude Code 在 Shopify 扩大的是「谁能构建」，而不只是加快已经在构建的人。
- [Fifth Dimension](https://cloud.google.com/customers/fifth-dimension-anthropic) 的工程师普遍在 Google Cloud 上使用 Claude Code。他们合计每月编写超过 300,000 行代码，接受率达 98%。

## 开始使用

本文的目标是帮你熟悉现有的工具与能力，用它们管理 Google Cloud 上 Claude Code 的成本并展示 ROI。作为平台工程师，这套系统不仅用于察觉和观察用户群中的行为，它还给你动态调整治理与设置所需的知识。

这是一个持续循环：从合理的默认值开始，例如组织范围的支出上限、默认模型和模型允许清单，然后随着用量数据的到来按角色和团队细化。通过跟踪实际使用并把指标与从 Claude Code 获得的价值关联起来，你就可以把这些交付给需要分析使用 Claude Code 的 ROI 与业务影响的利益相关方。

![展示 Control - Track - Prove 框架持续循环的图示](https://assets.claude.com/9a83ef407d2df018b107f8108d1955ad70702d7f.png)

组织如何使用 Google Cloud 上的 Claude Code，以及从这些使用中获得的价值，都会随着我们交给 Claude 的工作量和工作类型不断加深、更加多样而演变。这里概述的 **control → track → prove** 框架，是衡量 Claude Code 部署各个方面与成果的稳定起点。
