# 我们如何在各产品中约束 Claude

发布于 2026 年 5 月 25 日

随着 agent 能力增强，它们潜在的「爆炸半径」也在扩大。工程上的问题是如何给它设上限。以下是我们构建 claude.ai、Claude Code 和 Cowork 约束体系时学到的经验。

十二个月前，我们会当场否决「给 Claude 足够权限、以至于能搞垮一个 Anthropic 内部服务」这样的想法。今天，这种级别的访问已是常态，而 Anthropic 的开发人员因此更高效。这类部署的风险由两部分组成：一次失败有多可能发生，以及一次失败能造成多大损害。防护和模型训练上的进展一直在压低第一者；而第二者——理论爆炸半径——只随着能力和访问的扩展而增大。然而，当 agent 变得能够完成过去需要一个人甚至一个团队的工作时，*不*部署的代价变得足够大，以至于风险-收益的天平强烈倾向采用——只要产品能被做得安全。工程上的问题就变成了如何给爆炸半径设上限。

当能给一个自主 agent 的相对损害设界——比如通过控制其运行环境——高实用性的能力就能成为部署的理由。Claude Mythos Preview 就是一个例子：2026 年 4 月，它的爆炸半径被认为太高、不宜发布。不过，随着防守方加固关键系统、防护逐步成熟，我们预期具有类似能力水平的模型会更广泛地发布——尽管某些风险始终存在。模型能力是 agent 部署总风险中的一个重要因素。

大体上有两种做法。

第一种是通过人在回路（human-in-the-loop）来监督 agent 的行为。Claude Code 过去通过在每一轮向用户请求许可，来防止 agent 采取非预期动作。理论上这行得通，但我们发现这种做法容易失效。我们的遥测数据显示，用户批准了约 93% 的许可提示。用户看到的批准请求越多，他们对每一条投入的注意力就越少，随着时间推移，其监督变得不那么勤勉。我们最近构建了 Claude Code auto 模式，[自动化那些更安全的批准](https://www.anthropic.com/engineering/claude-code-auto-mode) 以减轻这种批准疲劳。但漏洞仍然存在——任何概率性的防护都有一个非零的漏检率。1

约束爆炸半径的第二种做法——也是本文的重点——是约束（containment）。与其监督 agent *做* 什么，我们监督它 *能做* 什么，方法是通过沙箱、虚拟机和出网管控等手段强制执行访问边界。这是 Anthropic 工程投入最多精力的地方，也是许多最出人意料的安全失败发生的地方。

过去两年，我们发布了三款主要的 agentic 产品：[claude.ai](http://claude.ai/redirect/website.v1.cfa522b9-0c91-4cdc-8682-37f2a645bcc9)、Claude Code 和 Claude Cowork。各自服务不同的受众，需要不同的约束架构。本文分享哪些经受住了考验、哪些出了事，以及我们一路上关于 agent 安全学到的东西。

## **三类风险，三道防务**

对 agent 的安全风险落入三类之一：

**用户滥用：** 一个用户——出于恶意或粗心——指挥 agent 做有害的事。这从要求 agent 绕过某道他觉得烦人的检查，到运行一条他不理解的破坏性命令，再到蓄意指定伤害，无所不包。

**模型失当：** agent 采取了一个没人要求的有害动作。随着模型改进，它们在大多数行为评测上更加对齐，但这并不意味着风险必然缩小。能力较弱的模型更可能误读情境、犯明显的错误。能力更强的模型犯错更少，但也更擅于找到通往目标的意外路径，常常通过绕开那些没人想到要写下来的限制。

在 Anthropic，我们见过 Claude 模型为了完成一个任务而「热心地」[逃出沙箱](https://red.anthropic.com/2026/mythos-preview/)，检查 git 历史以[找到一道编码测试的答案](https://assets.anthropic.com/m/64823ba7485345a7/Claude-Opus-4-5-System-Card.pdf)，以及自发识别它正在跑的基准以便[解密其答案密钥](https://www.anthropic.com/engineering/eval-awareness-browsecomp)。每个模型都带来一套新能力，有时被以出人意料的方式调动起来。

**外部攻击者：** agent 通过工具、文件或网络访问等外部向量被攻击。这一类既包括 prompt 注入，也包括针对 agent 运行时、编排层或代理的传统攻击。

在构建约束和防御系统时，我们把防线施加在三个主要组件上：

**agent 运行的环境。** 我们用进程沙箱、虚拟机、文件系统边界和出网管控来约束 agent 能在何处、如何行动。目标是设定一条硬性边界，界定 agent 能触达什么。例如，如果凭证从不进入沙箱，那么无论起因是用户、是模型找到一条「创造性」路径，还是攻击者，它们都无法被外泄。

一道紧密的边界也意味着你可以放宽监督。Claude Code 的[参考 devcontainer](https://code.claude.com/docs/en/devcontainer) 正是为此存在，好让 agent 能无人值守地运行，而不需要逐动作批准。

**agent consults 所咨询的模型。** 这里的机制包括系统 prompt、分类器、探针和训练修改。由于模型是概率性的，这些手段只塑造 agent *倾向于* 做什么，而非它理论上能做什么。

这些防线是强大的。在 Gray Swan 的 Agent Red Teaming 基准上——它测试对 prompt 注入的易感性——[Claude Opus 4.7](https://cdn.sanity.io/files/4zrzovbb/website/037f06850df7fbe871e206dad004c3db5fd50340.pdf) 把单次尝试的攻击成功率压制到约 0.1%，100 次自适应尝试后约 5–6%。Claude Code auto 模式在约 83% 的过度积极行为[执行之前](https://www.anthropic.com/engineering/claude-code-auto-mode)就将其捕获。但即便有业界领先的防线，模型层的保护永远不可能 100% 有效，这也是为什么它不能独自扛起。

**agent 能触达的外部内容。** MCP 服务器、第三方插件和网络搜索工具，都把你无法控制的来源的内容馈入 agent 的上下文。一个经过审计的连接器并不等于经过审计的数据——举例说，一个 GitHub 连接器可以把一份被投毒的 README 直接加载进模型的上下文，尽管它通过了恶意软件检查。细致地限制工具权限能帮助限制爆炸半径。例如，一个只有数据库只读访问的 agent，可以比一个会写入生产的 agent 部署得广泛得多。

防线应当彼此重叠、互为补充。当环境层的防线不可用时，模型层就得补上这个缺口（这正是 Claude Code [auto 模式](https://claude.com/blog/auto-mode)的设计初衷）。在本地，环境和模型防线可以防御恶意的工具输出，但防线也可以加在链条更上方、通过限制工具的能力和访问来实现。

要防御的三个组件：模型、它运行的环境，以及 agent 能触达的外部内容。

## **约束 agent 的模式**

聚焦于环境层，我们描述三种隔离模式，以及它们如何为每个 Claude 平台——[claude.ai](http://claude.ai/redirect/website.v1.cfa522b9-0c91-4cdc-8682-37f2a645bcc9)、Claude Code 和 Cowork——量身调整。我们是在找到 agent 所需能力与用户所需干预程度之间的平衡之后，逐步得出每种设计的。

### **模式 1：短暂容器（claude.ai 代码执行）**

尽管 claude.ai 最为人所知的是一个聊天界面，它也能编写和运行代码、生成文件、调用连接器。当 Claude 在 claude.ai 内运行代码时，它是在隔离基础设施上的一个 [gVisor](https://en.wikipedia.org/wiki/GVisor) 容器里做的。agent 完全在服务端；本地机器上不运行任何代码，文件系统是短暂的（每会话一个）。爆炸半径极小，但 Claude 能做什么的上限也极小——没有持久工作区，也访问不到用户的文件系统。

这也让 [claude.ai](http://claude.ai/redirect/website.v1.cfa522b9-0c91-4cdc-8682-37f2a645bcc9) 服从一个更传统的威胁模型。我们要保护的不是用户的机器免受 agent 之害；而是保护我们自己的基础设施，以及让各租户彼此隔离。我们为 [claude.ai](http://claude.ai/redirect/website.v1.cfa522b9-0c91-4cdc-8682-37f2a645bcc9) 做的发布前工作，以传统安全工作为主，如网络配置、内部服务认证和编排。

那项工作强化了安全领域最古老的那条教训：最薄弱的一层，是你自己亲手搭的那层。gVisor 和 [seccomp](https://en.wikipedia.org/wiki/Seccomp) 抵御资源充足的对手已经久得超过 agentic AI 的存在时间，所以审查的精力都花在了我们围绕它们新建的那些部件上。我们稍后会回到这点，因为在我们影响最大的一次事故中，出问题的也正是我们的自定义代理。

### **模式 2：人在回路沙箱（Claude Code）**

Claude Code 运行在用户的机器上，访问其文件系统、shell 和网络。没有这些，编码 agent 的用处就很有限，因此必须找到一种安全授予这种访问的办法。

一种做法是依赖人在回路。这对 Claude Code 才可行，因为平均用户是熟悉编码环境的开发者：他能读 bash、明白 `rm -rf` 做什么、一周里已经从不信任来源跑过好几次 npm install。这一切意味着，当一个「允许这个吗」的对话框弹出时，他们很可能具备评估 agent 打算做什么、以及其中风险的专业知识。有鉴于此，Claude Code 以最简单的防线发布：允许读取，写入、bash 和网络访问需要批准。

然而，如前所述，批准疲劳[在几周内](https://www.reddit.com/r/ClaudeAI/comments/1rru8zw/just_picked_up_a_new_keyboard_cant_wait_to_write/)就显现了。讽刺的是，这意味着一个本为提供监督而设计的功能，可能反而起了相反作用——一些用户可能干脆不再留意。作为缓解轻率批准的第一步，我们发布了一个操作系统级沙箱（macOS 上的 Seatbelt，Linux 上的 bubblewrap），加固边界：允许读取，允许在工作区内写入，但默认拒绝网络。在沙箱内，agent 大体上无需被打断地运行。结果是许可提示减少了 84%，而我们把[运行时开源](https://github.com/anthropic-experimental/sandbox-runtime)了，让边界可审计。

我们的[匿名使用数据](https://www.anthropic.com/news/measuring-agent-autonomy)也显示，资深用户自动批准的概率约是新用户的两倍，但他们也更频繁地在中途打断 agent。资深用户不是逐步做门控，而是只在 agent 跑偏时才去监督。这或许是人类偏爱与 agent 共事方式的一种自然演进，但它同样易失，要求用户足够技术、足够专注，才能从一开始就注意到漂移。随着模型能力提升、agent 开始编写越来越有雄心的 bash，要注意到这种漂移就更难了。而当用户转向多 agent 系统时，这种做法也更不太可能是一种有效的监督策略。

#### **我们漏掉的风险：信任对话框之前的一切**

2025 年中到 2026 年 1 月间，我们通过负责任披露程序收到了关于 Claude Code 漏洞的报告。其中三个漏洞针对的是在用户尚未同意任何事 *之前* 执行的代码。要理解这怎么可能，考虑最直接的情形：一个开发者克隆一个仓库来审阅一个 pull request，而该仓库含有一个定义了一个 hook 的 .claude/settings.json。因为 Claude Code 在启动时——在弹出标准的「你信任这个文件夹吗？」提示之前——就读取项目设置——攻击者编写并提交的那个 hook 就会被自动执行。其余的情形结构上类似，即在信任边界建立之前，就解析了来自那个尚未被信任目录的输入。

每种情形的修复都是同样的形状：把项目本地配置的解析和执行推迟到用户接受信任提示之后。如果你在构建类似的东西，把项目打开、配置加载和 localhost 监听器，都当作你在处理任何来自互联网的入站请求来对待。它们不该仅仅因为感觉是本地来的、且在用户同意之前就到达，而被默认信任。

#### **我们漏掉的风险：把用户当作注入向量**

2026 年 2 月，在一次受控的内部红队演练中，一名研究员成功钓鱼了一位员工，让其带着一个恶意 prompt 启动 Claude Code。那封钓鱼邮件看起来像普通的协作——一封「你能替我跑这个吗？」的邮件，附着一个可直接粘贴的 prompt——而 prompt 本身读起来像常规的任务指令。但在某些设置步骤中间，它温和地要求 Claude 读取 ~/.aws/credentials、编码其内容，并把它们 POST 到一个外部端点。在该 prompt 的 25 次重试中，Claude 完成了 24 次外泄。

这是一次 *直接* 的 prompt 注入——攻击者的指令是经用户到达的，而非经工具输出或抓取的内容。我们的模型层防线锚定在用户意图上——当输入指令的是用户本人时，分类器没有任何异常可抓。一个人类承包商拿到同样的脚本，也会做同样的事。

在这种情形下唯一站得住的防线是环境，具体说是阻断 POST（无论意图如何）的出网管控，以及一开始就把 ~/.aws 挡在可及之外的文件系统边界。

（当我们把可用的 prompt 分享进内部 Slack 讨论时，有人指出某些内部 agent 会 *读取* Slack。载荷就此变成了环境中的东西。我们在那条讨论串里加了一个[金丝雀字符串](https://www.fortinet.com/resources/cyberglossary/what-is-canary-in-cybersecurity)，好让我们察觉是否有东西捡起了它。在一个 agent 阅读一切的世界里，调查工具本身也是一个攻击面。）

### **模式 3：本地虚拟机（Claude Cowork）**

Claude Cowork 运行在用户的桌面上，访问一个由用户选定的工作区文件夹。因为该平台是为一般知识工作而非软件工程构建的，平均用户远不那么可能精通 bash。

结果，人在回路沙箱的策略可能无法迁移；一个非技术的知识工作者，不该被指望去判断像 `find . -name "*.tmp" -exec rm {} \;` 这样的 bash 咒语。当批准一个例外需要典型用户并不具备的专业知识时，管理员就该设一条绝对的、始终在线的边界。

为实现这一点，我们 Claude Cowork 的最初版本在一个完整的虚拟机里运行，使用平台的厂商 hypervisor（macOS 上的 Apple Virtualization framework，Windows 上的 HCS）。这个 VM 有自己的 Linux 内核、自己的文件系统和自己的进程表。用户选定的工作区和 .claude 文件夹被挂载；主机上的其他任何东西都不可见。凭证留在主机的钥匙串里，永不进入来宾机。这一设计防范了 Claude 在某个时刻以失当方式行事的可能性。一个被攻破的 Claude 仍可能损坏工作区文件夹里的东西，因此架构被设计成确保那是它 *唯一* 能触达的东西（直到用户添加连接器），且由用户控制挂载那里的内容。

在最初这个架构——我们称的 full-VM 模式——里，agent 循环本身运行在来宾机内，因此 Claude 作为一个普通的 Linux 用户执行、并不自知自己被沙箱化了。对比 Claude Code，那里有一个特权进程坐在沙箱之外，逐命令地决定是否强制执行；一个有说服力的注入 prompt 或一次疲劳的批准点击，就能让那个进程去运行某个未沙箱化的东西。在这里，没有任何外层进程握着逃生舱的钥匙，因此也就没有任何有权批准例外的组件。

Claude Cowork VM 的六大隔离机制。其中两个在来宾内核之外强制执行，因而能在 agent 于 VM 内获得 root 级访问后依然幸存。另外四个由来宾机执行、并被刻意保持最简，因为外层承担了其余部分。

然而，我们很快意识到，把整个 agent 跑在 full-VM 模式会带来实际问题：VM 启动过程中的任何失败都会让 Cowork 不可用。把 agent 循环移 *到* VM *之外*、同时把代码执行留在里面，让 Claude 仍能回应用户、帮忙调试问题，而不是卡死在一个错误上。这一改动造成的安全影响极小，因为 VM 仍对 agent 执行的代码施加文件系统和网络管控。

另外，我们也把本地 MCP 服务器移到了 VM 之外。把它们跑在 VM 内，让它们更难被审计、在 VM 更新时制造脆弱的依赖问题，也不支持那些需要与本地进程（如数据库）交互的 MCP——这样的服务器无论如何都得跑在主机上。这一改动让 Claude Cowork 与本地 MCP 服务器在 Claude Desktop 中已有的方式对齐：把它们当作任何用户可能选择安装的软件来对待，并把决定启用哪些本地 MCP（若有）的责任交给管理员。远程 MCP 服务器不受影响，因为它们不在用户机器上运行。

把 agent 循环放在 VM 内，意味着 VM 里的任何失败都会让 Cowork 变得不可用。host 模式更可靠，因为即使 VM 崩溃，agent 仍能回应，同时它通过隔离代码执行仍然提供重要的安全保障。

文件系统控制是另一个重要的架构选择。Claude 需要能访问主机上 *某些* 文件才有用，但我们想最小化爆炸半径、并就本地文件访问向用户提供透明度。我们发现，提供不同的文件挂载模式有助于细致地控制风险；Claude Cowork 提供只读、读写、读写不可删除三种。这里一个潜在的坑是：符号链接的解析必须 *在* 路径校验之前发生，而非之后，否则一个位于已授权文件夹内的符号链接可以指向外面、从而逃逸。对企业客户，我们允许管理员通过 MDM 设置里的挂载路径允许清单来控制这一点。

#### **我们漏掉的风险：通过一个获批准域的泄密**

一个通过获批准域外泄数据的清晰例子，来自一次第三方披露。Claude Cowork 的出网允许清单正确地放行前往 api.anthropic.com 的流量——不调用我们自己的 API，该产品无法工作。在这个案例中，一个恶意文件被放入用户挂载的工作区，里面带着隐藏指令以及一个由攻击者控制的 API 密钥。Claude 遵照指令，读取了工作区里的其他文件，并用攻击者的密钥调用 Anthropic 的 Files API。出网代理检查了目的地，看到 api.anthropic.com，就放行了。文件被上传到了攻击者的 Anthropic 账户。沙箱完美工作，数据却仍被外泄了。

此前，我们把允许清单概念化为一个目的地过滤器——某种告诉 Claude *这些域名可以交谈* 的东西。但它也许最好被概念化为一次能力授予。经由允许清单上任何域名可达的每一个函数，如今都是一个攻击面。允许 api.anthropic.com 就意味着允许向任意 Anthropic 账户上传文件。

我们用 VM 内部一个防御性的中间人（man-in-the-middle）代理修复了它，它拦截前往我们 API 的流量。它只放行带着 VM 自己分配的会话 token 的请求；攻击者嵌入的密钥会被代理拒绝。它还屏蔽那些会启用到服务端 fetch 的请求头。代理被放在 VM 里而非我们的服务器上，因为只有 VM 知道来源——从服务器的视角，一个 Cowork 请求与任何其他 API 客户端无法区分。

上：前往 api.anthropic.com 的流量被放行，导致出网。下：用拦截前往我们 API 流量的中间人代理来修复。

这也是「你自己亲手搭的软件往往最弱」这条原则的第二个实例。跨我们各产品的 hypervisor、seccomp 和 gVisor 一直可靠。我们自定义的允许清单代理才是出问题的那块。

#### **我们漏掉的风险：VM 隔离也把端点检测软件挡在外面了**

在评估 Claude Cowork 时，企业安全团队会问：「为什么我们的 EDR 看不到里面？」答案是：那个把 Claude 关住的同一道隔离，也把基于主机的端点检测与响应（EDR）挡在了外面。从 EDR 的视角，Claude Cowork 是一个不透明的 hypervisor 进程。它无法检查来宾机。

隔离会降低可见度，而对于合规态势依赖端点可见性的团队，不透明是个麻烦。我们当前的缓解手段，是用拉取式 [OTLP](https://opentelemetry.io/docs/specs/otel/protocol/) 导出，让管理员事后取回事件日志，但这与实时监控不是一回事。如果你在构建类似的东西，为这场对话早点做预算。

| **环境** | 短暂容器（[claude.ai](http://claude.ai)） | HITL 沙箱（Claude Code） | 密封 VM（Claude Cowork） |
| --- | --- | --- | --- |
| **代价：隔离开销** | 容器启动 | 低延迟原生沙箱 | 完整 VM 启动 |
| **代价：用户依赖** | N/A | 必须解读 bash | N/A |
| **风险：爆炸半径** | 服务端容器（由 gVisor + 主机基础设施边界守护） | 本地工作区 | 挂载的工作区（由 vsock + hypervisor 边界守护） |

## **信任 agent 读到的东西**

企业常常问我们如何保护 MCP 连接。这是个好问题，但正确的那个比 MCP 本身更宽泛。提供给 agent 的任何外部资源，都同时代表两种风险：传统供应链意义上的代码执行风险，以及一个 prompt 注入向量。传统的依赖审计（锁定版本、验证签名、审查源码）应对前者，却漏掉了后者。

**远程 vs 本地，比看上去更重要。** 一个本地安装的工具是可审计的。你能读它的代码、锁定它的版本，并知道它不会在你眼皮下改变。一个远程工具——一个托管的 MCP 服务器、一个云连接器——在你批准它之后的任何时刻都可能改变行为；你安装时的信任决定可能已不再适用。我们的[连接器目录](https://claude.com/connectors)通过持续审查来应对这一点，但目录之外任何东西都应被当作不可信。先拿假数据在它上面运行，在一个恶意工具爆炸半径能被约束的环境里运行。

**即使工具可信，工具输出也是一个攻击面。** 前面提到的 GitHub README 例子正是这种情形；任何施加在网页上的输入扫描，都应以同样的严谨度施加在启用网络的工具结果上。尽管这会增加延迟、并非完美防线，我们还是倾向于实时检查：一旦一次被投毒的工具返回把 agent 引向了外泄数据，日志里只会显示一次成功、获授权的 API 调用。没有事后可寻的信号。

在 Claude Code 和 Claude Cowork 中，工具调用经由代理路由，这些代理执行网络与文件策略，并能在返回值进入模型上下文之前检查它。做检查的分类器可以是一个小巧快速的模型；它不必是那个在做推理的模型。

## **展望未来**

模型和产品正快速推进。随着它们前进，风险变形演化，我们的缓解手段必须跟上步伐去应对。

**持久记忆投毒。** 跨会话持续存在的 agent 上下文份额不断增长——这包括产品记忆、CLAUDE.md 文件、挂载的工作区，以及排定的和长时间运行 agent 的状态目录。任何落入这些之中一处的注入，都会在 agent 每次启动时被重新加载。随着更多 agent 状态熬过会话，我们面临着经典后渗透意义上的新持久化机制。会话启动时的好分类器将不得不变得更普遍。

**多 agent 信任升级。** 一方面，子 agent 可以隔离不可信内容，向主 agent 返回结构化的事实而非原始文本。另一方面，这可以被滥用：如果一个子 agent 的输出被当作比原始工具结果更高的信任级——因为它来自「我们自己」——就引入了一种 prompt 注入的新向量。在多 agent 系统里，在分配不同信任级与变得易于信任升级之间，存在权衡。

**agent 身份。** Claude Cowork 对 agent 身份的回答是具体的：凭证留在主机钥匙串，VM 得到一个每会话、作用域收窄的 token，且该 token 可以独立于用户的 token 被吊销。不过，我们开始面对一个跨平台 agent 身份的更广泛问题。agent 应当拥有自己的主体身份，还是应当作为用户的延伸、继承用户的权限？最终，答案可能是两者的融合。

随着 agent 能力增强，攻击面在不断转移。我们见到的那些失败类型，很可能在各行各业和各实验室被重演。我们需要对 agent 专属的安全态势进行集体投入——从共享的基准和披露规范，到通用的身份标准和跨厂商红队。本文聚焦于约束，但那只是 agent 安全图景的一部分。至于治理、可观测性和整个技术栈的其余部分，参见 [NIST 关于 AI agent 身份与授权的项目](https://www.nccoe.nist.gov/projects/software-and-ai-agent-identity-and-authorization)、由澳大利亚 ACSC 联合 CISA 和英国 NCSC 牵头的 [六机构关于采用 agentic AI 的指南](https://media.defense.gov/2026/Apr/30/2003922823/-1/-1/0/CAREFUL%20ADOPTION%20OF%20AGENTIC%20AI%20SERVICES_FINAL.PDF)，以及 [ISO/IEC 42001](https://www.iso.org/standard/42001)——AI 管理标准。我们的 Glasswing 计划是一份贡献，但我们期待与伙伴和竞争对手就这一关键议题合作。

## **总结**

简而言之，有几条原则我们不断回到：

**先在环境层设计约束，再在模型层引导行为。** 教会我们最多的两起事故——员工钓鱼和第三方允许清单披露——都是出网（egress）案例，数据从一个被允许的路径流出。在每一起中，模型层都帮不上忙；对它来说没有异常可抓。当所有概率性的防线都落空时，那道确定性边界才是真正挨上那一击的。

**让隔离强度匹配用户的监督能力。** 一个能读 bash 的开发者和一个不能的知识工作者，跑的不是同一个威胁模型。用户能否评估 agent 即将做什么——这个问题应当帮助决定约束策略，而在任一方向上答错（对专家摩擦太多、对非专家信任太多）本身就是一种失败。

**警惕自定义组件。** 久经考验的 hypervisor、系统调用过滤器和容器运行时，比你能构建的任何东西都熬过了更多对抗性关注。在这里描述的每一次部署中，标准原语都挺住了，而我们在它们周围做的工作却暴露了缺陷。

归根结底，虽然 agent 可能是一类新软件，它们的系统级交互并不是。它们仍然读文件、开 socket、起进程；这使得用成熟的工具做约束，成为一种关键且可行的防御。随着 AI 发展，部署的风险-收益平衡会不断转移，但给爆炸半径设一道硬性上限，常常能把那个平衡推向正确的方向。
