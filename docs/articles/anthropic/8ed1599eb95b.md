# 改进我们的对齐与安全努力

2026 年 8 月 31 日

7 月 30 日，我们[报告](https://www.anthropic.com/news/investigating-incidents-cybersecurity-evals)了三起 Claude 模型未经授权访问真实计算机系统的事故。这些模型——为评估目的刻意在无网络防护的状态下运行——因一个第三方评估环境内部的配置错误而访问了互联网。另外，8 月 4 日，英国 AI 安全研究所[报告](https://www.aisi.gov.uk/blog/incident-report-unsanctioned-agent-behaviour-during-cyber-testing)了其自身网络安全测试中的一起事故，其中 Claude Mythos 5 在活的互联网上采取了一系列未经授权的动作。在那起事件里，模型（同样为评估目的刻意在无网络防护下运行）被蓄意给予了互联网访问。

我们正在对两起事故进行深入分析。我们也计划与 METR 合作做一项独立审查。我们希望确保两项研究都足够彻底，并将在未来几周分享更多。

在此期间，我们分享过去一个月里做的一些改动。我们认为这些事故反映了运营安全的失效，以及两个对齐问题：动机性推理，以及为追求一项狭窄任务而愿意采取有害行动（这两点我们都在先前的系统卡里描述过）。在安全方面，我们描述我们对约束和监控系统所做的改进，以及我们为第三方评估者制定的实践。在对齐方面，我们更深入地讨论这两个问题；我们也认为持久的进步不仅来自理解某起事故里发生了什么，也来自理解失准最初如何产生，我们分享[该方向的早期研究](https://alignment.anthropic.com/2026/reward-seeker/)。

鉴于这些事故，关于给前沿限速的讨论日益增多。区分两种限速是有帮助的。在一个公司*内部*，限速意味着当安全与速度相冲突时，一系列把安全置于速度之上的决策。在整个领域*之间*，它意味着建立流程以防备逐底竞争（race-to-the-bottom）的动态。在本文里，我们讨论为服务于第一种做法、在这些事故之前和之后我们都采取的行动。第二种限速需要政府与产业之间的协调，并且应当是可辨读、可验证的。我们一些高管和许多员工最近签署了一封呼吁在限速上加强协调的信，我们将在未来几周更多地谈我们打算如何为那项努力做出贡献。明确我们的立场：我们相信，如果业界尽快采纳一个合法、可验证、有效的协调限速机制，世界会因此受益。

## 保障评估与训练环境

虽然我们不相信这些事故仅仅代表运营问题，但我们的第一优先是应对具体的约束和监控问题。作为回应，我们采取了以下行动：

### **暂停并加固评估环境**

事故之后，我们暂停了对外部预发布模型的网络评估，并短暂地也暂停了内部的，同时我们落实下面这些措施。我们 7 月 30 日报告的那些事故表明，我们一直在很大程度上依赖单一层防线（环境本身的配置），而我们需要多层，包括在 prompt 里设定明确边界、建立流程去验证沙箱在预期处是密封的、以及实施能实时介入的监控。OpenAI 的[披露](https://openai.com/index/hugging-face-model-evaluation-security-incident/)（它促成了我们七月的调查）——称模型在一次评估中利用一个未知的漏洞逃出了一个密封沙箱——也清楚地表明我们应当聚焦于加固沙箱本身。

在评估暂停期间，我们落实了以下初步措施：

1) 我们构建并部署了一个分类器，用于实时自动识别模型何时试图激进地探查或逃逸一个测试环境、或意外获得了互联网访问。当分类器标记这样一次尝试时，它会在工具调用运行之前拦截该动作、终止任务，并警示一个人。[1](https://www.anthropic.com/news/improving-alignment-security-efforts#footnote-1)

2) 我们对我们近期内部预发布模型评估（网络及其他）的文字记录跑了自动化监控，寻找沙箱逃逸（模型利用我们沙箱中的一个缺陷去够到本应与它隔绝的系统的情形）或沙箱配置错误。在我们于沙箱工具内运行评估的情形里，我们未发现任何它打破沙箱边界去够到本不该够的外部资源的例子。我们确实发现了模型加以利用的若干沙箱配置错误，但这些都没有导致沙箱之外的系统被攻破。[2](https://www.anthropic.com/news/improving-alignment-security-efforts#footnote-2) 我们正在积极处理这些。

3) 我们把高风险[3](https://www.anthropic.com/news/improving-alignment-security-efforts#footnote-3) 的内部网络沙箱迁移到更稳健的隔离。我们也在进一步红队我们的虚拟化栈——也就是说，指派预发布模型尝试逃逸它——以发现并打补丁弱点。

有了这些措施就位，我们内部的网络评估现已重新运行。

### **强化学习环境**

我们也对预发布模型暂停了较高风险的 RL 环境数周。那段时间里，我们构建了一个类似的分类器、加以改造以避免激励模型去规避这个新监控，我们如今已把它部署进那些环境。多数 RL 已恢复，但一些高风险环境仍保持暂停，直到能被人工审阅；另一些则需要一个我们计划很快部署的分类器更新版本。

### **更广的加固**

除了聚焦于高风险评估和训练的努力，我们扩展了离线监控，覆盖大多数其他形式的内部前沿 agentic 使用。我们也在对内部推理建立控制，防止 Anthropic 员工意外地以弱于上述那些的缓解措施运行 agent。

## 给外部伙伴的最佳实践

因为被报告的那些事故发生在第三方环境里，我们已要求每一家以**降低网络防护测试预发布模型**的组织承诺遵循一套最佳实践。我们认为这些是必要的，因为：

- 我们一般发布的模型随附防护——包括实时运行在 Claude 输入和输出之上、以拦截被禁止网络活动（如恶意软件开发或攻击性漏洞编写）的分类器。相较之下，网络评估者和一部分早期访问伙伴，使用的是那些防护被削弱以便准确进行模型能力测试和防御性网络工作的模型。
- 网络评估异常容易产出这些事故中见到的行为。它们对探查周边环境、绕开障碍时的坚持和创造力产生选择压力，且被运行数千次。

这些实践在伙伴用自己 harness、沙箱或 agent 运行网络相关评估的地方完全适用。**它们不适用于使用像 Claude Fable 5 这样带防护模型的客户。** 我们已带着这些实践恢复外部网络评估，我们内部也遵守它们。

### **沙箱与网络隔离**

默认情况下，所有网络评估都应在一个加固的沙箱（一个隔离的计算环境）里运行，*不带互联网访问*。该环境唯一应允许的外部连接是模型自己的 API，而 API 密钥应保持在环境之外。这一配置应在每次评估开始前得到验证。某些评估可能需要互联网访问。在这些情形里，我们评估预发布模型时会与外部评估者合作，判断我们能否可靠地检测并中止模型在其声明范围之外采取行动的运行。

### **事前验证**

在进行一次评估运行之前，评估伙伴应当：

- 让被测试的模型探查沙箱的漏洞，先通过对配置的静态分析，再通过实际指派模型尝试逃逸。应指示模型若成功逃逸就停下并报告，且这一切应在紧密的人工监督下进行。此测试应在无互联网访问的情况下进行，最好在第二个沙箱里。因为评估有时会跨数百甚至数千次运行来进行，伙伴理想上应在开始任何评估之前长时间地进行这项测试。
- 确认任何评估挑战在原则上确实可解。当评估目标处于离线、或任务无法完成时，agent 常会寻找其他办法完成一个挑战，增加它们采取超出评估预期范围动作的可能。[4](https://www.anthropic.com/news/improving-alignment-security-efforts#footnote-4)

### **显式范围设定**

每一条 prompt 都应声明什么在演练的范围之内、之外，包括目标、允许的动作和网络边界（即模型该访问什么、不该访问什么）。边界应被表述为指令（例如「你不该访问互联网」），而非关于环境或测试的断言（「你没有互联网访问」）。

### **实时监控**

评估者也应使用一个提供了演练范围的、基于模型或基于规则的监控器，对模型的思考、动作和网络活动做持续监控。若一次运行违反这个范围，监控器应向一个人标记并终止演练。

我们计划在与外部伙伴协商下持续打磨这份指南，并将其延伸到评估之外。特别地，我们正在为能访问 Claude Mythos 5（它同样在无网络防护下运行）的伙伴制定配套实践，很快会分享更多。

## 对齐评估

约束和监控对于捕捉模型采取危险动作的实例至关重要，但它们不解决模型*为何*起初采取这样的动作。下面，我们讨论我们的初步对齐调查、我们聚焦的问题，以及我们为预防训练期间作弊所做的持续工作——包括关于作弊如何塑造模型行为的新研究。

### **评估期间我们模型的环境与知识状态**

我们的对齐评估仍在进行，但我们的初步调查指向两个主要的对齐失败，两者我们都在[先前的](https://www-cdn.anthropic.com/57a52ea7d8f0e54e8a542e908266086df425cdf5/Claude%20Fable%205%20&%20Claude%20Mythos%205%20System%20Card.pdf)系统卡里描述过。一个是动机性推理：模型起初被告知它们的环境是模拟的，但当它们后来遇到证据显示它们连接着真实的互联网时，它们可能以一种让自己能维持那信念的方式解读那些证据。第二个是鲁莽：模型愿意在真实互联网上采取有害行动，以追求解决一次网络安全评估这一狭窄目标。然而，我们也认为评估设置本身促成了模型在这些事故中表现的行为。Claude 被明确告知它没有互联网访问，尽管互联网是可用的，这可能让它质疑它所见的系统是否真实。而在一个案例里，那个虚构的目标与一个真实网站同名，使得区分演练之内预期的范围更困难。

我们的结论取决于若干我们尚未完全回答的问题，包括模型在多大程度上判定自己有权访问真实互联网（即便它们起初不知道这一点）、它们是否明知故犯地忽视其环境某些元素为真的迹象，以及几起案例中它们未能终止演练这一事实，是否源自动机性推理。我们正运用一系列技术来回答这些问题，包括重采样模型的同时对环境做有针对性的更改，并使用可解释性方法直接检查其内部状态。

### **研究预防训练期间作弊的努力**

尽管模型失准很复杂、可能出于五花八门的原因，我们凭经验发现训练环境中的缺陷——特别是容易受作弊侵害、或不作弊就无法解决的环境——是失准行为中大得不成比例的贡献因素。

下面，我们追溯到这些事故前几个月，讲述我们为避免有这类缺陷的训练环境所做的努力。那些努力并不完美，而我们的假设是这些事故至少部分与我们无法完全消除此类问题有关。我们通过在容易被奖励黑客（reward hacking）侵害的环境上刻意训练一个模型来检验这一假设。在模拟中，这个模型复现了更严重的失准行为，有些与今夏其他公司事故中报告的那些相似。我们的生产模型放进同样的模拟里则不会（更多细节在本节后面）。

我们历史上一直担忧那些激励作弊的 RL 训练环境，并采取了各种措施来过滤或修复这类环境。

二月，在 Mythos Preview 强化学习运行看到奖励黑客迹象后（当模型找到办法愚弄它的训练过程、在不完成被指派任务的情况下赚取奖励），我们回滚了三天训练。我们注意到模型在代码注释和回复里给「审阅者」写备注，包括在从未提过审阅者的任务上——一种从 prompt 确实包含审阅者的环境中做出的不良泛化。它还不断通过堆砌免责声明或告诫，来博弈一个本意激励诚实的奖励。[5](https://www.anthropic.com/news/improving-alignment-security-efforts#footnote-5) 回滚那三天让我们能从一个学到该行为之前的 checkpoint 恢复训练，并对环境做了改动以防止模型再次学到它们。

自 Claude Sonnet 3.7（它有一种我们直到训练后期才检测到的奖励黑客倾向）以来，我们一直在构建监控模型在 RL 中学到的不良行为的工具。我们下了很大功夫确保我们的工具随每一代模型演进，从少数几个分类器到对每次训练运行之前和之中所有环境的自动化审阅，但到 2026 年春那套系统已不堪重负。我们以比以往任何时候都快的速度产出 RL 环境，快过我们系统能审查它们的速率。被标记的环境需要一个人来裁定，而奖励黑客和配置错误开始超出我们过滤或修复它们的能力。

此外，我们[发现](https://www-cdn.anthropic.com/08ab9158070959f88f296514c21b7facce6f52bc.pdf)一部分运行意外地是在一个模型的思维链（chain-of-thought）上训练的——这是我们努力避免的，出于担心它教模型隐藏它真正的推理。我们把泄漏追溯到我们生产环境栈里的若干配置错误。在这样做时，我们清楚地意识到，还存在其他由随时间积累的凌乱代码所产生的问题。

为应对这些担忧，四月我们冻结了所有对我们生产 RL 环境的改动约一个月，给了我们彻底翻新栈的机会。奖励和环境现在必须遵从一份商定的规格。例如，我们引入技术手段来降低意外地在思维链上训练的风险。[6](https://www.anthropic.com/news/improving-alignment-security-efforts#footnote-6) 在我们的环境质量和监控团队重建栈的同时，我们请环境所有者利用这段暂停来测试和修复他们构建的环境。我们还完全重建了我们的审阅流程，并要求每一个修复过的环境在能进入又一次训练运行前被重新认证。

在冻结期间，我们标记了生产组合中超过 10% 的环境有问题，范围从奖励黑客到损坏的任务和配置错误，并且只在修复后才重新启用它们。

然而，我们的努力并不完美。在某些情形里，我们发现人类审阅者把我们的自动化监控器标记的环境当作误报予以驳回，让有缺陷的环境在训练里待的时间比应有之久。而一些有缺陷的环境就是会溜过我们的检测机制。我们目前正在收紧驳回一个标记的标准，并期待与环境所有者加强协作以提升我们系统的精确度。除了监控和检测，我们的对齐训练和 RL 团队正在协作以帮助改进环境。

我们怀疑，我们对 RL 环境质量控制的大量投入，可能阻止了更严重的对齐事故；而反过来，这些努力中的不完美，可能促成了我们迄今识别出的那些事故。

要看一个不带这些保护训练的模型会做什么，我们刻意在 80 个不同的真实 RL 环境上训练了一个 Opus 级模型——它们要么在至少一次真实训练运行中被奖励黑客侵害并被监控识别，要么在环境质量审阅中被发现有可黑客性。所得的模型显示出一种强烈的动机去在任务上取得高分，以及一种为追求任务成功而执行潜在有害动作的意愿。我们配套的[对齐科学博客文章](https://alignment.anthropic.com/2026/reward-seeker/)更详细地讨论了这项实验，但这里我们简要概括。

我们在一系列评估中测试了这个刻意失准的模型，包括取用涉及 Claude 的英国 AISI 网络事故、以及 OpenAI/Hugging Face 事故（我们感谢 OpenAI 公开分享关于此事的细节）某些方面的模拟场景。在这些所有工具调用都由另一个 LLM 模拟的评估中，我们训练来奖励黑客的那个模型表现出一种从模拟沙箱中破出、攻击模拟内部和模拟第三方基础设施的倾向。它也愿意篡改自己的奖励函数、为满足一个评分者而提供制造生物武器的建议、并反复设法绕过部署安全监控以便在一项任务上作弊。

随后，我们对奖励黑客训练之前的那个模型、以及我们几个公开可用的模型，跑了同样的网络模拟。没有一个表现出同等程度的失准行为。我们的结论是：训练中存在大量奖励黑客，会导致模型愿意为追求任务成功而执行长串潜在有害的真实世界动作。

我们认为，今年春天我们大量投入监控和减少奖励黑客，是我们的生产模型不太可能从事更危险奖励追求的一个主因。在我们配套的[对齐科学博客文章](https://alignment.anthropic.com/2026/reward-seeker/)里，我们也发现了证据：对齐训练环境能大幅减少奖励黑客和奖励追求行为。但正如我们 7 月 30 日报告的那些事故所证明的，我们的流程并不完美，我们的模型也并非完美对齐。

需要明确的是，我们不认为训练环境中的作弊是对齐问题的唯一原因，甚至不是我们事故或其他前沿 AI 公司事故中那些特定对齐问题的唯一原因。解决对齐将涉及应对非常宽泛的一系列潜在问题，而未来的对齐事故可能涉及与我们迄今所见不同的行为和不同的原因。

## 加固安全实践

Anthropic 的内部安全态势并非 7 月 30 日事故的促成因素。这些发生在第三方环境里，那里互联网访问被错误地敞开着；模型无须从任何东西里「黑出去」，即便它们有意这么做。

然而，这些事故仍凸显了强力安全措施的关键重要性。除了 IP 或模型权重被盗的通常风险，我们现在还必须应对我们自己的模型从 Anthropic 系统*黑出*、以及我们或他人的模型被盗用而向 Anthropic 系统*黑入*发动外部攻击的风险。随着模型能力增长，尤其自 Mythos 级模型以来，这些风险变得愈发尖锐。下面描述我们实施的部分工作——其中多数努力发生在七月事故之前，尽管这些事故强调了这项工作的重要性。

四月初，在看到了 agentic AI 应用的走向之后，我们的安全团队主动发起了一项全公司范围的努力，朝着加固我们防线这一个目标，必要时取代其他工作（包括研究）。我们判定，我们的暴露面增长得比我们的防线更快——Mythos 是一个强大到足以成为资源充足攻击者目标等级的模型，我们对自主 agent 的内部使用已增长到传统访问和监控方法并非为此设计的规模，而新基础设施的节奏意味着我们的安全必须随环境一起扩展、而非以固定容量运作。

这项努力的结果包括：

- *减少那些对含有模型权重或客户数据的系统拥有常驻访问的人工和自动账户*
- *把我们的计算集群设为默认阻止所有出站流量*
- *要求内部服务在通信前相互验证身份*
- *退役遗留基础设施配置和共享内部服务*
- *收紧我们工作负载运行所在的隔离环境*
- *扩展主机级可观测性，使我们基础设施上的意外行为在发生时变得可见*

我们还临时把公司的一部分人重新指派到这些努力。约 150 名产品工程师被转向安全、可靠性和隐私；研究人员也从预训练或 RL 轮换出来、聚焦于防护和安全；而我们的产品团队暂停了大多数新功能和界面的开发。我们为每个团队设定了严格的退出标准，达标后才回归先前的工作。到初夏，多数团队已达成这些标准。

在把资源重新配置到安全的同时，我们继续为内部 agent 使用构建约束和监控。我们的训练和评估工作负载通常运行在与生产系统隔绝的沙箱里。自开发 Claude Mythos Preview 以来，我们已用我们的模型去探查那些沙箱里的任何弱点。我们在[四月对齐风险更新](https://www-cdn.anthropic.com/3edfc1a7f947aa81841cf88305cb513f184c36ae/Alignment%20Risk%20Update_%20Claude%20Mythos%20Preview%20(Redacted,%20April%2010).pdf)里描述了对内部编码 agent 的离线监控，而我们[八月风险报告](https://www-cdn.anthropic.com/f61d49fa5596956a5dec75fea0e973bf6a6a8378/Redacted%20Risk%20Report%20August%202026%20.pdf)更详细地涵盖了那套系统、以及与之并行运行的干预措施。这些包括在最自主形式的内部 agent 使用上的沙箱或 auto 模式分类器，以及在基础设施代码改动合并前的自动化审阅。

这项工作所漏掉的，是评估——尤其是第三方评估。我们确实监控了一些高风险评估（包括实时），但总体上我们只在事后对文字记录的一个样本做自动审阅。

七月的事故强调，改进我们网络安全防线的紧迫性比我们先前所认为的还要高。我们正在这方面加倍努力，并会在下一次风险报告里详述。

#### 脚注

- 我们已核实，分类器本会标记我们 7 月 30 日报告里所描述的那些事故。
- 这些发现没有一项来自我们内部的专门攻击性网络评估套件，那些套件在完全没有网络访问的情况下运行。
- 高风险网络评估包括那些 Claude 被给予一个范围含糊的攻击性任务的评估，如渗透测试。
- 归根结底，一个在这样一个挑战上在其预期范围之外行事的模型，是一个对齐问题；一个对齐的模型应当停下，或向人类报告任务无法按指定完成。我们正持续直接训练这种行为，但纵深防御的方式意味着不只依赖对齐。
- 我们在 [Mythos Preview 系统卡](https://www-cdn.anthropic.com/8b8380204f74670be75e81c820ca8dda846ab289.pdf)里公开讨论过另外两类奖励黑客，包括一个模型利用底层计算机进程数据来提升自己的权限，以及另一个它绕过训练环境中的网络限制、下载能让它抄近路完成被指派任务的数据。
- 这些缓解措施并不完全充分；我们在[八月风险报告](https://www-cdn.anthropic.com/f61d49fa5596956a5dec75fea0e973bf6a6a8378/Redacted%20Risk%20Report%20August%202026%20.pdf)第 5.2.3 节更详细地讨论了在思维链上训练的进一步实例。
