## 01 架构

一个标准 agent 循环里的单一模型，为长尾配备 skill、为调用你已有系统配备工具。这你只决定一次。

### **什么是商务 agent？**

我们把商务 agent 定义为一个简化跨在线目录买卖的 agent。

有些 agent 面向消费者：它们搜索、比较、替代、并组装订单。那可以是一个零售购物车、一份旅行行程、一次手机套餐变更、或为一场演出保留的座位。有些 agent 面向企业：它们回答关于销售的问题、运行促销和活动、并管理库存和定价。

核心架构是一个模型处在[标准 agent 循环](https://www.anthropic.com/engineering/building-effective-agents)里：就一个目标推理、探索上下文、通过工具采取行动、通过 skill 学习流程、提出澄清问题、并观察结果直到目标达成。

它前面没有一个把对话做切分的意图路由器，它后面也没有一组领域专有的 agent。

### **工程上下文**

#### **用 skill，而非子 agent**

一个商务 agent 得覆盖跨许多类别和意图的宽泛能力范围，这很诱人地让你为每个领域建一个子 agent。

实践中这被证明是次优的，因为一次商务对话是一个跨多个意图和多轮、紧密耦合的会话，需要大量共享上下文。

在子 agent 架构里，编排者持有购物车或暂存的改动、用户偏好和对话历史。

每一次交给子 agent 的交接，都是一次丢失状态的操作，这常常影响子 agent 响应的质量、进而影响整体响应。除此之外，每次交接可能花数倍的 token、并增加数秒延迟。

这些领域也很少能干净地分离。一个退货流程可能需要订单历史、当前购物车和产品目录，这意味着「每领域一个子 agent」的做法要么到处复制那份访问、要么在任务中途交接。

随着模型变聪明，它们也能处理更长的上下文、更多 skill 和更多工具，于是今天这些排布规则背后的限制，每一代模型都在松动。

相反，[agent skill](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) 给你类似的每领域模块性和上下文控制，却没有交接税，因为 skill 指令加载进那个已经持有全部历史的主 agent。

在我们跨多个企业部署的比较中，一个带 skill 的单一 agent，在质量上持续胜过「一切用一个 prompt」的设计和子 agent 设计，且常常每任务成本和延迟更低。

子 agent 真正能派上用场的时候，是编排者能把它们当作一个工具来调用、用于一个窄的或自包含、值得有自己专属上下文窗口的任务。

一个常见的生产例子是深度研究子 agent——子 agent 搜索并阅读文档、编写并运行代码、遍历数据模型、撞进死胡同。所有工作都在一个或多个子 agent 内部发生，只有一个紧凑的答案回到编排者。

另一个例外，是一个已经有自己专用 agent 的领域。如果你的药房或金融服务体验运行着一个带自己合规界面的专门 agent，正确的做法可能是一次移交——由那个 agent 接管任务、在它自己的循环里直接和用户协作直到任务完成。

区别在于对对话的所有权。一次移交让领域 agent 成为用户的对接方，而委派让编排者保持对接、在一轮之内把领域 agent 进进出出、并在每次交换上劣化。

#### **系统 prompt 还是 skill：按频率决定**

决定把一组指令放进系统 prompt 还是 skill 时，主要因素是 agent 多频繁地需要它。加载一个 skill 花一个模型轮次，所以 agent 多数轮次都需要的东西通常放进系统 prompt。

不过，这确实取决于你的流量如何分布、以及你的评测显示出什么 agent 行为。一个好的起点是：任何与你三分之一及以上流量相关的东西——无论是发布前预期的还是生产里观察到的——放进系统 prompt，其余放进 skill。

如果一个 skill 能从你已有一个的信号（例如用户来自哪个页面）被预测到，我们建议你在第一次模型调用之前从 harness 注入它，从而省掉加载 skill 的额外一轮。

关键的指令，例如安全和法律规则、品牌约束，以及像过敏这样的关键用户事实，永远放进系统 prompt。

对商务 agent，这意味着产品搜索住在 prompt 里，因为几乎每个会话都会碰到它，而 skill 承担功能长尾。

在我们的[参考实现](https://github.com/anthropics/commerce-agents)里，购物 agent 的 prompt 持有事实根据、购物车和结账语义、以及呈现规则，而以下 skill 覆盖其余：search-discovery、purchase-research、planning-goals、customer-care 和 memory-personalization。

商家 agent 以同样的方式切分，把 performance-insights、catalog-listings、inventory-operations、pricing-promotions 和 marketing-campaigns 作为它的 skill，每个运营领域一个。

**在 prompt 里** —— 购物 agent：事实根据、购物车和结账语义、呈现规则、以及产品搜索。

**购物 skill**（长尾）：search-discovery · purchase-research · planning-goals · customer-care · memory-personalization

**商家 skill**（每运营领域一个）：performance-insights · catalog-listings · inventory-operations · pricing-promotions · marketing-campaigns

### **工程 agent 工具**

我们关于[为 agent 编写高效工具](https://www.anthropic.com/engineering/writing-tools-for-agents)的文章涵盖了通用的工具设计。有两点在商务上最为要紧：

**在你核心系统和逻辑之上构建 agent 工具。**

一家商务公司本已有搜索和排序、一个购物车、一个偏好与档案存储、一个库存系统、促销和活动引擎、销售分析等等，每一个都编码了打磨多年、并看着模型永远看不到的信号的逻辑。

agent 的工具应当去调用那些系统、而不是重新实现它们，而工具边界就是它们的逻辑终结、模型判断接管的地方。

例如，当 agent 调用 `search_products` 时，结果应当已经排好序抵达；它的活是决定哪些结果服务于用户目标、展示多少、以及如何呈现它们。

**工具结果就是上下文。**

返回模型据以推理的那些字段、丢弃其余。每一行搜索结果都带图像 URL，是惯常的元凶。

视需要在工具内部重塑原始响应，包括当从数据里看不明显时追加一个下一步。

这对错误场景尤其相关，在那里模型从指令中而非错误码中受益。例如，加一条错误指令「查询可用性时请包含一个产品 ID」，而不是一个笼统的 403。

#### **UI 组件即工具**

多数商务 agent 响应是 UI 组件而非散文，无论是一个产品轮播、一份行程、一张座位图、还是一张图表。这意味着 agent 必须发出一个 schema 而非文本。

团队有时从 prompt 模型发出自定义标签、并在客户端解析它们起步。随着界面增多，这一做法会失效，因为：

- 模型在你标记语言上的训练不如在工具调用上那么充分，所以随着嵌套组件增多，可靠性下降。仅靠 prompt 不保证格式良好的数据。
- 标签定义住在系统 prompt 里，所以每个新组件都让上下文膨胀、每次编辑都冒着在 prompt 别处引发回归的风险。
- 过往对话最终以一种只有你的解析器能读的格式被存储，所以加载历史要么意味着在客户端解析原始消息，要么意味着在模型 API 原生格式之外保存一份副本。

经受住考验的模式，是把每个 UI 组件做成一个工具。模型带类型参数调用 `present_products`、`present_itinerary` 或 `present_plan_comparison`；你的服务器校验并丰富这次调用、并发出一个事件；你的客户端渲染它。

因为组件是工具调用，它们已经以原生格式在 messages 数组里，所以你重新加载一个旧对话时不必再解析。一个示例呈现工具契约见下以及[参考仓库](https://github.com/anthropics/commerce-agents)。

权衡在流式粒度。工具调用的每个顶层参数都会在服务器上缓冲以供校验，所以一个呈现工具的子组件即便开着流式也会分步抵达。这影响感知延迟。

要得到一个 token 级的流，在工具体定义上设 `eager_input_streaming: true`，它会跳过缓冲、连同服务器端的 schema 保证一起跳过。

在我们的评测里，schema 违规在 Claude Sonnet 级及以上模型上非常罕见，但为漏网的情形把调用包进一次重试。

呈现工具也给 agent 一份屏幕上有什么的记录。当顾客说「第一家酒店」或「左边往下数第三个」时，布局就在 messages 数组里、在上一次呈现调用的参数里。

要让它奏效，参数必须反映渲染出的布局，所以按 UI 的结构去组织它们——用有序的行列和轮播，而非客户端重排的平铺列表。

## 02 让它快又实惠

在两条战线上攻击延迟——端到端和感知——并让缓存承担成本。这一切都不该为了达标而牺牲智能。

延迟在商务里很重要，而消费者界面最不宽容。然而，在 agentic 界面上，我们一贯看到能推动留存、参与度和购物车大小这些指标的，是结果的质量。

答案是否相关、任务是否真正完成，相对于边际的延迟收益，对这些指标更关键。

所以在两条战线上攻击延迟。通过良好的工程最小化端到端延迟，并把这一点与削减感知延迟配对（因为看着 agent 工作的时间被读作进度）。

每个用户都有一个延迟预算，而下面的技术让 agent 待在预算之内、又不为达标牺牲智能。

### **最小化任务完成延迟**

任务完成延迟，是在各模型轮次上「最后 token 时间加工具处理时间」的总和。这给了你三个可努力的杠杆：更少轮次、更快工具、更快 token。这些杠杆有时会相互竞争，所以该最小化的是总和、而非其中任何一个。

**更少轮次**：提前加载可能的上下文、提升模型智能、并让模型并行调用独立的工具。

**更快工具**：优化工具自己的后端，并在参数一完成就急切地派发工具。

**更快 token**：通过在你的评测套件上扫参来选择模型及其配置。

#### **更少轮次**

查询复杂度会增加轮次，且通常不在你的掌控之内。模型智能和相关上下文帮助 agent 用更少轮次达到任务完成。我们在这一块的一些关键经验包括：

- **提前加载可能的上下文。** 如果用户是从一个产品页打开助手，或商家是从一个活动仪表盘打开它，把那个页面的数据放进会话上下文。对话很可能就是关于它的，而凭上下文作答不多花轮次。
- **提升模型智能。** 更聪明的模型能在任务完成中减少总轮次，因为 agent 能更高效地规划并发出工具调用。这常常盖过它们更慢的 token。如果你的查询偏向复杂，或生产显示出每任务超过约五个轮次，更快的模型往往就是更聪明的那个。哪个算更快取决于你的流量，所以通过扫参来选择，如下文「选择模型」所述。
- **让模型并行调用独立的工具**。商务用例常常需要许多操作并行：无论是搜多个产品、查询多份政策文档，还是从多个销售数据源拉记录。并行工具确保多个独立查询不烧掉额外轮次。prompt 模型在一轮之内调用多个工具、并在一个用户消息里以一个工具结果数组的形式返回结果（见[并行工具使用文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)）。

#### **更快工具**

- **优化工具自己的后端。** 有时一个工具确实要扇出——一个带「获取今日快照」查询的商家 agent，用三次独立调用读销售、库存和活动状态。但我们常看到工具边界成了缺失的后端逻辑被缝到一起的地方：一次可用性检查会去调目录拿 SKU、按门店调库存服务、调履约服务拿截止时间、然后在工具自己的代码里应用替代规则和自提资格再作答。这个工具如今就因领域知识而超载、随规则变化难保正确、并扛着本该坐在上游系统里的逻辑。当你发现自己在工具里写那种逻辑时，解法是一个能回答该问题的后端端点、并用一个 agent 工具去调它。
- **急切地派发工具。** 工具参数像其他 token 一样从模型里流出，所以 harness 能在每个工具的参数完成时就执行它、并在模型仍在流式输出其他并行工具或内容块时处理它。我们见过这把关到几百毫秒的多秒空档缩小、而 [Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview) 默认就这么做。你应当 prompt 模型先发出它最慢的调用，以获得最大延迟收益。

### **感知延迟**

感知延迟是用户感觉直到屏幕做某事的时长。它对消费者用例尤其关键，那里任何交易摩擦都会影响结账率和营收。两项技术在不碰模型的前提下缩短它：

- **边成形边流式发送组件。** 一个渲染出的商务响应通常是 500-700 个输出 token，若不流式，就是五秒或更久的转圈。在流式输出时把呈现工具的每个参数发给客户端、并渐进地渲染页面。
- **展示工作过程。** 在 agent 收集上下文时，为每一步用平实语言渲染一条简短进度行（例如「正在查找水边的酒店」。你可以从工具已有的参数（如一次产品搜索的查询）来构建它，或添加一个额外的 `user_facing_message` 参数工具，prompt 模型去写那行字。

上面两个面板用同样的 agent、同样的工具和 prompt 运行；只有 harness 不同。总时间大致相同，但用户看到某些东西的时间大不相同。

### **Prompt 缓存**

Prompt 缓存是你最大的成本削减候选项，而商务流量非常适合它。缓存的输入 token 读取只花新鲜读取的十分之一，而缓存写入带着约 1.25 倍的溢价，但一个缓存的前缀在第二次使用时就回本。在量大面向客户的应用里，你用最便宜、默认 5 分钟缓存过期就能达到非常高的缓存命中水平。

我们见过的最佳商务部署运行在 90-99% 的缓存命中率，而那正是从一开始就该为之设计的区间。我们的经验显示，缓存的 token 读取在约 10 万 token 时也大约快 1.5 到 2 倍，token 越多、扩展越接近线性。

缓存是基于前缀的。一次请求从缓存读到与先前某请求第一个不同的字节为止，所以要紧的不仅是上下文里有什么，还有它们的顺序。把一次请求想成三段，按它们变化的频率排布：

- **全局**：系统 prompt 的大部分和工具体定义，跨每个会话完全相同。这是你最热的缓存，而在规模上很可能永不过期。让它在各轮和跨会话保持逐字节一致、并在其末尾放一个缓存断点。
- **会话**：每用户上下文和对话历史，它们跨会话不同、但在单个会话内保持稳定。这一段在全局段之后。
- **易变**：任何在会话内变化的东西，例如当前时间或当前页面。把它放在请求的最末尾，要么作为最新一轮用户消息里一个带标签的块，要么在支持[会话中途系统消息](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)的模型上，作为一条 system 角色消息附加到 messages 数组。我们见到的最常见错误，是把一个时间戳或当前页面放在系统 prompt 的顶部，它悄无声息地在每次请求上破坏缓存。

这里有两个实现细节要记住。第一，skill 应当作为工具结果被加载，而非追加到系统 prompt 上。这样 skill 正文就落在对话前缀里、连同它一起被缓存。

第二，在每一轮里把断点向前滚动：一次请求允许有限数量的断点，所以把最新的断点移到每轮用户消息的末尾。这样每一轮都从缓存读取累积的历史，包括像搜索响应这样的长工具结果。

### **选择模型及其配置**

[模型大小和 effort 设置](https://claude.com/blog/claude-model-and-effort-level-in-claude-code)是同一种权衡——智能 versus 延迟和成本——而两者你都该凭衡量来选择：

- **定好你的指标和你的底线。** 选定你业务赖以运转的质量指标（任务完成、答案相关性、有据准确率）、你不会低于的评测分数、以及你的 p50 和 p99 延迟与成本预算。
- **扫参。** 在你考虑范围内的*每一*个模型和 effort 级别上跑你整个评测套件。我们建议商家 agent 从 Opus 起步（其任务分析密集），消费者 agent 从 Sonnet 起步（其延迟更重）。如果你有生产流量，按你真实的查询组合来加权结果。然后让数字来决定。有时 Opus 5 在驱动购物车任务上的提升，值得它对 Sonnet 的成本差；有时不值得。
- **仔细地读结果。** 有两件事常让团队意外。第一，一个 prompt 是针对某个模型调优的，所以用单一 prompt 跑的扫参，可能在它本非为其撰写的其他模型上表现欠佳。一个更小的模型通常需要当前模型自行推断的指令，而一个更大的模型会逐字遵循那些更小模型正在忽略的指令。在下结论排除任何候选之前，对每个候选的失败案例做几轮迭代是廉价的一步。第二，一个更智能的配置有时在延迟上胜出（最常见在 p90 和 p99），尽管 token 更慢，因为它更好地规划其工具调用、在最复杂请求上需要更少轮次。

衡量每完成任务的成本、而非每模型调用的成本，因为一个更便宜但需要更多轮次、或更常失败的模型并不更便宜。当结果接近、而成本契合你每任务的经济性和延迟时，选择智能。质量才是驱动采用和留存的东西，并为你在未来 6 个月随模型变得更好而留出构建的空间。

## 03 把它投入生产

记忆、安全、评测，以及跨组织扩展这项工作：是什么让一个 agent 通过生产、并把它留在那里。

最后，我们谈是什么让一个 agent 通过生产：记忆、安全、评测，以及跨组织扩展这项工作。

### **熬过会话的记忆**

你与客户的关系和互动很重要。记忆是让 agent 能从上次对话停下的地方接续、而不是从零开始的东西。一位在三月提到坚果过敏的购物者，不该在六月还得重复；一位每周一都查同样三个活动的商家，不该每次都得点名它们。长期记忆——那些应当跨会话存续的事实——是一个你去构建的系统，它有三个部分：事实如何存储、如何写入、如何读取。

#### **存储记忆**

记忆属于你的系统，不属于模型。

当档案小、而 agent 是唯一读者时，一份平铺的 markdown 档案管用。多数生产商务 agent 会长出它的容量，而实际的替代品是你已经在运营的那个数据库。一条事实是一个小的、带类型的记录：一个键（如 `shoe_size`、`default_store`、`preferred_report_cadence`）、一个短值、一个类别、以及它来自的会话。有些键你事先决定、每个用户都有；其余由抽取器发现。数据库随存储增长保持可查询，让你能就特定属性构建确定性行为，并能与你已有的用户数据连接。

对面向商家的 agent，按人而非按账户来组织关键记忆。商家登录常在多个操作员之间共享，所以每位操作员需要他们自己的档案，而读取必须尊重那位操作员的权限：一位店经理的 agent 不该记起一位区经理说过的某条事实。

在商务领域，agent 记忆持有个人数据。值得记住的事实往往是最受监管的那些，而各司法辖区之间的规则不同。把记忆当作一个数据处理的设计问题、而不仅是一个存储问题。实践中那意味着四件事：

- **决定你愿意持有哪些类型的记忆。** 在写入路径上强制执行这一点，用一个每次保存都要经过的校验器，而非仅在 prompt 里。
- **给用户一种查看、更正和删除已存内容的途径。** 把删除接入你的账户删除和数据请求流程。
- **设定一个保留期。** 几年前的一条偏好很可能已过时，所以一个保留期有助于让记忆事实保持新鲜。
- **记忆应当是每部署的一个开关。** 这让无法承担这些义务的辖区可以不带它运行。

#### **写入记忆**

异步地写记忆。在每一轮末尾，或在长会话里每隔几轮，一个在独立线程或进程里的 agent 读对话、并在存储里创建、更新或删除事实，同时随着会话推进保留自己的工作上下文。

它对对话的延迟一无所加，并在我们内部商务记忆评测套件上把事实召回率提高了 13%。

那个显而易见的替代——一个 agent 调用以保存事实的工具——对一个延迟敏感的商务 agent 是错误的。每次保存都是一次用户可见轮次内的工具调用，而除非整个存储都在上下文里，一次保存需要先读一次以便更新或去重，那本身又是一轮。

它还在每一轮里往 agent 面前多放一个决定，而在我们的评测里，这种注意力的争夺表现为漏掉的记忆。

分离出抽取器也让你能精确地 prompt 它。它只读用户和助手的文本、从不读工具结果，于是一份产品描述或评论不会变成一条关于用户的事实。它的 prompt 说清什么算一条事实——一个所说的尺寸、一项饮食约束、一种履约偏好、一位商家惯用的物化视图——以及什么不算，例如任何来自商品页的东西或一次性的细节。

#### **读取记忆**

分三层读记忆。

**始终在上下文里**：一小份固定的事实集在每一轮进入上下文：那些几乎每个请求都依赖的，例如购物者的默认门店和履约偏好，或一位操作员的门店和角色。

**每轮预取**：与当前请求相关的事实，按预加载 skill 所用的同一批信号每轮预取：一次鞋类搜索拉取尺码和品牌偏好，一个活动问题拉取操作员的惯用指标。

**藏在一个查找工具之后**：其余一切。

因为记忆是每用户上下文，它全都放在会话段里、在全局缓存断点之下。

### **安全：执法住在 harness 里**

prompt 是安全行为开始的地方，但在商务里它不能是安全被强制执行的地方。失败是财务性的、且常常不可逆，而一条 prompt 规则距被跳过，只差一次注入或一个坏样本。下面每一条规则都在代码里、在消费者和商家 agent 双方都强制执行，并被定义一次，以便每个运行时共享它。

#### **模型做暂存；人或策略执行**

没有一次模型工具调用能移动资金或改变业务。下单、支付、退款、价格更改和活动发起，全都以 harness 而非模型控制的一个动作收尾。

在消费者侧，这是结构性的：结账工具渲染购物车并带一个下单按钮，而 agent 调用的后端接口压根没有扣款方法。

在商家侧，每个写工具都产出一个带服务器生成 ID 的暂存改动，而 `apply_change` 只对通过一个真实界面被批准过的 ID 才成功：操作员门户里的一个按钮、CLI 里的一次确认、或当 agent 跑在 Managed Agents 上时平台自己的工具批准提示。

护栏在应用时对照当前限额被重新检查，而不是对照改动被暂存时生效的限额。无论界面是什么，形状是一样的：模型最危险的动作是提议，而批准经由你业务早已为那类改动使用的制单-复核（maker-checker）流程路由。

#### **写入和渲染只接受服务器签发的 ID**

harness 维护一份每会话的记录，装着服务器交给模型的每一个 ID，而那份记录是任何写入或渲染唯一接受的密钥。

购物车只接受服务器返回给本会话的产品 ID，而商家工具只接受 agent 实际读过的列表和活动 ID。以任何其他方式抵达的 ID——幻觉出的、用户粘贴的、埋在评论里的——在后端看到之前就被拒绝。

同一条规则覆盖 UI。呈现工具接受 ID，而服务器自己去填产品、订单或改动记录，于是一张卡片只渲染服务器自己填好的记录。

它也覆盖受托方：商家分析子 agent 读数据，但从不往 agent 可写入的 ID 集合里添加。

对于费用、披露和其他受监管内容，模型选择对哪个产品做披露，而服务器从获批准的文案里提供每一个字。同样的费用字段在商家 agent 的保护清单上，于是柜台两侧都不能更改或转述它们，而评测逐字节检查渲染出的字符串。

#### **有上限的交易必须顶得住反复请求**

多数商务界面对一个用户能买某商品多少设有上限——用于票务分配、促销定价或欺诈控制——而 agent 会重试、改述、并并行化，以一个人点按钮绝不会的方式。

因此上限在行级别上、按其会在写入后被执行的方式被执行，于是一句「再加两个」不能叠越其上，而一个会话的购物车写入被串行化，使单轮内的并行工具调用不能组合越限。

商家改动以同样的方式对照价格波动、折扣深度、补货大小和活动预算的上限被检查，外加一份任何改动都不得触碰的保护字段清单。这条规则可推广：在每个结果状态上、而非请求上执行每一道限制，并按会话串行化写入。

#### **第三方内容被净化**

在商务里，多数上下文是由不是你的人写的——卖家、评论者、竞争对手——所以每次后端读取都是不受信任的输入、都要经过一个净化器。

每个由第三方撰写的工具结果，如列表、评论、政策、卖家消息和存储的记忆，在模型看到之前都被净化并用一个带固定标签的围栏包起来。

净化器剥离控制和双向字符、移除任何模仿围栏标记的东西、拆解模仿对话轮次或工具调用的文本、并对大小设上限——这一切的设计，是为了阻止一个敌意的列表冒充系统或填满上下文。

prompt 承担着契约的另一半：被围栏的文字是要去报告的素材，绝不要去据以行动的素材。

### **评测：发布一个非确定性系统**

从一次小的 prompt 改动到一个新工具，任何事都能以难以预测的方式改变 agent 行为，而你在发布的改动往往不是引发回归的那一个。评测就是你在部署前先弄清这点的办法。我们早先关于[agent 的评测](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)的文章涵盖了通用实践。本节涵盖商务 agent 的具体事项。

**评估快照，而非对话**

模型的 API 是无状态的，所以 agent 输出什么，是系统 prompt、工具和 messages 数组的函数。这意味着一段商务对话所能抵达的任何状态，都能被直接构造。于是创建一个评估用例，意味着构造测试状态、附加测试用户消息、并让 agent 从那里跑起来。

随后给结果打分：最终状态和渲染出的响应，包括最后一次写入的参数。在多数情形里，我们不建议去给 agent 抵达那里的路径打分，因为这样的测试用例既脆弱又具限制。

模拟用户的评估——其中第二个模型扮演用户、一个评审员给整段对话打分——是衡量的糟糕工具。两个非确定性系统相互作用需要更大样本、每次试验成本更高、更难评判、并产生难以归因的失败。它们对发现覆盖度缺口、以及对 agent 做一个大致的感觉检查有用，所以用它们去发现案例，然后把每个案例写成一个快照。

#### **在艰难条件下评估行为**

多数团队没能正确地测试被注入的状态。一个用例应当编码失败的先决条件、而不仅仅是任务。如果一个行为只在一轮带着几个工具调用的繁忙首轮之后、或在会话早先的一处矛盾之后才显现，那么一个从干净状态开始的用例会在每个配置上通过、不提供有意义的信息。

我们观察到多数套件都重仓于这类干净状态的用例，所以要确保你的一部分从冗长、杂乱或相互矛盾的历史开始。

##### **覆盖各类商务 agent 评估**

有效的评估需要既测期望行为、也测不期望行为。

对每个正面用例，写下它的负面对应：为每一句「应当拒绝」写一个「应当服务」，为每一句「应当询问」写一个「应当直接做」。缺失的负面用例，是我们在一个套件里发现的最常见缺口。

评估以下几类：

- **核心请求**：构成你流量主体的那些，因为这里的一个失败会影响多数会话。这些包括简单查找、多约束请求、产品和套餐问题、以及多意图消息。对这些问题，检查每个价格、可用性和属性都能追溯到返回的数据，而 agent 在数据缺失时会说数据缺失、而不是编造。
- **依赖上下文的请求**：例如对屏幕上内容的引用、从早先轮次延续的约束、以及针对现有购物车的写入。评估记忆也落进这一桶。检查记忆被抽取、被检索、并改变了答案。
- **安全与品牌用例**：那里的失败要花钱或花信任。这些包括尝试的注入、试图读取另一用户数据的尝试、以及受监管的语言——逐字节检查。把注入拆成两个用例：用户自撰的注入（指令来自用户自己的消息），和数据面注入（它被埋在通过工具结果抵达的产品名、评论或网页片段里）。
- **界面评估**：确保渲染出正确的组件、商品上限被尊重、并且面向用户的文本里没有内部标识符。也要测超时和空结果。
- **同时属于多种能力的请求。** 一位操作员问「如果我把它降价 15%，我有足够的库存来覆盖需求吗？」那是一个定价问题、也是一个库存问题。正确的解会把降价连同库存预测一起暂存；错误的解做一个、跳过另一个。按能力写的评估抓不到这个，因为每个只给自己的那一半打分。为那些需要两个相邻能力一起上的请求写用例，并给答案的两半都打分。

##### **与领域专家一起写评估，并用真实事故**

与那些亲眼见到失败的事关领域专家合作——产品、法务、商家运营、客户关怀和品类管理里的成员——来设计测试用例。真实的失败造出最好的评估，而每用户流程 50-100 个评估用例是一个好的起点。

确保有用例的多样性，如上所述。生产文字记录是从中汲取新用例的绝佳来源，尤其是那些棘手的。编码 agent 擅长生成额外的用例和对抗性变体。[参考仓库](https://github.com/anthropics/commerce-agents)含一个 Claude Code 插件，带着一个按我们推荐方法构建的、撰写评估的 skill。

#### **在一个大组织里发布**

在一家商务企业里，agent 由许多工程团队构建。搜索、结账、定价、营销技术、客户关怀和目录平台，各自拥有 agent 所依赖的系统，各自按自己的节奏发布，而每一个都会想添加或更改一个工具、一个 skill、或一条 prompt 规则。

不同于一个服务，agent 没有严格保护其他模块的模块边界：定价团队所做的改动，与结账共享一个上下文窗口。

诱人的解法是把系统拆成许多子 agent，一个业务单元一个。正如第 1 部分所讨论的，出于质量我们不建议这么做。相反，我们铺排一个为多团队协作去风险的过程：

- **所有权随系统走。** 每个 skill 和工具都有单一归属团队。例如，定价拥有促销工具和定价 skill，关怀拥有订单和退货工具以及 customer-care skill。那份共享 prompt 对公共部分有一个单一的平台级归属者、对领域专属部分有一个领域归属者。
- **一次改动与它的用例一起发布，而 CI 为它跑一组选定的用例。** 一个贡献 skill 的团队也贡献它的用例，包括负面用例和针对相邻 skill 的边界用例。在每个 pull request 上跑整个套件，太慢、太贵、活不下来，所以要从中构建一个 CI 集。那个集将由一组最高流量请求的核心用例和每一个安全用例组成。在此之上，为改动所触及的任何东西跑用例。对一个 skill，那意味着它自己的用例和邻居的边界用例。对一个工具，那是每一个调用它的用例。对那份共享 prompt，那是整个评估套件，因为一切都在读系统 prompt。我们建议就几次试验的通过率、以及缓存命中率和每轮成本做门控。在夜间和每次发布前跑整个套件也是好实践。跨团队的回归就在这些运行里被抓到。
- **agent 也应当纳入发布日历。** 它是一个部署单元，于是一个坏改动会一次性抵达每个用户。先把 prompt 和 skill 改动滚到一个小批金丝雀队列，保留一个无需部署就能关掉单个 skill 的开关，并像你对其他系统冻结那样，在高峰时段之前冻结 agent。

关于这一安排的人性一面，见[构建高效的人机协作团队](https://claude.com/blog/building-effective-human-agent-teams)。

## **展望未来**

本文所描述的大部分内容，都与模型无关。工具调用你已在运行的系统，skill 编码你已在遵循的流程，评测就是把你的产品需求文档写成测试，而 harness 执行你本会为任何客户端执行的政策。模型会持续改进，而当一款更好的模型发布时，我们描述的架构会以一次配置改动加一轮评估扫参来采纳它。其余一切继续管用。

思考你产品界面的路线图也很重要。这一架构会比聊天面板更长寿。同一个 agent 能在语音上工作，也能在用户开口前就对一次票价下跌主动行动。对一个已经有了评估和工具的团队，那些都是呈现层的项目。更长远些，你店面的一部分流量会来自代表用户购物的 agent。那些让你的 agent 保持在界内的来源、暂存和批准规则，也正是让你能安全地把工具向那些 agent 开放的东西。

商务历来奖励把购买过程做得尽可能顺畅。agent 让那轻松得多。查看[完整的参考实现](https://github.com/anthropics/commerce-agents)，含消费者和商家两种 agent、以及零售、旅游、电信和娱乐可运行的示例。
