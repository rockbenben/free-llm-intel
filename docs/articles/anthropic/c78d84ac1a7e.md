# 量化 agentic 编码评测中的基础设施噪声

发布于 2026 年 2 月 5 日

仅基础设施配置一项，就能让 agentic 编码基准的分数上下浮动若干个百分点——有时甚至比榜单上头部模型之间的差距还大。

像 SWE-bench 和 Terminal-Bench 这样的 agentic 编码基准，常被用来比较前沿模型的软件工程能力——榜单头部名次之间往往只相差几个百分点。这些分数常常被当作模型相对能力的精确度量，并日益左右着「该部署哪个模型」的决策。然而我们发现，仅基础设施配置就能造成超出这些差距幅度的差异。在内部实验中，Terminal-Bench 2.0 上资源最多与最少的配置之间相差 6 个百分点（p < 0.01）。

静态基准直接给模型的输出打分——运行环境不参与结果。agentic 编码评测则不同：模型被赋予一个完整的环境，在其中编写程序、运行测试、安装依赖，并跨多轮迭代。运行时不再是被动的容器，而是问题求解过程的组成部分。两个拥有不同资源预算和时限的 agent，做的并不是同一份考卷。

评测开发者已开始考虑这一点。例如 Terminal-Bench 2.0 在其最新的 2.0 版本中，按任务逐一指定了推荐的 CPU 与内存。然而，指定资源和始终如一地强制执行资源是两回事。而且我们发现，强制执行的方法本身也会改变基准最终实际测量的内容。

## **我们是如何走到这一步的**

我们在一个 Google Kubernetes Engine 集群上运行 Terminal-Bench 2.0。在校准配置时，我们注意到自己的分数与基准官方榜单对不上，且基础设施错误率高得惊人：多达 6% 的任务因 pod 错误而失败，其中大多数与模型解决任务的能力无关。

分数的差异归结于强制执行方式。我们的 Kubernetes 实现把每任务的资源规格同时当作下限和硬性上限：每个容器被保证获得指定资源，但一旦超过就会被杀掉。容器运行时通过两个独立参数来强制执行资源：一个保证分配（预留的初始资源），以及一个会导致容器被杀掉的硬上限。当这两者设为同一个值时，就为瞬时尖峰留下了零余量：一次瞬时的内存波动就可能把本可以成功的容器 OOM-kill（内存溢出杀掉）。为了缓解这一点，Terminal-Bench 的榜单使用了另一家沙箱提供方，其实现更宽松——允许临时超配而不终止容器，以偏向基础设施层面的稳定性。

这一发现引出了更大的问题：资源配置到底在多大程度上影响评测分数？

为了量化脚手架（scaffold）的影响，我们在六种资源配置下运行 Terminal-Bench 2.0，从严格按每任务规格执行（1x，规格同时作为下限和上限），到完全无上限。其余一切保持恒定：相同的 Claude 模型、相同的 harness、相同的任务集。

在我们的实验中，成功率随资源余量增大而上升。这主要归因于基础设施错误率在每一步单调下降，从严格执行的 5.8% 降到无上限时的 0.5%。从严格执行到 3x 余量（5.8% 降到 2.1%）的降幅在 p < 0.001 上显著。余量越多，因超出分配而被杀的容器就越少。

从 1x 到 3x，成功分数在噪声范围内波动（p=0.40）。多数在 1x 时崩溃的任务无论如何都会失败——这是我们在数据中观察到的。agent 不断试探，撞上一堵资源墙，然后被抢占，但它本就从未走在通往正确解的路上。

然而大约从 3x 起，这一趋势发生变化：成功率的上升快于基础设施错误的下降。

从 3x 到无上限，基础设施错误再降 1.6 个百分点，而成功却几乎跳升 4 个百分点。额外的资源让 agent 能够尝试那些只有靠充裕分配才奏效的方法，例如拉取大型依赖、启动开销大的子进程、运行内存密集型的测试套件。在无上限资源下，相对 1x 的总提升为 +6 个百分点（p < 0.01）。在边际上，像 `rstan-to-pystan` 和 `compile-compcert` 这样的任务，在获得内存余量后成功率显著提升。

## **这如何影响测量**

在大约 3x 的 Terminal-Bench 规格以内，额外资源解决的是基础设施可靠性问题，即瞬时资源尖峰。Terminal-Bench 维护者所用的沙箱提供方其实是在幕后隐式地做这件事——评测变得更稳定，却没有变得更简单。

然而在 3x 以上，额外资源开始真正帮助 agent 解决它原本无法解决的问题，这表明限制确实会改变评测所测量的内容。严苛的限制会无意间奖励极其高效的策略，而宽松的限制更宽容，会奖励那些能更好利用所有可用资源的 agent。

一个能极快写出精简高效代码的 agent，会在严苛约束下表现出色。一个用重型工具暴力求解的 agent，则会在宽松约束下表现出色。两者都是正当值得测的东西，但把它们压缩成一个分数、又不说明资源配置，就使得这些差异——以及现实世界的可推广性——难以解读。

在 `bn-fit-modify`（一个要求做贝叶斯网络拟合的 Terminal-Bench 任务）上，某些模型的第一步动作是安装标准 Python 数据科学栈：`pandas`、`networkx`、`scikit-learn,` 以及它们的全部工具链。在宽松限制下，这行得通。在严苛限制下，pod 会在安装阶段内存耗尽，agent 还没来得及写下一行解题代码。存在一种更精简的策略（仅用标准库从零实现数学），有些模型确实默认采用它，另一些则不然。不同模型有不同的默认方法，而资源配置恰好决定了这些方法中的哪些能成功。我们在不同 Anthropic 模型上复现了这一核心发现。效应的方向一致，只是幅度不同。同样的趋势似乎在 Claude 以外的模型上也成立，但我们尚未严格测试。

我们还通过在 SWE-bench 上做交叉实验，测试这一模式是否在 Terminal-Bench 之外的评测上成立。我们在 227 道题、每题 10 个样本的范围内，把总可用内存从基线一直调高到 5x。同样的效应成立，只是幅度更小：分数仍随内存单调上升，但 5x 只比 1x 高 1.54 个百分点。SWE-bench 任务对资源的需求更低，因此效应更小是预期之中的，但这表明在 SWE-bench 上资源分配也并非中立。

## **其他方差来源**

资源分配并非唯一的隐藏变量。在某些配置下，时限也开始发挥作用。

原则上，评测设置中的每一个元素都能影响最终分数——从集群健康到硬件规格，从并发级别乃至到出网带宽。agentic 评测按其构造就是端到端的系统测试，系统的任何组件都可能充当混淆因子。我们曾零星观察到，通过率会随一天中的时段波动，很可能因为 API 延迟随流量模式和事故而变化。我们尚未正式量化这一效应，但它说明了一个更大的道理：「模型能力」与「基础设施行为」之间的边界，比单个基准分数所暗示的要模糊得多。模型提供方可以通过专用硬件来为其评测基础设施屏蔽这种影响，但外部评估者无法轻易做到同样。

公开基准通常意在测量纯粹的模型能力，但实践中它们有可能把模型能力与基础设施怪癖混为一谈。有时这或许是可取的，因为它实现了整个技术栈的端到端测试；但更多时候并非如此。对于打算公开共享的编码评测，在一天中的多个时段、跨多天运行会有助于平均掉噪声。

## **我们的建议**

理想情形是在完全相同的硬件条件下运行每次评测——既包括运行评测的脚手架，也包括推理栈——这将确保全面可复现。然而这未必总是可行的。

鉴于容器运行时实际如何强制执行资源——通过一个保证分配和一个单独的硬杀死阈值——我们建议评测按任务同时指定这两个参数，而不是单一钉死的值。单个精确规格会把保证分配设为等于杀死阈值，留下零余量：我们在 1x 时记录到的瞬时内存尖峰就足以让评测失稳。把两个参数分开，能让你给容器留出足够的喘息空间以避免无谓的 OOM-kill，同时仍执行一个防止分数虚高的硬上限。

两者之间的区间应当校准到：下限和上限处的分数落在彼此的噪声范围之内。例如，在 Terminal-Bench 2.0 中，把上限设在每任务规格的 3x，将基础设施错误率削减了约三分之二（从 5.8% 到 2.1%，p < 0.001），同时让分数提升保持温和、远在噪声之内（p = 0.40）。这是一个合理的权衡：基础设施这个混淆因子在很大程度上被中和了，又没有移除有意义的资源压力。确切的倍数会因基准和任务分布而异，因而应当报告，但这个经验校准的原则是通用的。

## **我们为何在意**

这些发现带来的实际影响，超出了评测基础设施本身。基准分数正日益被用作决策输入，但这种关注度（和依赖度）的提升，并没有在其如何运行或报告方面带来相应的严谨。就现状而言，榜单上 2 分的领先，可能反映的是真实的能力差异，也可能只是反映某个评测跑在了更强悍的硬件上，又或者跑在了某个更走运的时段，或二者皆有。若没有公布（或标准化）的设置配置，外部很难分辨，除非有关各方愿意额外费力在完全相同条件下复现客观结果。

对 Anthropic 这样的实验室而言，其含义是：agentic 评测的资源配置应当被当作一等实验变量来对待，像提示格式或采样温度一样严谨地记录和控制。对基准维护者而言，公布推荐资源规格（如 Terminal-Bench 2.0 所做）能帮上大忙，而说明强制执行方法则会补上我们所识别的缺口。对任何使用基准结果的人来说，核心结论是：agentic 评测上的小分数差异，其不确定性比所报数字的精确度所暗示的要大得多——尤其是一些混淆因子实在难以控制。

在资源方法被标准化之前，我们的数据表明：在评测配置被记录并匹配之前，榜单上低于 3 个百分点的差异都值得怀疑。我们在 Terminal-Bench 的中等资源配置范围内观察到的散布仅略低于 2 个百分点。朴素的二项式置信区间本身就已横跨 1-2 个百分点；我们在此记录的基础设施混淆因子是叠加在其之上，而非包含在其之内。而在分配范围的极端，散布达到了 6。

几分领先，可能意味着真实的能力鸿沟——也可能只不过是一台更大的虚拟机。
