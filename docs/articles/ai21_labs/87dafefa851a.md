## 一种解析从右向左（RTL）书写的 PDF 文档及低资源语言的新技术

当前的解析策略用在希伯来语、阿拉伯语等从右向左（RTL）书写的语言上时会失效。我们引入一种新颖的编码技术，把 PDF 文档从 RTL 格式转换成易于解析的 LTR 格式，使 RTL 文档的整体解析质量显著超越当前 SOTA。

## 挑战：低资源语言的解析鸿沟

在 [RAG](https://www.ai21.com/blog/structured-rag-enterprise-accuracy/) 架构中，文档解析是基础的摄取层。如果解析过程无法准确捕捉文档的结构与语义细微之处，就会向流水线引入大量噪声。这往往造成「垃圾进、垃圾出」的困境，很难靠下游优化或精巧的提示词彻底解决。

在一次系统性的解析器评估中，我们用一个包含文本与表格的合成文档数据集测试了语言对解析质量的影响。结果触目惊心：以从右向左（RTL）语言书写的文档，其解析质量相比 LTR 文档大幅下降，并且充斥着格式错误和明目张胆的幻觉。

这不只是学术发现。我们正在构建需要支持希伯来语和其他 RTL 语言的 RAG 系统，而这一解析鸿沟正严重损害客户处理自身数据的能力。认识到现有解析器无论对我们的基准还是客户需求都不够用，我们决心填补这一鸿沟。

用 GPT-4.1 解析时，文本中出现大量幻觉。例如把「上尿路（דרכי השתן העליונות）」替换成了「下尿路（דרכי שתן תחתונות）」。

### 深入问题

为了解决这个挑战，我们开发了一种新技术，把这些语言转换成以英语为中心的解析器能理解的格式。通过弥合这一鸿沟，我们让现有工具在 RTL 语言上释放出全部性能。

第一步是参照 [OmniDocBench](https://github.com/opendatalab/OmniDocBench) 构建一个强健的希伯来语数据集——这套指标是解析器评估在学术界与工业界的标准。这确保了对常见企业格式的覆盖，如复杂表格、演示幻灯片、技术论文和商业报告。

随后我们把该数据集经过一个自动解析加人工校验的流程。

- **预处理：** 一个改进版的 [MonkeyOCR](https://github.com/Yuliang-Liu/MonkeyOCR)（一个用 VLM 同时做版面检测和各部分 OCR 的流水线解析器）为页面元素生成初始元数据，包括类型、阅读顺序和位置。
- **标注：** 借助我们数据标注系统中的定制界面，利用预解析数据快速标记内容、类型与阅读顺序。

### 探索解法

已知的解析策略各有缺陷：从零训练新模型对数据和算力的需求太高；基于规则的修补无法应对反复无常的幻觉和格式 bug。

常规工具都出局后，我们必须发挥创意。我们一开始就知道解析器擅长处理英语和数字数据，于是策略是把问题转移到系统本来就理解的格式里。我们首先尝试用数字表示单词来验证这一思路，但解析器要么忽略内容，要么丢失文档结构。这把我们引向实验的核心：我们能否「骗」过解析器，让它把一份 RTL 文档当作英语文档来处理？

我们尝试了多种方法，以确定编码这种「英语」表示的最优方式：

- **直接翻译：** 我们先把 RTL 文本直接翻译成英语。虽然这为解析器提供了可识别的语言，但词长与方向性的差异造成了严重的格式错误。文本经常越过表格分隔线，破坏文档的原始版面。
- **基于长度的映射：** 随后我们尝试把每个 RTL 单词映射到一个字符数完全相同的英文单词。然而由于字符宽度不一（例如 "i" 与 "w"），文本仍无法与原始文档结构对齐，导致重叠和版面不稳定。
- **基于形状的映射（最终解法）：** 最后，我们改进方法，按单词的视觉几何形状（而不仅是字符长度）来选择英文单词。通过匹配 RTL 文本的物理「形状」和包围盒，我们成功保全了文档的完整性。

这种基于形状的编码被证明高度有效。我们的实验揭示了一个关键洞见：图形结构——包括文本的结构和文档的结构——对解析质量的影响比语义内容更大。**通过优先保证版面，我们成功把高性能的英语解析能力借用到了 RTL 语言上。**

## 破解密码：用 Word Shape Encoding 改进 RTL 解析

确定基于形状的映射是最有希望的路径后，我们按以下流程实现了方案：

- **构建参考索引：** 我们取一个大型英文词汇集合，用标准字体（"Arial"）和字号（"10"）渲染并测量每个单词。这让我们能测出每个单词的精确宽高，并把这些维度映射进一个持久化索引。这一索引阶段离线完成，创建一张固定的「形状-单词」索引表，作为整个编码过程的基础。

- **编码 RTL 文档：** 我们抽取文档中的每个单词（英文单词和数字除外）及其对应的包围盒。根据包围盒的尺寸，我们用 KNN 算法把每个 RTL 单词映射到一个矩形尺寸相近的英文单词，并用余弦相似度函数来归一化不同字号。结果是每个 RTL 单词与「形状-单词」索引表中一个英文单词之间形成一对一（可逆）的映射。

- **文档渲染：** 编码完成后，我们利用结果渲染出原始 PDF 的「英语等价」版本。这包括两个主要动作：**文本替换**与**版面镜像**，把文档从 RTL 转换为 LTR。
- **文本替换：** 我们把每个 RTL 单词替换为其映射的英文单词。虽然字体统一为 Arial，我们保留了原始样式，包括字号、加粗和斜体。
- **空间镜像：** 为契合 LTR 阅读习惯，我们反转所有页面元素的横坐标。**图像与文本：** 移动到页面上的精确镜像位置。**矢量图形：** 完整镜像，确保视觉与结构一致。

最后，我们把替换和镜像后的元素渲染成一份新的 PDF。这个「看起来像英语」的文件保持了原文档精确的图形结构，同时与标准英语解析器完全兼容。

- **文档解析**：处理后的 PDF 现在看起来就是标准英语，任何 LTR 模型无需修改即可处理。为了检验这种通用性，我们以 PDF 转 Markdown（MD）为基准，在多种不同模型架构上进行了实验（详见下文）。
- **解码：** 给定 Markdown 输出与原始映射表，我们可以把每个矩形块翻译回原先编码的单词，把原始语义重新带回文本。我们使用 Levenshtein 距离寻找最佳匹配的原始单词，而不是精确匹配。因为一些解析器本质上是统计式的，我们发现它们即使对我们编码后的英文单词也可能产生细微偏差。例如下面这个案例：

- **目标：** 我们编码文档中的英文单词是 **"paypal"**。
- **解析器错误：** 模型把这个词幻觉成了 **"payplus"**。
- **解决：** 通过相似度搜索，我们的系统识别出预期匹配是 **"paypal"**，进而成功指回原始希伯来语单词：**"הבהרה"**。

## 评估与结果

为了验证方法的有效性，我们在多种多样的解析方案上做了基准测试。确保方法在不同架构「类型」——从多模态模型到闭源企业工具——上都保持稳健，这一点很重要。

我们把解析器分为三组：

- **视觉语言模型（VLMs）：** 能直接处理图像的统一模型，例如 **GPT-4o**、**Gemini 3.0** 和 **Qwen2.5-VL**。这些模型代表了视觉文档理解的当前最先进水平。
- **模块化流水线：** 这类解析器分阶段处理文档，先识别页面结构（版面分析），再分别处理表格或段落等单个元素。例子包括 [MinerU](https://mineru.net) 和 [Marker](https://github.com/datalab-to/marker)。
- **黑盒 / SaaS 商业方案：** 来自第三方厂商的专有解析器，不公开底层实现。例子包括 [LLaMaParse](https://www.llamaindex.ai/llamaparse) 和 [Apryse](https://apryse.com)。

### 评估框架

我们通过比较这些模型在使用与不使用我们的 Word Shape Encoding 方法时的表现来度量成功。使用人工标注的希伯来语文档 ground-truth 数据集，我们评估两个主要指标：

- **文本解析准确率：** 准确且按正确顺序提取段落文本的能力，以原始文档与解析文档之间的编辑距离度量。
- **表格抽取质量：** 我们使用 Table-TEDS，一种同时比较表格结构与内容的方法。

#### 结果

结果显示，在不同模型上都相对当前 SOTA 有显著提升，表格方面尤为突出。主要的例外是 Gemini：它在希伯来语解析上整体表现很差，而对我们方法则是只能用「过敏反应」来形容的糟糕结果。

## 把 Word Shape Encoding 用在其他 RTL 语言上

虽然我们的方法对希伯来语始终能改进结果，阿拉伯语的表现则更微妙。以 [**Kitab-Bench**](https://github.com/mbzuai-oryx/KITAB-Bench) 为评估框架，我们观察到性能分化：我们的编码方法提升了 **GPT-4o-mini** 的解析质量，却让 **GPT-4.1** 的质量下降。

我们推断：对 RTL 格式的处理并非解析质量的唯一决定因素，模型对特定语言的曝光度非常重要。对阿拉伯语这样的广泛使用语言，尽管其书写体系复杂，解析质量依然很高，原因很可能是可用的训练数据量极其庞大。

为了验证这一理论，我们需要一个量化指标来评估模型对阿拉伯语 OCR 的理解程度——以缺乏「困惑（confusion）」来表达。我们假设：如果模型「困惑」，那么对同一提示多次提问会得到差异显著的回答。我们把这定义为 **自洽性（self-consistency）**：同一输入下独立输出之间的一致程度。

计算方法：对我们的测试集解析 $n$ 次，计算所有输出之间的平均两两相似度。数学表达为：

\text{Self-Consistency} = \frac{1}{n(n-1)/2} \sum_{i=1}^{n-1} \sum_{j=i+1}^n S(G_i, G_j)

其中：

- n 是独立解析的次数。
- G_i 和 G_j 是各次生成的解析结果。
- S 是由 **OmniDocBench** 指标定义的相似度函数。

我们的自洽性分析揭示了一个清晰的模式：

- **GPT-4.1 + 阿拉伯语：** 基线自洽性高，这解释了为什么我们的编码方法几乎带不来改进——模型本来就擅长阿拉伯语 OCR。
- **GPT-4.1 + 希伯来语：** 基线自洽性较低，我们的方法可度量地降低了这种困惑。
- **GPT-4o-mini + 阿拉伯语：** 表现与 GPT-4.1 处理希伯来语时类似——升高的困惑被我们的方法成功缓解。

简言之，我们的方法在模型最不自信的场合带来最大的收益，原因很可能是训练数据中对该语言的曝光有限。

## 训练我们自己的模型

尽管一开始不愿意训练自己的解析模型，我们最终还是这么做了。我们的编码方法带来了强劲的 RTL 性能，但有一个关键限制：依赖 PDF 元数据。这意味着它无法处理其他文件格式（如 PowerPoint）或扫描/图像型的 PDF。视觉语言模型（VLM）能解决这个问题：它们以图像为输入，不依赖元数据。

除技术限制外，还有一个现实因素：在多数 ML 基础设施中，模型是一等公民。一个独立模型比一个包装我们方法的服务更容易部署。

基于这些约束，我们用原始方法生成的数据训练了一个新模型。结果：一个继承了同样高质量 RTL 解析能力、且泛化到 PDF 之外的模型。

### 构建训练数据

**采样：** 我们首先从网上精选 PDF，优先选取含表格的幻灯片与文档，以贴合我们主要客户的核心用例。从每份文档中随机抽取一页。

**生成目标：** 我们把每个抽样页面转换成 120 DPI 图像。然后用我们的方法处理原始 PDF 页面，生成对应的 Markdown 输出，作为「ground truth」目标。

**过滤：** 为确保数据质量，我们应用两条过滤标准：

- **内容相关性：** 过滤掉希伯来语文本量不足的页面。由于我们的方法依赖 PDF 元数据（文本层），可检测文本的存在是文件可用的必要代理。
- **置信度检查：** 使用前文描述的[自置信度](https://docs.google.com/document/d/10JwLpORxwVD4RqPx9LaaOdrij1tEbk0gIQhoPsF7DhI/edit?tab=t.d4tryxbxx32p#heading=h.433d1zil1ady)指标，剔除方法返回低置信分数的所有样本，确保模型只在高确定性样本上训练。

**训练：** 我们从 [DeepSeekOCR](https://github.com/deepseek-ai/DeepSeek-OCR) 起步，因为它在规模（3B 参数）与已有希伯来语能力之间取得了很好的平衡。随后用上一节生成的数据对该模型进行微调，并以人工整理的希伯来语数据集作为测试集。

**结果：** 尽管训练仍在进行，早期结果已令人鼓舞——我们超越了 SOTA，当前的解析模型超过了 GPT-5.2。如前所述，在 GPT 模型上叠加 Word Shape Encoding 能进一步改进 RTL 解析。

话虽如此，我们确实看到表格质量有所下滑。分析错误后，我们发现某些表格类型模型难以准确重建。我们认为原因在于：

- **数据不足：** 我们的训练集可能不够大，未能覆盖这些边缘情况。
- **微调深度：** 模型可能对这些模式的学习尤其困难，需要更有针对性的数据和更深入微调过程。

## 结论

在这篇文章中，我们提出了 Word Shape Encoding——一种通过借用 LTR 解析器优势来弥合低资源语言解析鸿沟的新方法。我们证明该方法在我们的希伯来语数据集上表现最佳，并随后展示了如何用它的输出来合成训练数据。这让我们得以训练一个独立模型，克服原始方法对元数据的依赖。

我们训练的模型前景可期，但技术挑战仍在。我们预期扩大训练数据集并打磨方法会带来更多提升。

展望未来，我们看到 Word Shape Encoding 可以延伸到其他复杂解析挑战，如图表和图形解析。但这里有一个更大的理念，其适用性超越解析本身：找出模型的弱点，然后构造一个「归约函数」，把那些问题映射到模型的强项领域。在我们的案例中，我们把一个希伯来语感知问题转换成了英语推理问题。我们相信这一策略的适用范围远超解析、也远超 RTL 语言。
