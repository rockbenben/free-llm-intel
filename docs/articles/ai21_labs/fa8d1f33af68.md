## 简要概述

我们在 SWE-rebench 基准上取得了一项新的最先进（SOTA）成果：针对 12 月到 3 月之间的 123 个 issue，issue 解决率达到 60.9%，超过了该切片上此前公开的最好成绩。

这一成果来自对 agent 上下文提取阶段的重新思考——这是我们坚持并不断打磨的一个反直觉的设计选择。我们摒弃了「先富化、再求解」（enrich then solve）的做法——即先做上下文提取、再生成解决方案——而是将顺序反转：先大规模生成解决方案，再利用生成的候选方案来实现更好的上下文提取。要达到最先进水平，光靠顺序反转还不够——还需要精心优化提取器（extractor）如何利用这些候选方案，从而浮现出最相关的代码。

我们的发现表明：对某个任务先做简单的初始并行 *N* 次求解尝试，就能显著帮助代码库探索，产出一张高度聚焦的上下文地图，并可在 agent 的最终评估步骤中加以利用，生成更准确的输出。这一执行策略显著提升（noticeably improves）了 agent 的准确率，且不推高成本，也胜过在传统顺序下对生成步骤做朴素的规模扩张。

这项工作融入了 AI21 更广泛的 agent 优化研究脉络，与此前的案例研究（[SWE-bench Verified](https://www.ai21.com/blog/test-time-compute-swe-bench/)、[BrowseComp-Plus、Deep Research Bench](https://www.ai21.com/blog/maestro-deep-research-agents/)）一脉相承，每一篇都受益于 AI21 Maestro 优化方法中不同的策略。我们希望我们围绕编码 agent 流水线顺序所做的贡献，能够成为构建日益精准、日益低成本的 AI 软件工程师的蓝图。

在这篇文章中，我们将逐步展示从基线 ReAct 循环到这一成果的全过程——并说明我们如何在把总成本控制在一个领先编码 agent 之下之余，不断推高准确率。

## Agentic coding 的架构

Agentic coding（智能体化编程）已迅速成为人工智能中最令人兴奋、研究最密集的前沿领域之一。现代的编码 agent——如 Claude Code、Codex 和 Cursor——已超越简单的代码补全工具，被设计为自主的软件工程师——推理复杂问题、导航大型代码库、执行多步骤任务来解决现实世界的问题。

### 编码基准的解剖结构

为了准确评估这些 agent，业界逐渐形成了一套标准化的基准架构。典型的设置如下：

- **输入：** agent 会收到一段自然语言的 **issue 描述**（例如一个 GitHub issue），描述某个 bug 或功能需求。
- **环境：** agent 被放入一个 **Docker 容器**，其中包含目标代码仓库以及必要的运行时环境。
- **执行：** agent 通过执行动作与该环境交互——最典型的是通过终端运行 **bash 命令**，用于搜索文件、运行测试和编辑代码。
- **输出：** 目标是让 agent 产出解决方案，通常以 **git patch** 的形式呈现。随后基准会用一组隐藏单元测试来评估这个 patch，验证 issue 是否真正被解决。

### 建立基线：经典 ReAct 循环

从零开始构建编码 agent 时，最直接的起点就是经典的 **ReAct（Reasoning and Acting，推理与行动）循环**。

要在编码基准环境中运行这个基础实现，只需给 agent 配备单一而强大的工具：**访问 Docker 终端**。agent 阅读 issue，推理下一步该做什么，执行一条终端命令（例如 grep、cat 或 pytest），观察输出，然后重复这个循环，直到它认为问题已经解决。

为了建立基线，我们实现了这个经典 ReAct 循环，并在 SWE-rebench 的 2025/12/15–2026/3/1 评估窗口上，使用 GPT-5.2 作为生成模型（设置为 medium 推理强度）进行评估。在这些条件下，原始 agent 达到了 **53.8%** 的解决率。我们之所以使用 SWE-rebench，正是因为它被设计用来抵御影响旧数据集的数据污染（contamination）和过拟合——而随后取得的提升也来自超越该基准的通用设计选择。虽然这是一个不错的基线分数，但要把成功率推得更高，我们需要更复杂的编排策略。

## 达到更高的解决率：利用常见优化策略

研究人员提出了多种提升 agent 准确率的方法，例如上下文富化（收集相关的代码仓库信息）、[横向扩展](https://arxiv.org/abs/2501.14723)（并行生成并评估多个候选解决方案），以及将二者结合的[「先富化再扩展」（"enrich then scale"）agent 架构](https://arxiv.org/abs/2407.01489)所带来的综合收益。下面我们逐一审视。

### 策略一：上下文富化

在基础 ReAct 循环中，没有显式的步骤划分；agent 只有一个宽泛的目标——解决 issue。虽然这种设置自然会促使 agent 自行执行一些信息收集动作，但完全从零开始，让导航大型代码库成为一道巨大的障碍。

我们的实验表明，在最开始引入一个**专门的上下文富化步骤**可以改善结果。这并不意味着 agent 之后不需要随机应变地收集更多信息，只是它有了一个比基础 ReAct 循环更「有准备」的起点。当我们引入这个专门步骤——架构为一个简短、聚焦的 ReAct 循环，由同一个模型驱动，唯一目标是收集相关源代码——基线解决率从 **53.8% 提升到 55.6%**。

### 策略二：横向扩展

由于基于 LLM 的编码 agent 本质上是非确定性的，用完全相同的 agent 对完全相同的 issue 描述多次运行，可能产生完全不同的轨迹和结果。agent 第一次尝试可能陷入死循环，却在第二或第三次运行时凭运气找到了正确解法——这一点在我们早前[关于 SWE-bench Verified 的工作中已经演示过](https://www.ai21.com/blog/test-time-compute-swe-bench/)。

横向扩展正是利用了这一行为，把算力预算当作提升准确率的杠杆。我们不依赖单一线性运行，而是横向扩展：

- **生成并行 rollout：** 多次并行运行 agent，生成一组多样化的候选 patch。
- **选出最优：** 使用某种选择机制（例如 LLM 评审 judge）评估候选并挑出最佳者；若没有候选看起来正确，则由它综合出一个更好的。

为了在实验中验证这一策略，我们对每个 issue 将基线 ReAct 循环并行运行五次，并使用 LLM judge 从生成的候选中挑选最优 patch。这一简单的横向扩展策略成功把解决率从 **53.8% 提升到 55.4%**，展示了用推理算力换性能的力量。这也揭示了一个有用的上限：设想一个「完美」评审——一个只要五个候选中有任何一个正确就总能选对的 oracle。在该 oracle 下，我们的解决率将达到 63.8%（即所谓的 pass@5 指标）。真实 LLM 评审的成绩与这个 oracle 之间的距离就是「选择差距」（selection gap）：那些我们已经生成却没能选出的正确解。换句话说，**扩展抬高了天花板；我们能兑现多少取决于评审的质量。**

至此，我们手中已有两个各自被证明有效的策略。如果把它们结合起来，解决率还能推多高？

## 组合优化策略：反转流水线顺序的威力

一旦决定同时实现横向扩展和上下文富化，下一个设计选择就是以*什么样的顺序*来组合它们。

### 直觉做法：先富化、再扩展

将这两种策略按标准线性方式编排的做法已有文献记载，如前所述。

- **上下文富化：** 运行一个专门步骤，收集相关代码库信息。
- **横向扩展：** 将富化后的上下文喂给 agent，生成多个候选 rollout。
- **选择：** 从生成的候选中挑选最佳 patch。

这种做法看起来很合理——先给 agent 提供上下文，让它生成更好的初始尝试。事实上，这一假设也确实成立了。通过实现这种方式，我们把解决率提升到了 **57.7%**。

然而，尽管这一方法带来了明显收益——相对 53.8% 的起点尤其如此——我们当前的选择机制仍把大量性能留在了桌上。选对候选往往需要看到相关代码库的更广上下文，而不只是评估孤立的最终 git patch。这正是我们先前定义的选择差距——在这里它相当宽：我们的真实评审（而非 oracle）远低于 63.8% 的 pass@5 天花板。

可能的原因是：评审在缺乏更广泛代码库上下文的情况下逐个评估孤立的 git patch，无法分辨真正正确的修复与「看起来像对的」修复。

归根结底，这个差距凸显了一个强大的机会：要缩短与 pass@5 潜力之间的距离，我们必须确保评审拥有做出最优选择所需的全局视角。我们怎样才能给 agent 注入更多相关数据呢？

### 我们的做法：先扩展、后富化

选择差距指向了根本原因：我们的评审在缺乏足够上下文（关于 patch 所触及代码的上下文）的情况下于多个 patch 之间做选择。先富化并不能解决这个问题——仅凭 issue 描述构建的上下文只是部分的，因为提取器对修复实际应该落在哪里毫无信号。

但这个信号其实已经存在于我们的流水线中。我们生成的五个 rollout 中的每一个，实际上都是关于「修复位于何处」的假设：应该探索哪些文件和函数。按照「先富化、再扩展」的方式工作时，我们只把这些 rollout 用于最终投票，而丢弃了它们的定位（localization）信号。反转顺序则能利用这一信号：让提取器先看到候选 rollout，用它们在最终选择之前引导一次远为精准的搜索。

于是我们的流水线变成：*初始 rollout → 上下文富化 → 输出选择*

真正开始见效的就是这里：通过反转方法，我们超越了直觉设置，把分数推到了 **59.7%** 的解决率。

它有效——但为什么？当工具只能基于一份原始 issue 描述在海量代码库中盲目搜索时，上下文提取是出了名的难。通过移动流水线位置，我们把初始候选 rollout 直接喂给源代码提取器（由 GPT-5.2 medium 推理驱动）——实际上是**向上下文富化阶段注入了一些上下文**。这是我们使用的系统提示词：

```
Round-1 system prompt (_LLM_GUIDED_SYSTEM):
You are helping select relevant source code for a code-review task.
You will be given a problem statement and one or more candidate patches (unified diffs).
Your job is to output up to 10 bash commands that we will run in the repository root.
1. Show the full definition of functions/classes that the patch modifies (grep -n or sed to extract a range).
2. Show callers of those functions (grep -rn 'func_name' src/).
3. Show test files that cover the changed code (grep -rn 'func_name' tests/ or find tests/ -name '*.py').
4. Show imports and dependencies of the changed files (head -n 30 file.py to see imports).
5. Show any related config, schema, or fixture files referenced in the patch.
Rules:
- Do NOT produce commands that output more than ~150 lines (avoid plain `cat` on large files).
- Prefer: `grep -n -A 10 'pattern' file`, `sed -n 'N,Mp' file`, `head -n 80 file`.
- Output format: one command per line, no numbering, no explanations.
- You may wrap the block in ```bash ... ```.

Then it runs multiple rounds, with the follow-up prompt (_LLM_GUIDED_FOLLOWUP) on each subsequent round:
Based on the outputs above, suggest up to 10 more bash commands to dig deeper.
Focus on gaps revealed by round 1 — for example:
- If a function was referenced but its definition wasn't shown, fetch it now.
- If a test file was found, show the relevant test cases.
- If an import pointed to another module, show the relevant parts of that module.
- If output was truncated, use `sed -n` to fetch the missing range.
Same format: one command per line, no numbering, no explanations. Only commands that add NEW information not already shown above.
```

提取器不再是在黑暗中摸索，而是可以分析初始 rollout 试图在哪里做修复，并把搜索聚焦到代码库中这些高概率区域。作为一个实际的附带好处，既然我们已经决定做横向扩展，这些候选 rollout 是我们已经在算力预算里「付过钱」的，我们顺势利用它们来引导提取器。这种定向富化让最终选择步骤（此时由 GPT-5.2 high 推理驱动）能在远为精准的数据上工作，从而使整条流水线更加有效。

#### 度量「上下文覆盖率」

为了证明注入的 rollout 上下文确实相关，我们对照基准提供的「gold patch」来度量其有效性。虽然「gold 上下文」并没有一个权威定义，但基准*确实*提供了每个 issue 求解所需的 ground-truth patch。我们利用这一信息追踪提取器浮现「真正需要修复的文件」的成功程度，比较两种提取器：

- 仅基于 issue 的提取器：只喂问题描述，即「富化 → 扩展」方案中的做法
- issue + 候选提取器：喂问题描述 + 五个候选 patch，即我们的「扩展 → 富化」方案中的做法。

从数据来看，感知 patch 的流水线（patch-aware pipeline）最突出的优势并不只是一般覆盖率的边际提升——而是对可能酿成灾难的失败筑起了巨大的护栏。

最亮眼的发现是：提取器一个 gold 源文件都没访问到的情况从 **9.3% 降到仅 2.7%**，意味着完全盲区总计**减少了 71%**，这表明给提取器提供上下文能有效防止它彻底走错兔子洞。

虽然感知 patch 的提取器平均打开的文件略多一些（10.4 对 9.2），但这点探索量的增加是极小的代价。通过利用我们已生成的候选 rollout，我们几乎消除了 agent 完全「失明」的场景，确保最终选择阶段始终植根于正确的代码库上下文。

至此，我们手中已经有了一套经 SWE-rebench 成绩证实的提升 agent 准确率的可靠方法。

## 成本-质量权衡：驾驭帕累托前沿

到目前为止，我们一直专注于最大化 agent 质量。但在生产工程中，准确率不能在真空中评估——我们还必须关注算力成本。把推理预算当作可控变量，横向扩展和上下文富化让我们得以驾驭一条经典的**帕累托曲线**，明确地用可预测的开销换取质量提升。

为了给出参照，把各流水线变体放到一个现实的财务上限下衡量。我们取 SWE-rebench 排行榜上报告的 **Claude Code** 成本作为预算上限，目标是看在不超过该成本的前提下，这套架构究竟能做到多高的质量。

我们的实验揭示了沿成本-质量曲线一条高效清晰的演进路径：

- **打破效率壁垒：** 仅生成五个初始 rollout，再应用我们的感知 patch、源代码富化的上下文提取器，就在基线之上显著提升了 agent 质量——同时总执行成本仍从容地*低于*我们的参照上限。通过用已经付费的候选来引导上下文阶段，我们实现了有意义的质量提升，而 token 开销没有连锁爆炸。
- **榨干剩余预算：** 实现我们的方案后，我们发现以相当的准确率计，成本仍比 Claude Code 低约 $0.30。如何把这部分剩余预算进一步转化为准确率增益？于是我们引入了一个轻量 agent 层，专做自动化验证。这个专门的 Test Agent 会动态创建仓库测试，并过滤掉任何未通过测试的候选 patch，在进入最终选择阶段之前净化候选列表。

这套多阶段架构——横向扩展、用初始 patch 富化上下文、以轻量测试生成做过滤——把我们的最终成功率推到了 **60.9%**。这不仅控制在现实预算之内，还略超过了排行榜上报告的最先进成绩。

## 关键要点

- **执行策略本身就是一个超参数**。关键不仅在于你应用了哪些策略，还在于你以何种顺序组合它们——优化执行策略本身就是一个独立的杠杆。横向扩展和上下文富化各自已被独立证明有效；按正确的顺序一起应用——先扩展、后富化——就能在不增加任何算力成本的情况下把 agent 推远超出基线 ReAct 循环。
- **复用你已经付费的东西。** 如果你已经在为横向扩展付成本，就把这份资产的价值最大化。那些 rollout 不只是潜在答案，它们是极其丰富的数据点。
- **向「上下文步骤」注入上下文。** 把这些初始 rollout 传递给下游——无论传给源代码提取器还是 agent 架构中的任何其他步骤——都能让你的各步骤带着焦点工作，而不是盲目行事。
