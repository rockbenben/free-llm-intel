### 摘要（TL;DR）

**在为我们的编码 agent 做基准测试时，我们注意到 LLM 评审 judge——Maestro 中负责从并行 agent 运行里挑选最佳输出的组件——表现得好得可疑。数据污染（contamination）是头号嫌疑——但当我们在一份模型不可能见过的干净数据集上复现出同样的偏差时，我们意识到另有隐情：评审学会偏爱那些「看起来像 gold 答案」的解——极简、干净、聚焦——压过了真正能工作的输出。本文在基准数据上分离并量化了这种「类金」（gold-like）偏好的影响，并给出缓解其影响的策略，以维护编码基准结果的可信度。**

## 一个新的数据失真元凶

当 LLM 在公开基准上表现好得可疑时，元凶通常是数据污染。因此，当我们发现 reducer——一个从并行 agent 运行中挑选最佳 patch 的 LLM 评审——在 SWE-bench Verified 上对 gold 答案表现出明显偏爱时，我们自然而然地怀疑模型是在回忆数据集。两个月后 [OpenAI 宣布](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)他们也得出同样结论，进一步坐实了我们的疑虑：太多近期前沿模型都熟悉 SWE-bench Verified 数据集。SWE-bench 被宣告已受污染。

回到我们的实验室，我们在 [SWE-rebench](https://swe-rebench.com)——一个更新的、抗污染的——数据集上复现了实验；然而对 gold 答案的偏爱依然存在。这是一个巨大的警铃。

在这个案例中，LLM 评审并不是在记住具体解——但它*确实*在学习「类 gold」patch 的特质，例如最小性和清晰度。这些特质通常被视为优点，但在这里，它们造成了与我们成功标准的**错位**：模型把表面特质置于功能正确性之上，常常偏爱一个「干净的」错误解而舍弃一个「 messy（脏乱）的」正确解。事实证明，LLM 评审交付的是形式而非功能。

随着调查深入，我们发现这些看似「正面」的风格偏好，其扭曲程度可能不亚于显式的数据污染。为了解决它，我们重新设计了 reducer 的提示词，加入具体的优先级规则。经过几轮迭代，我们制定了足够细致的提示词准则，使模型的判断与我们的真实成功标准对齐。下文分享这段历程，供其他希望排查基准结果中污染与失真来源、构建更可靠编码 agent 性能度量的构建者参考。

## reducer 是什么？快速介绍

由于基于 LLM 的 agent 是非确定性的，同一查询多次运行会产生不同输出；只要运行足够多次，至少有一个很可能是正确的。难点在于识别哪一个是正确的。这就是 pass@k（k 次运行中至少一次答对的频率）与你实际拿到的分数之间的差距——后者完全取决于你挑出正确输出的能力。

在 Maestro——AI21 面向 agent 任务的编排元模型（meta model）框架——中，系统会启动多个 agent 并行处理问题，并选择最佳输出。最后一步由一个我们称为 reducer 的组件处理——本质上是一个选择器，它取回所有候选输出，并且希望在我们配置得当时，挑出最好的那个。

## 为 SWE-bench agent 构建 reducer

### SWE-bench 挑战

SWE-bench 是评估编码 agent 的一个流行基准。输入是一个 GitHub issue 和一个仓库的 Docker 镜像，期望输出是包含解决该 issue 所需改动的 Git patch。agent 的任务是探索仓库、理解 issue 并生成 patch。只要测试通过，patch 就被视为成功（不论其代码质量）。

SWE-bench agent 的一种常见做法是使用带单一工具的 ReAct 循环：一个 Docker 终端，让 agent 通过 bash 命令与仓库交互。我们首先在 Maestro 内实现该 agent 来收集一个输出 patch 数据集。我们用两个不同模型（GPT-5 mini 和 MiniMax-M2.1）生成 patch，并对每个样例运行多次以获得 pass@k 分数：

这些结果展示了一个优秀 SWE-bench reducer 的潜力：随着 *k* 增大分数不断提高，说明在每个实例上多次运行会返回「好」patch 与「坏」patch 的混合。如果我们有一个好的 reducer，只需多次运行同一 agent，依靠 reducer 挑选最佳候选，就能取得显著提升。

### 将 reducer 变体适配到 SWE-bench

基于我们对 [SWE-bench](https://www.ai21.com/blog/test-time-compute-swe-bench/) 基准的理解，如何实现一个最能支持 agent 输出正确 patch 的 reducer？以下是我们把上述三类 reducer 适配到 SWE-bench 场景的做法：

- **随机 reducer：** 由于 agent 常常结束时没做任何改动，输出空 patch 的情况并不罕见。在 SWE-bench 中，「弃权」没有额外加分，因此任何 reducer 都应先过滤掉空 patch 的候选。这一步让「随机」reducer 的分数自动高于 pass@1。
- **多数投票 reducer：** 由于这里的输出是 Git patch，定义「相同」输出并不简单。「完全匹配」过于严格，因此我们定义的匹配逻辑会忽略格式、注释和额外的测试代码。平均而言，由此得到的分数通常高于随机 reducer，但在更难的样例上可能反而低于随机 reducer。
- **LLM 评审：** 这类 reducer 可以有不同层次的复杂度和成本，取决于我们在上下文中包含哪些信息（例如只有 patch、完整 agent 轨迹、仓库代码等）。由于单看 patch 往往不足以做决定，patch reducer 常常暴露出 LLM 的固有偏差，这使它成为一个特别值得研究的 reducer。

因此，接下来我们只聚焦基于 LLM 的 patch reducer。

## reducer 实战：测试一个 SWE-bench patch reducer

我们首先实现了一个基础 patch reducer——对 Claude Opus 4.5 发起单次 LLM 调用，使用如下提示词：

```
You are given an issue from a GitHub repository and a set of proposed solutions (in the form of git patch candidates).
Please choose the patch with the highest chance of resolving the issue.
Your focus should be solely on the correctness of the patches, not on their code quality or style.
```

我们在「reducer 相关样例」（reducer-relevant examples）数据集上运行了这个 reducer（即并非所有候选都同为好或同为坏的样例，最终留下 400 个样例：234 个来自 GPT-5 mini，166 个来自 MiniMax-M2.1）。

从这些数字看，这个简单的三行提示词似乎已经在早期基线之上带来了提升。理论上很棒……但也引发了担忧。

## 污染现身

我们怀疑这一提升中至少有一部分可归因于众所周知的 SWE-bench 污染问题。我们评估所用的 400 个示例子集源自 2024 年 8 月发布的 SWEBench-Verified。而我们 reducer 使用的模型 Claude Opus 4.5 发布于 2025 年 11 月，知识截止日期为 2025 年 8 月。这条时间线意味着我们的实验可能被污染：模型掌握了本应隐藏的答案信息。这正是 OpenAI [博客文章](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified)（前文提及）所表达的观点，该文展示了近期 LLM 曾在基准的隐藏测试与 gold patch 上训练过的部分证据。

鉴于我们对污染的担忧，我们需要一种验证结果可信度的方法。

## 量化污染：一个实验

**初始假设：**

patch reducer 提升的相当一部分，可归因于它因 SWE-bench 污染而知道的 gold patch。

**实验：**

- 取上一节的 400 个 reducer 相关样例
- 把每个样例变成两个「正候选 + 负候选」配对样例：第一个样例：随机选择正、负候选。第二个样例：使用同一个负候选，但把正候选替换为 gold patch。
- 把样例收集为两个新的独立数据集：「positive vs. negative」和「gold vs. negative」。
- 在两个数据集上分别运行 patch reducer，检查准确率的差异。

**结果：**
reducer 在「gold vs. negative」上的准确率远高于「positive vs. negative」。

所以这就证明模型记住了 gold patch，对吧？

未必。要真正验证这一假设，我们需要确认这种现象不会发生在更近期、没有污染风险的数据集上。

### 在 SWE-rebench 上验证

[SWE-rebench](https://swe-rebench.com) 是一个相对新的数据集，与 SWE-bench 类似，但包含更近期的 GitHub issue，其中一些——关键在于——创建于 Claude Opus 4.5 截止日期*之后*。

我们取了 2025 年 8 月至 2026 年 2 月的 258 个 issue，在其上运行我们的 agent（同样使用 GPT-5 mini 和 MiniMax-M2.1）来为 reducer 构造样例。

最终得到 169 个 reducer 相关样例，并按前述方式转换为「positive vs. negative」和「gold vs. negative」数据集。

现在我们运行同一个实验，出人意料的是……得到了同样的差距。

### 金光闪闪，却并非真金：重新思考污染偏差

SWE-rebench 的实验结果意味着模型记住了 gold patch 吗？

大概没有。但模型很可能确实偏爱「类 gold」的解——金光闪闪却并非真金的解。换句话说，它可能不知道 gold patch 的*内容*，但它知道 gold patch 的一般*特征*。

例如，主要特征之一是最小性（minimality）。gold patch 通常不做任何无关的代码改动。然而如前所述，SWE-bench（以及 SWE-rebench）的成功标准全在于通过隐藏测试；并不要求代码最小化。一个编码 agent 可能把代码弄得乱七八糟，依然能拿到解决问题的分数。

### 但 gold 一定都闪光吗？

然而在 SWE-rebench 上运行时，生成的正 patch 与 gold patch 在改动数量上的差异对所有子集而言并不都那么显著；对 MiniMax-M2.1 生成的 patch，这个差距只有 7%。深入分析后我们发现，虽然多数情况下 gold patch 更短，但也存在 gold patch 反而更长的实例。gold patch 不是应该是对 issue 最简约的解吗？如何解释这种矛盾？

一种解释与文档有关。在运行 SWE-rebench 时我们发现，超过 20% 的 gold patch 包含文档文件更新（.md、.rst、changelog、示例、notebook），而我们的生成 patch 中完全没有这类内容（在 SWE-bench 的 gold patch 中也极少见）。

但即使剔除涉及文档文件改动的情况，我们仍观察到一些例子：正 patch 提供了更简约的改动，而 gold patch 似乎在满足原始 issue 未指明、测试也未评估的额外需求。它在技术上或许算 gold，却已失去了光泽。

为了度量这类「patch 冗余」对我们 reducer 的影响，我们计算了可归因于此因素的 reducer 错误率。我们把「冗余错误」定义为：一个正确 patch 被拒绝，且 reducer 的推理将其标注为 *redundant（冗余）*、*unnecessary（不必要）*、*unrelated（无关）* 或 *irrelevant（不相干）* 的任何样例。所得数据显示，这些错误在 positive-negative 样例中最常见，但在 gold-negative 数据集（包括 SWE-bench 子集）的失败中也占了相当比例。

到目前为止，我们的实验给出了证据：金光闪闪的不一定是 gold，有时连 gold 都不闪光。既然如此，我们怎样才能防止 reducer 被华丽的外表带偏？

## 回到（提示词）设计桌前

我们那简单的三行提示词是否足以让 reducer 在基线分数上取得显著提升？是的。但它是因为「正确的」原因吗？恐怕不是。

看来，如果我们想要一个能克服模型固有偏差、优先考虑 patch 正确性的 reducer，我们那句三行声明（"Your focus should be solely on the correctness.."）是不够的。我们必须提供一套远为详细的规则，明确针对 patch 的各种品质，并给出清晰的优先级路线图。于是我们的下一步就是用这样一套规则更新提示词，并重跑实验。结果毫不含糊：**positive-negative 与 gold-negative 之间的差距完全消失（对 SWE-bench）或大体消失（对 SWE-rebench）。**

你可以看看我们为达成这些结果所使用的详细提示词：

```
You are given an issue from a GitHub repository and a set of proposed solutions (in the form of git patch candidates).
Please choose the patch with the highest chance of resolving the issue.

EVALUATION PRIORITIES (in order):

1. CORRECTNESS & COMPLETENESS (most important)
   - The fix must COMPLETELY solve the issue — partial fixes are wrong even if they look clean.
   - If the issue implies multiple affected code paths (e.g., serialize AND deserialize, multiple backends), ALL must be fixed.
   - A multi-file fix that's complete is better than a single-file fix that's incomplete.
   - A candidate may resolve the issue even if it makes some redundant changes. DON'T disqualify a candidate just because it makes redundant changes.
   - A messy-looking fix is better than a clean-looking fix that doesn't solve the issue.
   - Mentally trace the failing case with the fix applied — does it actually work now?

2. REGRESSION SAFETY
   - Ideally every change should directly serve the fix. But don't disqualify a candidate for redundant changes if the fix is still correct.
   - Watch for: changed method signatures other code depends on, removed fallbacks, changed return types.

3. MINIMALITY (tiebreaker only)
   - Only consider minimality after correctness and completeness are established. 
   - Adding tests, docs, or helper functions should not affect your selection.

COMPARISON TIPS:
- If multiple candidates make the same core fix — differentiate on errors or edge-case coverage, not on style or readability.
- Ignore differences in test files, comments, formatting, or variable naming.
```

## 结语：实验的关键要点

- 在流行基准上好得可疑的表现并不一定意味着数据泄漏；它也可能是对正确解风格「指纹」的归纳偏差。
- 当你的任务恰好与这种偏差同向时，一个简单的提示词可能就够了。但当正确的解「看起来」不符合模型预期时，你需要详细的规则来强制把判断重新对齐到你的成功标准上。

具体到 SWE agent，这个实验强调：仅度量功能正确性可能提供的信息还不够。展望未来，我们或许需要增加新的指标来度量最小性、清晰度等非功能品质。
