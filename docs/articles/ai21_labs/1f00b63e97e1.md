## 简要说明

作为我们在 agent 优化上的更大主题的一部分，我们发布了一项[展示水平与垂直扩展策略同样有效](https://www.ai21.com/blog/maestro-deep-research-agents/)的研究，对象是 SWE agent。但在我们的实验里，传统做法是对所有问题施加统一的算力预算，仿佛每个**任务**都**难度相同**。

而在受控实验室之外，这个假设站不住。

现实中我们知道：**任务难度服从重尾分布**——相当一部分任务低投入即可解决，而另一些需要很大预算。例如，在[此前详述我们如何在 SWE-rebench 上取得 SOTA 的文章](https://www.ai21.com/blog/first-scale-then-enrich-how-the-right-execution-strategy-helped-us-reach-state-of-the-art-on-swe-rebench/)中我们发现：该 benchmark 采样出的任务约 50% 用 GPT-5.2 的一次 rollout 就能解决，而我们原来的策略对每一个都跑五次 rollout。这就是白白流失的金钱。

在如此多公司审视自己的 token 消耗、寻找削减成本之道的当下，我们带来最新研究：**可根据任务难度自适应的预算感知执行策略**——只在需要时多花钱。延续我们在 SWE-rebench 上的工作，我们展示级联（cascading）与并行执行策略配合提前停止如何让你按需优化成本或速度、同时保持质量：级联省下最后一次 rollout 的成本，并行执行则免除等待最后一次 rollout 的时间——如下图示意。本文介绍我们如何设计这些执行策略，以及取得的成果。

## **总览：我们现有的 SWE 多 agent 架构**

在深入这些执行策略之前，先回顾我们使用的 agent 架构（见下图）。完整概述在我们此前那篇[选对 SWE agent 执行策略如何帮我们在 SWE-rebench 上达成 SOTA](https://www.ai21.com/blog/first-scale-then-enrich-how-the-right-execution-strategy-helped-us-reach-state-of-the-art-on-swe-rebench/)的文章里，这里只说基础：

- **并行生成：**每个查询，agent 并行生成 *N* 个候选补丁（rollouts），每条 rollout 的最后一步包含一个自我置信分数。同时，一个测试 agent 编写并收集一个正确补丁应当通过的测试。
- **过滤：**任何未通过所收集测试的候选被淘汰。
- **抽取：**抽取与剩余候选相关的仓库源代码。
- **归约（Reduce）：**Agent 从经过过滤、上下文富化的池中选出唯一的最终候选。

由于 rollout 生成既是主要成本又可并行化，它是我们在本工作中实验的首要杠杆——通过控制 rollout 的数量与执行顺序。

## **为 SWE agent 任务改造 best-of-N 执行策略**

在 BrowseComp-Plus 和 DeepResearch-Bench 等 benchmark 上，我们[已经探索过不同的执行策略](https://www.ai21.com/blog/maestro-deep-research-agents/)，利用 agent 的自我置信来决定在每个任务上投入多少算力，包括：

- **带提前停止的级联（成本优化）：**从便宜模型开始，只有失败或置信度低时才升级到更贵的模型；廉价处理简单查询省下的成本，抵消了长尾难题上的昂贵模型开销。
- **带提前停止的并行执行（延迟优化）：**一次性发射所有 rollout；一旦确认某个可接受的候选，任何仍在进行的 rollout 立刻终止。这样不为永远不会用到的补全付费，在早早被自信解决的查询上尤其如此。

在上述执行策略中，我们假设每个候选解可以被独立评估。但正如我们在[上一篇关于 SWE-rebench 的研究](https://www.ai21.com/blog/first-scale-then-enrich-how-the-right-execution-strategy-helped-us-reach-state-of-the-art-on-swe-rebench/)中发现的：仅凭单独候选的自我置信分数来做选择，明显不如使用 LLM Judge（也就是**选择器，selector**）。选择器不是分析单个候选，而是在做最终决定之前，**审视生成的整个候选池**以及相关源代码。

**因为选择器依赖这种全局视野，我们必须调整方法。**我们不能再简单地问"*这个单独的解够不够好、可以提前停止吗？*"相反，我们的接受标准必须转向群体动态："*我们是否已拥有足够好的候选池，让选择器能够有效工作？*"

## **预测选择器的表现**

这一转变改变了我们验证管道的方式。因为选择器从集体池中做出最终选择或综合，我们需要一种方法自信地预测：这个池是否包含足够的信号，让选择器产出好结果（唯一例外是列表里只有一个候选——那种情况根本不需要选择器）。

我们发现需要两个预测来支撑对选择器能力的总体预测：

- **预测 #1：对候选列表运行选择器将解决该任务。**我们称之为 Resolve-Now（RN），由一个为此目的训练的专用分类器计算——带校准阈值 p_target（p 代表 precision，精确率）。
- **预测 #2：生成更多候选、再运行选择器将解决该任务。**我们称之为 **Resolve-Later（RL）**。我们训练另一个分类器来预测"选择器在更大批次候选上运行时解决任务的概率"，再减去 Resolve-Now，得到再生成一批 rollout 的边际收益估计。同样为它学习一个校准阈值 *g*（g 代表 *gain*，收益）。

只要 *p_target* 或 *g* 越过我们的阈值，我们就把它当作"此刻候选池已经足够好"的信号。是的话就停止生成更多 rollout，继续走管道。重要的是，*p_target* 和 *g* 是我们可以按自己的标准把玩的参数：例如提高 *p_target* 的阈值或降低 *g* 的阈值，会让提前停止更少发生、但更安全（更贵，却更准）。

## **生成更多信号**

然而我们发现，**自我置信并不是足够强的信号**来决定何时提前停止一个 SWE 任务。我们需要生成更多特征，让分类器能更有底气地做出提前停止的判断。以下是我们构造的部分特征：

- **测试 agent：**如前所述，它在并行生成阶段同时运行，编写并收集补丁应通过的测试、并对每个候选执行。它由更小更便宜的模型驱动（此处为 GPT-5-Mini），其输出——通过了多少测试、多少候选通过了全部测试——干净利落、易于聚合，比多跑一次 rollout 便宜得多。
- **补丁一致性：**各 rollout 生成的 git patch 之间的差异。
- **仓库搜索一致性：**各 rollout 在仓库中搜索路径的变化与覆盖度。
- **其他元数据：**agent 所执行的步数、工具错误率等元数据。

然后把它们汇编成特征向量喂给分类器，用于预测 RN 和 RL。这组特征中最强的是自我置信和基于测试的特征；但即便如此它们仍属平平——因为预测一个 SWE 补丁是否正确，本身就是真正的难题。

好在，做出成功的停止决策并不需要完美分类器——我们只需要一个[校准良好的尾部](https://scikit-learn.org/stable/modules/calibration.html)。

## **结果**

### **第一部分：带提前停止的级联（成本优化）**

把上述级联策略适配到 SWE agent 场景，我们执行了以下步骤：

- 预定义一串 *N* 值（例如 [1, 3, 5]）。
- 跑 *N=1* 的一次 rollout 并等待完成。
- 评估我们的 RN 和 RL 分类器，决定停止还是生成更多运行。
- 如果分类器没有足够把握停下来，我们就发射更多 rollout 达到下一个 *N* 值（*N=3*），再次评估分类器决定是否停止。
- 如此"级联"，直到停止或触及兜底的最大 *N*——本例中是 5。

把级联执行策略应用于我们的 SWE agent，*N* 值取 [1, 3, 5, 10]，我们看到超过 50% 的任务被提前停止，只花了全部预算的一小部分：

我们在与前次同一 SWE-rebench 数据集切片（2025 年 12 月-2026 年 3 月，123 个 issue，从中采样出训练集和测试集）上评估结果，把每种策略与"始终跑满最大 *N*"的基线对比。

**调节 RN 与 RL 的阈值会描出一条 Pareto 前沿**，每个点代表成本、延迟与质量之间的一种权衡。从训练集学到的最优配置（图中菱形标记）在测试集上表现并非完美，但展示了扎实的泛化（同等质量、比基线更便宜），留下轻微的泛化差距：与菱形同等 resolve 率的点落在其左侧，意味着存在同样质量、成本与延迟更低的配置。

因此，一方面收益明确：我们在削减至多 44% 算力的同时保持了完全相同的质量。另一方面有个代价：级联用延迟换成本。由于各阶段顺序执行，**错过一次提前停止意味着等待一整波新 rollout 从头跑到尾**。相比一次性并行发射全部 *N* 个 rollout，这引入了 20% 到 41% 的延迟溢价。

此外，为追求极限成本节约而增加更多阶段，会让总体 resolve 率轻微下滑（-0.6%）——既因为 *N* 增大时我们的分类器变弱，也因为顺序步骤越多，误报触发错误提前停止的累积概率自然上升。

**归根结底，级联是我们最偏向成本的选项：它是最便宜的策略，但比基线跑得慢。**

### **第二部分：带提前停止的并行执行（延迟优化）**

如果你承担不起延迟溢价，可以用并行执行加提前停止，把完全相同的停止决策换一种方式落地。

我们不在阶段之间等待，而是一开始就并行发射全部最大 *N* 的 rollout。随着 rollout 完成并到达指定阶段阈值，我们对已完成的候选运行同样的 RN/RL 分类器。停止信号一经触发，立刻终止所有仍在活动的 rollout，削减成本。

这从两个方面改变了性能画像，而底层分类器、阈值和 resolve 结果完全不变：

- **延迟下降而非上升：**最慢的 rollout 恰恰是被我们提前终止的那些。不必等待掉队者，执行在满足停止标准的那一刻结束。
- **成本节约幅度较小：**被终止的 rollout 在被击杀前仍消耗了一些算力（按运行时长比例计费）。你拿出一部分成本节约买回速度。

也就是说，两个轴向都在改善——并行执行严格优于标准的"全部发射然后傻等"。注意：增加更多阶段会扩大延迟收益，但伴随约 -2% 的小型质量折衷。

## **告别统一预算的理由**

两种方法——带提前停止的级联与并行执行——都描出一条固定质量下的 Pareto 前沿，可根据想要的成本或延迟定制。在固定质量 *N=3* 下（下图），权衡清晰可见；同样的原则在 *N* 扩展到 5 或 10 时依然成立。

图表一目了然：**统一的算力预算严格次优。**但击败基线要求对我们此前的 benchmark 策略做彻底重构。因为 SWE 任务独特地复杂，原始的自我置信并不是支撑提前停止决策的足够强信号。

我们把重心转向预测下游选择器的表现，并工程化出一整套丰富的特征。这最终解锁了我们所需的精确信号，用来调整执行策略、成功超越基线。

## **要点**

这项工程工作的回报，是一个可以在任务质量几乎不降的前提下管理成本-延迟权衡的旋钮：

- **带提前停止的级联最大化节约**：由于顺序阶段牺牲墙钟时间，算力成本最多砍掉 44%。
- **带提前停止的并行执行最大化速度**：通过中途击杀表现不佳的 rollout，比基线提速最多 25%。

对构建者来说，这意味着你不必再死守僵化的一刀切执行预算——在保持卓越 agent 质量的同时，获得按成本或速度优化的更大自由度。
