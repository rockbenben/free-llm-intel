> TL;DR：在对 agentic 工作流做实验时——尤其是有多个并行 LLM 调用的 agent——缓存会因为 LLM 的非确定性而失效。这些工作流需要的是一种同时支持两种矛盾行为的缓存机制：可复现性与方差。我们设计了一种把每次 LLM 调用在管道中的位置编码进缓存 key 的方案，使其不受管道执行顺序变化的影响。结果是更干净、更广泛的实验：你可以只改一个 prompt 而复用其余的缓存结果；可以在完全相同的上游输出上对任意组件做 A/B 测试；还可以运行 best-of-N 推理，而不会让多条分支坍缩到同一个答案。

## 非确定性世界里的缓存

不用我们提醒，你也知道由于一些核心特性，agent 很难评估。它们是：

- **复杂**（许多流程，而且常常并行）
- **动态**（其行动路线由 LLM 临场决定）
- **长时运行**（一次会话可能耗时几分钟甚至几小时）
- **昂贵**

于是，缓存成了管理评估实验的惯用手段。

但问题就在这里（抱歉）：

缓存是为确定性世界打造的——同样的输入，同样的输出，次次如此。作为非确定性实体，LLM 不守这些规则。你用同样的 prompt 调用同样的模型，其实**期待**得到不同的结果——你甚至可以用 temperature 来控制差异的程度。

然而我们工程工具箱里的大多数构件，都内嵌着那个确定性假设。当你不假思索地把这些构件套用在 LLM 上时，**东西会坏掉，而且一开始看起来并不像坏了。**

这正是我们研究实验室里发生的事。我们的算法开发者——当时正在跑 agent 评估——开始报告"缓存坏了"。当我们的软件工程团队前去排查后，我们意识到缺失的是一种能在每次 agent 评估运行中同时保证可复现性*和*方差的缓存机制。于是我们把它造了出来。本篇博客详述了从问题到方案的这条路。

## 复现方差：定义问题

在实验室里构建和测试 agent 时，我们使用 Maestro 在运行时对其优化。在推理时，Maestro 可以利用 **best-of-N 采样**：对同一任务生成 *N* 次独立尝试并返回最好的一个，从而让 agent 输出的准确性不被任何单次 LLM 调用的噪声拖低。除了提升 agent 准确性，这一方法对生成 agent 表现的指示指标也发挥了关键作用，比如方差估计和 *Success@K* 指标——正如我们在[此前关于如何登顶 SWE-bench 排行榜的文章](https://www.ai21.com/blog/scaling-agentic-evaluation-swe-bench/)中展示的。

所以当我们开始收到"缓存坏了！！"这样的消息时，情况令人担忧。细看之后，问题比这更微妙：研究人员期待缓存提供可复现性——但由于 LLM 的非确定性本质，重新运行同一个 agent 会重新计算——却不会复现——结果。于是我们看到了这样的情况：

重新运行一个实验时，期望未改动的 prompt 命中缓存（cache hits）、实验快速跑完——结果却得到不同的答案（缓存未命中）。

为 success@K 运行实验时期望出现方差（缓存未命中），结果却得到相同的答案（缓存命中）。

我们的研究人员需要的是一种在同一管道内支持两种不同缓存行为——可复现性与方差——的机制，能选择性地决定何时复用结果、何时重新计算。如果能做到这一点，我们就能解锁如何*复现*一次 best-of-N 运行。

## 画出相互矛盾的缓存行为

要复现一次 best-of-N 的 agent 运行，最理想的是我们能直接开/关可复现性。

可复现性可以在最简单的缓存行为示例中体现：两次相同 prompt 的 LLM 调用——把缓存开关打到 **on** 就能做到。

## 设计缓存 key

此时已经清楚：简单的开/关切换不足以实现**复现方差**这种微妙组合。我们需要利用 LLM API 的设置/参数来设计一个缓存 key——附着在 LLM 调用上、决定哪些调用共享结果、哪些不共享的字符串——使其能满足那些相互矛盾的条件。

缓存 key 之所以关键，是因为除了一个可用的可复现性开/关切换之外，它是我们所剩的唯一能影响缓存行为的杠杆。

两个核心假设塑造了我们的方案设计：

- 我们可以为每次 LLM 调用附加一个**缓存 key**
- 缓存**命中**要求 prompt **和**缓存 key 同时匹配

在这个过程中，我们把"给我写一首诗"的 LLM 调用称为"generation"步骤，把"<诗>是一首合格的俳句吗"称为"validation"步骤。

### **尝试 1：用步骤名做缓存 key**

如果把缓存 key 设为直接使用步骤名，三个 Generate 分支就能共享同一个 key。于是复现时，Generate₂ 会命中 Generate₁ 的缓存结果，依此类推。三个分支，一个答案。这说明我们的缓存 key 不够具体：我们需要某种方式区分这三个不同的 Generate 调用。

### **尝试 2：步骤名 + 计数器**

让调用易于区分的一个自然修法：每个调用完成时就编一个号。第 1 次运行完美——每个生成分支都拿到一个编号。下一次运行我们可以复用 gen_0、gen_1、gen_2 这些 key 来复现这种方差。

缓存总是吐出最先完成的那个 key。但完成顺序是不可预测的，因此我们需要一个与该顺序无关的缓存 key，让 prompt-响应的配对无论各 prompt 以什么顺序完成都能保持不变。

### **解法：编码图上的位置，而非执行顺序**

突破来自于我们意识到：缓存 key 必须像 prompt 编码组合关系那样去编码组合关系。agent 循环中每个点的缓存 key 编码它*位于*流程何处：哪个步骤、哪个分支（run index）、消费了哪些上游输出。

现在，当编码这种位置信息后，我们看到 gen_0、gen_1 变得彼此不同：两个不同的 LLM 调用，两个不同的结果。而复现时，key val(gen_0) 匹配到包含诗 1 的 prompt，**与完成顺序无关**。由于 validate 和 fix 的缓存 key 继承其上游身份，整条分支保持正确接线。我们终于逼近了最初设想的那张图——复现一次 best-of-N 运行应有的样子。

### **再加一层：嵌套的 fan-out**

此前我们看的是每个生成分支只产生一个后续验证步骤的情形。但如果每个生成分支并行"扇出"到多个验证步骤呢？我们需要一种方式按顺序复现那种行为，同时保留前面各次尝试中关于时序与位置编码吸取的所有教训。

为此，key 的索引必须保持局部——限定在其直接上游父节点的作用域内，而不是全局计数器。

## 兼顾可复现性与方差的缓存 key：经验教训

### 缓存 key 的构造规则

通过上述尝试，我们可以归纳出三条构造缓存 key 的规则，以支持 best-of-N、可复现性和嵌套 fan-out：

**规则 01：每个节点的 key 应包含其步骤名**
两个不同的步骤（Generate 与 Validate）绝不能相互碰撞。

**规则 02：每个节点的 key 包含一个 run index，且局部限定在其直接上游父节点内**
同一步骤的两个"fan-out"（并行）分支应被分配不同的索引（gen_0、gen_1）。索引由图结构决定，绝不由执行顺序决定。

**规则 03：每个节点的 key 包含其上游依赖的 key**
val_0(gen_0) 与 val_0(gen_1) 是不同的 key，因为它们继承的父节点不同。这是递归的：任何节点的 key 编码了从图根出发的完整路径。

实际实现中，代码量很小。每个步骤构造自己的 key 并传给 LLM 服务商，由其负责缓存的查找与存储：

```
def run_step(step_name, run_index, upstreams, prompt):
    if upstreams:
        parent_keys = ",".join(u.cache_key for u in upstreams)
        cache_key = f"{step_name}_{run_index}({parent_keys})"
    else:
        cache_key = f"{step_name}_{run_index}"

    result = llm_call(prompt, cache_key=cache_key)
    return Output(value=result, cache_key=cache_key)
```

### 缓存 key 的命名

我们刚刚构造的这种缓存 key，当然可以按需添加任意多的前缀和后缀。在我们的场景里，我们想把实验名作为种子加进 key：

JavaScript

```
experiment_v3::gen_0
experiment_v3::val_0(gen_0)
experiment_v3::fix_0(val_0(gen_0))
```

记住：缓存命中需要 key 和 prompt 同时匹配。通过设计这样的缓存 key，你可以同时改动实验名（控制 key）和组件的代码（控制 prompt），从而构造出我们所需的各种组合。例如，用不同的实验名，就能把完全相同的整条管道重新计算 *N* 次。反过来，如果我们在已跑过的实验中发现了 bug，只需修改一个组件，其余所有先前的计算都从缓存取回，节省宝贵的时间和金钱。

掌握实验名和组件代码这两个控制点之后，我们可以构造三种场景：

**1. 复现。用完全相同的参数再跑一次实验：**

**2. A/B 测试。再跑一次实验，但只替换其中一个步骤的内容：**
这种测试可以带来：

- Generate 命中——相同的 key、相同的 prompt。
- Validate 未命中——相同的 key，但 prompt 不同。
- Fix 未命中——相同的 key，但其输入变了。

**3. 全新运行。更换实验名：**

在这个场景中，所有 key 都变了，因此没有任何匹配，每个步骤都会重新计算。

## 缓存 key 设计：对 agent 评估的影响

有了这些设计模式，改动一个 prompt 意味着只有从该点之后的 LLM 调用才会真正运行，之前的 LLM 调用都会从缓存加载。

这意味着：

- 你可以在完全相同的上游输出上对任意组件做 A/B 测试
- Best-of-N 给你的是 *N* 条真正独立的分支，而不是同一缓存结果的 *N* 份拷贝
- 每一个命中缓存的步骤都是一次你不必付费的 LLM 调用；在规模化之下，这意味着把实验从"需要精打细算"变成"日常循环的一部分"

缓存是让我们让 agentic 工作流变得快速、可复现、迭代便宜的最强大工具之一。但 LLM 的非确定性本质打破了传统缓存赖以成立的假设，所以弥合这一缺口靠的绝不是一个简单的 key-value 存储。它需要的是一种刻意的、尊重这些系统核心处非确定性的设计。
