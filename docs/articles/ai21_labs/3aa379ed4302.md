摘要（TL;DR）

Padding 是训练 LLM 时算力浪费的一个重要来源。对于 Transformer-SSM 混合模型，这仍是一个难题——sequence packing 之类的方法在那些架构上不易应用。我们通过一种与模型无关的方法——利用 micro-batch 级截断与 padding 感知的 micro-batching——消除了约 90% 与 padding 相关的开销。这种方法为现有和未来的模型架构提供了一个简单、广泛适用的替代方案，显著提升训练效率。

## 应对 online-RL 训练中的低效

训练效率是大规模模型开发的关键关切，既影响算力使用，也影响墙钟时间，最终影响成本。这些权衡在 online-RL 训练中尤为突出：训练运行长生命周期且算力密集，使低效迅速复利放大。

过去几个月，我们的 *Labs in Front* 系列探讨了提升 online-RL 训练流水线效率的多个方向，包括同事们的[通过动态数据 snoozing 提升数据效率](https://www.ai21.com/blog/dynamic-data-snoozing/)的工作（主要优化 rollout 生成阶段），以及[高效扩展多节点 judge LLM 部署](https://www.ai21.com/blog/scaling-vllm-without-oom/)的努力（针对奖励计算阶段）。这些工作共同体现了在整个训练流程各阶段减少浪费、提升利用率的更广泛推进。

本文聚焦训练流程中的策略更新（policy update）阶段，它涵盖 reference 前向传播和训练的前向-反向传播。我们对这一阶段的关注，与本系列此前关于推理和奖励计算的工作形成互补。我们识别出策略更新阶段内与 padding 相关的浪费是低效的重要来源，并展示如何以与模型无关的方式缓解它。

### 为 Transformer 打造的训练系统遇上其他架构

现代 LLM 训练栈大多围绕 transformer 模型构建，许多高影响力的效率优化就是专门为 transformer 工作负载实现的。与此同时，非 transformer 与混合架构在实践中日益常见，其动机往往是解决标准 transformer 已知的低效与局限。例子包括：[Qwen3-next（DeltaNet）](https://qwen.ai/blog?id=4074cca80393150c248e508aa62983f9cb7d27cd&from=research.latest-advancements-list)、[Nemotron（Mamba2）](https://developer.nvidia.com/blog/inside-nvidia-nemotron-3-techniques-tools-and-data-that-make-it-efficient-and-accurate/)、[Granite（Mamba2）](https://www.ibm.com/new/announcements/ibm-granite-4-0-hyper-efficient-high-performance-hybrid-models)，以及我们自己的 [Jamba 模型（Mamba）](https://arxiv.org/abs/2403.19887)。随着这些架构获得采用，一些缺口随之浮现：transformer 专属的优化不再适用，先前隐藏的低效来源暴露出来。

我们以训练 [**Jamba2-3B**](https://www.ai21.com/blog/introducing-jamba2/)——我们交替堆叠 attention 层与 Mamba 状态空间层的混合架构——来说明这一场景，使用的框架是 [**VeRL**](https://github.com/verl-project/verl)，一个流行的 LLM online-RL 训练框架。VeRL 继承了许多以 transformer 为中心的设计选择，这在训练 Jamba 这类混合架构时会清晰地暴露出来。

在这一场景中最显著的缺失优化之一，就是对 padding 的高效处理。padding 即添加虚拟 token 使变长序列适配固定张量形状，它可能成为算力浪费的重大来源。

## 处理 padding 浪费

训练批次通常包含长度差异极大的序列，处理方式是把批次内所有序列通过添加虚拟 token pad 到同一长度。虽然 padding 让批处理成为可能，但这些 token 不携带任何信息，却仍被模型处理，消耗算力与内存而不产生有效工作。先前对常见 NLP 数据集的分析表明，在标准的定长批处理下，padding 可占到所有被处理 token 的约 50%，在某些现实场景中甚至更高（[Krell et al., 2021](https://arxiv.org/abs/2107.02027)）。

在 RL 训练中，这一低效被模型生成响应长度的波动进一步放大——即使是相似的 prompt，长度也可能相差很大。结果是，padding 相关的浪费影响策略更新步骤的多个阶段，最显著的是 reference 前向传播和训练的前向-反向传播。由于这些阶段占整体步骤时间的很大比例，过度的 padding 会成为训练效率的瓶颈。

*定长 micro-batch 中的 padding 浪费。一个 pad 到固定最大序列长度（如此处所示的 8 个 token）的 micro-batch 包含真实 token 后跟 padding token。在这个例子中，40 个 token 里有 16 个（40%）是 padding，意味着相当一部分计算和内存花在了不携带信息的 token 上。*

### 消除 transformer 训练中的 padding：sequence packing

对于 transformer 训练，经典解法是 sequence packing：把多条变长序列拼接成一条更长的序列，彻底消除 padding 需求。Transformer 将 token 级层（如 MLP 和归一化层）与 attention 层交替编排。token 级层对每个 token 独立运算，因此无需任何特殊处理即可处理打包序列。

但 attention 层会在序列中的位置之间混合信息。在许多预训练和 SFT 流水线中，不做显式序列边界强制的朴素打包在实践中往往可行，因为模型学会了把特殊的序列起止 token 当作软分隔符。Online-RL 对推理-训练不一致更敏感：rollout 时与训练时条件化的差异会引入不稳定性。因此，必须强制序列边界，使一条序列中的 token 不会注意到另一条序列的 token。

现代 attention 实现通过尊重序列边界、避免跨序列 attention 来支持这一点。关键在于，这不是朴素掩码——朴素掩码仍会对整条拼接序列付出二次方计算。取而代之，高效实现直接利用序列边界来限制 attention 计算，使 token 只在其原始序列内做注意。

*Sequence packing 通过拼接消除 padding。多条变长序列被拼接成单条稠密序列，完全避免 padding。高效 attention 实现尊重序列边界，使 token 只在其原始序列内互相注意，从而在消除 padding 的同时避免不必要的 attention 计算。*

### Sequence packing 超越 transformer 之外

Sequence packing 是一项需要**显式、架构专属支持**的优化。Transformer 受益于能高效处理打包序列的成熟实现，但那是大量专门工程的结果，而不是序列模型的普遍属性。

同样的要求也适用于其他类别的序列模型，包括状态空间与混合架构。支持沿序列维度拼接多条独立序列，需要每个架构各自实现正确且高效的序列边界处理。缺少这种支持，sequence packing 就无法直接应用。

Mamba 是这一更广模式的一个具体例子。虽然已有研究工作探索为 Mamba 添加打包支持（例如 *PackMamba: Efficient Processing of Variable-Length Sequences in Mamba Training*；Xu et al., 2024），但这样做需要不小的改动和仔细验证。从训练基础设施角度看，这会增加实现复杂度、扩大正确性风险面，并把训练栈与特定架构紧密耦合。

这促使我们发问：能否在不依赖对模型计算做架构专属改动的前提下，消除大部分与 padding 相关的低效？

## 另一个角度：在模型之外减少 padding

我们没有问「如何让模型支持打包序列」，而是问了这个问题：

*在张量到达模型之前，我们能消除多少 padding？*

这不是 sequence packing 的替代品，也不是说 kernel 级优化不重要。它代表设计空间中的另一个位置——强调改动小、风险低、迭代快、适用广。

在实践中，这意味着做少量针对性改动。概括来说，我们：

- 截断每个 micro-batch 中多余的 padding。
- 重新排列 micro-batch，以支持进一步的 padding 截断。

这些改动只涉及 padding token 以及序列如何分组进 micro-batch。由于 micro-batch 纯粹用于内存管理、梯度在其上累积形成有效训练批次，我们可以自由改变这种分组。所有非 padding token 上的输出保持完全一致（通过直接输出比对验证），用该方法训练的模型达到与标准 padding 相同的下游质量。

下文各节说明其工作原理以及在实际中带来的收益。

## 多余 padding 截断

默认情况下，VeRL 将序列 pad 到由训练配置决定的固定最大长度。这个最大值由最大 prompt 长度与最大响应长度构成：前者实际上控制哪些 prompt 被允许进入训练（更长的 prompt 被过滤掉），后者限制模型允许生成的 token 数。由于大多数 prompt 和响应都显著短于这些配置上限，这种 padding 方案常造成大量不必要的 padding。在 prompt 与响应长度异构的混合数据集上训练时，这种效应尤为明显。我们先从给定的一个 micro-batch 出发，尽可能消除其中的 padding。

我们用 **micro-batch 级截断**来解决。我们识别张量边界处连续的 padding 块，并截断张量将其移除。

为了让截断尽可能有效，我们先处理一个实际细节：**VeRL 的双侧 padding**。Prompt 做左 padding、补全做右 padding，这使 padding 分散在序列两端。当 padding 这样被分开时，截断只能从每一侧分别移除 padding，限制了总共能消除的 padding 量。

为了解决这一点，在截断之前，我们把左 padding 移到右侧，使所有 padding 连续地聚在序列末尾（实现为一次张量 roll，并相应调整 attention mask 与 position ID）。这一步纯粹是张量重排，但它让截断能移除更多 padding。

*Micro-batch 级 padding 截断。序列最初被 pad 到固定最大长度。左 padding 被平移至右侧使 padding 连续，随后通过把 micro-batch 张量截断到 micro-batch 内的最大序列长度来移除 padding。*

### 阶段性结果

**实验设置：** 我们在一系列训练配置上评估了这一方法，包括更复杂的多数据集场景。为聚焦呈现，我们报告在 GSM8K 上的标准单数据集 online-RL 配置的结果，运行于单个 H100 节点（8 块 GPU）。我们使用 batch size 32、最大 prompt 长度 4k token、最大响应长度 8k token。所报数字为连续 10 个步骤的平均策略更新步骤时间（取整到最近秒），分别给出 Qwen2.5-7B-Base 和 Jamba2-3B 的结果。

**结果**：应用 **padding 截断**后，包含 reference 前向传播和训练前向-反向传播的策略更新步骤时间显著下降：

- **Jamba2-3B**：45s → 20s（约 56% 降幅）
- **Qwen2.5-7B**：63s → 22s（约 65% 降幅）

*Micro-batch 级 padding 截断对策略更新步骤时间的影响：应用前后策略更新步骤时间的对比。*

**分析：** 如此幅度加速的原因在于长度分布的长尾，以及现实多数据集训练中必须容纳罕见的长样例。虽然这个特定数据集可以用更小的配置上限，但现实的混合数据集场景需要容纳这类长尾样例。在这个 GSM8K 配置中，prompt 通常只有几百 token（常约 200），却被 pad 到 4k 上限；响应通常约 500–1000 token，罕见离群值可达 6–8k。因此许多 micro-batch 包含大量 padding，而截断移除了其中很大比例的 padding token——尤其在合并左 padding 之后——带来了我们观察到的大幅提升。

尽管取得了这些大收益，相对 sequence packing（Qwen 为 16s，Jamba 为 14s）仍有明显差距。原因在于 **micro-batch 内部的长度方差**：较短的序列仍被迫与其被分到的组里最长的序列对齐，留下截断单独无法消除的可观 padding。

这引出了一个自然的问题：能否通过更聪明地把序列分组进 micro-batch，以架构无关的方式进一步缩小这个差距？

## Padding 感知的动态 micro-batching

即便截断很激进，padding 浪费仍高度取决于序列如何分组。在一个 micro-batch 中，所有序列都要 pad 到与最长序列一致，迫使较短序列做不必要的工作。

为解决这一点，我们引入 **padding 感知的动态 micro-batching**：我们按长度对序列排序，并按该顺序增量构建 micro-batch。在把一个序列加入正在构建的 micro-batch 之前，我们先计算截断后的 micro-batch token 数——即所有序列 pad 到当前 micro-batch 中最长序列长度后的总量——若加入该序列会超出 token 预算，就开启一个新的 micro-batch。

这一方法达成两个目标。第一，通过把长度相近的序列分在一组，它减少了必需的 padding 量，并使更激进的截断成为可能。第二，通过强制固定 token 预算，它让各 micro-batch 之间的计算与内存用量可预测。结果是，各 micro-batch 可能包含不同数量的序列，但总 token 数相近——相比序列数，这是计算与内存用量好得多的代理指标。

*Padding 感知的动态 micro-batching。标准 micro-batching 可能把极短和极长的序列分到一组，迫使组内所有序列对齐最长者。Padding 感知的动态 micro-batching 在固定 token 预算下把长度相近的序列分组，降低组内方差并支持更激进的 padding 截断。*

### Padding 感知动态 micro-batching 的影响

在截断之上加入 **padding 感知动态 micro-batching**，策略更新步骤时间进一步降至：

- **Jamba2-3B**：20s → 14s（额外约 30% 降幅）
- **Qwen2.5-7B**：22s → 16s（额外约 27% 降幅）

*Padding 感知 micro-batching 对策略更新步骤时间的影响：仅使用 micro-batch 级 padding 截断，以及截断加上 padding 感知 micro-batching 时的策略更新步骤时间。*

现在可以拉远视角，把最终配置 **外部 padding 最小化（external padding minimization）** 与 **sequence packing** 做比较。

对于非 transformer 和混合模型（如 Jamba），通常不支持对打包序列的正确高效处理。在没有架构专属支持的情况下把打包序列喂给这些模型，会导致序列之间的信息泄漏并使训练失效。尽管如此，仍可运行这类配置并测量所得步骤时间。因此我们把 sequence packing 的结果仅作为时间参考来报告——它表示假如 padding 被彻底消除时可达到的步骤时间——而不是一个可用或正确的训练配置。

*与 sequence packing 的比较：默认批处理、外部 padding 最小化与 sequence packing 的策略更新步骤时间。*

在两种架构上，图景一致：

- 对 **Qwen2.5-7B**，外部 padding 最小化把策略更新步骤时间相对 VeRL 默认降低约 **75%**（63s → 16s），达到通过 sequence packing 消除 padding 所能取得改进（12s）的约 **93%**。
- 对 **Jamba2-3B**，它把策略更新步骤时间降低约 **69%**（45s → 14s），相对无 padding 参考值（11s）——此处以 sequence packing 作为计时代理报告——达到约 **91%** 的改进。

换句话说，**用一种与架构无关的方法**，我们几乎消除了所有与 padding 相关的低效，并闭合了与 sequence packing 之间的大部分性能差距。

## 结语

现代训练栈针对 transformer 做了深度优化。当训练另一种模型架构时，这些优化往往失效，而 padding 这类看似细小的问题会变成主要成本。

让我们备受鼓舞的是：有时并不需要架构专属改动，就能把大部分性能找回来。在我们的案例中，训练基础设施里一组小型的、与架构无关的机制——多余 padding 截断与 padding 感知的动态 micro-batching——消除了大部分与 padding 相关的低效，让策略更新步骤时间接近彻底移除 padding 时的水平。

至关重要的是，这不仅适用于 Jamba，也适用于 Qwen 这样的标准 transformer 模型。这种普适性很重要：这类方法可以减少在达到合理训练效率之前重新实现复杂的模型专属内部特性（如 sequence packing 支持）的需要，从而**加速新架构的采用**。

更广泛的教训并不是这些具体修改放之四海皆准，也不是 kernel 级或模型级的优化不重要。恰恰相反：在承诺做更高风险的内部改动之前——尤其是在以 transformer为中心的训练栈内训练非 transformer 架构时——往往值得先寻找消除无用功的模型无关修复。
