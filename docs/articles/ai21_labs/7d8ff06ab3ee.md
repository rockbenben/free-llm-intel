摘要（TL;DR）

在多个并发训练作业之间共享 LLM-as-a-Judge（JLM）部署可以减少 GPU 利用率不足，但会让部署在负载下变得脆弱易垮。我们通过双管齐下的方式缓解了这一问题：优化单节点性能 + 扩展多节点部署，最终形成了一套适用于任何面对可变负载的高吞吐推理部署的策略。

## 挑战：多节点 LLM 部署要在负载下不垮

在我们 [Jamba 模型家族](https://www.ai21.com/blog/introducing-jamba2/)的最后训练阶段，我们引入了 online-RL（GRPO）的定制实现。Online RL 训练需要一个把模型行为引向正确方向的奖励函数。对于数学这类可验证任务，奖励很容易用确定性函数定义。但自由格式任务（如问答和指令遵循）需要更复杂的、基于模型的奖励——我们用 LLMs-as-a-Judge（JLM）来实现。

在经典的 online RL 设置中，JLM 只在奖励阶段被使用，在每个 GRPO 训练步骤的其余时间闲置，导致 GPU 利用率不足。一种缓解方式是彻底异步的方案，它能最大化单个训练作业的 GPU 利用率，但会带来其他复杂性与约束。另一种解法是在多个训练作业之间共享 JLM 部署——当一个作业忙于策略更新时，其他作业可以使用本会闲置的 JLM。

这提升了 GPU 利用率，但也让 JLM 暴露于来自多方、不可预测的流量突增。我们需要让 JLM 部署足够健壮，能同时支撑多个并发训练作业而不被负载压垮。本文分享我们经历的过程与学到的经验。

虽然我们的用例聚焦于服务 GRPO 训练的 JLM，但这些原则适用于任何面对可变负载的高吞吐 vLLM 部署——无论你是在服务有流量尖峰的聊天应用、跑批量推理，还是支撑像我们这样的 ML 训练流水线。

开始正题。

## 双管齐下：优化多节点 LLM 部署的关键

和许多经典系统架构挑战一样，我们选择从两个角度引入优化来解决这一问题：纵向（单节点性能）与横向（多节点扩展）。

## 纵向角度：优化单节点性能

由于我们用 vLLM 作为 JLM 的推理框架，我们首先检视 vLLM 的配置。vLLM 引擎暴露了大量控制其执行的参数，从批处理策略、批大小到内存分配与利用率。针对我们特定的序列长度、负载模式、模型架构和硬件调优这些参数，可以显著改善性能与 GPU 利用率。

我们使用了 OpenShift 的 [Auto-Tune vLLM](https://github.com/openshift-psap/auto-tuning-vllm)，它借助 [GuideLLM](https://github.com/vllm-project/guidellm) 做基准测试，用 [Optuna](https://optuna.org/) 做多目标超参数优化。

### 第 1 步：分析我们的负载

在运行 Auto-Tune 之前，我们需要先确定几个关键参数：

- **序列长度分布：** 输入/输出长度的最小值、最大值与平均值。这些数字决定如何生成合成测试数据并让其分布匹配真实流量模式。
- **流量模式：** 请求是突发式（burst）到达还是恒定流？这影响 vLLM 的批处理配置——例如 `--max-num-seqs`。对突发流量（如我们的场景），vLLM 需要高取值把大量请求尖峰吸收进单个批次。对恒定速率流量，较低取值可以降低单请求延迟。
- **优化目标：** 我们为吞吐还是延迟优化？换言之，我们更关心单个请求的耗时，还是整批的处理时间？

负载刻画完成后，我们配置优化运行。我们使用 Auto-Tune vLLM 的 NSGA-II 策略——一种多目标遗传算法——来探索参数空间，寻找帕累托最优配置。

这是我们为算法定义的搜索空间——我们希望优化的 vLLM 引擎参数及每个参数要测试的取值范围：

#### *基准测试配置*

每个候选配置都用匹配我们负载的合成流量测试：

- 100–1K 输出 token

- 每次试验 5 分钟超时

#### *优化目标*

我们定义了评估每个候选配置的优化指标：

- 输出 token/秒（最大化）
- 请求/秒（最大化）
- 请求延迟（最小化）
- 首 token 时间（TTFT，最小化）
- token 间延迟（TPOT，最小化）

### 第 3 步：运行试验

优化共运行 300 次试验，其中 125 次成功完成。一些配置遇到 OOM 错误或超时——但这在预料之中，框架也优雅地处理了这些情况。

### 第 4 步：挑选优胜配置

由于我们同时优化五个指标，最终剩下 24 个帕累托最优配置，代表我们在上面列出的指标之间的不同权衡。由于我们的目标是最大化吞吐——我们需要完整奖励计算尽快结束，好进入策略更新阶段——我们选择了 token 吞吐最高的配置。

最终的 vLLM 配置如下：

**模型：** 32B 稠密 attention 模型
**硬件：** H100 SXM 80GB

看到结果，你可能会想：调优后的配置当然比旧配置吞吐高——它用了 4 倍的 GPU 资源！

答案藏在我们评估配置的方式里：

比较配置时，我们在*部署*层面评估吞吐。给定固定 GPU 预算，应如何在多个 vLLM 进程之间分配以达到最佳性能？

公式是：

`num_instances = total_gpus / tensor_parallel_size `

`total_throughput = num_instances × throughput_per_instance`

由于我们测试了 `tp ∈ {1, 2, 4, 8}`，可以归一化到 8 块 GPU 总量进行比较。`tp=4` 产生最优分数意味着 **2×4 卡实例的表现优于**：

- 8×1 卡实例
- 4×2 卡实例
- 1×8 卡实例

为什么是 `tp=4`？我们无法下定论，但猜测它对我们的负载是一个甜点：`tp=1` 时每个实例的 KV cache 内存有限，限制其能承载的并发请求数——这对我们的突发流量模式很致命。改用 `tp=4` 把内存池化到 4 块 GPU 上，能容纳显著更多的并发序列。但 `tp=8` 很可能边际收益递减：跨 GPU 通信开销增长，而额外的 KV cache 容量带来的边际收益变小。就我们的具体用例而言，`tp=4` 是恰当的取舍。

### 第 5 步：度量收益

在比较旧配置与调优配置的性能之前，我们需要把 vLLM 版本升级对结果的影响隔离出来。为此，我们用 GuideLLM 跑了三组独立测试：

- 旧配置 + 旧版 vLLM
- 旧配置 + 新版 vLLM
- 调优配置 + 新版 vLLM

我们使用以下测试命令：

旧配置（`rate` 和 `max-requests` 反映分摊在 4×1 卡实例上的负载）：

```
guidellm benchmark \
  --target "http://localhost:8000" \
  --profile throughput \
  --rate 25 \
  --max-requests 500 \
  --data "prompt_tokens=2000,output_tokens=500"
```

调优配置（单个 4 卡实例）：

```
guidellm benchmark \
  --target "http://localhost:8000" \
  --profile throughput \
  --rate 100 \
  --max-requests 2000 \
  --data "prompt_tokens=2000,output_tokens=500"
```

隔离建立之后，我们终于可以查看基准测试结果、度量改进幅度。看主要指标吞吐，最后一项测试——新版 vLLM 上的调优配置——表现最佳，一目了然。

## 横向角度：扩展多节点部署

纵向优化给了我们显著的单实例提升，但还不足以应对多个并发训练作业带来的不可预测负载。为了解决这个问题，我们采取横向方案：动态扩展 JLM 部署。

### 第 1 步：定义自动扩缩指标

表面上看，动态扩展需要为 vLLM 实例定义一个自动扩缩（autoscaling）指标。但选对指标并不简单。

来看几个常见的自动扩缩指标，以及它们在 LLM 推理上为什么失灵：

- **资源利用率：**  **GPU 利用率**：GPU 满载恰恰是我们配置得当追求的结果。100% GPU 利用率不是过载信号——而是效率信号。基于 GPU 利用率扩容会不停触发，即便系统正从容处理负载。**内存利用率**：用于 KV cache 的显存随请求完成与新请求到达而波动——高利用率可能说明批处理健康，而非过载。主要承载请求队列的宿主机内存通常充裕，不会成为瓶颈。
- **吞吐指标：** *输入 token/秒*或*输出 token/秒*这类指标，在实例达到饱和后进入平台期。超过那一点后，吞吐保持稳定，而新请求在队列中越积越多。单看吞吐无法区分「处理得很好」和「被积压淹没」。

那么也许应该直接看积压本身？

快速回顾一下 vLLM 如何处理进来的请求：

- **进来的请求先入队**，然后才被调度处理。
- **连续批处理（continuous batching）机制**从队列中调度请求，直至触及 `–max-num-batched-tokens` 和 `–max-num-seqs` 定义的上限。
- **其余请求在队列中**（CPU 内存里）等待，直到 GPU 腾出空间。

明白这点后，我们可以看到：判断实例过载的好指标，可能是客户端的真实体验——请求排队越来越久才得到响应，因为队列持续增长。我们把它称为**客户端感知延迟（client-perceived latency）**。

vLLM 暴露了两个 Prometheus 指标来捕捉这一点：

- `**vllm:num_requests_waiting**`：当前入队、等待被调度的请求数。
- **`vllm:request_queue_time_seconds`**：请求在处理开始前在队列中等待的时长。

两者反映同一底层信号：当实例跟不上进来的负载，队列增长、等待时间上升。虽然这些指标因受序列长度影响而并不完美，但仍能较好地指示客户端感知延迟。

我们选择队列长度而非队列时间，因为它更简单：是一个直接的计数，便于理解和调参。

### 第 2 步：实现我们的 HPA 配置

对于水平 Pod 自动扩缩器（HPA），我们选择基于**部署内所有 Pod 的平均队列长度**扩缩。当 `vllm:num_requests_waiting` 的均值越过设定阈值，Kubernetes 就会拉起更多实例。

对于最小副本数，我们设置了一个足够高的数字，以便在新实例启动期间仍能承接突发流量。

```
deployment:
  autoscaling:
    minReplicas: 2
    maxReplicas: 10
    metrics:
      metric:
        name: vllm:num_requests_waiting
      target:
        value: 1000
```

### 第 3 步：找到合适的阈值

每 Pod 1,000 个待处理请求的阈值是经验确定的——它大致对应队列等待时间开始影响我们训练作业超时的临界点。在调优后的配置能高效消化约 4K 请求突发的前提下，平均队列达到 1,000 意味着我们接近容量上限，应该横向扩容。

一些来自实践的经验：

- **扩容决策快，但实例启动慢**：vLLM 实例初始化需要大量时间——把模型权重载入 GPU、profiling、编译 CUDA kernel/图。在我们的场景中，一个新的 JLM 实例大约需要 **3 分钟**才能就绪。这意味着你的阈值应足够「宽容」，能容忍新实例启动期间的排队。过于激进的阈值会在请求已经超时之际才触发扩容，为时已晚。
- **缩容应当保守**：我们为缩容配置了 **15 分钟稳定窗口**，避免抖动。你不会希望刚下线一个实例，几分钟后又需要它，反复支付启动成本。
- **调好客户端超时与重试（如果可以的话）：** 设置请求超时要考虑扩容期间的排队——失败太快只会把请求送到另一个队列的尾部。重试之间使用指数退避，避免给已经紧张的体系雪上加霜。

## 回顾：关键建议

部署这些改动并经过几轮微调之后，我们的 JLM 部署能够平稳支撑多个并发训练作业。

以下是我们学到的东西的总结：

### 纵向优化

- **了解你的负载**：调优之前先刻画流量——最大与平均序列长度、突发模式，以及你在为吞吐还是延迟优化。这些认知驱动每一个配置决策。
- **使用自动化调优**：像 [Auto-Tune vLLM](https://github.com/openshift-psap/auto-tuning-vllm) 这样的工具能系统地探索配置空间。手动调优枯燥乏味，且常错过非显见的最佳点（比如我们的 tp=4 发现）。
- **重新审视你的配置**：我们此前的 `--max-num-seqs`（64）和 `--max-num-batched-tokens`（2K，默认值）对我们的负载来说过于保守。把它们分别调到 1,792 和 49K——加上切换到 tp=4——就在同样的 GPU 预算下释放了 2 倍吞吐与 2 倍低的延迟。
- **质疑你对 tensor parallelism 的假设**：模型能放进一块 GPU，不代表 tp=1 最优。多测几种配置——KV cache 容量与通信开销之间的最佳平衡取决于你的负载。
- **隔离变量**：做基准测试时，把版本升级的影响与配置改动的影响分开。在我们这里，vLLM 0.8.5 → 0.11.0 带来约 15% 的提升，而配置调优在此之上又有约 1.8 倍。

### **横向扩展**

- **选对自动扩缩指标**：像 `vllm:num_requests_waiting` 或 `vllm:request_queue_time_seconds` 这样反映客户端感知负载的队列指标，可以很好地指示实例过载。
- **考虑缓慢的启动**：vLLM 实例初始化要几分钟。把自动扩缩阈值设得足够高，以容忍新实例启动期间的排队。
- **缩容要保守**：使用较长的稳定窗口，避免抖动和反复支付启动成本。
- **让客户端超时与扩缩延迟对齐：** 考虑扩容延迟；使用指数退避避免放大负载。
