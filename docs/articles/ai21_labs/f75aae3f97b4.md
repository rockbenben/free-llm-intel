# 我们如何将 GitLab Duo Code Review 的成本降低 98%

简报

*我们在*[*Martian 的 Code Review Bench*](https://codereview.withmartian.com/) *上把 GitLab Duo Code Review 的成本砍掉了 98%，而且没有牺牲 review 质量；这一切都来自对 harness 的优化：每个 stage 跑哪个模型、每个 stage 读多少上下文。单靠其中任何一个改动都到不了这个数。开放权重模型在少数几篇超大 review 上卡住了，正是压缩上下文才让它们全都装得下。*

*图 1. 结果表中每种设置的成本对 F1。整个过程中 F1 与基线的差距都在 2 分以内。同一个压缩步骤在基线上省下 19%，在换模型之后省下 84%；在对数轴上，箭头长度反映节省的百分比。*

一个 agent 的成本最终由它的 harness 决定：它跑哪些 stage、每个 stage 读什么、由哪个模型来干活。我们选中了 GitLab Duo Code Review——它的 harness 是源码可见的——先量清楚钱花在哪里，再在自己 agent 的协助下跑实验，一次只改一件事，直到账单不再往下掉。

但真正的看点不是 harness 上最终那几处改动，而是我们走到那里的过程。每个 stage 都换成更小的模型，质量会掉。每个 stage 都换到开放权重模型，砍掉了 85% 的成本，但我们没停在这一步。压缩乍看无足轻重，可只有两件事一起做才拿得到 98%，因为开放权重模型的部署窗口决定了它到底能接哪些请求。模型定价格，harness 决定你有没有机会用上这个价格。

我们是在公开的 pull request 上跑的这套实验，不涉及 GitLab 的生产流量或客户数据。质量指标是某一个公开 benchmark 上的 F1，由两个 judge 打分。成本是按公开的 list price 计算的 token 消耗，我们自己托管的那个模型也算在内，所以它衡量的是 harness 消耗了多少。我们自己的基础设施花了多少钱是另一个问题。这些配置是在打分所用的同 50 个 pull request 上挑选并调优的，因此请把它们当作该 benchmark 上的实测结果来看；它们在陌生代码库上是否成立未经测试。完整方法在文末。

## **一条四个 stage 的流水线**

[Duo Code Review](https://docs.gitlab.com/user/duo_agent_platform/flows/foundational_flows/code_review/) 是 GitLab Duo Agent Platform 的 Code Review Flow，负责审查 merge request 并发评论。测试时它默认跑 Claude Sonnet 5，而 GitLab 已经把这条基于 LangGraph 构建的 flow 发布在它 source-available 的 ai-assist 仓库里。这一点加上一个公开 benchmark，就是我们选它的原因。

它跑四个模型 stage，每个都有自己的 prompt 和至多两个工具：

- **Exploration** 列出改动文件周边的仓库目录树。
- **File fetching** 读取相关文件：测试、调用方、自定义指令。
- **Analysis** 把取回的内容整理成笔记。
- **Review** 完整读取 diff 和改动最多的文件，然后发出评论。

*图 2. Duo Code Review 的四个 stage。每个都从一份全新的 prompt 起步，最多带两个工具。*

我们此前做的所有通用优化，针对的都是 Claude Code 这类 coding agent——它们会不断重发一个越滚越大、塞满工具输出和工具定义的会话。Duo Code Review 的各个 stage 彼此独立：每次都以全新 prompt 起步，最多带两个工具，也没有历史可以裁剪。我们的默认手段无处发力，改动的请求数为零。

结论就是：**harness 优化没有放之四海皆准的做法**；每个 harness 都需要各自细致的分析。

## **钱花在哪里**

*图 3. 基线每个 PR 的 $0.589 花在了哪里。review 占账单的 65%，其中读多少和推理多少大致各半。*

review 占账单的 65%，光是它的输出就占了总量的三分之一：发评论前可以自由思考，**Sonnet 5 每次 review 大约写 18,600 个 token，几乎全是 reasoning。**只负责决定读哪些文件的 Exploration 和 fetching 占 27%。Analysis 占 9%。

钱主要花在三个地方：每个 stage 读的上下文、那些机械性的 stage、以及 review 的 reasoning。没有任何单一改动能同时覆盖三处，但下面的每一步都能拿下其中一处。

## **发现 1：上下文更少，reasoning 更多**

**能不能让 review 少读一些又不伤它的质量？**能，但省下来的比算术推算的少。

review stage 构建上下文时，会完整包含改动文件，再附上一份 diff——其中每一行都套在一个重复标注其类型和两侧行号的标签里。而 unified diff 用一个字符就能标记同一行。

我们在 flow 之前把这两处都做了压缩，用的是规则而不是模型：没有任何内容被摘要。文件开窗保留每个改动的 hunk，并在新旧行号区间两侧各留 25 行，其余省略。diff 压缩把那份逐行 diff 重写成标准的 unified diff，hunk 和行号都保持一致。

review prompt 的中位数从 59K 降到 32K token。花在 review 上下文上的开销降得更多，达 62%，因为最大的那些 prompt 缩得最狠。

但 review 的成本只降了五分之一。**压缩打开之后，Sonnet 5 反而写得更多**：每次 review 约 23,800 个输出 token，而不是 18,600，几乎全是 reasoning。我们还没隔离出原因，但它限制了压缩单独能省下的上限。单靠压缩，成本从 $0.589 降到 $0.475，节省 19.4%，F1 为 47.2%，延迟是原来的 1.16x。

*图 4. 基线对比压缩。花在 review 上下文上的开销下降 62%，但它的 reasoning 输出增长 28%，所以账单只降 19%。*

## **发现 2：开放权重模型在每个 stage 都稳住了**

**换模型能走多远？**这取决于你换的是哪个 stage。

我们一开始是把 Claude Haiku 4.5 一次只搬到一个 stage 上。在 exploration 和 fetching 上，它挑出的文件和 Sonnet 5 一样。另外两个 stage 的早期测试就没这么客气了：Haiku 放到 analysis 上质量下滑，放到 review 上质量大幅下跌。同一个模型，位置不同，结果天差地别。只把它用在两个机械性 stage 上时，Haiku 在 F1 不变的前提下砍掉 15.4% 的账单，叠加压缩则是 34.6%。

Haiku 只能走到这里。它守不住 review 的质量——而那正是钱的大头所在；而且它的价格只有 Sonnet 5 的一半，即便守住了也不足以明显撼动账单。要动 review 的 reasoning，就得离开 Claude 家族。

接着我们转向开放权重模型：DeepSeek V4 Flash，这是我们试的第一个，用 vLLM 部署在 H100 上自托管。按 Together AI 的 list price，它每个输入 token 比 Sonnet 5 便宜 14 倍，每个输出 token 便宜 36 倍。四个 stage 全换上它、压缩关掉，成本降到 $0.086，节省 85.3%，F1 为 48.4%，延迟是原来的 0.37x。在这个 benchmark 上，它在每个 stage 都稳住了，review 也包括在内。

两处 harness 设置才让这份稳定成立。reasoning effort 是靠测量定下来的（见「不管用的部分」）。另外，DeepSeek 上大约每七次 review 调用就有一次结束时没有发出评论；GitLab 自带的纠错步骤会对每一篇重试，所以每条 review 都发出去了，这些重试也计入了成本。

## **为什么节省停在 85%**

我们的 DeepSeek 部署接受最长 256K token 的 prompt；更长的仍留在 Sonnet 5 上，好让 review 能够完成。该模型支持 1M，但要服务那么大的窗口需要更复杂的部署，而且它在超长上下文下的质量仍有争议。不开压缩时，有些 review prompt 会到 480K，50 个 PR 中有 3 个越过上限，产生 11 次回退调用。

*图 5. 每个 stage 都换到开放权重模型且不开压缩时，50 个 PR 中有 3 个（6%）超过 256K 的部署窗口，回退到 Sonnet 5。这 11 次调用扛着每个 PR 剩余 $0.086 成本中的 77%。*

**6% 的 pull request 扛着剩下成本的 77%**。而溢出的那些 prompt 正是最大的 review，它们之所以大，原因恰好就是发现 1 里讲的那几条。

于是把压缩放了回来，这一次是为了让 prompt 装得下。最大的 review prompt 从 480K 降到 109K。每条 review 都装得下，没有任何回退。成本降到每个 PR $0.0135，比基线低 97.7%，F1 为 47.2%，延迟是原来的 0.35x，第二个 judge 的评分差距在半个百分点以内。

*图 6. 一路走下来每个 PR 的成本。Claude 上最好的配置到 $0.385，每个 stage 都用开放权重模型到 $0.086，再加上压缩就是 $0.0135：比基线低 98%，F1 为 47.2% 对 46.4%。*

到这一步，压缩本身省下的 token 大约值每个 PR $0.006，它买到的其实是「装得下」。在 Claude 面前，压缩是一种成本优化；在 256K 的部署面前，压缩让每条 review 都留在开放权重模型上。

1M 的部署同样能消除回退。但它不会减少每个 review 读取的内容，还会把担子压在模型质量最没有定论的那些长度上。

## **不管用的部分**

| **我们试过什么** | **我们发现了什么** |
| --- | --- |
| 提高 reasoning effort | 在 30 篇试验 review 上开到「max」，召回率从 38.9% 升到 52.8%，而 F1 只从 35.0% 挪到 35.4%，延迟却是 3.5x：发现更多、成本更高、review 并没有更好 |
| prompt 缓存 | 能复用的东西很少。同一 stage 内的请求共享指令，但各 stage 之间没有共同前缀，所以每个 stage 都要读的 diff 和文件无法跨 stage 复用 |
| 给 exploration 和 fetching 换更低价的模型 | 不值得测。最终配置里这两个 stage 每个 PR 只花 $0.005（总计 $0.0135），所以就算模型免费，也只会给节省再加约一个百分点 |

## **结果**

| **配置** | **F1** | **每个 PR 的成本** | **相对基线的成本** |
| --- | --- | --- | --- |
| **留在 Claude 上** |  |  |  |
| 基线：每个 stage 都用 Sonnet 5 | 46.4% | $0.589 | 0% |
| 只用压缩 | 47.2% | $0.475 | −19.4% |
| exploration 和 fetching 用 Haiku 4.5 | 46.3% | $0.498 | −15.4% |
| exploration 和 fetching 用 Haiku 4.5，再加压缩 | 46.0% | $0.385 | −34.6% |
| **引入开放权重模型** |  |  |  |
| exploration 和 fetching 用 DeepSeek，再加压缩 | 45.9% | $0.370 | −37.1% |
| 除 review 外全部用 DeepSeek，再加压缩 | 45.1% | $0.317 | −46.1% |
| 每个 stage 都用 DeepSeek | 48.4% | $0.086 | −85.3% |
| 每个 stage 都用 DeepSeek，再加压缩 | 47.2% | $0.0135 | −97.7% |

凡未点名的 stage 都跑在 Sonnet 5 上。没有任何配置在两个 judge 上把 F1 挪动超过 2 分。最终配置的 review 比基线更精准（46.8% 对 41.9%），但抓到的问题略少（召回率 47.6% 对 52.0%），而且每次约 9,000 个 token 对比 18,600，延迟约为原来的三分之一。

## **小结**

- 账单集中在三个地方，每一处需要不同的改动：共享上下文、机械性 stage、以及 review 的 reasoning。
- Haiku 4.5 在两个机械性 stage 上守住了质量，在 analysis 和 review 上丢了。
- 开启压缩后，review prompt 的中位数缩短了 46%，而 reasoning 输出增长了 28%。
- 50 个 PR 中的 3 个扛着剩余成本的 77%，直到压缩让每条 review 都装进部署窗口。

压缩单独值是 19.4%。放在换模型之后，同样的压缩值剩下成本的 84%，因为那时它的任务已经变成让 prompt 装得下。

正是这种相互依赖让 harness 优化变难，也正是它值得做的原因。本研究里的这些设置不断改变着彼此的价值。压缩在 Sonnet 5 上值账单的五分之一，在 256K 部署上却决定了最终结果。Haiku 在两个 stage 上安全，另外两个上却伤了质量。要走到 98%，就得把配置当作一个整体来搜索，而这份搜索正是节省的来源。

具体这些设置只属于这个 agent，而且已经过时了：我们跑完之后，GitLab 已把 Duo Code Review 换到 Sonnet 5.5。方法倒是更能迁移。动手改任何东西之前，先按 stage 量成本。一次只改一个变量，并且每落下一个新改动就回头复测之前的改动。多数团队手上没有公开 benchmark 可以对着做；我们认为同一个循环用在一份真实流量的切片上同样成立，一旦某个配置在大部分流量上站得住，它就成为 harness 里的一行。

## **附录：我们怎么测的**

下表里的一切在第一次运行之前就已固定。我们自己的 agent 在这些规则之内帮忙跑搜索，负责提出、执行并给配置打分。

| **我们在什么上测** | **Martian 的 Code Review Bench 完整离线集：来自 Sentry、Grafana、Cal.com、Discourse 和 Keycloak 的 50 个真实 pull request，带 173 条经人工核实的「golden」评论，也就是一次好 review 应该抓到的问题** |
| --- | --- |
| review 怎么打分 | judge 模型把 agent 的评论与 golden 评论做匹配。精确率：它发出的评论里有多少匹配上。召回率：它找到了多少条 golden 评论。F1 平衡两者。Claude Opus 4.5 用 Martian 的 prompt 当 judge，GPT-5.2 作交叉校验 |
| 「可比」是什么意思 | 每个配置对每个 PR 各 review 3 次。可比指的是即使在 95% 置信区间的悲观一端，F1 相对基线的差距也小于 5 分，且两个 judge 都如此 |
| 成本怎么计价 | 按公开的每百万输入/输出 token 单价，不计缓存折扣：Sonnet 5 为 2/10，Haiku 4.5 为 1/5。DeepSeek V4 Flash 是我们自托管的，所以我们按 Together AI 的公开费率 0.14/0.28 计价，而不是我们自己的服务成本 |
| 基线 | 出厂状态的 agent，每个 stage 都用 Sonnet 5：F1 46.4%，每个 PR $0.589（code_review flow 2.0.0，ai-assist commit 5272972） |

为了校验我们的打分，我们把它跑在 Martian 公开的那批 GitLab 自己记录的 PR review 上：52.3% F1，对照 Martian 的 54.2%。它们来自另一个配置，所以只能验证我们的打分方法，说明不了我们基线的情况。这些都是公开的 PR，其内容可能出现在训练数据里。我们能排除的是 review 模型从题目本身复述出答案：只给每个 PR 的标题、URL 和 commit 链接时，两者的 F1 都只有约 4%。agent 读到的每个文件都来自固定版本的离线副本。
