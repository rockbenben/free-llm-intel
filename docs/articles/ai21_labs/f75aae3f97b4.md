简介

*我们在* [*Martian 的代码审查基准*](https://codereview.withmartian.com/) *上将 GitLab Duo 代码审查的成本削减了 98%，而没有损失审查质量，而这一切都来自于优化工具：每个阶段运行的模型以及每个阶段读取的上下文量。这两种改变都是单独实现的。开放权重模型因一些过大的评论而停滞不前，而压缩上下文才是使它们适合的原因。*

*图 1. 结果表中每种设置相对于 F1 的成本。 F1 始终保持在基线的两点以内。相同的压缩步骤比基线节省 19%，模型切换后节省 84%；在对数轴上，箭头长度反映了节省的百分比。*

代理的成本最终由其工具决定：它运行哪个阶段、每个阶段读取什么以及哪个模型执行工作。我们采用了 GitLab Duo Code Review，其工具包是可用的，测量了它的资金所在，并且在我们自己的代理帮助进行实验的情况下，一次更改一件事，直到账单停止下降。

但真正的故事并不是安全带的最终变化；而是安全带的最终变化。这就是我们到达那里的方式。在每个阶段切换到较小的模型都会损害质量。在每个阶段改用开放式重量模型可以降低 85% 的成本，但我们并没有就此止步。虽然压缩乍一看似乎微乎其微，但 98% 仅在两者中都出现，因为开放权重模型的部署窗口决定了它可以接受哪些请求。模型决定价格。安全带决定了你是否可以使用它。

我们在公共拉取请求上运行了这个，没有 GitLab 生产流量或客户数据。质量在一项公共基准测试中为 F1，由两名评委打分。成本是按公布的标价计算的象征性支出，包括我们自己服务的模型，因此它衡量了线束的消耗量。我们自己的基础设施成本是一个单独的问题。配置是根据它们评分的相同 50 个拉取请求来选择和调整的，因此请阅读这些基准测试的测量结果；他们如何保留新的代码库尚未经过测试。完整的方法论在最后。

## **具有四个阶段的管道**

[Duo Code Review](https://docs.gitlab.com/user/duo_agent_platform/flows/foundational_flows/code_review/)，GitLab Duo Agent Platform 的代码审核流程，审核合并请求并发布评论。在测试时，它默认运行 Claude Sonnet 5，GitLab 在其源可用的 ai-assist 存储库中发布了基于 LangGraph 构建的流程。这加上公共基准，就是我们选择它的原因。

它运行四个模型阶段，每个阶段都有自己的提示符和最多两个工具：

- **探索**列出已更改文件周围的存储库树。
- **文件获取**读取相关文件：测试、调用者、自定义指令。
- **分析**将获取的内容转化为笔记。
- **审阅** 完整读取差异和更改最多的文件，然后发布评论。

*图 2.Duo Code Review 的四个阶段。每个都从一个最多有两个工具的新提示开始。*

我们构建的每一个通用优化都针对像 Claude Code 这样的编码代理，它重新发送充满工具输出和工具定义的不断增长的对话。 Duo Code Review 的阶段是独立的：每个阶段都以新的提示开始，最多携带两个工具，并且没有需要修剪的历史记录。我们的默认设置没有任何可操作的内容，并且更改了零请求。

事实证明，**没有一种放之四海而皆准的线束优化方法**；每个线束都需要仔细分析。

## **钱去哪儿了**

*图 3. 每个 PR 0.589 美元的基线。评论占法案的 65%，几乎各占其阅读内容和推理数量。*

评论占账单的 65%，仅其输出就占总数的三分之一：在发布之前自由思考，**Sonnet 5 每次评论写入约 18,600 个标记，几乎都是推理。** 探索和获取仅决定读取哪些文件，占 27%。分析为9%。

钱主要花在三个地方：每个阶段阅读的上下文、机械阶段和评论的推理。没有任何单一的改变可以达到所有三个，但下面的每个步骤都可以达到其中一个。

## **发现 1：更少的上下文，更多的推理**

**我们可以在不损害评论的情况下删减内容吗？** 是的，而且它节省的费用比算术建议的要少。

审查阶段构建其上下文，包括完整更改的文件，以及差异，其中每一行都位于重复其类型和行号的标签中。统一差异用一个字符标记同一行。

我们在流程前面压缩了两者，使用规则而不是模型：没有任何总结。文件窗口保留每个更改的块以及旧行范围和新行范围两侧的 25 行，并忽略其余部分。差异压缩将每行差异重写为具有相同块和行号的标准统一差异。

审核提示中位数从 59K 减少到 32K。审查上下文的支出进一步下降了 62%，因为最大的提示缩减得最严重。

然而，审查的成本仅下降了五分之一。 **启用压缩后，Sonnet 5 还编写了更多**：每次评论大约有 23,800 个输出标记，而不是 18,600 个，几乎都是推理。我们还没有找出原因，但它限制了压缩本身可以节省的成本。压缩本身的成本从 0.589 美元降低到 0.475 美元，节省了 19.4%，F1 为 47.2%，延迟为 1.16 倍。

*图 4. 压实基线。审查上下文的支出下降了 62%，但其推理输出增长了 28%，因此费用仅下降了 19%。*

## **发现2：每个阶段都保持开放重量模型**

**改变模型能让你走多远？**这取决于你改变的阶段。

我们首先将 Claude Haiku 4.5 一次移到一个舞台上。在探索和获取时，它选择了与 Sonnet 5 相同的文件。对另外两个的早期测试就不那么友好了：分析时俳句的质量下降，审查时质量急剧下降。相同的型号，根据安装位置的不同，结果也截然不同。保持在两个机械阶段，Haiku 在 F1 不变的情况下减少了 15.4% 的费用，在压实情况下减少了 34.6%。

这就是俳句所能达到的极限了。它无法保证评论的质量，而评论的质量是大部分钱所在，而且以 Sonnet 5 的一半价格，即使它能保证评论的质量，也不足以改变账单。达到审查的推理就意味着离开克劳德家族。

然后，我们转向开放权重模型：DeepSeek V4 Flash，这是我们尝试的第一个模型，我们在 H100 上通过 vLLM 提供该模型。按照 Together AI 的标价计算，每个输入代币的成本比 Sonnet 5 低 14 倍，每个输出代币的成本低 36 倍。启用所有四个阶段并关闭压缩后，成本降至 0.086 美元，节省了 85.3%，F1 为 48.4%，延迟为 0.37 倍。在这个基准测试中，它在每个阶段都进行了测试，包括审查。

两种安全带设置使这一点得以保持。推理努力是通过测量来确定的（参见“什么没有帮助”）。 DeepSeek 上大约有七分之一的审核电话没有发布就结束了； GitLab 自己的更正步骤会重试每一个，因此每条评论都会发布，并且重试都包含在成本中。

## **为什么节省在 85% 就停止了**

我们的 DeepSeek 部署接受最多 256K 代币的提示； Sonnet 5 上的任何内容都将保留，以便审核完成。该模型支持 1M，但服务该窗口需要更复杂的部署，并且其在很长上下文中的质量仍然存在争议。如果没有压缩，一些审查提示会达到 480K，并且 50 个 PR 中的 3 个超出限制，产生 11 个回退调用。

*图 5. 在开放权重模型的每个阶段且没有压缩的情况下，50 个 PR 中的 3 个 (6%) 超过了 256K 部署并回落到 Sonnet 5。这 11 个调用占每个 PR 剩余 0.086 美元的 77%。*

**6% 的拉取请求包含剩余内容的 77%**。溢出的提示是最大的评论，其原因与发现 1 中的原因相同。

所以压缩又回来了，这次是为了让提示适合。最大的审阅提示从 480K 下降到 109K。每一篇评论都很合适。没有什么会倒退。每个 PR 的成本达到 0.0135 美元，比基线低 97.7%，F1 为 47.2%，延迟为 0.35 倍，第二个判断的误差在半个点之内。

*图 6. 一路上每个 PR 的成本。 Claude 上的最佳设置达到 0.385 美元，每个阶段的开放重量模型达到 0.086 美元，增加压缩使其达到 0.0135 美元：比基线低 98%，F1 为 47.2%，F1 为 46.4%。*

那时，压缩本身的代币节省约为每个 PR 0.006 美元。买的东西都是合适的。在Claude面前，compaction是一种成本优化。在 256K 部署之前，它保留对开放权重模型的每次审查。

1M 部署也将消除后备措施。它不会缩小每篇评论的内容，并且会在其质量最不稳定的长度上依赖模型。

## **总结**

- 该法案位于三个地方，每个地方都需要不同的改变：共享背景、机械阶段和审查推理。
- Haiku 4.5 在两个机械阶段保持了质量，但在分析和审查中失去了质量。
- 通过压缩，复习提示中位数减少了 46%，而推理输出增加了 28%。
- 50 个 PR 中的 3 个承担了剩余成本的 77%，直到压缩使每次审查都适合部署窗口。

压实本身的价值为 19.4%。在模型更改后添加，相同的压缩值是剩余值的 84%，因为那时它的工作是使提示适合。

这种相互依赖性使得线束优化变得困难，同时也是它获得回报的原因。这项研究中的设置不断改变彼此的价值。压缩仅占 Sonnet 5 成本的五分之一，并决定了 256K 部署的结果。俳句在两个赛段都很安全，但在另外两个赛段却影响了质量。达到 98% 意味着要搜索整个配置，而搜索正是节省成本的来源。

具体设置属于该代理，并且它们已经过时了：自从我们运行此代理以来，GitLab 已将 Duo Code Review 移至 Sonnet 5.5。该方法传播得更好。在改变任何东西之前测量每个阶段的成本。一次更改一个变量，并在每个新变量落地后重新测试之前的更改。大多数团队没有公开的工作基准；我们期望相同的循环能够在实时流量的一部分上工作，并且一旦配置保留了大部分流量，它就成为线束中的一条线。
