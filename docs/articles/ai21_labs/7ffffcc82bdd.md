如果你看看 2024 年的 LinkedIn 帖子和主题演讲标题，你可能会以为那是 AI agent 的*元*年。社交网络上充斥着各种 agent 处理复杂任务的视频，从点披萨到写生产级代码。概念上的飞跃出现在 Anthropic 于 10 月发布"[Computer use](https://www.anthropic.com/news/3-5-models-and-computer-use)"之后，紧接着 OpenAI 的"[Operator](https://openai.com/index/introducing-operator/)"更进一步——agent 连接到计算机，获得键盘和鼠标的访问权限，就像真正的人类一样。尽管这些仍是早期技术，但它们被如此自然地呈现出来这一事实本身，既令人兴奋又令人不安。

许多公司承诺用单个 AI agent 取代整个开发团队的解决方案，但现实描绘的是另一番景象。不仅实际生产环境中几乎没有 AI agent，而且大多数自称 AI agent 的产品*缺乏真正的"自主性（agency）"*。承诺与现实之间的差距并不令人意外——这是科技界屡见不鲜的模式。尽管如此，理解这个差距*为什么*如此之大仍然至关重要，尤其是在我们面对一项旨在改变我们开发和运行软件系统方式的技术时。

## 为什么生产环境中的 AI Agent 这么少？

两年前，把大语言模型（LLM）放进生产环境的想法几乎不可想象，而今天每家公司都有生成式 AI 团队。LLM 的主要挑战我们闭着眼睛都能背出来：这些是统计模型，其输出并不总是可靠，无论是格式问题还是彻头彻尾的幻觉。归根结底，它们以文本为输入、以文本为输出，尽管它们有时展现出非凡的"理解力"，但孤立地看仍然是受限的。

从这一点自然演进出的概念是[*复合 AI 系统（Compound AI Systems）*](https://bair.berkeley.edu/blog/2024-02-18/compound-ai-systems/)——把语言模型作为更大系统的一部分来使用。这种方式可以对输出提供更强的保证，或对输入做更好的调优。一个经典例子是 RAG（检索增强生成），它已成为标准方法。AI agent 是这种方法一个尤为复杂的示例。其核心是一个观察当前态势、采取行动、接收反馈、然后重复循环的组件。但借用本叔叔的话改编一下："*能力*越复杂，*挑战*就越大"。

我们可以把这些挑战归纳为四个主要方面。

### 1. 质量

我们交给 AI agent 的任务，往往对人类自己来说都很困难。以项目管理为例——你需要同时把握业务和技术层面，与不同的人有效沟通，并做出艰难决策。虽然我们看到模型推理能力取得了令人瞩目的突破（例如 [OpenAI 的 o3](https://www.youtube.com/watch?v=SKBG1sqdyIU)），但它们还不够成熟到可以独立担当。而且语言模型常见的所有责任和可靠性问题在这里同样适用。诚然，AI agent 包含大量护栏层，但总体而言我们对 agent 的期望*高于*对标准语言模型的期望。可靠性问题的一个生动例子是针对 [Air Canada](https://www.forbes.com/sites/marisagarcia/2024-02-19/what-air-canada-lost-in-remarkable-lying-ai-chatbot-case/) 的诉讼——该案最终以该公司为其聊天机器人的错误信息赔付告终。有这样的判例在先，任何公司在把 AI agent 驱动的功能推向生产环境之前都会三思。

### 2. 资源

就像钉小钉子不需要大锤，简单任务也不需要一套完整的 AI agent。运行一个 AI agent 涉及多次模型调用——每次调用都要花钱——因此开销可能迅速累积。低效的实现可能为完成单个简单任务就发起上百次不同的调用。再算上每次调用的处理时间，你可能要等上几分钟才能得到一个也许近在眼前的答案。

### 3. 透明度

深度学习总体上（尤其是 LLM）存在严重的可解释性问题。这些模型为什么做出那样的决策？其依据是什么？这一挑战对 AI agent 同样严重，因为要破解其行为背后的理由极其困难。

这一切源于基于复杂统计计算做出的决策。即使你要求 agent 解释它如何得出该决定，你又怎能确定它说的是实话，而不是事后"编造"一个理由？许多开发者感觉自己在跟黑箱打交道，这既让开发过程变得复杂，也妨碍了结果的一致性。

### 4. 开发复杂度

构建一个生产就绪的 AI agent 需要深厚的技能储备。你需要处理语言模型的专业能力（谁有时间去打磨"完美"的 prompt？）、获取高质量数据（无论是公开数据还是内部数据）的能力，以及评估 agent 表现的手段（即便对更简单的语言模型而言这也是个难题）。

## 那么，如果这些不是真正的"Agent"，它们是什么？

在现阶段，大多数商业"AI Agent"解决方案通常属于以下几类之一：

### 工具使用与 Function Calling

这个概念最早出现在 [AI21 2022 年的一篇论文](https://arxiv.org/pdf/2205.00445)中，后来由 [OpenAI 正式引入](https://openai.com/index/function-calling-and-other-api-updates/)其 API。想法很简单：语言模型擅长写作类任务，那数学计算呢？或者上网搜索相关信息呢？通过把它们连接到外部工具，我们可以扩展其能力。
调用语言模型时，你提供一组"工具"（实际就是函数签名）。如果模型意识到它需要更多信息或外部资源，它就会输出对相应工具的调用。这里的"agentic"要素是那个检查语言模型输出、检测其何时想调用外部函数、执行该调用并把结果回喂给模型的系统。这项技术如今已较为稳定，事实上，主要的企业平台（AWS、Azure AI、Google Vertex）主打的正是这类 agent。

### LLM 作为路由器

这里我们谈论的同样是一个*系统*，而非纯粹的 agent。其核心是一个语言模型，它接收传入请求并将其路由到合适的资源——无论是外部工具、Python 脚本，还是更小的专用语言模型。一个例子是 [arcee.ai](http://arcee.ai)。

### ReAct——推理与行动

该方法最早于 [2023 年被提出](https://arxiv.org/pdf/2210.03629)，结合了任何 agent 的两项基本能力：对指令和状态进行推理的能力，以及采取行动的能力。它使用[思维链（Chain of Thought）](https://arxiv.org/pdf/2201.11903)等技术来处理深度逻辑过程（想象需要一步步求解的应用题），再加上连接外部工具的能力。在每一步，模型基于已有数据做出*观察*，决定一个*行动*，执行它，然后进入下一个观察阶段。如此循环，直到最终决定向用户返回响应。
这里存在明显的限制：过程是顺序运行的，这使运行时优化变得困难。此外，最终用户无法控制决策序列，一切都以自主方式进行。这也许方便，但结果并不总是理想，而且调试几乎不可能。

## 但这不仅仅是炒作

格局正在快速变化，2025 年确实很可能是 AI Agent 之年（或至少又是相关的一年）。挑战很清晰：质量、成本、透明度和复杂度。但克服它们并非不可能，只是需要换一种思维方式。

整个生态系统都聚焦于此。在 AI21，我们不只是旁观这一进程——我们正忙于构建。下一代 AI agent 不会是高级版的函数调用器。它们将是有能力、可靠的、为真实世界影响而打造的。
