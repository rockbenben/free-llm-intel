欢迎 Maestro！一个规划并执行所有任务的系统。

在这篇文章中，我们将介绍 Maestro 的智能规划能力，以及它如何确定解决复杂任务的最佳行动路径，并重点展示*带要求生成*这一强力用例。它还内建了文件搜索（RAG 系统）和网页搜索。我们将说明如何用 Maestro 解决复杂问题或改进现有管道，并演示它如何增强当今最好的 LLM。

## Maestro 是做什么的？

顾名思义：用户不再编写一条堆满指令的复杂 prompt，而是把输入拆成一条指令（instruction）和一组要求（requirements）。要求可以是内容、风格、格式、体裁、视角以及各类护栏。Maestro 在整个生成过程中持续对照要求校验输出，确保它们被满足。然后它产出结果、给每项要求打分，并对任何未满足的要求给出详细反馈。

这看起来似乎比直接给一条指令多花了功夫。为什么不自动从完整指令里提取要求呢？

是的，它多花了一些功夫，但正如那句话所说——这是特性，不是缺陷。简单讲，显式地指明要求，让 Maestro 得以在生成期间校验输出并提供反馈，把更多的控制权与可见性交到用户手里。

## Maestro 如何规划和执行任务？

Maestro 的核心是一个动态规划系统，在推理时决定解决给定任务的最佳行动序列。系统擅长自我校验与纠错，持续对照你指定的要求评估输出。

与依赖单次生成尝试的传统方法不同，Maestro 使用推理时算力扩展来校验结果并迭代改进。它不遵循固定套路，而是智能地规划实现你目标的最有效路径。

通常，更多算力意味着更高质量。Maestro 通过精巧的规划机制利用这一原则：给定质量阈值和预算，Maestro 会在遵守预算限制与质量阈值的同时规划并执行任务。任意时刻都有一个候选解，Maestro 不断改进它，直到所有要求被满足或预算耗尽。

本质上，每次对 Maestro 的调用都会构建一棵由 LLM 和其他工具调用组成的树。基于任务要求和可用预算，Maestro 策略性地计划采用哪些技术。 Maestro 可能纳入执行计划的技术示例：

- **Best-of-N**：每次 LLM 调用都生成多次——用不同模型，或用同一模型配高 temperature。成功概率低的候选被舍弃。这一方法关乎树的宽度。
- **生成并修复**：每个有希望的候选（得分不错或被认为易于修复的）都会进入修订循环，生成与反馈再喂给下一轮生成（其中也可能用 Best-of-N）。这一方法关乎树的深度。

这只是 Maestro 动态规划过程可采用的众多技术中的两个例子。系统持续评估在剩余预算下哪些行动会产生最佳结果，并相应调整自己的打法。

让 Maestro 与众不同的不只是算法技术，构建过程中还倾注了大量工程考量。Maestro 的智能执行机制理解所执行代码内部的依赖关系，通过平衡并行与串行操作来优化整个系统的性能。

把以上所有组合起来，就形成了一个既能快速解决问题、又能持续改进结果直至触及预算限制的系统。

## 这带来了什么？

使用 Maestro，任何开发者都可以：

- ***更快**地工作*——那些为生产环境独自搭建整个系统的开发者都清楚，这远比任何 Jupyter notebook 教程或 15 分钟的 YouTube 指南复杂。它需要手工规划复杂工作流：评估并决定哪个模型表现最佳、定义校验逻辑、从错误中恢复，等等。而现在，你只需调用 Maestro，就能按你的预算获得质量保证。
- ***更聪明**地工作*——如果你注意到输出不够好的趋势，多半意味着你需要增加一条要求。例如，在大规模用 Maestro 做代码生成时，我们发现某些输出总是失败。检查后注意到，问题出在包含撇号的字符串上（撇号前若没有反斜杠就会引发错误）。把这条具体要求加进 Maestro 后，问题立刻修复。

## 它有效吗？

我们在两类问题上评估了 Maestro：复杂 RAG 系统与要求遵循。

### 复杂 RAG 系统

为了评估 Maestro 在 RAG 管道内解决复杂问题时对常见系统的增强，我们在 [FRAMES](https://huggingface.co/datasets/google/frames-benchmark) benchmark 上测试其性能。该 benchmark 提出了特别具有挑战性的多跳问题，要求系统跨多份文档检索并整合信息，同时执行复杂推理任务。可以看到，使用动态规划的 Maestro 胜过了那些依赖 LLM 在运行时做决策的现有 agentic 系统。

### 要求遵循

对 Maestro 的评估在多个数据集上以多种方法进行。我们在 [IFEval](https://huggingface.co/datasets/google/IFEval) 上测试了 Maestro——这是一个广受认可的、包含可用启发式规则验证的可验证指令数据集。

我们的评估采用两种不同方法：

- LLM-as-a-Judge：我们把验证函数转换为语义要求（例如把 "no_comma" 转成"在你的整个回答中，避免使用任何逗号。"）。这些就成为 Maestro 需要满足的要求。
- 代码验证：我们以程序方式实现这些验证，在 Maestro 的改进迭代中做更精确的评估。这利用了 Maestro 的一项关键特性——允许开发者把自己的校验器作为系统的一部分。

如下方图表所示，相对于标准 LLM 调用，Maestro 取得了显著提升，进一步证明了它在不同类型要求上的有效性。

我们还开发了一个名为"Requirements Following"（要求遵循）的数据集。它包含约束极强的指令，突出 grounding 类任务，如问答和摘要。要求主要聚焦格式、语气和 grounding，以及各类专门要求。

数据集中的一条示例：

Instruction：

*假设你是一位帮助专业人士成为领导者的商业教练。做一个概述。*

Requirements：

- 用 50 个词回答
- 只概述输入文本中关于倾听的内容
- 每当出现 leader(s) 或 manager(s) 时用斜体书写
- 输出中不要提及任何具体的人

可以看到，指令并没有按特定格式书写；要求的措辞也相对宽泛，可以涵盖从长度、风格到内容的各种规定。

我们在该数据集上用两个指标衡量质量。第一个是"要求满足度"（requirement satisfaction），衡量有多少要求被满足。下图展示了数据集中所有样例里 fulfilled 要求的百分比（验证使用 LLM 作为裁判）。即便对 o3 这样原始分数已经很高的先进模型，Maestro 仍能带来显著提升。

第二个指标是"accuracy"，更严格：我们统计所有拿到满分的样例（即全部要求被满足）。可以看到基线表现与 Maestro 增强后的结果之间存在显著差距。

我们还做了人类评估。专业人员以方法论流程进行盲评，衡量满意等级：非常满意、比较满意或不满意。下面可以看到，与单次调用 gpt-4o 相比，Maestro 大幅提高了"非常满意"的比例，同时显著降低了"不满意"的比例。

## 结论

Maestro 通过智能任务规划和显式要求定义，赋予开发者对 LLM 输出前所未有的控制力。通过动态规划最佳行动序列、把指令与要求分离，我们创造了一个在复杂任务上始终超越最先进模型的系统。

少花时间做 prompt 工程和工作流设计，多时间做真正重要的构建。数据不言自明——Maestro 交付更高质量、更能满足你特定要求的输出，同时通过智能规划优化你的算力预算。
