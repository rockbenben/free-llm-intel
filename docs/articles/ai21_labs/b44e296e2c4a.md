ChatGPT 发布、展示大语言模型（LLM）惊人能力至今已近两年。紧随其后，GitHub Copilot 问世并迅速成为现代程序员的必需品。我们每天都在听说各家公司开发 AI、推出无数个 beta 版本。

然而，ChatGPT 和 Copilot（以及它们的竞品）主要被懂技术的用户所用——这些人能盯得住 AI 生成的输出。虽然我们偶尔会听说组织内部的用例——潜在损害极小——但作为一名普通终端用户，我的姑妈仍然在等更多实用的功能。她想要 WhatsApp 或 Facebook 信息流的自动摘要、Gmail 的自动邮件撰写、Spotify 在收听前给出播客亮点、Netflix 问几个偏好问题来推荐影片。

这些用例任何人都想得到，哪怕毫无 AI 专业知识；它们共同点是按理不需要微调、检索增强生成（RAG）或 agent 这类高级技术——只要打磨好的 prompt 就行。十分钟内就能为它们做出 PoC，但近两年过去了，这些功能一个都没有。[华盛顿邮报](https://www.washingtonpost.com/technology/2024-04-18/ai-bubble-hype-dying-money/)的一篇文章甚至声称炒作的泡沫正在泄气。

***那么，究竟是什么阻止 AI 被整合进我们今天要用的每一款软件产品？***

**不是延迟和成本的问题：**与普遍认知相反，LLM 相当便宜。例如，J.K. 罗琳花了 17 年写完整个哈利·波特系列，GPT-4 只需几个小时、大约 15 美元。放到商业语境里：电商店铺的一条产品描述通常要花几小时、公司成本 10-20 美元，而 AI 只需几秒、一美分。

**不是幻觉的问题：**虽然幻觉起初是 LLM 的主要毛病，但检索增强生成（RAG）等进展已[大幅降低了其出现频率](https://www.ai21.com/research/in-context-retrieval-augmented-language-models)。此外，现代 LLM 经常会在信息不足时主动表明，使公然幻觉变得罕见。有了护栏这类交叉核验内容的机制，加上这些模型带来的巨大价值，剩余的幻觉风险是可控的。只要向用户清晰传达潜在的不准确之处，我们就能负责任地利用 AI 之利，同时让用户知情并保持警惕。

## 障碍到底是什么？

作为世界头部 LLM 公司之一的解决方案负责人，过去两年我有机会与许多客户合作，了解了拖慢这项技术采用的种种缺口。以下是我学到的：

### 1. 认知缺口

人们常常高估 AI 的能力。例如，GPT-4 尽管精密，[连"strawberry"里有几个 'R' 都数不清](https://www.inc.com/kit-eaton/how-many-rs-in-strawberry-this-ai-cant-tell-you.html)。ChatGPT 这个产品带着联网搜索、图像分析等附加能力，营造出"所有 LLM 都能完成复杂独立任务"的幻觉。我服务过一个客户，部署了一个模型并期望它用常识、图像和互联网数据交叉核验输入，一旦发现潜在不一致就警告用户。然而，没有显式指令和带 function calling 支持的恰当应用层，LLM 自己做不到这件事。即便是已经玩过 LLM 的技术型用户，仍认为需要用自家数据微调模型才能跑通自己的用例。其实模型微调通常既耗资源又非必要。相反，prompt 工程是更高效的方式，能在不改动模型的前提下定制其响应。

### 2. 产品创造力不足

尽管高管们把 AI 视为游戏规则改变者，他们的团队却常常困在常规思维里，无法充分释放其潜力。产品经理们往往死守聊天界面——很大程度上是 ChatGPT 的成功使然——但不是每个产品都需要依赖聊天。想想 Microsoft Excel：直观的 GUI 让用户通过简单点击和单元格选择完成复杂任务。如果换成聊天界面、要你逐格用文字描述，一个直白的任务就会变成令人抓狂的"猜战舰"。对于功能明确的产品，聊天可能碍事多于帮忙。这就是为什么即便 ChatGPT 如此全能，用户依然喜爱 [Wordtune](https://www.wordtune.com/) 这类界面友好的 AI 工具。

### 3. 数据隐私顾虑

LLM 依赖 prompt 里的数据运作，但 GDPR、HIPAA 等严格隐私法规阻止公司把敏感信息交给第三方。本地部署方案解决了量大、算力和硬件充足公司的这一问题，而较小的公司可以考虑把私有化部署放在自己的 VPC 里——一个更节约成本和资源的选择。Amazon Bedrock 这类云端工具虽然把数据留在客户环境内，但尚未完全成熟，处理 RAG 这类复杂任务时尤其如此。结果是公司被迫等待：要么等这些工具进化，要么在冗长的第三方供应商审批流程里跋涉。

### 4. 技术缺口

虽然幻觉大体得到治理，LLM 仍因其非确定性本质面临问题——管理一个每次答案都略有不同的产品是困难的。例如，要求模型输出 JSON，可能得到格式各异的返回，让响应解析几乎不可能。可解释性也是关键：模型为何选这个响应而不是那个，常常无从知晓，拖慢开发。此外，把复杂任务交给 LLM 很棘手，尤其当准确性至关重要时。比如我让模型生成一条 SQL 查询，一个用 ">" 代替 ">=" 的小错就可能导致错误答案。想象问"迪士尼自 2020 年以来发了多少部电影？"，因为这个错误你得到 117 而不是[正确的 139](https://en.wikipedia.org/wiki/List_of_Walt_Disney_Studios_films_(2020%E2%80%932029))。看不到生成的查询，用户就无法核验答案，方案的可靠性因此受限。

### 5. 评估挑战

评估文本是个苦差事。尽管有无数的自动 benchmark、天天发布在 benchmark 上超越对手的新模型，但当涉及"这个模型对我的用例是否合适"时，没有任何东西可以替代人工抽样一大批有代表性的问题、逐一审阅答案，看输出是否达到期望标准。但这通常是客户挣扎最厉害的地方。在经典机器学习中——无论分类还是回归——都有相对简单的自动化方法检查模型准确率。但在 LLM 上没有魔法方案，必须下足功夫，直到确信解决方案足够好。

### 6. 期望与时间表

AI 整合最大的挑战之一是期望与现实的落差，尤其体现在时间表上。有了 LLM，做一个 PoC 只需五分钟，于是客户期待几周内就有一个功能完备的产品。然而，把 PoC 推进到生产级方案，需要全面的规划、开发和测试。它不只是把 LLM 配上 prompt 端给终端用户——和任何应用一样，构建 AI 应用需要：仔细定义输入、输出以及二者之间的关系；定义指标、收集数据；把任务拆分成模型更容易完成的小子任务；实现每个组件并把它们彼此以及与别的系统、工具集成；确保方案满足特定用例要求；并对它做彻底测试，以在各种场景中准确、一致地应对。每一步都对确保方案可靠、安全、持续交付价值至关重要——但五分钟 PoC 与漫长开发之间的反差，会侵蚀客户对这项技术的信任。

回到起点——这项技术变得可用且广为人知已两年，我的姑妈仍在等她的功能。投资人多半也会失望，按他们的预期现在就该有回报了。然而，没有任何新技术在两年内成为主导——互联网没有、社交媒体没有、云计算也没有。所以，哪怕这真是一个即将破裂的泡沫，事实是：即便破裂，技术也会留下来，一如当年的互联网泡沫。它在这里，是因为它已经带来真实价值——毕竟，它帮我写下了这篇文章。
