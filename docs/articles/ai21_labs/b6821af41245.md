### 太长不看

在用 GRPO 训练我们的 Jamba 3B 模型时，我们撞上了一个诡异的 rollout 与训练之间的 logprob 不一致。根因最后被证明是深埋在 vLLM 一个 CUDA kernel 里的静默整数溢出——只在 cache 槽位数超过约 47,935 时才会触发。修复只差两个字符。找到它的旅程却毫不轻松。

调试强化学习系统最棘手的部分之一，是 bug 几乎从不主动自我介绍。

在基于人类反馈的强化学习中，正确性是承重的，且未必可见。一个常见的健全性检查是：对比 rollout 引擎赋给自家补全的对数概率，与刚刚加载的训练模型在同样序列上算出的对数概率——在任何权重更新发生之前。健康的系统里，两者应几乎相同：同样的权重、同样的输入、同样的数字。它们一旦分道扬镳，就是一个金丝雀信号：上游已经出了错。

最近，在为 Jamba 3B 模型搭建 GRPO 训练环境时，我们恰恰撞上这类问题。[Jamba](https://www.ai21.com/jamba/) 是 AI21 的注意力-Mamba 混合模型——一个把标准注意力与 Mamba 状态空间层结合的 3B 参数架构。正是这种混合属性（下文会看到）让这个 bug 如此难寻。训练技术栈包括：用于编排的 Ray、带 FSDP 做权重更新的训练路径，以及一条 rollout 路径——通过 vLLM 生成补全、并用我们的内部评估服务打分。我们看到的是 rollout 与 FSDP 侧之间的对数概率不一致。乍看之下，无从判断问题来自训练、推理、同步，还是来自它们交互中某个更微妙的地方。

剧透：它是深埋在某个 CUDA kernel 里的一次教科书级无符号整数索引溢出。**有趣的是旅程**，不是终点，所以我们深挖一下。

## 第一个问题：bug 到底住在哪一层？

在这样的系统里，GRPO 并不是一个东西，它不是你平常的 model.fit()。它是由若干界限分明的阶段组成的管道，每一层都有自己的假设：

- rollout 生成
- 基于 FSDP 的训练
- 通过 Ray 的分布式协调
- 推理时组件与训练时组件之间的交接

典型的 GRPO 训练流程如下图所示：

图 1：使用 vLLM 与 FSDP 的典型 GRPO 训练循环。vLLM 负责 rollout 生成并计算 log π_old；FSDP 模型在任何权重更新前对同样的补全重算 log π_train。两者之间的平均绝对差（健全性检查，对吧）在每轮迭代开始时应当约等于 0。

当 vLLM 引擎的 logprob 与 FSDP 中刚加载模型的 logprob 之间开始出现尖峰——在任何权重更新之前——本能的诱惑是把所有东西一起检查一遍。但那通常毫无出路。在分布式 RL 系统里，如果不激进地收窄搜索空间，你最终调试的是整个技术栈，而不是那个 bug。

于是真正的任务变成：能否判断这个问题属于 rollout 侧、FSDP 侧，还是中间的权重同步？

传统调试智慧说：找到一个能以受控方式扰动系统的超参数，观察症状是否随之移动。

## **找到那个杠杆**

观察 logprobs 差值的行为后，一个关键发现是：尖峰并非随机。它们周期性出现——以固定间隔反复破坏与恢复。按我们的默认实验配置，尖峰直到大约第 12 步才出现，这带来的疑问比答案还多。

图 2：vLLM rollout 与 FSDP 重算之间平均绝对 logprob 差（rollouts_num=8，默认配置）。尖峰呈周期出现——大约每 12 步一次——而非随机，暗示这是一个有结构的、反复出现的误差源，而不是训练噪声。

查看那些步骤前后的模型 rollout，有一些乱码补全，但并非全部。我们取出这些步骤的权重，试图在独立的 vLLM 实例中复现问题。生成看起来完全正常。死胡同。

随后我们开始有条理地搜寻"杠杆"。灵光一现来自这样的实验：把每个 prompt 的 rollout 数翻倍——8、16、32，直到 128——我们发现尖峰的周期与该数字严丝合缝地联动。整个调试叙事由此彻底改写。

如果 logprob 差值的尖峰按与 rollout 数量绑定的模式移动，那么这个 bug 极不可能是 FSDP 训练的某种通用不稳定。症状是被 rollout 行为"结构化"出来的。这还不能完全证明 bug 的位置，但给了你一个锋利得多的假设：问题很可能在训练路径消费数据*之前*就被引入了。

**那是转折点。**

图 3：尖峰周期与 rollouts_num（8、16、32、64、128）的函数关系。随着每个 prompt 的 rollout 数增加，尖峰在训练中提前触发。rollouts_num=128 时，第一步就触发尖峰——一个关键的诊断信号，把嫌疑从训练动力学移向 rollout 路径本身。

## 从"训练不稳定"到"可复现的 rollout 问题"

在那个观察之前，问题看起来像个 RL 训练 bug；之后，它更像一个恰好浮现于 RL 训练期间的 rollout 路径 bug。

这个区分非常重要。一次完整的 RL 训练是调试底层正确性问题的糟糕场所：层次太多、异步机制太多、原始信号被模糊掉的地方太多。理想的调试路径永远是逐层剥离，直到问题存活在尽可能小的环境里。

于是目标变成：把问题从"GRPO 训练期间有什么不对"压缩为"我们可以按需复现，在尽可能早的 rollout 上复现"。

下一个里程碑是让问题在第零步复现——细看那张图，每个 prompt 128 次 rollout 的那条曲线在第一次 rollout 就出现尖峰。

图 4：不同 rollout 数下第一步 logprob 差的放大视图。rollouts_num=128（绿色）时，差值在第一步就达到约 0.11——证实 bug 在任何训练状态累积之前就已存在，并使第零步复现成为可能。

这是一次巨大的化简。一旦 bug 在最早的时机就出现，你不再需要推理优化器历史、训练漂移、奖励效应、梯度累积或长程 RL 动力学。**你调试的不再是学习，而是执行**——这是一个好对付得多的问题。没有需要交代的累积训练状态，没有需要理清的后段 RL 动力学。只有一个确定性的失败，按需重复，小到足以妥善插桩。

在我们的场景里，抵达第零步意味着：第一次 rollout 的 logprob 与 FSDP logprob 之间的差距（先于任何权重更新）让我们把问题从完整 RL 工作流中剥离，隔离进底层的推理路径。我们此前只用 vLLM 复现的尝试之所以失败，是因为我们采样了正常数量的补全（8 或 16）。这个 bug 需要规模才会露头。一个始于 VeRL/GRPO 的调试问题，本质上变成了推理引擎的调试问题。

这正是系统调试中你想要的转变：从一个复杂的涌现症状，到一个最小、确定性的复现。手握独立复现脚本后，我们有条不紊地继续收窄，又发现了另一个杠杆：vLLM 的 GPU 内存利用率参数。把它降到 50% 可完全避开问题；超过该值则稳定复现。现在我们知道它与 vLLM 内部缓存分配预算有关。

在我们的 Jamba 案例中，由于它是注意力-Mamba 混合模型，嫌疑人要么是注意力 KV-cache，要么是 Mamba 状态缓存。

再用一个纯注意力模型跑一次消融，问题没有出现——这排除了 KV-cache 的嫌疑，把爆炸半径限定在 vLLM 内部 Mamba-1 的 CUDA kernel 上。

## Bug

它住在 selective scan CUDA kernel 的指针算术里。一旦你看到它，就知道这不是那种你会欣赏的 bug，而是那种因为它藏得实在太安静、让你不得不带着几分不情愿去敬佩的 bug。`SSMParamsBase` 结构把 `index_t` 定义为 `uint32_t`，所有步长字段——包括 `ssm_states_batch_stride`——都继承了这个类型。在 kernel 中，每个 batch 的 SSM 状态基址由 cache_index（一个 `int`）乘以 `ssm_states_batch_stride`（一个 `uint32_t`）算出。由于两个操作数都是 32 位类型，乘法在运行时按 32 位算术执行，一旦结果超过 `UINT32_MAX` 就静默回绕。当 batch 步长为 89,600 个元素时，只要 `cache_index` 超过约 47,935，乘积就溢出 `UINT32_MAX`。在我们总计 69,776 个 cache 槽位的配置下，约 31% 的槽位受到影响——kernel 正在把 SSM 状态写到错误的内存位置，而本应写入的槽位保持全零。

想想这意味着什么：**你的缓存有 31% 在静默地烂掉**。没有崩溃，没有警告。只是错误的数字穿越整个训练，表现为一个从外看像"训练不稳定"的 logprob 失配。

修复如下，见这个 vLLM 上游 [PR](https://github.com/vllm-project/vllm/pull/35275/changes?diff=unified)：

```
struct SSParamsBase {
-     using index_t = uint32_t;
+     using index_t = size_t; 
```

把 `index_t` 拓宽为 `size_t`——在该 kernel 里编译为 `uint64`——确保所有步长乘法使用 64 位算术。数周的调查，两个字符的改动。

图 5：Mamba-1 selective scan CUDA kernel 中的指针偏移溢出。当 cache_index × ssm_states_batch_stride 超过 UINT32_MAX（约 42.9 亿）时，32 位算术静默回绕。batch 步长 89,600 时，超过 47,935 的索引就会溢出——影响 69,776 个总缓存槽位中约 31%，它们收到被腐蚀的 SSM 状态写入，而本应的槽位保持清零。

## 真正的调试经验

技术问题本身当然重要，但更大的教训是方法论上的。

调试 RL 系统——尤其是分布式系统——最难的部分往往不是修复 bug，而是为它找到正确的边界。

真正推进局面的有几件事，值得精确点名。

- 最有用的一个：**寻找能改变失败"结构"的变量**，而不仅是它的量级。增加 rollout 数不只是放大了误差——它改变了尖峰的间距。这个结构性变化比更响亮的误差信号信息量大得多。它告诉我们失败是被 rollout 过程本身组织起来的，直接指向了该看哪里。
- 抵制"调试整个训练"的冲动。改为追问：管道内存在哪些相互独立的子系统，如何隔离地施压于它们。
- 一旦有了方向性假设，全力奔向最小复现。如果 bug 能在第零步复现，就不要再在 500 步的 RL 运行里追它。

## 收尾的思考

在分布式 RL 系统里，Ray、FSDP、rollout worker 和训练循环能让一个相当局部的 bug 看起来像系统级故障。这正是这类系统调试充满迷惑性的原因：可见的症状往往更多反映 bug 周围的架构，而非 bug 本身。本案中的解药，是抵制把整个技术栈当成不可透的魔法，转而用系统自身的结构反制它：改变一个维度、观察失败的形状、追问哪个组件能产生这种模式。这把一个模糊的对数概率失配变成了一次有的放矢的调查。

对我而言，这是 RL 基础设施工作中最被低估的部分之一：调试过程往往和训练算法本身一样有趣。一次好的调试不仅是找出坏在哪里，而是把一个庞大、分布式、多组件的问题收缩成小到足以清晰推理的东西。本案的路径从 GRPO 训练开始，到 rollout 对 FSDP 的怀疑，到与 rollout 相关的周期性，到第零步复现，最后把问题隔离进推理引擎。正是这一递进的化简让 bug 变得可解——说实话，也正是它让这类工程工作充满乐趣。
