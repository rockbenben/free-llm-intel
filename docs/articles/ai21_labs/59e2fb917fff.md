用测试时计算（test-time compute，TTC）扩展 agent，在很大程度上依赖并行运行多条推理路径。AI21 Maestro——我们的 TTC 优先（TTC-first）agentic 框架——正是围绕这一理念构建的：AI21 Maestro 并发执行多条轨迹（trajectories），探索不同方案并选出最佳结果。

这种方式在只读任务上已被证明非常有效，例如基于内部知识库回答复杂问题。但当我们把 AI21 Maestro 用到代码上时，撞上了一堵硬墙：并行 agent 在"想"的时候配合良好，一开始"做"就崩了。只要多个分支能编辑同一批文件、修改共享状态或触发外部副作用，冲突就出现了：

- 多个 subagent 在同一代码库上工作会产生相互冲突的变更
- 两个 agent 同时编辑会让文件损坏
- 我们需要一个干净的机制，在试出糟糕策略时回滚

这些问题必须解决，才能充分发挥 AI21 Maestro 执行引擎（Execution Engine）的能力。其根源并非某个框架特有的问题，而是一个结构性问题——想让"会行动"的 agent 受益于测试时计算，就必须解决它。这一挑战不限于编码，同样的问题横跨多个领域：

- **数据库 agent**执行 schema 变更，需要安全的回滚
- **文档 agent**做出可能相互覆盖的编辑
- **基础设施 agent**开通云资源，可能留下配置了一半的环境

*模式是普适的：只读的 agent 可以共享一个环境；写入的 agent 需要隔离。*为了正确地扩展和并行化 agent，我们意识到必须扩展 MCP 协议，让它适配 TTC 时代。

## MCP 缺失的一层

对于编码任务，AI21 Maestro 的 agent 要做的不只是提议编辑，它们必须执行：跑 shell 命令、编译、运行测试、检查输出。我们用 MCP（[Model Context Protocol](https://modelcontextprotocol.io/)）来处理这些工具调用。MCP 是把 AI agent 连接到外部能力的事实标准，也把工具执行处理得很好。但 MCP 对其运行所在的执行上下文没有任何约定。MCP 告诉你一个工具做什么、如何调用，而不是*在哪里*运行、与其他调用共享什么状态。

这对只读 agent 没问题。但当 agent 开始修改状态时，"环境"也成了共享的可变状态。在我们的场景里，subagent 不只是读文件：它们在写文件、运行格式化工具、生成构建产物、编辑配置，然后做经典的"改代码跑测试"。如果两个 subagent 在同一工作目录里这么干，混乱就开始了：一个 agent 的 git checkout 让另一个 agent 的测试运行作废；一个 agent 的依赖更新改变另一个 agent 的构建；临时文件互相碰撞。

并不是系统层面缺少隔离：多数领域早已有了创建"安全沙箱"的办法。Git 可以用 worktree 分叉工作副本；数据库可以用事务隔离变更；文档可以借版本历史开分支。问题在于 MCP 没有办法"命名"这种隔离上下文，也没有办法把它跨工具调用携带下去。

MCP 告诉 agent *能*做什么。我们需要的正是缺失的一块：这些动作发生在*哪里*。具体说，就是隔离的工作区（workspaces），让多个 subagent 可以并行运作而不互相踩脚。我们的解法是给 MCP 扩展出一个 Workspace 层：一组原语（primitives），任何会改变状态的 agent 都可以借此获得隔离，而无需重写自己的工具。

### MCP workspace 层

对我们来说，在协议层面做这个改动很重要。因为不同的问题需要不同的工作区抽象，协议只定义操作，各领域自行选择操作背后的隔离机制。这让不同的 MCP 客户端能够以适合自己环境的方式实现工作区隔离，同时共享同一份契约。

我们设计了五个与领域无关的原语，覆盖任何状态变更上下文的生命周期：

要为 agent 提供工作区隔离，接口保持不变；变的只是底层实现。

## 我们的实现：基于 git worktree 的编码 agent

一旦在协议层面定义了工作区原语，挑战就转向 MCP 客户端应如何在实践中实现它们。从负责执行工具的客户端视角看，工作区隔离必须具体、高效，并与既有开发者工作流兼容。对编码 agent 而言，这化为几个要求：fork 要足够快——一次运行中要分叉几十次；留存要足够便宜——测试执行期间得让它们一直存在；可合并、可 diff——因为 compare 和 merge 是一等原语。这很快收窄了选项。

我们最终选择了 git worktree。几天后，我们欣慰地看到 Cursor 团队发布文章，说他们采用了同样的做法。

Git worktree 恰好给了我们所需要的一切：

- **近乎即时的工作区创建：**启动一个新 checkout 只需毫秒
- **内建变更追踪：**每个工作区映射到一个分支
- **原生合并能力：**把胜出分支合回来，不需要定制的胶水代码
- **低磁盘开销：**Git 对象在各 worktree 间共享

选定 worktree 后，它与我们的工作区原语几乎 1:1 对应，"协议 vs. 实现"的故事就这样咬合上了。

## 这解锁了什么

工作区隔离不只是防止碰撞，它改变了测试时计算与多 agent 系统在状态变更任务上的应用方式。

1. **并行 subagent 执行**

多个 subagent 可同时工作而互不干扰。每个都有自己的工作区，并发从此是默认项，而不是特例。

2. **推测式求解**

并行跑多种策略，丢弃失败者，合并胜出者。agent 不再被迫押在单一路径上，它可以探索解空间，而不是过早承诺。

3. **安全的实验**

回滚就是一个删除操作。失败的尝试只是扔掉的工作区。这消除了畏惧心理，让大胆实验变得廉价。

4. **一个领域无关的模式**

我们定义的工作区原语并不限于代码。同一模式可以在各领域催生新的 agent 架构：

普适模式是：`initialize → work in isolation → compare → merge or discard`。任何 agent 会变更状态的领域，都可以用自己的隔离机制（事务、快照、版本历史等）实现同一接口。

## 成果与展望

当我们着手把知识智能体变成编码 agent 时，撞上了一个根本缺口：会修改状态的 agent 需要隔离，但协议层没有表达方式。于是我们用五个工作区原语扩展了 MCP：`initialize`、`clone`、`merge`、`compare` 和 `delete`。它们与领域无关，凡是 agent 不只读状态、还会改变状态的地方都适用。

对我们以 git worktree 实现的编码 agent，效果立竿见影：从 1 种主动方案到 16 路并行尝试，零协调开销——因为每个 subagent 都在自己的工作区里干活。更大的故事是这个模式所解锁的可能：跨领域安全地探索、实验和修改状态的多 agent 系统。

MCP 标准化了 agent 调用工具的方式，但把有状态执行留在了隐含层面。当 agent 从"读"走向"写"和"行动"，这个缺口就从偶然变成了结构性。工作区原语为"agent 动作如何与状态交互"定义了共享契约，同时把实现选择留给客户端。既然这属于本该由协议层承担的职责，我们希望在官方 MCP 协议中扩展这一能力，让安全、隔离的状态变更成为标准能力。

如果你正在构建会触碰状态的 agent（代码、数据库、文档、基础设施），请考虑为你的领域实现工作区原语。隔离的模式是普适的，隔离的机制由你来选。
