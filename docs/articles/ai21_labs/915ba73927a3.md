太长不看

AI21 Maestro 是一个通用 agentic 框架，能自动扩展算力并优化编排。我们展示它如何通过结构化计划、自动水平扩展和决策论优化技术，显著提升模型在 SWE-bench-verified 上的表现。

## 引言

随着 agentic 任务变得更复杂、执行方差更大，核心挑战变成：如何在庞大而漫长的轨迹之间高效分配测试时算力（test-time compute，TTC）。

推理模型是对这一问题较早的回答。这些模型动态分配更多 token 来"思考"，以更好地选择自己的轨迹。随后，"best of N"（同样用更多算力换准确率）或"agent/模型路由"（学会把问题路由给能解决它的最便宜模型）等策略也加入了 agentic 游戏，并在许多用例中证明了价值。

这些技术虽有用，却有两个短板：

- **它们依赖"黑箱编排"：**当前策略把每次运行当作一个封闭单元，而不是协同团队的一部分。这些运行像待在各自房间里的人，对彼此的进展一无所知，只能在执行结束后被评估。
- 它们只训练一次，之后在推理时按"在训练集上平均表现最好"的策略应用。这意味着它们不仅承受训练数据分布与推理时分布之间的偏移，而且系统每接入一个新模型、新 agent、新 prompt 或新工具，都需要整体重训。

升级到更强的模型无法解决这些根本缺陷，因为其底层限制是架构性的。我们认为，要解决这些问题需要**结构化的 Test-Time Compute 机制**——具体说，是在执行期间显式且自适应地分配资源、从而在资源约束下提升准确率的系统。

AI21 Maestro 正是这样一个通用 agentic 框架。它把关于编排的决策从 LLM 推理本身中分离出来，从而对长程多步任务实现更好的控制。为了展示其威力并解释部分原理，我们来看它对 SWE-bench 任务的影响。

**[**[我们在 200,000+ 次 SWE-bench 运行中评估 agent 学到的经验](https://www.ai21.com/blog/scaling-agentic-evaluation-swe-bench/)**](https://www.ai21.com/blog/scaling-agentic-evaluation-swe-bench/)**

## 把 AI21 Maestro 应用于 SWE-bench

SWE-bench-verified 是最知名的 agentic 代码 benchmark 之一。它的任务需要几十甚至上百步，放大了诸如 agent 卡死、或解决简单问题代价高昂这类问题。带有专门逻辑和定制工具的专用 SWE agent 曾长期霸榜，但近期的前沿模型已经追上来——用简单 bash 工具的"朴素"执行几乎追平了那些量身定制的 agent。

为了公平评估 AI21 Maestro，我们采取如下做法：只给 Maestro bash 权限（以及 LLM），并与 mini-swe-agent——SWE-bench 官方发布的基于 ReAct 的 agent——在相同模型和相同 bash 工具下对比。我们专门用 GPT-5 和 GPT-5 mini 测试了 AI21 Maestro，但同样的方法和收益可以推广到其他模型。

粉色条形是运行 AI21 Maestro 的结果，其余全部是 SWE-bench 上的公开成绩。

如上图所示，AI21 Maestro 显著提升了 GPT-5 和 GPT-5-mini 的表现。事实上，有了 Maestro，GPT-5 达到了 Claude 4.5 Opus 和 Gemini 3 Pro——公开成绩中的顶尖选手——的总体水平。

为了理解提升从何而来，我们聚焦 Maestro 的三个组成部分（还有其他，我们将在别处展开）：

- 水平扩展
- 结构化计划
- 探索动作空间

## 组件 1：用水平扩展获得更好的成本/准确率

正如若干专用 SWE agent（例如 TRAE）已经展示的：只要能可靠地识别最佳输出，水平扩展更便宜的模型可能比使用更强更大的模型更具成本效益。下图清楚展示了这种权衡：并行跑 8 条 gpt-5-mini 轨迹，比单跑一次 gpt-5 得分更高、成本更低。但还剩两个挑战：(a) 自动地、且仅在有价值的时刻扩展；(b) 选择正确的轨迹。

每个模型在 1、2、4、8 次并行运行下的 resolved 条目百分比与条目中位成本，假设存在一个能选对答案的 oracle reducer。成本按 OpenAI 公开 API 价格计算。

Maestro 解决第一个挑战的方式，是从底层就以 Test-Time-Compute 为理念构建。Maestro 考虑的每个"分支"都内建了预期成本与价值的建模，依据或是离线仿真学到的先验，或是开发者的手动输入。这样，开发者无需手工编码并行执行工作流并在其间做优化，而是让 Maestro 在可能时基于预算自行并行。

每当 Maestro 分叉，它都对那些轨迹保持完全的观测与控制。分支结束时运行校验器（Validators），再由 Reducer 从各分支中混合/挑选最终候选。这意味着 Maestro 可以叫住卡死的 agent，或在某一条分支成功完成后终止所有仍在运行的分支——开发者不必为此写任何定制代码或逻辑。Maestro 的执行引擎内建了对"即便包含状态变更动作"也能并行的支持，否则朴素的并行执行会造成写入冲突与状态不一致。仅这一项就带来巨大的收益与潜力，分数已经说明。

## 组件 2：结构化计划的力量

今天多数通用 agent 都是 ReAct 框架的后裔：围绕原始 prompt 和 ReAct 式循环构建的 agent。规划、决策与执行全部经由 token 生成中介——何时继续、重试、分叉或停止这类选择，是从下一个 token 的预测里推断出来的。模型把整个控制流编码在自己的文本上下文里，这让 agent **看起来像一个程序，行为却像一个随机过程**——成本、延迟和准确率的方差都很大。

数据集中每个条目的成本在 16 次运行中测量，并为每个条目计算变异系数（CV = std/mean）。箱线图展示 CV 在数据集上的分布。GPT-5 与 GPT-5 mini 的方差都很高、分布相似，无论成功还是失败的运行。

来看 mini-swe-agent 定义的 ReACT agent 的 prompt。它很简单，概述了解决任何 SWE 任务的基本步骤：

```
## Recommended Workflow

This workflows should be done step-by-step so that you can iterate on your changes and any possible problems.

1. Analyze the codebase by finding and reading relevant files
2. Create a script to reproduce the issue
3. Edit the source code to resolve the issue
4. Verify your fix works by running your script again
5. Test edge cases to ensure your fix is robust
6. Submit your changes and finish your work by issuing the following command: `echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT`. Do not combine it with any other command. <important>After this command, you cannot continue working on this task.</important>
```

从 TTC 的视角看，这些步骤并非生而平等。有些步骤大概更复杂，值得投入更多资源；有些是只读的，因而更容易并行；另一些则会改变仓库状态。与黑箱的 ReAct 型 agent 不同，AI21 Maestro 使用以 AI21 Maestro 计划定义语言（Plan Definition Language，PDL）写成的**结构化程序化计划**，支持独立步骤并行执行，以及**步骤级**的动态 TTCS（Test-Time Compute Scaling，测试时算力扩展）。

为了明智地编排这些轨迹，Maestro 使用以 AI21 Maestro 计划定义语言写成的**结构化程序化计划**。这些计划由用户编写或由 Planner 模型动态生成，把任务逻辑分解为离散步骤，同时把每个步骤内部具体的编排与 TTCS 决策抽象出去。它们把基于文本的推理/ReACT 轨迹替换成可编译、可解析、可编排的代码。

除并行和步骤级 TTCS 外，Maestro 的结构化计划相对 ReAct/推理模型式 agentic 计划还有这些关键优势：

- 显式的数据与控制流：Maestro 的结构化计划以代码书写，可以规定数据依赖、控制流、变量、条件及其他"胶水代码"——这些都是自由文本办不到的。
- 更好的可解释性：plans 短小、以层次化代码表达，容易理解——无需再去调试一条 40K 长的推理链。
- 计划强制执行：推理模型和 ReAct agent 容易卡死或偏离原计划。有了结构化计划，即便在长轨迹中执行也能被强制和掌控。
- Python 原生：不同于某些使用私有流程表示的框架，现代 LLM 对 Python 相当娴熟，因此模型无需专门训练就能产出出色的 PDL 计划。
- 设计即安全：由于模型可以在运行时创建计划，PDL 被限制在定义计划所需的最小语法内。模型生成的计划不能 import 库或执行其他不安全操作。

对于 SWE-bench，我们评估了两种结构化计划变体：第一种是**用户创建的**计划，复刻 mini-swe-agent prompt 中描述的同一工作流；第二种是一个在运行时为每个条目动态规划的 planner 模型。

两种结构化计划方法的示例：左边是用户定义的、把 mini-swe-agent prompt 里整个 benchmark 共用的那份计划的结构化版本；右边是 Planner 模型动态生成计划中某一部分的 2 个示例。

即便在单条轨迹上，两种方法都显示出对同模型 ReAct-based agent 的优势。而当我们在水平方向扩展时，可以看到结构化计划的提升速率更高。

在 GPT-5 mini 之上，每种规划方法在 1、2、4、8 次并行运行下的 resolved 条目百分比，假设存在一个能选对答案的 oracle reducer。

运行时差异可以在抽样一个数据集条目、观察其轨迹时看到。下图中，我们看到 ReAct agent 过早迎来一个虚假的"顿悟"时刻，在没有建立对问题的充分认知时就着手打补丁，随后在"修复-测试"之间循环却始终无法解决。相比之下，结构化执行在前期投入更多精力构建上下文和编写测试，这最终让它成功了。

左侧：benchmark 某个样例样本上，不同步骤在主要计划部件间的分布。ReAct 的步骤是人工阅读其输出后划分的。右侧：预定义计划在整个 benchmark 上分配到各主要计划部件的步骤总体分布。

## 组件 3：探索动作空间

在前面各支柱之上，Maestro 此刻在每个瞬间都拥有一系列可执行的动作：选择横跨不同模型、不同成本画像的 agent（常常并行运行）、使用多模型的规划与基于计划的轨迹，以及在校验、剪枝或终止执行路径上随局势展开的机制。挑战在于：给定目标与资源，如何最优地导航这个动作空间——决定采取哪些行动、何时采取。

AI21 Maestro 不是去优化单一的"最佳"平均动作，而是组装一组互补动作的组合（portfolio），共同覆盖问题空间。实践中，一群各有擅长的中等表现 agent 组成的多样化集合，会胜过少数几个收敛到同一解的最先进 agent。真正的挑战在于高效地在其中做选择与编排。

做得得当，这应当能缩小"单个 agent 所能达成的"与"最优编排器会选择的"之间的差距：即每个任务上能成功的最廉价执行。这种方法不靠扩展模型规模或 thinking token，而是更高效地使用既有能力，从而移动 Pareto 前沿。

每条灰色线代表单轨迹的准确率（含 GPT-5 家族不同模型、Maestro 结构化方式），以每条目美元上限为约束（x 轴）。粉色线代表最优编排器在任意成本下选择最佳动作的准确率。

## 总结

AI21 Maestro 是一个编排框架，提供对长程 agentic 流程自动化、细粒度的优化。它是通用型的、普适的，但为了展示威力，我们演示了它如何提升 SWE-bench 上的表现。我们还描述了 Maestro 中支撑这些表现的一些要素：水平扩展与自动智能并行、基于 Python 的结构化计划，以及用决策论优化技术探索庞大动作空间。
