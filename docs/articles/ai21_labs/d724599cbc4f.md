## 简要说明

executor-orchestrator（执行者-编排者）架构作为节省前沿算力的方式近期重新受到关注。在那种架构中，由前沿模型评估任务、制定计划，并在更小、更便宜的执行模型之间进行编排以获得解决方案。我们认为，通过审视整条管道的构建方式，节省的空间还可以更大。

在我们的方案中，**先调用便宜的模型来处理 token 量大的上下文探索和提取，并针对呈现最高质量的上下文做优化**。等到最后调用前沿模型时，它已手握完整上下文，只需一次调用就能写出正确的补丁。

正是这一架构，让我们以**每任务仅 5.99 美元**的开销，在 [SWE-Bench Pro](https://labs.scale.com/leaderboard/swe_bench_pro_public) 上达到了 **80.8% 的 resolve rate** 这一 SOTA 水平；相比之下，其他混合方案——如 [Fireworks AI 最近的 worker + advisor 实验](https://fireworks.ai/blog/frontier-open-source-worker-with-closed-source-advisor)——在追求省钱的过程中牺牲了质量。

## **实验设置与基线**

我们采用标准的 coding-agent 基准测试设置，详见[我们此前的工作](https://www.ai21.com/blog/first-scale-then-enrich-how-the-right-execution-strategy-helped-us-reach-state-of-the-art-on-swe-rebench/)：agent 接收一个自然语言的 issue，在装有目标仓库的 Docker 容器内工作，通过终端命令行动，并输出一个用隐藏测试评分的 git patch。我们的基线是一个经典的 ReAct（推理 + 行动）循环，Docker 终端是其唯一工具。开源的 MiniMax-M3 单次通过即可解决完整公开 SWE-Bench Pro 集合中 57% 的任务。这是一个扎实的基线，但要进一步抬高需要更精巧的编排。

## **工程化多模型管道以提升 agent 性能**

提升 resolve rate 的一个简单答案本可以是把 MiniMax-M3 换成前沿模型。但我们的目标不仅是提高质量，还要在算力成本上低于当前的 SOTA 结果。若用前沿 agent，它会把整个预算同时花在探索和生成上，导致成本大幅上升。

我们的解法是用心思考管道的构建方式。

此前，我们测量过[调换传统 coding agent 管道的顺序如何同时改善准确性和效率](https://www.ai21.com/blog/first-scale-then-enrich-how-the-right-execution-strategy-helped-us-reach-state-of-the-art-on-swe-rebench/)：与其先提取上下文再生成解决方案，我们先大规模生成解决方案，再利用这些候选来改进上下文提取。

现在，我们继续考察精心设计 coding agent 管道如何在大幅降低单任务总成本的同时显著提升质量。我们提出两个关键做法：第一，把每个步骤分配给在该步骤所需工作上效率最高的模型；第二，对 agent 进行工程设计，使得在调用前沿模型进行最终写入时，它拥有最好的可用上下文。

你可以把它想象成一个团队，有初级、高级和首席成员。在这里，我们的**初级**模型并行铺满整个仓库：搜索、尝试修复、运行测试。不是每次尝试都命中，但合起来它们绘制出了修复所在的地图。**高级**模型接手它们的尝试，深挖其接触过的代码，写清楚真正的修复依赖于什么：涉及的函数、其调用者、覆盖它们的测试。到这时，**首席**模型才坐下来，根据一份准备充分的简报，一次性写出补丁。

这就是我们的管道：MiniMax-M3 当初级，GPT-5.2 当高级，前沿模型（Opus 4.8 或 Fable 5）当首席——只在它们的技术能改变结果的最后一步才请其出手。

## **评估我们的代码覆盖效率：我们呈现的是正确的上下文吗？**

这条管道效率的主要来源之一，是只把最相关、最高质量的上下文交给前沿模型，让它生成补丁时保持专注。由于解决方案补丁可达数万 token，无关上下文会添加噪声，把模型从正确解法上带偏、使其四处游荡，从而推高成本。

因此在最终生成（步骤 3）之前，我们检查所组装的上下文是否真的包含修复所需的代码。方法是对照基准测试的 gold patch 进行测量：对每个任务，gold patch 触及的行中有多大比例也出现在我们组装的上下文里？我们从两个维度追踪这一点：

**并行 rollout（初级模型）。** 每个 rollout 是开源起草模型（MiniMax-M3）解决该 issue 的一次完整尝试。随着我们沿图 3 的 x 轴前进，池子从 1→10 增长，更多尝试合起来触及更多相关代码。

**上下文提取（高级模型）。** 在候选补丁之上，GPT-5.2 拉入修复所依赖的周边代码。图中阴影抬升部分就是该提取步骤在 rollout 之外增加的覆盖。

*图 3. Gold patch 行覆盖率 vs. rollout 池大小，对比有无 GPT-5.2 上下文提取（阴影 = 抬升量）。基于 731 个公开 SWE-Bench Pro 任务的每实例平均值。*

我们分别测量两类代码行：

- **删除行（Removed lines）**是 gold patch 删除或修改的行，它们存在于原始代码中。这里的覆盖率有助于回答：我们在仓库里找对要修的"地点"了吗？借助并行 rollout 和上下文提取，我们在这类行上达到约 90% 的覆盖率。
- **新增行（Added lines）**是修复引入的新代码。这里的覆盖率有助于回答：我们提出正确修复方案的能力如何？在这类行上，我们达到约 71% 的覆盖率。

## **关键要点**

- **让模型匹配阶段。** 开源的较弱模型不仅更便宜，如今也已足够好，可以有效地生成 rollout 并搜索仓库。把前沿质量留给开源弱模型仍难以胜任的困难任务尾部。
- **复用你已经付费换来的东西。** 把初级模型的并行 rollout 视为它们本来的"修复地图"。把这一信号喂给上下文提取，而不是投票之后就丢弃。
- **在尝试解决任务之后再收集源代码上下文。** 在已知补丁之间搜索有区分度的上下文，能产出聚焦得多、也有效得多的源代码上下文供下一步使用。
- **节制地消费前沿算力。** 在准备充分的上下文上做一次性前沿生成，胜过端到端使用前沿模型的 agent。把昂贵的模型用在质量最关键的步骤上。

这是我们通过在不同模型间组合正确的执行策略来优化 agent 性能的更大努力中的一环。下一步是训练源代码上下文提取步骤，以达到更高的覆盖率。
