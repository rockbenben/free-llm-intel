# 隆重推出 Teel – 面向 agent 的涡轮高效执行库（但不仅仅是）

**简要说明**

*Teel 是一个开源 Python 运行时，它能在你以顺序方式写下的代码里，把彼此独立的 IO 密集型调用重叠起来执行。不用 `async`，不用 `await`，不用 `futures`，不用 `gather`。给昂贵的函数标上 `@cacheable`，给编排标上 `@jit`，一个「魔法」影子解释器就会在你的字节码上抢在当前行之前先往前读，找出那些参数早已知的调用，并在主线程赶到之前把它们派发到后台线程上。在 Princeton 的 Tree of Thoughts 上，未经修改：运行时平均减少 83%，最长的一次是 8.07 倍。在 Deep Agents 编码 agent 里，比 LLM 生成的 `async` JavaScript 平均快 19%。去看看仓库：[*github.com/AI21Labs/teel*](https://github.com/AI21Labs/teel)*

*图 1：同样的代码，不同的调度。在纯 Python 里，每次 search 都得等它前一次。有了 Teel，三个彼此独立的 search 同时跑，而 summarize 和 check 只要各自的输入就绪就立刻开始。*

## **为什么这对 agent 重要**

眼下的 agent 质量，主要来自[在推理时投入更多算力](https://arxiv.org/abs/2408.03314)。跑一个集成。[生成五个候选补丁而不是一个](https://arxiv.org/abs/2407.21787)。[把一个任务拆给 N 个子 agent，再把它们带回来的东西合并](https://www.anthropic.com/research/multi-agent-research-system)。技术各不相同，底下却是同一种执行形态：扇出一大堆彼此独立、IO 密集型的工作，然后再收拢回来。

我们最近在 [BrowseComp-Plus](https://www.ai21.com/blog/maestro-deep-research-agents/)、[SWE-rebench](https://www.ai21.com/blog/first-scale-then-enrich-how-the-right-execution-strategy-helped-us-reach-state-of-the-art-on-swe-rebench/) 和 [DeepResearch Bench II](https://www.ai21.com/blog/merging-weak-agents-into-a-state-of-the-art-deep-researcher/) 上的结果，出自三项互不相关的技术，却在算力层面画出了同一幅图景：许多彼此独立的 rollout、retrieval、tool call 或整段 agent 运行，相互重叠，然后合并。

而且越来越多地，那套编排是由 agent 自己写的。在 LangChain 的 Deep Agents 里，模型[写一段简短的脚本来派发它自己的子 agent](https://www.langchain.com/blog/introducing-dynamic-subagents-in-deep-agents)，而不是一个一个工具调用地去调它们。无论这脚本由谁来写，所有那些扇出都是有代价的。agent swarm 把这件事推到最远：Moonshot 的 [Kimi Agent Swarm](https://www.kimi.com/help/agent/agent-swarm) 最多并行跑 300 个子 agent，并报告完成任务比单个 agent 快约 4.5 倍。

## **问题所在**

当我们对自家 agent 的运行做性能剖析时，墙钟时间的大部分都花在一条阻塞在 socket 上的线程上：模型调用、retrieval、tool call、沙盒里的一次 shell exec。削减主 agent 代码几乎没让总量动多少。真正的杠杆，在于那些彼此不依赖的等待。

在 Python 里，要让这些等待重叠，意味着先重写你的代码。要同时跑两个调用，你得把它们变成 `async`。于是每个调用它们的函数也不得不变成 `async`，调用那些函数的每个函数同样如此。你在一个地方想要的改动会爬满整条调用链，直到编排逻辑和并发的管线接管变成同样的那几行代码。每一次新的扇出，都意味着再来一遍。而当一个模型来写这段代码时，它每一次运行都得把这一切全写对。

下面是一个小型 code-review agent 的三种写法：按原样写、用 `asyncio` 重写，以及按原样写再加上 Teel 的装饰器。它会请模型指出每个改动文件里最严重的 bug，再问那些发现是否应当阻止合并，然后要么请求修改、要么放行。

*图 2：同一个 code-review agent 的三种写法：纯 Python（7.1 秒）、用 asyncio 重写（3.0 秒），以及原代码加 Teel 的装饰器（2.9 秒）。asyncio 版本需要三个任务、两次取消和一个 finally 块，才能做到 Teel 独自完成的事。*

版本 2 和版本 3 在差不多的时间跑完，3.0 秒和 2.9 秒，对照顺序执行的 7.1 秒。两者都用同一种方式到达那里：在结论出来之前就把两种可能的后续都启动，并留下它选中的那一个。Teel 独自做到这点，方法是在结论还悬着时，if 的两个分支都跟进。`asyncio` 版本靠手工做到，用了三个任务、两次取消、一个 finally 块，以及它所调用的每个函数的一个 `async` 孪生版。区别不在于并发。区别在于谁得去发现它、并管理它。

这正是我们造 Teel 的原因。并发不该是开发者——或 agent——所写代码的一部分。它可以是运行时的活儿。你写顺序版本。Teel 抢在当前执行行之前读你函数的字节码，发现那些不在等任何东西的调用，并提前在后台线程上启动它们。等你的代码走到那些调用时，结果早已就绪，或正在路上。

## **成果**

| **Workload** | **Baseline** | **With Teel** | **Speedup** |
| --- | --- | --- | --- |
| [Tree-of-thoughts-llm](https://github.com/princeton-nlp/tree-of-thought-llm)（最长的一次） | 307s | 38s | **8.07x** |
| [RLM in LangChain Deep Agents](https://www.langchain.com/blog/introducing-dynamic-subagents-in-deep-agents)（同步 Python） | 150s | 58s | **2.58x** |
| [RLM in LangChain Deep Agents](https://www.langchain.com/blog/introducing-dynamic-subagents-in-deep-agents)（async JS） | 71s | 58s | **1.22x** |

**未经修改的 Tree of Thoughts。** 我们在 Game of 24 样本上、用 GPT-4 跑了 Princeton 的 tree-of-thoughts-llm，且没有编辑这个仓库：`@jit`、`@cacheable` 和 `@inline` 都是从外部套上去的。它是一段教科书式的扇出，却写成教科书式的顺序代码（生成候选、评估、保留最佳、递归），而原版一次只走一个独立的兄弟节点。运行时平均减少 83%，低的一端从 148 秒降到 24 秒，高的一端从 307 秒降到 38 秒。

**模型在运行时写的代码。** LangChain 的 Deep Agents 附带一个 code agent，带一个 `js_eval` 工具：模型通过产出一段在 QuickJS 沙盒里运行的代码片段来解决任务。这段代码可以调用 `tools.web_search()`，并通过 `task()` 派生子 agent，所以模型是在现场编写一次扇出。但它是以 `async` JavaScript 来编写的，这等于把并发模型交回给模型自己，而模型在主动去用 `Promise.all` 这件事上并不稳定。

我们 fork 了 Deep Agents，把代码片段语言换成在 Teel 之下的同步 Python，本预期生成代码更简单、但在速度上有所牺牲。结果它反而更快：在十道混合 web search 与 LLM 的 prompt 上，**平均 58 秒，对照 `async` JS 的 71 秒，以及同一份 Python 顺序执行的 150 秒。** Teel 把模型忘了重叠的独立调用并行化，并在需要它们的那个决策之前，投机地跑起后备分支。（同一个 prompt 每次都产出不同的代码，所以这里比较的是生成程序的分布，而不是同一个程序的两套实现。）我们的 fork 在 [github.com/AI21Labs/deepagents](https://github.com/AI21Labs/deepagents)。

## **API**

一共有三个装饰器和一个上下文管理器。Teel 目前要求 Python 恰好是 3.12.13；「已知限制」会解释原因。

```
1from teel import cacheable, jit, Teel
2
3@cacheable                     # a discrete, expensive, parallelizable step:
4def fetch(url): ...            # an LLM call, an HTTP request, a retrieval
5
6@cacheable
7def summarize(text): ...
8
9@jit                           # orchestration Teel is allowed to analyze
10def research(a, b):
11    pa = fetch(a)              # no dependency between these two
12    pb = fetch(b)              # Teel runs them at the same time
13    return summarize(pa + pb)  # waits only for what it truly needs
14
15with Teel():                             # inside this context, independent
16    answer = research("a.txt", "b.txt")  # calls overlap - no async in sight
```

`@cacheable` 标出那些值得提前派发的重函数。结果会被记忆化，键由参数的 `json.dumps` 构建，所以请让你的参数保持 JSON 可序列化、且平淡无奇。

`@jit` 标出 Teel 被允许往里看的函数。这就是你的编排层。

`@inline` 是可选的。它标出那些廉价的小 helper（字符串格式化、往 dict 里翻找），Teel 可能会在前瞻期间真正执行它们，这通常能挖出更多值得提前派发的 `@cacheable` 调用。

`with Teel():` 把它打开。在上下文之外，每个被装饰的函数都原封不动地作为普通 Python 运行。

## **它如何工作**

**为什么是字节码？** Teel 的实现足够古怪，所以通往那里的路值得花 30 秒，因为每一步都解释了下一步。每一步都保留着同一个执行主意——彼此独立的调用并行运行——只改变了你编写编排所使用的那个接口。

第一个版本在 Celery 上跑编排。Canvas 的 signatures 给了我们一张真正的 DAG，集群能据此调度：利用率上去了，运行可续跑，编排终于和计算分开了。但它写起来是真痛苦，因为编排就是业务逻辑，而 Celery 逼着你用一种不太像 Python 的「管道加签名」方言来写业务逻辑。

所以我们把它搬回了 Python，或者说 Python 的一个受限子集。我们用 `ast` 解析那个子集，把它编译成一张执行图，并自己写了个执行器。这张图本身就很有回报：独立的函数能并行跑，if 分支能在条件求值出来之前就被投机地进入，像 func(x, y) 这样的调用能在 x 和 y 还悬着的时候就把活儿推进到它的子调用里。而这一切，只对我们愿意解析的那部分语言可用。

要摆脱这个限制，就得放弃 `ast`。字节码，是每个 Python 程序看起来都一样的那个层面。

**运行时怎么知道你接下来要调用什么？** 当一个 `@jit` 函数运行时，Teel 把执行状态复制进一个受限的影子解释器，并逐步走你主线程还没走到的那些字节码。它在自己的副本上操作，所以你程序的状态不会被动。

**Teel 会构建一张依赖图吗？** 不会。`ast` 版本会。Teel 从来不需要整张图，每个调用只要一个答案：*这个调用的参数就绪了吗？* 任何它还算不出来的值，比如一个仍在进行中的 `@cacheable` 调用的结果，都被标记为 pending，而从某个 pending 值算出来的任何东西也都是 pending：

```
1pa  = fetch(a)        # arguments known: dispatched now, pa is pending
2pb  = fetch(b)        # arguments known: dispatched now, pb is pending
3s   = pa + pb         # built from pending values: pending
4out = summarize(s)    # pending argument: not dispatched yet
```

当前瞻抵达一个没有 pending 参数的 `@cacheable` 调用时，Teel 把它派发给一个 `ThreadPoolExecutor`，并把结果记忆化。等你的代码真正走到那一行，答案早已就绪，或正在路上。两个不消费彼此结果的调用永远不会互相等待，这就是为什么扇出不需要特别支持：`[answer(q) for q in sub_questions]` 会为每一个问题早已知的 `answer(q)` 都派发出去。并行是默认，你通过制造一个真正的数据依赖来退出。

**它是怎么够到你程序的状态的？** Teel 用 `sys._getframe()` 抓取帧栈，用一个小型 C 扩展（`frameinspect`）从 CPython 里把每一帧完整的值栈拽出来，并读 `f_lasti` 来找到最后一条真正被执行的指令。影子解释器就从那里开始往前迈步。

要到达那个状态，是个「受了诅咒」的操作。读取一个活动帧的值栈，并不是 CPython 会提供给你的东西，这就是为什么 `frameinspect` 要对着 CPython 的内部头文件编译，整个东西也被钉死在一个精确的解释器版本上。完整的、逐 opcode 的走查在 [README 的 Under the hood 一节](https://github.com/AI21Labs/teel/blob/main/README.md#under-the-hood)里。

## 契约

**你承诺什么。** Teel 会做三件普通解释器绝不做的事：它比你的代码更早地运行一个函数，有时会运行一个你的代码永远到不了的函数，还会交回一个存好的结果而不是重新运行它。只有当一个函数不在乎它什么时候运行、运行多少次时，这些才合法。想象一个会发邮件或扣款的 `@cacheable` 函数：Teel 可能会为你程序从没走的那个分支运行它，而没什么能把邮件撤回。这就是 `@cacheable` 的契约，而且责任在你：不写数据库、不读时钟、没有隐藏状态、参数要 JSON 可序列化，因为它们 `json.dumps` 出来的东西就是记忆化的键。`@jit` 什么都不承诺。它是读取你字节码的许可，而不是关于这个函数干什么的断言。

**Teel 承诺什么。** 同一个调用只运行一次：pending 和已完成的任务都以「函数加参数」为键，所以第二个前瞻即使发现了同一个 `fetch(url)`，也会挂到第一个上，而不是再发一次请求。失败的调用会被丢弃，而不是被缓存，前提是失败是暂时的。

**而一次猜错的代价是时间和 token，不是正确性。** 影子解释器从不产出你的答案。CPython 依然会把你的函数从头到尾执行完，一条指令接一条指令，就和没有 Teel 时一模一样，唯一的区别是有些调用发现自己早已在缓存里躺着答案了。猜错，你就白白烧掉一次后台调用，如果它是一次 LLM 调用，还得搭上它的 token。什么都猜不到，你就付完整的顺序执行价格。可一旦你打破了纯度契约，后果就得你自己扛。那是 Teel 保护不了你的唯一一种失败模式。

## **可观测性：墙钟究竟花去了哪里**

当运行时决定什么提前跑时，你需要一个办法来看清它到底决定了什么。给上下文一个路径，Teel 就会记录整次运行：

```
1with Teel(trace_path="teel-trace.json"):
2    research("a.txt", "b.txt")
3
4# open teel-trace.json at https://ui.perfetto.dev/
```

输出是一个 Chrome trace-event 文件，所以 Perfetto 会把它渲染成一条时间线：每个 `@cacheable` 调用一条横条，落在真正跑它的那条线程上，带开始时间和持续时长，重叠起来的工作就显示成并排的横条。

一旦你把 test-time compute 调大调小，per-call 这个粒度才开始变得要紧。在一个棘手的 agentic 基准上，结果很少再是单个数字：我们 BrowseComp-Plus 的工作报告的是一条准确率相对成本与延迟的前沿曲线，好让一个团队读出它负担得起的质量。如果你只能端到端地测量，你就画不出一条延迟前沿。

要测量加速，把同一段代码跑两遍。一个 `@cacheable` 函数在没有活动上下文时会被原样运行，所以基线不是一个单独的、顺序实现的东西，它就是那个一模一样的程序。

```
1# timed(label) runs research("a.txt", "b.txt") and prints its wall clock
2
3baseline = timed("sequential")       # no context, plain Python
4
5with Teel():
6    optimized = timed("with Teel")   # same code, now overlapped
7
8assert baseline == optimized         # same answer, different clock
```

**这将走向何处**

并行和可观测性都源自同一个决定：一次运行就是「一组以其参数为键的调用」。把这一步再往前挪一点，一次 agent 运行就不再是一个用完即弃的进程，而变成可复用的数据。把结果持久化下来，之后的某次运行就能从中被满足：没变的调用是命中，任何被一个改动过的输入流入的调用都会拿到一个新键并重新运行。于是你就有了崩溃续跑、对着钉住的输出来调试，以及迭代编排而无需为每一次 tool call 重新付费。你也因此有了 human-in-the-loop：一个 agent 在一个决策点把自己的状态冻结下来，由一个人来审查，运行几小时后在另一台主机上续跑。

## 已知限制

这是一个带着两处锋利边角的概念验证。它被钉死在 Python 3.12.13 这个精确版本上，因为 `frameinspect` 是对着 CPython 的内部头文件编译的。而且 GIL 依然适用：后台调用跑在一个 `ThreadPoolExecutor` 上，所以 IO、网络调用，以及像 NumPy 这样不碰 GIL 的工作，都能好好重叠；但对 CPU 密集型、受 GIL 约束的工作，没戏。

克隆它，装饰你自己的函数，包住你的入口点，从 README 开始：[github.com/AI21Labs/teel](https://github.com/AI21Labs/teel)
