**简述**

*Teel 是一个开源 Python 运行时，它与您按顺序编写的代码中的独立 IO 绑定调用重叠。没有* *`异步`**，没有* *`等待`**，没有`futures`，没有* *`聚集`**。用 * *`@cacheable`** 标记昂贵的函数，用 * *`@jit`** 标记编排，并且神奇的影子解释器会提前读取字节码，找到参数已知的调用，并在主线程到达之前将它们分派到后台线程上。在普林斯顿的思想之树上，未经修改：平均运行时间减少 83%，最长运行时间减少 8.07 倍。比 Deep Agents 编码代理中 LLM 生成的“异步”JavaScript 平均快 19%。检查仓库：* [*github.com/AI21Labs/teel*](https://github.com/AI21Labs/teel)

*图 1：相同的代码，不同的时间表。在普通的 Python 中，每次搜索都会等待前一个搜索。使用 Teel，三个独立的搜索会同时运行，并在输入准备好后立即开始汇总和检查。*

## **为什么这对代理商很重要**

目前代理的质量主要来自[在推理上花费更多的计算](https://arxiv.org/abs/2408.03314)。运行一个乐团。 [生成五个候选补丁而不是一个](https://arxiv.org/abs/2407.21787)。 [将任务拆分到 N 个子代理并合并它们返回的内容](https://www.anthropic.com/research/multi-agent-research-system)。不同的技术，下面是一种执行形式：分散大量独立的、IO 密集型工作，然后将其重新连接起来。

我们最近在 [BrowseComp-Plus](https://www.ai21.com/blog/maestro-deep-research-agents/)、[SWE-rebench](https://www.ai21.com/blog/first-scale-then-enrich-how-the-right-execution-strategy-helped-us-reach-state-of-the-art-on-swe-rebench/) 和 [DeepResearch Bench] 上取得的结果II](https://www.ai21.com/blog/merging-weak-agents-into-a-state-of-the-art-deep-researcher/)来自三种不相关的技术，并在计算级别绘制了相同的图片：许多独立的推出、检索、工具调用或整个代理运行、重叠，然后合并。

越来越多的情况是，代理自己编写编排。在LangChain的深度代理中，模型[编写一个简短的脚本来调度自己的子代理](https://www.langchain.com/blog/introducing-dynamic-subagents-in-deep-agents)，而不是一次调用它们一个工具。无论是谁写的，所有的扇出都是有代价的。代理群走得更远：Moonshot 的 [Kimi Agent Swarm](https://www.kimi.com/help/agent/agent-swarm) 并行运行多达 300 个子代理，报告完成任务的速度比单个代理快约 4.5 倍。

## **问题**

当我们分析代理的运行时，大部分挂钟都是位于套接字上的线程：模型调用、检索、工具调用、沙箱中的 shell 执行程序。削减主要代理代码几乎没有改变总数。杠杆作用在于相互不依赖的等待。

在 Python 中，重叠这些等待意味着首先重写代码。要同时运行两个调用，请将它们设置为“异步”。然后，每个调用它们的函数也必须成为“异步”，每个调用它们的函数也是如此。您想要在一个地方进行的更改会爬升整个调用链，直到编排逻辑和并发管道成为相同的代码行。每一次新的扇出都意味着再次进行。当模型编写该代码时，它必须在每次运行时都正确无误。

这是一个小型代码审查代理，有三种方式：按编写方式、用“asyncio”重写以及按编写方式加上 Teel 的装饰器。它会向模型询问每个更改的文件中最严重的错误，询问这些发现是否应该阻止合并，然后请求更改或批准。

*图 2：一个代码审查代理以三种方式编写：纯 Python (7.1s)、使用 asyncio 重写 (3.0s) 以及使用 Teel 装饰器的原始代码 (2.9s)。 asyncio 版本需要三个任务、两个取消和一个finally 块来匹配Teel 自己所做的事情。*

版本 2 和版本 3 大约在同一时间完成，分别为 3.0 秒和 2.9 秒，顺序为 7.1 秒。两者以相同的方式到达那里：他们在判决作出之前开始两种可能的后续行动，并保留其中所选择的一项。 Teel 自己做到了这一点，在判决仍在等待期间，遵循 if 的两个分支。 “asyncio”版本是手动完成的，包含三个任务、两个取消、一个finally块以及它调用的每个函数的“async”双胞胎。区别不在于并发性。谁必须找到它并管理它。

这就是我们创建 Teel 的原因。并发性不一定是开发人员或代理编写的代码的一部分。这可能是运行时的工作。您编写顺序版本。 Teel 在当前运行的行之前读取函数的字节码，发现未等待任何内容的调用，并在后台线程上尽早启动它们。当您的代码到达他们时，结果已经在那里或正在路上。

**思想之树，未修改。** 我们使用 GPT-4 在 Game of 24 个样本上运行了普林斯顿的思想之树-llm，无需编辑存储库：“@jit”、“@cacheable”和“@inline”是从外部应用的。它是一本以教科书顺序代码形式编写的教科书扇出（生成候选者、评估、保留最好的、递归），并且原始版本一次走一个独立的兄弟姐妹。平均运行时间减少了 83%，从低端的 148 秒减少到 24 秒，从高端的 307 秒减少到 38 秒。

**模型在运行时编写的代码。** LangChain 的 Deep Agents 提供了带有“js_eval”工具的 dcode 代理：模型通过发出在 QuickJS 沙箱中运行的代码片段来解决任务。该代码片段可以调用“tools.web_search()”并通过“task()”生成子代理，因此该模型正在动态创作扇出。但它是用“异步”JavaScript 编写的，它将并发模型交给模型本身，并且模型在达到 Promise.all 时不一致。

我们分叉了 Deep Agents，并将代码片段语言替换为 Teel 下的同步 Python，希望以一定的速度代价获得更简单的生成代码。相反，它的结果更快：在 10 个混合的网络搜索和 LLM 提示中，**平均 58 秒，“异步”JS 平均耗时 71 秒，同一 Python 顺序运行则为 150 秒。** Teel 并行化模型忘记重叠的独立调用，并在需要它们的决策之前推测性地运行后备分支。 （相同的提示每次都会产生不同的代码，因此这比较的是生成的程序的分布，而不是一个程序的两个实现。）我们的分支位于 [github.com/AI21Labs/deepagents](https://github.com/AI21Labs/deepagents)。

## **API**

有三个装饰器和一个上下文管理器。 Teel 目前需要 Python 3.12.13；已知的限制解释了原因。
```
1from teel import cacheable, jit, Teel
2
3@cacheable                     # a discrete, expensive, parallelizable step:
4def fetch(url): ...            # an LLM call, an HTTP request, a retrieval
5
6@cacheable
7def summarize(text): ...
8
9@jit                           # orchestration Teel is allowed to analyze
10def research(a, b):
11    pa = fetch(a)              # no dependency between these two
12    pb = fetch(b)              # Teel runs them at the same time
13    return summarize(pa + pb)  # waits only for what it truly needs
14
15with Teel():                             # inside this context, independent
16    answer = research("a.txt", "b.txt")  # calls overlap - no async in sight
```
`@cacheable` 标记了值得尽早调度的繁重函数。结果存储在从参数的“json.dumps”构建的键上，因此请保持这些参数可 JSON 序列化且无聊。

`@jit` 标记允许 Teel 查看内部的函数。这是您的编排层。

`@inline` 是可选的。它标记了 Teel 在前瞻期间可能实际执行的廉价助手（字符串格式化、字典挖掘），这通常会提前发现更多“@cacheable”调用以进行分派。

`with Teel():` 将其打开。在上下文之外，每个修饰函数都以纯 Python 的方式运行，未受影响。

## **它是如何工作的**

**为什么是字节码？** Teel 的实现很奇怪，那里的路径值 30 秒，因为每一步都解释了下一步。每一步都保持相同的执行思路，独立的调用并行运行，只改变你编写编排的接口。

第一个版本在 Celery 上运行编排。 Canvas 签名为我们提供了集群可以调度的真正 DAG：利用率提高、运行可恢复、编排最终与计算分离。写起来也很痛苦，因为编排是业务逻辑，而 Celery 让你用管道和签名方言编写业务逻辑，这并不完全是 Python。

因此，我们将其带回到 Python 中，或者带回 Python 的一个受限子集中。我们用“ast”解析该子集，将其编译成执行图并编写我们自己的执行器。该图以其自身的方式得到了回报：独立的函数并行运行，如果在测试解决之前可以推测性地输入主体，并且像 func(x, y) 这样的调用可以在 x 和 y 仍然悬而未决时推入其子调用。所有这些仅适用于我们愿意解析的语言片段。

放弃限制就意味着放弃“ast”。字节码是每个 Python 程序看起来都相同的级别。

**运行时如何知道您要调用什么？** 当“@jit”函数运行时，Teel 将执行状态复制到有限的影子解释器中，并逐步执行主线程尚未到达的字节码。它在自己的副本上运行，因此程序的状态不会受到影响。

**Teel 是否构建了依赖关系图？** 不。`ast` 版本做到了。 Teel 永远不需要整个图，每次调用只需要一个答案：*此调用的参数准备好了吗？*它还无法计算的任何值（例如仍在运行中的“@cacheable”调用的结果）都被标记为待处理，并且从待处理值计算出的任何内容也都处于待处理状态：
```
1pa  = fetch(a)        # arguments known: dispatched now, pa is pending
2pb  = fetch(b)        # arguments known: dispatched now, pb is pending
3s   = pa + pb         # built from pending values: pending
4out = summarize(s)    # pending argument: not dispatched yet
```
当lookahead到达没有挂起参数的“@cacheable”调用时，Teel将其分派到“ThreadPoolExecutor”并记住结果。当您的代码真正到达该行时，答案已经存在或正在路上。不消耗彼此结果的两个调用永远不会互相等待，这就是扇出不需要特殊支持的原因：“[answer(q) for q in sub_questions]”调度每个问题已知的“answer(q)”。并行性是默认设置，您可以通过创建真实的数据依赖关系来选择退出。

**它如何获取程序的状态？** Teel 使用“sys._getframe()”获取帧堆栈，使用小型 C 扩展（“frameinspect”）从 CPython 中提取每个帧的完整值堆栈，并读取“f_lasti”以查找实际执行的最后一条指令。这就是影子解释器开始前进的地方。

达到这种状态是一个被诅咒的操作。 CPython 无法提供读取实时帧的值堆栈的功能，这就是为什么“frameinspect”针对 CPython 的内部标头进行编译，并且整个内容都固定到一个确切的解释器版本。完整的演练（逐个操作码）位于 [README 的“幕后”部分](https://github.com/AI21Labs/teel/blob/main/README.md#under-the-hood)。

## 合同

**你的承诺。** Teel 做了三件事，这是普通解释器不会做的：它比你的代码更早运行一个函数，有时运行一个你的代码永远不会到达的函数，并返回保存的结果而不是再次运行它。仅当函数不关心运行时间或运行频率时，每个函数才是合法的。想象一个发送电子邮件或向卡收费的“@cacheable”函数：Teel 可能会为您的程序从未使用过的分支运行它，并且不会取消发送电子邮件。这就是“@cacheable”合约，它由你负责：没有数据库写入，没有读取时钟，没有隐藏状态，以及 JSON 可序列化参数，因为其中的“json.dumps”是备忘录键。 `@jit` 没有任何承诺。这是读取字节码的权限，而不是关于该函数的功能的声明。

**Teel 的承诺。** 相同的调用运行一次：待处理和已完成的任务由函数加参数作为键控，因此发现相同“fetch(url)”的第二个前瞻会附加到第一个请求，而不是触发另一个请求。假设故障是暂时的，失败的调用将被丢弃而不是被缓存。

**错误的猜测会花费时间和代币，而不是正确性。**影子解释器永远不会产生你的答案。 CPython 仍然按照指令执行您的函数直至完成，与没有 Teel 时完全相同，唯一的区别是某些调用发现其结果已在缓存中。如果猜错了，你就会烧掉后台调用，如果是 LLM 调用，还要加上它的代币。无需猜测，您只需支付全部连续价格。不过，打破纯度合同，你就拥有结果。这是 Teel 无法保护您免受的一种故障模式。

## **可观察性：挂钟实际去了哪里**

当运行时决定提前运行什么时，您需要一种方法来查看它所决定的内容。给上下文一个路径，Teel 记录运行：
```
1with Teel(trace_path="teel-trace.json"):
2    research("a.txt", "b.txt")
3
4# open teel-trace.json at https://ui.perfetto.dev/
```
输出是 Chrome 跟踪事件文件，因此 Perfetto 将其呈现为时间线：在运行它的线程上，每个“@cacheable”调用一个小节，包含开始时间和持续时间，并且重叠工作显示为并排的小节。

一旦您上下调整测试时计算，每次调用的粒度就开始变得重要。硬代理基准测试的结果不再是单一数字：我们的 BrowseComp-Plus 工作报告了针对成本和延迟的准确性前沿，因此团队可以读出其可以承受的质量。您无法绘制延迟边界，只能测量端到端。

要测量加速比，请运行相同的代码两次。 “@cacheable”函数在没有活动上下文的情况下运行，因此基线不是单独的顺序实现，而是相同的程序。
```
1# timed(label) runs research("a.txt", "b.txt") and prints its wall clock
2
3baseline = timed("sequential")       # no context, plain Python
4
5with Teel():
6    optimized = timed("with Teel")   # same code, now overlapped
7
8assert baseline == optimized         # same answer, different clock
```
**这会去哪里**

并行性和可观察性都遵循一个决定：运行是一组由其参数键入的调用。更进一步，代理运行将不再是一次性流程，而是可重复使用的数据。保留结果，并可以从中提供稍后的运行：未更改的调用将被命中，编辑后的输入流入的任何调用都会获得新的密钥并重新运行。这使您可以崩溃恢复、针对固定输出进行调试以及迭代编排，而无需为每个工具调用重新付费。它还为您提供了人机交互：代理在决策点冻结其状态，人员进行审查，几小时后在不同的主机上恢复运行。

## 已知限制

这是一个具有两个尖锐边缘的概念证明。它完全固定在 Python 3.12.13 上，因为“frameinspect”是针对 CPython 的内部标头进行编译的。 GIL 仍然适用：后台调用在“ThreadPoolExecutor”上运行，因此 IO、网络调用和无 GIL 的工作（如 NumPy）可以很好地重叠，但对于 CPU 限制、GIL 约束的工作，则没有骰子。
