多年来，我们一直与企业合作，试图把他们的数据变成可用的东西。每个团队都怀着同样的期望：*RAG 终于能让他们的知识规模化发挥作用*。但等我们介入时，现实已经给了他们一击。答案是流畅的，没错，但并不总是可靠。

假设你问的是业绩趋势或供应商比较，基于 LLM 的系统只给你一半图景。它可能浮出几段相关摘录，却漏掉关键数据点；或泛泛总结一些弱相关信息，并不直接回答问题。在金融和合规领域，这些缺口不是无害的——它们是重大风险。

我们知道 RAG 没有彻底坏掉，但要让它可靠到能给企业使用，还需要加把力。于是我们构建了 Structured RAG（S-RAG）：一种为检索带来结构与推理的增强，实现精确、可审计的答案。它内建于 AI21 Maestro——我们驱动关键任务企业 agent 的 AI 编排系统。

想要更技术向？[深入阅读我们的 Structured RAG 研究论文](https://arxiv.org/abs/2511.08505v1)。

与检索文本块、然后指望 LLM 基于有限上下文答对的传统 RAG 不同，S-RAG 在离线阶段把信息从非结构化文档抽取进一个关系数据库。在运行时，它使用 SQL 查询在这份结构化数据上检索和推理。这意味着需要聚合、比较或过滤的分析性问题——企业赖以生存的那类问题——终于能被准确、透明地回答。

**示例：** 面对一个多数 RAG 系统答不对的简单财务问题，Maestro 的 S-RAG 直接从结构化数据中检索精确值，而不是基于文本邻近度去猜。

## Embedding 式 RAG 的短板

Embedding 式 RAG——第一代知识智能体的基石——标志着检索增强生成演进中的一个重要里程碑。它把查询和文档嵌入高维向量，意在检索语义"接近"的文本片段，喂给 LLM 做推理。

但对企业来说，这一方法在三种关键情形下力有不逮。

### 1. 回答聚合类问题

我们见过客户——尤其是金融和合规领域——在看似简单的分析查询上撞墙：

- "去年所有子公司中资本开支的最大值是多少？"
- "按准时交付率排名前五的供应商是谁？"
- "安全事故逐季度呈什么趋势？"

这些不是"大海捞针"式查询——答案并不藏在几段文本里。要正确回答这些分析查询，系统必须跨可能多达数十或数百条记录进行过滤、比较和聚合。

Embedding 式 RAG 没有执行这些操作的通用方法。它检索固定数量的文本块交给 LLM，而 LLM 必须在有限的上下文窗口内、用非常有限的算术能力尝试推理。

### 2. 需要穷尽覆盖的问题

企业团队常问要求完整、穷尽清单的问题：

- "列出所有 2025 年前到期且违约金超过 100 万美元的合同。"
- "哪些员工的认证今年会过期？"
- "展示所有监管变化影响报告要求的市场。"

漏掉哪怕一项都不是小麻烦，而是合规风险。而基于 embedding 的检索本质上是概率性的，其优化目标是找到最匹配的单个文本块，而不是全部相关证据。由于它只按相似度打分取回一个子集，永远无法保证*全量*检索。这在财务报告或监管合规等领域不可接受——在那里，穷尽覆盖与正确性同等重要。

### 3. 稠密或无区分度的语料

最后，想想技术文档或监管备案这类语料。它们稠密、重复、以属性为驱动。文档之间可能只差几个数字或条款，查询则可能聚焦于条款编号或型号 ID 这样的精确属性。在这些场景下，embedding 相似度坍缩了。检索变得嘈杂，因为 embedding 模型并未学会这些术语背后的语义，于是无关但"相近"的段落常常挤掉真正的答案。

例如在财务分析查询中，多数报告看起来几乎一模一样、术语雷同——"total liabilities""shareholder equity""net income"。对 embedding 模型而言，它们全都相关。结果是语义检索常常浮出一堆上下文中接近、实则不回答问题的无关文档。

**Structured RAG 登场。**

## 用 AI21 Maestro 增强 RAG

AI21 Maestro 以 Structured RAG 解决这些问题，扩展了 RAG 系统在企业环境中能准确处理的查询范围。

AI21 Maestro 不把文档仅当作非结构化文本，而是在摄取阶段利用结构，弥补 embedding 检索的缺陷。它分析文档以检测重复出现的模式。例如：

- **在财务备案中**，每份报告都描述收入、运营开支、资本开支等属性。
- **在 HR 简历中**，每条记录都包含教育背景、工作年限和证书。
- **在合同中**，条款遵循标准章节，如终止、违约金和适用法律。

但由于文档是各自独立撰写的，同一个值可能以多种格式出现——比如 "1,000,000"、"1M"，或干脆一个 "1"。没有标准化，跨这类文档做推理几乎不可能。

AI21 Maestro 自动推断出捕捉这些属性的 schema。借助 Structured RAG，每份文档被转换为对齐该 schema 的结构化记录，具有一致的格式、术语和校验。用户可以在摄取前审查、编辑和调整自动生成的 schema 以满足自身需求。整个语料变成一个结构化数据库，并保留与原文的链接，做到透明可控。

在推理时，当用户提出的相关问题对应到某个可用 schema，AI21 Maestro 把自然语言问题翻译为对这个结构化数据库的正式 SQL 查询。

这使得传统 RAG 无法执行的精确分析操作成为可能——最大/最小值计算、趋势分析、复杂过滤——同时保持可追溯性。

- "各子公司中最高的 ARR 是多少？"
- "展示按年度的平均员工数增长。"
- "2020 年之后签署的合同里哪些包含仲裁条款？"

执行 SQL 后，Maestro 把结果交还 LLM，生成流畅、可直接用于业务的回答。

## 性能与混合检索

这一方法在[聚合类查询](https://huggingface.co/datasets/ai21labs/aggregative_questions)上比 embedding 式系统带来最高 60% 的更高准确率，并在穷尽覆盖类问题上实现近乎完美的召回（前提是 schema 正确）。

*在聚合问题 benchmark 上，对 embedding 式 RAG（生成模型为 gpt-o3）、OpenAI Responses API 与 Structured RAG 的比较。*

但并非所有信息都能规整地装进 schema。有些属性罕见，或问题需要对叙事文本推理。在这些情况下，AI21 Maestro 先用 Structured RAG 收窄数据集，再在缩小后的集合上应用 embedding 检索。

这种混合检索在穷尽覆盖与灵活性之间取得平衡，确保不漏掉相关信息，同时仍能支持细腻的、重文本的问题。它还通过先按精确属性查询，绕开了稠密语料的失效模式。
