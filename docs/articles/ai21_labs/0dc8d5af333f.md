Google Cloud 最近发布了 [AI21 在 AI Hypercomputer 上的故事](https://cloud.google.com/blog/products/containers-kubernetes/ai21-trains-its-models-on-ai-hypercomputer)，其中提到高优先级工作负载的启动等待时间（time-to-start）缩短了 83%。以下是我们如何在 GKE 上用 Kueue 达成这一结果的完整技术拆解。

## 简要概述

在 Kubernetes 上运行 AI 训练工作负载的人都清楚一个反复出现的难题：多支团队共享一个大型 GPU 机群。本文中，我们分享一个真实案例——来自我们一个共享 GKE 集群，规模约为 10,000 块 GPU、跨多支团队使用——讲述我们如何从内部消息频道里的人工协调，迁移到 Kueue：一个开源、Kubernetes 原生的作业排队系统，能自动准入（admit）、排定优先级并抢占（preempt）工作负载。故事始于采用 Kueue，最终演变为我们与 Google 背后 Kueue 团队的紧密协作——我们真实生产环境的需求直接反哺进 Kueue 的路线图。我们将回顾我们尝试过什么、成效如何——人工干预率和关键作业「饥饿」时长等指标大幅下降——以及在生产环境运行它总结出的经验如何反哺 Kueue 本身，包括新功能 Admission Fair Sharing（AFS），现已向所有用户提供。

## 一个共享难题

GPU 是稀缺资源，这已不是秘密。任何从事模型训练——需要长时间大量占用 GPU——的人都对这个问题深有体会。它的有限性意味着，在研究员、MLOps、工程师和对齐（alignment）等多支团队之间分配 GPU 会变得格外棘手，尤其是在训练期间，并引出一些难题：

- 如何在多支团队之间公平共享一种有限、昂贵的资源？
- 当需求超过容量时，谁该被优先满足？
- 是否应该中断一个正在运行的工作负载，为更高优先级的工作腾出空间？
- 如何调和优先级不同、对「紧急」定义也不同的团队？

### 「改造前」：在团队频道里谈判资源

最初，我们是在一个名为 *#gpu-resources* 的内部消息频道里应对这些问题的。当某人需要的 GPU 型号已被占满时，就在频道里问一声，祈祷有人腾出容量。

图 1：#gpu-resources 频道典型的一天——人工请求、临时协调，一些角落闲置着容量，另一些角落却在挨饿。

在集群还有余量时，这种基于频道的协商还管用。一旦利用率持续贴近 100%——对于昂贵的预留 GPU 机群这正是目标——每一个新请求都会变成一场零和的驱逐谈判，频道就此撞墙。

放任人工协商，这套体系的裂缝很快显现：

- 大量真实工程时间浪费在分流与谈判上
- 排队不公平
- 一些角落闲置着容量，另一些角落却在挨饿
- 依赖临时的「魔法命令」来腾出足够的工作负载容量

我们需要构建更好的东西。第一步是确立一个理想 GPU 管理系统应有的设计原则。

### 理想 GPU 管理系统的四大支柱

- **公平（Fairness）：** 调度决策依据各团队的使用情况系统化地做出，而不是先到先得或「谁嗓门大谁赢」。
- **秩序（Order）：** 工作负载排队反映业务优先级，而不只是时间戳。
- **效率（Efficiency）：** 开发者不必再手动删除自己闲置或非关键的工作负载。
- **技术完整性（Technical integrity）：** 多 Pod（gang）作业在全部资源就绪之前不会启动，防止部分部署。

## 从设计原则到落地：构建 GPU 管理系统

### 我们的构件

本文聚焦我们在 Google Cloud（GCP）上的一个共享 GKE 集群——即部署了这套系统的那个。它把大约 10,000 块 GPU 池化给多支团队使用。

我们刻意把它作为单一共享池运行，而不是一支团队一个集群：Kubernetes 起很多集群很容易，但集群之间共享容量很难。把所有资源放在一个池子里，才保住了高利用率——也才把我们如何在池内调度这件事的压力真正逼出来。

该集群的配置如下：

我们有三种机器容量——预留（reserved）、spot（竞价）、以及 [Dynamic Workload Scheduler 的 flex-start 模式](https://cloud.google.com/blog/products/compute/introducing-dynamic-workload-scheduler)——需要支撑三类不同的训练研发工作负载：

- Debug pod：开发者可能希望在真实生产环境远程调试，而不是在自己的笔记本上本地调试
- 训练作业（Training jobs）：批处理工作负载，可在一秒内从 1 个扩展到数百个。它们可以是单节点作业，也可以是需要多台机器并行运行的多节点作业。我们用 [Indexed Jobs](https://kubernetes.io/blog/2021/04/19/introducing-indexed-jobs/) 来管理并行度。
- 推理模型（Inference models）：供我们的强化学习训练作业使用，以 Kubernetes deployment 形式管理，通过 [HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/) 扩缩容。

这些工作负载又可按可否被抢占进一步分类：

- 不可抢占（Non-preemptible）：中途打断它们是自动亮红灯的事——代价高昂、浪费资源，还可能伤及时间关键的工作负载。
- 可抢占（Preemptible）：中途打断的后果轻微到可以忽略。

### 寻找解法：评估原生 K8s

在评估第三方工具之前，我们先检查了 Kubernetes 原生日志具备什么。我们看到的如下：

| 原语（Primitive） | 提供什么 | 短板所在 |
| --- | --- | --- |
| PriorityClass | 关键 Pod 可以抢占非关键 Pod。 | 效率与秩序：工作在 Pod 级别而非工作负载级别，没有「gang 规模」概念，可能整批低优先级运行被抢占，哪怕高优先级作业只需要其中 1 块 GPU。 |
| ResourceQuota | 对每个 namespace 的 CPU/内存/GPU/对象数量设硬上限。 | 公平：容量闲置时团队之间无法借用；超额 Pod 在准入时直接被拒绝，而不是排队。 |
| LimitRange | namespace 内容器级的默认/最小/最大请求。 | 公平：它是护栏，不是调度器。 |
| Job / Indexed Job | 带 completions/parallelism 的工作负载抽象。 | 技术完整性：没有全有或全无（all-or-nothing）的语义。若 4 个 Pod 中 3 个调度成功而第 4 个放不下，前 3 个照样运行并烧掉 GPU。 |

我们需要转向其他批调度器方案，才能找到同时满足四项标准的选项。由于 GKE 不自带批调度器，我们评估了三款：Apache [YuniKorn](https://github.com/apache/yunikorn-core/)、[Volcano](https://github.com/volcano-sh/volcano) 和 [Kueue](https://github.com/kubernetes-sigs/kueue)。当时 Volcano 功能更多，但与我们的环境集成不够顺滑；YuniKorn 则没有覆盖我们全部用例。在简洁性与集成度上，Kueue 胜出。

## 与 Kueue 一起工作

Kueue 是一组作业排队相关的 API 和控制器。它是作业级别的管理器，决定一个作业何时应被准入启动（即可以创建 Pod）、何时应当停止（即应删除活动 Pod）。

### 第 1 步：验证系统标准

把我们的四大支柱映射到 Kueue 的特性上，我们看到它能够满足我们全部的标准：

- **公平：** Kueue 提供两个互补机制：[Preemption Fair Sharing](https://kueue.sigs.k8s.io/docs/concepts/preemption/#fair-sharing)（通过抢占来平衡集群使用）和 [Admission Fair Sharing（AFS）](https://kueue.sigs.k8s.io/docs/concepts/admission_fair_sharing/)（优先准入历史上用得少的团队的工作负载）。
- **秩序：** [Workload Priority Classes](https://kueue.sigs.k8s.io/docs/concepts/workload_priority_class/) 补上了我们发现的原生 Kubernetes PriorityClass 的缺口，同时控制排队顺序与抢占顺序。Admission Fair Sharing 在基于时间戳的排序之上又加了一根杠杆。
- **效率：** Kueue 的核心资源 [ClusterQueue](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/) 让管理员能细粒度控制[抢占行为](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/#preemption)，并集成 Fair Sharing 与 Workload Priority Classes。Kueue 自动处理工作负载清理。
- **技术完整性：** Kueue 的全有或全无语义与我们的 Indexed Jobs 无缝结合：多 Pod gang 只有在每个 Pod 都能运行时才会被准入。

### 第 2 步：定义实现需求

Kueue 支持了我们内部 GPU 管理系统所需的总体行为。但要指导落地，我们还需要梳理更多需求。我们与该集群使用的主要干系人——算法研发负责人（Algorithm Developer Leads）——坐下来，明确他们对系统行为的具体要求：

| 池（Pool） | 何时使用 | 争用行为 |
| --- | --- | --- |
| 团队级保障配额（Per-team guaranteed） | 一个团队的基础配额 | 配额可调；永不被抢占 |
| 共享保障（单节点） | 团队需要的单节点容量超出自有配额 | 按芯片数公平共享；永不被抢占 |
| 共享保障（多节点） | 多节点训练作业，包括需要几乎整个（甚至全部）池的「Hero Jobs」 | 按芯片数公平共享；仅被 critical 优先级的工作负载抢占 |
| 机会型（单节点） | 可容忍抢占的尽力而为型工作（debug pod、低优先级实验） | 公平共享；所属池回收时被抢占。这是保持高利用率的关键杠杆。 |
| 按需（On-demand） | 其他池全满，或需要预留机群中没有的 GPU 型号 | 不能抢占别人，也不能被抢占。两种形式：spot（可抢占）或 DWS（不可抢占）。可以请求任意加速卡类型。 |

### 第 3 步：落地第一版设计（v0.10）

从管理员视角，我们在第一版中构建了三层容量：

- **保障容量（Guaranteed capacity）：** 每个团队有自己的单节点作业配额、一个用于多节点作业的共享池，以及另一个用于单节点作业的共享池。
- **可抢占容量（Preemptible capacity）：** 单一共享池，租户之间公平共享，可借用任何闲置的保障容量。这是保持高利用率、帮助容量在团队间流动的关键。
- **按需容量（On-demand capacity）：** 用于系统已满且没有工作负载可被安全抢占的情形：开发者可以动态开通新机器。它也适合测试预留池之外的 GPU 型号。

从开发者视角，我们希望「路由到哪个队列」越简单越好。用标签描述开销水平（low/high）、可否被抢占（false/true）、优先级（low/medium/high/critical）；这些答案加上作业是单节点还是多节点，就共同决定了它最终落入哪个队列。

图 2：开发者视角下，三个标签（spend、preemptible、priority）加上单节点/多节点，完全决定一个工作负载落入哪个队列。

## v0.10 失败在哪里：公平与碎片化

### 公平缺口

我们实现该方案时，**Admission Fair Sharing（AFS）** 尚不存在，系统里只能用抢占式的 Fair Sharing。这让我们无法同时满足多节点场景的这两个需求：

- 基于芯片数在租户之间公平调度
- 该配额内不同团队之间不发生抢占，除非有人显式给自己的 indexed job 指定「critical priority」

秉承开源的贡献精神，我们直接把这一挑战提给了 Kueue 团队；他们迅速回应并推出了 AFS，带来两个关键行为：

- 抢占那些「饿着别的团队」的团队的工作负载
- 调整队列中工作负载的顺序，优先照顾使用量低的团队

对我们而言，这正是支撑任何强大开源项目的最佳反馈闭环：在真实使用中发现需求，再把这些知识反哺给产品。

这也意味着我们有了公平缺口的解法。

### 碎片化问题

我们还碰上第二个问题：有时 Pod 被准入了，却没有单台机器真能满足 Pod 的需求。我们的名义配额总和恰好等于 GPU 总数，所以起初这看起来像个 bug。

暴露问题的是这种情况：每台机器有 8 块 GPU，我们提交一个需要在同一节点上用满 8 块的作业。如果 GPU 容量以 1+1+4+2 的形态散落在四个节点上，配额账面上说有 8 块空闲——但 8 卡作业却无处可落。这正是我们遇到的碎片化。

图 3：GPU 碎片化。散落在四个节点上、形如 1+1+4+2 的 8 块空闲 GPU，放不下一个 8 卡作业。

GKE 尽管尽力做装箱（bin-pack），但在我们的体系中 Kueue 并不是调度器，它不了解我们的集群拓扑（每台机器 8 卡）。

我们找到的修复方案，是 v0.10 中没用到的一个 Kueue 特性：**Topology Aware Scheduling（[TAS](https://kueue.sigs.k8s.io/docs/concepts/topology_aware_scheduling/)）**。TAS 常围绕 gang 调度被启用——例如让分布式作业物理上彼此靠近以降低延迟和成本——而我们的动机不同。

我们经常在集群里空闲超过 8 块 GPU，却没有任何单个节点空着 8 块。一个叫 Topology 的直白自定义资源（custom resource）让管理员可以告诉 Kueue 在调度决策中应考虑哪些拓扑。严格来说 Kueue 不是调度器，但配置了 TAS 之后，Kueue 会在准入的工作负载上设置 nodeName。对我们来说，这就相当于得到了一个新的调度器。

手握 AFS 和 TAS，我们与主要干系人——算法研发负责人——再次聚首。最初的待办清单现在都可解了：

- AFS 允许多节点的公平共享
- TAS 则让 Kueue 能拒绝准入放不下的 Pod；用 LeastFreeCapacity 算法调度，把新工作负载优先装箱到已用得最满的节点上，减少碎片化；并停止做出那些其实腾不出容量的抢占决策。

至此，公平缺口和碎片化问题都解决了。

但就像每场好会议一样，我们从讨论中带着两个新需求离场：

- **可抢占单节点池内部的优先级驱动抢占。** priority=low 的单节点可抢占工作负载可以被同池中 medium/high 的工作负载抢占。
- **一条新的多节点尽力而为（best-effort）通道。** 多节点工作负载可以用 priority=low 选择加入；容量吃紧时它们被 medium/high 多节点工作负载抢占，而在需要时它们仍可抢占单节点可抢占工作负载。

基于我们从 AFS 和 TAS 学到的东西，加上这两个新需求，我们把 Kueue 实现重新设计到了 v0.15 版本。

## 重设计纳入 AFS + TAS（v0.15）

新版本 v0.15 保留了 v0.10 的布局，但加入两处适配以支持我们在首版落地中识别出的必要行为：

- **可抢占容量现在能感知优先级。** 共享的单节点可抢占池按工作负载优先级拆分——priority=low 的工作负载运行在自己的通道里，当 medium/high 工作负载需要空间时最先被抢占。一条新的多节点尽力而为通道同时加入设计：多节点工作负载可以用 priority=low 选择加入，在这里它们需要时抢占单节点可抢占工作负载，自身则被 medium/high 多节点工作负载抢占。
- **准入与放置变得更聪明。** Admission Fair Sharing（AFS）在优先级与时间戳排序之上，现在会根据各团队历史芯片-小时（chip-hours）用量重新平衡队列顺序。Topology Aware Scheduling（TAS）会拒绝准入那些放不到单个节点上的工作负载，并用 LeastFreeCapacity 调度以保持集群装箱紧密。

保障容量（Guaranteed Capacity）与按需容量（On-Demand Capacity）与 v0.10 相比保持不变。

面向开发者的决策树纳入了新通道：

图 4：开发者视角的 v0.15。与 v0.10 相同的三个标签，但 priority=low 现在为单节点和多节点工作负载各自拆出了独立的可抢占队列。

从用户视角，没有新标签、也没有新标签值，所以接口未变。唯一变化的是优先级如何影响工作负载的路由——对多节点和单节点可抢占工作负载，low 现在与 medium、high 分离开来。

## 「改造后」：实施 Kueue 的影响

GPU 不再通过内部团队频道谈判。如今 AI21 的每一个工作负载——无论是单节点 debug pod、多节点训练运行还是推理部署——都会被自动分配到正确的队列。Kueue 端到端自动管理整个流程，无需人工谈判：从排队和优先级排序，到清理以及跨团队的 GPU 使用公平性。

如今 #gpu-resources 频道已经归档。团队负责人不再仲裁 GPU 争夺战，研究员把时间花在实验上，而不是讨要容量。好的基础设施不只是省下 GPU 小时——它让研究员能专注于自己热爱并擅长的事：科学。切换到 Kueue 之后，我们从数字上找回了这些：

### 运营层面的收获

- 每周人工干预次数：20 → 0
- 「僵尸」/部分分配的作业被消灭
- 碎片化比例：15% → 8%
- 每周花在团队消息频道里谈判 GPU 的时间：数小时 → 无
- Hero job 平均被「饿」的时长：72 小时 → 12 小时

## 经验与结语

对所有正在应对集群内 GPU 资源共享挑战的人，这是我们从事人工谈判体系转向 Kueue 自动化管理过程中学到的核心经验：

- **在工作负载级别调度，而不是 Pod 级别。** 原生 Kubernetes 抢占会毫无顾忌地杀掉一个四 Pod 训练运行中的一个 Pod，让另外三个继续烧 GPU。分布式训练要求 gang/全有或全无的准入。
- **队列不理解你的拓扑，就称不上调度器。** 配额账面上有 8 块 GPU 空闲；碎片化（散落在四个节点上的 1+1+4+2）意味着 8 卡作业无处安放。Topology Aware Scheduling 让 Kueue 能拒绝放不下的作业，并把放置钉到已用得最满的节点上优先执行，把队列变成真正会调度的东西。
- **刻意让机群贴着 100% 跑。** 对预留 GPU 机群，满载利用率是目标，不是警报。让它安全的前提，是一条可抢占/机会型通道，借用闲置容量并在回收时归还，这样「满」才不会变成「堵」。

任何训练模型的公司都会告诉你：跨团队共享 GPU 不是一个容易解决的问题。当用量通过内部团队频道异步谈判，或被一刀切地拆成各团队独立集群时，时间与算力效率都会大打折扣。两种方式都有 GPU 闲置、与业务优先级不一致、作业被打断的风险。

只有当我们转向用 Kueue 为团队的单一共享集群处理准入、优先级与抢占之后，容量才真正做到自动分配：跨团队公平、按业务优先级排序、无需人工干预即可回收。
