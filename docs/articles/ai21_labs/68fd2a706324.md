还记得大家都以为 GenAI 会解决……嗯，万事万物吗？是啊，关于那件事。进入 GenAI 革命的第三年，我们已经学到一些关于这些模型能（和不能）做什么的残酷真相。让我们划破炒作，谈谈我们真实的站位——因为下一波 AI 创新，带着真正的 agentic 能力，比你想象的更近。

## 并不简单的当下

企业 GenAI 的实情是这样的：就像一边开着赛车一边造这辆赛车。没错，技术令人惊叹，但要规模化？这才是滋味复杂的地方。最初的实施暴露了我们未曾预料的挑战——基础设施成本比预估高出 40-60%，集成周期比计划拉长 2-3 倍。

在 AI21 Labs，我们开发了 Jamba，一个把 Mamba 状态空间层的效率与 Transformer 注意力的精准结合的混合模型。这一架构支持处理多达 256k token 的上下文，重新定义了金融文档综合、长篇数据分析等企业应用。但也要清醒：没有任何单一架构能解决所有挑战——每种架构都有自己的取舍。

Jamba 代表着 GenAI 的一次关键转向——由用血泪换来的教训和深思熟虑的设计选择驱动。

## 现在真正管用的（和不管用的）

成功、准确的 GenAI 输出，秘方不在单一成分——而是一套多种互补方法组合成的配方：

### 1. RAG（检索增强生成）

‍把它想象成给 AI 一场开卷考试。通过在推理时提供相关信息，RAG 让模型能更精准地回答复杂问题。模型拥有的相关上下文越多，输出越好。

不过，RAG 实现常常在以下方面挣扎：

- 数据质量问题导致结果不一致
- 大规模检索的计算成本高昂
- 与现有数据库的集成要求复杂

### 2. 系统化工作流

‍把大问题切成小块。早期的"agentic"工作流依赖僵硬的、基于规则的"静态链"来保证准确性。AI21 的对话式 RAG 引擎就是这种方法的范例，通过一步步构建任务来提升输出质量。

- 在构建 RAG 引擎的过程中，我们学到了残酷的一课：

- 早期的"agentic"工作流太僵化、太脆弱
- 错误处理需要比最初设想的更精密
- 对复杂任务，人工监督仍然关键

### 3. Prompt 工程

- **‍**这个时髦的说法描述的是"与模型对话"的艺术，教会你的 AI 说你的语言。有点像当一名模型低语者。提供定制的 prompt——有时配上"few-shot"示例——能显著提升表现。

虽然 prompt 工程能大幅提升表现，但它不是银弹：

- 不同模型的结果差异巨大
- prompt 库的维护日益复杂
- 随着模型演进需要持续更新

### 4. 长上下文处理

- **‍**因为有时候你需要整个故事。长上下文为什么重要？Databricks 的研究表明，上下文增加，准确率也随之增加。对现实任务，更长的上下文窗口没有商量余地。

更长的上下文窗口提升准确性，但也伴随取舍：

- 处理成本大幅上升
- 内存需求可能令人却步
- 并非所有任务都同等受益于扩展上下文

4 个精选 RAG 数据集上的长上下文表现——Databricks

把上述策略组合起来——过往示例、一套自我校验的系统化方法、全面的上下文——你就在喂给模型一座数据山。想想处理 Google、Meta、Amazon 和 Microsoft 各 10 年的 10-K 报告，那是 16,000 页的上下文！长上下文不只是有用——它是颠覆性的。

## Transformer 的问题

但坑在这里：Transformer 架构统治着 GenAI 市场（如 GPT、Claude），却在处理超长上下文时撞上墙。Transformer 贪吃内存，在大输入规模下慢得痛苦。即便号称支持长上下文的模型，实践中也很少超过 100k token。

玩过基于 Transformer 模型的人大概也注意到，尽管某些模型声明了很长的上下文窗口，它们实际消化不了 100k token 以上。

这时 **Mamba** 登场——一个状态空间模型，Transformer 的第一个真正的替代者。虽然更高效，Mamba 的准确性还够不上 Transformer 水准……这正是 **Jamba** 来的意义。

## Jamba：两全其美

Jamba 是 *Joint Attention and Mamba* 的缩写。这是我们创新的架构，结合了：

- **Transformer 注意力层**，带来无出其右的准确性。
- **Mamba 层**，带来效率与吞吐。

每个 Jamba "block" 包含七个 Mamba 层和一个注意力层——在质量与可扩展性之间取得完美平衡。下面你会看到，在衡量有效上下文长度的 NVIDIA RULER benchmark 上，Jamba 设立了新标准。我们的模型在多达 256k token 上表现出色，远超竞争对手。

**为什么这很重要：**有了长上下文能力，Jamba 赋能这样的用例：

- 解析数千页的财务报告。
- 综合历史数据以获得高级洞见。

### 长上下文 benchmark：NVIDIA 的 RULER

NVIDIA 的 RULER benchmark 测试模型处理长上下文的能力。它取代了"大海捞针"这类旧评估——后者专注于在海量文本中寻找随机字符串，但并不衡量对大上下文的意义性理解。

RULER 评估模型的有效上下文长度——它们实际能处理和使用的数据量。虽然该 benchmark 止步于 128k token，我们的内部测试表明 Jamba 是唯一能到 256k token 的模型。

GitHub 排行榜说明了一切：Jamba Large 稳居第一，Jamba 紧随其后位列第三。

## 来自前线的关键教训

### 我们搞错了什么

- **初始成本预估**——基础设施成本通常超出预估 40-60%
- **实施时间表**——视公司数据科学成熟度不同，项目有时比计划花 2-3 倍时间
- **技能要求**——某些团队培训需要 6 个月以上，而不是预期的 6-8 周
- **数据准备**——消耗了 60% 的项目时间，远超预期

### 我们学到了什么

#### 1. 技术现实检查

- 上手 GenAI 容易，但为企业使用做规模化比预期的难得多
- 标准的现成语言模型很少能为企业使用做好准备——它们运行昂贵，准确性也不够
- 成功部署 GenAI 需要系统架构与优化方面的深厚技术专长

#### 2. 聊天界面的力量

- 游戏规则改变者是从基础 AI 模型转向对话式"chat"界面
- 这一转变让 GenAI 对用户友好、易变得多
- 更多人无需技术知识就能开始使用 GenAI

#### 3. 企业部署需求

- 公司需要灵活的 GenAI 运行位置选项（云、自有服务器或混合）
- 安全顾虑常常意味着自建基础设施
- 成本管理至关重要——算力和 API 调用都是
- 公司必须优化资源使用以维持合理成本

#### 4. 把准确性做对

- 一次准确性检查不够——你需要多层校验
- 你给模型的上下文越多，它表现越好
- 组合多个 AI 模型有助于减少错误和偏见
- 常规测试与验证是保持质量的必需

## 真实用例：金融 Term Sheet 生成

Term sheet（投资条款清单）正是最适合自动化的任务之一。银行员工天天处理它们——重复、标准，只需要基本信息提取和格式化的文档。它乏味、耗时、低价值。用 Jamba 这样的长上下文模型自动化这一过程，省时间、提准确性，并让员工聚焦于更有影响力的任务。以下是实现路径。

### 从核心设计价值出发

构建 GenAI 解决方案意味着聚焦这些关键原则：

- **用户控制：**我要有打磨输出的灵活性。
- **系统化方法：**为了提高准确性，我要能为正确的任务挑选正确的工具。
- **上下文化输入：**我会在推理时提供所有相关数据以增强模型表现。

以这些价值为地基，我们来看它如何落地。

### 第 1 步：上下文化输入与要点

- **输入数据：**从原始输入开始，如语音转写记录或其他记录。
- **人在回路：**用 Jamba Mini 从输入中提取并验证关键要点。这些经过验证的要点稍后还将充当准确性检查的锚点。

### 第 2 步：用定制 Prompt 生成

生成 agent 负责两个主要过程：

- **为 Few-Shot Prompt 做 RAG：**不是检索数据直接使用，而是用检索增强生成（RAG）挑选相关 term sheet 的范例。这一步确保模型采用适合任务的正确语气、结构和上下文。
- **带上下文的生成：**组合输入数据、关键要点和定制范例，生成 term sheet 初稿。这确保模型在推理时拥有全部相关上下文，带来精准而贴身的输出。

### 第 3 步：为质量保证做验证

验证对于确保输出达到高标准至关重要。

- **要点核验：**把生成的输出与已验证的关键要点交叉检查。
- **独立评审：**用另一个模型（如 Claude）充当裁判，对生成内容给出反馈。这种多模型方法减少偏见、提升可靠性。

### 成果

最终产出的是一份高质量 term sheet，生成更快，并内建准确性检查。

### 真实世界已被验证的成功

我们为一家领先的国际银行部署了类似方案，在保持严格准确性与合规标准的同时自动化了 term sheet 生成。这些同样的设计模式如今应用于其他用例，证明了 Jamba 的灵活性与可扩展性。

### 随处无缝部署

Jamba 的突出优势之一是它的开源底座，允许在任何需要的地方部署——本地、云端或混合配置。这种灵活性为企业用户确保安全和控制，而 Jamba 出色的 benchmark 成绩强化了它的价值。

Jamba 帮你构建强大的 GenAI 应用：融合深厚专长、聪明设计与能在企业规模运行的灵活部署。今天就能满足你的需求，为明天的自主 AI 而生。

## 下一个前沿：Agent

GenAI 的未来在于 agentic 工作流——能够适应复杂任务的动态系统。不同于今天僵硬、顺序的自动化，真正的 AI agent 将会：

- 处理长上下文，随新信息动态调整。
- 自主探索不同的行动路径。
- 从失败中学习，实时转向。

要让这一愿景成真，模型需要*极*长的上下文窗口，以及整合多种工具与信息源的能力。技术在演进，但我们才刚刚触及表面。

不过，虽然 GenAI 的未来在 agentic 工作流，我们必须对当前的局限保持现实：

- 真正的自主仍然是一大挑战
- 错误恢复能力仍然原始
- 跨工具与系统的整合需要改进
- 成本与资源需求可能令人却步

## 前路

GenAI 早期的炒作描绘了一幅可能性无限的图景。实践中，旅程要沉稳得多。准确性、可扩展性与动态适应力仍是挑战——但我们正在进步。

GenAI 早期的炒作描绘了一幅可能性无限的图景。实践中，旅程要沉稳得多。虽然我们在准确性、可扩展性和动态适应力等方面取得了长足进展，重要挑战依然存在：

- 基础设施成本需要进一步下降
- 集成流程必须更加标准化
- 安全与合规框架需要走向成熟
- 团队培训与发展需要持续投入

Jamba 的成功展示了当你把创新的架构、深思熟虑的设计与企业级执行力结合时可能的成就。这项技术不是魔法解决方案，但当它以现实的预期和周密的规划被谨慎实施时，它能交付巨大的价值。而当我们迈入 agent 的时代，最好的尚在前方。

GenAI 不只是在兑现预期——它在重新定义预期。
