太长不看

*在给你的智能体（agent）投入更多算力之前，先问这一句：你的智能体能验证自己的结果吗（也就是说，它能认出自己已经拿到了正确答案吗）？对某些任务来说，可验证性很直接：任务本身就交给你检查候选的条件，以及何时停手的判断依据。对另一些任务，就没那么清楚了。本文要谈的是：为什么恰恰是这一个属性——可验证性——应当决定你下一步把预算花在哪里：完成度可检查时，投资验证；不可检查时，投资多样性与聚合。*

## 反对"先扩容"的默认答案

去问大多数工程师怎样改进一个智能体，多数人会说：扩大规模（scale it）。更多尝试、更长且强化过的上下文、更强的模型。这个回答默认当前架构已经是对的——只是劲儿不够大。多数时候，扩大规模确实有效，但它是最贵的那条路。

一年多的智能体优化研究里，我们一遍又一遍地看到这个假设（架构正确、只是算力不足）为什么不成立。破绽就出在发现架构内部的低效：给参差的任务套用统一的预算、生成出信号和 rollout 却又把它们丢掉、在开源模型就够好的情况下硬跑 frontier 模型。每一个这样的时刻都意味着：在扩大规模之前，智能体的架构还有进一步优化的空间。

**有一条简单的试金石：候选答案能不能拿什么东西来检验？** 这是任务的属性，它会让你的架构分岔。能，就投资验证与选择（selection）；不能，就投资多样性与聚合（aggregation）。

然后是第二个问题，它关于你的管道而非任务：管道是否已经用尽了它手头可得的那个检查？这一个问题，我们用 oracle 实验来回答。

图 1.

智能体架构的决策框架。起决定作用的问题是候选答案能否被验证——这是任务的属性，而不是模型的属性。可验证的任务偏向把钱投在验证与选择上；不可验证的任务偏向多样性与聚合。

验证机制能换来的只有一样东西：允许你押定某一个候选、把其余全部扔掉。当你造不出验证机制时，多样性与聚合就是替身：跑出各种各样的尝试，再把它们合并——因为没有检查，你无法安全地押定其中任何一个。

本文中，我们用这块试金石检视四个领域的智能体管道——agentic search（智能体式搜索）、deep research（深度研究）、RAG 索引、agentic coding（智能体式编程）——并用我们得到的答案去优化既有架构、提升每一处的表现。

## **任务 #1：Agentic Search**

**智能体能认出自己拿到了正确答案吗？能。答案是一个单独的实体，而条件是明确给出的。**

一道多跳（multi-hop）智能体搜索题用条件来限定它的答案，而答案是一个简短的单一实体，比如某一个人。正是这种形态让检查变得高效：拿明面上给出的条件去验证一个实体，覆盖的空间比原始搜索窄得多。

换一种形态，答案也跟着变。改成问"所有母亲没读完高中的诺贝尔奖得主"，你找到的每个候选依然可检验，但"是否已经全找到了"不可检验——因为确认完整性等于重跑一遍搜索。精确率（precision）依然可验证，覆盖率不行。同样的分裂会在任务 #4 再次出现。

在动手构建任何东西之前，我们先跑了一次 oracle 实验：直接依据 ground-truth 答案来做选择，从而造出一个任何运行时系统都不可能超越的天花板——因为没有真实系统真的看得到这些答案。这么做很容易，而且它能很快把策略淘汰掉。例如我们看到 pass@k 远高于 pass@1，说明正确答案常常在许多次尝试中出现过，但单独某一次尝试通常不会是找到它的那一次。

知道答案本来就在候选池里——只是没被选中——帮我们把注意力对准了验证。我们展示两种改进验证信号的做法，只在质量确实值得付费时才付费：

**等着被利用的免费信号。** 在 BrowseComp-Plus 上，模型自身的置信度分数经过校准后，与准确率的贴合程度足以用来做选择。搭配一个"在不同查询上各自失败"的模型集成，[这套做法达到 95.18% 的准确率并创下 state of the art](https://www.ai21.com/blog/maestro-deep-research-agents/)。

**值得为之付费的信号。** 置信度是自我评估，因此它不会带来任何关于世界的新证据，而模型完全有可能同时又错又自信。当生成器足够强、校准足够好时，这是可以忍受的。

在 FACTS-Search 上测试小模型集成时我们看到了这一点。事实是，小模型经常产出错误答案——只要错误答案人气够高，多数投票（majority voting）就翻不了盘。所以我们把置信度分数换成一个[独立验证器（independent verifier）](https://www.ai21.com/blog/you-need-a-verifier/)：它从零开始重新研究每个候选，并否决错误的那些。

我们训练了自己的 8B 验证器，在"开源 + 闭源"模型集成上追平了 frontier 验证器的质量——成本低 3.2 倍。把同一个验证器用于纯开源集成时，在完全相同的候选之上，它比朴素多数投票把准确率提升了 28%——那个候选池上 frontier 验证器所能拿到的收益，它拿到了八成以上，而价格大约只有 1/100。

图 2.

单一查询上，多数投票对比"先验证再投票"。六次采样尝试给出三个不同答案（A ×3、B ×2、C ×1），其中只有 C 正确。多数投票选中 A。独立验证器在聚合之前就把 A 和 B 否掉，对存活的候选投票则选中 C。

## **任务 #2：Deep Research**

**智能体能认出自己拿到了正确答案吗？不能。没有办法知道一份完整的报告应当包含什么。**

deep research 任务要求智能体调查一个开放性问题并产出一份报告。让报告优秀的是覆盖率：它呈现出来的相关事实、发现与注意事项的集合。没人能提前把这个集合写下来。对比任务 #1——那里问题自带的条件本身就是清单；而这里的目标是一个没人能在完工之前枚举出来的集合。

这把任务一分为二。报告中任何单条论断都可检验，就像那份诺贝尔名单上的每个名字都可检验一样。但报告是否完整则不可检验，因为确认完整性等于重做一遍研究。精确率保住了，覆盖率没有——而评判一份报告靠的恰恰是覆盖率。

[DeepResearch Bench II](https://agentresearchlab.com/benchmarks/deepresearch-bench-ii/index.html#home) 把这点讲得很具体：它按一长串由专家撰写的评分细则（rubric）条目给报告打分，权重极大程度地压在"答案应当包含哪些具体事实"上。这些条目在评分前一直保密，但保密并不是根本问题。在生产环境里，你会很乐意把评分细则直接交给模型。要点在于：这份清单只能由专家事后建起来，因为没有办法事先产出它。而在生产环境里，压根就没有清单。

于是在真正要紧的指标上，没有任何验证器能把一份报告排在另一份之上。这里我们只能把多样性与聚合当作策略，而这正是要点所在：它们不是验证的替代品，而是验证缺席时的退路。

所以我们跑了几次 [oracle 实验](https://www.ai21.com/blog/merging-weak-agents-into-a-state-of-the-art-deep-researcher/)，这次涉及两种策略：

- **选择（selection）**，也就是任务 #1 里奏效的那一招，意味着只留下最好的那一份报告、丢掉其余。即便用上 oracle 选择器，天花板仍然低于 state of the art——这正是前面那个结论以数字形式落地：没有检查，押定单一候选就是输。
- **合并（merging）** 意味着拿若干份报告，把它们的事实整合成一份；用 oracle 合并器时，天花板稳稳越过 SOTA。

图 3.

DeepResearch Bench II 上各报告的评分细则覆盖情况（示意）。列代表中游排名的单个智能体各自产出的报告；行代表评分细则条目；填充的格子表示覆盖。每份报告都只覆盖少数条目，且报告之间的覆盖相关性很弱，因此合并后的报告几乎覆盖了全部条目，而没有任何单份报告接近它。这与 oracle 结果一致：选择的天花板被压在 state of the art 之下，合并则没有。

合并所得分数与已发表 SOTA 之间的那段差距说明，正确的事实本来就在那里——只是散落各处。

于是我们搭了一条管道，把这些事实全部汇集到一处。用我们自己设计的算法，我们把排行榜上七个低排名智能体的报告合并起来，让一份报告继承它们全部的事实。**这份合并出的报告拿到了第一名，超过产出它的每一个智能体，也超过此前的 state of the art。**

## **任务 #3：RAG 索引**

**智能体能认出自己拿到了正确答案吗？不能，而且它还不知道将来会被问什么。**

索引也许是可验证性面临的最大挑战之一，因为决策——chunk 要多大？——必须提前做出，在任何问题被提出之前。一份政策手册既要回答"4.2 节里精确的提前通知期是多久"，也要回答"和客户吃晚餐能不能报销"。前者由一行文字就能答完；后者只能靠文档另一头的若干条规则共同回答，而它们单独任何一条都不是答案。[押定单一 chunk 尺寸，会把 20-40% 的召回（recall）白白留在桌上。](https://www.ai21.com/blog/query-dependent-chunking/)

图 4.

依赖查询的 chunk 粒度。同一份文档上的两个查询需要大小不同的检索单元：第一个只要一行，第二个要若干小节。由于 chunk 尺寸在索引时就固定下来、早于任何查询到达，没有哪一种粒度能同时服务两者。

这正是我们需要多样性的一个例子。没错，以多种分辨率建索引要多花存储、要多做 fan-out，但这是正确的取舍（你能想象一个客服助手为了省钱而放弃检索到正确答案吗？）。无法验证并不总是意味着少花钱。

## **任务 #4：Agentic Coding**

**智能体能认出自己拿到了正确答案吗？结尾处能，中途不能。**

编程任务的验证很复杂，这既让它成为最有用的案例，也让它成为最常被误读的案例。

在一次运行的末尾，检查硬到不能再硬：测试要么通过要么不通过，而你没法把两个 patch 合并成一个更好的 patch。而在运行过程中，什么都没有。你可能已经触及仓库的大部分内容，却依然无法排除某些文件。

所以，尽管末端条件是二元的，中间过程却受覆盖率约束——这让编程智能体看起来非常像一个召回问题（或者一份 deep research 报告）。我们在实验中看到了这一点：把候选 patch 一起喂给上下文检索，而不只是给 issue 描述，让管道在"找齐所有相关文件"上强了许多。这么做之后，智能体漏掉全部相关文件的 issue 占比从 9.3% 降到 2.7%，[换来 resolve rate 提升 3.2 个百分点](https://www.ai21.com/blog/first-scale-then-enrich-how-the-right-execution-strategy-helped-us-reach-state-of-the-art-on-swe-rebench/)。召回大幅提升却只换来准确率小幅增益，这正是"把一个不可验证的步骤当成可验证来对待"的指纹。

为了让每个步骤匹配它自身的可验证潜力，我们给它们分别配置了不同级别的模型。初级模型（开源 MiniMax-M3）并行地在仓库里铺开探索，覆盖那些没人能确认是否已被覆盖的部分。一个高级模型（GPT-5.2）把它们的尝试提炼成"这个修复依赖于什么"。只有到那时，牵头者——一个 frontier 模型——才动笔写一次 patch，而那正是唯一存在真实检查的时刻：[在 SWE-Bench Pro 上 80.8% 的 resolve rate，state of the art](https://www.ai21.com/blog/better-and-cheaper-together-open-models-explore-frontier-models-patch/)，每个任务 $5.99，而得分更低、独自作战的 frontier 智能体要 $18.28。

图 5.

按可验证性划分的编程管道。初级开源模型并行探索仓库；高级模型把它们的轨迹（trajectories）提炼成一份关于相关函数、调用方与测试的简报；牵头的 frontier 模型一次性生成 patch。frontier 推理被限定在唯一带有正确性信号的阶段——测试套件。

## 总结

上面每一项都始于一次廉价的度量，而不是一个更大的模型：把 pass@k 与 pass@1 放在一起读、给验证器和生成器比价、数一数评分细则条目、跑一次 oracle 实验。模型还会持续进步，但这不会改变这一点：智能体能否认出自己的成功，是任务的属性，而不是运行它的那个模型的属性。先问这个。再决定你是否还需要扩大规模。
