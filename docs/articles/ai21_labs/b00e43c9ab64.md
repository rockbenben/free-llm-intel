Agentic benchmark 可能有数百个问题，每个问题需要几十步。要获得统计置信度，你得把它们跑很多遍。加起来就是数万次运行——而为简短、线性执行设计的评估方法，在 agent 轨迹变得冗长、分叉、有状态之后就撑不住了。

在把我们测试时计算（test-time compute）agentic 框架 **AI21 Maestro** 应用于 SWE-bench Verified 的过程中，我们运行了**超过 200,000 次评估**。本文中，我们介绍为规模化解决这些挑战而构建的评估架构，并分享面向在生产中评估 agentic 系统的开发者、AgentOps 和 MLOps 团队的实战经验。

## 为什么 agentic 评估是个基础设施问题

评估一个标准 LLM 已经非平凡，而 agentic 系统带来的层层复杂性，并不是一次性评估管道在设计上能应对的。因为像 AI21 Maestro 这样的 agent 是有状态、主动参与的——穿行于代码库、执行终端命令、反复迭代——挑战更少关乎方法论，更多关乎**基础设施瓶颈**。

要在规模上达到统计置信度，我们必须解决三个具体的技术约束：

- **吞吐之墙（时长与重复）：**与毫秒级响应的聊天机器人不同，一次 agentic 运行是高延迟、多步骤的工作流。再算上**重复度（Duplicity）**——同一 benchmark 实例要在多个随机种子下重复运行以测量方差——你就面临巨大的算力开销。我们不只是在跑一次测试，而是在编排数千个并发、持续数分钟的有状态会话。
- **状态碰撞（隔离需求）：**Agent 有写的能力——它们修改文件系统、改变环境状态。为确保评估完整性，每条轨迹必须严格隔离，防止一个 agent 幻觉出的代码变更毒害下一个 agent 的环境。这带来巨大的容器编排挑战：如何供应数千个全新沙箱，而不让开销拖垮性能？
- **可靠性税（可续跑性）：**在 200,000 次运行的战役中，基础设施故障（pod 驱逐、网络抖动、runner 超时）是统计学上的必然。在长时间运行的评估里，一条 2 小时的轨迹在 99% 处丢失是对 token 和算力的巨大浪费。我们需要一种解耦架构，把**生成**（制作补丁）与**评估**（跑测试）分开，实现细粒度的可续跑。

这些不只是理论障碍，它们正是导致我们最初的本地实现和天真 Kubernetes 实现在负载下失败的主要技术摩擦。

## 尝试 #1："本地优先"的假设撞上云现实

SWE-bench 的官方代码是为本地运行写的。它假设你有一个 Hugging Face 缓存目录以避免重复下载 benchmark，并且它会为推理和评估分别启动 Docker 容器，想当然地认为 `docker run` 总能用。

实践中，有意义的评估不会发生在本地机器上——除非是初始调试阶段。本地运行适合快速迭代和设断点，但规模化评估需要真正的基础设施。我们的是基于 Kubernetes、通过 Argo Workflows 编排的环境——在这里我们可以可靠地度量性能、质量和我们在意的白盒指标，同时享受弹性、容错和集群 HPA 带来的水平扩展。

不幸的是，SWE-bench 的假设没有一条在 Kubernetes 上成立。

首先，全新的 pod 不存缓存数据。原样运行 SWE-bench 代码的结果，是每个 pod 启动时都试图从 HuggingFace 下载 benchmark。在规模上，我们开始撞上 429 限流——不是因为什么高深攻击，只是因为我们意外地把同样的文件请求了成千上万次。

其次，很明显，把 SWE-bench 代码原样搬进我们的 Kubernetes 环境行不通。你不能在 Kubernetes pod 里简单地 `docker run` 就指望一切顺滑。容器内容器执行需要特权访问、增加开销、让资源管理变复杂。我们必须修改运行代码的方式，使其兼容我们的测试环境。

## 尝试 #2：改造 SWE-bench 代码

第二次尝试，我们保留了 SWE-bench 原有基于 Docker 的评估逻辑，并让它在我们的 Kubernetes 环境内工作。我们改造了代码，使每次评估运行都在运行评估的 Kubernetes pod 内供应一个全新的 Docker 容器：下载仓库、安装依赖、执行 AI21 Maestro、评估生成的补丁，然后完成时拆掉一切。

在 SWE-bench 的规模下，这笔账很快大得惊人。约 500 个实例，跑两种变体，每次运行还要重复多遍来测量方差（比如重复度 4、8、16），意味着单个评估窗口内要供应和拆除约 16,000 个 Docker 容器。

它跑起来了——但很慢，且因资源争用和外部限流而有显著失败率。

我们必须找到为系统减负、提升在线率的方法。

## 尝试 #3：跨运行共享资源

真正的"顿悟"时刻出现在我们盘点每次运行中到底什么是唯一的、什么可以在该实例的所有运行间共享之后：

如果我们能把运行之间共享的东西预先供应好——然后让后续多次运行使用这些资源呢？换句话说，如果能让模拟环境变成多租户的呢？

于是我们把评估栈精简为类似这样的架构：

为了测试这个新的多租户模拟环境，我们在 Kubernetes 集群中部署了约 500 个 pod（每个 SWE-bench 实例一个）。每个 pod 包含上述共享资源：

- **仓库**，检出到正确的 commit
- **MCP server**，随时可执行命令
- **已安装的依赖**，跨运行持久存在

这些 pod 只需供应一次（在评估开始时），随后即可服务针对同一 SWE-bench 代码实例的数十次 AI21 Maestro 运行——无论这些运行是串行还是并行。这乍看有悖直觉：在同一实例上跑多条轨迹显然会打架，仓库文件被先手改变。正因如此，我们扩展了 MCP 协议，并为隔离环境开发了专用的 MCP 客户端。

## 行家建议：内建可续跑性

我们把评估系统设计成生成步骤与评估步骤明确分离：

- 生成步骤：AI21 Maestro 分析 issue、探索代码库并产出补丁
- 评估步骤：应用补丁、运行测试套件、判定 issue 是否解决

如果某次运行在评估阶段失败——比如测试 runner 超时或 pod 被驱逐——我们不需要重新生成补丁。生成产物已被持久化，我们只需重跑评估步骤，省下生成耗费的全部时间和 token。

这也支持处理部分完成的数据。如果 80% 的运行成功完成，我们就能分析这些结果，同时重试或调查剩下的 20%。不必等 100% 完成才能学到有用的东西。

## 扩展多租户模拟环境

多租户模拟环境就位、指标接入之后，我们转攻规模化。当前的 SLA 支持跨所有评估的 10,000 次并行运行；下一步，我们计划通过在同一 pod 上加入多个执行器，把这一数字至少推高 10 倍。

那种每次运行都单独供应的模式，连同它的限流和资源争用瓶颈，永远不可能让我们达到多租户模拟环境所支撑的规模：

达到这种规模，不仅是对任何方法建立统计置信度的必需，它还能暴露小规模测试看不到的系统效率洞见。你需要数千次运行——镜像企业 AI 系统在真实世界的预期用量——才能识别并度量这些效率。

当你能在一天内跑 35,000 次隔离评估而不用启动 100,000 个容器，你就能像我们迭代模型那样迭代 agent：用数据、高速、且胸有成竹。
