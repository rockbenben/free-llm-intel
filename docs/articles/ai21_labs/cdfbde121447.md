## 简要说明

[DeepResearch Bench II](https://agentresearchlab.com/benchmarks/deepresearch-bench-ii/index.html#home)（DRB II）是一个 benchmark，用 132 个任务、9,430 条专家撰写的评分细则为 deep research agent 打分。我们以 **64.38** 的 TotalScore 登顶第一——比此前报告的最佳成绩**高出 3.2 分**。做法是：把较弱 agent（排行榜第 7-13 名，没有一个超过 45 分）的输出合并起来。

***图 1：** 2026 年 6 月 24 日的 DRB II 排行榜，我们的参赛系统（AI21）位居第一，TotalScore 64.38。*

## **六个月涨了 20 分：变了什么？**

大约六个月前，DRB II 上最好的 deep research agent 得分约为 45。自那以后，这个领域做了所有领域都会做的事：造出更强的 agent——更好的编排、搜索、任务分解，底下更好的模型。每一分进步都来自把单个 agent 变得更强。

我们想问一个不同的问题：不是"我们如何造一个更强的 agent？"，而是"从已有的这些 agent 里，我们还能榨出多少？"

这个问题值得问，因为 deep research 的本质如此。给定一个真实任务（比如"评估投资电动车充电基础设施的收益与风险"），agent 工作几分钟、搜索网页、写出一份长报告。难的不在写作，而在信息召回（Information Recall）：浮现出答案所依赖的那些具体、可验证的事实，不漏掉要紧的。而信息召回有一个写作不具备的性质：两份平庸的报告很少漏掉相同的事实。一份缺失的地方，另一份多半补上了。事实早已存在，散落在市面上的各份报告里，只是没有人把它们拼到一起。

于是我们来拼。通过合并那些没人会称为最先进的 agent 的输出，**我们没有创造任何一个新 agent，就登上了排行榜首位。**

*对那个显而易见的质疑——"登顶排行榜"听起来像"刷 benchmark"——先做个简短说明：恰恰相反，这里是 boosting，一种通用的集成技术，DRB II 只是我们展示它的地方。该方法只要求对同一任务有若干多样化的尝试——完全可以是来自你自己的。*

## **动手之前先理解任务**

在写任何代码之前，我们先花了第一份精力去分析"做得好"到底需要什么。

DRB II 从三个维度衡量一份研究报告，每个维度以细粒度评分细则的通过率计分：

***图 2：** DRB II 从三个维度为报告打分。Information Recall 在评分细则数量上占绝对主导（每任务 52.9 条，Analysis 为 12.8 条、Presentation 为 5.7 条），因此它驱动了大部分分数。*

每条评分细则都在衡量同样的维度，所以评分细则的构成比例告诉你分数主要反映哪种能力（这对任何由众多等权检查项构成的指标都成立，不限于这一个）。在这里，最重要的是 Information Recall。

恰好，我们需要的报告早已公开。排名第 7-13 的 agent 把完整输出发布在 [Hugging Face](https://huggingface.co/datasets/muset-ai/DeepResearch-Bench-II-Dataset/tree/main) 上。我们下载它们、重新实现指标，并对照排行榜确认复现了每个 agent 的精确分数。我们的起点不是白纸，而是每个任务的七份完整报告——总体没有一份超过 45 分，其中最好的一份也比前任榜首的 61 分差着 16 分。

## **Oracle 实验：那里已经有多少？**

接着我们跑了 oracle 实验：在持有标准答案的理想化流程下，测量这七份弱报告合起来究竟包含多少相关信息——在投入任何真实算力之前。我们试了两种。Oracle *selector*（选择器）为每个任务从七份报告中挑出最好的单份；oracle *merger*（合并器）把多份报告合成一份。

**图 3：** *与其选出最佳的单份报告（0.56），Oracle Merger 跨多份报告合并各项评分细则上的最佳贡献，得分 0.70。*

结果清晰得惊人：每个任务只挑一个胜者，你仍然达不到当前 SOTA。

但 merger 轻松越过 SOTA，证明这七份报告合起来远多于任何单独一份。而且它不只是把事实列表拉长：因为不同报告覆盖不同领地，合并提高了 Information Recall、支撑了更深的分析，甚至读起来更顺。

我们还发现这些收益平滑可扩展：只合并最好的 4 份报告就已超过排行榜 SOTA，随着加入更多报告，质量持续上升——形成了一个成本与质量之间的旋钮。

一个微妙之处让合并更有威力。Information Recall 有上限（你不可能超过所有输入中存在的既有事实），但**分析**没有：融合各自只看到部分图景的报告，能浮现出任何原始报告都不含的跨源洞见；即便在事实重叠的地方，不同报告对它们的推理方式也不同，所以汇集多方视角本身就能锐化分析。**信息一直都在**，只是散落的；提升分数的，正是"把它们聚到一起"这个动作。

***图 4：** Oracle-merge 的质量随合并候选数（k）上升。仅合并 7 份报告中最好的 4 份（0.646）就已超过 0.61 的排行榜 SOTA，收益随接近全 oracle 上限 0.70 而递减。*

## **方法：凝聚式两两合并**

Oracle 证明了头部空间是真实的；问题是如何在没有标准答案的情况下把它拿到手。我们的答案是凝聚式（agglomerative）合并：不做挑选或重写，而是反复把报告两两融合成一份，直到只剩一份，继承所有输入的事实。我们之所以两两进行，是因为一次合并越少，保留的事实越多——下面会看到。

方法分两个阶段：生成候选报告，然后合并。大多数尝试集中在第一阶段——生成新的、更好的报告；而第二阶段，任何能产出多样化、合理尝试的 agent 都可以，这就是我们能从公开输出取材的原因。

对每个任务，我们拿这七份报告跑一次凝聚式合并，反复把候选合并为一体，直到只剩一份报告。每次合并由 Gemini 3.1 Pro 执行，prompt 刻意保持简单：保留两份输入中的每一条事实，并调和冲突。输出是 132 份合并报告，每任务一份。

这正是聚合胜过锤炼单个 agent 的原因。单个 agent 一开始就押注一种分解方式，下游一切都被它继承：漏掉一条线索，就处处都漏。合并多个独立 agent 的 rollout，则大幅提高"每个回答部分都被某条 rollout 覆盖"的概率。**没有哪个 agent 足够好，但它们合起来覆盖了整个空间。**

主要的杠杆是每步合并多少候选——一个干净的速度-质量旋钮。例如，一次两份能产出最好的 Information Recall（上下文里只有两份报告，模型几乎不漏任何东西），但也最慢，要六步才归并为一份。你可以通过增加候选数来减少步数（三份候选要四步；七份一起只要一步），但随着报告挤占上下文，准确性会受损。更大的合并步长会抬升 Presentation，但压低 Information Recall 和 TotalScore，而 Presentation 权重太低，补偿不回来。

由于 Information Recall 承载了分数、任务对延迟又不敏感，我们最终采用了两两合并；但旋钮就在那里可以拧：延迟敏感的部署可以用更大的步长，只放弃几分，换来少得多的串行合并。

***图 5：** 每步合并的候选越多，步数越少但准确性越低：Information Recall 与 TotalScore 下降，Presentation 上升。我们发布的是两两合并版（每步两份）。这里的分数来自合并步长的消融实验；最终报告结果为 64.38。*

（还有一个我们尚未拉动的杠杆，是很有前景的下一步方向：合并顺序，它需要一个平凡的相似度函数。先合并最不相似的报告，可以让每步的重叠最少。）

## **结果**

我们的管道得分 **64.38**：**DRB II 第一，超过此前 SOTA 3.2 分**——建立在排名第 7-13 的 agent 之上，合并的是单份得分在 38 到 45 之间的报告。

## **下一步**

造一个像样的 agent 越来越便宜。有了 Claude Code 或 Cursor 这样的工具，搭一个能产出合理报告的 research agent 几乎已是大宗商品，这样的 agent 数量只会增长。瓶颈已经不是"你能不能造出一个好 agent？"，而是"你能从已有的那许多个里得到什么？"

**答案是：远比其中任何一个单独交付的要多。**当成功意味着覆盖事实，而事实散布在独立尝试之间时，我们证明了合并 agent 胜过锤炼单个 agent——甚至不需要你自己拥有任何前沿模型。**你合并的尝试数量是一个旋钮**：我们从榜上最便宜、最旧的报告起步就拿到了第一，若从更强的 agent 出发，也许两份就够。
