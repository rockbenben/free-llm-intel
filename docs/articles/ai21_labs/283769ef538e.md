摘要（TL;DR）

在开发一款新的 Jamba 模型时，我们注意到它每千条 prompt 会有一次生成完全胡言乱语的内容。定位并解决这个 bug 把我们带进了 vLLM 的核心，最终触及它的调度器与不同模型架构之间的交互方式。除了[在下面分享我们的修复](https://github.com/vllm-project/vllm/pull/32118)，我们也分享过程中学到的关于调试 vLLM 这种庞大代码库的经验。希望这份详尽的复盘能让你下一次 vLLM 调试之旅少一些畏途。

## 问题：干草堆里的胡话

在 AI21 Labs，我们从零构建并训练自己的 Jamba 系列 LLM。在开发 [Jamba Reasoning 3B](https://www.ai21.com/blog/introducing-jamba-reasoning-3b/) 时，我们在强化学习（RL）训练流水线里发现了一个令人担忧的现象：模型偶尔会生成纯粹的胡言乱语。不是那种微妙的质量退化，而是彻底的疯话。

我们靠监控各次生成的最大 logprobs 捕捉到它。Logprobs 衡量模型置信度——数值越接近 0，确定性越高。通常，劣质生成伴随低置信度。但我们的胡话却有高置信分数。模型自信地犯错，说明有东西深深坏掉了，而不只是输出质量差。

*每个尖峰都对应模型生成的一段胡话。x 轴为训练步编号，y 轴为 vLLM 与 transformers 输出之间 logprob 的绝对差。*

显然 bug 不来自模型本身：同样的 checkpoint 在 Hugging Face 的 transformers 下工作完美；问题只在特定运行时条件下出现；而且是经过数百次请求后偶发，并非从一开始就稳定复现。这个模式把矛头指向 vLLM，特别是它的请求调度与缓存管理。

这个 bug 严重到只要它还存在，我们就不能发布模型。我们必须修复它。难处在于它只偶发出现——大约一千条 prompt 才来一次。要在这堆干草里找到针，需要耐心、有条理的调试，最终还要给 vLLM 本身做插桩。所有这些工作的成果，如今已作为[合入 vLLM 项目的修复](https://github.com/vllm-project/vllm/pull/32118)上线。

如果你在用 vLLM 跑推理——无论是生产服务、RL 训练还是评估流水线——理解调度器如何与 Mamba 这类模型架构交互，能帮你避免静默的数据腐化。下面分享我们调试 vLLM 庞大代码库的分步过程，以及一路学到的经验。

### 调试脚本

为了系统化地检测并度量这些失败，我们构建了一个比对脚本，它成了整个调查中我们的主要诊断工具，因为它允许我们对同一批 token ID 比较 logprobs；也就是说，我们不需要用 transformers 重新生成，而是判断 transformers 对 vLLM 的输出*本来会*给出什么。

正常情况下，vLLM 与 transformers 对相同 token 应产生几乎一致的 logprobs（除去微小的浮点差异）。但当 vLLM 因状态腐化生成垃圾时，logprobs 会剧烈分道扬镳：vLLM 可能对某个无意义 token 报告高置信度，而 transformers 正确地显示它本应极不可能。这种不一致揭示了 vLLM 对「在真实序列上下文中毫无意义的 token」感到「自信」。

比对脚本分两个阶段：

- 用 vLLM 生成：把成批的 prompt 送入 vLLM，收集生成的 token 及其 logprobs。
- 用 transformers 验证：把同样的 prompt 加上它们的生成结果送入 Hugging Face transformers，为完全相同的 token 序列计算参考 logprobs。

```
# Pseudo-code for the debug comparison script

# 1. Load model
model_name = "ai21labs/AI21-Jamba-Reasoning-3B"
vllm_model = load_vllm(model_name)
hf_model = load_transformers(model_name)
batch_size = 128

# 2. Generate with vLLM and capture logprobs
prompts = ["Prompt0", "Prompt1", ...]  # 1024 prompts
all_vllm_outputs = []
for batch_idx in range(0, len(prompts), batch_size):
    batch = prompts[batch_idx : batch_idx + batch_size]
    vllm_outputs = vllm_model.generate(batch, return_logprobs=True)
    all_vllm_outputs.extend(vllm_outputs)

# 3. For each output, feed prompt + generated tokens to HF and get logits
for prompt_idx, vllm_out in enumerate(all_vllm_outputs):
      full_sequence = prompt + vllm_out.generated_tokens
      hf_logits = hf_model.forward(full_sequence)
      hf_logprobs = compute_logprobs(hf_logits)

      # 4. Compare vLLM's generation logprobs vs HF's logprobs for same sequence
      for token_idx, (v_logprob, h_logprob) in enumerate(zip(vllm_out.logprobs, hf_logprobs)):
          diff = abs(v_logprob - h_logprob)
          if diff > threshold:
              print(f"Mismatch at prompt {prompt_idx}, token {token_idx}")
              print(f"  vLLM: {v_logprob}, HF: {h_logprob}, diff: {diff}")
```

## 复现那个「无法复现」的 bug

我们的第一个目标听起来很简单：稳定复现问题。但这条路上知易行难。

我们从 RL 数据集出发——成千上万条长度不一的 prompt——用 `ai21labs/AI21-Jamba-Reasoning-3B` 跑推理。我们以 128 为批发送入 1024 条 prompt，模拟我们的 RL 设置。

什么都没有。全部干净生成。

### 引入内存约束

我们思考 RL 中有哪些条件可能与测试设置不同。然后灵光一闪：内存压力。

在 RL 训练期间，GPU 内存被大量占用，意味着 SSM 状态缓存几乎全满，缓存槽位被激进地回收复用。与 attention 模型不同——由于序列长度掩码的存在，陈旧的 KV cache 无法污染新序列——Mamba 的 SSM 状态是整段序列历史的压缩表示。如果新请求读到了上一条序列的陈旧状态，就像带着别人的记忆开始一段对话：状态是递归累积的，开头的垃圾会腐化随后的一切。

*隐藏状态 h 以递归方式更新。如果新请求被误判为 decode，它在进行第一次更新之前，就会从那个内存槽位的前一位主人那里加载一个陈旧的 h。图片来自 Maarten Grootendorst。*

vLLM 允许通过 gpu_memory_utilization 控制 GPU 内存分配。该参数设定 vLLM 将使用每块 GPU 内存的比例，用于模型权重、激活值和 KV cache。我们把它从 0.9 降到 0.2，迫使调度器在紧张的内存约束下运作。

```
llm = LLM(
    model="ai21labs/AI21-Jamba-Reasoning-3B",
    gpu_memory_utilization=0.2,
)
```

重跑调试脚本之后，它出现了：请求 854 生成了胡话。

```

whenlickatori- rub22 RION None 1thATH CASE in2 or AND T6V9 startingenedEN
,ian [-th, a   aBPO enumerate5 and out 11EM A A, following,AN   1Compact to...
```

我们再跑一遍。同样的请求，同样的胡话。在 `temperature=0` 下，这个 bug 是确定性的。

现在我们有的东西可以追了。

### 高效复现

理想情况下，我们希望能用更少的步骤复现 bug——比如第一次或第二次请求就触发——让调试更容易。我们尝试用 `num_gpu_blocks_override` 更精细地控制内存分配；这个参数允许你直接指定要分配的缓存块数量，绕过 vLLM 基于 `gpu_memory_utilization` 的自动计算。我们从非常低的值（如 10、15、40 块）试起，但这让 vLLM 慢到爬行的地步——块太少意味着请求无法被高效调度。

较高的值（如 56 或 64）运行正常但不复现 bug，所以我们必须坚持 `gpu_memory_utilization=0.2` 所形成的那个特定内存压力模式。鉴于时间限制，我们沿用了这个方案，尽管今后值得探索如何更快地复现这个 bug。

## 深入 CUDA 兔子洞

现在能复现了，我们终于能直面核心问题：它到底从哪里来？

最初的假设指向 CUDA prefill kernel——那里的内存 bug 出了名的隐蔽，不会用崩溃来打招呼。当新请求开始时，prefill kernel 应当从零初始化 SSM 状态。而如果它读取了未初始化内存、没清掉陈旧缓存条目、或写错了缓存槽位，就都能解释这些垃圾输出。bug 的偶发性也就说得通了：由于块索引的 off-by-one，请求 A 会读到请求 B 的状态，结果取决于那个内存槽里恰好残留着什么——有时是零，有时是上一个请求遗留的状态。

我们潜入 CUDA kernel，它正是 Mamba 递归的心脏。

```
//  csrc/mamba/mamba_ssm/selective_scan_fwd.cu

template<typename Ktraits>
__global__ void selective_scan_fwd_kernel(SSMParamsBase params) {
    const int cache_index = cache_indices == nullptr
        ? batch_id
        : cache_indices[batch_id];

    const bool has_initial_state =
        params.has_initial_state_ptr == nullptr
            ? false
            : reinterpret_cast<bool *>(params.has_initial_state_ptr)[batch_id];

    scan_t running_prefix;
    if (chunk > 0) {
        running_prefix = smem_running_prefix[state_idx + r * MAX_DSTATE];
    } else {
        if (has_initial_state) {
     running_prefix = make_float2(1.0, float(ssm_states[state_offset]));
        } else {
            running_prefix = make_float2(1.0, 0.0);
        }
    }
}
```

逻辑看起来没问题：若 `has_initial_state` 为 false（新序列），初始化为零；为 true（因 chunked prefill 或 kernel 内部 chunk 而延续的序列），从缓存加载。我们加上了边界检查，验证了指针运算，并检查了全部 28 层 Mamba 的 SSM 状态有无 NaN 和无穷值。一切都很干净。

接着我们用 NVIDIA 的 compute sanitizer 工具检查越界写入和内存泄漏。

```
compute-sanitizer --tool memcheck python my_debug_script.py
```

没有错误：所有内存访问都在边界内。看来我们得提出一个新假设了。

我们花了几小时检查这里的张量，想看是否有请求被误分类、分配到了错误的分组。是不是一个 prefill 请求不小心混进了 decode 批次？我们比想象中更接近真相，但 bug 太隐蔽，而跨越 28 层 Mamba、1024 个请求的张量 dump 让人无从下手。我们只能继续挖。

## 来自 V0 的线索

由于我们此前的 RL 工作负载使用 vLLM 的 V0 引擎（旧的、已弃用的引擎架构）时没有这个问题，我们在 V0 上跑了同样的工作负载做对照。

又一次：没有胡话，全部完美生成。

V1 与 V0 下的模型行为可能差在哪？我们想起了 V0 里一个古老的怪癖：由于一个 bug，Mamba1 模型实际上从未调用过 decode kernels——所有请求都走 prefill 路径。

Prefill kernels *必须*把状态初始化为零（因为它们处理序列的开头），而 decode kernels *必须*从内存加载状态（因为它们假定序列已在进行中）。

为了做一次完全等条件的对照，我们魔改了 V1，强制所有请求走 prefill kernels、彻底绕开 decode。关键改动在 `mamba_mixer.py`：

胡话消失了。每一次生成都是干净的。

我们以为破案了：bug 一定在 decode kernels 里！我们迫不及待地扎进 Triton decode kernels，加打印、检查指针计算、验证内存访问模式。

但什么都没有。Decode kernels 是对的。回到原点。

## 调试之墙

总结一下，到这一步我们已经跑完了一长串检查清单：

- `compute-sanitizer` 没有内存错误
- CUDA kernel 检查通过
- SSM 状态干净
- 拆分逻辑看起来正确
- Decode 的数学是对的

问题是确定性的，但只在数百个请求处理之后才出现。尽管尝试了各种 `num_gpu_blocks_override` 取值，我们仍无法在前几个请求上轻松复现它。

这个时间特征至关重要。它意味着 bug 不在模型初始化或 SSM 层的第一趟处理里，而在于 vLLM 如何*随时间*管理请求。调度器、缓存回收逻辑或批次组装必有一个牵涉其中。我们需要缩小范围，找到流水线中出错的位置。

## 缺失的一块：请求身份

我们已经确定，问题不在于 kernels 在做什么，而在于它们*何时*被调用、为*哪个*请求调用。

但调试 vLLM 的难点在于：当张量到达模型层时，所有请求身份信息都已丢失。调度器用请求 ID 工作，但模型只看到打包的张量与索引。请求 854 只是……藏在那些张量里的某个位置。

我们需要把请求 ID 贯穿整个前向传播，这样就能专门在请求 854 被处理时设下断点。

## 给 vLLM 的 forward context 插桩

vLLM 用一个 `ForwardContext` dataclass 把元数据传递过模型。我们添加了请求追踪：

## 真相大白

请求追踪就位后，我们设好断点，等待请求 854 出现。

命中时，我们检查了批次组成。req_ids 显示请求 854 位于索引 86：

```

    ...
    '845-a1a7ebcb',  # index 77
    '846-9218e1e3',  # index 78
    ...
    '852-b1e447b5',  # index 84
    '853-bb41acbe',  # index 85
    '854-a83e1fd2',  # index 86 - our culprit
]
```

我们打印了 `is_decode` 分类数组：

```
is_decode = array([
    True,  True,  True,  ...  True,   # indices 0-53: regular decodes
    False, False, False, ... False,   # indices 54-85: prefills
    True                              # index 86: request 854 - marked as DECODE!
])
```

请求 854 在*首次*出现时就被分类为 decode。但为什么？我们检查了 `num_scheduled_tokens` 数组：

```
num_scheduled_tokens_np = array([
    1, 1, 1, ... 1,                    # indices 0-53: decodes (1 token each)
    83, 181, 181, 469, 1343, ...       # indices 54-85: prefills (many tokens)
    1                                  # index 86: request 854 - only 1 token!
])
```

调度器的 token 预算已经耗尽。请求 854——一个全新的 prompt——只被分到 1 个 token。而当时的分类逻辑是：

```
is_decode = num_scheduled_tokens == 1
```

只调度 1 个 token = 一定是 decode，对吧？错。请求 854 的 num_computed_tokens=0——它是一个从未被处理过的新请求。它本应被分类为 prefill，但单 token 的分配让它看起来像 decode。

```
#  vllm/v1/attention/backends/utils.py
def reorder_batch_to_split_decodes_and_prefills(...):
		...
		is_decode = num_scheduled_tokens_np <= decode_threshold # BUG
		is_extend = (~is_decode) & (num_computed_tokens_np > 0)
		is_prefill = (~is_decode) & (num_computed_tokens_np == 0)
```

调度 1 个 token 的请求，无论它是新请求还是延续请求，都会被分类为「decode」。但请求 854 是全新的；它此前从未被处理过。

## 根本原因

完整的失败链条如下：

- 调度器的 token 预算几乎耗尽（由于较低的 `gpu_memory_utilization`）
- 新请求 854 到达，有 475 个 token 要处理
- 调度器只能给它分配 1 个 token
- 1 个 token → 被 reorder 逻辑分类为「decode」
- Decode 路径假定了已有状态 → 从缓存读取 SSM 状态
- 但请求 854 的缓存槽里装着前一个已完成请求留下的垃圾
- 模型基于这个被腐化的状态进行生成
- 后续迭代继续带着这个被腐化的状态

### 为什么 transformers 没有这个问题

你可能会想：同样的 bug 不会波及带 KV cache 的 transformer 模型吗？答案是不会，原因植根于 attention 与 SSM 递归的根本差异。

Transformer 的 attention 使用序列长度掩码。FlashAttention 运行时，会收到一个 `seqused_k` 张量，精确指明每个请求存在多少个有效的 KV token：

**Attention：先写后读（Write-then-Read）**

```
# FlashAttention forward (vllm/v1/attention/backends/flash_attn.py)

# Step 1: WRITE current token's K,V to cache
reshape_and_cache_flash(key, value, key_cache, value_cache, slot_mapping, ...)

# Step 2: READ from cache for attention computation
flash_attn_varlen_func(
    q=query,
    k=key_cache,   # includes freshly written K
    v=value_cache, # includes freshly written V
    seqused_k=seq_lens,  # bounds attention to valid positions
    ...
)
```

即使新请求被误分类为「decode」，它自己的 K、V 也会在 attention 读取缓存*之前*先写入。位置 0 处的陈旧数据会最先被覆盖。

Mamba 没有这样的边界。SSM 状态作为一个完整的向量被加载：

```
# Mamba selective_state_update kernel (mamba_ssm.py)

# Step 1: READ state from cache (assumes continuing a sequence)
state = tl.load(state_ptrs, ...)

# Step 2: Compute with loaded state
state = state * dA + dB * x

# Step 3: WRITE updated state back to cache
tl.store(dst_state_ptrs, state, ...)
```

当新请求被误分类为「decode」，它会在写入任何东西之前先读取上一个请求的陈旧状态。计算从一开始就是被腐化的。

这就是为什么在我上文描述的测试中，prefill kernel 能让 Mamba 正常工作——它通过 `has_initial_state` 标志显式地把状态初始化为零。而 decode kernel 假定状态已经是有效的。

## 修复

根本原因清楚之后，修复很简单。我们修改了分类逻辑，考虑请求是否真正是新请求：

```
#  vllm/v1/attention/backends/utils.py

def reorder_batch_to_split_decodes_and_prefills(...):
    # NEW: A request is prefill if it has no computed tokens (it's new)
    is_prefill = num_computed_tokens_np == 0
    # Decode/extend only applies to requests that already have context
    is_decode = (num_scheduled_tokens_np <= decode_threshold) & (~is_prefill)
    is_extend = (num_scheduled_tokens_np > decode_threshold) & (~is_prefill)
```

现在，`num_computed_tokens == 0` 的请求无论调度了多少 token 都一律分类为 prefill。只有已经拥有已计算 token 的请求才可能被分类为 decode。

## 经验教训

- 内存压力会暴露理想条件下不显现的 bug。要在资源受限的情况下测试。
- 确定性是你的朋友。一旦拥有了 `temperature=0` 下可复现的案例，调试就变得可解了。
- 给你的系统插桩。给 vLLM 前向传播加上请求 ID 追踪是个小改动，却让 bug 立刻现形。最好的调试工具有时是你自己造的那把。
- 信任，但验证。Decode kernels 在数学上是对的，只是它们被在错误的时刻、为错误的请求调用了。
- 差之毫厘的排查也有价值。检查拆分逻辑时，我看的就是出问题的地方，却没法在铺天盖地的张量数据中看出 bug。请求 ID 插桩给了我恰好的可见性。

## 最后的话

这段调试之旅的教训不止适用于 Mamba。无论你处理的是 attention 模型、MoE 还是任何其他架构，核心原则不变：在现实条件下复现、给关键路径插桩、拿 logprobs 与一个已知良好的基线（如 HuggingFace 的 transformers）做比对、不要死守第一个假设——bug 可能藏在你完全没想到的层。希望这份详尽的复盘能让你下一次 vLLM 调试之旅少一些畏途。

如果你在 vLLM 中运行 Mamba 模型，请确保使用带此修复的 `v0.14.0` 版本，或确保新请求总是从 prefill 初始化开始。
