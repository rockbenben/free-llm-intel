### 太长不看

AI 开发的瓶颈已经转移。难点不再是如何把自然语言翻译成代码，而是如何把人类的潜意识翻译成一份有意识的规格说明。

## 软件开发的终结

几十年来，我们以为编码才是难点。产品经理写一份 PRD，开发者要花几周才能把它变成可运行的软件。而如今，借助 Claude Code 或 Cursor 这样的工具，你可以在几分钟内从自然语言走到 Python。

没错，人人都在谈论软件开发的终结，但我们其实并没有移除瓶颈，只是把它挪了个位置。而新的瓶颈更难对付，尤其当产品本身就是 AI 时——比如一个内部知识 agent 或一个客服聊天机器人。

今天的问题不在于**如何**告诉计算机去做某事。问题在于人类其实并不知道自己**想要**计算机做什么。

## "我看到才知道"悖论

1964 年，大法官 Potter Stewart 以一句广为流传的话定义了硬核色情内容："*我看到的时候自然认得出来。*"

人类体验软件需求的方式恰恰如此。我们不擅长生成抽象规则，却非常擅长批评具体示例。

如果你让业务干系人为一个客服聊天机器人定义需求，他们会写出泛泛的套话："*要礼貌、专业。*"但当那个 agent 给出一段干巴巴、机器人式的回答时，他们会立刻尖叫："*不对！不是这样！*"

这就是 Agent 时代的核心摩擦：**我们正试图用有限的、线性的指令，去定义无限的、递归的行为系统。**

## "Dwight"谬误：数据 ≠ 上下文

我们所*感受到的*与我们能*说清楚的*之间的这道鸿沟，恰恰是"多喂点数据"这类幼稚 AI 方案屡屡失败的原因。

想想 Dwight Schrute——那位传奇员工，他对组织的一切了如指掌：历史、政治、各种捷径，还有《太空堡垒卡拉狄加》。办公室里发生了一起枪击意外后，Dwight 辞职去了 Staples，管理层说："*我们造一个 Dwight-Bot 吧。把他 20 年的邮件全部喂进 RAG 就行。*"

他们真把机器人造出来了，然后它失败了。为什么？

因为 Dwight 的价值不在于他持有的数据，而在于他运用的**上下文**。他知道什么时候可以无视 2018 年的那条政策，因为"会计部的 Jeff 根本不在乎"。摄取数据捕获的是文字，而不是组织的**潜意识知识**。

## 言语行为陷阱：话语 ≠ 意图

但即便我们解决了"数据 vs. 上下文"的问题，一个更深的问题仍然存在：理解意图，而不仅是信息。

[Agent](https://www.ai21.com/ai-agents/)即使"正确"回答时也常常失败。它们听懂了字句，却错失了用户真正想达成的目标。

原因很简单。在语言中，我们不只是传递信息，我们还通过语言执行行为（这一概念由 [*Austin 与 Searle 的言语行为理论*](https://www.researchgate.net/publication/353274370_Speech_Act_Theory_From_Austin_to_Searle)形式化）。

看这个例子：

**用户：**"*打印机又卡纸了。*"

**糟糕的 agent（拘泥字面）：**

"*我了解了。卡纸通常是由滚轮错位或异物造成的。*"

（事实正确，语用上毫无用处。）

**出色的 agent（聚焦意图）：**

"*我已经开了一张工单。需要我把你的打印任务路由到 3 楼的备用打印机吗？*"

用户做的不是陈述事实，而是发出了一项指令。"糟糕的 agent"之所以失败，不是因为逻辑错误，而是因为一个**适切性失误（felicity error）**。它没有执行用户实际需要的言语行为。

## Claude Code 的幻觉：为什么"基于规格"的 AI 还不够

这些失败不是理论上的。它们直接体现在我们今天要构建 AI 系统的方式中。有趣的是，行业已经在朝正确的方向移动。

[Claude Code](https://www.atcyrus.com/stories/claude-code-ask-user-question-tool-guide)等工具引入了 AskUserQuestion 之类的功能，让模型在写下第一行代码之前主动"面试"开发者。多年来我们痴迷于 prompt engineering，如今是模型来 prompt *你*了。这承认了一个更深层的真相：构建软件不是写代码，而是拷问意图。

然而，这制造了一种危险的幻觉。Claude 的"面试"工具旨在消解*技术*歧义，而非*概念*歧义。如果业务干系人说"*根据 Dwight 的邮件做一个机器人*"，Claude 会问出关于向量数据库或身份认证的出色的技术问题。但它*不会*问 Dwight 本人是否真的遵守了那些成文规则，也不会去读公司里那些不成文的政治暗流。它不会挑战前提本身。

要把人类的潜意识意图转化为可用的产品，你不能只把原始需求丢给一个 AI 编码助手。你需要主动探查那些有缺陷的假设，在编码开始之前就把真正的需求架构出来。否则，Claude 确实会帮你更高效地构建——但构建出错误的东西。

## 解决方案：主动发现与 AI 产品架构师

要构建一个真正可用的 AI 系统，你需要的不只是编码助手。你需要一位经验丰富的构建者，扮演主动调查员的角色。这需要一套**主动发现（Active Discovery）**方法论：把组织的潜意识意图转化为具体、务实的 PRD。流程如下：

### 1. 来源映射阶段：上下文与数据

业余者会问业务干系人："*机器人应该做什么？*"经验丰富的 AI 构建者会问："*机器人实际知道什么？*"

我们映射**上下文**：这个 agent 是独立的吗？它是某个遗留系统的一部分吗？

我们映射**数据**：真正的事实来源是什么？

关键在于，经验丰富的构建者会主动搜捕那些**隐性缺口**。他们识别出 Dwight 记在脑子里的不成文规则和上下文，并迫使组织在写第一行代码之前就把它们明确定义出来。

### 2. Mock 循环：以模拟代替规格

人类很难在脑海中准确模拟复杂的会话树。如果你向业务干系人要规则，他们只会给你无用的套话。相反，经验丰富的 AI 构建者会生成**Mock**：代表不同客户意图的模拟输入/输出对。

例如：

- **场景 A：** agent 把"*打印机卡纸了*"当作投诉（共情）。
- **场景 B：** agent 把它当作工单请求（行动）。
- **场景 C：** agent 把它当作故障排查咨询（指导）。

干系人不需要指定后端逻辑。他们只需指认并说："*场景 B 才是我的意思。*"AI 构建者通过这一流程在迭代中提炼出真正的需求。

### 3. 盲区检测：主动拷问

如果你给 AI 编码助手下达互相矛盾的指令，它不会提出异议。但经验丰富的 AI 构建者会主动分析干系人的选择，揭露逻辑上的不一致。
"*你说机器人应该乐于助人。但在场景 4 里，你否决了故障排查。
*那么目标究竟是解决问题，还是仅仅记录问题？*"

这种主动拷问迫使业务方从模糊的"感觉"走向严格的定义。

### 4. 覆盖：驯服无限

在传统软件中，你可以测试所有重要的东西：输入是有限的，行为是确定性的。在 AI 系统中，两者都不成立。

语言是无限的，模型行为是概率性的。这正是传统单元测试失灵的地方。挑战不在于覆盖率，而在于代表性。

经验丰富的 AI 构建者不枚举用例。他们策划有代表性的场景用于评估：愤怒的客户、含糊的请求、缺失的上下文。同样重要的是，他们定义什么是范围之外。一个差旅 agent 不需要懂狭义相对论；它需要处理的是正确的问题分布。

有了合适的护栏和有代表性的样本，[生产环境的行为](https://www.ai21.com/blog/mind-the-gap/)自然跟上。在 AI 中，不存在 100% 的准确率，只有在定义边界内保持一致的行为。

## 结论：活的 PRD

这一流程的产出不是一个静态文档，而是一份活的配置。当干系人完成对 mock 的纠正时，产品其实已经建成了。PRD *就是* prompt。

人的角色已经改变：我们不再是绘制蓝图的架构师，我们通过迭代来塑造行为，就像父母教育孩子。我们纠正、引导，并解释原因。

瓶颈不再是代码，而是清晰度。而清晰度不来自口述——它来自一套严谨的拷问、挑战与打磨的过程，直到系统如实反映出产品背后的真实意图。
