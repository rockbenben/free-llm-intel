# 双层 AI 智能体：为什么你需要两个模型

看一个长时间运行的编码或运维智能体的 trace，你会看到同一个模式。相当大比例的步骤是机械性的：构造一个工具调用、检查输出格式、在瞬时错误上重试、摘要一段日志、给结果分类。这些都不需要前沿推理，都不需要一个 GPQA Diamond 考到 90% 的模型。它们需要的是一个能可靠遵循指令、响应快、单次调用不贵的模型。

问题在于：大多数团队把这些步骤全部路由给他们用在规划步骤上的那个昂贵模型——只因为已经有它的 API key。NVIDIA 在 8 月 11 日发布 [Nemotron 3.5 Lightning](https://deepinfra.com/nvidia/NVIDIA-Nemotron-3.5-Lightning) 时直接点出了这个做法：对智能体实际所做的大部分工作来说，前沿推理模型是错误的工具。这个论点值得认真对待——不是因为 Nemotron 3.5 Lightning 是唯一值得考虑的执行力模型，而是因为 NVIDIA 围绕这一前提构建了一整个模型类别加一个路由库，这本身就是一个信号：业界已经收敛到同一个结构性结论。

本文为双层智能体架构（two-tier agent）做出论证，解释单模型技术栈的成本究竟流向何处，并展示路由切分在实践中长什么样。

## token 都去了哪里

多数前沿模型部署背后的直觉是：模型靠"聪明"挣回自己的成本。对规划步骤这是真的，对智能体 token 预算的大头却不是。

2025 到 2026 年间 token 价格降了很多，多数企业仍然在超 AI 预算。原因是：智能体工作流把 token 消耗乘了倍，而这种乘法不是单轮定价直觉能捕捉的。用户向聊天机器人问一个问题，产生一次推理调用；一个智能体完成等价任务，可能产生三十次：规划步骤、工具调用、结果读取、验证循环、子智能体委派、错误处理、上下文压缩，最后再加一遍综合。每一项都是独立的推理调用，每一项都按输出费率计费。

随 Nemotron 3.5 Lightning 发布一同公布的 [LangChain 基准](https://blogs.nvidia.com/blog/nemotron-lightning-switchyard-rtx-dgx/)把这一点讲得很具体。在 145 个多轮智能体任务上，用一个升级路由器在 Lightning 与 [Claude Opus 4.8](https://deepinfra.com/anthropic/claude-opus-4-8) 之间路由，成本比纯前沿基线降低了 74%。只有 7% 的调用去了前沿模型，其余 93% 由执行模型处理。准确率的代价大约是 6 个百分点。

这个 7% 值得停下来想一想。如果一个真实多轮基准中 93% 的调用都能由一个便宜的执行模型处理、只付出 6 个百分点的准确率代价，那么问题已经不是双层路由值不值得做，而是"一个模型包打一切"为什么还是默认。

## 什么该给前沿模型，什么不该

这道切分比乍看之下更符合直觉。执行层不是质量上的妥协，而是一个认知：智能体所做的大部分事情，压根不是质量问题。

| **任务类型** | **示例** | **路由到** | **原因** |
| --- | --- | --- | --- |
| 规划与编排 | 分解一个目标、决定调用哪些工具、综合互相冲突的结果、应对意外失败 | 前沿模型 | 需要真正的推理、判断力，以及贯穿整个任务的上下文 |
| 工具调用格式化 | 构造 JSON payload、填充函数 schema、组织一条搜索 query | 执行模型 | 结构是确定性的；正确性可验证；不需要推理 |
| 结果校验 | 工具返回了错误吗？输出在预期范围内吗？格式匹配吗？ | 执行模型 | 模式匹配与 schema 检查；可重复且快 |
| 重试逻辑 | 重发失败的 API 调用、在瞬时错误上调整参数 | 执行模型 | 不含判断的条件逻辑，更适合交给代码或一个小模型 |
| 上下文摘要 | 把一长段工具输出压缩后再传回规划器 | 执行模型 | 抽取任务；不需要前沿级理解力 |
| 分类与路由决策 | 这个工具输出是错误还是结果？下一步该走哪个？ | 执行模型 | 边界明确、结果可枚举的决策，可靠地跑起来很便宜 |
| 最终综合与输出 | 基于累积的结果产出面向用户的答复 | 前沿模型 | 输出的质量与连贯性要紧；这就是用户看到的东西 |

画这条线有个好用的启发式：只要你能用程序校验输出——schema、格式、区间、已知错误码——这个任务就不需要前沿模型。校验是便宜的；只要生成空间被良好约束，生成一个能通过校验的东西不需要前沿级推理。

真正需要前沿模型的任务，是那些正确性无法低成本校验的：从多个工具输出中综合互相冲突的信息、在真正含糊的下一步之间做抉择、产出必须连贯且说理充分的用户可见输出。而这些任务在一条长智能体循环里是稀疏的：一个设计良好的智能体在一个复杂任务里可能发起上百次工具调用，而只做出五个真正的规划决策。

## Paul Gauthier 在 2025 年跑过的那个实证

这套架构的实证案例并不是从 Nemotron 3.5 Lightning 才开始的。2025 年 1 月，Aider 创始人 Paul Gauthier 发布了[结果](https://x.com/paulgauthier/status/1882833360567095682)：用 [DeepSeek R1](https://deepinfra.com/deepseek-ai/DeepSeek-R1-0528) 做推理与规划、Claude Sonnet 做代码编辑，在 Aider 的 polyglot 基准上命中 SOTA，成本只有单用 OpenAI o1 的十四分之一。

架构很简单。R1 负责思考：分析代码库、判定哪些文件相关、起草实现计划。Sonnet 负责精确编辑：拿一份清晰的规格，在代码里执行它。R1 的推理按 token 算便宜，Sonnet 的编辑按步骤算精准，谁都不替谁干活。结果胜过单一前沿模型，花费只是零头。

这个模式已经被推广。UC Berkeley、Anyscale 和 Canva 发表在 ICLR 2025 的研究显示，经过训练的路由系统在混合复杂度工作负载上带来 85% 的成本削减，同时保持 GPT-4 性能的 95%。核心发现是：一个小分类器就能把大多数流量路由给更小的模型，且在这些任务上没有可测量的质量退化。这正是 Gauthier 当年手动在生产里跑通的同一个洞见。

## 执行模型需要成为什么

不是每个小模型都适合执行层。它的要求和通用模型不同。

**指令遵循重于推理广度。** 执行模型的职责是被精确且一致地指哪打哪。它不需要推理"这条指令对不对"——规划器已经定过了。它需要遵守 schema、正确调用工具、返回结构化输出。为智能体 harness 蒸馏或微调过的模型，常常在这类任务上胜过更大的通用模型，尽管激活参数少得多。Nemotron 3.5 Lightning 专门针对 OpenClaw 和 Hermes Agent 做过训练，正是出于这个原因。

**延迟。** 在一条长智能体循环里，执行模型的响应时间会累积。每个工具调用多花 2 秒的模型，在 100 步的智能体上就是多花 200 秒。Nemotron 3.5 Lightning 对同规模模型的 4 倍速度优势在这里特别相关。它的 Mamba-2 + MoE + Attention 混合架构在预训练阶段就内建了多 token 预测，为吞吐而设计，而不是为最大推理深度。

**可预测性。** 执行模型需要以优雅且可预期的方式失败。一个时而产出正确 JSON、时而产出结构不同的东西的模型，比一个能力稍弱但以已知方式失败的模型更难绕。执行模型的失败模式应当可枚举、可被校验步骤捕获，进而触发向前沿模型的升级。

**可微调性。** 执行模型的任务足够窄、足够重复，领域定制微调是可行的。客服智能体的工具调用格式、编码智能体的错误分类 schema、运维智能体的日志解析模式——这些都能由一个在几百个样本上微调过的小模型学会。Nemotron 3.5 Lightning 随附通过 NeMo Automodel 的 LoRA 与全量 SFT 支持，正是为了促成这一点。一个在你具体任务分布上微调过的执行模型，几乎总会以同样成本胜过通用小模型。

## 实践中行得通的模型搭配

执行模型的选择，与其说取决于抽象能力排名，不如说取决于你现有的基础设施，以及执行任务长什么样。

| **规划器（前沿）** | **执行器（便宜）** | **成本占比（估算）** | **适合** |
| --- | --- | --- | --- |
| Claude Opus 4.8 | Nemotron 3.5 Lightning | 约 10% 调用给前沿 / 约 90% 给执行 | 综合质量至关重要的复杂推理智能体 |
| DeepSeek V4 Pro | DeepSeek V4 Flash | 约 15% 调用给前沿 / 约 85% 给执行 | 成本敏感的流水线；两个模型共享同一 API 格式 |
| Kimi K3 | Qwen3 30B-A3B | 约 10% 调用给前沿 / 约 90% 给执行 | 要求执行层可自托管的纯开放权重栈 |
| GPT-5.6 Sol | Nemotron 3.5 Lightning 或 GPT-5.6 Luna | 约 7% 调用给前沿 / 约 93% 给执行 | OpenAI 原生流水线；Luna 与 Sol 共享同一 API 面 |

[V4 Pro](https://deepinfra.com/deepseek-ai/DeepSeek-V4-Pro-0813) 与 [V4 Flash](https://deepinfra.com/deepseek-ai/DeepSeek-V4-Flash-0731) 这对搭配值得专门一说。两个模型在 DeepInfra 上共享同一 API 格式：同样的端点结构、同样的参数接口、同样的 function calling schema。实现路由切分是一行模型名的改动，不是集成改动：规划调用指向 deepseek-v4-pro，执行调用指向 deepseek-v4-flash，其余代码原封不动。对已经在跑 DeepSeek 的团队，这是通往双层架构摩擦最低的路径。

Opus 4.8 配 Lightning 则是有 LangChain 基准数据背书的那对。145 个多轮任务上 74% 的成本削减，是这个特定架构可获得的最严谨的公开结果。约 6 个百分点的准确率代价有分量，但对多数生产工作负载可控——毕竟要紧的决策仍然由前沿模型处理。

## NeMo Switchyard 如何框定路由问题

NVIDIA 随 Nemotron 3.5 Lightning 发布了 NeMo Switchyard。它是一个开源路由库，把智能体的每一步分派给可用的最划算模型。这个设计值得理解，因为它把多数团队目前临时处理的东西变成了显式结构。

Switchyard 把路由当作智能体架构里的一等关注点，而不是部署细节。智能体循环中的每一步按类型分类——规划、工具执行、校验、委派——并路由到相应的模型层级。规划器和执行器不需要意识到彼此存在，交接由路由器处理。该库被设计成可与 LangGraph、LlamaIndex 等主流智能体框架组合，路由层坐在框架与模型 API 之间，而不是嵌在任何一边。

Switchyard 点明的关键架构论点：路由策略是与智能体逻辑分离的独立制品。智能体做什么——它的工具、目标、prompts——定义一次；每一步由哪个模型处理，则是一个可以独立更改、实验和监控的配置决策。正是这个分离，让调成本-质量权衡变成调路由阈值，而不是改写智能体代码。

实现这套架构不必非用 Switchyard。LangGraph 的条件边、LlamaIndex 的路由抽象、或对任务分类的简单 if-else 都行得通。Switchyard 多给的是路由问题的一套结构化词汇，以及与 Nemotron 模型家族的预制集成。底层模式——给每一步分类、路由到能可靠处理它的最便宜模型、失败时升级——与框架无关。

## 升级路径与路由本身同等重要

一个正常情况路由正确、却在执行模型能力不及时装死的双层架构，比单模型栈更糟。从执行器到规划器的升级路径需要显式、快速、可观测。

实用模式：执行模型的输出伴随一个置信信号返回。可以是一个显式分数、一个结构化的不确定性字段，或者就是响应 schema 里的一个标志。路由器在把输出交给下一步之前先检查该信号。如果执行模型标了低置信，或输出没通过格式校验，路由器就把同一步重新路由给前沿模型。前沿模型的输出替换掉执行模型失败的尝试，智能体循环继续。

不要做什么：让失败静默累积；仅凭输出结构推断置信度；把每次校验失败都升级给前沿模型。第一条产出悄悄劣化的结果而账单上毫无信号；第二条在结构合法但语义错误的输出上制造虚假信心；第三条则抹掉这套架构本该带来的大部分成本节省。

可观测的路由，是让这套架构可持续维护的运营要求。记录每一步由哪个模型处理、执行模型的置信信号、以及是否发生过升级。这份 trace 会告诉你：路由阈值校准得对不对、哪类任务升级得超出预期、执行模型在哪里需要微调。没有它，你就是在盲飞——飞越这套架构本应优化的成本-质量权衡。

## 这对单任务成本意味着什么

一旦路由切分定下来，实际的算术很直白。以一个在复杂任务上发出 80 次模型调用的编码智能体为例：6 个规划决策路由给 Opus 4.8，74 个执行步骤路由给 Nemotron 3.5 Lightning 或 V4 Flash。按 Opus 4.8 每百万输出 $25、Lightning 每百万 $0.40 计，规划步骤平均 500 输出 token、执行步骤平均 200：

**单模型**（全部 Opus 4.8）：80 次调用 × 平均 200 token × $25/M = 每任务 $0.40

**双层**（6 前沿 + 74 执行）：6 × 500 × $25/M + 74 × 200 × $0.40/M = $0.075 + $0.006 = 每任务 $0.081

这是模型账单上 80% 的成本削减。按每月 100,000 个任务算，单模型栈花 $40,000，双层栈花 $8,100。质量上的取舍完全取决于那 74 个执行步骤是否被正确分类——它们是否确实是执行模型能可靠处理的结构化、可验证的工作。把分类做对，就是这套架构要求你做的工程。

单价在跌、账单在涨，这中间的落差几乎全可以用智能体工作流对 token 消耗的乘数效应来解释。双层架构是缩小这一落差的最直接可用的杠杆——不是削减智能体做的事，而是把它做的大部分事情，跑在与任务实际体量相称的基础设施上。
