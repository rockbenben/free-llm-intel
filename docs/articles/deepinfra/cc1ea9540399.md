# Token 冗长度是新的定价之战

每一轮新模型发布，我们都看到新的基准声明，以及新的为其 token 价值辩护的说辞。然而，当团队针对真实工作负载比较模型时，仅看标价会掩盖每个任务在"模型需要付出多少工作量才能解决任务"上的巨大差异。

更便宜的 token 未必带来更低的成本。那么，究竟什么在决定运行一个模型的真实成本？

本文将探讨 token 消耗的隐藏成本——推理、重试与任务效率如何影响总成本——并讨论 DeepInfra 如何帮助管理和优化这些因素。

## 定价页上从不写出的隐藏成本

按 token 计费不会告诉你一个任务实际要花多少钱。

单 token 更便宜的模型，运行起来未必更省。从一个模型拿一百万 token，产出的文本量未必和另一个模型一样，完成的任务也未必相同。这就是为什么"每 token 单价"作为独立的成本度量如此不中用。

但 token 消耗制造了隐藏的成本差异：一个更便宜的模型如果需要试好几次，可能反而更贵；一个更贵的模型如果一次做对，可能反而更经济。

真实成本的取决于定价页上印着的那个数字之外的东西——一个模型用多少 token、多高效地完成任务、多常成功。因此，两个 token 价格相近的模型，真实世界的成本可以天差地别。

## Kimi K3 与 DeepSeek V4 Pro：token 用量的基准观察

在同一基准上评测时，模型间的 token 消耗可以有天壤之别。

在 Artificial Analysis 评测期间，Kimi K3 生成了 [1.3 亿输出 token](https://deepinfra.com/blog/kimi-k3-model-analysis-api-provider-comparison)，是可比开放权重模型中位数 6,300 万的两倍多。Kimi K3 永远开启的推理特性是其异常高的 token 用量的成因之一。

Kimi K3 也处在中端到高端的定价带：输出每百万 token $15，而开放权重模型的中位数是 $10。把它的高 token 消耗加进成本方程，每一次基准运行都变得格外昂贵。

DeepSeek V4 Pro 呈现的是同一问题的另一面。在其 Think Max 模式下，它生成了约 [1.9 亿输出 token](https://deepinfra.com/blog/deepseek-v4-pro-model-overview)，是可比开放权重模型 4,700 万中位数的四倍多。按每百万输出 token $2.60 的费率，这笔用量约产生 $494 的输出 token 费用，而中位用量只需约 $122。

然而 DeepSeek V4 Pro 的输出单价远低于 Kimi K3。即便如此，它的高 token 消耗依然推高了整体运行成本。这恰恰说明单看 token 价格多么容易误导：一个模型可以单 token 更便宜，却要消耗多得多的 token 才能完成一个任务。因此，生成的 token 数量本身，就在改变运行一个模型的经济学。

## 为什么有些模型要多用这么多 token

模型解决同一个任务所用 token 的数量可以差异巨大。几个因素共同造成这种差异：

### 推理深度影响 token 用量

推理模型会动用额外的 token 在产出最终答案之前推演问题。这些 reasoning token 在最终回复里看不见，但照样计入输出用量和成本。

更高的推理强度会推高 token 消耗和响应延迟。一个简短的可见答案，实际用掉的 token 可能远超其字面显示的体量。

### 分词器改变文本的计数方式

token 用量还取决于模型如何把文本切分成 token。一个 token 可以是一个字符、一个词的一部分、整个词或标点。

同一段文本，因模型、编码和语言的不同而产生不同的 token 计数。空格、大小写、拼写等因素也决定文本如何被切分。

### 模型规模不是唯一因素

单看模型规模说不出一个任务会消耗多少 token。token 用量取决于输入、生成的输出、reasoning token，以及模型处理任务的方式。

输入 token 的数量并不能预测模型会生成多少输出 token。token 消耗取决于工作负载和模型的行为，而不只是模型的大小。

## token 用量何时演变成推理问题

token 消耗影响完成任务所需的计算工作量。生成更多输出 token 需要更多计算，但这个关系不是线性的。输入长度、上下文、媒体类型、推理深度和具体用例，都会影响一个任务需要的计算量。

模型也可能在产出最终回复之前用额外的 token 做推理。创建一小套预定义标签通常需要的 token 更少；而从图像化文档生成完整 schema，则要求模型分析多得多的信息。模型越是需要分析输入或推演任务，推理过程就可能越吃计算。

输出生成还造成延迟，因为输出 token 是逐个顺序生成的：每个新 token 都依赖它之前生成的 token，长输出因此可能显著耗时。输入处理的工作方式不同——大部分输入可以并行处理。这让输出长度成为推理延迟中的重要因素，对生成长回复或需要大量推理的工作负载尤其如此。

更吃重的工作负载可能需要更多计算资源并抬高推理成本。既然工作负载复杂度各异，团队就需要手段来控制每个请求要消耗多少计算。推理基础设施可以通过 reasoning effort、上下文缓存和模型选择提供这些控制。

这些控制能在保留复杂任务所需资源的同时，削减不必要的计算。目标不是单纯少生成 token，而是把计算量与任务的真实需求对齐。

## DeepInfra 在哪里改变推理经济学

既然我们已经理解推理经济学不只是挑每 token 单价最低、或平均单次最便宜的模型，下一个问题就是：如何控制决定推理实际成本的那些因素——你发多少上下文、模型推理多少、每个请求被多高效地服务。

[DeepInfra](https://docs.deepinfra.com/?utm_source=chatgpt.com#why-deepinfra) 是一个 AI 推理云平台，为团队提供 [200 多个开源模型](https://docs.deepinfra.com/models)的访问，以及私有 GPU 部署。它赋予开发者对这些因素的可见性与控制权，帮助其有效管理推理任务的成本与性能。

以下能力展示了团队如何掌控推理经济学：

### Prompt 缓存降低重复输入的成本

许多工作负载在每个请求里重复发送同样的上下文：一段很长的 system prompt、一个大文档，或一组固定的 few-shot 示例。

DeepInfra 的 prompt 缓存在 prompt 开头与某个已缓存前缀匹配时复用 [key-value（KV）](https://docs.deepinfra.com/chat/prompt-caching)缓存，避免重算已缓存的部分，从而缩短首 token 时间并降低成本。

当同一个前缀出现在许多请求的开头，这些 token 就能以显著更低的成本被服务。这让缓存对反复发送相同 system prompt、文档或其他静态上下文的工作负载格外有用。

Prompt 缓存在支持的模型上自动生效。团队把稳定内容放在 prompt 开头、让前缀在各请求之间保持完全一致，就能拿到最多收益。

### 请求级成本可见性展示真实支出

DeepInfra 的 [API 响应](https://docs.deepinfra.com/quickstart)中包含 prompt token、completion token、总 token 与估算成本。

这为团队提供了推理用量的请求级视图：能看出成本究竟来自大输入、长输出，还是两者皆有。对上下文随时间增长、或智能体为完成一个任务发起多次调用的工作负载，这一点很重要。

团队可以用这种可见性跨模型、跨工作负载比较真实的请求成本；它也简化了识别高成本请求、寻找削减不必要 token 用量的机会。

### 推理控制让开发者用深度换成本

DeepInfra 的 [reasoning_effort](https://docs.deepinfra.com/chat/reasoning) 参数控制模型做多少推理：档位更高意味着更深的推理、更多输出 token 和更高延迟，也可能抬高推理成本。

开发者可以按任务设置推理强度：复杂的数学、逻辑和编程问题用高档；简单问答、翻译、摘要可以用低档甚至完全关闭推理。成本敏感的工作负载用 none 或 low 来减少不必要的推理。

团队也可以直接按工作负载在推理模型与非推理模型之间选择。

### 实时推理指标展示服务效率

DeepInfra 提供[实时推理指标](https://docs.deepinfra.com/api-reference/logs-%26-metrics/get-live-metrics)，包括 tokens_per_second、time_to_first_token、requests_per_second。这些指标刻画服务性能的不同侧面：每秒 token 衡量生成吞吐；首 token 时间展示生成开始得多快；每秒请求数展示部署正承载多少请求流量。

对于独享部署，你还会收到平均首 token 时间、平均每 token 时间、请求数、输入输出 token 数、总推理时间和错误率等指标。

这些指标为基于 token 的成本补充了语境：团队能看到一个部署处理了多少流量、处理得多高效。这很重要，因为推理成本不仅取决于每请求的 token 数，还取决于每天跑多少请求、以及工作负载被服务得多高效。

## 最后的话

一个更贵但话少的模型，最终可能整体更便宜——而没有任何定价页会展示这一点。更值得盯的指标是"每成功完成一个任务的成本"，而不是"每百万 token 的价格"。
