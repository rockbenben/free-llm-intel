# 详解 MCP 服务器：开发者实用指南

让 AI 应用访问数据库、API、文件系统或内部服务，听起来简单——直到你需要维护这个集成。你要定义模型能访问什么、描述有哪些操作、安全地执行请求、返回[结构化结果](https://docs.deepinfra.com/chat/structured-outputs)，还要处理认证。当另一个 AI 应用需要同样的能力时，这套工作你还得再来一遍。

[Model Context Protocol（MCP）](https://modelcontextprotocol.io/docs/2026-07-28/getting-started/intro)把这个连接标准化了。你可以通过一个 MCP 服务器暴露工具和上下文，让兼容的应用经同一协议发现并使用它们。

要交付一个有用的 MCP 服务器，你需要理解它在应用栈中的位置、应该暴露什么、客户端如何与它连接，以及当集成走出本地原型时，哪些设计决策才要紧。

本文将解释 MCP 服务器如何工作、如何在 tools、resources 和 prompts 之间做选择，以及把 MCP 服务器搬进生产需要考虑什么。

## MCP 服务器到底做什么？

MCP 服务器是 AI 应用与你希望该应用使用的系统之间的边界。[MCP](https://github.com/phuihock/mcp-deeinfra) 遵循 host-client-server（宿主-客户端-服务器）架构。

- **MCP host：** 协调交互的 AI 应用。
- **MCP client：** host 内部负责连接某一个 MCP 服务器的组件。
- **MCP server：** 向该客户端暴露上下文与能力的程序。

单个 host 可以连接多个服务器。它为每个连接创建独立的 MCP client，以保持服务器边界彼此独立。例如，一个编码智能体可以连一个源码控制服务器、一个 issue 跟踪服务器、一个内部文档服务器。

MCP 还把数据层与传输层分开。数据层定义协议消息、能力发现、tools、resources、prompts 及相关行为；传输层决定这些消息如何在客户端与服务器之间流动。因此同一套服务器能力既可以通过标准 I/O 在本地暴露，也可以经 HTTP 远程暴露。

下面是一个最小代码示例：用 FastMCP 创建一个 MCP tool，通过 MCP client 发现它，把它的 schema 传给 DeepInfra 托管的模型，并把模型的 tool call 经由 MCP 服务器路由回来。

安装 FastMCP（MCP 服务器与客户端）和 OpenAI SDK（调用 DeepInfra 的 OpenAI 兼容 API）：

```
pip install fastmcp openai
```

导入依赖并创建 FastMCP 服务器。@mcp.tool() 装饰器把 get_weather 暴露为一个 MCP tool，并从 Python 函数推导出它的输入 schema。

```
import asyncio
import json
import os
from fastmcp import FastMCP, Client
from openai import OpenAI



mcp = FastMCP("WeatherServer")



@mcp.tool()
def get_weather(city: str) -> str:
    """Get current weather for a city."""
    weather_db = {
        "london":   "Overcast, 14C, humidity 78%",
        "tokyo":    "Partly cloudy, 28C, humidity 65%",
        "new york": "Clear sky, 22C, humidity 45%",
        "paris":    "Light rain, 16C, humidity 82%",
        "dubai":    "Sunny, 42C, humidity 20%",
    }
    return weather_db.get(
        city.lower(),
        f"No data for '{city}'. Try: {', '.join(weather_db.keys())}",
    )
```

创建 MCP client，用 list_tools() 发现服务器暴露的能力。发现到的 MCP schema 随后被转换成模型期望的 OpenAI 兼容 tool 格式。

```
client = Client(mcp)

async def discover_tools() -> list[dict]:
    async with client:
        mcp_tools = await client.list_tools()
        return [
            {
                "type": "function",
                "function": {
                    "name":        t.name,
                    "description": t.description or "",
                    "parameters":  t.inputSchema,
                },
            }
            for t in mcp_tools
        ]
```

配置 OpenAI 客户端指向 DeepInfra 的 [OpenAI 兼容端点](https://docs.deepinfra.com/api-reference/introduction)。模型收到发现到的工具后，可以通过 tool calling 选择一个并生成其参数。

```
DEEPINFRA_API_KEY = os.getenv("DEEPINFRA_API_KEY", "your_api_key_here")

llm = OpenAI(
    api_key=DEEPINFRA_API_KEY,
    base_url="https://api.deepinfra.com/v1/openai",
)

MODEL = "zai-org/GLM-5.2"

async def agent(user_message: str, tools: list[dict]) -> str:
    messages = [
        {"role": "system", "content": "You are a helpful weather assistant. Use the provided tools to answer questions. Be concise."},
        {"role": "user", "content": user_message},
    ]

    async with client:
        while True:
            response = llm.chat.completions.create(
                model=MODEL,
                messages=messages,
                tools=tools,
                tool_choice="auto",
            )
            assistant_msg = response.choices[0].message
            messages.append(assistant_msg)

            if not assistant_msg.tool_calls:
                return assistant_msg.content

            for tc in assistant_msg.tool_calls:
                tool_name = tc.function.name
                tool_args = json.loads(tc.function.arguments)
                result = await client.call_tool(tool_name, tool_args)

                result_text = ""
                if hasattr(result, "content"):
                    result_text = "\n".join(
                        c.text for c in result.content if hasattr(c, "text")
                    )
                else:
                    result_text = str(result)

                messages.append({
                    "role": "tool",
                    "tool_call_id": tc.id,
                    "content": result_text,
                })
```

当模型返回一个 tool call 时，client.call_tool() 把它路由给 MCP 服务器执行。结果带着匹配的 tool_call_id 加入对话，让模型在下一步推理中使用它，要么再发起一次 tool call，要么给出最终答案。

最后是发现可用工具，并发出一个需要模型使用其中某个工具的请求。asyncio.run() 启动这个异步 MCP 工作流。

```
async def main():
    tools = await discover_tools()

    queries = [
        "What's the weather like in Tokyo?",
        "Compare the weather in London and New York. Which city is warmer?",
    ]

    for q in queries:
        print(f"Q: {q}")
        answer = await agent(q, tools)
        print(f"A: {answer}\n")



if __name__ == "__main__":
    asyncio.run(main())
```

## Tools、Resources 与 Prompts：你的服务器该暴露什么？

MCP 服务器暴露三种主要的服务器端原语，各有不同的控制模型：tools 由模型控制，resources 由应用控制，prompts 由用户控制。

### Tools：当 AI 需要"做某事"

MCP tools 是模型可以调用的可操作接口，用于服务用户的请求与上下文。当模型需要执行动作或进行计算时用它——查询数据库、取回订单、创建 issue，或调用既有 API 操作。

每个 tool 通过输入 schema 声明可用的操作及其接受的输入。当模型选中一个 tool，MCP client 向服务器发送请求，服务器执行操作并返回结果。

### Resources：当 AI 需要"上下文"

Resources 暴露的信息由 AI 应用负责访问，并作为上下文提供给模型。host 决定从可用资源中取哪些、如何把它们的内容放进[模型的上下文](https://deepinfra.com/blog/build-a-rag-app-with-deepinfra-and-langchain)。

MCP 用 URI（Uniform Resource Identifier）标识资源，让服务器能以一致的接口暴露来自不同底层源（如数据库）的数据。

### Prompts：当你想要可复用的交互模式

Prompts 是供用户显式选择的、可复用的交互模板，例如评审一个代码改动或分析一次事故。一个 prompt 可以定义要发给模型的消息，并接受用于定制这次交互的参数。

MCP 服务器定义 prompt，client 把它呈现给用户，用户调用时服务器返回组装完成的消息。

## MCP 服务器 vs. API vs. Function Calling：到底有什么不同？

MCP 服务器、API 和 function calling 可以同时出现在同一个请求里，但各自的目的不同。

- **API** 定义软件如何与一个服务交互。如果你的 CRM 已经暴露了获取账户信息的端点，MCP 不会让这个端点变得多余。
- **MCP 服务器** 可以站在这些 API 前面，用 MCP 客户端理解的接口暴露挑选出来的操作。底层 API 依然负责真正的业务逻辑。
- **Function calling** 更贴近模型。模型收到工具定义，判断是否需要执行某个操作，并生成带参数的 tool call。应用负责执行被请求的操作，并把结果返回给模型。

每一层在请求中控制什么：

| **层** | **它定义什么** | **在请求中的角色** |
| --- | --- | --- |
| **Function calling** | 模型可以请求哪些工具及其参数 schema | 让模型选择操作并生成参数 |
| **MCP 服务器** | 通过 MCP 暴露哪些外部能力 | 让工具和上下文对 MCP 客户端可发现、可访问 |
| **API** | 服务的端点与应用契约 | 执行或提供对底层应用功能的访问 |

## 本地还是远程？选择 MCP 服务器的运行方式

MCP 定义了两种标准传输：STDIO 与 Streamable HTTP。它们承载相同的协议语义，却造就不同的运行模式。

### 本地 MCP 服务器：STDIO

MCP client 以子进程方式用 STDIO 启动服务器，通过标准输入输出交换以换行分隔的 JSON-RPC 消息。服务器从 stdin 读协议消息，把协议消息写到 stdout，并可以用 stderr 做诊断。任何写入 stdout 的、不是合法 MCP 消息的内容都可能打断协议流。

STDIO 还把部署边界保持得很小。在证明能力可用之前，不需要运维远程端点、TLS 终结、多租户路由或网络授权层。

这个模式很适合本地文件系统与源代码操作、开发者或桌面工具，以及需要访问本地凭证或进程的流。

STDIO 传输让 MCP 客户端启动一个本地服务器进程，并通过标准输入输出交换消息。

### 远程 MCP 服务器：Streamable HTTP

Streamable HTTP 下，MCP 服务器独立运行，可同时服务多个客户端。按当前协议，客户端把消息作为 HTTP POST 请求发送到[单个 MCP 端点](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)。响应可以返回 JSON，在需要流式时走请求级的 Server-Sent Events（SSE）流。

这让 Streamable HTTP 更适合共享服务、SaaS 集成和生产部署。代价是你从此要处理标准的服务议题：认证、授权、限流、租户隔离与监控。

对受保护的 HTTP 服务器，MCP 定义了一个[基于 OAuth 的授权模型](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)，其中 access token 针对目标 MCP 资源进行校验。

## 当 MCP 服务器走出 Demo，什么会先崩？

Demo 只证明服务器能提供一个能力并返回一个结果。生产中，可靠性取决于：模型选对工具、权限约束住动作、失败可以恢复、执行过程可观测。

- **工具太多会让选择更不可靠。** 每个工具定义都在扩大模型的决策空间和输入上下文。随着提供的函数增多，模型质量会下降，而且函数定义也计入[输入 token 用量](https://docs.deepinfra.com/chat/tool-calling?utm_source=chatgpt.com)。让可用工具集聚焦于工作流真正需要的能力，而不是把每个后端端点都暴露出去。
- **含糊的工具契约导致错误调用。** search_user 和 find_user 这类相似工具，除非用途写得很明白，否则难以区分。用有明显区别的名称、描述和输入 schema，让模型能判断哪个操作适用并生成合法参数。
- **光有认证管不住动作。** 合法的调用方不应自动拥有调用所有工具的权限。使用最小权限 scopes，让客户端只申请操作所需权限，并在破坏性或高影响动作前加确认或策略闸门。
- **笼统的错误阻碍恢复。** MCP 区分协议失败与工具执行错误。针对非法参数、授权失败、上游故障或业务规则违例返回具体的错误，让模型能判断要不要重试、怎么重试。
- **API 级监控解释不了智能体的失败。** 要追踪从模型决策到工具请求、MCP 执行、再到上游服务和工具输出的完整路径。采集工具名、延迟、执行状态、授权失败和重试次数，用来定位失败源自[模型选择](https://deepinfra.com/blog/deepseek-v4-flash-vs-qwen3-6-vs-glm-4-6-benchmarks)、MCP 服务器还是底层服务。

## 什么时候该用 MCP，什么时候是杀鸡用牛刀？

当"能力边界"本身需要变成可复用时，MCP 才最有价值。

如果多个 [AI host](https://deepinfra.com/blog/hosted-agents) 需要同一个集成，或者能力应该被轻松发现而不是嵌死在单一应用里，MCP 服务器提供了一个稳定的集成面。它还让你在更换模型和[智能体框架](https://deepinfra.com/blog/frontier-level-agents-on-open-models-langchain-deep-agents-nvidia-nemotron-3-ultra-live-on-deepinfra)时不必重建对内部系统的访问。

当一个小而静态的工作流的两端都属于同一个应用时，它的说服力就弱了。如果一个智能体只需要一个私有 API 操作，而且不会有别的客户端复用它，普通 function calling 可能依旧更简单。

一个有用的检验标准：你是在标准化一个可复用的集成，还是在给单个函数又套了一层协议。

## DeepInfra 在 MCP 技术栈中的位置

MCP 提供对工具和上下文的标准化访问，而模型决定调用哪个工具、发送什么参数、以及如何使用结果。

DeepInfra 通过其 [OpenAI 兼容 API](https://docs.deepinfra.com/api-reference/introduction) 提供那个[推理层](https://deepinfra.com/blog/how-deepinfra-built-on-nvidias-inference-stack-and-why-it-paid-off)。其支持的模型可以用 [tool calling](https://docs.deepinfra.com/chat/tool-calling) 选择函数并生成结构化参数。应用经由 MCP 服务器调用被请求的工具，把结果返回给模型，再运行下一步推理以继续或完成任务。DeepInfra 支持自动工具选择、单工具调用和并行工具调用——尽管并行调用的质量因模型而异。

由于 MCP 集成与推理保持分离，你可以对比[不同模型](https://deepinfra.com/models)在工具调用可靠性、延迟、上下文窗口和[推理成本](https://deepinfra.com/pricing)上的差别，而不用改动 MCP 服务器或其后端集成。DeepInfra 目前通过其推理平台提供 100+ 开源模型。

## 结语

交付一个 MCP 服务器，从能力边界开始。决定模型应该能做什么、应用只需要读什么、可复用的 prompts 是否增值。保持工具聚焦、schema 清晰。

本地工作流用 STDIO；作为共享基础设施服务时切换到 Streamable HTTP。上生产之前，把授权、错误语义、可观测性和工具选择行为当作接口的一部分来对待。

此外，让 MCP 专注于标准化对外部能力的访问，业务逻辑继续留在现有服务里。这份分离也让推理层可以演进，而不必重做 MCP 集成。
