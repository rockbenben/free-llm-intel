# 决策模型：AI 智能体的快速层

发布于 2026.10.13 · Niklas

![Decision Models：AI 智能体的快速层](https://deepinfrabldev.wpenginepowered.com/wp-content/uploads/2026/10/Decision-Models_-The-Missing-Layer.png)

有一个决策，你的智能体每场会话要做上几十次，而你可能正在掏钱让一个前沿模型来接手。这个请求该走又快又便宜的模型，还是走贵的那个？这次工具调用执行起来安全吗？任务是真的完成了，还是智能体自己觉得完成了？这六份检索回来的文档里，哪一份跟问题相关？

这些全都是选项集合固定的有界选择。没有哪一个需要生成散文，没有哪一个需要思维链，也没有哪一个应该花掉一次 Claude 或 GPT-5.5 调用那么贵。但对今天大多数构建智能体流水线的团队来说，他们付的恰恰就是这个钱——因为只要一个决策不是规则表能处理的，回路里那个 LLM 就是最省事的默认选项。

2026 年 9 月，一个新的模型品类出现来解决这个问题，它扩散的速度超过过去一年里智能体工具领域的任何东西。TypeSafe AI 在 9 月 15 日发布了 Jev。开源替代品 Laya 三天后跟进。基于开放解码器的 Kev 也在同一周亮相。AWS 在 10 月 1 日发布了 Strands Decider 2B。OpenAI 在同一周的 DevDay 2026 上宣布了 Decisions API，并在 10 月 6 日把它推入公测。随后不久，一个叫 Ollaya 的本地运行时出现，把七个开放决策模型打包在同一个 API 端点之后。这个品类从不存在到被争夺，用了不到三周。

这篇文章会讲清楚：决策模型到底是什么，它的架构与生成式 LLM 有何不同，专有与开放选项的当前格局是什么样，这些模型在智能体流水线里落在哪一层，以及那些诚实的局限在哪里。

## 决策模型到底是什么

决策模型有两个输入：一段上下文（一条消息、一份文档、智能体的对话历史、一次工具调用拟定的参数），以及一组预定义的候选答案。它从这组答案里返回一个，并给每个选项配一个置信度分数。它从不生成文本。输出永远是你提供的那些选项中的一个，附带一个概率。

TypeSafe 把它叫作「System One model」，这是刻意呼应 Kahneman 的双加工框架：把决策模型定位为快速、自动的认知层，负责处理有界判断；把生成式 LLM 留给缓慢、审慎的推理。

这个名字已经在整个领域里留下来，甚至对不是 TypeSafe 的实现也如此。三类问题已经成了这个领域里所有实现的标准接口：

| **问题类型** | **返回** | **示例** |
| --- | --- | --- |
| Choice | 从固定列表里选一个选项 | 给这张工单分流：billing / technical / shipping / other |
| Score | 0 到 1 之间的一个数 | 紧急度评分，从 0（低）到 1（危急） |
| Noul (yes/no) | 0 到 1 之间的一个概率 | 这次工具调用是否有用户原话作为依据？ |

置信度分数不是一个礼貌性的附赠功能。它是让决策模型可自动化的那个机制。你让生成式 LLM 把一条消息分成 billing 还是 technical，即使这条消息本身就模糊，它几乎总会给你一个答案——文本生成就是这么干活的。而带有校准过的置信度分数的决策模型，让你可以设一个阈值：高于 0.85 就自动执行，低于它就转交给人类或一个更大的模型。你可以按具体场景里「决策做错一次的代价」来调这个阈值的位置。这件事用生成式模型的输出来做，怎么做都不干净。

## 架构是怎么运作的

决策模型的定义性架构特征，是它没有语言建模头。标准的基于 transformer 的 LLM 末端有一个头，它在每一步生成都产出覆盖整个词表的概率分布，然后按顺序从这个分布里采样，生成文本。那个词表投影开销很大，而顺序采样正是文本生成要花上几秒的原因。

决策模型把这个词表头摘掉，换成一个指针头或决策头，只对你提供的那些具体选项打分。没有词表，没有采样。模型读上下文，读选项，在单次前向传播里给每个选项产出一个分数。

这一架构差异带来了惊人的延迟下降。Jev 报告端到端延迟 70–500ms，前沿模型则是 3 秒以上。OpenAI 的 Decisions API 在 DevDay 上演示的是约 150ms，相比之下标准 Luna 调用是 1,600ms——大约快了 10 倍。AWS 的 Strands Decider 2B 跑在 H100 GPU 上，报告决策时间在 100ms 以下。

摘掉词表头的另一个后果是：没有输出 token 成本。决策模型只对输入计费。按 Jev 每百万输入 token $0.042 的价格，跟一次前沿模型调用比起来，成本对比就不是边际性的了。一条每月过 1,000 万个决策的流水线，走 Jev 花 $420。同样这些决策走 [Claude Haiku 4.5](https://deepinfra.com/anthropic/claude-haiku-4-5)——已经是较便宜的生成式选项之一——一旦算上把分类结果说出来所需的输出 token，成本要高出好几个数量级。

## 每个模型如何训练校准

决策模型返回的置信度分数，只有经过校准才有用——0.85 的置信度要真的对应 85% 的情况下是对的。校准做对比准确率做对更难，也正是这个品类里不同模型在技术上分道扬镳的地方。

在所有严肃实现里已经成为标准的那一套训练方法，叫 RLCD：Reinforcement Learning for Calibrated Decisions（为校准决策做强化学习）。RLCD 不是用交叉熵损失来训练（交叉熵追求准确率，但会把输出训得过度自信），而是让模型去最大化严格适当的评分规则（strictly proper scoring rule）。最常用的是 Brier score 和对数 scoring rule。这样训出来的模型，有动力在真正只有 60% 把握的时候说 0.6，而不是为了多挣一点准确率奖励把数字向上凑到 0.95。

Laya 把它的 RLCD 实现公开写在文档里：GRPO 风格的策略梯度，奖励是对数、球面和排序概率三种 scoring rule 的组合，完全不使用监督交叉熵损失。TypeSafe 说 Jev 也是用 RLCD 训练的，但没有公布细节。Strands Decider 2B 的训练配方随模型权重一起以 Apache 2.0 公开，描述了类似的做法。

校准质量在实践上的后果，体现在基于阈值的路由上。如果你的决策模型在一类它其实只有 72% 情况正确的决策上，稳定地报出 0.92 置信度，那 0.85 这个阈值给你的就是虚假的踏实感。针对 JevBench 的独立评测显示，Jev 目前在这批可用选项里校准最好，开源实现正在以超出预期的速度缩小差距。

## 当前格局

决策模型这个赛道，在不到三周里从一个专有选项变成了多方争夺的市场。截至 2026 年 10 月上旬，各个选项的位置如下：

| **模型** | **架构** | **参数量** | **延迟** | **成本** | **许可** | **部署** |
| --- | --- | --- | --- | --- | --- | --- |
| Jev 1.13 (TypeSafe) | 专有，并行 | 未公开 | 70–500ms | $0.042/M 输入 | 专有 | Cloud API, OpenRouter |
| Strands Decider 2B (AWS) | Qwen3.5-2B + 指针头 | 2B（约 1M 指针头） | 约 100ms (GPU) | 免费（自托管） | Apache 2.0 | 本地, Bedrock AgentCore |
| Laya (Convai) | ModernBERT-large + 决策头 | 421M | 33ms (GPU) | 免费（自托管） | Apache 2.0 | 本地, Docker, MCP |
| Kev-4B (Jared Palmer) | Qwen3.5-4B + LoRA + 指针头 | 4B | 18ms (H100) | 免费（自托管） | 开放权重 | 本地服务器 |
| OpenAI Decisions API | GPT-6 Luna（专用版） | 未公开 | 约 150ms | 专有 | 专有 | Cloud API |
| Ollaya | 运行时（打包 Laya, Decider, Kev 等） | 各异 | 8ms (Laya-multilingual) | 免费（自托管） | Apache 2.0 | 桌面, Docker, CLI |

开源阵营里的架构分野值得搞清楚，因为它会带来不同的实际取舍。

- **Laya：** 用的是双向编码器（ModernBERT-large，421M 参数）加一个训练过的决策头。双向编码器在给出输出之前，会从两个方向把整段上下文读一遍，这让它们在参数量不高的情况下有相当强的理解力。缺点是 Laya 的 base checkpoint（不带 typed-decisions 微调的那一个）在 JevBench 上只拿到中游分数。
- **Kev：** 用的是 [Qwen3.5](https://deepinfra.com/Qwen/Qwen3.5-27B) 解码器主干，加一个 rank-16 的 LoRA 适配器，再加一个自定义的指针头。指针头比较 <decide> 结束 token 位置的隐藏状态和每个选项的结束 token，返回校准过的概率。因为 Kev 保留了完整的自回归解码器主干，它带着生成式模型那样的理解力，只是把输出从词表分布改走指针。Kev-4B 在独立的 2,394 题评测上超过 Laya 的三个 checkpoint。Kev-27B 需要一块 80GB GPU，或者一台带 96–128GB 统一内存的 Mac——这更接近一个小生成式模型的部署，而不是一个轻量分类器。
- **Strands Decider 2B：** 走的是 Kev 那一路架构：Qwen3.5-2B 的解码器主体，把语言模型头摘掉，换成一个约 1M 参数的指针头。AWS 连同权重一起公布了完整的训练配方和数据清单，这是几个实现里最可核查的一个。独立评测给出的 Strands Decider 在 100 题评测集上路由准确率 72%——低于 Jev 的云端表现，但和 Laya 的 base checkpoint 打得住。AWS 文档里明确写出它的设计意图：让 Decider 承担智能体稳定命中的那部分场景（高频、低歧义的路由和工具门控），凡是置信度低于设定阈值的都升级给 LLM。在一场与 [Claude Haiku 4.5](https://deepinfra.com/anthropic/claude-haiku-4-5) 的正面基准里，混合方案——高置信度的决策交给 Decider，Haiku 只在置信度低于 0.6 时兜底——把准确率打到了 90%，而 Decider 单打独斗只有 72%。
- **OpenAI 的 Decisions API：** 走的路子和所有开放模型都不一样：它是通过 GPT-6 Luna 的一个专用版本来做决策，而不是一套专门设计的决策架构。实际含义是，它的理解能力很可能高于任何一个开放模型，代价是专有定价，以及输入必须走 OpenAI 基础设施这一约束。它同时支持文本和图像输入，这是所有开放模型目前都还没有的。

## 决策模型在智能体流水线里落在哪一层

品类出现后的最初几周里，用这些模型的开发者社区里最稳定地浮现出十二个用例，值得被明确地梳理出来——因为正确的心理模型不是「决策模型是做分类的」，而是「决策模型负责的是所有此刻不必要地跑在你 LLM 上的有界选择」。

### 路由与编排

- **模型路由**：给进来的请求按复杂度打分，路由到能应付得起的最便宜的模型。一个决策模型带置信度分数地把复杂度分成 low/medium/high，可以替掉一组手写规则，或者一次昂贵的预调用 LLM。高吞吐流水线上的复利式节省非常可观，举例来说，每一个被正确路由到 [Deepseek V4-Flash](https://deepinfra.com/deepseek-ai/DeepSeek-V4-Flash) 而不是 [Claude Opus 4.7](https://deepinfra.com/anthropic/claude-opus-4-7) 的请求，大约省下 $24.72/M 输出 token。
- **工具选择**：给定可用工具的描述和当前智能体状态，[下一个该由智能体调用哪个工具](https://deepinfra.com/blog/deepinfra-function-calling-guide)？这恰好就是一个从已知选项集合里做的有界选择。
- **编排分叉**：在多智能体系统里，这个子任务应该交给哪个智能体？决策模型按当前状态给每个智能体打分，返回一个带置信度加权的分派结果

### 安全与护栏

- **工具调用门控**：在执行一个被提议的工具调用之前，先确认参数是站得住脚的、来自用户实际说过的话。AWS 文档里 Strands 的例子抓到一个天气智能体在用户还没说城市时就调用工具——决策模型把这次调用标为太早，而不是让智能体编一个地点出来。这种模式站在智能体和每一次工具调用之间，多加的开销在 100ms 以下。
- **破坏性动作分类**：这条 shell 命令 / 数据库写入 / 文件删除能不能自动执行，还是要升级给人类？带校准置信度的决策模型让这道闸门变得可调——你可以按自己环境里「执行错一次的代价」来定阈值。
- **内容策略**：这条用户消息在本应用的范围之内吗？在决策层而不是 LLM 层就把超出范围的请求路由出去，意味着每一条被拒的输入都省下了一整次 LLM 调用的成本。

### 评估与质量控制

- **完成度校验**：智能体的任务真的做完了，还是它错误地判断自己做完了？这是 agentic coding 里最顽固的失败模式之一。测试还没通过、实现还不完整，智能体却报告成功。在每一轮循环里用一个决策模型带置信度阈值来评估完成度，就在智能体退出之前多加了一道轻量检查。
- **输出质量打分**：把 LLM 的最新输出往下游传之前，先给它的相关性、正确性或任务对齐度打一个分。单次检查成本极低，让这一步可以在每一步生成都跑，而不只是事后复核。

### 记忆与上下文管理

- **记忆检索相关性**：这十条检索回来的记忆块里，哪几条跟当前查询真正相关？一个决策模型替掉了原本为了 [重排序](https://deepinfra.com/blog/llm-rerankers) 而做的第二次 LLM 调用。
- **上下文压缩门控**：新的信息量够不够触发对智能体工作记忆的一次更新，还是可以继续沿用当前上下文？这是一次成本极低的判断，能持续运行而不会明显加负担。
- **优先级分类**：在一堆待办任务的队列里，给每一个打紧急度分数，据此路由。

### 这些用例说明了什么

这些用例身上共同的一点是：决策是有界且重复的。选项集合你事先就知道。正确的答案不需要生成一段解释。为这种事跑一个前沿 LLM，就像请一个高级工程师整天只做判断题——技术上做得了，但工具选错了。

## 与这个品类一起长出来的基准

[JevBench](https://benchmarkheaven.com/jev-models) 是一个评测决策模型在路由和分类任务上表现的基准，它伴随 Jev 一起出现，现在已经成了各实现之间事实上的对比标准。2026 年 10 月上旬的独立结果给出的分数是：Jev（TypeSafe 的专有模型）63.29（公开集 86.6% / 密封集 36.7% 准确率），Strands Decider 2B 为 0.723（在 231 题上准确率 72.3%），Laya 的 421M base checkpoint 在同一标度上是 30.25。

关于这几个数字有两点要说明。第一，Jev 与开源实现之间在难题上的差距是真实存在的，但拿 Laya 的 base checkpoint 做对比是错的：laya-typed-decisions 那个微调过的 checkpoint 在它自己的基准上有 0.766 的准确率，那才是为生产智能体决策任务设计的那一个。第二，所有这些模型都只有几周大。开源实现正在以超出预期的速度追近差距；Kev 结果里所呈现的改进速度（Kev-4B 在 2,394 题评测上超过所有 Laya checkpoint）意味着，六个月之后这个品类会长成另一副样子。

独立测试给出的诚实校准发现是：Strands Decider 2B 单独跑时 72% 的准确率，放到「LLM 处理低置信度情况」的混合架构里就变成了 90%。对大多数生产用例来说，正确的问题不是「这个模型能不能追平 Jev？」，而是「把 n% 的决策路由给 Decider、剩下的走 LLM，在准确率和成本之间怎么换？」

## 决策模型的那些坑

决策模型解决的是一个真问题，这个品类的势头也不太可能倒回去。但在生产环境里押注某一个之前，有三个局限值得知道。

### 难题上的差距是真的

JevBench 的密封集准确率分数暴露出一个事实：开源实现在真正含糊或复杂的决策上，明显差于 Jev。在一个清晰的例子上给出高置信度预测，和在一个边界例子上给出可靠表现，不是一回事。如果你的应用依赖的是分布在尾部上的那些决策能做对，目前的开源选项还做不到。[混合架构模式](https://deepinfra.com/blog/two-tier-agent-two-models)（高置信度的情况交给决策模型，其余靠 LLM 兜底）就是针对这一局限的工程解法，也正是 AWS 明确推荐给 Strands Decider 的模式。

### 决策模型不做推理

从一组预定义选项里返回一个有界选择，并不等于理解为什么这个选择是对的。一个把消息分类为「billing」的决策模型，没法解释它的推理，抓不到超出它训练分布的边界情况，也无法泛化到它没见过的选项集合。对那些需要理解新上下文、需要生成一段简短解释、或者需要处理训练时不存在的选项的应用来说，决策模型就是错的工具。

### CPU 部署很慢

Strands Decider 2B 跑在 CPU 上，一次决策要 4 秒以上——这比一次快速的 LLM API 调用还慢。决策模型的延迟优势，前提是 GPU 推理。对开发者机器上或边缘环境里的本地部署（没有 GPU 加速），延迟画像完全变样。Ollaya 的 Laya-multilingual checkpoint 是目前最快的一档，GPU 上中位数 8ms；换到 CPU 上，看硬件不同，这个数字会放大 50–100 倍。

## 这对智能体流水线设计意味着什么

决策模型作为智能体技术栈里的一个独立层浮现出来，这改变了在规模上运行的流水线的设计模式。在此之前，智能体控制流的选项只有三种：把决策写进代码（规则表、if/else 逻辑），调用一次 LLM 再把输出解析出来，又或者用生成式模型的结构化输出。每一种都有代价：规则表脆弱、处理不了语义复杂度；LLM 调用又贵又慢；结构化输出还是要付完整的生成成本，外加一层解析开销。

决策模型多给了一个选项：一个专门打造的判断层，延迟在 200ms 以下、输出成本近乎为零，带校准的置信度，让基于阈值的自动化变得可行。正确的架构不是「用决策模型代替 LLM」，而是「让决策模型负责那些不需要生成式推理的高频有界选择，把 LLM 留给真正需要它的那些长时序任务」。

大多数团队实际的起点是模型路由。一个决策模型只要能正确识别出 80% 的请求适合走便宜模型（V4-Flash、Haiku），把剩下 20% 路由到前沿模型，就能把这个品类的大部分成本节省拿到手，而不需要把流水线大改。Jev 每百万输入 token $0.042，或者自托管 Strands Decider 的边际成本为零——这一层路由在生产流量跑起来的当天就能把自己回本。

这个品类才三周大。围绕它长出来的基础设施表明，决策模型不是一次产品发布，而是智能体基础设施栈里新的一层。下一次你的智能体做一个有界选择时，值得问一问：这个选择到底需不需要一个语言模型。
