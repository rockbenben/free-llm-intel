## **Granite 4.2 8B 简介**

[Granite 4.2 8B](https://deepinfra.com/ibm-granite/granite-4.2-8b) 是 IBM Granite 4.2 家族中的中等规模推理模型。IBM 将其定位为一款面向通用企业应用的均衡模型。内置在 *<think>…</think>* 标签之内的 chain-of-thought 推理，支撑它在 AIME 2025（86.67）和 LiveCodeBench v6（73.24）这类偏重推理的基准上取得强劲结果。

三种 thinking 模式让你能针对每次查询在深度与延迟之间做权衡：完整 thinking（默认）、non-thinking 和 low-effort。

该模型是 decoder-only 的 dense transformer。它使用 grouped query attention（32 个 attention head 与 8 个 KV head）、rotary position embeddings（RoPE），以及带 SwiGLU 激活的 MLP。

它支持 12 种语言：英语、德语、西班牙语、法语、日语、葡萄牙语、阿拉伯语、捷克语、意大利语、韩语、荷兰语和中文。

### **核心能力**

- **内置推理：** 原生 chain-of-thought 提升了在数学、编码和复杂多步问题上的表现。
- **灵活的 thinking 模式：** 你可以在同一个模型内切换完整 thinking、non-thinking 和 low-effort 模式。
- **推理增强的 tool calling：** 模型在发起调用之前，会先推理该调用哪个工具、以及为什么调用它。
- **Agentic 工作流：** 强化学习覆盖了真实仓库上的软件工程、多步终端任务和多跳 web 搜索。

## **API 供应商对比**

Artificial Analysis 为 Granite 4.2 8B 跟踪两家供应商：DeepInfra 和 CoreWeave。OpenRouter 在两者之间做路由，Puter.js 则提供免费的开发者集成。

| **供应商** | **混合价格（每 1M tokens）** | **输出速度** | **延迟（首 chunk 中位数）** | **关键差异点** |
| --- | --- | --- | --- | --- |
| DeepInfra | $0.05 | 120 t/s | 0.77 s | 最低的输入与缓存价格（每 1M 分别为 $0.06 和 $0.015），以及实测最高的输出速度 |
| CoreWeave | $0.07 | 89 t/s | 0.74 s | 最低的输出价格（每 1M $0.15），首 chunk 延迟略低 |
| OpenRouter | 走 DeepInfra 路由时为 $0.06 输入 / $0.25 输出 | 取决于被路由到的供应商 | 取决于被路由到的供应商 | 通过一个 OpenAI 兼容 API，在 DeepInfra 与 CoreWeave 之间自动 failover |
| Puter.js | 在用户付费模式下对开发者免费 | 未公布 | 未公布 | 免费集成，无需后端或 API key 配置 |

表中的延迟是到首个 chunk 的中位时间。推理模型在吐出第一个答案 token 之前还要花时间思考。Artificial Analysis 在 DeepInfra 上测得该时间为 17.78 秒，在 CoreWeave 上为 22.65 秒。

OpenRouter 自己的供应商表在吞吐上给出了同样的排序，DeepInfra 领先于 CoreWeave。

## **模型的局限**

在部署 Granite 4.2 8B 之前，有几项局限需要权衡：

- **冗长：** 模型在整个 Intelligence Index 上生成了 130M 输出 tokens，而中位数为 82M。更长的输出会推高[输出成本](https://deepinfra.com/blog/inference-economics-ai-costs-at-scale)，因此要为此留出预算。
- **推理延迟：** 到第一个答案 token 的时间包含思考时间。non-thinking 和 low-effort 模式可以缩短对延迟敏感的请求的等待。
- **内存占用：** 权重在 bfloat16 下约占 16 GB，4-bit 量化版本可将其缩减到约 4 至 6 GB。KV cache 会随上下文长度和并发量增长，因此要服务完整的 131K 窗口，所需内存远超权重本身。
- **多语言差异：** 微调主要依赖英语的指令-回复对，因此多语言对话质量可能参差不齐。IBM 指出 few-shot 示例会有帮助。
- **安全与输出质量：** IBM 指出模型偶尔可能产生不准确、有偏或有害的回答，并建议搭配 Granite Guardian 使用。推理标签内的内容是中间思考过程，并不代表最终结论。
- **编码余量：** SWE-Bench Verified 达到 47.67。SWE-Bench Pro 的 19.11 和 Terminal-Bench 2.1 的 20.56 表明，在更难的 agentic 编码任务上仍有成长空间。
- **仅限文本：** 模型只支持文本输入与输出，不具备图像处理能力。

## **评估模型所用的方法**

本评测综合了独立的 Artificial Analysis 测量、IBM 公布的结果以及供应商数据。

### **智能评估**

- 模型按 Artificial Analysis Intelligence Index 评分。它是对 agents（30%）、编码（20%）、科学推理（20%）和通用知识（30%）的加权平均。
- Granite 4.2 8B 得分为 11，高于同规模开放权重模型的中位数 8。

### **性能指标**

- **Time to first token（TTFT）：** 从发送请求到收到响应第一个 token 之间的时间。
- **输出速度：** 第一个 token 到达之后每秒收到的平均 token 数。
- [**混合定价：**](https://deepinfra.com/blog/pricing-101-token-math-cost-per-completion) 按 cache 命中、输入和输出 tokens 的 7:2:1 比例计算，可近似真实的使用成本。

### **基准数据集**

IBM 针对 8B 模型公布的评测（运行在基于 NeMo Evaluator SDK 的框架上）包括：

- 面向软件工程的 SWE-Bench Verified（47.67）、SWE-Bench Multilingual（30.78）和 SWE-Bench Pro（19.11）
- 面向科学与数学推理的 GPQA（64.14）和 AIME 2025（86.67）
- 面向 tool calling 的 Berkeley Function Calling Leaderboard v4（52.39）和 τ³-bench（58.06）
- 面向指令遵循的 IFBench（79.33）和 Arena-Hard-V2（65.19）

这些结果是 IBM 自己报告的，因此在独立评测跟上之前，应把它们视为方向性参考。

### **供应商对比**

- Artificial Analysis 从价格、输出速度和延迟三方面对供应商做基准测试。
- OpenRouter 的数据提供了路由行为与可用性信息。

## **分析要点**

- **相对其规模而言很强的智能：** Granite 4.2 8B 在 Intelligence Index 上得分 11。这高于可比的开放权重模型的中位数 8，并在全部 141 个模型中排名第 35。
- **通过第三方供应商实现的成本效率：** DeepInfra 标价每 1M 输入 tokens $0.06、每 1M 输出 tokens $0.25、每 1M 缓存 tokens $0.015。折算下来是 $0.05 的混合费率，每个 Intelligence Index 任务约 $0.02。
- **Apache 2.0 许可证：** 宽松的许可证允许商业部署、微调和自托管。
- **灵活的推理模式：** 在完整 thinking、low-effort 和 non-thinking 模式之间切换，可以针对每次查询调节深度与延迟的取舍。
- **原生** [**tool calling**](https://deepinfra.com/blog/deepinfra-function-calling-guide)**：** 推理增强的 tool calling 让模型在行动之前先权衡该用哪个工具。IBM 报告 τ³-bench 为 58.06，BFCL v4 为 52.39。
- **有竞争力的速度与冗长的输出：** 以每秒 98.4 个输出 tokens 计，模型快于约 75 的中位数。但它的冗长仍然影响总响应时间与成本。
- **自托管是可行的：** IBM 发布了 FP8、NVFP4、MXFP4 和 GGUF 变体。在限制上下文长度的情况下，4-bit 版本可以塞进消费级 GPU。

## **结论**

Granite 4.2 8B 在紧凑、许可证宽松的封装中交出了强劲的推理能力。它适合希望具备以下条件的组织：

- 具备完整模型权重透明度的企业级推理
- 通过有竞争力的第三方 API 供应商实现高性价比部署
- 支持原生 tool calling 与多步推理的 agentic 工作流
- 覆盖 12 种受支持语言的多语言能力

DeepInfra 是最强的主要 API 选择，它把最低的输入与缓存价格和实测最高的输出速度结合在一起。输出量大的工作负载可以考虑 CoreWeave；当自动 failover 和更高可用性最重要时，选择 OpenRouter。

该模型适合范围明确的任务，例如分类、元数据生成、[结构化 API 调用](https://deepinfra.com/blog/json-mode)、文档处理和内部助手。人工审核应当成为工作流的一部分。要求苛刻的面向客户的分析或前沿的软件工程，可能需要更大的模型。
