# 最佳 JEV 替代方案：托管 API 和开放模型 (2026)

发布于 2026.10.30，作者 Stefan Fidanov

![最佳 JEV 替代方案：托管 API 和开放模型 (2026)](https://deepinfrabldev.wpenginepowered.com/wp-content/uploads/2026/10/jev.png)

Jev 还没满月就有了竞争对手。TypeSafe 于 9 月 15 日发布了它，到 10 月的第一周，OpenAI 已宣布推出 Decisions API，Cloudflare 和 AWS 已交付开放权重的决策模型，GitHub 上则摆出了一排开源的 Jev 替代方案：Laya、OpenJev、Kev、AnyJev。我们用同一批决策任务跑了 Jev 和你今天实际能触及的那些替代方案。

Jev 的替代方案可归为三条路线：托管决策 API、自己跑的开放模型，或者让你产品已经在调用的 LLM endpoint 只从固定列表里作答。第三条路线正是 DeepInfra 的位置，大多数团队今天下午就能试。它不是最快的那条：Jev 的中位耗时是 245 ms，而 DeepInfra 上的 DeepSeek-V4.1-Flash 在同样的 96.5% 准确率下要 568 ms，跑在笔记本上的一个 2B 模型则把两者都甩在了后面。

## Jev 替代方案必须替代什么

[Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev) 是一个决策模型。你发给它一个状态（文本或 JSON）和一组有名字的问题，它发回的是数字：哪个选项合适、文本落在量表的哪个位置，或者一个是否陈述的可能性有多大。它从不写散文，因此不会返回你没给过它的选项。我们的 [TypeSafe Jev 评测](https://deepinfra.com/blog/typesafe-jev-review)在五个小任务上测试了它。

任何替代方案都得在四件事上不落下风，而 Jev 在每一件上都立了标杆：

| **你需要什么** | **Jev 1.13.0** |
| --- | --- |
| 回答类型 | choice（最多 255 个选项）、score（2 到 10 级）、noul（一个是否陈述） |
| 置信度 | 每个选项一个概率，choice 上另有一个 confidence 字段 |
| 速度 | TypeSafe 标称 70 到 500 ms；我们评测里约 280 ms p50 |
| 价格 | 每 1M 输入 token $0.042，输出免费 |

速度和价格正是 Jev 最难被击败的地方：评测里的五个任务一共用了约 11,500 个输入 token，$5 的试用余额纹丝不动。但置信度是各替代方案差异最大的地方。只有当 0.9 意味着大约十次里有九次是对的，概率才有帮助。这就是校准，下文以期望校准误差（ECE）来度量，即声称的置信度与实际准确率之间的平均差距。[AI 模型校准：没人优化的那个基准](https://deepinfra.com/blog/ai-model-calibration-benchmark)讲的正是当你代码里的某个阈值开始依赖它时，这条差距会带来什么。

## 路线一：托管的 Jev 替代方案

托管 API 保留了 Jev 最好的性质：你什么都不用自己跑。变的是你依赖的人是谁。

**OpenAI Decisions API。** OpenAI 在 [9 月 29 日的 DevDay](https://openai.com/index/devday-2026-recap/) 上宣布了它，并于 10 月 6 日开放为[公开测试版](https://developers.openai.com/api/docs/guides/decisions)。它跑在 GPT-6 Luna 上，文本和图像都能读；图像恰是 Jev 唯一读不了的输入。choice 回答按 Jev 的形状返回：每个选项一个概率，外加一个 confidence 字段。输入每 1M token $0.10，输出免费，比 Jev 的费率高出两倍还多一点。这一轮测试没有包含它。

**Cloudflare Clef 与 Clef-flash。** Cloudflare 于 [10 月 1 日](https://blog.cloudflare.com/clef-decision-models/)将两者以 Apache 2.0 开放权重发布，并托管在 [Workers AI](https://developers.cloudflare.com/workers-ai/models/clef/) 上，输入价格为每 1M token $0.24 和 $0.09。这是 Jev 价格的两到六倍，但如果托管条款不再合用，你可以把权重搬到别处，而且 Clef 能读图像和视频。Cloudflare 的发布文章称 Clef 在 BANKING77 上取得 94.2 的 macro-F1，而 Jev 是 79.7。这些是厂商自己给的数字；Clef 的托管版本同样没进我们的测试赛道。

选这两者的代价和选 Jev 一样：一家公司提供的决策专用 API，与你已经在付费的那个 LLM 分开计价。

## 路线二：自己跑的开源 Jev 替代方案

开源的 Jev 替代方案分成三个家族，而家族决定了每一个的运行成本。

**小型 encoder。** Laya 是一个 322M 到 421M、ModernBERT 级别、带决策头的模型，轻到 CPU 就能跑。它的 README 指出了 encoder 的极限在哪：对照第三方公布的 Jev 数字，它在 4 分类的 AG News 上胜出（0.950 对 0.910），却在 BANKING77 的 70 多个标签上跌到 0.425 对 0.870。

**带 pointer head 的微调 Qwen。** Strands Decider 2B、OpenJev 和 Kev 把小型 Qwen 模型的文本头换成分类头，于是一次前向传播就能返回每个选项的概率。Kev 1.0 提供 0.8B 到 27B，其 README 称在同一开发集上 Kev-27B 为 0.851，对 Jev 的 0.857。AWS 公布了 Strands Decider 2B 的权重、训练数据和方案。

**免训练的 logit 读取器。** SemIf 和 Nokia 的 AnyJev 直接读取现成开放模型在选项标签上的 next-token 概率，什么都不用训练。AnyJev 还会轮换选项顺序来抵消位置偏置，在 Qwen3-8B 上把 20 分类的 BANKING77 准确率从 0.747 提到 0.803，并把 ECE 从 0.240 压到 0.184。

| **项目** | **家族** | **规模** | **许可证** | **Jev 兼容 API** | **运行于** |
| --- | --- | --- | --- | --- | --- |
| [Laya](https://github.com/NandhaKishorM/laya) | encoder | 322M 到 421M | Apache 2.0 | 有，/v1/systemone | CPU、CUDA、Apple MPS |
| [Strands Decider 2B](https://github.com/strands-labs/strands-decider) | pointer head | 约 2B（Qwen3.5-2B） | Apache 2.0 | /v1/systemone，AWS 未对照 Jev 验证 | CUDA、Apple MPS 或 MLX、CPU |
| [OpenJev](https://github.com/alanhuangyoo/OpenJev) | pointer head | 1.7B、4B、8B | Apache 2.0，部分训练数据仅限研究 | 有，/v1/systemone | 单张消费级 GPU，或 1.7B 跑在笔记本上 |
| [Kev](https://github.com/jaredpalmer/kev) | pointer head | 0.8B 到 27B | Apache 2.0 | 有，/v1/systemone | GPU，或 Apple silicon 上的 MLX |
| [AnyJev](https://github.com/nokia-applied-research/AnyJev) | 免训练 | 任意开放模型 | Apache 2.0 | 无，Python 库 | transformers、vLLM、SGLang、llama.cpp |
| [SemIf](https://github.com/TheoLeeCJ/SemIf) | 免训练 | 任意开放模型 | MIT | 无 | CUDA、MLX、WebGPU |

六个项目里有四个讲 Jev 的 /v1/systemone 线格式，所以把评测里的 helper 换到本地模型只需要换个 URL：

```
import os, requests

def ask(state, questions, url="https://api.typesafe.ai/v1/systemone", key=None, model="jev-1.13.0"):
    headers = {"Authorization": f"Bearer {key}"} if key else {}
    r = requests.post(url, headers=headers, timeout=30,
                      json={"model": model, "state": state, "questions": questions})
    r.raise_for_status()
    return r.json()["answers"]

QUEUE = {"queue": {"type": "choice", "instructions": "Which support queue should handle this ticket?",
          "criteria": {"billing": "Charges, invoices, refunds",
                       "shipping": "Delivery status, lost or late packages",
                       "technical": "Errors, setup problems, broken features"}}}

ticket = "I was charged twice for my March invoice."
hosted = ask(ticket, QUEUE, key=os.environ["TYPESAFE_API_KEY"])
# Strands Decider 2B on the same laptop: strands-decider serve <checkpoint> --port 8000
local = ask(ticket, QUEUE, url="http://127.0.0.1:8000/v1/systemone")copy
```

AWS 的文档说 Strands 服务与 Jev API 的兼容性未经证实。而在我们的运行里，它原样接下了同一个请求——还是同一个 ask() helper，只换了 URL。

## 路线三：在 DeepInfra 上用 structured outputs 做 Jev 式决策

读到 Jev 的大多数团队已经在为某个 LLM endpoint 付费。那个 endpoint 能不能顺便把决策也做了？只要它服务的是开放模型，就能——前提是你拿走模型自由书写的能力。DeepInfra 支持兼容 OpenAI 的 [structured outputs](https://docs.deepinfra.com/chat/structured-outputs) json_schema 模式，而一个只含一个字段的 schema——该字段是你选项 id 的 enum——会让解码器只剩一件事可做：从列表里挑。没有自由文本要解析，而且你能拿到 Jev 兜售的那条同样的保证：答案永远是你给出的选项之一。

```
import json, math, os
from openai import OpenAI

client = OpenAI(api_key=os.environ["DEEPINFRA_API_TOKEN"],
                base_url="https://api.deepinfra.com/v1/openai")

def decide(state, question, options, model="Qwen/Qwen3.5-9B", priority=False):
    listing = "\n".join(f"- {k}: {v}" for k, v in options.items())
    r = client.chat.completions.create(
        model=model,
        messages=[{"role": "system", "content": "You make one decision about the text. Pick exactly one of the listed options."},
                  {"role": "user", "content": f"Text:\n{state}\n\nQuestion: {question}\n\nOptions:\n{listing}"}],
        response_format={"type": "json_schema", "json_schema": {"name": "decision", "strict": True, "schema": {
            "type": "object", "properties": {"decision": {"type": "string", "enum": list(options)}},
            "required": ["decision"], "additionalProperties": False}}},
        temperature=0, max_tokens=20, logprobs=True,
        extra_body={"reasoning_effort": "none", "chat_template_kwargs": {"enable_thinking": False}},
        **({"service_tier": "priority"} if priority else {}),
    )
    choice = json.loads(r.choices[0].message.content)["decision"]
    conf = next((math.exp(t.logprob) for t in r.choices[0].logprobs.content
                 if t.token.strip(' "') and choice.startswith(t.token.strip(' "'))), None)
    return choice, confcopy
```

几个设置承担了关键分量。temperature=0 让选择可复现。[Qwen3.5-9B](https://deepinfra.com/Qwen/Qwen3.5-9B) 是混合推理模型，所以必须把 thinking 关掉，否则你花钱推理了一大段，只换回一个词。logprobs=True 返回每个生成 token 的对数概率，而所选值的第一个 token 是这条路线里最接近置信度分数的东西。它只是所选答案的概率，不是每个选项的概率。像这样的小 schema 也是最不容易出错的，[可靠的纯 JSON 响应](https://deepinfra.com/blog/deepinfra-json-only-responses)一文有解释。

成本结构与 Jev 不同。Jev 只对输入计费。在这里，选项列表跟着 prompt 一起进去，输出是大约七个 token 的 JSON，所以一次决策大约是一个短 prompt 加几个输出 token，按模型的牌价计。目录里带 structured output 标记的模型都行，包括每 1M 输入 token $0.03 的 [gpt-oss-20b](https://deepinfra.com/openai/gpt-oss-20b) 和 $0.07 的 [Mistral Small 3.2](https://deepinfra.com/mistralai/Mistral-Small-3.2-24B-Instruct-2506)。

当任务需要每个选项的概率——就像评测里的工单路由边际所做的那样——就直接给选项打分。completions endpoint 配 echo=True 会返回每个 prompt token 的对数概率，于是你把每个选项接到 prompt 后面，读出模型觉得它有多大可能。这就是 SemIf 的方法，在 DeepInfra 的 API 上重做了一遍：

```
TMPL = "<|im_start|>user\n{u}<|im_end|>\n<|im_start|>assistant\n<think>\n\n</think>\n\n"

def option_probs(prompt, options, model="Qwen/Qwen3.5-9B"):
    base = TMPL.format(u=prompt + "\n\nAnswer with the option name only.")
    scores = {}
    for o in options:  # one call per option; run them in parallel in production
        lp = client.completions.create(model=model, prompt=base + o, max_tokens=1,
                                       temperature=0, logprobs=1, echo=True).choices[0].logprobs
        scores[o] = sum(v for off, v in zip(lp.text_offset, lp.token_logprobs)
                        if len(base) <= off < len(base) + len(o))
    z = sum(math.exp(v) for v in scores.values())
    return {o: math.exp(v) / z for o, v in scores.items()}copy
```

Echo 每个选项要一次调用，而且每次都重发 prompt，所以长状态加多选项很快就会累积起来。在下面的横向比拼里，它每次决策的成本几乎是同一模型上 enum 赛道的三倍。两种读数交回来的是不同的东西，而这个差别决定了各自能接哪些活：

## 在同一套题上测过的 Jev 替代方案

每条赛道都拿到同样的 144 个决策，来自 SemIf 那套 MIT 许可的 [authored144 数据集](https://github.com/TheoLeeCJ/SemIf/blob/master/benchmarks/data/authored144.jsonl)：三个家族的三选项选择，分别问证据是否支持某个论断、某条规则是否允许某个动作，以及哪个候选人满足某项要求。SemIf 自家的 4B 模型在这套题上报出 0.813 的平衡准确率。调用于 10 月 17 日从一台笔记本上逐条发出，所以延迟是完整的客户端往返。准确率按与标签的精确匹配计，ECE 用十个置信度分箱，每 1,000 次决策的成本来自每个响应的计费用量。

参赛赛道是：TypeSafe API 上的 Jev 1.13.0；DeepInfra 上用 enum structured outputs 的 Qwen3.5-9B 和 [DeepSeek-V4.1-Flash](https://deepinfra.com/deepseek-ai/DeepSeek-V4.1-Flash)；再次上场、走 DeepInfra priority 层级的 Qwen3.5-9B；带 echo 打分的 Qwen3.5-9B；以及在 M1 Max MacBook Pro 上经 MPS 运行的 Strands Decider 2B。DeepSeek-V4.1-Flash 入选，是因为它就是评测里用来起草回复的那个模型，即「你已经在调用的 endpoint」那种情形。

| **赛道** | **位置** | **准确率** | **ECE** | **p50 ms** | **p95 ms** | **$ / 1k** |
| --- | --- | --- | --- | --- | --- | --- |
| Jev 1.13.0 | TypeSafe API | 96.5% | 0.011 | 245 | 341 | $0.0156 |
| DeepSeek-V4.1-Flash，enum | DeepInfra | 96.5% | 0.040 | 568 | 903 | $0.0173 |
| Qwen3.5-9B，echo | DeepInfra completions | 93.8% | 0.043 | 632 | 1,218 | $0.0364 |
| Strands Decider 2B | 本地，M1 Max 经 MPS | 93.8% | 0.140 | 154 | 237 | $0（你自己的硬件） |
| Qwen3.5-9B，enum，priority | DeepInfra priority 层级 | 92.4% | 0.059 | 1,236 | 1,822 | $0.0189 |
| Qwen3.5-9B，enum | DeepInfra | 91.7% | 0.058 | 1,222 | 2,578 | $0.0126 |

Jev 和 DeepSeek-V4.1-Flash 在准确率上打平，144 题各对 139 题，而 Jev 的置信度是所有赛道里校准最好的：ECE 0.011，对 DeepSeek 的 0.040。enum 赛道的首 token 置信度比预期更靠得住。在每条 DeepInfra 赛道上，给出 0.85 及以上置信度的答案有 99% 是对的，所以只有当读数必须覆盖每个选项而不是只点名胜者时，echo 打分的那些额外调用才值回票价。但 Strands 是个异类。它在准确率上追平了 echo，却低估了自己：平均置信度只有 0.80，实际却有 94% 的时间是对的。

笔记本上的 Strands 以 154 ms 最快，因为它不用为网络跳数付费。走网络的赛道里，Jev 245 ms 作答、DeepSeek-V4.1-Flash 568 ms，而更小一些的模型 Qwen3.5-9B 无论有没有 priority 都要大约 1.2 秒。

带 enum schema 的 Qwen3.5-9B 是最便宜的托管赛道，每 1,000 次决策 $0.0126，比 Jev 低约 20%。DeepSeek-V4.1-Flash 是 $0.0173，echo 则 $0.0364——因为它每个三选项决策要发三次调用。换个说法：一百万次决策，在这里任何一条托管赛道上都是 $13 到 $36。

一个局限：表里每一行都是三选项的 choice。这套题没测 score 或 noul，也没测 70 多个标签的工单路由。

## 当速度决定一切：把本地决策器放在 DeepInfra 前面

如果有一道闸门卡在请求路径上——比如 agent 前面的 prompt 注入筛查——几百毫秒就很要命。DeepInfra 的 [priority 层级](https://deepinfra.com/blog/priority-service-tier)以 1.5 倍标准价把请求提到调度队列最前面，而在我们的运行里，它几乎没动 Qwen3.5-9B 的 p50（1,222 到 1,236 ms），只是把 p95 从 2,578 压到 1,822 ms。Priority 削的是慢尾巴，放过了典型调用，而即便削过的尾巴仍是 Jev 341 ms 的五倍多。对闸门来说，DeepInfra 上更快的杠杆是模型本身：DeepSeek-V4.1-Flash 在标准层级的 p95 是 903 ms。反过来，等得起的决策——比如每晚给所有未关闭工单重新打分——可以放到打八折的 [flex 层级](https://deepinfra.com/blog/flex-service-tier)上跑。

另一个答案是别再把所有决策都发过网络。应用服务器上的 2B 决策模型负责回答那些又短又简单的问题，它拿不准的、或超出它长度处理能力的，再交给 DeepInfra。Strands Decider 2B [默认读 4,096 个 token](https://www.eesel.ai/blog/strands-decider)，所以长状态会自动升级出去：

```
def route_ticket(ticket):
    a = ask(ticket, QUEUE, url="http://127.0.0.1:8000/v1/systemone")["queue"]
    if max(a["probabilities"].values()) >= 0.85 and len(ticket) < 8000:
        return a["choice"], "local"
    q = QUEUE["queue"]
    choice, conf = decide(ticket, q["instructions"], q["criteria"],
                          model="deepseek-ai/DeepSeek-V4.1-Flash", priority=True)
    return choice, "deepinfra"copy
```

这就是评测里那个模型路由器的私有赛道，只是方向调了个头：在那里，本地模型把敏感 prompt 挡在云端之外；在这里，它把又快又确定的决策留在网络之外，把 DeepInfra 调用花在 2B 模型更可能答错的案子上。0.85 这个阈值在比拼数据集上站得住。Strands 的 144 个答案里有 71 个达到或超过它，而这 71 个全对。剩下 73 个交给 DeepSeek-V4.1-Flash 后，总分 144 题对 139 题——正是 Jev 的数字——而一半决策从未离开过本机。这只是在三选项问题上跑的一次，所以务必用你自己的标签重新校验这条分界。agent 里同样的双模型形态见[为什么两层 agent 需要两个模型](https://deepinfra.com/blog/two-tier-agent-two-models)。

## 该选哪个 Jev 替代方案

- **选 Jev**，如果你需要托管 p95 低于 400 ms、输入是英文文本，且可以接受一个封闭 API。它在比拼里的置信度校准也是最好的，而价格与最便宜的赛道相差不到一分钱。
- **选 DeepInfra structured outputs**，如果你已经在那里调用某个开放模型。同一个 key、同一个 SDK、多一个 schema，每 1,000 次决策 $0.013 到 $0.017，而[小型开放权重模型](https://deepinfra.com/blog/small-open-weight-models-cost)能在用量增长时把这个价格持续压低。任务需要每个选项的概率时，改用 echo 打分。
- **选 Strands Decider 2B 或 OpenJev**，用于请求路径上的闸门，或不能离开机器的数据。
- **选 Laya**，如果你需要它的多语言检查点支持的 100 多种语言，或只有 CPU 的托管环境。
- **选 Kev**，如果你照着 Jev 做过原型，想在自家的 GPU 或 Mac 上用同一种线格式。
- **选 AnyJev 或 SemIf**，如果你已经在 vLLM 或 llama.cpp 上自托管某个开放模型，想不训练任何东西就拿到每个选项的概率。
- **选 Workers AI 上的 Clef 或 OpenAI Decisions API**，如果你的决策依赖图像。能读视频的只有 Clef。

## FAQ

### 有免费的 Jev 替代方案吗？

有。上面六个开放项目都免费，许可是 Apache 2.0 或 MIT，而 Strands Decider 2B、Laya 和 OpenJev 的 1.7B 模型都能在笔记本上跑。你付的是硬件而不是 token 的钱——不过 Jev 在小用量下本来也几乎免费。

### 我能用普通 LLM 代替 Jev 吗？

能，只要你约束它的输出。enum schema 能让任何受支持的开放模型从固定列表里挑，logprobs 则给出所选答案的置信度。只是延迟会比专用决策模型高（我们测得 DeepSeek-V4.1-Flash 为 568 ms，对 Jev 的 245 ms），而且在混合推理模型上要把 thinking 关掉。

### OpenAI 的 Decisions API 返回概率吗？

会。OpenAI 的 [Decisions 指南](https://developers.openai.com/api/docs/guides/decisions)说 choice 回答为每个选项携带一个概率，外加一个独立的 confidence 字段。我们还没实测过这些概率的校准程度，所以在你的代码里的阈值开始依赖它们之前，先对照你自己标注过的样例核一核。

### Jev 替代方案能只在 CPU 上跑吗？

能，但慢。在[公开测试](https://www.eesel.ai/blog/strands-decider)中，Strands Decider 2B 用 CPU 在八线程 Xeon 上跑，一个短输入大约 1.6 秒；约 3,000 token 时要 16 到 18 秒。这适合批处理任务，不适合用户在线等待的闸门。
