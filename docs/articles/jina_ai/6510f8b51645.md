# 从多模态 LLM 引导出音频 embedding

把任意多模态 LLM 变成一个小型音频 embedding 模型，用少 25 倍的数据就能超过 CLAP。

Han Xiao · 7 分钟阅读

jina-ai/audio-embedding-kickstarter

Google 最近发布了 [Gemini Embedding 2](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-embedding-2)，这是他们第一个原生多模态 embedding 模型。文本、图像、视频、音频、文档，全部映射到同一个 3072 维的向量空间。这是更广泛的 **omni embedding 模型**趋势的一部分：用单一架构处理所有模态的统一模型，从 [jina-embeddings-v4](https://arxiv.org/abs/2506.18902) 到 [Omni-Embed-Nemotron](https://arxiv.org/abs/2501.05052) 再到 [Omni-5](https://arxiv.org/abs/2505.14659)。

在去年的 EMNLP BoF 会议上，我把 omni 模型列为 2026 年稠密检索（dense retrieval）的关键方向之一。

引起我们注意的是音频。大多数人听到"多模态 embedding"首先想到图像，也许还有视频。音频是被遗忘的模态：更难采集、更难标注、做的人也更少。在 Jina AI，我们恰好研究过这个问题，作为通往 omni embeddings 工作的一部分，构建了小型（参数小于 1.2B）音频 embedding 模型。Gemini Embedding 2 的发布，正是分享我们一路所学的好时机。

## 音频 embedding

音频 embedding 是一段音频的定长向量表示。给定一条原始波形，模型输出一个稠密向量（通常 768 到 3072 维），用来捕捉声音的语义内容。两段语义相近的音频会产生相近的 embedding，一段音频在共享 embedding 空间中会与它的文字描述彼此靠近。这是 omni embedding 拼图中的一块：一旦你能把音频连同文本、图像嵌入到同一个向量空间，就解锁了跨所有模态的跨模态检索。

自 2022 年以来的主流方法是 [Contrastive Language-Audio Pretraining (CLAP)](https://arxiv.org/abs/2206.04769)，把 [CLIP](https://arxiv.org/abs/2103.00020) 扩展到音频。[LAION-CLAP](https://arxiv.org/abs/2211.06687) 用 63 万对数据和特征融合将这一方法规模化。最强的变体（[Elizalde et al., 2023](https://arxiv.org/abs/2309.05767)）在 460 万对数据上训练，使用一个覆盖 22 种不同音频任务的音频编码器，并搭配一个自回归解码器，在 250M 参数下于 AudioCaps 上取得 42.0 的 cvR@5。

我们走的是另一条路：把已经能理解音频的多模态 LLM 变成 embedding 模型。

## 架构

先说输入和输出分别是什么。输入是原始音频：从任意标准格式（WAV、MP3、FLAC）解码出的波形，并重采样为 16kHz 单声道。音频编码器把这条波形转换成 128 个 bin 的 log-mel 频谱图，再处理成一串特征 token，速率约为每秒 150 个 token。一段 10 秒的音频会变成大约 1500 个 token。最大输入长度是 30 秒，更长的音频需要分块。输出是单个稠密向量（即 embedding），通常 896 到 3584 维，取决于 LLM 主干的规模。

我们从 [Qwen2.5-Omni](https://arxiv.org/abs/2503.15394) 出发，这是一个具备原生音频理解能力的多模态 LLM。它有三个组件：一个音频编码器（约 0.6-0.8B 参数），通过一个约 4.5M 的线性投影把波形转成特征向量；一个 LLM 主干（0.5-7B 参数），同时处理音频特征和文本 token，每个 transformer 层增加约 0.2B 参数；一个池化层，把最后的隐藏状态做均值池化成单个 embedding 向量。两种模态共享同一个 LLM 主干，所以从预训练起它们就已经大致对齐。

左：标准做法，端到端微调整个 MLLM（3-7B 参数）。右：模块组合，把一个预训练音频编码器与一个更小的 LLM 主干配对。共享的主干同时处理音频特征和文本 token，在同一个向量空间中产出 embedding。

训练目标是 InfoNCE 对比损失。每种模态独立编码，损失在两个方向上分别计算后取平均：

```
def training_step(audio_batch, text_batch):
    audio_embeds = model.encode_audio(audio_batch)  # [B, D]
    text_embeds = model.encode_text(text_batch)      # [B, D]
    
    audio_embeds = F.normalize(audio_embeds, dim=-1)
    text_embeds = F.normalize(text_embeds, dim=-1)
    
    sim = audio_embeds @ text_embeds.T / temperature  # [B, B]
    labels = torch.arange(len(sim), device=sim.device)
    loss = (F.cross_entropy(sim, labels) + 
            F.cross_entropy(sim.T, labels)) / 2
    return loss
```

## 训练数据

五个音频-文本配对数据集，共 181K 个样本：

| 数据集 | 样本数 | 说明 |
| --- | --- | --- |
| [AudioSetStrong](https://huggingface.co/datasets/cvssp/WavCaps) | 108K | 带时间标注的事件，GPT 生成的描述（AudioSet 子集） |
| [FSD50K](https://zenodo.org/record/4060432) | 41K | 人工标注的声音事件，200 类 |
| [Clotho](https://zenodo.org/record/3490684) | 19K | 音频描述生成，详尽的描述 |
| [UrbanSound8K](https://github.com/LAION-AI/audio-dataset) | 9K | 城市声音分类 |
| [MACS](https://huggingface.co/datasets/milesway6/MACS) | 4K | 城市声学场景 |

CLAP 用了完整的 AudioSet（2M+ 音频）加上其他来源，合计 4.6M 对数据。我们只用了 AudioSetStrong（约 100K）。从一个预训练的 MLLM 出发，能大幅减少所需的数据量。

```
def load_sample(audio_path, caption):
    waveform, sr = torchaudio.load(audio_path)
    waveform = torchaudio.transforms.Resample(sr, 16000)(waveform)
    audio_inputs = processor.feature_extractor(
        waveform, sampling_rate=16000, return_tensors="pt"
    )
    text_inputs = processor.tokenizer(caption, padding=True, return_tensors="pt")
    return audio_inputs, text_inputs
```

## 四种方法

目标：一个参数低于 1.2B、且能超过 CLAP 的音频 embedding 模型。

**完整模型微调。** 在音频-文本配对上微调 Qwen2.5-Omni-7B：AudioCaps T2A cvR@5 = 63.2，Clotho T2A = 39.2。这是性能上界，但 7B 无法部署。[Tevatron 2.0](https://arxiv.org/abs/2505.02466) 类似地只在 AudioCaps 上微调（61.2，但在 Clotho 上只有 11.9，说明单数据集训练的泛化能力很差）。[ColQwen-Omni](https://arxiv.org/abs/2509.07538) 在视觉文档任务上微调、完全不使用音频数据，通过跨模态迁移达到了 37.4。

**层剪枝。** 从 7B 模型中移除 transformer 层。每层约 0.2B，所以 10 层的模型总计约 3.5B。

随 transformer 层被移除，性能与模型规模的关系。AudioCaps（红色）从 20 层到 5 层时，cvR@5 从 63.2 降到 56.0。所有配置仍超过 CLAP 基线（虚线）。即使到 5 层（2.3B 参数），模型也无法达到 1B 的目标。

| 层数 | 参数 | AudioCaps T2A cvR@5 | Clotho T2A cvR@5 |
| --- | --- | --- | --- |
| 20 | 5.8B | 63.2 | 39.2 |
| 10 | 3.5B | 58.2 | 36.5 |
| 5 | 2.3B | 56.0 | 36.0 |

batch size（32、64、128）没有带来有意义的差别。更大的 batch 起初有帮助，但后面可能反而下降：在 Clotho 上，batch 128 在 2K 步时达到 31.3 NDCG，却在 10K 步时掉到 29.3。

**纯文本模态迁移。** 只在文本配对上微调（MultiNLI、SNLI、FEVER、SciFact），依赖预训练带来的跨模态对齐。在完整的 7B 上有效（AudioCaps 46.1，超过 CLAP 的 42.0），但在剪枝后的 10 层模型上彻底失败（cvR@5 = 5.9）。跨模态的连接分布在整个网络中，无法在剪枝后保留下来。

**模块组合。** 这是突破口：从一个模型取音频编码器，从另一个模型取小 LLM，甚至可以跨模型家族。Qwen2.5-Omni 分三个阶段训练：（1）冻结 LLM、只训练音频/视觉编码器；（2）全部参数解冻；（3）32K 上下文。我们把来自不同阶段的模块组合起来：

| 配置 | 音频编码器 | LLM | 参数 |
| --- | --- | --- | --- |
| M1 | Qwen3-Omni（0.6B，阶段 1 之前） | Qwen2.5-0.5B | 1.1B |
| M2 | Qwen3-Omni（0.6B，阶段 1 之前） | Qwen2.5-3B | 3.6B |
| M3 | Qwen2.5-Omni-3B（0.8B，阶段 3 之后） | Qwen2.5-3B | 3.8B |
| M4 | Qwen2.5-Omni-3B（完整） | 完整 3B | 3.8B |

实现细节：Qwen3-Omni 使用的是 `Qwen3OmniMoePreTrainedModel`，而独立的 Qwen3 用的是 `Qwen3ForCausalLM`。我们先初始化一个维度匹配的 Omni 模型外壳，再把权重复制到对应位置。

各配置在 AudioCaps 和 Clotho 上的 T2A cvR@5。M1 在 1.1B 参数下，AudioCaps 达到 49.7，比 CLAP（42.0）高 18%。使用来自阶段 3 之后训练、对齐更好的音频编码器能提升结果（M3 相比 M2：AudioCaps +4.2）。LLM 预训练的第 2、3 阶段对 embedding 质量并不关键（M3 与 M4 的差异在噪声范围内）。

## 评估

评估音频 embedding 本质上是评估检索质量：给定一条文本查询，模型能否找到正确的那段音频？关键难点在于"正确"取决于数据集。AudioCaps 的描述具体（"一个男人说话，随后门关上了"），而 Clotho 的描述抽象（"一种安静的氛围，远处有隆隆声"）。一个只会记住表面音频特征的模型在 AudioCaps 上表现好，在 Clotho 上却很吃力。我们最看重的，是跨描述风格的泛化能力。

CV-Recall@5（cvR@5）：对每条文本查询，检查正确的那段音频是否出现在 top-5 结果中。对所有查询取二值分数的平均。这是 [MTEB](https://github.com/embeddings-benchmark/mteb) 音频检索中的标准指标。

```
def evaluate_cvr_at_k(model, dataset, k=5):
    audio_embeds = model.encode_audio(dataset.audio_clips)
    text_embeds = model.encode_text(dataset.text_queries)
    sim = F.normalize(audio_embeds) @ F.normalize(text_embeds).T
    
    hits = 0
    for i in range(len(dataset.text_queries)):
        top_k = sim[:, i].argsort(descending=True)[:k]
        if dataset.ground_truth[i] in top_k:
            hits += 1
    return hits / len(dataset.text_queries)
```

来自 MTEB 的三个评估数据集：AudioCaps（源自视频、人工描述）、AudioSetStrong（带时间标注、GPT 描述）、Clotho（多样、抽象描述）。CLAP 用了完整的 AudioSet（2M+），而我们用的是 AudioSetStrong（约 100K），这部分解释了 CLAP 在该基准上的优势。

横向条形图，比较所有模型配置在 AudioCaps、AudioSetStrong 和 Clotho 上的 T2A 检索表现。红色虚线标出 CLAP 基线。模块组合模型（绿色）以小得多的规模取得了很强的结果。完整微调的 7B 模型（深蓝）设定了上界。

## 应用

音频 embedding 正在传统检索之外的领域变得重要。在 agent 系统中，音频 embedding 能实现意图路由：一个收到语音输入的 agent，可以对音频做 embedding，并基于语义相似度把它路由到合适的工具或子 agent，而不必等待完整转写。声音事件分类支撑着工业场景、智能家居自动化和安防系统中的实时监控。在多模态 agent 工作流中，音频 embedding 让 agent 像处理文本和图像一样，对音频内容进行检索、比较和推理。音乐与媒体应用则用它来做相似度检索、版权检测和内容推荐。当语音界面成为 AI agent 的默认交互方式，能在设备端运行的紧凑音频 embedding 对低延迟、保护隐私的应用就变得至关重要。

## 结论

从预训练的 MLLM 出发，是最大的单一杠杆。它一次性提供了跨模态对齐、强大的文本编码器和够用的音频编码器。模块组合是最有前景的方向：把来自不同模型、不同训练阶段的音频编码器和 LLM 混搭，打开了一个几乎无人探索的设计空间。我们的模型在 AudioCaps 上占优，但在 Clotho 上只能追平 CLAP——Clotho 的抽象描述暴露了 AudioCaps 掩盖不住的弱点。跨模态迁移无法在模型压缩后存活下来。

这项工作是通往 omni embedding 模型的一步：一个把文本、图像、音频、视频和文档嵌入到统一检索空间的模型。模块组合方法表明，通过复用预训练组件就能高效地引导出新模态。下一步包括：激活参数小于 500M 的 MoE 架构、把模块组合与模态迁移结合，以及用 WavCaps、MusicCaps 和语音数据集来扩充数据。
