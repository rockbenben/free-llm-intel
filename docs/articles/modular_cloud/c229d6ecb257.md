# KVCache 的五个时代

## 引言

**Key–Value Cache（KV cache/KVCache）**是现代 LLM 服务系统的基础构件。它保存过去的注意力状态，让模型能高效生成新 token，而无需大量重复计算。

LLM 推理分两个阶段：**Prefill（预填充）**与 **Decode（解码）**。在 Prefill 阶段，为输入 prompt 中的每个 token 计算注意力状态；随后的 Decode 阶段，通过对既往 token 关联的 Key-Value 做注意力，以自回归方式逐个生成新 token。

https://www.nature.com/articles/s41586-023-06647-8

vLLM、SGLang、TensorRT-LLM 和 MAX Serve 都构建在日益精密的 KV cache 管理之上。本博客探讨 KV cache 在这些推理引擎中的演进与角色。

## 时代 0：GenAI 之前（<2017）

在 transformer 接管一切之前，深度学习由*无状态的前馈*架构主导，如 ResNet、YOLO、VGG、Inception。这些模型不需要跨推理步骤保持持久状态，所以 KVCache 的概念根本不存在——即便在 ONNX 或 TensorRT 这样的推理框架里也没有。

## 时代 1：连续 KV Cache（2017）

最初的 [transformer（2017）](https://arxiv.org/pdf/1706.03762)奠定了日后统治 ML 的架构。这一设计背离了此前的模型，需要一个 KVCache 来高效跟踪每个请求的状态。尽管如此，transformer 带来的智能跃升远远超过了其附加复杂度。

当时，早期 LLM 服务引擎朴素地实现 KV cache：

- 对每个请求，预分配一个容纳 `max_seq_len` 个 token 的连续 KV 张量。
- 存储量为每请求 `2 x num_layers × num_heads × head_dim × max_seq_len`。

这种连续 KV cache 设计极其浪费，但相比为每个 token 重新计算注意力键值仍有巨大的性能收益：

- ✔ 简单
- ✘ 内存用量因 `max_seq_len × batch_size` 因子而激进膨胀
- ✘ 受内存容量限制，`max_batch_size` 受限
- ✘ 变长请求导致高内存碎片
- ✘ 多数请求远短于 `max_seq_len`，留下大量浪费的容量

HuggingFace Transformers 等早期推理引擎就采用这一方案。

## 时代 2：PagedAttention（2023）

突破随 **vLLM** 引入的 [PagedAttention](https://arxiv.org/abs/2309.06180) 到来。核心思想是借鉴[操作系统的技术](https://en.wikipedia.org/wiki/Page_table)：把 KV 分配在固定大小的页中，随序列增长动态分配。

**收益：**

- ✔ 大幅改善内存利用率、减少碎片
- ✔ 支持数百/数千并发请求
- ✔ 用更大 batch 推高吞吐
- ✔ 通过 [Prefix Caching](https://arxiv.org/pdf/2312.07104) 实现高效 KV cache 复用——对多轮聊天负载是巨大的吞吐倍增器

PagedAttention 成为 LLM 服务的事实标准，催生了 TensorRT-LLM、SGLang 等新推理引擎。

## 时代 3：异构 KV Caches（2024）

ML 世界与 LLM 服务版图如今复杂得多。新优化加上现代多模态与混合模型，要求*多种不同类别的状态*，每种都有各自不同的缓存需求。在这个时代，“KV Cache”一词已被远远拉伸超出其本义。

- **投机解码（Speculative decoding）**：由小的草稿模型先行生成多个 token，再由大的目标模型在一次前向中验证并接受，从而加速 LLM 推理。用这种技术，草稿模型与目标模型需要各自维护独立的 KV cache。
- [**Vision encoders**](https://github.com/vllm-project/vllm/pull/9871)：视觉-语言模型（VLM）中的视觉编码器生成的大图像 embedding 可缓存并跨请求复用。虽然这与“KV cache”或 prefix caching 的传统概念不同，但遵循同样的原理——为昂贵的中间状态做 memoization。受益于此缓存的模型包括 QwenVL 与 InternVL。
- **量化 KV Cache**：FP8 等低精度数据类型有助于降低 KV cache 的存储需求，依赖逐 tensor/行/块的缩放因子保持数值范围。这要求 KV cache 实现同时管理这些缩放因子的内存。
- **滑动窗口注意力（SWA）**：限制每个 token 只关注前 `window_size` 个 token 而非整个序列，减少内存与计算。于是 KV cache 管理与 prefix caching 必须追踪哪些 token 落在当前窗口内，缓存命中与驱逐变得比全注意力更复杂。![Fig 11. https://arxiv.org/pdf/2503.18292](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6984ecaaa581b58f7daac003_image.png)Fig 11. [https://arxiv.org/pdf/2503.18292](https://arxiv.org/pdf/2503.18292)
- [**Mamba / 状态空间模型**](https://arxiv.org/pdf/2312.00752)用循环状态取代注意力，每来一个新 token 更新一个大的状态向量。这让 prefix caching 更复杂：服务系统必须决定何时、如何对演化的状态向量做 checkpoint 或存储以供未来复用。
- **复合模型（Composite Models）**由多个子模型组成。例如把 LLM 主干与音频解码器组合是常见模式。每个子模型可能需要维护独立的 KV caches。
- **混合模型（Hybrid Models）**在单一模型内组合多种层类型，常常需要维护多个 KV cache 以处理各层不同的注意力或状态机制。例子包括：Sliding Window Attention + Full Attention（Gemma2/3、Ministral、GPT-OSS、Cohere）；Mamba + Full Attention（Jamba、Bamba、Minimax）；Local Chunked + Full Attention（Llama4）。![Fig 1. https://arxiv.org/pdf/2503.18292](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6984ecaae42b0afd0dea3c60_image.png)Fig 1. KV cache 在形状、生命周期与属性上的这种异构与多样性，促使现代 LLM 服务引擎创建专门的管理器。例如 vLLM 除常规 KV cache 外还有 [Vision Encoding Cache](https://github.com/vllm-project/vllm/pull/9871)、[Mamba Cache](https://github.com/ZZBoom/vllm/blob/c7d93c1a9605767733d9e091d98e4ee5df747565/vllm/model_executor/models/mamba_cache.py) 等。

这一设计也带来若干**挑战**：

- ✘ 多个 KV cache 管理器造成的内存碎片可能导致小 batch
- ✘ 服务器启动时难以预测每种 KV cache 该分配多少内存
- ✘ 互不相通的 Prefix Caching 实现导致次优的命中率
- ✘ 多样性让特性组合变得困难

## 时代 4：分布式 KV Cache（2025+）

随着 LLM 变大、负载增加，单 GPU 或单节点不再够用。LLM 服务与 KV cache 正在走向多节点、分布式，常常横跨整个数据中心。管理如此大规模的 KV cache 需要新技术：

- [**分离式推理（Disaggregated Inference）**](https://arxiv.org/pdf/2401.09670)：把 LLM 推理拆分为 **Prefill** 与 **Decode** 两阶段，部署并缩放在不同的模型实例上，减少干扰、优化资源使用。关键挑战是高效地把 KV cache 从 Prefill 节点传输到 Decode 节点。近期出现了新的分离变体，如 [Encoder Disaggregation](https://blog.vllm.ai/2025-12-15/vllm-epd.html)。
- [KV Cache 感知的负载均衡](https://docs.nvidia.com/dynamo/archive/0.4.0/architecture/kv_cache_routing.html)：请求路由优先选择已持有相关 KV cache 的实例，最大化 **prefix cache 命中**。这需要集群全域视角下各实例 KV cache 的当前状态。
- [**分层 KVCache**](https://arxiv.org/pdf/2407.00079v1)：为扩大 KV cache 容量，可把**冷页**从 GPU 内存溢出到更充裕的 CPU RAM 或 SSD。这在保持热页常驻 GPU 低延迟访问的同时扩大了有效 KV cache 尺寸。从更低缓存层加载/存储某一层模型 KV cache 的较高延迟，可以与其上一层的 GPU 执行重叠来隐藏。

许多 Kubernetes 原生的新推理方案应运而生以驯服这种复杂性：Nvidia Dynamo、vLLM Production Stack、llm-d、AIBrix。然而分布式 LLM 推理依然非常难：

- ✘ 许多现有优化或架构仍与分布式推理不兼容，如投机解码或 VLM
- ✘ 尽管开源方案广泛可得，部署仍需专家知识与大量耐心
- ✘ 跨节点 GPU 组网（Infiniband 或 RoCE）充满挑战，[NIXL](https://github.com/ai-dynamo/nixl) 等库尚处早期
- ✘ 大规模分布式系统存在诸多固有难题：failover 管理、掉队者（stragglers）、硬件缺陷、自动扩缩等

## 时代 5：统一混合 KV Caches（2025+）

下一个阶段是构建**统一 KV 内存系统**：*多种异构 KV 类型共享同一个内存池*，而非彼此隔离的分配器。这个时代另一个贯穿主题是追求**所有可用优化之间的可组合性**。

这一演化正在发生！

**新兴方案：**

- [vLLM / Jenga – Huge Pages + LCM Sizing](https://arxiv.org/pdf/2503.18292)：使用**大页（huge pages）**，页大小取较小页格式的**最小公倍数**，让不同 KV 形状高效共存。统一的 Prefix Caching 设计同时考虑多种 KV cache，改善均衡与命中率。

# 结论

从一项简单优化——缓存注意力状态避免重复计算——起步，KV cache 已演化为现代 AI 基础设施中最复杂的子系统之一。每个时代都带来新挑战：内存碎片、异构模型架构、分布式协调，以及如今对跨所有维度干净组合的统一系统的需求。随着新模型、新优化与新硬件涌现，KV cache 管理需要在 LLM 推理栈的所有层——从 GPU kernels 到集群调度——持续创新。
