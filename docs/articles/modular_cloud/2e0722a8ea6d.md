# 为什么 LLM 推理需要一种新型路由器——第 2 部分

Aayush Deshpande

Deep Dhillon

Alexandr Nikitin

Michael Dunn-OConnor

工程

在 [第 1 部分](https://www.modular.com/blog/why-llm-inference-needs-a-new-kind-of-router-part-1)，我们论证了 LLM 路由与 HTTP 路由有质的不同：推理后端持有传统负载均衡器会忽略的状态。本文讲我们识别出的三层里的第一层——数据层，它让那份状态在每一次推理请求的热路径上可被查询。

要把一个请求路由到缓存前缀最优的那个 pod，你需要知道哪些 block 缓存在哪些 pod 上。听起来简单，直到你看那些数字。你可能有上百个 pod，每个都有上千个缓存 block。状态每秒可能变化上百次。在这般复杂之下，查询必须在微秒内返回，因为它们位于每条推理请求的关键路径上。

一个哈希表加一把互斥锁，不足以应付推理路由这种规模和速率。你需要一个专为这种访问模式设计的数据结构：一种能提供快速并发读、批量写、幂等事件处理和高效查询响应的办法。

本文一步步讲我们如何构建那个数据结构。

## 问题

给定一个被 tokenize 成 N 个 block 哈希（查询链）的请求，以及集群里 P 个存活 pod，返回一个按"每个 pod 缓存了这 N 个 block 中的多少个"排序的 pod 排名清单。

约束是：

- 微秒级查询延迟。这跑在热路径上，每条推理请求都经过它。
- 与进行中的更新并发。Pod 在不断地缓存和驱逐 block。查询和更新同时发生。
- 对 pod 更迭有韧性。Pod 随部署扩缩或重启而被增删。索引需要反映当前的存活集合，而不让陈旧条目随时间累积。
- 精确到足以路由正确。不必完美一致（一些陈旧无所谓），但要精确到我们所选的 pod 真的拥有我们预期的那份缓存。

一个具体例子：假设有 64 个 pod、每次查询 32 个 block、每秒 1,000 个请求。一个朴素做法（对每个 block，对每个 pod，检查该 pod 是否缓存了它）是每请求 32 × 64 = 2,048 次查找。合计下来就是每秒两百多万。撇开锁竞争不谈，这个做法满足不了微秒延迟约束。我们需要别的东西。

## 状态从哪来

数据层不产生缓存状态，它消费状态。

LLM 引擎在缓存内容变化时发出 block 级事件：

- **Registered（已注册）：** 某个 block 已在某个 pod 上某块特定内存层里被缓存。
- **Evicted（已驱逐）：** 某个 block 已从某个 pod 上某一层里被移除。
- **Shutdown（关停）：** 某个 pod 要离开了。

这些事件如何抵达路由层，取决于部署。有些环境用 NATS（带 JetStream）这样的发布/订阅结构。另一些用从每个引擎实例到路由器的直接 gRPC 流。未来的部署可能用 Kafka、Redis Streams，或完全不同的东西。

数据层的职责是对传输方式保持无感。新增一个事件源，意味着实现一个消费者接口。索引器看到的是一串带类型的事件，它不知道也不关心它们来自什么消息基础设施。

从这个设计引出两条要求。

**幂等操作。** 同一个事件可能到达两次。在消费者重启时重放上一个小时的 block 事件是常态。注册一个已被索引的 block 是空操作。驱逐一个已经不在的 block 是空操作。关停一个已经死掉的 pod 是空操作。这些是有效状态，不是错误情形。

**多消费者安全。** 两个消费者（例如 NATS 和 gRPC）可能同时向同一个索引器供数据。它们不该冲突。这由幂等性保证：如果两个消费者都看到"pod A 注册了 block X"、都写它，结果和一个消费者写一次是一样的。

## 存储：HostBitmap

索引要回答的核心问题是：哪些 pod 有这个 block？

朴素的表示是每个 block 存一个 pod 标识符切片：`blockHash → [podA, podC, podF]`。它能用，却在规模上以不断累积的方式浪费。每个 pod 标识符是一个字符串指针。每个切片有自己的底层数组和头。数百万个小堆分配给 Go 的垃圾回收器施加持续压力。而检查"pod X 有 block Y 吗"意味着对切片做一次线性扫描。

这个问题是在一个有界 pod 群体上的集合归属测试，而它最高效的表示是位图（bitmap）。

位图给每个 pod 分配一个索引（0、1、……、P−1），并把"拥有此 block 的 pod 集合"表示成一个定宽位向量。每个 pod 一位。集合操作（并、交、补）变成位运算。归属是一次单比特测试。population count（数 1 的个数）在 x86-64 上编译成一条 `POPCNT` 指令。

我们把 pod 数封顶在 256，作为部署级设计选择。256 比我们在生产环境里见过的任何单编排器部署都大，而且将来可以放宽而不需重新设计。在 256 个 pod 时，位图是 256 位 = 32 字节 = 四个 `uint64` 字。`HostBitmap` 类型就是四个平铺的 `uint64`。我们按编排器实例封顶 pod 数。这天然契合一种 [cell 式部署架构](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/what-is-a-cell-based-architecture.html)，其中每个路由实例拥有一个自包含的 pod cell，横向扩展靠多跑 cell、而非把某一个加宽。这个上限比我们在生产环境里见过的任何单 cell 部署都大，将来可以放宽而无需重新设计数据结构。HostBitmap 是一个定长的 `uint64` 字平铺数组，按上限取尺寸，没有指针、堆分配或间接寻址。

整个索引是 `map[blockHash] → HostBitmap`。对集群在任何地方缓存过的每个 block，这个 map 存着哪些 pod 有它。

## 并发：给索引分片

单个 `map[blockHash] → HostBitmap` 在没有并发写走锁之前是能用的。可一旦有，每次更新（每条 Registered 或 Evicted 事件）都会和其他每次更新、以及每次读串行化。在每秒数百事件、跨数千 block 下，锁成了瓶颈。

解法是分片。我们把索引拆成 256 个独立的 map，每个有自己的锁。一个 block 的分片，由对 block 哈希取哈希、再取高位来决定。我们选 256，是因为它在我们的目标吞吐下让每分片竞争可忽略不计，同时把内存开销保持得极小。对不同分片的写并行进行，读也是。对同一分片的读写仍会竞争，但只争一次 map 操作，而非一次完整扫描。

### 用于分片分布的斐波那契哈希

来自累积哈希的 block 哈希并非均匀随机。它们带着反映输入 token 分布的结构。直接用哈希低位选分片，会把相关的 block 聚进同一分片，把 256 路并行又变回少数几个热点分片。

在从高位提取分片索引之前，我们先把 block 哈希过一个以黄金比常数为乘数的乘性哈希（64 位下是 `0x9E3779B97F4A7C15`），这项技术叫斐波那契哈希。黄金比乘数是 2^64 除以 φ（黄金比，约 1.618）。即便连续的输入，也会在输出范围内以相邻像之间的最大间距散开——一个由三距离定理推出的结果。

### 缓存行填充

每个分片结构都被填充，好让它从各自 64 字节缓存行边界开始。没有填充时，两个相邻分片可能共享一条缓存行。对其中一个的写，会让每条缓存了另一个的 CPU 核上的那一行失效。这就是伪共享（false sharing），它会悄然杀死那些看似便于并行化负载上的并发。填充总共花约 16 KB（256 个分片 × 64 字节），彻底消除了这个问题。

有了 256 个分片和斐波那契分布，任一 block 落进某个特定分片的概率是 1/256。在 1,000 QPS（每秒查询）、每查询 32 个 block 下，每个分片大约看到 125 次查找和每秒寥寥几次写。竞争被有效地降到最小。

## 查询：用二分搜索做前缀匹配

存储能以常数时间回答"pod X 有 block Y 吗"。路由需要回答一个更难的问题：对一条 N 个 block 的查询链，每个 pod 各有其中多少个？

朴素做法是那个 N × P 循环。对查询链里的 N 个 block 每一个，在其分片里查位图，再检查 P 个 pod 每一个。在 64 个 pod、32 个 block 下，就是每请求 2,048 次分片查找。在 1,000 QPS 下这将需要每秒两百多万次查找，从而不可能满足微秒查询延迟目标。

累积 block 哈希就是解法。我们系统里的 block 哈希并非独立。每个 block 的哈希是它自己的 token 和上一个 block 哈希的函数。block 4 的哈希纳入了从 block 0 到 3 的一切。

后果是：如果一个 pod 以某个特定哈希缓存了 block 5，那它必然以完全相同的一条哈希链计算过 block 0 到 4。缓存命中形成一个连续前缀。不存在"我有 block 5 但没有 block 3"。若 block-5 哈希匹配，到 block 4 为止的前缀也匹配了。

这把查询从一次 N × P 扫描，变成对下降点的一次二分搜索：使每个 pod 都缓存了查询链前 K 个 block 的最大 K。因为前缀连续，二分搜索适用。

### 演算示例

这里有一个用四个 pod、八个 block 做二分搜索前缀匹配的示例。

markdown

```
Query chain: [H0, H1, H2, H3, H4, H5, H6, H7]

Pod A has cached: H0–H5    (prefix depth 6)
Pod B has cached: H0–H3    (prefix depth 4)
Pod C has cached: H0–H7    (prefix depth 8, full chain)
Pod D has cached: H0–H1    (prefix depth 2)
```

**第 1 步。** 检查 block H3（中点）。查 H3 的分片，把位图与存活-pod 位图求交。

结果：{A, B, C}。Pod D 在 H3 之前就断了。

**第 2 步。** 对幸存者 {A, B, C}，检查 H5（上半部分的中点）。

结果：{A, C}。Pod B 在 H3 和 H5 之间断了。

**第 3 步。** 检查 H6。

结果：{C}。Pod A 在 H5 和 H6 之间断了。

**第 4 步。** 检查 H7。

结果：{C}。Pod C 有完整的一条链。

对断了的那些 pod（A、B、D），我们用二分搜索找它们精确的断点深度。这个示例里总分片查找：大约 10 次。朴素的 P × N 扫描会要 32 次。

### 时间复杂度

复杂度是 O(K × log N)，其中 K 是幸存 pod 集里不同断点深度的个数。如果所有 pod 有相同的前缀深度，K = 1，搜索在 log N 次查找内完成。如果每个 pod 深度都不同，K = P。

实践中，同一部署里的 pod 往往有相似的缓存状态（它们都处理过来自同一分布的先前请求），所以 K 很小。

二分搜索的开销随 log N 和 K 伸缩，两者都不大。它不随 P 伸缩。pod 数翻倍不改变分片查找的次数。它改变的是位图上的 population count，而那是每字一次常数时间操作。

## 正确性：链式与可用性是两码事

这一数据层里两个不同的问题都涉及哈希，值得把各自解决什么讲精确。

累积链式解决一个正确性问题。两个不同的请求可能恰好在 block 3 上共享相同 token，却在序列更早处不同。如果 block 仅由自身 token 的局部哈希标识，那些请求会产出同样的 H3，而路由器会把它们的 block-3 KV 缓存条目当作可互换。它们并不是：注意力值取决于完整上下文，而非仅局部 token。在不匹配的前缀之间共享缓存会产出不正确的模型输出。

累积链式确保每个 block 哈希编码到那一点为止的完整 token 序列，而非只是那个 block 里的 token。两个恰好在 block 3 共享相同 token、却在更早处不同的请求，会产出不同的 H3。KV 缓存条目是不同的，所以路由器把它们当作不同——而模型看到正确的上下文。

位图查找解决一个可用性问题。给定一条正确的哈希链，那些哈希里此刻究竟有哪些真的存在于哪些 pod 上？Block 会被驱逐。Pod 会崩溃。哈希链描述的是一个 pod 的缓存需要含什么才能服务一个请求；位图记录的是它实际含什么。路由两者都要：用链式来问对问题，用位图来针对实时集群状态准确回答它。

## 分层存储：block 住在哪

当部署加入 CPU 内存和 SSD 卸载层（见我们 [KV 缓存的五个时代](https://www.modular.com/blog/the-five-eras-of-kvcache) 一文），问题就从"这个 pod 有这个 block 吗"扩展成"它住在这个 pod 上的哪里"。GPU 内存严格快于 CPU 内存，CPU 内存严格快于 SSD。路由器应优先选那些把 block 放在最快可访问层的 pod。

诱人的做法是把 HostBitmap 扩展成按层的：每个 block 三个位图而非一个。它能用，但会让热路径膨胀。多数路由决策并不需要按层信息，它们只要"谁有这个 block"。在每次查询上都付这笔额外开销是浪费。

取而代之，我们把索引拆成两层。

**路由分片。** 上面描述的那个 256 分片的 HostBitmap 索引。在热路径上回答"谁有这个 block"。它在每次请求上被查询。

**Host 层映射。** 一个独立的、按 pod 的数据结构，回答"这个 block 住在这个 pod 上的哪里"。层映射只在选定了一个胜出 pod 之后才被查，用来生成注入下游请求的缓存提示。

这个拆分自然源自访问模式。路由决策在每次请求上查热路径。层信息只为胜者拉取。这两个数据结构可以独立地定尺寸和调优。

## Host 生命周期：两阶段移除

Pod 来来去去。当一个 pod 的事件停止到达（无论它崩溃、被驱逐，还是在排空）时，索引器需要立即停止向它路由。当新 pod 接上它的槽位时，路由需要能接住它。

朴素做法是遍历每个分片、把死 pod 的位从每个位图里清掉。对上万个 block，这会把分片锁长时间持有，并阻塞路由查询。

我们改用两阶段移除。

**阶段 1：即时存活更新。** 每个 pod 在一个全局存活位图里有一位，独立于按 block 的分片。当一个 pod 被判为死亡时，我们在存活位图里用比较并交换（CAS）把它的位置为 0。此后每条路由查询都把候选位图与存活位图求交，于是死 pod 被即刻排除，而不碰任何一个分片。

**阶段 2：有界并发清理。** 死 pod 的按 block 分片条目仍在那里，被存活位图掩蔽掉。一个后台 goroutine 以有界并发上限遍历各分片、清掉死 pod 的位。清理完成时，两样东西被回收：死 pod 那按层的 block → 位置（偏移、长度、设备）映射，以及那些"死 pod 是最后一个存活持有者"的 block 的路由分片条目。没有这第二次清扫，随着集群更迭，那些再没有存活 pod 持有的 block 哈希会在索引里不断累积。这些阶段的结果是热路径保持快。清理按索引器自己的节奏进行，不阻塞路由。

## 拼在一起

Modular Cloud 路由系统里的数据层：

- 一个 256 分片的 ShardedBlockIndexer。每个分片把 blockHash → HostBitmap。斐波那契分布，好让相关 block 散开。缓存行填充，以避免伪共享。
- 一个独立的存活位图用于 pod 存活状态，在关停事件上用 CAS 更新。
- 按 pod 的层映射，用于冷路径，把胜出候选解析成缓存提示位置（GPU/CPU/SSD）。
- 事件消费者（NATS、gRPC、其他），通过幂等操作把 Registered/Evicted/Shutdown 事件推入索引器。设计上对传输无感。
- 一条查询路径，通过在累积哈希链上二分搜索来回答"每个 pod 有这条链里的多少个 block"：O(K × log N) 次分片查找，而非 P × N。

结果是一个数据结构，它能在一个推理编排器的热路径上处理每秒数万次查询，同时让并发的事件流实时地更新它。

## 结论

缓存感知路由只和它底下的数据层一样快。如果回答"哪些 pod 有这些 block"要花毫秒，那你在任何打分逻辑运行之前就已经把延迟预算花光了。这里的架构（分片位图、为均匀性做斐波那契分布、经在累积 block 哈希上二分搜索来查询、并对 pod 更迭用两阶段 host 生命周期）把这个回答保持在微秒量级。

数据层回答一个问题：谁有缓存？缓存亲和只是路由决策的一个输入。负载、会话状态、租户优先级、硬件角色、KV 缓存传输的节点局部性——这些统统要参与，而不同部署给它们不同的权重。数据层给你事实。决策层告诉你对这些事实该怎么做。
