# OpenCL 与 CUDA C++ 替代方案怎么样？（AI 算力民主化，第 5 篇）

**GenAI 也许是新的，但 GPU 不是！** 多年来，许多人尝试用 C++ 创建可移植的 GPU 编程模型，从 OpenCL 到 SYCL 再到 OneAPI 等等。这些曾是最有希望的 CUDA 替代方案，旨在让 AI 算力走向民主化——你可能从未听说过它们，因为它们未能在 AI 领域变得重要。

这些项目都对计算做出过实质贡献，但如果我们真想为未来释放 AI 算力，就必须批判性地审视阻碍它们的失误——而不只是歌颂胜利。从宏观上看，问题源于“[开放竞合](https://en.wikipedia.org/wiki/Open_coopetition)”（open coopetition）的挑战——行业玩家既合作又竞争——以及一路走来的具体管理失误。

让我们深入看看。🚀

## CUDA C++ 替代方案：OpenCL、SYCL 及其他

有许多项目曾致力于打开 GPU 编程的大门，但我最熟悉的是 [**OpenCL**](https://en.wikipedia.org/wiki/OpenCL)。与 CUDA 一样，OpenCL 旨在为程序员提供类似 C++ 的体验来编写运行在 GPU 上的代码。这段历史对我很私人：2008 年，我是 Apple 实现 OpenCL 的主力工程师之一（这是我所开发的 [Clang 编译器](https://en.wikipedia.org/wiki/Clang)的首次生产应用）。在[发布之后](https://en.wikipedia.org/wiki/OpenCL#History)，我们做了一个关键决定：把它贡献给 [Khronos Group](https://www.khronos.org/opencl/)，以便在整个行业被采用和标准化。

这一决定带来了 OpenCL 在业界的广泛采用（参见[这些 logo](https://www.khronos.org/opencl/)），尤其是在移动和嵌入式设备领域。时至今日它仍然非常成功，支撑着 Android 等平台的 GPU 计算，以及 DSP 等专门应用。与 CUDA 不同，OpenCL 从一开始就为可移植性而设计，旨在支持跨 CPU、GPU 和其他加速器的异构计算。OpenCL 还启发了 SyCL、Vulkan、SPIR-V、oneAPI、WebCL 等众多系统。

然而，尽管有技术优势和广泛采用，[**OpenCL 从未成为主导的 AI 计算平台**](https://github.com/tensorflow/tensorflow/issues/22#issuecomment-155145957)。原因有几个：开放竞合的固有张力、由此衍生出的技术问题、AI 需求不断演变，以及 NVIDIA 与 TensorFlow 和 PyTorch 的统一战略。

### **“”[**竞合**](https://en.wikipedia.org/wiki/Open_coopetition)**”下的委员会速度**

2008 年，Apple 在 PC 领域只是小玩家，认为行业标准化能帮助它触达更多开发者。然而，虽然 OpenCL 在硬件厂商中获得了广泛采用，它的演进很快撞上一个大障碍：委员会驱动开发的速度。对 Apple 而言，这种缓慢、共识驱动的过程是致命的：我们想快速推进平台、增加新特性（例如加入 C++ 模板）、表达 Apple 平台的差异化。我们面对一个残酷现实——委员会标准的坏处在于事情突然以委员会共识的速度前进……那感觉如同冰川。

硬件厂商都认可统一软件生态的长期收益，但在短期内，它们是激烈的竞争者。这导致了微妙但重大的问题：参与者不会向委员会透露自己正在开发的硬件特性（那等于给竞争对手先发优势），而是把创新保密直到硬件发布之后，只在特性变成大宗商品时才在（改用厂商私有扩展的）事后加以讨论。

竞合：竞争者之间的“合作”

这对 Apple 成了大问题——这家公司想快速而秘密地行动，在产品发布时一鸣惊人。因此，Apple 决定放弃 OpenCL：转而推出 Metal，从未把 OpenCL 带上 iOS，后来又在 macOS 中将其弃用。其他公司坚守 OpenCL，但这些结构性挑战持续限制它以最前沿 AI 与 GPU 创新的速度演进的能力。

### **OpenCL 的技术问题**

虽然 Apple 大胆地把 OpenCL 标准贡献给了 Khronos，但并没有全力以赴：它贡献的是一份技术规范——却没有完整的参考实现。虽然编译器前端的一部分（Clang）是开源的，但不存在共享的 OpenCL 运行时，迫使各厂商开发自己的定制分支并补全编译器。每个厂商都必须维护自己的实现（一个“fork”），而没有共享的、持续演进的参考基准，OpenCL 变成了厂商私有分支和扩展的拼凑物。这种碎片化最终削弱了它的可移植性——而这正是它被设计出来要实现的东西。

此外，由于厂商们藏匿差异化特性或将其隔离到厂商私有扩展中，这些扩展数量爆炸，使 OpenCL（及其衍生项目）进一步碎片化，侵蚀了它作为统一的厂商无关平台的能力。OpenCL 兼容性与一致性测试的薄弱使这些问题雪上加霜。除此之外，它还继承了我们[之前讨论过的所有“C++ 问题”](https://www.modular.com/blog/democratizing-ai-compute-part-4-cuda-is-the-incumbent-but-is-it-any-good/#pythoncuda)。

开发者想要稳定、支持完善的工具——但 OpenCL 的碎片化、薄弱的一致性测试和参差不齐的厂商支持使它成为一件令人沮丧的苦差事。一位开发者如此总结：[**使用 OpenCL “就像拥抱仙人掌一样舒坦”**](https://futhark-lang.org/blog/2024-07-17-opencl-cuda-hip.html#:~:text=it%20is%20because%20OpenCL%20has,comfortable%20as%20hugging%20a%20cactus)。哎哟。

一位开发者形容使用 OpenCL 的感觉是

"about as comfortable as hugging a cactus."

当 OpenCL 在碎片化和缓慢的委员会演进中挣扎时，AI 正在快速进步——无论是软件框架还是硬件能力。这使得 OpenCL 所提供的与现代 AI 工作负载所需之间的鸿沟进一步加大。

## AI 研究与 AI GPU 硬件不断演变的需求

TensorFlow 和 PyTorch 的问世掀起了 AI 研究的革命——得益于基础设施的改进和大型科技公司资金的巨量涌入。这对 OpenCL 构成重大挑战。虽然它能进行 GPU 计算，但缺乏大规模训练与推理所必需的高层 AI 库和优化。与 CUDA 不同，它对矩阵乘法、Flash Attention 或数据中心规模训练等关键操作没有内建支持。

业界跨公司扩展 TensorFlow 和 [PyTorch](https://github.com/pytorch/pytorch/issues/488) 以使用 OpenCL 的努力很快撞上根本性路障（[尽管需求显而易见且旺盛](https://github.com/tensorflow/tensorflow/issues/22)）。那些继续“抱仙人掌”的开发者很快发现一个残酷现实：如果你无法释放新硬件的全部性能，向新硬件的可移植性毫无意义。由于没有表达可移植的硬件专属增强能力的方法——加之竞合扼杀了协作——进展停滞了。

一个再明显不过的例子？OpenCL *至今*没有为 Tensor Cores 提供标准化[支持](https://www.modular.com/blog/democratizing-ai-compute-part-4-cuda-is-the-incumbent-but-is-it-any-good/#tensorcores)——正是这些专用硬件单元支撑着现代 GPU 和 AI 加速器中高效的矩阵乘法。这意味着使用 OpenCL 往往比使用 CUDA 或其他碎片化的厂商原生软件慢 5 到 10 倍。对于计算成本已经高得惊人的 GenAI，**5 到 10 倍的减速不只是不方便——而是彻底的致命伤**。

### **NVIDIA 对 TensorFlow 和 PyTorch 的战略打法**

当 OpenCL 在碎片化治理的重压下挣扎时，NVIDIA 采取了截然不同的路线——高度受控、极具战略、无情高效，正如我们[之前讨论的](https://www.modular.com/blog/democratizing-ai-compute-part-3-how-did-cuda-succeed)。它积极地与 TensorFlow 和 PyTorch 共同设计 CUDA 的高层库，确保这些框架总是在 NVIDIA 硬件上跑得最好。由于这些框架原生构建在 CUDA 之上，NVIDIA 拥有巨大的先发优势——并通过开箱即用的性能优化进一步加码。

NVIDIA 维持着一个象征性的 OpenCL 实现——但被战略性地削弱了（例如不能使用 TensorCores）——以确保 CUDA 实现总是必需的。NVIDIA 在行业中持续上升的统治地位，使其得以保证 CUDA 实现永远是投入最多的那个。随着时间推移，OpenCL 支持先是衰落，继而消失——而 CUDA 巩固了其无可争议的标准地位。

## 我们能从这些 C++ GPU 项目中学到什么？

以上历史对我们这些亲历者来说很清楚，但真正的价值在于以史为鉴。据此，我认为成功的系统必须：

- 提供**参考实现**，而不只是一纸规范和“兼容性”测试。兼容性应由一个可运行、可采用、可扩展的实现来定义——而不是一个 PDF。
- 由参考实现的维护者提供**强有力的领导与愿景**。
- 在**行业领导者的硬件上跑出顶级性能**——否则它永远是二流的替代品，无法统一行业。
- **快速演进**以满足变化的需求，因为 AI 研究不会停滞，AI 硬件创新仍在加速。
- **培养开发者的热爱**，提供出色的可用性、工具和快速的编译。另外，“像 C++”在 AI 领域根本算不上卖点！
- **建设开放社区**，因为没有广泛采用，技术实力毫无意义。
- **避免碎片化**——一个分裂成互不兼容分支的标准，无法为软件开发者提供有效的统一层。

这些就是我不相信 OpenCL 这类委员会项目能够成功的根本原因。这也是我对 [Intel 的 OneAPI](https://oneapi.io/)（现为 [UXL Foundation](https://uxlfoundation.org/)）等项目更加怀疑的原因：它们*名义上*开放，实际上却由一家与所有其他厂商竞争的硬件厂商掌控。

## AI 编译器怎么样？

就在 C++ 路线无法为硬件厂商统一 AI 算力的同时，AI 行业还面临着一个更大的挑战——即便在 NVIDIA 硬件上使用 CUDA。如果所有代码都要靠人手写，我们如何扩展 AI 算力？芯片太多、AI 算法太多、工作负载的组合太多，无法手工逐一优化。

随着 AI 的影响力与日俱增，它不可避免地吸引了系统开发者和编译器工程师的关注——包括我自己。在下一篇博文中，我们将深入探讨 TVM、OpenXLA、MLIR 等广为人知的“AI 编译器”栈——审视什么行得通、什么行不通，以及我们能带走哪些教训。遗憾的是，这些教训与上文并无太大不同：
