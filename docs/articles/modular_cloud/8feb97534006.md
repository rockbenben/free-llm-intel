# MLSys 2026 的三大趋势

MLSys 2026 为研究与产业界的推理现状提供了极佳的总览。今年有六场 LLM 服务专场（是去年的两倍），议程覆盖了 Modular 使命核心的机会与挑战。Modular 很高兴赞助本届大会，我们的首席科学家 Abdul Dakkak 做了[闪电演讲](https://mlsys.org/virtual/2026/sponsor-lightning-talk/10024)，介绍 Modular 平台的最先进性能。参会的团队注意到贯穿演讲、海报与主题报告的三大趋势。这些都是 Modular 依靠独特技术栈、从第一性原理一直在解的题。

## 趋势一：智能体正在书写从 kernel 到系统的一切

周日的主题演讲定下基调。Mark Saroufim 的 [*When AI Starts Writing Systems Code*](https://mlsys.org/virtual/2026/invited-talk/3655) 展示了新手 kernel 开发者借助 AI 智能体写出能在竞技黑客松名列前茅的 kernels 的例子。随后他诙谐地拆了一些这类“智能体成就”的台——演示智能体如何作弊基准、只对提供的测试用例过拟合而无法泛化。Saroufim 没有坐等一代“永远守规矩”的智能体，而是提出了“零信任”验证的必要：构建足够全面的基准，不再依赖善意提交。

Lidong Zhou 周二的主题演讲 [*The Next Horizon of Systems: From MLSys to System Intelligence*](https://mlsys.org/virtual/2026/invited-talk/3665) 主张系统社群必须把 AI 智能体视为底层代码的首要作者来做规划。Zhou 展示了一个 Rust 微内核（Nanvix）：AI 生成的规格与证明逐模块通过验证；在一个 150 任务的证明生成基准上，通过率从 2%（GPT-4o，基于 prompt）爬升到 91.3%（经过自调试微调的 LLaMA-3.1 8B）。演讲也记录了模型无法完成证明时走的捷径：把代码包进 `external_body` 绕过验证器、埋入错误的后置条件、把证明负担推给调用方。

这些演讲的共同结论是：智能体工程要求规格、设计与验证上有高得多的严谨度。

后续演讲展示了智能体工程在 kernel 与系统各处的具体应用。[*AccelOpt: A Self-Improving LLM Agentic System for AI Accelerator Kernel Optimization*](https://mlsys.org/virtual/2026/poster/10168) 描述了一个闭环系统：LLM 提出加速器 kernel 变体、做 profiling、再把结果喂回给自己。ML for Systems 场次的 [*FlashInfer-Bench: Building the Virtuous Cycle for AI-driven LLM Systems*](https://mlsys.org/virtual/2026/oral/3832) 把这框定为反馈回路：基准的存在就是给智能体一个可优化的对象。

驱动这一切的 kernel 编写之痛也直接登台。[*FlashAttention-4: Algorithm and Kernel Pipelining Co-Design for Asymmetric Hardware Scaling*](https://mlsys.org/virtual/2026/poster/3536) 把实现从 CUDA C++ 模板迁到嵌入 Python 的 CuTe-DSL，目标明确：让下游开发者能扩展 kernel 而不必改动核心框架。[*HipKittens: Fast and Furious AMD Kernels*](https://mlsys.org/virtual/2026/poster/3512) 与 [*ParallelKittens: Systematic and Practical Simplification of Multi-GPU AI Kernels*](https://mlsys.org/virtual/2026/oral/3845) 都主张为 kernel 工程提供更简的抽象集。共同的假设是：人类 kernel 作者不会再为每个加速器世代重写一片模板森林；而抽象对智能体的助益至少不亚于对人类开发者。

### Modular 的方案

Modular 工程师与社区已经在用智能体编写 Mojo 代码，并利用那些让 Mojo 特别适合智能体工程的语言特性。Mojo 健壮的类型系统、高效的编译与清晰的错误信息，支撑起“智能体开发 + 人工验证”的紧反馈回路。我们的博客 [Translating to Mojo via AI Agents](https://www.modular.com/blog/translating-to-mojo-via-ai-agents) 给了这一工作流的实践指南。官方 [`modular/skills`](https://github.com/modular/skills) 包可接入 Claude Code、Cursor 等编码智能体，纠正模型可能产出的误解与过时模式。在那篇文章里，Brad Larson 让智能体在单次会话中把 CUDA softmax kernel（[Szymon Ożóg 的 FastSoftmax](https://github.com/SzymonOzog/FastSoftmax)）转成可移植的 Mojo 版本，跑在 NVIDIA、AMD 与 Apple silicon 上。[Automatika Robotics](https://forum.modular.com/t/project-mojo-for-robotics-porting-gpu-navigation-kernels-jetson-strix-halo/2952) 对他们的 EMOS / kompass-core 负载做了同样的自主导航 kernel 移植，智能体首轮就报告 15.973 ms，对比 SYCL/CUDA 基线 16.358 ms——且 Mojo 侧未做任何优化。[Ehsan Kermani 的另一篇博客](https://www.modular.com/blog/how-i-built-a-pure-mojo-app-and-10-libraries-with-ai-agents) 则演示了高效的智能体工程，造出测试完善、满足社区真实需求的 Mojo 库。

第二个连接点在 kernel 侧。Modular kernel 团队创造的可组合抽象记录在我们的 [Structured Mojo Kernels 博客系列](https://www.modular.com/structured-mojo-kernels)。这一模式把生产 kernel 拆成三个组件（TileIO、TilePipeline、TileOp），用上下文管理器让错误的同步根本无法表达。重写 B200 matmul 把 14,683 行砍到 7,634 行，性能稳定在 1770 TFLOPS。Structured Mojo Kernels 模式同时适用于 NVIDIA 与 AMD，并已开源在 [Modular 仓库](https://github.com/modular/modular)。这正是对 FlashAttention-4 维护之论的直接回答：一个简洁到足以让人类（或智能体）推理的 kernel 层，抽象扛得住硬件变化，且不以性能为代价。

## 趋势二：KV cache 成为主导性子系统

KV cache 是大会讨论度最高的单一话题。周三下午的 LLM Serving 3 专场实际上就是一堂 KV cache 课——连续六篇论文都关于该主题。

Yuhan Liu 关于 [*LMCache: An Efficient KV Cache Layer for Enterprise-Scale LLM Inference*](https://arxiv.org/abs/2510.09665) 的报告直接给出了架构论点。该论文把 KV cache 当作一等数据结构而非推理的内部副产品，并报告真实部署中 KV cache 的使用量已超出 GPU 内存：五周的遥测数据显示，存储的 KV cache 中绝大部分已放不进 GPU，而每 token 的复用次数在用户间增长了 19% 以上。该系统现已支持八种存储后端（NFS、WEKA、GPU-Direct Storage、Mooncake Store、NIXL、S3、InfiniStore、Valkey）、四种处理器类型（NVIDIA、AMD、Ascend、TPU）和两个推理引擎（vLLM、SGLang）。这种覆盖广度是必需的：缓存层必须可移植，因为其下的存储与算力硬件并不同质。

合起来读，这些论文描述的是同一场转变。KV cache 正日益分布式、异构且复杂，其放置、传输、驱逐与复用策略横跨 GPU 内存、主机 DRAM、本地磁盘与分布式存储。趋势已推进到出现了为缓存定制芯片的市场：[Netpreme](https://netpreme.com/) 正在打造带网络化内存分层的 Memory Processing Unit，卖点是给 XPU 内存扩展 100 倍。当一个子系统开始催生自己的硬件供应商，它就不再是实现细节了。

优化缓存的其他手段是量化与稀疏——两者并用直接驯服内存需求。[Kitty: Accurate and Efficient 2-bit KV Cache Quantization with Dynamic Channel-wise Precision Boost](https://openreview.net/forum?id=r3mQiuYKIN) 在同等内存预算下支持 8 倍大的 batch，提升吞吐。SGLang 团队的 [HiSparse: Turbocharging Sparse Attention with Hierarchical Memory](https://www.lmsys.org/blog/2026-04-10-sglang-hisparse/)（Christos Kozyrakis 在周五关于推理效率的主题演讲中点了名）把稀疏注意力与分层内存结合：GPU 保留常访问 KV 区域的设备热缓冲，不活跃条目卸载到主机内存。在 GLM-5.1-FP8 的长上下文负载上吞吐最高 5 倍。量化压缩了缓存的持有成本，稀疏压缩了引擎必须关注的范围，两者配对是长上下文推理的务实答案。

共同的主线是：缓存正从引擎中被拽出来，变成一个自成一体的分布式系统——有自己的调度、自己的存储分层、自己的复用语义。

### Modular 的方案

这正是 Brian Zhang 在其博客 [The Five Eras of KVCache](https://www.modular.com/blog/the-five-eras-of-kvcache) 描述的趋势。文章追踪缓存的演化：从 2023 年引擎内部的局部优化，经过 PagedAttention、prefix caching、卸载，终至缓存统一、分布式、跨异构基础设施可组合的时代。MLSys 2026 的论文记录了这些优化的紧迫性——而它们从一开始就内建在 Modular Cloud 中。

想了解分布式 KV cache 在集群层如何工作，可参阅 Modular 博客的推理路由系列。[*Why LLM Inference Needs a New Kind of Router*](https://www.modular.com/blog/why-llm-inference-needs-a-new-kind-of-router-part-1) 论证路由决策与 KV cache 状态不可分：路由器必须缓存感知，而累积链式索引与位图索引让这在规模上可行。拉远视角，Kyle Caverly 的 [MAX Serve 从 prompt 到响应走读](https://youtu.be/hewZwTwDBcM?si=gZX08UlKiPDRTE4r)是理解 KV cache 在整体推理平台中位置的极佳入门。MLSys 的论文描述了高效 KV cache 管理的多种进路。这些论文印证了 Modular 多年建设的紧迫价值。Modular Cloud 实现了大规模分布式推理的可组合方案，跨硬件可用，并能灵活跟随不断演进的优化。

## 趋势三：推理负载正在利用异构硬件

异构性贯穿 MLSys 2026 全部六场 LLM Serving 专场和两场服务主题的 Industry Track。Esha Choukse 第一天的受邀演讲 [*Beyond Model Serving: Cross-Stack Co-Design for Agentic Systems*](https://mlsys.org/virtual/2026/invited-talk/3650) 定了框架：硬件多样性是高效服务交互式、多模态与智能体系统的前提。

Meta 的 Industry Track 论文 [*Optimizing Deployment Configurations for LLM Inference*](https://mlsys.org/virtual/2026/oral/3780) 展示了即使在单模型部署中异构性的收益。论文记录了把 prefill 跑在一种加速器、decode 跑在另一种所带来的 15%-25% TCO（总拥有成本）改善——因为 prefill 是计算受限（偏好高 FLOP/s），decode 是内存带宽受限（偏好高 HBM 带宽）。同场次 NVIDIA 的 [*Beyond the Buzz: A Pragmatic Take on Inference Disaggregation*](https://mlsys.org/virtual/2026/oral/3819) 承认 prefill-decode 分离真实且有价值，但前提是速率匹配、KV 传输、缓存路由与弹性扩缩必须同时解决。[*BOute: Cost-Efficient LLM Serving with Heterogeneous LLMs and GPUs via Multi-Objective Bayesian Optimization*](https://mlsys.org/virtual/2026/oral/3795) 把“哪个模型跑在哪个加速器上”的选择当作搜索问题。多模态与生成模型场次的 [*TriInfer: Hybrid EPD Disaggregation for Efficient Multimodal Large Language Model Inference*](https://mlsys.org/virtual/2026/oral/3756) 把分离从两阶段扩展到面向多模态负载的 encode-prefill-decode 三段。

硬件专属的 kernel 工作说明了这为何重要。[*SuperInfer: SLO-Aware Rotary Scheduling and Memory Management for LLM Inference on Superchips*](https://mlsys.org/virtual/2026/oral/3809) 发现现有卸载框架对 GH200 的 NVLink-C2C 互连利用率不足其 900 GB/s 容量的 5%，因为它们把它当 PCIe 用。论文结论：瓶颈在软件栈。[*SHIP: SRAM-Based Huge Inference Pipelines for Fast LLM Serving*](https://mlsys.org/virtual/2026/oral/3834) 描述了 Groq 基于 LPU 的服务栈：整个模型放进 SRAM，编译器以周期粒度静态调度集合通信。[*TokenWeave: Efficient Compute-Communication Overlap for Distributed LLM Inference*](https://mlsys.org/virtual/2026/oral/3744) 依赖 PyTorch 的 SymmetricMemory API 与 NVLink4 的 NVSHARP 引擎——这两者的存在恰恰因为厂商专属的集合通信路径已不再契合 kernel 作者想要的工作方式。

异构硬件在多模态推理与成本优化上提供优势，但可能被厂商专属的软件栈所束缚。

### Modular 的方案

MAX 从底层就是为硬件多元而建。一个容器跑 NVIDIA GPU、AMD GPU 与 CPU。kernel 层用 Mojo 编写——面向每个硬件目标编译，而不是包装厂商专属库。运行时硬件感知，但不绑定特定硬件。

在真实负载上（如 [Hippocratic AI](https://www.modular.com/blog/hippocratic-ai-partners-with-modular-to-power-flexible-high-quality-inference-for-real-time-patient-conversations)），对 400B+ 参数模型，MAX 相对 NVIDIA B300 上的 SGLang 做到 500ms 以下的平均 TTFT、约快 30% 的 P99 端到端、快 22% 的平均端到端。对比 B200 上的 vLLM，Modular 栈在 Kimi-K2.5 上 P50 TTFT 快 5.5 倍、在 Gemma-4-31B-it 上 P99 TTFT 快 2.5 倍，两者吞吐均 1.5 倍。Flux.2-dev 图像生成负载在同一软件栈中，B200 上比 `torch.compile` 的 PyTorch Diffusers 快 6.9 倍，AMD MI355x 上快 3.8 倍。更多 MAX 的最先进性能可见 [Modular 的 MLSys 闪电演讲](https://mlsys.org/virtual/2026/sponsor-lightning-talk/10024)。

高效的推理服务需要榨取全部可用硬件的潜力以满足不断变化的行业需求。MLSys 2026 的专场把推理栈的组件拆开孤立优化：kernel、KVCache、服务层等。Modular 则把整个栈重写为一个系统，从而能从 kernel 到云做全局优化。这一打法让我们站在研究最前沿，达成贯穿全栈的优化。
