# Mojo n-body 示例简明指南

自 2023 年 8 月起，Mojo 仓库中就包含一个名为 [*nbody.mojo*](https://github.com/modularml/mojo/blob/main/examples/nbody.mojo) 的小型基准测试示例。这段代码源自 [The Computer Language Benchmarks Game](https://en.wikipedia.org/wiki/The_Computer_Language_Benchmarks_Game) 中的一个示例——该网站会对流行编程语言实现的各种算法进行基准测试。

[N-body 是 Computer Language Benchmark Game 的基准测试项目之一](https://benchmarksgame-team.pages.debian.net/benchmarksgame/description/nbody.html#nbody)，被描述为一个“使用简单辛积分器模拟巨行星轨道”的程序。这个基准测试在考察单核数值性能方面表现出色。由于它只是一个简单的常微分方程（ODE）求解器，因此不易并行化（不过正如我们将看到的，可以实现基础的向量化）。除此之外，对轨道动力学进行数值积分还增加了一层复杂性：实现中的微小积分误差很容易随时间呈指数级增长，从而使计算失稳。这使得 n-body 问题成为同时检验实现速度与准确性的良好测试。

[本文将简要介绍 Mojo 的 n-body 示例](https://github.com/modularml/mojo/blob/main/examples/nbody.mojo)，详细描述其中的代码。虽然不会深入数学细节，但会讲解一些轨道力学知识。在此过程中，还将展示如何利用 Mojo 的内建功能和标准库开始编写你自己的优化代码。

### 安装 Mojo

首先安装 Mojo，它是 MAX 框架的一部分。安装 MAX 和 Mojo 的完整说明见 [MAX 文档](https://docs.modular.com/max/install)。安装 Mojo 后，即可从 [Mojo GitHub 仓库](https://github.com/modularml/mojo.git) 获取 n-body 示例代码。

Bash

git clone https://github.com/modularml/mojo.git

示例代码位于 *mojo/examples* 目录中。

### 从 Mojo 标准库导入

示例开头从标准库导入了若干模块。

Mojo

from math import sqrt
from benchmark import run, keep
from collections import List

标准库包含了 Mojo 的许多功能，包括常用数学函数、基准测试工具、列表等标准集合类型，以及测试与验证方法。

### 设置数据结构

接下来，定义整个仿真过程中使用的常量。

Mojo

# for consistency with other implementations, alias PI
# you can also directly use math.pi from the standard library
alias PI = 3.141592653589793
alias SOLAR_MASS = 4 * PI * PI
alias DAYS_PER_YEAR = 365.24

尽管标准库的 math 模块已包含常量 pi（*math.pi*），但这里出于便利以及与 Benchmarks Game 其他仿真保持一致的考虑重新定义了它。

在讲解这个仿真时将频繁出现一个主题：如何为使计算更快、更简捷、更稳定而做出取舍。计量单位的选择就是一个绝佳的例子。在本仿真中，质量单位取太阳质量除以 4π²，时间单位取一年，距离单位取一个[天文单位](https://en.wikipedia.org/wiki/Astronomical_unit)（AU），大致相当于日地平均距离。

**为什么选择这些单位？**

在本仿真中，我们考虑的是一个遵循经典力学的轨道动力系统。这意味着可以使用[牛顿万有引力定律](https://en.wikipedia.org/wiki/Newton%27s_law_of_universal_gravitation)来建模天体之间的相互作用。

由此可以推出[开普勒行星运动定律](https://en.wikipedia.org/wiki/Kepler%27s_laws_of_planetary_motion)成立，我们可以据此指导单位的选择。

行星运动图，作者 Hankwang - CC BY 2.5

开普勒第三定律指出 T²/a³ 为常数，其中 T 定义为小天体绕大天体运行的轨道周期，a 为两天体之间的距离。对地球和太阳而言，该常数约为 GM/4π²，其中 G 为引力常量，M 为太阳质量。

利用这一经实验观测确定的知识，我们将质量单位定为太阳质量乘以 4π²。这意味着在本仿真及这一单位选择下，引力常量等于 1。你可以在[开普勒行星运动定律的 Wikipedia 页面](https://en.wikipedia.org/wiki/Kepler%27s_laws_of_planetary_motion)上深入了解这一点。

这些选择不仅通过[去掉一次乘法](https://en.wikipedia.org/wiki/Identity_element#Definitions)简化了引力加速度的计算，还帮助把我们的计算缩放到合理的数值范围，降低了因舍入误差在仿真中引入数值不稳定性的可能性。单位的选择实际上对运动方程做了归一化。

单位确定之后，就该定义行星的数据结构了。每颗行星（以及太阳）都有三个定义其状态的主要组成部分：

- 三维空间中的可变位置。
- 三维空间中的可变速度。
- 恒定的质量。

Mojo

@value
struct Planet:
    var pos: SIMD[DType.float64, 4]
    var velocity: SIMD[DType.float64, 4]
    var mass: Float64

    fn __init__(
        inout self,
        pos: SIMD[DType.float64, 4],
        velocity: SIMD[DType.float64, 4],
        mass: Float64,
    ):
        self.pos = pos
        self.velocity = velocity
        self.mass = mass

Planet 结构由 [Mojo struct](https://docs.modular.com/mojo/manual/structs) 表示，并加上 [*@value* 装饰器](https://docs.modular.com/mojo/manual/decorators/value)，它告诉 Mojo 编译器自动合成必要的生命周期方法，使该结构具备完整的值语义。也就是说，它会自动创建与 Mojo [所有权模型](https://docs.modular.com/mojo/manual/values/)兼容的 *__init__()*、 *__copyinit__()* 和 *__moveinit__()* 方法。在处理由内置类型组成的简单结构时，这会简化你的代码库，使其更易读、更可靠。

位置和速度向量在内部用 [Mojo SIMD 类型](https://docs.modular.com/mojo/manual/types#simd-and-dtype)表示，即长度为 4 的 *float64* 向量。用长度为 4 的向量可能让你感到意外，因为位置和速度只有三个维度。

SIMD 数据类型要求向量宽度能够放入计算寄存器，这限制了向量长度的选择。长度为 4 的 SIMD 向量是能容纳行星位置和速度的最小尺寸，因此我们需要“浪费”一个 *float64* 值来换取并行计算。这是一个空间与时间之间的权衡示例：空间上用 4 个浮点数存放 3 个值；时间上则可以使用 SIMD 运算同时对 3 个值执行一次计算。

保证其正常工作的一个关键在于：初始化行星对象时，务必将每个 SIMD 类型的最后一项设为零，防止这些多余值污染计算结果。这种技术称为填充（padding），在编写优化计算核时十分常见：它利用向量化运算，同时在计算上“忽略”([computationally “ignoring”](https://en.wikipedia.org/wiki/Additive_identity))我们不关心的填充值。

有了 Planet 数据结构，现在就可以创建带有初始状态（包括位置和速度）的行星表示了。

Mojo

alias Sun = Planet(
    0,
    0,
    SOLAR_MASS,
)

整个初始状态以天体列表的形式存储，第一项是最大的天体——太阳。位置以 AU 编码，速度以 AU/年表示，质量则按太阳质量除以 4π² 进行缩放。初始状态由转换为适当单位的观测数据设定。这些初始状态数值是如何确定的超出了本篇博文的范围，它们取自 Benchmarks Game 的仿真。

除太阳外，本仿真只涉及外太阳系的四颗类木天体：木星、土星、天王星和海王星。太阳被定义在仿真中心，位置和速度均为零。注意在太阳的初始化中，我们只需向构造函数传入单个值即可初始化 SIMD 数组的所有元素。对于 SIMD 数据类型，如果只向构造函数传递一个值，Mojo 会假设你希望将向量中的每一项都初始化为同一个值。

对于行星，我们显式使用四个值来构造：位置和速度各三个非零值，第四维填零，以防止末位值破坏后续代码中会遇到的 SIMD 归约（reduce）运算。

仿真的初始状态和运行状态存储在一个 [*List*](https://docs.modular.com/mojo/stdlib/collections/list/List) 中，它是 [Mojo 标准库](https://docs.modular.com/mojo/lib)中可用的[集合模块](https://docs.modular.com/mojo/stdlib/collections/)之一。回想一下，由于用 [*@value*](https://docs.modular.com/mojo/manual/decorators/value) 装饰了 Planet 结构，我们立即获得了与 Mojo `List` 集合类型的完全兼容。

初始化代码块还展示了 Mojo 的另一项优化特性：[*alias*](https://docs.modular.com/mojo/manual/parameters/#alias-named-parameter-expressions)。别名定义了一个编译期常量值，在运行时不可更改。我们可以用别名在编译期固定初始状态，然后在计算中使用运行时变量（[*var*](https://docs.modular.com/mojo/manual/variables)）。

### 计算动量偏移

在运行仿真之前，还有一项初始化工作必须处理。虽然太阳被设为仿真的固定中心，但整个仿真质心的速度目前并不为零。这意味着在计算运动方程时，仿真中的质心将以恒定速度在空间中移动。这种额外的运动会导致数值稳定性下降，我们可以通过确保仿真质心静止来抵消它。

Mojo

fn offset_momentum(inout bodies: List[Planet]):
    var p = SIMD[DType.float64, 4]()

    for body in bodies:
        p += body[].velocity * body[].mass

    var body = bodies[0]
    body.velocity = -p / SOLAR_MASS

    bodies[0] = body

为此，我们先根据初始状态计算动量偏移，然后调整太阳的位置和速度以抵消该偏移。这有助于防止仿真随时间漂移、保持稳定参考系，并确保结果真实准确。

动量定义为天体的质量乘以其速度。在 offset_momentum 方法中，我们遍历仿真中的每个天体，累加每个天体的动量以求得总动量，然后通过调整太阳的初始速度（此前设为零）将其从太阳处扣除。

注意，该方法以 *inout* 参数形式接收行星列表，使列表成为可变引用。这意味着方法返回后，调用方会看到方法中对行星列表所做的全部修改。

### 对动力系统做积分

仿真中的大部分工作由 *advance* 函数完成，它将运动方程向前积分一个时间步。它以 *inout* 可变引用参数形式接收行星列表，并接收时间步参数 *dt*，[默认情况下](https://docs.modular.com/mojo/manual/functions#fn-functions)dt 是不可变引用，遵循 Mojo 的*借用*（borrowed）[参数约定](https://docs.modular.com/mojo/manual/values/ownership#argument-conventions)。

Mojo

fn advance(inout bodies: List[Planet], dt: Float64):
    for i in range(len(INITIAL_SYSTEM)):
        for j in range(i+1, len(INITIAL_SYSTEM)):
            var body_i = bodies[i]
            var body_j = bodies[j]
            var diff = body_i.pos - body_j.pos
            var diff_sqr = (diff * diff).reduce_add()
            var mag = dt / (diff_sqr * sqrt(diff_sqr))

            body_i.velocity -= diff * body_j.mass * mag
            body_j.velocity += diff * body_i.mass * mag

            bodies[i] = body_i
            bodies[j] = body_j

    for body in bodies:
        body[].pos += dt * body[].velocity

从宏观上看，它计算每个天体因万有引力而对其他天体施加的速度变化。然后使用更新后的速度更新每个天体的位置。这种两步更新之所以可行，是因为该算法使用由运动方程推导出的辛积分器来确定系统中每个天体的更新量。这也称为[半隐式欧拉法](https://en.wikipedia.org/wiki/Semi-implicit_Euler_method)。虽然该方法的完整推导超出本篇博文的范围，但我们可以指出：辛积分器对行星动力系统很有用，因为它们守恒能量。相比之下，一般的常微分方程求解器不守恒能量，可能给仿真引入不稳定性。

关于这一实现有几点值得注意。第一，出于必要，这是关于天体数量的 O(n²) 算法。每个行星天体都对其他天体有引力影响，需要大约 n² 量级的计算。然而，由于天体间的作用力是对称的，我们只需计算一次两个对象之间的力，就能把计算量减半。

第二，由于每个维度相互独立，我们可以用 SIMD 运算更快地完成加法和乘法。我们还使用 SIMD 的 *reduce_add* 运算来计算天体间距离的平方。这也是为什么必须用零填充第四位位置和速度值，以确保未定义的内存初始化不会影响计算。

第三，由于我们选择的单位使引力常量为 1，它不会出现在计算中。

### 计算系统能量

我们将每个天体的动能与天体间的势能相加，得到系统的总能量。可以用这个计算来检验仿真的正确性与稳定性。由于这是一个封闭系统，总能量应保持恒定，而选择辛积分器正是为了维持这一不变量。

Mojo

fn energy(bodies: List[Planet]) -> Float64:
    var e: Float64 = 0

    for i in range(len(INITIAL_SYSTEM)):
        var body_i = bodies[i]
        e += (
            0.5
            * body_i.mass
            * (body_i.velocity * body_i.velocity).reduce_add()
        )
        for j in range(i+i, len(INITIAL_SYSTEM)):
            var body_j = bodies[j]
            var diff = body_i.pos - body_j.pos
            var distance = sqrt((diff * diff).reduce_add())
            e -= (body_i.mass * body_j.mass) / distance

    return e

动能就是简单的 ½mv²（这里 SIMD 乘法和 *reduce_add* 再次派上用场），其中 m 为天体质量，v 为速度。两个天体间的势能为 -GMm/r，其中 G 为引力常量，M 为第一个天体的质量，m 为第二个天体的质量，r 为两者之间的距离。再次提醒：由于我们最初的单位选择，此式中的 G 为 1，势能只是两质量之积除以它们之间的距离。

### 整合所有内容

运行仿真所需的一切都已就绪。我们首先初始化仿真，创建系统初始状态的副本，并在仿真开始时计算系统能量，以便在结束时验证其稳定性。

Mojo

def run_system():
    print("Starting nbody...")

    var system = INITIAL_SYSTEM
    offset_momentum(system)

    print("Energy of System:", energy(system))

    for i in range(50_000_000):
        advance(system, 0.01)

    var system_energy = energy(system)
    assert_almost_equal(system_energy, -0.1690599)
    print("Energy of System:", system_energy)

我们以 0.01 的时间步运行仿真 5000 万步。这意味着仿真每次向前推算 3.5 天，共预测 5 万年的轨道动力学。对 *advance* 函数的 5000 万次调用，让我们能清楚地看到确保 `advance` 被当作内联代码而非函数调用所带来的收益。

仿真结束时，我们重新计算系统能量，并验证其与初始能量在计算精度范围内相等。注意，为提高可读性，我们可以使用下划线来分隔大数字。

### 对代码做基准测试

除了直接运行仿真，我们还可以提供另一种方法对其性能做基准测试。为保证基准测试代码的准确性，我们使用标准库 [benchmark 包](https://docs.modular.com/mojo/stdlib/benchmark/)中的 [*keep*](https://docs.modular.com/mojo/stdlib/benchmark/compiler/keep) 函数，确保 Mojo 编译器不会优化掉能量计算。通常情况下，如果 Mojo 判定某个方法没有副作用，就会把那段代码优化掉。

Mojo

def benchmark():
    fn benchmark_fn():
        var system = INITIAL_SYSTEM
        offset_momentum(system)
        keep(energy(system))

        for i in range(50_000_000):
            advance(system, 0.01)

        keep(energy(system))

    run[benchmark_fn](max_runtime_secs=0.5).print()

## 运行仿真

要把仿真构建为独立程序，我们需要提供一个 main 函数作为应用入口。

Mojo

def main():
    run_system()

可以使用以下命令构建应用：

Bash

mojo build nbody.mojo
./nbody.mojo

要运行代码的基准测试版本，请把 *run_system* 命令改为 *benchmark*，重新编译并运行。在一台具有 512 位宽 SIMD 的 Intel x86 系统上，对 5000 万次迭代做三次基准测试，结果为：
