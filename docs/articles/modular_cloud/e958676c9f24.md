# CUDA 是现任霸主，但它真的好吗？（AI 算力民主化，第 4 篇）

要回答 CUDA 是否“好”这个问题，比听起来要棘手得多。我们说的是原始性能？功能集？还是它对 AI 开发世界的更广泛影响？CUDA 是否“好”，取决于*你问谁*以及*他们需要什么*。在本文中，我们将从那些每天使用 CUDA、在 GenAI 生态内构建东西的人的视角来评估 CUDA：

- 对于在 CUDA 之上构建的 AI 工程师，它是一个不可或缺的工具，但同时也伴随着版本管理的头疼、不透明的驱动行为和深度的平台依赖。
- 对于为 NVIDIA 硬件编写 GPU 代码的 AI 工程师，CUDA 提供了强大的优化能力，但前提是你必须接受为达到顶级性能所必需的痛苦。
- 对于那些希望 AI 工作负载运行在多家厂商 GPU 上的人，CUDA 更像是障碍而非解决方案。
- 还有 NVIDIA 自己——这家围绕 CUDA 建立财富的公司，从中获取巨额利润，并不断巩固其对 AI 算力的统治。

那么，CUDA 到底“好”吗？让我们逐一深入每种视角寻找答案！🤿

## AI 工程师

如今许多工程师在 AI 框架和智能体库之上构建应用，比如 [LlamaIndex](https://www.llamaindex.ai/)、[LangChain](https://www.langchain.com/) 和 [AutoGen](https://github.com/microsoft/autogen?tab=readme-ov-file)，并不需要深入了解底层硬件细节。对这些工程师而言，CUDA 是强大的盟友。它的成熟度和行业主导地位带来了显著优势：大多数 AI 库都为与 NVIDIA 硬件无缝协作而设计，全行业聚焦单一平台也促进了协作。

然而，CUDA 的统治地位也带来了一整套挥之不去的挑战。最大的障碍之一是管理不同 CUDA 版本的复杂性，这可能是一场噩梦。这种沮丧正是大量段子的主题：

图片来源：

x.com/ordax

这对许多工程师来说是真实的生活体验。这些 AI 从业者需要不断确保 CUDA 工具包、NVIDIA 驱动和 AI 框架之间的兼容。版本不匹配会导致令人抓狂的构建失败或运行时错误，无数开发者都曾亲身经历过：

> "I failed to build the system with the latest NVIDIA PyTorch docker image. The reason is PyTorch installed by pip is built with CUDA 11.7 while the container uses CUDA 12.1." (github.com)

或者：

> "Navigating Nvidia GPU drivers and CUDA development software can be challenging. Upgrading CUDA versions or updating the Linux system may lead to issues such as GPU driver corruption." (dev.to)

遗憾的是，这类头疼问题并不少见。修复它们往往需要深厚的专业知识和大量排障时间。NVIDIA 对不透明工具和繁琐配置流程的依赖，劝退了新人，也拖慢了创新。

针对这些挑战，NVIDIA 历来选择向栈的上层移动来解决一个个点状问题，而不是修复根本问题——CUDA 层本身。例如，它最近推出了 NIM（NVIDIA Inference Microservices），一套旨在简化 AI 模型部署的容器化微服务。这也许能理顺某一用例，但 NIM 同时把底层操作抽象掉了，加剧了锁定，并限制了对底层优化与创新的访问——而那正是 CUDA 价值主张的关键。

在 CUDA 之上构建的 AI 工程师面临兼容性与部署挑战的同时，那些更贴近硬件的人——特别是 AI 模型开发者和性能工程师——则要面对另一套完全不同的权衡。

## AI 模型开发者与性能工程师

对于推动 AI 模型极限的研究人员和工程师，CUDA 既是不可或缺的工具，也是令人沮丧的掣肘。对他们而言，CUDA 不是一个 API，而是他们编写的每一个性能关键操作的基础。这些工程师工作在优化的最底层，编写自定义 CUDA kernel、调优内存访问模式、从 NVIDIA 硬件中榨取最后一分性能。GenAI 的规模和成本要求他们这样做。但 CUDA 究竟是赋能了他们，还是限制了他们的创新能力？

尽管占据统治地位，CUDA 已显老态。它设计于 2007 年，远早于深度学习，更不用说 GenAI。自那以后，GPU 发生了巨大演进，Tensor Cores 和稀疏化特性成为 AI 加速的核心。CUDA 早期的贡献是让 GPU 编程变得简单，但它没有跟上现代 GPU 为 transformers 和 GenAI 性能所必需的新特性。这迫使工程师绕开它的种种限制，才能达到工作负载所需的性能。

###### CUDA 做不到现代 GPU 能做的一切

像 [FlashAttention-3](https://pytorch.org/blog/flashattention-3/)（[示例代码](https://github.com/Dao-AILab/flash-attention/blob/a09abcd32d3cae4d83b313446e887f38d02b799f/hopper/copy_sm90_bulk_reduce.hpp#L22)）和 [DeepSeek](https://www.modular.com/blog/democratizing-compute-part-1-deepseeks-impact-on-ai) 创新这样的前沿技术，要求开发者穿透 CUDA 下沉到 PTX——NVIDIA 更底层的汇编语言。PTX 的文档不完整，随硬件代际不断变化，对开发者来说实际上是个黑盒。

更成问题的是，PTX 比 CUDA 更深地锁死在 NVIDIA 上，可用性甚至更差。然而，对于追求极限性能的团队别无选择：他们被迫绕过 CUDA，忍受巨大的痛苦。

###### **Tensor Cores：性能的必需品，却藏在黑魔法之后**

如今，AI 模型的大部分 FLOPs 来自“[Tensor Cores](https://leimao.github.io/blog/NVIDIA-Tensor-Core-Programming/)”，而非传统 CUDA cores。但直接为 Tensor Cores 编程绝非易事。虽然 NVIDIA 提供了一些抽象（如 cuBLAS 和 CUTLASS），要把 GPU 用到极致仍然需要晦涩的知识、反复试错的测试，而且往往要[逆向工程未记录的行为](https://www.tomshardware.com/tech-industry/artificial-intelligence/deepseeks-ai-breakthrough-bypasses-industry-standard-cuda-uses-assembly-like-ptx-programming-instead)。每一代新 GPU 的 Tensor Cores 都在变化，而[文档却年久失修](https://developer.nvidia.com/blog/programming-tensor-cores-cuda-9/)。这使工程师可用的资源有限，难以充分释放硬件潜力。

图片来源：NVIDIA

###### **AI 是 Python，但 CUDA 是 C++**

另一个重大限制是编写 CUDA [本质上必须使用 C++](https://docs.nvidia.com/cuda/cuda-c-programming-guide/)，而现代 AI 开发几乎全在 Python 中进行。在 PyTorch 上处理模型与性能的工程师并不想在 Python 和 C++ 之间来回切换——这两种语言的心智模式截然不同。这种错位拖慢了迭代、制造了不必要的摩擦，还迫使 AI 工程师去操心底层性能细节，而本该专注于模型改进。此外，CUDA 依赖 [C++ 模板](https://github.com/NVIDIA/cutlass)，导致[编译速度慢得痛苦](https://developer.nvidia.com/blog/reducing-application-build-times-using-cuda-c-compilation-aids/)，错误信息也常常令人不知所云。

## 构建可移植软件的工程师与研究人员

并不是所有人都乐意把软件锁死在 NVIDIA 的硬件上，而且挑战很明确。CUDA 无法运行在其他厂商的硬件上（比如[你口袋里的超级计算机](https://www.visualcapitalist.com/the-supercomputer-in-your-pocket/)），而也没有任何替代方案能提供 CUDA 在 NVIDIA 硬件上的全部性能与能力。这迫使开发者为多个平台把 AI 代码写好几遍。

在实践中，许多跨平台 AI 努力都举步维艰。早期版本的 TensorFlow 和 PyTorch 曾有 OpenCL 后端，但在功能和速度上都远落后于 CUDA 后端，导致大多数用户留在了 NVIDIA 阵营。维护多条代码路径（NVIDIA 用 CUDA，其他平台用别的）成本高昂，而在 AI 快速进步之下，只有大型组织才有资源做这类投入。

CUDA 造成的分裂形成了一个自我强化的循环：由于 NVIDIA 拥有最大的用户群和最强大的硬件，大多数开发者优先面向 CUDA，并希望其他人迟早会跟上。这进一步巩固了 CUDA 作为 AI 默认平台的统治。

我们将在下一篇博文中探讨 OpenCL、TritonLang 和 MLIR 编译器等替代方案，理解为什么这些选项未能动摇 CUDA 的统治。

## CUDA 对 NVIDIA 自己好吗？

当然，答案是肯定的：“CUDA 护城河”造就了一个赢家通吃的局面。到 2023 年，NVIDIA 占据[数据中心 GPU 市场约 98% 的份额](https://www.datacenterdynamics.com/en/news/nvidia-gpu-shipments-totaled-376m-in-2023-equating-to-a-98-market-share-report/#:~:text=As%20reported%20by%20HPCwire%2C%20the,company%20in%20the%20year%20prior)，奠定了其在 AI 领域的统治。正如我们在[前几篇](https://www.modular.com/blog/democratizing-ai-compute-part-3-how-did-cuda-succeed)中讨论的，CUDA 是连接 NVIDIA 现在与未来产品的桥梁，推动 Blackwell 等新架构的采用，维系 NVIDIA 在 AI 算力上的领先地位。

然而，像 [Jim Keller](https://en.wikipedia.org/wiki/Jim_Keller_(engineer)) 这样的传奇硬件专家则认为“[CUDA 是沼泽，不是护城河](https://www.tomshardware.com/tech-industry/artificial-intelligence/jim-keller-criticizes-nvidias-cuda-and-x86-cudas-a-swamp-not-a-moat-x86-was-a-swamp-too)”，并将其类比于拖住 Intel 的 X86 架构。

“

CUDA's a swamp, not a moat

，”

Jim Keller

这样论断。

CUDA 怎么会成为 NVIDIA 的问题？有几方面挑战。

###### **CUDA 的可用性对 NVIDIA 自身冲击最大**

Jensen Huang 有句名言：NVIDIA 的[软件工程师比硬件工程师还多](https://www.wsj.com/tech/ai/ai-nvidia-apple-amd-jensen-huang-software-bb581f5a)，其中相当一部分专职编写 CUDA。但 CUDA 内部的可用性与可扩展性挑战拖慢了创新，迫使 NVIDIA 大量招聘工程师来四处救火。

###### **CUDA 的沉重拖累新硬件铺开**

CUDA 无法在 NVIDIA 自己的各代硬件之间提供性能可移植性，而其库的庞大规模也是一把双刃剑。推出 Blackwell 这样的新一代 GPU 时，NVIDIA 面临选择：要么重写 CUDA，要么发布无法完全释放新架构性能的硬件。这解释了为什么每一代新产品[发布时性能都不理想](https://www.forbes.com/sites/karlfreund/2023-09-08/nvidia-adds-new-software-that-can-double-h100-inference-performance/)。CUDA 覆盖面的这种扩张既昂贵又耗时。

###### **创新者的窘境**

NVIDIA 对向后兼容的承诺（CUDA 早期的卖点之一）如今已成为阻碍其快速创新的“技术债”。虽然为老一代 GPU 提供支持对其开发者群体至关重要，但这迫使 NVIDIA 把稳定置于革命性变化之上。这种长期支持消耗时间和资源，也可能限制其未来的灵活性。

尽管 NVIDIA 向开发者承诺了连续性，但 Blackwell 若[不破坏与 Hopper PTX 的兼容](https://docs.nvidia.com/cuda/blackwell-compatibility-guide/#application-compatibility-on-blackwell-architecture)就无法达成性能目标，而现在一些 [Hopper PTX 操作](https://docs.nvidia.com/cuda/parallel-thread-execution/#asynchronous-multiply-and-accumulate-instruction-wgmma-mma-async)在 Blackwell 上已不可用。这意味着绕过 CUDA 直接使用 PTX 的高级开发者，可能会发现不得不为下一代硬件重写代码。

尽管有这些挑战，NVIDIA 在软件上的强劲执行力和早期战略决策仍为未来增长占据了有利位置。随着 GenAI 崛起和建立在 CUDA 之上的生态不断扩大，NVIDIA 有望继续站在 AI 算力的最前沿，并已迅速成长为[全球市值最高的公司之一](https://www.washingtonpost.com/business/2024-11-05/nvidia-tops-apple/)。

## CUDA 的替代方案在哪里？

总而言之，CUDA 既是祝福也是负担，取决于你处于生态的哪一侧。它的[巨大成功](https://www.modular.com/blog/democratizing-ai-compute-part-3-how-did-cuda-succeed)造就了 NVIDIA 的统治，但它的复杂性、技术债和厂商锁定为开发者及 AI 算力的未来带来了重大挑战。

随着 AI 硬件快速演进，一个自然的问题浮现：CUDA 的替代方案在哪里？为什么还没有另一种方法解决这些问题？在第 5 篇中，我们将探讨最主要的替代方案，审视阻碍它们突破 CUDA 护城河的技术与战略问题。🚀
