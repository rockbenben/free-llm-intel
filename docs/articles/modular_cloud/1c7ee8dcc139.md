# 2026 年 LLVM 开发者会议上的Modular

迈克尔·邓恩-奥康纳

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a82c/6aeb932a7c8fed75ff9caae5_LLVM-CoverImg.jpeg)

社区

Modular 最近在加利福尼亚州圣克拉拉举行的 [2026 LLVM 开发者会议](https://llvm.swoogo.com/2026devmtg/agenda) 上度过了三天（10 月 26 日至 28 日），在那里我们举办了全天的 MAX 和 Mojo 研讨会，进行了有关设备图的技术演讲，并在走廊和我们的展位上与 LLVM 社区的人们进行了交谈。这是我们第一次从头到尾分享整个 Modular 堆栈的详细信息，[所有源代码可供与会者遵循](https://www.modular.com/blog/max-license)。我们展示了 Mojo 语言的内部架构、如何跨堆栈使用 MLIR，以及如何使用图形编译器对 Mojo 进行分层等主题。这篇文章涵盖了我们介绍的内容、我们听到的内容以及我们未来的合作前景。

Mojo 和 MAX 研讨会海报

## 研讨会：Mojo 内部深入探讨和路线图

10 月 26 日星期一，我们举办了“Mojo：内部深入探讨和路线图”，这是一个面向熟悉 LLVM 和 MLIR 的编译器工程师的全天会议。目标是向观众提供 Mojo 构建方式的工作图，从编译器和类型系统到 GPU 后端和标准库。尽管有这个名字，但这不仅仅是 Mojo 上的一次会议。我们在 Mojo 提供的基础上构建了 MAX，因此我们还介绍了 MAX 如何针对新的加速器硬件，以及它如何为复杂的 AI 模型编译和优化计算图。 [新提供的源代码](https://www.modular.com/blog/max-license) MAX 让我们首次展示了整个 Modular 堆栈如何协同工作。

Mojo 是基于 MLIR（[LLVM 的一个子项目](https://mlir.llvm.org/)）构建的，因此活跃用户和贡献者对这种语言有独特的看法，尽管许多人对 Mojo 和 MAX 是陌生的。与一般观众相比，我们能够更深入地了解 Mojo 和 MAX 的内部结构。不幸的是，LLVM 研讨会没有记录，但幻灯片如下。

### 每个演讲涵盖的内容

- [Mojo 在 LLVM 生态系统中的地位](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-LLVM-Ecosystem.pdf)**.** Billy Zhu、Lukas Hermann 和 Weiwei Chen 将 Mojo 定义为加速器 MLIR 上面向用户的层，其中硬件专业化由领域专家的库执行可以编写，而不是锁定在编译器或供应商二进制文件中。 Mojo 为程序员提供了直接 MLIR 和 LLVM IR 访问的全部功能，充当 AI 的统一 LLVM 风格层。
- [Mojo 编译器架构概述](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-Compiler-Architecture.pdf)**.** Billy Zhu 和 Weiwei Chen 深入研究了 Mojo 编译器基于 MLIR 的独特设计。他们讨论了 Mojo 解析器如何在没有 AST 的情况下直接发出参数化 MLIR，并延迟解析声明。他们还介绍了阐述器如何异步具体化通用代码，以及插件系统如何允许在不分叉整个编译器的情况下添加新的后端。
- [插件架构：将编译器和 SDK 与特定于硬件的部分分离](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Making-New-Hardware-Boring.pdf)**.** Connor Gray 展示了 Modular 如何通过可编程插件创建可移植且高性能的 AI 堆栈。任何人都可以通过实现简单的 Mojo `PluginHooks` 和 `MaxPluginHooks` 特征来扩展标准库和 MAX 加速器库，为新硬件提供优化支持。这些插件非常简洁，Qualcomm Cloud AI 100的后端只有263行。完整的插件架构将使插件能够将整个Modular堆栈引入新硬件，这是[Modular硬件联盟](https://www.modular.com/alliance)的关键技术推动者。
- [价值所有权、生命周期和起源：Mojo 的内存安全模型](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-Ownership.pdf)**.** Chris Lattner 解释了 Mojo 起源系统的优点：无需垃圾收集器的内存安全、系统级控制以及在需要时逃逸到不安全的 API。一般来说，程序员在定义返回引用的 API 之前不必考虑引用。编译器检查生命周期并在最后一次使用后立即销毁每个值，这提供了更小的捕获集、更多的尾部调用和复制到移动优化，以及与类型系统的其余部分组合的线性类型。
- [Mojo 如何支持非 LLVM 后端（TPU 和 Trainium）](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-How-Mojo-Supports-Non-LLVM-Back-Ends.pdf)**.** Kolya Panchenko 解释了为什么 TPU 和 Trainium 是难以通用的硬件后端语言。他们期望类型化、平铺式、结构化的代码，而 Mojo 没有“memref”类型。第一个里程碑是用 Mojo 编写的矢量添加，可编译为 TPU 的 Mosaic MLIR。
- [MAX 图形编译器和内核融合背后的 MLIR 方言](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-Graph-Compiler.pdf)**.** Feras Bouulala 在整个 MAX 管道中演示了 RMS 范数示例。一路上，他展示了每个阶段应用的优化以及使 MAX 在模型调试方面脱颖而出的功能，包括 Python 堆栈跟踪和跟踪。
- [我们如何在 Mojo 中编写 Mojo](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-How-We-Write-Mojo-in-Mojo.pdf)**.** Joe Loser 和 Nathan Ward 在 MLIR 中从头开始构建了一个“Int”，然后展示了如何以相同的方式构建 Mojo 标准库中的类型。一些叶子类型包装 MLIR（如 Bool、SIMD 和 Pointer），然后使用这些叶子在 Mojo 中构建其他类型。
- [案例研究：抽象硬件细节的元编程](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-Metaprogramming-Magic.pdf)**.** Kern Handa 描述了在 64 位主机后面启动 32 位设备。该案例研究详细介绍了三个问题（固定的 C 入口点、将参数打包到灵活的数组中以及序列化闭包），每个问题都通过 Mojo 库代码解决。克恩 (Kern) 演示了如何开发加速器主要是图书馆的工作。

## 技术讲座：超越记录和重放

10 月 28 日星期三，我们图形执行团队的 Spenser Bauman 介绍了 [超越记录和重播](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-Roadmap-Compiler-first-device-graph-synthesis.pdf)，这是一个在编译器中构建设备图的案例，例如里面的例子MAX，而不是在运行时捕获它们。如果您不熟悉，CUDA 和 HIP（以及其他加速器）都提供了一种将操作图发送到加速器的方法，而不是单独发送每个操作。

随着 GPU 变得越来越快，CPU 到加速器的通信成本也会增加，直到占用大部分推理时间。设备图通过立即向设备提交整个工作序列来解决这个问题。 MAX 使用它们，每个广泛使用的服务堆栈也是如此。构建命令的通常方法是记录和重放：在运行时捕获命令流，然后重放它。 CUDA 和 HIP 都提供此功能。

斯宾塞指出了这种方法的两个问题：

- 记录和重放将复杂性分散到图形执行器、异步运行时、内存池、内核和驱动程序中。
- 这取决于并非每个供应商都提供的捕获模式。一些加速器公开了设备图或命令缓冲区构造 API，但没有等效的记录和重放，这使得它们超出了基于捕获的堆栈的范围。

Modular 正在寻求的替代方案是使用图形编译器直接构建这些设备图。 MAX 中的图形编译器已经知道最终设备图形的基本结构，而不是捕获然后重放图形。图形编译器可以构建设备图并发出对目标的图形构建 API 的直接调用。演讲讨论了该设计的四个部分：

- 内核如何声明其设备图功能。
- 前端 IR 标记具有设备图功能的区域。
- 对设备图进行建模的中端方言和操作。
- 用于使用它们的 Mojo 级 API。

该方法已经在实践中发挥作用。生产 Gemma 4 模型现在通过一个或多个 GPU 上的设备图合成来端到端运行，并且单个模型可以包含多个设备图区域。直接构建图表比记录图表快约 40%。 CUDA、HIP 和 Qualcomm AI100 都有“DeviceGraphBuilder”实现，所有这些都位于一个接口后面，因此相同的方法可以扩展到新的目标。

## 接下来会发生什么

研讨会以 Mojo 路线图和贡献邀请结束。

[**Roadmap**](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-Roadmap.pdf)**.** Denis Gurchenkov 概述了 Mojo 语言功能对于内核编程的近期优先级（枚举和模式匹配、更多编译时元编程、地址空间等硬件概念的语法）以及长期目标到 2027 年，开发人员将能够编写高性能 CPU 代码，并进行必要的异步/等待、动态调度、线程和网络开发。在编译器方面，计划是提供 GPU 和 NPU 后端源，支持可插拔 MLIR 和 LLVM 后端，启用 WASM 后端，并继续提高编译速度。工具和社区项目包括自动 Mojo 和 C 互操作性、调试器、测试框架、基于 pixi 构建的包管理器以及基于 Bazel 的构建系统。

[Modular 的开源之旅](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Modulars-Open-Source-Journey.pdf)**.** Brad Larson 和 Joe Loser 追溯了 Mojo 和 MAX 三年的渐进开源历程，从 [2017 年 3 月的 Mojo 标准库] 开始。 2024 年，](https://www.modular.com/blog/the-next-big-step-in-mojo-open-source)一直到几周前[开源 Mojo](https://www.modular.com/blog/mojo-open-source) 和[使 MAX 完全可用](https://www.modular.com/blog/max-license)。整个Modular堆栈现在是从公共“modular/modular”存储库（现在拥有超过 30,000 个 GitHub star！）构建的，这是一个非常令人兴奋的里程碑。我们在开源 Mojo 和 MAX 的过程中也学到了很多经验教训，我们将在本次演示中对此进行介绍。

随着 Mojo 和 MAX 的所有源代码现已公开，该团队给与会者留下了一条信息：请[克隆](https://github.com/modular/modular)[`modular/modular`](https://github.com/modular/modular)[存储库](https://github.com/modular/modular)，从源代码构建 Mojo 和 MAX，并尝试扩展平台。查看[Mojo 的贡献者指南](https://github.com/modular/modular/tree/main/Mojo/docs/contributing) 以及[MAX 的新添加指南](https://github.com/modular/modular/tree/main/max/docs/contributing)，并了解在何处以及如何对两者进行上游修复和添加。

Modular（和高通）是 LLVM 基金会活动的长期支持者，对此感到自豪，今年尤其特别：我们终于让每个人都回到了我们的工作幕后，并很高兴看到社区将构建什么。
