# Modular 在 LLVM Developers' Meeting 2026 上

Michael Dunn-OConnor

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a82c/6aeb932a7c8fed75ff9caae5_LLVM-CoverImg.jpeg)

社区

Modular 最近在加州圣克拉拉参加了为期三天的 [2026 LLVM Developers' Meeting](https://llvm.swoogo.com/2026devmtg/agenda)（10 月 26 日至 28 日）：我们办了一场全天的 MAX 和 Mojo 工作坊，做了一场关于 device graph 的技术演讲，还在走廊里、展台前和 LLVM 社区的朋友们聊了很多。这是我们第一次能完整分享整个 Modular 技术栈的细节，与会者可以[拿到全部源码跟着看](https://www.modular.com/blog/max-license)。我们展示了 Mojo 语言的内部架构、我们如何在整个技术栈中使用 MLIR，以及我们如何用图编译器把 Mojo 分层组合起来，等等。本文介绍我们讲了什么、听到了什么，以及我们看到了哪些后续合作的机会。

Mojo 和 MAX 工作坊海报

## 工作坊：Mojo 内部机制深入解析与路线图

10 月 26 日（周一），我们举办了“Mojo：Internals Deep Dive and Roadmap”全天专场，面向熟悉 LLVM 和 MLIR 的编译器工程师。目标是让这批听众对 Mojo 是如何构建起来的有一张可用的地图：从编译器和类型系统，到 GPU 后端和标准库。这场专场尽管名字里只有 Mojo，却并不只讲 Mojo。MAX 构建在 Mojo 提供的基础之上，所以我们也讲了 MAX 如何支持新的加速器硬件，以及它如何为复杂的 AI 模型编译和优化计算图。[刚刚开放源码](https://www.modular.com/blog/max-license)的 MAX 让我们第一次能够展示整个 Modular 技术栈是如何协同工作的。

Mojo 构建在 MLIR（[LLVM 的子项目](https://mlir.llvm.org/)）之上，因此这批活跃用户和贡献者对这门语言有着独特的视角，尽管其中很多人是第一次接触 Mojo 和 MAX。我们得以比面向普通听众时更深入地讲解 Mojo 和 MAX 的内部机制。遗憾的是，LLVM 工作坊不做录像，不过幻灯片附在下面。

### 各场演讲的内容

- [Mojo 在 LLVM 生态中的位置](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-LLVM-Ecosystem.pdf)**。**Billy Zhu、Lukas Hermann 和 Weiwei Chen 把 Mojo 定位为加速器场景下 MLIR 之上的用户层：硬件特化由领域专家能够编写的库来完成，而不是锁死在编译器或厂商的二进制里。Mojo 赋予程序员直接访问 MLIR 和 LLVM IR 的全部能力，充当面向 AI 的统一 LLVM 风格层。
- [Mojo 编译器架构概览](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-Compiler-Architecture.pdf)**。**Billy Zhu 和 Weiwei Chen 深入讲解了 Mojo 编译器独特的、基于 MLIR 的设计。他们讨论了 Mojo 解析器如何直接产出参数化 MLIR、完全没有 AST，以及如何惰性解析声明。他们还介绍了 elaborator 如何异步地把泛型代码具体化，以及插件系统如何让新增后端无需 fork 整个编译器。
- [插件架构：把编译器和 SDK 与硬件相关的部分分开](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Making-New-Hardware-Boring.pdf)**。**Connor Gray 展示了 Modular 如何通过可编程插件构建一个可移植、高性能的 AI 技术栈。任何人都可以通过实现简单的 Mojo `PluginHooks` 和 `MaxPluginHooks` trait，为标准库和 MAX 加速器库加上对新硬件的优化支持。这些插件很精炼，Qualcomm Cloud AI 100 的后端只有 263 行。完整的插件架构将让插件能把整个 Modular 技术栈带到新硬件上，这是 [Modular 硬件联盟](https://www.modular.com/alliance)的关键技术使能项。
- [值的所有权、生命周期与 origin：Mojo 的内存安全模型](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-Ownership.pdf)**。**Chris Lattner 解释了 Mojo 的 origin 体系带来的好处：不靠垃圾回收也能有内存安全、系统级控制能力，以及在需要时可以逃生到 unsafe API。一般来说，程序员直到要定义返回引用的 API 时才需要操心引用。编译器会检查生命周期，并在每个值最后一次使用之后立刻销毁它，由此带来更小的捕获集合、更多的尾调用与 copy-to-move 优化，以及与类型系统其余部分可组合的线性类型。
- [Mojo 如何支持非 LLVM 后端（TPU 和 Trainium）](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-How-Mojo-Supports-Non-LLVM-Back-Ends.pdf)**。**Kolya Panchenko 解释了为什么 TPU 和 Trainium 对一门通用语言来说是很棘手的硬件后端。它们要求类型化、分块（tiled）、结构化的代码，而 Mojo 没有 `memref` 类型。第一个里程碑是用 Mojo 写一个 vector add，并编译成给 TPU 用的 Mosaic MLIR。
- [MAX 图编译器与 kernel 融合背后的 MLIR dialect](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-Graph-Compiler.pdf)**。**Feras Boulala 用一个 RMS-norm 的例子走完了整个 MAX 流水线。沿途他展示了各个阶段所应用的优化，以及让 MAX 在调试模型时与众不同的特性，包括 Python 堆栈跟踪和 tracing。
- [我们如何用 Mojo 写 Mojo](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-How-We-Write-Mojo-in-Mojo.pdf)**。**Joe Loser 和 Nathan Ward 在 MLIR 里从零构建了一个 `Int`，然后展示了 Mojo 标准库里的类型是如何以同样的方式构建的。少数叶子类型包装 MLIR（比如 Bool、SIMD 和 Pointer），其余类型则用这些叶子在 Mojo 中构建。
- [案例研究：把硬件细节抽象掉的元编程](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-Metaprogramming-Magic.pdf)**。**Kern Handa 讲述了在 64 位主机背后 bring up 一块 32 位设备的过程。这个案例拆解了三个问题（固定的 C 入口点、把参数打包进 flexible array、以及序列化闭包），每个都用 Mojo 库代码解决。Kern 演示了：bring up 一个加速器，大部分工作其实是库的工作。

## 技术演讲：超越 Record & Replay

10 月 28 日（周三），我们 Graph Execution 团队的 Spenser Bauman 作了题为[超越 Record & Replay](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-Roadmap-Compiler-first-device-graph-synthesis.pdf)的演讲，主张在编译器中构建设备图（比如 MAX 内部的那个），而不是在运行时捕获它们。如果你还不熟悉：CUDA 和 HIP（以及其他加速器）都提供了一种手段，可以把一整张操作图发给加速器，而不是逐个发送每个操作。

随着 GPU 越来越快，CPU 与加速器之间的通信开销会不断增长，直到占掉推理时间的很大一部分。设备图通过一次性把整个工作序列提交给设备来解决这个问题。MAX 用设备图，所有广泛使用的推理服务栈也都用。构建设备图的常见做法是 record and replay：在运行时捕获一串命令流，然后回放。CUDA 和 HIP 都提供了这种能力。

Spenser 指出了这种做法存在的两个问题：

- record and replay 会把复杂度摊到图执行器、异步运行时、内存池、kernel 和驱动上。
- 它依赖一种并非所有厂商都会提供的捕获模式。有些加速器提供了构建设备图或 command buffer 的 API，却没有等价的 record and replay 能力，这就把它们挡在了基于捕获的技术栈之外。

Modular 正在走的另一条路，是用图编译器直接构建这些设备图。图编译器无需先捕获再回放：MAX 内部的图编译器本来就掌握最终设备图的基本结构，可以直接构建设备图，并向目标平台的图构建 API 发出直接调用。演讲梳理了这个设计的四个部分：

- kernel 如何声明自己具备的设备图能力。
- 标记出具备设备图能力的区域的前端 IR。
- 用来对设备图建模的中端 dialect 与操作。
- 在 Mojo 层面使用这些能力的 API。

这套方案已经在实践中跑通了。一个生产环境的 Gemma 4 模型现在可以在一个或多个 GPU 上、端到端地走设备图合成流程运行，单个模型也可以包含多个设备图区域。直接构建图比录制图快约 40%。CUDA、HIP 和 Qualcomm AI100 都已有 `DeviceGraphBuilder` 实现，统一在同一个接口之后，因此同样的方案可以扩展到新的目标平台。

## 接下来是什么

工作坊以 Mojo 路线图和对大家参与贡献的邀请收尾。

[**路线图**](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Mojo-Roadmap.pdf)**。**Denis Gurchenkov 概述了近期的重点：面向 kernel 编程的 Mojo 语言特性（枚举与模式匹配、更多编译期元编程、地址空间等硬件概念对应的语法），以及 2027 年更长远的目标——触达编写高性能 CPU 代码的开发者，为此需要开发 async/await、动态分发、线程和网络能力。在编译器一侧，计划是让 GPU 和 NPU 后端开放源码、支持可插拔的 MLIR 和 LLVM 后端、启用 WASM 后端，并持续提升编译速度。工具与社区方面的项目包括 Mojo 与 C 的自动互操作、调试器、测试框架、基于 pixi 的包管理器，以及基于 Bazel 的构建系统。

[**Modular 的开源之旅**](https://github.com/modular/devrel-extras/blob/main/slides/2026/LLVM-Dev-Mtg-2026-Modulars-Open-Source-Journey.pdf)**。**Brad Larson 和 Joe Loser 回顾了三年间 Mojo 和 MAX 逐步开源的过程：从 [2024 年 3 月的 Mojo 标准库](https://www.modular.com/blog/the-next-big-step-in-mojo-open-source)，一直到几周前的[开源 Mojo](https://www.modular.com/blog/mojo-open-source) 和[让 MAX 完全开放源码](https://www.modular.com/blog/max-license)。现在整个 Modular 技术栈都可以从公开的 `modular/modular` 仓库构建（该仓库现在已有超过 30,000 个 GitHub star！），这是一个极其令人振奋的里程碑。在 Mojo 和 MAX 开源的过程中，我们也吸取了很多教训，这次演讲里都有涉及。

既然 Mojo 和 MAX 的全部源码现在都已公开，团队留给与会者的信息只有一句话：请[克隆](https://github.com/modular/modular)[`modular/modular`](https://github.com/modular/modular)[ 仓库](https://github.com/modular/modular)，从源码构建 Mojo 和 MAX，并试着扩展这个平台。也请看看 [Mojo 的贡献者指南](https://github.com/modular/modular/tree/main/Mojo/docs/contributing)，以及[新增的 MAX 指南](https://github.com/modular/modular/tree/main/max/docs/contributing)，了解你可以从哪些地方、以什么方式把两者的修复与新增内容贡献回上游。

Modular（以及 Qualcomm）是 LLVM Foundation 活动的长期支持者，对此我们深感自豪；今年尤其特别：我们终于把幕后的工作完整展示给了大家，也很期待看到社区将构建出什么。
