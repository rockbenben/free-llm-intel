# 为什么 LLM 推理需要一种新型路由器 - 第 1 部分

HTTP 路由多年来一直是个已解决的问题。轮询、一致性哈希、最少连接——任选其一，放在一组完全相同的服务器前面，流量就会相当均匀地分散。

但随后大语言模型来了。

这里的后端不是可互换的 web 服务器，而是持有大型本地 KV cache 的 GPU pod，这些 KV cache 存放在高带宽的 RAM 或 SSD 中。这类状态的重建代价高昂，在集群里并非处处可用，而且往往决定了一个请求是快速返回，还是花几秒重算之前的工作。有些 pod 可能专精 prefill，另一些专精 decode。一次对话通常横跨多个请求，单次推理调用有时需要两个后端依次配合。关于"可互换后端"和"独立请求"的旧假设，无法支撑这些需求。

缓存路由：盲目 vs 感知

传统路由对这一切视而不见。它把每个后端当作可互换、每个请求当作独立、每个 pod 当作同样合适。而 GPU pod 三者都不是：它们有状态、各有专长、彼此异构。推理路由必须把这点考虑进去。

这是三部曲系列的第一篇，谈的是路由要变成什么才能处理推理工作负载。Modular Cloud 的编排层正是围绕这个路由问题构建的，本系列会解释它如何解决。

## 多年的无状态路由

HTTP 时代的负载均衡建立在一小套算法之上，每种算法都为某种特定部署形态调校。它们策略不同，但共享同一个前提：无状态后端。

经典路由策略

**轮询（Round-robin）**把请求均匀分发到一组完全相同的后端。它假设每个后端服务每个请求的成本相同。这可以想象成负载均衡器后面八份同一个 web 服务的副本，各拿 12.5% 的流量。简单、公平、无状态。

**一致性哈希（Consistent hashing）**对请求的某个属性（键、URL、会话标识）做哈希，把每个请求路由到哈希环上位置最接近的后端。当你希望同一个键始终落到同一个后端时——客户端缓存或会话亲和——它就是首选路由策略。后端的"粘性"是请求键的函数，而非后端内存里持有什么的函数。

**最少请求（Least-requests）**把每个新请求发往当前活跃请求最少的后端，假设活跃请求越少意味着余量越大。它在每个请求工作量大致相当时有效。

这些策略共享三条同样的假设：

- 任何后端都能服务任何请求。分配是一个策略选择，而非正确性选择。
- 请求是独立的。第 N 个请求发生了什么，不会改变第 N+1 个请求该怎么处理。
- 后端是可互换的。负载均衡器可以换一个而客户端不会察觉。

这些假设对无状态 web 服务成立。LLM 推理把三条全打破了。

## LLM 在哪里打破了模型

LLM 工作负载在四个具体方面违反了无状态假设。每一个都引入了传统路由无从处理的一个维度。

### KV 缓存状态

KV 缓存状态：同一个 prompt，80 倍的延迟差距

当一个 pod 服务一个推理请求时，前向传播会构建一个 KV cache：模型对每个 token 位置的中间状态，存放在 GPU 内存里。现代引擎在响应完成后会保留这份 cache，以便后续共享同一前缀的请求可以跳过相应的计算。

这极大改变了路由问题。一个 10 万 token 的 prompt 落到一个已缓存前 7.5 万 token 的 pod 上，可以在毫秒内完成 prefill；同一个 prompt 打到一个冷 pod 上则要几秒。对缓存状态视而不见的轮询，会让相同请求的首 token 时间（TTFT）不可预测。

在规模化场景下，缓存状态是 prefill 延迟差异的首要驱动因素。一个根据缓存驻留情况来挑选 pod 的路由器，每次命中都能消除与共享前缀长度成正比的 prefill 计算。这腾出了集群本会花在重算已完成工作上的 GPU 周期。

### 硬件专业化

LLM 推理有两个阶段，它们对硬件的压力不同。

prefill 与 decode pod

Prefill 并行处理整个 prompt，是计算受限型：GPU 核被密集[矩阵乘法](https://www.modular.com/blog/matrix-multiplication-on-nvidias-blackwell-part-1-introduction)占满，一次对上千个 token 做运算。

Decode 逐个自回归地生成 token，每个 token 依赖它之前的所有 token，是内存带宽受限型：这意味着 GPU 大部分时间花在从高带宽内存（HBM）取模型权重和 KV cache，大部分计算单元闲置。

把两个阶段跑在同一个 pod 上，意味着硬件对哪个阶段都没调优到位。Prefill 需要密集计算，decode 需要内存带宽。为其中一个优化的 pod，会浪费另一个所需的东西。解耦式部署会为每个阶段分别调优 pod，而单个客户端请求要把工作分给两者。

现代引擎用分块 prefill 把两个阶段交错在同一 pod 上，模糊了这条边界。但计算 vs 带宽的根本差异仍然成立，而当你在部署层面做解耦时，路由器必须知道哪个 pod 能做什么。

### 对话连续性

多轮对话与会话亲和

多数 LLM 流量是多轮的。用户发一条消息，助手回复，用户再发一条——而这条消息隐式地包含了整段对话历史作为上下文。

第 N+1 轮与第 N 轮共享一个前缀：系统 prompt、所有先前轮次、所有先前的助手回复。如果第 N 轮的 KV cache 仍驻留在某个 pod 上，那么第 N+1 轮共享部分的 prefill 实际上是免费的。如果 cache 已被逐出，或者第 N+1 轮落到了另一个 pod，共享前缀就得从头重算。

HTTP 里的会话亲和过去意味着"把这个用户的请求路由到同一后端，好让应用能用内存里的状态"。在 LLM 推理里含义相同，只不过那个内存状态是 KV cache。做得对不对，决定了从第一轮之后每一轮是亚秒级响应还是多秒级响应。

### 多步执行

prefill → decode 流程

单个面向客户端的请求可能需要多个后端。

在解耦式部署中，prefill pod 构建 KV cache，decode pod 生成 token，谁都无法单独服务请求。路由器先选一个 prefill pod，再选一个 decode pod，然后编排整个序列：把 prompt 发给 prefill，等待完成，把同一个 prompt 加上缓存提示发给 decode，再把 token 流式返回给客户端。

HTTP 负载均衡器不这么做。它们为每个请求只选一个后端。给单分发路由加上多步协调，是另一种完全不同形态的路由。

## 三层

上面四个维度中的每一个都对路由系统提出要求。这些要求落在三个不同的架构关注点上，各由一个独立层处理。

三层路由

### 数据层

这一层以路由决策所需的延迟追踪 LLM 特有的状态。"N 个 pod 里哪些缓存了这些 block？"必须在微秒内可答、能承受并发更新、对 pod 频繁更替保持韧性。一个加锁的哈希表并不够用。

### 决策层

这一层把路由逻辑表达为小型、可测试、可复用组件的组合。运维人员选一个 filter、几个 scorer、一个 picker，组装成一个 profile。框架在构建期校验这个组合，而不是在凌晨三点的流量下。

### 执行层

这一层在决策层之上协调多步请求流程。单分发路由是多步的退化情形：一个 pod、一个步骤。解耦的 prefill/decode 是一般情形：两个 pod、两个步骤，第二个决策受第一个影响。同一个框架能处理两者，而无需为每个变体新增一个 HTTP 处理器。

本系列的第 2、3 部分会构建这些层。

## Modular Cloud 的路由层

本系列描述 Modular Cloud 分布式推理框架内部的路由层，以及它在生产推理工作负载中如何处理上述四个问题。

前缀感知路由（分词、block 级哈希、带负载均衡决胜的缓存感知打分、上游延迟的熔断器）以一个 profile 配置的形式发布，而非一个新算法。当团队需要一种新路由行为时，工作是把插件组合成一个新 profile，而不是从零写一个新路由策略。每一种新部署形态都复用已有组件。

## 结论

LLM 引入了四个传统负载均衡器无从处理的维度：使后端选择成为性能关键决策的 KV cache 状态、把单个请求拆分到不同 pod 类型的硬件专业化、把会话绑定到缓存驻留的对话连续性、以及需要协调一串后端而非只选一个的多步执行。

这个问题已从多个角度被攻克。NVIDIA Dynamo、llm-d、vLLM production-stack、AIBrix、KServe 和 Envoy AI Gateway 各自在不同方向推进了推理路由：解耦的 prefill/decode、前缀感知调度、KV 感知的负载均衡、生产级服务原语。Modular Cloud 建立在那些基础之上。为了支持它所瞄准的多样部署形态，Modular Cloud 把可组合插件和多步执行都作为一等原语，于是新部署形态变成你组装的一个 profile，而不是你 fork 的一个策略。

这正是 Modular Cloud 路由层要填补的空缺：三个架构层，以组合作为扩展模型，而非 fork 或包装。本系列其余部分会展示它如何构建。
