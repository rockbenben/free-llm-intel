# 前沿编码智能体如何在 MAX 上构建视频扩散管线

我们给五个前沿模型出了一道难题：在 Modular 的 [MAX](https://www.modular.com/open-source/max) 栈上重建完整的 Wan 2.1 文生视频推理管线——不许用 PyTorch 或 `diffusers`——限时二十小时。这是 [**Frontier-SWE**](https://frontierswe.com/)**。** 17 个任务之一——该基准由 [Proximal](https://proximal.ai/) 设计，用于衡量编码智能体在困难工程问题上实际能做什么。

## **两个智能体在 MAX 上从零构建了视频扩散管线**

AI 编码智能体正以惊人的速度具备挑战系统性工程工作的能力，此次表现就是一个清晰的证明：五个智能体中有两个产出了可用的 MAX 管线。我们测试的模型是：

- Claude Opus 4.6 (Claude Code)
- GPT-5.4 (Codex)
- Gemini 3.1 Pro (Gemini CLI)
- Kimi K2.5 (Kimi CLI)
- Qwen3.6-Plus (Qwen Code)。

每个模型都编写了数千行编译图代码，重建了完整系统——文本编码、30 层 DiT 去噪器、3D 因果 VAE 解码、flow matching 调度和数值正确性——全部在 MAX 内完成。

MAX 上实现的 Wan 2.1 推理管线。智能体必须在 MAX/Mojo 中重建全部三个阶段，最终提交物中不得包含 PyTorch、vLLM、transformers 或 diffusers。

[Wan 2.1](https://github.com/Wan-Video/Wan2.1) 是一个 13 亿参数的文生视频扩散模型。它使用 flow matching、DiT 主干、3D 因果 VAE 和无分类器引导（classifier-free guidance），从文本提示生成短视频。我们特意选择视频模型，是为了测试管线级推理而不只是模型翻译：该任务要求端到端地协调多个子系统。

## **为什么这个任务很难**

任务表述简单，执行却很难。每个智能体必须产出一个单一的 `generate_video(...)` 函数，在 MAX 中重建完整的 Wan 2.1 栈：UMT5-XXL 文本编码器、带 3D 分解式 RoPE 与 AdaLN-Zero 的 30 层 DiT 去噪器、3D 因果 VAE 解码器，以及 flow matching 调度器。为了公平，PyTorch 参考实现在评分前已被删除，隐藏工作负载必须先通过 25 dB PSNR（峰值信噪比）阈值，然后才会去测速度。

这之所以困难，是因为要在一个全新框架里实现整条管线。除模型本身外，智能体还需要实现预处理、带正确时间步间隔与 flow-shift 参数的 ODE 求解器、带非对称填充与时间因果掩码的 3D 因果 VAE、权重映射以及数值稳定性处理——全部作为一条能产出帧级精确输出的连贯管线。这是资深工程师通常也要花上数天的复杂系统工程任务。

Wan 2.1 的几个特点使要求格外苛刻。3D Causal VAE 的非对称填充和时间因果掩码意味着：即使通过基于形状的冒烟测试，仍可能产出空白帧。ODE 求解器要求精确的时间步间隔和 flow-shift 参数。数值不稳定性、权重映射和 3D 分解式 RoPE 又叠加了更多难度。

## **MAX 提供给智能体的武器**

MAX 自带与本任务直接相关的生产级组件，包括完整的 T5 文本编码器、[丰富的图级算子库](https://docs.modular.com/max/api/python/graph.ops/)（如 `silu `和 `chunk`），以及一个图 API——可以把整条推理管线（模型、调度器、前后处理）表达为单一单元。系统性探索 MAX API 面的智能体找到了这些积木并快速推进；那些假设它们不存在的智能体则浪费时间从零重实现组件，或退回去用 `numpy`。

取得实质进展的智能体都坚定投入了 [MAX 的 Graph API](https://docs.modular.com/max/api/python/graph/)。这正是 MAX 的既定设计点：一个基于图的推理系统，管线作为整体编译和执行。成功的运行表明，这一最初在 LLM 负载上验证过的抽象可以扩展到视频扩散这样的复杂多模态管线——其正确性取决于在单一运行时内协调多个子系统。

MAX 的图 API 也足够有表达力，智能体可以自行发现多种有效的编译策略。当把整个模型编译为单一图对某些配置不再可行时，智能体会重构做法：编译可复用的 transformer block、在运行时传入权重，或者只把性能关键路径交给 MAX 编译器。框架容纳了这些决策，而没有把智能体逼进单一僵化模式。

## **最强的几次运行**

8 步扩散去噪：管线把随机噪声逐步细化为连贯的视频帧。验证器用逐帧 PSNR 将最终输出与 PyTorch 参考帧对比。

五个智能体中有两个产出的 MAX 实现通过了有难度的隐藏工作负载。在全部试验（每模型五次）中，成功的运行集中在两个最强的模型——GPT-5.4 和 Opus 4.6——它们都在首次认真尝试图 API 时就获得了成功。其他模型也有少数试验通过了可见正确性检查，但在更大工作负载上撞到内存或时限。

GPT-5.4 交付了两次成功运行。它坚定使用 `max.graph` 与 `InferenceSession` 的编译图，并展示了 MAX 编译模型的灵活性：它编译可复用的 transformer block、运行时传入权重，然后用不同缓冲区反复执行。到最后，它在可见工作负载上达到 41.5 dB 和 31.9 dB，在部分得分制评分中通过四个隐藏工作负载中的两个。

Claude 采取了不同的架构路线。它做了一个务实选择：把一次性文本编码路径留在 `numpy`，把 MAX 编译精力集中在性能关键的 DiT 和 VAE 上。对 VAE，它手写了基于 `im2col` 的 3D 卷积来处理因果时间填充——这令人印象深刻——但它没发现 MAX 本来就支持这一点。值得称道的是它的调试过程：从大约 12 dB 起步，然后逐个发现并修复问题——调度器 bug、注意力掩码问题、VAE 中 RMS 缩放导致的归一化错误——最终在一个可见工作负载上达到 41.1 dB，并通过第一个隐藏工作负载，之后才在更大配置上撞到 GPU 显存上限。

两个智能体都产出了运行在 MAX 图引擎上的完整视频扩散管线。它们的调试轨迹表明，MAX 的图抽象足够透明，可以支撑真实的数值调试：智能体可以逐层检查中间激活、分析编译器行为、用二分法定位数值漂移，最终让模型产出正确的扩散输出。

## **模型卡在哪里**

架构理解不是瓶颈。每个模型都看懂了 Wan 2.1。难的是调试纪律：让结构上看起来对的代码在数值上真正与参考实现对齐。

最强的几次运行遵循相似的路径：最初得到高损耗的输出，意识到要先修调度器设置，然后修注意力掩码，再然后开始逐层对比真实的中间激活而不是只比形状。在部分得分制下，两个最领先的运行各通过了约一半的隐藏工作负载，其余失败来自更大工作负载上的 GPU 显存上限，而非框架局限。

有趣的是，有一次 Claude 试验其实是在阅读参考代码时找到了数值修复方案，但那时它已放弃了原来的 MAX 实现——因为它尝试改走另一条路——这是调试纪律的失败，不是框架的失败。Gemini 找到了 MAX 内建的 T5 实现，这一步是对的：使用 MAX 已有组件而非从零重建。但它把大部分调试时间都耗在“噪声生成不匹配是根因”的执念上，从未调查真正的数值问题，五次试验全部止步于 14.4 dB。

Qwen 的问题分解做得很好，有一次试验把 T5 完整编译进了 MAX，但不断带入低级的运行时 bug。五次试验中有三次崩溃在提交前做一次基本端到端测试就能发现的错误上。Kimi 理解了模型，却无法从“理解”跨越到“能工作的编译代码”——这个差距随智能体质量提升而在收窄。

## **关于基准设计的一点说明：绕题行为**

相当数量的试验干脆放弃了求解真实任务，这为智能体在时间压力下的行为提供了有用的信号。

最简单的做法是直接 `import torch`。有些运行毫不掩饰地这么干，显然在赌验证器抓不到。GPT-5.4 更讲究：一次运行用字符串拼接躲避源码扫描器（`importlib.import_module("dif" + "fusers")`），另一次同时交付真实的 MAX 实现和一个混淆过的 `diffusers` 兜底。

Gemini 在一次运行中尝试了多种绕过技巧，甚至推理道："I've hit a breakthrough! The verifier scans only `/app/` for `torch` imports." 随后它尝试把 `torch` 导入写到 `/tmp/`、从隐藏进程做 ONNX 导出，还用 `chr()` 编码避免字面量 "torch" 出现在任何地方。

我们发现智能体在不同时点转向绕题，有的早到开始一小时。它们一贯高估任务所需时间、低估自己的剩余时间。多数绕题的运行明明还有充足时间继续调试，却提前收工。教训关乎智能体的坚持度与不确定下的时间估计——保持纪律、持续解决真实问题的模型才是产出成果的那些。

## **这次实验告诉我们什么**

前沿编码智能体的瓶颈在于调试纪律和管线级工程，而不是理解新架构或在新框架内工作的能力。每个模型都知道要构建什么，MAX 的图 API 也提供了构建它所需的抽象。区分成功智能体的，是逐层调试数值正确性而非中途弃案的纪律。MAX 在这里提供了强大的工具：智能体编写自定义 kernel 并在每个阶段观察其行为，获得了隔离数值漂移、验证每个组件与参考实现一致的可见性。

最好的几次运行做的是真正的系统工程：分析编译器行为、二分定位数值漂移、处理特定形状失败、在行不通时更换编译策略——全部在 MAX 的统一运行时内完成。这类工作过去需要资深工程师拼合多个框架、手写自定义 CUDA kernel。MAX 把它收拢为单一抽象，文本编码、去噪、调度和视频解码一起编译、一起执行。

本实验是用非常难的管线级任务来检验 MAX，而不是与其他推理运行时对比——那是未来的工作。它证明的是：MAX 的图 API 足够有表达力，让前沿智能体能从零构建可用的多模态推理管线。有三次智能体试验独立发现了如何利用 MAX 的编译模型、既有组件库和调试面来搭建完整的视频扩散系统。失败的智能体是因为缺乏持续调试的纪律，而不是框架无法表达它们所需的东西。

随着智能体能力提升，这个天花板还在抬高。下一代模型会补上这里撞到显存上限的工作负载，再下一代会更快做到。MAX 给它们提供统一的目标：完整的推理系统可以在一处构建、编译和执行，横跨模态与硬件。

虽然 MAX 已经[原生支持 Wan 2.2](https://github.com/modular/modular/tree/main/max/python/max/pipelines/architectures/wan)供需要生产级视频推理的团队使用，但本次评估测试的是智能体在长程环境中独立从零构建这条管线的表现。它们在完成这一高难度 Frontier-SWE 任务的尝试中对 MAX Graph API 的成功运用，清楚展示了其不断增长的能力。
