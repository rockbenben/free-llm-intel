# 理解 SIMD：琐碎问题的无限复杂性

Ash Vardanian

工程

‍*这篇客座博客来自 *[*Ash Vardanian*](https://github.com/ashvardanian)*，*[*Unum*](https://www.unum.cloud)* 的创始人。他致力于构建高性能计算与存储系统，这是开源 *[*Unum Cloud 项目*](https://github.com/unum-cloud)* 的一部分。*

现代 CPU 拥有一种惊人的超能力：**超标量操作**，通过单指令多数据（SIMD）并行处理来实现。 一个 *单核* 不用一次只做一种操作，而是能并行做多达 4、8、16、甚至 32 种操作。从某种意义上说，一颗现代 CPU 就像一块迷你 GPU，能执行大量同步计算。然而，正因为写并行操作太棘手，几乎所有的潜力都没被挖掘出来，最终得到的代码一次只做一种操作。

最近，我们四个人——Ash Vardanian（[@ashvardanian](https://x.com/ashvardanian)）、Evan Ovadia（[@verdagon](https://x.com/verdagon)）、Daniel Lemiere（[@lemire](https://x.com/lemire)）和 Chris Lattner（[@clattner_llvm](https://x.com/clattner_llvm)）——聊了聊是什么在阻碍开发者更有效地使用超标量操作，以及我们该如何为 CPU 写出最优软件、创造更好的抽象。

在这里，我们分享多年来在 [SimSIMD](https://github.com/ashvardanian/simsimd) 库里实现 SIMD 内核所学到的东西。该库目前为数十个数据库管理系统（DBMS）产品和 AI 公司驱动向量数学——其软件部署在超过 1 亿台设备上。虽然最早的 SIMD 指令集早在 1966 年就被定义，但和 SIMD 打交道的痛点一直存在：

- **高性能计算实际上是在逆向工程架构细节。**
- **自动向量化不可靠：** 编译器没法可靠地替我们搞定这件事。
- **SIMD 指令很复杂，** 连 Arm 都开始看起来比 x86 更"CISC 化"了！
- **性能不可预测，** 即便是在不同 CPU 之间共享的同一套指令集上。
- **调试复杂：** 没有一个查看寄存器的简单办法。
- **CPU 特定代码很棘手，** 无论是编译期还是动态派发。
- **计算精度不一致，** 不同 CPU 和指令集上的浮点运算皆是如此。

我们来探索这些挑战，以及 Mojo 如何通过实现机器学习里最琐碎却最普及的操作之一来帮忙解决它们：**余弦相似度。** 余弦相似度通过测量两个向量之间的夹角，来计算它们彼此有多接近。

## 余弦相似度简介

你或许会惊讶于余弦相似度有多普及。农业机器人用它来 [每小时用视觉制导的激光电击 20 万株杂草](https://www.youtube.com/watch?v=isl4G_-aTyk)，新的基于 ML 的方法用它来提升气候模型的速度和精度，而几乎每一条 [检索增强生成](https://en.wikipedia.org/wiki/Retrieval-augmented_generation)（RAG）流水线都在用余弦相似度来衡量用户提示词与已有知识库之间的相似度。

下面这张简化示意图说明了 RAG 如何使用余弦相似度。一条语言处理的 ML 流水线把文本转换成向量，这些向量以数字方式捕捉词和句子的含义，相似的向量共享相似的含义。这些有语义的向量叫做嵌入（embedding）。余弦相似度是一种计算嵌入向量之间差异的方式，用来判断它们在语义上是否相似。

测量嵌入距离的简化示例。改编自

Samuel Partee

余弦相似度可以用这段琐碎的 Python 代码来表达，它取两个向量的点积，再除以向量的长度来归一化：

Python

def cosine_similarity(a: list[float], b: list[float]) -> float:
    dot_product = sum(ai * bi for ai, bi in zip(a, b))
    norm_a = sum(ai * ai for ai in a) ** 0.5
    norm_b = sum(bi * bi for bi in b) ** 0.5
    if norm_a == 0 or norm_b == 0: return 1
    if dot_product == 0: return 0
    return dot_product / (norm_a * norm_b)

尽管这个算法很简单，我们还是能从现在这段代码里榨出好几个数量级的性能。在 NumPy 里，同一个算法可以这样实现：

Python

import numpy as np

def cosine_similarity(a: np.ndarray, b: np.ndarray) -> float:    
    a, b = np.asarray(a), np.asarray(b)
    dot_product = np.dot(a, b)
    norm_a, norm_b = np.linalg.norm(a), np.linalg.norm(b)
    if norm_a == 0 or norm_b == 0: return 1
    if dot_product == 0: return 0
    return dot_product / (norm_a * norm_b)

这个 NumPy 实现相对朴素算法有显著提升，但我们还能做得更好！

## **混合精度**

在本文余下部分，我们会用到如今机器学习里最常见的数值类型，`bfloat16` 类型。

`bfloat16` 是一种 16 位浮点数类型，其范围和精度都比 IEEE 标准的 `float32` 类型小得多，因此算起来快得多。它也不同于 IEEE 标准的 `float16` 类型。

bfloat16 与 float32 的对比

令许多人意外的是，`bfloat16` 与 `float32` 之间的互转比 `float16` 容易得多——就是一次位移，因为它的指数占用同样多的位数。这让它在实践中更好用，即便在缺乏原生支持的旧硬件上：只需位移把它转成 `float32`、用一条 `float32` 指令、再位移转回来即可。

尽管我们很喜欢 `bfloat16`，却不该只用它。这个类型引入的不精确会迅速累积，导致结果严重失准。为了应对这点，我们可以在 **同一次计算里混合不同的数值类型。**

例如，向量用 `bfloat16`，乘进 `float32` 累加器，最终 [归一化](https://mathworld.wolfram.com/NormalizedVector.html) 时再上转（upcast）到 `float64`。在 C++23 里它会长这样：

不幸的是，这段代码有几个问题。

首先，C++ 标准 [并不要求](https://en.cppreference.com/w/cpp/header/stdfloat) 定义那些类型，所以并非每个编译器都有它们。**要用这些更快的数据类型写可移植代码，通常需要更多功夫。**

其次，众所周知，即便在这样数据并行的代码里，编译器也很难 [向量化](https://stackoverflow.com/a/1422181) 低精度代码，有时 [高达 99% 的单核性能白白丢掉](https://ashvardanian.com/posts/gcc-12-vs-avx512fp16/)，而混合精度下更糟！**想要可靠的数据并行，你就必须显式地表达。**

最后，双精度除法，加上一个逐位精确的 `std::sqrt` [实现](https://sourceware.org/git/?p=glibc.git;a=blob;f=sysdeps/ieee754/dbl-64/e_sqrt.c;h=017d30416ca9b92cdc87a6cc840ca30791bba558;hb=c064f6a613844181f411aabb2662384a6aefb69e)，会引入若干代码分支，并给小输入带来大量 [延迟](https://cs.stackexchange.com/a/80871)。**用更快的指令可以避免这些。**

为了解决这些问题，我们来用 `rsqrt` 倒数平方根（1/√x）近似，并显式使用 SIMD 内建函数，为每个常见目标平台加速这段代码。

我们先从我 [SimSIMD](https://github.com/ashvardanian/SimSIMD) 库里看几个 C 99 跨平台内核。

### **Intel Haswell 的基线实现**

Intel Haswell 及更新的 x86 CPU 世代都支持 [AVX2](https://dev.to/karapto/what-is-intel-avx2-2cad)，这是一套 256 位的 SIMD 指令集，对应 CPU 上新增的 32 个 YMM 寄存器文件。这让我们一次能做 8 个并行的 `float32` 操作。

上面那个内核专门针对 AVX2 硬件后，大体长这样。

C

void simsimd_cos_bf16_haswell(simsimd_bf16_t const * a, simsimd_bf16_t const * b, simsimd_size_t n, simsimd_distance_t * result) {
    __m256 a_vec, b_vec;
    // Initialize our accumulators, each will have 8 words/scalars.
    __m256 ab_vec = _mm256_setzero_ps(), a2_vec = _mm256_setzero_ps(), b2_vec = _mm256_setzero_ps();

    while (n) {
        // Load the next 128 bits from the inputs, then cast.

        b_vec = _simsimd_bf16x8_to_f32x8_haswell(_mm_loadu_si128((__m128i const*)b));
        n -= 8, a += 8, b += 8;

        // Multiply and add them to the accumulator variables.

        b2_vec = _mm256_fmadd_ps(b_vec, b_vec, b2_vec);

我们会在下面稍后实现那些 `TODO` 块，但你也能在 [simsimd/spatial.h](https://github.com/ashvardanian/SimSIMD/blob/81799b6dd8cf28ac71873db7fec34ed85f381ce8/include/simsimd/spatial.h#L942) 里看到完整的 `simsimd_cos_bf16_haswell` 实现。

这个循环做三件主要的事。

首先，它用 `_mm_loadu_si128` 从一个可能未对齐的内存地址加载 128 位。要小心用这个，而不是 `_mm_load_si128`——后者在向量的地址不能被 16（XMM 寄存器以字节计的大小）整除时会崩溃。

其次，它用 `_simsimd_bf16x8_to_f32x8_haswell` 从 `bfloat16` 转换到 `float32`。它把输入解读为 8 个 16 位整数、把它们转成 32 位整数，然后左移 16 位：

C

__m256 _simsimd_bf16x8_to_f32x8_haswell(__m128i a) {
    return _mm256_castsi256_ps(_mm256_slli_epi32(_mm256_cvtepu16_epi32(a), 16));
}

第三，我们用 `_mm256_fmadd_ps` 把 `a_vec` 的 8 个字与 `b_vec` 的 8 个字相乘，**从而把点积累加** 进 `ab_vec` 的 8 个标量。这是一条融合乘加（FMA）指令，比分别乘、加更快：

Text

| 架构       | `mul` 延迟 | `add` 延迟 | `fmadd` 延迟 |
| :----------------- | ------------: | ------------: | --------------: |
| Intel Haswell      |      5 周期 |      3 周期 |        5 周期 |
| Intel Skylake-X    |      4 周期 |      4 周期 |        4 周期 |
| Intel Ice Lake     |      4 周期 |      4 周期 |        4 周期 |
| AMD Zen4           |      3 周期 |      3 周期 |        4 周期 |

对其中多数指令和 CPU 核设计而言，两个这样的操作可以同时执行。我们每个周期调用 FMA 三次：一次做真正的点积，两次把"平方范数"累加进 `a2_vec` 和 `b2_vec`。

循环之后，我们需要 **水平累加**，也就是把 `ab_vec` 的 8 个字相加，得到一个单一的数。我们来说说怎么做！

#### **削减水平累加**

SIMD 在实践中棘手的一点是 **避免对整个寄存器做水平累加，** 因为那是一种慢操作。

只要可能，累加就该放到循环之外，而这通常需要在寄存器内部做一些洗牌（shuffle）来构成一棵树形归约。

例如，`_simsimd_reduce_f32x8_haswell` 底层可能长这样：

C

simsimd_f64_t _simsimd_reduce_f32x8_haswell(__m256 vec) {
    __m128 low_f32 = _mm256_castps256_ps128(vec);
    __m128 high_f32 = _mm256_extractf128_ps(vec, 1);
    __m256d low_f64 = _mm256_cvtps_pd(low_f32);
    __m256d high_f64 = _mm256_cvtps_pd(high_f32);
    __m256d sum = _mm256_add_pd(low_f64, high_f64);
    __m128d sum_low = _mm256_castpd256_pd128(sum);
    __m128d sum_high = _mm256_extractf128_pd(sum, 1);
    __m128d sum128 = _mm_add_pd(sum_low, sum_high);
    sum128 = _mm_hadd_pd(sum128, sum128);
    return _mm_cvtsd_f64(sum128);
}

在我们的函数里，会这样用它：

C

simsimd_f64_t ab = _simsimd_reduce_f32x8_haswell(ab_vec);
simsimd_f64_t a2 = _simsimd_reduce_f32x8_haswell(a2_vec);
simsimd_f64_t b2 = _simsimd_reduce_f32x8_haswell(b2_vec);

现在，我们有了：

- 一个单一的 `ab` 数，`a` 和 `b` 的点积。
- 一个单一的 `a2` 数，`a` 与自身的点积，即 `a` 的"平方 [范数](https://mathworld.wolfram.com/NormalizedVector.html)"。
- 一个类似的 `b` 的平方范数。

#### **AVX2 里的倒数平方根近似**

我们函数的最后一行会是这个：

C

*result = _simsimd_cos_normalize_f64_haswell(ab, a2, b2);

它需要算 `a` 和 `b` 的点积，除以归一化后的 `a` 和归一化后的 `b`，像这段伪代码这样：

C

*result = ab / (sqrt(a2) * sqrt(b2))

没错：要归一化结果，不是一个，而是 *两个* 平方根。

我们会用 `_mm_rsqrt_ps` 指令。它对双精度浮点不可用，但对单精度浮点仍是很好的选择。我们的函数大概会长这样：

C

simsimd_distance_t _simsimd_cos_normalize_f64_haswell(simsimd_f64_t ab, simsimd_f64_t a2, simsimd_f64_t b2) {
    if (ab == 0) return 0;
    if (a2 == 0 || b2 == 0) return 1;

    __m128d squares = _mm_set_pd(a2, b2);
    __m128d rsqrts = _mm_cvtps_pd(_mm_rsqrt_ps(_mm_cvtpd_ps(squares)));
    
    // TODO: More precision!

    simsimd_f64_t a2_reciprocal = _mm_cvtsd_f64(_mm_unpackhi_pd(rsqrts, rsqrts));
    simsimd_f64_t b2_reciprocal = _mm_cvtsd_f64(rsqrts);
    return ab * a2_reciprocal * b2_reciprocal;
}

然而，`_mm_rsqrt_ps` 指令可能引入高达 `1.5*2^-12` 的误差，正如 Intel 所记录的。

一篇 2009 年的优秀文章 [Timing Square Root](https://web.archive.org/web/20210208132927/http://assemblyrequired.crashworks.org/timing-square-root/) 比较了原生 `rsqrt` 指令（存在于 SSE 及更新的 x86 SIMD 指令集中）与 John Carmack 的 [快速倒数平方根](https://en.wikipedia.org/wiki/Fast_inverse_square_root) 的精度和速度，文中提到用一次 [牛顿-拉夫逊迭代](https://en.wikipedia.org/wiki/Newton%27s_method) 作为替代来提升数值精度，我们这里也会做类似的事来改进我们的算法：

C

simsimd_distance_t _simsimd_cos_normalize_f64_haswell(simsimd_f64_t ab, simsimd_f64_t a2, simsimd_f64_t b2) {
    if (ab == 0) return 0;
    if (a2 == 0 || b2 == 0) return 1;

    __m128d squares = _mm_set_pd(a2, b2);
    __m128d rsqrts = _mm_cvtps_pd(_mm_rsqrt_ps(_mm_cvtpd_ps(squares)));
    
    // Newton-Raphson iteration:
    rsqrts = _mm_add_pd(
        _mm_mul_pd(_mm_set1_pd(1.5), rsqrts),
        _mm_mul_pd(_mm_mul_pd(_mm_mul_pd(squares, _mm_set1_pd(-0.5)), rsqrts), _mm_mul_pd(rsqrts, rsqrts)));

    simsimd_f64_t a2_reciprocal = _mm_cvtsd_f64(_mm_unpackhi_pd(rsqrts, rsqrts));
    simsimd_f64_t b2_reciprocal = _mm_cvtsd_f64(rsqrts);
    return ab * a2_reciprocal * b2_reciprocal;
}

必须记住，各家 CPU 的 `rsqrt` 指令会有不同的性能和精度。等我们写完 `simsimd_cos_bf16_haswell` 函数，就会在下面看到它和 [AVX-512](https://docs.google.com/document/d/1lUiTY6um-qRI0I1Rdo2ZAWkIBWZGM7E034QjWlu625s/edit#bookmark=id.ji429glcnc5d) 的比较。

#### **部分加载**

我们的循环里还有一个假设必须修正：

C

// TODO: Handle input lengths that aren't a multiple of 8

这段以及许多其他生产级 SIMD 代码库里最难看的部分，可能就是"部分加载"逻辑了。

它是把变长数据切成定长寄存器块的自然结果。

正因如此，几乎每个内核都有一个"主循环"和一个处理最后几个元素的"尾部循环"。

在 x86 的 AVX-512 和 Arm 的 SVE 之前，没有办法加载一个部分寄存器，所以代码得稍微复杂些。

#### **x86 AVX-512 里的掩码**

AVX-512 是第一套引入掩码的 SIMD 指令集，掩码是一种基于掩码 **部分执行指令** 的方式。例如，如果你有一个含 8 个字/标量的寄存器，你可以用一个掩码只递增其中的 5 个。

每个核不仅含 32 个 `ZMM` 寄存器，还含 8 个 `KMASK` 寄存器，可用来控制指令的执行。把它们当成 8 个额外的普通标量寄存器就好，里面有 8、16、32 或 64 位。在它们和通用寄存器之间来回移动并非免费，但拿它们做掩码仍然比分支更好。

用这些特殊的掩码操作指令，掩码之间的交织、测试和相互合并也是原生支持的：

先前，在我们的 `simsimd_cos_bf16_haswell` 内核里，我们用这段代码把 8 个输入的 `bfloat16` 加进 `ab_vec` 等：

`ab_vec` 有 512 位宽，装着 16 个 `bfloat32`。你可能以为我们现在要往里加 16 个输入的 `bfloat16`，但 **这还更好：** `vdpbf16ps` 把 **32** 个输入数处理进我们这 16 字的 `ab_vec`。它取每个输入头 **两个** 字的点积，把它们的点积加到结果第一个字上（像 `ab_vec[0] += a[0] * b[0] + a[1] * b[1]`），然后对其余的字也这么干。

我们用 `_mm512_dpbf16_ps` 函数来做这条指令，把这段加进我们的循环：

b2_vec = _mm512_dpbf16_ps(b2_vec, (__m512bh)(b_i16_vec), (__m512bh)(b_i16_vec));

#### **AVX-512 的倒数平方根近似**

我们需要从概念上计算 `ab / (sqrt(a2) * sqrt(b2))`。

在我们前面的 `_simsimd_cos_normalize_f64_haswell` 函数里，我们用 `rsqrtps` 指令（通过 `_mm_rsqrt_ps` 内建函数）来算倒数平方根。在 AVX-512 里，它们被 `_mm512_rsqrt14_ps` 内建函数和 `vrsqrt14ps` 指令取代了。

幸运的是，最大误差界从 `1.5*2^-12` 改进到了 `2^-14`。

还有一条双精度指令 `vrsqrt14pd`（通过 `_mm512_rsqrt14_pd` 内建函数）。

它精度相同，但我们可以省去类型转换。

C

simsimd_distance_t _simsimd_cos_normalize_f64_skylake(simsimd_f64_t ab, simsimd_f64_t a2, simsimd_f64_t b2) {
    if (ab == 0) return 0;
    if (a2 == 0 || b2 == 0) return 1;

    __m128d squares = _mm_set_pd(a2, b2);
    __m128d rsqrts = _mm_maskz_rsqrt14_pd(0xFF, squares);
    rsqrts = _mm_add_pd( // Newton-Raphson iteration:
        _mm_mul_pd(_mm_set1_pd(1.5), rsqrts),
        _mm_mul_pd(_mm_mul_pd(_mm_mul_pd(squares, _mm_set1_pd(-0.5)), rsqrts), _mm_mul_pd(rsqrts, rsqrts)));

    simsimd_f64_t a2_reciprocal = _mm_cvtsd_f64(_mm_unpackhi_pd(rsqrts, rsqrts));
    simsimd_f64_t b2_reciprocal = _mm_cvtsd_f64(rsqrts);
    return ab * a2_reciprocal * b2_reciprocal;
}

#### **CISC vs RISC，并不是人们说的那样**

Arm 指令集常被叫作 RISC（精简指令集计算机），x86 指令集常被叫作 CISC（复杂指令集计算机）。

但实践中，Arm 指令集可能更复杂，尤其考虑到所有这些指令实际上只作用于 64 位和 128 位寄存器，而 x86 指令还涵盖 256 位和 512 位寄存器！

这里举个例子。

在发现 `vbfdotq_f32` 内建函数（由 Mark Reed 建议）之前，SimSIMD 用 `vbfmmlaq_f32` 和 `vbfmmlaq_f32` 内建函数来计算两个向量的点积。

它也是一条融合乘加指令，但设计成只取向量的奇数或偶数分量，所以我们的聚合方式不同：

C

ab_high_vec = vbfmlaltq_f32(ab_high_vec, a_vec, b_vec);
ab_low_vec = vbfmlalbq_f32(ab_low_vec, a_vec, b_vec);
a2_high_vec = vbfmlaltq_f32(a2_high_vec, a_vec, a_vec);
a2_low_vec = vbfmlalbq_f32(a2_low_vec, a_vec, a_vec);
b2_high_vec = vbfmlaltq_f32(b2_high_vec, b_vec, b_vec);
b2_low_vec = vbfmlalbq_f32(b2_low_vec, b_vec, b_vec);

换句话说，`ab_high_vec` 只含偶数分量，`ab_low_vec` 只含奇数分量。

这条指令对复数点积可能更有意义，那里我们或许想从一个复数向量里只加载实部字、或只加载虚部字。

至于余弦距离，还有一个此前在 SimSIMD 里测过的、不那么直观的取巧做法。

NEON 含一条 `BFMMLA` 指令：

> BFloat16 floating-point matrix multiply-accumulates into 2x2 matrix.
> This instruction multiplies the 2x4 matrix of BF16 values held in the first 128-bit source vector by the 4x2 BF16 matrix in the second 128-bit source vector.
> The resulting 2x2 single-precision matrix product is then added destructively to the 2x2 single-precision matrix in the 128-bit destination vector.
> This is equivalent to performing a 4-way dot product per destination element.
> The instruction ignores the FPCR and does not update the FPSR exception status.

在我看来一点也不 RISC！但它在某个时刻看上去很有前景。把向量 \(a\) 和 \(b\) 拼接成一个矩阵 \(X\)，再用一条指令算点积 \(X^T X\)，是个好主意。它会含 4 个点积，我们可以丢掉其中 1 个、保留 3 个：\(a \cdot b\)、\(a \cdot a\) 和 \(b \cdot b\)，全是余弦相似度所需。那个内核可能类似这样：

#### **逆向工程 Arm 的精度**

和 x86 类似，`rsqrt` 指令在 NEON 里也有，但只对单精度浮点。

与 x86 不同，文档很有限：

1. 我们无法知道指令的延迟。

2. 我们甚至没被告知最大相对误差。

第一点可以含糊地用这个事实解释：Arm 不生产自己的芯片，而是把设计授权给其他公司。尽管如此，一份不同芯片的计时库会非常有用。第二点纯属谜——除非你去逆向它！

我写了 [这个基准测试程序](https://gist.github.com/ashvardanian/5e5cf585d63f8ab6d240932313c75411)，它估算 Arm NEON、SSE、AVX2 和 AVX-512 里 `rsqrt` 近似的精度。

幸运的是，要测的唯一输入只有 40 亿个，在现代 CPU 上就几秒钟。

### **Arm SVE 的基线实现**

Arm SVE 很不寻常。

它不像 AVX-512 那样是首个支持掩码的。

但它 *确实* 是第一个定义了可变宽度、由实现决定寄存器的，寄存器可以是 128、256、512、1024 或 2048 位宽。

这意味着在一颗 CPU 上，一个 svbfloat16_t 可能 128 位宽（8 个 `bfloat16`），在另一颗 CPU 上可能 1024 位宽（装得下 64 个 `bfloat16`），而编译出的程序却是同一个。你只能在运行时通过调用 `svcnth` 函数来知道它们的宽度，它会告诉我们在这颗 CPU 上一个 SVE 向量能装多少个 16 位字。

在这个谱系的最末（2048 位），CPU 实际上正在和 GPU 趋同，但尽管如此，所有真实实现都是 128 位宽的。

一个内核可能长这样：

    simsimd_size_t i = 0;
    svfloat32_t ab_vec = svdupq_n_f32(0.f, 0.f, 0.f, 0.f);
    svfloat32_t a2_vec = svdupq_n_f32(0.f, 0.f, 0.f, 0.f);
    svfloat32_t b2_vec = svdupq_n_f32(0.f, 0.f, 0.f, 0.f);
    bfloat16_t const* a = (bfloat16_t const*)(a_enum);
    bfloat16_t const* b = (bfloat16_t const*)(b_enum);
    do {
        svbool_t progress_vec = svwhilelt_b16((unsigned int)i, (unsigned int)n);
        svbfloat16_t a_vec = svld1_bf16(progress_vec, a + i);
        svbfloat16_t b_vec = svld1_bf16(progress_vec, b + i);
        ab_vec = svbfdot_f32(ab_vec, a_vec, b_vec);
        a2_vec = svbfdot_f32(a2_vec, a_vec, a_vec);
        b2_vec = svbfdot_f32(b2_vec, b_vec, b_vec);
        i += svcnth();
    } while (i

<

n);

    simsimd_f32_t ab = svaddv_f32(svptrue_b32(), ab_vec);
    simsimd_f32_t a2 = svaddv_f32(svptrue_b32(), a2_vec);
    simsimd_f32_t b2 = svaddv_f32(svptrue_b32(), b2_vec);
    *result = _simsimd_cos_normalize_f32_neon(ab, a2, b2);
}

这是 CPU 特定代码很重要、不要过度依赖抽象的另一个原因：有些架构非常不寻常。

#### **Arm SVE 里的掩码**

看到"可变宽度、由实现决定的寄存器"，你可能会问自己：循环的最后一次迭代，若剩余元素填不满一整个向量，是怎么处理余下元素的？在 SVE 里，推荐的做法是用"进度掩码"（像那个 `progress_vec`），并用"while less than"内建函数（像那个 `svwhilelt_b16`）来构建它们。它是我们为 AVX-512 尾部用的 `_bzhi_u32` 的一个更强大的替代。

## 累加起来性能收益

回头看看所有硬件特定的优化，我们能相对最初的朴素实现和标准 NumPy 实现看到好几个数量级的提升。利用并榨取硬件特性，在 Intel 硬件上把性能从 10 MB/s 提到了 60.3 GB/s，在 Arm 硬件上从 4 MB/s 提到了 29.7 GB/s。它凸显了即便对最简单的计算算法，专门的硬件加速库有多么绝对的重要。

针对余弦相似度的、按架构特定的 SIMD 优化带来的性能提升。

## **打包与分发库**

贯穿全文，我提到过好几次 CPU 特定代码很重要。但正确地交付 CPU 特定代码可能很棘手。

最简单最快的做法就是针对某个特定硬件平台编译。比如用 `-march=native`，你的编译器会假定将要运行这份软件的目标机器支持与本机相同的全部汇编指令。我们可以为不同平台实现若干内核，并在编译期选出最佳后端。

C

void simsimd_cos_bf16(
simsimd_bf16_t const* a, simsimd_bf16_t const* b, simsimd_size_t n,
             simsimd_distance_t* d) {

    simsimd_cos_bf16_genoa(a, b, n, d);
#elif SIMSIMD_TARGET_HASWELL
    simsimd_cos_bf16_haswell(a, b, n, d);
#elif SIMSIMD_TARGET_SVE_BF16
    simsimd_cos_bf16_sve(a, b, n, d);
#elif SIMSIMD_TARGET_NEON_BF16

#else

#endif
}

但如果我们事先不知道目标机器，就会想把每个函数的多份优化内核打进一个二进制里，并在运行时区分。程序启动时，它检查当前 CPU 的型号或能力，选对实现。这通常叫"动态派发"。在 x86 上实现它，我们调用 CPUID 指令去查询若干特性寄存器：

C

simsimd_capability_t simsimd_capabilities_x86(void) {
   /// The states of 4 registers populated for a specific "cpuid" assembly call
   union four_registers_t {
       int array[4];
       struct separate_t {
           unsigned eax, ebx, ecx, edx;
       } named;
   } info1, info7, info7sub1;


#if defined(_MSC_VER)
   __cpuidex(info1.array, 1, 0);
   __cpuidex(info7.array, 7, 0);
   __cpuidex(info7sub1.array, 7, 1);
#else
   __asm__ __volatile__("cpuid"
                        : "=a"(info1.named.eax), "=b"(info1.named.ebx), "=c"(info1.named.ecx), "=d"(info1.named.edx)
                        : "a"(1), "c"(0));
   __asm__ __volatile__("cpuid"
                        : "=a"(info7.named.eax), "=b"(info7.named.ebx), "=c"(info7.named.ecx), "=d"(info7.named.edx)
                        : "a"(7), "c"(0));
   __asm__ __volatile__("cpuid"
                        : "=a"(info7sub1.named.eax), "=b"(info7sub1.named.ebx), "=c"(info7sub1.named.ecx),
                          "=d"(info7sub1.named.edx)
                        : "a"(7), "c"(1));
#endif
   unsigned supports_avx2 = (info7.named.ebx & 0x00000020) != 0; // Function ID 7, EBX register
   unsigned supports_f16c = (info1.named.ecx & 0x20000000) != 0; // Function ID 1, ECX register
   unsigned supports_fma = (info1.named.ecx & 0x00001000) != 0; // Function ID 1, ECX register
   unsigned supports_avx512f = (info7.named.ebx & 0x00010000) != 0; // Function ID 7, EBX register
   unsigned supports_avx512fp16 = (info7.named.edx & 0x00800000) != 0; // Function ID 7, EDX register
   unsigned supports_avx512vnni = (info7.named.ecx & 0x00000800) != 0; // Function ID 7, ECX register
   unsigned supports_avx512ifma = (info7.named.ebx & 0x00200000) != 0; // Function ID 7, EBX register
   unsigned supports_avx512bitalg = (info7.named.ecx & 0x00001000) != 0; // Function ID 7, ECX register
   unsigned supports_avx512vbmi2 = (info7.named.ecx & 0x00000040) != 0; // Function ID 7, ECX register
   unsigned supports_avx512vpopcntdq = (info7.named.ecx & 0x00004000) != 0; // Function ID 7, ECX register
   unsigned supports_avx512bf16 = (info7sub1.named.eax & 0x00000020) != 0; // Function ID 7, Sub-leaf 1, EAX register
}

这段代码在用 Clang 和 GCC 编译时使用内联汇编。Microsoft Visual Studio 编译器不支持内联汇编，但提供了一个内建函数来弥补。

一旦查询到特性标志，就必须把它们解包，用来为每种输入参数类型与 CPU 能力的组合选对内核实现。在我的另一个库 [StringZilla](https://github.com/ashvardanian/StringZilla)（它定义的字符串操作集合小得多）里，那是逐个函数地做的。但在 SimSIMD——它已有超过 350 个内核、还在快速增长——里，所有内核被按不同 CPU 世代分进若干类别，比如 Intel 的"Haswell"和"Ice Lake"、AMD 的"Genoa"。鉴于 x86_64 ISA 的碎片化，向几十个相似内核派发时，这是一个更简单、也更能面向未来的设计：

换句话说，与其为 [Intel、AMD 和 Centurion 横跨的几十种 x86 核设计](https://x.com/InstLatx64/status/1520707682356842496) 各做一个独立实现，SimSIMD 选定几个"能力级别"，以第一个支持某指令系列的服务器级 CPU 产品线命名：Sapphire Rapids 对应 AVX512-FP16、Genoa 对应 AVX-512BF16、Ice Lake 对应 VNNI/VBMI 及其他 AVX-512 整数处理指令、Skylake-X 对应基础 AVX-512 支持、Haswell 对应 AVX2、F16C 和 FMA，等等。

下一步是把受支持的 CPU 特性映射进我们的"能力级别"：

C

unsigned supports_haswell = supports_avx2 && supports_f16c && supports_fma;
   unsigned supports_skylake = supports_avx512f;

   unsigned supports_genoa = supports_avx512bf16;
   unsigned supports_sapphire = supports_avx512fp16;

## **结论**

如你所见，SIMD 满是挑战！记住，这只是我们计算一个余弦距离的一个简单例子。

但值得。当一个人跨过种种障碍、正确地驾驭 SIMD 时，它会释放出惊人的性能，往往比朴素串行代码高出一个 *数量级*。

希望你享受了这场 SIMD 复杂性的旋风之旅！它相当长，但我们甚至没去分析 x86 上不同指令系列的端口利用率。我们没深究近期 Arm 核的 SME 和流式 SVE 模式。我们也没研究 CPU 频率缩放的授权问题，尽管这些方面中许多已被跑在你喜爱数据产品底层的 [SimSIMD](https://github.com/ashvardanian/simsimd) 内核覆盖了。还有那么多在前面！
