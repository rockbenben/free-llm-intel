# Structured Mojo Kernels 第 2 篇——三根支柱

在[第 1 篇](https://www.modular.com/blog/structured-mojo-kernels-part-1-peak-performance-half-the-code)中，我们介绍了结构化 kernel 架构并论证了它为何存在。传统 GPU kernel（流水线协调、数据搬运与计算交缠在数千行里）难以推理、维护与扩展。给传统 kernel 加 block-scaled 量化等于写一个新 kernel；为一个新硬件特性加支持，就要去动与这特性毫无关系的代码。Structured Mojo Kernels 通过把关注点分离进三个带明确接口的组件解决了这一点，我们也展示了成果：代码少 48%、性能相同，一个 conv2d kernel 仅用约 130 行 conv 专属代码就复用了整个 matmul 基础设施。

本文讲解 Structured Mojo Kernels 的各组件：TileIO、TilePipeline 与 TileOp。每个组件是 kernel 执行流水线中的一个节点，它们之间的连接构成关注点的逻辑分离，让 kernel 更易扩展与更新。这种组织之所以要紧，是因为 GPU kernel 不会静止不变。把硬件优化的实现抽象为模式后，同一 kernel 结构就能以极少的重写在 NVIDIA 与 AMD 的各代硬件间适应。

## 数据流模型

结构化 matmul kernel 让数据穿过三个不同的内存层级：全局内存（DRAM）、共享内存（SMEM/LDS）、以及寄存器或 tensor memory。三个组件是数据流中的节点，各司执行的不同阶段。TileIO 把 tile 从 DRAM 搬进共享内存；TilePipeline 信号化哪些 tile 可供消费、哪些已空可再填；TileOp 从共享内存读、执行 MMA 指令、写累加器。各组件间的关注点分离，让我们能隔离地推理每个组件。

## TileIO：数据搬运抽象

TileIO 负责所有跨内存层级的数据搬运。它的职责是把平台特定 DMA 操作的复杂性藏进干净的接口之后。

### TileIO 封装了什么

| Concern | NVIDIA | AMD | Encapsulated By |
| --- | --- | --- | --- |
| DMA operation | `TMA async_copy` | `load_to_lds` | `load()` |
| Address calculation | TMA descriptors | Buffer resources | Constructor |
| Layout transformation | TMA swizzle modes | Manual swizzle | Configuration |
| Masking/bounds | TMA handles | Manual checks | `load()` |

### NVIDIA：TileLoaderTMA

在 NVIDIA Blackwell 上，TileIO 包装 TMA（[Tensor Memory Accelerator，前文博客有解释](https://www.modular.com/blog/matrix-multiplication-on-nvidias-blackwell-part-1-introduction)）操作。加载器保存一个 TMA descriptor 指针和用于 cluster 分发的 multicast mask：

mojo

```
struct TileLoaderTMA[
    tma_origin: ImmutOrigin,
    dtype: DType,
    gmem_layout: Layout,
    desc_layout: Layout,
    /,
    *,
    cta_group: Int,
](TrivialRegisterPassable):
    """TMA-based tile loader for Blackwell."""

    comptime TmaOp = TMATensorTile[Self.dtype, Self.gmem_layout, Self.desc_layout]

    # TMA descriptor pointer (referencing grid constant)
    var tma_op: Pointer[Self.TmaOp, Self.tma_origin]
    # Multicast mask for cluster distribution
    var multicast_mask: UInt16

    @always_inline
    def load[tile_layout: Layout, /, alignment: Int = 128](
        self,
        dest: SMemTile[Self.dtype, tile_layout, alignment=alignment],
        ref[AddressSpace.SHARED] barrier: SharedMemBarrier,
        k_coord: UInt,
        row_coord: UInt,
    ):
        """Load a tile asynchronously via TMA hardware."""
        self.tma_op[].async_multicast_load[Self.cta_group](
            dest, barrier, (k_coord, row_coord), self.multicast_mask
        )
```

这个加载器刻意保持极简：它只包一个 TMA descriptor 与一个 multicast mask，暴露一个数据搬运原语。编排（k-group 迭代、barrier 管理、期望字节数）全归 kernel，加载器通过 TilePipeline 暴露的 stage 就绪/消费协议与之交互——TilePipeline 见下文“TilePipeline：流水线协调者”一节。

### AMD：TileLoaderLDS

在 AMD 上，TileIO 用 buffer resource 做协作式全局内存到 LDS 的加载。该架构要求根本不同的加载策略：

mojo

```
struct TileLoaderLDS[
    dtype: DType,
    src_layout: Layout,
    src_tile_layout: Layout,
    num_loading_warps: Int,
    swizzle: Optional[Swizzle] = Optional[Swizzle](),
    load_width: Int = simd_width_of[dtype](),
    use_full_tile_width: Bool = False,
](TrivialRegisterPassable):
    """Cooperative global→LDS tile loader with swizzle support.

    Loading Modes (controlled by use_full_tile_width):
    - False: Interleaved layout for BF16 where MMA_K < BK
    - True: Row-major layout for FP8 where MMA_K == BK
    """

    var buffer: AMDBufferResource
    var thread_row: Int
    var thread_col: Int
    var warp_id: Int

    # Each warp loads a portion of the tile cooperatively
    # AMDBufferResource provides automatic out-of-bounds clamping to zero
```

尽管机制完全不同，这一抽象让 API 使用者得以避开硬件细节，两边的调用点看起来一模一样。

## TilePipeline：流水线协调者

TilePipeline 管理让加载、计算、存储互相重叠的 producer-consumer 流水线。它不搬运数据、不跑 MMA 指令——只信号化 tile 何时满了、何时空了。

Sequence diagram of the producer-consumer pipeline

### NVIDIA：InputTilePipeline

在 NVIDIA Blackwell 上，TilePipeline 使用硬件 [`mbarrier`](https://docs.modular.com/mojo/std/gpu/memory/) 原语。`mbarrier` 提供硬件加速的 arrive/wait、与 TMA 集成的自动字节计数，以及跨流水线 stage 的 phase 跟踪。用 payload 类型参数化流水线，意味着同一套同步逻辑同时适用于标准与 block-scaled 的 tile 配置——不同的只有 payload：

mojo

```
struct InputTilePipeline[
    Payload: TilePayload,
    num_group_stages: Int,
    k_group_size: Int,
](TrivialRegisterPassable):
    """Tile pipeline with configurable payload type.

    Separates synchronization from tile storage. The Payload parameter
    (e.g., StandardTilePayload or BlockScaledTilePayload) holds tile arrays.
    """

    comptime Pipeline = ProducerConsumerPipeline[Self.num_group_stages]

    var pipeline: Self.Pipeline
    var payload: Self.Payload

    @always_inline
    def __init__(out self, barriers: Self.BarrierArray, payload: Self.Payload):
        self.pipeline = {barriers.ptr}
        self.payload = payload

    def producer(ref [origin]self) -> InputProducer[...]:
        """Get producer role handle."""
        return InputProducer(pipeline_ptr=Pointer(to=self))

    def consumer(ref [origin]self) -> InputConsumer[...]:
        """Get consumer role handle."""
        return InputConsumer(pipeline_ptr=Pointer(to=self))
```

`InputProducer` 与 `InputConsumer` 角色句柄提供返回上下文管理器的 `acquire()` 方法。`with producer.acquire() as tiles:` 模式自动处理进入时的 barrier 等待与退出时的 stage 推进。

### AMD：原子计数器同步

AMD 没有 `mbarrier` 操作。因此 AMD 上的 kernel 无法把 barrier 字节计数卸载给硬件，所有同步都是显式的。设计上用 `SyncStrategy` trait 让环形缓冲逻辑与同步机制互相独立：

mojo

```
trait SyncStrategy(TrivialRegisterPassable):
    """Interface for producer-consumer synchronization protocols."""

    def wait_producer_acquire(self, tile_idx: Int, stage: Int, phase: Int32): ...
    def signal_producer_release(mut self, tile_idx: Int, stage: Int): ...
    def wait_consumer_acquire(self, tile_idx: Int, stage: Int, phase: Int32): ...
    def signal_consumer_release(mut self, tile_idx: Int, stage: Int): ...
```

两个具体实现以简单性与低竞争相权衡：

mojo

```
struct SingleCounterSync[...](SyncStrategy):
    """One atomic counter per tile. Simpler but higher contention."""
    var sync_counter: SMemArray[Int32, total_tiles]

struct SplitCounterSync[...](SyncStrategy):
    """Separate producer/consumer counters. Reduces contention."""
    var producer_counters: SMemArray[Int32, total_tiles]
    var consumer_counters: SMemArray[Int32, total_tiles]
```

值得直接审视底层同步原语：

mojo

```
@always_inline
def wait_for_counter(
    counter: UnsafePointer[Int32, address_space = AddressSpace.SHARED],
    threshold: Int32,
):
    """Spin-wait until counter reaches threshold."""
    while Atomic.load(counter) < threshold:
        inlined_assembly["s_sleep 0", ...]()

@always_inline
def increment_counter_if_first_thread(
    counter: UnsafePointer[Int32, address_space = AddressSpace.SHARED],
    increment: Int32,
):
    """Atomically increment counter, but only from first thread in warp."""
    if thread_idx.x % WARP_SIZE == 0:
        _ = Atomic.fetch_add(counter, increment)
```

这里有两个不显然的决策。第一，每个 warp 中只有第一条线程递增计数器。warp 内所有线程锁步执行，若所有线程（AMD 上是 64 条）都发 `fetch_add`，一次正确的递增会变成 64 次。第二，`s_sleep 0` 让出 warp 调度器，而不是在紧自旋里烧计算周期。在 AMD 上，发一条零周期休眠提示，让其他 wavefront 在本条等待时得以推进。

尽管原语完全不同，NVIDIA 与 AMD 的 TilePipeline 暴露同样的 acquire/release 接口。其上的环形缓冲逻辑是平台无关的。

## TileOp：计算驱动器

TileOp 封装全部矩阵计算：把操作数从共享内存载入寄存器（或 TMEM）、执行 MMA/mfma 指令、管理累加器存储。

### NVIDIA Blackwell：基于 TMEM 的累加器

Blackwell 引入了 Tensor Memory（[TMEM，前文博客有解释](https://www.modular.com/blog/matrix-multiplication-on-nvidias-blackwell-part-2-using-hardware-features-to-optimize-matmul)）——每 SM 256KB、专用于累加器存储的暂存器。这很重要，因为把累加器搬出寄存器文件就腾出了寄存器做别的事，并支持更大的 tile 尺寸。TileOp 通过上下文管理器管理完整 TMEM 生命周期：

mojo

```
struct MmaWarpContext[
    opc: OutputPipelineConfig,
    mma_threads: Int,
    epilogue_threads: Int,
](TrivialRegisterPassable):
    """MMA warp context - owns TMEM lifecycle and output pipeline.

    __enter__: Signals epilogue that TMEM is allocated
    __exit__: Waits for epilogue, deallocates TMEM
    """

    comptime Tmem = TmemAllocation[Self.opc.cta_group]
    comptime Pipeline = OutputTilePipeline[Self.opc]
    comptime Dealloc = TmemDeallocBarrier[Self.opc.cta_group]

    var tmem: Self.Tmem
    var output_pipeline: Self.Pipeline
    var dealloc_barrier: Self.Dealloc

    @always_inline
    def __enter__(self) -> Self:
        Self.Sync.arrive()  # Signal epilogue that TMEM is ready
        return self

    @always_inline
    def __exit__(self):
        self.dealloc_barrier.complete_dealloc(self.tmem)
```

上下文管理的意义不止于整洁。TMEM 只有在 epilogue warp 读完累加器之后才能释放。MMA warp 若提前释放，epilogue 就会读到垃圾；若永不释放，下一次 kernel 调用就无法分配。

作为流水线的一部分，MMA 操作本身从流水线接收 tiles、执行 `tcgen05.mma` 指令、把结果写入 TMEM 累加器。

### AMD MI300X：基于寄存器的累加器

AMD 上没有专用 tensor memory。累加器与操作数同住 VGPR，由编译器管理其分配。因此我们把 TileOperator 定义为：

mojo

```
struct AmdTileOperator[
    InType: DType,
    OutType: DType,
    mma_shape: IndexList[3],
    ...
](TrivialRegisterPassable):
    """Matrix operations on AMD using mfma instructions."""

    var _a_reg_tile: Self.ARegTileType
    var _b_reg_tile: Self.BRegTileType
    var out_reg_tile: Self.OutRegTileType  # Accumulator in registers

    def load_tile_fragment[k_tile_idx: Int](
        self,
        smem_tile_a: TileTensor,
        smem_tile_b: TileTensor,
    ):
        """Load operands from LDS to registers with swizzle handling."""
        comptime for i in range(num_fragments):
            self._a_reg_tile[i] = smem_tile_a.load[swizzle](i, k_tile_idx)
            self._b_reg_tile[i] = smem_tile_b.load[swizzle](i, k_tile_idx)

    def mma_compute[k_tile_idx: Int](self):
        """Execute mfma instruction."""
        self.out_reg_tile = mfma[mma_shape](
            self._a_reg_tile, self._b_reg_tile, self.out_reg_tile,
        )
```

### 关键差异

| Aspect | NVIDIA Blackwell | AMD MI300X |
| --- | --- | --- |
| Accumulator storage | Tensor Memory (256KB) | Registers (VGPRs) |
| Instruction | `tcgen05.mma` | `mfma` |
| Operand source | Direct from SMEM | Must load to registers first |
| Allocation | Explicit allocate/deallocate | Compiler-managed |

两个 TileOp 实现呈现同样的概念接口（载入 fragment、计算 MMA、存储结果），但资源生命周期在结构上不同。NVIDIA 对上下文管理器的需求是显式 TMEM 分配的直接结果；AMD 不需要这种包装，因为编译器自动处理寄存器生命周期。

## `TileTensor`：张量数据结构

三个组件共享同一个地基：[**`TileTensor`**](https://docs.modular.com/mojo/kernels/layout/tile_tensor/TileTensor/)。这一抽象携带编译期布局信息（形状、stride、swizzle 模式）、内存地址空间归属（全局内存、共享内存、寄存器）与类型安全的访问模式。正因为 `TileTensor`，TileIO、TilePipeline 与 TileOp 之间才能互递 tile，而任何组件都不用了解对方的内部表示。

### 示例：线程到元素的映射

mojo

```
# Map 64 threads to a 16x64 output tile
comptime thread_layout = Layout.row_major(8, 4)

# Each thread handles 2 consecutive elements
var my_elements = output_tile
    .vectorize[1, 2]()                      # View as 2-element vectors
    .distribute[thread_layout](lane_id())   # My portion

# Write my portion
comptime for i in range(my_elements.shape[0]()):
    for j in range(my_elements.shape[1]()):
        my_elements[i, j] = accumulator[i * stride + j]
```

## 把一切拼起来：完整流水线

以下是三个组件在真实 Blackwell 结构化 matmul kernel 中的协作方式。每条 warp 角色只有一个职责，流水线结构在代码中是显式的。

### 设置：共享内存与流水线初始化

mojo

```
# From the Blackwell structured matmul kernel's run() method

# Setup: shared memory, pipeline, and context
ref smem = external_memory[...].bitcast[Self.SmemType]()[]
var tile_payload = Self.TilePayload(smem.a_tiles(), smem.b_tiles())
var input_pipeline = Self.InputTilePipeline(
    smem.pipelines.input_barriers(), tile_payload)
var ctx = Self.Context(smem.pipelines.tmem_addr())
var work_iter = scheduler.work_iterator()
```

### TMA 加载 warp：只管数据搬运

load warp 获取 producer stage、发射 TMA 加载、信号化完成。除了 TilePipeline 暴露的内容，它不碰累加器也不碰 barrier。

mojo

```
# TMA Load Warp: data movement specialist
if WarpRole.is_main_load():
    with input_pipeline.producer() as producer:
        while work_iter.has_work():
            with work_iter.next() as current:
                for i in range(0, num_iters, Self.config.k_group_size):
                    with producer.acquire() as tiles:
                        Self.load_input_tiles(a_tma_op, b_tma_op, tiles, ...)
                syncwarp()
        producer.drain()
```

### MMA warp：只管计算

MMA warp 等待输入流水线、计算、向输出流水线发信号。`mma_ctx` 在这个块的整个生命期内拥有 TMEM 分配：进入上下文即向 epilogue 信号累加器已分配；退出上下文则在 epilogue 信号读完之后才释放。

mojo

```
# MMA Warp: compute specialist
if WarpRole.is_mma():
    var mma_ctx = Self.MmaCtx.create(...)
    with mma_ctx:
        while work_iter.has_work():
            with work_iter.wait_and_advance():
                if ctx.elect_one_cta:
                    with mma_ctx.output_pipeline.producer() as output_stage:
                        with input_pipeline.consumer() as consumer:
                            for i in range(0, num_iters, Self.config.k_group_size):
                                with consumer.acquire() as input_tiles:
                                    Self.mma(output_stage.tmem, input_tiles, mma_op, ...)
```

### Epilogue warp：只管输出

epilogue warp 通过输出流水线从 TMEM 读取，写入全局内存。它完成时向 MMA warp 发信号，触发 TMEM 释放。

mojo

```
# Epilogue Warp: output specialist
if WarpRole.is_epilogue():
    var epi_ctx = Self.EpilogueCtx(...)
    with epi_ctx:
        while work_iter.has_work():
            with work_iter.next() as current:
                with epi_ctx.output_pipeline.consumer() as output_stage:
                    tile_writer.write_batched(smem.c_tiles(), output_stage, ...)
```

## 接下来

我们已从内部看完每根支柱：TileIO 搬数据，TilePipeline 协调时序，TileOp 做计算。在[第 3 篇](https://www.modular.com/blog/structured-mojo-kernels-part-3-composition-in-practice)中，我们将探索这种模块化设计的实际收益：拿 conv2d 与 block-scaled matmul 两个真实 kernel 家族，逐条追踪它们如何围绕 matmul 地基构建。

## TL;DR

- **TileIO** 拥有数据搬运：把 TMA 与 buffer 加载的差异藏进单个 `load()` 调用。
- **TilePipeline** 拥有协调：NVIDIA 上用 `mbarrier`，AMD 上用原子计数器，acquire/release 接口不变。
- **TileOp** 拥有计算：NVIDIA 上用 TMEM（配显式 RAII 生命周期），AMD 上用寄存器（编译器管理）。
- **`TileTensor`** 是共享数据抽象：跨所有内存层级与地址空间的同一类型。
- **组件边界由类型而非约定强制**：load warp 发不出 MMA 指令，因为 TilePipeline 不暴露那个接口。
