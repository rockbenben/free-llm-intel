# Reintroducing MAX’s Module

Kathy Wu

Alister Burt

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a82c/6aff3d96149fad6867cf98f0_ReleaseBlogPost-Option_%25281%2529.jpeg)

Engineering

MAX is built for production inference at maximum speed. We recently redesigned our `Module` API to help developers build fast models even faster. `Module` is a standard building block in machine learning frameworks, and this post explains how and why we rebuilt this API, diving into a few key aspects:

- How the new design speeds up development
- Production inference with the new `Module`
- Support for distributed computation
- Simplification of the `Module` APIs
- Familiar PyTorch-like syntax
- Where the new `Module` sits in the stack compared to its predecessor

## Rebuilding MAX’s AI framework

Modular has focused on production inference with state-of-the-art performance. MAX's advantage is its compilation stack: cross-architecture, optimized Mojo kernels, plus graph compilation and execution that aggressively fuse kernels and plan memory.

The legacy `Module` was built directly on our graph stack. The graph-forward approach delivered excellent performance, but the developer experience left room for improvement. We closed the gap by introducing a new Eager layer on top of the graph stack, then rebuilding `Module` on top of it.

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6aff3d35cf2b4cc97a204c52_stack_diagram_1.png)

## Familiar, PyTorch-like syntax

If you've written a PyTorch model, the new `Module` should feel familiar. Here is the same layer in MAX and in PyTorch:

python

```
# MAX
from max.nn import Module
from max.tensor import Tensor

class MyLayer(Module):
    def __init__(self, in_dim, out_dim):
        self.weight = Tensor.zeros([out_dim, in_dim])
        self.bias = Tensor.zeros([out_dim])

    def forward(self, x):
        return x @ self.weight.T + self.bias
```

python

```
# PyTorch
import torch
from torch import nn

class MyLayer(nn.Module):
    def __init__(self, in_dim, out_dim):
        super().__init__()
        self.weight = nn.Parameter(torch.zeros(out_dim, in_dim))
        self.bias = nn.Parameter(torch.zeros(out_dim))

    def forward(self, x):
        return x @ self.weight.T + self.bias
```

The differences are intentional simplifications of the design: no `super().__init__()` call, and plain `Tensor`s instead of `nn.Parameter`.

## Eager execution enables faster development

Agents have fundamentally changed the development cycle. While model performance remains critical for production workloads, enabling fast iteration during development is arguably more important than ever. Paying a compilation cost on every unit test and debug log is painful.

Eager execution avoids expensive graph compilation and instead starts computing results immediately. When you first run Gemma 4 using the new `Module` your first token appears much more quickly.

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6aff3d35fbb5b6653299fb67_startup_time_chart_1.png)

Debugging models also gets a lot faster!

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6aff3d3558f1987d62d2a796_debugging_a_layer.gif)

## Production inference with the new `Module`

The redesigned `Module` still serves our primary use case, production inference. The built-in `compile` method traces the model and compiles it as a graph, which lets MAX optimize the computation using knowledge about the whole model. Our graph compiler performs:

- Operation fusion, to reduce launch overhead.
- Constant folding and other initialization-time lifting, to avoid repeating the same constant compute on every loop.
- Execution and memory planning, so MAX can plan storage and reuse buffers instead of allocating new ones.
- Shape inference and reasoning about dynamic shapes, which supports all of the above.

`Module` directly supports both eager and compiled execution, so model authors get the best of both worlds:

python

```
model = DeepSeekV3(config)

# Option 1: Call eagerly
model.load_state_dict(state_dict)
model(inputs)

# Option 2: Compile, then call
compiled = model.compile(*input_types, weights=state_dict)
compiled(inputs)
```

## Distributed computation: split work across many devices

The redesign was a chance to rethink how we write distributed models. The framework's role is to structure the scaling of a computation from a single GPU to many.

There is no single right way to do that. Many parallelism strategies exist because GPUs differ in compute and memory limits, models differ in layers and dimensions, and inputs differ in shape. Here are several ways to distribute a model:

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6aff3d36d840e29bf1ddffd2_tensor_parallelism.gif)

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6aff3d368798806989f4456e_pipeline_parallelism.gif)

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6aff3d36a98f5293499a160d_data_parallelism.gif)

Lower-level abstractions in MAX can now express data parallelism, pipeline parallelism, or tensor parallelism. A `Tensor` is still a logical N-D array, but it can now live on more than one device. Operations on distributed tensors behave according to specific sharding rules.

A future post will dive deeper into the specifics of our distributed computation support. For now, see below how a row parallel linear layer is implemented:

## Tree utilities

A `Module` is now a `Tree`, a new API in MAX inspired by [JAX’s Pytrees](https://docs.jax.dev/en/latest/pytrees.html). `Tree`s are made of `Module`s and `Tensor`s which simplifies two things:

- `Module.parameters` and `Module.descendants` use tree traversal to collect connected `Module`s and `Tensor`s.
- `Module.trace` and `Module.compile` use `tree.map` to convert `Tensor`s into graph weights.

These APIs also indirectly help with serialization: tree `flatten` produces both the flattened leaves and a `TreeDef` object that stores the tree structure.

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6aff414aa964ec05b8c4675a_tree_diagram_white.png)

As an example, we use `Tree.map` to quantize only the expert layers in a mixture-of-experts model.

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6aff402560bbdcb52d503671_tree_map_quantize_experts_5.gif)

## Simpler APIs for handling graphs, weight tensors and dtypes

We also removed abstractions and boilerplate that were no longer needed.

**No symbolic **`**Weight**`** class.** `Weight` existed to track and create weights in the graph. Now you use `Tensor` directly in a `Module`.

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6aff3d3777e8487f07c00742_code_diff_example_1_1.png)

**Default **`**dtype**`** and **`**device**`**.** The layer at the top of this post defines neither. A default `dtype` and `device` context manager means a model that uses one device or dtype everywhere doesn't need to pass them to every layer. You can still set them per layer when needed.

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6aff3d37beb5520f17172f9e_code_diff_example_2_1.png)

**Built-in **`**compile**`**.** Graph construction boilerplate is gone. Every `Module` now has a `compile` method, covered in the production inference section above.

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a81f/6aff3d3743de88213eee0959_code_diff_example_3_1.png)

## Final thoughts

The legacy `Module` implementation now lives in `max.nn.legacy` and will be removed in Q1 2027, so now is a good time to migrate your existing models. We’re also restructuring `max.nn` around the new `max.tensor` and `max.functional libraries.`

The best place to get started is the [Model Bringup Workflow tutorial](https://max.modular.com/develop/model-bringup-workflow/), which walks through building a model end to end with the new APIs.

Looking ahead, 2027 brings quantization, training, and multi-node support. Next in this series is a framework overview showing where MAX fits in the ML framework landscape, followed by posts on eager execution, distributed tensors, serialization, and more.
