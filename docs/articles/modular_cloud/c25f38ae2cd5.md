# Blackwell 上的矩阵乘法：第 4 篇——突破 SOTA

> 🛠️ 本系列提到的所有 kernel 代码均已开源在 GitHub。


在这篇博文中，我们将继续在 NVIDIA Blackwell 上构建最先进（SOTA）matmul kernel 的旅程，探索 cluster launch control（CLC）优化。文章结尾我们将再提升 15% 性能，达到 1772 TFLOPs，超越当前的 SOTA。


### Kernel 8：CLC 持久化 kernel

在[第 3 篇](https://www.modular.com/blog/matrix-multiplication-on-nvidias-blackwell-part-3-the-optimizations-behind-85-of-sota-performance)中，我们提到 matmul kernel 仍受两大开销困扰：

- 共享内存与 barrier 的初始化需要在每个 ***Wave***（波次，其含义下文解释）之间重启。
- 对 C 矩阵的写入无法重叠。

本节讨论如何用持久化 kernel 消除这两个开销。
Kernel 8 的代码在[这里](https://github.com/modular/modular/blob/main/max/kernels/test/gpu/linalg/matmul_blackwell_iterative/8_clc_tmem_ping.mojo)。

### **什么是持久化 kernel？**

要理解持久化 kernel，必须先解释什么是 **wave**。在 GPU 中，一个 wave 指可以一次性分配给所有可用流式多处理器（SM）的一批线程块。kernel 的执行可以看作一系列 wave 依次处理，直到所有工作完成。

就 matmul 而言——线程块代表整个工作负载，线程块 ID 对应块 tile 坐标——持久化 kernel 意味着由 kernel 作者而非硬件来调度这些块 tile 坐标。

在 Hopper 架构上，我们可以定义一个像这样工作的[tile 调度器](https://github.com/modular/modular/blob/main/max/kernels/src/linalg/matmul_tile_scheduler.mojo)：

- 按可用 SM 的数量启动同样多的 Cooperative Thread Arrays（CTA）
- 让每个 CTA 计算矩阵乘加（MMA）并存储一个输出 tile
- 写出一旦完成，就把下一个待计算 tile 的坐标交给它
- 持续 `Num_Tiles / Num_SM's` 次迭代

以下代码展示我们如何为当前 CTA 取回下一个工作 tile。

fn fetch_next_work(mut self) -> WorkInfo:
  self.idx += num_idle_ctas
  return self.idx

调度器不断给 CTA 喂新的工作 tile，直到没有更多工作（即 `work_info` 失效），从而让 CTA 保持驻留。通过让 CTA 常驻 SM，我们消除了启动下一个块的开销时间，调度看起来像这样：

**然而**，静态持久化 kernel 有几个问题：

- 它假设 kernel 总是在利用所有 SM。当 GPU 同时启动多个 kernel 时并非如此。
- 它不知道哪些 SM 空闲/忙碌。

如果同一 GPU 上还有其他 kernel 在跑，这些因素会导致次优调度；如果线程块跑在前面几个 wave，还会造成 SM 饥饿。Blackwell 用 Cluster Launch Control（CLC）解决了这两个问题。

### CLC 调度器深潜

NVIDIA Blackwell 架构的一个新事物是芯片上内置的调度器。硬件不再依赖软件管理的分发，而是通过一个优雅的 producer-consumer 模型来编排工作。思路变成：

- 按问题形状需要启动尽可能多的线程块。
- 调度 warp（集群中第 1 个 CTA 的第 4 个 warp）尝试把工作 tile “*取消*”，把它们指派给空闲 SM。
- 调度 warp 还会把坐标写入集群内所有 CTA 的一块专用共享内存位置，信号化 16 字节数据的到达。
- 信号到达后，集群内所有 CTA 从该共享内存位置读取坐标。

此过程持续到 GPU 处理完所有线程块。

[tile 调度器](https://github.com/modular/modular/blob/main/max/kernels/src/linalg/matmul_tile_scheduler_sm100.mojo)在 Mojo 中的高层实现看起来像这样：

Mojo

struct TileScheduler[num_pipeline_stages: Int]:
  @always_inline
  fn fetch_next_work(self, ...) -> WorkInfo:
    # Wait for the 16 bytes arrival.
    index, phase = consumer_state.index(), consumer_state.phase()
    self.full_mbar[index].wait(phase)
    # Read work coordinate from shared memory location.
    var work_tile = work_info_from_clc_response(self.clc_response[index])
    # Signal scheduler CTA that work coordinate is fetched.
    self.empty_mbar[index].arrive_cluster(0)
        
    return work_tile
        
  @always_inline  
  fn advance_to_next_work(self, ...) -> PipelineState:
    index, phase = producer_state.index(), producer_state.phase()
    # Wait for work coordinate to be fetched.
    self.empty_mbar[index].wait(phase())
    # Set a arrival signal of 16 bytes.
    self.full_mbar[index].arrive_and_expect_bytes()
    
    if elect_one_sync():
      # Try to cancel thread blocks and write coordinate 
      # to clc_response.
      clusterlaunchcontrol_try_cancel[multicast=True](
        self.clc_response + index, self.full_mbar + index,
      )
    return producer_state.next()

Copy

这里我们用 `empty_mbar` 和 `full_mbar` 来信号化工作 tile 坐标的到达与取回。仔细看你会发现我们还为 `TileScheduler` 实现了流水线化。这个设计决策的理由在下一节讨论。

有了这个实现，我们至少能把下一个 wave 的 Tensor Memory Accelerator（TMA）加载与当前 wave 的 C 写出重叠。但要消除 CLC 调度的开销以及不同 wave 的 MMA 之间的停顿，还有更多工作要做。

### 流水线化 CLC 取回

为了消除 CLC 调度开销，我们把它流水线化。思路与之前的 kernel 相同：

if WarpRole.is_main_load():
  for work in scheduler(clc_consumer_state):

if WarpRole.is_scheduler() and is_first_cta_in_cluster:

    # Pre-fetch next tile while current one processes
    clc_producer_state = next(scheduler(clc_producer_state))
        
# MMA and Epilogue warps.

上面的代码中，若假设 2 级流水线，我们为每个 CTA 的 CLC 响应预留 2 个共享内存位置。`load_warp` 始终等待坐标被写入当前流水线状态索引对应的共享内存，而 `scheduler_warp` 可以抢先一步，把下一个坐标写入下一个共享内存位置。

`scheduler_warp` 唯一需要等待 `load_warp` 的情形，是流水线索引已经绕完整个流水线而坐标仍未被 `load_warp` 取回。

现在调度看起来好多了。它把调度工作 tile 的开销移到与下一个 wave 的 TMA 加载重叠的位置。

### **TMEM 作为循环缓冲区**

对累加器使用单一 Tensor Memory（TMEM）地址带来两大缺陷：

- **空闲 warp**：当 epilogue warp 把数据从 TMEM → SMEM → GMEM 搬运时，producer 和 consumer warp 无事可做。如果它们去处理下一个 tile，就会覆写 epilogue warp 正在读取的 tensor memory 数据。
- **MMA 与输出串行**：输出与下一个 wave 的 MMA 仍是串行执行的。原因在于 MMA warp 与输出 warp 之间经由 TMEM 的数据依赖。

为解决这一点，我们可以像之前对共享内存中的 A、B 那样，把 TMEM 当作循环缓冲区。假设我们选择 `MMA_N == 256`，那么当 `epilogue` warp 写出第 0-255 列结果的同时，`mma` warp 可以并发地把下一个 tile 的结果累加到第 256-511 列。

概念上，这是一个顺理成章的优化。我们只需定义 `accum_full` 和 `accum_empty` barrier 来信号化 TMEM 缓冲区哪一级是空/满。而且因为它只影响我们的 `mma` 和 `epilogue` warp，支持它的代码改动极小：

**MMA warp**

var accum_producer_state = PipelineState[2](0, 1, 0)
var accum_consumer_state = PipelineState[2]()
var stage_stride_cols = 512 // 2  # = 256 columns per stage

if WarpRole.is_mma():
  for work in scheduler:
    # wait for either half of tmem to be empty
    accum_index, phase = accum_producer_state.index(), accum_producer_state.phase()
    accum_empty_mbar[accum_index].wait()

    # its not over-written until its been emptied

修复了上述两大开销之后，我们得到了最优调度。

与我们的 Hopper（H100）matmul 调度相比，可以看到 Blackwell（B200）kernel 的每个阶段都异步执行。这一切都归功于 Blackwell 全新的 tensor memory 和 CLC——它们让 producer-consumer 模型得以调度工作 tile。

所有优化就位后，我们的 kernel 在 4096x4096x4096 形状上达到 1772.9 TFLOPs，为 cuBLAS 的 100.6%。

然而，如果看其他形状（如 8192x8192x8192），我们的性能仍是 cuBLAS 的 90%。所以这里还有进一步的优化空间。

### Kernel 9：线程块 Swizzle

既然我们能把工作 tile 调度到 SM，剩下的唯一优化就是提升 L2 缓存命中。我们可以用一个叫 **block swizzling** 的技巧做到。

要理解它，得先想象 CLC 如何把块 tile 调度到每个 wave。在下面的图中，假设我们启动一个 `6x5` 的集群——形成 28 个按 cluster 计的工作 tile。

再假设 GPU 每个 wave 有 9 个可用 SM。分配给每个 wave 的工作 tile 如下所示。

看 `Wave 0`：对矩阵 A，我们需要工作 tile ([0, 5], k)；对矩阵 B，我们需要 ([0, 1], k)。也就是矩阵 A 要 6 次加载、矩阵 B 要 2 次从全局内存加载。因为只有矩阵 A 的 ([0, 2], k) 和矩阵 B 的 ([0, 1], k) 可以被多个工作 tile 复用。结果就是，内存 tile 因复用率太低而被挤出 L2。

Swizzle 模式允许我们沿 N 维移动、形成之字形排布，从而把一批共享同一工作坐标的工作 tile 调度到一起。沿 N 维移动的 tile 数量称为 `block_swizzle_size`。最优的 `block_swizzle_size` 取决于问题形状与所启动的按 cluster 计的块 tile 数量。

### 应用到生产形状

到目前为止，为了简化，我们专注于 4096、8192 这类方阵。这对博客演示很好，但这些形状不会出现在生产 LLM 中。实践中，M 维取决于 batch size 与 prompt 长度，范围在 O(10²) 到 O(10³) 量级；N、K 维则取决于模型。下图展示 [gemma-3-27B-it](https://builds.modular.com/models/gemma-3-it/27B) 模型的形状。

针对生产所用形状优化时，关键是选择最优参数——包括 MMA 形状、流水线级数、block swizzle 模式等——以高效编排我们讲过的各项优化。这些参数的选取以最小化每 SM 工作量（等价于最大化所有 SM 的利用率）为准。例如，服务 Gemma 3 涉及形状为 `MxNxK = 512x8192x5376` 的 matmul。用我们演示过的 2xSM MMA 指令形状 256x256，会产生 `512/128 x 8192/256 = 128` 个 CTA。而若把指令形状缩小到 256x224，kernel 会创建 148 个 CTA——恰好完美映射到 B200 的 148 个 SM。

不过，有些形状需要细腻的参数选择，难以凭经验计算，因为流水线级数与输出 tile 之间存在微妙权衡（见[系列第 3 篇](https://www.modular.com/blog/matrix-multiplication-on-nvidias-blackwell-part-3-the-optimizations-behind-85-of-sota-performance)）。好在 Mojo 有一个内建自动调优框架（[`kbench`](https://github.com/modular/modular/blob/main/max/kernels/benchmarks/autotune/README.md)），可针对给定问题形状选择最优参数。通过自动调优并使用真实工作负载，MAX 在 NVIDIA Blackwell 系统上运行 Gemma 3 27B 时，相比 SOTA 实现最多匹配或超出 6%。
