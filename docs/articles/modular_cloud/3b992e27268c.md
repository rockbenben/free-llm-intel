# 为什么 LLM 推理需要一种新型路由器——第 3 部分

Aayush Deshpande

Deep Dhillon

Alexandr Nikitin

Michael Dunn-OConnor

工程

在本系列的 [第 2 部分](https://www.modular.com/blog/why-llm-inference-needs-a-new-kind-of-router-part-2)，我们构建了一个数据结构，能在每次请求上以微秒查询出哪些 pod 有用户的 KVCache block。本文越过集群和缓存状态，讲 Modular Cloud 如何生成路由决策、并把它们派发到各个 pod。

多数路由栈出厂就带一组固定算法：round-robin、least-requests、一致性哈希等。这些通常是彼此独立的实现，而非可组合的组件。结果就是，当一个客户要"带并发上限的一致性哈希"或"带会话粘性的缓存感知"时，就得从零加一个新算法。分离式 prefill/decode 让这种膨胀更甚。传统上每个变体都有自己的 HTTP 处理器、服务发现逻辑、代理代码和会话管理。那每个变体要多写几百行管线代码。

取而代之，Modular Cloud 的路由层由少量阶段构成，行为被表达成可组合的插件。新需求可以用插件满足，新的执行模式通过组合这些插件产生。

## 五个阶段

Modular Cloud 里的每个路由决策都经过同样的五个阶段、同样的顺序：`Prepare` → `Filter` → `Score` → `Pick` → `Execute`。

`Prepare` 用下游各阶段所需的东西丰富路由上下文：对提示词做 tokenize、把它哈希成 block、从某个头部提取一个会话键、并为一致性哈希计算一个哈希键。它每请求运行一次，在任何候选评估之前。

`Filter` 移除那些因健康检查、硬件角色匹配（prefill 请求绝不能到只跑 decode 的 pod）和并发度而无法服务请求的候选。然后它输出一个更小的候选清单。

`Score` 基于缓存亲和、负载、节点局部性等因素，给每个剩余候选打一个质量分。一个路由配置可以含多个打分器（scorer），各自在不同因素上评估候选。

`Pick` 从打分后的清单里用一个策略选出一个或多个候选：`MaxScorePicker`（确定性，最高分胜出）、`RoundRobinPicker`（带状态的轮转）、或 `SessionPicker`（粘性查找）。多个分数可以用显式权重组合成最终的逐候选得分。`Pick` 随后输出一个 `RoutingPlan`，它是一个元组列表，表示角色、候选、失败策略等。

`Execute` 派发这个 `RoutingPlan`。对单次派发路由，这是一次 HTTP 代理调用。对分离式 prefill/decode 这样的多步计划，它跑一个有序流程：调用 prefill pod，等待，调用 decode pod，然后流式返回响应。

我们的很多灵感来自 Endpoint Picker（EPP），即 [Gateway API Inference Extension（GAIE）](https://gateway-api-inference-extension.sigs.k8s.io/) 的路由组件。EPP 实际上只返回单个端点，而我们希望路由层支持多端点的执行。为了获得那份灵活性，我们用 `Prepare` 和 `Execute` 这样的额外阶段扩展了我们的配置。

与 EPP 不同，`Prepare` 是与打分分离的独立阶段。Tokenize 和 block 哈希很贵，而从头部提取会话键很便宜。把这些混进打分，会逼你对每个打分器重做昂贵工作，并给共享派生输入的打分器把依赖图搞复杂。把 Prepare 分出来，让框架有单一处去运行昂贵的变换、并把结果缓存给流水线的其余部分。

此外，`Execute` 是一流的阶段，而非隐式一步。EPP 的流水线止于 `Pick`，而执行结果的东西活在流水线之外。这对单次派发路由管用——那里"执行"就是单个 HTTP 代理。但当执行有自己的结构时它就崩了，正如分离式 prefill/decode 那样——那里计划是一个序列而非单步。把 `Execute` 放进流水线，同一套框架就能用同一个抽象同时处理简单和复杂的派发。

## 插件能组合，算法不能

这五个阶段之所以可组合，是因为它们有明确定义的接口和清晰的关注点分离。一个打分器在一个准则上评估每个候选、产出一个逐候选得分。框架用显式权重组合多个打分器，一个 picker 选出胜者。不同的路由策略通过组合这些可复用插件来创建，从而更容易实现新模式。

`RoundRobinScorer` 优先给轮转里的下一个端点。当它与 `LeastLoadScorer` 组合时，那个优先会被加权向更空的队列。

一致性哈希有一个从请求派生哈希键的 preparer，和一个选出匹配那个键之候选的 picker。潜在候选可以按负载、缓存亲和、局部性，或任何加权组合作打分。

缓存感知路由用两个 preparer 和两个 scorer。preparer 预先对提示词做 tokenize 和哈希。`CacheAffinityScorer` 奖励那些已经持有 block 的 pod，而 `LeastLoadScorer` 防止热点化。权重控制着复用与容量之间的那个权衡。

类似地，把缓存感知路由与会话粘性结合，可以通过组合现有的 preparer 和 scorer 达成。一旦你有了带干净接口的五个阶段，那些熟门熟路的路由行为就被分解成阶段级插件。而这些插件组合成新的执行模式。

## 插件之间的带类型状态

插件之间需要通信。`TokenizePreparer` 产出一个 `BlockHashPreparer` 消费的 token 数组，而它之后又被 `CacheAffinityScorer` 消费。

它们如何在彼此不耦合的情况下通信？框架在 `RoutingContext` 上提供带类型的槽。一个槽是一个带名字和编译期类型的带类型键。`TokenizePreparer` 写进 Tokens 槽。`BlockHashPreparer` 读 `Tokens` 并写 `BlockHashes`。`CacheAffinityScorer` 读 `BlockHashes`。这三个插件里没有一个需要引用彼此就能完成这些读/写。

这层间接带来两个好处：

- **解耦：** 你可以把 `TokenizePreparer` 换成另一个实现（一个为特定模型系列调优的 tokenizer），而下游任何插件都毫不知情。要紧的只是有东西写进 Tokens 槽。
- **编译期带类型：** 槽是带类型的，读取者拿到正确的类型。不匹配是构建期错误，因此更容易追踪和解决。

对比一下 EPP 的做法。EPP 通过一个叫 `CycleState` 的结构共享逐请求的插件状态，它背后是一个以不透明字符串为键、以 interface{} 类型值为内容的键值存储。其上添加了类型安全的泛型访问器，它们在调用点抓住类型不匹配。然而，存储骨子里仍是字符串键的。两个插件可以各自独立选了同一个键而冲突，而直到生产里出问题时系统里才没有任何东西察觉。Gateway API Inference Extension（GAIE）社区意识到了这一点，正在积极讨论改进。

我们能在构建期用带类型、解析于构建期的槽来补上这个缺口。

## 构建期校验

当框架组合一个路由配置时，它能静态检查一组不变式：每个槽读取者都有一个写入者，每个声明的依赖都出现在组合里，依赖图没有环，没有两个插件被错序或声明了冲突的依赖。

如果任何检查失败，服务就不启动。运维者在部署时看到一条结构化错误，而不是在生产里一次失败的读时才遇上来。你可以放心地构建新配置，因为错误会立刻浮现。

## `Selector` / `Workflow` / `Executor` 的拆分

到目前为止，我们描述的是一条单次派发流水线：一趟通过 `Prepare` → `Filter` → `Score` → `Pick` → `Execute`，选一个 pod、发一次 HTTP 调用。多数路由长这样，但分离式 prefill/decode 不是。分离意味着一个客户端请求由两个 pod 服务。Prefill 构建 KV 缓存，decode 生成 token。路由得两个都选，而第二次选择依赖于第一次。

框架用五个阶段流水线之上的一个三层抽象来处理这个。

`Selector`：一个 `Selector` 是一趟通过 Prepare → Filter → Score → Pick。它取一组候选、返回一个选定的候选（或一个排名清单）。

`Workflow`：一个 `Workflow` 组合一个或多个 `Selector`、产出完整的 `RoutingPlan`。一个单次派发的 `Workflow` 用一个 `Selector`。一个 prefill/decode 的 `Workflow` 用两个。一个给 prefill pod，一个给 decode pod。decode `Selector` 的决策可以依赖于 prefill `Selector` 选了什么，因为它们共享一个 `RoutingContext`。

`Executor`：一个 `Executor` 取 `RoutingPlan` 并派发它。一个单次派发的 `Executor` 做一次 HTTP 代理。一个顺序 `Executor` 做 prefill-等待-然后-decode 的模式，并在每一步带有请求改写、body 注入和响应流式输出的钩子。

这个组合线性扩展。单次派发用一个 `Selector`，分离式 prefill/decode 用两个。一个假设性的三步工作流（先过一个预处理器路由、然后 prefill、然后 decode）会用三个。`Workflow` 抽象处理任意数量所需 `Selector` 的组合。新增一个执行模式需要的是一个不同的 `Workflow` 和一个不同的 `Executor`，而不是一个新的 HTTP 处理器。

## 执行层：多步协调

`Selector`、`Workflow`、`Executor` 的拆分在分离式 prefill/decode 上最有价值——那里一个单一请求由两个 pod 服务，需要额外协调。在 prefill 构建好 KV 缓存之前，decode 不能开始。两个 pod 的选择可以并发发生（prefill 和 decode 选择是独立的决策），但执行是顺序的：

- 用 max_tokens=1 把请求发给 prefill pod。
- 等待 prefill 完成。
- 带一个指向 prefill pod 缓存的缓存提示，把请求发给 decode pod。
- 把 decode pod 的 token 流式返回给客户端。

一个分离式 `Workflow` 用两个共享同一个 `RoutingContext` 的 `Selector`。共享一个上下文让第二个决策能建立在第一个之上。prefill `Selector` 记录它选的 pod，decode `Selector` 读那个值，好让它能优先一个靠近 prefill pod 的 decode pod，最小化缓存必须迁移的距离。随后那个顺序 `Executor` 执行上面这些步骤、并把响应流式返回给客户端。

每个 `Selector` 都用与单次派发路由相同的插件和打分，运行同样的 `Prepare`、`Filter`、`Score` 和 `Pick` 阶段。

分离是否有帮助取决于工作负载。加州大学圣迭戈分校的 Hao AI Lab 发表了一篇 [18 个月回顾](https://haoailab.com/blogs/distserve-retro/)，讲分离在哪里有用、哪里没用。简短版本：分离在长上下文、缓存冷的负载上胜出，而在短上下文、高命中率负载上落败。

当分离确实划算时，框架用的是与单次派发路由相同的插件、同一个 `RoutingContext` 和同样的打分逻辑。不需要一个平行的系统。

## 新增一个行为

往这个框架里加一个新路由行为要四步。

假设我们想要一个地理邻近打分器，优先选与客户端同区域的 pod。我们会实现 `Scorer` 接口、带一个 `Score(ctx, candidates) []float64` 方法，把插件类型注册到框架的插件登记表，把这个打分器加进想要它的各个配置，并把它对其他打分器加权。配置作者决定权重，而框架在启动时校验组合。

## 三层，一套框架

在这三篇里，我们演示了 Modular Cloud 的路由层如何让我们快速实现新的路由优化。数据层以微秒查询延迟追踪哪些 KV 缓存 block 住在哪些 pod 上。决策层把路由行为表达成可组合的插件，而非硬编码的算法。执行层在一个请求触及多个 pod 时（如分离式 prefill/decode）协调多步流程。

我们计划在本系列之后跟进一篇对推理调度的深度剖析。路由决定哪个 pod 处理一个请求。调度决定哪些请求接下来跑、以什么批次、对着什么缓存状态。这个博客系列将探索我们如何把调度当作单一系统来对待，从而让我们对大规模推理做整体优化。
