# 我如何用 AI 智能体构建纯 Mojo 应用（和 10 个库）

几天前 Modular 发布了 [Translating to Mojo via AI Agents](https://www.modular.com/blog/translating-to-mojo-via-ai-agents)，Brad 在其中演示了如何使用官方 [`modular/skills`](https://github.com/modular/skills) 把 CUDA softmax kernel 翻译为可移植的 Mojo，并在一次智能体运行中把五个社区项目升级到 `mojo == 1.0.0b1`。那篇回答的是“今天智能体能否把一个定义良好的东西移植到 Mojo？”——答案是能。

**本文回答下一个问题**：这种能力能扩展到多远？用同样的 skills、同样的 `1.0.0b1` 编译器和几周的业余时间，一个开发者加一个智能体能否立起一整个全新的生态系统？mobin 及其 10 个库就是结果。

我上线了一个生产级 pastebin 服务（HTTP 服务器、WebSocket 实时流、SQLite 数据库、JSON 序列化、URL 路由、gzip 压缩等），后端零 Python。全部是 [Mojo](https://docs.modular.com/mojo/)。你现在就可以访问 [mobin.fly.dev](http://mobin.fly.dev/) 试用。

故事的重点不是 pastebin。重点是：为了构建这一个应用，我最终从零构建了 10 个 Mojo 库和一个文档工具，全程借助 AI 编码智能体（以及 [agent skills](https://www.modular.com/blog/translating-to-mojo-via-ai-agents)），作为副业项目。整件事只花了几周的零敲碎打，而不是数月的全职投入。

这就是 [Andrej Karpathy](https://karpathy.bearblog.dev/sequoia-ascent-2026/) 近期所称的 *Agentic Engineering*（智能体工程）。引用他 2026 年 1 月 26 日的 [X 帖子](https://x.com/karpathy/status/2015883857489522876)：

> I rapidly went from about 80% manual+autocomplete coding and 20% agents in November to 80% agent coding and 20% edits+touchups in December. I really am mostly programming in English now... This is easily the biggest change to my basic coding workflow in ~2 decades of programming and it happened over the course of a few weeks.

这个比例与我的体验吻合。我设计 API、做架构决策；智能体写 FFI 绑定、测试套件和大部分跨仓库升级工作。Karpathy 在 Sequoia Ascent 2026 上把同一转变概括为从“vibe coding”（抬高地基线）到“Agentic Engineering”（抬高天花板）：更多纪律、更多编排、*更多品味*，以及少得多的打字。

Chris Lattner 在 [What the Claude C Compiler reveals about the future of software](https://www.modular.com/blog/the-claude-c-compiler-what-it-reveals-about-the-future-of-software) 中从平台侧说了同一件事：AI 正从代码补全走向工程参与，实现性工作正在被自动化，稀缺的技能变成了架构、设计与判断。

这是一次刻意的演练。[Mojo 1.0 beta 已来](https://www.modular.com/blog/the-path-to-mojo-1-0)，我想在 `mojo == 1.0.0b1` 上压力测试整个生态，构建一个触及每一层的东西：网络、持久化、序列化、配置、测试、文档。Mojo 能做的已经远比人们想象的要多。

## 我们构建了什么

[mobin](https://github.com/ehsanmok/mobin) 是一个 pastebin 服务。粘贴代码、得到可分享链接，还有一个通过 WebSocket 推送的新粘贴实时流。后端是一个 1.1 MB 的 AOT 编译 Mojo 二进制，跑在免费档 [Fly.io](http://fly.io/) 的 `shared-cpu-1x` 256 MB 虚拟机上，前面是 [flare](https://github.com/ehsanmok/flare) 的多 worker reactor（每个 CPU 核一条 pthread，因此生产 VM 上 1 个 worker，多核主机上 N 个），中间件栈负责 gzip 压缩与基于 ETag 的 304 缓存。`fly logs` 里应用侧延迟为每请求 1 ms。

为了构建它，我需要一些尚不存在或缺少特定功能的库。于是我把它们造了出来：

## AI 智能体如何加速一切

整个项目我都用 [Cursor](https://cursor.com/) 配合 [Mojo agent skills](https://github.com/modular/skills)。工作流大体遵循典型的智能体开发模式：

- 我在 plan mode 里描述库应该做什么、API 面、关键类型、按我的品味它用起来应该是什么感觉，迭代几轮直到对方案满意。
- 智能体搭出包结构、写核心逻辑、生成初版测试套件。
- 我审查 API 设计，调整命名与签名，对任何不够 Pythonic 的地方提出异议。
- 智能体补齐边界情况、增加测试、写 docstring。
- 重复。

智能体省时最多的是 FFI 样板。`sqlite` 有约 40 个到 `libsqlite3` 的函数指针绑定。`json` 包装了 simdjson 的 C API，还带一个原生 Mojo CPU 后端。`uuid` 调用操作系统随机数生成器。手写这些代码既繁琐又易错。智能体每次都能在第一或第二次尝试就生成正确代码。

库调研是另一个大项。写任何新库之前，我会把智能体指向已有成果并要求综合报告。[morph](https://github.com/ehsanmok/morph) 的编译期反射 serde 就是对 [reflect-cpp](https://github.com/getml/reflect-cpp) 设计的直接移植。[flare](https://github.com/ehsanmok/flare) 的中间件、路由器、typed-extractor 和每 worker `SO_REUSEPORT` 监听器等形态，收敛到了 Rust 侧 actix_web、hyper、axum 以及 Python 侧 FastAPI 验证过的做法。智能体读设计文档比我快，还能指出两个库在某原语上的分歧。

测试生成也是一大收获。我描述想测的行为，智能体产出 15 到 20 个带我想不到的边界用例的测试函数。整个生态有数百个测试，多数由智能体编写。

跨仓库依赖更新同样出色。到了把所有库升级到 `mojo = "==1.0.0b1"` 的时候，我对智能体说：“按 changelog 把所有仓库改为 pin mojo 1.0.0b1，修复破坏、测试并推送。”它逐仓库更新 pin、修复编译错误、跑测试、提交并推送。整次版本提升在所有仓库中几乎作为一趟机械化流程完成。下文的 `pixi-build` 源码构建依赖模型，是那趟流程如此顺滑的另一个原因。

仍然需要我来判断的：API 设计、架构权衡、跨 nightly 版本的兼容性排障。智能体擅长执行定义良好的计划；人决定计划应该是什么。

## API 设计：从 Python 的最佳实践中汲取，带上 Mojo 风味

每个库的指导原则都是：看开发者已经熟悉并喜爱的 Python API，然后在 Mojo 中复刻那种手感。不要发明新模式。Mojo 给你系统级性能，但调用点应该读起来像 Python 等价物。这才是降低采用门槛的方式。Python 开发者应能读 Mojo 代码并立刻知道它在干什么。

套路很简单。设计任何库前，我先研究该领域成熟的 Python API 并把它当蓝图。Mojo 让这件事很容易，因为它的许多构造本身就是 Pythonic 的。

### 数据模型：`@dataclass` 变为 `@fieldwise_init` struct

Python 开发者用 `@dataclass` 定义数据。[mobin](https://github.com/ehsanmok/mobin) 的 `Paste` struct 用同样的形态：

mojo

```
@fieldwise_init
struct Paste(Defaultable, Movable, ImplicitlyCopyable):
    var id: String
    var title: String
    var content: String
    var language: String
    var created_at: Int
    var expires_at: Int
    var views: Int

    def __init__(out self):
        self.id = ""
        self.title = ""
        self.content = ""
        self.language = "plain"
        self.created_at = 0
        self.expires_at = 0
        self.views = 0
```

如果你在 Python 里用过 `@dataclass`，合成出来的构造函数会很眼熟，但 `@fieldwise_init` 在设计上比 `@dataclass` 更窄。它**只**生成按字段的位序 `__init__`，不做别的事（更多细节见 [Mojolang 文档](https://mojolang.org/docs/reference/decorators/fieldwise-init/)）。

### Flare 的风味：Rust 的 reactor，Python 的人机工程

[flare](https://github.com/ehsanmok/flare) 是一个 thread-per-core reactor（`kqueue` / `epoll`），上面套一个 FastAPI 形状的 handler API。三个层次，三组前人成果。

**底层（reactor）。** 每 worker 一个事件循环，不是一连接一线程，热路径无锁。与 `tokio` 和 `nginx` 同形。默认多 worker 模式用 `SO_REUSEPORT` 绑 N 个监听器（对应 `actix_web`）；`FLARE_REUSEPORT_WORKERS=0` 切换为 tokio 风格的共享 accept（对应 `hyper` / `axum`）。在 4-worker 基准中，flare 交出了四者中最干净的 p99.99。

**顶层（handlers）。** `def handler(req: Request) -> Response`，正是 Flask 和 FastAPI 用的签名。`Router.get("/path", handler)` 注册它。`from flare.prelude import *` 拉入 `Request`、`Response`、`Router`、`HttpServer`、`ok`、`ok_json`、`not_found`、`bad_request`。Hello world：

mojo

```
from flare.prelude import *

def hello(req: Request) -> Response:    # no raises: body cannot fail
    return ok("hello")

def main() raises:
    HttpServer.bind(SocketAddr.localhost(8080)).serve(hello)
```

**中层（组合）。** 类型化提取器（`PathInt["id"]`、`QueryInt`、`HeaderStr`、`Form[T]`、`Json[T]`、`Cookies`）是 struct 字段，在 `serve` 运行前解析；缺失或畸形输入变成经过净化的 400。与 `axum` 的 extractors 和 FastAPI 的类型化参数同一模型。中间件（`Logger`、`RequestId`、`CatchPanic`、`Compress`、`Conditional`、`Cors`）像 `tower` 层一样嵌套，只是这条链会单态化为每个 handler 一次直接调用序列，没有 vtable 分发。共享状态用 `App[S]` / `State[S]`，与 `actix_web` 的 `Data<T>` 和 `axum` 的 `State<S>` 同形。

传输层（`WsClient`、`TcpStream`、`TlsConnector`、`UdpSocket`）是上下文管理器，所以 Python 风格的 `with` 块会自动执行清理：

mojo

```
with WsClient.connect("wss://echo.websocket.events") as ws:
    ws.send_text("hello")
    msg = ws.recv()
```

mobin 用到了每一层。

### 数据库：`sqlite3` 变为 sqlite

Python 的 `sqlite3` 模块是标准库里使用最广的 API 之一。[sqlite](https://github.com/ehsanmok/sqlite) 库直接照映它：

mojo

```
db = Database(":memory:")
db.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT)")

stmt = db.prepare("INSERT INTO users VALUES (?, ?)")
stmt.bind_int(1, 42)
stmt.bind_text(2, "Alice")
_ = stmt.step()
```

`Database(":memory:")`、`execute()`、`prepare()`、带 `?` 占位符的参数化查询。这些是每个 Python 开发者都在用的模式。其上的 ORM 层遵循同样原则：定义一个 struct，库负责建表和 CRUD。

### JSON：`json` 模块变为 json 库

Python 的 `json.loads()` 和 `json.dumps()` 可能是整个生态里最广为人知的 API。[json](https://github.com/ehsanmok/json) 库精确照映它们：

mojo

```
from json import loads, dumps

var data = loads('{"name": "Alice", "age": 30}')
print(dumps(data, indent="  "))
```

同样的函数名、同样的行为。`load()` 从文件句柄读取，`dump()` 写入句柄。Python 开发者不需要学任何新东西。

但 Mojo 的参数化系统在这里加了 Python 做不到的东西。同一个 `loads` 函数接受编译期 `target` 参数来选择解析后端：

mojo

```
data = loads('{"key": "value"}')                    # native Mojo CPU (default)
data = loads[target="cpu-simdjson"](text)           # simdjson FFI fallback
data = loads[target="gpu"](huge_json)               # GPU-accelerated
values = loads[format="ndjson"](newline_delimited)  # NDJSON format
lazy = loads[lazy=True](huge_json)                  # lazy parsing
```

API 面与 Python 的 `json` 模块完全一致。参数化的 `[target=...]` 就是 Mojo 风味：你在编译期选择更快的后端，调用点不用变。Python 无法表达这一点——你得靠不同的库或运行时开关。在 Mojo 里，它是一个函数加一个编译期开关。

### 序列化：Pydantic 变为 morph

Pydantic 教会 Python 开发者：序列化应该从模型定义自动完成。[morph](https://github.com/ehsanmok/morph) 通过编译期反射做同样的事，而且从单个 struct 定义覆盖多种格式：

mojo

```
from morph.json import write as json_write, read as json_read
from morph.toml import to_toml, from_toml
from morph.csv import to_csv, from_csv

json_str = json_write(paste)         # Paste -> JSON
toml_str = to_toml(paste)            # Paste -> TOML
csv_str  = to_csv(paste)             # Paste -> CSV

from_j = json_read[Paste](json_str)
from_t = from_toml[Paste](toml_str)
from_c = from_csv[Paste](csv_str)
```

一个 struct，三种输出格式。没有 schema 定义、没有手工字段映射、没有格式专属注解。morph 在编译期反射 struct 字段，为每种格式生成序列化代码。心智模型与 Pydantic 的 `model_dump()` 和 `model_validate()` 完全相同，只是横跨 JSON、TOML 和 CSV，一行适配器都不用写。

### 模糊测试：Hypothesis / atheris 变为 mozz

用 [Hypothesis](https://hypothesis.readthedocs.io/) 做基于属性的测试、用 [atheris](https://github.com/google/atheris) 做变异模糊测试的 Python 开发者会一眼认出 [mozz](https://github.com/ehsanmok/mozz)：

mojo

```
from mozz import fuzz, FuzzConfig

def target(data: List[UInt8]) raises:
    _ = some_parser(data)

def main() raises:
    fuzz(target, FuzzConfig(max_runs=100_000, seed=42))
```

一次调用即变异模糊测试，就像 atheris。带自动收缩（shrinking）的属性测试，就像 Hypothesis。定义一个性质、提供一个生成器，mozz 会把失败输入最小化到可复现的最小用例。

这是刻意的策略，不只是风格偏好。Mojo 最大的采用优势在于 Python 开发者的人数已胜过其他一切系统编程社区。如果你的 Mojo 库用起来像他们已经在用的 Python 库，学习曲线几乎归零。他们得到熟悉的 API，底下是编译性能、SIMD 和 `comptime`。你不需要向他们推销新范式，只需展示同样的模式跑得更快。

## 测试

每个库都遵循同一测试模式。测试用 `std.testing` 断言，跑在内存 fixture 上，不需要外部测试运行器。

[mobin](https://github.com/ehsanmok/mobin) 里的一个典型测试：

mojo

```
def _open_db() raises -> Database:
    db = Database(":memory:")
    init_db(db)
    return db^

def test_db_create_and_get() raises:
    db = _open_db()
    p = _make_paste("id-1", "Hello", "print('hi')")
    db_create(db, p)

    got = db_get(db, "id-1")
    assert_true(got.__bool__())
    paste = got.value()
    assert_equal(paste.id, "id-1")
    assert_equal(paste.title, "Hello")
    assert_equal(paste.content, "print('hi')")
```

`Database(":memory:")` 给每个测试一个全新的 SQLite 数据库。无共享状态、无清理、无需管理 fixture。测试并行运行互不干扰。

对处理不可信输入的库（[flare](https://github.com/ehsanmok/flare)、[sqlite](https://github.com/ehsanmok/sqlite)），我用 [mozz](https://github.com/ehsanmok/mozz) 做模糊测试。mozz 有两种模式。

变异模糊测试向你的解析器投掷随机字节序列，检查它干净地抛错而不是 panic：

mojo

```
fuzz(target, FuzzConfig(max_runs=100_000, seed=42))
```

属性测试生成类型化的值并验证不变量：

mojo

```
forall[UInt8](
    uint8_always_in_range, gen_uint8, minimize_uint8, trials=500, seed=1
)
```

当某个性质失败，mozz 自动把失败输入收缩为可复现的最小用例。这在 sqlite 的文本处理和 flare 的 HTTP 头解析中抓到过真 bug。

CI 通过 GitHub Actions 在每次 push 上运行，配 [Pixi](https://pixi.sh/)：

mojo

```
steps:
  - uses: actions/checkout@v4
  - uses: prefix-dev/setup-pixi@v0.9.4
  - run: pixi run tests
```

checkout 之后只有两行 YAML。CI 配置在所有 Mojo 仓库中完全相同。

## 每个库一致的结构

生态中每个库都遵循同一布局：

mojo

```
lib_name/
├── lib_name/          <- Mojo package directory
│   ├── __init__.mojo
│   └── ...
├── tests/
│   └── test_*.mojo
├── pixi.toml          <- dependencies + tasks
├── LICENSE
├── README.md
└── .github/workflows/ci.yml
```

处处同一 CI 模板：`setup-pixi` 然后 `pixi run tests`，在 `ubuntu-latest` 与 `macos-15` 上做矩阵。同一测试模式：`std.testing` 断言、内存 fixture、每个测试文件一个 `def main()` 入口。

这种一致性比看上去更重要。当所有库工作方式相同，你无需学习新的项目结构就能给其中任何一个做贡献。AI 智能体也能干得更快，因为模式可预测。

## 用 Pixi 做包管理

如果你用过 [uv](https://docs.astral.sh/uv/)，[pixi](https://pixi.sh/) 感觉就像 uv++。对通过 `--pypi` 添加的 PyPI 依赖，pixi 底层用 uv；对 Conda 包则用自家的高速 Rust 求解器。它是 Mojo 项目的正确工具，有两个具体原因。

第一是 `pixi-build`，即 Mojo 库的源码构建路径。启用 `preview = ["pixi-build"]` 后，pixi 通过 [`rattler-build`](https://prefix-dev.github.io/rattler-build/) 解析你以 git tag 标定的 Mojo 依赖，由它针对使用者声明的 `mojo` 版本从源码构建每个库。Mojo 包没有 Conda channel，也没有预构建的 `.mojopkg` 可分发。依赖图中的每个库都用你项目 pin 的同一编译器构建，这意味着两个库不可能对“自己是用哪个 Mojo 版本构建的”产生分歧。曾经困扰早期 Mojo 开发的 MLIR 字节码不兼容陷阱，在这个模型下消失了。

第二是 `pixi.lock` 把每个传递依赖 pin 到精确构建。两位开发者运行 `pixi install` 得到逐字节一致的环境。配合源码构建，一个声明的 `mojo == 1.0.0b1` 可以可复现地贯穿整张依赖图。

[mobin](https://github.com/ehsanmok/mobin) 实际的 `pixi.toml` 长这样：

mojo

```
[workspace]
name      = "mobin"
platforms = ["linux-64", "osx-arm64", "linux-aarch64"]
preview   = ["pixi-build"]

[dependencies]
mojo   = "==1.0.0b1"
flare  = { git = "https://github.com/ehsanmok/flare.git",  tag = "v0.7.0" }
json   = { git = "https://github.com/ehsanmok/json.git",   tag = "v0.1.6" }
morph  = { git = "https://github.com/ehsanmok/morph.git",  tag = "v0.1.2" }
sqlite = { git = "https://github.com/ehsanmok/sqlite.git", tag = "v0.1.2" }
envo   = { git = "https://github.com/ehsanmok/envo.git",   tag = "v0.1.2" }
uuid   = { git = "https://github.com/ehsanmok/uuid.git",   tag = "v0.1.2" }
tempo  = { git = "https://github.com/ehsanmok/tempo.git",  tag = "v0.1.2" }
pprint = { git = "https://github.com/ehsanmok/pprint.git", tag = "v0.1.2" }
```

每个依赖都是指向带 tag 发布的 git 引用。[flare](https://github.com/ehsanmok/flare) 是最成熟的库，停在 v0.7.0，完成了多 worker reactor、中间件和 typed-extractor 的工作；生态其余部分是更小、聚焦的库，停在 v0.1.x。像 openssl、ca-certificates 和 zlib 这样的系统库仍来自 Conda channel，因为它们不是 Mojo 包，pixi 把这部分也打理得很好。

整个 mobin 项目（Mojo 编译器、全部 8 个 Mojo 依赖、系统库）冷启动 `pixi install` 在源码构建流水线已暖的情况下不到 30 秒。热安装几乎瞬时。

## 今天在 Mojo 1.0.0b1 上构建

Mojo 的 Beta-1 已经发布。semver 的承诺是认真的：针对 1.0.x 构建的包在整个 1.x 系列中会持续可用。[The path to Mojo 1.0](https://www.modular.com/blog/the-path-to-mojo-1-0) 一文讲述后续故事。

生态需要库。当 1.0 发布时，已经存在的项目会成为所有人赖以构建的地基。HTTP 服务器、数据库绑定、序列化、测试工具、CLI 框架。这些都应当存在，而成为“早期者”的窗口就是现在。

我对此有一个判断：如果我们正确运用 Agentic Engineering，Mojo 1.0 之后的第一年至少会像 Rust 1.0 之后的第五年。Rust 的生态花了多年才建立，因为每个 crate 都是手写的。有了智能体工程，一个开发者带着自己的品味能在几天内交付一个测试完善的库，而不是几个月。我在几周内构建了 10 个库和一个生产应用。把这一点乘上一个以同样方式工作的开发者社区，生态会迅速充实。

这条路对任何人可行。挑一个生态缺口。用 Pixi 做包管理，用 `preview = ["pixi-build"]` 做源码构建。遵循一致的项目结构。先规划，再写 Pythonic 的 API。用 `std.testing` 和 mozz 测试。用 GitHub Actions 配 CI。发布。
