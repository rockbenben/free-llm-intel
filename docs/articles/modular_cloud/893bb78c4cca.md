# 2025 年的 PyTorch 和 LLVM——跟上人工智能创新的步伐

我和几位队友有幸参加了 AI 软件栈的两场近期开发者大会：在旧金山举行的 [PyTorch Conference 2025](https://pytorch.org/event/pytorch-conference-2025/)（10 月 22-23 日）和在圣克拉拉举行的 [LLVM Developers' Meeting](https://llvm.swoogo.com/2025devmtg/home)（10 月 28-29 日）。这篇博客分享我在大会演讲和与开发者的交流中最突出的几点观察。

这两场服务的是迥然不同的社区——PyTorch 在 AI 应用层，LLVM 在编译器基础设施层。但我观察到了惊人的趋同：随着 AI 创新加速，两个社区都在与同样根本的基础设施难题搏斗。

## PyTorch Conference：不确定的开发者未来

在 PyTorch 大会，我印象最深的一幕发生在给一位计算机专业学生看我们的演示之后。我问她有什么问题，本以为会是性能对比或编译器逻辑之类。结果她讲的是她为研究项目开发内核时遇到的种种挑战。和 PyTorch 上的许多开发者一样，她最习惯写 Python，觉得内核优化所需的那一堆语言和框架又多又复杂、令人喘不过气。她问："我该怎么学？从哪里开始？"

作为教育者，我很爱听这样的问题。但她的故事捕捉到了一种我在各场报告和整个展厅里都感受到的不确定感。谁都不想掉队，可从研究到生产的路上却摆着那么多面向不同阶段的语言和框架。当前生态要求把一堆彼此割裂的工具拼起来、再确保它们高效协同——在一个由硬件多样性和模型快速演进定义的未来，这条路越走越显得力不从心。

行业变化如此之快，许多与会者讨论的不是 *AI 几年后会做什么*——而是*他们自己将在 AI 里做什么*。这种对 AI 开发中人的体验的关注，贯穿了整个座谈会和演讲。

图片由 PyTorch Foundation 提供

当 [Mark Saroufim 展示 Backend Bench](https://youtu.be/XdORM2pkyH8?si=MBYzF-rkIRszcaAs) 时，他抛出问题："如果我们能让 LLM 把这些算子全写出来，快速拉起一个新后端，会怎样？"在介绍 Helion（他称之为"带 tile 的 PyTorch"）时，他着重强调了 LLM 用 Helion 编程有多容易。贯穿这些话题，Saroufim 描绘了一个由 LLM 生成内核并自动调优到高效性能的未来。

在 [Jeremy Howard 与 Anna Tong 的主题对话](https://youtu.be/w-A77TVr2fs?si=MHGoh0ECAPJvTwhw)中，他谈到了自己所说的"vibe coding 的反面"——用 AI 来提升你的能力、学习新东西，而不是把复杂性自动化掉。关于 LLM 在 AI 开发中能做到什么、开发者真正愿意把哪些工作交给 LLM，仍有大量开放问题。

来到我们展位的与会者提出了类似的问题：怎么用 LLM 写 Mojo 内核。这显然是许多人心里在想的事——如何让重复劳动更高效，同时不牺牲那些帮你解决明天更难问题的学习？比起代码助手的现状，人们更好奇几年后的 AI 工程长什么样。

### 硬件多样性

AI 世界的不确定性与机遇，在硬件侧同样清晰。2025 年 AI 数据中心大幅增长，对硬件的需求毫无降温迹象。大会如实反映了这一点——大大小小的硬件厂商同台争夺市场份额。

大量报告聚焦 CUDA，印证了 [NVIDIA 拥有深厚的软件护城河](https://www.modular.com/blog/democratizing-ai-compute-part-9-why-do-hw-companies-struggle-to-build-ai-software)。然而数据中心和边缘设备上的硬件多样性都在快速扩张。其他玩家也在重金投入——从 AMD、Intel、高通等传统厂商，到 Google（TPU）、AWS（Trainium）这样的科技巨头，再到 Groq、Rebellions、Tenstorrent、Furiosa（我们的展位邻居）等加速器初创。

开发者要跟上跨硬件世代的架构变化、管理当前栈中的多样硬件，挑战巨大。在[主题技术深潜](https://youtu.be/XdORM2pkyH8?si=_U4RufSdhDCF-adN)中，Meta 的 Peng Wu 指出异构硬件是 AI 推理领域的首要行业趋势。不少演讲者和与会者提到 Anthropic 的[三起近期故障的复盘文章](https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues)——其中描述了同一批 bug 在不同平台上以不同速率表现出不同症状。Anthropic 那篇难得坦诚的复盘显然引起了共鸣：开发者们早已感到硬件变化快过他们评估和调试性能问题的速度。

来源：PyTorch Foundation YouTube 频道

要在现代 GPU 上达成峰值性能，需要对硬件特定功能的深度专业知识——而这些功能每一代硬件都在变。开发者常常必须下沉到 CUDA C++ 甚至更低层的 PTX 汇编才能解锁新硬件的性能红利，这让内核编写成了只有专家工程师才能穿行的瓶颈。

与此同时，另一些团队正在迈向编译器优先的未来：PyTorch Dynamo、TorchInductor 以及 TileIR 这类编译器 dialect 等工具，从更高层的抽象自动生成内核。（我们博客里[关于 AI 编译器还有更多](https://www.modular.com/blog/democratizing-ai-compute-part-6-what-about-ai-compilers)。）

作为一种替代路径，Spenser Bauman 做了题为 [Mojo + PyTorch: A Simpler, Faster Path To Custom Kernels](https://www.youtube.com/watch?v=mket48-xpSk) 的演讲，讲解如何用 Mojo（一门 Python 风格的语言）编写既高性能又硬件无关的 GPU 内核。几乎所有和我聊过内核开发的开发者都提到了同样的目标。

开发者想要的是：在多样且不断变化的硬件栈上实现高性能推理——但不以开发者体验为代价。如果要改变流程，他们希望有一门语言同时满足可移植性和精确控制。他们还想写出能活得比单一硬件世代更久的代码。和这么多以开放心态、学习热情面对行业不确定性的人交流，令人如沐春风。

## LLVM Developers' Meeting：如何为多样硬件而构建

接下来的那一周，我参加了 LLVM Developers' Meeting。

虽然大会的编译器话题五花八门——从优化 C 循环到缓解硬件漏洞——但有多场报告表明，LLVM 社区正面对和 PyTorch 社区一样的硬件多样性挑战。

今年的 LLVM Developers' Meeting 反复出现一个焦点：[MLIR](https://mlir.llvm.org/)——一个专为给多样硬件构建编译器而设计的开源编译器框架。MLIR 贯穿全场，从培训工作坊到 dialect、模式重写、崩溃复现工具，乃至用于 MLIR 可编程性的 Python DSL。

LLVM 社区持续采用 MLIR，为爆发式增长的硬件目标——CPU、GPU、TPU 及其他 AI 加速器——构建稳固支持，同时不碎片化自己的工具、不制造维护噩梦。Modular 团队也做了关于我们 MLIR 实践的报告——MLIR 正是 Mojo 编程语言和 MAX 图编译器的地基（幻灯片链接见下文）。

### 以十年为单位思考，而不是以年

两场大会都以开源工具为中心，因此开源话题主导了关于 AI 未来的讨论不足为奇。Meta 的 Alban Desmaison 庆祝了 PyTorch 九岁生日，并强调了 GitHub 贡献规模的增长。Jeremy Howard 称开源是[「全球社区推进我们软件能力的正确方式」](https://youtu.be/w-A77TVr2fs?si=fewE7Af4ryApvog1&t=816)，并提到 [DeepSeek 对开源社区的巨大影响](https://www.modular.com/blog/democratizing-compute-part-1-deepseeks-impact-on-ai)。

LLVM Developers' Meeting 的主题演讲以开源项目的长期视角脱颖而出。Arm 主任工程师 Peter Smith 开场先回望了 25 BC——即 Clang 纪元前 25 年（[Before](https://clang.llvm.org/) Clang）的编译器世界。他以技术细节回顾了自己和团队如何用 15 年时间，一步步把 Arm 工具链中的专有部件替换成 LLVM 技术——如今提供了基于 LLVM libc 的完全开源工具链。他谈的是那些将影响团队未来数十年工作的迁移与维护策略决策。

围在 Weiwei Chen 的 Mojo GPU Compilation 海报前的编译器工程师们同样在作长期思考。要造能活几十年的软件，不能为单一芯片做优化。你得跨设备、跨厂商、跨工作负载解决性能问题。你得有办法[同时为眼前的硬件和尚不存在的硬件构建](https://www.modular.com/blog/modulars-bet-to-break-out-of-the-matrix-democratizing-ai-compute-part-10)。这种长期思维对社区氛围的影响显而易见：来自彼此竞争的硬件厂商和软件团队的开发者对彼此的工作表现出真诚的兴趣与热情——他们看起来并不纠结今天是谁最大，而在乎一起为未来造点东西。

## 趋同：同样的问题，不同的层

连着参加两场大会，一个清晰的模式浮现出来：无论你工作在 PyTorch 的 AI 层还是 LLVM 的编译器层，你面对的挑战都类似：

- **两种语言问题**：PyTorch 开发者写 Python，但性能上仍需要 C++。编译器开发者支持高层语言，但必须理解底层硬件。
- **硬件碎片化**：AI 加速器大爆发——NVIDIA、AMD、高通、定制 ASIC——意味着两个社区都花费巨大精力跨厂商、跨世代做硬件特定优化。
- **性能 vs. 生产力**：研究者想要 Python 的易用。生产工程师需要 C++ 的性能。编译器工程师想要可移植，却又需要硬件特定优化。
- **速度 vs. 稳定**：AI 跑得太快，工具链疲于奔命。等基础设施为一个世代的模型或硬件成熟，下一波已经到来。

还有一种说法是"权衡的超立方体"（hypercube of tradeoffs）——Feras Boulala 在他关于我们 MAX JIT 图编译器的演讲中提到。他用这个词描述深度学习工程师面对的软件困境——不只是性能与可移植性、底层控制与高层抽象之间的权衡，还有调试能力、可扩展性等众多维度的取舍。

## 弥合鸿沟：一体化的进路

与两场大会上的开发者交流，我注意到一个模式：他们要找的不是对现有工具的渐进改进。他们在想是否存在一种根本不同的进路——能把这些权衡坍缩掉，而不逼他们二选一。

我们相信 Modular Platform 提供的正是这种根本不同的进路。

Modular Platform 的中心是 **Mojo 语言**。它自底向上构建于 MLIR 之上，为全栈提供单一编程语言——从 CPU 上的高层 AI 应用代码，一直到底层 GPU 内核。在两场大会上，我们通过这几场报告分享 Mojo 如何解锁可编程性、性能与可移植性：

- PyTorch Conference 上 Spenser Bauman 的 "Mojo + PyTorch: A Simpler, Faster Path To Custom Kernels"，展示如何用 Mojo 为 PyTorch 编写 GPU 内核，交付高性能且硬件无关的内核。[查看幻灯片](https://modular-assets.s3.us-east-1.amazonaws.com/slides/PyTorch-Conf-2025-Mojo-PyTorch-custom-kernels.pdf)并在 [YouTube 观看](https://www.youtube.com/watch?v=mket48-xpSk)。
- LLVM 大会上 Billy Zhu 和 Chris Lattner 的 "Building Modern Language Frontends with MLIR"，技术深潜 Mojo 如何利用 MLIR 为异构计算构建编译期元编程系统。[查看幻灯片](https://modular-assets.s3.us-east-1.amazonaws.com/slides/LLVM-Mtg-2025-Modern-Language-Frontends-with-MLIR.pdf)。
- LLVM 上 Weiwei Chen 和 Abdul Dakkak 的 "Mojo GPU Compilation"，一场闪电演讲，讲 Mojo 独特的编译流程如何支持 CPU+GPU 编程、并把 GPU 内核高效卸载到加速器。[查看幻灯片](https://modular-assets.s3.us-east-1.amazonaws.com/slides/LLVM-Mtg-2025-Mojo-GPU-Compilation-lightning-talk.pdf)。

## 展望未来

PyTorch Conference 和 LLVM Developers' Meeting 上讨论的那些挑战不会消失——随着模型变大、硬件愈发多样，它们只会加剧。前进之路需要一个能够：

- 统一不同背景、不同技能水平的开发者；
- 跨框架与运行时统一底层软件；
- 跨厂商、设备与用例统一硬件的解决方案。

两场大会上的对话说明了一件事：AI 社区不只是准备好接受减少碎片化的方案——他们在主动寻找。那位问"从哪里开始"的学生，和那些以十年为单位思考而非以季度为单位思考的编译器工程师，都在找同一样东西：能跟上创新步伐、又不必让他们不断重建地基的工具。

这正是我们打造 Modular Platform 的原因：它让你用一个统一平台完成构建与部署，而不逼你在性能、可移植性与生产力之间做选择。
