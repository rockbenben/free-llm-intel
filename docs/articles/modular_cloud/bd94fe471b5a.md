# 探索 Mojo 中的元编程

*本文由客座作者 Brian Grenier 撰写。他是一名从事心脏影像处理的 C++ 开发者，也是 Mojo 标准库的活跃贡献者。他维护两个开源 Mojo 库：纯 Mojo 的 JSON 解析器 EmberJSON，以及类型安全的量纲分析工具包 Kelvin。你经常能在 *[*Modular 论坛*](https://forum.modular.com/u/bgreni/summary)* 和 Discord 服务器上看到他的分享与答疑（@eggsquad）。*

Mojo 的参数（parameter）系统是它最强大、最具表达力的特性之一。本文将深入探讨 Mojo 元编程能力中一个聚焦的子集。想要广度优先地了解这些特性，请参阅官方 [Modular 文档](https://docs.modular.com/mojo/manual/parameters/)。

本文许多示例附带 LLVM-IR 片段，用以说明 Mojo 编译器在底层做了什么。如果你不熟悉 LLVM-IR，可以在[这里](https://llvm.org/docs/LangRef.html)找到实用的语言参考。

## 用于编译期计算 parameter

*元编程*是一种在众多编程语言中被广泛使用的技术——我们编写能修改自身或其他代码的代码。Python 在运行时动态完成这些，而 Rust、C++、Mojo 这类编译型语言则提供工具，指引编译器在编译期生成和修改代码。如果你熟悉 Rust 的泛型或 C++ 的模板，Mojo 的 parameter 系统会让你倍感亲切。

元编程的一个常见用途是创建[泛型](https://en.wikipedia.org/wiki/Generic_programming)函数和类型；Python 可以通过[鸭子类型](https://en.wikipedia.org/wiki/Duck_typing)隐式做到。Python 解释器通常不关心变量的类型，直到要对它执行某个操作时才去看——只要你传给函数的类型满足那些操作的要求，一切就能顺利运行。

Mojo

def doubler(a):
    return  a  +  a

b = doubler(2)
c = doubler(1.245)

`‍`不使用泛型的话，Mojo 这样的静态类型语言就必须为同一函数编写多个定义，才能处理不同的输入类型：

Mojo

fn doubler(i: Int) -> Int:
    return i + i

fn doubler(s: Float64) -> Float64:
    return s + s

var a = doubler(2)
var b = doubler(20.0)

`‍`函数重复定义的问题可以用泛型解决，而 Mojo 的泛型正是 parameter 系统的一部分。在 Mojo 中，结构体或函数所需的 parameter 集合用方括号列表定义。所有 parameter 都必须是编译期已知的类型或表达式。Mojo 用 `trait`（特征）告知编译器类型 parameter 可以绑定哪些种类的类型。借助 trait，我们可以这样定义一个 `Addable` trait：

Mojo

trait Addable:
    fn __add__(self, other: Self) -> Self:
        ...

`‍`有了它，我们就能写一个新的 `doubler` 函数，同时作用于上面两种类型——只需告诉编译器："这个函数适用于*所有*带有 `Addable` trait、因而实现了 `__add__` 方法的类型。"

Mojo

@no_inline
fn doubler[T: Addable](a: T) -> T:
    return a + a

‍`‍`深入研究 Mojo 编译器输出的 LLVM-IR，可以看到编译器已经替我们完成了工作——为每个类型生成了不同的函数定义：

LLVM

; Function Attrs: noinline
define internal i64 "playground::doubler[playground::Addable]..."(i64 noundef %0) #1 {
    %2 = add i64 %0, %0
    ret i64 %2
}

; Function Attrs: noinline
define internal double @"playground::doubler[playground::Addable]..."(double noundef %0) #1 {
    %2 = fadd contract double %0, %0
    ret double %2
}

### 函数的 parameter 与 argument

在继续深入之前，"parameter"和"argument"有什么区别？Mojo 允许函数定义两类输入：一类必须在函数实例化时于编译期确定，另一类允许直到运行时调用才确定。我们需要术语来讨论这件事，因此把函数的编译期输入称为"parameter"——你可以说函数被"parameter 化"了——而运行时输入称为 argument。

例如，下面这个函数把 `width` 作为 parameter，它必须在编译期已知。它出现在 `arg1` 和 `arg2`（运行时已知）的类型中，并支持乘法这类运算：

Mojo

fn take_floats[width: Int](arg1: SIMD[DType.float16, width],
                           arg2: SIMD[DType.float16, width*2]):
   constrained[width > 4]()
   ...

def main():
    take_floats(SIMD[DType.float16, 1](),
                SIMD[DType.float16, 2]())) # compile error, width is not > 4

parameter 的值永远不可变，还可以进一步用于其他编译期表达式。注意在 [`constrained`](https://docs.modular.com/mojo/stdlib/builtin/constrained/constrained) 函数调用中，`width` 被用于和 `4` 的比较表达式。`constrained` 让我们能做编译期断言（类似其他语言的 `static_assert`）。这里我们武断地断言 `width` 的值总是大于 4。

parameter 的值还可以"翻墙"进入运行时域——观察常量 `30` 如何被直接放进了 IR 输出的乘法表达式：

Mojo

@no_inline
fn multiplier[m: Int](a: Int) -> Int:
    return m * a  # "m" is a compile time value used at runtime.

def main():
    print(multiplier[30](2))

LLVM

define internal i64 @"playground::multiplier[::Int](::Int),m=30"(i64 noundef %0) #1 {
    %2 = mul i64 %0, 30
    ret i64 %2
}

## `alias` 关键字

Mojo 提供了非常强大的 `alias` 关键字，既能为类型创建新名字，也能定义编译期常量。在后一种情况下，`alias` 相当于编译期版的 `var`。由于 `alias` 定义的值在编译期已知，它们也能用在 parameter 列表里：

Mojo

alias IntList = List[Int]

alias MyConstant = 5

multiplier[MyConstant](10)

`‍`看 IR 输出，`MyConstants` 的值已被直接嵌入表达式：

LLVM

define internal i64 @"playground::multiplier[::Int](::Int),m=5"(i64 noundef %0) #1 {
    %2 = mul i64 %0, 5 ;

<

- The input value being multiplied by our constant 5
    ret i64 %2
}

`‍`多亏了 Mojo 的编译期解释器，`alias` 还能预先计算不平凡的表达式，从而把运行时的计算卸载给编译器：

Mojo

fn fib(n: Int) -> Int:
    if n

<

= 1:
        return n
    return fib(n - 1) + fib(n - 2)

fn main():
    alias f = fib(30)
    print(f)

‍`‍`就这样，这次函数调用被折叠成了一条 store 指令：

LLVM

define dso_local i32 @main(i32 noundef %0, ptr noundef %1) #0 {
    %3 = alloca i64, i64 1, align 8
    ...

    store i64 832040, ptr %3, align 8 ;

<

- the output of fib(30)
    ...
}

`‍`使用 `alias` 时，Mojo *保证*表达式会被完全编译期折叠。任何无法在编译期计算的指令（比如特殊硬件 intrinsic）都会导致编译失败。

你甚至可以为参数化函数创建 alias——回到我们的 `multiplier` 函数，可以造出一个总是把输入乘二的函数：

Mojo

alias doubler = multiplier[2]

def main():
    print(doubler(2))

`‍`编译器有时还能完全省去编译期变量在运行时的实体化。例如，你为一个 `InlineArray` 创建 `alias`，再用编译期已知的值去索引它，编译器会直接把数组访问替换成对应的值：

Mojo

alias l = InlineArray[Int, 3](45, 34, 32)

@no_inline
fn get_val() -> Int:
    return l[1]

fn main():
    print(get_val())

LLVM

define internal i64 @"playground::get_val()"() #1 {
  ret i64 34
}

## 编译期分支

借助 parameter 值的力量，我们甚至可以用 `@parameter if` 语句在编译期做分支决策：

Mojo

@no_inline
fn foo[n: Int]() -> String:
    @parameter
    if n

<

0:
        return "Negative number"
    else:
        return "Positive number"
fn main():
	print(foo[1]())
	print(foo[-1]())

`‍`在 IR 中可以看到，`if` 语句被折叠成了常量值分支。Mojo *保证*不可达代码不会被编译进最终二进制文件。所以它实际上等价于 C/C++ 里的 `#ifdef` 表达式，但强大得多——两个分支都会做类型检查。这意味着编写多设备目标（如 GPU 和 CPU）代码的开发者，在整个代码库中都享有类型安全，无论当前在为哪个平台编译：`‍
`

LLVM

define internal { ptr, i64, i64 } @"playground::foo[::Int](),n=-1"() #1 {
    ...
    br i1 true, label %6, label %9
    ...

最近，Mojo 标准库新增了 `is_compile_time` 函数，允许在编译期和运行时分别执行不同行为：`‍
`

Mojo

@no_inline
fn foo() -> String:
    if is_compile_time():
        return "CTime"
    else:
        return "Runtime"

fn main():
    alias s = foo()
    print(s)
    print(foo())

这通常用于给那些会调用平台特定指令（`MLIR` 解释器无法处理）、或包含编译期无意义表达式的函数提供回退实现。Mojo 标准库中的这个例子就是如此：`‍
`

LLVM

@always_inline("nodebug")
fn assume(val: Bool):
    """Signals to the optimizer that the condition is always true. This allows
    the optimizer to optimize the code.

    Args:
      val: The input value which is assumed to be `True`.
    """
    if is_compile_time():
        return
    llvm_intrinsic["llvm.assume", NoneType](val)

这种情况下，解释器一旦尝试求值 `llvm_intrinsic["llvm.assume", NoneType](val)` 就会报错，所以我们在编译期路径中直接忽略它。

## 循环展开

循环展开是编译器用来省去循环变量递增和分支指令处理开销的优化技术。在性能关键的应用里，程序员甚至会手动展开。在 Mojo 中，用 `@parameter` 装饰器可以确保编译器总是展开特定循环：`‍
`

Mojo

var a = 0
var l = List(1, 2, 3)
for i in range(3):
    a += l[i]

# manually unrolled version
var a = 0
var l = List(1, 2, 3)
a += l[0]
a += l[1]
a += l[2]

# @parameter for
var a = 0
var l = List(1, 2, 3)

@parameter
for i in range(3):
    a += l[i]

在 IR 中可以看到循环已被内联：`‍
`

LLVM

%35 = load i64, ptr %19, align 8
%36 = load i64, ptr %6, align 8
%37 = add i64 %36, %35 ; <- a += l[0]
store i64 %37, ptr %6, align 8
%38 = getelementptr inbounds i64, ptr %19, i32 1
%39 = load i64, ptr %38, align 8
%40 = load i64, ptr %6, align 8
%41 = add i64 %40, %39 ; <- a += l[1]
store i64 %41, ptr %6, align 8
%42 = getelementptr inbounds i64, ptr %19, i32 2
%43 = load i64, ptr %42, align 8
%44 = load i64, ptr %6, align 8
%45 = add i64 %44, %43 ; <- a += l[2]
store i64 %45, ptr %6, align 8

## 依赖类型

顾名思义，[依赖类型](https://medium.com/background-thread/the-future-of-programming-is-dependent-types-programming-word-of-the-day-fcd5f2634878)是定义依赖于值的类型。举个具体例子，看一个由 `Int` 支撑的结构体：`‍
`

Mojo

@value
@register_passable("trivial")
struct Adder[I: Int]:

    @always_inline('builtin')
    fn __init__(out self):
        pass

    @always_inline('builtin')
    fn __add__[OI: Int, //](self, other: Adder[OI]) -> Adder[I + OI]:
        return {}

`Adder` 接受值 parameter `I`；因此 `I` 的具体值成了 `Adder` 类型定义的一部分。注意在 `Adder.__add___()` 的定义中，我们利用这一性质，把加法编码为类型系统变换，从而强制其编译期求值。`@always_inline('builtin')` 装饰器用于确保方法体可以被完全编译期折叠，于是像 `Adder[1]() + Adder[3]()` 这样的表达式在此就恰好等于 `Adder[4]()`。更详细的解释参见该[特性提案](https://github.com/modular/modular/blob/main/mojo/proposals/always_inline_builtin.md)。

以这种方式编码信息，还适合用来强制要求函数 argument 以特定值参数化：`‍
`

Mojo

fn must_add_two[AI: Int, //](a: Adder[AI], b: Adder[2]) -> Adder[AI + 2]:
    return a + b

fn main():
    print(must_add_two(Adder[10](), Adder[2]()).I)
    # print(must_add_two(Adder[10](), Adder[3]()).I) # Compilation error

由于加法运算已经搬进了类型系统，结果值 `I` 最终只是实体化为一条值为 `12` 的运行时 store 指令：

LLVM

store i64 12, ptr %3, align 8

## 在类型系统中表示复杂信息

为了展示 parameter 能表示的更复杂内容，我们来深入一个我写的库——[`Kelvin`](https://github.com/bgreni/Kelvin)。它是一个类型安全的量纲分析库，所有安全检查都在编译期完成，以确保相对裸数值的性能开销最小。我们来看看如何在代码中表示"每秒 10 米"。

首先需要一个物理"量纲"的定义——我们在这里定义一个带 3 个 parameter 的结构体 `Dimension`：

- `Z`：量纲的指数值，例如面积的长度量纲中 `Z` 的值为 `2`
- `R`：量纲的标度，用于区分同一单位的不同标度，例如 `Meters` 与 `Kilometers`
- `suffix`：值的字符串后缀，如 `km`、`K`、`mol` 等

另外还有一个独立的 `Angle` 结构体，因为角度不是真正的量纲，行为也不同：

Mojo

struct Dimension[Z: IntLiteral, R: Ratio, suffix: String](...):
    ...

struct Angle[R: Ratio, suffix: String](./..):
    ...

Mojo 的 parameter 系统允许我们编写返回类型依赖于输入的函数。由此我们可以构建如下示例：为 `Dimension` 定义减法方法——把输入量纲的 `Z` 值相减，并返回一个新的参数化量纲类型：`‍
`

Mojo

@always_inline("builtin")
fn __sub__(
    self, other: Dimension
) -> Dimension[Z - other.Z, R | other.R, suffix or other.suffix]:
    return {}

这一行为为后面的一些酷炫操作打下了基础。

再举一例：SI 单位制有 7 个基本量纲，因此我们可以组合 7 个量纲单位加一个角度单位，构成一个值的 `Dimensions`：`‍
`

Mojo

struct Dimensions[
    L: Dimension,  # Length dimension.
    M: Dimension,  # Mass dimension.
    T: Dimension,  # Time dimension.
    EC: Dimension, # Electric current dimension.
    TH: Dimension, # Temperature dimension.
    A: Dimension,  # Substance amount dimension.
    CD: Dimension, # Luminosity dimension.
    Ang: Angle,    # The angle component of the quantity.
](...):
    ...

现在可以用刚定义的 `__sub__` 方法来定义量纲相除的结果。位于分母的单位表示为负的 `Z` 值，例如 `m / s` 表示为 `m^1 s^-1`：`‍`

Mojo

@always_inline("builtin")
fn __truediv__(
    self, other: Dimensions
) -> Dimensions[
    L - other.L,
    M - other.M,
    T - other.T,
    EC - other.EC,
    TH - other.TH,
    A - other.A,
    CD - other.CD,
    Ang.pick_non_null(other.Ang),
]:
    return {}

`‍`铺垫完成后，我们就可以定义表示实际数值的 `Quantity` 结构体：`‍`

Mojo

struct Quantity[D: Dimensions, DT: DType = DType.float64, Width: UInt = 1](...)
    alias ValueType = SIMD[DT, Width]
    var _value: Self.ValueType
    ...

接着用 `alias` 就能轻松定义具体单位：

Mojo

alias Meter = Quantity[
    Dimensions[
        Dimension[1, Ratio.Unitary, "m"](),
        Dimension.Invalid,
        Dimension.Invalid,
        Dimension.Invalid,
        Dimension.Invalid,
        Dimension.Invalid,
        Dimension.Invalid,
        Angle.Invalid,
    ](),
    _,
    _,
]

alias Second = Quantity[
    Dimensions[
        Dimension.Invalid,
        Dimension.Invalid,
        Dimension[1, Ratio.Unitary, "s"](),
        Dimension.Invalid,
        Dimension.Invalid,
        Dimension.Invalid,
        Dimension.Invalid,
        Angle.Invalid,
    ](),
    _,
    _,
]

由于我们定义了 `Dimensions / Dimensions` 运算，现在一行代码就能定义速度这样的导出单位：`‍`

Mojo

alias MetersPerSecond = Quantity[Meter.D / Second.D, _, _]

`‍`借助编译期编程的威力，我们可以在 `Quantity` 上定义遵守 SI 单位制规则的操作，而这些规则*全部*在编译期验证。先从简单例子入手（因为加法/减法只在量纲相同的量之间才有意义），我们用特殊的 `Self` 类型确保 `self` 和 `other` 是完全相同的类型：`‍`

Mojo

@always_inline
fn __add__(self, other: Self) -> Self:
    return Self(self._value + other._value)

var s1 = Second(10)
var s2 = Second(30)
var s3 = s1 + s2 # All good

var bad = s1 + Meter(20) # compiler error

`‍`乘法和除法稍微复杂些，因为这两个操作允许作用于不匹配的单位，且返回类型依赖于输入类型——这里以除法为例：

Mojo

@always_inline
fn __truediv__[
    OD: Dimensions
](self, other: Quantity[OD, DT, Width]) -> Quantity[D / OD, DT, Width]:

    _dimension_scale_check[D, OD]()
    return {self._value / other._value}

这里在编译期有一条静态断言，检查两个类型的量纲标度是否匹配——例如"米每秒"和"英里每小时"量纲相同，但因单位标度不同而不兼容。在返回类型上，我们用 `D / OD` 计算导出量纲；因此方法的输出正是我们从这个运算中期望的精确类型：`‍
`

Mojo

var s = Second(10)
var m = Meter(20)

var v: MetersPerSecond = m / s

检查 IR，可以看到所有 parameter 的复杂性都已被解析，剩下的只是一条简单的除法运算：`‍
`

LLVM

%3 = fdiv contract double %1, %0

## 负责任地使用这种力量

准确理解这些抽象如何运作，是高效使用它们的关键。例如，`@parameter for` 循环***永远***会把整个循环展开，可能造成二进制膨胀和负面性能影响：

LLVM

@parameter
for i in range(1000000):
    print(i)

## 小结

Mojo 为在编译期无缝执行代码提供了强大的工具，让程序员能在类型系统中构建强有力的抽象，把相关复杂度彻底从运行时移除。相关工作也在持续推进（比如[`parameter 化 alias`](https://github.com/modular/modular/blob/main/mojo/proposals/parametric_alias.md)）。
