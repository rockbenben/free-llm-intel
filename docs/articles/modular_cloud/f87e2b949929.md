# Blackwell 上的矩阵乘法（一）：简介

> 🛠️ 本系列提到的所有内核代码都已在 GitHub 上开源。

这个系列的博客将展示如何：

- 在 Blackwell 上编写一个高性能 GPU 内核，性能可与 NVIDIA 的 cuBLAS 实现相媲美。
- 展示如何利用 Mojo 的特色功能，让内核尽可能简洁。

我们希望这一系列博客能成为 NVIDIA Blackwell GPU 的*参考工作日志*。此前已有针对 NVIDIA [Ampere](https://siboehm.com/articles/22/CUDA-MMM) 和 [Hopper](https://cudaforfun.substack.com/p/outperforming-cublas-on-h100-a-worklog) 代 GPU 的优化工作，但目前还没有一份针对 Blackwell GPU 优化的蓝图。

在第 1 篇（即本文）中，我们会介绍什么是矩阵乘法（matmul）、它对 LLM 的重要性，以及为什么需要优化它。接着解释什么是 GPU、Ampere 以来 GPU 的演进历史，最后演示如何用 4 行 Mojo 写一个简单（性能不算高）的 GPU matmul 实现。

在第 2 篇中，我们会介绍 Blackwell GPU 新增的硬件指令，并继续提升内核性能，让它用上这些新硬件指令。随着系列推进，我们会逐步利用 Blackwell 的新特性来改进 matmul 实现，直到系列结尾，性能超越 NVIDIA 的 cuBLAS 库。

性能速览

## 什么是 matmul？

给定两个稠密矩阵 `A` 和 `B`，维度分别为 `MxK` 和 `KxN`，我们要计算矩阵乘法 `C = A.B`，其定义为

Mojo

for row in range(M):
  for col in range(N):
    C[row][col] = 0
    for inner in range(K):
      C[row][col] += A[row][inner]*B[inner][col]

由于矩阵乘法是线性代数的核心，并出现在众多领域，人们围绕高效算法已经做了大量研究。想深入了解 matmul 背景的读者，推荐阅读我们 [2 年前](https://www.modular.com/blog/ais-compute-fragmentation-what-matrix-multiplication-teaches-us)的那篇博客。

### 为什么 matmul 在今天如此重要？

所有 LLM——无论是 Meta 的 Llama、阿里的 Qwen、Deepseek、Anthropic 的 Claude、OpenAI 的 ChatGPT，还是 Google 的 Gemini——核心都在使用矩阵乘法。这些 matmul 可能以不同名字出现：比如多层感知机（MLP，有时也叫 Linear 层）就是一次 `A.B^T` 的 matmul 运算。Attention、Latent Attention、Mixture of Experts 等同理。

事实上，如果我们看一下 Llama 8B 模型在 2xB200 上使用 FP8 的性能剖析，会发现模型超过 83% 的运行时间都在执行某种形式的 matmul（如 linear、attention 和 MLP 层）。

matmul 占 Llama 8B 执行时间的 80% 以上

因此，即使 matmul 性能只提升 10%，也能带来约 8% 的端到端加速。对于每年在推理服务上花费数亿美元的公司来说，这些优化直接转化为数百万美元的成本节省。

### 我们为什么关心 GPU？

我们仍然从 matmul 出发来说明 GPU 的价值。为简单起见，假设 `A` 和 `B` 都是方阵：

矩阵乘法的简化示意图

如果要在 CPU 上做这个 matmul，我们需要写出这样的伪代码：

mojo

for row in range(M):
  for col in range(N):
    for inner in range(K):
      result[row][col]+=A[row][inner]*B[inner][col];

本质上，这段代码为每个输出元素计算沿 `K` 维度的内积。

矩阵乘法即一组内积

CPU 的核心数量只有几百个量级（低端 CPU 大约 32 核，高端型号也就 128 核左右）。而 GPU 提供大规模并行：现代 GPU 可同时处理超过 10 万个线程（B200 最多可达 151,552 个线程），这让它成为矩阵乘法这类重复性、数据并行操作的理想硬件。

为了进一步提速，近几代 GPU（从 Volta 开始）都配备了专门用于矩阵乘累加（MMA）操作的高速硬件单元——Tensor Core（张量核心）。早期的 Tensor Core 只能处理小规模 matmul（16x16x16 量级），而 Blackwell 引入的第五代 Tensor Core 可以完成大块的子矩阵乘法（最大 256x256x16），使 Blackwell GPU 的峰值计算吞吐进一步提升。

### 从硬件架构师视角看 GPU？

要更好地理解 GPU，我们先从硬件架构角度看看 GPU 的组织方式。GPU 和其他[冯·诺依曼](https://en.wikipedia.org/wiki/Von_Neumann_architecture)架构一样，由负责计算的单元（即算术逻辑单元，ALU）和负责为这些计算加载/存储数据的单元组成。一块 GPU 包含多个流式多处理器（[SM](https://docs.modular.com/glossary/gpu/streaming-multiprocessor)）、在这些 SM 之间共享的 [L2 缓存与全局内存](https://docs.modular.com/glossary/gpu/memory)，以及到主机设备（CPU）的互连。

GPU 架构

GPU 上的线程被分组为块，称为[线程块](https://docs.modular.com/glossary/gpu/thread-block)或协作线程阵列（CTA）。每个这样的块会被调度到**单个** [SM](https://docs.modular.com/glossary/gpu/streaming-multiprocessor) 上。每个 SM 通过共享的 L2 缓存访问数据，L2 再从全局内存加载数据。每个 SM 上的线程还可以访问另外两块存储区域：

- 寄存器：局部变量，每个线程私有。
- 共享内存：在同一个 SM 内的线程之间可见。从 Hopper 开始，多个 CTA 可以组成一个集群（cluster），同一集群内的 CTA 可以互相访问对方的共享内存。

协作线程阵列的布局

### 什么是 Tensor Core？

GPU 本身是一个加速器，而其内部还藏着数百个微型加速器——Tensor Core。Tensor Core 是专门执行矩阵乘累加操作的单元，这与能做通用算术计算的其他 ALU 单元不同。

通过一个例子来理解 Tensor Core 的定义。假设我们要把两个矩阵相乘，`A` 矩阵维度为 `MxK`，`B` 矩阵维度为 `KxN`：

MxK 矩阵乘以 KxN 矩阵

CUDA core 每条指令只能处理一次融合乘加运算，也就是把矩阵 `A` 中的一个元素与矩阵 `B` 中的一个元素相乘，并累加到 `C` 上。而 Tensor Core 一条指令就能完成一次 MMA 运算（比如一个 64×128 的 tile）。

单个 CUDA core 的矩阵乘法

单个 Tensor Core 的矩阵乘法

性能提升显而易见。在维度为 `MxN` 的大矩阵上，我们可以把 matmul 分解为多个小 matmul（这就是所谓的 tiling 分块技术，后续博客会详细讨论），用更少的指令完成计算，从而获得巨大的加速。

每个 SM 上 Tensor Core 的数量（好奇的话：4 个）并不重要。因为当我们发射 MMA 指令时，硬件会自动负责把 MMA 任务划分并分派给各个 Tensor Core。

在 Hopper 上，最大的 WGMMA（Warp Group Matrix Multiply and Accumulate， warp 组矩阵乘累加）形状是 64×256×16。WGMMA 指令需要四个 warp（一个 warp group），且结果要存在线程寄存器里。而 Blackwell 的第五代 Tensor Core（tcgen05）把 MMA 扩展到 2 SM 上的 256x256x16，并引入了 tensor memory（张量内存）来降低寄存器占用（后续文章会详细讲）。

### 什么是 GPU 编程？

GPU 编程基础的详细描述超出了本文范围。有很多资源讲解 GPU 编程范式，其中很棒的两份是 [Mojo GPU Puzzles](https://puzzles.modular.com/introduction.html) 和 GPU [术语表](https://docs.modular.com/glossary/)。

由于 GPU 提供大规模并行，我们必须换一种思路来编程。例如，传统 CPU 编程用循环顺序处理数据：

Mojo

# CPU approach for i in range(data_size):
result[i] = process(data[i])

在 GPU 上，我们把这种模型完全反过来，通过线程来处理数据。与其顺序遍历数据，我们把成千上万个并行线程直接映射到数据上。对于上面的例子，函数体就变成了：

Mojo

# GPU approach (conceptual)
thread_id = global_idx.x
result[thread_id] = process(data[thread_id])

在 GPU 上，每个线程只负责计算一个元素，不再需要显式循环。这种从"一步步走查数据"到"用计算覆盖全部数据"的思维转变，正是 GPU 编程的核心。如果对照[弗林分类法](https://en.wikipedia.org/wiki/Flynn%27s_taxonomy)，这就对应单指令多线程（SIMT）编程模型。

启动一个[内核](https://docs.modular.com/glossary/gpu/kernel)（调用函数）时，你要指定每个[块](https://docs.modular.com/glossary/gpu/thread-block)中的线程数（也叫 block size），以及要启动多少个块（即 [grid](https://docs.modular.com/glossary/gpu/grid) 大小）。硬件会把每个块映射到一个 SM 上。因此，同一个块内的线程可以共享内存、彼此同步，但不同块之间无法直接通信——除非它们属于同一个集群（后面会讲）。注意：每个线程块只会在一个 SM 上执行，但每个 SM 可以同时执行多个块（CTA）：

回顾一下：我们启动一个由 CTA 组成的 grid——每个 CTA 包含一段连续的线程数组——每个 CTA 被调度到一个 SM 上。

再深入看 CTA 的执行模型：每个块还会进一步细分为若干 warp。一个 warp 由 32 个线程组成，这些线程以锁步方式运行同一个程序计数器。所以如果我们启动一个 128 线程的块，实际上就隐含启动了 4 个 warp。两者是同一回事，不需要你额外做任何编程。

CTA 到块与 warp 的划分

每个 SM 内部有 4 个 warp 调度器（以 warp 为粒度发射指令的物理单元）。不同的 warp 可以在不同 warp 调度器上并行执行，也可以在同一调度器上并发执行。

这一点很有用：如果当前 warp 的指令还没准备好执行，SM 可以转去执行其他 warp——从而帮程序员隐藏部分延迟。举个例子，某个 warp 需要从内存取数据，就得等数据到达。warp 调度器不会干等，而是切换到另一个数据已就绪的 warp。这样 GPU 就不会空转。

优化后的 warp 调度示例

这种编程范式并非 Blackwell 独有——把线程分组为 warp 的做法近二十年来基本没变过，从 NVIDIA 的 Tesla 架构时代即是如此。

### 线程块集群（thread block clustering）

在 Hopper 和 Blackwell 上，程序员可以把多个 CTA 组成一个集群（cluster）。集群保证其所有块被调度到同一 GPU 处理集群（GPC）内物理相连的 SM 上。这种邻近性让集群内不同 SM 上的块可以直接访问彼此的共享内存，绕过全局内存，等效地扩大了可用的共享内存空间。由此，GPU 执行层次中多了一个新层级：位于块与 grid 之间的集群。

## NVIDIA 的 GPU——过去三代一览

过去五年，NVIDIA 通过一系列开创性的平台发布彻底改变了 GPU 架构。从 2020 年推出的 Ampere 架构到如今最前沿的 Blackwell 平台，每一代都在计算性能、内存带宽和 AI 加速能力上带来了大幅提升。本节梳理 Ampere、Hopper 和 Blackwell 三代架构的定义性特征与创新。

### NVIDIA 的 Ampere 架构

Ampere 于 2020 年 5 月发布，让 Tensor Core 有了长足进步（尽管 Tensor Core 早在几代之前就已引入）。从规格上看，Ampere 拥有：

- 108 个流式多处理器（SM）
- 每个 SM 4 个 Tensor Core
- 80GB 高带宽内存（最高 2.0 TB/s）
- 每个 SM 192KB 共享内存 + L1 缓存（合用）
- 每个 SM 65,536 个寄存器
- 所有 SM 共享的 40MB L2 缓存
- 异步拷贝，可在 global -> shared memory 的拷贝之间建立更深的软件流水线

Ampere 架构

### NVIDIA 的 Hopper 架构

Hopper 于 2022 年底发布，在 Ampere 基础上进一步提升，至今仍被广泛用于 LLM 部署。Hopper 的规格如下：

- 132 个流式多处理器（SM）
- 每个 SM 4 个 Tensor Core
- 80GB 高带宽内存（3.35TB/s）
- 每个 SM 256KB 共享内存 + L1 缓存（合用）
- 每个 SM 65,536 个寄存器
- 所有 SM 共享的 50MB L2 缓存
- 引入 TMA 引擎优化块级内存拷贝
- 与下一代硬件不向前兼容

Hopper 架构

### NVIDIA 的 Blackwell 架构

Blackwell 是 NVIDIA 最新的架构，也是当前 LLM 部署的 SOTA 架构。它在 Hopper 和 Ampere 的基础上提升了算力，并提供了若干关键特性来加速执行：

- 148 个流式多处理器（SM）
- 每个 SM 4 个 Tensor Core
- 7.672 TB/s 高带宽内存
- 每个 SM 228 KB 共享内存 + L1 缓存（合用）
- 每个 SM 65,536 个寄存器
- 所有 SM 共享的 192 MB L2 缓存
- 第五代 Tensor Core 架构
- **256 KB 的 Tensor Memory（张量内存）**

| 指标 | A100（基准） | H100 | H200 | B100 | B200 |

随着 GPU 在 FLOPs/s 和带宽上越来越强，要达到峰值性能的编程模型也在演进。下面回顾各代架构上的最优操作调度方式。

### Pre-Ampere 时代的优化

Ampere 引入了异步数据搬运。在 Ampere 之前，访存操作会阻塞计算，我们只能这样：从 global 加载数据 → 等待 → 计算 → 等待 → 存储结果

Pre-Ampere 时代的优化

因此，在 Ampere 之前的架构上要靠双缓冲（double buffering），并在每个 SM 上放多个 CTA 来重叠数据传输与计算。这会争抢 SM 有限的内存资源，迫使我们在内存延迟和最优分块之间做取舍。

### Ampere 时代的优化

借助 Ampere 的异步拷贝指令（`cp.async`），可以在单个 CTA 内把数据加载和 MMA 操作做成流水线，实现重叠。

Ampere 时代的优化

使用 `cp.async` 指令，线程可以发出内存拷贝后立即去做别的工作，把内存传输延迟藏在 MMA 操作背后。

> ✅ Ampere 的胜利：让输入加载与计算重叠

> ❌ Ampere 的问题：CTA 启动开销

### Hopper 时代的优化

Hopper 架构为数据传输和 MMA 引入了新指令：

- TMA（Tensor Memory Accelerator，张量内存加速器）：TMA 是专门搬运多维张量的硬件单元。不再需要每个线程自己算地址、逐个元素加载，TMA 可以在全局内存和共享内存之间异步搬运整个张量 tile。
- 异步 Warp 组 MMA（WGMMA）：Ampere 虽然能让 MMA（同步指令）与数据传输重叠，但 WGMMA 指令本身是异步的，不仅能让 MMA 与内存访问重叠，还能与其他核心计算重叠。

由此诞生了一种新的 matmul 开发范式——持久化内核（Persistent Kernels）。这一技术会在后续博客中深入讨论，简言之，它让 CTA 常驻 SM 上连续处理多个 tile，无需返回主机。这消除了内核启动开销，并让前一个 tile 的输出与后一个 tile 的加载重叠起来。

Hopper 时代的优化

> ✅ Hopper 的胜利：降低 CTA 启动开销，并在 tile 之间重叠数据传输。

> ❌ Hopper 的问题：WGMMA 消费者占用大量寄存器，且 Tensor Core 与 ALU 之间存在争用。

### Blackwell 时代的优化

Blackwell 架构引入了 tcgen05 指令和 tensor memory，MMA 的结果存放到新的专用硬件——张量内存中。这打破了 WGMMA 对寄存器的依赖。我们现在可以做更多级流水线，而不再污染寄存器。

Blackwell 时代的优化

这形成了三级流水线：

- **加载输入**（TMA）——通过 TMA 引擎加载数据
- **执行 MMA**（Tensor Cores）——完成 MMA 运算并写入张量内存
- **存储输出**（从 Tensor Memory）——把结果从张量内存写回全局内存

三个阶段可以在不同的存储区域上同时运行：tile `N` 在计算，tile `N+1` 在加载，tile `N-1` 在写回——构成一条软件流水线。

> ✅ Blackwell 的胜利：把写回阶段也纳入流水线

> ❌ Blackwell 的问题：张量内存只支持非常有限的指令

可以看到，硬件越先进，通往峰值性能的算法就越复杂。事实上，CUDA 编程模型也已经不够用了——许多指令（如 `tcgen05`）只在 PTX 层面提供。这并不理想，而 Mojo 正是来补这个缺口的。

### 4 行写出 matmul

有了 GPU 编程和硬件的知识储备，我们终于可以——*终于*——把 matmul 函数改写成 GPU 上的 matmul 内核了。这很简单，就像这样：

Mojo

acc = Float32(0)
for k in range(K):
  acc += a[global_idx.y, k] * b[global_idx.x, k]
c[row, col] = acc

我们创建了一个足够大的二维线程网格，覆盖整个 `C` 矩阵：

- 每个线程计算输出矩阵 `C` 的一个元素，元素位置由该线程的唯一 id 决定
- `row = global_idx.y
col = global_idx.x
`
- 线程块被映射到输出矩阵的各个 tile

内核对 `C` 矩阵的每个输出同时执行这个点积。

对每个输出并发执行点积

matmul 函数的输入是 LayoutTensor。想进一步了解 LayoutTensor，参见 Mojo Manual 中的 [Using LayoutTensor](https://docs.modular.com/mojo/manual/layout/tensors/) 一节。

Mojo

fn matmul_kernel[
    M: Int, N: Int, K: Int
](
  c: LayoutTensor[DType.bfloat16, Layout.row_major(M, N)],
  a: LayoutTensor[DType.bfloat16, Layout.row_major(M, K)],
  b: LayoutTensor[DType.bfloat16, Layout.row_major(N, K)],
):
# previous 4 lines of code

`‍`这让我们无需自己处理索引/寻址内存所需的代数运算（比如对矩阵 `A`，本来要写成 `a[row * K + col]`）。

### 数据类型与类型转换

由于我们关注的是 LLM，而 BFloat16 是 LLM 中最流行的数据类型，本系列将全程使用 BFloat16。这是一种半精度浮点类型，占用 2 字节内存，与 Float16 类似但有一些额外好处：

BF16 的指数范围可达 -126→127，因此能表示的数值范围远大于传统 FP16。其最大正值为 $$3.39x10^{38}$$，而 FP16 仅为 $$6.55x10^4$$。更大的范围使它非常适合深度学习和 LLM 应用——这些场景需要容纳横跨多个数量级的梯度，而单个数值的精度并不关键。

不过有一个坑：当累加大量值（`K` 次迭代）时，BF16 的舍入误差会迅速累积（因为它的尾数位数少，相邻可表示值之间的"跳格"较大）。为了避免这一点，我们可以修改代码，用更高精度累加中间结果：

Mojo

for k in range(K):
  acc += a[global_idx.y, k].cast[DType.float32]() *
         b[global_idx.x, k].cast[DType.float32]()
c[global_idx.y, global_idx.x] = acc.cast[DType.bfloat16]()

`‍`用 FP32 做累加可以在归约过程中保持数值精度，同时仍然享受 BFloat16 的内存优势。注意，Tensor Core 同样会把 BFloat16 的累加结果放在 Float32 中。归约结果在写回全局内存前会降精度转换回 BFloat16。

为了衡量内核性能，我们运行了这段[代码](https://github.com/modular/modular/blob/main/max/kernels/test/gpu/linalg/matmul_blackwell_iterative/1_naive_sm100.mojo)，测量它达到的 FLOPS（每秒浮点运算次数）。在这个设置下，我们计算 `A(MK)*B(KN) = C(MN)`。输出中有 `MN` 个元素，每个元素做一次长度为 `K` 的点积（`K` 次乘法和 `K` 次加法）。因此内核总共做 `(MN)2K` 次浮点运算，性能（FLOPS）即为 `2MNK/time`。我们的内核跑出 5 TFLOPs。

朴素 GPU 内核的性能

5 TFLOPs 不算差（毕竟代码只有 4 行），但对比 cuBLAS 的 SOTA 成绩 1763 TFLOPs，以及 B200 系统 2250 TFLOPs 的理论峰值，就差得远了。
