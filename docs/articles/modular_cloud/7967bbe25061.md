# Modular 25.7：更快的推理、更安全的 GPU 编程、更统一的开发者体验

今天，我们很高兴发布 Modular Platform 25.7——一次深化我们"为 AI 构建统一高性能计算层"愿景的更新。完全开放的 MAX Python API、实验性的下一代建模 API、对 NVIDIA Grace 超级芯片的扩展硬件支持，以及更安全、更强大的 Mojo GPU 编程体验，让本次发布使我们更接近这样一个生态：开发者花在对抗基础设施上的时间更少，花在推进 AI 能力上的时间更多。

# **MAX：更快、更易用、更开放**

MAX 持续进化为可用的最快的跨厂商推理框架。在 25.7 中，我们在三个方向上加深了 MAX：开放性、建模灵活性与生产级控制。

## MAX：构建高性能推理模型的好方式

从这个版本起，MAX 的整个 Python 接口已[完全开源](https://github.com/modular/modular/tree/main/max/python/max)。这给开发者带来：

- 对 MAX 模型如何跨硬件厂商构建、执行和服务的可见性。
- MAX ↔ PyTorch 互操作等特性[如何实现](https://github.com/modular/modular/blob/main/max/python/max/torch/torch.py)的真实示例。
- 通过新近可见的单元测试更清楚地理解内部抽象，更容易推理性能与正确性。
- 更好的 bug 报告与贡献路径，加速整个生态的迭代。

我们一直在努力打磨 API、启用一等的 "eager" 编程模型，并真正释放我们下一代技术栈的威力。现在是向更多开发者开放的时候了，因此我们开源整个 API，并开始教大家如何构建 MAX 原生模型。

## **全新的（实验性）Model API 与开发工作流**

25.7 引入了重新设计的 Model API，由新的 `max.nn.module_v3` 和 `max.experimental.tensor` 组成——它们共同带来 MAX 发布以来最重要的建模升级。

新 API 为开发者带来更贴合其熟悉的高层模型抽象的体验，把更好的建模人体工学带进 MAX。你按习惯的方式写模型，MAX 在底层完成重活：

- **类 PyTorch 语法**，定义与组合模型的认知开销极低
- **惰性求值**，eager 语义与 PyTorch 的 eager 模式一致，便于调试
- 不再需要手工构图，也不再需要 session-load-run 的仪式
- 直观的权重加载：`load_static_dict()`，与 PyTorch 类似
- **纯 MAX/Mojo 技术栈**：不依赖 PyTorch、NumPy 或其他框架

准备好上生产时，只需加上 `model.compile(input_type)`，即可解锁整模型编译的性能收益。这启用了完整的前置（AOT）图编译，带来你期待自 MAX 的全部速度与内存效率优势。

python

```
import max.nn.module_v3 as nn
from max.experimental import functional as F, tensor, random

class MyModel(nn.Module):
    def __init__(self):
        self.fc = nn.Linear(10, 10)
        self.proj = nn.Linear(10, 1)

    def __call__(self, x: tensor.Tensor) -> tensor.Tensor:
        x = self.fc(x)
        x = F.gelu(x)
        x = self.proj(x)
        return x

model = MyModel()
input = random.normal((10, 10))
# for development and debugging
max_output = model(input)
# for production
compiled_model = model.compile(input.type)
max_output = compile_model(input)
```

最新的 API 极大加速了模型开发、调试与定制——尤其对扩展前沿规模架构的团队。要用上新的 [model APIs](https://docs.modular.com/max/api/python/experimental/)，可以看看我们新的在线书[用 MAX 从零构建 LLM](https://llm.modular.com/?__hstc=48884729.17e8006993cbcdfba9a63fb46db56952.1763487023000.1763487023000.1763529172227.2&__hssc=48884729.2.1763529172227&__hsfp=2481089013)。这是一门从 GPT-2 开始的构建 LLM 引导课，沿途讲解 transformer 模型的每个组件。欢迎在 [forum.modular.com](http://forum.modular.com/) 给我们反馈，或在 [github.com/modular/modular/issues](http://github.com/modular/modular/issues) 报告 bug 或功能请求。

## **扩展的模型与硬件支持**

25.7 显著拓宽了 MAX 在模型与硬件上的覆盖，确保在最新加速器和系统架构上的高性能推理。

- MAX 现在支持在连接 ARM CPU 主机的 GPU 上运行 bfloat16 模型，包括 Grace Hopper (GH200) 和 Grace Blackwell (GB200) 系统。这基于围绕 Grace 超级芯片架构构建的下一代 NVIDIA 平台，解锁更高性能与更低功耗。
- MAX 在视觉模型上交付超额的性能收益：相比 25.6，在 Qwen2.5-VL 上额外提升 +30-80% 吞吐量，相比 vLLM 超过 2 倍性能。
- 对 GPT-OSS 的早期支持已经落地，MXFP4 集成即将到来，以解锁重大的 4-bit 性能收益。

这些更新共同加深了 MAX 作为最快的完全可移植推理引擎的地位。敬请期待我们下个版本中非常重大的模型与性能更新。

## **面向实时定制的动态 LoRA**

25.7 引入对 Dynamic LoRA 的支持，最初面向语音和低延迟实时工作负载做了调优。它让开发者可以：

- 在运行时热切换 LoRA adapter
- 不重启服务器就个性化模型
- 用 LoRA 实现说话人或领域特定的行为
- 为生产工作负载实现近零开销的调优

这对需要快速、高保真、低成本模型适配的场景至关重要。如今，MAX 中的动态 LoRA 正在为 Inworld AI 的声音克隆等实时应用提供动力，我们将很快把它扩展到更多模型。

# Mojo：更安全、更好的 Apple GPU 支持等

Mojo 正在进化为编写高性能 GPU 代码最简单、最可移植的方式。在此过程中，我们增强硬件支持、添加新语言特性、提升语言的整体安全性。

## **增强的 Apple Silicon GPU 支持**

我们在 25.6 发布了 Apple silicon GPU 的初步支持，在 25.7 中我们持续扩展这些 GPU 上基础 intrinsics 与能力的覆盖，包括

- 对同步原语的支持
- 共享内存访问
- 把 warp 操作映射到 Metal 等价物

因此，在 25.7 中你现在可以在 Apple silicon GPU 上运行我们[热门 Mojo GPU puzzles](https://puzzles.modular.com/introduction.html)中的 20 个，而上一个版本只能跑 5 个。

Mojo 现在提供了在 Apple 硬件上开发 AI kernel 最清爽的路径之一——不需要厂商专用 API。

## **更安全的 GPU 编程**

GPU 代码中的正确性和非法内存访问错误可能很隐蔽、极难诊断。更早抓住它们、让它们更显眼，能在新写 kernel 或 AI 模型时省下大量时间。在 25.7 中，Mojo 语言和库做了几项重要改进来抓住常见的 GPU 编程问题：

- GPU 函数现在通过 `enqueue_function_checked()` 进行强类型检查，在许多潜在崩溃和坏内存访问发生前就识别它们。
- 新近重构的 `UnsafePointer` 类型，修复了一些常见的生命周期问题和意外的不安全改动。
- 不再有 `Int` 与 `UInt` 之间的隐式转换——这是 GPU kernel 中常见数值正确性问题的根源。
- 关于约束失败（constraint failure）的错误消息大幅改善：调用栈、行号和打印的参数值。
- 扩展了用 Address Sanitizer 检测 Mojo 代码内存泄漏和非法访问的支持。

除语言与库特性外，一个新的 `TestSuite` 模块为 Mojo 更好的单元测试打下基础。它提供清晰的测试结果接口、自动测试发现等能力。

这些安全改进契合我们的长期目标：Mojo 让 GPU 编程感觉像在编写高层、安全的系统代码。
