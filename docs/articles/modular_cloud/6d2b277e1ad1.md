## 内核 5：multicast 与 2xSM MMA

从 NVIDIA Hopper 一代开始，流式多处理器（SM）可以分组，同一 SM 组内的协作线程阵列（CTA）可以互相访问对方的共享内存（即分布式共享内存访问）。这在 Blackwell 上带来两项高级优化：

- 张量内存加速器（TMA）multicast（多播）——Hopper 起即支持：多个 SM 协作把一个 tile 加载进共享内存。
- 2xSM 矩阵乘累加（MMA）：2 个 SM 的 Tensor Core 利用各自共享内存中的输入，协作完成一次大规模 MMA 运算。

我们来研究这两项技术，看它们在代码中如何体现。首先要做的是把集群大小（`cluster_shape`）告知代码。Kernel 5 的代码在[这里](https://github.com/modular/modular/blob/main/max/kernels/test/gpu/linalg/matmul_blackwell_iterative/5_2sm.mojo)。在 Mojo 中可以用 `@__llvm_metadata` 装饰器实现：

Mojo

@__llvm_metadata(`nvvm.cluster_dim`=cluster_shape)
fn blackwell_tma_pair_umma_kernel[
  a_type, 
  ...other parameters...,
  cluster_shape
]

以上代码在编译期为内核设定"CTA 集群"的启动形状。同一集群内的 CTA 可以互相访问共享内存。

### CTA 内存多播

要理解内存多播，先看一个简单例子：如果没有这个功能，我们得怎么做。为了便于可视化，设 A、B、C 都是 256x256 矩阵，此时我们启动 4 个 CTA。

图 2：4 个 CTA 计算两个 256x256 矩阵相乘

每个 CTA 计算一个 128x128 的 tile。看看各 CTA 在 `K/BK` 循环中加载哪些 tile：

图 3：CTA 的 tile 加载

注意内存加载中的冗余。这和[系列开篇](https://www.modular.com/blog/matrix-multiplication-on-nvidias-blackwell-part-2-using-hardware-features-to-optimize-matmul#shared)注意到的冗余类似，只是这次冗余发生在 tile 粒度而非元素粒度。

怎么缓解？如果我们把这 4 个 CTA 组成一个 2x2 集群，SM 就能互相访问共享内存，这样每个 SM 可以从全局内存加载一个 tile，再把它广播给邻居。

有了这个能力，我们可以调整加载策略：同一行的两个 CTA 各自只加载 A 中 tile 的一半，再把这一半广播给邻居。这样两个 CTA 都只做一半的加载，却都能拿到完整 tile。可视化如下：

图 4：CTA 多播 A 的 tile 行

同样的技术可以扩展到 B 矩阵的加载：

图 5：CTA 多播 B 的 tile 列

这项技术称为 multicast（多播），并且可扩展。例如启动 4x4 集群时，可以让每个 CTA 加载自己 tile 的一半，其余数据从同伴处获得。看看 Mojo 中如何实现。我们先在主机侧声明 TMA 操作：

  b_type, 2, (BN // cluster_shape[0], BK), swizzle_mode=b_swizzle

由于每个 CTA 会把 A、B 的共享内存 tile 切分并广播给对应的同伴 CTA，我们按集群维度把 TMA tile 划分。在 GPU 内核中，用下面的方式发起多播加载：

### 2xSM MMA

上面展示了分布式共享内存和多播如何减少全局内存到共享内存的数据量。但仍有一个限制——tile 在分布式共享内存中是重复存储的。回看例子中的 CTA 0 和 1，两个 CTA 都在共享内存里存了一份 `BNxBK` 的 tile，如下图左侧所示。既然每个 CTA 都能访问对方的共享内存，同一 tile 存两份就是浪费资源。

图 6：分布式共享内存中的 tile 重复

Blackwell 的 2xSM MMA 指令（`tcgen05.mma.cta_group::2`）正是为解决这个问题设计的。如[图 6 右侧](https://www.modular.com/blog/matrix-multiplication-on-nvidias-blackwell-part-3-the-optimizations-behind-85-of-sota-performance#figure-06)所示，CTA 0 和 1 成对工作，各自只加载 B tile 的一半。2xSM MMA 指令能同时看到共享内存中的两半，并协调两个 SM 上的 Tensor Core 完成相当于两次单 SM MMA 规模的大运算。对比上面左右两图，2 个 SM 计算的是同样的 MMA 工作量 `2*BM x MMA_N x BK`（`MMA_N` 表示 MMA 形状的 N 维度），产出同样的结果，但 2xSM 指令把 B tile 的共享内存占用减半了。

与"多播加载 + 单 SM MMA"相比，2xSM MMA 从两个方面减少共享内存流量。第一，CTA 0 和 1 仍像多播加载那样各加载 B tile 的同一半（见[图 5](https://www.modular.com/blog/matrix-multiplication-on-nvidias-blackwell-part-3-the-optimizations-behind-85-of-sota-performance#figure-05)），但那只是一次普通 TMA 传输，多播这一步被省掉了。其次，B tile 从共享内存到 tensor memory 的流量也减半，因为我们在分布式共享内存中只保存一份。

发起 2xSM MMA 的代码与单 SM MMA（[见上一篇博客](https://www.modular.com/blog/matrix-multiplication-on-nvidias-blackwell-part-2-using-hardware-features-to-optimize-matmul#mma)）非常相似，区别在于使用了 `elect_one_cta`。由于两个 SM 协作完成一次 MMA 运算，只应由一个 CTA 发射指令——即每对 CTA 中 ID 为偶数的那个。因此 `elect_one_cta` 是一个选择发射 CTA（也称 leader CTA）的谓词。

#### Tensor memory 布局

使用 2xSM MMA 指令时，两个 CTA 均分 M 维度（`MMA_M`），即 `BM = MMA_M/2`，各自在 tensor memory 中持有形状为 `BM x MMA_N` 的一半结果。该指令支持 `MMA_M` 取 128 和 256。当 `MMA_M=256` 时，每一半的 TMEM 布局与单 SM MMA 相同，如下图 7 所示。上半部分存在 leader CTA，下半部分在其配对 CTA 中。向全局内存的输出与上一篇博客中 kernel 4 的做法一致。

图 7：tensor memory 布局

当 `MMA_M = 128` 时布局有所不同。由于 `MMA_M = 128` 在生产中不太常用，这里略过细节，[请读者直接看代码](https://github.com/modular/modular)。

这一实现让我们来到 360.2 TFLOPs，约为 SOTA 目标的 20%。看性能剖析，即使用的是高级 MMA 指令，我们仍然受限于全局内存吞吐——计算依然要等待数据传输完成。下一项优化就是要消除这一障碍，加大计算与传输的重叠。

## 内核 6：2SM 流水线

为了在讲解这个内核时保持代码整洁，我们把"通过 TMA 加载 tile 到共享内存"的逻辑封装成 `load_AB()` 调用，把"调用 MMA"的逻辑封装成 `consume_AB()`，再进一步把写出的代码抽象成 `store_C`。Kernel 6 的代码在[这里](https://github.com/modular/modular/blob/main/max/kernels/test/gpu/linalg/matmul_blackwell_iterative/6_2sm_pipelined.mojo)。

在这个粒度上，上一个内核做的事情是：

Mojo

for i range(K/BK):
  # Issue asynchronous TMA load
  load_AB()
  # Wait on barrier until they're loaded
  tma_mbar[0].wait(tma_phase)
  # Issue asynchronous MMA
  consume_AB()
  # Wait on barrier until they're consumed
  mma_mbar[0].wait(mma_phase)

store_C()	# Write the results out

在任何时刻，都有一半硬件在空转：要么 Tensor Core 在等数据到达，要么 TMA 在等 MMA 结束以腾出共享内存缓冲区。数据依赖让 CTA 无法同时利用两个硬件单元。

图 9：CTA 之间因数据依赖产生的争用

### MMA 与 TMA 的流水线化

克服空转的经典算法是在共享内存中引入多个缓冲区，通过流水线让 MMA 与 TMA 重叠。要做这件事，先检查共享内存用量。

在 Blackwell GPU 上，内核最多可访问 227 KB 共享内存（共享内存 + L1 缓存合共 228 KB，但必须给 L1 留 1 KB）。到目前为止，针对 BF16 最大的 256x256x16 形状 2xSM MMA 指令，我们的用量是：

- 一个 A tile：`BM x BK x 2B = (MMA_M / 2) * 64 * 2B = 16 KB`
- 一个 B tile：`BN x BK x 2B = (MMA_N / 2) * 64 * 2B = 16 KB`
- 一个 C tile：`BM x MMA_N x 2B = 64 KB`

用掉的容量还不到一半。利用剩余的共享内存容量，我们引入 5 个 stage，并把它们组织成一个[循环缓冲区](https://en.wikipedia.org/wiki/Circular_buffer)。

图 10：5 级循环缓冲区

然后让 TMA 和 MMA 并行地在缓冲区上推进：当 MMA 在消费某个缓冲区时，TMA 可以往另一个缓冲区[预取](https://en.wikipedia.org/wiki/Prefetching)数据供后续计算使用。这样就能加大计算与通信的重叠。

图 11：借助循环缓冲区实现通信与计算的重叠

### **Warp 特化**

要实现这种流水线模式，还得引入另一个重要概念——warp specialization（warp 特化）。此前几个内核一直用 4 个 warp，因为从 TMEM 加载、发起 TMA 和 MMA 都必须发生在 0 号线程。要让 TMA 和 MMA 并行发射、分别作用于不同流水线 stage，就得让不同的 warp 各司其职，这就是 **warp specialization**。高层代码结构如下：

Mojo

if WarpRole.is_main_load():
    for i in range(num_iters):
      ...
      mma_mbar[stage].wait(phase)
      # issue TMA loads and singals tma_bar
      ...

    if WarpRole.is_mma():
      for i in range(num_iters):
        ...
        tma_mbar[stage].wait(phase)
        # Issue 2xSM MMA and signals mma_mbar
        ...
        mma_arrive_multicast[cta_group](mma_mbar, c_mma_mask)

我们专门安排一个 warp 发射 TMA、一个 warp 发射 MMA，两者并发地遍历各 tile。此外还需要 warp 之间互相通知：某个 tile 是否已到达、是否已消费、底层缓冲区是否可以写入新数据。这种通信通过内存屏障完成。上面沿用了之前内核的内存屏障，只是 MMA warp 现在等待的是 TMA 屏障（由 TMA warp 发信号）以确认输入就绪可算；类似地，TMA warp 等待 MMA 屏障以确认缓冲区已腾空可写入新数据。

### 输出

输出阶段仍需要 4 个 warp 来使用 TMEM。遵循 warp 特化思路，我们为输出单独分配 4 个 warp。下一篇文章中这将必不可少——以便让输出与 TMA、MMA 重叠。我们还需要另一个内存屏障，在 MMA 与输出 warp 之间通信"MMA 结果已就绪可输出"。高层结构变成：

Mojo

if WarpRole.is_main_load():
    for i in range(num_iters):
      ...
      mma_mbar[stage].wait(phase)
      # issue TMA loads and singals tma_bar
      ...
      if WarpRole.is_mma():
        for i in range(num_iters):
          ...
          tma_mbar[stage].wait(phase)
          # Issue 2xSM MMA and signals mma_mbar
          ...
          mma_arrive_multicast[cta_group](mma_mbar, c_mma_mask)
        # Signal output warps
        if elect_one_sync():
          mma_arrive_multicast[cta_group](compute_barrier, mma_complete_mask)
            
  if WarpRole.is_epilogue():
    compute_barrier[].wait()

    ...

这里 MMA warp 额外向一个新的内存屏障 `compute_barrier` 发信号，输出 warp 则在 `compute_barrier` 上等待以确保结果就绪。写出部分与之前相同。

对这套流水线策略做基准测试，性能来到 1429 TFLOPs，即 SOTA 的 81%。

## 内核 7：写出的双缓冲

到目前为止我们优化的是输入到 matmul 的数据加载，其实输出的存储同样可以优化。先快速回顾一下结果是如何从 TMEM 存到全局内存的。Kernel 7 的代码在[这里](https://github.com/modular/modular/blob/main/max/kernels/test/gpu/linalg/matmul_blackwell_iterative/7_double_buf_writeout.mojo)。

Mojo

def store_c():
  # move all of tensor memory into registers
  registers = tcgen05_ld[
  	parameters
  ](tmem_address)
  # move all of registers into shared memory
  for block_offset in range(BN/TMA_BN):
  	for st_matrix_offset in range(TMA_BN//16):
      st_matrix[c_smem_tile, registers]
  # move the entire shared memory tile into global memory
  c_tma_op.async_store(
    c_tma_tile,
      ((block_idx.x * MMA_N + thread_idx.x * TMA_BN), (block_idx.y * BM)),
    )

存储 C 数据分三大步：TMEM → 寄存器，寄存器 → 共享内存，共享内存 → 全局内存。由于数据依赖，这些传输是顺序执行的。但这并非必须——尤其 TMA store 本身就是异步的。套用之前的思路，我们可以把 TMA 和 MMA 操作流水线化。

具体做法是在共享内存中声明两个形状为 `BM x StageN` 的输出 tile（即双缓冲），在两者之间来回切换。为简单起见，我们从 `stageN = 32` 开始（这是一个可调的值）。双缓冲流水线策略在两次迭代中的效果如下图所示。`stmatrix` 把第一个输出 tile 存进共享内存后，我们发出 TMA store 但不阻塞，而是立刻开始从 TMEM 加载、用另一个缓冲区把数据写入共享内存。采用这种调度，TMA store 就与另一个 tile 的 TMEM ⇒ 寄存器 ⇒ 共享内存传输重叠了。

图 13：双缓冲流水线的第 1 次迭代

图 14：双缓冲流水线的第 2 次迭代

要在 Mojo 中实现这个流水线策略，先把输出拆成 `MMA_N / StageN = 8` 次迭代。每次迭代从 TMEM 处理 `stageN = 32` 列。TMEM 加载和 `stmatrix` 代码为简洁起见省略了，其实与之前内核基本相同，只是操作的 tile 更小。

这段代码的关键在于如何同步 TMA store。回顾一下：`commit_group` 把之前的 TMA store 提交为一组，`wait_group[N]` 等到最多只剩最后 N 组仍在途（第 N+1、N+2 等组已完成）。上面的代码中，第一次迭代不等待，因为它可以用第二个缓冲区继续推进；第二次到第 `num_stage - 1` 次迭代则等到只剩 1 个 TMA store 在途。这就让 TMA store 得以与下一次迭代的 TMEM 加载和 `stmatrix` 重叠。最后，末次迭代自然要等所有 TMA store 完成。

这种流水线执行还附带一个（免费的）好处。要解释这一点，得回顾 kernel 5 的共享内存用量。

- 5 份 A、B tile 用于流水线：`5 * (BM + BN) * BK * 2B = 160 KB`
- 用于输出的 C tile：`BM * BN * 2B = 64 KB`
- 内存屏障、tensor memory 地址等少量占用。

输出占了共享内存用量的约 40%。而现在内核只用 `2 * BM * StageN * 2B = 16 KB`，省下的 48 KB 可以用来加深流水线，让 TMA 与 MMA 有更多重叠空间。

这项优化又带来 64 TFlops 的提速，内核达到 SOTA 的 85%。
