# LLVM 开发者大会 2026：agentic 时代的持久基础设施

Michael Dunn-OConnor

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a82c/6aeb932a7c8fed75ff9caae5_LLVM-CoverImg.jpeg)

社区

我参加了今年的 [LLVM 开发者大会](https://llvm.swoogo.com/2026devmtg/12144109)，一场场演讲绕来绕去都回到同一个问题上：加速器代码的增长速度已经超过它周围共享工具的建设速度。agentic 开发，正如周二的主题演讲所说，是那头房间里的大象。团队可以为特定设备快速生成优化代码，而这种速度会让人感觉架构是可以随便扔的。当下的节奏在把团队推向一次性方案，但持久的软件基础设施仍然依赖共享的标准、工具和抽象。像 LLVM 这样的社区，未来几年要处理的正是这层紧张关系，才能继续造得出留得住的基础设施。近期 Domain-Specific Languages（DSL）的爆发式增长就是这层紧张关系的一个症状，也是给 [MAX](https://max.modular.com/) 和 [Mojo](https://mojolang.org/) 送来的一次重大机会。

Weiwei Chen 在 2026 LLVM 开发者大会 MAX 与 Mojo Workshop 上做演讲

### **在 agentic 时代维护开源软件项目**

Kristof Beyls 的主题演讲提出的问题是：agentic 工程对编译器的未来意味着什么。他借用 Daniel Kahneman 那本 [*《思考，快与慢》*](https://en.wikipedia.org/wiki/Thinking,_Fast_and_Slow) 里 System 1 与 System 2 的划分，把 agents 比作 System 1 思维：快、直觉、产出量大；在他这套类比里，编译器属于 System 2：慢、审慎、按规则办事。从这个视角看，agents 并没有让编译器变得不那么重要，反而让那层审慎、可验证的东西更重要——因为快速的代码生成，只有在背后有靠得住的东西撑着时才有用。

Kristof 对这一问题的追问，同时也透露了很多关于开源软件项目未来的东西。Kristof 认为，持久的开源项目依赖三件事：把意图传达清楚、把认知维持住、把贡献者扶持好。如果贡献要延续核心维护者所期待的架构愿景和质量标准，项目就得更刻意地把那份意图写下来、传出去。

传统上，贡献者是通过提 issue、提提案、提 pull request，再一轮轮修订，自然而然地把项目的架构和规范内化进自己脑子里的。Kristof 强调 "contributor poker" 至今仍然重要：赌一个新贡献者会给项目带来价值，哪怕他第一个 PR 还得靠维护者费力气才落得下去。如果 agents 正在把这个过程里那些有生产力的摩擦力磨掉，那就得靠沟通把它补回来（以及更好的提交校验）。现场听众对"贡献者认知能否与 agentic 贡献相容"要更怀疑一些，理由是"drive-by"式的 PR 以及新贡献者根本不沟通（Zig 就正因这一点[禁止了 AI 贡献](https://kristoff.it/blog/contributor-poker-and-ai/)）。在 agentic 时代投入贡献者，一个关键动作是让项目即便规模变大也依然让人读得懂，从而拦住那些急切的贡献者把思考交给 agent。

### **减少重复劳动**

周三的主题演讲来自 Google 的 Nick Desaulniers、Anshul Nigham 和 Jordan Rupprecht，聚焦在维护一份 LLVM tip-of-tree fork 的机会与挑战上。其中一个发现很扎眼：更新拖一次就会拖更多次，因为 breaking change 会累积。维护者们发现，同一个 monorepo 里各个团队都在各自独立地应用 LLVM 和 MLIR 的更新，重复做维护工作。演讲者给出的方案是更好的共享工具，让协作更高效、更协调。这些结论和前一天主题演讲的要点相互呼应。一次性贴膏药的方案比以往任何时候都容易做，但各个团队脱离共享架构与共享工具，就是在重复投入，最后留下越来越难懂、越来越难维护的代码。

### **借 DSL 提速**

新一代加速器不断到来，老一代仍在服役，所以工作假设是新硬件必须和现有硬件并行跑，而不是取而代之。NVIDIA 的 Rajat Bajpai 讲了怎么更新接口，让开发者能用上新硬件特性、同时保住向后兼容。在走廊里聊天时，工程师们从另一面描述着同一种张力：既要写针对具体加速器的可读代码，又要同时支持多种架构。最常见的答案似乎是——造越来越多的 Domain-Specific Languages（DSL）。

Maksim Levental、Guray Ozen 和 Amir Mohammad Tavakkoli 关于 NVIDIA 的 BaseDSL 项目的演讲说明，团队正在设法更高效地造新 DSL。BaseDSL 是一个平台，通过一系列插件在 MLIR 之上搭建自定义 Python DSL，让各团队起自己 DSL 的时候少做重复劳动。但即便有了共享框架，团队最后拿到的仍然是互不兼容的 DSL、仍然没有共享工具，而且每一条都得单独维护。BaseDSL 目前仅在 NVIDIA 内部使用，但现场关于要不要开源的提问说明，更广泛的社区希望有一种更省事的方式来造 DSL。

然而 DSL 的扩散和主题演讲立起来的原则是冲突的。Kristof 说，持久的项目需要共享的意图和给人看得懂的抽象。Google 的主题演讲展示了重复维护的成本。越来越多的 DSL 却把团队往反方向拉。每一条 DSL 都提供了必要的优化，但它们合在一起，就把需要被理解、被写文档、被维护的东西乘了好多倍。另一条向前走去的路，是像 Mojo 这样的语言——在不同加速器之间带来共享的抽象和工具，同时在性能上不妥协。

### **Mojo 所带来的（其实并不）独一无二的机会**

今年，Modular 主持了一整天的会前 workshop，主题是 Mojo 和 MAX。workshop 结束的时候，我心里在想：Mojo 有机会在不同团队、不同硬件之间造出一个共享生态，这份机会是独一无二的。Chris Lattner 提醒我，Mojo 现在所处的局面，正是八年前的 MLIR。

那时候 Chris 还在 Google，要给五种不同的芯片支撑 AI 编译器开发，每一种都有自己的技术栈。各团队都在自己造基于 SSA 的优化器，架构和工具没法共享。MLIR 的做法是把这些编译器的实现细节统一到一个标准里，团队可以在更高的抽象层级上工作，互操作也高效得多。

Mojo 提供的是一个统一层，做法和 MLIR 一样，只是往上抬了一层。它是一门完整的语言，通过 MLIR 做 lowering，所以它建立在 LLVM 贡献者已经熟悉的那套基础设施之上。这些 DSL 正在解决的那些问题，要求给开发者很高的控制权、要求跨各种加速器都拿到性能，Mojo 就是围绕这些需求设计的，语法可读、metaprogramming 也够强。[关于 Mojo 与 Triton 这类 DSL 相比如何的更多背景，看 Fabio 的 [Structured Mojo Kernels](https://www.modular.com/structured-mojo-kernels) 系列。]

MAX 叠在 Mojo 之上，把这份统一做完。MAX 提供加速器支持，Mojo 就是它的编程接口。硬件支持在 MAX 里造一次，用同一门语言来调优，而不是让每个团队带着自己的 DSL 和技术栈重来一遍。MAX 与 Mojo 生态合流之后，也让那种协作成为可能——正是这种协作把大项目的方向和架构愿景绑在一起。[Modular hardware alliance](https://www.modular.com/alliance) 正在推进这件事，通过协调硬件 bring-up 的模式来落地。这个联盟把 LLVM 那套模式应用到 AI 计算上：由多家硬件厂商共建同一层软件，用一致性测试让整个生态保持兼容。

### **建设一个社区**

Kristof 的主题演讲之后，一位听众（本身也是 LLVM 的维护者）去排队做 Q&A，说自己被大批 drive-by、AI 生成的 PR 磨到既挫败又灰心，因为根本没有一个人类开发者愿意接反馈、把 PR 一路推到底。整个会场都能看出那种共鸣。问题并不限于开源的外部贡献。在 agentic 时代维护关键软件，需要共享的工具、标准和抽象。还需要一个愿意把人的时间投到协作、投到塑造共享愿景、投到带新贡献者上的社区。我在 Mojo 社区里看到这些实践正在长出来，也有像 [Mojo 贡献者指南](https://mojolang.org/community/contributing/) 和 [Modular AI Tool Use Policy](https://github.com/modular/modular/blob/7e509d8d281a7fe8354e838a3d19245bbc27d175/AI_TOOL_POLICY.md)（灵感来自 [LLVM AI Tool Use Policy](https://llvm.org/docs/AIToolPolicy.html)）这样的资源在支撑着它。离开今年的 LLVM 开发者大会时，我确信这样的社区仍然是做得出来的。
