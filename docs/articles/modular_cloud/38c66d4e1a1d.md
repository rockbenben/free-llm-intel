# LLVM 开发会议 2026：代理时代的耐用基础设施

迈克尔·邓恩-奥康纳

![](https://cdn.prod.website-files.com/68c9c3107effc2ea46e1a82c/6aeb932a7c8fed75ff9caae5_LLVM-CoverImg.jpeg)

社区

我参加了今年的 [LLVM 开发会议](https://llvm.swoogo.com/2026devmtg/12144109)，会谈不断回到同样的问题：加速器代码的倍增速度比周围的共享工具更快。正如周二的主题演讲所说，代理开发是房间里的大象。团队可以快速生成代码以针对特定设备进行优化，而这种速度可以使架构感觉是一次性的。虽然当前的步伐将团队拉向一次性解决方案，但持久的软件基础设施仍然依赖于共享的标准、工具和抽象。像 LLVM 这样的社区需要在未来几年克服这种紧张局势，继续建设持久的基础设施。最近领域特定语言 (DSL) 的激增就是这种紧张关系的一个症状，并且为 [MAX](https://max.modular.com/) 和 [Mojo](https://mojolang.org/) 提供了重大机遇。

Weiwei Chen 在 2026 年 LLVM 开发者会议 MAX 和 Mojo 研讨会上发表演讲

### **在代理时代维护开源软件项目**

Kristof Beyls 的主题演讲询问代理工程对编译器的未来意味着什么。借鉴 Daniel Kahneman 的[*思考，快与慢*](https://en.wikipedia.org/wiki/Thinking,_Fast_and_Slow) 中系统 1 和系统 2 的区别，Kristof 将智能体与系统 1 的思维进行了比较：快速、直观且多产。在他的比较中，编译器属于系统 2：缓慢、深思熟虑且受规则约束。从这个角度来看，代理不会降低编译器的相关性。它们使经过深思熟虑的、可验证的层变得更加重要，因为快速代码生成只有在有可靠的支持时才有用。

Kristof 对这个问题的探索也揭示了很多关于开源软件项目的未来。 Kristof 认为持久的开源项目取决于三件事：沟通意图、保持认知和支持贡献者。如果贡献是为了维持核心维护者期望的架构愿景和质量标准，那么项目需要更刻意地记录和共享该意图。

传统上，贡献者通过提交和修改问题、提案和拉取请求来有机地内部化项目的架构和标准。 Kristof 强调了“贡献者扑克”的持续重要性：押注新的贡献者将为项目带来有价值的补充，即使他们的第一个 PR 需要维护者的努力才能落地。如果代理商正在消除此过程中的生产性摩擦，则必须通过沟通（以及更好地验证提交）来加强它。观众更加怀疑贡献者认知与代理贡献是否兼容，理由是“路过”的 PR 和新贡献者缺乏沟通（正是出于这个原因，Zig [禁止人工智能贡献](https://kristoff.it/blog/contributor-poker-and-ai/)）。在代理时代投资贡献者的一个关键步骤是，即使项目规模扩大，也要保持人类可以理解的程度，以阻止热心的贡献者将自己的想法交给代理。

### **减少重复工作**

周三的主题演讲（来自 Google 的 Nick Desaulniers、Anshul Nigham 和 Jordan Rupprecht）重点讨论了维护 LLVM 树尖分支的机遇和挑战。一个突出的发现是：随着重大变化的复合，延迟更新会导致更多的延迟。维护人员发现，团队在同一个单一存储库中独立应用 LLVM 和 MLIR 更新，从而重复了维护工作。演讲者的解决方案是更好的共享工具，以实现更高效、更协调的工作。这些结论呼应了前一天主题演讲的要点。一次性创可贴解决方案比以往任何时候都更容易，但跨团队共享架构和工具的偏离会导致重复工作，并使代码更难以理解和维护。

### **通过 DSL 的速度**

新的加速器不断涌现，而早期的加速器仍在使用，因此工作假设是新硬件必须与现有硬件一起运行，而不是取代它。 NVIDIA 的 Rajat Bajpai 介绍了更新界面，以便开发人员可以使用新的硬件功能，同时保持向后兼容性。在走廊谈话中，工程师们从另一方描述了同样的紧张局势：如何在支持多种架构的同时编写可读的、特定于加速器的代码。最常见的答案似乎是创建越来越多的领域特定语言（DSL）。

Maksim Levental、Guray Ozen 和 Amir Mohammad Tavakkoli 关于 NVIDIA BaseDSL 项目的演讲表明，团队正在寻求更高效地创建新的 DSL。 BaseDSL 是一个平台，用于通过一系列插件在 MLIR 之上构建自定义 Python DSL，从而减少团队启动自己的 DSL 时的重复工作。即使使用共享框架，团队最终仍然会遇到不兼容的 DSL 和没有共享工具，并且每一个都必须维护。 BaseDSL 目前属于 NVIDIA 内部，但观众对开源的疑问表明更广泛的社区希望有一种更简单的方法来创建 DSL。

然而 DSL 的传播与主题演讲所确立的原则相冲突。克里斯托夫认为，持久的项目需要共同的意图和人类可读的抽象。谷歌的主题演讲展示了重复维护的成本。越来越多的 DSL 将团队拉向另一个方向。每个 DSL 都提供了必要的优化，但它们一起增加了必须理解、记录和维护的内容。另一种前进的道路是像 Mojo 这样的语言，它可以在不影响性能的情况下跨加速器共享抽象和工具。

### **Mojo 提供的（实际上不是）独特的机会**

今年，Modular 主持了为期一天的关于 Mojo 和 MAX 的会前研讨会。在研讨会结束时，我认为 Mojo 在不同团队和硬件之间创建共享生态系统的机会是独一无二的。 Chris Lattner 向我指出，Mojo 的处境与 MLIR 八年前的处境相同。

当时 Chris 在 Google，支持五种不同芯片的人工智能编译器开发，每种芯片都有自己的堆栈。每个团队都在构建自己的基于 SSA 的优化器，无法共享架构或工具。 MLIR 通过将这些编译器的实现细节统一到一个标准中解决了这个问题。团队可以在更高的抽象级别上工作并更有效地进行互操作。

Mojo 提供了一个统一层，与 MLIR 的方式相同，是堆栈的上一层。它是一种通过 MLIR 降低的完整语言，因此它构建在 LLVM 贡献者已经知道的基础架构上。 DSL 正在解决的问题需要开发人员在不同的加速器上实现高度控制和性能，而 Mojo 就是围绕这些要求而设计的，具有可读的语法和强大的元编程。 [有关 Mojo 与 Triton 等 DSL 的比较的更多背景信息，请参阅 Fabio 的 [结构化 Mojo 内核](https://www.modular.com/structed-mojo-kernels) 系列。]

MAX 在 Mojo 上分层以完成统一。 MAX 以 Mojo 作为编程接口提供加速器支持。硬件支持在 MAX 中构建一次并通过单一语言进行优化，而不是使用每个团队的 DSL 和堆栈进行重建。统一的 MAX 和 Mojo 生态系统还可以实现协作，使大型项目与架构愿景保持一致。 [Modular硬件联盟](https://www.modular.com/alliance) 正在通过协调硬件启动模式来推进这项工作。该联盟将 LLVM 模型应用于人工智能计算：跨硬件供应商构建的通用软件层，并通过一致性测试来保持生态系统兼容。

### **建立社区**

Kristof 的主题演讲结束后，一位观众（和 LLVM 维护者）排队参加问答，并描述了因提交大量由 AI 生成的 PR 而感到沮丧和沮丧，而没有人类开发人员愿意接受反馈并完成它们。整个房间里都可以看到共识和同理心。这个问题不仅限于对开源的外部贡献。在代理时代维护关键软件将需要共享工具、标准和抽象。它还需要一个愿意投入人力时间进行协作、制定共同愿景和指导新贡献者的社区。我看到 Mojo 社区中出现了这些做法，并得到了 [Mojo 贡献者指南](https://mojolang.org/community/contributing/) 和 [Modular AI 工具使用政策](https://github.com/modular/modular/blob/7e509d8d281a7fe8354e838a3d19245bbc27d175/AI_TOOL_POLICY.md) 等资源的支持（受到 [LLVM AI 工具使用政策](https://llvm.org/docs/AIToolPolicy.html) 的启发）。离开今年的 LLVM 开发会议时，我确信这种社区仍然是可能的。
