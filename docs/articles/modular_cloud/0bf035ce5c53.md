# 结构化 Mojo 内核（四）：可移植性与未来之路

本系列的[第 1](https://www.modular.com/blog/structured-mojo-kernels-part-1-peak-performance-half-the-code)–[3](https://www.modular.com/blog/part3_composition_in_practice.md)篇表明：把 IO、流水线、计算三类关注点分离成可组合的组件，能在不牺牲性能的前提下简化开发。本篇要证明的是——当目标硬件改变时，结构化 Mojo 内核的收益依然成立。

GPU 可移植性的历史记录毁誉参半。"一次编写，到处运行"通常等于"一次编写，到处跑得慢"。CUTLASS 根本不尝试跨出 NVIDIA 硬件，而且在同代硬件内也常常受限。Triton 提供了可移植性，但在非 NVIDIA 目标上性能滑坡。传统智慧说：可移植和快，你只能选一个。

结构化 Mojo 内核给出第三个选项：生而可移植，再逐步特化。

## AMD MI355X：一台真正不同的机器

AMD MI355X（CDNA4）在硬件层面与 NVIDIA Blackwell 几乎没有共同点。下表总结了两者在能力与术语上的差异：

| 特性 | NVIDIA B200 | AMD MI355X |
| --- | --- | --- |
| 线程组规模 | 32（warp） | 64（wave） |
| 寄存器分配 | 动态 | 静态（均分） |
| 专用 tensor 内存 | 有（TMEM，256KB） | 无（只有寄存器） |
| 硬件屏障 | `mbarrier`（arrive/wait、字节计数） | 无（用原子操作或 `s_barrier`） |
| 异步内存引擎 | TMA（基于描述符、硬件 im2col） | 仅有 `load_to_lds` |
| 每 SM/CU 共享内存 | 228KB | 160KB |
| 矩阵指令 | `tcgen05.mma` | `mfma` |

这些差异是实质性的——它们影响你如何组织线程、如何同步、如何管理内存、如何隐藏延迟。只瞄准最小公分母，会把大量性能留在桌上。

### 为什么 warp 特化在 AMD 上行不通

在 NVIDIA 上，寄存器分配是动态的。只发 TMA 加载的 producer warp 几乎不需要寄存器；跑 MMA 的 consumer warp 拿更多寄存器。寄存器堆据此分区，两边都不浪费容量。

在 AMD 上，所有 wave 平分寄存器。如果你把一半 wave 拨给加载（低寄存器压力）、另一半拨给计算（高寄存器压力），你就浪费了一半寄存器堆——硬件不管你需要多少，一律平分。

这意味着 NVIDIA 那套专职 producer/consumer warp 的模式在 AMD 上并不高效，需要换一种协调策略。

### 乒乓流水线模式

我们的 AMD 内核采用**交替模式**：全部 8 个 wave 既参与加载也参与计算。两个 wave 组（waves 0–3 与 waves 4–7）每个阶段轮换角色：

- **阶段 A**：第 0 组从 stage 0 计算，同时第 1 组向 stage 1 加载。
- **阶段 B**：第 1 组从 stage 1 计算，同时第 0 组向 stage 0 加载。

双缓冲共享内存确保永远有一组数据就绪、另一组在预取。`s_barrier` 操作用以保证跨 wave 组的这一同步。结果是 GPU 的满负荷利用。

### 什么共享，什么适配

尽管硬件差异巨大，两个平台仍共享地基：

**跨平台共享的部分：**

- **TileTensor 与布局代数：**同样的编译期布局类型在两个平台上描述 tile 形状、步长和 swizzle 模式。共享内存里的 `TileTensor[BF16, Layout[...]]`，无论底层存储是 NVIDIA SMEM 还是 AMD LDS，行为完全一致。
- **基于 tile 的分解：**两个平台用同样方式对 matmul 分块（[Goto & Van Der Geijn 调度](https://www.cs.utexas.edu/~flame/pubs/GotoTOMS_final.pdf)与硬件无关）。M、N、K 的 tile 维度、循环结构、输出 tile 布局都是共享的。
- **编译期配置：**`comptime BM = 128`、`comptime BN = 256`、`comptime num_stages = 5`。参数化在两边以同样方式工作。

**各平台的适配部分：**

- **协调策略：**NVIDIA：warp 特化的 producer/consumer + 硬件 `mbarrier`。AMD：基于屏障双缓冲的乒乓模式。
- **同步原语：**NVIDIA：`mbarrier` arrive/wait。AMD：`s_barrier` + 原子计数器。
- **累加器管理：**NVIDIA：TMEM，显式 allocate/deallocate。AMD：基于寄存器的累加器，编译器管理。
- **数据搬运：**NVIDIA：TMA（异步、基于描述符）。AMD：协作式 `load_to_lds`。

共享与平台特定之间的这条边界，正是结构化 Mojo 内核架构的全部要义。平台特定代码住在 TileIO、TilePipeline、TileOp 的实现里，组合它们的内核逻辑不变。

## 可移植的 warp 特化内核

乒乓内核是 AMD 上的一种有效策略。但结构化组件让更有野心的事情成为可能：一套内核结构同时在 AMD 和 NVIDIA 上运行，为了性能再换入平台特定的组件。

计划从这样一个 warp 特化内核开始（与 Blackwell 上相同的协调模式）——让它同时跑在 AMD MI355X 和 NVIDIA A100/H100 上。起步阶段它必然欠佳；目标是验证共同结构成立。然后逐个特化组件：

| 组件 | 公共基线 | NVIDIA 特化 | AMD 特化 |
| --- | --- | --- | --- |
| **TileIO** | 软件管理加载 | TMA（异步、基于描述符） | 协作式 `load_to_lds` |
| **TileOp** | 通用 MMA 包装 | `tcgen05.mma`（Blackwell）/ `wgmma`（Hopper） | `mfma` |
| **TilePipeline** | 软件屏障 | 硬件 `mbarrier` | 原子计数器 |
| **调度** | 软件 tile 分发 | CLC（硬件调度） | 软件回退 |

每一项特化只让内核在对应平台上更快，不波及其他平台。这就是把组合用在可移植性上：你不重写内核，你特化组件。

内核的控制流（循环结构、warp 角色、流水线分级）保持不变。变的只是每个组件接口背后的实现。一次 `TileIO.load()` 调用在 Blackwell 上分派到 TMA、在 AMD 上分派到协作式加载，而内核不知道也不关心是哪种。

可移植内核是本系列一路构建的组件边界的直接产物。Conv2d 证明了换 TileIO 可行；block-scaled matmul 证明了参数化 TilePipeline 可行。可移植内核同时运用这两种技法、横跨多个平台。

## Mojo 如何成就内核组合

这套架构之所以成立，有一个更深的原因——Mojo 在语言层面与 C++ 的分野。

CUTLASS 通过模板特化实现代码复用。你定义一个带数百个类型参数的基础模板，再为每个硬件目标、每种数据类型、每种 tile 形状做部分特化。结果是 50 万行以上的代码库：新增一个平台等于新增一层特化体系，读懂任何一个内核都要穿越多层模板解析。

GPU 编程是在严苛约束下演化出来的：共享内存小、寄存器预算紧、没有虚函数、没有堆分配。C++ 模板是唯一活过这些约束的复用机制。但现代 GPU 有数百 KB 共享内存、专用 tensor 内存、硬件调度单元和异步 DMA 引擎。一个生产内核的软件复杂度已可与数据库引擎比肩——而在那个领域，没人会选模板作为主要架构工具。工具没有跟上硬件。

结构化 Mojo 内核通过组合实现复用。你构建接口干净的小组件，然后把它们拼起来。加载器不同？换 TileIO。数据格式不同？参数化 TilePayload。平台不同？提供满足同一套接口的新组件实现。

C++ 模板是一门独立的亚语言。模板元编程强大，但语法形同外星：那些错误信息、那些 SFINAE（Substitution Failure Is Not An Error）技巧、那些递归模板模式，都源于模板语言当初就不是被作为通用编程语言设计的。于是复用需要庞大的框架机器来支撑。

Mojo 的元编程语言就是 Mojo。一个 `comptime` 表达式在编译期求值，用的就是运行时代码的同一套语法、同一套类型、同一种控制流。参数化结构体就像普通结构体。trait 就像接口。没有第二套模板语言要学，没有框架机器要穿。

在 Mojo 中写可复用代码的自然方式，就和你写任何代码一样：接口清晰的小结构体，组合起来。结构化 Mojo 内核里的"结构化"不是一个框架，而是把基础软件工程应用到一个"以前的工具让基础软件工程行不通"的领域。

结构化 Mojo 内核是 Modular 打造"高性能、可移植计算的统一 AI 推理平台"使命中的又一步。这需要一个可快速扩展、能在多样硬件上可持续维护的内核层。而这些代码是开源的——任何想为多硬件目标编写和维护内核的开发者，都能拿到同样的架构红利。

## 系列结语

本系列出发时回答的是 GPU 编程社区琢磨多年的一个问题：能不能既有干净、可维护的代码，又不牺牲峰值性能？

这是我们找到的答案。

### 数字

| 指标 | CUTLASS | Mojo | 变化 |
| --- | --- | --- | --- |
| Conv2d 特定代码 | 约 870 行 | 约 130 行 | **-85%** |
| 增加 block-scaled | 约 1,500 行 | 约 200 行 | **-87%** |
| 性能 | 基线 | 持平 | **零成本** |

结构化 Mojo 内核用一小部分代码达到与等价 CUTLASS 内核相同的性能。一个新操作（conv2d）靠换 TileIO 用 130 行写成；一种新数据格式（block-scaled matmul）靠参数化 TilePayload 用 200 行加入。架构的收益在持续复利。

### 三条原则

**关注点分离。**TileIO、TilePipeline、TileOp：每个组件拥有自己的领域。conv2d 的移植直接证明了这一点：换掉 TileIO，TilePipeline 和 TileOp 毫发无损。

**组合优于特化。**用 trait 和参数化类型，而非模板体系。三个 TilePayload 实现共享一条流水线；conv2d 共享整个内核基础设施。Mojo 的 `comptime` 系统让这成为写可复用 GPU 代码的自然方式。

**资源管理。**TMEM、流水线、屏障这类 GPU 资源必须显式获取和释放。在 C++ 内核里，这套生命周期通常由手工管理——意味着泄漏和 use-after-free bug 都有可能。Mojo 的上下文管理器把资源生命周期绑定到词法作用域：编译器强制在作用域退出时释放。

### 接下来

- **可移植内核。**一套 warp 特化内核同时跑在 AMD 与 NVIDIA 上，组件逐步特化。
- **注意力融合。**卷积已完成，下一个是 attention；同样的组合原则适用于多阶段融合内核。
- **自动调度。**用约束求解器寻找最优指令排序，把手工调优的调度换成系统性最优的调度。
- **你的贡献。**代码开源。这套架构就是为了解自家硬件的人来扩展而设计的。

## 摘要

- **AMD MI355X 的执行模型根本不同。**静态寄存器、无 TMEM、无 `mbarrier`。乒乓模式直接回应了静态寄存器分配这一约束；tile 分解与布局代数原样带过去。
- **可移植意味着逐步特化，而非源码兼容。**组件边界让你能换平台特定实现而不必重写内核逻辑。
- **组合胜过特化，功劳在 Mojo 的元编程。**CUTLASS 用 C++ 模板特化：50 万行以上、仅限 NVIDIA。结构化内核用组合：小组件、干净接口、平台无关的内核逻辑。这一分野源自语言本身。
- **数字在规模下依然成立。**代码减 48%，conv2d 130 行，block-scaled matmul 200 行，性能零损失。在架构上建的内核越多，削减越复利。
- **这是一个地基。**可移植的 warp 特化内核、注意力融合、自动调度都在路上。原则不变，工作的疆域会继续扩大。
