# MAX GPU：新一代 GenAI 平台上最先进的吞吐量

高性能是 AI 推理栈最重要的特性之一，却常被刚接触 AI 的开发者误解。提升性能永远是在准确率、吞吐量、延迟、质量、时间和成本之间权衡。更麻烦的是，这些权衡几乎总是与某种期望的产品结果相关联。我们在 Modular 对此深有体会——许多设计伙伴和早期客户都在摸索部署高性能 AI 工作负载的最佳方式。

我们帮助众多 AI 工程师和部署者理解：累积的性能增益能让曾经不可想象的应用成为现实——从"可行"跨到"实用"，再变成"平常"。因此我们常向客户解释，基准测试[向来是个难题](https://www.modular.com/blog/how-to-be-confident-in-your-performance-benchmarking)，而本篇要探讨的是：为 MAX Serve 这类 GPU AI 推理服务器做性能基准测试也不例外。

> 想亲手跑跑这些基准测试？完整说明和脚本见这份基准测试教程。

LLM 性能受诸多因素影响，包括底层模型、硬件架构、提示词与响应的长度分布、请求模式等等。更复杂的是，[刻画性能的方式也五花八门](https://hao-ai-lab.github.io/blogs/distserve/)，包括首 token 时间（TTFT）、每输出 token 时间（TPOT）、请求与 token 吞吐量，以及[有效吞吐量（goodput）](https://en.wikipedia.org/wiki/Goodput)。

在 MAX GPU 的首个 24.6 版本中，我们聚焦于能合理代表真实用例和受控测试环境的常见工作负载与指标。我们沿用了 [vLLM 项目的方法学](https://blog.vllm.ai/2024/09/05/perf-update.html)，用异步工作负载配置（即所有请求在时间轴开始时一次性发出）对 [ShareGPTv3](https://blog.vllm.ai/2024/09/05/perf-update.html) 和 sonnet 数据集做了基准测试。选择这些基准还有一个额外好处：为衡量 MAX GPU 性能提供了一个标准参照点。

这些工作负载突出以吞吐量为主指标——异步工作负载没有严格的延迟 SLA，当所有请求一次性发出时，TTFT、TPOT 这类延迟指标实际上就退化成了被模糊处理的吞吐量指标。我们很高兴分享 MAX GPU 发布预览版的高层初始性能结果：测试环境是配备 A100-80GB SXM 的 `a2-ultragpu-g1` GCP 实例，精度为 `bfloat16`。需要说明，这些数字尚未包含 paged attention 及一些其他优化，它们会在 2025 年落地。

以下各节将对这些性能指标做详细分析，考察 MAX GPU 当前的能力、与其他流行服务平台的对比，以及未来可改进的方向。*关于基准测试方法的完整细节，请参阅文末附录。*

## 理解性能

理解 MAX GPU 性能的最简单方式之一就是拿它和别的东西对比。我们选择简单易懂的基准，让对比尽可能直接。虽然我们是 MAX GPU 的专家，但并不是 vLLM 等替代栈的专家——它们各自也都很出色。我们与 vLLM 对比的首要目标是理解我们自己栈的能力、限制和改进方向，而不是下什么确定性的性能结论。

另一个注意事项是 MAX GPU 和 vLLM 使用不同的 KV 缓存算法。vLLM 围绕 PagedAttention 算法构建，而 MAX GPU 在 24.6 版本中使用朴素的缓存实现。MAX GPU 的这一限制主要影响"同时在飞请求数上限"这个参数。在 ShareGPTv3 工作负载上，MAX 最多只支持 248 个并发请求，而 vLLM 可以支持 512 个——足以覆盖基准中的每个请求。在请求更短的 Sonnet Prefill-Heavy 和 Decode-Heavy 工作负载上，MAX 的朴素缓存可以支持 512 个并发请求。因此我们在两个取值下都给出 MAX 的结果，以展示其对性能的影响。

图 2：vLLM 与 MAX 在并发请求上限分别为 248 和 512 时的请求吞吐量对比，覆盖 ShareGPTv3、Sonnet Prefill-Heavy 和 Sonnet Decode-Heavy 三个基准工作负载。每个基准运行 500 条提示词。详情见附录 B。

这个对比中有几点很显眼：

- MAX GPU 在 Decode-Heavy 上的性能随并发请求数增加**显著提升**，这或许能解释它在低并发上限下 ShareGPTv3 表现相对较差。
- MAX GPU 在 Prefill-Heavy 上的性能随并发请求数增加略有**下降**，这很奇怪。
- MAX GPU 在 Sonnet Prefill-Heavy 和 Decode-Heavy 两个数据集上**表现都不错**，后者需要较高的并发请求上限。

这些都是我们想去排查和修复的问题，也正是我们把 24.6 版 MAX GPU 定位为预览版的原因。我们离加入 PagedAttention 支持已经很近——我们相信它能普遍提升性能，但即便没有它，我们取得的进展也足以自豪。

### Batching is all you need：内存效率、批大小与吞吐量

并发请求数增加带动 MAX GPU 吞吐量提升，这非常合理。简化来说，LLM 推理引擎大部分时间在做三件事：

- 把模型权重从 DRAM 读进 SRAM。
- 把 KV 缓存数据在 DRAM 与 SRAM 之间读写。
- 执行大量算术运算。

第 2、3 部分的工作量只取决于请求本身的具体情况，即提示词和响应的长度。而第 1 步的工作量与请求、甚至请求数量都无关。模型权重对每个请求都相同，所以每轮迭代每个批次只需加载一次。大批次摊薄了模型权重加载的成本，从而提升吞吐量。

要达到大批次，推理引擎需要把大量请求装进 KV 缓存。PagedAttention 比朴素 attention 更节省内存，因为它按请求的实际长度而非最大长度来预留 KV 缓存空间。在 ShareGPTv3 数据集中——现实场景也大多如此——请求长度差异很大。相比之下，Sonnet Decode-Heavy 和 Prefill-Heavy 工作负载被构造成请求长度近乎均匀，因此 PagedAttention 与朴素 KV 缓存之间的功能差异较小。这就是为什么 MAX GPU 能在 Sonnet 数据集上以最多 512 并发请求做基准，却在 ShareGPTv3 上不行。提高上限让 Decode-Heavy 的性能提升了 14%！

那为什么 Prefill-Heavy 反而变差了？MAX GPU 构建 prefill 批次时使用的最大批大小比 decode 更小（本例中为 32），这是平衡吞吐量与延迟的常见做法。因此我们本以为 Prefill-Heavy 的性能不依赖并发请求上限。这能解释性能为何没怎么提升，但解释不了为何下降。

### 用 GPU 利用率调试性能

在构建 MAX GPU 这样的复杂系统时，能把性能变化归因到栈中的具体位置，对开发过程非常有帮助。想要做到完美归因几乎不可能，但即便是不完美的归因框架也很有价值。

我们发现特别有用的一个性能指标是 GPU 利用率。按 NVIDIA 工具链的定义，GPU 利用率衡量 GPU 内核处于活动执行状态的时间百分比。这个指标能把总运行时间拆成两部分：**内核时间**（GPU 正在处理）和**非内核时间**（GPU 空闲）。

我们在服务基准中加入了 GPU 利用率测量（借助出色的 `nvitop` 包），可以为 Prefill-Heavy 基准生成指标，帮助我们理解大批次请求下性能损失的原因。

图 3：MAX GPU 在 Sonnet Prefill-Heavy 基准工作负载上的性能指标与并发请求上限的对比。指标的详细定义见附录 A，基准工作负载见附录 B。

可以看到，提高并发请求上限实际上让内核时间略有减少，这符合预期。总体吞吐量的退化应归因于非内核时间的增加——GPU 利用率的下降也印证了这一点。

把这个洞见带回代码，我们认识到：MAX Serve 跟不上这类吞吐量基准开始时涌进的请求洪峰，*并且* MAX Engine 在等 decode 批次填满，导致最大批大小越大时 GPU 停机时间越长。我们正在针对这类突发场景优化 MAX Serve，预计下个版本在该场景下 GPU 利用率会保持稳定。这也提醒我们：衡量整个 AI 推理栈的性能（而不只是 AI 推理引擎）至关重要。

我们还可以看 vLLM 的 GPU 利用率，因为我们把 GPU 指标跟踪加在了基准客户端里，而非只加在 MAX GPU 中。这次看 500 条提示词的 ShareGPTv3 工作负载。

图 4：ShareGPTv3 基准工作负载上 MAX 与 vLLM 的性能指标对比。指标的详细定义见附录 A，基准工作负载见附录 B。

对请求吞吐量和 GPU 利用率来说，越高越好；对内核时间和非内核时间来说，越低越好。

可以看到，vLLM 在内核时间上略有优势，而 MAX 在非内核时间上略有优势。两者互相抵消，最终吞吐量非常接近——差距在 2% 以内。这说明 MAX 可以通过内核性能来提升，而 vLLM 可以通过降低非内核开销来提升。我们预期 MAX 的内核性能在支持 paged attention 的更大批次后会追平差距。

## 接下来是什么？

我们对 MAX GPU 目前的性能感到自豪，也清楚存在一些未来能交付更高性能的工作负载。有多项重要优化没赶得上 24.6，其中最主要的是 PagedAttention 及其带来的内存和批大小改进。我们还在寻求普遍提升小批次下的性能，未来会分享低负载条件下延迟指标的剖析。

基准工作负载与真实用例之间的对齐一直是难题，我们也承认，没有反馈能走多远是有限的。我们很想了解你的工作负载，无论你是否在使用 MAX 栈。我们坚信 MAX GPU 栈的价值，并乐于为你的问题优化它。欢迎到[论坛](https://forum.modular.com/)上和我们聊，并请给我们反馈！2025 年还有更多精彩内容，敬请期待！

## 附录

### 附录 A：性能指标

- **请求吞吐量（req/s）：** 请求总数除以基准运行秒数。
- **输入 token 吞吐量（tok/s）：** 输入 token 总数除以基准运行秒数。
- **输出 token 吞吐量（tok/s）：** 输出 token 总数除以基准运行秒数。输出 token 数是近似值，因为它依赖客户端对响应文本的重新分词，切分结果可能与实际生成的 token 不完全一致。
- **GPU 利用率（%）：** 基准运行期间至少有一个内核在执行的时间占比。
- **内核时间（s）：** 基准期间至少有一个内核在执行的时间总和。
- **非内核时间（s）：** 基准期间没有任何内核执行的时间总和。内核时间与非内核时间之和等于基准总时长。

### 附录 B：基准工作负载

#### ShareGPTv3

[ShareGPTv3 数据集](https://huggingface.co/datasets/anon8231489123/ShareGPT_Vicuna_unfiltered)包含多轮聊天对话。对话的第一轮作为提示词，第二轮作为期望响应，其余轮次全部丢弃。对提示词和期望响应做分词以测量其长度，并按以下条件过滤数据集：提示词大于 4 token 且不超过 1024 token，响应大于 4 token，提示词 + 响应不超过 2048 token。响应长度作为最大输出 token 数随请求发送，并设置请求忽略结束符（EOS）。这样响应长度就被强制与数据集中的一致。平均提示词和响应长度都在 200 token 左右，响应最长接近 2048 输入 token。我们使用 500 条提示词的随机样本运行，不过 5000 也是流行的选择。

#### Sonnet Prefill-Heavy 与 Decode-Heavy

Sonnet 数据集包含 37 首莎士比亚十四行诗的 518 行。每条提示词由两部分构成：一个对每条提示词都固定的前缀，以及从数据集 518 行中随机采样的后缀。与 ShareGPTv3 工作负载不同，提示词会套用聊天模板格式化。与 ShareGPTv3 相同的是，最大输出 token 数被显式设置，且请求被配置为忽略 EOS，以提供最大的可复现性和对工作负载规模的控制。这正是 Prefill-Heavy 和 Decode-Heavy 两种工作负载唯一的差别：Prefill-Heavy 的响应长度设为 16 token，Decode-Heavy 设为 256 token。尽管名字如此，Decode-Heavy 数据集实际上更接近 Prefill 与 Decode 迭代的时间均分。

### 附录 C：我们如何执行基准测试

为了尽量减小基准方法学上的差异，我们的基准客户端基于 vLLM 的 [benchmark_serving.py](https://github.com/vllm-project/vllm/blob/main/benchmarks/benchmark_serving.py) 脚本。我们的版本和详细使用说明见 [MAX 仓库](https://github.com/modularml/max/blob/nightly/pipelines/benchmarking/benchmark_serving.py)。

我们对 MAX GPU 和 vLLM 都测试了容器化版本，vLLM 的配置与其 [nightly-tests.json](https://github.com/vllm-project/vllm/blob/main/.buildkite/nightly-benchmarks/tests/nightly-tests.json) 配置文件保持一致。vLLM：

Bash

docker run --rm --gpus=1 \
    --ipc=host \
    -e HUGGING_FACE_HUB_TOKEN=${HUGGING_FACE_HUB_TOKEN} \
    -p 8000:8000 \
    vllm/vllm-openai:v0.6.3.post1 \
    --model meta-llama/Meta-Llama-3.1-8B-Instruct \
    --num-scheduler-steps 10 \
    --max-num-seqs 512 \
    --max-model-len 2048 \
    --gpu-memory-utilization 0.9 \
    --disable_log_stats \
    --disable_log_requests

`‍`MAX：

Bash

docker run --rm --gpus=1 \
    --ipc=host \
    -e HUGGING_FACE_HUB_TOKEN=${HUGGING_FACE_HUB_TOKEN} \
    -p 8000:8000 \
    -e MODULAR_STRUCTURED_LOGGING=0 \
    modular/max-openai-api:24.6.0 \
    --model-name meta-llama/Meta-Llama-3.1-8B-Instruct \
    --huggingface-repo-id modularai/llama-3.1 \
    --max-num-steps 10 \
    --cache-strategy continuous \
    --max-cache-batch-size 248 \ 
    --max-length 2048 \
    --pad-to-multiple-of 2

`‍`在 Prefill-Heavy 和 Decode-Heavy 场景下，我们设置 `--max-length 768`，并在展示性能与并发请求上限关系时把 `--max-cache-batch-size` 设为 `248` 或 `512`。
