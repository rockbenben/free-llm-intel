# Modular 与高通：相同的代码，新的芯片

今天在 ModCon 主题演讲上，我们分享了 Modular 多芯片（multi-silicon）工作的一项重大里程碑：高通（Qualcomm Technologies）的数据中心 AI 加速器已集成进 Modular Platform。高通深耕高性能、低功耗计算数十年，如今把这份专长投入到专为最佳"每瓦每美元性能"而设计的推理芯片上。开发者现在通过他们在 NVIDIA 和 AMD GPU 上已在使用的同一套软件栈，就能触达这些硬件。这一里程碑是迈向更广泛统一软件基础的一小步——未来它将覆盖从边缘到云端的更多业界加速器。

每当一款新的 AI 加速器进入市场，开发者都要面对同样的问题：我们的栈要重写多少？Modular 的统一计算平台正在让答案变得明确：一行都不用。

在高通收购 Modular Inc 之后，我们很高兴地宣布：高通的数据中心 AI 加速器路线图——从 Qualcomm® Cloud AI 100 开始，延伸至 Qualcomm Dragonfly™ AI 200 及后续世代——正在集成到 Modular 垂直整合的 AI 软件平台（Mojo 与 MAX）中。

这意味着运行在 NVIDIA 和 AMD GPU 上的同一套代码，现在也能面向高通的芯片。相同的抽象，相同的开发者体验，一流的性能，为智能体（Agent）而生。这是第一款集成进 Modular 栈的 ASIC（NPU），也是 MAX 与 Mojo 可移植性的又一力证。

两家公司共享同一个信念：开发者和企业应该能为自己的工作负载挑选最合适的硬件，而不必重写软件栈。

## **数周完成原生适配**

过去几个月，Modular 与高通的工程师并肩工作，把 Qualcomm Cloud AI 100 Ultra 集成进 MAX 和 Mojo。

集成推进得很快。在矩阵乘法内核跑上 Qualcomm Cloud AI 100 后的几周内，团队就让 GPT-2 在 MAX 上端到端执行起来——用的是与 NVIDIA、AMD GPU 相同的高层模型定义和主机代码路径。此后我们扩展到一个现代模型：从第一个 Gemma 4 内核工作到线上服务端点就绪，整个 bring-up 用时不到六个月。

这与典型的硬件 bring-up 不同：集成是原生融入，不是外挂拼凑。Mojo 直接编译到 Qualcomm® Hexagon™ LLVM NPU 后端。硬件能力通过与 GPU 编程相同的抽象，直接映射进 Mojo 标准库。经由 MAX 的设备驱动连接器，Qualcomm Cloud AI 100 以与 NVIDIA、AMD、Apple Metal GPU 相同的方式插入图编译器、服务框架和运行时。

结果就是实践中的可移植 AI 基础设施：新硬件加入平台，开发者体验保持一致。Qualcomm AI 100 的集成，是覆盖高通 AI 加速器路线图（包括 Qualcomm Dragonfly AI200、AI250、AI300）更广泛合作的首个证明。

本文余下部分深入讲述我们如何走到这一步。Bring-up 及后续各节按阶段组织：打基础阶段——让 Mojo 编译器和图编译器可用、为 NPU 写下第一批内核；GPT-2 "Hello World" 管线阶段——拿到可复现的数字；然后是扩展到四颗芯片上运行的 Gemma 4 31B 模型、经 max serve 上线服务；最后一个阶段，新模型和新特性从数周缩短到数天。我们在不到一个季度内从 *Mojo 能跑* 走到 *Gemma 4 在线服务*，并且有信心让下一个使能的模型更快。我们不是在复制 CUDA；我们是在为可移植栈构建一条进入的路径。

## **Qualcomm Cloud AI 100 硬件**

Qualcomm Cloud AI 100 Ultra 是一款性能与成本兼优的 AI 推理方案，专为生成式 AI 和大语言模型（LLM）设计。

Qualcomm Cloud AI 100 Ultra 有 4 个设备、各配 32 GB 内存，每个设备由 16 个 NSP 组成。NSP 支持多线程，我们利用这一点来编排不同的向量（HVX）、DMA 和矩阵（HMX）单元，构建软件流水线。对模型工作影响最大的是两个单元：**HVX** 向量引擎，负责宽 SIMD 向量和逐元素运算，映射到上游 LLVM 的 Hexagon 向量 intrinsic；以及 **HMX** 矩阵引擎，一个专职矩阵乘的单元，承担 GEMM 和 attention 的重活。

内存模型也不同。它没有现代 GPU 上的统一内存；设备使用分立的片上 **VTCM** 和片外 DDR，数据通过 **DMA** 显式在两者间搬运。想要好性能，就必须有意识地把工作切块放进 VTCM、用 DMA 移动数据，而不是指望缓存层次替你隐藏这一切。

HMX 单元要求其操作的数据采用特定布局（称为 *crouton 布局*），转换是有成本的，所以从开发者角度必须尽量把转换成本降到最低。有时留在 HVX 向量引擎上反而比付转换成本更划算。

## **阶段 0：打好地基**

基础建设是后续所有模型适配工作的支撑，因此团队花了大量时间在 Qualcomm Cloud AI 100 系列上搭建 Mojo 平台。这一初始验证与使能工作聚焦于让编译器后端、各类 pass 以及设备特性 API 在目标硬件上跑通。

Mojo 编译器原生利用上游 LLVM，因此在 Qualcomm Cloud AI 100 平台上我们复用现成的 LLVM Hexagon DSP 后端，让我们的 SIMD 类型和运算正确下降（lower）到 Hexagon 向量 intrinsic（HVX）。HMX 和 DMA 则通过绑定（binding）暴露进 Mojo 编程模型，让内核专家能榨干设备性能。

我们把 DeviceContext API（目前面向 NVIDIA 和 AMD GPU 的接口）实现为在 Qualcomm Cloud AI 100 Ultra 卡上运行时对接其 JIT API（用于把内核派发到设备的 JIT 接口）。QAIC JIT API 支持在每个 NSP 上创建命令缓冲区、入队主机与设备间的数据拷贝操作，这些都能映射到 DeviceContext 的等价功能。DeviceContext 本身没有根本性改动，只需适配两点：从 GPU API 的多派发模式改为单流派发，以及把 GPU 的 block/grid 概念改造成 NPU 的对应物。

不过，最大的挑战之一是内核签名预期的差异。Mojo 内核的参数通常是带类型的参数，而 QAIC JIT API 要求内核参数是内存中连续的指针数组。要把 Mojo 内核转成 QAIC 支持的入口点，典型 AI 软件栈得写专门的编译器 pass 来转换函数参数格式。而我们利用 Mojo 语言的反射与编译期能力，把这个从 Mojo 内核签名到 QAIC JIT 签名的转换*纯用 Mojo* 实现了。这大幅简化了实现，还缩短了编译时间。

基本的内核派发跑通后，图编译器概念验证也水到渠成：一个逐元素操作映射为图编译器生成的单个逐元素内核。第一个操作验证了整栈在设备上的可用性，之后我们就能把重心转向优化和性能。

NPU 在许多方面与 GPU 根本不同。一个关键差异是内核派发：GPU 按 grid 和 block 派发，NPU 则按核数与线程数工作。而且如上所述，Qualcomm Cloud AI 100 是 SIMD 设备而非 SIMT，内核编程模型本质不同。

python

```
# Create the NPU device context.
ctx = DeviceContext(device_id=0, api="qaic")

# Allocate device buffers.
var lhs_device = ctx.enqueue_create_buffer[float_dtype](VECTOR_SIZE)
var rhs_device = ctx.enqueue_create_buffer[float_dtype](VECTOR_SIZE)
var result_device = ctx.enqueue_create_buffer[float_dtype](VECTOR_SIZE)

# Copy inputs host -> device.
ctx.enqueue_copy(lhs_device, lhs_host)
ctx.enqueue_copy(rhs_device, rhs_host)
ctx.synchronize()

# Compile: compile_function auto-generates the QAIC entry-point wrapper
# from the kernel's typed signature.
var kernel_func = ctx.compile_function[vector_add_kernel]()

# Launch across the NPU cores/threads.
ctx.enqueue_function(
    kernel_func,
    lhs_device,
    rhs_device,
    result_device,
    Dim(NUM_CORES),
    Dim(THREAD_MASK),
)
ctx.synchronize()

# Copy result device -> host.
ctx.enqueue_copy(result_host, result_device)
ctx.synchronize()
```

下面这段是 Qualcomm Cloud AI 100 NPU 上一个基本的向量加法 Mojo 内核。*npu_work_range* 函数是一个便利辅助函数，把向量总长度均分到所有 NSP 上，并以 mojo 函数的形式供内核使用。获取原生线程与核 ID 的函数同样可用。

python

```
def vector_add_kernel(
    lhs: UnsafePointer[Float32, MutAnyOrigin],
    rhs: UnsafePointer[Float32, MutAnyOrigin],
    result: UnsafePointer[Float32, MutAnyOrigin],
):
    """Vector addition kernel."""
    # Split the total work across all NSP threads; each gets a sub-range.
    var (start, end) = npu_work_range(VECTOR_SIZE)

    for i in range(start, end):
        result[i] = lhs[i] + rhs[i]
```

我们本可以为 NPU 实现一个 SIMT（类 GPU）编程模型，但这并非必需。Modular 栈能在不强加特定编程模型的前提下利用全部硬件特性。对于确需 SIMT 的硬件和算法，我们提供让该层级编程更轻松的抽象。总体上，我们按模式（map、reduction 等）为不同操作分类，并提供把计算（要映射的函数）与调度（循环迭代安排）分离的抽象。于是鱼与熊掌兼得，而不会有次等的性能。

对于 matmul、attention 这类重度内核，内核工程师使用硬件特定 API 与概念为目标手写优化内核，并通过编译期条件尽可能复用现有基础设施。

由于这是我们第一次带起一个非 GPU 目标，加之 QAIC JIT API 相对较新，我们花了大量时间与高通工程师共同设计特性、排查性能瓶颈、让接口更稳定更贴近生产。得益于此，下一个 NPU 的接入会快得多；我们也已经在做 DeviceContext API 的下一版迭代，使其更通用、更便于硬件公司采用。

**要点：** 软件栈的模块化让我们能专注于 NPU *独有的差异点*，其余部分全部复用。建立在 LLVM、MLIR 这类标准技术之上，意味着我们的地基足够坚实。

## **阶段 1：GPT-2 端到端与第一批真实数字**

Mojo 与图路径就绪后，GPT-2 124M 成为 Qualcomm Cloud AI 100 上支持的首个完整模型。GPT-2 是 LLM 界的"Hello World"——小而好测，但足以跑通整条模型管线、图编译器和各类算子。

内核工程师用 HMX 单元写了一个优化的 GEMM 内核，支持任意 M/K/N 值，带 VTCM 分块和 DMA 支持。他们还实现了 GPT-2 所需的全部基础构件，如 LayerNorm、softmax、attention，以及前面提到的逐元素模式。这些 Mojo 构件可在多个模型间复用，并经过独立验证。

随后我们把这些内核接入图编译器，逐个启用，直到图编译器能构建整个模型。第一次运行大约比我们作为基线的 Qualcomm Cloud AI 100 PyTorch 实现慢 1.6 倍。

经过约三周的优化，我们达到**基线的 6.7 倍**，明显快过基线。除其他手段外，我们：

- 实现自定义算子把每一层融合，减少逐算子的内核启动开销，并把融合范围扩展到逐元素之外；
- 为 M=1 的 decode 形状写了专门的 **HVX GEMV 内核**——在这种场景下比 HMX matmul 更快，因为它绕开了 crouton 布局转换；
- 加入**设备信息缓存**和**异步函数派发**，隐藏驱动开销；
- 并应用了多种运行时缓存与派发优化，进一步降低驱动成本。

模型使能只花了几天。我们拿 LLM handbook 中定义的模型，为 Qualcomm Cloud AI 100 平台创建一个带融合算子的变体。随后的几周花在优化软件栈、内核和整体测试基础设施上。

from max.driver import CPU, Accelerator, Device

# ... Model runner ...
dev = Accelerator(0)
with F.lazy(), default_device(dev), default_dtype(DType.float16):

上面的代码展示如何在 MAX 中实例化 GPT-2 模型。这段代码对所有加速器都一样，底层库会把实现路由到当前活动目标。

由于 Mojo 编译器已在设备上工作，在部分团队做 GPT-2 的同时，另一些工程师已经在为下一个阶段 Gemma 4 编写单个内核。借助测试脚手架（test harness），工程师可以在模型跑起来之前就用 Mojo 编写和优化内核。这正是 Modular 软件栈的一大优势。

**要点：** 用 GPT-2 作为初始硬件 bring-up 工具，让我们能快速优化系统侧实现、打通图编译器、设计融合策略，同时内核工程师继续打磨纯 Mojo 内核。而且所有工作都能在多个模型间复用。

## **阶段 2：把 Gemma 4 稠密模型推到 max serve**

确认 GPT-2 稳定且优化到位后，团队其余成员转战 Gemma 4。内核被接入模型定义，图编译器得以在模型管线中调用它们。

从 Modular 栈的视角看，GPT-2 与 Gemma 4 的主要差异在于内核复杂度和通信（fp16 下带 KV Cache 的 Gemma 4 放不进单颗 SoC）。在 GPT-2 上验证过的系统基本面保持不变，我们可以专注于 Gemma 4 特有的差异。

### **更复杂的内核**

Gemma 4 需要比 GPT-2 更丰富的算子集，最典型的是真正的 attention 路径。我们构建了一个分页 flash-attention 内核（Qualcomm Cloud AI 100 上的第一个），设计灵感来自 Flash Attention 4，使用线程特化与软件流水线。我们还实现了现代解码器所需的全部其他内核（旋转位置编码、RMSNorm 等），图编译器则在其能做到的地方自动融合相邻操作。

更有意思的决策是硬件驱动的。HMX 矩阵单元期望权重采用打包的 "crouton" 布局，只有当矩阵乘足够大、能摊薄转换成本时，付这笔转换费才划算。因此在 batch size 为 1 的访存受限 decode 步上，我们走向量单元的 GEMV 内核、完全跳过转换，只在更大的 batch size 上 HMX 路径回本时才切换过去。这类选择由内核剖析和参数化驱动——那让我们能快速验证一系列不同输入下的 mojo 内核。

### **扩展到单设备之外**

一张 Qualcomm Cloud AI 100 Ultra 卡含 4 颗 SoC（每颗 SoC 称为一个*设备*），每颗 SoC 有 32 GB 内存。fp16 的 Gemma 4 31B 仅权重就需要约 60 GB，几乎是单颗 SoC 32 GB 的两倍。模型必须通过张量并行（TP=4）分片到四个设备上。我们利用 QCCL 库，它通过主机接口暴露 all-reduce、broadcast 和 all-gather 集合通信。

具体来说，张量并行把模型分片到四颗芯片上：QKV 与 MLP-up 投影按列并行，attention-output 与 MLP-down 投影按行并行。因此每一层都需要一次**集合通信步（all-reduce）**把部分结果拼回完整，才能继续。集成工作很早就开始了，但直到我们让分布式 matmul 跨全部四颗 SoC 跑起来、权重与激活都分片在各芯片上之后，才得到完全验证。

Qualcomm Cloud AI 100 的通信库（QCCL）相对较新，依赖主机驱动的通信（而非设备发起），因此相比其他方案自然有额外开销。降低这一开销是持续进行的工作，但该库接入我们栈的过程很直接。

### **能跑，就能服务**

我们用引擎基准验证模型，确认 Gemma 4 31B 的输出在容差内匹配 fp16 参考模型。

随后切换到 max serve——它在我们的推理服务器环境中加载同一模型架构。模型和服务环境都不需要任何改动；我们只是把 max serve 指向模型架构文件。这样所有服务工具都能复用，尤其是 max benchmark，我们用其验证不同工作负载并提取性能结果。

我们的 Gemma4 模型性能与 Qualcomm Cloud AI 100 上现有软件方案不相上下

模型上线服务、能跑各类基准（如 arxiv、sharegpt）之后，我们识别出了更多优化空间。例如，我们实现了 MXFP6 权重（加载模型前先转换权重）和基于 int8 的 KV cache，在几乎不损失精度的情况下把 KV cache 用量大致减半。

**要点：** 从一台设备到四台，只需要打通通信层，代码无需进一步改动。而且模型一旦使能，通过 max serve 跑起来轻而易举。

## **阶段 3：从数周到数天，新模型与新特性**

稠密模型上线服务、通用优化落地后，支持新模型或新优化变得越来越简单。特别是在 bring-up 的最后 3 周，我们使能了投机解码（speculative decoding）和 Gemma 4 MoE 变体——两者都复用现有基础设施，为 Qualcomm Cloud AI 100 做的定制非常少。

### **投机解码**

Gemma 4 和其他 LLM 一样一次生成一个 token，每一步都是访存受限。我们用投机解码来加速响应。投机解码使用一个小的快速草稿模型提前提出若干 token（当前配置为 3 个），然后由大的 Gemma 4 模型在一次前向传播中验证，接受其中一致的 token。只要草稿模型正确，一次大模型步的代价就能产出多个 token。

我们的实现用较小的 Gemma 4 "assistant" 权重作草稿模型，对 31B 稠密模型做验证。

投机解码在 Qualcomm Cloud AI 100 上能带来出色性能提升的原因之一，是我们可以增大稠密模型的 M 尺寸（从 1 到 4），这样 decode 路径和 flash-attention 内核就能把多个 GEMV 归并成一个 GEMM、改用 HMX 单元；而较小的草稿模型仍可用 HVX 上快速的 M=1 GEMV 实现。

加入投机解码不需要改动服务架构。我们走同样的 max serve 路径、同样的张量并行分片、同样的内核，只是把较小的权重调度进模型管线。

### **混合专家（Mixture of Experts）变体**

Google 还提供了 Gemma 4 的 Mixture of Experts（MoE）变体——一个 26B 模型，对任意给定 token 仅激活 3.8B 参数，经由一组 MLP 路由。

用 Modular 栈添加 MoE 变体是件顺理成章的事。大部分架构与稠密模型共享（attention、RMSNorm、RoPE、分页 KV cache 等）。我们甚至把投机解码实现直接复用到了 MoE 模型上。

我们实现了路由内核（top-k 步骤）决定每个 token 去哪些专家，并实现了分组 matmul 以高效评估被选中的专家。这全都是在现有实现上的增量改动：只需针对目标平台使能模型，所有现有基础设施（如图编译器优化）原样复用。

QCCL 目前是实现是主机驱动的（通信原语经由主机同步），内核内（in-kernel）的通信原语版本尚未可用，因此我们选择用张量并行而非专家并行来服务 MoE。这样就不必依赖可能很慢的专家 all-to-all。一旦 QCCL 支持内核内通信，我们可以轻松实现 EP 变体，并探索不同配置，在不同工作负载下调优性能。

**要点：** 使能高级特性或模型变体变成增量任务，大部分工作量被摊薄。每一个都只花了一两天完成使能与调优。

## **我们在哪里，接下来去哪里**

那个头条数字（不到一个季度搞定 Gemma 4）只是预告片；重要的是我们如何做到。有三点值得强调。

第一，**这个栈的可移植性是构造出来的。** 为了触达一类新硬件，我们没有分叉模型、图编译器或服务层。**所有硬件目标都活在同一个仓库里，共享绝大部分代码。** 同一个 DeviceContext 抽象，此前面向 NVIDIA 和 AMD GPU，现在面向一个执行模型截然不同的 NPU；同一条模型定义，能在单设备上跑，也能跨四个设备跑，然后直接进 max serve。

第二，**难题被提前化解。** 从基础做起（目标平台上的 Mojo 支持、作为 "Hello World" 的 GPT-2），让我们得以在项目早期就把风险卸掉、为 Gemma 4 打下坚固地基，今后把其他模型带上这颗芯片只会更容易。

**第三，与高通工程师的共同设计加速了工作。** 我们的实现不断对 JIT API 施压，一起解决这些功能与性能问题缩短了每一轮的周转时间。高通通过定期同步会和技术交流，把内核工程师需要的目标硬件细节分享给我们；作为回报，他们也看到了 Modular 栈如何"锻炼"他们的芯片。文档加上通往厂商团队的直达通道，把一个能用的后端变成了一份高性能的实现。

结果是：这套软件栈如今已在 Modular cloud 上服务 token，并且随时能接纳新硬件与新模型。**我们在重度使用智能体工具与技能来加速工作流**——用智能体优化内核、把模型移植到 MAX、自动跑基准和分析结果。AI 模型能从代码库、文档和智能体知识库中快速获取上下文。我们已经建成第一个面向 Qualcomm Dragonfly 系列的知识库，工具有了正确的上下文，迭代速度更快了。

下一步已经在进行：Qualcomm Dragonfly AI 200 是 Qualcomm Cloud AI 100 面向 LLM 时代的演进版。Mojo 编译器支持已在设备上工作，GPT-2 已经能跑。我们正在验证并优化栈的其余部分，以利用更大的内存和高得多的矩阵吞吐。Qualcomm Dragonfly AI 200 原生支持 fp8 和 bf16，用这些格式训练的模型可以在其上高效运行，而我们的栈早已原生支持这两种类型。前方仍有工作：压低 decode 步的 all-reduce 成本、把上下文长度推得更远、带来 Gemma 4 之外的新模型。但核心结论立得住：一个现代模型、一类新硬件，不到六个月带到线上服务端点——用的就是一个为可移植而生的栈。在 Modular，我们会继续迭代，让这个栈更可移植、更高效：DeviceContext 的下一个版本，将把后端 bring-up 交到硬件公司自己手上。
