## Inkwell：为高速扩散而设计的应用

Inkwell 是一个 web 应用，让用户带着自定义角色在无限分叉的路径上创作交互式故事书。当用户打开一个故事，第一页的文字和图像就流入——文字在第一秒内通过 WebSocket 逐字符出现，插图在你阅读时逐渐绘就，而当你点击一个选择时，下一页已经写好并配好插图。围绕新内容的无缝生成来打造用户体验，需要一个能在规模下胜任的推理层。

## 为什么 TTFT 决定你的架构

Inkwell 的核心优化是在文本生成完成之前就开始图像扩散。Gemma 对每一页的结构化输出是一个单一 JSON 对象，字段按顺序为 `title → story → image_prompt → character_anchor → story_plan → choices`。一个流式抽取器监视部分 JSON，在 `image_prompt` 闭合的那一刻（约 305 个 token 中的第 200 个）调用 Flux endpoint。LLM 还会继续流式输出约 1.3 秒的文本。Flux 那 3.3 秒的工作是针对那段尾流进行的，而不是在其之后。

（当 LLM）解析完成时，Flux 还剩约 2 秒的工作。一条 8 秒的串行流水线就变成了文字 420 ms TTFT、总计约 5.9 秒的重叠耗时，而用户全程都在阅读，而不是盯着一个加载动画。

只有当推理提供方在长结构化提示上具备快速 TTFT 和充足的稳态吞吐量时，这个架构才成立。一个延迟的 `image_prompt` 响应会同时给流式文本和图像生成造成瓶颈。

## 预取与 85% 的缓存命中率

流式重叠把首屏拉到 420 ms，但一次冷生成下整页仍需约 5.9 秒。一个以响应性定义的产品需要在任何可能的地方压低这个平均值。

在线性故事里，这通过在用户阅读当前页时预加载并缓存下一页来解决。当用户选择一个"选择你自己的冒险"故事时，会提供三个分叉选项，因此下一页是未知的。Inkwell 不是等用户选择后才生成下一页让用户干等，而是并行预取三个可能的页面。每次预取的生成都带上父场景的 `image_seed`、`character_anchor`、`art_style` 和 `story_plan`，确保视觉与叙事上的连贯。

基于流量数据，用户每页阅读约 7 秒，这稳稳高于那些下一页生成所需的 5.9 秒。当用户从提供的三个选项中选择一个（在生产中约 85% 的情况下会这样），翻页耗时 48 ms。只有在新故事的第一页，或当用户写入一条任何预取都无法预见的完全自定义路径时，用户等待才会超过这个时间。用户所体验到的平均翻页由缓存命中主导，而非由冷生成主导。

## 推理平台的重要性

Modular Cloud 的三个平台属性让 Inkwell 的设计成为可能，而这类属性只有当你在一个不具备它们的推理平台上构建过之后，才真正能体会到。

### 面向两种模态的单一 API 表面

Gemma 4 31B 和 Flux 2-dev 都在 Modular Cloud 上以兼容 OpenResponses API 的 endpoint 暴露。

提供方抽象只是单次构造函数调用：

python

```
self.client = AsyncOpenAI(
    base_url=settings.flux_base_url,  # or llm_base_url
    api_key=settings.modular_api_key,
)
```

更换提供方只是一次环境变量的更改，经由一个 `FallbackProvider` 包装器路由：

python

```
class FallbackProvider:
    async def generate_opening_page(self, prompt, **kw):
        try:
            return await self.primary.generate_opening_page(prompt, **kw)
        except Exception as exc:
            logger.warning("llm_primary_failed err=%s — falling back", exc)
            return await self.secondary.generate_opening_page(prompt, **kw)
```

提示词展开一侧的解析器并不关心是哪个提供方应答的。这消除了数百行提供方专用胶水代码的需要。

### 让重叠设计可行的延迟

在 Modular Cloud 上，Inkwell 在长结构化提示上有 420 ms 的首 token 时间和 78 tok/s 的稳态吞吐量。这使得上文所述文本与图像的重叠生成成为可能。由于 LLM 响应包含供扩散模型使用的 `image_prompt`，更慢的提供方会造成图像生成等待时间的级联放大。

### 运行时占用

Modular 的运行时不到 700 MB，Inkwell 后端镜像总计约 220 MB。在 [Cloudflare](https://www.cloudflare.com/) Containers（Firecracker VM）上，更小的镜像意味着更快的冷启动。一个每 5 分钟的 cron 预热 ping 让无状态池容器保持温热，这在 standard-1 空闲定价下每个环境每周约 4 美元。更小的 Modular 容器占用意味着冷启动既更快也更少。实际上：那些本会在第一次翻页时造成可见延迟的冷启动，反而在 WebSocket 握手完成之前就已就绪。

## 接下来：流式去噪

Inkwell 中剩余的最大延迟是 Flux 调用。即便有 LLM 重叠，用户仍要等约 3 秒图像才出现。Flux API 目前只返回最终的去噪步（第 25 步中的第 25 步），尽管第 5、10、17 步已经包含了大部分可感知的信号：可辨认的构图、定型的色彩与光照、浮现的纹理。第 22 到 25 步精修的是在 1024px 下大多无法感知的细节，但用户要等全部完成才能看到任何东西。这正是 MAX 架构直接发挥作用的地方。MAX 不把每个扩散阶段分别经 PyTorch 运行并在其间做内存往返，而是通过 MLIR 把整条流水线（DiT、VAE、文本编码器、调度器）编译成一个融合的单一执行图。每个去噪步一起被优化，而这条编译好的流水线正是 Modular 能实现服务端中间态发射（intermediate-emit）的原因：这些步骤本就作为一张连贯的图在执行，而非一串必须在 API 边界重新拼接的独立调用。Modular 正在实现这个服务端发射。API 会把去噪步作为 `Server-Sent Events: {step: N, total: 25, image_base64: "..."}` 流式传输。客户端在帧到达时做交叉淡化。

t = 0.4 s → step 5/25（粗略构图，主体可辨认）

t = 0.8 s → step 10/25（色彩与光照定型）

t = 1.5 s → step 17/25（纹理就位）

t = 3.0 s → step 25/25（最终）

把流式去噪与文字打字机结合起来，意味着每一页从第一秒起就成了一条多模态流：文字在页面上填充的同时图像绽放。计算仍是同样的 3.3 秒，但用户从 0.4 秒起就被吸引，而不是等待最终的揭晓。

## 低延迟用户体验的模式

Inkwell 的每一项优化都有一个一致的模式：不要等待完整响应——在中间态到来时就把它们流式输出，并优化首屏时间。

这包括：把故事角色一到达就流式送往打字机、在部分 JSON 的 `image_prompt` 一闭合就抽取它、在用户选择之前就预取所有分叉路径，以及很快地在用户阅读时从 Flux 流式输出中间去噪步。扩散模型一直在内部发射中间态；Modular 正在实现这个服务端发射。

推理平台的职责是让每一种这样的模式成为可能，而不是要求应用绕开它们。一个实时生成式消费级应用中最大的单点杠杆，已不再是模型，而是一个能交付更快响应并暴露中间态的平台。这正是 Modular Cloud 被构建来提供的，而这两个属性让本文中的每一项优化成为可能。
