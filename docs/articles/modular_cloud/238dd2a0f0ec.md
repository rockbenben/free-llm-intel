# GPU 内核的软件流水线（一）：流水线问题

Flash Attention 是个很简单的算法：分块的背靠背 matmul，中间夹一个在线 softmax。整个算法几十行伪代码就能写完。可 Flash Attention 4 的生产内核却有 2,875 行，而最难写对的部分不是数学——是异步执行和流水线同步，全部靠人手从一个任何标准调试工具都无法验证的调度推导出来。

在这个系列的多篇文章中，我们将从第一性原理出发探讨 GPU 内核的软件流水线：把依赖关系形式化为图，用约束求解器解出最优调度，并展示这一切如何通过纯 Mojo 集成进 [MAX](https://www.modular.com/open-source/max)。我们在[《Blackwell 上的矩阵乘法》系列](https://www.modular.com/matrix-multiplication-on-blackwell)的[第 2-4 篇](https://www.modular.com/blog/matrix-multiplication-on-nvidias-blackwell-part-2-using-hardware-features-to-optimize-matmul)中已经探讨过它在矩阵乘法上的实际形态。

在深入细节之前，本文先概览 Flash Attention 4 这类高级内核如何被表达为数据流流水线。后续文章会讨论这套形式化如何帮助我们降低复杂度、提升现代设计的可组合性。

## 注意力机制

本文以 [Attention](https://arxiv.org/abs/1706.03762) 作为驱动示例。具体说，我们研究 Flash Attention（[Dao et al. 2022](https://arxiv.org/abs/2205.14135)、[Dao 2023](https://arxiv.org/abs/2307.08691)、[Shah et al. 2024](https://arxiv.org/abs/2407.08608)、[Zadouri et al. 2026](https://arxiv.org/abs/2603.05451)）算法来展示 GPU 流水线问题。选 attention 做案例研究，是因为算法简单，但要拉满硬件利用率却需要复杂的流水线方案。后文统称 FA；FA3 指适用于 Hopper 的算法，FA4 指适用于 Blackwell 的版本。

### 什么是 attention

多头注意力计算：

$$O = \operatorname{softmax}(QK^T)\, V$$

其中 $Q \in \mathbb{R}^{M \times d}$，$K, V \in \mathbb{R}^{N \times d}$，输出 $O \in \mathbb{R}^{M \times d}$。这里 $M$ 是查询长度（prefill 时为整个序列，decode 时为 1），$N$ 是 KV-cache 长度，$d$ 是 head 维度。

一个具体例子：Qwen3-8B 的 $d = 128$，32 个 Q head 通过分组查询注意力（GQA，Q 与 KV 的比例为 4:1）共享 8 个 KV head，上下文最长可达 $N = 32,768$。GQA 意味着每 4 个 Q head 共用 1 个 KV head，在同样的 Q 计算量下把 KV-cache 读取量降为 1/4。

整个计算分三步：$S = QK^T$（matmul 1）、$P = \operatorname{softmax}(S)$（逐行归一化）、$O = PV$（matmul 2）。完整分数矩阵 $S$ 是 $M \times N$。取最长上下文时，每个 head 就是一张 32768×32768 的矩阵。这非常大——但注意，它只是计算过程中的一个中间矩阵。Flash Attention 算法用循环融合（loop fusion）和循环分块（loop tiling）解决了这个问题。

### 背靠背 matmul：为什么分块至关重要

解决"中间矩阵太大"的问题可以用分块。要理解分块策略，先把 softmax 放到一边，把 attention 简化为两次背靠背 matmul：$O = QK^T V$。逐元素展开：

$$O_{i,l} = \sum_j \underbrace{\sum_k Q_{i,k}\, K_{j,k}}_{S_{i,j}} V_{j,l}$$

**朴素做法**（不落盘中间矩阵 $S$，对每个输出 $(i,l)$ 从头重算内层求和）的代价是 $O(2MNd^2)$ FLOPs。**先把 $S$ 物化**再算 $O = SV$，代价是 $\underbrace{2MNd}_{S=QK^T} + \underbrace{2MNd}_{O=SV} = O(4MNd)$，FLOPs 少了 $d/2 = 64$ 倍——但 $S$ 是 $M \times N$，寄存器或共享内存都装不下。

关键在于观察 $d$**很小**。一个 $B_M \times d$ 的 Q 块是 128×128×2B = 32KB，在单个 SM 的 228KB 共享内存里绰绰有余。所以我们不分 $d$ 维，只分序列维度 $M$ 和 $N$：

python

```
for bm in range(M // B_M):      # grid of CTAs (one per query block)
  for bn in range(N // B_N):    # sequential inner loop
    S_j = Q[bm] @ K[bn].T      # B_M × B_N, in registers
    O[bm] += S_j @ V[bn]        # accumulate
```

两个目标同时达成：$O(4MNd)$ 的 FLOPs，且 $S_j$ 只有 $B_M \times B_N$，从产生到消费全程留在寄存器里。完整的 $M \times N$ 分数矩阵永远不会被物化。Q 只加载进共享内存一次，每次内层迭代复用；K、V 的 tile 则流水式穿过。

> 图 3：分块 attention——Q 驻留共享内存，K 与 V 的 tile 流水穿过。

### softmax 如何破坏分块 attention

上面的分块策略解决了两次 matmul。但 attention 计算在两次 matmul 之间夹了一个 softmax，我们得直面它。问题是：softmax 要在 $S$ 的整行上归一化：

$$\operatorname{softmax}(S)_{i,j} = \frac{e^{S_{i,j} - m_i}}{\sum_{k=1}^{N} e^{S_{i,k} - m_i}}, \qquad m_i = \max_k S_{i,k}$$

有了分块，我们每次只能看到 $S$ 的一个 $B_N$ 宽的切片。我们既没有整行的最大值 $m_i$（数值稳定性所需），也没有完整的分母。朴素做法得对 KV tile 扫两遍：一遍算全局 max 和 sum，一遍归一化并乘 $V$。

### 在线 softmax 实现单遍 attention

解法是在线 softmax（Milakov 与 Gimelshein，"Online normalizer calculation for softmax"（2018），[arXiv:1805.02867](https://arxiv.org/abs/1805.02867)）。Flash Attention 不扫两遍，而是维护运行最大值 $m$、运行和 $\ell$，并随时修正输出累加器。设 $\alpha_j = e^{m_{j-1} - m_j}$。处理完第 $j$ 个 KV tile 后：

$$\begin{align*} m_j &= \max(m_{j-1},\; \max S_j) \\ \ell_j &= \operatorname{diag}(\alpha_j)\,\ell_{j-1} + e^{S_j - m_j}\, \mathbf{1} \\ O_j &= \operatorname{diag}(\alpha_j)\,O_{j-1} + e^{S_j - m_j}\, V_j \end{align*}$$

修正因子 $\alpha_j$ 把所有历史项从 $e^{-m_{j-1}}$ 重新缩放到 $e^{-m_j}$，维持不变式：每个 tile 处理后 $O_j = \sum_{t \leq j} e^{S_t - m_j} V_t$、$\ell_j = \sum_{t \leq j} e^{S_t - m_j}\,\mathbf{1}$。最后一个 tile 结束，$O/\ell = \operatorname{softmax}(S)\, V$ 精确成立。

当 $m_j = m_{j-1}$（头几个 tile 之后的常见情况），$\alpha_j = 1$，重缩放是无操作。更一般地，当 $m$ 的变化小到不会引起数值问题时，重缩放可以整个跳过。FA4 就用了这个优化，更新规则形如 `m = new_max if new_max > m + 8 else m`。这样 softmax 后的最大值被限制在 $2^8$ 以内，后续运算也不会溢出。

> 图 4：跨 tile 的在线 softmax 修正。

伪代码如下（我们加了硬件标注，指明各部分用的是哪块硬件）：

python

```
m = -inf; l = 0; O = 0
for j in range(N // B_N):
    K_j = tma_load(K[j])                 # @load (TMA)
    V_j = tma_load(V[j])                 # @load (TMA)
    S_j   = Q @ K_j.T                    # @mma  (tensor cores)
    m_new = max(m, rowmax(S_j))          # @math (CUDA cores)
    alpha = exp(m - m_new)               # @math (CUDA cores)
    P_j   = exp(S_j - m_new)             # @math (CUDA cores)
    l     = alpha * l + rowsum(P_j)      # @math (CUDA cores)
    O     = alpha * O                    # @math (CUDA cores)  rescale
    O     = O + P_j @ V_j                # @mma  (tensor cores)
    m     = m_new
O = O / l
```

这是对 K 和 V 的单遍扫描，工作量 $O(4MNd)$。代价是每次迭代有一个依赖上一次迭代结果的修正步骤（`rescale`），形成一条循环携带依赖。

### 未流水线的 FA3 内层循环

把一切拼起来，FA3 内核（SM90，Hopper）把在线 softmax attention 算法凝练为 **3 个功能单元**上的 **8 个操作**。两个 warp group：`@tma`（producer，负责 TMA 加载）和 `@consumer`（负责其余一切）。三个用于调度的硬件单元：`tma`、`tc`（Tensor Core）、`cuda`（CUDA core）。

python

```
alloc Q_shared, K_shared, V_shared : shared   # Q once; K,V double-buffered
alloc S, P, m, O : reg

for k in range(N):
    async K_shared = tma_load_K(K, k)          # @tma      tma
    async V_shared = tma_load_V(V, k)          # @tma      tma
    async S = wgmma_qk(Q_shared, K_shared)     # @consumer tc
    sync  (old_m, m) = rowmax(S, m)            # @consumer cuda
    sync  P = softmax(S, m)                    # @consumer cuda
    sync  P_bf16 = cast_p(P)                   # @consumer cuda
    sync  O = rescale(O, old_m, m)             # @consumer cuda
    async O = wgmma_pv(O, P_bf16, V_shared)    # @consumer tc
```

两个 TMA 操作（异步，由共享内存屏障跟踪），两个 Tensor Core 操作（异步，经 commit/wait group 跟踪），四个 CUDA core 操作（同步，在发射它的 warp 上执行）。

依赖结构有 13 条边：9 条同迭代写后读依赖，2 条循环携带递归（d=1），2 条双缓冲共享内存的写后读反依赖（d=2）。

> 图 5：FA3 依赖图——13 条边：9 同迭代、2 循环携带、2 写后读。

顺序写出来，这份代码干净又正确。但它也很慢，因为任何时刻只有一个单元在工作。

## GPU 流水线问题

我们有了一个正确、顺序的内层循环。但这个循环很慢——没有充分利用可用的硬件单元。现代 GPU 的 SM 至少有三个可独立调度的硬件单元：

| 单元 | 干什么 | 操作示例 |
| --- | --- | --- |
| **TMA**（Tensor Memory Accelerator） | 异步大块内存传输（GMEM ↔ SMEM） | `tma_load`、`tma_store` |
| **Tensor Core** | 矩阵乘累加 | `wgmma`（SM90）、`umma`（SM100） |
| **CUDA Core** | 标量/向量运算、归约、类型转换 | `softmax`、`rescale`、`cast` |

这些单元可以*同时*工作，但上面的顺序循环让它们大部分时间在空转：

python

```
for each tile:
    load tile         # TMA busy,  tensor cores idle, CUDA cores idle
    matmul (QK)       # TMA idle,  tensor cores busy, CUDA cores idle
    softmax + rescale # TMA idle,  tensor cores idle, CUDA cores busy
    matmul (PV)       # TMA idle,  tensor cores busy, CUDA cores idle
```

流水线把迭代重叠起来，让所有单元同时运转：

> 图 6：未流水线 vs. 流水线执行——重叠迭代让所有硬件单元保持活跃。

> 图 7：GPU SM 结构图——TMA、Tensor Core、CUDA core 作为独立状态机运行。

关键的架构事实是：TMA、Tensor Core 的 MMA 单元和 CUDA core 是**彼此独立的硬件状态机，相互之间没有任何隐式顺序**。

**TMA（SM90、SM100 可用）**是一台自主的 DMA 引擎。发出 `tma_load` 后它就独立运行，不消耗任何 warp 周期。完成通过 `mbarrier` 对象通知：那是带相位 bit 和预期字节计数器的硬件屏障。消费者在匹配的相位上调用 `mbar_wait()`。

**WGMMA（SM90 可用）和 UMMA（SM100 可用）**是异步 MMA 单元。你用 `commit_group()` / `wait_group(N)` 派发异步 matmul 并跟踪完成。在 Blackwell 上，UMMA 把结果写进 TMEM——一个 Tensor Core 私有的、类寄存器空间，CUDA core 不能直接访问。在 Hopper 上，WGMMA 写入寄存器。两代的调度问题相同（异步派发、显式完成跟踪），但 SM100 多了第三个需要协调的存储空间。

单元之间的每条依赖都必须手工同步，否则就引入一个静默的数据竞争。可以想象，这种协调有多难。

### 流水线有两个层次：warp 之间与 warp 之内

要提升内层循环性能，就得重叠迭代。但 FA3 内核其实在单一循环体里统一了两个层次的重叠：

> 图 8：两个层次的流水线——warp group 之间（producer/consumer）与 warp group 之内（Tensor Core/CUDA core 重叠）。

**层次 1：warp group 之间。**一个专职 *producer* warp group 跑 TMA 加载，另一个 *consumer* warp group 跑其余一切。两组通过带 `mbarrier` 同步的共享内存环形缓冲区通信。K、V tile 做 n 缓冲（n 个物理槽位），producer 可以提前加载，consumer 同时从另一个槽位读取。

在依赖图中，这一层由距离 d=n（距离=缓冲深度）的写后读边编码。`wgmma_qk` →d=n→ `tma_load_K` 这条边表示：第 k 次迭代的读者必须在第 k+n 次迭代的写者覆写同一槽位（k mod n = (k+n) mod n）之前读完。手工等价物是读完后的 `mbar_arrive(empty[slot])` 和写入前的 `mbar_wait(empty[slot])`。这一对屏障调用就是图上的一条边。改变缓冲深度只是改变 d。

**层次 2：warp group 之内。**在 consumer warp group 内部，Tensor Core 操作与 CUDA core 操作相互重叠。`wgmma_qk` 异步发射，运行期间 CUDA core 处理*上一次*迭代的 `rowmax`/`softmax`/`rescale`。这通过 `commit_group()` / `wait_group(N)` 管理。

在依赖图中，这一层由 S、P、m、O 上 11 条 d=0 和 d=1 的写后读边编码。求解器给出的 stage 分配直接决定了每个 `commit_group()` 和 `wait_group(N)` 该放在哪里。

### **为什么流水线化的 GPU 内核难调试**

听起来很好写 🙂？流水线解决了利用率问题，却制造了新问题：得到的代码极其复杂，难调试，也难适配和复用。

> 图 9：流水线样板代码的冰山——算法逻辑只占内核代码的一小部分。

FA3（[`flash_attn/hopper/mainloop_fwd_sm90_tma_gmma_ws.hpp`](https://github.com/Dao-AILab/flash-attention/blob/6362bd3bcad059aa15fd993c6a9d5d1ee8a11418/hopper/mainloop_fwd_sm90_tma_gmma_ws.hpp) + [`hopper/flash_fwd_kernel_sm90.h`](https://github.com/Dao-AILab/flash-attention/blob/6362bd3bcad059aa15fd993c6a9d5d1ee8a11418/hopper/flash_fwd_kernel_sm90.h)）有 1717+458=2175 行。FA4（[`flash_attn/cute/flash_fwd_sm100.py`](https://github.com/Dao-AILab/flash-attention/blob/6362bd3bcad059aa15fd993c6a9d5d1ee8a11418/flash_attn/cute/flash_fwd_sm100.py)）有 2,875 行。算法本身（在线 softmax、掩码、输出累加）只占其中一小部分。其余全是派发特化、硬件特定的内存布局，以及贯穿始终的流水线同步。而且算法与同步之间是紧耦合的：

- **环形缓冲区索引。**K、V tile 共享一个循环缓冲区，共享内存里有 n 个物理槽位（i mod n）。
- **屏障管理。**`mbar_expect_bytes()`、`mbar_wait()`、`mbar_arrive()`，还要跟踪相位 bit。
- **异步组跟踪。**`commit_group()` 和 `wait_group(N)` 管理在途的 WGMMA/UMMA 操作，参数 N 取决于*调度*。
- **Prologue 与 epilogue。**稳态循环体假设流水线是满的，头几次和尾几次迭代需要手写特例。
- **跨存储空间搬运。**FA4 中 TMEM 是 Tensor Core 私有的；前面说过，TMEM 与寄存器之间的数据搬运需要显式同步传输。

以上每一条都由调度推导而来，每一条上一个小小的笔误就能造出竞争条件。结果是，这类流水线极难编写。

**但工具不是已经存在了吗？**

**NVIDIA 的 **[**compute-sanitizer**](https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/index.html)** 确实能抓一大类错误，但它不跟踪 TMA 或异步 WGMMA/UMMA 指令。**比如跑 `compute-sanitizer --tool racecheck`，TMA 竞争什么都不会报。所以在 sanitizer 这条路上你无能为力。

你说那就 printf？问题是 bug 非确定性、依赖时序、输入规模、硬件配置，printf 观察并不奏效。加一个 printf 就可能把时序改动到足以掩盖竞争。甚至一次毫不相关的重构（改个 tile 大小、换个循环顺序）都可能让隐藏的竞争浮出水面。

**维护负担：**加一个操作就意味着重新推导调度、更新每个 `wait_group`、调整 prologue 和 epilogue。从 SM90 移植到 SM100 意味着推倒重写。FA4 与 FA3 实现的是同一个算法，却几乎不共享任何同步代码。

### Flash Attention 4：问题更严重

以上还只是 8 个操作、3 个单元的 FA3。FA4 让问题显著升级——它在 Datacenter Blackwell 上让两个 Q tile 同时对同一条 KV 流做处理。内层循环膨胀到 5 个功能单元上的 14 个操作：

python

```
alloc Q0_shared, Q1_shared, K_shared, V_shared : shared
alloc m0, row_sum0, m1, row_sum1 : reg
alloc S0, P0, O0, S1, P1, O1 : tmem

for k in range(N):
    async K = tma_load_K(K, k)             # @load  tma
    async V = tma_load_V(V, k)             # @load  tma
    async S0 = umma_qk(Q0, K)              # @mma   tc
    async S1 = umma_qk(Q1, K)              # @mma   tc
    sync  (m0, old_m0) = rowmax(S0, m0)    # @s0    cuda
    sync  (m1, old_m1) = rowmax(S1, m1)    # @s1    cuda
    sync  P0 = softmax(S0, m0)             # @s0    cuda
    sync  P1 = softmax(S1, m1)             # @s1    cuda
    sync  row_sum0 = rowsum(row_sum0, P0)  # @s0    cuda
    sync  row_sum1 = rowsum(row_sum1, P1)  # @s1    cuda
    sync  O0 = rescale(O0, old_m0, m0)     # @corr  cuda
    sync  O1 = rescale(O1, old_m1, m1)     # @corr  cuda
    async O0 = umma_pv(O0, P0, V)          # @mma   tc
    async O1 = umma_pv(O1, P1, V)          # @mma   tc
```

- **5 个内层循环角色**（共 512 线程、16 个 warp）：`@load`（warp 13，TMA）、`@mma`（warp 12，UMMA）、`@s0`（warps 0-3，CUDA）、`@s1`（warps 4-7，CUDA）、`@corr`（warps 8-11，CUDA）。其余 warp 只负责释放寄存器。
- **3 个存储空间**：共享内存（K、V tile）、TMEM（S、P、O，Tensor Core 私有）、寄存器（m、old_m、row_sum）。
- **28 条依赖边**：18 条同迭代、6 条循环携带（d=1）、4 条写后读（d=4，对应四缓冲共享内存）。
- **平行的 Q0/Q1 通道**共享 K、V 加载，但统计量与累加器各自独立。
- **相邻组融合**：在每个统计 warp group 内，rowmax → softmax → rowsum 作为对单个 tile 不可分割的序列执行。

## NVIDIA 之外的 GPU 流水线：AMD 与其他平台

而且这不是 NVIDIA 独有的问题。这个模式在所有硬件上都是通用的：

[异步生产者 + 异步消费者 + 共享缓冲区 = 流水线问题。](https://www.modular.com/blog/structured-mojo-kernels-part-1-peak-performance-half-the-code)

| 平台 | 异步拷贝 | 矩阵单元 | 同步机制 |
| --- | --- | --- | --- |
| NVIDIA Hopper / Blackwell | TMA | WGMMA / UMMA | mbarrier、commit/wait |
| AMD CDNA / RDNA | 异步拷贝引擎 | MFMA | LDS 屏障 |

只要一个内核的内层循环能分解为可独立调度单元上的操作，它就面临同样的调度与同步挑战。

## 下一步：用约束规划求解调度

现在我们已经细了解了 attention，也体会了流水线编程的复杂。第 2 篇将给出解法。我们把问题形式化为软件流水线问题：表示循环体内所有依赖（FA3：8 个操作、13 条边）。然后用模调度（modulo scheduling）约束搜索空间：每个迭代都用同一份调度、只是平移 T 个周期。这便把问题转化为一个整数线性规划，可在毫秒内求解。

拿到调度后，我们推导缓冲区生命周期与拷贝次数，确定每个共享内存 tile 需要几个物理槽位；再利用变量活跃性（liveness）压缩寄存器用量。
