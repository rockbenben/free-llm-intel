# Poolside on Dell：在您的边界内实现前沿人工智能的有效途径

大多数企业级 AI 的讨论仍然始于一个云端假设：模型住在别处，数据去往模型，工作通过 API 完成。这一默认设置把许多组织推向了它们本不必面对的取舍：在能力与控制、速度与安全、实验与治理之间做选择——同时创造出一种让 AI 的经济性随 token 消耗线性增长的成本结构。

运行在 Dell 上的 Poolside 为客户提供另一条路径：在自己边界内运行的前沿 AI，企业可以在更靠近自身数据的位置安全地生成 token，获得更好的性能、更强的治理和更可预测的经济性。它构建在 Dell 的企业级基础设施之上，底下是 NVIDIA 的加速计算平台、网络和 AI 软件，上面是 Poolside 的安全 agent 平台。

对于高度受监管的团队，这很重要，因为它们的要求往往没有商量余地。国防、情报、金融服务、医疗和关键基础设施组织所处的环境里，敏感代码和数据不能脱离客户的掌控。气隙网络、STIG 加固镜像、获批硬件清单、已有的 ATO 边界、成型的采购路径，这些都不是边缘情况，它们就是运营模式本身。

但本地部署的理由比监管指令宽泛得多。agentic AI 可能消耗好几个数量级的 token，而且它不是一份干净、可预测的 API 负载。随着采用规模扩大，agent 运行得更久、走更多步骤、调用更多工具，有时在产出有用结果之前已经做了大量工作。在按量计费的模型下，这种 token 的不确定性会直接变成成本的不确定性。

有了本地部署，组织可以围绕已知的基础设施成本做规划，通过更高的利用率改善 token 经济性，并在自己的运营模式内部治理可用性，而不必依赖共享容量、上游限流或某家厂商的发布排期。团队不必把每一次用量上升都当成新的预算风险，而是可以专注于让 agent 在创造价值的位置上干活。

访问与审计遵循同样的逻辑。身份经由既有的身份提供商流转。轨迹日志落在现有的安全工具里，包括 SIEM。数据留存遵循组织既有的策略。整个部署没有任何一环处在安全团队世界模型之外，因为没有任何一环被要求如此。贯穿其中的主线是控制。对于运行关键负载的组织，AI 必须运行在它们已经信任的高效基础设施、安全边界和运营模式之内。这不是配置上的偏好，而是能否使用 AI 的先决条件。

大多数 AI 工具仍然假设相反的前提：团队可以把工作发到某个云服务，围绕某家厂商去调整自己的控制，或者接受对 agent 如何运作的有限可见性。

正是这道差距决定了我们以这样的方式构建 Poolside，也决定了我们与 Dell 的合作为何重要。

## 最难的部署教会我们的事

差不多两年前，有人问 Poolside 能否把前沿 AI 带进大多数厂商从未触及的环境：气隙、STIG 加固、涉密、主权。在不到九个月里，Poolside 从原型走到了全球最安全的环境之一内部、拿到 ATO 批准的生产部署。我们认识到，这类部署没有统一的模板；但我们也证明了，路径是存在的。

那部分工作塑造了我们对技术栈每一层的思考方式。Ubuntu 和 RHEL 按 DISA STIG 加固。RKE2 跑在涉密 Kubernetes 基线上。完全气隙运行，没有任何出站调用。身份、加密 secrets、对象存储和本地容器镜像仓库全部打包在边界之内。凭据在运行时注入，并自动从输出、日志和 agent 轨迹中脱敏。每一个 agent 动作都被记录成可检索的轨迹，可导出到组织的 SIEM。这些没有一样是事后补装的，它们是我们出发的地基，因为我们为之构建的那些团队把安全当作先决条件，而不是一个功能。

此后我们一直在更难的问题上推进。我们的推理层是 vLLM 的自研变体，在客户实际运行的负载上比上游快得多，而且这个差距还在持续拉大。结果是单个节点在 SLA 之内能服务更多开发者，并且我们每交付一个版本，计算足迹都更高效。在这套足迹的最小一端，我们在 Dell Pro Max GB10 或 [NVIDIA DGX Spark](https://www.nvidia.com/en-us/products/workstations/dgx-spark/) 这类边缘级硬件上运行我们的 Laguna XS 模型，早期结果很有力，针对的正是单开发者和小型团队的用例——这些场景此前没有合适又负担得起的本地方案。

这条轨迹是一以贯之的：越来越多的 AI 技术栈正在离开远端云服务，进入客户自己掌控的基础设施，从安全的数据中心到更小的本地部署足迹。

## Poolside on Dell

在 Dell 硬件上，Poolside 以交钥匙系统的形式交付，有两种配置。合适的路径取决于客户已经拥有什么样的基础设施，以及他们希望我们带来多少。

**单节点 RKE2，完全自包含。
**运行 Poolside 所需的一切都随交付包一起提供：跑在 STIG 加固 Ubuntu 上的 RKE2 Kubernetes 集群、PostgreSQL、承担 S3 兼容对象存储的 SeaweedFS、承担身份的 Keycloak、cert-manager、NVIDIA GPU operator、本地容器镜像仓库、推理栈，以及 Poolside Console。客户提供硬件。没有外部依赖，没有出站网络要求。大多数国防、情报和涉密客户走的是这条路，因为它能干净地落进已有的 ATO 边界之内。

**用 Helm 装在客户的 Kubernetes 上，灵活。
**对于运行自己 Kubernetes 平台的企业客户——无论是上游发行版、Red Hat OpenShift 还是托管的同类产品——由客户提供周边基础设施：容器镜像仓库、身份提供商、PostgreSQL、证书管理、ingress、storage class 以及 GPU operator。

Poolside 通过 Helm 安装在它们之上。同一个平台，同一个 Console，同一套审计模型。变化的只是我们带来的部分与客户已经就位的部分之间的那道接缝。

对于要把 Poolside 服务给数千名开发者的组织，我们也支持在 Dell 硬件上做多节点集群。多个企业机架节点作为一个 Poolside 集群运行，推理与平台服务分布在它们之间，同时向每一位用户呈现同一个 Console 和同一套审计模型。当单节点足迹无法覆盖全部用户群体、但部署又必须留在客户边界之内时，大型企业和联邦项目办公室走的就是这条路。

## 推出面向 Dell AI Factory 的 Poolside Blueprint

Dell 客户现在有了一条从采购订单到跑起来的部署之间更可复制的路径。

面向 [Dell AI Factory with NVIDIA](https://www.dell.com/en-us/dt/corporate/newsroom/announcements/detailpage.press-releases~usa~2026~03~dell-ai-factory-with-nvidia-delivers-proven-path-to-enterprise-ai-roi.htm) 的 Poolside Blueprint 是一套经过 Dell 验证的部署自动化，收录在 [Dell Automation Platform](https://www.dell.com/en-us/lp/dt/automation-platform) 目录里。它把 Poolside 的安装包进 Dell 标准的编排、生命周期和验证工作流之中。一个预检校验器会在安装继续之前确认客户的硬件与周边基础设施符合该平台的要求。随后 Blueprint 按照 Dell 客户在其他 Dell AI Factory 解决方案上已经在用的同一套自动化模式，在其之上部署 Poolside。

对于通过 [Dell AI Factory with NVIDIA](https://www.dell.com/en-us/dt/corporate/newsroom/announcements/detailpage.press-releases~usa~2026~03~dell-ai-factory-with-nvidia-delivers-proven-path-to-enterprise-ai-roi.htm) 采购的客户，这带来了一条从硬件交付到运行中、受治理的 Poolside 环境的更可复制路径。Dell 带来企业级基础设施和部署自动化。NVIDIA 带来加速计算、网络和 AI 软件。Poolside 带来运行在其上的安全 agent 平台。合在一起，这给了客户一条从采购订单到生产部署更清晰的路线：安装前的未知项更少，途中的定制集成工作也更少。

## 从客户现状出发

高效部署只是通往生产的一半，另一半是采购。

公共部门和受监管的企业买家，通常通过既有的合同载体、OEM 协议以及经销商关系来采用新技术，而这些他们的采购与安全团队早已熟悉。对于已经在大规模采购 Dell 基础设施的客户，Poolside on Dell AI Factory with NVIDIA 给了他们一条更熟悉的采用路线：它能与既有的采购动作对齐，而不必把每一次部署都强行塞进一条全新的厂商路径。这对客户团队很重要，因为采用安全 AI 的障碍很少只在技术层面，它同样在运营、商业和流程层面。从已获批的基础设施到受治理的部署这条路越顺，客户就能越快从评估走到真正的使用。

## 多条路径中的一条

Dell 硬件是 Poolside Platform 四条部署路径之一。客户也可以在自己的裸金属上部署 Poolside，在 AWS、Azure 或 Google Cloud 上已有的 VPC 内部署，或者通过 Helm 部署在客户自备的 NVIDIA AI 基础设施上。同样的基础模型、同样的 Console、同样的 agent 编排、同样的审计轨迹，在所有这些路径上都是一致的。

这之所以重要，是因为这段旅程很少在同一处开始并在同一处结束。一个组织可能从安全机房里的一台塔式服务器起步，随着用户规模增长扩展到企业机架，再为一项相邻的、敏感度较低的工作接入某个区域的 VPC——全程都不需要更换底层平台。Poolside Platform 从一开始就是为这一点而设计的。

对这些组织而言，本地的前沿 AI 就应该是这个样子。
