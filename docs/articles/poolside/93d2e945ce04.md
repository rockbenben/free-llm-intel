# 设计世界一流的代码执行环境

**TL;DR: ** 我们详细介绍 Poolside 的代码执行环境。我们先描述如何把仓库从外部世界拉进 Saucer，也就是我们的修订版本服务系统。然后讨论我们把仓库自动转换成镜像的做法，包括我们为这项任务使用 AI agent。我们还会讨论如何用层高效地表示多个修订版本，以及如何大规模地服务代码执行请求。

## 引言

在 Model Factory 系列的三篇 [  往期帖子](https://poolside.ai/blog/titan-the-model-factory-s-furnace)中，我们谈了从数据摄取到预训练的一切。现在我们既有数据，也有了一个预训练模型，就可以开始思考如何让模型专门服务于以编码为中心的任务。

在 Poolside，我们实现编码专属性（coding specificity）的关键方式之一，就是让模型从代码执行反馈中学习，这被称为 Reinforcement Learning via Code Execution Feedback（RLCEF）。自 2023 年我们创立 Poolside 以来，RLCEF 一直是我们最关键的创新之一，我们为这条路线投入巨大。事实上，我们持续在这一领域开拓新的改进，并且我们坚信，使用 RLCEF 能让我们突破当前预训练数据的局限（关于这一点更多内容，见 [  我们的研究声明](https://poolside.ai/vision/research)）。

不过，要更详细地解释 RLCEF，我们得先说明我们究竟是怎么为模型产出代码执行反馈的。

在这篇帖子里，我们给出代码执行环境的细节。我们先讨论为什么必须把仓库构建进容器，以及这一步究竟给了我们什么。

然后我们描述把仓库从外部世界拉进我们自研的修订版本服务系统（名为 Saucer）的过程。接着我们详谈如何把仓库构建成镜像，包括对难以构建的仓库使用 AI agent。我们还会讨论如何用镜像层高效地处理仓库的修订版本，以及如何大规模地服务代码执行请求。

## 从万米高空俯瞰我们的代码执行平台

在进入代码执行平台的细节之前，值得先从更宏观的视角看一下整个系统是怎么运转的。确实，站在这个视角能帮我们理解：为什么我们在代码执行平台上做了某些设计选择，这些决策又是如何帮我们在模型训练期间达成目标的。

先回顾一下，RLCEF 背后的高层目标，是让模型通过从代码执行反馈中学习来学会编码。直观地说，我们就是想让模型像人类学写代码那样学写代码——不只是读别人的代码，而是从写程序、跑测试、检查编译错误以及其他软件开发工作流中确定性地学习。更进一步，我们希望模型能带着「针对某个特定仓库解决一个任务」这个目标去编写并执行代码，就像软件工程师在现实世界里所做的那样。这就给我们勾勒出下面这幅关于需求的高层图景：

即便有了这些高层目标，我们还有一些运维层面的顾虑。一方面，我们都知道冗长的反馈周期会拖慢软件开发；从执行反馈训练模型同样如此。这意味着我们要主动避开任何会拖慢「模型从代码执行反馈中学习」这件事速度的东西；执行代码要等很久是绝对不行的。另一方面，模型必须在一个安全、隔离的环境里执行代码；我们要确保模型不会带出任何连带影响，也要确保模型只基于它真正看到的东西来学习。但要求还不止这些：我们得能真正执行某个特定仓库里的代码。这包括知道怎么执行某个仓库的测试套件，以及怎么计算该仓库的测试覆盖率。此外，理想情况下我们还要为调用仓库中的代码提供一个狭窄的操作面：我们不想让模型去承担「代码究竟是怎么被执行的」这些细节的负担，只想让它从执行代码所带来的反馈中学习。而这一切同样需要在一个安全且隔离的环境里发生。

实际来说，我们不想让某个代码执行任务的实例去干扰别的实例，或者干扰代码执行服务的其余部分。再往前一步，我们也不希望把自己限制在某个特定的仓库修订版本上：我们还希望在修订版本之间切换，同时不过度加重我们仓库存储系统的负担。

我们先来解决第一批需求。真正独立自成一体的软件项目少之又少。事实上，大多数软件项目都有这样或那样的依赖，或者有环境要求，只有满足之后项目才真正能部署。换句话说，对每一个我们想用于 RLCEF 的仓库，我们都要提供一个可复现的环境。为此，我们为每个想用的仓库构建一个镜像。这篇帖子后面会进一步深入这一点，但现在我们可以把一个镜像理解为某个特定软件项目的完整执行环境。需要指出，一个镜像装着某个项目的全部依赖，从而实现轻松、无需改动的执行。我们也想说明，用镜像来执行代码还有别的好处，比如精简的存储和容易的版本管理。

鉴于我们的代码执行环境里有几十万个仓库，我们需要一套完全自动化的方式，为任意仓库构建镜像。此外，我们还必须能对几乎任意一个仓库修订版本自动构建镜像。这就引出下面这幅图景：

如前所述，我们要能为代码执行管线上任意仓库的几乎任意修订版本构建镜像。目前我们已经索引了超过 80 万个仓库，因此处理这些修订版本绝非易事。这要求我们谨慎地从外部世界摄取仓库，并高效地存储所有构建出来的镜像。我们分两步来做。第一步，我们把仓库拉入一个内部服务——并从这个服务对外提供仓库——它名为 Saucer。需要指出，Saucer 的设计目标是跨多个物理节点提供高吞吐的服务。用 Saucer 让我们得以避开第三方服务的限流，也让我们对自己所服务的仓库有更多掌控。然后我们从 Saucer 读取目标仓库并构建对应的镜像，于是得到下面这条工作流：

## Saucer

正如我们所说，Model Factory 里有一个仓库托管服务，名为 Saucer。从高层看，Saucer 让我们能高效地读取代码执行环境中某个仓库在任意修订版本下的任意文件。尽管这篇帖子的重点是构建整个仓库，但我们要强调：能拉取任意特定修订版本下的任意文件，这件事本身对模型训练就极有用。

Saucer 的主要目的，是把已经摄取的仓库高效地服务给下游。为此，Saucer 提供两个 gRPC 端点供应用调用。其中第一个是一个简单的服务，从仓库的某个特定修订版本取文件；Saucer 提供的另一个服务，则让一个 Saucer 部署从外部世界摄取一个新仓库。

摄取是这样工作的。我们先把希望摄取的仓库位置推到一个 Kafka topic 上。需要指出，我们在这个任务上用 Kafka，是因为它让我们能轻松地从零重建 Saucer——只要把整个 topic 重新读一遍，我们就能复现所有的摄取动作。一旦仓库位置被追加到 Kafka topic，Saucer 就会自动感知到有新任务可用并开始摄取。往 Kafka 推送这件事多少是手动的，但这是有意为之。实际上的原因是，摄取仓库会引发下游变化——尤其对正在使用 Saucer 的模型而言——所以我们在这一点上格外小心。话虽如此，手动触发一次 Saucer 摄取也算不上困难，典型的摄取排程只需几分钟。底层方面，我们所有的 Kafka 部署都由 Redpanda 驱动，那是一个很出色的 Kafka 兼容系统，为我们的工作和负载提供了顶尖的性能。

摄取一旦被触发，Saucer 就会尝试下载这个仓库。和任何分布式系统一样，这个任务会因为各种各样的原因失败。实践中我们遵循两阶段的下载流程：先尝试用并行化的 runner 下载仓库，一旦失败就退回到单个、非并行的 worker。如果单个 worker 也失败了，我们就把错误记录下来并跳过这个仓库的下载（也就是不会反复重试这次下载）。

仓库下载完成后，Saucer 会把它重新打包成一种下载友好的格式。直观上，我们从 Saucer 读取的次数远多于写入，所以我们会格外用心地把仓库打包成读取友好的格式。就 Git 仓库来说，我们用一个 Git packfile 外加一个 index 文件来打包仓库，从而可以轻松访问仓库里的任意文件。同样，这一步也需要小心，因为复现性上有许多坑。比方说，Git packfile 并不是确定性地打包文件，于是同一次摄取的两次不同运行会得到不同的 packfile。假如我们独立于 index 文件去重新生成 packfile，这种非确定性之后就会带来问题。所有这些细节加起来，就成了一个相当复杂的系统，而我们一路把它演化至今。

说到底，Saucer 是 Model Factory 里一个很有用的服务。除了让我们能轻松地扩展实验——毕竟整条管线都在我们掌控之中——我们还可以用 Saucer 把详细的文件信息提供给其他下游服务，比如某些后训练管线。事实上，我们甚至可以部署一个 Saucer 服务器，允许模型去改写某个特定仓库的历史，从而让我们能教会模型处理更复杂的任务。

## 构建镜像

既然目标仓库已经进了 Saucer，我们就来谈怎么真正从仓库走到镜像。从高层看，我们理想中的工作流大致是这样的：

首先，从第一性原理出发推一推：我们要怎么才能构建一个任意的软件项目。具体一点，设想我们决定在某个特定修订版本上构建一个没有文档的仓库。我们实际会怎么做？

那么，我们能从要构建的仓库里拿到一些上下文线索。例如，一个 Rust 仓库几乎肯定依赖 Cargo 来构建，因此我们只需要用仓库的 manifest 来构建这个仓库。我们不需要读任何构建说明就能推断出该这么做——我们全部的推断都来自项目结构和别的上下文线索。现实里还有别的这类例子。例如，Go 项目通常也是通过一个标准化的构建系统来构建的，Python 项目同样会用 pyproject.toml 文件包装起来。因此，我们通常可以——尽管是启发式地——依据上下文线索推断出某些项目该怎么构建。把这一步加进我们的工作流程，我们就得到了这样一个工作流：

从某种意义上说，有标准化构建系统的语言提供的是「容易」的情形，因为规则只有几条。但情况并不总是这样：在多个操作系统上，C 和 C++ 项目在现实中有许多种构建系统。所以我们需要找到一种办法，基于我们发现的系统来定义构建规则，而不是基于语言本身。即便如此，这仍可能以各种各样的方式失败。我们可能遇到某个项目就是用一套已知规则构建不出来的，也可能没能覆盖某个特定构建系统提供的全部行为。在这些情况下，我们最初的启发式这一步就可能失败。为了应对这一点，我们会记录某个项目失败的原因——要么按构建系统类型，要么按缺失的规则——并把结果推到一个 Grafana 看板上。这很有用，因为它让我们之后能深挖这次失败为什么发生、下一次该怎么解决。我们还必须留意多个构建系统同时存在这个事实：比方说，有些仓库会同时包含 Makefile 和一个 CMakeLists.txt 文件。基于前者构建多半行不通，但基于后者重新生成 Makefile 多半能成。

话虽如此，知道一个项目该怎么构建，并不意味着我们真能把这个项目构建出来。回到前面那个 C++ 的例子，如果某些构建依赖没有在某个地方以程序可读的方式被正确指定，我们就可能漏掉它们。如果依赖其实是以人类可读的形式写着的，比如说写在 README 里，却没写进构建脚本，这种情况就会发生。同样，我们会把这些错误记录到 Grafana，一旦有问题就转到另一个项目。

一旦搞清了项目的构建方式，我们还需要运行项目的测试套件。这主要是为了让下游任务能进行：如果测试套件一开始就跑不过，我们很难判断我们的 RL 代码效果有多好。同样，我们得知道实际该怎么跑测试套件，而这也随语言不同而不同。我们用静态规则来跟踪这一点，方式与我们处理构建的方式类似，这非常有用。类似地，在没能跑起那些测试的情况下，我们也会跟踪测试套件里的错误并推到 Grafana。我们还允许构建方请求本次执行的测试覆盖率：直观上，这也是为了让下游任务能正常工作。如果我们不这么做，那些以改进测试覆盖率为目标的任务就会因为种种原因无从下手。

最后，我们现在终于可以把产出的镜像推入一个 OCI 镜像仓库。出于可扩展性的考虑，我们自己运营一个 OCI 镜像仓库实例，底层存储由一个简单的 S3 bucket 提供。这样的配置让我们能用上通常在一个常规 OCI 配置里做不到的优化。例如，我们不是直接从镜像仓库读取镜像，而是有一项优化允许我们直接从 S3 读取镜像层。这项特定优化的好处是让我们更容易地并发处理镜像请求，并且给了我们更少的故障点。需要指出，这些优化并不会给「往 OCI 镜像仓库添加新镜像」增加复杂度，而且这一步所幸比前面的步骤直白得多。我们这里不过多展开细节，但要点是这一步依然可能失败——毕竟这是一次跨网络的操作——所以我们也同样盯着这里的错误。

这整套流程并非万无一失，甚至离「人会怎么做」还差得远。举例来说，上面描述的系统完全没有去研读 README 文件的能力：所有推断都是基于仓库里的文件、以启发式的方式完成的。而且，尽管上面描述的系统会尝试一次「最佳情况」下的构建，它并不怎么健壮：我们只是拿规则去和要构建的那个仓库做匹配。这和一个人的做法很不一样。比如，一位有经验的软件工程师会先试着读说明（如果有的话），尝试构建项目，然后针对任何失败不断迭代，直到项目构建成功。遗憾的是，我们的静态规则没能完美地模仿这套做法，我们这套基于静态规则的系统在遇到错误时直接放弃。

为了绕开这个问题，我们现在用一个我们自己训练出来的、用于构建项目的 agent 来补强构建系统。与我们的静态规则不同，这个 agent 能够理解 README、调用外部工具来获取额外上下文，并在先前的构建失败上继续迭代。用这个 agent 来构建镜像带来了相当大的提升，尤其是在那些依赖复杂的 C++ 项目上。对我们来说，这是一个格外令人振奋的进展；毕竟，**我们现在有了一个在 Factory 里训练出来的 agent，正在反过来改进 Factory。**

## 处理修订版本

既然我们现在已经能从仓库构建出镜像了，就可以把注意力转向我们如何处理修订版本。先回顾一下：版本控制系统里的一个仓库由若干修订版本（也就是 commit）组成，每个 commit 代表仓库在某一时刻的状态。

不同的版本控制系统处理 commit 的方式也不同。例如，Git 版本控制系统会为每个修订版本存一个树对象，记录仓库的完整状态。一个 commit 对象引用某个特定的树对象。因为每个修订版本都有对应的树对象，我们可以通过计算两个树对象之间的差，来算出两个 commit 之间的差异——也就是 diff。

我们对镜像采用类似的做法。要讲清这个想法，得先讲 OCI 规范是如何定义镜像的。简单说，镜像被定义为一组「层」加上一些相关的元数据。在这个语境里，层就是按某种特定方式存放的一组文件。需要指出，每个镜像所关联的文件系统，就是构成这个镜像的那些层的并集。从这个角度看，层可以被看成文件系统的一部分，我们把它叠加在已经解开的文件系统部分之上。事实证明这是一个非常有用的抽象。例如，我们可以把一个操作系统定义成基础层，然后把任何某个镜像特有的改动作为新的一层叠加在上面。

如果把这两个系统——版本控制的修订版本和层——稍微眯眼看一看，就会发现它们非常相似。首先，我们知道版本控制的修订版本通常表示为相邻 commit 之间的 diff。另一方面，层是一层叠一层地顺序应用，从而构建出一个镜像的文件系统。于是有了下面这个洞见：我们可以干脆把 commit 之间的 diff 表示成我们镜像里的另一个层。诚然，这个洞见过分简化了；例如操作系统级的依赖会在一个项目的各个仓库修订版本之间有所不同，其他构建产物也一样。为了简洁，我们略去如何处理这些额外细节的具体做法，但高层上我们先尝试构建仓库的某一个修订版本，然后把得到的镜像用作后续修订版本的基础镜像。这套做法的最终结果是：每个修订版本新增的镜像层只包含发生改动的文件，以及依赖和构建产物上的增量，于是每个修订版本对应的 OCI 镜像层都相对较薄。

现在我们把注意力转向这个想法究竟是怎么实现的。首先，镜像里的层通常是借助 Linux 的 OverlayFS 文件系统来解开的。与上面描述的做法类似，OverlayFS 把几个挂载点解开，组合成文件系统中单一的一个挂载点。引人注目的是，这正是我们处理多个修订版本所需要的全部：我们只把 diff 映射到不同的挂载点，其余交给 OverlayFS 处理。不过要说明，我们在 OverlayFS 之上还实现了各种额外的优化。例如，我们不会为每一种可能的改动都新建一层，因为有些改动（比如元数据改动）意义不足以撑起一整个新层。我们的镜像构建系统替我们处理了所有这些底层优化，让我们能为仓库产出紧凑的镜像。

把修订版本当作层来处理，给我们带来了不少有用的好处。具体来说，我们得以避开处理修订版本所需的平方级存储要求：我们可以只存一个带层的镜像，而不必为每个修订版本各存一个不同的镜像。而且，取用某个特定镜像依然很快，因为我们只需指定自己关心哪个 commit，剩下的交给我们的叠加系统处理。

最后简单提一句：针对镜像本身，我们有一套优化过的存储系统。直观上，一个镜像一旦构建出来，很可能被用到很多次，但某个特定镜像我们只构建一次。因此，我们没有使用普通的存储系统，而是用面向读取优化的格式和系统来存镜像。这种做法在实践中大幅缩短了我们部署镜像所花的时间。

## 处理执行

既然我们现在能构建镜像以及镜像的修订版本了，我们来细说代码执行服务究竟是怎么运营的。本节先不管执行过程中所有与模型相关的部分；相反，我们只专注代码执行本身实际上是如何推进的。

代码执行服务提供一个高层 API，允许用户开启会话。每个会话都绑定到我们镜像仓库里某个特定的 OCI 镜像，而每个镜像都如前几节所述构建而成。会话一旦开始，用户可以进行范围很广的操作。一方面，我们允许用户在镜像上运行底层操作，比如改动文件系统或执行任意命令。另一方面，用户也能执行层次高得多的任务，比如执行某个特定项目关联的全部测试，并以统一格式采集测试覆盖率。

到这里，我们一直用「用户」这个词来描述与代码执行服务的交互。在 Model Factory 里，「用户」通常是一个通过 RLCEF 学习的模型。因此，我们不能依赖临时起意的方式去和代码执行服务交互；相反，我们需要明确规定好的 API 来完成交互。

模型可以用两种方式与代码执行服务交互：通过代码执行服务直接提供的端点，或者通过我们 Task Engine 提供的抽象。第一种，模型可以直接与代码执行服务提供的端点交互；底层上，代码执行服务提供了一组 gRPC 端点，于是模型可以根据我们想要的结果，简单地与某个特定端点交互。虽然这是与代码执行交互最灵活的方式，但处理起来有些复杂：边界情况很多，而且我们最终发现，直接与这些端点交互容易写出杂乱无章的代码。为了绕开这一点，我们在 Task Engine 里实现了一系列端点抽象。需要指出，这些抽象覆盖了常见用例：例如，我们有一个用来运行容器内测试套件全部测试的抽象，还有另一个用来对容器内的源码跑 linter 的抽象。我们要强调，这个过程通常是迭代的，交互会跑很多轮。比方说，模型可以先写一些代码，然后跑 linter，再执行测试套件。事实上，我们甚至允许模型在收到前面步骤的结果之前就提交新请求，因为这样更贴合开发者通常遵循的模式。

我们注意到，这个方案里有很多细节需要照顾到。显然，在我们这个规模下，单台服务器对代码执行服务远远不够：同时在途的请求实在太多。这就立刻要求我们在代码执行框架里拉起多台服务器。不过，这也带来一个机会：既然我们很可能同时让同一个仓库的多个修订版本处于活跃状态，那么理想做法是把同一个镜像的所有活跃修订版本部署到同一台服务器上。从存储角度看这尤其有用，因为我们可以在 OverlayFS 上玩些巧妙的花活，减少暴露全部修订版本所需的存储量。但这个做法也有它的问题。我们现在需要小心地把指向同一仓库的请求路由到正确的服务器；同时还得注意，别让某台特定服务器被大量并发请求压垮。实践中这真会发生，因为某些仓库在模型训练期间是极好的试验场。诚然，这些问题相对好解决，但之所以能搭出一个健壮的代码执行服务，靠的正是我们能在 Model Factory 里快速迭代想法的能力。
