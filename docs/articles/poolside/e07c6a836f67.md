# 为模型工厂收集和加工原材料

## 深入解析模型工厂的数据管线

**TL;DR**：数据是基础模型训练的命脉。在这篇文章里，我们会深入讲解我们的数据处理管线与工作流，覆盖我们整条数据流程。具体而言，我们讨论数据管线每个环节背后的工程实现，包括数据摄取、合成数据生成、过滤、去重、混合与流式拉取。

## 引言

在我们[上一篇博文](https://poolside.ai/blog/introducing-the-model-factory)中，我们介绍了 Model Factory（模型工厂）——Poolside 用来大规模训练基础模型的内部系统框架。既然已经从高层理解了这座工厂如何运转，现在就可以讨论工厂的各个组成部分，以及它们如何彼此咬合。

在今天的这篇文章里，我们要深挖 Model Factory 中体量最大的部分之一：我们的数据管线。沿用工厂这个类比，数据管线就是在把原材料喂进训练机器之前，检验和加工运抵原材料的地方。它涵盖所有环节：从把原材料卸进工厂的仓库，到合成地制造新原料，到检验它们的质量，再到预处理，最后直到把它们打包成适合我们训练机器的形态。

我们开始吧。

## 数据摄取

在讨论数据处理之前，我们需要先说明我们把数据摄取进数据湖的方式。实践中，数据摄取是我们整条管线里最「临场定制」的一环，因为我们要处理各种各样的数据集，每个数据集都有自己的布局、文件格式和元数据。这些来源本身也高度多样，输入从结构化数据库到原始文件、再到网页抓取结果都有。为了应对这种复杂性，我们的数据摄取管线既高度灵活，又被设计成以固定形态产出数据资产。

摄取数据的第一步是找到合适的数据来源。一方面，确实有许多可用于训练的开源数据集，但我们常常发现这些数据集要么质量太低，要么根本无法为大规模训练提供足够的 token。此外，现有数据集中可能包含大量对我们目的毫无用处的内容，比如广告。因此，虽然我们确实会使用开源数据集，但我们也会从零开始构建自己的内部数据集，用来训练基础模型。例如针对代码数据，我们会部署专门的管线来挑选契合我们使用场景的数据（下面会更详细地讨论）。

现在我们把注意力转向摄取数据这个过程。复习一下：我们语料库中的每个数据集都表示为一张独立的 Apache Iceberg 表。

这些 Iceberg 表中的每一张都由一个 Dagster 资产产出。具体来说，我们先写一个定义 Iceberg 表的 Dagster 资产，然后触发一次摄取运行。出人意料的是，要做的就只有这些：Dagster 的 IO 引擎会替我们把剩下的工作干完。

值得讨论一下这个过程在实践中是怎么运作的。特别地，回想一下，Dagster 允许我们用 Python 装饰器以声明式的方式定义数据资产，而工作流的编排交给我们的 CI 管线处理。尤其重要的是，Dagster 资产允许我们定义资产是如何构造出来的，包括底层数据如何映射到一张 Iceberg 表。这些函数封装了每个来源特有的逻辑，把从连接建立到数据抽取的一切管了起来。把真正的拉取过程委托给这些专门的函数，让我们在管线中保住了模块化和清晰度，也就更容易扩展和维护。换句话说，这套做法覆盖了应对多样数据源所需的一切：我们只需为某个特定数据源定义一个转换，然后在资产定义里调用这个转换即可。

我们看一个例子。我们的 Dagster 资产大致长这样：

```
@table_asset(
    group_name=”nl”,
    partitions_def=...,
    …,
)
def example_asset(context, pyspark, ingests, …) -> DataFrame:
    …
    df = …
    return df.filter(...)
```

上面这个函数只是个桩（stub），而我们用来表示和拉取数据的具体函数，很大程度上取决于数据源自身的特征。例如，在处理来自 Hugging Face 的自然语言数据集时，我们常常碰到以 Parquet 文件存储的数据集。Parquet 文件在大规模存储和查询上非常高效，但要把它们整合进我们基于 Iceberg 的数据架构，就需要定义合适的元数据结构和转换逻辑。取决于我们的摄取配置，我们也许可以直接使用这些文件，也许需要定义如何把它们组织成适合下游工作流的样子。另一方面，并非所有数据都以这种包装整齐的形式抵达，有时我们要从更原始得多的来源摄取数据。这可能包括非结构化文件、原始日志，甚至是流式输入——它们需要先做预处理，才能被整合进我们的标准数据模型。处理这些情形需要自定义的抽取与转换逻辑，以确保数据契合我们的下游工作流；不过正如上面所见，这样做并不构成对我们开发的阻碍。

当然，也可能出现底层数据集质量不够的情况。事实上，我们经常遇到被错误解析、或被序列化成文本表示的数据集。为了绕开这个问题，我们会执行 OCR 来准确解析数据集。值得一提的是，我们把 OCR 能力作为 Model Factory 本身的一部分来部署，这让我们能用工厂里所有其他工具来考察这些 OCR 技术相对既有基线的效果。对我们来说，这种集成代表了一个令人兴奋的前沿：计算机视觉与自然语言处理在此交汇，用来增强数据集的构建。

代码数据集带来的是另一类挑战。虽然现实世界里确实存在代码数据集，但它们通常要么太小、要么质量太低，我们无法使用。而代码仓库通常只集中在互联网上的少数几个地方，而不是散布在整个互联网上。因此，尽管现有的代码数据集不能满足我们的使用场景，我们仍能通过周期性地把开源仓库（以及它们的许多修订版本）拉进我们的数据管线来处理这个问题。我们并不会把所有能拿到的开源仓库都拉进来；相反，我们只拉那些通过我们质量和许可检查的仓库。

把所有这些部分组合起来，我们就得到了数据摄取管线更完整的全貌：

在此值得提一句，我们的数据团队对数据质量近乎偏执，会花大量时间手工检视数据集以保证质量。这种把关至关重要，因为这些工作往往涉及细腻的取舍，无法靠简单的自动化或通用规则来解决。我们的数据团队在摄取过程中精心筛选数据，确保质量达到我们的用途要求。此外，我们的工程师和研究员会特别留心把与数据集关联的额外元数据一并摄取进来；这对我们的数据过滤步骤尤其有用。事实上，我们管线最有用的特性之一，是我们可以从零重跑整条流程（结果完全可复现），这让我们能够为已有数据集补充额外的元数据。

最后，我们摄取管线的强项之一是它能无缝扩展，这主要归功于我们把它建立在 Spark 之上的决定。Spark 的分布式计算能力确实让我们能够快速且可靠地处理海量数据。举例来说，在基线算力上我们每天大约能摄取 20 万亿 token。这一负载的表现，同时证明了我们架构的健壮性和工作流的高效性。

## 合成数据生成

虽然有海量网络数据可供训练，但就预训练数据而言，这些数据集只提供了拼图中的一块。从某种角度看，在网络数据上训练所带来的影响早已人尽皆知——毕竟所有基础模型提供商都这么做。但现有数据集在内容上通常非常偏斜，对某些任务甚至可能根本找不到规模足够的数据集。为了绕开这个问题，Poolside 大量使用合成数据生成技术，包括在预训练规模上使用。在非模块化的工作流里，采集这一量级的合成数据是件难事；然而，当我们把合成生成纳入 Model Factory 时，我们发现自己其实已经备齐了所有零件——只需要把它们组装起来。

在继续之前，值得指出的是，采集合成数据需要格外谨慎。毕竟，生成合成数据的原因之一，就是为了预训练产出某种特定类型的高质量数据。我们会对合成产出的数据施加适量的人工复核与过滤，从而避免使用有偏或低质的合成数据。我们想强调，对非合成数据集而言，这件事的难度是一样的。事实上，由于工厂里我们所有的数据管线都与具体数据集无关，我们能够以完全相同的方式对待合成数据集和任何其他数据集；而且我们会定期检视合成生成数据集的完整血缘。

现在来讨论我们如何生成合成数据。作为例子，我们讲讲如何从一批仓库生成代码执行数据集。具体来说，我们会取某些预先定义的测试，在指定输入上执行这些测试并记录输出，以此产出代码执行数据集。直觉上，这类数据集的目标是教会模型如何在静态语境下推理代码的执行。我们代码执行平台实际如何工作的细节，会在本系列的后续文章里讨论，所以眼下我们只谈生成这类数据的组织流程。

我们做的第一件事是把一个 worker 进程部署到某个特定节点上。这个部署需要一些考量。一方面，这类合成数据生成通常是低优先级任务，所以我们允许这些任务在节点上被抢占，把资源让给更紧迫的计算作业。另一方面，合成数据生成的负载可能以难以预测的方式变化，所以我们通常把这些任务部署成分布在负载均衡服务后面的多个副本上。这两个彼此冲突的需求，由工厂的编排器轻松调和，因为它对所有待处理作业及其相对优先级有全局视图。

worker 部署妥当之后，我们就要真正生成数据了。这里我们不深入太多细节，但在这个具体案例中，worker 只需拿一组预定义的输入调用我们的代码执行环境，然后收集输出即可。在其他一些场景里，我们可能采用 agent 化的设置，让 worker 在多次迭代中反复与代码执行环境交互。所有这些迭代结束后，我们把得到的数据输出到正在构建的那个数据集里。就自然语言任务而言，我们可能对一篇已有文档跑一个作业，比如改写作业。合成数据生成过程中我们所做的一切都是可调的，所有步骤都取决于数据集的底层目标。这些流程通常会产出大规模数据集，供我们的模型在训练或微调阶段学习。

到此为止的描述是刻意组织得听起来完全靠手工的，但事实上它是全自动的。确实，管线的每一个环节都由 Dagster 和我们的编排器协调——从处理一直到代码执行。实际上，我们通常只需要决定部署哪个 worker、想生成什么样的数据、以及作业的规模，剩下的交给工厂。这套自动化把生成合成数据的人工负担彻底摘掉了。**限制我们的只剩产出想法的速度，而不再是生成这些数据的手工工作量。**

现在我们把注意力转向这个过程在实践中如何落地。首先回想一下，我们所有的数据都以 Iceberg 表的形式存放在数据湖里。要为某个特定数据集创建一张 Iceberg 表，我们只需重复数据摄取时用的那套步骤：创建一个描述底层表的 Dagster 资产，然后用我们合成数据生成引擎产出的数据填充这张表。合成数据生成任务本身的触发方式与 Model Factory 里任何其他作业完全一样：我们只要指定底层作业的属性，剩下的交给 Dagster。

## 数据过滤

数据摄取完成之后，我们可以把注意力转向管线里的第一道精炼工序：数据过滤。顾名思义，数据过滤就是从已有数据集中移除数据样本的过程，最终目标是提升底层数据的质量。继续之前，我们想强调：数据处理与过滤本质上是一个迭代过程。也就是说，我们不是把某一套规则跑一遍就翻篇，而是对任何一个给定数据集都循环进行多轮分析、精炼与再评估。我们确实会不断施加过滤器并检视数据集，确保一切都符合我们的质量和分布目标。这本该是件耗时的事，但 Model Factory 让这个过程大幅提速。确实，Model Factory 让我们能够并行评估多种数据组合；更关键的是，它允许我们把每一个数据集变体追溯回它的原始来源。这让我们能追踪某些改动如何改变某个给定数据集的质量。

在继续之前，先谈谈我们希望靠过滤数据集达成什么。直觉上，我们追求的是提升模型所见数据的质量，因为这对下游模型表现有很强的影响。要做到这一点，我们既要优化每个单独文件的内容，也要优化数据集整体的分布。就前者而言，我们主要想确保输入文档的语言质量是好的：我们寻找高质量的写作、良好的结构和有信息量的内容。同样地，我们会明确移除任何检测到的仇恨、辱骂或粗俗内容。我们过滤策略的第二部分聚焦于提升数据集整体的质量，这里我们追求两个不同的目标。第一，我们要确保任何一个具体数据集在内容类别上具备足够的多样性。直觉上，这等同于移除某些数据集中可能存在的、无意的「类别性上采样」。举例来说，我们过去注意到常见可得的网络数据里广告泛滥，这会对我们模型的下游表现造成不成比例的拖累。因此，我们大体上追求数据在不同文档类别上相对均匀的分布。第二，我们希望得到相当平坦的文档长度分布；也就是说，我们要确保语料库中的文档长度大致服从均匀分布。我们追求这种分布有两个原因：一是我们想确保模型在训练期间不会只看到某个特定长度的文档，因为这可能对下游模型表现造成负面影响；二是我们想确保有足够的灵活性，让我们的文档打包过程能高效运转（关于这一过程的更多细节见「数据打包」一节）。

为了达成这些目标，我们在 Model Factory 里构建了若干稳健的管线步骤。需要强调的是，并非每个过滤步骤都会用在每个数据集上，因为这样并不总是合理的。例如，我们不认为多数开源软件会包含任何广告，所以不会对这些代码套用基于广告的过滤。另一方面，纯自然语言数据按定义就不含任何代码，在这里套用代码质量过滤不会有好结果。在所有这些情形下，我们高度依赖数据团队工程师和研究员的经验来迭代改进我们的数据集；我们也会花大量时间手工检视数据样本，以确保我们的过滤步骤不会损害底层数据集的质量。不过我们确实注意到，我们的过滤步骤通常相当激进，有时最终得到的高质量数据集只剩原始规模的个位数百分比。话虽如此，现在我们详细描述这些步骤。为了便于讲解，我们把重点放在我们最近对某个基于网络的数据集所做的一次清理上。

我们对这个数据集做的第一件事，是套用一系列启发式过滤器。这些启发式过滤器旨在用极低的代价剥掉低质内容。与本节其他过滤器不同，这些过滤器相当通用，通常用来移除已知的坏内容，比如粗俗用语或仇恨言论。我们也会预先丢弃对应某些类型广告的自然语言文档。我们要强调，这些启发式过滤器并不完美，它们会漏掉低质量文档。

套用这些轻量过滤器之后，我们通常会再跑一遍利用数据集专有元数据的过滤。具体来说，某些数据集（无论公开还是私有）中的文档带有额外的元数据，我们可以用它们进一步筛选文档。我们注意到，这类过滤通常按逐实例的方式应用，因此我们并不总是使用它。例如，如果我们关心的是某个数据集的基线质量，我们通常不会套用基于元数据的过滤。另外，我们会把「某篇特定文档为何被从数据集中剔除」的原因记录在过滤后的资产里，这让我们能人工检视过滤器的质量。有了 Model Factory，这类检视出奇地简单：因为每个数据资产都是不可变的、并且自带完整的血缘，我们总能把任何一次文档缺失追溯到它的根因。正是这种不可变性与可追溯性，让在 Model Factory 里提升过滤器质量变得异常直接。

不过，轻量过滤器很少足以保证我们拿到足够高质量的数据，所以我们还得施加一些更重的过滤器。例如，这个特定数据集里的数据在观感上仍明显偏向某些主题，比如广告。这种分布显然与我们追求文档主题较为均匀分布的目标相背。而且在这个具体案例里，我们无法使用该数据集已有的标签，因为几乎所有文档都没有关联标签。为了绕开这个问题，我们应用了 K-means 聚类算法，把这个数据集里的文档聚成大约 1.5 万个文档主题簇。这次聚类完成后，我们查看文档的分布，注意到文档仍然存在很强的结构，于是以更细的粒度重复了 K-means 聚类，这一次产出了约 300 万个细粒度文档簇。

这些簇产出之后，我们需要决定哪些簇保留、哪些簇丢弃。为了决定保留哪些簇，我们拿出一个已经训练好的代理模型（proxy model），在每个簇上继续训练并记录 loss。直觉上，导致 loss 偏低的簇往往要么太简单、要么冗余，而给出高 loss 的簇往往噪声很大。在这些情况下，我们直接丢弃导致高 loss 的簇，并对容易学习的簇做下采样。就我们当前的例子而言，仅此一步就从目标数据集中移除了约 24% 的原始数据。

但仅仅丢掉一些簇并不意味着完事了。确实，在这个阶段我们注意到剩下的数据依然严重偏向广告数据。于是我们把清理继续下去，在已经过滤过的数据集上施加一个简单的分类器，又从数据集中移除了 19% 的原始数据。广告被大幅下采样之后，我们接着决定把目标转向提升数据集其余部分的整体质量。由于我们的启发式过滤器可能漏掉某些形式的粗俗用语和非英文文档，我们随后动用了检测文档质量的工具。在这一次具体处理中，我们丢弃了那些粗俗的或包含低质量写作的文档。令人惊讶的是，这又带来了约 14% 的额外缩减。

继续之前，我们简要提一句：这项工作非常值得做。确实，在我们的示例数据集上应用这些过滤步骤后，在我们使用的所有预训练基准上都相对基线有所提升，平均相对提升约 5%，最大的相对提升相对基线高达 150%。这个提升幅度足够大，以至于我们在产出预训练数据配比的过程中，会定期把这些步骤应用到数百个数据集上。更宽泛地说，使用数据过滤（连同我们数据管线的其他环节）之后，在我们的许多次消融实验里，所得数据集的结果都明显优于当前所有可用的开源数据集。

## 去重

现在把注意力转向去重。我们会先描述如何处理文件级的模糊去重，然后看仓库级的模糊去重，最后从实现角度讨论去重是怎么落地的。

不过在深入去重之前，我们先讨论为什么要做去重。直觉上，去重通过移除某个数据集中意外的数据上采样来提升模型的下游表现；因此我们对它在管线中的角色格外重视。此外，去重是管线中第一个涉及多个独立数据集相互作用的步骤——毕竟我们是逐个过滤数据集的——所以我们需要小心地处理多个数据资产，同时不降低数据集的整体质量。

从高层次看，我们通过对数据集使用 Ioffe 的 Weighted MinHash 方案的一个变体来实现模糊去重。相比 SimHash 之类的替代方案，我们选择这条路是因为它在很宽的相似度阈值范围内精度都更高 [[]](https://poolside.ai/blog/gathering-and-processing-raw-materials-for-the-model-factory#df58d1b03fbb)。在识别近似重复文档上更高的精度，让我们能更有效地维护数据集的质量与多样性。继续之前，我们回顾一下：MinHash（以及它的所有变体）近似的是 Jaccard 相似度度量（即两个不同集合的交集与并集之比）。相比之下，Weighted MinHash 通过引入按词频加权的机制扩展了这一方案，从而得到更高水平的准确度。

现在更详细地讲讲这个过程。我们的去重过程从为整个语料库构建一份完整词表开始，同时统计每个 token 的频率。这一步确保每个 token 的重要性按其在文档间的分布得到恰当加权，为相似度比较立起一个有意义的基线。就自然语言文档而言，我们用一个简单的预训练 tokenizer 对输入文档做 tokenize，从而高效地构建词表。另一方面，对代码文档，我们使用特定语言的 tokenizer，以确保某些 token——比如分号——不会在最终词表里被过度表示。

我们管线的下一步是用这张频率表把每个文档映射成一种新的加权词袋（weighted bag-of-words）表示。每个表示都附带一些元数据，比如文档的原始标识符。

表示构建完成之后，我们把它流式送进真正的 MinHash 步骤。直觉上，MinHash 步骤接受一个输入表示，输出单个 `b` 位哈希。我们随后把这个 `b` 位哈希切成若干条各 `k` 位的 band；每一组 `k` 位都是全局哈希表里一个独立的键，于是每个文档被映射到 `b / k` 个不同的桶。`b` 和 `k` 的确切取值取决于所希望的相似度水平，但对给定的相似度水平，`b` 和 `k` 的最优值很容易计算。实际上，被映射到哈希表同一槽位的文档，在该哈希方案下很可能就是近似重复的。

接下来我们需要处理哈希表里的桶。由于每个文档被映射到 `b / k` 个不同的桶，我们的哈希表相当于一张文档之间未物化的图，边表示文档之间的相似关系。把这张图物化之后，我们就能识别出由相似性连起来的文档连通分量。而一旦找出一个连通分量，我们总得用某种方式处理这些连通分量。我们没有把每个连通分量当作一个团（clique，那种情况下只选一篇文档就够了），而是通过在连通分量上求解顶点覆盖（Vertex Cover）搜索问题来切入去重问题。这一选择的理由是相似边并不严格传递，随便只挑一篇文档有丢失重要内容的风险。Vertex Cover 的解会选出一组文档，它们合起来「覆盖」了所有相似边，因而能更好地保留每个分量内部的多样性。实践中，我们用一个简单直接的贪心启发式来近似 Vertex Cover，它在多数情况下与精确求解器表现相当。

最后，在选出用于训练的最终数据集之前，我们通常会在不同的相似度阈值下把去重管线跑好几遍。这种多阶段过程在数据集规模与产出质量之间做权衡：较高的相似度阈值能更激进地削减重复，但有丢失多样性的风险；较低的阈值保留更多数据，却可能留下不想要的冗余。通过仔细调参，我们确保最终数据集同时保住质量与效率，以服务于下游训练任务。

既然讨论完我们如何对文档应用模糊去重，就可以来处理仓库级去重了。在产出连通分量集合之前，我们走的流程和文件级完全一样。一旦得到连通分量集合，我们就把图里的节点映射回它们原来的仓库，把对应同一个仓库的所有节点合并起来。但与文件级去重不同，我们还有两个额外的顾虑要处理。第一，我们仍需处理这样一个事实：约 40% 的仓库被聚进了一个巨大的分量里。为了应对这一点，我们额外引入了一套打标机制，按仓库的宽泛主题把它们分组。虽然这意味着分量不再对应严格意义上的重复项，但我们能更容易地把那些不符合我们要找的东西的仓库剥掉。另一方面，我们也想确保自己保留下了已知优质的仓库；毕竟，如果能保留项目的原始版本，我们就不想留下它的 fork。这只需我们把 Vertex Cover 算法略微改造一下，让它把额外的元数据纳入考量，从而在仓库级去重的产出中保留高质量仓库。

收尾之前，值得讨论一下我们的去重管线随时间是如何演进的，因为它凸显了 Model Factory 在实践中如何帮我们放大效率。最初——也就是 Model Factory 存在很久以前——我们把去重实现成一个端到端的单体程序，跑在一台 u-24tb1.112xlarge 的 EC2 实例上，配了 24TB 系统内存。可以预见，我们很快就感受到用这条路的压力，于是把去重重新实现为一串各自独立运行的管线。值得注意的是，这个特定方案有几个瓶颈：有好几个子步骤被限制在单机上，这大幅拉长了跑一次去重所需的时间。最糟的是，用这种方式跑去重需要大量人工交互；作业要手动启动，失败的作业要人工排查解决。这带来了一个奇特的连锁效应：我们发现自己会尽量不去为小数据集跑完整的去重管线，因为人工工作量实在太高。这个连锁效应催生出了各种各样的 hack——其中一些事后看其实非常有洞察力；但这个例子恰恰说明，我们的去重管线远远没有达到工厂级使用所需要的水平。

到我们着手构建 Model Factory 时，实现一种健壮又好用的去重形式是我们愿望清单上的头一名。为此，我们按与数据管线其余部分相同的方式对去重建模：我们仍然把去重的每一步当作一个独立的程序，但每个独立程序如今都重度使用 Spark，从而更容易扩展。当然，并非每一步都能轻易并行化，我们不得不从算法工具箱里搬出一些招数——比如大规模并行的连通分量算法——以消除任何单节点步骤。此外，我们用 Dagster 来编排去重，这让我们能轻松地把中间结果落成为数据资产。事实证明这个决定极其有用。把中间结果物化为 Iceberg 表，让我们能轻松追踪血缘、识别每个处理步骤的影响。更好的是，用这种方式产出中间步骤，我们能在单个步骤失败或被打断时更容易地恢复。

Model Factory 版本的去重相对旧版的提升，再怎么强调都不过分。以前，去重是一个跑起来很沉重的过程，需要近乎不间断地盯守和管理才能正确处理；现在，它只是我们手里又一个「按一下按钮」的数据工作流。尤其重要的是，把去重变成 Model Factory 管线里普通的一环，为各种意想不到的使用场景打开了大门——如今我们会在各式各样的数据集上部署完整去重，而从前我们根本不会这么做。

## 依赖排序

现在我们把注意力转向如何把文档打包成对训练有用的形式。不过，在深入我们究竟如何打包文档之前，得先谈谈我们如何确保模型以有利于高效训练的顺序看到文档。本节我们只聚焦代码文档，因为自然语言这边的考量要轻松得多。

用下一个 token 预测训练的基础模型依赖上下文才能正常表现。这一点在自然语言语境下几乎是显然的：如果我们随意调换某些段落的顺序，几乎不能指望模型学到东西。然而，当我们向模型提供代码文档时，同样需要确保模型能提前看到所有相关的上下文。要明白这有多要紧，看看下面这个 C 程序：

```
#include<string.h>

void our_memcpy(void* dst, void* src, size_t nbytes) {
     memcpy(a, b, nbytes);
}
```

很明显，如果不先包含 `string.h` 就把这个程序的内容放进来，很难为模型提供足够的信息来准确预测后续的 token。换句话说，我们需要在训练时按依赖顺序向模型提供代码。我们把处理这个问题的技术称为依赖排序（dependency sorting，简称 Depsort）。用算法的语言说，这个过程对应于计算一张图的拓扑排序，目标是把节点（这里是文件）排成一个顺序，使每个节点都出现在依赖它的任何节点之前。这个过程并不像听起来那么直接。虽然众所周知 DAG 至少有一个拓扑序，但我们的输入图未必是无环的。也就是说，我们不能假定严格的拓扑排序在我们的输入图上有良好定义。为了解决这个问题，我们采用我们称之为「尽力而为的拓扑排序」的做法：我们转而计算拓扑排序的一个近似，在不要求图无环的前提下，尽可能多地保留依赖信息。

假设我们要对一个项目的仓库施加 Depsort。我们首先要做的是在项目所有文件之间构建一张依赖图。然而，构建这张依赖图的过程并不轻松。我们不依赖 grep 或其他基于文本的搜索工具这类启发式手段——它们很容易漏掉某些关系，尤其在那些允许文件之间复杂或循环引用的语言里——而是用一套更严格的做法。具体来说，我们注意到代码文件本身就以符号级信息（比如函数和类）的形式，包含了抽取依赖信息所需的全部信息。事实上，在前两个例子里我们已经隐式地用到了这些信息。因此，我们先从项目的抽象语法树里抽取符号级信息，然后检测哪些文件用到了哪些符号。这套做法等价于构建依赖图；例如，如果文件 X 定义了某个函数 `foo()`，而文件 Y 调用了 `foo`，那么显然文件 X 是文件 Y 的依赖。

抽出这些文件依赖之后，我们在依赖图上执行经典拓扑排序算法的一个变体。我们的变体具体是在依赖图上跑深度优先搜索。这种做法隐式地把依赖图当作一棵树，于是任何环都会在遍历过程中被随意地在某些位置打断。这当然纯属启发式，我们并不能保证得到「最好」的那个拓扑序。但在实践中，这种任意的打断看起来并没有对模型质量产生负面影响。

上面描述的做法当然只是一种可能的实现。在某些编程语言里，可以拿到关于项目结构的额外信息——最典型的就是以包（package）形式存在的信息。当能访问包级元数据时，我们会利用它把拓扑排序分成两层：先跨包排序以理清高层依赖，然后在每个包内部对单个文件排序。这多出来的一层排序让我们更接近「最好」的拓扑序，同时不给 Model Factory 增添多少额外复杂度。

## 数据打包

既然已经在我们的代码文档之间建立了依赖关系，下一步就是把这些文档组织并打包成适合训练的形式。这一步对优化我们向模型呈现数据的方式至关重要，尤其是在上下文窗口有限、数据集庞大的情况下。

这个打包过程的主要目标是提升我们基础模型训练的效率。我们不是把每篇文档填充到占满整个上下文窗口——那种做法浪费空间和计算资源——而是把多篇文档打包进同一个上下文窗口，让每个训练样本可用的 token 数最大化。这套做法会带来一些复杂性，因为我们现在需要确保这些文档在训练期间互不干扰；不过处理这件事相对直接，我们会在那篇讲训练管线的文章里讨论。

为了讲解方便，我们先聚焦于在单个仓库内部打包代码文档。首先，我们用特定的元数据对所有已经 tokenize 的文档排序，比如它们在上一节所述拓扑排序中输出的顺序。对超出目标上下文规模的文档，我们把它切成更小的块（chunk），以确保每一片都能落进打包约束之内。预处理完成后，就要真正打包文档了。在最基本的情况下，我们通过产出一份「打包计划」（packing plan）把文档映射到打包后的文档，也就是一份把文档（或文档块）转换成打包文档的映射。我们通常用知名的 best-fit 装箱算法来产出这份计划。继续之前，值得说说我们为什么用 best-fit 而不是别的方法。我们最初用的是 next-fit 方案，简单地把文档一篇接一篇往里加，直到一个上下文窗口填满。但因为打包效率不高，这样做留下大约 15% 的未用空间。相比之下，best-fit 提供的打包紧密得多，上下文窗口的利用率常常接近 100%。打包计划确定之后，我们按各文档关联的元数据和打包键所规定的顺序，把输入文档串接起来，生成最终的打包文档。

前面描述的做法对小代码仓库很管用。然而，用一份全局计划的可扩展性并不好；产出打包计划也许只是线性时间的操作，但要把它扩展到一个机器集群上却很难。为了解决这个问题，我们采用混合方案，为打包定义多个子计划。具体来说，我们引入一个预哈希步骤来切分我们的仓库：先把每个仓库映射到几千个桶中的某一个，然后再把这些桶进一步细分成每块几千篇文档的块。接着我们对每个文档块独立地施加打包过程，从而让整个机器集群都能高效地扩展这一过程。

到此描述的做法只适用于代码仓库和代码文档。不过我们对自然语言文档的流程大体相同：我们把每一篇单独的文本文档当作它自己一个独立的仓库，然后重复上面描述的同一套流程。这样做确保了文档级的完整性得到保留——毕竟我们不会跨桶打包仓库——同时我们得以复用已有的文档打包管线。

## 数据混合

最后，来谈谈我们如何为训练产出和管理数据混合配比。要描述这个过程，得先介绍我们用于产出数据混合的内部平台，它被恰如其分地命名为 Blender。

在深入 Blender 之前，值得重申一下我们想要达成什么。在传统的基础模型训练中，数据混合与数据分发是紧耦合的：我们先要产出一份混合配比，然后确保这份配比被分发到合适的节点上。过去这件事是手工完成的：我们会把若干数据集完全物化，然后手工算出一份合适的混合配比，再把数据集分发到各个节点上。这种做法虽然可行，却严重缺乏灵活性。我们显然需要提前知道节点数量，否则就不知道该把混合后的数据集放置到哪里。而且我们还得在分发数据集之前把数据集完全物化并定好数据混合配比，这让人很难纠正错误。同样清楚的是，这种做法意味着我们无法轻松处理实时数据源：我们需要从一个实时源里抓取一部分、分发出去，然后在实时源演进时重复这个过程。这条路显然无法在多个实时源、多种数据配比上扩展。为了解决这个问题，我们构建了 Blender——我们用于配置和拉取混合配比的内部平台。顾名思义，Blender 提供了从多个来源（包括实时来源）产出数据混合的工具。实践中，Blender 充当一个数据流式服务，让我们能够按一组预定义的条件，轻松地从各种各样的 Iceberg 表里拉取数据。尤其值得注意的是，这些表已经按上一节的技术预先做过 tokenize 和打包，从而把这些细节与数据流式和混合解耦开来。

在底层，Blender 提供两个 gRPC 服务。第一，Blender 提供一个 API 调用，为某个特定的数据混合产出一份名为 BlendConfig 的配置。每个 BlendConfig 都是不可变对象，对已有 BlendConfig 的更新只会产出一个新的 BlendConfig。BlendConfig 由若干数据源（称为 BlendSource）组成，每个 BlendSource 恰好包含从某张特定 Iceberg 数据表或表快照读取所需的信息。值得注意的是，每个 BlendSource 都包含一次应当读取的表行数，以及这个数据源是否是「实时」的、或者是否应当被过采样。我们把数据源中应当读取的行数称为该源的「权重」。

定义好一个 BlendConfig 之后，我们可以通过调用 Blender 提供的第二个 gRPC 服务——也就是真正提供数据的那个——来拉取数据。数据查询服务每次被调用时，Blender 会遍历 BlendConfig 里指定的表，并返回每张表中一个子集的行。如前所述，每张表返回的确切行数由各表 BlendSource 里的权重指定。在某个请求可用的数据不够时——例如从实时表读取——Blender 就直接阻塞，直到有足够的数据可用。无论如何，一旦 Blender 为这个请求收集到数据，结果就会流式回传给调用节点，供训练期间使用。此外，这个服务的每个响应还包含当前相对于混合序列起点的偏移，这让我们既能在排查 loss 尖峰时重新拉取此前的数据，也能为后续的训练步骤拉取新数据。

Blender 是我们用于配置和从训练数据集拉取混合配比的内部平台。提醒一下，我们把训练数据集表示为 Iceberg 表，它们已用前面几节的技术完成 tokenize 与打包。Blender 本身由两个 gRPC 服务构成：一个让我们配置数据，另一个让我们从各种训练数据集的表里拉取数据。

最后，正如你所见，Blender 让产出复杂的数据配比变得出奇地简单；我们只需指定正确的 BlendConfig 和 BlendSources。这和我们从前的做法是翻天覆地的变化。以前，我们必须手工预分发数据、提前定好配比、并预先预留节点。从前我们要花大量时间构建混合配比，现在我们可以直接指定我们需要什么，Blender 替我们搞定。这种易用性把数据混合变成了我们工厂里普通的一环，如今我们能在从前根本做不了的地方轻松试验多种不同的数据混合配比。这在强化学习工作流的场景下尤其有用；不过要了解更多细节，你还得等后续的文章！
