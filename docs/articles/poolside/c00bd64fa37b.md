# 泰坦，模型工厂的熔炉

**TL;DR：** 我们公开自己分布式训练代码库 Titan 的细节。Titan 为大规模基础模型训练提供了一批贴近硬件的技巧、优化手段和日志设施。随后我们会讨论如何把 Titan 作为 Model Factory 的一部分来开展大规模的架构实验，最后讨论我们如何在 10K GPU 集群上可靠地训练大型基础模型。

## 引言

在[我们的上一篇文章](https://poolside.ai/blog/gathering-and-processing-raw-materials-for-the-model-factory)里，我们讨论了 Poolside 的数据技术栈，从数据摄取一路讲到产出数据混合配比。既然那些细节都覆盖完了，现在我们可以深入自家 Model Factory 的熔炉：我们的预训练代码库，名为 Titan。

今天这篇帖子，我们来看预训练代码库背后的设计理念。具体来说，我们先讨论 Titan 这个代码库是怎么来的，其中也会谈到我们此前的预训练代码库。然后讲我们如何把这些经验用起来，把 Titan 设计成一个既灵活又高性能的预训练代码库。接着我们讨论如何把 Titan 作为 Model Factory 的一部分来开展大规模架构实验。最后收尾时，讨论我们如何在 10K GPU 集群上大规模地、可靠地训练并自动评测大型基础模型。

## 我们是如何选定 Titan 的

在深入 Titan 怎么工作之前，先说清楚 Titan 是怎么来的很值得。毕竟，很少有人能一次就做对。

尽管我们现在已经有了一个运转完善的工厂来训练模型、跑架构实验，情况却并非一直如此。事实上，2023 年 4 月 Poolside 成立时，我们操心的事情和今天完全不同。首先，我们的算力预算比今天小几个数量级；第一个训练集群只有寥寥几台配备 A100 GPU 的节点。与此同时我们的团队也很小：我们的 Foundations 团队一直到 2024 年年初都只有三名工程师，之后才迅速开始扩张。

当你只在几个节点上训练时，你的优先事项和你拥有 10K GPU 时的优先事项长得完全不一样。你必须把「随时能调试训练」这件事放在很高的优先级上，并且真正紧盯训练过程中发生的底层细节。事实上，因为我们的 GPU 数量相对很少，我们通常同时只跑着几个 GPU 任务，这让监控相对轻松。我们也极其在意显存上限。我们知道自己想对不同规模的模型做实验，不想过早限制自己做这些实验的能力。

这些约束给我们出了一道题：我们要么改造一个大型开源训练框架来适配我们的需求，要么把所有东西都从零写起。最终我们走的是混合路线：用 PyTorch 和其他开源库混合起来，搭了一个内部的分布式预训练代码库，叫 Monster。有些地方我们手工封装并 fork 了底层库，比如 Xformers、libtorch 和 NCCL；另一些地方我们自己实现 CUDA 和 Triton kernel。以我们当时的约束条件来看，构建 Monster 是正确的决定，参与过它的人至今对「从零搭起我们自己的 Monster」怀有美好的回忆。

但过了一会儿，Monster 开始踉跄。回头看，压在 Monster 上的压力来自四个不同的方向。第一，随着时间推移，我们的约束条件和优先事项变了。原先我们只是并行跑几个任务，转眼间就变成了同时执行上百个任务。到了这个规模，如果没有合适的工具，逐个调试失败的任务就变得基本不可行。此外，我们很难跟上外部世界：几乎我们想要的每一个功能，都得自己造。更紧迫的是，我们发现自己落后了：我们的优化不如外部世界的优化好，这主要归因于我们构建 Monster 的方式。具体来说，早期我们把 Monster 围绕 pipeline parallelism 来设计，而我们这套设计的不灵活意味着每当我们要加新功能，Monster 就吱嘎作响。从某种意义上说，这种不灵活正是追逐每一项优化的结果。我们把 Monster 的一个个部件都做得性能极强，但代价是代码变得非常僵硬、缺乏弹性。直观地讲，这就是 Amdahl 定律 [[]](https://poolside.ai/blog/titan-the-model-factory-s-furnace#be83d58adc02) 的后果：我们有一大堆在 microbenchmark 上表现优异的代码，但这些代码对我们预训练任务的整体运行时间其实贡献不了多少。更有甚者，那些被精心优化过的代码反而拦住了我们去实施更大范围的优化，限制了我们做全局改动的能力。另外，完全自研的预训练代码库还带来很大的上手挑战。庞大而复杂的代码库本来就越读越难，我们意识到自己花了很多时间去争论术语和代码布局。而且，尽管性能不错，Monster 依然强加了自己太多设计主张，想让扩展变得很难。它根本就不适合用在 Model Factory 里。

我们开始思考哪些地方能做得不一样。巧合的是，TorchTitan 恰好是在我们开始寻找 Monster 替代方案的前后发布的。对不了解它的人来说，TorchTitan 是一个开源项目，它广泛使用各种 PyTorch 特性，为分布式训练提供一个高效而简洁的模板。对我们而言尤其关键的一点是，TorchTitan 由 PyTorch 团队撰写和维护，这意味着 PyTorch 核心的改进能非常顺手地在 TorchTitan 里用上。虽然我们在 Monster 内部也自己实现过其中一些改进，但我们很快意识到，用 TorchTitan 训练新模型会比用 Monster 高效得多。更重要的是，我们还意识到 TorchTitan 能够提供一种灵活性，这是我们 Monster 那套实现根本比不上的。经过最初的若干实验后，我们决定让 Monster 退役，改用建立在 TorchTitan 之上的新代码库，取名 Titan。

那么，Titan 给了什么是 Monster 没给过的？第一，有了 Titan，我们总能跟上开源世界：TorchTitan 是一个极其活跃的开源项目，我们从 Torch 和 TorchTitan 的上游创新中受益巨大。这些上游创新不仅让我们能把时间集中到实现 Model Factory 所依赖的其他功能上，也让我们能专注于跑架构实验、提升 Model Factory 更广泛层面的可用性。此外，使用 PyTorch 原生库让上手容易得多：本来就熟悉 PyTorch 的工程师学起怎么用 Titan 要轻松得多。而最重要的是，Titan 足够灵活，给了我们一块尝试新想法与新优化的试验场，从而进一步让我们能够去推进 AI 的前沿。

## Titan 是怎么组织的？

既然知道了 Titan 是怎么来的，我们就可以看看它提供什么、又是怎么组织的。

首先有必要说明，Titan 并不是把 Monster 彻底重写。恰恰相反。我们开始搭建 Titan 时，把 Monster 的全部代码迁移进了新的 Titan 仓库的一个子目录。然后随着时间推移，我们逐步把某些组件替换成来自其他来源的、更灵活的等价实现。在那些第三方依赖本身就是同类最佳选择的地方，我们把它们保留了下来。

接着我们开始引入 TorchTitan。提醒一下，TorchTitan 为大规模训练提供了若干有用的组件，其中包括几种并行策略。我们也大量使用 TorchTitan 的其他组件，比如简洁的训练脚本组织方式、checkpointing，以及其他一些 helper。但我们不会盲目使用这些组件。它们并不总是契合我们的用例，也不总能满足我们全部的要求。这些情况下，我们通常用自己的定制组件把它们换掉。这种做法让我们得以兼得两边的好处：既能从开源世界拿走有用的东西，也能在需要时自己造新组件。我们自己依然实现了若干新组件。举例来说，我们整套 mixture-of-experts 技术栈都是自研的，而且我们也会定期给代码库的其他部分加上新的定制组件。

Titan 本身可以有多种使用方式。实际上，Titan 能够部署在各种各样的拓扑上：从单台机器，到我们完整的 H200 集群，甚至更大规模。实现新功能时我们经常利用这种灵活性：先在单个开发节点上试验新想法和新实现，等功能经过充分测试之后再放大实验规模。值得一提的是，一个分布式预训练代码库并不是孤立存在的。确实，大规模运行分布式预训练任务需要多层编排，从节点调度到身份认证都是。所幸 Titan 能很好地嵌进 Model Factory，我们可以用过去造好的原语来替我们处理这些事项。实际上，我们可以通过 Kubernetes 毫不费力地把 Titan 部署到我们的 H200 节点上，所有的节点调度都由我们的编排器和 torchrun 替我们处理。

我们也用别的方式使用 Titan。首先，把 Titan 仅仅称作一个分布式预训练代码库在技术上并不准确。更确切地说，**Titan 是一个分布式训练代码库**；它支持监督微调（SFT）、各种 mid-training 技术，并且让我们能处理各种强化学习工作负载。我们如何运作 SFT 和强化学习，会在后续篇章里讨论，但有一点值得强调：Model Factory 里每一个 AI 工作负载的分布式训练都由 Titan 提供。

从运维角度看，Titan 可以在我们的 Dagster 工作区内部被调用和调度，这让我们能轻松启动实验（关于我们如何使用 Dagster，请参阅本系列[较早的几篇文章](https://poolside.ai/blog/gathering-and-processing-raw-materials-for-the-model-factory)）。实际上，Titan 工作负载既可以通过手动方式——也就是经由 Dagster UI——触发，也可以通过我们的持续集成 pipeline 触发。这让启动新实验和新训练运行变得极其简单，只需点几下鼠标就能开始。实际上，Dagster 里每一个 Titan 工作负载都会产出一个带版本的 Dagster 资产，汇入我们已有的数据血缘。从这个角度看，我们的 Dagster 血缘起的作用不止是数据血缘：它还是我们在 Model Factory 内部跑过的每一次训练实验和数据实验的历史日志。

Titan 同时也作为其他项目的依赖存在。我们此前提到过，Titan 为各种各样的训练和强化学习工作负载提供训练能力。但 Titan 也可以被显式地当作其他项目的项目依赖来使用。举例来说，我们把 Titan 作为 Atlas（我们的推理代码库）的一个依赖，用来为推理的某些环节取得参照结果。这意味着我们可以对照一个已知基线快速实现新模型：直接用 Titan 的 forward pass 实现，为推理构建该模型的专用实现，然后检查两者是否一致。在这种设定下能够校验等价性非常有用，尤其当我们最终用上了各种优化之后。

## 用 Titan 训练

虽然拥有一个最先进的预训练代码库在纸面上当然是件好事，但建造这样一个代码库是个昂贵又耗时的过程。因此，只有当它真的能让我们成功产出高质量基础模型时，拥有这样一个代码库才讲得通。所以，这一节我们讨论如何用 Titan 跑大规模架构实验，以及 Titan 如何让我们在生产规模上成功训练基础模型。

### 架构实验

在进入架构实验之前，先回顾一下我们为什么把这类实验视为大规模训练成功的必经环节，是很值得的。

训练一个大规模基础模型是极其耗时且昂贵的工程；世界上真正从零开始预训练大规模基础模型的公司只有寥寥几家。生产规模的运行通常一次就要占用数千张 GPU 达数周乃至数月，每一个小时都金贵。既然开销如此之大，我们当然希望能提前知道这笔开销花得值（也就是说，训练结束后我们真的能拿到一个不错的基础模型）。更宽泛地讲，训出一个「好」模型，是在许多不同的取舍之间小心平衡的产物。一方面，我们可以训一个极大的模型，它在下游 benchmark 上表现出色，但造这样一个模型所需的成本和时间可能沉重得让人无法承受。另一方面，便宜地训一个小模型很容易，但它在有用任务上的下游表现很可能很差。换句话说，我们真正关心的，是在固定的算力和时间预算下，造出我们所能造出的最好的模型。

做到这一点的一个办法是建立 scaling laws。直观地说，scaling law 就是拿一个小模型的 loss 曲线，预测随着模型参数量增加，这条 loss 曲线会如何变化。这正是我们想要的：我们只管训一个小模型，看它的 loss 曲线，然后预测同一个模型的更大版本会有怎样的表现。文献里把这种做法称为 hyperparameter transfer（超参迁移）。我们要指出，文献中可以找到多种实现超参迁移的做法，包括 mu-P 这一族技术。为了简洁，我们略过我们自己使用的是哪些技术的具体细节，但要强调：Titan 足够灵活，在实践中能容纳多种不同的超参迁移技术。

我们在 Model Factory 里用如下方式建立 scaling laws。我们先确定针对某一次参数搜索（或参数扫描）我们想跑哪些实验，或者说我们有意探索的那个特定搜索空间。实践中，我们最后通常会得到上千个小实验，覆盖各种各样的参数，横跨不同的架构细节和各种各样的超参数。然后我们写一个简单的 Python 程序，为每个实验产出一份不同的配置。之后，当我们启动这些实验时，每一份配置都会作为带版本的资产登记进 Dagster，同时一并登记生成这份特定配置所用的源代码。一旦某个配置在 Dagster 里登记完成，它就正式成为工厂的一部分，真正的魔法随之发生。举例来说，我们可以自动触发评测，并针对产出的每一个 checkpoint 为其排期，这样我们就能超越只看 loss 曲线。每个模型的指标也会直接流入我们的 Neptune 看板，实验结束后我们最终就是看这些指标来判断哪个模型表现最好。与此同时，我们也会看这些实验期间采集到的其他指标，比如单次训练迭代耗时，或者某个模型训练运行过程中观察到的硬件利用率峰值。把所有这些信息收在一处，我们就能更轻松地迭代我们的架构实验，并最终决定我们要用哪个模型架构去跑生产规模的训练。

当然，我们也能在 Model Factory 里跑其他种类的参数扫描。举例来说，假设我们想针对某个特定模型架构做一轮关于 batch sizes 的配置扫描。提醒一下，选择 batch size 需要做出小心的权衡：batch size 大可以让训练更快，但模型在训练过程中非常容易卡进 local minima（局部极小值）。相反，小的 batch size 更容易跳出局部极小值，但由于硬件利用率更低，训练通常要慢得多。

尽管我们可以凭直觉猜出一个合适的 batch size，但这远不是做出如此重要选择的严谨办法。我们可以换一种做法：对合适的 batch size 做一次经验性搜索，从而给这个过程注入一些严谨性。有了 Model Factory，这个过程几乎不费力气。下面我们把这个过程细讲一遍。和上一个例子一样，我们先写一个 Python 脚本来替我们生成配置。具体来说，我们先声明一个装着候选配置的 Python 字典。为了这个例子，我们按 head 数量来作键，但这并不是硬性限制：

```
sweep_params = {
      1: {
         "batch_sizes": [(1, 8)],
         ...
      },
}
```

然后我们在一个 builder 函数里遍历这些参数。builder 函数会为每一个参数取值产出一份不同的 Dagster 配置。

```
for n_heads, config in sweep_params:
    # Create a new Dagster asset for this run
```

就这样！随后我们只要打开 Dagster UI，点几个按钮，所有的运行就会立刻替我们启动。具体来说，每一份配置对应一次新的预训练运行，所有调度和资源分配的细节都由工厂替我们处理。而且，我们需要的每一项指标都会被自动推送到我们的指标平台，让我们能轻松追踪实验随时间如何演进。值得一提的是，并非每个工作流都遵循这套流程；有些工作流是通过我们的持续集成 pipeline，或者通过我们写的其他脚本触发的。但总体的过程——只需要定义我们想探索什么——几乎总是这么简单。

值得强调这种做法如何改变了我们在 Poolside 所做的工作。过去，跑架构实验是我们发怵的事；每一个任务都要精心写配置、手工部署、贴身盯守。如今我们经常一个周末就跑上百个实验，周一早上到工位就有结果可以查看。我们甚至可以深挖这些实验：分析 loss 曲线、查看训练日志，并以一种过去根本做不到的方式得出新的洞见。

### 生产规模的预训练

实验告一段落之后，我们就准备好启动一次生产规模的预训练运行。令人惊叹的是，Model Factory 让这件事和启动一个实验一样简单；我们只要定义一份与我们想执行的生产规模训练任务对应的配置文件，然后用和普通实验完全相同的方式把一切启动起来。就是这么简单。

和小规模实验相比，这里有几个实操层面的差别。首先，我们会对训练过程中产出的 checkpoint 跑自动评测，有时频率高到每几百个训练 step 就一次。关于评测是怎么实现的，我们会在系列后续篇章里多讲一些，但这里值得先指出：一次训练里我们会对同一个模型跑多次评测。底层机制是，当一个新的 checkpoint 被推送到某个 Dagster 分区时，Dagster 会自动触发评测。需要强调的是，我们的评测是解耦的、各自单独调度的（也就是说我们并不强迫所有评测并行运行，甚至不要求它们大致在同一时刻跑）。这主要是为了灵活性；如果我们的集群很忙，我们可能没有容量把所有评测并行跑完。不过，只要某一次评测结束，这次评测的分数就会被推到 Neptune，让我们能持续追踪模型性能在训练过程中如何变化。

尽管在 Model Factory 里启动评测和训练运行很容易，生产规模预训练这件事本身却一点也不简单。实际上，生产规模的预训练运行通常需要比小型实验运行多得多的小心。直观地说，差别主要在于规模：因为我们的生产规模训练跑在多得多的 GPU 上，能出错的地方也就多得多。举例来说，GPU 故障发生得频繁得多，loss spike 可能让训练运行脱轨，网络问题也可能把训练磨到完全停摆。而且这些问题随时都可能出现：一般来说，预训练报错特别爱践踏人的睡觉时间。

过去，这些问题出现时我们只能手工解决，于是熬过了许多深夜和清晨。我们当时想，一定得有比全靠人手做这些更好的办法吧？

我们从三个不同方向下手解决这些问题。第一，一分预防胜过十分治疗，我们可以在启动训练之前先对我们的训练节点跑「pre-flight checks」（起飞前检查），从而防住许多问题。直观地说，我们的起飞前检查要确保节点在用于训练时是稳定的，我们会对节点的许多方面做压力测试，确认它们足够稳定。实践中，这些起飞前检查能扫掉许多唾手可得的问题，比如网络断连或者有故障的硬件。我们要强调的是，我们的起飞前检查本身也在随时间不断演进，我们会持续加入新的测试、监测更多的指标，以确保在开始训练一个模型之前一切都按预期工作。

无论我们跑什么样的起飞前检查，预训练期间依然会出错：在我们的规模上这是不可避免的。有些错误来自起飞前检查抓不到的程序 bug，比如一个 off-by-one 错误，或者 NCCL communicator 里的死锁。也有时候，模型训练就是会跑歪。loss spike 很容易出现，而要揪出这类错误的根因需要大量的技巧和耐心。实践中，我们通常借助预训练期间采集到的指标来诊断这类问题。此外，Titan 本身就配备了多种调试设施。我们把训练日志直接流入 Sentry，Titan 还支持启用 PyTorch 的 FlightRecorder 软件，让我们能事后回看并调试失败的训练运行。最后，我们还有各种自研的专有工具与技术，让我们能在 Model Factory 里调试失败或表现不佳的训练运行，从而获得公开可用的工具之外的洞见。

然而，直接排查错误意味着我们要投入大量人力来管理训练并重启训练。不过，确实存在一种办法可以自动解决这些问题，而不需要我们的工程师对每一个失败的训练任务都动手干预。事实证明，从实际操作来看，预训练期间发生的几乎所有错误情形，都能按照一套标准操作手册来解决。举个例子，设想有一台单独的故障节点扰乱了预训练。过去我们调试这种错误的方式是：先隔离那台故障节点，用一台已知可用的节点替换它，然后手工重启训练。但这个过程没有理由非得由人工来处理；事实上，把这个过程自动化，很可能比依赖某位工程师更不容易出错。

为了应对这类问题以及其他相似的问题，我们把健壮的自动恢复实现为 Model Factory 的一部分。Model Factory 里的每一项恢复自动化都负责某一种特定的错误情形，比如某台节点开始失效。实践中，这些自动化会在训练看起来已经停摆一段可配置的时长之后启动。假设是十分钟。值得一提的是，我们的自动恢复系统也包含自动重启，让我们能从停滞的训练中快速恢复。

虽然我们的自动恢复能处理绝大多数错误情形，但仍有少数罕见错误无法自动恢复。这些情况下，我们启用一套兜底系统来提醒我们的某位工程师。更详细地说，我们用 incident.io 来监测我们 Grafana 看板里的指标。如果 incident.io 服务发现一段可配置的时长内没有出现新的指标，比如三十分钟，那么 incident.io 就会向我们的值班工程师以及一个 Poolside 全员 Slack 频道发一次 soft ping（软提醒）。发软提醒主要是给任何自动恢复流程留出完成所需的时间，因为自动重启有时要花上一阵。如果过了另一段可配置的时长（比如一小时）训练仍未恢复，值班工程师就会收到一次 hard ping（硬提醒）去重启。这条提醒一旦被确认响应，系统就会自动新建一个 Slack 频道，用来讨论与该 incident 相关的内容。值得一提的是，这个 Slack 频道能让我们在各位工程师之间快速共享上下文，从而带来更快的定位与重启。

和手工重启训练相比，自动重启给我们工程师带来的生活质量提升再怎么强调都不为过。举例来说，Poolside 产出的第一个模型——Malibu v1——的训练运行，是一段持续数周、近乎要不停贴身看护和调试的艰苦时期。尽管那段经历催生了许多关于大规模模型训练的重要教训，但如今我们这套新做法带来的从容与安心，在 Model Factory 之前的日子里简直像是求不到的东西。
