# 载体和信标

## 在 Model Factory 内部运行推理与评测

**TL;DR：** 我们在这里详述 Poolside 是如何运行推理与评测的。我们先介绍我们的推理代码库（名为 Atlas），并说明 Atlas 如今的设计是如何形成的。接着描述 Atlas 的组织结构，然后讨论我们如何在范围很广的硬件平台上实现推理。再之后，我们说明如何把推理作为 Model Factory 的一部分来部署和提供服务。最后，我们讨论 Atlas 如何与我们的评测平台配合，在预训练期间乃至其后稳健地评判我们的模型。

## 引言

在之前的几篇博文里，我们从数据管线一路谈到了代码执行。但这些工具无论多么有用，如果我们没法把模型服务给内部和外部的客户，它们也成就不了什么。更进一步说，如果模型本身质量不行，那么整套尝试都是徒劳。

在这篇博文里，我们讨论推理与评测方面的系统。我们先谈 Atlas，也就是我们的推理代码库——具体来说，我们通过阐述一个高质量推理代码库背后的关键原则，来解释我们为什么把 Atlas 设计成现在这个样子。然后我们深入 Atlas 在实践中是如何组织的，以及我们如何用它来大规模运行推理。过程中我们会谈到我们如何在 GPU 和 Trainium 硬件上实现推理。接着我们谈如何在集群上部署和调度推理作业，最后以一段关于我们的推理平台与评测平台如何协同工作的讨论收尾。

## Atlas 为何存在：打造一个出色的推理实现

在我们讲 Atlas 如何帮助我们达成目标之前，先谈谈 Atlas 为什么是现在这个形态、它试图解决什么问题。毕竟，不去理解一个系统为什么存在就想去理解它本身，很少是个好主意。

推理在 Poolside 承担着许多角色。简单说，推理是我们与模型交互的主要方式：我们发出请求，拿回响应，如此往复，直到我们满意为止。但我们对这次交互的期待，完全取决于我们的意图——取决于我们一开始为什么要和模型交互。事实证明，正是这一区别让实现推理变成了一件非常微妙、棘手的事。

要理解这个区别为什么重要，我们聚焦两种不同的推理用例。一方面，agentic 工作流往往是运行时间很长的任务，因此衡量性能的首要指标是推理服务能提供的原始吞吐量。另一方面，代码补全工作流对延迟极其敏感，吞吐量通常退居次要考虑。哪怕这个区别本身也可能有欺骗性：在某些场景下，单个用户的高性能可能至关重要，而在另一些情境下我们可能判断，同时处理大量用户请求所带来的经济性胜过纯粹的速度。而这还不是全部：如果我们在性能或内存上更加受限，还可以使用量化之类的技术，用精度换取性能。推理这种延迟—吞吐量—精度之间的权衡对用户体验影响巨大，而归根结底，一个好的推理实现会试图同时满足所有这些标准，或者至少提供在它们之间轻松取舍的能力。

但真正出色的推理实现还需要提供更多东西。如前所述，推理是各种有趣工作负载的载体：评测、强化学习，甚至某些种类的后训练，都需要高效的推理才能顺利运行。有意思的是，这给推理实现附加了一层负担：纯粹的灵活性。直观上讲，如果我们无法在推理代码库里快速实现任何配套机制，就赶不上那些激动人心的新想法出现的速度。这种灵活性甚至超越纯粹的 AI 工作负载；我们需要能够在推理代码库里灵活地实现新模型和新优化，从而持续推动 AI 研究向前。

最后，一个推理服务还需要提供若干生活质量特性，才能真正可用。首先，推理服务是一个分布式系统，因此我们必须时刻留心错误上报、可观测性和容错。同样，一个好的推理服务应当能在很宽的硬件范围内快速部署，并且理想情况下足够灵活，能适应不同的内存约束和系统配置。再往前一步，推理服务还应当向用户提供稳定的接口：无论底层发生了什么优化或改动，一个好的推理服务都应该让应用能够方便地发出请求、收到响应。这并不意味着一个好的推理服务不该为某些用例提供专门化的 API。恰恰相反。但推理服务最终应当在一种稳定的配置下易于使用。

我们应对这些挑战的方案就是 Atlas，我们的推理代码库。就像希腊神话中的泰坦一样，Atlas 以稳健可靠的方式扛起了运行基础模型推理这项繁重任务，服务多种模型架构、跨越多个硬件平台。归根结底，Atlas 为范围很广的工作负载提供了出色的灵活性与性能，无论这些负载来自 Factory 内部还是来自我们的客户。

接下来两节我们会讨论 Atlas 的技术细节。但在继续之前，值得先勾勒一下 Atlas 背后的理念。如我们前面所说，一个有用的推理平台的关键要素之一是灵活性，无论在工作负载还是实现上都是如此。Atlas 把这个想法再往前推了一步。事实上，我们的根本论点是：在推理这个语境里，能够灵活地做出改变几乎就是全部要点。从实践上讲，灵活性会带来快速复利的收益；随着时间推移，不够灵活本可能带来的好处，会被灵活性所产生的改进所超过。当然，无边界的灵活性同样不是好主意——总得在某处引入结构。但通过谨慎地平衡灵活性与结构之间的取舍，我们几乎不费力气就得到了一个良好推理服务所需的一切。而且复利收益并不只限于推理服务本身；它们会扩散到整个 Model Factory，提升我们在别处快速迭代的能力。

## Atlas 如何做到：用灵活性制造复利收益

现在我们把注意力转向 Atlas 的组织结构，看我们如何靠灵活性制造复利收益。

从宏观上看，Atlas 是一个为推理工作负载提供组件的库。这些组件大体可以分成两类：我们自己实现的组件，以及从开源推理库里包装来的组件。和我们的预训练代码库 Titan 一样，我们取开源世界最好的部分，并在现成方案不够贴合需求时自己实现变体。每个组件都可以看作一个负责单一动作的实体。例如，我们有几个实现层归一化的组件，各自针对略微不同的使用场景。

这个设计决策带来若干好处。首先，Atlas 基于组合的设计让我们能够根据具体需求方便地替换组件。举例来说，transformer block 通常会用到某种形式的层归一化，而层归一化正是算子融合的首要候选。不过，根据底层平台自身的特性，我们可能在不同平台上希望把层归一化和不同的操作融合在一起。把 transformer block 表示为一个组件之后，我们就能方便地替换实现，而不必改动 Atlas 库的其余部分。此外，用这种方式把算法表示为组件，我们还能轻松地为不同模型架构实现推理。例如在 transformer 里，多层感知机（MLP）几乎总被放在 attention block 之后，但具体用的是哪种 MLP——或者用的是哪种 attention 机制——在不同模型之间是有差异的。把 MLP 和 transformer block 都抽象成组件，我们就能先为模型定义一个高层结构，再针对每种具体架构做特化。

而且，Atlas 这种基于组合的方式意味着我们能轻松地从开源推理库里引入各种组件。具体而言，截至撰写本文时，Atlas 包装了 vLLM——一个流行的开源推理代码库——的各种组件。这给我们带来了实实在在的益处。例如，我们不必自己去重新实现 KV 缓存或前缀缓存这类通用功能，可以直接在 Atlas 里使用外部世界对这些组件的实现。此外，我们是开源的坚定信仰者，会尽可能把自己的改动和修复回馈给这些库。这不仅让我们能支撑开源事业，也减少了上游库与 Atlas 之间的分歧。在 Atlas 与上游代码库出现分歧的场合，我们可以简单地把改动重新 rebase 到任何新版本之上。

然而，这种方法最大的好处之一，是我们能够为各种任务定义通用接口，比如在一批请求上执行推理。从高层视角看，推理究竟是如何被执行的细节无关紧要；我们只需满足所约定的接口。这使得改动其他组件——比如 vLLM 的调度器——变得可控得多。

既然已经从宏观上讨论了 Atlas 的组织方式，我们就可以深入 Atlas 内部是怎么运转的。如前所述，Atlas 为各种任务提供通用接口，因而能够严丝合缝地嵌入现有的推理库。从实现角度看，这些通用接口的背后是每个模型的具体实例化。例如，我们的 Malibu 模型的推理会经由一个通用接口进入一个为 Malibu 推理特化的类。

虽然我们为每个模型都准备了专门的类，但要强调的是，这些类通常相当轻量。实际上，我们通常只是定义某个特定模型运行推理所需要的各个接口，然后把细节委派给另一个处理平台相关细节的外部类。下一节我们会谈实际如何处理不同的算力平台，这里先说明 Atlas 足够灵活，截至撰写本文时它能在 CUDA、ROCm 和 Trainium 平台上运行。眼下我们先把底层实现当成一个黑盒，于是就有下面这张图。

Atlas 还能够把我们的预训练代码库 Titan 作为依赖来使用。事实上，出于兼容性考虑，Atlas 的模型配置类继承自 Titan。我们要强调，只把 Titan 当作推理的唯一来源是不明智的：毕竟推理实现和训练实现差别很大，某些对推理有用的技术未必对训练有用。换句话说，一个操作的优秀训练实现，不一定是同一操作的优秀推理实现。但 Titan 让我们能够把 Atlas 的输出与一个已知可用的基线做对比，从而为我们的推理实现提供强有力的正确性保证。这一点在我们把新优化集成进 Atlas 时尤其重要，因为那时很容易不小心引入回归。

Atlas 可以用多种方式部署。一方面，Atlas 可以作为我们标准的、基于 Kubernetes 的部署系统的一部分，部署在我们的 worker 节点上。下文"在 Factory 中部署推理"一节会详细讲这套系统如何运作，这里我们先指出：这种部署方式让 Atlas 与 Model Factory 的其余部分结合得非常顺畅。另一方面，Atlas 也能作为独立包安装，这让我们可以在各种环境和配置下部署 Atlas。事实上，能在本地使用 Atlas 的好处并不只限于开发工作流：它意味着在我们的标准工具链不可用的环境里，我们也能部署 Atlas。

## Atlas 身在何处：跨平台优化推理

现在我们把注意力转向我们如何在不同平台上实现并优化推理。为了本节的目的，我们会同时讨论 GPU 上的推理和 Trainium 上的推理。要强调的是，这些只是示例；Atlas 足够灵活，能让我们把推理部署到各种各样的算力平台上。

如上一节所述，我们通常提供一个包装类来为某个特定模型提供推理。这种通用接口的一个好处是，我们能把平台相关的细节抽象掉。事实上，vLLM 里也能找到类似的做法，它用所谓的 `ModelForCausalLM` 类来表示模型。为了给这些类加上平台相关的能力，我们只需以平台特定的实现去派生包装类，每个子类都负责在该特定平台上运行推理所需的全部细节。然后我们根据 Atlas 部署所在的底层硬件，在运行时加载正确的子类。

现在我们谈如何在 GPU 上实现推理。CUDA 和 ROCm 在开源世界都得到了很好的支持：外部世界有许多优化好的 kernel，Torch 也为这两个平台提供了稳固的基线。然而，许多底层优化和硬件能力在开源世界里相当少见；毕竟新硬件一直在发布，但高性能 kernel 往往需要一段时间才会出现。而且外部世界的快 kernel 也未必充分利用了某个具体平台所提供的全部能力。为了利用这些能力，我们会定期为所针对的硬件平台编写自己的 kernel，从而让我们能够站在——甚至超越——推理性能的最前沿。考虑到我们很可能为每个平台准备不同的 kernel，我们把 CUDA 实现和 ROCm 实现分别包装起来，于是得到如下的高层视图。

Trainium 上的推理大体与 GPU 上的推理相似，只是有几处值得注意的差异。简单讲，Trainium 加速器遵循的设计策略与 GPU 不同；直白地说，Trainium 包含数量较少但强大的核心，而 GPU 通常由大量、相对较弱的核心组成。两种方案并无高下之分，各有优点和缺点。不过差异足够大，必须靠平台特定的实现才能把各自的潜力发挥出来。幸好这一点和我们的 GPU 方案是一样的，因此我们只需再产出一个包装类来实现 Trainium 推理。

从编程的角度看还有其他差异。值得注意的是，Trainium 执行工作负载时，先把一个所谓的计算图编译成可执行文件，然后在多次调用之间复用它。这带来几个好处：程序的完整视图对编译器很有用，但代价是控制流的决策通常是在编译阶段做出的。这让代码在设备上执行时呈现为直线程序，与 CUDA graph、HIP graph 的做法很相似。这其实给了我们一个机会：推理中几乎所有的控制流决策，都关系到我们是在跑最初的处理（即 prefill）还是在跑随后的 token 生成。由于这两个阶段的瓶颈不同，我们确实能从为 prefill 和 token 生成分别编写实现中获益。我们还通过用 NKI 编程语言编写自定义 kernel 进一步优化这一过程。总体上，所有这些决策共同让我们的模型在 Trainium 上取得了 state-of-the-art 的性能。

尽管我们为使用的每一种设备优化推理，但真要写出足够快的推理实现，还有其他方面需要考虑。比如，kernel 启动的开销可能超过 kernel 在设备上实际执行所花的时间，这是众所周知的。但较少为人知的是，这种行为是会波动的，尤其从主机 CPU 的视角看。事实上，很多事情都会导致推理性能不佳，比如 NUMA 亲和性配置不对，或者垃圾回收参数配置不对。鉴于这类问题相当普遍，Poolside 的推理团队花了大量时间做性能分析、优化整个系统的性能，而不只是设备端的性能。

除了 kernel 和 CPU 调优之外，Poolside 的推理团队还在为 Atlas 基准测试高层推理技术上投入大量时间和精力。同样要强调的是，这类工作大体是有条件的，很少有哪种优化能在所有情况下都带来收益。例如，前缀缓存在代码补全场景里格外出彩，因为多个请求很可能共享同一个前缀。但前缀缓存相比纯 KV 缓存需要额外的内存管理，所以前缀缓存也不一定总是合适。既然某些优化只在有条件的情况下才有用，我们会审慎权衡 Atlas 的每一次新增或改动，确保总体变化确实是正向的。

实现推理的另一个关键环节是保持正确性。事实上，尽管我们在整个 Model Factory 里都很有节制地使用单元测试和集成测试，Atlas 还是采取了额外的措施来防范潜在的回归。具体而言，我们给 Atlas 施加了比其他项目更高的测试负担，原因有两个。第一，Atlas 是我们客户工作负载的推理引擎，我们认为这个领域的 bug 是不可接受的。第二，由于推理在 Factory 中充当了那么多其他工作负载的载体，哪怕一个小 bug 的后果也可能很严重。我们要强调，这些后果不只是浪费我们的时间和金钱：一个 bug 还可能影响我们实验的结果，把我们引向错误的结论。为了大规模地防止回归，Atlas 在测试上采取了较为重手的方式。特别是，Atlas 包含若干针对 Model Factory 整个子系统的端到端测试：我们作为持续集成（CI）流程的一部分拉起完整的作业部署，并把任何结果与已知正确的取值做细致比对。此外，我们为我们支持的每个硬件平台部署不同的 CI 流程，从而确保一个平台上的推理不会被另一个平台的改动悄悄破坏。这套流程确实需要一些细腻的处理才能做好，但这里任何复杂之处，与它让我们在做出改动时所获得的信心相比都微不足道。

在我们转向实际如何部署推理之前，值得说说实现上的灵活性给了我们什么。首先，我们能够把 Model Factory 的推理需求和底层硬件解耦：不必只依赖 GPU，我们能把某些推理任务卸载到其他类型的硬件上。此外，Atlas 的灵活性也意味着我们能轻松适配新的客户环境和工作负载；我们只需把现有的推理代码适配到新平台，Atlas 的其他能力会处理好剩下的部分。

## Atlas 何时登场：在 Factory 中部署推理

既然已经了解我们在 Poolside 实际是怎么实现推理的，就可以开始讨论推理作为 Model Factory 的一部分通常是怎么使用的。

毫不夸张地说，推理驱动着 Model Factory 内部几乎的一切，也驱动着每一个使用它的人。首先，推理让我们能够快速地把模型放到范围很广的基准上做评测，从而让我们能够在训练期间和训练之后方便地判断模型表现如何。我们要强调，这是 Model Factory 至关重要的一环；如果缺少客观评判实验的能力，我们就无法准确解读任何结果。此外，推理让我们能够轻松地生成新的合成数据集、开展大规模后训练，以及运行大规模强化学习工作流。简单讲，如果没有一条便捷快速的推理路径，Model Factory 的产出会低得多。

上一节我们已经讲了如何在 Factory 内部快速地运行推理，所以现在我们来谈如何轻松地运行推理。大体而言，轻松地运行推理需要把三件事做好。一方面，我们需要一种管理模型部署和算力集群的方式：毕竟推理部署就是计算作业，所以要和 Factory 里其余的作业放在一起权衡。另一方面，我们还得让 Model Factory 的其他部分能够方便地调用推理，否则我们就没法把手里的资源用到最好。

要解释整套系统是怎么运作的，我们需要揭开 Model Factory 内部作业部署管理的面纱。毕竟我们不是只在集群上跑推理；我们还必须兼顾执行任何需要 GPU 的工作负载的能力。换句话说，我们需要对作业调度采取一种全局的视角。

大规模地调度作业是一件复杂的事；而且并非所有计算作业都同等重要。例如，一次大规模训练运行不应该被许多小规模的合成数据生成任务挡在后面；训练显然更重要。换句话说，我们需要能够按优先级来调度作业。此外，并非所有计算作业都能合理地标记为"已完成"。比如，我们可能在集群上部署一个内部模型来做 vibe checking，但这样的作业该在什么时候算作完成，至少从自动化的角度看不显然。也并非所有计算作业都应当事先要求固定数量的 GPU；vibe checking 可能永远只需要几张 GPU，但有些情况下我们就是希望一个作业尽快跑完。这意味着我们需要以某种方式把这件事编码进去：分配给某个任务的 GPU 数量可能随时间动态变化。而我们还必须小心，别让 GPU 节点变得碎片化：很容易一不小心就落到这样的境地——没有任何节点还有足够的空闲 GPU，除了极小的作业之外什么都调度不了。

为了实现所有这些能力，我们采用两层方案。首先，我们用 Kubernetes 管理底层节点，从而利用它自动（且可伸缩地）在我们规模达 10K 张 GPU 的集群上部署容器化工作负载的能力。不过我们并不是原封不动地使用 Kubernetes；我们还使用了一个名为 Volcano 的第三方调度器。Volcano 是一个开源的、被广泛使用的 Kubernetes 批调度系统，支持更高级的用例。例如，Volcano 支持通过 binpacking 把作业分配到节点，减少我们集群上的作业碎片化。Volcano 还给了我们强大的调度原语，比如全有或全无调度以及公平共享。不仅如此，

Volcano 还让我们能够通过多个优先级队列给作业排定先后，从而轻松地把某些计算作业优先安排。把 Volcano、Kubernetes 和 Dagster 一起用起来，我们还能实现更高级的功能；例如，我们可以把某些作业标记为静态的（即需要确切数量的 GPU）或动态的（即可以扩容到 GPU 数量的上限）。我们也有高级的作业生命周期原语。例如，我们用 Dagster 在部署被使用时自动更新该部署的 TTL，防止某些作业过早过期，某些作业可以被标记为可驱逐的，以便在有更紧迫的计算作业需要调度时进行抢占。我们的调度系统还支持 backfill，避免极小的作业被更大、存续时间更长的任务阻塞。

把调度的细节放在一边之后，现在可以讨论我们如何调度推理部署。答案很简单：我们调度推理部署的方式，和我们调度任何其他计算作业的方式一模一样。直观上讲，这是 Model Factory 中各层抽象如何叠合的一个推论——它们作为一个整体，作用大于各部分之和。就管理推理的基础设施而言，我们可以直接复用 Model Factory 其余部分已有的调度组件。具体来说，我们可以通过提交作业的方式把推理工作负载调度到我们的 GPU 节点上，这和提交其他任何工作负载没有区别，剩下的交给我们的调度器处理。此外，我们并不绑定于某一种特定的底层硬件；Atlas 是完全容器化的，因此我们可以轻松地把 Atlas 部署在任何兼容的节点上。从图上看就是下面这样。

既然知道了推理部署是如何被调度的，我们还需要决定实际怎么部署和提供推理服务。事实上这也很简单：我们只需指定一个 checkpoint 和一些工作负载细节。具体来说，我们可以部署一个 Atlas 容器，它在初始化时会自动下载指定的 checkpoint。实践中，我们可以通过三种方式之一来指定所使用的 checkpoint。在我们已有现成 checkpoint 的情况下，我们只需把 checkpoint 的标识符作为作业启动配置的一部分传给容器。然而我们也可能想在 checkpoint 还不存在时就启动某个工作流；例如，当我们在训练过程中运行评测时，在 checkpoint 产出之前我们并不知道它的标识符。幸好，Dagster 支持这种串联起来的工作流，让我们可以先物化一个 checkpoint 资产，然后把标识符自动传给后续的任何部署。最后，我们还支持把模型权重从用于训练的 GPU 直接传输到用于推理的 GPU，这被称为 GPU<>GPU weight transfer。我们会在接下来的一篇博文里讨论最后这种方式的细节，但眼下值得知道的是：它同样能严丝合缝地接入 Model Factory 其余的抽象。

部署完成之后，提供推理服务就相对容易了。具体来说，Poolside 有一个内部推理 API，负责 Model Factory 内部所有推理请求的路由与处理。值得注意的是，我们的内部推理 API 替我们管理了许多技术细节，例如支持推理副本，以及智能请求路由。我们的内部 API 还提供了若干附加功能，例如获取内部日志和上游 Dagster 信息的能力。

就这样！所有细节都处理完之后，我们只需在上游代码里指定想用的部署，就可以开始运行我们选择的任何工作流。一切都会自动跑起来。当然，每个工作负载具体如何与底层推理服务交互——就使用模式之类而言——取决于我们正在执行的具体任务。但在 Factory 里，这些统统能被轻松抽象掉。

在我们转向某个具体的推理用例之前，值得强调推理（以及围绕它的扎实基础设施）在多大程度上支撑着 Factory。如果我们每次都得手动部署模型，就几乎做不了自动评测；要是不时刻盯着基础设施，我们根本跟不上节奏。不过，让模型可以被方便地手动部署，同样让我们能够快速地对新生成的模型做 vibe check 看能力，并以低摩擦的方式跑临时实验。在大规模训练和强化学习工作流的场景下，这些好处只会继续复利叠加；事实上，很难想象一个没有自动且便捷的推理部署、还能跑我们当前这些工作负载的世界。

## 评测

在这篇博文收尾之前，我们讨论一下如何用 Atlas 和 Model Factory 来实现大规模的自动评测。

简单回顾一下，评测是一种判断模型在特定任务上学得如何的机制。具体来说，评测让我们能够判断模型在有价值的下游任务上表现如何；这也是外部世界通常使用评测的方式。但在 Poolside，我们还会以另一种方式使用评测：我们在模型训练的很早阶段就部署评测，用来把那些我们预期会助推下游表现的具体、基础的能力撬出来，例如数学能力或自然语言理解。直观上讲，我们希望模型在训练早期就表现出这些技能，因为它们是良好软件工程表现的前提：在训练早期获得并夯实这些技能，会带来一个在我们关心的任务上表现更好的模型。要想就模型在这些任务上的表现拿到强信号，我们需要在训练期间频繁地运行评测，而我们的规模化能力正是在这里真正关键。我们此前的博文提到过，我们运行着成千上万的数据实验和架构实验；如果不能准确、快速地评测这些实验，它们就会卡住我们继续实验和训练模型的能力。

尽管我们大量使用评测，但值得强调的是，没有任何评测是完美的。智能是多面的，没有任何单一测试能准确衡量智能——无论它是人工的还是别的形态。更重要的是，一个模型的质量在某种程度上是主观的，而造出一个人们乐于使用的模型，靠的远不止漂亮的基准结果。然而，规律地运行多样化且有代表性的评测，仍然能帮助我们理解模型在训练和实验过程中的表现与演化。挑选好的评测，既是一门科学，同样也是一门艺术——但这个话题我们留到下次再谈。此处我们聚焦于评测作为 Model Factory 的一部分是如何被运行和实现的。

我们要面对的第一个问题是评测本身应该如何实现。假设我们只考虑内部自研的评测（即不存在外部现成的实现）。这里我们有哪些选择？一方面，我们可以把评测实现为独立的脚本，原样执行评测并把结果推到某个仪表盘上。但这种方式谈不上严谨；毕竟单个的、没有版本管理的脚本很容易失控。另一方面，我们可以把每一项评测实现为 Model Factory 的一个独立部分，从而受益于我们在 Factory 里已经建好的那些抽象。根据我们的经验，复用这些抽象带来的好处并不止是代码复用。事实上，好的抽象往往带来更干净的代码，而我们发现 Model Factory 让我们更容易精确地隔离出某一项具体评测的运行方式。而且，我们能够利用已经深度优化过的组件，例如我们的推理服务。

事实上，我们会更进一步，把外部评测也用 Model Factory 的方式重新实现。这一点可能有争议，但收益很明确。确实，外部评测并不保证能接入 Factory；它们可能用不常见的编程语言写成，或者压根不支持大规模部署。事实上，Poolside 的工程师会定期把现有评测重写成 Model Factory 的原生部分。直白讲，我们把自己运行的所有评测都表达为 Model Factory 里的资产。这有多个好处。把评测表示为资产，意味着我们能更轻易地在多个实验之间重新调用评测；和 Factory 的其他部分一样，评测本身成为一个可复用的组件。此外，把评测当作 Model Factory 里的资产，意味着我们能为高级工作流利用 Factory 更广泛的整套机制。

我们放大看最后这一点，考虑下面这种情况。假设我们有一个庞大的评测框架，它没法接入 Model Factory，而我们想用这个框架来评测一个 checkpoint。首先，一个庞大的评测框架很可能需要大量 GPU 才能在某个 checkpoint 上跑评测。由于这个框架与 Model Factory 的调度器不兼容，我们就得手动分配 GPU，然后可能靠手工执行这些评测。哪怕实际上只有一项评测需要所有这些 GPU，也已经无所谓了：我们既然已经手动把它们分配走了，它们就不能再被别的东西复用。更重要的是，我们还得自己针对指定的 checkpoint 手动执行这个框架；即便我们在这里加上某种形式的自动化，和用 Model Factory 里的抽象所能得到的相比，我们仍然是在倒退。

现在看看 Model Factory 能帮我们做到什么。首先，我们把评测框架拆解为一个个独立的、Model Factory 原生的资产。这样我们就可以把每项评测当作各自可独立调度的作业；这意味着我们不需要一次占用大量 GPU，而编排器会替我们处理实际的调度。这种方式还有另一个好处：正因为各项评测是可独立调度的，我们实际上可以针对不同的 checkpoint 并行地多次运行同一个评测。这在我们的规模上之所以可行，全靠 Model Factory 内部的抽象；我们不必半夜醒来跑评测，Model Factory 把一切都替我们做完，第二天早上结果就准备就绪。于是得到如下的高层工作流：

关于评测该如何实现的讨论到此结束，接下来考虑我们怎么把评测接入 Factory。运行评测需要运行推理，因此我们要能快速拉起推理部署。幸好，我们已经有现成的路子：复用推理服务已有的抽象就能做到这一点。对于针对已知 checkpoint 的工作流，比如微调类工作流，我们前面讲过的那些抽象已经足够了。但对于在预训练过程中产生的 checkpoint，还有一块拼图要找：我们需要在 checkpoint 尚未产出之前就指定用哪一个。对我们来说幸运的是，Dagster 支持这类工作负载：训练作业只需向 Dagster 推送一个 checkpoint 已就绪的通知，推理作业就会被自动调度。如前所述，每项评测都被独立调度和执行，结果自动推送到一个 Neptune 仪表盘。这不仅便于查看，而且是完全自动的；通常不需要人工干预。实际上唯一需要人工干预的情形，是某项评测没能跑起来；不过解决这类错误通常比较简单，重新触发失败的流程通常也就是点一个按钮的事。

最后，我们要强调，以我们的这种规模和频率运行评测，如果没有 Model Factory 提供给我们的这些能力，根本是不可能的事。跨不同训练运行的不同 checkpoint 手动运行评测已经够有挑战了，而按不同频率对新 checkpoint 运行评测简直是噩梦。这还没算上需要为这件事预留宝贵的具备推理能力的节点，或者在不同 checkpoint 上跑不同评测子集这些任务；直白讲，我们几乎根本不会去尝试运行评测。相比之下，Model Factory 让运行评测变得如此轻松，我们简直没有理由不用它们——无论是在刚产出的 checkpoint 上，还是作为微调或强化学习工作流的一部分。
