# 最后的润色

**TL;DR：** 我们用这篇文章为整个 Model Factory 系列收尾，说明我们如何使用它来开展大规模后训练。具体而言，我们先讨论 Poolside 使用的两种后训练技术：监督微调（SFT）和强化学习（RL）。我们说明 Model Factory 如何支持编排大规模后训练工作负载，并以 SFT 和 RL 工作负载为例。最后，我们介绍我们为 Poolside 的后训练构建的两款工具：一个名为 Podium 的数据集查看器，以及 GPU<>GPU 权重传输。

## 引言

在本系列之前的文章里，我们讨论了 Model Factory 几乎每一个方面的内容。我们已经建好了一切所需，用来处理海量数据集、快速训练出色的基础模型、教模型写代码、评估特定能力，以及大规模提供推理服务。但要产出在真实环境中表现出有用能力的基础模型，还有更多事要做。更进一步，我们希望产出的模型具备的能力，超出了传统预训练单独所能赋予的范围。为了达成这些目标，我们需要采用一些额外的技术。

在这篇文章里，我们讨论在 Poolside 我们如何对模型开展后训练。具体来说，我们会考虑后训练流程的两个方面，即监督微调（SFT）和强化学习（RL）。我们先解释我们为什么要在模型上做后训练，并在这个过程中介绍 SFT 和 RL。然后我们讨论我们如何已经引入了编排和部署后训练工作负载所需几乎全部的部件，并以 SFT 和 RL 工作负载为例。最后，我们通过讨论我们为后训练工作负载构建的两套系统来收尾，即一个数据集查看器和 GPU<>GPU 权重传输。

在正式开始之前，重要的是要记住，尤其这一篇不应被孤立地阅读。事实上，Model Factory 系列的每一篇文章都在为这一篇做铺垫，因为后训练复用的是我们在系列更早部分已经引入的组件。这是有意为之：可复用的组件和大规模编排，正是 Model Factory 能成为打造顶尖基础模型的强大工具的两个主因。这里我们会聚焦于我们新加入 Model Factory、用以支持后训练工作负载的特性，以及我们如何编排已有组件来支撑这些工作负载的规模化运行。

我们开始吧。

## 我们为什么要做后训练？

先简要回顾一下基础模型训练。正如我们在本系列的[第一篇文章](https://poolside.ai/blog/introducing-the-model-factory)中所说，典型的基础模型训练始于构建一个用于训练模型的初始数据集。然后我们用那个数据集开展一段高强度的训练期，也就是预训练，产出一个训练好的基座模型。

基座模型虽然知识丰富，但通常并不擅长解决问题。因此，在预训练之后往往会做一些额外步骤，也就是后训练。后训练的目标是产出具备专门能力的模型，比如遵循指令，或者精通某些任务。本质上，可以把后训练看作这样一个过程：把一个基础的文本补全模型升级成一个能处理对话、使用工具、显式思考并解决各种问题的助手。由于我们希望在模型身上获得多种行为和能力，后训练可能分多轮进行，于是得到下面这幅图：

需要强调的是，不应把后训练仅仅看作预训练的附加品。事实上，要让模型在实践中真正可用、真正智能，后训练是必不可少的。举一个具体的例子：Poolside 的主要用例是产出在软件开发方面出色的模型。基座模型通常对语言语法和数学很有知识，但从基础知识到成为一名优秀软件工程师之间有着巨大的鸿沟。在人类身上也是如此：软件工程师需要大量的操作性知识和专业能力才能胜任。模型并无二致，一个好的基座模型与一个能在真实环境中充当有效编码 agent 的模型之间差别很大。因此，我们在后训练流程上投入了大量算力和精力，确保我们构建的模型在实践中真正有用。

我们来考虑两种不同的后训练形式：监督微调（SFT）和强化学习（RL）。在进入我们如何在 Model Factory 里构建这些工作负载之前，先简要说明 Poolside 如何使用 SFT 和 RL。

一方面，我们通常用 SFT 引导模型表现出可预期的行为，比如产出结构化输出，或呈现出某种「人格」。我们也用 SFT 为 RL 工作负载提供「热启动」。实践中我们遵循标准的 SFT 流程：构建一个 SFT 数据集，在预训练 checkpoint 上继续训练，然后保存得到的 checkpoint。而且，和我们的预训练工作负载类似，我们会在 SFT 实验期间定期运行评估，这让我们理解模型在 SFT 实验过程中如何变化。下一节我们会讨论运行 SFT 工作流的技术细节，但值得记住的是，真正的难点在于生成高质量数据集，而 SFT 所需的几乎其他一切在 Model Factory 中都已经实现。事实上，我们负责 SFT 的工程师和研究员会花大量时间人工检查并迭代 SFT 数据集，以确保它们的质量。我们会在后面一节讨论我们为此流程构建的工具（Podium）。

另一方面，当我们试图教模型表现出更长程的推理与智能时，通常会启用 RL 算法。例如，我们用通过代码执行反馈进行强化学习（Reinforcement Learning via Code Execution Feedback，RLCEF）技术来教模型推理并理解各种与软件工程相关的问题。重要的是，我们的 RL 工作负载重度依赖 Model Factory 的其他基础设施，因为它们既需要大量编排也需要大量算力才能成功运行。举个例子，我们的 RLCEF 技术要求我们摄取并处理大量任务、执行代码来解决这些任务，并根据反馈做出调整。这个过程不仅需要大量通用算力，还需要几乎不间断地访问一个高性能推理服务。

值得一提的是，我们在大规模异步场景下运行 RL。实践中这意味着我们把 acting 和 training 跑在不同的节点上，从而进入 off-policy 的 RL 工作负载。这主要是出于可扩展性考虑（也就是说，我们只有异步地运行 RL 工作负载才能高效扩展）。这要求我们在跑 training 的节点和跑 acting 的节点之间小心地同步权重。本文后面我们会概述我们为此使用的技术，即 GPU<>GPU 权重传输。

## Factory 已经能支撑后训练

现在来看看运行后训练工作负载需要什么。非常简单：

`sft_asset = model_asset(model_name=”sft”, job_config={...}, ...)`

就这样。我们只需要一个合适的配置文件，其余的交给 Factory。

这段描述看似非常简短，但重点正在于此。在本系列走到这一阶段时，我们的观点是：工作负载的具体细节几乎无关紧要。在我们看来，Model Factory 的主要优势是它实现了跨多种规模的工作负载自动化端到端编排。Model Factory 里有很多有用的组件，没错，但组件只是更大拼图的一块块碎片。真正的好处在于，Model Factory 提供了以容错且可复现的方式自动调度并编排任意复杂系统的机制。如果没有这些自动化机制，即便我们保留其他所有组件，Model Factory 对我们而言都会远没有那么有用。换个说法，Model Factory 的各个组件之所以价值超过其部分之和，是因为我们实现的自动化，而不是反过来。事实上，我们的后训练工作负载几乎完全由此前介绍过的 Factory 组件支撑起来；为了让它跑通，我们只需要额外构建少数几样东西。换句话说，正因为 Model Factory 的结构，我们几乎是免费获得了开展大规模后训练工作负载的能力。当然，有时我们确实需要为某些任务或某些体验上的改进构建新组件，但最终这些组件通常是有益的补充，而不是前置条件。

在深入每种工作负载的细节之前，值得进一步说明我们在 Model Factory 里如何组织实验。虽然本系列早前的文章已经提过，我们所有的实验都基于配置文件。这些配置文件有两种产生方式：手工编写的原始 Markdown 文件，或在 Model Factory 内部以编程方式生成。值得注意的是，这些 Markdown 文件允许我们指定实验每一个部分的细节。一方面，它们允许我们指定各种参数和细节，从学习率到 GPU 数量。这些构成了我们实验性工作负载的基础，而其轻量的结构让我们无需再费力搭建复杂的新配置文件，就能很容易地启动新实验。另一方面，配置文件里还指定了某次实验应当使用的确切镜像。这意味着我们所有实验都是完全可复现、可重复的——确实，除了硬件故障的情况，从同一份配置启动的运行我们应当得到完全一致的结果。而且因为我们是基于确切版本启动的，当 Model Factory 更大范围的其他部分发生变化时，我们的实验通常只需极少的改动。当我们把这一点与 Dagster 中更广泛的系统结合起来，就得到了相当了不起的东西：一份在 Poolside 运行的每个实验的完全可复现的记录簿。以我们的经验，以这种方式用 Dagster 带来巨大的沟通收益。例如，在 Dagster 里分享进行中的实验，比我们还没建好 Model Factory 之前容易得多。而且因为所有人都能看到实验，就不存在孤岛：团队里每个人都能看到并询问你的实验。这种对协作的侧重也意味着我们把可复用代码放在优先位置，从而减少了一次性脚本和一次性流水线。在我们看来，这是 Model Factory 最好的地方之一：当所有人都优先构建强健、可复用的组件时，收益会复利累积，最终把事情正经地建起来反而比东拼西凑更省事。

## Model Factory 中的 SFT

我们现在来看 SFT 工作负载。如前所述，SFT 与预训练非常相似：我们把数据集流式送入若干训练节点，运行一类训练式工作负载，运行自动化评估，最终把新产出的 checkpoint 存入存储服务。所有这些步骤都由我们此前介绍过的 Factory 部件支撑。确实，数据流式传输由我们的数据混合与流式平台（Blender）提供；训练用我们的分布式训练代码库（Titan）执行；评估由我们更大的评估系统处理。我们甚至可以复用现有的调度基础设施来部署 SFT 工作负载。而运行实验的流转方式和 Factory 其余部分相同：研究员只要新建一份配置文件或 fork 一份旧的就能跑新实验。然后，一旦他们确定配置并在 Github 上合并，我们的 CI runner 会在 Dagster 里自动调度并编排由此产生的任务。当然，这些工作负载也会用到我们其他 Model Factory 工具，比如日志和指标流；而所有任务优先级与调度都由 Volcano 和 Kubernetes 干净利落地处理。这一切加在一起，就得到 SFT 流水线如何映射到 Model Factory 组件的如下高层图景：

## Model Factory 中的 RL

我们的 RL 工作负载同样受益于 Model Factory 整体的成熟度。确实，尽管运行 RL 工作负载相比 SFT 需要额外的组件——例如 actor-critic 循环、奖励模型基础设施，甚至异步 RL 工具——其余部件都已就位。这不该令人意外：毕竟 Model Factory 是一个编排复杂 AI 工作负载的通用系统，后训练只是一个具体案例。事实上，尽管 RL 与 SFT 有差异，运行实验的步骤是一样的：研究员创建新的配置文件并构建任何新资产；之后我们要做的只是在 Dagster 里触发相应的工作流。其他一切，从调度到日志，都由 Model Factory 中我们已经介绍的组件处理。

作为示例，我们讲讲如何运行 RLCEF 工作负载。回顾一下，RLCEF 是我们用来通过强化学习教模型解决各种软件工程任务与问题的技术。我们通常把 RLCEF 拆成两部分：一个解决问题的 actor，以及运行训练式工作负载的节点。更详细地说，我们的 actor 通常从数据存储读取输入数据，然后尝试解决输入数据上的任务。actor 随后通过奖励机制进行学习，并把它们的会话记录送入 Blender。最后，训练节点从 Blender 读取会话记录，在产出的数据上学习。

上面所需的一切都由我们的 Dagster 集成来编排和处理，所以我们要做的只是实现 RL 算法本身。实际操作中，我们把 RL 算法作为 ModelFactory 内独立的部件来实现，只需在实验的配置文件里指定要用哪一个。事实上，Model Factory 的 RL 部分已经变得足够庞大，几乎像一个自己的「子工厂」在运转：我们拥有一切组件，从 GRPO、PPO 这样的算法，到 actor-critic 循环以及各种工作负载定制。而每个组件都是围绕 Model Factory 中其他久经测试的组件构建的；例如，我们的 RL actor 都通过可扩展的 Task Engine 调用代码执行，这让我们能同时处理数千万个并发任务。

总之，能够复用 Factory 组件带来的收益再怎么强调都不为过。Poolside 的研究员和工程师不把时间花在手工跑基准或编排数据流水线上；他们把时间花在思考如何改进 Poolside 的模型上。而且，因为 Model Factory 是按可扩展系统构建的，一切都行得通——哪怕我们必须换掉某些组件。我们只需要构建自己需要的单个组件，Factory 的其余部分会确保一切正常运转。

## 我们专为后训练构建的东西

现在我们已经看到 Model Factory 如何支撑后训练，接下来谈谈我们专门为后训练加入 Factory 的一些东西。在深入细节之前，值得强调这些组件遵循与 Factory 其余部分相同的原则，而且我们在此讨论的系统都不局限于后训练。事实上恰恰相反：我们即将讨论的两个组件都已经在后训练之外找到了实际用例。

## Podium，我们的数据集查看器

如前所述，我们在 Poolside 会花大量时间人工检查微调数据集，确保它们是高质量的。这部分原因在于，生成某个微调数据集时很容易引入难以察觉的 bug。例如，为了产出结构化输出（比如 JSON 或 XML）而对模型做微调是很常见的，但如果没有合适的工具来检查数据集，这些 bug 很容易漏掉。检查数据集还能带来更多洞见。例如，检查微调数据集能形成关于如何生成微调数据集的良好直觉；确实，通过看到哪些生成方式成功了，我们能提升未来生成新数据集的能力。同时，检查数据集也让我们能提升数据集的质量：我们对哪些数据集好、哪些差会有很强的感觉。这有一个直接的好处：如果我们在某个特定的高质量数据集上微调，而模型质量没有提升，那必定是微调方法本身有问题。

为了检查微调数据集，我们构建了一个内部工具，叫 Podium。Podium 让研究员加载特定数据集、生成新样本并查看结果。底层实现上，Podium 支持从我们的 Dagster 加载整张 Apache Iceberg 表，这给了我们对数据集近乎无可比拟的洞察。实践中我们发现 Podium 在三个方面帮助我们。第一，Podium 让可视化复杂数据集变得直接，让我们容易发现畸形样本并修复 bug。这在结构化的输入输出或其他复杂情况下尤其有用。第二，Podium 让我们在扩大生成规模之前先在小数据集上迭代；坦率地说，在一个注定产不出好数据集的方法上浪费大规模算力毫无意义。最后，Podium 让我们看到模型随时间如何演变：因为我们可以针对任意 checkpoint 生成新样本，Podium 让我们很轻松地看到模型因微调而发生的变化。

和 Model Factory 的其余部分一样，Podium 现在也被用于多种原本没打算过的用途。例如，我们最近扩展了 Podium 以支持检查自定义样本，让任何参与 vibe checking 的人都能快速给出某些模型表现糟糕的 prompt。通过这样的扩展，我们让系统性地收集关于模型表现的主观反馈容易得多；换句话说，我们更容易说明我们觉得某个模型应当在哪些地方改进。这也意味着我们可以轻松构建新的内部评估，把新的核心能力建进我们的模型里。

## GPU<>GPU 权重传输

在为整个系列收尾之前，先讨论 Model Factory 在 RL 工作负载中被大量使用的其中一个组件：GPU<>GPU 权重传输。

回想一下，我们的 RL 工作负载通常分为两部分：actor 组件和训练组件。因为我们大规模运行这些工作负载，必然需要以 off-policy 模式运行 RL 工作负载。然而，鉴于 off-policy RL 可能导致模型质量不佳，我们需要一个方案来快速同步用于训练和用于 acting 的节点之间的权重。为了便于讨论，我们会从「把权重在训练与推理之间移动」的角度谈权重同步，因为正是在这里最终需要快速同步。

首先，我们可以在训练和推理中使用同一批节点，但这让扩展变得困难。我们不仅必须同时决定训练和推理各自的节点数量，而且无法独立扩展任一工作负载。如果增加推理工作负载的节点数，我们就必须同时为训练投入更多节点，不管是否真的需要。就算我们设法接受了这个限制，还得处理这个方法带来的其他问题。例如，训练与推理通常不会使用相同的 mesh，因此无法保证每个训练节点都持有无需网络活动就能在同一节点上做推理所需的正确张量。当然，我们可以通过 AllGather 在网络上传输张量，但这会实质性影响训练并导致内存占用上升。换句话说，从 Model Factory 的角度看，把推理和训练同机部署根本行不通。

虽然我们本可以复用 Model Factory 的大规模存储系统，但有个更明显的办法。直觉上，我们希望能有一种方式，直接把权重从用于训练的 GPU 传到用于推理的 GPU，不需要任何中间步骤。这个做法——我们称之为 GPU<>GPU 权重传输——在 RL 社区的各类 RL 工作负载中已被广泛使用。在我们这里，区别主要体现在规模上。事实上，要让 GPU<>GPU 传输对我们管用，我们必须能极其快速地传输权重，因为这关系到尽可能贴近 on-policy。而且，我们要做到这一点而训练或推理都不出现明显 slowdown；否则我们根本享受不到性能提升带来的好处。

为了确定 GPU<>GPU 传输在实践中究竟是不是我们能用的东西，我们开始更仔细地研究我们的 P5e 节点。不了解的话，P5e 节点是配备 8 块 Nvidia H200 GPU 的 AWS EC2 实例，每个 P5e 节点通过其 EFAv3 网络结构提供约 3200Gbps 的总网络带宽。值得注意的是，P5e 节点还提供 GPUDirect RDMA 能力，这是一种让 GPU 之间快速访问彼此内存而无需 CPU 参与的方式。这 3200Gbps 的网络带宽相当可观。毕竟，即使是 bfloat16 精度存储的 Llama 405B 也只有 810GB，所以在全速利用下我们大约 2 秒就能传完所有权重。这看起来很有希望，但它真是能用起来的吗？

答案是可以。下面说明我们是怎么做的。

首先，把训练和推理同机部署的朴素做法需要执行一次 AllGather 操作。AllGather 非常灵活，但有更好的办法。我们只需要找到一种方式，告诉参与 acting 的那些 GPU 要把权重直接发到哪里。最简单的场景是我们想做一对一传输时。可以把这个场景想象成从左侧的 `n` 块 GPU 发到右侧的 `n` 块 GPU：权重之间存在严格的一对一映射。

这种情况下，我们可以直接利用 NCCL 已有的点对点原语来传输数据，在设备之间直接发送。不过这已是最简单的可能情况；毕竟我们可能要从左侧的 `n` 块 GPU 发到右侧的 `m` 块 GPU。例如我们想试验量化推理时就可能这样：训练需要 2 块 GPU，而推理只要 1 块。稍微把视角拉远，我们甚至可以想象左侧每块 GPU 需要向右侧每块 GPU 发送不同分块的情形，这需要更复杂的方案。

我们要怎么在一般情况下解决这个问题？诀窍在于定义一个抽象拓扑，由它替我们处理这些细节。直觉上，我们只需要一种方式告诉左侧任意 GPU 要向右侧每个节点发送什么。这是个已被解决的问题——MPI 实现对类似技术已经支持多年——但我们仍需为 NCCL 实现这样的方案。我们注意到，实现这样的方案相当复杂，即使它讲起来很直观。我们需要处理训练和推理可能有不同 mesh 这一事实；两者之间未必存在直接的一对一映射。事实上，有时不同的张量需要以不同方式分布。例如，expert parallel 的张量需要遵循与构成 attention 块的张量不同的路由策略。而且，即便采用同样的扩展方式，比如张量并行，我们在微调中使用的 GPU 数量也可能与推理时不同。这些细节加起来是大量的工程工作，但我们最终有了一个满足我们所有标准的方案。关键的是，GPU<>GPU 权重传输现在只是 Model Factory 里又一台机器，我们可以用它来完成各种任务。

即使在典型的工程工作之外，也值得强调：实现 GPU<>GPU 传输在我们这样的规模上其实是一项极其复杂且脆弱的任务。从软件角度看，强烈需要确保集群里所有节点的软件版本完全一致；哪怕只是 NCCL 库这类细微的不匹配，也可能导致难以诊断的 bug 和问题。此外，我们在实现 GPU<>GPU 传输时经常遇到死锁。这些死锁原因各异，从 send/recv 顺序不匹配到跨 stream 的资源争用。例如，我们需要为 NCCL 里所有的收发连接加上 warmup，否则它们会在之后失败。所幸我们把这些都解决了，但代价是许多小时的调试。这一点尤其值得停留：根据我们的经验，调试 GPU<>GPU 传输的反馈周期异常地长。这主要是因为规模。确实，我们发现在较小规模机器集合上的稳定性并不能指示更大规模机器集合上的稳定性，因此我们必须在数千块 GPU 上跑很多测试。由于故障主要是非确定性的，我们花了很多时间等待故障出现，然后才能深入排查。

收尾之前，我们谈谈在 Model Factory 的语境下 GPU<>GPU 传输给了我们什么。打个比方，GPU<>GPU 传输就像在我们的训练高炉和推理机器之间装了一条传送带。以前我们得把权重卸载到相对慢的存储系统上；现在 GPU<>GPU 权重传输让我们能在微调与推理之间快速移动权重。值得注意的是，我们对 GPU<>GPU 权重传输的实现实际上是完全异步运行的，让我们在等待权重到达推理节点期间继续训练。这种高效传输对其他工作负载也极其有用：例如，我们可以利用 GPU<>GPU 权重传输按需快速拉起新的推理副本，而不必从大规模存储系统取模型权重。事实上，和 Factory 其余组件一样，应当把 GPU<>GPU 权重传输看成一个更大、完全编排起来的系统中又一块部件，它的用途非常广泛。
