## 我们发布了 Laguna 家族的头两个模型 Laguna M.1 和 Laguna XS.2，以及我们用来训练和运行 agent 的运行时，它们通过两款处于 preview 阶段的产品体验对外提供。

Laguna M.1 来得更早，在去年年底完成了预训练；它是我们在整个家族里构建其他一切的那个底座。Laguna XS.2 是一个小得多的模型，但相对于它的规模来说能力强得惊人，它也是我们第一次开放权重。两款模型都可以通过我们的 API 以及在 OpenRouter 上限时免费使用，而 Laguna XS.2 的权重也以 Apache 2.0 许可证提供。

Laguna XS.2 和 Laguna M.1 是为长周期工作打造的 agentic coding 模型。到目前为止，我们一直专注于把能力过硬、可以部署进最高安全等级环境的模型，交付给我们的政府和公共部门客户。而且，尽管我们对这些客户的承诺始终不变，我们现在已经准备好把我们所处的位置向全世界分享。我们同样很高兴把 Laguna XS.2——我们最新一代的模型——的权重释放给开放生态，用来支持构建者和更广泛的研究社区。

我们正在朝能够支撑更有能力 agent 的模型努力；并且我们相信这条路必须穿过 coding 能力，以及越来越长周期的任务。创造软件是许多其他能力得以表达出来的那项核心技能。

如今，大多数 agent 通过 tool calling 与世界交互，而结构化的接口会把 agent 限制在一组事先定义好的固定动作上。我们认为这是一种过渡期的形态。软件是一个远为富有表达力的接口。一个能够编写并执行代码的 agent，可以组合动作、把工作并行化，并自行搭起临时的系统来与世界交互。

这些模型是我们 Applied Research 组织大约 60 人共同工作的成果，覆盖架构、数据、预训练和强化学习。我们很高兴把这些工作带到这个世界上，并看看社区用它造出些什么。

## 模型构建

我们所有的模型都是从零开始训练的。这意味着我们自己的数据工作、我们自己的训练代码库（Titan，我们在[这篇文章](https://poolside.ai/blog/titan-the-model-factory-s-furnace)里讲过它），以及我们自己的 agent RL 基础设施。Laguna 把这套技术栈推到了极限，尤其在三个领域：包含合成数据在内的数据管线、我们如何优化 Muon 优化器的效率，以及我们的异步 on-policy RL 方案。

### 数据与自动混合

Laguna M.1 和 XS.2 都是在 30T 以上的 token 上训练的。要达到那个规模，并在训练中把它用出成效，就必须把数据的生成、处理、筛选和混合都推到极限。

#### 大规模网络数据

我们在构建和筛选数据集上极为用心。我们把网络数据的筛选看作质量与多样性上的联合优化。我们把质量建模成一个连续的、多维的信号，用一个综合分值来给数据排序，并且在整个技术栈里大量使用模型来获取质量信号。关键在于，我们并不是只保留最高质量的数据。我们发现那样会偏向 STEM 和推理，所以我们保留中、低质量档位中的一部分来守住多样性，而多样性对泛化能力至关重要。

与那种为短 token 周期做优化、只追求精度的管线相比，这一做法在保住性能的同时，多带来了约 2× 的唯一 token。当扩展到更长的训练周期时，这份收益依然存在，这也凸显出与质量并重的多样性有多重要。

我们还做了一次细致的去重分析，并印证了 FineWeb 的假设：全局去重会以不成比例的方式移除高质量数据。通过让全局去重与快照去重之间的质量分布对齐，我们得以进一步缩小下游性能上的差距。

#### 合成数据

为了把自然的网络数据补齐，我们用合成数据在那些其他手段难以控制的维度上补强训练配比。在 Laguna XS.2 中，它在所有预训练阶段里大约占最终训练配比的 13%，是在 organic 数据之上做叠加而不是取而代之，并在后者力有不逮之处加以扩展。Laguna 系列使用了约 4.4T 以上的合成 token。

为了在预训练规模下保住多样性和有效性，我们的工作横跨在 seed-heavy 与 pipeline-heavy 两端之间的谱系上。在 seed-heavy 那一端，我们把内容重排成多种格式（Q&A、结构化列表、对话等等），让信息的呈现方式规范化，好让模型从多个角度看到有价值的产物。在 pipeline-heavy 那一端，我们进入特征抽取与重新组合，把隐含的推理、结构和关系显式化，并用新的形式和语境把它们教给模型。

我们也把合成生成扩展到狭窄的高信号领域之外。除了 STEM 和代码，我们还把这些管线用在更宽的数据配比上，在扩大覆盖面的同时保持较高的、有扎实依据的信号密度。

我们的做法被设计成融入更大的训练生态，聚焦于稳健性，让合成数据在整个训练过程中更早、也更持续地发挥作用。

#### AutoMixer：数据配比优化

数据的筛选、以及进入训练的那个配比，对最终的模型性能影响极大。我们开发了一套自动混合框架，用来系统性地探索并优化预训练数据配比。automixer 每次运行都不再依赖人工启发式，而是训练一群约 60 个规模足够大的代理模型，各自使用不同的数据配比，并在关键的能力组（代码、数学、STEM、常识）上度量表现。基于这些运行，我们拟合出代理回归器，用来近似数据集比例的变化如何影响下游评测。这就给了我们一个从数据配比到性能的、学出来的映射，我们可以直接对它做优化来提出改进后的配比。这一做法受到 Olmix、MDE 和 RegMix 等近期工作的启发，但针对我们的场景做了改造：用更丰富的数据分组，并在一个较强的先验周围做受控探索，以适配紧张的代理模型预算。

学出来的信号既符合直觉，又有信息量。代码性能强烈地由合成来源和经过筛选的代码来源驱动，而通用的网络数据往往会拖累它。数学性能主要从多样的网络数学数据中获益。STEM 知识与学术类和教育类文本相关。重要的是，回归不仅还原出这些符合预期的关系，还提供了远为细粒度的视角来看各个子集是如何贡献的，从而支持更精确的取舍。为了避免平凡的解（例如过度押注在某一个高信号来源上），我们把优化向一个基线配比做正则化，并模拟目标的重复率。

当扩展到明显更大的模型和更长的训练周期时，相对于那条由一系列独立且代价更高的消融实验得到的强先验基线，优化后的配比在目标能力上——尤其是代码和数学——带来了可观的收益，并且没有损害在留出基准上的泛化。

### Muon

在 Laguna XS.2 和 Laguna M.1 的所有训练阶段里，我们都使用了 Muon 优化器的一个内部分布式实现。在最初的预训练消融中，我们只用了大约少 15% 的步数，就达到了与 AdamW 基线相同的训练 loss，最终模型上的评测还有大幅的绝对提升，同时还做到了跨模型规模的学习率迁移。

与许多其他优化器相比，Muon 会带来可观的计算开销，我们通过把计算分布到各个 rank 上来应对它。从高层看，Muon 需要把梯度聚合进一个 momentum buffer，对梯度施加 Nesterov momentum，通过 Newton-Schulz 对梯度做正交化，再用正交化后的梯度来更新参数。朴素做法下，每个 rank 都得对每一个完整参数把这一整套都做一遍。我们的实现把每个参数和梯度只分配给参与其分片的 rank 中的一个，在那个 rank 上收集完整的参数和梯度，执行 Newton-Schulz，然后把对应的、已正交化的梯度分片重新分发回组内所有其他 rank，由它们各自更新本地的参数分片。这样实际上就消除了 Muon 优化器的计算瓶颈，代价是额外的通信。

我们的实现把批量化通信与 Newton-Schulz 计算重叠起来。Muon 还有一个额外的好处，就是相比 AdamW 内存需求更低，因为每个参数只需要一份状态而不是两份；这一点在 checkpoint 的保存和加载上同样有益。我们还支持为 Newton-Schulz 过程启用 CUDA graph，以降低在正交化过程里启动许多相对小的 kernel 所带来的 CPU 开销，这对较小的模型尤其有利。得益于以上这些，在 Laguna M.1 的预训练期间，优化器带来的开销不到训练步耗时的 1%。

由于更新和计算会在各模型副本（也就是 DDP rank）之间复制，我们对模型权重做了周期性的哈希校验，以断言所有副本持有完全相同的权重。这些校验主要用来捕获由有缺陷的 GPU 造成的静默数据损坏（SDC）；具体来说，是起源于算术逻辑与流水线寄存器的那些错误，它们与 DRAM 和 SRAM 不同，不在 ECC 保护的覆盖范围之内。哈希校验同时也验证我们分布式训练实现的正确性，防范数据竞争、集合通信 bug 以及副本之间的发散。

### Agent RL

为了让我们的模型在长周期 agentic 任务上表现出色，我们构建了一套完全异步的 online RL 系统，它在训练循环内部使用我们的 agentic harness，跑在大量贴近现实的端到端软件工程、terminal 以及工具集成推理任务上。

我们的 RL 技术栈是一套自研系统，把几个主要组件松耦合在一起：推理与 rollout 生成、代码执行沙箱的编排、轨迹打分、缓冲与过滤，以及分布式训练。

从高层看，循环里的一次往返是这样的：trainer 发布一个新的 checkpoint，它被部署到我们的推理集群上。Actor 进程从数据集中拉取任务，拉起沙箱容器，并用刚刚部署好的模型针对每个任务运行我们的生产版 agent 二进制。产出的轨迹被打分、过滤，并写入 Iceberg 表。trainer 持续消费这些记录，并产出下一个 checkpoint。推理和训练以异步方式并行运行，两者的吞吐经过调配，用来平衡 off-policy 的过期程度。我们的模块化做法帮助我们在每个组件上快速迭代，也能方便地替换组件来试验新想法。

#### 面向长周期任务的异步 rollout

现实的软件工程任务会在很长的时间跨度里牵涉数量极大的 tool call：读文件、跑测试、迭代一个 patch、重跑整个测试套件。如果 trainer 必须等齐一整批轨迹才能迈出一步，那么 GPU 在一天的墙上时间里绝大部分都在闲置，而长轨迹在训练数据里的占比也会被系统性地压低。

我们采用完全异步的布置。Actor 和 trainer 各自独立运行，轨迹经过一个队列缓冲，其中显式地把关限制一次 rollout 允许落后当前 policy 多远。Actor 持续针对最新的 checkpoint 生成数据。trainer 按自己的节奏拉取记录，并有一个可配置的参数来控制最大的 off-policy 程度。

为了在 trainer 和推理之间同步 checkpoint，我们基于 GPUDirect RDMA 开发了一套自定义的权重传输方案，它让我们在几秒之内就能传输数百 GB 的权重。对于 Laguna M.1，我们可以在训练与推理之间跨节点、在 5 秒内传完 BF16 权重。

在长 rollout 期间，训练往往已经推进到了一个新的 checkpoint，这是常事。遇到那种情况，我们以吞吐为优先，在不打断正在进行的推理请求的前提下更新推理模型。为了进一步优化吞吐，推理侧支持以 FP8 运行模型权重和 KV cache，即使训练是在 BF16 上。我们把同一个 agent 发出的所有请求路由到同一个推理副本，从而让 KV cache 能跨轮次复用。

#### off-policy RL 下的训练稳定性

我们把 RL 管线针对规模和吞吐做优化，这使得训练在某种程度上是 off-policy 的。off-policy 程度有几个来源：过期的模型参数、非确定性的 kernel，乃至推理与训练之间数值精度上的不匹配。其中过期这一点尤其属于设计使然。推理模型和训练模型之间在训练步数上的差距，是按经验调出来的，用来在数据新鲜度和系统吞吐之间做平衡。

一个常见的、会导致 off-policy 的问题，是数据从 rollout 生成一路接到训练的那种衔接方式。朴素的实现会对数据重新 tokenize，从而造成 token 表示上的不一致。我们的 actor 反其道而行，被设计成 token-in、token-out 的方式，token ID 在整条轨迹的多个 agentic 轮次之间都保持不变。

为了在 off-policy 状态下稳定训练，我们使用了 CISPO 算法的一个变体。我们的 RL 运行在长达多日的训练中保持稳定并持续取得性能提升，而不需要熵正则这类额外的稳定性手段。
