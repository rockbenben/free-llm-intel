# 基础模型建设背后隐藏的工程

## 介绍 Model Factory

**TL;DR**：传统的基础模型训练方式需要大量人工介入，改进信号稀少，迭代速度也慢。为了解决这些问题，我们构建了 Model Factory——Poolside 内部的系统框架，用来快速训练、放大规模，并试验新型基础模型。在这篇文章里，我们分享构建 Model Factory 的方法论与背后的思考。

## 引言

AI 的世界正处在一次寒武纪大爆发之中：新的模型、想法和技术每天都在涌现，想要跟上节奏本身已经成了一份全职工作。新想法凭直觉被提出，部署在超计算机规模的集群上，并被推进生产环境，而与之配套的理论远远还没跟上。这样的推进速度给追求 AGI 的公司带来了一个严峻的挑战——具体来说就是：我们如何把自己的评估、采纳和部署这些创新的能力也扩展得足够快，快到足以保持领先？

组织通常沿两条轴扩张：靠人扩张，以及靠工程扩张。招募顶尖的工程师和研究人员可以拓展可能性的边界，但多招工程师至多只能让生产力线性增长。相比之下，AI 的前进速度至少是指数级增长的；线性增长根本不够用。换句话说，若不带来实质性的生产力提升，光靠不断招更多的工程师和研究人员，我们没法保持领先。这一要求与传统那种线性的模型训练方式相冲突——过去，大量工程时间通常都被花在手动处理训练任务上。

从 Poolside 成立的第一天起，我们就知道自己需要更多东西：一种能跟上我们想法产生速度的办法。我们需要能够自动测试新想法、拿它们和可靠的基线做基准对比，并带着信心和速度把新模型跑起来。我们需要能把结果的变化追溯到早前的决策，需要能轻松地进行超参数搜索，还需要把严谨性和可复现性重新注入我们的模型训练。我们甚至需要一种公平的方式，在 GPU 集群上调度所有这些相互竞争的任务。

我们需要的是一座模型工厂。而既然这样的东西并不存在，我们就自己造了一座。

在这个博客系列里，我们会带你深入参观 Poolside 内部用于训练基础模型的系统框架，我们叫它 Model Factory。我们会展示这座工厂的布局、它所要解决的高层目标，以及它完整的流水线。我们会深入讲我们怎么使用它、它由哪些机器构成，以及我们如何接入新的机器。我们也会聊一些为了把机器串联起来而造的传送带，比如 GPU 到 GPU 的权重传输。我们甚至会谈到一些我们试过、但最终放弃的想法，比如完全自动调优的矩阵乘法。

但首先，让我们从这几个话题开始：Model Factory 是怎么来的、它让我们能够做什么，以及我们在底层是怎么给它供能的。

## Model Factory 导览

为了解释 Model Factory 为什么能让我们应付组合式的复杂度，我们得先理解它是如何演化来的，以及这段演化如何造就了它今天的设计。为此，设想这样一个场景：我们想尽可能最优地训练一个基础模型。

### 第一轮迭代：传统的基础模型训练

作为第一次近似，我们先在一个预先确定的数据集上训练一个预先确定的架构。为了简单起见，我们沿用常见的模型训练做法：从数据存储里加载数据，跑模型的前向传播，计算损失，跑反向传播，重复这个过程直到把所有数据处理完。模型训练完成之后，我们再施加微调，为模型加上基本的指令遵循能力。这样就得到一条大致像这样的流水线：

### 第二轮迭代：自动化的模型评估

再看一下我们此刻的流水线。我们首先缺的是一套严谨的方法，用来自动评估模型在某些下游任务上的能力。用户反馈当然是王道，但它并不适合用来获取预训练规模的洞察。虽然评估基础模型能力的基准有很多，但在这个阶段我们并不需要定下具体用哪些评估；我们只需要引入一种方式，按固定的（可调的）间隔来评估我们的模型。理想情况下，我们还希望能针对不同的训练任务调整所用的评估项。我们甚至可以再往前走一步，去评估模型的质量在预训练过程中是如何变化的，而不只是在微调期间。带着这些考虑，调整后的流水线大致变成了这样：

### 第三轮迭代：从代码执行中做强化学习

有了评估系统之后，我们可以进一步思考怎样改进我们的模型。人类学习和成长的途径之一就是外部反馈。同样，我们可以超越下一 token 预测，用典型微调方法之外的、大量使用强化学习的技术来提升模型能力。这条路子要求我们把强化学习当成头等大事来对待；如今我们已经实现了一套独立的、模块化的强化学习系统，其中包含多种强化学习技术（并且同时支持同步与异步强化学习）。

我们这套模块化的强化学习系统还包含若干 actor 组件，我们可以把它们动态实例化进自己的工作流里。这带来的直接好处是：我们能在不改动 Model Factory 周边机器的前提下，拉起新的 agent 和 reward。

此外，我们还投入了大量精力，为基础模型搭建了一个安全、隔离的代码环境，让模型在其中自我博弈和探索。这个环境包含大约一百万个公开仓库（以及它们的绝大部分历史版本），每个都连同可执行的测试套件一起容器化，供我们用来改进模型。任务本身通过一个高可扩展的专用任务引擎分发给我们的强化学习算法，从而能够轻松编排数以百万计的复杂 agent 工作流并行运行。任务引擎本身非常通用，也适用于在线强化学习的负载。把任务引擎和我们的代码执行环境结合起来，我们就能够教会 agent 工作流去处理真实世界的软件开发。

### 第四轮迭代：自动化的架构消融实验

现在我们可以把注意力转到如何试验模型架构上。显然，在架构上做实验会带来模型性能上的变化。毕竟，模型的架构会强烈影响它在某个任务上的表现。不过，改动模型架构也伴随着一些艰难的取舍。一方面，模型的各个方面并非完全由技术性能决定：举例来说，小模型可以在超长上下文上提供低延迟推理，但代价是相比大模型表现较差。而这些约束其实是一份礼物，因为它们让我们能够约束住本来看不到边的搜索空间。更重要的是，跨模型布局、参数规模、层数等方面，我们仍然有巨大的搜索空间要去探索。我们甚至可以考虑全新的架构，比如 transformer 与线性注意力变体的混合体。你能想到的任何微调，我们都能用这座工厂高效地试一遍。但房间里还有一头大象：在大语言模型上做实验，是一件极其耗时又昂贵的事情。为了把 GPU 集群用到最优，我们需要在预训练期间考虑一切可能的优化手段与可观测性技术。幸运的是，我们在 Poolside 已经攒下了一大袋子用来优化预训练代码库的技巧。我们还用上了好几种能让我们先在小模型上做实验、进而预测其放大到规模之后表现的技术，比如 mu-P。

在这一点上，值得谈谈我们如何应对「在固定规模的 GPU 集群上调度所有这些额外工作」的巨大复杂度。乍看之下，我们似乎可以只用一个现成的调度器（比如 SLURM），在 GPU 上随意安排任务。但在我们的场景里，这样做其实是不够的，因为现在任务之间存在依赖关系：我们的评估框架需要访问推理服务，而推理又得等待正在预训练的模型产出 checkpoint。为了管理这种复杂度，我们设计并实现了一个统一的 Kubernetes 编排器，用一致而严谨的方式处理所有这些活动部件。附带的好处是，当 GPU 空闲时，我们可以用这样一个编排器去调度额外的、有用的任务，比如合成数据生成。

### 第五轮迭代：自动化的数据精炼

回头看，我们会发现最初那条流水线里还有一块没有被动过：最初的原始数据集。就像真实工厂里的原材料一样，我们 Model Factory 的产出很大程度上取决于我们喂给这些机器的数据的质量和数量。一方面，众所周知，AI 模型的学习效率比人类低几个数量级，我们通常要用上万亿 token 来训练，才能看到潜在能力浮现。然而，肆意地拿几万亿 token 去训并不是通往成功的路径；毕竟，没有人是靠读《远大前程》学会写代码的。相反，我们还要确保模型在预训练中看到足够多、混合良好的高质量数据。更麻烦的是，尽管数据清洗和数据精炼技术早已为人熟知，但不同的数据精炼步骤与下游性能之间的相互作用往往很难理解。换个说法，我们真正需要的是一种贯穿数据精炼各环节的血缘（lineage）：把血缘关联回模型表现的能力，以及大规模的半自动化实验。

在数据流水线所扮演的角色上，还有一些现实层面的顾虑。一方面，预训练所需的数据体量之大，要求我们必须格外留意数据摄取和处理的速度。坦白说，用一个慢的、无法扩展的方案，对训练性能的破坏会灾难性到让我们可能永远腾不出手去验证一个新想法。同样，低质量的数据摄取会严重损害基础模型的泛化能力与表现；一条摄取流水线不仅要快，还必须尽可能准确。反过来看，我们经常需要生成数千亿个新的合成数据 token，还要摄取、重新摄取并重写大片的既有网络数据，这意味着我们要处理的数据量极其庞大。不过，既然我们的工厂里已经有一台推理引擎，我们只要再加一台合成数据生成机器、把它接到推理引擎上就可以了。

### 第六轮迭代：自动化的数据混合

既然已经把相关的数据集都产出来了，我们还需要一种办法来评估这些数据集应该如何混合、以怎样的方式供给模型。我们当然可以简单地把训练数据 shuffle 一下，但我们还需要聪明的办法来决定数据配比应该是多少，以及数据以什么顺序送达。所有这些加起来，就是工厂里的多个新组件。还有一个问题是，训练时数据通常以一个巨大的整体数据集形式提供，这让我们很难对错误或范围变化做出调整。而且，提供这样一个数据集会带来很多让训练变得困难的现实问题。举例来说，物化出一个单一数据集要求我们提前把集群规模定死；训练也得等到整个数据集全部产出之后才能开始。更进一步，仅仅是把一个超大单体数据集分发到 GPU 集群上——以及重新物化的开销——就是高效训练的一道实质性门槛。从实验的角度看，把这个数据集序列化还会把数据配比和数据顺序绑死在数据集上，导致我们每跑一次新配比配置的实验都得重新分发一次数据集。我们解决这些问题的办法，是不再这样做，而是直接从上游数据源把数据流式送入训练，这样我们就能在不同实验之间轻松、随时地改变数据配比或数据量，甚至能在模型训练进行当中实时调整。

现在所有的积木都到位了，我们才真正到了可以造模型的阶段。但训练模型依然是一个漫长而棘手的过程，我们仍然需要为工厂提供某种可观测性。我们实现可观测性的办法，是给工厂里的机器装上仪表盘和旋钮，把大量指标流式推送到各种仪表盘服务。这种方式让我们能盯着与模型训练有关的一切，从损失曲线到单步耗时，以及其间的每一件事。我们还会采集大量生产环境指标，这让我们能确保对工厂本身所做的改动既稳定又有益。

我们还需要一种方式，对从工厂出来的模型做某种形式的质量保证（也就是 vibe checking，凭手感验收）。这种质量保证超出了自动化评估的范畴：我们想手动去试用、去验证流水线上下来的每一个模型。我们的做法是再加一个验证平台，把新产出的模型部署到我们的推理服务上，这样我们就能在日常工作中对这些模型做压力测试。

关于 Model Factory，还有最后一件事要谈：也就是自动化。我们在构建新 AI 模型这件事上确实加进了可观的效率，但如果这份效率需要用多得多的工程时间去换，那一切都白费了。为了应对这种复杂度，我们把数据实验和架构实验都表示为可编程的资产。具体地说，我们把对数据精炼和模型架构的改动，都物化成结构化的实验文件，由编排器自动排队并执行。走这条路给我们两个关键好处。一方面，把配置表示成代码，让我们获得了以严谨方式完全复现实验结果的能力。其次，这种方式带来极快的反馈循环。比如，调度一轮新的扫参——例如对 batch size 或学习率做搜索——用时不到十分钟，而不是几天。这降低了尝试新想法的摩擦，让我们更容易把新的创新推进生产环境。

### Model Factory 究竟给了我们什么？

现在我们可以开始思考，除了已经谈过的这些，这条流水线还能给我们什么。首先要注意，这条流水线里的各个子系统彼此相当解耦，因此每个子系统都可以任意复杂。这种解耦在实践中极为有用：举例来说，我们可以改造或修改数据流水线，而不需要对工厂的其他任何部分做任何调整。同样，我们可以随意调整数据配比、模型架构或微调技术，而不用改动别的任何东西。这让我们有能力应付构建基础模型时那种组合式的复杂度。仅仅调整工厂的一个部件，我们就能一下子探索全新的组件组合与架构。最后要指出，上面描述的这条流水线是完全模块化的，从而在训练模型时可以采用元层面的策略。比如，我们可能想针对某个特定模型改变所用的微调量。换句话说，我们这套机器组成的 ensemble 可以随意改变，让我们能做到彻底务实、彻底由实验驱动。我们甚至可以在需要时插入额外的机器或系统，让这座工厂几乎能随意生长，进一步承接和支撑我们的需求。

Model Factory 对我们保持在 AI 前沿作战的能力产生了多大的影响，怎么强调都不过分。比如我们以往的去重工作，过去要排期和运行一次得花掉超过一周的工程时间；现在，我们只要点一下按钮就能毫不费力地对数据集去重。过去要花几周来组织和排期的实验，现在由编排器在一小时内处理完——常常只要十分钟，这为我们的团队解锁了一个新的生产力层级。从主观感受上说，我们也注意到，跟以往的流水线相比，工厂带来的开发者体验要好得多，让新工程师的上手变得容易很多。

最重要的是，工厂给了我们巨大的杠杆，让我们能快速尝试新想法、构建新的基础模型。我们不再要等上一整周才拿到结果，而是在一个周末就能跑完超计算机规模的实验。我们不再需要手动触发流水线的各个步骤，只要描述一份实验配置，剩下的事工厂全部替我们处理，甚至会自动触发新的步骤。

## 实践中的 Model Factory 长什么样？

现在我们已经对 Model Factory 在理论上的运作方式有了不错的了解，接下来可以看看我们在 Poolside 实际上是怎么把它建起来的。后续的文章里我们会做更深入的讲解，所以这里先只谈高层细节。

### Model Factory 的高层布局

在实践中，Model Factory 可以看作若干套系统叠在一个统一的 Kubernetes 编排器之下。这个编排器负责在我们一万张 H200 GPU 的集群上部署和排定作业优先级。事实证明，这个过程还需要构建若干额外的约束并加以处理。举例来说，我们数据流水线的一些环节（比如去重）其实并不需要 GPU 也能跑成功；事实上，我们完全可以把它们跑在 CPU 节点上，把宝贵的 GPU 留给其他任务。为了做到这一点，我们扩展了自己的编排器，让它处理多种不同的节点池类型，这样我们就能轻松地把某些任务调度到不同类型的节点上。我们当然也要说明，工厂的设计对底层用哪种加速器是基本无关的，GPU 或节点的确切数量都可以随意调整，而不会影响背后的理念。工厂到集群的部署完全用 Helm chart 自动化，集群本身则由 Terraform 管理。

有了编排器之后，我们需要思考实验是怎么组织的。前面提到过，我们所有的实验（数据处理和架构都算）都是代码化的（也就是说，对模型架构或数据处理步骤的每一次改动，都以一段带版本管理的代码来表示）。具体来说，我们所有的数据实验都用 Spark 数据帧（dataframe）来写，这为所有数据实验提供了毫不费力的可扩展性。相比之下，我们的模型架构实验通常以 Python 字典的形式给出，随后由程序校验并转换成结构化的 Markdown 文件。这种转换让我们能轻松地把已有实验往新方向延伸——我们只需要在原有的字典上扩展，覆盖新的参数即可。两种情况下，一旦实验被定义出来，它会立刻作为我们持续集成工作流的一部分被部署出去。

除了提供一种无缝顺畅的工作方式，把实验作为持续集成的一部分来执行，还带来了极高水平的可复现性：毕竟，只要重新触发那个作业，我们就能重建整个实验。最后，特别是对于数据实验，我们能把产出的数据作为资产物化到 Iceberg 数据湖中，从而获得容易的版本管理和可靠性——这对机器学习研究和落地实施都至关重要。

### 数据集管理

关键在于，Iceberg 表还允许我们查询任意数据资产所保留的任意版本，连同完整的元数据和血缘。事实上，工厂里任何兼容 Apache Iceberg 的引擎（Engine）也都能查询这些数据资产，从而实现强大的自动化工作流。实践中，我们用 Starburst 的 SQL 能力来查询我们的 Iceberg 表，这样就能轻松地可视化和检查查询结果。

在这一点上，值得一提的是一次训练通常会消耗数百个数据资产，而每一个资产就代表一个完整的数据集。我们是通过 Dagster 平台做到这一点的，它就是 Model Factory 跳动的心脏。Dagster 提供了一种便捷的方式来编排不同的数据流水线步骤和模型训练。另外，Dagster 还允许我们根据已产出的资产来有条件地运行代码，这让我们能快速检查，并在质量太低、或数据打包效率太低的情况下剔除某个数据集。更宽泛地说，Dagster 还能让我们直接从 Web UI 启动训练，并指定训练过程中的自动化子步骤，比如把 checkpoint 卸载给推理，或在工作流中触发评估。这些改动做起来极其简单：我们只要提供一份对应的配置文件即可。我们甚至可以用 Dagster 快速在已有的资产和工作流上分叉，按既有排期或在其他工作流运行过程中自动启动新工作流，并把已有实验的结果可视化。

Dagster 自动启动作业的一个不可或缺的领域是我们的评估工作流。我们不是手动触发评估，而是按一个实验一个实验的方式来配置评估的启动。这些评估通常每 100 到 1000 个训练步自动执行一次，确切数值写在该实验的配置文件里。

我们通常会针对一系列能够体现基础模型通用能力的基准跑多种评估，范围从通用知识和推理能力，到完成编程特定任务的能力，所有结果都会被自动存储并汇报。关键在于，由于评估是一种相对轻量的推理负载，我们允许评估工作流为了长时运行的作业而被抢占，也允许它被提高优先级，从而提供更快的反馈循环。

### 测量一切

如前所述，我们在整座 Model Factory 上采集海量指标。一方面，我们通常会把训练指标——损失曲线、梯度、评估——流式推送到 Neptune 数据平台。关键在于，Neptune 允许我们在工厂的不同运行之间比较指标，这让我们能更深入地了解自己的想法在训练中实际表现如何。不过，训练指标只能说明有限的问题，而要论模型质量，还得实际试过才算数。为了让我们能更容易地探查产出模型的内部情况，我们团队造了一套内部工具，统称 Podium。Podium 让我们能手动查询和交互模型、用评估把模型互相比对，并与多种微调数据集交互以进一步改进模型。我们要强调的是，模型评估——或者说 "vibe checking"——在 Poolside 是全公司共同参与的事；从工程师到 go-to-market 团队的成员，每个人都会定期对 Model Factory 流水线上下来的模型给出反馈。这些反馈确实帮我们训出了比单纯追逐更好指标所能达到的水平更好的模型。

另一方面，我们也会为工厂里的所有子系统采集生产环境指标，并把结果流式送进一系列 Grafana 仪表盘。和 Neptune 指标不同，我们的 Grafana 指标通常关注的是工厂里这些系统的可靠性和性能，而不是正在训练的模型。这些指标是判断改动的有用风向标：我们可以直接查看新的想法或微调在实践中对工厂运转的影响。过去，这些 Grafana 指标在我们诊断新技术带来的问题、以及识别故障节点时起到了关键作用。

### 规模化预训练

从评估往前，我们来到自己的预训练代码库 Titan。Titan 是一个基于 PyTorch 的最先进预训练库。和其他主流训练框架一样，Titan 内置了大量底层调优以确保峰值性能，此外还带有一些公开预训练代码库里并不常见的可观测性工具。在性能方面，我们大量使用 PyTorch 的 "torch.compile" 特性，确保自动生成的 kernel 足够高效，同时在必要的地方重度使用 Triton 和 CUDA kernel。另外，Titan 还有一个格外有用的特性：它深深嵌在我们的推理代码库 Atlas 内部。这个设计决定让我们能把新的模型架构快速推进生产环境，因为我们随时可以保证推理实现和训练实现高度一致。实际上，我们通常会让 Model Factory 在实验期间自动帮我们检查这种等价性，从而让我们专注于峰值性能所需的那些底层优化。Atlas 本身是一个庞大的封装库，包在其他流行的推理库外面。要指出的是，Atlas 在广泛的硬件平台上服务于多种不同的负载——评估、生产环境的客户推理、预训练实验。确实，Atlas 原生运行在 NVIDIA、AMD 和 Trainium 加速器上，让我们在选择部署方式时有很大的回旋余地。

具体操作上，我们要么把一个推理任务调度成一个专用作业——需要占用集群里固定数量的节点——要么把它调度成一个可按需伸缩的弹性任务。这种自动伸缩既保证了我们的 GPU 永不空闲，也保证了重要的实验不会被低优先级的任务堵住。

### 规模化的代码执行

现在我们把注意力转向自己的代码执行平台。我们的代码执行平台为模型提供了一个安全、隔离的环境，让它们通过编写和执行代码来解题。为了给模型提供这样的环境，我们建了一个平台，它能在 OCI 容器里自动构建 GitHub 仓库，具体用哪种构建机制取决于一组启发式规则。实践中，我们依据一系列启发式规则来构建容器，构建任务则调度在一个规模可任意伸缩的节点池上。我们还使用了一套健壮的可观测性系统来上报构建失败，这让我们能进一步打磨、调试和改进构建启发式。就规模而言，我们的代码执行环境里包含大约一百万个仓库（以及它们的许多历史版本），覆盖多种编程语言，而且我们不断往这个环境里新增并构建新的仓库。我们要强调，构建容器这件事本身一直在演化，最近我们用基于 agent 的构建方式取得了非常巨大的成功。对我们来说这是一个尤其令人兴奋的进展，因为一个用 Model Factory 造出来的 agent，现在正在反过来改进那座造出它的工厂。更宽泛地说，我们的代码执行平台也是我们模型评估的核心组件，为模型在软件开发任务上的改进提供强反馈信号。

最后，所有这些东西拼合到了一起。作为 Kubernetes 编排器的一部分，我们把 Model Factory 的每一个组件都构建为一个 Docker 容器，然后部署在不同的节点池上。具体的部署细节完全取决于集群当前的负载和工作流本身，但我们的编排器允许我们抢占低优先级作业，把资源让给更紧迫的作业。此外，编排器本身也支持回填（backfill），好让短小的任务能被迅速完成。
