# 从零开始理解分离式推理

[Isaac Tai](https://www.cerebras.ai/author/isaac-tai)[Zhenwei Gao](https://www.cerebras.ai/author/zhenwei-gao)

传统上，提高推理吞吐意味着增加硬件，或者同时服务更多请求。但把并发推高，会拖慢每个用户的 token 生成速度。

通过采用一种称为分离式的技术，我们在早期结果中把吞吐量提升了 5×——使用同样数量的 Cerebras 系统，token 生成速度没有任何损失。

在 Cerebras，我们正引领异构分离式的发展，也就是把多种类型的芯片组合进一套推理系统。把推理中受内存限制或受计算限制的各个环节分配给不同的硬件，我们获得了超出同构分离式的收益。

这是该主题系列的第一篇。如果你听过“分离式”这个词，或者听过“prefill 受计算限制、decode 受内存限制”这个说法，却搞不清它们到底指什么，那么这篇文章就是为你写的。

我们会从最基础的地方把这种直觉建立起来：

- 加速器如何在计算与内存搬运之间取得平衡
- 推理的不同阶段分别是什么
- 它们为什么对硬件提出不同的要求
- 分离式如何改善整个系统

### 加速器是如何工作的

加速器是为加速特定类型计算而造的硬件。GPU 就是一个例子。我们可以把加速器看作协同执行程序的两个部分。

- **计算单元**自己完成算术运算——加法、乘法、按位逻辑等操作。
- **内存**负责存储数据。通常是用户输入、模型权重、中间值和结果。

GPU

计算：每个方块是一个计算单元。它们并行执行算术运算。

算术运算只发生在加速器的计算单元里，而不发生在内存里。因此，每一次计算都必然伴随数据搬运。要想高效使用加速器，工程师会尽量让每次搬运产出尽可能多的算术运算：*数据一旦从内存搬过来，在搬运更多数据之前，我们能完成多少次计算？*

**算术强度**就是衡量这种效率的指标。它指的是搬运一定量数据所对应的计算“工作量”。更准确地说，是浮点运算次数除以传输的字节数。

算术强度等于 FLOPs 除以传输的字节数。算术强度 = FLOPs / 传输的字节数

算术强度告诉我们每搬运一个字节做了多少计算；它并不直接告诉我们某个操作跑得多快。当处理器大部分时间都在等数据时，内存带宽最关键；当它一直忙于计算时，算力就更重要。

吃透算术强度，是理解 LLM 各个计算阶段的关键。我们来看几个真实例子。

### 两个矩阵相加

考虑一个简单的矩阵相加。要在加速器上完成它，我们需要从内存读取两个矩阵，在计算核心中做加法，再把结果写回去。

我们看一个真实的例子。

这里，我们从内存载入两个数（各 2 字节），执行一次 FLOP 把它们相加，然后把 2 字节的结果写回内存。这样就是 1 次 FLOP 对应传输 6 字节，算术强度为每字节 0.167 次 FLOP。

算术强度：1 FLOPs 除以传输的 6 字节：4 字节载入计算单元，2 字节存回内存。1 FLOPs / 6 字节传输 = 0.167 FLOP/byte

### prefill

在 prefill 阶段，整个提示词被*并行*处理。

前面我们了解到，规模更大的矩阵乘法因为数据复用更多而具有更高的算术强度。用更长的输入提示词可以让这一点更明显：

真实场景中的提示词可能包含数千甚至数十万个 token。把一个 100 页的 PDF 上传给聊天机器人，本质上就产生了一个需要处理的巨大矩阵计算。

这就是 prefill 的算术强度相对较高的原因！它是一次大型矩阵运算。

### decode

在 decode 阶段，token 被逐个生成。

乍看之下，模型似乎每次都要把不断变长的整个序列跑一遍同样的大矩阵乘法。但语言模型用 **KV cache** 避开了这一点。

KV cache 保存了为先前 token 计算出的 key 和 value，因此不必重新计算它们。随着上下文增长，读取和使用这份缓存的工作量也会增加。

本文不会深入讨论 KV cache 的全部复杂性，但你可以把矩阵中的灰色部分理解为 token 生成每一步中已缓存的数据。结果就是一次小得多的矩阵运算。

得益于这份缓存，我们避免了重新计算先前 token 的 key 和 value。

> 注意：加速器仍然要从内存中读取已缓存的 key 和 value，并在 attention 中使用它们。我们这里只画出新 token 进入计算单元，是为了强调先前 token 的 key 和 value 是被复用而不是被重算。想了解真实的矩阵运算，见 Hugging Face 的 KV cache 指南。

### prefill 与 decode 的特征不同

在两个阶段中，模型的全部权重都必须被送到计算单元。这可能意味着搬运数百 GB 甚至数 TB 的数据。无论 prefill 阶段处理的是上百万 token 的提示词，还是 decode 阶段只处理一个新输入 token，生成一个 token 都要搬运这些数据。

这就是为什么 prefill 和 decode 在内存搬运量相近的情况下，计算负载却如此不同：

### 共享调度的难题

到目前为止，我们跟踪的是单个请求在系统中的流转。但在生产环境中，一台推理服务器通常要同时处理许多请求：有些请求处于 prefill 阶段，另一些已经在 decode 阶段生成 token 了。

当 prefill 和 decode 跑在同一批硬件上，它们会互相干扰。prefill 计算密集程度很高，会拖住正在进行的 decode 请求。

### 分离式架构

我们先回顾一下到目前为止学到的内容：

- 加速器（硬件）负责执行算术运算。其方式是：把数据从内存搬到计算单元，再把数据写回内存。
- 在搬运同样多数据的情况下，有些工作负载能完成更多算术运算。
- prefill 和 decode 是推理的不同阶段。
- prefill 因为要并行处理多个 token，计算量很大。
- decode 每一步对每个请求只处理一个新 token，但仍需为模型权重和 KV cache 进行大量内存访问。
- 在同一批硬件上平衡这两种工作负载很困难，规模化时必然要做取舍。

分离式是一种系统设计模式。它识别出资源需求不同的工作，然后把它们分开运行，而不是强迫它们共用同一个硬件池。

分离式系统使用两个独立的硬件池：一个用于 prefill，一个用于 decode。选择“分离式”，看看调度因此有何变化。

在共享池中，首 token 延迟与 token 间延迟直接耦合。开始一个新提示词可能拖慢正在进行的响应；保护正在进行的响应又会让新提示词一直等待。

分离式远不只是“流式输出更顺滑”。更根本地说，分离式改变了服务系统的控制接口。

### 对取舍有更多控制

在共享池中，容量、批处理和调度决策同时影响 prefill 和 decode。一旦把阶段分开，运维者就可以独立调节每一侧——分配硬件、设定批处理策略，并按产品需求决定更偏重延迟还是吞吐。

例如，对首 token 延迟有严格目标的系统，可以为 prefill 预留更多容量，让进来的提示词立刻开始处理，而不占用 decode 的容量。优先保证流式体验顺滑的系统，可以给 decode 一个更大或调度更紧凑的池，即使在提示词流量激增时也让进行中的响应持续推进。

但把阶段分开也带来一个新需求：池与池之间的数据传输。这个设计中最关键的新增环节就是 **KV cache** 的传输。

### KV 传输

prefill 构建出 KV cache 之后，系统把这份状态传输到 decode 池，在那里载入内存，生成才能继续。

模型权重在两个池里本来都已加载，而 KV cache 不同，它是与请求相关的数据。交接会带来额外的网络与协调开销，这正是分离式在规模化时最有吸引力的原因：当并发工作足够多时，独立配置和调度 prefill 与 decode 带来的收益可以超过传输状态和运维两套池的成本。

prefill 处理完一个提示词后，decode 需要 prefill 创建的那份与请求相关的状态。两个池都已经有模型权重，所以必须跨越边界的状态就是 KV cache。

### 异构分离式

到目前为止，我们的例子展示的都是把 prefill 和 decode 分离到使用同一种硬件的两个池里。

当引入异构硬件组合时，分离式会更强大。问题不再只是哪一款加速器该跑这个模型，而是哪种加速器组合最能服务这种工作负载。

如果每个池都可以指派给不同的硬件，专用硬件就变得极具吸引力：某一维度——比如提示词处理、内存带宽、token 速度或成本效率——特别出色的加速器，可以带来超过只用单一类型芯片做分离式的性能提升。

### 为什么有些加速器更擅长 decode？

回想一下 decode 的不同之处：我们搬运了大量数据，只为产出一个新 token。它的算术强度相对较低，所以单纯增加 FLOP 算力并不一定能让 token 来得更快。计算单元需要从内存获得更多数据供给。

在 GPU 上，模型数据主要存放在高带宽内存（HBM）中。在计算单元能使用这些数据之前，数据要先经由更小、更快的片上内存和缓存（包括 SRAM）逐级中转。这种内存层级在提供大容量的同时也有快速的本地存储，但数据仍必须从共享的外部内存向计算核心搬运。

Cerebras 走的是另一条路：把 SRAM 与计算单元一起分布到整片晶圆上。这让计算单元能快速访问邻近的内存：

GPU

共享的 HBM 为众多计算单元供数

WSE

### 分离式的目标

同构分离式与异构分离式带来的好处是*不同的*。

同构系统通常着眼于通过让 token 生成更平滑来改善响应，而异构系统则被优化成从专用硬件中挖掘出最大价值。对 Cerebras 来说，就是提供极致速度而不牺牲吞吐。

设想一个由五块 GPU 组成的聚合式系统，每块 GPU 把 80% 的执行时间花在 prefill 上、20% 花在 decode 上。进行中的响应只有在所属 GPU 执行 decode 步骤时才会推进。把五分之四的时间花在 prefill 上，会拖慢输出 token 生成的*平均*速度。

示意性假设

示意性的 prefill/decode 交替执行，decode 步骤为 10 ms，传输开销可忽略。总请求吞吐相同：通过一块 decode GPU 的流量提升到 5×，响应完成速度快 5×，其活跃批大小保持不变。

五块 GPU 合计的执行时间里，decode 只相当于一块 GPU 的量。在这个理想化的稳态下，分离式把这份工作交给一块专用 GPU，把 prefill 交给其余四块。这块 decode GPU 可以在不与 prefill 竞争的情况下推进响应，在 GPU 总数不变的前提下改善 token 节奏。

共享 GPU 花在 prefill 上的时间越多，改善幅度就越大。如果 GPU 本来就把大部分时间花在 decode 上，那么在同构系统中可消除的干扰就更少。但减少干扰只是做分离式的理由之一。在异构系统中，分离式优化的是更好的硬件专用化。

假设目前由五片 Cerebras WSE 同时承担两个阶段。把 prefill 移到另一个加速器池，就能让这些晶圆专注于 decode——它们的能力在那里最有价值。

Cerebras 分离式解锁了在不牺牲世界级交互性的前提下扩展推理的能力。

### Cerebras 用分离式扩展超快 token 的规模

对超快生成的需求正在快速增长。随着越来越多应用走向 agentic，制约因素越来越不只是模型的总容量，而是我们一次能向用户交付多少快 token。

在 Cerebras，我们正在构建异构推理系统来满足这一需求。目标不只是提高总吞吐——而是扩大推理的规模，同时保住那种让应用感觉瞬时的超快 token 速度。

在传统的聚合式系统中，提升容量意味着部署更多硬件。借助合作方的加速器来处理提示词，我们在早期测试中用同样的 WSE 占地规模把容量提升了 5×。

我们已经宣布与多家硬件伙伴建立合作，把更多超快 token 带给市场，这反映了我们的判断：异构硬件将成为今后推理的核心策略。
