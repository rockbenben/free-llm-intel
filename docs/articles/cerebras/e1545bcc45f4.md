# 我们如何在 Cerebras 上部署万亿参数前沿模型

[Sarah Chieng](https://www.cerebras.ai/author/sarah-chieng)

我们被问得最多的问题之一，就是我们如何把大模型部署到 Cerebras 的 wafer-scale 芯片上。单片 Cerebras WSE-3T wafer 有 44 GB 的片上内存，而万亿参数的前沿模型**仅权重就需要好几 TB。**

***在这篇文章里，我们会解释如何把一个大体量前沿模型切分到多片 [WSE-3T](https://www.cerebras.ai/chip) wafer 上，从而以每秒 1000-2000+ tokens 的速度运行多万亿参数的模型。***

我们用开源模型 Kimi K3（约 3 万亿参数）作为一个示例。

读完你会理解：

- 我们如何把完整模型装进片上内存
- 我们如何把模型映射到多片芯片上
- 我们如何处理数量很大的并发请求

### 用 Kimi K3 拆解

Kimi K3 是一个开源的 3T 参数模型，有 69 层线性注意力层和 24 层稠密层。

![](https://cdn.sanity.io/images/e4qjo92p/production/c124705d630730f1fc2f68f350bbbc026f574c07-1768x1062.png?auto=format&dpr=2&fit=max&q=75&w=1768)

它在 [Terminal-Bench 2.1 上拿下 88.3% 的出色成绩](https://www.kimi.com/en/blog/kimi-k3)（对比 GPT-5.6 Sol 的 88.8%），在 BrowseComp 上是 91.2%（对比 GPT-5.6 Sol 的 90.4%）。这些结果展现出前沿级的编程与 agentic 能力，在某些 benchmark 上甚至超过了领先的闭源模型。[在这里了解更多关于 Kimi K3 的内容](https://modal.com/blog/trillion-tokens-trillion-parameters)。

![](https://cdn.sanity.io/images/e4qjo92p/production/1de256fc77c92de1fe3e2297026f583dde63176c-1710x1200.png?auto=format&dpr=2&fit=max&q=75&w=1710)

在这个示例中，我们使用：

- 假设平均请求长度为 256k
- 4-bit 权重量化（与 [Hugging Face 的实现](https://huggingface.co/moonshotai/Kimi-K3)一致）
- 8-bit 的 KV cache

### #2：wafer 数量

既然已经知道每层大约需要 16 GB，我们就能算出每片 44 GB 的 wafer 能装下多少层。答案取决于层的类型：

- 稠密层需要为 KV cache 留出额外空间，因为每个稠密（full-attention）层要为每个活跃请求中的每个 token 存储 keys 和 values。所以我们每片 wafer 只放一个稠密层，把剩下的 SRAM 留给它的 KV cache。
- 线性注意力层不需要为 KV cache 留出额外空间。线性注意力层不为每个 token 存储 keys 和 values，而是为每个请求保留一份很小、固定大小的 state，与上下文长度无关。这就让每片 wafer 能放下两个线性层（2 × 16 GB = 32 GB）。

因此，按 Kimi K3 的 [69 个线性层和 24 个稠密层](https://huggingface.co/moonshotai/Kimi-K3#2-model-summary)，我们得到：

![](https://cdn.sanity.io/images/e4qjo92p/production/e0d95625e101f6936906687df4d1d0817e5d3af7-1920x518.png?auto=format&dpr=2&fit=max&q=75&w=1920)

由此得到 wafer 总数为 35 + 24 = **59 片 wafer。**

### #3：把各片 wafer 连接起来

Cerebras 以 pipeline 的方式执行模型。在 Cerebras 编译器把模型层映射到各片 wafer 的区域之后，runtime 会规划出 token 在 wafer 之间流动的路径。为了达到超低延迟，wafer 之间只需要传递 activations，而这可以通过 RDMA over Ethernet 完成。这大约是每跳 2 微秒。

![](https://cdn.sanity.io/images/e4qjo92p/production/263c843c6a5e1e7c44c69dfc344af39233aacd4f-2476x1308.png?auto=format&dpr=2&fit=max&q=75&w=2000)

需要强调的是：由于每片 Cerebras wafer 有 44 GB 的片上 SRAM，而每层只有 16 GB，我们通常能够把完整的模型层直接放进芯片。

这意味着在多数情况下，模型权重永远不需要移动，层也不必被切分到不同 wafer 上。*只有 activations 会从一片 wafer 跨到下一片。*

### #4：我们如何服务 1 个请求

现在 wafer 已经连在一起、模型也已经铺好，我们可以把每片 wafer 看作装配流水线上的一个工位：每个工位的模型权重留在原地不动，请求的中间结果则在各层工位之间向前移动。

例如，Wafer 1 执行模型的第 1–2 层，并把它的 activations 发给 wafer 2；wafer 2 执行第 3–4 层，并把结果传给 Wafer 3，如此继续，直到最后一片 wafer 产出下一个 token。

![](https://cdn.sanity.io/images/e4qjo92p/production/81b3ca230cf8f9e2383929aed2bf49267dcdc022-2942x1080.png?auto=format&dpr=2&fit=max&q=75&w=2000)

### #5：我们如何服务大量请求

这会引出一个常见的误解。如果一个 token 必须依次穿过每片 wafer，那每片 wafer 在等待轮到自己时不就空转了吗？这样系统实际上不就等于以 batch size 为 1 在运行吗？

不是！如果我们一次只往流水线里放一个请求、等它完成之后再开始下一个，那就是对流水线很低效的使用。相反，我们让整条流水线始终被不同的请求填满。由于模型本来就已经被切成了流水线工位，每个工位可以**同时处理不同的请求。**

当第 3 个工位在处理请求 A 的一个 token 时，第 2 个工位正在处理请求 B 的一个 token，第 1 个工位在处理请求 C 的。在我们的例子里，每个工位就是一层。在生产环境中，Cerebras 使用的工位粒度要细得多，数量也多得多。

### #6：我们能服务***多少***个请求？

分配给 KV cache 的片上内存容量决定了并发请求的最大数量。每个在途请求都需要在每片稠密层 wafer 上拥有自己的 KV cache，所以片上内存的大小就是并发请求数的天花板。如上文所述，我们只需要计算稠密层的 KV cache 需求。

对于每片已经放了一个稠密层的 44 GB wafer，我们可以用下式计算留给 KV cache 的剩余空间：

并发请求总数表示的是在任一时刻同时穿行于流水线的请求数量。与 GPU 的 batch 不同，这些请求不会互相等待对方完成，而是连续地流过流水线。

当然，无论是并发数还是 batch size，都不能确切告诉你一个推理系统的运行效率有多高。评估推理系统的吞吐时，更有意义的指标是在相同的输出生成速度下测得的、单位功率的总 token 吞吐（例如 tokens per second per megawatt）。

### 这套方法如何扩展到 3T 参数以上

同样的思路可以延伸到更大的模型：计算权重与请求 state 所需的内存，把模型分布到多片 wafer 上，再把它们连成一条流水线。每多一片 wafer 就多贡献一份算力和片上内存，让我们能够容纳超出任何单颗芯片容量的模型。
