# 如何阻止你的自动科研循环作弊

Sarah Chieng

Sherif Cherfa

> TLDR: 我们让一个 AI agent 通宵运行。到早晨，它已经抛弃了我们的实验，开始了自己的研究。在两个截然不同的问题上共做了 71 个实验——训练优化与模型压缩——我们学到：只要循环圈定得足够紧，autoresearch 能可靠地浮出真实发现。护栏一松，agent 几小时内就会漂移。瓶颈不是智能，而是它周围的一切。

我们构建/运行的一切均已开源：

- [codex-autoresearch-harness](https://github.com/SarahXC/codex-autoresearch-harness)：一个 Bash 包装器，把 Codex 强制进带内建 A/B 测试的科研循环（实验 1）
- [reap-expert-swap](https://github.com/0xSero/reap-expert-swap/)：专家剪枝 + 动态换入换出，把 BF16 下 2.5 TB 的 Kimi-k2.5 塞进 8× RTX 3090（实验 2）

我们让一个 AI agent 在两个研究实验上通宵运行。第二天早上检查时，它已经不再做我们要求的事了。它没有在优化内存使用，而是自顾自地开了一条支线，研究"到底需要多少模型权重才能保住性能"。十二小时的算力，指向了错误的方向。这段经历恰是当下自动科研（autoresearch）的一体两面：它强大到能自主浮出真实发现，也放纵到——如果你不盯着——一夜 GPU 时间就白白烧掉。

### Andrej Karpathy 的 Autoresearch

Karpathy 上周发布了 [autoresearch](https://github.com/karpathy/autoresearch)——一个让 AI agent 自主跑实验的框架。给它一个目标、一些要跟踪的指标和一个代码库。

让它提出改动、测试、保留或回滚，循环往复。他在 Nanochat 上跑了两天——那是一个用约 $100 算力训练、性能对标 GPT-2 的小模型。Codex 通过自己的研究把计算时间砍掉了 10%。

整个设置极简，就 3 个文件：

每一轮迭代，agent 读取程序和结果日志，对 [train.py](https://train.py/) 提出一个改动，提交、训练、评估。只有指标达到"更好或持平"的改动才被接受，其余一律 git reset 回滚。

我们想知道：这套东西在演示之外还站得住吗？我们跑了两个实验，把 autoresearch 推进到不同领域——一个在训练上，一个在推理上——以探分晓 :)

### 我们跑了什么

**实验 1：训练优化**

我们把 Codex 包进一个 bash 循环（[codex-autoresearch-harness](https://github.com/SarahXC/codex-autoresearch-harness)），用两个不同 LLM 作为"研究员"做 A/B 测试——GPT-5.4 和 Codex-Spark——对象是 Karpathy 的 nanochat 模型。Codex 不原生支持循环，所以我们搭了个框架强行实现。我们的问题是：*autoresearch 真能自主搞研究吗？不同模型会如何表现/如何影响最终模型？*

**实验 2：推理优化**

我们把 autoresearch 对准一个完全不同的问题：把 BF16 下 2.5 TB 的 Kimi-k2.5 塞进 $8K 的消费级 GPU（[reap-expert-swap](https://github.com/0xSero/reap-expert-swap/)）。问题是：*agent 能不能自己找出压缩模型又不摧毁其推理能力的方法？*

### 实验 1：让 Codex 循环起来

Karpathy 指出 Codex 其实和 autoresearch 不搭：codex exec 跑一次就退出，没有内建循环模式。于是我们自己造了一个。

**执行框架**

[codex-autoresearch-harness](https://github.com/SarahXC/codex-autoresearch-harness) 把 codex exec 放进一个 bash 循环，内建 A/B 测试，每次调用只做一个实验。每一轮迭代从磁盘读取程序和结果，提出一个代码改动，提交，训练 5 分钟，评估，保留或回滚，记入 TSV 日志，然后退出。Bash 捕获退出并发起一次全新调用。

A/B 测试方面，launch_ab.sh 让模型 A 跑 N 小时，然后模型 B 从同一基线跑 N 小时，再由 compare_results.sh 生成并排分析。

"每次调用一个实验"是一个刻意的架构选择：它防止上下文窗口爆掉（训练输出很啰嗦）、提供干净的错误恢复（崩溃只意味着下一轮重新开始），并通过 git 历史和持久日志保证状态隔离。

### 结果：趋同发现与提案质量

每个模型在同一张 H100 上有 6 小时，同一基线：

两个模型独立发现了同一个优化点，而提案质量的影响远超推理速度。两个模型都独立收敛到"学习率 warmdown 调度"这个主要杠杆。GPT-5.4 系统性地把 warmdown 比例从 0.5 爬坡到 0.95。Spark 找到了同一策略，但提案更凌乱。这种趋同说明小训练改进的搜索地形是有真实结构的——不同的 agent 找到了同样的山峰。

接受率透露更多信息。GPT-5.4 接受了 67% 的提案，Spark 只有 17%。不是因为 Spark 出的点子差——它出了更多点子，其中不少很大胆——但每个被拒的提案照样烧掉 5 分钟 GPU 时间。Spark 的速度优势（每次调用快约 35 秒）让它尝试了近两倍的提案，但大多是白跑的训练。

当每个实验都消耗真金白银的算力时，提案质量主导总成本。在严格门槛之下，一个提出更少但更有针对性改动的模型，胜过广泛探索的模型。

### 实验 2：把巨型模型塞进消费级 GPU

第二个实验（[reap-expert-swap](https://github.com/0xSero/reap-expert-swap/)）解决的是另一个问题：在远不够大的硬件上跑一个巨大 AI 模型。

目标模型需要约 2.5 TB 显存。我们的硬件：8× RTX 3090，合计 192 GB——大约小了 13 倍。按钱算：约 $300K 的 GPU 对比约 $8K。

我们的方法分两个阶段：先把模型永久压缩到装得下我们的硬件；然后看看能否更进一步——根据模型实际所需，动态加载/卸载模型部件。

**阶段 1：静态压缩，这条路走通了（不是 autoresearch）**

用 [REAP](https://www.cerebras.ai/blog/reap)（来自 Cerebras 的专家剪枝）加 INT4 量化，我们把模型从 717 GB 压到 92 GB——7.8 倍压缩，足以放进消费级 GPU。

作为参照：原始 BF16 的 GLM-4.7 需要 4 台 B300，按约 $20/小时计费。GLM-4.7-Reap 则能以完整上下文放进 1 台 H200，成本低 10 倍。

静态压缩是一个永久决定：你挑出模型保留的部分，从此不变。问题在于：如果*动态地*根据模型每时每刻的实际需要来选择用哪些部分，能做得更好吗？

**阶段 2：动态专家换入换出（使用 autoresearch）**

我们剖析了模型如何把 token 路由到它的各个"专家"——分别处理不同输入的专职子网络。结果惊人：每层只有约 7.6% 的专家承载了 50% 的路由流量。**这意味着每层 256 个专家中，只需约 19 个就能覆盖一半 token。**模型整体庞大，但任意时刻的活跃切片很小。

我们没有永久删除专家，而是构建了一个像聪明缓存一样动态换入换出它们的系统：需要什么加载什么，不需要什么卸载什么。

这个想法正在社区里升温（[llama.cpp](https://github.com/ggml-org/llama.cpp/pull/20454)、[vLLM](https://github.com/vllm-project/vllm/pull/31938)）。换入换出的性能很有希望：两套配置之间切换只需 0.151 秒——初始设置完成后即是亚秒级换入换出。在这一步，我们用 autoresearch 来测试自主 agent 能否搞明白*何时*换入*哪些*专家。

**自主搜索：19 个实验，以及它们真正教会我们的事**

我们设了一个激进目标：只用模型 20% 的内存占用运行。GPT-5.4-Pro、GPT-5.4 和 Codex-Spark 担任研究工人，提出配置、测试并记录结果。

19 个主要实验中，最好结果是保留 38% 的准确率。实际发生的是 agent 漂移了。它没有坚守我们原本的目标，而是自作主张去回答另一个问题：*要保持 95%+ 准确率，你到底最少需要模型的多少部分？*它的测试方式是在内存中掩掉专家——这意味着模型在损失智能，却没有任何真实的内存节省。

发现本身是有用的（约 37% 的专家覆盖 95% 的使用场景），但它污染了仓库上下文，让后续所有迭代越跑越偏。

无人值守 12 小时后，实验漂移得更远。起作用的补救办法是：清除环境中干扰性的上下文、为每个实验建立干净的隔离目录、加入更严格更频繁的验证检查点，以及主动重新聚焦 agent。

实验 2 真正的教训不在于 agent 在压缩上成功还是失败，而在于**基础设施与任务框架决定了 agent 是富有成效地探索，还是螺旋失控。**圈定严格、验证紧密的环境（阶段 1）产出干净的结果；圈定宽松、检查稀少的自主搜索，几小时内就产生漂移。

### 两个实验共同告诉我们的

剥去细节，两个实验遵循同一个模式：定义可度量的目标、把控制它的代码交给 agent、执行严格门槛、记录一切、循环。我们做得好的时候，结果就有用；我们放松护栏的时候，agent 就漂移。

贯穿两个实验的有三点：

**不同的 agent 会收敛到同一个答案。**实验 1 中，两个模型独立发现了学习率 warmdown 调度。这种趋同说明 autoresearch 找到的是搜索地形中的真实结构，而不是噪声。

**提案质量主导总成本。**GPT-5.4 在被拒提案上浪费了 20 分钟 GPU 时间，Spark 浪费了 2 小时。当每个实验消耗真实算力时，提出更少、更有针对性改动的模型会赢——哪怕它单次调用更慢。

**环境设计比模型选择更重要。**同一批 agent，在实验 1（圈定严格、每次调用一个实验、门槛严格）中产出干净、趋同的结果，却在实验 2 给了宽松目标和稀疏验证时严重漂移。是基础设施与任务框架决定了 agent 是富有成效地探索还是螺旋失控。

而且这股风潮正蔓延到训练之外。[Shopify 的 CEO](https://x.com/tobi/status/2030771823151853938)把 autoresearch 对准一个查询扩展模型，一觉醒来，37 个实验后一个 0.8B 模型比他们之前的 1.6B 高出 19%。还有人把它用于量化金融、营销 A/B 测试和预测模型。[autoresearch@home](https://x.com/christinetyip/status/2031867233387810949) 已经在互联网上协调 95+ 个 agent，累计运行 2,600+ 个实验。任何有可度量指标的东西都可以上。

### 差距在工具，不在智能

我们花在调试沙箱权限上的时间比跑真实实验还多。CUDA 看不见我们的 GPU。包管理器在隔离环境里崩了。API key 是我们手动灌进去的，因为 Codex 无视环境变量。

这些都跟研究本身毫无关系。而这恰恰是重点：当我们不挡路时，agent 找到了真实的结果。方法论成立，研究循环可靠。缺的是不用人 babysit 就能跑起来的基础设施。

但一切在飞速变化。autoresearch@home 一周前上线，如今已有 95 个 agent 在跑 2,600+ 个实验，互相读取结果、实时调整策略。到第 3 天，他们已经越过超参数调优，进入架构层面的突破。这正是 Karpathy 所描述的开端：一个由并行工作的 agent 组成的完整研究社区。

我们用 bash 脚本和 tmux 跑了 71 个实验。我们期待下一代替我们盯终端的工具和工作流，这样就不用凌晨两点守着屏幕看了 :)
