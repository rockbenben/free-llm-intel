# 构建多 Agent 工作流的经验教训

Sarah Chieng

Sherif Cherfa

我付了预付订阅费（**每月 $200**），写下我祈祷正确的 prompt（**既当 prompt 工程师又当上下文工程师**），然后等。35 分钟后，它还在"synthesizing""perusing""effecting""germinating"（*这些词是谁想出来的*）。到头来，我手里是一堆烂代码文件、一个肿胀的上下文窗口，正掰着左手指数剩下的 token。

好吧，我拿了个苹果，触发 compact，敲下一段*火力全开的口头辱骂*，从头重新解释一切，祈祷下一次尝试能比上一次走得更远……结果失望依旧。*事到如今，AI 编码的火花与乐趣早已死透。*

### 别再当一次性的 Sloperator

这就是**单 agent 天花板**。每个用 AI agent 构建的开发者，都会在他的项目从 3D HTML 贪吃蛇毕业到更实用的东西的那一刻撞上它。原因有两个：

- 我们对单个 agent 期望过高
- 我们没有把问题拆成足够简单、可验证的任务

而这个时候，大多数人会向你兜售：(a) 一门没用的 prompt 工程课，(b) 又一个帮你管理上下文的 SaaS 工具，(c) 或者问你为什么还没试"几秒前刚发布"的新模型——我们今天不干这个。

相反，我们将带你走一遍真正有效的做法：运转一个正经的**后厨（back of house）**。多 agent 工作流。

### 欢迎来到后厨

多 agent 工作流在最近几周变得实际可行，有几个原因：底层模型变强了，流行的 AI 编码 agent 让多 agent 编排更容易搭建。上一季度，OpenAI 在 Codex 工作流中推出了更深的编排能力，Anthropic 则继续扩展 Claude Code 和 MCP 生态。

但最大的解锁是速度。Codex Spark 大约以 **1,200 tokens/秒** 运行，这让引入并行与验证步骤变得可行——否则它们的时间成本高到没法跑。

举一个用 Codex 加 Figma MCP 把网站复刻进 Figma 的示例任务：单 agent 工作流平均 36.5 分钟/次、平均需要 12 次人工干预（且 100% 失败）；多 agent 工作流 5.2 分钟跑完、2 次人工干预，一次成功。

### 什么是多 agent 工作流？

***多 agent 工作流***在架构层面解决单 agent 天花板。不再是一位厨师包打天下，而是有一位**主厨（head chef）**接单，把工作拆成范围明确、可验证的工单，再把每张工单交给一名**档口厨师（line cook）**执行。

**主厨（编排者）**

主厨的职责是从人类手里接单，拆成一份可执行的工单清单，然后呼叫各档口厨师各自去完成一个更小、边界明确的工作。

**档口厨师（子 agent）**

档口厨师的职责是拿起主厨给的工单（任务指派）并把活干完，不问理由。每个厨师都有自己的全新工位（上下文窗口），干完活，把盘子交回，然后打卡下班。

保持秩序井然的诀窍在于：档口厨师拿不到整张订单的历史。它也拿不到你那 15,000 token 的总计划书——它不需要看那么多。它只拿到做这一道具体菜所需的最小可用上下文。

在 Codex 这类 AI agent 里，你只要直接告诉你的 agent"用 subagents"，就能造出一个档口厨师。新实例会获得一份 prompt、一组它能访问的文件，以及它需要的上下文。

### 运转后厨立刻可得三大胜果

相比"一枪梭哈"你现在构建的东西、或死守单一的前沿昂贵模型，编排者加子 agent 带来三个明确的胜利。

**1. Token：你的有效上下文窗口从约 200K 扩展到 2500 万以上**

人类、编排者和子 agent 的交互方式如下：

- 人类只与编排者对话
- 编排者被剥离除 *delegate_task* 以外的所有工具
- 编排者如果想采取行动，就通过 *delegate_task* 派生一个子 agent
- 每个子 agent 有自己的全新上下文窗口，初始只有一份 prompt
- 子 agent 可以读写、使用 MCP 以及任何其他工具
- 子 agent 把自己工作的摘要交还主厨

这意味着编排者永远不必亲自读文件、写文件或看工具调用结果——它的上下文窗口实际上延伸到了它能派生的子 agent 数量上限。你可以干一整天而不丢上下文、不 compact、不重开。

**2. 控制：你可以在 agentic 循环的每一步强制执行顺序工作流**

不再是一个 agent 又探索又烹饪又试吃又摆盘，每一步都成为一张精确、有序的工单。这也是"不同任务用不同模型"的绝佳用武之地。有了 Codex Spark 这样快得多的模型（约 1,200 toks/秒），我们可以加上平时耗时到根本跑不起的验证与 QA 步骤。

编排者按剧本走，每个阶段派生一个子 agent：

- 子 agent A 把订单拆成带子任务和验收标准的"合同"
- 子 agent B 探索下一个子任务
- 子 agent C 测试上一个子任务生成的代码 a. 若测试通过验证标准，继续 b. 否则重新召唤编码厨师修复已识别的问题
- 子 agent D 为子任务写文档并更新范围清单
- 若还有子任务未完成，从第 2 步继续。否则，服务结束。

在内部试验中，相比同一任务简介下的单 agent 运行，这个顺序循环把人工干预减少了 84.3%。

**3. 速度：定义良好的任务可以并行跑**

如果你的任务允许，可以并行派生多个子 agent。这很适合：

- 生成 logo、图片、吉祥物、素材、样机、设计稿或测试
- 以快几个数量级的速度探索巨型代码库
- 快速构建多个页面——每个子 agent 负责代码库互不相同的部分，不会互相覆盖

跑五个并行的吉祥物生成大约花一分钟，而顺序执行要五分钟——在口味驱动的探索型任务上约 5 倍提速。

### 真正管用的 5 种模式

你刚被提拔为专业厨房的主厨。你有一整支厨师队伍、一板工单，却不知从何下手。过去几周，我们在不同 AI agent 上试了几十种工作流和配置。以下是我们发现构建多 agent 工作流行之有效的五种模式。

如果你是新手，就从上往下读 :)

### 模式 1：备菜线（The Prep Line）

开餐前，专业厨房不会让一位厨师慢条斯理地切所有蔬菜。而是一排备菜工各自独立在同一个工位上干活：一个切洋葱，一个处理红葱头，一个给蛋白质分装。最后，副厨师长验收，挑出过关的。

这正是设计探索、代码变体或测试生成的正确形态：让你的厨师们各自产出许多选项，然后人工挑出最好的。每个厨师拿同一份任务简介独立开工，而你（没错，你有一个小任务）策展结果。这是入门多 agent 工作流最容易的方式，因为每个任务完全独立，没有文件冲突、依赖图或合并逻辑。

举个例子：我们想为 [Parchi](https://github.com/0xsero/parchi) 创作 50 个吉祥物变体，于是派出 5 个 Codex Spark 子 agent，每个产 10 个变体。然后我们摘取喜欢的，扔掉其余。

这种模式最妙的一点：它也是往你的 AI 工作流里注入**品味**的好办法。**如今的模型几乎没有什么品味。很可能，你自己也没什么品味。**对大多数开发者来说，蛮力解法是搜集设计或图形模式的样例，或给 AI 编码 agent 塞够风格规范——那工作量跟你自己手写 html/css 也差不多了。与其干这种繁琐的手工活，不如让主厨呼叫一支厨师小队，然后***摘取你的最爱***。

### 模式 2：晚餐高峰（The Dinner Rush）

周五晚上的用餐高峰，厨房里每个工位——煎台、烤台、冷盘台、甜品台——同时开火。每个厨师负责不同的活儿，但他们同时在出盘，共同完成同一张订单。

这就是"swarms（蜂群）"背后的概念，由 MoonshotAI 在训练 [Kimi-K2.5](https://huggingface.co/moonshotai/Kimi-K2.5) 时开创。在 swarms 中，每个厨师对单一、有边界、**互不相同**的任务负责。这些厨师同时开工，都朝向同一个共享目标。

适合的场景：构建一个应用的多个独立组件、为不同模块写测试，或把页面从一个框架移植到另一个框架。

要让这套配置跑得顺，需要几个条件：

- 你需要一份极其具体的工作范围。
- 这个范围要能拆成独立的、可验证的步骤。
- 每个任务必须有清晰记录的依赖关系。
- 每个任务最好只涉及一组预先定义的文件改动，厨师之间才不会互相覆盖。

***重要*：**关键要求是任务不共享文件。一旦两个厨师需要编辑同一个文件，你就需要换一种模式。

### 模式 3：按道菜顺序上（Courses in Sequence）

品鉴菜单不会一次性全上。前戏小菜（amuse-bouche）先出，才有人开火做前菜；前菜撤盘，主菜才开始摆盘，甜品按部就班等待。但在同一道菜内部，所有工位都在并行烹饪。

这就是**分阶段并行执行（phased parallel execution）**的思想。你把项目拆成一道道菜（或"波次"），后一道严格依赖前一道。每一道之内，任意数量的任务和厨师可以并行。这非常适合大型项目，比如整个应用重建或大规模重构。

要让这种模式成立，你需要依赖树、严格的排序和打磨过的 prompt。可以参考 [https://factory.ai/news/missions](https://factory.ai/news/missions) 看看他们是怎么处理的。

来看一个重建整套 UI 的真实例子。第一道菜探索并测绘了一切，第二道菜则建立在这份共享理解之上。两道菜的厨师都不需要完整的对话历史，他们拿到恰好与自己工单相关的上下文简报。

作为人类，你要清晰地定义需求。课程结构同时给你并行性*和*顺序性——这就是它能比纯蜂群更好地扩展到真实项目的原因。

### 模式 4：从备菜到成菜的流水线装配（The Prep-to-Plate Assembly）

你的厨师们不各自从头造一道完整的菜。一个工位修剪并腌制蛋白质，下一个煎制，再下一个进烤箱收尾，最后由传菜员摆盘点缀。每个工位一个清晰职责，干净交接，绝不让上一单的酱汁拖进下一单。

在这种模式中，厨师沿出菜台顺序接力。每人完成一小步，验证它，然后把工件交给下一站。

**这种模式再适合长时任务不过——只要它们有清晰、可观察、可验证的结果**，也适合重研究的任务或多步流水线。核心原则：不要拖着无关历史在一条巨型 thread 里走。每个阶段只拿完成自己那部分所需的上下文，然后交接。状态活在文件和任务队列里，不在对话里。

*阶段之间干净交接。状态活在文件与任务队列中，不在对话历史里。*

这里有一个目标是在特定硬件上跑自定义模型的例子。特别注意每个厨师的任务如何清晰而有边界。

### 模式 5：Gordon Ramsay 来了

在专业厨房里，厨师做菜，但菜不会直接端给顾客（*我倒希望会*）。它先要通过检查：一个人看火候对不对，另一个人看是否与订单相符、摆盘是否正确。

这最后一种模式与其说是项目架构，不如说是一种***纪律***：把*写*代码的厨师和*检查*代码的厨师分开。一个 builder 烹饪；两个验证者（一个代码评审员，一个视觉/功能测试员）并行验证输出。任何一个验证者标记出问题，builder 就再来一轮。**尤其有了 Codex Spark 这种近乎即时的编码模型，添加验证几乎免费。**

在这套工作流中，同一时刻只有一个 builder 在写，但多个验证者可以同时运行。这是避免合并冲突和上下文漂移最重要的单一规则，并且它适用于本清单上*每一种*模式的内部。

**何时使用：永远。无论你跑哪种模式，都把它叠加在上面。**把构建与验证分离，能在失败级联到下游任务之前抓住它。验证环节使用浏览器自动化、截图和确定性测试。目标是：任何厨师的输出，没有"确认可用"的证据就不许端上出菜台。
