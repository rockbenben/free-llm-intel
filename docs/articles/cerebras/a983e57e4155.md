# 用 Docker 化执行环境扩展 SWE Agent 数据收集

Vijay Srinivas

作者：[Gune S](https://www.linkedin.com/in/gune-s-54892643/)、[Sahil Lathiya](https://www.linkedin.com/in/sahil-lathiya-5255741a9/)、[APOORV PANDEY](https://www.linkedin.com/in/apoorv-pandey-a13692116/)、[Mritunjai Chandra](https://www.linkedin.com/in/mritunjai-chandra/)、[Vijay Srinivas](https://www.linkedin.com/in/vijay-srinivas-h/)、[Ganesh Venkatesh](https://www.linkedin.com/in/ganesh-venkatesh/)

### 引言

我们专注于构建高质量 agentic 流程训练平台，包括对强化学习（RL）、数据集和 ML 配方（recipes）的支持。几周前我们发布了 RL 平台，而这个项目代表我们的数据集基础设施计划。

### 为什么这很重要

**挑战**：训练面向软件工程的有效 AI agent 需要：

- **高质量数据集**：多样化的优质语料，包含 PR 标题/描述、issue 标题/描述、base commit、补丁、单元测试文件，以及 GitHub 提供的其他元数据
- **可复现环境**：跨不同仓库一致的执行环境
- **高质量信号**：用于学习的清晰通过/失败信号（FAIL_TO_PASS 测试）
- **规模**：数千个多样化的真实软件工程任务
- **验证**：通过正规测试确证过的测试结论

**我们的方案**：我们的数据策展流水线加仓库沙箱生成器提供：

- **数据策展流水线**：内建对仓库的查询能力，提取其结构、依赖，以及训练 SWE agent 所需的各类字段
- **自动化代码执行基础设施**：处理复杂的依赖解析与环境搭建
- **丰富元数据**：内嵌用于训练信号的测试分类
- **可移植性**：处处可运行的自包含 Docker 镜像

### 对 Agentic AI 开发的影响

这套基础设施使得以下成为可能：

- **监督学习**：在带清晰前后状态的、经过验证的 bug 修复上训练模型
- **强化学习**：提供带奖励信号（测试结果）的可执行环境
- **评估**：衡量 agent 表现的标准化基准
- **研究**：跨不同方法的可复现实验

### 规模化愿景

我们的方法论被设计为可**数量级**扩展：

- **当前能力**：全自动化处理 1000+ 实例

我们正在为面向软件工程 AI agent 的最大规模高质量数据集打地基。

### 数据集收集方法论

为构建高质量、多样化的真实软件项目语料，我们从三条互补的流水线获取仓库：PyPI 关联项目、高影响力 GitHub 仓库，以及多模态代码库。每条流水线都设定了严格的质量与活跃度阈值，确保只纳入成熟、协作开发的项目。

- **基于 PyPI 的仓库实例。**我们从与 PyPI 包关联的仓库入手，聚焦社区参与度高的项目。要求仓库以 Python 为主（≥60% 代码量）并展现有意义的开发活跃度：至少 100 个 pull request 或 issue、100 个 fork。应用这些过滤并再做一次去污染（decontamination）后，这条流贡献了约 **107,000 个精选仓库实例**。
- **基于 GitHub Star 的仓库实例。**为捕捉广泛采用、有影响力的项目，我们另行按 GitHub 热度收集仓库。只考虑至少 10,000 star、且有明确活跃维护证据（至少 100 个 PR 或 issue、100 个 fork）的仓库。套用同样的 ≥60% Python 要求与去污染，再得 **50,000 个高质量实例**。
- **多模态仓库实例。**最后，为把数据集扩展到纯 Python 项目之外，我们纳入了将 Python 与其他语言或数据模态结合的多模态仓库。使用同样的活跃度标准（≥100 PR/issue 且 ≥100 fork）与 ≥60% Python 阈值，我们从一个精选的 **700 个多模态仓库**集合中提取了 **3,500 个实例**。

这些流水线一起确保了跨包生态、热门开源项目和丰富多模态代码库的广泛覆盖，产出适合下游分析与模型训练的、均衡且过滤严格的数据集。

### 代码执行环境的架构

**代码执行平台总览**

该代码执行平台对 Python 仓库进行端到端的差分测试自动化：搭建隔离工作区，分析仓库结构与依赖，生成优化过的 dockerfile，构建环境并用自动的 LLM 修复处理构建失败。随后以迭代自动纠错的方式做稳健的测试发现，在隔离的 docker 运行中分别执行基线测试与打补丁后的测试，比对结果，把测试分类为 FAIL_TO_PASS 或 PASS_TO_PASS。一个"反转"阶段通过撤销主补丁重新校验分类，确保准确。最终，系统产出完整工件，包括日志、docker 文件、摘要，以及捕获整个构建、测试与差分分析生命周期的详细 JSON 结果。
