# 排查「死掉的 MoE 模型」：一份分步指南

[Daria Soboleva](https://www.cerebras.ai/author/dariasoboleva)[Aman Tiwari](https://www.cerebras.ai/author/aman-tiwari)

### 读到最后你会看到什么

我猜你一听到 Mixture-of-Experts（MoE），立刻就会想「这又是只有 Google 才训得起的东西」，对吧？这正是我们今天要打破的迷思。没错，那些有名的 MoE 模型确实很大——是万亿参数的量级（Kimi Team, 2025）。但这就好比因为存在 GPT-4 就干脆不碰神经网络。从零搭一个感知机网络，不到 20 行代码就够了。

遗憾的是，「训练 MoE 模型对大多数人来说高不可攀」是个相当普遍的误解。事实上，我们写这篇博客的时候，Aman 提出的第一个问题就是它：做这件事难道不需要一大集群算力吗？但有一个反直觉的事实——MoE 关键不只在规模，它是一种你可以把规模缩小、照样能看到同样好处的技术。

读完这篇博客，你会学会训练一个小型 MoE 模型，并在 GPT-2 这个规模上击败稠密（dense）模型。至于算力——你只需要自己的笔记本（好吧，也许再加一台小型加速节点，但绝不是数据中心）。下面就开始。

### 前置要求

如果你还不熟悉稠密的 GPT-2 风格模型，我们强烈建议先看 Andrej Karpathy 的 [Let’s reproduce GPT-2 (124M)](https://www.youtube.com/watch?v=l8pRSuU81PU)，然后再回到这篇博客——我们在它的基础上继续搭建，专门聚焦 MoE。

### 环境准备

让我们为大规模训练 run 做好准备。我们基于 [modded-nanogpt](https://github.com/cat-state/modded-nanogpt-moe/tree/blogpost-version) 代码库（Jordan et al., 2024a）来搭建，它提供了一个扎实的 124M、GPT-2 同类的基线，在 FineWeb 数据集上训练（Penedo et al., 2024）。我们的模型是一个 decoder-only transformer，使用了  (So et al., 2022)、RoPE (Su et al., 2023)、RMSNorm (Zhang and Sennrich, 2019) 和 QK-Norm (Henry et al., 2020)，用 Muon 优化器（Jordan et al., 2024b）训练。它基本上就是一个现代化版的 GPT-2，11 分钟就能训完。如果你有 Cerebras 硬件可用，可以在上面跟着做；没有的话，在 GPU 上也一样跑得通。要开始的话，先下载 NanoGPT 的 MoE 分支：

上面的步骤下载好 FineWeb 训练文件之后，用你顺手的编辑器或 IDE 打开 *train_gpt_moe.py*（想直接跑实验的话，这个文件里有我们完整的 MoE 实现）。或者，如果你更想跟着一行行写、把 MoE 的各个组件一步步实现出来，那就打开 *train_gpt.py*。另外，一切都是可以缩小的（模型规模也一样），我们鼓励你随便折腾——把这篇博客当成起点。去把东西弄坏，去试奇怪的设置，看看会发生什么。

### expert 网络放在哪里

好了，你已经把 modded-nanogpt 代码库拉到本地，正盯着代码看。激动人心的部分来了——把 (Soboleva, 2025a) 里提出的那个 MoE 概念变成你真能训练出来的东西。第一步相当直接：把单个前馈网络（FFN）换成多个 expert 网络。

图 1：每个 expert 其实就是 GPT-2 的 FFN。expert 类的定义见 [train_gpt_moe.py#L184-L196](https://github.com/cat-state/modded-nanogpt-moe/blob/blogpost-version/train_gpt_moe.py##L184-L196)，实例化逻辑见 [train_gpt_moe.py#L263](https://github.com/cat-state/modded-nanogpt-moe/blob/blogpost-version/train_gpt_moe.py##L263)。

从图 1 可以看到，每个 expert 就是 GPT-2 的 FFN 原样复制粘贴过来的（两层线性层，中间隔着一个非线性）。那这些 expert 网络该怎么用？图 2 展示的是我们在处理 token 批次时如何组合各个 expert 的输出，它把 (Soboleva, 2025a) 中的单 token 做法扩展到了批量。注意，这个实现并不快，还会浪费计算，但对教学很有用。

图 2：批量处理时的 expert 混合（见 train [train_gpt_moe.py#L208-L225)](https://github.com/cat-state/modded-nanogpt-moe/blob/blogpost-version/train_gpt_moe.py##L208-L225)。

正如本系列第 2 部分所说，MoE 的 routing 很棘手，它可能把这些模型理论上带来的好处彻底抵消掉。接下来的小节里，我们保持 expert 架构和混合逻辑不变，只摆弄 routing，观察它如何改变模型的质量。先说好：我们会先把事情弄糟、会犯错，就像真实生活里实际发生的那样。

### 学习型 routing

学习型 routing（learned routing）是业界标准，Google、OpenAI、Anthropic 等发布的那些出色 MoE 模型用的都是它。现在轮到你亲手搭一遍了。理论部分在第 2 部分已经讲过，这里我们只关注它的实际实现。图 3 显示，学习型 routing 有两个目标：一是通过可学习的权重为每个 token 找到最合适的 expert，二是通过负载均衡让所有 expert 都被用上。这组双重目标通常正是我们给自己挖坑的地方，那我们来看看把这个训练 run 启动之后会发生什么。把辅助损失（auxiliary loss）接进模型，在所有层上求和，再以 0.01 的权重加到交叉熵损失上。

图 3：学习型 routing 的实现：（上）决定 token-expert 分配的 router 逻辑，（下）用于负载均衡的辅助损失。router 的定义在 [train_gpt_moe.py#L228-L240](https://github.com/cat-state/modded-nanogpt-moe/blob/blogpost-version/train_gpt_moe.py##L228-L240)，负载均衡逻辑在 [train_gpt_moe.py#L242-L250](https://github.com/cat-state/modded-nanogpt-moe/blob/blogpost-version/train_gpt_moe.py##L242-L250)。

该来看损失曲线了。图 4 显示我们的 MoE 已经打败了稠密 GPT-2 基线。恭喜，你实现了第一个能工作的 MoE 模型。不过等等——我们说过会给自己挖坑，可一切都很顺利，那这份指南为什么还存在？你可能已经注意到，在 MoE 101 系列第 2 部分里我们承诺过：4 个 expert 配学习型 routing，相对稠密 GPT-2 基线大约有 2% 的提升。现在我们只拿到这一半收益，另外 1% 去哪儿了？这就是大多数研究者都经历过的时刻：照着别人的论文实现，结果并没有论文里承诺的效果。在这份指南里我们要把它修好，一起正经地排查一遍。

图 4：4 个 expert 配学习型 routing 的 MoE 优于稠密 GPT-2 模型。损失的领先幅度随着训练不断拉大，到我们目标的 2.4B token 时为 1%。要复现这张图，请运行 [plot.ipynb](https://github.com/cat-state/modded-nanogpt-moe/blob/blogpost-version/plots/plot.ipynb)。

记住，我们的 router 有两个目标：为每个 token 找到最合适的 expert，以及让所有 expert 都被用上。第二个目标很容易验证，直接看 expert 利用率统计就知道做得怎么样。图 5 显示每一层几乎完美均衡。双重目标里的负载均衡这一部分看起来运转良好——问题不在这里。

图 5：expert 利用率（跨层平均）很快收敛到接近 25%；总共 4 个 expert，这是完全均衡的情形。要复现这张图，请运行 [plot.ipynb](https://github.com/cat-state/modded-nanogpt-moe/blob/blogpost-version/plots/plot.ipynb)。

回到「为每个 token 找到最合适的 expert」这个嫌疑对象上。要排查 router 到底在学什么，可以看梯度范数。问题出在图 6 上：router 从损失的交叉熵部分拿到的梯度几乎为零！也就是说，你的 router 只直接学会了负载均衡。而它本该学会「哪个 expert 对每个 token 最好」的那部分呢？那个信号根本没有传到 router。先别往下翻看答案，回头看看图 3 里的代码。你能找出那个让我们的 router 拿不到交叉熵梯度的 bug 吗？给个小提示：特别考虑一下 *top_k = 1* 的情况。

图 6：*top_k=1 * 的学习型 router 从交叉熵损失拿到的梯度为零，梯度只来自目标中的负载均衡部分。要复现这张图，请运行 [plot.ipynb.](https://github.com/cat-state/modded-nanogpt-moe/blob/blogpost-version/plots/plot.ipynb)

### 修复学习型 routing

我们刚学到的这一点很重要：即使负载均衡完美无缺，学习型 routing 也可能完全没用。router 确实在学东西，但它真正学会的只有负载均衡，而不是如何 routing 出专业化的 expert（也就是改善交叉熵）。遗憾的是，许多 MoE 论文从不提这个问题，大多只盯着负载均衡的毛病，于是白白丢掉了可观的性能……

好，我们来诊断这个 bug，你可以对照一下自己猜得对不对。当 *top_k = 1* 时，有 *gate.sum(dim=-1, keepdim=True) = gate*，于是我们的归一化 *gate = gate / gate.sum(...)* 变成 *gate = gate / gate = 1*。这意味着交叉熵梯度永远到不了 router 权重，学习信号就此中断。注意这专门是 *top_k = 1* 才有的问题。而在 *top_k = 2* 时，从图 7 可以看到梯度流看起来是正常的。为什么？两个 expert 同时激活时，gate 在归一化过程中保留了它们之间的相对差异，router 仍然在学哪个 expert 该拿到更大的权重。这就像只问「你有兴趣申请数学学位吗？」，没有其他选项可供比较，就很难做出有把握的选择。但如果你问的是：「数学学位和物理学位你更感兴趣哪个？」，那么你对数学学位 0.9 的置信、对物理学位 0.1 的置信，立刻就让决定容易得多。

图 7：*top_k=2* 的学习型 router 从交叉熵损失拿到了相当可观的梯度，与 *top_k=1* 那种梯度为零的情况不同。要复现这张图，请运行 [plot.ipynb](https://github.com/cat-state/modded-nanogpt-moe/blob/blogpost-version/plots/plot.ipynb)。

这也就提示了我们的修法。针对 *top_k = 1*，我们引入一个「空 expert」（null expert）——一个永远不会被激活的幽灵 expert，但它给了 router 一个可用来对比预测的选项。与 shared experts 做法会同时推高参数量和计算量不同，我们的幽灵 expert 不带来任何计算开销，也不增加任何参数。思路和 Bachlechner et al., 2020 处理神经网络深层梯度消失问题的做法类似：我们要增强流入 router 的梯度。图 8 展示了可以怎么实现。

图 8：加入一个「空 expert」，让 router 有可供对比的对象，从而带来更好的梯度流。

*null_expert_bias* 是一个可调参数，我们几乎没做调优，在实验里把它设为 10。现在 router 必须证明：选择一个真实 expert 为什么比选那个幽灵选项更好，这正是我们想要的对比。来看看它是否真能改善梯度流。图 9 显示，我们终于从双重目标的交叉熵部分收到了可观的梯度，而且和图 7 中 *top_k = 2* 观察到的行为吻合。「学习」这才真正开始。结果是图 10 所示：我们的 MoE 模型现在比稠密基线好 2%。一行修复换来的是相当大的收益（而且按我们的经验，规模越大它越明显）。

图 9：在 *top_k=1* 的情况下使用「空 expert」，抬升了来自双重目标交叉熵部分、流向 router 的梯度。要复现这张图，请运行 [plot.ipynb](https://github.com/cat-state/modded-nanogpt-moe/blob/blogpost-version/plots/plot.ipynb)。

花点时间想想刚才发生了什么。你手上是一个坏得很隐蔽的 MoE 模型，学习信号完全中断了。你查到根因、做了针对性修复，然后——信号又流起来了。我们相对稠密 GPT-2 基线拿到的收益几乎翻了一倍。注意，你不必增加参数量或计算量，连超参扫描都不需要。你只是修好了 MoE 网络里一个很小的部件：router，而它极大地改变了模型的质量。

图 10：带「空 expert」的学习型 routing、4 个 expert 的 MoE，在目标的 2.4B token 处比 GPT-2 模型好 2%。「空 expert」的存在让相对稠密基线的收益几乎翻倍。要复现这张图，请运行 [plot.ipynb](https://github.com/cat-state/modded-nanogpt-moe/blob/blogpost-version/plots/plot.ipynb)。

### 我们做到了什么

还记得开头吗？你大概也曾认定 MoE 不过是又一项「只有 Google 量级才玩得起」的技术。我们就是来把它证伪的。我们拿了一个很小的 124M 参数 GPT-2 模型——那种用最少算力预算就能训起来的模型——让它跑出了效果。学习型 routing 一开始并没有在「学习」，一个小修复就让它活了过来。我们观察到，仅仅调整 router 带来的收益就非常可观。我们没有调超参，也没有把算力花在 batch size 扫描上，只是诊断出真正坏掉的地方，做了针对性修复，然后把它解决了。

MoE 棘手，因为它们会以很隐蔽的方式失败。这是个不太讨好的观点：完美的负载均衡并不意味着 router 在「学习」。现在你也知道了。但 MoE 也是实打实的，一旦你修好了真正坏掉的部分，收益立刻就来，而且相当显著。

我们的排查方法（由假设驱动的追查、测量正确的指标、理解失败模式）远不止适用于 MoE。当你的模型死掉时（一定会发生的），你会知道怎样把它们救回来，而这件事并不需要一座数据中心。

好，你已经能训练一个 4 个 expert 的 MoE 模型了，但试着把它扩到 64 个 expert，就会撞上 OOM 错误。在 [规模化 MoE：让稀疏模型在真实硬件上跑得快](https://www.cerebras.ai/blog/moe-guide-scale) 里，我们会排查这背后的原因并把它修好。

### 讨论

做这篇博客的过程中，我们还发现了一些别的零散现象：

- 只把归一化 *(gate = gate / gate.sum(...))* 去掉并没有帮助（至少 *top_k = 1* 的情况没有）。虽然确实有来自交叉熵损失的梯度在流动，但「学习」信号仍然极弱，效果比稠密 GPT-2 基线更差。
- 因为我们是在 modded-nanogpt 上搭的，所以用了 Muon 优化器。我们也在 EleutherAI/nanoGPT-mup 之上跑了一些实验，它用的是 Adam，transformer 架构也稍旧一点。我们发现，用 Adam 时，如果梯度信号只来自负载均衡损失（也就是带着归一化 bug 的那种情形），学习型 routing 超不过稠密 GPT-2 基线；而用 Muon 时它确实能超过。也许 Muon 能帮助 expert 网络在 router 监督较少的情况下学起来，不过我们没有深入研究这一现象。
- 我们试过把 hash routing 跑通——就是 (Soboleva, 2025b) 里介绍的那个版本。出人意料的是，无论用 Adam 还是 Muon 优化器，hash routing 都没能超过稠密 GPT-2 基线（除非把 GPT-2 风格的网络只堆到 4 层）。我们没有花时间去弄清 hash 实现坏在哪里，所以如果你去试并且找到了 bug，请告诉我们。
