### 现在一切都更容易了。

我捣鼓 agent 编排已经有一段时间了。目前我全天候跑着 10-20 个 agent。AI agent 已经真的能把我的想法变成现实。

和许多开发者一样，我一直在[感受 token 焦虑](https://writing.nikunjk.com/p/token-anxiety)。我现在能做的事情比历史上任何时候都多，每当有一点空闲时间，我就想再启动一个 agent 会话。

- 看到一个我不想花钱买的酷炫产品？Codex 会替我建一个。
- 有个想看到成真点子？Codex 会替我建一个。
- 重复做同一件事让我有点烦？Codex 拜托了。

如果你有一支无限耐心、聪明又乐于助人的 agent 大军等着你的下一条命令，我们为什么不加以利用呢？

### 上限在哪里？

我的职业生涯从 Web 开发起步。那时候，做一个精致的作品集网站要花上几周。

我清楚记得 agentic 工程刚开始流行时，人们构建应用和网站的速度前所未有。当时的工具和执行框架主要还是围绕编码。

所以当我看到 Figma MCP 的更新时，格外惊讶和兴奋。基于 Figma 设计稿来构建前端一向更有乐趣——前端开发者与设计师的协作，正是你喜爱的应用和网站如此出色的原因。

Codex 能帮忙完成这个过程吗？

### Codex + Figma——打破工作孤岛

我想验证 Figma MCP 的最新功能能否让我轻松地用 Codex 创建设计面板。一个 agent 能不能准确、快速地创建新设计？

这在组织内部打开了很多扇门：人们可以更有效地跨部门协作。想象每个产品讨论都有自己不断演进的 Figma 设计板……当利益相关方还在讨论产品需求时，agent 就能实时演进 Figma 设计！

设计师和开发者也能更顺畅地在"设计功能"与"开发功能"之间切换，甚至在两者需求之间做协调。为了验证这一点，我开始动手折腾 Figma。

### 成功长什么样

它必须比让 agent 直接复刻一个网站更简单、更稳定。它应该让"迭代设计"比"从零写代码"容易得多。

示例成功标准：

- 我可以给 Codex 任何网站链接
- 它需要摄取该网站，并在 Figma 中重建一个一模一样的复刻版
- 该复刻版必须遵循正确的设计规范正确的组件切分使用变量进行设计（background-color、文字层级）设计应可直接从 Figma 落地实现
- 在 Figma 中创建这些设计应少于 30 分钟
- 全程无需动手，不需要人工引导

### 配置 Codex 和 Figma

开始之前的一些前置条件：

### 常见问题。

我在 20 多个会话中测试了这套工作流，遇到 3 类反复出现的问题：

### 1. Figma 设计极其消耗上下文

Figma 中的单个视口，仅页面的 HTML、CSS 和内容就可能吃掉 64k-128K token。这还没算上：

- 思考轨迹（thinking traces）
- 工具调用与结果
- 模型修补小问题的开销
- 我的 prompt 和指令
- 系统 prompt 与工具定义
- MCP 与 Skill 定义

等 agent 搬完半个页面，它就得触发压缩（compaction）来腾出上下文空间继续工作。而每次压缩，模型都会偏离实验的原始目标。

### 2. 移植设计太慢了。

有一次跑了两个多小时，agent 只搬进 2 个页面，之后试图继续时，就陷入了"看网站-看设计-查工具调用-读设计"的死循环。

这样行不通，尤其目标网站还很小，远不及我真正想测试的规模。我不能等上两个小时，结果还要再开一个会话，再次掉进同一个循环。

### 3. Agent 没有基于最新版本的 MCP 训练过

我看着模型飞快取得一些进展，兴奋起来，然后几分钟后它拒绝再使用 MCP。它没有用厂商认可的工具，而是决定自己造一个粗糙的 HTML 导入器。

它试图用 agent-browser CLI 把设计手动导入 Figma——这行不通，因为 Figma 不支持这个工作流。无论我怎么引导，一旦上下文里积累了 10 万 token，它就会退回到这个行为。

### 4. 应对错误

要发挥这套配置的最大价值，我强烈建议使用最新版本的 Codex、Plugin/MCP，并使用 [Figma 官方打包好的 skill，它会教会模型如何使用 MCP。](https://github.com/figma/mcp-server-guide/blob/main/skills/figma-use/SKILL.md)

**我遇到的主要问题：**
- Figma 设计占用过多上下文
- agent 开箱即用地不知道如何使用更新后的工具
- 运行时间过长（任务拖到几个小时）

**我的解决方法：**
- 用子 agent 确保不压垮单个 agent
- 在 Figma 的 GitHub 上查找 skill 和指南
- 并行化工作

### Codex 能从自己的错误中学习。

我让 Codex 复盘所有历史会话，找出失败点，然后上网搜索正确的使用指南应该是什么。

1. 它搜索了我的会话历史
2. 它判断出自己一直在用错误的工具
3. 它上网搜索并[找到了 Figma write skill](https://github.com/figma/mcp-server-guide/blob/main/skills/figma-use/SKILL.md)
4. 它返回了一份定义清晰的 prompt，我可以不断微调直到跑通

这带来了巨大差别。原本完全跑不通的东西至少能跑起来了——但速度仍然太慢，不可接受。

### 让 Codex 全速轰鸣（BRRRR）。

最后一件要解决的事是输出速度：所有事情都在串行执行。如果我想让它复制 5 个页面，它会一丝不苟地一个一个抄，这会耗到天荒地老。

这是两个主要问题造成的：

1. Codex 需要消化天文数字般的 token 量
2. 一切都是顺序执行的

**要理解这套机制，可以想象：**

- 主编排 agent 只做一件事：派生子 agent
- 每个子 agent 拿到目标网站中 1 个页面的链接
- 每个子 agent 只做自己那个页面，别的什么都不碰
- 编排者审查各模型的输出，然后要么放行，要么再派生子 agent 去修复问题

一开始，我想把编排者的指令打磨到"绝不犯蠢"的程度，所以用了 GPT-5.4-Medium，迭代了几轮；跑通之后，我就有了一个范围足够清晰的复用 prompt，交给 GPT-5.3-Codex-Spark 就能处理。
