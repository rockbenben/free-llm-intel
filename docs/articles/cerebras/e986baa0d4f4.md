# 我们是如何构建内部知识库的

Isaac Tai

Daniel Kim

Mike Gao

员工每天向我们内部知识库提问超过 15,000 次。它上线仅 3 个月，就已成为公司内采用最广泛的内部工具之一。使用者包括人类、自动化程序和 agent。

在 Cerebras，我们的团队横跨数据中心运维、芯片设计、硬件、训练、推理、云平台等领域。每年有数百名新员工加入，我们的沟通渠道一度被重复的问题淹没：

> "X 在哪里能找到？""Y 方面的专家是谁？""Z 是什么？"

我们构建了 Cerebras Knowledge，帮助人们把人与系统同有用的信息连接起来。

### 到数据所在的地方去接它

在一家组织内部找信息很难。数据散落在各个工具里，几乎每个季度都会有人提出同一个聪明的解法：把所有东西都记录到一个平台上，让一切信息集中在一个地方。而"单一事实来源"的梦想，实践中几乎从未成立。

信息总是在最顺手、最符合人体工学的地方产生：文档里的修订建议、Slack 里的帖子、GitHub 里的代码引用、Jira 里的状态元数据。这些平台是为其特定领域量身打造的，经过多年产品工程与分析的打磨。在 Google Docs 里讨论一个 pull request 会是糟糕透顶的体验。

所以我们着手设计的系统，要求对既有行为的最小改变。在数据采集这一侧，这意味着直接从每个平台抽取数据。

### 知识库的解剖结构

我们的知识库提供三样东西：

- 一个收集与存储内部数据的平台。
- 一个查询这些数据的平台。
- 一个强制执行认证与授权、并带审计和分析的层。

核心是一张单一的 Postgres 表，存放来自众多来源的 embedding、原始摘要和元数据。系统持续摄取全公司的数据，维护着一个随时可查的数据存储。

我们想要一个简单、却能兼容多数数据形态的数据接口，也希望 Cerebras 的其他开发者能构建自定义连接器。最终的设计刻意保持简单：从 Slack 帖子到 netlist，每个来源都落入同一张 embeddings 表；表里的任何内容都可以通过同一接口立即查询：

每个数据源自己定义数据是什么、如何连接、多久抓取一次。无论来自 Slack、代码仓库、文档系统还是自定义数据库，产生的每一行 embedding 都遵循同一接口。

### Slack

Slack 是我们需要重点设计的最重要数据源。全公司最新的工程讨论都发生在这里。

### 我们如何处理非结构化的 Slack 对话

我们最初测试过：对原始文本做简单 embedding 是否够用。很快我们意识到，单靠向量搜索不足以匹配所有相关数据。

Slack 消息带来几个挑战：

- 信息密度天差地别："hey yeah sure mike"和一段详尽的 kernel 讲解都是消息。
- 消息长短不一，短消息在余弦相似度上经常胜过更长、更详细的消息。
- 一条消息的含义往往取决于它所在的对话。

我们需要混合方案。我们构建 Slack 摄取时，让每个 thread 都能同时被多种搜索技术检索到，各技术正好补上其他技术的短板：

- **全文搜索**捕捉 embedding 会模糊掉的精确 token：报错字符串、flag 名、主机名。工程师粘贴一条原样报错时，精确的词法匹配几乎总是最好的证据，任何语义相似度都不应盖过它。
- **Embedding 搜索**捕捉转述。问"restore hangs after manifest load"的人和回答"checkpoint stalls on the NFS mount"的人可能词汇毫不重叠。向量相似度正是把问题与换了措辞的答案连接起来的东西。(1)
- **逆文档频率（IDF）**把信号从口水里分离出来。一条围绕罕见 token（比如某个冷门 config flag）构建的短消息值得上榜。"sounds good, thanks!"在 embedding 空间里离很多查询都很近，但一旦考虑词的稀有度，得分近乎为零。
- **时间衰减**编码了"Slack 答案会过期"这一事实。两个 thread 可以回答同一个问题，而六个月前那个描述的可能是已不存在的 infrastructure。当相关性相当时，新的 thread 胜出。

### Socket Mode

为了实时收集数据，我们在 workspace 里安装了一个 Slack bot 并以 Socket Mode 运行。Slack 会通过一条持久 WebSocket 把每个消息事件推送给我们，因此我们无需轮询 Web API、耗尽它的速率限制，就能得到实时更新。

当一个事件到达，我们立即确认它，用稳定的 event ID 去重，并把该消息标记给摄取消费者。

摄取消费者不会孤立地保存一条新消息。它会解析消息所属的 thread，从 Slack API 重新拉取整段对话，包括主帖和每一条回复，然后把整个 thread 作为一行写回。因此，对既有 thread 的一条回复会重新拉取主帖和所有兄弟消息，使存储的内容、参与者列表和最后活动时间戳始终反映完整对话。

我们系统中的每个 Slack channel 都有自己独立的数据源。这为数据新鲜度提供了细粒度调优。例如，一个团队可以选择更高频地摄取繁忙的 incident channel。

### Threads 和消息

Slack 原始文本一落地就可做关键词搜索，因为我们对原始内容维护着一个 Postgres 全文（GIN）索引。但要让向量搜索真正有用，我们还要做一些额外处理。(8)

在蒸馏（distillation）阶段，一个 LLM 从完整 thread 中抽取结构化数据：

- 一个工程师真的会拿去搜索的一句话问题。
- 一段简短摘要。
- 解决方案（resolution）。
- 提及的系统与代码引用。

我们把这些数据点 embedding 后写入共享的 embeddings 表。原始对话记录并不直接 embedding。实验中，当 thread 被归一化成一致格式时，准确率显著提升。(7,9) 额外的元数据也让语义匹配拥有更有用的信号。

### Bursting

此时 Slack 搜索已经不错，但我们不断遇到同一个问题：长 thread 里的重要消息未必会体现在 thread 级摘要中。

为了增强单条消息的信号，我们使用 bursting。一个 burst 是同一作者的连续若干条消息。我们会对单个 burst 做 embedding，并把 thread 主题作为上下文前置(2)——因为有时答案就藏在某一条跑题的消息里，而它的词汇从未进入 thread 摘要。Burst embedding 让那条消息可以独立被找到。

为了阻止低信号数据进入数据库，每个 burst 会针对一组加权信号打分，越过阈值才会被 embedding：

- 它包含在语料中相对稀有的 token，IDF 至少 4.0。
- 合并后的 burst 至少 200 字符。
- burst 中一条或多条消息带有 reaction，提供社交加成。

蒸馏之后，达标的 burst 会被 embedding，并与 thread 级记录一起存入 embeddings 表。

### 代码仓库

最初我们争论过是否有必要给代码仓库做 embedding。随着 Claude Code 等命令行工具的兴起，在"grep is all you need"看似成立的时候去做代码 embedding 感觉有悖直觉。在与业界同行交流并阅读 Cursor 关于大型代码库语义搜索的结论后，我们决定试一试。

我们有许多内部仓库，有的超过 40 GB。我们最关心的是如何高效地保持它们新鲜。

### 用 CocoIndex 维护代码 embedding

几轮实验后，我们选定了 CocoIndex——一个专注于代码库向量化的开源文档 embedding 框架。

对每个仓库，我们按语言特定的正则边界切分代码，边界从粗到细排序。切分器优先尝试更高层的边界，比如类；如果产生的 chunk 仍然太大，就退到方法边界，再到更小的块。我们把产生的 chunk 做 embedding，向量写入 Postgres。一个文件可能在不同具体程度上产生多个 embedding，比如文件级和函数级记录。

CocoIndex 在 Postgres 中跟踪同步元数据。每次 commit，它只对变更的代码 chunk 重新 embedding、重新导出，而不是重算整个仓库。这对我们格外合适，因为同步状态和 embedding 存储就在同一个数据库里。

随着代码库数量增长，我们把仓库接入搬进了配置文件，让团队可以自行提交，其中包括文件路径级别的白名单和黑名单。

### 自定义数据源

有些团队已有自己的数据库，不想为了进知识库而把数据搬去 Slack 或文档系统。他们想在自己的既有表上拥有同样的查询接口。

为支持这一点，我们把自定义来源当作插件脚本。团队提一个 PR，附上一个小型 Python 模块——知道如何从自己的系统读取并发出与我们 embeddings 表同形状的行列——再加上一个对应的数据源条目。

只要脚本按与其他 embedding 行相同的 schema 写入共享数据库，技术栈其余部分就无需改动。数据即可与 Slack、代码、文档一起被查询，系统其他地方不需要任何特殊处理。

### 规划与工具扇出

对每个查询，我们先跑一轮简短的规划：由 LLM 决定哪些工具和数据源可能有用。主要工具：

- subsystem_index：逐文件的 LLM 摘要。
- search：跨 Slack、wiki、代码及其他已索引来源的统一向量流水线，内部完成合并与重排。
- search_slack：直接检索 Slack。
- search_code：对源代码仓库跑 ripgrep。
- recent_prs：与问题相关的近期 pull request。
- who_knows：在某主题上展示过专长的人。

规划器基于一份紧凑的索引摘要工作：存在哪些项目、每个项目里有哪些来源、每个来源擅长回答什么。给定用户查询和生效范围，它发出工具选择，由执行器并行扇出，归一化成统一的证据格式，再交给最终综合的 LLM。(4)

平滑常数让"共识"比"单票强推"更重要：一个在多个检索器里都排在前列的文档，可以击败只在其中一个检索器里排第一的文档。然后我们把重复的 chunk 合并回同一个来源，限制每个文件能贡献的结果数量，最终得到一个更多样的前二十。

我们把原始查询和这些候选发给一个小型 reranker 模型。它给每份文档打 0 到 10 分，我们保留前十。(6)

排名最终确定后，我们为胜出者补回上下文。例如，匹配到一节 wiki 时，我们会把相邻的两节也拉进来，让被切分拆散的标题、前提条件和注意事项不丢失。这让读者拿到一个完整的片段，而不是一段孤立、缺失重要上下文的段落。

所以 search 的输出是一包丰富的证据：由不同检索器融合而来、在来源级去重、针对实际提问重排，最后才扩展上周边上下文。

### MCP

在 MCP 集成中，我们把检索积木作为直接工具暴露，而不是藏在一个"回答这个问题"的端点后面。这些工具刻意保持简单、尽可能不含 LLM，让客户端可以又快又便宜地查询它们。(5)

每个 MCP 工具对应一个底层检索原语，例如 search_slack、search_code、search 或 who_knows。工具的输入和输出狭窄、结构化且稳定，使任何客户端或 agent 都能轻松调用，而无需把额外的编排逻辑嵌进工具本身。

多数工具只跑一条查询流水线——向量搜索、词法搜索或 ripgrep——应用轻量的打分启发式，然后返回原始证据行。

Claude Code 或任何兼容 MCP 的 agent 成为编排引擎。它决定调用哪些工具、按什么顺序、如何把结果组装成最终答案或代码编辑。检索层本身不依赖那些 LLM 决策即可服务请求。

### Web UI

在 Web UI 中，同样的工具都存在，但它们接到的是一条为每个用户问题端到端运行的完整查询流水线。UI agent 承担规划器和执行器步骤。

**规划器：**一次轻量 LLM 检视查询和当前项目，选择要调用的检索工具，例如 search、search_slack 和 subsystem_index。

**执行器：**系统并行扇出这些工具调用，收集结果，归一化成共享的证据 schema，附得分、时新性和来源提示。

**综合：**最后一次 LLM 接收类型化的证据包与原始问题，产出 UI 中展示的答案，包括引用、注意事项和跨来源综合。

从用户视角看，Web UI 就是"问一个问题，得到一个答案"。底层跑的正是 MCP 客户端可以显式复刻的 planner → executor → synthesizer 模式。

### 组织

随着语料增长，"到处搜所有东西"迅速变得没用。编译器团队的工程师不想要 infrastructure runbooks 出现在结果里，反之亦然。项目（Projects）就是我们让搜索默认相关的机制。

### 项目与作用域搜索

我们引入"项目"作为组织查询所运行于其上的工作区的主要方式。一个项目是一组命名的数据源捆绑：某个团队或计划相关的特定 Slack channel、代码仓库、内部数据库和文档空间。

项目刻意保持轻量。同一个数据源——比如共享的 incidents channel 或中心平台仓库——可以被多个项目引用，而无须复制。

### 接入与默认值

在 onboarding 中，用户会被提示选择或创建与其工作方式匹配的默认项目，例如 ML 训练基础设施、Compiler 或 Data Center Operations。

该默认项目存在用户档案上并自动界定查询范围。新工程师不需要先搞明白哪些 Slack channel、仓库或文档空间重要，就能得到高信号的答复。

### 最后的话

归根结底，知识库之所以好用，是因为它主动到信息已经在的地方去对接人，而不是强行把一切塞进一个僵硬系统。通过组合多种搜索技术，我们能快速浮出证据。最终得到的搜索体验，既足够灵活以容纳真实的公司数据，又足够有结构，能在 Cerebras 持续成长中保持有用。
