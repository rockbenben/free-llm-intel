# 我们用大白话教会 AI Agent 给我们的云控制台做 QA

Kartik Malunjkar

Urmi Banerjee

Hagay Lupesko

Cerebras 以速度闻名。我们的平台提供业界最快的 token 服务——但速度不只是硅片，也是我们多快能把开发者每天都在用的控制台、playground 和计费流程交付出去。而发布越快，一个问题的声音就越大：**我们怎么知道没弄坏什么？**

传统答案是脆弱的机械装置。人类写一大篇充满 CSS selector 的脚本，前端团队改了一个 div 的名字，一夜之间半数套件亮红——不是产品坏了，而是测试坏了。这笔税随你的移动速度水涨船高。

于是我们换了一个问题：*如果测试像 QA 工程师的笔记一样可读、像 QA 工程师一样自己跑、还能在 UI 漂移时自己修好自己呢？*这就是 `console-prompt-tests`——一个内部框架：每条测试都是一段大白话，由一个 LLM agent 驾驶真实浏览器执行。以下是构建过程中的所学。

跑了几个月，回报是具体的——下面每个数字都是*改造前 → 改造后*：

#### 真实运行。一次真实测试的截帧：agent 在 Cerebras Cloud 登录页打开真实浏览器，剩下的它自己来——没有 fixture，没有 mock。

### 测试是一段话，不是一份脚本

这是我们套件中一条完整的真实测试。不是伪代码——这就是系统实际运行的文件：

*一个 .pt 文件——一个 prompt 测试。没有 data-testid，没有 getByRole()，没有 network-idle 等待。只有意图。*

视野里没有任何 selector——没有 `data-testid`，没有 `getByRole('button', { name: /github/i })`，没有等一个可能永远不来的 network-idle 事件。只有意图，用你给队友描述流程的方式写出来。

Agent 读到这个意图，看着*眼前真实的页面*，像人一样找到那个 GitHub 按钮。改类名、重排 DOM——测试耸耸肩。它从来不是在看 markup，而是在看页面。

就这一条性质——**描述行为而非标记的测试**——让系统的其余部分成为可能。

#### 同一场 UI 重构能让 selector 套件全红，却动不了一条 prompt 测试——E2E 抖动最大的源头，没了。

### 它是怎么工作的：一个 agent、一个浏览器、一套协议

底层是三块部件在干活。

**1. Prompt 运行器。**一个 Python 执行器（`run_prompt_with_agent.py`）加载 .pt 文件，交给 LLM coding agent，然后开场：日志、超时、全新浏览器会话、每条测试录屏——所以每次运行都留下一个可以回看的 .mov。

**2. Playwright MCP。**Agent 拿不到浏览器的原始权限。它通过 **Model Context Protocol（MCP）**驾驶一个 [Playwright](https://playwright.dev/) 实例——一个只暴露测试者所需能力的工具接口：*navigate*、*click*、*type*、*wait for text*、*screenshot*。Agent 规划，MCP 执行，浏览器响应，agent 再看一眼。是感知-行动循环，不是固定脚本。

**3. 一个真实、已登录的浏览器。**这些测试对着真实部署运行——staging 环境或本地 Docker 栈——带真认证。我们处理好了麻烦的部分（GitHub 首次登录的设备验证邮件、headless CI 下的 NextAuth 会话铸造），所以 agent 落在一个已认证的控制台里，直抵被测流程。

#### 硬编码脚本在按钮一移动的刹那就失败。一个能看见页面的 agent 会适应、重试，并且只在人类也会失败时才失败——当被要求的事真的做不到时。每个循环都留下录像、日志和截图。

这个循环的回报是*韧性*：套件随 UI 一起弯折，而不是撞碎在它上面。

#### 真实运行 · TC-017 agent 落地并驾驶的页面。TC-017 更换选中的模型（Usage 面板右上角），并验证代码片段随之更新——在 .pt 里就是一个大白话步骤。

### 从测试计划到测试套件，全自动

手写几十条端到端测试，恰恰是我们想逃离的苦役。所以我们基本不写了。

- **从 PDF 测试计划。**`generate_tests_from_pdf.py` 吃进一份 QA 测试计划，吐出一批可直接运行的 .pt 文件，一个场景一个。测试计划*变成*测试套件。
- **从活的 UI。**`generate_tests_from_baseline.py` 抓取每个页面的 DOM 基线，据实际存在的内容生成 sanity 测试——覆盖面随产品演进，DOM diff 会在页面在我们脚下变动时报警。

#### 套件会自我描述。因为每条 CUJ 都带大白话摘要，跑测试的同一份语料也喂给那个判断"眼前这个 PR 被测没测到"的覆盖率 agent。

今天，套件覆盖**数十条关键用户旅程**——即 CUJ 目录——遍及整个控制台：get-started、playground、API keys、analytics、logs、members、billing、组织设置和 chat app。每条都是自动生成的目录里的一行，精确描述它检查什么，并打上标记（`Smoke, Billing, release-gate`……），于是一次 90 秒冒烟通过或全量回归都只是一条命令。

### 每个 PR 上知道*该测什么*

测试套件的好坏，取决于你对"它覆盖了眼前这个改动吗"的信心。于是我们把同一份智能对准了自己的 pull request。

一个 **PR 覆盖率 agent** 把 diff 与 CUJ 目录交叉比对，问出发布经理会问的问题：*现有测试已经跑过这个改动了没有——如果没有，新测试需要补什么？*因为每条 CUJ 都带着验证内容的大白话描述，agent 能对覆盖率做语义推理，而不是 grep 文件路径。缺口在发布*之前*可见，而不是事故之后。

这闭合了多数测试套件留着的环口。光跑你有的测试不够；你得知道你的测试什么时候不够。

### 我们最骄傲的部分：会自愈的测试

任何大型 E2E 套件的现实是：一夜之间，总有测试变红。贵的不是跑套件，而是早上的分诊。*真 bug？网络抖动导致的 flaky？UI 挪了个按钮？还是基础设施挂了？*于是我们把分诊做进了系统。

每晚跑批，一个路由 skill——`heal-batch`——读取结果，按*类型*给每个失败归类：UI/流程漂移、flaky、基础设施/会话死亡、真实产品 bug，或 runner 自身能力缺口。每类路由到专职处理器。对最常见的情况——UI 漂移导致某个过时的 .pt 步骤对不上了——一个调试 agent 从录屏、截图和日志重建失败现场，然后**拉起 UI、现场复现流程**来确认它的假设，再提出修复。

#### 五种失败类型，五个处理器。只有最常见的一种——UI 漂移——会被自动修复，且只通过这样一条流水线：模型只提议、从不动手，应用步骤是字面的查找替换，在真实重跑通过之前什么都不算修好。最终仍由人类合并。

让这件事可信的是护栏，值得精确说明：

结果是一套能自行吸收快节奏前端日常磨损的套件，只在真正值得喊工程师的失败上才升级：真 bug。

### 从测试套件到发布闸门

跑好、修好一个套件是一回事；判断整个*发布*是否安全可交付是另一回事。在用户旅程开跑之前，流水线读取每个 diff 并**给风险打分**——标记真正引发故障的模式：数据库迁移、feature flag 翻转、顺序依赖、破坏性 API 变更。一道**确定性底线**，模型只能抬高不能压低，让三十个 PR 里那一个危险分子无法被悄悄放行。

测试结束后，流水线起草发布文档——PR 归组为大白话的功能条目，附上风险与测试结果——最后给出建议：**Go、No-Go，或带条件放行（Go-with-checks）**。过去要吃掉一个周一上午的书面报告，现在是一趟约 20 分钟的运行；任何没经过风险打分、测试、并在真实环境中证明全绿的东西都不许发布。

### 跑在可扩展 runner 上的 Skills

这一切都不是一个巨石程序。每项能力——风险打分、跑一条旅程、失败归类、修复过时测试、发布说明——都是独立的 **skill**，由同一个容器化 runner 执行任意一项。添加新能力就是加一个 skill，而不是重写流水线。

正是这个设计让它可扩展。每次运行是一个内含 skill runner 的 **pod**；skills 互相串联，这条链同时跨大量 pull request 运行，每个都在自己的 pod 里。功能更多就意味着 skill 更多；工作更多就意味着 pod 更多，**EKS 横向扩容**去接住。Pod 使用 Pod Identity 而非静态密钥——每个 pod 只能写恰好一个 S3 桶，且没有任何通往生产环境的路径。

流水线是云原生的：跑在 EKS，由 AWS Step Function 编排。轻量阶段——解析一次发布包含哪些 commit、记录一次运行——是以秒计数的 Lambda；需要真实浏览器或长时间运行的重型阶段——跑旅程、分诊失败、发布、开修复 PR——以 Kubernetes Jobs 运行。产出落入 S3 与 DynamoDB。

- 一个容器化 runner，多个 pod

#### 每项能力都是 skill；同一个容器化 runner 执行其中任何一个。把这条链同时在多个 pull request 上跑——各占一个 pod——EKS 横向扩展。Runner 提议；确定性代码拍板；每一次合并由人批准。

#### 作为云上 DAG 的发布流水线。Step Functions 编排，轻量阶段是 Lambda，四个重型阶段以 EKS pod 运行。

### 让 AI 干这个，安全吗？

这是正确的问题，诚实的回答从显然处开始：语言模型不是确定性的——你不能靠"模型大概做对了"去发布客户软件。所以我们在 AI *决定*什么和*提议*什么之间划了条硬线。把关发布的规则是**固定的**，每次都同样生效：模型只能抬高的风险底线，以及只有真实在线重跑才能给出的通过。AI 做的事是**提议**——它起草风险理由、写测试、建议修复、拟发布说明。它从不合并、从不写生产、不持有常驻凭证，其输出会先经结构化校验，下游才会据此操作。

#### AI 提议，确定性代码决定，人类批准每一次合并——模型能让流水线更聪明，但永远不会更危险。

其上再叠常规护栏：**最小权限访问**——用 Pod Identity 而非静态密钥，每个 pod 限定在单一命名空间、一个 S3 桶，没有通往生产的路径——外加按 run 沙箱化的容器、锁死的 egress、放在保险库里的密钥，以及一切皆有审计日志。还有那条永不改变的规则：每一次合并都由人类批准。

### 我们学到了什么

- **描述意图，而非实现。**测试一停止引用 markup，E2E 抖动最大的源头就消失了。一个能感知页面的 agent，从根本上比一个直接寻址页面的脚本更健壮。
- **让 agent 看见，别只让它行动。**录屏和截图不只是调试用——它们是让自愈循环保持诚实的实地真相。凭证据提出、经现场确认的修复，才是你敢信的修复。
- **在要紧处保持确定性。**LLM 是判断层；它们绝不该是*执行*层。把"提议"（模型）与"应用/验证"（机械）严格分开，正是我们能在让自愈自动化的同时，永不把一次幻构改动自动合进 main 的原因。
- **把智能对准整个循环。**最大的胜利不在*跑*测试——而在*生成*测试、把它们*圈定*到每个 PR、以及*修复*它们。跑测试反而是最简单的部分。

### 接下来往哪走

这是一个预告：当快模型便宜到足以活在开发循环*之内*、而不是在旁边的时候，QA 会长什么样。当测试是一段话，人人都能写。当 agent 能看见页面，套件就不再与前端打架。而当它能自行分诊、自愈，工程师就把日子花在真 bug 上，而不是红色构建上。

而且它不会只待在 Console。我们已在把同一套框架推向 API Gateway 和 API Server，让平台核心的请求路径获得同样"一段话大小、能自愈"的覆盖。

速度一直是 Cerebras 的故事。现在它也包含"知道自己发布对了"的速度——用的就是我们自己在平台上服务的那批快模型。
