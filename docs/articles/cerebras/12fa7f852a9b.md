8x7B 到底是什么意思？你大概以为它是 8 个 expert、每个 token 激活 7B 参数。我们也是这么想的。结果它实际激活的是 13B 参数。可等等，13B 是从哪来的？这正是本文要澄清的困惑（[直接跳到答案](https://www.cerebras.ai/blog/moe-guide-calculator#calc)）。

我们会通过回答几个问题来解释这些数字对推理意味着什么：需要多少内存、需要多少 GPU、生产部署里最常撞上的瓶颈是什么。我们会看到：单 GPU 部署是 memory-bound（内存带宽受限），多 GPU 配置是 communication-bound（通信受限），而 Cerebras WSE 这类专用硬件则是 compute-bound（算力受限）。

起初我们只想写一篇关于 MoE 算术的短文，然后一路往下挖，越挖越深。原本的基础运算，最后变成了对推理瓶颈、硬件架构和部署策略的完整讲解。欢迎来到 MoE 推理 101。标题没变，范围变了。

到这里为止，Mixture-of-Experts（MoE）这一系列讲的都是训练：第 3 篇里你自己训练了一个 MoE 模型，第 4 篇把它扩展到生产规模。然后呢？我们转向推理。推理时模型权重是冻结的，没有梯度，也没有优化器状态。跟训练模式相比，这听起来简单得多。但是！MoE 推理做的活儿更少，挑战却自成一套。

有意思的是：训练模型的人很少考虑推理成本，反过来也一样。本文作者也不例外，但我们正在努力改好。所以，如果你要部署 MoE 模型，或者你已经训练好一个 MoE 模型、想知道自己的设计选择带来了什么，又或者你只是想搞明白怎么高效跑 MoE 推理，那就继续往下读。

### 我需要多少内存？

想避开推理部署时撞上 OOM 错误？我们来看占据内存空间的两大部分：模型权重和 kv-cache。为了简化计算，我们采用标准的现代 transformer 配置：RoPE 位置编码（Su et al., 2023）、SwiGLU 非线性（Shazeer, 2020; Dauphin et al., 2016）、layer norm、多头注意力（multi-head attention）、不共享权重的 embedding（untied embeddings），以及业界标准的可学习路由（learned routing）（Soboleva, 2025a）。

### 我需要多少算力？

就像前面估算了跑 MoE 推理所需的内存，这里我们重点估算 FLOPs（Floating Point Operations，浮点运算次数）的数量。之后会把 FLOPs 换算成吞吐量和延迟指标，用它们来回答 MoE 模型能跑多快。

推理有两个关键阶段。第一个叫 prefill（预填充），模型一次性处理整个 prompt。第二个阶段我们开始生成答案：自回归 transformer 一次只能生成一个 token，每个新 token 都依赖此前生成的 token。我们把第二个阶段叫 decode（解码）。先算 prefill 阶段花掉的 FLOPs，之后再对 decode 做单独分析。

transformer 里的运算大多是 matrix-vector、matrix-matrix 和 Hadamard 计算，所以先确定这几种基础运算各需要多少 FLOPs。

### 为什么我的 GPU 不 brrr？

第 2 节算出了需要多少内存，第 3 节算出了模型需要多少 FLOPs。理论看起来很扎实，但做过实验的人都知道，这套数字在实践中常常对不上，非常令人抓狂。那我们就一起验证一遍，弄清楚 GPU 为什么常常闲着、不 brrr。我们把 Qwen3-30B-A3B（一个激活参数 3B、总参数 30B 的 MoE 模型）（Yang et al., 2025）加载到一张 H100 GPU 上[1]，测量它在 decode 阶段生成 token 的速度：

跑一下，得到大约 3 ms。这算好还是算差？我们来判断。把第 3 节的 decode 公式拿来，代入 Qwen3-30B-A3B 的参数（），得到每个 token 大约 5.9 GFLOPs 的计算量。你的 H100 峰值是 800 TFLOPs/s Bekman (2023-2024)，按此应当 7.4 s 就能处理一个 token。相对于实测的 3 ms，这只是一小截。剩下的时间都去哪儿了？

推理时两件事并行发生：一边把权重从 HBM 内存流式读入 GPU 的片上 SRAM，一边在这些权重上执行计算。哪个更慢，哪个就成为瓶颈。我们来估算搬运权重的时间：把 Qwen3-30B-A3B 的数字代入第 2 节的内存公式，算出每个 token 激活多少参数（在 MoE 层权重的计算里，把  换成  这个倍乘系数就行），因为我们只需要加载真正用到的那些 expert。在 bf16 精度（）下，每个 token 大约要搬运 6 GB 权重。按 H100 实际可达的 2.8 TB/s 内存带宽，加载这些权重约需 2.1 ms。也就是说，我们 99.5% 以上的时间都在搬运权重，真正用于计算的不到 0.5%。这很糟。

那为什么我的 GPU 不 brrr？因为眼下我们是 memory-bound。在 memory-bound 区间，大部分时间耗在数据搬运上，GPU 利用率始终很低，算力和 $$$ 都被浪费。我们想待的区间叫 compute-bound：计算占主导，GPU 利用率很高。那怎么从 memory-bound 转到 compute-bound？我们接着看。不过先介绍几个对分析有用的指标。

### 我量的东西对吗？

### 怎么切到 compute-bound 区间？

从 memory-bound 转到 compute-bound 的一条路，是在内存搬运量不变的前提下增加计算量。把多条 prompt 打包成一个 batch 就能做到。实际上，生产级推理就是这么运作的：同时服务多个用户（比如把用户请求打包成  条序列的 batch）。这样一来，同一份模型权重就能在 batch 内的全部  条序列上复用。很好，那是不是把 batch size 直接拉到很大就行？也不全是。我们对 Qwen3-30B-A3B 扫一遍不同的 batch size，同时测量第 5 节定义的延迟和吞吐量，目标是找到那个能让吞吐量最大化、而延迟增长不过分的 batch size。扫完之后，你应该会看到与图 3 相近的结果。

### 多加 GPU 会怎样？

上一节我们为单张 GPU 找到了最佳点：batch size 为 256 时从 memory-bound 转入 compute-bound。现在来考虑多张 GPU 的情况。把模型切分到多张 GPU 上，就需要某种模型并行。对 MoE 来说，我们用 expert 并行（Expert Parallelism，EP）。有了 EP，Qwen3-30B-A3B 的 128 个 expert 被分片到多张 GPU 上，每个 MoE 层都要做一次开销很大的 all-to-all 交换：把 token 分发到各个 expert 网络，计算结束后再把结果收回来（见图 4）。

图 4：含 6 个 expert 的 MoE 模型，以 expert 并行部署在 2 张 GPU 上。expert 均匀分配到各加速设备；其余参数（attention、layer norm、router 等）在每个设备上复制一份，用数据并行训练。

我们在 MoE 101 系列第 4 篇（Soboleva, 2025b）中展示过，这种 all-to-all 通信会成为 MoE 模型的瓶颈，在那里你没法简单地靠加大 batch 绕开它。与单 GPU 情况不同，增大 batch size 会让通信和计算同比例增长。于是我们撞到了两堵墙：MoE 模型在单张 GPU 上是 memory-bound，在多 GPU 配置下是 communication-bound。两者源自同一个架构约束——计算与内存彼此分离，靠带宽受限的连线相连。但如果你的硬件从一开始就是 compute-bound 呢？我们来看看在 Cerebras 硬件上跑推理会发生什么。

### 用 Cerebras WSE 从一开始就 compute-bound 会怎样？

在 Cerebras WSE 上跑推理，可以把整个模型以流水线方式铺在晶圆上（图 5）。每一层映射到一块物理区域，其权重和 kv-cache 就近存放在片上 SRAM。各区域相邻布置，层与层之间的 token 流动几乎没有延迟开销，因为它们都在同一块芯片上。最后一层的输出会绕回去，用于生成下一个 token。

图 5：含 6 个 expert 的 MoE 模型在 Cerebras WSE 设备上的布局。每一层（包括 expert）映射到晶圆上的一块物理区域，权重就近存放。token 沿流水线在各区域之间流动。

还记得单 GPU 分析（第 4 节）里，我们把 99.5% 的总时间花在从 HBM 加载 Qwen3-30B-A3B 的权重上。而在 Cerebras WSE 上，模型权重不像 GPU 那样存在片外 HBM，整个模型都住在片上 SRAM 里。这样模型权重永远不需要进出芯片，你也永远不会 memory-bound——MoE 也不例外。batch size 为 1 时就已经是 compute-bound，第 6 节针对单 GPU 做的那批实验可以直接跳过。

至于多 GPU 的情况（第 7 节），我们说明过 expert 并行会引入通信瓶颈：每次前向传播都需要开销很大的 all-to-all 操作，把 token 路由到位于不同 GPU 上的正确 expert。用 Cerebras WSE 就没有这个通信瓶颈。所有 expert 都在同一块芯片上，权重就近分布在各 PE 中，不需要 all-to-all 操作。

### 到这里你学到了什么

回头看，MoE 一开始似乎复杂得没法下手，对吧？万亿参数的模型好像只有大实验室才碰得起。但你已经把它一块一块解开了：你理解了 MoE 为什么有效，打下了基础；选对了路由策略，也看清了其中的取舍；从零开始调试了一个坏掉的 MoE，修掉了让大多数实现翻车的梯度流 bug；在 GPU 和 Cerebras WSE 上都把规模推到了生产级；还攻克了推理算术与瓶颈。你从理论走到了生产。

更重要的是，你学到了方法论：怎样问对问题。用哪种路由策略，为什么？router 塌缩时到底坏在哪里？怎样在不撞瓶颈的情况下扩展规模？假设驱动的调试、量对指标，这些才是真正的关键。

### 计算器

我们找不到一个能同时估算 MoE 模型算力和内存需求的好用工具，于是做了这个简单的计算器，两样都能算。你可以拿任意模型配置来试，这里用它回答开头那个问题：8x7B 到底是什么意思？指南开头我们以为它是 8 个 expert、每个 token 激活 7B 参数，现在来验证这一点。把 [Mixtral-8x7B](https://huggingface.co/mistralai/Mixtral-8x7B-v0.1) 的配置代入计算器，你会看到 decode 阶段约 0.03 TFLOPs/token。再代入 [Mistral-7B](https://huggingface.co/mistralai/Mistral-7B-v0.1) 的配置（一个 7B 的 dense 网络），结果大约只有它的一半。所以 Mixtral-8x7B 每个 token 激活的并不是 7B 参数，而是更多。要弄清确切数字，把 [Llama-2-13b](https://huggingface.co/meta-llama/Llama-2-13b)（一个 13B 的 dense 网络）代进去，你会得到约 0.03 TFLOPs/token，与 Mixtral-8x7B 完全一致。于是我们看到：Mixtral-8x7B 实际每个 token 激活 13B 参数，而不是 7B。MoE 的算术到此讲清楚了。
