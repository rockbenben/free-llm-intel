# 模型再聪明，也救不了糟糕的 harness

[Sarah Chieng](https://www.cerebras.ai/author/sarah-chieng)[William Ryan](https://www.cerebras.ai/author/william-ryan)[Sherif Cherfa](https://www.cerebras.ai/author/sherif-cherfa)

一个 agent 粗略看就是装在 harness 里、并在某个环境中运行的模型。

**模型**提供智能。它负责推理、做决策、写代码，并决定下一步采取什么行动。**环境**是这些工作实际发生的计算机、代码仓库、浏览器或容器，而用户（有时是另一个 agent）负责给出目标，并在需要时提供指引。

**harness** 决定模型能看到什么、能采取哪些行动、结果如何回喂给下一次推理，以及工作何时算真正完成。

![](https://cdn.sanity.io/images/e4qjo92p/production/4c5dfeb50d444cc97f3af43d97e61be8895896ec-4040x1397.png?auto=format&dpr=2&fit=max&q=75&w=2000)

![](https://cdn.sanity.io/images/e4qjo92p/production/0fa06f54c42a11bcce559661ffabae5c21b7b568-4950x1656.png?auto=format&dpr=2&fit=max&q=75&w=2000)

你可以把 harness engineering 理解为你围绕模型搭建的那套系统——它让模型成为完成真实工作的引擎。模型有多聪明并不重要，没有 harness，它就只是一台生成 token 的机器。是 harness 让那份智能真正有用，是 harness 把模型变成 agent。

harness 有很多种类型。它们各自偏向不同类型的工作

- 个人工作：Openclaw 和 Hermes 主要是个人 agent，它们被嵌入到外部应用中（Telegram、Discord、iMessage）。
- 编程：这类 harness 通常在终端里，或在代码编辑器里运行。也有为强化学习和研究设计的 harness，为金融、市场营销以及许多其他垂直领域设计的 harness。
- 知识工作：ChatGPT Work 和 Claude Desktop App 就是很好的例子。虽然很多人也把它们当 coding agent 用，但这些应用有大量的工具和插件，能让你的 agent 连上 Slack、Notion、Gmail、Sheets、Teams、Clickup 等工具——目标都是支撑通用的知识工作。

![](https://cdn.sanity.io/images/e4qjo92p/production/47a43fe069beddf7e91c225027345e51d4c835e8-2168x1926.png?auto=format&dpr=2&fit=max&q=75&w=2000)

![](https://cdn.sanity.io/images/e4qjo92p/production/19dfa24cf2aaa63be95005b6f374b61848d53dc1-2140x2027.png?auto=format&dpr=2&fit=max&q=75&w=2000)

#### 图中来自 OpenAI 的 ChatGPT Work，拥有面向通用工作与软件工程的健壮插件生态。

但从根本上说，它们共享同一副骨架。今天我们要拆解 agentic harness 的各层，好更清楚地理解我们这门手艺所用的工具。

### 什么是 harness？

大语言模型接收输入，用这些输入生成下一个 token，再把刚生成的那个 token 追加到输入上，loop 就这样持续运转，直到它认为自己完成了。单靠自身，它们无法：

- 使用计算机
- 维持持久状态
- 搜索网页
- 运行 shell 命令
- 读取、编辑或创建文件
- 执行代码
- 甚至无法验证自己产出的东西到底能不能用

如果说大语言模型是大脑，那 harness 就是它的身体。

当你给出这样一个 query 时：

![](https://cdn.sanity.io/images/e4qjo92p/production/4d09e4cef9cc0ec3caff71bdadd0382f97789453-3840x998.png?auto=format&dpr=2&fit=max&q=75&w=2000)

你的 prompt 并不是直接发给模型、然后神奇地带着一个已完成的补丁回来。harness 会把许多次推理调用组合成这样一个反馈 loop：

![](https://cdn.sanity.io/images/e4qjo92p/production/12759c8b8d982b4d4515c07b1d3291776ce3546d-3840x3348.png?auto=format&dpr=2&fit=max&q=75&w=2000)

**这个 loop 就是我们所说的 “agent”。**

而这里列出的每一步，都需要相当多的工程工作

![](https://cdn.sanity.io/images/e4qjo92p/production/db667a809a23fae4584607fd3826c52ce8f9102b-2712x2540.png?auto=format&dpr=2&fit=max&q=75&w=2000)

harness 通常负责：

- **Prompt 构建** - 系统/开发者指令、代码仓库指令、用户 prompt。
- **上下文选择** - 哪些文件、既往消息、工具输出、记忆、diff 等是可见的。
- **工具** - shell、文件编辑、搜索、网页、MCP 工具、Git、测试。
- **工具 schema** - 这些能力如何描述给模型。
- **工具执行** - 真正把模型的意图转化为行动。
- **Agent loop** - 决定工具结果如何返回，并触发下一次推理。
- **状态** - 跨步骤/跨会话记住发生过什么。
- **编排** - 派生出专门化或并行的 agent。
- **Hooks** - 在预设的触发点上确定性地执行脚本（linting、拦截危险命令、代码 review）。
- **记忆** - 个人上下文被存储起来并注入模型 prompt，帮助 agent“记住”既往会话。
- **上下文压缩** - 决定随着会话增长，什么被摘要、什么被丢弃。
- **规划** - plans、TODO 列表、子目标。
- **权限/沙箱** - agent 被允许执行什么。
- **错误处理** - 重试、失败的命令、超时。
- **验证** - 测试、linting、检查改动是否真的有效。
- **终止** - 决定 agent 的这一轮何时真正结束。
- **约束** - 规定 agent 能做什么、不能做什么的规则。

**harness 能够改变结果**

如果你在不同的编程工具里用过同一个模型，你大概已经有体会了。模型也许相同，但体验和输出质量会有天壤之别。

一篇论文，[*Stop Comparing LLM Agents Without Disclosing the Harness*](https://arxiv.org/html/2605.23950v1)，报告称 **Claude Opus 4.5 在标准化的 SEAL scaffold 下得分 45.9%，而通过 Claude Code 使用时得分 55.4%**——在 SWE-bench Pro 上。

![](https://cdn.sanity.io/images/e4qjo92p/production/bc46387046766b6ab7db94c827db585f108529fe-903x868.png?auto=format&dpr=2&fit=max&q=75&w=903)

[Stop Comparing LLM Agents Without Disclosing the Harness](https://arxiv.org/html/2605.23950v1) 中的表 1

而且复杂未必为王。有时更小的 tool schema 比再多几层编排更能提升一个 agent。最近，Prime Intellect 发布了他们的 coding harness。Prime Agent 基于 Pi 构建，已经设法跑赢了自家模型在训练时所用到的那些 harness。

![](https://cdn.sanity.io/images/e4qjo92p/production/7a509e64b6f2e34deaf5e72bbb8e5bfe3a239dbe-2048x1200.png?auto=format&dpr=2&fit=max&q=75&w=2000)

这里的启示是：如果两次测试用的不是同一个 harness，那么告诉你“模型 A 胜过模型 B”的 benchmark 有时确实会在无意之中误导人。**上下文（以及 harness）很重要。**

一个 benchmark 结果属于一对「模型-harness」组合。harness 变了，结果也可能变。而随着 harness 变得更有野心，它们也会发起更多次模型调用。**快推理的价值正是从这里开始显现。**

![](https://cdn.sanity.io/images/e4qjo92p/production/e1aef720979a09e236f79e86ae56c0fbcf9e8f2d-3174x2244.png?auto=format&dpr=2&fit=max&q=75&w=2000)

[Artificial Analysis 的 harness 对比](https://artificialanalysis.ai/agents/coding-agents?coding-agents-harness-comparison-chart=harness-deep-swe)

在这里可以看得很清楚：同一个模型，性能会随 harness 不同而天差地别。

### **harness 是推理次数的倍增器**

看看 **harness 负责**的那张清单：规划、loop、重试、验证、测试、压缩、编排、review。其中每一项都需要另一次模型调用，消耗 token，而更重要的是消耗时间。

一轮验证也许能抓到 bug，但也会让运行时长翻倍。subagent 可以把其中一些工作并行化，但编排者仍然要规划、派发并综合这些结果，而这些步骤全都得顺序执行。

每一次模型调用都会增加延迟，而在一个基本串行的 agent loop 里，大致的时间预算长这样：

![](https://cdn.sanity.io/images/e4qjo92p/production/18e8b92d94612820d19d5561f63393b643a189da-3658x2648.png?auto=format&dpr=2&fit=max&q=75&w=2000)

一步慢了，十步就没法看了。反过来，如果模型的步进足够快，harness 就有富余去做更多有用的工作——在 agent 失去交互感之前。

这个区别很要紧。[在 Cerebras 上运行 GPT-5.6 Sol 可达每秒 750 tokens，完整一轮的响应最低只需 0.4 秒](https://www.cerebras.ai/blog/getting-the-most-out-of-gpt-5-6-sol-terra-and-luna)。这个量级的速度解锁了新的能力，并为 harness 在推理、工具使用、恢复和验证上提供了更大的预算。

### **“快 harness” 能做到哪些不同的事**

一旦模型延迟变小，工程师就能把省下来的时间用在几种有用的方向上。

- **实时 agent 编排。** 像 GPT 5.6 Sol Ultrafast 这样聪明的模型可以编排大型项目和大范围的 subagent fan-out，把延迟上的收益快速复利式放大。
- **以人的速度使用电脑**。agent 已经能用电脑了，但与人类相比它们仍然笨拙、易出错而且缓慢。快速推理移除了那种让 agent 以人类速度行动的延迟。
- **Live Steering。** agent 对纠正即时作出反应，带来真正协作式的体验。
- **推测执行。** 还在权衡某种做法的用户，可以用 work tree 实时实现并测试好几种备选方案，拿到的是能跑起来的选项，而不是假设性的建议。
- **激进的重试与自我纠错。** agent 可以在代码写出的同时激进地测试并修复它自己的代码，而给最终用户带来的代价极小。文件一经编辑 Hooks 就立刻触发，在毫秒级完成验证或修复。
- **自适应界面。** agent 能针对当前状态实时生成预览、图表、可视化和 mock-up。

这些只是几个例子，一个有想象力的构建者当然能以成千上万种有益的方式利用低延迟推理；但整体上最大的收益，无疑是让人以交互的方式、实时地参与到构建过程中来。搜索、推理、工具使用和编辑收敛进一个更紧的 loop，更接近与一个真正的结对编程伙伴协作的感觉。

### 构建一个轻量级白板应用

为了把 harness 的影响与模型的智能隔离开来看，我们跑了一个简单的受控实验：她用的是 **Claude Opus 4.6，同一个任务，但放进两个不同的 coding agent 里：Factory Droid 和 Claude Code。**

两个 agent 都从空代码仓库开始，并收到同一个 prompt：

![](https://cdn.sanity.io/images/e4qjo92p/production/fe32869a0f4d1d2d8e2c854b78bf6e3139f41392-3840x998.png?auto=format&dpr=2&fit=max&q=75&w=2000)

eval 聚焦于同样的五项要求：绘制矩形和箭头；选中、移动和删除元素；撤销与重做；导出为 PNG；以及在浏览器里运行结果。**两个 agent 都通过了全部五项要求。**差别在于各自的 harness 把同一个模型转化为经过验证的工作时有多高效。

![](https://cdn.sanity.io/images/e4qjo92p/production/841d1860eeb44a923ec35b717067428ecc4f2751-3566x2024.png?auto=format&dpr=2&fit=max&q=75&w=2000)

在这一次运行中，Factory 提前 **11 分钟完成，快了约 2.4×，所用的 tool call 数量大约只有一半**。它还在报告完成之前定位并修复了一个会造成阻塞的 hit-testing 问题，随后把剩下的非阻塞缺口记录在案。

这并不意味着某个 harness 会赢下所有任务，但它是一个很好的示例，说明 harness 作为推理次数倍增器的作用：**即使模型保持不变，它周围的系统也能实质性地改变最终结果的路径、成本、速度和质量。**

*注：结果会因 harness、任务和模型配置的不同而变化。*

### **harness 成为瓶颈**

当前，agent 最大的瓶颈是推理步骤。有了 Cerebras Fast Inference，情况不再如此。新的瓶颈变成了 harness 本身，更具体地说，是 tool call。

在与 agent 协作时，tool call 既关键又常见。就像上面的例子那样，一个任务可以串起几十次、某些情况下上百次 tool call。下面是一些我们在真实生产代码库里跑过的示例任务，让你对某个任务大概会用掉多少次 tool call 有个概念。

![](https://cdn.sanity.io/images/e4qjo92p/production/0328e057de3b24e9843b3f12b85513e2cc4bfdad-4040x2539.png?auto=format&dpr=2&fit=max&q=75&w=2000)

当推理不再是较慢的那一步，harness 工程师就能专注于优化 agent 技术栈的其余部分，为 harness 自身的效率与性能做优化。

### **速度改变 harness 的形态**

这些 agent 能力本身未必是新的。几乎任何 harness 都能跑测试、编排 agent、操作浏览器或生成可视化。区别在于这些动作是否切合实际，是否放得进「交互之内」，还是会逼着你把工作丢到后台去。

慢推理会把人推向次数更少、体量更大的模型调用。多步骤工作变成异步，用户在 agent 已经做完大部分决策之后才来 review 结果（错误也随之累积）。别忘了，模型很聪明，但它们并非不会出错。**一个高自主性、设计品味好的人留在 loop 里，提供判断、指引和方向把控，依然无可替代。**
