# AlphaSense 如何用快速推理让 Agentic 研究变得可交互

Alec McLean

Griffin Marge

**Cerebras 方：** Alec McLean 和 Griffin Marge

**AlphaSense 方：** Chris Ackerson、Daniel Campos、Eldar Tinjic、Matt Lapointe、Mohit Sharma、Prashant Budania 和 Yumo Luo

### **通过低延迟 GenAI 的架构取舍，树立企业研究的新标杆**

企业用户不再满足于一个返回文档列表、把综合提炼留给自己的搜索框。他们想要一个研究伙伴——一个能理解问题、拆解问题、检索相关证据并给出清晰、有据答案的系统。

想象一位正在为财报电话会做准备的股票分析师。与其手工拼接会议记录、监管文件和新闻，他直接问："本季度利润率扩张的关键风险是什么？"系统拉取相关段落，权衡相互冲突的信号，返回一个附证据的结构化答案。过去要几小时的活，现在变成可以分钟级迭代的事。

这正是 AlphaSense Generative Search 的抱负——让深入的、循证的研究在日常工作流中变得可行。但企业研究产品面临一个核心取舍：更高质量的答案需要更多规划、检索和评估，而每一步都增加延迟。即便系统在幕后做更多工作，用户依然期待响应有交互感。

为此，AlphaSense 与 Cerebras 合作，为其平台中依赖大量快速、重复模型调用的部分提供动力。通过压低路由、查询生成、证据评估等环节的延迟，Cerebras 让同样的响应窗口内塞进更多推理成为可能。

结果是架构层面的转变：Generative Search 不必把一切塌缩进单个 prompt、也不必限制步骤数量，而是可以把规划、检索、评估的多个阶段组合成单一响应敏捷的体验。

### **商业挑战：研究必须有交互感**

AlphaSense 的用户处在研究质量与速度都重要的环境中。用户可能想要关于一家公司竞争地位、一个市场趋势、一项监管动态，或一次管理层变动的观点。准确回答往往需要若干层叠加的任务：

- 识别相关的公司、人物、市场、产品和事件
- 判断哪些来源适合该问题
- 从结构化与非结构化内容中检索段落
- 评估哪些片段相关、冗余、过时或相互矛盾
- 把最强证据综合成清晰的答案

传统搜索架构能快速返回文档，但把大部分推理留给了用户。Agentic 研究架构能干更多活，却引入了新瓶颈：每一个额外的推理、路由或评估步骤，通常都要再调一次模型。

这就构成了产品与架构的双重挑战。用户期待默认体验感觉很快，但最高质量的答案往往需要更多中间推理。系统必须决定：在用户察觉延迟之前，做多少工作。

### **为什么延迟会成为架构约束**

当 Generative Search 团队从传统检索扩展到规划、路由、证据评估和自适应研究模式时，他们遇到了一个新约束。每个新增能力通常都要再调一次模型，而每次模型调用都消耗用户响应时间预算的一部分。

这就是推理延迟超越性能指标的地方。在 agentic 应用中，它成为架构设计约束。每次模型调用越慢，应用在失去交互感之前能承担的模型决策就越少。

对 Generative Search 这样的系统，这往往迫使艰难的架构取舍：

- **把多重职责塌缩进一个 prompt。**不为路由、检索规划、证据评估、综合分别使用专职模型，而是把这些任务塞进单个 prompt 以减少模型调用数。
- **用启发式规则替代模型驱动的决策。**意图分类、工具选择、工作流路由由静态规则或正则处理，因为多一次 LLM 调用延迟就超标。
- **少评估证据。**即便检索返回数百个候选段落，在综合前只能检查很小一部分，增加了漏掉相关或冲突信息的风险。
- **串行化本可并行的工作。**独立任务顺序执行，以减少并发模型调用数量、简化延迟管理。
- **限制工作流的适应性。**每个请求走相似执行路径，因为从轻量回答动态升级到深度研究工作流会带来不可预测的延迟。

对 AlphaSense 而言，降低推理延迟改变了这些取舍。Generative Search 不必把工作流塌缩成更少更大的 prompt，而可以把研究分解为规划、检索、证据评估等更小的专职模型调用，同时依旧交付有交互感的体验。

更广地看，这阐释了 agentic AI 系统的一条重要原则——**快速推理不只是让现有工作流变快，它扩展的是架构设计空间。**当单次模型调用成本下降，开发者就获得自由：组合更丰富的工作流、评估更多证据、为每个用户的问题动态调整执行路径，而不超出应用的响应时间预算。

### **方案概览**

AlphaSense 不再对所有询问一视同仁，而是把 Generative Search 围绕"先规划、自适应"的研究工作流重新设计。系统不依赖单个 prompt 完成检索、推理与综合，而是把研究分解为一串可根据请求复杂度调整的专职决策。

第一个决策是判断问题实际需要多少研究。一个直白的问题可能只需轻量的检索与综合路径；更复杂的请求（比如比较对立分析师观点、评估一家公司的战略地位）则受益于先做更多规划、检索和证据评估，再生成答案。

为支持这些不同负载，Generative Search 提供三种研究模式：

- **Auto：**为快速、可交互的响应优化，减少不必要规划，同时仍产出有用的、循证的答案。
- **Think Longer：**当问题值得更深入分析时，为规划和证据评估分配更多时间。
- **Deep Research：**执行更完整的工作流——更大范围检索、更多中间推理、在更多可信来源上做更深综合。

一个关键架构决策是：它们不是独立产品或独立流水线。它们共享一套通用研究架构，根据用户意图和延迟期望动态调整执行的规划、检索、工具使用、证据评估和综合的深度。

Cerebras 加速这条工作流中依赖大量快速重复模型调用的部分。这些调用往往发生在用户看到答案之前：分类意图、选择研究模式、生成检索查询、评估候选证据、决定最终哪些信息进入综合模型。虽然用户对它们不可见，但它们对最终答案质量和整体体验的响应性有着超比例的影响。

### **示意性研究工作流**

这里并非要描述 AlphaSense 的确切实现。它展示的是一种架构模式：在编排层和证据层用快速推理处理重复、延迟敏感的决策，把更深推理留给规划密集或综合密集、能给用户带来最多可见价值的步骤。

### **延迟如何塑造应用架构**

AlphaSense Generative Search 团队在评估不同架构时，追求的并不只是更快的模型响应，而是在用户察觉延迟之前，系统能负担多少推理。

每个交互式 AI 应用都在有限的响应时间预算内运行。对 Generative Search，这个预算必须容纳检索、编排、证据评估、综合、网络，以及每一次中间模型调用。

单次模型调用越快，同样的用户体验里能装下的架构选项就越多。

对 AlphaSense，这意味着架构不必再把每次模型调用当成昂贵资源。Generative Search 可以在整条工作流中大量使用快速的专职模型调用——意图分类、查询生成、证据打分、上下文选择——把更深的推理留给最终综合阶段。

更广泛的教训远不止企业研究。根本取舍不是延迟对成本，而是架构灵活性。更低的推理延迟扩大了生产中可行的应用设计集合。开发者不必依赖单个庞然 prompt 去完成所有任务，而可以组合更小的、目的明确的模型调用——它们更容易独立优化、扩展和演进，同时保持交互式用户体验。

更快的推理影响三个维度：响应性、吞吐量和产品雄心。

- **响应性：**Auto 模式能快速完成路由与工具选择决策，帮助维持"产品在即时回应用户问题"的感觉。使用 Cerebras 后，p90 首 token 时间下降 88%，从 19.5 秒降到 2.3 秒，同一模型的**服务速度快 8.5 倍**。

- **产品雄心：**更低的延迟给了 AlphaSense 更大空间去设计自适应路由、可扩展的证据评估，以及在可信来源上的更深综合。AlphaSense 还观察到，更快的响应与更低的放弃率和更高的使用量相关，助推产品采用与留存。

### **经验教训**

AlphaSense 的重新设计为构建 agentic 企业 AI 系统的团队提炼了几条教训。

**先设计延迟预算，再写 prompt：**调用图决定产品负担得起什么。在优化 prompt 之前，团队应了解响应时间预算、所需模型调用数量、哪些调用可以并行，以及哪些调用对答案质量至关重要。

**把控制面、证据面和综合工作分开：**并非每个模型调用都是同一个用途。路由与规划调用应当快速、可组合。证据评估调用应能跨大量候选扩展。综合调用则应专注于从最佳可用上下文中产出最终面向用户的答案。

**在重复决策处使用快模型：**快速推理在系统需要大量快速决策处最有价值——分类意图、选择工具、生成检索查询、片段打分、过滤上下文。这些是用户可能永远看不见的隐形步骤，却强烈影响答案质量。

**让产品模式共享一套架构：**Auto、Think Longer 和 Deep Research 不应各自要求完全不同的技术栈。一套能上下调节深度的共享架构，让用户更容易掌控速度与完整性的取舍。
