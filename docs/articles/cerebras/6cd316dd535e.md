# 别再交付 AI 垃圾代码：Codex Spark 如何改变你的编码方式

Sarah Chieng

Sherif Cherfa

过去几年，我们发展出一系列颇为有趣的用法。想想 Ralph 循环和多 agent 编排系统：写非常详尽的 prompt，跑 8 小时的会话，或者让机器上随时挂着 10 个实例。

这些复杂度的大部分源自同一个问题：LLM 太慢。如果你发完 prompt 只能干等，产出反而不如发完 prompt 就转去做下一个任务。

### Spark 很快。

Codex Spark 改变了开发者与 AI 协作的方式。一个能生成 1,200+ tokens/秒 的编码模型让实时协作成为可能，但也要求一套不同的方法。在这个速度下，马虎的交互会有代价，与 LLM 协作必须更加有意识地来进行。

本指南就是我们使用 GPT-5.3-Codex-Spark 的实战手册。

### 分清何时用 Codex、何时用 Spark

Codex 如今涵盖两种互补的模式：

- **Deep mode（深度模式）：** 大型 prompt、长时任务
- **Fast mode（快速模式）：** 快速、迭代式协作

GPT-5.3-Codex-Spark 是在 Cerebras WSE 硬件上提供的 Codex 变体，为低延迟交互优化，能够生成超过 1,200 tokens/秒。

因为在 Spark 上生成几乎是即时的，你可以把 /diff、/review、单元测试甚至浏览器 QA 塞进每一次提交循环而不损失时间。调试更容易了。写谨慎、具体的 prompt 更容易了。抠细节也更容易了。

### 技巧 #1：把 Codex Spark 当作结对程序员

不要写冗长、复杂、包含多个诉求的 prompt，而要像对待同事那样对待 Codex Spark。"打断并纠偏"是 Spark 的核心交互模式。对许多开发者来说，这是一块新的肌肉。

一次只专注一件事：协作，而不是委派。保持在循环内，模型运行时不要切去其他标签页或窗口。Spark 是一把电动工具；它的速度让你能专注于细节的同时把事情做完。即时反馈让你能更深入地进入代码库，而不必开多个窗口来做这件事。

引导和操纵模型的一些示例说法：

- "只改 ___"
- "先别动类型。"
- "继续之前先给我看 diff。"

协作开发一个功能的好的准则：先创建测试、运行它们、循环直到通过，然后进入下一个任务。这套工作流把传统上整个产品周期压缩到几分钟。

### 技巧 #2：**速度让验证变得廉价**

验证与反馈循环是与 AI agent 成功交互的基础，但搭建它们需要时间。让 evals、测试、规则和文档保持最新，通常意味着又一份维护负担。

而由于 Spark 的速度，在步骤之间插入测试和评估给开发周期增加的开销微乎其微。你可以在几分钟内制定计划、探索、创建测试和环境、更新文档、跑 QA 任务。

验证框架能提升模型的表现与输出质量，并减少花在修 bug 和回归问题上的开发周期。

- **Pre-commit hooks（提交前钩子）：** Spark 可以配置定制化钩子，在特定事件时自动触发。例如在提交时运行 QA。
- **测试套件：** 验证新改动不会破坏现有功能。Spark 快到可以在每个任务之间跑完你的完整套件。
- **Lint 与类型系统：** 在编写时强制代码风格并捕获类型错误。
- **基于浏览器的 QA 自动化：** 验证 UI 改动在浏览器里真的能工作。
- **就绪报告与 diff 审查：** 在你亲自审查之前，总结变更内容并标记潜在问题。

以上这些让你能以 Spark 允许的速度狂奔，而不必回头为它收拾残局。它们还在模型工作过程中持续给模型反馈，从而提高其自主性。许多兼容 Codex 的执行框架（如 OpenCode、Pi、Droid）已内置这些能力，搭建成本极低。

### 技巧 #3：探索更多实现路径

用慢模型时，开发者会早早锁定一条实现路径，因为探索太昂贵。用 Spark 时，你可以在决策前生成并测试多种方案。当你仍在摸索某个功能应有的样子、或想要定制时，这一点尤其宝贵。

**没有 Codex Spark 时我们可能会这样 prompt：**"请为 Navigation 实现一个带 4 个标签页的侧边栏：home、about、blog、contract，使用 Tokyo Night 主题。"

> 5 分钟后："我构建了一个 Tokyo Night 蓝紫主题、白色文字的侧边栏。悬停时使用紫色高亮。"

有了 Codex Spark 我们可以这样 prompt："我想要一个导航侧边栏。我喜欢 Tokyo Night 主题，但请你生成 10 个版本，在主题和组件上做出变体。"

*1 分钟后：*"我在 /mocks 里构建了 5 个导航侧边栏。每个都有自己的主题和组件层级。我已经在你的浏览器里打开了它们——告诉我你喜欢哪个，我就在你的应用里实现它。"

这招甚至适用于幻灯片、照片、视频和写作。

### 技巧 #4：跑 1 个会话，而不是 10 个

慢模型把我们推向了并行主义：你开 10 个标签页，发 10 个 prompt，然后干等。你被迫站在鸟瞰视角工作，因为每隔几个小时才能审几百行代码。

而用 Spark，你每分钟生成数千行代码。你不能让它在多个同时改动的 agent 之间堆积如山。代码审查成了新的瓶颈，Spark 最适合扮演结对程序员，而不是一支被委派的施工队。

最多用 2-3 个会话，且只用于真正独立的轨道（如后端 vs 前端、彼此分离的服务）。

### 技巧 #5：全新的上下文窗口，持久化的记忆

Codex 把一个会话称为一个 thread（线程）。Thread 可以是本地（沙箱化的）或云端的。你可以运行多个 thread，但要避免多个 thread 碰同一个文件。

总体而言，模型在更窄、范围明确的上下文中工作时会产出最锐利、最确定的输出。随着上下文增长，压缩（compaction）和指令漂移会更容易发生，因为模型必须压缩更多状态。话虽如此，Spark 在其完整的 128K 窗口内表现都很强劲。关键不是完全避免大上下文，而是有意识地使用它。

在约 1,200 tokens/秒 下，Spark 大约 2 分钟的连续生成就能填满其 128K 上下文窗口。要把 Spark 用到极致，请频繁开启新会话，并让你的研究上下文留在仓库内。

**把上下文窗口当作工作记忆，而不是长期存储。**持久状态放进文件。会话保持聚焦。目标完成就重置。

一个有用的心智模型是：

**管理上下文长度的最好技巧：把大任务拆成小的、有边界的目标。**让每个会话围绕一个目标做增量推进，这样每个会话都产出无 bug、文档完善、可运行的代码。你会得到更确定的行为和更少的压缩意外。

下面这些命令就是我们榨干 Spark 性能的方式：

- /new —— 每当成功完成一个任务就用它。
- /fork —— 如果你对某次输出感到满意，fork 并重命名会话以便日后复用。
- /permissions —— 模型太快，没有这个命令你根本无法在运行中引导它。
- /review —— 和 Spark 一起审代码轻而易举，能帮你快速揪出垃圾代码。
- /skills —— Spark 擅长即时执行预定义工作流。
- /rename —— 重命名会话有助于区分好运行与坏运行。多用它。

### 技巧 #6：外置状态，保留一份"外部"记忆

参加结对编程时，你通常会做笔记、讨论工单、来回共享文件。在与人协作、快速推进的同时用书面形式记录进展，正是做出好工作的关键。

Spark 快到足以让你享受文档、工单和草稿板的全部好处，而撰写和维护这些文件不再成为负担。

一个最小化的外部记忆系统：

- AGENTS.md —— 仓库特有的规范、命令、坑（Codex CLI 可通过 /init 自动生成）。
- PLAN.md —— 清单式计划 + 完成定义（definition of done）
- PROGRESS.md —— 简短的进行日志：改了什么、失败什么、下一步是什么
- VERIFY.md —— 证明其可用的确切命令（测试、lint、e2e）

这消除了歧义，减少跨会话的漂移。Git 成为你的记忆层。Spark 成为无状态的执行器。

Spark 执行时应当：

- 读取 PLAN.md
- 实现一个清单项
- 运行 VERIFY.md 中的命令
- 更新 PROGRESS.md

这与 ["Ralph 循环"](https://github.com/snarktank/ralph)背后的核心思想一致：每次迭代使用干净的上下文，而记忆通过 git 和小文件持久保存。

Ralph 循环在 Spark 上大放异彩。不用跑一整晚，你花几分钟就能取得同等的产出。Ralph 的架构会为每个工作单元自动派生新会话。

### 技巧 #7：为任务选择合适的 Codex 模型。

一个兼顾 Codex-5.3 深思熟虑与 Codex-5.3-Spark 速度的好用工作流是：用 Codex-5.3 生成全面的计划，然后切换到 Codex-5.3-Spark 快速实现。

Codex 应用和 CLI 现在提供子 agent 功能，你可以配置 Spark 处理特定类型的任务：更新文档、做研究、清理代码或做定向修改。

Codex 则专注于真正需要深度上下文和推理的工作。总完成时间会下降，因为你减少了慢模型需要承担的量。

**示例 #1：用 Codex 做架构，用 Spark 做执行。**

**示例 #2：Spark 处理聚焦任务，Codex 负责长周期工作。**

你可以把两个模型看作开发生命周期的两个部分：GPT-5.3-Codex 负责研究、规划和最终审查——它受益于更长的上下文和精度；GPT-5.3-Codex-Spark 负责快速执行与迭代。

### 技巧 #8：更紧的权限与限制

在 1,200 tokens/秒 下，Spark 能极快地推进很大范围。过去因为模型慢，我们让它一次会话做更多事而监管更少。如今我们可以设置精确的护栏，并在模型工作过程中随时纠正它。

例如：

- 禁止模型删除文件：不许 rm -rf
- diff 规模上限：**≤ 150 LOC**（或"除非另有要求 ≤ 30 LOC"）
- 在所有测试通过、类型正确并写好 commit message 之前，模型不得提交
- 模型只能读取和编辑——不得创建新文件

Codex CLI 对审批和沙箱有显式的控制。你可以在远程环境中使用 GPT-5.3-Codex-Spark，享受其近乎即时的响应和 SOTA 智能。自主运行 Codex Spark 时请遵循通用标准：使用容器化、虚拟机和沙箱。

- CLI 支持 -yolo 模式
- codex exec 默认使用**只读沙箱**；只在需要时放宽权限。
- 用 /permissions 在会话中收紧或放宽。

Codex CLI 会在运行时强制执行这些规则，几乎不需要最终用户做额外配置。也欢迎探索类似工具，找到适合你的组合。

### 技巧 #9：文档园艺 agent（把防漂移当作持续过程）

OpenAI 描述了一种 ["doc-gardening"（文档园艺）agent](https://openai.com/index/harness-engineering/)，它扫描过时文档并自动开出修复 PR，通过 CI 检查来强制执行。文档对于提高"模型一次就产出可用的高质量代码"的概率至关重要。

当推理等待时间可以忽略不计时，生成并打磨文档就变得毫不费力。我们为所有 LLM 保持两条文档准则的经验法则是：

- **给人看的** —— 环境搭建指南和仓库的更高层信息。
- **给 LLM 看的** —— 模式、系统 prompt、规范、图示和文件位置。

你可以把 Spark 与 CI 工具链耦合，自动化文档的生成、审查、更新和清理。这让仓库里的上下文保持有价值且高效，同时改善你的体验和模型的输出。
