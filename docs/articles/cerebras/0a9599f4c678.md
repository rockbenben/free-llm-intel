# 生成漂亮的 UI

Sarah Chieng

*Sherif Cherfa 与 Halley Chang 亦有贡献*

我们对 AI 生成的作品有一种本能的怀疑。这在写作中表现得尤为明显——那些模式已经为人熟知，连标点（[em dash](https://www.mcsweeneys.net/articles/the-em-dash-responds-to-the-ai-allegations) —）都成了"这里用了 AI"的通用信号。设计领域比写作慢一拍，但正在跟上。近期的模型能产出更好的 UI，但仍然需要大量的手把手引导和 prompt"创可贴"。总体而言，AI 生成的设计往往缺少人类设计师营造出的那种深深的满足感、喜悦或巧思。

### 平庸的 prompt 只能产出平庸的结果

媒体理论家 Marshall McLuhan 常因"人与工具共同演化"的观点被引用："我们塑造工具，此后工具塑造我们。"虽然 AI 能创造出表面上"漂亮"的设计，但它们往往是浅薄的。当你给模型一个泛泛的 prompt，你就得到一个泛泛的输出。当你的意图缺乏方向，结果也会如此。

例如，这是我们用过的一段基础 prompt：*"你好！我想让你为我的电脑配件推荐业务做一个网站，要好看，用深色模式。"*

我们得到的是无聊且可预测的东西：

- 经典的深色背景
- 滥用的卡片
- 盒子上的侧边阴影
- Inter 字体
- 带渐变文字的 Hero 区块
- 三列式特性区块
- 我们从没要求过的、带社交图标的经典页脚

我们在 AI 输出中看到模式，就像在写作中看到模式一样。甚至有指南——[Signs of AI Writing](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing)——专门给它们打标。在测试泛泛 prompt 的过程中，我们也整理出了一份 AI 设计常见"破绽"清单：

- **一切都变成仪表盘** 有一种慢性病：恨不得把所有东西都做得像 AI SaaS 仪表盘，哪怕它本不该是。每个 AI 模型似乎都有这种倾向。哪怕你在为一家面包店做落地页、或做一个作品集网站，只要稍微眯眼一看，你几乎总能把它错认成仪表盘。

而"为什么总是 SaaS 仪表盘"的原因主要是统计学的：大量现代 Web 与 UI 训练数据严重偏向 SaaS 产品、仪表盘、组件库和创业公司落地页。
- **卡片里套卡片** 最可靠也最讨厌的破绽之一。AI 把内容包进一个卡片，然后发现需要组织卡片内的内容，于是又加了更多卡片。结果就是一路嵌套到底的容器。

参见示例 prompt：'给我一个儿童电子邮件客户端'

- **过度编码与不请自来的重构** 最令人抓狂的事情之一，是你的设计已经完成了 99%，只需要一个小改动。你要求改一个按钮，AI 却重构了整棵组件树。你要求加一个简单的 API 调用，它却重写了不相关的错误处理，或加上你没要的类型。

这正是 Codex-Spark（在 Cerebras 上 1200 tokens/秒）这类快速且聚焦的模型大放异彩的领域之一。它倾向于只做那件具体的事然后停手。其余时候，你需要把话说死：

- **指令泄漏到 UI** 更尴尬的失败模式之一：实现说明变成了可见的产品文案。"在这里给用户名字加个占位符"原封不动地作为占位文字出现在线上页面。
- **能跑，但看着不对** 从技术上讲，很多 AI 生成的 UI 是能用的。能编译、能运行，但有些地方就是***不对劲***：间距错位、移动端表现糟糕、组件不对。如果你让它复刻你指定的网站，输出往往像是凭记忆画出的劣质截图，而非真正的重建。距离取代前端设计师还有很长的路要走，但一些真正令人兴奋的进展已经让 AI 生成漂亮 UI 成为可能。
- **没有构图感** AI 不思考元素之间的关系，它只逐个思考元素。结果就是一堆正确的组件，却没有组织逻辑把它们拢在一起。

尽管有这些问题，有意义的进步正让 AI 生成的 UI 从噱头变得更像一个可行的起点。

### 现在有什么不一样？

**生成更快意味着迭代更快。**当一次"prompt 到结果"的往返从 3 分钟变成 30 秒，你不会再太早下注、太晚纠偏。如今，在 Codex-Spark 这类于 Cerebras 上以 ~1,200 tokens/秒 运行的系统加持下，循环收紧了。你可以接连快速地试探、丢弃、打磨。

**视觉模型让你能"展示"而非只是"描述"。**现在你的模型真的能看见自己在构建什么，并利用更新后的信息自我迭代、更好地理解自己的进展。

**围绕设计系统的工具更好了。**shadcn/ui、Figma MCP 集成和标准化 design tokens 等工具给了模型可运作的约束。如今已有了真正的基础设施，让 AI 有现成东西可用，而不是逼它从零发明一套设计。

### 一开始就端正意图

无论你是否身处创意岗位，在使用 AI 工具生成视觉内容时，意图设定都很重要。最有意义的 AI 辅助设计，是用 AI 去填补你技能和短板的空白，把你真正想做的项目做出来。

我们认识到：把 AI 当作设计师或整个设计流程的替代品（那样只会产出复读式的、空洞乏味的东西），不如把它用作**提升、重新诠释并拓宽创意视角的中介工具**——此时 AI 的全部潜力才会喷涌而出。毕竟，说到底，设计只是**解决问题**的另一种视觉形式。

以下是我们用 AI 解决常见设计问题的一些方式：

- 制作压花（embossing）效果：[用 FigmaMake 进行 vibecode，自动化 UI 原型并制作 DIY 铝制压花（@Designteamofone）](https://www.instagram.com/reel/DV_L__flPY-/)。历史上这是一个复杂的过程，需要在 Photoshop 里改一堆不同的设置。在 Figma/FigmaMake 里，你可以一次 prompt 达到类似效果！

- 用 [Flora.ai](http://flora.ai/) 这类软件生成设计样机（mockup）：样机对于把设计放进真实环境、让它看起来和摸起来都真实非常重要。过去，制作样机意味着从专门提供样机文件的网站（如 Mockup World、Bendito Mockups、Mr. Mockup 等）下载 Photoshop 文件，再把你的设计贴到产品图上。但这也导致大量设计师使用同一批烂大街的样机文件（尤其是那些质量高、不俗气的样机）。另一个选择是自己给设计好的实物拍照或自制样机，但代价是需要摄影器材、摄影技巧，以及*时间*去布置一切——而有时我们恰恰没有时间！如今，有了 [Flora.ai](http://flora.ai/) 这样的样机生成网站，你可以极致具体地 prompt 你想要的环境氛围，*并且*得到绝无雷同的设计。

### 8 种方法（3 个类别）

几年前，能写一个贪吃蛇游戏或用 AI 克隆一个设计就让我们乐不可支。如今随着 AI 模型所能达成的复杂度不断提升，我们对 AI 生成设计的可能性空间敞开心胸。以下是我们生成漂亮 UI 的 3 大方向（和 8 个实操方法）。

### 1. 使用 shadcn/ui（并接入 MCP）

先跑一遍 shadcn preset。

这会把组件库以真实源代码的形式装进项目。之后，AI 在写任何东西之前可以先读这些组件，而不是自己发明。

大多数组件库都是黑盒。你导入它们，AI 根据训练数据猜 API，而那些数据可能早已过时。[shadcn/ui](https://ui.shadcn.com/) 不同：源代码归你所有，组件活在你的项目里，AI 可以在动手前先读它们。

[MCP 集成](https://github.com/Jpisnice/shadcn-ui-mcp-server)让这件事更上层楼。连上 shadcn MCP 服务器后，模型会在对话过程中查询实时的组件注册表。问它"给数据表加排序"，它会拉取当前的文档，而不是幻构出六个月前的 props。

使用这套方式的团队反馈：组件第一次尝试就能编译通过。如果你曾目睹 AI 花四轮迭代与自己的 import 路径搏斗，你就会在乎这一点。

### 2. 先定设计，再碰代码

做设计决策最糟的时机就是生成进行到一半时。AI 会替你做决定，而且专挑训练数据里最常见的：可能是 Inter、天蓝色按钮或圆角卡片。

在输入任何 prompt 之前，先定好：精确的十六进制色值、字体栈、间距刻度、总体布局逻辑。然后把它编码到 AI 读得到的地方，比如 Tailwind config、design tokens 文件或 CSS 自定义属性。[designtoken.md](https://designtoken.md/) 提供了一个不错的格式。

命名方面，用意图化命名而非原始值命名也有帮助。*--color-primary* 胜过 *--color-blue*，因为模型知道它属于什么语境。*--color-error* 能阻止它误把你的成功绿用在错误状态上。

[Figma 的 MCP](https://help.figma.com/hc/en-us/articles/32132100833559-Guide-to-the-Figma-MCP-server)更进一步。如果你一直在 Figma 里用定义好的组件做设计，AI 可以直接读取它们，从而减少猜测。

用 GPT-Image-2 生成多个样机，并把它们作为提示喂给 Codex 以获得更高质量的输出。这套工作流在避免浪费 token 和产出令人失望的垃圾应用方面极为有效，强烈推荐！

### 3. **让 Tailwind 学会说不**

Tailwind 的配置文件是一个强制执行机制。如果你只定义你想要的颜色，任意十六进制值就会被 lint 拦下。AI 不得不使用你的体系，而不是另发明一套平行宇宙。语义化命名很重要：

当颜色被命名为 destructive，AI 就不会在成功按钮上伸手去拿它。语境编码进了名字里。再加一条 lint 规则禁用任意 Tailwind 值（*text-[17px]*、*bg-[#4a9f8c]*），你就从结构上让"脱轨"变得困难。

### 4. 用小步改动来迭代

"我想要深色模式……还有卡片/盒子少一点"是一个合理的诉求，但太含糊了。AI 删掉两个卡片就宣布完工了。

更好的工作流是：一个小改动，在浏览器打开站点，看一眼，具体说出哪里不对。

"这个按钮需要再加 4px 内边距。""这个标题字重太轻。""这两个区块之间的间距感觉挤。"这些是可修复的指令。"让它好看点"不是。

[GPT-5.4 的视觉能力](https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4)让这个循环更紧。截个图，递给模型，描述视觉上哪里不对，拿到修复。"渲染-截图-描述-打磨"这个循环到达目的地的速度，比任何前置规格文档都快。

### 5. 先来采访我

我发现构建风格指南最好的方法之一，就是不再试图一个人写完全部。我通常先给模型几个锚点：我喜欢的颜色、感觉接近的截图，也许再来一两个质感对了的组件或网站。但我不会马上让它把这些变成设计系统，而是先让它采访我。尤其在快模型上，这种来回迭代和对话几秒钟就能完成。借助 [grill-me skill](https://github.com/mattpocock/skills/blob/main/skills/productivity/grill-me/SKILL.md) 也会有帮助。

这之所以好用，是因为模型往往比我更擅长注意到"缺了什么"。它会问：

- 你的目标受众是谁？
- 这个页面的目标是什么？

Thomas Wiegold 关于 frontend-design 插件的文章在"完整的风格指南"上也持类似观点：与其依赖魔法工具，不如强迫模型在产出 CSS 之前先声明目的、基调、约束与差异化。他还指出，死板的像素级规格会让输出在技术上服帖，视觉上却了无生气。

### 6. 生成多个方案，选一个，往深里做

得到更好设计最"自由"的方式之一，是在表态之前先要几个图形方向。生成五个粗糙变体只要几分钟，尤其是有 Codex Spark 这样的快模型。然后摘取你最喜欢的设计，继续在那个版本上迭代。

例如，你可以 prompt 出气质、布局或配色截然不同的方案。挑最接近的那个。然后："保留它的配色和字体，但试试非对称布局。"OpenAI 在他们的[前端生成指南](https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4)中明确点出这一招：先生成情绪板（mood board），再下注。

### 7. 跑"构建-观看-修改"循环

GPT-5.5 可以给渲染出的 UI 截图以复核结果。或者，你可以直接"指"出问题而不是用语言描述。比如，与其说"这个按钮的 padding 看起来不对"，不如递上一张圈出问题位置的截图。

### 8. 用真实丑陋的数据，而不是漂亮占位数据

大多数 AI 生成的 UI 比它的真实水平看起来更好，因为数据是假的。名字都很短，价格都对齐，描述长度一致。空状态从不出现，错误状态只是装饰。

### TLDR

放任不管，模型会默认输出统计学上最常见的那版"好看 UI"：深色背景、圆角卡片、渐变标题、三列特性网格、Inter 字体、页脚。

最好的工作流把模型当作一个快速但过度自信的初级设计师来指挥：选定意图，在它跑偏时及时察觉，并推向刻意的惊喜与个性。模型更快、更懂视觉、更擅长在既有体系内工作，这让天花板比几年前高了许多。但人仍然要选择最重要的东西：感觉与方向。:)
