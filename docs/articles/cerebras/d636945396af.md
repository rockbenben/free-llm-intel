# MCP 与 CLI 之争，核心在速度

Zhenwei Gao

MCP 经历了它的成长之年，随后又度过了动荡的一周。

Perplexity CTO Denis Yarats 在 Ask 2026 大会上登台，宣布 Perplexity 正在远离 MCP……回归 API 和 CLI。

Twitter 立刻分裂成两个阵营。

这并不意外，考虑到 MCP 从 2024 年 11 月 Anthropic 的开放标准起步，仅用十三个月就实现了全行业采用，[月下载量超过 9700 万次](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation)（1），覆盖众多公司和平台。

然而，作为一家头部 AI 公司，Perplexity 却选择转身离开。

MCP 的开销并非凭空而来。该协议的工作[方式](https://modelcontextprotocol.io/docs/getting-started/intro)（2）是把模型交互引导到特定、可审计的路径上：每次工具调用都携带完整的 schema 定义，每次认证握手都端到端运行，每一步都要等上一步完成后才开始下一步。这种可预测性恰恰是企业级部署所需要的。

但它有代价：在多步骤工作流中，每个结构化的步骤都会增加延迟，而这些成本会在长长的工具调用链上不断累积。

### **反对 MCP 的理由**

为这一转变欢呼的人认为，MCP 的 token 开销是一种有害的约束，会拖慢运行时，并且随着接入工具增多而愈发恶化。DevCommunity 的 Samir Amzani [指出](https://dev.to/amzani/your-mcp-server-is-eating-your-context-window-theres-a-simpler-way-3ja2)（3），仅连接 GitHub、Slack 和 Sentry 三个服务，就可能在 agent 读到任何一条用户消息之前，往 MCP 上下文窗口里塞进超过 55,000 个 token 的工具定义；其 token 用量比 CLI 高出 [3-42 倍](https://www.scalekit.com/blog/mcp-vs-cli-use)（4）不等。

### **支持 MCP 的理由**

不过，支持者虽然承认 MCP 存在延迟问题，但也指出了开发者转向 CLI 将失去的东西。CLI 轻量、快速，但同样是静态的：只能调用被明确编程好的工具，要求开发者为每个服务单独管理认证，而且没有供可观测性或调试使用的共享协议层。

Perplexity 没有给出官方解释，但这道分歧反映的是真实的开发需求：对延迟要求更苛刻的团队可能觉得 CLI 更实用，而优先考虑可观测性和生产安全性的团队则可能认为 MCP 的结构物有所值。

### **超越协议选择本身**

切换到 CLI 和 API 确实能解决一些问题：token 开销下降，单步延迟改善。但它无法解决所有问题。一些根本性约束——规模化的延迟累积、不安全的代码执行——并不是换一层接口就能彻底消除的。

这些更深层的约束指向两个值得审视的领域：推理基础设施和代码执行环境。

### **考量之一：更快的推理**

首先是推理基础设施——更快的推理直接针对延迟问题。为低延迟 AI 工作流设计的新一代芯片架构，例如 [Cerebras 的 Wafer-Scale Engine](https://www.cerebras.ai/chip)（5），将模型权重保存在跨晶圆片上存储器中，而不依赖片外存储，从而消除了传统 GPU 推理的内存瓶颈。其结果是最快可达 [3,000 tokens/秒](https://inference-docs.cerebras.ai/models/overview)（6），视模型不同，约比传统 GPU 方案[快 15 倍](https://www.cerebras.ai/blog/speedandaccuracyblog)（7）。

这种速度改变了对 MCP 的权衡计算。把更快的推理与真正的 MCP 服务器搭配起来——用 GitHub 获取代码上下文、用 Slack 获取团队数据、用 Atlassian 获取项目状态——每次工具调用的延迟成本都会显著缩小。当底层推理足够快时，那些让 MCP 显得不实用的开销就变得更可控了。

对于已经把 MCP 的可审计结构放在首位的企业来说，这一点很重要：更快的推理不需要以牺牲安全层为代价，它只是让整个技术栈——包括工具调用在内——在生产环境中更加可行。

另一个考量在于安全的代码执行。运行 agent 生成的代码，需要在安全与速度之间做权衡。

[Monty](https://github.com/pydantic/monty)（8）是 Pydantic 发布的一个用 Rust 编写的最小化 Python 解释器，它选择了另一条路——把作用域压到最小。Monty 不启动容器、也不暴露完整运行时，只运行 agent 需要的部分：默认没有文件系统访问、没有网络调用、没有环境变量，除非显式授予；只有在外部调用需要授权时才暂停。由于解释器极其精简，prompt 注入的攻击面也相应变小。

它的启动时间[低于 0.06ms，相比之下 Docker 是 195ms，沙箱服务则超过 1,000ms](https://github.com/pydantic/monty)（9）。不过 Monty 仍处于实验阶段，只支持 Python 的一个子集，且不支持第三方库，因此还不能用于生产环境。但它为后续迭代和开发提供了蓝图。

### **这些考量同时惠及 MCP 和 CLI**

推动 MCP 与 CLI 之争的那些痛点是真实存在的：token 开销、拖沓的工作流、运行 agent 生成代码的风险——这些都无可争辩。但如何让体验提速，相当大一部分答案位于推理基础设施和执行环境，而不仅仅是协议本身。而且这些改进并非 MCP 独享——同理，CLI 工作流也能因此提速。

### **把约束放回语境**

Perplexity 是针对真实约束做出的务实选择，那些悄悄转向 CLI 的众多团队也是如此：因为 MCP 感觉太慢了。同样有大量团队坚定留守 MCP。就各自具体的开发需求而言，两种决定都是合理的。

在 MCP 与 CLI 的争论继续发酵之时，抛开协议不谈，推理基础设施和执行环境同样值得同等关注。
