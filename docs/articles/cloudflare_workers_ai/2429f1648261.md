## 2026-02-17

Chat Completions API 支持 gpt-oss 模型，tool calling 改进

- [`@cf/openai/gpt-oss-120b`](https://developers.cloudflare.com/workers-ai/models/gpt-oss-120b/) 和 [`@cf/openai/gpt-oss-20b`](https://developers.cloudflare.com/workers-ai/models/gpt-oss-20b/) 现已支持 Chat Completions API 格式。可以在 `/v1/chat/completions` 中使用 `messages` 数组，也可以使用 `/ai/run`——它会自动识别您的输入格式，同时接受 Chat Completions（`messages`）、旧式 Completions（`prompt`）或 Responses API（`input`）。
- **[Bug 修复]** 修复了多个文本生成模型 schema 中的 bug：消息对象的 `content` 字段此前只接受字符串值。该字段现已正确同时接受字符串内容和数组内容（用于多模态输入的结构化内容部分）。此修复适用于所有受影响的聊天模型，包括 GPT-OSS 模型、Llama 3.x、Mistral、Qwen 等。
- **[Bug 修复]** tool call 往返（round-trip）现在可以正常工作。binding 不再拒绝它自己生成的 `tool_call_id` 值，修复了多轮 tool calling 对话的问题。
- **[Bug 修复]** `content: null` 且带有 `tool_calls` 的 assistant 消息，现在在 Workers AI binding 和 REST API（`/v1/chat/completions`）中都能被正确接受，修复了 tool call 往返失败的问题。
- **[Bug 修复]** 流式响应现在只在 usage chunk 上正确报告 `finish_reason`，与 OpenAI 的流式行为保持一致，避免出现重复的 finish 事件。
- **[Bug 修复]** `/v1/chat/completions` 现在会保留模型返回的原始 tool call ID，而不再重新生成。此前该端点会生成新 ID，导致 AI SDK 客户端无法把 tool 结果与原始调用匹配上，破坏了多轮 tool calling。
- **[Bug 修复]** 使用 tools 时，`/v1/chat/completions` 现在会在最后一个 usage chunk 中正确报告 `finish_reason: "tool_calls"`。此前它硬编码为 `finish_reason: "stop"`，导致 AI SDK 客户端误以为对话已经完成而没有继续执行 tool calls。

## 2025-02-21

Workers AI bug 修复

- 我们修复了 `max_tokens` 默认值未被正确遵循的 bug——`max_tokens` 现在正确地默认模型页面所示的 `256`。依赖此前行为的用户可能将其视为破坏性变更。如果您希望生成更多 token，请将 `max_tokens` 参数设置为所需值。
- 我们更新了模型页面以展示上下文窗口——其定义为 prompt 使用的 token 数 + 响应使用的 token 数。如果 prompt + 响应的 token 总量超过上下文窗口，请求将报错。请根据您的 prompt 长度和上下文窗口长度合理设置 `max_tokens`，以确保获得成功的响应。
