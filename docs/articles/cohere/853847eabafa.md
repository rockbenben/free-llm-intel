# 扩展 coding agent 团队的经验教训：用 30% 的成本触达前沿水平

coding agent 团队已经在构建大规模软件，但它们究竟该如何组织，才能既最有效又最高效？

![](https://cdn.sanity.io/images/rjtqmwfu/web3-prod/ef8dcc11f006e85e91e7f1ee6803ef8a1ce91ce5-1913x1076.svg)

核心要点

- **agent 团队开出了 inference-time scaling 的一条新维度。** 在有挑战的编码任务上，组织良好的团队胜过单个 agent，在 ProgramBench 上的收益最高可达约 10 个百分点。但这些收益伴随 3–7× 的更高成本。问题不在于更多的 agent 是否有用，而在于如何让这部分额外算力真正起作用。
- **把 agent 分配到哪里，比你加了几个更重要。** 在 ProgramBench 上，只委派探索与规划，就能匹配同时委派规划、实现与验证的表现，而成本只有一半。当 agents 对准任务真正的瓶颈时，协作的回报最大。
- **一个强 lead 配上便宜的 workers，就能以低 70% 的成本交出接近前沿的表现。** 一个 Sol lead 协调 16 个廉价的 Luna 规划 workers，达到 61.8% 的 reward；而把每个阶段都委派的纯 Sol 团队是 63.2%，成本却从 $510 降到了 $155。

### agent 团队正在构建软件

过去一年里，coding agent 团队从有意思的 demo 走向了构建大规模软件项目。16 个 Claude agents 写出了一个 10 万行、能够构建 Linux kernel 的 C 编译器，整个项目花了约 2,000 次 agent sessions 和 $20,000 的 API 成本 [[1](https://www.anthropic.com/engineering/building-c-compiler)]。Cursor 运行了数百个 agents，一起从零写出一个 web browser，代码超过一百万行，用时约一周 [[2](https://cursor.com/blog/scaling-agents)]。Bun 从 Zig 移植到 Rust 用了 11 天，高峰期有 64 个 Claude agents 并行运行 [[3](https://bun.com/blog/bun-in-rust)]。

这些团队都产出了能工作的软件，但它们在许多方面同时彼此不同，从模型和角色到项目本身的规模都是如此。那个 C 编译器的 agents 以对等方式工作、没有 orchestrator，通过 lock files 认领任务。Cursor 用的是层级结构，planners 递归地把工作拆成子任务，委派给数百个 worker agents。Bun 则指派固定角色，把每块工作交给一个 implementer、两个 adversarial reviewers 和一个 fixer。

然而，把它们拿来互相比较，很少能说明哪些设计选择真正起了作用、相比单个 agent 又花了多少钱。Factory 对他们自己的多 agent 系统的研究——该系统让一个 orchestrator、一个 implementer 和一个 validator 在一个固定循环里轮转——说明了这项成本可以有多大 [[4](https://factory.com/news/what-it-takes-for-coding-agents-to-complete-large-software-tasks)]。在重建地理空间库 GDAL 这一个任务上，他们的三角色团队把单个 agent 达到的 reward 翻了一倍多，几乎与参考程序行为对等，但成本是 14 倍、耗时是 13 倍。

所以 agent 团队能做的事比单个 agent 更多，但运行起来成本更高，通常也更耗时。这引出一个重要问题：如果一支 agent 团队是消耗 inference compute 的一种新方式，那么**它该如何组织，才能既有效又高效？** 为了回答这个问题，我们搭了一个受控 testbed，并在其上运行 coding agent 团队。

**图 1.** 一次 coding agent 团队运行的示意。一个 lead 把工作分派给它的 workers，由后者在一个共享 workspace 里探索原程序、写代码并检查。

### 一个受控 testbed

**一个极简 harness**

我们故意把 harness 做得极简——灵感来自 [mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent) [[5](https://arxiv.org/abs/2405.15793)]——这样就能一次只改一个设计选择。每个 agent 都通过一个简单的 `bash` 工具工作，在整支团队共享的一个 workspace 里。有一个 agent 是 lead，它接收任务，并用一个 `delegate_agent` 工具分派工作。一个 worker 只看到分给它的那个子任务，做完就回报。拿到任务后，lead 动态决定要 spawn 多少个 workers、每个做什么，以及如何把它们返回的东西汇总起来。1

每次 `delegate_agent` 调用要么启动一个带全新 context window 的新 worker，要么唤醒一个 lead 之前用过的 worker。被唤醒的 worker 保留它先前的上下文，所以 lead 可以接着和一个已经了解部分程序的 agent 继续往下走。例如，lead 可以让一个 worker 去修它自己写的代码里的 bug，而不用从零开始给一个新 worker 讲背景。

在此基础上，我们改变五件事：

- **lead 在哪些环节使用 workers。** 我们用两个主要 prompts 来指示 lead agent，两者的区别在于给出的指导多少。*minimal* prompt 告诉 lead 它负责一支团队，并要求它给 workers 分配彼此有别、相互独立的任务，但其余一切——从用多少个 workers 到如何分解任务——都留给 lead。*PIV* prompt 增加了一个结构化的工作流：探索与规划（P）、实现（I）、验证（V），并要求 lead 在这三个阶段都使用 workers。
- **lead 如何等待。** *blocking* 的 lead 等它的 workers 回报，期间什么都不做。*asynchronous* 的 lead 在它们运行期间继续干活，并多出两个工具：用 `wait_for_updates` 等待下一份报告，用 `list_agents` 查看它的 workers。
- **哪些模型担任哪些角色。** 团队里每个 agent 都需要最强、最贵的模型吗？我们用两类团队来测这一点。在 *homogeneous* 团队里，lead 和它的 workers 全都跑同一个模型。在 *heterogeneous* 团队里，lead 保留强模型，workers 跑一个更便宜的模型。可以想象成一位资深工程师指挥工作、做关键决策，而大部分跑腿的活由初级工程师完成。
- **一共有多少个 workers。** 团队越大就一定越好吗？为了探索这一点，我们比较两种设置。第一种由 lead 自己决定需要多少个 workers。第二种我们把团队规模固定在 2、4、8 或 16 个 workers，看 reward 和成本随团队变大如何变化。
- **agents 之间如何通信。** 默认情况下，所有通信都经过 lead：它分派每个子任务，也接收每个 worker 的报告。在另一组运行中，我们给 agents 提供一个 `send_message` 工具，让它们直接互相发消息。

**图 2.** 两个 lead 分派同样的子任务，每次 worker 运行的耗时也相同。blocking 的 lead 一直空着，直到它的 workers 回报。asynchronous 的 lead 继续干活，第一批报告一到就开启第二轮。横条表示工作的时间区间，向下的箭头是对 `delegate_agent` 的调用，向上的箭头把报告带回给 lead。时间仅为示意。

### ProgramBench

我们在 ProgramBench [[6](https://arxiv.org/abs/2605.03546)] 上测试这些选择，这是一个包含 200 个待从零重建程序的 benchmark。每个任务里，agent 从一个空 workspace 开始，里面只有原程序的可执行文件（它能运行但不能读）以及该程序的文档。它必须试探这个程序，摸清它的接口、边界情况和行为，然后写出一份行为相同的新实现。我们给每个任务打分，看的是重建出的程序在一套隐藏行为测试集上通过的占比，再把这些分数在任务上取平均，得到全文报告的 reward。2

任务范围从小型命令行工具（如 jq 和 ripgrep）到大型系统（如 SQLite、FFmpeg 和 PHP 解释器）。最难的那些仍然远不可及。在 FFmpeg 上，[公开 leaderboard](https://programbench.com) 上最好的提交只通过了约 10% 的测试。

每个任务都需要工作流的全部三个阶段：弄清程序在做什么、把它写出来、再对照原程序检查。这让 ProgramBench 成为一个不错的 testbed，可以看出哪些阶段能从额外的 agents 中获益。

**图 3.** 一个 ProgramBench 任务 `dsq`，一个在 JSON、CSV 和其他数据文件上运行 SQL 查询的命令行工具。上半部分是使用 minimal prompt 的单个 Sol agent，下半部分是使用 PIV prompt 的 asynchronous Sol 团队。单个 agent 把它的程序写成一个 Python 文件，而团队把它拆成若干模块，其中一些由 workers 编写。团队那一面板跟踪的是某一次运行的文件，命令是从 agents 自己的命令简化而来的，时间仅为示意。

我们主要关注三个 GPT-5.6 模型：Luna、Terra 和 Sol，按能力和成本递增排列。除非另有说明，我们在全部 200 个 ProgramBench 任务上把每种配置各跑三次，并报告三次运行在 reward、总成本和总 wall-clock 时间上的平均值。单个任务的分数会随运行波动，标准差约 6 分；但整个 benchmark 层面的平均值稳定得多，典型配置的标准差是 0.5 分，噪声最大的一种也只有 1.4 分。每种配置跑的都是同一批任务，所以我们逐任务地把每支团队与它的 solo 基线比较，并报告这些差值的 95% 置信区间。

我们也跑了 Commit0-Lite [[7](https://arxiv.org/abs/2412.01769)]，这是一组 16 个 Python 库，其实现已被移除。agent 会拿到每个库的仓库骨架、文档和单元测试，必须把代码补齐让测试通过。在 ProgramBench 上，agent 得靠运行原程序来弄清楚要构建什么。在 Commit0 上，这些给到的材料已经把规格写明了，于是这个 benchmark 能说明：当规格已经给定时，同样的阶段是否还划算。只有 16 个任务，所以我们把它当作次要验证。

### 团队胜过 solo agents，但要付出代价

我们从最简单的比较开始：一个 Sol agent 对阵一支 Sol agents 团队。用同样的 minimal prompt，blocking 团队平均通过 61.8% 的测试，而 solo agent 是 52.1%。给 solo agent 换上 PIV prompt 能缩小一部分差距（57.7%），但使用 PIV prompt 的 blocking 团队仍然领先约 5 分（63.1%）。

我们也用 asynchronous lead 跑了这两种 prompts——它可以在它的 workers 运行期间继续干活。这四支 Sol 团队的成本都在对应 solo agent 的 4 到 7 倍之间。用 PIV prompt 时，asynchronous 团队比 blocking 团队少花 19.5% 的时间完成，reward 大致相同。

用 minimal prompt 时，asynchronous 团队少花 60% 的时间完成，但它的 lead 自己承担了更多工作，每个任务只委派 4.4 次，而 blocking lead 是 6.1 次。这支团队相对使用 minimal prompt 的 solo agent 只涨了 3.8 分，而 blocking 团队是 9.7 分；55.9% 的结果甚至低于使用 PIV prompt 的 solo agent（57.7%）。

**图 4.** 平均 reward 对照 inference 成本（左）和 wall-clock 时间（右），两者都是全部 200 个任务的总量、再对三次运行取平均。误差线是每支团队与对应 solo agent 逐任务成对差值的 95% 区间。

### workers 在规划阶段回报最大

为了弄清 workers 在哪些环节划算，我们指示 lead 只在一个阶段把子任务委派给 workers，其余两个阶段由它自己完成。在探索与规划（P）下，workers 运行程序以了解其行为并起草一份计划，lead 负责实现和验证。在实现（I）下，workers 写代码。在验证（V）下，workers 测试 lead 的实现。

规划是明显的赢家。在 asynchronous 团队中，只委派规划的 lead 达到了与委派所有阶段的 lead 相当的 reward（63.6% 对 63.2%），成本却只有一半（$249 对 $510）。按每 $100 额外成本换来的 reward 来衡量，规划的效率大约是次优阶段的两倍。3

**图 5.** 只委派一个阶段或委派全部三个阶段的 asynchronous Sol 团队。数值为三次运行的平均值。线从 solo PIV agent 连向每支团队。虚线箭头从 PIV 团队指向规划团队，后者的成本只有一半。误差线是相对 solo PIV agent 的成对 95% 区间。

例如，在 `dsq` 上，使用 PIV prompt 的 solo agent 平均通过 60% 的测试。只委派规划的团队，配 asynchronous lead 时通过 79%，配 blocking lead 时通过 76%，而且它们六次运行中的每一次都胜过了任何一次 solo 运行。委派实现或验证的团队只通过了 58% 到 71%。

原因出在这个 benchmark 的设计上。目标程序是一个黑盒，所以它的行为必须靠运行来发现。规划的 workers 并行做这件事，各自探测程序接口的不同部分，把探到的结果交给 lead。随后 lead 自己在对要构建之物有更完整图景的情况下把代码写出来。

别的工作也报告过相关发现。Factory 的 validator 在写下任何代码之前，先探测参考程序，构建出一个可执行的、关于“done”意味着什么的标准 [[4](https://factory.com/news/what-it-takes-for-coding-agents-to-complete-large-software-tasks)]。Carlini 的 C 编译器团队在 Linux kernel 上卡住时，是靠把 GCC 当作 oracle 来对比才脱困的 [[1](https://www.anthropic.com/engineering/building-c-compiler)]。每一种情况里，确切知道要构建什么才是瓶颈，把算力投在那里就有回报。

Commit0 展示了这件事的另一面。在那里，仓库已经把要构建什么摆明了；在我们十种团队设置中有八种，最有效的委派阶段是实现而非规划。不过，GPT-5.6 Sol 这样的前沿模型已接近把 Commit0 打满——一个称职的 solo agent 在 16 个任务里的 12 个上已经通过全部测试，只剩 4 个任务是团队可能做得更好的，所以我们把这一点当作提示性证据而非定论。

### 规划的 workers 可以很便宜

如果规划的 workers 主要是给 lead 收集信息，它们还需要是强模型吗？我们让 Sol 继续担任 lead，把它的规划 workers 换成 Luna，一个便宜得多的模型。这支团队相对纯 Sol 团队让出了几分（60.5% 对 63.6%）。但用 solo agent 作基准来衡量，它保住了纯 Sol 团队收益的 47.5%，只花掉其额外成本的 13.9%，所以每一美元换来的 reward 是三倍多。

现在把它和不看任务就可能搭出来的方案比一比。一个自然的对照同样会是 PIV 设置：告诉一个强 lead 在每个阶段都用强 workers。那支团队达到 63.2%，但成本是 $510。通过认识到 ProgramBench 的瓶颈在于发现程序在做什么，并且只在规划上投入便宜的 workers，我们只用五分之一的成本，就和它只差 2.7 分了。

**图 6.** 图 5 的那几支团队，加上两支由 Sol lead 配 Luna workers 的团队（worker 圆点更小），一支只委派规划，一支委派全部三个阶段。所有团队都是 asynchronous。虚线箭头从纯 Sol 的规划团队指向 Luna 的规划团队，标注的是 Luna 团队占纯 Sol 团队收益与额外成本的比例，两者都以 solo PIV agent 为起点衡量。误差线是相对 solo PIV agent 的成对 95% 区间。

为了把 lead 的贡献和 workers 的贡献拆开，我们把 workers 固定在 Luna，把 lead 从 Luna 升级到 Terra 再到 Sol。每升级一次 reward 都在上升，从 42.5% 到 51.6% 再到 60.5%（图 7），而且每支团队都胜过一个运行其 lead 所用模型的 solo agent（37.4%、47.2% 和 57.7%）。不过便宜的 workers 补不上一个更弱的 lead。Terra lead 配 Luna workers，仍然不及独自干活的 Sol agent（51.6% 对 57.7%）。

**图 7.** solo PIV agents 与 asynchronous 规划团队的平均 reward 对照总 inference 成本（对数刻度）。*homogeneous* 团队——每个 agent 用同一个模型——圆点大小一致；*heterogeneous* 团队——较强 lead 配 Luna workers——worker 圆点更小。阴影带连接的是三支使用 Luna workers 的团队。

这与 Meta 近期关于 meta-reasoning 的工作相吻合 [[8](https://arxiv.org/abs/2609.38147)]。他们的系统把一个 agent 拆成 controller 和 workers：controller 决定接下来做什么、要在哪些早先的结果上继续构建，workers 去做那部分工作。用同样的 workers 和同样的预算，更好的 controller 在 ProgramBench 上得分更高（GPT-5.5 下 71.5% 对 63.7%），而且随着预算增加它的优势还在扩大，更简单的 control 则趋于平缓。在他们的设置和我们的设置里，更强的决策者都抬高了同一批 workers 的成果。

### 扩展 workers 的数量

到目前为止，用多少个 workers 由 lead 自己选。为了看更多 workers 增添了什么，我们把团队规模固定下来，给一个 Sol lead 配 2、4、8 或 16 个 Luna workers。规划团队随着变大改善了整体表现，从 2 个时的 59.6% 到 16 个时的 61.8%。即便是 16 个，Luna 规划者的成本也只有 $155，比纯 Sol 的规划团队（$249）低 38%，比委派全部三个阶段的纯 Sol 团队（$510）低 70%，同时与这两者的差距都保持在 2 分以内。

实现与验证的 workers 表现不同。它们从 2 个增加到 4 个时有改善，之后继续加人就略微回落。深入运行内部可以看出原因。无论团队规模多大，每个规划者大约运行 7 次参考程序，所以规划者越多，就让 lead 看到越多程序的行为。就整支团队而言，参考程序的运行次数从 2 个规划者时的 15 次增长到 16 个时的 109 次，规划者的报告也从 17,000 字符增长到 75,000 字符。

额外的 implementers 没有带来这类信息。每个拿到的计划切片更薄，任务量从 2 个 implementers 时每人约 1,400 字符缩水到 16 个时的 440 字符。implementers 贡献的代码占比从 2 个时的 54% 升到 16 个时的 85%，但 lead 把合并后的程序拿去和参考程序对照检查的次数并没有变多——无论合并的是两块还是十六块，都是 5 到 6 次运行。

**图 8.** 一个 asynchronous Sol lead 配 2 到 16 个 Luna workers 的 reward，按团队规模（左）和总成本（右）绘制。每个带 Luna workers 的标记里，每个 worker 对应一个小圆点。圆点大小一致的标记是由 lead 自行决定规模的纯 Sol 团队。每种固定规模的配置只跑一次。误差线是相对 solo PIV agent 的成对 95% 区间。

### 探索通信

到目前为止，agents 只在 lead 分派工作时、以及 worker 回报时交换信息。我们也试过给每个 agent 一个 `send_message` 工具，可以触达任何其他正在运行的 agent。

在我们的运行中，我们注意到这个通道主要被用来向上汇报。在使用 PIV prompt 的 Sol 团队里，84% 的消息是从 workers 发给 lead 的，内容是阶段性发现、建议的接口、测试失败和问题。4 workers 之间的消息平均每个任务不到一条；即使告诉 workers 把彼此当作协作者，也只升到每个任务约一条。

更强的模型更频繁地使用这个通道。Sol agents 写的消息文本量是 Luna agents 的 3.4 到 5 倍，Sol leads 也向自己的 workers 回了更多指导。然而 reward 方面，Sol 和 Terra 团队保持不变，Luna 团队则掉了 4 到 7 分。一种可能的解释是，源源不断的阶段性更新把一个较弱的 lead 淹没了，而更强的 lead 能消化它。另一种是 Luna workers 用不好这个工具——它们的 `send_message` 调用约一半格式不对，被 harness 拒绝了。

**图 9.** 带 send_message 工具的 asynchronous 纯 Luna、纯 Terra 和纯 Sol 团队。斜纹段表示被拒绝的调用。左：每个任务的消息数。中：每个任务的消息文本量。右：与同一支团队不带该工具相比的 reward 变化，附成对 95% 区间。

话虽如此，在合适的设置里通信仍然可能有用。我们的 harness 是围绕拆分工作并委派它来构建的。minimal 和 PIV 两种 prompts 都要求 lead 给 workers 分配彼此有别、相互独立的任务，所以每个 worker 手里没什么别的 worker 需要的东西。这样看来，workers 给 lead 发消息远多于给彼此发消息，也就合情合理了。

与此形成对照的是，Park 等人发现，当 agents 共享一个目标和一个公共 workspace、没有固定角色时，一支由 5 个能通信的 agents 组成的团队在 ARC-AGI-3 上追平了 33 个独立 agents 中最好的那个 [[9](https://arxiv.org/abs/2609.21032)]。他们称之为 *verified progress sharing* 的关键要素在于：agents 能够核查一个队友的发现是否真的算改进。Agensh 是 Microsoft 的一个自组织 harness，也报告了在大型扁平团队中合作自发涌现的现象 [[10](https://arxiv.org/abs/2609.26781)]。

agents 之间互相说多少话，取决于任务、工作怎么拆分、agents 如何被 prompts，以及它们的模型是如何训练的。我们预计，当 agents 追求同一个目标、能互相检查彼此的进度，并且被要求把通信当作工作的一部分时，发消息这件事最要紧；我们正在后续工作中积极探索这一点。

### 其他模型如何使用一支团队

我们还在 ProgramBench 的一个 30 任务子集（10 个简单、10 个中等、10 个困难任务）上，用完全相同的工具和 prompts 测了另外五个模型，并和 GPT-5.6 在同样这些任务上的运行做比较。5 对每个模型，我们各跑一次 solo、blocking 和 asynchronous 团队的试验，同时使用 minimal 和 PIV 两种 prompt 设置。每个模型只跑一次，所以几分以内的差异可能只是噪声。

这些模型使用团队的方式差别很大。GPT-5.6 团队频繁委派，相对其最好的 solo agent 最多涨了 6.9 分，而且多数团队设置都占了上风。Claude Opus 4.8 表现大致相同，用 PIV prompt 配 asynchronous lead 涨了 5.9 分。Claude Opus 4.7 很少委派，每个任务最多 1.3 次，它的团队相对其最好的 solo agent 几乎没有收益。6 Claude Haiku 4.5 和 Gemini 3.7 Flash 像 GPT-5.6 一样乐于委派，却从中得不到任何东西。Gemini 3.8 Flash 用 PIV prompt 配 blocking lead 涨了 3.1 分，但配 asynchronous lead 时反而掉了 4.6 分。

**图 10.** 在 ProgramBench 的 30 任务子集上，每个任务的委派次数（左）以及团队相对最好 solo agent 的提升（右）。对每个模型，提升都是与 minimal 和 PIV 两种 prompts 中得分更高的那个 solo agent 相比。每个标记代表四种团队设置之一。GPT-5.6 的结果是这 30 个任务上三次运行的平均值。其他模型只跑一次，所以约 5 分以内的差异可能只是噪声。

团队要有帮助，两件事得同时做对。lead 必须选择委派，而且必须好好利用带回来的东西。Opus 4.7 输在第一点，Haiku 4.5 和 Gemini 3.7 Flash 输在第二点。两个 Opus 模型说明这件事在一个家族内部就能变这么多。Opus 4.7 几乎不委派，而更新的 Opus 4.8 像 GPT-5.6 那样把工作铺开给一支团队，并从中获益。至于更新的模型是否普遍更擅长带领团队，靠每个模型只跑一次我们无法下定论。

这些模型组织自己程序的方式也不同。GPT-5.6 用 Python 重建了多数程序（占提交的 70% 到 93%），不管原程序是用什么语言写的。Claude 模型在 72% 到 90% 的提交里用原程序的原始语言重新实现它，两个 Gemini Flash 模型居中（43% 到 70%）。Claude Opus 4.8 和两个 Gemini 模型还把自己的程序分散到更多文件里——每个任务的中位数是 5 到 11 个源文件，而 GPT-5.6 是 1 到 3 个。

### 接下来

我们的结果指向好几个令我们兴奋的方向。

- **层级结构 versus 自组织。** 在 ProgramBench 上，单个 lead 能把整个程序尽收眼底，所以层级结构很管用。但一支由数千个 agents 组成、连续工作数周的团队，大概会超出任何单个 lead 能跟踪的范围。这样的团队必须决定由谁分配角色、信息如何流动、什么时候重组。在那个规模上，agents 将需要直接分享它们学到的东西，也许通过它们自己发明的协议。Pretraining 已经给了它们基本的动作，比如汇报、提问和委派。随着模型扩展，真正的协调是会从这些动作里涌现，还是必须靠训练获得——我们认为这是扩展 inference 的核心未解问题。
- **其他通信形式。** 在我们的运行里，消息大多重复了 lead 反正也会从报告中收到的内容。共享目标、共享进度日志，或者携带可核查证据的消息，也许能给 agents 更多开口的理由。
- **适应任务。** 规划在 ProgramBench 上有回报，因为规格必须靠发现；但在别的任务上瓶颈可能在别处。在 Commit0 上，帮助最大的是实现。一个能判断出自己手上任务卡在哪里的 lead，可以直接把 workers 调过去，而不需要被告知该委派哪个阶段。
- **训练模型去带领。** 不同模型使用团队的水平差别很大，这暗示带领是一项可以训练的技能。一个善于委派、能权衡相互冲突的报告、知道何时该等待的 lead，可以从同一批 workers 身上得到更多产出。

我们的团队之所以能运转，很大程度上取决于 lead：它选择委派什么，以及它如何对待带回来的报告。随着模型越来越擅长带领团队，组织团队的最佳方式大概也会改变。

脚注

- 当团队规模是动态的时候，一个 lead 每个任务最多启动 5 个不同的 workers，超过这个数它就必须唤醒自己已经用过的。把上限提到 20 改变了 lead 的委派方式，但没有改变团队做得好不好。lead 启动了更多新 workers 而不是唤醒旧的，委派总数每个任务最多变化 0.9 次，reward 的变化在 −1.6 到 +1.6 分之间。
- ProgramBench 的作者按完全解决的任务占比给模型排名，把通过至少 95% 测试的任务（“almost resolved”）作为次级参考。如今完全解决的任务很少，所以为了衡量团队设计如何改变表现，我们使用更细粒度的通过测试占比。
- 效率指的是每 $100 额外成本、相对 solo PIV agent 换来的 reward。在 asynchronous leads 下，规划每 $100 换来 3.4 分，次优阶段（实现）是 1.7 分。在 blocking leads 下，差距更小（3.8 对 2.4，即 1.6 倍）。
- 提问很少，占 worker 发给 lead 消息的 6%。略少于半数的提问是关于某个 worker 负责的部分该如何与其余部分衔接，比如另一个模块期望哪些函数名或参数类型。略多于三分之一的提问是在问：某个 worker 的构建覆盖了参考程序之后，参考程序去了哪里；剩下的多数是在问参考程序的确切行为。Sol leads 回答了这些提问的 74%。
- 我们也在 30 任务子集上试过 Claude Opus 5，但在 8 个试验任务全部撞上 8 小时超时之后就停下了。那些任务每个大约花掉 $500，约为 Opus 4.8 团队每个任务开销的 15 倍。
- Opus 4.7 是唯一一个 solo agent 用 PIV prompt 明显比用 minimal prompt 更差的模型（46.8% 对 50.9%）。如果用同一 prompt 的 solo agent 来衡量，它的 PIV 团队本可涨 5.5 到 6.4 分。而相对它最好的 solo agent——图 10 用的就是这个基准——只涨了 1.4 到 2.3 分。
