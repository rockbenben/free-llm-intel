# Agent 蔓延：如何在企业里管理 agent 的激增

![](https://cdn.sanity.io/images/rjtqmwfu/web3-prod/1094f3e6b1cb6e160811e3553dd4baed23dca498-3840x2160.png?auto=format&fit=max&q=80&w=1130)

[企业级 AI agent 平台](https://cohere.com/blog/introducing-north-2)的发展，让员工构建并部署 agent 来支持自己的工作变得容易得多。

但随着 agent 创建变得更加去中心化，企业面临一个新的管理问题：如何跟踪整个组织已经构建了哪些 agent。缺少这种可见性，团队可能难以找到并复用现有的 agent，而对企业数据和系统的访问也会变得更难治理。当 agent 的这种激增变得难以管理时，它就成了 agent 蔓延。

在本文里，我们会解释为什么激增本身并非坏事，考察企业通常如何管理 agent 蔓延，并考虑一条让变体 agent 相互竞争的替代路子。

## 为什么 agent 激增未必是坏事

制造出 agent 蔓延可能性的同一批工具，也让实验变得容易得多。员工不必每次发现一个能从 agent 受益的任务时，都只能依赖一个中心化的 AI 或工程团队。相反，他们可以自行[构建并测试 agent](https://cohere.com/blog/building-ai-agents)，针对他们想要增强的那份工作的具体情形来定制。

这种去中心化的实验是有价值的。第一，离一条工作流最近的人，往往最有条件判断它能如何被 agent 精简。第二，当有用的 agent 可以被共享和复用时，最初为一个团队开发的方案也能被其他面对类似问题的团队采纳。因此在组织层面，激增可以说明员工正在积极检验新想法，并为 agent 发现有用的应用。

这就引出一个问题：agent 数目不断增长是否总会带来更多开销。毕竟，更多 agent 并不必然意味着更高的推理成本——一个没被使用的 agent 不会仅仅因为它存在就消耗 token。管理负担是在管理 agent 的流程跟不上其不断增长的数目时才出现的。*到那时*，agent 激增更贴切的说法才是 agent 蔓延。

> 激增可以说明员工正在积极检验新想法，并为 agent 发现有用的应用。

## 企业目前如何管理 agent 蔓延

如今的企业通常用下列做法之一来管理不断扩大的 agent 资产群：

- **集中交付**：一个中心化的 AI 或工程团队为组织的其余部分构建并治理 agent。这能提供更紧的控制，但也可能限制创新的节奏。
- **联邦式交付**：业务单元或各个团队自己负责 agent 的开发与运行，而职能中枢提供共享的基础设施、标准和[治理模式](https://cohere.com/blog/ai-governance-challenges)。
- **混合交付**：中枢团队与业务团队在共同的标准和治理模式下，分担构建与运行 agent 的责任。

在这些运营模式中，企业正越来越多地使用 agent 注册表来维护一份对其 agent 资产群的共享视图。注册表帮助组织跟踪 agent 的归属、使用情况和访问权限，同时帮助员工发现已经存在的 agent。这种安排强化了一种普遍取向：避免重复。团队应当默认先复用现有方案，而不是先构建新东西。

当然，限制不必要的重复有充分理由。这是减少蔓延的显而易见之法：员工要筛的重叠选项更少，企业要监控和治理的 agent 也更少。

但把重复一律视为该避免的东西，也可能压制创新。如果仅仅因为已经有一个能用的 agent 存在就不该再构建替代方案，组织就失去了发现更便宜、更可靠或更契合任务的解法的机会。

> 把重复一律视为该避免的东西，会压制创新。

## 一条替代路子：让 agent 变体相互竞争

企业怎样才能为有用的重复留出空间，同时不让它演变成 agent 蔓延？

一种做法是把重复当作临时状态而非永久安排。如果一个团队有可信的理由相信自己能改进某个「在位」agent，就应允许它构建一个「挑战者」变体。不过，挑战者能否继续使用，应当取决于它是否展现出相对在位者的实质性优势。

这种竞争模式需要在在位者与挑战者之间做一次有明确时限、基于证据的比较。具体指标取决于用例，但可以包括可靠性、token 用量、延迟等衡量维度，以及任务表现。

一旦收集到足够证据可以做出有意义的比较，组织就能决定是让挑战者取代在位者，还是把它下线。如果挑战者被证明更适合在位者所承担工作的某一部分，两个 agent 都可以作为不同的备选保留下来。

举个例子，设想一家银行的商业贷款部门，其中一个中枢团队构建了一个[金融 agent](https://cohere.com/blog/ai-agents-for-financial-services)，为客户经理起草信用备忘录。一支处理常规年审的贷款团队相信自己能做得更好，于是构建了一个面向同一范围任务的挑战者，使用一个更小、更便宜的模型，并增加一个把财务数字与支撑文件交叉核对的步骤。

在 30 天里，两个 agent 为一组有代表性的案例起草备忘录，从常规年审到更复杂的融资案例。银行用四项指标来比较它们：有多少数字能正确追溯到其源文件、信贷官员对每份草稿的修改力度、每份备忘录的 token 成本，以及产出首份草稿的耗时。

如果挑战者在不同类型的工作上交付的质量相当而成本明显更低，它就取代在位者。如果它表现不足又没带来任何实质优势，它就被下线。而如果它在常规年审上胜出、却在复杂的新融资上吃力，两个 agent 都留下——各自承担它处理得最好的那部分工作。

因此，要让这条路子行得通，就必须容忍一定程度的重复，但仅限于这种重复能带来有益竞争的时候。一旦测试显示某个竞争 agent 相对另一个没有优势，两者同时留下就再无理由。

## 最后的想法

避免 agent 蔓延并不需要把重复彻底消除。

如果企业想要比较相互竞争的方案，一定程度的重复——或者说变体——是必要的。

关键在于把变体与选择压力配对。让 agent 的创建变得容易、但让它能否留存变成有条件的，企业就能保住持续实验带来的好处，而不滑向蔓延。
