# 在 AWS 上使用 Cohere AI 构建金融研究助理

![](https://cdn.sanity.io/images/rjtqmwfu/web3-prod/a9f5cf4c07f32484927a5f451a4763453a1cd062-3840x2160.png?auto=format&fit=max&q=80&w=1130)

要点

- **在 AWS 上构建金融研究助理。** 将 Cohere Embed、Rerank 和 Parse 与 Amazon SageMaker AI、OpenSearch Serverless 和 Amazon Bedrock 相结合，以搜索财务文件并通过页面级引用生成答案。
- **优化检索质量、延迟和成本。** 使用 Embed Pro 实现高质量文档索引，使用 Embed Fast 实现低延迟查询，并通过可配置的嵌入维度和量化来平衡准确性和存储。
- **通过 Rerank 提高搜索相关性。** 使用 Rerank Pro 对检索到的页面重新排序，并使用上下文焦点来识别相关段落并减少发送到答案模型的文本量。
- **处理复杂的财务文档。** 使用 Cohere Parse 处理扫描或表格较多的页面，并结合文本和页面图像以帮助答案模型解释财务数据并保留上下文。
- **在您自己的 AWS 账户中部署和实验。** 使用基于 CloudFormation 的演示来探索检索、重新排名、上下文焦点和引用支持的答案，同时了解不同配置的权衡。

作为一名金融分析师，一天中的大部分时间都归结为在长达数百页的文件中找到一个数字，然后证明它的来源。两者都不像听起来那么容易。该数字很少出现在正文中。它通常位于表格、脚注或图表中，并且可以以不同的名称显示在不同的位置。

在这篇文章中，我们展示了如何使用 Amazon SageMaker AI 上的 Cohere 模型构建财务申报研究助理 - 用于搜索的嵌入、用于对结果排序的重新排序以及用于将硬页面转换为干净文本的解析。 Amazon Bedrock 上的 Anthropic Claude 将用于撰写答案，并为每项主张提供引用。

我们将从使这项工作变得困难的原因开始，然后概述解决方案，然后将本文的大部分内容花在其背后的设计决策以及何时您会做出不同的决定。最后，我们展示了如何在您自己的 AWS 账户中部署该解决方案并亲自尝试。

### **为什么金融研究很难自动化**

金融研究看起来像一个搜索问题，但它具有打破简单方法的特征。

**答案就在布局中。** 以 10-K 为例，这是美国上市公司向美国证券交易委员会提交的年度报告，涵盖业务、风险及其经审计的财务报表（[10-K 表格包含的内容](https://www.investor.gov/introduction-investing/investing-basics/glossary/form-10-k)）。您需要的数据通常以表格形式呈现，形式为按年份划分的净利息收入、按层级划分的监管资本、按贷款类型划分的冲销等。当 PDF 转换为纯文本时，表格会失去行和列的关系，多列页面可能会以错误的顺序出现，而且图表通常会消失。

**
无法验证的答案是没有用的。** 如果不知道“CET1 比率为 11.9%”来自哪个文件、哪个页面，也不知道该数字来自表格、图表还是句子，分析师就无法在备忘录中写下“CET1 比率为 11.9%”。这项工作的助手必须展示其来源，而阅读者必须能够快速检查它们。

**
数量和成本加起来。** 研究团队可能会索引多年来的数千份文件。每个页面都嵌入一次，但每个问题也都嵌入，并且针对每个问题运行的每个模型都会增加时间和成本。

**
并非每份文档都是干净的。** 文件以数字 PDF 形式到达，但也以扫描的证物、传真协议和根本没有文本层的拍照页面形式到达。

**
问题并不总是以文档的语言提出。**覆盖多个市场的团队经常用一种语言询问用另一种语言编写的文档。

因此，一个有用的助手必须做一些事情，例如当答案在表格中时找到正确的页面，使每个答案都可检查，控制成本和延迟，处理不干净的页面以及跨语言工作。

### **
解决方案概述
**

解决方案是由一名研究助理回答有关一系列申请的问题，并显示每项索赔的来源页面。它使用四种模型，每种模型都有一项工作：

- **Cohere Embed** 将每个页面和每个问题转换为一个向量，该向量是捕获其含义的数字列表，以便与问题相关的页面靠近它。 [嵌入分为两层](https://cohere.com/blog/embed-5)：**Embed Pro**，专为最高检索质量和离线索引而构建，**Embed Fast**，专为实时请求路径上的低延迟而构建。
- [Cohere Rerank](https://cohere.com/blog/rerank-5) 从向量搜索中获取问题和最佳候选页面，将每一对一起读取，并将它们按更好的顺序排列。通过 **Context Focus**，Rerank 还可以标记每个页面上回答问题的段落。与 Embed 一样，Rerank 也分为两层：**Rerank Pro**，专为实现最高准确度而构建；**Rerank Fast**，专为降低延迟而构建。我们使用 **Rerank Pro**，因为对于财务助理来说，找到正确的页面通常比更快的答案更重要。
- **Cohere Parse** 读取页面图像并返回干净的 Markdown，其中表格作为真实的行和列。它用于文本较弱的页面。
- **Amazon Bedrock 上的人类Claude** 阅读首页并写出答案，并引用每一页。

人们可以通过具有三个功能的网络应用程序来使用它：

- **助理。** 询问有关备案的问题。助手找到最相关的页面，阅读它们，然后写下答案，其中每个主张都引用其页面。每条引文还说明事实是否来自表格、图表、正文、脚注或图形，只需单击一下即可打开页面图像进行检查。
- **搜索。** 相同的搜索，没有生成的答案。它可以并排显示使用和不使用重新排序的结果，以便您可以看到重新排序如何更改它们，并且“重新排序”列显示在每个页面上选择的上下文焦点段落。
- **解析。**解析从您可以下载的页面中将表格提取为行，并将扫描的页面转换为文本。

在引擎盖下有两个流程。 **摄取** 每页运行一次，首先运行 Parse，对于需要它的页面，然后使用 Embed Pro 嵌入文本，并将向量存储到向量索引中。 **回答** 对每个问题运行，其中 Embed Fast 嵌入问题，然后检索最接近的页面，并且可以选择通过 Rerank 重新排序。最后，Claude从首页写下了答案。 Cohere 模型作为 Amazon SageMaker AI 上的实时端点运行，从 AWS Marketplace 部署；矢量索引是 Amazon OpenSearch Serverless； Web 应用程序、登录、API 和摄取管道都是无服务器 AWS 服务。

**使用 Embed Pro 建立索引，使用 Embed Fast 查询

**索引和查询有不同的需求。页面提前嵌入一次，因此您可以负担得起最准确的模型。当有人等待时，问题会被嵌入，每天数千次，因此每次调用的速度和成本最为重要。 Embed Pro 和 Embed Fast 共享[一个嵌入空间](https://cohere.com/blog/embed-5)，这意味着使用 Fast 嵌入的问题可以直接与使用 Pro 嵌入的页面进行比较。您可以在索引中获得 Pro 的质量，并在每个问题上获得 Fast 的速度，而无需重建索引。下图显示了每个模型的位置。

![](https://cdn.sanity.io/images/rjtqmwfu/web3-prod/77ae250249c8dbe6fae885147c751f5a630366a7-4520x2400.png?auto=format&fit=max&q=80&w=800)

第二个选择是每个向量的大小。 Embed 提供[六种输出大小，从 256 到 2,048 维，采用浮点数、int8 或二进制](https://cohere.com/blog/embed-5)。嵌入是俄罗斯套娃表示，其中模型经过训练，以便第一个维度承载最多的含义，因此较短的向量保留了较长向量所说的大部分内容。我们选择 **1,024 个维度存储为 int8**，每个维度一个字节：

- **存储 **- 1,024 维 int8 向量需要 1 KB 的原始存储空间，而 2,048 维 float32 向量则需要 8 KB - 减少了 8 倍。对于一百万页，这相当于大约 1 GB 与 8 GB 的原始矢量数据。实际的向量索引存储和成本还取决于索引结构、元数据和基础设施开销。
- **质量 **- 1,024 是范围的中间值，int8 比二进制保留更多细节。当答案必须是正确的页面而不仅仅是相似的页面时，这是一个明智的默认设置。
- **何时更改 **- 如果检索质量比存储更重要，请使用 2,048 维。对于成本占主导地位的非常大的档案，使用 512、256 或二进制向量；二进制比 float32 小 32 倍。

无论您选择什么，查询端都必须使用与索引相同的大小和格式。稍后更改它意味着再次嵌入每个页面，因此值得尽早解决。

**嵌入页面文本，并保留答案的图像

**嵌入可以将页面文本、页面图像或两者一起嵌入为一个向量，全部嵌入同一空间中。每种选择都适合不同类型的文档。

**页面文本**是最便宜和最简单的：每页一个向量，重新排序读取文本，因此它可以在同一页面上工作，并且您可以在每个结果旁边显示文本片段。问题是，它的好坏取决于提取的文本，其中大多数时间表可能会失去其结构，图表会消失，并且扫描根本没有文本，直到有人读取它。

**页面图像**不需要提取文本。表格、图表和布局与页面的外观一样，适用于扫描件和照片。每页的成本更高，更难显示页面匹配的原因，并且重新排名仍然需要文本。

**两者一起**（融合的文本和图像向量）为搜索提供了页面的两个视图，但代价是图像价格和更大的嵌入调用。

年度报告和 10-K 是具有良好文本的数字文档，因此我们嵌入了页面文本。文本丢失的内容（主要是图表和复杂的表格），我们在回答时通过让Claude看到页面图像来恢复。如果您的页面主要是扫描件、幻灯片、图表或图表，例如投资者演示、扫描协议或传真展品，请嵌入图像或两者兼而有之。

**每种语言都有一个嵌入空间

**[Embed 支持 100 多种语言和 128K 令牌上下文窗口](https://cohere.com/blog/embed-5)。无论语言如何，问题和页面都位于同一空间，因此诸如“impact de l'immobilier Commercial sur leegment Global Banking de Bank of America”之类的法语问题可以直接找到英语的 Bank of America 页面。然后Claude用问题的语言写下答案，并保持引文不变。

我们选择这样做，而不是首先将问题翻译成英语。无需构建、运行或付费的翻译步骤，也不存在术语翻译错误导致搜索结果错误的风险。 Rerank Pro 也是[多语言的，支持 100 多种语言](https://docs.cohere.com/docs/rerank)。与往常一样，请在您自己的文档中检查对您重要的语言。

**将Rerank设为可选阶段，并使其效果可见

**矢量搜索速度很快，因为每个页面都通过一个数字（两个矢量之间的距离）与问题进行比较。重新排序器的工作方式不同，它将问题和每个候选页面一起读取，这使得它能够权衡单个向量无法容纳的细节。 Rerank Pro [同时读取多达 32K 的问题和页面标记，适用于 100 多种语言，并处理半结构化内容，例如表格和 JSON](https://docs.cohere.com/docs/rerank)。在此设计中，矢量搜索返回 30 个候选者，然后 Rerank 选择 5 个属于 Claude 的候选者。

重新排序位于查询路径上，因此每个问题都会感受到它的延迟。我们仍然选择 Rerank Pro 而不是 Rerank Fast，因为在金融研究中，错误的页面比较慢的答案成本更高。如果交互速度对您的用户更重要，则 Rerank Fast 会接受相同的请求并返回相同类型的结果，因此它们之间的切换是配置更改，而不是代码更改。

额外的阅读会花费时间来解决每个问题和要运行的端点，其帮助程度取决于您的文档和问题。因此，我们将重新排序设置为一个可以打开或关闭的阶段，并使其效果可见：助手显示每个步骤花费的时间，搜索可以并排显示两个结果列表，并用箭头指示每个页面的移动方式。

你应该什么时候打开它？查看没有它的正确页面的着陆位置。如果它通常位于或接近顶部，请关闭重新排名并保持快速答案。如果它经常出现在列表中的较低位置，或者问题又长又具体，则重新排名是通常的解决方法。

Rerank 5 还为每个页面返回一个 [0 到 1 之间的校准相关性分数](https://docs.cohere.com/docs/rerank)，因此从一个问题到下一个问题，相同的截止值意味着相同的事情。您可以使用它来告诉用户没有页面可以很好匹配，或者触发另一个搜索，而不是从弱页面进行回答。

**只解析需要的页面

**解析读取页面图像并返回[Markdown 或内容块，带有边界框，并理解表格、表单、图表和图像](https://aws.amazon.com/marketplace/pp/prodview-25vdn5x53zqgo)。它是一个按小时付费的 GPU 端点，干净的数字页面已经有可用的文本，因此我们有选择地使用它。摄取步骤中的路由器逐页决定：

- 文本很少的页面将被解析（封面或没有文本层的扫描）
- 大部分文本位于表格内的页面将被解析
- 所有其他页面保留其现有文本。

解析输出被保存，因此每个页面都会被解析一次，无论您重建索引的频率如何。如果您需要表格作为电子表格或数据库的数据，Parse 也是将它们从页面中取出的方法。

**让答案模型阅读该页面，并说出每个事实的来源

**搜索在页面文本上运行，但答案不一定如此。对于它选择的五个页面中的每一页，查询函数都会向Claude发送页面图像和页面文本，要么是完整提取的文本，要么只是重新排序标记的段落（参见下一节），并告诉Claude信任两者不一致的图像。这就是让答案来自图表或文本失去结构的表格的原因。

Claude还被告知只能从这些页面中回答，当这些页面不包含答案时要清楚地说出，并以[文档页面 | ] 的形式引用每一个声明。 kind]，其中 kind 是表格、图表、文本、脚注或图形。该应用程序将每个引文转换为页面图像的编号链接，显示其旁边的类型，并在页面上重复它（“答案取自：表格”）。分析师可以看到助理引用了哪个页面和类型的内容来支持大写数字，并打开原始页面直接验证信息。

代价是额外的输入令牌和Claude的处理时间。在文本旁边包含五个页面图像会增加令牌消耗和响应延迟，具体取决于图像分辨率、页面内容和所使用的模型。该演示有一个可以省略图像的开关，这样您就可以看到自己问题的差异。

**仅向Claude发送重要的段落

**即使有正确的五页，每一页的大部分内容都不是关于问题的。一张 10-K 页可以容纳整个表格、一页风险因素或几个不相关的注释，Claude会阅读所有这些内容，并且您需要付费。

Rerank 5 的功能不仅仅是排序页面。打开上下文焦点后，它还会返回每个页面上与问题匹配的段落，作为具有相关性分数的字符范围。这是重新排名请求上的设置，而不是单独的模型，并且不会更改排名。在此设计中，查询功能要求对选定的五个页面上的段落进行重新排序，并按页面顺序仅向 Claude 发送这些段落，而不是整页文本。

这有三个作用：

- **更少的输入标记。** Claude 仅读取每个页面文本的相关部分，因此答案成本更低，返回速度更快。
- **更清晰的提示。** 随着不相关的文本消失，答案模型的注意力就减少了。
- **更容易检查。** 该应用程序会突出显示页面文本中的段落，因此读者可以准确地看到答案的依据，而不仅仅是哪个页面。

权衡是上下文。段落本身可能会丢失其周围的内容，例如表格的列标题或列引用的年份。上下文焦点对于可以识别和检索特定信息的有针对性的问题最有效。结构化内容（例如表格和表单）可能更具挑战性，因为重要的关系可能跨越多个部分，因此将其拆分为有意义的块。对于更广泛的任务，例如总结整个页面，提供完整页面内容通常会产生更完整和准确的结果。然而，Cohere 的内部评估表明，即使将输入标记减少 50-75%，Context Focus 仍保留了绝大多数答案准确性，这表明标记减少和准确性之间的权衡远不是线性的。

这就是页面图像占据一席之地的地方，Claude仍然可以看到整个页面，因此它可以读取标题和单元格省略的段落。如果最低的令牌数最重要，请发送不带图像的段落；如果数字必须准确，请发送带有图像的段落。 Context Focus 将相关段落作为同一 Rerank 请求的一部分返回，无需单独的模型或额外的 API 调用。

该演示对每个选项都有一个开关：上下文焦点和页面图像。每个答案都会显示有多少代币发送给了Claude，并突出显示了发送的段落，因此您可以看到自己问题的权衡。

**使昂贵的部件易于关闭

**Cohere 模型作为实时 SageMaker 端点运行，实时端点按其存在的每小时计费，无论是否有人提出问题。对于飞行员或突发工作的团队来说，闲置的 GPU 时间是最大的成本。因此，部署有一项设置，可以删除所有模型端点，同时保留数据、索引和 Web 应用程序。稍后重新打开模型不需要新的摄取。在稳定的生产使用中，您可以添加自动缩放和警报。

### **演示范围**

该演示是一个工作起点，而不是生产系统。它基于 [ViDoRe V3 基准](https://huggingface.co/datasets/vidore/vidore_v3_finance_en) ([论文](https://arxiv.org/abs/2601.08620)) 的财务子集的三份公开年度报告（美国银行、摩根士丹利和富国银行，2024 财年；928 页），该报告还提供英语、法语、西班牙语、德语、意大利语和葡萄牙语。

为了使演示保持较小且快速尝试，我们做出了一些与上述设计不同的选择：

- **预提取的文档文本：** 使用基准数据集提供的文本对页面进行索引，从而简化部署。虽然该架构支持扫描和复杂文档的 Cohere Parse，但该演示不包括解析任意上传的 PDF。
- **Embed Pro 用于索引和查询：** 该演示使用 Embed Pro 进行文档索引和查询嵌入，无需单独的 Embed Fast 端点并降低 GPU 成本。
- **Rerank Fast 而不是 Rerank Pro：** Rerank Fast 在较小的 GPU 实例上运行，避免了 Rerank Pro 的更高 GPU 要求和潜在的容量限制。两者都使用相同的请求和响应格式，因此切换到 Rerank Pro 只需要更改模板配置。
- **可配置的检索和答案生成：** 默认情况下，助手中启用重新排名，并带有用于重新排名、上下文焦点和页面图像的开关。默认情况下，搜索运行时不进行重新排名，但允许并排比较以评估对相关性、延迟和令牌使用的影响。
- **最少 GPU 基础设施：** 该演示在“us-east-1”中为每个部署的模型使用一个“ml.g5.xlarge”实例，并为该区域配置了 AWS Marketplace 模型包。
- **简化的安全性和访问：** 该演示包括一名用户、一个具有受数据访问策略保护的公共网络访问的 OpenSearch 集合，并且没有 Bedrock Guardrails。这些设置最大限度地降低了部署复杂性，并且用于评估，而不是生产。
- **固定文档数据集：** 该演示加载一组预定义的财务归档页面，而不是支持摄取用户上传的 PDF。

在生产环境中部署之前需要考虑的事项：

- **网络：** 使用 VPC 终端节点和 OpenSearch Serverless 的私有访问。
- **身份：**使用您的身份提供商，每个用户或每个团队都可以访问文档。
- **加密：**数据存储桶使用客户管理的 AWS KMS 密钥；其他商店使用 AWS 托管或 AWS 拥有的密钥。
- **操作：**添加监控、警报、端点自动缩放和预算警报。
- **查询模型：**为问题添加快速嵌入。
- **Reranker：** 使用 Rerank Pro。

### **关键要点**

培养一名金融研究助理需要的不仅仅是寻找相关文件。这意味着检索正确的信息，保留表格和图形的上下文，并使答案易于验证。通过将 Cohere Embed、Rerank 和 Parse 与 AWS 服务相结合，该架构为构建处理复杂财务文档的研究助理提供了一个起点。

关键的设计考虑因素是：

- **从检索质量开始。** 根据您的文档选择嵌入策略，并在优化答案生成之前验证检索性能。
- **将管道与您的文档相匹配。** 使用文本嵌入来处理干净的文档，使用解析来处理复杂的布局和扫描页面，并在视觉信息很重要时使用图像嵌入。
- **平衡质量、延迟和成本。** 使用 Embed Pro 进行索引，使用 Embed Fast 进行查询，并在它们提供价值的地方添加 Rerank 和 Parse。
- **只发送模型需要的内容。** Rerank 的上下文焦点选择回答问题的段落，页面图像保留它们周围的上下文。
- **使答案可验证。** 提供页面级引用和原始文档的访问权限，以便分析师可以检查支持证据。
