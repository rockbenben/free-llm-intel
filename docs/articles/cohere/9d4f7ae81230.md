# 推出 Embed 5——新一代前沿 embedding 模型家族

我们迄今最强的 embedding 模型，现提供 Pro 和 Fast 两档。

核心要点

- **先进水平的企业检索：**Embed 5 Pro 在我们测试的所有模型中取得最高平均分，尤其在金融数据集、解析后的 PDF 和视觉丰富文档上。
- **新的 Fast 档：**Embed 5 Fast 为延迟和成本敏感的工作负载带来强劲检索质量，价格为每百万 token 0.08 美元。
- **一个索引，两个模型：**Pro 和 Fast 共享同一 embedding 空间，团队可以用 Pro 建索引、用任一模型查询，无需重新索引。
- **为复杂企业数据而生：**Embed 5 支持多模态输入与检索、100+ 种语言，以及用于长文档的 128K token 上下文窗口。
- **规模化下更高效：**Matryoshka 表示和低精度输出降低向量存储与搜索成本，量化权重则降低私有部署的服务需求。

今天，我们发布 Embed 5——一个站在高质量企业检索前沿的全新 embedding 模型家族。

Embed 5 在复杂企业数据上带来更强检索，同时给团队更多对延迟、成本和部署的控制。**Embed 5 Pro** 面向多模态、多语言、金融、代码和解析文档检索的最大质量而优化。**Embed 5 Fast** 为延迟与成本敏感的工作负载提供极具竞争力的性能。两个档位共享单一 embedding 空间，团队可以用 Pro 建索引、用任一模型查询，而无需重建索引。

Embed 5 为搜索、RAG 和 agentic 工作流奠定检索基础：在噪声到达昂贵的生成模型之前浮现更多相关上下文并将其过滤。用 Embed 提升答案质量和用户体验，同时帮助把下游推理成本控制在合理范围。

Embed 5 今天起正式可用，支持 [Cohere API 与 Model Vault](http://dashboard.cohere.com)、[Microsoft Foundry](https://ai.azure.com/catalog/models/Cohere-Embed-V5-Pro) 和 [Amazon SageMaker](https://aws.amazon.com/marketplace/pp/prodview-pobc74bcuaohi)。定价为 Pro 每百万 token 0.12 美元，Fast 每百万 token 0.08 美元。

## 性能

Embed 5 Pro 带来我们迄今最强的检索表现。它在 ViDoRe V3、金融文档、解析 PDF、图像检索以及关键商业语言上，取得我们所测模型中的最高平均分。

Embed 5 也是首个用 **RCP-nDCG@10**——我们最新的检索评测方法——评估的模型家族。它不只对照有限的固定标签集打分，而是按查询相关的具体相关性标准评估检回文档，捕捉相关结果并给出在你自己语料上表现的更完整视图。1 [阅读更多关于 RCP-nDCG@10](http://www.cohere.com/blog/rcp-ndcg)。

### 企业文档

Embed 5 在意义藏于表格、图表、示意图和版式（而非仅有文本）的视觉丰富文档上表现出色。在 [ViDoRe V3](https://huggingface.co/blog/QuentinJG/introducing-vidore-v3) 上——该基准的文档采样自关键企业领域，包括财报、技术手册、监管材料、政府报告、教科书和讲义——Embed 5 Pro 平均 85.8 分，相比 Embed 4 提升惊人的 8.8 分。2

这使它领先 Voyage 4 Large（83.7）、Gemini Embedding 2（83.2）和 OpenAI text-embedding-3-large（75.5）。Pro 在八个领域中独领先五个，在能源领域与 Voyage 4 Large 打平；相比 Embed 4 最大的增益在 HR（+11.4）和工业（+10.3）。Embed 5 Fast 平均 84.5，同样领先 Gemini Embedding 2 和 Voyage 4 Large。完整结果见[这里](https://docs.google.com/spreadsheets/d/1HLj1KOjJdFh9bTAc6lbWxG7VfjkRMeE7V11Q0eojtAA/edit?gid=0#gid=0)。

八个视觉丰富文档领域的检索质量（RCP-nDCG@10）。评测使用解析后的文本输出，由 ViDoRe 的作者们策划。

### 金融

Embed 5 Pro 确立了自己在金融文档检索领域领先 embedding 模型的地位。

Pro 在三个主流公开金融基准上排名第一；Fast 尽管比同类小得多，在每个基准上均排名第二：[FinanceBench](https://arxiv.org/abs/2311.11944)（Pro 80.1，Fast 80.0）、[FinQA](https://arxiv.org/abs/2109.00122)（90.0、88.8）和 ViDoRe V3 Finance（85.0、83.9）。

综合来看，Pro 比紧随其后的非 Cohere 竞争者 Gemini Embedding 2 平均高 3.3 分。与 OpenAI text-embedding-3-large 相比，在 FinanceBench 上领先扩大到 21.4 分。

### 多模态

**解析后的 PDF**

多数企业搜索流水线仍先把 PDF 转成文本再做 embedding，但该过程会剥离结构。表格丢失行列关系，多栏版式可能打乱阅读顺序，重复的页眉引入噪声，图表则常常完全消失。这让解析文档检索比干净文本基准所暗示的更难。

我们的解析文档套件涵盖服务文档、企业报告、SEC 文件、产品手册和隐私政策。Embed 5 Pro 在整个套件上取得最高平均 84.8，领先 Voyage 4 Large 的 83.6、Embed 5 Fast 的 83.4、Gemini Embedding 2 的 80.8 和 Embed 4 的 78.6。下图突出展示了一组熟悉的公开基准子集，Embed 5 Pro 在 FinanceBench 和 CoFiF 所代表的金融文档上尤其强劲。

代表性公开基准上的解析文档检索（RCP-nDCG@10）。文档使用 Gemini 1.5 Flash 解析。"Full suite average" 包含图中未展示的额外数据集。

**页面图像与 text-image 融合文档**

有些文档用视觉呈现更好。扫描页、幻灯片、示意图和图表包含文本抽取可能遗漏的信息。Embed 5 可以直接嵌入页面图像（page-image），也可以把图像与其元数据合成单个向量（fused text-image）。

在 text-image 融合语料上，Embed 5 Pro 在五个数据集上平均 82.3，领先 Embed 5 Fast 的 81.2 和 Gemini Embedding 2 的 61.3。Pro 在套件的每个数据集上都胜过 Gemini Embedding 2。Page image 检索同样稳健：Embed 5 Pro 在金融数据集上持续领先，五个数据集平均 77.0，领先 Embed 5 Fast（73.2）、Embed 4（71.1）、Voyage Multimodal 3.5（70.1）和 Gemini Embedding 2（56.7）。

文本查询下的多模态文档检索（nDCG@10）。Fused text-image 检索把页面图像与文档元数据合成单个 embedding。RepairBench 报告多个多语言查询子集的平均值。High Finance 是 Cohere 内部标注的一组问题，要求模型检索相关的投行与对冲基金演示材料。

文本查询下的多模态文档检索（nDCG@10）。Image-only 检索仅使用页面图像回答问题。AR = 阿拉伯语；JA = 日语；KO = 韩语。

## 认识 Embed 5 Fast

Embed 5 Fast 是一个更轻量的模型，为延迟敏感、大流量的检索而建。它的价格比 Pro 低三分之一，同时保留相同的 128K token 上下文、多模态输入、多语言覆盖和多种压缩输出格式。

这在查询路径上最要紧——每次搜索都要支付 embedding 延迟，而在每个任务可能发起数十次搜索的 agentic 工作流中还会成倍放大。Fast 更小的占用也降低私有部署的服务成本，并加速大批量摄取和重建索引任务。

就以更接近索引效率的文档吞吐量而言——Fast 始终更高效，在不同上下文尺寸下平均吞吐量比 Pro 高 2.4 倍。

约 200-token 和约 1K-token 上下文长度下 Fast 与 Pro 的平均文档吞吐量，以每秒处理文档数衡量。越高越好。

### 性能

Fast 抬高了紧凑型 embedding 模型的门槛。在 ViDoRe V3 上，它领先 Voyage 4 Nano 近 7 分，领先 Jina Embeddings v5 Text Small、Perplexity 和微软的 Harrier 0.6B 十分以上。它胜过 Qwen3-VL-Embedding-2B 约 20 分，尽管自身规模只有后者的一半左右。如上所见，它的平均分在 ViDoRe V3 和金融检索上还超过 Gemini Embedding 2 和 Voyage 4 Large。在解析 PDF 上它超过 Gemini Embedding 2（83.4 对 80.8），略低于 Voyage 4 Large（83.6）。

### 两个模型，一个 embedding 空间

Pro 和 Fast 共享单一 embedding 空间，因此任一模型的向量可以直接比较。我们在覆盖文本、图像、融合和解析文档检索的 40 个开发数据集上测试了所有语料/查询组合。

共享空间让团队可以独立选择每一档：文档可以用 Pro 索引以获得最大质量，查询则用 Fast 获得更低延迟和成本——无需重建索引。跨模型组合的表现仍接近同模型基线（Fast 和 Pro 查询的平均损失仅为 1.6% 和 2.7%），没有任何数据集出现严重失败。

对多数客户，我们推荐如下部署模式：**用 Pro 索引，用 Fast 查询。**它保留了全 Pro 系统大部分的质量增益，同时在请求时保持 Fast 的延迟与成本优势。3

## 向量存储

在企业规模下，向量索引的运营成本可能高于生成它的模型。Embed 5 支持 Matryoshka representation learning 和低精度输出，让团队可以压缩向量尺寸，精细控制质量、存储与搜索成本之间的权衡。这些节省可能非常可观：一个 2,048 维 float32 向量需要 8 KB；一个 1,024 维 int8 向量只用 1 KB；一个 256 维 binary 向量仅 32 字节——缩小 256 倍。在 1 亿个 chunk 上，原始向量存储从约 819 GB 降到 3.2 GB。

重要的是，int8 在 Embed 5 Pro 和 Fast 上都保留了接近全精度的检索质量。对多数部署，我们推荐 1,024 维 int8 向量作为性能-效率的最佳平衡点。binary 占用最小，需牺牲一些精度，适合在高精度重排之前做快速的第一遍检索。

不同向量维度与精度下检索质量（RCP-nDCG@10）与存储成本的关系。存储成本以 2048 维 FP32 向量为基准相对给出。越靠左越高效。检索在 ViDoRe V3（八个数据集）上评测。

## 开始使用

通过 Cohere API、Model Vault、Microsoft Foundry（[Pro](https://ai.azure.com/catalog/models/Cohere-Embed-V5-Pro)、[Fast](https://ai.azure.com/catalog/models/Cohere-Embed-V5-Fast)）和 Amazon SageMaker（[Pro](https://aws.amazon.com/marketplace/pp/prodview-pobc74bcuaohi)、[Fast](https://aws.amazon.com/marketplace/pp/prodview-qffayhd7sgkja)）部署 Embed 5 Pro 和 Embed 5 Fast，或直接在 [North](http://cohere.com/north) 内使用 Embed 5。对于在你自己 VPC 或本地的私有部署，两个模型均可用 vLLM 服务。[批量 embedding 已可用](https://docs.cohere.com/docs/embed-jobs-api)，适合大规模摄取。

**用你已在使用的工具构建。**Embed 5 能融入现有检索栈，与多种框架和向量数据库集成，包括 LangChain、Haystack、Weaviate、Qdrant、Pinecone、Elasticsearch、MongoDB、Redis、Milvus 和 OpenSearch。[阅读文档](https://docs.cohere.com/docs/integrations)。

先[创建 API key](http://dashboard.cohere.com)，然后用下面的代码片段快速发出你的第一次查询。

```
import os, cohere, numpy as np

co = cohere.ClientV2(api_key=os.environ["CO_API_KEY"])

documents = [
    "Net interest margin narrowed 12 bps to 2.61% as deposit costs rose.",
    "Torque the mounting bolts to 45 Nm in a star pattern before refitting the cover.",
    "Employees accrue 1.5 days of paid leave for each month of service.",
]

doc_embeddings = co.embed(
    model="embed-v5.0-pro",
    input_type="search_document",
    texts=documents,
    output_dimension=1024,
    embedding_types=["float"],
).embeddings.float_

query_embedding = co.embed(
    model="embed-v5.0-pro",
    input_type="search_query",
    texts=["What happened to net interest margin last quarter?"],
    output_dimension=1024,
    embedding_types=["float"],
).embeddings.float_[0]

docs = np.array(doc_embeddings)
query = np.array(query_embedding)

scores = docs @ query / (
    np.linalg.norm(docs, axis=1) * np.linalg.norm(query)
)

print(documents[int(np.argmax(scores))])
```
