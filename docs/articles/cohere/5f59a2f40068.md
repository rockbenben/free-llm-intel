# 硬件感知的动态投机解码

投机解码（SD）是一种在不损失任何质量的前提下加速大语言模型（LLM）推理的流行技术。LLM 推理一次生成一个 token。SD 改为使用更小的*草稿（draft）*模型提议多个 token，然后由更大的*目标（target）*模型在单个时间步内验证。由于每步可以接受多于一个 token，生成因此提速。

SD 通过利用 GPU 的 **compute** 与 **memory bandwidth** 之间的权衡来实现加速。把多个请求批处理能提高 GPU 利用率，但工作区间取决于批大小（BS）：

- 在 **小 BS** 下，推理受**内存带宽约束（memory bandwidth-bound）**：把 LLM 权重从 HBM 载入 SRAM 的开销占主导。
- 在 **大 BS** 下，推理变为**计算约束（compute-bound）**：LLM 权重与大量请求 token 的矩阵乘法占主导。

SD 中花费的时间有两个主要组成部分：

***Time in SD = Time to draft tokens (small draft model) + Time to verify draft tokens (large target model)***

草稿模型的运行成本低得多。如果草稿产出 K 个 token，目标模型必须处理 BS × (K+1) 个 token，这使得验证成为瓶颈，因为在给定 BS 下它要做 K+1 倍的计算。在现代 GPU 上，计算单元的速度通常比内存带宽快约两个数量级，所以在内存带宽约束的小 BS 推理期间，计算单元大体闲置。SD 利用这一空隙：在验证阶段让 K+1 倍的 token 流过目标模型，用上本来会被浪费的算力。

## 投机解码的挑战

### 生产环境中的动态批处理

随着批大小增长，普通 LLM 推理越来越变为计算约束，不再留下可供 SD 利用的闲置算力。在这个区间，SD 反而可能比普通推理*更慢*。这限制了 SD 在生产系统中的使用——生产环境的 BS 很少很小，而且是动态变化的。

### 强化学习（RL）

RL 在**训练**阶段（更新模型权重）和 **rollout** 阶段（生成数据和奖励信号用于训练）之间交替。rollout 阶段是主要瓶颈，可能消耗多达 [85% 的资源](https://microsoft.ai/pdf/mai-thinking-1.pdf)。由于扩展 RL 是提升模型智能的重要途径，加速 RL rollout 推理是一个需要解决的重要问题。

然而，使用推理模型做 RL 会产生长尾分布：批中的单个请求可能持续生成很长时间，拖住整批的其他请求、浪费资源。SD 本可以帮助这些长尾生成，但因为它在高 BS 下损害吞吐，其在完整部署中的总体效用受到限制。

这些挑战共同指向同一个需求：一个更好的 SD 系统应当**基于硬件约束控制最优 K**，从而在完整生产系统和大规模 RL rollout 中都保持有用。

### 动态投机解码

这就是**硬件感知的动态 SD（DSD）**的用武之地。DSD 通过让草稿 token 数量自适应来改进标准 SD。SD 中 K 是固定的；DSD 中，最优 K 根据模型与硬件的交互来选择。推理受内存带宽约束时 DSD 增大 K，受计算约束时减小 K。

对**稠密（dense）**模型，这通常意味着低 BS 时 K 更高、高 BS 时 K 更低，最优 K 随 BS 增长单调递减。对 **MoE（Mixture-of-Experts）**模型，最优 K 随 BS *非单调*变化：

- 在**低 BS**，最优 K 起点较低，因为验证需要加载额外的 experts。
- 在**中 BS**，最优 K 上升，因为几乎所有 experts 已被加载，验证几乎不再增加额外的 expert 加载。
- 在**高 BS**，最优 K 再次下降，与稠密模型一致，因为计算已进入计算约束区间。

想更深入地理解这些机制，见我们此前关于 SD 与 MoE 交互的[博客文章](https://cohere.com/blog/mixture-of-experts-models-get-more-from-speculative-decoding)。

那么，如何找到最优的草稿 token 数量？我们需要理解从 K 到 K+1 个草稿 token 的边际贡献。处理一个草稿 token 的*计算*成本与其位置无关——第一个和最后一个草稿 token 成本相同。但它对**接受长度（Acceptance Length，AL）**的贡献则高度依赖位置：它[指数衰减](https://proceedings.mlr.press/v202/leviathan23a/leviathan23a.pdf)，因此靠前的 token 被接受的概率远高于靠后的。所以我们需要一个指标，来刻画"多加一个草稿 token"时的这一权衡。

现有的 DSD 工作（如 [TurboSpec](https://arxiv.org/pdf/2406.14066)）用 **goodput** 作这个指标。我们也用 goodput，但把它简化为：

***goodput = AL / ITL***

AL 是接受长度，ITL 是 token 间隔延迟（大体等于 draft 与 verify 时间之和）。这捕捉了 K 个草稿 token 对 AL 的边际贡献与墙上时钟成本之间的权衡，数值越高意味着加速越好。这个简洁的公式让 DSD 易于适配未来的模型架构；而且由于 ITL 已经封装了所有操作的联合影响，无需对每个组件单独 profiling 再重新组合。我们运行离线 profiling 测量 AL 和 ITL、找到最优 K，并将其存为运行时使用的查找表。这张离线表解决了冷启动问题，并且可扩展：它可以纳入来自引擎运行时指标的实时 AL 与 ITL 统计，让 DSD 适应不断变化的工作负载。

### 结果

我们在 MT-Bench 数据集上比较三种配置：**vanilla**（不使用投机解码）、**fixed-K SD**（我们的 SD 基线，用固定 K=3 的 EAGLE draft head 实现）和 **DSD**（动态 K）。样本数上采样到 20 * BS，意味着使用了 20 个 BS 波次。

我们对 **Command A**（Dense）和 **Command A+**（MoE）分别 profile 了 DSD 选出的最优 K。实证结果验证了上文描述的趋势：稠密模型的最优 K 随 BS 增加单调递减，MoE 模型则不然——Command A+ 在中 BS 可以达到更高的最优 K。

我们还以 **TOPS/user**（每用户每秒输出 token 数）为基准测评。对 **Command A（Dense）**，DSD 的收益在整个 BS 区间都很明确：

- 在**低 BS**，DSD 与 SD（K=3）的加速持平。
- 在**高 BS（64/128）**，DSD 比 SD 和 vanilla 模型都快。
- 在**极高 BS（256）**，DSD 与 vanilla TOPS 持平——尽管 SD 在 BS 128 和 256 出现倒退。

具体而言，DSD 在 BS 128 和 BS 256 上均**比 SD 快约 23%**。它在 BS 128 上**比 vanilla 快 7.5%**，在 BS 256 上**快 1.82%**，而 SD 在这一区间相对 vanilla 出现倒退。换句话说，DSD 在 SD 有用武之地时拿到 SD 的加速，而在固定 K 的 SD 会帮倒忙的地方优雅地回退到接近 vanilla 的性能。

对 **Command A+（MoE）**，SD 和 DSD 带来相近的加速。原因是 DSD 在 BS 区间的绝大部分选择 K=3——与 fixed-K SD 一致——只有在 BS 16 到 32 之间选择 K=5。这个更高的 K 没有转化为额外加速，最可能的原因是 EAGLE head 按单时间步训练却要在 K > 1 个时间步上复用，接受度不足以带来增益。我们预期较新的方法，如 [EAGLE-3](https://arxiv.org/abs/2503.01840) 或 [DFlash](https://arxiv.org/abs/2602.06036)，会在此场景显示更清晰的收益。

### 我们对 vLLM 的贡献

今年早些时候，我们把这一优化贡献给了 vLLM（[pull request](https://github.com/vllm-project/vllm/pull/32374)；用法见 [vLLM 文档](https://docs.vllm.ai/en/latest/features/speculative_decoding/dynamic_speculative_decoding/)）。DSD 的想法并不新鲜，朴素的实现也简单，真正的挑战是在 vLLM 这样高度优化的推理框架内部采纳它。vLLM 带有许多优化——如**异步调度（async scheduling）**和**完整 CUDA Graph（full CUDA Graph）**——DSD 必须与它们全部兼容，才能榨干 vLLM 的效率。下面讨论最重要的两项。

### 与异步调度的兼容

推理框架先**调度**请求（CPU 工作），然后运行**模型推理**（GPU 工作）。历史上 GPU 是瓶颈，但随着生产级 GPU 越来越快，CPU 调度开销相对变大——GPU 提前完成，等待下一批被调度。为解决这一点，vLLM 引入了[**异步调度**](https://vllm.ai/blog/2026-03-24-mrv2)：把时间步 **T+1** 的调度器工作（在 CPU 上）与时间步 **T** 的 model runner（在 GPU 上）重叠，从而隐藏调度延迟。这把调度器在 CPU 上的开销降到最低。

关键在于，T+1 的调度器运行时*没有*来自 T 的 model runner 输出——后者仍在并行执行。这可行是因为调度器完全在 CPU 上基于计数和占位符提前一步工作；实际 token 值留在 GPU 上，由 model runner 晚一步通过 GPU 侧 scatter 消费。只有轻量计数（占位符和 token 数）异步跨越进程边界。

调度器告诉 model runner 要生成多少个草稿 token，以及要验证上一时间步产生的多少草稿 token。DSD 打破了"每个时间步生成和验证相同数量草稿 token"的假设，这改变了调度器和 model runner 双方的记账逻辑。

### 与完整 CUDA Graph 的兼容

模型前向传播要启动许多 CUDA kernel，每次 kernel 启动都有 CPU 开销。随着现代生产级 GPU 越来越快，这些跨大量 kernel 累积的每次启动开销，占总推理时间的比例变得可观。**完整 CUDA Graph（FCG）**通过在 warmup 期间捕获全部 kernel 启动、以单次 graph launch 取代多次单独启动来消除这一开销。

vLLM 为 decode 请求提供 [FCG 支持](https://docs.vllm.ai/en/latest/design/cuda_graphs/#full-cuda-graph-capturing-warm-up)，方式是捕获 <batch 中 token 数, 固定 K> 的组合。DSD 把它扩展为捕获 <batch 中 token 数, 不同最优 K>，记录更多组合，使运行时改变 K 仍能命中已捕获的 CUDA Graph（[pull request](https://github.com/vllm-project/vllm/pull/45953)）。

下图展示 max K=3 的示例。在该 batch 含 8 个 token 的例子中，标准 SD 只捕获 <8 tokens, K=3>，而 DSD 捕获所有使 token 数能被 K+1 整除的有效 K——即 <8 tokens, K=1> 和 <8 tokens, K=3>。能被 K+1 整除意味着 batch 中每个请求都是 decode 请求，这正是 vLLM 中路由到 FCG 的条件。
