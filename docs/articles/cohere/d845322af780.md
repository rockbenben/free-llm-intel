# 用 AI Agent 自动化 Fork 维护

你维护着一个 fork。上游在演进。你同步、遇到问题、修复、验证、发布。几周后上游又动了。循环往复。

本文介绍一种用 AI 编码 agent 自动化这一循环的通用方法。我们把它应用到自己的 vLLM fork 上，并走一遍真实案例：一次例行的上游发布悄然弄坏了 Cohere 的 [cohere-transcribe-03-2026](https://huggingface.co/CohereLabs/cohere-transcribe-03-2026) ASR 模型在我们 fork 上的表现，而修复最终以 vLLM PR 的形式回流上游。

实际执行中，这种方式把消化一次新上游发布的时间从**数周压缩到数天**，人类只需审核最终结果。支撑这套工作流的 skills 已在 [cohere-ai/vllm-skills](https://github.com/cohere-ai/vllm-skills) 开源。

## 问题所在

长期维护一个活跃开发项目的 fork 是一项反复出现的成本。但上游发布也带来了你需要的功能、性能改进和 bug 修复。保持同步不只是维护，而是 fork 持续变好的方式。问题在于，每次上游发布都会引入一次**扰动**：合并冲突、API 变更、函数移除、新增依赖或失败的测试。fork 维护者的工作就是吸收这种扰动，恢复可用状态。

这类工作的结构始终不变：

- **同步（Sync）**：把新的上游版本并入 fork。
- **度量（Measure）**：跑测试、基准、评测，看看坏了什么。
- **修复（Fix）**：解决冲突、适配 API 变更、更新测试。
- **重复（Repeat）**：反复执行第 2 到第 3 步，直到全部通过。
- **发布（Ship）**：交付更新后的 fork。

这是一个反馈回路。每个维护 fork 的团队其实都已经有了它，只是它又慢又手动。对我们的 vLLM fork 来说，消化一次典型的上游发布过去要花数周的间歇性开发投入；下述工作的目标是把它降到数天，且大部分是无人在场的 agent 时间。

## 反馈系统

在控制论中，[闭环系统](https://en.wikipedia.org/wiki/Closed-loop_controller)会不断将自己的输出与参考值比较并调整以消除差距。但真实系统还会面对**扰动**：把系统推离期望状态的外部输入。

- **r(t)** 是参考值（reference），即系统应当产出的期望值。
- **y(t)** 是输出（output），即系统实际产出的值。
- **e(t)** 是误差（error），即参考值与测量值之间的差距，计算为 r(t) − measured_output。
- **d(t)** 是扰动（disturbance），作用于系统、把输出推离参考值的外部力量。

控制器利用误差来调节系统；反馈让输出靠近目标。设计良好的反馈回路不仅跟踪参考值，还能**抑制扰动**：检测扰动对输出的影响，在无人工干预的情况下把误差拉回零。

定速巡航是教科书级的例子。你设定期望速度（参考值），车辆保持该速度（系统），但突然出现上坡或逆风（扰动）。一个好的控制器会察觉速度下降并自动调整油门。

Fork 维护的结构完全相同。

控制论

Fork 维护

r(t)，参考值

自定义改动在最新上游上正确工作

d(t)，扰动

新的上游发布：冲突、API 变更、破坏性变更

控制器

解决冲突、更新补丁、修复测试

系统

fork 本身（代码、测试、CI）

y(t)，输出

同步后 fork 的运行时行为

测量

测试套件、基准、评测

e(t)，误差

期望行为与同步后实际行为之间的差异

目标是把整个回路——**同步、度量、修复、重复**——自动化，从而以最少的人工干预吸收上游的改进。

## Agent 出现之前的流程

让 fork 与上游同步有几种方式：**merge**、**cherry-pick** 和 **rebase** 最常见。Merge 保留双方历史，但会产生盘根错节的提交图，难以区分自定义改动和上游改动。Cherry-pick 控制精确，但当上游每个版本移动数百个提交时无法扩展；最终你要维护一份不断漂移的挑选清单。Rebase 把你的自定义提交重放到新的上游 tag 之上，产生干净的线性历史，你的补丁清晰地叠在最上面。代价是 rebase 会重写历史并强制 force-push，但对于一个在快速演进的上游上只有少量自定义提交的 fork，这份清爽是值得的。

在 Cohere，我们很早就确定使用 rebase。在下文基于 agent 的工作流之前，我们的流水线已经混合了脚本化自动化和手动工作。

- **Rebase：**一个 GitHub Actions 工作流尝试 rebase 到目标上游 tag，并从共享的 `git rerere` 缓存重放此前遇到过的冲突解决方案。
- **解决冲突：**当工作流的自动 rebase 失败时，由开发人员在本地接手，手动解决剩余冲突（通常有 LLM 助手协助），验证 CI，并上传更新后的 rerere 缓存。
- **验证并发布：**rebase 后的分支 CI 全绿后，即成为 fork 的新基线。

这个流程已经结合了几种自动化：`git rerere` 重放已知解决方案，GitHub Actions 执行 rebase 尝试和 CI，LLM 协助单个编码和调试任务。但人类仍然是控制器的一部分，要把各个环节缝合起来、决定采用哪些修复、决定何时重跑。反馈回路是能用的，只是转得慢。下文的基于 agent 的工作流保持同样的结构，但让 agent 扮演控制器角色，于是迭代以机器速度进行，人类只在边缘介入。

## 逐个组件地自动化

该方法把回路拆解成三个可由 agent 自动化的组件，每个组件对应控制图中的一块。

### 1. 扰动注入

一个 agent skill 负责检测并应用新的上游发布。它把 fork rebase 到新 tag 上并自动解决合并冲突。这就是进入系统的扰动：一次有意为之的自动化动作，我们知道它会短暂弄坏一些东西，但希望尽快吸收。

该 skill 需要：

- 检测 fork 当前基于哪个上游 tag
- 检查是否存在更新的 tag
- 带着 fork 的自定义提交执行 `git rebase --onto`
- 解决冲突（借助上游 diff 上下文做出有依据的决定）

### 2. 度量采集

rebase 之后，fork 处于未知状态。度量告诉你要离目标还有多远：一个所有自定义行为完好的可用 fork。没有它，agent 就是盲飞。

度量本身（测试、基准、评测）由项目定义，在任何自动化之前就存在。agent 自动化的是**采集**它们：一个测试运行器 skill 知道如何搭建环境、执行验证套件并汇报结果。

- **Tests**：单元、集成与正确性测试
- **Benchmarks**：性能检查（吞吐、延迟、资源占用）
- **Evals**：领域质量指标（准确率、perplexity、任务得分）

输出就是误差信号：哪些测试失败、哪些基准退化、哪些评测劣化。度量越丰富可靠，控制器收敛越快。测试套件单薄的 fork 提供不了多少信号，agent 会不知道什么坏了、离完成有多远。

### 3. 控制器

一个 agent skill 把回路闭合。rebase 落地、度量结果回来后，该 skill：

- 读取测试与基准结果
- 识别失败和退化
- 应用修复（解决构建错误、更新失效测试、适配 API 变更）
- 重新运行度量
- 重复直到全部度量通过，否则上报人类

这就是把误差驱动到零的控制器。关键洞见在于，agent 不需要第一次就把 rebase 做对，它只需要迭代——正如一个开发者会做的那样。

## 案例研究：vLLM

[vLLM](https://github.com/vllm-project/vllm) 是一个开源 LLM 推理引擎。在 Cohere，我们把它用在推理栈的各个环节：从模型开发期的 RL rollout 和评测，到生产环境中服务用户请求。我们维护一个 fork 来承载自定义提交——额外的模型支持、自定义 kernel 与优化、修改过的入口点、额外的测试——其中一些正在往上游合入，另一些则专属于我们的需求。挑战在于把这些提交重放到每次新的上游发布上而不破坏任何东西。上游大约每隔几周切一个发布，每个都分量不小：两个 tag 之间的 diff 常常涉及数百个文件。

### 一次 rebase 如何运行

本节中：**v1** / **v2** 指新旧上游 tag，**b1** / **b2** 指 rebase 前后的 fork 分支。

一次典型调用：*"`/auto-rebase sync` the current branch with the latest upstream release and make sure `<test>` passes."*

- **auto-rebase** 检查前置条件（`gh auth status`），然后调用 **detect-upstream-base** 找到 v1（例如 `v0.19.0`）。
- 它拉取上游 tag 并发现 v2（`v0.19.1`）。它把发布内容呈现给用户，等待确认。
- 它从用户处收集验证项（例如 `pytest tests/entrypoints/openai/correctness/test_transcription_api_correctness.py`）。
- 它调用 **rebase-assistant**，其执行：分析 b1 上的自定义提交（`git log v1..HEAD`）；先用 **local-test-runner**（配 v1 wheel）验证测试在 b1 上通过——这是确保已知良好基线的关卡；备份 b1、创建 b2，可选地把自定义提交 squash；执行 `git rebase --onto upstream/v0.19.1 <fork-point> HEAD`；通过对比 `upstream/v1..upstream/v2` 的 diff 来理解变化并解决冲突；在 b2 上用 **local-test-runner**（配 v2 wheel）跑测试；若测试失败：检查失败项、与 v1 基线对比、应用修复并重跑（内层反馈回路）
- 全部检查通过后，**auto-rebase** 呈现总结（重放的提交、解决的冲突、测试结果），并询问是否推送。

作为一系列 skill 交互的顺序：

内层回路是控制器在 b2 上迭代：local-test-runner 报告失败，rebase-assistant 应用修复并重跑，直到测试通过。

### 完整示例：Cohere Transcribe 在 v0.19.1 上

下面是这个回路一次真实的端到端调用。

**准备：**我们的 fork 停在 [cohere-transcribe-v0.19.0](https://github.com/dongluw/vllm/tree/cohere-transcribe-v0.19.0)，在上游 `v0.19.0` 之上有唯一一个自定义提交，用于启用 Cohere [cohere-transcribe-03-2026](https://huggingface.co/CohereLabs/cohere-transcribe-03-2026) ASR 模型的正确性测试。vLLM 在 `v0.19.0` 加入了对这一模型架构的支持，但由于权重尚未发布，上游把测试注释掉了。我们的自定义提交只是取消其中一行的注释。

```
        # TODO (ekagra): turn on after asr release
        # CohereASR is used to test the variable encoder length code paths
        ("CohereLabs/cohere-transcribe-03-2026", 11.92),
```

该测试在 earnings-22 验证集的一个过滤切片上运行模型，并断言 WER ≤ 11.92。这一个数字就是我们的度量信号 `y(t)`。fork 健康时，这个数字稳定在 11.92 附近；一旦坏了，它会爆掉。

**扰动：**上游切出 `v0.19.1`。这是一次增量发布，但并不小：包含 `transformers` 版本升级和相关重构。我们用一条 prompt 运行 auto-rebase。

```
/auto-rebase let's sync current branch with latest upstream release,
make sure the test CohereLabs/cohere-transcribe-03-2026 passes
@tests/entrypoints/openai/correctness/test_transcription_api_correctness.py:172-173
```

**结果：**

- 把自定义提交 rebase 到 `v0.19.1` 并在 b2 重跑测试后，结果是 **WER = 100**——彻底失败，模型输出全是乱码。
- 控制器回路定位了这次退化：rebase-assistant 对 `upstream/v0.19.0..upstream/v0.19.1` 做了 diff，把失败追溯到一次 `transformers` 版本升级改变了模型 tokenizer 处理 prompt prefix 的方式，并应用了一个快速规避修复。在单次交互式会话内，WER 回到约 11.92，fork 在 `v0.19.1` 上恢复全绿。

回路端到端跑通了：扰动到来，控制器吸收了它，fork 自动回到健康状态。

**后续：**由于这个 bug 影响该模型的所有下游用户，我们提交了 [vllm-project/vllm#40582](https://github.com/vllm-project/vllm/pull/40582)，把临时规避变成正式的上游修复。一旦合入，下一个发布就不再需要为该模型打 fork 补丁；对所有人来说扰动消失了。

## 超越 vLLM

同样的闭环结构适用于任何需要吸收外部变更并收敛回可用状态的代码库。

另一个最近的例子是我们内部维护的 HuggingFace transformers fork，我们在公开发布之前先行维护 [command-a-plus-05-2026](https://huggingface.co/CohereLabs/command-a-plus-05-2026-bf16)。当 [transformers v5](https://huggingface.co/blog/transformers-v5) 落地，带来废弃参数移除、新的必填签名和 tokenizer 行为变化——所有这些就是扰动。同样的回路照常运转：升级到 v5，运行模型的正确性评测与生成测试，让 agent 在失败上迭代。各种问题在导入路径、API 调用、tokenizer 默认值上浮现；一些被自主修复，另一些需要人类介入解决。这个循环持续进行，直到模型在公开发布前于 v5 上正确生成。

skills 不同，但结构完全一致：引入变更、度量差距、闭合回路。

## 结语

Fork 维护的结构不变：同步、度量、修复、重复。变化的是回路转动的速度。

在基于 agent 的工作流之前，把我们的 vLLM fork 同步到一个新上游发布要花**数周**：等待有人切换上下文来处理，手动分诊冲突，重跑 CI，逐个调试失败。有了 auto-rebase 驱动控制器回路，时间线压缩到了**数天**。而且因为预期度量已预先配置在仓库里，整条流水线无需人工输入即可运行；人只需要审阅结果。

该方法可以推广到任何对"可用"有可度量定义的 fork：检测扰动、采集度量，让 agent 在误差上迭代。skills 是可组合的，控制论的表达方式也让它们易于适配到新的代码库。

本文描述的 skills 已在 [cohere-ai/vllm-skills](https://github.com/cohere-ai/vllm-skills) 开源。如果你维护着一个 fork 并想试试这套方法，第一步是写一个度量（一个测试、一个基准、一个评测）来刻画你的 fork 何谓"健康"。回路的其余部分由此展开。
