# North Mini Code 的 Megakernel 服务引擎内幕

一次技术深潜：Cohere 的 megakernel 方案如何在 H100 上实现 1.58 倍更快的 LLM 服务。

今天，Cohere 发布一个围绕 decode megakernel 构建的 [North Mini Code](https://cohere.com/north-mini-code) 服务引擎：单卡 H100 上的 BF16，端到端比 vLLM 快 1.25× - 1.41×。服务引擎的代码见 [GitHub](https://github.com/cohere-ai/cohere-megakernel)。

多数 LLM 服务栈仍把每次前向传播视作一串 kernel：启动 QKV，等待；启动 attention，等待；启动 MoE，等待。每次启动本身都没问题，问题在中间的等待。在小批大小下，GPU 在每个 decode 步中相当大一部分时间花在等待而非计算上。

自回归 decode——尤其在低批大小下——本质上是内存约束（memory-bound）的。每个 decode 步要从 HBM 搬运很大一部分内存，而相对做的计算很少。因此正确的提问方式是"我们能多有效地利用内存带宽"，而不是 flop。以 North Mini Code 为例：这是一个 30B 模型，每个 token 激活 3.3B 参数，BF16 下意味着每个 decode 步要流式加载 6.6 GB 权重，8K 上下文时外加约 0.5 GB 的 KV cache。H100 通过 HBM 提供 3.35 TB/s 的带宽，Speed-of-Light（SoL）约在 470 tok/s。vLLM 服务该模型的速度是 185 tok/s，仅为 SoL 的 39%。

Megakernel 近来备受关注，被视为弥合这一差距的方式：不是一百个小 kernel，而是把整个前向传播作为一个持久化 kernel 来运行。从 [Hazy Research 的 "Look Ma, No Bubbles!"](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles) 这项开创性工作（下文会回顾其设计）出发，大量后续工作相继发布，取得了不同程度的加速。已有工作主要沿两个方向：自动生成 megakernel 的编译器，以及只测 batch size 1 下 decode 速度的独立演示。

我们更进一步。本文呈现的，是我们认为首个完全围绕 decode megakernel 构建的成熟服务系统。它支持真实服务器所需的一切：continuous batching、paged attention、不等长序列，全部藏在一个支持 tool calling 的 OpenAI 兼容端点后面。把 OpenCode 指向它，你就能用它写代码。

在 batch size 1 下，我们的 megakernel 达到 292 tok/s，即 SoL 的 62%——比 vLLM 快 1.58×。这一优势在各批大小下保持，并延伸到 256K 上下文，且准确率无可测损失。

图 1：batch size 1 下各种上下文长度的 decode 吞吐。Megakernel 始终优于 vLLM。

我们还发现，megakernel 比其名声所暗示的要好写得多，因此我们附上一份把你已有的 kernel 移植进来的配方。我们的实现是一个单独的 CUDA 文件：没有编译器，没有新的编程范式，没有奇异的抽象——只是普通的分块 GEMM 和普通的 paged attention，重排成符合单一调用约定的样子。

## **什么是 Megakernel？**

一块 GPU 大致是 100–150 个独立处理器，称为 SM（streaming multiprocessor），它们都运行同一个程序——一个 *kernel*——处理不同的数据。megakernel 是单个持久化 kernel，运行整个前向传播：我们为每个 SM 恰好启动一个 threadblock，它在整个 decode 步中保持驻留。各 block 不再从驱动接收工作，而是读取一份*任务列表*——一组它应执行的小工作单元，由主机侧准备好放在全局内存中。数据依赖不再由 kernel 边界编码，而是表达为全局内存中的显式计数器：任务完成时递增自己那个，需要输入时自旋等待别人的。

结果是：调度单位从"整个操作"缩小到"某个操作的一个 tile"，同步单位从"整块 GPU"缩小到"任务所依赖的那些特定生产者"。

图 2：一个 decode 步，从主机到设备。主机不再按操作各启动一个 kernel，而是把该步分解为任务——每个任务是一个操作的一个 tile——并在各 SM 之间轮询分发，使每个 SM 在全局内存中拥有自己的任务列表。大多数任务的顺序由主机侧调度器确定（见调度器一节）。Full attention 和 MoE 是例外：它们的任务数取决于实时序列长度与路由，因此放进任何 SM 都可拉取的共享工作队列。细节见后续小节。

## **加速从何而来**

推理引擎通常按操作各启动一个 kernel——RMSNorm、QKV、attention、MoE 等——大部分优化精力用于让每个 kernel 尽可能快。这对训练和 prefill 很有效，因为那里的负载是大的计算约束 GEMM，每个 kernel 都有足够工作让 SM 饱和。

Decode 是相反的区间：它受内存带宽和延迟约束。一个 decode 步主要是低算术强度的 GEMV，所以其速度取决于权重从 HBM 流入共享内存有多快。任何让权重停止流动的东西都是损失的时间，而"按操作分 kernel"的做法有好几处会让它们停下流动。这些停顿加起来，占了典型推理引擎闲置的那 61% 带宽的大头。

最简单的收益来自**更少的启动与同步开销**。两个相邻 kernel 之间，每个 SM 都必须先完成，任何 SM 才能开始下一个，而且驱动还要派发下一个 grid。对于每层由几十个小子 kernel 组成的 decode 步，这些空隙会不断累加。Megakernel 每个步只支付一次这一成本，而不是每个操作一次。我们再列三个对本模型更重要、按大致影响排序的收益：

### **1. 减少 wave quantization**

假设一个 kernel 有 200 个 tile 的工作要做，而 GPU 有 132 个 SM。前 132 个 tile 并行运行；剩下的 68 个在第二个 wave 里跑，同时 64 个 SM 闲置。这个 kernel 花了 2 个 wave 的时间干了 1.5 个 wave 的工作，而且 kernel 越小，这种取整带来的浪费越严重。这不是"把工作分得更均匀"就能解决的——GEMM tile 形状受矩阵维度和 kernel 设计约束，总 tile 数很少恰好落在 SM 数量的整数倍上。

图 3：Wave quantization 降低 GPU 利用率。

在 megakernel 里没有需要向上取整的边界：输入就绪的 tile 会在任何空闲 SM 上开始。North Mini Code 从这一点获得的收益比多数架构更大，因为它使用*并行 transformer 层*：attention 和 MoE 前馈由同一个归一化输入分别计算，直到层尾才通过融合的 residual add + RMSNorm 重新汇合，所以 attention 和 MoE 都不需要彼此的输出。

图 4：North Mini Code 使用的并行 transformer 层。

有了 megakernel，我们可以用就绪的工作"回填"空闲 SM。并行 transformer 层允许更激进的回填：只要可能，我们就*确定性地*把大概率已就绪的任务放到空闲 SM 上。放置的细节见任务调度器一节。下图中，我们对比了常规服务栈与 megakernel 调度同一个 MoE decode 层的情形。

图 5：同一个 MoE decode 层，同样的操作、同样的顺序，两种调度方式。上：按操作分 kernel。由于 wave quantization 和硬件抖动，各 attention 并非同时完成；kernel 边界上的屏障让每个 SM 都要等最慢的那个（斜线区域），每个 kernel 边界都重复这一模式。下：megakernel。每个 SM 完成自己的 attention 工作后就开始一个 MoE tile，同一段区间承载的是工作而不是等待。图中用 16 个 SM、每个操作几十个 tile 绘制以便看清任务；真实 kernel 有 132 个 SM、数千个任务。持续时间仅示意，时间轴为相对值。

### **2. 丢弃伪依赖**

即便工作负载完全相同，SM 也不会同时完成。Kernel 边界是全 grid 屏障，最慢的 SM 决定所有人的节奏。例如，attention 按 4 个 key/value 分组切分，其中一组提前完成后，那个 SM 只能等其余三组追上来——尽管它的下一个操作实际需要的数据早已在内存里。细粒度屏障去掉了这种伪依赖：某个 KV 组的 O-proj 只要在*该组*的 attention 输出落地即可开始。同样，MoE 的下投影任务只要对应 expert 的上投影任务完成就能开始，无需等所有 expert 的上投影。

### **3. 权重预取**

权重不可变——它们完全不依赖本步的激活值。因此一个任务可以在其激活依赖满足*之前*就开始把权重 tile 从 HBM 流入共享内存——这在 kernel 边界下是不允许的。我们把这一点用得最狠的地方是 router 和 QKV 投影：它们在前一层 O-proj 的尾部、RMSNorm 尚未运行时就预取权重，收割本来会被闲置的带宽。

## **我们的起点**

我们的设计大量借鉴了前文提到的 Hazy Research 开创性博客的洞见——那篇工作把 Llama-3.2-1B 的一次前向传播融合成单个 kernel，在 batch size 1 下达到了 H100 内存带宽的 78%，而 vLLM 和 SGLang 只有大约一半。他们的三个思想对我们至关重要：

- **GPU 上的"任务解释器"模式。**每个 SM 遍历一份由主机准备、跨前向传播复用的任务描述符列表。一个 controller warp 读取描述符，把任务派发给各种设备端函数，每个函数实现一种操作。我们在图 2 和图 6 中描述该思想的实现。
- **基于计数器的同步。**依赖屏障就是全局内存中的普通整数，每步前清零。任务完成时递增一个，开始前在另一个上自旋等待。实现细节见 Barriers 一节与图 7。
- **跨任务边界的重叠。**一个任务可以在同一 SM 上前一个任务还在写结果时，就开始加载自己的权重。

### **我们做得不同的地方**

我们的实现与他们的 megakernel 有若干不同。我们的 GEMM 实现重度依赖 tensor core 指令，即使在 batch size 1 也一样——我们发现 wgmma 在我们的场景下比 CUDA core 略快，且降低寄存器压力。

另一个不同是：我们不用共享内存分页来实现权重预取。我们最初尝试过 shared-memory paging，它允许内存在前一个任务释放缓冲区之前就开始加载。但实践中，簿记逻辑复杂、持续引入 bug，且开销高过收益。于是每个 opcode 改为在编译期静态获得自己的 warp-specialized 流水线及共享内存布局，我们从两个更便宜的地方获得重叠。

**同类型的相邻 GEMM 任务之间。**一个 MoE GEMM 任务遍历一串 tile，流水线让 stage 相位跨整个列表保持，而不是在每个 tile 边界清空再重灌流水线。在 MoE GEMM 内部，当前 tile 还在 tensor core 或 epilogue 上时，下一个 tile 的权重已经在途。因为是同一操作、同一共享内存布局，共享内存分页简化成了一个普通的多级流水线。这种预取与 persistent grouped GEMM kernel 精神相通。

**GEMM 流水线内部。**权重不可变，所以生产者 warp 在跨 SM 等待激活*之前*就发出权重 tile 的加载；在后文所示的伪代码（Listings 1）里，`prefetch_weight_tiles` 位于 `wait_input_bars` 之上。MoE 下投影就是这样一例：expert 权重在 up/gate 还在计算下投影将要消费的状态时就开始从 HBM 流入。因此一个被输入阻塞的任务仍在搬运字节。另一个例子是 QKV 和 router 在 RMS norm 完成前的预取。

我们在调度上也下了很大功夫。多数任务遵循主机构建、可精确调优的静态调度；attention 和 MoE 用本地工作窃取来平衡 continuous batching 与路由带来的运行时可变负载。下文详述。

### **所有操作共用一套 ABI**

整个 megakernel 可以看作由统一调用约定缝合起来的各种小 kernel——每个小 kernel 必须恰好以 3 个 warp group 实现（每个 warp group 含 4 个 warp），包含 8 个 consumer warp、1 个 controller warp、1 个 producer 和 1 个 storer warp，每个 warp 受各自的寄存器要求约束。此外，每个小 kernel 必须从一个固定大小的任务描述符读取其"参数"。我们认为这种约定类似于编译器与操作系统中的应用二进制接口（ABI），全文用 **"ABI"** 一词描述该约定。

以 GEMM 为例理解 ABI 如何工作。

图 6：一个 GEMM tile 如何变成 SM 上的工作。主机把输出切成 tile，每个写成一个 32 个 int32 的描述符。在设备上，controller warp 读取下一个描述符并按其 opcode 分发——QKV、attention、O-proj，或其他十四种之一——于是同一个 SM 可以连续运行不同操作。2×4 的网格仅为示意；真实的 batch 1 QKV 有 80 个 tile。

让这种东西保持"可以手写"的，正是每个操作（不只是 GEMM）都遵守那套 ABI：任务是什么、以什么形状运行、如何宣告完成。一旦所有操作遵循同一 ABI，把它们组装成 megakernel 就变得完全可控。本节余下部分逐一展开这三件事。

### **任务**

Megakernel 不发明新操作。它把常规的 decode 计算图——QKV、attention、O-proj、router、MoE、residual/RMSNorm、LM head——下降为一列小的分块*任务*。十六个 opcode 覆盖整个 decode 步：

**所有 GEMM opcode 共用一条流水线。**O-proj、router、稠密 FFN、LM head 和两种 MoE expert GEMM 运行同一个 warp-specialized 主体：生产者把权重与激活 tile 流入共享内存的 stage 环，消费者在 tensor core 上累加，storer 写出输出 tile 并在屏障上 arrive。各 opcode 之间变化的只是一小串操作细节——哪些张量、等哪个屏障、给哪个屏障发信号、epilogue 是否融合 SiLU-and-multiply、存储是否是 split-K 归约。QKV 就是同一条流水线，只是写回 HBM 前在寄存器内应用 RoPE。MoE drain 也是同一条流水线，只是取下一个 tile 的方式不同：它们从队列认领工作，而不是从描述符读坐标。

结果是，添加一个新的 GEMM 任务只是小改动而不是新 kernel。我们不重写 load/math/store 循环，只填上那些细节。

### **任务描述符**

每个任务描述符是 32 个 int32 字段，由主机编码器写入按 SM 划分的缓冲区。字段 0 是 opcode；其余为操作特定字段：哪一层、哪个输出 tile、哪个 split-K 切片、走多少个 K-tile，以及——最关键的部分——**等哪个屏障、等到什么计数、完成后给哪个屏障发信号**。

设备侧很直接。每个 block 有一个 warp 充当 *controller*：它把即将到来的描述符预取进一个小的共享内存环，使 SM 永远不会在等任务描述符上停顿。其余 warp 从那个环上弹出任务并执行。

其中大部分沿用独立 Hopper GEMM 的标准生产者/消费者 warp-specialization 模式。Megakernel 的贡献在于：每个 opcode——包括 attention 和 RMSNorm——都用同一形状，于是刚完成一个 QKV tile 的 SM 可以接着运行一个 attention 切片，而无需改变 warp 数量或各 warp 的角色。

角色是编译期标签而非运行时分支。每个操作主体按角色模板化，`if constexpr (role == PRODUCER)` 在编译期删除不可达代码。这让我们能像写普通 GEMM 那样在一个函数里写下 producer、consumer 和 storer，而每个 warp 只保留它实际执行的路径。

Controller 从不进入那个函数。它有自己独立的循环，唯一的职责是把下一个描述符预取进小的共享内存环、并在槽位就绪时通知 worker。一个小注意点：worker 之间不能用 `__syncthreads()` 同步——那会等待与 worker 独立运行的 controller warp——所以它们在一个排除 controller 的命名屏障（`worker_sync`）上互相会合。

下面是 megakernel 中一个 GEMM 任务的概览。如果你写过 warp-specialized 的 Hopper kernel，应该会觉得结构似曾相识。MoE drain 就是同一个任务，套在一个循环里、对从队列认领的 tile 反复调用。

```
def gemm_task(task):  # compute Y = X @ W
    if constexpr (role == producer):
        prefetch_weight_tiles(task)      # optional, before the wait
        wait_input_bars(task)            # cross-SM: my activations ready?
        for k in k_tiles(task):
            tma_load_A_B(k)              # async copy HBM -> shared memory
            signal_stage_ready(k)        # intra-block: stage k is loaded
    elif constexpr (role == consumer):
        for k in k_tiles(task):
            wait_stage_ready(k)
            wgmma(k)                     # tensor-core MMA
        epilogue_to_smem()
    elif constexpr (role == storer):
        tma_store_Y()                    # async copy shared memory -> HBM
        arrive_output_bar(task)          # cross-SM: my tile is visible
    worker_sync()                        # all worker warps; excluding controller

def moe_drain_task(task):
    while True:
        tile_id = atomicAdd(n_claimed_tiles, 1)
        if tile_id >= len(moe_workqueue)：
            break
        tile = moe_workqueue[tile_id]
        gemm_task(tile)

def controller_loop(tasks):
    for i in range(len(tasks)):
        slot = ring[i % RING]
        if i >= RING:
            wait(slot.done)              # workers finished with this slot
        slot.task = load(tasks[i])   # prefetch the next descriptor
        arrive(slot.ready)               # signal workers: you can start

def worker_loop():
    for i in range(len(tasks)):
        slot = ring[i % RING]
        wait(slot.ready)                 # descriptor is in shared memory
        gemm_task(slot.task)             # or switch(opcode) onto another body
        if storer:
            arrive(slot.done)            # slot is free for the next prefetch
```

Listings 1：演示如何在 megakernel 中实现一个 GEMM 任务。整体结构遵循 Hopper 上标准的 warp specialized GEMM。

`if constexpr` 分支就是上文的编译期标签，不是运行时 switch。两条独立 kernel 中不会出现的是 `wait_input_bars` 和 `arrive_output_bar`——描述符里携带的跨 SM 计数器。`prefetch_weight_tiles` 位于等待之上，是另一手 megakernel 专有的可选动作。

Controller 始终保持领先 worker 一个描述符，且从不加入它们的屏障。Attention、routing 和 MoE drain 填充同样的 producer / consumer / storer 槽位；变的只是 `worker_loop` 里的 `switch (opcode)`。把你已有的 kernel 放进 megakernel 的摩擦，就是那两个屏障调用加上这层包裹循环——而不是一套新的编程模型。

### **屏障（Barriers）**

受 Hazy Research 启发，我们的屏障实现为全局内存中的计数器。

```
// wait: spin until enough upstream tasks have arrived
while (*(volatile const uint32_t*)bar < target) {
    __nanosleep(20);
}
__threadfence();

// arrive: publish my tile, then signal downstream tasks
fence.proxy.async;     // make async (TMA) stores visible first
__threadfence();       // make data computed by this SM visible to others
atomicAdd(bar, 1);
```

Listings 2：我们把屏障实现为全局内存中的计数器。等待的线程自旋等待直到依赖被满足。

这就是全部的依赖机制。任务等待的是单个*计数*，而非某个特定上游任务，这使得依赖的通知和等待无论扇入扇出多大都是 O(1)。fence 至关重要，它确保 SM 之间没有静默导致数据损坏的数据竞争。

## 如何编写一个 megakernel？

Megakernel 听起来像彻底重写。实践中，ABI 把工作范围控制在很小：一旦某个操作遵循了公共 threadblock 形状和描述符格式，它就和其他任务一样插入 megakernel。性能关键的逻辑可以直接复用自现有 kernel。

我们给从现有 kernel 库出发的人的配方是：

- **从本身就具备独立竞争力的 GEMM 和 attention kernel 开始。**Megakernel 消除的是操作*之间*的胶水；它不会让一个慢操作变快。我们的实现单独对打即可持平 cuBLAS 和 FlashAttention-3，用的是普通 warp-specialized 流水线，没有 TMA multicast 也没有 ping-pong 调度。
- **让 kernel 适配 ABI。**恰好使用 8 个 consumer warp，最多 3 个 producer/storer warp。对标准 Hopper warp-specialized kernel，这主要意味着把 producer 和 consumer 代码拆成独立函数，让按 warpgroup 划分的寄存器限制生效。
- **加上表达其数据依赖的屏障。**一个 GEMM tile 或一个 KV 组成为一个任务。下游操作需要仔细等待相应屏障以确保数据完整性。
- **把任务描述符写入全局内存任务列表。**调优任务顺序与放置以获得最佳吞吐。

难的是第三步。计数屏障在 *N* 个线程 arrive 时就释放，并不检查来的是*哪些*线程，所以一个 arrive 次数不对的 opcode 可能让 warps 漂移到不同任务上，很久之后才死锁。屏障记账需要显式的不变量和谨慎的测试。

一套描述符格式、一种 block 形状、一个计数器协议，构成了全部的集成契约。这让添加新操作成为一个边界清晰的工程任务，而不是一个"新 kernel 架构"项目。

## **任务调度器：把任务映射到 SM**

实现 megakernel 本身之后，我们需要决定如何给每个 SM 分配任务、以及任务按什么顺序执行。这份分配称为*任务调度（task schedule）*。任务调度器接收任务图，输出每个 SM 顺序执行的确切任务列表。实际上，设计调度时我们有很大自由。细粒度屏障只通过"任务必须在其输入就绪后才开始"来保证 megakernel 的正确性。只要调度不会造成循环等待，任务可以随意重排。不同调度产出相同结果，但吞吐会有相当大的差异。

我们的调度基本是静态的，只对少数操作做动态工作窃取。

**静态部分：wave 顺序与放置。**主机为每层构建具名的 wave（`qkv`、`router`、`attn`、`moe_up_drain`、`oproj`、`rmsnorm`……），选定顺序，摊平成一个任务列表，然后把任务 *k* 发给 SM *k mod 132*。当前顺序把 router 和 route setup 排在 attention 之前：

```
qkv → router → top-k → route setup → MoE gather → attention → MoE up/down → O-proj → RMSNorm
```

这一顺序让 MoE 分支抢跑，使计算量不大的 routing 能与较重的 QKV GEMM 一起调度，更好利用 SM。超出这个简单图景，调度的效果很难隔离：改一个 wave 会改变其下游何时就绪、哪些任务共享一个 SM、以及 HBM 带宽如何在任务间分配。这些选择在整层范围内相互作用。

我们的实验表明调度很重要。我们跑了两个 8K 输入长度、uniform-routing 的消融，只改 wave 顺序。

**交错式（Interleaved）。**attention 开始后，MoE up/down 在 attention combine 之前运行。理由是让两个分支都随时有就绪工作，减少 SM 的等待时间：

```
qkv → router → top-k → route setup → MoE gather
→ attention → MoE up/down → attention combine → MoE combine → O-proj → RMSNorm
```

**Attention 优先（Attention first）。**在任何 MoE GEMM 之前启动 attention combine 和 O-proj，同时仍让 router 提前开始

```
qkv → router → top-k → route setup → MoE gather
  → attention → attention combine → O-proj → MoE up/down → MoE combine → RMSNorm
```

**动态部分：对可变规模工作做本地工作窃取。**Full attention 对每个在跑请求读取的 KV 长度差异极大，而 router 决定每个 MoE expert 收到多少 token。这些 tile 数量只在步进行中才知道。

这一分工是深思熟虑的。静态调度固定了大部分任务顺序与放置，给我们调优性能所需的控制——上面的 wave 顺序消融已经表明。本地工作窃取只处理主机无法预知的负载不均。静态任务列表预留固定数量的小*认领（claimer）*任务；一个 `ATTN_DRAIN` 或 `MOE_*_DRAIN` 认领者用原子操作从其 stage 的共享队列里窃取下一个条目并执行，直到队列排空。Attention 认领者窃取 attention tile，MoE 认领者窃取 MoE tile。认领者数量控制并行度，而当前 attention 队列反映批中的实时请求。这让静态调度保持稳定，又能在每次批变化时不必重建整个列表就平衡可变负载。

### **我们试过的其他调度器**

项目早期，在针对稠密模型时，我们构建过几个更复杂的调度器。一个是贪心的、拓扑感知的调度器，根据每个任务的内存读取量估计其成本。我们还试过暴力搜索：从数百个随机候选中挑出最佳调度。在那个负载上，两者都比纯轮询快约 10%。MoE 改变了问题：路由使其工作量与放置都是动态的，那些稠密模型调度器无法顺畅迁移。我们最终选择更简单的轮询加调优 wave 顺序，再配合上文所述的工作窃取。不过，如果简单轮询在 Blackwell GPU 上或 NVFP4、FP8 这类更低位宽的量化场景中不足以支撑 megakernel，我们计划重新审视那些更复杂的调度器。

### **Kernel 周围的服务引擎**

服务器有两个长期存在的主机侧线程。一个 Python 线程充当控制面：接受请求、运行 prefill、管理 KV 容量与批次。一个原生 C++ 线程为获得最大性能而独占 decode。两个线程交错运作：Python 暂停 C++ 以做 prefill 或变更活动批大小。

这种交接之所以存在，是因为 megakernel 运行的是提前构建的任务列表：tile 数量、屏障索引、某个 tile 属于哪个槽位，都已烘焙进去。因此 Python 在准入、退役或重塑批次之前先让 decode 停靠（park），随后 C++ 以匹配新批大小与上下文的调度恢复运行。下图展示了双方各自拥有的状态以及调度如何变化：

图 8：步开始时，C++ 循环清空 megakernel 将用到的所有 scratch 缓冲与屏障计数器。然后取最长在跑请求的上下文，为当前批大小选择一个预构建调度。该调度固定 GEMM tile 及其他静态工作；相邻的上下文桶（bucket）若静态任务描述符缓冲相同则复用同一调度。Full-attention 是例外：C++ 根据实时长度计算每请求的切片数并上传，GPU 在排空 attention 队列时读取它。

### **Python 与 C++ 轮流上场**

C++ 独占 continuous decode 循环：更新 KV 位置、清理单步状态、选择调度、启动 megakernel、采样并流式发出结果 token。只要有活动请求，它就重复这个循环。Python 独占一切会改变批次的操作：接受请求、运行其 prefill、分配或驱逐槽位、切换到更小的批大小。

`park / resume` 箭头就是这两个所有者之间的交接：

```
# Python control plane
while server_is_running:
    request = wait_for_new_request()

    decode_service.request_pause()       # C++ finishes its current decode step.
    decode_service.wait_until_parked()   # GPU is now idle; C++ will not read batch state.

    prefill(request)                     # Ordinary prefill kernels populate its KV pages.
    decode_service.admit_or_evict(request)
    decode_service.switch_batch_size_if_needed()

    decode_service.resume()              # C++ snapshots the new state and keeps decoding.
```

```
// C++ decode service
while (!stop) {
    if (pause_requested || active_requests == 0) {
        signal_parked();                  // Python may now mutate the batch.
        wait_for_resume_or_admission();
        continue;
    }

    update_kv_page_tables();
    clear_scratch_and_barriers();
    select_schedule(max_live_context());
    launch_megakernel();
    sample_and_stream_tokens();
    retire_finished_requests();
}
```

停靠（parking）是可变批次状态的所有权边界。Python 在 C++ 等待期间修改每请求元数据、token 缓冲、KV 页表，以及可能属于新批大小的指针。C++ 只在 resume 之后快照这些状态，并在下一个 decode 步独占它。这让 megakernel 不会观察到一个更新到一半的批次。当前的取舍很简单：prefill 暂停 decode，所以引擎尚不会在 GPU 上混合 prefill 与 decode。当没有活动请求时，C++ 自行停靠，Python 在准入后把它唤醒。

从外部看，这是一个支持流式、前缀缓存和 tool call 的 OpenAI 兼容服务器。

### **已知限制**

这些是当前实现的限制，而非设计的限制。我们计划把它们补齐。

- **不混合 prefill 与 decode。**一次 prefill 会暂停所有 decode 请求。对于大量极短请求的负载，这会略损性能。
- **最大批大小为 8。**这是配置限制，不是 megakernel 的架构限制。必要时服务器*可以*支持更大批大小，只是我们尚未调优大批大小的性能。
- **MK 仅用于 decode。**Prefill 以普通 PyTorch kernel 运行。

## **性能**

### **Decode 吞吐**

**设置。**所有数字在单张 H100（132 SM）上运行 North Mini Code 测得。基线是 vLLM v0.24，使用 FA3 attention 后端和 Triton MoE 后端，禁用 prefill。两个引擎都对着合成的 KV cache 做 decode，以将 decode 计算与 prefill 隔离。我们在 1K 个输出 token 上测量 decode 吞吐。

我们报告两种基准设置，两者差异很能说明问题。

- **真实 checkpoint。**两个引擎都使用真实的 North Mini Code 权重，因此 MoE expert 分布是模型真实的、相关联的路由。
- **Uniform routing。**vLLM 以模拟的均匀随机路由运行；megakernel 以随机权重运行，产生近似均匀的 expert 分布。

8K 上下文，按各批大小下的 vLLM 归一化：

图 9：megakernel 与 vLLM 在 8K 上下文下的 decode 吞吐对比。Megakernel 在真实 expert 分布下获得更高加速。

首先，在 uniform routing 下，流水线气泡最多的时候加速最大。Batch size 1 时每请求的工作最少，因此 GPU 时间中很大比例花在流水线气泡和 kernel 边界上。随着批大小增长，流水线气泡占总时间的比例下降，差距随之缩小。

其次，加速取决于 expert 分布。Batch size 8 下，megakernel 在真实 expert 分布下快 1.32×，uniform routing 下快 1.14×。真实请求经常选中相同的 experts，使活跃 expert 集合稀疏。MoE 总工作量因此更少，流水线气泡在步中占比更大——而这些正是 megakernel 能消除的空隙。Uniform routing 把 token 摊到许多 experts 上，留下更多 MoE 工作和更少可回收的气泡。因此合成的 uniform routing 会低估 megakernel 在真实流量上的加速，我们把它作为更难的对照报告在此。

### **我们学到了什么**

**Megakernel 起步比想象简单。**我们不需要编译器，也不需要新编程模型。普通的 GEMM 和 attention kernel 已经完成了最难的数学；把它们包进一个共享调用约定——相同的 warp 角色、任务格式和屏障协议——就足够手工组装 megakernel，一次一个操作。

**Megakernel 在真实流量的 MoE 模型上加速更大。**真实请求常命中相同的 experts，所以 MoE 工作稀疏，留下更多空闲时间让 megakernel 用其他就绪工作填满。

**Megakernel 与服务器配合良好。**Continuous batching 和 paged attention 都与 megakernel 相处融洽。Decode 作为单一持久 kernel 留在 GPU 上，配一个 C++ 主机循环，另有一条独立的 Python 线程控制引擎。

**Kernel 快了之后，剩下的加速在调度。**哪个 SM 跑哪个 tile、按什么顺序，是 kernel 调优之外的另一个性能旋钮。

### **下一步**

第一个问题是这一设计能延伸到 decode 之外多远。Prefill 的形状非常不同，混合 prefill/decode 批次将要求调度器让两种负载都保持推进、同时不打断对延迟敏感的 decode。

我们也在为 RTX Blackwell（如 RTX Pro 6000 和 RTX 50 系列）构建 megakernel，FP8 和 FP4 量化在路上。这是对 ABI 与调度设计能在多大程度上经受不同 GPU 架构和低位宽 kernel 考验的一个有用测试。我们计划很快发布 RTX megakernel。

在那之后，我们要把同样的方法带进数据中心 Blackwell 和多 GPU 推理。Tensor 并行与 expert 并行引入跨设备集合通信，新增一层同步边界，也潜在带来更多可供 megakernel 回收的流水线气泡。
