# Spaces：一个为人类也为 Agent 打造的 CLI

大多数开发者工具都是同一个开头。有件事要反复做，于是你写了个脚本。脚本长出了 flag。flag 长出了子命令。不知不觉，你就得到了一个 CLI。

我们在构建一个内部平台工具来帮助 solutions 团队更快交付时，经历的正是这个过程。它负责搭建项目脚手架、拉起开发环境、生成配置、部署到 staging。

随着 CLI 覆盖的范围变大，内部用户也变多了。接着，有意思的事情发生了：突然之间，我们不再只为人类开发者构建，也要为编码 Agent 构建。

## 好的 DX 应该是什么样

在谈 Agent 之前，先谈谈什么让一个 CLI 对人类开发者真正好用。

Spaces 在无聊的事情上有明确主张。它替你选定合理的目录结构。它生成那些你本来要从上个项目里拷贝过来的配置文件。它把服务接线到一起，让你的 API 和前端第一天就能对话，而不是花一小时改 YAML 或"vibe"出来。

一次典型会话是这样的：

```
$ spaces init my-project$ cd my-project$ spaces dev
```

三条命令。从零到一个带热重载、数据库和生成的 Dockerfile、正在运行的多服务项目。这就是标准。

真正重要的命令大体分三类：

- **Scaffolding（搭建）** —— 这些创建结构、提问、展示选项、让你探索。
- **Development（开发）** —— 这些是你的内循环。它们只管"跑"。
- **Operations（运维）** —— 这些会碰生产。小心，行动前先复核。

这些都是入场券。但随后我们的"第二用户"登场了，我们发现自己需要的东西稍有不同，而且有趣得多。

## 第二用户：Agent

我们为 `init` 做了一个 TUI 模块选择器。有花哨的变更、命令，看起来很棒。

然后一个 Agent 试图使用它。

Agent 看到的是原始 ANSI 转义码。`\\\\x1b[36m?\\\\x1b[0m Select components`。它发不出方向键，也无法切换选项。它被完全挡在命令之外。

事后看，解法显而易见：加一个 `--components` flag。但真正的洞察比一个 flag 更大。

## 每个 prompt 都是一个伪装成对话框的 flag

每次你的 CLI 提出交互式问题，都隐含一份契约："我需要这个信息才能继续。" 要履行这份契约，你可以用交互式对话框，也可以用 flag 或配置文件。

诀窍是先想*信息*本身，再想*输入方式*。

```
def init_command(    components: str | None = Option(None),    yes: bool = Option(False, "-y"),):    if components:        selected = components.split(",")    elif yes:        selected = get_defaults()    else:        selected = show_picker()
    # Same logic from here    create_project(selected)
```

三条输入路径，一条执行路径。业务逻辑不知道输入是怎么来的。这意味着你只需测一次，而不是三次。

`-y` flag 值得单独一说。它不只是"跳过确认"。它是一份契约，说的是：*我用程序化方式提供了你需要的全部信息，不要阻塞在 stdin 上。* 用 `-y` 运行时，每个对话框要么解析为 flag 值，要么解析为聪明的默认值。做不到就大声失败，而不是挂起。

**实践示例：本文中那些交互元素。**

这些元素是在一个全新仓库里构建的。我们随后要求一个 Agent 把项目接入 [spaces cli] 完成部署。它先对相关命令跑一遍 `--help` 来理解接口。据此，它推断出需要哪些配置文件、生成了 `config.yaml`、连好了 Dockerfile 和 registry 设置——全程无需人把手教。

在同一趟操作中，它配置好了 GitHub Actions CI 管线。从一条 prompt 到线上部署用时不到 10 分钟（我们正努力进一步压缩这个周期时间）。此后仓库配置完备，embeds 借助 [Koyeb](https://www.koyeb.com/) [完成了部署](https://spaces-blogs-staging-mistral-01d83c8e.koyeb.app/)——作为一个 Space，由 Spaces 自己搭建脚手架并部署。是的，这篇讲 Spaces 的博客文章里嵌入的交互 demo，就运行在一个 Space 上。*盗梦空间（Spaception）*。

因为每个交互输入都有等价的 flag，Agent 才能端到端自主操作。

## 把结构化数据当接口

我们团队构建的这个 CLI 帮助 applied AI 工程师交付应用。但应用并不都长一个样。有的需要后端加向量数据库，有的只需要关系型数据库、前端和几个 API，还有的是完全没有 UI 的 worker 服务。

我们不愿把模块类型写死，于是做了一个插件系统：每个组件都是一个声明自身属性的插件：

```
class ModulePlugin(BaseModel):    type_id: str    category: str    default_port: int
    def get_env_vars(self) -> list[EnvVarDef]: ...    def get_dev_command(self, port: int) -> str: ...
```

插件是可内省的。你可以列出它们、序列化它们、diff 它们。人类浏览 TUI 选择器；Agent 查询 registry 拿回 JSON。同一份数据，不同的呈现方式。

这顺手解决了一个我们此前不自知的问题。以前，新增一种模块类型意味着更新选择器、Dockerfile 生成器、env 文件写入器和 compose 模板。现在意味着写一个插件类。registry 是唯一事实来源，一切从它读取。

## 向 Agent 介绍你的项目

> 有句老话叫内容为王。对 Agent 而言，上下文才是王。

我们为 Agent 可用性做的最有影响的事，是在每次 `init` 时生成两个文件：

`context.json` —— 项目的结构化快照：存在哪些模块、使用哪些端口、有哪些运行命令、需要什么环境变量。

`AGENTS.md` —— 一组为 LLM 写的规则，比寻常写法更偏祈使句。不是"本项目使用 PostgreSQL"，而是"测试数据库变更前先运行 `mycli dev --migrate`。"

在行动前阅读这两个文件的 Agent 犯的错误会显著减少。基本上，它不会去猜端口号、跑错测试命令、尝试安装已由工具链管理的依赖。

context 文件还能破除 Agent 的过期假设。当你添加一个模块或更改部署目标，context 文件会在下一次 `dev` 或 `init` 时自动更新。Agent 每次读到的都是新鲜状态。

## 隐式状态是敌人

我们遇到的最微妙的问题是隐式状态。我们的 `add` 命令从当前工作目录读取 `config.yaml`。人类会不假思索地 `cd` 到正确目录。而从 workspace 根目录执行命令的 Agent，完全不知道自己应该位于某个子目录。

修复方式：

```
# Before: CWD dependencyconfig = load_config(Path.cwd() / "config.yaml")
# After: explicit with fallbackconfig = load_config(    path or find_config_in_parents(Path.cwd()))
```

每一个隐藏假设——CWD、环境变量、`$HOME` 里的 dotfile——都是 Agent 会绊倒的地方。显式参数配合理的回退，既解除了 Agent 的障碍，也让人类更容易写脚本。

## 检查清单

回望，这些改动单看都很小，只是一组原则被一致地贯彻：

- 每个交互输入都有 flag 等价物
- 每个 flag 在无头模式下都有聪明的默认值
- 状态是显式的。CWD、环境变量与配置路径是输入，不是假设
- 插件是数据模型，不只是代码。默认内省可见
- context 文件为 Agent（以及 CI 和脚本）提供项目的结构化描述

## 为所有人打造更好的工具

有趣的是，这一切没有让 CLI 对人类变差。TUI 选择器依然好用、依然炫，进度转轮依然转，确认对话框依然确认。我们只是多开了一扇门。

而那第二扇门最终成了更重要的那扇。不是因为 Agent 比人类更重要，而是它们施加的约束，与让一个 CLI 可组合、可脚本化、可测试的约束本来就是同一批。为 Agent 设计，倒逼我们造出了对所有人都更好的工具。

如果你正在构建开发者工具，你不需要单独的 Agent API。你需要审视每一个 `input()` 调用、每一处 CWD 假设、每一个只能漂亮打印的输出，然后问：如果屏幕那头是一个进程而不是人呢？

这个问题的答案，无论如何都会让你的工具变得更好。
