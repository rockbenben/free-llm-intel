# 堆会说谎：调试 vLLM 中的一处内存泄漏

几个月前，我们的团队调查了一起疑似发生在 vLLM 中的内存泄漏。起初我们以为问题很容易定位——应该是代码库上层的事。但越往深处查，它就越复杂。本文是我们全新"工程深潜"（Engineering Deep Dive）系列的第一篇，在这个系列中，我们将分享在 Mistral AI 如何开展技术调查并构建解决方案。

问题最初出现在我们一款[前沿模型](https://docs.mistral.ai/getting-started/models)分离式服务（disaggregated serving）的预生产测试中。内存占用在稳步攀升，但只在特定条件下：使用 vLLM、使用我们的 [Mistral Medium 3.1 模型](https://docs.mistral.ai/models/mistral-medium-3-1-25-08)、并开启图编译。没有崩溃也没有错误，只是在类生产流量下系统内存以每分钟 400 MB 的速度线性增长。几个小时后就会进入 "out of memory" 状态。

接下来是一场有条理的追猎：从高层 Python 工具开始，一路下沉到内核级追踪，最终揭开真正的源头。以下是我们的追踪过程，以及它揭示的当今软件依赖层的隐藏风险。

## **一场玩捉迷藏的泄漏**

最初，我们沿着标准排障路径推进：尝试在更小的模型上、关闭更多生产优化的方式复现问题，从而隔离泄漏源。但在尝试了不同设置和模型之后，我们无法在别的配置上复现。这个错误只在启用了 NIXL 的 Prefill/Decode 分离部署下出现。

鉴于 Prefill/Decode（P/D）分离在我们的故事中扮演核心角色，请允许我们先介绍这种推理部署的高层机制。P/D 分离把一个查询的处理拆分为两个阶段，由不同实例完成：

- 首先，路由器向一个 prefill vLLM 实例发送"prefill 请求"（设置 `max_tokens=1`，并置空的 KV Transfer 元数据集合），以计算该请求的 KVCache。
- 完成后，路由器把 KVCache 元数据连同"decode 请求"一起转发给一个 decode vLLM 实例。
- KVCache 传输经由 NIXL 发起，token 生成在 decode vLLM 实例上进行，使用并扩展传输过来的 KVCache。

泄漏只在这套分离部署的 decode 侧被观测到，强烈提示通过 NIXL 进行的 KV Cache 传输就是泄漏根源。在我们的环境中 **NIXL** 依赖 **UCX**（Unified Communication X）——一个为分布式系统数据交换设计的高性能通信库。UCX 支持在大量技术上做优化传输，包括 **Infiniband**——一种低延迟、高吞吐的互连技术，常见于 HPC 和数据中心。

*P/D 分离服务部署概览。*

在调查的剩余部分，我们就在这个环境中工作，并首先使用 Python 内存剖析工具来定位泄漏源。

我们尝试了 Memray 和 Guppy 3，但都没显示泄漏，它们能让我们观察到的一切都很正常。试图用 GDB 则让整个进程崩溃。我们的 vLLM 部署对 Valgrind 这类工具来说也太过沉重，慢到不实用甚至根本用不了。

显然需要更强的工具来追踪泄漏。但在投入更多时间之前，我们决定先确认这个泄漏对其他人也可复现。我们通过在 vLLM 团队的 GitHub 仓库开 [issue](https://github.com/vllm-project/vllm/issues/24264) 联系了他们，这帮助我们确认自己不是唯一遇到该问题的人，值得更深入的调查。

## **用 Heaptrack 数 malloc 和 free**

为了更好地追踪发生了什么，我们转向 [Heaptrack](https://github.com/KDE/heaptrack)：一个内存剖析器，它会接管 `malloc`、`free` 等内存操作，并把事件连同栈回溯一起记录下来。

Heaptrack 的作者 Millian Wolf 写过一篇很棒的入门[博客](https://milianw.de/blog/heaptrack-a-heap-memory-profiler-for-linux.html)教你如何使用该工具。整个过程分两步：先带追踪运行程序，再解读数据转储。

为了追踪限制在 vLLM worker 进程内的分配，我们通过 vLLM 把 `LD_PRELOAD` 设置为 `libheaptrack_preload.so`，确保这个库先于其他库加载，并接管内存分配函数的行为，为我们产出数据转储。

随后我们就能通过 `heaptrack_interpret` 可视化这些数据：

```
$ git clone https://github.com/KDE/heaptrack.git$ cd heaptrack && mkdir build && cd build && cmake .. && sudo make install
# Setting LD_PRELOAD=/path/to/libheaptrack_preload.so creates a temporary file named heaptrack.<pid>, here the pid is 2028233
$ /usr/local/lib/heaptrack/libexec/heaptrack_interpret < heaptrack.2028233 | gzip > heaptrack.vllm.2028233.gz
```

Heaptrack 提供所有堆分配的交互式细粒度视图，精确到函数级。我们可以追踪每一次 `malloc` 和 `free`，并得到内存使用的清晰分解。

*Heaptrack 展示的我们的 vLLM worker 的内存使用*

到这一步，你可能会问：内存泄漏在哪？确实，唯一可见的内存增长来自一次惰性的 NIXL 初始化。

为了验证泄漏确实发生在这套环境中，我们跑了一次 vLLM benchmark，并用 `heaptrack_interpret` 创建了两个 Heaptrack 快照：一个在开始时，一个接近结束时。尽管堆内存本身保持稳定，但**峰值常驻内存（RSS）**——我们将在下一节展开——在两个快照之间不同。这个差异在 Heaptrack 的汇总标签页上可见。

## **超越堆：理解常驻内存与系统级分配**

要理解 Heaptrack 为什么检测不到泄漏，我们得先弄清楚 **Resident Set Size（RSS）**到底包含什么。RSS 表示进程占用在 RAM 中的那部分内存，它不只是堆。具体包括：

- **堆**，传统上通过 legacy 的 `sbrk` 和 `brk` 系统调用管理，它们调整或设置程序的 break 地址——标记堆段末端的指针。
- **栈**，存放局部变量与函数调用帧。
- **匿名内存映射**，即直接通过 `mmap` 系统调用分配、没有文件背书（file backing）的内存区域。自定义分配器或 `malloc` 分配较大内存块时常用它。匿名映射的地址通常位于**堆地址空间与栈地址空间之间**，这一区域称为**内存映射段（memory mapping segment）**。

虽然 `malloc` 对小分配可以使用 `sbrk`，但现代实现通常优先使用带匿名映射的 `mmap`，因为它更灵活，并且允许分配 huge page（依配置为 2MB 或 1GB 的内存页）。

Heaptrack 只挂钩 glibc 的 `malloc` 和 `free` 函数。这意味着它能追踪所有由 `malloc` 直接分配的传统堆内存和匿名映射，但会错过通过直接 `mmap` 调用，或 glibc 控制之外的其他系统级机制分配的内存。

所幸，追踪正在发生的事并非束手无策。`/proc` 文件系统是 Linux 中一个特殊目录，充当**内核 API**，暴露一个与运行中进程交互的虚拟接口，提供进程细节的实时访问，例如：

- `/proc/<pid>/fd`，列出进程打开的所有文件描述符。
- `/proc/<pid>/maps`，展示进程内存区域的详细地图，包括堆、栈、共享库和匿名映射。
- 还有很多（在 `/proc/<pid>/` 里简单 `ls` 一下就能看到可用内容）。

为继续调查，我们使用 `pmap` 命令——它读取 `/proc/<pid>/maps` 并以人类可读的格式呈现内存使用情况。我们的目标是随时间追踪内存区域的变化，于是运行：

```
$ watch -n 1 "pmap -X $pid | (head -n 2 && tail -n +3 | sort -k7 -nr)"
```

这条命令每秒运行一次 `pmap`，显示指定 PID 的扩展内存信息，跳过表头，并按内存大小排序输出，让我们聚焦最大的内存区域。

通过这条命令，我们观察到一个有趣的模式：只有一部分匿名内存映射随时间增长，而且它们的起始地址在变化。这些分配的大小随时间变得巨大，而其他大多数分配纹丝不动。

*我们的 `pmap` 命令列出的内存页按 RSS 大小排序，很容易发现可疑分配。橙色点标出了一个示例。*

这种行为是 `mremap` 的特征——一个用于**调整现有内存区域大小或将其搬迁**而不释放它们的系统调用。与在堆内运作、依赖 glibc 内存管理的 `realloc` 不同，`mremap` 工作在更低层，常被自定义分配器、库甚至手工内存管理代码用来动态调整内存布局。

这个模式也可能来自 `munmap` 与 `mmap` 的反复循环——内存被释放又重新分配，但总用量持续增长，原因可能是**碎片化、自定义分配器中的泄漏，或不当的重置大小逻辑**。在我们的案例中，变化的地址加上增长的规模强烈提示内存在被重新分配却从未被正确释放。

这是我们的第一个具体线索：泄漏不在堆里，而在**被不断调整大小却没有正确释放的匿名内存区域**中。

## **用 BPFtrace 追踪泄漏**

我们的调查已把泄漏范围缩小到裸 `mmap` 或 `mremap` 调用，但需要确认到底是哪一个。第一次尝试是用 `LD_PRELOAD` 加载一个[小型自定义 C 库](https://gist.github.com/hasB4K/5211529e2a1741c478f253b82c110d69)，记录每一次 `mmap` 和 `mremap` 调用——既然 Heaptrack 做不到——希望拦截到我们关心的那些。然而这条路有局限：**并非所有** `mmap/mremap` **都经过 glibc**。我们的自定义钩子看到了一些分配，但它们与 `pmap` 输出中正在泄漏的地址对不上。泄漏区域仍在增长，绕开了我们的 `LD_PRELOAD` 钩子。这说明那些分配要么是通过手工执行 syscall 完成的，要么存在另一套挂钩机制。

为了看到全貌，我们转向 **BPFtrace**——一个实时追踪系统调用和内核事件的工具。它依赖 Linux 内核的 **eBPF 虚拟机**，执行挂载在 tracepoint 或探针上的轻量、预先校验的字节码，实现安全且低开销的分析。一些 Kubernetes 工具也用 BPFtrace 检测集群中的异常或危险行为，比如越权访问或资源滥用，同时不威胁内核稳定。

我们也考虑过 `strace`，但它依赖 `PTRACE`，在这个阶段分析该问题太慢了。于是我们写了一个 BPFtrace 脚本，记录**每一次** `mmap` **和** `mremap` **调用**及其参数与栈回溯，包括不经过 glibc 的调用。以下是我们在 [Le Chat](https://chat.mistral.ai/) 协助下编写的脚本：

```
tracepoint:syscalls:sys_enter_mmap /pid == (uint64)$1/ {    printf("Stack trace:\n%s\n", ustack(perf));    printf("PID/TID: %d %d | ", pid, tid);    printf("ENTER mmap(addr=%p, len=%d, prot=%d, flags=%d, fd=%d, off=%d)\n",           args->addr, args->len, args->prot, args->flags, args->fd, args->off);}tracepoint:syscalls:sys_exit_mmap /pid == (uint64)$1/ {    printf("PID/TID: %d %d | ", pid, tid);    printf("EXIT mmap: ret=%p\n", args->ret);
}tracepoint:syscalls:sys_enter_munmap /pid == (uint64)$1/ {    printf("PID/TID: %d %d | ", pid, tid);    printf("ENTER munmap(addr=%p, len=%d)\n", args->addr, args->len);}tracepoint:syscalls:sys_exit_munmap /pid == (uint64)$1/ {    printf("PID/TID: %d %d | ", pid, tid);    printf("EXIT munmap: ret=%d\n", args->ret);}tracepoint:syscalls:sys_enter_mremap /pid == (uint64)$1/ {    printf("PID/TID: %d %d | mremap", pid, tid);    printf("old_addr=%p, old_len=%d, new_len=%d, flags=%d, new_addr=%p)\n",           args->addr, args->old_len, args->new_len, args->flags, args->new_addr);}tracepoint:syscalls:sys_exit_mremap /pid == (uint64)$1/ {    printf("PID/TID: %d %d | ", pid, tid);    printf("EXIT mremap: ret=%p\n", args->ret);}
```

我们以 root 身份运行该脚本，把 `$pid` 替换为按照 `pmap` 判断正在泄漏的 vLLM worker 进程的 PID：

```
bpftrace /host/script_bpftrace.txt $pid > out_$pid.txt
```

概括地说，这个脚本：

- 在 `mmap`、`munmap` 和 `mremap` 系统调用进入内核时进行追踪。
- 打印线程 ID、调用类型、请求的地址和长度。
- 打印**用户态栈回溯**（BPFtrace 中的 `ustack`），以定位调用的出处。

以下是该脚本的一个输出示例：

```
Stack trace:  7ffff7d6b88d syscall+29 (/usr/lib/x86_64-linux-gnu/libc.so.6)PID/TID: 441359 441359 | ENTER mmap(addr=(nil), len=151552, prot=3, flags=34, fd=-1, off=0)PID/TID: 441359 441359 | EXIT mmap: ret=0x7fd8a78ee000
```

*BPFtrace 脚本的输出片段。`syscall+29` 很关键。*

到这一步，先综合一下我们已经收集的信息：

- `pmap` 让我们看到了可疑增长的分配及其基地址。
- BPFtrace 让我们弄清这些地址是通过 `mmap` 调用获得的，而不是 `mremap`。这出乎我们意料，因为对一个不断增长的内存分配来说，`mremap` 才是理想嫌疑对象。
- 更耐人寻味的是，这些调用源自 `syscall+29`，即 [glibc 的裸 syscall 包装函数](https://sourceware.org/git/?p=glibc.git;a=blob;f=sysdeps/unix/sysv/linux/x86_64/syscall.S;hb=5d1cb431aa#l37)，它允许用户通过 `syscall(SYS_mmap, ...)` 这样的 API 执行裸系统调用。

这是重大进展，但还需要进一步调查。虽然 BPFtrace 展示了系统调用本身的用户栈回溯（其文档中的 `ustack`），但它只给出了用户调用栈的第一个元素，而不是通向这次分配的完整用户态上下文。我们看到 `mmap` 在哪里被调用，却看不到前面的调用者。这些信息对我们至关重要，于是我们试图理解为什么拿不到它，最初以为是环境中**禁用了 frame pointer** 所致，决定往这个方向查。

补充背景：frame pointer 是一种把函数调用返回地址保存在寄存器或内存位置的特性，使工具得以重建完整调用栈。frame pointer 历史上作为优化被大多数库关闭，因为它带来轻微开销；但如今性能收益相对调试价值已可忽略，现代发行版已开始重新启用它。

遗憾的是，从 Ubuntu 22.04 LTS 切换到 Ubuntu 24.04 LTS（对原生库启用了 frame pointer）并不够。这提示真凶是一个已经过优化、禁用了 frame pointer 的 Python 依赖。

我们琢磨了一阵：哪个 Python 包会绕过标准的库调用直接做这种 syscall？到这一步，有两个潜在嫌疑：

- **UCX（Unified Communication X）**，一个用于加速网络与 RDMA（远程直接内存访问）的高性能通信库。UCX 是 NIXL 的依赖，而 vLLM 用 NIXL 做分离式服务。UCX 以其底层内存优化著称，包括自定义内存分配器。
- **PyTorch**，它自行做内存管理与优化，为性能常常绕过标准分配器。PyTorch 的自定义分配和 JIT 编译也可能是泄漏的原因。

两个嫌疑人都在台上，我们需要更深挖的手段。这一步我们转向了 GDB 自动化。

## **GDB 自动化救场**

在调查更早期使用 GDB 不可行，原因很简单：GDB 附加到整个进程。对 vLLM 来说，把 GDB 附加到主进程会暂停所有 worker，无法实时观察泄漏。而泄漏不引发崩溃，内存转储又因进程体量太大而不切实际。我们陷入僵局。

不过，从 BPFtrace 日志中我们注意到，每次泄漏的 `mmap` 调用都源自同一个地址。如上一节所述，该地址并不直接指向 `mmap`，而是位于 glibc 的 `syscall` 轻量包装函数内部。这个函数绕开了 glibc 常规的 `mmap` 包装，这解释了为什么我们此前的 `LD_PRELOAD` 钩子漏掉了它。我们试过用 `LD_PRELOAD` 拦截 glibc 的 `syscall`，但奇怪的是也不行……几乎不留给我们任何动态追踪这些调用的办法。

既然泄漏调用总是来自同一条 `syscall` 指令，我们可以让 GDB 自动化——只在该特定地址命中时中断。做法如下：

- 我们在 `syscall` 地址上设置一个**条件断点**，仅当系统调用号匹配 `SYS_mmap` 时触发。
- 临时在 `mmap` 系统调用出口处中断，检查返回值（即分配的地址），并打印完整栈回溯。
- 一次性倾倒所有可用上下文：返回地址、调用栈，以及其他相关寄存器或内存。
- **在 benchmark 期间运行这个条件脚本几秒钟**，把捕获到的返回地址与我们的 `pmap` 监控对照，确认它们是否匹配已知的泄漏区域。

以下是脚本，可通过 `gdb -x gdb_script.txt` 运行：

```
# Attach to the processattach 2199304
# Open a log file for outputset logging file syscall_output.txtset logging on
# Set a conditional breakpoint on syscall for rdi == 9 (mmap)break syscall if $rdi == 9
# Commands for the syscall breakpointcommands  silent  # Set a temporary breakpoint at the return point  tbreak *0x00007ffff7d9525d  # Commands for the temporary breakpoint  commands $bpnum + 1    silent    set $ret_val = $rax    bt    printf "Syscall returned: rax = 0x%012lx\n", $ret_val    continue  end  continueend
# Run the processcontinue
```

这个方法带来两大好处：

- 我们在分配发生的那一刻捕获了完整的用户态栈回溯——这是 BPFtrace 无法可靠提供的。
- 我们还可以把返回的地址与 `pmap` 输出交叉比对，确认它们是否匹配泄漏区域。

简言之，我们把 GDB 变成了一个有的放矢、低侵入的观察者：只在泄漏发生时中断、打印我们需要的一切、然后让进程继续。这终于让我们把 `mmap` 调用与 `pmap` 中看到的增长的匿名区域连成一线。

第一份栈回溯显示 Python（第 `#5` 行）通过 UCX（第 `#4` 行）调用 `mmap`，这很意外——正常情况下 Python 应该直接调用 glibc 的 `mmap`。

## **查明 UCX 内存钩子的角色**

我们把这些发现分享给 vLLM 团队，他们帮助我们验证并完善了对问题的理解。我们共同发现，UCX 使用一种 [mmap 钩子机制](https://github.com/openucx/ucx/blob/179a0e728d7ff0109f916f139e9efd4aa3f207e8/src/ucm/mmap/install.c#L354)来为 InfiniBand 优化内存操作，包括为传输预缓存数据（一项叫 Registration Cache、即 RCache 的特性）。InfiniBand 的内存管理往往开销很大，因为需要硬件级的内存注册。

然而，这个机制默认拦截**所有** `mmap` **调用**，而不仅是 UCX 或 InfiniBand 相关的调用。这种大范围拦截解释了为什么我们先前用基于 `LD_PRELOAD` 的 `mmap` 钩子追踪分配的尝试会失败：UCX 会[动态改写](https://github.com/openucx/ucx/blob/efd5356e0aac6a9d1e7f3b9ab4dfa8e4d90b64fc/src/ucm/util/reloc.c#L742)应用程序用来调用 `mmap`、`munmap` 等函数的 **GOT（全局偏移表）条目**。这就是它完全绕开我们此前钩子的原因。我们还发现，当检测到 Valgrind 时，这个钩子机制会[自动禁用](https://github.com/openucx/ucx/blob/179a0e728d7ff0109f916f139e9efd4aa3f207e8/src/ucm/malloc/malloc_hook.c#L845)——这本来也会妨碍我们用 Valgrind 做更深入的分析。

GOT 是动态链接器用于解析动态链接库函数调用的数据结构。程序启动时，动态链接器会用共享库中函数（如 `mmap`）的实际地址填充 GOT。

在运行时修改 GOT 通常被认为是坏实践，因为它可能引入不稳定、加大调试难度、破坏程序或库其他部分所依赖的假设。但 UCX 这么做有其正当理由：它借此管理自己的 Registration Cache，后者跟踪"已注册"（或"已钉住"）的内存。这类内存被固定原地，确保虚拟地址到物理地址的映射保持不变。这使网卡可以直接在网络结构与 RAM 之间传输数据而无需 CPU 参与——对性能至关重要，但也需要小心处理，因为注册内存是有限资源。

## **解决问题**

既然知道了 `mmap` 钩子机制在起作用，我们意识到这其实是好消息，因为可以通过设置环境变量 `UCX_MEM_MMAP_HOOK_MODE=none` 把它整个禁用。它成功关闭了这一行为，**在不影响性能的前提下解决了内存泄漏**。在通过 RDMA 发送各种零散内存块时 `mmap` 钩子很有用，但在 vLLM 的场景中，我们只需要处理**一整块连续的内存区域**：整个 vLLM KVCache Manager 的内存。NIXL 只需为其传输注册这块内存一次。因此，在 vLLM 用例中，禁用钩子机制是安全的，对分离式服务的性能没有负面影响。

与 UCX 团队讨论后我们了解到，UCX 在 `munmap` 被调用时并不会立即释放内存，而是把该区域移入一个失效队列（invalidation queue）留待稍后清理。这个队列由 UCX 的内存池管理，会按需动态扩容以容纳更多条目。结果就是内存区域不断堆积却不被释放，而不断变大的队列又需要额外分配——这解释了为什么 `munmap` 操作期间会调用 `mmap`。作为泄漏的替代解法，设置环境变量 `UCX_RCACHE_MAX_UNRELEASED=1024`（默认值为 `inf`）可限制队列中未释放内存区域的数量，迫使 UCX 在达到阈值时启动清理。

问题在于，这一切本不该发生。NIXL 和 vLLM 确实在[调用](https://github.com/ai-dynamo/nixl/blob/f41fc127a8ed993908a6cac799728637a7e1f26a/src/plugins/ucx/ucx_backend.cpp#L394) `ucp_worker_progress()` 函数，而它本应触发内存池清理。在这个特定边缘情况下它为何没有被触发，目前仍不清楚。但这表明把 `UCX_RCACHE_MAX_UNRELEASED` 的默认值设为无穷大是不对的。UCX 和 NIXL 团队决定[在下一次 NIXL 版本中改变这一行为](https://github.com/ai-dynamo/nixl/pull/1210)。在此期间，我们已在 vLLM 仓库合入一个[修复](https://github.com/vllm-project/vllm/pull/32181)，帮助社区避免踩进同一个泄漏。

## **调查过程回顾**

简要回顾整个调查：

- 在**生产环境**部署我们一款前沿模型的分离式服务时，我们注意到**内存泄漏快速增长**。
- 我们试图精简环境、做一个最小复现。不幸的是，**这个 bug 只在复杂环境——大模型且启用分离式服务——下复现。**
- 我们转向 Memray、Guppy 3 和 Heaptrack 分析泄漏。**这些工具都没有给出明显结果。**不过我们在 Heaptrack 的指标里发现异常：**常驻内存大得不寻常**，于是决定往这个方向深挖。
- 借助 `pmap`，我们看到 **RSS 分配持续增长，并附带各自的基指针**。
- 我们想弄清是谁在做这些调用。写了一点脚本并使用 BPFtrace 后，**我们发现泄漏源自** `mmap` **调用。**尽管竭尽全力，我们仍无法采集完整栈回溯（那本可以让我们锁定肇事的调用点），但**这让我们判断这些 syscall 出自一个深度优化的包**。
- 凭借收集到的信息，我们**设置了极其精确的 GDB 断点，只会被肇事调用触发**。
- 我们发现**这些调用是 UCX 发出的**。虽然调用的目的正当——提升 InfiniBand 传输性能——它却在 RSS 中造成不断增长的分配，并**让我们数天无法部署分离式服务**。
- 查明泄漏源头后，变通方案很容易找到：**设置** `UCX_MEM_MMAP_HOOK_MODE=none` **解决了我们的问题。**我们在 [vLLM 仓库中讨论了这次调查](https://github.com/vllm-project/vllm/issues/24264)，并为社区合入了[一个补丁](https://github.com/vllm-project/vllm/pull/32181)。

## **我们学到了什么**

现代软件栈构建在层层依赖之上，每一层都增加复杂性和潜在故障点。这些抽象极大提升了程序员的生产力，却不能让他们与栈底层的隐患完全绝缘。这就是为什么调试时必须做好深挖的准备。而在这种环境中做深挖很少是直截了当的，尤其是当性能优化引入微妙的边缘情况时。UCX 就是一个很好的例子。它的设计以性能为先，但它拦截 `mmap` 调用的方式可能制造难以追踪的风险。这次经历再次证明，在深度互联的系统中诊断问题可能有多难。

这次调查也说明，在与性能关键型依赖打交道时，透明与协作何其重要。我们感谢与 [vLLM](https://vllm.ai/)、[NIXL](https://github.com/ai-dynamo/nixl) 和 [UCX](https://openucx.org/) 团队的协作——他们帮助确认并解决了这一行为。他们的专业知识对最终解决至关重要，我们期待继续携手合作。
