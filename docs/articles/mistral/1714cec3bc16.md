# Leanstral：可信 vibe-coding 的开源基石

AI Agent 已被证明是代码生成的高效工具。然而，当我们把这些模型推向高风险领域——从前沿研究数学到关键任务软件——会遇到一个规模化瓶颈：人工评审。人工验证所需的时间与专门知识，成了工程速度的主要阻力。

我们设想新一代更得力的编码 Agent：既能完成任务，又能对照严格规范形式化证明其实现。人类不再调试机器生成的逻辑，而是直接说明想要什么。今天，我们朝着这个愿景迈出了第一步。

## 发布 Leanstral

我们发布 Leanstral，首个专为 Lean 4 设计的开源代码 Agent。Lean 4 是一个证明助手，能够表达复杂数学对象（如[完全oid 空间（perfectoid spaces）](https://xenaproject.wordpress.com/2020-12-05/liquid-tensor-experiment/)）以及软件规范（如 [Rust 片段的性质](https://github.com/AeneasVerif/aeneas)）。与现有那些只是大型通才模型外壳、或聚焦单一数学题的证明系统不同，Leanstral 设计上追求高效（6B 激活参数），并为在真实形式化仓库中操作而训练。

- 开放且易得：我们以 Apache 2.0 许可证发布 Leanstral 权重，在 Mistral vibe 中提供 Agent 模式，并开放免费 API endpoint。我们还将发布详述训练方法的技术报告，以及全新评测套件 FLTEval，让评测超越对竞赛数学的专注。
- 高效且强大：Leanstral 采用高稀疏架构，并针对证明工程任务做了优化。借助以 Lean 作为完美验证器的并行推理，Leanstral 相比现有闭源竞品既高性能又具成本效益。
- 可通过 MCP 升级：Leanstral 通过 vibe 支持任意 MCP，并经过专门训练，在使用最频繁的 lean-lsp-mcp 上达到最佳性能。

## 评测

为了反映真实证明工程场景中的实用性，我们以"完成 FLT 项目每个 PR 中的全部形式化证明并正确定义新数学概念"为基准测试 Leanstral，而非孤立的数学题。对比对象包括领先的编码 Agent（Claude Opus 4.6、Sonnet 4.6、Haiku 4.5）与开源模型（Qwen3.5 397B-A17B、Kimi-K2.5 1T-A32B、GLM5 744B-A40B）。

### Leanstral 对比开源模型

Leanstral-120B-A6B 相比规模大得多的开源同行显示出显著的效率优势。GLM5-744B-A40B 和 Kimi-K2.5-1T-32B 等模型难以扩展，FLTEval 分数分别止步于约 16.6 和 20.1，而 Leanstral 仅凭单次通过（single pass）就超越了它们两者。

即便是表现最强的开源竞品 Qwen3.5-397B-A17B，也需要 4 次通过才达到 25.4 分。相比之下，Leanstral 用一半投入（pass@2）就取得更高的 26.3 分，并继续线性扩展，在同等成本水平达到 29.3 分。

### Leanstral 对比 Claude 家族

Leanstral 是 Claude 套件的高性价比替代，以几分之一的价格提供有竞争力的性能：Leanstral pass@2 得分 26.3，比 Sonnet 高 2.6 分，而运行成本仅 $36，Sonnet 则为 $549。在 pass@16 时，Leanstral 得分 31.9，稳稳超出 Sonnet 8 分。Claude Opus 4.6 仍是质量上的领先者，但其成本高达 $1,650，是运行 Leanstral 的 92 倍。

## 案例研究

### 回答 Stackexchange 上关于最新版 Lean 变更的帖子

当破坏性变更伴随新的 Lean 版本发布时，迁移代码可能是一场噩梦。我们向 Leanstral 投喂了 [Proof Assistants Stack Exchange 上一个真实问题](https://proofassistants.stackexchange.com/questions/6471/a-strange-issue-with-a-type-alias-in-lean4)：一个脚本在 Lean 4.29.0-rc6 中神秘地无法再编译（由于版本太新，我们没有用训练数据覆盖它）。罪魁祸首是一条 rewrite（`rw`）策略，突然无法再匹配涉及一个简单类型别名的模式——该别名最初写作 `def T2 := List Bool`。

Leanstral 没有瞎猜，而是挽起袖子干了起来。它成功构建了测试代码以复现报错环境，并诊断出底层的问题在于定义相等性（definitional equality）。模型正确识别出：因为 `def` 创建的是一个需要显式展开的刚性定义，它实际上阻碍了 `rw` 策略看到其匹配所需的底层结构。

它提出的修复很简单：把 `def` 换成 `abbrev`。由于 `abbrev` 创建的透明别名与原始类型立即在定义上相等，`rw` 策略就能再次完美匹配证明中的模式 `(L2 n).length`。Leanstral 完成了任务，并向用户完美解释了原理。

### 程序推理

我们从 [https://www.cs.princeton.edu/courses/archive/fall10/cos441/sf/Imp.html](https://www.cs.princeton.edu/courses/archive/fall10/cos441/sf/Imp.html) 复制了 Rocq 中的若干定义，要求 Leanstral 转换为 Lean。它成功了，甚至还实现了自定义记号。代码片段示例：

```

-- Notation for command evaluationnotation:50 c " / " st " ⇒ " st' => ceval c st st'
```
