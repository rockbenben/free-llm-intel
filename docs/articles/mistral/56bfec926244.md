# 用 AI Agent 现代化复杂遗留代码

遗留代码现代化充满挑战，尤其是把复杂的 Fortran 77 系统迁移到现代 C++。Mistral 成功迁移了一个物理密集型油藏模拟器中的 40,000 行代码——方法是搭建用于数值校验的 parity harness、用 AI Agent 为代码库补文档，并采用带人工监督的结构化工作流来确保高质量、可维护的代码。关键经验包括：把数值一致性放在首位、在迁移前先组织好文档、在 Agent 自主性与人工评审之间取得平衡。

遗留科学代码库会积累数十年，当原作者离职，嵌入代码中的知识便难以恢复。而且，使用一个没有活跃开发者生态的语言，意味着失去在他人成果之上构建的机会。Mistral 帮助一家欧洲能源运营商把 40,000 行 Fortran 77 迁移到 C++——那是一个物理密集的油藏模拟器，没有测试套件，也没有集中文档。

## 在遗留代码现代化中超越"代码翻译"。

把语法从一种语言翻成另一种语言，基本已被解决。让任何近期模型把一段不太冷门语言的代码片段翻成另一门语言，几次迭代内大概率就能收敛到可接受的结果。然而，把一个完整系统从过程式语言迁移到面向对象 C++，会带来架构重构需求，使任务变得不平凡。

正如名字暗示的，Fortran 77 于 1977 年标准化，用它编写的代码直接打上那个时代的约束烙印：没有模块、没有命名空间、没有结构化类型。状态存活在 COMMON 块里——全程序共享的全局内存。变量按首字母隐式定类型，因此一个拼错的名字会悄无声息地创建一个新变量，而不是抛出编译错误。

举个简单但有代表性的例子，下面是一段一阶泰勒展开的实现。输入输出都是 COMMON 块中的全局变量，而 `IC` 是整数仅仅是因为它的首字母落在 I 到 N 之间。变量名相当晦涩，因为长度被限制在 6 个字符。

```
   SUBROUTINE GASDEN   INCLUDE 'common.h'   DO 10 IC = 1, NCELL10 RHOG(IC) = ROG(IV) + DROG(IV)*(P(IC)-PTAB(IV))   END
```

在 C++ 中，就能利用显式类型、编写面向对象代码，并返回值而不是写全局变量：

```
double gasDensity(const GasProperties& gas, double pressure) {    size_t i = lookup(gas.pressure, pressure);    return gas.density[i] + gas.slope[i] * (pressure - gas.pressure[i]);}
```

四散的 COMMON 数组收敛为一个 `GasProperties` 参数，网格循环移到了调用方，因此不存在可以逐行核对的对应关系——这正是迁移难以验证的原因。

这些结构性差异，加上要集成 PetSc 等现代科学计算框架的要求，让我们在迁移开始前就不得不回答几个重要问题：

- 如何证明迁移后的代码库与遗留代码库在数值上一致
- 如何把迁移拆成可管理的块
- 如何最好地利用自主 Agent 加速流程

## 在迁移遗留代码之前先搭建 parity harness。

在放开 Agent 之前，我们需要一种方式证明两套代码库是一致的。这里的"一致"指输出的数值相等——既包括最终结果，也包括由客户油藏工程师标记的一组关键中间点。

我们加入了：

- 可以导出 Fortran 代码库状态的子程序
- 一个把这些检查点（checkpoint）加载进 C++ 的测试框架
- [Skill.md](http://Skill.md) 文件，引导 Agent 正确使用它们

在迁移工作流中，Agent 成功地对 Fortran 代码库做了插桩以转储状态快照，并使用 C++ 测试框架验证已迁移模块的正确性。

先构建 harness 的这部分对项目是一笔净收益：它让长时间的 Agent 运行更安全；而数值 parity 易于验证，是展示某段代码已成功迁移的有力论据。我们认为这应当是所有代码现代化项目的第一个步骤之一。

下面的例子说明了这一点。我们先在 Fortran 代码中插入一行，转储 RHOG 变量的值（本次运行中为 42.71834），然后把同一个值作为参考检查点，用来测试迁移后的 C++ 模块。

## 用 AI Agent 理解和撰写遗留代码库文档。

项目的文档散落在旧 PDF 和埋在 Fortran 源码里的注释中，而整个工作最大的意外收获之一，就是梳理齐这些文档并把它们搬到代码旁边。

幸运的是，Fortran 这样的过程式代码有个便利属性：整个程序可以画成一棵单一的主调—被调树。我们用一个自研解析器解析代码库生成了这棵树，然后用 [Vibe CLI](https://mistral.ai/products/vibe/) 派出上百个 Agent 为其补文档。每个 Agent 都可以通过文档库和 [Mistral OCR](https://mistral.ai/solutions/document-ai/) 拉入相关 PDF。

从树的叶子出发自底向上，每个节点派生一个子 Agent 为其撰写文档，并向原仓库开一个 PR。一个按 cron 计划持续循环运行的评审 Agent 负责寻找新开的 PR，进行评审并在必要时安排修复任务。

## 利用 AI Agent 进行代码现代化。

第一次尝试，我们给予 Agent 完全自主权：每个 Fortran 子程序一个 Agent，各自在一周时间内独立把自己的函数翻译成 C++。结果是能运行的，但称不上代码现代化。COMMON 块一比一变成了全局 struct；由 GOTO 驱动的控制流原样保留，没有被重构为循环或提前返回。它看起来像是用 C++ 语法重新打了一遍的 Fortran，而不是现代化代码。

第二次尝试中，我们用"给 Agent 结构而不只是自主权"来解决：每个模块由一个 planner、一个 coder、一个 tester 和一个代码质量评审 Agent 协作完成。代码质量比第一次显著提升。但源码的复杂度最终还是绊住了 Agent：它们撞上一个 bug，尝试几次修复后便卡住，却没有人能介入。

我们落到了一个折中点：由一名人类操作一套 coder、tester、reviewer Agent 工作流，逐模块迁移代码库。这既保留了第二次尝试的代码质量，又加入了人类检查点，在 Agent 卡住时予以解困。下一节详述这套工作流。

## 为复杂代码迁移运行结构化的 AI Agent 工作流。

代码库有了文档、parity harness 就位之后，剩下最有意思的部分，就是调校我们敢给 Agent 多少自主权、同时仍能产出可合并的代码。两个极端我们都试过：从完全自主运行到紧密监督的人工会话。下面的结构化工作流是我们针对这个用例落定的方案。

与客户方的油藏工程师合作，我们用主调—被调树识别独立模块——规模可控的自包含子树（经验上，约 10,000 行 Fortran 以下）。每个模块走同一套工作流：

- 生成目标 C++ 架构。
- 与一位油藏工程师评审该架构。
- 获批后，拆分为任务队列。
- 每个任务跑一个实现子工作流：plan → implement → test → 循环。
- 由人类评审产生的 PR，反复要求修改直到合并。

### 认识 AI 辅助遗留代码现代化的边界。

第一个冲刺覆盖了核心功能：300,000 行中的 40,000 行。Fortran 代码库自包含且可运行，这是有利的起始条件。那些依赖外部系统、缺少可运行基线、或承载了无任何文档记载的物理知识的迁移，会带来本文未讨论的额外挑战。

## 现代化复杂遗留系统的三条原则。

这个项目的三条经验应可迁移到任何大型遗留系统迁移。

- 在写迁移代码之前先搭建 parity harness——数值一致是一个模块完成的最低成本、最有说服力的证明。
- 在依靠 Agent 之前先把文档理顺，因为你无法迁移没人能读懂的代码。
- 在这个规模上，带人工评审关卡的结构化工作流，胜过完全自主和纯手工两种方式。
