# 自动导航中的 Rails 测试：构建一个写"开发者不愿写的测试"的 Agent

在大多数大型 Rails 单体应用中，组织把编写新功能置于为它们写测试之上。日积月累，越来越多的代码没有测试，迫使团队花更多时间调试痛苦的 bug。

我们构建了一个自主 Agent 来弥合这个缺口。它读取 Rails 源文件，生成或改进 RSpec 测试，对照风格规则和覆盖率目标做校验，并在 CI/CD 管线中无需人工干预地运行。为了在这种规模的代码库上工作，它以并行方式运行：多个实例同时处理不同的文件。

## 从 Agent 的眼中看 RSpec

Ruby 是动态类型的：没有编译步骤，错误在运行时才浮现。对我们的 Agent 来说，这意味着验证测试语法的唯一方式就是执行它。[**RSpec**](https://rspec.info/) 是 Rails 的标准测试框架，让测试富有表达力且可读，但其领域专用语言很容易写错。

当 Agent 阅读一个 Ruby on Rails 代码库时，它主要读五种文件类型（model、serializer、controller、mailer、helper），每种结构不同（因此测试方式也不同）。Agent 需要为每种类型准备不同的指令。

一个好处是：源文件到 spec 文件的映射几乎是 1:1。通用约定是：

![Standard Mapping](https://mistral.ai/_astro/5825a803-d859-48f1-a3f8-ea095da3416a_Z28qkgI.webp?dpl=6abbd11780b53c00082eea6f)

不过这个规则也有少数例外，比如 `app/controllers/` 有时映射到 `spec/requests/`；有时一个源文件会有多个 spec 文件，此时约定是：

![Edge Cases](https://mistral.ai/_astro/6ba9925a-0be9-410e-ba7f-e23d961531c2_1kk2nz.webp?dpl=6abbd11780b53c00082eea6f)

这种直白的映射让"定位任意文件的测试"或"找出完全没有测试的文件"都变得容易。

对我们的 Agent 来说更难的地方在于：为避免重复代码，RSpec 大量依赖共享上下文：factory、fixture、数据库 schema……

- **Factories：**用于创建带预定义属性的测试对象的可复用模板，让一致的测试数据易于生成。
- **Fixtures：**预载测试数据库记录的静态数据文件，为测试提供固定的基线。

如果某个 factory 文件不存在，Agent 就创建它；如果存在，Agent 就复用它。由于 factory 被许多测试共享（不同于 spec 文件），粗心的改动很容易破坏其他地方的测试，所以更新这些文件必须谨慎。

## 用 Vibe 构建 Agent

我们在 [**Vibe**](https://mistral.ai/products/vibe)（Mistral 的开源编码助手）之上构建了这个 Agent。默认系统 prompt 对这个项目已经够用，所以我们聚焦三个杠杆：仓库级上下文、专门 skills 和自定义工具。

### 上下文工程

上下文工程是我们方法的核心。Vibe 支持仓库级 `AGENTS.md` 文件：当在根目录带有这个文件的仓库中运行时，其内容会自动追加到系统 prompt。

我们使用的 `AGENTS.md` 提供了目标仓库的基础信息，但更重要的是，它为 Agent 提供了一份**逐步执行计划：**

```
1. Read the source file2. Read the documentation (if it exists)3. Check if a spec already exists4. Choose and read exactly one skill based on the source file location5. Find existing patterns, factories, and helpers6. Execute the skill (Extract → Factory → Generate tests)7. Validate with Rubocop tool8. Validate with SimpleCov tool
```

每一步都包含"做什么"和"成功标准是什么"的细节。我们还在认为需要引导 Agent 的领域加入了一些 RSpec 最佳实践。示例：

```
- **NEVER** use `be_present`, `be_truthy`, `be_between`, or `include(:key)`These are vague. Use `eq(exact_value)` always
```

我们发现 Agent 有时会跳过方法或漏测边缘情况：生成的 spec *看起来*完整，却悄悄忽略了源文件里的几个 public 方法。为对策，`AGENTS.md` 以强制自查收尾：Agent 在结束前必须重读源文件并明确自问"我测了每个 public 方法吗？数一遍。"如有遗漏，就得回头补。

有了这个强制 Agent 遵循严格计划的通用 `AGENTS.md`，我们的质量分数从 **0.68 升到 0.74**——全部来自一个只含框架级指令的 markdown 文件。

### 使用 SKILLS 文件：

回想 `AGENTS.md` 的第 4 步：

`4. Choose and read exactly one skill based on the source file location`

单个通用 skill 只会产出平庸结果：测 model 文件足够精确的指令，用在 controller 文件上就是错误指令。

行得通的做法是每个类别单独建一个 skills 文件，外加一个纯 Ruby 文件的。

以下是用于测试 controller 的基础 skills 文件示例：

```
---name: "Generate Request Spec"description: "Generate RSpec request tests for a Rails controller. Use when the source file is in app/controllers/."---
# Generate Request Spec
## File Scope
- `spec/requests//_spec.rb` — drop `_controller` from the filename- `spec/factories/.rb` — create or update if needed
## Example tests for Controllers
# frozen_string_literal: truerequire 'rails_helper'
describe 'Admin::Users', type: :request do  let(:user) { create(:user, :admin) }  before { sign_in user }
  # Unauthorized access — one test per action  describe '#authorized?' do    let(:user) { create(:user) }    it 'GET /admin/users redirects' do      get '/admin/users'      expect(response).to have_http_status(:redirect)    end  end
  # Each action: happy + sad paths  describe 'POST /admin/users' do    let(:valid_params)   { { user: attributes_for(:user) } }    let(:invalid_params) { { user: { email: '' } } }
    context 'with valid params' do      it 'creates a record' do        expect { post '/admin/users', params: valid_params }.to change(User, :count).by(1)        expect(response).to have_http_status(:created)      end    end
    context 'with invalid params' do      it 'returns unprocessable entity with errors' do        post '/admin/users', params: invalid_params        expect(response).to have_http_status(:unprocessable_entity)        json = JSON.parse(response.body, symbolize_names: true)        expect(json[:errors]).to include("Email can't be blank")      end    end  endend
## Critical Rules
- **Assert content, not just status:** always parse JSON and verify exact values- **Test exact error messages:** `include("Email can't be blank")`, not `be_present`- **Verify state changes:** use `.by(1)` and check the created record's attributes- **Cover all actions:** index, show, create, update, destroy, and any custom actions- **Test auth on every action:** verify unauthorized users get the correct status code- Use `let` only, never `@instance_variables`; `sign_in user` again before `follow_redirect!`
```

### 添加自定义工具

Vibe 内置了读写文件、运行 bash 命令和编辑代码的工具。但它也支持自定义工具与 MCP 来扩展动作空间。对这个项目，自定义工具是关键。

经过一些试验，我们选择了：

- 一个 [RuboCop](https://rubocop.org/) lint 工具，运行 `rubocop` 命令检测风格违规，让 Agent 回到代码去修复。
- 一个与 RSpec 集成的 [SimpleCov](https://github.com/simplecov-ruby/simplecov) 工具，同时检查代码覆盖率与测试正确性。把它放在最后一步是关键：它保证 Agent 写的每个测试真的被执行过。

以下是我们实现 Rubocop lint 工具的简化版本：

```
import asynciofrom pathlib import Path
from pydantic import BaseModelfrom vibe.core.tools.base import BaseTool, ToolError
class RubocopLintResult(BaseModel):    command: str    output: str    success: bool    exit_code: int | None = None
class RubocopLint(BaseTool):    description = "Lint spec files using Rubocop."
    async def run(self, spec_path: str):        spec_path = Path(spec_path)
        cmd = ["rubocop", "--format", "simple", str(spec_path)]        proc = await asyncio.create_subprocess_exec(            *cmd, stdout=asyncio.subprocess.PIPE, stderr=asyncio.subprocess.PIPE        )
        try:            stdout, stderr = await asyncio.wait_for(proc.communicate(), timeout=60)        except TimeoutError:            proc.kill()            await proc.wait()            raise ToolError("Rubocop timed out after 60s")
        output = stdout.decode("utf-8", errors="ignore")
        yield RubocopLintResult(            command=" ".join(cmd),            output=output,            success=proc.returncode == 0,            exit_code=proc.returncode        )
```

SimpleCov 工具遵循相同模式但做得更多：它用 RSpec 运行 spec 文件，收集每个测试的通过/失败结果，并报告源文件的覆盖率百分比。Agent 会收到哪些测试失败（附错误消息），以及源文件的哪些行从未被执行。这给了它自我纠错所需的足够信息。

我们最初接入这个工具时，只有约三分之一的生成测试能在首次执行时通过。Agent 在几次迭代内自我纠正了所有失败。没有这一步，其中一些测试根本不会被运行。

## 度量测试质量

一个好的单元测试遵循 [**Arrange-Act-Assert**](https://semaphore.io/blog/aaa-pattern-test-automation) 模式：布置状态、执行一个行为、验证结果。它应使用精确断言，覆盖正常与错误两条路径，并且失败信息能清楚指出坏在了哪里。

![Good Testing](https://mistral.ai/_astro/32542f94-4778-4112-820f-203e96ef0735_N7Ion.webp?dpl=6abbd11780b53c00082eea6f)

### 基于工具的指标

现有的 Ruby on Rails 工具让我们容易获得若干指标：

- **RSpec：**Ruby 最流行的测试框架。用富有表达力的语法编写可读、结构良好的测试。
- **RuboCop：**Ruby 静态代码分析与格式化工具，帮助执行风格指南、保持代码一致。
- **SimpleCov：**Ruby 代码覆盖率工具，衡量测试套件执行了多少代码。

从这些工具中，我们可以提取几个有用的量化指标：通过的测试比例、每个文件的 RuboCop 违规数、单元测试套件覆盖的代码比例、执行速度。这些指标为衡量测试套件的总体表现提供了扎实的基线。

但仅凭这些数字无法判断一个测试文件是否真的好。两个文件都零 RuboCop 违规、100% 覆盖、全部测试通过时，我们该怎么比较？量化指标可能完全相同，但测试质量的定性差异依然存在。

### LLM-as-a-judge

LLM-as-a-judge 的思路是问一个 LLM："所有错误条件都测到了吗？"或"这是个好的测试吗？"，然后根据明确标准返回 0 到 1 的分数。

Prompt 示例：

```
## Good Tests
Precise values: `eq(100)`, not `be_present` or `be_a(Float)`.State changes: `change { User.count }.by(1)`.Error paths: `raise_error(ArgumentError, "message")`.Boundary cases: Test exact values at thresholds (e.g., `page(0)`).Public interface: No `.send(:private_method)`.
## Bad Tests
Vague assertions: `be_truthy`, `be_an(Array)`."Doesn't crash" tests: `not_to raise_error`.Testing private methods.Over-mocking (tests mocks, not behavior).No assertions on return values.
## Scoring Rules
- 1.0: Precise assertions on return values/state + all key paths covered (happy, error, boundaries).- 0.8: Precise assertions on all tested paths, but 1-2 edge cases missing entirely.- 0.6: All key paths covered, but 1-2 tests use vague assertions (e.g., `be_truthy` instead of `eq(expected)`) or minor over-mocking.- 0.4: Some tests have precise assertions; others are vague, over-mocked, or skip return value checks.- 0.2: Most tests lack meaningful assertions: vague matchers, stubbed-out logic, no verification of actual output.- 0.0: Tests are structurally broken: testing private methods, no real assertions, or verifying mocks instead of behavior.
```

这里的 "Scoring Rules" 部分尤其重要，它让分数在多次运行间更一致。没有它，Agent 就缺少"评分该多严或多松"的明确定义。

这样的分数不如工具输出或资深开发者评审那样权威。但它是当前版本 Agent 表现的良好指示——尤其当在仓库中对每个文件规模化运行时。

#### LLM-as-a-judge 评测的局限：

凡是能写成文本的东西都可以用 LLM-as-a-judge 打分，这让它用途广泛。但分数输出不是确定性的。即使 *temperature=0*，也会因 kernel 操作顺序而产生方差。实践中同一评估的输出总是很接近，但这种不确定性对某些用例可能是问题。

对我们的用例，由于我们一次打分的不是单个测试而通常是几十到几百个，这个局限可以接受。聚合分数保持稳定。

### 缺括号问题

LLM-as-a-judge 还有一个核心问题：一个测试可以质量很高但根本跑不起来，或者其背后的逻辑完全错误。

示例：

```
RSpec.describe User, "#full_name" do  it "combines first and last name with a space" do    user = User.new(first_name: "Ada", last_name: "Lovelace"
    expect(user.full_name).to eq("Ada Lovelace")  endend
```

这个测试看起来很棒。它测一个行为，描述清晰、读起来像文档，遵循 [**Arrange-Act-Assert**](https://semaphore.io/blog/aaa-pattern-test-automation):，如果被破坏会以有用的消息失败。

我们用先前定义的评分 prompt 把该测试交给多个模型评估，平均给分是 0.75。开发者扫一眼大概也会同意。

但这个测试有一个核心缺陷：**它跑不起来。**全部因为 `User.new()` 少了一个右括号 `)`。这是致命缺陷，让这个测试绝对不可用。

这个例子容易防范。但导致语法错误的其他可能性还有很多：

- **版本错误：**使用了不兼容 Ruby 或 Rails 版本的方法或语法
- **不存在的方法：**某些方法可能已被移除、改名，或从未存在
- **Factory/fixture 错误：**引用了缺失的 factory、错误的属性或缺失的关联
- **缺失依赖：**使用了测试环境中未包含的 gem 或模块

## 实验

我们做了一次实验，检验 Agent 能否扛住真实代码库。目标仓库包含 275 个源文件，一半已有测试覆盖，另一半完全没有。

我们把 Agent 指向每个文件，无论其是否已有测试。对未覆盖的文件，它成功地从零生成 spec；对已有测试的文件，它重写并改进了它们。

我们用 LLM-as-a-judge 对每个 spec 文件前后打分。已测文件的聚合分数从 0.49 升到 0.74，覆盖率达到 100%。仍有改进空间，但结果验证了这套方法。

| Metric | Result |
| --- | --- |
| Files processed | 275 |
| Tests passing | 100% |
| Average line coverage (SimpleCov) | 100% |
| RuboCop violations after self-correction | 0 |
| LLM-as-a-judge score | 0.74 |

### 按文件类型

并非所有文件类型都容易测。Model 得分最高：其业务逻辑自包含，测试模式可预测。Controller 更难，HTTP 请求处理引入了更多出错空间。

| File type | LLM-as-a-judge |
| --- | --- |
| Models | 0.81 |
| Controllers | 0.67 |
| Serializers | 0.80 |

### 它能跑吗？

把 SimpleCov 与 RSpec 执行捆绑为最后一步、强制 Agent 运行它写的每个测试，是整个项目中影响最大的一个决定。首次执行只有约三分之一的测试通过。Agent 在几次迭代内自我纠正了所有失败。

没有这一步，LLM-as-a-judge 就会把这些跑不起来的测试评为高质量——即规模化出现的缺括号问题。
