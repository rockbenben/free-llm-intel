## 引言

今天我们推出 Schematron，一个专用模型家族，负责把凌乱的 HTML 变成干净的、结构化的 JSON。

Schematron-8B 和 Schematron-3B 提供前沿水准的抽取质量，成本只有大型通用 LLM 的 1-2%，推理速度比它们快 10 倍以上。正因为专注于 HTML 到 JSON 这一件事，它们能够应付格式错误的 HTML、复杂的 JSON schema，并且在各种上下文长度上都表现出色。

这些模型解锁了此前在经济上根本不可行的工作负载，并让 web agent 更快、更准。

[Schematron-3B](https://huggingface.co/inference-net/Schematron-3B) 和 [Schematron-8B](https://huggingface.co/inference-net/Schematron-8B) 都是开源的，今天起可在 Hugging Face 上取到，也能通过我们的[无服务器 API](https://inference.net/models) 使用。

代码示例见我们的[文档](https://docs.inference.net/workhorse-models/schematron)和 [samples 仓库](https://github.com/context-labs/inference-samples/blob/main/examples/schematron-scrape-companies/schematron-scrape-companies.ipynb)。

## 结构化 Web 数据的难题

尽管如今最强的 LLM 在从凌乱 HTML 里抽取数据方面极其有效，但它们在现实世界的抓取工作流里往往不实用：要以可接受的准确率处理数百万个页面，得花上数万美元。

我们团队通过构建几十个抓取器和爬虫亲身经历过这一点，也切身感受到一种需要——一个更负担得起的 HTML 解析模型，同时不牺牲抽取质量。

我们构建 Schematron，是为了以生产工作负载划得来的价格给出前沿模型的准确率。监控竞争对手价格、聚合商品目录，或是构建研究 agent，全都要求从凌乱的 HTML 里抽取干净的、带类型的数据——Schematron 解决了这项任务，而且价格低到足以解锁新的用例。

## 认识 Schematron 家族

我们为 Schematron 训练了两个版本：准确率很高的 Schematron-8B，以及准确率略低一点但快得多的 Schematron-3B。

**Schematron-8B** 擅长复杂的抽取任务，能以出色的准确率处理错综复杂的嵌套 schema 和非常长的文档。当准确率最重要时，它就是你的首选。

**Schematron-3B** 在更简单的抽取任务上提供极高的性价比，用几百毫秒处理完一个标准网页，同时在常见用例上保持亮眼的准确率。

两个模型共享的核心能力：

- **128K token 上下文窗口**：用于处理长页面
- **严格 JSON 模式**：保证输出可解析、符合 schema，遵循度 100%

这些模型的质量足以匹敌前沿模型，而体积小得多、速度也快得多。我们用 Gemini 2.5 Pro 给抽取结果按 1-5 打分，5 分代表一次完美的抽取。选 Gemini 2.5 Pro 是因为它那出色的长上下文能力。

LLM-as-a-judge：各模型的平均质量得分

## 顶级的速度与成本

Schematron 的速度解锁了新的 agent 化用例，让 LLM 浏览和解析 web 的速度快上一个数量级。相比前沿模型降低 10 倍的延迟，同时还省下开发者时间与服务器资源，这对大规模爬取和抓取作业至关重要。

有些抓取/解析任务对时间极其敏感，比如为实时交易解析金融文档。在这类用例里，一个像 Schematron 这样快的模型能给你显著的优势。

各模型的平均延迟

或许更重要的是，Schematron 比使用一个前沿模型便宜得多。Schematron-8B 和 Schematron 3B 分别比 GPT-5 便宜 40 倍和 80 倍。这解锁了互联网规模的抓取作业——过去除了资金最雄厚的团队，谁都做不起。它也使得监控大批页面变得划算，尤其是那些依赖页面结构各异的外部站点的实时数据。

## 我们为什么要构建 Schematron

### 爬取/抓取 Web 是一项重 token 的活动

之所以构建 Schematron，是因为用一个 LLM 把一个 HTML 页面变成 JSON——这件每天被执行数十亿次的任务——实在太贵了。一个网站的原始 HTML 体量巨大，即便清洗过，平均每页也在 10k token 左右，而且可能远远超出这个数。

在 Schematron 之前，团队要么用大模型飞快地烧光预算，要么以糟糕的准确率做解析。我们希望 Schematron 能让更有野心的 web 爬取与解析项目成为可能，因为一个便宜到这种程度的模型，让人可以重新评估这些项目到底行不行得通。

### Web 搜索尤其低效

用 web 搜索给 LLM 做接地（grounding），可能取回 5-100 个相关页面。把这些页面的上下文全部传进去会贵到无法承受，但给 LLM 做接地又是必要的——因为加上 web 上下文之后，它们比只依赖 LLM 自身的知识要贴合事实得多。

### 小模型在专化任务上表现出色

与其用大型通用模型，一个专门为 JSON schema 抽取微调过的小模型效果好得多。我们不再为自己不需要的智能付费，而是把小模型里的全部参数都集中在这一个具体任务上。结果是 Schematron-8B 比 Gemini 2.5 Flash 更快、便宜 5 倍，准确率却一样。

## 用 Schematron 与 Web 搜索提升 LLM 的事实性

我们用 SimpleQA 来评测 Schematron 提升 web 搜索准确率的能力，SimpleQA 是一个考察事实性问答能力的基准。

### 方法

我们的测试流水线由四个阶段构成：

- **查询生成**：一个主 LLM（GPT-5 Nano 或 GPT-4.1）生成搜索查询，并定义一个数据抽取 schema
- **Web 搜索**：一个搜索服务商（SERP 或 Exa）执行这些查询并取回相关页面
- **结构化抽取**：Schematron-8B 按照该 schema 从取回的页面中抽取结构化的 JSON 数据
- **答案合成**：主 LLM 用抽取出的结构化数据生成最终答案

## 结果

SimpleQA 基准得分

在没有任何搜索增强的情况下，GPT-5 Nano 和 GPT-4.1 都很难正确回答大多数事实性问题。

引入 web 搜索之后，结果大幅改善。当我们加上 SERP 并用 Schematron-8B 做抽取，GPT-5 Nano 能答对大多数原本把它难住的问题。Exa 与 Schematron-8B 的组合把性能又往上推了一截，让 GPT-5 Nano 在五道题里能正确答出四道以上。

以 GPT-4.1 作为基础模型时，同样的 Exa-Schematron 流水线达到了接近专家水准的表现，说明这些收益会随着基础模型的质量一同放大。

## 关键发现

在作为抽取模型的正面对比中，Schematron-8B 始终强于 Gemini-2.5-Flash。哪怕更小的 Schematron-3B 配上 Exa 也被证明非常有效，这说明结构化抽取带来的事实性提升并不取决于模型大小。

这些发现揭示了结构化抽取如何改变 LLM 使用 web 搜索的经济账。Schematron 让 web 增强后的事实性在经济上变得可行，因为它处理的是结构化的抽取结果而不是整个网页——每次查询避开了数万个 token。

## 我们是怎么构建 Schematron 的

为了造出真正同时理解 HTML 结构与 JSON schema 的模型，我们起步于汇集一个庞大的语料库：来自 Common Crawl 的 100 万个真实世界网页。我们通过对网页做聚类来构建一个合成的 schema 数据集，用一组组的网站摘要去生成那些可能用得上的 schema，本质上是在模拟一个反向的搜索过程。

这种做法与真实世界的使用方式相映照：你定义一次 schema，然后在多个相似页面上反复使用它。我们以前沿模型作为老师，在各种不同的领域里创造了数十万个抽取样例。

我们用课程学习（curriculum learning）逐步在更长的上下文长度上训练模型做抽取，在整个训练过程中一点点让它接触越来越复杂的文档。这保证了即便到了 128K token 的上限，表现依然稳定。得到的是真正理解 schema 与 HTML 结构之间关系的模型，即使面对长文档也一样。

## 为开发者而造

使用 Schematron 模型的方式是：用 Pydantic、Zod 或 JSON Schema 定义你的 schema，传入原始 HTML，取回经过校验、类型安全的数据，可直接用在你的应用里。

从任意电商页面抽取商品信息就这么简单：

```
import os
from pydantic import BaseModel, Field
from openai import OpenAI

# 1) Define your schema (nested data and lists are supported)

class Product(BaseModel):
    name: str
    price: float = Field(
        ..., description=(
            "Primary price of the product."
        )
    )
    specs: dict = Field(
        default_factory=dict,
        description="Specs of the product.",
    )
    tags: list[str] = Field(
        default_factory=list,
        description="Tags assigned of the product.",
    )

# 2) Messy HTML (could be the full page; trim to the relevant region when possible)
html = """
<div id="item">
    <h2 class="title">MacBook Pro M3</h2>
    <p>Price: <b>$2,499.99</b> USD</p>
    <ul info>
    <li>RAM: 16GB</li>
    <li>Storage: 512GB SSD</li>
    </ul>
    <span class="tag">laptop</span>
    <span class="tag">professional</span>
    <span class="tag">macbook</span>
    <span class="tag">apple</span>
</div>
"""

# 3) Client setup
client = OpenAI(
    base_url="https://api.inference.net/v1",
    api_key=os.environ.get("INFERENCE_API_KEY"),
)

# 4) Responses API extraction (typed parsing)
response = client.chat.completions.parse(
    model="inference-net/schematron-8b",
    messages=[
        {"role": "user", "content": html},
    ],
    response_format=Product,
)

print(response.choices[0].message.content)
```

## 开源与 API 访问

我们相信，像 Schematron 这样的专用模型代表了 AI 应用的未来——未来的应用将建立在精心训练的、擅长特定任务的小模型之上，而不是那些试图无所不能的昂贵通用模型。

这就是我们让 Schematron 通过多种渠道提供的原因：

- **[Inference.net](http://inference.net/)**** API**：用我们托管的 API 立刻开始抽取，只为你用到的部分付费，没有任何前期成本。
- **开源**：[Schematron-3B](https://huggingface.co/inference-net/Schematron-3B) 和 [Schematron-8B](https://huggingface.co/inference-net/Schematron-8B) 都以宽松许可证发布在 Hugging Face 上。把它们部署在你自己的基础设施上、为你的特定领域做微调，或者直接集成进你的应用。
- **批处理**：我们的 [Batch](https://docs.inference.net/features/batch-api#batch-api) 和[异步 API](https://docs.inference.net/features/asynchronous-inference/overview#getting-started) 能在大规模抽取上省下可观的成本。

对于爬取，我们推荐一条 webhook 工作流：提交一个异步请求，结果会被推送到你的 [webhook](https://docs.inference.net/features/asynchronous-inference/webhooks/getting-started-with-webhooks)（通常在几秒之内），由你 upsert 进数据库，同时保留与批处理同等的节省。
