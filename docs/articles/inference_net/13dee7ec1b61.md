过去几个月，我们一直在推理路由栈上下功夫，把重心越来越集中在一个用 Elixir 编写的自定义请求路由器上。这是系列博客的第一篇，讲我们如何把规模做到每天数万亿 token，以及其中的经验。本文聚焦分词器：仅靠分词这一环，我们就把 SGLang 提速 33 倍、把 vLLM 提速 12 倍。

## 分词到底为什么重要？

![推理请求的时间线：分词、prefill，然后每一步解码一个 token，TTFT 标在第一个解码步骤之后](https://inference.net/assets/request-timeline-Dr9A6UVv.png)

处理一个推理请求时，在拿到第一个输出 token 之前要经过 4 个主要阶段：分词、Routing、Prefill 和 Decode。

我们的路由层依据输入上下文长度做决策。要知道输入有多长，就得先做分词，或者用个粗略估算（比如每四个输入字符算一个 token）。请求路由出去之后，我们用某个主流开源推理引擎做 prefill 和 decode。这些引擎都支持两种输入方式：接受 chat completion，或者接受原始 token ID。过去我们依赖开源推理引擎去做分词、prefill，最后才开始 decode。

![旧热路径示意图：请求经过一个 Elixir 节点完成分词并挑选实例，随后完整的 JSON 被发到 vLLM 或 SGLang 实例，由它再分一次词](https://inference.net/assets/old-hot-path-CKjXcuQL.png)

我们过去的路由方式：把完整的 JSON 载荷发给引擎

我们的路由层对请求做分词，估算这个请求会占用多少 token。限制输入上下文长度能让推理引擎处理得更快，所以知道请求长度，就可以把短请求路由到“短池”，相比按模型完整上下文长度配置的池子，性能更好。生产热路径上用的分词器是 [Toks](https://github.com/actual-computer/toks)（来自 Actual, Inc.），但有个前提：它不渲染 chat 模板，而且是用 C 写的，C 并不原生在我们的路由栈里，接入得额外做工作。

过去几个月需求增长，我们把开源推理引擎推到了极限，现在维护着 vLLM 和 SGLang 的内部 fork，为提高效率打了补丁。但我们仍然撞上根本性的天花板：它们的前端目前是 Python 写的，单线程解释型语言，意味着变慢、GIL（Global Interpreter Lock，全局解释器锁）争用等等，这些都会影响 TTFT（time to first token，首个 token 时间）。与其发送原始 JSON 请求，不如直接给引擎发原始 token ID，把分词在 Python 进程里执行的开销省掉！

## 我们为什么更快？

我们一直是 Elixir 和 BEAM 的支持者，去年十二月起就在生产环境的 Router 上使用它。Ericsson 的 Open Telecom Platform（OTP）是我们能扛住每天数亿请求的根本原因之一。但它远不够快，赢不了这里其他分词器，所以我们决定借助 [Native Implemented Functions（NIFs）](https://www.erlang.org/doc/system/nif.html)，把 Rust、C 和 Assembly 纳入 BEAM 的监督树。

![ChatTokenizer 内部结构示意图，横跨 Elixir、Rust 和 C 三条通道：请求处理器、拆分图像、构建 prompt、segment 缓存、跨 vCPU 编码、展开图像、token ID](https://inference.net/assets/tokenizer-internals-DXiylxBU.png)

分词器的核心仍然是 Actual 的 `toks`，它用优化过的汇编产出与 Hugging Face tokenizers 一一对应的 token ID，速度是后者的 13-151 倍。但 Toks 还不支持渲染 chat 模板和图像，也不支持我们内部需要的其他一些功能。于是我们在它外面搭了一个 Rust 加 Elixir 的配套库，来处理这些功能以及更多。

elixir

```
{:ok, tok} =
  ChatTokenizer.load("moonshotai/Kimi-K3.1-Pro", revision: "6d0a0202956796543364d666ab19c6ad1a494ee1")

compiled =
  ChatTokenizer.compile(tok,
    # varies by model
    engine: :sglang,

    # usually passed to the engines
    default_chat_template_kwargs: %{"reasoning_effort" => "high"},
  )
```

### 主要改进

下面每项改进后文都会细说，为了不让这篇文章长得离谱，先给出几个大改进的 tl;dr。

- Deepseek v4.1 Flash 和 Kimi K3.1 Pro 的 chat 模板移植到了原生 Rust，Jinja/Python 实现留作参照，并用单元测试验证
- 删掉了 Deepseek 编码器里的一个二次循环，Kimi 重复的模板片段在单次请求内做了记忆化
- token ID 以 little-endian u32 的二进制形式从 C/Rust 传给 Elixir，而不是用列表传递，避免来回传列表的开销
- 内联 base64 图像用 SIMD 字节扫描定位，作为指向原始请求的子二进制交给 Rust，而不是复制出来
- 我们避免反复解析整个 JSON body，只提取引擎真正需要的字段

### 读图像元数据，而不是读整张图

agent 流量里到处都是图像。一个 1M token、带 8 张内联图像的请求，JSON 大约 30MB，其中几乎全是 base64。朴素做法（我们最初就是这么干的）是解析整个 body，把每个图像字符串复制出来，base64 解码，再打开图像，只为了知道它有多大——因为引擎要算出插入多少个图像占位 token，只需要这一个信息。

所以我们不再这么做了：

- 在解析任何内容之前，先对原始请求做一次 SIMD 字节扫描（memchr），找出长度超过 4KiB 的 `"data:` 字符串。
- 每张图像以子二进制形式进入 Rust——BEAM 用这种方式指向原始请求的二进制，而不是复制。在 JSON 里，我们把图像换成一个极小的标记（`data:x-chat-tokenizer-ref,0`），于是这个 30MB 的请求实际只按几 MB 文本去解析。
- 我们趁它还是 base64 的时候直接从 PNG/GIF/WebP/JPEG 头部读出宽高，一个像素都不解码（引擎会应用 EXIF 方向的，我们也照做）。
- 然后套用模型自己的 resize 规则（Deepseek v4.1、Kimi K3、Qwen-VL 等），把这个尺寸换算成引擎本会生成的确切图像 token 数。

![柱状图：约 1M token、带 8 张图像的 DeepSeek v4.1 请求上，zero-copy 图像优化前后、SGLang gateway、SGLang 和 vLLM 的每秒请求数](https://inference.net/assets/zero-copy-images-CPr_Jr3u.png)

Deepseek v4.1，约 1M token 加 8 张内联图像，8 个 vCPU 下的 req/s。zero-copy 图像优化前与优化后，对比 SGLang gateway 以及 vLLM、SGLang 自己的预处理。SGLang gateway 跳过图像展开，所以它的 ID 与引擎对不上。

这一步让百万 token 请求从 22.5 req/s 提到 167 req/s，单核上的单次请求从 240ms 降到 28ms。作为对比，vLLM 和 SGLang 自己的预处理处理同样的请求只有 1.3 和 1.6 req/s，大约每次 2-3 秒。

### 只解析你需要的那部分 JSON

另一件让我们意外的事，是光读一个请求、随后又把它大部分丢掉，竟然花了那么多时间：

- `serde_json` 用标量循环对每个字符串做 UTF-8 校验，这部分大约占整个 chat 请求的十分之一。我们改成先对整个 body 做一次 SIMD UTF-8 校验，然后当作已验证的字符串来解析。
- chat 请求大多是很小的对象（一条 message、一个 content part、一个 tool call），键只有那么几个。对每个键做哈希是杀鸡用牛刀，所以键数在 8 个以内的，我们直接线性扫。
- 我们只取引擎会读的字段，并在 Rust 里套用引擎自己的请求规则（比如 vLLM 如何预解析 tool call 参数），这样 body 不会被解析两次，也不会重新序列化。
- 送进 `toks` 的文本同样做 SIMD UTF-8 校验。标准库在 CJK 密集的 prompt 上大约 3GB/s，这占了 `toks` 整个编码时间的五分之一。

也不是什么都奏效。我们试过并行 JSON 解析和并行模板渲染，两个都拆掉了——唤醒线程的代价超过了它们省下的活。

## 高负载下的表现

测吞吐量当然好看，但你总能把数字做得比生产环境里高好几倍。在写这个库的过程中，我们还测了负载下长尾怎么长，问自己一个问题：当一台 serving 实例越来越忙，那些慢请求究竟有多慢？

![垂直须线图：ChatTokenizer 与 SGLang gateway 在 DeepSeek v4.1 和 Kimi K3.1 上按 prompt 大小划分的 p50 与 p99 延迟](https://inference.net/assets/latency-under-load-DbziloSv.png)

8 个 vCPU 全部占满时每请求的延迟，我们对比 SGLang gateway。圆点是 p50，端帽是 p99。每个 prompt 大小各有自己的轴。越低越好。

从 8K 到 160K token 的 prompt，在两个模型上，我们的 p99 都低于 SGLang gateway 的中位数。Deepseek 上约 37K token 时，我们的 p99 是 2.6ms，而他们的 p50 是 2.9ms（他们的 p99 是 15.9ms）。这要归功于 NIFs 跑在 dirty CPU scheduler 上：一个百万 token 的请求不会卡住 BEAM 的其余部分，分词器在啃大请求或大量请求时，路由器照样能继续路由。

## 与引擎自身相比如何？

我们把 vLLM 和 SGLang 自己的请求预处理（应用 chat 模板、解析 body、再产出 token）拿过来，在同一进程内与我们的实现做基准对比。

![柱状图：ChatTokenizer、vLLM 和 SGLang 在 DeepSeek v4.1 和 Kimi K3.1 上按 prompt 大小划分的每秒请求数](https://inference.net/assets/vs-engine-preprocessing-Dgzpx28J.png)

ChatTokenizer 对比 vLLM 和 SGLang 自身预处理的按 prompt 大小划分的 req/s，进程内，8 个 vCPU。每个 prompt 大小各有自己的轴。越高越好。

在两个模型的每一个尺寸上，我们都快 53-181 倍。既然我们现在发给推理引擎的是原始 token ID 而不是原始 JSON，我们想知道这会给推理引擎带来什么影响。

![折线图：随着并发客户端增加，SGLang 和 vLLM HTTP 服务器的每秒请求数，分别使用我们的 token ID 和原始 chat](https://inference.net/assets/engine-servers-with-our-ids-DE7swN_4.png)

Kimi K3.1，约 37K token 的 prompt，4 个 API 进程下引擎 HTTP 服务器吞吐量随并发上升的变化。原始 chat 对比我们的 token ID。每个引擎各有自己的轴。越高越好。

发送 ID 让 SGLang 从 31 req/s 变成 1,031 req/s（33 倍），让 vLLM 从 43 变成 505 req/s（12 倍）。用原始 chat 时，每个 API 服务器进程大约到一个核就压平了，因为分词是在该进程的 GIL 下用 Python 跑的。在 8 vCPU 的机器上，开到 4 个进程也只让 vLLM 从 13 提到 43 req/s；而发我们的 ID，同样的 4 个进程能干到 505。这就是本文开头说的热路径变化：在路由器里分词一次，推理引擎就再也不必分词了。

### 分词的准确性

我们分词器的一条核心要求，是输出与引擎完全一致。如果我们发出的 token ID 和引擎从原始 chat 本会产出的不完全一样，模型看到的 prompt 就和客户发的不是同一个，可能让模型表现得很怪——我们深挖这件事时发现，引擎之外的大多数分词器根本做不到一致。

麻烦之处在于，分词不只是把文本过一遍分词器。每个引擎会先渲染 chat 模板、套用自己的请求规则；每个引擎都有自己的怪癖，产出的 token 略有不同。比如 vLLM 会解析 tool call 参数再重新序列化，模型看到的 JSON 与客户端发的并非逐字节相同。所以我们按请求要发往的引擎采用不同的分词方式，确保 token 对该引擎是正确的。

![一个 tool call 的 token 框：vLLM 的参考 ID、ChatTokenizer 完全相同的 ID，以及另一个把两个 token 合并、结果不匹配的分词器](https://inference.net/assets/what-accurate-means-DKqHJEJ8.png)

我们说的“准确”是什么意思。vLLM 解析 tool call 参数，chat 模板重新序列化时会在冒号后加一个空格，所以模型看到的 prompt 不是客户端发出的字符串。一个直接渲染原始参数字符串的分词器，产出的 token ID 就不一样。只有每个 ID 都相同、顺序也相同，我们才把这个请求算作匹配。示例仅作说明。

![散点图：ChatTokenizer、SGLang gateway、Baseten、NVIDIA Dynamo、HF transformers 和 vLLM 的 token ID 匹配 vLLM 的请求占比与每秒请求数的关系](https://inference.net/assets/accuracy-vs-throughput-DDKWNOej.png)

Deepseek v4.1，约 8K token 的 prompt，8 个 vCPU。token ID 与 vLLM 完全一致的请求占比，对比 req/s。越靠右上越好。

每项基准测试里，我们都把 token 与 vLLM 的结果比对：两个模型、每个 prompt 尺寸下，100% 的请求都是逐一匹配。其他库在短对话上表现尚可，但请求里一有 tool call 和更长的对话就开始漂移。约 8K token 时，SGLang gateway 只匹配 16%（这在预期之内，SGLang 渲染模板的方式与 vLLM 不同），NVIDIA Dynamo 73%，HF transformers 96%。带图像的约 1M token 请求上，其他所有库都是 0%；而在 Kimi K3.1 上，HF transformers 渲染出的 prompt 完全不对，因为它忽略了 `reasoning_effort`。

### 与其他分词器的补充对比

Baseten 写过一篇博客，讲他们如何用自己的库 [`basetenkenizer`](https://github.com/basetenlabs/basetenkenizer) 加速 Kimi 分词，所以我们想在 Kimi K3.1 上把两个库比一比。他们的 Rust 分词器渲染不了 Kimi 的 chat 模板，所以生产路径是 Python 渲染、Rust 编码。为了公平，我们只比编码这一步，在他们自己的 API 上，让两个库编码完全相同的预渲染 Kimi K3.1 片段。

![柱状图：ChatTokenizer 与 basetenkenizer（固定线程池和默认线程池两种设置）在 Kimi K3.1 上仅编码的每秒请求数，按 prompt 大小划分](https://inference.net/assets/encode-only-vs-basetenkenizer-DRelix1i.png)

仅编码，Kimi K3.1。ChatTokenizer 与 basetenkenizer 的 encode_segments 在相同预渲染片段上的 req/s，8 个 worker 跑在 8 个 vCPU 上。basetenkenizer 展示了每 worker 固定 1 核（它的更快设置）和使用默认线程池两种情况。每个 prompt 大小各有自己的轴。

8 个 worker 下，从约 200 到约 1.1M token，我们比他们最快的设置快 1.9-5.7 倍。

## agentic 工作负载与缓存

我们流量中有很大一部分是 agentic 的，每一轮都会把整个对话重发一遍。于是我们重放了 8 个 agent 对话，每个 213 轮，每轮从 2K 到 160K token 不等。

![柱状图：多轮 agent 重放的每秒请求数，各库的冷启动与开启 segment 缓存两种情况](https://inference.net/assets/multi-turn-agent-replay-Ct-PY_84.png)

多轮 agent 重放，8 个 vCPU 下的 req/s。实心是冷启动，空心是开启我们的 segment 缓存。

segment 缓存是内容寻址的，在所有 BEAM 进程之间共享，所以对话的一段一旦编码过，就永远不会再编码。大约到第 30 轮之后，98-99% 的 token 直接来自缓存。收益“只有”1.2-1.8 倍，因为即使整轮全命中缓存，仍然要解析请求、渲染整个对话，而这每一轮都在增长，依旧是我们想解决的瓶颈。

- 每张图都是标注的 Deepseek v4.1 或 Kimi K3.1，8 个 vCPU。
