# 混合注意力模型是 SLM 的未来

A

Amar Singh

## 引言

Specialized Language Models 之所以有吸引力的一个主要原因，是相对于 GPT-5 这类大型通用模型，它们的参数数量很低。更小的模型每秒能产出更多 token，每个 token 所需的算力比更大的模型更少，最终带来更低的运营成本，以及在特定任务上更好的成本-性能比。

虽然降低参数数量可以改善大规模运行 LLM 的经济性，但一个模型要多小仍然对特定任务上的有监督微调（Supervised Fine-Tuning，SFT）有用，这件事是有极限的——一个 1B 参数的模型也许能以 8B 参数模型 10 倍的速度产出 token，但它不太可能保持同样的准确率。

简单说，一个 1B 参数的模型也许很快，但它也会……相当迟钝。

那么，除了直接用一个更小的模型之外，我们还能怎样提升某个特定任务的总吞吐量？答案是混合注意力（Hybrid-Attention）。

## 混合注意力

在最近的一个项目里，我们需要把 HTML-to-JSON 转换任务的总 token 吞吐量最大化。HTML 文档往往很长（轻松就 100k+ token），即便是 8B 参数的模型也很难给出我们想要的吞吐量。我们把各种路子都试了一遍：更小的模型、MoE、推理引擎优化，甚至是在 AMD 上构建。这些路径都没有给出我们需要的性能。

一次巧合的幸运之下，我碰到了 NVIDIA 的 [Nemotron Nano v2](https://huggingface.co/nvidia/NVIDIA-Nemotron-Nano-9B-v2)，它声称相比任何其他类型的模型都大幅提升了吞吐量。它是一个混合推理模型，尽管把它适配到我们的训练流程需要下一番苦功，但回报完全对得起这份投入。

与只依赖 self-attention 机制的传统 transformer 不同，Nemotron Nano v2 把 [Mamba-2](https://huggingface.co/docs/transformers/en/model_doc/mamba2) 状态空间层（约 92% 的层）与 Transformer self-attention 块（约 8% 的层）混合在一起。这种做法利用了 Mamba-2 在序列处理上的高效，同时在需要全局上下文混合的地方保留 transformer 块。最终得到的模型既保持了传统 transformer 的推理质量，又大幅降低了计算开销。

Nemotron Nano v2 原本的训练过程也很有意思。首先，一个 12B 参数的基础模型用 FP8 recipe 在 20 万亿 token 上完成训练，然后上下文窗口被扩展到 128k。随后模型通过剪枝和蒸馏被压缩到 9B 参数，同时保留了 56 层以及混合层的排布模式。这个架构不含位置嵌入，并全程使用 RMSNorm。这一设计选择直接应对了语言建模里最大的挑战之一：KV cache 的显存和计算量随序列长度呈平方级增长。

为了让 Nemotron Nano v2 在长上下文应用里真正发挥光彩，我们实现了若干补丁，确保能把长上下文训练塞进 GPU 显存。具体来说，使用 ring attention 让我们可以处理通常放不进显存的更长序列，办法是把计算分布到多台设备上。尽管他们的训练过程里用到了它，我们还是得调整它，让它能在 Huggingface Trainer 生态里工作，尤其是要适配 Tri Dao 的 Flash Attention 包。结果是，我们能够对上下文长度高达 500K token 的请求做微调。

为了验证这个模型是否真的带来了差别，我们在一个高要求的科学摘要任务上，对 Nemotron Nano v2 和 Qwen 3 14B 做了全面的对比。在一个规模很大、结构化的科学摘要任务上微调之后，两个模型在一套 ensemble LLM-as-a-judge 评估下都表现得极为出色。Qwen 3 14B 的平均摘要质量略高一些，但 Nemotron Nano v2 紧随其后，稳稳落在强而可用于生产的摘要模型区间之内。一个配套的问答基准也呈现出类似的结果。两个模型都聚拢在强劲的商业基线附近。

Nemotron 真正胜过一切的地方是它的吞吐量。在一套相同的 8×H200 配置上，使用 tensor parallelism 设为 8 的 vLLM，Nemotron 给出的端到端吞吐量比 Qwen 3 14B 高约 2.25 倍。具体数字讲述了一个很有说服力的故事：Nemotron 达到每秒 0.97 个请求，而 Qwen 是每秒 0.43；输出解码吞吐为每秒 4,880.76 token，相比之下 Qwen 是每秒 2,588.30。输入 prefill token 方面，Nemotron 达到每秒 16,943.69 token，而 Qwen 是每秒 7,516.54。

在单请求场景下，Nemotron 的处理速度是每秒 76.17 token，而 Qwen 是每秒 39.59。虽然这些数字都比论文里的吞吐量数字（声称在 8k 输入/16k 输出的场景下 tokens/s 高出 6 倍）略低一些，但它仍然远超我们试过的其他任何优化。

当所有人都在关注绝对数值时，有一个关键指标我认为是 Nemotron Nano 目前处于领先位置的：吞吐量与成本之比。微调模型的整套权衡，都是围绕改善成本、吞吐量和延迟，同时尽力维持质量。虽然在同一个数据集上它的微调效果比 Qwen 稍差一些，但它靠喷涌般的 token 输出把这点补了回来。在你需要训练一个模型去处理海量数据集的场合（我们很快就会宣布相关内容），这个模型应该是值得考虑的宝贵资产。注：完整的方法论、数据集构成以及详细的评估拆解，将在未来某篇博客里分享。
