## 引言

AI 产品通常从强大的前沿模型起步。早期原型效果不错。准确率很高。开发推进很快。但随着用量增长，另一个问题出现了。运行这些模型的成本迅速上升，于是你会发现，那些成就了创新的工具，可能变成把它规模化的最大障碍。

你面对的是一组熟悉的取舍：

- **质量与成本： **高质量的前沿模型能给出很强的结果，但规模化之后运行起来很贵。
- **成本与准确率：**更小的通用模型能降低成本，却常常达不到生产环境的质量要求。
- **便利与控制： **基于 API 的方案让集成更简单，却限制了对性能、延迟和模型演进的掌控。

结果是质量、成本与运营掌控之间一个很难的平衡。

[Inference.net](http://inference.net/) 就是为解决这个问题而创建的。我们不依赖通用模型，而是为你的具体工作负载量身打造专用 AI 模型。这些模型用你的真实数据训练，并针对你的应用所执行的那些确切任务做过优化。

这套做法能让你：

- 保持生产级的准确率
- 大幅降低推理成本
- 完全掌控模型表现与后续开发
- 可预期地扩展 AI 系统

[NVIDIA Nemotron 开放模型](https://developer.nvidia.com/nemotron#:~:text=Tutorials-,NVIDIA%20Nemotron%20Models,-Nemotron%20models%20are)和 [NVIDIA NeMo ](https://github.com/NVIDIA-NeMo/)框架这类底层技术，提供了让这套做法真正可行的基础。

本文说明这套系统如何运作，并展示两个真实部署如何在保持高精度的同时取得 25 倍和 50 倍的成本下降。

## Inference.net 的做法：为目标用途而造的模型

许多生产 AI 系统只执行相对窄的一批任务——从文档里抽取结构化数据、总结海量文本、给内容分类，或生成结构化输出。但这些工作负载往往由那些为了解决上千种不同问题而设计的巨型通用模型来驱动。这些模型虽然强大，却为应用可能永远不会用到的能力承担了可观的计算开销。结果是模型的广度与任务的专用性之间错配，带来更高的成本、不必要的复杂度，以及随着用量规模化而越来越显眼的低效。

Inference.net 的应对方式，是为你所做的那件事专门设计模型。每个项目通常遵循一个结构化的流程：

- **定义任务与评估标准** - 分析真实的生产数据，确立清晰的成功指标，例如准确率阈值、幻觉率或分类表现。
- **训练一个专用模型 **- 用你的数据对一个基础模型做精调，并针对你工作负载的确切输入与输出模式做优化。
- **部署生产基础设施** - 把模型部署在经过优化的 GPU 基础设施上，并通过 OpenAI 兼容的 API 暴露出来，让你在不必重建应用栈的情况下完成集成。

得到的是一个把一件事做到极好、而不是在很多件事上做到还不错的模型。

### 为什么模型架构重要

训练一个专用模型时，底层架构会直接影响准确率和成本。Inference.net 常在 [Nemotron 开放模型](https://developer.nvidia.com/nemotron#:~:text=Tutorials-,NVIDIA%20Nemotron%20Models,-Nemotron%20models%20are)之上构建，它把多种架构技术结合起来，在建模能力与高效推理之间取得平衡。这些模型整合了：

- **序列高效的处理层 **，用来降低计算开销
- **注意力机制**，保留捕捉文本中长距离关系的能力
- **稠密表示层**，支持针对领域特有模式做精调

这种平衡让模型能有效地学习你的专用任务、保持很强的推理能力，并在生产环境里高效运行。对高吞吐的工作负载来说，这些特性直接影响运营的经济账。

### 在生产规模上训练专用模型

在生产规模上打造按具体用例定制的模型，需要一套训练框架，能处理跨大型 GPU 集群的分布式训练、海量数据集和自定义评估流水线，同时不必逼着你成为底层并行化和基础设施复杂性的专家。

Inferenc.net 用 [NeMo ](https://github.com/NVIDIA-NeMo/)框架和 [Megatron-Bridge](https://github.com/NVIDIA-NeMo/Megatron-Bridge) 开源库——它是 NeMo 框架的一部分——来填补这一空缺。Megatron Bridge 提供开箱即用的内置训练循环，同时暴露干净的扩展点，以满足每个项目所需的定制。对更大的模型，尤其是超过 30B 参数的模型和混合专家（MoE）模型，它能接入 [Megatron-LM](https://github.com/NVIDIA/Megatron-LM) 的分布式训练能力，包括张量并行、流水线并行和专家并行。这些能力对于高效利用大型 GPU 集群、控制训练时间和成本至关重要。

如今，这套技术栈支撑着 Inference.net 各个客户工作负载里每周数十个训练任务。它处理的范围从单节点上的小型监督精调运行，到跨多节点 GPU 集群的大规模分布式训练。正是它让我们能在几周而不是几个月内从用例定义走到生产部署，而不需要你自己建 GPU 基础设施或招聘 ML 工程团队。

## 每月 2 万亿 token 的企业数据抽取

我们的一位客户运营着一个每天处理数百万条 AI 生成响应的平台。他们的核心工作负载是结构化数据抽取——从半结构化文本里识别实体、引用与分类，用来驱动分析看板、竞争情报和业绩报告。

在每月处理约 2 万亿 token 的量级上，准确率至关重要。漏掉一个实体、或凭空造出一条引用，都会顺着下游系统传导出去，直接变成可衡量的业务影响。

### 在不破坏经济性的前提下保持准确率

客户的抽取流水线有严格的性能要求。它需要在实体识别上保持高 F1 分数、在引用上保持接近零的幻觉率、在分类上有可靠的精确匹配表现——同时还要每月处理约 2 万亿 token。

最初有一个前沿 API 模型满足了这些质量要求。但在这个规模上，按 token 计价很快变得难以持续。用量增长，AI 成本也跟着增长，产品增长就变成了一个利润率问题。

换成更小的通用模型来降成本的尝试又制造了新的风险。实体被漏掉，引用被编造，分类准确率跌到可接受阈值以下。系统对下游的分析和报告变得不可靠。这是很多组织都会遇到的一种循环：先用一个强大的模型把质量做出来，然后为了扛住账单一点点把智能换掉。

客户需要打破这个循环——守住自己的准确率阈值，又不付前沿模型的价格，同时取得对自家 AI 系统的长期掌控。

### 解决方案：一个专用语言模型

我们与客户协作，从用例定义推进到生产部署，遵循我们在所有客户项目中都会使用的结构化流程：

**1. 定义任务与评估框架**

第一步是深入理解这个工作负载。我们没有依赖样例输入，而是分析了大规模的真实生产流量，捕捉边界情形、格式变体与失效模式的完整分布。

我们与客户的工程团队紧密协作，构建了一份黄金评估数据集，并为 F1 分数、精确匹配准确率与幻觉率定义了清晰的性能阈值。这些指标在任何模型训练开始之前就先确立了客观的通过／不通过标准。

**2. 训练并优化模型**

随后我们用 Inference.net 的内部工具，以及经由 NeMo Megatron Bridge 的前沿模型蒸馏，制作了约 500,000 条高质量训练样本。

我们评估了若干基础架构，最终选定 Nemotron 2 Nano，它在精调容量与推理吞吐之间给出了很强的平衡。之后又在客户的生产数据上通过监督训练对该模型做进一步精调，对照评估框架反复迭代，直到它稳定达到所需的质量目标。

**3. 在生产环境部署**

最终模型经由 Inference.net 的自定义推理栈部署在 CoreWeave 的 GPU 上，暴露出可直接接入客户现有流水线的 OpenAI 兼容 API。

从客户的角度看，部署不需要采购 GPU、不需要招聘 ML 人员、也没有 DevOps 负担。这套系统只是替换了此前的 API 端点，却带来了明显更好的经济性。

### 成效：以一小部分成本拿到前沿水平的准确率

下表把为该客户工作负载打造的专用模型的表现，与他们流水线中此前测过的两个通用模型做了对比：

| 指标 | 专用 Nemotron 模型 | GPT-5（参考） | GPT-4o-mini（参考） |
| --- | --- | --- | --- |
| F1 分数 | 0.809 | 0.825 | 0.722 |
| 精确匹配 | 0.428 | 0.455 | 0.308 |
| 幻觉率 | 可忽略 | 可忽略 | 频繁 |
| **相对成本** | **1x** | **25x** | **~3x** |

该专用模型取得 0.809 的 F1 分数，达到了客户的生产质量阈值，同时保持可忽略的幻觉率。它可靠地抽取实体与引用，没有引入会传导进下游分析的误差。

作为参考，GPT-5 在同一评估集上得到 0.825 的 Fi 分数——只高出很小一点——尽管它是一个明显更大、为支持广泛任务而设计的通用模型。这个 9B 的专用模型把 F1 差距缩小到了 2 个百分点以内，同时它是为单一工作负载优化的。

客户此前测过 GPT-4o-mini 作为省成本的替代方案，它取得 0.722 的 F1 分数，但频繁引入幻觉，因此远低于生产所需的可靠性阈值。

在每月处理约 2 万亿 token 的量级上，推理成本降到了此前支出的不到 4%，即**降低 25 倍**。

同样重要的是，客户如今拥有自己的模型权重、评估框架和部署环境，不再受制于外部 API 的变更、速率限制或下线时间表。

## 案例研究：用不到 10 万美元处理 1 亿篇研究论文

Inference.net 把同样的做法用在了一项与 LAION 合作的开放科学计划 [Project OSSAS](https://inference.net/blog/project-aella) 上。该项目的目标是通过把大量学术论文转换成 AI 生成的结构化摘要，让世界上的科学知识更容易获取。

### 挑战：让大规模科学知识变得可获取

项目的范围很宏大：把 1 亿篇研究论文处理成结构化、可检索的摘要。守住质量至关重要。摘要既要保留原论文的事实内容，又要保持简洁、对下游分析有用。

两项指标定义了成功：

- **问答准确率，**衡量摘要是否保住了论文的关键事实
- **LLM-as-Judge 评估**，衡量摘要的整体质量

按前沿 API 的定价，处理整个语料要花费超过 500 万美元——远不是一个非营利计划所能支撑的。

要让项目可行，团队需要一种既能保持事实准确、又能大幅降低每份文档处理成本的办法，而不是只去抽样一小部分研究论文。

### 解决方案：训练一个专用摘要模型

Inference.net 打造了一个为科学文献设计的任务专用摘要模型。团队在一个由 110,000 篇研究论文与来自前沿模型的高质量摘要配对整理出的精选数据集上，精调了 Nemotron 2 Nano 12B。这套做法让专用模型学到有效的摘要模式，同时受益于为高效推理优化过的架构。

得到的模型——OSSAS-Nemotron-12B——使用 vLLM 部署在 8xH200 的 GPU 节点上，使系统能够处理全部 1 亿篇论文的语料。

### 成效：以一小部分成本拿到前沿水平的准确率

下表展示该专用模型的表现，以前沿模型 GPT-5 作为参考。

| 指标 | OSSAS-Nemotron-12B | GPT-5（参考） |
| --- | --- | --- |
| LLM-as-Judge 分数 | 4.25 / 5 | 4.85 / 5 |
| 问答准确率 | 73.9% | 74.6% |
| **1 亿篇论文的成本** | **< $100,000** | **$5M+** |

在问答准确率——与事实可靠性最直接挂钩的那项指标——上，该专用模型得到 73.9%，比作为参考的前沿模型 GPT-5 低不到 1 个百分点。

尽管 LLM-as-Judge 分数显示出更大的差距——4.25 对 4.85（满分 5）——但结果确认了摘要保住了研究发现与分析所需的关键信息。

经济影响显著。每篇论文的处理成本降到 0.001 美元以下，而使用前沿 API 则超过 0.05 美元。

这次 50 倍的成本下降，把一个本要花费 500 万美元以上的项目变成了一项 10 万美元以下的工程，使得处理整个语料在经济上变得可行，而不是只抽一个小得多的子集。

因此，这个项目在守住研究应用所需的事实可靠性的同时，打开了大规模获取科学知识的通道。

## 打法手册：专用模型何时占优

两个部署都遵循了同一个核心模式。在每一个案例中，经济优势都不是出发点——它们是技术路径的直接结果。

当三个条件同时具备时，这套打法的效果特别好。

**1. 清晰定义的任务与评估标准**

当任务能被精确定义和度量时，按用例定制的模型最有效。团队必须能够清楚说明「好」长什么样，并用客观指标来评估模型表现。

在企业案例里，这意味着在训练开始前定义 F1 分数、精确匹配准确率与幻觉率的阈值。在研究案例里，评估框架依赖问答准确率和经人工校准的质量分数。

这种严格程度让这套做法真正可行。模型开发变成一个由可测量目标引导的迭代过程，而不是靠主观判断。

**2. 高处理量**

在规模上，专用模型变得格外有说服力。当系统处理数十亿或数万亿 token 时，效率上哪怕很小的改进都能转化成可观的成本下降。

在两个案例研究中，工作负载的量级——一个是每月 2 万亿 token，另一个是 1 亿份文档——让训练与基础设施的固定成本可以被巨量的使用摊薄。

在这个规模上，按量计费的 API 定价的经济性常常崩掉。起初看着像增长的东西，很快就变成利润率的挑战。

**3. 领域特有的模式**

许多生产工作负载包含一些模式，通用模型能处理得尚可，但对关键任务系统来说不够稳定一致。

用真实的生产数据训练，让专用模型能学到最重要的那些细节：领域特有术语、格式变体，以及出现在长尾输入里的边界情形与失效模式。

专用模型不去和前沿模型在所有可能的任务上竞争，而是专注把一件工作负载做到极好。它们用广度换深度——对生产系统来说，这套做法往往带来更好的可靠性，以及高效得多的经济性。
