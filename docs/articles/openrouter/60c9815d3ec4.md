# AI 治理清单：LLM 架构先行

Deloitte 报告 AI 雄心与 AI 治理成熟度之间存在 53 个百分点的差距。[74% 的企业](https://www.deloitte.com/us/en/about/press-room/state-of-ai-report-2026.html)计划在两年内部署 agentic AI，而只有 21% 拥有治理自主 agent 的成熟模式。

对工程团队而言，AI 治理清单只有在能映射到架构时才有用，因为政策语言无法告诉你谁调用了哪个模型、哪个 provider 处理了请求、审计留痕在哪里。

三种路由姿态——托管网关、自托管网关、直接 API——对应你的 LLM 技术栈实际能满足的治理要求，各自的映射方式不同。

## 治理缺口在哪里变得具体

治理缺口显现于 agentic AI 离开试点项目、进入生产工作流之时。对工程负责人，这个缺口变得具体，是在模型调用接触客户上下文、经由外部 provider 路由、并产生技术栈无法回答的审计问题的时候。

Deloitte 还发现，数据隐私与安全位列领导者对 AI 的前几大关切。这让工程负责人处境尴尬：你的团队可能已经在把模型调用接入生产工作流，而治理还活在一电子表格里、一份政策文档里、或一个会议议程里。

### 为什么 53 个百分点的差距要紧

这个差距要紧，因为 agentic AI 不会待在 demo 里。它调用工具、接触客户上下文、触发下游工作流，制造出总得有人解释的支出。

你的技术栈必须回答：谁调用了哪个模型、哪个 provider 处理了请求、成本多少、审计留痕在哪里。

### 为什么治理清单产不出审计日志

OWASP 给合规负责人提供了有用的起点。[OWASP LLM 应用网络安全与治理清单](https://genai.owasp.org/resource/llm-applications-cybersecurity-and-governance-checklist-english/)面向「高管、技术、网络安全、隐私、合规与法务领域的领导者，DevSecOps、MLSecOps 与网络安全团队及防守人员」。当工作是风险评估、供应商管理、指导委员会和政策归属时，这个定位是合理的。

勾选治理领域产出的是一个 PDF，不是支出可见性、provider 归因，也不是一个可审计的统一端点。那份 PDF 可以指导整个计划，但它无法证明某个内部工具在高危用例中是否使用了获批模型，也无法产出你团队周一上班就需要的那份审计留痕。

你的清单可能是对的，而你的技术栈仍然无法证明发生了什么。

## 你的路由架构就是你的第一层治理

LLM 治理的第一步，是让模型流量经过一个能够记录用量、provider、成本和访问决策的架构。API 治理正是在这里从政策措辞变成工程界面。如果请求路径抓不住证据，治理计划从一开始就有盲区。

### 三种架构姿态

托管网关把模型调用经第三方路由层转发，用于 provider 访问、用量记录和路由控制。

自托管网关把该层放进你自己的基础设施，用更多运营责任换更多控制权。

直接 API 访问让每个服务直连模型 provider，把治理原语留给各个团队自己解决。

### 每种姿态默认给你什么

以下是各路由姿态在你团队添加自定义控制之前实际能证明什么的务实基线。

| 姿态 | 支出可见性 | Provider 归因 | 数据主权 | RBAC | 审计留痕 |
| --- | --- | --- | --- | --- | --- |
| 托管网关（OpenRouter、Portkey） | 有。OpenRouter activity 仪表盘，按 API key | 有。每请求 provider 归因 | 有。Zero Data Retention 路由控制 | 按 key 与 workspace 控制；完整 RBAC 见 Portkey | 用量与 provider 记录；完整审计日志见 Portkey |
| 自托管网关（LiteLLM） | 有。虚拟 key 的支出跟踪 | 有。按路由记录 provider | 有。基础设施与日志留在你的控制内 | 有。LiteLLM Enterprise | 有。LiteLLM Enterprise 审计日志加 Prometheus |
| 直接 API | 无 | 无 | 无共享控制面 | 无 | 无 |

这张表显示哪些治理证据是默认存在的，哪些还需要你的团队自己建设。

### 为什么直接 API 访问留下缺口

直接 API 访问给你零治理原语。散落在十二个微服务里的六家 provider key，给不了你一个可以检视支出、provider 归因、访问控制或审计历史的地方。一旦用量扩散超出一个团队，你的路由架构就成为「一份报告」和「一次大扫除」之间的区别。

下一步是把这条架构基线变成你的技术栈真正能回答的治理清单。

## 一份映射到你技术栈的治理清单

有用的治理清单，会区分「你的路由层能证明的控制」和「你的组织仍需自己承担的控制」。把清单当作五根支柱：

- Inventory（清单）：在用哪些 AI 系统、模型和 provider
- Accountability（问责）：谁拥有每个系统、工具和审批路径
- Access（访问）：哪些团队可以为高危用例使用获批工具
- Evidence（证据）：哪些日志支撑审计留痕、数据驻留和支出之问
- Compliance（合规）：哪些控制需要政策审查、偏见评估、事件响应计划或 EU AI Act 文档

工程上的问题是：不打手忙脚乱，你当前的技术栈能证明其中哪些。

### AI 清单与模型跟踪

你的 AI 清单从请求路径开始。如果每个模型调用都经过同一个端点路由，你就能看清哪些应用在用哪些模型、这种用法如何随时间变化。如果每个团队直连 provider，你的清单只存在于有人记得记录的地方。

电子表格能列出获批系统。路由层能显示生产流量是否与清单相符。

### 支出可见性与预算控制

支出可见性常常是你拿到的最早预警系统。OpenRouter 通过 [activity 仪表盘](https://openrouter.ai/activity)暴露按 key 的用量，给工程负责人一个在财务或安全把它演成消防演习之前先检查用量的地方。自托管网关在你配好跟踪、仪表盘和告警后也能提供同样视图。

直接 API 访问留给你的只有各 provider 的账单页面，以及每个服务自己记的东西。当一个团队负责一个功能时这还可行。当多个团队面向不同 provider 上线 AI 功能、没人答得出是哪个项目造成了峰值时，它就崩了。

### Provider 归因与数据驻留

如果你的 prompt 含客户数据，处理它的那个 provider 就成了合规相关事实。你需要知道请求流向哪里，而不仅是哪个模型响应了。

OpenRouter 暴露每请求的 provider 归因，支持 [Zero Data Retention](https://openrouter.ai/blog/insights/zero-data-retention/)路由，你也可以用同一套 provider 控制[强制数据驻留](https://openrouter.ai/blog/insights/ai-data-residency/)。直接 API 访问则让每段 provider 关系各自孤立。

### 访问控制、获批工具与高危用例

高危用例——如招聘、放贷、医疗分诊或财务决策——需要比内部摘要更严的规则。

OpenRouter 在 API-key 和 workspace 级别划定访问范围，你可以按团队或应用拆分 key、设置单 key 预算，并分配 [guardrails](https://openrouter.ai/docs/guides/features/guardrails)把每个 key 或成员限制在获批的模型与 provider 内。需要在一个平台内集中式 RBAC 和路由级强制执行的团队，可以在其上叠加 Portkey 或 LiteLLM Enterprise。

### 审计留痕与持续监控

这些控制对所有治理计划都重要，因为它们证明的是部署之后发生了什么，而不只是政策想要什么。

托管网关可以快速提供其中部分证据。OpenRouter [Logs](https://openrouter.ai/docs/guides/features/logs)记录每次 generation 的模型、最终 provider、API key、延迟和成本，[Broadcast](https://openrouter.ai/docs/guides/features/broadcast)把这些追踪数据发送到你的可观测性平台。自托管网关在你围绕它建设了日志与监控后能给出更深证据。直接 API 访问不给你任何共享留痕，除非你的团队在每个 provider 集成上各建一套。

### EU AI Act、agentic AI 以及架构满足不了的部分

EU AI Act 增加的要求不是任何路由层能单独满足的。对高危 AI 系统，[Regulation (EU) 2024/1689](https://eur-lex.europa.eu/eli/reg/2024/1689/oj)下的法规覆盖了技术文档、透明度、人类监督、符合性评估、上市后监控和严重事件报告等义务。这些要求需要请求路径之外的流程、归属和评审。

Agentic AI 让这条边界更重要，因为自主系统可以调用工具、采取行动、在工作流中推进，而不需要人逐步批准。你的路由层能展示系统调用了什么、请求去了哪里，但你的治理框架仍必须定义人类何时介入、事件如何处理。针对 agent 特有的运行时控制，见 [agentic AI 治理](https://openrouter.ai/blog/insights/agentic-ai-governance/)。

## 托管网关给你什么、不给你什么

托管网关给你一个快速的治理基线，而不是完整的治理计划。它帮你集中模型访问、查看用量、控制路由，但它不消除政策、采购评审或按负载特性做合规决策的需要。

### OpenRouter 默认提供什么

价值在于集中。不是散落在各服务里的 provider key，而是一个负责模型访问、provider 选择、用量可见性和数据政策控制（如 Zero Data Retention 路由）的路由层。这给工程负责人一个务实的地方，开始回答谁调用了什么模型、哪个 provider 处理的、花了多少钱。

这些控制重要，因为它们紧挨请求路径。它们减少日后的清理工作。它们也让下一个治理决策更明确：把控制留在路由层、加在应用代码里，还是交给采购与合规评审。

### Portkey 的框架大体是对的

Portkey 在其 2026 年 1 月的指南中主张，[「可观测性成为基石」](https://portkey.ai/blog/the-complete-guide-to-llm-observability/)，支撑治理、审计、优化以及对生产结果的信心。这个次序是对的：先观察系统，再声称你治理了它。

当你第一个问题是 LLM 访问碎片化、可见性薄弱时，用托管网关。当你的需求扩展到正式的脱敏工作流、自定义授权或超出路由日志的审计证据时，把它们当作独立的设计决策。

## 自托管 vs 托管治理

自托管与托管网关解决同一个可见性问题，所有权模式不同。

### 什么时候 LiteLLM 占优

对想要完全控制的团队，自托管 LiteLLM 是常见建议，这个建议有实据。LiteLLM 有 [40K+ GitHub stars](https://github.com/BerriAI/litellm)，功能集就是为想要直接控制自己网关的平台团队打造的。

当控制比速度更重要时用自托管。它适合需要完全数据主权、自定义认证、内部日志标准、模型访问控制，且要与现有平台系统深度集成的团队。也适合已有能力再运行一个生产服务的团队。

### 什么时候托管网关占优

当你答不出谁在哪些模型上花了多少钱、发往哪些 provider 时，用托管网关。

它立刻给你支出、provider 选择和使用模式的证据，而不必把网关运维变成一个新的平台项目。

### 自托管的运营成本

自托管不是消除治理成本，而是把它搬进你团队的待办列表。你负责部署、日志基础设施、可用性、升级和事件响应，包括那些决定网关是成为可靠基础设施还是又一个脆弱服务的问题：

- 谁打补丁？
- 谁处理 provider 故障？
- 谁维护仪表盘和告警？
- 审计时谁解释缺失的日志？

如果你有这支团队，自托管可行。
