# 支持机器人的模型路由：廉价优先的常见问题解答处理

OpenRouter ·10/2/2026

廉价优先的模型路由，就是把常规客服问题交给便宜的小模型，并把选中的疑难或不确定请求升级到更强的模型。只要便宜路径满足你的客服要求，它就能避免"每条消息都用一个能干模型"的开销。应用侧的做法有三种：静态规则、基于分类器的分诊、带置信度阈值的答案检查。

本文比较这三种做法，说明流程中哪些部分由 OpenRouter 负责，走一遍带可复制请求的客服流程，并给出加升级之前要测什么。

## 太长不看

- 窄而可辨认的 FAQ 用静态规则；表述多变的稳定类别用分类器分诊；希望便宜模型先作答时用答案检查。
- 客服政策的验收检查留在你的应用里。我们的模型回退处理的是请求错误；一次成功但错误的答案，需要你在代码里另做一次升级决定。
- 拿廉价优先和"只用便宜的""只用更强的"做对比：答案验收率、含被丢弃尝试的总成本、升级率、整轮延迟。
- 只在评估显示升级能修复失败的地方加升级。把本来已达标的便宜答案换掉的升级，只是加钱加延迟，不改善回答。

## 什么时候便宜模型适合常规 FAQ

一个能干的模型能让初始集成保持简单。如果常规 FAQ 在便宜模型上就能达到你的质量要求，这部分流量就成了降低模型支出的候选。拿同一份批准过的文档测两个模型，候选从我们的[模型目录](https://openrouter.ai/models)挑，价格看当前[定价](https://openrouter.ai/pricing)。

分类器调用和二次尝试同样消耗时间和预算。选哪种做法，取决于你在生成之前能识别什么、在之后能检查什么。

## 三种路由做法

Anthropic 的[构建高效 agent 指南](https://www.anthropic.com/engineering/building-effective-agents)把路由描述为"给输入分类、再把它导向一个专门的后续任务"——简单问题给小模型，难问题给更强的模型。下面的构建与维护估算是我们对一个小型客服应用的规划判断。

这些做法可以共存。规则或分类决定请求从哪里开始，答案检查决定它的产出可不可接受。模型的自我报告置信度，在你拿自己的问题对照正确性验证之前，不是正确概率——在那之前把它当排序信号。

## 你的应用拥有什么，OpenRouter 负责什么

以质量为基础的路由，意味着你要维护规则或分类器、验收检查、升级决定和监控。这些都可以住在你自己的客服应用里，不需要单独的路由服务。

想让我们替你选初始模型的话，我们的 [Auto Router](https://openrouter.ai/docs/guides/routing/routers/auto-router)（用 `"model": "openrouter/auto"` 选择）会按任务类型给每个提示词分类，从 OpenRouter 用户在此类任务上实际消费的模型里挑一个。有序的[模型回退](https://openrouter.ai/docs/guides/routing/model-fallbacks)列表以 `models` 数组发送，在限流、提供商宕机、内容审核拒绝等错误之后由下一个模型重试请求。客服政策的验收检查仍是你的责任。

想让我们选初始模型，用 Auto Router。知道偏好模型、需要错误恢复，用有序回退列表。至于廉价优先的质量升级，是你的应用检查候选、检查不过就再要一份回答。

下面的流程展示这个职责分工。

## OpenRouter 上的一个客服实例流程

### 第 1 步：选模型之前先定义结果

HarborDesk 是一个虚构的 SaaS 产品，有一批固定的 FAQ。它的机器人能解释政策、建议转人工，但不能查看账户或做任何修改。一轮合格的对话要么回答问题、要么要求澄清、要么建议人工支持。

能可靠识别、且答案固定的意图，用批准过的模板。意图选择要单独测试，确保正确的措辞对上正确的问题。需要理解的请求进入下面的生成回答路径。

### 第 2 步：升级之前先检查生成的答案

对需要生成的请求，便宜模型提供第一候选和分诊信号。验收决定由你的应用做。

![廉价优先客服路由流程图：来消息和批准的 FAQ 进入便宜模型，返回候选答案和分诊信号；一个决策节点问应用是否接受候选——接受则走回答、澄清或建议转人工；不接受则做一次更强模型的尝试，第二个决策节点问更强答案是否通过应用检查——通过走同样的回答路径，不通过走澄清或寻求人工复查](https://openrouter.ai/blog/images/cheap-first-support-routing-flow.png)

设想一个客户问怎么取消订阅并申请退款。按 HarborDesk 的政策，所有者在 Settings > Billing 里取消，退款申请由账务团队审核。

- 接受一个讲清两步、又不承诺退款的便宜答案。
- 扣留那种把一切都推给账务团队、漏掉所有者可自助取消的答案。有批准模板覆盖就用模板；你的评估显示更强模型能修正这个遗漏，就请求一次更强模型尝试。
- 客户要求机器人批准退款时，建议转账务人工。更强模型也给不出那个权限。

检查政策内容和预期动作——合法的 JSON 本身不构成为正确。保留对话上下文，对更强答案跑同样的检查，一次升级之后止步。

### 第 3 步：配置错误回退，记录请求成本

这段代码发送一个带有序回退列表的请求。运行前安装 `requests` 并设置 `OPENROUTER_API_KEY`。那段虚构 FAQ 为示例提供上下文。

```
import os
import requests

messages = [
    {
        "role": "system",
        "content": (
            "Answer only from this fictional HarborDesk FAQ. "
            "Owners can cancel under Settings > Billing. "
            "Billing support reviews refund requests. "
            "You cannot inspect accounts, cancel plans, or approve refunds. "
            "Ask for clarification when necessary."
        ),
    },
    {"role": "user", "content": "How do I cancel my subscription and request a refund?"},
]

response = requests.post(
    "https://openrouter.ai/api/v1/chat/completions",
    headers={"Authorization": "Bearer " + os.environ["OPENROUTER_API_KEY"]},
    json={
        "models": ["openai/gpt-4.1-mini", "openai/gpt-4.1"],
        "messages": messages,
        "max_tokens": 512,
        "stream": False,
    },
    timeout=60,
)
response.raise_for_status()
data = response.json()
if "error" in data:
    raise RuntimeError(f"Completion failed: {data['error']}")
choices = data.get("choices", [])
if not choices:
    raise RuntimeError("Completion returned no choices")
choice = choices[0]
if choice.get("error") is not None or choice.get("finish_reason") == "error":
    raise RuntimeError(f"Completion failed: {choice.get('error', 'unknown error')}")
print({
    "id": data["id"],
    "model": data["model"],
    "answer": choice["message"]["content"],
    "cost": data.get("usage", {}).get("cost"),
})
```

`models` 数组在可回退的错误（限流、提供商宕机之类）之后尝试下一个模型。一次成功但错误的答案不会触发它。质量升级需要应用侧检查加上一次独立的更强模型请求。

两处错误检查的存在原因：模型开始处理请求后在产出过程中失败时，我们仍可能返回 HTTP 200。`error` 对象出现在响应体顶层，或者存在部分内容时出现在 `choices[0]` 内、`finish_reason` 为 `error`。两种形态见[错误与调试](https://openrouter.ai/docs/api_reference/errors-and-debugging)参考。两种都当失败处理，别把部分输出当答案打印。

代码打印的是一份未经校验的候选，供查看。`usage.cost` 字段是我们为该请求收取的额度金额；`model` 是实际产出响应的模型——回退触发时这一点很重要。每个请求两个都要记录。你的应用升级时，把两次调用相加，包括被丢弃的便宜草稿。响应没带 `cost` 值时，先记为"未知"再对照你的 [activity](https://openrouter.ai/activity) 页对账，别记成零。`usage` 对象见[用量核算](https://openrouter.ai/docs/cookbook/administration/usage-accounting) cookbook。

## 测量升级率与每解决工单成本

对总是先试便宜模型的管线，每个请求的期望模型成本用这个公式：

```
expected_cost = cost_cheap + cost_check_1
              + escalation_fraction * (cost_strong + cost_check_2)
```

检查项里要含任何评估器或分类器的调用成本，升级请求按更强模型的成本计。把结果和"只用便宜""只用更强"（含各自的检查）在同一质量目标和延迟限制下比较。

每种路由策略都跟踪这些指标。

- **升级率。**走了更强模型尝试的请求占比。
- **被接受的错误答案。**通过了你的检查、但没通过人工复查的便宜答案。
- **被升级的正确答案。**本已达标的便宜答案仍被升级。每一次都平添一笔更强模型费用和一次调用的延迟，却不改善回答。
- **转接恰当性。**请求需要机器人没有的权限时，它是否建议了人工。
- **整轮延迟。**从客户消息到返回答案的时间，升级请求含两个模型阶段。

高升级率值得检查被升级的问题，但它本身不证明阈值设错了。

每解决工单成本：把一个工单批次的全部模型支出（含未解决的）除以在规定重开窗口内达到既定解决定义的工单数。测试集上的答案验收率衡量的是回答质量，不是客户问题解决——两个指标要分开。

在生产启用升级之前，在留出的客服问题上跑这套对比。覆盖直白 FAQ、含糊请求、故障排查和需要人工转接的请求，每个答案对照预定义的内容标准和预期动作评分。升级只在其"以你接受的成本和延迟把不及格答案变成及格"的地方才站得住。

## 结论

从批准模板加便宜模型基线起步，服务一个窄 FAQ。按你的负载选规则、分类或答案检查，然后只在同一质量目标和延迟限制下和更强模型比。升级只在它修好足够多失败、值回成本和延迟时才加。客服政策变化时重新审视你的检查。

## 常见问题

### 能不搭自建路由服务吗？

路由可以留在你的客服应用内。想让我们选初始模型就用 Auto Router；用 `models` 回退数组让我们在请求错误后重试另一个模型。客服专属的验收检查——答案是否符合你的取消政策——仍然住在你应用里。模型 ID 放配置里，提示词和评估数据保持可移植，方便以后换模型。

### 便宜模型能在生成中途请教更强模型吗？

本指南的流程不行。便宜模型先完成候选答案，然后你的应用决定是否请求一份更强模型的答案。要在一个回合中途请教另一个模型，需要你的代码里有显式的工具或编排步骤：调用更强模型、把它的输出送回进行中的工作流。`models` 回退数组不会创造那个机制——它只在错误之后用另一个模型重试请求。

### FAQ 分诊该选哪个模型？

从留出客服问题（含含糊请求和政策例外）上满足你质量目标的最便宜候选开始。测整轮延迟而不是单调用延迟——最快的模型调用如果需要二次尝试的频率高，最终的客服响应反而更慢。从一小组高频问题开始，随评估揭示哪些路由有效再扩张。
