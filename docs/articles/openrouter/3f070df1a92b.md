# Auto Exacto：自适应质量路由，默认开启

去年 10 月我们上线了 [Exacto](https://openrouter.ai/announcements/provider-variance-introducing-exacto)：经过人工甄选端点、借助经过验证的 provider 子集，tool-calling 准确率更高。与默认路由相比，Exacto 在 Tau2Bench 和 LiveMCPBench 上的分数提升了 10-20%。

但社区反馈说他们期待的更多。你必须在模型 slug 后面加 `:exacto`，而且只对已支持的模型有效。而且 provider 列表是静态的，靠人工更新，在我们重新跑分析之前一直冻结。

**Auto Exacto 就是要解决这些反馈。**它大约每 5 分钟基于三类信号重新评估 provider：吞吐、tool-call 遥测和基准分数。对于包含 tools 的请求，它默认开启。

```
{
  "model": "moonshotai/kimi-k2.5",
  "messages": [
    {"role": "user", "content": "Find me a flight to Denver."}
  ],
  "tools": [...]
}
```

如果你想在非 tool-calling 请求上获得同样的质量加权路由，可以在任意模型 slug 后加 `:exacto` 来主动开启，和以前一样。这对所有模型、所有请求类型都有效，类似用于吞吐排序的 `:nitro` 和用于价格排序的 `:floor`。

**第一周难题**

provider 差异在模型发布时达到峰值，而那也正是最多的人想用它的时候。

推理引擎需要为新聊天模板、新格式、新参数打补丁。Moonshot 发布 Kimi K2 时，vLLM 和 SGLang 的提交在第一天就准备好了，但发布后仍花了几周才把事情做对。

[Artificial Analysis 展示过这一点](https://artificialanalysis.ai/models/gpt-oss-120b)：gpt-oss-120b 第一周差异巨大，一个月后收敛到很窄的区间。

Auto Exacto 在这个窗口期帮助最大。尚未稳定的 provider 会被自动降权，随着它们改进又会自动回升。不需要人工去更新任何列表。

**我们一直在测什么**

自 2025 年 8 月起，我们对 OpenRouter 全站每一个 `tool_call` 响应进行评分。我们测量三件事：

- `tool_call` 是合法 JSON 吗？
- tool 名字真的在用户提供的 tools 里吗？
- schema 匹配吗？

我们已用这种方式测量了数十亿次 tool call，历时数月，对这个信号有很高的信心。

不过生产流量有局限——某个 provider 主要被 Kilo Code 用户调用，另一个则是演示型 tool calling 应用的流量。schema 可能差异极大，尤其在复杂度上、提供的 tool 数量上，当然用例也不同。仅凭真实数据无法做出干净的横向比较，所以我们还搭建了受控基准。

**TauBench Verified 与 GPQA-Diamond**

我们按周期在多个 provider 上跑两个基准：

**TauBench Verified Airline**（来自 τ²-Bench 套件，使用 AWS-AGI Verified 数据集）。面向 agent 的 tool-calling 评测，航空客服领域。它足够小，可以频繁运行而不烧钱，又足够复杂，能暴露真实的 provider 差异。注意这个数据集与常见公开发布的不是同一个，所以我们 TauBench Airline 的分数与你在网上看到的并不等价。数据集可在[这里](https://github.com/amazon-agi/tau2-bench-verified)找到。

**GPQA-Diamond**，一个大家应该都熟悉的、知识密集型的推理基准，给了我们第二条评估轴。此前我们曾与 [Florian Brand](https://x.com/Xeophon) 及 Epoch 团队合作，用这个基准做过 provider 差异分析。他们的[发现](https://epoch.ai/gradient-updates/why-benchmarking-is-hard)是：对于成熟模型，各 provider 在 GPQA-Diamond 上的中位数聚得很紧——差异大多是噪声。但当差异真实存在时，它就很显眼。

**我们的发现**

过去几周，我们已在一个内部账户上以生产环境验证这个路由变更，微调行为并通过该账户跑基准。最近几天，我们为我们一部分头部 tool-calling 模型全局启用了 auto exacto——包括 GLM-4.7、GLM-5、DeepSeek V3.2 和 gpt-oss-120b。

以下是自 3 月 10 日周二美东时间 17 点以来，我们的默认路由在各模型上的改善情况（旧的价格加权算法 vs 新的 auto exacto 算法）：

- GLM-5 和 GLM-4.7 的 tool call 错误率分别下降了 88% 和 80%，agent 可靠性大幅提升。此前我们看到的错误率约为 8%，现在平均接近 1%。20 轮运行的 Tau Bench Verified Airline 分数与 Z.AI 官方端点保持一致。
- gpt-oss-120b 的错误率下降 36%，从 5.6% 降到 3.5%，其 TauBench 分数从 53% 提升到 55%（+2%），与我们的各 provider 平均 55% 持平。
- DeepSeek V3.2 的 tool call 错误率下降 16%。这里的主要改善是 TauBench 分数从 69% 升到 74%，5 个百分点的提升远超噪声范围，具有统计显著性。

GPQA Diamond 的结果仍在跑，我们要收集统计上显著的数据。未来几天我们会用这些结果更新本文。

**路由如何工作**

Auto Exacto 用三类信号对 provider 分类：

- **吞吐。**从生产流量持续测量的每秒生成 token 数。
- **Tool-call 遥测。**自 8 月以来持续收集的生产数据：JSON 合法性、schema 合规性、tool 名称准确率。
- **基准分数。**TauBench Airline 和 GPQA-Diamond，借助 [Groq 的 OpenBench](https://github.com/groq/openbench)在我们的内部基础设施上按周期运行。

这三类信号汇入一个按模型自适应的阈值系统。系统用服务该模型的所有 provider 的中位数与中位数绝对偏差，计算每个模型「好」与「坏」的标准。只有当某 provider 相对同模型其他 provider 构成统计离群值时才会被标记。

provider 落入三个层级之一：

- **Verified good（已验证良好）。**数据充足，且三类信号均无异常。
- **Insufficient data（数据不足）。**请求量还不足以评判——它们居中，不享有一等待遇，但也不受惩罚。
- **Deranked（降权）。**在一个或多个信号上是统计离群值，被排到队尾。

在每层内部，原始路由顺序（价格、延迟、你的偏好）保持不变。本次发布我们选择不把吞吐、基准和 tool-call 数据揉成一个综合分。我们只是把表现最差的 provider 推到最后。这样更容易理解，也更容易调试。

未来可能会有一个纳入更多信号（包括价格）的综合分，为所有请求——无论是否 tool calling——构建类似的质量加权路由。我们欢迎任何反馈或想法：在你所有用例中最看重什么。

OpenRouter 大约每 5 分钟重新计算所有分数。每次计算时，每个模型每项信号的参考统计量（中位数、偏差、计算出的阈值）都会被持久化，并保留完整的审计记录。如果我们需要调试为什么某 provider 上周二下午 3 点被降权，随时可以查。

**我们观察但（暂）不路由的信号**

偶尔，我们会注意到某 provider 在相同基准任务上比中位数多烧 30% 的 token。这可能意味着循环、填充，或推理引擎的怪癖，新模型尤其如此。我们目前不采取行动，但会排查并向相关 provider 报告问题。

我们还会注意到一些对所有 provider 都存在的其他信号，包括排队时间和吞吐波动。我们会评估这些信号的价值，考虑后续纳入。

**基础设施**

我们基于 [Groq 的 OpenBench](https://github.com/groq/openbench)构建了内部工具（Mission Control），它封装了英国 AI Safety Institute 的 Inspect 框架。Temporal 负责长时工作流。基准在 GCP 的 GKE 容器上运行，内存超配到 16GB，因为 agent 评测很吃内存。

同一基准、同一环境、同一配置，按周期运行。人不在两次运行之间调变量。每个 provider 每个模型多次运行取平均。

**关于量化与 tool-call 解析器**

人们总把 provider 差异归咎于量化。我们没有看到单纯量化对 tool-call 质量的可测量影响。

真正的元凶通常是 tool-call 解析器。而这一般是推理引擎的问题，不是 provider 偷工减料。即使模型实验室在发布前直接与 vLLM、SGLang 等推理引擎团队合作，也常常一次做不对。所有人都需要时间来摸清一个模型想怎么用 tools、怎么成功解析这些调用。

Florian Brand 的 GPQA-Diamond [分析](https://epoch.ai/gradient-updates/why-benchmarking-is-hard)显示，量化水平差异极大的各 provider 中位数几乎相同。DeepInfra 采用激进量化，表现经常不错。Novita 的 FP4 击败了 FP8 的 provider。Kimi K2 的官方权重本身就是原生 int4 发布的。

**上线情况**

Auto Exacto 现已上线。工作方式如下：

- **Tool-calling 请求**：对 provider 数量足以测量差异的任意模型默认开启。
- **所有其他请求**：在任意模型 slug 后加 `:exacto`，对所有模型有效。
- **新 provider**：在承接足够流量之前保持中间层级。我们不会把你推向未经验证的端点。

关于价格：质量加权路由可能偏好比绝对最低价略贵的 provider。如果你无论如何都想要最便宜的推理，可以用 `:floor` 快捷方式，或直接固定 provider。

```
{
  "model": "moonshotai/kimi-k2:floor"
  // OR, use this:
  "provider": { "order": ["fireworks"] }
}
```
