# 最便宜的 token 是缓存 token：提示词缓存 + 粘性路由

OpenRouter ·7/21/2026 · 更新于 9/24/2026

你的 agent 每一轮都发送同样的系统提示词、工具定义、schema 和政策指令。一个 6 轮的会话里，同一段开头内容你可能被计费 6 次——尽管唯一变化的只是用户的最新消息或 agent 的最新工具结果。

提示词缓存解决这个问题：提供商从缓存读取提示词中重复的部分，而不是每次都按全价收你的钱。粘性路由则让这件事跨轮成立——把一个会话持续送回那个持有热缓存的提供商。

本文谈钱：缓存 token 多少钱、缓存读写为什么定价不同、`session_id` 如何从第一轮就让会话保持热度，以及怎么确认缓存真的在工作。

## 太长不看

- 缓存读的价格是普通输入 token 的 0.1x 到 0.5x，视提供商而定。Claude Sonnet 4.6 上，缓存读 $0.30/M 对输入 $3.00/M，恰好 0.1x。
- 第一个请求要付缓存写。Anthropic 的写是输入的 1.25x（5 分钟 TTL）或 2.0x（1 小时 TTL），一次没人复用的写反而比不缓存更贵。
- 热缓存只有在下一个请求落在同一个提供商端点上才有用。在 70 多家提供商之间，第二轮可能落到冷端点，你就付全价。
- 我们的粘性路由把后续请求钉回持有热缓存的提供商；`session_id` 则从第一个成功请求起就强制这一点——在任何缓存命中发生之前。
- 缓存未命中有 4 种原因：提示词太短、缓存过期、开头内容一直在变、请求漂到了另一家提供商。查 usage 响应里的 `cached_tokens` 确认命中。

## 提示词缓存能把 token 成本砍多少？

缓存读是普通输入价的 0.1x 到 0.5x，视提供商而定。这个区间正是缓存能大幅压低 agent 循环成本的原因。

重复的那部分往往就是花钱的那部分：长系统提示词、工具定义、JSON schema、护栏、检索到的文档，或让模型保持一致的示例。没有缓存时，每一轮都要为它们全部再付一次全价；有了缓存，第一个请求把它写入缓存，之后的请求按便宜价读回。

提供商视角：

| 提供商 | 缓存读 | 缓存写 | 启用方式 |
| --- | --- | --- | --- |
| Anthropic Claude（5 分钟 TTL） | 输入的 0.1x | 输入的 1.25x | 自动或显式 |
| Anthropic Claude（1 小时 TTL） | 输入的 0.1x | 输入的 2.0x | 显式（`ttl: "1h"`） |
| OpenAI（GPT-5.6 之前） | 输入的 0.25x–0.50x | 免费 | 自动 |
| OpenAI（GPT-5.6 及以后） | 输入的 0.25x–0.50x | 输入的 1.25x | 自动或显式 |
| Google Gemini（隐式） | 输入的 0.25x | 免费 | 自动 |
| Grok（xAI） | 输入的 0.25x | 免费 | 自动 |
| Moonshot AI | 输入的 0.25x | 免费 | 自动 |
| Groq | 输入的 0.5x | 免费 | 自动（Kimi K2 系列） |
| DeepSeek | 输入的 0.1x | 输入的 1.0x | 自动 |
| Alibaba Qwen | 输入的 0.1x | 输入的 1.25x | 显式（`cache_control`） |
| Z.AI | 约输入的 0.2x | 免费 | 自动 |

完整拆解见[提示词缓存文档](https://openrouter.ai/docs/guides/best-practices/prompt-caching)。具体到美元仍取决于模型和路由到的提供商；乘数告诉你的是该提供商上缓存输入与普通输入的对比。

对做 agent 的人来说，规律很简单：第一轮可能付了建缓存的钱，但只要开头那块被复用，之后每一轮都便宜得多。

## 钱花在哪：缓存写 vs 缓存读？

提示词缓存有两个成本：写和读。

写在提供商存下提示词中可复用的部分时发生，读在后续请求复用这份存储内容时发生。同一份内容被读到足以覆盖写成本时，你就净赚了。

一些提供商上，写比普通输入更贵。Anthropic 的缓存写：默认 5 分钟 TTL 是输入的 1.25x，1 小时 TTL 是 2.0x。一次没人复用的 Anthropic 缓存写，比同一提示词不做缓存还贵。

一次性请求，缓存可能帮不上忙。多轮 agent 则默认就是重复：整个会话都带着同样的指令、工具、schema 和政策上下文。写成本几轮之内就能回本。

短促、下一轮很快到达的场景用 5 分钟缓存寿命（TTL）；会话可能暂停到默认缓存过期、但内容仍值得留着时用 1 小时档。

## 为什么热缓存不一定帮到下一个请求？

热缓存只有当下一个请求落在持有它的提供商端点上才有用。

请求可以路由到很多提供商时，第一轮可能在这家写缓存，第二轮落到别家。第二家没有热缓存可读——请求照样能work，但你付全价，`cached_tokens` 低或为零。

这就是我们把粘性路由和提示词缓存配对的原因。一次命中缓存的请求之后，当某提供商的缓存读价低于普通输入价时，我们把同一模型的后续请求路由回同一个提供商端点。被粘住的提供商不可用时，OpenRouter 转到下一家可用提供商，而不是让请求失败。

默认情况下，OpenRouter 用第一个 system/developer 消息加第一个非 system 消息的哈希来识别一个对话。开头消息不变时这没问题。

agent 常常破坏这个前提：有的会在总结状态、重排工具上下文或添加运行元数据时改写自己的开头消息。开头消息一变，哈希就变，对话可能落到另一家提供商。解法是显式的 `session_id`。

![agent 会话示意图：session_id 让第 1 轮到第 N 轮都留在同一提供商上，缓存写一次、之后是便宜缓存读；粘住的提供商失败时自动转移到新提供商](https://openrouter.ai/blog/images/prompt-caching-agent-session.png)

## 用 session_id 从第一轮就强制热缓存

agent 循环请设 `session_id`。传了它，OpenRouter 直接把它当粘性路由键，不再从开头消息推导。

带 `session_id`，粘性路由在第一个成功请求后就生效——在任何缓存命中发生之前。不带它，粘性只在检测到缓存命中之后才开始。对多轮 agent，这就是"从第一轮起可靠"的缓存和"时冷时热"的缓存的区别。

`session_id` 可以作为请求体顶层字段或经 `x-session-id` 头发送。在同一个对话或 agent 运行内保持稳定，长度控制在 256 字符内。

```
curl https://openrouter.ai/api/v1/chat/completions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "anthropic/claude-sonnet-4.6",
    "session_id": "my-agent-session-abc123",
    "messages": [{"role": "system", "content": "..."}]
  }'
```

```
from openrouter import OpenRouter

client = OpenRouter()

resp = client.chat.send(
    model="anthropic/claude-sonnet-4.6",
    session_id="my-agent-session-abc123",
    messages=[{"role": "system", "content": "..."}],
)
```

```
import { OpenRouter } from '@openrouter/sdk';

const openRouter = new OpenRouter({ apiKey: process.env.OPENROUTER_API_KEY });

const response = await openRouter.chat.send({
  model: 'anthropic/claude-sonnet-4.6',
  session_id: 'my-agent-session-abc123',
  messages: [{ role: 'system', content: '...' }],
});
```

取值对齐你的工作单元：一个聊天线程、工单、工作流运行或 agent 任务。别每轮新建一个 `session_id`——那样请求就不再落在持缓存的提供商上。

如果你用 [Auto Router](https://openrouter.ai/docs/guides/routing/routers/auto-router#session-stickiness) 或 [Pareto Router](https://openrouter.ai/docs/guides/routing/routers/pareto-router#session-stickiness) 这类路由器模型，会话粘性也尽最大努力复用路由器选中的模型而不只是提供商：只要被记住的模型还在路由器当前候选里，后续轮就优先它；任务或设置变化时路由器仍可能改选。

## 怎么确认提示词缓存到底有没有生效？

最快的办法是[检查用量](https://openrouter.ai/docs/cookbook/administration/usage-accounting)。

响应里，`usage.prompt_tokens_details.cached_tokens` 显示从缓存读了多少 token——大于零即命中。`cache_write_tokens` 显示一次写缓存请求中写了多少 token。

```
{
  "usage": {
    "prompt_tokens": 10339,
    "completion_tokens": 60,
    "total_tokens": 10399,
    "prompt_tokens_details": {
      "cached_tokens": 10318,
      "cache_write_tokens": 0
    }
  }
}
```

这个例子里，提示词 token 的绝大部分来自缓存，且这一轮没有写新缓存。

可以在三处检查缓存行为：[Activity 页面](https://openrouter.ai/activity)的详情视图、`/api/v1/generation` API，以及 API 响应携带的 `usage.prompt_tokens_details` 对象。

用 `cache_discount` 看一次生成省了多少。写要收费的提供商上，写那一轮你可能看到负的折扣，因为缓存写比普通输入更贵；之后的读轮次，折扣应当转正。

![带标注的 usage 对象，展示 cached_tokens、cache_write_tokens 和 cache_discount 字段及各自能证实什么](https://openrouter.ai/blog/images/prompt-caching-usage-inspection.png)

## 缓存为什么会未命中，怎么止住？

缓存看起来坏了，通常逃不出四件事：提示词太短、缓存过期、开头内容变了、请求漂到了另一家提供商。

### 提示词低于提供商的最低门槛

每家提供商都有最小提示词规模，低于它什么都不缓存。Anthropic 上：Claude Opus 4.5 至 4.8 和 Claude Haiku 4.5 需要 4,096 token；Claude Haiku 3.5 需要 2,048；Claude Sonnet 4、4.5、4.6（及 Opus 4 / 4.1）需要 1,024。OpenAI 需要 1,024。Gemini 2.5 Pro 需要 4,096，Gemini 2.5 Flash 需要 1,024。

你的可复用内容在门槛之下，缓存就不会启动。别为了凑数往里塞填充文本。缓存要用在你本来就有大量可复用内容的地方：工具、schema、检索文档、示例或政策文本。

### 缓存在两轮之间过期了

缓存活不长。Anthropic 默认 5 分钟，长会话有 1 小时选项。Gemini 的隐式缓存约 3-5 分钟，且读它不会续期。缓存一过期，下一个请求就得重新写。

用户经常在轮次之间长时间停顿的话，在支持的提供商上用更长 TTL，或者把 agent 设计成"空闲后接受一次新写"。

### 提示词开头一直在变

自动和隐式缓存在提示词开头保持不变时效果最好。稳定的东西放前面：系统指令、工具、schema、固定参照材料。变化的东西放后面：用户问题、时间戳、临时状态、工具输出、短命元数据。

细节很重要：第一条系统消息里放个时间戳，等于每轮都把提示词变成新的。它不需要进缓存内容的话，挪到后面的 user 或 tool 消息里。

### 请求漂到了另一家提供商

缓存活在被写入的地方。后续请求路由到别的提供商端点，那个端点读不到之前的缓存。

agent 工作流请设 `session_id`，让粘性路由把会话留在热提供商上。一个注意点：如果你自己设了 `provider.order`，你的顺序优先于粘性路由。确实需要指定提供商顺序时，用[提供商路由控制](https://openrouter.ai/docs/guides/routing/provider-selection)。

## 把缓存和粘性路由合进 agent 循环

agent 每轮发送同样内容的话，照着这份清单做：

- 稳定内容放前面：系统提示词、工具定义、schema、政策、长生命周期上下文。
- 变化内容放后面：用户消息、工具结果、时间戳、本次运行的状态。
- 需要显式 `cache_control` 的提供商要启用提示词缓存。
- 给对话或工作流运行设一个稳定的 `session_id`。
- 检查 `cached_tokens` 和 `cache_discount`，确认读确实在发生。

粗算一下：一个 agent 在 6 轮里重复同样 10,000 token。

| 场景 | 第 1 轮 | 第 2-6 轮 | 总成本（相对 1 轮不缓存） |
| --- | --- | --- | --- |
| 不缓存 | 全量输入 | 每轮全量输入 | 6.0x |
| Anthropic 5 分钟缓存 + 粘性路由 | 1.25x 写 | 0.1x 读 | 1.75x |
| 免费写的提供商 + 0.25x 读 | 1.0x 输入/写 | 0.25x 读 | 2.25x |
| 免费写的提供商 + 0.5x 读 | 1.0x 输入/写 | 0.5x 读 | 3.5x |

这个例子只算重复内容，不含较小的变化消息和模型的输出 token。轮数越多，节省越大。

![实例对照表：10 轮不缓存全价 vs 缓存加粘性路由，最终计费输入 token 减少约 75-90%](https://openrouter.ai/blog/images/prompt-caching-worked-example.png)

什么时候用什么：

- 复用内容随对话增长的多轮对话，用自动缓存。
- 明确知道哪些大块该缓存时用显式断点：检索到的文档、长参照文件、角色卡、CSV 数据、政策文本。
- agent 会话、客服工单、聊天线程、工作流运行，以及开头消息可能在轮间变化的任何对话，用 `session_id`。
- Anthropic 的长会话、默认 5 分钟可能在轮间过期时，用 1 小时缓存；短而密集的往来用默认。

agent 反复发送同样昂贵的内容时，缓存读加粘性路由让它不再成为循环里最贵的部分。缓存降低的是你发送的 token 的单价；至于先把每 token 单价压下来的路由设置，见[如何在 OpenRouter 上获得最低成本 LLM 推理](https://openrouter.ai/blog/tutorials/how-to-get-the-lowest-cost-llm-inference-on-openrouter/)。

## 常见问题

### OpenRouter 支持提示词缓存吗？

支持。OpenRouter 在受支持的提供商和模型上支持提示词缓存。多数提供商自动启用；Anthropic 和 Alibaba Qwen 用 `cache_control` 做显式缓存。缓存读是普通输入价的 0.1x 到 0.5x（视提供商），被复用的前缀在第一个请求之后便宜得多。

### OpenRouter 上缓存 token 多少钱？

缓存读是普通输入价的 0.1x 到 0.5x，视提供商。Anthropic、DeepSeek 和 Alibaba Qwen 可按 0.1x 读；OpenAI 0.25x–0.50x；Gemini、Grok 和 Moonshot 0.25x；Groq 0.5x。

### 为什么经 OpenRouter 提示词缓存没生效？

常见原因：提示词低于提供商的 token 门槛、缓存过期、前缀不稳定、轮次之间提供商漂移。agent 工作流先设稳定的 `session_id`，再查 usage 响应里的 `cached_tokens`——任何大于零的值即确认命中。

### 怎么让缓存在 agent 的各轮之间保持热度？

为对话、工单或工作流运行传一个稳定的 `session_id`。OpenRouter 用它作粘性路由键，后续请求回到持有热缓存的同一端点。设了 `session_id`，粘性在第一个成功请求后就激活，无需等到观察到缓存命中。

### 怎么检查缓存省了钱？

查 `usage.prompt_tokens_details` 里的 `cached_tokens`（缓存读）和 `cache_write_tokens`（缓存写）；`cached_tokens` 大于零即确认命中。也可以读响应里的 `cache_discount` 看逐生成的成本效果，或打开 [Activity 页面](https://openrouter.ai/activity)详情视图和 `/api/v1/generation` API。

### 缓存对 Auto Router 有效吗？

有效。设了 `session_id` 后，Auto Router、Pareto Router 这类路由器模型会为会话同时钉住解析出的模型和提供商，后续轮持续命中同一份热缓存。
