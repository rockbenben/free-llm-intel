# 如何测试 AI 智能体的工具调用准确率

OpenRouter ·9/30/2026

agent 用工具时可能在两个地方失败：选错工具，或选对了工具却发错参数。

这两种失败告诉你的事不一样。agent 调了 `lookup_order` 而不是 `refund_order`，问题是工具选择。调了 `refund_order` 却带错 `order_id`，说明工具选对了、参数传错了。

本指南讲测试工具调用行为的三种方法：第一种是无参照大语言模型（LLM）裁判；第二种是确定性参数检查；第三种是轨迹比较。最后演示如何通过 OpenRouter 把同一批测试用例跑在多个支持工具的模型上。

## 太长不看

- 工具选择和参数正确性分开测。agent 可能选错工具、没必要地调一个工具，或选对工具传烂参数。
- 知道期望工具或期望参数值时用确定性检查。正确性取决于上下文、或多个选择都成立时用无参照 LLM 裁判。
- 用 JSON Schema 抓格式错误和结构非法的参数，参数值另行检查——schema 合法的值照样可以是错的。
- 工具调用的顺序要紧时用轨迹比较。多条路径都能到达同一个有效结果时，别强求唯一的确切序列。
- 比较模型时，测试用例、评分规则、模型设置和路由配置对所有候选保持一致。

## 两种失败模式，需要两种测试

先盯工具决定本身，再检查模型产出的调用。

### 工具选择

假设一个内部客服 agent 能用 `lookup_order`、`issue_refund` 和 `search_docs`。

用户问退款政策写了什么，`search_docs` 是合适的工具。用户要求给订单 `ord_7281` 退款，agent 可能需要先查订单再退款。你的测试集还应包含"模型已有足够信息直接作答、不该调工具"的用例。

无工具用例之所以重要，是因为只看响应里有没有 `tool_calls` 不够格——一个调了不必要或错误函数的模型同样产出工具调用。

期望工具明确唯一时，在代码里把返回的工具名和期望值比对。多个工具都合理时，精确匹配会误杀有效选择——这正是 LLM 裁判更有用的地方。

### 参数正确性

模型选定工具后，检查它生成的参数。这个检查分两部分：结构和值。

结构校验抓的是：非法 JSON、缺失必填字段、类型错误、非法枚举值，以及工具不接受的参数。

一个结构合法的调用，值仍可能是错的。

```
{
  "order_id": "ord_7282"
}
```

`order_id` 定义为字符串，这个载荷就满足 schema。但用户问的是 `ord_7281`，它仍然是错的。

现成评估框架做的是同一个切分：DeepEval 把 [Tool Correctness](https://deepeval.com/docs/metrics-tool-correctness) 和 [Argument Correctness](https://deepeval.com/docs/metrics-argument-correctness) 分成两个指标，Phoenix 为 [tool selection](https://arize.com/docs/phoenix/evaluation/pre-built-metrics/tool-selection) 单设一个评估器。

## 方法 1：无参照 LLM 裁判

无参照裁判不需要固定期望答案就能给一次工具调用打分。正确性取决于上下文、或多个选择都可能成立、代码里没有单一值可比时，这个方法有用。

工具选择上，把用户的请求、agent 可用的工具清单和模型的输出一起给裁判，让它判断所选工具是否恰当——包括模型本来是否应该干脆不用工具。

想象一个同时有 `web_search` 和 `search_internal_docs` 的研究 agent：未必存在唯一正确的选择，更好的工具取决于用户问了什么、对话里已有什么信息。

参数上同样的问题也存在：一条搜索查询、描述或日期范围可能完全符合 schema，却没能表达用户的意思。没有固定值可比时，裁判可以评语义。

无参照裁判仍然需要清晰的"什么算正确"的指令。比较候选模型时，把指令和裁判模型都固定；全量使用之前，先拿一小批你亲自复核过的用例检查裁判的判断。

相等检查、schema 校验器或业务规则能可靠回答同一个问题时，用它们，别用裁判。

## 方法 2：参数的确定性 schema 检查

不是每个参数错误都需要另一次模型调用。工具 schema 能证明失败时，就在代码里验证。

看这个工具定义：

```
tools = [
    {
        "type": "function",
        "function": {
            "name": "lookup_order",
            "description": "Look up an order by its ID.",
            "parameters": {
                "type": "object",
                "properties": {
                    "order_id": {"type": "string"},
                    "include_items": {"type": "boolean"},
                },
                "required": ["order_id"],
                "additionalProperties": False,
            },
        },
    }
]
```

发给模型的同一份 schema，可以用来验证它返回的参数。缺失的 `order_id`、该是 boolean 的 `include_items` 传了字符串、未声明的字段如 `customer_email`——都能抓到。

## 方法 3：轨迹比较

工具选择和参数检查覆盖的是单次调用。多步 agent 还会在调用序列上失败。序列本身是需求的一部分时，轨迹比较直接测它。

一个退款流程可能要求依次三步：

```
lookup_order
    ↓
verify_refund_eligibility
    ↓
issue_refund
```

严格匹配只在"顺序是硬要求"时才有意义。[LangSmith 的轨迹评估器](https://docs.langchain.com/langsmith/trajectory-evals)正因如此支持 strict、unordered、subset、superset 四种匹配。严格检查强求一个序列，其余模式接受不同顺序、或只要求特定的调用集合。

agent 基准也用同样的处理方式。[τ²-bench](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md) 里，记录的动作列表是一条参照轨迹，回放它推导出数据库的目标终态；任何能产出等价终态的工具调用序列都通过数据库检查。

`lookup_customer` 和 `lookup_subscription` 两种先后都行的话，别因为你的参照用了另一种就判这条序列失败。改为检查必需的调用集合或 resulting 终态。

一个测试用例可以叠用多个检查：先比对工具名，再用 JSON Schema 验证参数，然后把已知参数值与期望载荷比对。

## 把同一套评估跑在多个模型上

定义好测试用例和评分器之后，同一套 harness 可以逐个跑在每个候选模型上。

我们在所有受支持模型上暴露[同一个工具调用接口](https://openrouter.ai/docs/guides/features/tool-calling)，比较哪个模型都不需要单独接一家提供商。

示例把 `tool_choice` 设为 `"auto"`。提供 tools 时这本来就是默认，显式写出来是为了让"无工具测试"更好读。

这个例子用 OpenAI Python SDK 配我们的 OpenAI 兼容端点。先装依赖：

```
pip install openai jsonschema
```

在环境里设好 `OPENROUTER_API_KEY`，然后把同一批用例跑在每个候选模型上。

```
import json
import os

from jsonschema import Draft7Validator, ValidationError
from openai import OpenAI

client = OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key=os.environ["OPENROUTER_API_KEY"],
)

tools = [
    {
        "type": "function",
        "function": {
            "name": "lookup_order",
            "description": "Look up an order by its ID.",
            "parameters": {
                "type": "object",
                "properties": {
                    "order_id": {"type": "string"},
                },
                "required": ["order_id"],
                "additionalProperties": False,
            },
        },
    }
]

tool_schemas = {
    tool["function"]["name"]: tool["function"]["parameters"]
    for tool in tools
}

test_cases = [
    {
        "name": "known order",
        "messages": [
            {
                "role": "user",
                "content": "Check the status of order ord_7281.",
            }
        ],
        "expected_calls": [
            {
                "name": "lookup_order",
                "arguments": {"order_id": "ord_7281"},
            }
        ],
    },
    {
        "name": "no tool needed",
        "messages": [
            {
                "role": "user",
                "content": "What does an order status of 'shipped' mean?",
            }
        ],
        "expected_calls": [],
    },
]

models = [
    "anthropic/claude-opus-5",
    "openai/gpt-5.6-sol",
    "moonshotai/kimi-k3",
]


def grade_case(model, case):
    response = client.chat.completions.create(
        model=model,
        messages=case["messages"],
        tools=tools,
        tool_choice="auto",
        extra_body={
            "reasoning": {"effort": "low"},
            "provider": {"require_parameters": True},
        },
    )

    calls = response.choices[0].message.tool_calls or []
    expected_calls = case["expected_calls"]

    actual_names = [call.function.name for call in calls]
    expected_names = [call["name"] for call in expected_calls]
    tool_selection = actual_names == expected_names

    schema_results = []
    parsed_calls = []

    for call in calls:
        name = call.function.name
        schema = tool_schemas.get(name)

        if schema is None:
            schema_results.append(False)
            continue

        try:
            arguments = json.loads(call.function.arguments)
            Draft7Validator(schema).validate(arguments)
        except (json.JSONDecodeError, ValidationError):
            schema_results.append(False)
            continue

        schema_results.append(True)
        parsed_calls.append(
            {
                "name": name,
                "arguments": arguments,
            }
        )

    schema_valid = all(schema_results) if calls else None

    argument_values = None
    if expected_calls:
        argument_values = (
            schema_valid is True
            and parsed_calls == expected_calls
        )

    if expected_calls:
        passed = (
            tool_selection
            and schema_valid is True
            and argument_values is True
        )
    else:
        passed = tool_selection

    return {
        "tool_selection": tool_selection,
        "schema_valid": schema_valid,
        "argument_values": argument_values,
        "passed": passed,
    }


for model in models:
    results = [
        grade_case(model, case)
        for case in test_cases
    ]

    passed = sum(result["passed"] for result in results)

    print(f"{model}: {passed}/{len(results)} cases passed")

    for case, result in zip(test_cases, results):
        print(f"  {case['name']}: {result}")
```

正确的"无工具"用例计入工具选择和整体结果——它没有 schema 或参数载荷可评。对返回了工具的用例，harness 先验证每一个调用，再把返回的值与期望载荷比对。

harness 给所有候选统一设 `reasoning.effort` 为 `low`，免得默认推理强度的差异被当成工具调用准确率的差异。上面三个模型在 models 端点的 `reasoning` 对象的 `supported_efforts` 数组里都列着 `low`。它还设了 `provider.require_parameters` 为 `true`：模型的 `supported_parameters` 列表可能包含某个只有该模型部分提供商端点接受的参数，默认路由下不支持该参数的提供商照样收到请求并忽略它；设了 `require_parameters` 后，请求只路由到支持其中每个参数的提供商，每条被评分的响应都跑在 harness 要求的强度上。该字段见[提供商路由](https://openrouter.ai/docs/guides/routing/provider-selection#requiring-providers-to-support-all-parameters)。harness 没设 `temperature`，因为 `openai/gpt-5.6-sol` 的 `supported_parameters` 里不列 `temperature`。你列表里的每个候选都接受 `temperature` 时，也把它显式设上。

上面的模型 ID 只是示例。[models 端点](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties)的每个条目有 `supported_parameters` 数组，数组里同时有 `tools` 和 `tool_choice` 的模型才支持这套 harness。把候选清单钉进长期评估套件之前，先查当前的[工具调用模型合集](https://openrouter.ai/collections/tool-calling-models)。

认真的对比里，每个测试用例要跑多次，别让模型的分数建立在单次响应上。更大的套件还应包含你的应用真会遇到的难题：缺参数、描述相近的工具、一次多个调用、以及不该用工具的请求。

这套 harness 评的是一轮工具调用。多步 agent 要收集整条轨迹上的所有调用，按工作流要求比较序列或 resulting 终态。

提供商路由也会影响你的比较到底在测什么。[Auto Exacto](https://openrouter.ai/docs/guides/routing/auto-exacto) 默认在每个带 tools 的请求上运行、为你选的模型重排提供商，因此可能改变哪个提供商端点服务这次工具调用。它的输入之一是工具调用错误率：对每个带 tools 的请求，我们检查模型返回的每个工具调用，把结构性失败归类为 `InvalidJson`、`UnknownName` 或 `SchemaMismatch`——按 JSON Schema Draft 7 用你提供的 `parameters` schema 验证 `arguments`。这个指标测的是提供商行为，不能替代你自己 harness 里的本地 schema 验证——这就是上面的例子自己验参数的原因。

想测应用在生产中会用的路由配置，就给所有候选保持 Auto Exacto 开启。想做端点级对比，就用我们的[提供商路由控制](https://openrouter.ai/docs/guides/routing/provider-selection)钉住提供商：`provider` 对象里 `order` 填该提供商 slug、`allow_fallbacks` 设 `false`，每个请求都落在同一个端点。

运行之间保持提示词、工具、测试用例、裁判模型和评估标准一致。采样和推理参数如 `temperature`、`reasoning` 显式设置而不是靠默认值，并确认每个候选支持你设的参数。harness 里别设 `max_tokens`：被截断的响应会砍掉工具调用的 JSON，表现为 `InvalidJson` 失败——和模型的工具选择毫无关系。

不想自己维护跨模型运行器的话，[Ori Eval](https://openrouter.ai/blog/announcements/ori-eval/) 会让你的 agent 对着候选模型跑、对它调用和避开的工具做断言，并用 LLM 裁判给开放答案打分。

## 常见错误

测试用例或评分规则太窄，工具调用评估给你的就是误导性结果。

- **只测干净的请求。**加入信息不全的用例、相似的工具、不该调用工具的用例，以及模型应该追问值而不是编造值的提示词。
- **只检查 `tool_calls[0]`。**一个响应可能包含多个调用，整个数组都要评。
- **把合法载荷当正确载荷。**schema 校验判断不了一个合法的值是不是对的客户、订单、日期或金额。
- **模型之间改动评估。**工具、提示词、裁判、模型设置或路由策略一变，比较的就不再是同一件事。
