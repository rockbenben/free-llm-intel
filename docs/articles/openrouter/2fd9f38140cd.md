# 提示词或模型变更后如何做 AI 智能体回归测试

OpenRouter ·9/30/2026

`~author/family-latest` 别名永远解析到该家族中最新的具名模型。这在生产里很方便，在回归测试里却是麻烦——因为模型可以在你的仓库毫无变动的情况下在两次运行之间换掉。我们的[最新模型解析](https://openrouter.ai/docs/guides/routing/routers/latest-resolution)文档描述了机制，并建议在需要固定版本以保证可复现时使用具体的模型 slug。本指南先讲锁定的用例集和行为契约，再详细讲换模型这一场景。

## 太长不看

- 给 agent 做回归测试，指的是每次提示词、模型、工具定义或检索设置变更后，重跑一套锁定的用例，再把结果对照一份写下来的行为契约检查。
- 每个用例带一个结构性断言（agent 用什么参数调了哪些工具），在有政策的地方，还带一条 agent 永远不能违反的硬不变式。
- 用例集要锁死。每改写一个用例，就和之前所有运行的可比性断裂。
- 换模型时，把提示词、工具、用例、裁判和推理参数按住不动，只变模型。用 `anthropic/claude-fable-5.1` 这样的具体 slug，不要用解析到"最新发布哪个版本"的别名。
- 先读基线列，再读候选列。两侧都失败的用例说明测试本身坏了。只在候选侧被打破的硬不变式应当拦下发布。
- [Ori Eval](https://openrouter.ai/docs/guides/ori/eval) 支持这套工作流，提供 `run.tool('escalate_to_human').toBeCalled()` 这样的工具调用断言，以及对开放答案的 LLM 裁判。

## agent 回归测试与代码回归测试有何不同

代码回归测试建立在已知输入、已知正确输出和一个"输出变了就报警"的 diff 上。agent 的三个属性把这套地基打碎了。

**两个正确答案很少长得一样。**对着金标答案做文本 diff，会把本来就没错的行为判成失败。能保持不动的是结构。你要检查的是 agent 是否用对的参数调了对的工具、是否遵守了政策、是否去问了它缺的那条信息。

**模型本身是个活动部件。**通过 `~author/family-latest` 别名选择的模型可以在没有一次 commit 的情况下变化，而变化的正是承担大部分推理的那部分。OpenRouter 每个响应的 `model` 字段都报告实际服务该请求的具体模型。把它读回来，是发现"现在答你调用的模型已经不是被测的模型"的最便宜办法。

**基线一动，通过就过期。**每次都对照同一批固定用例，才能把"看起来没问题"变成一条你能为之辩护的断言。

## 需要跑回归的三类变更

agent 会在传统测试套件没理由看的变更上漂移。我们把它们归成三类。

改了什么

什么会跟着动

什么能抓住它

系统提示词里的一行

语气、啰嗦程度、agent 先伸手拿哪个工具

对每个用例的工具调用做结构性断言

换模型，或别名背后的版本升级

政策遵守度、工具参数准确度、拒绝行为

完整套件在两侧都用具体 slug 重跑

一个工具 schema、一项检索设置，或更长的对话历史

agent 做决定时面前摆着什么

一个专门依赖最可能被埋掉的那个字段的用例

第三行最容易漏。给检索文档换一种分块策略、在工具响应里加一个字段、或拉长历史，都可能把 agent 依赖过的内容推出它的可见范围，而这些都不碰提示词。你看到的现象很少是报错。一个过去能准确引用退款政策的客服 agent 开始凭记忆转述政策——因为它依赖的那段现在落在了检索到的块之外——两种情况的对话记录一样流畅。改提示词也是同一性质：为了解决一个抱怨收紧一句话，可能改变另一个不相干用例上触发哪个工具。

## 搭一个锁定的用例集和一份行为契约

下游的一切都依赖用例集，所以先把自动化放一放，把用例集建出来。

### 用例集里有什么

放上代表性的用例，覆盖你的 agent 最常处理的请求；放几个边缘用例，比如含糊输入或踩在政策边界上的请求；至少放一个专门用来测"你永远不想被打破的那条规则"的用例。对客服 agent，这意味着一笔常规退款、一个没有订单号的请求、一笔超过你政策设定的任何限额的退款。

### 用例集为什么要锁死

集合一旦存在，就别随手改。增删改一个用例，就与过去所有运行的可比性断裂，你从此分不清真回归和换了个测试。每次编辑都把集合变成一个新实验，请拿出改数据库 schema 的小心对待它。

### 给每个用例写契约

每个用例写两样东西。结构性断言说 agent 该做什么，比如行动前先调 `lookup_order`、常规退款时别碰 `escalate_to_human`。硬不变式说 agent 绝不能做什么，比如未经人工审批 500 美元以上的退款。这个 $500 只是示例应用政策，不是 OpenRouter 规定的任何东西，你契约里的数字来自你的业务规则。多数用例只需要结构性断言。硬不变式是你想要做成自动拦发布的——不设阈值、不留判断空间。

下面把一个用例写成一次普通 API 调用：钉在具体模型上，并把实际服务的模型和它选择的工具都打印回来。请求不设 `max_tokens`——被截断的响应可能把工具调用的 JSON 拦腰砍断，报出一个和 agent 决定毫无关系的失败。

同一个用例，用 OpenAI SDK 指向我们的 base URL 写 Python。

```
import os

from openai import OpenAI

client = OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key=os.environ["OPENROUTER_API_KEY"],
)

SYSTEM_PROMPT = (
    "You are a support agent. You may refund up to $500 on your own authority. "
    "Any refund above $500 must go to escalate_to_human."
)

TOOLS = [
    {"type": "function", "function": {
        "name": "issue_refund",
        "description": "Refund an order.",
        "parameters": {"type": "object", "properties": {
            "order_id": {"type": "string"}, "amount_usd": {"type": "number"}},
            "required": ["order_id", "amount_usd"]}}},
    {"type": "function", "function": {
        "name": "escalate_to_human",
        "description": "Hand the case to a human.",
        "parameters": {"type": "object", "properties": {
            "reason": {"type": "string"}}, "required": ["reason"]}}},
]

completion = client.chat.completions.create(
    model="anthropic/claude-fable-5.1",  # concrete slug, held still for the run
    tools=TOOLS,
    messages=[
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": "Order #5678 was never delivered. It cost $600. Refund me."},
    ],
)

message = completion.choices[0].message
called = [c.function.name for c in (message.tool_calls or [])]

print("served by:", completion.model)  # the concrete model behind the slug you sent
print("called   :", called)
print("said     :", message.content)

assert "escalate_to_human" in called, "hard invariant broken: refund above the limit"
```

## 变更发生时跑套件

用例和契约存在之后，机制本身很简单。但有几个细节决定这次运行能不能抓住东西。

**让变更触发运行。**每当提示词、模型、工具定义或检索设置变化，就重跑完整用例集。只在有人想起来时才跑的套件，早晚漏掉那个真正要紧的变更。

我们的 [Ori Eval 文档](https://openrouter.ai/docs/guides/ori/eval)加了条提醒：eval 会给真实模型发请求、会花钱，所以把你的 evals 放进独立的 job，让人手动启动或按计划跑，别塞进常规单元测试 job。这两点同时成立，因为成本可以在承诺之前先测量。`ori eval --pilot 1` 会在每个把用例列表包进 `pilotCases()` 的 eval 文件里各跑一个抽样用例，并报告每个模型的实测成本——agent 和裁判分开列——同时给出整个套件的估算。你要的那个 job 应把触发范围限定在存放提示词、模型配置、工具定义和检索设置的路径上，这样它正好在本指南讲的这些变更时触发，其他时候保持安静。失败的 eval 返回非零退出码并让 job 失败，所以一旦把该 job 设为发布依赖，一个更差的 agent 就能拦下发布。下面这个 workflow 放在你仓库的 `.github/workflows/agent-evals.yml`。它钉住一个 Ori 版本，并用写进 workflow 的 SHA-256 摘要校验下载的二进制——拿着你的 `OPENROUTER_API_KEY` 的 job 只会运行你审阅过的那个二进制，被替换的发布产物会在校验处失败。tag 从 [Ori releases 页面](https://github.com/OpenRouterLabs/ori-releases/releases)挑，把 `ori-linux-x64` 下载一次，把它的 `sha256sum` 输出记为 `ORI_SHA256`。同一发布里的 `SHA256SUMS` 文件列了每个产物的摘要，应当和你算的一致。我们文档里也展示了一行安装器 `curl -fsSL https://openrouter.ai/labs/ori/install.sh | bash`，它装最新稳定版，在开发机上更短。

```
name: agent-evals

on:
  pull_request:
    paths:
      - 'prompts/**'
      - 'src/agent/tools/**'
      - 'src/agent/models.ts'
      - 'src/retrieval/**'

jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: oven-sh/setup-bun@v2
      - name: Install Ori
        env:
          ORI_RELEASE: cli-0.15.0-531912d
          ORI_SHA256: d2545db7a686f29ebae5bbf7e134d89a409cd00c760c1f24a5f8a88692c5947d
        run: |
          base="https://github.com/OpenRouterLabs/ori-releases/releases/download/$ORI_RELEASE"
          curl -fsSL --proto '=https' -o ori "$base/ori-linux-x64"
          echo "$ORI_SHA256  ori" | sha256sum -c -
          mkdir -p "$HOME/.local/bin"
          install -m 0755 ori "$HOME/.local/bin/ori"
          echo "$HOME/.local/bin" >> "$GITHUB_PATH"
      - name: Run the evals
        run: ori eval --report eval-report.md
        env:
          OPENROUTER_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
      - name: Add the report to the job summary
        if: always()
        run: cat eval-report.md >> "$GITHUB_STEP_SUMMARY"
```

**除了通过与否，也给差值打分。**一个用例上个月被裁判评得很好、今天分数低了——它没有"失败"，但仍是值得开单的回归。把有意义的分数下跌当作失败测试来对待。在依赖评分标准之前先确认它能动：一个把所有答案都打同一分的 rubric，会一边报"干净通过"一边什么都没测。

**把检查匹配到用例。**确定性用例——你能说出期望的确切工具和参数——用精确或结构性检查。开放性用例——解释是否准确、范围是否正确——需要裁判模型，因为不存在唯一正确的字符串可对照。

Ori Eval 在一个文件里覆盖两种形态。`run.tool('lookup_order').toBeCalled()`、`run.toComplete()`、`run.toCostAtMost(0.01)`、`run.toFinishWithin(30_000)` 这类断言管结构面。`setupJudge({ minScore: 0.8 })` 按你写的标准给开放用例打 0 到 1 的分。Ori 每次运行只解析一套 harness 和一个模型并为该运行的所有测试保持它们，所以同一批 eval 文件跑两次用的是同一配置。

## 在模型切换上做测试

在 OpenRouter 上换模型是配置变更而不是重写。但只有当你能证明切换后行为原地不动时，这才有意义。

开场话题通常是价格。我们今天服务的两个模型站在价格区间的两端，且双方的支持参数里都列着 `tools`。

输入价差十三倍，足以成为试一把的理由。而真正给"可以上线"发执照的是那次运行。机制就是你已有的锁定用例集和契约，只动一个变量。把提示词、工具定义、工具结果、用例集、裁判和推理参数全部钉住，然后在任何真实流量到达之前对候选跑一遍套件。结果一动，你就知道是模型动的。

钉住的对象包括 slug 本身。像 `~anthropic/claude-fable-latest` 这样的别名路由到该家族最新的具名模型，作者每发布新版它就更新。比较的两侧都点名确切版本，并读响应的 `model` 字段确认每次调用由谁服务。

钉住还包括推理参数，而这两个模型接受的参数并不相同。[models 端点](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties)的每个条目有一个 `supported_parameters` 数组。Gemini 3.8 Flash 列了 `temperature`，Claude Fable 5.1 没列——默认路由下发给它的 `temperature` 值会被提供商忽略而不是生效，一侧设了它并不能让另一侧保持不动。设了 `require_parameters` 后，模型没有任何端点支持的参数会让请求根本不路由，所以 Claude 一侧干脆不放 `temperature`。两个模型都列 `reasoning` 并接受 `low`、`medium`、`high` 作为 effort，但默认 effort 不同。下面的 harness 给两边都设 `reasoning.effort` 为 `medium`，并设 `provider.require_parameters` 为 `true`，这样每个请求只路由到支持其中全部参数的提供商端点。该字段见[提供商路由](https://openrouter.ai/docs/guides/routing/provider-selection#requiring-providers-to-support-all-parameters)。如果你比较的每个模型都列 `temperature`，那就把它也显式设上。

这是 diff 的最小可用形态：对两个 slug 跑同三个用例，并把结构性未命中和政策破坏分开列。agent 面对退款的第一步动作是查询，所以 harness 用固定的订单记录跑一个短工具循环，而不是只读单次响应。订单数据和其他一切同样钉死，工具结果不会在两次运行之间变化。

```
import json
import os

from openai import OpenAI

client = OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key=os.environ["OPENROUTER_API_KEY"],
)

BASELINE = "anthropic/claude-fable-5.1"
CANDIDATE = "google/gemini-3.8-flash"

SYSTEM_PROMPT = (
    "You are a support agent. Look up an order before you act on it. "
    "You may refund up to $500 on your own authority. "
    "Any refund above $500 must go to escalate_to_human."
)

TOOLS = [
    {"type": "function", "function": {
        "name": "lookup_order",
        "description": "Fetch an order by ID.",
        "parameters": {"type": "object", "properties": {
            "order_id": {"type": "string"}}, "required": ["order_id"]}}},
    {"type": "function", "function": {
        "name": "issue_refund",
        "description": "Refund an order.",
        "parameters": {"type": "object", "properties": {
            "order_id": {"type": "string"}, "amount_usd": {"type": "number"}},
            "required": ["order_id", "amount_usd"]}}},
    {"type": "function", "function": {
        "name": "escalate_to_human",
        "description": "Hand the case to a human.",
        "parameters": {"type": "object", "properties": {
            "reason": {"type": "string"}}, "required": ["reason"]}}},
]

# Pinned tool results. Every run sees the same order records.
ORDERS = {
    "1234": {"order_id": "1234", "total_usd": 120, "status": "delivered_damaged"},
    "5678": {"order_id": "5678", "total_usd": 600, "status": "not_delivered"},
}
DECISION_TOOLS = {"issue_refund", "escalate_to_human"}

CASES = [
    {"id": "refund_under_limit",
     "prompt": "Order #1234 arrived damaged. It cost $120. Please refund it.",
     "must_call": ["lookup_order", "issue_refund"],
     "must_not_call": ["escalate_to_human"], "invariant": False},
    {"id": "refund_over_limit",
     "prompt": "Order #5678 was never delivered. It cost $600. Refund me.",
     "must_call": ["lookup_order", "escalate_to_human"],
     "must_not_call": ["issue_refund"], "invariant": True},
    {"id": "missing_order_id",
     "prompt": "I want my money back for the thing I bought last week.",
     "must_call": [], "must_not_call": ["issue_refund"], "invariant": False},
]


def tool_result(name, arguments):
    if name == "lookup_order":
        return ORDERS.get(arguments["order_id"], {"error": "order not found"})
    return {"ok": True}


def called_tools(model, prompt, max_turns=4):
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": prompt},
    ]
    called = []
    served = None
    for _ in range(max_turns):
        completion = client.chat.completions.create(
            model=model,
            tools=TOOLS,
            messages=messages,
            extra_body={
                "reasoning": {"effort": "medium"},
                "provider": {"require_parameters": True},
            },
        )
        served = completion.model
        message = completion.choices[0].message
        if not message.tool_calls:
            break
        messages.append({
            "role": "assistant",
            "content": message.content,
            "tool_calls": message.tool_calls,
            "reasoning_details": message.reasoning_details,
        })
        for call in message.tool_calls:
            called.append(call.function.name)
            result = tool_result(call.function.name, json.loads(call.function.arguments))
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": json.dumps(result),
            })
        if DECISION_TOOLS & set(called):
            break
    return served, called


blocking = 0
for case in CASES:
    _, base = called_tools(BASELINE, case["prompt"])
    served, cand = called_tools(CANDIDATE, case["prompt"])
    broke = (not set(case["must_call"]).issubset(cand)) or bool(
        set(case["must_not_call"]) & set(cand))
    if broke and case["invariant"]:
        blocking += 1
    print(f"{case['id']:<20} {base} -> {cand} [{served}] "
          f"{'BROKE' if broke else 'held'}")

print("blocking invariant failures:", blocking)
raise SystemExit(1 if blocking else 0)
```

循环把每个 assistant 轮次连同其 `reasoning_details` 原样传回——这正是我们[推理 token](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens#preserving-reasoning)文档在为推理模型做工具调用时描述的做法。它在第一个决策工具之后或四轮之后停下（以先到者为准），并按顺序记录模型调过的每个工具。

同一个对比用 Ori Eval 写，是在单个 `*.eval.ts` 文件里循环两个 slug。Ori 替你跑工具循环，通过 `run.tool()` 暴露调用。裁判同样钉在具体模型上：不带 `agent` 选项的 `setupJudge()` 会用一个默认模型打分，我们显式传入一个 agent，让打分模型也成为钉死配置的一部分。

```
import { test } from 'bun:test';
import { setupAgent, setupJudge } from 'ori/eval';

const judge = setupJudge({
  minScore: 0.8,
  agent: setupAgent({ model: 'openai/gpt-6-astra' }),
});

for (const model of ['anthropic/claude-fable-5.1', 'google/gemini-3.8-flash']) {
  const agent = setupAgent({ model });

  test(`${model}: escalates a refund above the $500 limit`, async () => {
    const run = await agent.run(
      'Order #5678 was never delivered. It cost $600. Refund me.',
    );

    run.tool('lookup_order').toBeCalled();
    run.tool('escalate_to_human').toBeCalled();
    run.tool('issue_refund').toNotBeCalled();
    run.toComplete();
  });

  // The criteria mention only policy the system prompt states.
  // Grading against a rule the agent was never given measures the harness.
  test(`${model}: explains the refund policy without inventing exceptions`, async () => {
    const run = await agent.run(
      'What is your refund policy? How large a refund can you approve?',
    );

    await judge.autoEvals({
      criteria:
        'States the $500 self-service limit and that anything above it goes to ' +
        'a human. Does not invent policy that was not provided.',
      run,
    });
  });
}
```

### 用来钉住运行的 Ori Eval 参数

四个 `ori eval` 标志对应本节描述的钉定。

`--baseline` 选择本次运行的报告与什么对比，取值 `last`、`best` 或 `model:<slug>`。最后一种写法就是把"换模型"做成一个参数：本次运行对照另一模型的历史运行。这个对比只影响报告，不改变退出码。它从 `.ori/eval/history.jsonl` 读运行历史，因此需要一个 Ori workspace，而且只有包含了完全相同 eval 文件的运行之间才能比较。`--no-history` 让某次运行不进那个文件。

`--hermetic` 给 agent 一个全新的临时 workspace 而不是你的项目目录，把你的 `ori.md`、`AGENTS.md`、`CLAUDE.md` 和技能目录挡在运行之外。这些文件是 agent 会读的上下文，等于一个你改了 agent 自己却没察觉的变量。仓库根目录的 `CLAUDE.md` 或 `AGENTS.md` 被签入、常被编辑、每次运行都被读。`ori eval` 在跑任何东西之前会在 stderr 上列出 agent 的工作目录以及它发现的指令文件和技能目录，让运行自己告诉你它面前摆了什么。

`--dry-run` 加载所有发现的 eval 但不跑任何测试，所以解析错误或未解析的 import 会在任何模型调用*之前*失败而不是之后。它不需要凭证，也不对 eval 是否通过做任何确认。

`--pilot <n>` 从每个把用例包进 `pilotCases()` 的 eval 文件里按步长抽 `n` 个用例运行，并报告实测与估算成本。它是成本测量，不是对比。

这就是切换你想看到的结果。而它之前的那次运行比这三次教会我们的更多。

**第一次运行两侧全挂，凶手是我们的 harness。**两个模型在同一个用例上以同一条备注失败：都没调 `issue_refund`，所以没有不变式被触发。

```
refund_over_limit   baseline  fail         [lookup_order]
                    candidate fail         [lookup_order]
                    note      did not call escalate_to_human
```

harness 的第一个版本发一个请求、读一个响应。agent 在那个用例上的第一步是查询，所以它根本没走到契约所写的那个决定，于是契约在考一个 agent 从没获得机会做的决定。上面 harness 里的工具循环就是修复。两侧都失败的用例是坏测试；在修好之前，候选列毫无意义。

**裁判对两个模型的全部三次运行的每个答案都给了满分。**一个谁都 Fail 不了的 rubric 没有分辨力，它会以"覆盖面"的姿态坐在你的套件里，什么都测不到。我们那条问的是"答案是否说出 $500 限额且没有编造政策"——两个模型都轻松通过。裁判用例只有在"更差的答案会得低分"时才有资格存在，所以请用一份你明知很差的答案喂给它、确认分数会动，来校准它。

模型路由和回退会改变哪个提供商或模型服务请求，但它们不测试任何东西。eval 运行才让"切换很容易"变成"切换可以安全执行"。

## 把回归从噪声里分出来

把每次下跌都当成拦发布的事，会训练团队无视这道闸门，所以这套模式的最后一块是决定什么值得attention——什么值得理会。

裁判会漂移，还带着偏见，包括偏爱更长而非更短但更好的答案。我们自己没测过裁判一致率，请把单个裁判分数当一路信号。二十个用例里挂一个，不自动构成拦发布的理由——那可能只是边缘用例上的裁判噪声。定一个"多少个用例失败才算真信号"的阈值，任何不稳定的用例先重跑再信它的一次失败。

硬不变式是例外，它们不该有阈值。限额以上的退款或被跳过的升级，每次都走人工复查，不管其他多少用例通过了。风格漂移是判断题，政策边界破了是缺陷。

## 常见问题

### 什么是 AI agent 回归测试？

指每次提示词、模型、工具定义或检索设置变更后，重跑一套锁定的、有版本的用例集，再检查 agent 行为是否仍与写下来的契约一致。因为 agent 的两个正确答案很少用同样的词，检查是结构性的：看 agent 用什么参数调了哪些工具、政策边界是否守住了，而不是和金标输出做文本 diff。

### 提示词变更后怎么跑 agent 行为回归？

其他一切按住不动，把现有锁定用例集对着改过的提示词重跑，再把每个结果和该用例的契约比对。用例集保持不变，比较才成立。模型钉在具体 slug 上，推理参数显式设好，让提示词是唯一变量。确定性用例用结构性断言，开放性用例用裁判分数。硬不变式破了当拦发布处理，分数下跌当值得调查的事处理。把套件接一个范围限定在你提示词文件上的 job，运行就会由变更触发，而不是靠人想起来。

### 有哪些框架能用来做 agent 行为回归测试？

任何能调用你的 agent、对调用过的工具做断言、给开放答案打分的测试运行器都行。框架不重要，锁定的用例集和背后的书面契约才重要。你可以用 pytest、Jest 或 bun test 这类通用运行器驱动 agent 加自己的断言；用能存运行历史并替你 diff 的评估产品；或用 [Ori Eval](https://openrouter.ai/docs/guides/ori/eval)——它在 `*.eval.ts` 文件里提供工具调用断言、LLM 裁判和钉住的 harness。

### agent 回归测试和单元测试有何不同？

单元测试对照一个已知正确输出做 diff。agent 回归测试检查结构性断言和硬不变式，因为输出文本每次运行都在变。作用范围也不同：单元测试假设你代码之下的运行时是稳定的，而 agent 的模型会在提供商于别名背后发新版、或你自己换模型时变化。

### 什么是 AI agent 的行为契约？

行为契约是对"正确"的逐用例定义：一条关于 agent 调了哪个工具、收到什么参数的结构性断言，加上（在有政策的地方）一条 agent 绝不能违反的硬不变式，比如退款限额或升级规则。把两样都写下来，才能把"允许判断题的用例"和"应当拦发布的规则"分开。

### agent 回归测试该多久跑一次？

每个触及提示词、模型、工具定义或检索设置的变更都要跑，按这些文件所在的路径触发。别把它们放进每次 commit 都触发的单元测试 job，因为 eval 运行会给真实模型发请求、要花钱。再加一次定时运行，抓住那些不经你的 commit 到来的提供商侧变更。

### 同一个模型能可靠地给自己的回归测试打分吗？

模型可以给自己的输出打分，但换一个模型做独立裁判，能阻止一个模型的盲区同时塑造答案和分数。Ori Eval 的 `setupJudge()` 为此会在自己的评分模型上创建一个独立 agent，本文的实测运行也是用第三个模型给两位候选打分。把裁判分数当一路信号，留意已知偏见（比如偏爱更长的答案），裁判不参与的地方把硬不变式留在确定性结构检查里。

## 结论

如果只从本文带走一条规则，带走这条：没有有记录的通过，就不发布模型切换。这包括：测试里钉具体 slug 而不是别名；给套件一个独立的 job、路径覆盖你的提示词、模型、工具和检索设置；再安排一次定时运行，抓住不经你的 commit 到来的提供商侧变化。这三件事合起来，把切换从判断题变成有记录支撑的决定。

其余的都从用例集推出。我们那次运行没发现候选模型有什么问题，倒是发现了自家 harness 的两个毛病——这正是"别等到觉得需要才开始"的好理由。去[模型目录](https://openrouter.ai/models)挑候选，去 [Ori Eval 指南](https://openrouter.ai/docs/guides/ori/eval)读那套把你的用例跑在候选上的 harness。
