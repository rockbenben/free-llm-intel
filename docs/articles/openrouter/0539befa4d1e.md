# 如何评估 LLM Provider 的延迟、吞吐与可用性表现

开发者选择 LLM 时常常先定模型——Claude、Llama、Gemini 或 DeepSeek——然后把 provider 当成次要决策。这可以理解。但仅凭模型选择，并不能告诉你该模型经由某个具体 provider 端点时的表现。

同一个模型可以通过多个 provider 端点运行，而每个端点的基础设施、路由行为、量化选择和故障模式都可能不同。你的用户和系统会在很实际的层面感受到这些差异。有的 provider 首 token 很快，但后续输出变慢；有的 provider 跑更低精度的 variant，在难题上会出现漂移；还有的 provider 正常流量下表现好，高负载下就崩。

Provider 评估比较的是服务环境，而不是把模型当作独立产品。它问的是：用户要等多久才见到首 token、响应的其余部分来得多快、provider 在负载下行为如何、模型跑在什么精度上。

本指南按你能据以行动的顺序讨论这些问题：延迟、吞吐、可用性、量化。能量化这些权衡之后，下一步是把结果转化为路由逻辑，让你的应用不再硬编码某一家「单次基准跑出来最快」的 provider。

## Tl;dr

- 同一个模型在不同 provider 端点上行为不同。基础设施、量化、负载处理、路由默认值都会改变结果，即使模型 slug 完全相同。
- 四项指标决定 provider 表现：延迟（首 token 时间）、吞吐（输出 tokens/秒）、可用性、量化。
- 延迟要看 p90/p99，不要看平均值。尾部才是面向用户的应用真正感受到的；批处理任务可以按 p50 评估。
- 量化是隐藏的质量变量。两家 provider 可以用不同精度服务同一模型；质量重要时用 `quantizations` 字段固定它。
- 用排行榜筛候选，然后在你自己的 prompt 上验证。基准测的是某一端点在某一时刻的表现；你的负载不是基准的负载。
- 把评估变成路由策略。设置 `provider.sort`、百分位阈值、`quantizations` 和 fallbacks，让 provider 选择始终锚定在你的测量上，而不是硬编码的名字。

## 评估 provider 表现的 4 项指标

聊天产品、文档生成流水线和后台摘要任务需要的性能画像不一样。正确的 provider 取决于负载。

| 指标 | 度量什么 | 何时重要 | 要看什么 |
| --- | --- | --- | --- |
| 延迟（首 token 时间） | 发出请求到收到第一个生成 token 的时间 | 面向用户的聊天、agent、流式界面和交互式工作流 | p90 和 p99 延迟，不只是典型延迟 |
| 吞吐（输出速度） | 生成开始之后每秒产出的输出 token 数 | 长回答、批量生成、文档起草、代码生成、摘要 | 整个生成过程中持续的 tokens/秒 |
| 可用性与健康度 | provider 随时间的健康状态、错误率和宕机行为 | 需要稳定完成行为的生产应用 | 故障转移行为、近期 provider 错误、恢复路径 |
| 量化 | 服务模型权重所用的精度级别 | 质量敏感的 prompt、推理、编码、长上下文任务 | 更低精度可降低成本与内存，但也可能损害难题表现 |

一家 provider 可能在响应开头显得快，但等完整答案出来时仍让你觉得慢。首 token 时间（TTFT）捕捉体验的前半段；输出速度捕捉后半段，因为它度量生成开始后 provider 每秒生成多少 token。TTFT 很强的 provider，若持续 token 速率下滑，长文体验仍可能很差；吞吐很强的 provider，若首 token 迟到，在聊天界面里仍可能体感糟糕。

可用性补上速度指标覆盖不到的生产层。一家在基准条件下表现良好的 provider，如果在高峰时段故障、意外限流、或引发迫使重试的错误尖峰，照样会伤害应用。

把这些测量分开之后，下一步是以适当的置信水平去读它们。中位延迟能描述典型请求，但生产系统还需要知道有多少请求远远慢于典型值。这就是 p50、p75、p90、p99 等百分位指标比平均值更有用的地方。

## 如何解读百分位延迟与吞吐

平均值会掩盖造成最差用户体验的那些请求。如果一家 provider 大多数请求响应很快，但偶尔严重卡住，平均值看起来可能仍然可以接受，但你的用户记住的是卡住的那次。

我们按每个模型和 provider，用滚动 5 分钟窗口的百分位统计跟踪[延迟与吞吐指标](https://openrouter.ai/docs/guides/routing/provider-selection)。可用的百分位是 p50、p75、p90 和 p99。

| 百分位 | 如何解读 | 它告诉你什么 |
| --- | --- | --- |
| p50 | 50% 的请求快于此值 | 典型性能 |
| p75 | 75% 的请求快于此值 | 中上体验 |
| p90 | 90% 的请求快于此值 | 请求尾部的稳定性 |
| p99 | 99% 的请求快于此值 | 最坏情况的尾部行为 |

p50 延迟值描述中位请求，但可能掩盖分布中远远偏出去的那些。一家 provider 可以 p50 很强、p99 很弱：典型请求体感没问题，但一小撮却意义不小的请求慢到造成可见延迟。

该看哪个百分位，取决于延迟实际伤害工作流的位置。聊天界面里，延迟出现在首 token 到来之前，所以 p90 和 p99 延迟能说明典型请求之外的体验是否稳定。批处理任务里，用户并不等着每个响应开始，所以持续输出速度更能反映系统长期能完成多少工作。

一个具体例子：2026 年 6 月 24 日（UTC），两家服务 `anthropic/claude-sonnet-4.5` 的 provider 在 1 天窗口上呈现了不同的延迟曲线，且两家的 p99 尾部都远比其 p50 值所暗示的更宽。

![Line chart of latency percentiles for Claude Sonnet 4.5 on Amazon Bedrock and Google Vertex, showing p50 values of 6.3s and 7.8s widening to p99 values of 77.4s and 92.1s](https://openrouter.ai/blog/images/evaluate-provider-latency-percentiles.png)

百分位展示 provider 响应的稳定性，但解释不了同一模型两家 provider 之间的所有差异。当延迟和吞吐看清之后，下一个问题是：两家 provider 是否在以相同形态服务这个模型。

## 为什么量化会改变 provider 结果

量化是最容易被忽略的 provider 差异之一，因为模型名字并不总能揭示模型如何被服务。两家 provider 可以暴露同一个模型 slug，却跑在不同精度上。一条路由可能保留更多原始权重精度，另一条可能降低精度以减少内存占用、提升服务效率，或让端点运营成本更低。

降低精度会改变模型在各种 prompt 下的行为。更低精度可以让模型更快、服务成本更低，但也可能改变模型处理需要谨慎推理、代码正确性、长上下文或严格指令遵循的 prompt 的方式。

我们把量化作为路由决策暴露出来，因为 provider 选择不应把同名模型的每个端点视为等价。[quantizations](https://openrouter.ai/docs/guides/routing/provider-selection) 字段让你选择应用可以使用的精度级别，让质量风险成为路由策略的一部分，而不是藏在 provider 侧的细节。

| 量化值 | 实际解读 | 质量风险 |
| --- | --- | --- |
| `fp32` | 最高精度，对大多数托管推理的经济性通常不现实 | 最低 |
| `fp16` | 常见的高质量推理精度 | 低 |
| `bf16` | 常见的高质量推理精度，常用于现代加速器 | 低 |
| `fp8` | 较低精度的浮点服务 | 低到中 |
| `int8` | 较低精度的整数服务 | 中 |
| `fp6` | 较低精度的浮点服务 | 中 |
| `fp4` | 非常低精度的浮点服务 | 较高 |
| `int4` | 非常低精度的整数服务 | 较高 |
| `unknown` | Provider 精度未知 | 未知 |

把这张表当作决策工具：你的负载能为更低的成本或更快的速度牺牲多少精度。一个摘要流水线也许可以容忍低精度端点，只要输出在你自己的测试集上保持稳定的话。而代码编辑工作流、tool-calling agent 或重推理任务，给不了你静默质量损失的余地——微小的漂移就能改变答案、打断调用，或产出看着合理实则失败的代码。

当评估表明某负载需要更高精度时，用 `quantizations` 字段限制应用可用的 provider 端点：

```
{
  "provider": {
    "quantizations": ["fp16", "bf16"]
  }
}
```

如果评估显示某 provider 的端点对你的 prompt 表现不佳，也可以排除它：

```
{
  "provider": {
    "ignore": ["provider-slug"]
  }
}
```

模型名字开启评估，provider 端点完成评估。量化正是公开基准与生产行为分道扬镳的原因之一。

## 如何读 provider 基准而不被骗

[公开排行榜](https://openrouter.ai/rankings)帮你缩小候选集，但描述不了你的生产路径。基准在某个时点测量所选端点，用的是它自己的 prompt、参数、区域和评分方法。你的应用使用的端点、prompt 形态或路由路径可能和基准测的不同。

一次有用的 provider 基准审查，应当先检查基准公布的方法学，再把结果当作生产证据：

| 问题 | 为什么重要 |
| --- | --- |
| 基准是否区分首 token 时间和输出速度？ | 不同负载在意的「快」不一样。 |
| 它报告尾部表现还是只报告平均表现？ | 尾部指标暴露平均值能掩盖的可靠性问题。 |
| 它是否指明 provider 端点与服务配置？ | 同一模型在不同 provider 上行为可能不同。 |
| 它是否考虑量化？ | 快的端点可能拿精度换服务效率。 |
| 它是否反映当前表现？ | 随流量、路由和基础设施变化，provider 的速度和可用性会漂移。 |
| 它是否匹配你的 prompt？ | 通用基准未必能预测你产品的负载。 |

当基准结果引出第二轮在你自己负载下的测试时，它才真正有用。如果排行榜指向一家快的 provider，下一个问题是那个端点在你的 prompt 长度、路由路径和质量要求下是否仍然快。如果是，就把结果转成路由规则。

从静态排名硬编码单一 provider 会造出脆弱的架构。Provider 行为随流量、宕机、路由路径和服务配置而变化。这正是我们路由层要处理的问题。

## 为什么多 provider 路由改变了 provider 评估

孤立地评估一家 provider，只能告诉你它在你的测量条件下如何表现。它无法告诉你当 provider 撞上速率限制、在高负载下变慢、或临时不可用时会发生什么。如果你的应用依赖单一 provider 端点，每一场 provider 侧故障都会成为你应用行为的一部分。

路由层把评估从一次性的 provider 选择变成持续的选择问题。你不再把每次 provider 宕机、限流或降速当作应用故障，而是可以自动绕开这些情况。

[我们实时监控各 provider 的响应时间、错误率和可用性](https://openrouter.ai/docs/guides/best-practices/uptime-optimization)。我们的默认路由会对过去 30 秒内出现显著宕机的 provider 降权，在稳定的 provider 之间按偏向低价的权重做负载均衡，其余保留为 fallback。

多 provider 路由不保证完美可用性。它的作用是在 provider 故障或不可用时提供替代路径，降低对单一端点的依赖。

[Model fallbacks](https://openrouter.ai/docs/guides/routing/model-fallbacks) 在 provider 级路由不够用时应用同样的原则。如果主模型因其 provider 宕机、被限流或无法回答而不能完成请求，OpenRouter 可以尝试 fallback 列表中的下一个模型。

一个务实的路由策略应回答三个问题：

| 问题 | 路由含义 |
| --- | --- |
| 应用能否容忍同一模型换 provider？ | 使用 provider 路由并允许 fallbacks。 |
| 应用能否在首个模型失败时换模型？ | 使用 model fallbacks。 |
| 应用是否因合规或合同要求严格控制 provider？ | 使用 provider `order`、provider `only`，或禁用 fallbacks。 |

## 把 provider 评估变成路由策略

![Flowchart mapping routing goals to provider settings: sort by price, throughput, or latency, quantizations for precision, ignore for avoiding a provider, fallbacks for resilience, and performance thresholds for SLA-like guardrails](https://openrouter.ai/blog/images/evaluate-provider-routing-flowchart.png)

主要[路由控制](https://openrouter.ai/docs/guides/routing/provider-selection)位于 `provider` 对象内。它们让你对 provider 排序、设置性能阈值偏好、选择或避开 provider 端点、按量化过滤、决定 fallback 是否可跑。Model fallback 使用 `models` 数组。

| 评估结果 | 路由设置 |
| --- | --- |
| 请求应首先使用最低价 provider | `provider.sort: "price"` 或 `:floor` 模型后缀 |
| 请求应优先更高的输出速度 | `provider.sort: "throughput"` 或 `:nitro` 模型后缀 |
| 请求应优先更低的首 token 时间 | `provider.sort: "latency"` |
| 请求应找到仍达到吞吐阈值的最低价格端点 | `provider.sort: { by: "price", partition: "none" }` 加 `preferred_min_throughput` |
| 请求应找到仍低于延迟阈值的最低价格端点 | `provider.sort: { by: "price", partition: "none" }` 加 `preferred_max_latency` |
| 负载需要特定服务精度 | `provider.quantizations` |
| 某 provider 没通过你的评估 | `provider.ignore` |
| 请求必须首先走某一条 provider 路径 | `provider.order` |
| 请求不得回退到其他 provider | `provider.allow_fallbacks: false` |
| 应用可在首个模型失败时用另一模型 | `models` fallback 数组 |

最简单的控制是[模型后缀](https://openrouter.ai/docs/guides/routing/provider-selection)。当请求应优先高吞吐 provider 时加 `:nitro`：

```
curl https://openrouter.ai/api/v1/chat/completions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "meta-llama/llama-3.3-70b-instruct:nitro",
    "messages": [
      { "role": "user", "content": "Write a concise product summary." }
    ]
  }'
```

当请求应优先低价时加 `:floor`：

```
curl https://openrouter.ai/api/v1/chat/completions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "meta-llama/llama-3.3-70b-instruct:floor",
    "messages": [
      { "role": "user", "content": "Write a concise product summary." }
    ]
  }'
```

当单一偏好应主导请求时这些快捷方式很有效。生产路由往往需要更窄的规则。例如，客服工作流可能需要仍能维持足够吞吐以处理较长摘要的最便宜端点。此时把价格排序和吞吐偏好组合起来：

```
import { OpenRouter } from '@openrouter/sdk';

const openRouter = new OpenRouter({
  apiKey: process.env.OPENROUTER_API_KEY,
});

const completion = await openRouter.chat.send({
  models: [
    'anthropic/claude-sonnet-4.5',
    'openai/gpt-5-mini',
    'google/gemini-3-flash-preview',
  ],
  messages: [
    {
      role: 'user',
      content: 'Summarize this customer support thread and identify the next action.',
    },
  ],
  provider: {
    sort: {
      by: 'price',
      partition: 'none',
    },
    preferredMinThroughput: {
      p90: 50,
    },
  },
  stream: false,
});
```

这个请求让 OpenRouter 在所列表模型中查看，优先选择达到 p90 50 tokens/秒的最便宜模型与 provider 端点。低于阈值的端点并不会从路由中消失，只是被排到偏好选项之后——当全部偏好端点失败时它们仍然可用。

聊天工作流可以用同样的模式做延迟。如果首 token 延迟是用户可见的瓶颈，把价格排序与延迟偏好组合：

```
const completion = await openRouter.chat.send({
  models: ['anthropic/claude-sonnet-4.5', 'openai/gpt-5-mini'],
  messages: [
    {
      role: 'user',
      content: 'Answer this user message in a support chat.',
    },
  ],
  provider: {
    sort: {
      by: 'price',
      partition: 'none',
    },
    preferredMaxLatency: {
      p90: 3,
    },
  },
  stream: false,
});
```

这个请求让价格仍在决策中，但优先选择把 p90 延迟保持在 3 秒以内的端点。这个偏好来自 provider 评估，而不是固定的 provider 选择。

同样的模式适用于质量和可靠性决策。如果某负载在更高精度端点上表现更好，加一个量化过滤器：

```
const completion = await openRouter.chat.send({
  model: 'deepseek/deepseek-v3.2',
  messages: [{ role: 'user', content: 'Review this code change for logic errors.' }],
  provider: {
    quantizations: ['fp16', 'bf16'],
  },
  stream: false,
});
```

如果某 provider 没通过你的测试集，或不满足你的运营要求，把它排除出路由：

```
const completion = await openRouter.chat.send({
  model: 'meta-llama/llama-3.3-70b-instruct',
  messages: [{ role: 'user', content: 'Draft a release note from these changes.' }],
  provider: {
    ignore: ['provider-slug'],
  },
  stream: false,
});
```

如果完成可靠性比死守单一模型更重要，用 [fallback 列表](https://openrouter.ai/docs/guides/routing/model-fallbacks)：

```
const completion = await openRouter.chat.send({
  models: [
    'anthropic/claude-sonnet-4.5',
    'openai/gpt-5-mini',
    'google/gemini-3-flash-preview',
  ],
  messages: [
    {
      role: 'user',
      content: 'Summarize this incident report and list the next actions.',
    },
  ],
  stream: false,
});
```

路由策略应当产生在测量之后，而不是之前。设定阈值之前，你需要一个简单的评估流程来告诉你哪些阈值重要。

## 5 步 provider 评估清单

- **先定义负载。**不要从 provider 开始，从你需要的产品行为开始。流式聊天应用应测首 token 时间和 p90 延迟。批量生成工作流应测吞吐和总完成时间。重推理工作流要加上质量检查和量化审查。
- **用外部基准和实时 provider 数据筛候选。**用[公开排行榜](https://openrouter.ai/rankings)确定候选，再到我们目录中该[模型页面](https://openrouter.ai/models)检查当前 provider 数据。
- **用你自己的 prompt 测试。**运行代表你产品真实负载的 prompt。包含短 prompt、长 prompt、简单 prompt，以及通常会搞垮弱势 provider 的那些 prompt。同时测速度、可靠性和输出质量。
- **检查量化与 provider 行为。**如果两家 provider 服务同一模型但一家的难题答案更差，先查服务路径再怪模型。当你的评估支持该决策时，固定更高精度或排除较弱端点。
- **用路由落实结果。**把评估转成[请求设置](https://openrouter.ai/docs/guides/routing/provider-selection)。用 `sort`、`:nitro`、`:floor`、`preferred_min_throughput`、`preferred_max_latency`、`quantizations`、`ignore` 和 fallbacks，让应用与测量保持一致。这让 provider 选择绑定在你的应用上而非泛化的市场排名，也让性能评审在 provider 行为随时间变化时依然可重复。

## FAQ

### LLM provider 的延迟与吞吐有何区别？

延迟度量用户在首 token 到达之前的等待时间。吞吐度量生成开始之后 provider 每秒产出的输出 token 数。聊天界面通常优先延迟，长输出工作流优先吞吐。

### p50、p90、p99 对 LLM 延迟意味着什么？

p50 是中位请求体验。p90 意味着 90% 的请求在此延迟值或更快之内完成。p99 展示分布的最远尾部，当应用必须对几乎所有用户可预期地响应时你需要它。

### 为什么同一个模型在不同 provider 上表现不同？

Provider 端点会改变服务环境。量化、基础设施、上下文支持、负载和 provider 默认设置都会影响输出行为。模型 slug 标识的是模型家族，但 provider 路径影响生产结果。

### 我该如何避开表现差的 provider？

确认问题确实随 provider 变化后，先在你自己的 prompt 上复现。如果问题可复现，用 `provider.ignore` 排除该 provider。如果问题看起来与更低精度有关，用 `provider.quantizations` 优先更高精度的端点。

### 多 provider 路由能提升可用性吗？

多 provider 路由可以在 provider 故障、限流或宕机时通过备用路径提升可靠性。它降低了对单一 provider 的依赖，但仍取决于路由策略的质量和可用的 provider。

### 使用故障转移有额外费用吗？

没有。请求按最终服务的模型与 provider 端点计价。OpenRouter 不在 provider 价格上加价，无论路由到一家还是十家 provider，失败的请求都不计费。

### 我该怎么路由到最快的 provider？

在意首 token 时间时用 `provider.sort: "latency"`。在意长文生成速度时用 `provider.sort: "throughput"` 或 `:nitro` 后缀。当你需要可预期的性能而非单纯速度偏好时，加上百分位阈值。
