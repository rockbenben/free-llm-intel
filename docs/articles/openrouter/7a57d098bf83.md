# 用 Fusion 超越前沿模型表现

我们发现，综合多个模型的结果可以显著超越单个模型的能力上限。介绍 Fusion：一个让你像调用单个模型一样轻松获得综合结果的工具。你可以选择一组参与模型（panel），再指定一个负责把各家结果融合在一起的裁判模型（judge）。

为了理解 Fusion 的收益，我们使用了一个同时考察推理、工具使用与知识储备的深度研究基准。我们发现：

- 模型面板（panel）稳定优于单个模型
- 用前沿模型组面板即可达到超越前沿的表现
- 平价模型组的面板可以击败前沿模型，并逼近前沿面板的成绩

现在就在 chatroom 里[试试 Fusion](https://openrouter.ai/fusion)，或查看 [API 文档](https://openrouter.ai/docs/guides/features/server-tools/fusion)把它集成进你的应用。

## 模型面板在深度研究任务上稳定胜出

我们在 [DRACO 基准](https://arxiv.org/abs/2602.11685)的 100 个深度研究任务上测试了 Fusion。部分亮点：

- Fable 5 + GPT-5.5** 融合得分 69.0%**，超过每一个单独模型，包括 Fable 5 单跑的 65.3%**。
- 一个平价面板（Gemini 3 Flash、Kimi K2.6 和 DeepSeek V4 Pro）击败了 GPT-5.5 和 Opus 4.8，距离 Fable 5 的分数只差 1%，而成本只有其 50%。

## 一次 API 调用，融合多个模型的最佳输出

当你向 Fusion 发送 prompt 时，我们会把它并行分发给一组模型，每个模型都启用 web search 和 web fetch。裁判模型阅读所有面板响应并产出结构化分析：共识点、矛盾点、部分覆盖、独有洞见、盲区。然后由发起调用的模型基于这份分析写出最终答案。

整条流水线在服务端运行，因此调用它和调用单个模型一样简单。

直接用单个模型 slug 调用 Fusion：

```
{
  "model": "openrouter/fusion",
  "messages": [
    { "role": "user", "content": "What are the strongest arguments for and against carbon taxes?" }
  ]
}
```

或自定义面板：

```
{
  "model": "openrouter/fusion",
  "messages": [{ "role": "user", "content": "..." }],
  "plugins": [{
    "id": "fusion",
    "model": "google/gemini-3-flash-preview",
    "analysis_models": [
      "google/gemini-3-flash-preview",
      "moonshotai/kimi-k2.6",
      "deepseek/deepseek-v4-pro"
    ]
  }]
}
```

## 选择 DRACO 来考察推理、tool calling 与简洁度

我们需要一个能分辨「听起来全面」和「确实全面」的基准。标准基准考的是事实记忆或推理谜题，考不出 Fusion 为之而建的能力：研究复杂问题、综合多来源信息、产出全面且有充分引用的分析。

[DRACO](https://arxiv.org/abs/2602.11685)（出自 [Perplexity AI](https://www.perplexity.ai/)）正是为此设计。它包含 100 个深度研究任务，横跨 10 个领域：学术研究、金融、法律、医学、技术、UX 设计、通识、大海捞针式检索、个性化助手和产品对比。

每个任务附带约 39 条加权评分标准的 rubric，分为四类：

- **Factual Accuracy（事实准确性）**（约 20 条）：回答必须答对的可验证论断
- **Breadth & Depth（广度与深度）**（约 9 条）：综合质量、权衡分析、可操作建议
- **Presentation Quality（呈现质量）**（约 6 条）：术语、格式、可读性
- **Citation Quality（引用质量）**（约 5 条）：带有可用出处的原始来源引用

评分标准可以带负权重。命中负权重标准意味着回答中存在错误。例如危险的医疗建议会被重罚。这些负向标准也让「靠啰嗦刷分」变得困难：自信地讲错话的模型会被扣分。

每个回答由裁判模型按标准逐条评分，独立评三次。我们报告的是所有任务的平均归一化分数（0-100）。

DRACO 有作者自己承认的局限：它只评测纯文本、纯英文交互，其静态任务集未必能完全泛化到未来的深度研究应用。绝对分数也依赖裁判模型的选择（论文报告不同裁判之间有 10-25 分的漂移），但系统的相对排名保持稳定。

## 防止模型作弊

当我们给面板模型开放 web search 后，我们发现了一个令人警觉的现象：它们在网上找到了 DRACO 的评分 rubric。虽然这是搜索词恰好命中而非刻意作弊，但确实暴露了真实的污染风险。

我们的解决办法是把结果托管位置排除在 web search 和 web fetch 之外，阻止模型访问与基准 rubric 相关的页面。OpenRouter 的 [server tools](https://openrouter.ai/docs/guides/features/server-tools)通过 Exa 或 Parallel 等第三方 provider 对所有模型通用支持这类排除列表，所以应用它只是一行配置改动，无需逐模型打补丁。本文中的所有结果都是在排除列表就位后产出的。

如果你在跑自己的 eval，同样的机制也可用：在 [tool 定义](https://openrouter.ai/docs/guides/features/server-tools/web-search)中给 web_search 传 `excluded_domains`，或给 web_fetch 传 `blocked_domains`，阻止面板访问特定来源。

## 模型与自己融合也能显著提升

我们把 Opus 4.8 与自己配对组成双模型面板，并由 Opus 4.8 同时担任综合者。结果：65.5%，比 Opus 4.8 单跑（58.8%）高出 6.7 分。这说明 Fusion 提升中相当一部分来自综合步骤本身，而不只是组合了不同架构的模型。同一个 prompt 跑两次会产生不同的推理路径、不同的 tool call、不同的来源选择。这还不足以超越多样化模型组合，但帮助我们理解了综合本身的影响。

## 关于 DRACO 实现方式的说明

我们小心复现了 DRACO 论文描述的方法，唯一区别是使用 Gemini 3.1 Pro Preview 作为裁判，而非论文选择的 Gemini 3 Pro。因此我们的分数与原论文公开结果不可直接比较。

我们希望保留促成作者选择该裁判的高人机对齐特性，同时获得新模型的鉴别力。在 Gemini 3.1 Pro Preview 于基准本身得分偏低后，我们用 Claude Sonnet 4.6 对裁判做了校验，发现它保留了促成作者选其为裁判的品质。我们的目标是展示 Fusion 与单个模型之间的相对差异。

## 6/14 更新：发布后的 FAQ

Fusion 的反响非常棒，谢谢大家！我们正在审阅所有反馈、建议和 bug 报告。多项改进已经上线，接下来几天我们会继续处理。以下是被问最多的几个问题的答案：

### Fusion 是 Fable 的即插即用替代品吗？

不是。基准显示融合多个模型可以在深度研究任务上达到并超过 Fable 水平的表现。我们只测了一类任务（DRACO 深度研究），但这个方法很可能适用于许多我们尚未测试的其他工作流。很想听听你在哪些用例中发现它好用。

DRACO 也不包含长周期任务，而那正是 Fable 的强项。

### 编程场景该怎么用 Fusion？

Fusion 不是编程模型的即插即用替代品。它是给你的编程模型开放一个 [server tool](https://openrouter.ai/docs/guides/features/server-tools/fusion)。基础模型直接处理日常编码，并可以选择在值得花更多时间和金钱换取彻底答案的问题上调用 Fusion（例如架构决策，或最佳实践方案的调研）。何时值得多视角由模型自己判断。

### 基准中的模型能使用哪些工具？

所有模型，无论是 Fusion 面板还是单跑，都拥有相同的三个 server tool：

- `openrouter:web_search`（经 [Exa](https://exa.ai)）
- `openrouter:web_fetch`（经 [Exa](https://exa.ai)）
- `openrouter:bash`

所有配置保持工具集完全一致以确保公平比较。Fusion 面板与单跑的唯一差别在于是否综合了多个模型的输出，而非可用工具不同。

### DeepSeek V4 Pro 的表现令人惊讶，数据准确吗？

DeepSeek 的表现也让我们惊讶。60.3% 的成绩与 Opus 4.8 和 GPT-5.5 相当。

一个假设：如果给 Opus 4.8 更大的 tool-calling 预算，它会得更高。它似乎是更「饿」的模型，时间与工具越多表现越好。相比之下，Fable 更善于审慎使用 tool-call 预算、先长时间思考再行动。基准固定的 tool-call 预算可能压缩了采用不同工具使用策略的模型之间的差距。

### 它慢吗？慢多少？

你发请求的目标模型照常运行，速度与平时相同。只有当模型遇到问题、认为用 Fusion 会有收益时，响应才会变慢。Fusion 一旦被调用，会启动一个多步流程，通常比普通调用长 2-3 倍。期间它把你的 prompt 发给多个模型、等待全部完成、再处理结果产出融合回答。我们这样设计，是为了在常规模型执行速度与「需要时有超越前沿的答案」之间取得平衡。

### 有哪些使用 Fusion 的方式？

Fusion 有四种用法，底层逻辑完全相同：

- **Chatroom。**打开 [openrouter.ai/fusion](https://openrouter.ai/fusion)，选预设或自建面板。无需写代码。
- **Model slug。**向我们的任意推理端点发送 `"model": "openrouter/fusion"`，Fusion plugin 会自动注入一个由前沿模型组成的默认面板。只需替换你的 model 字符串即可使用。[文档](https://openrouter.ai/docs/guides/routing/routers/fusion-router)
- **Server tool。**在 tools 数组里加 `{ "type": "openrouter:fusion" }`。控制力最强：自选执行融合的模型，并可将 Fusion 与其他工具组合。你发请求的模型会自行决定是否调用 Fusion。[文档](https://openrouter.ai/docs/guides/features/server-tools/fusion)
- **Plugin。**照常调用 completions 或 responses，再在请求里加 `"plugins": [{ "id": "fusion", ... }]` 指定你的面板。你指定的模型就是负责综合结果的模型。[文档](https://openrouter.ai/docs/guides/features/plugins/fusion)
