# Jev 与 LLM 裁判对比

Kenny Rogers ·9/21/2026 · 更新于 9/24/2026

多数团队给 agent 输出打分的方式，是把输出交给一个 LLM、让它写一份裁决。这个模式叫 LLM-as-a-judge（LLM 裁判），好用到了成为默认的程度。TypeSafe 的决策模型 Jev 也能给同样的输出打分，但方式不同——而方式不同会改变你拿结果能做什么。本文解释这个区别、展示在我们的测量里它在哪儿起了作用，以及哪种 rubric（评分标准）该用哪种裁判。

本文假设你知道 LLM-as-a-judge 是什么。不知道的话，先读 [LLM 裁判：自动为 AI 智能体的输出打分](https://openrouter.ai/blog/tutorials/llm-as-a-judge-evaluate-ai-agents/)。

## 太长不看

LLM 裁判写一份裁决；Jev 对一个有类型的问题给出概率。当 rubric 是封闭的、证据就在请求里时，Jev 与 LLM 裁判在准确率上打平；Jev 的概率校准更好、价格是五分之一、延迟是十分之一。当 rubric 是开放的、需要通读整篇文章时，LLM 裁判与专家评分贴合得多。

![对比 Jev 和 LLM 裁判的五项测量。与标签一致率 95.5% 对 94.3%。Brier 分数 0.043 对 0.054。延迟中位数 171 ms 对 1,662 ms。每千次裁决成本 $0.021 对 $0.114。摘要一致性上与专家的 Spearman 相关 0.47 对 0.72。每行的条形按该行自身单位缩放。](https://openrouter.ai/blog/images/jev-vs-llm-as-a-judge-tldr.png)

- **用 Jev**：标准封闭且证据在场——答案是否有原文支撑、是否合规、是否匹配参照。需要阈值或路由规则时，或需要快到、便宜到能放进请求路径的裁判时，也用它。
- **用 LLM 裁判**：开放式 rubric、长上下文检查（例如摘要一致性检查），以及需要有人读到"答案为什么不行"的文字解释时。
- **两者都不用**：代码能精确检查的标准。决定既重大又是新情况时，用人。

下文讲这些数字从哪里来、两个裁判为什么表现出这样的行为。

## 两种不同形态的答案

LLM 裁判是生成式模型。你给它一份 rubric 和一个输出，它写文本。要 JSON 它就写 JSON；要 confidence 数字它就写一个数字。裁决的每一部分——包括 confidence——都是模型选择产出的文本。那个数字是被"写"出来的，不是被"测"出来的。

Jev 是决策模型。你不要求它写任何东西。你问它一个固定问题、带一组固定的可能答案，它返回每个答案的概率。问题有三种形态：

| 问题类型 | 你问什么 | Jev 返回什么 | 用来做什么 |
| --- | --- | --- | --- |
| Noul | 一个带 `true`/`false` 标准的是非问题 | `noul`，为真的概率 | 通过/失败闸门：这个答案有支撑吗？这条回复合规吗？ |
| Choice | 从 N 个带标签的选项里选一个 | `choice`、每个选项的 `probabilities`、`confidence` | 成对偏好、类别型 rubric |
| Score | 在你定义的有序刻度上打分 | `score`、每档 `probabilities`、`legend`、`confidence` | Likert 式 rubric：连贯性 1 到 5、严重度低/中/高 |

两种请求长得很像。同一份忠实度 rubric，两种问法：

```
// LLM judge: a prompt, and a verdict parsed out of the text that comes back.
const verdict = await chat.chat.send({
  chatRequest: {
    model: '~openai/gpt-luna-latest',
    temperature: 0,
    responseFormat: { type: 'json_object' },
    messages: [
      { role: 'system', content: `Grade the answer. acceptable = ${RUBRIC_TRUE} unacceptable = ${RUBRIC_FALSE} Reply with JSON: {"acceptable": true|false, "confidence": 0 to 1}` },
      { role: 'user', content: `knowledge: ${knowledge}\n\nquestion: ${question}\n\nanswer: ${answer}` },
    ],
  },
});
// -> {"acceptable": false, "confidence": 1}

// Jev: a typed question over the same state, and a probability back.
const decision = await decisions.alpha.decisions.create({
  decisionsRequest: {
    model: 'typesafe/jev-1.13',
    state: { knowledge, question, answer },
    questions: {
      acceptable: {
        type: 'noul',
        instructions: 'Does answer directly answer question using only facts that knowledge states?',
        criteria: { true: RUBRIC_TRUE, false: RUBRIC_FALSE },
      },
    },
  },
});
// -> answers.acceptable.noul === 0.01
```

LLM 裁判的 `1` 是它写下的数字；Jev 的 `0.01` 是一个关于频率的断言：很多这样的答案里，约 1% 最终应当是可接受的。这个断言可以被检验。它成立，你就能设阈值、把不确定的中间地带路由给人、并推演错误率。不成立，概率就只是装饰。完整的请求与响应形态见 [Decisions API 参考](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-questions-and-answers-request)和 [TypeSafe SDK 指南](https://openrouter.ai/docs/guides/community/typesafe-sdk)。

## 我们怎么比

2026 年 9 月 21 日，我们经 OpenRouter 在两个公开数据集上跑了两个裁判。整轮花了 $0.041。

**忠实度集。**我们从 [HaluEval](https://huggingface.co/datasets/pminervini/HaluEval)（[Li 等，2023](https://arxiv.org/abs/2305.11747)）的 QA 分区取 50 行，每行有一篇短文章、一个问题、一个正确答案和一个编造答案，合计 100 个答案。我们让 Devin——替我们跑这个实验的编码 agent——对照文章逐项复核，丢掉 6 行乱码或含糊的行，把 8 个编造答案因文章支持而改标为可接受。最终 88 项：52 可接受、36 不可接受。这是封闭 rubric：证据就在手上，问题是答案是否守住它。

**摘要集。**我们从 [SummEval](https://huggingface.co/datasets/mteb/summeval)（[Fabbri 等，2021](https://arxiv.org/abs/2007.12626)）取 10 篇新闻文章，每篇有 5 条机器写的摘要。人类专家曾给每条摘要按 1 到 5 打连贯性（读起来顺不顺）和一致性（是否守着文章事实）的分。这是在一个长得多文本上的更难、更开放的 rubric。

**裁判。**Jev 以 `typesafe/jev-1.13` 运行，解析到 `typesafe/jev-1.13-20260917`。LLM 裁判以 `~openai/gpt-luna-latest` 运行，解析到 `openai/gpt-5.6-luna`，配 `temperature: 0` 和 JSON 输出。两个裁判拿到完全相同的 rubric 文本，任何差异都来自模型而不是措辞。

每次判断我们记录裁决、概率、延迟和响应的 `usage.cost`。对 LLM 裁判，我们把"acceptable 加 confidence"换算成可接受概率，让两个裁判落在同一个 0 到 1 的尺度上。

## 一致率打平

88 项忠实度上，Jev 与标签一致 84 项，LLM 裁判 83 项。两者精确率都是 0.98。两个错判里有一项是双方共同的，而那两项其实都是标签错了。当两个裁判在同一项上和你意见相左，检查你的标签。

只看准确率的话，两者没什么可选。但准确率是错的镜片——它只问裁判落在 0.5 的哪边，把 0.51 和 0.99 一视同仁。

## 分歧在校准

看概率是否当真，我们用了两个视角。Brier 分数是裁判给出的概率与真实 0/1 标签间的均方误差——一个 90% 自信地出错的裁判，比 60% 自信地出错的罚得更重。可靠性表把案例按裁判给出的概率分组，报告这些案例实际可接受的比例。

Jev 的 Brier 分数 0.043，LLM 裁判 0.054。可靠性表解释了原因。

```
jev:  bin 0.0-0.2: n=34 mean_p=0.04 observed=0.03
      bin 0.2-0.4: n=1  mean_p=0.34 observed=1.00
      bin 0.4-0.6: n=4  mean_p=0.48 observed=0.50
      bin 0.6-0.8: n=7  mean_p=0.74 observed=1.00
      bin 0.8-1.0: n=42 mean_p=0.93 observed=0.98
llm:  bin 0.0-0.2: n=39 mean_p=0.01 observed=0.10
      bin 0.8-1.0: n=49 mean_p=0.99 observed=0.98
```

Jev 把 4 个案例放在 0.4 到 0.6 之间，对了其中一半——这正是 0.5 该做到的。它打分 0.8 以上的案例实际可接受率 98%。LLM 裁判没有中间地带：88 个案例里它的置信度只出现过六个值（0.82、0.84、0.87、0.98、0.99 和 1），每个案例都落在 0 附近或 1 附近，而落在 0 附近的案例有 10% 其实是可接受的。它对自己的错误和对其他一切同样确信。

实践上，这就是"可以据以路由的裁判"和"只能阅读的裁判"的差别。Jev 的 88 个案例里有 7 个落在 0.3 到 0.7 之间，那些恰恰值得发给人。LLM 裁判一个都没给我们。

## 成本和延迟差 5 倍与 10 倍

Jev 每千次裁决 $0.021，延迟中位数 171 ms。LLM 裁判每千次 $0.114，用时 1,662 ms。对每晚跑 1,000 项的评估，成本差一年约 $34，无所谓。但如果裁判坐在请求路径里、答案不出就不放行响应，延迟差就非常重要——这正是 Jev 能在生产里当闸门、而 LLM 裁判适合当离线评分器的原因。

## 两个裁判都顶住了经典偏见，Jev 略胜

[MT-Bench 论文](https://arxiv.org/abs/2306.05685)发现 LLM 裁判有两个常见偏见：偏好先呈现的答案，偏好两个答案里更长的那个。两种都容易测，我们全测了。

**位置。**我们把同样两个答案给每个裁判看两遍、第二次调换顺序，覆盖全部 36 对"一个可接受、一个不可接受"的答案。对 Jev 这是每个槽位一条 criteria 的 Choice 问题。两个裁判在顺序翻转时都没改选。两者在 72 次排序里都对 70 次、且在两种顺序下错过同一对——指向标签而不是位置。你自己跑这个测试时，请挑你最难的配对（两个答案质量接近的）跑，位置偏见就在那里显形。另外 Choice 的 criteria 只在"一个可接受另一个不可接受"时成立；若两个都可能可接受，请把每条 criteria 写成比较（更具体、支撑更强、更贴题）而不是标签，否则 Jev 没有能匹配上的选项。

**冗长度。**我们拿每个不可接受答案，用其原文里的两句真话把它加长。加长后的答案仍然是错的，但平均长度从 69 字符涨到 376。我们只保留加长后仍然错误的配对——有少数情况抄进去的句子碰巧包含正确答案，加长版反而可接受了。

| 裁判 | 未加长的错误答案被接受 | 加长的错误答案被接受 | 翻转 |
| --- | --- | --- | --- |
| Jev Noul | 36 里 1 | 36 里 2 | 1（概率 0.48 到 0.57） |
| LLM 裁判 | 36 里 1 | 36 里 4 | 3 |

加长让 Jev 挪了挪：它对错误答案的平均可接受概率从 0.08 升到 0.12，唯一越过 0.5 的那个案例本来就坐在 0.48。LLM 裁判翻转了三个案例，每个都从"自信拒绝"变成"自信接受"。模式和校准表里一致：Jev 不确定时会说出来；LLM 裁判错的时候，错得很有信心。

## LLM 裁判赢在哪里

裁判需要通读整篇文章时，局面就变了。50 条 SummEval 摘要上，Jev 每个标准一个问题——五种档位写成 criteria 的 Score 问题；LLM 裁判拿到同样的五档描述、返回 1 到 5 的整数。我们用 Spearman 相关对照专家平均（1.0 代表排序完全一致）。

| 标准 | Jev Score 对专家的 Spearman | LLM 裁判对专家的 Spearman |
| --- | --- | --- |
| 连贯性 | 0.42 | 0.44 |
| 一致性 | 0.47 | 0.72 |

连贯性打平。一致性——抓幻觉时你在乎的那个标准——是 LLM 裁判的明显胜利。我们的猜测是：检查一致性意味着逐条主张走查摘要、找出文章在哪里支撑每一条。这对生成式模型是天然的按步进行的过程，而 Jev 必须在一次通过约 1,000 token 的 state 中完成它。

Jev 在这里并非没用。两个裁判都抓住了专家一致性评分低于 4 的全部 3 条摘要、其余 47 条零误报，Jev 仍能当粗粒度的通过/失败闸门。但要一个跟得上专家判断的排序，LLM 裁判是更好的信号。Jev 每千条摘要 $0.043、168 ms；LLM 裁判 $0.261、2,902 ms——这份信号你大约要多付 6 倍。Jev 这里的花费是忠实度场景的两倍，因为每个请求携带约两倍的输入 token：整篇文章加两个 Score 问题，而不是一个短文章加一个 Noul。

还有两种生成式裁判才是对的工具的情形，我们没有基准测试，因为没有可对照的答案。

- **开放式 rubric。**问题是"这是个好答案吗"又没有写下来的标准时，你需要生成式裁判。Jev 需要把标准写清楚——你写不出来，就没法问 Jev。
- **需要成文的解释。**审核人需要知道答案为什么失败时，LLM 裁判的推理过程就是产品。Jev 只告诉你它多有把握，别的没有。

## 哪种 rubric 用哪种裁判

LLM 裁判有三个替代项：代码里的确定性检查、一个 Jev 问题，或一个人。请按标准逐个选，不要按项目整体选。

| 如果标准是…… | 用什么 | 因为 |
| --- | --- | --- |
| 代码能检查的（schema、算术、禁用字符串） | 确定性检查 | 精确、免费、没有偏见要测 |
| 封闭、证据在场、需要概率或阈值的（有原文支撑、合规、匹配参照） | Jev Noul 或 Choice | 校准的概率、约 170 ms、每千次约 $0.02 |
| 档位可描述的有序刻度（严重度、1 到 5 的语气） | Jev Score | 每档分布加 confidence，同样成本画像 |
| 开放，或需要对长上下文推理（摘要一致性、计划质量） | LLM 裁判 | 我们测试中一致性上对专家相关 0.72 对 0.47 |
| 需要一段给人读的文字解释 | LLM 裁判 | Jev 只返回概率，不返回解释 |
| 后果重大又是新情况 | 人 | 两个裁判都不能替代人 |

[Jev verified cascade cookbook](https://openrouter.ai/docs/cookbook/evaluate-and-optimize/jev-verified-cascade) 展示了中间几行在生产中的用法：便宜模型起草答案，一个 Jev 问题验证它，落在不确定带间的升级上去。[用 Jev 为工具调用把关 cookbook](https://openrouter.ai/docs/cookbook/building-agents/gate-tool-calls-with-jev) 把同一思想用在 agent 的工具调用上。

## 定你自己的阈值

我们的数字展示的是取舍的形状。要定生产阈值，你需要在自己的数据上做同样的测量。

- 标注 50 到 100 个能代表你生产内容的条目，并写下"什么算可接受"的定义。
- 每条都发给两个裁判，记录概率、延迟和 `usage.cost`。
- 构建可靠性表，忽略准确率那一行。把接受阈值选为你愿意签字背书的最低概率段，把接受与拒绝阈值之间的全部发给人或 LLM 裁判。
- rubric 或模型版本变化时重跑这张表。每个 Decisions 响应的 `model` 字段告诉你是哪个版本作答。

[Jev 模型页面](https://openrouter.ai/typesafe/jev-1.13)有当前定价和限制；[TypeSafe SDK 指南](https://openrouter.ai/docs/guides/community/typesafe-sdk)有完整的 Decisions API 形态；[LLM 裁判一文](https://openrouter.ai/blog/tutorials/llm-as-a-judge-evaluate-ai-agents/)讲 rubric 一开始怎么写。

Jev 对你还陌生的话，[什么是 Jev？](https://openrouter.ai/blog/insights/what-is-jev/)解释模型和三种问题类型；[Jev vs LLM](https://openrouter.ai/blog/tutorials/jev-vs-llm-when-to-use-each/) 覆盖"决策模型何时替代生成调用"这个更大的问题。想要不同任务上的第二个准确率测量，[Jev 的分类精度能赶上前沿模型吗？](https://openrouter.ai/blog/insights/jev-vs-claude-opus-5-classification/) 在 Banking77 上把 Jev 和 Claude Opus 5 对跑。[Jev 文档中心](https://openrouter.ai/docs/guides/community/jev)收录 OpenRouter 上全部 Jev 指南和 cookbook。

## 常见问题

### Jev 是一个校准过的裁判模型吗？

Jev 每次判断都带一个概率，在我们 88 项忠实度集上这些概率是准的：Brier 分数 0.043，Jev 给出 0.8 以上概率时答案实际可接受率 98%。校准取决于你测的具体任务，选阈值之前先在自己的标签上测。

### LLM-as-a-judge 有什么替代方案？

代码能定答案时用确定性检查。任何后果重大或新出的情况，引入人。有概率有好处的封闭 rubric 场景，用 Jev 这样的决策模型。多数生产流水线是三者的混合。开放式 rubric 和需要成文解释的场景，留着生成式裁判。

### 什么时候仍然该用 LLM 当裁判而不是 Jev？

rubric 开放、标准写不下来时；分数需要一段文字解释时；判断必须在长文本上逐步进行时。SummEval 摘要的事实一致性上，LLM 裁判对专家的相关是 0.72，Jev 是 0.47。

### 我怎么为自己的评估校准 Jev？

标注 50 到 100 条，每条通过 Decisions API 作为 Noul 或 Score 问题发给 Jev，记录概率、延迟和 usage.cost。计算与你标签的一致率和 Brier 分数，按概率分组建可靠性表，再从表上选阈值。
