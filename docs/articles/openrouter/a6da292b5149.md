# Guardrails 把 organization 级上限与 workspace 默认设置分开

Sasha Blumenfeld ·2026 年 10 月 30 日

![Guardrails 将 organization 级上限与 workspace 默认设置分离开来](https://openrouter.ai/blog/images/guardrail-policies.png)

一年前，OpenRouter 上的大多数公司只在几个团队里使用 AI。如今它已经渗透到各个部门。在 10 人及以上的团队里使用 OpenRouter 的人增长了 70 倍，而随着越来越多的工作转向 agent，平均每个 organization 运行的活跃 API key 也变成了原来的三倍。

管理这一切的 admins 反复提出同一个诉求：为整个 organization 定一套规则，同时又能给需要更多额度的人留出破例的空间。

我们重构了 Guardrails 的配置方式，如今 admins 可以设定 organization 级别的整体限制，在这些限制内给不同的人分配不同的预算和模型访问权限，并且能够单独修改每一条策略。

要开始使用，打开你 workspace 的 [Guardrails 页面](https://openrouter.ai/workspaces) 来设置策略，或者阅读 [Guardrail Policies 文档](https://openrouter.ai/docs/guides/features/guardrails/policies)。

## 我们为什么改 Guardrails

Guardrails 的第一版，是为那种早期的形态打造的：几个团队，寥寥几个 API key。而今天我们看到的是成百上千的员工通过 SSO 登录，每一台工程师的笔记本上都跑着 coding agent，还有平台团队要为这一切的成本负责。

![选择一种 guardrail 类型：Budget、Model & provider access 或 Content moderation。](https://openrouter.ai/blog/images/guardrail-policies-approval-workflow.png)

这一变化体现在客户向我们提出的诉求上：

- **按人设预算，并可破例。** 团队想要一个对所有人都适用的默认月度或周度预算，再给需要的人单独设一个更高的。如果每一档预算都要对应一条 guardrail，那有一家客户眼看就要为它大约 1,200 名员工逐一创建单独的 guardrail。
- **默认从严起步。** 客户希望新成员一开始就用最保守的设置，之后再随时间逐步获得更多权限。旧的模式恰恰相反：workspace 默认值是任何人能拿到的上限，其余每一条 guardrail 都只能在这个基础上进一步收紧。
- **一条规则覆盖多个 workspace。** 拥有多个业务单元的公司，想把 ZDR、provider 和 region 规则只设一次，而不是把同一条 guardrail 复制到每一个 workspace 里。
- **有一套处理申请的办法。** admins 不断被请求为某个项目提高预算或放开某个新模型的访问权限，他们希望批准这种请求是一次快速的改动，而不必推倒重建。

如今一些客户已经在 Guardrails 之上搭建了自己的内部工作流。一名员工为某个项目申请更高的预算或某个特定模型的访问权限，说明理由，然后由一名 admin 批准。有了分开的策略类型、以及由 organization 设定的上限，批准这样一个请求就是一处改动：他们只需要给这个人指派一条不同的预算或模型访问策略，系统就会自动把它保持在 organization 的上限之内。

## organization 上限与 workspace 默认值分离

Organization admins 现在可以为整个 workspace 设定上限，比如预算上限、Zero Data Retention 要求，或者哪些 models 和 providers 可以使用。这些上限适用于该 workspace 里的每一位成员和每一个 API key，包括那些拥有自己预算或模型策略的人。

在这些上限之内，由 workspace admins 来设定默认值。新成员一加入就能拿到一个默认的预算和模型列表，而 admin 可以给特定的人更高的预算或更多模型的访问权限。这一切都不能越过 organization 的上限。

![配置一条预算 guardrail：每月 $2,000 的额度上限，并把 BYOK 的支出也算在内。](https://openrouter.ai/blog/images/guardrail-policies-limits-defaults.png)

落到实践中，情况是这样的：一名 organization admin 把 Engineering workspace 限制为每人每月 $2,000、只允许 ZDR 的 providers，并且不开放某个高成本模型的访问。workspace admin 把新成员的默认值设为每月 $200，配以团队的标准模型。一名新加入的工程师会自动拿到 $200 这个默认值。而一位牵头做 agent 项目的资深工程师，可以拿到每月 $1,500 并使用更多模型。这个 workspace 里没有任何人能超过每月 $2,000，也不能使用非 ZDR 的 provider。

## Budget、模型访问与内容审核是分开的策略

一条 guardrail 过去会把预算、模型与 provider 访问、内容审核捆绑进一个具名对象。现在它们被拆成了三种独立的策略类型：

- **Budget**：设定一个以美元计的支出上限，按日、周或月重置。
- **Model and provider access**：管控哪些 models 和 providers 可以使用，以及 ZDR 与 data regions。
- **Content moderation**：涵盖 prompt injection 防护、敏感信息检测，以及自定义内容过滤器。

我们之所以把它们拆开，是因为它们并不会一起变动。一个人的预算可能每来一个新项目就变一次，而团队的模型列表和审核规则几个月都可以保持不变。

现在团队共享一条模型访问策略和一条内容审核策略，你可以只改某个人的预算，而不必动其他任何东西。

## 向后兼容

要保留你现有的配置，不需要改动任何东西。已有的 guardrails 会保留各自的 ID、继续执行同样的规则，guardrails API 和 Terraform 资源也和以前一样工作。每条 guardrail 现在还会分别显示为独立的预算、模型访问和内容审核策略，因此你可以在准备好了的时候，按 workspace 一个一个地迁移过来。

如果你通过 API 或 Terraform 来管理 guardrails，请先阅读 [Migrating to Guardrail Policies](https://openrouter.ai/docs/guides/features/guardrails/policies-migration)，因为在 dashboard 里所做的改动不会同步回你的配置。

## 开始使用

想试一试，就打开你所管理的任意一个 workspace 里的 Guardrails 页面。你已有的 guardrails 会以独立策略的形式已经在那里了。一个好的第一步是：只提高某个人的预算，而不改动其他任何东西。Organization admins 可以通过 Workspace-wide guardrails 来设定整个 organization 范围内的上限。完整配置请见 [Guardrail Policies 文档](https://openrouter.ai/docs/guides/features/guardrails/policies)。

## 常见问题

### 什么是 OpenRouter Guardrails？

Guardrails 让 organizations 能够管控其成员和 API key 的支出、模型与 provider 访问，以及内容审核。

### 我能给不同的人设不同的 AI 预算吗？

可以。给某个成员或某个 API key 指派一条预算策略。它按日、周或月重置，并且不能超过你的 organization admin 设定的上限。

### 预算是在整个 workspace 里共享的吗？

不是。每条预算是按成员或按 API key 各自生效的，而不是一个共享池。每月 $100 的上限，意思是每个人最多可以花到 $100。

### 我已有的 guardrails 会怎样？

它们会继续执行同样的规则，并保留各自的 ID。每一条现在还会以最多三条独立策略的形式呈现。

### 我需要迁移到新的 API 吗？

不需要。已有的 guardrails API 和 Terraform 资源会继续工作。新的策略端点与它们并存，位于 `/api/v1/guardrails/policies` 之下。

### 谁可以管理 guardrail 策略？

Organization admins 可以管理每一条策略，包括整个 organization 范围内的上限。Workspace admins 管理所在 workspace 里的策略。
