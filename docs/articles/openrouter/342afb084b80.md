# Agent 框架对比：Tool-Calling Schema 的处理

你构建了一个 tool calling 正常工作的 agent，然后换掉背后的模型，tool call 开始失败。你的 tool 定义没变，变的是模型期望的请求和响应格式——因为每个 provider 对 tool 定义、tool call 响应、参数编码和 tool 结果都用自己的结构。如果你的技术栈里没有任何东西在这些结构之间做翻译，换模型就意味着新的解析代码和新的失败模式。

本文对比六个 agent 框架如何定义 tool schema、如何跨 provider 翻译它们，以及每种情况下翻译发生在哪一层。然后展示我们如何在 API 层归一化 tool calling，让你的应用收发的结构对 OpenRouter 上每个支持 tool 的模型都保持一致。

## Tl;dr

- OpenAI、Anthropic 和 Google 各自用不同的线上格式（wire format）定义 tools 并返回 tool call。为一家写的 tool 定义拿到另一家不能直接用。
- LangChain 和 LangGraph 为每个 provider 各做一份 tool 定义翻译。CrewAI 把翻译委托给它路由到的 client。OpenAI Agents SDK、Claude Agent SDK 和 Google ADK 围绕单一 provider 的格式构建。Microsoft Agent Framework 委托给所配置的 model connector。
- OpenRouter 接受 OpenAI 风格的 `tools` 数组，并为每个支持 tool calling 的模型返回标准 `tool_calls` 响应，因此换模型只是改 model 字符串。
- 对包含 tools 的请求，Auto Exacto 默认基于吞吐、tool-calling 成功率和基准数据重排 provider，其背后的 Tool Call Error Rate 指标在每个模型的 Performance 标签页可见。

## 为什么各 provider 的 tool-calling schema 不同

各家对「什么是 tool」是有共识的。tool 有名字、有描述、有一个声明其参数的 schema。模型读这三样东西，决定是否调用 tool，并生成参数。

共识到此为止。每家把这些内容包进自己的请求和响应格式，而这些格式互不兼容。

在 [OpenAI 的 Chat Completions API](https://platform.openai.com/docs/guides/function-calling) 中，你传入一个 `tools` 数组，每条带 `type: "function"` 和一个 `function` 对象，内含名称、描述和 JSON Schema `parameters`。当模型想用 tool 时，assistant 消息携带一个 `tool_calls` 数组，每次调用的 `arguments` 字段是 JSON 编码的字符串。

```
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "Get the current weather for a city",
        "parameters": {
          "type": "object",
          "properties": { "city": { "type": "string" } },
          "required": ["city"]
        }
      }
    }
  ]
}
```

[Anthropic 的 Messages API](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) 使用更扁平的定义，schema 放在 `input_schema` 下。模型的请求以 assistant 消息内的 `tool_use` content block 返回，参数已解析进 `input` 对象，回合以 `stop_reason: "tool_use"` 结束。

```
{
  "tools": [
    {
      "name": "get_weather",
      "description": "Get the current weather for a city",
      "input_schema": {
        "type": "object",
        "properties": { "city": { "type": "string" } },
        "required": ["city"]
      }
    }
  ]
}
```

[Google 的 Gemini API](https://ai.google.dev/gemini-api/docs/function-calling) 把 tool 定义嵌套在 `generateContent` 请求的 `function_declarations` 数组里，模型的请求作为响应内容中的 `functionCall` part 返回，而不是独立的顶层字段。Google 较新的 Interactions API 又接受另一种 tool 条目结构，`type: "function"` 位于每个 tool 的顶层。

```
{
  "tools": [
    {
      "function_declarations": [
        {
          "name": "get_weather",
          "description": "Get the current weather for a city",
          "parameters": {
            "type": "object",
            "properties": { "city": { "type": "string" } },
            "required": ["city"]
          }
        }
      ]
    }
  ]
}
```

就一个 tool，三种请求结构、三种响应结构。开源模型再加一种情况：没有专门训练过输出 tool-calling 格式的模型，只能以文本形式产出 tool call。对这类模型的任何 tool-calling 支持，都取决于服务层把 tool 定义放进 prompt、再把模型输出解析回调用。这种解析不属于任何 provider 的线上格式，失败方式也与原生格式不同。

你的应用只定义一个 tool，但它必须产出的确切请求结构取决于请求背后的模型。要么你的技术栈里有东西把这唯一定义改写成各模型的正确格式，要么你自己写并维护这层翻译。

## Schema 翻译可以存在于哪里

翻译可以运行在三个地方。

- **在你的应用里。**你自己编写各 provider 的请求/响应映射，并随 provider 变化持续维护。
- **在框架里。**agent 框架或其委托的 provider client 接一份 tool 定义，产出各 provider 的格式。
- **在 API 层。**位于所有模型前面的网关接受一种格式，在去往各 provider 的路上翻译。我们的 [tool calling](https://openrouter.ai/docs/guides/features/tool-calling)和[结构化输出](https://openrouter.ai/docs/guides/features/structured-outputs)文档完整展示了归一化后的结构。

下面这些框架的差别主要在于承担了第二种方案的多少，以及把哪家 provider 当作原生格式。

## 各框架如何处理 tool schema

这里每个框架都支持 tool calling。不同的是翻译住在哪一层、框架自己掌握多少。

### LangChain 与 LangGraph

你用 `@tool` 装饰器把一个 Python 函数加类型注解定义为 tool，类型注解就是 tool 的输入 schema。用 `bind_tools()` 把 tools 挂到模型上，`create_agent` 运行 tool-calling 循环。LangChain 的 [chat model 集成](https://docs.langchain.com/oss/python/langchain/models)把定义翻译成各 provider 的格式，因此同一份 agent 代码可以通过 `init_chat_model` 跑在 OpenAI、Anthropic 和 Google 模型上。

这层抽象把线上格式差异从你的代码里藏了起来。任何一次翻译的质量取决于具体 provider 集成，所以要针对你计划上线的确切模型做测试。LangChain 还在 `langchain-openrouter` 包中提供了 [OpenRouter chat model 集成](https://docs.langchain.com/oss/python/integrations/chat/openrouter)，你可以通过 `init_chat_model` 选择任何 OpenRouter 模型，把各 provider 的翻译交给我们的 API。

关于 MCP，LangChain 提供了文档化的 [`MCPAdapter`](https://docs.langchain.com/oss/python/langchain/mcp)，基于 FastMCP 构建，可发现 server 的 tools 并适配为 LangChain tools。`langchain.mcp` 命名空间要求 `langchain[mcp]>=1.4.0`，且文档标注为 beta。

### CrewAI

CrewAI 围绕角色和任务组织。你把 tools 分配给 agent，由 crew 协调工作。CrewAI 自己不实现 provider 专属的 tool 格式化。

CrewAI 的 [LLM 文档](https://docs.crewai.com/en/concepts/llms)描述了对 OpenAI、Anthropic、Google Gemini API、Azure、AWS Bedrock 和 Snowflake Cortex 的原生 SDK 集成，通过你配置的 `provider/model-id` 字符串选择。其余所有 provider 走 LiteLLM。无论哪种情况，schema 处理都属于 CrewAI 路由到的那个 client，而非 CrewAI 本身。

关于 MCP，`crewai-tools` 包提供 [`MCPServerAdapter`](https://docs.crewai.com/en/mcp/overview) 以及 stdio、SSE 和 streamable HTTP server 的传输类。

### OpenAI Agents SDK

[OpenAI Agents SDK](https://openai.github.io/openai-agents-python/) 围绕 OpenAI 的 tool 格式构建。你用 `@function_tool` 装饰器定义函数 tool，SDK 根据函数签名和 docstring 生成参数的 JSON Schema。它在 OpenAI 模型上提供最完整的支持，包括在 OpenAI 侧运行的 hosted tools。

但它不限于 OpenAI。SDK 的 [model 文档](https://openai.github.io/openai-agents-python/models/)描述了通向其方 provider 的三条内置路径：`set_default_openai_client` 通过设置 `base_url` 和 `api_key` 让 SDK 指向 OpenAI 兼容端点；`ModelProvider` 为单次运行应用自定义 provider；`Agent.model` 为单个 agent 设置模型。Any-LLM 和 LiteLLM 被文档标注为尽力而为、beta 的第三方适配器，用于内置路径覆盖不到的情况。当你经由 Chat Completions 而非 Responses API 路由时，SDK 会丢弃 Responses 专属字段，且文档警告某些 provider 不支持 JSON Schema 结构化输出。越远离 OpenAI 的模型，你越依赖兼容层而非第一方支持。

MCP 支持是[内置的](https://openai.github.io/openai-agents-python/mcp/)，覆盖经 OpenAI Responses API 的 hosted MCP server tools，以及通过 stdio 和 HTTP 传输直连 MCP server。

### Claude Agent SDK

[Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 是 Claude Code 背后的 agent 运行框架，打包为 Python 和 TypeScript 库。与 Anthropic Messages API 不同，它替你运行 tool 执行循环，内置工具、上下文管理、权限、hooks 和 subagents。你用 Python 的 `@tool` 装饰器或 TypeScript 的 `tool()` 定义自定义 tool，用 `create_sdk_mcp_server` 把它们包进进程内 MCP server，再把该 server 传给 query。

它面向 Claude 模型，因此 tool call 直接使用 Anthropic 原生 `tool_use` 格式。不存在跨 provider 翻译层。把它指向非 Anthropic 模型并非其设计用途。

### Microsoft Agent Framework

微软将 [Agent Framework](https://learn.microsoft.com/en-us/agent-framework/overview/agent-framework-overview) 定位为 AutoGen 和 Semantic Kernel 的直接继任者，融合 AutoGen 的 agent 抽象与 Semantic Kernel 的企业特性，并加入显式工作流。其概述列出的受支持模型 provider 包括 Microsoft Foundry、Anthropic、Azure OpenAI、OpenAI 和 Ollama，tool call 与 MCP server 通过 agent 抽象处理。

Tool 以类型化函数挂到 agent 上，框架将其转为带 JSON Schema 的 function tool。Tool-calling 翻译属于你配置的 model connector，换 provider 就等于换 schema 处理方式。微软发布了[从 AutoGen 迁移的指南](https://learn.microsoft.com/en-us/agent-framework/migration-guide/from-autogen/)供迁移团队参考。

### Google ADK

Google 的 [Agent Development Kit](https://google.github.io/adk-docs/agents/models/) 为 Gemini 及其原生 `function_declarations` 格式构建。当你把 Python 函数传入 agent 的 tool 列表，ADK 将其包装为 `FunctionTool`，并根据函数签名和 docstring 生成 schema。

对 Gemini 之外的模型，ADK 文档提供了 connector 页面，包括 [LiteLLM connector](https://google.github.io/adk-docs/agents/models/litellm/)。走这条路径时，对 Claude 或 GPT 模型的调用经由 LiteLLM 的翻译，而非 ADK 原生机制，这些模型上的 schema 行为归于那个集成。请针对你计划使用的确切模型做测试。

关于 MCP，ADK 提供 [`McpToolset`](https://google.github.io/adk-docs/tools-custom/mcp-tools/)，连接 MCP server 并把其 tools 暴露给 agent。

## 框架对比

选择框架前，先按 [tool-calling 支持过滤我们的模型目录](https://openrouter.ai/models?supported_parameters=tools)。框架列出了某 provider 适配器，与模型原生支持 tool calling，是两回事，它们之间的差距正是意外的来源。

| 框架 | 如何定义 tool | 谁负责跨 provider 翻译 schema | MCP 支持 |
| --- | --- | --- | --- |
| LangChain 与 LangGraph | 带类型注解的 Python 函数加 `@tool` 装饰器 | LangChain 的各 provider chat model 集成 | `langchain.mcp` 命名空间中的 `MCPAdapter`，文档标注 beta |
| CrewAI | 按角色分配给 agent 的 tool | 被路由的 client：原生 provider SDK 或 LiteLLM | `crewai-tools` 中的 `MCPServerAdapter` |
| OpenAI Agents SDK | `@function_tool`，自动生成 JSON Schema | 无第一方翻译。其他 provider 经 OpenAI 兼容端点或 beta 的 Any-LLM、LiteLLM 适配器 | 内置，hosted 与直连 MCP server |
| Claude Agent SDK | 进程内 MCP server 中的 `@tool` | 无。设计上单一 provider | 内置，MCP client 配合进程内 server |
| Microsoft Agent Framework | 类型化函数转为 function tool | 所配置的 model connector | 内置，MCP server 经 agent 抽象 |
| Google ADK | Python 函数包装为 `FunctionTool` | 无原生跨 provider 路径。非 Gemini 模型经 LiteLLM 等 connector | `McpToolset` |

把这张表当作起点，投入使用前请核对最新文档。这些框架发布频繁，tool-calling 行为正是会变的部分之一。

## 换模型时会坏什么

失败有几种形态，上面没有任何框架能消除它们。

一家 provider 接受的 schema 会被更严格的那家拒绝。深层嵌套的参数对象、不常见的类型、或一家忽略而另一家强制的约束，都足以在新模型上产生请求错误。

没有原生 tool calling 的模型会把调用作为纯文本返回。流水线里没有东西认出它是 `tool_call`，于是没有错误可捕获，只有一个不是你循环所预期的响应。除非框架或你自己的代码加了文本解析兜底，agent 只会停止推进而不是抛错。

修复行为各不相同。有些代码路径在调用畸形返回时抛出可捕获的错误。另一些把检测和恢复留给你。如果你的 agent 循环假设一种行为而框架提供另一种，换模型可能让错误无声无息。

更微妙的一种不需要跨模型家族换模型。同一模型由两家不同 provider 服务，返回有效 tool call 的比率可能不同。自 2025 年 8 月起我们对 OpenRouter 上每一次 tool call 响应评分，并在 [Auto Exacto 公告](https://openrouter.ai/blog/announcements/auto-exacto/)中报告：在我们将 tool-calling 流量从弱势端点迁走后，受影响 provider 上 GLM-5 和 GLM-4.7 的 tool call 错误率从约 8% 降到接近 1%。

我们把每次失败的 tool call 归为三类，同样这三项检查也适用于你自己的日志。`InvalidJson` 指参数无法解析为 JSON。`UnknownName` 指调用的函数名不在请求的 tool 列表里。`SchemaMismatch` 指参数无法通过 tool 的参数 schema 校验。关于循环机制，包括重试、停止条件、逐轮控制，见我们构建 [tool-calling agent 循环](https://openrouter.ai/blog/tutorials/build-tool-calling-agent-loop/)的指南。

## 在 API 层归一化 tool calling

翻译所在的第三个地方是 API 层，位于框架之下。我们一次性在所有模型前面归一化 tool calling，让它之上的一切都看不到 provider 差异。

你发送带 `tools` 数组的 OpenAI 风格请求。我们把它转换为目标 provider 的格式、运行，并返回标准 `tool_calls` 响应。对每个支持 tool calling 的模型，你收发的结构都相同，换模型只是改 model 字符串。

下面的例子用 OpenAI 格式定义 tool 一次，无论请求由哪个模型执行，都从 `message.tool_calls` 读取结果。

```
import json
import os

from openai import OpenAI

client = OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key=os.environ["OPENROUTER_API_KEY"],
)


def get_weather(city: str) -> dict:
    return {"city": city, "forecast": "sunny", "temperature_c": 24}


tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Get the current weather for a city",
        "parameters": {
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"],
        },
    },
}]

messages = [{"role": "user", "content": "What's the weather in Lisbon?"}]

# Change this string to anthropic/claude-sonnet-4.6 or google/gemini-3.5-flash
# and nothing else in this file changes.
response = client.chat.completions.create(
    model="openai/gpt-5.5",
    messages=messages,
    tools=tools,
)

choice = response.choices[0]
messages.append(choice.message)

# The same tool_calls shape comes back from every tool-capable model.
for call in choice.message.tool_calls or []:
    args = json.loads(call.function.arguments)  # arguments is a JSON string
    result = get_weather(**args)
    messages.append({
        "role": "tool",
        "tool_call_id": call.id,
        "content": json.dumps(result),
    })
```

有两样东西跨所有模型保持不变。Tool 定义和你要解析的响应是同一份。`tool_calls` 永远是数组，且每个 `arguments` 值都是 JSON 字符串，所以遍历数组逐条解析，而不是假设只有一次调用。

这不是 agent 框架的替代品。你仍需要某个东西来运行循环、维护状态、决定何时停止。它移除的是你应用里各模型专属的 tool-calling 适配代码。schema 翻译从你维护的层挪到了你调用的层。

## Tool-calling 请求的 provider 路由

归一化格式只是可靠性问题的一半。另一半是哪个 provider 来跑调用。因为我们为每次 tool call 响应评分，我们可以把 tool-calling 请求路由向那些返回有效 tool call 比率最高的端点。

[Auto Exacto](https://openrouter.ai/docs/guides/routing/auto-exacto) 默认运行在所有包含 tools 的请求上，无需配置。它用三类信号重排你所选模型的可用 provider：吞吐是每个端点的实时每秒 token 测量；tool-calling 成功率源自 Tool Call Error Rate 指标；基准数据来自我们自建的基准设施，按周期对已注册的 provider 端点跑 GPQA Diamond 和 Tau2-Bench Airline。

Tool Call Error Rate 指标位于每个模型页面的 Performance 标签。对每个包含 tools 的请求，我们检查模型返回的每一次 tool call，用 JSON Schema Draft 7 将其 `arguments` 与你提供的 `tools[].function.parameters` schema 做校验。`parameters` schema 缺失或编译失败的 tool 计为有效，因此当调用方 schema 本身畸形时该指标保持保守。该指标按请求聚合而非按 tool call，所以一次请求里的多次坏调用只计一次。

Auto Exacto 可能与保持 prompt 缓存温暖的粘性 provider 路由冲突，因为它可能在会话中途把请求移到不同端点。如果你的 agent 循环更在意缓存命中率而非 provider 重排，文档说明了如何用 `provider` 对象里的 `sort: "price"` 或 `:floor` 模型 variant 禁用 Auto Exacto。

在依赖任一机制之前要做两项检查。tool calling 并非通用，请通过上面的目录过滤或模型页面确认你路由到的每个模型支持它。如果你在同一 agent 上跑多个模型比较质量，请同时比较成本。各模型当前费率见[定价页](https://openrouter.ai/pricing)。

## 结论

Tool calling 不是一种格式。有些框架是翻译者，有些原生属于单一 provider，还有些把问题委托给底层的 connector 或 client。如果你需要某家 provider 的最深支持，OpenAI Agents SDK 或 Claude Agent SDK 这类原生 SDK 最合适。如果你需要在 provider 之间移动，LangChain 和 LangGraph 在框架层承担最多翻译，或者你可以在 API 层归一化 tool calling，把翻译移出框架。在动手构建之前先决定 schema 翻译住在哪一层，换模型就能一直保持一行改动。

## 常见问题

### 主流 agent 框架处理 tool-calling schema 有何不同？

不同在 schema 翻译运行的位置。LangChain 和 LangGraph 通过各 provider 的 chat model 集成，把一份 tool 定义翻译成各 provider 格式。CrewAI 委托给它路由到的 provider SDK 或 LiteLLM client。OpenAI Agents SDK、Claude Agent SDK 和 Google ADK 各围绕单一 provider 格式构建，通过兼容端点、适配器或 connector 触达其他 provider。Microsoft Agent Framework 把翻译交给所配置的 model connector。在 API 层归一化 tool calling 则把翻译移到它们全部之下。

### tool calling 该选哪个 agent SDK？

按你需要的模型集合选 SDK。若计划留在某 provider 的模型上，OpenAI Agents SDK 或 Claude Agent SDK 这类 provider 原生 SDK 最合适。跨 provider 移动时 LangChain 和 LangGraph 承担最多翻译。CrewAI 把翻译委托给路由到的 client。经由 OpenRouter 路由可让 tool 定义和响应结构跨模型保持一致，SDK 选择从此不再限制模型选择。

### 哪些 agent SDK 支持 MCP？

OpenAI Agents SDK、Claude Agent SDK、Microsoft Agent Framework、Google ADK、LangChain 和 CrewAI 都文档化了将 Model Context Protocol server 作为 tool 来源的支持。集成深度不一，LangChain 当前 MCP 命名空间标注为 beta。MCP 标准化了 tools 如何被发现和描述，但没有标准化模型的 tool-calling 线上格式——那是本文讨论的另一个问题。

### 如何让长 tool-calling 循环跨模型正常工作？

调用模型、检查 finish reason、执行每个请求的 tool、按 tool call ID 追加结果，重复直到模型不再请求 tool 或你到达步数上限。执行前校验 tool 参数，因为模型可能返回不符合你 schema 的参数。归一化 tool-calling 格式让循环没有各模型分支，并路由向 tool call 错误率低的 provider。
