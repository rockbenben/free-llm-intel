# 实时 Web 搜索基准：为你的 Agent 选对引擎、深度与模型

Ayush Patel · 2026-08-12

对大多数 LLM 请求而言，web 搜索已经是标配——用来克服知识截止日期。实验室和搜索提供商进化很快，让搜索更有效也更经济，但也把一堆棘手的选择留给了我们：是用某些实验室内置的原生搜索，还是接入 Exa、Parallel、Perplexity 这类第三方引擎？搜一次够不够？如果不够，该让 agent 持续搜索多久？更多的搜索轮次换来的质量值不值？

我们构建了实时排行榜（live leaderboard），帮助你用数据决定最佳搜索配置。数据见[我们的新 Benchmarks 页面](https://openrouter.ai/benchmarks)。

## 我们对所有组合做基准，找出强弱项

配置一次搜索请求，你有四个决策点：

- **模型。** 负责写出生成后提交给搜索引擎的确切查询，并处理返回的结果。
- **引擎。** 你可以选择特定引擎，也可以依赖某些实验室提供的捆绑引擎。在 OpenRouter 上，我们提供 Exa、Parallel 和 Perplexity，以及 OpenAI、Anthropic、Google 等实验室的原生引擎。
- **搜索方式。** 可以在调用模型之前先执行搜索、把结果作为上下文传入；也可以给模型配一个 web 搜索工具，由它自行决定何时调用。
- **搜索预算。** 如果选择搜索工具方式，还可以给模型一个预算，限定它允许发起多少次搜索。这让模型在不满意结果时调整查询，或进行追加搜索。我们的运行使用 1、5 或 25 轮。

为了全面理解 web 搜索性能，我们定期在多个模型、引擎和搜索配置下运行四个基准：

- [BrowseComp](https://openrouter.ai/benchmarks/browsecomp)：需要真实浏览的困难事实查找
- [DeepSearchQA](https://openrouter.ai/benchmarks/deepsearchqa)：多跳研究问题
- [WideSearch](https://openrouter.ai/benchmarks/widesearch)：覆盖面广的"填满整张表"式收集
- [HLE](https://openrouter.ai/benchmarks/hle)：允许搜索的专家级考试问题

每个页面都按质量、性价比和速度对配置排名，让你能针对你的工作负载最重要的因素来做决策。排行榜是实时的，随着新的运行落地、新的模型和引擎加入，数字会变动。今天的榜首不保证还是明天的榜首。本文不会花太多时间讲今天的领先者，因为我们预期它会变化。相反，来看看数据对"如何为你的工作负载做决策"告诉了我们什么。

## 搜索预算比其他任何因素都重要

把引擎预算从一轮往上增加，对质量的提升超过你能做的任何其他单项改动。举例说明，下面是我们最初在 Perplexity 上跑 BrowseComp、三种不同预算的结果：

| 模型，配合 Perplexity | 1 轮 | 5 轮 | 25 轮 |
| --- | --- | --- | --- |
| Claude Opus 5, high | 35.8% ($0.14) | 66.5% ($0.51) | **89.0%** ($0.99) |
| GPT-5.6 Sol, high | 46.3% ($0.20) | 65.2% ($0.29) | **82.4%** ($0.50) |
| GPT-5.6 Luna, extra-high | 33.7% ($0.02) | 57.0% ($0.04) | **74.0%** ($0.10) |

这一规律在我们测量的所有 provider 上都成立：

![BrowseComp 在各搜索预算下的模型轨迹图，覆盖 Exa、Parallel、Perplexity 和 OpenAI 原生引擎；线条颜色表示搜索引擎，线型和末端标记表示模型](https://openrouter.ai/blog/images/web-search-benchmark/browsecomp-budget-ladder.png)

这些运行仅覆盖 BrowseComp，使用 server tool、每次搜索返回十条结果，不进行页面抓取和代码执行，且每个配置取最近一次有效运行。

增加搜索深度是我们发现的最便宜的提质手段。从 1 轮提升到 25 轮大致使得分翻倍，而每问题的成本只增加 2.5 到 7 倍。

你可能以为这会普遍拖慢响应时间，但事实并非总是如此。例如，Luna 在 1 轮时每问题耗时 140 秒，25 轮时反而是 111 秒。在我们同时跑了 1 轮和 5 轮的 35 个配置中，超过三分之一在轮次更少时反而更慢。它们全是 OpenAI 的模型——这些模型用额外的推理来应对受限的搜索预算。

另一方面，在较简单的任务上，搜索深度可能反而伤害成本。例如在 HLE 上，GPT-5.6 Sol 配合 Perplexity 在 1 轮和 25 轮的得分相近，成本却是三倍。如果你的搜索往往比较简单，把预算限制住可能仍然是值得的。

## 最坏情况的成本由你的失败率驱动

扩展预算有害的另一种情形，是模型根本找不到答案。我们发现，模型即便最终会失败，也会把预算耗尽来试图找到答案。

| 套件（25 轮预算） | 答对时的平均搜索次数 | 答错时的平均搜索次数 |
| --- | --- | --- |
| BrowseComp | 10.3 | 19.7 |
| DeepSearchQA | 11.7 | 20.1 |
| HLE | 5.2 | 7.5 |
| WideSearch | 17.6 | 23.4 |

我们记录到的最深尝试是在一个 WideSearch 表格上搜索了 81 次，最终评分仍为错误。如果你的工作负载失败率很高，那么降低搜索深度很可能是削减成本的高效路径。

## 引擎固然重要，模型更重要

预算定了之后，下一个最重要的问题是选用哪个模型。

| 模型 | Perplexity | Exa | Parallel |
| --- | --- | --- | --- |
| Claude Opus 5, high | **89.0%** ($0.99) | 82.2% ($1.29) | 88.8% ($2.42) |
| GPT-5.6 Sol, high | **82.4%** ($0.50) | 77.8% ($0.54) | 76.6% ($1.26) |
| DeepSeek V4 Flash, high | **77.0%** ($0.08) | 67.4% ($0.12) | 64.6% ($0.10) |
| GPT-5.6 Luna, extra-high | **74.0%** ($0.10) | 68.4% ($0.14) | 58.0% ($0.11) |

上表是 25 轮下的 BrowseComp 结果，对比了前沿模型与高性价比模型在各搜索引擎上的表现。

固定模型、更换引擎，得分平均变化 10 个百分点；而前沿模型与经济型模型之间的平均差距更大，为 15 个百分点。跨引擎来看，价格波动最大的是前沿模型：最贵的引擎是最便宜引擎的 2.5 倍；经济型模型则为 1.5 倍。

之所以能做这样的对比，是因为 server tool 位于 provider 之上。你在请求中更换模型，搜索行为保持一致——哪怕某个模型的 provider 本身不提供任何搜索。

当然，基准只是性能可能性的参考。它们告诉你哪些配置值得一试、大致花费多少。这些选择在你自己的真实任务上的成本和质量会有差异，所以对这些页面最有价值的用法是把它们当作候选清单，然后用你自己的问题去跑排名前几行的配置。

## 在你自己的工作负载上试

上面每一项都是你现在就能在 OpenRouter 上设置的请求参数。

- **Web plugin。** [web plugin](https://openrouter.ai/docs/guides/features/plugins/web-search) 在模型开始生成之前执行一次搜索，对于只需要新鲜事实的问题，这是又快又便宜的选择。
- **Server tool。** [server tool](https://openrouter.ai/docs/guides/features/server-tools/web-search) 把搜索工具交给模型，由它决定接下来查什么，适合答案需要多步才能找到的情形。
- **引擎。** 在 OpenRouter 上，把 `engine` 设为 `exa`、`parallel`、`perplexity` 或 `native`；`auto` 会先尝试原生引擎，再回退到第三方。
- **搜索预算。** 顶层的 `max_tool_calls` 请求字段限定它能获得多少 agent 轮次，也就是它必须作答前最多可以搜索多少轮；`max_results` 设定每次返回的结果数量。

一个合理的起点：挑选最接近你任务的套件，取与最高分相差几分以内最便宜的配置，然后针对其上两三行重跑你自己的评测集，看额外开销是否体现在你的结果里。

## 基准方法论

每次运行都通过公开的 OpenRouter API 打到生产 endpoint，使用我们的[开源基准测试框架](https://github.com/OpenRouterTeam/benchmark-harness)。

- **隔离到搜索性能。** 为确保只比较搜索配置，我们统一为每次搜索十条结果、不进行页面抓取、不执行代码。每个模型的 reasoning 固定，如表中所示。
- **评分严格。** 每个被评估的答案对照官方答案键判对错，在需要语义比较时使用 LLM judge。WideSearch 还单独报告答题项级别的准确率。
- **成本和速度按问题计。** 成本是包含评分在内的总支出除以被评估的问题数。速度是每个被评估问题的候选生成时间。
- **每个页面展示每个配置最近一次有效运行。** 一次运行在完成最少问题数后即为有效，新运行会取代旧运行。

## FAQ

### 这些分数与厂商公布的 agent 排行榜相比如何？

不能直接比较。这些基准公布的大多数榜单衡量的是完整的 agent 产品，融合了搜索、整页抓取和代码工具。这些排行榜隔离的是搜索配置：模型只阅读搜索结果摘要，页面抓取和代码工具都关闭。这样可以对各配置直接比较，但不会把基准分数最大化。

### 我该选哪个搜索引擎？

取决于模型和任务，这正是这些页面存在的意义。引擎之间的差距对某些模型很大、对另一些则可忽略，而且某 provider 自家的原生搜索并不自动就是它的最佳选项。查看最接近你工作负载套件的实时排行榜，在分数的同时阅读成本和延迟，并定期复查——随着新运行落地，排序会变化。

### 这些数字有多新？

排行榜始终展示每个配置最近一次有效运行，由 OpenRouter 的基准测试框架打到生产 endpoint 执行。新运行会在页面上取代旧运行。
