# OpenRouter 可靠性和自动故障转移：请求如何保持成功

OpenRouter ·6/12/2026 · 更新于 9/24/2026

直接调用一家提供商，就意味着一个单点故障。它一宕机，你的用户就开始看到报错，而你一小时后才知道——从一张工单里。这就是 OpenRouter 要解决的问题：它路由每一个请求、让请求保持成功——跨提供商自动进行，配置之后还能跨模型。

在 OpenRouter 上，你用两个相互独立的配置把可靠性做进应用。提供商故障转移是自动的、默认开启；模型回退是自选开启。

这两层覆盖不同的故障：如果主力模型的每家提供商同时失败，提供商故障转移就无处可去，模型回退是第二道防线。

这份配置值得作为每个项目的起点。复制过去再调整：

```
from openrouter import OpenRouter

client = OpenRouter(api_key="<OPENROUTER_API_KEY>")

completion = client.chat.send(
    model="anthropic/claude-sonnet-4.6",
    models=["openai/gpt-5.4-mini"],  # fallback if the primary fails
    messages=[{"role": "user", "content": "Summarize this incident report."}],
)
```

## 太长不看

- LLM 请求失败的原因可预期：提供商宕机、速率限制（429）、上下文长度错误、内容审核拒绝。
- 可靠性分两层：提供商层故障转移（默认开启，在单个模型内恢复）和模型层回退（通过 `models` 数组自选开启，跨模型恢复）。
- 路由层实时探测提供商健康、绕开宕机，所以最坏情况下的可用性也好于任何一家你直接集成的单一提供商。
- 故障转移会按顺序走完你的 `models` 列表；列表耗尽后返回最后一个错误，所以请把可靠的兜底模型排在最后。
- 最终失败的请求不收钱，但用户报告过边缘情形（某些 429 路径、部分输出）仍然消耗了额度。请盯紧 activity log 并设置支出限额。
- 用 `only`/`ignore`/`order` 限定提供商，是拿可靠性换控制权：候选集越窄，回退选项越少。

## LLM API 请求为什么会失败？

提供商宕机、速率限制（429）、上下文长度校验错误、内容审核拒绝——这是 LLM 请求失败的可预期原因。单一直连提供商的集成对它们任何一条都没有恢复路径，所以每一条都会变成用户可见的错误。

最简单的例子是速率限制。你直连一家提供商，撞上它每分钟的上限，你只有退避、排队或失败三个选项。哪一个都帮不了那个盯着加载转圈的用户。

社区把路由层称作"[AI 的 DNS](https://news.ycombinator.com/item?id=45050428)“是有原因的：它活着，是因为它有不止一个可以把请求发过去的地方。

这 4 种失败模式各自对应 OpenRouter 的一个恢复层，弄清哪层管哪件事，才能把可靠性配对。

### 4 种失败模式，对应到恢复层

什么会坏，OpenRouter 的哪一层能救。

| 失败模式 | 表现 | 由谁恢复 |
| --- | --- | --- |
| 提供商宕机/不可用 | 5xx、超时、连接被断 | 提供商层故障转移（换下一家提供商） |
| 速率限制（429） | 提供商返回 "Too Many Requests" | 提供商层故障转移，然后模型回退 |
| 上下文长度错误 | 提示词超出模型窗口 | 模型层回退（换更大上下文的模型） |
| 审核拒绝 | 有过滤的模型拒绝回答 | 模型层回退（换无过滤的模型） |

前两种是 infrastructure 问题，第二家提供商就能解决；后两种是模型问题，得第二个模型来解决。

## OpenRouter 上失败的请求要付钱吗？

短答：不要。故障转移耗尽后请求最终失败时，你不被计费；只为成功的那次运行付钱（[零补全保险](https://openrouter.ai/docs/guides/features/zero-completion-insurance)）。

这让"以重试为设计前提"很便宜：一条烧过 3 家提供商才成功的回退链，你只付一次成功补全的钱。你可以放心大胆地配回退，不用每次失败都盯着计费表。

### 要提前规划的例外

现实世界的边缘情形是存在的，与其让你从计费仪表盘上发现，不如在这里先读到手。有用户报告过错误 429 消耗了额度、或部分输出在报错情况下仍被计了账。所以政策是"只为成功运行付费"，但少数 429 路径和部分输出确实漏网了。

诚实的取舍：零补全保险是真的，但不是密不透风的。查你的 activity log 确认到底为什么扣了钱，并设硬支出限额，让边缘情形刷不出大账单。带支出上限去设计，而不是假设每个失败请求都免费。

## 提供商故障转移 vs 模型回退

OpenRouter 在两个不同的层面上从失败中恢复。提供商层故障转移自动且默认开启；模型层回退要通过 `models` 数组自选开启。一层让单个模型跨提供商活着，另一层整个换到别的模型。

OpenRouter 自动在提供商之间故障转移，你用 `ignore`、`only`、`order` 塑造候选集。常见情况你不用写任何重试逻辑。

`ignore` 按 slug 屏蔽特定提供商；`only` 限定白名单；`order` 设定明确的"先试这个"顺序。

三者都会收窄候选集，请有意识地使用：可回退的提供商越少，回退选项越少。

|  | 提供商层故障转移 | 模型层回退 |
| --- | --- | --- |
| 恢复什么 | 服务你模型的提供商宕机或 429 | 整个模型不可用，外加上下文长度和审核拒绝 |
| 默认 | 开（`allow_fallbacks: true`） | 关，直到你设置 `models` 数组 |
| 控制它的配置 | `allow_fallbacks`、`order`、`only`、`ignore` | `models` 数组（优先级顺序） |
| 恢复范围 | 同一模型，换提供商 | 整个换到另一个模型 |

![OpenRouter 两层可靠性示意图：提供商层故障转移在单个模型内换提供商，模型层回退切换到另一个模型](https://openrouter.ai/blog/images/failover-two-layers.png)

这是静态视角。下面的图展示运行时实际发生的事：单个请求如何穿过两层、从哪里以成功或最终错误离开。

![请求生命周期流程图：请求先试主力模型的各提供商，再落到回退列表里的下一个模型，最终以成功或最终错误离开](https://openrouter.ai/blog/images/failover-request-lifecycle.png)

### 提供商层故障转移：一个模型，多家提供商

像 Claude Sonnet 4.6 这样的单个模型通常由多家提供商服务。如果 OpenRouter 选中的提供商返回 5xx 或对你限流，它会自动为该模型试下一家提供商。这一层由 `allow_fallbacks` 管，默认 `true`（[提供商选择文档](https://openrouter.ai/docs/guides/routing/provider-selection)）。

零配置。发出第一个请求你就拥有了它。

### 模型层回退：整个模型不可用时

如果你主力模型的每家提供商都失败了，提供商层故障转移已无路可走。这时 `models` 数组接管：OpenRouter 移到你列表里的下一个模型（[模型回退文档](https://openrouter.ai/docs/guides/routing/model-fallbacks)）。这一层需要自选开启，因为它改变了"由哪个模型作答"——这个决定只有你能做。

上下文长度错误或审核拒绝同样会触发这一层，因为这些问题换一家提供商解决不了。

两层协同工作，但幕后机制不同。提供商层故障转移无需配置自动运行。下面是它对每个请求实际做的事。

## 提供商层故障转移如何让一个模型保持在线

对每个模型，OpenRouter 在各提供商之间做负载均衡以最大化在线率，规则公开且分 3 步：优先过去 30 秒无显著宕机的提供商；在稳定的候选中按价格平方倒数加权挑成本最低的；其余留作回退（[提供商选择文档](https://openrouter.ai/docs/guides/routing/provider-selection)）。这是一个可靠性优先、顺带管成本的机制。

实际效果：过去 30 秒内出过错的提供商自动排到队尾；在稳定提供商里，最便宜的那个按价差的大约平方倍被优先选中。可靠性第一、成本第二、全自动。

对在线率真正重要的是那 30 秒窗口。最近半分钟打过嗉的提供商会自动让出队首，不需要你做任何事。

### 推一遍负载均衡的数学

文档里的实例展示了可靠性和成本如何配合。假设提供商 A $1/M token、提供商 B $2/M、提供商 C $3/M，且 B 最近宕过几次。

OpenRouter 先路由到 A；由于平方倒数加权（1/3² = 1/9），A 先于 C 被尝试的概率约是 C 的 9 倍。A 失败则下一个是 C。最近不稳的 B 最后被试：宕机史把不可靠的提供商压到队尾，但不排除它。

![价格加权故障转移实例：$1/M 的提供商 A 先试，$3/M 的提供商 C 第二，近期退化的 $2/M 提供商 B 最后](https://openrouter.ai/blog/images/failover-provider-weighting.png)

这是默认行为。但如果你已经知道某家提供商不行，不必等路由数学慢慢发现。

### 控制候选集

你可以塑造哪些提供商有资格，这也是屏蔽不可靠提供商的方法：

- `order`：按明确顺序尝试，如 `order: ["anthropic", "together"]`。
- `only`：本请求提供商 slug 的白名单。
- `ignore`：黑名单，如 `provider: { ignore: ["deepinfra"] }` 用来跳过一个你发现提供过度量化模型的端点。
- `allow_fallbacks: false`：硬停在你指定的提供商，不自动找替补。

诚实的取舍：用 `only`、`ignore` 或 `order` 收窄"可能显著减少回退选项、限制请求恢复能力"（[提供商选择文档](https://openrouter.ai/docs/guides/routing/provider-selection)，原文引述）。你排除的每一家提供商，就是一个少一处可能的恢复点。收窄池子买来控制权，花掉的是可靠性，剪枝请三思。

### 不丢池子的前提下约束最坏延迟

需要可预测延迟时，用 `preferred_max_latency` 或 `preferred_min_throughput` 设滚动 5 分钟窗口的分位数阈值（[提供商选择文档](https://openrouter.ai/docs/guides/routing/provider-selection)）。达不到阈值的端点会被降优先级而不是排除。和 `ignore` 组合起来长这样：

```
completion = client.chat.send(
    model="deepseek/deepseek-v4-flash",
    provider={
        "preferred_max_latency": {"p90": 3},   # prefer <3s for 90% of requests
        "ignore": ["deepinfra"],               # skip a known-bad endpoint
    },
    messages=[{"role": "user", "content": "Classify this ticket."}],
)
```

以上全部都是在让一个模型跨提供商活着。但如果该模型的每家提供商都倒下了，提供商故障转移已无处可去。

模型回退接管，尝试你列表中的下一个模型。它们是顺序协作的两层，`models` 数组就是打开第二层的开关。

## 如何配置模型回退

按优先级传一个 `models` 数组；第一个模型的所有提供商都出错时，OpenRouter 就试下一个模型（[模型回退文档](https://openrouter.ai/docs/guides/routing/model-fallbacks)）。一个数组，零重试代码。OpenRouter 各 SDK 把 `models` 作为一等字段；用 OpenAI SDK 时通过 `extra_body` 传入。

cURL：

```
curl https://openrouter.ai/api/v1/chat/completions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "models": ["anthropic/claude-sonnet-4.6", "openai/gpt-5.4-mini"],
    "messages": [{"role": "user", "content": "Draft a release note."}]
  }'
```

TypeScript：

```
import { OpenRouter } from '@openrouter/sdk';

const openRouter = new OpenRouter({ apiKey: process.env.OPENROUTER_API_KEY });

const completion = await openRouter.chat.send({
  models: ['anthropic/claude-sonnet-4.6', 'openai/gpt-5.4-mini'],
  messages: [{ role: 'user', content: 'Draft a release note.' }],
});
```

### 完整的触发条件清单

知道回退存在，不如知道它何时触发。以下 4 个条件中的任意一个都能触发，直接引自[模型回退文档](https://openrouter.ai/docs/guides/routing/model-fallbacks)：

| 触发条件 | 含义 | 哪层恢复 |
| --- | --- | --- |
| 宕机 | 提供商不可达或持续 5xx | 提供商层，然后模型层 |
| 速率限制 | 提供商返回 429 | 提供商层，然后模型层 |
| 上下文长度校验错误 | 提示词超出模型窗口 | 模型层（移到更大上下文的模型） |
| 审核标记 | 有过滤的模型拒绝回答 | 模型层（移到无过滤的模型） |

定价跟随真正作答的那个模型，模型名在响应的 `model` 字段里返回。请检查该字段确认是谁服务了请求，尤其是回退触发之后。

触发清单讲了回退何时启动。它没讲的是何时停止。

### 只有撞上才会知道的边界

回退止步于你列表的末尾。"如果回退模型也宕机或返回错误，OpenRouter 就把那个错误返回给你"（[模型回退文档](https://openrouter.ai/docs/guides/routing/model-fallbacks)）。它只按顺序走完你的 `models` 数组一次，不存在无限重试链。

当故障不属于 OpenRouter 归类为"可回退"的错误时，回退也不会触发（例如畸形请求的 400 会原样打回来）。

实际解法：排列 `models` 数组时，把最可靠的兜底模型放在最后——那个在所有前面模型都倒下后你还敢托付答案的模型。

## OpenRouter 如何实时绕开宕机

OpenRouter 持续监控所有提供商的响应时间、错误率和可用性，并基于这些实时反馈路由（[在线率优化文档](https://openrouter.ai/docs/guides/best-practices/uptime-optimization)）。你不用自建监控就获得自动的提供商健康探测——这正是企业评估者第一个问的可靠性功能。这些实时数据喂给 30 秒宕机窗口：此刻正在退化的提供商，此刻就会被绕开，不用等状态页更新。

### 可验证的公开在线率

文档内嵌了 Claude Sonnet 4.6、GLM 5.1 等模型的实时在线率小组件，提供商可用性是你看得见的东西，而不是选择相信的东西（[在线率优化文档](https://openrouter.ai/docs/guides/best-practices/uptime-optimization)）。三个信号进路由决策：

- 响应时间：把慢端点降权。
- 错误率：让持续 5xx 的提供商退出队首。
- 可用性：驱动 30 秒宕机窗口。

如果你在为生产环境做评估，这就是答案：实时健康路由、30 秒宕机窗口，加上真正可验证的逐模型公开在线率——而不是 PPT 上的一个可用性百分比。

### 平台健康 vs 路由健康

逐提供商的路由健康负责实时引导单个请求。平台层面的健康——网关本体——在 [status.openrouter.ai](https://status.openrouter.ai)。

影响整个网关的事故请看状态页；单个提供商抽风，交给实时路由自己处理就好。

路由健康 OpenRouter 自动管，网关本体要你自己盯。那么故障转移不管哪些事？

## 故障转移不覆盖什么

故障转移从提供商和模型错误中恢复，边界就在这里。它不会永远重试，抓不住"没报错但很烂"的响应，不能在所有提供商上退还被取消的流，也无法让网关本体对自家宕机免疫。下面精确说明它止步何处、每件事你该怎么办。

| 边界 | 含义 | 你的对策 |
| --- | --- | --- |
| 受限于你的列表 | `models` 数组里每个模型都报错后，返回最后一个错误 | 把可靠的兜底模型排在 `models` 最后 |
| 非错误的拒绝 | "烂"但不报错的响应不是回退触发条件 | 正确性重要时自己校验响应 |
| 流取消 | 中止流在部分提供商上仍然计费（包括 Bedrock、Groq、Google、Mistral） | 成本敏感的流式路径只路由到支持取消的提供商，或为此留预算 |
| 网关依赖 | 路由层自己也会宕机（2025 年 8 月，约 50 分钟） | 在你这边设计重试；盯住 status.openrouter.ai |

### 受限于你的列表，且只对分类过的错误生效

回退按顺序尝试 `models` 数组里的每个模型。最后一个也失败时，那个错误就回到你手上（[模型回退文档](https://openrouter.ai/docs/guides/routing/model-fallbacks)）；你列的之外没有重试链。

更要注意：模型带着 200 状态返回垃圾时，回退根本不会触发。OpenRouter 只在被分类的错误上触发。把 `models` 数组以可靠兜底模型收尾，正确性重要时自己校验响应。

### 某些提供商上取消流仍继续计费

流在客户端停止渲染、账单却按全额落账时，你的第一反应通常是翻日志。你会怀疑提示词触发了内容审核标记，或者花时间找一个根本不存在的 5xx。

一部分提供商——包括 Bedrock、Groq、Google 和 Mistral——不支持流取消（[流式参考](https://openrouter.ai/docs/api/reference/streaming)）。你在响应中途 abort 时，连接在你这边关闭了，模型却在它那边继续生成（并继续计费）。

对策：成本敏感的流式路径显式地只路由到支持流取消的提供商，或者为超支留预算。

### 网关本身也是依赖

2025 年 8 月，一次约 50 分钟的[数据库宕机](https://status.openrouter.ai/incidents/wn69pKYg-WoP)把路由层打倒了。路由层也有自己的单点故障。

[Hacker News 帖子](https://news.ycombinator.com/item?id=45050428)自己的结论很公道："可用性仍然好于任何单一提供商"，但它不是零风险。在你这边设计重试，并通过 [status.openrouter.ai](https://status.openrouter.ai) 关注网关级事故。

## 生产环境故障转移配置清单

两层合一，再加一道支出护栏。下面的配置是多数生产环境该有的形态：一条带可靠底价的模型链、默认提供商故障转移保持开启、排除一个已知劣质端点、给面向用户的路径设延迟阈值。

| 步骤 | 动作 |
| --- | --- |
| 1 | 设置 `models` 数组，最可靠的兜底模型放最后，让最终回退是你最信任的那个。 |
| 2 | 保持 `allow_fallbacks: true`（默认），除非合规或 BYOK 合同强制单一提供商。 |
| 3 | 用 `ignore` 排除你发现服务不佳的提供商端点；每个模型页面的提供商在线率标签就是发现它们的办法。 |
| 4 | 给面向用户的路径加 `preferred_max_latency` 分位数阈值，约束尾部延迟。 |
| 5 | 信赖零补全保险，同时设置支出限额，并为 429 边缘情形盯住 activity log。 |
| 6 | 监控 [status.openrouter.ai](https://status.openrouter.ai) 的网关级事故。 |

这就是每个项目推荐的起始配置。复制过去再调整：

```
from openrouter import OpenRouter

client = OpenRouter(api_key="<OPENROUTER_API_KEY>")

completion = client.chat.send(
    model="anthropic/claude-sonnet-4.6",
    models=["openai/gpt-5.4-mini", "google/gemini-3.5-flash"],  # floor model last
    provider={
        "ignore": ["deepinfra"],               # exclude a known-bad endpoint
        "preferred_max_latency": {"p90": 3},   # bound worst-case latency
        # allow_fallbacks stays true by default
    },
    messages=[{"role": "user", "content": "Summarize this thread."}],
)

print(completion.model)  # confirm which model answered
```

拿到 API key，故障转移的默认值就已经生效。我们建议第一天就加上 `models` 数组——这是你能设置的最便宜的安全网。

## 常见问题

### 提供商宕机时 OpenRouter 怎么处理故障转移？

对由多家提供商服务的单个模型，选中的提供商返回 5xx 或限流时，OpenRouter 自动尝试下一家。这个提供商层故障转移默认开启（`allow_fallbacks: true`），无需任何配置（[提供商选择文档](https://openrouter.ai/docs/guides/routing/provider-selection)）。

### 提供商故障转移和模型回退有什么区别？

提供商层故障转移靠换提供商保住一个模型，是自动的。模型层回退通过 `models` 数组整体切换到另一个模型，需要自选开启。前者从提供商宕机和速率限制中恢复；后者还能从上下文长度错误和审核拒绝中恢复。

### 什么会触发 OpenRouter 的自动回退？

4 个条件：宕机、速率限制、上下文长度校验错误、有过滤模型的审核标记（[模型回退文档](https://openrouter.ai/docs/guides/routing/model-fallbacks)）。宕机和限流先在提供商层处理，再落到模型层；上下文长度和审核直接在模型层处理。

### OpenRouter 对失败的请求收费吗？

不收。只为成功的运行付钱；故障转移耗尽后失败的请求不计费（[零补全保险](https://openrouter.ai/docs/guides/features/zero-completion-insurance)）。但请为一个有据可查的例外做规划：用户报告过某些 429 路径和部分输出仍消耗了额度，所以请设支出限额并查看 activity log。

### 生产环境中 OpenRouter 有多可靠？

它用 30 秒健康窗口和公开的逐模型在线率实时绕开提供商宕机（[在线率优化文档](https://openrouter.ai/docs/guides/best-practices/uptime-optimization)），这让它的最坏情况可用性优于任何直接集成的单一提供商。但并非零风险：[2025 年 8 月的网关宕机](https://status.openrouter.ai/incidents/wn69pKYg-WoP)说明路由层也有自己的依赖。设计好重试，并监控 [status.openrouter.ai](https://status.openrouter.ai)。

### 怎么在 OpenRouter 上设置回退模型？

按优先级传 `models` 数组。OpenRouter 各 SDK 把 `models` 作为一等字段，如 `models=["openai/gpt-5.4-mini"]`；用 OpenAI SDK 时通过 `extra_body` 传入（[模型回退文档](https://openrouter.ai/docs/guides/routing/model-fallbacks)）。

把最可靠的模型放最后，让最终回退成为你的地板。
