# 在 OpenRouter 上治理团队的 AI 支出

OpenRouter · 2026-08-06 · 更新于 2026-09-24

你团队的 AI 账单，等于每个工程师手里所有 key 的总和。一位开发者为某个小实验建了个 key，另一位把几个 key 接进了 CI 流水线，还有一位把 token 粘进 notebook、原型跑通之后就忘了那个 key 还活着。

单看每一件事都谈不上粗心，但加总起来，账单就变得难以解释。OpenRouter 有 6 个控制手段能为此建立秩序，本文逐一讲清每个手段、适合什么样的团队、需要什么套餐。

这些控制是层层叠加的。所以先用能覆盖你风险的最便宜的那一个，确有需要再加。当两个控制重叠时，更严格的那个生效：允许列表取交集，较低的预算先拦截。

## 在 OpenRouter 上治理团队 AI 支出最快的方式是什么？

挑一个最适合你团队风险的最便宜控制，然后逐层加码。小团队往往第一天只需要每 key 限额加上 Activity 面板。

每个控制干的是三类工作中的一种。预算和每 key 限额决定"能花多少"；模型与 provider 允许列表决定"能花在哪"；Activity 面板展示"谁花的"。这 6 个控制分布在这三类工作上并且协同发力，所以你很少需要同时上全部 6 个。

### 控制手段对照表

自上而下读。能拦截支出的控制排在前面，只做跟踪的排在最后。除 workspace budgets 需要 Enterprise 外，全部在免费和按量付费（PAYG）套餐上可用。

| 控制 | 封顶或限制什么 | 在哪里设置 | 谁可以设置 | 套餐层级 | 拦截还是跟踪 |
| --- | --- | --- | --- | --- | --- |
| 每 key credit limit | 单个 API key 可花费的 credit 总额 | Dashboard 或 Management API | key 的所有者 | Free / PAYG | 拦截（超限拒绝） |
| Guardrails | 按成员或 key 的预算 + 模型/provider 允许列表 + 隐私 | Settings › Privacy | 账号所有者（组织内为 org admin） | Free / PAYG | 拦截（触顶返回 403） |
| Workspace budgets | 整个 workspace 的总支出 | Workspace 设置或 Management API | 组织管理员 | Enterprise | 拦截（触顶返回 403） |
| Presets | 请求使用的模型、路由与配置 | Presets 设置 | 组织成员（共享到全组织需 admin） | Free / PAYG | 跟踪（默认值，非硬上限） |
| 组织与角色 | 谁拥有支出权限；共享 credit 池 | Organization 设置 | 组织管理员 | Free / PAYG | 跟踪（是结构，不是上限） |
| Activity 面板 | 什么都不限制；只做报告 | Activity 页面 | 全体组织成员（可见性） | Free / PAYG | 跟踪（用量 + 导出） |

一套务实的配置通常是至少一个拦截型控制配一个报告型控制。例如：给生产服务 key 设月度限额，再用 Activity 面板告诉你支出是否真的落在该服务上。如果某个开发者需要比别人更严的模型允许列表或预算，就为那位成员加一个 guardrail。

## 你到底在为什么付钱？

在设置任何控制之前，先弄清支出本身是什么。我们[不加成 provider 定价](https://openrouter.ai/pricing)，模型目录里的价格就是推理的实际成本。平台费在购买 credit 时收取（标准 PAYG 卡充值 5.5%，最低 $0.80），而不是按请求收。失败的请求根本不计费。

所以没有需要稽查的隐藏加成。这些控制的职责很简单：封顶你的团队实际跑了多少推理。

[模型目录](https://openrouter.ai/models)列出了你要封顶的各模型费率。

### 自带 key（BYOK）的支出行为不同

BYOK 支出不总是记在你预期的地方，所以在围绕它搭控制之前要先查清。当你通过自己的 provider key 路由时，我们按[模型成本收取 5% 费用](https://openrouter.ai/docs/guides/overview/auth/byok)。免费额度取决于套餐，按目录价的推理成本计量。当前额度详情见[定价页面](https://openrouter.ai/pricing)。

Workspace budgets 和 guardrail budgets 默认都只统计 OpenRouter credit 支出，所以如果你的团队主要跑自己的 provider key，一个预算覆盖的账单比看上去要少。两者都有一个 **Include BYOK spend** 设置（`include_byok_in_budgets`），打开后 BYOK 推理也计入限额。

让每次请求更便宜，与封顶团队支出是两个话题。前者见[以成本为导向的 provider 路由](https://openrouter.ai/blog/tutorials/how-to-get-the-lowest-cost-llm-inference-on-openrouter/)和 [prompt 缓存](https://openrouter.ai/docs/guides/best-practices/prompt-caching)。

## 如何给单个 API key 封顶支出？

每 key 限额是最简单的硬上限。它限制一个 API key，且不需要组织就能用。

当你想给某一个工程师、服务、环境、原型或外包的 key 封顶时使用。staging key 可以配一个较小的每日限额；生产服务 key 可以配一个较大的月度限额；临时评估 key 可以按周重置，让实验在评审结束后自动停支。

限额可以在 dashboard 中设置，也可以通过 [Management API](https://openrouter.ai/docs/guides/overview/auth/management-api-keys) 设置——它能创建、轮换、更新和禁用 key。这意味着内部发放流程可以让每个 key 从第一天起就带限额，而不必指望有人事后补上。

它的弱点在于：每 key 限额封的是 key，不是人。如果一个人持有 5 个各自带每日限额的 key，他就能花掉 5 个限额之和——key 之间互不知情。每 key 限额也不管调用方能使用哪些模型或 provider。

从每 key 限额起步。当你需要一条跟着人走的规则，或者一条把预算与模型、provider、隐私限制合并的规则时，再上 guardrails。

## Guardrails 如何控制预算、模型和隐私？

一个 [guardrail](https://openrouter.ai/docs/guides/features/guardrails) 是跟着人或跟着 key 走的策略。

一个 guardrail 可以同时包含预算限额、模型允许列表、provider 允许列表、Zero Data Retention 规则、prompt 注入与越狱检测、敏感信息处理以及自定义 regex 过滤。把它指派给一个组织成员，就成为该成员所有 key 的基线；也可以直接指派给单个 API key 实现精确控制。

当"封住这个 key"不够、你真正想要的规则是"这个人只能用这些模型、在这个预算内、在这些隐私规则下"时，就用 guardrail。

平台团队通常会走到这一步，因为不同群体需要的东西不同：组织里一组人在生产环境用前沿模型——推理准确率比价格重要；另一组跑依赖大吞吐的批处理任务，可以用更便宜的模型；第三组要处理可能含敏感信息的输入，需要 ZDR。Guardrails 让你一次设好这些规则，而不是要求每个应用团队把政策写进代码。

![Guardrail 分层示意图：账号级设置、workspace 默认、成员 guardrail 与 API key guardrail 合成一个最终生效的请求策略——允许列表取交集，任一层启用 ZDR 即生效，各预算独立校验](https://openrouter.ai/blog/images/governing-guardrail-layering.png)

我们遵循一条简单的分层规则：更严格的永远获胜。图中参与一个请求的层次包括：你的账号设置、workspace 默认值、指派给成员账号的 guardrail、直接指派给某个 API key 的 guardrail。所有层合成一个生效的请求策略。

当多个 guardrail 同时作用于一个请求时，其访问受最严格规则约束。模型与 provider 允许列表同理。例如账号基线允许 10 个模型、而 API key guardrail 只允许其中 3 个，那么该 key 得到的是 3 个模型而不是 10 个。provider 允许列表也一样。对 ZDR 而言，任何一层为某个模型组打开它，它就是打开的。

当多层都设置了敏感信息过滤器时，它们全部生效；若其中一个过滤器拦截请求而另一个做脱敏，拦截的规则获胜。预算也是分别校验的。如果团队同时设了成员级预算和 key 级预算，它们不会合成一个池子——一个请求必须同时通过两个预算。

对于控制预算的 guardrail，强制执行是按用户、按 key 独立计算的，并不共享。也就是说一个 guardrail 预算独立作用于你指派到的每个成员和每个 key。把同一个每日预算 guardrail 给三个成员，每人各自享有那个预算，而不是共享一个大池子。当一个 key 向 OpenRouter 发出请求时，用量同时计入该 key 的预算和该 key 所属成员的预算。

这正是用 guardrails 而非只用每 key 限额的主要理由。有了 guardrails，你可以非常轻松地封住一个人跨所有 key 的总支出，同时仍保留在某个应用需要更小上限时单独收紧某一个 key 的能力。

有几点要知道。在组织中，只有 admin 管理 guardrails（个人账号也能为自己的 key 创建 guardrails）。注意允许列表需要随你的模型政策变化做维护。还有，当预算耗尽时，调用方会直接收到 403，事先没有任何警告。

## 什么时候该用 workspace budget？

当你需要给整个 workspace 上硬上限、不管里面有多少 key 时，就用 workspace budget。为每日、每周、每月或终身窗口设一个 USD 限额，[OpenRouter 会在触顶时以 403 拦截请求](https://openrouter.ai/docs/guides/features/workspaces/workspace-budgets)。这一下封住了整个环境，你不必逐个稽查里面的每个 key。

### 套餐层级限制

Workspace budgets 是 Enterprise 功能，由组织管理员创建和管理。每 key 限额和 guardrails 在免费与 PAYG 套餐上都可用，workspace budgets 则不行。如果你不在 Enterprise，用按成员的 guardrail 预算来替代封顶团队支出。

### Workspace 如何嵌合

一个 workspace 把一支团队的配置与另一支隔离开。每个 workspace 有[自己的 key、guardrails、BYOK、路由、presets、plugins、可观测性、成员和预算](https://openrouter.ai/docs/guides/features/workspaces)。但计费、管理 key 和隐私设置在账号层级，Activity 与 Logs 也是账号级视图（可按 workspace 过滤）。因此，workspace budget 实际上一次性封住了经该 workspace 路由的一切，而且只有 admin 能创建或删除 workspace。

有几条限制要知道：

- **短窗口预算必须更小。** 终身预算必须大于月度预算，月度必须大于周度，周度必须大于日度。
- **BYOK 请求。** 使用你自己的 provider key（BYOK）、因而不消耗 OpenRouter credit 的请求，默认不计入预算。打开 workspace 的 **Include BYOK spend** 设置才计入。
- **在途请求。** 预算触顶时已在途的请求会被允许完成，所以实际支出可能略微超出，之后下一条请求才被拦截。
- **暂不支持邮件或 webhook 告警。** 请求被拦截时调用方会收到 403，你可以进入 workspace 设置查看预算状态。

完整规则与实现细节见 [workspace budgets 文档](https://openrouter.ai/docs/guides/features/workspaces/workspace-budgets)和 [enterprise quickstart](https://openrouter.ai/docs/cookbook/get-started/enterprise-quickstart)。

## Preset 能控制团队的支出吗？

不能直接控制。[Presets](https://openrouter.ai/docs/guides/features/presets) 设定请求行为的默认值，但不会自动给请求成本封顶。这就是为什么它们排在上文三个硬上限（每 key 限额、guardrail 预算、workspace 预算）之下。

Preset 是一个具名配置，以 `@preset/slug` 引用，可以包含模型选择、fallback 模型、provider 路由、system prompt 和生成参数。各团队把请求指向一个共享 preset、在一处改配置，而不是在每个服务里硬编码这些选择。

很多浪费的 AI 支出始于陈旧的配置：某个服务为一个不再需要的任务钉着昂贵模型；另一个忘了按价格排序 provider；第三个留着一条老 prompt，在无人在意的上下文上烧 token。Presets 给平台团队一个可以修复默认值的单一位置。

例如，团队可以建一个 "support-triage" preset：使用成本相称的模型、设置 `provider: { "sort": "price" }`、并让各应用保持 system prompt 一致。当团队需要更换模型或路由策略时，改 preset 即可，而不必跨多个服务发布代码。

其局限是 preset 引导行为而非强制执行。请求可以通过自带参数覆盖任何 preset 值。所以 preset 适合标准化自觉守规的应用，不适合阻止一个硬要传不同参数的调用方。

## 组织与角色如何控制"谁能花钱"？

组织把所有成员的支出汇入一个共享 credit 池，并决定谁来管理它。所有成员从[集中计费](https://openrouter.ai/docs/cookbook/administration/organization-management)支取。只有 admin 能购买 credit 和设置计费、provider 与隐私配置。成员创建并只能看到自己的 key。

当超过一两个人共享 AI 支出、又希望只有一张账单和一套管理员时，就创建组织。

角色只有两种：**Admin** 和 **Member**。Admin 掌握支出权限，成员在其下工作，没有更细粒度的子团队权限。组织级 presets 和 guardrails 让 admin 设定作用于全组织的默认值。

组织有一些限制你应该知道：

- [组织成员上限为 10 人](https://openrouter.ai/docs/cookbook/administration/organization-management)——需要更多请联系支持提高上限。
- 个人 credit 转入组织可在 credits 页面自助完成，但有资格规则（账号与成员年龄、新购 credit、冷却期），按发票计费的组织不能接收转入。
- 个人账号不能直接转换为组织。
- 组织内部的隔离来自 workspaces，而不是角色。每个 workspace 有自己的 key、guardrails 和预算，而组织保持一张账单。

## Activity 面板能展示团队支出的什么？

![团队支出去向示意图：每个 API 响应携带的 usage 对象、每个 key 的日/周/月用量窗口、组织级 Activity 面板，以及按模型、API key 或创建者分组的 CSV/PDF 导出](https://openrouter.ai/blog/images/governing-spend-reporting.png)

Activity 面板是其他所有控制之下的报告层。每个 API 响应都带一个含 token 数与成本的 `usage` 对象，并且每个 key 都暴露日、周、月用量总计。在组织中，Activity 面板展示跨成员的用量，导出可按 Model、API Key 或 Creator（组织成员）分组。谁在哪个模型上花了什么，就在这里查明。

有一点要知道：在组织语境下，[activity feed 向所有成员展示所有成员的用量元数据](https://openrouter.ai/docs/cookbook/administration/organization-management)。这包括模型、成本和时间，但绝不包括 prompts 或 responses。成员不能把 feed 过滤为只看自己的活动——这对共同担责是好事，但可能让期望组织内隐私的团队意外。

顺带一提：增加更多 key 或账号并不会提高你的速率限制。Rate limits 与支出限额是两个话题，参见 [rate-limits 参考](https://openrouter.ai/docs/api/reference/limits)。

## 哪些控制适合你的团队？

![决策地图：把团队场景对应到 OpenRouter 支出控制——个人项目用每 key 限额；小团队加组织与 Activity 面板；多团队加 guardrails、presets 与 workspaces；受监管数据加 ZDR、PII 控制与 provider 允许列表](https://openrouter.ai/blog/images/governing-decision-map.png)

这里有一条决策启发式，把上面的控制匹配到你的情形。默认选择能完全覆盖风险的最便宜那一个，除非有理由不这么做。只有当你确实需要给整个环境上硬上限时，才动用 Enterprise 的 workspace budgets。下面每一行是一个决策：

- **个人或副业项目。** 一个带月度重置的每 key credit limit 就够了。
- **小团队、一张账单（10 人以下）。** 建一个组织放共享池，配每 key 限额，用 Activity 面板看谁在花什么。当某个人的访问或预算需要与其他人不同时，加一个 guardrail。
- **多团队，或 staging 对 prod。** 用 workspaces 隔离，为每个成员或 key 配 guardrail 管预算，配模型允许列表，用 presets 标准化配置。在 Enterprise 上再加 workspace budgets。
- **受监管或敏感数据。** 带按模型组 [ZDR](https://openrouter.ai/blog/insights/zero-data-retention/)、PII 过滤器和 provider 允许列表的 guardrails。我们符合 SOC 2 Type 2，但不提供 HIPAA 商业伙伴协议（BAA），因此需要 BAA 的健康数据工作负载目前不适合这一特定要求。

无论你的团队今天是什么样，从简单开始。现在就设每 key 限额，等团队规模或合规要求真正到来时再加 guardrails 和 workspace budgets。一步步的点选版教程见[团队支出控制设置指南](https://openrouter.ai/blog/tutorials/team-spend-controls-setup/)。

## 常见问题

### 我能在 OpenRouter 上按 API key 设支出限额吗？

能。任何套餐（免费或付费）下的每个 API key 都可以设一个以 credit 计的 `limit`，以及 daily、weekly 或 monthly 的 `limit_reset`。超过限额的请求会被拒绝，剩余余额可通过 `GET /api/v1/key` 读取。

### 我如何给整个团队封顶支出？

取决于套餐。免费与 PAYG 套餐上，为每个成员或 key 指派带预算的 guardrail。每个成员和每个 key 各有自己的预算，超过即 403。Enterprise 上，workspace budget 一次性封住整个 workspace。

### 我能限制团队可用的模型吗？

能，通过 guardrail 的模型允许列表（并可同时配 provider 允许列表）。空允许列表意味着所有模型都允许。多个 guardrail 同时生效时，允许列表取交集，即最严格的那个获胜。

### 组织成员能互相看到支出吗？

在组织中，Activity feed 会向所有成员展示所有成员的用量元数据（模型、成本和时间）。我们不存储 prompts 或 responses，因此请求内容始终不可见。组织语境下 feed 不能只过滤出自己的活动。

### 一个 OpenRouter 组织最多能有多少人？

组织上限为 10 名成员。需要更多时，请告诉我们！

### OpenRouter 支持按团队的成本归因吗？

目前支持，但只到成员级别。Activity 面板的导出可按 Creator（组织成员）分组，每个 key 也报告日、周、月总计。没有按子团队的归因。

### 触顶之前 OpenRouter 会给我告警吗？

暂不会。触顶时请求直接得到 403，事先没有邮件或 webhook 警告。你可以在 dashboard 查看当前状态。这对每 key 限额、guardrail 预算和 workspace 预算一视同仁。

### 对医疗团队来说 OpenRouter 符合 HIPAA 吗？

我们目前不提供 HIPAA 商业伙伴协议（BAA）。我们符合 SOC 2 Type 2，因此对需要 BAA 的健康数据工作负载，该特定需求需要另寻路径。
