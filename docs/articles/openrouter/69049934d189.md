# LLM 裁判：自动为 AI 智能体的输出打分

OpenRouter ·9/14/2026 · 更新于 9/24/2026

一个 agent 可以通过每一个确定性测试，仍然给出糟糕的回答。客服 agent 可以调对订单查询工具、取到正确的政策，然后在回复里漏掉退款期限。工具断言全过了，但没有任何环节检查最终回答是否准确、完整、有用。

LLM-as-a-judge（LLM 裁判）评估补的就是这个洞。第二个模型拿你用人话写的标准来审查候选 agent 的输出，返回一个分数。它给了你一个可复现的办法，去测那些存在多种合法表述的开放式回答。

## LLM 裁判是什么

你跑一个候选，把它的输出和相关工具结果交给裁判。裁判对照你写的 rubric（评分规则）给这些证据打分。分数低于你设的阈值，评估就失败。

![流程图：一次候选运行连同其答案和工具轨迹进入一个带着 rubric 的裁判模型，返回分数和理由](https://openrouter.ai/blog/images/llm-as-a-judge-flow.png)

裁判就是一次和普通调用无异的模型请求。它读文本、应用你的标准、返回一个数字。把这个数字当作固定装置下的一次测量，而不是 ground truth。

### 裁判模型与候选模型

- 候选是被测系统。它回答用户、调用工具、写出你在意的那个输出。
- 裁判是另一个模型。它不解决原始任务，只给候选已经完成的东西打分。

尽量让两个角色跑在不同模型上。2023 年的论文 [《Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena》](https://arxiv.org/abs/2306.05685)中，Zheng 等人指出自我增强、位置和冗长三种偏见：裁判可能偏袒自己生成的答案、被摆在优先位置的答案，或无论质量更长的那个答案。

只把可见回复和套用 rubric 所需的工具结果给裁判。裁判一旦能看到候选的隐藏推理，评分就不再独立。

### rubric 评分、精确匹配与人工评审

精确匹配拿字符串或结构化字段和测试数据对照。只有唯一正确答案时用。

在精确匹配和完整 rubric 之间，还有一种确定性内容检查：断言必出现某个短语。在 Ori Eval 里就是 `run.toMention()`。答案必须包含特定术语、但周边表述自由时，它最合适。

rubric 是一个人就能执行的一小组规则。"引用 14 天期限且不编造例外"是 rubric；"听起来有帮助"不是。

人类评审定义质量线，但人不可能给大评估集的每次运行打分，而且两位评审对同一输出可能得出不同结论。裁判是可复现的替身——前提是你拿一小组人工标注校准过它。

### 逐点、成对与参照评分

LLM 裁判有三种评估模式：

| 模式 | 裁判收到什么 | 何时用 |
| --- | --- | --- |
| 逐点（pointwise） | 一个候选输出加一份 rubric | 在 CI 中执行质量线，或监控生产抽样 |
| 成对（pairwise） | 两个候选输出加一份比较规则 | 比较模型、提示词或 agent 版本 |
| 参照式 | 候选输出、rubric 和一份可信参照 | 对照已知的正确答案或来源检查事实覆盖 |

本指南用逐点评分，因为每次运行要么达标要么不达标。成对评估时，两种呈现顺序都要评，以发现位置偏见。参照式评估适合参照包含回答必须保留的事实、而非必须照抄的措辞的场合。

## 什么时候用 LLM 裁判

要求明确、但不是唯一确切输出时，用 LLM 裁判。例如：

- **有依据的回答。**检查最终回答是否用了检索到的数据、没引入无支撑的主张。
- **指令遵循。**验证回答是否遵守了引用政策、索要缺失信息或避免某个动作等要求。
- **完整性。**确认 agent 覆盖了多部分请求的每一部分。
- **语气。**评估回答是否符合作-defined 的客服、法务或品牌口吻。
- **工具使用的成果。**在确定性测试确认了哪些工具跑过之后，裁判评 agent 是否正确使用了工具结果。

结果能直接检查时，LLM 裁判不合适。JSON 结构用 schema 校验器，算术用计算器，工具参数和副作用用单元测试。必须永远拦截某动作的规则要保持确定性。裁判可以审计最终回答的质量，但不该是关键政策的唯一执行层。

一个工具调用测试可以断言 agent 调了一次 `lookup_order`、未经批准从不调 `issue_refund`。裁判随后评的是 agent 的最终回答是否准确解释了发生了什么。如果你还需要搭建执行层，从我们的[工具调用指南](https://openrouter.ai/docs/guides/features/tool-calling)开始。

## 用 Ori Eval 给 agent 打分

[Ori Eval](https://openrouter.ai/docs/guides/ori/eval) 针对你自己的提示词和 agent 行为跑评估。一个 eval 是用 Bun 测试运行器跑的 TypeScript 文件。Ori 在一次运行中解析出一套 harness 和一个模型，并为该运行的每个测试保持它们，提示词无法在运行中途改变配置。模型对比文件仍可以为每个候选模型启动独立的运行。

最快的起点是通过你的编码 agent。下面这条命令是给 agent 跑的，不是让你在终端粘贴的——让 agent 执行它，再按输出里的指示做：

```
curl -fsSL https://openrouter.ai/skills/spawn-ori-eval
```

`spawn-ori-eval` skill 会安装 Ori、确认你已登录、问你要评估什么、写出 eval、运行候选模型，并在给出分数、耗时和成本支撑下推荐一个。它在临时目录工作，不会往你项目里加 eval 文件。想把文件留在项目里、或逐部分检查评估时，用下面的手动步骤。

Ori 的 `setupJudge()` 在自己的模型上创建一个独立的评分 agent，`autoEvals()` 按你的标准给一次候选运行打分。下面的例子测一个回答退款问题的客服 agent。它假设你已有的 Ori harness 能触达该客服 agent 及其工具。

### 1. 安装 Ori 并登录

安装 Ori CLI，然后认证一次：

```
curl -fsSL https://openrouter.ai/labs/ori/install.sh | bash
ori login
```

Ori 用 Bun 跑评估文件。没装 Bun 时，`ori eval` 会请求权限来安装。CI 或其他非交互环境下，命令会停下并告诉你怎么装 Bun。你的应用不需要是 TypeScript 项目。

### 2. 定义一条可观察的质量要求

从你见过或想防住的一次失败开始。这个例子里：agent 必须引用 14 天退款期限，且不得编造政策例外。

这条标准比"给出有帮助的回答"更强，因为任何人都能执行它而不必猜"有帮助"算什么。它同时点名了必需的证据和失败条件。

### 3. 创建评估

创建 `evals/support/refund-quality.eval.ts`：

```
import { test } from 'bun:test';
import { setupAgent, setupJudge } from 'ori/eval';

const agent = setupAgent();
const judge = setupJudge({ minScore: 0.8 });

test('explains the refund policy accurately', async () => {
  const run = await agent.run('Can I refund a digital order that I placed 10 days ago?');

  run.tool('lookup_refund_policy').toBeCalled();
  run.toComplete();

  await judge.autoEvals({
    criteria:
      'States the 14-day refund window, answers the question directly, and does not invent exceptions.',
    run,
  });
});
```

这个测试用了两层评估。`run.tool()` 和 `run.toComplete()` 断言检查可观察的动作，`autoEvals()` 评已完成回答的含义。`minScore` 设定能通过的下限——这里的 `0.8` 只是起始值，请对照你自己的有标注回答校准，下文可靠性一节会讲。

`setupJudge()` 用自己的模型评分，与被测模型分开。想换一个模型评分，就传入你自己的 agent 给 `setupJudge()`。[Ori Eval 文档](https://openrouter.ai/docs/guides/ori/eval#give-a-score-to-an-open-answer)有写法。

### 4. 运行评估

在项目目录运行测试：

```
ori eval --report eval-report.md
```

Ori 找到当前目录下的所有 `*.eval.ts`，用 `bun test` 运行，并以 `bun test` 的退出码退出——评估失败则命令失败。`--report` 写一份 Markdown 报告，可以和其余测试输出一起查看。

LLM 评估会发真实的模型请求。把它们放在单独的 CI job 里：手动触发、按计划、或发布前跑——别塞进每次单元测试。`OPENROUTER_API_KEY` 存为 repository secret；设了这个变量，Ori 在 CI 里就不需要 `ori login`。Ori Eval 文档的 [Run an eval in CI](https://openrouter.ai/docs/guides/ori/eval#run-an-eval-in-ci) 一节有完整的 GitHub Actions 示例。

## 跨模型比较同一个 agent

逐点评估跑通后，就可以对多个候选模型运行它。做的时候保持标准和裁判固定。给 `setupAgent()` 传 `{ model }` 会为该运行选择模型，下面每一次迭代都是自己的模型对同一份标准和裁判。

```
import { test } from 'bun:test';
import { candidateModels, setupAgent, setupJudge } from 'ori/eval';

const judge = setupJudge({ minScore: 0.8 });

const candidates = await candidateModels({
  limit: 5,
  maxPromptPrice: 0.000005,
});

for (const model of candidates) {
  test(`refund policy response on ${model}`, async () => {
    const run = await setupAgent({ model }).run(
      'Can I refund a digital order that I placed 10 days ago?',
    );

    await judge.autoEvals({
      criteria:
        'States the 14-day refund window, answers the question directly, and does not invent exceptions.',
      run,
    });
  });
}
```

`candidateModels()` 从我们的实时目录返回模型 slug，每一个都能直接进测试名和 `setupAgent({ model })`。候选可按提示词或补全价格、上下文长度、必需参数、输入模态、质量指数以及模型是否即将下架来过滤。价格按 token 计，`maxPromptPrice: 0.000005` 就是每百万输入 token 五美元的封顶。

动态选择适合发现模型。回归测试请显式点名候选模型，目录变了测试比较的集合才不会变，并用 `assertModelIsLive(slug)` 让模型下架时 eval 以清晰消息失败。每条结果都要记录候选、裁判、harness、rubric、模型参数和测试数据。

## 让裁判可靠

拿人工已标注的例子检查裁判。做到这一点之前，它的分数都未被证实。本节剩下的部分讲装置变化时如何保持这份检查有效。

### 用可观察的证据写标准

把宽泛的质量标签换成裁判能在回答中定位到的要求。

- **弱。**"回答准确且有帮助。"
- **好。**"回答写明 14 天退款期限、使用了检索到的订单日期、并且不声称退款已经发放。"

需要诊断失败时把不相关的维度分开。用一个分数同时评准确性、语气、完整性和格式，只能告诉你质量掉了，不能告诉你掉在哪。

Ori 导出一个 `startingCriteria` 对象，内含 `accuracy`、`completeness`、`instructionFollowing`、`safety`、`structuredOutput` 和 `toneAndVoice` 的可编辑 rubric，把一个作为 `criteria` 传给 `judge.autoEvals()`。把它们当基础去定制。"使用检索到的订单状态、且批准前不承诺退款"比通用的准确性 rubric 告诉裁判的多。

### 用人工标注样例校准裁判

建一个小数据集：清晰的通过、清晰的失败，以及来自真实 agent 交互的边缘案例。先让负责质量的人打分，再把裁判的裁决与那些标签比对。

裁判不同意时，检查原因：可能 rubric 含糊、例子暴露了一条缺失的标准、或裁判模型本身不合适。换裁判、换 rubric 或换评估数据时，重新做这套校准。

把你的有标注问答对放进一个 JSON 文件，用 `test.each` 驱动：

```
import supportPairs from './support-pairs.json';

test.each(supportPairs)('answers: $question', async ({ question, mustMention }) => {
  const run = await agent.run(question);
  run.toMention(mustMention);
  run.toComplete();
});
```

### 让评估保持盲测

只给裁判套用 rubric 所需的信息：原始任务、可见回答、相关工具结果和必要的可信参照材料。去掉候选模型名等可能影响分数的信号。

成对评估时，把两个答案以相反位置各比一次。结论变了就再看一遍，而不是硬选一个赢家。

### 控制变更，正视方差

rubric 和测试数据集的精确版本放进版本控制。分数旁边记录候选与裁判模型 slug、harness 版本、路由配置和生成参数。

这让变更可追溯，但不会让模型输出变确定。阈值附近的小幅波动可能只是正常方差；在代表性测试集上反复出现的下跌，才是更强的回归证据。

### 保护生产数据

用户的真实数据比你编的提示词是更好的测试用例。把生产轨迹放进评估数据集之前删除个人或敏感数据，并审阅涉及模型和提供商的数据政策。我们的[数据收集文档](https://openrouter.ai/docs/guides/privacy/data-collection)讲我们的日志控制和请求元数据处理。

## 管理评估成本

LLM 评审给每次被评估的运行叠加模型请求，成本随测试用例数、候选模型数和 rubric 维度增长。

可以通过这些方式控成本：

- 每次 commit 只跑确定性检查，LLM 评估按计划或发布前跑。
- 对代表性生产轨迹抽样，而不是给每次交互打分。
- 一次聚焦的裁判调用，代替多条重叠的标准。
- 常规回归检查用更小的候选集。
- 只发裁判套用 rubric 需要的上下文。

裁判不必是能用的最大的那个模型，它需要的是稳定遵循细粒度评分指令。用我们的[模型目录](https://openrouter.ai/models)对比当前能力和价格，而不是把固定价格抄进评估代码。

## 下一步

从一次真实失败开始，写一条别的评审员也能执行的标准，拿人工标注样例测裁判。[Ori Eval 指南](https://openrouter.ai/docs/guides/ori/eval)覆盖 eval 文件格式、`candidateModels()`、`setupJudge()`、`--baseline` 对比和 CI 中跑评估。

标准封闭、需要校准概率而不是一份文字裁决时（例如某主张是否有来源支撑），决策模型可以替代裁判调用。[Jev 与 LLM 裁判对比](https://openrouter.ai/blog/tutorials/jev-vs-llm-as-a-judge/)在同一批任务上测量两者，展示各自在何处站得住。

## 常见问题

### LLM-as-a-judge 是什么意思？

用一个语言模型对照书面标准评估另一个系统的输出。候选产出答案，另一个裁判模型给它打分。

### 怎么自动给 AI agent 的输出打分？

让 agent 跑测试提示词，捕获它的回答和相关工具轨迹。把这些证据连同具体 rubric 交给裁判模型，存储分数；当分数低于你用人工评审样例校准过的阈值时，判评估失败。

### LLM 裁判评估有多准？

准确性取决于裁判模型、rubric、任务和测试数据。LLM 裁判能以有用的程度与人类偏好一致，但也表现出偏见和输出方差。在拿裁判做发布决定之前，先在你自己的人工标注样例上测量一致率。

### 同一个 LLM 能给自己的输出当裁判吗？

能，但模型可能偏袒自己的风格、重复同样的盲区。尽量用单独的裁判模型。非用同一模型不可时，把裁判请求分开、隐藏不必要的候选上下文，并用人工标签验证分数。

### 什么样的 LLM 裁判 rubric 是好的？

点名可观察的证据、定义失败条件、给裁判足够上下文以得出与内行评审相同的结论。把"要有帮助"换成"写明 14 天期限且不编造例外"这类要求。

### 该用逐点还是成对评估？

每次 agent 运行都必须达到固定质量线时用逐点。比较两个模型或提示词版本时用成对。成对测试里请颠倒答案顺序，检查位置是否影响结果。

### 什么时候不该用 LLM 当裁判？

代码能精确判定结果时别用。schema、计算、工具参数、权限和关键执行规则应当用确定性检查。裁判留给这些检查测不了的语义质量。
