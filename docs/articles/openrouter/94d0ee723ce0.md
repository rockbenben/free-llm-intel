# 如何通过 API 将图像发送至 LLM（视觉指南）

OpenRouter ·8/14/2026

想让一个有视觉能力的大语言模型（LLM）读截图、看图表，或回答照片里的问题，你得把请求体搭对。本文只讲图像输入——模型读你给它的图，不生成也不编辑。

模式很简单：发一条聊天消息，其 content 数组里含一个 text 部件和一个 `image_url` 部件，打到我们的[图像理解端点](https://openrouter.ai/docs/guides/overview/multimodal/image-understanding)。之后请求形态不再变，想换任何一个我们支持的视觉模型，只改 `model` 字段。

有的模型 OCR（光学字符识别）更强，有的读 UI 截图更稳，有的对图表推理更仔细。因为输入形态不变，你可以在不动集成的情况下测这些差异。

本文覆盖：给多模态模型发图、公共 URL 与 base64 上传怎么选、多模态 RAG 管线怎么搭，以及上生产后真正要紧的实践限制。

## 太长不看

我们通过 Chat Completions API 支持多模态图像理解。

- **端点：**`POST /api/v1/chat/completions`
- **请求体：**一个 `messages` 数组，其中用户消息的 `content` 是部件列表：一个 `{"type": "text"}` 加一个 `{"type": "image_url"}`。
- **模型：**任何支持图像输入的 slug（如 `anthropic/claude-opus-4.8`、`google/gemini-3-flash-preview`）。随意换——请求体完全相同。

## 基本请求：给聊天调用附一张图

请求就是一条用户消息，content 数组里两个部件：文本加 `image_url`。本文后面都建立在这个请求上。

### 消息的 content 数组

纯文本聊天把 `content` 作为普通字符串发送。加入图像后，`content` 变成有类型对象的数组：

```
{
  "role": "user",
  "content": [
    { "type": "text", "text": "What's in this image?" },
    { "type": "image_url", "image_url": { "url": "https://example.com/receipt.jpg" } }
  ]
}
```

顺序重要——把 text 部件放前面，我们的解析按这个来。如果你的用例真的需要先图后文，请把这种铺垫写进系统提示词，而不是试图重排 content 数组。

![一个含 text 部件和 image 部件的 content 数组，流经 OpenRouter chat completions 端点到达任何有视觉能力的模型——包括 Claude、Gemini、Qwen-VL 和 Llama Vision——并返回结构化的文本回答](https://openrouter.ai/blog/images/send-image-to-llm-flow.png)

### base64 data URL vs 托管图片 URL：各在什么时候用

`image_url.url` 字段接受两种形态：普通的公共 HTTP(S) 链接，或形如 `data:image/jpeg;base64,<encoded-bytes>` 的 base64 data URL。用哪个取决于文件现在住在哪。

图片已公开托管——CDN、带签名链接的 S3 桶、你自己的服务器——就传 URL。请求保持小，提供商自己去取字节。

图片在本地，或根本不该有公开 URL——用户上传的证件、内部文档——就编码成 base64 放进请求。请求变大、上传变慢，但文件只通过这一次 API 调用离开你的系统。

![并排对比：托管 URL——请求小、提供商拉取图片、需要公开链接；base64 data URL——字节随请求内联、上传更慢、图片永不公开](https://openrouter.ai/blog/images/send-image-to-llm-url-vs-base64.png)

base64 还有第二个优势：托管 URL 可能因访问控制、区域封锁或签名过期而失败——字节已经在请求里时，这类失败不可能发生。两种形态都支持 PNG、JPEG、WebP 和 GIF。

### 可运行的示例：cURL、Python 和 TypeScript

同一个请求，三种语言。跨模型唯一要变的行是 `MODEL`。

#### cURL（托管 URL）

```
curl https://openrouter.ai/api/v1/chat/completions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "anthropic/claude-opus-4.8",
    "messages": [
      { "role": "user", "content": [
        { "type": "text", "text": "What total is on this receipt?" },
        { "type": "image_url", "image_url": { "url": "https://example.com/receipt.jpg" } }
      ]}
    ]
  }'
```

#### Python（本地文件 → base64）

```
import base64, os, requests

def to_data_url(path: str, mime: str = "image/jpeg") -> str:
    with open(path, "rb") as f:
        b64 = base64.b64encode(f.read()).decode("utf-8")
    return f"data:{mime};base64,{b64}"

MODEL = "anthropic/claude-opus-4.8"  # swap this one string for any vision model

resp = requests.post(
    "https://openrouter.ai/api/v1/chat/completions",
    headers={"Authorization": f"Bearer {os.environ['OPENROUTER_API_KEY']}"},
    json={
        "model": MODEL,
        "messages": [{
            "role": "user",
            "content": [
                {"type": "text", "text": "What total is on this receipt?"},
                {"type": "image_url", "image_url": {"url": to_data_url("receipt.jpg")}},
            ],
        }],
    },
)
print(resp.json()["choices"][0]["message"]["content"])
```

#### TypeScript（本地文件 → base64）

```
import { readFile } from "node:fs/promises";

const MODEL = "anthropic/claude-opus-4.8"; // change only this to swap models
const bytes = await readFile("receipt.jpg");
const dataUrl = `data:image/jpeg;base64,${bytes.toString("base64")}`;

const res = await fetch("https://openrouter.ai/api/v1/chat/completions", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.OPENROUTER_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    model: MODEL,
    messages: [{
      role: "user",
      content: [
        { type: "text", text: "What total is on this receipt?" },
        { type: "image_url", image_url: { url: dataUrl } },
      ],
    }],
  }),
});
const data = await res.json();
console.log(data.choices[0].message.content);
```

## 选一个视觉模型

OpenRouter 上每个视觉模型都吃同一种请求形态。换模型改 `model` 字段，其余不动。这让你不改集成就能横向比较模型。

### 什么让一个模型具备视觉能力

不是目录里每个模型都能读图。一个模型是视觉语言模型（VLM），是因为它把文本模型和图像编码器配对，能在 token 之外吃进像素。在 OpenRouter 上你可以直接查：模型架构里 `input_modalities` 下列有 `image`，就支持图像输入。向没列它的模型发 `image_url` 部件，请求会失败。先查目录。

### 成本、上下文窗口与各自的强项

请求形态在这些模型之间相同，但模型行为不同。价格、上下文窗口、延迟，以及对 OCR、图表或一般场景理解的好坏都有差异。承诺之前，拿你的真实图片测候选模型。

| 模型 | 输入 $/M token | 上下文 | 适合 |
| --- | --- | --- | --- |
| `anthropic/claude-opus-4.8` | $5.00 | 1M | 密集文档，对图表/表格的细致推理 |
| `anthropic/claude-sonnet-5` | $2.00 | 1M | 更低成本的均衡文档理解 |
| `google/gemini-3-flash-preview` | $0.50 | 1M | 高量截图与通用问答，低延迟 |
| `google/gemini-2.5-flash` | $0.30 | 1M | 便宜的批量 OCR 与打标 |
| `qwen/qwen3-vl-235b-a22b-instruct` | 约 $0.26 | 256K | 开放权重 OCR 与多语言文本抽取 |
| `meta-llama/llama-4-scout` | 约 $0.10 | 1.3M | 开放权重的通用视觉，易自托管 |

*价格和上下文窗口随模型更替变化。本表只作示意，依赖之前请从 [/models](https://openrouter.ai/models) 拉实时数字。*

### 把目录过滤成视觉模型

查目录，别硬编码模型清单。

```
import requests

models = requests.get("https://openrouter.ai/api/v1/models").json()["data"]
vision = [m["id"] for m in models
          if "image" in m["architecture"]["input_modalities"]]
print(vision)  # models that accept image input
```

因为请求体对它们全都一模一样，你可以在发起请求时从这份列表里任选。按价格、上下文窗口或你的应用在乎的任何维度排序，而不是提前写死一个模型。

## 发送多张图和长文档

### 一个请求里的多张图

每个请求不限一张图。往 content 数组里加多少个 `image_url` 部件都行。前后对比、多页扫描、一次问多张图表就靠它：

```
{
  "role": "user",
  "content": [
    { "type": "text", "text": "Which chart shows higher Q4 revenue?" },
    { "type": "image_url", "image_url": { "url": "https://example.com/2025.png" } },
    { "type": "image_url", "image_url": { "url": "https://example.com/2026.png" } }
  ]
}
```

### 实践限制：图片数、分辨率和 token 成本

没有统一上限，限制按提供商、按模型设定。一次几张一般都没问题，几十张同发前请查具体模型的端点页。每张图都增加 token，成本随图片数和分辨率一起涨——发送整页扫描件时尤其明显。

### 什么时候该先降分辨率或预裁剪

手机拍的收据通常宽 4000 像素——没有任何模型需要这份分辨率去读底部那个总额。把图缩到文字仍然可读的最小尺寸；已经知道哪部分重要的，裁到那个区域。两步都降 token 成本。裁剪通常还提准确率，因为删掉了模型本要处理的其他视觉内容。

## 图像 tokenization 如何工作

图像被切成 patch（图块）、转成嵌入、再作为 token 处理——所以更高分辨率意味着更多 token、更高成本。过程是：一个图像编码器（通常是 Vision Transformer）把图切成固定尺寸图块的网格，每个图块转成一个嵌入向量——表征图像这一小片的向量——这些嵌入和文本 token 混在一起作为 token 传给语言模型。模型从没见过原始像素，看到的是图块嵌入。

后果很简单：像素越多、图块越多；图块越多，账单上的 token 越多。降分辨率直接减少编码器产出的图块数。一张图具体花多少 token 因提供商而异，要精确数字请查具体模型的端点页。

## 多模态 RAG：检索含图像的文档

多模态 RAG 把图像、图表和扫描页与文本一起索引，检索可以返回视觉内容，并在回答时交给视觉模型。它解决的是：多数真实文档不是纯文本。季报里最关键的那个数可能只出现在一张柱状图里。纯文本的检索管线靠 OCR，而 OCR 经常读错图甚至跳过图。索引从没捕获过这份视觉内容，检索自然永远找不到它。

### 索引策略 A：图像总结成文本，再嵌入

索引时，把每张图表、插图、扫描页发给 VLM，要一份文本总结；用你常规的文本嵌入模型嵌入这份总结，同时保留回指原图的指针。好处是检索完全基于文本，可以无缝放进你现有的向量库。代价是检索质量取决于总结——VLM 索引时漏掉的东西，之后也找不到。

### 索引策略 B：原生多模态嵌入

跳过总结，直接嵌入图像——用把图像和文本放进同一向量空间的多模态嵌入模型。文本查询于是可以直接匹配图像。你保留了更多视觉细节，但技术栈里需要多模态嵌入模型和支持其输出的向量库。文档较简单、想复用现有工具时用策略 A；图表和插图承载着总结会丢的细节时用策略 B。

![多模态 RAG 架构示意图：文档解析成文本与图像分块，用"图像总结为文本"或"原生多模态嵌入"两种路经索引，检索时把问题、最相关的文本匹配和图像匹配组装进一个视觉模型的提示词](https://openrouter.ai/blog/images/send-image-to-llm-rag.png)

### 组装提示词：把检索到的文本和图像喂给 VLM

回答这一步两种索引策略相同：取最匹配的文本与图像分块，用问题、检索文本和检索到的 `image_url` 部件构造一个 content 数组：

```
def answer(question, retrieved):
    content = [{"type": "text", "text": question}]
    for r in retrieved:
        if r["type"] == "text":
            content.append({"type": "text", "text": r["text"]})
        else:  # image chunk
            content.append({"type": "image_url",
                            "image_url": {"url": r["url"]}})
    return requests.post(
        "https://openrouter.ai/api/v1/chat/completions",
        headers={"Authorization": f"Bearer {os.environ['OPENROUTER_API_KEY']}"},
        json={"model": "anthropic/claude-opus-4.8", "messages":
              [{"role": "user", "content": content}]},
    ).json()
```

### 一个最小的端到端代码草图

整条管线：把源文档解析成文本与图像分块；每个分块用总结或多模态嵌入索引；对进来的查询检索最匹配项；组装上面展示的多模态提示词；用视觉模型作答。只有解析、索引、检索这几步是 RAG 特有的——最后的回答调用就是本文开头那个请求。输出要结构化数据而不是散文的话，加上工具调用。

## 这套做法不适合什么

- **实时视频理解。**别把每一帧都流进聊天请求。抽样几帧塞进图像数组可以，但那是权宜之计，不是视频管线。真正的视频工作需要刻意的抽帧策略、帧数的硬限制，以及这个端点本不为之设计的延迟处理。
- **低分辨率下像素级或密集小字的 OCR。**通用 VLM 会漏掉源图里非常小的字符。每个字符都必须对时，先放大或裁剪，或者干脆用专门的 OCR 管线。
- **生成或编辑图像。**本文只讲图像输入——模型读你给的图。创建新图或修改已有图是另一种请求形态，见我们的[图像生成文档](https://openrouter.ai/docs/guides/overview/multimodal/image-generation)。

## 结论

给 LLM 发图，就是用一个含 text 部件和 `image_url` 部件的 content 数组。URL 指向托管文件或携带 base64 字节，请求形态不变。改 `model` 字段，同一个请求体对所有接受图像输入的模型都能用。多模态 RAG 管线只是在回答时刻发这同一个请求——由检索先挑好该发哪张图。

三件事记住：

- **一个请求体适配所有视觉模型。**换模型时 content 数组什么都不变，变的只有一个字符串。
- **按图片住在哪选 URL 还是 base64。**公开已托管的用 URL，本地或私密的用 base64。无论哪种，发送前先缩图保住 token 成本。
- **RAG 只是在同一个调用前面加了检索。**把图表和扫描件与文本一起索引，检索到对的那些，再用开头的请求把选中的图发给模型。

到目录里浏览[支持视觉的模型](https://openrouter.ai/models)，不动集成就来回换。

## 常见问题

### 我能给 API 发图片吗？

能。在消息 content 数组里、文本旁边加一个 `image_url` 或 base64 data URL 部件，任何有视觉能力的模型都能读它。不管最后哪家提供商服务，请求的形态不变——变的只有 `model` 字段。

### 能拿图片做 RAG 吗？

能。把图表、表格和扫描页与文本并排索引：索引时把图像总结成文本，或用多模态嵌入模型直接嵌入。查询时检索相关的文本与图像分块，在同一个请求里一起发给视觉模型。

### 多模态 LLM 怎么处理图像？

图像编码器把图切成固定尺寸的图块，每个图块转成嵌入，再作为 token 与文本 token 混合传给语言模型。模型在这些嵌入上推理，从不接触原始像素。

### 多模态 LLM 怎么给图像做 tokenization？

管线是图块→嵌入→token。分辨率越高图块越多，token 越多，成本越高。发送前降分辨率是直接控制这项成本的办法。

### base64 还是 URL：用哪个？

图片已经公开托管，用 URL——请求更小。图片在本地、私密，或提供商没法可靠地从它的托管位置抓取，就编成 base64。

### 一次能发几张图？

没有统一的数字，取决于提供商和模型。一次几张通常安全，大批量之前请查该模型的端点页——每张图都在同时增加 token 数和成本。

### 所有模型都支持图像输入吗？

不是。只有 `input_modalities` 下列了 `image` 的模型接受 `image_url` 部件。查目录来确定哪些模型合格，别假设。

### 一张图花多少 token？

与分辨率成比例：像素越多、图块越多、token 越多。各提供商的计数方式不同，要精确成本估算，上量之前查该模型的端点页。

### 图像输入能和工具调用或结构化输出组合吗？

能。给视觉请求加工具调用，模型返回的就是 `{ "total": 42.10 }` 这样的类型化 JSON 而不是一句话。这是从收据、表单和扫描件里抽取结构化字段的常见模式。
