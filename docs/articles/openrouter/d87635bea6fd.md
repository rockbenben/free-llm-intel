# 基于置信度的模型升级路由阈值

OpenRouter · 2026-10-01

把每个请求都发给你最强的模型，能用最高价格换好答案——因为那些便宜模型本可以答对的请求，你也按前沿价付费。固定路由规则（比如按关键词或任务类型选模型）省钱，但随着流量变化需要不断重写。

基于置信度的升级（confidence-based escalation）介于两者之间。你让模型给自己的答案打分，然后按这个分数路由。高分答案留在便宜模型上，低分答案转给更强的模型。本指南分五步把它搭起来。

## Tl;dr

- 基于置信度的升级按模型为自家答案报告的分数来路由每个请求，于是便宜模型处理它有把握的请求，更强的模型只见它没把握的。
- 用 structured outputs 强制输出分数。一个要求数值型 confidence 字段的 JSON schema 能从每个模型给你同一形态的信号，而不必从自由文本里的含糊措辞去猜。
- 用排序，不用绝对数值。0.85 并不是经过校准的"85% 正确概率"。在你自己的流量上验证低分答案确实比高分答案更常出错，然后按这个次序路由。
- 从你自己的数据定阈值。把有代表性的流量跑过便宜模型，看每个分数段的错误率，把分界线放在错误率开始爬升的地方。
- 把阈值当作需要回头复查的设置。记录分数分布、升级率、以及未升级答案的错误率，当模型或流量变化时重新调参。

## 置信度分数是什么、不是什么

这个分数是模型的自我报告。模型产生它的方式和产生答案其余部分的方式相同，因此它带着同样的不确定性。两个相同的分数并不保证相同的正确概率。某个 prompt 上的 0.85 与另一个 prompt 或另一个模型上的 0.85 不可互换，这个数字也不是经过校准的概率。

你能用的是校验过之后的排序。把一批你自己的请求跑过便宜模型，给答案评分并按分数分组。如果低分段的答案比高分段更常出错，那么即便绝对数值不可信，这个次序仍然可用于路由。你要找的不是"等于 90% 正确率"的那个分数，而是排序中能把"可以上线的答案"与"需要第二次调用的答案"分开的那个点。第 2 步就是这个测量。

## 第 1 步：用 structured outputs 得到数值型 confidence 字段

不要从自由文本里读不确定性。没有东西规定模型没把握时必须在其行文里含糊其辞，也不存在一套固定的含糊措辞词表可供解析。

相反，用 [structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs) 让模型把 confidence 字段作为经过 schema 校验的响应的一部分返回。你传入类型为 `json_schema` 的 `response_format`，同时要求一个 answer 和一个 0 到 1 之间的数值 confidence：

```
{
  "model": "openai/gpt-5.6-luna",
  "messages": [
    {
      "role": "user",
      "content": "..."
    }
  ],
  "provider": {
    "require_parameters": true
  },
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "answer_with_confidence",
      "strict": true,
      "schema": {
        "type": "object",
        "properties": {
          "answer": {
            "type": "string"
          },
          "confidence": {
            "type": "number",
            "description": "How likely the answer is correct, from 0 (a guess) to 1 (certain)."
          }
        },
        "required": ["answer", "confidence"],
        "additionalProperties": false
      }
    }
  }
}
```

如此一来，无论哪个模型应答，每个响应都带有一个你的路由代码可以直接读取的数值 confidence。决定升级什么从"解析语言"变成了"比较数字"。

schema 把 0 到 1 的范围写在字段的 `description` 里，而不是用 `minimum` 和 `maximum` 关键字。Anthropic 的 [structured outputs 文档](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)把 `minimum`、`maximum` 这类数值约束列为不支持，因此 description 写法是跨 provider 都可行的那种。`strict: true` 会要求有原生 strict 模式的 provider 严格执行 schema。执行力度因 provider 而异，有些把 schema 当作强提示而非保证，所以在依据解析结果路由之前先验证解析出的 JSON。

在依赖这套机制前做两项检查。第一，structured output 支持是按 provider endpoint 设定的，不是按模型设定的，同一个模型可能由支持与不支持的两类 provider 提供服务。把 [models 页面](https://openrouter.ai/models?order=newest&supported_parameters=structured_outputs)筛选为至少有一个支持 endpoint 的模型，并查看模型页面 Providers 一节中的 `structured_outputs` 参数。第二，在你的 [provider 偏好](https://openrouter.ai/docs/guides/routing/provider-selection)里设置 `require_parameters: true`，这样我们只会把请求路由到支持其全部参数的 endpoint。没有这个标志时，`response_format` 只是软偏好：模型有支持的 endpoint 时我们会路由过去，但如果该模型没有任何 endpoint 支持，我们仍会发出请求，而该参数会被忽略。

## 第 2 步：从你自己的错误率出发定一个初始阈值

阈值来自对你自己流量的测量，而不是从某篇指南里抄一个数字。把有代表性的一批请求通过上面的 schema 跑过便宜模型，记录 confidence 分数以及每个答案是否正确，然后把分界线设在错误率开始爬升的位置。线之上的请求由便宜模型解决，线之下的升级到更强的模型。

先从保守的一侧起步。前期过度升级、之后再放宽阈值，花的是钱；升级不足，放出去的是自信的错误答案。

错误率在 0.70 以下急剧上升，所以 0.7 是候选分界点。阈值设为 0.7 会升级其下的两段，即 14% 的请求，其余 86% 留在便宜模型上解决。

在这个样本里，便宜模型的整体错误率略低于 10%。把最低的 14% 升级后，你保留答案的错误率降到约 4%，代价是大约每七个请求多一次调用。在自己流量上跑这套的意义是找到你自己的分界点，而不是照搬 0.7。

## 第 3 步：在准确率、成本与延迟之间调阈值

阈值是在升级量和错误率之间做交换。调高它，更多请求获得第二次调用，能抓住更多错误，但更贵也更慢。调低它，更多请求留在便宜模型上，更快更便宜，但更多错误答案会漏出去。设在哪里取决于一个错误答案对你的产品意味着什么。有三件事影响这个选择。

**准确率。** 更高的阈值会把更多边缘答案送去第二次调用，因此漏出去的错误更少。在演算示例中，把分界点从 0.7 提到 0.85，会把原本带 11% 错误率的 0.70 到 0.84 段也升级掉：升级量从 14% 升到 32%，保留答案的错误率从约 4% 降到约 2%。

**成本。** 每次升级都是在已付费的便宜调用之外多一次模型调用。这笔开销取决于便宜模型与升级目标模型之间的价差，以及你升级的频率。在确定目标升级率之前先查当前的[按模型定价](https://openrouter.ai/pricing)。档位之间的价差和价格本身都会随新模型发布而变化。

**延迟。** 被升级的请求多走一个来回，所以更慢。如果很大比例的流量被升级，这条慢路径可能顶到延迟预算。当你的产品有硬性响应时间上限时，这个上限可能先于成本或准确率限制你的升级幅度。

## 第 4 步：在你的代码里路由低置信度请求

阈值定好后，由你的代码做升级决策。它读取 confidence 字段，当分数低于线时，把请求发给更强的模型。这个第二次调用由你的代码发起，我们不会代劳。我们的 [model fallbacks](https://openrouter.ai/docs/guides/routing/model-fallbacks) 在模型返回错误时触发，而不是在它返回一个置信度偏低的合法答案时触发。有两种组织这个决策的方式。

**在同一函数内重试。** 把调用包进一个函数。先发给便宜模型、读取 confidence，若低于阈值，就把同样的 messages 发给更强的模型并返回那个答案。升级策略集中在一处：改阈值或改升级目标时只需改一次，不会有任何调用点还留在旧决策上。

**跑一个独立的第一遍。** 把便宜模型调用视为第一遍：记录它的答案和分数，只有当分数落到线下时才调用更强的模型。这样代码多一些，但它记录了便宜模型升级的频率、以及它的分数是否仍与真实错误对得上——这正是第 5 步中你重新调参所用的数据。

模型 ID 就是字符串，所以两个档位都可以通过配置而非代码来更换。挑选便宜档和强档模型时请浏览[我们的模型目录](https://openrouter.ai/models)，因为每个档位的最佳选择会随新模型发布而变化。

你还可以在以上任一模式之下叠加错误故障转移。传入 `models` 数组后，当第一个模型返回错误时，调用会自动故障转移到列表中的下一个模型。默认情况下任何错误都可能触发 fallback，包括 provider 宕机、限流、被过滤模型上的内容审核标记，以及上下文长度校验错误。我们按最终应答的模型计费，并在响应的 `model` 字段返回该模型。这与你的置信度升级是两套独立机制：它因错误触发，不因低置信度的合法答案触发，因此两者可以共存——fallback 保证每次调用活着，你的阈值决定一个活着的答案何时需要更强的模型。

## 第 5 步：在生产中监控并重新调参

上线时合适的阈值可能日后就不再合适。从第一天起记录三样东西。

- 分数分布，以便在模型或流量变化时重跑第 2 步的校准。
- 随时间变化的升级率。
- 未升级答案的错误率——这个数字告诉你分界点是否仍称职。

有东西变了就重新调参。把便宜模型或升级目标换成新版本，会改变分数分布；流量朝更难或更简单的请求偏移，会移动你的错误带。成本压力可能促使你用更高的错误率换更低的升级率。阈值是一个随这些因素变化而持续调整的设置。

## 常见错误

**把自我报告的分数当作经过校准的概率。** 这个方法建立在排序上，不建立在字面可能性上。按分数给一批答案排序，错误答案会向低端聚集，但 0.9 并不意味着该答案 90% 的情况下正确。请按第 2 步的"按分数段看错误率"来设阈值，而不是照搬原始数字。

**对所有任务类型用同一个阈值。** 回答"你们的退款政策是什么"的客服机器人和回答"我今天取消会不会被扣费"的客服机器人，一个错误答案的代价并不相同。单一全局阈值要么对简单情形过度升级，要么对高风险情形升级不足。凡是你了解任务类型的地方，给每种类型自己的阈值。

**上线后不监控升级率。** 适合你校准批次的阈值，可能随流量迁移或底层模型更换而失效，而且不会有任何报错来提醒你。

## 结论

基于置信度的升级让请求在模型报告高置信度时留在便宜模型上，只在它不自信时才为更强的模型付费，无需关键词或任务类型规则。闭环很小：用 structured outputs 强制一个数值 confidence 字段；按分数段从你自己的错误率找分界点，而不是拍一个数字；选择适合你追踪方式的路线模式——策略集中在一个函数里，或第一遍单独留日志。然后上线后盯住未升级答案的错误率，随模型与流量变化做调整。

## 常见问题

### 什么是置信度阈值？

置信度阈值是你据以决定是否把请求转给更强模型的分数线：低于它就放弃便宜模型的答案。线之上，答案原样上线；线之下，请求升级。这条线由你自己的错误率数据定，不是默认值。

### AI 里的置信度分数是什么？

置信度分数是模型通常在 0 到 1 之间随答案一同报告的一个数字，用来表示它有多确定。它是自我报告，不是经过校准的概率，所以 0.9 并不意味着 90% 的正确可能。你能测量并依赖的是次序：在一批你自己的请求上，先确认低分答案确实比高分答案更常出错，然后再依据分数路由。

### 设置置信度阈值最可靠的方法是什么，让轻量模型处理大部分请求、只在置信度低时请教高级模型？

在你自己的流量上测量。把有代表性的一批请求跑过轻量模型，记录每个置信度分数和答案是否正确，按分数段分组。在错误率急剧上升处设阈值。这样轻量模型处理线上的一切请求，只有线下低置信度的请求才交给高级模型。先保守起步，再一边盯着保留答案的错误率一边调整。

### 如何自动从小模型升级到前沿模型？

让小模型用 structured outputs 返回数值 confidence 字段，然后让你的代码据此路由。分数低于你的阈值时，把同一请求发给前沿模型——可以在同一函数内联完成，也可以显式做第二次调用。OpenRouter 的 model fallbacks 是另一项功能：它们在 provider 宕机或限流等错误发生时把调用转给另一个模型，而不是在置信度分数低时转，所以两套机制要分开。
