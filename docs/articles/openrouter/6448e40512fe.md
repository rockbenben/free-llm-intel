# Jev 是什么？为开发人员解释 TypeSafe 的决策模型

Kenny Rogers ·9/21/2026 · 更新于 9/24/2026

Jev 是什么？你该拿它干什么？它是 [TypeSafe](https://typesafe.ai) 的决策模型：接收一段文本加一个有类型的问题，返回一个有类型的答案，答案从你预定义的选项中产生。比如我有个工单路由问题——这张工单该去 billing、technical 还是 account——Jev 看工单文本，然后从预定义选项中给出一个回答：`billing`。但它比这更酷，因为它除了给出答案选项的校准概率，还给出其他每个选项的概率。哦对了，还有一个总体置信度分数（后面细说）。TypeSafe 把这类模型叫 System One 模型，Jev 是其中的第一个。

但 Jev 实际返回什么？来看！它返回三种原语，下面每种都附有真实的 API 响应。这里教你怎么读概率而不骗自己，以及怎么带着 OpenRouter API key 调用 Jev。

## 什么是决策模型（System One 模型）？

Jev 是一个决策模型。System One 模型接收一份状态（state），并根据这份状态返回一个决策。在 Jev 这里，决策永远是你预先定义的有类型值，外加一个 0 到 1 之间的实际概率数。名字来自 Daniel Kahneman 在《思考，快与慢》里提出的 System One：快速的模式匹配式思维；System Two 则是慢速、刻意思考的。

那什么让它成为决策模型而不是某个神谕？决策模型必须从一个你事先定好的小型值集合中返回结果。没有自由文本，所以没有任何东西需要解析，也不用担心幻觉。

TypeSafe 对 Jev 做了校准：当它说 0.8（80% 的概率）时，意思就是字面意思——像降水概率 80% 那样，这类回答 Jev 大约 80% 的时候是对的（[System One 概念](https://docs.typesafe.ai/concepts/system-one)）。

这只在跨大量答案取平均时成立，单个答案照样可能错。这有实际影响，后文会回到这一点。

## Jev vs LLM：各自返回什么

理解了两者各做什么，Jev 和 LLM 的区别就清楚了。两者都能读自然语言，分野完全在输出侧。

并排对比是这样：

|  | 生成式 LLM | Jev |
| --- | --- | --- |
| 输出 | token：散文、代码、你要的 JSON | 一个有类型的答案 + 一个概率分布 |
| 结构有保证吗？ | 只有配合结构化输出才有，内容仍可能错 | 永远是你的选项之一、一个分值，或是/否概率 |
| 不确定性 | 藏在文字里 | 以数字返回，可以直接做阈值判断 |
| 输入 | 文本，通常还有图像、音频或视频 | 仅文本（字符串、JSON 对象、文本数组） |
| OpenRouter 价格 | 因模型而异，输入输出都计费 | 每百万输入 token $0.042，输出免费 |

需要文字作为主要输出时——回复、摘要、代码补丁——用 LLM。需要做一个可被代码执行的决策时，用 Jev。几乎每个真实场景里两套系统是配合的：Jev 路由和校验，LLM 提供语言。配套文章 [Jev vs LLM：何时使用哪一个](https://openrouter.ai/blog/tutorials/jev-vs-llm-when-to-use-each/) 讲的就是这个分工，在 140 个客服案例上做了基准，并用 TypeScript 把两者接在一起。

## Jev 的三种原语：Choice、Score 和 Noul

你问 Jev 的每个问题都属于三种类型之一。一次请求由两部分组成：`state`（待评估的文本）和一个 `questions` 对象，里面是一个或多个有类型的问题。Jev 一趟全部答完，每个答案放在你给的键名下。

下面的例子是我 2026 年 9 月 21 日实际发出的调用。它们通过 OpenRouter 的 Decisions API 打到 `typesafe/jev-1.13`，只要设好 `OPENROUTER_API_KEY`，示例可以照原样跑。

### Choice：从固定集合中选一项

从 API 拿到一个 Choice 时，它永远带三样东西：选中的选项、每个选项的概率，和一个 confidence 值。

这条命令发出请求：

```
curl https://openrouter.ai/api/alpha/decisions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "typesafe/jev-1.13",
    "state": "My invoice for September shows two charges for the Pro plan. I only have one workspace.",
    "questions": {
      "team": {
        "type": "choice",
        "instructions": "Which team should handle this ticket?",
        "criteria": {
          "billing": "Charges, invoices, and refunds",
          "technical": "Bugs, outages, and broken features",
          "account": "Login, password, and profile changes"
        }
      }
    }
  }'
```

这个响应展示了 API 返回的内容：

```
{
  "model": "typesafe/jev-1.13-20260917",
  "answers": {
    "team": {
      "type": "choice",
      "choice": "billing",
      "probabilities": { "technical": 0, "account": 0, "billing": 1 },
      "confidence": 1
    }
  },
  "usage": { "input_tokens": 357, "output_tokens": 38, "cost": 0.000014994 },
  "id": "gen-dec-1790013975-0Cpw7ykY8YRfP85l4eqS",
  "provider": "TypeSafe"
}
```

Jev 在做选择之前会读 `criteria` 里的描述，所以请像给新同事做入职简报那样写它们。TypeSafe 的 [API 参考](https://docs.typesafe.ai/api)说明问题 id（这里是 `team`）永远不会发给模型，所有含义都得靠描述承载。另外，`model` 字段标明了 OpenRouter 实际服务的快照版本。

### Score：在你描述的有序档位上打分

Score 接收一个有序数组的档位描述。它返回一个代表文本打分的数字，外加一份 `legend`（把数组每个索引映射到其描述）、Jev 对每个档位的概率和一个 confidence 值。

```
curl https://openrouter.ai/api/alpha/decisions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "typesafe/jev-1.13",
    "state": "Export to CSV fails with a 500 error for every workspace in our org since this morning. We can still download JSON exports, but our finance team can only import CSV.",
    "questions": {
      "severity": {
        "type": "score",
        "instructions": "How severe is this bug report?",
        "criteria": [
          "Cosmetic; no impact to functionality",
          "Broken or degraded feature, but a workaround exists",
          "Blocking issue; no workaround exists"
        ]
      }
    }
  }'
```

```
{
  "model": "typesafe/jev-1.13-20260917",
  "answers": {
    "severity": {
      "type": "score",
      "score": 1.15,
      "legend": {
        "0": "Cosmetic; no impact to functionality",
        "1": "Broken or degraded feature, but a workaround exists",
        "2": "Blocking issue; no workaround exists"
      },
      "probabilities": { "0": 0, "1": 0.85, "2": 0.15 },
      "confidence": 0.77
    }
  },
  "usage": { "input_tokens": 354, "output_tokens": 17, "cost": 0.000014868 },
  "id": "gen-dec-1790013976-PwmCQLkieCXkoK3qb8Ja",
  "provider": "TypeSafe"
}
```

分数 1.15 是档位的概率加权平均：0.85 乘 1 加 0.15 乘 2，上面响应里都有体现。你自己跑会落在几分之差内，因为 Jev 的概率在调用之间会小幅浮动。Jev 把"我们还能下载 JSON 导出"读成了 workaround，所以主要落在档位 1；同时因为财务用不了这个 workaround，它也给"blocking"分了一些权重。

因为分数在序数尺度上，档位必须按从小到大真实排序，每个档位都要用文字描述。TypeSafe 文档列了 [Score 原语](https://docs.typesafe.ai/primitives/score)的细节，包括最多 10 档的上限。

### Noul：一个是/否命题成立的概率

Noul 是三种原语里最简单的一种。输入一个命题，返回答案为"是"的概率。

下面这条命令发出请求：

```
curl https://openrouter.ai/api/alpha/decisions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "typesafe/jev-1.13",
    "state": "I was charged twice for September. Please refund the duplicate charge.",
    "questions": {
      "refund": {
        "type": "noul",
        "instructions": "Is the customer asking for money back?"
      }
    }
  }'
```

这是 API 返回的响应：

```
{
  "model": "typesafe/jev-1.13-20260917",
  "answers": {
    "refund": { "type": "noul", "noul": 0.99 }
  },
  "usage": { "input_tokens": 287, "output_tokens": 20, "cost": 0.000012054 },
  "id": "gen-dec-1790013977-LxrJdV3aOEliWmRmdmh9",
  "provider": "TypeSafe"
}
```

注意 Noul 答案没有单独的 `confidence` 字段，概率本身就是全部答案。下一节解释怎么解读它。

### 一次调用问全三种

你也许在问：那个 `questions` 对象能塞多少问题？想塞多少塞多少。`state` 也不必是纯字符串：它可以是一个 JSON 对象，带着这带来的一切灵活性。你的 instructions 可以用反引号按字段名引用它。

假设你想对同一张工单一次性问出一个 Choice、一个 Score 和一个 Noul，一个来回搞定。

发出这个请求的命令如下。

```
curl https://openrouter.ai/api/alpha/decisions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "typesafe/jev-1.13",
    "state": {
      "ticket": "Hi, I was charged twice for my Pro subscription this month. Please fix this before my next payroll run on Friday."
    },
    "questions": {
      "team": {
        "type": "choice",
        "instructions": "Which team should handle `ticket`?",
        "criteria": {
          "billing": "Charges, invoices, and refunds",
          "technical": "Bugs, outages, and broken features",
          "account": "Login, password, and profile changes"
        }
      },
      "urgency": {
        "type": "score",
        "instructions": "How urgent is `ticket`?",
        "criteria": [
          "No deadline; routine question",
          "Customer wants a fix soon but nothing is blocked",
          "Customer names a deadline or something is blocked now"
        ]
      },
      "refund": {
        "type": "noul",
        "instructions": "Is the customer in `ticket` asking for money back?"
      }

```

下面展示的响应就是 API 返回的那个。

  "answers": {
    "team": {

## 怎么读 Jev 的概率和置信度

读 Jev 的概率和 confidence 时，有三条准则要记住。

**Noul 接近 0.5 时，那是 Jev 在说"我也不知道该怎么想"。**把它读成一种不确定状态。做个小实验演示一下。我对这段 state——"我这个月卡上出现了两笔扣款。如果其中一笔是弄错了，我有什么选择？"——问了同一个退款问题"客户是不是在要回钱？"，两次独立调用。一次返回 Noul `0.52`，同一条消息原样（真的逐字相同）再问，Jev 返回了 `0.49`。如果你忍不住想说"嗨，客户就是要退钱呗"，请想想客户在消息里从头到尾没有一次开口要过钱。他们在边上打转，Jev 感受到了两个方向的拉扯，换作你我也同样确定不了。而之前那次显式退款请求的 Noul 打到了 `0.99`。看出模式了吗？结果落在中间时，把它当作第三种结果——一个你可以据此行动的结果。追问一个问题，或者把工单转给真人。

**Choice 和 Score 的 confidence 衡量的是分布有多集中。**分布的重量越集中到一个结果上，confidence 越高。集中在单一选项的 choice 会给出高 confidence 数字（0 到 1 的量表）。confidence 越高，说明选项之间越少犹豫。但 Jev 把注意力集中到一个选项上，并不等于答案是对的。TypeSafe 的 confidence 数字取自其 `probabilities` 的形状，而不是实际正确率（[confidence 文档](https://docs.typesafe.ai/confidence)）。极端情况下，把所有重量都给一个结果的模型 confidence 为 1.0，集中度越低这个数越小。

用那张 billing 例子就能验证。这段 `state` 更含糊："我昨天升级到了 Pro，但控制台还显示 Free，而且我被扣了费。到底是哪个？"下面的响应就是 API 实际返回的：

```
{
  "type": "choice",
  "choice": "billing",
  "probabilities": { "account": 0.02, "technical": 0.19, "billing": 0.79 },
  "confidence": 0.69
}
```

Jev 仍然选 `billing`，但近两成重量压在 `technical` 上，confidence 掉到了 0.69。confidence 衡量的是 Jev 在选项之间有多纠结——但这些选项选得好不好，是你的事。

**用你自己的标注数据定你自己的阈值。**运维建议很简单。校准只在总体上成立，这意味着适合你的分界线取决于你的错误有多贵。TypeSafe 的 [confidence 指南](https://docs.typesafe.ai/confidence)建议分三段：confidence 高于一条阈值就自动执行；中间地带谨慎推进——标记出来加一层用户确认，或干脆标记待审；低于另一条阈值就转给人或另一个系统。

这些段怎么定？标注几百个例子。对每个例子，看 Jev 的概率落在哪。然后挑出能让"自动执行段"内错误率在你可接受范围的阈值。

## Jev 留给你代码做的事

有几件事 Jev 不做，尽管你可能期待一个模型会做。这些事留在你自己的代码或一个 LLM 那里：

- **文本生成。**每个 Jev 响应都是前面展示的三种有类型形态之一，绝不是补全、不是 JSON 正文、不是解释。流水线需要一句话时，让 LLM 产出它、Jev 检查它。[verified cascade cookbook](https://openrouter.ai/docs/cookbook/evaluate-and-optimize/jev-verified-cascade) 演示了这个模式。
- **可见的推理。**Jev 只返回你的选项上的分布，别的什么都没有。没有理由说明，没有思维链。把分布当作要记录和做阈值判断的信号即可。要审计轨迹的话，记录请求 ID、问题名、概率和你的代码应用的阈值。别把 `state` 本身放进日志——工单和文档里有客户数据。
- **工具调用、对话或多步计划。**Jev 一个来回内回答你关于你发来的 state 的问题。它不做工具调用、不持有对话、不走步骤。它在 agent 内部担任"做决定"的部分，比如[为工具调用把关](https://openrouter.ai/docs/cookbook/building-agents/gate-tool-calls-with-jev)。

三条说完了！还有两条约束要记住：

- Jev 只接受文本：字符串、JSON 对象或文本数组。没有图像、音频或视频。
- 精确算术、日期运算、阈值比较不是 Jev 的活。先算好，再把语义部分交给 Jev。

## 什么时候用 Jev 模型

现在你知道 Jev 做什么了，说说什么时候该用：当你的 LLM 本该给出的答案能装进一个 enum、一个布尔或一个数字的时候。

**该用 Jev 的时候**

- **路由与分诊：**定队列、定负责人、定优先级。每张工单一个 Choice 加一个 Score。
- **规模化分类与打标：**便宜到（见下文价格）可以每行都跑；输出天生就是标签。
- **为 agent 行动把关：**破坏性工具执行前，用一个 Noul 问"用户的请求是否授权删除这些文件"，低于你的阈值就拦截。
- **校验 LLM 输出：**用 LLM 起草，然后问 Jev 该草稿是否扎根于你提供的政策文本。
- **排序与过滤：**把候选对描述好的档位打分，然后排序。

**不该用 Jev 的时候**

当答案必须是文字、输入是图像、或逻辑是确定性的时候。精确规则？一个正则或数据库查询胜过任何模型。想在写码之前先玩玩它，[Jev Lab](https://openrouter.ai/labs/jev) 在浏览器里用实时调用跑其中的几种模式。

## 如何在 OpenRouter 上访问 Jev

你需要一个 [OpenRouter API key](https://openrouter.ai/settings/keys)和一个模型 ID：`typesafe/jev-1.13`（钉版本）或 `~typesafe/jev-latest`（跟随最新版本的别名）。同一个调用可以用三种方式发出：OpenRouter SDK、TypeSafe SDK，或裸 HTTP。

### 用 OpenRouter SDK 调 Decisions API

下面的代码与置信度一节里那张更含糊工单的调用相同：通过 OpenRouter TypeScript SDK 的 `alpha.decisions` 发 `POST https://openrouter.ai/api/alpha/decisions`。代码在 SDK 1.3.11 上测过，用 `npm install @openrouter/sdk` 安装。因为用了顶层 `await`，请用 `bun run` 或作为 ES 模块运行。开跑：

```
import { OpenRouter } from '@openrouter/sdk';

const openrouter = new OpenRouter({ apiKey: process.env.OPENROUTER_API_KEY });

const decision = await openrouter.alpha.decisions.create({
  decisionsRequest: {
    model: 'typesafe/jev-1.13',
    state: 'I upgraded to Pro yesterday but the dashboard still says Free and I got charged. Which one is it?',
    questions: {
      team: {
        type: 'choice',
        instructions: 'Which team should handle this ticket?',
        criteria: {
          billing: 'Charges, invoices, and refunds',
          technical: 'Bugs, outages, and broken features',
          account: 'Login, password, and profile changes',
        },
      },
    },
  },
});

const team = decision.answers.team;
if (team.type === 'choice') {
  console.log(team.choice, team.probabilities, team.confidence);
}
```

```
billing { account: 0.01, technical: 0.15, billing: 0.84 } 0.77
```

注意这里的数字与之前对同一工单的运行（0.79 和 0.69）不同。Jev 的概率在调用之间会有波动，所以阈值最好定在"段"上而不是精确值上。最后注意 OpenRouter SDK 返回的是小驼峰的 `decision.usage.inputTokens` 和 `decision.usage.outputTokens`，不是裸 API 的 `input_tokens` 和 `output_tokens`。

### 指向 OpenRouter 的 TypeSafe JavaScript SDK

第二条调用路径是 TypeSafe SDK：把 SDK 的 base URL 指向 OpenRouter，用你的 OpenRouter API key 当它的 API key。SDK 会在 base URL 后接 `/v1/systemone`。像 `jev-1.13` 这样的裸模型名会映射到 `typesafe/jev-1.13`。下面是同一个 Jev 调用，用 `@typesafe-ai/sdk`；代码在 SDK 0.6.0 上测过：

```
import { TypeSafeClient } from '@typesafe-ai/sdk';

const client = new TypeSafeClient({
  apiKey: process.env.OPENROUTER_API_KEY,
  baseURL: 'https://openrouter.ai/api',
});

const result = await client.systemOne({
  model: 'jev-1.13',
  state: 'Export to CSV fails with a 500 error for every workspace in our org since this morning. We can still download JSON exports, but our finance team can only import CSV.',
  questions: {
    severity: {
      type: 'score',
      instructions: 'How severe is this bug report?',
      criteria: [
        'Cosmetic; no impact to functionality',
        'Broken or degraded feature, but a workaround exists',
        'Blocking issue; no workaround exists',
      ],
    },
  },
});

console.log(result.answers.severity);
```

```
{
  type: "score",
  score: 1.19,
  legend: {
    "0": "Cosmetic; no impact to functionality",
    "1": "Broken or degraded feature, but a workaround exists",
    "2": "Blocking issue; no workaround exists",
  },
  probabilities: {
    "0": 0,
    "1": 0.81,
    "2": 0.19,
  },
  confidence: 0.72,
}
```

## 常见问题

### Jev 是什么？

Jev 是 TypeSafe 出品的决策模型。你和多数模型的交互方式是发文本。Jev 不只是这样：你发文本加一个或多个有类型的问题，拿回来的是带校准概率的有类型答案。没有文本生成。TypeSafe 把这类模型叫 System One 模型。

### 谁做的 Jev？

Jev 是一个决策模型，由 TypeSafe 构建——这家 AI 实验室由 Diogo Almeida、Erik Gafni 和 Sasha Sheng 创立。Jev 于 2026 年 9 月 15 日早期访问发布，当前版本是 Jev 1.13。你可以通过 TypeSafe 自家 API 或 OpenRouter 拿到它。

### Jev 是 LLM 吗？

不是。Jev 是非生成式的决策模型，LLM 是生成式模型：Jev 像 LLM 一样读你的自然语言，但之后不生成任何文本、任何 token。根据问题不同，Jev 返回三种答案形态之一：一组预定选项中的一个选择、一组定义档位上的一个分数，或是/否的概率。因为没有生成文本，就没有东西需要解析，也没有输出幻觉的可能。

### Jev 用来干什么？

好，你要决定哪张客服工单路由给哪个团队；你要把这篇博客归入某个内容类型；你想基于置信度阈值给 AI agent 的工具调用把关；你要把一组候选排个序；你要拿政策文本校验一份草稿。眼熟吗？这些场景里，以前的做法是问 LLM 一个问题，再用正则抠出一个布尔值或枚举值。认识一下 Jev——为这类决策专门打造的模型，替代"LLM 加正则"的工作流。

### 我怎么访问 Jev？

想通过 OpenRouter 用 Jev？你只需要一个 OpenRouter API key，向 [https://openrouter.ai/api/alpha/decisions](https://openrouter.ai/api/alpha/decisions) 发一个 POST，model 填 typesafe/jev-1.13。也可以用 OpenRouter SDK 里的 decisions 客户端，甚至直接用 TypeSafe 的 JavaScript 和 Python SDK——把 base URL 设成 [https://openrouter.ai/api](https://openrouter.ai/api)、传入你的 OpenRouter key 即可。

### Jev 多少钱？

截至 2026 年 9 月 21 日，Jev 1.13 在 OpenRouter 上是每百万输入 token $0.042（输出完全免费）。也就是一次典型的短工单三问题调用大约 450 个输入 token，花你约千分之两美分。所以老规矩：查模型页面看当前价格。

### Jev 是开源的吗？

不是。Jev 是专有模型，没有公开权重，也没有论文。不过你可以通过 TypeSafe API 或 OpenRouter 调用它。
