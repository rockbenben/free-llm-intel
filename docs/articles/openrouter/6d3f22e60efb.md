# 隐式缓存算不算提示词保留？

Chris Clark ·10/23/2025 · 更新于 6/24/2026

OpenRouter 监控来自每个提供商的每一个端点，掌握它们当前的数据保留政策。我们把结果发布在 API 和文档里，并在 API 中支持 [ZDR](https://openrouter.ai/blog/insights/is-implicit-caching-prompt-retention/(https:/openrouter.ai/docs/features/zdr))（零数据保留）路由规则。但数据保留不是非黑即白的：具体说，Google 持[立场](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/vertex-ai-zero-data-retention)认为，带隐式提示词缓存的模型实际上就是在"保留"数据。大多数提供商并不同意——所以我们决定形成自己的独立判断。

## 什么是隐式缓存？

缓存之所以重要，首要原因是它能省下一大笔钱。LLM 生成的每个 token 都依赖它之前的所有内容，从零重算这些依赖是极大的浪费。通过把代表模型中间激活的键和值张量（即所谓 "KV cache"，KV 缓存）存进某种存储机制，提供商可以跳过提示词的 prefill（预填充），用少得多的算力继续对话。隐式缓存的意思仅仅是：这个缓存是自动维护的，在幕后发生，用户没有显式控制权。

显式缓存做的是同一件事，但用户通过控制头指定提示词中哪些部分要提供商缓存。数据被存储以供复用，这件事是明示的。因此显式缓存从不被视为数据保留。问题在于*隐式*缓存——这种在推理系统内部自动发生的行为——在 Zero Data Retention（ZDR，零数据保留）标准下是否应当被当作保留。

## 存储的三个层级

服务大模型（大致）会用到三个层级的存储和内存：

- **设备内存（HBM / GPU VRAM）：** 活跃推理就发生在这里。键和值在实时生成 token 期间住在这里。这一层没有争议：KV 权重显然必须载入 GPU 才能产出。
- **主机内存（CPU DRAM）：** GPU 显存装满或发生上下文切换时，KV 缓存可能溢出到主机 DRAM。事实上，很多推理配置正在*逐 token 之间*频繁地把 KV 缓存换入换出设备内存，让每个推理消费者都能拿到连续不断的 token 流，而不被某个长生成阻塞。这同样是易失内存，没人会把它算作提示词数据的"保留"。
- **NVMe / SSD 换页：** 大多数商用推理部署会把缓存再延伸一步，通过 NVMe 把 KV 张量换页到高速 SSD 存储上。这让模型能支撑比 GPU 加 DRAM 总容量更多的并发会话。真正意义上的"提示词缓存"主要发生在这一层，争议也在这里。

## 盒子里到底装的是什么???

理想情况下，被换页到外接 SSD 上的应该只有 KV 张量（把提示词预填充进 LLM 后得到的浮点矩阵）。传入提示词的一个单向哈希键会和张量一起存放，这样新提示词进来时可以查一下能否从 SSD 加载预先算好的 KV 缓存。原始提示词的 token ID 或文本片段不应该和张量存在一起。

我们已经和托管专有模型的超大规模云厂商核实过，确实没有任何 token 或文本被换页到 SSD。我们也专门和 Groq、Cerebras 验证过这一点（它们其实提供隐式缓存，但一切存在 DRAM 里，根本不用 SSD！）。我们尚未发现任何把文本或 token 换页到 SSD 的提供商，但对所有提供商的这项核查会持续进行。

最后值得指出：实现这套 SSD 架构的*提供商数量*，远多于公开提供缓存价格/隐式缓存的数量。缓存 KV 张量能让推理更高效，提供商有动力去实现它，又没有义务把节省让给客户、或公开为缓存提示词提供更低价。这正是为什么我们持续深挖各提供商的部署、在底层验证它到底怎么运作，而不只盯着那些公开宣称隐式缓存的提供商。

## 保留问题

那么，隐式缓存算*数据保留*吗？我们不这么认为。缓存在技术上确实短暂保存了派生数据，但只是为了性能的连续性，而且保存的形式既不可恢复，作为用户数据也没有意义。KV 张量是转瞬即逝的，与原始 token 不对齐，在多数架构里会话终止或缓存被逐出时就清掉了。另外，这些 SSD 物理上就摆在 GPU 机架旁边，并不是存在提供商云里的日志存储或其他什么系统中"保留"下来。

KV 张量历来被视为很难甚至不可能逆向还原成 token/明文：它们是依赖模型的表示，前向传播一旦完成就失去与离散词表信息的对齐。即使直接拿到这些张量，恢复原始提示词也很可能很难。话虽如此，这个假设有[近期研究提出了挑战](https://www.usenix.org/system/files/usenixsecurity25-dong-tian.pdf)，KV 缓存数据确实值得保护——但我们不认为通过本地部署的 SSD 做短暂存储，会比同样的值放在 CPU DRAM 里实质性地增大攻击面。

那么一个足够有动机的攻击者（比如拥有完全物理访问、时间无限的国家级对手）能否从换页出去的缓存里恢复信息？也许能，但对任何瞬态计算内存来说都是如此。而且和易失内存里的张量不同，SSD 上的数据通常是加密的。实际而言，这些信息在任何运营或可提取的意义上都没有被保留。

## 提供商差异与解读

我们认为，Google 关于 Gemini 的隐式缓存使其不符合 ZDR 的立场过于保守，也不是客户在评估 ZDR 立场时真正在问的东西。

OpenRouter 采取务实的看法。基于我们对隐式缓存实际运作方式的理解，以及和提供商的沟通，我们认为瞬态 KV 缓存*不构成*数据保留。因此，在我们的平台上，有隐式缓存但没有其他形式持久存储的端点符合 ZDR 标准。

不过，透明度仍然重要。我们[精确记录](https://openrouter.ai/docs/features/zdr#zero-retention-endpoints)了哪些端点支持隐式缓存，在意这种存储形式的客户可以避开这些端点。如果你不同意我们的解读，直接配置你的路由规则即可。

## 结论

隐式缓存是性能优化机制，不是数据保留机制。这个区分很重要：ZDR 要保护的是用户数据免于持久化，而不是免于那些在推理过程之外转瞬即逝、无法被检视的内存内张量。我们认为，当客户表达对 ZDR 的偏好时，他们的意思并不是"把缓存关掉"。

但最重要的是，OpenRouter 会持续与提供商合作，确保其最敏感的数据得到妥善保护，并投入精力去理解、记录这些信息，让它对客户真正可操作。
