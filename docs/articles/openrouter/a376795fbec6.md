# RAG 中的 reranking：如何用 reranker 修复错误检索

OpenRouter ·11/13/2026

![RAG 中的 reranking：如何用 reranker 修复错误检索](https://openrouter.ai/blog/images/reranking-rag.png)![RAG 中的 reranking：如何用 reranker 修复错误检索](https://openrouter.ai/blog/images/reranking-rag-dark.png)

当 RAG（Retrieval-Augmented Generation）应用给出错误答案、而正确信息明明就在文档里时，问题往往出在检索。向量搜索很擅长找到主题对路的块，却常被「差一点就对」的结果骗到：用户问的是 Growth 套餐，它却把 Enterprise 套餐的 bucket 上限捞了回来。RAG 中的 reranking 就是来解决这个的——取向量搜索的前 30 个候选，交给专用的[交叉编码器模型](https://openrouter.ai/docs/api/api-reference/rerank/submit-a-rerank-request)，让它针对问题直接给每个块重新打分。

在 274 个问题的基准测试里，标准向量搜索用 google/gemini-embedding-2，有 **81%** 的情况下把完全正确的块排在第一位。加上 voyageai/rerank-3-lite 对前 30 个结果做 rerank，这个比例升到 **97%**，每 1,000 次查询大约花 $0.10。别忘了这是在一个小型合成数据集上测的，真实收益取决于你的文档，不过下面的流程能帮你测出自己的基线。

```
TL;DR
Retrieve about 30 candidates, rerank them, and send the top 3 to the LLM.
voyageai/rerank-3-lite and voyageai/rerank-3 were the most accurate dedicated rerank models and the cheapest of all 11 rerankers, at $0.10 and $0.26 per 1,000 queries.
An LLM reranker (openai/gpt-6-luna) put the right chunk first for 99.6% of questions, but each call took 4.0 seconds against 1.3 for a rerank model.
The cheap voyageai/voyage-4-lite plus voyageai/rerank-3-lite reached 96.7% precision@1, against 81.0% for the more expensive google/gemini-embedding-2 alone.
Set input_type on embedding calls. Leaving it out costs 7 to 12 points of precision@1.
cohere/rerank-v3.5 reads only the first 4,096 tokens (4K) of a document and gives no error.
```

## RAG 为什么会检索到错误的块？

标准向量搜索吃力，是因为 embedding 模型在看到用户问题之前，就把整段块压成了一个向量。如果一段 130 词的块在讲 bucket 上限，具体套餐名只占整段里的一两个词。结果，Starter、Growth、Scale、Enterprise 几个套餐的向量在向量空间里几乎叠在一起，检索器很容易把错误的套餐排到最前。

为了不靠主观打分来测检索准确率，我们给一个虚构的存储服务 Fernbank 造了一套受控数据集。语料有 274 个块，涵盖文档、错误码、SDK 指南、changelog 条目和噪声，其中还包括特意用来诱捕朴素关键词匹配和向量匹配的未答复论坛帖、支持工单。每个块都用 anthropic/claude-sonnet-5.5 从一组固定事实生成，再用脚本核对过。问题由另一个模型 openai/gpt-6.1-sol 编写。因为每个问题都对应唯一一个正确的块，我们打分时不需要人为判断。

在完整测试集里，有一个问题是「在 Growth 套餐下，一个 Fernbank 账户最多能创建多少个 bucket？」。google/gemini-embedding-2 把 Starter、Enterprise、Scale 三个套餐的块排在第 1、2、3 位，一个未答复的论坛帖排第 4，真正的 Growth 套餐答案排在第 5。如果你的 RAG 管道只把前三个候选送给 LLM，模型连正确的文档都看不到。

reranker 用交叉编码器架构解决这个问题。它不是孤立地评估文档，而是把用户问题和每个候选块一起处理。对几千个文档跑交叉编码器，实时查询根本吃不消，所以先用向量搜索当快速检索器，把范围收窄成一份候选清单，再交给 reranker 排序。

## 怎么给 RAG 管道加一个 reranker

你不需要替换现有的 embedding 搜索。把它留作第一阶段检索，把它返回的候选数量调大，再在把最终结果交给 LLM 之前加一次 rerank 调用。

![带 reranker 的 RAG 管道：问题、向量搜索前 30 个块、rerank 模型、前 3 个块、LLM 答案](https://openrouter.ai/blog/images/reranking-rag-1.png)

*用 embedding 取回 30 个块，rerank 之后把前 3 个送给 LLM。*

下面的 Python 例子用了我们的 embeddings 和 rerank API。它先用余弦相似度取回候选块，再用 voyageai/rerank-3-lite 做 rerank，返回排名最高的三个结果。

你需要一个 OPENROUTER_API_KEY 环境变量，并装好 numpy 和 requests。

***Python***

```
import os
 
import numpy as np
import requests
 
API = "https://openrouter.ai/api/v1"
HEADERS = {"Authorization": f"Bearer {os.environ['OPENROUTER_API_KEY']}"}
 
def embed(texts, input_type, model="google/gemini-embedding-2"):
    r = requests.post(f"{API}/embeddings", headers=HEADERS, timeout=120,
                      json={"model": model, "input": texts,
                            "input_type": input_type})
    r.raise_for_status()
    data = sorted(r.json()["data"], key=lambda d: d["index"])
    v = np.array([d["embedding"] for d in data])
    return v / np.linalg.norm(v, axis=1, keepdims=True)
 
def retrieve(question, chunks, chunk_vectors, n=30):
    sims = chunk_vectors @ embed([question], "search_query")[0]
    return [(sims[i], chunks[i]) for i in np.argsort(-sims)[:n]]
 
def rerank(question, candidates, top_n=3, model="voyageai/rerank-3-lite"):
    r = requests.post(f"{API}/rerank", headers=HEADERS, timeout=120,
                      json={"model": model, "query": question,
                            "documents": candidates, "top_n": top_n})
    r.raise_for_status()
    data = r.json()
    ranked = [(res["relevance_score"], candidates[res["index"]])
              for res in data["results"]]
    return ranked, data.get("usage", {}).get("cost")
 
# Your knowledge base, already split into chunks
chunks = [
    "Starter plan limits: an account on the Starter plan can create up to "
    "10 buckets.",
    "Scale plan limits: accounts on the Scale plan can hold up to "
    "2,500 buckets.",
    "Enterprise plan limits: Enterprise accounts can create up to "
    "40,000 buckets.",
    "Growth plan limits: an account on the Growth plan can hold up to "
    "150 buckets.",
    "Q: What's the bucket cap on the Growth plan? Reply: I think it "
    "changed recently, check the docs.",
    "Growth plan object size: a single object on the Growth plan can be "
    "up to 50 GB.",
]
chunk_vectors = embed(chunks, "search_document")
 
question = ("How many buckets can I create in a single account "
            "on the Growth plan?")
retrieved = retrieve(question, chunks, chunk_vectors)
print("Vector search:")
for sim, text in retrieved:
    print(f"  {sim:.3f} {text[:60]}")
 
ranked, cost = rerank(question, [text for _, text in retrieved])
print(f"Reranked (${cost:.7f}):")
for score, text in ranked:
    print(f"  {score:.3f} {text[:60]}")
```

***输出***

```

  0.832 Growth plan limits: an account on the Growth plan can hold u
  0.758 Starter plan limits: an account on the Starter plan can crea
  0.741 Scale plan limits: accounts on the Scale plan can hold up to
  0.737 Enterprise plan limits: Enterprise accounts can create up to
  0.717 Growth plan object size: a single object on the Growth plan
  0.695 Q: What's the bucket cap on the Growth plan? Reply: I think
Reranked ($0.0000038):
  0.922 Growth plan limits: an account on the Growth plan can hold u
  0.793 Q: What's the bucket cap on the Growth plan? Reply: I think
  0.727 Starter plan limits: an account on the Starter plan can crea
```

有了这些一句话的短块，向量搜索已经把正确的 Growth 套餐上限排在了第一位。余弦相似度分数从 0.695 到 0.832，几个候选挨得比较近。rerank 之后，正确的块拿到 0.922 的相关性分数；那篇未答复的论坛帖以 0.793 升到第二位，压过了 Starter 套餐那条。

第二条结果说明了一个重要局限：相关性不等于正确性。论坛帖问的是同一个问题，所以 reranker 认为它相关，哪怕它并没有回答问题。在这个简化例子里，reranker 没有去改第一条结果，因为它本来就对了。在完整基准测试里，用的是 130 词的块，向量搜索在 19% 的问题上把错误的块排在首位（包括 Growth 套餐那个问题），用 voyageai/rerank-3-lite 做 rerank 修好了其中大多数。

实际的经验是：给 LLM 送几个强候选，别只押一个结果。另外，也该考虑把未答复的讨论，以及其它只是提到问题、却没解决问题的内容过滤掉。

代码里还有两处细节值得处理对：

- 第一，input_type 参数告诉 embedding 模型，它编码的是搜索查询还是文档。有些模型对这两类输入区别对待，漏掉这个参数会拖累检索。在我们的测试里，不设它会把 Gemini 的 precision@1 从 81.0% 拉到 74.1%，把 voyageai/voyage-4-lite 从 64.6% 拉到 52.9%。见 [embeddings API 参考](https://openrouter.ai/docs/api/api-reference/embeddings/submit-an-embedding-request)，它把这个参数当作字符串，记录的取值是 search_query 和 search_document。
- 第二，top_n 控制的是 reranker 返回多少条结果，不是它评估多少条。模型仍会给你送进去的每个候选打分，所以候选数量同时影响成本和延迟。

## 怎么判断 rerank 有没有帮上忙？

reranker 可能改善了结果排序，却未必改善用户拿到的答案。要判断值不值得加，先量一量改动前后的检索准确率，再评估最终答案。

> 1. 从 precision@1 入手：第一个取回的块里含有正确答案的问题占比。起步不需要多大的评估集。从应用日志里挑 50 个真实问题，每个标好它对应的正确块，就能得到一条初始基线。关于如何从生产流量构建黄金评估数据集，那份指南讲了该怎么搭一套。
> 2. 别只靠 recall@5：它衡量正确的块有没有出现在前五名里，不管具体位置。在我们的测试里，Gemini 的 recall@5 有 98.2%，precision@1 却只有 81.0%。正确信息通常就在结果里，只是不一定排在头部。

我们也测了对最终答案的影响。用 anthropic/claude-haiku-5.5，拿每种检索配置返回的块去回答全部 274 个问题，再把回答和已知事实对照。

| **送给 LLM 的块** | **答案正确** | **上下文含正确块** |
| --- | --- | --- |
| voyage-4-lite 前 5，不 rerank | 93.1% | 93.1% |
| gemini-embedding-2 前 5，不 rerank | 97.1% | 98.2% |
| gemini-embedding-2 前 3，不 rerank | 95.6% | 96.0% |
| gemini-embedding-2 前 30，rerank 到 3 | 99.3% | 100% |
| voyage-4-lite 前 30，rerank 到 3 | 99.3% | 99.6% |

*我们 2026 年 10 月 8 日那次运行有 274 个问题。rerank 用的是 voyageai/rerank-3-lite。*

结果表明，rerank 让 LLM 用更少的块答对了更多问题。大多数错误答案都源于信息缺失。正确块没进前三的情况里，十次有九次模型会回答说给的段落里没有答案。换句话说，应用告诉用户它不知道，可它自己的文档其实答得上来。

rerank 是通过改善送到模型面前的块来解决这个问题的。它还让我们从送 5 个块改成送 3 个，把 LLM 作答成本从每 1,000 个问题 $0.22 降到 $0.16。rerank 调用本身多花 $0.10，所以在我们的配置下，每 1,000 个问题净多花 $0.04。

rerank 到底能不能替你省钱，取决于你的模型、文档大小和查询量，所以要把从检索到最终答案的整条管道，成本和准确率一起量。

## 哪种 reranker 模型最适合 RAG？

我们用 google/gemini-embedding-2 为 274 个问题各取回相同的 30 个候选，比较了 11 个 reranker。这样比较准确率、延迟和成本就有了统一的基础。

在我们测过的专用 rerank 模型里，Voyage 的 reranker 在准确率和价格上的组合最好。

| **reranker** | **precision@1** | **中位耗时（秒，我们的环境）** | **每 1,000 次查询（$）** |
| --- | --- | --- | --- |
| 无（仅 embedding） | 81.0% | n/a | n/a |
| voyageai/rerank-3 | 97.8% | 1.27 | $0.26 |
| voyageai/rerank-3-lite | 97.1% | 1.26 | $0.10 |
| voyageai/rerank-2.5-lite | 96.7% | 1.50 | $0.10 |
| voyageai/rerank-2.5 | 96.4% | 1.30 | $0.26 |
| cohere/rerank-4-pro | 95.3% | 1.54 | $2.50 |
| qwen/qwen3-reranker-8b | 92.3% | 1.51 | $1.49 |
| cohere/rerank-4-fast | 92.0% | 1.25 | $2.00 |
| cohere/rerank-v3.5 | 90.5% | 1.47 | $1.00 |
| openai/gpt-6-luna (LLM) | 99.6% | 4.01 | $0.70 |
| anthropic/claude-haiku-5.5 (LLM) | 98.9% | 4.44 | $0.87 |
| google/gemini-3.8-flash (LLM) | 100% | 3.25 | $4.14 |

*我们 2026 年 10 月 8 日的运行。成本是每次响应的用量费用，与 GET /api/v1/generation 一致。每个中位数里约 0.9 秒是测试机的网络开销。*

在这个数据集上，voyageai/rerank-3 有 97.8% 的时候把正确块排在第一位，Lite 版是 97.1%。在 274 个问题的测试里，这个差距只相当于两道题，小到不足以证明更贵的模型就一定更好。先从 voyageai/rerank-3-lite 起步，再在你自己的评估集上和 voyageai/rerank-3 比一比。两者用的是同一个 /rerank endpoint，切换模型只要改模型标识符。

价格差异主要来自各家供应商的计费方式，我们的 [rerank 模型页面](https://openrouter.ai/collections/rerank-models)上列了。Voyage 和 Qwen 按 token 计费（每百万 $0.02 到 $0.20），Cohere 则对每次最多 100 篇文档的搜索收 $0.001 到 $0.0025，与文档长度无关。我们的 30 个候选大约合 5,000 个 Voyage token，所以 Voyage 模型格外便宜。在这些短块上，Cohere 的 reranker 成本大约是 Voyage 方案的 4 到 25 倍，具体看比的是哪两个模型。在测试里，给 Cohere 送 101 篇文档还触发了第二次搜索计费。

对具体错误码（比如 FB-2411）的问题，rerank 带来的改善尤其明显。只用 embedding 搜索时，voyageai/voyage-4-lite 把正确条目排在首位的比例只有 25%，google/gemini-embedding-2 是 53.6%。11 个 reranker 在这个子集上都做到了 100%。错误码条目讲的往往是相似的错误，embedding 看起来可能很像。交叉编码器能把问题里的确切代码和每个候选里的代码逐一对比，挑出正确的那条。

如果你想知道开发者用得最多的是哪些模型，我们的 [rerank 模型排名](https://openrouter.ai/rankings/rerank)是另一个有用的参考。截至 2026 年 10 月 20 日，voyageai/rerank-2.5 在截至 10 月 18 日的那一周以 468 万次请求领先，它在我们的测试里得分 96.4%。用得多不多值得参考，但不能代替拿自己的文档去测。模型表现、价格和供应商延迟都会变。[reranking 模型集合](https://openrouter.ai/collections/rerank-models)列出了可用选项和当前详情。

## 该对多少篇文档做 rerank？

先对大约 30 个候选做 rerank，再根据评估结果调整数量。

为了看候选数量怎么影响表现，我们用 voyageai/rerank-3-lite 测了 voyageai/voyage-4-lite 取回的不同候选数：

| **rerank 的候选数** | **候选中含正确块** | **rerank 后 precision@1** | **每 1,000 次查询（$）** |
| --- | --- | --- | --- |
| 10 | 97.1% | 94.5% | $0.035 |
| 20 | 98.9% | 96.4% | $0.070 |
| 30 | 99.6% | 96.7% | $0.104 |
| 50 | 100% | 97.1% | $0.174 |
| 100 | 100% | 97.1% | $0.348 |

*我们 2026 年 10 月 8 日的运行用了 274 个问题，第一阶段是 voyageai/voyage-4-lite。*

候选数从 10 增到 30，precision@1 从 94.5% 提到 96.7%。再增到 50，准确率到 97.1%，只多解决一道题，rerank 成本却涨了约三分之二。从 50 增到 100 个候选，准确率没有再提高。

rerank 有它的极限：只有第一阶段检索把相关块放进了候选集，它才有机会把它提上来。如果向量搜索彻底漏掉了答案，任何 reranker 都找不回来。

知识库更大时，用评估集找出那个临界点：再多取候选，正确块可得的问题占比也不再明显上升。比起想当然地认为 30 对所有应用都最优，这样选候选数更靠谱。

## LLM 能当 reranker 用吗？

在我们的基准测试里，基于 LLM 的 reranker 最准，但返回结果也更慢。我们没有把每个候选丢给专用 rerank 模型，而是把问题和全部 30 个带编号的块一起交给一个 chat 模型，让它按相关度顺序返回块的 ID。我们用了严格的[结构化输出 schema](https://openrouter.ai/docs/guides/features/structured-outputs)来保证返回格式符合预期。

两种做法有个关键区别。专用 reranker 是把每个候选单独拿去和问题比对打分；LLM 能把所有候选一起读进来互相比较，遇到多篇文档信息相近时就有优势。

在我们的测试里，openai/gpt-6-luna 以每 1,000 次查询 $0.70 做到 99.6% 的 precision@1，这是 LLM 成本区间的低端，另一端是 google/gemini-3.8-flash 的 $4.14。精度比专用 reranker 更高，但在我们的环境里每次调用约要 4 秒，专用模型约 1.3 秒。

在用户等着答案的交互式应用里，这点额外时间就很要紧。LLM rerank 更合适批处理，或者那种找对信息特别重要、多等一点延迟也能接受的应用。

别忘了，我们的基准用的是干净、由模型生成的文本。真实知识库里格式不统一、文档不完整，还有各种别的麻烦，所以不能想当然地认为 LLM reranker 在更乱的真实数据上还能保持同样的优势。

## 有了混合搜索或更好的 embedding 模型，还需要 reranker 吗？

混合搜索和更好的 embedding 模型都能改善检索，但我们的基准显示，两者都不如加一个 reranker 有效。混合搜索把向量相似度和基于关键词的检索（常用 BM25）结合起来。我们用倒数排名融合（RRF）合并结果，把两套排名并成一套。

在我们的测试集上，混合搜索把 voyageai/voyage-4-lite 的 precision@1 从 64.6% 提到 69.3%。但换成 google/gemini-embedding-2，precision@1 反而从 81.0% 掉到 78.8%，尽管 recall@5 改善了。更强的 embedding 模型确实胜过了便宜的那个：Gemini 的 precision@1 是 81.0%，Voyage 4 Lite 是 64.6%。但 Gemini 的 embedding 价格是每百万 token $0.20，Voyage 4 Lite 只要 $0.02。把便宜的 embedding 模型和 voyageai/rerank-3-lite 搭配，precision@1 达到了 96.7%。

混合搜索和更好的 embedding 仍然有用，因为它们干的活不一样：混合搜索能捞回向量搜索漏掉的候选，更强的 embedding 模型能改善初始排名。reranker 则再加一层，把每个候选直接和问题比对。

想拿到最好的结果，就把这些方案分开评、也合起来评。挑第一阶段的 embedding 模型时，可以参照[我们的 embedding 模型对比](https://openrouter.ai/blog/insights/best-embedding-models-2026/)。

## 什么会让 rerank 失效？

文档超出模型的上下文上限时，rerank 可能悄无声息地失败。比如 cohere/rerank-v3.5 有 [4,096 token 的上下文上限](https://openrouter.ai/cohere/rerank-v3.5)，文档里含答案的那部分它可能根本没看到。

我们用两篇 11,000 token 的文档测了这一点，它们只有最后一句不同。其中一篇含答案，但两篇拿到的相关性分数一样：0.2703。模型等于漏掉了区分它们的那个细节。相比之下，voyageai/rerank-3-lite 给两篇打了 0.7812 和 0.3242，正确地把含答案那篇排在更高。Cohere 4 系列、voyageai/rerank-3 和 qwen/qwen3-reranker-8b 也都把正确文档排得更靠前。查一下你用的 reranker 的上下文上限，让块稳稳留在限制之内。

另一个问题是模型兼容性：/rerank endpoint 只接受 rerank 模型。把 chat 模型 openai/gpt-6-luna 发过去，会返回 400 Model openai/gpt-6-luna does not exist，和拼错模型标识符时拿到的是同一个错误。发请求之前，先确认模型出现在 [reranking 模型集合](https://openrouter.ai/collections/rerank-models)里。

## 常见问题

### 什么是 RAG 中的 reranking？

RAG 中的 reranking 是第二步检索：rerank 模型针对问题给向量搜索返回的每个块打分并重排，让最相关的少数几个进入 LLM。rerank 模型把问题和块一起读，因此能抓出「差一点就对」的情况，比如给了错误套餐的正确上限。在我们 274 个问题的测试里，它把正确块排第一的比例从 81% 提到了 97%。

### 哪些 reranker 模型最适合 RAG？

在我们 2026 年 10 月的测试里，voyageai/rerank-3 和 voyageai/rerank-3-lite 是最准的专用 rerank 模型，也是成本最低的 reranker，在 274 个问题里分别有 97.8% 和 97.1% 把正确块排在第一位。LLM reranker 分数更高，但每次调用约要 4 秒。

### 该对多少篇文档做 rerank？

对大约 30 个候选做 rerank；知识库更大时就往上加，直到正确块能稳定出现。在我们的测试里，从 30 加到 50 把 precision@1 从 96.7% 提到 97.1%（噪声范围内只多一道题），rerank 成本却涨了三分之二。
