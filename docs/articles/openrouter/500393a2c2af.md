# 用生产流量构建金标准评测数据集

OpenRouter ·9/30/2026

你更新了一个提示词，或者某家提供商在同一个模型 ID 下发新检查点，生产环境就出现了回归。用户最近一周的抱怨和上一周看起来有点不一样。像 [MMLU](https://arxiv.org/abs/2009.03300) 这样的公开基准抓不到这个——它衡量的是跨学科的通用能力，不是模型怎么处理你产品的流量。

金标准评测数据集（golden eval dataset）补的就是这个缺口。它是一批精选的生产输入，配上经过人工复核的期望输出，用 Git 做版本管理，每次部署前都要跑。它回答的是基准回答不了的那个问题：这次变更，对你实际服务的流量，是帮忙还是添乱？

本指南讲清楚金标准集是什么、为什么生产数据比合成数据更是好地基、从真实流量构建的五步流程，还讲怎么用同一个 API 把同一套集子跑在多个候选模型上——让下一次选模型的依据是你自己流量的证据，而不是榜单排名。

## 太长不看

- 金标准评测数据集：精选的生产输入 + 经复核的期望输出，作为每次重大变更前的回归测试。
- 集合一旦存在，你就可以用一个 API 在多个模型上跑它，凭自己流量的证据选下一个模型。
- 规模要配得上任务：探究单个问题约 10 条，完整回归集 100 到 1,000 条。合适的大小取决于指标、方差和你要检出的最小差异。
- 失败模式的覆盖面比数量更重要。真实例子带着你用户撞过的坑，合成例子带着别人想象出来的坑。
- 数据集、评分规则和基线要一起管版本。否则一次回归到底是模型、提示词还是数据集变了，你分不清。

## 金标准评测数据集是什么

金标准评测数据集是一批生产样本配上经复核的期望输出，从训练中留出、每个发布候选都要评估。每条期望输出都由具备领域知识的人确认过，或者判定该条不需要——因为格式、安全或语气这类无参照检查本身就是通过标准。

复核正是这套集合有用之处。没有它，分数一下降，你分不清是变更让质量退化了，还是第 23 条的标签本来就是错的。

把它当作行为的回归测试套件，而不是代码的。它在 CI 里跑，有已知正确的期望输出，抓的是两次部署之间的漂移。它和单元测试的区别在于期望输出是一个判断，所以 harness 要做的比字符串比较更多。

金标准集不是基准，不是训练集，也不是 A/B 测试。基准衡量通用能力，金标准集在**你的**流量上衡量能力。训练集教模型，金标准集在模型退化时抓住它。A/B 测试衡量真实用户的结果，金标准集衡量一个变更安不安全到值不值得拿去做 A/B 测试。

## 为什么生产数据是更好的地基

合成评估测的是模型回答"某人想象中的用户问题"的能力。你要测的是你的用户问过的问题，用的还是他们的措辞。生产流量作为地基好在三点。

**分布是对的。**如果你的流量 70% 与定价有关，你的评估集就该 70% 与定价有关。从想象的边缘情形里抽出来的合成集保不住这个分布。保住观测到的分布，回归分数才能反映用户影响。

**失败模式正是你在意的那些。**用户能发现你想都想不到要写下来的失败模式：一条混了三种语言的消息、一张贴了整个错误日志的工单、一个提到你上季度改过名的功能的查询。合成集里不会有这些——除非有人先想到。

**例子跟着你的产品走。**一个客服机器人半年前上线了密码重置处理，如今收到的却是多账户问题、退款升级和竞品 UI 的截图。从生产抽样的金标准集会跟踪这种漂移，发布当天冻结的合成集不会。

合成例子仍有一席之地，但定位是补充而不是地基。用它填补"已知失败模式但真实样本太少"的覆盖缺口。可以用带[结构化输出](https://openrouter.ai/docs/guides/features/structured-outputs)的模型调用生成，让每个例子落在你的数据集 schema 里，或者改写已有条目。在元数据里标注 synthetic，并让它们在集合中保持少数。

## 五步流程

![五步流程示意图：拉取生产流量、去重并聚类、补充期望输出、首轮评估、提交 Git 接入 CI，最终冻结的集合通过同一个 API 用于跨候选模型的基准测试](https://openrouter.ai/blog/images/golden-eval-five-step-process.png)

### 第 1 步：抽取一份生产流量样本

从一两周的日志输入输出开始。功能有季节性或使用量稀薄时，用更长的窗口。

先随机抽样，再看抽出来的是什么。流量有长尾时，随机样本会过度代表头部。这通常正是你要的——头部的回归影响的用户最多——但要检查稀有而关键的意图到底有没有出现。

将来可能要切片分析的字段全都记下来：意图、功能域、用户分群、时间戳，以及产出你所抽样响应的模型和提示词版本。这些元数据事后无法重建。

对生产流量抽样就是对用户数据抽样。核对你的服务条款，在数据进入评估 harness 之前先跑完 PII 清洗管线，并记录哪些例子被你转换过，以便日后能复现清洗。

进入第 2 步的原始池子目标为几百条。之后要大量裁剪。

### 第 2 步：去重并聚类

生产流量是重复的。一个客服 chatbot 可能一天里见到一百次"怎么重置密码"、只是措辞略有出入。集合里要的是其中一条，不是五十条。

精确匹配的去重抓不到改写。要抓住它们，检查数据集是否已覆盖同一意图——把规范化后的输入做精确匹配，或在输入之间比较[嵌入相似度](https://developers.openai.com/api/docs/guides/embeddings)。

得到去重后的池子，再在池内为覆盖面抽样。一半流量是同一个意图时，这个意图应占金标准集约一半——但不是全部。一个代表性不足的意图惨败，代价高于一个代表性充分的意图体面失败，所以往你输不起的失败模式上加权。

关于目标规模，[Langfuse 的指引](https://langfuse.com/resources/engineering/golden-dataset-evaluation)是有用的起点。数字当参考，按你的流量与评估目标调整。

用途

典型规模

探究单个问题

约 10 条

测试模型能力边界

约 10 条复杂的未解例子

大变更的 CI 检查

100 到 1,000 条，覆盖生产分布

对抗性提示词的护栏测试

大而持续增长，随发现随加

保留一个几十到小几百条的子集做 PR 闸门以保持速度，完整集合留给发布分支或夜间运行。

### 第 3 步：补充期望输出

每个输入，都得有合格的判断者写下正确输出长什么样。有时那是一个字符串，更多时候是一份 rubric（评分规则）：哪些事实必须在、哪些断言不能出现、要求什么语气或格式。

两个 rubric 选择能让评分更一致。用二元标准：每条标准要么 MET 要么 UNMET。用分析型 rubric——逐条标准分别打分——而不是只给一个总分的整体型 rubric。分析型 rubric 告诉你**什么变差了**，而不只是有没有变差。

让两个人独立标注一个子集。分歧之处，把问题归给 rubric，不归给人。修 rubric，直到两位评审给同一份模型输出打出同样的分。

不是每条都需要写死的期望输出。仅由无参照评估器检查的条目——格式有效性、安全、语气——根本不需要期望输出。金标准集可以两类混装。

### 第 4 步：跑首轮评估并修 rubric

在信任这套集合之前，拿当前的生产模型跑一遍它，逐条看所有失败。

把失败归三类。真失败：模型答错了、期望输出是对的——保留。rubric 问题：模型给了合理答案，但你的期望输出没预料到——修期望输出。歧义例子：任何讲道理的 rubric 都判不了——删掉。

这一轮预期要砍掉集合的一部分。砍多少取决于第 3 步的期望输出写得有多认真。砍本身就是这一轮的意义。无论模型怎么变通过率都纹丝不动的金标准集，什么都没在测。

别跳过这步。这里没抓住的 rubric 问题，将来会在一次真实部署中伪装成假回归。

### 第 5 步：提交 Git、接入 CI、持续迭代

金标准集应当住在你的代码库里，与提示词和运行它的代码同版本管理。这是把它从临时质量检查变成回归测试的关键。

最小目录结构长这样：

```
/evals
  /golden
    dataset.jsonl        # one example per line
    rubric.md            # how to grade
    run.ts               # loader and harness
    baseline.json        # pass rates on the current production model
  /synthetic
    dataset.jsonl        # rare failure modes, marked with synthetic: true
```

每个例子存成一行 JSON，字段包括输入、期望输出、标签和元数据。rubric 存成一份人类可读、评分器从中读取的文档，任何看 PR diff 的人都能看出通过率的移动是不是 rubric 变更造成的。

`dataset.jsonl` 里的一行长这样：

```
{"id":"pw-reset-locked-account","input":"i cant log in, tried resetting three times and its saying account locked. help","expected":"The bot should acknowledge the lockout, ask for the account email, and route to the account-recovery flow. It must not offer to reset the password directly.","rubric":"must_ask_email;must_route_recovery;must_not_reset_directly","tags":["password_reset","edge_case"],"synthetic":false}
```

不同字段服务不同读者。`id` 给每条一个穿越 Git diff 的稳定引用。`input` 是生产输入，清洗后逐字保留。`expected` 是人类可读的散文，LLM 裁判能读。`rubric` 放裁判评分用的机器可检查标准。`tags` 让你按意图切通过率。`synthetic` 在汇总指标里把真实和合成条目分开。

把 harness 接进 CI，每个提示词变更或模型切换都跑。通过率跌幅超过定义阈值就让构建失败，小于一跌也要书面确认才能过。一个在每次 pull request 上调用 harness 的 [GitHub Actions](https://docs.github.com/en/actions) workflow，起步就够了。

按节奏刷新集合。每季度评审六个月以前的条目、逐条对照当前产品行为，是合理的默认。产品变化快就按月来。陈旧的金标准集迟早会失去对生产行为的预测力。

rubric 和数据一起管版本。一次失败的运行只有能诊断才有用，而 rubric 变更是事后最难抓的变更。有人为了修一个看似假回归改了标准，这个修改就应当作为 PR diff 里的可见变更出现，而不是六周后一个无法解释的通过率移动。

不要因为条目一直通过就退役它们。通过着的条目正在证明那个行为仍然成立。只有当它测的行为在产品里已不存在、或期望输出如今是错的，才退役。

## 用一个 API 做跨模型基准

当你有了 100 条带期望输出的例子，把同一套集子跑在另一个模型上，就能告诉你那个模型在**你的工作负载**上表现如何——不是 MMLU 上的，不是别人家的编码 harness 上的，是你用户发来的问题上的。

跨厂商比较模型通常意味着每个候选一套 SDK、一套认证、一种响应形态、一套限流。通过 [OpenRouter](https://openrouter.ai)，同一个 OpenAI 兼容请求体可以在整个[模型目录](https://openrouter.ai/models)上用。对共享接口且支持你请求所用参数的候选，把 `model: "openai/gpt-5.1"` 改成 `model: "anthropic/claude-fable-5.1"`、重跑 harness 就是比较。模型在上下文长度、工具支持或参数上不同时，请为每个候选预留一些集成工作。[models 端点](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties)的每个条目列出模型上下文长度和 `supported_parameters` 数组，切换前先查一下。

一个最小 harness 长这样：

```
import OpenAI from "openai";
import { readFileSync } from "fs";

const client = new OpenAI({
  apiKey: process.env.OPENROUTER_API_KEY ?? "",
  baseURL: "https://openrouter.ai/api/v1",
});

const dataset = readFileSync("./evals/golden/dataset.jsonl", "utf-8")
  .trim()
  .split("\n")
  .map((line) => JSON.parse(line));

const modelsToTest = [
  "openai/gpt-5.1",
  "anthropic/claude-fable-5.1",
  "google/gemini-3.8-flash",
];

const results: Record<string, { pass: number; total: number }> = {};

for (const model of modelsToTest) {
  results[model] = { pass: 0, total: 0 };

  for (const example of dataset) {
    const response = await client.chat.completions.create({
      model,
      messages: [{ role: "user", content: example.input }],
    });

    const output = response.choices[0].message.content ?? "";
    const passed = grade(output, example.expected, example.rubric);

    results[model].total += 1;
    if (passed) results[model].pass += 1;
  }
}

console.table(results);
```

`grade` 函数是 rubric 住的地方。字符串匹配的用例，它可以是 `output.includes(expected)`。rubric 评分的用例，它通常是再发一次 LLM 调用：把 rubric 和响应交给一个强的[裁判模型](https://openrouter.ai/rankings)，问它每条标准是否满足。

发给裁判的标准检查提示词长这样：

```
Rubric criteria (each MET or UNMET):
{criteria}

Response to grade:
{response}

For each criterion, output MET or UNMET on its own line. No prose.
```

裁判每条标准返回一个 MET 或 UNMET，`grade()` 把它解析为"全部 MET 则通过，否则失败"。二元标准加"不要散文"的指令，让裁判输出在多次运行之间稳定到可解析。

设计良好的 rubric（二元标准、带锚定示例）之上，LLM 裁判对回归检测足够可靠。它与人类评审的一致率随任务、rubric 和裁判模型变化，所以在依赖它的分数之前，先用一批人工标注样本校准裁判。裁判的可靠性还会随随机种子浮动。[一项研究](https://arxiv.org/abs/2412.12509)让三个 LLM 裁判给 BIG-Bench Hard 问题的回答各打 100 次分，只改种子不改其他，测得裁判间的一致率在不同重复间从 0.167 到 1.00 不等——这个尺度上 1.0 是完全一致。用与被测模型不同的模型当裁判以避免自我偏好偏差；高风险决定上，别把裁判的单次运行当 ground truth。

在所有模型上评同一套集子。运行之间改了数据集，你就在同时测两样东西。冻结集合、记录 commit hash，然后换模型。

看质量也看成本。在你金标准集上最准的模型，每次调用可能贵过第二名 30 倍，而质量差距只有两个百分点。把这个取舍摆到预算负责人面前。跑完整基准之前，我们的[模型对比页](https://openrouter.ai/compare)先显示两个模型的价格差距。

需要可复现时就用提供商路由控制。同一个模型 slug 可能路由到不同提供商，提供商行为会有细微差异。要把一次基准钉在一家提供商上：在 `provider` 对象里把 [`order` 字段](https://openrouter.ai/docs/guides/routing/provider-selection#ordering-specific-providers)设为该提供商的 slug，并把 `allow_fallbacks` 设为 `false`。只设 `order` 时，所列提供商不可用我们仍会落到其他提供商。

## 结论

金标准评测数据集告诉你一次变更在你服务的流量上是帮忙还是添乱。从生产数据构建、逐条复核期望输出、把集合连同 rubric 和基线一起管版本、每次部署都跑。

有了它，用一个 API 把同一套集子跨多模型跑就是回报。对兼容的候选，比较变成改一个模型标识符加一次重跑——外加逐候选核对上下文长度、工具支持和参数。

## 常见问题

### 金标准评测数据集该多大？

从 20 到 50 条经过复核、覆盖你最要紧失败模式的条目开始。向 100 到 1,000 条的完整回归集增长，并为每个 PR 的检查保留更小的子集。合适的大小取决于指标、流量分布和你要检出的最小质量差异。失败模式的覆盖面比绝对数量重要。

### 该用生产数据还是合成数据？

生产数据打地基，合成例子补已知覆盖缺口。真实流量保住分布、保住用户制造的失败模式。为你真实样本太少的稀有失败模式增补合成用例，元数据里标注 synthetic，并让它们保持少数。

### 金标准集该多久刷新一次？

每季度评审一次；提示词、模型或产品行为变化快时更频繁。旧条目对照当前行为检查，新观察到的失败模式补进来，只退役产品里已不存在的行为的条目。保留历史版本，以便复现过去的回归。

### 能用 LLM 当裁判吗？

能，附两个条件。rubric 要具体到"两个人类给同一输出打出同样分"；在依赖分数之前要用人工标注样本校准裁判。高风险决定别用单次运行定论，也别让被测模型给自己当裁判。

### 金标准集和基准的区别是什么？

基准拿公开测试衡量模型的通用能力；金标准集在你自己的流量上衡量能力。基准帮你缩小模型候选名单，金标准集告诉你名单里哪个模型能服务你的产品。谁也替代不了谁。
