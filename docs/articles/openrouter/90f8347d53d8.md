# OpenRouter Fusion：工作原理与适用场景

OpenRouter · 2026-09-10 · 更新于 2026-09-24

[Fusion](https://openrouter.ai/docs/guides/routing/routers/fusion-router) 是我们的复合模型（compound model）。它接收一个 prompt，把它变成若干模型之间的一场简短辩论。我们同时把你的 prompt 发给一个专家模型小组，由一个 judge 比较所有响应，供发起调用的模型写出单一的最终答案。

用 Fusion，你拿一部分速度和 token 换质量。本页讲清 Fusion 做什么、代价几何、什么时候胜过单模型、什么时候不。

## Tl;dr

- **Fusion 做什么。** 它让一个模型获得一个多模型审议（deliberation）工具。小组并行作答，judge 梳理一致与分歧，发起调用的模型据此写出最终响应。
- **代价。** 一次被触发的 Fusion 调用会增加小组与 judge 的补全开销。默认三模型小组在同一 prompt 上的花费约为单次补全的四到五倍，耗时通常长两到三倍。
- **何时使用。** 把 Fusion 当作选择性的升级路径，用于复杂研究、专家级评审，以及"答错比多花几次模型调用更贵"的决策。

## 什么是 OpenRouter Fusion？

Fusion 是一套复合推理系统，让模型获得多模型审议能力。当模型触发 Fusion 时，若干模型并行回答该 prompt。一个 judge 比较它们的响应并产出结构化分析，随后据此生成最终答案。

这使 Fusion 不同于单次模型调用。单次调用沿一个模型的推理路径走，而 Fusion 能把多条推理路径、多种取材选择和多种解读汇进同一个响应。

Fusion 和 [auto-routing](https://openrouter.ai/blog/insights/model-routing/) 干的是不同的活。Auto-routing 为你的请求挑一个模型：它给 prompt 的任务类型分类，然后选 OpenRouter 社区在那类任务上花费最多的模型。Fusion 则把多个模型组合起来、混合它们的答案，可能给出比小组中任何单一成员都更强的回答。

## OpenRouter Fusion 如何工作

Fusion 在普通模型请求内部加入一个审议循环。

流水线分四个阶段：

- **发起调用的模型评估 prompt。** 当你使用 Fusion 时，我们先把别名解析成一个模型并挂上 Fusion 工具。模型可以直接回答，也可以在任务值得更多分析时触发 Fusion。
- **小组并行工作。** 一到八个参与模型各自独立回答 prompt。每个组员都可以使用 OpenRouter 的 [web search 和 web fetch](https://openrouter.ai/blog/announcements/agentic-web-tools/) 去找时效性来源。
- **judge 比较响应。** 我们文档里把这个角色叫 analyst。judge 识别共识、矛盾、部分覆盖、独特洞见和盲区，并把这份比较作为结构化分析返回。
- **发起调用的模型写答案。** 原始模型收到 judge 的分析，用它生成返回给你应用的响应。

judge 的职责是比较，而不是简单投票。三个模型重复同一个无依据的说法，并不会让它自动正确。judge 也能把一个只出现在一份响应里的有用观点浮现出来，或指出所有组员都漏掉的缺口。

### 质量增益从哪里来

Fusion 受益于模型之间的多样性和同模型不同运行之间的差异。不同模型可能选择不同方法、注意到不同约束、检索到不同来源。甚至同一模型的两次运行也可能沿不同推理路径、做出不同的工具调用。

我们测过第二种效应：让 Claude Opus 4.8 与另一次 Opus 4.8 运行配对，并用同一个模型做综合。该融合配置在我们的 DRACO 基准运行中得分 65.5%，而单独一次 Opus 4.8 运行是 58.8%。这 6.7 个百分点的提升说明，即便没有模型多样性，比较与综合过程本身也能贡献实质价值。

多模型集成（ensembling）是成熟技术。Fusion 的产品价值在工程层面：你通过一个模型 slug 或一个 server tool 就能加上小组、judge、工具和综合循环，而不必自己搭建并维护这套编排。

## Fusion 对比单模型

Fusion 能改善困难答案，但它是靠干更多活做到的。

### 质量取决于任务

在 [DRACO](https://openrouter.ai/blog/announcements/fusion-beats-frontier/)——Perplexity AI 的深度研究基准——上，使用 Gemini 3 Flash、Kimi K2.6 和 DeepSeek V4 Pro 的平价 Fusion 小组得分约 64.7%，而 Claude Fable 5 单模型约 65.3%。由于内容过滤器，基于 Fable 的结果只覆盖 100 个任务中的 93 个，因此直接比较略有不均。

DRACO 测的是深度研究，不是原生编码或通用聊天。Fusion 的综合在研究与分析类 prompt 上帮助最大——多种视角确实能磨利答案的地方。不要假设同样的优势幅度适用于每个任务。

### token 更多，但按任务算的成本仍可能占优

Fusion 要为多个模型调用加 judge 付费，所以单个请求用的 token 比单模型调用多。不过"每次调用的成本"并不总是关键数字，"每个正确答案的成本"往往更重要。

如果一次 Fusion 调用就给出正确答案，而便宜模型需要三次尝试、一次重跑外加人工核查，那么整段任务算下来 Fusion 反而更便宜。要算的是达成结果的总成本，不是单个请求的价格。我们的 [Fusion model 页面](https://openrouter.ai/openrouter/fusion)有最新费用。

### 延迟会长两到三倍

Fusion 调用通常比标准单模型调用慢两到三倍。小组是并发运行的，你不是逐个模型排队等，但你仍要等最慢的组员，然后再等 judge。这段延迟通常把聊天、自动补全等实时路径排除在外。

### 设计上就非确定

一个小组加一个综合步骤，运行与运行之间可能给出不同结果。这是有意为之。对一次性研究任务这没问题，但当你需要可复现的输出——评测套件、回归测试，或任何拿今天结果和昨天结果比对的检查——它就变成问题。

## 何时该用 Fusion、何时该跳过

最强的生产模式是选择性升级。让模型直接处理日常活，把 Fusion 留给那一小部分值得额外审视的 prompt。若要逐步升级到单个更强模型，参见 [Advisor server tool](https://openrouter.ai/blog/announcements/advisor-server-tool/)。

### 用于答错代价高昂的高风险、研究型 prompt

研究问题、专家评审、对比分析、尽调摘要——凡是准确率为先、事后纠错要消耗真实时间或金钱的地方。实际场景举例：在投入战略会议之前，从十几个时效性来源总结一个竞争格局。

### 用于你原本会手动问多个模型的场景

如果你当前的工作流是拿同一个问题问三个模型、再自己比较答案，Fusion 干的正是这件事。而且 judge 比人工比对更一致。

### 延迟敏感或高 QPS 的交互路径要跳过

当用户在等响应时，两到三倍的延迟太长。实际场景：客服聊天机器人、行内代码补全。

### 复现性敏感的工作负载要跳过

评测、回归套件，以及任何需要跨运行稳定结果的东西。非确定性会让这些比较不可靠。实际场景：一条检查 LLM 输出是否变化的 CI 流水线。

### 单个中档模型已经搞定的简单、边界清晰的任务要跳过

如果一个中档模型今天就能返回正确答案，小组只是徒增成本和延迟。实际场景：分类、抽取、短改写、格式转换。

## 如何使用 OpenRouter Fusion

你可以在网页界面里测试 Fusion，也可以通过任意受支持的推理 endpoint 调用它。

### 无代码路径

打开 [Fusion lab](https://openrouter.ai/fusion)，选一个 preset，输入一个能从多视角受益的 prompt。

从一个你已知很难的 prompt 开始。把融合结果与你当前生产模型的答案做比较，看是否事实错误更少、覆盖更广、分歧处理更清楚、人工编辑更少。

界面也允许你自建小组，再把配置搬进你的应用。

### Fusion API

最简单的 API 路径是把当前模型 slug 换成 `openrouter/fusion`。不做额外配置时，Fusion 使用默认 Quality 小组，并由模型决定是否值得审议。

下面的例子选择 `general-budget` preset，覆盖其 judge 模型，并强制 Fusion 运行：

```
import os

from openai import OpenAI

client = OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key=os.environ["OPENROUTER_API_KEY"],
)

response = client.chat.completions.create(
    model="openrouter/fusion",
    messages=[{
        "role": "user",
        "content": "Compare three approaches to multi-tenant data isolation.",
    }],
    tool_choice="required",
    extra_body={
        "plugins": [{
            "id": "fusion",
            "preset": "general-budget",
            "model": "~openai/gpt-latest",
        }]
    },
)

print(response.choices[0].message.content)
```

preset 负责挑选一个经过精选的小组。嵌套的 `model` 字段选择 judge，当你使用 Fusion 模型别名时，也决定写最终响应的模型。显式的 `analysis_models` 或 `model` 值会覆盖 preset 中对应的设置。[`tool_choice: "required"`](https://openrouter.ai/docs/guides/routing/routers/fusion-router#forcing-fusion-on-every-request) 强制模型触发 Fusion，而不是让它自己决定。

当前可用的通用 presets 包括：

- `general-high`：最强的全能小组
- `general-budget`：更便宜的组员搭配前沿模型 judge
- `general-fast`：围绕相近响应时间优化的小组

你也可以把 [`openrouter:fusion` server tool](https://openrouter.ai/docs/guides/features/server-tools/fusion) 挂到你自己的外层模型上。当同一个模型需要在应用的其他工具之外同时获得 Fusion 访问时，这条路很有用。

完整请求格式见 [Fusion Router 文档](https://openrouter.ai/docs/guides/routing/routers/fusion-router)，可复用配置管理见 [Presets 指南](https://openrouter.ai/docs/guides/features/presets)。

## 结论

Fusion 给困难 prompt 不止一次机会，并给你的应用一种结构化的方式来比较这些尝试。在快速的首个答案不够用的研究、评审和高代价决策上，它能带来提升。

额外的审视有可度量的代价：小组和 judge 会增加 token、成本、延迟和输出方差。当这些开销能减少重试、人工比对，或减少依据不完整答案行动的风险时，它们才值回票价。

从你真实工作负载里挑一个难的 prompt 开始。用"每个被采纳结果的成本"来比较 Fusion 与你当前模型，而不是只看模型单价。

用 [Fusion Router](https://openrouter.ai/docs/guides/routing/routers/fusion-router) 试一试，或阅读 [Fusion 基准发布公告](https://openrouter.ai/blog/announcements/fusion-beats-frontier/) 了解完整的 DRACO 方法论与结果。

## 常见问题

### OpenRouter Fusion 是怎么工作的？

OpenRouter Fusion 让发起调用的模型把一个 prompt 并行发给多个组员模型。一个 judge 比较各响应，返回覆盖共识、矛盾、部分覆盖、独特洞见与盲区的结构化分析。发起调用的模型再用这份分析写出最终答案。

### AI 中的模型融合是什么？

模型融合可以指合并模型参数，也可以指合并多个模型的输出。OpenRouter Fusion 在推理期间做的是输出级审议：收集独立响应、经由 judge 比较，并把得到的分析交给写最终响应的模型。

### OpenRouter Fusion 比 Fable 5 更好吗？

在 Perplexity AI 的 DRACO 深度研究基准上，Fusion 在若干前沿小组配置中胜过了单独运行的 Fable 5。一个平价小组得分 64.7%，Fable 5 为 65.3%，而一个前沿小组得分 69.0%。由于内容过滤器，基于 Fable 的结果只覆盖 100 个任务中的 93 个。这些结果适用于深度研究，并不能证明 Fusion 在长程或通用工作负载上可以取代 Fable。

### OpenRouter Fusion 有 API 吗？

有。你可以用 `openrouter/fusion` 模型 slug 调用 OpenRouter Fusion API，或把 Fusion 作为 `openrouter:fusion` server tool 挂载。`fusion` plugin 为这两种入口配置小组和 judge，但它自身不会启动一次 Fusion 运行。两种入口使用同一套底层的小组、judge 与最终答案流水线。
