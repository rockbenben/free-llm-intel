# OpenRouter 模型路由的工作原理

OpenRouter ·6/12/2026 · 更新于 9/24/2026

如果 Anthropic 在流量中途对你限流，你的应用不该返回 500。就这一个失败模式，就是很多团队一开始找 LLM 路由器的主要原因。OpenRouter 把每个请求路由到 70 多家提供商，而方式完全由你控制——精确到提供商顺序、价格上限和回退链。

OpenRouter 的路由是两个独立决策：哪个模型回答请求，以及哪个提供商为该模型提供服务。本指南里的每个配置项都对应这两个决策之一。把它们分开看，才能在出问题时配置对的那一层。

[OpenRouter Python SDK](https://openrouter.ai/docs/client-sdks/python/overview)（`pip install openrouter`）几行代码就能到位，切换模型只是改一个字符串。（已经在用 OpenAI SDK？把它的 base URL 指向 `https://openrouter.ai/api/v1` 也一样能用。）

```
from openrouter import OpenRouter

client = OpenRouter(api_key="<OPENROUTER_API_KEY>")

resp = client.chat.send(
    model="anthropic/claude-sonnet-4.6",  # change this string to switch models
    messages=[{"role": "user", "content": "Summarize this changelog."}],
)
```

集成就这么完了。路由全在那一个端点背后发生，本指南接下来逐层拆解它暴露出的路由层，配上可以直接复制的确切配置。

## LLM 路由器实际做什么

这两个决策嵌在一个更大的职责里。路由器把一个请求收到一个端点，再把它交接给应当作答的模型和提供商。每个路由器都干下面 4 件事中的几件，而 OpenRouter 全包了：

| 职责 | 决定什么 | OpenRouter 在哪里做 |
| --- | --- | --- |
| 模型选择 | 哪个模型回答提示词 | `model` 字段，或 `openrouter/auto` |
| 提供商选择 | 哪个提供商为该模型服务 | `provider` 对象（默认：基于价格） |
| 负载均衡 | 如何在稳定的提供商之间分配流量 | 价格平方倒数加权 |
| 故障转移 | 出错时改试什么 | `models` 数组 + 提供商回退 |

[RouteLLM](https://github.com/lm-sys/RouteLLM)、[LLMRouter](https://github.com/ulab-uiuc/LLMRouter) 这类开源项目是你自托管、接进自己基础设施的路由库。OpenRouter 是你直接调用的路由器：一个托管服务，一个端点挡在 [400 多个模型](https://openrouter.ai/models)前面。

当你要决定是自己持有路由逻辑还是交出去时，这个区分很重要；我们在"路由器 vs 网关"一节里会回到这一点。

## OpenRouter 的两层路由

![OpenRouter 两层路由示意图：请求先经过模型路由，再经过提供商路由，然后到选定的提供商，并以响应形式返回](https://openrouter.ai/blog/images/model-routing-two-layers.png)

OpenRouter 在两个独立的层上路由：模型路由（哪个模型作答）和提供商路由（哪个提供商为该模型服务）。把这两层分清楚，下面每个配置就都能各归其位。

一个[兼容 OpenAI 的端点](https://openrouter.ai/docs/quickstart)挡在这两层前面：`https://openrouter.ai/api/v1`，一个 API key，70 多家提供商的 400 多个模型。你调用 OpenRouter 的方式和调用 OpenAI 一模一样，扇出在幕后完成。

### 每个路由决策发生在哪里

最小请求就在一个载荷里展示了这两个决策。

```
curl https://openrouter.ai/api/v1/chat/completions \
  -H "Authorization: Bearer $OPENROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "anthropic/claude-sonnet-4.6",
    "messages": [{"role": "user", "content": "Hello"}]
  }'
```

`model` 字段就是你的模型路由决策。如果某个模型由多家提供商服务，OpenRouter 的提供商路由会挑出处理这一次具体调用的那一家。模型由你显式指定；除非你覆盖，提供商选择自动运行。

### 一个 key，多家提供商

单 key 配置意味着你用一个 OpenRouter API key 就能访问多家提供商。想改用自己的提供商 key 的话，[BYOK 指南](https://openrouter.ai/docs/use-cases/byok)讲了那条路。它保留你现有的提供商协议，并在其上叠加故障转移和路由。

## 哪种路由模式适配哪种活

在讲机制之前，先给地图。后面的小节会讲每种模式怎么工作。当默认路由看不到你的约束时，用覆盖项来管：合规、延迟预算、成本上限、跨模型韧性。

| 你的处境 | 用什么 | 为什么 |
| --- | --- | --- |
| 要最便宜且可靠，不关心哪家提供商 | 默认负载均衡 | 平方倒数加权自动搞定 |
| 必须命中某一家提供商（合规、BYOK、区域） | `provider.order` + `allow_fallbacks: false` | 硬性止步，不会静默回退 |
| 延迟敏感（面向用户的聊天） | `:nitro` | 按吞吐路由 |
| 有成本上限的批处理 | `:floor` / `max_price` | 按价格路由，并强制执行上限 |
| 需要跨模型韧性 | `models` 回退数组 | 扛得住整个模型下线 |
| 不知道用户会发什么样的提示词 | `openrouter/auto` | 市场支出份额按提示词逐个挑选 |

本指南剩余部分按顺序讲这些模式，从"什么都不设置时会运行"的那一种讲起。

## 提供商路由如何工作

![价格加权提供商路由的实例图：提供商 A（$1/M）先试，提供商 C（$3/M）第二，提供商 B（$2/M）因近期宕机排最后](https://openrouter.ai/blog/images/model-routing-provider-weighting.png)

默认情况下，OpenRouter 把请求发给最便宜且可靠的提供商，按价格的平方倒数加权。这就是做路由决策的那一层，每个请求都会跑，除非你覆盖它。

### 默认策略，分步看

当一个模型有多家提供商、而你没有设置 `sort` 或 `order` 时，OpenRouter 按[提供商路由文档](https://openrouter.ai/docs/guides/routing/provider-selection)执行 3 步：

- 优先选过去 30 秒内没有显著宕机的提供商（不稳定的排到队尾，但不会被移除）。
- 在稳定的提供商中，从成本最低的候选里按价格平方倒数加权挑选。
- 其余提供商作为回退。

设置 `sort` 或 `order`，或在你的[账户设置](https://openrouter.ai/settings/preferences)里设了默认排序，就会关掉负载均衡、改按你的规则路由。都不设置，你得到的就是价格加权默认。

### 实例推演（为什么平方倒数加权重要）

下面是文档里对默认策略如何落地的实例推演。假设某模型由 3 家提供商服务：提供商 A $1/M token，提供商 B $2/M，提供商 C $3/M，而且提供商 B 近期有过宕机。

平方倒数加权意味着 A 被首先尝试的概率约是 C 的 9 倍（1/3² 让 C 的权重只有 A 的 1/9）。A 失败的话，下一个是 C。刚宕机过的 B 排最后试。

取平方这个动作会把流量用力推向最便宜的稳定选项，而不是平均摊开——所以当一家健康的 $1/M 提供商就在眼前时，你不会去付 $3/M。

OpenRouter 在生产环境里跨 70 多家提供商运行这个策略，每月处理[100 万亿 token](https://openrouter.ai)，上面那个例子就来自这份运行现实。要记住的两条规则：30 秒宕机窗口，和价格平方倒数加权。

关于这个默认还有一点要提醒：它管的是标准请求。带 tools 的请求会走 [Auto Exacto](https://openrouter.ai/docs/guides/routing/auto-exacto)——OpenRouter 面向工具调用的质量优先路由步骤，它按工具调用质量信号给提供商分层（表现最差的排到最后）并默认运行。任何显式的 `provider.sort` 或 `order` 都会跳过它，所以要让工具调用请求按价格路由，请用 `:floor` 或 `provider.sort: "price"`。

## 用 provider 对象控制路由

在请求体里加一个 `provider` 对象，你就完全覆盖了默认。整个对象在[这里](https://openrouter.ai/docs/guides/routing/provider-selection)有文档；下面这些是开发者最先伸手用的字段。

| 字段 | 作用 | 默认 |
| --- | --- | --- |
| `order` | 严格按这个顺序尝试提供商 | 未设置 |
| `allow_fallbacks` | 你指定的提供商失败时落到其他提供商 | `true` |
| `sort` | 按 `"price"`、`"throughput"` 或 `"latency"` 路由 | 未设置 |
| `only` | 限定在这个提供商白名单内 | 未设置 |
| `ignore` | 排除这些提供商 | 未设置 |
| `quantizations` | 限定特定的量化精度 | 未设置 |
| `data_collection` | 对用数据训练模型的提供商 `"allow"` 或 `"deny"` | 未设置 |
| `zdr` | 要求 ZDR（零数据保留）提供商 | 未设置 |
| `max_price` | 给可接受的每 token 价格设上限 | 未设置 |
| `preferred_min_throughput` | 优先选择高于此吞吐的提供商 | 未设置 |
| `preferred_max_latency` | 优先选择低于此延迟的提供商 | 未设置 |
| `require_parameters` | 只使用支持你请求参数的提供商 | 未设置 |

### 怎么强制指定某家提供商？

当你必须只命中某一家特定提供商（合规要求、BYOK 合同、区域约束）时，设置 order 并关掉回退。

```
{
  "model": "openai/gpt-5.5",
  "provider": { "order": ["openai", "azure"], "allow_fallbacks": false }
}
```

OpenRouter 会先试 OpenAI，再试 Azure，然后止步。它永远不会回退到你没批准过的第三家提供商。

### 排除有低质量变体的提供商

提供商的质量有好有坏，OpenRouter 对此说得很直白。有些提供商提供的模型量化得更狠，同一个模型在这家就比在别家表现差。没有一个你能用来排序或过滤的质量分数，但你可以直接把某家排除。

```
{
  "model": "meta-llama/llama-4-maverick",
  "provider": { "ignore": ["deepinfra"] }
}
```

要更精细的控制，`quantizations` 可以把范围限定在你信任的精度档位上。面对这种质量参差，这就是你可控的抓手。

### 定位特定的提供商端点

提供商 slug 按基础名匹配。像 `"google-vertex"` 这样的 slug 会匹配 OpenRouter 拥有的该提供商全部 Vertex 区域和端点。要钉住单个变体，就用完整 slug，例如 `"deepinfra/turbo"` 而不是 `"deepinfra"`。

基础 slug 是大网，完整 slug 是手术刀。

## :nitro 和 :floor 做什么

在模型后加 `:nitro` 就是为速度优化，加 `:floor` 就是为成本优化。它们是 `provider.sort: "throughput"` 和 `provider.sort: "price"` 的快捷方式，外加一点：`:nitro` 还会把[优先服务层级](https://openrouter.ai/docs/guides/features/service-tiers)的端点纳入候选，`:floor` 则纳入 flex 层级的端点。整个改动就发生在模型字符串里，连 provider 对象都不用写。

| Slug | 优化目标 | 等价于 |
| --- | --- | --- |
| `model:nitro` | 吞吐（速度） | `provider.sort: "throughput"` 加上优先层级端点 |
| `model:floor` | 价格（成本） | `provider.sort: "price"` 加上 flex 层级端点 |
| `model`（裸写） | 最便宜且可靠的平衡 | 默认价格加权路由 |

一行改动版：

```
model="meta-llama/llama-4-maverick:nitro"   # route for speed
model="meta-llama/llama-4-maverick:floor"   # route for cost
```

用户能直接感到延迟的面向用户聊天用 `:nitro`；成本才是约束的批处理作业用 `:floor`。有成本上限的工作，把 `:floor` 和 `max_price`、BYOK 经济账搭配起来用。

## 模型路由与故障转移如何配合

![模型回退示意图：claude-sonnet-4.5 的所有提供商依次失败，请求落到 gpt-5-mini](https://openrouter.ai/blog/images/model-routing-model-fallback.png)

要扛住提供商错误，配置一个 `models` 回退数组，再靠 OpenRouter 的自动提供商故障转移兜底。这里是两个机制叠加，各自作用在不同层。提供商路由让单个模型跨多家提供商存活，模型回退则处理该模型所有提供商同时失败的情况。

这已覆盖大多数提供商错误，但挡不住全站级的宕机。想更深入理解提供商故障转移与模型回退的区别以及如何测试，看 [OpenRouter failover and fallbacks explained](https://openrouter.ai/blog/insights/reliability-failover/)。

简短版：列好备用模型，剩下的交给提供商故障转移，失败的请求你不会付钱。

### 模型回退（models 数组）

按优先级传入 models。第一个出错时，OpenRouter 就试下一个。

```
resp = client.chat.send(
    model="anthropic/claude-sonnet-4.6",
    models=["openai/gpt-5.4-mini"],  # tried in order if the primary fails
    messages=[{"role": "user", "content": "..."}],
)
```

OpenRouter 各 SDK 把 `models` 当作一等字段。（用 OpenAI SDK 时通过 `extra_body` 传入，因为它是 OpenRouter 的扩展。）回退会在上下文长度错误、内容审核标记、限流和宕机时触发。计费按真正跑起来的那个模型，不按先前报错退出的。

### 提供商级故障转移（单个模型内部）

模型回退之下还有第二道安全网。在单个模型内部，如果选中的提供商返回 5xx 或对你限流，OpenRouter 会自动落到服务该模型的下一家提供商。这默认开启（`allow_fallbacks: true`），过去 30 秒内有过宕机的提供商都会被降优先级。

经济账让它值得依赖。失败的请求不计费；OpenRouter 的[零补全保险](https://openrouter.ai/docs/guides/features/zero-completion-insurance)意味着你只为真正完成的那次运行付钱。

### 故障转移覆盖什么、不覆盖什么

故障转移有一些值得知道的边界。按[流式文档](https://openrouter.ai/docs/api/reference/streaming)，中止流并不能在部分提供商上停止计费（包括 Bedrock、Groq、Google 和 Mistral），所以在这些提供商上被取消的流照样可能产生费用。

而且故障转移能绕过提供商级故障，却绕不过 OpenRouter 自身：[2025 年 8 月的宕机](https://status.openrouter.ai/incidents/wn69pKYg-WoP)（约 50 分钟的数据库事故）让整个服务都停了，回退也不例外。提供商故障转移是真实且自动的；它是韧性的一层，不是 SLA 承诺。两手都要规划。

## Auto Router，以及什么时候用它

把请求发到 `openrouter/auto`，就等于把模型选择交给了 OpenRouter 而不是你自己。适合某个提示词的最佳模型并不固定时使用，比如混合负载——有的请求需要强推理，有的只需要快速补全。当你确切知道要哪个模型时，就显式设置。

Auto Router 的[动力来自市场智慧](https://openrouter.ai/docs/guides/routing/routers/auto-router)：它先把你的提示词分类到某个任务类型，再按 OpenRouter 社区在过去滚动 7 天窗口里对这类任务的总支出来给候选排名。

### Auto Router 怎么挑

候选池跟随实时市场支出而非固定阵容；[Auto Router 文档](https://openrouter.ai/docs/guides/routing/routers/auto-router)解释了候选如何排名。调用之后，响应的 `model` 字段会告诉你究竟是哪个模型作答，你永远不用猜。

你可以通过请求设置来引导选择。`cost_tier` 决定你愿意花多少钱，从 `low`（最便宜但能干的模型）经 `medium`、`high`、`xhigh` 直到 `max`（不计价格选最强）。不设置时，路由器大致从 `low` 档位里挑。

`allowed_models` 用 `anthropic/*` 这样的通配模式把选择限制在某个提供商家族内。

```
{
  "model": "openrouter/auto",
  "plugins": [
    {
      "id": "auto-router",
      "cost_tier": "max",
      "allowed_models": ["anthropic/*", "openai/*"]
    }
  ]
}
```

价格方面，Auto Router 不收加价。选中最便宜的模型就按那个模型的标准费率付费，[和直接调用它一样](https://openrouter.ai/docs/features/model-routing)。

### Auto Router vs 手动 models 数组

两者都叫"路由"，但控制权是反转的。用 `openrouter/auto`，模型由 OpenRouter 决定。用 `models` 回退数组，顺序由你决定，OpenRouter 只在出错时照着走。

不知道用户会发什么提示词时用 Auto Router；清楚自己的模型偏好、只想在它背后垫一层韧性时用回退数组。

## 路由器 vs 网关，OpenRouter 坐在哪里

网关是统一接入点（一个端点、认证、限流、可观测性）；路由器做逐请求决策（哪个模型、哪个提供商）。OpenRouter 是你调用的网关，同时内置了决定每个请求由哪个模型和提供商处理的路由逻辑。

| 能力 | 路由器 | 网关 | OpenRouter |
| --- | --- | --- | --- |
| 逐请求的模型/提供商决策 | 有 | 只管接入 | 有 |
| 自动故障转移 | 有 | 视情况 | 有 |
| 单一统一端点 | 视情况 | 有 | 有 |
| 托管 vs 自托管 | 均可 | 均可 | 托管 |

我们的 [LLM 网关指南](https://openrouter.ai/blog/insights/llm-gateway/)完整定义了网关这一层；路由是其中的机制。想要自己运营的自托管"网关+路由器"，LiteLLM 是自己-host 的选项，OpenRouter 是直接-call 的选项。

## 常见问题

### LLM 路由如何工作？

路由器挡在你的应用与多个模型和提供商之间，决定每个请求去哪里。它管 4 件事：模型选择、提供商选择、负载均衡和故障转移。你往一个端点发一个请求，路由器选目的地。

### OpenRouter 怎么选提供商？

默认先降权过去 30 秒内有显著宕机的提供商，然后在成本最低的提供商之间按价格平方倒数加权挑选，其余留作回退。设置 `sort` 或 `order` 就会覆盖这个默认。

### LLM 路由器和 LLM 网关有什么区别？

网关是统一接入点（一个端点、认证、可观测性）。路由器做逐请求决策，决定哪个模型和提供商处理这次调用。OpenRouter 两者皆是：一个同时会做路由的、你直接调用的网关。

### 怎么让 OpenRouter 故障转移到另一个模型或提供商？

模型级回退：按优先级传 `models` 数组（在上下文长度错误、审核标记、限流和宕机时触发）。提供商级故障转移：在单个模型内部，OpenRouter 默认自动完成（`allow_fallbacks: true`）。失败的请求不计费。

### :nitro 和 :floor 做什么？

模型 slug 后加 `:nitro` 会按吞吐对提供商排序，并把优先服务层级的端点纳入候选池。加 `:floor` 按价格排序，并纳入 flex 层级端点。两者都只是模型字符串的一行改动。

### Auto Router 要额外收费吗？

不要。`openrouter/auto` 选中哪个模型，就按那个模型的标准费率付费，没有 Auto Router 附加费。
