# 我们如何为 OpenRouter 构建自校正定位系统

孙罗伯特·11/12/2026

![OpenRouter 日语主页。](https://openrouter.ai/blog/images/openrouter-in-8-languages-ja-home.png)

除了英语之外，OpenRouter 现在还支持简体中文、西班牙语、葡萄牙语（巴西）、德语、法语、日本语、한국어。从今天开始，本地化处于测试阶段。要进行切换，请从帐户菜单中选择一种语言，或直接转到 [openrouter.ai/ja](https://openrouter.ai/ja) 或 [openrouter.ai/ko/models](https://openrouter.ai/ko/models) 等地址。

![韩语 OpenRouter 模型页面，包含翻译后的过滤器、选项卡和模型元数据。](https://openrouter.ai/blog/images/openrouter-in-8-languages-ko-models.png)

翻译网站并保持翻译最新是很困难的，对我们来说尤其如此。 OpenRouter 的网站有 16,918 个英文字符串，我们每天都会更改其中一些字符串，因此一次性翻译将在一周内过时。我们构建了一个循环来帮助我们大规模地做到这一点。每天，它都会找到发生变化的字符串，进行翻译，在代码中检查它们，并让第二个模型根据英语验证其含义。当翻译检查失败或验证者拒绝它时，循环会将其发送回并附上原因并重试。重试循环是系统自我纠正的一部分。

有些错误仍然会过去，人们会发现这些错误。当审稿人和读者报告错误时，我们会将其转化为术语表规则、风格注释或覆盖，而每日审稿发现的错误也成为每个未来模型必须通过的测试用例。整个管道运行在 OpenRouter 上。

## 翻译位于代码旁边的 Git 中

在任何模型介入之前，翻译都需要一个家。我们使用开源 [General Translation](https://generaltranslation.com) 运行时在 React 代码中包装字符串。我们将翻译作为 JSON 目录提交到代码旁边，并在运行时在本地加载它们，因此请求路径中不存在任何翻译服务。字符串在合并后的一天内就会被挑选出来进行翻译。在此之前，页面显示英文源代码。每个翻译的条目还存储了它所来自的英语的指纹。当有人编辑英文时，指纹会停止匹配，并且该条目会返回到队列中。此规则允许每日运行找到每个陈旧条目，而无需重新翻译整个目录。

## 管道

该队列中的每个字符串在到达站点之前都会经过五个阶段。

![字符串如何翻译：新文本进入翻译器模型，然后代码检查，然后验证器模型，然后审阅，然后上线。失败的检查和验证者拒绝会返回给翻译者，审阅者或读者标记的修复会进入术语表。](https://openrouter.ai/blog/images/openrouter-in-8-languages-translation-loop.png)

### 1.提取

脚本扫描前端并将每个包装的英文字符串写入源目录。每个条目都记录其文件及其 UI 角色，例如按钮、标题或表格标题。这个角色很重要，因为同一个英语单词在不同的地方可能需要不同的翻译。按钮上的“队列”是一条指令，本文后面的缺陷之一是将其翻译为名词的模型。

### 2. 翻译

我们将新的和更改的字符串批量发送到 GPT-6.1 Sol，最多 40 个，并使用结构化输出来保存对严格 JSON 模式的回复。每个请求都包含我们的全局和每种语言的样式注释、批次中任何产品术语的词汇表规则以及每个字符串的 UI 角色。

以下是译者对一批日语的请求的简化示例，其中风格注释和术语表规则被缩短。
```
{
  "model": "openai/gpt-6.1-sol",
  "messages": [
    {
      "role": "system",
      "content": "Translate OpenRouter UI strings into Japanese. ..."
    },
    {
      "role": "user",
      "content": "[{\"id\":\"q1\",\"role\":\"button\",\"text\":\"Queue\"}]"
    }
  ],
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "translations",
      "strict": true,
      "schema": {
        "type": "object",
        "properties": {
          "translations": {
            "type": "array",
            "items": {
              "type": "object",
              "properties": {
                "id": { "type": "string" },
                "text": { "type": "string" }
              },
              "required": ["id", "text"],
              "additionalProperties": false
            }
          }
        },
        "required": ["translations"],
        "additionalProperties": false
      }
    }
  }
}
```
由于 OpenRouter 上的每个模型都接受相同的请求，因此尝试不同的转换器意味着仅更改模型 slug。这就是我们在本文后面进行模型比较的方式。

### 3.检查

代码会拒绝破坏 ICU 占位符、复数分支、富文本标记、前导或尾随空格或以术语表禁止的形式呈现产品术语的回复。我们以较小的片段重新发送被拒绝的批次，命名失败，默认情况下最多 4 次通过。该限制是一个最多为 20 的设置。在最后一次传递后仍然失败的字符串将保留为英语，并在拉取请求中进行标记。

### 4. 验证

对同一模型的第二次调用（充当验证者）会对照英语读取每个翻译，并按严重程度列出错误。任何严重或重大错误，例如删除的子句或颠倒的含义，都会将字符串连同迄今为止所附的所有异议发送回译者。翻译器在第一次尝试后最多可以重试 3 次，最后一次重试需要更多的推理工作。每个字符串的花费没有单独的上限，因为重试限制已经对其进行了限制。计算检查重新发送的次数，一个字符串最多可能需要四次翻译尝试，每次最多四次检查通过，并在每次尝试后调用验证程序。最坏的情况是每种语言每个字符串大约有 20 个模型调用。如果验证器关闭，管道不会写入任何内容，并且字符串仍为英文。读一天英语的读者比看未经检查的翻译的读者要好。

### 5. 回顾

每个每日批次都会作为拉取请求落地。人工智能审阅者会读取差异并发布结果，而一个人会合并拉取请求。

## 我们如何衡量

本文的其余部分依赖于三个评估套件，因此在数字开始之前了解每个套件测试的内容会有所帮助。

- **模型比较（254 个案例）** 使用不同的翻译器模型运行管道，并使用生产验证器对每个回复进行评分。我们用它来选择翻译。
- **管道比较（454 例）** 将一个模型运行两次，一次通过完整管道，一次仅使用两行提示。代码检查、验证者、来自其他三个模型系列的判断以及反向翻译检查都会对其进行评分。
- **缺陷套件（22 个案例）** 包含验证者通过后每日审查发现的真实错误。每种情况都禁止发货的错误。

## 我们尝试过但扔掉的东西

现在管道看起来很简单，因为我们在评估测量后删除了第一个设计的三个部分。

### 更便宜的翻译器

我们首先测试了一个更小、更便宜的型号，GPT-6 Luna (`openai/gpt-6-luna`)。在模型比较中，它第一次尝试就通过了 91.7% 的案例，而 GPT-6.1 Sol 则为 99.2%。最弱的语言是韩语和日语。它最严重的失败是我们的翻译框架 General Translation 无法编译的回复，例如它对“{value} 的旧别名”的翻译。每次重试时，这些失败都会持续存在。

较重型号的价格约为 3.4 倍，1.94 美元，而 254 箱则为 0.57 美元。我们支付差价是因为修复一条永远不会收敛的错误字符串比立即修复它需要更多的时间和精力。

### 单独的判断模型

在验证器存在之前，一个单独的判断模型对每个翻译进行评分，并且我们重新翻译它标记或标记为不确定的任何内容。为了看看它的工作效果如何，我们用三种字符串标记了基准：已知错误、更正的翻译（早期错误的手动修复版本，应该会通过）和干净的样本。法官确实发现了真正的问题。在一次基准测试中，它将 91% 的实际缺陷标记为不确定。它还标记了 14 个更正翻译中的 11 个和 150 个干净翻译中的 42 个，因此它送回了大量优秀作品进行重新翻译。

验证器就位后，关闭判断器会将首次通过准确率从 99.2% 降低到 98.8%，但最终结果保持不变。法官已将约 45% 的初稿发回重新翻译。我们现在默认将其保留。

### 给一个人留下硬伤

起初，验证者在每次重试时拒绝的字符串都保持未翻译状态，直到有人手动修复它。对目录进行全面重新翻译，将 16,274 个字符串翻译成 7 种语言，剩下 97 个这样的字符串 (0.09%)。现在，管道根据验证者的发现对被拒绝的草稿进行排名，提交错误最少的草稿，并将其标记在拉取请求中以供审查。循环总是以翻译结束，即使该翻译仍然带有标记的错误，并且该标记将其放在合并拉取请求的人的前面。

## 管道在裸模型上添加了什么

管道增加的大部分内容是减少彻底的错误。为了测量它，我们的评估在 454 个案例中运行相同的模型两次，一次通过整个管道，一次使用两行提示，没有样式注释、术语表或重试。裸模型返回了一个格式错误的回复，还剩下 453 对进行比较。

|测量 |裸模|完整管道 |
| --- | --- | --- |
|未通过术语表或作者检查 | 147 共 453 | 4 共 454 条 |
|第一次通过时被验证者接受 | 306 名中的 263 名通过了检查 (85.9%) | 454 项中的 448 项 (98.7%) |
|来自其他模范家庭的三位评委总结的严重错误| 203 | 203 109 | 109
|双方在整体偏好上获胜 | 117 | 117 139 | 139
|意义在回译中得以保留| 90.8% | 89.3% |

撰写的检查是针对一个评估案例的手写规则。例如，中文中的“Queue”不能翻译为“队列”，即“发货”的名词形式。检查失败次数从 147 次下降到 4 次，词汇表和重试正在发挥作用。

验证者的首次通过数据使用不同的基础。对于裸模型来说，通过代码检查的是 306 个字符串，对于管道来说，全部是 454 个字符串。验证器与翻译器来自同一模型系列，因此它的通过率告诉我们模型与自身一致的频率。我们使用 GPT-6.1 Sol 来完成这两项工作，因为它是我们测试的两个翻译器中更准确的一个。为了获得外部视图，评估还将每对未标记的翻译发送给来自其他型号系列（Claude Opus 5.5、Gemini 4 Argon 和 DeepSeek V4 Pro）的三位评委。在三位评委中，他们发现管道的输出存在 109 个严重错误，裸模型的输出存在 203 个严重错误。每个法官的错误都是单独计数的，因此所有三个法官都标记的字符串会将总数加三。

根据 453 对的总体偏好，评委们在 139 对中选择了管道，在 117 对中选择了裸模型，其中 61 对和 136 对的两个翻译是相同的。这个余量比检查失败和严重错误显示的要窄得多，因此管道的价值主要在于它消除的特定错误。

最后一行将每个回复回译为英语，并询问其含义是否仍然存在。裸模型得分为 90.8%，管道得分为 89.3%。反向翻译无法看到术语或寄存器，这是管道更改的大部分内容，因此我们将此结果视为平局。

## 反馈循环

验证者在发布之前发现了大部分错误，读者则发现了其余的一些错误。

![日语主页上突出显示的文本，带有用于发送反馈的弹出窗口。](https://openrouter.ai/blog/images/openrouter-in-8-languages-report.png)

在“语言”对话框中打开“选择报告”功能，然后突出显示所有翻译文本、添加注释并发送。每份报告均附带语言、页面和确切的文本。模型首先对其进行分类，选择四个修复程序之一，然后在几分钟内完成修复。我们的人工智能审核员会检查修复情况，并由一个人进行最终合并。

- **含义错误。** 该字符串在同一天恢复为英语，然后获得更正的翻译。
- **错误的术语。** 我们将术语与该语言的接受形式和拒绝形式一起添加到词汇表中。我们固定合规性和协议名称，例如 HIPAA、SOC 2、OAuth 和 SAML，因此管道将它们保留为英文。
- **语气或标点符号错误。** 该规则包含在该语言的风格注释中。
- **一个错误的字符串。** 精确的覆盖会固定已批准的措辞，并且以后的运行都无法更改它。

验证者通过后每日审查发现的错误将进入缺陷套件。目前已有22例。其中包括翻译为需要动词的按钮上的名词的“队列”、呈现为道路交通的“影子交通”，以及含义颠倒的 HIPAA 设置。每个案例都禁止发生错误，因此任何未来的模型、提示或术语表更改都会导致错误返回，从而导致评估失败。

## 费用是多少

当我们第一次定价时，将所有 16,274 个字符串完全重新翻译成 7 种语言，总共 113,918 个翻译，包括翻译和验证在内，价格约为 430 美元。我们通过对每种语言的生产规模批量定价并扩大规模来得出这个数字。计算得出，每种语言每个字符串的费用不到半美分。验证费用略多于一半，约为 228 美元，即每种语言每个字符串 0.002 美元。此后该目录已增至 16,918 个字符串，如今完整重新翻译的成本约为 460 美元。每日循环仅发送更改的内容，一天包含 7 种语言的 677 个更改的字符串，成本约为 18 美元。

这两个数字仅涵盖翻译和验证调用。他们忽略了构建管道的工程时间、人工智能审核员和分类模型的调用以及合并每个日常拉取请求的人员。

今天的 16,918 个字符串包含 136,429 个英语单词，因此 7 种语言总共 955,003 个单词，这使得我们的成本约为每个单词 0.0005 美元。以下是截至 2026 年 11 月 10 日，按 Smartling 和 Gengo 发布的每个字起价进行的相同完整重译。

这些是标价；企业合同是经过谈判的，机器翻译上方的每一行都包括我们的数字中遗漏的人工审核或项目管理。最接近的同类选项是 Smartling 的机器翻译，而我们的管道成本大约是 Smartling 的 6%。

## 你可以重用什么

如果您要本地化自己的产品，则可以直接继承此设计的四个部分。

- 根据英文来源对每个翻译进行指纹识别，以便陈旧的条目重新排队。
- 在任何模型审查含义之前，让代码拒绝损坏的占位符、复数分支、标签和禁用术语。
- 使用验证程序来命名每个错误及其严重性，并将这些异议发送回翻译人员。
- 将人们发现的每个错误转化为术语表规则、样式注释、覆盖或评估案例。

## 将您的反馈发送给我们

当我们处于测试阶段时，一些措辞将会被取消，修复它的最快方法是使用“语言”对话框中的“选择报告”来报告它。我们审查每份报告并将其转化为术语表规则、样式注释或覆盖。

## 常见问题

### OpenRouter 支持哪些语言？

OpenRouter 有英语、简体中文、西班牙语、巴西葡萄牙语、德语、法语、日语和韩语版本。本地化处于测试阶段。

### 如何更改 OpenRouter 上的语言？

从帐户菜单中选择一种语言，或打开本地化地址，例如 openrouter.ai/ja。

### 哪些型号可以翻译 OpenRouter？

GPT-6.1 Sol (openai/gpt-6.1-sol) 翻译每个字符串，对同一模型的第二次调用将其与英语进行验证。两者都通过 OpenRouter API 运行。

### 翻译整个网站需要多少钱？

将当今的 16,918 个字符串完全重新翻译成 7 种语言的成本约为 460 美元，其中包括翻译和验证，每种语言每个字符串的成本不到 0.5 美分。按照 Smartling 公布的机器翻译费率计算，同样的工作成本约为 7,200 美元，按照公布的人工智能和人工翻译费率计算，成本约为 57,300 美元至 191,000 美元。

### 如何报告错误的翻译？

在“语言”对话框中打开“选择报告”功能，突出显示读错的文本，添加注释，然后提交。
