# 我们如何为 OpenRouter 构建自校正本地化系统

Robert Sun ·11/12/2026

![日语版 OpenRouter 首页。](https://openrouter.ai/blog/images/openrouter-in-8-languages-ja-home.png)

除英语外，OpenRouter 现在还支持 简体中文、Español、Português (Brasil)、Deutsch、Français、日本語 和 한국어。本地化从今天起进入 beta。切换方式：在账户菜单里选一种语言，或直接访问 [openrouter.ai/ja](https://openrouter.ai/ja)、[openrouter.ai/ko/models](https://openrouter.ai/ko/models) 这类地址。

![韩语版 OpenRouter 模型页，过滤器、标签页和模型元数据均已翻译。](https://openrouter.ai/blog/images/openrouter-in-8-languages-ko-models.png)

翻译一个网站、并让译文持续保持更新，是件难事，对我们尤其如此。OpenRouter 站点有 16,918 条英文字符串，我们每天都会改动其中一部分，所以一次性翻译一周内就会过时。为此我们搭了一套循环来规模化地做这件事：每天找出变化的字符串、翻译、在代码里做检查，再让第二个模型对照英文核验语义。一旦翻译没通过检查，或被校验器驳回，循环就把它连同原因退回去重试。这个重试循环，正是系统能自我纠正的部分。

仍有一些错误会漏过去，被人发现。当审阅者和读者反馈错误时，我们把它变成术语表规则、风格说明或覆盖项；每日审查抓到的错误也会变成测试用例，往后每个模型都必须通过。整套流水线跑在 OpenRouter 上。

## 译文与代码一起放在 Git 里

在模型介入之前，译文先得有个落脚处。我们用开源的 [General Translation](https://generaltranslation.com) runtime 在 React 代码里包裹字符串，把译文作为 JSON 目录提交到代码旁边，运行时在本地加载，因此请求链路上没有任何翻译服务。一条字符串合并后一天内就会被挑去翻译，在此之前页面先显示英文原文。每条译文还存有一份它所对应英文的指纹。有人改了英文，指纹就不再匹配，该条目会重新回到队列。正是这条规则，让每日任务能找出所有过期条目，而不必重译整个目录。

## 流水线

队列里的每条字符串上线前都要经过五个阶段。

![一条字符串的翻译流程：新文本交给翻译模型，再做代码检查、校验模型、审查，最后上线。检查失败和校验驳回会退回翻译模型；审阅者或读者标记的修正会进入术语表。](https://openrouter.ai/blog/images/openrouter-in-8-languages-translation-loop.png)

### 1. 提取

脚本扫描前端，把每条被包裹的英文字符串写进源目录。每条记录都记下它所在的文件和 UI 角色，比如按钮、标题或表头。角色很关键：同一个英文词在不同位置可能需要不同译法。按钮上的「Queue」是一条指令，而本文后面提到的缺陷之一，就是有模型把它译成了名词。

### 2. 翻译

我们把新增和有变化的字符串分批送给 GPT-6.1 Sol，每批最多 40 条，并用 [Structured Outputs](https://openrouter.ai/docs/guides/features/structured-outputs) 把回复约束在严格的 JSON schema 内。每个请求都带上全局和分语言的风格说明、批次里涉及的产品术语对应的术语表规则，以及每条字符串的 UI 角色。

下面是一个简化后的翻译请求示例，针对一批日语字符串，风格说明和术语表规则做了删减。

```
{
  "model": "openai/gpt-6.1-sol",
  "messages": [
    {
      "role": "system",
      "content": "Translate OpenRouter UI strings into Japanese. ..."
    },
    {
      "role": "user",
      "content": "[{\"id\":\"q1\",\"role\":\"button\",\"text\":\"Queue\"}]"
    }
  ],
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "translations",
      "strict": true,
      "schema": {
        "type": "object",
        "properties": {
          "translations": {
            "type": "array",
            "items": {
              "type": "object",
              "properties": {
                "id": { "type": "string" },
                "text": { "type": "string" }
              },
              "required": ["id", "text"],
              "additionalProperties": false
            }
          }
        },
        "required": ["translations"],
        "additionalProperties": false
      }
    }
  }
}
```

由于 OpenRouter 上每个模型都接收同样的请求，换一个翻译模型只需改 model slug。本文后面的模型对比就是这么做的。

### 3. 检查

只要回复破坏了 ICU 占位符、复数分支、富文本标签、首尾空白，或把产品术语写成了术语表禁止的形式，代码就会驳回。被驳回的批次我们会拆小重发，并点明失败原因，默认最多 4 轮。这个上限是个可配置到 20 的设置。最后一轮仍失败的字符串保持英文，并在 pull request 里标记出来。

### 4. 校验

同一个模型的第二次调用充当校验器，逐条对照英文审阅译文，并按严重程度列出错误。凡是 critical 或 major 错误，比如漏掉从句或语义反转，都会把字符串连同迄今所有异议一起退回翻译器。翻译器在首次尝试后最多重试 3 次，最后一次重试会加大 reasoning effort。每条字符串的花费没有单独上限，因为重试次数已经把它框住了。把检查重发也算上，一条字符串最多经历四次翻译尝试、每次最多四轮检查，外加每次尝试后一次校验调用。这样最坏情况下，每种语言每条字符串约 20 次模型调用。如果校验器不可用，流水线什么都不写，字符串保持英文。让读者看一天英文，也好过看一条没校验过的译文。

### 5. 审查

每天的批次都会落成一个 pull request。AI reviewer 读 diff 并给出意见，最后由人来合并这个 pull request。

## 我们如何衡量

本文余下部分要用到三套 eval 套件，在看数字之前，先说清各自测什么。

- **模型对比（254 个案例）**：用不同翻译模型跑流水线，再用生产环境的校验器给每条回复打分。我们用它来挑选翻译器。
- **流水线对比（454 个案例）**：同一个模型跑两次，一次走完整流水线，一次只用两行 prompt。代码检查、校验器、来自另外三个模型家族的评审模型，以及回译检查都会给它打分。
- **缺陷套件（22 个案例）**：收录每日审查在校验器放行之后抓到的真实错误。每个案例都禁止再犯当初上线的那个错误。

## 我们试过又放弃的做法

如今流水线看着简单，是因为 eval 测完之后，我们把最初设计里的三块去掉了。

### 更便宜的翻译模型

我们先试了更小更便宜的 GPT-6 Luna (`openai/gpt-6-luna`)。在模型对比里，它首次通过率是 91.7%，GPT-6.1 Sol 是 99.2%。它最弱的语言是韩语和日语，最棘手的失败是翻译框架 General Translation 编译不了的回复，比如它对 “Legacy alias of {value}” 的翻译，这类失败每一轮重试都照旧出现。

较重的模型成本大约是 3.4 倍：这 254 个案例上 $1.94 对 $0.57。我们愿意付这个差价，因为一条始终收敛不了的错误字符串，修起来比一开始就做对更费时费力。

### 单独的评审模型

在校验器出现之前，有一个单独的评审模型给每条翻译打分，凡是它标记或有疑问的，我们都重译。为了看效果，我们给一套基准标了三类字符串：已知错误、修正后的译文（早先错误的人工修复版，本应通过）、以及干净样本。评审模型确实抓到了真问题：某次基准运行里，它把那轮 91% 的真实缺陷标成了不确定。但它同时也标了 14 条修正译文里的 11 条、150 条干净样本里的 42 条，把大量好结果退回去重译。

有了校验器之后再关掉评审模型，首次通过准确率从 99.2% 降到 98.8%，最终结果没变。此前评审模型把约 45% 的初稿退回去重译。现在我们默认把它关掉。

### 把难处理的字符串留给人

起初，被校验器每轮重试都驳回的字符串会一直不翻译，直到有人手工修好。一次全量重译——16,274 条字符串译成 7 种语言——留下了 97 条这样的字符串（0.09%）。现在流水线会按校验器的意见给被驳回的草稿排序，提交错误最少的那条，并在 pull request 里标记出来供审查。循环总会以一条译文收尾，哪怕它仍带着被标记的错误，而这个标记会把它摆到合并 pull request 的人面前。

## 流水线相比裸模型多了什么

流水线带来的好处，大部分是更少的硬错误。为了量化，我们让同一个模型在 454 个案例上跑两遍：一遍走完整流水线，一遍只用两行 prompt，不带风格说明、术语表和重试。裸模型返回了一条格式错误的回复，因此剩 453 对可比。

| 指标 | 裸模型 | 完整流水线 |
| --- | --- | --- |
| 未通过术语表或手写检查 | 147 / 453 | 4 / 454 |
| 首轮即被校验器接受 | 通过检查的 306 条中 263 条（85.9%） | 全部 454 条中 448 条（98.7%） |
| critical 错误，三个来自其他模型家族的评审模型合计 | 203 | 109 |
| 整体偏好上各方胜出的对数 | 117 | 139 |
| 回译后语义保留 | 90.8% | 89.3% |

手写检查是针对单个 eval 案例写的规则。例如中文里的「Queue」不能译成「队列」——当初上线的就是那个名词形式。检查失败从 147 降到 4，正是术语表和重试起了作用。

校验器的首轮数字基数不同：裸模型是那 306 条通过代码检查的字符串，流水线则是全部 454 条。校验器和翻译器同属一个模型家族，所以它的通过率反映的是模型与自己意见一致的频率。两项工作我们都用 GPT-6.1 Sol，因为它是我们测过的两个翻译器里更准的那个。为了有外部视角，eval 还会把每一对译文去掉标签，送给另外三个模型家族的评审模型：Claude Opus 5.5、Gemini 4 Argon 和 DeepSeek V4 Pro。三个评审模型合计在流水线的输出里发现 109 个 critical 错误，在裸模型的输出里发现 203 个。每个评审模型的错误单独计数，所以一条被三个都标记的字符串会给总数加三。

在 453 对的整体偏好上，评审模型有 139 对选了流水线、117 对选了裸模型，61 对打平，还有 136 对两条译文完全相同。这个差距比检查失败数和 critical 错误数体现出来的窄得多，所以流水线的价值主要体现在它消掉的那几类具体错误上。

最后一行把每条回复回译成英文，再看语义是否保留。裸模型得 90.8%，流水线得 89.3%。回译看不到术语和语域，而这恰恰是流水线改动最多的地方，所以我们把这个结果当成平局。

## 反馈闭环

校验器在上线前拦下大部分错误，读者再补上剩下的一部分。

![日语首页上被选中的文本，以及针对它发送反馈的弹窗。](https://openrouter.ai/blog/images/openrouter-in-8-languages-report.png)

在 Language 对话框里打开 select-to-report，然后选中任意译文、加一句说明、发送。每条反馈都带着语言、页面和确切文本一起送达。模型先做分诊，从四种修正里选一种，几分钟内把修正提上去。我们的 AI reviewer 检查这个修正，最后由人完成合并。

- **语义错误。** 该字符串当天先回退成英文，随后拿到修正后的译文。
- **术语错误。** 我们把该术语连同这一语言里认可的形式和要拒掉的形式一起加进术语表。像 HIPAA、SOC 2、OAuth、SAML 这类合规和协议名称，我们会固定住，让流水线保持英文不译。
- **语气或标点错误。** 规则写进该语言的风格说明。
- **单条字符串出错。** 用一条精确的覆盖项固定已批准的措辞，之后再跑也不会改动它。

每日审查在校验器放行之后抓到的错误，会进入缺陷套件，目前有 22 个案例。其中包括把需要动词的按钮上的「Queue」译成名词、把 “shadow traffic” 译成道路交通、以及一处语义被反转的 HIPAA 设置。每个案例都禁止再犯当初上线的错误，因此往后任何模型、prompt 或术语表的改动只要把它带回来，eval 就会失败。

## 成本

我们第一次核算时，把全部 16,274 条字符串重译成 7 种语言、共 113,918 条翻译，含翻译和校验约 $430。这个数字是按每种语言用生产规模的批次定价、再放大推出来的，算下来每种语言每条字符串不到半美分。校验略高于一半，约 $228，即每种语言每条字符串 $0.002。此后目录涨到 16,918 条，如今做一次全量重译约 $460。每日循环只送变化的部分，某天 7 种语言共有 677 条字符串变动，成本约 $18。

这两个数字只覆盖翻译和校验调用，不含搭建流水线的工程时间、AI reviewer 和分诊模型的调用，以及每天合并 pull request 的人。

如今 16,918 条字符串共含 136,429 个英文词，7 种语言合计 955,003 词，折算下来我们的成本约每词 $0.0005。下面是同样一次全量重译，按 Smartling 和 Gengo 公布的词单价起价计算，截至 2026 年 11 月 10 日。

| 方案 | 单价 | 整站，7 种语言 |
| --- | --- | --- |
| 我们的流水线，翻译与校验 | 每词约 $0.0005 | 约 $460 |
| Smartling Machine Translation | 每词 $0.0075 | 约 $7,200 |
| Smartling AI Translation | 每词 $0.06 | 约 $57,300 |
| Gengo Standard | 每词 $0.09 | 约 $86,000 |
| Smartling AI Human Translation | 每词 $0.12 | 约 $114,600 |
| Gengo Advanced | 每词 $0.18 | 约 $171,900 |
| Smartling Human Translation | 每词 $0.20 | 约 $191,000 |

这些都是标价；企业合同另议，而且上面除机器翻译外的每一行都含人工审校或项目管理，我们的数字没把这部分算进去。最接近同类可比的是 Smartling 的机器翻译，我们的流水线成本大约是它的 6%。

## 可以复用的部分

如果你也在给自己的产品做本地化，这套设计里有四块可以直接搬过去。

- 给每条译文按它的英文原文算指纹，让过期条目自己重新入队。
- 在任何模型审阅语义之前，先让代码拦下坏掉的占位符、复数分支、标签和禁用术语。
- 用能点明每个错误及其严重程度的校验器，并把这些异议退回给翻译器。
- 把人抓到的每一个错误，都变成术语表规则、风格说明、覆盖项或 eval 案例。

## 向我们提反馈

beta 期间难免有些措辞不到位，最快的修法是在 Language 对话框里用 select-to-report 反馈。我们会看每一条反馈，把它变成术语表规则、风格说明或覆盖项。

## 常见问题

### OpenRouter 支持哪些语言？

OpenRouter 提供英语、简体中文、西班牙语、巴西葡萄牙语、德语、法语、日语和韩语版本。本地化处于 beta。

### 如何切换 OpenRouter 的语言？

在账户菜单里选一种语言，或打开 openrouter.ai/ja 这类本地化地址。

### 哪些模型负责翻译 OpenRouter？

GPT-6.1 Sol (openai/gpt-6.1-sol) 翻译每条字符串，同一个模型的第二次调用对照英文校验。两者都通过 OpenRouter API 运行。

### 翻译整个站点要花多少钱？

把如今 16,918 条字符串全量重译成 7 种语言，含翻译和校验约 $460，即每种语言每条字符串不到半美分。同样的工作按 Smartling 公布的机器翻译费率约 $7,200，按公布的 AI 与人工翻译费率约 $57,300 到 $191,000。

### 如何反馈一条糟糕的译文？

在 Language 对话框里打开 select-to-report，选中读着不对的文本，加一句说明，提交即可。
