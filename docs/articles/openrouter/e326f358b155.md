# Agent 模型的成本-质量权衡框架

OpenRouter · 2026-10-01

按排行榜名次给 agent 选模型，会为那些便宜模型以同等准确率就能完成的任务支付前沿价。要回答的问题不是"哪个模型得分最高"，而是"对于你眼前的任务，能满足要求的模型里最便宜的是哪个"。

本指南是一个三步框架，帮你做出这个判断：先定下任务所需的质量线，再在你自己的样本上测量"每质量分的成本"，最后选择以足够裕量越过质量线的最便宜模型。

## Tl;dr

- 在比较模型之前，先给每个任务定质量线。低于质量线的模型无论多便宜都出局。
- 用一个便宜档、一个中档和一个前沿档模型跑 20 到 50 个你自己的样本，用同一份 rubric 打分，再用成本除以得分，得到每质量分成本。
- 选择越过质量线、且超出幅度大于你观测到的跨运行分数波动的最便宜模型。
- 成本直接读每个响应的 `usage.cost` 字段，而不是拿标价乘以估算 token 数。
- 当候选模型或其价格变化时重跑比较。

## 排行榜名次不会告诉你的事

排行榜把模型在一系列与你毫无关系的任务上的结果做了平均。代码排名第一的模型，在你的结构化数据抽取任务上未必第一；一个在推理基准上不起眼的中档模型，回答你的 FAQ 流量可能已经好过你的要求。

Agent 任务往往很窄，例如给工单分类、抽取一个字段、或在模型没把握时升级处理。便宜模型在窄任务上能否达到与前沿模型相同的准确率，这是一个测量问题，排行榜不会替你测。

Agent 的成本也不止一问一答。一次 chat completion 只计一次费，而一个 agent 为每次工具调用、每个中间步骤、每次重试都要付费。一个三步循环在返回答案前至少按 token 单价付了三次钱。如果你按排行榜名次选，就可能为一个便宜模型以同等准确率就能处理的任务，重复支付三倍的价。

## 第 1 步：定义任务所需的质量线

在比较任何东西之前，先决定"够好"对这个任务意味着什么。每件事的线都不同，而它是之后每一步都要通过的过滤器。

如果错误答案是负担——合规、医疗或法务审查即是如此——就把线定高，接受更高的单请求成本。如果任务是大批量客服或聊天，总体结果比任何单次响应更重要：一个能正确解决 90% 日常请求、并把剩下 10% 干净升级出去的便宜模型，对该任务可能可以接受。线定在哪里由你决定，框架负责对它测量。

延迟敏感的工作，如欺诈检测和实时聊天，会加上第三个约束。一个又便宜又准但慢到不满足任务的模型，在轮到成本和准确率说话之前就已经出局。

速度、成本和准确率无法同时最大化。确定你的任务有哪些约束，候选列表就收窄了。

如果你不确定一个任务落在哪里，一个起点是所有任务先跑中档模型，然后按测量暴露出的问题把任务分流：中档模型大材小用的任务移到更便宜的；达不到线的任务升档。让测量决定每个任务需要哪一档，而不是一开始拍脑袋。

## 第 2 步：在你自己的样本上测量每质量分成本

拉取你的 agent 实际会遇到的文档、工单和 prompt。用你自己的流量，不用公开数据集，也不用基准样例。重点是对你的任务做测量。

用一个便宜选项、一个中档选项和一个前沿选项跑这些样本，用同一份一致的 rubric 打分。对分类这类确定性任务，与标准答案做精确匹配（exact match）——恰好只有一个正确值时适用。对开放式任务，用 LLM 作为 judge 给质量打分，我们的 [LLM-as-a-judge 指南](https://openrouter.ai/blog/tutorials/llm-as-a-judge-evaluate-ai-agents/)讲解如何搭建。当所有候选返回同一形态的输出时打分更容易，这正是 [structured outputs 与 `response_format`](https://openrouter.ai/docs/guides/features/structured-outputs)的用途。

把模型的每 1,000 次请求成本除以其质量得分，你就得到一个可在候选之间、在不同规模测试集之间直接比较的"每质量分成本"。用一个短脚本执行：只换模型字符串，并从每个响应的 `usage` 对象读取单请求成本。如 [usage accounting 文档](https://openrouter.ai/docs/cookbook/administration/usage-accounting)所述，我们在每个非流式响应以及每个流式响应的最后一条消息里返回 `usage` 对象，无需任何额外请求参数。`usage.cost` 就是该请求向你账户收取的美元金额。OpenAI Python SDK 会保留它未定义的响应字段，因此 `r.usage.cost` 可以作为属性访问。

```
import json
import os

from openai import OpenAI

client = OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key=os.environ["OPENROUTER_API_KEY"],
)

ROUTING_PROMPT = open("routing_prompt.txt").read()
test_set = json.load(open("test_set.json"))  # 20-50 of your own {"ticket": ..., "label": ...} examples

candidates = [
    "openai/gpt-5.6-luna",
    "google/gemini-3.7-flash",
    "anthropic/claude-opus-5",
]

for model in candidates:
    total_cost, correct = 0.0, 0
    for ex in test_set:
        r = client.chat.completions.create(
            model=model,
            messages=[
                {"role": "system", "content": ROUTING_PROMPT},
                {"role": "user", "content": ex["ticket"]},
            ],
        )
        total_cost += r.usage.cost
        answer = (r.choices[0].message.content or "").strip()
        correct += int(answer == ex["label"])

    score = correct / len(test_set)
    points = score * 100
    cost_per_1k = total_cost / len(test_set) * 1000
    cost_per_point = cost_per_1k / points if points else float("inf")
    print(f"{model}: score={score:.0%}  cost/1K=${cost_per_1k:.2f}  cost/point=${cost_per_point:.4f}")
```

响应可能不带任何文本内容（例如模型拒绝回答时），脚本会把缺失内容当作空答案、计为错误，并把它产生的成本计入总额。得分为零的模型没有每质量分成本，脚本为它打印 `inf` 而不是除以零。

下面是一个客服路由任务的演算示例。假设每个请求约发 700 个输入 token（工单加一段简短的 system prompt）、返回约 150 个输出 token。每 1,000 次请求的成本为 `(700 / 1M × 输入价) + (150 / 1M × 输出价)`，再乘以 1,000。每质量分成本就是该成本除以质量得分。

价格取自 2026-09-18 [模型目录](https://openrouter.ai/models)中 [GPT-5.6 Luna](https://openrouter.ai/openai/gpt-5.6-luna)、[Gemini 3.7 Flash](https://openrouter.ai/google/gemini-3.7-flash) 和 [Claude Opus 5](https://openrouter.ai/anthropic/claude-opus-5)的标价，即目录列出的模型级价格。各个 provider endpoint 以及 flex 和 priority [service tiers](https://openrouter.ai/docs/guides/features/service-tiers)按各自费率计费，且 GPT-5.6 Luna 对 prompt token 达到或超过 272,000 的请求按更高费率计费。token 数量和质量得分仅为示意，你实际跑出的数字会取而代之。

按框架运行的顺序读这张表。第一步先用质量线做闸门。线定在 85% 时，GPT-5.6 Luna 以 82 出局，它每质量分成本低也就无所谓了——低于线的模型无论每分多便宜都不合格。剩下 Gemini 3.7 Flash 和 Claude Opus 5。

在两个过线者中取更便宜的：Gemini 3.7 Flash 每 1,000 次请求 $1.09，而 Claude Opus 5 要 $7.25，买到的却是任务并不需要的分数。Gemini 3.7 Flash 是选择，且它以 4 分的裕量过线。

情境一变，答案就变。如果一次误路由意味着错过 SLA、你把线定在 95%，那么只有 Claude Opus 5 过线，你就付这个 $7.25。目标不是挑最高分，而是知道哪个模型花最少的钱越过你的线，并看清当你伸出手去够线以上时，你为此支付的差距。

## 第 3 步：选择以裕量越过质量线的最便宜模型

选以裕量过线的最便宜模型，而不是选综合排名第一的模型。裕量之所以重要，是因为数字会动。

provider 更新权重时模型得分会漂移，你自己的流量会随时间变化，新版本会改变格局。裕量应由观测设定，而不是拍一个固定百分比。把候选跑不止一遍，或跨一个新的流量切片跑，记录分数在运行之间的波动幅度，并要求胜出者越过质量线的幅度大于那个观测波动。

一个只在单次小样本上勉强达线的模型，应当先越过一个更高的内部目标值，你才正式采用它——这样常规波动才不会在生产中把它压到线以下。

## 模型或价格变化时重跑比较

新模型发布得很勤，既有模型的价格也会变。2026 年 5 月到 9 月间，我们的目录加入了四个 Gemini Flash 版本：Gemini 3.5 Flash（2026-05-19）、Gemini 3.6 Flash（2026-07-21）、Gemini 3.7 Flash（2026-08-13）和 Gemini 3.8 Flash（2026-09-02）。你几个月前跑的比较可能已经过时，所以每当候选更新或调价就重跑一次。

在我们这边，重跑成本很低。我们暴露一个 OpenAI 兼容 API，换模型只是改配置：base URL、key 和 SDK 都不变。把模型字符串从 `openai/gpt-5.6-luna` 改成 `anthropic/claude-opus-5`，上面的脚本就跑在新模型上了。

你不必为每个想测试的 provider 写一个新集成——这正是让你能在新模型发布的当周就拿自己的样本重跑的前提。同样这一行的替换，也是多 agent 架构中[模型路由](https://openrouter.ai/blog/insights/model-routing/)所依赖的。

有两件事让框架扎在真实数字上。我们在你做出承诺之前就在[模型目录](https://openrouter.ai/models)展示按模型定价，你的比较在成本一侧从实时数据出发；而由于每个响应都报告 `usage.cost`，你测量的支出就是我们实际计费的钱，不是价目表估算。

## 常见问题

### AI 模型的成本与质量权衡是什么？

它是"一个请求花多少"与"模型在你的任务上表现多好"之间的权衡。速度是第三个约束：又便宜又准但慢得不适合任务的模型仍然出局。选模型意味着决定任务需要多少质量、并为那个付费，而不是为能买到的最高分付费。

### AI agent 最好的模型是哪个？

没有唯一的最佳模型。适合某个 agent 的模型取决于它的任务要越过什么质量线、要在什么延迟内响应、要处理多大量。能过合规审查线的模型，比客服分诊这类任务所需的花费更高；而便宜到适合分诊的模型，可能过不了合规审查的线。

### agent 工作负载如何计价？

我们目录中的文本模型列出每 token 的 prompt 费率和 completion 费率。部分 endpoint 还列出缓存输入、reasoning token、每请求费用，以及 flex 或 priority service tiers 的费率。Agent 工作负载在首个请求之上还有工具调用和重试，所以单次补全的 token 价格会低估一次任务的成本。请在完整的 agent 运行上测量成本，并从每个响应的 `usage.cost` 读取。

### 多 agent 设计比单 agent 更贵还是更便宜？

取决于工作怎么切分。多 agent 设计可以把路由和分类交给便宜模型，只在确实需要的请求上调用更贵的模型，这比把所有请求都发给贵模型省钱。但它也增加了请求数，所以要测量整个运行，而不是假设切分一定省钱。

## 结论

定义质量线，在你自己的样本上测量完整运行，选择以大于跨运行波动的幅度过线的最低成本模型。保留脚本和样本集，以便在模型、价格或流量变化时重跑比较。
