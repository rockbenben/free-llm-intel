今天，我们推出 Mercury Edit 2：一款专为现代开发工作流中最延迟敏感的环节——下一个编辑预测（next-edit prediction）——而构建的 diffusion LLM（dLLM）。该模型升级了我们此前的下一个编辑模型，并与现有的自动补全端点形成互补。

Mercury Edit 2 根据你的近期编辑和代码库上下文，预测你接下来要改什么。由于它使用 diffusion 并行生成 token，建议到达的速度快到让人感觉它是你自己思考的一部分。按下 Tab 即可采纳。

## 我们如何训练模型

为了训练这个模型，我们精心整理了一份覆盖多种语言和场景的高质量编辑数据集。这些样本教会模型如何把编辑历史和代码库上下文解读为一条有针对性的下一个编辑建议。模型虽然强大，但我们也发现它在编辑的频繁程度和长度上会过于积极，对用户造成干扰。

为了解决这个问题，我们通过记录模型收到的显式反馈（接受还是拒绝某个编辑），收集了一份高质量的人类偏好数据集。基于这份数据集，我们利用一种名为 KTO 的非配对强化学习方法，使模型与人类偏好对齐。我们发现这一步对提升模型的实用性很重要。

结果很明确。新模型的编辑被采纳的次数高出 48%，凸显了这一改进的价值；它展示编辑的选择性也提高了 27%，带来更有针对性、更少干扰的编辑。

## 与其他模型的对比

下一个编辑建议必须既高质量又快速。为了衡量质量，我们在三个开源基准（[Instinct](https://huggingface.co/datasets/continuedev/instinct-data)、[Fill-in-the-middle (FIM)](https://github.com/openai/human-eval-infilling) 和 [Next-edit Prediction (NEP)](https://github.com/lurf21/NextEditPrediction)）以及一个内部下一个编辑基准上测试模型。FIM 通过针对修改后的代码运行测试用例来验证编辑。其余三个基准使用 LLM-as-a-judge，基于所提编辑与人工撰写的 gold-standard 答案之间的相似度判断正确性。这套基准覆盖多种编辑场景，如行补全、变量重命名、重构、功能实现等等。最终的质量指标取四者的平均。速度方面，我们测量在一组具有代表性的请求上的端到端延迟。为便于比较，我们还基准测试了若干定制的 next-edit 模型以及 speed-optimized 的前沿模型。我们发现，*Mercury Edit 2 在质量和速度两方面都优于其他方案*。
