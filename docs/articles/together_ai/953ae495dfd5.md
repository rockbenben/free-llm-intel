MiniMax M3 是一个多合一模型，集最先进的编码性能、agentic 工作流支持与原生多模态推理于一体。在这些能力之上，它还被设计为支持 1M 上下文，同时服务起来高度经济。这使它很适合真实世界任务——长文档、代码库、工具使用、图像和迭代推理常常一起出现、且大量占用上下文。与上一代相比，服务 M3 带来更多挑战：新能力要求在更多维度做优化，包括稀疏注意力计算、更大的 KV 缓存管理、多模态处理等。

## 架构 / 特性

M3 最新颖的架构变化是 MiniMax 稀疏注意力（MSA），专为解决 MiniMax M2.7 中看到的注意力计算瓶颈而设计。其块稀疏注意力机制限制每个 query 最多可注意的 token 数，降低长上下文处理成本、让长得多的上下文窗口变得可行。这带来 prefill 阶段超过 9 倍、decode 阶段超过 15 倍的加速。

本质上，MSA 的计算由两部分组成：先做 score 计算，为每个 KV 组确定最值得注意的 K 个 block，然后在 query token 与这些 block 之间做密集注意力。这一设计沿 KV 组维度保留表达力的同时，仍然限制单个 query token 注意的 KV token 上限。注意力计算本身不再随上下文长度按 N^2 扩展，因此非常适合长上下文负载。

我们在 B200 上、并发 8、agentic 风格流量形态（60k 前缀缓存）下测量了 kernel 执行时间分解：MSA 大幅降低了每轮迭代中实际注意力计算所占的墙钟时间比例。

在 60K 前缀缓存、并发 8、NVIDIA B200 的 agentic 风格流量下，另一个独立的 kernel 执行分解同样显示 MSA 显著减少了每轮迭代花在注意力计算上的墙钟时间占比。

除注意力架构变化外，M3 还随附带视觉组件的多模态支持，以及新的图像和视频预处理功能。

鉴于这些根本变化，Together AI 与 MiniMax 工程团队紧密合作应对新出现的挑战。主要挑战包括：

- 尽管 MiniMax 稀疏注意力计算本身高效，从工程角度支持 1M 上下文长度仍具挑战。
- 视频与图像处理天然比文本 tokenize 复杂得多。

## 优化

### KV-Block-Major 稀疏注意力

prefill 期间，对长上下文输入注意力计算仍可能是一个大因素：对每个 token，我们要计算 Selected *Block* × *KV Head Group* × *Tokens*。块稀疏注意力的本质允许多个 query 注意相同的 key-value block。因此，如果我们逐个 query 迭代、与 KV block 计算注意力，就会重复 GPU 上从 HBM 到 SRAM 的 KV 搬运。把 KV 组放在外层循环迭代、内层循环计算 query token 之间的注意力，能带来更好的算术强度——因为 KV 缓存只搬运一次。

为此，我们需要把 {q, kv block} 的映射重组为 {kv block, q} 并重新实现注意力 kernel。由于对某个 kv block 我们只计算部分 O 输出，需要基于 Log-Sum-Exp 的最终 "reduction" 来重标定输出 O 并求和。

### 将 MSA 集成进 Paged Attention

在现代推理引擎中，paged attention 常用于管理请求的 KV 缓存上下文。大多数高度优化的注意力 kernel 写死了对特定 page size 集合的支持。阻碍我们使用这些 kernel 的问题是：不同 KV 组选中的 block 不一样。

在 Together AI，我们提出一种把 MiniMax 稀疏注意力集成进引擎的新方法。decode 期间，我们先基于选中的 block 构建 page table，把 KV-group 维度展平进 batch 维度，并利用 KV 缓存张量的 strided view 为注意力 kernel 提供检索 KV page 所需的指针。诀窍在 stride：page 地址按 D 递进选择虚拟 page 起点，而 token 按 Hkv * D 递进。这将一个物理张量解交织成每头独立 page，于是每个展平行都能使用不同的 page table。

这一设计让我们能直接使用现有支持 GQA 的注意力 kernel，而无需从零重写一个支持稀疏注意力的新 kernel。由于每个 query 选中的 block 有限，为 block 到 page 查找映射的 kernel 开销极低。这个设计给 decode 吞吐带来 5% 的提升。

### Decode Index Scoring Kernel 优化

decode 时，MSA 把大量成本从密集注意力移入 score/top-k 索引器。对每个 decode query，引擎将 query 侧索引向量与候选 key 侧索引向量比较，把每个 128 token 的 KV block 归约为单一分数，只保留 top block 给真正的注意力 kernel。这个扫描位于每个生成 token 的关键路径上，而在长上下文下，候选 block 数随上下文长度增长。Decode scoring 的形状是小 query index、长 key index。把一批 decode query 当成一个更大 GEMM 处理很诱人，但 score/indexing 这一步不只是密集矩阵乘：每个请求和每个 K 组有自己的候选 block 范围、掩码、逐 block 归约和 top-k 边界。把 query 拼接起来仍会留下 GEMM 周围参差的 gather-and-reduce 问题，还会把 padding 和额外簿记强加到关键路径上。我们的优化路径因此使用 *AB 交换的 HMMA 布局*：128 token 的 key-index block 成为 MMA 的 M 维度，query 侧只 pad 进更小的 *N* 维度。kernel 用异步拷贝为 128 token K 索引做 staging、预取下一页、用 HMMA 以 bfloat16 计算点积，并把每页归约为一个 block 分数。

### 网关处的多模态预处理

SMG（Serving Model Gateway）是一个基于 Rust 的模型网关，位于 OpenAI 兼容 API 与推理引擎之间。除路由和 tokenize 外，SMG 承担一个对多模态模型特别重要的角色：在请求抵达 GPU worker 之前，在 CPU 上完成全部视觉预处理。

图像和视频输入在对视觉编码器有用之前需要相当多 CPU 工作：下载、解码、抽帧、缩放、转换为 patch 张量。在推理引擎内部做这些会占用本应用于生成的资源。SMG 在网关处处理这一切，请求命中 GPU 时张量已经就绪。

对 M3，这意味着：取视频、用 FFmpeg 抽帧、按 FPS（每秒帧数）选择子集、缩放归一化，然后把时间维度烤进去做 patchify。产出是一个扁平 patch 张量和一个小 grid 元数据张量，打包进 gRPC 消息。Worker 只需直接运行视觉编码器——其端不做预处理。

此外，SMG 的多模态流水线围绕 Rust traits 组织，把模型专属预处理逻辑与流水线管道分离。加入 M3 多模态支持只是用 M3 专属常量实现这些 traits；流水线本身没有改动。同一套架构适用于多数具备视觉能力的开源模型，并跨推理引擎运行时泛化。

自收到 MiniMax M3 权重与模型架构以来，我们全力以赴提升推理性能。在常见 agentic 形态流量的各并发级别上，我们达到了 81%–125% 的提升。

## 未来工作

新架构带来新基础设施与工程挑战。在 Together AI，我们的目标是提供最好的推理性能。关于 M3 我们正在积极推进的若干主题：
 1. 稀疏注意力架构引入了更多小型 kernel，例如 kv block 上的 topk、把 q-kv 映射重组为 kv-q 等，还有更多 kernel 融合机会。我们的 Kernel Agent Research 团队正在积极开发能写生产级 kernel 的 agent。
