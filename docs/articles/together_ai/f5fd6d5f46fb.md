## 摘要

一家全球金融科技公司通过 Together 的 Dedicated Model Inference 在 GLM 5.2 上运行其编码助手，应对静态容量规划根本跟不上其节奏的、尖峰化的工程时段流量。

有了 DMI，客户的工程师自己扩展 endpoint、发布模型、测试变更——不用提工单、不用等 Together。结果是：基础设施跟采用它的团队一样快。

## 工作负载

这位客户向几十个市场的数百万用户交付金融产品，增长毫无放缓迹象。要维持这个速度，首先是一个工程问题——公司的工程师正依靠 AI 编码 agent 来做到这一点。

这把推理放上了公司交付速度的关键路径，而不只是藏在某一个面向客户的功能里。工作负载运行 GLM-5.2——那只为长程编码和 agentic 工作打造的 mixture-of-experts 模型——在 Together 上服务。流量跟着工作日走：尖峰、集中在工程时段，而且每有一个团队把 agent 纳入工作流就再攀高一截。

## 约束：容量规划跟不上采用速度

### 运维掌控

这位客户在与其他推理提供商合作跑编码工作负载之后找到 Together，先整合到我们早期的 dedicated 产品上。那个产品能用，但不是为这种工作负载的实际行为设计的。编码助手流量不是平稳的：它是峰值负载、相对低 TPS，集中在工程时段，并随更多团队把 agent 放进日常工作流而在并发和 prompt 尺寸上出现剧烈突发。这个形态正是工作负载迁移到 GLM-5.2 时，把并发（而非原始吞吐）作为设计优先级的原因。

在早期的模式下，吸收这种突发意味着得有人提前预见到它。准备好把 agent 纳入日常工作流的团队常常在**等**容量而不是**开通**容量，客户的平台团队替每一个团队吸收协调工作——提交请求、估算集群规模。团队尽力提前规划，但当采用在时间和规模上都变得不可预测时，规划就失效了。你无法预测由一百个工程团队各自独立决定"本周更用力地依赖编码 agent"所驱动的突发。

当容量按昨天的预测开通、而流量真实地尖峰时，prefill 容量和 KV 缓存余量恰好在突发期间——最需要它们的时刻——被耗尽，产生 agentic 编码工作流无法容忍的数分钟级请求排队。事后修复，与把"看见负载并提前扩容"的能力交给客户自己的团队，是协调问题与基础设施问题之间的区别。

## 客户要求：自助、可观测、并发

客户围绕自主性（而不只是原始性能）对 Together 团队提出要求，而工作负载自身的形态说明了原因。编码助手流量的 ISL p50/p90/p95 约为 81K/163K/178K token，RPS p50/p90/p95 为 3/6/7——一个峰值负载、相对低 TPS 的模式，并发突发远比原始每秒 token 数重要。这就是客户向 Together 提出以下要求的背景：

- **自助开通**：一个工程团队应该能自己建起 endpoint 并把流量打上去，不用提交请求、不用等平台组。这是相对早期模式的转变——过去每个新团队的容量请求都要经过 Together 和客户平台团队两级。
- **自己的团队能行动的可观测性**：使用和性能数据以编程方式可得，让容量决策落在做决策的团队手里，而不是在缓存命中率劣化之类的情况下被路由进支持队列。
- **集中负载下的吞吐与快速扩容**：在工作时段峰值期间保持持续性能，而不是基准测试条件下的表现——在 256K 上下文下跨多副本配置运行数十块 B200，规模专门按保住并发余量设计。
- **模型流动性**：随前沿推进更换模型的空间，无需重新谈判——实践中已由同一账号上从 GLM 5.1 到 GLM 5.2 的迁移证明，外加一次对缓存与负载均衡参数做的调优——那是配置更新，不是重新部署。

## **交付了什么：完整的 endpoint 控制权、一个指标 API 和模型流动性**

### 通过 API、UI 或 CLI 配置 endpoint

Dedicated Model Inference 暴露完整的 endpoint 生命周期：创建、定容、扩容策略和配置变更。客户的基础设施团队在一次迁移重塑其 GLM 5.2 endpoint 时正好用了这套能力——转向更少、更大的副本：总占用不变，副本数与每副本芯片数的比例变了。几天后这个重塑撞上接近 100% 的 prefill 容量，请求排队一到三分钟、decode 吞吐跌到约每秒 5 token 时，修复方案不是新部署、也不是给 Together 提工单，而是一次在线配置变更：恢复调优过的"会话感知缓存路由"策略，替换 DMI 默认的"按 hash 缓存感知"策略，并放宽 max-inflight-per-worker 阈值。全部当天推送、零停机。

### 指标 API

以编程方式访问 endpoint 使用与性能数据，正是找到根因的办法。Together API Support 团队通过指标数据端到端追踪了一个 192 秒的慢请求，发现它不是计算受限——几乎整段时间都排在来自其他请求的 230 万 token 的 pending-prefill 积压之后，而不是因为它自己的 25 万 token prompt。这就是自助可观测性的具体价值：客户自己的团队诊断出一个**排队问题**而非**容量问题**，无需等 Together 拉日志。

### 快速访问丰富的模型库

Dedicated Model Inference 让用户自助获取前沿开源模型，还提供性能感知的配置，帮助客户在 TTFT、TPS、TPM 等指标之间任选组合。随着编码 agent 用法的演化，客户团队与 Together 的前置部署工程师紧密合作，持续优化这些配置。

这体现为 GLM 5.1 到 GLM 5.2、以及上下文长度迭代都在同一账号和 endpoint 模式上完成迁移，全程无关约谈判。也体现为客户团队自己做的一次深思熟虑的配置取舍：基于其流量画像，他们评估了一个 1M 上下文的配置并**拒绝**了它，因为把上下文翻倍到 1M 会削减其峰值负载、低 TPS 工作负载真正依赖的并发余量。团队选择留在 256K/512K。

## 时间线：从早期负载测试到规模化生产 endpoint

编码助手的合作关系比 GLM 5.2 生产 endpoint 早了几个月。Together 的 Solutions Architecture 团队此前已建成模拟客户真实使用模式的专用负载测试基础设施，最初对着更早的 GLM 版本做了验证。

这块铺路石直接带入了 GLM 5.1。早期，客户的项目负责人在周末要求对 GLM 5.1 在 8 到 16 块 B200 上做一个清单式的并发测试，明确面向编码用例、区别于此前面向消费者、关注延迟的测试。Together 当天交出了测试 endpoint，GLM 5.1 达标并进入生产：两个专用 endpoint，按访问权限划分，作为客户面向内部开发者的编码助手运行。

- **转向 GLM 5.2：** 客户把编码工作负载迁移到 GLM 5.2，生产 endpoint 开始以 256K 上下文、56 块 B200（14 副本 × 4 B200）运行它，为匹配客户峰值负载、相对低 TPS 的流量形态，优先并发而非原始吞吐。
- **自助迁移到 DMI：** Together 的 CX 团队把客户的 GLM 5.2 endpoint 迁移到 DMI 自助平台，把扩容、自定义权重发布和蓝绿测试的控制权交给客户，Together 的 SA/FDE 团队待命支持任何性能调优。

## 结果

### 改配置或发布模型更新的时间

在 DMI 之前，改配置或加容量意味着要走 Together 的流程：提交请求、估算集群、等重新部署。每个想采用 agent 的工程团队都往这同一个队列里加人，客户的平台团队最终替整个组织做协调。

在 DMI 上，整个流程内化了：

- **扩容：** 客户直接调整容量，不用给 Together 提工单。
- **自定义权重发布：** 新模型版本上线无需重新部署周期。
- **蓝绿测试：** 客户按自己的时间表，对照生产流量验证变更。

## 下一步：第二个工作负载与区域

这次部署不再是一个 endpoint，而开始成为一个创新平台。这个模式正在作为一条流水线而非一次性项目复制。客户团队已在规划一个新区域里的专用 GLM 5.1 节点，按真实生产负载定容。它的工作负载形态与最初的编码助手不同：一个聊天式的客服 NLP 工作负载，而非长程 agentic 编码——落在同一套基础设施和开通模式上。
