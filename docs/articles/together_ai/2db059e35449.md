# 大规模推理基准测试：编码 Agent

## 摘要

在真实生产编码 agent 工作负载上，Together Inference Engine 在相同硬件上比第二快的开源引擎多交付 **31% 的 TPS**，并在饱和点保持 **2 倍更优的 TTFT**。这些收益来自全栈优化：ThunderMLA、定制 kernel 重写，以及在真实流量上的端到端 profiling。

多数推理基准测试度量的是单个用户打一个专属 endpoint。数字很好看。但它们对推断生产表现毫无用处。

生产环境里，你运行的是数十乃至数百个并发请求。它们竞争同一份 KV 缓存、同一条内存带宽、同样的 GPU 周期。重要的是当系统承压时每个用户的遭遇。我们构建这个基准就是为了回答编码 agent 的这个问题。这是一种对推理压力很大的工作负载：长输入、高并发、对负载下的延迟劣化零容忍。

这是第一版。随着我们继续构建，我们会持续更新。

## 编码 Agent 工作负载长什么样

编码 agent 的请求携带大量上下文：正在编辑的文件、周边代码、对话历史、检索到的片段。输入很长。输出有意义但有边界——你生成的是一函数，不是一篇文章。

更难的挑战是并发。许多用户同时打到 endpoint 上，这些请求之间的相互作用是单用户基准永远捕捉不到的。随着流量增加，KV 缓存被填满，调度压力上升，每用户吞吐下降，首 token 时间（TTFT）攀升。到某个点，系统不再有用。不同的引擎在截然不同的流量水平到达那个点。

我们设计了一个高流量基准来拷问这一点，建模自我在服务大规模生产编码 agent 流量时观察到的请求分布。Prompt 长度约从 45k 到 200k token，模拟真实编码会话的增长；生成长度平均约 450 token。关键指标是 TPM（每分钟输入 token）、每用户 TPS（每秒 token）和 p50 TTFT。

## 推理必须做对什么

对编码 agent，TTFT 是决定工具"感觉快"还是"坏掉了"的指标。开发者提交请求后，在第一个 token 到来之前什么也看不到。这段"提交到出流"之间的空窗，就是赢得或失去信任的地方。输出速度也重要，但居其次：token 一旦开始流动，即使生成速率中等，体验也是流畅的。

第二个约束是长上下文下的并发。编码 agent 请求不只是长——它们长*且*同时。数十位开发者同时打同一 endpoint，各自携带 80k+ token 的上下文，造成单用户基准永远不会暴露的 KV 缓存压力。随着缓存填满，调度器腾挪空间变小。Prefill 延迟上升，TTFT 劣化。在足够高的流量下，系统在正式失败之前就已不再有用。

第三个约束是输出形态。你生成的是一函数，不是一篇文章。生成长度有界——平均约 450 token——这意味着饱和点的吞吐在这里与摘要或文档生成类工作负载看起来不同。系统承受的不是持续的 decode 压力，而是持续的 *prefill* 压力，外加频繁的短促 decode 突发。为长 decode 运行优化的引擎在这里未必赢。

这三条约束——TTFT 敏感、并发长上下文负载、prefill 为主的输出形态——正是这个基准要拷问的东西。

## 方法学

**硬件：** 每个引擎 4× NVIDIA B200（SGLang：8× B200——见下方说明）。

**工作负载：** 长 prompt、高并发、真实的会话流动。Prompt 长度约从 45k 到 200k token，模拟真实编码会话增长。生成长度平均 450 token（p50：293，p99：2,230）。难度随流量上升：更高 QPS 下，更长的 prompt 和不断增长的 KV 缓存制造更多 prefill 压力、更多需要维护的上下文，以及随会话流动加剧的 KV 缓存颠簸。

**EAGLE 推测解码：** 3 个草稿 token。接受率（约 70%）从真实的合成 prompt 数据中自然涌现——我们没有人为设定。

**引擎配置：** TensorRT-LLM 对这种工作负载调优良好，是一个强基线。SGLang 已尽可能对齐配置；我们没有做穷尽的调优实验，所以可能存在有限的改进空间。所有引擎都配置为低延迟。这与吞吐优化配置不同——后者会增大最大 decode 批大小、使用 prefill-decode 分离，用输出 TPS 换更高输入 TPM。

## 我们优化了什么

我们的性能收益来自把推理当作全栈问题来处理：端到端 profiling、识别最昂贵的操作，然后逐个消灭它们。

**ThunderMLA。** Kimi K2.5 使用 DeepSeek 的多头潜在注意力（MLA）架构。标准实现每个 decode 步骤要发起两次独立 kernel。我们的 [ThunderMLA](https://hazyresearch.stanford.edu/blog/2025-03-04-thundermla)——ThunderKittens kernel 库的一部分——把它们融合为一个 megakernel，消除启动开销和两者之间的尾部效应。在代表性 decode 工作负载上，ThunderMLA 比 DeepSeek 自家的 FlashMLA 快 20–35%。

在 ThunderMLA 之外，我们对全栈做了 profiling——驱动行为、内存布局、kernel 执行——并移除发现的每一个瓶颈。有些只需要配置修改，有些则需要从头写 kernel。我们写的 kernel 在这份工作负载上超过了 TensorRT-LLM 的开源同类实现。

## 结果

我们在 Kimi K2.5 上加 EAGLE 推测解码，把 Together Inference Engine 与两个基线对比：

- **TensorRT-LLM** —— 4 块 NVIDIA B200 GPU
- **SGLang** —— 8 块 NVIDIA B200 GPU

**关于 SGLang 的说明：** 在 SGLang 上以 TP4 运行 Kimi K2.5 + EAGLE 会内存溢出——在这个模型上 SGLang 的 EAGLE 实现比 TensorRT-LLM 需要更多内存。我们用 TP8（8 块 GPU）跑通了它。TensorRT-LLM 和 Together Inference Engine 跑在 4 块 GPU 上。

在每 GPU 625 TPM（总 2.5M TPM）时，Together Inference Engine 比 TensorRT-LLM 多交付 31% 的 TPS，并且是唯一 TTFT 仍在 1 秒以内的引擎。

### 劣化曲线

曲线的形状比任何单个数据点更重要。每个推理引擎最终都会饱和：KV 缓存填满、调度压力增大、TTFT 攀升。引擎之间的差别在于这一切何时发生、有多快。

在 2.5M TPM 时，每个引擎都已超出舒适区间：

| 引擎 | GPU 数 | p50 TTFT |
| --- | --- | --- |
| **Together IE** | 4 | **0.71s** |
| TensorRT-LLM | 4 | 1.1s |
| SGLang | 8 | 5.1s |

在 2.5M TPM 下度量。

在所有引擎都在劣化的流量水平上，Together IE 的 TTFT **比 TensorRT-LLM 好 2 倍**、**比 SGLang 好 3 倍**。系统有更多余量：在其他引擎已不可用的负载下仍然可用。
