# 我们在 Together AI 如何做 agent evals

对我们的文档、skills 和 API 错误信息做的小修复，把任务完成率从 67% 提升到了 96%。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6afa9c3ab2afb145aa0ddad7_how-we-make-it-easy-for-agents-to-use-together-ai-hero.png)

- 作者：Hassan El Mghari、Sam Barrowclough、Zain Hasan、Mo King

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6afa9c3ab2afb145aa0ddad7_how-we-make-it-easy-for-agents-to-use-together-ai-hero.png)

今年早些时候，我们开始看到越来越多开发者用 coding agents 基于 Together AI 构建应用。

原因不难看出：开发者要手工把一个应用接到生产推理上，可能要花上几天甚至几周，尤其是刚接触这个平台的人。但对于使用我们 SDK 和 CLI 的 agent 来说，只需要几分钟——至少理论上是这样。

实践中，我们并不知道指向我们平台的 agents 能否高效地与 Together 协作，也不知道它们是否在撞障碍、钻牛角尖或直接失败，并在过程中浪费 token。

随着开发者把越来越多工作交给 agents，开发者体验（DX）正日益等同于 agent 体验（AX）。你的软件越容易被 agents 使用，开发者就越容易把它接入自己的产品和工作流。

GitHub 就是 AX 出色的教科书案例：平台上的活动在过去一年增长了两倍，2026 年约 40% 的 PR 由 agents 发起（而且我们敢打赌，在所有提交中它们写的代码行数远不止 40%）。这要归功于 GitHub 出色的 API、CLI 和文档，它们让 agents 用起来格外容易。*（本文作者在 agents 开始替他使用 GitHub CLI 之前，甚至不知道它有 CLI，而现在他大概每天要用 1000+ 次）。*

为了提升 Together AI 的 AX，我们需要一种方法来衡量我们的平台对 agent 到底有多友好。本文将介绍我们如何运行 agent evals、它们暴露出的两个问题及我们的修复，以及我们学到了什么。

## 我们在 Together 如何运行 agent evals

### 构建任务清单

在开始评估之前，我们需要知道 agents 实际被要求做什么……这样我们才能，怎么说呢，判断它们能不能做到。我们开始整理一份开发者在 Together 上常做的任务清单，比如跑一个批量推理作业、搭建一个语音 agent，或者管理推理 endpoint 的自动扩缩容。

所谓 *task*，其实就是一个 prompt，也就是你会让 agent 去做的一件事——例如：

> 列出可用的 GPU 集群区域和实例类型，打印出最便宜的选项，并给出你将以按需方式预留它一小时所会执行的确切命令。不要真正预留。

要通过这项 eval，agent 必须：

- 找到最新的价格信息。
- 调用 regions API endpoint 列出可用区域。
- 把两者结合起来找到最便宜的选项。
- 生成一条用于创建集群的有效 CLI 命令。

这个 prompt 同时要求可用性和价格，却没提这些细节分别存在于两个不同的地方。这很真实：普通用户大概事先并不知道每条信息在哪里，这很容易让人和 agents 都栽跟头。

### 三种配置

整理好任务清单后，我们用三种方式各跑一遍：

- **Baseline：** agent 只拿到 prompt，没有任何特殊配置，模拟普通开发者的工作流。它可以使用所有默认工具，比如从网上抓取文档，但我们不给它任何特定的 MCP connectors 或 skills。
- **MCP：** agent 通过我们的 MCP server 直接访问我们的[文档](http://docs.together.ai/)，这样它遇到障碍时就知道该去哪里查。
- **Skills：** 我们把 [Together skill package](https://github.com/togethercomputer/skills) 交给 agent，其中包含使用我们服务的说明和示例，专门为 agents 编写。

### 运行矩阵

每次完整评估都会用三个模型，把每个任务对每种 agent 配置各跑一遍，每个任务两次尝试——因此每种配置下每个任务共六次尝试，如下方我们 9 月 30 日的运行结果所示：

![9 月 30 日使用 Opus 5.5、Sonnet 5.5 和 GPT-6.1 Sol 运行的 12 个任务在 baseline、MCP 和 skills 配置下的通过率表，每个单元格六次尝试。大多数单元格为 6/6。例外是 vision（baseline 5/6，skills 3/6）、GPU clusters（baseline 0/6，MCP 5/6）、shadow traffic（baseline 3/6，MCP 4/6，skills 5/6）、autoscaling（baseline 4/5，skills 3/6）和 observability（baseline 4/6）。](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af776b4aabea401e8bc832d_02%20%C2%B7%20chart%20%C2%B7%20run%20matrix%20sep%2030%20%C2%B7%201200x675.png)

Agents 在 215 次计分运行中通过了 192 次。GPU cluster 任务在所有 baseline 运行中都失败了，却在所有 skills 运行中都通过了。

### 自动化运行

刚开始搭建 evals 时，所有事情都是手工做的：打开一个新终端，把 prompt 粘贴进 Claude Code，让 agent 自己干活（或者干不成活），然后对每种配置重复一遍。这既手工又枯燥，所以一旦想清楚系统的形态，我们就开始自动化。

现在我们把每个 agent 放在 [Together sandbox](https://docs.together.ai/docs/together-code-sandbox) 里运行，这样它们不会干扰我们的本地环境，也不会互相干扰。GitHub Actions 负责环境准备、启动 agent、事后清理并保存结果，而一个 proxy 负责处理 agent 发往 Together API 的请求并记录活动，让我们能看到 agent 调用了哪些 endpoints、返回了什么。

### 给运行打分

一次运行结束后，一个 LLM judge 会审阅任务 prompt 和记录的会话，然后给出三种判定之一：

- **Pass：** 任务的每项要求都满足了。
- **Incomplete：** agent 尝试了任务，但部分必需步骤未完成或未验证。
- **Fail：** agent 过早放弃、违反了明确约束，或者给出了错误结果（RIP）。

失败和未完成的判定并不一定告诉我们问题出在 agent、API 还是缺失的证据上。它们只是告诉我们该从哪里开始查。

我们也会调查通过了的运行。agent 往往能绕过令人困惑的响应仍然完成任务，这些“脱困”过程正好告诉我们该修什么来提升 token 效率。

为了让这种审查可行，我们做了一个结果查看器，用来比较不同模型和配置的表现。对每次运行，它会显示 prompt、agent 用过的工具、收到的响应以及任何 API 活动：

![gpu-clusters 任务的 eval 结果查看器截图：6 次运行，通过率 67%。Baseline 2 次中通过 0 次，MCP 2/2，skills 2/2。skills 运行平均 44 秒、6 次工具调用、19.58 万 input tokens、花费 $0.16；baseline 则为 1 分 21 秒、13 次工具调用、34.58 万 tokens、$0.26。](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af776ef7db21f2dd0cedc66_05%20%C2%B7%20diagram%20%C2%B7%20results%20viewer%20%C2%B7%20gpu-clusters%20config%20comparison%20%C2%B7%201200%20wide.png)

## 案例一：GPU cluster 定价

还记得前面那个 GPU cluster 任务吗？

> 列出可用的 GPU 集群区域和实例类型，打印出最便宜的选项，并给出你将以按需方式预留它一小时所会执行的确切命令。不要真正预留。

看起来挺简单，但去年初夏跑 evals 时，Sonnet 4.6 在这个任务上 15 次尝试只通过了 4 次，即使启用了 skills 也是如此。

我们的复盘发现，失败的运行里出现了同一个模式：Sonnet 把我们 CLI 参考中的示例输出（只列了一个区域和两种 GPU 类型）当成了实时库存。它还跳过了区域查询，在从未查看定价页的情况下，直接说出它认为最便宜的选项。

问题出在我们这边。首先，示例输出没有明确标注，因此没有任何东西提示 agent 去运行命令获取相关数据。其次，我们的 skill 文件链接到的是 GPU clusters 的营销页，而不是价格表，所以 Sonnet 打开了营销页，没看到任何真实价格，就只好尽力猜一个最便宜的 GPU。

能力更强的模型能绕过这个问题。同一时期，Opus 4.8 用相同配置 14 次尝试通过了 13 次。根据 transcript，它注意到 `list_regions` 的响应里没有价格，于是一直搜索，直到在我们的文档里找到。这就是为什么用能力较弱的模型测试产品至关重要；如果我们只用 Opus 测试，发现这个缺口可能要花长得多的时间。

### 隔离失败

为了修复它，我们把 GPU clusters skill 从完整 skill package 中抽出来，隔离出这个失败，并写了一个更窄的 prompt，只复现这一个问题。用旧 skill 文件测试时它每次都失败，于是我们有了可靠的复现步骤（使用旧 skill）和测试每个新版本的简单办法（更新 skill）。

我们迭代了好几轮，最后落到一个小改动：在 skill 里加两句话，把 agent 指向价格表，并说明如何结合实时的 regions API 使用它：

> 查询 GET <https://api.together.ai/v1/compute/regions>，或运行 tg clusters list-regions --json，获取实时的区域库存、支持的实例类型以及兼容的 CUDA/driver 组合。打开 GPU Cluster 价格表查看当前的按需与预留价格。

改动之后，在我们测试的所有使用 skills 配置的模型上，这个任务的通过率都是 100%。

### 发现 API 中的缺口

同一个 GPU 任务还暴露了我们 API 中的一个问题。在最近一次 baseline 运行中，Opus 5.5 得到了 incomplete 判定，transcript 显示它撞上了两个并不是模型的错的死胡同。

运行一开始很顺利。agent 调用 `/v1/compute/regions` 获取区域和实例类型。接着，为了找价格，它调用了 `/v1/compute/instance-types`，API 返回 400 和这条消息：

> Region is required. Example: us-central-8. Use /v1/clusters/regions to get list of regions.

于是 agent 按照错误消息所说的去做：

- 它用第一次查询得到的区域重试了请求。结果拿到的不是实例类型，而是一个 `404`。
- 它调用了错误所建议的 `/v1/clusters/regions`……但这个路由并不存在，于是又得到一个 `404`。

我们自己的错误消息把 agent 送到了一个不存在的路由，而本应能成功的重试也失败了。开发者如果照着这条消息手工操作，同样会被卡住。我们随后修复了错误消息，让它指向 `/v1/compute/regions`，并修好了第一个 `404` 背后的路由 bug。

## 案例二：重建我们的 skill package

我们过去维护 14 个独立的 Together skills，每个产品面一个。用起来很痛苦：你必须事先知道哪些 skills 适用于你的工作流，然后逐个安装和调用。这些 skills 还互相重叠，重复同样的 SDK 指南和设置说明，而且每个都足够长，同时加载几个就会把 agent 的上下文撑大。

上个月，我们把这 14 个 skills 合并成了一个[统一版本](https://github.com/togethercomputer/skills)。它在底层仍然是模块化的：为避免上下文膨胀，agent 先读一个简短的 router，然后只在 router 说相关时才打开对应的产品指南、参考文件或示例脚本。

我们希望一个 skill 能胜过 14 个，但为了确认，我们在启用 skills 的情况下，把统一 skill 跑了一遍 eval 任务。我们的基准是 9 月 30 日的结果：使用 14 个 skill 配置的所有运行通过率为 90%。

但新 skill 表现很糟——72 次运行只通过 54 次（75%），未完成的有 18 次（而不是 7 次），每次运行的成本还翻了一倍多。

于是我们翻遍 eval transcript，只改运行结果指向问题的地方。有三个问题反复出现：

- **上下文太多：** 最初的统一 router 约 14,000 字符，每个任务都要加载，而且它让 agents 把每份指南完整读一遍。（说好的避免上下文膨胀呢……）运行最终加载的 skill 内容比使用 14 个独立 skills 时多了 57%。我们把 router 削减到 6,000 字符以内，并在每份产品指南末尾加一个菜单，简要说明每份参考和脚本分别包含什么，让 agents 只打开需要的部分。
- **过时的产品信息：** 代码示例里用到的一些模型已不再在 serverless 上提供服务，还有一份产品指南覆盖了已废弃的功能。agents 浪费时间在恢复或重试永远不会成功的请求上。我们把每个示例都换成确认可用的 live 模型，让 agents 去查 catalog 而不是重试，并创建了一个 cloud agent，根据产品变化自动更新 skill。
- **示例代码里的 bug：** 脚本中的小问题，比如把 JPEG 字节存成 `.png` 文件名，会让每一个使用它们的 agent 翻车。我们在源头修好了这些问题，并增加了定期实测代码示例、让它们保持新鲜的自动化。

修好这些之后，统一 skill 在 72 次运行中通过了 70 次，比我们第一次尝试高出 22 个百分点，也比最初的 14 个 skills 高出 7 个百分点。运行平均耗时还比原来的 skills 少 20%，每次运行的成本也回落到最初水平。

![六张柱状图，对比最初的 14 个 skills、第一次统一迭代和最终的统一 skill。通过率：90.3%、75.0%、97.2%。未完成率：9.7%、25.0%、2.8%。平均耗时：11.6、10.2、9.3 分钟。平均 tokens：134 万、113 万、119 万。平均轮数：19.7、21.2、19.1。平均每次运行成本：$0.431、$0.898、$0.433。](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af776d2bd15d856ebedb67b_03%20%C2%B7%20chart%20%C2%B7%20eval-driven%20skill%20development%20%C2%B7%201200x675.png)

第一版统一 skill 把通过率拉低到 75%，每次运行成本翻倍。经过 evals 找出的修复后，最终版本以原来的成本通过了 97.2% 的运行。

## 四个月 evals 之后，我们处在什么位置

回到 6 月，我们的文档和 skills 对 agents 几乎没什么帮助。6 月 15 日，使用 Opus 4.8 时，baseline 通过了 75% 的运行。文档 MCP（67%）和 skills（75%）都没有提升表现。

到 9 月 30 日，在三个模型上，baseline 已爬升到 82%。文档 MCP 达到 96%，skills 达到 90%，而新的统一 skill 在 10 月 8 日达到了 97%。

这不是受控对比——各次快照使用的模型和任务不同，所以其中一些提升无疑来自底层模型的改进，以及我们对 CLI 和 SDK 的改进。这大概能解释 baseline 上涨的 7 个百分点，但引导式配置上涨了 20 多个百分点，我们把额外这部分归功于 evals 挖出的文档和 skills 修复。

![agent eval 通过率的分组柱状图。Baseline：6 月 15 日 75%，9 月 30 日 82%。Docs MCP：6 月 15 日 67%，9 月 30 日 96%。Skills：6 月 15 日 75%，10 月 8 日使用最终统一 skill 时 97%。](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7775a2ec14c42c5d85e20_04%20%C2%B7%20chart%20%C2%B7%20pass%20rates%20by%20config%20%C2%B7%201200x675.png)

从 6 月到秋季，docs MCP 的通过率上涨 29 个百分点，skills 上涨 22 个，而 baseline 上涨 7 个。各次快照使用的任务、模型和 skill 版本不同。

## 我们学到了什么

如果你只是略读本文，这里是 TL;DR：

- **agent 可访问性提升使用量：** 像 GitHub 那样：开发者在 web GUI 上手工能做的一切，也应该能从你的 CLI 或 SDK 以编程方式完成。我们发现 agents 和 CLI 配合最好，因为 CLI 通过 help 文本自我说明。说到这个——
- **文档是产品的核心部分：** 如果你的平台没有被准确记录，或者文档不易被获取（例如通过 llms.txt、skill package 或 MCP server），那么它对 agents 就可能不可用。CLI help 文本和 API 错误消息也算，而这些通常是 agent 卡住时最先看的地方。
- **引导比用哪个前沿模型更重要：** 9 月 30 日，三个模型（Claude Sonnet、Opus 和 GPT Sol）的最终成绩彼此相差只有几分。加上我们的文档/skills 后，通过率分别从 82% 提到 96% 和 97%。
- **反过来，只用强模型有时会掩盖问题：** Opus 能绕过我们 API 和 skill package 中的缺口，而 Sonnet 一头栽了进去——我们正是这样发现并修好问题的。跑 evals 时，一定要覆盖能力谱系上的各种模型。
- **改进 AX 往往只需要一个小修复：** 在 skill 文件里加两句话，就让我们的 GPU cluster eval 从（Sonnet 的）15 次通过 4 次变成三个模型全部 100%。修复很小，但如果不是通过 eval 流程，我们可能永远发现不了。

## 运行你自己的 evals

如果你在运营一个开发平台，agents 正在用你的产品，至少它们肯定在尝试用。弄清效果如何的最好办法，是搭建自己的评估系统。

为此，我们正在开源用来构建 evals 的 package。你创建一份任务清单（agent prompts），并决定如何给运行打分（用代码测试或 LLM judge）。这个 package 会启动 agents、运行任务，并在本地 dashboard 中追踪一切，让你可以比较不同配置和过往运行。它将于下周发布，同时还会有一篇关于如何使用它的博客文章。
