# 我们如何在 Together AI 进行代理评估

对我们的文档、技能和 API 错误进行的小修复将任务完成率从 67% 提高到 96%。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6afa9c3ab2afb145aa0ddad7_how-we-make-it-easy-for-agents-to-use-together-ai-hero.png)

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6afa9c3ab2afb145aa0ddad7_how-we-make-it-easy-for-agents-to-use-together-ai-hero.png)

今年早些时候，我们开始看到越来越多的开发人员使用编码代理与 Together AI 进行构建。

不难看出原因：开发人员可能需要几天甚至几周的时间才能手动连接应用程序以进行生产推理，特别是如果他们是该平台的新手。但对于使用我们的 SDK 和 CLI 的代理来说，只需要几分钟——至少在理论上是这样。

在实践中，我们不知道指向我们平台的代理是否能够有效地与 Together 合作，或者他们是否遇到障碍、陷入困境或彻底失败，并在此过程中浪费代币。

随着开发人员将更多工作委托给代理，开发人员体验 (DX) 越来越成为代理体验 (AX) 的代名词。您的软件越容易让客服人员使用，开发人员就越容易将其构建到自己的产品和工作流程中。

GitHub 是伟大 AX 的教科书示例：过去一年，平台上的活动增加了两倍，代理在 2026 年打开了约 40% 的 PR（而且，我们愿意打赌，在所有提交中编写了超过 40% 的代码行）。这要归功于 GitHub 出色的 API、CLI 和文档，所有这些都使得代理使用起来异常简单。 *（这位作者甚至不知道 GitHub 有 CLI，直到代理开始为他使用它，现在他可能每天使用它 1000 多次）。*

为了改进 Together AI 的 AX，我们需要一种方法来衡量我们的平台的代理就绪程度。在这篇文章中，我们将介绍如何运行代理评估、他们发现的两个问题以及我们如何修复它们，以及我们学到了什么。

## 我们如何在 Together 上运行代理评估

### 建立任务列表

在我们开始评估之前，我们需要知道特工实际上被要求做什么……这样我们就可以，你知道，弄清楚他们是否可以做这些事情。我们开始构建开发人员在 Together 上处理的常见任务列表，例如运行批量推理作业、构建语音代理或管理推理端点的自动缩放。

通过“任务”，我们实际上只是指提示，即您告诉客服人员要做的事情，例如：

> 列出可用的 GPU 集群区域和实例类型，打印最便宜的选项，并显示您将运行以按需保留一小时的确切命令。实际上不要保留它。

要通过评估，代理必须：

- 查找最新的定价信息。
- 调用区域 API 端点以列出可用区域。
- 将两者结合起来找到最便宜的选择。
- 生成用于创建集群的有效 CLI 命令。

该提示询问可用性和定价，但没有提及这些详细信息位于两个不同的地方。这是现实的，因为普通用户可能事先并不知道每条信息所在的位置，这很容易让人类和代理都陷入困境。

### 三种配置

建立任务列表后，我们以三种方式运行每一项：

- **基线：** 代理仅收到提示，无需特殊配置，反映了普通开发人员的工作流程。它可以使用所有默认工具，例如从网络获取文档，但我们没有为其提供任何特定的 MCP 连接器或技能。
- **MCP：** 代理可以通过我们的 MCP 服务器直接访问我们的[文档](http://docs.together.ai/)，因此它知道在遇到障碍时确切地知道在哪里进行搜索。
- **技能：** 我们为代理提供[Together 技能包](https://github.com/togethercomputer/skills)，其中包含专门为代理编写的使用我们服务的说明和示例。

### 自动化运行

当我们开始构建评估时，我们手动运行所有操作：打开一个新终端，将提示粘贴到 Claude Code 中，让代理执行其操作（或无法执行其操作），然后对每个配置重复。这是手动且乏味的，所以一旦我们弄清楚了我们想要的系统的形状，我们就开始将其自动化。

现在，我们在 [Together sandbox](https://docs.together.ai/docs/together-code-sandbox) 中运行每个代理，这样它们就不会干扰我们的本地环境或相互干扰。 GitHub Actions 处理设置、启动代理、随后清理并保存结果，而代理则处理代理对 Together API 的请求并记录活动，因此我们可以看到代理调用了哪些端点以及返回了什么。

### 得分

运行结束后，LLM法官会审查任务提示和录制的会话，然后指定以下三个裁决之一：

- **通过：** 满足每项任务要求。
- **不完整：** 代理尝试执行任务，但某些必需的步骤未完成或未经验证。
- **失败：** 代理提前放弃、违反显式约束或产生不正确的结果 (RIP)。

失败和不完整的判决并不一定能告诉我们问题是否出在代理、API 或丢失的证据上。他们只是告诉我们从哪里开始寻找。

我们也调查传球。代理通常可以解决令人困惑的响应并仍然完成，这些恢复向我们展示了如何修复以提高令牌效率。

为了使该审查切实可行，我们构建了一个结果查看器，用于比较不同模型和配置的执行情况。对于每次运行，它都会显示提示、代理使用的工具、返回的响应以及任何 API 活动：

## 案例研究 1：GPU 集群定价

还记得之前的 GPU 集群任务吗？

> 列出可用的 GPU 集群区域和实例类型，打印最便宜的选项，并显示您将运行以按需保留一小时的确切命令。实际上不要保留它。

看起来很简单，但当我们去年夏初进行评估时，即使启用了技能，Sonnet 4.6 也仅通过了 15 次尝试中的 4 次。

我们的事后分析揭示了失败运行中的相同模式：Sonnet 处理我们的 CLI 参考中的示例输出，其中列出了单个区域和两种 GPU 类型，就好像它是实时清单一样。它还跳过了区域查找，并在没有检查定价页面的情况下命名了它认为最便宜的选项。

问题出在我们这边。首先，示例输出没有正确标记，因此没有任何信息告诉代理运行命令来检索相关数据。其次，我们的技能文件链接到 GPU 集群营销页面而不是定价表，因此 Sonnet 打开营销页面，没有看到任何实际价格，只是尽力猜测可用的最便宜的 GPU。

更强大的模型能够解决这个问题。在同一时期，Opus 4.8 使用相同的配置通过了 14 次尝试中的 13 次。根据记录，它注意到“list_regions”响应不包含价格，因此它继续搜索，直到在我们的文档中找到它们。这就是为什么使用能力较差的模型来测试您的产品至关重要；如果我们只使用 Opus 进行测试，我们将需要更长的时间才能找到差距。

### 隔离故障

为了解决这个问题，我们通过从完整的技能包中提取 GPU 集群技能来隔离故障，并编写了一个更窄的提示来仅重现此问题。每次针对旧技能文件进行测试时都会失败，因此我们有可靠的重现步骤（使用旧技能），以及测试每个新版本的简单方法（更新技能）。

我们经历了几次迭代，直到做出了一个小改变：技能中的两个新句子将代理指向定价表，并解释了如何将其与实时区域 API 一起使用：

> 查询 GET <https://api.together.ai/v1/compute/regions> 或运行 tg cluster list-regions --json 以获取实时区域清单、支持的实例类型和兼容的 CUDA/驱动程序对。打开 GPU 集群定价表，了解当前的按需费率和预留费率。

进行此更改后，我们使用启用技能的配置测试的所有模型的任务都在 100% 的时间内通过了。

### 寻找我们 API 中的差距

同样的 GPU 任务也在我们的 API 中出现了问题。在最近的基线运行中，Opus 5.5 得到了不完整的结论，记录显示它遇到了两个死胡同，但这不是模型的错。

跑步开始顺利。代理调用“/v1/compute/regions”来检索区域和实例类型。然后，在查找价格时，它调用 `/v1/compute/instance-types`，API 返回 400 并包含以下消息：

> 地区为必填项。示例：us-central-8。使用 /v1/clusters/regions 获取区域列表。

因此，代理执行了错误指示它执行的操作：

- 它使用第一次查找的区域重试请求。它得到的不是实例类型，而是“404”。
- 它名为“/v1/clusters/regions”，这是错误建议的路由……但该路由不存在，因此它得到了另一个“404”。

我们自己的错误消息已将代理发送到不存在的路由，并且本应有效的重试也失败了。如果开发人员手动跟踪该消息，也会同样陷入困境。此后，我们修复了错误消息以指向“/v1/compute/regions”，以及第一个“404”后面的路由错误。

## 案例研究 2：重建我们的技能包

我们曾经维护 14 项独立的 Together 技能，每个产品表面一项。它们使用起来很痛苦：您必须提前知道哪些技能适用于您的工作流程，然后安装并调用每一项。这些技能也有重叠，重复相同的 SDK 指导和设置说明，而且每项技能都足够长，串联加载其中一些可能会使代理的上下文变得臃肿。

上个月，我们将这 14 项技能合并为一个[单一统一版本](https://github.com/togethercomputer/skills)。它在底层仍然是模块化的：为了避免上下文膨胀，代理首先读取一个简短的路由器，然后仅在路由器表示相关时才打开每个产品指南、参考文件或示例脚本。

我们希望一项技能能够击败 14 项技能，但为了确保这一点，我们在启用技能的情况下通过评估任务运行统一技能。我们的酒吧是 9 月 30 日的结果，使用 14 技能配置的所有运行的通过率为 90%。

但这项新技能却失败了——它只通过了 72 次运行中的 54 次（75%），还有 18 次不完整，而不是 7 次，而且每次运行的成本是原来的两倍多。

因此，我们梳理了评估记录，仅在运行指出问题的地方更改了技能。三个问题不断出现：

- **上下文太多：** 第一个统一路由器大约有 14,000 个字符，加载到每个任务上，它告诉代理完整阅读每个指南。 （避免上下文膨胀就这么多了……）运行最终加载的技能内容比 14 项单独技能多了 57%。我们将路由器的字符数减少到 6,000 个字符以下，并在每个产品指南的末尾添加一个菜单，简要描述每个参考和脚本包含的内容，以便代理仅打开他们需要的内容。
- **过时的产品信息：** 代码示例中使用的一些模型不再在无服务器上提供，并且一个产品指南涵盖了一项已弃用的功能。代理浪费时间恢复或重试永远不会成功的请求。我们将每个样本转移到已确认的实时模型中，告诉代理检查目录而不是重试，并创建了一个云代理来自动更新技能以响应产品变化。
- **示例代码中的错误：** 脚本中的小问题，例如将 JPEG 字节保存在“.png”名称下，会使每个使用它们的代理脱轨。我们从源头修复了这些问题，并添加了自动化功能来定期实时测试代码示例并使其保持新鲜。

完成这些修复后，统一技能通过了 72 次运行中的 70 次，比我们第一次尝试好 22 分，比我们开始时的 14 项技能好 7 分。与使用原始技能相比，平均运行时间减少了 20%，并且每次运行的成本也回落到了初始水平。

## 经过四个月的评估后我们的情况

早在六月份，我们的文档和技能对客服人员根本没有多大帮助。 6 月 15 日，运行 Opus 4.8，基线通过了 75% 的运行。文档 MCP (67%) 和技能 (75%) 都没有提高性能。

截至 9 月 30 日，三个模型的基线已攀升至 82%。文档 MCP 为 96%，技能为 90%，新的统一技能在 10 月 8 日达到 97%。

这不是一个受控的比较——快照使用了不同的模型和任务，因此其中一些收益无疑来自于底层模型的改进，以及我们对 CLI 和 SDK 的改进。这可能解释了基线上升 7 点的原因，但指导设置上升了 20 多点，我们将额外的收益归功于我们的评估发现的文档和技能修复。

## 我们学到了什么

如果您正在浏览这篇文章，请看以下 TL;DR：

- **代理可访问性增加了使用率：** 就像 GitHub 一样：开发人员可以使用 Web GUI 手动完成的所有操作也应该可以通过 CLI 或 SDK 以编程方式获得。我们发现代理与 CLI 配合使用效果最佳，因为 CLI 通过帮助文本记录自身。说到这里——
- **文档是产品的核心部分：** 如果没有准确记录，或者您的文档无法访问（例如，使用 llms.txt、技能包或 MCP 服务器），您的平台可能无法供代理使用。 CLI 帮助文本和 API 错误消息也很重要，这些通常是代理遇到问题时首先查看的地方。
- **指导比您使用哪个前沿模型更重要：** 9 月 30 日，所有三个模型（Claude Sonnet、Opus 和 GPT Sol）都以几分的差距完成。添加我们的文档/技能将通过率从 82% 分别提高到 96% 和 97%。
- **相反，仅使用强大的模型有时会隐藏问题：** Opus 能够解决我们的 API 和技能包中的差距，而 Sonnet 则融入其中 - 这就是我们发现并解决问题的方式。当您运行评估时，请确保在整个功能范围内测试模型。
- **改进 AX 通常只需要一个小修复：** 在我们的技能文件中添加两句话，使我们的 GPU 集群评估从 15 次传递中的 4 次（对于 Sonnet）到所有三个模型的 100%。修复很小，但如果不通过评估过程，我们可能永远找不到它。

## 运行你自己的评估

如果您正在运行开发平台，那么代理正在使用您的产品，或者至少他们肯定正在尝试这样做。了解进展情况的最佳方法是建立自己的评估系统。

为了帮助解决这个问题，我们开源了用于构建评估的包。您创建一个任务列表（代理提示）并决定如何对您的运行进行评分（使用代码测试或LLM法官）。该包启动代理、运行任务并跟踪本地仪表板中的所有内容，以便您可以比较配置和过去的运行。它将在下周发布，同时还有另一篇关于如何使用它的博客文章。
