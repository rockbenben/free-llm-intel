Together 的 kernels 团队最近获得了对 NVIDIA Vera Rubin NVL72 平台的访问。过去几天我们埋头研究新的 ISA、拿 micro 戳这块芯片。有趣的新特性真不少！我们已经给 ThunderKittens 加上了在 Vera Rubin 上写 NVFP4 和 FP8 GEMM 的一些功能，并帮助小伙伴们探索星辰。

Astronomer Kittens。太可爱了！

在深入 Rubin 交付了什么之前，先用一次 Blackwell GPU GEMM 快速热身。

## 起点：一次 NVIDIA HGX B200 GEMM

NVIDIA Blackwell 架构的第五代 tensor core 从根本上改变了 GEMM 的编程模型。NVIDIA Hopper 架构的 `wgmma` 指令由一个 warpgroup 集体发出，而 Blackwell 的 `tcgen05` 指令由单个线程发出，让一个小 producer warp 就能驱动 tensor core。累加器也从寄存器移进了 Tensor Memory，操作数直接从共享内存读取，使单个 MMA 能跨两个 SM 上的两个 CTA。

要在 Blackwell 上达到有竞争力的性能，我们的 GEMM：

- 启动 threadblock cluster，让每个 CTA 对通过 TMA multicast 共享操作数，把从 HBM 来的内存流量减半。
- 在 cluster 内做 warp 专业化：loader 通过 TMA 把 A、B 搬入共享内存，单个 MMA warp 驱动 tensor core，一个 consumer warpgroup 把完成的累加器从 tensor memory 搬到 HBM。
- 持续运行，一块 tile 的输入流入的同时，前一块 tile 的输出还在排出。

通过这些努力，我们取得如下结果。

关于这些 kernel 及其优化的更多内容，见我们先前的 [Together 博客](https://www.together.ai/blog/thunderkittens-nvidia-blackwell-gpus)或 [ThunderKittens 2.0](https://hazyresearch.stanford.edu/blog/2026-02-19-tk-2) 发布！

由于 Rubin 保留了 Blackwell 的编程模型，我们的旧 GEMM 仍然能跑。然而天真地在 Vera Rubin 上跑它们，我们观察到 NVFP4 和 FP8 kernel 只达到 roofline 的约 42.1% 和 44.4%——优化空间很大！

本文其余部分分两块。先讲与 GEMM 相关的 Rubin 新特性、以及如何在 ThunderKittens 中使用它们。然后我们把这些特性逐步整合进现有的 Blackwell NVFP4 kernel，把它推到 22 PFLOPS 以上，与 cuBLAS 和 CuTe DSL 并驾齐驱。

我们发现的核心问题是：虽然 Rubin 让 tensor core 以两倍速消费操作数，但旧的 Blackwell kernel 喂得不够快。要触及计算天花板，tile 需要让已经在片上的数据榨出更多复用。

## NVIDIA Vera Rubin 平台有什么新的？

对照厂商规格，我们看到从 Blackwell 到 Vera Rubin 的如下改进。

|  | NVIDIA HGX B200 | NVIDIA Vera Rubin NVL72 |
| --- | --- | --- |
| NVFP4 Tensor Core | 9 PFLOPS / GPU | 35 PFLOPS / GPU |
| FP8 Tensor Core | 4.5 PFLOPS / GPU | 17.5 PFLOPS / GPU |
| FP16 / BF16 Tensor Core | 2.25 PFLOPS / GPU | 4 PFLOPS / GPU |
| 内存带宽 | 8 TB/s / GPU | 22 TB/s / GPU |
| SM 数 | 148 / GPU | 224 / GPU |
| 峰值功率 | 1000W / GPU | 2300W / GPU |

就编写高性能 GEMM 而言，我们特别记下以下特性。

### 1. Tensor core 每次吃两倍 K

回顾一下：`tcgen05.mma` 在 MxNxK tile 上计算 C = A@B + C，每步沿 K 消费固定字节数。Blackwell 上这步是 32 字节，而 Vera Rubin 上可以提高到 64 字节。MMA 本身仍取相同周期数，所以双 K 让我们能把两倍的塞进同一个指令窗口。

在 ThunderKittens 里，我们通过给现有 mma 操作的新模板参数表达这一点。

```
mma_ABt    (...);   // Blackwell 默认：32 字节 K 步
mma_ABt<64>(...);   // Vera Rubin：64 字节 K 步
```

### 2. Tensor memory 增长到 576 列

Blackwell 引入了 tensor memory 概念——一个 128 lane x 512 column x 32-bit 的空间，tensor core 可直接读写。Vera Rubin 上这个空间增到 576 列，额外提供 32 KiB 的 tensor memory。

注意这些额外的列只能通过 `.exclusive` 限定符访问——PTX 9.4 新增，确保 SM 上只有一块活跃的 tensor memory 分配。非 exclusive 分配仍上限 512 且必须是 2 的幂。

ThunderKittens 用户可以用 tensor memory 分配器的模板参数请求它，指定分配是 exclusive 的。

```
template<int _nblocks_per_sm, int _ncta, bool _managed = true, bool _exclusive = false>
struct tensor_allocator { .... }

tensor_allocator<1, C::CLUSTER_SIZE, false> tm; // Blackwell 默认：512 列
tensor_allocator<1, C::CLUSTER_SIZE, false, true>  tm; // Rubin：最高 576 列
```

### 3. 共享内存增长到 328 KiB

Hopper 和 Blackwell 提供 228 KiB 共享内存，Vera Rubin 引入可动态增到 328 KiB 的超大共享内存模式。这是一个 host 侧设置，可如下调用。

```
CUfunction function = nullptr;
cudaGetFuncBySymbol(&function,reinterpret_cast<const void*>(kernel));
cuFuncSetAttribute(function, CU_FUNC_ATTRIBUTE_SHARED_MEMORY_MODE,
                   CU_SHARED_MEMORY_MODE_ALLOW_OVERSIZED_SHARED_MEMORY);
```

### 4. B 侧 collector

Blackwell 引入了 collector buffer 概念——一个小 MMA staging 缓冲，可以锁住 A tile，让下一条指令从那里取，而不是从共享内存。Vera Rubin 用 `.collector::b::*` 把这一功能扩展到 B tile。

为利用它，我们用四个描述其对 collector buffer 动作的标签注释每个 MMA 的操作数。

- "FILL" 从共享内存读取操作数并锁住
- "USE" 从 buffer 读
- "LASTUSE" 从 buffer 读并释放
- "DISCARD" 是默认，跳过锁住

这些标签是复用的许可限定符，而非保证。也就是说即使有复用许可，Tensor Core 仍可能重新加载矩阵。

现在两个操作数都能常驻 collector buffer，我们可以实验新模式。例如在 2x2 块上，两侧都收集可以把四个 MMA 从八次操作数读取降到只有五次。

在 ThunderKittens 里可如下暴露：

```
mma2_ABt_chunk<64, false, false, collector::FILL,collector::DISCARD>(C[0][0], a0, b0, ...);
mma2_ABt_chunk<64, false, false, collector::LASTUSE, collector::FILL   >(C[0][1], a0, b1, ...);
mma2_ABt_chunk<64, false, false, collector::FILL,    collector::LASTUSE>(C[1][1], a1, b1, ...);
mma2_ABt_chunk<64, false, false, collector::LASTUSE, collector::DISCARD>(C[1][0], a1, b0, ...);
```

### 5. 提早 A 释放

`tcgen05.commit` 在其处理的 MMA 完成后到达 mbarrier，通知 producer 一个 stage 槽可复用。PTX 9.4 引入 `tcgen05.commit.sync_restrict::shared::read::mma::a`，一条允许我们为 A tile 提前发信号的新指令。不用等 MMA 完成，我们可以只要 MMA 从共享内存读完其 A 操作数就立刻触发 barrier，通知 tma loader 开始存下一 stage 的数据。

ThunderKittens 引入一种新 commit 类型让用户表达这一点。

```
tensor_commit<2> (inputs_finished[stage], mask); // MMA 退役时到达
tensor_aread_commit<2>(A_finished[slot], mask); // MMA 读完 A 时到达
```

## 构建 GEMM

现在我们有了新特性和一个 Blackwell GEMM。以下章节把这些特性逐步整合进现有 Blackwell kernel，并解释迁往 Vera Rubin 时为什么需要它们。

### 加宽指令：

最直觉的瓶颈来自仍依赖 Blackwell 的 32 字节 K 步。在 Vera Rubin 上，这种编码的 ISA 天花板约 16.8 PFLOPs，而我们的 NVFP4 Blackwell GEMM 开箱已达 14.7 PFLOPs（天花板的 88%）。要再推高，必须把 MMA 处理的 K 字节翻倍。

然而简单把更宽编码开给现有 Blackwell kernel，我们注意到性能只有微幅提升、而非预期的 2 倍。更宽 MMA 让 tensor core 翻倍快消费操作数，却无助于我们供得更快。要让双 K 有用，我们拉两个杠杆：少搬字节，加深流水线以确保抓取相互重叠。

### 少读字节：

要抓更少字节，我们在同一 CTA 对上沿 M 维度叠第二块输出 tile。由于两块累加器只差在 M，我们能让它们共享同一个 B chunk。我们原始 Blackwell NVFP4 kernel 用 1x1 切分格式，意味着覆盖 M512xN256 输出需要两个 pair job、各自搬运自己的 B。转向 2x1 格式后，B 只需抓一次就覆盖同样输出，减少操作数流量。

这种 2x1 切分格式在我们的 NVFP4 Blackwell kernel 里不容易实现，因为 tensor memory 上限 256 KiB。两块 M256xN256 累加器已占满 512 列，block-scaled MMA 没有空间存 A、B 的 scale。程序员本可以绕开这个约束——让 epilogue warp 只加载累加器列的一部分再发 MMA-empty 信号、让下一 K tile 的 MMA 开始——但这引入了无法隐藏的小延迟。幸运的是，有了 Vera Rubin 的额外 64 列，我们可以直接存 scale 因子，不必跳这个舞。

### 加深流水线：

改变切分格式减少操作数流量，但无助于缩短每次抓取的时间。下一个挑战是让 tensor core 持续被喂饱。Vera Rubin 更大的共享内存允许我们建更深的流水线，提前为更多 tile staging、给传输更多时间完成。对 NVFP4 和 FP8 的 16k 平方 GEMM 扫描 ring 深度，结果如下。

NVFP4 16k 平方 GEMM：

| Smem Tile 级数 | 所需共享内存 | 达成 TFLOPS |
| --- | --- | --- |
| 3 | 202 KiB | 17,054 |
| 4 | 258 KiB | 20,595 |
| 5 | 314 KiB | 22,239 |

FP8（E4M3）16k 平方 GEMM：

| 配置 | 所需共享内存 | 达成 TFLOPS |
| --- | --- | --- |
| 4 | 209 KiB | 10,895 |
| 5 | 257 KiB | 11,995 |
| 6 | 305 KiB | 11,288 |

虽然最后一级增益最大，但要注意这些收益依赖前面那些优化。下面是把 K 步大小、共享内存流水线和切分策略独立扫描的结果。

### 最后的润色：

为把 kernel 推得更远，我们玩转了几个最后的旋钮

- **Kernel 配置调优：** 我们在不同负载间进一步调优 kernel 以取得最高性能。关于 CTA pair 尺寸，Blackwell kernel 原有的 1x1 tile 格式对较小方形负载性能最好。更大的形状我们用 2x1 CTA pair 切分，外加调优过的 cluster 大小 2、4 或 8 个 CTA。此外所有形状下，我们都置换 tile rasterization 顺序以改善内存局部性与性能。
- **B 侧 collector：** 既然我们用 2x1 切分格式，就能用 B 侧 collector。一条 MMA 指定"FILL"、下一条"LASTUSE"，B 读取就只发生一次而不是两次。我们测得约 1-3% 改善。
- **使用 `sync_restrict::shared::read::mma::a`：** 对更大的 64k 和 128k 平方 NVFP4 GEMM，我们观察到提早 A 释放分别带来 13.5% 和 22.1% 加速。我们发现这条指令在较大尺寸上很有用——那里 A tile 与其他资源争抢驻留，导致其行在复用之间被逐出、迫使 loader 等待它们。这让我们得以兑现提早 A 复用的收益。小尺寸上，A tile 从不离开 L2，读取本来就已经够快、不需要提早。为使用这条指令，我们修改了传统 ring 顺序逻辑。正常 GEMM 中 A、B tile 同属一个 ring、在单个 commit 下齐步走。但提早 A 释放要生效，必须解耦两块 tile、让 A 加载能独立行动。提早 A 释放需要在更早信号上释放 A 的槽，所以我们给 A 自己的 ring 和一对 arrived/finished barrier。
- **L2 逐出提示：** 我们给 A 操作数标 EVICT_LAST，鼓励 L2 为复用它们的后续 job 保持驻留。复用收益来自跨 job 而非 cluster 内，帮助约几个 0.1%。

注意以上所有测量都使用 NVIDIA CUDA 13.4、在 Qualification Sample（QS）GPU 上产生。我们预期所有基线的性能会随 Vera Rubin 软件发布继续改进。
