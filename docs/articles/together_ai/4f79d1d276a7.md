# 配置专用模型推理

endpoint、deployment 与 config 是如何配合的，以及路由为什么跟随容量、而不是跟随固定百分比。

- 作者：Mitali Meratwal、Zain Hasan
- 目录[为生产环境选定的 40 多个模型……为生产环境选定的 40 多个模型……为生产环境选定的 40 多个模型……](https://www.together.ai/blog/configuring-dedicated-model-inference)

摘要

Together AI 平台上的专用模型推理由三个部分组成：**endpoint**（你或你的客户端所调用的那个稳定名称）、**deployment**（在它背后运行副本的具体模型 + 硬件组合），以及 **config**（描述一个模型如何运行的配方）。一套感知容量的流量划分把这三个实体绑在一起。正是这套架构让 rollout、A/B 测试、影子实验、零停机变更等各种能力成为可能。下面我们会在一个真实 endpoint 上，用实测流量展示感知容量的路由是如何工作的。

## 资源模型如何运作

- **config** 是一份配方，指定引擎、GPU 类型与数量，以及并行方式和优化档位（throughput、latency、balanced）。config 是**不可变的**，每个 config 都有一个形如 `cr_...` 的 ID。你的 deployment 永远精确指向那一份被测试过的 config。
- **deployment** 把一个模型（在某个特定 revision 上）绑定到一个 config，为它配置一条*自动扩缩容策略*，并运行副本。deployment 就是有意做成用完即弃的，创建与销毁都应被视为日常操作。
- **endpoint** 是一个固定的身份：一个限定名称（`<project_slug>/<endpoint_name>`），你的应用把它作为 `model` 参数传给普通的 [推理](https://www.together.ai/dedicated-model-inference) API。endpoint 带有一个**流量划分**，用来决定请求在其各个 deployment 之间如何路由。

理解这一点有个简单办法：看 ID。系统里的每一个 ID 都会通过前缀告诉你它是什么，这让日志和脚本自带说明：`proj_`（project）、`ml_`（model）、`cr_`（config revision）、`endpoint_`、`dep_`（deployment）、`rol_`（rollout）。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62b860d26c312daad25162_CleanShot_2026-07-09_at_22.50.39.png)

**平台上每一个高级操作，说到底都只是"再加一个 deployment，并给它分配一个流量路由权重"。** *A/B 测试*就是带 cohort 分配的若干 deployment。*影子实验*是权重为零、接收镜像流量的一个 deployment。停止（stopping）一个 deployment，就是把副本数的上下界都设为 0/0。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62b8cc38b0ad4ed9589602_CleanShot_2026-07-09_at_22.51.25.png)

## 基于权重的流量划分

流量划分是一份 `{deployment_id, weight}` 条目列表，其中的权重是按*每个就绪副本*计算的。路由器把每个 deployment 的有效容量算作 `weight × ready_replicas`，并按这一容量成比例地路由。

走一遍上面那张图：两个 deployment 的权重都是 1，但 deployment A 有 1 个就绪副本（容量 1），deployment B 有 3 个（容量 3），于是流量按 **25%/75% 划分**。权重相等意味着*每个副本的负载相等*，而不是流量份额相等。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62b93ae048383400af5cbe_CleanShot_2026-07-09_at_22.45.47.png)

我们之所以这样设计，是因为它让路由和扩缩容变成同一场对话：

- **自动扩缩容天然成立。** 当 deployment A 从 1 个副本扩到 3 个，它的容量变为三倍，并自动承接成比例更多的流量。若是朴素的百分比方案，一个被钉死在 "25%" 的 deployment 会在缩容时被打满、在扩容时闲置。
- **每个副本的负载才是你能控制的。** 权重 1 与权重 2 表达的是"B 的每个副本应当比 A 的每个副本多干一倍的活"。
- **没就绪的副本不计入。** 一个正在冷启动、或退化到 0 个就绪副本的 deployment，贡献的容量为零，因此流量会流向真正能提供服务的副本。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62b97f01412dc482e53558_CleanShot_2026-07-09_at_22.52.45.png)

权重是正数，且没有求和约束，所以 `0.7/0.3` 和 `700/300` 描述的是同一种路由。如果你*想要*不随副本数变化的固定流量份额，可以配置 A/B 实验的 cohort，它支持加总为 100% 的整数百分比。

设置一次划分只需要一次带 field mask 的 PATCH：

```
    
      tg beta endpoints update $DEPLOYMENT_A --traffic-weight 1
tg beta endpoints update $DEPLOYMENT_B --traffic-weight 1

# take a deployment out of rotation without scaling it down
tg beta endpoints update $DEPLOYMENT_B --traffic-weight 0
          
```

## 底层机制：选择 config

你不必从零编写 config。受支持模型目录里的每一个模型都随附若干 **deployment profile**，那是我们做过基准测试并持续改进的、经过认证的模型 + config 组合：

```
    
      tg beta models public zai-org/GLM-5.2 --json | jq '.data[0].deploymentProfiles[]'

# or, once you have the model ID, list its deployable configs directly:
tg beta models configs ml_CcEtnFUbitJYNja6TTR6U
          
```

```
    
{
  "profileId": "profile-cabcbcec874c",
  "certifiedConfigRevisionId": "cr_Cd35DNpQuHM3RihtCkN59",
  "certifiedModelRevisionId": "rv_CcEuPu4Gk6c4M7v4PTYuG",
  "gpuType": "NVIDIA-B200",
  "gpuCount": 4,
  "quantization": "FP4",
  "performanceBenchmarks": {},
  "config": "projects/proj_CbdXDuLRFhUPv1mGfxwUc/configs/cr_Cd35DNpQuHM3RihtCkN59",
  "model": "projects/proj_CbdXDuLRFhUPv1mGfxwUc/models/ml_CcEtnFUbitJYNja6TTR6U/revisions/rv_CcEuPu4Gk6c4M7v4PTYuG",
  "parallelism": "TP4"
}
    
```

接下来，你可以把 model 和 config 的资源名复制进一条创建 deployment 的命令：

```
    
      tg beta endpoints deploy zai-org/GLM-5.2 \
  --endpoint my-glm-endpoint \
  --config cr_Cd35DNpQuHM3RihtCkN59 \
  --traffic-weight 1
          
```

当你要在多个 config *之间*做选择时，这些选择器会告诉你每份配方优化的是什么：

| 选择器 | 取值 | 它所编码的取舍 |  |  |
| --- | --- | --- | --- | --- |
| accelerator_type | H100, H200, B200, … | 成本 vs 显存带宽 vs 可用性 |  |  |
| accelerator_count | 1, 2, 4, 8 | 装得下模型 + KV-cache 余量 |  |  |
| optimization | latency / throughput / balanced | 最根本的服务化取舍（见下） |  |  |
| topology | 例如 aggregated/disaggregated | 模型如何切分到多块 GPU 上 |  |  |

optimization 这条轴，会是你花时间最多的一个选择。

- latency 档位为 time-to-first-token 优化：更小的批次、eager 调度，每个请求都能更早被处理，代价是每块 GPU 的总 tokens/sec 下降。
- throughput 档位把批次堆得更大：最大化每 GPU 小时的聚合 token 数，而单个请求要等更久才能加入一个批次。如果你在做一个交互式聊天产品，大概应该选 latency；而离线流水线和批量摘要可以用 throughput 的 config。
- 当你的流量两者都有的时候，balanced 是一个不错的默认值。

config 之所以不可变，是因为 cr_ revision 永不改动，也就是说：一个 deployment 的行为不可能因为有人在共享 config 上"随手调了一个开关"而漂移。任何改动都是一次新 revision；旧的那一份仍然是有效且经过测试的回滚目标。投机解码（speculative decoding）同样可以从这里触发，因为 draft 模型是 *config* 的一个属性。

## 边界情况

**1. 某个 deployment 在流量划分里，但有 0 个就绪副本。**

因为容量 = 权重 × 0 = 0，它不会收到任何流量；其他 deployment 会吸收它那一份。等副本恢复，流量会自动地、并按比例流回来。

**2. 我能删除一个还在流量划分里的 deployment 吗？**

你应该先把它从划分里移除，再删除。拆除的顺序是：排空流量 → 停止 → 删除，API 也会把你推向这个顺序。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62bbf7c76ae2af542d33af_CleanShot_2026-07-09_at_22.55.25.png)

**3. 流量划分 vs. A/B 成员百分比 vs. canary 步进百分比**

**traffic-split 权重**（相对容量、稳态路由）、**A/B 成员百分比**（整数形式的 cohort 份额，加总为 100，且不随副本数变化而固定），以及 **canary 步进百分比**（一次 rollout 的过渡时间表）。这是三件不同的工具、对应三件不同的活，它们按固定顺序组合：路由先解析**权重划分**（按容量抽出一个候选 deployment），接着如果该候选是某个 **A/B 实验**的对照组，这个实验会重新抽样（把对照组的份额在各实验臂之间细分），然后如果该候选是某次**进行中的 rollout** 的源，该 rollout 会重新抽样（按当前步骤百分比在源与目标之间划分），最后在胜出的那个 deployment 内部选定一个 cluster。rollout 会代你操纵它自己的 stage。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62bc45c496ab2a0095385c_CleanShot_2026-07-09_at_22.56.31.png)

**4. 我的客户端用的是哪个名字？**

就是 endpoint，它形如 `<project_slug>/<endpoint_name>`，可以作为 `model` 字符串传给标准推理 API。即使你去做一次 rollout、更换硬件、跑 A/B 测试，它都保持不变。

## 展示感知容量路由的实验

我们对着一个真实 endpoint 跑了这个实验，它带两个单 H100 的 deployment，用来展示按权重划分流量的实际效果。两个 deployment 的权重各为 1，起始各 1 个就绪副本。我们发出 599 个打了标记的请求，并把每一个请求归到服务它的 deployment 上；然后把 A 从 1 个副本扩到 2 个，再发 599 个请求，以下是从 deployment 侧观察到的路由：

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62bc93c496ab2a0095488a_image.png)

| 阶段 | 副本数（A : B） | 预期份额 | 实测份额 | n |
| --- | --- | --- | --- | --- |
| 1 | 1 : 1 | 50 / 50 | 47.6 / 52.4 | 599 |
| 2 | 2 : 1 | 66.7 / 33.3 | 69.4 / 30.6 | 599 |

因为路由跟随容量，而容量跟着副本走。在 deployment A 内部，它的两个 pod 各自承载了总流量的约 30–40%（39.6% 和 29.9%）——路由器在 pod 之间同样是均衡的。

为了让 profile 的取舍更具体，我们在演示 endpoint 上把两个认证 profile 各按 1 个副本扫了一遍：并发 4 / 8 / 16 下各 60 秒的闭环压测档位、200 token 的生成，token 数取自 API 自身的 `usage` 字段：

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62bcfc38b0ad4ed959ad4b_image%201.png)

| Profile | c=4 | c=8 | c=16 | TTFT p95 @ c16 |
| --- | --- | --- | --- | --- |
| A · Qwen3.5-9B (BF16, TP1) | 362 tok/s | 789 tok/s | 1,464 tok/s | 368 ms |
| B · Qwen3-VL-8B (BF16, TP1) | 495 tok/s | 243 tok/s | 240 tok/s | 323 ms |

这张表就是"要实测"的整个论点：**B 在低并发下胜出，随后急剧退化。** A 的 batching 表现很好，从 c4 到 c16 吞吐达到 4 倍，而 TTFT p95 只上升约 17%。B 在并发 4 时*比* A 更快，然后就饱和了：越过 c≈4 之后，它的有效请求速率不再增长，聚合吞吐减半，并且每分钟开始有几条请求彻底卡住。如果你只在并发 4 做过压测，你就会为一个高并发负载选下 B，然后要到生产环境才发现这个行为。

两个 profile 都没有"错"——它们只是同一条服务化前沿上的不同点，而*你的*模型的 profile 也会有自己的曲线。起始 config 给你的是一批可供测试的起点；像这样一小时的压测，会告诉你哪一个适配你的流量。

## 自己动手试试！

整套模型，五条命令：

```
    
      # 1. Identity: who am I / what project
tg whoami

# 2. Pick a certified profile for your model
tg beta models public --product dedicated

# 3. One command: endpoint + deployment + traffic split + wait
tg beta endpoints deploy $MODEL --endpoint my-endpoint --traffic-weight 1

# 4. Call it — the qualified name is the model string
resp = client.chat.completions.create(
model="my-project/my-endpoint",   # the endpoint's qualified name IS the model string
messages=[{"role": "user", "content": "Hello!"}],
)

# 5. See what you built
together beta endpoints get $ENDPOINT_ID
    
```

从这里出发，本系列里的其余一切，都只是再多一个 deployment 的事。
