# 配置专用模型推理

端点、部署和配置如何组合在一起，以及为什么路由遵循容量而不是固定百分比。

- 作者米塔利·梅拉特瓦尔 (Mitali Meratwal)、扎因·哈桑 (Zain Hasan)
- 目录[40+ 个用于生产的模型...40+ 个用于生产的模型...40+ 个用于生产的模型...](https://www.together.ai/blog/configuring-dedicated-model-inference)

总结

Together AI 平台上的专用模型推理由三部分组成：**端点**（您或您的客户调用的稳定名称）、**部署**（特定模型+在其背后运行副本的硬件组合）和**配置**（模型运行方式的方法）。容量感知的流量分割将这三个实体联系在一起。该架构支持各种其他功能，例如推出、A/B 测试、影子实验、零停机更改。下面我们将展示容量感知路由如何针对具有测量流量的实时端点进行工作。

## 资源模型如何工作

- **配置**是指定引擎、GPU 类型和数量以及并行性和优化配置文件（吞吐量、延迟、平衡）的配方。配置是**不可变的**，每个配置都有一个像 `cr_...` 这样的 ID。您的部署始终准确地指向已测试的配置。
- **部署**将一个模型（在特定修订版）绑定到一个配置，为其提供*自动缩放策略*，并运行副本。部署是有目的的一次性的，创建和销毁应该被视为例行公事。
- **端点**是一个固定标识：应用程序在普通 [inference](https://www.together.ai/dedicated-model-inference) API 中作为“model”参数传递的限定名称 (`<project_slug>/<endpoint_name>`)。端点具有**流量分割**，用于确定其部署上的请求路由。

理解这一点的一种简单方法是通过引用 ID，系统中的每个 ID 通过前缀告诉您它是什么，这使得日志和脚本可以自记录：“proj_”（项目）、“ml_”（模型）、“cr_”（配置修订版）、“endpoint_”、“dep_”（部署）、“rol_”（部署）。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62b860d26c312daad25162_CleanShot_2026-07-09_at_22.50.39.png)

**平台中的每个高级操作只是“添加部署，并为其分配流量路由权重”** *A/B 测试*是具有队列分配的部署。 *影子实验*是接收镜像流量的权重为零的部署。停止部署会将最小和最大副本限制为 0/0。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62b8cc38b0ad4ed9589602_CleanShot_2026-07-09_at_22.51.25.png)

## 基于权重的流量分割

流量分割是一个“{deployment_id，weight}”条目列表，其中权重是每个*就绪副本***。**路由器将每个部署的有效容量计算为“权重×ready_replicas”，并按比例路由到该容量。

浏览上图：两个部署的权重均为 1，但部署 A 有 1 个就绪副本（容量 1），部署 B 有 3 个副本（容量 3），因此流量遵循 **25%/75% 分配**。相等的权重意味着“每个副本负载相等”，而不是相等的流量份额。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62b93ae048383400af5cbe_CleanShot_2026-07-09_at_22.45.47.png)

我们这样设计是因为它使路由和缩放成为相同的对话：

- **自动扩展是免费的。** 当部署 A 从 1 个副本扩展到 3 个副本时，其容量将增加两倍，并且会自动按比例吸收更多流量。对于简单的百分比，固定在“25%”的部署在缩小规模时会饱和，而在扩大规模时会闲置。
- **每个副本负载由您控制。** 权重 1 与权重 2 表示“B 的每个副本的工作强度应该是 A 的每个副本的两倍”
- **未准备好的副本不算数。** 部署中期冷启动或降级为 0 个就绪副本，贡献的容量为零，因此流量流向实际可以提供服务的部分。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62b97f01412dc482e53558_CleanShot_2026-07-09_at_22.52.45.png)

权重是正数，没有总和约束，因此“0.7/0.3”和“700/300”描述相同的路由。如果您“想要”固定流量份额，而不管副本数量如何，您可以设置 A/B 实验队列，允许总和为 100% 的整数百分比。

设置分割是一个带有字段掩码的 PATCH：
```
    
      tg beta endpoints update $DEPLOYMENT_A --traffic-weight 1
tg beta endpoints update $DEPLOYMENT_B --traffic-weight 1

# take a deployment out of rotation without scaling it down
tg beta endpoints update $DEPLOYMENT_B --traffic-weight 0
          
```
## 底层：选择配置

您不需要从头开始编写配置。支持的模型目录中的每个模型都附带**部署配置文件**，它们是经过认证的模型+配置对，我们进行基准测试并不断改进：
```
    
      tg beta models public zai-org/GLM-5.2 --json | jq '.data[0].deploymentProfiles[]'

# or, once you have the model ID, list its deployable configs directly:
tg beta models configs ml_CcEtnFUbitJYNja6TTR6U
          
```

```
    
{
  "profileId": "profile-cabcbcec874c",
  "certifiedConfigRevisionId": "cr_Cd35DNpQuHM3RihtCkN59",
  "certifiedModelRevisionId": "rv_CcEuPu4Gk6c4M7v4PTYuG",
  "gpuType": "NVIDIA-B200",
  "gpuCount": 4,
  "quantization": "FP4",
  "performanceBenchmarks": {},
  "config": "projects/proj_CbdXDuLRFhUPv1mGfxwUc/configs/cr_Cd35DNpQuHM3RihtCkN59",
  "model": "projects/proj_CbdXDuLRFhUPv1mGfxwUc/models/ml_CcEtnFUbitJYNja6TTR6U/revisions/rv_CcEuPu4Gk6c4M7v4PTYuG",
  "parallelism": "TP4"

```
从那里您可以将模型和配置资源名称复制到部署创建中：
```
    
      tg beta endpoints deploy zai-org/GLM-5.2 \
  --endpoint my-glm-endpoint \
  --config cr_Cd35DNpQuHM3RihtCkN59 \
  --traffic-weight 1
          
```
当您在*之间*配置中进行选择时，选择器会告诉您每个配方优化的内容：

|选择器|价值观 |它编码的权衡|  |  |
| ---| ---| ---| ---| ---|
|加速器类型 | H100、H200、B200、…… |成本、内存带宽、可用性  |  |
|加速器计数 | 1、2、4、8 |拟合模型 + KV 缓存空间 |  |  |
|优化|延迟/吞吐量/平衡|基本的服务权衡（下）|  |  |
|拓扑 |例如汇总/分类 |模型如何跨 GPU 拆分 |  |  |

优化轴是您花费最多时间进行选择的轴。

- 延迟配置文件优化了第一个令牌的时间：较小的批次、急切的调度、每个请求更快地得到关注，但代价是每个 GPU 每秒的总令牌数。
- 吞吐量配置文件打包更大的批次：最大化每 GPU 小时的聚合令牌，并且单个请求需要等待更长的时间才能加入批次。如果您正在构建交互式聊天，您可能希望考虑延迟，而离线管道和批量汇总可以使用吞吐量配置。
- 当您的流量同时拥有两者时，平衡是一个很好的默认值。

配置是不可变的，因为 cr_ 修订永远不会改变，即部署的行为不会因为有人“只是在共享配置上调整了标志”而发生漂移。更改是新的修订；旧的仍然是有效的、经过测试的回滚目标。推测解码也可以从这里触发，因为草稿模型是 *config.* 的属性

## 边缘情况

**1.部署处于拆分中，但有 0 个就绪副本。**

因为容量 = 权重 × 0 = 0，所以没有收到流量；其他部署将吸收其份额。当副本恢复时，流量会自动按比例回流。

**2.我可以删除仍在流量分配中的部署吗？**

您应该先将其从拆分中删除，然后再删除。拆卸顺序包括排出流量 → 停止 → 删除，API 会将您推向该顺序。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62bbf7c76ae2af542d33af_CleanShot_2026-07-09_at_22.55.25.png)

**3.流量分配与 A/B 成员百分比与金丝雀步百分比**

**流量分割权重**（容量相对，稳态路由），**A/B 成员百分比**（整数群组份额，总和为 100，并且无论副本数量如何都是固定的），以及 **金丝雀步骤百分比**（推出的过渡计划）。这是针对三种不同作业的三种不同工具，它们按固定顺序组成：路由首先解决**权重分割**（按容量采样的候选部署），然后如果候选是其控制（在臂之间细分控制份额），则进行 **A/B 实验**重新采样，然后如果候选是其源（按当前步骤百分比在源和目标之间分割），则 **主动推出** 重新采样，最后在获胜部署内选择一个集群。首次展示会代表您操纵其阶段。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62bc45c496ab2a0095385c_CleanShot_2026-07-09_at_22.56.31.png)

**4.我的客户使用什么名字？**

类似于“<project_slug>/<endpoint_name>”的端点可以作为标准推理 API 中的“model”字符串传递。即使您选择执行部署、交换硬件、运行 A/B 测试，这也将保持不变。

## 实验显示容量感知路由

我们针对具有两个单 H100 部署的实时端点运行此测试，以显示权重模型流量分割的实际情况。两个部署，每个部署的权重为 1，每个部署都以 1 个就绪副本开始。我们发送了 599 个标记请求并将每个请求归因于其服务部署，然后将 A 从 1 → 2 个副本进行缩放并发送了 599 个以上请求，并捕获了以下路由（如部署所示）：

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62bc93c496ab2a0095488a_image.png)

|相|复制品 (A : B) |预期份额 |测量份额 | n |
| ---| ---| ---| ---| ---|
| 1 | 1 : 1 | 50 / 50 | 50 / 50 47.6 / 52.4 | 47.6 / 52.4 599 | 599
| 2 | 2 : 1 | 66.7 / 33.3 | 69.4 / 30.6 | 599 | 599

因为路由遵循容量，而容量又遵循副本。在部署 A 中，其两个 Pod 各自承载约 30-40% 的总流量（39.6% 和 29.9%），路由器也在 Pod 之间实现平衡。

为了使配置文件权衡具体化，我们从演示端点扫描了两个经过认证的配置文件，每个配置文件一个副本，并发性为 4 / 8 / 16 时的 60 秒闭环级别，200 个代币生成，代币计数取自 API 自己的“usage”字段：

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a62bcfc38b0ad4ed959ad4b_image%201.png)

|简介 | c = 4 | c = 8 | c=16 | TTFT p95 @ c16 |
| ---| ---| ---| ---| ---|
| A·Qwen3.5-9B（BF16、TP1）| 362 托克/秒 | 789 托克/秒 | 1,464 托克/秒 | 368 毫秒 |
| B·Qwen3-VL-8B（BF16、TP1）| 495 托克/秒 | 243 托克/秒 | 240 托克/秒 | 323 毫秒 |

该表是衡量的全部论点：**B 在低并发下获胜，然后急剧下降。** A 批处理良好，吞吐量从 c4 到 c16 提高了 4 倍，而 TTFT p95 仅增长了约 17%。 B 在并发数为 4 时比 A *快*，然后饱和：超过 c≈4 后，其有效请求率停止增长，总吞吐量减半，并且每分钟的一些请求开始完全停滞。如果您仅在并发度 4 下进行负载测试，那么您会为高并发工作负载选择 B，并且仅在生产中发现此行为。

两种配置文件都不是“错误的”，它们只是服务边界上的不同点，并且*您的*模型的配置文件将有自己的曲线。起始配置为您提供了一种测试起始点的方法；像这样的一小时扫描会告诉您哪一个适合您的流量。

## 自己尝试一下！

整个模型由五个命令组成：
```
    
      # 1. Identity: who am I / what project
tg whoami

# 2. Pick a certified profile for your model
tg beta models public --product dedicated

# 3. One command: endpoint + deployment + traffic split + wait
tg beta endpoints deploy $MODEL --endpoint my-endpoint --traffic-weight 1

# 4. Call it — the qualified name is the model string
resp = client.chat.completions.create(
model="my-project/my-endpoint",   # the endpoint's qualified name IS the model string
messages=[{"role": "user", "content": "Hello!"}],
)

# 5. See what you built
together beta endpoints get $ENDPOINT_ID
    
```
从这里开始，本系列中的所有其他内容都需要再进行一次部署。
