# 在生产环境中对模型进行 A/B 测试

A/B 测试实施指南

## 摘要

A/B 实验可以把一个 endpoint 的真实流量切分为固定队列：一个对照（control）加最多 20 个变体（variant），每个变体有一个百分比流量份额。这让你能在自己选择的曝光水平上，衡量候选模型在*真实用户*面前的表现。提升某个变体的流量占比只需一次调用；你可以用蓝绿发布（blue-green rollout）来晋升胜出者。删除实验后，100% 的流量会回到对照，无需事后拆除任何客户端或路由逻辑改动。下面我们会在一个真实 endpoint 上跑一次实验：按 95%/5% 创建，逐步提升到 80%/20% 和 50%/50%，然后删除，并在每个阶段检查实际观测到的流量份额。

## 为生产环境中的 LLM 实施 A/B 测试

迟早每个团队都想回答同一个问题：*与当前模型相比，新模型对我们的用户真的更好吗？*不是在某项基准上更好，而是在留存率、点赞率、任务完成率——你的产品实际度量的任何指标——上更好。

*影子流量（shadow traffic）*回答不了这个问题。影子复制能告诉你候选模型在*运维层面*是可靠的——延迟、错误、吞吐都没问题——但它的响应会被丢弃，没有任何用户会基于这些响应采取行动。质量上的问题需要真实暴露给终端用户：让一部分用户使用模型 B，然后对比发生了什么。

通常团队会在应用层自己搭这套东西，靠以下某种组合：

- 功能开关（feature flag），或在客户端代码里对用户 ID 做 hash-mod-100。
- 两个 endpoint（或两个硬编码的模型字符串）让客户端切换。
- 某处一个电子表格，说明 A 组和 B 组是什么意思。

这能用，但它把你的实验和基础设施以日后有害的方式纠缠在一起：路由逻辑随应用一起发布，分组切分会因客户端缓存决策而漂移，甚至实验"结束"之后，分支代码还会长期存在，因为没人确定删除它是安全的。

Together AI 平台让你在 endpoint 层面运行 A/B 实验逻辑。

## 工作原理

一个 A/B 实验挂载到某个 endpoint 上，声明若干成员：恰好一个 **control（对照）** 和一个或多个 **variant（变体）**，每个成员指向一个 deployment，各自带一个 `percent` 设置，总和必须为 100，用于控制流量路由。

endpoint 路由器的工作方式是：每当基础流量把请求发给对照时，实验就在各分支之间重新采样并重新分配——例如 95% 留在对照，5% 走向变体。

精确地说机制是：**实验对控制在基础流量切分中所占的份额进行再细分。**路由首先通过权重切分解析请求；当胜出者是某个 A/B 实验的对照时，请求再按实验各成员的百分比在分支间重新采样。由于对照是切分成员中唯一的入口，成员百分比因此*就是*绝对流量份额。还值得注意的一点是：如果一个对照的切分权重为零，实验就没有东西可细分，整个实验因此接收不到任何流量。

关键在于，**变体 deployment 绝对不能出现在 endpoint 的流量切分里**，平台要求变体的权重必须为零；只有对照存在于基础切分中。实验将完全掌控路由给变体的流量；变体的百分比*就是*它的流量份额。如果变体还能从切分中按容量权重抽取流量，你的测量结果就会被悄悄扭曲。一个理解方式是：把变体像影子部署那样设置——创建、处于 `READY` 状态、权重为零——然后让实验的百分比设置把流量路由过去。

这里另一个重要点是：A/B 百分比是**真实的固定流量份额**，总和为 100%，且与副本数量无关。我们刻意让它与流量切分权重（按每就绪副本计算、跟随容量）不同。实验是一种*测量仪器*；你希望在测量期间切分保持恒定，而不是随自动扩缩容漂移。

创建一个 95/5 实验：

```
    
      tg beta endpoints ab my-org/candidate-model --control $CONTROL_DEPLOYMENT --percent 5
          
```

你的客户端不会察觉这个实验，因为从表面上看，相同的 endpoint 名称、API 和密钥都不变。而在后端，5% 的请求现在将由变体候选模型来响应。

## 底层机制：提升、度量、结束

### 提升 = 重新发送整个成员集

没有单独的"ramp（提升）"API，一次 update 会*替换完整的成员列表*。这让心智模型保持简单（实验永远恰好等于它的成员所声明的样子），并让每一次提升都成为一次显式、可审查的变更：

```
    
      # 第 2 周：候选在 5% 上表现良好 ——> 提升到 20%
client.beta.endpoints.ab_experiments.update(
    id=experiment_id,
    endpoint_id=endpoint_id,
    update_mask="members",
    etag=experiment.etag,   # 队友并行的提升会被拒绝，而不是被覆盖
    members=[
        {"deployment_id": control_dep, "percent": 80, "role": "AB_EXPERIMENT_MEMBER_ROLE_CONTROL"},
        {"deployment_id": variant_dep, "percent": 20, "role": "AB_EXPERIMENT_MEMBER_ROLE_VARIANT"},
    ],
)
    
```

更新受 etag 保护，因为如果在你编写更新的同时某个队友已经提升了实验，你的请求会被拒绝，而不是悄悄覆盖对方的改动。

有了这个 API 设计，你仍然需要做出常见的曝光选择：给 B 组路由多少流量：

| 切分 | 信号速度 | 风险 | 适用时机 |
| --- | --- | --- | --- |
| 95/5 | 慢（需要流量/时间积累） | 最小 | 新模型，首次真实曝光 |
| 80/20 | 中等 | 可控 | 候选撑过了 5%；你想要更有分量的读数 |
| 50/50 | 最快 | 一半用户 | 在两个已知可靠选项之间做最后阶段的确认 |

借助最多 **20 个变体成员**，你还可以运行多路测试。比如说你想同时尝试一个全精度 endpoint 和三个量化变体（V1、V2、V3）。只要百分比总和仍为 100% 且恰好有一个对照，这就会按预期工作。

### 度量：把平台指标与你的产品指标做 join

每个请求都由某个特定 deployment 服务，而每一项*平台指标*都按 deployment 提供——所以对比中的基础设施部分（每个队列的延迟、错误、吞吐）只是一个过滤器的事情，不是一个项目。产品部分则归你：记录每个响应由哪个 deployment 服务（它在响应元数据里），连同你的质量信号——评分、重试、任务完成——一起存下来，join 的键就是 deployment ID。平台刻意不去猜测你的质量指标；它让归因变得轻而易举，判断交给你的分析系统。

### 结束：先晋升，再删除

假设实验显示变体胜出。结束它是两步流程：

- **通过 rollout 晋升。**从对照 deployment 向变体 deployment 执行一次蓝绿 *rollout*。健康门禁、传播等待和回滚保护全部生效。
- **删除实验。**所有实验路由消失，100% 的流量随后遵循 endpoint 的基础流量切分——而 rollout 之后，基础切分正指向你的胜出者。

而如果变体落败，你只需删除实验，流量会全部回到对照。在后端，变体 deployment 会缩容到零或被删除。

```
    
tg beta endpoints rm abx_abc123        # 删除实验；100% 流量回到基础切分
tg beta endpoints rm dep_variant123    # 或者删除变体 —— 自动拆除实验 + 切分
    
```

## 边缘情况

**变体在实验中途劣化，影响范围（blast radius）有多大？**

只有它自己的队列。各个 deployment 被独立监控、独立自动扩缩容，这意味着一个挣扎中的变体不会把对照拖下水。修复方法：重新发送不含这个故障变体的成员集，它的用户会在一定的传播时间内回到对照。这也是为什么从 5% 起步是个好主意。

**实际观测到的份额真的和配置的百分比一致吗？**

在有意义的流量下，是的！想看实际效果，参考下面的实验。在小窗口内你会遇到采样噪声：1,000 个请求里的 5% 份额是个小样本。如果你的观测份额偏差很大*并且*持续偏差，请检查上文的设置规则。

**同一个 endpoint 上可以同时跑 A/B 实验和 rollout 吗？**

可以，并且组合顺序是明确定义的：路由先解析基础切分，然后是 A/B 实验（细分对照的份额），**然后**是 rollout（在源 deployment 与其 rollout 目标之间重新采样）。平台仍然强制每个 endpoint 只有一个*活跃 rollout*，但这些阶段被设计为在重叠时可以正确组合。

**队列是按用户粘滞的吗？**

分配使用请求的**采样键（sampling key）**，例如请求体顶层的 `prompt_cache_key` 或 `user` 字段，因此携带相同键的请求会一致地路由，同一个用户在整个会话中可以稳定停留在一个测试分支上。没有键的请求实际上是每个请求随机分配（我们下面的实验测量用的就是无键流量，这正是观测份额与百分比如此接近的原因）。如果你的研究需要按用户保持一致——尤其是多轮对话的质量对比——请发送一个稳定的 `user` 字段。

**切分之下自动扩缩容会怎样？**

每个成员 deployment 按自己的策略扩缩容，规模由自己那份流量决定。一个变体占 5%、边界 1-2，对照占 95%、边界 2-8，是完全正常的形态。你应该独立关注每个队列的副本数，下图记录的就是这一点。

## 完整演示一个 A/B 实验：从开始到结束

我们在一个真实 endpoint 上跑了完整生命周期：按 95/5 创建，提升到 80/20，提升到 50/50，然后删除。期间维持稳定的 3 RPS 请求流，每个请求都归因到服务它的那个 deployment。下图展示了变体侧看到的流量，绿点记录变体的流量份额：

以下是每个阶段配置的与实际观测的流量份额：

| 配置（对照 / 变体） | 实际观测 | 请求数 |
| --- | --- | --- |
| 95 / 5 | 95.3 / 4.7 | 1,330 |
| 80 / 20 | 79.2 / 20.8 | 1,348 |
| 50 / 50 | 50.2 / 49.8 | 1,348 |
| 已删除 | 100.0 / 0 | 360 |

这次运行中值得指出的三个细节：

- **每次提升真的只是一个调用**，用当前的 `etag` 重新发送完整成员集即可。两次提升之间 etag 从 `1 → 2 → 3` 递进；一个过期的 etag 会被拒绝，而不是悄悄覆盖队友的改动。
- **传播很快但不是即时的。**我们在每次更新后等待约 75 秒再测量；路由层感知实验变更的时间尺度与流量切分变更相同，约 30–60 秒。
- **删除：**移除实验后我们连续发送 360 个请求，全部落在对照上。除了删除本身，没有遗留的分组逻辑需要拆除。

## 自己动手试试！

你需要一个带对照 deployment 正在服务流量的 endpoint，外加一个候选 deployment（已创建、处于 `READY` 状态、*不*在流量切分中）。然后：

- 按 **95/5** 创建实验。
- 让它运行直到积累足够流量——5% 的全部意义就在于曝光保持低位的同时收集数据。
- 数据说话时，用一次 update 提升；结论明确时，用 rollout 晋升。结束后删除——没有别的需要清理。
