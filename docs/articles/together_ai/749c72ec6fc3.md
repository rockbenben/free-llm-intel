# Together Post-Training 上线：按你的方式做前沿级模型后训练

- 作者：Ivan Provilkov, Gleb Khaykin, Denis Mazur, Nikita Smetanin, Egor Timofeev, Conner Manuel, Felix Zhang, Alex Mazitov, Jasmine Li, Gleb Vazhenin, Sergei Vorobyov, Qingyang Wu, Derek Petersen, Arseniy Belorukov, Artem Chumachenko, Aman Singhal, Alpay Ariyak, Jisen Li, Vladimir Malinovskii, Maksim Abraham, Zhongzhu Zhou, Denis Fedorenko, Sonny Khan, David Wang, Jennifer Wu, Max Ryabinin
- 目录[40+ 个被生产环境选中的模型……40+ 个被生产环境选中的模型……40+ 个被生产环境选中的模型……](https://www.together.ai/blog/together-post-training)

我们正式推出 Together Post-Training——一个在我们平台上构建自定义模型的新服务，既能通过 RL 用环境奖励来训，也能通过 SFT 用监督数据来训。这项服务的设计目标，是让你在不必背负沉重 infra 负担的情况下，获得灵活而高效的模型塑造。

Together Post-Training 让定义 training loop 变得简单，而我们在底层对系统与基础设施做协同优化，兼顾模型质量与训练速度。现在，没有任何东西横亘在你和那个*独一无二属于你*的最佳模型之间。

## 自定义模型的价值

2026 年，为你的 AI 工作负载训练自定义模型已经不再是个小众话题。企业正在主动探索它，用来降低成本并提升特定任务上的表现。许多 AI-native 和 AI-forward 的组织不再只靠 context 或 harness 工程来修正模型行为、提升效率，而是直接训练专职的 agent，以 frontier 模型一小部分的成本和运行时间达到同等质量。除此之外，自己训模型还带来更强的掌控力和灵活性：产出的 checkpoint 可以部署在任何位置，可以继续打磨，甚至可以在本地使用。

在 Together，我们希望让每一位 AI 开发者都能尽可能省心地为自家任务拿到最好的模型。要给一个好模型做后训练，得在数据整理、训练算法和评测协议上反复迭代。更麻烦的是，RL 的基础设施还在变得越来越复杂，「一处效率优化」和「一个拖住你整个 run 的隐性 bug」之间只有一线之隔。要把这些在大模型上可靠且规模化地完成，本身又是另一套挑战。

frontier 实验室为上面的每一个问题都配了整支队伍。一次性啃下所有挑战是一笔巨大的投入，所以很多本可以从后训练受益的公司根本没开始，或者开始了就卡住。Together Post-Training 负责全部优化和基础设施，又不去碍你的手；我们的 forward-deployed 团队与客户并肩合作，帮忙把端到端的工作流跑通。这让每一位研究者或领域专家都能专注自己最擅长的事，其余的交给我们。

## Together Post-Training 概览

后训练的复杂度一直在演进，围绕它的工具也该跟着演进。Together Post-Training 提供一套 ML 开发者熟悉的常见抽象，也让你能掌控每个实验所使用的资源，同时保证底层的所有计算既快、又省钱，而最重要的，是正确的。

我们之所以把服务建成这样，是为了给你的实验提供最高程度的灵活性。你可以跑 LoRA 训练，包括让多个 LoRA adapter 共享同一份 GPU 容量；也可以在部分模型上跑全权重实验。与我们的 [fine-tuning 服务](https://www.together.ai/fine-tuning)不同，Together Post-Training 的整个 training loop 都由你来定义。你可以使用最契合你这套配置的数据、environment 或 agentic harness，也可以在训练过程的任意环节加上你需要的步骤（例如 logging 或外部 benchmark）。完整工作流如下：

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6ad63421bade9a234b1c05a1_6ad6340765d98d48127a6d24_post-training-workflow-overview.png)

*使用 Together Post-Training 的高层概览。左：在用户侧执行的命令；右：在 Together 侧运行的服务组件。*

所有实验都跑在 Model Resources 上——那是完全属于你的 GPU 配额，不必和其他人的请求争抢优先级。每个 Model Resource 可以承载一个或数个 Training Session，每个 session 对应一个使用同一 base model 的实验（例如一组 LoRA adapter）。这意味着你能拿到最佳的 rollout 与训练性能，因为你永远不必与在同一硬件上执行的其他用户请求竞争。同时，专属的 GPU 配额意味着你可以跑全权重 finetuning，在适配大规模知识密集型任务时走得比 LoRA 更远。

分配好 model resource 并启动 session 之后，你就可以执行 training loop 的每一步。每个 session 包含一个 Trainer 实例，负责运行前向/反向步骤并更新权重，以及若干 Generator 实例，负责从 policy 执行 rollout。针对每一个模型，我们都深度优化训练与 rollout 性能，确保所有操作既快、又在各栈之间数值对齐。如果是 SFT，你可以用 0 个 generator 启动 model resource 以节省成本。trainer 参数在哪个时点发送给 generator 由你决定；我们也支持异步 RL，让两部分始终保持很高的 GPU 利用率，尤其在长 agentic rollout 的场景下。

我们既支持一批标准 loss（从 cross-entropy 和 GRPO 到 CISPO 和 DPPO），也允许你在本地计算自定义的训练目标，把它的梯度发给 Trainer 去计算更新。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6ad63420bade9a234b1c0599_6ad63405c21d46af1248bce7_post-training-custom-loss-example.png)

*自定义 loss 训练示例，出自 *[*Together Post-Training 文档*](https://docs.together.ai/docs/post-training/custom-loss-functions)

Together Post-Training 上线时带来一批领先的开放权重模型，包括 Muse Spark Open、GLM 5.3、Kimi K3 和 Qwen 3.8-27B。未来几周我们会扩充这份清单，确保你既能用上能力最强的 frontier LLM，也能用上高效的小模型。

## 质量、性能与效率

把后训练基础设施的内部细节交托出去，是个需要勇气的决定。我们的团队在复杂机器学习系统里抓过隐性 bug，这是第一手经验——从推进 RL 研究的前沿，到训练过服务数百万用户的 LLM。我们明白 **最好的训练栈，是能让你拿到最好模型的那一个**，而搭建这样的基础设施要求所有组件都被仔细实现并协同设计。

出于这些原因，我们在开发这项服务时把产出模型的质量当作北极星。影响 RL 结果的老大难问题之一，是训练引擎与推理引擎之间的对齐：如果同一份模型权重因为数值不匹配而产出略有差别的输出，整个 run 可能表现不佳甚至崩掉。我们消除训练与推理之间大量造成 policy 漂移的来源，既使用 [Rollout Routing Replay](https://arxiv.org/abs/2510.11370) 这类标准技术，也使用由我们在训练稳定性上的研究驱动的进阶优化。

除了模型质量，我们也致力于让每一次 run 尽可能快、尽可能高效，因为后训练需要多轮迭代：run 结束得越早、花费越少，你能验证的想法就越多。RL 的大部分时间花在生成 rollout 上，这让我们得以复用 Together 推理产品背后多年的研究与工程积累。我们的 rollout 引擎汲取的就是自家 serving 栈的同一套优化。对多轮 agent，智能的缓存与路由把冗余计算降到最低，同时把内存成本控制在界限之内。训练侧，经过优化的并行策略与 sequence packing 同时加速 SFT 和 RL 步骤。

用 Together Post-Training，每个实验按它真正需要的量来定规格，多一分都不用付。如果你的实验卡在 rollout 并发上，你可以申请精确数量的 sampler 副本。几个 LoRA 实验可以共享一个 model resource，所以跑一轮 sweep 并不意味着给每个配置都预留更多 GPU。我们按 GPU-minute 对每个 model resource 计费，但得益于 dedicated 与 multi-LoRA serving 栈上的大量优化，一旦你把实验规模拉起来，训练的总成本就会低于按 token 计价。

## 训练之后的优化部署

后训练实验做完之后，把每个产出的模型并排跑起来对比输出往往很重要。我们现已在 Dedicated Model Inference 中支持 [multi-LoRA adapter serving](https://docs.together.ai/docs/post-training/multi-lora-deployment)：不必为每个 run 单独起一个生产部署，你可以在一个 GPU 部署里按自己的节奏切换 adapter，帮助你降低 serving 成本。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6ad63420bade9a234b1c059e_6ad63406492c6c1fe7742748_post-training-train-evaluate-serve.png)

最后，把模型转换成在生产环境中以最高吞吐运行，意味着相比 rollout 生成，它可能运行在更低的精度、不同的硬件配置和不同的 kernel 上。通过算法层面与系统层面改进的组合，我们确保每个训练 checkpoint 在 serving 时都保住了质量，即使从 multi-LoRA 采样切换到全性能的 [FP4 精度 merged inference](https://docs.together.ai/docs/post-training/prepare-for-fp4-inference) 也一样。

## 上手

要开始你的第一批后训练实验，请安装最新的 [Together SDK](https://github.com/togethercomputer/together-py) 并[阅读文档](https://docs.together.ai/docs/post-training/overview)。我们还提供一批 cookbook 来帮你上手 Together Post-Training，可在 [github.com/togethercomputer/post-training-cookbook](https://github.com/togethercomputer/post-training-cookbook) 找到。这些 cookbook 提供的示例包括：在标准 GSM8K benchmark 上用 GRPO 训练、把 DPO 实现成自定义 loss，以及在同一个 model resource 内训练多个 LoRA adapter。如果你已有的配置用上了 Tinker API 这类后训练服务，我们也提供一个从它们迁移过来的简单办法：脚本里换掉一行，其余都可以保持不变：

```
-import tinker
+import together.post_training.tinker as tinker
```

更多细节请阅读我们的 [Tinker 迁移指南](https://docs.together.ai/docs/post-training/migrate-from-tinker)。
