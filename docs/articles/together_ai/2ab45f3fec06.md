随着开源模型质量追平闭源模型，大量开发者与组织正寻求转向开源模型，以换取更多所有权、掌控力和经济性。本文深入剖析开发者从闭源转向开源时需要考虑的开放模型 AI 技术栈。

用开放模型做 agentic 软件开发，不需要你学会训练模型、买一整架 GPU，或成为机器学习专家。从应用开发者的视角看，这套栈与使用闭源模型出奇地相似：你有一个回答 prompt 的模型，和一个管理你与模型之间交互的 harness。

如果你已经会用 Claude Code，你离用上开放模型比你想的近得多。

## MIGHT 技术栈

这套栈可以拆成以下独立部分：

- **Model（模型）：** 解读你的请求、决定做什么的组件。
- **Inference（推理）：** 模型实际运行的基础设施与推理提供商。
- **Gateways and routers（网关与路由器）：** 决定哪个模型或提供商处理每个请求的层，在成本、速度与能力之间做平衡。
- **Harness（外壳）：** 管理对话、给模型工具访问权、并把它连到你的代码库的应用。
- **Tools（Skills 与 MCP）：** 告诉模型如何做特定任务的知识，包括给模型和 harness 提供相关上下文。

这些层彼此独立，这为每一层做出更适合你开发工作流的技术决策打开了大门。相应地，这让你能在新模型发布的当下就上手实验。

新模型不断涌现。有的更快，有的更便宜，有的在某类工作上出奇地好。如果换模型只需几分钟而不是重建工作流，你就真的能去实验它们。

本文会逐层探索这套栈，解释每层做什么、可以如何定制。我们从模型层开始。

## 模型

模型接收你的 prompt，基于训练数据预测最可能的后续 token 来生成响应。在我们的栈里，它扮演智能层，负责推理、决策、决定在你的代码库里改什么。

模型大小不一，总体上越大的模型能力越强、推理越好、复杂任务表现越可靠。多数主流开放模型如今是 Mixture-of-Experts（MoE）模型，包含许多专精"专家"，但每次 token 生成只激活其中一小部分。这让它们参数总量更大、却只需激活较少参数，运行所需算力因此更少。

### 大模型

大模型通常以其参数量和训练所用算力定义。这些模型有超强的能力，从训练数据中识别模式、关系与抽象。实践中，"大"通常还意味着模型在更多数据上、训练更久、消耗了显著更多的算力资源。

这些额外容量转化为几项重要收益。大模型更擅长多步推理——需要同时跟踪多个约束、并根据问题前文做决策的场景。这使它们在接到含糊或说明不足的任务时表现出色，因为它们能调用更广泛的学习模式来补齐缺失细节。

大型开放模型的一个好例子是 [Kimi K3](https://www.together.ai/models/kimi-k3)，总参数 1.8T、激活参数 104B。当你需要执行复杂任务时选用 Kimi K3 这样的大模型，例如：

- 重构现有认证系统
- 把代码库升级到新框架
- 审查 pull request
- 理解一个 SQL 数据库为何突然变慢

大模型的一个优势是跨类型工作的鲁棒性。它们可以在写代码、解释系统、调试问题、规划变更之间切换，而不需要 tightly scoped 的指令。这让它们在 agent 式工作流中格外有用——模型要决定下一步做什么，而不是简单执行一条指令。

大模型也更善用长对话。当一次给出许多文件、日志或信息片段时，它们能维持连贯性、跨整个输入关联相关细节。

这也许会让你觉得大模型总是更好，但实践中大小模型之间存在取舍。接下来看选择小模型的理由。

### 小模型

大小之别与其说是质量，不如说是它们能从容处理多少歧义。

当任务定义清晰、范围严格时，小模型能与大得多的模型表现相当。如果你通过明确说出想要的来消除歧义，它们会变得极其有效。

小模型擅长规格明确的工作，因为它们不需要猜你的架构、推断隐藏需求或探索多种可能的解读。它们就是照指令执行。

小型开放模型的例子是 [GLM 5.3 Flash](https://www.together.ai/models/glm-5-3-flash)，总参数 320B、激活参数 18B。与 Kimi K3 对比，它大约小 6 倍、便宜约 20 倍。

当任务狭窄、规格明确时，这些模型好得令人惊讶，例如：

- 更新这个函数以接受另一个选项。
- 为这个文件写测试。
- 解释一个具体错误。
- 审查这个 50 行函数的 bug。
- 重命名这个 API 并更新其调用方。

这些任务没有多少歧义。模型不需要建立对你整个代码库的详细理解，也不需要在几种架构方案间抉择。

小模型最重要的优势是运行显著更快、更便宜。

生成每个 token 需要更少算力。实践中这意味着更低的延迟响应和更低的每请求成本。对许多日常编码任务，这个速度差异立即可感——模型回得快、迭代发生得快、你可以反复运行而不担心成本。

与其把大模型看作"比小模型好"，更好的方式是把它们当作工具箱里的两类工具。

### 模型即工具

更大的模型可能更可靠地解决问题，但也可能慢好几倍或贵好几倍。如果一个小模型能正确完成同样的单文件改动，几乎没有理由拿大的。

随时间推移，开始把模型选择当作挑工具，而不是选冠军。

从一批大模型和小模型开始，通过反复使用了解它们的能力与局限。你很快会形成判断：代码库里的哪些任务可以交给不同尺寸的模型。

接下来看在哪里找模型。

### 挑选模型

新模型每周发布，多到不可能全部亲自评估。

[The Open Frontier](https://www.theopenfrontier.com/) 和 [Artificial Analysis](https://artificialanalysis.ai/agents/coding-agents) 这样的排行榜对发现可得模型、粗略了解模型在智能、编码能力、速度和价格上的比较很有用。

不要花太多时间去认定排行榜上唯一最好的模型。基准把大量行为压缩成一个分数，而你的实际负载具体得多。一个总体排名稍低的模型，可能在你每天做的那类编码工作上非常出色。

作为参考，目前该领域最受欢迎的开放模型是 GLM 5.3 Flash、[DeepSeek V4 Flash](https://www.together.ai/models/deepseek-v4-flash-0731)、Kimi K3 和 [MiniMax M3](https://www.together.ai/models/minimax-m3)。不过这些变化极快。

选定几个要试的模型后，下一步是找托管它们的提供商。

## 推理提供商

因为开放模型在单一生态之外可得，你可以选择它们在哪里运行。最简单的起步方式是云推理提供商和云网关。

这些提供商的工作方式是：你发一个 API 请求，他们在自己的 GPU 上运行模型。你按发送给模型的输入和模型的输出付费，以 token 计量。

这让云提供商非常适合实验。想试新模型，创建一个 API key、指定模型名、开始发请求即可。[Together AI](https://www.together.ai/) 等提供商提供大目录，单一账号即可访问许多不同的大小模型。

两个提供商运行同一模型，通常应产生相近结果——尤其当你使用相同模型版本和采样设置时。性能、价格、延迟和 API 特性可能有差异，但底层模型是同一个。

这种分离意味着：你先因为喜欢模型的行为选模型，再按价格或性能选提供商或网关。

## 网关与路由器

并非所有推理提供商都统一托管所有模型，这不幸地意味着你不能只用一个推理提供商覆盖所有模型。网关和路由器通过让你跨多个推理提供商访问许多不同模型来解决这一点。当你想在闭源与开放模型之间路由时尤其有用。

网关位于多个推理提供商前面，把它们聚合在一个 API 之后，让你跨不同后端路由请求、比较价格与延迟、换模型而不用改代码。它充当与你和底层推理提供商之间的翻译和路由层。两个值得探索的流行云网关是 [openrouter.ai](https://openrouter.ai/) 和 [vercel.com/ai-gateway](https://vercel.com/ai-gateway)。

你也可以用 [litellm.ai](https://www.litellm.ai/) 这样的工具在本地或自己的服务器上运行自己的路由器。这些路由器给你一个单一 API endpoint，让你在已配置的多个推理提供商账号之间路由。

选定推理提供商或云网关后，下一步是设置你的 harness。

## Harness

Harness 是栈中你直接交互的部分。它通常是运行在你电脑上的程序，位于你、你的代码库和模型之间。它维持对话，并给模型可用于与真实世界交互的工具。

假设你问：

> 这个代码库里认证是在哪里处理的？

Harness 把问题发给模型。

模型可能决定回答这个问题的第一件事是搜索代码库中 `auth`、`session` 或 `login` 这类词。它响应时请求 harness 运行这些搜索。

Harness 在你的电脑上运行搜索命令，把结果发回模型。

基于这些结果，模型请求 harness 读取几个文件的代码。Harness 把这些文件内容加入与模型的对话。

几轮之后，模型已有足够信息回答你的认证问题。它可以答出代码库里所有包含认证代码的文件与行号。

重点在于：模型并没有搜索你的文件系统或执行 shell 命令。模型决定该发生什么，harness 是让事情发生的那部分。

这意味着编码 agent 的质量不只取决于模型。

好的 harness 知道如何暴露工具、收集相关上下文、管理长对话、应用补丁、展示变更、在合适时机请求许可、以及命令失败时恢复。

同一个模型在两个不同 harness 里，手感可以明显不同。

### 挑选 harness

和模型一样，可选的 harness 清单也在不断增长。

这些 harness 形态各异：有终端 CLI harness、在 IDE 内运行的编辑器扩展、提供更可视化界面的 Web 或桌面应用。

理念上也有很大差异。

一个 harness 可能暴露数十种功能、集成、后台 agent 和项目管理工具。另一个可能有意只给对话、shell 和文件编辑。两种路线没有天然优劣。

以下是几个支持开放模型的流行 harness：

- PI：[https://pi.dev/](https://pi.dev/)
- OpenCode：[https://opencode.ai/](https://opencode.ai/)
- Amp：[https://ampcode.com/](https://ampcode.com/)

多数 harness 都很容易从一个提供商或模型换成另一个。事实上，这常常是开源 harness 的卖点。换模型往往是一条命令或一处配置改动。

对 Claude Code、Codex 这样的闭源 harness，你可以用 [TogetherLink](https://togetherlink.vercel.app/) 这类工具把它们连到当今流行的开放权重模型。

选定 harness 后，下一步是为你自己的工作流定制它。

## 工具（Skills 与 MCP）

Harness 还可以通过 skills 和 MCP server 扩展。这些是有用的附加件，提供你的 harness 可以共享给模型的指令与工具。

Skills 是可复用的指令，告诉模型如何执行特定任务或使用特定工具。与其把所有东西塞进一个大 prompt，skills 可以由 harness 在需要时加载，给模型部署应用、审查代码或使用某框架等专业领域的知识。你可以在 [skills.sh](https://www.skills.sh/) 网站发现社区 skills。

MCP（Model Context Protocol 的缩写）是一个标准，通过共同接口把 AI agent 连接到外部工具与数据源。这些 server 让 harness 与数据库、API、文件系统和开发者工具交互，而不需要每个都定制集成。你可以在 [mcp.so](https://mcp.so/) 网站找到现成的 MCP server。不同提供商也有自己的 MCP server，例如 Together AI 的在[这里](https://docs.together.ai/docs/agent-skills#docs-mcp-server)。

接下来探索如何有效管理工作流中的上下文。

### 管理上下文

一旦你开始在模型之间切换，上下文就变得重要。

上下文是当前对话中分享给模型的一切。它包括你的 prompt、模型此前的响应、harness 附加的文件、shell 输出、搜索结果、工具调用，以及会话期间累积的任何东西。

模型能处理的上下文有上限。即使还没触及这个硬限制，非常长的对话也会变得不那么有用。

一次编码会话可能从狭窄定义的任务开始，最终累积二十个文件、几种失败方案、几页测试输出，以及不再相关的讨论。

模型现在每次响应都必须穿过这一切来推理。

改善模型输出最简单的方法之一，是知道何时结束当前会话、开启新对话。

### 新会话

对 agent 工作流能做的最简单改进之一就是更频繁地开新线程。

例如，完成一个任务后，在开始下一个任务之前务必开新会话。或者你试了一种方案、想换个角度重新思考问题，就从新开始。

如果你换模型，也最好从新开始。

因为对话本身会影响模型处理问题的方式。一个新模型被丢进一场漫长的调试会话，会继承前一场会话的所有假设、实验和死胡同。

### 规划、实现与审查

值得一试的工作流是把你的 prompt 拆给三个不同模型，各有明确目标。第一个模型规划，第二个模型实现，第三个模型审查。

大模型是出色的规划者。它们能把开放式 prompt 拆解为定义良好、彼此隔离的任务。

然后用小模型逐个开始实现每个任务。为每个任务创建新会话，保持上下文小而专注。如果某个任务对小模型太复杂，换大模型让它完成。

最后，任务完成后由大模型审查全部工作。审查中出现问题，整个过程可以重来：从审查反馈创建新的规划会话，让整个过程自循环。

这个方法的一个好处是不必把它变成正式系统。熟练运用不同模型，让你在代码库中工作时随时在规划、实现、审查之间快速跳转。

## 为实验而构建

理解栈的各层，让你能轻松实验不同模型、提供商和 harness，而不必改变整个工作流。多数情况下，换模型就像改一个配置值一样简单。换提供商只是把同一个 harness 指向不同的 API endpoint。即使是引入路由器或网关这样更结构性的变化，也可以在不触碰你日常工作方式的前提下加入。

这种分离消除了采用新模型常见摩擦。你不必承诺单一系统，而可以把模型当作稳定工作流中可互换的组件。你的 harness 保持一致，工具和快捷键不变，只有底层智能层在变化。这让你在真实任务上试驾模型、在实践中比较成本与延迟、并逐步建立"什么模型最适合什么问题"的直觉变得容易。

你可以通过升级模型、切换提供商或加入路由层，持续迭代你的技术栈，而不会丢失日常开发工作的节奏。

## 开放技术栈

开放模型最令人兴奋的部分，不只是有更多模型可选，而是整个技术栈变得可组合。

你可以按任务选模型，按价格与性能选提供商/网关，按自己的工作方式选 harness，再用工作流需要的 skills 和工具扩展这个 harness。

例如，你的编码技术栈可以是：OpenCode 作 harness，GLM 5.3 Flash 跑在 Together AI，加上构建优秀 UI 的 [grill-me](https://www.skills.sh/mattpocock/skills/grill-me) 与 [hallmark](https://www.skills.sh/nutlope/hallmark/hallmark) skills，加上用 Playwright MCP 做浏览器自动化。

这些组件没有一个需要来自同一家公司。如果下周出了更好的模型，你直接换上即可，其他什么都不用换。有了开放权重模型，你还可以把模型带去别处、甚至自己运行（哪怕是在自己的笔记本上，用 [ollama](https://ollama.com/) 这类工具）。

这才是开放模型的更大承诺。

不是选择一个 AI 编码产品，而是构建你自己的 AI 编码技术栈。
