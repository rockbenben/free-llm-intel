# LLM 推理的自动缩放端点

在专用推理上为冷启动选择扩展指标、调整窗口和预算。

总结

借助 Together AI 平台上的专用模型推理，您可以根据推理引擎实际理解的指标（例如正在进行的请求、TTFT、GPU 利用率、令牌吞吐量）自动扩展您的部署。您可以设置副本边界，选择一个指标和目标，然后调整两个窗口来控制其扩展的急切程度和缩小的耐心程度。了解并选择正确的指标非常重要，因为它决定了您的部署在高峰流量下的表现，并影响用户将看到的延迟。下面我们将介绍如何选择正确的自动缩放指标，并展示一个在三种不同的自动缩放策略下重放相同负载的实验。

## 过度配置和不足配置的成本都很昂贵

使用[专用推理](https://www.together.ai/dedicated-model-inference)，您按副本分钟付费，这使得容量规划在两种故障模式之间取得平衡：

- **过度配置 -** 您需要为 GPU 支付 15% 利用率的费用，这样您就可以在峰值流量到达时处理峰值流量。几乎永远不可行，尤其是在当前 GPU 受限的环境中。
- **配置不足 -** 当流量超过您的副本可以批量处理的流量时，您的 p95 性能就会急剧下降。 LLM 服务会非线性降级：达到并发限制的副本不会变得“慢一点”，它会开始排队，并且 TTFT 可能会从 200 毫秒增加到 15 秒。

“只是自动缩放”是显而易见的答案，对于无状态 Web 服务来说它大多有效。但 LLM 服务是一个不同的野兽，它打破了经典自动扩展所依赖的两个假设：

- **CPU 风格的指标与负载有关。** 当引擎的请求队列已经备份时，GPU 可以读取 60% 的利用率，并且利用率正在测量算术强度，而不是*压力*。根据错误信号扩展部署意味着系统将响应一个无法描述实际问题的数字。
- **冷启动可能需要几分钟的时间。** 必须将新的副本放置在 GPU 节点上，提取数十 GB 的权重，将它们加载到 VRAM 中，然后进行预热。这意味着您无法通过扩展来摆脱峰值，因为当峰值到达时，扩展已经为时已晚。这意味着一个好的自动缩放器的工作是尽早对“领先”信号采取行动。

由于这些细微差别以及每个客户的不同要求，我们的平台为您提供了一系列推理本机指标，并允许您选择部署的扩展方式。这篇文章可以帮助你更好的选择！

## 它是如何工作的

每个部署都带有一个自动缩放策略：副本边界、一个或多个带有目标的缩放指标以及计时窗口。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a68e81509533799cd7b59f9_CleanShot_2026-07-09_at_21.10.56.png)

控制循环如下：观察到的指标→所需的副本（“ceil（N×观察到的/目标）”）→时序窗口抑制→限制到边界→GPU放置。观察到的负载反馈和环路不断评估，并自动根据容量进行流量分配。

核心循环是成比例的，这意味着如果您的目标是每个副本有 8 个正在进行的请求，而您观察到的是 16 个，则系统将需要两倍的副本（假设 2x 副本在最小、最大范围内）。计时窗口可用于添加去抖动效果，以便副本计数不会振荡：

- **`scale_up_window`**：添加副本之前压力必须持续多长时间。保持简短；错误扩展的成本仅为几分钟的复制时间，而错过扩展的成本则是增加了面向用户的延迟。
- **`scale_down_window`**（默认**5m**）：在删除副本之前，事情必须保持平静多长时间。保持比流量的自然节奏更长的时间；错误的缩减成本可能会导致下一个高峰到来时的冷启动。

这种急切向上和耐心向下自动缩放窗口的不对称权衡对于调整非常重要，并且需要直观地了解您的特定流量分布。向上窗口错误会花费金钱，而向下窗口错误会花费延迟*和*金钱（因为您只想直接扩展，在备份过程中支付冷启动费用）。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a68e85018101149cbe9a7df_CleanShot_2026-07-09_at_21.41.22.png)

设置它是一个补丁：
```
    
tg beta endpoints update ""$DEPLOYMENT_ID" \
  --min-replicas 1 --max-replicas 6 \
  --scale-up-window 60s --scale-down-window 300s \
  --scaling-metric ttft --scaling-target 500 --scaling-percentile p95
    
```
需要记住的一些设置：

- `min_replicas == max_replicas` ：这会导致固定大小的部署，自动缩放实际上已关闭。
- 将两者设置为“min_replicas = max_replicas = 0”→部署**停止**（状态“STOPPED”，计费停止）。这可以用作暂停开发端点的一种方法。
- 给出一个范围可以打开缩放功能；如果您设置了界限但没有指标，平台将应用默认值：**`inflight_requests`，目标为 8**。

## 底层：自动缩放的指标

您可以自动缩放的八个指标。选择正确的方案取决于您想要保护您的部署免受什么影响。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a68e8e4f4380c27de8a29eb_CleanShot_2026-07-09_at_21.42.21.png)

自动扩展指标包括并发驱动（领先；安全默认）、SLO 驱动（跟踪；按承诺扩展）、效率驱动（成本优先）。如果您附加多个指标，则使用列表中的第一个指标。

选择正确指标的三种方法：

- **并发驱动（`inflight_requests`）是一个安全的默认值。** 飞行计数是一个“领先”指标：当需求超过服务但延迟明显下降之前，它会上升。该指标不需要流或百分位数选择，它直接映射到引擎如何批量请求。该指标的目标 8 表示“我希望每个副本处理大约 8 个并发请求”。您可以针对批处理良好的短提示聊天工作负载提高该值，针对需要较长时间预填充的编码代理长上下文流量降低该值。
- **SLO 驱动的指标（`ttft`、`e2e_latency`）：** 如果您与用户的合约是“一秒内的第一个代币”，那么 `ttft` p95 上的扩展正是针对这一点。延迟是一个“尾随”信号，这意味着当 p95 突破设定阈值时，用户已经可以注意到它，因此您通常应该将延迟指标与“min_replicas”中的诚实余量配对。
- 另一件需要记住的事情是每个代币的指标需要流媒体流量。 `ttft`、`decoding_speed` 和 `throughput_per_replica` 仅在流路径上发出。如果您的客户不进行流式传输，则这些指标没有数据，您不应基于它们构建自动缩放策略。 （“e2e_latency”是一个例外，因为它是针对流式和非流式工作负载进行测量的）。
- **效率驱动（`gpu_utilization`、`token_utilization`）：最大限度地利用硬件。** 这些优化成本：保持副本繁忙，仅在队列真正饱和时增加容量。使用这些指标时，您需要了解“已利用”对于您的工作负载的真正含义。如果工作负载没有延迟健康，GPU 可能会很忙，并且接近 100% 的利用率目标不会为到达突发留下空间。如果您扩大利用率，您应该仔细观察您的 p95 Grafana 图表。

在选择要扩展的指标时，请牢记此表：

|公制|措施|类型 |好用时| TTFT p95 @ c16 |
| ---| ---| ---| ---| ---|
|飞行请求 |每个副本的并发请求数AVERAGE_VALUE |默认。坚固、领先、与发动机无关 | 368 毫秒 |

## 空闲关闭和冷启动

**不存在通过自动唤醒缩放到零的情况。** `min_replicas: 0` 仅与 `max_replicas: 0` 一起使用才合法，这是一种显式“停止”部署的方法。唤醒需要显式操作，并且对已停止部署的请求会返回错误而不是触发启动。这意味着您应该围绕自动停止和显式重启窗口来规划开发和暂存端点。
```
    
      tg beta endpoints update dep_abc123 --min-replicas 0 --max-replicas 0   # explicit stop
          
```
使用此自动停止功能时，了解**冷启动预算**非常重要。您可以将冷启动视为由以下阶段组成：GPU 放置 → 权重下载 → 引擎负载 → 预热，并且部署的事件源为每个阶段添加时间戳 (pod.startup_phase_changed)：

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a68ea2950c15b85bc15f282_CleanShot_2026-07-09_at_21.55.19.png)

较大的模型可能具有相应较长的重量下载、发动机负载和预热时间。为了更好地了解这些数字，我们在下面展示了在热集群上的 1×H100 副本上运行时得到的结果：

|场景|测量 |
| ---| ---|
|基础目录模型（Qwen3.5-9B），创建→副本准备| 86s（拉取图像〜30s→开始〜30s→准备）|
|自定义微调，新的 18GB 权重，创建 → 就绪 | 145秒|
|副本就绪 → 通过路由提供第一个令牌 | +26–40 秒 |
|放大 1→2 个副本 |约 2.5 分钟 |
|从 STOPPED 重新启动（权重已在平台端）|约 1–2 分钟 |

请注意，这些窗口以分钟为单位进行测量，这意味着只有当使用之间的间隔相对于重新启动而言很长并且空闲期后的第一个用户愿意容忍显式启动（或错误然后重试流程）时，自动停止才会发挥作用。这种权衡对于开发和登台端点来说是可以的，但对于任何具有 p95 SLO 或无人值守的调用者的情况，您通常应该保留 min_replicas: 1。

## 边缘情况

**尖峰比冷启动到达得更快。到底发生了什么？**‍

现有副本上的请求队列（“inflight_requests”和引擎队列深度将增加），并且延迟将随着 TTFT 首先增加而降低，然后在新副本出现时出现错误/超时风险。这意味着，如果您的流量可以在 90 秒内激增 10 倍，并且冷启动时间为 4 分钟，那么*唯一的*防御措施是“min_replicas”余量或保持闲置容量的更高目标策略。这更多的是一个容量形状问题，而不是一个调整问题，最好在发布之前回答。

**我的自动缩放器会阻碍部署吗？**

不会。当“推出”正在进行时，平台会在两个部署上固定自动缩放范围；否则，部署的副本计数将因步骤中的缩减决策而被撤销。当部署完成或中止时，您配置的边界将自动恢复。

**扩展如何与流量分配相互作用？**

这是顺利处理的，因为流量分割权重是*每个就绪副本*（容量 = 权重 × 就绪副本），自动扩展的部署会按比例吸收更多流量，而**无需更改路由**。自动缩放和路由工作在相同的容量图上。

**为什么我的副本计数看起来像锯齿？**

这是缩小窗口短于流量自然节奏的典型症状。突发流量 + 1 分钟下降窗口 = 每个波谷缩减，每个波峰冷启动。要解决此问题，您应该加宽“scale_down_window”，直到锯齿变平。这使您可以用几分钟的复制时间来消除重复的冷启动。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a68eb2af0963b208204d5a0_CleanShot_2026-07-09_at_22.17.19.png)

## 使用不同的策略自动扩展相同的负载

我们在 Qwen3.5-9B 部署上运行此实验（每个副本 1×H100，边界 1-3），在每轮之前重置为正好 1 个副本，然后相同的脚本负载重播三次：约 12 到约 48 RPS 之间的正弦波，带有两个 80 rps 尖峰。在三种不同的自动缩放策略下重复了这一点：

- `inflight_requests` 目标 8
- `ttft` p95 目标 300 毫秒
- `gpu_utilization` 目标 75%

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a68eb4807ac0c9801146d95_CleanShot_2026-07-09_at_19.56.362x.png)

|政策 |缩放？ |复制分钟 |请求（错误）|发生了什么|
| ---| ---| ---| ---| ---|
|飞行请求 (8) | 1→2→3 | 26 | 26 40.6k (536) |对每一波浪潮都有反应；其额外的容量明显降低了p95中窗|
| ttft p95（300 毫秒）|从来没有| 18 | 18 46.4k (6) |发动机 TTFT 始终保持在目标范围内；没有看到缩放|
| GPU 利用率 (75%) |从来没有| 18 | 18 46.5k (2) |利用率从未超过 75%；没有看到缩放|

从上述运行中得到的三个教训：

- **仅触发并发信号。** 客户端 p95 在此负载下以 3-5 *秒* 运行，并且明显饱和，但“ttft”策略从未扩展，因为引擎端第一个令牌的时间保持较低：引擎的连续批处理将队列压力吸收到“总”延迟，而不是第一个令牌延迟。并且“gpu_utilization”从未扩展，因为短的突发请求使 GPU 低于 75%。这两项政策都在解读在系统饱和时看起来健康的信号。 `inflight_requests` ，直接队列压力信号是唯一发现问题的信号，这就是为什么它是默认信号。
- **容量的帮助完全如承诺的那样。** 在运行中的策略持有 2 个副本的时间段（约 6-11 分钟），其 p95 的运行明显“低于”相同负载上的单副本策略，中间面板显示了差距。
- **在选择策略之前了解副本的饱和点。** 一个副本以 3-5 秒的 p95 速度提供 12-48 rps 的服务，不会发生故障，但如果您有 500 毫秒的 SLO，那么这将是不行的。

## 自己尝试一下！

从默认值开始，然后根据证据进行调整：

- 设置实际范围（“min”=您的基本负载需求，“max”=您的预算承受范围）并采用默认的“inflight_requests”目标 8。
- 在*指标 API* 中观察一周的流量：副本计数、队列压力、p95。
- 然后，调整：延迟 SLO → 添加“ttft”策略（如果您进行流式传输）；成本压力 → 尝试通过诚实的 p95 监控进行利用；锯齿→加宽下窗。
