# LLM 推理端点的自动扩缩容

在专属推理上选择扩缩指标、调优时间窗口，并为冷启动留出预算。

摘要

在 Together AI 平台上用 Dedicated Model Inference，**你**可以让自己的部署按推理引擎真正看得懂的指标来自动扩缩容，比如 in-flight requests、TTFT、GPU 利用率、token 吞吐量。你可以设定副本上下界、挑一个指标和目标值，再调两个窗口，它们分别控制它向上扩得有多积极、向下缩得有多耐心。理解并选对指标很重要，因为它决定了你的部署在尖峰流量下会怎么表现，也影响你的用户会看到的延迟。下面我们会讲如何选对该拿来自动扩缩容的指标，并展示一个实验：同一份负载在三种不同的自动扩缩容策略下重放。

## 超配和欠配都很贵

用[专属推理](https://www.together.ai/dedicated-model-inference)时你按副本分钟付费，这让容量规划变成在两种失败模式之间找平衡：

- **超配 -** 你付钱让 GPU 闲在 15% 的利用率上，只为了在峰值流量到来时（如果它来的话）能够扛住。这几乎从来都不可行，尤其是在当前 GPU 受限的环境里。
- **欠配 -** 流量一超过你的副本能够成批处理的量，你的 p95 就会急剧恶化。LLM 服务是非线性退化的：一个到了并发上限的副本不是「慢一点点」，而是开始排队，而 TTFT 可能从 200ms 飙到 15s。

「给它上自动扩缩容就行了」是显而易见的答案，而且对无状态的 web 服务它大体管用。但 LLM 服务是另一头野兽，它打破了经典自动扩缩容所依赖的两个假设：

- **CPU 那一类的指标会对负载撒谎。** 一台 GPU 可能读出 60% 的利用率，而引擎的请求队列已经在往回堵了，并且利用率量的是算术强度，不是*压力*。拿错误的信号去扩缩部署，意味着系统会对一个并不描述真实问题的数字作出反应。
- **冷启动可能要花上几分钟。** 一个新副本要落到某个 GPU 节点上、拉下几十 GB 的权重、把它们装进 VRAM 并预热。这意味着你没法靠扩缩来冲出一次尖峰，因为等尖峰到来时再扩容已经太晚了。于是这也意味着，一个好的自动扩缩容器的职责是尽早对*先行*信号作出动作。

由于这些细微差别，再加上每个客户的需求都各不相同，我们的平台给出一份推理原生指标的目录，并让你自己选择部署怎么扩缩。这篇帖子就是来帮你选对的！

## 它是怎么工作的

每个部署都带着一份自动扩缩容策略：副本上下界、一个或多个带目标值的扩缩指标，以及计时窗口。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a68e81509533799cd7b59f9_CleanShot_2026-07-09_at_21.10.56.png)

控制回路是这样走的：观测到的指标 → 期望副本数（`ceil(N × observed/target)`）→ 计时窗口做阻尼 → 夹到上下界内 → GPU 落位。观测到的负载会回灌进来，回路持续评估，而流量切分自动跟着容量走。

核心回路是比例式的，也就是说如果你把目标定为每个副本 8 个 in-flight requests，而你正在观测到 16，系统就会想要两倍的副本（假设这 2 倍副本落在 min、max 上下界之内）。计时窗口可以用来加上一种消抖效果，好让副本数不会来回震荡：

- **`scale_up_window`**：加副本之前压力必须持续多久。把它保持在短的这一侧；一次误扩的代价只是几个副本分钟，而一次漏扩的代价是用户可感延迟升高。
- **`scale_down_window`**（默认 **5m**）：撤副本之前局面必须保持平静多久。把它保持得比你流量的自然节拍更长；一次误缩的代价，可能是在下一个峰值到来的当口正好撞上一次冷启动。

这种「扩得急、缩得有耐心」的不对称权衡非常值得调，而且要求你对自己特定的流量分布有直觉式的理解。上行窗口上的失误花的是钱，而下行窗口上的失误既赔延迟*又*赔钱（因为你转眼就想再扩回去，并在回去的路上为冷启动付费）。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a68e85018101149cbe9a7df_CleanShot_2026-07-09_at_21.41.22.png)

设置它只要一个 PATCH：

```
    
tg beta endpoints update ""$DEPLOYMENT_ID" \
  --min-replicas 1 --max-replicas 6 \
  --scale-up-window 60s --scale-down-window 300s \
  --scaling-metric ttft --scaling-target 500 --scaling-percentile p95
    
```

有几个设置需要记在心上：

- `min_replicas == max_replicas`：结果就是一个固定大小的部署，自动扩缩容实际上被关掉了。
- 把两者都设成 `min_replicas = max_replicas = 0` → 部署会**停止**（状态 `STOPPED`，计费也停了）。这可以当作一种暂停你 dev 端点的办法。
- 给出一个区间就会打开扩缩；如果你设了上下界但没设指标，平台会套用默认值：**`inflight_requests`，目标 8**。

## 底层机制：可以拿来自动扩缩容的指标

你可以拿来自动扩缩容的指标有八个。选对哪一个，取决于你想让部署免于哪一种情况。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a68e8e4f4380c27de8a29eb_CleanShot_2026-07-09_at_21.42.21.png)

自动扩缩容指标包括并发驱动的（先行；也是稳妥的默认值）、SLO 驱动的（滞后；按承诺来扩缩）、效率驱动的（成本优先）。如果你挂了多个指标，用的是列表里的第一个。

关于如何挑对指标，有三种思路：

- **并发驱动的（`inflight_requests`）是稳妥的默认值。** in-flight 数量是一个*先行*指标：当需求超过服务能力时它就上升，而且是在延迟明显恶化之前。这个指标不需要流式，也不用选百分位，并且直接对应引擎成批处理请求的方式。给它设的目标值 8 说的是「我要每个副本大约同时处理八个请求」。对于成批效果好的短 prompt 聊天类负载，你可以把它调高；对于 prefill 更耗时的 coding agent 长上下文流量，则把它调低。
- **SLO 驱动的指标（`ttft`、`e2e_latency`）：** 如果你与用户的约定是「第一个 token 在一秒之内出来」，那么按 `ttft` 的 p95 来扩缩针对的正是这一点。延迟是一个*滞后*信号，也就是说等 p95 突破你设的阈值时，用户其实已经能察觉了，所以通常应该把一个延迟指标与 `min_replicas` 里老实留出的余量配对使用。
- 还要记住的一点是，逐 token 的指标需要流式流量。`ttft`、`decoding_speed` 和 `throughput_per_replica` 只在流式路径上才会发出。如果你的客户端不走流式，这些指标就没有数据，你不该把自己的自动扩缩容策略建在它们之上。（`e2e_latency` 是个例外，因为对流式和非流式负载它都会测量）。
- **效率驱动的（`gpu_utilization`、`token_utilization`）：把硬件榨出最多产出。** 这些指标为成本而优化：让副本保持忙碌，只在整池真正饱和时才加容量。使用这些指标时，你需要理解「被利用」对你的负载到底意味着什么。GPU 可以很忙，而负载并不延迟健康，并且接近 100% 的利用率目标不会为到达突发留下任何余量。如果你按利用率来扩缩，就应该紧盯你的 p95 Grafana 图表。

选择要按哪个指标扩缩时，下面这张表值得放在心里：

| 指标 | 度量什么 | 类型 | 适合什么时候用 | TTFT p95 @ c16 |
| --- | --- | --- | --- | --- |
| inflight_requests | 每个副本的并发请求数 | AVERAGE_VALUE | 默认。稳健、先行、与引擎无关 | 368 ms |
| ttft | 首个 token 的耗时 | VALUE • 百分位（默认 p95） | 你对响应性有一条延迟 SLO | 323 ms |
| e2e_latency | 完整请求的延迟 | VALUE • 百分位 | 对总完成时间有 SLO |  |
| gpu_utilization | GPU 忙碌百分比 | UTILIZATION（0–100） | 能容忍延迟波动的成本优先负载 |  |
| token_utilization | token 容量的使用情况 | UTILIZATION | 逼近引擎上限的批量/吞吐类负载 |  |
| throughput_per_replica | 每个副本可持续的 tokens/s | AVERAGE_VALUE | 持续生成的管线 |  |
| decoding_speed | 每个请求的 tokens/s | VALUE | 守护每个用户的生成速度 |  |
| cache_hit_rate | 前缀缓存的有效性 | UTILIZATION | 专家向：缓存密集的 serving 模式 |  |

## 空闲关停与冷启动

**没有「缩到零并自动唤醒」这回事。** `min_replicas: 0` 只有和 `max_replicas: 0` 一起才合法，而那是显式*停止*部署的一种方式。唤醒需要一个显式动作，而发往一个已停止部署的请求返回的是错误，并不会触发一次启动。这意味着你应该围绕「自动停止加上显式重启窗口」来规划你的 dev 和 staging 端点。

```
    
      tg beta endpoints update dep_abc123 --min-replicas 0 --max-replicas 0   # explicit stop
          
```

使用这个自动停止功能时，理解**冷启动预算**很重要。你可以把一次冷启动看成由以下阶段组成：GPU 落位 → 权重下载 → 引擎加载 → 预热，而部署的事件流会给每个阶段打上时间戳（pod.startup_phase_changed）：

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a68ea2950c15b85bc15f282_CleanShot_2026-07-09_at_21.55.19.png)

更大的模型，其权重下载、引擎加载和预热时段可能按比例更长。为了让你对这些数字有更好的感觉，下面给出我们在预热过的集群上、用 1×H100 副本跨多次运行拿到的结果：

| 场景 | 实测 |
| --- | --- |
| 目录基础模型（Qwen3.5-9B），创建 → 副本 READY | 86s（PullingImage 约 30s → Starting 约 30s → ready） |
| 自定义微调模型，全新的 18GB 权重，创建 → READY | 145s |
| 副本 READY → 经路由吐出第一个 token | +26–40s |
| 扩容 1→2 个副本 | 约 2.5 分钟 |
| 从 STOPPED 重启（权重已在平台侧） | 约 1–2 分钟 |

请注意这些窗口是按分钟计的，也就是说，只有当使用间隔相对于重启足够长、而且空闲期之后的第一个用户愿意容忍一次显式启动（或者「先报错再重试」的流程）时，自动停止才划算。这种取舍对 dev 和 staging 端点没问题，但对任何带着 p95 SLO 或无人值守调用方的东西，你通常应该保持 min_replicas: 1。

## 边界情形

**尖峰比一次冷启动来得还快。实际会发生什么？**

请求会在现有副本上排队（`inflight_requests` 和引擎队列深度都会上升），而延迟会随之恶化：先是 TTFT 升高，随后是错误/超时的风险，与此同时新副本正在起来。这意味着如果你的流量能在 90 秒内飙 10 倍，而你的冷启动要 4 分钟，那么*唯一*的防线就是给 `min_replicas` 留出余量，或者用一个目标值更高的策略把宽松容量垫起来。这更像是一个容量形态问题，而不是一个调参问题，而且最好在上线日之前就想清楚。

**我的自动扩缩容器会和一次 rollout 打架吗？**

不会。在一次*rollout*进行期间，平台会把两个部署的自动扩缩容上下界钉住；否则 rollout 的副本数会被某一步中途的一次缩容决定给抵消掉。当 rollout 完成或中止时，你配置好的上下界会自动恢复。

**扩缩与流量切分之间如何相互作用？**

这一点处理得很顺，因为流量切分的权重是*按每个就绪副本*计的（容量 = 权重 × 就绪副本数），一个扩容的部署会自动吸收按比例更多的流量，而**不需要任何路由改动**。自动扩缩容和路由依据的是同一张容量图。

**为什么我的副本数看起来像锯齿？**

这就是缩容窗口短于你流量自然节拍的典型症状。突发流量 + 1 分钟的下行窗口 = 每个波谷都缩容、每个波峰都冷启动。要解决它，你应该把 `scale_down_window` 放宽，直到锯齿被抹平。这样你就能用几个副本分钟的代价，消掉反复出现的冷启动。

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a68eb2af0963b208204d5a0_CleanShot_2026-07-09_at_22.17.19.png)

## 用不同策略对同一份负载做自动扩缩容

我们在一个 Qwen3.5-9B 部署上跑了这个实验（每个副本 1×H100，上下界 1–3），每轮之前都重置到正好 1 个副本，然后把同一份脚本化的负载重放三次：一个在约 12 到约 48 RPS 之间起伏的正弦波，带有两次 80 rps 的尖峰。这在三种不同的自动扩缩容策略下各重复了一遍：

- `inflight_requests` 目标 8
- `ttft` p95 目标 300 ms
- `gpu_utilization` 目标 75%

![__wf_reserved_inherit](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6a68eb4807ac0c9801146d95_CleanShot_2026-07-09_at_19.56.362x.png)

| 策略 | 有扩缩吗 | 副本分钟 | 请求数（错误数） | 发生了什么 |
| --- | --- | --- | --- | --- |
| inflight_requests（8） | 1→2→3 | 26 | 40.6k（536） | 对每一波都作出反应；它多出来的容量在窗口中段明显压低了 p95 |
| ttft p95（300ms） | 从未 | 18 | 46.4k（6） | 引擎 TTFT 全程都在目标之下；没有看到扩缩 |
| gpu_utilization（75%） | 从未 | 18 | 46.5k（2） | 利用率从未越过 75%；没有看到扩缩 |

从上面几次运行得到三条教训：

- **只有并发信号触发了。** 在这份负载下，客户端 p95 跑在 3–5 *秒*上、明显已经饱和，但 `ttft` 策略从来没有扩缩，因为引擎侧的首个 token 耗时一直保持很低：引擎的连续 batching 会把队列压力吸收进*总*延迟，而不是一阶 token 延迟。而 `gpu_utilization` 从未扩缩，是因为短而突发的请求让 GPU 停在它自己 75% 的门槛之下。两个策略读到的信号看起来都很健康，而系统已经饱和了。`inflight_requests`，这个直接的队列压力信号，是唯一看见了问题的那个，这也是它成为默认值的原因。
- **容量给出的帮助正好和它承诺的一致。** 在 inflight 策略保持 2 个副本的那段区间（约第 6–11 分钟），在完全相同的负载下它的 p95 明显*低于*单副本的那几个策略，而中间那一格图就显示出了这个差距。
- **在选定策略之前，先弄清楚你副本的饱和点。** 一个副本在 12–48 rps 下以 3–5s 的 p95 提供服务而没有倒下，但如果你有一条 500 ms 的 SLO，这就是不可接受的。

## 自己动手试试！

从默认值起步，再依据证据来调：

- 设好真实的上下界（`min` = 你的基础负载需要多少，`max` = 你的预算能承受多少），并采用默认的 `inflight_requests` 目标 8。
- 在*指标 API* 里观察一周的流量：副本数、队列压力、p95。
- 到那时才动手调：延迟 SLO → 加一条 `ttft` 策略（前提是你走流式）；成本压力 → 试试利用率指标并诚实监控 p95；锯齿 → 放宽下行窗口。
