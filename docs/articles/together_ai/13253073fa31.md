# 让开放模型适用于长期代理工作负载

线束和推理引擎必须各自做好哪些工作，才能使长时间的代理会话在长期任务中保持快速。

- 作者 Zain Hasan、Parth Sareen（Ollama）
- 目录[40+ 模型选择用于生产...40+ 模型选择用于生产...40+ 模型选择用于生产...](https://www.together.ai/blog/making-open-models-work-for-long-horizon-agentic-workloads)

总结

编码代理每次都会再次发送整个对话。前缀缓存可防止推理引擎重做该工作，但前提是该工具不考虑提示的开头，并且引擎将每个回合发送回已缓存的 GPU。 AI 和 Ollama 一起在交接的相反方向工作，因此我们写下了客户端和推理引擎端需要做什么才能成功构建代理应用程序。

编码代理具有奇怪的流量模式。每当代理采取步骤时，线束都会向模型发送迄今为止的整个对话：系统提示、每个工具定义、您的请求、代理已读取的每个文件以及它运行的每个命令。返回的通常是一个几十个令牌长的工具调用。然后又发生了，上次的一切都加上了一点。

这种大输入序列长度 (ISL) 和小输出序列长度 (OSL) 是大多数代理工作负载的特征。如果 GPU 必须每次都从头开始处理整个记录，那么长会话的每一步都会变得更慢、成本更高。 **前缀缓存**可以节省大部分工作。问题是，如果你不小心，也很容易破坏前缀缓存。

我们从相反的角度来看待这个问题。 Ollama 致力于线束集成，这意味着决定每个请求的内容。人工智能共同作用于推理引擎，这意味着决定请求到达时会发生什么。我们不断发现，双方的大部分工作都是为了保护缓存免受另一方对其进行的操作，因此我们希望将其全部记录在一个地方，以帮助代理和基础设施构建者！

## 智能体转向对于 GPU 来说是什么样的

每个请求都会经历两个阶段。第一个是预填充：引擎在一次大的并行传递中读取整个提示并生成第一个令牌。 GPU 擅长于此，因为它可以同时完成大量数学运算，从而最大限度地提高算术强度。预填充决定了在任何新令牌出现之前等待的时间。第二个是解码：模型一次写入一个标记，然后每个新标记都需要回读并参与其之前的所有内容。解码更多地受到内存带宽的限制，而不是计算的限制，并且它决定了文本流输出的速度。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af79f818c63dd9bfb9f1852_image%201.webp)

正常的聊天响应在两个阶段都花费时间，而代理轮流主要是预填充，因为输入是整个会话，输出通常是简短的工具调用。推理模型在此基础上添加思考标记，有时会添加很多标记，但随着会话增长到数以万计的标记，输入仍然占主导地位。每转一次，输入都会变长，而输出则保持大致相同的大小——一些工具调用。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af79fe9d4ce10f61a062fba_image%202.webp)

那么对于代理商来说，“这个模型有多快？”主要意思是“它能以多快的速度完成对先前转折的长期历史记录？”快速处理具有大量先前轮次的任务的方法是将其缓存并读回，而不是重新计算。

## 缓存为王

描绘 KV 缓存（甚至前缀缓存）的最简单方法是读取。想象一下，要阅读页面上的每个新单词，您必须从头开始。页面越往下看，你的速度就越慢，因为你必须不断地重读已经读过的所有内容。这是一个没有缓存的模型。缓存在单个请求中解决了这个问题：引擎保留对早期令牌（存储为中间键、值对）所做的工作，并仅计算新令牌。

前缀缓存在请求之间执行相同的操作。代理会话的第 7 回合是第 6 回合加上一点，因此如果引擎仍然保留第 6 回合的工作，则只需处理新部分。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a0c59830f120ed9f25b8_image%203.webp)

算术很简单。如果每回合添加相同的数量，则十回合不缓存过程 1 + 2 + … + 10 = 55 个提示单位。通过缓存，它们可以处理 10 次。在 100 次转弯时，这对于编码任务来说并不罕见，分别是 5,050 次和 100 次。实际转弯的大小各不相同，因此请将这些视为理想化的数字。缓存的会话也不是完全免费的，因为每个新令牌仍然需要处理缓存的会话。但该模式成立：如果没有缓存，您重做的工作会随着会话长度的平方而增长。

问题是前缀缓存从提示的开头匹配到第一个不同的标记，然后停止在那里。第一个差异之后的所有内容都必须再次处理。

添加到提示的末尾不需要任何额外费用。更改之前的任何内容，即使是单个字符，都意味着重新处理其后的所有内容。如果更改接近顶部，则您实际上已经丢弃了整个会话，现在必须重建缓存。这篇文章中的几乎所有其他内容都遵循这一规则。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a17c345302d7bf5f504f_image%204.webp)

安全带决定了第一个变化的着陆位置。当下一个请求出现时，引擎决定缓存是否仍然存在。我们将从安全带开始。

## 线束和 API

在 Ollama 方面，我们提供了通过“ollama launch”命令连接您最喜欢的线束的功能。因此，您可以将 Claude Code、Codex、Pi（等）等工具与 DeepSeek-V4.1-Flash 和 GLM-5.3 等开放模型连接起来，并维护现有的工作流程。

将线束连接到 API 似乎很容易，但线束和模型之间存在许多转换层和不同的期望。这通常是造成缓存损坏（产生时间和金钱成本）、无法解释的代理行为以及线束彻底错误的原因。

### 加载工具晚了

背带现在携带相当多的工具。如果每个定义都预先出现在提示中，那么您会将上下文花在任务永远不会使用的工具上，并且模型在选择正确的工具方面会变得更糟。较新的工具添加了工具搜索功能来缓解这一问题，代理在搜索工具后可以加载并使用该工具。

假设您有一名具有此功能的个人助理作为代理人。如果您要求代理将已加星标的事件导出到日历，它会搜索“日历”，加载 `save_calendar` 定义并调用它。

对于缓存，问题在于该定义在哪里。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a33a50a1e098dee56917_Image%205.webp)

显而易见的方法是将定义添加到工具列表中。这可行，但工具列表位于提示顶部附近、对话之前。因此，如果前缀在再次处理后更改了所有内容。在长时间的会话中，这可能是数十万个令牌。更好的方法是将定义放在最后，新内容无论如何都会放在最后。

但并非每个模型都支持这一点。某些聊天模板不希望在对话进行到一半时出现工具定义，并且调用会出错。因此，线束是否可以延迟加载工具而无需付费取决于型号。用户不必知道这一点，但构建线束的任何人都必须知道。

### 高层的事情发生了变化

破坏缓存的最简单方法是在系统提示符中添加一些不断变化的内容，例如当前时间戳、git 状态或代理不断移动的工作目录。如果线束每次都以新值重新呈现系统提示，则每次都是完全重新读取。

会话中固定但会话之间有所不同的内容（例如用户名或会话开始日期）不会损害该会话。它们确实会阻止新会话重用已缓存的设置，我们将在引擎方面进行介绍。无论哪种方式，修复方法都是相同的：将该信息一次性放入任务消息中，并保持各处的系统提示相同。

### 推理努力

我们在奥拉马一侧击中了这个。在 GLM-5.3-Flash 中，推理工作不是单独设置侧面的引擎手柄。聊天模板将其写入第一个系统块，位于工具和对话之前。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a399b2df36518f1f7f48_image%206.webp)

假设你正忙于一项长期任务，但进展并不顺利。你的努力程度从低到高。这是一个合理的做法，但现在下一个请求几乎在第一个标记处与上一个请求不同。这意味着整个会话将被再次处理。从长远来看，更改一项设置可能需要花费数十万代币。

我们的建议是在一开始就选择一个努力水平并留在那里。如果您确实需要更多思考，那么在更高的设置下开始新的会话通常比继续旧的会话更便宜，而且您也可以从中获得清晰的背景。您还可以在更改推理值之前进行压缩，以减少提示标记的数量。

### 大工具结果

工具的输出成为下一个请求以及之后的每个请求的一部分。如果代理在需要 40 行时读取了 3,000 行的文件，则您无需为此付费；您在剩余的每个回合中都需要付费（即使它被缓存，您也会失去上下文窗口）。为了解决这个问题，线束通常会减少工具的输出。这是正确的决定，但如何削减工具产量很重要。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a3e9af01ebe9d38469a5_image%207.webp)

这是一个很容易意外造成的失败。任务是修复日历导出中的时区错误。代理读取“calendar.py”，该工具返回 640 行文件的前 100 行，但没有说它已停止。重要的函数“convert_timezone”位于第 420 行。该模型不知道它丢失了任何内容。

修复是输出中的一行，告诉模型它获得了 640 行中的第 1 到 100 行，并且它可以搜索文件或请求另一个范围。这样，模型搜索“timezone”，找到第 420 行，并读取第 410 至 450 行。削减输出可以节省资金。不说出来就剪掉它，你就能得到一个模型，可以自信地编辑它从未见过的代码。

### 子代理

像 Kimi K3、GLM-5.3 和 GLM-5.3-Flash 这样的开放模型现在非常擅长分割大任务并将部分任务交给子代理。线束启动每个子代理的方式决定了它可以重用多少父代理的缓存。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a43a91420901cc5f7063_image%208.webp)

一种选择是子代理继承所有内容：相同的系统提示、工具和对话，以及其分配。边聊就是这样工作的。它们从父会话中分支出来，因此整个前缀已经被缓存。另一种选择是发送简短信息：相同的系统提示和工具，然后仅发送子代理所需的文件和说明。在这种情况下，缓存将覆盖设置，仅此而已。

严格来说，继承听起来更好，但事实并非如此。缓存的前缀处理起来很便宜，但不是免费的。子代理生成的每个令牌仍然需要读取它，并且它始终占用 GPU 内存。需要两个文件和一个清单的审阅者可能不需要三百转的历史记录。如果您为子代理提供自己的系统提示符，则它与父代理根本不共享任何内容，甚至设置也不共享。

## 发动机侧

你可以完美地完成上述所有事情，但仍然没有受益。缓存必须仍然存在，并且下一个请求必须到达保存它的机器。

在 Together AI，我们将推理引擎视为保持 GPU 忙碌的机器。单个 GPU 每年的租金约为 5 万美元，因此理想情况下它永远不应该闲置，并且在任何时候它都在为数百个用户提供服务，而每个用户的请求都处于不同的阶段。代理流量以几种特定方式推动这些限制。

### 路由请求以实现最佳缓存命中

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a49b45ce62ee261e6b63_image%209.webp)

会话的缓存位于特定数据中心的特定节点上。如果对话中的下一回合落在其他地方，则该节点必须从头开始处理所有先前的回合，并且现在两个节点正在存储相同的前缀。为了正确路由，我们首先需要选择一个运行模型、具有容量并且是会话运行的数据中心。然后我们需要在其中选择一个具有先前回合缓存的节点。

选取节点的方法主要有两种。简单的方法是使用密钥：客户端在每个请求中发送类似“prompt_cache_key”的内容，然后理想情况下我们将具有相同密钥的每个请求路由到同一节点。另一种方法是散列前缀并将请求发送到缓存了最长匹配前缀的节点，即使另一个会话将其放在那里。

第二个选项是保持系统提示相同的另一个原因。如果线束的每个会话都以完全相同的系统提示和工具定义开始，则全新的会话可能能够找到已缓存的设置。如果您在其中放置唯一标识符，那么每个会话都保证冷启动。

它也不像总是将请求发送到热节点那么简单。有时，热节点流量过载，然后选择是在那里排队等待，还是占用一个空闲节点并付费再次处理前缀。在这种负载感知路由范例中，有时缓存未命中可能是更好的选择。因此，如果后端的推理引擎未正确实现，即使是完全稳定的提示也不能保证命中。

### 在回合之间保持缓存处于活动状态

仅当仍有缓存可供路由时，路由才有帮助。代理通常会调用工具，然后在测试运行时等待几分钟。始终将该会话的缓存保留在 GPU 内存中会占用活跃用户所需的空间，而丢弃它意味着当代理从其工具调用返回时重新读取所有内容。因此，我们还可以在会话空闲时将缓存卸载到 CPU 内存，并在下一轮恢复它。

内存是其中大部分背后的限制。我们无法提前知道响应是 30 个令牌还是 30,000 个令牌，因此我们不会为最坏情况的最大上下文长度场景保留空间，而是在每个请求需要时以小块形式分配缓存内存 (PagedAttention)，这是操作系统处理 RAM 的方式。我们在每次传递时都会重建正在运行的批处理（连续批处理），因此当一个代理同时启动五个子代理时，每个新请求都会在一个子代理释放时占用一个槽，而不是等待一批中最慢的一个完成。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a4e6b74c7c6e90bb58ce_image%2010.webp)

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a4f38d1a4ce1e55f057a_image%2011.webp)

对于构建工具的任何人来说，结果是缓存内存的空间（而不是计算空间）通常限制了 GPU 一次可以处理的请求数量。每个超大的工具结果以及每个携带不相关历史记录的子代理都会占用另一个会话的缓存本可以使用的内存。

特工们还将预填充/解码的分离推向了极致，给出了巨大的提示和微小的答案。为了更好地优化这一点，我们在不同的集群上运行这两个阶段。其中一个针对计算进行了调整并进行预填充；另一个针对内存带宽进行了调整，可以同时解码数百个流，并通过 RDMA 在它们之间传输缓存。这样，一波长时间的代理提示就不会减慢其他人的令牌流。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a510c31830c1fd345d8d_image%2012.webp)

## 综合起来：一场会议，双方

这是在一次会话中所有这些内容的样子。

在线束方面，代理找到日历工具并将其添加到对话末尾，因此其上方没有任何变化。它读取“calendar.py”，发现它只获得了 640 行中的第 1 到 100 行，搜索“时区”，并读取正确的部分。努力停留在起点。审阅者子代理继承会话以根据“sessions.json”检查“agenda.ics”。

在引擎端，每次都会返回到缓存了会话的节点。当测试运行时，缓存在 CPU 内存中等待。审阅者的请求会插入到正在运行的批次中，并且每个回合仅处理新内容。

使用代理的人看不到所有这些；他们只是看到它在九十度转弯时保持快速。但只有双方都尽自己的一份力量，这才有效。线束可以使提示保持完全稳定，并且如果引擎将第 7 圈发送到错误的机器，仍然会丢失缓存。如果线束每次都改变第一条线，那么发动机可以完美地布线，但仍然会丢失它。
