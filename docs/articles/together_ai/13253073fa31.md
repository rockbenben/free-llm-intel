# 让开放模型适用于长时程 agentic 工作负载

harness 和推理引擎各自要做对什么，才能让长时间的 agent 会话在长时程任务中保持快速。

- 作者Zain Hasan、Parth Sareen（Ollama）
- 目录[40+ 个面向生产环境精选的模型...40+ 个面向生产环境精选的模型...40+ 个面向生产环境精选的模型...](https://www.together.ai/blog/making-open-models-work-for-long-horizon-agentic-workloads)

摘要

编程 agent 每一轮都会把整段对话重新发一遍。prefix caching 让推理引擎不必重做这些工作，但前提是 harness 不去动 prompt 的开头，并且引擎能把每一轮都送回已经缓存了它的那块 GPU。Together AI 和 Ollama 恰好站在这次交接的两头，所以我们把这些写下来：客户端和推理引擎两侧各自需要做什么，才能成功构建 agentic 应用。

编程 agent 的流量模式很特别。agent 每走一步，harness 都会把到目前为止的整段对话发给模型：system prompt、每个工具定义、你的请求、agent 读过的每个文件、它执行过的每条命令。回来的通常是一个几十 token 长的 tool call。然后下一次再来一遍，内容就是上次的全部再加上一点新的。

这种大输入序列长度（ISL）配小输出序列长度（OSL）的组合，是大多数 agentic 工作负载的特征。如果 GPU 每一轮都得从头处理整份记录，长时间会话就会随着每一步越来越慢、越来越贵。**Prefix caching** 省掉了其中大部分工作。问题是，稍不留神也很容易把 prefix cache 弄坏。

我们从相反的两端来碰这个问题。Ollama 做的是 harness 集成，也就是决定每个请求里放什么；Together AI 做的是推理引擎，也就是决定请求到达之后发生什么。我们不断发现，两侧的很多工作其实都是在保护 cache，免受另一侧可能对它做的事影响，所以我们想把这些集中写在一处，既帮 agent 构建者，也帮基础设施构建者！

## 一次 agent 轮次在 GPU 眼里是什么样

每个请求都要经过两个阶段。第一阶段是 prefill：引擎用一次大规模的并行处理读完整段 prompt，并产出第一个 token。GPU 擅长这个，因为这是一次性完成的大量数学运算，能把算术强度拉满。prefill 决定了你要等多久才会出现新的 token。第二阶段是 decode：模型一个 token 一个 token 地写出答案的剩余部分，每生成一个新 token 都需要回读并 attend 之前的所有内容。decode 更多受内存带宽而不是算力限制，它决定了文字流出的速度。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af79f818c63dd9bfb9f1852_image%201.webp)

一次普通的聊天响应会在两个阶段上都花时间，而一次 agent 轮次大部分时间是 prefill，因为输入是整个会话、输出通常是一个很短的 tool call。推理模型还要在此基础上再生成 thinking token，有时候还很多；但当会话增长到几万 token 时，占大头的仍然是输入。每一轮输入都更长，而输出大小基本不变——几个 tool call。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af79fe9d4ce10f61a062fba_image%202.webp)

所以对 agent 来说，“这个模型有多快？”基本上等于“它多快能过完一长串既往轮次的历史记录？”。要快速处理一个带有大量既往轮次的任务，办法就是把它缓存起来再读回来，而不是重新计算。

## Cache 为王

把 KV cache（甚至 prefix cache 也一样）想成阅读是最容易的。想象你每读页面上的一个新词，都得从顶部重新开始读：读得越靠下就越慢，因为你一直在重读已经读过的内容。这就是没有 cache 的模型。cache 在单个请求之内解决了这个问题：引擎保留之前 token 上做过的工作（以中间 key、value 对的形式存储），只计算新的那一个。

prefix caching 则在请求之间做同样的事。agent 会话的第 7 轮就是第 6 轮再加一点内容，所以如果引擎还保留着第 6 轮的工作，它就只需要处理新增的部分。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a0c59830f120ed9f25b8_image%203.webp)

算术很简单。假设每一轮新增的量相同，那么十轮下来，不做缓存要处理 1 + 2 + … + 10 = 55 个单位的 prompt；有缓存只需处理 10。到一百轮——对编程任务不算罕见——就是 5,050 对 100。真实的轮次大小会有变化，所以这些数字只当理想化估算。有缓存的会话也不是完全免费，因为每生成一个新 token 仍然要 attend 那些已缓存的 token。但规律是成立的：不做缓存时，重复的工作量随会话长度的平方增长。

关键在于，prefix cache 从 prompt 的开头开始匹配，一直匹配到第一个不同的 token 就停下。第一个差异点之后的所有内容都得重新处理。

往 prompt 末尾追加内容不会带来额外开销。改动更靠前的任何地方，哪怕只改一个字符，都意味着其后的所有内容要重新处理。如果改动靠近开头，你等于把整个会话丢掉、现在必须重建 cache。本文后面几乎所有内容，都是从这一条规则推出来的。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a17c345302d7bf5f504f_image%204.webp)

第一个改动落在哪里，由 harness 决定；下一个请求到来时 cache 还在不在，由引擎决定。我们先从 harness 讲起。

## Harness 与 API

在 Ollama 这边，我们上线了通过 `ollama launch` 命令连接你常用 harness 的能力。这样你就可以把 Claude Code、Codex、Pi 等 harness 与 DeepSeek-V4.1-Flash、GLM-5.3 这样的开放模型连接起来，同时保持现有的工作流。

把 harness 接到一个 API 上看起来可能很简单，但 harness 与模型之间隔着许多层转换和各不相同的预期。这常常是 cache 失效（既费时间又费钱）、agent 行为无法解释，以及 harness 直接报错的根源。

### 把工具定义放在后面加载

harness 现在携带的工具不少。如果每个定义都一开始就塞进 prompt，你会把 context 花在任务根本不会用到的工具上，模型挑对工具的能力也会变差。较新的 harness 为此加了 tool search 功能：agent 先搜索，找到之后再自己加载并使用该工具。

假设你有一个具备这种能力的个人助理 agent。你让它把你标星的事件导出到日历，它会搜索“calendar”，加载 `save_calendar` 的定义，然后调用它。

对 cache 来说，问题在于这个定义被放在哪里。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a33a50a1e098dee56917_Image%205.webp)

最直接的做法是把定义加进工具列表。这行得通，但工具列表位于 prompt 靠顶部的位置、在对话之前。于是 prefix 一旦改变，它之后的所有内容都要重新处理。漫长的会话里，这可能是几十万 token。更好的做法是把定义放到末尾，反正新内容本来就从那里追加。

只不过并非所有模型都支持这种做法。有些 chat template 不接受对话进行到一半时出现工具定义，调用会直接报错。所以一个 harness 能否在不付出代价的情况下延后加载工具，取决于模型。普通用户不该需要知道这件事，但做 harness 的人必须知道。

### 顶部那些会变的东西

毁掉 cache 最容易的办法，就是在 system prompt 里放每轮都会变的东西，比如当前时间戳、git status，或者 agent 不断切换的工作目录。如果 harness 每一轮都用最新的值重新渲染 system prompt，那么每一轮都是完整重读。

在单个会话内固定、但不同会话之间会不同的东西，比如用户名字、会话启动的日期，不会伤到这个会话。但它们会让新会话无法复用已经缓存的 setup——这一点我们到引擎侧再讲。无论哪种情况，修法都一样：把这些信息一次性放进任务消息里，让 system prompt 在各处都保持一致。

### 推理强度

这一条是我们在 Ollama 侧撞上的。在 GLM-5.3-Flash 里，reasoning effort 不是引擎在旁边单独处理的设置，chat template 会把它写进最前面的 system 块，排在工具和对话之前。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a399b2df36518f1f7f48_image%206.webp)

假设你正深陷一个长任务，而且进展不顺。你把 effort 从 low 调到 high——这本身很合理，但下一个请求和上一个请求几乎在第一个 token 处就不一样了，这意味着整个会话要重新处理一遍。在一个长任务里，改一个设置可能就要花掉几十万 token。

我们的建议是一开始就选好 effort 等级，然后保持不变。如果你确实需要更多思考，用更高设置开一个新会话，往往比继续旧会话更便宜，顺带还能得到一个干净的 context。你也可以在改动 reasoning 值之前先 compact，以减少 prompt token 的数量。

### 巨大的工具输出

工具的输出会成为下一个请求的一部分，也会成为其后的每一个请求的一部分。如果 agent 只需要四十行，却读了 3,000 行的文件，你付出的代价不是一次性的，而是后面每一轮都要付（即便有缓存，也占掉了 context window）。为了对抗这一点，harness 常常会裁剪工具输出。这个方向是对的，但怎么裁很关键。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a3e9af01ebe9d38469a5_image%207.webp)

这里有一个很容易在无意中做出来的失败案例。任务是修一个日历导出功能里的时区 bug。agent 读取 `calendar.py`，工具返回了这个 640 行文件的前 100 行，却没有说明它截断了。真正要紧的函数 `convert_timezone` 在第 420 行。模型完全不知道自己漏了东西。

修法是输出里多一行，告诉模型它拿到的是 640 行中的第 1 到 100 行，并且它可以搜索文件或请求另一个范围。有了这一行，模型会搜索“timezone”，找到第 420 行，然后读第 410 到 450 行。裁剪输出能省钱；裁了却不说，只会得到一个信心满满地改着自己从未看过的代码的模型。

### 子 agent

Kimi K3、GLM-5.3 和 GLM-5.3-Flash 这样的开放模型，现在很擅长把一个大任务拆开、把各个片段分给子 agent。harness 如何启动每个子 agent，决定了它能复用父级 cache 的多少部分。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a43a91420901cc5f7063_image%208.webp)

一种做法是让子 agent 继承一切：相同的 system prompt、工具和对话，再加上分配给它的任务。侧边聊天就是这样：它从父会话分叉出来，所以整个 prefix 已经在 cache 里了。另一种做法是发一份任务简报：相同的 system prompt 和工具，然后只给子 agent 它需要的文件和指令。这种情况下，cache 只覆盖 setup，别无其他。

继承听起来严格更好，但并非如此。已缓存的 prefix 处理起来便宜，但不是免费：子 agent 生成的每个 token 仍然要读一遍它，而且它全程占用 GPU 内存。一个只需要两个文件加一份检查清单的 reviewer，大概不需要三百轮的历史记录。而如果你给子 agent 一套自己的 system prompt，它和父级就什么都不共享了，连 setup 都不共享。

## 引擎一侧

上面这些你都可以做得无可挑剔，却依然得不到好处。cache 必须还在，下一个请求必须到达持有它的那台机器。

在 Together AI，我们把推理引擎看作一台让 GPU 保持忙碌的机器。单块 GPU 每年的租用成本约为 5 万美元，所以理想情况下它永远不该闲着；而任意时刻，它都在服务数百个各自处于请求不同阶段的用户。agent 流量会以几种具体方式挤压这些约束。

### 为最优 cache 命中而路由请求

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a49b45ce62ee261e6b63_image%209.webp)

一个会话的 cache 存在某个数据中心里的某个特定节点上。如果对话的下一轮落到了别处，那个节点就得从头处理之前所有轮次，而且现在两个节点都在存同一段 prefix。要正确路由，我们首先得选一个既运行该模型、又有容量、并且这个会话一直待着的数据中心；然后才能在它里面选一个存有前几轮 cache 的节点。

选节点主要有两种方式。简单的一种是用 key：客户端在每次请求里带上类似 `prompt_cache_key` 的东西，然后理想情况下我们把同样 key 的每个请求都路由到同一个节点。另一种做法是对 prefix 做哈希，把请求发给缓存了最长匹配 prefix 的节点，哪怕那段 prefix 是另一个会话留下的。

第二种做法也是要保持 system prompt 一致的另一个理由。如果一个 harness 的每个会话都以完全相同的 system prompt 和工具定义开头，那么全新的会话有可能直接找到已经缓存好的 setup。如果你在里面放了唯一标识符，那每个会话都注定冷启动。

这也不等于永远把请求发给那个热节点就完事。有时热节点流量已经过载，这时就要在“在那里排队等”和“用一台空闲节点、但再付一次处理 prefix 的代价”之间做选择。在这种负载感知的路由范式里，有时候 cache miss 反而是更划算的一笔。所以即便 prompt 完美稳定，如果后端的推理引擎实现不正确，也保证不了命中。

### 在轮次之间让 cache 保持存活

路由只有在还有 cache 可路由时才有用。agent 常常发起一个 tool call，然后等上几分钟让测试跑完。把该会话的 cache 全程留在 GPU 内存里，会占掉活跃用户所需的空间；而把它丢弃，又意味着 agent 从 tool call 回来后要把所有东西重读一遍。所以我们还可以在会话空闲时把 cache offload 到 CPU 内存，下一轮再恢复回来。

内存是这一切背后最主要的约束。我们无法事先知道一次响应会是 30 个 token 还是 30,000 个 token，所以我们不为最坏情况下的最大 context 长度预留空间，而是按每个请求的需要以小块分配 cache 内存（PagedAttention），就像操作系统管理 RAM 那样。并且我们每一轮都重建运行中的 batch（continuous batching），这样当 agent 一次发出五个子 agent 时，每个新请求都能在空位释放的瞬间占据一个槽位，而不是等 batch 里最慢的那个跑完。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a4e6b74c7c6e90bb58ce_image%2010.webp)

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a4f38d1a4ce1e55f057a_image%2011.webp)

对做 harness 的人来说，结论是：限制一块 GPU 同时能服务多少请求的，通常是 cache 内存的余量，而不是算力。每一个过大的工具输出、每一个带着无关历史的子 agent，都在占用本可以留给其他会话 cache 的内存。

agent 还会把 prefill/decode 的拆分推到极致：prompt 极大，答案极小。为了更好地优化这一点，我们把两个阶段放在不同的集群上运行。一个集群为算力调优，负责 prefill；另一个为内存带宽调优，负责同时为数百条流做 decode，两者之间的 cache 通过 RDMA 传输。这样一来，一波很长的 agent prompt 不会拖慢其他人的 token 流。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6af7a510c31830c1fd345d8d_image%2012.webp)

## 综合来看：一个会话，两侧协同

下面这些放在一个会话里是什么样子。

在 harness 一侧：agent 找到日历工具，把它加在对话末尾，所以它之上的内容没有任何变化。它读取 `calendar.py`，发现只拿到 640 行里的第 1 到 100 行，于是搜索“timezone”，读到正确的区段。effort 保持在最初的值。一个 reviewer 子 agent 继承这个会话，用 `sessions.json` 核对 `agenda.ics`。

在引擎一侧：每一轮都回到缓存了该会话的那个节点。测试运行期间，cache 在 CPU 内存里等待。reviewer 的请求插进正在运行的 batch，每一轮只处理新增的内容。

这一切对使用 agent 的人来说都不可见，他们只会看到到第九十轮时它依然很快。但它只有在两侧都各尽其责时才成立。harness 可以把 prompt 保持得完美稳定，可如果引擎把第 7 轮发到了错误的机器上，cache 照样会丢。引擎可以路由得完美无缺，可如果 harness 每轮都改第一行，cache 也一样会丢。
