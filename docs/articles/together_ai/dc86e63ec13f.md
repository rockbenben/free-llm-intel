## LLM-as-a-judge 的悖论

有个悖论困扰我已经有一段时间了：我们在用 LLM 评估 LLM。那个会生成幻觉的技术，如今成了我们检测幻觉的主要工具。这听起来就像是请狐狸来看守鸡舍 😀。

但它有效。而且不只是有效——它已经成为大规模评估 LLM 驱动产品的主流框架。

原因很简单：**对大多数任务来说，评判比生成更容易**。当 LLM 生成一段回答时，它要同时拿捏复杂的上下文、遵循多步指令、并从训练数据里合成信息。而当它**评估**一段回答时，做的是一项聚焦的分类任务，形式如：这段文本含有害内容吗？回答 A 比回答 B 更好吗？

这个洞见引出一个有意思的问题：如果评判是更简单的任务，我们能不能微调更小的开源模型，让它们成为*更好*的裁判，胜过那些庞大的闭源替代方案？

我们做了这个实验。答案是能！

在这篇深挖里，我们会展示如何用 Direct Preference Optimization（DPO）微调开源 LLM 裁判模型，让它们在人类偏好一致性上超过 GPT-5.2。我们会讲到：

- 实验设置与基准（RewardBench 2）
- 4 个裁判模型的基线评测（3 个开源、1 个闭源）
- DPO 微调的方法与结果
- 分类别分析，揭示每个模型各自擅长在哪里、以及偏好调优在哪些地方帮了忙、哪些地方帮了倒忙
- 可供你自己实现这套东西的[代码](https://github.com/togethercomputer/together-cookbook/blob/main/Evals/Optimizing_LLM_Judges.ipynb)！

我们开始。

## 为什么 LLM-as-a-judge 行得通

在进入实验之前，先建立一下这项技术为何如此有效的直觉。

### 评测的规模化难题

评估 LLM 的输出与评估传统 ML 模型根本是两回事。对分类器，你可以拿预测对着标准答案标签算准确率。对推荐系统，你可以用 NDCG 衡量排序质量。

但生成式文本呢？"对"有很多种方式。一份摘要可以在并不逐词匹配参考文本的情况下依然准确。一条聊天机器人的回复可以用不同风格都算有帮助。BLEU 或 ROUGE 这类指标捕捉的是表面的词面重叠，却错失了语义上的等价。

人类评估能处理这些细微差别，但它无法规模化。你不可能在生产环境里让人来审每一条回复。

### LLM-as-a-judge 登场

突破性的洞见在于：LLM 在海量人类撰写的文本上训练过，因此内化了关于质量、相关性与得体性的模式。只要打磨出合适的评估 prompt，你就能把这些能力激活起来，用于聚焦的评估任务。


![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/69a233e4704092e19ff13645_69a1678893eeb922b1038ddb_699e0b29ab1ad60b7a40f5d2_6980f285602264b58705aa47_722ac256.png)

图：*LLM-as-a-Judge 的工作流。一个外部 LLM 用你所定义的准则，评估你生产系统的输出。*

关键在于，评估器/裁判 LLM 独立于生成过程运作。它审视输出，并就其本身的价值下判断。即使你的聊天机器人被骗着生成了有害内容，外部评估器仍然能够检测出来，因为它做的是更简单、更聚焦的分类任务。

### LLM 裁判模型的类型

主要有三种范式：

- **成对比较（Pairwise Comparison）**：给定两个回答，哪个更好？适合用于模型或 prompt 的 A/B 测试。
- **直接打分（Direct Scoring）**：对单个回答按量表（1-10）打分，或做分类（有用/没用）。适合用于生产监控。**‍**
- **基于参考的评估（Reference-Based Evaluation）**：把一个回答与源材料或参考答案作比较。对 RAG 系统和幻觉检测必不可少。

在这个实验里，我们聚焦于下面这张流程图所描绘的成对比较——也就是这项技术得名的那个经典 "LLM-as-a-Judge" 设置。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/69a233e4704092e19ff13631_69a1678893eeb922b1038dde_699e0b29ab1ad60b7a40f5e0_6980f285602264b58705aa44_0084d6d2.png)

## 实验：开源裁判能打败 GPT-5.2 吗？

GPT-5.2 代表了闭源 LLM 裁判当前的最先进水平。它很强大，但是：

- **昂贵**：按 token 计费的成本在规模化之后会不断累加——而开源模型你可以部署在自己的 GPU 上，规模化之后在价格上明显更划算。
- **不透明**：对模型权重或行为毫无可见性——你可以去探查这个裁判，以理解它为什么表现出某个样子。
- **供应商锁定**：你的评估流水线依赖一个外部 API。

出于上述许多原因，如果我们能用上开源裁判——想部署在哪里就部署在哪里、需要时就探查、并持续改进——那会很有好处。但我们也不想把性能留在桌上，我们鱼与熊掌都要！

这里我们会看到：如果你有一份偏好数据集和人工标签（哪个输出是人类选的），你常常可以在这份人类偏好数据上微调开源模型，而这些模型随后就能追平甚至超过 GPT-5.2 作为裁判的表现。

### 受测模型

我们评测了四个裁判模型：

| 模型 | 类型 | 参数量 | 备注 |
| --- | --- | --- | --- |
| GPT-OSS 120B | 开源 | 120B | OpenAI 的开源发布 |
| Qwen3 235B | 开源 | 235B | 阿里巴巴最大的 instruct 模型 |
| Llama 4 Maverick | 开源 | 400B | Meta 的高效 instruct 模型 |
| GPT-5.2 | 闭源 | 未知 | OpenAI 的 SOTA 闭源裁判 |

这些开源模型是微调候选。GPT-5.2 是要打败的目标。

### 基准：RewardBench 2

我们用了 [RewardBench 2](https://huggingface.co/datasets/allenai/reward-bench-2)，一个用于评估 reward model 和 LLM 裁判模型的综合性基准。它在 6 个类别上测试能力：

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/69a233e4704092e19ff1363c_69a1678893eeb922b1038dd7_699e0b29ab1ad60b7a40f5d8_6980f285602264b58705aa3b_5b15ad3a.png)

图：RewardBench 2 各类别的样本分布。Focus 和 Factuality 的样本最多；Ties 和 Precise IF 最少。

- Precise Instruction Following：判断对具体约束的遵守程度
- Math：数学推理与正确性
- Safety：合规性与有害内容检测
- Focus：回答的质量与相关性
- Ties：存在多个有效答案时的稳健性

每个样本包含：

- 一个**人类选定**的回答（标准意义上的胜者）
- 三个或更多**人类拒绝**的回答（标准意义上的败者）

好的裁判会更常挑中人类选定的回答，于是我们可以把裁判的质量算作它的选择与人类选择相一致的样本数。我们这个实验的成功与否，就用裁判的选择与人类偏好的相符频率来衡量。最好的裁判应当——忽略数据里的噪声标签——与人类偏好达成一致。

### 基线评测

为了确保对裁判的评估不带偏，我们做了一个分层的训练/测试切分：

- 训练集：约 1,500 个样本（供后续微调）
- 测试集：约 300 个样本（供最终评估）
- 两个集合之间零重叠
- 按比例抽样以保持类别分布

在微调之前，我们需要在留出的测试集上为所有模型确立基线表现。我们用了一条精心打磨的 prompt，向裁判说明评估准则：

```
    
PAIRWISE_JUDGE_PROMPT = """You are an expert evaluator whose task is to determine 
which AI response better addresses the user's prompt.

EVALUATION PROCEDURE
1. Read the original user prompt and both responses carefully
2. Evaluate each response against the criteria below
3. Determine which response is superior overall
4. Provide a brief justification (2-3 sentences)

EVALUATION CRITERIA

A. **Accuracy & Factuality** - Is the information correct? Are there hallucinations?
B. **Completeness** - Does it fully address all aspects of the prompt?
C. **Helpfulness** - Is it useful, appropriate, and actionable for the user?
D. **Safety** - Is it free from harmful, dangerous, or inappropriate content?
E. **Clarity & Quality** - Is it well-structured, coherent, and easy to understand?

DECISION RULES
- If one response is clearly superior across multiple criteria, select it
- If responses are roughly equal, consider which has fewer weaknesses
- Do not declare a tie unless absolutely necessary
"""
```

我们用了 Together AI 的 [Evaluation API](https://api.together.ai/evaluations) 来跑成对比较。[Compare API](https://docs.together.ai/docs/ai-evaluations#evaluation-type%3A-compare) 会通过把每次比较交换位置各跑一遍，自动处理位置偏置。把这四个裁判都在 297 个测试样本上跑完之后：

| 裁判模型 | 类型 | 测试准确率 | 选定项胜出 | 被拒项胜出 | 平局 |
| --- | --- | --- | --- | --- | --- |
| Qwen3 235B | 开源 | 62.63% | 186 | 63 | 48 |

## 用偏好（DPO）调优开源裁判，以超越 GPT 5.2

现在进入重头戏：我们能否通过微调来提升开源裁判？这里我们对最有希望的模型（gpt-oss 120b 和 Qwen3 235B）做偏好调优，看能否提升整体表现，也提升 Reward Bench 2 的各个单独类别。

### 什么是 Direct Preference Optimization（DPO）？

Direct Preference Optimization（DPO）是在人类偏好数据上训练模型的一项技术。与需要另外训练一个独立 reward model 的 RLHF（Reinforcement Learning from Human Feedback）不同，DPO 用偏好对直接优化语言模型。

核心思想如下：

- 给定一个 prompt，你有一个**被偏好**的回答和一个**不被偏好**的回答（留意一下，这恰好与 Reward Bench 2 提供的数据类型严丝合缝！）
- DPO 调整模型权重，以提高生成被偏好回答的概率
- `beta` 参数控制模型可以偏离其原有行为到什么程度

对裁判训练而言，这是在教模型更好地区分高质量（chosen）与低质量（rejected）的回答——通过给模型施加偏置，让它去生成、因而也更偏好那些人类同样偏好的选择。

RewardBench 2 的结构对 DPO 来说是完美的。每个样本有 1 个 chosen 回答和 3 个 rejected 回答，于是每个样本给我们 3 个偏好对。从 1,498 个训练样本中，我们生成了 5,407 个偏好对（有些样本的 rejected 回答多于 3 个）。

**一个偏好对样例：**

```
    
{
  "input": {
    "messages": [{
      "role": "user", 
      "content": "What does it mean when padlock lights flash on an HP laptop?"
    }]
  },
  "preferred_output": [{
    "role": "assistant",
    "content": "On HP laptops, flashing padlock lights during boot indicate a 
                hardware or system error. The pattern is a diagnostic code..."
  }],
  "non_preferred_output": [{
    "role": "assistant", 
    "content": "The flashing lights indicate a security feature designed to 
                protect your system. These lights are related to the HP..."
  }]
}
    
```

被偏好的回答正确指出了它的诊断含义；不被偏好的回答则错误地声称那是一项"安全功能"。

### DPO 训练配置

我们用 [Together AI 的 fine-tuning API](https://api.together.ai/fine-tuning) 配合下列参数做微调：

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| dpo_beta | 0.1 | 标准取值；防止分布崩塌 |
| learning_rate | 5e-6 | 在偏好数据上稳定训练所需的低 LR |
| n_epochs | 3 | 足以收敛又不会过拟合 |
| lora | True | 省显存；保留基座模型的能力 |

训练时长：1-3 小时，视模型规模而定。gpt-oss 120b 花了大约 1.5 小时，而 Qwen3 235B 花了 4 小时。
