# 开放权重 AI 推理的生产平台

几分钟部署，安全发布，按你的 SLO 扩展。

## 摘要

我们发布推理平台的一次重大更新，让你无需自建技术栈就能完全掌控性能、成本与质量。模型几分钟上线，每个部署从第一天起就是生产级：一个稳定 endpoint 后运行多个 deployment，用 canary、蓝绿、滚动更新安全交付变更并在你的阈值上自动回滚，用 A/B 与影子测试在真实流量上验证，跨单区域或多区域自动扩缩容。

我们还宣布自定义训练封闭 beta，包括全权重和 LoRA 强化学习与监督微调，产出的 checkpoint 可直接部署到生产。申请自定义训练 beta 的访问：https://www.together.ai/contact-sales

开放权重模型如今在质量上追平闭源模型，运行成本只有零头，并且能针对你的任务完全定制。这个组合使它成为构建严肃 AI 产品与 agent 团队的地基。但采用开放权重模型的战略动机，仍然是行使掌控权的能力。与闭源替代品不同，开放权重模型把性能、质量和功能的控制权交到团队手里。许多商业 AI 应用采用了[多数开放权重 endpoint 策略](https://decagon.ai/blog/introducing-decagon-labs)，以维持对用户体验的完全掌控。许多企业用这种掌控把自己的宝贵专有 IP 融入模型，而不冒暴露给第三方的风险。

开放权重模型用户想要对性能、功能和质量的最大控制权，但很少有团队愿意每周去检验自己正确对齐一整套决策矩阵的能力——量化级别、并行方案、引擎参数、草稿模型架构，仅举几项。与此同时，实现最佳质量与性能的前沿技术演进一样快。在快速变化的 AI 版图中，没人有时间和意愿停下来读一整本年鉴的推理内部知识或一座研究论文小山——连运营着世界上最成功模型与 agent 的团队也不想。

Together Dedicated Model Inference 把我们服务每月超过 400 万亿 token 积累的经验应用到一个推理平台，它：

- 让用户对自己的模型、性能、成本、质量和功能拥有完全控制
- 避免因从零搭建每个推理栈和 endpoint 管理层而浪费的时间、花掉的预算和意外宕机
- 持续吸收[最新经过验证的研究](https://www.together.ai/blog/foundational-research-powering-efficient-inference-at-scale)，达到前沿水平的性能、质量和效率

这次更新把我们研究、模型优化和平台工程团队的进展汇集在一个服务里，为企业运行开放权重、授权闭源权重和微调模型提供更简单、更可靠、更优的方式。

交付这种控制与简单的结合，要求把推理当作比"把模型藏在 API 后面托管"更多的事情。你运行的精度、部署的硬件、使用的服务配置，以及扩展和路由流量的方式，都对性能、可靠性和成本有实在影响。

我们构建这个平台，是为了让你从实验走向生产不需要换平台或重建部署。[生产就绪](https://www.together.ai/blog/99-9-uptime-for-inference)内建在根基里——哪怕你还在测试和迭代。这意味着你可以安全地发布新版本、对照真实流量测试变更、镜像生产请求、跨 deployment 路由流量、随需求扩展，还能在事情不符合预期时回滚。

Decagon 的 Max Lu 这样描述这一转变：

> Together 已经让我们的延迟达到语音业务所需水平。他们新推理平台改变的是我们交付下一个模型版本的方式：我们可以在一小部分真实流量上金丝雀一个全新的微调模型，关键指标回归时自动回滚。我们将从"快的推理"走向"每周都能安全迭代的快推理"。

这正是我们最终想解锁的东西：不只是快速高效的推理，而是持续改进你在服务的模型、又不引入不必要风险的能力。你可以从 Together 已经优化的路径开始，随负载变得更有专精需求再逐步接管更多控制。这一原则贯穿整个平台——从你引入和配置模型的方式，到扩展、测试变更、观测性能、把新版本带入生产的方式。

## 带来你想服务的模型

从 Together 的模型平台部署模型，或带来你自己的开放权重或微调模型。你可以从 Hugging Face、S3 或本地机器上传完整模型权重或 adapter。

平台为模型的完整生命周期而设计——从早期微调一直到最终服务生产流量的那些版本。

## 选择模型如何运行

模型本身只是部署的一部分。硬件类型、量化、张量并行、推测解码和服务引擎，全都影响负载的性能与经济性。

你不必成为每一项选择的专家才能拿到强劲结果。Together 部署画像打包了我们研究和工程团队已经测试优化过的配置，你可以从一套验证过的设置起步，而不是从零组装。当需要更多控制时，那些选择仍然可用：可以选择不同的硬件和优化画像，随时间决定主要优化延迟、吞吐还是两者的平衡。

## 少花时间等模型启动

模型越大，启动时间越受数百 GB 权重搬运主导。我们重建了模型缓存与分发层，让权重在全舰队共享、并在部署需要之前主动预热。内部测试中，这在若干前沿模型上带来了约 4 倍更快的热启动。

| 模型大小 | 代表模型 | 平均部署时间 |
| --- | --- | --- |
| 小模型 | Qwen 2.5 7B, Qwen 3.5 9B, Llama 3.1 8B | 约 2–5 分钟 |
| 中型模型 | GPT-OSS 20B, Qwen 3.6 27B, Qwen 3.5 35B | 约 3–7 分钟 |
| 大模型 | Llama 3.3 70B, Qwen 3 235B | 约 4–12 分钟 |
| 前沿规模 MoE 模型 | Kimi K2.7, MiniMax M3, GLM 5.2 | 约 7–14 分钟 |

## 控制你的部署在哪里、如何扩展

选择模型运行在哪里——钉定到特定区域，或保持放置灵活。你还可以定义部署如何应对流量变化。

不同负载有不同的需求信号，所以自动扩缩容不应局限于单一通用指标。平台从一个合理默认开始，同时允许你按 inflight 请求数、GPU 利用率、首 token 时间、延迟、解码速度或吞吐扩展——当你的负载需要更具体的东西时。

## 在 deployment 演化时保持 endpoint 稳定

一个推理 endpoint 不再必须映射到单个静态 deployment。你可以在同一个 endpoint 后创建多个 deployment，各自用不同的模型权重、硬件或服务配置。

这让你能改变 API 背后运行的东西，而不迫使应用改变调用模型的方式。endpoint 保持稳定，背后的 deployment 演化——让测试、发布和替换模型或配置更容易，而不用重做应用层。

## 安全地把变更带入生产

用 canary、蓝绿或滚动更新逐步引入新的模型版本与配置。

平台处理流量移动和部署生命周期，同时让你控制变更推进多快、何时停止或回滚。你得到所需的生产控制，而不用自己构建发布机器。

## 在真实流量上测试而不让用户冒险

用 A/B 测试把一部分流量路由到不同 deployment，直接比较行为。用影子流量把生产请求镜像到一个新 deployment，而不影响返回给用户的响应。

这让你能用真正重要的流量评估新权重、配置和硬件，而不是只依赖离线基准或合成测试。

## 度量正在发生什么

新平台给你一个组织级、可抓取的 Prometheus endpoint，可以连接你选择的任何观测工具，构建 dashboard、设置告警、监控发布健康、比较 A/B 测试变体、度量影子流量与生产的差距。

我们还刷新了产品内分析体验，让部署健康、流量、性能和扩缩行为在 Together 内直接更容易理解。
