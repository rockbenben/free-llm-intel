# 推出 Hurdle：在你的 API、技能和文档上运行 agent 评估

Hurdle 是一个开源 npm 库，它让 Claude Code 和 Codex 针对你平台上的任务运行，用代码检查、guards 和 LLM judge 为每次运行评分，并按模型和条件显示通过率。

- 作者：Mo King, Sam Barrowclough, Hassan El Mghari
- 目录[40+ 个为生产环境选择的模型...40+ 个为生产环境选择的模型...40+ 个为生产环境选择的模型...](https://www.together.ai/blog/introducing-hurdle-run-agent-evals-on-your-api-skills-and-docs)

如果你在为开发者构建产品，你 already know 编码 agent 是开发者访问你的 API、SDK 和文档的主要方式之一。要了解 agent 能与你的平台配合得如何，你需要在真实世界任务上测试它们，最好覆盖具有代表性的模型、harness 和条件样本。手动编排这一切极其繁琐，这也是我们去年春天在 Together 开始做评估时吃尽苦头才发现的。

为了自动化这个过程，我们花了过去六个月构建 [Hurdle](https://github.com/togethercomputer/hurdle)，一个用于运行 agent 评估的 npm 库。今天我们将其开源，让你能像我们一样对你的平台 agent 体验进行基准测试。现在就用 `npx hurdle init` 开始，或者让你的 agent 帮你设置。

## Hurdle 如何工作

Hurdle 让你测试 Claude Code 和 Codex 使用你平台的效果如何。

你首先要写一个*任务*，它只是一个开发者会交给使用你产品的 agent 的提示词。你可以尝试覆盖开发者可能尝试的每个任务，或者聚焦于几个问题领域。Hurdle 会让 agent 针对你的任务运行，记录会话，并为运行评分。

评分具体如何运作由你决定。你可以选择一种方法，或混合搭配：

- **Code checks：** 关于运行的断言，例如 agent 必须发起的 API 请求，以及它应生成的文件或数据。
- **Guards：** 阻止 agent 执行不被允许操作的规则，例如启动昂贵的 GPU 集群——坏 agent >:( Hurdle 会阻止该 API 请求，并将任何尝试计为失败。
- **Judge：** 一个 LLM，它根据你用平实英文写的评分细则审查录制的会话，并判定 agent 是否通过。

你也可以在不同的*条件*下运行每个任务，这些条件设定 agent 启动时的上下文。例如，你可以在两个全新 agent 上运行同一个任务，一个安装你的 MCP server，一个不安装，以观察它有多大帮助或损害。

在多个模型上运行评估也是如此：Hurdle 会让你指定的每个 agent/模型组合运行每个任务。agent 不总是以同样方式运行两次，因此你还可以将每个任务/模型/条件组合重复多次，以获得总体通过率。

## 示例任务：找到最便宜的 GPU 集群

这是我们在自己的 eval 探索中想出的一个真实任务：

> 列出可用的 GPU 集群区域和实例类型，打印最便宜的选项，并展示你要按需预留它一小时所执行的确切命令。不要实际预留它。

要通过，agent 必须从 API 查询实时区域，在文档中找到当前价格，并生成有效的预留命令——但最重要的是，它不应创建付费集群。

以下是我们如何将前三个要求写成 Hurdle 检查：

```
// checks.mjs
import { defineChecks } from "hurdle";

// Hurdle calls this function after the agent finishes
export default defineChecks((run) => {

  // Passes only if the agent made a successful GET /v1/compute/regions call
  // Request checks only work for sandboxed runs
  run.expect.request({
    id: "regions",
    method: "GET",
    path: "/v1/compute/regions",
    status: 200,
  });

  // The rubric for the LLM judge
  run.judge(
    "Using the recorded session, assess whether the agent " +
    "retrieved official pricing, compared supported options, " +
    "and produced a valid reservation command. " +
    "Mark fail if the required pricing evidence is missing. " +
    "Note confusing API responses and recovery attempts."
  );
});
```

以下是防止 agent 启动真实集群的 guard。Hurdle 在 agent 工作期间执行 guard，并在 agent 完成后运行检查：

```
// guard.mjs
import { defineGuard } from "hurdle";

export default defineGuard((guard) => {
  // Block any request to create a cluster
  // The check fails if the agent tries the request
  guard.block.request({
    id: "no-reservation",
    method: "POST",
    path: "/v1/compute/clusters",
  });
});
```

## eval 套件

要运行任务，你将它加入一个*套件*，这是一个小文件，用来选择要运行的任务、运行它们的 agent 和条件，以及每次运行重复多少次。对于 GPU 集群任务，我们同时使用确定性代码检查和 LLM judge，因此将套件的 `verdict` 设为 `hybrid`，并指定一个 judge 模型：

```
// example.suite.mjs
import { defineSuite } from "hurdle";

export default defineSuite({
  // The API under test, and the name of the env var that holds its key.
  api: {
    authorizationCredential: "TOGETHER_API_KEY",
    hosts: ["api.together.ai"],
  },

  tasks: ["./tasks/gpu-cluster"],

  // The two models we tested in June.
  agents: [
    { runner: "claude-code", model: "claude-opus-4-8" },
    { runner: "claude-code", model: "claude-sonnet-4-6" },
  ],

  // Use conditions to run each task with and without our GPU clusters skill.
  conditions: {
    baseline: {},
    "with-skill": {
      skills: [{ name: "together-gpu-clusters", sourceDirectory: "skills/together-gpu-clusters" }],
    },
  },

  // Run every combination of task, agent, and condition 15 times.
  repeats: 15,

  // A run passes only if the code checks and the judge both pass.
  verdict: "hybrid",
  judge: { model: "claude-opus-4-8" },
});
```

## 运行并查看结果

`npx hurdle run` 会运行套件。加上 `--view` 会在套件完成时打开结果查看器：

```
npx hurdle run --view
```

Hurdle 会为套件中的每个 agent 和条件运行每个任务，次数由 `repeats` 指定。对于上面的套件，这是一个任务、两个模型、两个条件，每个重复 15 次，也就是 60 次运行。每次运行完成时，检查会出现在终端中，并标记为通过、失败或跳过。

查看器顶部显示套件的核心数字：通过率、平均时长和每次运行的平均成本。下方有一个网格，按任务和条件细分通过率，因此你可以看到哪些组合在失败：

## 本地运行

对于你信任的任务的快速测试，你可以在本地运行评估，就像你自己给 agent 写提示词时那样。

Hurdle 会在你机器上的临时工作区启动 `claude` 或 `codex` CLI，将任务的提示词和文件交给它，并记录会话。每个 agent 都从干净配置启动，因此你常规的 Claude Code 或 Codex 设置不会影响结果。

本地运行有两个注意事项：第一，Hurdle 无法看到或阻止 agent 的 API 请求，因此你不能使用 guards 或请求检查。但更重要的是，agent 会*以你的身份*运行，因此它可以读取本地文件并使用你的真实 API 密钥。

对于任何复杂或有风险的事情，你应始终使用沙箱。

## 沙箱运行

对于生产评估，Hurdle 使用 Together Sandbox API 启动隔离环境，编码 agent 可以在其中执行代码、安装依赖并与 API 交互，而不会访问你的本地机器。

每次运行都会获得一个全新沙箱，因此 agent 从干净环境开始，而不是继承之前运行的文件或状态。Together 处理沙箱基础设施，而 Hurdle 管理 agent 执行、API 请求监控和评估结果。

当你启动一次沙箱运行时，Hurdle 会启动一个名为 Guardian 的本地代理，然后向 Together 打开单个 WebSocket，由 Together 为该次运行启动一个全新的 [Together Sandbox](https://docs.together.ai/docs/together-code-sandbox)。agent 在该沙箱内工作，沙箱自身没有网络访问权限。agent 打开的每个连接都会通过该 socket 返回 Guardian，由 Guardian 允许或拒绝每个请求。

你的密钥永远不会进入沙箱——agent 得到随机占位符；当它调用你的 API 时，Guardian 会换入真实密钥并转发请求。agent 对模型提供商（Anthropic 或 OpenAI）的调用也走同一路径。

这种路由让 Hurdle 能够检查请求、执行 guards 并保障你的密钥安全：

- **API 请求检查：** 每个请求都经过 Guardian，因此你的检查可以确切看到 agent 发起了哪些调用。
- **Guards：** Guardian 用 403 响应被阻止的请求，因此该请求永远不会到达你的 API。
- **安全密钥：** agent 可以使用你的密钥但无法读取它们，因此如果某个占位符泄漏到记录中，也没什么大不了。

默认情况下，沙箱不会限制 agent 可以调用哪些 endpoint。agent 可以用你的密钥向你 API 发送任何请求，因此为你的评估使用一个低余额的专用密钥，并为任何危险操作添加 guard。

## 自己试试

你需要 Node.js 22.18 或更高版本，并安装 Claude Code 或 Codex CLI。

### 1. 设置你的项目

在新目录中创建一个项目：

```
mkdir my-evals && cd my-evals
npx hurdle init
```

要使用 Codex 而不是 Claude，添加 `--agent codex`：

```
npx hurdle init --agent codex
```

`init` 会创建一个 `evals/` 目录，其中包含起始套件和示例任务。

### 2. 添加你的 API 密钥

接下来，在 `my-evals` 中创建一个 `.env.local` 文件，并添加你的 Anthropic API 密钥。来自 `claude setup-token` 的 `CLAUDE_CODE_OAUTH_TOKEN` 也可以。如果你想使用沙箱，还需要设置你的 Together API 密钥。

```
# .env.local

# Add your Anthropic key
ANTHROPIC_API_KEY=your_api_key

# ... Or OAuth token
# CLAUDE_CODE_OAUTH_TOKEN=your_oauth_token

# ... Or your OpenAI key
# OPENAI_API_KEY=your_api_key

# Required for sandboxes
# TOGETHER_API_KEY=your_api_key
```

### 3. 运行起始任务

然后运行套件并打开结果查看器：

```
npx hurdle run --view
```

起始任务要求 agent 将一个文件复制到 `answer.txt`，一项代码检查会确认复制后的文件与原始文件匹配。这次运行发生在你自己的机器上，不使用沙箱。

### 4. 尝试一次沙箱运行

要尝试沙箱运行，使用捆绑的 Together API 示例，它告诉 agent 列出 Together 上可用的模型，进行一次简短的 chat completion，并保存响应。检查会确认 API 请求和保存的文件两者。

确保你已在 `.env.local` 中设置 `TOGETHER_API_KEY`，然后在同一个 `my-evals` 目录中运行这些命令：

```
npx hurdle init api-evals --example together-api
npx hurdle setup api-evals
npx hurdle run api-evals --view
```

`setup` 会检查你的凭据、安装 Guardian（目前仅限 macOS 或 Linux），并将项目设置为在 Together 沙箱中运行。沙箱和 chat completion 需要一些 Together 额度，但每次运行的 Together 侧成本应只占一小部分美分。

## 找到你自己的 hurdles

当你准备好评估自己的产品时，将你的 API 密钥以任意名称添加到 `.env.local`：

setup 会检查你的凭据、安装 Guardian（目前仅限 macOS 或 Linux），并将项目设置为在 Together 沙箱中运行。沙箱和 chat completion 需要一些 Together 额度，但每次运行的 Together 侧成本应只占一小部分美分。找到你自己的 hurdles 当你准备好评估自己的产品时，将你的 API 密钥以任意名称添加到 .env.local：

然后向套件添加一个 `api` 块，在其中指定该变量和你的 API 主机：

```
// example.suite.mjs
export default defineSuite({
  api: {
    // The name of the variable in .env.local. Don't paste the key itself here.
    authorizationCredential: "MY_API_KEY",
    hosts: ["api.example.com"],
  },
  // ...tasks, agents, and verdict
});
```

agent 会获得一个同名环境变量，因此你可以在提示词中直接引用它。

*(沙箱运行的一个注意事项：Guardian 只会将你的密钥换入 `Authorization` header，因此以其他方式接收密钥的 API 将无法认证。)*

之后，选择一个你的用户已经在交给其 agent 的任务。将它写成提示词，添加一项检查，并用两个模型运行：你能获得的最好模型，以及低一个档次的模型。每个重复几次，因为任何单次运行都可能偶然通过或失败。

Hurdle 在 [GitHub](https://github.com/togethercomputer/hurdle) 上开源，README 中还有一份关于如何编写你自己的评估的指南。

如果 Hurdle 找到了让你的 agent 出错的方法，请告诉我们！我们很想听听你发现的任何障碍以及你是如何修复它们的。
