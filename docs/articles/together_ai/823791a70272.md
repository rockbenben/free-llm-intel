# Hurdle 简介：在你的 API、技能与文档上运行 agent 评估

Hurdle 是一个开源的 npm 库，它让 Claude Code 和 Codex 在你的平台上执行任务，用代码检查、guards 和一个 LLM judge 为每次运行打分，并按模型与条件显示通过率。

- 作者：Mo King、Sam Barrowclough、Hassan El Mghari

如果你是在为开发者构建产品，你早就知道 coding agent 是开发者访问你的 API、SDK 和文档的主要方式之一。要弄清 agent 与你的平台配合得如何，你需要在真实任务上测试它们，最好覆盖有代表性的模型、harness 与条件组合。手动编排这一切极其繁琐——去年春天我们在 Together 开始做评估时，正是吃了这个苦头才知道的。

为了把这一过程自动化，过去六个月我们一直在构建 [Hurdle](https://github.com/togethercomputer/hurdle)，一个用于运行 agent 评估的 npm 库。今天我们把它开源，让你可以用和我们一样的方式，对平台的 agent 体验做基准测试。今天就可以用 `npx hurdle init` 开始，或者让你的 agent 帮你把它配置好。

## Hurdle 的工作原理

Hurdle 让你测试 Claude Code 和 Codex 能在多大程度上用好你的平台。

你从写一个*任务*开始，它就是一个开发者会交给 agent、让它配合你的产品工作的 prompt。你可以尝试覆盖开发者可能尝试的每一个任务，也可以聚焦在几个问题领域。Hurdle 让 agent 针对你的任务运行，记录会话，并为这次运行打分。

打分具体怎么进行由你决定。你可以选一种方法，也可以混搭：

- **代码检查（Code checks）：** 关于本次运行的断言，比如 agent 必须发出的 API 请求，以及它应当产出的文件或数据。
- **Guards：** 阻止 agent 执行不被允许的动作的规则，比如启动一个昂贵的 GPU 集群——坏 agent >:( Hurdle 会拦下该 API 请求，并把任何尝试计为失败。
- **Judge：** 一个 LLM，它按照你用平实英文写好的 rubric 审阅记录下来的会话，判定 agent 是否通过。

你也可以在不同的*条件*下运行每个任务，这些条件设定 agent 起步时的上下文。例如，你可以在两个全新的 agent 上运行同一个任务，一个装了你的 MCP server，一个没装，看看它帮了多少忙、又添了多少乱。

在多个模型上运行评估也是同理：Hurdle 会针对你指定的每一个 agent/model 组合运行每一个任务。agent 两次运行的表现并不总是一致，所以你也可以把每个 task/model/condition 组合重复多次，以得到总体通过率。

## 示例任务：找出最便宜的 GPU 集群

这是我们在自己的评估冒险中想出的一个真实任务：

> 列出可用的 GPU 集群区域与实例类型，打印最便宜的选项，并给出你要按需预留它一小时时会运行的那条确切命令。不要真的预留它。

要判定通过，agent 必须从 API 查询实时的区域信息，在文档里找到当前价格，并产出一条有效的预留命令——但最重要的是，它绝对不能创建付费集群。

下面是我们如何把前三条要求写成 Hurdle 检查的：

```
// checks.mjs
import { defineChecks } from "hurdle";

// Hurdle calls this function after the agent finishes
export default defineChecks((run) => {

  // Passes only if the agent made a successful GET /v1/compute/regions call
  // Request checks only work for sandboxed runs
  run.expect.request({
    id: "regions",
    method: "GET",
    path: "/v1/compute/regions",
    status: 200,
  });

  // The rubric for the LLM judge
  run.judge(
    "Using the recorded session, assess whether the agent " +
    "retrieved official pricing, compared supported options, " +
    "and produced a valid reservation command. " +
    "Mark fail if the required pricing evidence is missing. " +
    "Note confusing API responses and recovery attempts."
  );
});
```

还有一个 guard，用来阻止 agent 启动真实集群。Hurdle 在 agent 工作期间执行这个 guard，并在 agent 结束后运行检查：

```
// guard.mjs
import { defineGuard } from "hurdle";

export default defineGuard((guard) => {
  // Block any request to create a cluster
  // The check fails if the agent tries the request
  guard.block.request({
    id: "no-reservation",
    method: "POST",
    path: "/v1/compute/clusters",
  });
});
```

## 评估套件

要运行一个任务，你把它加到一个*套件（suite）*里，这是一个小文件，用来选定要运行的任务、搭配的 agent 与条件，以及每次运行重复多少遍。对于 GPU 集群这个任务，我们既用了确定性的代码检查，也用了 LLM judge，所以把套件的 `verdict` 设为 `hybrid`，并指定一个 judge 模型：

```
// example.suite.mjs
import { defineSuite } from "hurdle";

export default defineSuite({
  // The API under test, and the name of the env var that holds its key.
  api: {
    authorizationCredential: "TOGETHER_API_KEY",
    hosts: ["api.together.ai"],
  },

  tasks: ["./tasks/gpu-cluster"],

  // The two models we tested in June.
  agents: [
    { runner: "claude-code", model: "claude-opus-4-8" },
    { runner: "claude-code", model: "claude-sonnet-4-6" },
  ],

  // Use conditions to run each task with and without our GPU clusters skill.
  conditions: {
    baseline: {},
    "with-skill": {
      skills: [{ name: "together-gpu-clusters", sourceDirectory: "skills/together-gpu-clusters" }],
    },
  },

  // Run every combination of task, agent, and condition 15 times.
  repeats: 15,

  // A run passes only if the code checks and the judge both pass.
  verdict: "hybrid",
  judge: { model: "claude-opus-4-8" },
});
```

## 运行并查看结果

`npx hurdle run` 运行套件。加上 `--view` 会在套件结束时打开结果查看器：

```
npx hurdle run --view
```

Hurdle 会为套件里的每个 agent 和每个条件运行每个任务，重复次数由 `repeats` 决定。对上面那个套件而言，就是一个任务、两个模型、两种条件，每种各 15 次，也就是 60 次运行。每次运行结束时，检查结果会出现在终端里，标记为通过、失败或跳过。

查看器顶部显示套件的核心数字：通过率、平均时长和每次运行的平均成本。下面是一个网格，按任务和条件拆解通过率，让你看出哪些组合在失败：

## 本地运行

对于你信任的任务想做快速测试时，可以在本地运行你的评估，就像你自己在给 agent 下 prompt 一样。

Hurdle 会在你机器上的临时工作区里启动 `claude` 或 `codex` CLI，把任务的 prompt 与文件交给它，并记录整个会话。每个 agent 都从干净的配置起步，所以你日常的 Claude Code 或 Codex 配置不会影响结果。

本地运行有两个注意事项：第一，Hurdle 看不到也拦不住 agent 的 API 请求，因此你无法使用 guards 或请求检查。但更重要的是，agent 是以*你*的身份运行的，所以它能读本地文件、用你真实的 API key。

凡是复杂或有风险的事，都应该使用 sandbox。

## 沙箱运行

对于生产环境的评估，Hurdle 使用 Together Sandbox API 起出隔离环境，coding agent 可以在其中执行代码、安装依赖、与 API 交互，而不会访问你的本机。

每次运行都会得到一个全新的 sandbox，因此 agent 从干净的环境起步，而不会继承此前运行的文件或状态。Together 负责 sandbox 基础设施，Hurdle 则管理 agent 执行、API 请求监控和评估结果。

当你启动一次沙箱运行时，Hurdle 会先启动一个名为 Guardian 的本地代理，然后向 Together 打开一个 WebSocket，由后者为这次运行起出一个全新的 [Together Sandbox](https://docs.together.ai/docs/together-code-sandbox)。agent 在那个 sandbox 里工作，而该 sandbox 自身没有网络访问。agent 打开的每一条连接都会经那个 socket 回到 Guardian，由它放行或拒绝每一个请求。

你的 key 永远不会进入 sandbox——agent 拿到的是随机的替代值，当它调用你的 API 时，Guardian 换上真实的 key 并转发请求。agent 对模型提供方（Anthropic 或 OpenAI）的调用也走同一条路径。

正是这种路由让 Hurdle 能检查请求、执行 guards 并保证你的 key 安全：

- **API 请求检查：** 每个请求都经过 Guardian，因此你的检查能准确看到 agent 做了哪些调用。
- **Guards：** Guardian 对被拦下的请求返回 403，该请求因此永远到不了你的 API。
- **安全的 key：** agent 可以使用你的 key，但读不到它，所以就算一个替代值漏进了对话记录，也没什么大不了。

默认情况下，sandbox 不限制 agent 能调用哪些端点。agent 可以用你的 key 向你的 API 发送任何请求，所以给你的评估准备一个专用的、余额很低的 key，并为任何危险操作添加 guard。

## 自己试一试

你需要 Node.js 22.18 或更高版本，并安装 Claude Code 或 Codex CLI。

### 1. 设置你的项目

在新目录中创建一个项目：

```
mkdir my-evals && cd my-evals
npx hurdle init
```

如果想用 Codex 而不是 Claude，加上 `--agent codex`：

```
npx hurdle init --agent codex
```

`init` 会创建一个 `evals/` 目录，其中包含一个入门套件和示例任务。

### 2. 添加你的 API key

接下来，在 `my-evals` 中创建一个 `.env.local` 文件，并加入你的 Anthropic API key。用 `claude setup-token` 得到的 `CLAUDE_CODE_OAUTH_TOKEN` 也可以。如果你想使用 sandbox，还需要设置你的 Together API key。

```
# .env.local

# Add your Anthropic key
ANTHROPIC_API_KEY=your_api_key

# ... Or OAuth token
# CLAUDE_CODE_OAUTH_TOKEN=your_oauth_token

# ... Or your OpenAI key
# OPENAI_API_KEY=your_api_key

# Required for sandboxes
# TOGETHER_API_KEY=your_api_key
```

### 3. 运行入门任务

然后运行套件并打开结果查看器：

```
npx hurdle run --view
```

入门任务让 agent 把一个文件复制到 `answer.txt`，并由一项代码检查确认复制出的文件与原始文件一致。这次运行在你的本机上发生，不使用 sandbox。

### 4. 试试沙箱运行

要尝试沙箱运行，可以使用内置的 Together API 示例，它让 agent 列出 Together 上可用的模型、做一次简短的 chat completion，并保存响应。检查会同时确认 API 请求和保存下来的文件。

确认你已经在 `.env.local` 里设置了 `TOGETHER_API_KEY`，然后在同一个 `my-evals` 目录中运行这些命令：

```
npx hurdle init api-evals --example together-api
npx hurdle setup api-evals
npx hurdle run api-evals --view
```

`setup` 会检查你的凭据、安装 Guardian（目前仅支持 macOS 或 Linux），并把项目设为在 Together sandbox 中运行。sandbox 和 chat completion 都需要一些 Together 余额，但 Together 这一侧每次运行只应花费不到一美分的零头。

## 寻找你自己的 hurdle

当你准备好评估自己的产品时，把 API key 以任意你喜欢的名字加进 `.env.local`：

然后在这个套件里添加一个 `api` 块，写明那个变量名和你 API 的 host：

```
// example.suite.mjs
export default defineSuite({
  api: {
    // The name of the variable in .env.local. Don't paste the key itself here.
    authorizationCredential: "MY_API_KEY",
    hosts: ["api.example.com"],
  },
  // ...tasks, agents, and verdict
});
```

agent 会得到一个同名环境变量，因此你可以在 prompt 里直接引用它。

*(沙箱运行有一个注意事项：Guardian 只会把 key 换进 `Authorization` 头，所以那些从别处取 key 的 API 将无法完成鉴权。)*

接下来，挑一个你的用户已经在交给他们 agent 的任务。把它写成一个 prompt，加一项检查，然后用两个模型运行：你能拿到的最好的那个，以及低一个档位的那个。每个都重复几次，因为任何单次运行都可能因偶然通过或失败。

Hurdle 已在 [GitHub](https://github.com/togethercomputer/hurdle) 上开源，README 里还有一份关于如何编写你自己的评估的指南。

如果 Hurdle 发现你的 agent 有能被绊倒的地方，请告诉我们！我们很想听听你发现的障碍，以及你是怎么解决的。
