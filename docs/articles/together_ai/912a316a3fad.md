## 摘要

我们与 Stanford University、University of Wisconsin–Madison 和 Bauplan 合作，测试 LLM 能否优化数据库查询执行计划。结果表明，LLM 引导的计划改写可以在不修改数据库引擎本身的情况下提升执行性能。

近期 AI 的进展由底层系统基础设施的改进驱动。但这种关系不必是非对称的：AI 和 LLM 也可以用来优化大规模系统本身的功能组件。我们最近的论文展示了 AI 如何用于数据库查询优化。

传统查询优化依赖基于成本的估计器，用统计模型和预定义启发式计算执行路径。执行像 **"找出所有含太空旅行的科幻剧"** 这样的查询时，优化器必须决定执行策略：是先过滤科幻剧再检查哪些有太空旅行，还是反过来？如果数据分布在多张表（如 shows 表和 genres 表），应该先扫描哪张表、如何 join？优化器通过估计每个条件将匹配多少行来回答这些问题，然后选择预估成本最低的实际计划（操作顺序）。

**然而，这些估计通常假设属性独立。** 考虑一个流媒体数据集，你想找出既是"科幻"又"有太空旅行"的剧。如果 15% 的剧是科幻、8% 涉及太空旅行，假设独立会估计 1.2% 的剧同时满足（15% × 8%）。然而太空旅行剧绝大多数都是科幻，实际重叠接近 7%——几乎是预测值的 6 倍。

事实上，这些系统总体运行良好，但当启发式无法解释 schema 或数据内部的语义相关性时就会挣扎。正如 [Lohman](https://wp.sigmod.org/?p=1075)（2014）的例子指出的，基数估计是优化器低效的主导来源，因为行数误估会在成本模型中传播，导致对 join 顺序、访问路径和物理算子的系统性错误选择。这种数量级误差造成次优的物理计划，需要大量人工工程修正。

语义感知的 join 优化。通过把高选择性的 `date` 过滤提前，LLM 重排计划，让 sales 事实表在 join 前从 1510 万行裁剪到 290 万行，查询因此快得多。

## 查询优化是个已解决的问题吗？

这些估计错误的持续存在说明物理计划并非已解决——尤其在函数依赖常见的复杂 OLAP 负载上。

为应对这一点，我们引入 DBPlanBench——一个暴露 Apache DataFusion 引擎查询执行过程的 harness。该系统把内部物理算子图（包括 join 策略和分区方案）暴露给 LLM。这里的主要技术挑战是原始物理计划固有的信息密度：冗长的文件路径、分区元数据和类型编码很快塞满上下文窗口。

不做精心的序列化，整个计划可能超过 200 万字符，LLM 无法有效高效地对输入推理。我们的 harness 实现了一个序列化层，遍历引擎的物理算子图，把异构对象映射为统一的、token 高效的 JSON schema。

对单表压缩引擎统计信息的示例片段。完整 JSON 包含许多与执行无关的字段（如 `precisionInfo`、逐列 min/max 和 null 计数），而精简 stats 只保留 `n_rows`、`total_bytes` 等主要信号。

这一表示对文件级统计去重、移除与执行无关的字段，payload 约比原生序列化小 10 倍。

DBPlanBench 因此把优化任务从统计计算转换为语义推理问题——LLM 分析计划的拓扑，识别 join 顺序中的逻辑缺陷。

我们在 DataFusion 内部优化物理计划的优化 harness。

为安全地实施这些修复，我们指示 LLM 避免从零重新生成整个物理计划；而是对 DataFusion 现有物理计划做定点编辑，降低语法错误或非法计划拓扑的风险。具体地，LLM 生成 JSON Patch（RFC 6902）描述局部编辑，如交换 join 两侧、重排节点。这些 patch 比完整计划小几个数量级，直接应用在序列化图上，保证执行 DAG 的结构完整性。

交换 hashJoin 左右输入、同时更新两个子 ID 和 join key 的 JSON Patch 示例。它展示了怎样用一个小的局部 patch 改写一个 join（例如把更小的表放到 build 侧），而不必重新生成整个计划。

## 案例研究

统计估计失败的后果，在查询延迟和系统资源消耗两方面都可度量。在从 TPC-DS 派生版本生成的一条涉及跨渠道销售的特定查询中，默认 DataFusion 优化器选择先 join 较小的 item 表（3.6 万行）再 join 较大的 date 维度表（7.3 万行），假设较小的 join 更便宜。这一启发式没考虑到 date 维度上过滤条件 d_year=2001 的高选择性。LLM 优化的计划把这个顺序反转：提前应用 date 过滤，在后续 join 之前把 sales 事实表从 1510 万行裁剪到 290 万行。

这一结构性优化让查询提速 4.78 倍。更重要的是资源占用大幅下降：优化后的计划把聚合 hash 表构建时间从 10.16 秒降到 0.41 秒，总构建内存从 3.3 GB 削减到 411 MB。实验显示，在 TPC-H 和 TPC-DS 的生成查询负载上，中位加速在 1.1x 到 1.2x 左右，而该方法在一些复杂多 join 查询上带来大得多的收益——最高 4.78×，另有多条落在 1.5-1.7x 区间。

## 进化式计划修补

我们通过迭代精化演化查询计划。系统用 GPT-5 生成候选改进（以 JSON patch 形式），验证每个更改，保留降低延迟的 patch。这些 patch 应用后，系统再尝试从新计划出发生成新候选。通过跨多个步骤在成功优化上继续构建，这种进化式方法比独立采样许多计划取得更好的加速。

## 跨 scale factor 转移加速

我们使用的基准暴露一个 scale factor 参数，它在 schema 不变的情况下缩放表的基数。实践中，这让我们能构建一个小型原型数据库（如 Scale Factor 3，SF3）和一个更大的类生产数据库（如 SF10），二者结构相同、只差规模。

因为在全规模数据上探索许多候选计划代价高昂（每一步都要执行查询，还要为 LLM 生成的 patch 付费、等待），我们先在 SF3 上用进化搜索发现优秀的优化计划。对每条查询，再用确定性的规则脚本把最佳 SF3 计划转移到 SF10。脚本通过归一化的 schema/投影/谓词签名跨规模匹配扫描算子，把 SF3 优化计划改写为可在 SF10 运行的计划，保留 join 重排、join 侧交换等结构性编辑，同时执行安全检查（无悬空引用、合法 DAG 拓扑）。

经验上，我们在 SF3 选定的每个优化计划都能成功转移到 SF10，所得加速与原始加速紧密跟随。这验证了一个实用的"小处优化、大处部署"工作流：在负载的紧凑副本上跑一次昂贵的搜索，然后以最小额外工程把得到的计划提升到更大的生产数据库。

在小型 SF3 数据库上发现的加速大部分延续到更大的 SF10。每个点是一条查询，比较其在 SF3（横轴）与 SF10（纵轴）的加速。

## 结论

DBPlanBench 确立了一个事实：LLM 可以有效地充当语义基数估计器，修正统计启发式漏掉的物理计划错误。把紧凑计划序列化与进化式 patch 搜索结合，系统在不要求改动数据库内核的情况下，取得执行时间与内存压力的显著下降。harness 与代码已作为开源发布，供后续研究。
