## 摘要

我们推出 AutoJudge：一种通过任务专属有损推测解码加速大语言模型（LLM）推理的方法。它不再逐 token 匹配目标模型的输出分布，而是识别哪些生成出的 token 真正影响下游质量。相比先前方法，AutoJudge 不需要人工标注——它使用一个自监督方式训练的分类器。

AutoJudge 每个验证周期最多可接受 40 个草稿 token 而准确率仅轻微下降，相对标准推测解码取得 1.5–2 倍加速，且易于集成进现有 LLM 推理框架。我们将在 NeurIPS 2025 上展示关于 [AutoJudge](https://arxiv.org/abs/2504.20039) 的研究成果——欢迎来和团队交流了解更多！

推测解码通过给小的"草稿"模型与主"目标"模型配对来加速生成：草稿提出若干后续 token，目标并行验证。与目标一致的 token 被接受；第一个不一致（及其后所有）被拒绝。这使输出分布与目标模型自身的解码完全一致。

实践中，严格的分布匹配并非总是必要。**有损（lossy）**变体用一丁点质量换更多速度。Judge Decoding 就是这样一种做法：只有当接受不一致会伤害最终答案时才拒绝。例如数学错误、逻辑 bug 要紧，但无关紧要的风格改动往往不要紧。我们的工作直接建立在这个想法之上。

Judge Decoding 的麻烦在于**数据**：它需要人类为每个任务标注"关键"的不一致 token——又贵，又无法完美跨领域迁移。**AutoJudge** 通过自动挖掘这些重要 token 消除了这个瓶颈——不需要人类标注员。

## AutoJudge 方法

图 1：AutoJudge 的数据采集阶段

AutoJudge 包含以下阶段：

- **自动挖掘"重要的"不一致**
对一个 prompt，生成目标答案并定位草稿与目标模型意见不合之处。迭代地互换草稿 ↔ 目标 token 并**重新评估任务**（如 GSM8K 答案相等性或代码单元测试）。如果保留草稿 token 会破坏最终答案，该不一致就是*重要的*，否则是*不重要的*。这趟半贪心扫描只要答案有差异，就能可靠地至少浮出一个重要 token。
- **在既有 embedding 上训练一个微型分类器**
我们用一个简单的逻辑回归，输入是推测解码期间**已经算好的** transformer 隐藏状态。把草稿和目标 token 的 embedding 拼接起来效果最好，且对正则化选择和小幅架构变体都很鲁棒。**‍**
- **在验证时接受"不重要的"不一致**
在验证阶段——恰是基线会**拒绝**不一致草稿 token 的地方——我们调用分类器。若它预测该 token **不重要**，我们就**接受**它并继续前进，提高每个推测周期的接受 token 数。该方法与标准、树状、单模型多头等推测解码方法兼容，可嵌入 vLLM、TensorRT-LLM、TGI 等流行栈。实践中我们选一个**高召回**阈值（≥90%），在保护准确率的同时仍能跳过很大一部分 token。

图 2：额外接受的 token 带来更快推理的示例

图 2 展示 AutoJudge 如何在推测解码步骤中接受更多 token。AutoJudge 加入一个微型"裁判"，在每处不一致时询问：这个差异是否真的改变最终答案。在示例中，不一致只是无害的措辞——如 "equals" 与 "becomes"——我们接受它并保留其余草稿 token。如果它会改变正确性——比如数学步骤里的 "+" 与 "−"——我们拒绝。通过只拒绝关键不一致，我们保留草稿更长的片段，于是一次接受更多 token、生成更快、对质量影响很小。

## 性能基准

### 准确率-接受率的权衡

图 3：GSM8K 上的准确率与接受 token 数，（左）8-shot Llama-3.2 1B 草稿 / Llama-3.1 8B 目标，（右）0-shot Llama-3.1 8B 草稿 / Llama-3.1 70B 目标（均为 Instruct）。

图 3 展示 AutoJudge 如何移动速度-质量前沿：随着每周期接受的草稿 token 数增加（横轴），AutoJudge（红线）在接受更多草稿 token 的同时保持接近无损推测解码的准确率——而天真的 Top-K 基线准确率迅速下滑。这在两对模型上都成立（左 1B/8B，右 8B/70B），所以你可以选择一个给出更高 tokens/s、准确率代价极小的阈值。图 3（右）显示可以安全地接受三倍的 token，只付出 1% 的准确率下降——证明推测解码最多可安全接受 45 个 token 而质量损失极小。

## 推理加速

我们把 AutoJudge 集成进 **vLLM** 的推测解码，并在 GPU 上测量端到端 tokens/s（配置含 A100/H100，模型对见下方注记）。

### 数学推理（GSM8K）

跨各模型对，AutoJudge 都以小幅准确率权衡交付一致的吞吐增益：

- **Llama-3.1-405B（目标）/ 8B（草稿），8xH100：** 91.5%（约降 4%），**60.1 tokens/s**，**1.20×**。
- **Llama-3.1-70B（目标）/ 8B（草稿），4xA100：** 89.9%（约降 2%），**107.4 tokens/s**，**1.49×**。
- **Llama-3.1-8B（目标）/ 1B（草稿），1xA100：** 80.2%（约降 3%），**169.2 tokens/s**，**1.14×**。
 *基线：* 50.0（405B）、72.3（70B）、147.7（8B）tokens/s。

### 编程（LiveCodeBench）

AutoJudge 自动识别代码的关键 token 并提升接受率：

- **Llama-3.1-70B（目标）/ 8B（草稿）：** Pass@1 **28.0%**（约降 3%），**每周期约 35 个接受 token（约 3.5×）**。*基线接受 token：* 约 10
- **Llama-3.1-8B（目标）/ 1B（草稿）：** Pass@1 **14.5%**（约降 2.5%），**每周期约 30 个接受 token（约 2.3×）**。*基线接受 token：* 约 13

### Offloading 场景（带宽受限）

当链路带宽是瓶颈，更长的草稿窗口变得可行，加速成倍放大：

- **8B → 70B（GSM8K）：** **2.4 tokens/s**，**1.98×**，准确率 **90.4%**（约降 3%）。
- **8B → 70B（GSM8K）：** **1.4 tokens/s**，**1.20×**，准确率 **95.4%**（约 +0.5%）。
 *基线：* 1.19 tokens/s。

## 与 EAGLE-2 组合

AutoJudge 可以与 EAGLE-2 叠加（后者从目标模型的隐藏状态起草，无需独立草稿模型）。在 **GSM8K（0-shot）+ Llama-3.1-8B-Instruct** 上，AutoJudge 在微小准确率差异下比 EAGLE 再加约 **8–20% tokens/s**：**96.8、102.6、107.5 tokens/s** 对基线 **89.8**，准确率分别为 **81.3%、81.0%、78.1%**。

## 局限与实践注记

- 加速取决于不一致在多大频率上对该指标（如答案相等性、单元测试）*确实不重要*。创意写作这类任务留给的空间通常更小；更多实验（含长上下文 GSM 与写作）见论文附录。
- 可以偏向**高召回**的分类器阈值（≥90%），在保护质量的同时仍跳过很多 token。阈值最好在逐任务上调优。

## 结论

AutoJudge 提供一个简单、全自动的算法来加速推测解码循环：**接受无害的不一致，省下目标模型的调用，跑得更快。** 它移除了 judge 类方法的人工标注，学习每个任务上什么要紧，并用一个微型分类器消费你已经计算的 embedding，保证运行时开销极低。
