# AI Native Conf 上的重要研究与产品发布

Together Research 在 AI Native Conf 上发布 FlashAttention-4、Reinforcement Learning API、ThunderAgent、ATLAS-2 等成果。

AI Native Cloud 不只是一句定位口号。它是一个为 AI 原生人群量身打造的全栈 AI 云，由交付过 [FlashAttention](https://arxiv.org/abs/2205.14135) 和 [ThunderKittens](https://arxiv.org/abs/2410.20399) 等奠基性 AI 工作的研究员和工程师建造。发表那些研究的人，正是运行我们的客户——如 [Cursor](https://www.together.ai/customers/cursor) 和 [Decagon](https://www.together.ai/customers/decagon)——所依赖的生产系统的人。这种近距离很难复制。当一项技术从我们的研究计划中产生，我们可以快速从研究走向生产，把这些技术交付给客户、立即创造价值。

今天在首届 AI Native Conf 上，我们发布横跨三个领域的七项研究与产品成果：Kernel、强化学习、算法级推理优化。每一项都代表着我们"研究到生产"流水线的一次巨大推进，供客户直接使用。

## Kernel

### **FlashAttention-4**

FlashAttention 是为当今生产中许多大规模前沿语言模型提供动力的注意力引擎。由首席科学家 Tri Dao 领导的研究计划持续突破注意力能跑多快的极限。FlashAttention-4 将新算法与针对 NVIDIA Blackwell GPU 调优的 kernel 协同设计相结合，消除新出现的瓶颈，让 tensor core 保持忙碌。

它比 Triton 快 2.7 倍，比 cuDNN 9.13 快 1.3 倍。对于视频理解、编码 agent、测试时计算扩展这类长上下文工作负载，这意味着在最新 NVIDIA GPU 上以更低的每 token 成本实现更智能的能力。

[阅读 FlashAttention-4 发布博客。](https://www.together.ai/blog/flashattention-4)

### **Together Megakernel**

一家领先的实时语音 agent 公司带着一个硬性约束找到 Together：time-to-first-64-tokens 超过约 100ms 就会破坏对话体验。在他们此前的部署（跑在 NVIDIA B200 GPU 上）中，这个数字是 281ms。对多数工作负载来说很快，但对他们不够快。

Together 的 kernel 团队与他们合作选定模型架构，然后手工优化出一个 Megakernel 实现——用单个 kernel 运行整个模型，目标直指 NVIDIA H100 的 HBM 带宽上限。

最终部署达到 77ms——相比他们此前的部署，性能提升 3.6 倍，单位经济性改善 7.2 倍。Together Megakernel 是最初与斯坦福合作者共同开发的开源研究的生产实现。它与 FlashAttention 同源，是一种软硬件协同设计，弥合理论可能与已部署系统实际交付之间的差距。

[了解更多关于 Megakernel](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles)

### **together.compile**

产出 Together Megakernel 这类结果的 kernel 优化，历史上需要专家——那些对 GPU 线程块映射、内存带宽约束和硬件特定调优有深刻理解的工程师，其深度是多数团队团队里没有的。together.compile 把这一过程的相当部分自动化了。

作为 ThunderKittens 的扩展，together.compile 只需一次函数调用就能在启动时生成优化后的 kernel 栈——无需改动模型代码。将其应用于 [Hedra](https://www.together.ai/customers/hedra) 的 Omnia 视频模型时，together.compile 把 200 帧的生成加速了 25%。

在生产级 Flux Kontext 基准测试中，服务器启动加跨 17 种分辨率生成 51 张图，使用 together.compile 用时 329 秒，而 torch.compile 用时 558 秒：提升 41%。启动时间同样下降，这对大规模运行自动扩缩容图像/视频生成的团队很重要。

## 强化学习

### **Reinforcement Learning API**

Together 的 Reinforcement Learning API 把完整的 Together 技术栈带入 RL 训练。支撑 Together 生产推理的那些 kernel、推理优化和研究进展，如今直接作用于以 rollout 为主的工作负载——那个主导 RL 墙钟时间的瓶颈。

这个 API 给团队的是掌控权，而不是黑箱。推理与训练作为两个独立、可配置的层暴露——团队决定 rollout 配置、权重推送频率以及算力在哪里运行。Together 负责同步与调度；如何运行 RL 的决策权仍在你手里。这种抽象层级让团队能够真正优化自己的训练循环，而不是绕着别人对"RL 应该怎么跑"的假设做工作。

RL 墙钟时间的 70% 以上是 rollout——即推理——而这正是 Together 的研究计划直接发力之处。[分布感知推测解码](https://arxiv.org/abs/2511.13841)和 [ThunderAgent](https://arxiv.org/abs/2602.13692) 都瞄准让 rollout 变快的吞吐与延迟特性，把每一项研究进展转化为更快的 RL 训练循环。

剩下的瓶颈是权重分发：在每个训练步后把更新后的权重送达推理节点。在单一数据中心内，Together 几秒内就能把新权重推送到所有推理节点。在全球分布式规模下——跨区域的节点、不同的 GPU 类型——同步在一分钟内完成。

### **ThunderAgent**

Reinforcement Learning API 处理基础设施层。ThunderAgent 解决的是一旦被训练和服务的工作负载本身就是 agent 形态时的挑战——编码 agent、科学发现 agent、大规模运行的多步推理流水线。

现有推理系统把 agent 工作流当作一系列独立、无状态的请求来处理，这造成三个层层叠加的问题：

- KV 缓存颠簸（tool call 打断执行时反复重算上下文）
- 跨节点内存不均衡（一些 GPU 节点过载，而另一些闲置）
- 工具生命周期盲区（Docker 沙箱和网络端口不断累积、无人回收）

ThunderAgent 通过引入程序感知（program-aware）抽象解决全部三个问题——把每个 agent 工作流视为一等调度单元，纵览完整执行视图。成果是：agent 服务吞吐提升 1.5–3.6 倍，分布式 GPU 集群上的 RL rollout 提升 1.8–3.9 倍，磁盘内存节省 4.2 倍，超越此前最先进的系统。ThunderAgent 今日开源，它是高吞吐 agent 训练将如何构建的研究基石。

[在 arXiv 上阅读论文](https://arxiv.org/abs/2602.13692)。

## 算法级推理优化

### **ATLAS-2**

推测解码——用小草稿模型提出 token、由更大的目标模型验证——是降低推理延迟最有效的技术之一。问题在于它今天的部署方式：推测器离线训练、作为固定产物发布，并随目标模型更新或流量模式变化而退化。重新训练需要数周的流水线工作和大量目标模型激活数据。

ATLAS-2 引入了在线训练飞轮，把被接受和被拒绝的 token 作为信号，从实时流量中持续更新推测器。新版推测器可以热插拔进入生产，不中断服务。

在已有静态推测器的成熟模型上，ATLAS-2 额外带来 1.2 倍性能提升。这个差距会复利放大：静态推测器只训练一次，随流量分布移动其接受率衰减；ATLAS-2 持续适应，性能随分布演化而提升，而不是随之退化。

[阅读关于 Aurora](https://arxiv.org/abs/2602.06932)——ATLAS-2 背后的开源框架。

### **缓存感知的 prefill–decode 分离（CPD）**

长上下文推理的可持续吞吐提升最高 40%。

标准 prefill–decode 分离把计算密集的 prefill 与延迟敏感的 decode 分开。但所有 prefill——无论冷热——仍在竞争同一份容量。真实流量中，携带 100K+ 全新上下文的大型冷 prompt 与主要包含可复用上下文的多轮请求一起排队。TTFT 恶化并不是因为热请求需要大量计算，而是因为它们卡在需要大量计算的那些请求后面。

CPD 在服务栈中加入第三层。缓存感知路由器按缓存命中率对每个进入的请求分类并相应路由：

- **冷请求**去往专用的 pre-prefill 节点，由其计算新上下文并填充分布式 KV 缓存
- **热请求**去往通过 RDMA 抓取 KV 块而非重算的 prefill 节点
- Decode 节点保持隔离、专注延迟。

三层 KV 缓存体系——GPU 显存、主机 DRAM，以及经由 RDMA 连接的集群级分布式缓存——让高频访问的上下文随时间向 GPU 迁移。同一个 100K token 的上下文，首次请求需要数秒计算，预热之后只需几百毫秒即可服务。

在 NVIDIA B200 GPU 上、以冷热混合的长上下文编码 agent 工作负载评估，CPD 相比标准分离式设计将可持续 QPS 提升 35–40%。

[阅读更多关于 CPD](https://www.together.ai/blog/cache-aware-disaggregated-inference)。

## 下一步

每一项发布都会有各自的深度解读。但它们共享一条值得点明的主线。

FA4 中的 kernel 进展直接为未来的 Megakernel 实现提供养分。ThunderAgent 的程序感知调度塑造了 Reinforcement Learning API 处理 agent 训练工作负载的方式。ATLAS-2 的在线学习循环是我们思考"任何应在真实流量下自我改进的系统"的一个模板，而不仅适用于推测解码器。我们交付的每一块拼图，都成为解决下一个问题的基础设施。

这正是"AI native"真正所指的飞轮。研究推进平台，平台吸引暴露出下一个难题的工作负载，这些难题驱动下一轮研究。复利是真实的，这也是为什么"理论可能与 Together 上可用能力之间的差距"往往比任何地方都小的原因。纯基础设施公司能部署本领域产出的东西，纯研究实验室能推进本领域的认知。而两者的结合——在生产中运行的研究、反哺研究的生产——是我们从第一天起就在构建的东西，也是以上所有发布的底色。

当今最苛刻的 AI 应用，将需要能拓展可能性前沿的基础设施。这正是我们在 Together 构建的东西。
