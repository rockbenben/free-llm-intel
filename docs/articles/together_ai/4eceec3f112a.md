# 推理的 99.9% 正常运行时间意味着什么？

**TL;DR**

- 简短版本：每个可靠性等级都对应一个特定的故障域，而每个故障域都需要各自的架构来扛住。粗略地说：
- 99% 意味着你的架构能扛住节点级故障：GPU 硬件故障、驱动崩溃、热事件。要达到这一级，通常需要自动化健康检查、节点排空（draining），以及单一数据中心（DC）内的快速副本替换。
- 99.9% 意味着你的架构能扛住一整个数据中心的故障。这通常意味着模型权重部署在两个设施中、每一侧都有足够容量吸收全部负载，并且两侧同时承接真实流量，而不是冷备。
- 99.99% 意味着你的架构能扛住区域级中断。这通常需要带 AZ 冗余的多区域部署，以及预留的故障转移容量。

可靠性数字很容易发布。难的是解释这些数字意味着什么：架构实际覆盖了哪些故障域，提供商在那些层面是否真正控制基础设施，以及凌晨 3 点出故障时会发生什么。

Together 为 Cursor、Decagon、Cartesia、Yutori 这样的团队运行推理服务。下面这些情况我们大多都被呼叫过，这是我们学到的经验。

## 可靠性数字的问题

推理宕机时，某个人的产品也跟着宕机。GPU 推理的失败方式与传统服务不同：硬件本身有故障模式，而 CPU 基础设施没有，且系统为性能做了极限调优。每 GPU 每分钟 100 万 token、200 TPS，或语音模型凭借定制 kernel 做到 sub-50ms TTFT——这些都几乎不留余量。在这样的系统上叠加可靠性，每多一个 9，难度都呈指数级上升。

有用的心智模型是分层，每一层的故障模式各不相同：

- **计算：** 显存（VRAM）中的 ECC 错误（我们见到最常见的东西；它会静默损坏权重，请求照样返回但输出不可信）、过热降频、驱动崩溃、NVLink 故障、无论 GPU 状态如何都会杀死整台机器的网卡或 CPU 故障。
- **网络：** 交换机故障，会在彻底不可用之前先劣化性能的光模块问题，以及能拿下整个站点的边缘设备故障。
- **存储：** 会阻塞权重拉取、拖住重新调度并级联成容量问题的故障。
- **软件：** 路由 bug、调度器边缘情况、处理不慎就会传播开来的部署失败。

这些都不会孤立地失败。存储的一次抖动会表现为容量问题；热事件早在任何健康告警触发之前，就以输出质量下降的形式出现了。擅长这件事，意味着学会从误导性的症状中读出真正的信号。

## 每个 9 实际需要什么

每一级都是不同的工程问题，而不是同一个问题的更难版本。以下是每一级实际需要的东西，以及我们围绕它构建的能力。

### 99%：扛住节点故障

目标是在请求到达一个正在劣化的节点之前抓住它。快速检测、排空、替换。有意思的工程问题是可观测性。

被动健康检查（硬件遥测、指标）能在不占用容量的情况下提供可见性，但会漏掉一类只在真实 GPU 负载下才显现的故障。主动健康检查能抓住那些故障，但需要容量来运行。你没法对一块正在服务流量的 GPU 做压测，这里存在明显的张力。人人都想接近 100% 利用率运行，为健康检查维持多余容量，本质上是拿可靠性换低效。我们走的路是把重新调度做得足够快：把检查与调度器集成，让它们在负载之间的空隙里运行，并让检查本身尽可能快。这仍是我们持续调优的事情。

这一级的天花板是建筑本身。热事件、变电站事故、边缘路由器故障——其中任何一个都能让单 DC 部署倒下，无论 DC 内部有多少冗余。多数提供商为此准备了备用系统，但一个不经常在真实条件下演练的冗余系统，就像让一个六周没训练的球员替补上场。故障转移也许写在纸上，它是否真的管用是另一回事。

### 99.9%：扛住整个 DC 故障

这一级的故障域是整个设施：电力、制冷、网络入口、边缘网络。扛住它需要：权重部署在两个设施，每一侧都有足够容量吸收全部负载，外加能干净切换的流量路由。

决定一个提供商是否真正交付这一级的架构选择，在于他们是持续向两个设施发送真实流量，还是维持冷备。我们选择了持续。大多数 99.9% SLA 声明都隐含承诺了这一级。问题是声明背后的架构是否真的为此而建。

这也是基础设施所有权变得具体之处。从超大规模云厂商（hyperscaler）或 neocloud 租用容量的提供商并不拥有自己的故障域。当电力或制冷层出问题时，他们只能向真正拥有它的人提交工单。他们无法告诉你他们的 SLA 在那一层物理上能扛住什么，因为他们不控制那一层。选择 Together AI 时，一张工单就能覆盖硬件、网络、存储和软件，因为我们在整个全球布局上拥有从芯片到 token 的可见性。另一种情况是：先给提供商提工单，提供商再给 hyperscaler/neocloud 提工单，然后排队。那种凌晨 3 点是什么样，我们见过。

### 99.99%：扛住区域级中断

这一级背后的根本挑战是：我们在本质上不可靠的硬件上构建可靠的 infrastructure。GPU 故障率显著高于 CPU 故障率，每一种故障模式都必须被考虑在内。四个 9 需要：带 AZ 冗余的多区域部署，以及在故障转移区域预留足以吸收一次全区域中断的容量。关键词是"预留"。不是"我们能把流量路由过去"，而是"我们此刻在那里有闲置的空间"。

## 在选定提供商之前该问的问题

SLA 只是起点。下面这些问题直指其下的架构、出事时谁负责什么，以及恢复有多快。我们也期待你们这样问我们：

- **关于基础设施所有权：** 模型托管在哪里，是单区域还是多区域？你们拥有自己的基础设施，还是从 hyperscaler 或第三方租容量？谁负责数据中心——电力、制冷、网络传输？你们有物理访问权限，还是要走工单队列？如果一个 DC 出中断，你们能多快把那个部署挪到别处？你们是为这件事专门维持备用容量，还是把资源绷得很紧？
- **关于全栈专业能力：** 你们在整个栈上是否有芯片到 token 的可见性，还是在推理与硬件之间存在观测盲区？出问题时，你们的团队能直接访问硬件，还是依赖第三方来诊断和响应？你们的 GPU 硬件专业能力在推理软件之外有多深？
- **关于容量与故障转移：** 故障转移如何测试：持续跑真实流量，还是定期演练？当故障转移真正需要执行时，你们现实的 RTO 是多少？
- **关于 SLA 度量：** 每个 SLA 等级实际覆盖哪个故障域：节点、DC 还是区域？你们的 SLA 是在负载均衡器处度量，还是在推理成功完成处度量？客户端重试是否计入你们的正常运行时间度量？

## 我们的数字定义

模糊的 SLA 定义，正是承诺与交付之间的差距藏身之处。以下是我们确切度量什么，以及如何定义每个术语。

| 我们度量什么 | 我们如何定义 | 我们的数字 |
| --- | --- | --- |
| 实际交付的正常运行时间 | 推理端点成功服务请求的时间百分比（在推理完成处度量，而非负载均衡器） | 99.9%（持续交付） |
| 保证 SLA：单 DC | 单一数据中心部署的合同 SLA | 99% |
| 保证 SLA：多 DC | 多数据中心部署的合同 SLA | 99.9% |
| 故障转移时间 | 设施故障后将流量切换到健康容量所需时间 | 秒级 |
| 请求量 | 度量窗口内服务的推理请求 | 2B TPM+ |

我们在推理完成处度量，而不是在网关。一个请求到达负载均衡器但在 GPU 上失败，在我们的账目里就是宕机。还有一点：可用性和性能是不同的合同。在 Provisioned Throughput 中，你购买的是一份能交付特定 TPS 的 GPU 配额，而不仅仅是端点能响应。一个"在线"但只交付约定吞吐 30% 的服务，并没有兑现交易。

## 来看看我们的架构

每个提供商都会给你一个数字。真正重要的是其背后的架构是否为实现这个数字而建，以及他们是否拥有保证必须成立的那一层基础设施。

这些都是可以回答的问题。请任何提供商逐一讲解每个 SLA 等级背后的架构；问他们是拥有基础设施，还是坐在别人的东西之上；问故障转移路径是否在真实流量下运行。真正了解自己基础设施的提供商能很快作答。
