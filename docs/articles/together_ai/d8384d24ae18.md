Together GPU Clusters 公开预览：可中断的 GPU 计算，五分钟排空窗口，自动向目标容量回填。

今天我们宣布 Together GPU Clusters 的可抢占计算（preemptible compute）进入公开预览，所有区域的 Kubernetes 集群均可用。可抢占节点为团队提供了一种更低成本的方式，来运行可容忍中断的工作——短实验、推理突发、批处理任务——用的就是他们已经在用的同一套 GPU 基础设施，按不足一小时计费，固定为按需价格的 50%。从今天起，你就可以为新集群或现有集群添加可抢占容量。

## 可抢占计算如何工作

可抢占计算为 Together GPU Clusters 增加了第二种计算类型。标准节点同步交付、绝不被抢占。可抢占节点使用同样的 NVIDIA 加速算力，取自未使用的容量，并会在那些容量他处需要时被回收。

可抢占节点按按需价格的固定 50% 计费。费率恒定，不随现货（spot）市场波动。

当节点被回收时，集群遵循五分钟排空（最长 5 分钟）流程：

- **T+0** —— 节点被 cordon，触发一个 `TogetherPreempted` Kubernetes 事件，你的 pod 收到 SIGTERM。
- **T+0 到 T+5:00** —— 你的工作负载有最长五分钟（`terminationGracePeriodSeconds`）来做 checkpoint 并退出。
- **T+5:00** —— 节点被移除。

节点移除后，集群仍保留其可抢占目标，并在容量可用时自动向该目标回填。你不需要申请替换容量。

计费粒度为不足一小时，用量每一到两分钟计量一次。运行 12 分钟的节点大约按 12 分钟计费。

可抢占节点不是独立的集群类型。他们加入你的现有集群，标记为 `together.ai/compute-class=preemptible`，让可中断的 worker 跑在折扣容量上，而协调器、login pod 和服务副本留在标准节点上。

## 可抢占计算适合哪里

五分钟的回收流程让恢复行为成为决定性因素。能续跑、重试或重新排队的工作可以使用可抢占容量，而关键组件应留在标准节点上。

**短实验。** Ablation、配置扫描、快速微调、评估、蒸馏、批量推理都是好候选，只要工作能从 checkpoint 恢复或在 worker 消失后重试。Ray Train、PyTorch Lightning 这类框架无需干预即可从最新 checkpoint 恢复。作为参照，一个 321B 参数模型 GLM5.3 Flash 的全权重 checkpoint 约 3.5TB，即便在性能退化的并行文件系统上写入也只需 22 秒到 4 分钟。在五分钟排空窗口内留有富余。

**临时突发。** 当批处理或内部推理需求飙升时，加入更便宜的可抢占节点吸收突发和非关键负载，而不是为峰值维持标准容量、或冒突发期标准计算可用性不足的风险。被中断的请求会重新排队；面向用户的副本留在标准节点上。

共同主线：可分块、可 checkpoint、可重试的工作。多天不 checkpoint 的运行、没有回退路径的严格 SLO 服务，都不适合。

Together 有很强的 dogfooding 文化——若干内部研究、开发/测试和非关键生产负载就基于我们的可抢占计算 GPU 集群，让我们得以跨产品团队利用闲置容量。

## 启用之前

- **把可抢占节点当临时资源。** 预览期内没有最短节点生存时间，所以要频繁 checkpoint，并假设容量随时可能消失。
- **关键组件留在标准节点。** 协调器、login pod、面向用户的副本属于保证容量——用 `compute-class` label 来强制这一点。
- **用好排空窗口。** 把 `terminationGracePeriodSeconds` 设到最高 300 秒，在 pod 收到 SIGTERM 时做 checkpoint，并在节点被移除前退出。
- **集群至少需要一个标准节点**，且节点不能在两种计算类型之间就地转换。

## 如何使用

工作负载为抢占做好准备后，设置分两部分：设定可抢占目标，并把合适的工作调度到带 label 的节点上。

你可以在创建集群时或已在运行的集群上设置目标，使用 Together Cloud 控制台、CLI 或 API。API 同时报告请求的目标 `desired_preemptible_gpus` 和当前存活的容量 `allocated_preemptible_gpus`。由于可抢占节点取自未使用容量，容量紧张时实际分配量可能低于期望目标。

### 在新集群上

先选标准节点数，再在其上添加可抢占目标。

```
tg beta clusters create \
  --name my-cluster --region us-central-2 --gpu-type RTX_6000_PCI \
  --cluster-type KUBERNETES --num-gpus 8 --billing-type ON_DEMAND \
  --num-preemptible-gpus 8 \
  --project-id <proj_id>
```

### 在现有集群上

需要更多 worker 容量时调高可抢占目标，工作完成后调低。全程集群保持运行。

```
tg beta clusters update <cluster-id> --num-preemptible-gpus 16
```

### 在可抢占节点上调度工作

显式瞄准可抢占节点：

```
nodeSelector:
  together.ai/compute-class: preemptible
```

抢占通知以 SIGTERM 送达 pod、以 Kubernetes 事件（`reason=TogetherPreempted`）、在控制台的 Event Timeline、以及通过 Together API 的 `node_lifecycle_events` 提供——处理模式见[文档](https://docs.together.ai/docs/preemptible-compute)。
