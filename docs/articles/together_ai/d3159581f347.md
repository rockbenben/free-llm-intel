基准表错过了 DeepSeek-V4 的重点：真正重要的变化是架构。V4 把百万 token 上下文变成了一个服务系统问题。

模型通过一种混合注意力设计支持 1M token 上下文窗口：在 key-value（KV）存储之前压缩上下文、混合压缩与局部注意力路径，并改变前缀复用的方式。这些选择降低了 KV 压力，但只有当推理引擎能管理随之而来的缓存布局、恢复局部状态、有效组批、并选择匹配负载的 endpoint 画像时，这些节省才有意义。

本文聚焦 V4 的压缩稀疏注意力（CSA）/重度压缩注意力（HCA）/滑动窗口注意力（SWA）设计带来的服务影响，基于 Together 在 NVIDIA HGX B200 上的早期 bring-up 工作。V4 还包含其他架构与训练改动，包括流形约束超连接（mHC）残差连接和 Muon 优化器选择，但那些不在本文主要范围内。

## **V4 压缩 KV 缓存的 token 轴**

自回归推理把先前上下文存在 KV 缓存里。decode 期间，每个新生成的 token 都从这个存储状态读取并对其做注意力。缓存随序列长度增长：

`KV cache ∝ layers × tokens × kv_heads × head_dim × bytes`

在长上下文下，KV 缓存对服务造成双重打击：它限制并发，因为每个活跃请求占用内存；它拉低吞吐，因为 decode 每一步都要读取存储的上下文。V4 之所以重要，是因为它同时进攻这个问题的两侧：要存的缓存条目更少，要流经注意力的缓存条目也更少。

在 NVIDIA Blackwell 上，这种缓存压力直接映射到服务经济学。长上下文推理取决于：在保留足够 KV 以支撑并发的同时，为 decode 保住内存带宽。V4 的 token 轴压缩让这个取舍更有利：引擎有更多空间组批请求、复用前缀，把长上下文负载保持在高效服务区间内。

近期的模型架构已经削减了上述乘积中的不同项。分组查询注意力（GQA）减少 KV 头数。多头潜在注意力（MLA）把 KV 压缩成潜在表示。FP8、MXFP4 和 [NVFP4](https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/) 减少每元素字节数。DeepSeek-V3.2 稀疏注意力减少了 decode 期间需要读取的 KV 量，但全量缓存仍须常驻。

DeepSeek-V4 瞄准的是 token 轴。它在 KV 存储之前压缩上下文。

这才是重要的转变。

在原始 BF16 多头注意力计算下，一个 70B 级模型每 token 可能需要数兆字节 KV 缓存。确切系数取决于层数、KV 头数、head 维度和精度。在 1M token 时，缓存对单个请求变得不切实际。V4 的 token 轴压缩，加上 MLA 式的头压缩与低精度 KV，把每请求缓存占用降到让超长上下文实质更可行的程度。

早期 bring-up 中，V4 的服务能力更多取决于引擎如何处理 SWA 状态，而非压缩后的 CSA / HCA 缓存。一个全量 SWA 实现的实际每 token KV 占用反而高于我们的 V3 路径——约 3.8 KB 对 3.4 KB——因为引擎存储了完整的滑动窗口状态。

实际收益来自缓存策略。只保留最可能被复用的 SWA 状态，我们在单个 NVIDIA HGX B200 节点上把 KV 缓存总容量从约 1.2M token 提升到 3.7M token，改动极小。这是主要的服务教训：V4 的架构创造了长上下文效率的机会，但实际兑现的容量取决于推理引擎如何存储、重算和逐出不同缓存类型。

实际收益不止于完整 1M token 请求。它让 200K–500K token 的负载更并发、更不脆弱，因为引擎在内存压力迫使逐出或限制组批之前有更多 KV 预算。更早的百万 token 上下文模型在内存、并发与成本上仍留下重大服务挑战。当服务策略匹配缓存布局时，V4 把这个区间变成真正可用的负载。

## **V4 需要多种 KV 缓存布局**

许多现有服务路径假设接近单一的 KV 缓存布局：每层每 token 一个缓存对象，全栈同构。V4 要求三种不同缓存类型，跨层混合。

压缩稀疏注意力（CSA）以步长 4 压缩上下文，但每个压缩条目由稍宽的感受野构建。在 V4 配置中，每个条目总结 8 token 的邻域，所以相邻压缩条目在边界处重叠。当查询选取 128 个压缩条目时，它选的是局部邻域的摘要，而不是孤立的 token 位置。这让 CSA 对百万 token 前缀的选定区域拥有更细粒度的读取路径，同时仍缩减存储缓存占用。

重度压缩注意力（HCA）用同样的压缩思想但步长为 128。在 1M token 上下文长度下，这把缓存从 1M 个 token 位置降为约 8K 个压缩条目。这是与 CSA 的关键差异：压缩缓存小到模型可以对其做密集注意力，而无须选择 top-k 子集。HCA 给模型对整个上下文的粗粒度全局读取，CSA 给它对选定区域的细粒度稀疏读取。

滑动窗口注意力（SWA）保留局部路径。窗口很短，约 128 token，保持近期上下文精确。

全栈中，引擎要管理 CSA 压缩状态、HCA 压缩状态、SWA 局部状态，以及 CSA 和 HCA 压缩器用到的短未压缩尾部状态。这些对象大小、生命周期、读取模式各不相同。

新的注意力 kernel 只是工作的一部分。更难的服务问题是内存管理：组批请求、逐出缓存页、复用前缀，同时在模型不同部分依赖不同存储状态的情况下保持 decode 吞吐稳定。

## **前缀缓存变成一种存储策略**

前缀缓存通常始于简单规则：共享前缀、共享 KV。在 V4 这里，问题变成：共享哪种缓存？

一个共享前缀包含 CSA 状态、HCA 状态、SWA 状态，以及 CSA 与 HCA 压缩器用的未压缩尾部状态。CSA 和 HCA 足够紧凑、可高效存储。SWA 是精确局部状态，对长前缀存储更贵——一旦缓存层级移出 GPU 内存尤其如此。

DeepSeek 论文描述了三种 SWA 策略。

第一种存完整 SWA 缓存。复用简单，因为引擎能直接恢复完整前缀状态，但存储与写带宽增长很快。

第二种存周期性 SWA checkpoint。引擎每 K 个 token 保存一次状态，缓存命中时重算中间缺口。

第三种命中时重算 SWA。引擎存储压缩的 CSA / HCA 状态，前缀复用时重建 SWA 路径。代价以窗口大小乘层数为界。128 token 窗口、61 层，约 8K token 的重算。对一个 1M token 前缀，这笔取舍说得通。

在我们当前的 V4 bring-up 中使用第一种策略：存完整 SWA 缓存。这让前缀复用保持直截了当，在服务路径其余部分尚未成熟时避免加入重算复杂度。代价是更高的缓存占用，这使缓存策略与逐出行为随上下文长度和并发增长变得更重要。

V4 把前缀缓存变成跨缓存对象的策略决策：存 CSA 和 HCA、决定如何处理 SWA、按各自成本逐出每种类型。

## **V4 性能依赖工作区间**

V4 的收益最先出现在 KV 缓存主导的地方。

长上下文、decode 密集的负载大部分时间在读缓存，V4 的压缩缓存布局降低这种压力。

短上下文、prefill 密集的负载走不同路径。CSA top-k 选择、HCA 压缩读取和 SWA 引入了成熟密集注意力 kernel 路径之外的操作。Kernel 成熟度重要。精度格式也重要：V4 的 MoE 权重使用 MXFP4，在 NVIDIA Blackwell GPU 上性能特性与 NVFP4 不同。这让短上下文 prefill 对 kernel 成熟度尤其敏感，而长上下文 decode 更直接从 KV 缓存缩减受益。

这形成了一个区间分裂。长上下文负载早期就受益于 V4 的缓存节省；短上下文负载更依赖 kernel bring-up 与 prefill 优化。这对新架构是典型的：首个实现建立正确性，后续迭代收敛到硬件效率。

Together 正在 prefill 和 decode 两条路径上继续 V4 kernel 工作。

开发者应在自己的实际工作区间基准 V4。一个 1M 上下文编码 agent 与一个短上下文聊天助手，考验的是服务栈的不同部分。

## **同一份权重需要不同的服务画像**

V4 拉大了不同负载形态之间的差距。

长上下文 agent 最直接受益于架构。它们在 decode 时读取大量缓存，所以 V4 的压缩 KV 布局、更大的张量并行配置、组批和前缀复用都重要。这是模型的长上下文设计最先应当显形的区间。

跨共享仓库的编码 agent 与之相关，但服务问题更前缀密集。同样的项目文件、仓库状态或任务脚手架可能在多个请求间重复，于是缓存分层与 SWA 重算策略成为一阶选择。瓶颈同时包括长上下文和重复上下文复用。

短聊天位于频谱另一端。这些负载从百万 token 缓存压缩受益有限，反而暴露 prefill 延迟、小批开销与 kernel 成熟度。要服务好它们，可能需要更小的张量并行组、最小组批延迟，以及为短上下文路径调优的 kernel。

RL rollout 关心另一种经济单位：每条长轨迹的成本。它们可能与长上下文 agent 共享服务机制，但优化目标是实验吞吐——每份训练预算能生成多少条长程 rollout——而非单纯单请求延迟。

同一份权重可以服务所有这些负载，但每种在不同 endpoint 配置下表现最佳。Together 正在评估具有不同组批、并行和缓存策略的 endpoint 画像。

## **迁移到 V4 之前该测什么**

百万 token 服务对那些在长任务上累积状态的系统最有意义：编码 agent、研究 agent 及其他更长程任务。对这些负载，成本模型常常从每 token 价格转向每完成轨迹的成本。

把流量切到 V4 之前，基准四件事：上下文长度区间、前缀复用、缓存策略、endpoint 画像。

对长上下文 agent，测缓存命中率、decode 吞吐和每完成任务成本。首 token 时间只捕捉图景的一部分。

对短聊天，在你真实的上下文长度和 batch size 下比较延迟。V4 的长上下文收益未必先体现在短聊天延迟上。

对共享前缀负载，测 SWA 全量存储 vs 命中重算。前缀长度、缓存层级延迟和复用频率决定答案。

对 RL rollout，按轨迹长度与每实验 rollout 数计算成本，而不只看 token 价格。

对混合流量，预期取舍。一个 endpoint 可以服务混合负载，但负载形态明确后，画像专用 endpoint 通常表现更好。

质量仍需度量。更长上下文为有用状态、检索噪声、压缩伪影和延迟创造了更多空间。它也改变压缩策略：构建者对何时保留原始状态、何时摘要、何时重置有更多掌控。

## **结论**

DeepSeek-V4 的效率是一种系统属性。架构通过沿 token 轴压缩来降低 KV 压力，但服务引擎必须管理由这一选择衍生出的缓存类型、前缀策略、kernel 路径和 endpoint 画像。

这也是全栈协同设计重要之处。模型改变缓存布局，推理引擎改变内存管理与前缀策略，kernel 适配新的注意力与精度路径。NVIDIA 为 Blackwell 上的 V4 + MXFP4 提供 day 0 支持，也让开发者能用 NVFP4 优化性能。通过深度协同设计，Together AI 与 NVIDIA 都在通过软件优化持续提升硬件效率，例如 [NVIDIA Dynamo。极致协同设计在 DeepSeek V4 等领先开放模型上解锁最低每 token 成本，在 NVIDIA Blackwell 上释放更高性能](https://www.together.ai/blog/together-ai-at-nvidia-gtc-2026)。

跑起 V4 只是起点。把它的架构节省转化为更低延迟、更高并发和更便宜的长上下文负载，需要缓存策略工作、kernel 工作和负载专属的服务画像。下一步是度量：每 token KV 占用、上下文长度-吞吐曲线、前缀缓存策略影响，以及不同流量形态的 endpoint 画像。随着 V4 kernel 与缓存策略成熟，我们会发布这些数字。

## **FAQ**

**DeepSeek-V4 的上下文窗口是什么？** DeepSeek-V4 支持 1M token 上下文窗口。它通过一种混合注意力设计实现：在 key-value（KV）存储之前压缩上下文，混合压缩与局部注意力路径，并改变前缀复用方式。正是这一架构变化让百万 token 上下文成为可行的服务负载。

**DeepSeek-V4 中的压缩稀疏注意力（CSA）是什么？** CSA 以步长 4 压缩上下文，每个压缩条目总结 8 token 邻域，相邻条目在边界重叠。查询选取约 128 个这样的压缩条目，给模型一条进入前缀选定区域的细粒度稀疏路径，同时缩减存储缓存占用。

**重度压缩注意力（HCA）是什么？** HCA 使用与 CSA 相同的压缩机制但步长 128。在 1M token 上下文下，这把缓存从 1M 位置降为约 8K 压缩条目，小到模型可以对全部条目做密集注意力。HCA 提供粗粒度全局读取，CSA 提供选定区域的细粒度稀疏读取。

**DeepSeek-V4 相比更早模型如何减小 KV 缓存？** DeepSeek-V4 沿 KV 缓存的 token 轴压缩。早期技术削减缓存乘积中不同的项：GQA 减少 KV 头，MLA 压缩 head 维度，FP8/MXFP4/NVFP4 减少每元素字节数。DeepSeek-V3.2 减少了 decode 时需要读取的缓存量但保持全量缓存常驻。V4 减少的是存储的 token 条目本身数量。

**为什么服务 DeepSeek-V4 需要多种 KV 缓存布局？** 模型使用三条注意力路径（CSA、HCA 和滑动窗口注意力）跨层混合。每条产生大小、生命周期、读取模式不同的缓存对象。推理引擎必须按请求同时管理三者，这让内存管理、逐出和前缀复用比单缓存设计更难。

**前缀缓存在 DeepSeek-V4 中如何工作？** 前缀缓存变成逐缓存类型的策略决策。CSA 和 HCA 状态足够紧凑可存储。SWA 状态是精确局部状态，长前缀下变得昂贵。DeepSeek 论文描述三种选项：存全量 SWA、存周期 checkpoint，或缓存命中时重算 SWA。命中重算以窗口大小乘层数为界，对 1M token 前缀约 8K token 重算。

**哪些负载从 DeepSeek-V4 受益最大？** 长上下文、decode 密集的负载最先受益，包括编码 agent、研究 agent，以及在长任务上累积状态的 RL rollout。对这些，成本模型从每 token 价格转向每完成轨迹成本。短上下文聊天负载收益较小，因为它们暴露的是 prefill 延迟与 kernel 成熟度，而非 KV 缓存压力。

**我该把短聊天流量迁到 DeepSeek-V4 吗？** 先测。V4 的收益出现在 KV 缓存主导之处。短上下文、prefill 密集的负载考验仍在成熟的较新 kernel 路径（CSA top-k 选择、HCA 密集读取、MXFP4 MoE 权重）。切换之前在你真实的上下文长度和 batch size 下比较延迟。长上下文 agent 与短聊天即使在同一份权重上也可能需要不同的 endpoint 画像。
