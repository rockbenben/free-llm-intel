## 实验跟踪

一次运行的轨迹越早可见，下一个决策就能越早做出——调整数据、改超参，还是让它跑完。Fine-tuning 任务现在在每个训练和评估步记录指标，并直接通过 Together API、CLI 和 UI dashboard 暴露。指标、任务状态和产物留在同一处，让你整段模型开发旅程都待在同一个平台上。

每次运行捕捉核心训练信号：loss、gradient norm、learning rate。当你加上验证集，评估 loss 与指标会与训练指标一同跟踪。

在 dashboard 里，每个任务都有一个 Metrics 标签页，曲线在运行仍在进行中就实时更新——你可以选多个任务在同一组坐标轴上一起画图，让一次扫描读起来是一张图而不是十几个浏览器标签页。你也可以通过我们的 Python SDK 做同样的事：一条命令、终端里出曲线、无需切换上下文。

API 返回底层序列——每个记录的步，可按范围过滤或降采样。这样你可以把指标拉到 notebook、你已有的内部 dashboard 或任何去处。

[更多细节见文档](https://docs.together.ai/docs/fine-tuning/monitoring#retrieve-metrics)。

## 更多训练控制

### Expert LoRA

在 Mixture-of-Experts 模型里，超过 90% 的参数、以及模型真正*知道*的大部分内容，住在专家层里。标准 LoRA 微调从不碰它们：adapter 挂在注意力上，专家保持冻结。现在你可以把 LoRA adapter 放到专家本身，让你的任务能训练知识所在的那些层。

差异出现在任何需要模型学真正新东西的任务上。我们教模型 200 条编造的事实（基座模型原本一条都不知道）：包含专家层的 adapter 回忆出最多 89% 的新知识，而仅注意力的 adapter 在同一模型上止步 15%。它们还保住了模型更多既有知识，并在 MMLU-Pro 上 outright 取胜：75.3% 对 71.5%。

训练动态解释了差距：仅注意力 adapter 时，越来越多的 routed experts 在微调中干脆不再被使用；而专家 adapter 让整个 mixture 保持参与。

启用 expert adapter 很简单：只需把专家模块加进 `lora_trainable_modules`。其余微调工作流与[任何其他 LoRA 任务](https://docs.together.ai/docs/fine-tuning/lora-vs-full#target-moe-expert-layers)一样。

### Early Stopping

Fine-tuning 任务现在可以在停止改进时自动结束。这意味着你拿到的是最好的模型，而不只是最后一个，你也不用为不再有帮助的训练付费。启用 early stopping、提供验证集，我们在每次评估时盯着你的验证 loss。曲线走平时，我们停止运行、把验证 loss 最好的 checkpoint 留作你的最终模型，并自动退还每一个你没用到的训练步。

想要更细控制时，patience、对小改进的敏感度和 warmup 都可调。[完整参数参考在文档里](https://docs.together.ai/docs/fine-tuning/early-stopping)。

### 任意 batch size 支持

有些任务需要装不进 GPU 内存的 batch size：长序列、大模型，或为大全局 batch 调优的配方。现在无论单次前向装得下什么，你都可以按想要的任意有效 batch size 训练。设置 `gradient_accumulation_steps`，梯度在每次优化器更新前跨 micro-batch 累加，得到有效 batch = batch_size × gradient_accumulation_steps。[细节见文档](https://docs.together.ai/reference/post-fine-tunes#body-gradient-accumulation-steps)。

## 灵活透明的数据处理

### 检查 tokenize 后的数据

此前，数据处理在 fine-tuning 任务内部是黑箱：你看不到数据如何被 tokenize 和打包。当结果与你预期不同——chat template 的应用方式与你假设的不同、label 在错误的地方被 mask、行被静默截断——你会得到难以追溯原因的质量下滑。

现在你可以在启动任务前检查 tokenize 后的数据。预览上传文件中任意行，用即将微调的基座模型的精确 tokenizer 与 chat template 处理，确切看到训练将消费什么：token ID、token 字符串、逐 token label、对 loss 有贡献的 span，以及该行是否在模型最大序列长度处被截断。预览几秒完成。

你还可以检查训练循环实际消费了什么。每个 fine-tuning 任务现在暴露其完全准备好的数据集的一个子集——按 trainer 收到的样子 tokenize、打包、collate 完成。可通过 Python SDK 或控制台任务页的 Download 链接获取。

[数据集中预览详见文档](https://docs.together.ai/reference/cli/finetune#preview)。

### 样本权重

不是每个训练样本都值得同等对待。现代数据集常混合多个来源与领域——人工标注数据与合成数据并存、一个领域与另一个并存——而默认每个样本对训练的影响相同，不论质量或重要性。

Together Fine-Tuning 现已支持逐样本加权，让你精确控制每个数据点的影响。在 JSONL 文件里任意样本加一个 weight 字段，训练就相应缩放该样本对 loss 的贡献。权重适用于所有支持的 JSONL 数据格式和所有训练方法。

[样本权重详见文档](https://docs.together.ai/docs/fine-tuning/data-preparation#data-weights)。

### 事前文件验证

数据集验证过去在训练任务内部运行。如果你的文件第 59,000 行有一个格式错误的 tool call，你是在任务已排队、已调度、已启动之后才知道——等几分钟发现一个 typo。

现在，fine-tuning JSONL 文件上传完成即触发一次完整的服务端检查，结果直接落在文件对象上，让你在创建任务之前就能看到任何问题。检查覆盖完整 schema：消息结构与角色、工具定义与 tool-call/response 配对、reasoning 字段、多模态内容与图像解码、偏好对结构、样本权重的类型与范围——错误信息会带上问题样本的索引。

成功的验证还会报告我们从你的数据里检测到什么——数据集格式、行数、以及是否包含样本权重、消息权重、tools、并行 tool calls、reasoning trace 或图像——让你确认平台按你的意图读取了数据集。

[事前文件验证详见](https://docs.together.ai/docs/fine-tuning/data-preparation#wait-for-server-side-validation)。

### 打包控制

Sequence packing 是一种把多个序列拼接成一个以避免在 padding token 上浪费计算的技术。它显著提升吞吐、缩短训练时间，所以在 Together Fine-Tuning 中默认启用。尽管有这些效率好处，它并不总是正确选择：数据集小，packing 可能让每个 epoch 留下的优化步太少。

Sequence packing 及相应的阻止跨样本注意力的 2D attention mask 可视化（图源，采用 Creative Commons 4.0）。

现在你可以完全控制 sequence packing：用一个标志彻底禁用，或在预 tokenize 数据格式里用 `position_ids` 设定你想要的打包程度。

[更多信息见文档](https://docs.together.ai/docs/fine-tuning/data-preparation#packing)。

## 即将推出：从微调到推理的更快路径

每个中间 LoRA adapter 都将可以在微调还在进行时部署。你不用等整个训练任务完成，很快就能开始评估结果，每次迭代节省数小时乃至数天。第一个 adapter 一保存，你就可以通过 Dedicated Model Inference 部署它，或以 Multi-LoRA 方式挂到已在运行的 endpoint 上——避免为每个实验单独起 endpoint 的成本与启动时间。

首批支持计划在 GLM-5.3 上，随后是 Kimi K3。随着新工作流临近发布，我们会分享可用性细节、完整支持模型列表和完整 API 演练。
