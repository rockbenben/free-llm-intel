TL;DR

**直觉：** 别让一个天才一小时读完一座图书馆。让十个实习生各读一本书。

我们的研究 "When Does Divide and Conquer Work for Long Context LLM?"（ICLR 2026）引入了一个研究这一点的框架。我们发现，较小模型用一种策略性的"分而治之"设计，能在长上下文任务上追平或击败 GPT-4o 的单次处理。

[[paper, ICLR 2026](https://arxiv.org/abs/2506.16411)] [[code](https://github.com/nehzux/DivideConquerAgents)]

现代 LLM 越来越支持 128K、200K 乃至 1M+ token 的巨大上下文窗口。这在理论上解锁了强大用例，如在单个 prompt 里分析整个代码库或摘要全书。

然而，"把一切都塞进一个 prompt" 的承诺在实践中经常失败。随着上下文长度增长，性能以意外方式退化。"分而治之" 事实证明是长上下文任务的一个有吸引力的解法，如下图。

"分而治之" 框架。Planner 重写任务说明；每个 Worker 处理长文档的一个子集；Manager 汇总信息并给出最终答案。

在论文中我们发现，弱一些的模型用精心设计的"分而治之"框架，能在长上下文任务上追平或击败 GPT-4o 的单次处理。

## **核心问题：长度的"迷雾"**

我们如何充分利用这种"分而治之"方法在长上下文任务上的力量？我们把挑战拆成三种噪声源：

- **模型噪声（"脑雾"）：** 模型不是线性遗忘，而是被淹没。我们的研究表明模型困惑度随输入长度**超线性**增长。从数学上讲，切分任务更优——因为你每换一个更短的 chunk 就重置一次困惑计数器。
- **任务噪声（"孤岛效应"）：** 有时一个 chunk 单独看不懂（如代词指向前一章）。文本被切分时，这种"跨 chunk 依赖"制造噪声。
- **聚合器噪声（"糟糕摘要"）：** 即使 workers 完成了各自的工作，最终的 manager 模型可能无法正确拼接部分答案。

天真的 "MapReduce" 方法常因**聚合器噪声**而失败——即因为 manager 缺乏上下文，最终答案混乱或不一致。我们的框架预测：如果你通过更清晰的指令降低这种噪声，就能释放弱模型的力量。

**"第二大数"例子：** 考虑一个任务，workers 要帮忙在一个巨大列表里找第二小的数。如果你天真地要求每个 worker 在自己那段里"找第二小的数"，最终 manager 会失败——因为全局第二小的数可能恰好是某个 chunk 里最小的数。

- 天真 Prompt："找出第二小的数。"（失败）
- 规划后的 Prompt："识别并返回最小的两个数。"

仅仅调整 prompt 来应对这种聚合噪声，我们就确保 manager 拿到正确的数据来计算全局答案。

## **用实验验证理论**

我们在多样任务（检索、问答、摘要等）上测试了这个框架实现。如下图所示，用这个框架的弱模型（如 Llama-3-70B 或 Qwen-72B）胜过 GPT-4o 一次性读全文。当单次处理模型（红色虚线）随上下文长度增长退化时，D&C 模型保持高性能。

红色虚线是 GPT-4o 一次性处理整个文本。彩色线是用带规划的分而治之的较小模型。注意：在正确的 chunk size 下，弱模型稳定取胜。

## **工程收益**

从工程视角，这个框架带来三大实际好处：

- **更便宜：** 把重活交给更小更便宜的模型（Workers），而不是按旗舰 token 付费。
- **更快：** Workers 并行运行。避免用单个串行 pass 处理巨大 128k token 上下文的高延迟。
- **好调：** 我们发现，由于噪声曲线的可预测性，只测 5 个随机样本就足以找到最优 chunk size。你不需要对整个数据集做穷尽搜索。框架的另一种灵活性是解耦 worker 和 manager、给它们分配不同的 LLM 后端。

## **需要注意：什么时候该用单次处理而非分而治之**

这个方法不是银弹。它在跨 chunk 依赖适中的任务上表现最好——如问答、检索和摘要。当**任务噪声主导**时收益结束。如果你的任务要求追踪第 1 页上一个与第 100 页相连的微妙线索（如我们论文里的 "Dialogue Character Inference" 任务），"分" 这一步会破坏必要的上下文。在这些高协同的情况下，"天才" 模型通读整个图书馆仍是唯一去路。更多细节见论文。
