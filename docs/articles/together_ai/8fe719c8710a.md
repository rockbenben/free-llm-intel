# 如何评估和基准测试大语言模型（LLM）

测试、对比并理解 LLM 的性能。

TL;DR

学习如何用 MMLU、GSM8K、HumanEval 等数据集评估和基准测试大语言模型。更进一步，我们还将探索可靠的、面向真实世界的 LLM 性能测试的方法与最佳实践。

大语言模型（LLM）改变了我们与 AI 交互的方式——从驱动聊天机器人到生成代码、解决复杂数学问题。但随着这些模型日益精密，一个关键问题仍然存在：我们究竟如何度量它们的能力、判断**哪些模型真的更好**？

答案是基准测试与评估框架——我们用来测试、对比和理解 LLM 性能的系统化方法。理解如何正确评估 LLM 至关重要。

在这篇博客里，我们将探讨关于 LLM 评估你需要知道的一切：从优秀基准的基本原则，到实践中使用的各种评估方法学。此外，我们还附上实操代码 notebook，帮你上手对客户们每天都在做的真实用例跑评估！

## **为什么 LLM 基准与评估很重要**

### **进步的基石**

基准是 AI 开发与进步的指南针。它们让我们能回答根本问题：Kimi-K2 在 agentic 编码任务上比 Claude 更好吗？过去一年语言模型在数学推理上进步了多少？开源模型的哪个微调版本在你的内部评估上表现最好？

想想 DeepSeek R1 的发布——它因与前沿模型并驾齐驱的表现成为头条。公司的说法不是基于主观印象，而是有六种不同基准上的系统性评估背书，包括 AIME 2024、CodeForces、GSM8K 和 GPQA Diamond。这种标准化对比让整个 AI 社区能迅速理解 DeepSeek R1 相对于 OpenAI 的 o1、Anthropic Claude 系列等既有模型处于什么位置。

来源：https://huggingface.co/deepseek-ai/DeepSeek-R1

### **追踪 AI 革命**

基准还帮我们追踪 AI 能力的宏观趋势。以 MMLU 为例——它考察 57 个大学水平学科的知识。画出 MMLU 表现随时间的曲线，可以看到去年我们越过了一个迷人的拐点：开源模型已与闭源系统表现持平，某些情况下甚至更好——标志着 AI 版图的重大转变。

来源：https://x.com/maximelabonne/status/1972615048511250647

这种趋同不只是学术谈资，它对组织如何部署 AI、研究者如何获得前沿能力、以及整个 AI 生态如何演化都有深远影响。

### **识别能力与局限**

也许最重要的是，基准帮我们理解的不仅是模型能做什么，还有它们**不能**做什么。它们暴露盲区、指出需要改进的领域、引导研究优先级。这对构建可靠的 AI 系统、为真实世界部署设定合理预期至关重要。一个很好的例子见于近期发布的模型：它们在 OpenAI 的 SimpleQA 这类通用知识基准上反而表现退化。例如，Qwen3 235B 在多数 agentic 和推理基准上超过许多模型——但评估通用知识时严重不及格！这在后来的 Qwen3 Instruct 和 Reasoning 版本中已被修正，SimpleQA 上的表现显著更好。

来源：https://x.com/nathanhabib1011/status/1917230699582751157

## **什么构成一个好的 LLM 基准？五条关键原则**

基准并非生来平等。最有价值的评估框架共享五个关键特征，使其成为模型能力的可靠指标。

### **1. 难度：移动靶挑战**

好的基准必须足够难，才能区分不同模型。这看似显然，但比想象中难做到。想想 MATH——一个竞赛级数学题基准（下图中绿色线）。它刚推出时，最先进的模型只取得个位数准确率——那些题对 AI 系统几乎无解。

快进到今天，同一个基准上模型准确率已超过 90%。曾经的鉴别性测试对现代系统已是常规。这就是"基准饱和"现象：随模型进步，曾经困难的基准变简单，研究者必须不断开发更难的新评估。

上图显示这种趋势正在加速。模型在 MMLU 上达到高水平用了近四年，而 GPQA（博士级问题）这类新基准在一年内就被迅速攻克。这种加速反映了我们正目睹的 AI 发展的空前速度，也凸显拥有越来越难的基准以区分最强模型的重要性。

来源：https://x.com/_jasonwei/status/1889096555254456397

### **2. 多样性：超越单一领域测试**

大语言模型是通用系统，人们从娱乐到工作无所不用，评估因此应反映这种广度。只考数学推理的基准可能漏掉常识推理或创意写作中的关键局限。[MixEval](https://mixeval.github.io/) 框架很好地诠释了这一原则，展示了从 STEM 到社会动态等不同领域如何在评估空间中占据不同区域。

来源：https://arxiv.org/abs/2406.06565

多样性要求作用于两个层面。第一，我们需要覆盖不同能力的多个基准。第二，单个基准内部应包含多样的题型，避免被那些擅长特定模式但缺乏真正理解的模型"刷分"。

### **3. 有用性：把基准与真实世界 AI 用例连接起来**

一个基准可能又难又多样，但如果与现实应用无关，价值有限。最好的基准考察的能力要么对用户直接重要，要么是更复杂任务的基础。

以 GSM8K 为例——它考数学应用题。为什么这重要？第一，它是金融分析等更复杂数量推理任务的基础。第二，它直接帮到用户（学生可以让 ChatGPT 辅导作业）。第三，它提供了更广泛推理能力的可度量代理，帮研究者研究 AI 系统是否真能"思考"问题。

同样，HumanEval 用 LeetCode 风格题目考察编码能力。这个基准的价值在于：编码技能可迁移到构建软件 agent、帮用户准备技术面试，并提供 AI 系统把自然语言翻译成精确指令能力的洞见。

### **4. 可复现性：隐藏的复杂性**

好基准最被忽视的方面之一是可复现性。同一评估应在不同实现和不同研究者之间产生一致结果。不幸的是，这比想象中难。

想想 MMLU——让模型在四选一中做选择。听起来直接，但评估实现其实有多种方式：

- **原始做法**：用 A、B、C、D 选项提示模型，比较每个 token 的概率
- **替代做法**：比较概率时纳入所有可能的 token
- **基于序列的做法**：比较每个选项完整文本描述的概率

当不同机构的研究者分别实现这些做法时，他们得到了不同的结果和模型排名——下图展示了看似微小的 prompt 改动带来的高表现方差。这种不一致令人担忧，因为它意味着关于模型能力的结论可能取决于实现细节，而非真实性能差异。

来源：https://arxiv.org/abs/2310.11324

### **5. 数据污染：隐形的问题**

LLM 评估中最阴险的挑战也许是数据污染——基准题目出现在模型的训练数据里。现代语言模型在海量互联网文本上训练，其中可能包含载有基准题目的学术论文、教科书和网站。

GSM8K 与 GSM1K 的对比完美说明了这个问题。GSM8K 是被广泛使用的数学应用题基准，而 GSM1K 包含保证新颖的同类题目。研究者对比模型在两个基准上的表现时发现，很多模型在 GSM1K 上的分数显著更低——暗示 GSM8K 的高分可能部分反映的是记忆，而非真正的数学推理能力。

来源：https://arxiv.org/abs/2405.00332

MATH 基准的数据污染进一步凸显了这一点。当 SoTA 模型在美国数学奥赛（USAMO 2025）发布后数小时内（彻底排除数据污染的可能）接受评估时，即便当时最好的推理模型也考得惨不忍睹——低于 5%！

来源：https://arxiv.org/abs/2503.21934v1

对开源模型和数据集来说，这个问题尤其尖锐——训练数据与测试数据重叠的可能性更高、也更难检测。

## ‍**LLM 评估方法的类型**

LLM 评估包含若干不同的路径，各有优势和适用场景。

### **多选题与分类基准**

最直接的评估是给模型多选题或分类任务。这类基准打分清晰客观、易于规模化实现。例子包括：

- MMLU（大规模多任务语言理解）：考察通用知识
- HellaSwag：常识推理
- MATH：数学问题求解

这类基准的演化呈现一个有趣的模式。我们常看到基准"家族"——随模型进步，新版本取代旧版本：SWAG 被 HellaSwag 取代，GLUE 被 SuperGLUE 取代，MMLU 被 MMLU-Pro 取代（后者增加答案选项数量让题目更难）。

Together AI 在新的 Evaluations API 中支持运行分类评估，想看代码实现请看我们的 [notebook](https://github.com/togethercomputer/together-cookbook/blob/main/Evals/Classification_Evals.ipynb)！

### **生成与开放式评估**

多选题容易打分，但不能反映我们与语言模型的实际交互方式。实践中我们让模型生成自由形式的响应，因此生成评估对理解真实性能至关重要。例子包括：

- GSM8K（小学数学）：考察逐步数学推理，答案可自动验证
- HumanEval：通过带测试用例的函数补全评估代码生成
- TruthfulQA：度量事实准确性和抗幻觉能力

这些评估用"更接近真实用例"换掉了"容易评估"。多选题或封闭式数学题容易判分，但要评估得出正确答案所需的每一步、或在问题的多种正确解法之间做判断，就难得多。

### **人工评估**

如果想更进一步贴近真实使用情况，可以看人工评估——它能捕捉自动指标常常漏掉的细腻质量因素，代价是规模与一致性上的挑战。

**LM Arena** 是人工评估的标杆。用户与匿名模型交互，投票选出更好的响应。这种众包方式产生反映真实用户在多样问题上的偏好的 Elo 排名。

Arena 的强项在于规模：众包收集数百万场对话、覆盖所有可想象的主题上的偏好。不过其问题往往偏重休闲对话，而非专业领域任务。

**专项人工评估**聚焦特定领域，如编码 [Code Arena、软件工程（SWE-bench）或 HealthBench](https://arxiv.org/abs/2505.08775)。这类评估常有领域专家参与，能评估普通用户可能漏掉的技术正确性和质量因素。

### **LLM-as-a-judge**

用语言模型评估其他语言模型，因其可扩展性和灵活性获得大量关注。这种方式兼具"评估贴近真实使用"的实用性，又用 LLM（而非人类）执行实际评估来保持可扩展性！

**Alpaca Eval 2.0** 用 GPT-4 作为裁判，对照参考答案给模型响应打分，给出不同模型的胜率。**Arena Hard** 从 Chatbot Arena 精选困难 prompt，组成有挑战性的评估集。**多轮基准**评估长对话中的交互能力。

LLM-as-a-judge 的主要优势是评估标准可定制。不同于固定指标，你可以要求裁判评估特定方面，如技术准确性、对初学者的清晰度、行业术语的使用。

然而这种方式也有明显的局限。裁判模型倾向于偏好更长的响应而不论质量，而且常常偏袒自家模型家族的响应（GPT 模型偏好 GPT 的回答，诸如此类）。可靠的输出离不开恰当的校准与偏差修正，一个例子是 LM Arena 加入的 [style control](https://news.lmarena.ai/style-control/)。

## 可靠 LLM 评估的最佳实践

有效的 LLM 评估需要使用多个互补的基准，而不是依赖任何单一指标——不同基准捕捉模型能力的不同侧面。让评估标准对齐你的真实用例：如果你在构建客服聊天机器人，优先考虑帮助性和对话能力，而不是创意写作或数学推理。通过采用新颖测试集并保持适度的怀疑来防范数据污染风险。

对生产系统，实施持续评估框架以随时间监控性能，因为模型会因用户行为和数据的变化而漂移。
