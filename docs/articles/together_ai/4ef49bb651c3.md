过去几周，我们为 Together GPU Clusters 交付了一批改动，直指大规模训练与推理的运维现实：硬件会坏、调度器会漏、团队会长大到超出最初那份单人管理的 kubeconfig 工作流。本文讲述我们交付了什么、为什么这样构建，以及对你今天跑在 Together 上的工作负载意味着什么。

这些改动分为两个主题。第一个是**平台健康**：被动健康检查、自动节点修复和 Slinky 1.0，聚焦捕捉并恢复那些真正击垮任务的失败模式。第二个是**运维掌控**：全新的集群详情视图、外部 OIDC、启动脚本和验收测试可选项，聚焦在你的组织成长过程中提供运行集群所需的可见性、访问和定制钩子。

## **在故障发生时捕捉并修复**

如果你在大型集群上跑过多天的训练任务，你懂这个模式。一块 GPU 从 PCIe 总线上掉下来；一个 Xid 错误让一台节点退出轮转；热降频悄悄压住任务的吞吐，直到 loss 曲线走平你才察觉。

这些是规模下的稳态失败模式。重要的是你多快捕捉它们、多干净地恢复。

我们此前已有**主动健康检查**——用已知良好基线检验硬件的合成测试。主动检查在开通时和空闲节点上有用。被动检查把覆盖面延伸到真实负载运行期间出现的故障。

图：Health checks 标签页展示当前正在运行的所有主动健康检查及历史信息

所以我们构建了**被动健康检查**——像告警一样工作，在集群的每个节点上持续运行，观察真实负载、日志与指标，在劣化发生时即时浮现。当前的覆盖清单包括：GPU 掉出总线、热降频、Xid 错误、故障时 Slurm 节点 drain，以及一套持续扩展的硬件与软件故障信号。

被动检查以接近零的开销观察真实负载。了解更多见[这里](https://docs.together.ai/docs/health-checks)。

图：Repair 标签页展示节点修复建议与集群修复历史

只有检测只是一块仪表盘，所以我们把被动检查与**自动节点修复**配对。当监控系统检测到节点级问题，它会生成一个建议的修复动作，交给运维人员审查。共有四种修复动作，按故障特征自动映射：

- **Reboot：** 就地重启、保留本地数据。瞬态问题的默认选择
- **Reprovision：** 用干净镜像重建节点并清除本地数据
- **Failover：** 把工作负载迁到一块全新裸金属节点并清除本地数据
- **Remove：** 将节点撤出资源池、送修（RMA）

我们相信带人情味的自动化：你的训练 checkpoint 和推理副本太宝贵，不能冒险自动 drain。我们的'人在回路'方式让你保持掌控——系统检测并建议，你批准，Together 处理优雅的恢复。这是智能与安全之间的完美平衡。我们已经在为特定故障模式构建全自动节点修复选项，但目前我们优先保证你的生产负载不被打断。了解更多见[这里](https://docs.together.ai/docs/node-repair)。

结果？你把数小时的支持工单换成了几分钟的产品内工作流。从检测到解决，节点比以往更快地回到池中。

## **Together Slurm-on-K8s 2.0：Slurm on Kubernetes 的未来**

在 Kubernetes 上跑 Slurm 不应该感觉像是在与崩溃的守护进程、僵尸进程和调度器漂移做不懈斗争。我们基于对 OSS 项目 Slinky 的 fork，从零重建了 Slurm-on-Kubernetes 栈，让那些"故障时才扩容"的头疼事成为历史。

升级后的栈为你的集群带来：

**自愈 worker 守护进程：** 瞬态故障不可避免，但它们不该拖垮你的节点。新栈监管 worker，就地自动重启，让长训练运行保持韧性。

**不再有僵尸进程：** 忘掉孤儿子进程堵塞 PID 表、阻塞新作业的日子。新栈自动收割孤儿，确保节点每一次都干净、随时可干活。

**持久的作业记账：** `sacct` 历史过去住在临时存储上，意味着一次 pod 重启就能抹掉你整个记账数据库。我们把记账迁移到持久的 PVC 支撑存储，重启与重调度不再触碰你的数据。计费对账与事后作业分析在集群整个生命周期内保持完好。

**可靠的进程清理：** 过去作业结束时，daemon 化的子进程会溜出 Slurm 的视野继续运行——在两次运行之间扣押 GPU 内存和 /dev/shm 段，有时持续数天直到有人手动清理。新栈在内核级别追踪作业的每个后代，并在作业结束时可靠地全部清理。节点上的下一个作业每一次都从一台干净的机器开始。

**重调度后准确的 GPU 状态：** pod 重调度后，Slurm 认为存在哪些 GPU 的认知过去会与现实漂移——上一次形态留下的陈旧 GPU 标识与真实硬件不匹配，受影响的 GPU 会悄悄从可调度池中消失。新栈在每次节点启动时重建 Slurm 的 GPU 视图，可调度池始终与节点中实际存在的硬件一致。

除可靠性之外，新栈在集群的 Grafana dashboard 中暴露 DCGM 指标，让你开箱即得细粒度的每集群 GPU 利用率可见性。

所有新开通的 Slurm 集群默认运行最新栈。如果你在现有托管 Slurm 集群上，我们可以通过一个维护窗口免费就地为你迁移——联系你的客户团队安排。了解更多见[这里](https://docs.together.ai/docs/slurm)。

## **运维掌控**

可靠性只是画像的一半。当集群跨团队成长，访问、可见性和定制本身就成为运维问题。更多人需要访问，权限各不相同；运维需要不 SSH 进节点就知道集群上发生了什么；工作流需要定制，而不把每次改动变成支持工单。以下是我们为用户适配最关键需求构建的最新功能。

**全新的集群详情视图**

我们围绕运维真正会问集群的三个问题重建了集群概览页：

- 它健康吗？
- 它在被使用吗？
- 最近对它发生了什么？

新视图一眼呈现节点健康：healthy、booting、unhealthy、pending、paused。它还展示所有 GPU 节点的实时使用指标——利用率、内存、网络带宽——并可下钻到 Grafana 深入分析。同一页面还有一个事件时间线，展示集群范围内的节点状态变迁，以及集群的完整配置一处可见：区域、GPU 类型、驱动版本、网络、OS 镜像和计费费率。

三个新标签页并列在概览旁边：

- **Nodes** 提供带利用率数据、健康信号的详细列表和网格视图，以及修复/运行健康检查和 ssh 命令等节点操作。
- **Health checks** 给你集群主动与被动检查事件的历史时间线。
- **Repair** 给你节点修复动作的同样历史视图。两者都为事故复盘的问题存在："上周这个集群上到底发生了什么？"它们取代了过去在我们那里拉一条 Slack 线程的做法。

### **Kubernetes RBAC 的外部 OIDC**

如果你的团队今天访问 Kubernetes API，你多半在共享管理员 kubeconfig。一个运维人员时还管用，超过就崩。团队需要逐用户审计跟踪、逐用户吊销、最小权限访问，以及新成员加入/离职时更干净的路径。

我们加入了 **K8s RBAC 的外部 OIDC 支持**来解决这一点。你现在可以配置集群对着你现有的身份提供商（IdP）认证，包括 Google、Okta、Auth0、Microsoft Entra ID 或其他 OIDC 兼容提供商。每个团队成员以自己的身份运行 kubectl，API server 对着你的 IdP 验证 token，标准 Kubernetes RBAC（ClusterRoleBindings 和 RoleBindings）控制他们能做什么。你获得逐用户的 Kubernetes 访问、通过 IdP 的吊销、绑定到个人的审计跟踪，以及用于最小权限访问的标准 Kubernetes RBAC。

对在任何有意义规模上管理访问的团队，这是重大解锁。管理员 kubeconfig 变成破窗工具；成员进出在你的 IdP 里处理——本就该在那里；而"谁在集群上做了什么"的审计跟踪来自你的安全团队已经信任的系统。

外部 OIDC 必须在集群创建时配置。完整流程见 [OIDC 设置指南](https://docs.together.ai/docs/cluster-oidc)，含 Auth0、Okta、Google 的提供商特定说明。面向 Slurm 与 Kubernetes 集群的 Together OIDC 支持即将到来。

**用于集群定制的启动脚本**

多数生产集群都需要某种不在基础镜像里的设置：内部软件包、暂存空间准备、监控 agent、作业完成时的 Slack 通知。我们看到客户 SSH 进每台节点手动做这些事，或者提支持工单等我们处理。启动脚本把这类设置作为自助能力移入集群配置。

**启动脚本**让你通过 shell 脚本定制 Slurm worker 节点、login 节点和 controller，脚本在特定生命周期事件触发：

- **节点启动时：** 安装软件包、配置工具、运行节点接收工作前的任何准备
- **作业开始时：** 装载数据、准备暂存空间、配置每作业环境
- **作业结束时：** 清理暂存文件和游离进程、发送 Slack 通知、启动下游流水线

脚本在 Together Cloud 控制台配置，可在创建新集群时应用、无需重建。结果是：你原本要提工单或手动做的定制，现在声明一次、自动应用到整个集群。我们甚至校验脚本错误，让你免于之后的静默失败。了解更多定制化的启动脚本设置见[这里](https://docs.together.ai/docs/slurm-startup-scripts)。

**验收测试：更大、更长运行的集群可选择开启**

在 Together AI，我们既服务大规模生产训练/推理负载，也服务短促实验或单节点研究集群。对这些较小或短生命周期的集群，我们默认跳过验证 GPU 健康、网络和存储的验收测试套餐，直接进入可用。对多数集群，更快的可用时间才是更好的默认：少等待、更快见效——尤其考虑到我们对舰队中的空闲节点持续运行健康检查。

对更大的集群或长时间运行的训练任务，算式翻转。在开通时抓到一个坏节点，比在第 47 个 epoch 抓到便宜得多，而验证成本相对集群生命周期很小。这些情况下，我们建议在集群创建时启用验收测试。

这是一个深思熟虑的取舍，我们在 UI 里明说：验收测试默认关闭以加快开通；对多 GPU 训练或长期运行的生产集群，我们建议在创建时启用。

## **运维层面改变了什么**

这些改动合在一起，给运维一条从"出了问题"到"集群重新可用"的更短路径——健康信号、修复动作、访问控制和集群历史都在产品里。

研究员和 ML 工程师获得面向硬件故障的更强可靠性与韧性，以及劣化发生时更清晰的信号。平台团队为访问、修复、定制和事故复盘获得更好的控制面。运维获得持久记账数据、每集群 GPU 利用率指标，以及一个先回答基本问题的集群视图：健康吗、在用吗、最近发生了什么？
