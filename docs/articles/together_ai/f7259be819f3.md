# 金丝雀发布：在生产环境中零停机升级模型

专属推理上的分级流量爬坡、指标门禁与自动回滚。

## 摘要

Rollout（发布）以带门禁的步骤把真实流量从当前模型迁移到新 checkpoint。健康检查总是在流量移动之前运行；在 canary（金丝雀）模式下你还可以添加在每一步之后运行的指标门禁（比如 p95 延迟或错误率）。一旦门禁触发，发布停在当前金丝雀份额上，你可以取消它并反向再跑一遍。下面我们来真的跑一次：一个 Qwen2.5-7B → Qwen3.5-9B 的金丝雀，其门禁在 10% 流量时抓到 137% 的 p95 回归；我们取消并反向执行，期间真实请求持续被服务、零失败。

## 换模型是常规操作

如果你在生产环境运行模型，你早就知道要换入新 checkpoint 或新模型家族的需求：开放模型生态演进很快，候选模型通常在评估中表现出色，或承诺更好的吞吐。你想让它服务所有用户且不出岔子，还在它让人失望时留一条退路。常见的选项强迫你做取舍：

- **硬切换：** 把 endpoint 指向新模型，所有用户一次性暴露在新模型下。如果 p95 翻倍，你会从监控大盘得知——更糟的是从客户那里得知——然后在压力下回滚到一个还在冷启动的旧模型。
- **自制的分阶段切换：** 第二个部署加一个不断微调流量百分比的脚本，你盯着 Grafana，同时记得在将流量切回之前先把旧部署扩回容量。

这两种方案都把"人"当作安全机制。Rollout 把这个机制移进平台：你描述源、目标、步骤，以及"健康"的定义，平台在每个阶段照此执行。

## Rollout 如何工作

一次 rollout 在同一 endpoint 的两个 deployment 之间迁移流量：**source（源）**（今天在服务）和 **target（目标）**（明天你想让它服务）。你从三种策略中选一种：

- **Canary（金丝雀）：** 流量按你定义的分级百分比移动（如 10% → 50% → 100%；默认阶梯是 5% → 25% → 50% → 100%），步骤之间设有等待期和可选的指标检查。
- **Blue-green（蓝绿）：** 一次带门禁的 0% → 100% 切换。可以把它理解为单步金丝雀。
- **Rolling（滚动）：** 就地逐副本替换，保持总容量不变。适合容量受限的场景，尤其是不需要流量爬坡的同模型配置变更。

这个顺序是我们深思熟虑的选择；每一条都防止一类事故：

- **目标先扩容，*然后*才有流量移动。** 新部署没有容量就没有可重定向的请求：发布先停在那里。
- **健康门禁先运行，流量才切换。** 流量只会到达引擎已加载并已应答的副本，而不仅仅是"已启动"的副本。
- **传播等待位于切换与排空之间。** 在任何源容量被移除之前，先让路由缓存收敛。
- **源在流量移动*之后*才排空。** 上行时容量领先于流量；下行时流量领先于容量。
- **等待期和指标门禁在步骤被记录为完成之前。** 发生回归的步骤永远不会被标记为通过。

通过 API 或控制台创建的 rollout 处于 `PENDING` 状态，在你显式启动之前什么都不做（CLI 的 `rollout` 命令一步完成创建和启动）。这种两步创建/启动是刻意设计的：你可以先创建 rollout、审查它（或让队友审查），在你真正盯着的时候再启动。

上图中有两个状态值得说明：

- **`PAUSED`** 意味着*你*按下了暂停。发布原样停在当前位置，从同一步骤恢复。
- **`SYSTEM_PAUSED`** 意味着*平台*发现了问题——例如指标门禁失败、容量缺口或指标缺失——停下来等待人工批准。它会暂停、通知你并等待；取消永远是*你的*决定。

不存在让流量悬而未决的 `FAILED` 终态：一次 rollout 要么 `COMPLETED`（目标接管服务），要么 `CANCELED`（切分冻结在当前位置，你用反向 rollout 回去）。

### 一个步骤的解剖

以下拆解单个金丝雀步骤中发生的事，数据来自本文末尾的真实运行（Qwen2.5-7B → Qwen3.5-9B，各占一块 H100）。

传播等待的作用，是防止过期全局路由缓存把请求发往正在缩容的源。等待期被设定为指标窗口加上数据摄取延迟。冷启动主导第一步；后续步骤只是向一个已经在服务、已经发热的目标添加副本。

## 三种策略速览

三种策略都跑在同一个引擎和同一套健康门禁上；区别在于流量如何移动、重叠期间额外容量花费多少，以及是否存在供指标门禁使用的等待窗口。

|  | Canary | Blue-green | Rolling |
| --- | --- | --- | --- |
| 流量模式 | 按你选择的份额分步推进（默认 5% → 25% → 50% → 100%），每步保持一个等待窗口 | 一次 0% → 100% 切换，目标健康后执行 | 逐副本替换，流量跟随副本比例 |
| 额外容量 | 接近源规模；目标先扩大一步，源再排空对应份额 | 在源排空前两个部署都保持全量 | 每一步维持源的副本数；步骤中间多一个副本 |
| 典型时长 | 一次冷启动加每步一个等待期（带指标门禁时每步至少 390 秒） | 一次冷启动加 30 秒传播；几分钟 | 每个副本一次冷启动；大部署上最慢 |
| 指标门禁 | 有，每一步之后 | 无（没有等待窗口） | 无 |
| 如何回退 | 取消先冻结当前份额，然后反向执行 rollout | 反向执行 rollout；`--final-source-replicas 1` 让旧模型保持温热以便瞬时返回 | 反向执行 rollout |
| 适用场景 | 在接管 100% 之前用真实流量做测量 | 你能短暂负担双倍容量时最快的切换 | 在恒定 GPU 占用下做同模型引擎或配置变更 |

## 创建一次 rollout

下面是一个三步金丝雀：从服务当前模型的部署到服务候选模型的部署，带一个延迟回归门禁。CLI 以 `tg` 的形式随 `together` Python 包（2.34.0 或更新）提供。你传入 **target** 部署；当恰好只有一个部署在接收流量时源会被自动推断，否则显式传 `--source`：

```
    
# 1. 一条命令创建并启动 rollout。
#    间隔和窗口的单位是带 "s" 后缀的秒数（"600s"，而不是 "10m"）。
tg beta endpoints rollout $TARGET_DEPLOYMENT_ID \
  --source $SOURCE_DEPLOYMENT_ID \
  --canary \
  --steps 10,50,100 \
  --interval 600s \
  --metric router_latency --metric-stat p95 \
  --metric-max-regression 10 --metric-direction higher-is-worse \
  --metric-window 300s

# 2. 观察进展：传入 "Active Rollout" 下打印的 rollout ID，
#    或传入 endpoint ID 查看端点概览
tg beta endpoints get $ROLLOUT_ID
tg beta endpoints get $ENDPOINT_ID

# 3. 控制它：传入 endpoint ID 加恰好一个控制标志
tg beta endpoints rollout $ENDPOINT_ID --pause --reason "holding for review"
tg beta endpoints rollout $ENDPOINT_ID --resume
tg beta endpoints rollout $ENDPOINT_ID --promote
tg beta endpoints rollout $ENDPOINT_ID --cancel --reason "latency regression on target"
    
```

rollout 完成时源排空至零副本并停止（`--final-source-replicas` 默认为 0），目标以源的副本数作为其下限着陆（`--final-target-replicas`）。CLI 为每次 rollout 挂载一个指标门禁；要配多条规则请使用控制台或 API。

同样通过 REST API 完成——创建与启动是分开的调用，且一次 rollout 可以携带多条指标规则：

```
    
# 1. 创建 rollout。返回时状态为 PENDING；保存其 "id"（rol_...）为 $ROLLOUT_ID。
curl -s -X POST \
  "https://api.together.ai/v2/projects/$PROJECT_ID/endpoints/$ENDPOINT_ID/rollouts" \
  -H "Authorization: Bearer $TOGETHER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "sourceDeploymentId": "'$SOURCE_DEPLOYMENT_ID'",
    "targetDeploymentId": "'$TARGET_DEPLOYMENT_ID'",
    "canary": {
      "steps": [{"traffic": 10}, {"traffic": 50}, {"traffic": 100}],
      "stepInterval": "600s"
    },
    "metrics": [{
      "name": "router_latency",
      "stat": "METRIC_STAT_TYPE_PERCENTILE",
      "percentile": 95,
      "regressionCheck": {
        "direction": "REGRESSION_DIRECTION_HIGHER_IS_WORSE",
        "maxRegressionPercent": 10
      },
      "window": "300s"
    }]
  }'

# 2. 启动它：   POST .../rollouts/$ROLLOUT_ID/start   -d '{}'
# 3. 观察它：   GET  .../rollouts/$ROLLOUT_ID
    
```

API 在几处很严格：`percentile` 是整数（95，不是 "p95"）；枚举值带完整前缀（`METRIC_STAT_TYPE_*`、`REGRESSION_DIRECTION_*`、`THRESHOLD_OPERATOR_*`）；时长是 protobuf 字符串如 `"600s"`；目录之外的指标名会被 400 拒绝并列出支持的名称。排空源是默认行为，因此无需为此传任何参数。

回归检查可以这样理解：*在每个门禁处，把 target 最近 5 分钟的 p95 router 延迟（在路由器处度量的单请求时长，单位毫秒）与 source 的比较。如果 target 差超过 10%，就不要推进。*

### Python SDK

用 `together` 包（2.34.0 或更新）从 Python 发起同样的 rollout。这里字段名用 snake_case，网络上（wire）是 camelCase；SDK 负责转换。

```
    
from together import Together

client = Together()  # 读取 TOGETHER_API_KEY

rollout = client.beta.endpoints.rollouts.create(
    endpoint_id=ENDPOINT_ID,
    project_id=PROJECT_ID,
    source_deployment_id=SOURCE_DEPLOYMENT_ID,
    target_deployment_id=TARGET_DEPLOYMENT_ID,
    canary={"steps": [{"traffic": 10}, {"traffic": 50}, {"traffic": 100}], "step_interval": "600s"},
    metrics=[{
        "name": "router_latency", "stat": "METRIC_STAT_TYPE_PERCENTILE", "percentile": 95,
        "regression_check": {"direction": "REGRESSION_DIRECTION_HIGHER_IS_WORSE", "max_regression_percent": 10},
        "window": "300s",
    }],
)  # 状态：PENDING

client.beta.endpoints.rollouts.start(rollout.id, project_id=PROJECT_ID, endpoint_id=ENDPOINT_ID)

# 之后：.retrieve / .pause / .resume / .promote / .cancel 接受同样的 (id, project_id, endpoint_id)
    
```

## 控制一次 rollout

每次 rollout 都接受同样四个控制。一个 endpoint 最多只有一个活跃 rollout，所以 CLI 接收 endpoint ID，你很少需要 rollout ID。每个控制指令一经接受即返回；轮询 `tg beta endpoints get`（或 GET endpoint）直到 rollout 达到你期望的状态。rollout 活跃期间（包括暂停中），endpoint 的流量切分被锁定，其源和目标都不能被停止或删除。

### 暂停

Rollout 进入 `PAUSING`，让在途的步骤活动完成，然后在当前流量切分和副本数上以 `PAUSED` 保持。两个部署继续服务。暂停可以持续数天；平台永远不会自动恢复一个由操作员发起的暂停。

CLI

```
tg beta endpoints rollout $ENDPOINT_ID --pause --reason "holding for review"
```

REST

```
POST …/rollouts/$ROLLOUT_ID/pause
{"reason": "holding for review"}
```

### 恢复

从同一步骤继续，`PAUSED` 和 `SYSTEM_PAUSED` 皆适用。如果是门禁触发导致的暂停，门禁会基于新数据重新评估；该步骤不会被跳过。

CLI

```
tg beta endpoints rollout $ENDPOINT_ID --resume
```

REST

```
POST …/rollouts/$ROLLOUT_ID/resume
{}
```

### 晋升

跳过剩余金丝雀步骤，完整执行最后的 100% 步骤：目标扩到着陆规模、流量切换、传播等待和浸泡期（soak）照常运行，然后源排空。被跳过的步骤记录为 `SKIPPED`。这不是瞬时的：在一次步长间隔 10 分钟的测试运行中，在第 0 步执行 promote 仍然完整经历了最后一步的浸泡期。

CLI

```
tg beta endpoints rollout $ENDPOINT_ID --promote
```

REST

```
POST …/rollouts/$ROLLOUT_ID/promote
{}
```

### 取消

把当前流量切分冻结成 endpoint 的常驻权重，rollout 以 `CANCELED` 结束。什么都不缩容；两个部署按冻结的份额继续服务，直到你编辑切分或执行反向 rollout。在 0% 时被取消的目标会保持运行但没有流量；如果不再需要，把它缩到零或删除。

CLI

```
tg beta endpoints rollout $ENDPOINT_ID --cancel --reason "latency regression on target"
```

REST

```
POST …/rollouts/$ROLLOUT_ID/cancel
{"reason": "latency regression on target"}
```

### 反向 rollout

没有 rollback（回滚）这个动词。要把流量移回，在取消之后或完成之后，创建一个源和目标互换的新 rollout，然后启动它。任何策略都适用，门禁同样生效。取消之后，默认金丝雀阶梯会跳过新目标已经走过的步骤，默认的收尾副本数是两者之和。

CLI

```
tg beta endpoints rollout $OLD_SOURCE_ID --source $OLD_TARGET_ID --canary
```

REST

```
POST …/rollouts        (两个 ID 互换)
POST …/rollouts/$NEW_ROLLOUT_ID/start
```

对已结束 rollout（`COMPLETED` 或 `CANCELED`）的控制请求会被拒绝。用 `tg beta endpoints rm $ROLLOUT_ID` 从历史中删除已结束或从未启动的 rollout；删除记录不会改变它留下的流量切分。

## 底层机制：配置门禁

### 指标门禁

指标门禁是金丝雀专属能力：blue-green 和 rolling 仍会运行健康门禁，但分级指标对比依赖金丝雀的步骤结构才有意义。门禁在一个路由器侧三项指标构成的**封闭目录**上评估，源与目标的度量方式完全一致（任何其他指标名在创建时即被拒绝）：

- `router_error_rate`：路由器 5xx 响应占全部推理响应的比例，0-1 的比值（0.02 即 2%）
- `router_latency`：在路由器处度量的单请求时长，单位毫秒。它是双峰分布（中位数尝试常常是快速拒绝），所以要门禁在 `p95` 或更高，而不是均值
- `inflight_requests`：每就绪副本的并发请求数，在窗口内取平均（按每副本规模设阈值，而非全集群）

每条规则使用两种检查之一：

- **`regressionCheck`**（*相对*）："target 不得比 source 差超过 N%。"这是延迟的正确默认选择，因为它自校准：你不需要知道自己的绝对 p95，只需要新模型不该让它变差。设置 `direction` 让平台知道哪个方向更好/更差。
- **`thresholdCheck`**（*绝对*）："target 必须满足 `operator, value`"（例如错误率 `< 0.01`）。当你有硬性 SLO，或者源本身可能不健康、相对比较会变成"按曲线打分"时，用这个。

两个配方覆盖多数服务：

```
    
// 延迟敏感型服务：不接受任何明显更慢的东西
{
  "name": "router_latency",
  "stat": "METRIC_STAT_TYPE_PERCENTILE",
  "percentile": 95,
  "regressionCheck": {
    "direction": "REGRESSION_DIRECTION_HIGHER_IS_WORSE",
    "maxRegressionPercent": 10
  },
  "window": "300s"
},
// 讲究错误预算的团队：无论源表现如何，设硬性上限
{
  "name": "router_error_rate",
  "stat": "METRIC_STAT_TYPE_AVG",
  "thresholdCheck": {
    "operator": "THRESHOLD_OPERATOR_LT",
    "value": 0.01
  },
  "window": "300s"
}
    
```

### 时间窗口

三个时长会相互影响，务必同时考虑：

- **`window`**（默认 5m）：门禁比较指标时向回看多远。
- **`stepInterval`**（默认 3m）：每个步骤在当前流量水平等待多久后运行门禁。
- **指标摄取延迟**（约 90s）：从请求被服务到其数据点可查询之间的时间。

你必须等待至少 **`window + 摄取延迟`** 的时长，让门禁的整个回看窗口完全落在当前步骤的稳态内。如果等待时间短于窗口，门禁就会在比较部分描述*上一个*流量切分的指标。平台替你强制这一点：如果你请求的等待期对你的窗口来说太短，它会自动加大。不过带着这个规则去设计仍然更好：5 分钟窗口需要 6.5 分钟等待期。在默认 5m 窗口下，平台会把默认的 3m 间隔拉长为 390 秒（6 分 30 秒）；如果你自己设置 `stepInterval`，请让它至少为 `window + 90s`。

### 回归发生时会怎样

默认情况下，触发的门禁会把 rollout 置入 `SYSTEM_PAUSED`，意味着系统**暂停待审**。发布停在当前切分上（影响范围保持在你设的金丝雀百分比），由你决定：恢复（门禁重新评估）、晋升，或取消。

不存在自动中止：一次被确认的回归总会把发布交给一个人类停下来审查，因为把流量移回去本身就是一个应该有人盯着的变更。可恢复的原因则不同——容量缺口或指标管道缺口——平台会每 15 分钟重试一次，最长 3 小时，之后仍留给人类一个暂停态。平台还防误报：在因回归暂停之前，系统会在约 90 秒内重新查询数次，确保看到的不是摄取延迟或瞬时毛刺；拿不到可信数据的门禁会以 `METRICS_UNAVAILABLE` 暂停，而不是算作回归。

## 平台保证什么

三种策略都跑同一个步骤引擎，所以以下各条对 canary、blue-green、rolling 同样成立。

**1. 容量永远不会被向下取整。** 目标副本向上取整、源排空向下取整，所以同规模替换的副本数绝不会少于开始时。Rolling 在步骤中间加一个副本；blue-green 会短暂地让两个部署全量运行。你的自动扩缩容在计划之外增加的副本会被保留。

**2. 流量永远不会落在未就绪的容量上。** 每一步都按同一顺序执行：扩展目标、检查健康、切换流量、等 30 秒让路由收敛、排空源、等待、评估门禁、记录步骤。在等待期间发生回归的步骤永远不会被记录为通过。

**3. 每一侧始终拥有其份额所需副本数。** 只有当目标有足够的就绪副本承接新份额时流量才移动；源的排空永远不会低于其剩余份额。如果一个副本挂掉、当前切分无法再被服务，发布会保持在它能维持的最大切分上并以 `UNDER_SERVED` 暂停。

**4. Rollout 抬高下限，不与你的自动扩缩容打架。** 每一步只写每个部署的最小副本数，别无其他——有一个例外：目标的最大值会被提升一次，以便它能承接整个 endpoint，并保持提升。排空期间，源的最大值随其份额收缩。如果把最大值降到步骤所需以下，发布会以 `POLICY_INFEASIBLE` 暂停，而不是覆盖你的设置。

**5. 门禁总会给出裁决。** 回归检查在目标处于你设定的百分比预算内（相对源）时通过。没有源数据则通过；higher-is-worse 指标上源为零而目标非零则失败；其他情况的零源通过。阈值检查忽略源，直接拿目标与你的值比较。

**6. 门禁只读当前步骤的流量，且只读足够的量。** 等待期至少是指标窗口加约 90 秒摄取延迟，所以 300 秒窗口意味着 390 秒等待。p95 需要窗口内至少 20 个请求，p99 需要 100 个；不足时发布以 `METRICS_UNAVAILABLE` 暂停。错误率和 inflight 请求数只需要一个。

## 边缘情况

**1. 如果没有 GPU 容量给目标怎么办？**

Rollout 会在动手之前为*整个*旅程预先检查可行性，并在每次扩容时再查一次。容量不足会把发布以 `CAPACITY_EXHAUSTED` 类别置入 `SYSTEM_PAUSED`。此时什么都没移动，你的源毫发无损。恢复会重新检查容量，若已释放则继续。容量问题通常是暂时的，所以暂停优于失败。

**2. 我可以无限期暂停吗？**

可以。暂停不是一个挂起的连接，而是一个一等状态。Rollout 的设计就是能扛过多天的暂停，并恰好从离开的位置恢复。

当平台暂停一次 rollout 时，`status.condition` 会携带一个类型化的**失败类别**加一条人类可读的 `message`。包括：

| 类别 | 含义 | 你应该 |
| --- | --- | --- |
| `METRIC_REGRESSION` | 门禁基于真实数据触发 | 检查该步骤的指标读数；若问题在目标，取消并反向执行 rollout；若原因是外部干扰，恢复 |
| `METRICS_UNAVAILABLE` | 门禁拿不到可信数据 | 检查指标名/窗口；恢复时重新评估 |
| `CAPACITY_EXHAUSTED` | 下一步骤 GPU 不足 | 等待/腾出容量，然后恢复 |
| `UNDER_SERVED` | 一侧的就绪容量低于当前切分所需 | 恢复容量（自动重试）；若暂停持续则手动恢复 |
| `POLICY_INFEASIBLE` | 自动扩缩容限制容纳不下计划 | 提高目标的最大副本数，然后恢复 |

文档列出了其余类别及应对方法：[Troubleshooting rollouts](https://docs.together.ai/docs/dedicated-endpoints/rollouts#troubleshooting)。

## 真实 rollout 演示

以上所有东西看一次实际运行更容易信任，所以这里是一次在当前平台上（2026 年 9 月）的真实运行。我们把一个 live endpoint 从 **Qwen2.5-7B-Instruct** 升级到 **Qwen3.5-9B**，各用一块 H100，期间稳定的 5 RPS 聊天补全流量始终流经该 endpoint，每个响应码都被记录。更新的模型是我们想要的；rollout 回答的问题是它是否装得下旧模型立下的延迟预算。我们给了它 25% 的 p95 预算。

**设置。** 7B 已在服务。我们把 9B 作为第二个部署加到同一 endpoint 上，零流量零副本；rollout 需要时会自动启动它。

```
    
# $MODEL_ID 是 Qwen/Qwen3.5-9B-FP8。当模型只有一种 serving config 时 --config 可以省略。
tg beta endpoints deploy $MODEL_ID --endpoint $ENDPOINT_ID --config $CONFIG_ID \
  --min-replicas 0 --max-replicas 0 --traffic-weight 0
    
```

**启动。** 一条命令创建并启动金丝雀：10% → 50% → 100%，带一个在每步之后于 5 分钟窗口内比较目标与源 p95 router 延迟的门禁。

```
    
tg beta endpoints rollout $TARGET_DEPLOYMENT_ID --source $SOURCE_DEPLOYMENT_ID \
  --canary --steps 10,50,100 \
  --metric router_latency --metric-stat p95 \
  --metric-max-regression 25 --metric-direction higher-is-worse \
  --metric-window 300s      
    
```

**按时间线发生了什么**（自 rollout 开始计时）：

- **+3:57** 9B 完成冷启动、通过健康检查，10% 的请求开始落到它上。发布等待 30 秒让路由收敛，排空 7B 对应份额，然后浸泡。我们保留了步骤间隔的默认值，所以平台把它拉长到 390 秒以覆盖 300 秒窗口加摄取延迟。
- **+11:00** 门禁评估并触发。9B 的 p95 router 延迟为 **1,740 ms**，7B 为 **734 ms**，相对 25% 预算是 **137% 的回归**。发布进入 `SYSTEM_PAUSED`，10% 流量仍在目标上、什么都没拆除。这就是 `tg beta endpoints get $ROLLOUT_ID --json` 返回的内容（值单位毫秒）：

```

"currentTrafficPercent": 10,
"pauseInfo": {
  "reason": "metrics-regression: regression check router_latency failed: target=1740.38 vs source=734.20, regression=137.05% exceeds max=25.00% (direction=REGRESSION_DIRECTION_HIGHER_IS_WORSE)",
  "pausedAt": "2026-09-16T20:50:45Z"
},
"status": {
  "condition": {
    "category": "ROLLOUT_FAILURE_CATEGORY_METRIC_REGRESSION",
    "atStep": 0,
    "metrics": [
	    { 
		    "name": "router_latency", 
		    "stat": "METRIC_STAT_TYPE_PERCENTILE", 
		    "percentile": 95,
		    "check": "METRIC_CHECK_TYPE_REGRESSION",
		    "sourceValue": 734.20, 
		    "targetValue": 1740.38, 
		    "maxRegressionPercent": 25,
		    "direction": "REGRESSION_DIRECTION_HIGHER_IS_WORSE", 
		    "verdict": "METRIC_VERDICT_BREACHED" 
	    }
```

**做决定。** 回归是真实的，不是毛刺：9B 是推理模型，在相同 max_tokens 下每个请求生成更多内容。这是产品决策而不是该"恢复过去"的东西，所以我们取消并回去。

```
    
tg beta endpoints rollout $ENDPOINT_ID --cancel --reason "p95 latency regression on the Qwen3.5 target"
# 切分冻结在 90% / 10%；两个部署继续服务

tg beta endpoints rollout $SOURCE_DEPLOYMENT_ID --source $TARGET_DEPLOYMENT_ID --blue-green
# 7B 收回 100%，9B 排空到零
    
```

- **+11:09** `CANCELED`。切分在命令后 0.2 秒内冻结为 90/10。
- **+17:00** 反向 rollout 完成，距其开始 5 分 49 秒：100% 流量回到 7B，9B 排空到零并停止。大部分时间花在第二次 7B 副本冷启动上，因为取消之后默认收尾副本数是两者之和。

**整个探测程序的裁决**——覆盖切换、暂停、取消和反向的全部过程：**6,800 个请求，0 个非 200 响应**。

**审计线索。** 上面每一步都在 endpoint 的事件流里，可按 rollout ID 过滤：

```

```

## 自己动手试试！

**1. 一个 endpoint 上放两个部署。** 保留当前部署作为源，把候选作为零流量目标添加进来。`pip install -U together`（2.34.0 或更新）就带上 `tg` CLI：

```
    
# 一个停止、零流量的目标；rollout 扩容时会自动重启它。
# 加 --config cr_... 可锁定特定配置版本。
tg beta endpoints deploy $MODEL --endpoint $ENDPOINT_ID \
  --min-replicas 0 --max-replicas 0 --traffic-weight 0
    
```

**2. 创建并启动一个金丝雀**，用默认阶梯（5% → 25% → 50% → 100%）和一个 router_latency 回归门禁：

```
    
tg beta endpoints rollout $TARGET_DEPLOYMENT_ID --canary \
  --metric router_latency --metric-stat p95 \
  --metric-max-regression 10 --metric-direction higher-is-worse
    
```

**3. 观察它**：用 `tg beta endpoints get $ENDPOINT_ID`（或控制台中 endpoint 的 Rollouts 标签页）看它逐步推进。用 `tg beta endpoints rollout $ENDPOINT_ID --pause | --promote | --cancel` 暂停、晋升或取消。

整个过程中，endpoint URL 和你的客户端保持不变；只有其背后的模型在移动。
