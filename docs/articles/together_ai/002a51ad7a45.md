## 摘要

推测解码在生产环境中会"过期"——草稿模型会漂移，而离线重训练往往跟不上节奏。

Aurora 解决了这个问题。它是一个基于 RL 的开源框架，直接从真实推理 trace 中学习，在不中断服务的前提下持续更新推测器。

关键结果：

→ 在流量域不断切换中实现实时适应
→ 在训练充分的静态推测器之上再提速 1.25 倍

核心发现：从零开始的在线训练可以胜过精心预训练的静态基线。

在生产环境运行大语言模型，性能与成本是永恒的权衡。推测解码是标准杠杆：原理上它加速推理，实践中却常常不达预期——草稿模型会过期、接受率会漂移、离线重训练太慢也太贵，赶不上真实流量。如果你的系统能持续地、就地地、从它正在服务的请求本身学习，会怎样？

去年，我们发布了 [ATLAS](https://www.together.ai/blog/adaptive-learning-speculator-system-atlas)——我们迈向自适应推测器的第一步。那项工作打下了基础，但目标始终是一个完全自主、把服务与训练闭环连接起来的系统。

今天，我们发布 **Aurora**：一个基于 RL 的开源框架，从真实推理 trace 中学习并异步更新推测器——把推测解码从一次性的静态配置变成动态、自我改进的飞轮。这个统一设计解锁了标准流水线难以实现的能力，包括：(1) 直接缓解分布不匹配，相对强大的离线基线取得 1.25 倍提升；(2) 省去大规模 activation 采集流水线，降低基础设施成本；(3) 算法无关的框架，兼容未来的推测器设计；(4) 支持多样化、异构的用户需求。

在各项实验中，Aurora 在广泛使用的模型（如 Qwen3 和 Llama3）上，相对训练充分但静态的推测器额外取得 1.25 倍加速。

复现论文结果的代码已[开源](https://github.com/togethercomputer/aurora)，我们欢迎社区贡献。

Aurora 能快速适应切换中的领域。

## 1. 为什么"先训练后服务"的标准流水线会失效

离线推测训练在组织上很方便，但在生产中带来若干实际问题，限制了它的有效性。传统流水线是一条单行道——导致模型过期，并与真实性能脱节。

静态推测器通常随流量模式变化而退化。

传统推测解码遵循线性、静态的流程，随时间退化。Aurora 引入了循环、持续自适应的方式。

**验证器在移动，起草者却落后。**生产中的目标模型会变化——出于质量、安全、成本或硬件迁移的原因。推测器往往更新得慢得多，于是变得过期，推测性能随时间退化。

**离线蒸馏流水线代价高昂。**用于起草者训练的 activation 采集与回放流水线，在规模下的存储和运维成本可能极高。在生产规模下，存储足迹可以达到 PB 级，在内存、带宽和运维复杂度上代价高昂。Aurora 直接从真实服务 trace 中学习，大幅减轻这一负担。

**接受率不等于真实加速。**离线训练可以在实验室环境优化接受率，但生产加速取决于实际服务栈：kernel、数值精度（FP8/FP4）、批处理、调度以及硬件行为。离线上最好的草稿模型未必是线上最好的模型。实践中，多数团队训练多个草稿模型但最终只选一个——Aurora 因为在线运行，可以做直接的加速对比。

这些差距表明：推测解码不应只被当作一个建模问题（"训练一个更好的起草者"），而应被视为一个学习与服务联合的问题。

## 2. 核心思想：由 RL 驱动的"服务即训练"飞轮

Aurora 把推测解码变成一个服务到训练的飞轮。它不把推测器当作静态产物，而是从每一个它服务的请求中持续学习。

Aurora 提供由 RL 驱动的服务-训练飞轮。

系统围绕两个解耦的组件构建。推理服务器运行一个推测解码引擎（基于 SGLang 或 vLLM），配有目标模型和草稿模型。对每个请求，草稿模型提出一串 token，随后由目标模型并行验证。被接受和被拒绝 token 的结果——连同用于 EAGLE 式训练的隐藏状态——被流式写入一个分布式数据缓冲区。训练服务器异步运行：从缓冲区拉取批量的训练数据，在草稿模型的一个副本上执行梯度更新，并周期性地把改进后的权重热切换回推理服务器，不中断服务。

这个设计围绕两个生产现实构建。第一，服务效率才是真实目标——SLO 约束下的延迟、吞吐和每 token 成本。第二，同步必须是懒惰且无干扰的——频繁的权重推送会引发缓存失效和延迟抖动。为了让这个设计可靠工作，我们把在线推测训练重新表述为一个异步强化学习（RL）问题。

这不仅是理论上的便利——它让训练信号直接与真实部署效用对齐，而不仅是离线模仿质量。推测解码天然映射到强化学习：

| 推测解码 |  | RL 映射 |
| --- | --- | --- |
| 草稿模型 | → | 策略（π） |
| 目标验证器 | → | 环境 |
| 被接受的 token | → | 正奖励 |
| 被拒绝的提案 | → | 负向 / 反事实反馈 |

在这个框架下，最大化回报直接映射到最大化接受长度——而接受长度直接映射到解码加速。Aurora 一个微妙而强大的设计是：它不只从被接受的 token 中学习。接受损失（模仿）对被接受的 token 使用交叉熵，鼓励草稿复现验证器认可的延续；拒绝损失（Discard Sampling）用被拒绝的分支作为反事实监督，教会草稿什么不该提。

为了高效处理推测解码结果复杂的分支结构，我们采用了专门的 Tree Attention 机制。通过构造尊重推测树因果结构的自定义 attention mask，我们可以在单次批量的前向和反向传播中处理所有被接受和被拒绝的分支。

## 3. 对分布漂移的适应

为测试 Aurora 的鲁棒性，我们用一条跨五个领域的 40,000 条 prompt 流量模拟真实服务：数学推理、text-to-SQL、代码生成、金融、通用对话。这一构成反映了真实性部署场景——服务流量呈现异构且不断移动的分布。我们评估了两种流量模式：(i) 有序流，按领域分组请求以制造突变式分布漂移；(ii) 混合流，随机打乱 prompt 以近似平稳流量。

当请求按领域分组以制造突变的分布变化时，Aurora 持续适应。系统在每次漂移后约 10,000 个请求内恢复接受长度，展示了鲁棒的在线适应能力。

流量切换时，Aurora 在 Qwen3-8B 上超越了训练充分的静态推测器。

从训练充分的推测器出发，Aurora 通过持续适应在静态基线之上额外取得 1.25 倍加速。这表明 Aurora 的收益是在既有离线训练投入之上叠加放大的。

混合流量的结果尤其引人注目：从零开始的在线训练可以超过精心预训练的推测器的表现。接受长度达到 3.08（超过静态基线的 2.63 和"预训练再微调"基线的 2.99），吞吐稳定在 302.3 tokens/s。这从根本上挑战了"推测解码需要大量离线预训练"的传统认知。

## 4. 结论

Aurora 不只是又一个推测解码算法，它是一次系统层面的范式转变：把推测解码从静态、离线的任务变成动态、在线的学习过程。

这一转变解锁了实时效用反馈、领域漂移下的适应、相对大规模离线蒸馏流水线更低的基础设施成本，以及一个兼容未来推测器算法的系统层。这就是为什么对推测解码而言，正确的抽象不再只是孤立地"训练更好的草稿模型"，而是一个统一的训练-服务闭环。
