## 摘要

Dedicated Container Inference 让团队能够部署自定义生成式媒体模型——如视频生成、avatar 合成、图像处理——并直接使用他们无需自己搭建的生产级编排。你带上 Docker 容器，Together 负责自动扩缩容、排队、流量隔离和监控。已经在 Together GPU Cloud 上训练的团队，从训练到生产零制品传输。Creatify 和 Hedra 等客户获得了 1.4–2.6 倍的推理加速，这既来自平台架构，也来自 Together 研究团队的贴身优化。

自创立起，Together 就一直支撑大规模 LLM 推理。我们深刻理解这个领域，并为无状态请求、基于 token 的延迟和高度优化的服务路径打造了相应产品。

Dedicated Container Inference 为另一类工作负载而建。

过去一年，我们与把自定义非 LLM 模型部署到生产的团队密切合作。这些模型远不只是"文本进、文本出"的 API：视频生成流水线、avatar 合成、大规模图像处理，以及带有真实商业约束的自定义音频/媒体模型。

这些团队始终需要的不只是 GPU 或容器。他们需要在不自建作业编排层的情况下，让自定义推理代码在生产中运行。自动扩缩容、排队、流量隔离、重试、监控都很重要，但没人愿意在公司内部重新实现那套栈。

Dedicated Container Inference 就是我们对这个缺口的回答——把面向自定义模型的生产级编排带进 AI Native Cloud。

你带来容器和推理逻辑，我们负责部署、自动扩缩容、排队和作业级监控，专为 GPU 密集型工作负载打造。

## 有什么不同？

多数推理平台围绕单一抽象做优化：要么是无状态 endpoint，要么是大批处理作业。当你同时有实时与批量流量、客户分层和突发需求时，这就不够用了。

Dedicated Container Inference 围绕你的容器的作业编排构建，带来：

- 多条独立队列，而非单一 FIFO 流
- 策略驱动的流量控制，而非逐请求优先级
- 批量、实时与不可信流量之间的隔离
- 突发期间的可预测行为，无需过度供给

而差别不止在推理时。Together 是端到端的"训练到推理"平台。在 Together GPU Cloud 上训练的模型可以直接作为 Dedicated Container 部署，无需任何制品传输或额外工作。

对构建自定义模型的团队，这个紧闭环降低了运维开销，让从训练到生产的迁移更容易，且不引入新的失败模式。

## 架构速览

Dedicated Container Inference 构建在一个以容器为基础的部署框架上，作业（job）和队列（queue）是一等概念。我们不把推理硬塞进单一请求-响应形态，而是把你的容器当作执行单元，围绕它管理一切。

图 1：Dedicated Container Inference 架构

### 总体流程：

**你把模型打包成 Docker 容器**
容器包含你的运行时、依赖和推理代码。如何运行推理、使用什么库，由你决定。

**我们把该容器部署并管理在 GPU 基础设施上**
Together 负责开通 GPU、启动副本、处理网络、健康检查和监控。你不需要直接管理集群或节点。对于需要多 GPU 的大模型，我们内建通过 torchrun 的分布式推理支持。

**模型权重用 Volume 挂载**
每次更新权重就重建一个 50GB 容器，又慢又贵。用 volume 挂载，你只需上传一次权重，部署时附加即可。

**推理以作业形式运行**
请求被排队，由从你部署中拉起的 worker 执行。这支持长时间运行的作业、批量工作负载和混合流量模式。

**由队列深度或自选指标驱动的自动扩缩容**
根据利用率、队列长度、加权队列优先级，以及视频长度、目标等待时间等作业特征来扩缩容量。

**流量策略是显式的**
你可以定义多条队列，按客户等级、用例或 SLA 控制优先级。批量工作负载不会干扰实时请求，付费用户在流量尖峰时受到保障。

**可观测性内建**
指标、日志和作业状态开箱即用，随时监控状态。
