最好的前沿模型只能解决 87 个真实问题中不到三分之一——但有少数生成的 kernel 超过了任何公开可用的实现。

## 摘要

LLM 写 GPU kernel 已经出色得令人惊讶**[1][2][3]**，但当前度量这一进步的基准几乎都是单 GPU 的。在生产中，通信常是瓶颈：通信开销可以占到推理延迟的 20% 以上**[4]**，而且随着计算比互连带宽扩展得更快，这个缺口还在拉大。

[**ParallelKernelBench**](https://www.alphaxiv.org/abs/2606.parallel-kernel-bench)（PKB）提供一个面向多 GPU kernel 生成的基准与评估框架，包含 87 个来自真实代码库的问题，任务是用通过 NVLink 直接搬数据的 CUDA kernel 替换 PyTorch + NCCL。我们测试了 GPT-5.5、Gemini 3 Pro、Opus 4.7 等前沿编码模型。评估暴露出全面的表现缺口：正确解决的问题不到三分之一，其中又只有不到四分之一击败朴素基线。

我们将讲述它们为何失败、失败模式长什么样，以及几个模型出人意料地生成比任何公开实现都快的 kernel 的案例——其中包括一个 [NVIDIA NeMo-RL 的 GRPO 训练循环](https://github.com/NVIDIA-NeMo/RL/tree/main)kernel，此前没有公开的优化参考实现。

## 多 GPU 与单 GPU kernel 生成有何不同

LLM 在 GPU kernel 生成上已有进展，但这些进展大多在单 GPU 上度量。生产 AI 负载已不再 fitting 这个框架：它们横跨多块 GPU，性能越来越取决于通信而非仅仅是本地计算与内存。这一转变让多 GPU kernel 生成在三个方面成为不同的问题：

- **设计空间组合式膨胀。** 实践者组合张量、专家、数据、上下文和序列并行去贴合硬件，每种组合都创造不同的通信模式。
- **性能模型改变。** 单 GPU roofline 围绕计算与内存带宽构建。多 GPU 代码的瓶颈常在互连。
- **多 GPU kernel 生成了一个关键的新设计选择：** GPU 之间如何搬数据——通过 copy engine、TMA、SM load/store 还是 NVLS——以及是否把搬运与计算融合。

## ParallelKernelBench

我们构建 PKB，是为了测试模型能否超越纯粹的 `torch.dist`、真正写出生产级多 GPU kernel。每道题从一个标准 PyTorch + NCCL 实现和一段硬件拓扑描述出发。模型随后必须用借助 symmetric memory 跨 GPU 直接通信的 CUDA kernel 替换该参考实现。

PKB 评估流水线。每题提供任务、硬件拓扑和 PyTorch + NCCL 参考；模型生成自定义 CUDA kernel，按正确性、墙钟加速和通信 roofline 评估。

为确保 87 道题覆盖真实的生产并行类型空间，我们基于分布式工作负载的分类法构建它们。首先识别模型被切分的主要方式——张量、上下文、数据、专家、序列和 FSDP/ZeRO——以及各自创造的通信模式。然后从 [Megatron-LM](https://github.com/nvidia/megatron-lm)、[DeepSpeed](https://github.com/deepspeedai/deepspeed)、[DeepEP](https://github.com/deepseek-ai/DeepEP)、[TensorRT-LLM](https://github.com/NVIDIA/TensorRT-LLM)、[NeMo-RL](https://github.com/nvidia-nemo/rl) 等系统的代码库，以及长尾的非 LLM 负载（GNN 路由、分布式 FFT、高斯泼溅等）中选出 87 道题来覆盖该空间。另一个好处是：由于 PKB 参考用标准 PyTorch + NCCL 写成，基准不绑定任何单一特定硬件世代，而是设计为自然地随下一代硬件架构演化。

标准 transformer block 的并行化分类法。不同切分策略在归一化、attention 和 MLP 间创造不同的通信模式，以有代表性的 Gemma3-27B 层为例。

PKB 问题在并行类型（左）与源代码库（右）上的覆盖，横跨 RL 训练后处理、LLM 训练、kernel 库、视觉模型、GNN 等。

在评估模型之前，我们先检查 PyTorch + NCCL 基线是否留有真实余量。通信感知的 roofline 说是：多数 PKB 问题受 NVLink 瓶颈限制，基线运行远在硬件天花板之下。所以下一个问题很简单：模型能弥合这个缺口吗？

## 前沿模型在 PKB 上的表现

**不好。** Zero-shot 设置下，最好的模型解决 87 题中的 28 题，其中只有 22 个解比 PyTorch + NCCL 基线更快。采样三次把最好成绩提升到 36 个正确解、27 个快于基线的解，但 fast1@3 仍止步于 31%。

**单次采样的 LLM 在 PKB 上挣扎。** pass@k 报告 k 次尝试中最佳的正确率；fast1@k 统计既正确又击败 PyTorch + NCCL 基线的解。重复采样改善两个指标，但 fast1@3 峰值仍只有 31%（GPT-5.5），暗示超越采样噪声的根本性局限。

成功集中在熟悉的模式上：集合通信原语、张量并行 GEMM、以及 Ulysses 式上下文并行——它用 all-to-all 通信沿注意力头切分序列维度。这些是多 GPU 栈中在开源代码里最可见的部分，所以模型对它们可能有更强的先验。

失败则暗示比 CUDA 语法更深的问题。较弱的模型常编译失败，但较强的推理模型频繁产出能编译、却返回错误结果的 kernel。难的是对 rank 协调、数据划分和集合通信顺序的推理。

生成的 kernel 使用的通信机制也非常狭窄。多数依赖 copy engine 或 SM load/store 指令，而 TMA、NVLS 等更专门的机制几乎缺席。很多情况下，模型没有选择达成峰值性能所需的机制。我们将其归因于数据稀缺与硬件复杂性的组合：TMA、NVLS 等新原语需要穿梭于复杂的硬件特定抽象（如异步拷贝描述符或新的 NVLink 拓扑），模型在这些地方缺乏强先验。这让"能用"的分布式 kernel 与真正优化的 kernel 之间存在大缺口（一个面向未来工作的明确目标！）

前沿模型间的 fastp 分数分布。即便最好的模型（GPT-5.5）也随加速阈值上升迅速跌落；p = 1.0 时 fast1 止步约 31%。

按模型划分的 PKB 失败模式。较弱模型大多在编译期失败；较强的推理模型更常产出能编译但返回错误结果（输出不匹配）或死锁的 kernel。

GEMM + All-Gather 的 profiler trace：生成的 CUDA kernel（87.9 μs）通过 NVLink 让计算与通信重叠，击败 PyTorch + NCCL 参考（320.6 μs），但仍高于理论 roofline（4.99 μs）。

自然的下一步是给模型一个人类 kernel 作者会用的同样反馈回路。我们把 Gemini 3 Pro 包进一个可访问仓库、终端、编译器输出、正确性测试、速度测量和既往尝试的[agentic harness](https://github.com/SWE-agent/mini-swe-agent)。模型不再产出一个 kernel 就停，而是可以编译、跑基准、检查失败并修订。

Agentic 评估循环：模型写文件、跑正确性测试与基准，迭代直到解通过或步数预算耗尽。

这有帮助，但实际收益有限。Gemini 3 Pro 从单次设置的 24 个正确解提升到 87 题中 35 个，其中 26 个 kernel 击败 PyTorch + NCCL 基线。收益来自修复语法错误、形状错误和简单运行时 bug。大约 20 轮精化后性能进入平台期。反馈帮助模型调试分布式 kernel，但剩余的失败凸显一个更大的缺口：无法对 rank 协调、通信顺序和 GPU 间传输机制的最优选择进行推理。

## 全新的 kernel

用直接 NVLink load/store 替换 NCCL 集合通信的例子：参考实现除了 NCCL 集合还需要额外 reshaping；生成的 kernel 把计算操作与直接的对等内存读取融合。

除标准集合通信上的加速外，单次生成偶尔会浮现真正全新的高性能 kernel——针对那些没有公开优化参考的负载。这种能力预览了 AI 驱动优化的更广潜力；收益不只限于 Transformer，模型在状态空间模型、基因组学流水线、多模态 RL 循环上也能做得很好——这些领域的专精 kernel 相对主流 LLM 栈基本未被优化。

下面三个例子，每一个都用融合 symmetric-memory kernel 替代 NCCL 集合、通过 NVLink 直接搬数据。每个都在 4 块 H100 GPU 上经 100 次随机运行验证了正确性；速度测量遵循 [ThunderKittens 2.0](https://hazyresearch.stanford.edu/blog/2026-02-19-tk-2)**[5]** 的基准方法学（逐位一致的输入、L2 感知的输入组、500 次 warmup 迭代和 100 次连续 profiling 迭代）。

### NeMo vocab-parallel log-prob with top-*k*/top-*p* filtering（Gemini 3 Pro）

NVIDIA NeMo-RL 的 GRPO 训练循环中的核心一步：在 top-*k*/top-*p* 过滤分布下计算按词汇切分的 log-probability。PyTorch + NCCL 基线在过滤前跨 rank 聚合整个词汇表；生成的 kernel 完全跳过那些集合通信，用 symmetric memory 就地置换分片，同时把 log-softmax、token 抽取与 target gather 融合进单次 warp-shuffle 归约。

[Reference](https://nathanjpaek.github.io/parallel-kernel-bench/kernels/vocabplogtopk-reference.txt)

[Custom kernel](https://nathanjpaek.github.io/parallel-kernel-bench/kernels/vocabplogtopk-kernel.txt)

跨序列长度 M ∈ {1024, 2048, 4096, 8192, 16384} 相对 PyTorch + NCCL 的加速。配置：4 个 rank，B = 1，V = 32,000（每 rank 本地词汇 8,000），top-k = 10，top-p = 0.9。

### Hyena forward context parallelism（GPT-5.5）

Hyena 算子的上下文并行前向传播——其 FFT 卷积需要序列全局上下文。参考实现通过反复 `all_to_all` 调用在序列切分与通道切分布局间来回切换；生成的 kernel 把输入打包进单个 symmetric 分配，通过 NVLink 流式传输远端切片，在统一的一遍中计算门控与重索引。值得注意的是，性能在更长序列长度上会退化。

[Reference](https://nathanjpaek.github.io/parallel-kernel-bench/kernels/hyenacp-reference.txt)

[Custom kernel](https://nathanjpaek.github.io/parallel-kernel-bench/kernels/hyenacp-kernel.txt)

4 GPU 上跨本地序列长度 l ∈ {1024, 2048, 8192, 16384} 相对 PyTorch + NCCL 的加速。正确性与速度在 100 次试验上测量。

### SAM 3 all-gathered mask IoU suppression（GPT-5.5）

SAM 3 视频分割的跨 GPU 去重抑制：每帧之后，各 rank 用交并比比较预测区域，把重叠的 mask 清零。基线使用变长 `all_gather` 集合通信加密集 matmul；生成的解把它折叠为一条 symmetric-memory kernel 流水线，对 mask 做位打包，并用硬件 popcount 计算成对重叠。

[Reference](https://nathanjpaek.github.io/parallel-kernel-bench/kernels/sam3-reference.txt)

[Custom kernel](https://nathanjpaek.github.io/parallel-kernel-bench/kernels/sam3-kernel.txt)

固定 mask 分辨率 256 × 256、IoU 阈值 = 0.7 下，跨跟踪目标数 N ∈ {16, 32, 64, 128, 256, 512} 相对 PyTorch + NCCL 的加速。

## 后续研究

PKB 目前刻意限定在节点内 NVLink。自然的延伸是节点间组网——RoCE、InfiniBand——那里的设备侧 API 版图更年轻，以及 TPU 等其他加速器与拓扑。我们也想知道更高层抽象是帮助还是妨碍：PKB 已接受 [Triton](https://triton-lang.org/main/index.html) 和 [ParallelKittens](https://hazyresearch.stanford.edu/blog/2025-11-17-pk) 解，而 NCCL GIN、NVSHMEM 等新兴接口作为目标值得研究。把这些范式扩展进来，将促进 AI agent 如何在多样编程模型与硬件抽象中导航的进一步研究。

更大的目标是这件事背后更难问题的一个具体落点：能够自主优化和管理大规模分布式基础设施的 LLM 系统。对为语言模型训练与推理专门定制的基础设施，实现这种自主最终可能桥通到能处理自身端到端研究工程的 AI agent。
