Artificial Analysis 报告的 speed factor（每秒转录的输入音频秒数）——越高越好

## **模态很重要**

一个 100 万 token 的文本 prompt 能装下整个《哈利·波特》系列，体积也只有约 5 MB。这个规模听起来巨大，但输入本身是紧凑的。文本到达时几乎可以直接用于推理：tokenize、组批、送进模型。

音频改变了问题的形状。同样内容的有声书有 5 到 10 GB，比文本大约三个数量级。在它抵达 GPU 之前，服务器要先解容器格式、重采样、滤噪、跑 VAD、切分语音、计算音频特征。

模型侧也反转了。如今的 LLM 有数千亿乃至上万亿参数，服务的工作自然集中在 GPU 内部：量化、KV 缓存、attention kernel、批处理和并行。语音转文字模型小得多，通常在数亿到低位数十亿参数之间，因此周围的数据通路重要得多。

这让 ASR 服务成为一个全路径的系统问题，横跨 GPU 执行、CPU 预处理、内存搬运、传输、连接调度和运行时行为。同一套栈还要服务两种不同的形态：最看重吞吐的离线转录，以及由延迟和抖动主导的流式转录。

Together 的 ASR 栈服务 Artificial Analysis 榜单上延迟最低的两个语音转文字模型：NVIDIA 的 Parakeet-TDT 0.6B v3 和 OpenAI 的 Whisper Large v3。其中更快的那个，NVIDIA Parakeet-TDT 0.6B v3，能在 10 秒内转录约 20 小时语音——大致相当于《哈利·波特》电影全系列总时长。

本文其余部分拆解这一结果背后的生产改动：面向真实音频形状的 TensorRT profile、GPU 侧的解码器控制流、更少拷贝的 CPU 路径、事件化流式 I/O，以及运行时 GC 控制。

## **为真实音频形状编译编码器**

Parakeet 是 encoder-decoder 架构，约 95% 的权重在编码器里。编码器接收变长语音段、产生声学帧给解码器，这使它成为第一个要优化的地方。

音频输入长度跨度极大：从 200ms 的流式包到 30 秒不间断语音。为一种输入形状调优的 kernel 计划在另一种形状上可能慢得多，所以引擎在编译时就需要知道它将看到的形状分布。

在 TensorRT 之前，我们已经用 `torch.compile` 加 CUDA graph 走优化过的 PyTorch 路径，并按同样的形状 profile 调优过。这给了我们一个强基线：不离开 PyTorch 栈的形状感知执行。

TensorRT 为生产提供了一条更快的编码器路径。它提前构建优化的执行计划：尽可能融合 kernel、调优内存布局，并针对我们预期服务的形状范围对 kernel 变体做基准测试。

重要的细节是 profile 调优。只按最大输入形状调优的单一引擎，会迫使较短音频段走填充（padded）路径——对Streaming chunk 和短句尤其昂贵。一个多 profile 的 TensorRT 引擎让我们能在内存里只保留一份编码器权重的同时，按请求选择正确的优化 profile。

内存节省有限，大约从 6 GB 到 5 GB。更大的收益是避免坏的形状匹配，以及从优化的 PyTorch 迁到按 profile 调优的 TensorRT。在小输入区间，profile 感知的 TensorRT 可以比把请求塞进大填充 profile 快若干倍。

编码器优化完成后，解码器循环成为下一个瓶颈。

## **把 CPU 从解码器循环中移除**

Parakeet 的解码器遍历编码器的声学帧，为每个帧发出一个 token 或一个 `BLANK`（不推进转录的帧）。代码本质上是：

`state = init()`

`for frame in encoder_output:`

` token = predict(frame, state)`

` if token != BLANK:`

` emit(token)`

` state = update(state, token)`

profiling 时我们发现 `predict` 和 `update` 都很快，每次迭代的 GPU 工作以微秒计。

昂贵的是这个分支：

`if token != BLANK:`

这个分支要求 CPU 从 GPU 内存把 token 读回来决定走哪条路。这个主机同步使解码循环无法被捕获为单个 CUDA graph，并迫使每次迭代都在 Python 里往返。GPU 做几微秒的工作、等 CPU、启动下一个 kernel，每个请求重复几千次这种模式。

条件 CUDA graph 节点把这个分支搬到了 GPU 上。一个小的设备侧 kernel 评估条件，并告诉 CUDA 运行时是否进入"发出 token 并更新状态"的子图。分支在 GPU 内部解决，于是整个解码循环——计数器、条件、发出、状态更新——可以被捕获为单个 CUDA graph 并一次启动。

CPU 退出了解码器的内层循环，结果是解码器快 2 到 3 倍。

## **停止拷贝音频字节**

编码器和解码器跑顺之后，剩下的延迟来自模型周边的 CPU 路径。这正是我们审计过的大多数 ASR 代码的延迟预算所在：多余的拷贝、热路径上不必要的进程跳转、以及本应提高并行度的单线程函数。

第一个杠杆是消除不必要的进程边界。

音频预处理——无论文件解码、重采样、语音活动检测（VAD）、特征提取还是分块处理——大多是 I/O 或会释放 Python 全局解释器锁（GIL）的原生 C/C++ 工作。典型的微服务架构把预处理拆到三四个独立进程里，为工作负载并不需要的隔离付费。把其中大部分工作折叠进更少的进程，能消除在大文件上可能耗掉数百毫秒的内存拷贝和序列化/反序列化环节。

当真需要进程间通信时，ZeroMQ 之类的常见选项也带来可观开销。在我们的负载中，一个基于持久 Unix domain socket、直接传原始音频字节的简单自定义协议在高并发下表现最好，因为它的帧封装最小、且避免反复建连。

对大文件，socket 仍有两次拷贝：发送方用户态到内核缓冲，然后内核缓冲到接收方用户态。为避开这条路径，我们使用共享内存。共享内存让两个进程映射同一块物理区域，生产者写入的数据无需内核往返就对消费者可见。这给了我们一条零拷贝的数据通路。

复杂性成本是真实的，所以只在数据量值得时才动用共享内存。

## **对流式使用事件化 I/O**

流式 ASR 增加另一个问题：连接生命周期。

我们的第一个流式实现用"每连接一个线程"。当数百条流同时发送 chunk，数百个线程一起被唤醒，GIL 争用爆炸，尾延迟飙升。

我们改为一个线程阻塞在 `epoll` 上。

`epoll` 让一个线程注册数千条连接，用一次系统调用问内核："其中任何一条有数据时叫醒我"。消息到达时，内核返回整个就绪集合，该线程处理活跃 socket 后再回去睡眠。

同样的负载，调度器压力小得多。对流式 ASR，这种可预测性很重要，因为被延迟的部分转录会让语音系统"感觉慢"——即使平均延迟看起来正常。

## **冻结启动状态，消除 GC 尾延迟**

我们差点漏掉这一项。

流式工作负载承压时，p50 和 p90 延迟健康，但 p95 会周期性飙升约 200 ms。日志显示队列深度很小、GPU 时间正常，但平时 5 ms 内完成的 CPU 函数突然要跑 100 ms 以上。

后台有什么东西在从请求循环偷时间。

Profiling 指向 Python 的垃圾回收器（GC）。Python 大多数内存管理用引用计数，另有一个检测循环引用的收集器捕捉引用环。该收集器分代运行：最老的一代存放长生命周期对象，full collection 会遍历庞大的对象图。

我们在启动时预分配了一大片缓冲池、模型状态和查找表，专门为了避免稳态下的分配延迟。那些长生命周期对象落进了最老的一代，于是 full GC pass 要遍历数十万个引用。那就是那 200 ms 的停顿。

修复是启动预分配之后的一行：

`gc.freeze()`

`gc.freeze()` 告诉 Python 把预分配状态排除在后续 GC 扫描之外，正常请求作用域的对象照常被回收，而巨大的初始状态不再被动。

p95 飙升消失了，p50 也改善了，因为系统能维持更平滑的流量形态。

教训是：在模型之外继续 profiling。GPU 时间、队列深度、模型执行一切看起来正常；延迟飙升住在 Python 运行时里。

## **语音延迟是端到端的系统问题**

语音 agent 通常以级联方式运行：ASR 产出转录，LLM 生成响应，TTS 产出音频。ASR 是这条路径的第一级，它的延迟和抖动设定了用户可见响应时间的最早下界。

上述优化各自针对这条路径的不同部分。TensorRT 多 profile 引擎为真实音频形状调优编码器执行；条件 CUDA graph 把 CPU 往返从解码器循环中移除；持久 Unix domain socket、共享内存和 `epoll` 削减 CPU 路径开销；`gc.freeze()` 消除一个运行时层面的 p95 失败模式。

同样的约束适用于栈的其余部分：每一级都必须在模型执行、预处理、传输、调度和运行时行为上同时控制中位延迟和尾延迟。
