# Together Compiler：面向 AI 推理的持续编译

AI 推理负载是动态的。横跨新模型、硬件平台、客户、使用场景和流量形态，存在着数千种运行场景。再靠人工逐一优化每一种运行场景，已经无法规模化了。

- 架构差异极大：Transformer 问世已有约 11 年。我们本以为会出现更多收敛，但 OpenRouter 上排名前十的开源 LLM 没有两家用的是同一种架构！
- 负载差异极大：Together 每天要服务数万亿 token，分布在数千个客户身上，而每个客户的流量形态都不同（batch size、序列长度、MoE expert 不均衡、attention 稀疏度、会话时长、领域）。
- 硬件差异极大：H100、B200、B300、NVL72、VR、Groq 等等，每一种都需要截然不同的策略。

理论上，agent 非常适合这个问题。它们能够适应新的负载，并在所有可能的优化空间里搜索，而不必依赖那些困扰人类专家和传统机器学习编译器的固定规则或启发式。然而，今天的 agent 系统正被实验速度这一瓶颈卡住。

### **我们推出 Together Compiler（TKCC）：首个借助高吞吐 agent、面向多样推理负载做优化的 *真正* *持续* 的优化循环**

在不到 24 小时之内，TKCC 就在前沿开源模型（Kimi K3、GLM 5.3、MiniMax M3.1-Flash、DeepSeek v4.1-Flash）上取得了最高 2.6 倍的 TPS 提升；在 SemiAnalysis 的 InferenceX 基准的低延迟赛道上创下 state-of-the-art——MiniMax M3.1-Flash 上 1111 TPS、DeepSeek v4.1-Flash 上 1205 TPS；并在它们的主打场景 Llama 1B、batch size 1 上，比现有的开源 megakernel 高出 1.7 倍。此外，TKCC 还能泛化到语言模型推理以外的领域（气象建模、PDE、时间序列和生物学）。这一性能提升之所以可能，是因为 TKCC 的实验吞吐相比基线的 agent 性能优化系统高出 252 倍。Together Compiler 今天正在服务数万亿 token。

## 流量在持续变化

作为推理服务商，我们会看到各种各样的用户行为，它们源于区域性模式、新模型发布以及突发性。

- **区域性模式：**世界各地的用户可能有不同的模型偏好。我们观察到，一个国家工作时段的流量，其 prompt 比另一个国家长 1.4 倍（97k 对 70k）。
- **模型发布：**用户需要一些时间才能摸索出如何把新发布的模型接入自己的工作流。起初，他们往往选择基于聊天的交互与评估；紧接着，在发布仅仅两周之后，随着用户转向 agent 化的负载，prompt 长度就出现 80% 的增长。
- **突发性：**客户可能在一整天里随机的时刻发出成批的请求。如果处理不谨慎，prompt 长度可能突然翻倍，缓存命中率也会下滑。

显然，我们必须适应不断变化的用户行为，为每一个新的部署做专门的优化。

## Together Compiler 概览

TKCC 的输入是流量形态、模型和硬件。TKCC 使用 agent 为推理引擎生成一系列优化。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6aeaef19bddbf4ee964def1a_02-compiler-loop%402x.png)

图 1：随着流量漂移，Together Compiler 会重新编译——agent、persistent engine 与 ensemble 处在一个循环里。

### TKCC 的核心洞见如下：

**1. TKCC 最大化实验吞吐，并在 agent 优化过程中最小化 GPU 空闲时间**

**‍**现有大多数 agent 式推理优化系统，都要求 agent 为每一次新实验启动并销毁 VLLM、SGLang 或 TRT-LLM 这样的 engine。然而 engine 的启动耗时是数十 *分钟*，严重阻碍了实验吞吐（见下表）。TKCC 转而提出一种“persistent engines”的新范式：engine 只启动一次，就能热重载任意候选的 forward pass，完全不需要重启。为了让 persistent engine 时刻都有新的优化可测，TKCC 会派生多个 agent，持续产出想法，并通过一块 message board 相互沟通，把各自的工作并行推进。

| 阶段 | 现状（s） | Together Compiler（s） |
| --- | --- | --- |
| 进程 + worker 初始化 | 93 | – |
| 权重加载 | 50 | – |
| KV-cache 尺寸确定 | 21 | – |
| JIT kernel 预热 | 93 | – |
| 自动调优 | 193 | – |
| API server 就绪 | 10 | – |
| RPC 调用 + Together Compiler 搭建 | – | 1.7 |
| CUDA-graph 捕获 | 7 | 7.3 |
| **到可服务的总时间** | **467** | **9.0** |

表 1：engine 启动代价高昂

**2. TKCC 在测量吞吐与测量保真度之间平衡取舍**

**‍**现有的 agent 优化系统要么反复重启推理引擎，因而实验吞吐很低；要么在推理引擎之外孤立地优化独立 kernel，因而测量保真度很差。优化独立 kernel 的系统常常用随机输入数据来评估它们。然而，当现代架构用上 MoE、sparse-k attention 这类依赖数据的原语时，输入数据的分布会直接影响哪些优化策略可能胜出（见下图）。高保真的输入对于有效的优化至关重要。TKCC 用一个分层的 persistent engine 来平衡吞吐与保真的取舍：“fast engines”只加载少量层，最适合快速迭代和低方差的计时；“slower engines”加载许多层，最适合检验优化在真实数据分布上是否依然成立。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6aeaef2d1206e619f3a5d43a_03-expert-routing%402x.png)

图 2：输入数据会改变优化策略。

图 3：Together Compiler 的两级架构优于其他方案。

**3. TKCC 利用一份定制的 cost model 为 agent 挑选并行策略（例如 TP、EP、DCP 等），以达到最高性能**

现有系统在 SLA 要求之下挑选推理配置时已有相当精细的方法。然而，挑选理想配置同样面临吞吐与保真的取舍：逐一测量每一种并行配置是不可行的，尤其是在软件实现还不成熟的情况下。一种朴素的做法是基于原始硬件规格或 micro-benchmark 来挑选并行策略。但这样无法充分刻画依赖数据的流量特性，比如 MoE expert 不均衡、或者 prompt 长度分布不均。我们设计了一份 cost model，它采用分层的测量策略，把硬件规格、microbenchmark 和实测的 forward pass 都用上，从而构造出高保真的表示，同时快速剪枝配置搜索空间，以支撑持续的流量漂移。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6aeaf47a09cf3ea5aafc9c29_05%20%C2%B7%20cost%20per%20request%20vs%20decode%20TPS%20SLA%20%C2%B7%20attention%20split%20%2B%20measured%20vs%20spec%20%C2%B7%20on-brand%20%23151630.png)

## 结果

我们把 TKCC 与三类不同的基线做评估对比：人工调优的 megakernel、InferenceX 的 engine 配置，以及来自气象建模、PDE、时间序列和生物学模型等各个领域的流行 AI 代码库。

### MegaKernel 负载

我们先评估最具代表性的 MegaKernel 负载：batch size 为 1 的 Llama 1B。这一模型架构已经被人类专家和传统机器学习编译器充分优化过。TKCC 带来了高出 1.7 倍的 TPS，并且在序列长度增加时依然保持性能。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6aeaef70ecac1390b3de6711_06-fig5-h100-b200%402x.png)

图 5：在 H100 和 B200 上，Together Compiler 都优于 megakernel 与 CUDA graph 基线

### InferenceX AgentX 负载

我们在 SemiAnalysis 的 AgentX 基准上评估 TKCC。起点是前沿模型在各家推理引擎和各块硬件平台上已有报告的最佳开源 engine 配置。TKCC 在所有设置下都稳定地定义了性能前沿，相比高度优化的基线最高带来 2.6 倍的 TPS 提升。1

我们还专门评估了 batch size 为 1 的低延迟场景，并以 MiniMax M3.1-Flash 上的 1111 TPS、DeepSeek v4.1-Flash 上的 1205 TPS 创下 state-of-the-art。对于这些结果，我们用自家的 cost model 来挑选并行配置，而不是沿用 InferenceX 配置。用这种做法我们观察到了加速。

![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6aeaef8992165a8ccbf9ce66_07-fig6-throughput-vs-interactivity%402x.png)

图 6：在大多数模型上，同样的单用户速度下，Together Compiler 每块 GPU 能服务更多 token。


![](https://cdn.prod.website-files.com/69654e88dce9154b5f12070c/6aeaefa0e488f686e9121fd9_08-p50-p90-tps-per-user%402x.png)

图 7：在全部六组模型与芯片的组合上，Together Compiler 的单用户速度都快于最佳的 InferenceX 配置
