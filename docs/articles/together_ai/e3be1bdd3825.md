一个程序级调度器，消除 KV 缓存颠簸：在大规模 agentic 推理中交付超过 2 倍的单节点吞吐与近似线性的多节点扩展。

## 摘要

我们推出 ThunderAgent——一个高吞吐 agentic 推理系统。通过为 agentic LLM 请求调度引入全新的程序抽象，ThunderAgent 在我们的合成数据生成流水线中取得最高 2.5 倍单节点吞吐，并在 8 节点集群上带来 2.4 倍加速——吞吐随 GPU 节点数近乎线性扩展。

## 关键结果

→ 超过 2 倍的单节点吞吐，高并发下 P50 延迟约降 10 倍
→ 8 节点 2.4 倍加速，16 到 64 块 GPU 近线性扩展
→ 即插即用：一个 program_id 字段，OpenAI 兼容，与你现有的引擎级优化（如推测解码）共存

ThunderAgent 被 ICML 2026 接收为 Spotlight 论文。

这篇论文是 Georgia Institute of Technology、University of Illinois Urbana-Champaign、Carnegie Mellon University 和 Together AI 研究者的合作成果。

LLM 正越来越多地以 agent 形态部署。Claude Code、Codex、OpenClaw 这样的系统会推理、调用工具、读取结果、再推理，常常几十轮才完成一个任务。训练这些 agent 需要大规模合成数据生成，因为自然网络语料不包含多轮、使用工具的 agent 轨迹。为了生成像我们近期发布的 [CoderForge](https://www.together.ai/blog/coderforge-preview#coderforge-preview-data) 这样的 agentic 数据集，我们需要在高并发下运行 agentic 推理。

然而现有推理引擎在请求层面调度：每次 LLM 调用是独立单元，毫无"自己属于更长的多轮工作流"的意识。当 agent 暂停等待工具调用时，它的 KV 缓存可能被逐出以给其他请求腾地方，等 agent 恢复时又要从零重算。这给 SGLang、vLLM、TensorRT-LLM 等引擎在高并发服务 agentic 负载时造成根本性低效，包括 KV 缓存颠簸、多节点负载不均和工具管理中的资源浪费。本文中我们聚焦最关键的问题：KV 缓存颠簸。更全面的讨论见论文。

## 阻碍规模化 agentic 推理的因素

agentic 工作流在两个阶段间交替：GPU 繁重的**推理**阶段（模型正在生成 token）和 GPU 空闲的**行动**阶段（agent 在等编译器之类的工具返回）。当成百个 agent 并发运行时，它们的 KV 缓存在每个阶段增长、争抢有限的 GPU 内存。在这种内存压力下，vLLM 这样的传统推理引擎会用简单策略逐出 KV 缓存：最近最少使用——不管那份缓存是否几秒后就要被重新用到。

结果是一个恶性循环。agent A 暂停等工具调用；它的 KV 缓存被逐出，给 agent B 的 prefill 腾地方。当 agent A 的工具返回，引擎必须从零重算 agent A 的整个对话历史，而这又逐出了 agent C 上下文的缓存。高并发下，这种逐出与重算的级联会带来严重的吞吐与延迟劣化。我们把这个问题称为 **KV 缓存颠簸**。

简单地堆更多 GPU 节点并不能完全解决。现有 SGLang Model Gateway 这样的多节点路由器把每个 agent 钉定在固定节点上以保持缓存局部性。但由于 agentic 上下文长度不可预测地增长，一些节点被分配了长上下文的 agent 而内存耗尽，另一些节点带着富余容量闲置。过载节点依然颠簸。

采用 KV 缓存 offloading 也解决不了问题。LMCache、HiCache 这类策略把 KV 缓存卸载到 CPU 内存或磁盘，扩大了总缓存容量，却只是推迟颠簸。当并发 agent 的工作集超出所有存储层级时，逐出恢复，同样的恶性循环回来。

在内存压力下，请求级引擎会在 agent 暂停等工具的那一刻逐出其 KV 缓存，然后在恢复时重算整个对话，进而逐出下一个 agent 的缓存，级联成恶性循环。

## ThunderAgent 如何解决颠簸问题

请求级引擎无法独自修复颠簸，因为它们永远看不到"一系列 LLM 调用属于同一个更长工作流"。ThunderAgent 补上了这层视角。ThunderAgent 是一个轻量调度层，位于 agentic 客户端与推理后端之间。它把每个 agentic 工作流抽象成一个可调度的程序，追踪其执行阶段、KV 缓存占用和节点放置。

ThunderAgent 通过程序级调度缓解 KV 缓存颠簸：它监控每个节点的内存压力，选择性地暂停低优先级工作流，减少争抢缓存的程序数量。并发程序少了，剩余活跃工作流的 KV 缓存命中率显著更高、延迟更低。当被暂停的工作流准备好恢复时，ThunderAgent 通过全局等待队列把它们路由到可用容量最多的节点，在集群间平衡负载。

对多节点部署，ThunderAgent 用全局等待队列取代基于会话的静态节点钉定。当暂停的工作流准备恢复，ThunderAgent 把其请求路由到可用容量最多的节点。这种路由策略在 KV 缓存局部性与多节点负载均衡之间取得平衡，在整个集群同时实现高效缓存利用和均匀负载分布。

除多节点可扩展性外，ThunderAgent 还与 KV 缓存 offloading 兼容，把 GPU HBM、CPU RAM 和磁盘存储上的 KV 缓存容量视为统一池。offloading 本身只能推迟而非消除颠簸，但无论底层存储层级如何，ThunderAgent 的暂停-恢复策略都持续有效。

ThunderAgent 位于 agentic 客户端与推理后端之间，把每个工作流抽象为可调度程序。它在程序表中追踪执行阶段、KV 占用和节点放置，在内存压力下暂停低优先级程序，并通过全局等待队列把它们恢复到空闲容量最多的节点。

## 评估

我们把 ThunderAgent 集成进内部合成数据生成流水线——即 CoderForge 等数据集背后的同一套 harness 和基础设施：数百个 LLM 编码 agent 并发与沙箱环境交互几十轮，生成轨迹。

我们在单个 8×H100 节点上、使用 HiCache KV 缓存 offloading，把 ThunderAgent 与 SGLang 默认调度器对比。batch size 192 时，SGLang 吞吐跌到 390 token/s、平均延迟 65s；ThunderAgent 达成 803 token/s 吞吐、平均延迟 10.6s，把吞吐-延迟权衡的 Pareto 前沿向外扩展。

单个 8×H100 节点、HiCache offloading 下的吞吐与延迟，并发从 64 扫到 192。基线劣化时，ThunderAgent 保持吞吐、延迟近乎平坦。

我们把评估扩展到多节点集群，对比 [SGLang Gateway](https://docs.sglang.io/advanced_features/sgl_model_gateway.html#cache-aware-policy-tuning)，最多 8 块 H100 节点。如图所示，ThunderAgent 吞吐随 GPU 节点数近乎线性扩展，从 16 块到 64 块 GPU 时从 671 增长到 2,248 steps/min。同时 ThunderAgent 相对 SGLang Gateway 的加速随集群大小扩大——从 2 节点的 1.79× 到 8 节点的 2.39×。SGLang Gateway 造成随集群增长而加重的内存不均，而 ThunderAgent 的全局等待队列把恢复的工作流路由到任何有可用容量的节点，降低整个集群的内存不均。

从 2 到 8 个 H100 节点的吞吐扩展。ThunderAgent 保持近线性，并把对 SGLang Gateway 的领先扩大——从 2 节点 1.79× 到 8 节点 2.39×。

## 结论

核心转变是把每个 agent 工作流当作一个程序，而不是一串无关请求。正是这一个抽象让 ThunderAgent 能停止 KV 缓存颠簸、平衡跨节点负载、并持续兼容你已经在运行的 offloading 与解码优化。也是它让系统实际可采纳：工作流被端到端追踪，而无需改动你的推理后端。

除我们自己的合成数据流水线外，ThunderAgent 已被 SkyRL 和 NVIDIA Dynamo 等开源框架采用。我们认为程序抽象是下一代 agentic 推理系统的正确地基，并期待社区在其上构建什么。
