# 缓存感知的 prefill–decode 分离（CPD）：长上下文 LLM 服务提速最高 40%

## 摘要

服务长 prompt 不必意味着慢响应。在 Together AI，我们构建了缓存感知 prefill–decode 分离（cache-aware prefill–decode disaggregation，CPD）——一种按缓存命中率把冷、热工作负载刻意分开的服务架构，从而实现快速的上下文复用。通过隔离重量级 prefill 并利用分布式 KV 缓存，CPD 为长上下文推理带来最高 40% 的可持续吞吐提升和显著更低的首 token 时间（TTFT）——在混合的真实世界流量下尤其如此。

今天的 AI 原生应用正把上下文长度推向新极限。从多轮对话、编码 copilot 到 agent 记忆和检索增强系统，长 prompt 正在成为常态。但高效服务这些大上下文仍是挑战：**TTFT 上升且波动更大**。推理性能越来越不只取决于模型算力，还取决于系统处理共享上下文的效率。真实工作负载中，很多请求并非全新：有些包含相当大比例此前已出现过的上下文——如共享的 system prompt、对话历史或常见文档。我们称之为**热请求（warm requests）**；另一些引入的基本是新上下文、需要完整计算——这些是**冷请求（cold requests）**。

prefix caching 和 prefill–decode 分离（PD）等近期进展已经改善了长上下文服务。prefix caching 通过复用先前已算好的 prompt 前缀 KV 缓存减少重复工作；PD 则把计算密集的 prefill 阶段与延迟敏感的 decode 分开，减少两者相互干扰。再加上 chunk prefill、序列/上下文并行等相关技术，它们共同降低开销、提升硬件利用率。

然而，极高负载下的真实工作负载带来了超出常规服务场景的新挑战。设想一个系统：一些并发用户提交超过 10 万 token 的全新大 prompt，另一些用户继续进行大部分复用早期上下文的多轮对话。PD 保证了 decode 不被 prefill 阻塞，但所有 prefill——无论冷热——仍共享同一份 prefill 容量。大型冷 prompt 会一次占用这些资源数秒，本可通过缓存复用快速服务的热请求只能在同一队列里等待。结果是 TTFT 上升——不是因为热请求需要大量计算，而是因为它们卡在需要大量计算的请求后面。

为解决这个缺口，我们构建了缓存感知分离服务架构，用相互独立的计算资源分别处理冷热请求。通过识别一个请求包含多少可复用上下文，系统能做出更聪明的调度决策——减少无谓等待，把工作在计算资源间更有效地路由。系统不再让昂贵的冷 prefill 主导共享容量，而是为热请求铺快车道，同时高效处理新上下文。

结果是，缓存感知分离设计让系统在高负载下更从容地扩展。如图 1 所示，在尾延迟敏感的 SLA 下，它持续比传统基线维持更高的可达吞吐。在我们的评估中，CPD 相比现有分离式设计将可持续 QPS 提升最高 **35–40%**，即便存在大型冷 prompt，也能维持更紧的尾延迟边界。

## CPD 如何工作

我们提出缓存感知 prefill–decode 分离（CPD），它在标准 prefill–decode 分离服务之上扩展了**缓存感知路由**和**共享 KV 缓存层级**。核心思想很简单：*别让昂贵的"冷"prefill 挡住可复用上下文的快车道*。

系统把推理分为三种角色：

- **Pre-Prefill 节点**：处理低复用（冷）prompt，计算新上下文，并把 KV 缓存写入分布式缓存。
- **Prefill 节点**：优先处理高复用（热）请求，从缓存读取 KV 块而非重算前缀。
- **Decode 节点**：保持专注延迟，与 prefill 干扰隔离。

prefill 和 decode 本来已经分离，CPD 增加了一个专用的 **pre-prefill 层**，处理几乎没有缓存复用的请求。这些节点计算大规模新上下文，并把其 KV 缓存写入分布式缓存。与此同时，普通 prefill 节点专注可以复用已有状态的请求，从缓存读取 KV 块而不是重算。decode 节点保持隔离、专注延迟。

底层，CPD 依赖一个**三级 KV 缓存体系**，如图 2 所示。最快的一层在 GPU 显存，其次是主机 DRAM，以及经由 RDMA 连接的集群级分布式缓存。当一个冷请求被 pre-prefill 节点处理时，其 KV 状态被写入分布式缓存。后续的相似请求可以高带宽批量抓取这一状态，把原本数秒的计算变成数百毫秒的传输加轻量重算。随着时间推移，高频访问的上下文自然向 GPU 靠近，延迟进一步缩短。

图 2：系统总览

路由器把这一切串起来。对每个请求，它估计 prompt 有多大比例可以由缓存服务。低复用请求被导向 pre-prefill 节点，高复用请求直接进入普通 prefill 节点。这种**工作负载分离**防止大型冷 prefill 让共享算力饱和，同时系统仍能摄入新上下文并持续预热缓存。结果是一个在混合、突发长上下文工作负载下依然保持快车道很快的服务栈。

## 重复请求之间发生了什么

当相同或相似的长上下文多次出现——这在 copilot、agent 和多轮聊天场景中很常见——CPD 的收益就显现出来。每个请求都让工作负载进一步远离重计算受限，转向 prefix 缓存复用。

图 3：三次请求的模式。

#### **请求 1 —— 冷（引导）**

大上下文第一次出现时被分类为**冷**。路由器把它发往 **pre-prefill 节点**，执行完整的 prefill 计算。同时，生成的 KV 缓存被写入分布式缓存。

这个请求付出完整计算成本，但它通过把新上下文变成可复用状态*为系统做好铺垫*。

#### **请求 2 —— 热（分布式缓存复用）**

当同一上下文再次出现，路由器将其识别为**热**。普通 prefill 节点不再重算前缀，而是通过 RDMA 从分布式缓存抓取 KV 块并载入 GPU 显存。

现在，数秒的计算被高带宽传输和轻量处理取代。延迟大幅下降，GPU 计算压力也随之下降。

#### **请求 3 —— 热（本地复用）**

如果该上下文仍在同一节点上活跃，其 KV 状态可能已在 GPU 或主机内存中。无需分布式缓存传输——系统直接复用本地缓存。

此时 prefill 只剩极小的开销，延迟进一步收缩。原本需要数秒计算的同一个 10 万 token 上下文，如今可以在几百毫秒内服务完毕。此外，CPD 做的不只是复用前缀——它还把重计算与复用驱动的流量相互隔离，让系统扩展长上下文推理而不让冷工作负载主导共享资源。

## 评估

我们从两个互补的维度评估 CPD，它们对真实负载下的长上下文服务系统都至关重要：

- **负载增长下的延迟与吞吐扩展** —— 随目标 QPS 增加，TTFT（p50 和 p90）与每 GPU 吞吐如何演化。
- **竞争下的有效服务能力** —— 在 prefill 侧饱和导致延迟快速膨胀之前，系统每 GPU 能维持多少可持续 QPS。

我们把基于传统 PD 的部署与 CPD 对比，关注缓存感知分离如何改变冷热混合工作负载下的饱和行为与延迟：

- **2P1D/2P2D（基线）**：两个 prefill 节点加一或两个 decode 节点，使用标准 PD 路由，所有请求共享同一 prefill 容量。
- **CPD-1D/2D**：一条缓存感知流水线，包含一个专用 pre-prefill 层、一个普通 prefill 层和一或两个 decode 节点，由能区分冷热请求的 CPD 感知路由器协调。

所有实验在 NVIDIA **B200 GPU** 上进行。每个 prefill 阶段在每节点 4 块 B200 上使用张量并行，decode 阶段则在 4 块 B200 上使用带 attention 分片的数据并行。我们把在途请求上限设为 24，以反映现实的准入控制、避免无界的尾延迟放大。

对每个目标 QPS，系统在 30 秒内逐步提升流量，然后维持 600 秒稳态负载。QPS 从 0.4 扫到 1.6，步长 0.2，覆盖从轻度负载到饱和的系统行为。

### 工作负载配置

为反映真实的长上下文推理工作负载，我们基于一个具有大型共享上下文和多轮交互的编码 agent 场景设计基准。这一工作负载模拟 AI 辅助软件开发环境：agent 跨多轮维护大量代码库上下文——读文件、分析依赖、实现修改、迭代修复。使用合成数据，其中冷热 prefill 请求的现实配比会对 CPD 的调度决策形成压力。

### 结果

图 4 整体展示了随系统负载上升，CPD 如何重塑延迟扩展行为和服务容量。

图 4：随目标 QPS 增加，2P1D/2P2D 与 CPD 的性能对比。

#### 饱和行为

随着目标 QPS 上升，一旦 prefill 容量成为主导瓶颈，两个系统开始分道扬镳。2P1D 基线更早到达饱和，达成的 QPS 在**每 GPU 约 0.75–0.8** 处走平，之后排队延迟迅速增长。相比之下，CPD 在同样工作负载下持续扩展到约**每 GPU 1.1–1.15 QPS**，进入饱和前的可持续吞吐**提升约 40%**。

饱和点向右移动与图 4（左下）的吞吐曲线一致：负载上升时 CPD 保持更高的有效 prefill 吞吐。通过把冷 prefill 与缓存支撑的热请求分开，CPD 防止长时间运行的冷 prompt 独占共享 prefill 容量，让系统在更高的供给负载下高效运行。

#### 负载下的延迟

在轻负载下，2P1D 与 CPD 的 TTFT 中位数（p50）相当，说明 CPD 在没有拥塞的区间不引入额外开销。然而随着 QPS 逼近基线的饱和点，两者的行为急剧分化。

2P1D 的 TTFT p50 在超过 1 秒后陡升，迅速进入数秒量级，反映的是排在大冷 prefill 后面的等待。CPD 的上升则明显平缓得多：即使在基线已经饱和的目标 QPS 水平，CPD 仍维持**亚秒到低秒级的 TTFT 中位数**，如图 4（左上）所示。这一改善直接来自工作负载隔离——复用缓存上下文的热请求不再被迫昂贵的冷 prefill 执行之后等待。

尾延迟（TTFT p90）呈现出更微妙的模式。中等负载下，两个系统的 p90 表现相似。负载进一步上升时，两种设计的 p90 TTFT 都升高，但在整个评估范围内 CPD 始终低于或持平基线（图 4，右上）。重要的是，CPD 在中位延迟上取得大幅改善，同时没有引发不成比例的尾延迟放大。冷流量突发仍可能增加 pre-prefill 层内的排队，但其影响大体被控制住，保持了可预测的尾部行为。

#### 吞吐效率

图 4 的吞吐分解揭示了这些改善的深层原因。在高 QPS 下，CPD 维持更高的每 GPU prefill 吞吐，而基线的 prefill 吞吐随排队加剧先是走平随后劣化。生成（generation）吞吐在两个系统之间大体相当，说明观察到的性能差异主要来自更高效的 prefill 调度，而非 decode 侧优化。

#### 关键结果与讨论

图 4 显示 CPD 移动了冷热混合工作负载下长上下文服务的工作点。把 decode 容量从 1D 增至 2D 会提升整体吞吐并推迟饱和——对基线和 CPD 配置都成立，证实 decode 侧并行度确实提高了服务容量。

重要的是，即使在扩展 decode 容量时，CPD 依然交付一致的改进。在 1D 和 2D 设置下，CPD 都维持更高的每 GPU 有效 QPS，其中位 TTFT 的增长也比对应基线更平缓。此外，CPD 保持相当或更高的 decode 吞吐，表明其收益不限于 prefill 隔离，还延伸到更高效的端到端流水线利用。

这些改善不是由原始模型执行速度驱动，而是由 prefill 路径上的缓存感知隔离驱动。通过防止长时间运行的冷 prefill 阻塞缓存支撑的热请求，CPD 即使在高负载下也为复用保留了快车道。这凸显了一个事实：随着上下文窗口增长，系统级调度与复用感知设计与模型和硬件效率一起，成为推理性能的一阶因素。
