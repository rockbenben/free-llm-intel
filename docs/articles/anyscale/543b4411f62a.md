# Ray Compiled Graphs：原生 GPU 通信加持的 AI 负载优化

作者：Sang Cho、Sam Chan 和 Stephanie Wang | 2024 年 10 月 7 日

## 引言

随着 AI 模型的复杂度与规模持续攀升，围绕这些模型的工作负载与应用对底层软件基础设施和原语提出了新要求。不同于传统的 CPU 负载，训练和推理这类大型 AI 模型负载绝大部分是 GPU 密集型的，往往需要在数十乃至数百块加速器之间进行分布式计算与协调。

Compiled Graphs 将任务提交开销降到极低（约 50 微秒），而 Ray 标准任务提交开销为 1~2 毫秒。对于以吞吐为主的长时间运行负载（如数据处理或批处理），默认开销可以忽略；但对于亚秒级负载（如自回归 token 生成）则不可接受。

Compiled Graphs 还支持原生 GPU 到 GPU 传输，同时自动解决死锁、让通信与计算重叠。没有 Compiled Graphs 时，用户必须借助 NCCL 等带外通信原语才能实现低延迟 GPU 传输。

这些改进为 Ray 程序开启了令人兴奋的新机会：

- Ray Compiled Graphs 可以在 actor 之间以**毫秒级延迟**传输大型张量
- 使用 Compiled Graphs，你可以用**不到 70 行代码**表达复杂的流水线调度算法，同时在 4×A100 GPU 上运行 Llama 7B 模型时达到与 Deepspeed 等最先进库相当的性能
- 基于 Compiled Graphs、采用异构并行与 GPU 的多模态训练负载，**相比 PyTorch 标准 FSDP 实现取得了 43% 的 token-per-dollar 效率提升**

## Ray 中的 Compiled Graphs 介绍

Compiled Graphs 是 Ray 的新特性，提供类似经典 Ray Core 的 API，具备三大优势：

- 降低重复任务图的系统开销
- 通过 NVIDIA NCCL 原生支持 GPU-GPU 通信
- 优化调度以避免死锁，并充分利用计算与通信资源

与标准 Ray API 相比，Compiled Graphs 以*静态计算图*的形式表达。

利用程序的静态特性，Ray 可以提前为任务分配资源并在后续调用中复用。此外，Ray 可以预先正确分配内存，以利用要求收发双方对称的 NCCL 等优化通信原语。如下所示，Ray Compiled Graphs 可将简单 GPU 张量传输的延迟最多改善 140 倍，CPU 数据传输改善 17 倍。

**让我们深入了解机器学习负载中的一个常见模式：scatter-gather。**

首先安装 compiled graphs：

```
1pip install -U "ray[adag]"
```

scatter-gather 是机器学习负载中常见的分布式计算模式：把相同输入发给多个 worker（Ray Actors），再收集所有 worker 的结果。例如张量并行推理中，程序把相同的 CPU 数据发给所有 actor，actor 将 CPU 数据搬到 GPU 并运行只加载了分片权重的 torch 模型。我们用 Compiled Graphs 来表达这个程序。

先创建普通的 Ray actor，这里是 3 个：

```
1import ray
2from time import perf_counter
3
4@ray.remote
5class TensorProcessor:
6  def fwd(self, tensor: str) -> str:
7    # some_gpu_ops(tensor.to(torch.device()))
8    # In a typical application, this actor will move the 
9    # tensor to GPU and run a torch module. 
10    # We instead do nothing and return the string input immediately for simplicity.
11    return tensor
12
13N = 3
14actors = [TensorProcessor.remote() for _ in range(N)]
```

首先看看如何用普通 Ray 程序表达。

```
1# warmup actors
2for _ in range(10):
3    ray.get([actor.fwd.remote("hello") for actor in actors])
4
5s = perf_counter()
6result = ray.get([actor.fwd.remote("hello") for actor in actors])
7print("Normal ray programs took", (perf_counter() - s) * 1000, "ms")
8print(result)
```

然后，我们定义并编译一个把同一个输入占位符传给所有 actor 的 compiled graph。这里使用 Ray 的 DAG API，它以静态方式构建捕获计算图的中间表示。当输出节点多于一个时，需要使用 [MultiOutputNode](https://docs.ray.io/en/latest/ray-core/ray-dag.html#ray-dag-with-multiple-multioutputnode) 语法包装输出。

```
1import ray.dag
2
3# Define a DAG for lazy execution.
4with ray.dag.InputNode() as inp:
5    # Bind each actor task to the same input placeholder.
6    outputs = [actor.fwd.bind(inp) for actor in actors]
7    dag = ray.dag.MultiOutputNode(outputs)
```

现在要使用 Compiled Graphs，只需调用 `experimental_compile` 命令。Ray 会预先分配运行该图所需的全部资源，相比标准动态运行时执行速度快得多：

```
1compiled_graph = dag.experimental_compile()
2
3# warmup actors
4for _ in range(10):
5    ray.get(compiled_graph.execute("hello"))
6
7# Execute the DAG with different arguments:
8s = perf_counter()
9result = ray.get(compiled_graph.execute("hello"))
10print("Compiled Graphs took", (perf_counter() - s) * 1000, "ms")
11print(result)
12# ["hello", "hello", "hello"]
```

就这样！你可以用同一个程序扩展负载规模。这些 API 在多节点场景下同样有效。

底层机制上，资源被预先分配以降低执行期开销：

- 新的 Compiled Graphs 后端在编译时**静态**地为每个 actor 任务分配输入与输出缓冲区，而不再每次执行 DAG 时动态分配。这些缓冲区在**执行**时**复用**，actor 始终将结果直接**推送**给需要它的进程。
- 同一 Ray 节点上的所有 actor 共享同一块物理输入缓冲区，由 Ray Compiled Graphs 后端负责同步。这减少了任务参数序列化、为参数分配内存以及调用任务带来的单任务开销。
- 后端还会预先分配 actor 的执行循环。每个 actor 不再等待执行下一个任务的 RPC，而是在循环中等待通过已分配缓冲区传入的下一个 `echo` 任务的参数。

那么，如果想在不同 actor 任务之间流水线化执行呢？一个例子是[流水线并行推理](https://docs.vllm.ai/en/latest/serving/distributed_serving.html)：把一个 actor 的中间输出经共享内存传给下一个 actor，数据传输应与计算任务流水线化。我们可以在取回输出之前多次执行同一个 DAG，从而在不同 actor 间流水线化执行：

```
1# Teardown the previous dag.
2compiled_graph.teardown()
3with ray.dag.InputNode() as inp:
4  for actor in actors:
5    # Pass each actor task output as input to the next actor task.
6    inp = actor.fwd.bind(inp)
7  dag = inp
```

我们可以这样编译并执行：

```
1compiled_graph = dag.experimental_compile()
2# Call dag.execute() several times. The executions will be pipelined across the different actors.
3refs = [compiled_graph.execute(f"hello{i}") for i in range(N)]
4# Get the results, flushing the pipeline.
5for ref in refs:
6  print(ray.get(ref))
7# "hello0"
8# "hello1"
9# "hello2"
```

要演示 GPU-GPU 通信，可以构造一个向另一个 actor 发送张量的 actor。运行该示例请确保集群中至少有 2 块 GPU。

```
1import ray
2import ray.dag
3
4import torch
5
6assert ray.cluster_resources().get("GPU") >= 2, ("Insufficient number of GPUs available in the cluster.")
7
8@ray.remote(num_gpus=1)
9class GPUSender:
10  def send(self, shape):
11    return torch.zeros(shape, device="cuda")
12
13@ray.remote(num_gpus=1)
14class GPUReceiver:
15  def recv(self, tensor: torch.Tensor):
16    assert tensor.device.type == "cuda"
17    return tensor.shape
18
19sender = GPUSender.remote()
20receiver = GPUReceiver.remote()
```

接下来，定义并编译一个把 CUDA 张量从一个 actor 传给另一个 actor 的 compiled graph。借助下面的 `TorchTensorType` 类型提示，Ray 会在底层使用 NCCL，通过两块 GPU 之间的 GPU RDMA 传输张量。

```
1from ray.experimental.channel.torch_tensor_type import TorchTensorType
2with ray.dag.InputNode() as inp:
3  dag = sender.send.bind(inp)
4  # You have to specify transport="nccl", otherwise, it uses shared memory to transfer GPU tensors.
5  dag = dag.with_type_hint(TorchTensorType(transport="nccl"))
6  dag = receiver.recv.bind(dag)
7
8compiled_graph = dag.experimental_compile()
9# Execute the DAG. Ray aDAG will orchestrate any NCCL ops.
10assert ray.get(compiled_graph.execute((10, ))) == (10, )
```

## 基准测试

我们在多种通信模式上比较了 Ray Core（图中标注为 "Ray Standard Runtime"）与 Ray Compiled Graphs。

- Round Trip：构造一个 actor 反复向接收 actor 发送数据。
- Scatter-Gather：driver 向所有 actor 发送数据，并收集各 actor 的结果。
- Chain of tasks：构造一条 actor 流水线，每个 actor 从上一个 actor 接收数据并发送给下一个。

首先，为测量系统开销，我们在单节点与多节点上用 1 字节 CPU 数据运行上述计算模式的基准。以下基准运行在有 64 个 CPU 的 m5.16xlarge 实例上。

从下图可见，单节点上的 round trip 通信最快可提速 17 倍，多节点上可提速 2.7 倍。

对于更复杂的负载，如 scatter-gather 或任务链，**我们看到 Ray Compiled Graphs 可将延迟最多改善 20 倍。**

我们还比较了 Ray Core 与 Ray Compiled Graph 的 GPU 到 GPU 传输。我们在带 NVLink（A100）与不带 NVLink（A10G）的机器上，用 40MB CUDA 张量运行简单 round trip 基准，将张量传输 10 次并测量端到端延迟。

默认情况下，Ray Core 既没有对 torch 张量的原生零拷贝序列化支持，也不使用 NCCL 通信。

而 Ray Compiled Graph 在底层使用 NCCL 进行 GPU 到 GPU 传输以优化性能。在没有 NVLink 的 2 块 A10G 机器上，Ray Compiled Graphs 的张量传输延迟比 Ray Core 好 19 倍。**在带 NVLink 的 A100 上，延迟可降低近 140 倍。**

这些基准表明 compiled graphs 是强大的原语，能够打开一整类新兴 AI 应用。

## 使用场景

### 更快的模型并行推理

我们已把[compiled graphs 集成进 vLLM](https://github.com/vllm-project/vllm/issues/6556)——这个流行的开源 LLM 推理项目，使其可以用 Ray 实现张量并行与流水线并行推理。在流水线并行下，相比默认 NCCL 后端我们观察到 10-15% 的吞吐/延迟改善。

### 最先进的分布式训练

在分布式训练实验中，我们利用 Compiled Graphs 实现更复杂高效的训练策略。例如，通过使用异构设备与并行技术，我们显著提升了 CLIP 等多模态对比模型的训练吞吐。用原版 PyTorch 表达这样的程序要困难得多。

具体而言，通过对文本编码器与视觉编码器施加不同的并行方法，并把较小的文本编码器放到性价比更高的 GPU 上，相比 PyTorch 标准 FSDP 实现，我们观察到**训练吞吐提升 20%，token-per-dollar 效率提升 43%**。

我们还原型实现了多种流水线并行调度算法，如 afab、1f1b 和 zero bubble（[https://arxiv.org/pdf/2401.10241](https://arxiv.org/pdf/2401.10241)）。用**不到 70 行代码**即可表达复杂的流水线调度算法，同时在 4×A100 GPU 上的 Llama 7B 模型达到与 Deepspeed 等最先进库相当的性能。我们计划用更大规模负载进一步提升流水线并行训练性能。
