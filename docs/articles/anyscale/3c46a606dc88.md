# 大规模 Ray 任务监控：宣布在任意规模上持久化超过 10k 个任务

作者：[Nikita Vemuri](https://www.anyscale.com/blog?author=nikita-vemuri)、[Mengjin Yan](https://www.anyscale.com/blog?author=mengjin-yan)、[AlanGuo](https://www.anyscale.com/blog?author=alan-guo) 和 [Julian Forero](https://www.anyscale.com/blog?author=julian-forero) | 2025 年 9 月 12 日

今天，我们很高兴地宣布在 Anyscale 上推出持久性 [Ray 任务仪表板](https://docs.anyscale.com/monitoring/task-dashboard/)，它可以对 Ray 工作负载进行可扩展的监控和调试，并且在集群关闭后仍能保持可见性。 Anyscale 上的完全托管仪表板利用新的 Ray Event Export 框架，该框架从 **Ray 2.49 开始提供。**

[任务](https://docs.ray.io/en/latest/ray-core/key-concepts.html#tasks)，远程并行执行的函数，是 Ray 中分布式计算的基础。如果无法清晰地观察任务，诊断瓶颈、调试故障或调整性能很快就会变成猜测，从而减慢迭代速度并增加成本。

现有的 Ray Dashboard 任务视图一直是开发人员流行的工具，但它有两个关键限制：

- **10k 任务限制。** 任务数据存储在 Ray 的全局控制服务 (GCS) 内存中。为了避免系统过载，仅显示最近的 10k 任务，这远远低于大数据和 AI 工作负载的需求。 GCS 约束还限制了事件报告频率，这意味着一些可观测性数据可能会被丢弃。
- **不持久。** 仪表板由头节点提供服务，并在节点终止后消失。在作业完成后保持头节点处于活动状态是当今唯一的解决方法，但这并不具有成本效益。

借助基于 Ray 的事件导出框架构建的 Anyscale 上的任务持久性，开发人员现在可以通过托管仪表板以可扩展、经济高效的方式捕获和分析任务事件。

有关启用仪表板的说明，请参阅[文档](https://docs.anyscale.com/monitoring/task-dashboard#enable-system-cluster)。

## LinkAnyscale 任务仪表板

### LinkFeature 概述

Anyscale 任务仪表板对于 [Ray Core](https://docs.ray.io/en/latest/ray-core/walkthrough.html#what-s-ray-core) 用户特别有用，因此让我们以 Core 工作负载为例，其中任务执行一些工作量，并根据其输入进行配置。仪表板近乎实时更新，允许用户在作业运行时监控作业进度或在作业完成后分析结果。

**高级概述：** 仪表板的第一部分为用户提供了其工作进展情况的快速概述。顶部的摘要面板按状态（例如已完成、失败、正在运行等）提供任务计数的高级摘要。

### 链接架构

在 Anyscale 托管平台上构建持久仪表板时，维护数据隐私是一个关键的设计考虑因素。为了真正有用，仪表板必须包含详细信息，例如堆栈跟踪和函数名称，其中可能包含敏感的用户数据。为了平衡将客户数据保存在自己的云帐户中的要求，同时仍然提供响应迅速且可扩展的用户体验，我们构建了一个专用系统集群来为 Anyscale 任务仪表板提供支持。

![Ray 任务仪表板 - 图 5](https://images.ctfassets.net/xjan103pcp94/1Wz8xlbRUE3UkurOieyipS/d071aa112199b00e5d16572b12cf9722/image_4.png)图 5：将客户数据保存在自己的云帐户中的 Anyscale 任务仪表板的架构

Ray 任务仪表板 - 图 5

系统集群是**每个 Anyscale 云的单个临时实例**，在客户的帐户中运行，并在查看任务仪表板 UI 时保持活动状态。这种方法具有几个主要优点：

- **可扩展的后端：** 系统集群允许我们选择最好的工具，以确保任务仪表板后端根据用户工作负载有效扩展。因此，我们测试了仪表板能否顺利处理数百万个任务。
- **维护数据隐私：** 为任务仪表板提供支持的客户数据既不存储也不通过 Anyscale 控制平面进行流式传输，因为 UI 直接从客户云查询。
- **成本效率：** 由于自动终止策略会在任务仪表板空闲时自动关闭系统集群，因此额外成本保持在最低限度。

## LinkRay 事件导出框架

**任务仪表板的数据来自哪里？**

Ray 始终发出用户可以使用外部系统收集和保存的指标和日志。这些数据源虽然有用，但不足以支持任务仪表板中显示的所有详细视图。日志通常缺乏结构化信息，这使得它们难以转换和查询。另一方面，指标更适合聚合洞察，但添加高基数标签（例如任务 ID）可能会影响查询性能。由于这些限制，Ray 的指标无法提供仪表板中单个任务级别可见性所需的粒度级别。

为了解决这个问题，我们引入了 **Event Export**，这是一个新的开源系统，它会发出描述 Ray 工作负载进度的结构化事件。目前它支持任务事件，我们计划在不久的将来将覆盖范围扩大到 Ray 实体。

为了避免任务事件流量使 GCS 过载，我们在现有任务事件框架的基础上更新了 Ray 的事件发射架构。我们引入了每节点聚合器代理，而不是让每个核心工作人员直接将任务事件发送到 GCS。该代理从其节点上的所有核心工作人员收集事件并将它们转发到用户指定的 HTTP 端点。对于 Anyscale，这些事件被推送到接收器，接收器将它们写入对象存储，从而启用任务仪表板。

![Ray 任务仪表板 - 图 6](https://images.ctfassets.net/xjan103pcp94/KD6pJEXnGrsAUSsNiB93Z/cc6bf5a836ec54ec821d0cec6832c9b5/image_5.png)图 6：Ray 事件导出的架构，每个节点引入一个聚合器代理

Ray 任务仪表板 - 图 6

开源用户还可以通过设置消费者将此数据流式传输到他们选择的任何目的地来利用事件导出框架。发出的每个任务事件都包含重新创建仪表板中显示的任务视图所需的所有元数据和状态转换，因此任何 Ray 用户都可以根据自己的需求构建自定义的持久仪表板。

Ray 2.49 及更高版本中提供了事件导出框架。有关设置说明和示例，请查看官方[文档](https://docs.ray.io/en/master/ray-observability/user-guides/ray-event-export.html)。

## LinkFuture 计划

事件导出框架和系统集群架构是在 Anyscale 平台上构建完全持久的 Ray 仪表板的基础，这将增强用户监控、调试和优化 Ray 工作负载的方式。最终，这些数据还可以实现自动问题检测和工作负载优化。

我们正在积极致力于将来自其他 Ray Core 资源和库组件的事件添加到事件导出框架，并计划在 Anyscale 上推出其他持久仪表板。 Ray Train 和 Data 仪表板最近也发布了（[参见博客文章](https://www.anyscale.com/blog/ray-train-data-dashboard)），我们计划通过指向每个 Ray Data 操作员或 Train 工作人员的持久、详细任务数据的链接来增强它们。
