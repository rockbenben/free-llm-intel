# 大规模 Ray 任务监控：Anyscale 现已支持 1 万个以上任务的持久化

作者：[Nikita Vemuri](https://www.anyscale.com/blog?author=nikita-vemuri)、[Mengjin Yan](https://www.anyscale.com/blog?author=mengjin-yan)、[Alan Guo](https://www.anyscale.com/blog?author=alan-guo) 和 [Julian Forero](https://www.anyscale.com/blog?author=julian-forero) | 2025 年 9 月 12 日

今天我们很高兴地宣布，Anyscale 上推出了支持持久化的 [Ray Task Dashboard](https://docs.anyscale.com/monitoring/task-dashboard/)，它可以对 Ray 工作负载做可扩展的监控与调试，并且在集群关停之后依然保留这些数据。Anyscale 上这个全托管的 dashboard 借助了全新的 Ray Event Export 框架，该框架自 **Ray 2.49** 起提供。

[任务](https://docs.ray.io/en/latest/ray-core/key-concepts.html#tasks)是远程并行执行的函数，也是 Ray 中分布式计算的基础。如果看不清任务内部发生了什么，定位瓶颈、调试故障或调优性能很快就会变成靠猜，既拖慢迭代速度，又推高成本。

现有的 Ray Dashboard 任务视图一直是开发者常用的工具，但它有两个关键限制：

- **只有 1 万个任务的容量。**任务数据保存在 Ray Global Control Service（GCS）的内存里。为了避免系统过载，界面只显示最近 1 万个任务，这远低于大规模数据与 AI 工作负载的需求。GCS 的限制还会压低事件上报的频率，这意味着部分可观测性数据可能丢失。
- **不持久。** dashboard 由头节点对外提供服务，节点一被终止它就随之消失。目前唯一的变通做法是作业跑完之后继续保留头节点，但这并不划算。

借助 Anyscale 上的任务持久化能力——它构建在 Ray 的 Event Export 框架之上——开发者现在可以通过托管 dashboard，以可扩展且成本高效的方式采集并分析任务事件。

开启 dashboard 的步骤见[文档](https://docs.anyscale.com/monitoring/task-dashboard#enable-system-cluster)。

## Anyscale Task Dashboard

### 功能概览

Anyscale 的 task dashboard 对 [Ray Core](https://docs.ray.io/en/latest/ray-core/walkthrough.html#what-s-ray-core) 用户尤其有用，所以我们就拿一个 Core 工作负载当例子：其中的任务各自做一定量的工作，工作量由输入决定。 dashboard 近乎实时地更新，用户既能在作业运行时跟踪进度，也能在作业结束后分析结果。

**整体概览：** dashboard 的第一部分让用户快速了解作业进展如何。顶部的汇总面板按状态（例如 finished、failed、running 等）给出任务数量的总体概览。

### 架构

在 Anyscale 托管平台上做持久化 dashboard 时，数据隐私是关键的设计考量。要真正有用， dashboard 必须包含堆栈跟踪、函数名这类细节信息，而它们有可能带有用户的敏感数据。为了既把客户数据留在客户自己的云账号里，又给出响应快、可扩展的用户体验，我们专门搭建了一个 system cluster 来支撑 Anyscale 的 task dashboard。

![Ray Task Dashboard - 图 5](https://images.ctfassets.net/xjan103pcp94/1Wz8xlbRUE3UkurOieyipS/d071aa112199b00e5d16572b12cf9722/image_4.png)图 5：Anyscale task dashboard 的架构，客户数据始终留在其自己的云账号中

Ray Task Dashboard - 图 5

这个 system cluster 是**每个 Anyscale cloud 一个的临时实例**，运行在客户账号中，并且在有人查看 task dashboard UI 期间保持活跃。这种做法带来几个关键好处：

- **可扩展的后端：** system cluster 让我们能为 task dashboard 后端挑选最合适的工具，确保它随用户负载有效扩展。据此我们已经验证过， dashboard 能够平滑处理数百万个任务。
- **数据隐私有保障：** 支撑 task dashboard 的客户数据既不存储也不流经 Anyscale 控制面，因为 UI 直接向客户云端查询。
- **成本可控：** 由于配置了自动终止策略，system cluster 会在 task dashboard 空闲时自动关停，额外开销保持在极低水平。

## Ray Event Export 框架

**task dashboard 的数据从哪里来？**

Ray 一直在输出指标和日志，用户可以用外部系统把它们收集并持久化。这些数据源虽然有用，却不足以支撑 task dashboard 展示的那些细节视图。日志通常缺少结构化信息，难以转换和查询；指标更适合做聚合洞察，但加上任务 ID 这类高基数标签会影响查询性能。受这些限制所约，Ray 的指标提供不了 dashboard 中单个任务级可见性所需的粒度。

为了解决这个问题，我们推出了 **Event Export**，这是一套全新的开源系统，会输出描述 Ray 工作负载进展的结构化事件。目前它支持任务事件，我们计划在不久之后把覆盖范围扩展到更多 Ray 实体。

为了避免任务事件流量压垮 GCS，我们在现有任务事件框架的基础上更新了 Ray 的事件发射架构。我们不再让每个 core worker 直接把任务事件发给 GCS，而是引入了每节点一个的聚合 agent。这个 agent 收集所在节点上所有 core worker 的事件，并把它们转发到用户指定的 HTTP 端点。在 Anyscale 上，这些事件会被推送给一个接收器，由接收器写入对象存储，从而支撑起 task dashboard。

![Ray Task Dashboard - 图 6](https://images.ctfassets.net/xjan103pcp94/KD6pJEXnGrsAUSsNiB93Z/cc6bf5a836ec54ec821d0cec6832c9b5/image_5.png)图 6：Ray Event Export 的架构，为每个节点引入一个聚合 agent

Ray Task Dashboard - 图 6

开源用户同样可以用起 Event Export 框架：搭建自己的消费者，把这些数据流式传输到任意选择的目的地即可。每条发出的任务事件都包含重建 dashboard 中那个任务视图所需的全部元数据与状态流转，所以任何 Ray 用户都能按自己的需求搭一个自定义的持久化 dashboard。

Event Export 框架在 Ray 2.49 及之后的版本中可用。配置说明与示例见官方[文档](https://docs.ray.io/en/master/ray-observability/user-guides/ray-event-export.html)。

## 后续计划

Event Export 框架与 system cluster 架构共同构成底座，用于在 Anyscale 平台上打造完全持久化的 Ray dashboard，这会改变用户监控、调试和优化 Ray 工作负载的方式。这些数据最终还能支撑自动化的问题检测与工作负载优化。

我们正在积极把其他 Ray Core 资源和库组件的事件也接入 Event Export 框架，并计划在 Anyscale 上推出更多持久化 dashboard。Ray Train 和 Data 的 dashboard 也在近期发布了（[见博客文章](https://www.anyscale.com/blog/ray-train-data-dashboard)），我们计划增强它们，为每个 Ray Data operator 或 Train worker 关联到持久化的详细任务数据。
