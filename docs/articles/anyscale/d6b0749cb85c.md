# Anastasia 如何用 Ray 与 Anyscale 将 ML 流程加速 9 倍

作者：Juan Roberto Honorato | 2021 年 8 月 31 日

*Anastasia 平台上用 AI 进行预测的界面一览。*

*Juan Roberto Honorato 自四年多前 Anastasia.ai 创立起担任 AI Tech Lead，参与开发以 ML 驱动、为客户交付业务解决方案的平台。Anastasia 的使命是让 AI 惠及每家企业（democratize AI），为此需要可扩展且高性价比的技术。近期他也因此成为 Ray 的积极布道者。*

[Anastasia.ai](https://anastasia.ai/) 提供一个强大平台，让组织能以远少于传统所需的资源与投入大规模运转 AI 能力。本文讲述我们遇到的一个需求预测问题，以及用 [Ray](https://docs.ray.io/en/master/) 解决它所取得的惊人结果：与我们的 AWS Batch 实现相比，Ray 实现**快 9 倍**，成本降低 87%。

本文涵盖：

- Anastasia 平台是做什么的。
- 我们最初如何尝试用 Python 内置并行模块解决需求预测问题。
- 我们如何意识到需要快速横向扩展训练与超参数调优。
- Ray 如何帮我们轻松扩展。
- [Anyscale](https://www.anyscale.com/product) 如何让我们把系统进一步优化。

## Anastasia 平台做什么

Anastasia 的客户是各种规模的运营密集型业务，都需要预测未来某件事：需求、缺货、物料使用、备件需求等。我们利用历史数据与上下文信息训练模型，学习其中的动态规律，从而预测未来事件。

举例来说，客户需要预测的事项五花八门：

- ATM 维护要采购多少备件。
- 八月份能卖出多少自行车。
- 沙拉酱产品总共要备多少库存。
- 春季该为某个 SKU（库存单位）进多少件小码 T 恤。

基于既往趋势更好地预测未来销量（或其他事件），客户能显著转型业务：削减开支与浪费、提高利润率。

[Anastasia 平台](https://anastasia.ai/)的核心是我们的 AI Core 库（未来另文详述），其中最闪亮的明星是时间序列预测引擎。我们为每个商品或商品组（分组可由用户控制）训练一个多模型集成，让客户能轻松随实际条件变化持续训练和重训预测模型。

## 最初的纯 Python 方案

起初，每种模型对应一台 EC2 实例，实例内部做并行化。实例 CPU 全部占满。我们最初对结果挺满意，代码也自认高度优化，但很快撞到了天花板。

垂直扩展已到极限，大机器意味着高成本。我们没法缩容，成本不断累积。此外，大数据处理要等很久。我们还担心厂商锁定，希望有一套更灵活、可以长期在其上构建的系统。

## 横向扩展的需求

我们下一次尝试是用 AWS Batch 做横向扩展。不幸的是，这需要大规模代码改动，而且即便如此也无法自动扩缩，也无法使用 [spot 实例](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/using-spot-instances.html)。

我们还考虑过其他几个方案：

- **AWS Batch 多节点并行作业：** 容错很难做。
- **AWS EMR：** 看起来是为 Spark 负载设计的，我们觉得开销太高。
- **AWS SageMaker：** 我们觉得它死板、扩展性难以摸清；除非用内置算法，否则扩展不直观；还有 serving endpoint 的高成本。我们也担心厂商锁定。

最终我们选择了 [Ray 项目](https://github.com/ray-project/ray)及其[内置 autoscaler](https://docs.ray.io/en/releases-0.8.2/autoscaling.html)。用 Ray 只需很小的代码改动，autoscaler 就优雅地解决了我们的扩展与成本问题，且没有任何额外负担。

最重要的是，它解锁了 [Ray Tune](https://docs.ray.io/en/latest/tune/index.html) 用于超参数搜索，帮我们调优模型、取得最佳表现。它与训练以及 SigOpt、HyperOpt 等多种超参数搜索优化引擎无缝集成。

## Ray 如何帮我们轻松扩展

*我们用 Ray 扩展问题的粗略示意。*

客户一旦启动预测作业，我们的系统就把时间序列生成数值特征格式，喂给 Ray 上的 ML 流程 actor。我们为每个商品或商品组训练一个由多个模型组成的集成。

我们发现，与其用上客户数据集中的所有时间序列，不如对其中最相关的时间序列样本做子采样并跑超参数搜索。我们观察到，选出的时间序列代表了大部分趋势，让我们 a) 削减训练时间/成本，b) 防止过拟合。

随后启动 ML 流水线，训练好的模型序列化到 S3。这套实现缩短了开发新模型的时间——凡能在 Python 里跑的东西都和 Ray 配合良好，且开箱即得扩展能力。

## Ray Tune 在超参数搜索上的优势

训练模型时最终会使用 [Ray Tune](https://docs.ray.io/en/master/tune/index.html)。它是包装既有训练代码的简便方式，且按模型类型可选用最合适的搜索器：

- 对更复杂的 XGBoost 与 RNN 模型，使用[跑在 Ray Tune 上的 SigOpt](https://sigopt.com/blog/integrating-sigopt-and-raytune/)
- 对简单统计模型，使用[跑在 Ray Tune 上的 HyperOpt](https://docs.ray.io/en/master/tune/getting-started.html#a-basic-tune-tutorial)

Ray Tune 帮助把计算分发到各 worker，并促进 worker 间通信。各 worker 随后按所用搜索器（SigOpt 或 HyperOpt）推荐的下一组超参数执行。

我们没有找到其他开源超参数搜索框架能把分布式执行简化到这个程度。Ray Tune 让我们免于为搜索任务管理和扩缩云资源。

## 用 Ray 后立竿见影的回报

运行 Ray 实现并测量结果后，我们非常满意：

- 通过减少所用 CPU 核心数降低了成本。
- 结果更快——不再是一个模型对应一个 Batch 实例，而是所有实例服务于所有模型。也就是说所有机器始终都在被使用。
- 每核速度有肉眼可见的提升。

*纯 Python 与 Ray 对比。*

总体而言，对一个由 10 万条时间序列、每条 120 个数据点、384 个 CPU 核心组成的测试作业，与 AWS Batch 实现相比，我们的 Ray 实现快 9 倍、成本降低 87%（假如原本花 $100，现在只要 $13！）。

## 用 Anyscale 获得进一步提速

最初我们找过 Anyscale 的 Ray 开发者帮忙设计系统。随着时间推移，我们决定试用他们的托管平台，发现了若干优势。

使用托管平台永远是在成本与自身开发时间、资源、人力之间权衡。我们想专注于核心能力，而不是基础设施管理和运维。这正是 Anyscale 带来的收益。

Anyscale 在多个方面加速了我们的开发循环：

- 用 Ray Client 起新集群更快。
- 在 Anyscale 托管的集群上运行本地代码，只需改一个环境变量（RAY_ADDRESS=<cluster address>）那么简单。
- 作业治理：谁在何时做了什么，一目了然。
- 持久且清晰的日志：代码逻辑、集群自动扩缩、虚拟环境等。
- 借助简易的 CI/CD 集成自动管理代码依赖。
- 接近生产环境的测试环境。

我们还发现 Anyscale 团队的响应极其迅速，平台对新版 Ray 的支持从容平滑，让我们始终用上新特性，而不必担心出问题。
