# 将 Ray 的 AI 负载扩展到 1 万节点集群

作者：Yicheng Lu | 2026 年 8 月 25 日

***感谢以下人士对本工作的贡献、基准测试与评审：Edward Oakes、Mengjin Yan、Kartica Modi、Dhyey Shah、Josh Lee、Zac Policzer、Steve Alexander、Andrew Sy Kim（Google）、Mao Yancan（ByteDance）***

随着 Ray 被用于越来越多的新兴 AI 负载，我们观察到用户正从两个方向把 Ray Core 逼到极限：

- **批量推理、shuffle 及其他数据流水线：** 这类负载中，driver 管理着百万级对象的生命周期，同时调度循环处在关键路径上，限制了其持续任务吞吐。
- **大规模 RL 与 pre-/post-training：** 运行在 2,000 到 10,000 节点的集群上，数万个 actor 在网络拓扑约束下被调度。启动时间、故障后的重启时间对这类用户至关重要。

我们发现瓶颈反复落在三类：

- 线程之间的锁争用。
- 单个线程被异步工作压垮。
- 在过期的资源视图上做调度。

经过一轮 Ray Core 改进，与去年相比这些负载的现状如下：

- 500 节点批量推理端到端提速 **23%**。
- Ray Data shuffle 端到端提速 **24%**。
- 现在 Ray 能在更大、带拓扑约束的训练集群上启动更多 actor：2,000 节点下 placement group 就绪提速 **62 倍**；10,000 节点下提速 **303 倍**；2,000 节点下端到端 actor 启动提速 **6.5 倍**。可在 10,000 节点集群上扩展至 4 万个 actor——这是一年前无法支撑的规模。

本文余下部分逐一讲述我们如何发现每个瓶颈、如何应对。先从 driver 内部的数据流水线讲起，然后转到 10,000 节点的训练集群——上面三类瓶颈在两个故事里反复出现。

## 当 Driver 成为瓶颈

起初是 Ray Data 抛出的谜题：批量推理与 shuffle 流水线在 Ray Core 调用内部损失时间，调度循环随之变慢，持续任务吞吐与端到端时间都受拖累。但单独测量这些调用时，`ray.wait` 及其他 Ray Core API 都很快。那么时间去哪了？

要回答这个问题，我们跟踪一个对象的一生。百万个对象走的都是同一条路。

*图 1：一个对象的生命周期*

如图 1 所示，Ray driver 进程中有两个线程与我们的故事有关。Python 线程跑你自己的代码，如 `ray.wait` 和调度逻辑。C 线程是 Ray Core 的后台线程，处理所有异步工作。

看图 1 的 Python 线程部分：你调用 `f.remote()` 提交任务，拿回一个对象引用（ref），等待对象就绪（真实的 Ray Data 调度循环使用超时并持续检查），然后把 ref 传给下游其他任务。最后，对象用完、再没人需要它时，你丢掉这个 ref。

再看幕后。当你调用 `ray.wait`（一个 Ray Core API）时，它会让你的线程在对象的就绪条件变量上睡眠等待。任务在 worker 节点 A 上运行，输出对象存在 A 上。理想的等待时间应恰好等于任务运行时间。任务结束后 C 线程收到通知，做完记账（包括记录对象位置），然后唤醒 Python 线程。

接着你把 ref 传给下游任务 g。g 被调度到 worker 节点 B，B 需要知道对象在哪，于是订阅该对象的位置。C 线程此前记录了这个位置，现在把它发布出去。节点 B 从节点 A 拉取对象，任务 g 运行。

而幕后那次"丢弃"让对象引用计数归零，触发清理：向仍在等待该对象位置的人发布失败消息，让他们停止等待、放弃拉取，并释放集群中的所有副本。有了上面的背景，我们来看在 driver 中发现的瓶颈及解决方式。

### 两个线程，一把锁

*图 2：两个线程争抢同一把发布锁*

从上面的对象生命周期可见，两个线程都要发布对象更新，而所有发布操作由一把 publish lock 保护。如图 2，丢弃最后一个 ref 时，Python 线程需要抢这把锁；与此同时，C 线程需要同一把锁来发布对象位置。

两个线程、一把锁，在规模下导致严重争用。批量推理的特性决定了一直有对象在被拉取，因此 C 线程不断拿锁发布对象位置；同时对象用完就被持续丢弃，Python 线程也不断需要拿锁发布失败消息。在一个 500 节点的批量推理负载上，仅 publish lock 就吃掉了调度循环 17.4% 的时间。

对这类锁争用的解法，是把所有相关工作投递到单一线程。我们把每一次发布——包括那条失败消息——都移到 C 线程，Python 线程从此无需再碰发布锁，性能剖析里的锁争用随即消失。

### 不堪重负的单个线程

*图 3：C 线程过载时额外阻塞的时间*

第二个瓶颈藏在对象生命周期旅程的中间，就在 `ray.wait` 本身里。如图 3，你在 `ray.wait` 上花的时间不仅取决于对象产出多快，还取决于 C 线程多忙。等待时间中蓝色部分来自任务执行；红色部分是额外阻塞。当你的对象就绪时，C 线程可能还在处理大量其他对象的位置更新及各种杂务——这些全都排在 C 线程操作队列里唤醒操作之前。实测表明，这个队列延迟正是变慢的头号元凶。于是我们顺藤摸瓜，发现了两个问题。

第一个问题是 C 线程上海量的小回调。单个回调很便宜，但你投递几百万个时，投递本身就是性能杀手。在一次 shuffle 运行中，这类回调超过一百万个，占去 C 线程约 17% 的时间；每个回调执行仅 0.04 毫秒，却平均排队等了 5.7 秒。

追查发现这些回调大多是参数检查。任务提交前，每个参数都必须确认已在集群中某处产出——每个参数一个回调——而 shuffle 的 reduce 任务参数数量极其庞大。但 reduce 只有在全部 map 任务完成后才会开始，所以那些参数其实早就该产出完了。

问题在于：driver 过去即便参数在任务创建那一刻就已就绪，也会投递回调——为了规避一个潜在死锁。修复方案确保所有加锁都是安全的，仅当参数在任务创建时尚未就绪才投递异步检查。仅此一项就让 shuffle 端到端快了 9.2%。

第二个问题直接从剖析中跳了出来：C 线程三分之二的时间都在向其他节点发布对象位置更新。调查显示，每个节点上的每个任务都会订阅其参数的位置。但如果对象已经在本地节点上，任务根本无需订阅它的位置；而且 Ray 按数据就近调度任务，对象恰好在本地的概率相当高。我们做出改进：对已在本地的对象跳过订阅请求，driver 的发布流量随之减半。

与许多此处未能尽述的改进一起，这些修复把持续任务吞吐提升至多 1.6 倍。结果：批量推理流水线在 500 节点上端到端快了 23%，shuffle 快了 24%。

更长期来看，我们正在把 C 线程拆分为多个线程，进一步为 Ray Core 提速。

## 为大规模训练扩展

除了上述 Ray Data 负载，越来越多用户告诉我们：actor 的启动与重启时间才是他们大规模 RL 与 pre-/post-training 负载的限制因素。GPU 空转是昂贵的浪费，而且他们要付出多次——启动时一次，每次故障再来一次，因为 NCCL communicator 是全有或全无，死一个节点就意味着所有 actor 全部重启。

他们同样关心网络拓扑约束：actor 之间的数据传输速度对训练性能影响巨大，而表达约束的首选方式是 Ray 的拓扑感知 placement group 调度。例如使用 NVIDIA GB200 或 GB300 NVL72 机架时，常见配置是每个 18 节点机架一个 placement group，每节点一个 bundle，每个 bundle 里 4 个 actor，对应机架中的一块 GPU——18×4 恰好是 NVL72 的 72。

因此，为了按当前及未来的规模支撑 RL 与 pre-/post-training 负载，Ray 首先要向 10,000 节点级别扩展，然后让 placement group 调度与 actor 调度足够快。

### 在 10,000 节点下保持 GCS 稳定

GCS（Ray 的全局控制服务）位于控制面中心，承担的关键工作包括：

- 节点管理
- Actor 生命周期管理
- 提供内部键值存储
- 为 autoscaler 收集需求
- Placement group 调度

这些工作过去全部共享一个主线程，且其中很多开销随节点数增长。这正是第二类瓶颈——不堪重负的单个线程。事实上用户负载还没来，GCS 主线程就已经很忙了。所以当 actor 或 placement group 负载到来时，GCS 很快成为瓶颈并轻易被压垮。

我们把 GCS 改成多线程，使其能随集群扩展、承载 actor 负载。节点状态广播、内部键值存储、autoscaler 待处理需求收集，各自移到独立线程。

我们还减轻了留在 GCS 上的负担：节点变更订阅从 O(workers) 降到 O(nodes)；placement group 的 bundle 信息改为缓存，不再在 actor 提交时向 GCS 查询；启用 task events 后事件完全移出 GCS，直接流向 dashboard。

空闲负载现在是这个状态：在去年的 Ray（2.51）上，一个 10,000 节点、零作业提交的集群就已让 GCS 主线程约 61% 繁忙；而在今天的 nightly 上，同样的空闲集群约 38%。

结果是 GCS 在 10,000 节点下保持稳定。但这并不自动意味着调度变快——那是另一个问题。

### Ray 的分布式调度

Ray 的调度是分布式的。每个节点都能做调度，这意味着每个节点都必须知道整个集群的资源。如图 4，每个节点维护自己的本地资源视图，本地视图就是事实来源。任何变更时，节点对自己的资源视图做快照并把快照发给 GCS。GCS 汇总所有信息，再把每个变更扇出到每个节点，于是每个节点最终持有其他所有节点的资源视图。在 Ray 内部，这个传输服务叫 syncer。

*图 4：资源视图如何流转*

现在跟着一次简单的任务提交看 Ray 如何调度。提交者先把请求发给一个节点——原则上可以是任意节点，实践中通常是提交者所在的节点，或持有该任务大部分数据的节点。假设是节点 A。A 先检查能否本地放置任务；不行就根据其集群资源视图挑一个节点，本例是节点 B。A 随后乐观地从自己的视图里扣减该任务所需资源，并把决定交回提交者。提交者把请求发给节点 B，同样的流程继续。这次 B 接受、真实分配资源，任务在节点 B 上运行。

*图 5：Ray 如何调度一个任务*

注意这个设计依赖什么。节点 A 基于资源视图做决定，而视图可能过期，决定就可能是错的。此时提交者把请求发到节点 B，B 拒绝，我们重新调度。我们依赖 syncer 送达最新资源视图，依赖它纠正节点 A 错误的乐观扣减。这份依赖正是第三瓶颈的所在。syncer 一落后，上面这一切就都是在过期视图上调度。

### Placement Group：从数小时到数秒

规模下的 placement group 调度端到端很慢。一个原因直接来自上述设计。还记得乐观扣减，以及出错时由 syncer 纠正它的机制。有一个漏洞 syncer 无法覆盖，图 6 从头到尾走一遍：从节点 A 把请求交回提交者的那一刻起，A 就不再跟踪它，但 A 已在自己的视图里乐观扣减了节点 B 的资源。纠正错误扣减的唯一途径是 syncer 更新。于是若请求被提交者丢弃、或提交者死亡，节点 B 上什么都没发生，没有任何事件触发 syncer，节点 A 的扣减就永久泄漏了。

*图 6：请求永不到达时，扣减就泄漏*

为在 Ray 中解决这个问题，过去每三秒，每个节点都会把本地修改过的视图重置回上一次收到的快照；而 GCS 也在自己的资源视图上调度 placement group，同样如此。平时这无害，因为 syncer 远快于三秒，新快照持续到达。然而在大规模下 syncer 变慢，这份"保险"本身成了问题。placement group 通常在集群刚启动时就创建，于是每个节点上报的快照都显示集群在 init 时是空的。每三秒一次重置让已占用的资源看起来又空闲了，调度器其实根本没在调度，只是一直把 placement group 送进已经占满的节点，直到 syncer 追上来。

但 placement group 真的需要这个重置吗？事实上 placement group 调度与 Ray 的其他调度不同。如图 7 所示，placement group 走两阶段提交，且只能由 GCS 调度。GCS 先 prepare——尝试从各节点预留全部资源，只有所有预留都成功才 commit。与 actor 或任务请求不同，placement group 请求从不经由他人转发，而且得益于两阶段提交，GCS 始终知道它是否成功。所以 GCS 根本不需要这份保险。仅仅删掉 GCS 上的重置代码，10,000 节点下的 placement group 调度就收敛到秒级。

*图 7：Placement group 通过两阶段提交*

慢的另一部分是检查 placement group 就绪状态带来的开销。`pg.ready()` 是用户检查 placement group 是否就绪的 API。听起来只是个简单检查，但底层它过去会向 placement group 里提交一个 dummy task。任务能被调度进去就说明组已就绪；而任务天然返回 ref，`pg.ready()` 因此免费变成了异步 API。但这个捷径有真实代价：dummy task 会继承你作业的 runtime environment，于是一个简单资源检查可能要干等着装完 torch。而且该 API 每个 placement group 返回一个 ref，天然招致串行循环。我们发现很多用户这样写：

```
for pg in pgs:
    ray.get(pg.ready())
```

但每个 `ray.get` 都阻塞在自己的 dummy task 上，检查只能一个接一个：上一个 dummy task 结束才提交下一个。一千个组就是一千次串行往返。现在，`pg.ready()` 是对 GCS 的直接异步查询。它仍返回同样的 `ObjectRef`，但背后不再有任务，开销消失。

以上所有努力换来的成果——同样的 placement group 创建，从 200 到 10,000 节点，每 18 节点机架一组、每节点一个 bundle——在去年的 Ray 与今天的 nightly 上的对比：

### Actor 调度：落后事实数分钟

placement group 降到秒级后，在拓扑感知 placement group 内启动 actor 在 10,000 节点规模仍然慢。我们并行推进两条路径，分别解决下面两个问题。

第一个问题是 syncer 本身慢。Ray 假设每个节点都能做调度决策，因此如图 9，变更从每个节点扇入 GCS，再各自扇出到全部 10,000 个节点。这让 syncer 不堪重负，节点常常持有过期资源视图、做出糟糕决策。

*图 9：10,000 节点下 syncer 跟不上*

过期视图以两种方式伤害 actor，在 placement group 场景尤其明显。actor 调度通常经由 head node。拓扑感知 placement group 放置完成后，head node 需要拿到 placement group 的资源信息才能把 actor 调度进去。而 placement group 的资源最初只存在于持有它们的节点上，要靠 syncer 传播给 head node。syncer 慢——在 10,000 节点规模下我们看到高峰期传播约需 200 秒。所以在 placement group 信息到达之前，head node 根本无从调度。

信息到达后，head node 仍是在过期视图上调度，因为 syncer 往往送不快，三秒重置又让视图更旧。两者共同把 head node 推向错误决策：把 actor 送往已经占满的节点。于是出现拒绝与重调度；随着集群填满情况更糟，末尾出现越来越多的重调度。这条长尾我们直接观测到了。

为解决这个问题，我们正朝更中心化的调度机制演进。多数 Ray 负载其实只需要少数节点做调度决策，因此我们正在收回这个设计最初的假设——每个节点都能调度。一旦决策集中化，就只有少数节点需要整个集群的资源视图，syncer 负担更轻、视图更准，今天由过期视图造成的大部分拒绝随之消失。

第二个问题是：一个 actor 今天有两个"大脑"。GCS 决定它何时创建、重启、销毁；而 owner（通常是 driver）持有引用，知道还有谁在用。每次 actor 启动都要为这两个大脑之间的对话买单，图 10 完整走了一遍：从注册 actor、到对 actor 引用计数的常驻订阅、再到取回其地址，owner 与 GCS 之间至少四条消息。重启同样受累。记住，对训练负载一个 actor 死亡意味着全部 actor 死掉重启。数万个常驻订阅在同一时刻轰回 GCS，而重启要完整重放整段对话——每个 actor 一次，而且是同时再来一遍。

*图 10：Driver 与 GCS 之间的对话*

为了解决上述问题，我们正努力的方向是把 actor 生命周期移出 GCS、交给 owner。actor 生命周期管理最初放在 GCS 的原因是为了 detached actor：它们的生命周期独立于 driver，必须在 driver 死亡后存活。对非 detached actor，一旦生命周期归 owner 所有，这段对话的延迟就彻底消失。

下面的收益来自前述 GCS 与 placement group 工作，加上上述两条路径的早期成果——其中包括一项社区贡献：让 syncer 在可行时成批发送同步消息。所有努力叠加的效果——创建拓扑感知 placement group 再把 actor 调度进去——在去年的 Ray 与今天的 nightly 上：
