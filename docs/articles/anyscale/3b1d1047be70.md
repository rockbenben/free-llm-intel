# 用 Anyscale 上全量持久化的 Cluster 和 Actor Dashboards 监控、调试 Ray 工作负载

作者：[Carolyn Wang](https://www.anyscale.com/blog?author=carolyn-wang)、[Alan Guo](https://www.anyscale.com/blog?author=alan-guo)、[Geetanjali Garg](https://www.anyscale.com/blog?author=geetanjali-garg) 和 [Philip Wang](https://www.anyscale.com/blog?author=philip-wang) | 2026 年 5 月 15 日

今天，我们很高兴宣布推出 **Anyscale Cluster and Actor Dashboards**，这标志着 **全量持久化的 Ray Dashboard** 在 Anyscale 上完成全面推出。本次发布连同 [**Train**、**Data**](https://www.anyscale.com/blog/ray-train-data-dashboard) 和 [**Task**](https://www.anyscale.com/blog/ray-task-monitoring-persistent-logs) Dashboard，为 Ray 工作负载提供端到端的监控、调试和优化工具：从基础设施级监控到工作负载级洞察，所有数据都会持久化保留，供工作负载完成后的历史分析使用。

| **Dashboard** | **关注点** | **你能做什么** |
| --- | --- | --- |
| **Train** | 模型训练 | 监控进度、错误和性能剖析数据 |
| **Data** | 数据管道 | 通过 operator metrics 定位瓶颈 |
| **Task** | 分布式工作负载 | 分析数百万个分布式任务 |
| **Actor** | 分布式有状态工作负载 | 跟踪 actor 生命周期和性能 |
| **Cluster** | 基础设施 | 监控 node 健康状况和利用率 |

## 介绍 Cluster and Actor Dashboards

长期以来，Ray Dashboard 一直是了解分布式工作负载当前状态的重要工具：应用正在做什么（task、actor），以及运行得怎么样（node、硬件利用率）。不过，Ray Dashboard 有几个重要局限：

- **临时数据**：Ray 集群一旦关闭，所有 Dashboard 数据都会丢失。拿不到这些数据，事后排查就很困难，往往得从头复现问题——对于长时间运行或大规模的 job，这既昂贵又耗时。
- **规模有限 / 留存时间短**：为避免影响正在运行的工作负载，Ray 集群 Dashboard 只存储一部分数据。已失效 node 的数据仅保留 10 分钟，被终止的 actor 也只保留最近 100,000 个。

当工作负载扩展到数百个 node、数百万个 task 时，这些局限便不足以支撑现代 AI 与数据工作负载。

全新的 **Anyscale** **Cluster and Actor Dashboards** 不仅解决了这些局限，也改善了 Ray 工作负载整体的可观测性体验。这些 Dashboard 由 [**Ray Event Export Framework**](https://www.anyscale.com/blog/ray-task-monitoring-persistent-logs#ray-event-export-framework) 驱动，把集群事件以流式方式导出到集群之外，持久化到 Anyscale 托管的存储和查询引擎中，供长期分析使用。如此一来，开发者即便在集群终止之后，也能调试故障、分析性能、对比不同工作负载，而不必自己维护一套基础设施。

#### 主要改进包括：

- **全量持久化** – 即便集群关闭，数据依然可用，支持事后调试。
- **可扩展性** – 面向大规模 Ray 部署设计，可应对数千个 node、数百万个 actor。
- **增强的 UX** – 过滤、搜索和聚合更快，并新增可视化与历史信息，帮助你掌握集群拓扑和 actor 生命周期随时间的变化。
- **统一且可交互** – 工作负载 Dashboard（Train、Data）与系统 Dashboard（Cluster、Task、Actor）之间可无缝跳转，串起一条从整体概览到 node 级细节的统一调试路径。

## 端到端调试一条 Ray Data 嵌入管道

我们用一个调试场景，看看工作负载级的 Data、Train Dashboard，系统级的 Cluster dashboard，以及核心级的 Task、Actor Dashboard 在实践中如何配合。这个场景里，一条 Ray Data 管道耗时远超预期，而我们要在 job 已经完成之后，借助这些持久化的 Dashboard 找出原因。

Ray Data 在 Ray 之上提供高层 dataset API，简化了分布式数据处理。开发者通常从 Data dashboard 开始调试，它先给出 job 级上下文，再逐层下钻到系统级细节。

### 这条管道

我们用 Ray Data 搭建一条两阶段的音频嵌入管道。第一阶段在 CPU 上用 librosa 把原始音频片段转换成频谱图（声音的可视化表示，展示频率随时间的变化）。大规模处理音频数据时，必须先对原始音频解码、重采样到统一的采样率，再转换成适合 ML 模型的格式。这一步频谱图转换计算开销很大（CPU 密集），是音频 ML 的标准预处理，就像图像在送入视觉模型前要调整尺寸、做归一化一样。第二阶段在 GPU 上用 ViT-B/16 从这些频谱图里提取嵌入，供相似度搜索、聚类、流派分类等下游任务使用。

```
ds = ray.data.from_huggingface(hf_dataset)  # lewtun/music_genres
ds = ds.limit(19_000)
ds = ds.repartition(128)
ds = ds.random_shuffle()

# Stage 1: mel spectrogram extraction on CPU (8 actors, librosa + mel filterbank)
ds = ds.map_batches(SpectrogramExtractor, batch_size=16,
                    compute=ray.data.ActorPoolStrategy(size=8))

# Stage 2: ViT-B/16 embedding on GPU (1 actor, ~330 MB model)
ds = ds.map_batches(SpectrogramViTEmbedder, batch_size=64,
                    compute=ray.data.ActorPoolStrategy(size=1), num_gpus=1)
ds.write_parquet("/mnt/cluster_storage/audio_demo/output/")
```

这个集群有 1 个 CPU worker node（m5.2xlarge：8 CPU、32 GB RAM）和 1 个 GPU worker node（g4dn.xlarge：4 CPU、16 GB RAM、1× T4）。我们把频谱图提取阶段的 actor 并发度设为 8，好让这段 CPU 密集的工作保持高吞吐。

我们提交了包含 19,000 个音乐片段的 job。按现有基准，预计 10 分钟左右就能跑完，结果却用了一个多小时。job 成功了，所有嵌入也都写入了，但显然哪里出了问题。到底发生了什么？

### **第 1 步：Data Dashboard - 管道到底什么时候才真正产出输出？**

我们先看这个已完成 job 的 Data dashboard，它从 Ray 库级别给出工作负载概览，为进一步下钻到系统级、核心级 Dashboard 先建立好上下文。由于 Anyscale Dashboard 的数据在集群生命周期结束后依然保留，即便 job 已经完成，所有 metrics 仍可查看。

观察 operator metrics 随时间的变化，规律立刻显得可疑：

- `MapBatches(SpectrogramExtractor):` 从一开始就持续有吞吐，整个运行过程稳定地处理音频片段。
- `MapBatches(SpectrogramViTEmbedder):` 一个多小时里输出 0 行，直到最后五分钟才突然活跃起来。输入队列大小一直稳步增长，直到最后五分钟。所有嵌入都在收尾那一刻才产出。
- `Write:` 同样的规律 - 直到最后一刻才写入任何内容。

![Data dashboard 中针对 SpectrogramViTEmbedder data operator 的 metrics 视图。](https://images.ctfassets.net/xjan103pcp94/2BhAodCjw0JpOSMJJKu8JB/652a926f4a54692c455160ff464d50ec/image2.png)图 6：Data dashboard 中针对 SpectrogramViTEmbedder data operator 的 metrics 视图。

Data dashboard 中针对 SpectrogramViTEmbedder data operator 的 metrics 视图。

频谱图提取阶段几乎占满了整个 job 的运行时间，嵌入阶段却直到尾声才开始产出。这意味着 GPU 这个集群里最昂贵的资源，整整一个多小时完全空转。这直接变成了白花的钱：GPU node 全程开机计费，直到最后几分钟才真正干点活。嵌入阶段一直拿不到资源，直到提取 actor 释放了 GPU node 上的 CPU slot；于是管道实际上被串行化了 – 先跑完所有 CPU 活，再跑所有 GPU 活 – 把 Ray 本该提供的流水线并行优势全部丢光。

### 第 2 步：Task Dashboard - 为什么嵌入毫无进展？

想看这些 task 的聚合数据，我们切到 **Task dashboard**，可以看到：

- `SpectrogramExtractor` task 平均执行时间 20s。
- `SpectrogramViTEmbedder` task 平均执行时间不到 1s。

这些 task 一旦启动就跑得很正常，执行时间正常，也没有记录下任何错误。既然执行本身不是问题，瓶颈一定出在更早的环节：actor 还没有被调度。为什么？

### 第 3 步：Actor Dashboard - 嵌入 actor 为什么被延迟？

下一步来到 Actor dashboard，在这里能找到 SpectrogramViTEmbedder operator 对应的 actor。点进 actor 详情页，就能看到 Actor Events 时间线：

![SpectrogramViTEmbedder actor 的 Actor 详情页。](https://images.ctfassets.net/xjan103pcp94/193kd6ipbhjzLbXrJxD2Nf/c76bbe3dc40291ca987e69b85d9030cd/image6.png)图 9：SpectrogramViTEmbedder actor 的 Actor 详情页。

SpectrogramViTEmbedder actor 的 Actor 详情页。

这个 actor 等待调度等了一个多小时。它没有失败，也没有崩溃，只是在等一个空出来的 CPU slot 才能被调度。等到 14:09 终于被调度后，它只跑了几分钟，就顺利完成了全部嵌入工作。

它申请的资源是 `{"CPU": 1.0, "GPU": 1.0}`。GPU 全程空闲（没有别的任务会用它）。所以瓶颈不是 GPU，而是 CPU。这个 actor 在 GPU node 上找不到空闲的 CPU slot。

### 第 4 步：Cluster Dashboard - CPU slot 去哪儿了？

在 actor 详情页里点开 Node ID 链接，就跳到 Cluster dashboard 中这个 GPU node（g4dn.xlarge）的 node 详情视图。

![GPU node 的 node 详情页。](https://images.ctfassets.net/xjan103pcp94/5ozS9nZuGCO53mq0bkdPR5/df1bdd11057561fe64e13658ff7faea8/image5.png)图 10：GPU node 的 node 详情页。

GPU node 的 node 详情页。

![图 11：限定到 GPU node 的 Actor 表。](https://images.ctfassets.net/xjan103pcp94/67YQYyzofPQxGG9oOCc3nt/3ff257c6e28c477639d434120f2f6143/image12.png)限定到 GPU node 的 Actor 表。

图 11：限定到 GPU node 的 Actor 表。

这个 GPU node 有 4 个 CPU 和 1 个 GPU，打开 actors 选项卡，问题出在哪儿就一目了然了：4 个 `SpectrogramExtractor` actor 被调度到了这个 node 上，每个占掉一个 CPU slot，四个 slot 全部占满。而嵌入 actor 启动时同样需要一个 CPU，于是它根本无处可启动。

时间戳印证了整条事件链：那 4 个提取 actor 一直存活到 ~14:09；提取 actor 一结束、释放出 CPU slot，嵌入 actor 立刻就被调度了。

顺着 Anyscale Dashboard，我们查清并定位了根因：`concurrency=8` 个提取 actor 各申请 1 个 CPU，Ray 把它们均匀铺到集群里可用的 CPU slot 上：4 个落在 CPU node（8 个 CPU），4 个落在 GPU node（4 个 CPU）。等到 GPU actor 想启动时，唯一带 GPU 的那个 node 上已经没有空闲的 CPU slot。嵌入 actor 等了将近一个小时，直到提取阶段跑完、释放出 CPU slot，才终于被调度到这个 node 上。

### 修复方案

根因在于 Ray 把 4 个 `SpectrogramExtractor` actor 调度到了 GPU node 上，把可用的 CPU slot 占了个精光，嵌入 actor 因此始终起不来。要修这个问题，有以下几种推荐做法：

**1. 降低预处理并发度：**

```
ds = ds.map_batches(
    SpectrogramExtractor,
    batch_size=32, 
    compute=ray.data.ActorPoolStrategy(size=6),
)
```

这样 Ray 会把 actor 分配成 CPU node 上 3 个、GPU node 上 3 个。于是 `SpectrogramExtractor` actor 在 GPU node 上只占 4 个 CPU 里的 3 个。

![修复后频谱图嵌入管道的 Data dashboard 视图。](https://images.ctfassets.net/xjan103pcp94/7ySbj9RLLryGW6Cvkh7PxU/362d0290ca8989e665559fc36a6274f2/image7.png)图 12：修复后频谱图嵌入管道的 Data dashboard 视图。

修复后频谱图嵌入管道的 Data dashboard 视图。

**2. 用调度标签把工作负载隔离开：**

```
# In the Anyscale cluster config, label the CPU node with {"workload": "cpu-extraction"} 

.map_batches(
    SpectrogramExtractor,
    batch_size=32,
    compute=ray.data.ActorPoolStrategy(size=6),
    label_selectors={"workload": "cpu-extraction"},
)
```

这种做法把提取 actor 明确钉在 CPU node 上，无论 GPU node 有多少空闲容量，都不会落到它上面，从而保证 GPU node 始终有空闲的 CPU slot。保障最强，但也最死板 – 哪怕 GPU node 的 CPU 闲着，提取任务也永远用不上。

放置位置明确之后，并发度就成了一个可独立调节的参数。这里我们把提取 actor 数量保持在 6，给该 node 上的其他 task 留出 CPU 余量，但具体数值仍应按吞吐调优。

**3. 用 resources 定向放置工作负载：**

```
# In the Anyscale cluster config, add resources to the CPU node with {"extraction-cpu": 8} and to the GPU node with {"extraction-cpu": 2}

ds = ds.map_batches(
    SpectrogramExtractor,
    batch_size=32,
    compute=ray.data.ActorPoolStrategy(size=6),
    resources={"extraction-cpu": 1},
)
```

这给每个 node 上能跑多少个提取 actor 划定了明确的放置额度。GPU node 上的 CPU 提取最多占 2 个 CPU，另外 2 个 CPU 留给 GPU actor。它比标签更灵活 – GPU node 仍可在有上限的范围内分担一部分提取工作。

### 关键要点

这个 bug 格外棘手的地方在于，孤立地看，没有一处有问题：管道代码没错，集群总资源充足，每一项配置单独看都合理。问题只从 actor 放置、每个 actor 申请的 CPU、以及 GPU node 有限的 CPU 容量这三者的相互作用里冒出来——这正是那类没有趁手的可观测性工具就几乎无法诊断的系统性问题。

Anyscale Dashboard 让事后调试不仅可行，而且有章可循。Data dashboard 指出嵌入阶段是何时空转的，Task 和 Actor Dashboard 解释了它为何停滞将近一个小时，Cluster dashboard 则精准定位了那些 CPU slot 的去向。关键在于，这一整套分析在集群已经关闭之后依然可做，不必从头复现问题。
