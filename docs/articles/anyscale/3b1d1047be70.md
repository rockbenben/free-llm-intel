# 使用 Anyscale 上完全持久化的集群和 Actor 仪表板来监控和调试 Ray 工作负载

作者：[Carolyn Wang](https://www.anyscale.com/blog?author=carolyn-wang)、[AlanGuo](https://www.anyscale.com/blog?author=alan-guo)、[Geetanjali Garg](https://www.anyscale.com/blog?author=geetanjali-garg) 和 [Philip Wang](https://www.anyscale.com/blog?author=philip-wang) | 2026 年 5 月 15 日

今天，我们很高兴地宣布推出**Anyscale 集群和 Actor 仪表板**，完成在 Anyscale 上**完全持久的 Ray 仪表板**的推出。与 [**Train**、**Data**](https://www.anyscale.com/blog/ray-train-data-dashboard) 和 [**Task**](https://www.anyscale.com/blog/ray-task-monitoring-persistent-logs) 仪表板一起，此版本为 Ray 工作负载提供了端到端监控、调试和优化工具，从基础设施级监控到工作负载级洞察，所有这些都在工作负载完成后保留用于历史分析。

## Link介绍集群和 Actor 仪表板

Ray 仪表板长期以来一直是了解分布式工作负载当前状态的重要工具 - 您的应用程序正在做什么（任务、参与者）以及它如何运行（节点、硬件利用率）。然而，Ray 仪表板有重要的局限性：

- **临时数据**：一旦 Ray 集群关闭，所有仪表板数据都会丢失。如果无法访问这些数据，事后调查就会很困难，并且通常需要从头开始重现问题，这对于长期运行或大规模的作业来说是一个昂贵且耗时的过程。
- **规模有限/保留时间短**：为了避免影响正在运行的工作负载，Ray 集群仪表板仅存储一部分数据。死亡节点数据仅保留10分钟，并且仅保留最近被杀死的10万个演员。

随着工作负载扩展到数百个节点和数百万个任务，这些限制对于现代人工智能和数据工作负载来说已经不够了。

新的 **Anyscale** **集群和 Actor 仪表板** 解决了这些限制，并改善了 Ray 工作负载的整体可观察性体验。这些仪表板由 [**Ray Event Export Framework**](https://www.anyscale.com/blog/ray-task-monitoring-persistent-logs#ray-event-export-framework) 提供支持，将集群外的集群事件流式传输并持久保存到 Anyscale 管理的存储和查询引擎中，以进行长期分析。这使得开发人员即使在集群终止后也可以调试故障、分析性能并比较工作负载，而无需维护自己的基础设施。

#### LinkKey 改进包括：

- **完全持久性** – 即使在集群关闭后，数据仍可用于事后调试。
- **可扩展性** – 旨在处理具有数千个节点和数百万个参与者的大规模 Ray 部署。
- **增强的用户体验** – 更快的过滤、搜索和聚合，加上新的可视化和历史信息，以了解集群拓扑和参与者生命周期。
- **统一且交互式** – 工作负载仪表板（训练、数据）和系统仪表板（集群、任务、Actor）之间的无缝导航，提供从高级概述到节点级详细信息的统一调试过程。

## 端到端链接调试 Ray 数据嵌入管道

让我们通过一个调试场景来了解工作负载级数据和训练仪表板、系统级集群仪表板以及核心级任务和参与者仪表板在实践中如何协同工作。对于这种情况，Ray Data 管道完成所需的时间比预期要长得多，我们在作业完成后使用持久化仪表板来找出原因。

Ray Data 通过提供构建在 Ray 之上的高级数据集 API 来简化分布式数据处理。开发人员通常在数据仪表板中开始调试，该仪表板在深入了解系统级详细信息之前提供作业级上下文。

### 链接管道

我们正在使用 Ray Data 构建一个两级音频嵌入管道。第一阶段使用 CPU 上的 librosa 将原始音频剪辑转换为频谱图，即声音的视觉表示，显示频率如何随时间变化。大规模处理音频数据时，必须对原始音频进行解码、重新采样到一致的采样率，并转换为适合 ML 模型的格式。这种频谱图转换的计算成本很高（CPU 繁重），并且是音频 ML 的标准预处理步骤 - 类似于图像在输入视觉模型之前需要调整大小和标准化的方式。第二阶段使用 GPU 上的 ViT-B/16 从这些频谱图图像中提取嵌入，可用于相似性搜索、聚类和流派分类等下游任务。
```
ds = ray.data.from_huggingface(hf_dataset)  # lewtun/music_genres
ds = ds.limit(19_000)
ds = ds.repartition(128)
ds = ds.random_shuffle()

# Stage 1: mel spectrogram extraction on CPU (8 actors, librosa + mel filterbank)
ds = ds.map_batches(SpectrogramExtractor, batch_size=16,
                    compute=ray.data.ActorPoolStrategy(size=8))

# Stage 2: ViT-B/16 embedding on GPU (1 actor, ~330 MB model)
ds = ds.map_batches(SpectrogramViTEmbedder, batch_size=64,
                    compute=ray.data.ActorPoolStrategy(size=1), num_gpus=1)
ds.write_parquet("/mnt/cluster_storage/audio_demo/output/")
```
该集群有 1 个 CPU 工作节点（m5.2xlarge：8 个 CPU、32 GB RAM）和 1 个 GPU 工作节点（g4dn.xlarge：4 个 CPU、16 GB RAM、1× T4）。我们将频谱图提取阶段的 actor 并发度设置为 8，以在 CPU 密集型工作中保持高吞吐量。

我们提交了包含 19,000 个音乐剪辑的作业。根据现有基准，我们预计它会在 10 分钟左右完成。相反，需要一个多小时。工作成功，所有嵌入都已写入，但显然出现了问题。发生了什么？

### 链接**第 1 步：数据仪表板 - 管道何时实际产生输出？**

我们从已完成作业的数据仪表板开始，它提供了工作负载的 Ray 库级概述，并在进一步深入系统和核心级仪表板之前设置上下文。由于 Anyscale 仪表板会在集群生命周期结束后保留​​数据，因此即使作业已完成，所有指标仍然可用。

随着时间的推移查看操作员指标，该模式立即变得可疑：

- `MapBatches(SpectrogramExtractor)：` 从一开始就保持活跃吞吐量，在整个运行过程中稳定地处理音频剪辑。
- `MapBatches(SpectrogramViTEmbedder)：` 一个多小时内输出 0 行，然后在最后五分钟内突然爆发活动。直到最后五分钟，输入队列大小稳步增加。所有嵌入都是在最后生成的。
- `写：` 相同的模式 - 直到最后才写任何内容。

![指标视图范围仅限于数据仪表板中的 SpectrogramViTEmbedder 数据运算符。](https://images.ctfassets.net/xjan103pcp94/2BhAodCjw0JpOSMJJKu8JB/652a926f4a54692c455160ff464d50ec/image2.png)图 6：指标视图范围仅限于数据仪表板中的 SpectrogramViTEMbedder 数据运算符。

虽然频谱图提取阶段运行了绝大多数工作，但嵌入阶段仅在尾部开始产生输出。这意味着 GPU（集群中最昂贵的资源）完全闲置了一个多小时。这直接转化为浪费的支出，因为 GPU 节点一直在运行并累积成本，而直到最后几分钟才做出任何贡献。嵌入阶段资源匮乏，直到提取参与者释放 GPU 节点上的 CPU 插槽，因此管道有效地序列化 - 首先是所有 CPU 工作，然后是所有 GPU 工作 - 失去了 Ray 设计提供的所有管道优势。

### LinkStep 3：Actor 仪表板 - 为什么嵌入 Actor 会延迟？

下一步将我们带到 Actor 仪表板，在这里我们可以找到 SpectrogramViTEMbedder 运算符的 actor。点击演员详细信息页面，我们可以看到演员事件时间线：

![SpectrogramViTEmbedder actor 的 Actor 详细信息页面。](https://images.ctfassets.net/xjan103pcp94/193kd6ipbhjzLbXrJxD2Nf/c76bbe3dc40291ca987e69b85d9030cd/image6.png)图 9：SpectrogramViTEmbedder 的 Actor 详细信息页面演员。

SpectrogramViTMbedder actor 的 Actor 详细信息页面。

演员等了一个多小时。演员根本没有失败或崩溃；它只是等待 CPU 插槽打开，然后才能进行调度。一旦演员最终被安排在 14:09，它只运行了几分钟，就成功完成了所有嵌入工作。

所需资源显示`{"CPU": 1.0, "GPU": 1.0}`。 GPU 始终是空闲的（没有其他东西会使用它）。所以 GPU 不是限制——CPU 才是。参与者在 GPU 节点上找不到空闲的 CPU 插槽。

### LinkStep 4：集群仪表板 - CPU 插槽去了哪里？

在 Actor 详细信息页面中，我们单击 Node ID 链接，这会将我们带到 GPU 节点 (g4dn.xlarge) 的集群仪表板中的节点详细信息视图。

GPU 节点的节点详细信息页面。

![图 11：作用域为 GPU 节点的 Actor 表。](https://images.ctfassets.net/xjan103pcp94/67YQYyzofPQxGG9oOCc3nt/3ff257c6e28c477639d434120f2f6143/image12.png)作用域为 GPU 节点的 Actor 表。

图 11：作用域为 GPU 节点的 Actor 表。

GPU 节点有 4 个 CPU 和 1 个 GPU，检查 Actor 选项卡可以准确揭示问题所在。四个“SpectrogramExtractor”参与者已被安排到该节点上，每个参与者都占用一个CPU插槽，从而使所有四个插槽都被完全占用。由于嵌入 Actor 还需要 CPU 来启动，因此它无处可启动。

时间戳确认了事件链：这 4 个提取 Actor 一直存活到大约 14:09，当提取 Actor 完成并释放其 CPU 插槽时，嵌入 Actor 就被调度了。

从 Anyscale 仪表板中，我们调查并确定了核心问题：“concurrency=8”提取参与者每个请求 1 个 CPU，Ray 将它们均匀地分布在集群中的可用 CPU 插槽上：四个位于 CPU 节点（8 个 CPU）上，四个位于 GPU 节点（4 个 CPU）上。当 GPU actor 尝试启动时，唯一具有 GPU 的节点上没有空闲的 CPU 插槽。嵌入参与者等待了近一个小时，等待提取阶段完成并释放其 CPU 插槽，然后才最终在节点上进行调度。

### 链接修复

根本原因是 Ray 将四个“SpectrogramExtractor” actor 调度到 GPU 节点上，消耗了进程中的每个可用 CPU 插槽，并阻止了嵌入 actor 启动。有几个推荐选项可以解决此问题：

**1.减少预处理并发性：**
```
ds = ds.map_batches(
    SpectrogramExtractor,
    batch_size=32, 
    compute=ray.data.ActorPoolStrategy(size=6),
)
```
Ray 将分配 actor，以便 CPU 节点上有 3 个，GPU 节点上有 3 个。然后，“SpectrogramExtractor”参与者将仅消耗 GPU 节点上四分之三的 CPU。

![固定频谱图嵌入管道的数据仪表板视图。](https://images.ctfassets.net/xjan103pcp94/7ySbj9RLLryGW6Cvkh7PxU/362d0290ca8989e665559fc36a6274f2/image7.png)图 12：固定频谱图嵌入的数据仪表板视图管道。

固定频谱图嵌入管道的数据仪表板视图。

**2.使用调度标签来分隔工作负载：**
```
# In the Anyscale cluster config, label the CPU node with {"workload": "cpu-extraction"} 

.map_batches(
    SpectrogramExtractor,
    batch_size=32,
    compute=ray.data.ActorPoolStrategy(size=6),
    label_selectors={"workload": "cpu-extraction"},
)
```
这种方法明确地将提取参与者固定到 CPU 节点，防止它们登陆到 GPU 节点，无论可用容量如何，因此保证 GPU 节点有空闲的 CPU 插槽。最强的保证，但严格 - 提取永远不能使用任何 GPU 节点 CPU，即使它是空闲的。

一旦位置明确，并发性就成为一个独立的调节旋钮。我们将提取参与者的数量保留在 6 个，以便为节点上的其他任务留出 CPU 空间，但应该针对吞吐量进行调整。

**3.使用资源来定位工作负载：**
```
# In the Anyscale cluster config, add resources to the CPU node with {"extraction-cpu": 8} and to the GPU node with {"extraction-cpu": 2}

ds = ds.map_batches(
    SpectrogramExtractor,
    batch_size=32,
    compute=ray.data.ActorPoolStrategy(size=6),
    resources={"extraction-cpu": 1},
)
```
这为每个节点上可以运行的提取参与者数量设置了明确的放置预算。 GPU 节点上的 CPU 提取上限为 2 个 CPU，为 GPU actor 保留 2 个 CPU。这比标签更灵活——GPU 节点仍然可以参与有限数量的提取。

### 领键外卖

这个错误特别棘手的原因是，孤立地看，没有任何问题。管道代码是正确的，集群有足够的总资源，并且每个单独的配置选择本身都是合理的。该问题仅从 Actor 放置、每个 Actor CPU 请求和 GPU 节点有限的 CPU 容量之间的交互中显现出来，这正是一种系统性问题，如果没有适当的可观察性工具，几乎不可能诊断。

Anyscale 仪表板使事后调试不仅成为可能，而且变得有条不紊。数据仪表板确定了嵌入阶段何时空闲，任务和参与者仪表板解释了为什么它停滞了近一个小时，而集群仪表板则确定了这些 CPU 插槽的去向。重要的是，所有这些分析在集群关闭后都可用，无需从头开始重现问题。
