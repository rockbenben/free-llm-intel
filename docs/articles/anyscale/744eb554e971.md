期间，我们看到众多公司与个人用 Ray Serve 和 Anyscale Services 把各种 AI 应用送上生产：大语言模型、视频处理的多模型应用、高规模电商应用等等。自 2023 年 1 月以来，Ray Serve 与 Anyscale Services 的用量增长了超过 **600%**。

本文梳理我们在服务 Ray Serve 用户过程中识别出的常见挑战，然后介绍 Ray Serve 与 Anyscale Services 如何通过缩短上市时间、降低成本、保障生产可靠性来解决它们。

## 把 AI 送上生产的现代挑战

过去两年深度学习与生成式 AI 爆发，AI 应用变得更普及、更复杂、也更昂贵。随着更多个人和公司认真地把创新的 AI 应用部署到生产，这些挑战成为心头要事。

在与从小型团队到大型企业的 AI 从业者交流中，我们总结出行业三个共性问题：

- **缩短上市时间**：AI 版图变化极快，从业者也必须快。压缩从开发到生产的时间、用上最新 ML 技术，意味着给最终用户交付更多价值。微服务等既有模式带来复杂度，增加开发与运维开销。
- **降低成本**：相比传统 Web 服务，硬件昂贵得多，AI 应用需要灵活性与动态扩缩。GPU 的成本与稀缺性只会让问题更糟。像市场上多数方案那样把每个模型部署成自己的微服务，会导致硬件利用率低、运维开销高。
- **保障生产可靠性**：AI 应用日益支撑严肃而有价值的用例。AI 开发者需要相信自己能 7×24 运行一个复杂应用并响应事故。而这一挑战又要与成本、开发效率的优化相互权衡，难上加难。

Ray Serve 与 Anyscale Services 正是为解决这些挑战而生：

- **Ray Serve** 提供**简洁**、**灵活**与**扩展**，让你两头兼得：帮你压低成本、把硬件用到极致，同时为本地开发与测试提供以 Python 为中心的简单体验。
- **Anyscale Services** 托管**部署基础设施**与**集成**，经过大量生产检验。这确保你能可靠地运行生产、构建创新的 AI 应用，而不必操心维护基础设施。Anyscale Services 还叠加进一步的**硬件优化**，降低成本、最大化 GPU 可得性。

Ray Serve on Anyscale Services 的组合帮你优化完整服务栈——贯穿模型、应用与硬件三层。

## 缩短上市时间

压缩从想法到生产的时间至关重要——无论在 POC 阶段验证价值，还是持续改进应用，让研究者与工程师多产是首要任务，基础设施应体现这一点。

微服务因其给 Web 应用带来的好处（跨团队独立扩缩与部署）而成为 AI 应用的流行解。但这种架构会让本地开发与测试痛苦不堪，并为分别部署许多模型与业务逻辑带来沉重的 dev-ops 开销。

AI 从业者需要能轻松测试应用，不为基础设施配置操心。模型服务方案应当让研究代码到生产几乎不需要改动，提升迭代速度。

### 以开发者为中心的 Python API

Ray Serve 为服务 ML 模型与构建 AI 应用提供**简单的 Python 接口**——这是开发者喜爱 Ray Serve 的首要原因之一。

只需几个代码注解，你就能借助 Python 的简洁与表达力构建并部署复杂 ML 应用。Ray Serve 还与 FastAPI 集成，让你构建端到端应用，而不只是 ML 推理组件。而且，同一段代码在本地开发时与在生产中一样运行。a16z 近期一篇[博客](https://a16z.com/emerging-architectures-for-llm-applications/)总结了 LLM 应用的参考架构——这类应用都可以用 Ray Serve 无缝构建。构建生产级 AI 应用，你不必新学任何 Kubernetes 或其他服务基础设施的概念。

下面是用 Ray Serve 从"摘要 + 翻译"模型创建生产级 deployment 的示例代码：

```
1from starlette.requests import Request
2import ray
3from ray import serve
4from ray.serve.handle import RayServeHandle
5
6from transformers import pipeline
7
8@serve.deployment
9class Translator:
10    def __init__(self):
11        self.model = pipeline("translation_en_to_fr", model="t5-small")
12
13    def translate(self, text: str) -> str:
14        model_output = self.model(text)
15        return model_output[0]["translation_text"]
16
17@serve.deployment
18class Summarizer:
19    def __init__(self, translator: RayServeHandle):
20        self.model = pipeline("summarization", model="t5-small")
21        self.translator = translator
22
23    def summarize(self, text: str) -> str:
24        model_output = self.model(text, min_length=5, max_length=15)
25        summary = model_output[0]["summary_text"]
26        return summary
27
28    async def __call__(self, http_request: Request) -> str:
29        summary = self.summarize(await http_request.json())
30        translation = await self.translator.translate.remote(summary)
31        return translation
32
33app = Summarizer.bind(Translator.bind())
34
```

## 降低成本

AI 应用所需的计算资源比上一代 Web 服务多出数量级。典型 Web 服务是 IO 受限的，而现代 AI 应用每个请求都要大量计算。预处理与 ML 推理可以占用一颗 CPU 或 GPU 长达数秒，因此处理用户流量常常**需要大量 CPU 与 GPU 实例**。对 LLM 这样的大型生成式模型尤其如此。

这些硬件要求让 AI 应用既**至关重要又难以优化**。而需求增长、供给受限导致的 GPU 价格飙升只会雪上加霜。

ML 服务框架必须围绕**灵活性**与**动态扩缩**来构建。它应当易于定义和更新扩缩模式，并易于集成最先进技术来优化模型的硬件利用。但多数模型服务框架像微服务一样构建——每个 endpoint 后面藏一个模型。结果就是高运维开销、差硬件利用率，以及演进架构时处处痛苦。

### 服务多模型的硬件效率

Ray Serve 部署单一模型已经高效，而它的扩展灵活性与 API 在构建含多个模型与业务逻辑的复杂 ML 应用时更强大。**模型组合（model composition）**是我们最受欢迎的特性之一：把多个各自有不同硬件需求的模型串在一起，借助 Ray Serve 自动扩缩让它们独立伸缩。

这些模型每一个都可以在共享同一集群的同时独立升级。Ray Serve 支持**分数资源**，带来更低开销与更高效的基础设施利用，同时削减维护部署大量微服务的运维负担。

*Ray Serve 模型组合*

***"引入 Ray Serve 显著改善了我们的生产 ML 流水线性能，相当于公司每年 ML 推理总成本降低约 50%。" —— Samsara Staff ML 工程师 Pang Wu*

阅读 [Samsara](https://medium.com/samsara-engineering/building-a-modern-machine-learning-platform-with-ray-eb0271f9cbcf)为何转向 Ray Serve、以及如何利用模型组合降低服务成本。

ML 应用中一个新兴模式是服务许多硬件需求相似但流量分布不均的微调模型。适用场景包括：服务在特定数据集上微调的 LLM 或图像生成模型，或按客户/用例训练的预测模型。为高效支撑这一用例，我们在 Ray 2.5 推出了**模型多路复用（model multiplexing）**。模型多路复用有助于降低平均延迟，让你用更少硬件服务更多流量。Ray Serve 的多路复用相比基线达到 2 倍 QPS，相比 SageMaker Multi-Model Endpoints 高 20-30% QPS。

#### Anyscale 基础设施优化

**Anyscale Services** 在异构硬件支持之上进一步叠加基础设施级优化。通过可靠使用**spot 实例**与跨硬件类型的**智能实例选择**，你能获得 2-3 倍的成本削减与更好的 GPU 可得性。云厂商的 spot 实例比按需实例便宜 50-60%，但生产服务很少使用——因为它们可能被云厂商回收，造成可用性下跌。Anyscale Services 利用云厂商的早期信号，把 spot 实例平稳替换为按需实例，确保生产服务不丢任何请求。

Anyscale 基础设施还有高度优化的节点**启动时间**：自动扩缩的冷启动可做到 30 秒，而多数竞争平台要 5 分钟以上。我们支持多云，帮你避免厂商锁定。关于基础设施优化的更多细节见[这里](https://www.anyscale.com/blog/cloud-infrastructure-for-llm-and-generative-ai-applications)。
