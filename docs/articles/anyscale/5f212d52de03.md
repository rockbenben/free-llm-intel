# 将 KubeRay 捐赠给 CNCF

作者：[Andrew Sy Kim (Google)](https://www.anyscale.com/blog?author=andrew-sy-kim-google)、[Edward Oakes](https://www.anyscale.com/blog?author=edward-oakes)、[Kai-Hsun Chen](https://www.anyscale.com/blog?author=kai-hsun-chen)、[Jui-An Huang](https://www.anyscale.com/blog?author=jui-an-huang)、[Richard Liaw](https://www.anyscale.com/blog?author=richard-liaw)、[Robert Nishihara](https://www.anyscale.com/blog?author=robert-nishihara) 和 [KubeRay 团队](https://www.anyscale.com/blog?author=the-kuberay-team) | 2026 年 11 月 9 日

PARK 堆栈（PyTorch、AI 模型、Ray 和 Kubernetes）正在成为生产 AI 事实上的开源标准。在该堆栈中，[KubeRay](https://github.com/kuberay-project/kuberay) 已成为连接基于 Ray 构建的可扩展 AI 应用程序与 Kubernetes 计算编排的桥梁。

PARK 堆栈的几乎每个核心部分都已经存在于 Linux 基金会之下：PyTorch 和 Ray 通过 PyTorch 基金会，Kubernetes 通过云原生计算基金会 (CNCF)。 KubeRay 是缺失的一块。

今天，我们宣布 KubeRay 加入 CNCF，将整个 PARK 堆栈置于 Linux 基金会的治理之下，并让团队对其中立性和开放性充满信心。

## Kubernetes 上的 LinkScaling Ray 集群

KubeRay 是一个功能强大的开源工具包和 Kubernetes 运算符，旨在在云原生基础设施上无缝运行由 Ray 支持的分布式人工智能、机器学习和 Python 工作负载。随着分布式 AI 工作负载成为核心云原生构造，KubeRay 弥合了 Python 优先的 AI 框架和 Kubernetes 原生基础设施之间的差距。

![Kubernetes 原生基础设施](https://images.ctfassets.net/xjan103pcp94/1btTPrJds1cvpaScrP0wLf/31e6436d2d5532237184923cb2be64a3/Kubernetes-native_infrastruct.png)

Kubernetes 原生基础设施

KubeRay 提供了三个 Kubernetes 自定义资源定义 (CRD)，用于在生产中扩展和操作 Ray 工作负载：

- **RayCluster：** 在 Kubernetes 上运行 Ray 的基础构建块。 “RayCluster”管理 Ray 集群的整个生命周期，自动执行 Head 和 Worker Pod 配置、运行状况检查、全局控制服务 (GCS) 容错以及与 Ray Autoscaler 协调的动态自动缩放。
- **RayJob：** 专为批处理、分布式训练和强化学习 (RL) 工作负载而构建。 “RayJob”会自动配置临时“RayCluster”，在集群准备就绪后提交 Ray 作业，并在完成后拆除集群，以最大限度地提高计算和加速器利用率。
- **RayService：** 专为使用 Ray Serve 进行长寿命、高可用性在线推理而设计。 “RayService”管理底层的“RayCluster”和 Ray Serve 部署图，为生产 AI 服务实现零停机滚动升级、自动故障转移和无缝流量路由。

这些自定义资源共同为企业在 Ray 和 Kubernetes 之上构建现代机器学习平台奠定了基础。例如，像 Hark 这样的最终用户使用 KubeRay 来扩展他们的 AI 代理工作流程。

> “大规模运行多模式 AI 工作负载需要一个在 Python 优先的 AI 和 Kubernetes 之间紧密集成的平台。KubeRay 就是这座桥梁，帮助我们在 Hark 可靠地扩展并管理复杂的代理工作流程，这就是我们使用它的原因，也是我做出贡献的原因：我希望帮助更多的构建者充满信心地扩展生产 AI。”Kai-Hsun Chen，Hark 的 AI 基础设施负责人

## Link发展 KubeRay 生态系统

除了核心集群生命周期管理之外，KubeRay 还因其与其他 CNCF 项目和更广泛的云原生生态系统的深度集成而得到了广泛采用。 KubeRay 不是重新发明基础设施原语，而是直接插入团队已经依赖的工具平台：

- **使用 OpenTelemetry、Prometheus 和 Fluent Bit 实现可观察性：** Ray 在其指标管道中使用 OpenTelemetry 并以 Prometheus 格式公开指标，使运行 KubeRay 的平台团队能够监控集群利用率、任务执行和 Ray Serve 延迟及其现有 Kubernetes 基础设施。与 Fluent Bit 配合进行轻量级日志收集和转发，操作员可以轻松聚合临时和长期 Ray 集群中的分布式工作日志和作业日志。
- **使用 Kueue、Volcano 和 KAI 进行批量调度和配额管理：** 随着组织在稀缺的 GPU 和 TPU 资源上扩展分布式训练，KubeRay 与不同的调度程序原生集成，将 Kubernetes 原生作业队列引入“RayJob”和“RayCluster”。这可以实现组调度（全有或全无 Pod 放置）、多租户资源配额、优先级抢占和拓扑感知调度。
- **工作负载安全性和隔离：**随着人工智能工作负载的扩展，强大的安全性和多租户至关重要。 KubeRay 为使用自动化 mTLS 和 Kubernetes 网络策略保护 Ray 集群提供了基础。

## 链接下一步是什么？

KubeRay 迄今为止的成功归功于其快速增长的社区成员——我们要感谢迄今为止为 KubeRay 做出贡献的每个人。

成为 CNCF 沙箱项目只是 KubeRay 在开放、供应商中立治理下的下一章的开始，我们希望您能成为其中的一部分。

如果您参加 KubeCon NA 2026，请在我们的 [Birds of a Feather (BoF) 会议](https://events.linuxfoundation.org/kubecon-cloudnativecon-north-america/program/schedule/?id=1345967) 上与 KubeRay 维护人员会面，讨论路线图、分享生产用例并帮助塑造 Ray on Kubernetes 的未来。 Hark 还将 [发表演讲](https://events.linuxfoundation.org/kubecon-cloudnativecon-north-america/program/schedule/?id=1337241)，讲述他们如何将 KubeRay 用于多模式 AI 用例。

您还可以在 [CNCF](https://cncf-slack.netlify.app/) 或 [Ray Slack 工作区](https://www.ray.io/join-slack) 上的 #kuberay 频道与社区联系，并参加我们的[双周社区会议](https://zoom-lfx.platform.linuxfoundation.org/meetings/ray)。
