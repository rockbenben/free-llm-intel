# 可扩展的分布式训练：从单 GPU 限制到使用 Ray 在任意规模上进行可靠的多节点运行

作者

Julian Forero

与

Ian Jordan, PhD

|

2026 年 1 月 28 日

随着数据集和模型不断变大——尤其是横跨文本、图像、视频及其他非结构化数据的多模态系统——ML 团队终究会撞上一条硬限制：你的数据集或模型再也放不进单块 GPU。

要决策的不是要不要扩展，而是如何在继续沿用 XGBoost、PyTorch、DeepSpeed 或 Hugging Face Transformers 这些熟悉框架的前提下把它做成。

Ray 已经浮现为应对这一转变采用最广泛的开源框架，GitHub stars 超过 40k，每周下载量超过 1000 万。[Uber](https://www.uber.com/blog/open-source-and-in-house-how-uber-optimizes-llm-training/)、[Discord](https://discord.com/blog/from-single-node-to-multi-gpu-clusters-how-discord-made-distributed-compute-easy-for-ml-engineers)、[Attentive](https://youtu.be/mppzZ4hLjXs?si=Fs9zhjlgOpyYtrxE&t=219) 等许多团队都在用 Ray 扩展作业，而不必重写核心训练函数的逻辑。

- 如果你准备好把 Ray 当作分布式 AI 框架来学，[来看看这门免费课程](https://courses.anyscale.com/bundles/ray-train-special)。

如果你仍在评估从单节点实验走向分布式训练这一步，下面的小节梳理了关键的技术与业务考量，以及 Ray on Anyscale 如何同时降低开发者的摩擦和运维风险。

## 基础设施的协同设计不再是可选项

传统的流程是 ML 工程师在单 GPU 上训练、平台/MLOps 团队随后把它「生产化」——在多模态 AI 时代这套做法已经失效，因为训练本身同样是一个基础设施问题。

从单块 GPU 走到一台机器上多块互联的 GPU，通常还算可控。再往前、跨节点走，事情就难得多。多节点训练会带来本地工作流中并不存在的失效模式：

- GPU 故障会让节点掉线，造成局部失败
- 跨机器的依赖漂移
- 割裂的日志与指标
- 调试不再局限于本地
- 与常见 ML 框架的集成并不轻松
- 必须在节点之间协调并搬运的数据

上手指引清单很快就长成一大摞毫无差异化的基础设施工作：

- 供应并监控多节点 GPU 集群
- 配置网络
- 接好 SSH 启动器、Slurm 或 Kubernetes 作业
- 分配 PyTorch DDP（Distributed Data Parallel）的 rank 来协调 worker
- 管理数据分片与放置
- 构建一套容错的 checkpoint 系统

DIY 路线的代价不只是工程时间。它还体现为迭代变慢、实验脆弱、错过截止日期，以及永远进不了生产的模型。

## **数据准备开始变得很像训练**

随着模型和数据集变得更大、更多模态，数据准备与训练之间的基础设施边界开始消失。

过去那些类似 ETL 的预处理步骤，如今成了带模型的批量推理步骤，例如用 LLM 生成标签、生成 caption，或规模化地做 embedding 生成。这把数据准备从基于 CPU 的 ETL 变成了以 GPU 为中心的批量推理。

只为训练优化基础设施已经不够了。现代的模型开发要求把数据处理与训练当作一条端到端的单一工作流来对待，共用同一套扩展、调度与故障处理的决策。

## **GPU 稀缺且昂贵**

现代的训作业动辄横跨数小时或数天，还常常在多个节点上执行。在这样的时间尺度上，失败是意料之中的事，而不是例外。一次节点重启就可能损失数万美元的算力，这让可靠性成了训练循环的核心属性，而不是运维上事后补上的想法。

与此同时，GPU 也可能难以获得。为了管理有限的容量，团队常常预留大块的 GPU 配额，用来承接多个工作负载的峰值需求。实际情况是，像生产推理这样优先级更高的作业，经常抢占长时间运行的训练作业。在共享容量的模式下，硬件可用性始终在变，训练工作负载就必须容忍被打断，并适应不断变化的资源。

结果就是，效率与适应能力成了头等要务。

checkpoint 变得必不可少，但当单个 epoch 本身就要跑上数小时或数天时，粗放的 epoch 级 checkpoint 往往不够细。GPU 利用率高与单纯的规模大同样重要，这意味着团队需要看清资源实际是怎么被用掉的，并有能力据此优化。而硬件可用性始终是流动的，于是暂停、恢复、并根据不断变化的资源可用性来调整训练作业的能力，就成了关键项而非可选项。

## **为什么选 Ray——以及为什么选 Ray on Anyscale**

当数据准备和训练需要一起扩展时，单点方案和框架就会撑不住。Ray 提供一个统一的分布式处理引擎，加速端到端的实验，通常能把 [GPU 利用率](https://www.anyscale.com/blog/gpu-in-efficiency-in-ai-workloads)提升 50–70%。

Ray 接手了分布式系统里那些难做的部分：

- worker 协调
- 调度
- 容错
- 资源管理等等

借助 [Ray Train](https://www.youtube.com/watch?v=BuYkzhlCeEg) 库，开发者用 Python 表达训练函数应当如何扩展，而底层的并行化由 Ray 处理。团队可以扩展 PyTorch、XGBoost 和 Transformers，而不必自己去拼一套编排逻辑。

但只有 Ray 并不能卸掉全部的运维负担。集群生命周期管理、环境一致性、故障恢复和可观测性仍然归团队自己扛——这些工作会拖慢实验，也让人从模型开发上分心。

Ray on Anyscale 建立在同一个开源运行时之上，并通过加上专门打造的开发者工具（Anyscale Developer Central）来补上这个缺口，它提供：

- 交互式的多节点开发环境，可通过 VSCode、Cursor 或 Jupyter 访问
- 集中化的日志、指标与作业状态，让你不必 SSH 登录单个节点就能调试和优化分布式运行
- 开箱即用的[从数据集到模型的血缘追踪](https://www.anyscale.com/blog/announcing-lineage-tracking-ray-managed-anyscale)

以及一个托管的集群控制面（Anyscale Cluster Controller），它具备：

- 自动检测并替换不健康的节点，把人工介入降到最低
- 多云的作业队列管理与工作负载编排
- 面向训练与数据工作负载的全托管集群供应与拆除
- 跨云厂商的灵活部署，且无需改动应用代码
- 内置的用户与成本治理

有了 Anyscale，分布式训练不再像是一门独立的系统学科。它成了一种随你的模型自然扩展的方式，而不必把 ML 开发变成一份维护基础设施的差事。

| **类别** | **没有 Ray Train** | **Ray Train（OSS）** | **Anyscale 上的 Ray Train（托管）** |
| --- | --- | --- | --- |
| **集群供应** | 手工供应、搭建、网络、SSH/Slurm/K8s 配置 | 用户仍须自行创建并管理 Ray 集群 | 全托管的集群生命周期（供应、扩缩、拆除） |
| **环境可复现性** | 很难，驱动/CUDA 漂移、依赖冲突 | 必须维护自己的 Docker/conda 镜像并同步环境 | 有保证的、可复现的、带版本控制的环境 |
| **分布式搭建与 rank 管理** | 复杂的 DDP 配置；手工分配 rank | 由 Ray Train 自动处理 | 同样的 Ray Train API，但背后由托管的集群状态支撑 |
| **容错** | 手工的 checkpoint 逻辑，作业重启会打断训练 | Ray Train 提供 API，但集群可靠性要用户自己保证 | 生产级的容错 + [epoch 中途恢复](https://docs.anyscale.com/runtime/mid-epoch-resumption) + 自动恢复 |
| **弹性** | 不支持，节点丢失即作业终止 | 实践中不支持。弹性 API 存在，但缺少托管的自动扩缩器、协调一致的节点生命周期和平台级容错时它们跑不起来 | 可靠的、[由平台管理的弹性](https://docs.anyscale.com/runtime/train#elastic-training)（被抢占可自动恢复） |
| **数据流水线集成** | 自己手写的分片、预处理与数据搬运 | Ray Data 与 Train 的集成存在，但基础设施要用户自己调 | Ray Data 与 Train 在资源隔离下被编排到一起 |
| **运维负担** | 极高，集群故障的调试全靠手工 | 中等，Ray Train 简化了训练逻辑，但基础设施仍是用户的活儿 | 很低，平台负责集群健康、节点重启与自动扩缩 |
| **安全与治理** | 必须自建 IAM、VPC、审计日志与隔离 | 只有 OSS，全部安全层都要用户自己实现 | 企业级安全、IAM 集成、VPC 隔离、可审计 |
| **作业生命周期管理** | Bash 脚本、tmux、Slurm 作业、Kubernetes operator | 有 Ray Jobs 可用，但要用户自己维护 | 全托管的 Ray Jobs，带重试、日志与仪表盘 |
| **总体上你得到什么** | 一套脆弱的、由少数工程师维护的定制训练技术栈 | 一个更好的训练循环编排器，但基础设施仍是 DIY | 一个可上生产的分布式训练平台 |
| **总工程成本** | 巨大（数月乃至数年的投入） | 中等（可靠性 + 集群运维仍由你维护） | 极少（全部精力放在训练代码和流水线上） |
