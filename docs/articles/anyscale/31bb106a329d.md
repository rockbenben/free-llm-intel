# 用 Anyscale Replica Compaction 部署 Ray Serve，节点数最多省 50%

作者：Matt Connor、Akshay Malik 和 Cindy Zhang | 2024 年 7 月 15 日

拥抱 AI 的公司日益面临资源利用与成本管理的问题。模型服务与推理尤其需要随流量起伏而伸缩。Ray Serve 是构建在 Ray 上的可扩展模型服务库，正好应对这种动态。不过，尽管 Ray Serve 这样的开源系统能帮助管理流量增长，即便是精密的系统，在流量回落后也难以缩*容*。这类资源碎片化必然导致资源闲置、成本上升。

Anyscale 的新特性 Replica Compaction（副本压实）通过优化在线推理与模型服务的资源使用，帮助解决资源碎片化。下面看看这个特性如何工作、你在实践中如何使用它。

## 背景：什么是 Ray Serve？

Ray Serve 有几个核心概念：

- **Deployment（部署）**：一个 deployment 包含处理进来请求的业务逻辑或 ML 模型。
- **Replica（副本）**：replica 是 deployment 的一个可处理请求的实例，用 Ray Actor 实现。replica 数量可以扩缩（甚至自动扩缩）以匹配进来的请求负载。
- **Application（应用）**：application 是 Ray Serve 集群中的升级单元，由一个或多个 deployment 组成。
- **Service（服务）**：Service 是一个 Ray Serve 集群，可以由一个或多个 application 组成。

各 deployment 独立处理进来的请求，在多数情况下可实现并行处理与高效资源利用。例如，Ray Serve 可以在同一个 Service 上为 Llama-3-8B 与 Llama-3-70B 创建 deployment，并设置不同资源需求（每副本分别为 1 GPU 和 4 GPU）。这两个 deployment 会随各自的流量独立伸缩。

## 资源碎片化问题

资源碎片化发生在伸缩活动导致各节点资源利用不均的时候。随着 replica 增加，autoscaler 会启动新节点来承担增长的 deployment 负载。但当流量下降、模型缩容时，当初为高峰负载开的那些节点就变得利用率低下。这是成本升高、集群性能下降最常见的原因之一。

本质上，当伸缩某个特定 deployment 或模型（比如模型 A）时，Ray Serve 只考虑这一个 deployment 的流量与资源需求，其他 deployment（比如模型 B 和 C）的状态、replica 和流量都不在伸缩过程的考虑之内。由于伸缩一次只看单个 deployment，随着流量起伏、集群扩扩缩缩，资源碎片化不可避免。

## 用 Anyscale Replica Compaction 解决资源碎片化

我们很高兴推出 Replica Compaction 来应对资源碎片化。有了它，Anyscale 会自动把 replica 迁移到更少的节点上，以优化资源使用、降低成本。Replica Compaction 特性有三大组件：

- **Replica Migration（副本迁移）：** Compaction 持续监视集群，寻找迁移 replica 的机会。若某个节点使用率很低，Anyscale 的 Replica Compaction 会自动把 replica 迁移到容量充足的其他节点。集群中每个节点都会被检查，replica 更少、可被释放的节点优先处理。
- **零停机：** 迁移毫不费力。Anyscale Services 会无缝拉起新 replica、监控其健康、切换流量，再移除旧 replica。
- **Autoscaler 集成：** Anyscale Autoscaler 在迁移后持续搜寻空闲节点并按需关停，减少节点数——也就是成本。

再看上面同一个例子，这次加上 Anyscale 的 Replica Compaction。有了 Replica Compaction，Anyscale 能检测到模型 A 缩容，并自动把多余的模型 C replica 迁移进单个节点。

*Anyscale Replica Compaction 示例：Replica Compaction 发现资源碎片化正造成不必要的资源占用，随后果断地把 replica 自动转移（不打断生产流量）到单个节点，降低成本、提升利用率。*

## Replica Compaction 实战：真实结果

为测试新的 Replica Compaction 特性，Anyscale 在一个真实生产负载上运行了数月。看看我们跑了什么——以及 Replica Compaction 如何降本增效。

**案例研究：**

Anyscale 提供调用 LLM 的 serverless API，模型包括 Mistral、Mixtral、Llama3 等。这些模型作为 replica 部署在一个 Anyscale Service 上。该服务已运行数月，以差异巨大的流量模式为大规模用户服务 10 个以上模型。

发布 Anyscale Replica Compaction 之后，我们从**每 GPU 每秒 token 数**（tokens per GPU second）看到了显著的节省与效率提升。在其他条件不变（不改变张量并行、所服务模型或所用硬件）的情况下，Replica Compaction 之后的整体效率平均提升**约 10%**。启用次日，实例秒数下降 **3.7%**，而同一时期以 token 数计量的流量**增长了 11.2%**。由于我们用 A100、H100 等高端 GPU 服务模型，这转化为可观的成本优势。

Replica Compaction 的效果与节省幅度，取决于流量分布、deployment 数量与底层实例类型，差异很大。在负载较分散的场景（如上面的示例），成本可降低 50% 甚至更多！
