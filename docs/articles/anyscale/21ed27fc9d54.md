# Ray Data 中的 GPU 原生算子

作者：Richard Liaw、Felix Cheung 和 Lee Yang | 2026 年 8 月 25 日

Ray Data 是构建在 Ray 之上、专注于多模态数据处理与训练数据加载等 AI 负载的数据引擎。由于聚焦 AI 负载，GPU 是 Ray Data 的核心特性——它能将 GPU 视为一种调度资源，从而轻松把数据处理任务扩展到大量 GPU 上。

尽管如此，Ray Data 直接在 GPU 上执行的原生功能一直有限，这部分职责此前都交给调用 PyTorch、JAX 等 GPU 库的用户自定义函数。

近期，Anyscale 的 Ray Data 团队与 NVIDIA cuDF 团队合作，把更多基于 GPU 的算子更好地集成进 Ray Data。我们特别兴奋地宣布两项新特性：

- [cuDF](https://developer.nvidia.com/topics/ai/data-science/cuda-x-data-science-libraries/cudf) 成为 Ray Data map_batches 的后端
- 基于 [RapidsMPF](https://github.com/rapidsai/rapidsmpf) 的 GPU shuffle

在部分数据清洗（data curation）负载上，这些增强相比基于 CPU 的方案带来了最多 3 倍的 TCO 改善。

今天就可以通过 `pip install -U ray==2.58` 在 Ray 上试用。

## 背景

Ray Data 提供一组规范化数据处理算子，从 IO 到 shuffle 到 UDF。Ray Data 的差异化特性之一，是对 UDF 的一流 GPU 支持。例如，可以这样调度使用 GPU 的自定义代码：

```
import ray

ds = ray.data.read_parquet("s3://my-bucket/documents/")

def compute_gpu(batch: pd.DataFrame):
    ...

ds = ds.map_batches(compute_gpu, num_gpus=1, batch_size=4096, batch_format="pandas")
```

上述代码会自动启动多个 `compute_gpu` 调用，分别运行在你 Ray 集群中挂接不同 GPU 的不同进程上。

在用 Ray Data 做数据去重任务时，我们注意到两个改进机会：

- 流水线中存在计算密集的 DataFrame 操作，本可用 cuDF 加速，但这要求用户手动转换数据格式
- 这些特定任务有很重的哈希聚合步骤，计算密集，可以从更好的 GPU 加速中获益

为解决这两个机会点，我们为 Ray Data 添加了两个关键特性：cuDF 批量格式支持，以及基于 RapidsMPF 的 GPU 原生 shuffle 后端。

### cuDF 成为一等公民批量格式

Ray Data 原本有 3 种原生批量格式——Pandas DataFrame、Numpy 数组和 PyArrow Table。批量格式有两个用途：作为各阶段之间的数据交换格式，以及为用户编写自定义处理函数提供更熟悉的接口。

从 Ray 2.58 起，`map_batches` 接受 `batch_format="cudf"`，把你的 UDF 收到的数据从 pandas DataFrame 或 Arrow table 换成 `cudf.DataFrame`。

**cuDF** 是 NVIDIA 开源的 GPU 加速 DataFrame 库，是 NVIDIA CUDA-X 数据处理库系列的一员。它以类 Pandas 的 API 提供 GPU 加速的操作。对某些计算密集的操作，cuDF 可以比等效的 CPU 实现快上最多一个数量级、成本也更低。

```
import ray

ds = ray.data.read_parquet("s3://my-bucket/documents/")

def add_minhash(batch):  # batch is a cudf.DataFrame
    batch["minhash"] = batch["text"].str.minhash(seed=42, ...)
    return batch

ds = ds.map_batches(add_minhash, batch_format="cudf", num_gpus=1, batch_size=4096)
```

### 经由 RapidsMPF 的 GPU 原生 shuffle

用户现在可以通过一条构建在 [RapidsMPF](https://docs.rapids.ai/api/rapidsmpf/stable/) 上的全新 GPU 执行路径，使用 GPU 加速的 `repartition` 与哈希聚合。各 rank 之间直接经 UCXX 通信。跨 rank 的 shuffle 数据可利用 RDMA 或 NVLink 等高性能传输，绕过 CPU 与 Ray 对象存储。

与 cuDF 类似，对某些计算密集的操作，基于 RapidsMPF 的 shuffle 可以比等效的 CPU 实现快上最多一个数量级、成本也更低。

```
from ray.data.context import DataContext, ShuffleStrategy

ctx = DataContext.get_current()
ctx.shuffle_strategy = ShuffleStrategy.GPU_SHUFFLE

ds.repartition(num_blocks=256, keys=["doc_id"])
ds.groupby("band_id").count()
```

## 基准测试：模糊去重

推动我们这次合作的负载是**模糊文档去重（fuzzy document deduplication）**——基础模型训练数据清洗中的标准负载。基准测试采用[标准的 MinHash-LSH 方法](https://huggingface.co/blog/dedup)，流程如下：

*图 1：去重负载的各阶段。*

- 为每篇文档**生成 MinHash 签名**。
- 由签名**生成 LSH band**。
- **按 band 分组**，找出候选重复对。
- **对候选边去重。**
- 通过遍历图**计算连通分量**。
- **过滤重复项。**
- **持久化幸存者。**

第 1 步要为每个 n-gram 生成哈希值，哈希是计算密集型操作。

第 3 步与第 5 步的 shuffle 最重——groupby 操作用于形成重复对，而连通分量算法是一连串 groupby 操作。

在下面的实验中，我们看到由于 GPU 的集成与加速，这些步骤的性能得到改善。

以下实验使用 FineWeb 10BT 数据集，集群规模为 2 到 8 个节点。CPU 侧使用 m8id.4xlarge 实例类型：16 vCPU、64 GiB 内存，每小时 1.04416 美元。

GPU 评测使用 g6.4xlarge 实例类型：16 vCPU、64 GiB 内存，每小时 1.3232 美元。

实验代码基于 Ray 2.58，可[在此找到](https://github.com/ray-project/gpu-deduplication)。

### 生成 MinHash 签名

这一阶段把每篇文档切成一组 n-gram（n 取 5），并为每个 n-gram 生成 128 个哈希。

哈希步骤计算密集，我们比较了基于 Numpy 的基线方案与 cuDF 内置哈希实现。

| **节点数** | **2** | **4** | **8** |
| --- | --- | --- | --- |
| CPU 基线（s） | 1899 | 963 | 519 |
| GPU（cuDF）（s） | 125 | 63 | 33 |
| **加速比** | **15.2** | **15.3** | **15.7** |

由上可见，GPU 加速让该阶段的运行比同等规模的 CPU 集群**最多快 15 倍**。

### 分组阶段

在第 3 与第 5 步，我们执行局部敏感哈希：若文档之间发生哈希碰撞则把它们归组；并实现了一种[迭代式连通分量检测算法](https://research.google/pubs/connected-components-in-mapreduce-and-beyond/)，找出具有传递性碰撞的文档（例如文档 A 与 B 相似、C 与 B 相似，则 A 与 C 也应相似）。

| **节点数** | **2** | **4** | **8** |
| --- | --- | --- | --- |
| CPU 基线（s） | 1634 | 850 | 434 |
| GPU（RapidsMPF）（s） | 542 | 356 | 281 |
| **加速比** | **3.0** | **2.4** | **1.5** |

在这组对比中，增加 GPU 数量虽能缩短运行时间，但更高规模下的边际改善递减，成本节省随之减少。

由于这些阶段是 shuffle 密集型的，加入更多 GPU 也带来更多通信开销。对这一特定数据集与负载，2 GPU 最优——数据集可能太小，无法利用满 8 块 GPU。

### 端到端流水线

| **节点数** | **2** | **4** | **8** |
| --- | --- | --- | --- |
| CPU 基线（s） | 3718 | 1891 | 989 |
| GPU 加速（s） | 939 | 511 | 360 |
| **加速比** | **4.0** | **3.7** | **2.7** |
| CPU 基线（$） | **$2.16** | **$2.19** | **$2.29** |
| GPU 加速（$） | **$0.69** | **$0.75** | **$1.06** |
| **TCO 改善** | **3.1x** | **2.9x** | **2.2x** |

从固定硬件配置下的完整流水线可见，GPU 加速方案：

- 在成本最低的 CPU 对比点（2 节点）上，快 4 倍、TCO 改善 3.1 倍
- 在所有节点规模下都提供 TCO 与运行时间的改善

## 下一步

尽管上述结果令人鼓舞，我们距离性能上限仍很远。特别是，对先后使用 cuDF 与 RapidsMPF 的算子做算子融合（operator fusion），将带来性能的阶跃式提升。这能让 Ray Data 避免各阶段之间不必要的 host-to-device 往返，让数据留在 GPU 显存内。

在与终端用户的合作中，下一步还包括**为数据预处理器启用 GPU shuffle**，让基于 Ray Data preprocessor API 构建的特征工程流水线也能走 GPU 路径。

我们很高兴继续投入这一方向，为你的 AI 数据负载带来最佳的数据处理性能。Ray Data GPU shuffle 目前处于实验阶段，随 Ray 2.58 提供。试用后欢迎给我们反馈！
