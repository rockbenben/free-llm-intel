# 使用 Ray 进行规模机器人策略评估

作者：Ian Jordan 博士、Alicia Chua、Artur Niederfahrenhorst 和 Omar Shorbaji | 2026 年 6 月 26 日

*评估一个机器人基础模型，意味着要把重量级的 GPU 推理和重量级的 GPU 物理仿真器放在同一个闭环里，成千次地反复运行。本文展示如何用 Ray 与 Isaac Lab 把这两类负载分离开来，并在 Anyscale 上让它们各自独立扩缩。*

## 引言

策略评估是机器人学不可或缺的一环。真机评估慢、昂贵，而且不安全。相比之下，仿真安全、可复现、可并行，单次试跑的成本也很低。因此基于仿真的评估（sim-eval）是一件重要的工具。

然而，仿真在消除物理评估瓶颈的同时，又把它换成了一个分布式系统问题。评估机器人基础模型，意味着要在数百乃至数千次 rollout 中同时运行 GPU 密集的仿真和 GPU 密集的策略推理。规模一大，就会横跨多块 GPU 和多个节点。

由此出现三个挑战：

- **它是闭环，不是一趟批处理。** 策略推理与仿真逐步交替，一方的输出喂给另一方的输入。你无法把它们解耦成彼此独立的离线阶段。
- **两个 GPU 密集的负载无法共用一个进程或一块 GPU。** 一个 3B 的视觉-语言-动作（VLA）模型要占一块 GPU，Isaac Sim 的物理与渲染也要占一块 GPU。把它们放在一起，就会争抢显存与算力，互相拖慢。把它们放进同一个进程，两边的运行时则会直接冲突。
- **数百次 rollout 应当共享一份策略，而不是各自重新加载。** 每次 rollout 都需要自己的仿真器，但它们全都可以由一小批共享的策略副本来服务。两者叠加，扩大 rollout 数量就意味着要拉起 N 份 3B+ 模型的副本，这既浪费，在显存上也往往做不到。

Ray 与 Anyscale 直接解决了这三个难题。

- **闭环执行：** Ray task 与 actor 把仿真器作为彼此隔离的进程运行在整个集群上。每个仿真器一步步推进环境，调用策略服务取一个动作，施加该动作，然后重复。这让评估保持在线、闭环，而不是被迫塞进一条离线批处理管线。
- **分离 GPU 密集的负载：** Ray Serve 把策略作为一个可自动伸缩的服务来运行，用的正是生产环境中服务 LLM 的同一套原语。Isaac Lab 仿真器各自独立运行，每个都在自己的进程里、有自己的 GPU 配额。策略运行时与仿真运行时不必共享一个进程，也不必争抢同一块 GPU。
- **共享策略副本：** 数百个仿真器可以查询一个更小的共享策略副本池，而不是每次 rollout 都加载自己那份 3B VLA。当推理是瓶颈时你可以增加策略副本，当 rollout 吞吐是瓶颈时你可以增加仿真器。

Anyscale 把这套异构、出了名脆弱的机器人技术栈打包成一个可复现的集群镜像，并运行在托管的 Ray 集群上。这意味着你可以从单次 rollout 走到数百次并行 rollout，而不必从零重建基础设施。

在本文中，我们用 Ray Serve 部署 NVIDIA 的 GR00T-N1.7-3B VLA，用它驱动 Isaac Lab 抓取-放置场景中的一台 Unitree G1 人形机器人，并把闭环 rollout 铺开到整个集群上。

## 架构

策略与仿真器位于同一个 Anyscale Ray 集群的不同 GPU worker 上，通过 HTTP 通信。在我们的示例中，这一点是用一个 Jupyter Notebook 来演示的。head 节点上的 driver 用 Ray Serve 部署策略，然后以 Ray task 的形式拉起仿真 worker。每个 worker 驱动一个 Isaac Lab 环境，并且每消耗完一个动作块就向策略端点查询一次。

整个流程就是三段顶层代码：连接集群、把策略做成服务、把仿真器铺开。

## 第 1 部分：闭环评估需要在线的策略服务

**问题：** 策略推理要把观测（相机画面、关节状态、一条语言指令）转成动作，而且延迟要足够低，使一次闭环 rollout 能在合理时间内跑完。再加上数百次 rollout 会并发运行，推理就变成了一个 N 对 M 的服务问题：许多仿真 worker 应当去查询一个更小的共享策略副本池，由 Ray Serve 在它们之间路由请求，而不是每个仿真器都加载自己那份模型。

**Ray 的解法：** 把策略包进一个 Ray Serve deployment。`GR00TPolicyServer` 只是一个普通的 Python 类，用 `@serve.deployment` 和 `@serve.ingress(FastAPI())` 装饰。它把 GR00T-N1.7-3B 一次性加载到 GPU 上，并暴露 `POST /predict` 与 `GET /stats`。

```
from fastapi import FastAPI, Request, Response
from ray import serve
import pickle, torch

app = FastAPI()

@serve.deployment(ray_actor_options={"num_gpus": 1}, max_ongoing_requests=16)
@serve.ingress(app)
class GR00TPolicyServer:
    def __init__(self, model_path="nvidia/GR00T-N1.7-3B", embodiment_tag="REAL_G1"):
        from gr00t.policy.gr00t_policy import Gr00tPolicy
        from gr00t.data.embodiment_tags import EmbodimentTag
        self.policy = Gr00tPolicy(
            embodiment_tag=EmbodimentTag.resolve(embodiment_tag),
            model_path=model_path,
            device="cuda:0",
        )

    @app.post("/predict")
    async def predict(self, request: Request):
        obs = pickle.loads(await request.body())
        with torch.no_grad():
            action_chunk, _ = self.policy.get_action(obs)
        action = {k: v.detach().cpu().numpy() for k, v in action_chunk.items()}
        return Response(pickle.dumps({"action": action}),
                        media_type="application/octet-stream")
```

一次 `serve.run` 就会把一个副本调度到某块 GPU worker 上、加载模型并起好 HTTP 服务。这里有两个 deployment 选项很关键。注意：3B 模型的加载时间会超过 Ray Serve 默认的 30 秒健康检查窗口，所以我们把它放宽。另外，带门控的视觉-语言主干模型还需要在副本的环境里有一个 Hugging Face token，我们通过 `runtime_env` 把它传进去。

```
deployment = GR00TPolicyServer.options(
    num_replicas=1,
    health_check_timeout_s=300,        # 3B model load exceeds the 30s default
    ray_actor_options={
        "num_gpus": 1,
        "runtime_env": {"env_vars": {"HF_TOKEN": os.environ["HF_TOKEN"]}},
    },
).bind(model_path="nvidia/GR00T-N1.7-3B", embodiment_tag="REAL_G1")

serve.run(deployment, name="gr00t-policy")
```

端点起来之后，一条符合 GR00T 的 `REAL_G1` schema 的观测就能产出一个动作块。这条观测是一个嵌套 dict：一小叠相机画面、机器人在双臂、双手和腰部的关节状态，以及一句自然语言指令。策略返回一个 40 步的动作块，覆盖身体每一个被驱动的部位。

```
deployment = GR00TPolicyServer.options(num_replicas=4).bind(...)
```

这与生产环境中服务大语言模型用的是同一种模式。策略现在就是一个普通的 HTTP 微服务：有版本管理、有健康检查、可以水平扩容。仿真器一侧不需要知道存在多少个副本、它们跑在哪里。

## 第 2 部分：仿真器与策略不能共用一个进程或一块 GPU

**问题：** 最直接的本能是把仿真器和策略 import 进同一个 Python 进程，在循环里调用模型。这样虽然能跑通，但因为资源争抢而并非最优：Isaac Sim 的 GPU 物理与渲染要和 3B 模型争用同一份 VRAM 和算力，所以挤在同一块 GPU 上时两者互相卡住。

**解法：** 把每个仿真器作为独立于策略推理的隔离进程来运行——一个拥有自己干净的 Python 解释器和事件循环的 Ray task——让它通过第 1 部分那个 HTTP 端点跟策略通信，而不是通过进程内的句柄。这样策略和仿真器落在不同的 GPU 上，谁也不会阻塞谁。代价是每次推理多一次网络跳转，而这正是动作分块能够摊平的开销。

控制循环很小。仿真器只在当前动作块用完时才去查询策略，每次调用执行 `action_horizon` 步物理：

```
def query_policy(policy_url, obs, timeout=120.0):
    r = requests.post(policy_url.rstrip("/") + "/predict",
                      data=pickle.dumps(obs), timeout=timeout)
    r.raise_for_status()
    return pickle.loads(r.content)

action_horizon = 8            # execute 8 of GR00T's 40 steps before re-querying
chunk_idx = action_horizon    # force a query on the very first step

for step in range(max_steps):
    if chunk_idx >= action_horizon:
        action_chunk = query_policy(POLICY_URL, obs)["action"]   # HTTP POST /predict
        chunk_idx = 0
    obs, reward, done, info = env.step(action_chunk, step_idx=chunk_idx)
    chunk_idx += 1
    if done:
        break
```

在 `action_horizon = 8` 下，一次约 1.6 秒的推理覆盖 8 个物理步，因此运行策略的那块 GPU 能服务的仿真器数量，是「每一步都查询」这种朴素循环的 8 倍。

剩下的工作是转换。GR00T 和 Isaac Lab 说的是两套不同的 schema，把它们打通才是把任何 VLA 接进仿真器这件事里真正麻烦的部分。进来时，Isaac Lab 的观测 dict 被转换成 GR00T 那个嵌套的 `REAL_G1` 模态 dict：这是一个两帧的 `ego_view` 叠栈，以及以 9 维向量编码的末端执行器位姿（3 个平移值加上旋转矩阵的前两行）。出去时，GR00T 那个九个 key、40 步的动作块被压平成 Isaac Lab 任务所期望的扁平 `(1, 28)` 关节指令：

```
def _flatten_action(self, chunk, step_idx=0):
    """One step of GR00T's 9-key chunk -> Isaac Lab's flat (1, 28) joint action."""
    def pick(key, n):
        return np.asarray(chunk[key], dtype=np.float32)[0, step_idx][:n]

    flat = np.concatenate([
        pick("left_arm", 7), pick("right_arm", 7),    # 7 + 7
        pick("left_hand", 7), pick("right_hand", 7),  # 7 + 7  = 28
    ])
    return flat[None, :].astype(np.float32)           # (1, 28)
```

这层胶接好之后，策略与仿真器就隔着一条 HTTP 边界通信，同时各自运行在不同 GPU 上的独立进程里。仿真器仍然要等待每一个新的动作块，但动作分块把那次阻塞调用摊到了多个物理步上，并且避开了与策略服务器在 GPU/运行时的争抢。

## 第 3 部分：策略即服务

**问题：** 想对某个 checkpoint 说点什么，你需要很多次 rollout，覆盖不同的随机种子和起始状态，而且必须让它们并行运行——否则评估就成了整个模型开发循环里最慢的一环。更糟的是，让单次 rollout 得以成立的那套软件栈，在一台机器上组装起来就已经够痛苦，要在一个 GPU worker 集群上一模一样地复现更是难得多。它横跨 Isaac Lab、GR00T、一个带门控的 VLM 主干模型、被钉死版本的 `transformers` 与 `flash-attn`，还有好几处只是为了把模型加载进来就得打的运行时补丁。在多数机器人团队里，真正卡住评估吞吐量的其实是这个可复现性问题，而不是建模本身。

**解法——在 Anyscale 上用 Ray 铺开：** 由于策略是一个共享 HTTP 服务、每个仿真器是一个独立的 Ray task，从一次 rollout 扩到上百次轻而易举。每个 task 占用一块 GPU、跑自己的 rollout、查询共享的策略副本池，并保存自己的结果。

```
  @ray.remote(num_gpus=1, runtime_env={"env_vars": {"HF_TOKEN": os.environ["HF_TOKEN"]}})
  def run_sim_rollout(policy_url, seed=0):
      # Launch the simulator in its own process (see Part 2: Isaac Sim needs a
      # clean interpreter and event loop), pointed at the shared policy endpoint.
      import subprocess
      subprocess.run(
          ["python", "sim_worker.py", "--policy-url", policy_url, "--seed", str(seed)],
          check=True,
      )
      return load_results(seed)   # the subprocess writes its GIF + metrics

  results = ray.get([
      run_sim_rollout.remote(POLICY_URL, seed=s) for s in range(100)
  ])
```

分离式架构的价值就在这里兑现。仿真器与策略副本各自独立扩缩。如果 rollout 因为等推理而吃不饱，Ray Serve 可以通过增加副本并在它们之间路由请求来自动扩充策略副本池。如果策略副本池利用率不足，你可以铺出更多仿真 worker，由 Anyscale 按需求扩掉底层 GPU 集群的规模。这两边的改动都不碰对方的代码。同一套 runtime_env 机制既把门控 token 装进 Serve 副本，也下发给每一个仿真 task，因此凭证无需人工配置就能在整个集群里传递。

## 回报：把评估做成一个可伸缩的服务

把这些合在一起，评估就不再是一件脆弱、串行、被硬件绑住的手工活，而变成一个你可以像其他任何推理负载那样去扩容的服务。策略副本池通过同一个 HTTP 接口上报自己的健康状态与吞吐量。这既是一个存活性信号，也是一份记录，说明在一整轮评估扫描里这个副本池到底忙到什么程度：

```
import requests
print(requests.get(f"{POLICY_URL}/stats").json())
```

```
{
  "model_path": "nvidia/GR00T-N1.7-3B",
  "embodiment_tag": "REAL_G1",
  "num_params_B": 3.144016,
  "device": "cuda:0",
  "total_calls": 1,
  "avg_latency_ms": 1619.57,
  "load_time_s": 26.79
}
```

扩容不需要改动 rollout 逻辑的任何一行代码。想跑更多评估，就把仿真器的列表推导式写长一些。想更快地服务它们，就调高 `num_replicas`。仿真受限时增加 GPU worker，推理受限时增加策略副本。正是同一套 Ray 原语，把 LLM 推理撑到数千并发请求，也把机器人策略评估撑到数千并发 rollout。

## 下一步

如果你想自己动手试试：

- **在 Anyscale 上跑。** 在托管的 GPU 集群上部署策略并铺开 Isaac Lab rollout，技术栈预先构建好、权重预先缓存好，零基础设施搭建。
- **换 checkpoint。** 这个 deployment 把 `model_path` 作为参数接收，所以从基座模型换到一个任务微调模型（比如 NVIDIA 的 `nvidia/GR00T-N1.6-G1-PnPAppleToPlate`，正是在这个完全相同的抓取-放置任务上做后训练，是一行改动。平台保持不变。
- **扩大评估扫描。** 把策略侧的 `num_replicas` 与更大规模的 rollout 铺开结合起来，在数百个随机种子和起始条件下并行评估一个 checkpoint。
- [Ray Serve 文档](https://docs.ray.io/en/latest/serve/index.html)涵盖 deployment、自动伸缩与多副本服务。

机器人评估正在演变成一个基础设施问题。随着机器人基础模型越来越大、仿真负载的真实程度越来越高，评估开始变得像现代 AI 服务化：分布式 GPU 推理集群、异构调度、可自动伸缩的服务，以及配合严密的闭环负载。关键的架构转变是分离。策略与仿真器各自独立扩缩，通过 Ray Serve 相连，并由 Ray Core 在整个集群上编排。那些撑住 LLM 推理扩容的分布式系统模式，如今正在成为机器人仿真与评估的必需品。
