# Ray 引入 label selector：调度灵活性更强

作者：[Mengjin Yan](https://www.anyscale.com/blog?author=mengjin-yan) 和 [Ryan O'Leary (Google)](https://www.anyscale.com/blog?author=ryan-oleary-google) | 2025 年 10 月 30 日

*感谢其他所有为这个项目做出贡献的人：来自 Anyscale 的 Edward Oakes、Janet Li、Bruce Zhang、Alan Guo、Douglas Strodtman、Jui-An Huang、Han-Ju Chen，以及来自 Google GKE 团队的 Andrew Sy Kim。*

今天，我们联合 Google Kubernetes Engine 团队一起，为 Ray 引入 label selector——一种把工作负载放到合适节点上的更直接的做法。相关 API 和 UI 随 Ray 2.49 发布，并在 Ray Dashboard、KubeRay 以及基于 Ray 构建的 AI 计算平台 [Anyscale](https://www.anyscale.com/product/platform) 上可用。

有了全新的 Label Selector API，Ray 现在可以直接帮开发者做到这些事：

- 为 Ray 集群中的节点打上标签（例如 `cpu-family=intel`、`market-type=spot`、`region=us-west-1`）
- 启动任务、actor 或 placement group 时，直接声明诸如*“只在 intel 芯片的节点上运行”*这样的要求

借助这个新 API，团队能获得更好的开发体验：更容易用标签而不是各种 hack 来表达调度意图（详情见下文），也从第一天起就能依靠 UI 和 API 支持更轻松地排查放置问题。

## 以往的变通做法

当 Ray 开发者只想把部分任务调度到 Ray 集群里的 spot 节点上时，他们往往会在启动 Ray 节点时伪造一个 “spot” 自定义资源，然后每个任务只申请极小的一份（0.01）——寄希望于同一时刻挤在同一个节点上的任务不超过 100 个，从而不会把这份 “spot” 资源用光。

```
1ray start --resources '{"CPU": 8, "spot": 1}'
```

```
1@ray.remote(resources={"spot": 0.01})
2def func():
3    pass
```

上面的变通做法暴露出一类调度限制：非资源约束（spot 与 on-demand）被伪装成了 “资源”。这把资源数量（CPU/GPU/RAM）和放置约束（region/zone、spot 与 on-demand）混为一谈，迫使非资源类的需求只能用资源来建模。

第二个同样常见的限制是只支持精确匹配：许多 Ray 开发者需要 any-of 或反向匹配——例如 “不在 GPU 节点上” 或 “在 us-west1-a 或 us-west1-b 之中”——而此前的 API 无法表达这类诉求。

有了 label selector，Ray 开发者就能同时解决这两个限制。它让你可以用节点标签灵活表达任务、actor 以及 placement group 中 bundle 的调度要求；这些标签可以在创建 RayCluster 时定义，也可以由 Ray 自动探测（例如加速器类型）。

Ray 的 label selector 从 Kubernetes 的[标签和选择器](https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/)借鉴了思路，用大家熟悉的 API 与语义增强了两个系统之间的调度互操作性。这是 Ray 与 Kubernetes 协同解锁更高级用例的众多在进行中的工作之一。

用标签你可以做到：

- 固定在某个具体节点上（按 node id）
- 指定跑在或避开 head 节点、某个 worker group
- 只放到 CPU 节点
- 指定某个加速器或某一组加速器
- 选择节点的市场类型（spot 或 on-demand）
- 把负载留在某些 region/zone 之内或排除在外
- 按 CPU family（或其他主机特性）筛选
- 指定 TPU pod slice

用法说明和完整 API 细节见 [Anyscale](https://docs.anyscale.com/configuration/compute/advanced#labels) 和 [Ray 文档](https://docs.ray.io/en/releases-2.50.0/ray-core/scheduling/labels.html)。

## Label Selector API

### 用户代码中的 label selector

label selector 通过与节点标签做匹配，来表达某部分工作应该在哪里运行。

你可以给以下对象加上 label selector：

- 任务/actor：在 `@ray.remote(...)` 里使用 `label_selector`
- placement group：创建时使用 `bundle_label_selector=[...] `

支持的语义：match、not match、any-of、not-any-of

回到上面的例子，这些需求现在可以这样表达：

```
1import ray
2from ray.util.placement_group import placement_group
3
4# Schedule a task on spot instances only
5@ray.remote(label_selector={"ray.io/market-type": "spot"})
6def func():
7    pass
8
9# Placement group: avoid GPU worker group and run in us-west-1 or us-west-2
10pg = placement_group(
11    [{“CPU”: 1}] * 2, 
12    bundle_label_selector=[
13        {
14            "ray.io/node-group": "!gpu-node-group", 
15            "ray.io/region": "in(us-west-1,us-west-2)"
16        }
17    ] * 2,
18)
19
```

同一份代码可以在开源 Ray、Kubernetes，以及 Anyscale 这类托管服务上可移植地运行。

### 节点标签

节点标签是给节点附加的、供调度使用的属性（例如 cpu-family、accelerator-type，用于 spot/on-demand 的 market-type，以及 region/zone）。你可以：

- 在创建集群时定义标签（Anyscale UI/SDK、KubeRay RayCluster CR，或 `ray start`）。

```
1# KubeRay RayCluster CR: Label nodes in a worker group with AMD CPU
2spec:
3 workerGroupSpecs:
4  - replicas: 1
5    labels:
6      cpu-family: amd
7
```

```
1# ray start: Label a node with AMD CPU
2ray start --labels="cpu-family=amd"
```

- 在 Anyscale UI 上：为某个 worker group 的节点打上 AMD CPU 标签

![label selector - 图 1](https://images.ctfassets.net/xjan103pcp94/4uxHUzbYm3IdlIdYQnWxdK/7834bad992b8066a36691d6d0bc5517d/image_26.png)

label selector - 图 1

也可以依赖 Ray 和 Anyscale 提供的自动探测标签（例如加速器类型）。在 Anyscale 上，还会额外填充一批默认标签（market type、region/zone），以便实现更灵活的放置。[查看文档，了解更多默认标签](https://docs.anyscale.com/configuration/compute/advanced#head-node)。默认标签列表如下：

| **标签名称** | **说明** | **Anyscale 支持** | **OSS 支持** |
| --- | --- | --- | --- |
| `ray.io/node-id` | 为该节点生成的唯一 ID。 | 是 | 是 |
| `ray.io/accelerator-type` | 节点的加速器类型，例如 L4。 | 是 | 是 |
| `ray.io/market-type` | 标明该节点用的是 spot 实例还是 on-demand 实例。 | 是 | 否* |
| `ray.io/node-group` | 该节点所属 worker group 的名称；头节点则为 head。 | 是 | 否* |
| `ray.io/region` | 节点所在的云 region。 | 是 | 否* |
| `ray.io/availability-zone` | 节点所在的可用区。 | 是 | 否* |

注：* 这些默认标签不会被自动填充。但只要它们在 `ray start` 参数中，或在 KubeRay CR 顶层的 `labels` 字段里被显式指定，你依然可以使用这些标签。

### autoscaling 集群

label selector 对静态集群和 autoscaling 集群都适用。

在 Anyscale 上，autoscaler 会同时考虑资源形状和 label selector，扩容合适的 worker group，从而拉起带有所需标签的节点。开源 Ray 中对 label selector 的 autoscaling 支持将在 Ray 2.51 发布。

## 它是怎么工作的？

当你提交任务，或创建 actor、placement group 时，Ray 会把对应的 label selector（`label_selector`/`bundle_label_selector`）附加到请求上。每个节点的 Raylet 都持有该节点的标签（在创建 RayCluster 时由用户定义，或由 Ray 自动探测，例如加速器系列），以及其他所有节点的元数据。Raylet 中的调度器会同时利用 selector 和节点标签信息来做放置决策：它既检查标签是否匹配，也照常做资源适配检查。只有两项检查都通过，这个请求才被判定为可以调度到该节点。

在 autoscaling 集群中，Ray 的 global control store（GCS）会聚合未被满足的需求，并把 label selector 连同资源要求一起发给 autoscaler。autoscaler 利用这些信息扩容合适的 worker group，从而拉起带有所需标签的节点。

## 后续工作

当前的 label selector 是一个很好的起点，但我们还计划把它做得更好。

- **回退 label selector（有序偏好）**：目前每个请求只携带一个 label selector。我们计划为任务/actor/placement group 的 bundle 支持按顺序回退，这样你可以表达带优先级的意图，例如优先 accelerator=H100，否则接受 accelerator in {A100,H100}。
- **库层面支持：**把 label selector 的支持扩展到 Ray 的各库（例如 Ray Data、Ray Serve、Ray Train），让常见的调度模式被自动处理。
- **与 Kubernetes 更好的互操作性： **我们希望在继承 Kubernetes Pod 标签、并以 Kubernetes 原生方式影响 Pod 调度这两件事上，做到尽可能简单。
