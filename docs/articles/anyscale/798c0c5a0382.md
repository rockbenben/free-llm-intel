# 通用 Serverless 平台的理想底座

作者：Ben Lorica、Eric Liang 和 Ion Stoica | 2020 年 11 月 5 日

#### 为什么 Ray 有望在未来的 serverless 产品中扮演核心角色

计算基础设施的历史，是长周期内稳步改进的历史。云计算带来了如今被视为理所当然的多种能力：免去硬件的预先投入、按需支付计算资源、弹性伸缩。近年来上云进程[持续加速](https://www.networkworld.com/article/3512885/enterprises-now-spend-more-on-cloud-infrastructure-services-than-on-premises-data-center-gear.html)，许多公司现在混合使用本地基础设施与[多家云服务商](https://gradientflow.com/one-simple-chart-most-companies-use-multiple-cloud-providers/)。

2015 年，AWS 推出 Lambda，提供*云函数*服务并引入*serverless 计算*概念。Serverless 与云函数在两个关键方面不同于传统云计算：（1）serverless 抽象掉基础设施（伸缩、服务器配置），让开发者专注于写程序；（2）serverless 提供更细的计费粒度（亚秒级，而传统云计算按分钟）。

自 AWS Lambda 发布以来，业界对 serverless 与云函数的兴趣[持续增长](https://trends.google.com/trends/explore/TIMESERIES/1597100400?hl=en-US&tz=420&date=2015-01-01+2020-08-10&geo=US&q=serverless&sni=3)，各大云厂商如今都有类似产品。[专家预测](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2019/EECS-2019-3.pdf) serverless 的重要性将继续提升，未来会有更多应用运行在 serverless 计算平台上。但我们仍处于 serverless 计算的早期阶段。一篇广为流传的 2019 年论文（[“A Berkeley View on Serverless Computing”](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2019/EECS-2019-3.pdf)）描述了"serverless 计算要兑现承诺仍需应对的挑战与研究机会"。

本文审视当前云函数（也称 *FaaS* 或 serverless）的一些局限。我们指出，分布式计算框架 [Ray](https://github.com/ray-project/ray) 应对了其中许多挑战，并论证 Ray 是[通用 serverless 框架](https://www.youtube.com/watch?v=vzMXTpdJSuk)的正确底座。

## Serverless：专用 vs 通用

已有多个努力试图扩展 serverless 的边界。[ExCamera](http://ex.camera/nsdi17/)、[PyWren](http://pywren.io/)、[TF-on-serverless](https://www.serverless.com/blog/using-tensorflow-serverless-framework-deep-learning-image-recognition)、[Spark-on-Lambda](https://www.qubole.com/blog/spark-on-aws-lambda/) 等项目尝试在 Lambda 这类 FaaS 平台上运行更复杂的负载。若干业界平台提供类 serverless 的能力与体验，包括 [Amazon Aurora](https://aws.amazon.com/rds/aurora/serverless/)、[Databricks](https://databricks.com/blog/2017-06-07/databricks-serverless-next-generation-resource-management-for-apache-spark.html)、[BigQuery](https://cloud.google.com/serverless/whitepaper) 等。然而，这些产品通常面向*特定负载*，并不旨在运行任意应用。我们在下表中定义这样一个框架（Ray）的特征及关键权衡：

## 为什么用 Ray 做通用 Serverless？

**Ray 隐藏了服务器**

与现有 FaaS 平台一样，Ray 把服务器从应用中抽象掉。从 1.0 版本起，用户启动应用时无需指定集群大小或实例类型，只需向 Ray 提供可用资源集合（例如 AWS 上的实例类型列表，或本地集群的节点及其能力清单），Ray 会自动挑选实例类型，并动态扩缩以匹配应用需求。

**Ray 支持有状态应用**

Serverless 平台将存储与计算分离地扩缩，因此其上的计算是无状态的。云函数不保存先前的交易或知识。典型流程是：执行一次计算（函数调用），把结果写入存储服务，需要时另一个函数再取走输出使用。

[Actor 模型](https://en.wikipedia.org/wiki/Actor_model#Fundamental_concepts)是一种强大的编程范式，聚焦消息传递语义，本地或远程都无缝工作。Ray 支持 [actor](https://en.wikipedia.org/wiki/Actor_model)——即有状态的 worker（或服务）。一个能支持有状态计算的 serverless 平台会成倍扩大可承载应用的版图。有状态算子让 Ray 能高效支持流式计算、[机器学习模型服务](https://anyscale.com/blog/heres-what-you-need-to-look-for-in-a-model-server-to-build-ml-powered-services)和 Web 应用。事实上已有公司把 Ray 用在流式与机器学习结合的应用中。例如，蚂蚁集团"基于 Ray 构建了多范式融合引擎，在单一系统中组合流计算、图计算与机器学习，用于实时反欺诈与在线营销"。

**Ray 支持任务之间的直接通信**

几乎每个分布式应用——如流计算或数据处理——都需要在任务之间交换数据。遗憾的是，现有 serverless 平台不允许函数间直接通信。两个函数互相通信的唯一途径是经 S3 这类云存储系统，而这样又慢又贵。

相反，Ray 允许任意任务与 actor 相互通信，使应用能高效交换数据并实现任意的通信模式。

**Ray 让开发者能访问硬件加速器**

开发者最清楚哪种硬件资源最适合其应用，因此把资源控制权交给他们是任何计算平台的重要特性。FaaS 服务目前只让开发者指定执行时长上限与内存大小。但在某些应用中——尤其是机器学习模型训练——开发者需要访问特定加速器（GPU、TPU 等）。现阶段 FaaS 提供商不提供这种程度的资源控制。

构建在 Ray 之上的 serverless 平台在资源指定方面没有限制。Ray 用户已经可以描述所需的硬件资源（CPU、GPU、TPU 及其他加速器的数量）。未来版本的 Ray 甚至允许开发者指定精确的芯片型号（例如"两块 V100 GPU"）。

**Ray 提供开源 API**

编写 serverless 应用并不存在"标准 API"。我们相信 Ray 是这样一套开放 serverless API 的有力候选。Ray 允许开发者编写通用程序，而不仅是函数；它同时支持无状态与有状态应用，并覆盖广泛使用的编程语言（Python 与 Java，后续更多）。事实上，Ray 通常被描述为一个能以最小心力扩展应用的分布式计算平台。

**Ray 支持细粒度协调与控制，从而带来更好性能**

许多应用对数据局部性与调度的控制至关重要，包括那些需要在计算节点间分发和共享数据的大量应用。当前 serverless 产品不适合这类应用。例如，用 serverless 执行机器学习梯度计算的开发者，无法控制数据与云函数位于何处。另一个例子来自强化学习：开发者会希望在同一计算节点上训练策略并执行 rollout。

Ray 通过提供数据局部性与调度控制克服这些限制。使用 Ray 的开发者可以指定哪些 actor 应运行在同一台机器上。

**Ray 没有运行时限制**

当前产品（[Lambda](https://aws.amazon.com/about-aws/whats-new/2018/10/aws-lambda-supports-functions-that-can-run-up-to-15-minutes/)、[Cloud Functions](https://cloud.google.com/functions/docs/concepts/exec#:~:text=Function%20execution%20time%20is%20limited,period%20up%20to%209%20minutes.)、[Azure Functions](https://build5nines.com/azure-functions-extend-execution-timeout-past-5-minutes/#:~:text=One%20of%20the%20biggest%20benefits,originally%20set%20to%205%20minutes.)）的执行时长上限约为 15 分钟或更短，这限制了 FaaS 平台能支持的应用类型。而 Ray 运行于现有云或集群之上，没有时间限制。

## 但成本呢？

Serverless 最受欢迎的特性之一是按用量计费。Serverless 平台以毫秒为计量单位，传统云计算则以分钟计。

由于云厂商按实例层级收费，作为（开源）软件层的 Ray 自身无法足够快速地创建和释放计算资源以实现细粒度计量。例如，你在一个 32 核服务器上只跑了一个 actor，云厂商大概率按 32 核收费。Ray 无法弥合这种利用率与成本间的落差。要走到细粒度计量，需要在 [Ray 之上构建一个 serverless 平台](https://www.anyscale.com/product)。

话虽如此，Ray 能在几分钟内自动分配新实例并关停既有实例。因此，Ray 已能为运行 30 分钟这类较粗粒度的作业提供 serverless 能力。属于粗粒度作业范畴的例子包括流计算、模型训练与模型服务。

最后，Ray 对粗粒度负载也有带来大幅成本节约的潜力。云函数的成本可能比 100% 利用率运行的云计算实例高 4-5 倍。事实上，截至写作时，3GB 内存的 AWS Lambda [每 100ms 收费 $0.0000048958](https://aws.amazon.com/lambda/pricing/)，即每小时 $0.1762488；相比之下，4GB 内存的 t3.medium 实例[只要 $0.0416/小时](https://aws.amazon.com/ec2/pricing/on-demand/)，便宜 4.2 倍；按每 GB 内存计价则便宜 5.65 倍。这还是低估，因为它没把每请求费用算进去。

## **总结**

早在 2016 年，[专家们就已经指出](https://youtu.be/wYCLbLrEoqs?t=95) serverless 工具能让团队快速构建功能强大、可扩展的应用。此后，越来越多的开发者转向 serverless 技术构建应用。但 serverless 要兑现承诺，当前的产品（云函数）需要解决本文列出的种种局限。

各公司仍处于探索 serverless 技术的早期。我们相信 Ray 是通用 serverless 框架的理想底座。随着 AI 与其他数据密集型应用的兴起，Ray 有望在未来的 serverless 产品中扮演核心角色。
