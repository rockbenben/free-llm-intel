# uv + Ray：集群里无痛的 Python 依赖管理

作者：[Christina Zhu](https://www.anyscale.com/blog?author=christina-zhu) 与 [Philipp Moritz](https://www.anyscale.com/blog?author=philipp-moritz) | 2025 年 2 月 27 日

![uv + 博客头图 2](https://images.ctfassets.net/xjan103pcp94/2KhO6m2ouQYf5yJ3qF8iN0/cfbb66f0fd3e12d10c8a6323a3a31a65/Illustration_Dark_mode_updated.png?w=1200)

当我们发现 [uv 包管理器](https://docs.astral.sh/uv)时，我们意识到 Python 包管理的一个新时代已经到来。它以一致性和速度直击 Python 开发者的依赖难题，也让快速的开发迭代成为可能。

下面是 [astral.sh](http://astral.sh) 团队做对、而且我们特别喜欢的一些事情（并不穷尽）：

- **它们把整个环境都打包好了**：你不用再操心自己搭一套 Python 发行版——光是这件事本身就够麻烦的。把 [Python 环境交给 uv 来管理](https://docs.astral.sh/uv/concepts/python-versions/)就好。如果你愿意，uv 也支持使用系统安装的 Python。
- **他们把 uv 做得飞快：** 首先，它是用 Rust 写的，就像他们那款大获成功的 Python linter [ruff](https://github.com/astral-sh/ruff)。它围绕速度而设计，能快速下载包、把它们[缓存](https://docs.astral.sh/uv/concepts/cache/)到本地磁盘、在各个环境之间对依赖去重，并用硬链接把它们归拢到一起。
- **他们尊重既有 Python 惯例，并在此基础上做得更好：** 其中包括支持 [pyproject.toml](https://docs.astral.sh/uv/guides/projects/#pyprojecttoml)、出色的跨平台 [lockfile](https://docs.astral.sh/uv/concepts/projects/layout/#the-lockfile)支持、[可编辑包](https://docs.astral.sh/uv/concepts/projects/dependencies/#editable-dependencies)、[环境变量](https://docs.astral.sh/uv/configuration/files/#env)等等——新的能力不断加入，bug 也[一直在修](https://github.com/astral-sh/uv/blob/main/CHANGELOG.md)。

不过在分布式场景下，管理 Python 依赖仍然有挑战。集群上有大量进程要管，我们得确保它们所有依赖彼此一致。只要改动一个依赖，就得把这个改动传播到其余每一个节点，因为每个 worker 进程都需要相同的环境，好让所有代码都以同样的方式执行。一旦哪里出现版本不匹配，你可能就要花上好几个小时去 debug 到底哪里出了问题……这绝不是有意思的消遣。传统的解决办法是把一切都容器化，但这会让开发迭代慢得多——一旦代码和依赖有变动，就得重新构建一个新版本的容器并推送到所有节点。有时整个集群都要重启，于是更慢。

如果你只要跑一句 `uv run ... script.py` 就能启动一个分布式 Python 应用，而动态创建出来的环境会自动作用到集群上的每一个进程，那该多好？*剧透一下*：这正是我们要做的。先来看一个用 Ray 的简单例子。[Ray](https://docs.ray.io/en/latest/) 是一个计算引擎，为的就是让开发和运行分布式 Python 应用——尤其是 AI 应用——变得轻松。

由于这是[最新 Ray 2.43 版本](https://github.com/ray-project/ray/releases)的一项新功能，你目前需要先设置一个 feature flag：

```
1export RAY_RUNTIME_ENV_HOOK=ray._private.runtime_env.uv_runtime_env_hook.hook
```

我们计划，在从大家那里[收集到更多反馈](https://github.com/ray-project/ray/issues/50961)、必要时调整其行为之后，把它变成默认。

一旦设置好这个环境变量，Ray 就会自动检测到你的脚本是在 uv run 里运行的，并在同一个环境里启动所有 worker 进程。我们先看一个非常简单的例子。新建一个 `main.py` 文件，内容为：

```
1import emoji
2import ray
3
4@ray.remote
5def f():
6    return emoji.emojize('Python is :thumbs_up:')
7# Execute 1000 copies of f across a cluster.
8
9print(ray.get([f.remote() for _ in range(1000)]))
```

然后用下面这条命令运行它：

```
1uv run --with emoji main.py
```

这会在一个 Ray 集群里，跨若干 Python worker 进程运行 `f` 函数的 1000 份副本。`emoji` 这个依赖除了主脚本能用，所有 worker 进程也能用。此外，当前工作目录里的源代码对所有 worker 也都可见。

就这么简单！用 Ray + uv，你可以像平时在单机上用 uv 那样，为分布式应用管理 Python 依赖。

### 使用 uv 的端到端示例

接下来，我们走一个更详细的例子，看看 uv 怎么用，并深入它一些好用的特性。我们会创建一个用 Ray Data 跑 batch inference 的应用，用的是[全新的 LLM 集成](https://docs.ray.io/en/latest/data/working-with-llms.html)。先创建一个带上所需依赖的 pyproject.toml：

```
1[project]
2name = "my_llm_batch_inference"
3version = "0.1"
4dependencies = [
5  "numpy",
6  "ray[llm]",
7]
```

为了让 vLLM 正常工作，你可能需要运行下面这条：

```
1sudo apt-get update && sudo apt-get install -y build-essential
```

再准备一个 `batch_inference.py` 脚本，内容如下：

```
1import ray
2from ray.data.llm import vLLMEngineProcessorConfig, build_llm_processor
3import numpy as np
4
5config = vLLMEngineProcessorConfig(
6    model_source="unsloth/Llama-3.1-8B-Instruct",
7    engine_kwargs={
8        "enable_chunked_prefill": True,
9        "max_num_batched_tokens": 4096,
10        "max_model_len": 16384,
11    },
12    concurrency=1,
13    batch_size=64,
14)
15processor = build_llm_processor(
16    config,
17    preprocess=lambda row: dict(
18        messages=[
19            {"role": "system", "content": "You are a bot that responds with haikus."},
20            {"role": "user", "content": row["item"]}
21        ],
22        sampling_params=dict(
23            temperature=0.3,
24            max_tokens=250,
25        )
26    ),
27    postprocess=lambda row: dict(
28        answer=row["generated_text"],
29        **row  # This will return all the original columns in the dataset.
30    ),
31)
32
33ds = ray.data.from_items(["Start of the haiku is: Complete this for me..."])
34
35ds = processor(ds)
36ds.show(limit=1)
```

要运行这个应用，把 `pyproject.toml` 和 `batch_inference.py` 两个文件放到同一个目录，然后用 `uv run batch_inference.py` 执行。

注意，这只是一个非常简单的例子：跑一个小模型，数据是用 `ray.data.from_items` 加载的一个只含一条数据的内存数据集；但你可以用 Ray Data 支持的任意[数据源](https://docs.ray.io/en/latest/data/loading-data.html)来加载数据、任意[数据汇](https://docs.ray.io/en/latest/data/saving-data.html)来写结果，以及 vLLM 支持的任意模型来做 inference。

如果你想用一个 gated（需申请授权）的 Hugging Face 模型，可以在工作目录里建一个 `.env` 文件，像这样：

```
1HF_TOKEN = your_huggingface_token
```

然后用 `uv run --env-file .env batch_inference.py` 运行代码。

如果你想改某个依赖，可以把它 clone 到一个相对 `working_dir` 的路径 `./path/foo`，然后运行 `uv add --editable ./path/foo`。这会在你的 `pyproject.toml` 里追加一段，告诉 uv 用检出的（并被你改过的）代码，而不是原来的包。

### 它在底层是怎么工作的？

![uv ray 图 1](https://images.ctfassets.net/xjan103pcp94/2rjcTtNwdOmuzfEHsVGTdv/70cdcb1e017635119e0e27f1007a0df3/Managing_Dependencies_for_Ray_Applications_with_UV.png)

uv ray 图 1

**图：**没有 uv 时，script.py 跑在默认的 python 环境里，而它可能和 workers 运行所在的 runtime environment 不一样（左）；有了 uv，各环境通过「uv run」被同步，而环境的创建又因 uv 的缓存而提速

底层上，这套集成用的是 Ray 的[运行时环境](https://docs.ray.io/en/latest/ray-core/handling-dependencies.html)（runtime environment）功能，它允许在代码里指定环境。我们定义了一个新的底层 runtime environment 插件，叫 [py_executable](https://docs.ray.io/en/latest/ray-core/handling-dependencies.html#using-uv-for-package-management)。它让你指定用来启动 Ray workers 的 Python 可执行文件（含参数）。就 `uv` 而言，`py_executable` 被设成 `uv run`，并带上当初运行 driver 所用的同一批参数。此外，`working_dir` 这个 runtime environment 被用来把 driver 的工作目录（包括 `pyproject.toml)`传播给 workers。这样 `uv` 就能为 workers 配好运行所需的依赖和环境。

有一些进阶用法，你可能想在自己的程序里直接使用 `py_executable` 机制：

- **依赖异构的应用：** Ray 支持给不同的 task 或 actor 用不同的 runtime environment。这在不同 [Ray Serve 部署](https://docs.ray.io/en/latest/serve/production-guide/handling-dependencies.html#dependencies-per-deployment)里分别部署不同 inference 引擎、模型或微服务时很有用，Ray Data 里的异构数据流水线也一样。要实现这一点，你可以为每个不同的 runtime environment 指定不同的 `py_executable`，并给每个配上不同的 `--project` 参数来跑 `uv run`。可参考[这个仓库](https://github.com/pcmoritz/ray-isolated-environments)作为例子。
- **自定义 worker 运行的命令：** 在 workers 上，你可能想用一些 driver 用不到的特殊参数来定制 uv。又或者，你想用 poetry run、像 bazel 这样的构建系统、profiler 或 debugger 来运行进程。这些情况下，你都可以通过 `py_executable` 显式指定 worker 要跑在哪个可执行文件里。如果你要用更复杂的方式把多个进程包在一起，它甚至可以是一个存放在 `working_dir` 里的 shell 脚本。

### 在 Ray Job 里使用 uv

要在 Ray Job 里用 uv，这样提交运行作业：

```
1ray job submit --runtime-env-json '{"working_dir": ".", "py_executable": "uv run"}' -- uv run main.py
```

这能确保这个作业的 driver 和 workers 都跑在你的 `pyproject.toml` 所指定的 `uv` 环境里。

### 在 Ray Service 里使用 uv

要在 Ray Serve 里用 uv，像上面那样设置 `RAY_RUNTIME_ENV_HOOK`，然后用 `uv run serve run app:main` 运行服务。

### 最佳实践与小贴士

- 用 `uv lock` 生成 lockfile，把所有依赖冻结下来，这样某个包发布了新版本时，事情也不会以失控的方式发生变化。
- 如果你有一个 `requirements.txt` 文件、又不想用 `--with-requirements` 旗标，你可以用 `uv add -r requirement.txt` 把依赖加进你的 project.toml，之后配合 uv run 使用。
- 需要时，你可以通过 `UV_SYSTEM_PYTHON=1` 使用系统 python。
- 如果你的 `pyproject.toml` 在某个子目录里，你可以用 `uv run --project` 从那里用它。
- 如果你用 `uv run`，又想把工作目录设成不是当前工作目录的地方，就用 `--directory` 旗标。Ray 的 uv 集成会相应地把你的 `working_dir` 设置好。

### 我们 uv x Ray 开源工作的亮点

作为一个新开源项目的热心支持者，我们很幸运：一些 Ray 用户在这个功能正式发布之前就上手用了它，并提出了改进建议，谢谢你们！既然我们已随 Ray 2.43 把这个功能发布出来，我们希望收到更多反馈。

衷心感谢 uv 的维护者们和我们讨论这套集成，并迅速[修好了一个 bug](https://github.com/astral-sh/uv/issues/11219)——它出现在 Ray 里并发创建 uv 环境的时候。

### 结语

把 uv 和 Ray 结合，让分布式系统的 Python 依赖管理显著提升：uv 的快速环境搭建配上 Ray 可扩展的编程模型，保证了 worker 在整个集群上一致地执行。我们努力把 Ray + uv 做成以分布式方式运行代码的最佳方案，欢迎你在 [GitHub](https://github.com/ray-project/ray/issues/50961) 或 [Discourse](https://discuss.ray.io/) 上给我们反馈。

话虽如此，也有一些场景 uv 并不是可行的方案——你可能在一个成熟项目里，把不同的包管理器、仓库和二进制拼装在一起；又或者你身处一个有非常具体要求的企业环境。在 Anyscale，我们正在做一套依赖管理方案，它基于我们 OCI 兼容的[快速容器运行时](https://www.anyscale.com/blog/cloud-infrastructure-for-llm-and-generative-ai-applications#faster-instance-startup-time:-a-step-change-in-performance-for-genai-and-llm-applications)，既能支撑极快的开发迭代，也能满足各种各样的依赖需求。如果你对此感兴趣，不妨上手试试 [Anyscale Platform](https://www.anyscale.com/)。
