# Ray Data 中的 Shuffle V2：更快、容错的 Join 与聚合

作者：You-Cheng Lin 和 Yuanzhuo Yang | 2026 年 8 月 25 日

无论产出是训练语料、一批模型预测还是一份评估报告，同样的操作总是反复出现：对数十亿条记录去重、跨数据源 join 特征/模态/模型输出、计算分组统计以便过滤、采样与打分。而这些操作每一个都是 shuffle。

Shuffle 是 Ray Data 唯一无法流式化处理的操作。map 或 write 拿到一个块、变换它、传给下游，峰值内存跟着块大小走而非数据集大小。而 groupby、join 与 repartition 要求共享一个 key 的每一行被汇集到同一处，于是 shuffle worker 要持有整个分区，分区大小等于数据集除以分区数。数据多十倍，这个 worker 的内存就要多十倍。

Pipeline 就在 shuffle 处失败，OOM 就在这里发生，一个在 100GB 跑得好好的作业就在 1TB 处倒下。

Shuffle V2 是对 Ray Data shuffle 引擎的重新设计。它把 shuffle 中间结果物化在对象存储中，而不是堆积在一个长生命周期的 aggregator 里，由此带来：

- **稳定性：** 分片（shard）活在对象存储里，写满时溢出到磁盘，中间结果不再堆在 worker 堆内存中。
- **可扩展性：** map 与 reduce 都是普通任务，Ray 按集群当前空余决定同时运行多少个，而不是在数据到来之前就定死一个数目。
- **效率：** 解耦的设计容许旧引擎无法表达的优化：向量化聚合、跨 shuffle 边界的融合与压缩。

## V1 在哪里崩坏

当前的 Ray Data shuffle 依赖一组长生命周期的 aggregator actor。map 任务把各自的块分区，并把每个分片提交给拥有该分区的 actor。Actor 把这些分片一直持有到 shuffle 完成，再把每个分区定稿为输出块。

*Ray Data shuffle*

当前设计有一个致命特性——**分区状态累积在长生命周期 actor 的堆内存里。由此引出各种问题。**

**1. 数据集不能大于内存**
属于某分区的每个分片都在其 aggregator 的堆内存里待到 shuffle 结束，因此峰值时整个集群必须同时在各 actor 堆内存里装下整个数据集。

代价多大取决于操作。可归约聚合——sum、count、unique——能在分片到达时就折叠进滚动结果，其状态受不同分组数而非数据集约束。拼接型操作不行：join 或按 key 的 repartition 必须保留收到的每一行、到定稿时才合并，aggregator 最终持有整个分区。

**2. 丢失的状态无法重建**
分区只存在于累积它的 actor 内部，别处没有带 lineage 跟踪的副本可供 Ray 重建。丢一个 aggregator，就丢掉它拥有的全部分区，shuffle 无法恢复。

**3. Aggregator 池只按估计值定容一次**
池的大小由最初几个输入 bundle 的样本决定，远早于大部分数据被见到。倾斜的数据集或不具代表性的样本，会让池与真实到来的数据不匹配，而 shuffle 一旦开始就没有办法调整它。

**4. 预留被持有整个 shuffle 期间**
Aggregator 是预先预留的，因此 `num_aggregators x num_cpus` 从池启动一直到最后一个分区定稿都被占用，无论这些 actor 是否在干活。留给其他算子的资源所剩无几。

## 架构

V2 把 shuffle 拆成两个普通阶段，中间隔着对象存储。

**Map 阶段**按 key 分区每个输入块，每个分区返回一个分片——每个任务返回 `num_partitions + 1` 个值，一个元数据、每个分区各一个。每个分片编码为 Arrow IPC 缓冲区，可选压缩，作为拥有自己引用的独立对象落入对象存储。

**Reduce 阶段**每个任务负责一个分区。Reduce 任务收到其分区的分片引用，分批拉取、解码并应用聚合。没有任何东西被推进它；它在自己就绪时取回所需。

就这一个改动——中间结果活在对象存储而非 actor 堆内存——逐一化解了 V1 的问题。

*ShuffleMapOp、对象存储、ShuffleReduceOp*

**1. 溢出取代内存天花板**
分片是对象存储对象，对象存储在压力下会溢出到磁盘，shuffle 中间结果不再受 RAM 封顶。

**2. 利用 Ray Core 的 lineage 重建**
分片就是普通 Ray 对象。丢失的分片通过重新执行产出它的 map 任务来重建。因此丢失任何单个分片都不会导致整个作业失败。

**3. Reducer 内存来自实测**
不再依赖 shuffle 前的估计来决定 reducer actor 的规模，而是直接测量分区分片的真实大小，缓解估计不准造成的 reducer OOM。

**4. 没有阶段霸占另一个阶段需要的资源**
没有 aggregator 池，就没有任何东西在整个 shuffle 期间预留 CPU。map 与 reduce 在被调度时获取资源、结束时归还，容量流向真正有活的阶段——上游 read、map 阶段或某个 reduce 任务——而不是在等着分片到来的 actor 里空转。

## V2 解锁了什么

两个普通阶段之间的物化边界，不仅更安全，也更容易优化。下面每一项都是 aggregator 设计无法表达的。

### 输入合并（Input coalescing）

每个 map 任务对每个分区输出一个分片，因此 shuffle 产生 `map_tasks x partitions` 个中间对象。若每个输入块一个 map 任务，这个数随输入块数增长，很快到了 head 节点管不过来这些对象而 OOM 的地步。

合并缩小的是两个因子中的第一个——map 任务数。块被缓冲，一旦缓冲达到 `shuffle_input_batch_bytes`（默认 1 GiB）就合并进一个 map 任务，于是任务更少更大、分出的分片按比例更少，而搬运的数据量不变。缓冲按节点分组，因此合并后的任务恰好运行在其输入所在的节点，避免额外的对象传输。

### 中间分片压缩

分片是 Arrow IPC 缓冲区，IPC 写入选项带 codec——默认 `zstd`，通过 `hash_shuffle_compression` 也可选 `lz4` 或不压缩。这帮我们削减中间对象的数据大小，节省空间并提升对象传输性能。

*Ray Data - Shuffle 压缩 - TPC-H SF1000 Inner Join*

为展示压缩的收益，我们在 Ray 2.58 上、1 台 m5.2xlarge head 节点加 32 台 m5.4xlarge worker 上跑了 SF1000 join 基准。`zstd` 压得更狠但 CPU 成本更高；`lz4` 压得少但 CPU 便宜得多。

与不压缩相比，`zstd` 把溢出字节减少 91%、运行时间减少 26%。`lz4` 溢出比 `zstd` 多，但仍减少 68% 溢出字节、21% 运行时间。`zstd` 多花的 CPU，被它挡在溢出路径外的字节成倍偿还了。

选哪个 codec 取决于作业卡在哪：`zstd` 用 CPU 换更少的字节，`lz4` 反之。shuffle 受 IO 瓶颈时选 `zstd`，受 CPU 瓶颈时选 `lz4`，数据本身已压缩时选不压缩。

### 跨 shuffle 边界的融合

紧跟在 reduce 下游的 map 会被折叠进 reduce 任务本身。`groupby().sum()` 后接 `map_batches()` 不再需要把聚合结果写出再读回；map 直接在 reduce 任务内对已在内存中的块运行，一次物化就此消失。

目前只有边界这一侧能融合。上游 map 还不能折叠进 map 阶段，因为合并在决定 map 任务处理什么之前会跨 bundle 缓冲块，决策时并不存在可融合的单一上游任务。把两者调和——既保持低对象数、又吸收上游 map——是我们打算做的工作。

### 向量化聚合

V1 在 Python 里逐组迭代聚合、每组累积一个结果。V2 把整个块交给 Arrow 原生 group-by，map 侧与 reduce 侧都是如此——聚合成为对整个块的一次列式运算，而不是循环各组。

目前有九个聚合被向量化：`Count`、`Sum`、`Min`、`Max`、`Mean`、`MissingValuePercentage`、`ZeroPercentage`、`Unique` 与 `CountDistinct`。

仅这一项就让 `aggregate_groups` 测试取得 30 倍以上的性能提升。

## 磁盘 Shuffle

输入合并减少了中间对象数量，但没有消除天花板。driver 仍然持有每个分片的引用，而其可跟踪的对象数有硬上限。这个数量在两端都侵蚀吞吐：map 任务往对象存储放大量小对象、reduce 任务一次性解引用大量对象，都比整块搬运同样字节更慢。

为把边界推得更远，disk shuffle 把对象存储完全移出数据路径。三个改动使其成立。

**1. 中间数据绕过对象存储**

Map 输出直接写本地磁盘而不进 plasma，shuffle 数据从此不占对象存储内存，也无需支付溢出的代价。

**2. 每个 mapper 一个文件，按 offset 索引**

Mapper 写单个文件，返回一个持有其路径与逐分区 (offset, length) 索引的句柄。`map_tasks x partitions` 的对象数坍缩为每个 mapper 一个句柄，reduce 任务从每个文件中按字节区间读出自己的分区。

**3. 每个节点一个 Arrow Flight 服务器**

每个节点运行一个 detached actor，通过 Arrow Flight 提供分区区间服务——分片以 Arrow record batch 在专为搬运列式数据而生的协议上旅行，而不是自造线格式。每节点一个文件服务器服务所有读取；reducer 在每节点的单条 Flight 连接上批量提交字节区间，服务器按请求顺序以 seek + read 取每个区间。

我们计划在 **2.59** 发布 disk shuffle。

## 基准测试

下文所有数字来自 Ray Data 发布测试套件中的 TPC-H 数据，SF1000 规模，集群为 1 台 m5.2xlarge head 节点 + 32 台 m5.4xlarge worker，运行 Ray 2.58。每种配置资源完全相同；每张图报告其中三种：V1 hash shuffle、关闭向量化聚合的 V2、以及出厂形态的 V2。每次运行还把 Ray 的 inline 阈值调低为 `RAY_max_direct_call_object_size=8192`，避免小分片经由 driver 内联传输（可能让 driver OOM；该配置的更多信息见[调优指南](https://docs.ray.io/en/releases-2.58.0/data/data-internals.html#tuning-shuffle-v2)）；唯一例外是 V1 join 配置，使用 100 KiB 默认值。中间那根柱是为了分离架构的贡献与向量化的贡献——结果发现它们对不同负载各自重要。

标注 timeout 的柱子没有跑完。它们的加速比是相对超时值计算的下界，真实差距比所示数字更大。

两种效应解释了几乎全部差异，何者主导取决于负载。

**聚合主导之处，向量化取胜。** TPC-H `q21` 与 `aggregate_groups` 案例把大部分时间花在聚合 combiner 上，把这份工作交给 Arrow 原生 groupby 还能再值 20 倍——`q21` 单靠架构从 6.3k 秒降到 2.4k 秒，加上向量化后到 119 秒，端到端 53 倍。中间柱也显示了架构单独会输的地方：`q1`、`q13`、`q15` 比 V1 更慢（361s 对 240s，372s 对 272s）。这发生在真正被 shuffle 的数据很少时——上游的 filter 或 projection 让 shuffle 很小，V2 额外的编码与对象存储往返的成本就超过了架构节省。向量化生效后，V2 在每个查询上都赢了。

**V1 根本跑不完之处，架构取胜。** Join 与 map_groups 不跑聚合 combiner，向量化无处发力，只剩架构。在这一数据规模下，V1 的 aggregator 池在整个 shuffle 期间持有 CPU 预留，map 阶段只能争夺剩下的资源。V2 没有池要预留：map 与 reduce 在调度时取资源、结束时归还，容量流向有活的阶段。四种 join 全部在约 320 秒内完成。

## 启用方式

从 Ray 2.58 起，可以通过以下方式启用 shuffle V2：

```
from ray.data.context import DataContext, ShuffleStrategy

DataContext.get_current().shuffle_strategy = ShuffleStrategy.HASH_SHUFFLE_V2
```

即将发布的 Ray 2.59 会把该策略重命名为 `SHUFFLE_V2`，因为它已不再专属 hash 分区。`HASH_SHUFFLE_V2` 保留为别名，上面的代码片段继续有效。

更多细节见[调优指南](https://docs.ray.io/en/releases-2.58.0/data/data-internals.html#tuning-shuffle-v2)。

## Shuffle 策略版图

启用 V2 意味着设置一个 shuffle 策略，Ray Data 目前暴露五个：`HASH_SHUFFLE`（V1，今日默认）、`HASH_SHUFFLE_V2`、`GPU_SHUFFLE`、`SORT_SHUFFLE_PULL_BASED` 与 `SORT_SHUFFLE_PUSH_BASED`。

随着 V2 扩展到仍由 sort 引擎服务的算子，这些策略与 V1 将很快弃用，最终只剩 `SHUFFLE_V2` 与 `GPU_SHUFFLE` 两个。

## 下一步

### 把 `Sort` 与 `random_shuffle` 迁到 V2

`sort()` 与 `random_shuffle()` 目前仍运行在 sort 引擎上。把它们迁到 V2 的物化分片，正是让这些策略得以退役的前提。

### 增量 Join

今天的 join 会把两个输入的分区全部物化，再连同整个输出表一起物化。若从一侧构建哈希表、另一侧按批流过它，内存就受"build 侧 + 一个 batch"约束。这依赖 Arrow 26.0.0；该版本落地后我们就会支持。

## 立即试用

Shuffle V2 归结为一个决策：shuffle 中间结果活在对象存储，而不是长生命周期 actor 的堆里。其余一切由此而来。可溢出、带 lineage 追踪的分片，正是 V1 跑不完的 join 与 map_groups 如今能完成的原因；两个普通阶段加一条物化边界，则是合并、压缩、融合与 Arrow 原生聚合得以叠加其上的基础。

如果你的流水线在真实规模上做 groupby、join 或按键 repartition，V2 今天就值得打开。敬请关注，并参阅[指南与内部机制文档](https://docs.ray.io/en/releases-2.58.0/data/data-internals.html#shuffle-v2)了解更多！
