# 发布 Ray Direct Transport：Ray Core 支持 RDMA（上篇）

作者：Stephanie Wang、Qiaolin Yu、Dhyey Shah、Ricardo Decal 和 Richard Liaw | 2025 年 11 月 3 日

*Tl;dr：Ray Direct Transport 通过 RDMA 支撑的传输层，让 Ray 中的 GPU 传输快速而直接。学习如何用这个 API 为 LLM 强化学习等用例构建分布式系统。*

由于需要**灵活编排分布式 GPU**，Ray 在 LLM 强化学习（RL）领域迎来了大规模采用。Ray 提供分布式编排 API，让 RL 基础设施构建者可以组合训练与推理引擎、实现不同的放置与调度策略，并在不同框架和工具之间传输 rollout 数据与权重。

Ray 的 API 简化了编排，但许多 RL 负载需要在 **GPU 之间高效处理和传输大张量**，而这并不能被 Ray 基于 CPU 的对象存储很好支持。Ray 对象存储对驻留 CPU 内存的对象提供高带宽共享读取，却无法利用 Infiniband、NVLink 这类 GPU 到 GPU 直传的高性能通道。

今天我们推出 **Ray Direct Transport（RDT）**——Ray Core 的新特性，让用户能轻松利用 NVLink 或基于 Infiniband 的 RDMA（远程直接内存访问）等高带宽 GPU 间通信机制。使用 RDT，只需改动几行代码，GPU-GPU 传输就能比 Ray 原生对象存储**快最多 1000 倍**。

*Ray Direct Transport - 图 1*

为说明其工作方式，我们先介绍 LLM 强化学习的系统需求，然后演示如何用 RDT API 写一个能塞进单块 GPU 的简单 RL 训练脚本。我们用 RDT 管理 worker 间的数据传输，并展示如何在 [NCCL](https://developer.nvidia.com/nccl) 与 [NIXL](https://github.com/ai-dynamo/nixl/blob/main/README.md) 等库之间切换通信后端。

现在就可以用 [Ray 2.51.1](https://github.com/ray-project/ray/releases/tag/ray-2.51.1) 试用 RDT，从[文档](https://docs.ray.io/en/latest/ray-core/direct-transport.html)开始。

## LLM 强化学习的系统需求

与其他负载相比，LLM 强化学习有一套独特的系统需求。

*Ray Direct Transport - 图 2*

具体而言，RL 训练循环内有两个通信密集的步骤：

- *权重同步*：从训练框架到推理框架。每个训练 step 产生新的模型权重，框架需要把更新后的权重发给每个推理引擎副本。对大模型与集群，这可能是数百 GB 乃至 TB 级的数据传输。
- *Rollout 数据传输*：从推理到训练。纯文本模型产生的数据相对小，但对多模态模型这可能成为性能问题。

我们构建 RDT，以支持**通过专用数据传输层高效传输大对象**——尤其是那些用 RDMA 削减软件开销的传输：

- *大对象：* 随着模型增大，每个训练 step 所需的数据传输量急剧上升。因此减少不必要的数据拷贝、序列化等软件开销至关重要。
- *专用数据通道：* 现代 GPU 常配备 NVIDIA NVLink 这类高带宽互联，能大幅加速数据传输。同时，最快的传输方式因集群而异。用户应当能轻松选择并高效利用每个节点上可用的传输。

RDT 支持这些用例的方式是：让你用标准 Ray API 声明 actor 任务之间的数据依赖，但由你选择数据传输用哪种通道。当前 RDT 支持 [Gloo](https://github.com/pytorch/gloo) 与 NVIDIA 的 [NCCL](https://developer.nvidia.com/nccl)、[NIXL](https://github.com/ai-dynamo/nixl/blob/main/README.md) 库；未来版本将支持 CUDA IPC 等其他通道，并把传输层做成可插拔，允许自带 transport。

## 深入 Ray Direct Transport

先了解 API 如何工作。我们基于 [Ray Core API](https://docs.ray.io/en/latest/ray-core/key-concepts.html)，为 RDT 对象添加注解。

*图：Ray Direct Transport 架构图。Actor 任务可以返回与加载 GPU 张量。Actor 绕过 Ray 对象存储，用第三方 RDMA 通道（如 NVIDIA NCCL）直接交换数据。Driver 持有 RDT 对象元数据并协调传输。*

*Ray Direct Transport - 图 3*

**注：** 截至 Ray v2.50，RDT 仅对 Ray actor 可用，且只有 `torch.Tensor` 数据会经 RDT 通道传输。如果 `torch.Tensor` 嵌套在其他 Ray 对象里（例如 actor 返回一个 `torch.Tensor` 列表），非 `torch.Tensor` 数据仍会经 Ray 对象存储传输。

开始：定义一个 actor 类与一个返回 `torch.Tensor` 的任务：

```
1import torch
2import ray
3
4@ray.remote
5class MyActor:
6    def random_tensor(self):
7        return torch.randn(1000, 1000)
```

接着，用 `@ray.method(tensor_transport=transport_mode)` 装饰该 actor 任务，transport mode 可以是 "nccl"、"nixl"、"gloo" 或 "object_store"。这个例子我们用 [NIXL](https://github.com/ai-dynamo/nixl)，它支持 GPU-GPU 与 CPU-CPU 传输。

```
1@ray.remote
2class MyActor:
3    @ray.method(tensor_transport="nixl")
4    def random_tensor(self):
5        return torch.randn(1000, 1000)
```

这个装饰器可以加在任何返回 `torch.Tensor`、或返回嵌套在其他 Python 对象中的 `torch.Tensor` 的 actor 任务上。加上这个装饰器后，Ray 的行为会发生如下变化：

- 返回张量时，Ray 存的是张量的*引用*，而不是把它拷贝进基于 CPU 的 Ray 对象存储。
- 当 `ray.ObjectRef` 被传给另一个任务时，Ray 会用 NIXL 把张量传给目标任务。

注意，要让第（2）点生效，[`@ray.method(tensor_transport)`](https://docs.ray.io/en/latest/ray-core/api/doc/ray.method.html#ray.method) 装饰器只需加在*返回*张量的 actor 任务上；不要把它加在*消费*张量的 actor 任务上（除非那些任务也返回张量）。本例还假设张量的生产方与消费方都装了 NIXL。`pip install nixl` 是最简单的安装方式；要最佳性能，请查看[NIXL 源码构建说明](http://github.com/ai-dynamo/nixl/tree/main/contrib)。

现在就可以创建 RDT 对象并在 actor 之间传递。完整示例：

```
1import torch
2import ray
3
4@ray.remote
5class MyActor:
6    @ray.method(tensor_transport="nixl")
7    def random_tensor(self):
8        return torch.randn(1000, 1000)
9
10    def sum(self, tensor: torch.Tensor):
11        return torch.sum(tensor)
12
13sender, receiver = MyActor.remote(), MyActor.remote()
14
15# The tensor will be stored by the `sender` actor instead of in Ray's object
16# store.
17tensor = sender.random_tensor.remote()
18result = receiver.sum.remote(tensor)
19print(ray.get(result))
```

当 `ray.ObjectRef` 被传给另一个任务时，Ray 会用 Gloo 把张量从源 actor 直接传给目标 actor，而不是走默认对象存储。注意 [`@ray.method(tensor_transport)`](https://docs.ray.io/en/latest/ray-core/api/doc/ray.method.html#ray.method) 装饰器只加在*返回*张量的任务上；一旦加上该提示，接收方的 actor 任务 `receiver.sum` 会自动用 Gloo 接收张量。本例中，由于 `MyActor.sum` 没有 [`@ray.method(tensor_transport)`](https://docs.ray.io/en/latest/ray-core/api/doc/ray.method.html#ray.method) 装饰器，它返回 torch.sum(tensor) 时会走默认 Ray 对象存储通道。

更多示例（包括如何使用 `ray.put` 与基于集合通信的传输）见[文档](https://docs.ray.io/en/latest/ray-core/direct-transport.html)。

*图：使用 `ray.put` 时，调用方代替 driver 的位置，同时持有 RDT 对象的数据与元数据。*

## 性能

RDT 能显著加速 Ray actor 之间的对象传输。下面是不同 GPU 张量传输通道随对象大小变化的基准性能。基准在某个 actor 上创建 CUDA 张量，发给同节点另一块 GPU 上的第二个 actor；第二个 actor 把张量之和返回 driver。我们测量在两个 actor 上提交并完成任务的端到端时间，使用 2 块 NVIDIA H100 GPU。

*Ray Direct Transport - 图 5*

如预期，Ray 对象存储因 CPU 与 GPU 之间的拷贝而随对象大小扩展性很差；RDT 则利用 GPU 间高速链路把传输显著加速。

## RL 示例

接下来演示如何用 RDT 在一个极简 RL 示例中加速权重同步。后续博客中，我们会把示例扩展至 RDT 用于 rollout 数据传输，并支持多 GPU LLM。

我们的极简 RL 示例仿照用 RL 训练 LLM 的数据流。具体地，我们用 Group Relative Policy Optimization（GRPO）算法解一个玩具问题：我们的"环境"随机生成一个二维方向向量，模型必须预测八个罗盘方向中哪个与该向量最接近：

*Ray Direct Transport - 图 6*

GRPO 是训练 LLM 中流行起来的 RL 算法。它对每个输入生成一个*组*输出，并计算每个输出相对其组内平均奖励的*优势*。算法限制当前策略模型的预测不能与同模型此前版本差异过大，以稳定训练、避免对过往经验的"灾难性遗忘"。

下图展示本例涉及的各个 Ray actor 及每个 actor 所需资源。

*Ray Direct Transport - 图 7*

每条箭头把一个张量从一个 actor 移到另一个。RDT 可以应用于其中任何数据传输，本例我们只把它用在 Learner → Generator 的传输上，因为那里需要 GPU 到 GPU 拷贝。

应用的详细步骤：

- [CPU] "环境"生成随机二维向量。
- [GPU] *Generator* 策略预测哪个输入向量最接近 8 个罗盘方向之一：W、NW、N、NE、E、SE、S 或 SW。
- [CPU] *Scorer* 用余弦相似度解析地计算奖励。
- [CPU] 打过分的样本被加入 *ReplayBuffer*。ReplayBuffer 让模型能从过往经验学习。
- [GPU] *Learner* 模型从 replay buffer 采样，用 GRPO 算法更新权重。
- [GPU] *Learner* 把更新后的权重发给 *Generator*，完成一个训练 step。

为简洁，本文只展示训练脚本的关键部分。完整训练代码见[这里](https://github.com/ray-project/ray/blob/c4f0c24210f26df9700daddf1f02a7302ae82488/doc/source/ray-core/examples/rdt/grpo_contextual_bandits.py)。

每个训练 step，环境随机采样一批二维单位向量。这些状态向量是 Generator actor 的输入。策略模型以这些二维状态为输入，输出八个可能动作上的 logits。

```
1# The number of actions to sample for each state.
2GROUP_SIZE = 10
3
4@ray.remote(num_gpus=1)
5class Generator:
6    def __init__(self, scorer): ...
7
8    def generate(self, states: torch.Tensor):
9        # states are randomly sampled unit vectors.
10        logits = self.model(states.cuda())
11        dist = Categorical(logits=logits)
12        actions = dist.sample((GROUP_SIZE,))
13        logps = dist.log_prob(actions)
14        # Move tensors to CPU and send to the Scorer.
15        slice_batch = {
16            "policy_version": self.policy_version,
17            "state": states.detach().cpu(),
18            "actions": actions.transpose(0, 1).contiguous().detach().cpu(),
19            "old_logps": logps.transpose(0, 1).contiguous().detach().cpu(),
20            }
21        self.scorer.enqueue_trajectory_batch.remote(slice_batch)
22
23    def update_weights(self, cuda_weights):
24        # Recieve CUDA tensors from the Learner and update the model.
25        self.model.load_state_dict(cuda_weights).eval()
26        self.policy_version += 1
```

Scorer actor 收到 Generator 发来的 CPU 张量字典，用动作与原始状态向量的点积计算奖励。随后 Scorer 把打过分的轨迹发给 ReplayBuffer actor（使用默认 Ray 对象存储）。

```
1@ray.remote(num_gpus=1)
2class Scorer:
3    def __init__(self, replay_buffer):
4        self.replay_buffer = replay_buffer
5
6    def enqueue_trajectory_batch(self, batched_slices: dict):
7        rewards = ...  # Score trajectories and send to ReplayBuffer.
8        self.replay_buffer.put.remote(dict(policy_version=policy_version,
9                state=batched_slices["state"],
10                actions=batched_slices["actions"],
11                old_logps=batched_slices["old_logps"],
12                rewards=rewards
13        ))
14
```

ReplayBuffer actor 把打过分的样本存进自己的本地堆内存，并暴露另一个方法供 Learner 从缓冲区采样。

```
1@ray.remote
2class ReplayBuffer:
3    def __init__(self): 
4        self.storage = []
5
6    def put(self, slice: dict[str, torch.Tensor]):
7        self.storage.append(slice)
8
9    def sample_from(self, n: int) -> list[dict[str, torch.Tensor]]: ...
10
```

Learner actor 从 ReplayBuffer 与当前策略采样，做 GRPO 式权重更新：

```
1@ray.remote(num_gpus=1)
2class Learner:
3    def __init__(self, replay_buffer): ...
4    def step(self):
5        # Sample from ReplayBuffer
6        slices: list[TrajectorySlice] = ray.get(
7          self.replay_buffer.sample_from.remote(BATCH_SIZE)
8        )
9        # Perform GRPO update.
10        ...
11
```

最后，我们在 Learner 上暴露一个获取当前模型权重的方法，用来与 Generator 同步权重。

```
1@ray.remote(num_gpus=1)
2class Learner:
3    @ray.method(tensor_transport="nixl")
4    def get_weights(self):
5        return self.model.state_dict()
```

注意这里我们加了 `@ray.method(tensor_transport="nixl")` 装饰器，让权重传输走 RDT。底层上，这通过 [UCX 库](https://openucx.org/)做单边 RDMA 读，绕过 CPU 内存。没有这个装饰器，Ray 会把权重经 Ray 对象存储传输。

现在把一切组合起来：实现一个 Ray driver 程序，执行"one step off policy"的异步训练循环——在当前权重上并行启动生成与下一个 Learner step。每次 Learner 更新后，我们把权重同步回 Generator，确保生成至多落后一个策略版本。

```
1# Instantiate one instance of each actor.
2replay_buf = ReplayBuffer.remote()
3learner = Learner.remote(replay_buf)
4scorer = Scorer.remote(replay_buf)
5generator = Generator.remote(scorer)
6
7# Initialize the generator and replay buffer.
8generator.update_weights.remote(learner.get_weights.remote()
9generator.generate.remote(sample_unit_vector(BATCH_SIZE))
10# Training loop.
11for i in range(total_steps):
12    states = sample_unit_vector(batch_size=BATCH_SIZE)
13    generator.generate.remote(states)
14    # Launch the next learner step in parallel with generation.
15    learner.step.remote()
16    # Update the generator with new weights.
17    ray.get(generator.update_weights.remote(learner.get_weights.remote()))
18
```

这里我们依赖 Ray 的 [actor 任务顺序保证](https://docs.ray.io/en/latest/ray-core/actors/task-orders.html)，让 generator 在权重更新与生成之间正确交替。为简单起见，我们用 `ray.get` 阻塞在 Generator.update_weights 任务上，确保 Generator 在 Learner 开始下一个 step 前已收到完整权重；否则 Generator 可能收到部分更新的权重。避免 driver 阻塞调用的替代方法见完整训练代码[这里](https://github.com/ray-project/ray/blob/c4f0c24210f26df9700daddf1f02a7302ae82488/doc/source/ray-core/examples/rdt/grpo_contextual_bandits.py)。

在 NVIDIA B200 节点上，用默认 Ray 对象存储完成权重传输时每个 step 约 188ms。加上 `@ray.method(tensor_transport="nixl")` 装饰器后，每个 step 的运行时间降到 81ms——**改一行代码，提速 2.3 倍**！

## 下一步

RDT 处于 alpha 阶段，我们积极寻求反馈！进行中的特性包括性能增强、对 CUDA IPC 等替代张量传输的支持，以及自带 transport 的支持。我们的目标是达到与 Ray Core API 几乎同等的覆盖面，但当前有几个需要知晓的关键限制：

- 仅支持 Ray actor，不支持非 actor 的 Ray 任务。
- 尚未兼容 [asyncio](https://docs.python.org/3/library/asyncio.html)。进展请关注[跟踪 issue](https://github.com/ray-project/ray/issues/56398)。
- RDT 对象是*可变的*。这意味着 Ray 只持有张量的引用，在请求传输前不会拷贝其值。如果用户代码在传输发生前写入张量，接收方可能看到部分更新。这与 Ray 对象存储不同——后者总是按值拷贝数据以确保不可变。

更多用法见[文档](https://docs.ray.io/en/latest/ray-core/direct-transport.html)，bug 报告或反馈请[提 issue](https://github.com/ray-project/ray/issues)，并在 [Ray Summit](https://www.anyscale.com/ray-summit/2025) 与我们见面！本系列的第二篇将扩展示例，演示 RDT 用于 rollout 数据传输以及多 GPU LLM 的 RL 训练。
