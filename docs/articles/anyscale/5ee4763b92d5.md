# Anyscale 批量 LLM 推理将 AWS Bedrock 成本最多降低 6 倍

作者：Cody Yu、Scott Lee、Ricky Xu、William Lin、Praveen Gorthy 和 Richard Liaw | 2024 年 10 月 1 日

## 引言

LLM 席卷了整个科技行业。由于 GPU 价格居高不下，大量优化工作聚焦在推理成本上。但这些努力大多集中在面向延迟敏感、7×24 全天候负载的在线推理。

[在线推理](https://www.anyscale.com/use-case/llm-online-inference)提供低延迟的实时响应，而 [LLM 批量推理](https://www.anyscale.com/use-case/llm-batch-inference)通过优化 GPU 资源利用率，提供更高吞吐与更优成本效益。因此，对无需即时交互的任务，离线推理能更高效、更经济地使用 LLM。

在某些场景下，通过将批量推理面向吞吐量与成本（而非延迟与可用性）做优化，Anyscale 相比 AWS Bedrock、OpenAI 等在线推理服务商可降低成本至多 **2.9 倍，在共享前缀场景下最多可达 6 倍**。

## 在线推理与批量推理的核心区别是什么？

把在线方案改造用于离线批量负载十分常见。但两类用例存在关键差异。

在线推理通常配置为优化低延迟，而批量推理的配置则优化整体 token 吞吐量。

因此，两者的配置空间相当不同：

- 在线部署常用投机解码（speculative decoding）和高度张量并行等技术，用吞吐换延迟；批量推理则用流水线并行、KV cache 卸载等技术最大化吞吐。
- 在线推理为满足 SLA 常部署在高端硬件（H100、A100）上，而批量推理优先考虑每美元吞吐（throughput-per-dollar），可用更经济易得的 GPU（A10G、L4、L40S）实现。
- 在线部署还带有 HTTP 与请求处理相关开销，这些在批量场景中可以去除。

## 为什么在 Ray 与 Anyscale 上做 LLM 批量推理？

对自托管推理，在优化批量 LLM 推理方面，Ray 与 Anyscale 具有独特优势。Anyscale 上的 LLM 批量推理将使用我们技术栈的关键组件：自研推理引擎、Ray Data、Ray Core 与 [Anyscale Platform](https://www.anyscale.com/platform)。

推理方面，我们使用自研推理引擎实现优化的 LLM 推理。

- 该推理引擎基于流行的开源 LLM 推理引擎 vLLM。
- 作为开源基础设施的坚定支持者，我们的许多性能改进已回馈给 vLLM 开源项目，如 FP8 支持、chunked prefill 和投机解码。

Ray Core 与 Ray Data 为数据密集型 AI 负载而生，与其他批处理系统相比提供了一组独特能力。

- Ray Core 灵活的分布式原语（任务、actor）让 Ray 用户可以表达嵌套并行，使不同分布式库易于组合——在本例中就是 vLLM 与 Ray Data。
- Ray Data 支持 Python 异步原语做请求流水线化，从而实现高 GPU 利用率。
- Ray Data 还利用 Ray Core 内建的容错能力，得以有效使用高性价比的 spot 实例。

[Anyscale Platform](https://www.anyscale.com/platform) 是完全托管的 Ray 解决方案，专注于为使用 Ray 运行 AI 应用提供出色体验与高性价比。

- Anyscale 的 Smart Instance Manager 支持跨可用区实例搜索与灵活的计算配置，带来经济的硬件利用。
- Anyscale 提供一个加速模型加载的库，让大模型副本快速启动，这对自动扩缩容和应对不稳定计算环境至关重要。

我们还创建了新的库 RayLLM-Batch，目标就是针对 LLM 批量推理负载优化这套栈。

## RayLLM-Batch 介绍

[RayLLM-Batch](https://docs.anyscale.com/llms/batching/intro/) 是一个利用 Ray 与 Anyscale 组件、规模化优化 LLM 批量推理的库：

- **简化 API**：抽象底层栈的复杂性，让用户在工作负载可以便捷地表达并在批量推理集群上执行。
- **优化推理引擎**：融入自研性能特性，同时与开源仓库保持紧密对齐。
- **容错**：引入作业级检查点与恢复，提升大规模推理作业的可靠性。
- **批量 LLM 推理优化器**：根据负载特征与可用硬件调优和配置底层栈，以降低成本。

通过结合这些要素，RayLLM-Batch 为大规模批量 LLM 推理提供了强大而经济的解决方案，回应批处理负载独特的挑战与机会。

RayLLM-Batch 文档见[这里](https://docs.anyscale.com/canary/llms/batching/intro/)。

## 用 LLaMA 做基准测试

在下面的[实验](https://github.com/anyscale/batch-llm-inference-reproductions/tree/main)中，我们在 Anyscale 上以 Llama 3.1 8b Instruct 评估 RayLLM-Batch，并与常见替代方案对比：Bedrock、带批量定价的 Bedrock，以及带批量定价的 OpenAI GPT-4o mini。所有 Anyscale 实验均使用 AWS 上常见可按需供应的 GPU，如 L4 和 L40S。

我们用 2000 输入 token、100 输出 token、无共享前缀的数据集评估各方案——这是摘要类任务的典型请求形态。我们在 1000 个请求上评估性能，并按请求吞吐计算每 token 价格。对 Anyscale，我们同时评估原始 BF16 模型和 FP8 版本模型；后者在 Open LLM Leaderboard 评测分数上恢复了原 Llama 3.1 8b Instruct 的 99.28%，通常可替代原始 BF16 模型使用。

我们看到，在这一特定负载上，Anyscale FP8 部署比 OpenAI GPT-4o mini 的批量定价便宜 2.2 倍，比 Amazon Bedrock 便宜 2.9 倍。¹

在许多离线负载中，请求之间存在共享提示/前缀很常见。这种情况下成本差距可以大得多，因为 Anyscale 能利用前缀缓存（prefix caching），而 OpenAI 和 Bedrock 不能。在同一负载（2000/100，Llama 3.1 8b）、请求间 80% 共享前缀时，Anyscale 方案**比批量定价的 AWS Bedrock 便宜 6.1 倍**，比批量定价的 OpenAI GPT-4o mini 便宜 4.78 倍。

在下面的实验中，我们在 Anyscale 上以 Llama 3.1 70b Instruct 评估 RayLLM-Batch，并与 Amazon Bedrock 对 Llama 3.1 70b Instruct 模型的定价对比。评估数据集的请求为 2000 输入、100 输出 token，无共享前缀。

对 Anyscale，我们既评估原始 BF16 模型，也给出 FP8 版本的结果；后者在 Open LLM Leaderboard 评测分数上恢复了原 Llama 3.1 70b Instruct 的 99.88%，通常可替代原始 BF16 模型使用。

我们看到，在该负载上，Anyscale FP8 批量推理方案比 Amazon Bedrock 方案便宜 22%。

在请求间 80% 共享前缀时，Anyscale 方案比批量定价的 AWS Bedrock 方案便宜 1.8 倍。

显然，对所选负载，无论小模型还是大模型场景，Anyscale 都能在性价比上超越其他常见方案。注意，虽然我们尽量选择代表性负载，但用户实际性能会因其负载的具体细节而异。
