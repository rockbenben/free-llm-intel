# 异步推理实战：基于 Ray Serve 的视频索引服务

作者：Harshit Agarwal | 2026 年 8 月 18 日

*在*[早前的文章](https://www.anyscale.com/blog/ray-serve-autoscaling-async-inference-custom-routing)*中，我们介绍了 Ray Serve 的异步推理：把长时间运行的模型调用移出请求路径，由消息队列托底，自带自动重试与按队列深度扩缩。本文是其实战续篇：基于该特性构建一个真实服务——视频索引流水线，在高负载下运行，并与一个常见的托管替代方案对比。*

## 快速回顾：异步推理为何而生

在服务 ML 模型时，有些应用一次模型调用要跑几秒到几分钟，例如：转写一小时音频、索引一个视频，或生成一张图/一段视频。在普通同步 HTTP 端点上，请求要持续打开整个计算时长。毫秒级延迟下这种耦合不可见，但调用一长就带来两个问题。

其一，突发流量压在一个每个请求要几秒甚至几分钟才完成的机群上，worker 很快落后，客户端或任何中间跳转开始超时。其二，维持数分钟的连接，遭遇丢包或某跳故障的暴露面大得多。结果恰恰在无法预测的时刻，服务与整个系统变得更不可靠。

异步推理通过把请求调度与实际计算解耦来解决这些问题：客户端提交作业、立刻拿到一个 id；工作进入消息队列；一个按队列深度自动扩缩的 worker 池在后台处理；客户端轮询结果。

API 与设计细节见[早前文章](https://www.anyscale.com/blog/ray-serve-autoscaling-async-inference-custom-routing)，这里聚焦在其上构建服务并在真实流量下做基准。Ray Serve 提供的几块拼图，简述如下：

- `@task_consumer / @task_handler` —— 这两个装饰器把一个 deployment 方法变成从队列拉取的后台 worker。
- `TaskProcessorConfig` —— 配置项，把你的代码指向你自己运行的消息代理（支持 Redis 或 RabbitMQ 等），并提供*至少一次*投递机制、重试与[死信](https://en.wikipedia.org/wiki/Dead_letter_queue)路由。
- `enqueue_task_sync(...)` —— 从生产侧提交工作的函数，返回一个可供客户端轮询结果的任务 id。
- `AsyncInferenceAutoscalingPolicy` —— 基于队列深度扩缩 worker 池的自动扩缩策略。

## 应用：一个视频索引服务

视频索引是异步推理的天然场景。每个请求都要下载、解码并嵌入整个视频，工作时长从几秒到几分钟，且流量往往成批到达——批量上传或夜间回填。这个视频索引服务接收一个 S3 URI，立即返回任务 id；后台它下载视频，用 ffmpeg 切帧，在 GPU 上用 SigLIP 嵌入帧，再把向量写回 S3——单个请求可能要几十分钟。

应用由三个 deployment 组成，各自按自己的信号扩缩：

- **IndexingIngress**（CPU）—— 接收 `POST /index`，把用户发来的任务入队，返回任务 id。
- **VideoIndexConsumer**（CPU）—— `@task_consumer`，从队列消费任务，用 ffmpeg 下载并切分视频，然后调用编码器。这是按队列深度自动扩缩的 deployment。
- **VideoEncoder**（GPU）—— 持有 SigLIP 神经网络的标准 deployment。VideoIndexConsumer 通过 handle 调用它，帧在两者之间经 Ray 的 RPC 而非网络传输，它按自身 GPU 负载扩缩。

下图展示我们部署并测试的服务架构：紫色框是 deployment，黄色框是服务对接的外部系统。

*我们部署并测试的服务架构*

生产者（接受用户请求的 deployment）是一个非常简单的 ingress deployment。它把任务入队并返回 id，调用方永远不必等待工作完成：

```
@serve.ingress(fastapi_app)
class IndexingIngress:
    def __init__(self, consumer):
        self.adapter = instantiate_adapter_from_config(PROCESSOR_CONFIG)

    @fastapi_app.post("/index")
    async def index(self, req: IndexRequest):
        result = self.adapter.enqueue_task_sync(
            task_name=TASK_INDEX_VIDEO,
            kwargs={"video_uri": req.video_uri, "video_id": req.video_id},
        )
        return {"task_id": result.id, "status": result.status}
```

VideoIndexConsumer 是一段简单的同步 Python 代码。它对 video id 幂等，在 CPU 上切分视频，通过 handle 调用 GPU 编码器，并存储结果：

```
@serve.deployment(ray_actor_options={"num_cpus": FFMPEG_THREADS}, ...)
@task_consumer(task_processor_config=PROCESSOR_CONFIG)
class VideoIndexConsumer:
    def __init__(self, encoder):
        self.encoder = encoder               # GPU DeploymentHandle

    @task_handler(name=TASK_INDEX_VIDEO)
    def index_video(self, video_uri, video_id=None):
        if is_done(video_id):                  # idempotent on redelivery
            return {"status": "skipped_already_indexed"}
        chunks = chunk_video(download(video_uri))         # CPU: ffmpeg
        refs = [self.encoder.remote(c.frames) for c in chunks]
        vectors = [r.result()["frame_embeddings"] for r in refs]
        write_video_embeddings(video_id, vectors)         # store to S3
        mark_done(video_id)
        return {"status": "indexed", "num_chunks": len(chunks)}
```

**注**——在下文的基准中，我们把 **VideoIndexConsumer**（CPU）与 **VideoEncoder**（GPU）两个 deployment 融合进单个 GPU worker，前面仍保留同一个轻量 ingress。这样做是为了让对比尽可能公平，也更贴近替代方案 Amazon SageMaker 支持的部署形态。

SageMaker 不支持把这两个组件作为同一 endpoint 背后的独立 CPU 与 GPU 服务部署。唯一的替代做法是把它们暴露成完全独立的 endpoint；而那条路会让 SageMaker 更加吃亏：中间张量必须按值通过网络在两个 endpoint 之间传输，而 Ray Serve 通过共享对象存储按引用传递。因此下文展示的所有基准结果都采用双 deployment 架构（ingress + 一个融合 worker），而非前文描述的三 deployment 架构。

## 负载下的表现

我们的目标是压测该服务，评估其在持续过载下的可靠性与性能。理想情况下，服务应随进入流量扩展、尽快处理请求，且不丢弃用户请求。

可靠性通过负载测试期间的失败请求数评估；性能通过观察系统对增量负载的响应评估——尤其是它在保持吞吐与稳定的同时随流量伸缩的能力。

为检验这两面，我们跑了 20 分钟的洪水测试：持续 **50 RPS**，周期性尖峰到 **100 RPS**。该负载约是 4 GPU 机群处理能力的 **5-10 倍**，整个测试期间约 **67,000 个视频请求**。由于请求速率显著超出机群处理能力，积压不可避免——这正好检验系统的扩缩行为与持续压力下的韧性。

*67k 洪水下的自动扩缩*

我们观察到：

- **副本随需求扩缩**——随着积压增长，应用自动把 GPU 副本数从 **1** 提升到配置上限 **4**；积压清空后又缩回 **1**。没有固定机群，也不需要按每次突发手工调参。
- **零失败请求**——全部约 **67,000 个视频请求**都被成功接收、入队并最终处理。死信队列在整个测试期间保持为空，说明持续过载中没有请求被丢弃或失败。

## 与托管方案对比：Amazon SageMaker

为了给出参照，我们在 [**Amazon SageMaker Async Inference**](https://docs.aws.amazon.com/sagemaker/latest/dg/async-inference.html)——这类负载常见的托管方案——上跑了同一负载。与我们的配置一样，SageMaker 会对进入请求排队、按积压扩缩、从 S3 读并写回 S3。两套配置使用相同硬件（**4× NVIDIA T4 GPU**）、相同的 **1 帧 SigLIP** 负载、相同的 **20 分钟洪水测试**，都从单个冷实例起步。由于 SageMaker 异步 endpoint 只跑单个模型容器，我们在 Ray Serve 侧也使用前述的单一融合 deployment。

这意味着两侧的部署架构、硬件与负载完全一致，编排引擎是两者之间的主要差异。

| **指标（同一洪水，4× T4）** | **Ray Serve async** | **SageMaker Async** |
| --- | --- | --- |
| **达到满编机群时间（冷启动）** | 约 155 秒 | 约 589 秒 |
| **释放闲置容量（最快实测）** | 约 5 秒 | 约 104 秒 |
| **自动扩缩配置** | 1 个策略块 | 2 个步进策略 + 2 个告警（详见下文）* |
| **失败/丢失任务** | 0 | 0 |
| **Ack 延迟 p50（负载下）** | 12.8 ms | 11.8 ms |

* SageMaker endpoint 由两个 Application Auto Scaling 步进策略扩缩，各挂一个 CloudWatch 告警。**backlog-fast** 告警在 ApproximateBacklogSizePerInstance 达到 5 及以上（单个 60 秒数据点）时触发，**fast-out** 策略直接跳到 4 实例上限；**backlog-empty** 告警在总 ApproximateBacklogSize 降到 1 以下时触发，**fast-in** 策略回落至单实例。

*1 —— 提交 RPS 随时间曲线。*

*20 分钟洪水的提交负载（两个引擎的负载剖面完全相同）*

*1 —— GPU 副本/实例数随时间曲线。2 —— Ray Serve 与 Amazon SageMaker 的积压队列长度随时间对比。*

*洪水期间的机群规模：都扩到 4、都释放回 1*

以下是对比运行的几点观察：

- **扩容接近。** 两者都在同一量级达到 4 GPU 满编，其中大部分时间花在节点供给上——两边都要付这笔账。差别在扩容决策：Ray Serve 直接轮询队列深度，秒级响应；SageMaker 的决策受其 CloudWatch 指标分辨率约束。
- **缩容差异更大。** 队列清空后，Ray Serve 在几秒内缩回。我们在 SageMaker 上观察到的最快缩容约 **104 秒**。
- **Ray Serve 更容易搭建。** Ray Serve 侧只需一个自动扩缩策略块。要在 SageMaker 获得类似行为，必须配置多个扩缩策略与若干 CloudWatch 告警。
- **两边都没丢东西。** 两者都处理完整个洪水，死信队列为空。

关于 SageMaker 配置的说明：自动扩缩已调到平台允许的最灵敏。它用单个 60 秒的 CloudWatch 告警基于 **ApproximateBacklogSize** 与 **ApproximateBacklogSizePerInstance** 指标同时触发扩容与缩容。不可能更快，因为这些是标准分辨率指标，CloudWatch 告警最快也只能 60 秒评估一次。

### 端到端延迟

扩缩速度只是故事的一部分。另一半是——**用户要等多久**才能端到端完成请求。为此，我们统计了洪水测试中每个请求从提交视频到把嵌入写入 S3 的时间，结果如下：

*10 倍洪水（各约 67k 任务）下的端到端延迟分位数*

每个请求的**基础处理时间约 1-2 秒**，包括下载视频、跑 FFmpeg、生成嵌入与把结果写入 S3。这部分两个平台几乎一样。差距来自**排队等待**。可用 GPU 数量有限，请求必须等一块空闲 GPU 才能被处理。排队越久，整体延迟越高。

Ray Serve 对增长的积压响应更快，比 SageMaker 更早启动新副本。结果是请求在队列里等待时间更短，用户更早拿到结果。

## 异步推理什么时候合适

异步推理适合完成时间较长、维持 HTTP 连接打开不切实际的负载，也适合有突发流量尖峰的负载——请求可以在队列里等资源到位。用 Ray Serve，只需少量配置即可获得请求排队、可靠的请求处理与基于队列长度的自动扩缩。由于它是 Ray Serve 内建能力，同一应用无需改代码就能跑在任何云、本地机房甚至笔记本上。

该特性今天已在 Ray Serve 可用，更多细节见 [Ray Serve 文档](https://docs.ray.io/en/latest/serve/asynchronous-inference.html)。
