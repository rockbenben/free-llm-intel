在 LinkedIn AI 平台团队 Ali 与 Sasha 的近期演讲中，他们讨论了遇到的挑战与应对方式。这些挑战覆盖面很广：从管理复杂 AI 工作流、集成多种编程语言，到处理多样化用例。

另一个挑战是从同构基础设施转向异构基础设施。随着 GPU 越来越重要，LinkedIn 希望构建能无缝适配多样 GPU 配置的基础设施，而不是把同一套多租户方案反复复制。

自动扩缩容与资源利用也在他们的视野内。他们需要按需求高效伸缩资源、同时把浪费降到最低的方案。此外，他们还想简化从离线推理到在线推理的迁移——这通常需要大量重写代码。

## 引入 Ray 与推理图

LinkedIn 对这些挑战的解法是采纳 Ray 并提出推理图的概念。开源分布式计算框架 Ray 是构建和部署 AI 应用的强大工具，专为让 AI 负载在多个 CPU 与 GPU 上高效扩展而设计。

在 LinkedIn 的 AI 平台语境下，推理图指 AI 工作流的图形化表示。这些图封装了从数据预处理、模型推理到后处理的完整过程。通过这一方式，LinkedIn 意在简化 AI 工作流，让 AI 工程师专注于高层的编排与部署，不被底层细节拖住。

## 基于 Ray 的推理运行时

LinkedIn 基于 Ray 的推理运行时提供异构基础设施，每个推理图作为独立单元运作。这些图可以按不同副本数复制以满足特定需求，从而为 A/B 实验等用例实现可扩展的控制。

为让离线与在线推理无缝切换，LinkedIn 把 Ray 集成进了自己的实验框架。这一集成确保 AI 工程师能把模型顺利推向生产，而不被高门槛拦住。

推理图中的节点被拆分到多个图上，每个图还可以进一步划分为多个节点。节点类型取决于负载走 CPU 还是 GPU 计算。这种布局把数据密集型负载隔离到 CPU，同时把推理任务卸载到 GPU，实现最优资源利用。

LinkedIn 还把这套基础设施与负载均衡等关键组件集成，确保 AI 部署稳健可靠。

## 推理图的高层编排

为简化推理图的编写，LinkedIn 开发了名为 Proxima 的内部平台。该平台让 AI 工程师可以独立完成推理图的编写、部署与运行。Proxima 与 CI/CD 流水线、实验系统、特征基础设施深度集成，实现无缝协作与部署。

Proxima 平台使用 Python 进行直观的图配置。AI 工程师通过组合代表模型、预处理、后处理、特征获取等步骤的对象来创建图。这种高层编排方式让 AI 工程师高效工作，无需深入底层实现细节。

## 对 AI 负载的影响

引入 Ray 与推理图后，LinkedIn 处理 AI 负载的方式发生了显著变化。对 LLN（Low Latency Network，低延迟网络）用例，新基础设施的开销极小，通常以毫秒计。这些用例的重点是 GPU 上的模型推理，基础设施并未引入明显开销。

在对延迟至关重要的个性化模型场景，LinkedIn 优化基础设施以最小化序列化/反序列化成本：削减调用路径中的 Python 组件，引入基于 Java 的运行时。就特征获取而言，Python 与 Java 的性能差距相当可观。

LinkedIn 还在积极探索进一步降低序列化/反序列化开销的方案，目标即便是高性能要求的模型，也让 AI 负载效率最大化。

## 在线与离线推理

LinkedIn 基于 Ray 的基础设施一项亮眼成就，是同一张推理图可同时用于在线与离线推理。虽然两者的扩缩配置不同，推理图本身保持一致。这意味着 AI 工程师只需创建一张图，就能在两种环境中运行，大幅简化开发与部署流程。

离线推理方面，LinkedIn 用 Ray datasets 高效横向扩展负载，轻松应对大规模批处理。通过 actor 就近部署（co-location）与对象放置优化，他们尽量降低数据经网络传输的成本。
