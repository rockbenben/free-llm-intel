# 宣布成立 Ray on Accelerators 特别兴趣小组（SIG）

作者：[Zhe Zhang](https://www.anyscale.com/blog?author=zhe-zhang)、[Mengjin Yan](https://www.anyscale.com/blog?author=mengjin-yan)、[Ryan O'Leary (Google)](https://www.anyscale.com/blog?author=ryan-oleary-google) 与 [Richard Liaw](https://www.anyscale.com/blog?author=richard-liaw) | 2026 年 10 月 20 日

今天，我们宣布成立面向硬件加速器的 Ray 特别兴趣小组（SIG）。

十多年前 Ray 在 UC Berkeley 诞生时，计算的格局与今天大不相同。当时所说的「分布式计算」指的是运行 Apache Hadoop、Apache Spark 等框架的 CPU 集群。GPU 才刚刚开始从图形与科学计算领域进入机器学习。

如今，*加速计算*已成为 AI 开发与部署的核心，加速器及其能力也变得更加专用化、多样化。例如：

- NVIDIA 的 RTX 6000 Pro 支持横跨 AI 训练、推理、图形与视频的灵活工作负载
- NVIDIA B200 和 AMD MI355X 提供显著更大的显存容量以支撑更大的模型，而 GB200 NVL72 把 72 块 GPU 连接起来，面向通信密集型的大规模训练与推理。
- 在 GPU 之外，Google Ironwood TPU 面向超大规模 AI 工作负载，Groq LPU 则专注于低延迟推理。

Ray 社区一直在积极跟上这一转变。如今，Ray [支持十多种硬件加速器](https://docs.ray.io/en/latest/ray-core/scheduling/accelerators.html)，从 NVIDIA 和 AMD 的 GPU 到 TPU、Trainium、Gaudi 等等。我们认为，现在正是以此为基础，在整个 Ray 范围内开展一项更宏大、更系统化努力的关键时刻，让加速器易于使用、在大规模下高效、在生产中可靠。

Accelerator 特别兴趣小组旨在把硬件厂商、Ray 贡献者和应用开发者汇聚在一起，共同制定并推进一份共享的、厂商中立的 Ray 加速器支持路线图。这个公开的兴趣小组将负责让 Ray 工作负载在加速器碎片化、专用化的时代继续演进。

我们最初的路线图聚焦 3 个核心领域：**开发与测试基础设施、硬件感知能力，以及网络/传输，**下面各节将逐一展开。

## 开发与测试基础设施

可靠的加速器支持，需要开发、测试和调试时能可靠地获取硬件。维护者和贡献者需要在受影响的设备上验证改动、复现故障，并在问题到达用户之前捕获回归。随着 agentic 软件工程加快开发节奏，可靠的测试与验证变得更加重要：无论是人类贡献者还是编码 agent，都需要来自真实硬件和有代表性工作负载的可复现反馈。我们希望把这件事变成参与 Ray 贡献的常规环节，并为硬件厂商和云厂商贡献资源与专业知识提供清晰的路径。

我们最初的优先事项是：

- **共享硬件访问**。建立一套有文档记录的流程，把云端和厂商托管的加速器接入 Ray 的开发与测试基础设施，其中也包括让贡献者能够复现和调试故障的访问权限。
- **可复现的开发与测试环境**。提供持续维护的环境，并明确标注驱动、运行时和依赖版本，使贡献者能够复现 CI 结果，并在不同厂商之间一致地验证改动。
- **更广的 CI 覆盖**。在现有流水线之上，为 pull request 增加有针对性的检查，并扩大夜间测试与发布测试的范围。覆盖内容应包含分布式工作负载、故障恢复和性能回归，而不只是设备的基础功能。
- **可持续的运维与归属**。明确环境维护、故障排查以及保持各版本集成都可用的职责分工。让测试结果和基础设施健康状况可见，并管理容量与成本，使基础设施能随着参与度的增长而扩展。

## 硬件感知调度

要让应用充分发挥加速器的性能，Ray 首先必须知道每个节点上有哪些硬件、它们是如何组织的。随着加速器生态的演进，加速器节点不再只是若干相同设备的简单计数。工作负载的性能取决于设备之间的互连情况、设备与 CPU 和 NIC 的关系，以及节点如何被归入机架、TPU 切片等更大的域。

我们的目标是让 Ray 能够跨厂商、跨平台准确且一致地描绘这一结构。有了这幅图景，Ray 的调度器就能把任务和 actor 放到正确的硬件上，用户也能看到自己的集群由什么构成、如何连接。

我们最初的优先事项是：

- **通用硬件接口。** 定义厂商中立的接口，用于标记硬件、表示其架构并描述其规格，使应用和库可以面向能力编程，而不是编写厂商专属代码。这包括以一致的方式识别加速器 SKU（含发布时的新 SKU），也包括为新增加速器的厂商提供有文档记录的扩展点和检查清单。
- **更健壮的发现机制。** 强化 Ray 的发现机制，为每种加速器的集成明确归属，并用上一节所述的 CI 覆盖为其兜底。发现机制应捕获硬件的拓扑与架构，而不只是设备的类型和数量。
- **平台与云集成。** 与云厂商和部署平台合作，使发现结果能够反映集群实际运行所在环境的底层结构。有些信息（例如某个节点属于哪个机架或哪个切片）只能从平台获取，节点自身并不掌握。
- **硬件可见性。** 提供查看集群中加速器及其连接方式的能力，并在 Ray dashboard 上展示加速器指标。这既让用户确认 Ray 正确识别了自己的硬件、并了解工作被放置在哪里，也为贡献者提供了验证新集成的手段。
- **清晰的用户指南。** 记录 Ray 如何发现和表示硬件，以及如何在放置工作时使用这些信息。好的指南既能帮助应用开发者，也能帮助越来越多替他们编写 Ray 代码的编码 agent。

## 网络与 I/O 传输

在加速器之间搬运数据，往往和在加速器上执行计算同样重要。现代 AI 工作负载（例如大规模强化学习）需要把大型模型权重张量跨设备、跨节点地从训练 worker 搬到推理 worker。从历史上看，Ray 的对象存储是为 CPU 数据设计的，这意味着加速器张量必须先复制到主机内存、序列化，再经由标准的主机网络发送，才能到达另一个设备。

为避免这一瓶颈，我们引入了 **Ray Direct Transport（RDT）**，让 actor 可以通过 Ray 传递张量引用，同时在设备之间直接传输实际数据，并使用 UCX、RDMA 等高性能传输方式。我们的目标是让高速的直连数据传输在不同加速器、框架和网络结构上都能可靠工作，同时保持 Ray 熟悉的编程模型。

我们最初的优先事项是：

- **广泛的传输集成**。在 RDT 中支持更多种类的加速器、框架和互连方式，使 Ray 能在 actor 之间选择最快的路径——无论是切片内的 TPU ICI、同节点内的 NVLink，还是跨节点的 GPUDirect RDMA。
- **传输生命周期与恢复**。确保每种硬件传输在真实设备上都能干净地处理初始化、拆卸和错误恢复，使 RDT 在 actor 于强化学习、分离式服务等动态工作负载中扩缩或重启时依然可靠。
- **经验证的配置方案与可观测性**。让云厂商和硬件厂商能够发布经过验证的部署配置、对高吞吐工作负载进行基准测试，并给出清晰的诊断信息和传输指标。

## 范围

核心的调度与放置逻辑仍保留在 Ray Core 中，而 SIG Accelerator 负责定义 Ray 中加速器的插件接口、CI 测试和成熟度分级。硬件厂商和云厂商贡献并维护各自的设备插件、传输实现以及新 SKU 的首日支持，框架作者和 ML 从业者则用真实的工作负载需求为我们的路线图提供依据。

无论你是在构建新的加速器集成、在 Ray 上运行大规模训练或推理，还是在提供云与 CI 基础设施，我们都欢迎你参与进来！

- 参加我们的社区会议，讨论提案、评审路线图优先级、分享工作负载方面的反馈。
- 查看 Github 上与加速器相关的开放 [issue](https://github.com/ray-project/ray/issues) 和 PR，并向上游贡献。
