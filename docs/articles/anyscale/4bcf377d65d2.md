# 宣布成立 Ray on Accelerators 特别兴趣小组 (SIG)

作者：[张哲](https://www.anyscale.com/blog?author=zhe-zhang)、[颜孟金](https://www.anyscale.com/blog?author=mengjin-yan)、[Ryan O'Leary (Google)](https://www.anyscale.com/blog?author=ryan-oleary-google) 和 [Richard Liaw](https://www.anyscale.com/blog?author=richard-liaw) | 2026 年 10 月 20 日

今天，我们宣布成立 Ray 硬件加速器特别兴趣小组 (SIG)。

十多年前，当 Ray 在加州大学伯克利分校创建时，计算领域看起来非常不同。当时，“分布式计算”指的是运行 Apache Hadoop 和 Apache Spark 等框架的 CPU 集群。 GPU 刚刚从图形和科学计算转向机器学习。

如今，“加速计算”是人工智能开发和部署的前沿和中心，加速器及其功能变得更加专业化和多样化。例如：

- NVIDIA 的 RTX 6000 Pro 支持涵盖 AI 训练、推理、图形和视频的灵活工作负载
- NVIDIA B200s 和 AMD MI355X 提供更大的内存容量以支持更大的模型，GB200 NVL72 连接 72 个 GPU，用于通信密集型、大规模训练和推理。
- 除了 GPU 之外，Google Ironwood TPU 还针对大规模 AI 工作负载，而 Groq LPU 则专注于低延迟推理。

Ray 社区一直在积极努力跟上这一转变。如今，Ray [支持十多种硬件加速器](https://docs.ray.io/en/latest/ray-core/scheduling/accelerators.html)，从 NVIDIA 和 AMD GPU 到 TPU、Trainium、Gaudi 等。我们相信，现在是在此基础上进行更雄心勃勃、系统化努力的关键时刻，让 Ray 加速器易于使用、大规模高效且生产可靠。

加速器特别兴趣小组旨在将硬件供应商、Ray 贡献者和应用程序开发人员聚集在一起，定义和推进一个共享的、供应商中立的 Ray 加速器支持路线图。这个公共利益团体将负责使 Ray 工作负载能够在碎片化、专业化加速器的时代继续发展。

我们最初的路线图侧重于 3 个核心领域：**开发和测试基础设施、硬件感知功能和网络/传输，**在以下部分中概述。

## 链接开发和测试基础设施

可靠的加速器支持需要可靠地访问硬件以进行开发、测试和调试。维护者和贡献者需要在他们影响的设备上验证更改、重现故障并在到达用户之前捕获回归。随着代理软件工程加速开发，可靠的测试和验证变得更加重要：人类贡献者和编码代理都需要来自真实硬件和代表性工作负载的可重复反馈。我们希望将此成为为 Ray 做出贡献的常规部分，为硬件供应商和云提供商贡献资源和专业知识提供清晰的路径。

我们最初的优先事项是：

- **共享硬件访问**。建立一个记录流程，将云和供应商托管的加速器引入 Ray 的开发和测试基础设施，包括让贡献者能够重现和调试故障。
- **可重复的开发和测试环境**。为维护的环境提供明确的驱动程序、运行时和依赖项版本，以便贡献者可以重现 CI 结果并跨提供商一致地验证更改。
- **更广泛的 CI 覆盖范围**。通过有针对性地检查拉取请求以及更广泛的夜间和发布测试来扩展现有管道。覆盖范围应包括分布式工作负载、故障恢复和性能回归以及基本设备功能。
- **可持续经营和所有权**。定义维护环境、调查故障以及保持跨版本集成正常运行的职责。让测试结果和基础设施运行状况可见，并管理容量和成本，以便基础设施可以随着参与而增长。

## Link硬件感知调度

为了让应用程序充分利用加速器，Ray 首先必须了解每个节点拥有哪些硬件及其结构。随着加速器生态系统的发展，加速器节点不再只是相同设备的数量。工作负载性能取决于设备的互连性、设备与 CPU 和 NIC 的关系，以及节点分组到更大的域（例如机架和 TPU 切片）。

我们的目标是让 Ray 跨供应商和平台准确、一致地了解这种结构。有了这张图片，Ray 的调度程序就可以将任务和参与者放置在正确的硬件上，用户可以看到他们的集群是由什么组成的以及它是如何连接的。

我们最初的优先事项是：

- **通用硬件接口。** 定义供应商中立的接口，用于标记硬件、表示其架构并描述其规格，以便应用程序和库可以定位功能，而不是编写特定于供应商的代码。这包括以一致的方式识别加速器 SKU，包括发布时的新加速器 SKU。它还包括记录的扩展点和清单，供供应商添加新的加速器。
- **强化发现。** 加强 Ray 的发现机制，为每个加速器的集成提供明确的所有权，并通过上一节中描述的 CI 覆盖范围来支持它。发现应该捕获硬件的拓扑和架构，而不仅仅是设备的类型和数量。
- **平台和云集成。** 与云提供商和部署平台合作，以便发现反映集群运行的底层结构。其中一些信息（例如节点属于哪个机架或分片）只能从平台获得，而不能从节点本身获得。
- **硬件可见性。** 提供查看集群中的加速器及其连接方式的方法，以及 Ray 仪表板上的加速器指标。这可以让用户确认 Ray 正确地看到他们的硬件并了解他们的工作放置在哪里。它还为贡献者提供了一种验证新集成的方法。
- **清晰的用户指南。** 记录 Ray 如何发现和表示硬件，以及如何在布置工作时使用该信息。好的指南可以帮助应用程序开发人员和越来越多地为他们编写 Ray 代码的编码代理。

## LinkNetworking 和 I/O 传输

在加速器之间移动数据通常与在加速器本身上运行计算一样重要。现代人工智能工作负载，例如大规模强化学习，需要跨设备和节点移动大型模型权重张量，从训练到推理工作人员。从历史上看，Ray 的对象存储是为 CPU 数据构建的，这意味着加速器张量必须复制到主机内存、序列化并通过标准主机网络发送，然后才能到达另一个设备。

为了避免这个瓶颈，引入了**Ray Direct Transport (RDT)**，使参与者能够通过 Ray 传递对张量的引用，同时在设备之间直接传输实际数据并使用 UCX 和 RDMA 等高性能传输。我们的目标是使高速、直接的数据传输在不同的加速器、框架和网络结构上可靠地工作，同时保持 Ray 熟悉的编程模型。

我们最初的优先事项是：

- **广泛的运输一体化**。在 RDT 中支持更广泛的加速器、框架和互连，因此 Ray 可以选择 Actor 之间最快的路径，无论是通过片内 TPU ICI、同节点 NVLink 还是跨节点 GPUDirect RDMA。
- **运输生命周期和恢复**。确保每个硬件传输干净地处理真实设备上的初始化、拆卸和错误恢复，以便 RDT 在参与者在强化学习和分类服务等动态工作负载中扩展或重新启动时可靠地工作。
- **经过验证的配方和可观察性**。使云和硬件提供商能够发布经过验证的部署配置、对高吞吐量工作负载进行基准测试并提供清晰的诊断和传输指标。

## 链接范围

虽然核心调度和布局逻辑保留在 Ray Core 中，但 SIG Accelerator 负责定义 Ray 中加速器的插件接口、CI 测试和成熟度层。硬件供应商和云提供商贡献并维护自己的设备插件、传输和对新 SKU 的零日支持，而框架作者和 ML 从业者则根据实际工作负载需求制定我们的路线图。

## Link参与

无论您是构建新的加速器集成、在 Ray 上运行大规模训练或推理，还是提供云和 CI 基础设施，我们邀请您参与其中！

- 加入 [Ray Slack](https://www.ray.io/join-slack) 上的对话。
- 参加我们的社区会议，讨论提案、审查路线图优先事项并分享工作量反馈。
- 查看与开放加速器相关的[问题](https://github.com/ray-project/ray/issues) 和 Github 上的 PR 并向上游做出贡献。
