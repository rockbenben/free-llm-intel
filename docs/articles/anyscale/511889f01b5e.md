# 用 Ray Data 为 ML 训练提供快速、灵活、可扩展的数据加载

作者：Stephanie Wang、Scott Lee、Cheng Su、Hao Chen 和 Eric Liang | 2023 年 9 月 15 日

数据加载与预处理很容易成为真实 ML 流水线中的性能瓶颈。数据预处理也在变得更复杂。有了 Ray Data，数据加载可以做到快、灵活且可扩展。

跨多 GPU 扩展模型训练是人尽皆知的挑战，但数据加载与基于 CPU 的预处理同样容易成为真实 ML 流水线的性能瓶颈，导致 GPU 利用率低下、成本高昂。随着处理的数据类型日益多样，数据预处理需求也在变得更复杂。

[Ray Data](https://docs.ray.io/en/latest/data/data.html) 为 ML 训练提供灵活的数据加载器，底层用 Ray core 在异构算力上做并行与分布式预处理。它提供**流式数据集（streaming dataset）**抽象，让你在把 RAM 占用（右图）控制在范围内的同时最大化 GPU 利用率（左图）。

*使用 Ray Data 与 16 个单 GPU 节点的分布式训练作业（12:30 开始）期间，图像分类模型的 GPU 利用率（左）与 RAM 占用（右）。Ray Data 支持流式执行以实现高 GPU 利用率，同时保持内存占用恒定。*

本文将以公开的 [MLPerf](https://www.nvidia.com/en-us/data-center/resources/mlperf-benchmarks/) 图像分类基准为例，深入比较各个 OSS 数据加载器的性能。我们将展示 Ray Data 在多节点场景下提供无与伦比的灵活性与规模：**从云存储流式读取**、**异构集群**支持以及**内存分布式缓存**，同时在单节点性能上追平 PyTorch DataLoader、tf.data 等流行数据加载器。

具体涵盖的基准测量：

- 用 Ray Data 把大数据集从云存储流式送入分布式训练集群。
- 借助异构集群与数据集缓存，Ray Data 带来的额外横向扩展与性能收益。
- 单节点性能，并与其他开源数据加载器做性能拆解对比。

## Ray Data 的 ML 数据加载入门

[Ray Data](https://docs.ray.io/en/latest/data/data.html) 负责最后一公里的数据预处理，把数据从存储或 ETL 流水线搬进分布式训练或批量推理作业。它支持：

- 处理流行数据格式与模态，从 parquet 到原始图像、视频
- 从本地磁盘或云端存储的数据集流式读取
- 横向扩展到多 CPU、多节点
- 以及高级扩展特性，包括：
  - 分布式内存与磁盘缓存
  - 在 GPU 节点之外增加纯 CPU 节点做横向扩展
  - 数据预处理流水线中 OOM 故障的自动恢复

其他 OSS 数据加载器对前三项也有某种程度的支持，但 Ray Data 的亮点在于**构建复杂数据预处理流水线的灵活性**，以及**在规模下提供性能的能力**。下面更仔细地看一些差异：

接下来会更详细地比较这些数据加载器。本文余下部分使用 [MLPerf](https://www.nvidia.com/en-us/data-center/resources/mlperf-benchmarks/) 图像分类基准：测量在 [ImageNet-1k 数据集](https://www.kaggle.com/competitions/imagenet-object-localization-challenge/data)上训练 ResNet v1.5 模型的时间。原始数据集为 JPEG 图像，平均 100KB/张，总计 150GB；解码后约需 ~1TB RAM。

原数据集中的每张图像会经过随机裁剪、翻转、缩放，再转换为张量；多个张量可拼接成一个 batch，传入 GPU 显存。

随机化的预处理步骤用于数据增强，也意味着每次过一遍数据集都要重新执行所有步骤。而且由于完整 ImageNet 数据集大于内存，每个 epoch 都要重新读取并解码图像。

基准的公开参考实现见[这里](https://github.com/ray-project/mlperf-training/tree/master/image_classification)，用 TensorFlow 训练、tf.data 加载。下面是我们将使用的 Ray Data 代码，先用 `torchvision` transforms 定义预处理函数：

## 从云端把图像数据集流式送入训练集群

大型训练数据集通常存放在云端，方便训练集群访问。云存储也慢于本地磁盘。虽然把整个训练数据集下载到本地磁盘可以最大化预处理吞吐，但很多情况下这并不合理：

- 每个节点的磁盘空间不足以存放整个数据集
- 希望把数据下载与预处理、训练重叠进行
- 希望每个 worker 节点在每个 epoch 读取数据的不同随机子集

*把大数据集从云存储流式送入 4 GPU 集群并预处理。*

在这些场景下，Ray Data 有几个实用的云数据集内建特性，包括：

- 与 Amazon、GCP、Azure 等主流云存储系统之间流式传输到集群内存（反向亦可）。云存储支持经由 `[fsspec](https://filesystem-spec.readthedocs.io/en/latest/)` 提供。
- 能够读取并预处理云数据集的一个子集。
- 能够对 GPU trainer 集群静态或动态地自动分区数据集。
- 对数据预处理流水线任意阶段的缓存。Ray 还会代你管理缓存，按需让数据在内存与磁盘之间、各节点之间换入换出。

在进入这些高级特性之前，先看 S3 的性能与可扩展性。下图展示从 S3 流式读取数据到一个 GPU 节点集群（每节点 1 GPU、1 训练 worker）[1]时的总吞吐。每个训练 worker 在预处理后的数据集上跑空循环（无模型），以单独测量数据加载吞吐。我们选 PyTorch DataLoader 作为对照，因为在从本地磁盘读取的单节点基准中它表现最好。

这里可以看到，Ray Data（蓝色）随训练节点数线性扩展，与 PyTorch DataLoader（红色）表现相当。这里的性能主要来自并发 S3 读取。

对 PyTorch DataLoader，这需要一些手动调优。PyTorch 提供了 [S3FileLoader](https://pytorch.org/data/main/generated/torchdata.datapipes.iter.S3FileLoader.html)，遍历 S3 URL 列表并以字节产出数据。由于迭代器是单线程的，需要增大传给 DataLoader 的 `num_workers` 参数，它控制使用多少个 `multiprocessing` worker。但设得太高反而会变慢，甚至因 OOM 导致作业失败。我们发现把 num_workers 设为核心数的 16 倍效果最好，但这个数字取决于你的预处理步骤与所用模型。

在做分布式数据并行训练、每块 GPU trainer 应读取数据集的一个分区时，事情更复杂。用 PyTorch DataLoader，每块 GPU trainer 都有自己的数据加载器，因此你需要先把图像文件列表静态划分给各 GPU trainer，再划分给每个 trainer 的数据加载器 worker。如果要确保每个 epoch 读到数据集中的每张图像，还得保证训练用的 batch size 能整除每个数据分区的大小。

用 Ray Data，这一切自动完成。无论有多少核心、多少 trainer，代码都一样。

*2 节点 GPU 集群中的 Ray Data+Core 架构。每个 Ray 任务读取数据集的文件子集、应用预处理函数，把结果存入 Ray 的共享内存对象存储。结果随后可以送入本地 GPU、远端 GPU、进一步预处理，和/或缓存以供后续 epoch 使用。*

这之所以可行，是因为 Ray Data 利用 Ray Core 的通用分布式执行。底层上，Ray Data 把文件列表拆成更小的任务，提交给 Ray Core 在集群中调度。每个任务从 S3 下载文件到内存、应用预处理函数，然后把结果输出到 Ray 每节点的共享内存对象存储，之后可在后台拷贝到最近的 GPU 显存中。

## 用异构集群扩展数据预处理

如果你的数据预处理是 CPU 或 I/O 受限的，理想情况下希望预处理独立于 GPU 集群规模来扩展。用**异构集群**——由不同实例类型组成的集群，这里是 GPU+CPU 与纯 CPU——我们就能做到。只要 GPU 节点还有富余网络带宽，就可以在纯 CPU 节点上加载数据，把预处理后的数据传给 GPU 节点训练。

遗憾的是，现有开源数据加载器做不到，因为预处理线程必须与数据消费者同机部署。

不过用 Ray Data，我们可以在异构集群上运行**完全相同的代码**，并增加可用于数据预处理的核心数、内存和磁盘。这可行是因为 Ray Core 能在集群中调度任务，而其他数据加载器只支持单节点。纯 CPU 节点上的数据就绪后，Ray Data+Core 会在后台把它传给 GPU 节点。

这里最右侧的蓝色条代表异构配置：在 16 节点集群上再加 4 台 r5.16xlarge 节点，使 CPU 数量翻倍。作为回报，相比同构配置吞吐提升 65%。

## 用数据集缓存加速数据预处理

取决于负载和可用资源，在预处理的各个阶段缓存数据集也会有帮助，可以避免下载和预处理数据集所需的网络与 CPU 开销。

用 Ray Data，这**只需给要缓存的数据集加一行 `ds = ds.materialize()`**。底层上，数据集的结果被缓存在 Ray 对象存储中。当对象存储达到内存上限，Ray Core 还会自动把数据溢出到磁盘，避免内存耗尽。

在这一特定负载中，缓存原始图像（紫色）并没有提升吞吐。原因是缓存图像只省掉了 S3 读取，而每个 epoch 仍要应用随机预处理；此外这里缓存的是解码后的图像，比 Ray 默认的对象存储内存还大，导致了一些溢出。实践中，如果数据集输入远小于最终预处理输出，缓存输入的效果更好。未来 Ray Data 还可以通过在内存中缓存编码图像来改善这一点。

把缓存应用在预处理后的图像上效果就好得多，因为 GPU trainer 可以直接读缓存输出。但这也意味着每个 epoch 读到的数据是相同的。

## 单节点对比 Ray Data

最后，更深入地看 Ray Data 与其他开源数据加载器在单节点、从本地磁盘加载图像数据时的性能对比。总体而言，虽然 Ray Data 在图像处理上相比其他流行数据加载器有一些开销，但其灵活性与可扩展性足以超额弥补。

这里按每核吞吐与 tf.data、PyTorch DataLoader 对比，使用两个版本的基准：一个只做等尺寸缩放，另一个（即前文版本）还应用随机裁剪与翻转。tf.data 版本转换为 tf.Tensor，PyTorch 与 ray.data 转换为 torch.Tensor。

乍看之下有两个趋势很突出：

- tf.data 单独加载图像最快。这可能是因为 tf.data 有针对 tf.Tensor 格式优化的图像加载例程，而其他方案使用流行的 [PIL](https://pillow.readthedocs.io/en/stable/) 库。不过这一优势仅限于 TensorFlow 模型。
- Ray Data 达到 PyTorch DataLoader 吞吐的 ~70%（差距约 30%）。这一性能差距来自 Ray Data 相比 PyTorch DataLoader 做了额外的数据转换。这是 Ray Data 更高灵活性的非刻意副作用，我们当然想尽量消除它！请关注该领域的后续改进。

提升数据加载性能的常见手段是重排输入数据。这里我们可以重排输入，让每个文件存储解码后多张图像的数组，而不是每文件一张原始图像。这带来两点帮助，代价是额外（约 5 倍）存储：

- 避免每个 epoch 解码图像的开销。
- 每次读取更多字节，降低 I/O 开销。

事实上，我们甚至可以用 Ray Data 把这个离线预处理步骤扩展到多核多节点！下面是用 parquet 格式完成的快速示意：

```
1def to_bytes(row):
2    row["height"] = row["image"].shape[0]
3    row["width"] = row["image"].shape[1]
4    row["image"] = row["image"].tobytes()
5    return row
6
7# Offline: Write out batches of images in parquet format.
8ds = ray.data.read_images(input_dir, mode="RGB")
9ds = ds.map(to_bytes)
10ds.write_parquet(output_dir)
11
12def decode_image(row):
13	row["image"] = Image.frombytes("RGB", (row["height"], row["width"]), row["image"])
14	return {"image": np.array(row["image"])}
15
16# Online: Read the image data back in during training.
17ds = ray.data.read_parquet(output_dir).map(decode_image)
```

这里有两个有用的对照：支持从 [Parquet 读取](https://huggingface.co/docs/datasets/loading#parquet)的 [HuggingFace Dataset](https://huggingface.co/docs/datasets/index)，以及使用专用 [MDS](https://docs.mosaicml.com/projects/streaming/en/stable/fundamentals/dataset_format.html)（Mosaic Data Shard）格式的 MosaicML [StreamingDataset](https://docs.mosaicml.com/projects/streaming/en/stable/index.html)。可以把 MDS 理解为带索引文件的记录数组，支持快速随机查找。这两个 Dataset 都用 PyTorch DataLoader 做并行[2]，但额外提供了从云存储读取、洗牌和缓存数据集的工具。看看在这些不同文件格式上的性能：

这里 Ray Data 达到 MosaicML StreamingDataset 和 Parquet HuggingFace Dataset 吞吐的 75-85%（差距 15-25%）。与之前类似，差距来自额外的数据转换。消除这些开销并优化其他单线程操作，将是 Ray Data 后续版本的改进重点。例如，初步研究表明使用[优化的 PIL](https://github.com/uploadcare/pillow-simd)分支可获得高达 30% 的加速。

## 总结

本文展示了 [Ray Data](https://docs.ray.io/en/latest/data/data.html) 如何借助流式数据集、异构算力与更灵活的缓存方案，在规模上超越其他流行数据加载器。虽然原始性能仍有提升空间，但 Ray Data 提供了随 ML 训练作业扩展数据加载与预处理所需的关键性能特性，且比典型的基于 `multiprocessing` 的数据加载器需要更少的调优。

总体结果也与我们一些用户的体验吻合。例如 Pinterest 的这篇[近期博客](https://medium.com/pinterest-engineering/last-mile-data-processing-with-ray-629affbf34ff)展示了随着预处理变复杂，Ray Data 与 PyTorch DataLoader 的差距如何拉大：在其最复杂的预处理任务上，Ray Data 比 PyTorch DataLoader 快至多 45%。再加上用异构资源扩展的能力，他们最终节省了约 25% 的总训练成本！
