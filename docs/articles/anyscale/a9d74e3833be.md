# 不用 MapReduce 系统执行分布式 Shuffle

作者：Stephanie Wang | 2021 年 3 月 22 日

分布式 shuffle 是数据密集型操作，通常需要专门为此打造的系统。在本文中，我们将展示如何用 Ray——一个核心 API 不含任何 shuffle 操作的通用框架——以[几行 Python](https://github.com/ray-project/ray/blob/5a788474aa75e3b8b3ce7f234dbe81d264df522e/python/ray/experimental/shuffle.py)表达一个分布式 shuffle。

小数据集在内存里 shuffle 很简单。但更大的数据集带来新挑战：

- **多节点**：把内存容量扩展到单机之上，并让 map 与 reduce 阶段内部可以并行处理。
- **溢出到外部存储**：当数据集总量大于集群总内存时。
- **强制内存上限**：避免触发操作系统昂贵的 OOM 处理，如换页到磁盘或触发 [OOM killer](https://lwn.net/Articles/317814/)。

在更早的[博客](https://medium.com/distributed-computing-with-ray/data-processing-support-in-ray-ae8da34dce7e)中，我们展示过 Ray 可以作为数据处理应用的公共基座。本文将深入剖析 Ray 如何执行以 Python 任务表达的核外分布式 shuffle。

## 什么是 Shuffle？

由于体积庞大，分布式数据集通常以*分区（partitions）*存储，每个分区容纳一组行。这也提升了 map、filter 等操作的并行度。*Shuffle* 指数据集中任何需要跨分区重新分配数据的操作，例如排序和按键分组。

对大数据集做 shuffle 的常见方法，是把执行拆成 *map* 阶段和 *reduce* 阶段，数据在 map 与 reduce 任务之间被洗牌。例如，假设我们要排序一个 4 分区的数据集，目标是产出同样 4 分区、但按键有序的数据集。

*对 4 分区的分布式数据集做 shuffle，每个分区是一组 4 个块。以排序为例，每个方块是一个键区间互不相同的有序子分区；每个 reduce 任务对同色的子分区做归并排序。*

上图展示了这一过程。最初，未排序数据集按颜色分组（蓝、紫、绿、橙）。shuffle 的目标是按深浅色调重新分组（从浅到深）。这种重分组需要全对全通信：每个 map 任务（彩色圆圈）对每种色调产出 1 个中间结果（方块），这些中间结果被洗牌送到各自的 reduce 任务（灰色圆圈）。

这样的程序用 Ray 加 Python 函数即可编写。调用函数即创建任务。每个 map 任务返回多个值（每个 reduce 任务一个），每个 reduce 任务把这些输出作为自己的参数。用 [Ray API](https://docs.ray.io/en/master/ray-overview/index.html)写一个[排序](https://github.com/ray-project/ray/blob/5a788474aa75e3b8b3ce7f234dbe81d264df522e/python/ray/experimental/shuffle.py)大概长这样：

```
1import ray
2import numpy as np
3
4@ray.remote
5def map(data, npartitions):
6    outputs = [list() for _ in range(npartitions)]
7    for row in data:
8        outputs[int(row * npartitions)].append(row)
9    return tuple(sorted(output) for output in outputs)
10
11@ray.remote
12def reduce(*partitions):
13    # Flatten and sort the partitions.
14    return sorted(row for partition in partitions for row in partition)
15
16ray.init()
17npartitions = 4
18dataset = [np.random.rand(100) for _ in range(npartitions)]  # Random floats from the range [0, 1).
19map_outputs = [
20        map.options(num_returns=npartitions).remote(partition, npartitions)
21        for partition in dataset]
22outputs = []
23for i in range(npartitions):
24    # Gather one output from each map task.
25    outputs.append(reduce.remote(*[partition[i] for partition in map_outputs]))
26print(ray.get(outputs))
```

## 内存不构成约束时的单节点 Shuffle

分布式 shuffle 之所以难，是因为 map 与 reduce 阶段之间存在全对全依赖。N 个分区会产生 N^2 个中间结果，必须在 map 与 reduce 任务之间洗牌。

但当数据全部放得进内存时，这件事并不难。我们用前一个示例的缩小版，看看它在 Ray 上如何运行。

我们要对一个 4GB 数据集、2 个分区执行这个图。那么每个中间结果（方块）为 1GB：

*在 4GB 数据集、2 分区上执行该图。*

试试在一台 2 CPU、8GB 内存的机器上运行：

*2 CPU、8GB 内存的试验机器。*

首先，Ray 把 map 任务（蓝色与紫色）调度到两个 worker 槽位上。它们并行执行，并在本地 Ray 对象存储中创建各自的对象（蓝、紫方块）。

*Ray 把 map 任务调度到 worker 槽位。*

接着，Ray 调度 reduce 任务（灰色圆圈）。Ray 通过依赖解析来调度：只有当 reduce 任务的全部参数（map 阶段产出的蓝、紫方块）都在本地后，才调度该任务。每个 worker 从本地对象存储获得 map 输出的一份副本。由于对象存储以共享内存实现，如果对象基于 [NumPy](https://numpy.org/)，这一步可以[零拷贝](https://docs.ray.io/en/master/serialization.html)完成。reduce 任务结束后，Ray 自动对其参数进行垃圾回收。

*reduce 完成后 Ray 回收内存。*

Ray 管理了这个小型 shuffle 的并行度与任务依赖。当然它相当简单，因为所有数据都放得进单台机器的内存。下一个例子，我们将挑战完整规模的 shuffle，而且是在多节点上。

## 带外部存储溢出的多节点 Shuffle

试一个更大的例子：16GB、4 个分区，中间结果（方块）为 1GB：

*多节点 shuffle：溢出到外部存储。*

现在我们要在*分布式、核外（out-of-core）*环境中执行：比如 2 台机器的集群，每台 1 CPU、4GB 内存。由于整个数据集放不进内存，我们再加一个外部存储系统：

*加入外部存储。*

由于一次只能执行两个任务，每个阶段要分两波调度。蓝、紫 map 任务的第一波与单节点情况几乎一样，因为我们有足够内存存放它们的输出：

*外部存储暂存输出。*

但当另外两个 map 任务（绿、橙）运行时怎么办？我们没有足够内存存放那些输出！

*内存不足以存放两个输出。*

此时，每个 Ray 节点开始把当前对象（蓝、紫）溢出到外部存储，为新对象（绿、橙）腾出空间。这些对象必须溢出而非删除，因为 reduce 任务还依赖它们。

*蓝、紫对象被自动溢出到远端存储，为新的 map 任务输出（绿、橙）腾出空间。*

当然，在 reduce 阶段，我们还必须恢复被溢出的对象，reduce worker 才能从内存取到它们。每个 Ray 节点根据被调度任务的依赖（下图中红色描边）决定恢复哪些对象。为了给 reduce 任务的参数腾地方，每个 Ray 节点再次溢出本地对象。

*恢复 reduce 任务现在需要的已溢出对象。红色描边的方块是两个被调度 reduce 任务（灰色圆圈）所需的对象。为了给任务参数腾出空间，Ray 再次溢出，这次溢出绿色与橙色的 map 输出。*

总体而言，这个负载需要对 map 任务产出的 N^2 个中间结果进行一轮溢出与恢复，尚不包括读取初始数据集和写出最终结果所需的内存。例如，16GB 数据集时每个中间结果为 1GB，我们在 shuffle 步骤期间向外部存储写入并读回 16GB 数据。

当分区更小时，我们可能受外部存储系统随机 IO 能力的限制。过多的小读写请求会让外部存储成为瓶颈。为避免这一点，Ray 还会把发往同一目标（例如同一个文件）的多个中间结果合并成一次写请求。读的合并更棘手，我们计划未来在此实现文献中的优化。

## 限制内存的同时防止死锁

前面两个例子中，我们总有足够内存执行与核数等量的任务。在 2 节点的例子里，每个节点 1 CPU、4GB 内存，恰好是执行一个任务所需的量，调度因此很直接。

但资源不会总是这么均衡。内存密集型负载的一个挑战，是在不耗尽内存的前提下取得并行度。我们希望按机器的核数并行执行任务，又不希望并行任务多到超出节点内存。真发生的话，会触发操作系统的 OOM 处理，如 OOM killer。

Ray 通过为每个节点对象存储的总内存设置用户可配置的上限来避免这一点。但这只是解决方案的一部分。如果我们只按 CPU 可用性调度、无视内存需求，很容易撞上死锁。

例如，假设我们要在一台 2 CPU、6GB 内存的单机上执行上一个例子。若按 CPU 可用性调度任务，就可能出现这样的死锁：

*仅考虑 CPU 可用性的朴素调度可能产生死锁的示例。调度器试图同时调度两个 reduce 任务（灰色圆圈），造成死锁，因为两个任务各还需一块内存才能运行。*

一个任务只有当*全部*依赖都在本地对象存储后才能开始。这意味着要并行执行两个 reduce 任务，需要总共 8GB 内存存放其参数。但这里只有 6GB，于是死锁：每个任务完成前不能释放自己的参数，而每个任务还需要额外的 1GB 内存才能开始执行。

为了防止这一问题，Ray 的调度器同时考虑每个任务的*内存需求*——根据其输入参数的大小计算。系统按节点 CPU *与*内存的总可用性来调度任务：

*Ray 通过按 CPU 与内存可用性调度任务来防止死锁。Ray 发现内存只够一次执行一个任务，因此先取浅灰色任务的参数。该任务完成后，再对深灰色任务重复同样过程。*

因此在这个例子里，Ray 会看到每个任务共需 4GB 内存存放参数。由于我们只有 6GB 内存，尽管 CPU 足够同时跑两个任务，Ray 也一次只为一个 reduce 任务取参数。某个 reduce 任务结束后，释放其参数，再继续队列中的下一个 reduce 任务。

## 结语

本文展示了 Ray 如何为数据密集型应用提供内存管理。为此，Ray：

- 提供高性能的共享内存对象存储。
- 内存写满后将对象透明溢出到外部存储。
- 在任务调度时实施准入控制，强制内存上限并防止死锁。
