# 推出 Ray History Server：Ray on Kubernetes 的事后可观测性

作者：Andrew Sy Kim（Google）、Aaron Liang（Google）、Han-Ju Chen、Jia-wei Jiang、Kun Wu（阿里云）、Jui-An Huang、Mengjin Yan、Nai-Jui Yeh 和 Chun-Hao Wan | 2026 年 8 月 25 日

## Ray History Server

Ray 用户把 Ray 集群当作临时计算单元使用的情况越来越常见：为单个作业创建，作业完成即拆除。这种模式改善了成本效率与资源共享，在硬件加速器稀缺的容量受限环境中尤其如此。

这种方式的代价是：与长生命周期的集群不同，会话日志、内存状态和 Ray Dashboard 会随集群一起消失。用户可以把日志与指标导出到外部可观测系统，但调试一个失败的作业意味着要把任务与 actor 状态、各节点日志、错误 trace 对应起来。Ray Dashboard 正是把这一切关联在一起的唯一场所——没有它，事后调试几乎不可能。

随着最新的 KubeRay v1.7 发布，History Server 已晋升为 beta 并可用，让集群终止后的 Ray 集群数据依然可以访问。

Ray History Server 通过在集群终止后重建必要的 Ray 相关端点，弥合了这一可观测性缺口。

### 集群选择页

在深入 history server 之前，先看它能做什么。History server 提供内建的集群选择页，作为事后可观测的集中入口：动态发现并归档对象存储中保存的所有历史运行以及当前的在线集群。

*Ray History Server*

用户可以按集群名、namespace 与 owner 资源搜索、过滤过往或当前的运行。每个 session 条目会标明它是在线还是已终止。点击任何历史或在线 session，用户即被跳转到对应的 Ray Dashboard 界面。

对已终止的会话，history server 从对象存储采集的遥测数据重建 Dashboard；对在线会话，它把请求代理到集群正在运行的 Ray Dashboard——包括为启用了 Ray 认证的集群自动注入认证 token——无论集群是否还在运行，用户都拥有同一个入口。

选定会话后，history server 用兼容 Dashboard 的 REST API 支撑标准 Ray Dashboard 前端。无论集群还在线，还是已终止几小时或几天，用户浏览的都是他们早已熟悉的同一个 Dashboard 界面，并获得所需的全部事后上下文——不必为了保留访问权而闲置集群。

### 架构总览

History server 里到底有什么？两个主要组件，对应让 Ray 集群"复活"所需两个阶段（记录数据与回放数据）的根本差异：负责记录数据的组件是 collector，负责回放数据的另一个组件就是 history server 本身。

*Ray Pod 边界*

#### Collector 深入

先从 collector 说起。Collector 是挂在所有 Ray head 与 worker pod 上的 sidecar。如上所述，它的职责是从对应的 Ray 容器收集数据。Collector 内部有两条主要流程/子系统：一个负责日志，另一个负责 Ray 事件。

事件采集子系统目标是以磁盘优先的采集方式，捕获 Ray 负载的高速遥测而不过多消耗集群内存。启用事件导出 API 后，Ray 容器持续导出结构化运行时事件——从 driver 作业生命周期到节点特定事件。事件采集子系统不把几百万事件缓冲在内存里，而是立即把进来的负载直接流式写入本地磁盘。这些文件按可配置的时间间隔或文件大小阈值自动轮转。上传前还可以压缩，以最小化云对象存储的上传下载时间。为保证 collector 容器及 pod 的稳定，collector 还内建可配置的磁盘总限额与磁盘压力水位线——在瞬态故障或网络问题时，用 503 错误拒绝进来的事件请求。

事件采集子系统跟踪结构化事件，而日志采集子系统正如名字所示，处理 Ray 日志与集群元数据。它的主要工作是确保会话日志被上传到对象存储。上传发生在三个不同生命周期时刻：

- Pod 终止时：RayJob 结束或 Kubernetes 开始拆除 pod
- 启动与崩溃恢复时：上传上一个会话遗留的日志
- 会话切换时：Ray 在运行中轮转或开启新 session

除了上传日志，日志 collector 还充当集群元数据采集器。仅在 head pod 上，它在启动时一次性捕获 Ray 版本、时区等集群元数据，并周期性快照那些无法从事件重建的 Dashboard 端点（如 Ray Data 数据集与 placement group），使其最后已知状态在终止后仍然可用。

#### History Server 深入

History server 是系统的读路径：回放 collector 写下的数据。它是面向事后调试的按需、无状态重建引擎，把对象存储中原始的压缩文件变回原生 Ray Dashboard 体验。

每次请求都处理几百个事件与日志文件会耗尽资源，而维护一个持久的预处理档案通常昂贵且大部分时间闲置。为优化性能又确保稳定，history server 采用懒加载策略并以 LRU 缓存补足：

- 懒加载：把事件文件的拉取与解压推迟到用户选定具体会话之后，最小化对象存储请求与基础设施开销，避免不必要的读取，也消除了对托管数据库的依赖。对同一冷会话的并发请求会被合并，防止对对象存储的惊群读取；可配置的超时守护避免无限挂起。
- LRU 缓存：用条目数上限与字节预算双重约束内存用量。由于 Ray 会话的大小差异极大——从 2MB 到超过 500MB——基于大小的预算是让 history server 始终保持在 pod 内存限额之内的关键。

得益于这一设计，单个 history server 部署即可为许多集群提供事后可观测 Dashboard。

#### 对象存储

History server 在设计上存储无关，构建于单一存储接口之上。组织可以接入现有对象存储而不被厂商锁定。开箱即用，它原生支持：

- Google Cloud Storage：原生 GCS 集成，支持 GKE workload identity 实现免密钥认证
- AWS S3 与 MinIO：Amazon S3 及任何 S3 兼容对象存储，经 IAM Roles for Service Accounts 或静态凭证认证
- 阿里云 OSS：Aliyun Object Storage Service，配合服务账号的 RAM Role
- Azure Blob Storage：经 Azure Workload Identity 或连接字符串集成

存储布局是确定性的，任何会话都可以通过简单的前缀查找定位，即使多租户环境也是如此。数据按资源归属组织：路径中包含更高层的资源 owner（如 `RayJob`、`RayService`），支持更细粒度的过滤，并建立清晰的工作负载溯源。对象存储分为两棵子树：

- `cluster-metadata`：空文件的轻量索引，路径编码了 namespace、owner、cluster 与 session
- `cluster-history`：会话遥测——原始日志、事件文件与端点快照

```
cluster-metadata/
│   ├── raycluster/
│   │   └── <namespace>_<cluster_name>/
│   │       └── <session_name>                # Empty marker file
│   └── <rayjob|rayservice>/
│       └── <namespace>_<owner_name>_<cluster_name>/
│           └── <session_name>
cluster-history/
├── raycluster/
│   └── <namespace>/
│       └── <cluster_name>/
│           └── <session_name>/
│               ├── fetched_endpoints/   # Dashboard endpoint snapshots
│               │   ├── restful__api__v0__nodes__summary
│               │   └── ...
│               └── <node_id>/
│                   ├── logs/
│                   │   ├── dashboard_agent.log
│                   │   ├── raylet.out
│                   │   └── ...
│                   ├── node_events/
│                   │   └── <node_id>-<date_hour>   # Node event logs
│                   └── job_events/
│                       └── <job_id>/
│                           └── <node_id>-<date_hour> # Job event logs
└── <rayjob|rayservice>/
    └── <namespace>/
        └── <owner_name>/
            └── <cluster_name>/
                └── <session_name>/     # Same node layout as above
```

### 性能与容量基准

我们对 history server 数据路径做了 1k 到 50k 任务的会话基准，验证其线性扩展。应用了两项调优：给 history server 至少 1.5 CPU 核心，并在 collector 开启 gzip 压缩。压缩削减约 91% 的存储开销，额外的 CPU 让会话冷加载快约 2.4 倍、可打开的最大会话规模提升 2.5 倍。

| **指标** | **基线（gzip 关闭，0.5 CPU 核心）** | **调优后（gzip 开启，1.5 CPU 核心）** | **影响** |
| --- | --- | --- | --- |
| 每任务事件存储 | 约 3.75 KiB（4.3 个事件 × 895 B） | 约 355 B（10.85:1 压缩） | 小 91% |
| 10 万任务会话的存储 | 约 385 MiB | 约 35.5 MiB | 每会话省约 349.5 MiB |
| 每任务冷加载时间 | 约 0.2 ms（CPU 被限流） | 约 0.084 ms（未限流） | 快约 2.4 倍 |
| 可打开的最大会话 | 约 2 万任务（更大会话超出约 5 秒的 UI 预算） | 约 5 万任务（4.21 秒打开） | 大 2.5 倍 |

性能在 1.2 核心后趋于平坦，分配更多 CPU 没有可测量的改善，因此 1.5 到 2 核心是 history server 稳妥的初始容量建议。完整基准细节见 [history server 基准仓库](https://github.com/Future-Outlier/historyserver-benchmark)。

### 未来路线图

当前 history server 虽已 beta 并提供稳健的事后调试服务，仍有若干增强在设计中，以进一步简化运维、扩展可观测性。

- Collector sidecar 自动注入——为降低采用门槛，未来版本将在 KubeRay operator 中引入稳定的自动 collector 注入。用户将能在 `RayCluster` spec 中以声明式方式开启遥测采集。早期版本已通过 [`HistoryServerOptions`](https://github.com/ray-project/kuberay/blob/bf50aa1353295188ae9335bc0e9911dbe0754535/ray-operator/apis/ray/v1/raycluster_types.go#L274) 在 `RayClusterHistoryServer` feature gate 后面提供。
- 扩展指标与指标回放——事后调试常需要在查看任务的同时检查系统指标，我们的目标是内建历史指标时间线支持：捕获 GPU/CPU 利用率、内存压力与 actor 吞吐。
