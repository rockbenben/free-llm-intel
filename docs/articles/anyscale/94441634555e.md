# 宣布 Ray 支持 Google TPU 上的 PyTorch

作者：[Lehui Liu](https://www.anyscale.com/blog?author=lehui-liu)、[Richard Liaw](https://www.anyscale.com/blog?author=richard-liaw)、[Andrew Sy Kim (Google)](https://www.anyscale.com/blog?author=andrew-sy-kim-google)、[Nisha Mariam Johnson](https://www.anyscale.com/blog?author=nisha-mariam-johnson) 与 [Ryan O'Leary (Google)](https://www.anyscale.com/blog?author=ryan-oleary-google) | 2026 年 10 月 20 日

今年早些时候，在 Ray Summit 2026 上，我们介绍了 [PARK 技术栈](https://www.oreilly.com/radar/what-is-the-park-stack/)（PyTorch、AI 模型、Ray 和 Kubernetes）如何正在成为生产级 AI 的行业标准。长期以来，Ray 一直是 GPU 上 PyTorch 工作负载无处不在的分布式运行时。

今天，Anyscale 与 Google Cloud 宣布为 Google TPU 上的 PyTorch 提供原生 Ray 支持——TPU 是承载 Gemini 以及 Google Cloud 上大规模 AI 工作负载的基础超级计算基础设施。

在 Google 的 [TorchTPU 项目](https://cloud.google.com/blog/topics/ai-infrastructure/torchtpu-is-now-open-source-run-native-pytorch-on-tpus)以及 Google Kubernetes Engine（GKE）上的 KubeRay 的基础上，这一集成把原生、每个 worker 单设备的 PyTorch 体验带到了 Cloud TPU 上。运行在 GKE 上的平台团队与 ML 团队，现在可以在单一 Kubernetes 控制平面上，跨 GPU 和 TPU 调度、扩展并运维分布式 PyTorch 训练、vLLM 推理与强化学习（RL）工作负载。

## Google TPU 上的原生 PyTorch

从历史上看，在 Ray 上运行 TPU 工作负载需要适配主要为 JAX 设计的单程序多数据（SPMD）执行模型：每个宿主机 VM 上只有一个 Ray worker 进程，由它管理整台机器上挂载的所有 TPU 芯片。[TorchTPU](https://cloud.google.com/blog/topics/ai-infrastructure/torchtpu-is-now-open-source-run-native-pytorch-on-tpus) 于去年推出，是 Google 面向张量处理单元（Tensor Processing Unit）的原生 PyTorch 后端，带来了以 eager 模式为先的原生 TPU 集成，以及用于在 TPU 上运行分布式工作负载的 `torch.distributed` 扩展。

继 TorchTPU 之后，我们把 Ray 演进为每个 TPU 芯片运行一个 worker，与 PyTorch 开发者在 GPU 上习惯的每个 worker 单设备模型保持一致。

使用 Ray 和 TorchTPU 调度任务或 actor 时，每个 worker 申请一个逻辑 TPU 设备（`resources={"TPU": 1}`），就像 GPU worker 申请 `num_gpus=1` 一样：

- **设备隔离：** 正如 Ray 会为 GPU worker 自动设置 `CUDA_VISIBLE_DEVICES`，Ray 也会通过 `TPU_VISIBLE_CHIPS` 隔离各个 TPU 设备并把它们分配给 worker
- **原生的 PyTorch 设备与集合通信：** 在 Ray 任务或 actor 内部，把现有 PyTorch 代码从 GPU 迁移到 TPU，只需把 `"cuda"` 改成 `"tpu"`，并把分布式通信后端从 `"nccl"` 换成 `"tpu_dist"` 即可。
- **拓扑感知的成组调度：** GKE 把多主机 TPU 切片配置为通过高速芯片间互连（ICI）连接的节点池。为了利用这种物理布局，Ray 的 [SlicePlacementGroup](https://docs.ray.io/en/latest/ray-core/api/doc/ray.util.tpu.SlicePlacementGroup.html) API 提供了原生调度实现，保证各 actor 被成组调度到同一个 TPU 切片上。

下面是在 TPU 上使用 Ray actor 执行分布式 PyTorch `all_reduce` 的示例。除了资源请求和设备/后端字符串之外，这段代码与在 GPU 上运行的 Ray actor 完全相同：

```
import os
import ray
import torch
import torch.distributed as dist

# On GPU: @ray.remote(num_gpus=1)
@ray.remote(resources={"TPU": 1})
class TorchWorker:
    def __init__(self, rank: int, world_size: int):
        self.rank = rank
        self.world_size = world_size
        # Ray automatically isolates the assigned device via TPU_VISIBLE_CHIPS
        self.local_rank = os.environ["TPU_VISIBLE_CHIPS"]

    def run_all_reduce(self, master_addr: str, master_port: int):
        os.environ["MASTER_ADDR"] = master_addr
        os.environ["MASTER_PORT"] = str(master_port)
        os.environ["WORLD_SIZE"] = str(self.world_size)
        os.environ["RANK"] = str(self.rank)
        os.environ["LOCAL_RANK"] = self.local_rank

        # On GPU: dist.init_process_group(backend="nccl")
        dist.init_process_group(backend="tpu_dist")

        # On GPU: device = torch.device("cuda")
        device = torch.device("tpu")
        tensor = torch.ones(2, 2, device=device) * self.rank

        dist.all_reduce(tensor, op=dist.ReduceOp.SUM)
        return tensor.cpu().numpy()
```

## TPU 上的 TorchTrainer

对于分布式训练和微调，许多团队依赖 Ray Train 的 `TorchTrainer` 来编排分布式数据并行（DDP）、完全分片数据并行（FSDPv2）和 DTensor 工作负载，而无需为分布式进程组手写样板代码。

借助 Ray Train 对 TorchTPU 的原生支持，你现在可以在单主机和多主机 Cloud TPU 切片上运行现有的 `TorchTrainer` 脚本，对 PyTorch 训练循环零改动。

当你通过 `ScalingConfig` 为 TPU 配置 `TorchTrainer` 时，Ray Train 会自动处理底层所有 TPU 编排工作：

- **原子化预留 TPU 切片：** 只要在指定目标 `topology`（例如 `"4x4"`）和 `accelerator_type`（例如 `"TPU-V6E"` 或 `"TPU-V7X"`）的同时指定 `use_tpu=True`，`TorchTrainer` 就会在底层自动创建一个 `SlicePlacementGroup`。这保证所有训练 worker 都通过高速 ICI 被成组调度到连续的物理 TPU 切片上，避免资源碎片化。
- **自动化的 **`**tpu_dist**`** 引导：** Ray Train 会为每个 TPU 设备启动一个 worker（`resources_per_worker={"TPU": 1}`），自动配置 PyTorch 分布式环境变量（`RANK`、`WORLD_SIZE`、`LOCAL_RANK`、`MASTER_ADDR`、`MASTER_PORT`）以及 TorchTPU 的 slice-builder 地址和 mesh 拓扑，并初始化 `tpu_dist` 进程组。
- **可直接替换的 Ray Train 工具函数：** `ray.train.torch.get_device()`、`ray.train.torch.prepare_model()` 等标准 Ray Train 辅助函数会自动检测 TorchTPU 运行时，把模型移动到分配给它的 `tpu` 设备，并用 PyTorch 的 DistributedDataParallel 类包装模型。

下面是一个完整示例：使用 `TorchTrainer` 把一个 PyTorch 训练循环扩展到 16 芯片、多主机的 Trillium（`TPU-V6E`，`4x4` 拓扑）切片上：

```
import ray
from ray import train
from ray.train import ScalingConfig
from ray.train.torch import TorchTrainer
import torch
from torch import nn, optim
import torch.distributed as dist

def train_fn_per_worker(config):
    # Automatically resolves to torch.device("tpu") on TPU workers
    device = ray.train.torch.get_device()

    model = nn.Sequential(
        nn.Linear(10, 32),
        nn.ReLU(),
        nn.Linear(32, 1),
    ).to(device)

    # Wraps the model in DDP over the "tpu_dist" backend
    model = ray.train.torch.prepare_model(model)

    criterion = nn.MSELoss()
    optimizer = optim.SGD(model.parameters(), lr=0.05)

    inputs = torch.randn(128, 10, device=device)
    targets = inputs.sum(dim=1, keepdim=True)

    for epoch in range(10):
        optimizer.zero_grad()
        outputs = model(inputs)
        loss = criterion(outputs, targets)
        loss.backward()
        optimizer.step()

        train.report({"loss": loss.item(), "epoch": epoch + 1})

scaling_config = ScalingConfig(
    num_workers=16,
    use_tpu=True,
    topology="4x4",
    accelerator_type="TPU-V6E",
    resources_per_worker={"TPU": 1},
)

trainer = TorchTrainer(
    train_loop_per_worker=train_fn_per_worker,
    scaling_config=scaling_config,
)

result = trainer.fit()
```

关于在 Google Kubernetes Engine（GKE）上的完整端到端演练，请参见[使用 Ray 和 TorchTPU 在多主机 TPU 上训练模型](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/train-models-tpu-ray-torchtpu)。

## 配合 Ray Serve 使用 vLLM-TorchTPU

对于在线推理，[vLLM-TorchTPU](https://github.com/vllm-project/vllm-torchtpu) 把 TorchTPU 注册为 vLLM 平台插件，使 PyTorch 模型无需用 JAX 重写模型定义即可在 Cloud TPU 上编译和执行。再结合 [Ray Serve LLM](https://docs.ray.io/en/latest/serve/llm/index.html)，你就能用与 GPU 上相同的声明式 `LLMConfig` API，在单主机和多主机 TPU 切片上部署兼容 OpenAI 的 vLLM 端点。

当 `accelerator_type` 和 `accelerator_config` 指定了 TPU 切片时，Ray Serve 会为每个副本预留一个拓扑感知的 `SlicePlacementGroup`，并在整个切片上启动 vLLM 引擎 worker：

```
from ray.serve.llm import (
    LLMConfig,
    LLMServingArgs,
    ModelLoadingConfig,
    build_openai_app,
)
llm_config = LLMConfig(
    model_loading_config=ModelLoadingConfig(
        model_id="google/gemma-4-26B-A4B-it",
    ),
    # On GPU: accelerator_type="H100"
    accelerator_type="TPU-V6E",
    accelerator_config={
        "kind": "tpu",
        "topology": "4x4",
    },
    placement_group_config={
        "bundle_per_worker": {"TPU": 1},
    },
    engine_kwargs={
        "tensor_parallel_size": 16,
        "enable_expert_parallel": True,
        "max_model_len": 8192,
    },
)
app = build_openai_app(LLMServingArgs(llm_configs=[llm_config]))
```

关于在 Google Kubernetes Engine（GKE）上的完整端到端演练，请参见[使用 Ray 和 TorchTPU 在多主机 TPU 上服务 LLM](https://cloud.google.com/kubernetes-engine/docs/tutorials/serve-llm-tpu-ray-torchtpu)。

## 把 PARK 技术栈扩展到 TPU

随着 AI 工作负载从独立的训练作业演变为结合训练、高吞吐推理和强化学习的复合系统，各组织正在把开源 PARK 技术栈（PyTorch、AI 模型、Ray 和 Kubernetes）作为标准化选择。把 TorchTPU 引入 Ray 和 GKE，让这一愿景在 Google Cloud 上得以完整实现：PyTorch 开发者保留他们已经熟悉的 eager 执行模型和 Ray API，平台团队则获得 GKE 的拓扑感知自动扩缩容、弹性以及多加速器治理能力。

今天就可以上手：探索使用 Ray 和 TorchTPU 的端到端 GKE 教程——[服务 LLM](https://cloud.google.com/kubernetes-engine/docs/tutorials/serve-llm-tpu-ray-torchtpu)或[训练模型](https://docs.cloud.google.com/kubernetes-engine/docs/tutorials/train-models-tpu-ray-torchtpu)，并敬请期待我们把这一基础扩展到大规模 RL 后训练框架以及 GKE 上下一代 Ironwood（TPU v7x）切片。
