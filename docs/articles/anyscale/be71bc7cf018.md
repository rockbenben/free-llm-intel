## Link为什么 GPU 饥饿很难捕捉

模型训练是资本密集型的，因此训练团队需要密切关注 GPU 利用率。在数百或数千个 GPU 的规模上，即使是很小的速度下降也会导致大量 GPU 小时的损失。

为了保持 GPU 忙碌，下一批数据需要在模型完成当前数据时准备好。如果不是，GPU 就会坐下来等待。这就是 GPU 匮乏，也是利用率下降的最常见原因之一。它也是最安静的之一：没有崩溃，没有警报，作业只是运行得比应有的速度慢一点。

团队通常会注意到以下两种症状之一：GPU 利用率上下波动而不是保持稳定，或者训练运行时间比预期更长。例如，在下面的运行中，每个 GPU 上的 SM 活动不断上升和下降，而不是达到稳定状态：

![GPU SM 活动](https://images.ctfassets.net/xjan103pcp94/6efx8aEOfivG4fBTk2pWiR/d54c4eef90caf4f957228e1c63e2ae59/GPU_SM_Activity.png)

GPU SM 活动

这种模式是 GPU 匮乏的典型迹象。数据加载和训练并行运行：当 GPU 训练一批数据时，正在准备下一批数据。当准备一个批次比训练它花费的时间更长时，训练步骤首先完成，并且 GPU 处于空闲状态，直到下一个批次到达：

![训练步骤](https://images.ctfassets.net/xjan103pcp94/3HeLY6JhzRD8Xv2MB0z6pn/b88099eec738f33817d53eb3f7d8ff24/training_steps.png)

训练步骤

每个空闲间隙都是上面利用率图表中的下降之一。该症状很容易被发现。原因并非如此。批次可能会由于多种原因而延迟到达：上游数据管道缓慢、数据从另一个节点通过网络传输、训练工作人员上的繁重预处理（例如昂贵的 `collate_fn` 或主机到设备的副本）。每个原因都有不同的修复方法，因此第一步是找出哪个阶段是瓶颈。

本文的其余部分将介绍用于执行此操作的工具：

- **开源 Ray 中的数据摄取指标：**Ray Train 和 Ray Data 如何计时数据加载的每个阶段，以及如何读取 Grafana 图表以查看训练是否在数据上停滞、哪个阶段负责以及需要更改哪些内容。
- **Anyscale 上的数据摄取可观察性：**无需设置的相同图表，加上 Ray Train 仪表板上的实时数据摄取面板，该面板总结了每个正在运行的数据集的摄取健康状况。 KubeRay Connect 将这两种功能带入您自己管理的 KubeRay 集群中。

## LinkData 在开源 Ray 中摄取指标

从 Ray 2.58 开始，Ray Train 和 Ray Data 记录每个批次在数据加载的每个阶段花费的时间，以便您可以看到哪个阶段阻碍了训练。如果您的 Ray Train 代码已从 Ray Data 读取，则无需更改代码。

典型的设置如下所示。驱动程序定义一个 Ray 数据集，这里是从 S3 读取的 Parquet 文件，并将其传递给训练器。 Ray Train 为八名训练人员中的每一位提供了自己的数据集碎片。每个工作线程使用 `iter_torch_batches` 读取其分片，这会应用您的 `collate_fn` 并返回 64 行的批次作为 PyTorch 张量：
```
import ray
import ray.train
from ray.train import ScalingConfig
from ray.train.torch import TorchTrainer

train_ds = ray.data.read_parquet("s3://my-bucket/train/")

def train_func():
    shard = ray.train.get_dataset_shard("train")
    for batch in shard.iter_torch_batches(batch_size=64, collate_fn=my_collate):
        ...  # your training step

trainer = TorchTrainer(
    train_func,
    datasets={"train": train_ds},
    scaling_config=ScalingConfig(num_workers=8, use_gpu=True),
)
trainer.fit()
```
单个 `iter_torch_batches` 调用是所有数据加载发生的地方。与所有其他 Ray Data 迭代器（包括 `iter_batches`、`iter_rows` 和 `to_tf`）一样，它在将每个批次传递给训练循环之前通过相同的管道移动每个批次。

在该调用中，每个批次从射线数据管道到 GPU 的过程中都会经过六个阶段。其中任何一个都可能成为瓶颈：

| **舞台** | **它测量什么** |
| --- | --- |
|生产等待|等待上游 Ray Data 管道生成下一个块 |
|数据传输|向训练工作者获取块，包括从另一个节点的对象存储中获取块 |
|配料|将块切片并组合成批次，包括任何本地洗牌缓冲区 |
|格式|将每个批次转换为请求的格式，例如 NumPy 或 pandas |
|整理 |在训练工作线程上运行您自己的每批次预处理，例如将文本或填充序列标记为通用长度，以 `collate_fn` | 形式传入。
|完成 |在 `iter_torch_batches` 中将批次复制到 GPU（主机到设备传输） |

这些阶段不会在您的训练线程上依次运行。相反，后台线程池会同时运行它们，以便在训练步骤运行时准备下一批。只要在训练步骤完成之前准备好下一批，所有这些工作都是隐藏的，不会花费您任何挂钟时间。当下一批没有及时准备好时，训练循环将等待并且 GPU 处于空闲状态。该等待是公开的数据加载时间。雷将其记录在每个培训工人身上，以及每个阶段所花费的时间。

在开源 Ray 中，一旦您为集群设置了 Prometheus 和 Grafana，这些指标就会出现在 Grafana 的训练仪表板的数据摄取部分中。这些图表按顺序回答了三个问题，此处显示的是在昂贵的 `collate_fn` 上停滞的运行：

- **训练是否因数据而停滞？最大公开数据加载时间**显示训练循环在最慢的排名上等待每个批次的时间。如果为零，数据加载会继续进行，调整管道也无济于事。如果不是，则该时间是每个步骤的 GPU 空闲时间。
![最大暴露数据加载时间](https://images.ctfassets.net/xjan103pcp94/65VRgaMmjzZAXQSM0M4ZvI/f8fc9c56fcb80754a243bc9120a7c922/Max_Exposed_Data_Loading_Time.png)最大暴露数据加载时间
- **哪个阶段负责？按阶段划分的数据加载百分比细分**显示每个阶段在所有级别中汇总的数据加载时间份额。大量的生产等待份额意味着上游 Ray 数据管道无法足够快地生成数据。任何其他阶段的大部分工作都指向培训工人本身。
![按阶段划分的数据加载百分比细分](https://images.ctfassets.net/xjan103pcp94/6MxxlEPDpHt4S3KjISIsTa/6ad4c0422cfb4f022cc2f00f4b436756/Percentage_Data_Loading_Breakdown_by_Stage.png)按阶段划分的数据加载百分比细分
- **是每个等级还是只有一个？ **每个阶段都有自己的按等级细分的图表。如果一个排名远远高于其他排名，那么它就是一个掉队者，并且因为排名在每一步上都是同步的，所以一个缓慢的排名可能会阻碍整个运行。
![按等级的生产等待时间](https://images.ctfassets.net/xjan103pcp94/hm30tpbpea97dTcf8F0tQ/5a709f470f52229f8f1239ae6074de57/Production_wait_time_by_rank.png)按等级的生产等待时间

两个吞吐量图使视图更加完整。 **按等级划分的数据摄取吞吐量**显示每个等级每秒消耗的行数，而**数据生产吞吐量**显示 Ray Data 管道每秒交付给训练的行数。它们一起显示了健康运行的稳态率，因此排名之间的下降和不平衡很突出。

![按排名划分的数据摄取吞吐量和数据生产吞吐量](https://images.ctfassets.net/xjan103pcp94/48JKCQlR1RbRXrO6TBZMHe/7a3d17850cb65bc2ae74f2751144bd08/Data_Ingest_Throughput_by_Rank___Data_Production_Throughput.png)

按排名和数据生产吞吐量划分的数据摄取吞吐量

知道哪个阶段负责才能使问题变得可行，因为每个阶段都指向需要检查或更改的特定事项：

| **瓶颈** | **尝试什么** |
| --- | --- |
|生产等待|检查 Ray Data 仪表板以查找上游管道中最慢的操作员并调整其配置。您还可以添加仅包含 CPU 的节点，以便 Ray Data 可以横向扩展预处理，或者使用 `materialize()` 将预处理后的数据集缓存在内存中（如果合适）。 |
|数据传输|增加 `prefetch_batches` 以便块在训练步骤之前开始传输。值越高，内存中保存的批次越多，因此请观察训练节点上的内存使用情况。 |
|配料|如果您使用 `local_shuffle_buffer_size`，请减少它或对上游进行随机播放，例如使用 `map_batches` 随机播放或在读取时随机播放文件顺序。 |
|格式|增加 `prefetch_batches` 以便在训练步骤之前转换更多批次。 |
|整理 |使用 `map_batches` 将繁重的预处理从 `collate_fn` 移至 Ray Data 管道中，在整个集群中横向扩展，而不是在训练工作线程上运行。对于较轻的整理工作，增加 `prefetch_batches` 也可以通过在训练步骤之前准备更多批次来提供帮助。 |
|排名落后一位 |检查该等级的节点有什么不同。常见原因是 Ray Data 任务与训练工作线程竞争 CPU 或内存，以及从远程节点重复获取块。如果 Ray Data 任务正在争夺资源，请通过使用 `label_selector` 将数据集固定到仅 CPU 节点，使它们远离训练节点。 |

## LinkData 在 Anyscale 上摄取可观测性

在 Anyscale 上，您无需设置即可获得所有这些 Grafana 图表。 Anyscale 收集每次训练运行的指标，并在 Ray Train 仪表板上显示图表，因此无需托管 Prometheus 或 Grafana。

在 Grafana 图表之上，Anyscale 上的 Ray Train 仪表板包括一个实时数据摄取面板。您无需阅读十几个图表，而是可以实时查看整个集群的数据摄取运行状况。下面的加速记录显示了在整理时停滞的运行情况：

![实时数据摄取健康状况](https://images.ctfassets.net/xjan103pcp94/41aR4DzOauQ4hlZnkLZACd/d50db1f3ad178f82bdee37b75d318f5c/Live_data_ingestion_health.gif)

实时数据摄取健康状况

对于当前正在执行的每个射线数据数据集，面板显示以下内容。每批次指标适用于您选择的排名；记录显示最慢的排名。

- **摄取进度：**训练通过数据集的进度，作为摄取总数中的行数。
- **吞吐量：**每秒由上游数据管道生成并由训练摄取的行数。
- **暴露的数据加载停滞：**训练循环等待每批数据的时间。
- **训练计算时间：**每批训练步骤需要多长时间。
- **批次周期：**每个批次的总时间，分为训练计算和暴露的停顿。
- **阶段细分：**六个数据加载阶段中每一个阶段的每批时间，因此瓶颈很突出。在录音中，校对几乎占据了所有内容，直接指向`collate_fn`。
- **链接到 Grafana：**单击即可查看完整的数据摄取图表，了解历史指标和更多详细信息。

本节中的所有内容都是 Anyscale 平台内置的可观察性的一部分。如果您运行自己的 KubeRay 集群，[KubeRay Connect](https://docs.anyscale.com/kuberay-connect) 会将其提供给他们，而无需迁移工作负载。

有了这些指标，不稳定的 GPU 利用率就变成了可以追踪到单个瓶颈的东西，而不是你猜测的东西。修复该阶段，您的 GPU 就会保持正常状态：利用率上升并保持稳定，并且相同的运行在相同的硬件上更快完成。

要深入了解，请参阅 Ray 文档中的这些指南：

- [调试数据加载瓶颈](https://docs.ray.io/en/master/train/user-guides/data-loading-preprocessing.html#debug-data-loading-bottlenecks) 涵盖了完整的深入分析和每个结果的修复。
- [Ray Data 如何迭代数据？](https://docs.ray.io/en/master/data/internals.html#how-does-ray-data-iterate-over-data) 涵盖了六个阶段背后的线程模型。

## 链接摘要

GPU 利用率不稳定会告诉您出现问题，但不会告诉您具体问题是什么。从 Ray 2.58 开始，Ray Train 和 Ray Data 中的每阶段数据加载指标缩小了这一差距。它们会告诉您数据加载是否是阻碍训练的原因，如果是的话，瓶颈在哪里，以便您知道下一步该往哪里看。在开源 Ray 中，指标显示在 Grafana 的 Train Dashboard 中。在 Anyscale 上，您无需设置即可获得相同的图表，以及总结每个正在运行的数据集的实时数据摄取面板。

## 链接后续步骤

GPU 饥饿是导致生产训练难以调试的几个问题之一，Ray 团队正在继续将可观测性构建到 Ray Train 中，以解决最常见的问题。这是我们接下来要做的工作：

- **自动挂起检测和堆栈跟踪捕获。 **Ray Train 将检测训练何时停止进展，并自动捕获每个工作人员的堆栈跟踪，因此您可以看到每个工作人员卡在哪里，而无需重现挂起。
- **健康监测。 **更广泛地监控训练运行状况，包括硬件运行状况检查，以发现导致生产训练运行减慢或停止的问题。

如果您遇到这些工具未涵盖的数据提取问题，或者对我们接下来应该构建的内容有想法，请[在 GitHub 上提交问题](https://github.com/ray-project/ray/issues)。
