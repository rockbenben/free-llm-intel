## Link为什么 GPU 饥饿难以发现

模型训练是资本密集型工作，因此训练团队需要密切关注 GPU 利用率。在数百甚至数千张 GPU 的规模上，哪怕只是小幅变慢，累积起来也会损失大量 GPU 小时。

要让 GPU 保持忙碌，下一批数据必须在模型算完当前批次的那一刻就准备就绪。若没有准备好，GPU 就只能干等。这就是 GPU 饥饿（GPU starvation），也是利用率下降最常见的原因之一。它同时还是最不声张的问题之一：没有崩溃、没有告警，作业只是比应有的速度慢一点，一直跑下去。

团队通常会注意到两种症状之一：GPU 利用率上下摆动而不稳定，或者训练运行耗时超出预期。例如在下面这次运行中，每张 GPU 上的 SM 活动持续起伏，始终达不到平台期：

![GPU SM 活动](https://images.ctfassets.net/xjan103pcp94/6efx8aEOfivG4fBTk2pWiR/d54c4eef90caf4f957228e1c63e2ae59/GPU_SM_Activity.png)

GPU SM 活动

这种模式是 GPU 饥饿的典型迹象。数据加载与训练并行进行：GPU 在训练一个批次的同时，下一批数据正在准备。当准备一个批次的时间超过训练它的时间时，训练步骤先结束，GPU 只能空闲等待下一批到达：

![训练步骤](https://images.ctfassets.net/xjan103pcp94/3HeLY6JhzRD8Xv2MB0z6pn/b88099eec738f33817d53eb3f7d8ff24/training_steps.png)

训练步骤

每个空闲间隙就是上图利用率曲线中的一个低谷。症状很容易发现，原因却不然。批次迟到可能有很多原因：上游数据管道慢、数据从其他节点经网络传输、训练 worker 上繁重的预处理（例如开销很大的 `collate_fn`），或者 host-to-device 拷贝。每种原因都有不同的修复方式，所以第一步是找出哪个阶段是瓶颈。

本文余下部分将介绍用于此目的的工具：

- **开源 Ray 中的数据摄取指标：**Ray Train 和 Ray Data 如何为数据加载的每个阶段计时，以及如何阅读 Grafana 图表，判断训练是否在数据上停滞、是哪个阶段的问题、需要改什么。
- **Anyscale 上的数据摄取可观测性：**同样的图表，无需任何配置，另外 Ray Train 仪表板上还有一个实时数据摄取面板，汇总每个正在运行的数据集的摄取健康状况。KubeRay Connect 把这两者带到你自己管理的 KubeRay 集群。

## Link开源 Ray 中的数据摄取指标

从 Ray 2.58 开始，Ray Train 和 Ray Data 会记录每个批次在数据加载各个阶段所花的时间，让你看到是哪个阶段拖慢了训练。如果你的 Ray Train 代码已经从 Ray Data 读取数据，则无需改动任何代码。

典型设置如下。driver 定义一个 Ray Dataset（这里是读取自 S3 的 Parquet 文件），并把它传给 trainer。Ray Train 为八个训练 worker 各自分配数据集的一个分片。每个 worker 用 `iter_torch_batches` 读取自己的分片，该调用会应用你的 `collate_fn`，并以 PyTorch tensor 的形式返回每批 64 行：
```
import ray
import ray.train
from ray.train import ScalingConfig
from ray.train.torch import TorchTrainer

train_ds = ray.data.read_parquet("s3://my-bucket/train/")

def train_func():
    shard = ray.train.get_dataset_shard("train")
    for batch in shard.iter_torch_batches(batch_size=64, collate_fn=my_collate):
        ...  # your training step

trainer = TorchTrainer(
    train_func,
    datasets={"train": train_ds},
    scaling_config=ScalingConfig(num_workers=8, use_gpu=True),
)
trainer.fit()
```

所有数据加载都发生在那一次 `iter_torch_batches` 调用里。与 `iter_batches`、`iter_rows`、`to_tf` 等所有其他 Ray Data 迭代器一样，它让每个批次走完同一条流水线，再交给你的训练循环。

在这次调用内部，每个批次从 Ray Data 流水线到你的 GPU 要经过六个阶段。其中任何一个都可能成为瓶颈：

| **阶段** | **衡量内容** |
| --- | --- |
| 生产等待 | 等待上游 Ray Data 流水线产出下一个 block |
| 数据传输 | 把 block 取到训练 worker，包括从其他节点的 object store 取 |
| 组批 | 切分并把 block 组合成批次，包括任何本地 shuffle buffer |
| 格式转换 | 把每个批次转换为所请求的格式，例如 NumPy 或 pandas |
| Collate | 在训练 worker 上执行你自己的逐批预处理，例如对文本分词或把序列补齐到统一长度，通过 `collate_fn` 传入 |
| 收尾 | 在 `iter_torch_batches` 中把批次拷贝到 GPU（host-to-device 传输） |

这些阶段并不是在训练线程上依次执行的。相反，一个后台线程池会并发执行它们，在你运行训练步骤的同时准备下一个批次。只要下一批能在训练步骤结束前准备好，这些工作就完全被隐藏，不占用任何实际耗时。当下一批没能及时准备好，训练循环就会等待，GPU 随之空闲。这段等待就是「暴露的数据加载时间」（exposed data loading time）。Ray 会在每个训练 worker 上记录它，以及各阶段所花的时间。

在开源 Ray 中，只要你为集群搭好 Prometheus 和 Grafana，这些指标就会出现在 Grafana 中 Train Dashboard 的 Data Ingestion 区域。下面的图表依次回答三个问题，示例来自一次因开销很大的 `collate_fn` 而停滞的运行：

- **训练是否在数据上停滞？最大暴露数据加载时间**显示最慢 rank 上训练循环为每个批次等待多久。若该值为 0，说明数据加载跟得上，调优流水线不会有帮助。若不为 0，这段时间就是每一步上的 GPU 空闲时间。
![最大暴露数据加载时间](https://images.ctfassets.net/xjan103pcp94/65VRgaMmjzZAXQSM0M4ZvI/f8fc9c56fcb80754a243bc9120a7c922/Max_Exposed_Data_Loading_Time.png)最大暴露数据加载时间
- **是哪个阶段造成的？各阶段数据加载耗时占比**显示各阶段在数据加载时间中的份额，统计范围覆盖所有 rank。生产等待占比大，说明上游 Ray Data 流水线产出数据的速度不够快。其他任何阶段占比大，则说明问题出在训练 worker 自身的处理上。
![各阶段数据加载耗时占比](https://images.ctfassets.net/xjan103pcp94/6MxxlEPDpHt4S3KjISIsTa/6ad4c0422cfb4f022cc2f00f4b436756/Percentage_Data_Loading_Breakdown_by_Stage.png)各阶段数据加载耗时占比
- **是每个 rank 都这样，还是只有某一个？**每个阶段都有自己的图表，并按 rank 拆分。如果某个 rank 明显高于其他 rank，它就是掉队者（straggler）；而由于各 rank 在每一步都会同步，单个慢 rank 就能拖住整个运行。
![按 rank 划分的生产等待时间](https://images.ctfassets.net/xjan103pcp94/hm30tpbpea97dTcf8F0tQ/5a709f470f52229f8f1239ae6074de57/Production_wait_time_by_rank.png)按 rank 划分的生产等待时间

还有两张吞吐图补全视图。**按 rank 的数据摄取吞吐**显示每个 rank 每秒消费的行数，**数据生产吞吐**显示 Ray Data 流水线每秒向训练交付的行数。两者合起来呈现健康运行的稳态速率，于是跨 rank 的下降与不均衡就会凸显出来。

![按 rank 的数据摄取吞吐与数据生产吞吐](https://images.ctfassets.net/xjan103pcp94/48JKCQlR1RbRXrO6TBZMHe/7a3d17850cb65bc2ae74f2751144bd08/Data_Ingest_Throughput_by_Rank___Data_Production_Throughput.png)

按 rank 的数据摄取吞吐与数据生产吞吐

知道是哪个阶段的问题，问题才变得可操作，因为每个阶段都指向具体的检查或修改项：

| **瓶颈** | **可以尝试** |
| --- | --- |
| 生产等待 | 在 Ray Data 仪表板中查看上游流水线里最慢的算子并调整其配置。你也可以增加只含 CPU 的节点，让 Ray Data 横向扩展预处理；如果数据集放得下，可以用 `materialize()` 把预处理后的数据集缓存到内存中。 |
| 数据传输 | 增大 `prefetch_batches`，让 block 在训练步骤之前就开始传输。取值越大，内存中保留的批次越多，因此要留意训练节点上的内存使用。 |
| 组批 | 如果你使用了 `local_shuffle_buffer_size`，请调小它，或改在上游做 shuffle，例如用 `map_batches` 做 shuffle，或在读取时打乱文件顺序。 |
| 格式转换 | 增大 `prefetch_batches`，让更多批次在训练步骤之前完成格式转换。 |
| Collate | 把繁重的预处理从 `collate_fn` 移到 Ray Data 流水线中，用 `map_batches` 完成；这样它会在整个集群上横向扩展，而不是在训练 worker 上运行。对于较轻的 collate 工作，增大 `prefetch_batches` 也有帮助，因为它能提前准备更多批次。 |
| 单个掉队 rank | 检查该 rank 所在节点有什么不同。常见原因包括 Ray Data 任务与训练 worker 争抢 CPU 或内存，以及需要反复从远端节点拉取的 block。如果 Ray Data 任务在争抢资源，可以用 `label_selector` 把数据集固定到只含 CPU 的节点上，让它们不落在训练节点。 |

## LinkAnyscale 上的数据摄取可观测性

在 Anyscale 上，无需任何配置就能得到上述全部 Grafana 图表。Anyscale 会为每次训练运行收集指标，并在 Ray Train 仪表板上展示这些图表，因此你不需要自己托管 Prometheus 或 Grafana。

除了 Grafana 图表之外，Anyscale 上的 Ray Train 仪表板还包含一个实时数据摄取面板。你不必逐个翻阅十几个图表，而是通过一个实时视图掌握整个集群的数据摄取健康状况。下面这段加速录屏展示的是它在一个因 collate 而停滞的运行上的表现：

![实时数据摄取健康状况](https://images.ctfassets.net/xjan103pcp94/41aR4DzOauQ4hlZnkLZACd/d50db1f3ad178f82bdee37b75d318f5c/Live_data_ingestion_health.gif)

实时数据摄取健康状况

对于当前正在执行的每个 Ray Data 数据集，该面板会显示以下内容。逐批指标针对你选定的 rank；录屏中展示的是最慢的 rank。

- **摄取进度：**训练在数据集上推进到何处，以已摄取行数占总行数的形式表示。
- **吞吐：**上游数据流水线每秒产出的行数，以及训练总共摄取的行数。
- **暴露的数据加载停滞：**训练循环为每个批次等待数据的时间。
- **训练计算时间：**每个批次的训练步骤耗时。
- **批次周期：**每个批次的总耗时，拆分为训练计算与暴露的停滞。
- **阶段细分：**每个批次在六个数据加载阶段中各花多少时间，让瓶颈一目了然。录屏中，collate 几乎占满了全部时间，直接指向 `collate_fn`。
- **Grafana 链接：**一键跳转到完整的数据摄取图表，查看历史指标与更多细节。

本节介绍的所有内容都属于 Anyscale 平台内置的可观测性。如果你运行自己的 KubeRay 集群，[KubeRay Connect](https://docs.anyscale.com/kuberay-connect) 无需迁移工作负载就能把这一切带过去。

有了这些指标，GPU 利用率不稳就不再只能靠猜，而可以追溯到一个明确的瓶颈。修好那个阶段，GPU 就能持续有数据可算：利用率上升并保持稳定，同样的运行在同样的硬件上更早完成。

如需深入了解，请参阅 Ray 文档中的这些指南：

- [Debug data loading bottlenecks](https://docs.ray.io/en/master/train/user-guides/data-loading-preprocessing.html#debug-data-loading-bottlenecks) 完整介绍了逐层排查的方法，以及每种结果对应的修复方式。
- [How does Ray Data iterate over data?](https://docs.ray.io/en/master/data/internals.html#how-does-ray-data-iterate-over-data) 介绍了六个阶段背后的线程模型。

## Link总结

GPU 利用率不稳只会告诉你出了问题，却不告诉你问题是什么。从 Ray 2.58 开始，Ray Train 和 Ray Data 中的逐阶段数据加载指标填补了这一空白。它们会告诉你数据加载是否是拖住训练的原因，如果是，瓶颈又在哪里，从而让你知道下一步该查什么。在开源 Ray 中，这些指标会出现在 Grafana 的 Train Dashboard 里。在 Anyscale 上，无需配置就能得到同样的图表，外加一个实时数据摄取面板，为每个正在运行的数据集汇总情况。

## Link后续步骤

GPU 饥饿只是让生产训练难以调试的若干问题之一，Ray 团队正持续把可观测性构建进 Ray Train，以覆盖最常见的问题。以下是我们接下来的工作：

- **自动卡死检测与堆栈抓取。**Ray Train 将检测训练何时停止推进，并自动抓取每个 worker 的堆栈，让你无需复现卡死就能看到每个 worker 卡在哪里。
- **健康监控。**更全面的训练健康监控，包括硬件健康检查，以暴露那些拖慢甚至中断生产训练运行的问题。

如果你遇到这些工具未覆盖的数据摄取问题，或对我们接下来该做什么有想法，欢迎[在 GitHub 上提 issue](https://github.com/ray-project/ray/issues)。
