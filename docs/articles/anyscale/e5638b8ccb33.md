# Ray Serve 重大升级：在线推理延迟降低 88%、吞吐提升 11.1 倍

作者：Seiji Eicher、Abrar Sheikh、Alex Yang、Akshay Malik、Kourosh Hakhamaneshi 和 Spencer Peterson（Google）| 2026 年 3 月 24 日

## 引言

[Ray Serve](https://docs.ray.io/en/latest/serve/index.html) 让你能用 Python 轻松构建可扩展、可组合的 AI 应用，底层由 Ray Core 的 actor 管理与资源放置提供实力与性能。

Ray Serve 在 AI 应用（如 LLM 服务）的开发、迭代与部署上很受欢迎。但一些有延迟敏感要求的用户在规模下遇到了 Ray Serve 的性能问题。我们与 Google Kubernetes Engine（GKE）合作，定位了 Ray Serve 在需求增长时难以维持峰值性能的几个方面。

今天我们宣布 Ray Serve 框架的重大改进，让它性能更强，解锁新的延迟与吞吐 SLA。关键特性是：

- [HAProxy](https://www.haproxy.org/) ingress——一个高度优化、身经百战的 C 语言开源负载均衡器
- Ray Serve 副本之间的直接 gRPC 数据面通信

启用这些特性后，我们在推荐系统、规模化 LLM 推理等示例应用上取得了吞吐与延迟的改善。我们相信这是让 Ray Serve 成为在生产规模下开发、测试与部署 AI 应用的标准框架的关键改进。

*图（1）：启用优化的 Ray Serve 与当前默认设置的 Ray Serve 的相对性能增益。"RecSys" 与 "LLM" 结果见案例研究小节；"Echo Unary" 与 "Echo Streaming" 结果来自 Deep Dive 部分最后一张图，展示所有优化的叠加效应。被测 Ray Serve 应用在 unary 情形把两个 no-op deployment 串联，在 streaming 情形经两个 deployment 流式返回随机字节。*

*深度学习推荐系统（DLRM）流水线的架构图，使用 Ray Serve：客户端向 CPU ingress 副本发 HTTP 请求，ingress 攒批后转发给 GPU ranker deployment 做模型推理。*

两项优化都将自 Ray 2.55+ 提供，通过环境变量在集群初始化时启用。用法见 Ray Serve [性能调优](https://docs.ray.io/en/latest/serve/advanced-guides/performance.html)文档。

本文涵盖：

- 推荐系统与 LLM 推理用例的端到端结果
- 技术深潜与消融实验，拆解促成这些改进的每一项优化

## 案例研究：推荐系统

推荐系统是 Ray Serve [模型组合](https://docs.ray.io/en/latest/serve/model_composition.html)模式的天然场景：把异构计算组合为一个横跨 CPU 与 GPU 节点的单一应用。这正是 deployment 间开销层层累积的负载。

我们对一个深度学习推荐模型（DLRM）[流水线](https://github.com/anyscale/runtime-benchmarks/tree/main/serve-throughput)做了基准，包含两个组合 deployment。图（2）展示系统架构，由两部分组成：

- 一个 ingress deployment：接收 HTTP 请求，合成 32 个候选项的 batch，调用 ranker deployment。
- 一个 ranker deployment：最多攒 100 个并发请求（用 `@serve.batch`），运行神经网络（MLP + embedding 查找、点积、MLP）并返回分数。

*图（2）：作为 Ray Serve 应用的推荐系统流水线架构。客户端请求路由到 ingress deployment 副本并合成候选 batch；ingress 再把候选 batch 发给运行 167M 参数 DLRM 的 ranker deployment。*

*柱状图：Ray Serve 优化带来的性能增益。各负载吞吐最高提升 11.1 倍，P99 延迟依用例降低 75% 到 88%。*

为测量性能，我们扫描并发用户数，从客户端侧测量延迟与吞吐。如图（3），启用这些优化后，系统能在更低的延迟 SLA 下扩展到更高的最大 RPS。100 用户时，优化后吞吐已是基线的两倍多，P99 延迟低 25%。400 用户时差距进一步拉大——Ray Serve 默认 proxy 相比 HAProxy 率先饱和。

*图（3）：启用 HAProxy 与其他吞吐优化开关，可以为推荐系统用例打开新的 SLA 前沿——并发用户数决定了这类模型服务的经济性。*

*Ray Serve LLM 的 OpenAI 兼容服务架构图：客户端向 CPU 节点上的 OpenAI 风格 ingress 发送 chat completion 请求，ingress 转发给运行 vLLM 引擎做推理的 GPU LLM 服务器。*

## 案例研究：LLM 推理

[Ray Serve LLM](https://docs.ray.io/en/master/serve/llm/index.html) 是 Ray Serve + [vLLM](https://vllm.ai/) 针对在线高吞吐/低延迟 LLM 推理的优化实现。图（4）展示一个基本 Ray Serve LLM 流水线的架构，由两个 deployment 组成：

- `OpenAiIngress`：负责根据 model ID 把 OpenAI 协议映射到具体的模型 deployment
- `LLMServer` deployment：负责扩展 vLLM 引擎副本。

*图（4）：基本 Ray Serve LLM 应用的架构图。客户端请求先到达 OpenAiIngress deployment，按 model_id 映射到目标 LLMServer deployment；随后经 deployment handle 路由到目标 LLMServer deployment 中"负载最轻"的副本；最终请求被攒批进入异步 vLLM 引擎，token 流式返回客户端。*

*8 副本下的吞吐图：优化为 unary 带来最高 11.1 倍、streaming 带来 8.9 倍收益（相对基线）。*

**关于 Ray Serve LLM 架构的更多细节见[这里](https://docs.ray.io/en/master/serve/llm/architecture/overview.html)。**

我们分析近期 Ray Serve 优化的有效性，回答这个问题：

- 当我们扩展 vLLM 副本数时，单节点吞吐是否线性扩展？

### 扩展每节点副本数

实验方式：扫描单节点上服务 openai/gpt-oss-20b（TP1、每副本单块 H100）的 vLLM 副本数，每副本并发 256 用户。客户端负载为随机，输入序列长度（ISL）512 token，输出序列长度（OSL）128 token。使用默认 Ray Serve Proxy 时，往节点加更多副本收益递减——Python 进程先饱和了。而借助 HAProxy 更高的吞吐能力，如图（5）所示吞吐线性扩展，默认 proxy 则停在平台期。

*图（5）：借助 Ray Serve 的新优化，我们可以水平扩展 LLM 推理，在规模下获得更高单节点吞吐。没有 ingress 与 gRPC 的优化，扩展是次线性的。*

*单事件循环优化的图：优化配置在 unary 与 streaming 下吞吐比默认高约 1.2 倍。*

## 深潜

以下小节更详细地说明每项优化对 Ray Serve 性能的贡献。

### 基准测试设置

这些基准对一个 no-op 的 "echo" 应用做 unary 与 streaming 测试：deployment 只是把预定负载发送或流式返回给客户端。

这里 "unary" 指一次 RPC 调用以一个请求消息为输入、返回单个响应消息；"streaming" 指 gRPC 的"服务端流式"——一个请求产生多个响应消息。unary 与 streaming 实验中，Ray Serve 应用都由两个串联 deployment 组成：一个 ingress deployment 与一个子 deployment。

当客户端请求到达 ingress deployment 时，ingress 对子 deployment 调用一个远程函数。unary 实验中，子 deployment 的远程函数返回空字符串，ingress 给客户端返回空 HTTP 响应；streaming 实验中，子 deployment 返回 `ChatCompletionResponse` 的 SSE chunk。

### 优化 Deployment 间通信

默认情况下，一个 deployment 通过 handle 调用另一个 deployment 时，Ray Serve 会把它派发为 Ray Core actor task。小负载（<100KB）的参数被序列化后直接放进 `PushTaskRequest` [消息](https://github.com/ray-project/ray/blob/a20d303c51f92f6c4d42bc47b6a951a036c97cc7/src/ray/protobuf/common.proto#L761)；更大的负载则序列化后存入对象存储（Ray 的共享内存存储），按引用传递。图（6）展示了 Ray Serve 中 deployment 负载默认走的通路。

*图（6）：Ray Serve 默认使用标准 Actor Task 机制（包括 PushTaskRequest）完成 RPC。此时小负载（<100KB）经 PushTaskRequest 传递，更大的负载经 Ray 对象存储传输。*

*启用 HAProxy ingress 的 Ray Serve 架构图：请求经负载均衡路由到 CPU ingress 副本，再到 GPU 模型 deployment。*

Ray Core 数据面支持 ObjectRef、引用计数与 lineage 重建，这对大对象和复杂编排模式很有用。但遵循最小权力原则，Ray Serve 现在支持 deployment 间通信走直接点对点 gRPC，绕过 Ray Core。启用 interdeployment gRPC 后，Ray Serve 在副本 actor 之间建立直接 gRPC 通道，如图（7）。参数用 protobuf 序列化后点对点经网络发送。性能收益见图（8）：在相同延迟 SLA 下，unary 情形吞吐提升 1.5 倍，streaming 情形提升 2.4 倍。

*图（7）：有了 interdeployment gRPC，Ray Serve 副本把 RPC 数据直接发给彼此的 gRPC 服务器。这一优化可降低 deployment 副本间通信开销。*

*Ray Serve 中 gRPC 通信的示意图：ingress 用 gRPC 客户端直接调用 ranker 服务，绕过 Ray Core 消息。*

采用 gRPC 的 deployment 间通信后，Ray Serve 主要用 Ray Core 做 actor 放置、集群编排、指标传播与健康检查。而用户请求流量直接在 deployment 之间走 gRPC，不经过 Ray Core。

环境变量 `RAY_SERVE_USE_GRPC_BY_DEFAULT` 控制是否默认使用 gRPC。此外 Ray Serve 暴露 handle 选项，让开发者对每个 deployment handle 的传输方式有细粒度控制。例如：在以大负载为主的 application 中，开发者可以默认使用 Ray Core 传输，只对小负载的 deployment 选用 gRPC。详见[性能调优](https://docs.ray.io/en/latest/serve/advanced-guides/performance.html)文档。

*图（8）：unary 与 streaming 微基准性能对比 `RAY_SERVE_USE_GRPC_BY_DEFAULT` 在两个串联、各单副本 deployment 上的效果。no-op 负载的 unary 情形吞吐最高提升 1.5 倍，50 个 SSE chunk 的 streaming 情形最高 2.4 倍。*

*DLRM 服务对比图：优化后的 Ray Serve 把吞吐提高到约 1500 RPS，延迟低于默认配置。*

### 优化 Ingress 开销

内建的 Ray Serve Proxy 是一个基于 Python 的异步服务器（基于 Uvicorn 与 Starlette），接受客户端连接、通过 handle.remote() 把请求路由到合适的 deployment，再把响应流式返回。高并发下它成为瓶颈：抬高每请求延迟、封顶吞吐——无论健康副本总数多少。图（9）展示了禁用 HAProxy 时 Ray Serve proxy 层的架构。

*图（9）：Ray Serve Proxy 在 8000 端口终结 HTTP 连接，再通过 Ray 远程调用把请求内容传给 Ray Serve 应用中的 ingress deployment。*

*gRPC 性能对比图：启用 gRPC 后在相近延迟下吞吐更高，unary 约 1.5 倍、streaming 约 2.4 倍。*

*图（10）：把 Ray Serve Proxy 换成 HAProxy 后的 Ray Serve 框架架构图。Ingress deployment 内部各自持有位于 :30000 区间的 HTTP 服务器端口，HAProxy 把进来的请求直接路由到它们。*

*HAProxy 启用与关闭的对比图：HAProxy 改善吞吐与延迟，unary 最高 2.0 倍、streaming 最高 1.4 倍。*

启用 HAProxy 后（如图（10）），每个 ingress deployment 副本内部启动一个 HTTP 服务器。`ServeController` 会把这些服务器通知给 HAProxy，HAProxy 便可直接把请求路由到它们。HAProxy 是 C 语言的 HTTP 反向代理，常见于大规模生产系统。性能收益见图（11）：相同延迟 SLA 下，unary 情形吞吐提升 2 倍，streaming 提升 1.4 倍。

*图（11）：unary 与 streaming 微基准对比 `RAY_SERVE_ENABLE_HA_PROXY` 在两个串联、各单副本 deployment 上的效果。no-op 负载的 unary 情形吞吐最高 2 倍，50 个 SSE chunk 的 streaming 情形最高 1.4 倍。*

*Ray Serve 经 Actor RPC 通信的示意图：客户端把 HTTP 请求发给 ingress 副本，ingress 用 Ray Core 调用 ranker 副本，数据经对象存储传递。*

### 单事件循环

默认情况下，Ray Serve 把用户代码与路由任务放在分离的事件循环上运行，以免阻塞主系统事件循环。这确保了用户代码里的阻塞操作不会影响主系统事件循环，但也引入了开销——对写得规范的异步用户代码会影响性能。

环境变量 `RAY_SERVE_RUN_USER_CODE_IN_SEPARATE_THREAD` 与 `RAY_SERVE_RUN_ROUTER_IN_SEPARATE_LOOP` 允许开发者关闭分离事件循环，避免额外的任务协调开销。图（12）展示了收益：相同延迟 SLA 下吞吐约提升 20%。

*图（12）：unary 与 streaming 微基准对比 `RAY_SERVE_RUN_USER_CODE_IN_SEPARATE_THREAD` 与 `RAY_SERVE_RUN_ROUTER_IN_SEPARATE_LOOP` 在两个串联、各单副本 deployment 上的效果。no-op 负载 unary 情形吞吐最高 1.2 倍，50 个 SSE chunk 的 streaming 情形最高 1.2 倍。*

*吞吐 vs 副本数折线图：优化后的 Ray Serve 在 8 副本时扩展到约 40k token/s，默认配置只到约 14k。*

## 其他请求路径优化

除 gRPC 与 HAProxy 两大架构工作之外，我们还落地了一批请求路径改进，削减 Python、网络与运行时编排中的每请求开销。合力之下，负载下的延迟与吞吐都取得可观收益。

### 指标工作移出关键路径

指标只有在足够廉价时才有用。我们在副本与路由器中对更新做缓存与批处理，降低请求路径的指标开销，让请求执行少花时间在 instrumentation、多花时间在用户代码上。这在高并发下尤其明显——否则同步的指标记录本身就成了可测量的税负。PR：[#49971](https://github.com/ray-project/ray/pull/49971)、[#55897](https://github.com/ray-project/ray/pull/55897)

### 通过缓冲与缓存请求上下文降低日志开销

Serve 现在会缓冲请求日志，并在热点日志路径复用缓存的上下文，削减每请求重复的格式化与 I/O。我们还修复了缓冲上下文的正确性问题，在获得批处理收益的同时保持每请求元数据准确。PR：[#54269](https://github.com/ray-project/ray/pull/54269)、[#57245](https://github.com/ray-project/ray/pull/57245)、[#55166](https://github.com/ray-project/ray/pull/55166)、[#56094](https://github.com/ray-project/ray/pull/56094)

### Ingress 路径中每请求更少的异步任务

一项具体优化是减少每请求创建的 asyncio 任务数。在优化后的 ingress 副本路径上，当断开处理被禁用且没有配置超时的时候，Serve 跳过额外的任务编排，直接 await 用户代码，而不是一律派生单独的 request/receive 任务。实践中，这削减了事件循环调度开销，靠避免热路径上不必要的任务生命周期工作提升吞吐。

### 面向 unary 请求流的 Unary gRPC

并非每个 gRPC 请求都需要流式机制。我们为支持拒绝的路径增加了 unary-unary 处理，在本质上是请求/响应的负载上避开流式编排成本。这降低了每请求开销，改善常见 unary RPC 模式的吞吐。

### FastAPI 依赖解析优化（self/注入实例路径）

一个高影响的修复是把 `get_current_servable_instance` 改为异步，让 FastAPI 可以直接 await，而不必把依赖解析卸载到线程池。这移除了该路径上每个请求不必要的线程池调度，显著改善 FastAPI ingress 负载的延迟与 RPS。PR：[#55457](https://github.com/ray-project/ray/pull/55457)

### 路由器数据结构优化

请求路由器更新为使用更高效的内存结构（包括面向 O(1) 查找的路径）与更低分配的流程，削减每请求路由开销——副本数与流量并行度越高越明显。PR：[#60139](https://github.com/ray-project/ray/pull/60139)

尚未默认启用的吞吐优化统一收在一个开关 `RAY_SERVE_THROUGHPUT_OPTIMIZED` 之下，代码见[这里](https://github.com/ray-project/ray/blob/2bd8fed85ee177446d5373150f123d732c3498a8/python/ray/serve/_private/constants.py#L767)。把它们全部与 HAProxy 一起启用的效果如图（12）所示。图（12）的测试应用同样是两个 deployment 的组合，但各自扩到 8 副本，以展示 Ray Serve 单节点吞吐能力的提升。

*图（12）：unary 与 streaming 微基准对比 `RAY_SERVE_OPTIMIZED_THROUGHPUT` 在前面各图 deployment 的放大版（扩副本）上的效果。no-op 负载 unary 情形吞吐最高 11.1 倍，50 个 SSE chunk 的 streaming 情形最高 8.9 倍。*

*默认 Ray Serve proxy 的示意图：客户端请求经 Python proxy，再经 actor RPC 到 CPU ingress 与 GPU 模型 deployment。*

## 结语

我们讨论了分布在不同层的若干新优化，显著提升 Ray Serve 应用的吞吐并降低延迟。最引人注目的是：启用 HAProxy ingress 与 interdeployment gRPC 后，一个两级 DLRM 流水线从 490 QPS 提升到 1,573 QPS，同时 P99 延迟降低 75%。对使用 Ray Serve LLM 的 LLM 推理，我们在节点内扩副本时保持每副本的线性吞吐。复现上述结果的代码全部在[这里](https://github.com/anyscale/serve-performance-blog)。

我们正朝着让 gRPC 与 HAProxy 成为所有 deployment 间通信默认方案的方向努力。设计细节与讨论见 [RFC](https://github.com/ray-project/ray/issues/61212)。
