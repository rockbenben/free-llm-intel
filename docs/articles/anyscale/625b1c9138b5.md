# Ray 聚焦：我们如何做到每周发布 Ray

作者：Sam Chan | 2024 年 6 月 25 日

## **引言**

新模型、新加速器、新技术推动的 AI 创新正以惊人的速度演进。为跟上节奏，Anyscale 的 Ray 团队近期改为每周发布，确保修复与增强能更快抵达不断壮大的 Ray 社区。

本文探讨这次转型中的挑战与成果。

## **变革的必要性**

在实施每周发布之前，Ray 遵循六周一轮的发布周期。三个主要痛点：

- **不稳定测试（flaky tests）：** Ray 的 CI（即合并前后测试）与发布测试常以难以复现的方式失败，给判定那些本应由这些测试捕捉的根本稳定性与可靠性问题引入了噪音。
- **发布负担沉重：** 发布频率低导致每次都要赶着合并 PR，造成压力并可能产生疏漏。
- **用户挫败感：** 用户要等下一个发布周期才能用上新功能或 bug 修复，或者依赖 nightly 构建。

为解决这些问题，团队下决心提高发布频率。

## **克服不稳定**

为此，团队首先要处理 Ray 代码库内部的 instability。包括：

- **整治测试失败：** 去年，Ray 团队每周面临约 50-70 个失败测试。其中很多是非确定性、不稳定的，需要一次彻底清理。
- **系统性更新：** 团队实施了基础性更新以减少新问题的引入，同时对既有测试失败进行了一次严格的彻底清理。
- **文化转变：** 转向每周发布节奏需要公司文化的转变——鼓励更频繁、可控的更新，而不是周期性的高压发布期。

*把每周发布的阻塞项压到 0 并维持住。*

## **结果与影响**

过去两个月，我们成功地向 Ray 社区交付了每周发布。

此外，转向每周发布还带来了：

- **稳定性增强：** Ray 团队修复了约 [350+ 个问题与不稳定测试](https://github.com/issues?q=is%3Aissue+archived%3Afalse+label%3Aray-test-bot+label%3Astability+is%3Aclosed)，使每次周发布的测试通过率显著可靠起来。

  一些重点改进领域：
  - 修复与主要云和加速器供应商集成点的测试（例如确保 Ray 在 AWS/GCP 上可靠启动，并支持 AMD 等替代加速器厂商）。
  - 确保大规模批量推理被测试覆盖且可靠，尤其是 GPU 加速场景。
  - 修复测试基础设施及 Ray Core 基础组件本身的代码，如对象引用计数、内存管理、autoscaler 与调度器。
  - 修复压测 Ray Data 大规模数据 shuffle 可靠性的测试。
  - 清理并修复 Windows 平台上的不稳定与失败测试。

  完整分析与已关闭 issue 见：[ray-test-bot-stability.csv](https://docs.google.com/spreadsheets/d/1w-3QkK07XI8q2baZ2-5dIj_Ow0NMPR1oQP5Er3_3g2c/edit#gid=0)

- **发布流程顺畅：** 每周发布已成例行公事，干扰极小。得益于改进的测试基础设施，团队能及早发现性能回退、最大限度减少延误。
- **生产力提升：** 压力降低与规律发布节奏营造了更健康的工作环境，让工程师专注于持续改进。

*发布间隔天数（我们现在稳定在约 7 天的周发布）。*

## **挑战与未来计划**

尽管收益明显，转向每周发布也带来一些挑战：

- **升级频繁：** 用户需要更频繁升级才能保持最新，这可能构成运维负担。对 Anyscale 托管 Ray 平台的用户，我们确保新版本经过测试、无缝集成，从而简化了这一过程。
- **API 稳定性：** 随着 Ray 走向成熟，团队专注于增强 API 稳定性与文档，让用户更容易适应变更。

为应对这些挑战，Ray 团队正在探索长期支持（LTS）版本的想法，为偏好更低更新频率的用户提供稳定基座，同时提供托管升级服务以实现平滑过渡。

向每周发布的转型是 Ray 与 Anyscale 的一个重要里程碑，彰显我们对规模化稳定与可靠的承诺，同时保持与行业分布式机器学习前沿并驾齐驱的增强与创新节奏。

随着 Ray 演进，我们对健壮测试、精简流程与以用户为中心的功能的坚持，将保持其在分布式计算技术领域的领先地位。
