# Scaling the Science of Robot Decisions with Ray on Anyscale

作者 [Ian Jordan, PhD](https://www.anyscale.com/blog?author=ian-jordan-phd) | 2026 年 10 月 9 日

在 Ray 上对机器人基础模型做闭环评测，已经是一个被解决的模式：一个 policy 服务，把仿真器作为 Ray task，一个脚本跑一百次 rollout。我们已经在 [Scale Robot Policy Evaluation with Ray](https://www.anyscale.com/blog/distributed-sim-eval-robotics-ray-anyscale) 里写过它。这篇讲的是——当评测便宜到这个份上，你还能从中知道什么。

我们取一个冻结的真实数据 vision-language-action（VLA）策略——LeRobot 的 pi0.5 叠衣服 checkpoint——把它跑进它所训练的那台机器人的物理孪生体里。然后把这个孪生体当作测量仪器使用：做快速、受控的实验，每次只改动一处，测量冻结策略的决策如何变化。这同时回答两个问题。微调后的策略到底在看什么？而一个仿真器、或一条数据采集／合成数据管线，必须把哪些东西做对，才能让这个策略继续工作？

为了演示，这里的机制很简单但有效。我们取策略在孪生体里看到的一个观测，把它三张图像中的一张换成真实任务同一阶段的真实帧，其余全部保持一致，然后数一数策略在计划什么。这把策略的「抬起还是松开」决策定位到了腕部相机画面里夹爪尖端那几百个像素上。它告诉我们孪生体的抓取得长成什么样。它还让我们第一次看到冻结的 VLA 在仿真中零样本叠折一件布质 T 恤——没有真实像素，也没有微调。整项研究是一个 Ray 程序，我们的 notebook 在四张 L4 上六分钟就能复现它的核心。

## **问题**

你有一个在真实装置上能工作的 VLA。你把相机挪个位置，或者把它放进仿真器，它就不工作了，而没人能告诉你哪些像素重要。用更多数据微调是通常的答案，而且是个盲目的答案——因为你根本不知道该采什么数据。像 LIBERO-Plus 这样的 benchmark 展示了失效（视角或初始状态的变化让成功率从 95% 掉到 30% 以下），但没给出原因（[Fu et al., 2025](https://arxiv.org/abs/2510.13626)）。

过去十八个月里，这个领域的做法是用两种方式之一打开这个黑盒。激活层面的工作给你一个 2,000 维空间里的方向；仿真器里的行为层面工作给你一个成功率。两者都没法让硬件工程师决定相机该装在哪里，也没回答仿真器工程师最先问的那个问题：「场景里必须改什么，一个冻结的策略才能继续干它的活儿？」这需要一个受控实验——一个用同一状态、同一批图像、并且能只改一处然后分析策略动作的实验。真实机器人给不了你这些，因为没有两次复位是一样的。能做到的是一个物理孪生体。至于「决策在网络里的哪个位置」是另一个问题，那是孪生体存在之后的下一步（见延伸阅读中的引用）。

视频孪生体和 splat 孪生体无法为布料提供这种反事实，因为「捏合」没有物理。而且，也没有任何东西告诉你当手抬起时，两瓣夹爪之间那块布会怎么样。而叠衣服正是刚体评测失效的地方：这件衬衫有 25,000 个自由度，每一次抓取都会改变它的形状。所以我们从数据集的帧出发，为这个策略自己的装置建了一个物理孪生体。

## **设置：一个冻结的 pi0.5 与它自己装置的孪生体**

策略是 [lerobot/folding_latest](https://huggingface.co/lerobot/folding_latest)，由 LeRobot 在真实双臂 OpenArm 叠 T 恤数据上微调的 pi0.5。它是一个 30 亿参数的 PaliGemma VLM，加一个 3 亿参数的 flow-matching action expert。它看到三路相机（一路 640 x 480 的头戴相机和两路 1280 x 720 的腕部相机）、一个 16 维关节状态，以及指令 *"Fold the T-shirt properly"*。我们从不修改或微调它。每一次调用都是公开的 bf16 checkpoint。

孪生体是 Isaac Lab 3.0 配 Newton 物理后端。两条 OpenArm 从臂是取自厂商 URDF 的 MJWarp 关节体。LeRobot 打印的夹爪和外壳来自他们公开的零件。数据集的三路相机是通过把它们的重投影与帧内手读的像素位置做拟合而定位的。桌子是他们的，衬衫是一个 25,610 节点的 Newton VBD 布料。策略以 30 Hz 闭环运行在孪生体渲染出的图像和关节状态上。任何一次 rollout 消费的观测里，都不会被放进一个真实像素。

有一个替身做法，而且它很重要：抓取。对这个厚度的仿真布料做摩擦捏合是夹不住的，所有公开发表的仿真叠衣结果都用和我们一样的方式绕开它。夹爪闭合时，两瓣之间的布料节点被绑定到夹爪坐标系上并被带着走。我们多加了一个*捏合折叠*：横躺在张开夹爪上的布会被折进两瓣之间的一团里，因为那就是腕部相机必须看到的东西（后面会讲为什么）。被钉住的抓取永远夹得住，所以这个孪生体验证的是伸手、折叠策略与视觉运动控制，而不是夹持鲁棒性。这句话就写在 notebook 里引入这个替身的地方。

## **架构：一个策略服务、三个孪生体、一个 notebook**

下面所有内容都在一个集群上的一个 notebook 里。一个 GPU 上的策略服务，三个 GPU 上的三个孪生体，探针则作为同一个服务的并发客户端。架构就是 [Scale Robot Policy Evaluation with Ray](https://www.anyscale.com/blog/distributed-sim-eval-robotics-ray-anyscale) 里那套，它更详细地解释了为什么仿真器和策略不能共享一个进程或一张 GPU。这里简要复述：

![A policy service on one GPU, three twins across three GPUs, and the probes as concurrent clients of the same service.](https://images.ctfassets.net/xjan103pcp94/5n9ZHd5aDjx6WG5dhl1UFm/b079bb4131aff76d54cce383f47a6b96/A_policy_service_on_one_GPU__three_twins_across_three_GPUs__and_the_probes_as_concurrent_clients_of_the_same_service.png)

一个 GPU 上的策略服务、三个 GPU 上的三个孪生体，探针作为同一个服务的并发客户端。

**策略即服务。** 这里的 replica 对每个请求返回完整的 30 步 action chunk，并且不保存任何按客户端的状态：

```
@serve.deployment(ray_actor_options={"num_gpus": 1}, max_ongoing_requests=64)
@serve.ingress(app)
class PI05PolicyServer:
    def __init__(self):
        self.policy = Pi05Twin(ckpt)                     # lerobot's PI05Policy, bf16, frozen

    @serve.batch(max_batch_size=8, batch_wait_timeout_s=0.05)
    async def _batched(self, obs_list):                  # concurrent requests -> one forward pass
        ...
        return [chunk_i for chunk_i in chunks]           # each (30, 16): absolute joint targets, degrees

    @app.post("/predict")
    async def predict(self, request):                    # npz in: base, left_wrist, right_wrist, state16, task
        return await self._batched(decode(await request.body()))
```

无状态的 chunk 正是许多客户端能共享一个 replica 的原因。每个客户端自己执行部署节奏（取 chunk 的第 3 到 18 步执行，然后重新查询——与进程内循环做的完全一致）。并发调用——无论来自三个仿真器，还是来自一次发出八十调的探针——都会被批进一次前向。若没有共享的 replica，三个仿真器就得各自在一张 GPU 上加载 30 亿参数，而一张 24 GB 的 L4 装不下 Isaac Sim、布料解算器和策略三者。

**孪生体作为 task。** 每个孪生体是一个持有一张 GPU 的 Ray task。孪生体本身以子进程运行，因为 Isaac Sim 的 Kit 事件循环不能待在 Ray worker 里：

```
@ray.remote(num_gpus=1, num_cpus=4, max_retries=0)
def run_twin(name, policy_url, start_from, seconds):
    cmd = [sys.executable, "-u", "twin/rollout.py", "--policy-url", policy_url,
           "--start-from", start_from, "--seconds", str(seconds), "--out", f"{RUNS}/{name}"]
    return subprocess.run(cmd, ...)                      # the repo is already here: runtime_env working_dir

refs = [run_twin.remote(hold, POLICY_URL, f"data/start_states/{hold}.npz", 12) for hold in HOLDS]
```

`ray.init(runtime_env={"working_dir": "."})` 会把整个仓库送到每个 worker，内置的孪生体、它的资产和保存的夹持快照都包含在内。`max_retries=0` 是刻意的：一个被静默重试的孪生体会从头再跑，同时覆盖它自己的帧。

**保存的夹持快照。** 一次孪生体启动要一到三分钟（Kit、USD 场景、布料构建、RTX 预热）。一件沉降稳定的衬衫还要两百个仿真步，而这件布料的一个控制步在 A100 上大约要一秒物理时间。因此 notebook 里的孪生体从保存的夹持快照起步，布料的节点位置、臂状态、被钉住的节点和夹爪迟滞都被精确还原。

这些快照的入选条件是双手都被钉住——也就是替身机制已把布料节点绑到了每个夹爪上——并且腕部视角看上去是对的。后来补上一个更严的检验：夹爪闭合时，夹爪是不是真的在布料上方。在随附的状态里只有左侧通过。右手的钉合把几厘米之外的节点绑了上来，替身允许这么做，真夹爪不行。这就是钉合替身的已知失效，也正是这些片段用来验证还原路径和共享 replica、而不能作为双手抓取证据的原因。

```
python twin/rollout.py --policy-url http://head:8000 --seconds 60 --seed 9 --save-state-at 600,750,...,1800
python tools/pick_holds.py runs/holds_fwsafe_s9 --out holds_sheet.png        # the numbers, and the frames to look at
```

同一个脚本也能重放一段记录下来的动作序列（`--replay-from actions.npy`）。这就是这项研究的物理变体循环：一次孪生体改动，用八分钟对着录制的轨迹重测，而不是三十分钟的策略 rollout。重放并不是这些夹持快照的产生方式。面对 25,000 节点的布料，开环重放几秒内就会偏离闭环运行，第一次尝试就出现了被钉节点落在夹爪后方 17 到 46 厘米的情况，被「夹爪必须在布上」这条规则拒掉。

**探针。** 在一个被保存的时刻，我们手上有策略在孪生体里看到的精确输入。我们把其中一张图像换成真实任务同一阶段（episode 0 的 17.5 到 20 秒，双手都在夹持）的真实帧，状态和另外两张图像保持原样，然后多次查询服务。说清楚这里「真实」意味着什么：真实帧与孪生体那一刻的姿态、衬衫形状并不相同。相同的是那一刻之外的其他一切，所以这次替换就是两种条件之间唯一的差别，而计数吸收了采样器的随机性。这个不匹配是一项局限，也正是下一步把替换收窄到夹爪尖端那几百个像素的原因：

```
conditions = {"ALL_SIM":     dict(base=sim.base, left_wrist=sim.lw, right_wrist=sim.rw),
              "base=real":   dict(base=real.base, left_wrist=sim.lw, right_wrist=sim.rw),
              "wrists=real": dict(base=sim.base, left_wrist=real.lw, right_wrist=real.rw),
              "lw=real":     dict(base=sim.base, left_wrist=real.lw, right_wrist=sim.rw),
              "rw=real":     dict(base=sim.base, left_wrist=sim.lw, right_wrist=real.rw)}
rows = probe_grid(client, moments, conditions, repeats=4)     # 4 moments x 5 conditions x 4 = 80 calls, concurrent
```

每个返回的 chunk 由两个计数打分。*松开*指 chunk 中任意位置夹爪被命令到 -20 度以下。*计划中的抬升*指 chunk 结束时某只手的正向运动学高度比桌面至少高 20 厘米、且没有松开。第二条说的是策略的计划——它命令手抬起、两只夹爪都保持闭合——而不是布料的情况。一个 chunk 无法告诉你衬衫会不会真的被提起来。只有下面的闭环孪生体能量到那个。用计数，绝不用单次调用。pi0.5 的一个 chunk 是一次 flow-matching 采样，而 notebook 的第一个实验对同一时刻问四次，画出四条不同的手轨迹，有时相差几十厘米。这项研究的规矩是：任何关于策略的结论落笔之前，每个条件至少要有 12 个样本。

## **结果：策略读的是夹爪尖端**

这是折叠构型下四个夹持快照上的网格（双手都被钉住，带上面关于右手的说明），每个条件 16 个样本，取自 notebook 为本文跑的那次：

```
condition           n  plans lift  release  rel L  rel R
ALL_SIM            16           0       14     11     13
base=real          16           0       16      8     16
wrists=real        16          13        0      0      0
lw=real            16           0       16      0     16
rw=real            16           0       16     16      7
```

![What the policy was shown: the twin's wrist views (as the policy saw them) and the real frames swapped in for them.](https://images.ctfassets.net/xjan103pcp94/3ynZIEVNYMwNQhXM7tuyUN/2ec7d761386679e03f7feb86fd2f2d95/What_the_policy_was_shown_the_twin-s_wrist_views__as_the_policy_saw_them__and_the_real_frames_swapped_in_for_them.png)

策略所看到的输入：孪生体的腕部视角（策略所见的那样），以及换进它们位置的真实帧。

逐行读。用孪生体自己的图像时，策略会松手（16 次里 14 次松开，0 次计划抬升）。换进真实的头戴相机帧，什么都没变。把两路真实腕部帧都换进来，得到 16 次里 13 次计划抬升、零次松开。只换真实的*左*腕帧，左手就再也不松（16 次里 0 次），右手照旧松（16 次里 16 次）。只换右腕，模式镜像（左手 16 次里 16 次，右手 16 次里 7 次）。**左手自己的视野决定左手的松开。** 研究中在更多时刻上的数字与此一致：用孪生体腕部图像时，计划抬升 16 次里 0 次、松开 16 次里 8 到 16 次；用真实腕部图像时，计划抬升 16 次里 11 到 16 次、松开 0 到 3 次。真实帧与孪生体帧的差别不止那一团，所以这张网格只把决策定位到腕部相机。下一个实验才分离出画面里的具体是什么。

腕部画面里的什么？夹持时刻的真实帧显示，两瓣夹爪尖端之间有一团被捏合的*布料团*。孪生体的帧显示的是一条薄薄的窄边。拿真实帧、只把布团去掉（`gap`），计划抬升就消失了（notebook 那次 16 次里 0 次，研究中 8 次里 0 次）。反过来，只在孪生体帧里保留真实夹爪尖端那一小块补丁（`realjaw`，几百个像素），它就会像完整真实帧那样计划抬升（16 次里 11 次对 16 次里 12 次；研究中 8 次里 6 次对 8 次里 5 次）。三十种渲染变体（光照、材质、相机、模糊、对比度）让编码器距离只动了不到 0.03（0.167 到 0.198，而真实帧是 0.073）；而我们按抬升计数打分的 18 种图像级变体（色彩、锐度、镜头畸变、取景、夹爪轮廓、画上去的缝隙和布团、布束形状）每次 12 个样本里计划 0 到 3 次抬升，未编辑的孪生体帧是 0 到 1 次。被灰化、压暗、模糊或压平的真实布团仍然在 12 个样本里计划 9 到 12 次。线索是几何，不是纹理。决策住在夹爪尖端那块补丁里，按手分别如此，而线索就是两瓣之间的那一团布。

策略自己的编码器确定性地印证了这一点。把夹爪尖端的裁剪图用 pi0.5 内部的 SigLIP 视觉塔嵌入、做均值池化，再取到真实夹持帧的余弦距离。研究中的真实夹持帧落在 0.073，其他真实时刻在 0.09 到 0.15，我们的渲染在 0.15 到 0.22。notebook 里的左腕裁剪读作：孪生体 0.166，真实 0.086，夹爪尖端补丁 0.089，去掉布团 0.166。在 65 个腕部图像变体（每个至少 8 个样本）上，这个距离对各变体抬升率的排序 Spearman 相关为 -0.82。一个能预测随机计数的确定性数字，正是把「扫描」变成「搜索」的东西。notebook 通过同一个 replica 的 `/embed` 路由算出它。

从这张网格可以带走两件事。一个几何线索的决定力超过了三十个渲染变体，所以在为「逼真」付费之前先测测策略在读什么。而且策略自己的编码器给出一个能排序变体的确定性距离，于是搜索可以在不跑 rollout 的情况下进行。

## **从发现到折叠：孪生体改了什么**

这个发现同时是一条硬件事实和一条孪生体事实。夹爪处的捏合折叠就是因为它而存在：横躺在张开夹爪上的布料在夹爪闭合时被折进两瓣之间的一团，于是腕部相机看到的就是真实相机看到的东西。另外两处改动来自「看」而不是「探测」。布料不能自己动。一件仿真衬衫可以在附近没有机械臂的情况下抖动。它的 25,000 个节点挂在刚性弹簧上，由一个迭代次数封顶的迭代解算器推进，每个子步都会留下残差误差。弹簧足够硬时，这个残差不衰减，而是在网格自身的共振频率上振铃；消除它靠的是数值阻尼和 rest-sleep 钩子。有一组刚度改动让袖子和领口以 12 到 15 mm/s 波动，就恰好因为这个理由被拒。随附配置的节点速度中位数是 0.0 mm/s，而且每次运行都记录它，所以这条说法是量出来的，不是看出来的。桌子的几何与布局来自他们的影像，而不是来自工作台照片。

在这个配置下，一个策略、一种孪生体、42 个种子（120 或 150 秒），41 个有效。41 次运行里（除机械臂穿过桌子的那次——这是每次运行都要过的闸门，唯一那次失败落在 2 个「出桌」种子里）双手都被钉住、完成压平与对齐。21 次出现叠折时刻（投影面积降到平铺衬衫的 0.70 或以下）。10 次在结束时仍保持折叠。2 次衬衫被拖下桌子近侧边缘。notebook 用随附的每次运行汇总重算这张表，并把判定规则印在旁边。只看指标的规则给出 22、11 和 2，而研究中靠人眼判断把一次最终状态算作揉皱。最好的一次在 100 到 119 秒之间把衬衫对折，而失效模式也得到了同等的展示篇幅。

## **回报：一次多日的研究就是一个 Ray 程序**

这是本文的骨架，所以把账算清楚。支撑这些数字的那次多日研究，就是一个程序跑在一台 8 GPU 节点上。每一次 rollout、每一次替换扫描、每一个指标，都是从同一个 shell 用 `working_dir` 打包发出的 Ray task。这让我们一夜之间跑完 42 个种子和几十种孪生体变体，而重放动作序列把物理变体循环从三十分钟压到八分钟。notebook 就是同样这三块原语的教学尺寸版本：一个 Ray Serve replica 在一张 L4 上装下策略；三个 Isaac Lab 孪生体在另外三张 L4 上作为 task 运行，通过 HTTP 查询它；替换探针是同一个 replica 的并发客户端；每个阶段一结束就释放对应的 GPU。评测那篇跑的是一个策略的一百次 rollout。这里同一类服务回答几百条反事实查询，并按需拉起孪生体，在开发机上同样六分钟。

实测自我们的示例 notebook 代码（8 x A100 开发机，预算按 4 x L4 也能跑）：

```
cell                                             wall s
3 serve.run (returns at once)                       4.4     (deployment thread; the replica loads for 156 s in the background)
4 fan out the twins (returns at once)               0.0     (three Kit boots start on three GPUs)
5 wait for the replica + the stochastic chunk     162.0     (the wait: the twins boot and restore their holds meanwhile)
6 substitution probe (80 calls)                    13.8     (21 batches of ~4 on the replica, 667 ms per batch)
7 bunch vs sliver + encoder distance               11.3
8 collect the live rollouts (3 twins, 5 s each)   157.8     (335 s after fan-out; 0.9 steps/s per twin, ~600 ms per shared inference)
9 twin changes + 42-seed table                      0.4
10 shutdown                                         2.4
TOTAL (sum of cells)                              353.0     = 5.9 min on 8 x A100-40G (three GPUs for twins, one for the policy)
```

两个基础设施细节撑住了这份预算。replica 会把并发请求批处理，所以八十次探针调用花的是秒而不是分钟——八十次顺序采样一个 30 亿参数模型可就是分钟。而孪生体在服务能回答 `/stats` 之前不会迈步，于是权重加载、三次 Kit 启动和探针全都重叠在一起。

## **这对你自己的策略意味着什么**

夹爪尖端这个发现是针对这个 checkpoint、这套装置的。但我们得到它的方式不是，这才是重点。在你采更多数据、建一个仿真器、或为微调生成合成帧之前，你可以问策略它到底在读什么——对一个已部署的 replica 发几百条廉价查询，让计数说话。这样做之后得到四条通用经验，而 Ray 让它很容易。

在为逼真度花钱之前，先测策略在关注什么。三十个渲染变体什么都没改变，一个几何线索改变了一切。逐通道的替换会告诉你是哪些输入承载了这个大决策，而策略自己的编码器给你一个可搜索的确定性距离——在你为一个照片级场景或再一周遥操作数据付费之前。

让发现去设定仿真器的优先级，也设定数据管线的优先级。策略在读什么，就是孪生体必须做对什么、仿真增强或合成数据必须包含什么。对这个策略，那是腕部相机在夹爪尖端看到的画面。对你的策略，可能是另一个相机、另一块区域，或一个状态通道。同样风格的探测能找到它。

清楚你的孪生体能认证什么。我们的能认证伸手、抓取与压平，还不能认证从布料堆里提起，因为布料解算器无法带着堆上的布料走。每个孪生体都有这样一条线，而探针加上闭环运行会告诉你线在哪里，于是你知道哪些失效在仿真里可信、哪些要搬到真实装置上。

在微调之前先量基线。一个配置上的种子统计，把判定规则印在旁边，就是微调必须超过的数字。没有它们，「现在更好用了」只是一则轶事。

这些都不需要我们已经找到的那个具体答案。它需要的是一个藏在服务后面的冻结策略、一个能作为 task 启动的仿真器，以及一条便宜到能跑一夜的循环。

## **在 Anyscale 上运行**

随本博客一起发布的还有一个可运行的 notebook、内置的孪生体及其资产、保存的夹持快照、观测转储、作为任意 LeRobot 策略可复用工具的探针框架、42 种子的表，以及视频。`SETUP.md` 给出了 Anyscale 的计算配置，在四张 A100 上约六分钟跑完。同一个 notebook 在八张 A100 上也能跑——改配置，不改代码。checkpoint 是公开的。你需要自己的 Hugging Face token 来获取带访问限制的 PaliGemma tokenizer。

夹爪尖端这个发现和叠衣视频，就是这个工作负载变得可以廉价迭代之后你拿到的东西：一个 30 亿参数的冻结策略被查询了几万次，一个按需启动的布料仿真器，一条快到能跑一夜的科学循环——全都在一个集群上，作为一个程序。
