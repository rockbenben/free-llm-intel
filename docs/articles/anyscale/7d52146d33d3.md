# 使用 Ray Train 实现 epoch 中途的训练恢复

作者：[Jason Li](https://www.anyscale.com/blog?author=jason-li) | 2026 年 11 月 24 日

在大规模场景下，训练失败越来越常见，而衡量训练基础设施是否有效，标准就在于它多快能从失败中恢复。epoch 中途恢复（mid-epoch resumption）让 Ray Train 和 Ray Data 在保存模型的同时也对你的数据加载器（data loader）做 checkpoint，这样重启后的运行会从上一个 checkpoint 的位置继续，而不会破坏 exactly-once 训练。它带来的好处如下：

- **减少重复工作：** 重启的任务从上一个 checkpoint 继续，而不是把整个 epoch 重新跑一遍。
- **数据覆盖正确：** 即使在多次失败的情况下，每一行在每个 epoch 中仍然恰好被训练一次。
- **易于采用：** 它与你现有的 Ray Train checkpoint 配合工作，对训练脚本的改动极少。

在我们的基准测试中，启用 epoch 中途恢复后，一个在 epoch 进行到 75% 时失败的任务，相比通过跳过 batch 来恢复的方式，整体运行时间**快 9%**，美元成本**低 9%**。你的 epoch 越大，失败时节省的就越多。

epoch 中途恢复将随 Ray 2.61 发布，目前已可在 [Anyscale Runtime](https://docs.anyscale.com/runtime/mid-epoch-resumption) 中使用（从 Ray 2.50 版本起）。

## Link epoch 中途训练失败的代价

epoch 中途的训练失败可能代价高昂。设想一次运行，其最新的 checkpoint 保存在 epoch 进行到 75% 的位置，随后在 80% 处发生 worker 故障：

epoch 中途的训练失败可能代价高昂。设想一次运行，其最新的 checkpoint 保存在 epoch 进行到 75% 的位置，随后在 80% 处发生 worker 故障

模型从 75% 处的 checkpoint 恢复，但数据加载器没有任何关于自己读到哪里的记录。典型的恢复方式是从头重新开始这个 epoch，但这会带来两项代价：

- **数据不均衡：** 之前已消费的行在同一个 epoch 中被训练两次，而数据集其余部分只被训练一次，这会使模型学到的东西偏向那部分数据。
- **GPU 时间：** 额外的 GPU 时间被花在对已经消费过的行进行训练上。

这两项代价都会随 epoch 规模增长。在小数据集上，重放一个 epoch 的大部分只是很小的开销。然而，在一个需要一整天才能跑完的数据集上，一次较晚发生的失败可能又要多花一整天的 GPU 时间。

为了避免这些代价，团队通常会快进到训练失败的位置，在重启后跳过已经见过的 batch。然而，对于像 Ray Data 这类即时处理数据、不保证行顺序的流式加载器，被跳过的行仍然需要重新计算，而且快进也无法保证每一行恰好被训练一次。

于是，我们需要一个能自己记录哪些行已被消费、并把该记录与模型 checkpoint 一起保存的数据加载器，这样两者永远不会脱节。本文余下部分将说明 Ray Train 和 Ray Data 是如何做到这一点的，以及它在实践中节省了什么。

## Link 工作原理

![使用 epoch 中途恢复时，重启会从 75% 处的 checkpoint 继续](https://images.ctfassets.net/xjan103pcp94/62RcbskxSYDc6Cckd51bp6/bbc6ddc374dc72befaa4bc5743620d0e/With_mid-epoch_resumption__the_restart_picks_up_at_the_75-_checkpoint.png)

使用 epoch 中途恢复时，重启会从 75% 处的 checkpoint 继续

核心思路是记录已消费的行，而不是记录一个位置。Ray Data 不以固定顺序分发数据行，所以只知道消费了多少个 batch 并不足以重新找到自己的位置，但知道消费了哪些行则可以。为此，每一行都需要一个唯一 ID，每个 worker 记录它训练过的 ID，重启后 Ray Data 在读取时利用该记录跳过这些行。下面我们逐步看看 Ray Train 和 Ray Data 在保存与恢复进度时是如何做的。

### Link 保存进度

- **记录每个产出的 batch。** 一旦你用 `DatasetCheckpointConfig` 为某个数据集开启数据 checkpoint，Ray Data 的数据迭代器交给训练循环的每个 batch 都会被记录：后台线程会把该 batch 的行 ID 写入共享存储中的文件。
- **在 checkpoint 时提交。** 当你为模型做 checkpoint 时，还要对数据迭代器调用 `state_dict()`。该调用会刷新所有剩余的行 ID、关闭当前这一组文件，并返回一个小字典：epoch、checkpoint 索引、行 ID 文件所在的路径，以及 ID 列名。
- **与模型一起保存。** 你把该字典存入与模型和优化器状态相同的 checkpoint 中，并通过 `ray.train.report()` 上报它。模型与数据加载器状态一起提交，因此它们在“已经训练了什么”上始终一致。

每个 worker 写入自己的文件，按 rank、epoch 和 checkpoint 索引组织：

```
ray_data_checkpoints/train/
└── rank=0/
    └── epoch=0/
        ├── checkpoint=0/chunk_0.parquet
        ├── checkpoint=1/chunk_0.parquet
        └── checkpoint=2/chunk_0.parquet
```

默认情况下，这些文件位于你的 Ray Train 存储路径下，并在一个 epoch 结束后被删除，因为该 epoch 内已没有需要恢复的内容。

### Link 恢复进度

- **加载状态。** 任务重启时，你的训练函数通过 `ray.train.get_checkpoint()` 拿到最新的 checkpoint，从中读取保存的字典，并通过 `state_dict` 参数把它传给 `ray.train.get_dataset_shard()`。
- **加载已消费的行 ID。** Ray Data 读取该 epoch 中截至所保存 checkpoint 索引的行 ID 文件（跨所有 rank），并对它们排序，以便快速查找。
- **读取时过滤。** 读取之后紧跟一个过滤步骤，对每一行用二分查找，丢弃 ID 在该集合中的行。被跳过的行不会进入你的预处理或训练循环。
- **继续该 epoch。** 训练用剩余的行继续。该 epoch 结束后，后续 epoch 照常读取完整数据集。

由于过滤作用于整个数据集，而不是每个 worker 各自处理，剩余的行会被分配给重启后运行所拥有的任意 worker。恢复过程仍然需要重新读取输入文件，但读取并过滤一行的开销远小于对它做预处理并跑一次训练步骤。

## Link 使用 epoch 中途恢复

所有这些记录工作都发生在 Ray Train 和 Ray Data 内部。如果你已经用 `ray.train.report` 做 checkpoint，那么开启 epoch 中途恢复只需三处改动：告诉 Ray Train 要跟踪哪个数据集、把数据迭代器的状态与模型一起保存，并在恢复时把该状态传回去。

```
import ray
from ray.train import DataConfig, DatasetCheckpointConfig, ScalingConfig
from ray.train.torch import TorchTrainer

def train_func():
    model, data_state = build_model(), None
    if checkpoint := ray.train.get_checkpoint():
        model, data_state = load_checkpoint(checkpoint)  # your restore logic

    # Change 3: resume the data iterator from the saved state.
    shard = ray.train.get_dataset_shard("train", state_dict=data_state)

    for step, batch in enumerate(shard.iter_torch_batches(batch_size=64)):
        ...  # training step
        if step % 100 == 0:
            # Change 2: save the data iterator state with the model.
            checkpoint = save_checkpoint(model, data_state=shard.state_dict())
            ray.train.report({"step": step}, checkpoint=checkpoint)

trainer = TorchTrainer(
    train_func,
    datasets={"train": ray.data.read_parquet("s3://my-bucket/train/")},
    # Change 1: track which rows each worker has consumed.
    dataset_config=DataConfig(
        dataset_checkpoint_configs={
            "train": DatasetCheckpointConfig(id_column="id")
        }
    ),
    scaling_config=ScalingConfig(num_workers=16, use_gpu=True),
)
trainer.fit()
```

注意：`build_model`、`save_checkpoint` 和 `load_checkpoint` 代表你现有的模型与 checkpoint 代码。

上面每处改动的作用如下：

- **为该数据集开启数据 checkpoint。** 通过 `DataConfig(dataset_checkpoint_configs=...)` 为数据集传入 `DatasetCheckpointConfig`。`id_column` 指定唯一标识每一行的列，这里是名为 id 的列。如果你的数据没有这样的列，请参阅下面的要求。
- **在每次模型 checkpoint 时保存数据迭代器状态。** 每次做 checkpoint 时，在每个 worker 上调用 `shard.state_dict()`。在每个 worker 上，该调用确保该 worker 已消费的所有行 ID 都写入共享存储。它返回的并不是这些 ID，而是一个小的、可 JSON 序列化的字典，指向每个 worker 的文件存放位置，因此在每个 worker 上它都是相同的。在调用 `ray.train.report` 之前，把它存到 checkpoint 目录中模型的旁边。
- **在恢复时把状态传回去。** 从 checkpoint 中加载该字典并传给 `ray.train.get_dataset_shard`。每个 worker 加载的是同一个字典，所以每个 worker 都可以传入它。Ray Train 使用 rank 0 的副本设置恢复后的数据集。

完整的可运行脚本请见 [epoch 中途恢复文档](https://docs.anyscale.com/runtime/mid-epoch-resumption)。

### Link 要求

要使用 epoch 中途恢复，需满足若干条件：

- **每一行都需要唯一 ID。** 把 `id_column` 指向一个现有列，其值唯一且在预处理后仍然保留。如果你的数据没有这样的列，`generate_id_column=True` 会为你生成一个，并从训练循环看到的 batch 中移除。生成的 ID 目前仅支持 Parquet。
- **只使用保留行的转换。** 坚持使用不增加行的转换，例如 `map`、`map_batches` 和 `filter`，并把 ID 列一直传递到 pipeline 的末端。
- **checkpoint 需要共享存储。** 行 ID 文件默认写入你的 Ray Train 存储路径，因此它必须是每个节点都能访问的云存储或网络文件系统。
- **自动重启需要容错。** 在 `RunConfig` 中设置 `FailureConfig(max_failures=...)`，这样 Ray Train 会在失败后重启运行并恢复最新的 checkpoint。
- **在做 checkpoint 前完成一个 batch 的消费。** Ray Data 的迭代器一旦把 batch 交给你的循环，就认为该 batch 已被消费。如果你的框架会在模型训练之前把 batch 排队，请在调用 `ray.train.report` 之前清空该队列。否则，你的数据 checkpoint 会领先于模型实际训练到的位置。

## Link 评估影响

设置讲完了，那么当一个任务在 epoch 后期失败时，epoch 中途恢复实际能节省多少？我们在一项图像分类任务上做了基准测试。设置如下：

- **模型与数据：** ResNet-50（26M 参数），运行在修改过的 ImageNet 上，图像最高 2048x2048，1M 训练行、50k 验证行。
- **集群：** 16 块 A100 GPU 用于训练，另有 10 个 CPU 节点用于 Ray Data 预处理。
- **checkpoint 与验证：** 每 50 步一次。
- **失败：** 模拟在 epoch 进行到 75% 时发生失败。

在这个设置下，我们把同一个任务跑了两次：一次通过跳过 batch 在失败后回到恢复的位置，这也是 Hugging Face Transformers 等框架默认的做法；另一次使用 epoch 中途恢复：

| **指标** | **基线（跳过 batch）** | **epoch 中途恢复** |
| --- | --- | --- |
| 端到端时间 | 594 s | **542 s** |
| 成本 | $1.45 | **$1.32** |

与跳过 batch 相比，启用 epoch 中途恢复使端到端任务运行时间和美元成本都降低了 9%。如果不使用 epoch 中途恢复，跳过 batch 仍然需要读取、预处理并传输恢复点之前的每一行，结果只是把它们丢掉。epoch 中途恢复仍然会读取这些行，但在读取之后、任何预处理或传输到训练 worker 之前就把它们丢弃。这也是为什么 epoch 越大、预处理越重，节省就越多。

## Link 总结

训练任务会失败，而任务规模越大，每次失败的代价就越高。epoch 中途恢复把数据加载器的状态纳入 checkpoint，因此重启后的 Ray Train 任务会从上一个 checkpoint 的位置继续，让每一行恰好被训练一次。在我们的基准测试中，与跳过 batch 相比，它把任务的端到端运行时间和总成本降低了 9%，并且每一行在每个 epoch 中仍然恰好被训练一次。epoch 中途恢复从 Ray 2.61 起随开源 Ray 发布，目前已在 Anyscale Runtime 中可用（从 Ray 2.50 起）。使用细节请见 [epoch 中途恢复文档](https://docs.anyscale.com/runtime/mid-epoch-resumption)。如果你遇到问题，或对下一步该构建什么有想法，请[在 GitHub 上提交 issue](https://github.com/ray-project/ray/issues)。
