# 使用 Ray Train 在 epoch 中途恢复训练

作者：[Jason Li](https://www.anyscale.com/blog?author=jason-li) | 2026 年 11 月 24 日

训练规模越大，故障越常见。衡量训练基础设施是否有效，要看它能多快从故障中恢复。启用 epoch 中途恢复后，Ray Train 和 Ray Data 会把数据加载器的状态连同模型一起存入检查点。作业重启时从上一个检查点继续，依然保证每行数据在一个 epoch 内恰好参与一次训练。这项功能带来三点好处：

- **减少重复工作：**作业重启后从上一个检查点继续，省去从头跑完整个 epoch 的开销。
- **保证数据覆盖正确：**即使发生故障，每行数据在每个 epoch 内仍恰好参与一次训练。
- **易于接入：**支持现有的 Ray Train 检查点，训练脚本只需少量改动。

在我们的基准测试中，作业在一个 epoch 进行到 75% 时失败。与通过跳过批次恢复相比，启用 epoch 中途恢复后，**总体运行时间缩短 9%**，**费用降低 9%**。单个 epoch 越大，发生故障时节省的开销就越多。

这项功能将随 Ray 2.61 发布。目前，[Anyscale Runtime](https://docs.anyscale.com/runtime/mid-epoch-resumption) 从 Ray 2.50 起已支持。

## epoch 中途发生训练故障的代价

训练在 epoch 中途失败，代价可能很高。假设作业在一个 epoch 进行到 75% 时保存了最新检查点，随后一个 worker 在进度达到 80% 时发生故障：

训练在 epoch 中途失败可能代价高昂。图中的作业在一个 epoch 进行到 75% 时保存了最新检查点，随后一个 worker 在进度达到 80% 时发生故障。

模型可以从 75% 处的检查点恢复，但数据加载器并未记录当时的加载进度。常见的恢复办法是从头跑这个 epoch，这会带来两类开销：

- **数据失衡：**之前已经读过的数据行在同一 epoch 内参与两次训练，其余数据行只参与一次，导致模型学到的内容偏向前一部分数据。
- **GPU 时间：**重新训练已经处理过的数据行会额外占用 GPU。

这两类开销都会随 epoch 的规模增长。在小数据集上，重跑大半个 epoch 的代价有限。如果一个数据集需要一天才能跑完，临近结束时发生一次故障，就可能多花一天 GPU 时间。

为避免这些开销，团队通常会在重启后逐批略过已经见过的数据，尽快推进到训练失败的位置。Ray Data 这类流式加载器会即时处理数据，且不保证数据行的顺序，因此跳过的数据行仍需重新计算，这种快进办法也无法保证每行数据恰好参与一次训练。

为此，数据加载器需要自行记录已经处理过哪些数据行，并把记录与模型检查点一起保存，确保两边始终同步。下面介绍 Ray Train 和 Ray Data 如何做到这一点，以及在实际运行中能节省多少开销。

## 工作原理

![启用 epoch 中途恢复后，作业重启时从 75% 处的检查点接着运行](https://images.ctfassets.net/xjan103pcp94/62RcbskxSYDc6Cckd51bp6/bbc6ddc374dc72befaa4bc5743620d0e/With_mid-epoch_resumption__the_restart_picks_up_at_the_75-_checkpoint.png)

启用 epoch 中途恢复后，作业重启时从 75% 处的检查点接着运行。

关键是记录哪些数据行已经处理。Ray Data 不按固定顺序交付数据行，仅凭已处理的批次数无法找回进度，有了具体的数据行记录才可以。每行数据都需要一个唯一 ID，各 worker 记录自己训练时用过的 ID。重启后，Ray Data 在读取时根据记录跳过这些数据行。下面分别介绍 Ray Train 和 Ray Data 如何保存和恢复进度。

### 保存进度

- **记录每个交付的批次。**通过 `DatasetCheckpointConfig` 为数据集启用数据检查点后，Ray Data 的数据迭代器每向训练循环交付一个批次，后台线程就会把该批次的数据行 ID 写入共享存储中的文件。
- **生成检查点时提交记录。**为模型创建检查点时，同时调用数据迭代器的 `state_dict()` 方法。这个调用会把尚未写入的数据行 ID 刷入存储，关闭本次使用的文件，并返回一个小字典，其中包含 epoch、检查点索引、数据行 ID 文件的存放路径和 ID 列名。
- **与模型一起保存。**把字典、模型状态和优化器状态存入同一个检查点，再用 `ray.train.report()` 上报。模型和数据加载器状态一同提交，两者记录的训练进度始终一致。

各 worker 分别写入自己的文件，按 rank、epoch 和检查点索引组织：

```
ray_data_checkpoints/train/
└── rank=0/
    └── epoch=0/
        ├── checkpoint=0/chunk_0.parquet
        ├── checkpoint=1/chunk_0.parquet
        └── checkpoint=2/chunk_0.parquet
```

这些文件默认放在 Ray Train 的存储路径下。一个 epoch 完成后无需再从中途恢复，其文件也随之删除。

### 恢复进度

- **加载状态。**作业重启时，训练函数通过 `ray.train.get_checkpoint()` 获取最新检查点，读出保存的字典，再通过 `state_dict` 参数把它传给 `ray.train.get_dataset_shard()`。
- **加载已处理的数据行 ID。**Ray Data 读取该 epoch 内所有 rank 的数据行 ID 文件，读到已保存的检查点索引为止，再将 ID 排序，加快查找。
- **边读取边过滤。**读取后立即过滤，对每行数据执行二分查找，丢弃 ID 已在集合中的行。这些行不会进入预处理或训练循环。
- **继续当前 epoch。**训练用余下的数据行接着跑。当前 epoch 结束后，后续各个 epoch 照常读取完整数据集。

过滤针对整个数据集，剩余的数据行会分配到重启后的作业实际拥有的各个 worker。恢复时仍然要重读输入文件，但读取并过滤一行的成本远低于对它做预处理并执行一次训练步骤。

## 使用 epoch 中途恢复

这些记录工作由 Ray Train 和 Ray Data 在内部完成。如果你已通过 `ray.train.report` 创建检查点，只需三处改动就能启用 epoch 中途恢复：告诉 Ray Train 要跟踪哪个数据集，把数据迭代器状态与模型一起保存，恢复时再把该状态传回。

```
import ray
from ray.train import DataConfig, DatasetCheckpointConfig, ScalingConfig
from ray.train.torch import TorchTrainer

def train_func():
    model, data_state = build_model(), None
    if checkpoint := ray.train.get_checkpoint():
        model, data_state = load_checkpoint(checkpoint)  # your restore logic

    # Change 3: resume the data iterator from the saved state.
    shard = ray.train.get_dataset_shard("train", state_dict=data_state)

    for step, batch in enumerate(shard.iter_torch_batches(batch_size=64)):
        ...  # training step
        if step % 100 == 0:
            # Change 2: save the data iterator state with the model.
            checkpoint = save_checkpoint(model, data_state=shard.state_dict())
            ray.train.report({"step": step}, checkpoint=checkpoint)

trainer = TorchTrainer(
    train_func,
    datasets={"train": ray.data.read_parquet("s3://my-bucket/train/")},
    # Change 1: track which rows each worker has consumed.
    dataset_config=DataConfig(
        dataset_checkpoint_configs={
            "train": DatasetCheckpointConfig(id_column="id")
        }
    ),
    scaling_config=ScalingConfig(num_workers=16, use_gpu=True),
)
trainer.fit()
```

注：`build_model`、`save_checkpoint` 和 `load_checkpoint` 代表你已有的模型构建和检查点处理代码。

上面三处改动的作用如下：

- **为数据集启用数据检查点。**通过 `DataConfig(dataset_checkpoint_configs=...)` 为数据集传入 `DatasetCheckpointConfig`。`id_column` 指定唯一标识每行数据的列，这里是 id。如果数据里没有这样的列，请参见下方要求。
- **创建每个模型检查点时保存数据迭代器状态。**每次创建检查点时，在各个 worker 上调用 `shard.state_dict()`，确保该 worker 已处理的数据行 ID 全部写入共享存储。这个方法返回一个简短、可序列化为 JSON 的字典，指向各 worker 文件的存放位置。因此每个 worker 拿到的字典都一样。在调用 `ray.train.report` 之前，把字典和模型一起存入检查点目录。
- **恢复时传回状态。**从检查点加载字典并传给 `ray.train.get_dataset_shard`。各 worker 加载的是同一个字典，因此都可以传入它。Ray Train 使用 rank 0 传入的副本配置恢复后的数据集。

完整的可运行脚本见 [epoch 中途恢复文档](https://docs.anyscale.com/runtime/mid-epoch-resumption)。

### 使用要求

使用 epoch 中途恢复有以下要求：

- **每行数据都需要唯一 ID。**将 `id_column` 指向一列已有的唯一值，并确保该列在预处理后仍然保留。如果数据里没有这样的列，`generate_id_column=True` 会生成一列，并从交给训练循环的批次中移除该列。目前只支持为 Parquet 数据生成 ID。
- **仅使用不会新增数据行的转换。**可使用 `map`、`map_batches` 和 `filter` 等转换，并将 ID 列保留到流水线末尾。
- **检查点需要共享存储。**数据行 ID 文件默认写入 Ray Train 的存储路径，因此该路径必须指向所有节点都能访问的云存储或网络文件系统。
- **自动重启需要容错配置。**在 `RunConfig` 中设置 `FailureConfig(max_failures=...)`，让 Ray Train 在故障后重启作业并恢复最新检查点。
- **创建检查点前要完成当前批次的训练。**Ray Data 的迭代器把一个批次交给训练循环时，就会把它记为已处理。如果框架会先将批次入队，再交给模型训练，请先处理完队列中的批次，再调用 `ray.train.report`，以免数据检查点的进度超前于模型实际的训练进度。

## 效果评估

启用这项功能后，如果一次训练在 epoch 快结束时失败，实际能节省多少开销？我们用一个图像分类作业做了基准测试，配置如下：

- **模型与数据：**在修改过的 ImageNet 上训练 ResNet-50（2,600 万参数），图像最大分辨率为 2048 × 2048。训练集有 100 万行，验证集有 5 万行。
- **集群：**用 16 张 A100 GPU 训练，另外用 10 个 CPU 节点运行 Ray Data 预处理。
- **检查点与验证：**每 50 步执行一次。
- **故障：**在一个 epoch 进行到 75% 时模拟故障。

在同样的配置下，我们把作业跑了两次。第一次在故障后按 Hugging Face Transformers 等框架的默认做法，通过跳过批次回到检查点位置。第二次使用 epoch 中途恢复：

| **指标** | **基线（跳过批次）** | **epoch 中途恢复** |
| --- | --- | --- |
| 端到端用时 | 594 秒 | **542 秒** |
| 费用 | $1.45 | **$1.32** |

与跳过批次相比，启用 epoch 中途恢复后，作业的端到端用时和费用均降低了 9%。采用跳过批次的做法时，仍须读取、预处理并传输恢复点之前的每一行数据，之后才会把它们丢弃。采用 epoch 中途恢复时，这些行同样会被读取，但读取后立即丢弃，无需预处理，也无需传给训练 worker。因此，epoch 越大、预处理开销越高，节省的就越多。

## 总结

训练会发生故障，作业规模越大，每次故障的代价也越高。启用 epoch 中途恢复后，数据加载器状态会一并存入检查点。Ray Train 作业重启后从上一个检查点接着跑，每行数据恰好参与一次训练。在我们的基准测试中，与跳过批次相比，这项功能将作业的端到端用时和总费用均降低了 9%，并继续保证每行数据在每个 epoch 中恰好参与一次训练。开源版 Ray 从 2.61 起提供这项功能，Anyscale Runtime 目前已从 Ray 2.50 起提供。用法详见 [epoch 中途恢复文档](https://docs.anyscale.com/runtime/mid-epoch-resumption)。如果遇到问题，或对后续功能有想法，欢迎[在 GitHub 提交 issue](https://github.com/ray-project/ray/issues)。
