# 用 Ray 实现 JEPA 世界模型架构的实时推理

作者：[Omar Shorbaji](https://www.anyscale.com/blog?author=omar-shorbaji) 与 [Ian Jordan, PhD](https://www.anyscale.com/blog?author=ian-jordan-phd) | November 12, 2026

借助 V-JEPA2-AC，系统通过评估数百种可能的未来、挑出最接近目标的那一种，来决定机械臂下一步做什么。两次动作之间要耗掉相当长时间。本文给出一套设计并已实测的实现，把搜索搬进 Ray 集群，将这段时间压到一秒以内。

## Link**01 · 机器人入门**

机器人感知环境的部分观测，经某种策略选出一个动作，再由控制器执行，并按控制环频率不断重复。经典做法里，这三个环节都用闭式解求解，机器人上一块 CPU 就够跑完全部。

经典机器人学从第一性原理搭起这三个盒子：感知用手推的运动学，规划用轨迹优化，控制用 PID 或模型预测控制器。图 1 所示的这套方法支撑了数十年的工业自动化，但每换一个新任务、新物体或新环境，通常就得重新做一遍工程。

**经典机器人** — ~1 ms / 动作

![图 1. 每台机器人都在跑的循环](https://images.ctfassets.net/xjan103pcp94/5aLy255S6wnzgi5E817Asj/8662c462ba93f2cf31ad285f4639e909/Figure_1._The_loop_every_robot_runs.png)***图 1.*** *每台机器人都在跑的循环。感知把传感器读数变成状态，规划给出一条路径，控制照着执行，机械臂再经物理世界把环闭合。三者都在一块板载 CPU 上以闭式解求解。代价是工程量：策略只覆盖它被推导出来的那个任务。*

图 1. 每台机器人都在跑的循环

*Physical AI* 想用数据训练出来的网络替换掉其中部分或全部盒子，拿手推的精度换通用性：数据喂够的模型，能迁移到没有显式编程过的情形。

### Link**JEPA 架构如何补上「规划」这个盒子**

V-JEPA2-AC 就是这样一种模型，建立在 *Joint-Embedding Predictive Architecture*（JEPA）之上。在这套架构里，系统用模型评估数百种可能的未来，挑出最接近目标的一个，据此决定机械臂下一步做什么。图 2 展示了整套循环落在运行它的硬件上的样子。

在两个实验室的 Franka 机械臂上零样本部署、不针对具体环境做 fine-tuning 的情况下，V-JEPA2-AC 报告对未见过的物体做抓取放置有 65–80% 成功率，跑在单块 RTX 4090 上。但这样的配置**每规划一个动作就要 16 秒**，快不到能连续运行。

### Link**那十六秒究竟花在哪**

值得把一个规划步骤从头走到尾，因为这笔算术解释了本文余下的一切。机械臂静止不动；相机帧和目标图像各编码一次。接着搜索算法 CEM 从以当前最优猜测为中心的高斯分布里抽 800 条候选动作序列，逐条送进 predictor，拿结果和目标 embedding 比对打分，留下最好的 80 条，再把高斯重新中心化到它们上。这算一轮，如此重复十次：一只机械臂动一下，约要进行 8,000 次 predictor 评估。系统随后只执行胜出序列的第一个动作，其余丢弃，再从一帧新图像重来。这份开销是结构性的，每一步都会重现。

**V-JEPA2-AC 跑在单块板载 GPU 上** — 16 s / 动作

![图 2. 只有规划盒子变了](https://images.ctfassets.net/xjan103pcp94/54PrYjWdGSJ8OEMHJAZysm/f0fd37f697dfeae1dbddffef71e413d1/Figure_2._Only_the_plan_box_changes.png)***图 2.*** *只有规划盒子变了。机器人照样采集相机帧和关节状态，控制也没动，但闭式 planner 换成了模型，外加围着模型的一轮搜索。encoder 属于模型，所以编码发生在这一步、每步一次；随后的十轮循环才是贵的部分。*

图 2. 只有规划盒子变了

控制器还是**阻塞式**的：要等上一个动作完成才发下一个，规划永远和运动错开。机器人停住、规划十六秒、动一下、再停住。本文要解决的正是这种一顿一顿，而不是模型的准确率。

## Link**02 · 方法**

我们的做法第一步，是把世界模型推理从机器人挪到云服务器。这会在每个控制步上多出一趟网络往返的开销，但其他改进把它抵掉了。首先，它让模型得以跑在更强的 GPU 上。本实现用的是 NVIDIA A100-40GB GPU，显存比论文里的 24 GB RTX 4090 更大，bf16 吞吐量也高得多。

**同样的搜索放在单块云 GPU 上** — 21.4 s / 动作（实测，A100，优化后模型）

![图 3. 规划块把推理从机器人身上搬走](https://images.ctfassets.net/xjan103pcp94/793bpoEfPXi9p9NQAkiuXj/0c9bc70e625992db89d9e9aa55733c2c/Figure_3._The_plan_block_lifts_the_inference_off_the_robot.png)***图 3.*** *规划块把推理从机器人身上搬走。留在本地的只有传感和驱动，于是过网的只是一帧相机图像加关节状态，以及回传的一个动作向量。*

图 3. 规划块把推理从机器人身上搬走

光换更大的 GPU 还不够。Meta 的参考 planner 按这些设置在一块 A100 上原样跑，每个动作要 81.8 s；加上第 05 节的模型级优化后是 21.4 s。我们的 81.8 s 比论文在 4090 上的 16 s 慢，是因为我们照搬了 Meta 发布的规划代码（fp32、800 个候选 × 10 轮、两步 horizon）；论文里的耗时大概对应别的设置或精度。本文所有加速数据，都以同一硬件上我们自己那 81.8 s 基线为参照。快是快了，可机械臂在两次动作之间照样要停。

第二步是把负载摊到多块 GPU 上。切入点在于：同一轮 CEM 细化里，各条 rollout 可以各算各的，等这一轮推进前再汇总。论文把它们当成一个大批次塞在单块 GPU 上跑；其实没有什么要求它们必须待在一块 GPU 上。我们的实现在 Anyscale 上用了一个八 GPU 节点（8× A100-40GB）。

**搜索分布到 Ray 集群上** — 2.86 s / 动作（实测，8× A100）；每步 3 轮时 0.86 s

![图 4. 规划块内部的一步变了](https://images.ctfassets.net/xjan103pcp94/2NyeI9V5I80vK9qqcdv2sD/d82bbbc04e7df418774c405a6357cb37/Figure_4._One_step_inside_the_plan_block_changes.png)***图 4.*** *规划块内部的一步变了。一轮里 800 个候选彼此独立，于是 predict 这一步扇出到已经装好模型的温副本上，打分前再收拢。十轮仍是串行的，这正是延迟的下限所在。*

图 4. 规划块内部的一步变了

我们用 Ray 来实现这一点。

## Link**03 · Ray 入门**

### Link**把 Python 变成集群程序的通用框架**

[Ray](https://docs.ray.io/en/latest/ray-core/walkthrough.html) 是一个开源框架，最早诞生于 UC Berkeley 的 RISELab，现由 Anyscale 维护，能把普通 Python 从笔记本扩到集群，而不必把它重写成分布式系统。它只暴露一小组原语，代码结构大体还是顺序的。

### Link**Ray Core**

Ray Core 有两个和本文相关的积木。加了 @ray.remote 的函数会成为 **task**，调度到集群某处执行并返回一个 future；加了 @ray.remote 的类会成为 **actor**：一个钉在某台机器（也可绑定某块 GPU）上的有状态 worker，在两次调用之间把已加载的模型权重常驻着。task 适合一次性的并行活；actor 适合那种先花本钱把 12 亿参数的 checkpoint 载一次、之后应答许多轻量请求的进程。

### Link**Ray Serve**

Ray Serve 架在 Ray Core 之上：一句 @serve.deployment 声明，就够让 Ray 管起一组副本、路由请求、按负载伸缩。Ray Core 回答的是「怎么把一个函数跑到许多 worker 上」；Ray Serve 回答的是「怎么把它暴露成别的系统能调的服务」——这正是机器人控制环要的形态：一个每步被命中一次的低延迟 endpoint。

## Link**04 · 实现**

### Link**两个组合起来的 Ray Serve deployment**

这套设计是两个 Ray Serve deployment，中间用一个 handle 连起来。WorldModel 是 GPU 层：每块 GPU 一个副本，各自装着 encoder 和 predictor（我们在 8 块 A100 上跑了 8 个副本）。Planner 是驱动方：跑十轮 CEM 循环，把每轮扇出到那些副本，并对机器人每个控制步调用一次的那个 endpoint 提供服务。这样把它们组合起来，而不是用松散的 Ray Core actor，等于交给 Serve 统一管：放置、健康检查、重启，以及一份 KubeRay RayService 能不停机发布的声明式配置。下面这段只留骨架，隐去了内部细节；要紧的是扇出落在哪一层。部署布局图见图 5。

**serve_app.py** — Ray Serve · 骨架，细节从略

```
from ray import serve
Import ray
from ray.serve.handle import DeploymentHandle

# The GPU tier. One replica per GPU, pinned, weights resident between calls.
@serve.deployment(
    num_replicas=8,  # one per GPU
    ray_actor_options={"num_gpus": 1},
    max_ongoing_requests=1,          # one shard at a time, so fan-out maps 1:1
)
class WorldModel:
    def __init__(self, checkpoint): ...        # paid once, when Serve starts it
    def encode(self, frame, proprio): ...      # the encoder is part of the model
    def score(self, ctx, actions): ...   # one shard, one GPU batch

# The driver. Holds a handle to the GPU tier and runs the search.
@serve.deployment(num_replicas=2)
@serve.ingress(app)
class Planner:
    def __init__(self, model: DeploymentHandle):
        self.model = model

    @app.post("/plan")
    async def plan(self, frame, proprio, goal_image):
        obs, goal = await asyncio.gather(      # encode once per control step
            self.model.encode.remote(frame, proprio),
            self.model.encode.remote(goal_image),
        )
  ctx = ray.put((obs, goal))  # once per plan, read from shared memory
        mean, std = init_distribution(horizon, action_dim)

        for _ in range(10):                    # CEM rounds: sequential, the floor
            cands = sample(mean, std, n=800)
            scores = await asyncio.gather(*[   # fan out one shard per replica
                self.model.score.remote(ctx, shard)
                for shard in np.array_split(cands, 8)
            ])                                 # gather before the round refits
            mean, std = refit(cands, scores, elite_frac=0.1)

        return {"action": mean[0].tolist()}    # first action only, then re-plan

app_builder = Planner.bind(WorldModel.bind(CHECKPOINT))
```

整个设计靠两个选择撑起来。GPU 层把 num_replicas=8 钉死而不做自动伸缩，因为副本数在一轮中途变化会让延迟不可预测，而这里要的是稳定的每步预算。max_ongoing_requests=1 让每个副本一次只接一个分片，于是 8 路扇出能一块 GPU 落一个分片，而不是把好几个堆到少数副本上排队。底层每个副本仍是 Ray Core actor，这正是权重能常驻的原因；区别在于生命周期归 Serve 管。

**构建过程中的心得。 **有三处细节决定了延迟。第一，观测与目标的 latent（2.8 MB）每次规划用 ray.put 放进 Ray 的 object store 一次；每个副本从共享内存读出来、缓存到自己 GPU 上，于是一轮只需往外送约 5 KB 的候选动作、再把 energy 收回来，而 Ray 在一轮里占的整段开销（扇出、收拢、refit）不到 10 ms。第二，在 max_ongoing_requests=1 下，Serve 默认的 power-of-two-choices 路由器偶尔把两个分片塞到同一副本、让另一个闲着，把那一轮拖成两倍；Serve 的 round-robin 请求路由器则把一轮的分片落到连续副本上，一块 GPU 一个（50 轮零冲突）。第三，我们的 Serve 副本进程启动时环境里带着 TORCHDYNAMO_DISABLE=1，会悄悄把 torch.compile 变成空操作；在副本构造函数里把它清掉，找回了 1.35× 的加速。

## Link**05 · 结果**

### Link**在 8× A100 上实测**

我们按上面的设计做了实现，在一台带八块 A100-40GB GPU 的 Anyscale 节点上实测，搜索设置沿用第 01 节（800 个候选 × 10 轮，保留 80，horizon 2）。锚点是 Meta 的参考 planner，在一块 A100 上以 fp32 原样跑：每个动作 81.8 s。加 GPU 之前，我们先在单 GPU 上把模型本身变快：跨 rollout 步的 KV cache（predictor 是帧因果的，早先的帧无需重算）、带 FlashAttention 的 bf16，以及 torch.compile。结果与参考 energy 吻合（Pearson r = 0.9999），把单 GPU 压到每个动作 21.4 s，快了 4×。

![图 6. 实测每个动作的规划耗时](https://images.ctfassets.net/xjan103pcp94/1HObhsYqltV9tTxq161sK1/c8cd66020e487705829297b137563c19/Figure_6._Measured_planning_time_per_action.png)***图 6.*** *实测每个动作的规划耗时。Ray Serve 把每轮扇出到 8 块 A100 上（2.86 s，参考值的 29×）。闭环测试（第 06 节）里，每步跑 3 轮搜索而非 10 轮就达到相同精度，于是每个动作 0.86 s，是参考值的 96×。*

图 6. 实测每个动作的规划耗时

接着是扇出。每轮的 800 个候选拆给 W 个 WorldModel 副本，一副本一块 GPU。GPU 从 1 块加到 8 块，一次规划从 21.4 s 降到 2.86 s，加速 7.5×。相同随机种子在任何 GPU 数下都给出一模一样的规划，所以分片只改搜索快慢，不改它的答案。本文初稿提出的延迟模型也站得住：用实测的单 GPU 单轮（2.14 s）校准后，它预测 8 块 GPU 时是 2.94 s，实测 2.86 s。

### Link**规划延迟与集群规模**

一台 8 GPU 节点上的 A100-40GB 副本。点是实测值，线是延迟模型。

**8 个 A100 worker 下 2.86 s / 动作**。这比单块 A100 快 7.5×，比 Meta 的参考 planner 快 29×。

![图 7. 规划延迟与 GPU 副本数的关系](https://images.ctfassets.net/xjan103pcp94/4pO1gOaQkRV99oC3sFaJZI/bb4b1ff81a4e092cd463800cb3f4f4d8/Figure_7._Plan_latency_vs._number_of_GPU_replicas.png)***图 7.*** *规划延迟与 GPU 副本数的关系：8× A100 上的实测（点），对照以实测单 GPU 单轮校准的延迟模型（线；8 块 GPU 之外的虚线为外推）。*

模型：time(W) = 10 × ( r / effective(W) + 0.001s × (W − 1) )，其中 effective(W) = W / (1 + 0.008×(W−1))，r 为实测的单 GPU 单轮，在 A100 上是 2.14 s。超过 8 块 GPU 后曲线变平，因为每块 GPU 分到的 800 个候选已经很少。更大的集群主要靠同一层去服务更多机器人、或承载更大的搜索，才划得来。

**还有两项没测：**本地机器人与云区域之间的网络延迟，以及真实机械臂上的表现（我们的闭环测试拿世界模型当模拟器）。冷启动不落在请求路径上：副本在部署时用约 50 s 完成加载和编译，之后才接流量。换一种方式给候选分批也不改精度：1、2、4、8 块 GPU 下的规划完全一致。

## Link**06 · 进一步优化**

### Link**搜索本身不再是瓶颈后，还能试什么**

等每一轮都快到 GPU 的极限，剩下的就是十轮串成的链；再要提速，得改循环结构，而不是继续加 GPU。

#### Link**A. 非阻塞控制**

机器人还在执行第 *t* 步时，就开始规划第 *t*+1 步。这样把规划延迟藏进执行时间里，而不是叠加上去；改的是控制器，不是模型。

**实测。 **我们仿真了一每个动作耗时 1 s、落地带 4 mm 执行误差的机械臂。阻塞式控制器每步要 1.86 s（先规划，再动）。非阻塞控制则依据世界模型预测的第 t 步落点来规划第 t+1 步，每步 1.04 s，也就是运动本身再加 40 ms。最终精度相同，一段 12 步的 episode 用时从 25.3 s 降到了 15.3 s。

![图 8. 朝 21.6 cm 外目标的闭环 episode](https://images.ctfassets.net/xjan103pcp94/1wgt2z0xXlplOL8aVQriLB/a03c590900577a0d84d4c2cd843d4a55/Figure_8._Closed-loop_episodes_toward_a_goal_21.6_cm_away.png)***图 8.*** *以世界模型代替机器人，朝 21.6 cm 外目标进行的闭环 episode。左：每步 3 轮搜索用三分之一的规划时间达到与 10 轮相同的精度。右：非阻塞控制把 planner 从机器人的关键路径上移走。*

图 8. 朝 21.6 cm 外目标的闭环 episode

#### Link**B. 热启动 CEM**

滚动时域控制只留第一个动作，其余全丢。拿剩下的部分给下一步的分布做种子，而不是每次都从全新高斯出发，能让每次重规划在不到十轮里收敛，把并行性够不着的那段串行链缩短。

**实测。 **闭环测试里，每步 3 轮（8 块 A100 上 0.86 s）达到与完整 10 轮（2.83 s）相同的精度：两者都停在距起点 21.6 cm 的目标约 4 cm 处。从上一次规划热启动确实有效，但在这个任务上，全新开一轮 3 轮搜索也一样好，所以收益来自少跑几轮。一个任务到底需要几轮，值得逐个任务调。

#### Link**C. 机群级批处理**

按一台机器人配的 GPU 层，在两次请求之间是闲着的。放到 Serve endpoint 后面，同一层可以服务整个机群；请求批处理把不同机器人的分片塞进同一个 GPU batch，让同一批温 GPU 摊到许多机械臂上。

#### Link**D. 模型压缩**

对 predictor 做蒸馏或量化，直接缩小计算项本身，与它被摊到多少 worker 上无关。它和分布式是叠加关系，而不是互相争抢。

#### Link**E. 服务层优化**

predictor 沿 horizon 一步步向前 roll，于是 LLM serving 早已依赖的那一套也搬得过来：跨 rollout 步的 KV caching、prefill 与 decode 分离、continuous batching。它们在同一个 Serve deployment 里，从另一个方向去压同一个计算项。

**已实现。 **跨 rollout 步的 KV caching，连同 bf16、FlashAttention 和 torch.compile，都是实测系统的一部分。它在单 GPU 上带来 4×，并把参考 energy 对到 r = 0.9999。

## Link**07 · 要点**

这十六秒不是实现缺陷，而是刻意的架构选择带来的：JEPA 模型预测的是状态而非动作，所以动作得在推理时搜出来，不能从 policy head 里直接读。agentic 系统抽样大量候选再打分，做的是同一笔交易，好处也相同——系统不必重训就能指向一个新目标。

四种配置把这笔交易摆得很具体。手写策略换来毫秒级动作，代价是针对具体任务做工程。V-JEPA2-AC 用这份速度，换出一个能接受任何拍得下照片的目标的系统。把搜索搬到集群，则在不丢通用性的前提下把速度买回来，而且动的是基础设施，不是模型。在八块 A100 的一台节点上实测，Ray Serve 把完整搜索从每个动作 82 s 压到 2.9 s，其中分布式挑了大头，Ray 每轮只添不到 10 ms。十轮串行设下了再加硬件也搬不动的下限。用每步更少轮数去啃这个下限，能到 0.86 s；非阻塞控制再把剩下的藏进机械臂自身的运动里。
