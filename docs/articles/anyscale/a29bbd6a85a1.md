# 使用 Ray 对 JEPA 世界模型架构进行实时推理

作者：[Omar Shorbaji](https://www.anyscale.com/blog?author=omar-shorbaji) 和 [Ian Jordan 博士](https://www.anyscale.com/blog?author=ian-jordan-phd) | 2026 年 11 月 12 日

借助 V-JEPA2-AC，系统通过评估数百种可能的未来并选择最接近目标的一个来决定机器人手臂下一步应该做什么。两次移动之间需要花费大量时间。本文档介绍了一种设计和经过测试的实现，通过将搜索移至 Ray 集群来在一秒钟内实现这一目标。

## 链接**01 · 机器人入门**

机器人感知对环境的部分观察，通过某种策略选择一个动作，通过控制器执行它，并以控制环频率重复此操作。传统上，这三个函数中的每一个都以封闭形式求解，机器人上的 CPU 足以运行所有函数。

经典机器人技术根据第一原理构建了这三个盒子：用于感知的手动运动学、用于规划的轨迹优化、用于控制的 PID 或模型预测控制器。这种方法（如图 1 所示）是数十年工业自动化的基础，但每个新任务、对象或环境通常都需要新的工程设计。

**经典机器人** — ~1 毫秒/动作

![图 1. 每个机器人运行的循环](https://images.ctfassets.net/xjan103pcp94/5aLy255S6wnzgi5E817Asj/8662c462ba93f2cf31ad285f4639e909/Figure_1._The_loop_every_robot_runs.png)***图 1.*** *循环每个机器人运行。感知将传感器读数转化为状态，规划产生一条路径，控制执行它，而手臂则闭合物理世界的循环。所有这三个问题均在一个板载 CPU 上以封闭形式求解。它的成本是工程：该保单仅涵盖其衍生的任务。*

图 1. 每个机器人运行的循环

*物理人工智能*旨在用经过数据训练的网络取代部分或全部这些盒子，用手工得出的精度换取通用性：一个经过充分数据传输训练的模型，可以传输到未明确编程的情况。

### 链接**JEPA 架构如何填充“计划”框**

V-JEPA2-AC 就是这样的型号之一。它建立在*联合嵌入预测架构* (JEPA) 之上。在这种架构中，系统通过使用模型评估数百种可能的未来并选择最接近目标的一个来决定机器人手臂下一步应该做什么。图 2 显示了运行该循环的硬件上的整个循环。

V-JEPA2-AC 在两个实验室的 Franka 手臂上进行了零射击部署，无需针对特定环境进行微调，报告称在新物体的拾取和放置方面取得了 65-80% 的成功率。它在单个 RTX 4090 上运行。但是，该配置需要 **16 秒来规划每个操作**。它的速度不够快，无法连续运行。

### 链接**十六秒实际去向**

值得从头到尾地走一个计划步骤，因为算术解释了本文档的其余部分。手臂保持不动。相机帧和目标图像被编码一次。然后，搜索算法 CEM 从以其当前最佳猜测为中心的高斯中抽取 800 个候选动作序列，将每个序列推入预测器，根据目标嵌入对结果进行评分，保留最佳的 80 个，并将高斯重新以它们为中心。这是一轮，会发生十次：对一只手臂的一个小动作进行大约 8,000 次预测评估。然后，系统仅执行获胜序列的第一个动作，丢弃其余的动作，并从新的帧重新开始。成本是结构性的，并且在每一步都会重复出现。

**V-JEPA2-AC 在一个板载 GPU 上** — 16 秒/动作

![图 2. 仅计划框发生变化](https://images.ctfassets.net/xjan103pcp94/54PrYjWdGSJ8OEMHJAZysm/f0fd37f697dfeae1dbddffef71e413d1/Figure_2._Only_the_plan_box_changes.png)***图 2.*** *仅计划框发生变化。机器人仍然捕获相机框架及其关节状态，并且控制不变，但封闭式规划器被模型及其周围的搜索所取代。编码器是模型的一部分，因此编码发生在此处，每步一次；接下来的十轮循环是昂贵的部分。*

图 2. 仅计划框发生变化

控制器也是**阻塞**：它在发送下一个操作之前等待上一个操作完成，因此规划永远不会与运动重叠。机器人暂停，计划十六秒，移动，然后再次暂停。本文档要解决的问题是这种口吃问题，而不是模型的准确性。

## 链接**02 · 方法**

我们首先采用的方法是将世界模型推理从机器人转移到云服务器中。虽然这在每个控制步骤上引入了网络往返的新成本，但这被其他改进所抵消。首先，它提供了在更强大的 GPU 上提供模型服务的机会。在此实现中，我们使用 NVIDIA A100-40GB GPU，其内存比本文中使用的 24 GB RTX 4090 更多，并且 bf16 吞吐量显着提高。

**在一个云 GPU 上进行相同的搜索** — 21.4 秒/操作（测量，A100，优化模型）

![图 3. 计划块将推理从机器人](https://images.ctfassets.net/xjan103pcp94/793bpoEfPXi9p9NQAkiuXj/0c9bc70e625992db89d9e9aa55733c2c/Figure_3._The_plan_block_lifts_the_inference_off_the_robot.png)***图3.*** *计划块提升机器人的推理。留在本地的是传感和驱动，因此穿过网络的是一个相机帧加上其关节状态，以及一个动作向量返回。*

图 3. 计划块提升机器人的推理能力

仅靠更大的 GPU 是不够的。 Meta 的参考规划器在具有这些设置的一台 A100 上未经修改地运行，每个操作需要 81.8 秒；通过第 05 节中的模型级优化，需要 21.4 秒。我们的 81.8 秒比论文在 4090 上的 16 秒慢，因为我们按原样运行 Meta 发布的规划代码（fp32，800 个候选者 × 10 轮，两步地平线）；该论文的时间安排可能反映了不同的设置或精度。本文中的每个加速都是根据我们在相同硬件上自己的 81.8 秒基准进行测量的。速度更快，但手臂在动作之间仍然会停止。

第二步是在多个 GPU 之间分配负载。机会来自于注意到，在单个 CEM 细化回合中，可以独立计算并在回合继续之前收集。该论文将它们作为一个大批次在一个 GPU 上运行；没有什么需要它们留在一个 GPU 上。在我们的实施中，我们在 Anyscale 上使用一个 8 个 GPU 节点 (8× A100-40GB)。

**搜索分布在 Ray 集群上** — 2.86 秒/动作（测量，8× A100）； 0.86 秒，每步 3 轮

## 链接**03 · Ray 入门**

###链接**将Python变成集群程序的通用框架**

[Ray](https://docs.ray.io/en/latest/ray-core/walkthrough.html) 是一个开源框架，最初由加州大学伯克利分校的 RISELab 构建，现在由 Anyscale 维护，用于将普通 Python 从笔记本电脑扩展到集群，而无需将其重写为分布式系统。它公开了一小部分原语并保留了大部分顺序的代码结构。

### 链接**雷核心**

Ray Core 有两个重要的构建模块。 @ray.remote 函数成为一个 **任务**，安排在集群中的某个位置并返回一个 future。 @ray.remote 类成为一个 **actor**：一个固定在机器上的有状态工作线程，以及可选的 GPU，它可以在调用之间保持加载的模型权重。任务适合一次性并行工作；参与者适合一个付费加载一次 12 亿参数检查点的过程，然后回答许多廉价的请求。

### 链接**雷发球**

Ray Serve 位于 Ray Core 之上：@serve.deployment 声明足以让 Ray 管理副本池、路由请求和负载下的扩展。 Ray Core 回答了如何在许多工作线程上运行一个函数； Ray Serve 回答了如何将其公开为其他系统调用的服务，这是机器人控制循环所需的形状，每一步命中一次低延迟端点。

##链接**04·实施**

### 链接**两个 Ray Serve 部署，组成**

该设计是两个 Ray Serve 部署以及它们之间的一个手柄。 WorldModel 是 GPU 层：每个 GPU 一个副本，每个副本包含编码器和预测器（我们在 8 个 A100 上运行 8 个副本）。 Planner 是驱动程序：它运行十轮 CEM 循环，将每一轮分散到这些副本上，并为机器人在每个控制步骤调用一次的端点提供服务。以这种方式组合它们，而不是作为松散的 Ray Core Actor，将它们置于 Serve 的控制之下：放置、运行状况检查、重新启动和 KubeRay RayService 可以在不停机的情况下推出的声明性配置。下面的形状省略了内部结构；重要的是扇出位于何处。部署布局图见图 5。

**serve_app.py** — Ray Serve · 形状、细节已省略
```
from ray import serve
Import ray
from ray.serve.handle import DeploymentHandle

# The GPU tier. One replica per GPU, pinned, weights resident between calls.
@serve.deployment(
    num_replicas=8,  # one per GPU
    ray_actor_options={"num_gpus": 1},
    max_ongoing_requests=1,          # one shard at a time, so fan-out maps 1:1
)
class WorldModel:
    def __init__(self, checkpoint): ...        # paid once, when Serve starts it
    def encode(self, frame, proprio): ...      # the encoder is part of the model
    def score(self, ctx, actions): ...   # one shard, one GPU batch

# The driver. Holds a handle to the GPU tier and runs the search.
@serve.deployment(num_replicas=2)
@serve.ingress(app)
class Planner:
    def __init__(self, model: DeploymentHandle):
        self.model = model

    @app.post("/plan")
    async def plan(self, frame, proprio, goal_image):
        obs, goal = await asyncio.gather(      # encode once per control step
            self.model.encode.remote(frame, proprio),
            self.model.encode.remote(goal_image),
        )
  ctx = ray.put((obs, goal))  # once per plan, read from shared memory
        mean, std = init_distribution(horizon, action_dim)

        for _ in range(10):                    # CEM rounds: sequential, the floor
            cands = sample(mean, std, n=800)
            scores = await asyncio.gather(*[   # fan out one shard per replica
                self.model.score.remote(ctx, shard)
                for shard in np.array_split(cands, 8)
            ])                                 # gather before the round refits
            mean, std = refit(cands, scores, elite_frac=0.1)

        return {"action": mean[0].tolist()}    # first action only, then re-plan

app_builder = Planner.bind(WorldModel.bind(CHECKPOINT))
```
两种选择承载着设计。 GPU 层固定在 num_replicas=8 而不是自动缩放，因为副本计数在回合中发生变化的搜索具有不可预测的延迟，而关键是稳定的每步预算。 max_ongoing_requests=1 使每个副本一次获取一个分片，因此 8 路扇出为每个 GPU 提供一个分片，而不是在一个子集中对多个分片进行排队。在下面，每个副本仍然是 Ray Core actor，这就是权重保持驻留的原因；不同之处在于 Serve 拥有生命周期。

![图 5 Ray Serve on Anyscale 通过 DeploymentHandle 将面向机器人的 Planner 部署连接到温暖的 WorldModel 副本，其中一个模型](https://images.ctfassets.net/xjan103pcp94/2Rryj3kORaYUMKZbGnmmI0/9fd934b2fafedb46913144d268e14e2a/Figure_5_Ray_Ser ve_on_Anyscale_connects_the_robot-faceing_Planner_deployment_to_warm_WorldModel_replicas_through_a_Deployment.png)***图5:*** *Ray Serve on Anyscale 将面向机器人的 Planner 部署通过 DeploymentHandle 连接到温暖的 WorldModel 副本，其中一个模型*

图 5 Ray Serve on Anyscale 通过 DeploymentHandle 将面向机器人的 Planner 部署连接到热 WorldModel 副本，其中一个模型

**我们在构建它时学到了什么。 **三个细节决定了延迟。首先，观察和目标潜在变量 (2.8 MB) 使用 ray.put 按计划进入 Ray 的对象存储中一次；每个副本从共享内存中读取它们并将它们缓存在 GPU 上，因此每轮仅移出约 5 KB 的候选动作并将能量移回，并且 Ray 在一轮中的整个份额（扇出、聚集、重新调整）低于 10 毫秒。其次，当 max_ongoing_requests=1 时，Serve 的默认双选权路由器有时会在一个副本上放置两个分片，而另一个副本闲置，从而使该轮次加倍； Serve 的循环请求路由器将一轮的分片放置在连续的副本上，每个 GPU 一个（50 轮中零冲突）。第三，我们的服务副本进程在其环境中以 TORCHDYNAMO_DISABLE=1 启动，这会默默地将 torch.compile 变成无操作；在副本的构造函数中清除它可以恢复 1.35 倍的加速。

## 链接**05 · 结果**

### 链接**在 8× A100 上测量**

我们构建了上述设计，并使用第 01 节中的搜索设置（800 个候选 × 10 轮，保留 80，地平线 2）在一个具有 8 个 A100-40GB GPU 的 Anyscale 节点上对其进行了测量。锚点是 Meta 的参考规划器，在一台 A100 上以 fp32 运行未经修改：每个动作 81.8 秒。在添加 GPU 之前，我们在一个 GPU 上使模型本身更快：跨推出步骤的 KV 缓存（预测器是帧因果的，因此较早的帧永远不需要重新计算）、带有 FlashAttention 的 bf16 和 torch.compile。结果与参考能量匹配 (Pearson r = 0.9999)，并使一个 GPU 的每个动作耗时 21.4 秒，速度提高了 4 倍。

![图 6. 测量的每次操作计划时间](https://images.ctfassets.net/xjan103pcp94/1HObhsYqltV9tTxq161sK1/c8cd66020e487705829297b137563c19/Figure_6._Measured_planning_time_per_action.png)***图 6.*** *测量每个行动的计划时间。 Ray Serve 粉丝每回合超过 8 个 A100（2.86 秒，参考值的 29 倍）。在闭环测试（第 06 节）中，每步运行 3 轮（而不是 10 轮）达到了相同的精度，每个动作需要 0.86 秒，是参考值的 96 倍。*

图 6. 测量的每个操作的规划时间

然后是扇出。每轮的 800 个候选者分布在 W WorldModel 副本中，每个副本一个 GPU。 GPU 从 1 个增加到 8 个，计划时间从 21.4 秒缩短到 2.86 秒，加速了 7.5 倍。相同的种子在每个 GPU 计数上给出相同的计划，因此分片改变了搜索速度，但不会改变其答案。本文初稿中提出的延迟模型成立：在我们测量的单 GPU 回合（2.14 秒）上进行校准，它预测 8 个 GPU 时为 2.94 秒，而测量的为 2.86 秒。

一个 8-GPU 节点上的 A100-40GB 副本。测量点；该线是延迟模型。

**2.86 秒/8 个 A100 工作人员的动作**。这比 A100 快 7.5 倍，比 Meta 的参考规划器快 29 倍。

![图 7. 计划延迟与 GPU 数量的关系副本](https://images.ctfassets.net/xjan103pcp94/4pO1gOaQkRV99oC3sFaJZI/bb4b1ff81a4e092cd463800cb3f4f4d8/Figure_7._Plan_latency_vs._number_of_GPU_replicas.png)***图 7.*** *计划延迟与数量GPU 副本数，在 8× A100（点）上测量，对照在测量的单 GPU 回合上校准的延迟模型（线；超过 8 个 GPU 的虚线 = 投影）。*

模型：time(W) = 10 × ( r / effective(W) + 0.001s × (W − 1) )，其中 effective(W) = W / (1 + 0.008×(W−1))，r 是测量的单 GPU 回合，在 A100 上为 2.14 s。超过 8 个 GPU 后，曲线变平，因为每个 GPU 在 800 个候选者中所占的份额变小。较大的集群主要通过为同一层的更多机器人或更大的搜索提供服务而获得回报。

**有两件事仍未测量：**本地机器人和云区域之间的网络延迟，以及物理手臂上的性能（我们的闭环测试使用世界模型作为模拟器）。冷启动远离请求路径：副本在部署时大约 50 秒内加载和编译，然后才获取流量。以不同方式对候选进行批处理不会改变准确性：在 1、2、4 和 8 个 GPU 上的计划是相同的。

##链接**06·进一步优化**

### 链接**一旦搜索本身不再是瓶颈，该尝试什么**

一旦每一轮的速度达到 GPU 允许的速度，剩下的就是十个连续轮的链，下一个收益来自重组循环而不是添加 GPU。

#### 链接**A。非阻塞控制**

当机器人仍在执行步骤 *t* 时，开始计划步骤 *t*+1。这将计划延迟隐藏在执行时间之后，而不是增加它，这是控制器的更改，而不是模型的更改。

**测量。 **我们模拟了一只手臂，每次动作需要 1 秒，落地时有 4 毫米的执行误差。阻塞控制器每一步花费 1.86 秒（计划，然后移动）。非阻塞控制，根据世界模型对步骤 t 将落地的预测来规划步骤 t+1，每步花费 1.04 秒，即运动本身加上 40 毫秒。它达到了相同的最终精度，并且 12 步的剧集花费了 15.3 秒而不是 25.3 秒。

![图 8. 朝向 21.6 厘米目标的闭环事件离开](https://images.ctfassets.net/xjan103pcp94/1wgt2z0xXlplOL8aVQriLB/a03c590900577a0d84d4c2cd843d4a55/Figure_8._Closed-loop_episodes_toward_a_goal_21.6_cm_away.png)***图8.*** *以世界模型代替机器人，向 21.6 厘米外的目标进行闭环训练。左：每步 3 轮搜索在三分之一的规划时间内达到与 10 轮相同的精度。右：非阻塞控制将规划器从机器人的关键路径中移除。*

图 8. 朝向 21.6 厘米外目标的闭环事件

#### 链接**B。热启动 CEM**

后退控制会抛弃除第一个动作之外的所有内容。重新使用其余部分来播种下一步的分布，而不是新的高斯分布，让每个重新计划在不到十轮内收敛，从而缩小了顺序链并行性无法触及的范围。

**测量。 **在闭环测试中，每步 3 轮（8 个 A100 上为 0.86 秒）达到了与完整 10 轮（2.83 秒）相同的精度：两者都稳定在距离起始于 21.6 厘米远的目标约 4 厘米处。先前计划的热启动是有效的，但在这项任务中，新的 3 轮搜索效果同样好，因此收益来自于运行更少的轮次。每个任务需要多少轮值得调整。

#### 链接**C。车队级批处理**

适合一个机器人大小的 GPU 层在其请求之间处于空闲状态。在服务端点后面，同一层为一个车队提供服务，并且请求批处理可以将来自不同机器人的分片打包到一个 GPU 批次中，从而在多个臂上分摊相同的热 GPU。

#### 链接**D。模型压缩**

提取或量化预测器会缩小计算项本身，而与它分为多少个工作线程无关。它与分销相叠加，而不是与之竞争。

#### 链接**E。服务级别优化**

预测器逐步向前滚动，因此 LLM 服务已经依赖的内容得以延续：跨滚动步骤的 KV 缓存、预填充和解码分解、连续批处理。它们在同一服务部署内从不同方向缩小相同的计算项。

**实施的。 **跨推出步骤的 KV 缓存与 bf16、FlashAttention 和 torch.compile 一起是测量系统的一部分。它在单个 GPU 上提供 4× 并将参考能量匹配到 r = 0.9999。

## 链接**07·要点**

十六秒不是实现缺陷。它源自深思熟虑的架构选择：JEPA 模型预测状态而不是操作，因此必须在推理时搜索操作而不是读取策略头。这与贸易代理系统对许多候选人进行抽样并对他们进行评分时所做的相同，并且它具有相同的好处，即无需重新培训即可指向新目标的系统。

这四种设置使交易具体化。手写的策略购买毫秒级的操作并在特定任务的工程中为其付费。 V-JEPA2-AC 以这样的速度换取了一个可以接受您可以拍摄的任何目标的系统。将搜索转移到集群可以在不放弃通用性的情况下恢复速度，并且在基础设施中而不是在模型中进行。在 8 个 A100 的一个节点上进行测量，Ray Serve 将每个动作的完整搜索时间从 82 秒缩短到 2.9 秒，其中分布完成大部分工作，而 Ray 每轮增加的时间不到 10 毫秒。十个连续的回合设定了更多硬件无法移动的底线。每步攻击该楼层的回合数减少到 0.86 秒，并且非阻塞控制隐藏了手臂自身运动背后的剩余内容。
