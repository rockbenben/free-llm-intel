# 用 KubeRay 在 Kubernetes 上大规模运行 Ray

作者 [Nai-Jui Yeh](https://www.anyscale.com/blog?author=nai-jui-yeh)、[Chun-Hao Wan](https://www.anyscale.com/blog?author=chun-hao-wan) 和 [Philip Wang](https://www.anyscale.com/blog?author=philip-wang) | 2026 年 10 月 15 日

## Link什么是 KubeRay

Ray 是一个开源框架，用于把 Python 和 AI 工作负载扩展到许多台机器上。从分布式训练到在线服务，它都通过同一个 Python API 来处理，所以用户可以把代码写一次，然后跑在笔记本上，或者跑在一个一千节点的集群上。

而 Kubernetes 是大多数组织已经在运行其基础设施的地方。GPU、配额、访问控制、网络和监控都在那里管理。采用 Ray 的团队，很少希望 Kubernetes 之外再多一个集群管理器。他们希望 Ray 跑在自己已有的 Kubernetes 上。

难点在于 Kubernetes 只理解它自己的原生资源，比如 Pods、Services 和 Jobs。它没有 Ray 集群、Ray job 或 Ray Serve 应用的概念。因此直接在 Kubernetes 上运行 Ray，就意味着要自己写胶水：为 head 和 workers 写 Deployments、为 head 写一个 Service、写提交 jobs 并等待它们的脚本，以及自己写逻辑来扩缩 workers 或从故障中恢复。每个团队最后都在重搭同一套管道。

KubeRay 补上了这个缺口。它是一个开源的 Kubernetes operator，把 Ray 带入 Kubernetes 生态，为 Ray 工作负载提供 Kubernetes 原生的生命周期管理、自动扩缩容、调度、可靠性和可观测性。KubeRay 是今天在 Kubernetes 上运行 Ray 的标准方式，也是主要云厂商托管 Ray 产品的底座。

KubeRay 引入了三种自定义资源：RayCluster 用于长期运行的 Ray 集群，RayJob 用于自带临时集群的单个 job，RayService 用于 Ray Serve 应用。我们在下文的架构章节中说明这些资源如何工作。

### LinkKubeRay 之前与之后

通用 Kubernetes 起初或许能承载 Ray 运行所需的基础设施，却难以理解 Ray 本身，包括，于是每个平台团队都不得不一遍遍手写同样的 deployments、services、提交脚本和恢复逻辑去填补那个缺口。KubeRay 针对下列每一项任务，用一个 Kubernetes 原生资源取代了那些手工工作。

| **任务** | **通用 Kubernetes** | **KubeRay** |
| --- | --- | --- |
| 启动一个 Ray 集群 | 自己为 head 和 workers 手写 Deployments、为 head 写一个 Service，并亲自让它们保持同步 | 定义一个 RayCluster。operator 会创建并管理 head Pod、head Service 和 worker Pods |
| 运行批处理 job | 写脚本来提交 job、轮询完成状态，并在事后拆掉集群 | 定义一个 RayJob。KubeRay 创建一个专用的 RayCluster、提交 job，并在 job 结束时清理掉它 |
| 服务一个模型 | 为 Ray Serve 手工搭 Deployment 和 Service，再加上你自己的健康检查与发布逻辑 | 定义一个 RayService。KubeRay 让 Serve 应用在集群和 head 节点故障时保持可用，并支持零停机升级 |
| 随需求扩缩容 | 依赖 Kubernetes Horizontal Pod Autoscaler，而它看不到 Ray 的 tasks、actors 或 placement groups | 具备 Ray 感知的自动扩缩容，依据待处理 tasks、actors 和 placement groups 来扩缩 worker groups |
| 从 head 节点故障中恢复 | 自己写检测故障并重建集群状态的逻辑 | Global Control Service (GCS) 容错在 Ray Serve 应用继续运行的同时自动恢复集群元数据 |
| 监控与运维 | 自建工具来呈现 Ray 特有的状态 | Kubernetes 原生的 status 与 Events，再加上 kubectl ray 带来熟悉的 CLI 体验 |

## LinkKubeRay 在 Ray 与 Kubernetes 之间处于什么位置

![KubeRay 在 Ray 与 Kubernetes 之间处于什么位置](https://images.ctfassets.net/xjan103pcp94/7BB6IXXE9fqX6LXzQ5w2E/d639008de4b753381dd4d3eb1baeae7f/Where_KubeRay_fits_between_Ray_and_Kubernetes.png)

KubeRay 在 Ray 与 Kubernetes 之间处于什么位置

KubeRay 位于 Kubernetes 与 Ray 之间，而且它不取代其中任何一个调度器。Kubernetes 把 Pods 调度到节点上，Ray 则把 tasks 和 actors 调度到这些 Pods 内部的 CPU 和 GPU 上。KubeRay 把两边桥接起来：它把一个 RayCluster spec 变成 Pods，并把 Ray 的状态作为 status 字段和 events 回报给 Kubernetes。

这套分层也把两个角色的职责干净地切开了。平台团队工作在 Kubernetes 层和 operator 层：他们安装一次 KubeRay，然后用自己已在使用的工具管理节点池、配额、访问控制和监控。Ray 用户，例如 ML 工程师和数据科学家，工作在 Ray 层和应用层：他们编写 Ray 代码，并在 KubeRay 创建的自定义资源（RayCluster、RayJob 或 RayService）之上执行这些代码。

## LinkKubeRay 提供什么

![KubeRay Operator](https://images.ctfassets.net/xjan103pcp94/6v5XJKikUHPH5BmAOabtMt/3fc665ee2890d82934c123e7b5a77b14/KubeRay_Operator.png)

KubeRay Operator

KubeRay 是一个 Kubernetes operator，每种自定义资源对应一个 controller。RayCluster 是基本构件：operator 把它变成一个 head Pod、一个 head Service 和若干 worker Pods。RayJob 和 RayService 各自拥有一个 RayCluster，并补上各自工作负载需要的东西：RayJob 加的是一个 submitter，RayService 加的是 Serve 应用和一个 Serve Service。

### Link核心特性

#### LinkRayCluster

- **具备 Ray 感知的自动扩缩容。** 依据工作负载需求自动扩缩 worker groups，包括待处理 tasks、actors 和 placement groups。
- **Global Control Service (GCS) 容错。** 在 head 节点故障后恢复 Ray 集群元数据，同时让 Ray Serve 应用继续运行。
- **异构计算。** 在同一个 RayCluster 里运行具有不同 CPU 与加速器配置的 worker groups。

#### LinkRayJob

- **临时集群：** 为每个 job 创建一个专用 RayCluster，并在 job 结束后清理掉它。
- **多种提交方式：** 通过 Kubernetes Jobs、HTTP、sidecars 或交互式模式提交 jobs。
- **生命周期管理：** 依据 job 的结果配置重试、截止时间和清理策略。

#### LinkRayService

- **Kubernetes 原生的 Ray Serve：** 把 Ray Serve 应用作为你 Kubernetes 工作负载的一部分来定义和管理。
- **高可用：** 让 Ray Serve 应用在集群和 head 节点故障期间保持可用。
- **零停机升级：** 在不打断服务流量的情况下升级 Ray 应用与集群，支持蓝绿升级和增量升级。

#### LinkKubernetes 调度

- **Kueue 与 MultiKueue：** 把 Ray 工作负载接入 Kubernetes 资源配额与多集群调度。
- **Gang 调度：** 支持借助 Kubernetes Workload API、Volcano、YuniKorn、scheduler-plugins 和 NVIDIA KAI Scheduler 实现 gang 调度。
- **资源与标签感知的调度：** 把 Kubernetes 资源和标签暴露给 Ray，用于基于资源和标签的调度。

#### Link安全

- **Ray token 认证：** 用基于 token 的认证来保护 Ray 集群。
- **Kubernetes RBAC 认证：** 使用已有的 Kubernetes RBAC 策略来控制对 Ray 集群的访问。
- **mTLS 与 NetworkPolicy：** 加密 Ray 的 Pod-to-Pod 流量，并用 Kubernetes NetworkPolicies 隔离 Ray 集群。

#### Link可观测性

- **指标与仪表盘：** 用 Prometheus 和 Grafana 监控 Ray 工作负载与 KubeRay。
- **Kubernetes 原生的 status 与 events：** 通过 Kubernetes 的 status 和 Events 跟踪工作负载生命周期、排查 Ray 资源问题。
- **History Server：** 把 Ray 的事件与日志保存在对象存储中，并在集群已被删除之后仍然可以查看它们。

#### Link工具链

- **kubectl ray：** 用熟悉的命令行体验，简化管理 Kubernetes 上的 Ray 集群。
- **KubeRay API Server：** 为平台和用户界面提供简化的 API 来管理 KubeRay 资源。

## Link如何部署 KubeRay

KubeRay 可在任何 Kubernetes 集群上工作。先安装 KubeRay operator，然后用 Kubernetes 原生资源创建一个 Ray 工作负载。

**1. 安装 KubeRay**

按照 [KubeRay 入门指南](https://docs.ray.io/en/latest/cluster/kubernetes/getting-started.html) 把该 operator 安装到你的 Kubernetes 集群上。KubeRay 已在多个托管 Kubernetes 服务上通过测试，包括 **Amazon EKS、Google Kubernetes Engine (GKE) 和 Azure Kubernetes Service (AKS)**。

**2. 选择你的工作负载**

KubeRay 为运行 Ray 工作负载提供这些自定义资源：

- **RayCluster：** 为开发与原型验证运行一个 Ray 集群。
- **RayJob：** 用专用 RayCluster 运行批处理工作负载，集群的创建与清理自动完成。
- **RayService：** 部署并管理 Ray Serve 应用，具备高可用与零停机升级。
- **RayCronJob：** 使用 cron 表达式按周期重复运行 RayJob。

**3. 用 Kubernetes 部署**

用 KubeRay 部署一个 Ray 工作负载，就像 apply 一个 Kubernetes 自定义资源那样简单。

例如，一个 `RayJob` 会运行批处理训练工作负载，并管理该 job 所使用的 Ray 集群。KubeRay 创建 RayCluster、等待它就绪、提交训练 job，并可以在 job 结束时清理集群。

下面是一个在 Kubernetes 上用 CPU 对 Fashion MNIST 数据集训练 PyTorch 模型的例子，展示 KubeRay 创建 RayCluster、运行训练工作负载、跟踪其完成，以及管理集群生命周期。

训练代码使用 [Ray Train](https://docs.ray.io/en/latest/train/train.html)，而 KubeRay 用一个 `RayJob` 在 Kubernetes 上运行并管理它。

```
kubectl apply -f https://raw.githubusercontent.com/ray-project/kuberay/v1.7.0/ray-operator/config/samples/pytorch-mnist/ray-job.pytorch-mnist.yaml
```
