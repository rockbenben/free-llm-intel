# Ray Serve 全新 Grafana 仪表盘：实现前所未有的调试能力

作者：Abrar Sheikh、Akshay Malik 和 Alex Yang | 2026 年 2 月 16 日

从 **Ray v2.54+** 开始，Anyscale 随附一个**全新的 Ray Serve Grafana 仪表盘**，**仅在 Anyscale 平台提供**。它取代旧版 Serve 仪表盘，专为真实的生产调试而设计——就是那种要求你在几分钟（而不是几小时）内回答*"这事为什么偏偏现在发生？"*和*"系统到底在哪一环崩坏？"*的调试。

本文走查一个真实感十足的线上事故，展示新仪表盘如何从根本上改变调试工作流。

## **事故：一次例行部署后延迟飙升**

一个团队上线了新模型版本。QPS 平稳，错误率平稳。但**某个单个应用的 P99 延迟几乎翻倍**。

*端到端 HTTP 延迟仪表盘：随时间变化的 P50、P90、P99 响应时间，app1 的 P99 峰值接近 1.9 秒，P50 平均约 700–727 ms。*

用旧仪表盘，你能看到的只是"延迟变差了"——此外几乎没有别的。剩下的只有猜：

- 是模型执行时间吗？
- 路由器排队？
- 自动扩缩容滞后？
- 滚动发布期间的 replica 健康？
- Proxy 不稳定？

有了这个 Anyscale 专属的新仪表盘，这种歧义消失了。

## **时刻 1："这是部署问题还是运行时问题？"**

**Application Status Timeline** 与 **Deployment Status Timeline** 立刻给出答案。

你可以看到 deployment 的状态转移——HEALTHY → UPDATING → HEALTHY——与延迟回退直接对齐。这取代了过去只有统计数字的视图：那时生命周期变化是不可见的，除非你去翻日志。

*app1 Ranker 服务的 deployment 状态时间线：replica 数在 15:00 左右从 6 降到 3，15:05 前又扩回 6。*

接着，**Replica Health Heatmap** 展示在受影响窗口内 replica 是否真正健康——不只是数量，而是*随时间变化的部分健康度*。在本例中，它暴露了此前无人察觉的滚动升级不稳定。

*app1 Ranker 服务的 replica 健康热力图：随时间的性能评分，健康度在 15:00–15:07 左右降到黄色，15:10 前恢复到接近 100% 的绿色。*

**为何重要：**
调试的第一步从"猜测哪一层"变成了"确认生命周期状态"。

## **时刻 2："延迟到底是在哪里引入的？"**

新仪表盘把请求路径拆成三层，使其显式化：

- **DeploymentHandle Request QPS**（客户端入口）
- **Router Request QPS**（路由与排队）
- **Replica Request QPS**（用户代码执行）

*监控仪表盘：app1 Ranker 的 DeploymentHandle、Router 与 Replica 请求 QPS，流量在 15:05 左右跌到约 60 req/s，随后恢复到约 70–75 req/s。*

这些指标与 **Processing Latency、Router Fulfillment Latency** 和 **Queued Requests at Router** 配对呈现。

*app1 Ranker 的处理与路由完成延迟仪表盘：P50、P90、P99 指标，处理延迟稳定在约 1 秒，路由延迟在 15:05 左右飙升后回落基线。*

*app1 Ranker 监控仪表盘：排队与被指派请求、处理负载、调度任务与退避事件。处理峰值接近 79 个请求，负载均衡质量一度超过 2.5，随后稳定在约 2.0。*

在这次事故中，模式一目了然：

- 调度任务进入 backoff 的次数激增
- 路由器排队请求数激增
- 路由完成延迟激增
- Replica 处理延迟保持平稳

**结论：** 回退不在模型代码里——在路由与排队。

**为何重要：**
过去排队延迟与执行时间混为一谈。现在你能用数据证明瓶颈在哪。

## **时刻 3："为什么自动扩缩容没有解决它？"**

**Target vs. Actual Replicas Over Time** 面板显示：期望副本数在爬升，实际副本数却落在后面。

*app1 Ranker 的期望 vs 实际副本时间线：desired replicas 约 25，target 为 10，实际副本在 15:00 附近短暂跌破 10，随后回到目标水平。*

紧挨着的 **Blocked by Min/Max Limits** 揭示根因：autoscaler 想要更多副本，但撞上了 max_replicas。

*app1 Ranker 的 min/max 限制阻塞图：副本增量被钳制在约 15，15:00 附近短暂下探至 10–12，随后回到 15 的上限。*

要排除供给缓慢的可能，检查 **Replica Startup (P99)**。若它偏高，延迟来自启动准备（bootstrapping）；若不高，则是策略约束。

*app1 Ranker 的 replica 启动时间（P99）指标：99 分位为 1.98 分钟。*

**为何重要：**
你能区分*"我们撞到了扩缩上限"*与*"系统来不及增加容量"*——无需靠猜、无需翻日志。

## **从 Grafana 到 Anyscale 日志的无缝跳转（Ray 2.55，Anyscale 专属）**

从 Ray 2.55 开始，Anyscale 客户可以从 Services Grafana 仪表盘的任意面板（例如错误 QPS 或延迟图）直接跳转到 Anyscale Log Viewer，且时间范围与应用上下文已按完全相同的条件预过滤。只需一次点击，用户就被重定向到合适的 Anyscale Console 视图——workspace 或 service——日志自动按开始时间、结束时间、application、deployment 与 replica 过滤，实现精准圈定。默认视图包含 controller、replica 与 worker 日志，大幅缩短把指标尖峰与底层错误对应起来所需的时间。这种指标到日志的紧密集成消除了上下文切换与手工过滤，显著改善调试工作流，随 Ray 2.55 发布启用。

*按 Deployment 划分的错误 QPS 仪表盘：default MainRouter 与 ErrorGenerator 在 09:02 左右飙到 0.5 req/s，错误率持续偏高。*

*Anyscale Serve 可观测性仪表盘日志：default_MainRouter 与 default_ErrorGenerator 中的 RuntimeError "Intentional exception!"，500 POST 请求失败与完整 Python traceback。*

## **为什么它有生产级质感**

生产系统不会只在一个地方坏，它们跨层地坏。新仪表盘反映了这一现实：

- 生命周期状态是一等公民时间序列，不再埋在日志里
- 请求路径端到端可观测
- 自动扩缩决策不仅可见，而且可解释
- Serve 内部机制与用户代码可以用数据清晰切分

这就是运维成熟度的样子。系统不只告诉你*有*东西不对——它告诉你*哪里*不对、*为什么*。如果你在生产运行 Ray Serve，这个仪表盘就是"猜"与"知道"之间的差距。把 Ray 升级到 2.54，在 Anyscale Workspace 与 Services 上体验这些新增的可观测性特性。
