# 推出 Anyscale KubeRay Connect：全力押注 Kubernetes

作者：Elizabeth Hu、Philip Wang、Pratik Padalia、Chris Fellowes 和 Sridhar Konduri | 2026 年 8 月 25 日

如果你在 Kubernetes 上运行 Ray，大概率早已做出了选择：operator 用 [KubeRay](https://github.com/ray-project/kuberay)，排队用 Kueue 或 KAI，交付用 Argo CD，策略校验用 Kyverno。这套栈可用，团队熟悉它，你的平台也是围绕它搭建的。

在此之前，采用 Anyscale Platform 意味着抛弃这些选择。[Anyscale Operator](https://github.com/anyscale/helm-charts) 直接创建和管理 Pod，并不理解 KubeRay CRD，因此迁移到该平台意味着重写你的作业规格、GitOps 仓库以及围绕它们的工具链。

今天我们推出处于私有预览阶段的 **Anyscale KubeRay Connect**。它消除了这一取舍：保留你已经在运行的 KubeRay 栈，在其之上有 Anyscale 的可观测性与编排能力。你的 KubeRay Operator 照旧精确地 reconcile 你的 CR，你也继续以现有方式提交工作负载。

## 为什么需要 Anyscale KubeRay Connect

Anyscale 与 KubeRay 生态之间的鸿沟是双向的。KubeRay Connect 从两个方向将其弥合。

### 无需迁移的接入

没有迁移，没有 CR 重写。此前，由于平台不支持 CRD，你的 `RayJob`、`RayService` 和 `RayCluster` 规格无法进入 Anyscale，团队必须先把一切翻译成 Anyscale YAML。

现在，工程师可以让 Anyscale Connector 指向一个已经在运行的 KubeRay 集群，Anyscale 便把可观测性、调度和生命周期管理直接叠加到既有的 CR 上。安装只需一个比 Anyscale Operator 轻量得多的 Helm chart。

### 与 Kubernetes 生态互操作

KubeRay Connect 不直接驱动 Pod，而是构建在 KubeRay CRD 之上，把状态 reconcile 交给 KubeRay Operator——后者遵循标准的 Kubernetes 控制器架构。

这一区别之所以重要，是因为有海量工具构建在 [CustomResourceDefinition（CRD）与自定义控制器](https://kubernetes.io/docs/concepts/workloads/controllers/)这些 Kubernetes 原生原语之上。Kueue 可与 Deployments 和 KubeRay CRD 集成；Argo CD 和 Kyverno 同样如此。在 KubeRay Connect 之下，这一切继续可用。

## 它是什么

Anyscale 不创建 Pod，而是在准入（admission）阶段修改你已有的 KubeRay 规格，注入轻量级数据面 sidecar 来支撑可观测性。产品分为三个层级，我们按顺序发布。Observe（观测）是入口，也是刻意设计为摩擦最小的层级。

| **层级** | **功能** | **状态** |
| --- | --- | --- |
| **Observe** | Anyscale 自动采集全栈遥测数据——从硬件一直到你的 Ray 工作负载——并在 Anyscale 控制台中呈现：Ray 仪表盘、日志、事件和指标。 | 私有预览 |
| **Orchestrate** | Anyscale 的智能调度层利用 Observe 提供的可用性与健康信号，或你自定义的调度策略，在多个集群间放置工作负载，最大化利用率。 | 私有预览 |
| **Optimize** | 对 Ray 及 Ray 数据面参数进行性价比调优。 | 即将推出 |

## 架构速览

Anyscale KubeRay Connect 会在你的数据面安装三个 Anyscale 组件。

**Anyscale Connector** 负责控制操作：在 Anyscale Platform 与你的集群之间同步状态，并运行一个在准入时修补 KubeRay CR 的 MutatingWebhook。它通过 Helm 安装，是一个 Deployment，目前以单 Pod 运行。

**Cluster Telemetry Gateway** 负责聚合来自你 Ray 工作负载的日志和指标，并发送到 Anyscale 控制面。它是一个 OpenTelemetry Collector，随少量 sidecar 部署。

**Observability API** 以 Deployment 运行，为 Anyscale 控制台提供其读取的遥测接口。

把控制与遥测分离是刻意的选择。第一个好处是容错——Connector 只在 Pod 生命周期开始时（修改规格时）需要，之后即使崩溃也不影响已在流动的指标。反之亦然——遥测故障不影响新工作负载的准入。这一分离还带来安全性（身份拆分可防止作恶者）与可扩展性收益（并发操作各自独立触发 Kubernetes 自动扩缩容）。

这一设计带来四个特性：

- **仅出站（Egress-only）。** 每条连接都由你的数据面发起。Anyscale 控制面无需、也永远不需要进入你集群的入站通路。
- **Kubernetes 原生认证。** Connector 使用投影服务账号的 OIDC token 认证，并用集群自身的 JWKS 验证，无需在链路中使用 Anyscale API key。只要 OIDC issuer 可被我们访问，任何合规集群均可用。
- **抵御控制面故障。** 即使 Anyscale 控制面不可用，Ray 工作负载仍会继续运行并推进。
- **薄壳（thin-shim）Connector。** 控制逻辑从控制面拉取而非写死在 chart 里，因此修复和改进无需你执行 Helm upgrade 即可生效。

mutating webhook **默认 fail-closed**。若提交 KubeRay CR 时 Connector 不可用，CR 会被拒绝，而不是在未接入遥测的状态下准入。我们选择 fail-closed 而非 fail-open，以避免静默准入状态不完整的工作负载。该行为可配置。

如果 Connector 在工作负载*已准入之后*失败，遥测仍会流动，因为 Gateway 与之独立。你会丢失的是作业状态：向平台上报相位转换的正是 Connector，因此作业从 pending 到 running 到 terminated 的变化要等 Connector 恢复后才会出现在控制台。工作负载本身不受影响。

## 第一天就能获得什么

### 可观测性

一旦遥测网关开始流动，你的 KubeRay 工作负载即可开箱获得 Anyscale 可观测性，无论你通过 `kubectl apply` 还是 Anyscale API 提交都同样有效：

- **Ray 工作负载仪表盘** —— 为 Ray 量身打造的 Ray Data、Ray Train 和集群视图
- **任务与 actor 仪表盘**，在集群终止后仍然保留
- **经 Loki 的聚合日志**，外加按工作负载的独立日志
- **工作区、服务与作业事件**，包含 autoscaler 日志
- **Telescope**，新增横跨你机群、从硬件到 Ray 应用的全栈视图

最后一点值得强调：Telescope 现在能把硬件层信号（DCGM）、Kubernetes 基础设施事件一路关联到你的 Ray 应用——因此一个变慢的训练作业与其下方故障的 GPU 会出现在同一个地方。我们在最近的全栈可观测性[文章](https://www.anyscale.com/blog/anyscale-gpu-health-observability)中更详细地介绍了这项工作。

这些是 Anyscale 内置于平台的可观测性工具，现在几分钟内就能用在 KubeRay 工作负载上。

### 编排

预览版还涵盖 Kubernetes 上的工作负载提交、调度与状态跟踪：

- **直接提交 KubeRay CR** 到集群：`kubectl apply -f job.yaml`，或通过平台：`anyscale job submit -f job.yaml`
- 在 Anyscale 控制台**跟踪作业进度**、状态与重试
- **用 Kueue 排队**，把 Kueue 配置应用到你的 CR 上
- 用 Anyscale Scheduler 排队，支持 Kueue 直通或叠加模式——*即将推出*
