# 离线批量推理：Ray、Apache Spark 与 SageMaker 对比

作者：Amog Kamsetty、Eric Liang 和 Jules S. Damji | 2023 年 5 月 4 日

## TL;DR

随着越来越多公司使用大规模[机器学习（ML）模型](https://www.anyscale.com/machine-learning)做训练与评估，离线批量推理成为必不可少的负载。它伴随一系列挑战：管理计算基础设施；优化各类异构资源的利用；把数据从存储搬运到硬件加速器。应对这些挑战，Ray 表现出色——它能协调由多样资源组成的集群，让负载的特定资源需求得到更好的利用。

本文中，我们对比三种离线批量推理方案：AWS [SageMaker Batch Transform](https://docs.aws.amazon.com/sagemaker/latest/dg/batch-transform.html)、[Apache Spark](https://spark.apache.org/) 与 [Ray Data](https://docs.ray.io/en/latest/data/dataset.html)。实验表明，在离线图像分类任务上，Ray Data 最比比 SageMaker Batch Transform **快 17 倍**、比 Spark **快 2 倍**。Ray Data 也能有效扩展到 TB 级数据集。这些基准的代码已公开，见[这里](https://github.com/amogkam/batch-inference-benchmarks)。

## 引言

*图 1. 通用并行批处理架构*

离线批量推理是许多 AI 产品的关键负载，随着预训练基础模型的使用增长尤其如此。它看上去是个简单问题：给定一个训练好的模型和一个数据集，为每个数据点得到模型预测。

但要在规模下做好这件事挑战很多：

- **挑战 1：** 管理计算基础设施与云集群，尤其是当需要使用由不同实例类型构成的*异构集群*来最大化吞吐时。
- **挑战 2：** 并行化数据处理，并在任意时刻利用集群中所有资源（CPU 与 GPU）。
- **挑战 3：** 在云存储、用于预处理的 CPU 内存与用于模型推理的 GPU 显存之间高效搬运数据——对图像、文本这类非结构化数据尤其如此。这同时影响性能与开发者迭代速度。
- **挑战 4：** 在规模化工作的同时，还能轻松迭代开发的用户体验。

### 业界对离线批量推理有什么推荐？

业界尚未形成标准方案。[看起来每位 ML 从业者都有自己的心头好。](https://twitter.com/benhamner/status/1605730034450169857)

*推文截图*

我们看到三类方案试图解决上述挑战，但只有第三类把挑战全部解决。

- **批处理服务：** AWS、GCP、Azure 等云厂商提供批处理服务替你管理计算基础设施。[Modal Labs](https://modal.com/) 等新产品在云厂商之上再加一层用户体验，抽象掉更多复杂性。无论选哪个服务，流程都一样：你提供代码，服务在集群每个节点上运行它。然而，基础设施管理虽必要（挑战 #1），却远远不够。这类服务有局限——缺乏能应对挑战 #2、#3、#4 的软件库——因此只适合能自己编写优化批量推理代码的老手。
- **在线推理方案：** [Bento ML](https://www.bentoml.com/) 或 [Ray Serve](https://docs.ray.io/en/latest/serve/index.html) 等方案提供 API，让高性能推理代码易写，也能屏蔽基础设施复杂性。但它们是为在线推理而非离线批量推理设计的——这是需求不同的两个问题。这些方案在离线场景下往往表现不佳，以至于 [Bento ML 等推理服务商选择与 Apache Spark 集成](https://modelserving.com/blog/unifying-real-time-and-batch-inference-with-bentoml-and-spark)来做离线推理。
- **分布式数据系统：** 这类方案天生为海量数据设计，更适合应对上面列出的全部挑战。它们把大数据集拆成合理的批次处理，并能高效地把给定函数（即模型）映射到数据集上，从实质上处理大规模离线批量推理的挑战。代表有 [Apache Spark](https://spark.apache.org/) 与 [Ray Data](https://docs.ray.io/en/latest/data/dataset.html)。

最终我们观察到：对现代深度学习应用，Ray Data 是离线批量推理在性能与用户体验上最佳的实用方案。

我们做了以下对比与实验来佐证上述观察：

- 在图像分类用例上比较 AWS SageMaker Batch Transform、Apache Spark 与 Ray Data 的性能和开发体验
- 把 Ray Data 批量推理扩展到 10 TB，展示 90% 以上的 GPU 利用率

## 图像分类：SageMaker Batch Transform vs. Apache Spark vs. Ray Data

我们在离线设置下运行 [MLPerf Inference Benchmark](https://arxiv.org/abs/1911.02549) 套件中的图像分类任务。该基准使用 [ImageNet 2012 数据集](https://image-net.org/challenges/LSVRC/2012/2012-downloads.php#Images)的图像与预训练的 [PyTorch ResNet50 模型](https://pytorch.org/vision/main/models/generated/torchvision.models.resnet50.html)。

我们对完整的端到端批量推理负载计时。图像以 parquet 格式存放在公开 S3 桶中，负载包含三步：

- **从 S3 读取图像**
- **简单 CPU 预处理（缩放、裁剪、归一化）**
- **GPU 上的模型推理**

所有 Ray 实验在 Anyscale 上运行；Spark 实验在 Databricks runtime v12.0（Apache Spark 3.3.1）上运行。完整配置细节见[仓库](https://github.com/amogkam/batch-inference-benchmarks)。

其中 Spark 用了两种设置：

- **单集群：** CPU 预处理与 GPU 推理在同一集群完成。我们试了 PySpark Pandas UDF API 的两个版本：[Series-based 与 Iterator-based](https://spark.apache.org/docs/3.1.2/api/python/reference/api/pyspark.sql.functions.pandas_udf.html#pyspark.sql.functions.pandas_udf)。
- **多集群：** CPU 预处理在一个集群完成，预处理后的数据存入共享文件系统，GPU 推理在另一个集群进行。

上述实验的全部源码见[这里](https://github.com/amogkam/batch-inference-benchmarks)，还包括我们尝试过的其他各种配置的细节。

## 用 SageMaker Batch Transform 做批量推理

可以看到，无论吞吐还是成本，SageMaker Batch Transform 都不适合批量推理。

SageMaker 在一定程度上处理了**挑战 #1**、屏蔽了计算基础设施管理，但并没有解决其余挑战。

吞吐低的主因是：SageMaker Batch Transform 虽然自称是[大数据集批量推理方案](https://docs.aws.amazon.com/sagemaker/latest/dg/batch-transform.html)，底层却使用与在线服务系统相同的架构。它启动一个 HTTP 服务器，把你的模型部署成 endpoint，然后为每张图像向服务器单独发一个请求。

SageMaker 也不支持跨[多个文件](https://docs.aws.amazon.com/sagemaker/latest/dg/batch-transform.html)做 batching；即便你预先打包好数据，单请求的 payload 上限是 100MB，远不够把 GPU 喂饱。

在开发速度方面，跑这些基准时我们还遇到一些 SageMaker 的额外麻烦：每跑一次脚本都要拉起新集群，以及难以解读的堆栈跟踪，都拖慢了迭代。

在线推理方案自有其位置，但它们的额外开销、无法通过最大化 batch size 与有效流水线数据来充分利用集群资源和 GPU，使其在离线批量推理上效率极低。

## Spark 与 Ray 批量推理对比

显然，如前所见，把在线推理方案硬塞进离线场景不是正确路线。来比较两个分布式数据系统方案：Spark 与 Ray Data。

我们看到 Ray Data 的吞吐比 Spark 快 **2 倍**。逐项看两者在前面挑战下的表现：

### **挑战 #2：CPU 与 GPU 混合负载**

深度学习负载同时涉及 *CPU 和 GPU 计算*。要取得最优并行，集群中所有 CPU 与 GPU 在任何时刻都应被用满。然而这正是 Spark 调度的局限：所有 stage 被融合在一起，不管资源需求如何。也就是说在单集群设置下，总并行度受 GPU 数量限制，CPU 被浪费。同时，在读取与预处理步骤期间 GPU 完全空闲。

改用独立的 CPU 集群与 GPU 集群时，数据需要在 stage 之间持久化并来回搬运。总体看，对这类 CPU+GPU 负载，Spark 没有充分解决**挑战 #2**，无法并发利用集群所有资源。我们尝试过用 Spark 的 stage 级调度特性解决这个问题，但[未成功](https://github.com/amogkam/batch-inference-benchmarks/tree/main/spark#stage-level-scheduling)。

*图 2. Ray Data 如何高效流水线化并优化硬件利用：CPU/GPU。*

而 Ray Data 能独立伸缩 CPU 预处理与 GPU 推理步骤。它还让数据*在这些阶段之间流式传递*，提升 CPU 与 GPU 利用率、减少 OOM，并提供细粒度资源分配用于[自动扩缩与管理](https://docs.ray.io/en/latest/serve/scaling-and-resource-allocation.html#scaling-and-resource-allocation)。

### 挑战 #3：大型多维张量

深度学习负载常要处理图像、音频、视频这类复杂数据类型，它们由多维[数组](https://numpy.org/doc/stable/reference/generated/numpy.ndarray.html)表示。对这些数据类型的一等支持，对性能与开发体验不可或缺。Ray Data 原生把 Numpy 批量格式作为一等公民，不需要 Pandas——这更适合深度学习，带来更高性能与内存效率，[此前的基准已经展示过](https://www.anyscale.com/blog/ray-2-2-improved-developer-experience-performance-and-stability)。

### 挑战 #4：Ray 是 Python 原生的

另一个根本差异是 Ray 原生属于 Python，而 Spark 不是，这也影响性能。我们跑了一个套用 `time.sleep(1)` UDF 的微基准。令人意外的是，跑这个 UDF 花了 [80 秒](https://github.com/amogkam/batch-inference-benchmarks/tree/main/spark#microbenchmark)——我们认为源自 JVM<>Pyarrow 的开销！同样的微基准在 Ray Data 上只要[不到 5 秒](https://github.com/amogkam/batch-inference-benchmarks/blob/main/ray/README.md)。

更不用说这让 Spark 开发更难：调试时的推荐做法是把调试信息放进[输出的 pandas DataFrame，而不是用 print](https://stackoverflow.com/a/57175768)。

即使扩展到更大的 300GB 数据集（4 节点、16 GPU），这些性能差异依然成立：

*图 3. Spark 与 Ray 方案在 300GB 批量推理上的吞吐差异。*

大数据处理系统虽是离线推理的最佳方案类别，但对深度学习负载，Ray Data 胜过 Spark。

## 扩展 Ray Data、榨取性能

最后，我们测试 Ray Data 的可扩展性，并用由 GPU 节点与纯 CPU 节点混搭而成的*异构集群*尝试最大化性能。涉及复杂数据类型的深度学习负载常受内存限制，因此加入更多纯 CPU 节点，等于为集群增加总内存，更好地拉高 GPU 利用率。

与 SageMaker 或 Spark 不同，Ray 原生支持由不同实例类型构成的异构集群，彻底解决**挑战 #1**。

我们运行同一基准，换成 10TB 图像，集群由 10 台 g4dn.12xlarge 与 10 台 m5.16xlarge 组成。

**吞吐：11,580.958 图像/秒**

下图可见，Ray Data 在整个负载运行期间 GPU 利用率超过 90%：

*图 4. 集群全部 40 块 GPU 的利用率。整个负载期间我们大致保持 90%+ 的 GPU 利用率。*

能扩展到大量 GPU 与庞大数据规模，而无需重写代码、也不牺牲吞吐——这正是 Ray Data 相较于其他深度学习负载方案的独特之处。

## 结论

本文界定了规模化批量推理的四大技术挑战，并调研了业界常被提及的三种离线批量推理方案。基于这些方案，我们比较了 Ray、Spark 与 Amazon SageMaker Batch Transform。

结论是 Ray Data 最能满足全部四项挑战：

- Ray Data 屏蔽计算基础设施管理，且原生支持异构集群，可为内存受限负载最大化性能。
- Ray Data 让数据从云存储 -> CPU -> GPU *流式*传递，确保集群所有资源在任何时刻都被利用。这提升吞吐、降低总成本。
- Ray Data 原生支持多维张量，这对深度学习负载至关重要。
- Ray Data 是 Python 原生、可编程的，开发与调试都容易。

总体而言，Ray Data 是深度学习离线批量推理的最佳选择。在我们的图像分类基准中（见上图），Ray Data 大幅超越 SageMaker Batch Transform（**17 倍**）与 Spark（**2 倍**和 **3 倍**），并可线性扩展到 TB 级数据规模。全部基准代码见[这里](https://github.com/amogkam/batch-inference-benchmarks)。

最后，得益于更高吞吐以及 Ray 是开源方案，Ray 在 EC2 基础成本之上进一步降低了总体成本。
