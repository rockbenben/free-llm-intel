# KubeRay 生产实践：来自一线的最佳实践

作者 [Naila Khan](https://www.anyscale.com/blog?author=naila-khan) | 2026 年 10 月 26 日

*我们 KubeRay 系列的第二篇，来自一线。**[ 第 1 部分：用 KubeRay 在 Kubernetes 上大规模运行 Ray*](https://www.anyscale.com/blog/kuberay)* 介绍了 KubeRay 是什么、它的自定义资源，以及如何部署你的第一个 RayJob。*

第 1 部分结束在一个不错的时刻：一个 RayJob 达到 `SUCCEEDED`。本文从这里接着讲：当那一个 job 变成数百个、分散在多个团队与集群之间时，哪些地方会变。KubeRay 处理这种增长很在行；[一场公开发布的 Ray Summit 2024 演讲](https://www.youtube.com/watch?v=9S5WznGnIpE)展示了 Ray Train 扩展到 10,000 个 Kubernetes 节点。

如果你在 Kubernetes 上跑了一段时间 Ray，可能知道那个时刻。一旦越过几个节点、还有了第二个团队，某个时候，一个失败的 GPU job 就不再是敲一下 `kubectl logs` 的事。握着答案的那个集群可能已经没了，而为重跑预留的 GPU 仍在持续计费，同时有人还在琢磨问题出在代码、数据还是硬件上。

作为一名现场工程师，我大量时间都在和两类团队相处：一类是企业，要把 Ray 塞进原本为别的用途搭建的集群；另一类是数字原生公司，把 Ray 推到了前所未有的程度。他们往往会遇到同样那几种场景，而他们教会了我哪些实践经得起考验。本文分享的就是这些。

## 从快速入门到生产

第 1 部分的例子用 CPU 训练 Fashion MNIST。生产级 RayJob 用的是同一个资源，但有四处改动：申请 GPU、通过 Kueue 排在团队配额之后、不让工作落在 head 节点上、worker 从零开始扩缩。

```
1apiVersion: ray.io/v1
2kind: RayJob
3metadata:
4  name: nightly-train
5  labels:
6    kueue.x-k8s.io/queue-name: team-ml   # same quotas as every other GPU workload
7spec:
8  entrypoint: python train.py
9  shutdownAfterJobFinishes: true         # GPUs go back to the pool when done
10  ttlSecondsAfterFinished: 300
11  rayClusterSpec:
12    enableInTreeAutoscaling: true
13    headGroupSpec:
14      rayStartParams: { num-cpus: "0" }   # keep work off the head node
15      template: { ... }
16    workerGroupSpecs:
17      - groupName: gpu-workers
18        minReplicas: 0
19        maxReplicas: 16
20        template: { ... }                # nvidia.com/gpu requests go here
```

在这个规模上，第 1 部分讲的那些特性承担了更多工作：GPU 节点在多个 job 之间共享、worker 能缩回零、配额保证团队之间公平。对一个团队在一个集群上的情形，这份 spec 往往就够用了。

不过请注意 `shutdownAfterJobFinishes: true` 这一行。它对成本有利，也正是第一个生产场景的起点。

## 五种需要提前规划的生产场景

一旦 Ray 成为共享基础设施，团队更多、集群更多、GPU 浪费不起，一线就会反复出现同一种模式：在小规模下表现良好的默认配置，在生产级的并行与争用下需要重新调。这些都不是 KubeRay 的问题。每一个都处在 Ray、Kubernetes，以及同时运营两者的组织这三者的交界处。

- **调试数据与集群生命周期绑定。** 会自我清理的 RayJob，也顺带删掉了自己的 Ray dashboard。最难处理的是 driver 在头几分钟就退出的情况：GPU worker 起来、没收到任务，集群在任何人抓到 driver 日志之前就被拆掉了。事后几乎没什么可查的。
- **硬件故障以应用错误的形式暴露。** PCIe 或 NVLink 故障，或者挂死的 NFS 挂载，可能中断一次训练，而 pod 仍报告 Ready。Ray 会继续在那里调度工作，于是故障表现为应用错误。有些团队改造了 operator 并自定义了 resource 来检测失效硬件。
- **默认设置在规模化时需要调优。** 20 个集群争抢一个 GPU 池时，空闲的 GPU worker 可能在它的 placement group 还在形成时就被回收，训练因此无法开始。`maxReplicas` 不留余量，一旦 Ray Train 重试某个 out-of-memory 任务，autoscaler 就会卡住。每次重试还可能留下一个 placement group。一线的团队反馈，可靠性稳定下来之前要投入数周的平台工程。
- **head 节点中断会影响整个集群。** 为更新节点镜像和安全补丁而做的节点 drain 可能把 Ray 节点下线，内存压力也可能驱逐 head pod——[Klaviyo 的工程团队](https://klaviyo.tech/how-klaviyo-built-a-robust-model-serving-platform-with-ray-serve-c02ec65788b3)在 KubeRay 上运行 Ray Serve 一年后描述了这种情况。没有 GCS fault tolerance 时，整个集群都会失效。启用了它，只有在 head 大约十分钟内恢复时 worker 才能继续运行，这是 KubeRay worker 重连的默认超时。
- **Ray 与既有平台服务共用集群。** service mesh、共享 namespace、配额与审计要求都是先来的。一个在 Ray Serve 上服务数千个模型的企业团队发现，它的 Envoy sidecar 为每个 Ray 端口都建了一个 listener，压垮了 mesh 控制面，并影响了邻近服务。

## 生产环境 KubeRay 的六条最佳实践

这些都不需要新工具。每条实践对应上面某个场景，用的都是 Kubernetes 生态已经提供的东西。

### 1. 在集群消失之前持久化日志与事件

一开始就假定临时集群的 Ray dashboard 会消失。把第 1 部分里的 History Server 打开，让 Ray 的事件与日志落到对象存储，并用短生命周期的运行来测试它：driver 在头几分钟崩溃，是团队最容易漏掉的情形。如果你们团队在既有的日志栈里排查，也可以用 Fluent Bit 这类 sidecar 把日志一并送过去。对于正在排查的 job，调大 `ttlSecondsAfterFinished`，让集群比故障活得更久，久到足以查看。

补充一点背景，说明为什么这很重要。能看到已结束 RayJob 的日志和 dashboard，是 KubeRay 社区最老的诉求之一；早在 2023 年就有用户在提。它难做，是因为临时集群正是 RayJob 的全部意义所在，所以证据必须在集群消失之前离开集群。History Server 是社区给出的答案，由来自多个大型平台团队的贡献者共同构建。它在 KubeRay v1.6 以 alpha 引入，在 v1.7 晋升为 beta。它把 Ray 的事件和日志写入对象存储，让你在集群删除之后仍能查看。

### 2. 把 GPU 健康当作调度信号

运行 NVIDIA 的 DCGM exporter，不只对利用率告警，也要对 GPU Xid 错误告警。用节点健康检查给故障节点打 taint 或 cordon，让新的 Ray pod 不再落到那里。然后用第 1 部分讲的 label-aware 调度，把新的 Ray 工作留在健康节点上。KubeRay 的维护者也在讨论把 Kubernetes Pod 事件（包括与设备相关的故障）转发到 RayCluster 资源上以便处置（[issue #5304](https://github.com/ray-project/kuberay/issues/5304)）。

### 3. 针对争用调优，而不是针对一个安静的集群

在生产级的并行度上测试你的配置，而不是在单个集群上测。一线反复出现的是这五个设置：

- **Gang scheduling：** 用第 1 部分介绍的某个 gang 调度器（Volcano、YuniKorn、scheduler-plugins 或 NVIDIA KAI Scheduler），让一个 job 的 worker 要么一起启动、要么都不启动。这避免了先起来的 worker 在 placement group 形成期间空转。
- **Idle timeout：** 如果不做 gang scheduling，就调大 idle timeout，让先起来的 GPU worker 在 placement group 其余部分形成期间存活下来。
- `**maxReplicas**`** 余量：** 为 out-of-memory 被杀之后 Ray Train 申请的替补 worker 留出余地。按你需要的 worker 数再加至少两个来定规模。
- **有界重试：** 用 `RAY_task_oom_retries` 限制 out-of-memory 重试次数，让反复重试不会跑上几小时。
- **CPU 与 GPU 混合池：** 留意 autoscaler 是否在 GPU 成为瓶颈时还在加 CPU 节点，以及空闲的 CPU 节点在 GPU 密集阶段是否缩容。

```
1autoscalerOptions:
2  idleTimeoutSeconds: 600   # default is 60
3workerGroupSpecs:
4  - groupName: gpu-workers
5    maxReplicas: 10          # 8 needed + headroom for retries
```

也要留意重试之后残留的 placement group。它们占着 autoscaler 无法回收的资源。

### 4. 为 head 节点丢失而设计

- 在 head 上设置 `num-cpus: "0"`，这样 CPU 任务和 actor 不会被调度到那里。
- 启用 GCS fault tolerance 时，给每个关键工作负载配自己的外部 Redis，让 Redis 的问题被限制在一个工作负载内。
- 把依赖烤进镜像，而不是在运行时安装——后者可能塞满临时存储并导致 pod 被驱逐。
- 对 Ray Serve，设置 `max_replicas_per_node`，让单节点故障只影响一个 deployment 的一部分。

### 5. 把 Ray 装进你已有的集群

- 给 Ray 独立的 namespace，配上第 1 部分里的 RBAC 与 NetworkPolicy 控制，让 Ray 工作负载与邻近服务保持隔离。
- 如果你运行 service mesh，就把它留在边缘。把 Ray 的内部端口从 sidecar 中排除，改用 Ray 自带的 TLS 或 KubeRay 的 mTLS 支持（v1.7 中为 alpha）加密 Pod 到 Pod 的流量。为每个 Ray 端口都建一个 sidecar listener 会把 mesh 压垮。
- 给每个 RayJob 和 RayService 打上所属团队与成本中心的 label，这样第 1 部分里的 Kueue 配额同时也带来归属与成本分摊。

### 6. 对真正重要的失败告警，并把第一响应自动化

对 RayJob 的 `Failed` 状态、head pod 重启和 GPU Xid 错误告警。从第 1 部分讲过的内容起步：KubeRay 的 Kubernetes 原生 status 字段和 Events 已经在报告 RayJob 与 RayCluster 的状态，`kubectl ray` 让 on-call 工程师快速查看。对于那些响应方式总是相同的场景，比如 cordon 一台 GPU 出故障的节点，把它自动化，让 on-call 工程师从一个答案开始，而不是从一块 dashboard 开始。

## 当胶水代码开始产生成本

在第 1 部分里，KubeRay 取代了 Ray 与 Kubernetes 之间的胶水。到了集群舰队的规模，又会出现新一层的胶水。上面每条实践都可行。而每条实践也都是胶水：需要你团队里的某个人去搭建、维护和支持。一个团队、一个集群时，这还扛得住。有了第二个团队、第二个集群就不一样了——一个失败的 job、一次三小时的排队等待，或者审计人员的一个问题，每一样都要花真实时间去答。

快速自查一下。你是否：

- 只为了在临时 RayJob 终止前抓住日志而维护一条 pipeline？
- 花几个小时去判断一次故障出在 GPU、Kubernetes 还是 Ray？
- 手工调 autoscaler 的默认值，以免生产 job 卡住？
- 跑冗余集群或自建的 health checker 来让 Ray Serve 保持可用？
- 为了审计或成本分摊，手工把工作负载对应到团队？
- 跨多个集群、云或区域运营 Ray，超出了 MultiKueue 覆盖的范围？

如果其中两条以上描述的就是你的一周，那平台层大概值得一看。

## 接下来是什么：KubeRay Connect

我们构建了 Anyscale KubeRay Connect，目前处于[私有预览](https://www.anyscale.com/asset/kuberay-connect-private-preview-form)，让团队不必再自己去搭那一层。它架在你已经在跑的 KubeRay 之上。你的 operator 继续 reconcile 你的 CR，你继续用 `kubectl apply` 提交，你的 Kueue 队列和 GitOps 保持原样。什么都不用重写。

**无论你是刚刚开始用 KubeRay，还是已经在生产环境运行它，都保留你现有的 Kubernetes 与 KubeRay 栈，用全栈可观测性、多云编排、安全、治理与企业级支持来扩展你的平台，让开发者保持高效、更快交付。**

KubeRay Connect 通过一个 Helm chart 安装，作为紧挨你工作负载的一层薄壳。一个小小的 Anyscale Connector 在 admission 阶段 patch 你的 KubeRay spec，并注入轻量的遥测 sidecar。一个 collector 把 metrics 和 Kubernetes 事件送到 Anyscale 平台。

下面是 Connect 与这五个场景的对应关系：

| **场景** | **KubeRay Connect 做什么** |
| --- | --- |
| 调试数据与集群生命周期绑定 | 持久化的 task 与 actor dashboard、聚合日志，以及 job、service 和 autoscaler 事件，由平台代为管理，无需 kubectl 权限即可在 Anyscale 控制台中查看 |
| 硬件故障以应用错误的形式暴露 | 在一处关联 GPU metrics、Kubernetes 事件和 Ray 信号，让硬件故障出现在受影响任务的旁边 |
| 默认设置在规模化时需要调优 | 展示 autoscaler 事件和每个 job 的 GPU 利用率，让你看出 idle timeout 与副本数上限何时设错。Orchestrate 在你的 Kueue 队列之外补上单集群的 job 提交、调度与状态跟踪。自动调优 Ray 设置已在路线图中。 |
| head 节点中断会影响整个集群 | 展示故障前后的事件；你的容错设计仍然归你 |
| Ray 与既有平台服务共用集群 | 安装在你现有栈的旁边：只有出站连接、控制面没有 ingress，你的 Kueue 队列和 GitOps 保持不变。用于 RBAC 与归属的身份透传已在路线图中。 |

Connect 与你的集群设计并行工作：mesh 配置、Redis 拓扑和镜像大小仍由你决定，上面那些实践依然适用。把身份映射到人、把工作放置到整个集群舰队，目前仍然由你负责，而预览用户正在塑造接下来的方向。

安全模型是按可审计的思路设计的。每条连接都从你的集群内部发起，所以控制面不需要 ingress。认证使用 projected ServiceAccount OIDC token，而不是 API key。admission 默认 fail-closed，因此工作负载绝不会在缺少遥测的情况下被悄悄准入。
