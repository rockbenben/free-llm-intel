# 解析 Dask-on-Ray 的内存管理与性能

作者：Stephanie Wang | 2021 年 6 月 29 日

Ray 是一个通用分布式系统。Ray 的目标之一是将数据处理库（如 Dask、Spark）无缝集成到分布式应用中。作为该目标的一部分，Ray 提供了一个健壮的分布式内存管理器。本文旨在对比 Ray 与使用内置调度器的 Dask 在内存管理和性能上的差异。

[Dask-on-Ray](https://docs.ray.io/en/master/dask-on-ray.html) 是一个社区贡献的插件，现已随 Ray 一同发布，可以在 Ray 集群上运行任意 Dask 任务图。本文聚焦 Dask 与 Dask-on-Ray 的架构差异，并介绍我们近期在 Ray 上开发的两个特性：[对象溢出（object spilling）](https://docs.ray.io/en/master/memory-management.html#object-spilling)和[更好的内存用量控制](http://tinyurl.com/ray-white-paper#heading=h.x7l9irbjxnp)。这些特性让 Dask-on-Ray 能把排序扩展到比 Dask 内置调度器大 10 倍（甚至更多）的数据集。

我们将通过两个基础原语的微基准测试来比较 Dask 与 Dask-on-Ray：广播一个大对象，以及排序一个大数据集。具体将考察：

- 使用 Ray 的共享内存对象存储与 Dask 的进程内对象存储的影响。
- 选择线程还是进程作为 Dask worker 的后果。
- 内存压力下的系统可靠性，包括核外（out-of-core）处理的稳定性。

这些微基准测试表明，设计和配置一个能处理内存密集型工作负载的分布式系统并不简单。在本文中，我们解释了为什么 Ray 可以让这件事更简单。我们希望通过让 Ray 成为 Dask 及其他分布式库的通用后端，能让社区不必各自构建内存管理。

## 一个简短的免责声明

Dask 和 Ray 面向的使用场景不同，因此在功能上并不能直接比较。总能找到在 Dask 或 Ray 上更快的负载，我们展示的这几个微基准也无法覆盖数据处理工作负载的全貌。我们做微基准的目标，是让相同的高层操作在不同后端上运行，进行公平的同类比较。

*还需要说明的是，我们是 Ray 的开发者，绝不是 Dask 专家！我们为排序基准做了尽职调查，并在 Dask GitHub 上提交了跟踪 issue，见[*这里*](https://github.com/dask/dask/issues/7613)和[*这里*](https://github.com/dask/community/issues/151)。所有基准的测试代码与结果可在[*这里*](https://github.com/stephanie-wang/dask-on-ray-blog)找到。*

## Dask 与 Dask-on-Ray 内存管理入门

Dask 与 Dask-on-Ray 的单节点架构。每个灰色方框代表一个独立进程。Dask 使用进程内对象存储，每个 Dask worker 进程各一个。Dask-on-Ray 是 Ray 之上的薄封装层，而 Ray 每个节点使用单一共享内存对象存储。

Dask 与 Dask-on-Ray 的一个关键设计差异是对象存储的位置。在 Dask 中，对象存储是*进程内（in-process）*的，即每个 Dask worker 进程堆内有一个对象存储，其内容由该 worker 控制。在 Dask-on-Ray 中，每个节点只有一个对象存储，以*共享内存*实现，运行在负责该节点资源管理的 "raylet" 进程的一个线程里。两种设计都能让 worker 直接访问本地缓存的对象，但在内存占用和性能上特性差异显著。

另一个差异在于各系统内存管理行为的可配置性（某些情况下甚至是必选项）。两个系统都有不少此类参数（例如为溢出对象指定本地目录，我们会在排序基准中使用），这里只强调最相关的几个。

Dask 的调节旋钮有：

- 进程数与线程数。这很重要，因为每个进程有一个对象存储，同一进程内的 worker 线程可以直接共享对象存储。但另一方面，受 [GIL（全局解释器锁）](https://wiki.python.org/moin/GlobalInterpreterLock)影响，使用线程并不总是理想。
- 每个 worker 进程的内存上限。这是一个[**软**限制](https://distributed.dask.org/en/latest/worker.html#memory-management)。
- 内存压力的处理[阈值](https://distributed.dask.org/en/latest/worker.html#memory-management)。可以设置若干阈值，包括每个 worker 何时开始把对象溢出到磁盘、何时停止接受任务。

在 Dask-on-Ray 中，主要参数是每个节点上[对象存储可使用多少内存](https://docs.ray.io/en/master/package-ref.html#cmdoption-ray-start-object-store-memory)。这是由 Ray 强制执行的[**硬**限制](http://tinyurl.com/ray-white-paper#heading=h.x7l9irbjxnp)。

## 微基准：广播一个大对象

先看进程内对象存储（Dask）与共享内存对象存储（Dask-on-Ray）的区别。

进程内对象存储在为**同一 worker 进程中的其他线程**创建对象和读取对象时开销很低。这是因为它可以避免：

- 序列化/反序列化开销，因为对象直接以 Python 对象存储。
- IPC 开销，因为对象留在本地进程堆内。

但有时 worker 线程需要读取存储在**另一个 worker 进程中**的对象，以便在受 [GIL](https://wiki.python.org/moin/GlobalInterpreterLock) 限制的应用中获得并行性。此时进程内对象存储的代价更高，即使**这些 worker 在同一个节点上**。原因是：

- 序列化/反序列化开销。
- 复制或传输对象带来的 IPC 开销。
- 多个进程需要读取同一对象时，因额外副本导致更高的内存占用。

相比之下，共享内存对象在创建或读取对象时的**最低**成本更高：

- 创建时需要序列化对象，才能存入 raylet 进程。
- 读取时需要反序列化对象（不过视对象和[序列化格式](https://docs.ray.io/en/master/serialization.html#serialization)可避免）。
- 读取或创建对象至少需要 1 次 IPC。

但更强的共享性也有好处，尤其是**多个进程需要同一对象**时：

- 多个进程读取同一对象时内存占用更低，因为它们可以共享同一份内存副本。
- 在本节点读取对象的 IPC 开销更低，因为对象无需复制。

下面的微基准清楚地体现了这一点：把 1GB 的 numpy 数组传给许多并行任务（每节点 100 个），每个任务执行一次求和。每次求和约 1 秒，每节点有 32 个 vCPU，理论最优约 3–4 秒。因此这里显示的大部分时间都来自各对象存储设计的系统开销。

测量把 1GB 对象传给大量任务（100 任务/节点）所需时间。多线程 Dask 与 Dask-on-Ray 都能利用内存共享避免复制，但多进程 Dask 必须复制对象。Dask-on-Ray 同样使用多进程，但对象存于共享内存而非本地堆内存。

在把同一个大对象广播给许多任务时，只要 Dask worker 使用线程，Dask-on-Ray 与 Dask 的对象存储带来的开销大致相同。但如果用进程而非线程，Dask 的进程内对象存储就成为瓶颈，因为大部分时间花在了对象的序列化/反序列化和跨 worker 进程复制上。随着节点增多瓶颈更糟，因为对象还要通过网络复制。

那么，为什么不总是用线程作为 Dask worker 呢？问题在于 Python 的[全局解释器锁（GIL）](https://wiki.python.org/moin/GlobalInterpreterLock)。GIL 是进程级的，一次只能被一个线程持有，因此任何需要 GIL 的执行都会与同进程内其他执行线程串行化。虽然 numpy 等流行库会注意不长时间持有 GIL，但有时无法避免，尤其是需要编写自定义功能时。

再看同一个基准，这次额外比较任务持有 GIL 的版本。这种情况很常见：这里每个任务从输入数组中随机选取 1 万个元素，单线程约需 50–100ms。

测量把 1GB 对象传给大量任务（100 任务/节点）所需时间。多线程 Dask 可以避免不必要的内存复制（深橙色），但任务需要持有 GIL 时性能下降（浅橙色）。

这里就能看到 Dask 总是使用线程的问题。在单节点上，对持有 GIL 的任务使用线程（浅橙色）会迫使所有计算串行执行，运行时间远长于使用进程。而 Dask worker 进程在 -/+ GIL 之间的差异（深/浅红色）则大致相同，因为工作仍能并行完成（+GIL 略快，因为任务本身更短）。

另一方面，Dask-on-Ray（蓝色）*始终*使用进程来并行工作。扩展时存在一些开销，可能源于数据传输，但总体运行时间大致恒定。无论增加节点，还是任务是否持有 GIL，都是如此。

## 微基准：Shuffle（DataFrame.set_index）

看另一个微基准：对数据集排序。这对系统是有挑战的工作负载，因为排序需要 shuffle 数据集的各分区，形成全对全依赖。若数据集大于内存，系统还必须有某种把工作集部分溢出到外部存储（这里是本地磁盘）的机制。这些基准中，我们在一个 100 分区、单列的 Dask DataFrame 上使用 `set_index` 方法。

首先看 Dask 使用进程与线程的性能差异。先在 10GB DataFrame 上比较各系统。通常排序的工作集大小约为数据集的 2 倍，所以应该完全放得进我们 244GiB 的内存。

单节点（32 vCPU、244 GiB RAM、10GB 数据集、100 分区）上的 Dask.dataframe.set_index。Dask 排序性能取决于是否使用进程而非线程。

这里再次看到使用线程并不总是利于性能，可能因为 shuffle 需要较长时间持有 GIL。其余基准中，Dask 默认使用进程以提升并行度。

当数据集增大到 20GB，开始能看到内存压力的影响。取决于分区大小，Dask 的 `set_index` 实现可能需要把对象溢出到磁盘才能完成该操作。

在 100 分区（分区大小 200MB）时，Dask 未能完成，以 worker 失败异常退出。这很可能是因为在溢出足够对象腾出空间之前就触到了内存上限（可关注 GitHub issue [这里](https://github.com/dask/dask/issues/7613)）。

单节点（32 vCPU、244 GiB RAM、20GB 数据集）上的 Dask.dataframe.set_index，改变分区数。与 Dask-on-Ray 相比，Dask 的稳定性对分区数量十分敏感。

我们遵循了 Dask 社区的[建议](https://github.com/dask/dask/issues/7613)，增加了分区数，这应当能减少每个 worker 一次需要的内存总量。在 200 或 500 分区时，Dask 能够完成。而 Dask-on-Ray 在*任意*分区数下都能成功，性能也基本相同。

我们还发现，在保持分区数（100）不变时，调整 worker 进程数有助于 Dask 扩展到更大的数据集。这很合理，因为这让每个 worker 能同时容纳更多对象，代价是并行度下降。使用 8 个进程而非 32 个，Dask 能完成 20GB 但无法完成 100GB。使用 1 个进程，Dask 能完成 100GB，但当然会看到与 10GB 时类似的减速。

相比之下，Dask-on-Ray 为 Dask 图透明地管理 worker 数量，因此在单节点上，Dask-on-Ray 在所有数据集大小下都能完成。在 100GB 上，Dask-on-Ray 比使用 1 进程的 Dask（Dask 唯一成功的配置）快约 9 倍。

单节点（32 vCPU、244 GiB RAM、100 分区）上的 Dask.dataframe.set_index，扩展数据集大小。纵轴为对数刻度。把 Dask worker 从 32 个减到 8 个可让 Dask 完成 20GB，但无法完成 100GB。从 8 减到 1 可让 Dask 完成 100GB，但相比 Dask-on-Ray 慢 9 倍。

## 分析

可以看到，想为 Dask 排序找到合适的集群与应用配置相当棘手，至少在这个 Dask 版本（2021.4.0）上如此。虽然这只是一个内存密集型应用的例子，我们已经能看到各参数的影响：

- 进程与线程，以及各自的数量。
- 数据分区数。
- 每进程的[内存上限](https://distributed.dask.org/en/latest/worker.html#memory-management)，在前面基准中我们随进程数减少按比例调高了它。
- 用于溢出等的[内存阈值](https://distributed.dask.org/en/latest/worker.html#memory-management)。Dask 贡献者[建议](https://github.com/dask/dask/issues/7613)调整这些阈值以改善排序稳定性，但似乎没有效果。

理想情况下，这些参数应当只影响*性能*而不影响*能否取得进展*。

那么为什么 Dask-on-Ray 能完成 Dask 无法完成的更大规模排序？很难有确切结论，但这里有两个猜测。

第一，通过每节点使用单一共享内存对象存储，在使用进程实现并行所必需的场景下可以降低总内存占用。排序会产生全对全依赖，意味着每个 worker 都要读取至少一个由其他 worker 产出的对象。如果 worker 之间不共享内存，每个依赖都必须复制给接收方。

第二，通过每节点单一共享内存对象存储，更容易控制节点上使用的总内存量。在 Ray 中，有一个线程统一服务所有对象创建与读取请求，因此可以在任意时刻[精确控制对象使用的内存量](http://tinyurl.com/ray-white-paper#heading=h.x7l9irbjxnp)。例如，我们可以根据参数大小限制可并发运行的任务数。这些技术在 Dask 的进程内对象存储中同样可能实现，但由于对象分布在同一节点的多个 worker 中，需要跨多个进程协调内存用量。

最后，共享内存对象存储能更精确地度量每个节点的总内存用量。存放在 Ray 对象存储中的对象必然已经序列化，所以我们确切知道它们需要多少内存。虽然我们无法同样精确地统计 Python worker 的额外内存使用（如参数反序列化和临时变量），但这已让我们对每个任务的内存需求有很好的估计。相比之下，Dask 对象就是 Python 对象，其内存用量只能靠猜测；而且对象分散在多个进程中，要度量（和控制）节点上精确的总内存使用就需要在各进程间同步。

这三点特性共同让 Dask-on-Ray 能对单节点上任务输入输出使用的内存施加**硬**限制。这也让对象溢出的实现相对直接：一旦对象存储达到容量上限，新对象会被阻塞，直到已有对象被[溢出](http://tinyurl.com/ray-white-paper#heading=h.7ce0zjt0shwh)。类似地，所需对象会根据排队任务与可用内存被恢复。

总结我们的发现：

- 在处理超大数据集时，正确调优 Dask 配置可能相当困难。
- Ray 选择使用共享内存，有时会给 Dask-on-Ray 增加开销——需要把数据从 Python worker 复制到另一进程——但更多的共享也带来了大量性能收益。
- Ray 对溢出与恢复哪些对象的精确管理，是内存密集型 Dask-on-Ray 应用稳定性的关键。

## 在内存密集型应用中使用 Dask-on-Ray

Ray 的内存管理仍在积极开发中，所以确实存在一些 Ray 还能做得更好的内存密集型应用。如果你发现了这样的场景，请[提交 issue](https://github.com/ray-project/ray/issues/new/choose)，我们很乐意了解详情并帮助你！

但总体而言，我们相信上文强调的这些设计决策是根本性的，Ray 的对象存储整体架构是通向高效可靠分布式内存管理的正确道路。已经有 Dask-on-Ray 用户从中受益。例如，[一位用户](https://www.jennakwon.page/2021/03/benchmarks-dask-distributed-vs-ray-for.html)在处理 PB 级数据作业时发现，使用 Dask-on-Ray 让她节省了 3 倍的总算力成本、超过 10 倍的总运行时间。

### 附录：基准测试设置

所有基准均在 AWS EC2 的 i3.8xlarge 机器上运行，配备 32 vCPU、244 GiB 内存和 4 块 1.9TB NVMe SSD。我们使用 Python 3.8、Dask 和 Dask.distributed v2021.4.0，以及 [Ray nightly wheel](https://s3-us-west-2.amazonaws.com/ray-wheels/master/b986938f0ff22f86cb87aab9f3e0d4fa36457b8f/ray-2.0.0.dev0-cp38-cp38-manylinux2014_x86%20_64.whl)。所有 Dask-on-Ray 基准都可在即将发布的 Ray v1.5 上运行。

排序基准的所有输入数据以 gzipped Parquet 文件存放在 Amazon S3，使用 Dask 内置的 DataFrame S3 读取器读出。为优化 shuffle 微基准中核外处理的磁盘读写，我们挂载了 4 块 NVMe SSD 并让 Dask worker 指向其中一个挂载点。Ray 支持溢出到本地磁盘时使用多个目录，我们借此提升了 Dask-on-Ray 的读写吞吐。

Dask worker 使用默认内存限制，另有说明的除外。

对 Ray，排序基准中我们使用每节点 50GB 的对象存储上限。使用更大值是完全可行且通常推荐的（可直到操作系统指定的 /dev/shm 上限），但我们用较小的对象存储容量来绕过共享内存分配器的一个[已知 bug](https://github.com/ray-project/ray/issues/14182)。我们将在 Ray v1.5 中彻底修复该 bug。

注意，仅对 Dask-on-Ray，我们使用 shuffle 参数 `shuffle='tasks'` 和 `max_branch=float('inf')`，强制 Dask 在 Ray 上以任务图执行 shuffle，而不是用 Dask 原生 shuffle。Dask 使用这些参数时的结果与所报告的测量值没有显著差异。

所有基准脚本与结果见[这里](https://github.com/stephanie-wang/dask-on-ray-blog)。
