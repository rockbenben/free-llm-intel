# AI 负载中的 GPU（低）效率问题

作者：David Wang | 2026 年 1 月 21 日

*tl;dr：GPU 利用率往往很低，在规模化场景下这会拖慢模型迭代并推高算力成本。本文聚焦于为 CPU 为中心、无状态负载设计的计算架构如何损害 GPU 效率，以及 AI 原生的执行模型需要什么。*

现代 AI 构建并运行在 GPU 上，但在生产环境中这些加速器常常未被充分利用。横跨数据处理、模型训练与推理，生产 AI 负载的持续利用率往往远低于 50%——即使在负载之下也是如此。

问题不只是算力成本。未被充分利用的 GPU 直接限制吞吐量、拖慢模型迭代，并制约新模型训练、评估与部署的节奏。

这种低效的根源主要不在硬件或模型设计，而在于跨多机编排这些负载所使用的计算系统架构。

过去十年，默认的计算架构建立在 Web 应用与结构化数据负载的固有假设之上：仅 CPU 执行、无状态进程、粗粒度的容器化部署。

这些假设不适用于 AI 负载的计算模式。本文深入剖析 GPU 利用率低下的成因，并说明解决这一问题需要一种不同的执行模型。

## **AI 负载中的异构计算模式**

现代分布式系统很大程度上是被 Web 服务塑造的。在那类系统中，负载是均匀、无状态、CPU 受限的。一个服务实例端到端地处理请求，通过复制相同的容器水平扩展。资源需求随时间相对稳定，性能随副本数可预测地扩展。

AI 负载不遵循这一模式。

AI 负载不是单一的均匀执行，而是由多个阶段组成，各阶段的资源需求、执行特征与扩缩行为根本不同。这些阶段经常在 CPU 受限与 GPU 受限的计算之间来回切换——单个负载内往往多次切换——造成资源需求在请求或作业的生命周期内大幅波动。

*多模态数据流水线示意图，展示负载中离散的 CPU 受限与 GPU 受限阶段。*

尽管存在这种异构性，这些负载却常被打包进单一容器化运行时，靠对数据分片来横向扩展。于是 CPU 密集的预处理、GPU 密集的推理或训练、CPU 密集的后处理全被包在同一个容器里。GPU 就必须在整个生命周期都被占用，即使只在部分计算中才需要它。结果是负载的形状与基础设施的形状不匹配。

*示意图：在单一容器运行时上扩展 AI 负载导致低 GPU 利用率。*

这种低效遍布各类 AI 负载。

数据处理中，图像、视频、文本流经 CPU 密集的解码阶段，进入 GPU 推理，再回到 CPU 做格式化与存储。训练中，GPU 节点被迫承载跟不上节奏的 Python dataloader，让加速器挨饿。LLM 推理中，高吞吐的 prefill 与缓慢的自回归 decode 挤在同一个副本里，导致批处理次优——计算受限与访存受限的阶段互相拖累，造成长时间的空闲周期。

*可视化：多级视频处理流水线以单一容器扩展时对 GPU 利用率的影响。*

问题的根源在于：当 CPU 密集与 GPU 密集阶段被打包在一起、作为单一负载部署时，整个负载被迫作为一个整体扩展。这意味着昂贵的 GPU 在只有 CPU 阶段运行时也一直被占用，低利用率与高成本由此注定。

举个例子：设想一个容器先做 CPU 预处理再做 GPU 推理。你把它部署在有 8 GPU、64 CPU 的节点上。CPU 阶段占满 64 个 CPU，而 GPU 阶段只用掉 20% 的 GPU。如果你需要 5 倍吞吐，就必须把整个 GPU 实例再复制 4 份——尽管瓶颈从来不是 GPU。结果：5 个 GPU 节点，各自只用了 20% 的 GPU 容量。

随着模型规模增长，一个令人不适但不可否认的事实是：GPU 正在被浪费。

## **用分离式执行实现 AI 原生计算**

Ray 是一个开源计算框架，通过简洁的 Python API 支持 AI 负载的异构资源需求，高效地扩展负载。

Ray 不是把整个负载绑死在单体容器上，而是在底层把负载分解为独立阶段，每个阶段显式声明自己精确的、甚至分数的资源需求。CPU 处理只跑在 CPU 上，GPU 处理只跑在 GPU 上。计算任务可以运行在分数 GPU 上（配合动态划分与调度，支撑数十万处理任务）。数据在各阶段之间通过其内存对象存储持续流动，提供快速的分布式对象传递。

在数据处理中，Ray 把异构负载分离：将解码与解析非结构化数据（文本、图像、视频）等 CPU 受限阶段，与 GPU 加速的嵌入和模型推理阶段拆开。通过把这些阶段作为 DAG 中的独立组件编排（由 Ray Data 抽象），Ray 让 CPU 密集的数据准备可以独立于 GPU 执行来扩展。

*图示：Ray 通过分离式多阶段运行时驱动 GPU 满载利用。*

在训练中，Ray 把数据加载与 GPU 训练彻底分离。不再强迫 dataloader 在 GPU 上与 trainer 争抢，Ray 用一个可扩展的 CPU 池源源不断地向 GPU 输送就绪的 batch。GPU 不再受单一实例的 CPU:GPU 配比约束。

在推理——尤其是 LLM 服务——中，Ray 结合 vLLM 实现规模化的分离式服务，把计算受限的 prefill 阶段与访存受限的 decode 阶段解耦。通过把它们作为 DAG 中的独立阶段编排，Ray 实现了细粒度扩缩与资源隔离，显著优化硬件利用率与成本。

这正是 AI 原生执行为何如此重要——它弥合了 AI 负载实际行为与算力编排方式之间的鸿沟。

## **一个实际算例**

举个例子：设想的 AI 负载每 1 GPU 需要 64 CPU——并且你需要扩展到 2048 CPU 与 32 GPU。假设两种实例：

- 实例 1：GPU 实例：64 CPU + 8 GPU
- 实例 2：CPU 实例：64 CPU

*单一容器化运行时：* 在这种架构下，你必须使用 GPU 实例类型才能获得 GPU。由于负载吃 CPU，CPU 先于 GPU 被占满。为了得到所需算力（2048 CPU），你必须开 32 个 GPU 实例。

- 总资源：32 个 GPU 实例 × 每实例 8 GPU = 256 GPU
- 实际使用：你只用 32 个 GPU
- 浪费：GPU 利用率仅 12.5%，为凑够 CPU 而付费的 224 个 GPU 一直闲置。

*分离式多阶段运行时：* 换成 Ray，CPU 与 GPU 阶段被分离，为每个阶段提供精确的资源分配，所有被分配的 GPU 都被打满。

- GPU 阶段：需要 32 GPU -> 4 个 GPU 实例（提供 32 GPU 与 256 CPU）
- CPU 阶段：需要剩余 1792 CPU -> 28 个 CPU 实例
- 浪费：利用率 100%，所有资源全部打满。

*表格：Ray 显著提升 GPU 效率，所需 GPU 实例更少、利用率更高。*

同样的 CPU 总吞吐，用 Ray 后所需 GPU 实例从 32 个降到对计算真正有效的 4 个——同一负载下 GPU 需求降低 8 倍。这种效率适用于从数据处理、模型训练到推理的整条 AI 流水线。

## **面向 AI 负载的集群级调度**

Ray 提升了单个负载的利用率，但集群级调度仍是个问题。

AI 负载是突发且不均衡的。数据处理可能让 CPU 需求骤增，训练作业可能在有限时段需要成百上千块 GPU，推理负载可以在几分钟内飙升。静态的集群边界与固定资源池对这种波动的响应很差，常导致过度配置。

Anyscale 的解法是把计算资源变成一张共享的计算结构（compute fabric），而不是一堆彼此隔离的 CPU/GPU 集群。不再是每个团队各自维护一池加速器——每池按峰值负载配置、大部分时间闲置——计算被聚合进一个全局池，所有 Ray 负载从中取用。负载需要资源时就拿到；用完后资源立即回流共享池，供另一个负载使用。

*图示：Anyscale 的全局资源调度器（GRS）驱动集群级 GPU 效率。*

这种方式在波动且不均衡的 AI 负载之间取得更高的平均利用率，让 GPU 被重新分配给活跃计算而非闲置。Anyscale 按需求重塑集群，确保 GPU 永远在跑最高优先级的作业，而不是在欠载的集群里空转。

若要进一步节省算力，长时间运行的训练作业与批量推理负载可以利用高可靠性的 spot 容量。效果是：组织以更低的成本获得多得多的算力、高得多的利用率——高效运行所有 AI 负载。
