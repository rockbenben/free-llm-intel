# 连续批处理如何让 LLM 推理吞吐提升 23 倍，同时降低 p50 延迟

作者：Cade Daniel、Chen Shen、Eric Liang 和 Richard Liaw | 2023 年 6 月 22 日

在本文中，我们将介绍大语言模型（LLM）推理的基础知识，并指出传统批处理策略的低效之处。我们将引入**连续批处理（continuous batching）**，并讨论 HuggingFace text-generation-inference、vLLM 等现有批处理系统的基准测试结果。借助 vLLM，用户可以在降低 p50 延迟的同时获得 23 倍的 LLM 推理吞吐。

由于 LLM 巨大的 GPU 显存占用和[计算成本](https://www.anyscale.com/blog/continuous-batching-llm-inference)，对大多数真实应用而言，服务化占据了计算成本的大头。ML 工程师常把 LLM 当作"黑盒"，认为只能通过量化、自定义 CUDA kernel 等内部改动来优化。但事实并非完全如此。由于 LLM 是迭代式生成输出的，且 LLM 推理通常是访存受限而非计算受限，一些*系统级*的批处理优化能带来令人惊讶的效果——在真实负载上相差 10 倍以上。

其中一项近期的优化就是**连续批处理（continuous batching）**，也叫**动态批处理（dynamic batching）**，或带**迭代级调度**的批处理。我们想看看这种优化的实际表现。下文将展开细节，包括我们如何模拟生产负载，但先总结我们的发现：

- 结合连续批处理与配套显存优化（使用 [vLLM](https://twitter.com/zhuohan123/status/1671234707206590464?s=20)），吞吐提升最高达 23 倍。
- 使用连续批处理（无论是在 [Ray Serve](https://docs.ray.io/en/latest/serve/index.html) 还是 [Hugging Face 的 text-generation-inference](https://github.com/huggingface/text-generation-inference) 上），相比朴素批处理吞吐提升 8 倍。
- 使用优化的模型实现（[NVIDIA FasterTransformer](https://github.com/NVIDIA/FasterTransformer)），相比朴素批处理吞吐提升 4 倍。

你现在就可以试用连续批处理：参见[在 Ray Serve 上运行 vLLM 的示例](https://github.com/ray-project/ray/blob/cc983fc3e64c1ba215e981a43dd0119c03c74ff1/doc/source/serve/doc_code/vllm_example.py)。

本文余下内容结构如下：

- 介绍 LLM 推理的基本原理，指出传统基于请求的动态批处理策略的低效之处。
- 引入连续批处理，说明它如何解决基于请求的动态批处理的诸多低效。
- 然后讨论我们的基准测试结果，以及这对经济高效地服务 LLM 意味着什么。

## LLM 推理基础

关于 LLM 推理有很多需要了解的内容，更深入的资料我们推荐 [*Efficient Inference on a Single GPU*](https://huggingface.co/docs/transformers/perf_infer_gpu_one) 和 [*Optimization story: Bloom inference*](https://huggingface.co/blog/bloom-inference-optimization)。但从宏观上看，LLM 推理相当直观。

对每个请求：

- 从一串 token 开始（称为"prefix"或"prompt"）。
- LLM 逐个生成补全 token，直到产出停止 token 或达到最大序列长度才结束。

这是一个迭代过程：模型每多前向一次，就多得到一个补全 token。例如，用句子 "What is the capital of California: " 作为提示，需要十次前向迭代才能得到完整回复 ["S", "a", "c", "r", "a", "m", "e", "n", "t", "o"]。这个例子略有简化——实际中 token 并不与 ASCII 字符 1:1 对应（流行的 token 编码技术是 [Byte-Pair Encoding](https://en.wikipedia.org/wiki/Byte_pair_encoding)，超出了本文范围）——但无论你怎么切分序列，生成的迭代本质都是一样的。

*简化的 LLM 推理。这个玩具示例展示了一个最大序列长度为 8 个 token（T1、T2、…、T8）的假想模型。从提示 token（黄色）开始，迭代过程一次生成一个 token（蓝色）。一旦模型生成结束 token（红色），生成循环即停止。此例只有一条输入序列，因此批大小为 1。*

理解了迭代过程的简单性之后，我们深入讲几点你可能不了解的 LLM 推理特性：

- 提示 "What is the capital of California: " 的初次摄入（"prefill"）耗时与生成每个后续 token 的耗时相当。这是因为[prefill 阶段](https://github.com/huggingface/text-generation-inference/tree/f59fb8b630844c2ad2cd80e689202de89d45c37e/router#prefill-decode-and-past-key-values)预先计算了注意力机制的[一些输入](https://kipp.ly/transformer-inference-arithmetic/#kv-cache)（在整个生成生命周期内保持不变的 KV cache）。由于这些输入之间可以独立计算，prefill 阶段高效利用了 GPU 的并行算力。
- LLM 推理是[访存带宽受限（memory-IO bound）](https://en.wikipedia.org/wiki/Memory_bandwidth)的，而非计算受限。换句话说，目前把 1MB 数据装入 GPU 计算核心的时间，比这些核心对这 1MB 数据做完 LLM 计算的时间还长。这意味着 LLM 推理吞吐*在很大程度上取决于你能把多大的批塞进高带宽 GPU 显存*。细节参见 [NVIDIA 文档的这一页](https://docs.nvidia.com/deeplearning/performance/dl-performance-gpu-background/index.html#understand-perf)。
- GPU 显存消耗随基础模型大小 + token 序列长度增长。在[*Numbers every LLM developer should know*](https://github.com/ray-project/llm-numbers#1-mb-gpu-memory-required-for-1-token-of-output-with-a-13b-parameter-model)中估计，13B 参数模型序列中每个 token 几乎要消耗 1MB 状态。在有 40GB 显存的较高配 A100 上，粗略估算：存下 26GB 模型参数后还剩 14GB，约可同时容纳 1.4 万个 token。这看起来不少，实际上相当受限：如果把序列长度限制在 512，一个批最多只能处理约 28 条序列。序列长度更高时问题更糟——2048 的序列长度意味着批大小只能有 7 条序列。注意这还是上界，因为没有给中间计算留空间。

这一切意味着，只要优化显存使用，就有大量"留在桌上的收益"可拿。这正是模型量化等策略（如 [AutoGPTQ](https://github.com/PanQiWei/AutoGPTQ)）潜力巨大的原因：如果从 16-bit 表示换成 8-bit 能把显存用量减半，就能让出双倍空间支撑更大批。但并非所有策略都要改动模型权重。例如 [FlashAttention](https://github.com/Dao-AILab/flash-attention) 通过重组注意力计算以减少访存量，取得了显著的吞吐提升。

连续批处理是另一种无需改动模型的显存优化技术。下面我们先解释朴素批处理如何工作（以及为何低效），再说明连续批处理如何提升 LLM 生成的显存效率。

## LLM 批处理详解

GPU 是大规模并行计算架构，算力以每秒浮点运算次数（flops）衡量，达到太发级（[A100](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/a100/pdf/nvidia-a100-datasheet.pdf)）乃至千万亿次级（[H100](https://resources.nvidia.com/en-us-tensor-core/nvidia-tensor-core-gpu-datasheet)）。尽管算力惊人，LLM 仍难以让芯片饱和，因为大量内存带宽都被用于加载模型参数。

批处理是改善局面的一种方式：不必每次有输入序列都重新加载模型参数，而是加载一次参数、用它处理许多条输入序列。这更有效地利用了芯片内存带宽，带来更高的算力利用率、更高吞吐与更便宜的 LLM 推理。

### 朴素批处理 / 静态批处理

我们把这种传统批处理方式称为*静态批处理（static batching）*，因为批的大小在推理完成前保持不变。下面是静态批处理在 LLM 推理场景中的示意：

*用静态批处理完成四条序列。第一次迭代（左），每条序列从提示 token（黄色）生成一个 token（蓝色）。经过若干次迭代（右），已完成的序列大小各不相同，因为它们在各自的迭代中发出结束 token（红色）。即使序列 3 在两次迭代后就已完成，静态批处理仍意味着 GPU 处于低利用率，直到批中最后一条序列（本例为序列 2，六次迭代）生成完毕。*

与传统深度学习模型不同，由于 LLM 推理的迭代特性，其批处理颇为棘手。直观地说，这是因为请求可以在批中提前"完成"，但要释放其资源并把处于不同完成状态的新请求加入批中却不容易。这意味着当批中各序列的生成长度小于批内最大生成长度时，GPU 就处于低利用状态。上面右图中序列 1、3、4 结束 token 之后的白色方块正是如此。

静态批处理多久会让 GPU 闲置一次？取决于批中序列的生成长度。比如，可以用 LLM 推理只输出一个 token 来做分类任务（有更好的做法，但先拿它举例）。此时所有输出序列一样大（1 个 token）。如果输入序列也一样大（比如 512 个 token），那么每个静态批都能达到最佳 GPU 利用率。

另一方面，一个 LLM 聊天机器人服务既不能假设固定长度的输入序列，也不能假设固定长度的输出序列。截至写作时，专有模型提供的最大上下文长度超过 8K token。在静态批处理下，输出生成长度的方差会导致 GPU 大量闲置。难怪 OpenAI CEO Sam Altman 形容其算力成本高到[令人瞠目](https://twitter.com/sama/status/1599669571795185665?lang=en)。

在没有对用户输入和模型输出施加苛刻假设的情况下，未经优化的生产级 LLM 系统根本无法在不浪费 GPU、不承担过高成本的前提下服务流量。我们必须优化 LLM 的服务方式，才能让它们的能力被广泛使用。

### 连续批处理

业界意识到了这一低效，并提出了更好的方案。[*Orca: A Distributed Serving System for Transformer-Based Generative Models*](https://www.usenix.org/conference/osdi22/presentation/yu)是 OSDI '22 上发表的论文，据我们所知是第一个解决该问题的工作。Orca 不再等待批中每条序列都生成完毕，而是实现*迭代级*调度：批大小按每次迭代决定。效果是：一旦批中某条序列生成完成，就有一条新序列补进它的位置，相比静态批处理取得更高 GPU 利用率。

*用连续批处理完成七条序列。左为一次迭代后的批，右为多次迭代后的批。一条序列发出结束 token 后，我们立即在其位置插入新序列（即序列 S5、S6、S7）。这取得了更高 GPU 利用率，因为 GPU 不必等所有序列完成才开始新序列。*

现实比这个简化模型更复杂：prefill 阶段要消耗算力，且计算模式与生成不同，无法轻易与 token 生成合批。连续批处理框架目前通过超参数管理这一点：[waiting_served_ratio](https://github.com/huggingface/text-generation-inference/blob/f59fb8b630844c2ad2cd80e689202de89d45c37e/launcher/src/main.rs#L124-L135)，即等待 prefill 的请求与等待生成结束的请求的比例。

说到框架，Hugging Face 已把连续批处理产品化，落在其 Rust + Python 的 [text-generation-inference LLM 推理服务器](https://github.com/huggingface/text-generation-inference/tree/main)中。我们在下面的基准测试中使用其实现来理解连续批处理的性能特征。

***注****：连续批处理（continuous batching）、动态批处理（dynamic batching）与迭代级调度（iteration-level scheduling）含义非常接近，任何一个都可以用来描述这种批处理算法。我们选择使用"连续批处理"。"动态批处理"也贴切，但容易与请求级批处理混淆——后者指 LLM 推理服务器使用静态批，且其大小在当前批完全生成结束后才选定。我们认为"迭代级调度"描述的是调度机制本身，而非整体过程。*

## PagedAttention 与 vLLM

本文想展示静态批处理与连续批处理的差异。事实证明，在 Orca 设计基础上改进后，连续批处理还能解锁静态批处理做不到的显存优化。

PagedAttention 是 [vLLM](https://blog.vllm.ai/2023-06-20/vllm.html)（[GitHub](https://github.com/vllm-project/vllm/tree/main#easy-fast-and-cheap-llm-serving-for-everyone)）实现的新注意力机制。它从分页（[paging](https://en.wikipedia.org/wiki/Memory_paging)）和虚拟内存（[virtual memory](https://en.wikipedia.org/wiki/Virtual_memory)）等传统操作系统概念汲取灵感。它们允许 KV cache（即上文所述 prefill 阶段计算出的内容）以固定大小的"页"（块）分配内存，从而无需连续。注意力机制随后可以改写为在块对齐的输入上运算，使注意力能作用于不连续的内存区间。

这意味着缓冲区分配可以即时（just-in-time）而非预先完成：开始一次新生成时，框架不需要按 maximum_context_length 分配一整块连续缓冲区。每次迭代，调度器可以判断某次生成是否需要更多空间，并即时分配，完全不损失 PagedAttention 的性能。这虽不保证内存的完美利用（[他们的博客](https://blog.vllm.ai/2023-06-20/vllm.html)称浪费现在仅限于最后一个块、低于 4%），但相较业界广泛使用的预分配方案已有显著改善。

总而言之，PagedAttention + vLLM 带来巨大的显存节省，因为大多数序列不会占满整个上下文窗口。这些显存节省直接转化为更大的批大小，意味着更高吞吐和更便宜的服务。我们在下面的基准测试中加入了 vLLM。

## 基准测试设置

先介绍实验设置，再深入基准结果。

### 实验

我们的目标是观察连续批处理与静态批处理在模拟真实在线推理负载上的表现差异。从根本上说，我们关心成本。由于成本直接取决于在给定延迟下服务的效率，我们把它拆为吞吐与延迟两部分。

| **基准目标** | **测量方式** |
| --- | --- |
| 测量吞吐 | 处理 1000 个请求队列的时间，每个请求 512 个输入 token，生成长度从指数分布采样。 |
| 测量延迟 | 100 个请求的请求延迟，输入长度、输出长度可变，以固定平均速率到达。 |

数据集及其他细节在各自的结果小节中讨论。

### 硬件/模型

我们在 [Anyscale](https://www.anyscale.com/) 提供的单块 [NVIDIA A100 GPU](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/a100/pdf/nvidia-a100-datasheet-us-nvidia-1758950-r4-web.pdf) 上基准测试吞吐与延迟。我们的 A100 有 40GB GPU 显存。我们选择 [Meta 的 OPT-13B](https://huggingface.co/facebook/opt-13b) 模型，因为每个被测框架都有现成的集成。选择 13B 版本是因为它无需张量并行即可放入我们的 GPU，同时又足够大，能体现显存效率的挑战。我们不用张量并行（把每个 transformer 块切到多块 GPU 上）以保持实验简单，尽管静态批处理与连续批处理都兼容张量并行。

### 框架

我们测试两个静态批处理框架和三个连续批处理框架。静态批处理框架：

- [**Hugging Face Pipelines**](https://huggingface.co/docs/transformers/pipeline_tutorial)**。** 最简单的推理方案。它对任意模型提供易用 API 的静态批处理，且支持比纯文本生成更多的任务。我们把它作为基线。
- [**NVIDIA FasterTransformer**](https://github.com/NVIDIA/FasterTransformer)**。** 该库提供多种 transformer 模型的优化实现。目前只支持静态批处理（[Triton 推理服务器](https://github.com/triton-inference-server/server)提供请求级动态批处理，但还没有连续批处理）。它让我们看到对模型做极致优化后静态批处理能走多远——相比 [Hugging Face Hub 上](https://huggingface.co/facebook/opt-13b)相对未优化的 OPT-13B 实现，它是更有竞争力的基线。

连续批处理框架：

- [**Hugging Face text-generation-inference**](https://github.com/huggingface/text-generation-inference)**。** Hugging Face 用它驱动自家 LLM 在线推理 API 的推理服务器，[实现](https://github.com/huggingface/text-generation-inference/tree/main/router#continuous-batching)了连续批处理。
- **Ray Serve 上的连续批处理****。** [Ray Serve](https://docs.ray.io/en/latest/serve/index.html) 借助 Ray 的 serverless 能力提供无缝自动扩缩容、高可用和复杂 DAG 支持。为理解连续批处理的机制，我们用纯 Python 在 Ray Serve 上重新实现了 text-generation-inference 的核心连续批处理逻辑。结果会显示，我们的实现与 text-generation-inference 性能一致，验证了我们的理解。
- [**vLLM**](https://blog.vllm.ai/2023-06-20/vllm.html)**。** UC Berkeley 团队近期发布的开源项目（[GitHub](https://github.com/vllm-project/vllm)）。它在 Orca 连续批处理设计之上，完全接管动态内存分配，从而大幅减少各种形式的 GPU 显存碎片。我们测试该框架，因为它展示了迭代级调度与连续批处理所能解锁的进一步优化之影响。

## 基准结果：吞吐

基于对静态批处理的理解，我们预期当批内序列长度*方差*更大时，连续批处理会显著更优。为验证这一点，我们对每个框架用序列长度方差递增的四份数据集分别运行吞吐基准。

具体做法：构造含 1000 条序列的数据集，每条 512 个输入 token。我们配置模型始终按每条序列设定的生成长度输出（忽略结束 token，配置 max_tokens）。然后从均值 =128 token 的[指数分布](https://en.wikipedia.org/wiki/Exponential_distribution)采样 1000 个生成长度（每个请求一个）。选择指数分布是因为它能较好近似服务 ChatGPT 类应用时遇到的生成长度。为了改变每次运行的方差，我们只保留指数分布中小于等于 32、128、512 和 1536 的样本。总输出序列长度因此至多为 512+32=544、512+128=640、512+512=1024 和 512+1536=2048（模型的最大序列长度）。

随后我们用一个简单的 asyncio Python 基准脚本以 HTTP 向模型服务器提交请求。脚本以突发方式提交所有请求，让算力饱和。

结果如下：

*各框架吞吐（token/s）随序列长度方差增大而变化。*

如预期，在低方差生成长度下，静态批处理器与朴素连续批处理器表现几乎一致。但随着方差增大，朴素静态批处理性能跌至 81 token/s。FasterTransformer 显著改善了朴素静态批处理，直到生成长度上限 1536 之前几乎能追平朴素连续批处理器。Ray Serve 上的连续批处理与 text-generation-inference 表现大致相同——由于使用同样的批处理算法，这正是我们所预期的。

最令人印象深刻的是 vLLM。对每份数据集，vLLM 的性能相比朴素连续批处理都不止翻倍。我们尚未分析哪项优化对 vLLM 性能贡献最大，但我们猜测 vLLM 动态而非预先预留空间的能力使其能大幅提升批大小。

我们把这些结果相对朴素静态批处理的倍数画出：

*吞吐基准结果，以朴素静态批处理的提升倍数呈现，对数刻度。*

值得注意，即便 FasterTransformer 的 4 倍提升也已相当可观；我们非常期待 NVIDIA 实现连续批处理后测试 FasterTransformer + 连续批处理。但显然，即使模型已高度优化，连续批处理相比静态批处理仍是重大改进。而当像 vLLM 那样叠加连续批处理与迭代级调度所能解锁的进一步显存优化时，性能差距变成了巨大。

## 基准结果：延迟

在线推理端点常面临延迟-吞吐权衡，必须根据用户需求优化。我们在贴近真实的负载上做延迟基准，测量各框架下延迟[累积分布函数](https://en.wikipedia.org/wiki/Cumulative_distribution_function)的变化。

与吞吐基准类似，我们配置模型对每个请求始终输出一指定数量的 token。我们从 1 到 512 token 的[均匀分布](https://en.wikipedia.org/wiki/Discrete_uniform_distribution)采样长度，生成 100 条随机提示；从均值 =128、上限 1536 的截断指数分布采样 100 个输出长度。选这些数字是因为它们相当真实，且能让生成用满模型的全部上下文长度（512+1536=2048）。

与吞吐基准中同时提交所有请求不同，我们把每个请求延迟预定秒数。每个请求相对前一个请求的等待时长从[Poisson 分布](https://en.wikipedia.org/wiki/Poisson_distribution)采样，该分布以期望速率 λ 参数化，在本例即打到模型端点的每秒查询数（QPS）。我们分别在 QPS=1 和 QPS=4 下测量延迟，观察负载变化时延迟分布如何改变。

*各框架生成请求的中位延迟，平均负载 1 QPS 与 4 QPS。连续批处理系统改善了中位延迟。*

我们看到，连续批处理系统在提升吞吐的同时还*改善*了中位延迟。这是因为只要有空间，连续批处理系统允许在每次迭代把新请求加入现有批。那其他分位数呢？事实上，我们发现它在所有分位数上都改善了延迟：

*QPS=1 时各框架生成请求延迟的累积分布函数。静态批处理器与连续批处理器的曲线形状截然不同，原因在于连续批处理器存在迭代级批调度。在该负载下所有连续批处理器表现接近；FasterTransformer 明显优于朴素模型实现下的静态批处理。*

连续批处理在所有分位数上都改善延迟的原因与它改善 p50 延迟的原因相同：无论批中其他序列生成到什么阶段，新请求都可以被加入。但与静态批处理一样，连续批处理仍受 GPU 可用空间的限制。当服务系统被请求填满（平均批大小更高）时，就没有那么多机会在收到新请求时立即注入。把平均 QPS 提高到 4 就能看出来：

*QPS=4 时各框架生成请求延迟的累积分布函数。与 QPS=1 相比，FasterTransformer 的延迟分布变得更接近朴素模型上的静态批处理。Ray Serve 与 text-generation-inference 的连续批处理实现表现相近，但明显不如 vLLM。*

我们观察到 FasterTransformer 变得更像朴素静态批处理；而 text-generation-inference 和 Ray Serve 的连续批处理实现正朝着 FasterTransformer 在 QPS=1 时的曲线靠拢。也就是说，系统趋近饱和时，无法立即注入新请求的机会变少，请求延迟上升。这与 vLLM 的曲线一致——在 QPS=1 与 QPS=4 之间几乎不变。这是由于其先进的显存优化，它的最大批大小更高。

根据我们的观察，vLLM 在 QPS=8 左右趋于饱和，吞吐接近 1900 token/s。要与其他服务系统做严格同口径对比还需更多实验；但我们已经证明，连续批处理显著优于静态批处理：1）尽可能立即注入新请求从而降低延迟；2）解锁高级显存优化（vLLM 案例），提升系统饱和前可承受的 QPS。

## 结论

LLM 展现出一些惊人的能力，我们相信其影响大多尚未被发掘。我们分享了一种新的服务技术——连续批处理——的原理，以及它如何超越静态批处理：通过更少浪费调度新请求的机会来提升吞吐，通过能够立即把新请求注入计算流来改善延迟。我们期待看到大家用连续批处理做出什么，以及业界将走向何方。
