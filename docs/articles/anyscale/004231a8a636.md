# 用 Anyscale 全新的 Ray Train 与 Ray Data 看板，把分布式 AI 的监控和调试理顺

作者：[Alan Guo](https://www.anyscale.com/blog?author=alan-guo)、[Cuong Nguyen](https://www.anyscale.com/blog?author=cuong-nguyen)、[Justin Yu](https://www.anyscale.com/blog?author=justin-yu)、[Matthew Deng](https://www.anyscale.com/blog?author=matthew-deng)、[Matthew Owen](https://www.anyscale.com/blog?author=matthew-owen) 与 [Richard Liaw](https://www.anyscale.com/blog?author=richard-liaw) | 2025 年 5 月 20 日

[Ray Train](https://docs.ray.io/en/latest/train/overview.html) 和 [Ray Data](https://docs.ray.io/en/latest/data/key-concepts.html#data-key-concepts) 在 Ray 的分布式计算引擎之上提供熟悉的高层 API，让机器学习工程师能把精力放在模型训练和数据处理逻辑上。但说到可观测性，日志和指标往往四散各处、也没有按语义打标，工程师只能手动把它们拼起来才能做出可视化。即便如此费时费力、还容易出错，多数团队仍然缺一个统一界面来看整体运行状态，并逐层下钻去定位具体问题，比如数据加载瓶颈或者显存溢出。

为了让把模型训练和数据处理规模化的从业者调试更快、性能调优更直观，我们很高兴推出：

- **全新的 Ray Train 看板：** 提供四项关键可观测能力：训练进度、错误归因、日志/指标、性能剖析。既能下钻到 worker 级别的行为，又能用上内置的剖析工具，定位性能瓶颈因此简单得多。例如 Torch 训练运行可以直接用 `dynolog` 这类集成工具做剖析。[了解更多](https://www.anyscale.com/blog/ray-train-data-dashboard#ray-train-dashboard:-unified-observability-for-distributed-training)。
- **全新的 Ray Data 看板：** 有 Tree 和 DAG 视图对流水线做下钻、有算子级别的指标、还有按数据集聚合的日志，机器学习工程师能更快定位瓶颈、优化数据流水线的性能——而数据流水线正是 AI 应用的地基。[了解更多](https://www.anyscale.com/blog/ray-train-data-dashboard#ray-data-dashboard:-faster-pipeline-debugging-with-tree-and-dag-views)。

在 Anyscale 上，**Ray Data 和 Ray Train 的日志都会自动持久化**——哪怕集群已经挂掉（比如显存溢出），也能做有力的事后分析。不用为了复现错误而重跑、也不用为排查而让昂贵的集群一直开着，只是众多好处里的一条。持久的日志还方便你长期看趋势，在多轮运行中发现跑得慢或效率低的阶段，帮你找到优化机会。

用 Ray 这样的分布式框架把模型训练规模化会引入相当大的复杂度，尤其是监控进行中的任务和调试失败。如今从业者得手动拼凑散落在各个节点上的日志、指标和上下文，才能搞明白哪里出了错；而 worker 和节点数量一上去，这个过程就越来越费劲。

Anyscale 里全新的 Ray Train 看板针对这些挑战给出一整套工具，帮你理解和优化分布式训练负载：

- **统一的体验：** 一个界面访问日志和指标
- **进度跟踪：** 清晰呈现训练进度与任务状态
- **丰富的错误上下文**：了解错误、重试与容错行为
- **一键剖析：** 对正在运行的训练任务一键做 CPU、GPU 和内存剖析

### 日志与指标下钻的统一界面

分布式训练环境通常把日志和指标散在不同的系统和界面里，逼着你在 worker 日志、controller 输出和资源指标之间手动对齐信息。等训练规模扩到几十甚至上百个 worker，这种来回切换上下文就越来越让人烦躁，也越来越容易出错。

Ray Train 看板的解法是提供一个统一界面，在上面既能看 Train Controller 的日志和指标，也能看 Worker 进程的。

从 `TrainRun` 页面入手，拿到任务状态和性能的高层视图，再下钻到具体的 worker 页面去查进程级或节点级的行为。所有相关信息都带着上下文组织在一起，帮你省下时间，也减轻监控复杂分布式任务的脑力负担。

### 训练进度与任务状态的清晰呈现

你有没有想过训练任务的时间到底花在了哪里？Ray Train 看板引入了负载级别的抽象——除了直接看到所有 worker，还增加了训练运行（train run）和尝试（attempt）——帮你在从整体到细节的各个层级上理解分布式训练任务里正在发生什么。

从启动训练任务的那一刻起，你就能监控资源请求、调度行为和利用率。不用再猜训练集群里发生了什么，整个任务生命周期里执行进度和系统性能都有一张清晰的视图。

### 用于性能优化的一键剖析

识别分布式训练的性能瓶颈，过去要求你同时对 AI 框架和分布式系统都有很深的理解，还得会用多种各有分工的专用工具。

为了让优化性能更容易，Ray Train 看板集成了 `py-spy`、`dynolog` 这类剖析工具做按需的性能分析。用 `py-spy`，用户可以生成火焰图和栈追踪，找出 CPU 瓶颈或者卡死。对 Torch 训练运行，`dynolog` 能给出展示 CPU 与 GPU 全部活动的 trace，从中挖出训练流水线里的瓶颈。这些工具一键就能启动，让用户在整个集群上定位出可以优化的地方。

### 用 Tree 和 DAG 视图做进度概览与下钻

![图 3. Ray Data 看板里用 Tree 视图看数据流水线的高层状态](https://images.ctfassets.net/xjan103pcp94/pK7keNfR7RNPYw3OqBeiR/f9e8fe96c27c9e3cb735fe2aa5a45522/image5.png)

图 3. Ray Data 看板里用 Tree 视图看数据流水线的高层状态

*图 10. Ray Data 看板里用 Tree 视图看数据流水线的高层状态*

[Ray Data](https://docs.ray.io/en/latest/data/monitoring-your-workload.html#ray-data-logs) 的日志本身信息量很足，但对流水线的真实结构缺少开箱即用的可见性。为了快速暴露你负载的拓扑、好监控和调试流水线的不同阶段，Ray Data 看板同时给出 Tree 视图和 DAG 视图，一眼看清负载的真实拓扑。

来看一个实际的例子。假设你有一个用于训练的数据预处理负载，作为这个负载的一部分，你需要从多个 S3 数据源读取大量图片。

```
1dataset_01 = ray.data.read_parquet("s3://...", columns=["image", "label"])
2dataset_02 = ray.data.read_parquet("s3://...", columns=["image", "label"])
3dataset = dataset_01.union(dataset_02).limit(100000).map(map_fn(...))
```

Tree 视图一眼给出负载的总体状态。DAG 视图则提供另一套洞察：它让你看到流水线在各个阶段之间的推进。这个视图能展示并发的读操作、合并步骤和预处理活动，帮你快速确认流水线确实在按预期执行——不用再靠猜、也不用手动去查底层到底发生了什么。

### 用算子指标定位并解决瓶颈

Anyscale 里的 Ray Data 看板不只是告诉你「有地方慢了」，它更进一步给出细节，帮你精确定位到瓶颈到底在哪里。

看板上展示的是调试必需的那几类指标，包括：

- 进度（已处理的行数）
- 资源利用率（CPU、GPU 和内存）
- 并发度（活跃的 task 和 actor 数量）
- 实时吞吐与峰值吞吐
- 排队中的 block 数量

### 用感知数据集的日志视图追踪并修掉隐藏的问题

在分布式系统里调试数据问题是出了名的难。Ray 看板的 Log 视图会自动抓取并高亮那些原本几乎不可能发现的问题数据模式。日志默认就会发出，并回溯到关联的数据集上——不需要任何手动配置。和传统日志系统不同，Log 视图同时给出系统级日志和用户自己打的日志，让你对数据流水线有完整的可见性。

来看一个实际例子，看看全局的 Log 视图怎么把调试变简单。

下面这张图里，是一个 Ray Data 程序产生了格式错误的数据，因为 `inverse` 函数没有处理 0 值。这个程序在 map 函数里触发了除零错误。

```
1dataset01 = from_items([{"id": 1, "value": 100}, {"id": 2, "value": 0}])
2
3def inverse(batch):
4   return {
5       "id": batch["id"],
6       "value": 1/batch["value"],
7   }
8
9dataset01.map(inverse).materialize()
10
```

为了应对这一点，Log View 会把出问题的那个 block 的确切内容（这里是 `` `{`id`: 2, `value`: 0}` ``）连同指明错误出自哪里的栈追踪一起吐出来。

![图 9. 用 log view 看到格式错误的行数据](https://images.ctfassets.net/xjan103pcp94/YWWRuDZMbEltfidqqxVjB/c230a08cc99b381f49b3f8e5d3fd67bf/image3.png)
