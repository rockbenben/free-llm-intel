# Ray 与分离式混合并行，多模态 AI 训练提速 30%

作者：Masahiro Tanaka、Amjad Almahairi、Nithin Chalapathi、Matthew Deng、Praveen Gorthy、Richard Liaw 和 Stephanie Wang | 2025 年 12 月 9 日

多模态 AI 模型能够处理文本、图像、音频等多种模态的信息，正在推动下一波 AI 创新，支撑从高级搜索到自主系统的各类应用。然而，训练最先进的多模态模型既复杂又极其消耗算力。

本文展示如何借助 Ray 的分离式混合并行（disaggregated hybrid parallelism）来应对这一挑战。该思路为多模态模型的每一个独立模块分别定制最优的并行策略，从根本上提升大规模训练的效率。

我们在 Ray 上实现了这一策略，并用 Qwen-VL 32B 进行测试。与对整个模型统一施加张量并行相比，我们取得了 1.26–1.37 倍的吞吐量提升。此外，与 DeepSpeed ZeRO3 相比，我们能够训练长达 7 倍的序列。

欢迎查看[我们的仓库](https://github.com/ray-project/multimodal-training)亲自试用。

## 多模态训练中的系统级挑战

与传统大语言模型（LLM）通常由同质的、堆叠相同 Transformer 层构成的架构不同，多模态模型往往由高度专业化的"模块"组成，各模块的计算与显存需求差异巨大。

例如，许多视觉-语言模型（VLM）将视觉编码器与大语言模型（LLM）结合。图 1 展示了最受欢迎的 VLM 之一 Qwen-VL 的架构。首先，视觉编码器将高分辨率图像作为 token 序列进行处理；接着，Projector（投影器）对视觉编码器的隐藏状态进行适配，使其与 LLM 对齐，并把序列长度压缩到原来的四分之一；最后，LLM 处理投影后的视觉 token 与文本 token 拼接而成的输入。通常，视觉编码器比 LLM 主干小得多。以 Qwen-VL 2.5 为例，其视觉编码器只有 6.7 亿参数，而 LLM 部分从 30 亿到 720 亿参数不等。

图 1. Qwen-VL 的架构

使用高分辨率图像和视频（会产生长序列）训练大规模 VLM 面临诸多挑战。对于拥有数十亿参数的 LLM，把模型权重、梯度和优化器状态塞进单张 GPU 的显存往往是不可能的。为此，张量并行、DeepSpeed ZeRO3、PyTorch FSDP 等技术被广泛采用，将模型分片到多个设备上。此外，为了把超长序列放入 GPU 显存，通常还会使用 DeepSpeed-Ulysses [1] 和 Ring-Attention [2] 等序列并行算法。下面我们概述这些方法，并考察它们在多模态模型训练中产生的开销。

首先看张量并行。由于它需要对激活值进行 `allreduce` 通信，其开销随序列长度线性增长（图 2）。这给视觉编码器造成了瓶颈：视觉编码器处理的序列很长，但参数量很少，这种切分既无必要又代价高昂。

图 2. 张量并行

再看 DeepSpeed ZeRO3（图 3）。它使用 allgather 为每一层重组被分片的参数。虽然通信量随模型规模而非序列长度扩展，但这会迫使每张 GPU 临时持有完整参数以及未分片的序列。因此，长序列下峰值显存占用会急剧飙升，可能引发 OOM（显存溢出）错误。

图 3. DeepSpeed ZeRO3 / PyTorch FSDP

最后看序列并行（图 4）。它沿序列维度切分激活值，但不分片模型参数。因此，把大模型放入显存仍然不可能。

图 4. 序列并行

总结来说，把张量并行、DeepSpeed ZeRO3（PyTorch FSDP）或序列并行这些常用切分技术统一地应用到整个 VLM 架构上并不高效，因为它们无法适应视觉模块与语言模块各自不同的计算特征。

## Ray：让自然且高效的混合并行成为可能

为了克服上述挑战，我们提出基于 Ray 的分离式混合并行，为多模态模型的每个独立模块应用量身定制的最优并行化策略。

Ray 是一个用于扩展 AI 和 Python 应用的通用框架。其核心提供 actor（有状态的分布式对象）这一抽象。该抽象让开发者能够编排复杂且可扩展的工作负载，例如大规模数据处理（如 [Amazon](https://aws.amazon.com/blogs/opensource/amazons-exabyte-scale-migration-from-apache-spark-to-ray-on-amazon-ec2/)、[Apple](https://www.youtube.com/watch?v=w4N0JmJo6jQ) 和 [Netflix](https://www.youtube.com/watch?v=FarU2GM4yRQ) 的实践）以及强化学习流水线（如基于 [verl](https://github.com/volcengine/verl)、[OpenRLHF](https://github.com/OpenRLHF/OpenRLHF) 的方案）。

借助这一架构，开发者可以把不同的模块映射到独立的 Actor 组。这种设计让他们能够在简洁的训练循环中表达复杂的编排逻辑。此外，Ray Actor 的灵活性允许独立的资源分配：例如，开发者可以为每个组分配特定数量的 GPU 或节点，使硬件配置契合每个模块的独特需求。

图 5. 基于 Ray 的分离式混合并行总览

这种架构上的灵活性转化为直观简洁的代码。例如，我们可以实现一个 `ActorGroup` 类，封装单个模块在多张 GPU 上的并行化：

```
1class ActorGroup:
2    def __init__(
3        self, config, actor_cls,
4        num_actors, num_cpus, num_gpus,
5    ):
6        # Create Ray actors of the specified class
7        self._actors = [
8             remote_actor_cls.options(
9                    num_cpus=num_cpus,
10                    num_gpus=gpus_per_actor,
11             ).remote(config, i) for i in range(num_actors)]
12        self._setup_process_group()
13...
14
15def main():
16...
17    # Create actor group for vision 
18    vision_group = ActorGroup(
19        vision_config, VisionTrainerClass,
20        num_actors=vision_parallel_size, ...
21    )
22    # Create actor groups for text 
23    text_group = ActorGroup(
24        text_config, TextTrainerClass,
25        num_actors=text_parallel_size, ...
26    )
```

建立这些 Actor 组之后，可以用 Ray 构建一个**单一控制器（single controller）**来编排训练流程。下面的伪码展示了一个典型的多模态训练循环，它在视觉编码器组与 LLM 组之间协调前向与反向传播。

```
1for _ in range(num_iterations):
2    # Forward Pass
3    vision_output_refs = vision_group.forward(...)
4    text_output_refs = text_group.forward(vision_output_refs, ...)
5
6    losses = ray.get(text_output_refs) 
7
8    # Extract loss values
9    loss_values = [loss.item() if torch.is_tensor(loss) else loss for loss in losses]
10
11    # Backward Pass
12    text_backward_refs = text_group.backward()
13    vision_backward_refs = vision_group.backward(text_backward_refs)
14
15    # Optimizer Steps
16    text_group.optimizer_step(...)
17    vision_group.optimizer_step(...)
```

把编排逻辑与模块执行清晰分离，是 Ray 方案的核心优势。它让开发者能够定义复杂的混合并行策略，而无需把主训练循环弄得杂乱。

## 验证：采用分离式混合并行的 Qwen-VL 2.5

为了展示 Ray 的实际效果，我们使用最先进模型 Qwen-VL 进行了基准测试。如图 1 所示，Qwen-VL 将视觉编码器与 LLM 耦合在一起。如前所述，视觉编码器远小于 LLM，但处理的序列要长得多。因此，统一施加张量并行会引发通信瓶颈，而统一使用 DeepSpeed ZeRO3 则往往随着序列变长导致 OOM 错误。

我们的方案对视觉编码器应用序列并行，对 LLM 应用张量并行。该策略带来以下收益：

- **更低开销：** 在高速 NVLink 条件下，序列并行（DeepSpeed-Ulysses）的通信开销低于张量并行。
- **利用窗口注意力：** 借助 Window Attention，我们大幅减少了同步点。在 Qwen-VL 中，32 层里只有 4 层需要通信。
- **显存效率：** 我们仍能通过张量并行把 LLM 参数放入 GPU 显存。

为了量化这些收益，我们使用 Qwen-VL 2.5 32B 模型进行了基准测试，对比以下三种条件：

- DeepSpeed ZeRO3（原作者的实现）
- 张量并行
- 分离式混合并行：视觉编码器使用序列并行 + DeepSpeed ZeRO1，LLM 使用张量并行

实验在单机 8× H100 GPU 上进行，采用 BF16 混合精度、Flash Attention 2 和激活检查点（activation checkpointing）。我们使用 MSCOCO 数据集，通过对图像进行不同尺寸的缩放来测量不同序列长度下的性能。全局 batch size 上限为 8（对应 micro-batch size 为 1，即 ZeRO3 支持的最小值）。当显存限制使该配置不可行时，我们使用 GPU 能容纳的最大 batch size。ZeRO3 结果来自 Qwen-VL 仓库的实现，而张量并行基线是未使用 Ray 的内部实现。

图 6 展示了不同视觉 token 数量下的吞吐量（TP = 张量并行；SP = 序列并行）。

图 6. 三种并行化策略（SP+TP、纯 TP、ZeRO3）在 Qwen2.5-VL-32B 上、不同视觉序列长度（1k–65k token）下的吞吐量对比

主要发现如下：

- 在所有序列长度（1k–65k token）上，SP+TP 相对纯 TP 稳定取得 1.26–1.37 倍加速。
- SP+TP 能在 ZeRO3 失败的超长序列（65k token）上进行训练：ZeRO3 在 16k+ token 时因完整聚合参数与激活值的显存开销而 OOM，而 SP+TP 有效地把激活显存分布到各 GPU 上。
- ZeRO3 的性能依赖序列长度：在约 9k token 时最优，但短序列表现差、长序列会 OOM。而 SP+TP 在所有测试序列长度上都保持稳定且高吞吐。

这些结果清楚证明了分离式混合并行（SP+TP）方案的显著优势：相对纯张量并行取得一致的加速，并且相比 DeepSpeed ZeRO3 具有更优的显存效率和性能一致性，使其能在单体框架失败的长度下完成训练。

## 总结

我们提出分离式混合并行（DHP），用以解决 VLM 这类异构多模态 AI 模型训练中的计算挑战。DHP 不再为整个模型使用单一并行化策略，而是利用 Ray 为不同组件分别施加定制的并行方式（例如视觉编码器用序列并行、LLM 用张量并行）。Ray 通过为每个模块建立专属"Actor 组"并以单一控制器进行编排来实现这一点，有效化解了并行化与资源需求不匹配造成的低效。

基于 Qwen-VL 32B 的验证表明，Ray 实现的 DHP（SP+TP）相对纯张量并行基线取得了 1.26–1.37 倍加速。尤为关键的是，DHP 展现出更优的显存效率，能在 DeepSpeed ZeRO-3 因 OOM 失败的超长序列（16k+ token）上成功训练。这证实了 Ray 灵活、分离式架构对于大规模训练最先进多模态 AI 模型所需的速度与显存容量至关重要。

展望未来，我们计划把评估扩展到更大规模的 GPU 集群和异构硬件配置，并把该策略应用到更多样的多模态架构上，以进一步验证其通用性。
