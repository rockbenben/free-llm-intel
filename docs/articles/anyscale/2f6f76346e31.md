# 推出 Anyscale Physical AI Skill

作者：Kunling Geng、Alicia Chua、Ian Jordan 博士、Artur Niederfahrenhorst 和 Carl Winkler | 2026 年 7 月 23 日

今天我们推出 **Anyscale Physical AI Skill**——一个用于借助 Ray 与 Anyscale 构建机器人与自动驾驶系统的新工作负载技能。它会与你一起界定负载范围，把困难的系统决策显式化，并生成运行所需的代码、依赖版本锁定、计算配置与启动指令。它把 [Anyscale Agent Skills](https://www.anyscale.com/blog/announcing-anyscale-agent-skills-ray) 延伸到物理 AI 领域，是继 [LLM 后训练技能](https://www.anyscale.com/blog/anyscale-llm-post-training-skill)之后的又一成员。

### 支持的物理 AI 负载、模型与仿真环境

Physical AI Skill 覆盖六类不同负载。这里的**离线/开环 RL 后训练**指策略生成候选轨迹，但奖励来自已记录的数据、并不在实际环境中行动；**在线/闭环 RL 后训练**指策略在仿真器内行动，并从产生的状态转移中学习。这是"是否与环境交互"的区分——并非宣称开环路径实现了 CQL、IQL 等经典离线 RL 算法。

| 负载 | 模型家族 | 数据或仿真环境 | Ray 与训练栈 |
| --- | --- | --- | --- |
| **VLA 微调（模仿学习 / SFT）** | π0/π0.5、SmolVLA、OpenVLA-7B、GR00T-N1.5/N1.7、Alpamayo-1.5，以及 action-policy 模式下的 Cosmos3-Nano | LeRobot v3 机器人示教数据、PhysicalAI-AV 驾驶数据、自定义 episode 视频 | Ray Train（较小模型用 DDP；分片全量微调用 FSDP/FSDP2；LoRA 与冻结主干策略）；Ray Data（输入管线支持时用分离式 CPU 视频解码） |
| **离线/开环 VLA RL 后训练** | Alpamayo-1.5-10B 及其他带可验证轨迹奖励的 VLA 策略 | 已记录的 PhysicalAI-AV 轨迹，训练循环中不含仿真器 | Cosmos-RL（GRPO/RLVR 训练）；vLLM（策略 rollout）；Ray Core（多 GPU worker 上的策略与 rollout 放置） |
| **在线/闭环 VLA RL 后训练** | Alpamayo-1.5-10B | AlpaGym、AlpaSim 与 PhysicalAI-AV NuRec 场景，奖励来自动作后的状态转移 | Cosmos-RL（策略训练）；vLLM（策略 rollout）；AlpaSim（仿真服务）；Ray Core（多 GPU worker 预留与放置） |
| **机器人策略服务与闭环评估** | π0/π0.5、GR00T-N1.5/N1.7、Alpamayo-1.5 | LIBERO 操作任务、Isaac Sim 上的 Isaac Lab、AlpaSim 自动驾驶场景 | Ray Serve（HTTP 策略端点）；Ray Core（GPU 隔离的仿真 worker）；AlpaSim（gRPC 驱动与运行时服务） |
| **世界模型与动作条件训练** | Cosmos-Predict2-2B、ResNet-18 + Transformer 潜动态模型、V-JEPA/V-JEPA 2、扩散世界模型 | LeRobot/FMB 轨迹、多相机机器人或自动驾驶视频 | Ray Data（分布式预处理）；Ray Train（分布式训练）；Ray actor（想象 rollout 与模型预测控制） |
| **仿真器原生 RL、域随机化与扫描** | 预训练 Isaac 人形策略、Brax PPO 人形策略、引擎原生 agent | Isaac Sim 上的 Isaac Lab、搭配 Brax 的 MuJoCo MJX、无头 Unreal Engine 5.7 | Ray Core（每个仿真或训练进程一个 GPU 任务/actor，用于策略优化、鲁棒性扫描与游戏引擎编排） |

这些模型名称描述的是被端到端跑通过的配置，并不是一份封闭白名单。对于新的 VLA 或世界模型，技能会从最接近的已验证模型规模与负载架构出发，然后在启动前重新验证显存、依赖、数据适配器和评估。

## 为什么是物理 AI，为什么是现在？

物理 AI 正在同时重塑机器人与自动驾驶。[openpi](https://github.com/Physical-Intelligence/openpi)、[SmolVLA](https://huggingface.co/blog/smolvla)、[OpenVLA](https://github.com/openvla/openvla)、[GR00T](https://github.com/NVIDIA/Isaac-GR00T)、[Alpamayo 1.5](https://github.com/NVlabs/alpamayo1.5) 等视觉-语言-动作（VLA）模型，把相机观测、语言与状态映射为机器人或车辆的动作轨迹。在机器人领域，这类模型旨在跨任务泛化操作与人形行为。在自动驾驶领域，Alpamayo 1.5 将 VLA 推理与轨迹预测结合，用于研究[长尾驾驶场景](https://www.mobileye.com/blog/diagnosing-the-long-tail-how-mobileye-turns-edge-cases-into-targeted-training/)。其潜在的行业影响，是从机器人/车队数据到训练、仿真、评估、部署的闭环更短——而不只是得到一个更好的模型 checkpoint。

世界基础模型（world foundation models）是这一发展闭环的另一半。它们不只是选择下一个动作，而是对环境如何随时间演化进行建模与生成，帮助团队创建合成训练场景、预测未来状态、测试动作条件结果并训练策略。[NVIDIA Cosmos 3](https://github.com/NVIDIA/cosmos) 标志着重要进展：16B 的 Cosmos3-Nano 与 64B 的 Cosmos3-Super 采用统一全模态 Mixture-of-Transformers 架构，对文本、图像、视频、音频和动作进行推理与生成。对自动驾驶团队，这拓宽了长尾场景生成、未来预测与驾驶策略开发的工具箱；对机器人团队，同一底座也支撑跨机器人形态的世界仿真、具身推理与动作学习。

单个物理 AI 负载其实是伪装成分布式系统的小系统。微调一个 VLA，意味着在 CPU 上解码数千个 MP4 片段，同时（如果模型够大）还要把数十亿参数的 transformer 分片到多块 GPU 上。世界模型的后训练则叠加多相机视频管线、生成组件和大规模分布式 checkpoint。评估一个策略，意味着让重量级 GPU 物理仿真器与重量级 GPU 模型同步锁步运行数千次。强化学习可能同时要以上全部——trainer、rollout 引擎，有时还有一个完整的驾驶仿真器，共享一个集群、来回传递权重与观测。任何一层搞错——选错 GPU、过期的 transformers 版本锁定、一个从未下载到 worker 的门控 checkpoint——你都会在跑了几小时之后才发现，而不是在开始之前。

*异构的物理 AI 技术栈：物理 AI 工作流横跨 CPU 解码、多 GPU 训练、仿真与策略服务。*

## 你会得到什么

- **一份需求驱动的规划**：覆盖模型、数据、训练策略、评估方法、部署目标、GPU 形态与预计运行时间。
- **可直接运行的 Ray 与 Anyscale 产物**：基于端到端测试过的负载模式，而不是从零凭空生成的基础设施栈。
- **经过验证的系统指引**：显存测算、依赖锁定、门控模型访问、CPU/GPU 分离、仿真器拉起。
- **你完全拥有的标准代码**：Ray、PyTorch、LeRobot、Cosmos-RL 与仿真器原生组件——不是私有建模抽象。

这一区分很重要：受支持的配置以成功运行为依据，但每个生成的负载仍取决于你的模型、数据集、云和组织。先在一个 Anyscale Workspace 中验证，再晋升为无人值守的 Job 或生产 Service。

## 为什么物理 AI 负载难以落地运维

机器人学习模型与工具越来越触手可及，但一旦超出单 GPU 教程，系统负担便迅速增长。同样的运维问题在各负载中反复出现。

**计算是异构的——就在一个作业内部。** [LeRobot](https://github.com/huggingface/lerobot) 格式数据集把视频按相机存成 MP4 文件。解码它们吃 CPU 又吃内存；训练策略则是 GPU 密集。把两者放在同机，MP4 解码就会和一个 30GB 的训练进程争抢主机 RAM，直到节点 OOM。闭环评估更糟：策略推理与物理仿真逐步交替、前一个输出喂给下一个输入，每个组件都需要精心做 GPU 与进程隔离。

**物理 AI 的依赖是整体联动，不是单个包。** 一个负载可能组合模型代码、数据集处理器、GPU kernel、编译扩展、分布式训练与仿真器运行时。一次看似安全的升级可能重命名某个预处理 API、改变 checkpoint 行为，或让 GPU 扩展与框架/CUDA 运行时不兼容。仿真器还会带来系统级依赖，可能需要专门构建的镜像或一组容器化服务，而不是简单装个包。因此，各自挑选最新组件的通用编程智能体，可能产出一个看着合理、但直到负载跑到 GPU worker 上才失败的依赖环境。Physical AI Skill 从所选负载的已验证兼容集出发，在 driver、worker 与运行时镜像间一致地应用它，并把任何组件升级视为需要端到端重新验证的变更。

**显存很容易算少。** 7B 全量微调加混合精度 AdamW，在激活值之前就需要约 112–120 GB 存放权重、梯度、master weights 和优化器状态。这超出了 48 GB GPU 上 DDP 的容量；我们验证过的配置使用四路 FSDP FULL_SHARD。确切需求取决于精度、优化器、激活检查点与序列长度。Mixture-of-Transformers 模型要按**总**参数量（而非激活参数）测算：Cosmos3-Nano 的两个约 8B 塔会常驻全部约 16B 参数，即便每个 token 只激活其中一小部分。按错误的数字测算，运行在 step 0 就死。

**仿真器本身就是一套基础设施。** 在我们的 Isaac Lab 验证中，Isaac Sim 冷启动约需 15 分钟，且日志量大到会让朴素的基于 stdout 的子进程协议崩坏。AlpaSim 以六个嵌套容器中的 gRPC 服务运行；在验证过的 Podman Docker-compat 路径上，Compose 的 GPU 预留与常用 `--gpus` 标志会被忽略，GPU 放置必须通过 NVIDIA legacy container runtime 注入。

这些大多是一再重复的系统工程而非模型研究，但团队却不得不反复解决它们。

## Anyscale Physical AI Skill 如何工作

Physical AI Skill 把一个描述过的机器人学习负载，变成一套完整可运行的 Ray 与 Anyscale 产物——附带关于组件、GPU 形态、依赖、模型访问、评估与运行时间的显式规划。它不是丢给你一个空白文件，而是走一遍多选题式的需求流程，用真实运行验证过的系统模式构建负载。

具体地，技能会：

- **通过决策门对负载分类**——VLA 微调、RL 后训练、策略服务、闭环仿真、GPU 仿真扫描或世界模型后训练——并把非机器人专属的部分路由到对应的通用技能（Ray Train、Ray Serve、Ray Data）。
- **挑选合适的 Ray 组件**：[Ray Data](https://docs.ray.io/en/latest/data/data.html) 做 CPU 视频解码，[Ray Train](https://docs.ray.io/en/latest/train/train.html) 做分布式 GPU 训练（DDP、FSDP、FSDP2），[Ray Serve](https://docs.ray.io/en/latest/serve/index.html) 做策略端点，Ray Core 做仿真编排与 GPU 并行扇出。
- **依据已验证的表格测算硬件**而不是拍脑袋——以测试过的模型与训练配置为起点，并在 7B 全量微调需要分片、或 MoE 模型必须按总参数量测算时给出警告。
- **核验模型访问与版本锁定**——用真实文件拉取（而不只是元数据）确认门控下载可用，区分公开与门控仓库，并沿用负载所需的精确 `transformers`/`lerobot`/PyTorch 版本。
- **在启动前估算运行时间与 checkpoint 节奏**，不让 24 小时的运行在第 20 小时给你惊吓，也让第一个 checkpoint 早到足以看到信号。
- **使用验证过的编排模式**——在生成模型与数据集特定代码的同时，保留有效的分布式系统结构。
- **应用来自成功端到端运行的负载专属经验**——涵盖依赖兼容性、分布式策略、CPU/GPU 分离、资源放置、checkpoint 与恢复——让每个生成的负载从已验证的运作模式起步，而不是在拉起阶段重新踩坑。

由于技能生成的是标准开源代码——Ray、PyTorch、LeRobot、Cosmos-RL——而非私有抽象，你保有结果的全部控制权。它是一个你拥有的起点，不是黑盒。

*Anyscale Physical AI Skill 的需求流程：把需求转化为可运行的负载。*

## 没有技能 vs 有技能

给两个编程智能体同样的物理 AI 请求。没有技能的那个只能靠猜基础设施与依赖；有技能的那个从验证过的模式出发。

差异体现在被避免的故障上：

| 故障模式 | 没有技能 | 有技能 |
| --- | --- | --- |
| 模型选错 GPU | step 0 报 `CUDA out of memory` | 启动前按已验证的 VRAM 表测算 |
| 7B 全量微调跑在 DDP 上 | `OOM，模型+梯度+优化器状态约 120 GB` | 路由到单个 4 GPU 节点上的 FSDP FULL_SHARD |
| 视频数据导致主机 RAM OOM | `MP4 解码饿死训练进程` | 为 Ray Data 使用分离式 CPU 数据节点池 |
| 门控 checkpoint 从未下载 | GPU 集群已跑起来后才报 `403` | 在任何 GPU 工作开始前用真实文件下载验证 |
| 过期的库版本锁定 | `import 时 transformers API 不匹配` | 逐模型沿用精确版本锁定 |
| runtime-env 合并冲突 | `作业因重复键在启动时失败` | 自动为你设置 `RAY_OVERRIDE_JOB_RUNTIME_ENV=1` |
| MoE 按激活参数测算 | `配置不足，加载即死` | 按总参数量测算 |
| 多日运行很晚才发现 | `排期被打破` | 事先估算运行时长并给出更快硬件选项 |

## 眼见为实：一句话微调 Cosmos 3

[NVIDIA Cosmos 3](https://github.com/NVIDIA/cosmos) 很好地说明了物理 AI 技能为什么不能只有通用训练知识。[Cosmos3-Nano](https://huggingface.co/nvidia/Cosmos3-Nano) 是一个 16B、双塔的 Mixture-of-Transformers 模型，结合推理、生成与原生动作能力。把它微调成机器人策略，意味着要照顾完整 16B 常驻模型、自定义 CUDA 栈、分布式 checkpoint、LeRobot 视频解码，以及一个原本用 `torchrun` 启动的训练框架。

从你想要的结果开始：

```
Use the physical-ai skill to fine-tune Cosmos3-Nano in action-policy mode on my
LeRobot v3 dataset with LoRA, using one 4×L40S node on Anyscale.
```

技能会先确认动作空间、相机映射、数据集位置、GPU 拓扑、运行时间、checkpoint 节奏与评估计划，然后生成一个自包含目录：

```
cosmos3_nano_action_policy_20260710_120000/
├── README.md                    # architecture, hardware, run and recovery steps
├── user_request_summary.txt     # confirmed model, data, compute, and evaluation plan
├── workspace.yaml               # CPU head + one 4×L40S GPU worker
├── Containerfile                # Cosmos, PyTorch, CUDA, and flash-attn environment
├── setup_data.sh                # dataset and checkpoint staging
├── train_ray.py                 # Ray Train launcher for Cosmos
├── src/
│   ├── action_policy.py         # model and LoRA configuration
│   └── lerobot_dataset.py       # bimanual LeRobot v3 adaptation
└── run_config.toml              # batch, optimizer, parallelism, and checkpoints
```

生成的 driver 让 CPU head 保持轻量，并请 Ray Train 在 L40S 节点上放置四个 worker。Cosmos 保留其原生 trainer，Ray Train 取代 `torchrun` 作为分布式启动器。核心集成如下（省略了 setup 辅助与文件加载代码）：

```
import os
import runpy
import sys

import torch
from ray.train import FailureConfig, RunConfig, ScalingConfig
from ray.train.torch import TorchTrainer

def train_loop_per_worker(config):
    # Install the generated dataset/model configuration before importing Cosmos.
    _apply_xvla_adaptation(config["adaptation"], config["framework_dir"])

    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)
    os.chdir(config["framework_dir"])

    sys.argv = ["train", f"--sft-toml={config['toml']}"]
    runpy.run_module("cosmos_framework.scripts.train", run_name="__main__")

trainer = TorchTrainer(
    train_loop_per_worker,
    train_loop_config={
        "framework_dir": FRAMEWORK_DIR,
        "toml": RUN_CONFIG,
        "adaptation": generated_files,
        "overrides": [],
    },
    scaling_config=ScalingConfig(
        num_workers=4,
        use_gpu=True,
        resources_per_worker={"GPU": 1, "CPU": 10},
    ),
    run_config=RunConfig(
        name="cosmos3-action-policy",
        failure_config=FailureConfig(max_failures=0),
    ),
)
trainer.fit()
```

生成的配置使用 LoRA rank 32：**3070 万可训练参数**，约占 16B 模型的 **0.2%**。在 48 GB 的 L40S 上，验证过的单 rank batch 上限是 4；有效 batch size 通过梯度累积扩展，而不是加大单 rank batch。模型分片在单节点的 4 块 GPU 上，而 PyAV 在 CPU worker 上解码三相机 LeRobot 流。

在一次验证过的 4×L40S、60 iteration 运行中，窗口平均损失按三等分从 **12.20 → 10.66 → 8.93** 下降。分布式 checkpoint 落在第 30 与第 60 iteration；每个约 **86 GB**，因为包含模型、EMA 与 fp32 优化器状态。技能会在长跑开始前把这些负载专属约束呈现出来。

想看更接近常规 Ray Data → Ray Train 的 VLA 流水线，请阅读 [*Optimizing VLA Fine-Tuning Performance with LeRobot Datasets and Ray*](https://www.anyscale.com/blog/vision-language-action-pipelines-vla-robotics-ray-anyscale)：在 DROID 上，文件分组分区把冗余视频打开次数降低了 **135 倍**，从 286,000 降到 2,124。

## 深潜：驾驶 VLA 的闭环 RL 后训练

微调与服务化已是熟路。技能支持的最难负载——也是最能体现 Ray 与 Anyscale 价值的那个——是自动驾驶 VLA 的**闭环强化学习**。

### 为什么闭环不同

物理 AI 技能同时支持开环与闭环 RL。开环 RL 是更简单的起点：它把策略预测的轨迹与数据集中记录的轨迹比对打分，不运行仿真器。由于系统只需要训练策略并生成 rollout，其 GPU 显存与计算需求相对温和。

闭环 RL 回答更难的问题：如果车辆真的执行策略的动作会发生什么？它让策略与一个会对每个决策作出反应的仿真器**成环**。这产生更真实的反馈，但也明显更耗资源、运维更复杂。策略训练、rollout 推理、场景渲染、物理与仿真必须一起运行，既推高 GPU 显存与计算需求，也新增协调与故障模式。NVIDIA 的 [**AlpaSim**](https://github.com/NVlabs/alpasim) 提供这种反应式驾驶环境，[**AlpaGym**](https://github.com/NVlabs/alpagym) 把它接入 GRPO 训练，让奖励反映策略实际驾驶后的结果。

技能从同一个自然语言入口抵达这里：

```
Use the /anyscale-workload-physical-ai skill to run closed-loop GRPO post-training for Alpamayo-1.5 with AlpaSim.
```

闭环改变了显存画像。验证过的 AlpaGym 配置采用全参数策略更新、一个专用的策略推理 rollout 运行时，仿真器同在一台 8× A100-80GB 节点上。技能会在启动前标记这个昂贵的 worker，并建议在 Anyscale Workspace 中验证整套栈。

*Anyscale 上的闭环 GRPO：Cosmos-RL trainer + VLLM rollouts + AlpaSim（嵌套 Podman）。*

### Ray 与 Anyscale 解决了什么

管道工程在这里动真格，技能内置的修复在此兑现价值：

- **没有 Docker daemon 的嵌套容器。** AlpaSim 是一个六服务的 gRPC 栈。生成的负载用带 Docker 兼容 socket 的 rootful Podman 运行它。
- **真正可用的 GPU 透传。** 在这条验证过的 Podman 路径上，Compose 的 GPU 预留与 `--gpus` 均被忽略。生成的负载会逐服务打上 `NVIDIA_VISIBLE_DEVICES` 赋值补丁，并以 legacy 模式使用 `nvidia-container-runtime`。
- **有依据地选硬件。** 用 L40S 的小型 GPU 节点会撞显存墙。验证配置采用 8× A100-80GB，并用 `PREFER_SPOT` 与跨可用区扩容改善容量可得性。
- **门控访问、双重核验。** Alpamayo 权重与 `PhysicalAI-Autonomous-Vehicles-NuRec` 场景需要各自独立的 Hugging Face 授权。负载在用掉 A100 worker 之前以真实文件下载核验两者。

Ray 层刻意保持薄：在一个 worker 上预留全部 GPU，把验证过的多进程 harness 派发给它。在那个任务内部，训练/rollout/仿真循环由 AlpaGym 掌管。

```
import ray

@ray.remote(num_cpus=24, max_retries=0)
def run_phase(script: str, args: list[str]) -> int:
    return subprocess.run(
        ["bash", script, *args],
        cwd="/mnt/cluster_storage/alpagym/bundle",
        check=False,
    ).returncode

# Reserve all eight GPUs on the p4de worker. Inside this task, AlpaGym starts the
# Cosmos-RL trainer, AlpaGym rollout runtime, and nested-Podman AlpaSim services.
task = run_phase.options(num_gpus=8, accelerator_type="A100-80G")
return_code = ray.get(task.remote("run_all.sh", ["trend"]))
assert return_code == 0
```

### 智能体验证展示了什么

验证确认整条流水线能在 Anyscale 上端到端运行：自定义镜像、两项访问授权、嵌套 Podman 的 AlpaSim、Cosmos-RL 策略更新、AlpaGym rollout 与 checkpoint 导出。

最初的 smoke 配置使用粗粒度的 `progress_safety` 奖励、batch 为 1。它跑完了，但 `reward_std=0`，GRPO 没有组内学习信号。A100 趋势配置改用 `distance_to_gt`、`train_batch=8`、随机采样与多代生成。在一次 12 步运行中，`reward_std` 保持在 **0.001 到 0.011** 之间且损失下降，说明存在非零的优化信号。

运行**并未**显示奖励的明确上升。它只覆盖了一到五个基础策略已接近记录轨迹的常见场景。要评估策略质量改进，需要更难、更长的长尾场景、更多训练步，以及更多 rollout 与 trainer 副本。因此配套的 health scraper 分开检查三个条件：非零奖励方差、奖励趋势与损失趋势。这些结果验证了训练 harness 与学习信号的存在，但尚未验证策略质量的提升。

## 闭环：从一个负载到数据飞轮

各支柱合在一起比分开更强。一旦策略能在同一平台上被微调、服务化并在仿真中评估，这些环节就能组合成**数据飞轮**：训练策略、上线服务、在仿真器中 rollout、保留成功的轨迹、把它们并回数据集、再训练。我们用 π0.5 策略与 Isaac Lab Franka rollout 验证了这个环——Ray Train、Ray Serve 与 Ray Core 仿真 worker 跑在同一集群上，内置基于奖励过滤的数据集合并与前后对比。

把轨迹并回的最简方式是直接 union：把原始示教与越过奖励阈值的仿真 episode 拼接。这是完全够用的起点，也是我们验证飞轮时所用——但仿真/真实数据的配比本身就是值得调的旋钮，随着飞轮成熟，建议升级到更精细的策略。仿真数据太少，永远触及不到本应由仿真器暴露的长尾案例；太多，策略会向仿真器能刻画的行为漂移，遗忘其无法捕捉的真实世界细节——sim-to-real 差距反而扩大。由于合并只是一个 Ray Data 操作，你可以把朴素拼接换成加权或分层采样——限制仿真占比、过采样稀有场景、或在训练中做课程式仿真/真实混合——而无需改动飞轮的其余部分。

因为每个环节都使用标准 Ray API，飞轮不是一套单独的编排系统。它在单个 Python 原生工作流中组合 Ray Train、Ray Serve、Ray Core 与 Ray Data，可随数据集演化反复重跑。

*数据飞轮：训练策略、服务化、在仿真中 rollout、筛选成功轨迹、再训练。*

## 从开发到 Anyscale 生产

Anyscale Physical AI Skill 生成负载；**Anyscale Platform Skills** 负责运行与运维它。`/anyscale-platform-run` 启动，`/anyscale-platform-inspect` 读取运行中的负载状态，`/anyscale-platform-fix` 诊断并修复失败的运行。推荐路径是先在一个 [Anyscale Workspace](https://docs.anyscale.com/platform/workspaces/) 中验证，再把有限时长的训练与仿真负载晋升为 [Anyscale Job](https://docs.anyscale.com/platform/jobs/)，把生产端点晋升为 [Anyscale Service](https://docs.anyscale.com/platform/services/)。当不需要机器人专属编排时，技能会把通用负载路由到 `/anyscale-workload-ray-train`、`/anyscale-workload-ray-serve` 或 `/anyscale-workload-ray-data`。
