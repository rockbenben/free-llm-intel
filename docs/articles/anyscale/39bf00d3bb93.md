# 发布 Anyscale Runtime：由 Ray 驱动，让 AI 更快、更便宜、更具弹性

作者：Richard Liaw 和 Philip Wang | 2025 年 11 月 4 日

现代 AI 工作负载——从多模态数据处理到分布式训练和高吞吐推理——正在把基础设施推向极限。这些负载处理日益复杂的数据集（文本、视频、图像），依赖更大的、以 GPU 为主的先进模型，同时仍然依赖 CPU 完成解码、文件缩放等预处理任务。要大规模运行它们，需要在异构算力上的高效编排、高性能执行，以及硬件故障后的快速恢复。

开源分布式计算框架 Ray 提供了把 AI 与 Python 应用从单机扩展到数千台机器的必要基础——在异构（CPU + GPU）集群上进行任务并行与基于 actor 的计算。随着 AI 工作负载的规模与多样性持续增长，团队往往需要更强的可靠性保证，以及针对吞吐量、延迟、成本等具体负载需求调优的更高性能——若无分布式系统或云基础设施的深厚专长，这些挑战很难解决。

**Anyscale Runtime** 解决了全部这些问题。该 runtime **完全兼容 Ray API**，你可以直接带入现有应用——无需重写代码，没有锁定——同时获得：

- **更高的故障韧性**，减少算力浪费、提升大规模流水线的稳定性。支撑特性包括作业检查点（暂停/恢复批量推理处理）、epoch 中途恢复（暂停/恢复训练作业中的分布式数据加载）以及动态内存管理，可减少训练与推理负载的溢出和 OOM 错误。
- **相比运行开源 Ray 更快的性能与更低的计算成本**，覆盖大量目标负载——包括图像批量推理、特征处理、强化学习等。

与 [Anyscale platform](https://www.anyscale.com/product/platform) 的其他组件组合使用，团队能更快、更经济地构建和部署 AI 工作负载。Geotab——一个用于分析驾驶行为、提升道路安全的 AI 驱动远程信息处理平台——在在线（低延迟）视频处理上取得了 43 倍吞吐量提升与 4 倍 GPU 利用率改善。同样，AI 行程规划领域的领先者 TripAdvisor 借助 Anyscale 为其批量嵌入处理流水线节省了 70% 的成本。

想亲自验证 Anyscale Runtime 的能力，请查看我们的 [GitHub 仓库](https://github.com/anyscale/rayturbo-benchmarks/tree/main/)，探索并复现基准测试负载——我们将持续更新新数据集与配方。

## **Anyscale Runtime 提供为生产级 AI 优化的韧性与恢复能力**

想象一下——你在十块高端 GPU 上跑了 19 个小时的长训练，然后崩溃了。数万美元的算力——没了。你被迫从零重启，钱和时间都在燃烧。除成本之外，这类故障延误进度、推迟交付日期，侵蚀你的 AI 投资回报。如果因此丧失竞争优势，这种低效的代价更为高昂。

Anyscale Runtime 引入了若干为规模化的韧性与快速恢复而设计的特性，让团队专注于推进模型，而不是重做工作：

- **Ray Data 中的动态内存管理** —— 自动调整内存用量，减少训练与推理过程中的溢出与 OOM 错误。
- **作业检查点（Job Checkpointing）** —— 让长时间运行的推理负载可以暂停并恢复而不丢失进度。
- **Epoch 中途恢复（Mid-Epoch Resume）** —— 当使用 Ray Data 加载数据时，允许大规模训练作业从保存状态中途重启，避免时间和算力的浪费。

## **Anyscale Runtime 带来更快性能与更低的单次运行成本**

Anyscale Runtime 跨多种负载优化执行：更快更便宜的数据处理作业、更可靠的训练运行、更高吞吐的服务。我们的可复现基准显示：

- 图像批量推理快 2 倍、成本效率提升 6 倍
- 特征处理（编码、归一化等）快 10 倍
- 结构化数据处理快 2.5 倍
- 强化学习可扩展性提升 8 倍
- 高吞吐服务的 QPS 提升 7 倍
- 在线推理应用中的视频处理快 40%

以下是各负载的简要总结。想直接查看代码与数据配方、检验基准，请访问我们的 [GitHub 仓库](https://github.com/anyscale/runtime-benchmarks/tree/main/)。

### **图像批量推理**

流水线读取 JSONL——用 CPU 解码并变换图像批次，然后在 GPU 上用视觉 Transformer 模型推理，最后再用 CPU 将结果写回 JSONL。使用的数据集约 10TB。

可复现基准配方：[GitHub](https://github.com/anyscale/runtime-benchmarks/tree/main/image-batch-inference)

**性能：** 固定集群规模下，开源 Ray 用时 772 秒，Anyscale Runtime 用时 431 秒**（约快 2 倍）**

**成本：** 固定集群下 $63 对 $170（便宜 2.7 倍）；自动扩缩容运行下 $23 对 $142**（便宜 6 倍）**

### **特征预处理**

特征预处理——如编码和归一化——是 ML 中最反复迭代的环节之一。通常从小数据集实验开始，但在生产中迅速扩展到成百上千倍的数据。为评估这种增长模式下的性能，我们在 **OrdinalEncoder** 负载上以 **1GB 到 1TB 的数据集规模**对比了 Anyscale Runtime 与开源 Ray。

可复现基准配方及按数据集规模的性能：[GitHub](https://github.com/anyscale/runtime-benchmarks/tree/main/preprocessors)

**性能：** 随着负载规模增大，Anyscale Runtime 始终取得 10 倍或更好的性能，同时保持执行稳定。

### **结构化数据处理**

尽管文本、视频、图像等非结构化数据日益重要，结构化数据处理仍是现代数据与 AI 流水线的关键部分。涉及 join、聚合与过滤的负载常因序列化开销与大量 shuffle 而遇到性能瓶颈——使用 Python UDF 时尤甚。为评估这些常见条件下的性能，我们运行了 **TPC-H Q1 基准**。

可复现基准配方：[GitHub](https://github.com/anyscale/runtime-benchmarks/tree/main/tpch)

**性能：** 在 Scale Factor（SF）1000、128 个 CPU 的基准下，Anyscale Runtime 以 99.1 秒完成任务，Ray 约需 913 秒（10 倍加速）

### **高吞吐服务**

高吞吐服务对推荐引擎、欺诈与异常检测等实时系统至关重要。这类负载必须应对突发流量——每秒数千查询（QPS）——同时保持低延迟与一致性能，还不能过度配置资源。

Ray 可跨副本和节点动态扩缩，在负载下维持吞吐。Anyscale Runtime 在此基础上扩展了直接入口（direct ingress），精简请求到推理的路径，使服务更快更高效。为测试 QPS 扩展能力，我们基准测试了一个推荐模型，包含两个 Ray Serve 部署：一个负责请求处理与候选生成的 Ingress 服务，一个在 GPU 上运行深度学习推荐模型的 Ranker 服务。

可复现基准配方：[GitHub](https://github.com/anyscale/runtime-benchmarks/tree/main/serve-throughput)

**性能：** 使用 locust 模拟用户请求，在最大的运行（4 个 GPU 副本——Ranker 与 Ingress 部署副本保持 1:2 比例）中，Anyscale Runtime 支持 6300 req/s，Ray 为 900 req/s（提升 7 倍）

### **在线（延迟敏感）视频处理**

实时视频处理极具挑战，因为它把需要大量计算的大型数据集与严苛的延迟约束结合在一起——而从目标检测到自主系统这类"能看"的多模态应用日益需要它。这些负载运行横跨 CPU 与 GPU 阶段的复杂异构流水线——流程类似：视频输入 → 分块 → 抽帧 → 目标检测 → 结果。

可复现基准配方：[GitHub](https://github.com/anyscale/runtime-benchmarks/tree/main/serve-video-perf)

**性能：** 实现了两种推理场景：*分块推理*（每个 chunk 独立处理）与*合并推理*（对需要合并整段视频的应用把所有帧一起处理）。两种场景下，Anyscale Runtime 相比开源 Ray 均有**约 40% 的提升**。
