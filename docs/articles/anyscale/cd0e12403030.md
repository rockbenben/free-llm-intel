Double 11 已经成为全球最大的线上购物活动。为了支撑这种量级的线上活动，Ant Group 实现了一套基于 Ray 的灵活、高性能、稳定且可扩展的在线资源分配系统。

Double 11 已经成为全球最大的线上购物活动。为了支撑这种量级的线上活动，Ant Group 实现了一套基于 [Ray](https://github.com/ray-project/ray) 的灵活、高性能、稳定且可扩展的**在线资源分配系统**。该系统的部署规模已超过 6000 个 CPU cores，目前应用于非常广泛的使用场景，包括营销和订单分配。为此，需要考虑许多技术挑战，例如：

- 在线、近线和离线系统之间的工程链路复杂，如何降低多套系统带来的开发与维护成本。
- 如何在大规模线性规划（LP）问题上实现高性能求解。
- 当要求的 SLA 为 99.99%（即一年内的服务停机时间不超过一小时）时，如何保证在线服务的高可用。

本文以营销、搜索、推荐和广告场景为例，介绍基于 [Ray](https://docs.ray.io/en/master/) 的在线资源分配系统的一些应用。

## Link**1. 问题描述**

在推荐、搜索、营销和广告系统中，在线决策需要同时考虑点击率和转化率等偏好指标，以及资金、成本、流量等约束。在线资源分配要解决的，是在资源有限的约束下最大化整体 ROI。例如：

- 当某些优惠券库存有限时，如何最大化平台的总销量

## Link**2. 在线资源分配的抽象模型**

在线资源分配系统需要为每个到来的请求在线匹配合适的资源，同时考虑可用资源有限，以最大化整个系统的收益。在优惠券的例子中，请求的主体是用户，资源是优惠券。对于每个用户 *i*，平台可以估计 *j* 张优惠券带来的收益值 ![c_ij Ant Updated to be bigger](https://images.ctfassets.net/xjan103pcp94/5PBKVtTXmY4POBGKD04jZj/6cc76191d7a94063ef107d7c5f392212/c_ij_150.svg)，并选择其中一张推送给该用户。当没有资源约束时，每个在线决策就是选择最大的 ![c_ij Ant Updated to be bigger](https://images.ctfassets.net/xjan103pcp94/5PBKVtTXmY4POBGKD04jZj/6cc76191d7a94063ef107d7c5f392212/c_ij_150.svg)。当存在资源约束（例如每张优惠券 *j* 都有库存上限）时，最优解就不再是平凡的。假设总共有 *K* 个资源约束 ![ant b_k svg](https://images.ctfassets.net/xjan103pcp94/3nxIY4m1Mq6zVleBRgVHuv/b772e122d602e3c0d471edec04d889aa/ant_b_k.svg)，每个用户 *i* 被授予 ![ant x_ij](https://images.ctfassets.net/xjan103pcp94/3W1AnOBZuhPBQXxJaXxemb/cb359355952595836e719cd189bc3fd9/ant_x_ij.svg) 张优惠券 j，每张都会消耗第 k 个资源约束中的 ![ant m_ij^k](https://images.ctfassets.net/xjan103pcp94/1gFOuXpD3pyKT6IOySsD1Z/60d66528c902bbfa1b4b19cce76cebda/m_ij-k_100.svg)。那么在线资源分配就可以建模为一个 LP 问题 ![max_x_ij_c_ij](https://images.ctfassets.net/xjan103pcp94/6fNj0ha1QKbA3Wmtp3W9F0/6b83a9db0e3372f28701fe676218fc93/ant_max_sum_ij_x_ij_c_ij.svg)，求解决策变量 ![ant x_ij](https://images.ctfassets.net/xjan103pcp94/3W1AnOBZuhPBQXxJaXxemb/cb359355952595836e719cd189bc3fd9/ant_x_ij.svg)，使其在全局资源约束 ![ant_sum_m_ij^k_lessb_k](https://images.ctfassets.net/xjan103pcp94/3KfbNMoOB8XjwycDqY7rAD/1e2393a24b7a15071daefabb11ebbb5b/ant_sum_m_ij-k_lessb_k.svg) 下最大化整体收益。对于推荐、搜索、广告等工业应用场景，问题的变量规模常常是 1 亿（用户）* 10000（候选集），资源约束规模可超过 10000。

从实时决策的角度看，未来信息不可预知，无法提前确定全局最优解。要解决这个问题，我们需要考虑对未来信息的估计及其不确定性。一方面，可以把全局问题分解为实时子问题进行学习；考虑到在线应用环境变化很快，子问题需要以高时效（分钟级）求解。另一方面，我们要能快速服务单个决策请求。

在实现方案的设计上，我们拆分了不同的技术模块，包括：

- 在线决策服务
- 实时规划算法

在线决策服务使用问题在[线性规划对偶](http://theory.stanford.edu/~trevisan/cs261/lecture06.pdf)中的等价形式，并把实时规划算法计算出的对偶变量 ![lambda k](https://images.ctfassets.net/xjan103pcp94/7Df27UKdqIHyVQrK4oaezk/519d7841f38c5a73ca765918d843f201/ant_theta_k.svg) 作为输入参数，实现在线快速服务。

在实时规划算法的技术方案中，围绕精准预算控制与收益估计，设计了若干算法模块，包括：

- 实时模型校准：结合实时用户反馈，对前置模型的预测进行概率校准（如 CTR 和 CVR），保证良好的点估计性质。
- 实时流量预测：预估场景和活动的未来流量，实时拆分并平滑总预算。
- 实时约束修正：考虑到部分资源消耗的不确定性或滞后性，需要结合实际资源消耗，实时修正预期的预算消耗进度。
- 大规模/在线 LP 优化：求解在给定约束下收益最大化的规划问题。

这些算法的实现涉及离线、近线、在线链路以及不同的计算范式。在线链路直接面向用户请求，同步 RPC 调用，要求高可用、低延迟（ms 级）。近线链路允许基于在线请求结果快照进行实时规划，可以采用优化算法并在秒级返回所需的解。离线链路允许根据历史数据进行流量估计，可以在分钟级返回所需的解。

## Link**3. 系统架构与实现**

在线资源分配方案涉及复杂的工程实现，依赖离线和实时数据。算法的实现同时依赖实时计算与迭代计算。我们基于 Ray 构建了流式计算、服务化和迭代计算。物理架构如下图所示：

在线资源分配方案的物理架构

Physical architecture of online resource allocation solution

基于 Ray 的实时规划算法的逻辑包括：

- 迭代计算：拉取历史数据，使用时间序列模型预测未来的流量数据。
- 实时数据的流式处理并生成批量样本。到达 LP 求解周期时，流式链路把批量样本发送给 serving。serving 收到批量样本后，用它们求解 LP 优化问题。通过 Ray 的 [placement group 特性](https://docs.ray.io/en/master/)把求解器的 actor 部署到 GPU 机器上，并利用 GPU 对算法进行并行化。
- 实时校准模型的在线学习与训练。利用 Ray actor 天然的组网特性，实现 bulk synchronous parallel 模式的迭代计算。
- Ray streaming：当业务系统资源分配的最终结果与算法决策结果存在差距时，可用于累积实时分配结果以修正 LP 算法。

对偶变量求解出来后，可直接用于在线 rerank——这是一个要求高 SLA 的在线系统。我们基于 Ray 构建了在线服务框架，允许用户把任意业务逻辑发布为在线服务并进行流量控制，而无需关心资源部署、资源扩缩和集群容灾。

每个在线服务实例是一个由三类 Actor 组成的 Ray job：

- Master Actor：管理 Router Actors 和 Worker Actors。
- Router Actor：负责接收来自业务系统的请求，并按照流量控制策略把请求路由到指定的 Worker Actors。
- Worker Actor：接收来自 Router Actor 的请求并执行用户定义的业务逻辑。

在多数据中心/多 Cluster 的场景下，该在线服务框架包含一个名为 Keeper 的组件，它确保用户的在线服务 job 能在每个 Ray Cluster 中启动，并且可以在各 Cluster 之间进行流量切换，从而实现跨 Cluster 的 failover 能力。

在线服务实例一旦创建，在线业务系统就可以通过该框架提供的 Client 调用它。在线服务请求会由 Ray job 中的 Router Actor 接收，并路由到某个 Worker Actor 执行业务逻辑。

基于 Ray 方案的在线资源分配具有以下优势：

- Ray 提供了简单易用的 API，开发者可以快速实现上层框架。例如，我们用 **50 行代码**实现了 bulk synchronous parallel 模式的迭代计算。在线资源分配所涉及的离线、近线和在线链路全部基于 Ray 实现，大大降低了开发的学习与维护成本。

## Link**4. 总结**

基于 Ray 的在线资源分配方案已在 Ant Group 稳定运行，成功支撑了 Double 11、Double 12 等大型活动，部署规模达到超过 6000 个 CPU cores。目前，基于 Ray、使用单张 GPU 卡即可在秒级求解包含数百万变量和数百条约束的 LP 优化问题。为应对未来需求的增长，Ant Group 目前正在探索基于 Ray 的 GPU LP 求解方案——同一台机器上的多张 GPU 卡，或跨多台机器的多张 GPU 卡。这只是 Ant Group 对 Ray 的众多使用与贡献之一。例如，[Ant Group 还把 Ray 用作其 fusion engine 的分布式计算底座](https://www.youtube.com/watch?v=Wwv9YNlXx0Q)，并持续向 [Ray](https://github.com/ray-project/ray) 做出大量贡献，比如 [Java API](https://youtu.be/AFHyIEIfQYw)。如果你想更深入地了解我们如何使用 Ray，欢迎观看我们在即将举行的 [Ray Summit](https://raysummit.anyscale.com/) 上的演讲！
