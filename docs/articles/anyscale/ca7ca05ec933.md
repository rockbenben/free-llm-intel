# 编码智能体成本降低 90%：在 Anyscale 上用 Ray + vLLM 安全地提供 LLM 服务

作者：Kunling Geng、Aydin Abiar 和 Xing Fang | 2026 年 10 月 8 日

编码智能体会不断把仓库上下文、指令、工具结果和对话历史发出去，用来生成动作。这类工作恰恰是你手头最敏感的那些：你的源码、内部文档、架构决策，每一次按键都在把它们送出你的安全边界。[把运行时握在自己手里](https://www.anyscale.com/blog/learning-loops)，这些东西才始终属于你：代码、trace，以及那些最终能帮你把模型后训练得更贴合团队用法的使用数据。

除了数据隐私，按 token 付费的闭源 LLM 还意味着每位开发者、每个请求都有一条线性增长的账单，团队规模和智能体数量上去之后，也拿不到任何规模效应。把运行时握在自己手里同样改变了这一点，因为团队可以共享底层的 GPU。[BMW 算过这笔账](https://youtu.be/yKt-CpfrOIE?si=mFz8jRYluEfBFqpg&t=46)：少到 8 位开发者，从 API 转向自建推理就已经划算。但为编码自建自管一套 LLM 服务平台，在跑 GPU 集群时有它自己的运维难题。

成本方面，我们的成本模型给出的关键结论是：按每位开发者算，自托管只是按 token 计费的 API 价格的一个零头：

- **常驻服务：** 每月约 $2,920，折合每位注册开发者约 $58。
- **仅工作时段服务：** 每月约 $840，折合每位注册开发者约 $17。
- **API 基线：** 一位活跃开发者的 Claude Code API 等效开销，每月常常达到 $800 左右。

这些数字的前提是：RTX PRO 6000 每 GPU 节点小时约 $4，50 位注册开发者共用一块 GPU。它们属于规划用的推算，不是 TCO；完整的假设和限制见下文的成本对比一节。

在省钱之外，优化服务基础设施带来的性能提升同样可以量化。

我们实测评估的主要结论表明性能有显著提升：

- **恢复编译缓存，编译快 8.0 倍。** 在未启用 MTP 的 NVFP4 配置下，编译时间从 48.5 秒降到 6.0 秒。
- **用 CPU 侧 KV 缓存分层，请求吞吐提升 3.79 倍。** 在单副本的 GLM-5.2 评估中加入 512 GiB 的 CPU 缓存层后，58 条共同 prompt 的缓存 token 占比从 6.1% 升到 74.9%，TTFT（首 token 延迟）中位数从 48.4 秒降到 9.2 秒。
- **推测解码带来 1.86 倍的输出吞吐。** 多 token 预测（MTP）把输出吞吐从 65 tokens/s 提升到 121 tokens/s。
- **启用 CUDA graphs 后输出生成快 2.87 倍。** 与 eager 模式相比，客户端观察到的 token 吞吐从 15.9 tokens/s 提升到 45.6 tokens/s。

本指南提供一条分步路线，涵盖模型与硬件选型、服务部署、单副本调优、结合缓存感知路由的自动扩缩，以及多模型运维。

- **vLLM**：推理引擎，把模型加载到 GPU 上并生成 token。

## 编码智能体如何改变服务负载

### 编码智能体产生的远不止聊天流量

编码智能体的 prompt 把系统指令、仓库上下文、工具定义、诊断信息和对话历史拼在一起，产出的却往往只是一次简短的工具调用或一处编辑。这让负载呈 **prefill 密集**形态：庞大的输入主导了首 token 时间（TTFT）。

这些上下文大部分会在轮次之间重复，为[自动前缀 KV 缓存复用](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)留下了很大空间。到了团队规模，相互关联的请求突发又添上一层挑战。因此一个高性能平台必须同时平衡四个目标：低 TTFT、流畅的 token 流式输出、高缓存复用率，以及弹性容量。

图 2. 一个示意性的编码智能体会话：每一轮都重新发送一个庞大且高度重复的 prompt，只为产出一小段输出。每轮只有新增内容（橙色）需要重新做 prefill，其余都可以从 KV 缓存里取。

图 2. 示意性的编码智能体会话

编码智能体的运行外壳充当 API 客户端。配置了自定义端点之后，本地外壳——对 Cursor 这类托管客户端则是它的云端后端——会把请求发给一个兼容的模型服务，而不再依赖默认的托管模型。由于这些客户端使用不同的 API schema 和端点，服务基础设施必须把对应的路由暴露出来。仓库的[客户端集成指南](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part2-connect-clients-production/README.md)配置了这三条路径：

| **编码智能体** | **API 路径** |
| --- | --- |
| Cursor | `/v1/chat/completions` |
| Claude Code | `/v1/messages` |
| Codex | `/v1/responses` |

在 Anyscale 上托管开源权重模型可以带来几方面好处：

- **降低成本：** 当利用率足够高、能摊平固定基础设施开销时，单个 token 的边际成本更低。
- **掌控容量：** 减少对单一供应商速率限制的依赖，自行管理容量和排队。
- **安全与数据掌控：** 把推理链路的更多部分留在自己的网络之内。
- **降低模型供应商锁定：** 自己掌握模型和服务升级的节奏。
- **用自己的数据演进模型：** 采集经过审批的智能体 trace，用 [Ray Data](https://docs.ray.io/en/latest/data/data.html) 做筛选和评估，再用 [Ray Train](https://docs.ray.io/en/latest/train/train.html) 或某个 RL 框架后训练，转起数据飞轮。

**社区与透明度：** 借助开放生态来理解并定制模型行为。

### Ray Serve LLM 把它扩展到生产规模

vLLM 负责核心推理优化——[前缀缓存](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)、[分块 prefill](https://docs.vllm.ai/en/stable/configuration/optimization/#chunked-prefill)、[量化](https://docs.vllm.ai/en/stable/features/quantization/quantized_kvcache/)、[推测解码](https://docs.vllm.ai/en/stable/features/speculative_decoding/)、[模型并行](https://docs.vllm.ai/en/stable/serving/parallelism_scaling/)——但一套稳当的部署需要的不止这些。Ray Serve LLM 在其上加了一层生产能力，用来：

- 在多 GPU 环境之间扩展副本。
- 依据负载和缓存状态智能路由请求。
- 对外提供兼容 OpenAI 与 Anthropic 的 API。
- 让 token 从副本经 HAProxy 流式输出，同时绕过旧的 Python 接入跳。
- 把服务、模型和 GPU 的指标集中管理。
- 为 Wide-EP、prefill 分离这类复杂的多节点部署提供顺手的构建器

已公开的[近期 Ray Serve LLM 基准测试](https://www.anyscale.com/blog/high-performance-distributed-inference-ray-serve-llm-vllm-google-kubernetes-gke)显示，在引入 HAProxy、直接流式输出和 RayExecutorV2 之后，相对较早的不做批处理的 Ray Serve LLM 基线，prefill 密集型负载的累计吞吐最高提升 4.4 倍，decode 密集型负载最高提升 24.8 倍。在 Anyscale 上，Ray Serve LLM 还在推理引擎外围补上了托管的自动扩缩、可观测性和容错。

## 为编码智能体部署一个 LLM

一次可落地的部署分四步：

- 依据任务质量和服务占用面来选模型。
- 选择硬件和并行策略。
- 配置 vLLM 引擎和 Ray Serve 部署。
- 部署服务并逐个验证各编码客户端。

### 第 1 步：按任务成功率选模型，而不是只看榜单排名

开源权重模型的质量迭代很快。[Agent Arena 的开源模型智能体榜单](https://arena.ai/leaderboard/agent?license=open-source)这类智能体榜单适合作为起点，Qwen、DeepSeek、Kimi、GLM 等模型家族也日益聚焦编码和工具调用。但公开榜单只是起点，Anyscale 的 LLM 专家可以帮你为具体负载挑到最合适的模型。

常见的基准包括考察真实仓库 issue 解决的 [SWE-bench](https://www.swebench.com/)、考察终端任务的 [Terminal-Bench](https://www.tbench.ai/benchmarks)、考察长程多工具工作流的 [Toolathlon](https://toolathlon.xyz/introduction)、考察对话式工具调用的 [τ-bench](https://taubench.com/)、考察漏洞分析的 [CyberGym](https://www.cybergym.io/cybergym/)，以及考察专业知识工作的 [GDPval-AA v2](https://artificialanalysis.ai/evaluations/gdpval-aa)。分数通常反映的是整个智能体系统，而不仅仅是模型本身，所以只有在基准版本和评测设置一致时结果才可比。

用自己的活儿来评估候选模型：

- 多文件编辑与仓库导航。
- 跨多轮的结构化工具调用。
- 长上下文下的指令遵循。
- 调试与测试修复。
- 延迟，以及完成任务所需的轮数。

一个更小的模型如果一次可靠地就能完成日常工作，可能比需要更多 GPU 的大模型更便宜；一个更强的模型如果能避免重试，在难题上反而更划算。要衡量的是**每个成功任务的成本**，而不只是每百万 token 的成本。

### 第 2 步：让权重、运行时内存和 KV 缓存匹配硬件

GPU 显存要装下模型权重、KV 缓存、临时激活值、CUDA graphs 以及运行时开销。权重占的显存基本固定，随参数量和精度线性变化，所以当未量化的权重卡住部署时，**权重量化**就成了关键。KV 缓存保存活跃请求的 attention 状态，会随上下文长度和并发数增长。对长上下文的编码智能体负载来说，**KV 缓存量化**同样能压低每个 token 占用的显存。在硬件支持且质量验证通过的前提下把两者都量化，就能为并发的长请求腾出更多空间。

选择量化策略时，可以考虑以下几种格式：

- [**FP8**](https://docs.anyscale.com/llm/serving/performance-optimization)**：** 在硬件和运行时支持的前提下，权重和 [KV 缓存](https://docs.vllm.ai/en/stable/features/quantization/quantized_kvcache/) 都很合适的一个选择。相比 BF16 大致把原始存储减半；质量则仍取决于模型、任务和校准。
- [**NVFP4**](https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/)**：** 在 NVIDIA Blackwell GPU 上，该格式相比 FP8 又将被量化张量的原始存储减半。整个 checkpoint 的节省幅度更小，因为部分模块和元数据仍保持较高精度；实测的 Qwen checkpoint 约占 22 GB，FP8 版本是 27 GB，降幅约 19%。
- [**MxFP4**](https://huggingface.co/docs/transformers/quantization/mxfp4)**：** 4-bit 精度的开放替代方案，`gpt-oss` 等模型在用。

注意：硬件加速能发挥到什么程度，由运行时环境和 GPU 架构决定。这里部署的是 NVIDIA 的 [Qwen3.6-27B-NVFP4](https://huggingface.co/nvidia/Qwen3.6-27B-NVFP4) 权重，但所锁定的 vLLM 版本在 RTX PRO 6000 上对 dense NVFP4 走的是 Marlin 回退路径，而不是原生 kernel。此外，由于该设备不支持 NVFP4 的 KV 缓存，系统默认改用 FP8 KV 缓存。

图 4. 示意的 GPU 显存布局：NVFP4 权重把大部分显存留给 KV 缓存，FP8 KV 能装下的完整上下文数量约为 BF16 的两倍。

图 4. 示意的 GPU 显存布局

### 第 3 步：为模型和负载配置引擎

一份正确的服务配置是随模型而变的。除了显存和并行方式，还必须用对 chat template、reasoning 解析器、工具调用解析器、多模态上限和上下文长度。

仓库的 [Qwen 服务实现](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize/serve_qwen3_6_27b_optimized.py#L138-L182)配置为每个副本一块 GPU、256K 上下文上限、FP8 KV 缓存、本地前缀缓存、分块 prefill，以及 Qwen 专用的 reasoning 和工具解析器。下面的摘录给出相关的引擎参数；推测解码和编译缓存的行为在该实现里是单独配置的：

```
engine_kwargs = {
    "tensor_parallel_size": 1,
    "max_model_len": 262144,
    "gpu_memory_utilization": 0.9,
    "max_num_seqs": 32,
    "max_num_batched_tokens": 8192,
    "enable_prefix_caching": True,
    "kv_cache_dtype": "fp8",
    "quantization": "modelopt",
    "reasoning_parser": "qwen3",
    "tool_call_parser": "qwen3_coder",
    "enable_auto_tool_choice": True,
    "limit_mm_per_prompt": {"image": 4, "video": 0},
}
```

`max_model_len` 限定单个请求的上下文长度。`max_num_batched_tokens` 充当分块 prefill 的调度预算。`max_num_seqs` 则约束引擎的并发。

### 第 4 步：启用直接流式输出并接入客户端

仓库的[常驻服务配置](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize/service-always-on.yaml#L12-L30)在服务层面打开了 HAProxy 和直接流式输出：

```
env_vars:
  RAY_SERVE_ENABLE_HA_PROXY: "1"
  RAY_SERVE_LLM_ENABLE_DIRECT_STREAMING: "1"
```

按仓库的[编码智能体接入教程](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part2-connect-clients-production/README.md)操作。先部署[优化后的常驻服务](https://github.com/anyscale/llm-serving-for-coding-agents/tree/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize)：

```
anyscale service deploy -f service-always-on.yaml --working-dir .
```

然后从 **Anyscale Console → Services → Query** 复制对外的 `base_url` 和 bearer token。智能体在本地执行工具，但模型请求——包括指令、仓库上下文、对话历史和工具结果——以及模型返回的流式内容都要经过这个服务。

**Claude Code**

导出服务 URL 和 token，然后运行仓库的 [claude-service.sh](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part2-connect-clients-production/claude-service.sh)：

```
export ANYSCALE_BASE_URL=<base_url>/v1
export ANYSCALE_API_KEY=<token>
./claude-service.sh
```

这个启动脚本把服务根地址作为 `ANTHROPIC_BASE_URL` 传给 Claude Code，并通过 `ANTHROPIC_AUTH_TOKEN` 提供 token。

**Codex**

在同一目录下运行 [codex-service.sh](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part2-connect-clients-production/codex-service.sh)：

```
./codex-service.sh
```

它把 `/v1` 这个 URL 注册为一个自定义 provider，选择 `wire_api="responses"`，并把 bearer token 发往 `/v1/responses`。

**Cursor**

按教程里的 [Cursor 配置](https://github.com/anyscale/llm-serving-for-coding-agents/tree/95af323db8951d1a7e5ea588a4e8c706ae15c115/part2-connect-clients-production#cursor-gui)操作，并在 **Cursor Settings → Models → OpenAI API Key** 下填入这些值：

```
Override OpenAI Base URL:  <base_url>/v1
OpenAI API Key:            <token>
Custom model:              qwen3.6-27b
```

## 针对编码智能体流量优化单个副本

### 按既定 SLO 做延迟基准测试

TTFT、ITL、TPOT、prefill、decode 和 goodput 的完整定义见 [Anyscale 的 LLM 指标指南](https://docs.anyscale.com/llm/serving/benchmarking/metrics)。

不要只盯原始 token 吞吐，优先看 goodput，也就是满足目标延迟 SLO 的请求占比。激进的批处理能推高整体吞吐，却会损害交互式流式输出的表现。

### 用真实智能体会话做回放基准

整齐划一的合成 prompt 复现不出真正的智能体循环。真实流量混合着长短不一的轮次、重复的前缀、工具执行的等待，以及长尾的会话时长。要准确地测试你的配置，就把自己的 Claude Code JSONL 会话转换成带时间戳的请求流，保留 prompt 的增长和轮次间隔。如果还没有采集自己的会话，可以用公开的 [WekaTrace Claude Code 智能体会话语料](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-062126-256k)。

每个候选配置都要采集：

- TTFT、TPOT、ITL 以及端到端延迟的分布。
- 完成的智能体轮数与成功任务数。
- 输入/输出 token 数以及 prompt 缓存命中占比。
- 队列深度、抢占、KV 淘汰和 GPU 利用率。
- 工具调用错误和格式异常的回答。

### 按依赖顺序施加优化

下面的[单 GPU 实测](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize/notes/BENCHMARKS.md)都基于一块 RTX PRO 6000。多数 decode 结果用的是平均约 73K token 的真实 Claude 会话 prompt。每一行只动一个旋钮，因此收益不能累加。

| **优化项** | **优化前** | **优化后** | **实测变化** |
| --- | --- | --- | --- |
| CUDA graphs 对比 eager 模式（FP8 权重） | 15.9 输出 tokens/s | 45.6 输出 tokens/s | 2.87x |
| 多 token 预测对比基线（NVFP4 权重） | 65 输出 tokens/s | 121 输出 tokens/s | 1.86x |
| RunAI Streamer | 权重加载约 85 秒 | 权重加载约 25 秒 | 3.4x |
| 恢复编译缓存，vLLM 0.25.1 | 编译阶段 48.5 秒 | 编译阶段 6.0 秒 | 8.0x |

**1. **[**量化权重**](https://docs.vllm.ai/en/stable/features/quantization/)**，让模型高效落位。** 权重量化可以把一个多 GPU 部署压成单 GPU 部署，省掉 GPU 间通信，并腾出显存给 KV 缓存。收益取决于 GPU 的原生 kernel 和 checkpoint 的校准情况。任何一次精度改动，都既是性能改动也是质量改动。

**2. **[**量化 KV 缓存**](https://docs.vllm.ai/en/stable/features/quantization/quantized_kvcache/)**（在支持的前提下）。** 优化后的部署使用 FP8 KV 缓存。按容量推算，在被测的 96 GB GPU 上，BF16 KV 大约相当于 3.27 份 256K token 上下文的 KV 存储，FP8 KV 则是 6.53 份。

**3. 生产环境请保持 **[**CUDA graphs**](https://docs.vllm.ai/en/latest/design/cuda_graphs/)** 开启。** eager 模式下发算子有更多 CPU 参与，适合调试。CUDA graphs 把可复现的 GPU 工作捕获成图，降低启动开销。关掉 eager 模式（即保持 CUDA graphs 开启）后，输出速率从 15.9 tokens/s 提升到 45.6 tokens/s。

**4. 针对目标负载测试 **[**推测解码**](https://docs.vllm.ai/en/stable/features/speculative_decoding/mtp/)**。** 多 token 预测会同时提出并校验后续若干 token，以此降低 TPOT；`num_speculative_tokens` 控制预测的草稿 token 个数（比如设为 3 就是往后预测三个 token）。但净加速取决于接受率和校验开销。在并发 8 下，预测三个 token 得到 99 输出 tokens/s 和 0.50 turns/s，优于预测两个 token（80 tokens/s、0.50 turns/s），而预测四个 token 反而退化到 74 tokens/s。推测深度并非越高越好。输出准确性要放在第一位：上游 issue 记录过 MTP 与前缀缓存同开时工具调用被破坏的情况。启用 MTP 之前，用多轮回归测试把客户端、模型、解析器和 vLLM 之间的兼容性验证一遍。

**5. 精简初始化流程，把冷启动和稳态服务分开看。** 模型下载、权重加载、引擎编译、副本就绪是彼此独立的阶段，都影响部署速度。编译缓存对具体的软件版本、GPU 架构、模型、并行方式和启动参数都很敏感，一份过期的缓存要么直接失效，要么悄悄拖低性能。RunAI Streamer 此前把权重加载的时间降了下来，但仓库的[不兼容矩阵](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize/notes/INCOMPATIBILITIES.md)记录了在所测 vLLM 版本中，它的加载路径与 MTP 存在已知冲突。

实践中的顺序是：先关掉推测解码，确认工具调用正确；eager 模式只在需要调试时使用。正确性确认之后，打开预设的量化和上下文长度，再打开 CUDA graphs。接着调分块 prefill，并测试推测解码。最后优化冷启动，把完整的正确性用例和负载用例重跑一遍。

### 模型成本对比

仓库的[成本模型与假设](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize/notes/COST-ESTIMATE.md)按 RTX PRO 6000 这一配置每 GPU 节点小时约 $4 计算，50 位注册开发者共用一块 GPU。基于这些假设：

| **规划模式** | **GPU 节点小时/月** | **GPU 节点成本/月** | **每位注册开发者成本** |
| --- | --- | --- | --- |
| 常驻 | 730 | 约 $2,920 | 约 $58 |
| 仅工作时段 | 210 | 约 $840 | 约 $17 |

通过 Azure Marketplace 在 [Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/claude-models) 上提供的 Claude，价格遵循 [Claude Opus 5 的价目](https://platform.claude.com/docs/en/about-claude/pricing#claude-in-microsoft-foundry-pricing)：标准输入每百万 token（MTok）$5.00，缓存读取 $0.50/MTok，输出 $25.00/MTok。

一位活跃开发者每月的 Claude Code API 等效开销常常达到 $800。这与业界观察一致，包括 [Pylon 的记录](https://www.linkedin.com/posts/martykausas_our-anthropic-bill-is-about-to-jump-from-activity-7470505066148352000-zqnt)中重度用户达到每月 $800，以及[另一份相近的估算](https://simonwillison.net/2026/May/27/product-market-fit/)给出的 30 天 $1,199.79。公开的 trace 遥测也证实编码智能体负载极度偏向输入 token：

- [WekaTrace 数据集](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-062126-256k)显示输入与输出 token 之比为 117:1。
- SyFI TraceLab 的 [Claude trace](https://tracelab.cs.washington.edu/)记录了 269:1 的比例，prompt 缓存命中率 95.2%。

把 SyFI 的 95.2% 缓存输入占比（按缓存读取计费）算进去，剩下 4.8% 按五分钟的缓存写入计，按 Opus 5 的价格，每位开发者每月 $800 的支出大约对应 922M 输入 token 和 3.43M 输出 token。对一个 50 人的工程团队，每月 API 总用量约 $40,000、171M 输出 token。

每月 $40,000 这个数字只用作 API 支出的参照，不能直接换算成基础设施能省下的钱。短暂的、只针对某一配置的 decode 测试忽略了 prefill 开销、请求排队、整体 GPU 利用率、延迟 SLO 目标以及模型质量上的差异，因此无法可靠预测真实场景下能承载多少 worker。

同理，每位开发者的 GPU 成本只是规划阶段的推算，既不是总拥有成本（TCO），也不构成服务水平承诺。要准确算出需要多少副本、究竟能省多少，得用持续的 trace 回放，对照目标延迟 SLO 和任务成功率来评估 goodput，再把平台额外的运维开销计入。

## 用自动扩缩与缓存感知负载均衡扩容

### 分清引擎上限、准入上限与自动扩缩目标

仓库的[自动扩缩配置](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize/serve_qwen3_6_27b_optimized.py#L204-L220)给了一个具体的起点，[Anyscale 的调参指南](https://docs.anyscale.com/llm/serving/parameter-tuning#ray-serve-autoscaling-configuration)解释了该怎么调。这三个控制项各管各的：

- vLLM 的 `max_num_seqs` 约束单个引擎接纳的序列数。
- Ray Serve 的 `max_ongoing_requests` 约束发往某个副本的请求量。
- `target_ongoing_requests` 告诉自动扩缩器何时该增加副本。

为服务编码智能体的 LLM 部署配置自动扩缩，可以按下面的步骤走：

- **确定 KV 缓存的容量峰值：** 查看服务的启动日志，确认在最大上下文长度下支持的最大并发序列数（例如 256K 上下文窗口通常能撑住约 20 路并发流）。
- **估算实际负载的并发：** 依据平均 prompt 规模来调整序列上限。比如平均 prompt 长度为 85K token，就用 (256K / 85K) x 20 把目标定在约 60 个并发请求。
- **设定硬性准入上限：** 把引擎的调度容量（vLLM 的 `max_num_seqs`）和部署侧的闸门（Ray Serve 的 `max_ongoing_requests`）都设成这个算出来的上限（例如 60）。
- **设定自动扩缩触发点：** 把 `target_ongoing_requests` 设到比准入上限低约 20–30%（例如 40），让副本在请求开始排队之前就先扩容。
- **跟踪指标并持续调参：** 不断评估系统 goodput 和排队情况。当 prompt 长度逼近 256K 上限时调低并发阈值，以便在显存余量变窄时守住尾延迟。

编码智能体场景下，我们建议使用 Ray Serve LLM 的 [KVAwareRouter](https://docs.ray.io/en/master/serve/llm/user-guides/kv-aware-routing.html) 或一致性哈希（会话亲和）。KV 感知路由把前缀缓存复用与 token 负载感知路由结合起来。不过要注意，KV 感知路由目前只兼容 Codex。其他客户端或不兼容的配置，退回到一致性哈希来维持会话粘性。

正如[这篇博客](https://www.anyscale.com/blog/llm-kv-token-aware-routing)详述的，路由器先用 KV 缓存的重叠度估算可以跳过多少 prefill，再估算引擎仍然要做的功：

```
remaining prefill = incoming input tokens - reusable cached tokens
token-load score = weighted remaining prefill + active prefill + ongoing decode
```

路由器选择加权得分最低的副本，必要时会牺牲一些缓存复用换取更均衡的 token 负载。在形态各异的编码智能体 trace 上，相比单纯把缓存复用推到最高，这样能改善 TTFT、TPOT 和吞吐。

### 用 KV 缓存下沉延长缓存的有效生命周期

开发者停下来看代码或组织 prompt 时，团队里其他流量可能把他们会话的 block 从有限的 GPU 显存里挤出去。[KV 缓存下沉](https://docs.ray.io/en/releases-2.58.0/serve/llm/user-guides/kv-cache-offloading.html)把不活跃的 block 挪到容量更大的 CPU 内存或本地存储层，这样它们可以被取回，而不必从头重算。对编码智能体来说，下沉能在用户离开几小时再回来时保住会话上下文——历史是从 CPU/磁盘取回而不是重算，所以回来后依然有很快的 TTFT。

图 5. KV 缓存下沉：空闲的 block 挪到 CPU 或磁盘，复用时直接取回而不是重新计算。

图 5. KV 缓存下沉

在一次针对 GLM-5.2 负载的内部基准测试中，在 GPU 前缀缓存之外加上 512 GiB 的 CPU KV 缓存层，吞吐和延迟都明显好于只用 GPU 缓存。测试在单个节点上进行，配备 8 块 RTX PRO 6000（张量并行度为 8，NVFP4 权重，FP8 KV 缓存），以固定随机种子回放负载，名义窗口为 900 秒。

| **指标（900 秒运行）** | **仅 GPU 缓存** | **GPU 缓存 + CPU 层下沉** |
| --- | --- | --- |
| 完成请求数 | 58 | 215 |
| 请求吞吐 | 0.0625 req/s | 0.2367 req/s |

几个关键的运维结论：

- **吞吐提升：** 整体请求吞吐提高了 3.79 倍。
- **缓存效率更高：** 在 58 条共同完成的 prompt 上，缓存的 prompt token 占比从 6.1% 扩大到 74.9%。
- **延迟下降：** TTFT（首 token 延迟）中位数从 48.4 秒降到 9.2 秒，58 个请求里有 49 个的 TTFT 更低。

## 用多模型路由优化成本

副本路由优化的是硬件效率，多模型路由优化的则是整体开销。它决定多大比例的流量去付前沿模型的 API 溢价，多大比例跑在自建基础设施上。两者一起用，才能真正同时握住性能和成本。

常见的三种策略：

- **按任务复杂度路由。** 日常的编辑、检索和已知的 Agent Skills 交给更小的开源模型；把前沿模型留给困难的推理和关键的改动。
- **自建 LLM 服务容量吃紧时回退。** 如果 GPU 来不及为一次突发快速扩容，就改用经批准的托管模型，而不是放任队列无限增长。
- **托管额度用尽时回退到开源模型。** 订阅或 API 触到上限时，活儿照跑。

一个只占 CPU 的 LiteLLM 网关，可以在多个独立的 Ray Serve LLM 服务和外部供应商之前完成模型选择。仓库里附了一个[可直接部署的网关](https://github.com/anyscale/llm-serving-for-coding-agents/tree/95af323db8951d1a7e5ea588a4e8c706ae15c115/part4-litellm-router/gateway)，带有[主模型、回退模型与复杂度路由的配置](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part4-litellm-router/gateway/config.yaml#L27-L128)，另有一份[路由策略指南](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part4-litellm-router/ROUTING.md)。LiteLLM 的[自动路由文档](https://docs.litellm.ai/docs/proxy/auto_routing)覆盖了路由器底层的复杂度。关键词和技能感知规则既快又容易解释；分类器则能支撑更丰富的策略。显式的用户覆盖始终重要，因为没有哪个路由器能准确预测任务难度。

图 7. LiteLLM 路由网关：为 Claude Code 做成本感知的模型路由。

图 7. LiteLLM 路由网关

在我们内部的配置里，网关把简单请求路由给 Qwen，中等到高阶的文本任务给 GLM，复杂推理或多模态负载给 Claude。为了防止后续的工具结果步骤在流途中悄悄换掉模型，路由器会在会话剩下的整个过程中强制保持会话粘性。

保持这种会话粘性对平稳运行至关重要。编码智能体的迭代常常只把工具输出带回去、并没有新的用户 prompt，如果逐请求地评估路由，就可能让同一个会话在不同模型之间来回切换，而这些模型的 chat 格式、上下文上限和工具机制彼此冲突。

### 依靠可观测性与后训练持续改进

结合 [Anyscale 服务监控](https://docs.anyscale.com/services/monitoring)和 [Ray Serve LLM 仪表盘](https://docs.ray.io/en/latest/serve/llm/user-guides/observability.html)，从任务、模型、平台三个维度跟踪系统表现。

高质量的执行 trace 驱动一条迭代式的后训练流水线。通过 Langfuse 这类可观测性平台记录多轮交互，用 [Ray Data](https://docs.ray.io/en/latest/data/data.html) 做数据集的筛选与预处理，用自动化评测套件发现性能回退，再用 SkyRL 对开源模型做后训练——这是一个跑在 Ray 和 Anyscale 上的强化学习框架。[Coinbase 为它的 Onramp 欺诈检测智能体走的就是这条路](https://www.coinbase.com/blog/part-one-how-coinbase-built-evaluated-and-post-trained-a-fraud-agent)。它用自有的欺诈数据、通过 SkyRL 后训练了 Qwen3.5-9B，得到的模型在四项欺诈检测指标上都超过了 Claude Opus 4.5，端到端服务延迟还降低了 55%。每一轮后训练都把改进后的模型送回生产，一个静态部署就此变成会自我提升的智能体飞轮。
