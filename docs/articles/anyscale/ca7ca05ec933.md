# 将编码代理成本降低 90%：在 Anyscale 上使用 Ray + vLLM 提供安全的 LLM 服务

由

耿昆凌

,

艾丁·阿比亚尔

2026 年 10 月 8 日

编码代理重复发送存储库上下文、指令、工具结果和对话历史记录以生成操作。这项工作也是您所做的最敏感的工作之一：您的来源、您的内部文档、您的架构决策，在每次击键时留下您的界限。 [拥有运行时](https://www.anyscale.com/blog/learning-loops) 是您的：代码、跟踪和使用数据最终可以帮助您对这些模型进行后期训练，使它们更适合您的团队。

除了数据隐私之外，通过代币支付闭源法学硕士还意味着每个开发人员、每个请求的费用呈线性增长，并且无法随着团队和代理数量的增长而获得规模效率。拥有运行时还可以让团队共享底层 GPU，从而改变这种情况。 [BMW 发现了成本效益](https://youtu.be/yKt-CpfrOIE?si=mFz8jRYluEfBFqpg&t=46)，只需 8 名开发人员即可从 API 转向内部推理。但是，在运行 GPU 集群时，构建和管理内部 LLM 编码服务平台会带来其自身的运营挑战。

就成本而言，我们成本模型的主要发现表明，自托管成本只是每个开发人员每个代币 API 定价的一小部分：

- **始终在线服务：** 每月约 2,920 美元，或每个注册开发者约 58 美元。
- **仅工作时间服务：** 每月约 840 美元，或每个注册开发者约 17 美元。
- **API 基线：** 活跃的开发人员每月通常会花费约 800 美元的同等 Claude Code API 成本。

这些数字假设 RTX PRO 6000 和 50 名注册开发人员共享一个 GPU 每个 GPU 节点每小时大约 4 美元。他们正在规划预测而不是 TCO；完整的假设和注意事项位于下面的成本比较部分。

除了节省成本之外，优化服务基础设施还可以带来显着的性能提升。

我们的实证评估的主要结果表明性能显着提高：

- **通过编译缓存恢复，编译速度提高 8.0 倍。** 在无 MTP NVFP4 设置中，编译时间从 48.5 秒下降到 6.0 秒。
- **通过 CPU KV 缓存分层，请求吞吐量提高了 3.79 倍。** 在单副本 GLM-5.2 评估中添加 512 GiB CPU 层，将 58 个常见提示中提示令牌的缓存份额从 6.1% 增加到 74.9%，将首次令牌中值时间 (TTFT) 从 48.4 秒减少到 9.2 秒。
- **通过推测解码，输出吞吐量提高 1.86 倍。 **多令牌预测 (MTP) 将输出吞吐量从 65 个令牌/秒提高到 121 个令牌/秒。
- **启用 CUDA 图表后，输出生成速度提高了 2.87 倍。** 与在 eager 模式下运行相比，客户端观察到的令牌吞吐量从 15.9 个令牌/秒增加到 45.6 个令牌/秒。

## Link编码代理如何转移服务工作负载

### LinkCoding 代理产生的不仅仅是聊天流量

编码代理提示结合了系统指令、存储库上下文、工具定义、诊断和对话历史记录，通常仅生成简短的工具调用或编辑。这使得工作负载**预填充繁重**，大量输入主导了第一个令牌 (TTFT) 的时间。

大多数上下文都会轮流重复，为[自动前缀 KV 缓存重用](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)创造了强大的机会。在团队规模上，相关爆发增加了另一个挑战。因此，高性能平台必须平衡四个目标：低 TTFT、平滑的令牌流、高缓存重用和弹性容量。

图 2. 说明性编码代理会话：每一轮都会重新发送一个大的、大部分重复的提示以产生一个简短的输出。只有每回合的新内容（橙色）需要新鲜的预填充；其余的可以从 KV 缓存中获取。

图 2. 示例性编码代理会话

编码代理工具充当 API 客户端。配置自定义端点时，本地线束（或者对于 Cursor 等托管客户端而言，其云后端）会将请求发送到兼容的模型服务器，而不是依赖默认的托管模型。由于这些客户端使用不同的 API 模式和端点，因此服务基础设施必须公开相应的路由。存储库的[客户端集成指南](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part2-connect-clients-product/README.md)配置了这三个路径：

| **编码剂** | **API 路径** |
| --- | --- |
|光标| `/v1/chat/completions` |
|克劳德·代码 | `/v1/消息` |
|法典| `/v1/response` |

在 Anyscale 上托管开放权重模型可以带来多种好处：

- **降低成本：** 当利用率足够高以抵消固定基础设施费用时，降低边际代币成本。
- **控制容量：** 减少对单个提供商速率限制的依赖，同时管理您自己的容量和队列。
- **安全和数据控制：** 在网络内保留更多的推理路径。
- **减少模型提供商锁定：** 获得对模型和服务升级的控制。
- **使用您自己的数据发展 LLM：** 通过捕获批准的代理跟踪、使用 [Ray Data](https://docs.ray.io/en/latest/data/data.html) 进行整理和评估，以及使用 [Ray Train](https://docs.ray.io/en/latest/train/train.html) 或 RL 框架进行后期训练来创建数据飞轮。

**社区和透明度：** 利用开放的生态系统来理解和定制模型行为。

### LinkRay Serve LLM 将其扩展到生产

虽然 vLLM 处理核心推理优化，例如[前缀缓存](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)、[分块预填充](https://docs.vllm.ai/en/stable/configuration/optimization/#chunked-prefill)， [量化](https://docs.vllm.ai/en/stable/features/quantization/quantized_kvcache/)、[推测性解码](https://docs.vllm.ai/en/stable/features/speculative_decoding/)和[模型并行性](https://docs.vllm.ai/en/stable/serving/parallelism_scaling/)——稳健的部署需要更多。 Ray Serve LLM 添加了一个生产层：

- 跨多 GPU 环境扩展副本。
- 根据负载和缓存状态智能地路由请求。
- 公开 OpenAI 和 Anthropic 兼容的 API。
- 通过 HAProxy 从副本流式传输令牌，同时绕过旧版 Python 入口跃点。
- 集中服务、模型和 GPU 的指标。
- 符合人体工程学的构建器，适用于复杂的多节点部署，例如 Wide-EP 和预填充分解

[最近发布的 Ray Serve LLM 基准测试](https://www.anyscale.com/blog/high-performance-distributed-inference-ray-serve-llm-vllm-google-kubernetes-gke) 测量到，在引入 HAProxy、直接流式处理和RayExecutorV2.0在 Anyscale 上，Ray Serve LLM 在推理引擎周围添加了托管自动扩展、可观察性和容错能力。

## LinkDeploy 编码代理的 LLM

实际部署有四个步骤：

- 根据任务质量和服务足迹选择模型。
- 选择硬件和并行策略。
- 配置 vLLM 引擎和 Ray Serve 部署。
- 部署服务并验证每个编码客户端。

### LinkStep 1：为任务成功选择法学硕士，而不仅仅是排行榜排名

开放重量模型质量正在快速发展。 Agent 排行榜（例如 [Agent Arena 开源模型排名](https://arena.ai/leaderboard/agent?license=open-source)）是很好的起点，并且包括 Qwen、DeepSeek、Kimi 和 GLM 在内的模型系列越来越以编码和工具使用为目标。然而，公开排名只是一个起点，Anyscale LLM 专家可以帮助您为您的特定工作负载选择最佳模型。

常见的基准测试包括用于解决实际存储库问题的 [SWE-bench](https://www.swebench.com/)、用于终端任务的 [Terminal-Bench](https://www.tbench.ai/benchmarks)、用于长期多工具工作流程的 [Toolathlon](https://toolathlon.xyz/introduction)、用于对话工具使用的 [τ-bench](https://taubench.com/)、 [CyberGym](https://www.cybergym.io/cybergym/) 用于漏洞分析，[GDPval-AA v2](https://artificialanalysis.ai/evaluations/gdpval-aa) 用于专业知识工作。分数通常反映完整的代理系统（而不仅仅是模型），因此仅当基准版本和评估设置匹配时才比较结果。

根据您自己的工作评估候选模型：

- 多文件编辑和存储库导航。
- 结构化工具调用数轮。
- 长上下文指令跟随。
- 调试和测试修复。
- 完成任务所需的延迟和轮数。

在一个可靠的回合中完成常见工作的较小模型可能比需要更多 GPU 的较大模型更便宜。如果避免重试，更强大的模型对于困难任务可能会更便宜。衡量**每个成功任务的成本**，而不仅仅是每百万代币的成本。

### LinkStep 2：将权重、运行时内存和 KV 缓存适配到硬件

GPU 内存保存模型权重、KV 缓存、临时激活、CUDA 图和运行时开销。权重内存大部分是固定的，并随着参数数量和精度而缩放，因此当未量化的权重限制部署时，**权重量化**可能至关重要。 KV 缓存存储活动请求的注意力状态，并随着上下文长度和并发性而增长。对于长上下文编码代理工作负载，**KV 缓存量化**同样可以减少每个令牌的内存。当支持和质量验证时，对两者进行量化可以为并发长请求留下更多空间。

选择量化策略时，请考虑以下格式：

- [**FP8**](https://docs.anyscale.com/llm/serving/performance-optimization)**:** 当硬件和运行时支持时，权重和 KV 缓存的强大选项。与 BF16 相比，其原始存储量大约减少一半；质量仍然取决于模型、任务和校准。
- [**NVFP4**](https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low- precision-inference/)**：** 在 NVIDIA Blackwell GPU 上，与 FP8 相比，此格式将量化张量的原始存储减少一半。整个检查点的节省较小，因为某些模块和元数据保持较高的精度；测试的 Qwen 检查点使用了大约 22 GB，而 FP8 使用了 27 GB，减少了约 19%。
- [**MxFP4**](https://huggingface.co/docs/transformers/quantization/mxfp4)**：** 4 位精度的开放替代方案，由“gpt-oss”等模型使用。

注意：运行时设置和 GPU 架构决定了硬件加速的程度。虽然此处部署了 NVIDIA 的 [Qwen3.6-27B-NVFP4](https://huggingface.co/nvidia/Qwen3.6-27B-NVFP4) 权重，但固定的 vLLM 版本依赖于 Marlin 回退，而不是 RTX PRO 6000 硬件上密集 NVFP4 的本机内核。此外，由于该设备不支持 NVFP4 KV 缓存，因此系统默认使用 FP8 KV 缓存。

图 4. 说明性 GPU 内存布局：NVFP4 权重将大部分内存留给 KV 缓存，FP8 KV 适合的完整上下文数量大约是 BF16 的两倍。

图 4. 示例性 GPU 内存布局

### LinkStep 3：为模型和工作负载配置引擎

正确的服务配置是特定于型号的。除了内存和并行性之外，它还必须使用正确的聊天模板、推理解析器、工具调用解析器、多模式限制和上下文长度。

存储库的 [Qwen 服务实现](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize/serve_qwen3_6_27b_optimized.py#L138-L182)为每个副本配置一个 GPU， 256K 上下文限制、FP8 KV 缓存、本地前缀缓存、分块预填充以及 Qwen 特定推理和工具解析器。以下摘录显示了相关的引擎参数；该实现分别配置推测解码和编译缓存行为：
```
engine_kwargs = {
    "tensor_parallel_size": 1,
    "max_model_len": 262144,
    "gpu_memory_utilization": 0.9,
    "max_num_seqs": 32,
    "max_num_batched_tokens": 8192,
    "enable_prefix_caching": True,
    "kv_cache_dtype": "fp8",
    "quantization": "modelopt",
    "reasoning_parser": "qwen3",
    "tool_call_parser": "qwen3_coder",
    "enable_auto_tool_choice": True,
    "limit_mm_per_prompt": {"image": 4, "video": 0},
}
```
`max_model_len` 限制单个请求的上下文。 `max_num_batched_tokens` 用作分块预填充的调度程序预算。同时，“max_num_seqs”限制引擎并发。

### LinkStep 4：启用直接流式传输并连接客户端

存储库的 [always-on 服务配置](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize/service-always-on.yaml#L12-L30) 在服务级别启用 HAProxy 和直接流式传输：
```
env_vars:
  RAY_SERVE_ENABLE_HA_PROXY: "1"
  RAY_SERVE_LLM_ENABLE_DIRECT_STREAMING: "1"
```
请遵循存储库的 [coding-agent 连接教程](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part2-connect-clients-product/README.md)。首先，部署[优化的永远在线服务](https://github.com/anyscale/llm-serving-for-coding-agents/tree/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize)：
```
anyscale service deploy -f service-always-on.yaml --working-dir .
```
然后从 **Anyscale 控制台 → 服务 → 查询** 复制其公共“base_url”和不记名令牌。代理在本地执行工具，但模型请求（包括指令、存储库上下文、对话历史记录和工具结果）和流式模型响应通过服务传递。

**克劳德·代码**

导出服务 URL 和令牌，然后运行存储库的 [claude-service.sh](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part2-connect-clients-product/claude-service.sh)：
```
export ANYSCALE_BASE_URL=<base_url>/v1
export ANYSCALE_API_KEY=<token>
./claude-service.sh
```
启动器将服务根作为“ANTHROPIC_BASE_URL”传递给 Claude Code，并通过“ANTHROPIC_AUTH_TOKEN”提供令牌。

**法典**

从同一目录运行 [codex-service.sh](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part2-connect-clients-product/codex-service.sh)：
```
./codex-service.sh
```
它将 `/v1` URL 注册为自定义提供程序，选择 `wire_api="responses"`，并将承载令牌发送到 `/v1/responses`。

**光标**

按照教程的[光标设置](https://github.com/anyscale/llm-serving-for-coding-agents/tree/95af323db8951d1a7e5ea588a4e8c706ae15c115/part2-connect-clients-production#cursor-gui)并在**光标设置→模型→OpenAI API密钥**下输入这些值：
```
Override OpenAI Base URL:  <base_url>/v1
OpenAI API Key:            <token>
Custom model:              qwen3.6-27b
```
## LinkOptimize 编码代理流量的一个副本

### 针对定义的 SLO 的 LinkBenchmarking 延迟

有关 TTFT、ITL、TPOT、预填充、解码和良好吞吐量的全面定义，请参阅 [Anyscale 的 LLM 指标指南](https://docs.anyscale.com/llm/serving/benchmarking/metrics)。

不要只关注原始令牌吞吐量，而应优先考虑有效吞吐量（满足目标延迟 SLO 的请求比例）。虽然积极的批处理提高了整体吞吐量，但它可能会对交互式流媒体性能产生负面影响。

### LinkReplay 真实代理会话进行基准测试

统一的合成提示无法捕获真实的代理循环。现实世界的流量结合了长轮和短轮、重复的前缀、工具执行等待和重尾会话生命周期。要准确测试您的设置，请将您的 Claude Code JSONL 会话转换为带时间戳的请求流，以保持快速增长和轮间延迟。如果您还没有收集自己的会话，则可以使用公共 [WekaTrace Claude Code 代理会话语料库](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-062126-256k)。

对于每个候选配置，收集：

- TTFT、TPOT、ITL 和端到端延迟分布。
- 完成特工回合并成功完成任务。
- 输入/输出令牌和缓存提示令牌分数。
- 队列深度、抢占、KV 驱逐和 GPU 利用率。
- 工具调用错误和格式错误的响应。

### Link按依赖顺序应用优化

下面的[单 GPU 测量](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize/notes/BENCHMARKS.md) 使用一台 RTX PRO 6000。大多数解码结果是使用真实的 Claude 会话提示记录的平均约 73K 代币。每行隔离一个不同的旋钮；收益不是累积的。

| **优化** | **之前** | **之后** | **测量到的变化** |
| --- | --- | --- | --- |
| CUDA 图表与 eager 模式（FP8 权重）| 15.9 输出令牌/秒 | 45.6 输出令牌/秒 | 2.87 倍 |
|多令牌预测与基础（NVFP4 权重）| 65 个输出令牌/秒 | 121 个输出令牌/秒 | 1.86 倍 |
| RunAI主播|约85秒负重|约25秒负重| 3.4 倍 |
|恢复编译缓存，vLLM 0.25.1 | 48.5 s 编译阶段 | 6.0 s 编译阶段 | 8.0 倍 |

**1. **[**量化权重**](https://docs.vllm.ai/en/stable/features/quantization/)**以有效地拟合模型。**权重量化可以将多GPU部署转变为单GPU部署，消除GPU间通信并释放KV缓存的内存。好处取决于 GPU 的本机内核和检查点的校准。将每一次精度变化视为性能和质量变化。

**2. **[**量化 KV 缓存**](https://docs.vllm.ai/en/stable/features/quantization/quantized_kvcache/)**（如果支持）。** 优化部署使用 FP8 KV 缓存。在测试的 96 GB GPU 上，容量计算估计 KV 存储相当于 BF16 KV 的约 3.27 倍 256K 令牌上下文，以及 FP8 KV 的 6.53 倍。

**3.保持 **[**CUDA 图形**](https://docs.vllm.ai/en/latest/design/cuda_graphs/)** 为生产启用。** Eager 模式启动需要更多 CPU 参与的操作，对于调试非常有用。 CUDA 图表捕获可重复的 GPU 工作并减少启动开销。禁用 Eager 模式（保持 CUDA 图启用）将输出速率从 15.9 个令牌/秒增加到 45.6 个令牌/秒。

**4.针对目标工作负载测试**[**推测性解码**](https://docs.vllm.ai/en/stable/features/speculative_decoding/mtp/)**。**多令牌预测同时提出并验证多个未来令牌以减少 TPOT； `num_speculative_tokens` 参数控制预测的草稿令牌数量（例如，将其设置为 3 以预测前面的三个令牌）。然而，净加速取决于接受率和验证开销。在并发性为 8 时，预测三个令牌会产生 99 个输出令牌/秒和 0.50 个转数/秒，优于两个令牌（80 个令牌/秒，0.50 个转数/秒），而预测四个令牌会将性能降低到 74 个令牌/秒。投机深度越高并不一定越好。优先考虑输出准确性：上游问题指出，在将 MTP 与前缀缓存结合使用时，工具调用已损坏。在启用 MTP 之前，通过多轮回归测试验证客户端、模型、解析器和 vLLM 兼容性。

**5.简化初始化，将冷启动与稳态服务分开。**模型下载、权重加载、引擎编译和副本准备是影响部署速度的不同阶段。编译缓存对确切的软件版本、GPU 架构、模型、并行性和标志很敏感，这意味着过时的缓存可能会失败或默默地降低性能。虽然 RunAI Streamer 减少了早期的权重加载时间，但存储库的[不兼容性矩阵](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize/notes/INCOMPATIBILITIES.md)记录了其加载程序路径之间的已知冲突和测试的 vLLM 版本中的 MTP。

在实践中，首先建立正确的工具使用并禁用推测解码；仅在调试需要时使用 eager 模式。验证正确性后，启用预期的量化和上下文长度，然后启用 CUDA 图表。从那里开始，调整分块预填充并测试推测解码。最后，优化冷启动并重新运行完整的正确性和负载套件。

Claude 通过 [Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/claude-models) 上的 Azure 市场定价遵循 [Claude Opus 5 费率](https://platform.claude.com/docs/en/about-claude/pricing#claude-in-microsoft-foundry-pricing)：标准输入每百万代币 5.00 美元 (MTok)， $0.50/MTok 用于缓存读取，$25.00/MTok 用于输出。

一名活跃的开发人员每月的同等 Claude Code API 成本通常高达 800 美元。这与行业基准一致，包括[Pylon 的观察](https://www.linkedin.com/posts/martykausas_our-anthropic-bill-is-about-to-jump-from-activity-7470505066148352000-zqnt) 高级用户达到每月 800 美元和[另一个类似的估计](https://simonwillison.net/2026/May/27/product-market-fit/) 30 天内为 1,199.79 美元。公共跟踪遥测证实编码代理工作负载严重偏向输入令牌：

- [WekaTrace 数据集](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-062126-256k) 表示输入输出令牌比率为 117:1。
- SyFI TraceLab 的 [Claude Trace](https://tracelab.cs.washington.edu/) 记录了 269:1 的比率和 95.2% 的提示缓存命中率。

考虑到 SyFI 的 95.2% 缓存输入率（按缓存读取计费）并将剩余 4.8% 视为五分钟缓存写入，Opus 5 定价将每月 800 美元的支出转化为每个开发人员约 9.22 亿个输入代币和 343 万个输出代币。对于由 50 名开发人员组成的工程团队来说，API 总使用量约为 40,000 美元，每月输出 1.71 亿个代币。

同样，每个开发人员的 GPU 成本计算代表初步规划预测，而不是总拥有成本 (TCO) 或服务水平承诺。为了准确确定所需的副本数量和净节省，请根据目标延迟 SLO 和任务成功率评估持续跟踪重放的良好吞吐量，然后考虑额外的平台运营开销。

## LinkScale 具有自动缩放和缓存感知负载平衡功能

### LinkSeparate 引擎限制、准入限制和自动缩放目标

存储库的[自动缩放配置](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part3-optimize/serve_qwen3_6_27b_optimized.py#L204-L220)提供了一个具体的起点，而[Anyscale 的参数调整指南](https://docs.anyscale.com/llm/serving/parameter-tuning#ray-serve-autoscaling-configuration) 解释了如何调整它。三个控件有不同的用途：

- vLLM `max_num_seqs` 设置限制引擎允许的序列。
- Ray Serve 的“max_ongoing_requests”限制发送到副本的工作。
- `target_ongoing_requests` 设置告诉自动缩放器何时添加副本。

以下是为服务于编码代理的 LLM 部署设置自动扩展的分步过程：

- **确定峰值 KV 缓存容量：**检查服务器启动日志以确定最大上下文长度支持的最大并发序列（例如，256K 上下文窗口通常维持大约 20 个并发流）。
- **估计实际工作负载并发性：**根据平均提示大小调整序列限制。例如，平均提示长度为 85K 令牌，使用 (256K / 85K) x 20 缩放目标，以建立大约 60 个并发请求的目标。
- **设置硬准入界限：**将引擎的调度程序容量（vLLM 中的“max_num_seqs”）和部署防护（Ray Serve 中的“max_ongoing_requests”）与计算出的上限（例如 60）相匹配。
- **建立自动缩放触发器：**将 `target_ongoing_requests` 配置为比准入上限（例如 40）低大约 20-30%，以在请求排队之前启动副本缩放。
- **跟踪指标并细化参数：**持续评估系统的吞吐量和排队情况。如果提示长度接近 256K 上限，请降低并发阈值，以在内存空间变窄时保持尾部延迟。

对于编码代理，我们建议使用 Ray Serve LLM 的 [KVAwareRouter](https://docs.ray.io/en/master/serve/llm/user-guides/kv-aware-routing.html) 或一致哈希（会话亲和力）。 KV 感知路由将前缀缓存重用与令牌加载感知路由结合起来。但请注意，KV 感知路由目前仅与 Codex 兼容。对于其他客户端或不兼容的设置，请回退到一致的哈希以保持会话粘性。

正如[博客](https://www.anyscale.com/blog/llm-kv-token-aware-routing)中详细介绍的，路由器使用 KV 缓存重叠来估计可以跳过多少预填充，然后估计引擎仍然需要完成的工作：
```
remaining prefill = incoming input tokens - reusable cached tokens
token-load score = weighted remaining prefill + active prefill + ongoing decode
```
路由器选择具有最低加权分数的副本，并且可能会牺牲一些缓存重用以获得更平衡的令牌负载。在异构编码代理跟踪上，相对于单独最大化缓存重用，这可以提高 TTFT、TPOT 和吞吐量。

### LinkExtend 有用的缓存生命周期与 KV 缓存卸载

当开发人员暂停检查代码或编写提示时，其他团队流量可能会从有限的 GPU 内存中逐出其会话的块。 [KV 缓存卸载](https://docs.ray.io/en/releases-2.58.0/serve/llm/user-guides/kv-cache-offloading.html) 将不活动的块移动到更大的 CPU 内存或本地存储层，以便可以恢复它们而不是完全重新计算。对于编码代理来说，当用户离开并在数小时后返回时，卸载会保留会话上下文 - 历史记录是从 CPU/磁盘检索而不是重新计算，因此它们可以快速 TTFT 恢复。

图 5. KV 缓存卸载：空闲块移动到 CPU 或磁盘，并在重用时恢复，而不是重新计算。

图 5. KV 缓存卸载

在 GLM-5.2 工作负载的内部基准测试中，与单独的 GPU 缓存相比，添加 512 GiB CPU KV 缓存层以及 GPU 前缀缓存可显着提高吞吐量和延迟。该基准测试使用配备 8xRTX PRO 6000 GPU（8 个张量并行、NVFP4 权重和 FP8 KV 缓存）的单个节点进行评估，在标称 900 秒的窗口内重播了种子工作负载。

| --- | --- | --- |
|已完成的请求 | 58 | 58 215 | 215
|请求吞吐量| 0.0625 请求/秒 | 0.2367 请求/秒 |

主要运营要点包括：

- **吞吐量改进：**总体请求吞吐量增加了 3.79 倍。
- **更高的缓存效率：**在 58 个共享的已完成提示中，缓存提示令牌比例从 6.1% 扩大到 74.9%。
- **减少延迟：**首次令牌时间中值 (TTFT) 从 48.4 秒下降到 9.2 秒，58 个请求中有 49 个请求的 TTFT 较低。

## Link多模型路由成本优化

副本路由优化了硬件效率，而多模型路由则优化了总体支出。它决定了与在自托管基础设施上运行相比，有多少流量需要支付前沿 API 溢价。将两者结合起来可以让您完全控制性能和成本。

三个共同政策是：

- **按任务复杂性进行路由。** 将例行编辑、搜索和已知的代理技能发送到较小的开放模型；为困难的推理或关键的变化保留一个前沿模型。
- **当自托管 LLM 服务容量受到限制时进行回退。** 如果 GPU 无法足够快地扩展以应对突发情况，请使用经批准的托管模型，而不是允许队列无限制地增长。
- **当托管配额耗尽时，回退到开放模型。** 当订阅或 API 达到限制时，继续工作。

仅包含 CPU 的 LiteLLM 网关可以在单独的 Ray Serve LLM 服务和外部提供商面前实现模型选择。该存储库包括一个[可部署网关](https://github.com/anyscale/llm-serving-for-coding-agents/tree/95af323db8951d1a7e5ea588a4e8c706ae15c115/part4-litellm-router/gateway)和[主要、后备和复杂性路由器]配置](https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part4-litellm-router/gateway/config.yaml#L27-L128)，加上一个[路由策略指南]（https://github.com/anyscale/llm-serving-for-coding-agents/blob/95af323db8951d1a7e5ea588a4e8c706ae15c115/part4-litellm-router/ROUTING.md）。 LiteLLM 的[自动路由文档](https://docs.litellm.ai/docs/proxy/auto_routing) 涵盖了路由器的底层复杂性。关键字和技能感知规则快速且易于解释；分类器可以支持更丰富的策略。显式的用户覆盖仍然很重要，因为没有路由器能够完美地预测任务难度。

在我们的内部设置中，网关将简单请求路由到 Qwen，将中级到高级文本任务路由到 GLM，将复杂推理或多模式工作负载路由到 Claude。为了防止后续工具结果步骤在中途意外更改模型，路由器在整个剩余代理会话中强制执行会话粘性。

保持此会话粘性对于顺利运行至关重要。由于编码代理迭代经常在没有新用户提示的情况下传递工具输出，因此基于每个请求评估路由存在跨不同模型转移单个会话的风险，这些模型具有冲突的聊天格式、上下文边界和工具机制。
