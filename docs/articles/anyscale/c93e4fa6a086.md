# 释放 NVIDIA GB300 NVL72 的最大威力：Ray 中的 NVLink Domain 感知 Placement Group

作者：Joshua Lee、Mengjin Yan、Aaron Li、Edward Oakes、Mathew Wicks 和 Connor Pedersen | 2026 年 8 月 13 日

## 摘要

[NVIDIA GB300 NVL72](https://www.nvidia.com/en-us/data-center/gb300-nvl72/) 机架级系统把 72 块 [NVIDIA Blackwell GPU](https://www.nvidia.com/en-us/data-center/technologies/blackwell-architecture/) 与 36 颗 [NVIDIA Grace CPU](https://www.nvidia.com/en-us/data-center/grace-cpu/)，通过被称为 NVLink Domain 的机架级 [NVIDIA NVLink](https://www.nvidia.com/en-us/data-center/nvlink/) scale-up 网络互联在一起，带来巨大的性能飞跃。为了让 Ray 用户利用这种拓扑，我们推出 NVLink Domain 感知 Placement Group（Placement Groups）：一种多节点拓扑感知调度原语，把 placement group 的 bundle 同置于单个 NVLink Domain 内。本文解释它为何对 GB200/GB300 NVL72 系统重要，并分享 NVIDIA GEAR 研究实验室如何在真实的 GB300 NVL72 训练负载上验证这些收益。

此前，Ray placement group 关注的是单个节点所挂加速器的类型——比如选 [NVIDIA Hopper](https://www.nvidia.com/en-us/data-center/technologies/hopper-architecture/) 还是 Blackwell GPU。但 GB300 NVL72 这类新系统提供的是跨多节点的 NVLink Domain，必须拓扑感知地放置才能用得好。

NVLink Domain 感知 Placement Group 为 Ray 的调度模型增加了拓扑感知，让用户既能最大化高性能 GPU 通信，又能在故障期间保留拓扑意图。这个小小却强力的改动释放了 GB200/GB300 的潜力，也为多主机/多机架系统更通用的拓扑感知调度与自动扩缩打下地基。

## 多节点 NVLink Scale-up：NVIDIA GB300 NVL72

NVIDIA DGX H100、DGX H200 等传统 GPU 服务器把 8 块 GPU 装进单个节点，节点内通过 SXM 上的 NVLink 互联，节点间通信一般走 InfiniBand 或 RoCE。

*图 1. GB300 机架示例*

NVIDIA GB200 NVL72 与 GB300 NVL72 提供了全新的计算平台：整个机架的 72 块 Blackwell GPU 与 36 颗 Grace CPU 互联，每块 GPU 拥有 1,800 GB/s 的全对全带宽，实际上让所有 GPU 如同一块那样协同工作。

*图 2. GB300 NVL72 全对全拓扑*

对于集合通信与内存传输占主导的负载，GB200/GB300 NVL72 处于行业领先水平。

## 推出 Ray NVLink Domain 感知 Placement Group

要在 Ray 中用好 NVIDIA GB200/GB300 NVL72，用户需要能够请求把一组 actor 放置在同一个 NVLink Domain（对应一个机架）内。

此前 Ray placement group 不理解跨节点依赖：只能在节点级别做 [PACK 或 STRICT_PACK](https://docs.ray.io/en/latest/ray-core/scheduling/placement-group.html#placement-strategy)。例如，如果你试图对一个 placement group 里 18 个各需 4 GPU、2 CPU 的 bundle 做 STRICT_PACK，它将无法被调度——因为你实际是在请求一台拥有 72 块 GPU 的"单节点"！

之前的变通做法是给每个 GB300 NVL72 机架打一个自定义 label（如 "ray.io/gpu-domain"="rack-7"），再用 [bundle_label_selector](https://docs.ray.io/en/latest/ray-core/scheduling/labels.html#specify-label-requirements-for-placement-group-bundles) 把 bundle "钉"在该机架上。这是手工作业的，与自动扩缩或容错的组合性很差。

为此，我们在 placement group API 中引入 NVLink Domain 感知。用户通过在 placement group API 中定义新的拓扑策略字段来启用该特性，即 **topology_strategy = {ray.io/node-id: "PACK", ray.io/gpu-domain: "STRICT_PACK"}**。这个新字段告诉 Ray：所有 bundle 必须放在同一个 NVLink Domain 内。

例如，在含多个 GB300 机架的 Ray 集群中，以下 placement group 能确保你的 actor 被放在同一个 NVLink Domain 内：

```
1bundles = [{"GPU": 4, "CPU": 2}] * 16
2topology_strategy = {ray.io/node-id: "PACK", ray.io/gpu-domain: "STRICT_PACK"}
3pg = placement_group(
4bundles=bundles,
5      	topology_strategy=topology_strategy,
6      	name="gb300_single_rack_16_node_pg",
7)
8ray.get(pg.ready())
```

*图 3. 如果上述 placement group 调度成功，这是在一个含 2 个 GB300 机架的集群中的一种可能分配。*

这段代码看似简单，收益却很可观。

### 优化的网络性能

Domain 感知放置最直观的好处是网络性能提升。让紧耦合的 actor 留在同一 NVLink Domain 内，all_reduce 等集合操作就能用 NVLink 而非更慢的跨域路径。不仅如此，它还能让我们更好地利用 NVIDIA SHARP1 等新特性来加速集合通信。

### 应用感知的容错

当集群状态变化时，Ray 会保留应用的拓扑意图。若某节点故障或需要维护，只要容量存在，Ray 会从同一个 NVLink Domain 中替换该节点，而不是悄悄把工作负载拆散到不同机架。图 3 展示了一个例子。若容量不足，该 bundle 会排队等待重新调度——除非整组 bundle 全部下线，此时会自动选择一个新的 NVLink Domain 使用。这一容错机制一直是 Ray placement group 的重要部分，如今被扩展到这些多节点系统。

*图 4. placement group 已调度后，用同 domain 的节点替换故障节点的示例。*

## 真实案例：GB300 上的大规模分布式 VLA 训练

我们与 NVIDIA 的 [GEAR](https://research.nvidia.com/labs/gear/) 研究实验室合作，在他们于 GB300 集群上进行的大规模 [VLA](https://arxiv.org/pdf/2503.14734)（Vision Language Action）预训练任务中测试这一新特性。

为评估 Ray 中 NVLink Domain 感知 Placement Group 的收益，NVIDIA GEAR 跑了两次训练：一次启用、一次不启用该特性。每次运行使用 512 块 GPU（128 个节点），由 8 组、每组 64 块 GPU（16 个节点）构成。

*图 5. 第一次训练运行中 actor 放置不佳，训练期间无法有效利用 NVLink。*

*图 6. 第二次运行的示意图：每个 placement group 都同置于单个 NVLink Domain 内，每个 domain 留有 2 个备用节点。*

第二次运行实现了比第一次快 1.13 倍的每秒迭代。但这只是开始——要更充分地利用 GB300 独特的硬件能力，仍有进一步的空间。

为什么第二次运行更快？在第一次运行中，GPU 花更多时间与同 placement group 的对等端交换数据（例如 all_reduce 等集合操作期间）。而第二次运行中，actor 的放置使其受益于 NVLink 的高速 GPU 间内存共享，达到第一次运行无法实现的训练速度。

此外，让 Ray 知道 placement group 应当位于同一 NVLink Domain 后，在长时间训练中优雅处理故障也变得容易得多。

## 机架感知调度的其他用例

**分布式推理。** 使用分离式推理的服务负载常把 prefill 与 decode worker 分开。在 GB300 级系统上，让这些 worker 落在同一个 NVLink Domain 内尤为重要——它们可以沿最快的可用路径交换 KV cache 与中间状态。NVLink Domain 感知 Placement Group 让这件事容易得多：用户可以表达"相关的 prefill 与 decode actor 应同置于同一机架"的意图，而不必用机架专属 label 手工钉住。

**强化学习。** RL 负载有很多阶段：训练、rollout、评估，各自的通信模式不同。Domain 感知放置让用户把流水线中最紧耦合的部分（例如策略训练 worker，或频繁交换模型权重的 actor）留在一起，同时仍给 Ray 灵活度，把通信较轻的组件调度到别处。

## 下一步

该特性的首要目标是把 NVLink Domain 的感知带入 Ray 应用层。在未来几个版本中，我们将提供更多可见性与工具，帮助理解 GPU 局部性、为极致性能与互联效率优化放置。

我们还会在多个方向扩展 Placement Group API：

- NVLink Domain 感知 Placement Group 目前仅支持 STRICT_PACK。我们计划加入其他策略，如 STRICT_SPREAD——例如让你把 bundle 放到不同机架上。
- 嵌套拓扑：目前经 NVLink Domain 感知 Placement Group 表达的拓扑是扁平的。现实中基础设施通常是分层的——机架在数据中心内，数据中心在可用区内，依此类推。我们计划支持表达这类嵌套拓扑。
