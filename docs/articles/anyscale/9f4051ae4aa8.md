# Ray 分布式库集成模式

作者：Eric Liang 和 Zhe Zhang | 2021 年 6 月 14 日

Ray 拥有丰富的库[集成](https://docs.ray.io/en/master/ray-overview/ray-libraries.html)，从 [Horovod](https://horovod.readthedocs.io/en/stable/ray_include.html)、[Hugging Face](https://huggingface.co/docs/transformers/main/main_classes/trainer) 这样的机器学习库，到 [Spark](https://github.com/oap-project/raydp)、[Modin](https://docs.ray.io/en/master/rllib/index.html)、[Dask](https://docs.ray.io/en/master/) 这样的数据处理框架。但"与 Ray 集成"到底意味着什么？它给库的开发者与用户带来什么好处？

本文通过考察**三个常见的 Ray 库集成模式**来回答这些问题。我们会为每个集成层级给出若干 Ray 库的例子，展示每种模式（每个"层级"）如何解决库作者与用户的不同问题，并解释如何决定合适的集成层级。

## Ray 集成的三个层级

**层级 1：只做调度；通信在 Ray 之外完成**

*Ray 分布式库模式（图 1）*

- *Horovod [[*代码*](https://horovod.readthedocs.io/en/stable/api.html#horovod-ray-api)]：Horovod 用 Ray actor 调度 Horovod worker 进程，从而支持*[*动态扩缩*](https://www.anyscale.com/blog/ray-distributed-library-patterns)*，并让数据预处理在 Ray 内处理。*
- *Pytorch Lightning [[*代码*](https://github.com/ray-project/ray_lightning)]：类似地，Pytorch Lightning 支持在 Ray 上进行分布式数据并行训练，Ray 用于启动进程。*
- *Spark / RayDP [[*代码*](https://github.com/oap-project/raydp)]：RayDP 把 Spark executor 作为 Ray Java actor 启动，使 Spark 能运行在 Ray 内部。*

在这个层级，库把 Ray 用作语言内集的 actor 调度器，actor 之间的实际通信大多在*带外*（Ray 之外）完成。例如 [Horovod-on-Ray](https://horovod.readthedocs.io/en/stable/ray_include.html) 使用 NCCL 或基于 MPI 的集合通信，[RayDP](https://github.com/oap-project/raydp) 使用 Spark 内部的 RPC 与对象管理器。

*Ray 分布式库模式（图 2）*

乍看之下这种集成似乎很表面。但对于已有成熟、高性能内部通信栈、同时仍想要一些额外特性的库，这一层级往往才是正确选择，这些额外特性包括：

- 对 worker 调度与容错的细粒度控制（例如 [Elastic Horovod](https://www.uber.com/blog/horovod-ray/)）。
- 能把子程序嵌入更大的分布式程序运行（如调参），或在内存中把数据传给下游阶段（如 RayDP => [MLDataset](https://github.com/ray-project/ray/blob/master/python/ray/util/data/dataset.py) => 训练）。

```
1# Out-of-band communication example.
2
3# Launch the actors.
4workers = [MPIActor.remote(...) for _ in range(10)]
5for i, w in enumerate(workers):
6   w.init_for_rank.remote(i)
7
8# Ray triggers the collective op, but the actual communication
9# happens between the workers out-of-band (e.g., via MPI).
10ray.get([w.collective_op.remote() for w in workers])
```

我们看到库以这种方式集成 Ray，往往是因为"把组合与调度分布式程序的 API 做对"很难。Ray 在这里提供了通用的"[分布式胶水](https://medium.com/distributed-computing-with-ray/data-processing-support-in-ray-ae8da34dce7e)"，让库专注于自身核心功能而非运维事务。

## 层级 2：调度与通信

*Ray 分布式库模式（图 3）*

- *Hugging Face [[*博客*](https://huggingface.co/blog/ray-rag)]：Hugging Face 用 Ray actor 调用实现更快的分布式文档检索，用于微调。*
- *蚂蚁的在线资源分配 [[*博客*](https://www.anyscale.com/blog/online-resource-allocation-with-ray-at-ant-group)]：蚂蚁集团用 actor 通信实现广告与推荐的在线优化。*
- *Scikit-Learn [[*代码*](https://docs.ray.io/en/master/ray-more-libs/joblib.html)]：Ray 通过 joblib 并行接口支持 Scikit-Learn。*
- *Seldon Alibi [[*博客*](https://www.seldon.io/how-seldons-alibi-and-ray-make-model-explainability-easy-and-scalable)]：类似地，Alibi 用 actor 与 *[Serve](https://docs.ray.io/en/master/serve/index.html)* 扩展批量预测。*

许多应用与库用 Ray 并行化其程序，既利用 Ray 的调度能力（层级 1 的好处），也用任务与 actor 方法调用做通信。底层上，Ray [把任务与 actor 调用翻译为底层 gRPC 调用](https://medium.com/distributed-computing-with-ray/how-ray-uses-grpc-and-arrow-to-outperform-grpc-43ec368cb385?source=post_page-----f34c01b7905c--------------------------------)。

适合这类集成的库通常需要以下一项或多项：

- 低延迟通信，且想要比向算力 worker 池发送原始 RPC 调用更简单的编程模型。
- 可以并行化为大量独立任务的计算（如分布式 [multiprocessing](https://docs.ray.io/en/master/ray-more-libs/multiprocessing.html) 或 [joblib](https://docs.ray.io/en/master/ray-more-libs/joblib.html)）。
- 协调复杂 actor/task 拓扑的能力（如实现[强化学习](https://docs.ray.io/en/master/rllib.html)、[在线决策系统](https://www.anyscale.com/blog/online-resource-allocation-with-ray-at-ant-group)或[模型服务流水线](https://docs.ray.io/en/master/serve/index.html)）。

```
1# Task example.
2results = [evaluate.remote(latest_params) for arg in work_to_do]
3ray.get(results)
4
5# Actor example.
6workers = [Actor.remote() for _ in range(5)]
7for w in workers:
8    w.update(latest_params)
9results = [w.evaluate.remote() for w in workers]
10ray.get(results)
```

对需要专门通信模式的应用，我们目前仍建议层级 1 式集成。未来，[Ray Collectives](https://docs.google.com/document/d/1ySIg04FSrkCWUJGe-XX_mVw2sUH1kP8a8HzZn2UClj8/edit#heading=h.f1hawkpighc0) 将让更多库能以高性能原生实现在 Ray 上。

## 层级 3：调度、通信与分布式内存

*Ray 分布式库模式（图 4）*

- *XGBoost [[*代码*](https://github.com/ray-project/xgboost_ray)]：XGBoost on Ray 利用对象存储保存训练用的分布式数据矩阵。*
- *Modin [[*代码*](https://github.com/modin-project/modin)]：Modin 用对象存储在共享内存中保存分区块，用任务在这些块上执行计算。*
- *Mars [[*代码*](https://github.com/mars-project/mars)]：Mars 用 actor 与对象存储实现分布式执行与数据存储。*
- *Apache Airflow [[*代码*](https://registry.astronomer.io/providers/ray)]：Ray Airflow provider 让 Airflow operator 在 Ray 中执行，并用对象存储传递中间数据。*
- *Dask [[*代码*](https://github.com/ray-project/ray/tree/master/python/ray/util/dask)]：Ray Dask 调度器把 Dask 的中间结果存入对象存储，并用任务执行。*

最后但同样重要，库还可以利用 Ray 的分布式对象存储——它与 Ray 的任务和 actor API 无缝集成。严格地说，任何在 Ray 中传递大对象（>100KB）的应用，已经在使用 Ray 的分布式内存系统获取性能。

层级 3 的库进一步利用 Ray 分布式内存的这些特性：

- 一等公民的[对象引用](https://www.usenix.org/system/files/nsdi21-wang.pdf)，可以在 Ray 的任务与 actor 之间自由传递与获取，超出作用域后自动垃圾回收。
- [共享内存支持](https://ray-project.github.io/2017-08-08/plasma-in-memory-object-store.html)：大对象可以在同一机器的多个 worker 之间零拷贝共享，大幅提升效率。
- 对象溢出：把对象溢出到磁盘或远端存储，使大规模[数据处理](https://medium.com/distributed-computing-with-ray/executing-a-distributed-shuffle-without-a-mapreduce-system-d5856379426c)负载得以执行。

```
1# Store a large dataset in the object store.
2data_R = [ray.put(block) for block in large_data_blocks]
3
4# Store a small dataset in the object store.
5data_S = ray.put(small_data)
6
7# Example of implementing broadcast join between R and S using tasks.
8joined_R_S = [join.remote(R_i, data_S) for R_i in data_R]
```

Ray 自带库如 [Tune](https://docs.ray.io/en/master/tune/index.html)、[RLlib](https://docs.ray.io/en/master/rllib/index.html) 与 [Serve](https://docs.ray.io/en/master/serve/index.html) 也是层级 3 的例子，利用对象存储提供同类最佳的性能与灵活性。

## 选择合适的集成层级

人们容易觉得"集成越深越好"。但依照[最小权力原则（rule of least power）](https://en.wikipedia.org/wiki/Rule_of_least_power)，**我们建议为具体的库选择所需的最小集成层级**。我们对 Ray 的目标是让用户能以单个 Python 文件的简洁性构建复杂分布式应用——这在层级 1 集成下就已成立。

几条经验法则：

- 通信需求非常专门的库（如分布式 allreduce）应从层级 1 开始（之后可逐步加深）。例如 Horovod on Ray 主要用 actor，但也在扩展到用对象与任务做数据预处理。
- 可以按需挑选要利用的 Ray 特性——它们彼此协作，但多数应用只会用到其中一部分。例如 RayDP 只用 Ray actor，而 Dask-on-Ray 用任务与对象。

集成所需的工作量也随集成层级与库的成熟度变化。一般规律：

- 层级 1 集成可以从少于 200 行代码起步。
- 这通常是因为库自身已把启动 worker 的流程分离得很好。
- 层级 2-3 集成，视库不同，从轻松到工程量极大都有可能。例如：
- Dask-on-Ray 集成只花了几[几百行代码](https://github.com/ray-project/ray/blob/master/python/ray/util/dask/scheduler.py)，因为 Dask 本就设计为可插拔调度器。
- 类似地，scikit-learn 集成约 [50 行代码](https://github.com/ray-project/ray/blob/master/python/ray/util/joblib/ray_backend.py)，利用 joblib 作为集成点。
- 而另一方面，要让 Spark 全面接入 Ray 的内存子系统，则是一个大型工程项目。

## Ray 库之间的互操作

最后一个问题："Ray 库之间如何协作？"

几种常见模式：

- 库作为子程序：一个分布式库作为另一个库的子程序运行。又分两种：嵌套式，例如[在 Ray Tune 中把 XGBoost 训练作业作为一个 trial 运行](https://docs.ray.io/en/master/tune/tutorials/tune-xgboost.html)；交织式，例如在 [Dask-on-Ray](https://docs.ray.io/en/master/) 中，你可能想在 map 函数内部使用 Ray actor 或任务。
- 库间传数据：在 Airflow-on-Ray 中，数据[在工作流步骤之间](https://www.astronomer.io/blog/)通过 Ray 内存对象存储传递。RayDP 把 Spark 作业的输出写入 Ray 对象存储，使下游应用逻辑可以通过 MLDataset API [轻松访问](https://github.com/oap-project/raydp/tree/master/examples)。

最后，应用也可以简单同时调用多个库。一个 Ray 应用天然可以在各自的 task 与 actor 中使用多个库，而这些库彼此完全无需感知对方。
