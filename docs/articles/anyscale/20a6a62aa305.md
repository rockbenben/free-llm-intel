## Link概览

大语言模型（LLM）无疑改变了我们与信息交互的方式。但当我们向它们提出要求时，它们也有其固有的一堆局限。基座 LLM（如 `Llama-2-70b`、`gpt-4` 等）只了解它们训练时所接触的信息，一旦我们要求它们知道那之外的信息，它们就会力不从心。检索增强生成（RAG）类的 LLM 应用正是为了解决这一问题，把 LLM 的效用扩展到我们具体的数据源上。

在本指南中，我们将构建一个基于 RAG 的 LLM 应用，引入外部数据源来增强我们 LLM 的能力。具体而言，我们会构建一个能够回答关于 [Ray](https://github.com/ray-project/ray) —— 一个用于将 ML 工作负载生产化并规模化的 Python 框架 —— 问题的助手。这里的目标是让开发者更容易采用 Ray，同时，正如我们将在本指南中看到的，也帮助改进我们自己的 Ray 文档，并为其他 LLM 应用打下基础。我们还会分享一路上遇到的挑战，以及我们如何克服它们。

**注意**：我们已经把整份指南做了泛化处理，使得它可以轻松地被扩展用于在你自己的数据之上构建基于 RAG 的 LLM 应用。

- `Pass the query to the embedding model to semantically represent it as an embedded query vector.`
- `Pass the embedded query vector to our vector DB.`
- `Retrieve the top-k relevant contexts – measured by distance between the query embedding and all the embedded chunks in our knowledge base.`
- `Pass the query text and retrieved context text to our LLM.`
- `The LLM will generate a response using the provided content.`

除了构建我们的 LLM 应用，我们还将专注于在生产环境中把它规模化并对外服务。与传统的机器学习，乃至有监督深度学习不同，规模从最开始就是 LLM 应用的瓶颈。大数据集、大模型、计算密集型工作负载、服务需求等等。我们要把应用开发成能够应对任意规模，因为我们所处的世界还在持续增长。

我们还将专注于评估与性能。我们的应用牵涉许多移动的部件：embedding 模型、chunk 切分逻辑、LLM 本身等等，因此我们必须尝试不同的配置，以优化出最高质量的回复。然而，对一个生成式任务来说，评估并定量比较不同配置并非易事。我们会把应用各部分（给定 query 的检索、给定 source 的生成）的评估拆开来看，同时评估整体表现（端到端生成），并分享通向优化配置的发现。

**注意**：我们在本指南中会尝试不同的 LLM（OpenAI、Llama 等）。你需要 [OpenAI 凭据](https://platform.openai.com/account/api-keys)才能访问 [ChatGPT 模型](https://platform.openai.com/docs/models/)，并使用 [Anyscale Endpoints](https://endpoints.anyscale.com/)（提供公共与私有 endpoint）来服务 + 微调 OSS LLM。

### Link切分数据

现在我们有了一个 section 列表（含每个 section 的文本和来源），但还不能直接把它当作我们 RAG 应用的 context。每个 section 的文本长度参差不齐，其中很多是相当大的 chunk。

### Link嵌入数据

现在我们已经从各个 section 生成了小 chunk，需要一种方法为给定 query 找出最相关的那些。一个非常有效且快捷的办法是：用预训练模型来嵌入我们的数据，并用同一个模型嵌入 query。然后我们可以计算所有 chunk embedding 与 query embedding 之间的距离，从而确定 top-k chunk。可用于嵌入数据的预训练模型有很多，但最流行的一些可以通过 [HuggingFace 的 Massive Text Embedding Benchmark (MTEB)](https://huggingface.co/spaces/mteb/leaderboard) 排行榜来发现。这些模型在非常庞大的文本语料上通过 next/masked token prediction 之类的任务预训练，从而学会把 sub-token 表示到 N 维空间并捕捉语义关系。我们可以利用这一点来表示数据，并找出最相关的 context 用来回答给定 query。我们使用 Langchain 的 Embedding 封装（[HuggingFaceEmbeddings](https://api.python.langchain.com/en/latest/embeddings/langchain.embeddings.huggingface.HuggingFaceEmbeddings.html) 和 [OpenAIEmbeddings](https://api.python.langchain.com/en/latest/embeddings/langchain.embeddings.openai.OpenAIEmbeddings.html)）来便捷地加载模型并嵌入我们的文档 chunk。

**注意**：embedding 并不是判断哪些 chunk 更相关的方法。我们同样可以让一个 LLM 来决定！然而，因为 LLM 远比这些 embedding 模型大，且有最大 context 长度，更好的做法是用 embedding 检索出 top k chunk。然后我们可以在更少的 k 个 chunk 上用 LLM 来决定最终用作 context、回答我们 query 的 <k 个 chunk。我们还可以用重排序（如 [Cohere Rerank](https://txt.cohere.com/rerank/)）来进一步找出最该使用的 chunk。我们还可以把 embedding 与传统的检索方法（如关键词匹配）结合，这对匹配那些在嵌入 sub-token 时可能丢失的独特 token 会很有用。

```

16                model_kwargs={"device": "cuda"},
```

## Link生成回复

现在我们就可以用这些 context 从我们的 LLM 生成一个回复。没有这些我们检索到的相关 context，LLM 可能无法准确回答我们的问题。而且随着数据增长，我们可以同样轻松地嵌入并索引任何新数据，并把它检索出来回答问题。

### LinkAgent

让我们把 context 检索和回复生成结合起来，做成一个便捷的 query agent，用它就能轻松生成回复。它会负责搭好我们的 agent（embedding 与 LLM 模型），以及 context 检索，并把它们交给我们的 LLM 来生成回复。

```
1class QueryAgent:
2    def __init__(self, embedding_model_name="thenlper/gte-base",
3                 llm="meta-llama/Llama-2-70b-chat-hf", temperature=0.0, 
4                 max_context_length=4096, system_content="", assistant_content=""):
5
6        # Embedding model
7        self.embedding_model = get_embedding_model(
8            embedding_model_name=embedding_model_name, 
9            model_kwargs={"device": "cuda"}, 
10            encode_kwargs={"device": "cuda", "batch_size": 100})
11
12	 # Context length (restrict input length to 50% of total length)
13        max_context_length = int(0.5*max_context_length)
14
15        # LLM
16        self.llm = llm
17        self.temperature = temperature
18        self.context_length =  max_context_length - get_num_tokens(system_content + assistant_content)
19        self.system_content = system_content
20        self.assistant_content = assistant_content
21
22    def __call__(self, query, num_chunks=5, stream=True):

25            query=query,

28
29        # Generate response
30        context = [item["text"] for item in context_results]
31        sources = [item["source"] for item in context_results]
32        user_content = f"query: {query}, context: {context}"
33

35            llm=self.llm,
36            temperature=self.temperature,
```

## Link评估

到目前为止，我们为 RAG 应用的各个部分都选了典型的/随意的取值。但如果我们要改动其中的某些东西，比如切分逻辑、embedding 模型、LLM 等，我们怎么知道自己得到了一个比以前更好的配置？像这样的生成式任务很难定量评估，所以我们需要开发出可靠的方法来做这件事。

因为我们的应用有许多移动的部件，我们既要进行单元/组件级评估，也要进行端到端评估。逐组件的评估可以包括单独评估我们的检索（最好的 source 是否在我们检索到的 chunk 集合里），以及评估我们 LLM 的回复（给定最好的 source，LLM 能否产出高质量的回答）。而对于端到端评估，我们可以评估整个系统的质量（给定数据源，回复的质量如何）。

我们会让评估 LLM 用 context 给回复的质量在 1-5 之间打分，不过，我们也可以让它为其他维度产出分数，例如幻觉（生成的回答是否只使用所提供的 context 中的信息）、毒性等等。

**注意**：我们本可以把分数约束为二值（0/1），那样可能更可解释（如回复要么对要么错）。然而，我们给分数引入了更高的方差，以便更深入、更细粒度地理解 LLM 如何给回复打分（如 LLM 对回复的偏向）。

![llm 评估](https://images.ctfassets.net/xjan103pcp94/17UQdsEImsXOOdDlT06bvi/4a9b9e46e157541a1178b6938624176a/llm_evaluations.png)

### Link工具函数

在开始实验之前，我们要再定义几个工具函数。我们的评估工作流会用评估器来衡量我们应用端到端的质量（quality_score (overall)），因为回复同时取决于检索到的 context 和 LLM。但我们也会引入一个 retrieval_score 来衡量检索过程（切分 + 嵌入）的质量。我们判定 retrieval_score 的逻辑是：只要最佳 source 出现在我们检索到的 num_chunks 个 source 中的任何位置，就记为一次成功。我们没有考虑顺序、精确的页面 section 等，但我们可以加上这些约束来得到一个更保守的检索分数。

```
1def get_retrieval_score(references, generated):
2    matches = np.zeros(len(references))
3    for i in range(len(references)):
4        reference_source = references[i]["source"].split("#")[0]
5        if not reference_source:
6            matches[i] = 1
7            continue
8        for source in generated[i]["sources"]:
9            # sections don't have to perfectly match
10            if reference_source == source.split("#")[0]:
11                matches[i] = 1
12                continue
13    retrieval_score = np.mean(matches)
14    return retrieval_score
15
```

### LinkChunk 大小

接下来，我们评估各种 chunk 大小。较小的 chunk（但别太小！）能够封装原子概念，从而带来更精确的检索；而较大的 chunk 更容易受噪声影响。流行的策略包括：使用小 chunk，但检索它周围一点点[相邻 chunk](https://gpt-index.readthedocs.io/en/latest/end_to_end_tutorials/dev_practices/production_rag.html#decoupling-chunks-used-for-retrieval-vs-chunks-used-for-synthesis)（因为它们可能有相关信息），或者为每个文档存[多个 embedding](https://python.langchain.com/docs/modules/data_connection/retrievers/multi_vector)（如每个文档一个摘要 embedding）。

## Link微调

到目前为止我们所探索的一切，都涉及优化数据如何被预处理、以及原样使用我们的模型（embedding、LLM 等）。不过，用我们用例独有的数据来微调模型也值得一试。这能帮助我们更好地表示数据，最终提升我们的检索分数和质量分数。本节中，我们要微调我们的 embedding 模型。这里的直觉是：去学一个比默认 embedding 模型更具上下文的 token 表示，也许是值得的。如果我们大量存在以下情形，这一点尤其有影响力：

- 默认分词过程会将其拆成 subtoken、从而丢失 token 重要性的新 token
- 在我们的用例中含义随上下文而不同的已有 token

![rag-based-llm-applications-finetune-embeddings](https://images.ctfassets.net/xjan103pcp94/4G5324lsDZwq0jES7uBH0l/a715cd50af7061e1b3c57ec3e8038f05/rag-based-llm-applications-finetune-embeddings.png)

rag-based-llm-applications-finetune-embeddings

在微调 embedding 模型时，我们将探索两种方法：

- **full parameter**：包括 embedding 层以及其后的所有 encoder 层（transformer blocks）
- **embedding layer**：更好地表示我们独特的 subtoken，并避免过拟合（linear adapter 的一种形式）

**注意**：本节我们不会探索微调 LLM，因为我们之前的[实验](https://www.anyscale.com/blog/fine-tuning-llama-2-a-comprehensive-case-study-for-tailoring-models-to-unique-applications)（[LoRa 与 full parameter](https://www.anyscale.com/blog/fine-tuning-llms-lora-or-full-parameter-an-in-depth-analysis-with-llama-2)）已经表明，微调在[塑形而非塑实](https://www.anyscale.com/blog/fine-tuning-is-for-form-not-facts)方面帮助巨大，而这一点在我们的用例里帮不了太多（相比如 SQL 生成）。不过，你的用例可能从微调中获益，所以务必看看我们的 [Anyscale Endpoints 微调](https://www.anyscale.com/endpoints)，轻松调优并服务模型（完全托管，或私有部署在你自己的云上）。

### Link合成数据集

我们的第一步是创建一个数据集，用来微调 embedding 模型。我们当前的 embedding 模型是通过自监督学习训练的（word2vec、GloVe、next/masked token prediction 等），所以我们会继续用自监督工作流来微调。我们会复用与前面冷启动 QA 数据集一节非常相似的方法，从而把数据中的 section 映射到问题。这里的微调任务是：让模型判定我们数据集中哪个 section 最匹配输入 query。这一优化任务会让我们的 embedding 模型学到对我们数据集中 token 更好的表示。

**注意**：虽然我们本可以创建一个把 section 标题与 section 文本对应起来的数据集，但我们之所以创建合成 Q&A 数据集，是因为它最能代表我们想要学会嵌入的那类数据。

我们的 prompt 会略有不同，因为我们想要生成各式各样的问题；而且我们这里会用 `llama-70b`，以便能规模化这一 QA 生成过程（并避开任何速率限制）。为求周全，我们会为数据集中的每一个 section 生成一个问题，从而尽可能多地捕捉独特 token。

### Link验证

我们的验证评估标准涉及一个信息检索（IR）评估器，它会为每个 query 从语料库中检索 top k 个相似文档。[InformationRetrievalEvaluator](https://www.sbert.net/docs/package_reference/evaluation.html#sentence_transformers.evaluation.InformationRetrievalEvaluator) 需要以下输入：

- queries: `Dict[str, str]` # qid => query
- corpus: `Dict[str, str]` # cid => doc
- relevant_docs: `Dict[str, Set[str]]` # qid => Set[cid]

**注意**：虽然我们的数据集对于某个特定 query 可能有多段有效 section，我们会把除用来生成该 query 的那一段之外的所有其他 section 都当作负样本。这不是理想的场景，但引入的噪声很小，尤其因为我们用它来调一个表示层（而不是用于分类任务）。

## Link词汇检索

我们现在要用传统的词汇检索来补充基于向量 embedding 的检索，词汇检索会在我们的 query 与文档 chunk 之间寻找精确的 token 匹配。我们这里的直觉是：当语义表示可能捕捉不到时，词汇检索能帮助识别那些有精确关键词匹配的 chunk，尤其是对于在我们 embedding 模型中属于词汇表之外（因而以 subtoken 表示）的 token。但基于 embedding 的方法在捕捉隐式含义上仍然非常有优势，所以我们把基于向量 embedding 的检索与词汇检索各自检索到的若干 chunk 结合起来。

## Link重排序

到目前为止，在我们所有的方案里，我们一直用 embedding 模型（+ 词汇检索）来识别数据集中 top k 相关的 chunk。chunk 的数量（k）一直是个小数字，因为我们发现加太多 chunk 并没有帮助，而我们的 LLM 又有受限的 context 长度。然而，这一切都建立在以下假设之上：被检索到的 top k chunk 确实是最相关的 chunk，并且它们的顺序也是对的。如果增加 chunk 数量并没有帮助，是因为某些相关的 chunk 排在了有序列表的更靠后位置呢？而且语义表示虽然非常丰富，却不是为这个特定任务训练的。

本节我们实现重排序，好让我们能用语义与词汇检索方法在数据集上撒下一张更大的网（检索许多 chunk），然后基于用户的 query 对顺序重新排序。这里的直觉是：我们能用与我们用例专门相关的排序，来弥补语义表示上的缺口。我们会训练一个有监督模型，它对「给定某个用户 query，我们[文档](https://docs.ray.io/)的哪一部分最相关」做出预测。我们随后用这个预测来对相关 chunk 重排序，使得来自文档这一部分的 chunk 被移到列表顶部。

### Link预处理

我们先创建一些预处理函数，以更好地表示数据。举例来说，我们的文档里有很多驼峰命名（camel cased）的变量（如 `RayDeepSpeedStrategy`）。当对一个这样的词使用 tokenizer 时，我们往往会丢失那些我们明知有用的独立 token，反而被造出一些随机的 subtoken。

**注意**：我们并非未卜先知地知道要去创建这些独特的预处理函数！这一切都是有条理地反复迭代的结果。我们训练一个模型 → 查看错误的数据点 → 查看数据是如何被表示的（如 subtoken 化）→ 更新预处理 → 再迭代 ↺

```
1import re
2from transformers import BertTokenizer
3
4def split_camel_case_in_sentences(sentences):
5    def split_camel_case_word(word):
6        return re.sub("([a-z0-9])([A-Z])", r"\1 \2", word)
7    processed_sentences = []
8    for sentence in sentences:
9        processed_words = []   
10        for word in sentence.split():
11            processed_words.extend(split_camel_case_word(word).split())
12        processed_sentences.append(" ".join(processed_words))
13    return processed_sentences
14
15def preprocess(texts):
16    texts = [re.sub(r'(?<=\w)([?.,!])(?!\s)', r' \1', text) for text in texts]
17    texts = [text.replace("_", " ").replace("-", " ").replace("#", " ").replace(".html", "").replace(".", " ") for text in texts]
18    texts = split_camel_case_in_sentences(texts)  # camelcase
19    texts = [tokenizer.tokenize(text) for text in texts]  # subtokens
20    texts = [" ".join(word for word in text) for text in texts]
21    return texts
```

### Link重排序实验

现在，我们准备好用以下步骤在检索之后应用我们的重排序模型：

- 增大检索到的 context（这可以尝试），好让我们能应用重排序，从而得到一个更小的子集（`num_chunks`）。这里的直觉是：我们用语义和词汇检索来检索 N 个 chunk（N > k），然后用重排序来重排检索结果（top k）。
- 如果预测的 tag 高于 `threshold`，我们就把来自那个 tag 的所有检索 source 移到顶部。如果预测的 tag 低于阈值，则不执行重排序。这里的直觉是：除非我们对某个特定 query 关乎我们文档的哪些部分有信心（或它恰好涉及多个部分），否则我们不会错误地对结果重排序。
- 用检索到的 top k chunk 执行生成。

我们要直接改动 `QueryAgent` 类来纳入重排序：

## Link路由

看起来性能最强的 LLM `gpt-4-turbo` 同时也非常昂贵。而我们的 OSS LLM（`mixtral-8x7b-instruct-v0.1`）在质量上非常接近，但成本效益高出约 25 倍。然而，我们希望能提供兼具最强性能与最佳成本效益的方案。我们可以把 query 按其复杂度或主题路由给合适的 LLM，从而缩小开源模型与专有模型之间的性能差距。举例来说，在我们的应用里，开源模型在那些答案能从检索到的 context 轻易推断出的简单 query 上表现得非常好。然而，对于涉及推理、数字或代码示例的 query，OSS 模型就显得力不从心。为确定该用哪个合适的 LLM，我们可以训练一个分类器，它接收 query 并把它路由给最佳的 LLM。

`Question for gpt-4:
 {'question': 'if I am inside of a anyscale cluster how do I get my cluster-env-build-id', 'target': 0}
Question for OSS LLM:
 {'question': 'what is num_samples in tune?', 'target': 1}`

![image15](https://images.ctfassets.net/xjan103pcp94/7FWrvPPlIdz5fs8wQgxLFz/acbf21595b9401be677484c0de90a06f/routing-diagram.png)

- `Pass the query to a supervised classifier that will determine which LLM is appropriate to answer it.`
- `The predicted LLM receives the query.`
- `Pass the query to our embedding model to semantically represent it.`
- `Pass the retrieved context to the predicted LLM.`
- `Generate the response.`

为了实现这一点，我们手工标注了一份[包含 1.8k 条 query 的数据集](https://github.com/ray-project/llm-applications/blob/main/datasets/routing-dataset-train.jsonl)，按哪个模型（`gpt-4`（label=0）或 OSS LLM（label=1））更合适来标注 —— 默认我们路由给 OSS LLM，只有当 query 需要更高级的能力时我们才把它发送给 `gpt-4`。随后我们在一个已经用评估器打分的[测试数据集](https://github.com/ray-project/llm-applications/blob/main/datasets/routing-dataset-test.jsonl)上评估模型的表现。

## Link服务

现在我们准备好用最佳配置来对外服务我们的 Ray Assistant 了。我们要用 [Ray Serve](https://docs.ray.io/en/latest/serve/index.html) 搭配 [FastAPI](https://fastapi.tiangolo.com/) 来开发并扩展我们的服务。首先，我们会定义一些数据结构，如 Query 和 Answer，用来表示我们服务的输入与输出。我们还会定义一个小函数来加载我们的索引（假定对应的 SQL dump 文件已存在）。最后，我们可以定义我们的 QueryAgent 并用它来服务携带 query 的 POST 请求。而且我们可以用 [@serve.deployment](https://docs.ray.io/en/latest/serve/api/doc/ray.serve.Deployment.html) 装饰器，在我们想要的任意部署规模上服务 agent，在其中指定副本数、计算资源等。

```
1# Initialize application
2app = FastAPI()
3
4@serve.deployment(route_prefix="/", num_replicas=1, ray_actor_options={"num_cpus": 6, "num_gpus": 1})
5@serve.ingress(app)
6class RayAssistantDeployment:
7    def __init__(self, chunk_size, chunk_overlap, num_chunks, 
8                 embedding_model_name, embedding_dim,
9                 use_lexical_search, lexical_search_k, 
10                 use_reranking, rerank_threshold, rerank_k,
11                 llm, sql_dump_fp=None):
12
13        # Set up
14        chunks = build_or_load_index(
15            embedding_model_name=embedding_model_name, 
16            embedding_dim=embedding_dim, 
17            chunk_size=chunk_size, 
18            chunk_overlap=chunk_overlap,
19            sql_dump_fp=sql_dump_fp,
20        )
21
22        # Lexical index
23        lexical_index = None
24        self.lexical_search_k = lexical_search_k
25        if use_lexical_search:
26            texts = [re.sub(r"[^a-zA-Z0-9]", " ", chunk[1]).lower().split() for chunk in chunks]
27            lexical_index = BM25Okapi(texts)
28
29        # Reranker
30        reranker = None
31        self.rerank_threshold = rerank_threshold
32        self.rerank_k = rerank_k
33        if use_reranking:
34            reranker_fp = Path(EFS_DIR, "reranker.pkl")
35            with open(reranker_fp, "rb") as file:
36                reranker = pickle.load(file)
37
38        # Query agent
39        self.num_chunks = num_chunks
40        system_content = "Answer the query using the context provided. Be succinct. " \
41            "Contexts are organized in a list of dictionaries [{'text': <context>}, {'text': <context>}, ...]. " \
42            "Feel free to ignore any contexts in the list that don't seem relevant to the query. "
43        self.oss_agent = QueryAgent(
44            embedding_model_name=embedding_model_name,
45            chunks=chunks,
46            lexical_index=lexical_index,
47            reranker=reranker,
48            llm=llm,
49            max_context_length=MAX_CONTEXT_LENGTHS[llm],
50            system_content=system_content)
51        self.gpt_agent = QueryAgent(
52            embedding_model_name=embedding_model_name,
53            chunks=chunks,
54            lexical_index=lexical_index,
55            reranker=reranker,
56            llm="gpt-4",
57            max_context_length=MAX_CONTEXT_LENGTHS["gpt-4"],
58            system_content=system_content)
59
60        # Router
61        router_fp = Path(EFS_DIR, "router.pkl")
62        with open(router_fp, "rb") as file:
63            self.router = pickle.load(file)
64
65    @app.post("/query")
66    def query(self, query: Query) -> Answer:
67        use_oss_agent = self.router.predict([query.query])[0]
68        agent = self.oss_agent if use_oss_agent else self.gpt_agent
69        result = agent(
70            query=query.query, num_chunks=self.num_chunks, 
71            lexical_search_k=self.lexical_search_k, 
72            rerank_threshold=self.rerank_threshold, 
73            rerank_k=self.rerank_k, 
74            stream=False)
75        return Answer.parse_obj(result)
```

## Link数据飞轮

创建这样一个应用并非一劳永逸的事。持续迭代并让我们的应用保持最新极其重要。这包括不断重新索引我们的数据，好让应用基于最新的信息工作；也包括重新运行我们的实验，看看是否有任何决策需要改动。这种持续迭代的过程可以通过把工作流映射到 [CI/CD pipeline](https://madewithml.com/courses/mlops/cicd/) 来实现。

迭代中一个超越了自动化重索引、评估等的关键部分，涉及修复我们的数据本身。事实上，我们发现这是我们所能控制的、**最**有影响力的杠杆（远远超过上面那些检索与生成上的优化）。这里是一个我们已经定下来的工作流示例：

- 用户使用 RAG 应用就产品提问。
- 用反馈（👍/👎、访问过的 source 页面、top-k 余弦分数等）来识别表现不佳的 query。
- 检查检索到的资源、分词等，以判定这是检索、生成还是底层数据源的不足。
- 如果数据里有可改进之处，可拆成分节/页面等 → 就修！
- 在之前表现不佳的 query 上评估（并加入测试套件）。
- 重新索引并部署应用的新的、可能进一步优化的版本。

### Link产品与生产力

构建这样一个 LLM 应用对我们的产品和公司产生了巨大的影响。在产品和用户的整体开发者与用户采用度上，有可预期的 1 阶影响。能够以自助、即时的方式交互并解决用户所遇到的问题，这类功能会改善任何产品的体验。它让人们更容易成功，也把人们对 LLM 应用的看法从**锦上添花**提升为**必备**。
