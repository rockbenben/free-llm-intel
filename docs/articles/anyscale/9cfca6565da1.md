# LLM的开源强化学习库

作者：[Tyler Griggs](https://www.anyscale.com/blog?author=tyler-griggs) 和 [Philipp Moritz](https://www.anyscale.com/blog?author=philipp-moritz) | 2025 年 7 月 1 日

*本博文的内容于 2025 年 9 月 1 日更新，包含每个库的最新信息，并包含新的 *[*slime*](https://github.com/THUDM/slime)* 库。*

强化学习（RL）已成为现代大型语言模型开发不可或缺的一部分。除了传统的训练后使用人类反馈强化学习 (RLHF) 来使模型与人类偏好保持一致之外，基于可验证奖励的强化学习已成为扩展 LLM 能力的强大技术。随着高质量的预训练数据变得越来越稀缺，这种方法变得尤为重要。

最近的突破证明了这种范式的有效性，包括 OpenAI 的推理模型（[o1](https://openai.com/o1/) 和 [o3](https://openai.com/index/introducing-o3-and-o4-mini/)）和公开可用的 [DeepSeek R1](https://arxiv.org/abs/2501.12948) 模型。最新前沿将 LLM 强化学习扩展到多回合设置，其中模型充当与环境交互的代理以解决复杂任务。这代表着朝着创建可以作为跨不同领域的有效代理人的LLM迈出了重要的一步。

鉴于强化学习的潜力，开源生态系统经历了快速发展，出现了许多体现不同设计原则和优化选择的库。本分析从技术角度审视了领先的强化学习框架，评估了它们各自的优势和局限性。我们在开发[强化学习库](https://github.com/NovaSky-AI/SkyRL)的同时进行了这项研究，系统地分析现有解决方案，以了解每种方法固有的设计决策和架构权衡。通过分享这些见解，我们的目标是帮助研究人员和从业者更有效地驾驭当前的形势，并就哪些工具最适合他们的特定要求和用例做出明智的选择。

我们承认某些比较点可能是主观的 - 我们尽最大努力尽可能根据客观标准比较库，并提供库中相关代码的链接，以便您获得自己的印象。如果您认为某些内容被歪曲，请告诉我们。另外，请记住，这些库正在以非常快的速度发展，因此请务必查阅不同库的文档和代码以获取最新更新。

## Link我们比较的库

我们选择这些特定的库是基于它们最近的活动、与不同用例的相关性（从 RLHF 到代理 RL）以及它们在开源领域中不同架构哲学的表现。

**TRL：** Hugging Face 的流行库，与 Hugging Face 生态系统紧密集成，专注于 RL 的训练方面。

**Verl：** 来自字节跳动的流行高性能、功能丰富的 RL 堆栈，针对可扩展性和对高级训练技术的支持进行了优化。

**OpenRLHF：**最早流行的开源RLHF库之一，它既易于使用又高性能。与Verl类似，为后续很多框架铺平道路

**RAGEN：** Verl 的一个显着扩展，它扩展了其功能，重点关注多轮对话和多样化的 RL 环境。

**Nemo-RL：** NVIDIA 的综合后训练框架，采用简洁的界面设计，注重结构化数据流，同时也考虑到可扩展性和高性能。

**ROLL：** 阿里巴巴的新库，用于 RLHF、推理和多轮代理训练 - 旨在为研究人员提供灵活性，并可扩展以供大规模生产使用。

**AReaL：** Ant Research 的 RL 库，专注于异步训练，以提高训练吞吐量和可扩展性。

**slime**：来自清华大学和 [Z.ai](http://z.ai) 的 RL 库，专注于简单性和高性能，并且可以轻松集成任意自定义数据生成方法。

**验证者：** 该框架基于 TRL 构建，通过可验证的奖励简化了多轮 RL 的实施，优先考虑易用性。

**SkyRL**：来自伯克利的新 RL 库，专注于多轮代理训练，采用简单灵活的设计，允许高性能执行和适应各种场景。

## Link 强化学习库的用例和组件

强化学习库旨在简化能够解决复杂问题的强化学习策略的训练过程。用户定义他们的具体问题以及衡量解决方案质量的奖励函数，而库则处理底层培训机制以制定有效的策略。培训政策的常见问题包括：

- [编码](https://github.com/All-Hands-AI/OpenHands)，其中奖励是代码是否正确（例如，通过是否通过一套单元测试来衡量），
- [计算机使用](https://github.com/OpenInterpreter/open-interpreter)（即用计算机解决任务），其中奖励是任务是否成功解决，
- [制定数学证明](https://github.com/openreasoner/openr)，如果证明是给定命题的有效证明，则奖励为+1，否则奖励为0，并且
- [玩游戏](https://github.com/openai/gym)，奖励是游戏中最终获得的分数，或者策略是否能够击败游戏。

正如简介中提到的，LLM 的 RL 库有许多不同的用例：

- **来自人类反馈的强化学习 (RLHF)**：这是最初的 RL 训练后用例，并使LLM与人类偏好保持一致。作为其中的一部分，从人类那里收集偏好数据集，从中学习奖励模型，然后使用该模型运行强化学习以适应LLM。
- **推理模型：** 该用例使用解决数学或科学问题或编码等任务来提高LLM的推理能力。 LLM 不会立即输出答案，而是首先学习输出“思考”标记，这可以提高模型的性能。思维过程通常是通过运行强化学习来学习的，并对问题进行可验证的奖励。由于LLM在推理过程结束时给出单一答案，因此这通常被称为“单步”强化学习。
- **代理和多步骤强化学习：** 在此设置中，LLM 在环境中作为自主代理运行，执行多个连续操作来完成任务。这代表了最复杂的配置，并对支持库提出了最高的要求。图书馆必须协调环境和LLM，同时处理可能需要跨不同实例执行不同数量的步骤的问题。

强化学习库的核心可以分为两个基本组件：

- **生成器**，将LLM设置为与环境交互以解决问题并计算奖励。
- **训练器**根据生成阶段给出的奖励反馈更新模型。

框架的设计和集成这些组件的方式揭示了其核心理念和用例。有些库更专注于 RLHF，有些库针对训练推理模型进行了优化，还有一些库对生成和环境具有更强大的抽象，这使得它们更适合多轮 RL 和训练代理。

我们将首先更深入地探讨这些组件中可以进行的设计权衡。

### 链接生成器

生成阶段通常是计算中最昂贵的部分。它涉及在 LLM 上运行推理以及在环境中执行操作并计算奖励。通常，存在一个问题数据集，其中可能包含问题陈述的初始提示和/或代理应运行的环境参数。在可验证奖励的情况下，还存在问题正确答案的概念。对于每个问题，当前策略都会生成一个轨迹，其中包含由 LLM 生成的令牌序列，这些令牌包含在环境中采取的操作。不同的库以不同的方式表示这些轨迹，但 OpenAI 格式是常见的选择。

生成可以任意复杂，并在以树状方式探索更大的解决方案空间时使用分支等技术。可以轻松定义用于生成部署的自定义生成函数的库，为自定义采样、分支和搜索提供最大程度的灵活性。

环境是生成器的重要组成部分。在早期用于 RLHF 或训练推理模型的 RL 库中，通常没有明确的环境。相反，LLM的每个输出都通过奖励模型或自定义奖励函数形式的显式奖励进行评分。后来，添加了更明确的 API，通常类似于 OpenAI 的 Gym 界面，具有 init、step 和 Reset 函数。这允许在轨迹生成期间使用工具，以及 LLM 和环境之间的多步骤交互。在许多情况下，环境的实际执行发生在单独的容器/进程中或远程服务器上，因此可以隔离环境。

### 链接培训师

训练器是核心优化循环所在的位置，它获取生成阶段收集的轨迹数据并生成新策略。大多数库都已标准化支持 PPO 和 GRPO 训练算法。就用于在不同 GPU 之间分割模型的分片后端而言，有多种不同的选择，其中 Hugging Face trainer、FSDP、DeepSpeed 和 Megatron 是最受欢迎的。 FSDP 是与 PyTorch 紧密集成的更简单的选择之一，DeepSpeed 具有更积极的参数和优化器卸载，而 Megatron 是更大规模时性能最高的。一些库从 Hugging Face 的 TRL 库中获取训练代码，还有许多库在底层使用 veRL 的训练代码，该代码本身支持 FSDP 和 Megatron。

## 链接比较点

我们希望尽可能保持比较客观，因此我们专注于可以从库的代码和文档中客观推断出的比较点。我们链接到相关地方，以便用户形成自己的观点并做出自己的选择。

**采用率：**虽然描述库采用率的任何指标都不完美，但我们包括第一个版本、星星数量、总问题数和贡献者作为每个库采用率的代理。给定一个满足您的用例（例如，RLHF、训练推理模型、训练代理）并具有您需要的功能的库，更广泛采用的库通常更可取，因为它们在更多场景中进行了测试，因此通常更强大，并且更容易找到帮助。

**系统属性：** 除了列出库所针对的用例之外，我们还列出了每个库可以具有的属性：

- **效率**：支持推理/训练或异步训练的托管
- **可扩展性**：支持集群上多个 GPU 的推理和训练
- **Modular**：对于库的各个组件具有清晰的接口，可以实现这些组件来更改库的行为
- **灵活性**：尝试支持广泛的功能或可以轻松修改以支持不同的设置 - 在大多数情况下，这将是主观的，因为一些用户喜欢有很多配置选项，而其他用户则喜欢他们可以自行修改的简单实现

**组件：** 我们链接每个库的“强化学习库的组件”部分中描述的训练器、生成器和环境组件。这些组件可能并不总是完全遵循训练器、生成器和环境的划分 - 例如，某些库将生成器和环境统一为组合的多轮环境。我们还包括有关训练后端、推理引擎和环境层的以下信息：

**训练后端**：我们列出了库支持哪些训练后端（Hugging Face 训练器、FSDP、DeepSpeed 或 Megatron）以及不同框架支持哪些开箱即用的算法。

**推理引擎：** 最流行的推理引擎是 vLLM、SGLang、Hugging Face 转换器或通过 OpenAI API 的外部推理引擎。可能的部署模式包括推理引擎和训练引擎共置或单独部署。一些 RL 框架支持不受框架管理的外部推理引擎。共置训练和推理有助于减少 GPU 使用率，但灵活性较差。在涉及落后任务的长范围任务、异步推理工作负载、应使用不同的 GPU 类型进行训练和推理或训练和推理需要独立扩展时，分离训练和推理通常更可取。另一个设计决策是是否支持多个推理引擎以及多个推理引擎之间的负载平衡是在客户端还是服务器端完成。

**异步支持：** 库是否可以通过异步运行这两个活动来重叠训练和生成。这样做可以提高资源利用率，特别是对于落后者的长期部署，但会使学习动态变得复杂并可能不稳定。有多种方法可以将训练引擎更新的权重同步到推理引擎。一些方法需要在一个或多个训练引擎和所有推理引擎之间形成火炬分布式进程组，然后通过 NCCL、gloo 或 CUDA IPC 执行权重同步。这可以快速同步权重，但不灵活。有些方法通过检查模型权重到存储并将其加载到生成器中来实现同步，这更灵活但更慢。

**环境层**：不同的库对环境的支持不同。一些库仅支持单轮交互，没有显式的环境抽象。有些库具有环境抽象，但为了添加自定义环境，需要更改或分叉库本身。一些库支持在库外部实现自定义环境。一般来说，环境与生成过程的耦合越少，并且越容易集成现有环境（例如，以外部远程服务的形式）越好。为了使比较尽可能客观，并承认不同用户有不同的需求和偏好，我们链接了有关如何为每个库集成新环境的示例环境或文档，以便读者可以做出自己的决定。

**编排器：** RL 涉及彼此交互的不同组件（环境、推理引擎、训练引擎），并且可能需要以复杂的方式进行编排，例如，如果生成和训练位于相同的资源上或异步完成。此外，每个组件都由许多必须大规模运行的不同进程或容器组成。因此，拥有一个负责调度、通信、容错和自动扩展的编排器是有益的。由于其灵活性、可扩展性以及对异构计算的支持，许多 RL 库已在 Ray 上进行标准化以进行编排。

## 关于各个库的 LinkNotes

在本节中，我们将更详细地讨论上述一些库，并尝试让您了解它们构建的上下文以及它们最有用的用途。其中一些评论必然比上表更加主观，而且许多库正在快速发展，因此对一切都持保留态度。

**TRL：** 针对简单性和集成到 Hugging Face 生态系统进行了优化，例如数据集、变压器、加速器和 PEFT。它是为基于文本的训练后LLM（例如推理、RLHF）而构建的，除了 GRPO 和 PPO 之外，还支持监督微调以及 DPO。如果您对没有环境交互的基于文本的 RL 设置更感兴趣，那么这是一个不错的选择。然而，TRL 本身并不支持具有任意环境和更灵活的生成方案的多轮强化学习，这促使了其他库的开发，例如具有与 TRL 类似设计决策但也支持多轮强化学习和环境的验证器。总体而言，TRL 定义的内部接口比其他一些库少，这使得它更简单，但适应性也较差。

**Verl：** Verl 是为了性能和可扩展性而构建的，它支持所有成熟的训练框架，如 FSDP、DeepSpeed 和 Megatron。与 TRL 类似，它最初是一个用于训练推理模型并在没有环境的情况下进行单轮交互的库，但正在通过工具调用和多轮 RL 进行扩展，并且更灵活的环境/代理支持[正在出现](https://github.com/volcengine/verl/issues/1172)。出于性能原因，生成和训练紧密耦合。 Verl 拥有一个庞大的社区，并且开发非常积极，是LLM最成熟的开源 RL 库之一。已经有几个项目正在 Verl 之上构建，并以各种方式对其进行扩展 [[1]](https://github.com/TIGER-AI-Lab/verl-tool) [[2]](https://github.com/agentica-project/verl-pipeline) [[3]](https://github.com/RAGEN-AI/RAGEN)（包含完整列表） [此处](https://github.com/volcengine/verl?tab=readme-ov-file#awesome-work-using-verl))。

**OpenRLHF：** OpenRLHF 是为 RLHF 构建的，对奖励模型和不同的优化算法有很好的支持。它还支持异步训练以及生成和训练的托管。对环境/代理强化学习有一些支持，但没有专用接口。 OpenRLHF 已经成熟，拥有相当大的社区，并且在其之上构建了一些库，将其更多地扩展到[推理](https://github.com/Open-Reasoner-Zero/Open-Reasoner-Zero)以及[多智能体训练](https://github.com/TsinghuaC3I/MARTI)领域。

**RAGEN：** RAGEN 是一个构建在 Verl 之上的库，它集成了更明确的环境接口，并通过更好的代理和多轮 RL 支持扩展了 verl。它还使得定义自定义环境变得更加容易。

**AReal：** 该库特别关注性能并针对生成和训练的异步执行进行优化。为了实现最大性能，它对 PPO 实施可中断的推出和算法修改，以应对异步执行期间的数据陈旧问题。

**验证器：**解决了 TRL 的一些缺点，并增加了对环境和多轮工具使用的支持。与TRL类似，验证器也是基于Hugging Face Transformers Trainer。框架简单，深受研究人员欢迎。

**ROLL：** ROLL 旨在通过提供大量的接口（https://github.com/alibaba/ROLL/blob/b756338442d9d36c1fe4c951bc98ebc913bd95ae/assets/ROLL_map_high.png）并使库可配置来吸引不同范围的用户（大型人工智能实验室、从业者和研究人员）。

**NeMo-RL：** NeMo-RL 是最新的库之一，它为各种组件提供了明确定义的接口，并为轨迹和其他相关数据提供了清晰的数据表示。它在构建时考虑了多回合强化学习和环境支持。与 verl 类似，它也是为了性能和可扩展性而构建的，但它还不够成熟，生态系统也较少。

**SkyRL：** SkyRL 融合了上述许多库的知识，并提供简单而灵活的界面，旨在支持广泛的设置，并在构建时考虑了多轮代理设置。例如，它提供以下支持：同步或异步一次性流水线、并置或分解生成或训练、外部或集成推理引擎以及不同的权重同步方法。 SkyRL 最近发布，尚未成熟，生态系统也较少，但为代理场景提供了[几个示例脚本](https://github.com/NovaSky-AI/SkyRL/tree/main/skyrl-train/examples)。

**slime：** slime 是较新的库之一，它做出非常固执己见的决定，以使一切尽可能简单，但又保持高性能（例如，它在 sglang 和 megatron 上进行标准化，因为它们对大型 MoE 模型具有高性能）。它还包含一个数据缓冲区，可以在中央位置集中处理提示和转出数据。虽然 slime 支持托管，但它主要是为了考虑异步 RL 的解耦训练和生成而构建的。由于它专注于威震天，它的灵活性比其他一些训练框架稍差，但在支持自定义推出数据生成方面非常灵活。

## 链接结论

您可能会自然地问自己一个问题：“我应该使用哪个库？”。答案将取决于您所操作的设置和您的用例，您应该自己做出决定（希望本博客文章中的比较点会对您有所帮助）。我们可以提供一些可能有助于指导您做出决定的一般准则：

如果您正在优化训练大型模型或有严格的性能要求，那么 Verl 无疑是一个不错的选择。它是最成熟的库之一，但它对性能和可扩展性的关注也以牺牲一些灵活性为代价。如果您正在寻找更灵活的环境和代理支持，那么也值得研究 RAGEN（如果您喜欢 Verl）或其他一些框架，如 SkyRL、NeMo-RL、ROLL 或 AReal。

如果您是一名研究人员，最看重简单性和灵活性（例如，您想尝试不常用的新算法或方法，并花费大量时间更改源代码），那么值得检查验证器。

最后，如果您正在开发自己的库或对此领域感兴趣，请考虑[向 Ray Summit 2025 提交演讲](https://www.anyscale.com/blog/ray-summit-2025-call-for-proposals-cfp)，我们将在其中提供专门的后期培训和强化学习课程。
