# 面向 LLM 的开源强化学习库

作者：[Tyler Griggs](https://www.anyscale.com/blog?author=tyler-griggs) 和 [Philipp Moritz](https://www.anyscale.com/blog?author=philipp-moritz) | 2025 年 7 月 1 日

*本文内容已于 2025 年 9 月 1 日更新：补上了每个库的最新信息，并加入了新的*[*slime*](https://github.com/THUDM/slime)* 库。*

强化学习（RL）已经成为现代大语言模型开发中不可或缺的一环。除了用传统的人类反馈强化学习（RLHF）做后训练、把模型对齐到人类偏好之外，基于可验证奖励的 RL 也已经成为扩展 LLM 能力的一项有力技术。随着高质量预训练数据日益稀缺，这一路线的重要性愈发凸显。

近期的突破证明了这一范式的有效性，包括 OpenAI 的推理模型（[o1](https://openai.com/o1/) 和 [o3](https://openai.com/index/introducing-o3-and-o4-mini/)），以及公开可用的 [DeepSeek R1](https://arxiv.org/abs/2501.12948) 模型。最前沿的工作把 LLM 的强化学习扩展到了多轮设定：模型作为 agent 与环境交互来解决复杂任务。这是朝着「让 LLM 成为能在各类领域里真正管用的 agent」迈出的一大步。

正因为强化学习有这种潜力，开源生态经历了快速生长，涌现出大量体现不同设计原则与优化取舍的库。本文从技术视角审视主流的 RL 框架，评估它们各自的优势与局限。我们是在开发[一个强化学习库](https://github.com/NovaSky-AI/SkyRL)的过程中做这项研究的：为了理解每种方案固有的设计决策与架构取舍，我们系统性地分析了现有方案。分享这些洞察，是希望帮助研究者和从业者更有效地看清当前格局，并就哪些工具最适合自己的具体需求与用例做出有依据的选择。

我们也承认，其中一些比较点难免带有主观性——我们尽了最大努力按客观标准来比较这些库，并给出库中相关代码的链接，方便你自己形成判断。如果你觉得哪里有失实之处，请告诉我们。另外请记住，这些库演进得非常快，最新情况请务必查阅各库的文档与代码。

## 我们对比的库

选择这些具体的库，依据是它们近期的活跃度、对多样化用例（从 RLHF 到 agentic RL）的适配度，以及它们在开源版图里所代表的不同架构理念。

**TRL：** Hugging Face 出品的热门库，与 Hugging Face 生态紧密集成，聚焦于 RL 的训练那一侧。

**Verl：** ByteDance 出品的高性能、功能丰富的 RL 栈，同样很受欢迎，针对可扩展性和对先进训练技术的支持做了优化。

**OpenRLHF：** 最早流行的开源 RLHF 库之一，既易用又高性能。和 Verl 一样，为后来的许多框架铺了路

**RAGEN：** Verl 的一个值得关注的延伸，扩展了它的能力，重点放在多轮对话和多样的 RL 环境上。

**Nemo-RL：** NVIDIA 的全面后训练框架，设计上接口干净、聚焦结构化数据流，同时也把可扩展性与高性能放在心上。

**ROLL：** Alibaba 面向 RLHF、推理与多轮 agentic 训练的新库——对研究者足够灵活，也能扩展支撑大规模生产使用。

**AReaL：** Ant Research 的 RL 库，重点是用异步训练来提升训练吞吐与可扩展性。

**slime**：来自清华和 [Z.ai](http://z.ai) 的 RL 库，主打简单与高性能，集成任意自定义数据生成方法都很方便。

**Verifiers：** 构建在 TRL 之上，简化了「带可验证奖励的多轮 RL」的实现，把易用性放在第一位。

**SkyRL**：Berkeley 出品的 RL 新库，重点是多轮 agentic 训练，设计上简单而灵活，既能高性能地执行，也能适配各种各样的场景。

## RL 库的用例与组件

RL 库的目标，是简化「训练能解决复杂问题的 RL 策略」这件事。用户定义自己的具体问题，并给出衡量解答质量的奖励函数，库则负责底层的训练机制，把有效策略训出来。常见的训练问题包括：

- [编程](https://github.com/All-Hands-AI/OpenHands)，奖励看代码是否正确（例如以能否通过一组单元测试来度量），
- [计算机操作](https://github.com/OpenInterpreter/open-interpreter)（即用电脑完成任务），奖励看任务是否被成功解决，
- [构造数学证明](https://github.com/openreasoner/openr)，若证明对给定命题成立则奖励 +1，否则为 0，以及
- [玩游戏](https://github.com/openai/gym)，奖励是游戏中取得的最终得分，或者策略能否通关。

如引言所述，LLM 的 RL 库有好几类不同的用例：

- **人类反馈强化学习（RLHF）**：这是最早的 RL 后训练用例，用来把 LLM 对齐到人类偏好。具体做法是从人那里收集偏好数据集，据此学出一个奖励模型，再用它跑 RL 来调整 LLM。
- **推理模型：** 这一用例用解数学或科学问题、编程之类的任务来提升 LLM 的推理能力。LLM 不再立刻输出答案，而是学会先输出 "thinking" token，这能提升模型表现。思考过程通常靠在题目上跑带可验证奖励的 RL 学出来。由于 LLM 在推理过程结束时只给出一个答案，这常被称为「单步」RL。
- **Agentic 与多步 RL：** 在这种设定下，LLM 作为自主 agent 运行在一个环境里，连续执行多个动作来完成一项任务。这是最复杂的配置，对支撑库的要求也最高：库既要协调环境又要协调 LLM，还得处理不同实例所需步数差别极大的问题。

RL 库的核心可以拆成两个基本组件：

- **生成器**：把 LLM 配置成能够与环境交互，从而解题并计算奖励。
- **训练器**：根据生成阶段给出的奖励反馈来更新模型。

一个框架如何设计并整合这两个组件，体现出它的核心理念与适用场景。有些库更偏重 RLHF，有些为训练推理模型做了优化，另一些则在生成和环境上提供更强大的抽象，因而更适合多轮 RL 与训练 agent。

![面向 LLM 的开源 RL 库总览图](https://images.ctfassets.net/xjan103pcp94/3DTHR8PtMcYFYkFUnZVjTH/8aa576362b47aedbce2859583737dca6/image1.png)强化学习（RL）库的架构分为两个主要部分：生成与训练。在生成阶段，LLM Engine 在一个环境里执行多轮 rollout，产出数据和奖励信号。这些输出随后被送入训练阶段，用于更新模型的参数。这一过程构成一个反馈回路：不断变强的模型生成下一轮数据，从而持续精修。

我们先更深入地看看这些组件上可以做的设计取舍。

### 生成器

生成阶段往往是整个计算中最贵的部分。它既要对 LLM 做推理，也要在环境里执行动作并计算奖励。通常会有一个题目数据集，里面可能带着与问题描述对应的初始 prompt，和/或 agent 应当运行于其中的环境参数。在使用可验证奖励的情形里，还会有「这道题的正确答案」这一概念。针对每道题，当前策略生成一条轨迹，其中包含 LLM 产出的 token 序列，也就是在环境里采取的那些动作。不同的库用不同方式表示这些轨迹，而 OpenAI 格式是一个常见的选择。

生成过程可以复杂到任意程度，比如在更大的解空间里以树状方式探索时使用分支。那些让你方便地定义自定义 generate 函数来产出 rollout 的库，能为自定义采样、分支与搜索提供最大的灵活性。

环境是生成器的重要组成部分。在早期用于 RLHF 或训练推理模型的 RL 库里，往往没有显式的环境，而是给 LLM 的每个输出打分——要么用奖励模型，要么用一个自定义奖励函数形式的显式奖励。后来出现了更明确的 API，通常类似 OpenAI 的 gym 接口，带 init、step 和 reset 函数。这样就能在轨迹生成期间使用工具，也支持 LLM 与环境之间的多步交互。很多情况下，环境的实际执行发生在一个单独的容器/进程里或远程服务器上，以便把环境隔离开来。

### 训练器

训练器是核心优化循环所在，它拿生成阶段收集到的轨迹数据，产出新的策略。多数库都已标准化到同时支持 PPO 和 GRPO 两种训练算法。至于把模型切分到不同 GPU 上的分片后端，有好几种选择，最流行的是 Hugging Face trainer、FSDP、DeepSpeed 和 Megatron。FSDP 是较简单的选项之一，与 PyTorch 集成紧密；DeepSpeed 的参数与优化器卸载更激进；Megatron 在更大规模上性能最好。有些库的训练代码源自 Hugging Face 的 TRL 库，还有很多库在底层使用 veRL 的训练代码，而 veRL 本身支持 FSDP 和 Megatron。

## 比较维度

我们希望比较尽量客观，因此只关注那些能从库的代码与文档中客观推断出来的比较点，并链到相应位置，方便用户形成自己的看法、做出自己的选择。

**采用度：** 尽管描述一个库采用度的指标都不完美，我们还是把首次发布时间、star 数、issue 总数和贡献者数作为每个库采用度的一个代理指标一并列出。如果有库既能满足你的用例（例如 RLHF、训练推理模型、训练 agent），又具备你需要的特性，那么采用度更高的库通常更可取：它在更多场景下被验证过，因此总体上更健壮，也更容找到帮助。

**系统属性：** 除了列出库的目标用例，我们还列出每个库可以具备的属性：

- **效率**：支持推理/训练共置（colocation）或异步训练
- **可扩展性**：支持在集群上用大量 GPU 做推理和训练
- **模块化**：为库的各个组件提供清晰的接口，可以通过实现这些接口来改变库的行为
- **灵活性**：力图支持广泛的特性，或者很容易被改造成适配不同的设定——这一条在多数情况下难免主观，因为有的用户喜欢大量配置项，有的用户更喜欢能自己动手改的简单实现

**组件：** 我们把「RL 库的用例与组件」一节里描述的训练器、生成器和环境组件逐个链接出来。这些组件未必严格对应训练器、生成器、环境的划分——例如有些库把生成器和环境合并成一个统一的多轮环境。我们还给出关于训练后端、推理引擎与环境层的如下信息：

**训练后端**：我们列出该库支持哪些训练后端（Hugging Face trainer、FSDP、DeepSpeed 或 Megatron），以及各个框架开箱支持哪些算法。

**推理引擎：** 最流行的推理引擎是 vLLM、SGLang、Hugging Face transformers，或者通过 OpenAI API 使用外部推理引擎。可能的部署方式包括把推理引擎与训练引擎共置，或者分开部署。有些 RL 框架支持不由框架管理的外部推理引擎。训练与推理共置有助于减少 GPU 用量，但灵活性更差。在以下场景里，把训练和推理分开往往更可取：存在落尾者（stragglers）的长程任务、异步推理负载、训练与推理该用不同的 GPU 类型、或者训练和推理需要独立扩缩。另一个设计决策是是否支持多个推理引擎，以及多推理引擎之间的负载均衡是放在客户端还是服务端做。

**异步支持：** 库能否通过异步运行训练与生成这两个活动，让两者重叠。这样做能提升资源利用率，对特别长、有落尾者的 rollout 尤其明显，但会让学习动态更复杂、也可能更不稳定。把训练引擎更新过的权重同步到推理引擎有不同的做法：有些方法需要在训练引擎的一个或多个 rank 与全部推理引擎之间组成一个 torch distributed process group，再通过 NCCL、gloo 或 CUDA IPC 执行权重同步——这样同步权重很快，但不灵活；有些方法则靠把模型权重 checkpoint 到存储、再由生成器加载来完成同步，更灵活但更慢。

**环境层**：各库对环境的支持差别很大。有些库只支持单轮交互，没有显式的环境抽象。有些库有环境抽象，但要添加自定义环境就得改动或 fork 库本身。有些库支持在库之外实现自定义环境。总的来说，环境与生成过程耦合得越松、把现有环境（例如以外部远程服务的形式）集成进来越容易，就越好。为了让比较尽量客观，并承认不同用户有不同的需求和偏好，我们为每个库链出示例环境或「如何集成新环境」的文档，让读者自己判断。

**编排器：** RL 涉及互相交互的多个组件（环境、推理引擎、训练引擎），它们可能需要以复杂的方式被编排，例如生成与训练共置在同一批资源上、或以异步方式进行。此外每个组件都由许多不同的进程或容器组成，还得大规模地跑起来。因此，有一个负责调度、通信、容错和自动扩缩的编排器会很受益。凭借其灵活性、可扩展性和对异构计算的支持，许多 RL 库都选用 Ray 来做编排。

## 各库逐条说明

这一节我们更详细地讨论上面几个库，尽量让你了解它们是在什么背景下被构建出来的、分别最适合什么用途。其中一些评价难免比上面的表格更主观，而且许多库都演进得很快，所以请把这些话都当作参考，保留一分怀疑。

**TRL：** 为简单性和与 Hugging Face 生态的集成而优化，例如 datasets、transformers、accelerate 和 PEFT。它是为基于文本的后训练 LLM 构建的（例如用于推理、RLHF），除了 GRPO 和 PPO 之外还支持监督微调和 DPO。如果你更关心没有环境交互的纯文本 RL 设定，它是个好选择。但 TRL 原生并不支持带任意环境和更灵活生成方案的多轮 RL，正是这一点催生了其他库的开发，比如 verifiers——它与 TRL 的设计取向相似，同时支持多轮 RL 和环境。总体而言，TRL 定义的内部接口比其他一些库更少，这让它更简单，也更难适配。

**Verl：** Verl 为性能与可扩展性而生，支持 FSDP、DeepSpeed 和 Megatron 这些成熟的训练框架。和 TRL 类似，它最初也是一个训练推理模型、在没有环境的条件下做单轮交互的库，但正在被扩展出工具调用与多轮 RL，更灵活的环境/agent 支持也[正在出现](https://github.com/volcengine/verl/issues/1172)。出于性能考虑，它的生成与训练耦合得比较紧。Verl 社区庞大、开发非常活跃，是最成熟的开源 LLM RL 库之一。已经有若干项目构建在 Verl 之上并以各种方式扩展它：[[1]](https://github.com/TIGER-AI-Lab/verl-tool) [[2]](https://github.com/agentica-project/verl-pipeline) [[3]](https://github.com/RAGEN-AI/RAGEN)（完整列表见[这里](https://github.com/volcengine/verl?tab=readme-ov-file#awesome-work-using-verl)）。

**OpenRLHF：** OpenRLHF 为 RLHF 而生，对奖励模型和不同优化算法的支持都非常好。它同样支持异步训练，以及生成与训练共置。它对[环境 / agentic RL](https://openrlhf.readthedocs.io/en/latest/async_rl.html#asynchronous-agent-rl)有一定支持，但没有专门的接口。OpenRLHF 已经成熟、社区规模可观，也有构建在其上的库把它进一步扩展到[推理](https://github.com/Open-Reasoner-Zero/Open-Reasoner-Zero)以及[多 agent 训练](https://github.com/TsinghuaC3I/MARTI)领域。

**RAGEN：** RAGEN 是构建在 Verl 之上的库，集成了更明确的环境接口，并在 agent 与多轮 RL 支持上扩展了 verl，也让定义自定义环境变得更容易。

**AReal：** 这个库尤其专注于性能，针对生成与训练的异步执行做了优化。为了拿到最高性能，它实现了可中断的 rollout，并对 PPO 做了算法上的改动，以对抗异步执行期间的数据陈旧问题。

**Verifiers：** 补上了 TRL 的一些短板，增加了对环境和多轮工具使用的支持。和 TRL 一样，verifiers 也基于 Hugging Face transformers Trainer。框架简单，在研究者中很受欢迎。

**ROLL：** ROLL 面向多样的用户群体（大型 AI 实验室、从业者和研究者），办法是提供一大批[接口](https://github.com/alibaba/ROLL/blob/b756338442d9d36c1fe4c951bc98ebc913bd95ae/assets/ROLL_map_high.png)并让整个库可配置。

**NeMo-RL：** NeMo-RL 是较新的库之一，为各个组件定义了清晰的接口，对轨迹及其他相关数据也有清晰的数据表示。它构建时就把多轮 RL 与环境支持放在心上。和 verl 类似，它同样为性能与可扩展性而生，但还没有那么成熟，生态也更小。

**SkyRL：** SkyRL 吸收了上面许多库的经验，提供简单而灵活的接口，力图支持广泛的设定，构建时以多轮 agentic 场景为出发点。例如它支持：同步或异步的一次性流水线、共置或分离的生成与训练、外部或集成的推理引擎，以及不同的权重同步方法。SkyRL 前不久才发布，还不算成熟、生态也更小，但为 agentic 场景提供了[若干示例脚本](https://github.com/NovaSky-AI/SkyRL/tree/main/skyrl-train/examples)。

**slime：** slime 也是较新的库之一，做了一些很强势的取舍，力求一切尽可能简单同时保持高性能（例如它统一采用 sglang 和 megatron，因为二者对大型 MoE 模型性能更好）。它还内置一个 data buffer，把 prompt 与 rollout 数据的处理集中到一个中心位置。slime 支持共置，但构建时首先考虑的是解耦的训练与生成、以及异步 RL。由于聚焦 megatron，它在训练上比某些框架稍微不灵活一些，但在支持自定义 rollout 数据生成方面非常灵活。

## 结论

一个你自然会问自己的问题是：「我该用哪个库？」。答案取决于你所处的设定和你的用例，最终要你自己拿主意（希望本文的这些比较维度能帮到你）。我们可以给一些通用指引：

如果你在优化大模型训练，或者有严格的性能要求，那么看 Verl 大概是个不错的选择。它是成熟的库之一，但对性能与可扩展性的专注也带来了一些灵活性的损失。如果你想要更灵活的环境与 agent 支持，那么（在你喜欢 Verl 的前提下）也值得看看 RAGEN，或者其他一些框架，如 SkyRL、NeMo-RL、ROLL 或 AReal。

如果你是研究者，最看重简单与灵活（比如想尝试不常见的新算法或新思路，并且会花大量时间改源码），那 verifiers 值得一看。

最后，如果你在开发自己的库，或者对这个方向感兴趣，可以考虑[向 Ray Summit 2025 提交一个演讲](https://www.anyscale.com/blog/ray-summit-2025-call-for-proposals-cfp)——我们会为后训练和强化学习设置专门的分论坛。
