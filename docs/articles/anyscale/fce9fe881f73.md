# 优化 LLM 服务效率：用 Ray Serve LLM 从 KV Cache 复用走向 Token 负载感知

作者：Jeffrey Wang、Seiji Eicher、Kourosh Hakhamaneshi 和 Rudy Pei（NVIDIA）| 2026 年 8 月 25 日

在大规模 LLM 服务中，编排层对整体系统效率至关重要。编排层把异构请求流分发到一群 LLM 引擎副本上的有效程度，直接决定服务的 TTFT、TPOT 与吞吐量。运营一个 vLLM 副本集群时，你的路由器最重要的决策其实很简单：**下一个请求给谁？** 本文将剖析"只优化 KV cache 复用"这一误区，介绍 token 负载感知路由（token-load-aware routing），并解释它为何对高效 LLM 服务至关重要。

## LLM 请求路由的挑战

由于推理的自回归特性与 LLM 请求的高度可变性，LLM 服务与传统微服务路由有本质差异。传统微服务通常独立处理请求，把相关请求路由到同一副本几乎没有收益。LLM 服务则引入了状态性、高异构性与不可预测的执行成本。

- **有状态执行：** 引擎可以复用此前请求计算出的 KV cache。把请求路由到已持有其前缀的副本，能显著减少 prefill 计算与 TTFT。
- **高异构性：** 请求的输入与输出序列长度差异巨大，导致 GPU 资源使用与执行时间差异悬殊。
- **非确定性生成：** 即使输入相同，生成的输出 token 数也可能不同，令请求总成本难以预先预测。

这些特性共同给编排层出了独特难题：如何在利用 KV cache 复用的同时，平衡各引擎副本间的异构负载。

## 朴素优化：最大化 KV Cache 复用

最大化 KV cache 复用是降低 TTFT、优化服务效率最朴素的做法。常见的最大化复用方式有三种：会话亲和（session affinity）、前缀亲和（prefix affinity）与 KV cache 亲和（KV cache affinity）。

### 会话亲和

Ray Serve LLM 通过一致性哈希（consistent hashing）支持会话亲和，要求客户端把同一会话的请求关联到一个 session ID。对多轮负载，这会把后续轮次路由到同一副本，让它们复用早前轮次算好的 KV cache。

一致性哈希做会话亲和还有一个附带好处：**会话级负载均衡**——虚拟节点足够多时，它能把会话均匀分散到各副本。

*图 1：带虚拟节点的一致性哈希提供会话级负载均衡。*

```
session_affinity_config = LLMConfig(
    model_loading_config=...,
    deployment_config=(
        "request_router_config": RequestRouterConfig(
            request_router_class=(
                "ray.serve.experimental.",
                "consistent_hash_router.ConsistentHashRouter"
            )
        ),
    engine_kwargs={...},
)
```

### 前缀亲和

Ray Serve LLM 的前缀亲和路由器根据进来的请求构建一棵前缀树，记录哪些前缀被发往了哪个副本。后续请求沿树寻找前缀重叠最大的副本。

- **近似：** 前缀树跟踪的是请求字符串，而不是真实的 KV cache。KV 缓存按 token 级别工作，路由器的视图可能与引擎实际缓存状态不一致。
- **不感知逐出（eviction）：** 路由器假定见过的前缀仍在缓存中。高并发或长时间运行后，逐出会让这一视图过期。[KV cache 卸载](https://docs.ray.io/en/master/serve/llm/user-guides/kv-cache-offloading.html)能减少缓存未命中，但路由器仍同等看待所有缓存层级，忽略把卸载块重新加载回 GPU 显存的代价。

```
prefix_affinity_config = LLMConfig(
    model_loading_config=...,
    deployment_config=(
        "request_router_config": RequestRouterConfig(
            request_router_class=(
                "ray.serve.llm.",
                "request_router.PrefixCacheAffinityRouter",
        ),
    engine_kwargs={...},
)
```

### KV Cache 亲和

Ray Serve LLM 的 [KV aware 路由器](https://docs.ray.io/en/master/serve/llm/user-guides/kv-aware-routing.html)从引擎摄取 KV cache 事件，构建 KV cache 块的全局基数树（radix tree）。vLLM 在缓存块创建与移除时发出事件，让路由器对所有副本的 KV cache 状态保持最新视图，并能按 KV cache 块级别计算每个请求的重叠度。

我们与 [NVIDIA Dynamo](https://developer.nvidia.com/dynamo) 团队协作，通过模块化接口向外部库开放 Dynamo 的 KV indexer。事件面、请求面与数据面保持 Ray 原生，由 Dynamo 的 KV indexer 计算 KV cache 重叠并参与请求打分。打分结果随后由 Ray Serve 的请求面用来选择目标副本。

*图 2：KV 事件传输与全局 KV 基数树构建。vLLM 引擎在 KV cache 块创建或移除时发出 KV 事件。Ray Serve LLM 将这些事件转发给 KVAwareRouter，由 NVIDIA Dynamo 的 KV indexer 构建全局 KV 基数树并基于 KV cache 重叠为请求打分。*

```
kv_affinity_config = LLMConfig(
    model_loading_config=...,
    deployment_config=(
        "request_router_config": RequestRouterConfig(
            request_router_class=(
                "ray.serve.llm.",
                "request_router.KVAwareRouter",
        ),
    engine_kwargs={...},
)
```

除了 KV cache 重叠，Ray Serve LLM 的 KV cache 亲和路由器在做路由决策时还会计入 token 负载——这正是下文要展开的内容。

## 为什么只最大化 KV Cache 复用不够？

优化 KV cache 复用并不必然最大化服务性能。考虑一个存在掉队者（straggler）的异步多轮 RL rollout 负载，请求的输入输出序列长度差异很大：

- 每一步跑 8 个 rollout，每个 rollout 有 10 轮。
- 每个 rollout 以 2K token 的输入开始，每轮生成 1K token，只有两个掉队者的最后一轮生成 8K token。

*图 3：异步 RL 多轮 rollout 可视化。*

对异步 RL rollout，目标通常是最小化 step 时间，或在固定并发下最大化吞吐。我们用 p99 端到端 rollout 延迟作为 step 时间的代理指标。如图 4，我们在 concurrency=16 下比较三种路由器变体：

- `PureKVCacheAffinityRouter`：修改自 `KVAwareRouter`，**只**优化 KV cache 重叠。
- `ConsistentHashRouter`：同样为多轮对话最大化 KV cache 复用，并提供会话级负载均衡。我们给每个多轮 rollout 分配一个 session ID。
- `KVAwareRouter`：同时考虑 KV cache 重叠与 token 负载。

*图 4：异步多轮 RL rollout 下的路由器对比。KVAwareRouter 用一些 KV cache 命中率换取更均衡的 token 负载，得到更低的 p99 端到端 rollout 延迟。*

`KVAwareRouter` 尽管前缀缓存命中率更低，p99 rollout 端到端延迟却最好。深入看 KV cache 命中率与 token 负载*（估计副本上正在解码请求的活跃 KV cache 占用）*，`KVAwareRouter` 是在用 KV cache 命中率换取更均衡的 token 负载。

### 请求聚集（Request Herding）

由 `PureKVCacheAffinityRouter` 代表的纯 KV cache 亲和会导致请求聚集。一旦某副本缓存了共享前缀（比如 system prompt），后续请求看到缓存重叠就会优先路由到该副本。来自大量不同对话的请求撞在同一个副本上，造成 token 负载失衡。

### 负载均衡

一致性哈希在虚拟节点足够多时能平衡各副本的会话数量，但它把所有会话一视同仁。LLM 服务里并非如此：一个会话可能全是短请求，另一个可能变成跑很长的掉队者。多个掉队者可能落在同一个副本上，即使请求分布均匀也照样负载失衡。

会话亲和在保留 KV cache 局部性上表现出色，但**请求级别的均衡不保证真实的负载均衡**。

## 超越 KV Cache 复用：Token 负载感知更重要

来看引擎对每个请求实际做的功。请求经历两个阶段：

- **Prefill：** 引擎先复用任何重叠的 KV cache，再为剩余未缓存的输入 token 计算 KV cache。
- **Decode：** prefill 完成后，请求开始生成输出 token。每个解码步，引擎都要访问迄今所有 token 的 KV cache 并再做一次前向。

这揭示了把 KV cache 重叠当作路由目标的局限。KV cache 重叠告诉我们能**省下**多少 prefill 工作，却没告诉我们还**剩**多少工作要做。剩余负载来自两处：

- **Prefill 负载：** 活跃的 prefill token 加上尚未缓存的新进 token。
- **Decode 负载：** 活跃请求持续的解码工作。

**Token 负载**把两者合成一个指标，刻画每个副本上计算受限的 prefill 负载与访存受限的 decode 负载。

KV cache 亲和依然重要，但角色变了：**它是负载估计的代理，而不是路由目标本身。** KV cache 重叠告诉我们新进 prefill 可跳过多少，我们借此估计剩余 prefill 负载，再叠加正在进行的 decode 负载，得到总体 token 负载。

`KVAwareRouter` 就是 Ray Serve LLM 中带 token 负载感知的路由策略。相比一致性哈希的会话亲和，它还有一些额外好处：

- **自动 KV cache 复用：** 一致性哈希的会话亲和要求客户端提供 session ID，应用必须显式定义哪些请求属于同一会话。`KVAwareRouter` 则自动发现并复用可用的 KV cache，无需 session ID。
- **灵活性：** 你可以按负载调整打分函数的[系数](https://docs.ray.io/en/master/serve/llm/user-guides/kv-aware-routing.html#tune-the-scoring-weights)。

Ray Serve LLM 在整个生命周期跟踪每个请求：何时被准入、何时生成第一个 token、解码推进情况、何时完成。每个阶段路由器都相应更新其 token 负载，维持所有引擎副本负载的最新视图。Ray Serve LLM 提供端到端的请求面与控制面，并集成 Dynamo 的选择服务模块用于请求打分。

*图 5：Token 负载登记。每个请求在准入、prefill 完成、解码、请求完成的推进过程中，向 KVAwareRouter 登记并更新其 token 负载。路由器维持每个引擎 token 负载的最新视图，用于为后续请求打分与路由。*

可扩展性方面，Ray Serve LLM 会复制路由器实例，并在各路由器副本间维持最终一致的 token 负载视图。`KVAwareRouter` 本地做出路由决策，再异步与同侪路由器共享负载更新。这让路由与 token 流式输出远离同步路径，同时让所有路由器收敛到同一负载视图。

不过，对于以下负载，一致性哈希的会话亲和仍是强有力的选择：

- **缓存未命中代价特别高：** 对很长的多轮对话，把所有轮次留在同一副本可保证 KV cache 局部性。`KVAwareRouter` 视打分系数而定，可能用一些缓存重叠换更好的 token 负载平衡，因而需要调参。
- **跨会话 KV cache 复用有限：** 如果对话在共同的 system prompt 之后就分道扬镳，`KVAwareRouter` 跨会话可发现的额外缓存复用很少。
- **会话负载相似：** 当会话在输入/输出长度或执行时间上差异不大时，一致性哈希在会话级已经提供了合理的负载均衡。

## 案例研究：重放 Claude Code Trace

编码 agent 是当今最流行的 LLM 推理负载之一，我们就从真实的 Claude Code trace 中找灵感。我们在 [Weka Claude Code trace 语料库](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-062126-256k)的一个过滤子集上评估不同路由策略，子集能放进 `gpt-oss-120b` 的上下文窗口。

*图 6：Claude Code trace 样例。*

先看负载形状。两点很突出：会话高度异构，且每个会话内部有可观的 KV cache 复用机会。单个请求的输入输出长度就已差异悬殊，到会话层面差距更大：有的会话只有一轮，有的跨几十轮、累积数百万输入 token。

*图 7：Weka Claude Code 重放请求与重构会话的分布：单条上下文很长、输出变化极大、会话时长与轮数呈重尾分布。*

这就构成了一个有趣的路由权衡：是为了最大化 KV cache 复用把一个会话锁在同一副本，还是把 token 负载更均匀地摊开？

Ray Serve LLM 的 `KVAwareRouter` 在打分时同时考虑 KV cache 重叠与 token 负载。如结果所示，它比一致性哈希的会话亲和取得了更好的 TTFT、TPOT 与吞吐。

*图 8：Token 负载感知改善了异构 agentic 多轮负载的性能。KVAwareRouter 用一些前缀缓存命中率换取更好的 token 负载平衡，TTFT、TPOT 与吞吐随之改善。附带一提，随并发上升前缀缓存命中率下降，凸显了 KV cache 逐出的影响。*

要理解原因，看看活跃 decode 块数量的变异系数（CV）与前缀缓存命中率*。一致性哈希的会话亲和把同一会话的请求留在同一副本，很好地保留了 KV cache 复用；但它只在会话级均衡。当一个会话可能比另一个大得多、长得多时，均匀分散会话并不等于均匀分散 token 负载。

`KVAwareRouter` 则随并发上升，用一些前缀缓存命中率换取更好的 token 负载平衡。结果表明，对异构 LLM 负载，**在 KV cache 复用与 token 负载之间取得平衡**，比单纯最大化 KV cache 复用带来更好的整体服务性能。

**注：** 前缀缓存命中率是在同时具备两个 usage 字段的请求上，vLLM 上报的已缓存 prompt token 数占 prompt 总 token 数的按 token 加权比例。平均活跃 decode-block CV 是对每副本解码 KV 块失衡的离线重建：按 0.5 秒分箱，每个请求从第一个 token 到完成贡献估计的活跃 KV 块占用；CV 越低负载越均衡。

## 未来工作

回看本文开头列出的路由挑战，KVAwareRouter 处理了有状态执行与负载异构性，而非确定性生成仍是开放问题。由于准入时输出长度未知，起初预计很轻的请求可能进入漫长的解码阶段并撞在同一个副本上，造成意外的 token 负载失衡。如何准确计入这种不确定性，仍是全行业的开放挑战。一个方向是由 agentic harness 提供预期生成行为的提示。

近期，我们计划把 `KVAwareRouter` 支持扩展到 prefill-decode 分离部署、数据并行部署与多模态负载。路由仍是演进中的问题：选择在哪一层、什么粒度上路由，需要深入理解负载与部署架构。敬请关注后续更新！

## 结论

最优路由策略取决于负载，Ray Serve LLM 提供可插拔的可配置路由策略。一致性哈希的会话亲和在多轮对话中提供强 KV cache 复用，同时在副本间均衡会话。`KVAwareRouter` 更进一步，同时均衡 KV cache 重叠与 token 负载，实现更细粒度的负载均衡，为异构负载改善 TTFT、TPOT 与吞吐。

关键要点是：KV cache 重叠不应是唯一的路由目标。Token 负载同时刻画剩余的 prefill 工作与正在进行的 decode 负载，更能反映每个引擎上的真实工作。均衡这份工作、同时继续利用 KV cache 复用，才能导向更高效的 LLM 服务。
