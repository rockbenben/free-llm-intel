# Azure 上的 Anyscale 全面上市：使企业能够拥有完整的 AI 循环，而不仅仅是推理

由

卡塔琳娜·斯坦利

和

阿迪普·古普塔

|

2026 年 10 月 7 日

如今，[**Azure 上的 Anyscale**](http://anyscale.com/product/azure)** 已普遍可用**，因此企业可以运行自己的 AI 循环（涵盖数据处理、训练、训练后、评估和推理），并实现托管模型推理所期望的易用性。

通过代币租用智能是证明人工智能用例的最快方法。人工智能原生公司首先以这种方式构建，在前沿模型 API 上快速组装产品，相同的 API 使它们规模化。但一路走来，他们放弃了对三件事的控制：模型、数据和成本。该模型及其路线图属于其他人。使用例值得构建的数据必须离开公司环境才能到达模型。而且费用随着使用量的增加而直线上升，因此规模永远不会随着单位成本而降低。任何租房的人都会进行同样的交易。

人工智能本土公司首先遇到了这些限制。一旦用例证明了其价值，成本和数据暴露就成为问题。为了缓解这一问题，他们转向根据自己的数据定制的更小的、特定领域的模型，并在自己的 GPU 上运行，这使他们能够以更低的成本更快地做出响应。更大的优势来自于不断改进这些模型：拥有[学习循环](https://www.anyscale.com/blog/learning-loops)，将生产数据转化为训练和训练后运行，并将更新的模型转化为为其人工智能应用程序提供支持的推理部署。

该循环用一组需要共享 GPU 集群的 AI 工作负载（数据处理、训练和微调、训练后以及推理）取代了仅推理的管道。为了在多个 GPU 上运行多个工作负载，Ray 成为 AI 原生团队的通用运行时和编排层。企业希望走同样的道路，将他们已经信任的 Azure 治理扩展到循环的每一步。

Anyscale 将 Ray 从分布式计算引擎转变为企业级平台：团队构建和扩展循环的每一步，而 Anyscale 处理集群操作，所有这些都在他们已经在 Azure 上构建的安全和治理范围内。 Azure 客户从 Azure 门户部署它，在自己的订阅中的 Azure Kubernetes 服务 (AKS) 上运行生产 AI，并像任何其他 Azure 服务一样付费，支出计入现有的 Microsoft Azure 消费承诺 (MACC)。

借助 Azure 上的 Anyscale，您可以：

- **拥有你的 AI。** Anyscale 在开源 Ray 上运行，由 PyTorch 基金会管理。您的数据管道、训练代码和服务逻辑在开源上运行，跨[堆栈](https://www.anyscale.com/blog/ai-compute-open-source-stack-kubernetes-ray-pytorch-vllm)的每一层。
- **确保数据、评估和模型的安全。** 您的工作负载在您自己的 Azure 订阅中的 AKS 上运行，与您组织的 Microsoft Entra 租户关联。平台团队现有的 Azure RBAC 和 Azure Policy 控制保持不变。
- **增加每个 GPU 的输出以降低成本。** 共享 GPU 容量带来了规模效率，并且对您自己的数据进行后训练可以让团队转向更小的、特定领域的模型，从而降低服务成本。

## Link拥有你的人工智能

今年早些时候，Satya Nadella [提出了这个问题](https://x.com/satyanadella/status/2076323181154230284)：

> “我们必须将学习基础设施分发给每家公司，以便他们能够控制自己的学习循环……公司应该能够使用模型而不放弃使其独一无二的知识。”——萨蒂亚·纳德拉，微软董事长兼首席执行官

拥有你的人工智能意味着拥有改进它的循环。生产结果提供数据管理，管理数据提供培训，下一个模型版本将返回服务。 Azure 上的 Anyscale 在一个平台上运行整个循环。它使您能够管理多模式（文本、图像、视频、文档等）数据、比例模型微调和其他训练后技术（例如强化学习 (RL)）、支持训练后和微调，并通过更新和需求波动保持模型服务。对于其中每一个，Anyscale 都会协调计算以满足每个工作负载的需求。例如，要将 LLM 和其他模型部署为端点，[Anyscale 服务](https://docs.anyscale.com/services) 可以通过零停机升级进行部署，在空闲时扩展到零，并压缩副本以在实际流量下保持 GPU 利用率高。

该循环的每个阶段都在 Ray 上运行，可扩展 Python 代码。这意味着它可以与您的团队已经使用的开源 AI 框架（例如 PyTorch 和 vLLM）以及新推出的框架配合使用。您的管道和应用程序保持可移植性，因为它与开源 API 完全兼容。您的团队保持灵活性，因为他们可以采用新框架而不改变其扩展方式。

由于每个人工智能工作负载都由一个引擎运行，因此团队可以通过两种方式受益。他们可以简化对高级技术的使用，例如将推理和训练结合在一个循环中的[强化学习 (RL)](https://www.youtube.com/watch?v=QnxcDsMtaK8&pp=ygUYd3loeSBybCBpcyBoYXJkIGFueXNjYWxl)。在 Ray Summit 2026 上，Microsoft AI 分享了其前沿推理模型 MAI-Thinking-1 是使用 Ray 进行训练的（[在此处观看会议](https://www.youtube.com/watch?v=7fCwq7pIrkA)）。或者，他们可以从一个工作负载开始，然后毫无阻碍地扩展到下一个工作负载。 BMW 开始使用 Ray 进行[模型训练](https://www.youtube.com/watch?v=s3x3STd5vuU)，当需要[为 LLM 提供服务](https://youtu.be/yKt-CpfrOIE?si=JC1nlZTBK0GtB6_a&t=35) 时，它将 Ray 集成到他们的 AI 网关中，以便在整个企业中为开源模型运行推理。

## Link保证您的数据、评估和模型的安全

在构建 Ray 的工程师的支持下，Azure 上的 Anyscale 使 Ray 在您自己的 Azure 租户中做好生产准备、可扩展且可靠。这意味着您的数据、评估、模型和容器映像保留在您的订阅中。随着主权和差异化成为人工智能战略的核心，这将成为每个公司的要求，而不仅仅是那些有严格监管要求的公司。

网络模型是仅出口的。每个连接都源自 AKS 群集中的 Anyscale 操作员和 Ray 群集，出站到 Anyscale 控制平面，无需打开入站防火墙规则。预览公告中描绘了从订阅中的 AKS 数据平面到 Anyscale 托管的控制平面的完整部署架构。

Anyscale 资源是 Azure 原生资源，受 Azure RBAC 和 Azure 策略管理，并通过 Azure 进行 MACC 提款计费。

## Link降低成本

无论您运行一个还是五十个工作负载，每个令牌 API 都会收取相同的费率。在您自己的 GPU 上，利用率的每一次提高都会降低每个工作单元的成本。在整个典型企业中，传统 ML 基础设施的平均 GPU 利用率低于 30%。这种浪费始于单个工作负载，并在团队之间加剧，Anyscale 在各个层面都解决了这个问题。

通过优化单个工作负载和跨团队的调度和编排，Anyscale 可实现 80% 以上的平均 GPU 利用率。这意味着同一 GPU 组的工作量增加了 2-3 倍。

在工作负载级别，GPU 经常闲置等待数据：少数 CPU 无法足够快地加载和预处理下一批数据，无法让它们保持忙碌。 Anyscale 通过根据需要启动尽可能多的 CPU 工作线程来并行加载数据并将其直接流式传输到 GPU 来解决此问题，因此在 GPU 完成最后一批数据时，下一批数据就准备好了。作业还倾向于保留仅部分使用的整个 GPU，因此部分 GPU 可以让您将更多工作负载或模型打包到每个设备上。自动缩放会在作业耗尽内存之前调整资源，检查点会从最后完成的步骤重新启动失败的作业，而不是从头开始，因此现场驱逐或掉队的 GPU 不再在重新运行时消耗付费容量。

在整个团队中，浪费来自孤立的集群。每个团队都为其峰值保留足够的容量，仅在部分时间使用它，并在其他团队等待他们无法访问的计算时将其闲置。Anyscale 将这些集群池化到从单个窗格管理的共享计算中，在可用时立即提取、保留和按需容量。调度是优先级感知的，因此队列遵循业务优先级，当紧急工作到达时，优先级较低的工作会暂停而不是终止，然后从中断的地方继续。

三支队伍共享 H100 预订。当高优先级训练作业落地时，调度程序会抢占低优先级评估作业，并在训练作业完成后恢复它，从而使预留始终接近充分利用。

GPU 预留

在各个集群和区域中，该池表现得像一个整体。各地对 GPU 的需求都超过了供应，因此运行最大 AI 工作负载的团队将容量作为一个投资组合进行规划。 Anyscale 调度程序跨集群和​​ Azure 区域放置工作负载，并将 Azure 作为身份和策略的控制点。同样的模型扩展到客户在 Azure 之外附加的 GPU 容量，而 Azure 仍然是身份、治理和管理的所在地。

GPU 利用率是一个杠杆。另一个是模型本身。根据您自己的数据进行后训练和微调开放模型，团队可以用较小的、特定于任务的模型替换大型通用模型，这些模型的服务成本较低。但真正的成本还包括构建模型、运行数据处理，以及在单独的基础设施上进行后训练会增加运营开销，从而消除推理节省的成本。 Anyscale 在一个平台上运行每一步，因此较小的模型并不意味着需要为 AI 生命周期的不同步骤构建或维护新的堆栈。
