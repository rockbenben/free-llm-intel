# Anyscale on Azure 正式可用：让企业掌握完整的 AI 闭环，而不只是推理

作者：Katarina Stanley、Adhip Gupta | 2026 年 10 月 7 日

今天，[**Anyscale on Azure**](http://anyscale.com/product/azure)** 正式可用**，企业从此可以运转自己的 AI 闭环——涵盖数据处理、训练、后训练、评估和推理——同时得到他们从托管模型推理里期待的那份好用。

按 token 租用智能，是验证一个 AI 用例最快的路子。AI 原生公司最早就是这么建起来的：借助前沿模型的 API 快速拼装产品，后来也是同一批 API 把它们托上了规模。但一路上，它们交出了三样东西的掌控权：模型、自己的数据和成本。模型以及模型的路线图属于别人；让一个用例值得去做的那些数据，必须离开公司的环境才能送到模型那里；而账单随着用量笔直上涨，规模再大也换不来单位成本下降。任何租用的人，做的都是同一笔交换。

AI 原生公司最先撞上这些天花板。一个用例证明了价值之后，成本和数据外泄就成了问题。为了缓解这一点，它们转向更小的、面向特定领域的模型——用自己的数据做定制、跑在自己的 GPU 上，从而以更低的成本拿到更快的响应。更大的优势来自持续改进这些模型：把[学习闭环](https://www.anyscale.com/blog/learning-loops)握在自己手里——它把生产数据变成一轮轮训练和后训练，再把更新后的模型变成支撑其 AI 应用的推理部署。

这个闭环把只有推理的流水线，换成了一组需要共享 GPU 集群的 AI 负载——数据处理、训练与精调、后训练、推理。要在大量 GPU 上跑大量负载，Ray 成了 AI 原生团队共用的运行时和编排层。企业想要的是同一条路径，把自己本来就信任的 Azure 治理延伸到闭环的每一步。

Anyscale 把 Ray 从一个分布式计算引擎变成了企业就绪的平台：团队构建并扩展闭环的每一步，Anyscale 负责集群运维，而这一切都发生在他们已经在 Azure 上建好的安全与治理边界之内。Azure 客户从 Azure 门户部署它，在自己的 Azure 订阅内的 Azure Kubernetes Service（AKS）上运行生产级 AI，并按和其他 Azure 服务一样的方式付费，支出计入他们已有的 Microsoft Azure Consumption Commitment（MACC）。

借助 Anyscale on Azure，你可以：

- **掌握自己的 AI。** Anyscale 运行在开源的 Ray 之上，而 Ray 由 PyTorch Foundation 治理。你的数据管道、训练代码和服务逻辑全都跑在开源技术上，贯穿整个[技术栈](https://www.anyscale.com/blog/ai-compute-open-source-stack-kubernetes-ray-pytorch-vllm)的每一层。
- **让数据、评估和模型保持安全。** 你的负载跑在自己 Azure 订阅内的 AKS 上，关联到你组织的 Microsoft Entra tenant。平台团队现有的 Azure RBAC 和 Azure Policy 管控原样生效。
- **提高单卡产出以降低成本。** 共享的 GPU 容量带来规模效应，而基于自己数据的后训练，让团队可以转向更小、更专门的领域模型，服务起来也更便宜。

## 掌握自己的 AI

Satya Nadella 今年早些时候[阐述过这个主张](https://x.com/satyanadella/status/2076323181154230284)：

> 「把学习的基础设施交付给每一家公司，让他们能掌控自己的学习闭环，这件事势在必行……一家公司应当能够使用一个模型，而不必交出那些让自己之所以独特的知识。」– Satya Nadella，Microsoft 董事长兼 CEO

掌握自己的 AI，意味着掌握让它不断变好的那个闭环。生产结果喂给数据整理，整理好的数据喂给训练，下一个模型版本再回到服务里。Anyscale on Azure 在同一个平台上跑完整个闭环。它让你能整理自己的多模态数据（文本、图像、视频、文档等），把模型精调以及强化学习（RL）等其他后训练技术扩展到生产规模，支持后训练和精调，并在模型更新与需求波动中让模型持续对外服务。针对其中每一步，Anyscale 都会按各个负载的需求来编排算力。举例来说，要把 LLM 和其他模型部署成端点，[Anyscale Services](https://docs.anyscale.com/services) 的部署支持零停机升级、空闲时缩容到零，还会压缩副本，让 GPU 在真实流量下保持高利用率。

闭环的每一个阶段都跑在 Ray 上，而 Ray 能让 Python 代码扩展开来。这意味着它兼容你团队已经在用的开源 AI 框架，比如 PyTorch 和 vLLM，也兼容日后新出的框架。你的管道和应用保持可迁移，因为它与开源 API 完全兼容。你的团队保持灵活，因为他们可以采用新框架，而不必改变自己扩展规模的方式。

由于所有 AI 负载都由同一个引擎承载，团队能从两个方面受益。一是把高级技术用得更顺，比如[强化学习（RL）](https://www.youtube.com/watch?v=QnxcDsMtaK8&pp=ygUYd3loeSBybCBpcyBoYXJkIGFueXNjYWxl)这类把推理和训练合在同一个闭环里的技术。在 Ray Summit 2026 上，Microsoft AI 分享了自己的前沿推理模型 MAI-Thinking-1 就是用 Ray 训练的（[点这里观看这场演讲](https://www.youtube.com/watch?v=7fCwq7pIrkA)）。二是可以从一个负载起步，再毫无阻力地扩展到下一种负载。BMW 起初用 Ray 做[模型训练](https://www.youtube.com/watch?v=s3x3STd5vuU)，等到要[为 LLM 提供服务](https://youtu.be/yKt-CpfrOIE?si=JC1nlZTBK0GtB6_a&t=35)时，就把 Ray 集成进自己的 AI Gateway，在全企业范围运行开源模型的推理。

## 让数据、评估和模型保持安全

Anyscale on Azure 让 Ray 在你自己的 Azure tenant 里做到生产可用、可扩展且可靠，背后还有构建 Ray 的工程师提供支持。这意味着你的数据、评估、模型和容器镜像都留在你的订阅内。随着主权和差异化成为 AI 战略的核心，这会是每一家公司的要求，而不只是那些监管严格的公司。

网络模型是只出不进（egress-only）。每一条连接都由你 AKS 集群里的 Anyscale operator 和 Ray 集群发起，出站连到 Anyscale 控制面，不需要开放任何入站防火墙规则。完整的部署架构——从你订阅内的 AKS 数据面，到由 Anyscale 托管的控制面——在预览公告里有图示说明。

Anyscale 资源是 Azure 原生的，受 Azure RBAC 和 Azure Policy 治理，并通过 Azure 计费、计入 MACC 消耗。

## 降低成本

按 token 计费的 API，不管你跑一个负载还是五十个负载，费率都一样。而在自己的 GPU 上，利用率每提高一点，单位工作的成本就降一点。在一般企业里，传统 ML 基础设施的 GPU 平均利用率还不到 30%。这种浪费从单个负载内部开始，又在团队之间层层叠加，而 Anyscale 在每一个层面解决它。

通过对单个负载内部以及跨团队的调度与编排做优化，Anyscale 能把 GPU 平均利用率提升到 80% 以上。也就是说，同一批 GPU 能多干 2–3 倍的活。

在负载层面，GPU 常常闲着等数据：只有几颗 CPU，来不及把下一批数据加载并预处理完，让它们忙起来。Anyscale 的做法是按需拉起任意数量的 CPU worker 并行加载数据，直接流式送进 GPU，于是 GPU 处理完上一批的那一刻，下一批已经就绪。作业还往往整卡整卡地预留 GPU，实际却只用一部分，因此支持小数卡（fractional GPU）就能在每台设备上塞进更多负载或更多模型。自动扩缩会在作业把内存用尽之前先调整资源，checkpoint 则让失败的作业从最后完成的步骤重启而不是从头再来，于是一次 spot 实例回收或者一块拖后腿的 GPU，都不必再把已经付费的算力烧在重跑上。

在团队之间，浪费来自彼此孤立的集群。每个团队都按自己的峰值预留容量，只有一小部分时间用得上，而别的团队却在等待他们根本用不上的算力。Anyscale 把这些集群汇聚成共享算力，在同一个界面里统一管理，并按可用性取用 spot、预留和按需容量。调度是感知优先级的，队列跟随业务的优先级排序；紧急作业到来时，低优先级的工作是被暂停而不是被杀掉，之后从暂停的地方接着跑。

三个团队共用一份 H100 预留。高优先级的训练作业到来时，调度器抢占低优先级的评估作业，等训练作业跑完再把它恢复，让这份预留全程都接近满利用率。

GPU 预留

跨集群、跨 Region，这一池算力表现得像一个整体。GPU 的需求处处超过供给，所以跑着最大规模 AI 负载的团队会把容量当成一个投资组合来规划。Anyscale 调度器把负载放到各个集群和 Azure Region 上，而 Azure 是身份与策略的管控点。同样的模式也适用于客户在 Azure 之外接入的 GPU 容量，Azure 仍然是身份、治理和管理的落脚点。

GPU 利用率是一个抓手，另一个是模型本身。用自己的数据对开源模型做后训练和精调，团队就能用更小的、面向具体任务的模型替换掉大而通用的模型，服务成本也随之下降。但真实成本还得把「造模型」也算进去：如果数据处理和后训练跑在各自独立的基础设施上，由此增加的运维开销可能把推理省下的钱全部吃掉。Anyscale 在同一个平台上跑完每一步，所以换一个更小的模型，不意味着要为 AI 生命周期的不同环节再去搭建和维护一套新的技术栈。
