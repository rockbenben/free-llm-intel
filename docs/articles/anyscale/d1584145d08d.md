# SkyRL 中的 FP8 强化学习：保持训练与 Rollout 间的策略一致性

作者：Jinghan Yao、Eric Tang、Sumanth Hegde 和 Kourosh Hakhamaneshi | 2026 年 8 月 25 日

*SkyRL 现已支持 FP8 加速的训练与 rollout，并配备 on-policy 权重同步。在长程 RL 实验中，FP8 配置的收敛轨迹紧密跟随 BF16，同时把端到端 step 时间最多降低 23%。*

**TL;DR.** SkyRL 现在在强化学习栈的性能关键部分全面支持 FP8：训练期线性层的 GEMM、rollout 期的模型权重与 KV cache，以及 trainer 与 vLLM 之间的权重传输。关键的系统改动是一条同步通路——把 trainer 产出的 FP8 负载与 block scale 直接传给 rollout 引擎，避免可能改变 rollout 策略的"反量化-重新量化"边界。在长程 RL 运行中，FP8 配置在 8×H100 上的 Qwen3.5-9B 与 8×B200 上的 Qwen3.5-35B-A3B 上都紧密跟随 BF16 的收敛，并同时支持 blockwise 与 MXFP8 配方。在所评估的长 rollout 配置中，端到端 step 时间分别改善最多约 19% 与 23%；FP8 参数存储还额外使每 GPU 的 trainer 权重显存降低 39–42%。

**精度范围。** 本文中的"FP8"指 FP8 加速的线性层计算、FP8 主权重、FP8 rollout 权重与 KV cache，以及 FP8 感知的权重同步。精度敏感的张量（如 norm、embedding 等）、注意力和优化器状态仍保留 BF16 或 FP32。具体而言，我们在 Hopper 与 Blackwell 上分别使用 blockwise 配方和 MXFP8 配方。

**模型。** 所有实验均使用 Qwen3.5 系列（Qwen3.5-4B、Qwen3.5-9B、Qwen3.5-35B-A3B）。这些是混合注意力模型，其中部分层使用 gated-delta-network（GDN）线性注意力。

## 为什么 FP8 对强化学习重要

在许多 on-policy RL 负载（包括本文评估的配置）中，rollout 生成占端到端时间的很大比重。训练阶段随后对生成的 token 执行前向与反向传播。两个阶段都能从 FP8 获益，原因各不相同：训练中，低精度 GEMM 提升峰值算术吞吐；rollout 中，更小的表示降低访存量与 KV cache 容量需求。在 Hopper 与 Blackwell 的 Tensor Core 上，FP8 提供最高为 BF16 两倍的峰值矩阵乘吞吐，且每个 FP8 值只需一半存储。为进一步缩小显存占用并加快模型权重加载，还可以对 trainer 中的策略模型权重施加 FP8 量化，只保留 FP8 模型参数与 FP32 master weights，完全绕过 BF16 副本。这通常被称为 `*fp8_param*`。

近期工作得出了类似结论。[LMSYS 的 *Unified FP8*](https://www.lmsys.org/blog/2025-11-25-fp8-rl/) 表明，训练与服务使用一致的 FP8 方案，可以缩小混合精度 RL 中出现的 train–rollout log-prob 差距。NVIDIA NeMo RL 在其评估的 Hopper 配置中报告了 15–25% 的 step 时间缩减且精度紧密匹配。两者都建立在 DeepSeek-V3 使用的细粒度 block-scaling 方法之上，包括对权重采用 128×128 的 scale block，而非每个张量一个 scale。

在实验过程中我们发现，FP8 RL 的挑战并不只是在 trainer 和 rollout 引擎里各自独立开启 FP8。强化学习通过策略把两个系统耦合在一起：trainer 必须以受控的数值差异，优化那个真正生成采样轨迹的同一策略。

### 独立量化何时破坏策略一致性

一个直接的初始配置是：在 Megatron 中用 TE 的 per-tensor delayed-scaling 配方开启 Transformer Engine（TE）FP8，并设置 vLLM 的 `quantization="fp8"`。在一次 Qwen3.5-4B DAPO 运行中，该配置在 70 步内变得不稳定：reward 始终低于 BF16 基线，策略熵趋近于零，平均 importance-sampling 比率停在约 0.75 而不是 1.0，PPO clip 比率比 BF16 运行高出超过一个数量级。

*图 1：Qwen3.5-4B 上朴素 FP8 与 BF16 的 DAPO 对比。FP8 配置表现为 reward 停滞、熵下降、importance-sampling 比率远离 1，且 clip 比率大幅升高。*

根因：权重同步处的量化失配。故障源于两个引擎的接口，而非任何单独一条 FP8 计算路径：

- Megatron 与 TE 用量化后的 FP8 权重与 scale 元数据进行训练——blockwise 配方下每个 128×128 block 一个 scale，MXFP8 配方下每个 1x32 block 一个 scale。
- 权重同步时，原有的桥接层把权重反量化为 BF16，仅传输 BF16 数值，丢弃了 trainer 的 FP8 scale 元数据。
- vLLM 对收到的 BF16 值独立量化，由于量化配方不同，得到的 FP8 值与 Megatron 使用的 FP8 权重并不相同。

这一连串操作复合了两个 scale 各自独立选择的有损变换。结果 rollout 权重既不匹配 trainer 的量化表示，也不精确匹配更高精度的 checkpoint。这是 off-policy 的权重同步：rollout 引擎在采样一个 trainer 从未持有过的策略。

对 blockwise 配方，在 4B 模型全部量化权重上，trainer 与 rollout FP8 权重的平均相对误差为 0.038，约为任一表示相对 BF16 checkpoint 量化误差的 1.4 倍。每个引擎自身的量化误差单独看都可以接受；有问题的是两个引擎之间的分歧。trainer 在更新一个数值策略，rollout 引擎却在另一个策略上采样——这在 importance-sampling 与 clipping 诊断指标中得到了体现。

*图 2：Off-policy 权重同步（原路径）。桥接层导出不含 trainer block-scale 元数据的 BF16 值，随后 vLLM 推导出一个新的 FP8 表示。*

### On-policy FP8 权重同步

我们重新设计了 SkyRL 的权重同步，让 vLLM 直接消费 trainer 产出的 FP8 表示。我们称之为 **on-policy 权重同步（OPWS）**：rollout 引擎运行 trainer 正在更新的同一个数值策略，而不是它的一个重新量化近似。

*图 3：量化参数以 FP8 负载连同其 block scale 传输，精度敏感张量保持 BF16。vLLM 直接安装传入的表示，不再调用独立的量化器。*

有了这条通路，同步后 trainer 与 rollout 权重逐位相同：rollout 引擎收到 trainer 产出的完全一致的 FP8 值与 scale。剩余的 train–rollout log-prob 差异来自激活量化与 kernel 级数值差异。在 400 步的 Qwen3.5-9B 运行中，每 token 平均绝对 log-probability 差距保持在 0.02–0.03 且未随时间增大。这大约是两条 BF16 引擎路径之间差距的三倍——后者仅由 kernel 差异构成一个实际下限。

作为对照，BF16 trainer 搭配独立把权重量化为 FP8 的 rollout 引擎，初始差距就更大，并在第 400 步超过 0.05。这一趋势与每个同步点反复出现的量化失配相吻合。

*图 4：Qwen3.5-9B 上 rollout 引擎与 trainer 之间每 token 平均绝对 log-probability 差异。*

### 性能分析

FP8 并不会自动降低 RL step 时间。量化、scale 管理与 dispatch 会引入开销，而生成与训练对这些成本的响应不同。

**生成：更低的访存量转化为更低的延迟**

自回归解码主要是内存带宽受限的：每个解码 step 都要流式读取模型权重并访问活跃 KV cache，而算术运算相对较少。FP8 缩小了两者的表示体积，在匹配输出长度下降低了生成阶段耗时。

OPWS 还消除了 rollout 期的重新量化。权重与 scale 在下一次同步前保持不变，激活量化被融合进 GEMM kernel，解码经由捕获的 CUDA graph 重放。因此 FP8 与 BF16 rollout 配置的主机侧编排路径完全等价。

*图 8：Qwen3.5-9B 在匹配输出长度下的 step 拆解。标有 "KL on" 的行包含一次 reference 模型前向。*

**训练：GPU 收益被主机开销抵消**

训练在同一份权重上复用数千 token，使该阶段比解码更偏计算密集。GPU kernel 从 FP8 受益：GEMM 时间从 14.2 秒降至 10.9 秒，FP8 参数的 all-gather 使 NCCL 时间从 9.8 秒降至 6.4 秒。每个训练阶段测量到的 GPU kernel 总时间从 36.5 秒降至 32.0 秒。

开销在主机侧。与 rollout 权重不同，训练权重每个优化器 step 后都会变化。TE 必须推导 block scale，并同时维护行方向的 FP8 表示和反向传播使用的转置表示。在 64 个 microbatch 上重复这些工作，起初让 trainer 陷入主机 dispatch 受限的路径。增大 microbatch 并做 dispatch 优化后，归因的主机侧时间从 52.9 秒降至 16.9 秒。

*图 9：按类别的训练 kernel 时间，FP8 对比 BF16。FlashAttention 与 GDN 时间不变，因为所评估的 blockwise 配方只对线性层 GEMM 应用 FP8；两种配置中注意力都保持 BF16。*

端到端地看，训练阶段从 45.6 秒变为 44.0 秒，在当前 H100 实现下训练大致时间中性。因此端到端收益主要来自 rollout 生成。在 8×H100 与 Qwen3.5-9B 上，匹配输出长度下总 step 时间为 BF16 的 0.81–0.90 倍；长 rollout 时观察到的最大降幅约 19%。

*图 10：8×H100 上 Qwen3.5-9B 按输出长度划分的端到端 step 时间。rollout 越长，FP8 优势越大。*

在 8×B200 与 Qwen3.5-35B-A3B 上，观察到的最大端到端降幅约 23%，同样由生成驱动。因此 SkyRL 使用 `fp8_recipe="auto"`：在 Hopper 上选择 blockwise FP8，在支持的 Blackwell 上选择架构原生的 MXFP8。

*图 11：8×B200 上 Qwen3.5-35B-A3B 的端到端 step 时间。*

## 深入：FP32 与 2 的幂次 block scale 下的 FP8 量化

在 Hopper 上，TE 的 blockwise 配方可以使用全精度 FP32 scale，或使用被约束为 2 的幂的 FP32 值。Blackwell 上，tensor core 只支持 pow-2 scaling。后者只有指数部分有效的表示，粒度最多可能粗一倍。使用 `fp8_param` 时，优化器更新 FP32 master 副本，并在每一步后重新量化到 FP8 参数存储。由于 RL 更新可能很小，我们评估了更粗的 scale 网格是否会系统性地抑制这些更新。

在剖析的 DAPO 运行中，测量到的最大逐元素 master 权重更新为 `|ΔW| = 1.01 × 1e-6`，接近配置的学习率。平均每步相对更新 `|ΔW|/|W|` 为 `0.6–0.9 × 1e-4`。

**权重同步路径**

我们在 Qwen3.5-9B 权重上，对 trainer 侧 TE 2.11 `Float8BlockQuantizer` 更新路径做消融实验。经过长程 RL 优化器 step 后，FP8 参数存储的累积位移在两种 scale 格式下都与 FP32 master 权重的位移紧密吻合：

*图 12：左：长 RL 步中 FP8 权重累积位移，以 FP32 master 位移归一化，两种 scale 格式都接近 1。右：单次 master 权重更新与 FP8 存储对应变化之间的余弦相似度，随更新幅度分布。阴影区标出 9B 运行中实测的更新幅度。*

RL 量级的更新下单步余弦相似度低，本身并不说明优化器更新丢失了。在第 t 步，FP8 存储是从当前 master 权重重新计算的 `Q(W_t)`。它与 master 的偏差因此只是当前的量化误差，而不是此前每一步引入的独立舍入误差之和。长程位移测量表明，尽管每一步只兑现一部分有效权重更新，更新并未被系统性抵消。

**训练对比**

8×H100 上匹配的 200 步 DAPO 运行使用相同的种子与数据顺序，仅在 scale 表示上不同：

*图 13：使用 fp8_param 时，FP32 与 2 的幂 block scale 的 reward 与 pass@8。两条曲线全程保持接近。*

每 token 的 train–rollout log-probability 差距是唯一区分两种表示的量。pow-2 运行的差距更高，全程平均 0.034 对 0.026，这与其更粗的有效量化相符。两条轨迹平行演化且保持有界，该差异没有反映到 reward 或 pass@8 上：

*图 14：两种 scale 表示下 rollout 引擎与 trainer 之间每 token 平均绝对 log-probability 差异。pow-2 运行始终保持更高但同样稳定的差距。*

在该配置下，我们未观察到两种 scale 表示之间有实质性收敛差异。SkyRL 将 FP32 scale 作为 Hopper 默认。

另有一个平台层面的约束。在所测试的 TE 2.11 集成中，`fp8_param` 需要 Megatron 的分布式优化器通过 TE 的 `replace_raw_data` 把 FP8 参数存储重定向进打包缓冲区。该路径针对 Hopper 使用的 blockwise FP8 张量已实现，但 Blackwell 原生配方使用的 `MXFP8Tensor` 尚未支持。在该集成可用之前，原生 Blackwell 路径的主训练权重仍保持 BF16，尽管 FP8 依然能加速受支持的 GEMM。

**显存节省**

在 Hopper 上，通过 `fp8_param` 把可量化的主权重以单字节 E4M3 存储，使 Qwen3.5-9B 的策略参数存储从每 GPU 8.3 GiB 降到 5.1 GiB，减少 39%。对 MoE 模型效果更好，因为路由专家持有大部分参数且全部可量化：8 路专家并行的 Qwen3.5-35B-A3B 用同一配方把每 GPU 参数存储从 12.1 GiB 降到 7.0 GiB，减少 42%。两个模型都约有 1.9 GiB 仍以 BF16 保留，对应上文所述精度敏感张量集合。省出的 HBM 可用于更长上下文、更大 microbatch 或更宽 rollout batch。

由于 `fp8_param` 目前要求 Hopper blockwise 路径，以上数字描述的是 Hopper 部署；本文中的 B200 运行以 BF16 主权重训练。

*图 15：Hopper 上使用与不使用 fp8_param 的每 GPU 策略参数存储。BF16 剩余部分即精度敏感张量集合。*

## 当前范围与局限

- 性能取决于模型架构、输出长度、batch 形状、kernel 与硬件。本研究中最大的收益出现在 rollout 生成主导 step 时间时。
- FP8 并不覆盖所有操作与状态。注意力、部分选定参数、优化器状态与 master weights 在需要处使用更高精度。

## 实践要点

- 把权重同步视为数值正确性的一部分。训练与 rollout 的 kernel 各自都可以很稳定，但在二者界面上的独立量化会改变生成数据的策略。
- 按阶段归因性能。在所测配置中，FP8 的端到端收益主要来自带宽敏感的解码；主机侧工作目前限制了训练阶段的加速。
- 让量化表示跨引擎保持一致。数值、scale、张量排除名单与布局转换必须由同一份配置协调，而不是由 trainer 和 rollout 引擎各自独立推断。

## 复现说明

核心配置：

```
# Trainer: FP8 linear-layer GEMMs with an architecture-aware recipe
# Apply the corresponding keys to trainer.ref when a reference model is used.
trainer.policy.megatron_config.transformer_config_kwargs.fp8=e4m3
trainer.policy.megatron_config.transformer_config_kwargs.fp8_recipe=auto  
# Rollout: consume trainer-produced FP8 blocks and scales
generator.inference_engine.fp8_weight_sync_mode=auto
generator.inference_engine.engine_init_kwargs.kv_cache_dtype=fp8_e4m3
```
