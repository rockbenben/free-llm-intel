# Lila Sciences 与 Anyscale 如何把 GLM-5.3-Flash 训练扩展到 100 万 token

作者：[SkyRL Team](https://www.anyscale.com/blog?author=skyrl-team) 与 [Lila Sciences 的 AI Research Team](https://www.anyscale.com/blog?author=lila-sciences-ai-research-team) | 2026 年 11 月 5 日

[Lila Sciences](https://www.lila.ai/) 和 Anyscale 用 64 块 B200 GPU 训练了开源模型 GLM-5.3-Flash，每条序列 100 万 token。这是我们起步时那套训练栈所能处理长度的 64 倍，而每一项改动都已在 [SkyRL](https://blog.skyrl.ai/blog/1m-context-glm-5-3-flash) 中开源。Anyscale 这边负责 SkyRL 的团队与 Lila Sciences 的研究人员在其基础设施上、基于一套开源技术栈紧密合作，共同探索针对这一特定模型扩展 context 长度的研究路径。

科学数据天生就很长。一个基因组、一族同源的蛋白或 RNA 序列、或者一场持续数天的实验记录，一旦被切成几千 token，真正要紧的结构就丢失了。让 AI 与自主实验室闭环协作来做科学，也有同样的需求：假设、实验方案与仪器读数一轮轮累积下来，它的 context 会长到几十万 token。

如今许多开源模型都支持 1M token 的 context，但在很大的 context 取值下，它们对目标任务未必有开箱即用的表现。要补上这段差距，就得在该任务自己的数据上、按完整长度训练，既不截断也不做重度压缩。这项工作要做的正是这件事，用的是开源模型和开源训练栈。

成果速览：

- **每条序列 100 万 token** 能装进每块 GPU 的 144.5 GiB，低于 B200 的 178 GiB。
- 在 64 块 B200 上，1M 时达到 **13.7k tokens/s**，256k 时峰值 **24.9k tokens/s**。
- **模型确实用上了 context：** 在人类基因组上 fine-tuning 后，loss 的改善在那些前面已有几十万 token 上下文的 token 上最为明显。
- **开源：** 训练配方在 [SkyRL](https://github.com/NovaSky-AI/SkyRL/issues/2487) 里，另有若干项修复正在往 Megatron-LM 上游合并。

### Link如何让 GLM 5.3 Flash 达到 100 万 token 的 context？

GLM-5.3-Flash 是一个混合模型：45 层里有 34 层使用 linear attention（Kimi Delta Attention），11 层使用 DeepSeek Sparse Attention（DSA）。它还用了一条比通常宽 4 倍的 residual stream，以及 mixture-of-experts（MoE）层。这几样各自都需要单独处理。显存随序列长度在每一层里增长，而在 attention 里随长度的平方增长，所以每一项优化只是把上限推到下一个瓶颈为止。我们做了若干项优化，它们连同各自的实验和 PR，在[原始文章](https://blog.skyrl.ai/blog/1m-context-glm-5-3-flash)里都有详细记录。

每一项优化都在承重

我们遇到的大部分问题并不只针对 GLM，凡是使用同类组件的模型都能套用：

- **确认每一层跑的确实是你以为的那个 kernel：** GLM 的 sparse attention 层一直在无声地回退到 dense attention，因为那些 fused kernel 只接受 DeepSeek 精确的 tensor 形状。没有任何报错，这次运行只是在 16k 时就用掉每块 GPU 114 GiB，到 32k 直接显存耗尽。把 tensor 补齐到 sparse kernel 需要的形状，显存减半。
- **Sparse attention 是把平方级开销挪走，并没有消掉它。** DSA 每个 query 只 attend 2,048 个 token，但选出这些 token 意味着要把每个 query 跟整个序列打一遍分。把这个打分矩阵每次只算几百个 query，就能把它压在 2 GiB 以内；再把打分切分到各块 GPU 上、而不是每块都重复算一遍，256k 下的完整训练 step 快了 2.1 倍。
- **每一项省显存的手段都要用吞吐来换，所以长度需要多少就开多少。** 全量 recompute、CPU offloading 和 context parallelism，各自都是拿一部分速度换来更多 context。以 offloading 为例，它把 256k 下的峰值显存从 142 GiB 降到 98 GiB，但 step 时间多出 21%。我们只在那些不开就装不下的长度上才启用它。
- **用随机 token 做的 benchmark 会低估 MoE 模型的显存。** 真实文本的分布在各 expert 之间并不均匀：在一份真实的长 context 数据集上，最忙的 GPU 收到的 token 数约为平均值的 4 倍，于是 512k 处显存耗尽，而随机 token 的运行轻松就过了。把 MoE 层沿序列分块处理解决了这个问题。在给集群定规模之前，先用真实数据测显存。
- **要规划的不只是 GPU 显存，还有主机内存。** 在 100 万 token 下，offload 到 CPU 的各层输入在 context parallelism 之前约为每块 GPU 180 GB，一个 8 卡节点就是 1 TB 以上，而且它们还要与 optimizer state 共用主机 RAM。拷贝时使用 pinned memory（它们比 pageable memory 快 22%），并在每个 step 之后释放。
- **正确性要与速度分开验证。** 速度和显存数字可以来自随机权重，正确性不行。在使用真实权重的 RL 运行中，从 128k 到 100 万 token，trainer 的 log-probabilities 与 vLLM 的结果吻合在 0.04 -- 0.07（平均绝对差）以内，而一次 overfit 测试在 20 步里把 loss 从 1.65 压到 0.17。

把这些思路组合起来，我们就能在不同的 context 长度上都保持良好的吞吐

## Link训练结果

我们在人类基因组上以每条序列 512k token 做了 post-training，模型的 held-out loss 在 80 步内下降 4.8%，而且收益在那些前面上下文最多的 token 上最大。最后这一点正是它学会了利用长 context、而不只是局部模式的证据。

我们在人类参考基因组（hg38）的 1 号和 2 号染色体上训练，在模型从未见过的 22 号染色体上评估。DNA 是个好测试对象，因为它在每个尺度上都有结构，从短 motif 到横跨极长片段的模式。

为了把长程学习与局部学习分开，我们按 token 位置把 held-out loss 切分成每 32k token 一个桶，并对比 fine-tuning 前后的变化：

- **靠前的 token** 前面几乎没有 context，所以这里的任何改善都来自局部模式，例如短 motif 和碱基组成。
- **靠后的 token** 前面最多有 50 万 token 的 context。
- 局部学习对每个位置的帮助都一样，因此**靠后位置上更大的改善**只能来自只有它们才拥有的长 context。

## Link在 Anyscale 上运行

本文中的每一组实验都跑在 Ray 上，由 Anyscale 平台托管，集群位于 Lila 的云内，是 64 卡的 B200。SkyRL 用 Ray 来放置和协调它的训练与推理 workers，所以同一套配置既跑了基于随机 token 的显存 benchmark，也跑了真实数据上的 fine-tuning，还有拿 vLLM 校验 trainer 的 RL 运行。

想更深入地了解支持长 context 所使用的具体技术，请读这篇[详细的博客文章](https://blog.skyrl.ai/blog/1m-context-glm-5-3-flash)。
