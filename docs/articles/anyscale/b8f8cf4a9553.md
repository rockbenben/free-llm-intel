# 跨 CPU 与 GPU 的流式分布式执行

作者：Eric Liang、Stephanie Wang 和 Cheng Su | 2023 年 5 月 11 日

*在*[上一篇博客](https://www.anyscale.com/blog/offline-batch-inference-comparing-ray-apache-spark-and-sagemaker)中，我们展示了 Ray Data 如何在大规模批量推理负载上比 SageMaker 与 Apache Spark 这类框架提速。本文进一步深入 Ray Data 流式执行的原理，以及如何把它用于你自己的 ML 流水线。*

我们遇到的最苛刻的机器学习（ML）用例之一，是那些在分布式环境中横跨 CPU 与 GPU 设备的流水线。这类情形出现在多种负载中，包括：

- 批量推理：先有 CPU 密集的预处理阶段（如视频解码或图像缩放），再调用 GPU 密集的模型做预测。
- 分布式训练：GPU 训练前需要类似的 CPU 重变换来准备或增强数据集。

有趣的是，许多这类负载中，预处理步骤往往才是瓶颈。当预处理需要**跨多节点的并行度**以及**大量内存来缓冲 CPU 与 GPU 之间的结果**时尤其如此。

例如在内存中解码压缩图像：典型 JPEG 解压比是 10:1，意味着输出内存大小可能是输入的十倍，在 CPU 负载之外带来巨大内存压力。换成其他数据模态，挑战更复杂——比如视频：H264 的解压比可达 2000:1，100MB 的文件输入能产生 200GB 的帧输出。这意味着试图把 CPU 密集的预处理卸载到多 CPU、多机器的从业者，必须面对比本已庞大的源数据大得多的中间结果：

*图 1. 解压压缩图像，大图被溢出到磁盘*

*streaming_figure_1*

若天真地执行，这类计算与内存密集负载无法充分利用昂贵的 GPU 硬件。例如我们可以把 200GB 帧输出缓冲到磁盘，但那会带来几分钟的开销；即便与 GPU 计算重叠，GPU 上仍会出现长时间停顿。这正是集群环境下全流式执行的动机——通过让中间数据流经集群内存来避免这些延迟：

*图 2. 解压的中间数据经内存流式传递*

*streaming_figure_2*

本文带你回顾我们为 Ray Data 打造通用流式后端的过程，并演示前述苛刻用例的实现。我们讨论跨 CPU 与 GPU 的流水线执行相比批处理（bulk）的性能收益，以及它对分布式训练等多种负载的更广泛适用性。

## 集群中的流水线执行

要理解跨 CPU/GPU 流水线（流式）执行的必要性与优势，先看 [bulk synchronous parallel](https://en.wikipedia.org/wiki/Bulk_synchronous_parallel)（BSP）框架会如何处理批量推理。BSP 因简单与通用，是框架（MapReduce、Apache Spark 等）并行化分布式计算的常见方式。

顺带一提，单机内的流水线早已用于 [Torch DataLoader](https://pytorch.org/docs/stable/data.html#torch.utils.data.DataLoader)、[Petastorm](https://petastorm.readthedocs.io/en/latest/index.html) 这类数据加载库。这里我们讨论的是跨整个机器集群的流水线计算。

典型的批量推理作业由以下操作组成：

*图 3. 典型批量推理作业的顺序操作*

*streaming_figure_3*

实现这样一个推理作业，你会用 Ray Data（或类似框架）写代码：

```
1import ray
2
3# Define model and preprocessor.
4model = ...
5preprocess_fn = ...
6
7# Define the inference function.
8def model_fn(batch: Dict[str, np.ndarray]):
9    return {"results": model(batch)}
10
11# The following snippet implements the pipeline.
12ray.data.read_parquet(...) \           # 1. Load
13    .map_batches(preprocess_fn) \      # 2. Preprocess
14    .map_batches(model_fn) \           # 3. Inference
15    .write_parquet(...)                # 4. Save
16
```

在 BSP 框架中，这些操作都可以建模为 1:1 变换，并融合成单一阶段。阶段内的每个任务在本地依次执行上述操作：

*图 4. BSP 框架把操作建模为 1:1 变换*

*streaming_figure_4*

这种执行策略是**内存最优的**：没有中间数据，执行天然流水线化（因为只有一个阶段）。但在异构环境中问题出现了——某些流水线步骤更希望独立地跑在 CPU 或 GPU 上。在 Ray Data 中，这类推理流水线用会启动 GPU actor 的变换表达（`num_gpus=1` 与 `compute=ActorPoolStrategy`）：

```
1import ray
2from ray.data import ActorPoolStrategy
3
4Model = ...
5preprocess_fn = ...
6
7# Define the model as a stateful class with cached setup.
8class MyModelCallableCls:
9    def __init__(self):
10        self.model = Model(...)
11
12    def __call__(self, batch: Dict[str, np.ndarray]) ->
13        return {"results": self.model(batch)}
14
15# Modify the pipeline to use GPU actors.
16ray.data.read_parquet(...) \
17    .map_batches(preprocess_fn) \
18    .map_batches(
19          MyModelCallableCls,
20          num_gpus=1,
21          compute=ActorPoolStrategy(size=N)) \
22    .write_parquet(...)
```

上面的代码中，加载与预处理步骤跑在 CPU（阶段 1），推理跑在 GPU（阶段 2），结果保存又回到 CPU（阶段 3）。这种配置下，一旦中间结果（如解码出的视频帧）超过集群内存规模，就会把数据溢出到远端存储。因此我们看到 **BSP 对异构负载并非内存最优**：

*图 5. BSP 对异构负载并非内存最优*

*streaming_figure_5*

这些不必要的开销可以通过端到端跨集群的流水线（即流式）执行避免——下一节介绍。

## Ray Data 流式执行

在 Ray 2.4 中，我们把 Ray Data 的默认执行策略从 bulk synchronous 改为 streaming。这些流式 Dataset 与现有 API 完全向后兼容：可以懒式地用 map 操作变换、支持 shuffle 操作、也支持内存缓存/物化：

```
1# Create a dataset over parquet files
2ds: ray.data.Dataset = ray.data.read_parquet(...)
3
4# Transform the dataset
5ds = ds.map_batches(my_preprocess_fn)
6ds = ds.map_batches(my_model_fn)
7
8# Iterate over dataset batches in streaming fashion
9for batch in ds.iter_batches():
10   print(batch)
11
12# Materialize all contents of the dataset in memory
13ds = ds.materialize()
```

换句话说，Ray Data API 现在用流式执行来提升大数据集上的性能，而变换 API 与之前 Ray 版本一样简单。

## 视频处理示例

为更充分理解这一 API 的能力，我们走一遍视频处理流水线的示例。流水线中，我们先解码视频帧，用 ML 模型给每帧打标注，再对标注后的帧应用分类模型，最后把结果保存为 JSON：

*图 6. 解码视频帧、帧标注、应用分类、结果存 JSON 的流水线。*

*streaming_figure_6*

先声明流水线的各组件。为简洁起见这里只给桩类，你可以找到[完整骨架](https://gist.github.com/ericl/ac086f0a9bdf41b6101dca665045dfec)（以及[批量推理文档](https://docs.ray.io/en/master/data/batch_inference.html)），改一改就能用于你自己的负载。各步骤间的数据以 numpy 数组的 dict 传递：

```
1# Declare a function that decodes frames.
2def decode_frames(batch: Dict[str, np.ndarray]) -> Dict:
3    video_data = batch["bytes"]
4    ...
5    return {"frames": decoded_frames}
6
7# Declare a model that annotates decoded frame data.
8class FrameAnnotator:
9    def __init__(self):
10        self.model = ...
11
12    def __call__(self, batch: Dict[str, np.ndarray]) -> Dict:
13        frames = batch["frames"]
14        return {"annotated_frames": self.model(frames)}
15
16# Declare a model that classifies annotated frame data.
17class FrameClassifier:
18    def __init__(self):
19        self.model = ...
20
21    def __call__(self, batch: Dict[str, np.ndarray]) -> Dict:
22        frames = batch["annotated_frames"]
23        return {"results": self.model(frames)}
```

接着用 Ray Data 把这些步骤连起来。只需几行代码，而且可以为每一步定制 CPU 与 GPU 的资源需求：

```
1# Create a dataset from video binary data.
2ds = ray.data.read_binary(...)
3
4# Apply the decode step. We can customize the resources per
5# task. Here each decode task requests 4 CPUs from Ray.
6ds = ds.map_batches(decode_frames, num_cpus=4)
7
8# Apply the annotation step, using an actor pool of size 5.
9# Each actor runs on a CPU.
10ds = ds.map_batches(
11    FrameAnnotator,
12    compute=ActorPoolStrategy(size=5))
13
14# Apply the classification step, using a pool of 2 GPU actors,
15# and a fixed data batch size of 64 for the actor calls.
16ds = ds.map_batches(
17    FrameClassifier,
18    num_gpus=1,
19    batch_size=64,
20    compute=ActorPoolStrategy(size=2))
21
22# Trigger execution and write outputs to json.
23ds.write_json("/tmp/output")
24
```

上面配置出的流式拓扑在逻辑上如图所示。由于每一步的资源需求 / task vs actor 策略各不相同，这里每一步成为独立阶段（Ray Data 会融合资源需求等价的步骤）：

*图 7：跨 CPU 与 GPU 的流式执行*

*streaming_figure_7*

## 讨论

### 优化

为无缝执行这样的流式拓扑，Ray Data 底层提供了一系列优化，包括：

**内存稳定性**：Ray Data 依赖底层 Ray 调度器来调度任务与 actor，但仍需在流式拓扑内管理反压（back-pressure），以约束内存用量、避免对象存储溢出。做法是仅当新任务的调度能让流式执行保持在[配置的资源限制](https://docs.ray.io/en/master/data/data-internals.html#streaming-execution)之内时才调度。直观地说，必须对中间结果的内存设上限，才能避免退化为 bulk 执行。

**数据局部性**：虽然 Ray 本就会把任务放到输入参数本地的节点上，Ray Data 流式后端把这一点扩展到了 actor 任务的调度优化。例如上面的例子中，通过把解码出的帧路由到同一节点上的 actor，`decode_frames` 与 `FrameAnnotator` 步骤之间避免了许多网络流量。

**容错**：Ray Data 利用 Ray 内建的[容错](https://docs.ray.io/en/master/ray-core/fault-tolerance.html)处理大作业中的对象丢失。对象丢失时，依据 Ray 跟踪的任务 lineage 重算。若这些对象由 actor 产出，Ray 会先重启这些 actor 再重新提交任务。

### 可扩展性

为了给出 Ray Data 流式执行可扩展性上界的概念，我们跑了若干合成基准，压测 Ray 的对象管理器与 Ray Data [流式执行器](https://github.com/ray-project/ray/blob/master/python/ray/data/_internal/execution/streaming_executor.py)处理 20TiB 数组数据集。底层上 Ray Data 用 `ray.remote() / ray.wait()` 编排流式拓扑，因此其可扩展性与 Ray 本身相当：

*图 10. 压测 Ray 对象管理器与 Ray Data 流式执行器处理 20TiB 数组数据集的合成基准*

*streaming_figure_10*

这些基准在 500 台机器的集群上运行，测试一到四个阶段的流水线（与视频流式例子类似）。我们看到，在这套集群上最简流水线里，Ray Data 能以超过 1TiB/s 的速率处理输入数据。更复杂的多阶段流水线在大集群上仍能维持约 100-200GiB/s 的端到端吞吐。

### 分布式训练

如今相当一部分 [Ray Train](https://docs.ray.io/en/master/train/train.html) 用户也在把 Ray Data 作为 ML 训练的分布式数据后端。Ray Data 流式执行让这些用户能高效处理比集群内存更大的训练数据集，同时利用 CPU 与 GPU 节点加速作业。我们正在增强 Ray Train 的 API，使其原生支持 Ray Data 流式。
