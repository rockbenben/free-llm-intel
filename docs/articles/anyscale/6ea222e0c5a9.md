# 用 Ray Direct Transport 实现快速简易的强化学习权重同步（下篇）

作者：Stephanie Wang、Joshua Lee、Xinyu Zhang 和 Aaron Hao | 2026 年 8 月 18 日

Tl;dr：Ray Direct Transport（RDT）让 LLM 强化学习（RL）中基于 RDMA 的权重传输既快又省心。我们展示如何用 RDT API 最大化数据传输性能——相比朴素的 RDMA 实现最多提升 6 倍。

人人都知道 RDMA 很快。在需要 GPU 之间快速搬运大量数据的场景——例如 LLM 强化学习中的权重同步——它至关重要。但 RDMA 也要求开发者在数据传输前后管理额外的系统操作：内存分配、内存注册、元数据交换等。这些步骤的朴素实现很容易把传输本身的加速全部吃掉。

在[上篇](https://www.anyscale.com/blog/ray-direct-transport-rdma-support-in-ray-core)中，我们介绍了 [Ray Direct Transport](https://docs.ray.io/en/latest/ray-core/direct-transport/direct-transport.html)（RDT）——Ray Core 中为 Ray actor 间提供快速、简便的原生 RDMA 传输的特性。RDT 充当中间"胶水层"，连接构建在 Ray 上的开源引擎（如 [vLLM](https://github.com/vllm-project/vllm)）与提供 RDMA 设备间传输的第三方库（如 [NIXL](https://github.com/ai-dynamo/nixl)）。

*Ray Remote Direct Transport*

本篇（下篇）介绍最大化 RDT 应用性能的最佳实践。我们先走一遍与上篇类似的可用权重同步应用，然后介绍 RDMA 专属的 RDT API，帮你消除性能开销。**运用 RDT 最佳实践，我们在采用 Multi-Node NVLink（MNNVL）的 GB200 节点上，比朴素 RDMA 实现快最多 7.5 倍。**这些加速将通过与 [SkyRL](https://github.com/novasky-ai/skyrl)、[Miles](https://github.com/radixark/miles) 等 RL 框架的持续开源集成向所有人开放。

本文涵盖：

- 第 0 部分：RDMA 的基础，以及无论你用不用 RDT，不想要的性能开销可能来自哪里。
- 第 1 部分：在 Ray 中用 RDT 与 RDMA 做权重同步的可运行代码示例。
- 第 2 部分：如何最大化该示例的性能——尤其是传输许多小张量时。

## RDMA 小引

远程直接内存访问（RDMA）是一种网络技术，允许一台机器直接读写另一台机器的内存，而数据路径上完全不经过远端 CPU、操作系统或应用软件。不同于必须穿越内核网络栈多层的传统 TCP/IP 网络，支持 RDMA 的网卡（NIC）在应用内存缓冲区之间直接完成数据传输。这种"内核旁路"与"零拷贝"设计大幅降低延迟、CPU 开销与内存带宽消耗，让 RDMA 对分布式 AI 系统极具吸引力。

*传统基于 OS 的网络（左）vs RDMA 网络（右）。基于 OS 的网络为应用提供灵活的 socket 接口，但需要经过内核做更多拷贝；RDMA 网络完全绕过内核，直接在应用内存与网络之间传输数据。*

由于 RDMA 传输直接作用于应用内存缓冲区，应用必须确保传输开始前两端资源就位。这让高效的 RDMA 传输搭建比 TCP 之类稍费功夫。需要留意的主要步骤：

- 应用在两台主机上**分配**内存缓冲区，并把它们向 RDMA 网卡**注册**为"内存区域（memory region）"。每次注册至少需要一次系统调用，以把对应页钉在物理内存中；同时生成网卡直接访问所需的元数据：授权后续对已注册缓冲区做 RDMA 操作的本地与远端访问密钥。
- 应用通过带外通道（常用 gRPC 或 Ray）**交换**连接信息，包括内存区域的元数据。
- 对单边操作，发送方或接收方**提交（post）**操作（分别为 Write 或 Read），触发发起方网卡直接访问远端已注册内存、不打扰远端 CPU。网卡跨越网络传输数据，完成时生成完成通知。

结果是极其高效的数据通路：数据直接在两台机器的应用缓冲区之间移动，CPU 主要参与连接建立与完成处理，而非传输本身。

不过，这些额外步骤也可能有坑。每一步在何时、以何种方式执行，直接决定实际传输带宽可能远低于硬件带宽。例如一次内存注册要几十微秒——听起来不多，但当你的网络快到毫秒级就能传完 1GB 数据、而每次传输又包含许多内存区域时，开销迅速累积。

## 用 Ray Direct Transport（RDT）做 RDMA

[Mooncake](https://github.com/kvcache-ai/Mooncake)、NVIDIA [NIXL](https://github.com/ai-dynamo/nixl) 这类库帮用户管理各种 RDMA 操作，但要极致性能，你可能仍需自己打理内存缓冲区、注册等事务。RDMA 天然需要更多应用侧努力才能发挥最大性能，这一负担在某种意义上是根本性的。

在 Ray 中如何化解这一张力？Ray 作为分布式编排器的一大优势，是它对应用数据"何时、何地"需要传输本就有很强可见性。如果我们只把必要的 RDMA 元数据搭现有 Ray 数据传输协议的便车，就能既保留 Ray 友好的 API，又享受 RDMA 支撑的数据传输。这正是我们构建 RDT 的原因。

但世上没有免费的午餐。用 Ray RDT 达到极致性能仍需一些开发者投入，只是我们认为比直接裸用 RDMA 库要少。下面深入细节：先过一遍用 RDT 实现权重同步的最基本方式，再展示最大化性能的高级设计模式。

## 用 RDT 做权重同步：基础

我们使用一个模拟 LLM 强化学习权重传输的简单 PyTorch 示例：一个"sender"代表 trainer，一个"receiver"代表推理引擎。目标是实现零拷贝——让数据传输直接在 sender 与 receiver 的模型权重副本之间进行。

先介绍代码。想直接看完整可运行示例，代码在[这里](https://gist.github.com/Sparks0219/aad063fcba4e9753c61c4b4684b963d3)。

首先定义模型。我们用一个含单个线性层、2GiB 的模型：

```
class Model(torch.nn.Module):
    def __init__(self):
        super().__init__()
        # 2GiB matrix.
        TOTAL_SIZE_BYTES = 2 * 1024**3
        NUM_ROWS = 1_000
        self.layer = torch.nn.Linear(
            TOTAL_SIZE_BYTES // NUM_ROWS // 2, NUM_ROWS, dtype=torch.float16
        )
        self.layer.weight.zero_()

    def forward(self, x):
        with torch.no_grad():
            return self.layer(x)

    def get_views(self, num_views):
        return list(self.layer.weight[:num_views])
```

注意 `get_views` 方法把该层作为一个视图列表返回，每个视图对应权重矩阵的一行。这并非必须——你完全可以直接返回整个 `self.layer.weight`。我们用这个方法测试系统处理大量小张量视图的能力，类似于张量并行场景中矩阵按列分片的情形。

接着定义运行训练引擎的 Ray actor 类。

```
@ray.remote(num_gpus=1, enable_tensor_transport=True)
class Trainer:
    def __init__(self, num_views: int):
        self._model = Model().to("cuda")
        self._num_views = num_views
        self._model_version = 0
        # List of handles to inference engine actors.
        self._generators = []

    async def reset_generators(self, generators: List[ActorHandle[Generator]]):
        """Reset the generators, possibly while the training loop is already running."""
        self._generators = generators

    async def loop(self, num_iters: int):
        """Training loop"""
        for _ in range(num_iters):
            # 1. Update weights.
            self._model.layer.weight += 1
            self._model_version += 1

            # 2. Put weights in the Ray RDT store.
            views = self._model.get_views(self._num_views)
            weights_ref = ray.put(views, _tensor_transport="nixl")

            # 3. Push weights to generators.
            sync_tasks = [
                gen.sync_weights.remote(self._model_version, weights_ref) 
                for gen in self._generators
            ]

            # 4. Free weights from Ray memory.
            del weights_ref

            # 5. Wait for inference engines to finish syncing weights.
            ray.get(sync_tasks)

            # 6. Yield to let the controller reset the list of generators if needed.
            await asyncio.sleep(0)
```

Trainer 在循环中做以下事情：

- 更新权重。这里只是把所有值加 1；真实场景中是执行一个训练 step，可能还要与其他 trainer 副本同步梯度。
- 用 `ray.put` 把权重存入 Ray 基于 RDT 的对象存储。注意 `_tensor_transport="nixl"` 参数指定用 RDT 而非 Ray 的共享内存对象存储。
- 把第 2 步创建的 ObjectRef 列表传下去，向每个 generator 引擎推送权重。
- 删除本轮创建的所有 ObjectRef，确保 Ray 能垃圾回收相关元数据。
- 等待推理引擎完成权重传输。这一步也可以选择推迟到 trainer 下一次要更新权重之前。
- 让出事件循环。这确保当故障或自动扩缩事件改变 generator 成员时，集群 controller 能更新 trainer 的 generator 列表。

注意 `Trainer` 类在 `ray.remote` 中声明了 `enable_tensor_transport=True`，向 Ray 表明该 actor 可以用 RDT 存取对象。没有这个标志，带 `_tensor_transport` 参数的 `ray.put` 调用会直接报错。

再看 generator 逻辑。Generator 在循环中执行 rollout，但每轮之间让出，检查是否有 trainer 发来的权重同步请求。权重同步请求期间，generator：

- 暂停生成。
- 经 RDT 拉取 trainer 权重的一份副本。底层是向 trainer 提交一次 RDMA 读。
- 把拉取的缓冲区拷贝到本地权重副本。
- 恢复生成。

下面是简化版，只展示第 3 步。`Generator.sync_weights` 对应 trainer 调用 `gen.sync_weights.remote(self._model_version, weights_ref)` 的任务定义；在 generator 一侧，`weights_ref` 会被自动替换为经 RDT 与 NIXL 传过来的张量。

```
@ray.remote(num_gpus=1, enable_tensor_transport=True)
class Generator:
    def __init__(self, num_views: int):
        self._model = Model().to("cuda")
        self._num_views = num_views
        self._model_version = 0
        self._generation_event = asyncio.Event()

    async def sync_weights(self, model_version, weights: List[torch.Tensor]):
        """Synchronize weights with the trainer's copy."""
        # `weights` is the generator's copy of the Trainer's `views`, transferred via RDT and NIXL.
        # Copy pulled weights to local model copy.
        views = self._model.get_views(self._num_views)
        for view, weight in zip(views, weights):
            view.copy_(weight)
        self._model_version = model_version
```

最后是把这些组装起来的 driver 循环。

```
NUM_VIEWS, NUM_ITERS = 1_000, 100

generator = Generator.options(num_gpus=1).remote(NUM_VIEWS)
trainer = Trainer.options(num_gpus=1).remote(NUM_VIEWS)

trainer.reset_generators.remote([generator])

# Start loops concurrently and block until both finish
ray.get([
    trainer.loop.remote(NUM_ITERS), 
    generator.loop.remote(NUM_ITERS)
])
```

driver 创建一个 trainer actor 与一个 generator actor，各分配 1 块 GPU。driver 交换 actor 句柄，然后只需等待两个 actor 完成各自的长循环。之后 driver 可以保存结果、继续更多循环、启动新的 trainer 或 generator 等。

**小结：** 用 RDT 做权重同步让你专注于应用逻辑。内存注册、元数据交换、垃圾回收等典型 RDMA 操作全部由底层代管。但要好性能仍需更多功夫。接下来看 RDMA 的隐性开销如何显现、又如何缓解。

## 性能

在测试 RDT 权重同步期间，我们发现并修复了多个把实际传输带宽拉低到远低于硬件最优值的性能瓶颈——某些情况下达 10 倍以上！我们引入的性能修复分几类：

- **减少内存注册。** 内存注册要花时间。当训练与推理引擎采用不同的张量并行分片策略时尤其重要——那意味着要注册并发送大量小张量。
- **降低峰值内存开销。** 权重传输实现常在 RDMA 传输与源/目标模型权重之间额外用一个中间暂存缓冲区。这很方便，但增加峰值内存压力——对本就内存紧张的训练与推理引擎影响可观。
- **优化数据传输。** 传输速度受张量大小与数量影响：传许多小张量比传一个大张量慢，即便总字节数相同。下面介绍 RDT 中解决这些问题的 API。以下基准均在 2 个 GB200 节点间的跨节点传输上完成，使用 MNNVL（multi-node NVLink，单向点对点带宽 900 GB/s）。

## 减少内存注册

在 RL 的权重同步中，最终源与目标缓冲区的位置预先已知，且通常不随时间变化——每一步都在读写同样的位置。我们可以借此避免每次传输都重新注册内存。

在 Ray RDT 中，我们暴露了 API `ray.experimental.register_nixl_memory`，允许用户提前注册内存。当同一（些）张量会被多次发送时，在发送与接收 actor 上都使用该 API。接收侧还需配合使用后文将讨论的 `ray.experimental.set_target_for_ref`。已经用该 API 注册过的内存，传输时不会再次注册。示例片段：

```
import ray

@ray.remote(num_gpus=1, enable_tensor_transport=True)
class Trainer:
    def __init__(self, num_views: int):
        # Register weights on the sender actor.
        for param in self._model.parameters():
            ray.experimental.register_nixl_memory(param)
```

使用该 API 把内存注册的时间成本在 actor 创建时一次性付出，而不是在数据传输过程中见招拆招。下图是优化前后总传输时间对比：

*Ray.get vs Ray.get + register_nixl_memory 端到端传输时间*

内存注册变贵的另一种情形：你传输的许多小张量其实是同一个大张量的视图——训练与推理模型分片方式不同时很常见。

裸用 NIXL 时，常见做法是逐个注册每个子张量，开销很大。RDT 的 NIXL 后端实现了一项优化：只注册一次基张量（base tensor），然后把每个子张量作为该基张量内的偏移发送。随着子张量数量增长，内存注册乃至总传输时间都大幅改善：

## 降低峰值内存开销

到目前为止的示例代码中，接收方用 RDMA 把 sender 权重复制到一块暂存缓冲区，再用一次拷贝把数据搬到推理引擎的权重副本。这很方便，尤其是你需要对推理 worker 的权重副本做后处理时。但我们也可以把 trainer 权重直接拷进推理 worker 权重，省下一份内存。

为此我们引入了新 API `ray.experimental.set_target_for_ref`，告诉 RDT 进来的数据应该落在哪里。该 API 接收一个 RDT ObjectRef 与一个本地 `torch.Tensor` 列表——调用方希望接收进这些张量。

在我们的示例脚本中用法如下：

```
@ray.remote(num_gpus=1, enable_tensor_transport=True)
class Generator:
    def __init__(self, num_views: int):
        # ...
        # Since we are going to write directly to our local model weights on each transfer,
        # pre-register the memory to avoid having to register with each transfer.
        for param in self._model.parameters():
            ray.experimental.register_nixl_memory(param)

    async def sync_weights(self, model_version, refs: List[ray.ObjectRef]):
        # set_target_for_ref requires the receiver to have a copy of the
        # ObjectRef, not the underlying tensors. So for this example,
        # the Trainer wraps its `weights_ref` in a Python list and 
        # we unpack it to a single ObjectRef here.
        ref, = refs
        views = self._model.get_views(self._num_views)
        # The order of tensors in our local `views` must match the order on the trainer.
        ray.experimental.set_target_for_ref(ref, views)
        # `weights` shares the same underlying tensors as `views`. 
	 weights = ray.get(ref)
```

峰值内存用量用 `torch.cuda.memory.max_memory_allocated` 检查。此前，torch 缓存分配器里总能看到一次额外拷贝——20GB 权重会看到峰值 40GB。现在峰值保持 20GB。

## 优化数据传输

要最大化网络带宽，传输许多小张量是低效的。把众多小张量先变成连续内存"装桶（bucket）"往往更好。GPU 的 HBM 带宽很高，与总传输时间相比额外拷贝的开销可以忽略。注意：该方法能改善传输时间，但也因额外拷贝推高 trainer 的峰值内存。

你可以自己实现这一点，RDT 也内建了一个在底层做这种拷贝的内存池。池中所有内存都已预先注册，避免每次传输再做新的内存注册。

在我们的示例中启用它的方法：

```
@ray.remote(num_gpus=1, enable_tensor_transport=True)
class Trainer:
    def __init__(self):
        # ...
        # Pre-allocate a 1GB GPU memory pool for NIXL transfers.
        # This is instead of directly registering the Trainer's model weights.
        register_nixl_memory_pool(1024**3, torch.device("cuda"))
```

构造函数里加上这行后，`Trainer.loop` 中每次 `ray.put` 调用都会把张量拷进从 RDT 管理的内存池分配的连续内存缓冲区。通过决定一次 `ray.put` 传多少个张量，你可以调节桶的大小。注意接收侧我们仍保留 `register_nixl_memory` + `set_target_for_ref`，把内存注册从数据传输路径中移除。下图中还包含两项内存池改进，将在 Ray 2.59 正式提供——先睹为快：

单项性能改进都看完了，现在放到完整[脚本](https://gist.github.com/Sparks0219/aad063fcba4e9753c61c4b4684b963d3)里验证。下面是各步骤对端到端时间的贡献拆解：

剩余的开销是什么？拆开看：

- **Python 对象传输**：RDT 支持发送嵌在任意 Python 对象里的 PyTorch 张量。张量数据经 NIXL 走 RDMA，对象的其余部分序列化后经 Ray 原生基于 CPU 的数据面传输。较小的 Python 对象只需源 actor 到目标 actor 一条消息；而序列化数据超过 100KB 的大对象——比如本例这个 1 万张量列表——Ray Core 会额外做一次序列化/反序列化，经由 Ray 共享内存存储传输。
- **数据传输**：张量数据经 RDMA 的实际传输。本例最大硬件传输带宽 900GB/s，数据传输入身做到了 859 GB/s。
- **张量元数据管理**：管理 N 个张量会贯穿传输引入许多 O(N) 系统操作：跟踪每个张量的形状、校验形状与目标缓冲区匹配等。对本例传输的 1 万个视图，这目前给总传输时间增加几毫秒。

## RDT 的下一步

我们正与开源社区合作，把 RDT 集成进 RL 框架实现高性能权重同步。

[RDT 集成落地后](https://github.com/NovaSky-AI/SkyRL/pull/1753)，[SkyRL](https://github.com/NovaSky-AI/SkyRL) 在 4 台 8xH100 节点上同步 [Qwen/Qwen3-235B-A22B](https://huggingface.co/Qwen/Qwen3-235B-A22B) 权重只需 3.5 秒，比 SkyRL 中简单的 NCCL broadcast 实现快约 18 倍。

与 [Miles](https://github.com/radixark/miles/pull/1313) 的集成也在推进中。有了 RDT，Miles 同步 GLM-4.5-Air 只需 2.3 秒（4 台 8xH100 节点），比使用 [NCCL](https://github.com/nvidia/nccl) 快 2.2 倍、比 Mooncake Transfer Engine 快 1.14 倍。

与此同时，我们也在积极解决 RDT 的剩余性能问题，包括[优化小张量的 O(N) 开销](https://github.com/ray-project/ray/issues/65475)、缩短 [Python 对象数据的传输时间](https://github.com/ray-project/ray/issues/65490)、把内存池扩展到[接收侧张量](https://github.com/ray-project/ray/issues/64713)。从[文档](https://docs.ray.io/en/latest/ray-core/direct-transport/direct-transport.html)开始体验 RDT，告诉我们你的想法！
