# KubeRay v1.6 与 v1.7 发布

作者：KubeRay Team | 2026 年 8 月 25 日

特别感谢以下 KubeRay 贡献者：Anyscale（Jui-An Huang、Nai-Juei Yeh、Jun-Hao Wan）、Google Cloud（Andrew Sy Kim、Ryan O'Leary、Aaron Liang、Richa Banker）、Hark（Kai-Hsun Chen）、阿里云（Kun Wu）、Microsoft（Alima Azamat、Mark Rossetti）、Red Hat（Pat O'Connor、Laura Fitzgerald、Bryan Keane）、opensource4you（Han-Ju Chen、Jia-Wei Jiang、Jie-Kai Chang、Che-Yu Wu、Fu-Sheng Chen、Chih-Ting Yeh）

我们很高兴宣布 KubeRay v1.6 与 v1.7 发布，延续 Ray on Kubernetes 的强劲势头。这两个版本为在 Kubernetes 上运行 Ray 引入了多项增强，共包含约 75 位贡献者的 381 次以上提交。

**核心亮点**

- **History Server：** beta 发布——启动更快、内存占用更低、支持 ray auth token、collector sidecar 自动注入。
- **安全：** 原生 NetworkPolicy 支持、自动 mTLS 证书管理、基于 Kubernetes RBAC 的认证。
- **RayService：** 增量升级晋升为 beta，并支持回滚。
- **RayJob：** RayCronJob 支持、sidecar 提交器可独立重启、删除策略改进。
- **RayCluster：** Recreate 升级策略、可配置内建 Ingress、Autoscaler V2 worker group 优先级，多主机索引晋升 beta。
- **GCS 容错：** 内嵌 RocksDB 存储消除了对外部 Redis 的依赖，并改善集群删除的可靠性。
- **可观测性：** Kubernetes 平台事件呈现在 Ray Dashboard 中，简化基础设施故障排查。

## History Server（beta）

KubeRay History Server 是一个独立部署，让你在 `RayCluster` 被删除后仍能访问集群的日志与事件。这对 `RayJob` 尤其有用——它为单个作业创建临时 Ray 集群，作业完成即拆除。History Server 支持 `RayCluster`、`RayJob` 与 `RayService`。

它由两个组件构成：collector 与 history server。collector 以 sidecar 容器运行在 head 与 worker pod 上，把日志和事件上传到对象存储；history server 是独立部署，在这些数据之上提供 Ray Dashboard API 服务。

v1.6 引入的 alpha 版本在每次启动时处理全部事件并将其保存在内存中。v1.7 我们重新架构并晋升为 beta。新版本增加了懒加载、LRU 缓存等改进，降低内存占用与启动时间。还包含以下特性：

- 集群选择页，可轻松跳转至任何在线或历史 Ray 集群的 dashboard。

*Ray History Server*

- 可查看历史 Ray Data 数据集与 Ray Serve 应用

### Collector sidecar 自动注入（alpha）

KubeRay v1.7 引入 collector sidecar 自动注入，让采用 History Server 更省心。此前用户必须在每个 head 和 worker pod 模板中手动定义 collector 容器，包括其环境变量与 volume 挂载，还要在 Ray 容器上配置事件导出。现在只需在 RayCluster spec 中设置 `historyServerOptions.collectorOptions`，KubeRay 就会自动为所有 head 与 worker pod 注入配置正确的 collector sidecar。

```
apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: raycluster-historyserver
spec:
  historyServerOptions:
    collectorOptions:
      image: quay.io/kuberay/collector:v1.7.0
      env:
      - name: STORAGE_BACKEND
        value: "GCS"
      - name: GCS_BUCKET
        value: "my-gcs-bucket"
  ...
```

该功能默认关闭。使用前请启用 `RayClusterHistoryServer` feature gate。

### History Server 认证支持

[Ray token 认证](https://docs.ray.io/en/master/cluster/kubernetes/user-guides/kuberay-auth.html)（`spec.authOptions`）与 History Server 在 KubeRay 中是各自独立引入的——token 认证随 v1.5.1 发布，History Server alpha 随后在 v1.6 上线。在此之前两个特性无法同时使用：History Server 的两个组件都不传播 Ray Dashboard 所需的 `x-ray-authorization` 头。

结果是：启用 token 认证后，作业历史、Serve 应用等依赖 Dashboard 的数据取不到，而依赖在线集群代理的请求则整体失败。

KubeRay v1.7 在晋升 beta 之际，在 History Server 两个组件中都补上了这一缺口，让启用认证的 Ray 集群也能使用 History Server。

#### Collector

Collector 现在会用共享 token Secret，或在启用 `enableK8sTokenAuth` 时使用其投影的 Kubernetes ServiceAccount token，对 Ray Dashboard 进行认证。配合自动 Collector sidecar 注入无需额外配置：KubeRay 自动从 `authOptions` 派生正确的凭证。

```
apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: raycluster-historyserver-auth
spec:
  authOptions:
    mode: token
  historyServerOptions:
    collectorOptions:
      image: quay.io/kuberay/collector:v1.7.0
```

#### History Server

以 `--use-auth-token-mode=true` 启动，即可代理到启用认证的在线集群：它读取每个集群的 auth Secret、附上凭证，并剥离客户端传入的 authorization 头，防止查看者覆盖。需应用 [service_account_auth_token_mode.yaml](https://github.com/ray-project/kuberay/blob/master/historyserver/config/service_account_auth_token_mode.yaml) 以获取所需的 Secret 读权限。

在线集群代理目前仅支持共享 token 模式；`enableK8sTokenAuth` 对 collector 有效，但 history server 尚未支持。

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: historyserver
  labels:
    app: historyserver
spec:
  replicas: 1
  selector:
    matchLabels:
      app: historyserver
  template:
    metadata:
      labels:
        app: historyserver
    spec:
      serviceAccountName: historyserver
      containers:
      - name: historyserver
        ...
        image: historyserver:v0.1.0
        imagePullPolicy: IfNotPresent
        command:
        - historyserver
        - --use-auth-token-mode=true
```

## 安全增强

### Network Policy 支持（alpha）

KubeRay v1.7 引入原生 `NetworkPolicy` 支持。无需再为每个 `RayCluster` 的 head 与 worker pod 手工创建 `NetworkPolicy` 资源，现在可以直接在 `RayCluster` spec 中配置 `networkPolicy`：选择隔离模式 `DenyAll`、`DenyAllIngress` 或 `DenyAllEgress`，并用针对 head 与 worker pod 的 ingress/egress 规则显式放行流量。同一 Ray 集群内 pod 之间的流量永不被阻断。

下面的例子除 head pod 上的 Prometheus 指标抓取外拒绝所有流量：

```
apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: raycluster-network-policy
spec:
  networkPolicy:
    mode: DenyAll
    head:
      ingressRules:
      - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: <prometheus-namespace>
        ports:
        - port: 8080
          protocol: TCP
```

该功能默认关闭。使用前请启用 `RayClusterNetworkPolicy` feature gate。

### mTLS 支持（alpha）

从 KubeRay v1.7 起，为 Ray 启用 mTLS 时不再需要手动管理证书。operator 与 cert-manager 集成，自动为 head 与 worker pod 签发证书，用 mTLS 保护两者之间的通信。

使用时只需在 `RayCluster` spec 中添加 `tlsOptions`：

```
apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: raycluster-mtls
spec:
  tlsOptions:
    enabled: true
```

该功能需启用 `RayClusterMTLS` feature gate，并要求集群中已安装 cert-manager。

### 基于 Kubernetes RBAC 的 Token 认证

基于 token 的认证自 Ray 2.52.0 与 KubeRay v1.5.1 起支持：RayCluster controller 自动生成 token 并存入所有客户端共享的 Kubernetes Secret。KubeRay v1.6 从两方面增强了它：

- 认证与授权现在可以完全交给 Kubernetes。启用 `authOptions.enableK8sTokenAuth` 后，客户端用自己的 Kubernetes ServiceAccount token 认证，Ray 通过检查调用者对特定 RayCluster 是否拥有 ray:write 自定义动词来授权每个请求。这样你可以用标准 Kubernetes RBAC、以每用户身份（而非单一共享 token）控制谁可以访问 Ray 集群。该特性需要 Ray 2.55.0 或更高版本。

```
apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: raycluster-k8s-auth
spec:
  authOptions:
    mode: token
    enableK8sTokenAuth: true
  ...
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: ray-writer
rules:
- apiGroups: ["ray.io"]
  resources: ["rayclusters"]
  verbs: ["ray:write"]
```

详情见[文档](https://docs.ray.io/en/master/cluster/kubernetes/user-guides/kuberay-auth-rbac.html)。

- 用户现在可以通过设置 `authOptions.secretName` 提供自己的 token `Secret`，而不必让 KubeRay 生成。该 Secret 必须在 `auth_token` 数据键下存放 token。

```
apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: ray-cluster-with-auth
spec:
  enableInTreeAutoscaling: true
  authOptions:
    mode: token
    secretName: ray-cluster-token
```

## RayService 增强

### RayService 增量升级（beta）

RayService 的增量升级策略作为 alpha 特性在 KubeRay v1.5 引入。此后，基于测试与用户反馈，该特性增加了回滚支持和多项可靠性改进。

回滚允许通过把 RayService spec 改回当前正在服务流量的版本，来撤销进行中的升级。KubeRay 随后逐步把流量与容量迁回原集群并删除新集群，全程无停机。详情见[文档](https://docs.ray.io/en/master/cluster/kubernetes/user-guides/rayservice-incremental-upgrade.html#rollback)。

从 KubeRay v1.7 起，增量升级策略晋升为 beta，`RayServiceIncrementalUpgrade` feature gate 默认开启。

### RayService 与 Kueue 集成

从 Kueue v0.17.0 与 KubeRay v1.6.0 起，Kueue 把 RayService 自定义资源作为顶层作业管理，而不再经由它创建的 RayCluster。这使得 RayService 负载可以通过 MultiKueue 分发到多个 Kueue 管理的集群。KubeRay 与 Kueue 集成的更多细节见[这里](https://kueue.sigs.k8s.io/v0.17/docs/tasks/run/rayservices/)。

目前 RayService 升级存在一个限制，同时影响增量升级与零停机升级：升级期间 RayService 可能临时管理两个 RayCluster，流量从旧集群迁移到新集群。MultiKueue 目前不支持 Elastic RayService。关注进展可看 [kueue#11102](https://github.com/kubernetes-sigs/kueue/issues/11102)。

## RayJob 增强

### RayCronJob（alpha）

从 KubeRay v1.6 起，你可以用 `RayCronJob` 按 cron 计划原生调度 `RayJob`，无需依赖外部 cron 工具。KubeRay v1.7 新增时区支持，可指定调度所用时区；未设置时默认使用 KubeRay controller 的本地时区。

创建 `RayCronJob` 的例子：

```
apiVersion: ray.io/v1
kind: RayCronJob
metadata:
  name: example-raycronjob
spec:
  schedule: "*/5 * * * *"
  timeZone: "America/Los_Angeles"
  jobTemplate:
    # Everything below here is a standard RayJob spec
```

该功能默认关闭，需启用 `RayCronJob` feature gate。详情见[文档](https://docs.ray.io/en/master/cluster/kubernetes/getting-started/raycronjob-quick-start.html)。

### RayJob SidecarMode 重试（alpha）

RayJob 的 `SidecarMode` 在 KubeRay v1.5 引入，把作业提交器作为 sidecar 容器运行在 head pod 中。KubeRay v1.7 引入 `SidecarSubmitterRestart` feature gate。借助 Ray 2.54.0 改进的错误码处理，以及在 Kubernetes v1.35 中默认启用的 ContainerRestartRules 特性，提交器容器现在可以在瞬态错误时独立重启，而不重启 ray-head 容器。重启时，提交器先检查作业状态；若作业仍在运行，只是重新接入日志流，不再重新提交。

详细信息见[文档](https://docs.ray.io/en/master/cluster/kubernetes/user-guides/rayjob-sidecar-submitter-restart.html)。

### 减少对 wget 的依赖

此前 KubeRay 在多处健康检查中依赖 `wget`，包括 Ray pod 的就绪与存活探针，以及 RayJob SidecarMode 在提交作业前确认 GCS 健康的等待循环。这对不带 `wget` 的 Ray 镜像（例如即将推出的 slim Ray 镜像）成了问题：探针会失败，sidecar 作业提交可能在作业开始前就崩掉。

从 KubeRay v1.6 起，多数场景移除了该依赖。RayJob SidecarMode 的 GCS 等待循环改用 Python 的 `urllib`——由于提交器本就依赖 Ray CLI，`urllib` 总是可用，且在所有受支持 Ray 版本上都能工作。此外，Ray 2.53.0 引入统一的健康检查端点 `/api/healthz`，让 KubeRay 可以把 pod 探针从基于 exec 的 `wget` 命令切换为 Kubernetes 原生 HTTP 探针。

仍有一处需要组合检查：RayService worker 就绪需同时验证本地 raylet 与 Serve proxy，单个 HTTP 端点目前无法表达。Ray 社区正在推进统一 serving readiness 端点的工作，让这最后一项检查也能变成普通 HTTP 探针（见 [ray#60925](https://github.com/ray-project/ray/issues/60925)）。

### RayJobDeletionPolicy（beta）

`RayJobDeletionPolicy` 特性在 KubeRay v1.3 以 alpha 引入，允许通过 `spec.deletionStrategy` 精细配置 RayJob 结束后的清理行为，例如删除整个 RayCluster、只删 worker pod，或删除 RayJob 自身。从 KubeRay v1.6 起该特性晋升 beta，`RayJobDeletionPolicy` feature gate 默认开启。详情见[文档](https://docs.ray.io/en/master/cluster/kubernetes/getting-started/rayjob-quick-start.html#rayjob-configuration)。

## RayCluster 增强

### Recreate 升级策略

此前更新 RayCluster spec 的某些字段（如容器镜像），用户要么重建 RayCluster，要么等所有 Pod 删除后手动挂起再恢复。这对使用 [ArgoCD](https://argo-cd.readthedocs.io/en/stable/) 等 GitOps 系统部署的用户很不方便。

KubeRay 现在在 RayCluster 上支持 `spec.upgradeStrategy.type` 字段。设为 Recreate 后，controller 会在 spec 变化时删除集群中的所有 Pod，再按更新后的 spec 重新创建。应用新 spec 即可完成变更发布。

```
apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: raycluster-kuberay
spec:
  upgradeStrategy:
    type: Recreate
 … 
```

注意 `Recreate` 会先删除全部 Pod 再创建新 Pod，因此运行在集群上的 Ray 负载会丢失。该策略适用于可安全重启的集群。

### 可定制的 Ingress 选项

KubeRay 提供可选的内建 ingress 支持：启用 `spec.headGroupSpec.enableIngress` 后自动创建 Kubernetes Ingress 资源。该功能最初为简单的 NGINX 方案而设计，只覆盖基本暴露场景。

Ingress API 早于 Gateway API 出现且仍被广泛采用，因此我们收到大量让它更可配置的请求。此前需要定制生成 Ingress 的用户通常得自己创建或修改 Ingress。

KubeRay v1.7 引入 `spec.headGroupSpec.ingressOptions`，让用户定制生成的 Ingress，以更好契合部署需求。

```
apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: raycluster-ingress
spec:
  headGroupSpec:
    enableIngress: true
    ingressOptions:
      host: ray-dashboard.example.com
      path: /
      pathType: Prefix
      tls:
      - hosts:
        - ray-dashboard.example.com
        secretName: ray-dashboard-tls
```

### Autoscaler V2 的 worker group 优先级字段

Ray Autoscaler V2 此前用 `workerGroupSpecs` 的顺序来在多个可满足同一资源请求的 worker group 之间做取舍，用户难以显式控制优先选哪个组。

Ray 2.56 在 Autoscaler V2 中引入优先级感知的 worker group 选择。KubeRay v1.7 通过 `workerGroupSpecs` 的 `priority` 字段暴露该能力，让用户定义自己偏好的 worker group。

```
apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: raycluster-autoscaler-priority
spec:
  enableInTreeAutoscaling: true
  autoscalerOptions:
    version: v2
  workerGroupSpecs:
  - groupName: high-priority-worker-group
    priority: 10
    …
  - groupName: low-priority-worker-group
    priority: 0
    …
```

### RayMultiHostIndexing（beta）

`RayMultiHostIndexing` 特性在 KubeRay v1.5 以 alpha 引入，为多主机 worker group 提供稳定的副本与主机索引，适用于要求每个 worker 拥有一致主机/副本身份的分布式加速器负载。

在 KubeRay v1.6 中，该特性经过单元与端到端测试、以及用 SkyRL 和 `JaxTrainer` Ray Train API 对多主机 Ray 负载的人工验证后晋升 beta。这对多主机负载（尤其是多 slice 场景）很有用，也有助于实现 Ray Train 弹性等改进。

## GCS 容错

### 内嵌 RocksDB 后端（alpha）

从 KubeRay v1.7 与 Ray 2.57.0 起，支持为 Ray GCS 使用内嵌 [RocksDB](https://rocksdb.org/) 存储后端。此前启用 GCS 容错需要外部 Redis，用户要自行部署并运维一个 Redis 实例。现在可以使用内嵌 RocksDB 存储后端：它直接链接进 GCS 进程，把状态持久化到本地路径，不需要任何外部服务。KubeRay 通过 `gcsFaultToleranceOptions.backend: rocksdb` 暴露该能力。operator 自动创建 `PersistentVolumeClaim`（PVC）、挂载到 head pod 并设置所需环境变量。PVC 默认随 RayCluster 一并被 GC 回收；设置 `deletionPolicy: Retain` 可在集群删除后保留数据以便新集群从中恢复，或用 `claimName` 自带 PVC。

```
apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: raycluster-embedded-gcs-ft
spec:
  gcsFaultToleranceOptions:
    backend: rocksdb
    storage:
      size: 1Gi
      # deletionPolicy: Retain   # keep the data after the cluster is deleted
      # claimName: my-gcs-pvc    # or bring your own PVC
```

该特性在 Ray 与 KubeRay 中均为 alpha，默认关闭。使用前请启用 `GCSFaultToleranceEmbeddedStorage` feature gate。完整示例见[示例 YAML](https://github.com/ray-project/kuberay/blob/master/ray-operator/config/samples/ray-cluster.embedded-gcs-ft.yaml)。

### Redis 清理 finalizer 超时

当以 Redis 启用 GCS 容错时，KubeRay 会给 RayCluster 加一个 finalizer，并在删除时运行清理任务以移除 Redis 中的残留数据。此前如果清理任务未能完成，finalizer 就永远不会被移除，RayCluster 可能无限期卡在 Terminating 状态，也会阻塞 Kueue 等系统释放该集群的资源配额。从 KubeRay v1.7 起，finalizer 在超时后会被强制移除——默认 5 分钟，可通过 `ray.io/gcs-ft-deletion-timeout` 注解按集群配置。发生时 KubeRay 会发出 `ForceDeletedStuckCluster` 警告事件，其中包含外部存储的 namespace，便于你知道哪些 Redis 数据可能需要手动清理。

## 其他

### Kubernetes 上的 Ray 平台事件

当 Ray 负载遇到由底层节点基础设施引发的故障——例如 GPU XID 错误——Ray 应用可能只报告笼统的 CUDA 或任务失败，而实际根因却记录为与该节点关联的 Kubernetes Event。这让用户在 Ray Dashboard 排障时难以区分应用级故障与底层基础设施问题。

Ray 2.56.0 引入 Platform Events，把 KubeRay 自定义资源的 Kubernetes 生命周期事件呈现在 Ray Dashboard 中。详情见 [Enable Ray platform events on Kubernetes](https://docs.ray.io/en/master/cluster/kubernetes/user-guides/k8s-events.html)。

*KubeRay Platform Events*

### RayJob 完成时的 Volcano PodGroup 生命周期

此前当 RayJob 到达终态（Complete 或 Failed），KubeRay 会无条件删除关联的 Volcano PodGroup。本版修正了该行为：根据实时的 RayCluster 状态与删除策略更新 PodGroup 的 `MinMember` 与 `MinResources`，而不是一律删除。使用 `ClusterSelector` 的 RayJob 不在此列，因为该模式不支持 gang 调度。

KubeRay v1.7 带来了更强的可扩展性与更稳健的构件，助你基于 Ray on Kubernetes 打造规模化 ML 平台。展望 v1.8，我们正与 Ray 社区共同规划路线图。请在 [kuberay#2999](https://github.com/ray-project/kuberay/issues/2999) 分享你的反馈，参与塑造 KubeRay 的未来。

你也可以[加入 Ray Slack](https://www.ray.io/join-slack) 工作区的 #kuberay 频道提问。此外，关注 [Ray/KubeRay 社区 Google 日历](https://calendar.google.com/calendar/u/1?cid=Y19iZWIwYTUxZDQyZTczMTFmZWFmYTY5YjZiOTY1NjAxMTQ3ZTEzOTAxZWE0ZGU5YzA1NjFlZWQ5OTljY2FiOWM4QGdyb3VwLmNhbGVuZGFyLmdvb2dsZS5jb20)，参加 KubeRay 双周社区会议，与贡献者面对面。

按下面的说明开始使用，更多细节见 [Getting Started with KubeRay](https://docs.ray.io/en/master/cluster/kubernetes/getting-started.html)。

```
helm repo add kuberay https://ray-project.github.io/kuberay-helm/
helm repo update
# Install both CRDs and KubeRay operator v1.7.0.
helm install kuberay-operator kuberay/kuberay-operator --version 1.7.0
```
