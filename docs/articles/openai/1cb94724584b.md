# 在 API 中推出 GPT‑4.1

全新一代 GPT 模型系列，在编程、指令遵循与长上下文方面实现重大提升——并推出我们首款 nano 模型。

今天，我们在 API 中发布三个新模型：GPT‑4.1、GPT‑4.1 mini 和 GPT‑4.1 nano。这些模型全面超越 GPT‑4o 和 GPT‑4o mini，在编程和指令遵循方面提升显著。它们还拥有更大的上下文窗口——支持多达 100 万 token 的上下文——并凭借改进的长上下文理解能力更充分地利用这些上下文。知识截止日期更新为 2024 年 6 月。

GPT‑4.1 在以下行业标准测评中表现出色：

- **编程**：GPT‑4.1 在 [SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/) 上得分 54.6%，比 GPT‑4o 高出 21.4 个百分点，比 GPT‑4.5 高出 26.6 个百分点——使其成为编程领域领先的模型。
- **指令遵循：** 在衡量指令遵循能力的 [Scale 的 MultiChallenge⁠（在新窗口中打开）](https://scale.com/leaderboard/multichallenge) 基准上，GPT‑4.1 得分 38.3%，比 GPT‑4o 提升 10.5 个百分点。
- **长上下文：** 在多模态长上下文理解基准 [Video-MME⁠（在新窗口中打开）](https://video-mme.github.io/home_page.html) 上，GPT‑4.1 创下新的最先进成绩——在“长视频、无字幕”类别得分 72.0%，比 GPT‑4o 提升 6.7 个百分点。

虽然基准测试提供了有价值的洞见，但我们在训练这些模型时聚焦于现实世界的实用性。与开发者社区的紧密协作和伙伴关系，使我们能够针对对其应用最重要的任务优化这些模型。

为此，GPT‑4.1 模型家族以更低的成本提供了卓越的性能。这些模型在延迟曲线的每一点上都推动性能向前。

GPT‑4.1 mini 是小模型性能的重大飞跃，甚至在许多基准上超过 GPT‑4o。它在智能测评中与 GPT‑4o 持平或更优，同时将延迟降低近一半、成本降低 83%。

对于要求低延迟的任务，GPT‑4.1 nano 是我们可用最快、最便宜的模型。它以小巧的体积交付卓越性能，拥有 100 万 token 上下文窗口，在 MMLU 上得分 80.1%，GPQA 上得分 50.3%，Aider 多语言编程测评上得分 9.8%——甚至高于 GPT‑4o mini。它非常适合分类或自动补全之类的任务。

指令遵循可靠性和长上下文理解的这些改进，也让 GPT‑4.1 模型在为 agent（可代表用户独立完成任务的系统）提供动力方面显著更有效。结合 [Responses API⁠（在新窗口中打开）](https://platform.openai.com/docs/api-reference/responses) 这样的基础组件，开发者现在可以构建在真实软件工程、从长文档中提取洞见、以最少人工指导解决客户请求以及其他复杂任务上更有用、更可靠的 agent。

请注意，GPT‑4.1 仅通过 API 提供。在 ChatGPT 中，指令遵循、编程和智能方面的许多改进已逐步并入 GPT‑4o 的[最新版本⁠（在新窗口中打开）](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)，未来版本中我们还会继续并入更多改进。

我们还将开始弃用 API 中的 GPT‑4.5 Preview，因为 GPT‑4.1 在许多关键能力上提供相同或更优的性能，而成本和延迟低得多。GPT‑4.5 Preview 将于三个月后、2025 年 7 月 14 日关闭，以便开发者有时间迁移。GPT‑4.5 当初作为[研究预览版](https://openai.com/index/introducing-gpt-4-5/)推出，用于探索和试验一个大规模、计算密集的模型，我们从开发者反馈中学到了很多。我们会继续把你们认可的 GPT‑4.5 的创造力、写作质量、幽默感和细腻之处，传承到未来的 API 模型中。

下文我们将拆解 GPT‑4.1 在若干基准上的表现，并附上 Windsurf、Qodo、Hex、Blue J、Thomson Reuters、Carlyle 等 alpha 测试者的示例，展示它在生产环境中领域特定任务上的表现。

## 编程

GPT‑4.1 在各类编程任务上显著优于 GPT‑4o，包括以 agent 方式解决编程任务、前端编程、减少多余编辑、稳定遵循 diff 格式、确保一致的工具调用等等。

在衡量真实软件工程能力的 SWE-bench Verified 上，GPT‑4.1 完成了 54.6% 的任务，而 GPT‑4o（2024-11-20）为 33.2%。这反映了模型在探索代码仓库、完成任务、产出既能运行又能通过测试的代码方面能力的提升。

*在*[SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/)*中，模型会拿到一个代码仓库和问题描述，必须生成一个补丁来解决该问题。性能高度依赖于所用的提示词和工具。为便于复现并理解我们结果的语境，我们*[*在此*⁠（在新窗口中打开）](https://cookbook.openai.com/examples/gpt4-1_prompting_guide)*介绍了 GPT‑4.1 的评测设置。我们的得分剔除了 500 道题中 23 道在我们的基础设施上无法运行解法的题目；若保守地将其记 0 分，54.6% 的成绩为 52.1%。*

对于需要编辑大文件的 API 开发者，GPT‑4.1 在各种格式的 code diff 上可靠得多。GPT‑4.1 在 [Aider 多语言 diff 基准⁠（在新窗口中打开）](https://aider.chat/docs/leaderboards/) 上的得分是 GPT‑4o 的两倍多，甚至比 GPT‑4.5 高 8 个百分点。该测评既衡量跨多种编程语言的编码能力，也衡量模型以完整文件和 diff 格式产出变更的能力。我们专门训练 GPT‑4.1 更可靠地遵循 diff 格式，这让开发者只需让模型输出被修改的行、而不必重写整个文件，从而同时节省成本和延迟。要获得最佳的代码 diff 性能，请参阅我们的[提示词指南⁠（在新窗口中打开）](http://platform.openai.com/docs/guides/text?api-mode=responses#prompting-gpt-4-1-models)。对于偏好重写整个文件的开发者，我们已将 GPT‑4.1 的输出 token 上限提升到 32,768（GPT‑4o 为 16,384）。我们还建议使用 [Predicted Outputs⁠（在新窗口中打开）](https://platform.openai.com/docs/guides/predicted-outputs) 来降低整文件重写的延迟。

*在 Aider 的多语言基准中，模型通过编辑源文件来解答来自*[Exercism⁠（在新窗口中打开）](https://exercism.org/)*的编程练习，允许重试一次。“whole”格式要求模型重写整个文件，可能既慢又贵。“diff”格式要求模型写出一系列*[搜索/替换块⁠（在新窗口中打开）](https://aider.chat/docs/more/edit-formats.html)*。*

GPT‑4.1 在前端编程上也大幅改进于 GPT‑4o，能够构建功能更完善、外观更美观的 Web 应用。在我们的正面对比中，付费人工评审者有 80% 的情况下更偏好 GPT‑4.1 生成的网站。

**提示词：** 制作一个抽认卡 Web 应用。用户应能创建抽认卡、搜索已有的抽认卡、复习抽认卡，并查看复习统计。预先加载十张卡片，每张包含一个印地语单词或短语及其英文翻译。复习界面：在复习界面中，点击或按空格键应以平滑的 3D 动画翻牌显示翻译；按方向键应能翻阅卡片。搜索界面：搜索栏应在用户输入查询时动态提供结果列表。统计界面：统计页应以图表展示用户复习过的卡片数量和答对百分比。创建卡片界面：创建页应允许用户指定抽认卡正面和背面并加入其收藏。以上各界面都应可从侧边栏访问。生成一个单页 React 应用（所有样式内联）。

## 指令遵循

GPT‑4.1 更可靠地遵循指令，我们在多种指令遵循评测中测量到了显著提升。

我们开发了一个内部指令遵循评测，在多个维度、若干指令遵循关键类别上追踪模型表现，包括：

- **格式遵循。** 提供指定模型响应自定义格式的指令，如 XML、YAML、Markdown 等。
- **否定指令。** 指定模型应避免的行为。（例：“不要让用户联系客服”）
- **有序指令。** 提供一组模型必须按给定顺序执行的指令。（例：“先询问用户姓名，再询问其邮箱”）
- **内容要求。** 输出须包含特定信息的内容。（例：“撰写营养计划时必须包含蛋白质含量”）
- **排序。** 按特定方式排列输出。（例：“按人口数量排序响应”）
- **过度自信。** 指令模型在所请求信息不可得或请求不属于给定类别时回答“我不知道”或类似表述。（例：“如果你不知道答案，提供客服邮箱”）

这些类别源于开发者关于哪些方面对他们最重要、最相关的反馈。每个类别内，我们划分了简单、中等和困难的提示词。GPT‑4.1 在困难提示词上相较 GPT‑4o 的提升尤为显著。

*我们的内部指令遵循评测基于真实开发者用例与反馈，涵盖复杂度各异的任务，并叠加关于格式、详略、长度等指令。*

多轮指令遵循对许多开发者至关重要——模型需要在深入对话时保持一致性、记住用户先前说过的信息。我们训练 GPT‑4.1 更善于从对话历史消息中提取信息，从而让对话更自然。Scale 的 MultiChallenge 基准是这一能力的有效衡量，GPT‑4.1 比 GPT‑4o 高出 10.5 个百分点。

*在*[MultiChallenge⁠（在新窗口中打开）](https://scale.com/leaderboard/multichallenge)*中，模型在多轮对话中须正确使用来自先前消息的四类信息。*

GPT‑4.1 在 IFEval 上得分 87.4%，而 GPT‑4o 为 81.0%。IFEval 使用含可验证指令的提示词（例如指定内容长度，或避免某些词或格式）。

*在*[IFEval⁠（在新窗口中打开）](https://arxiv.org/abs/2311.07911)*中，模型必须生成符合各种指令的回答。*

更好的指令遵循既让现有应用更可靠，也催生了过去受可靠性拖累的新应用。早期测试者指出 GPT‑4.1 可能更“照字面执行”，因此我们建议在提示词中表达得明确、具体。有关 GPT‑4.1 提示词最佳实践的更多内容，请参阅提示词指南。

## 长上下文

GPT‑4.1、GPT‑4.1 mini 和 GPT‑4.1 nano 最多可处理 100 万 token 的上下文——此前 GPT‑4o 模型为 128,000。100 万 token 超过 8 份完整 React 代码库，因此长上下文非常适合处理大型代码库或大量长文档。

我们训练 GPT‑4.1 在整个 100 万上下文长度上可靠地关注信息。我们还训练它比 GPT‑4o 远更可靠地注意到相关文本，并在长、短上下文长度下忽略干扰项。长上下文理解是法律、编程、客户支持等众多领域应用的关键能力。

下面展示 GPT‑4.1 检索一小段隐藏信息（“针”）的能力，该针被放置在上下文窗口的不同位置。GPT‑4.1 在所有位置、所有上下文长度——直到 100 万 token——都能稳定、准确地取出针。无论相关信息位于输入的什么位置，它都能有效地提取与当前任务有关的细节。

*在我们的内部“草堆找针”评测中，GPT‑4.1、GPT‑4.1 mini 和 GPT‑4.1 nano 都能在长达 1M 的上下文中的任意位置取出针。*

不过，现实世界的任务很少像取出单根明显的“针”这么简单。我们发现用户经常需要模型检索并理解多条信息，并理解这些信息之间的关系。为展示这一能力，我们开源了一项新评测：OpenAI-MRCR（多轮指代消解，Multi-Round Coreference）。

OpenAI-MRCR 测试模型在上下文中找到并区分深藏的多根“针”的能力。评测由用户与助手间合成的多轮对话构成：用户请求某个主题的写作内容，例如“写一首关于貘的诗”或“写一篇关于岩石的博文”。随后我们在上下文中插入两个、四个或八个相同的请求。模型必须检索出与特定实例对应的回复（例如“给我第三首关于貘的诗”）。

难点在于这些请求与上下文其余部分的高度相似——模型很容易被细微差异误导，比如一篇关于貘的短篇小说而非诗，或一首关于青蛙而非貘的诗。我们发现，在 128K token 以内的上下文长度上 GPT‑4.1 优于 GPT‑4o，并且在长达 100 万 token 时仍保持强劲表现。

但该任务依然很难——对先进推理模型也是如此。我们公开[评测数据集⁠（在新窗口中打开）](https://huggingface.co/datasets/openai/mrcr)，以推动对真实世界长上下文检索的进一步研究。

我们同时发布 [Graphwalks⁠（在新窗口中打开）](https://huggingface.co/datasets/openai/graphwalks)，一个用于评估多跳长上下文推理的数据集。许多开发者的长上下文用例需要在上下文内完成多次逻辑跳转，比如写代码时在多个文件之间穿梭，或回答复杂法律问题时交叉参照多份文档。

模型（甚至人类）理论上可以通过通读一遍提示词来解决 OpenAI-MRCR 问题，但 Graphwalks 被设计为需要跨上下文中多个位置进行推理，无法顺序解决。

Graphwalks 在上下文窗口中填充一个由十六进制哈希构成的有向图，然后要求模型从图中一个随机节点开始执行广度优先搜索（BFS），再返回某一深度下的所有节点。GPT‑4.1 在该基准上达到 61.7% 的准确率，与 o1 表现持平，并大幅超过 GPT‑4o。

*在*[Graphwalks⁠（在新窗口中打开）](https://huggingface.co/datasets/openai/graphwalks)*中，模型被要求在一个大型图中从随机节点执行广度优先搜索。*

基准并不能说明全部，我们与 alpha 伙伴合作测试了 GPT‑4.1 在其真实世界长上下文任务上的表现。

## 真实世界示例

[**Thomson Reuters：**⁠（在新窗口中打开）](https://blogs.thomsonreuters.com/en-us/innovation/legal-ai-benchmarking-evaluating-long-context-performance-for-llms) Thomson Reuters 用其面向法律工作的专业级 AI 助手 CoCounsel 测试了 GPT‑4.1。与 GPT‑4o 相比，在其内部长上下文基准上使用 GPT‑4.1 时，多文档审阅准确率提升 17%——这是 CoCounsel 处理涉及多份冗长文档的复杂法律工作流能力的关键指标。他们特别发现，该模型在跨来源保持上下文、准确识别文档间细微关系（如相互冲突的条款或额外的补充语境）方面高度可靠——这些任务对法律分析和决策至关重要。

[**Carlyle**⁠（在新窗口中打开）](https://www.carlyle.com/)**：** Carlyle 使用 GPT‑4.1 在多个冗长文档（包括 PDF、Excel 文件及其他复杂格式）中精确提取细粒度财务数据。根据其内部评估，在从含密集数据的超大文档中检索这项任务上，它比此前表现好 50%，并且是首个成功克服其他可用模型关键局限的模型，包括草堆找针式检索、“迷失在中间”错误以及跨文档多跳推理。

除模型性能与准确率外，开发者还需要响应迅速、能跟上并满足用户需求的模型。我们改进了推理技术栈以缩短首 token 时间，配合提示词缓存（prompt caching）还能进一步降低延迟并节省成本。在我们的初步测试中，GPT‑4.1 在 128,000 token 上下文时首 token 延迟约十五秒，100 万 token 上下文时约一分钟。GPT‑4.1 mini 和 nano 更快，例如 GPT‑4.1 nano 在 128,000 输入 token 的查询中最常能在五秒内返回首个 token。

## 视觉

GPT‑4.1 家族在图像理解上异常出色，其中 GPT‑4.1 mini 尤其代表了显著飞跃，在图像基准上经常胜过 GPT‑4o。

*在*[MMMU⁠（在新窗口中打开）](https://mmmu-benchmark.github.io/)*中，模型回答包含图表、示意图、地图等的题目。（注意：即使图像未包含，许多答案仍可从上下文推断或猜测。）*

*在*[MathVista⁠（在新窗口中打开）](https://mathvista.github.io/)*中，模型求解视觉数学任务。*

## 定价

GPT‑4.1、GPT‑4.1 mini 和 GPT‑4.1 nano 现已向所有开发者开放。

通过对推理系统的效率改进，我们能够以更低价格提供 GPT‑4.1 系列。在中位查询上，GPT‑4.1 比 GPT‑4o 便宜 26%；GPT‑4.1 nano 是我们史上最便宜、最快的模型。对于反复传入相同上下文的查询，我们将这些新模型的提示词缓存折扣提高到 75%（此前为 50%）。最后，长上下文请求除标准按 token 计费外不收取任何额外费用。

## 结语

GPT‑4.1 是 AI 实际应用的重要一步。通过紧密关注真实世界开发者需求——从编程到指令遵循再到长上下文理解——这些模型为构建智能系统和复杂 agentic 应用解锁了新的可能。我们不断被开发者社区的创造力所鼓舞，也期待看到你们用 GPT‑4.1 构建什么。
