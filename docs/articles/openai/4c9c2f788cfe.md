# 将 Kubernetes 扩展到 2,500 个节点

我们[运行](https://blog.openai.com/infrastructure-for-deep-learning/) [Kubernetes](https://kubernetes.io/) 支撑深度学习研究已经两年多。虽然我们最大规模的工作负载直接管理裸云 VM，但 Kubernetes 提供了快速迭代周期、合理的可扩展性以及几乎无样板代码的体验，这对我们大多数实验来说是理想选择。我们目前运行着多个 Kubernetes 集群（部分在云上、部分在物理硬件上），其中最大的一个已被我们推高到超过 2,500 个节点。该集群运行在 Azure 上，由 D15v2 和 NC24 VM 混合组成。

在迈向这一规模的道路上，许多系统组件都出过故障，包括 etcd、Kube master、Docker 镜像拉取、网络、KubeDNS，甚至我们机器的 ARP 缓存。我们认为分享遇到的具体问题及解决方法会有帮助。

## etcd

当集群节点数超过 500 后，我们的研究员开始报告 [kubectl](https://kubernetes.io/docs/reference/kubectl/overview/) 命令行工具频繁超时。我们尝试增加 Kube master 数量（运行 [kube-apiserver](https://kubernetes.io/docs/reference/generated/kube-apiserver/) 的 VM）。这似乎暂时解决了问题，但一旦超过 10 个副本，我们就知道自己在治标不治本（作为对比，[GKE](https://cloud.google.com/kubernetes-engine/) 用单台 32 核 VM 就能服务 500 个节点）。

这让我们强烈怀疑作为 Kube master 核心状态存储的 [etcd](https://github.com/coreos/etcd) 集群。在 [Datadog](https://www.datadoghq.com/) 中我们看到，运行 etcd 副本的 DS15v2 机器写延迟飙升到数百毫秒——尽管每台机器都配有可支持 5,000 IOPS 的 P30 SSD。

用 [fio](https://github.com/axboe/fio) 做性能基准测试后，我们发现 etcd 只能用到约 10% 的可用 IOPS：写延迟为 2ms，而 etcd 做顺序 I/O，因此受延迟限制。

随后我们把每个节点的 etcd 目录移到本地临时磁盘——直连实例的 SSD，而非网络挂载盘。切换到本地盘后写延迟降到 200us，etcd 恢复了健康！

我们的集群一直运行良好，直到节点数约 1,000 时，etcd 的 commit 延迟又变高了。这次我们注意到 kube-apiserver 从 etcd 读取的流量超过 500MB/s。我们部署了 [Prometheus](https://github.com/coreos/kube-prometheus) 监控 apiserver，并设置了 `--audit-log-path` 和 `--audit-log-maxbackup` 参数以在 apiserver 上启用更多日志。这暴露出一批慢查询和对 Events 的 LIST API 的过度调用。

根本原因：[Fluentd](https://www.fluentd.org/) 和 Datadog 监控进程的默认配置，是由集群中每个节点都去查询 apiserver（例如此[问题](https://github.com/DataDog/dd-agent/issues/3381)，现已修复）。我们把这些进程的轮询调得不那么激进，apiserver 的负载便重新稳定下来：

另一个有用的调整是把 Kubernetes Events 存到单独的 etcd 集群，这样 Events 创建量的峰值不会影响主 etcd 实例的性能。做法很简单，把 `--etcd-servers-overrides` 参数设成类似：`--etcd-servers-overrides=/events#https://0.example.com:2381;­https://1.example.com:2381;­https://2.example.com:2381`

超过 1,000 节点后的另一种故障是触碰到 etcd 的硬性存储上限（默认 2GB），导致其停止接受写入。这引发了级联故障：我们所有 Kube 节点健康检查失败，[autoscaler](https://github.com/openai/kubernetes-ec2-autoscaler) 据此认为需要终止所有 worker。我们用 `--quota-backend-bytes` 参数调大了 etcd 上限，并给 autoscaler 加了一条合理性检查：若操作会终止超过 50% 的集群则不动作。

## Kube master

我们把 kube-apiserver、[kube-controller-manager](https://kubernetes.io/docs/reference/generated/kube-controller-manager/) 和 [kube-scheduler](https://kubernetes.io/docs/reference/generated/kube-scheduler/) 进程同机部署。为了实现[高可用](https://en.wikipedia.org/wiki/High-availability_cluster)，我们始终保持至少 2 个 master，并把 `--apiserver-count` 设为运行的 apiserver 数量（否则 Prometheus 监控可能在各实例间混淆）。

我们主要把 Kubernetes 用作批处理调度系统，依赖我们的 [autoscaler](https://github.com/openai/kubernetes-ec2-autoscaler) 动态伸缩集群——这让我们在保持快速迭代低延迟的同时显著降低闲置节点成本。默认的 kube-scheduler 策略是把负载均匀摊到各节点，但我们想要相反的效果：空闲节点才能被终止，大型 [pod](https://kubernetes.io/docs/concepts/workloads/pods/pod/) 也能被快速调度。因此我们改用以下策略：

#### Plain Text

```
1{2"kind" : "Policy",3"apiVersion" : "v1",4"predicates" : [5  {"name" : "GeneralPredicates"},6  {"name" : "MatchInterPodAffinity"},7  {"name" : "NoDiskConflict"},8  {"name" : "NoVolumeZoneConflict"},9  {"name" : "PodToleratesNodeTaints"}10  ],11"priorities" : [12  {"name" : "MostRequestedPriority", "weight" : 1},13  {"name" : "InterPodAffinityPriority", "weight" : 2}14  ]15}
```

我们大量使用 [KubeDNS](https://github.com/kubernetes/kubernetes/tree/master/cluster/addons/dns) 做服务发现，但新调度策略上线后不久它开始出现可靠性问题。我们发现故障只发生在 KubeDNS 的某些 pod 上。在新调度策略下，一些机器最终跑了 10 个以上的 KubeDNS 副本，形成热点，而每台 Azure VM 对外部域名查询有约 200QPS 的限制，我们已经超了。

解决办法是给 KubeDNS pod 加一条[反亲和规则](https://kubernetes.io/docs/concepts/configuration/assign-pod-node/#affinity-and-anti-affinity)：

#### Plain Text

```
1affinity:2 podAntiAffinity:3   requiredDuringSchedulingIgnoredDuringExecution:4   - weight: 1005     labelSelector:6       matchExpressions:7       - key: k8s-app8         operator: In9         values:10         - kube-dns11     topologyKey: kubernetes.io/hostname
```

## Docker 镜像拉取

我们的 [Dota](https://blog.openai.com/more-on-dota-2/) 项目最初在 Kubernetes 上起步。随着规模增长，我们注意到新加入的 Kubernetes 节点上，pod 常常长时间处于 [Pending](https://kubernetes.io/docs/tasks/debug-application-cluster/debug-pod-replication-controller/#my-pod-stays-pending) 状态。游戏镜像约 17GB，在新节点上往往要拉 30 分钟，所以 Dota 容器 Pending 一段时间可以理解——但其他容器也是如此。深入排查后，我们发现 [kubelet](https://kubernetes.io/docs/admin/kubelet) 有个 `--serialize-image-pulls` 参数，默认为 `true`，意味着 Dota 的镜像拉取会阻塞所有其他镜像。改成 `false` 需要把 Docker 从 AUFS 切到 overlay2。为进一步加速拉取，我们还像对 etcd 机器那样，把 Docker root 移到了实例直连 SSD。

即使优化了拉取速度，我们仍看到 pod 启动失败并伴随一条隐晦报错：`rpc error: code = 2 desc = net/http: request canceled`。kubelet 和 Docker 日志也显示镜像拉取因缺乏进展而被取消。我们追溯到根因：大镜像拉取/解压耗时过长，或存在很长的拉取队列。对此我们把 kubelet 的 `--image-pull-progress-deadline` 设为 30 分钟，并把 Docker daemon 的 `max-concurrent-downloads` 设为 10。（第二个选项并未加速大镜像的解压，但允许队列中的镜像并行拉取。）

最后一个 Docker 拉取问题出在 Google Container Registry。默认情况下，kubelet 会从 `gcr.io` 拉一个特殊镜像（由 `--pod-infra-container-image` 参数控制），启动任何新容器时都会用到它。如果这次拉取因任何原因失败——比如超出[配额](https://github.com/kubernetes/kubernetes/issues/50568)——该节点就无法启动任何容器。由于我们的节点经 NAT 访问 `gcr.io` 而没有独立公网 IP，撞上这一每 IP 配额限制的概率很高。解决方法很简单：用 `docker image save -o /opt/preloaded_docker_images.tar` 和 `docker image load -i /opt/preloaded_docker_images.tar`，把该 Docker 镜像预置进 Kubernetes worker 的机器镜像。为提升性能，我们还对一批常用的 OpenAI 内部镜像（比如 Dota 镜像）白名单做了同样处理。

## 网络

随着实验变大，它们也日益成为严重依赖网络的复杂分布式系统。我们刚开始跑分布式实验时就立刻发现网络配置不佳。机器之间直连带宽可达 10-15Gbit/s，而使用 Flannel 的 Kube pod 最高只有约 2Gbit/s。Machine Zone 的[公开基准](http://machinezone.github.io/research/networking-solutions-for-kubernetes/) 显示类似数字，说明问题多半不是配置不当，而是我们环境的某种固有开销。（相比之下，Flannel 在我们的物理机上没有增加这一开销。）

作为变通，用户可以加两个设置在自己的 pod 上禁用 Flannel：`hostNetwork: true` 和 `dnsPolicy: ClusterFirstWithHostNet`。（不过操作前请先阅读 Kubernetes 文档中的[警告](https://kubernetes.io/docs/concepts/configuration/overview/)。）

## ARP 缓存

尽管调优了 DNS，我们仍看到间歇性的 DNS 解析问题。某天一位工程师报告，对他的 Redis 服务器执行 `nc -v` 要 30 多秒才打印连接建立。我们追踪到内核 ARP 协议栈。最初调查 Redis pod 所在主机时发现网络严重异常：任何端口的通信都会卡住好几秒，本地 [dnsmasq](https://en.wikipedia.org/wiki/Dnsmasq) 守护进程解析不出任何 DNS 名，[`dig`](https://en.wikipedia.org/wiki/Dig_(command)) 只打印一条隐晦错误：`socket.c:1915: internal_send: 127.0.0.1#53: Invalid argument`。[dmesg](https://en.wikipedia.org/wiki/Dmesg) 日志更有信息量：`neighbor table overflow!`——ARP 缓存耗尽了空间。ARP 用于把网络地址（如 IPv4 地址）映射到物理地址（如 MAC 地址）。所幸这很容易修复，在 `/etc/sysctl.conf` 中设置几个选项即可：

#### Plain Text

```
1net.ipv4.neigh.default.gc_thresh1 = 800002net.ipv4.neigh.default.gc_thresh2 = 900003net.ipv4.neigh.default.gc_thresh3 = 100000
```

在 HPC 集群中调整这些设置很常见，而在 Kubernetes 集群中尤其相关：每个 pod 都有自己的 IP 地址，都会占用 ARP 缓存空间。
