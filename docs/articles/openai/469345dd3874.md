# 工作区 agent

理解、构建并使用 ChatGPT 中处理可重复工作的 agent。

大多数 ChatGPT 用户已经知道如何用 AI 处理一次性任务——起草、总结、头脑风暴或回答问题。AI 应用的下一阶段更广泛、更深入地嵌入日常工作。AI 不再只是帮助孤立的瞬间，而是越来越多地用于支持可重复的工作流——这些工作流依赖共享系统、标准化的交接、一致的输出，以及时机、准确性和流程等现实约束。

这正是 ChatGPT 中**工作区 agent（workspace agents）**的用武之地。它们为可重复的工作流而设计——那些你本来要手动完成、每次都重新解释步骤、在各个工具之间复制信息的工作。在我们的[博客文章](https://openai.com/index/introducing-workspace-agents-in-chatgpt/)中了解更多关于工作区 agent 的内容。

如果你是 agent 构建新手，我们先聚焦核心概念，这样当你开始构建时，就知道如何配置你的工作区 agent 以获得稳定的结果。

## 什么是 agent？

广义上讲，agent 是一个执行任务的系统，包含三个组件：一个触发器、一个可包含专门技能的流程，以及它可以连接的工具或系统。

| **组件** | **说明** | **示例** |
| --- | --- | --- |
| **触发器** | 什么启动 agent | 一个排程（“每个工作日 9 点”）或一次手动运行（“立即运行”）。 |
| **流程与技能** | agent 按什么步骤完成任务、达到你的预期 | 审阅输入、检查缺失信息、起草输出、交接或执行下一个动作。 |
| **工具与系统** | agent 可以用来收集信息的获批准的工具与集成，若允许还可执行动作 | Slack、CRM、内部文档、工单系统或共享文档 |

当工作具备以下特征时，agent 最有用：

- **可重复：** 同样的任务经常出现
- **有结构：** 输出有清晰的格式（这样你能判断 agent 做得好不好）
- **基于时间或事件驱动：** 按节奏运行，或由事件触发
- **依赖工具：** 需要读写你团队使用的系统

对于开放性思考、头脑风暴或探索性写作，普通聊天往往更合适——尤其是一次性任务。

agent 也不同于你过去可能构建过的传统 API 工作流。其他工具中的传统工作流往往是**确定性的**：每一步都被明确定义，除非你更改逻辑，系统每次都走相同的路径。agent 更偏向**概率性**。它们仍然在指令、工具和护栏之内运作，但会用模型来解读上下文、做出有边界的决策，并调整推进工作的方式。

## agent 的构造

设计工作区 agent 一个有用的方法是把它拆开。想象你把工作交给一个人之前会澄清什么：他负责什么、什么时候开始、什么情况应该让他暂停或停止、他能用哪些工具和信息、应遵循什么流程、必须守住哪些规则。

agent 可能需要访问插件。了解更多关于 [ChatGPT 插件](https://openai.com/business/plugins/)的信息。

下面是一些 agent 拆解示例：

|  | **营销活动总结 agent** | **产品反馈分诊 agent** | **销售管道总结 agent** |
| --- | --- | --- | --- |
| **目标：** agent 的总体目标是什么？ | 分析活动表现并推荐优化 | 汇总新的产品反馈并路由给合适的负责人 | 监控管道变化并标出风险与机会 |
| **触发器：** 什么启动工作？ | 每周一上午 10 点 | Slack 中的表单提交 | 每个工作日上午 8 点 |
| **流程：** 应遵循什么步骤？ | 拉取 KPI、识别趋势、起草总结、提出下一步、指派负责人 | 审阅反馈、归并相关项、总结关键主题、建议跟进负责人 | 审阅管道、标记风险、提出下一步 |
| **工具：** 需要访问哪些系统或应用？ | 分析工具和一个共享总结文档 | Slack、工单系统和一个总结文档 | CRM、邮件或 Slack，以及一个管道跟踪表 |
| **治理：** 需要哪些控制？何时应停止并升级？ | 输出建议草稿；预算变更前需审批 | 创建工单草稿；升级高优先级问题；提交前需审批 | 输出洞察与建议草稿；通知负责人；未经批准不直接对外联系 |

## agent 工作流示例

以下示例可以视为 **agent 工作流模式**：跨团队、跨职能反复出现的常见工作模式。每一个代表 agent 可以执行的一类核心工作流。具体的工具、数据和输出可能不同，但底层模式保持一致。

| **工作流** | **运作方式** | **示例用例** |
| --- | --- | --- |
| **简报**：从多处拉取信息、提炼，打包成可用于决策的东西。 | 1) 收集输入 2) 比较并提取关键信号 3) 面向受众做摘要 4) 以文档、备忘录或简报分享 | **销售：** 用 CRM、通话、Slack 和新闻构建账户简报。**市场：** 从分析、社交和文档汇编活动或竞品复盘。**高管：** 生成带建议的每日行业简报。 |
| **分诊与路由**：处理进入的事项，确保它们到达正确的下一步。 | 1) 审阅进入事项 2) 分类与定优先级 3) 路由或创建下一步交付物 4) 通知请求方和负责人 | **支持：** 把反馈变成缺陷、功能请求或跟进事项。**IT/运营：** 处理 Slack 中的内部请求并按紧急程度路由。**招聘：** 初筛进来的候选人并移入正确路径。 |
| **分析与建议**：解读数据或证据、形成观点，并转化为第一份交付物。 | 1) 拉取源数据 2) 分析模式、缺口与权衡 3) 形成建议 4) 起草备忘录、演示、表格或邮件 | **财务：** 对账预算与实际并起草经理备忘录。**产品/研究：** 分析用户反馈并提出优先级。**采购：** 比较供应商报价、制作决策矩阵、起草采购订单邮件。 |
| **内容创建**：创建或更新内容，并为特定受众或渠道定制。 | 1) 从笔记或源材料生成初稿 2) 编辑语气与准确性 3) 按受众与渠道定制 4) 发布或发送 | **市场：** 把简报变成活动素材并传阅征求意见。**经理：** 把笔记变成入职计划或培训模块。**销售：** 撰写跟进邮件、QBR 总结或干系人回顾。 |
| **规划与协调**：把目标变成排期工作和系统更新。 | 1) 基于约束制定计划 2) 检查依赖与可用性 3) 执行动作或准备执行 4) 更新系统并通知相关人员 | **PM/幕僚长：** 安排工作块、约会、更新跟踪器。**活动：** 协调外出团建、报名或差旅计划。**行政：** 管理表单、提醒、订单、预订和跟进。 |

## 在 ChatGPT 中使用 agent

你可能从使用组织已经构建好的 agent 开始。先理解该 agent 擅长做什么——它支持哪些任务、依赖哪些工具、产出什么类型的结果。

先用几个低风险请求观察它的行为。先试简单的输入，然后审阅结果，理解它处理任务的方式。

请记住，即使是很完善的 agent 仍然需要人类判断。往往只有你了解更大的背景、任务的分量，以及一个好的答案应该长什么样。

## 在 ChatGPT 中构建你自己的 agent

理解了基础知识并找到一个强用例后，你可以开始构建自己的工作区 agent。你可能已经在 ChatGPT 里建好了技能（skills）。工作区 agent 可以在其指令中使用技能。

*注：在 ChatGPT Enterprise 中，构建 agent 的权限由你的工作区管理员控制。*

- **从朴素语言开始：** 在 agent 构建器对话中，描述 agent 要做的工作、成功的结果长什么样，以及它需要遵守的约束。构建器能把这些转化为步骤明确的清晰工作流，你可以继续在对话中打磨，也可以直接编辑工作流和指令。
- **选择工具与连接器：** 挑选 agent 完成工作流可使用的获批准应用。你也可以描述 agent 需要访问的系统，构建器会引导你添加并完成身份验证。
- **选择触发器：** 决定 agent 何时运行。agent 触发器是启动 agent 运行的事件。工作区 agent 可以由人触发（有人请它做某事），也可以由排程触发（在设定时间运行）。你可以用 agent 构建器对话以朴素语言设置触发器。
- **添加护栏：** 为敏感动作设定边界、必需的审批，以及人在回路的检查点。你可以直接把这些加进 agent 构建器对话，构建器会相应修改指令。

## 用预览测试你的 agent

Agent 构建最好以迭代方式进行。在 ChatGPT 中，构建器就是这个循环的一部分。测试 agent 时，利用对话理解发生了什么、发现问题、逐步打磨指令。

从几个贴近现实的例子开始，既包括直接的请求，也包括上下文缺失或有歧义的更乱的请求。这能帮你观察 agent 的行为，以及哪里需要更清晰的指令或护栏。

## 编辑你的 agent

测试 agent 时，第一版不完美是预期内的。当感觉不对时，有两种有效的改进方式。

- **直接更新指令：** 在编辑器里做小而具体的修改，例如澄清某个步骤、调整输出格式或添加一个约束。
- **用自然语言辅导：** 问题不太明确时，用构建器对话来一起梳理。你可以指出它遗漏了什么、问开放式问题，或让它解释自己的推理，从而暴露指令中的缺口。

修改之后再测试一次，确认更新有效。

## 把 agent 推广到你的团队

工作区 agent 为共享的、可重复的工作而设计。[分享一个 agent](https://openai.com/business/workspace-agents/) 让你的团队获得完成某项任务的一致方式，而不必每次重新发明流程。

分享 agent 时，明确说明它的用途。在描述中写清它处理的任务、何时使用、要提供什么输入、预期什么样的输出。当共享 agent 绑定到团队已经理解的具体、重复性工作流时，效果最好。附上一两个示例提示词也能给别人一个清晰的起点，让采纳更顺畅。

请记住，工作区管理员通过基于角色的访问控制（RBAC）管理连接器和功能权限，因此同事可能需要相应权限，agent 才能使用 Slack、Gmail 或其他工具等系统。
