# 深入 Codex 沙箱

Codex 如何在你的机器上、在你设定的限制内运行命令。

作者：Michael Bolin，技术团队成员

在 OpenAI，我们在保护 agent 时采取[纵深防御](https://en.wikipedia.org/wiki/Defense_in_depth_(computing))的思路。我们在训练和对齐上的投入是这项工作的根基，同时我们也会在 agent harness [Codex](https://github.com/openai/codex) 中实现一些功能，以提供额外的防护。由于 Codex 最常做（也最有潜在风险）的事情之一就是在你的计算机上运行命令，我们构建了 *Codex sandbox*，让 Codex 能在你现有的环境中工作，并受你掌控的文件系统与网络限制的约束。

一个 [https://en.wikipedia.org/wiki/Sandbox_(computer_security](https://en.wikipedia.org/wiki/Sandbox_(computer_security))[*sandbox*](https://en.wikipedia.org/wiki/Sandbox_(computer_security)) 会限制程序在运行时可以访问哪些内容。对于整理照片这类任务，你可以把 Codex sandbox 配置成允许命令读取并修改 `~/Pictures` 里的文件，同时封禁网络访问以防上传。对于代码审查，你可以允许访问在线文档，同时让源文件保持只读。用户通过[https://learn.chatgpt.com/docs/permissions](https://learn.chatgpt.com/docs/permissions)[*permission profiles*](https://learn.chatgpt.com/docs/permissions) 来配置 Codex sandbox，它定义了 Codex 会话的文件系统与网络限制。

本文先讲 Codex 沙箱默认值背后的取舍，然后解释沙箱的设计，以及 harness 如何用它来运行命令。我们会展示终端用户和企业如何按各自的需求调整权限，以及开发者如何在自己的工具里复用这个沙箱。最后，我们来看看这些限制在 macOS、Linux 和 Windows 上分别是如何强制执行的。

## 选择沙箱的边界

在 Codex 中，我们的理念是为沙箱设定保守的默认值，同时仍然让它能完成有意义的工作。例如，当工作区根目录是一个 Git 仓库时，内置的 `:workspace` 权限配置会：

- **允许在工作区内写入，同时把 **`**.git**`** 和 **`**.codex**`** 这样的目录保持为只读。** 这样 Codex 就能直接修改源代码，不必为每一处改动都申请权限，同时又阻止它直接改动 `.codex/config.toml` 或 `.git/hooks` 下的 Git hook。
- **允许广泛的文件系统读取，但受限于用户现有的操作系统权限。** 编译器、运行时和构建工具都依赖仓库之外的 SDK、库和配置。把读取范围限制在工作区内，会破坏许多普通工作流。代价是机器上其他位置的敏感文件也可能保持可读（例如包含 API key 的配置文件）。
- **禁用网络访问。** 这会阻止向外部服务直接上传，包括试图把命令能读到的数据外泄出去的行为。它同时也拦下了下载依赖这类正当操作，这类操作需要额外授权。

这些限制挡住了很大一类不良行为，但有害操作仍然可能发生。例如，agent 可以把恶意代码注入本地已安装的包，比如 `node_modules/prettier`。由于 `node_modules` 通常被 Git 忽略，这样的改动可能不会出现在 `git status` 里。如果用户的编辑器在保存时调用的正是那份 Prettier，那么仅仅保存一个文件就可能在 Codex 沙箱之外执行恶意代码。这正是我们采取纵深防御的原因：沙箱限制命令能访问什么，而训练与对齐帮助模型按照用户的意图来使用这些访问权限。

关于如何调整沙箱权限，以及在企业环境中把它们与其他防护措施结合使用，请参阅 [Codex security cookbook](https://learn.chatgpt.com/docs/enterprise/security-cookbook)。

## 设计沙箱

虚拟机和 [containers](https://opencontainers.org/) 是两种常见的沙箱实现机制，但 Codex 沙箱走的是另一条路。Codex 不把计算搬到独立环境里去换取隔离，而是使用各平台自身的沙箱能力，约束运行在用户现有环境中的命令。

对许多开发者来说，自己的笔记本电脑就是一个量身定制、可以随时改动的开发环境。要在 Docker 容器里复现这个环境得花不少功夫，而且有些工作流仍然依赖只在宿主机上运行的工具。

例如，假设你要在 Mac 上用 Codex 开发一个 iOS 应用。如果你决定把 Codex 放进 Docker 里运行来做沙箱隔离，Codex 就无法运行由 Mac 原生可执行文件组成的 iOS 构建工具链，也无法启动 iPhone 模拟器来运行代码。基于 Docker 的工作流可以把构建和模拟器操作委派给 Mac 宿主机，但这些操作会在容器的沙箱之外执行，因而需要自己的一套限制。对 Codex 来说，我们更愿意把问题简化：在操作系统级的沙箱上重投入，让 Codex 能运行在最适合当前任务的环境里。

harness 通过一个在 macOS、Windows 和 Linux 上通用的 API 来暴露这些操作系统级的沙箱机制。这个 API 接收一条命令和一个权限配置。如果权限配置只允许有限的网络访问，调用方必须提供网络代理来强制执行这些限制：

#### Python

```
1# This is a simplified version of the actual API.2def spawn_command_under_sandbox(3    program_and_args: list[str],4    cwd: Path,5    env: dict[str, str],6    permission_profile: PermissionProfile,7    network_proxy: NetworkProxy | None,8) -> Child:
```

这个函数在沙箱中启动进程，并返回一个 `Child` 句柄，harness 可以用它等待进程结束。每个子进程都会继承父进程的沙箱约束，因此这些限制会贯穿命令所发起的整棵进程树，连比原始进程存活更久的后代进程也不例外。

下图展示了这些部件如何串联起来，从配置一直到运行一条受沙箱约束的命令。后续各节会逐一解释每个阶段。

## harness 如何利用沙箱

正如[Unrolling the Codex Agent Loop](https://openai.com/index/unrolling-the-codex-agent-loop/) 中所解释的，Codex harness 负责执行模型生成的工具调用。对于编码任务，最常用的工具是 *shell tool*，它运行命令的方式与用户在 Bash 这类交互式 shell 中执行命令差不多。这里我们以[一次性](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/core/src/tools/handlers/unified_exec/exec_command.rs#L483-L512)[`exec_command`](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/core/src/tools/handlers/unified_exec/exec_command.rs#L483-L512)[ shell tool](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/core/src/tools/handlers/unified_exec/exec_command.rs#L483-L512) 为例，说明 harness 如何借助沙箱实现所需的防护。

下面是一个简化版本，展示 Codex harness 在*没有沙箱*的情况下会如何执行 `exec_command` 工具调用：

#### Python

```
1# Illustrative implementation of the exec_command tool call.23class ExecCommandToolCall:4    cmd: str5    workdir: str | None = None6    shell: str | None = None7    login: bool = True8    timeout_ms: int = 10_00091011def perform_exec_command(tool_call: ExecCommandToolCall):12    program_and_args = [13        tool_call.shell or os.environ.get("SHELL") or "/bin/sh",14        "-lc" if tool_call.login else "-c",15        tool_call.cmd,16    ]17    child = subprocess.Popen(18        program_and_args,19        # workdir defaults to the turn's cwd, assumed here to be the process cwd.20        cwd=Path(tool_call.workdir or ".").absolute(),21        stdout=subprocess.PIPE,22        stderr=subprocess.STDOUT,23    )24    output, exit_code = collect_output(child, timeout_ms=tool_call.timeout_ms)25    return {"output": output, "exit_code": exit_code}
```

为了让命令受沙箱约束，harness 把对 `subprocess.Popen()` 的调用替换成 `spawn_command_under_sandbox()`。harness 会提供权限配置，需要时还会提供网络代理：

#### Python

```
1# Honoring the exec_command tool call while enforcing sandbox constraints.23def perform_exec_command_with_sandboxing(4    tool_call: ExecCommandToolCall,5    permission_profile: PermissionProfile,6    network_proxy: NetworkProxy | None,7):8    # ...build program_and_args as in the previous example...9    child = spawn_command_under_sandbox(10        program_and_args=program_and_args,11        cwd=Path(tool_call.workdir or ".").absolute(),12        env=os.environ.copy(),13        permission_profile=permission_profile,14        network_proxy=network_proxy,15    )16    output, exit_code = collect_output(child, timeout_ms=tool_call.timeout_ms)17    return {"output": output, "exit_code": exit_code}
```

`exec_command` 工具还允许模型为单条命令请求不同的权限，但由 harness 决定是否批准该请求：

#### Python

```
1class ExecCommandToolCall:2    # ...command-related fields...34    # Per-command sandbox override. Defaults to "use_default".5    sandbox_permissions: Literal[6        "use_default",7        "with_additional_permissions",8        "require_escalated",9    ] = "use_default"1011    # User-facing approval question; only for "require_escalated".12    justification: str | None = None1314    # Expand network or filesystem access; only for "with_additional_permissions".15    # AdditionalPermissions supports fine-grained options.16    additional_permissions: AdditionalPermissions | None = None
```

当指定 `use_default` 时，harness 使用该轮次的默认沙箱配置。`with_additional_permissions` 请求在沙箱内部扩大访问范围，而 `require_escalated` 请求在沙箱之外执行。harness 会在执行命令之前根据用户的偏好评估该请求。（例如，Codex 可能直接询问用户，也可能把请求转给 [auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review)。）如果执行获得授权，Codex 会把相应的 `permission_profile` 和 `network_proxy` 连同原始 `ExecCommandToolCall` 中的命令参数一起传给 `perform_exec_command_with_sandboxing()`。

shell tool 是 `spawn_command_under_sandbox()` 的主要使用方，harness 也会把它的沙箱基础设施复用到读取和修改本地文件等操作上。这种复用不止于 harness 本身：`codex sandbox` 命令让你能把沙箱化的命令执行引入自己的工具，我们稍后就会看到。接下来，先看看权限配置是如何定义的。

## 配置沙箱

命名的权限配置让你可以跨项目复用同一套文件系统与网络限制。你可以在 `config.toml` 的 `[permissions]` 下定义自己的配置。例如，下面定义了一个名为 `dev` 的配置，它[扩展](https://learn.chatgpt.com/docs/permissions#extend-a-profile)了内置的 `:workspace` 配置：

#### TOML

```
1# Use the dev profile by default.2default_permissions = "dev"34[permissions.dev]5# This is displayed when /permissions is run in the Codex CLI.6description = "Development with extra read-only protections."78# A profile can be derived from an existing profile.9# Profiles starting with ":" are provided by Codex.10extends = ":workspace"1112[permissions.dev.filesystem]13"~/build-cache" = "write"1415[permissions.dev.filesystem.":workspace_roots"]16".devcontainer" = "read"17".vscode" = "read"18"**/*.env" = "deny"19"secrets" = "deny"
```

`dev` 配置增加了对 `~/build-cache` 的写入权限，并对工作区中的文件施加了额外限制。文件系统条目可以授予只读访问（`read`）、授予读写访问（`write`），或者完全禁止访问（`deny`）。

`:workspace_roots` 表让你针对相对于项目工作区根目录的路径定义规则。默认情况下，Codex CLI 把自己的工作目录当作唯一的工作区根目录，而 ChatGPT 桌面应用则使用项目的源代码文件夹。Codex 会把每条规则应用到每一个根目录上，所以 `dev` 里的 `.vscode` 条目会让每个根目录下的 `.vscode` 目录都变成只读。

除了自己的规则，`dev` 还从 `:workspace` 继承了以下防护：

#### TOML

```
1[permissions.":workspace".filesystem.":workspace_roots"]2".agents" = "read"3".aws" = "read"4".codex" = "read"5".git" = "read"
```

### 网络权限

在为 Codex 中的沙箱配置网络时，大致有三种选择：

- 禁用所有网络访问（`:workspace` 配置的默认值）
- 启用完整的直接网络访问（`:danger-full-access` 配置的默认值）
- 把网络访问限制到代理上，由代理依据权限配置决定放行什么

要让 `dev` 获得直接网络访问，在 `config.toml` 顶层设置 `permissions.dev.network.enabled = true`。在网络代理关闭时，这会授予完整的网络访问。

要把 `dev` 限制到一组域名，启用网络代理并配置它的域名规则：

#### TOML

```
1[permissions.dev.network]2enabled = true34[permissions.dev.network.domains]5"*.openai.com" = "allow"6# Allow requests to local services by hostname or by IPv4/IPv6 loopback address.7"localhost" = "allow"8"127.0.0.1" = "allow"9"::1" = "allow"10"evil.example" = "deny"1112[features]13# If neither local config nor managed requirements enable the proxy,14# this profile allows direct network access; domain rules are not enforced.15network_proxy = true
```

域名规则支持精确名称和通配符模式，显式的 deny 规则优先于 allow 规则。对其他域名的请求需要审批，或者直接被阻断，如下文「网络代理」一节所述。

### 分层配置与限制执行

单个用户可以配置对多个项目生效的默认值，并针对某个特定的受信任项目覆盖这些默认值。企业管理员可能还想为自己的用户配置默认值，并限定这些用户可以改动哪些设置。Codex 通过分层配置和托管要求同时支持这两点。

如[配置优先级](https://learn.chatgpt.com/docs/config-file/config-basic#configuration-precedence)所述，Codex 会合并多个 `config.toml` 文件里的设置。表会递归合并，值冲突时优先级更高的来源获胜。数组则整体替换。

这也是权限配置用表来表示文件系统路径和网络域名的原因。团队可以在自己的配置里增加或覆盖单条条目，同时自动继承组织基础配置中其他所有条目的改动：

#### TOML

```
1[permissions.dev.filesystem.":workspace_roots"]2".idea" = "read"34[permissions.dev.network.domains]5"example.com" = "allow"
```

管理员还可以通过 `requirements.toml` 提供[托管要求](https://learn.chatgpt.com/docs/enterprise/managed-configuration)，以约束用户的配置选择。这些要求可以来自多个来源，包括系统文件和云端下发的策略。一个常见用途是设置 `allowed_permission_profiles`，约束企业用户可选的权限配置集合。例如，管理员可以指定这样的云端要求：

#### TOML

```
1default_permissions = ":read-only"23[allowed_permission_profiles]4":read-only" = true5":danger-full-access" = false
```

云端要求会优先于 `/etc/codex/requirements.toml` 里的系统要求文件，因此该文件中的条目无法覆盖上面显式的 `":danger-full-access" = false`。`:workspace` 未作规定，就允许另一个要求层来提供该条目。条目为 `false` 或在最终合并表中缺失的配置，都是不可用的。

这种分离让组织能够强制执行限制，同时让用户在这些限制之内调整自己的配置。最终得到的权限配置既可以由 harness 使用，也可以直接应用在一条命令上，我们接下来就会看到。

## 使用 `codex sandbox` 命令

Codex CLI 提供 `sandbox` 命令，方便在 Codex 配置里定义的权限配置下运行任意命令。它常被用来测试某个配置，确认沙箱确实拦住了它本该拦住的行为。

例如，下面这条命令试图把 VS Code 配置成在保存时运行一个恶意的自动格式化工具。假设 `.vscode` 已经存在，上面定义的 `dev` 配置应当阻止这次写入，因为该目录是只读的（`codex sandbox` 默认把 `cwd` 当作工作区根目录）：

#### Bash

```
1codex sandbox --permission-profile dev -- \2  bash -c 'cat > .vscode/settings.json' <<'JSON'3{4  "prettier.prettierPath": "./node_modules/evil-prettier",5  "[typescript]": {6    "editor.defaultFormatter": "esbenp.prettier-vscode",7    "editor.formatOnSave": true8  }9}10JSON
```

在 macOS 上，它确实会失败，报错如下：

#### Plain text

```
1bash: .vscode/settings.json: Operation not permitted
```

`codex sandbox` 命令让 Codex 的沙箱机制可以脱离 agent 会话独立使用。你可以用同样的配置语言和平台特有的强制手段，来约束自己工具启动的命令。

### 示例：为 MCP server 加上沙箱

对于在 `config.toml` 中配置的 stdio MCP server，Codex harness 不会尝试对启动该 server 的命令做沙箱隔离。Codex 无法可靠地推断这个 server 需要哪些文件或网络服务，套用默认的沙箱配置可能会破坏一份原本有效的配置。

例如，为配合 Codex 使用，配置 [`@modelcontextprotocol/server-memory`](https://www.npmjs.com/package/@modelcontextprotocol/server-memory) MCP server 的标准做法如下：

#### TOML

```
1[mcp_servers.memory]2command = "npx"3args = [4  "-y",5  "@modelcontextprotocol/server-memory@1.0.0"6]78[mcp_servers.memory.env]9MEMORY_FILE_PATH = "~/mcp-data/memory.jsonl"
```

由于这条 `npx` 命令在无沙箱的情况下运行，它可以以运行 Codex 的用户的同等权限写文件、发网络请求，这过于宽松了。为了把它锁住，我们可以定义一个名为 `memory-mcp` 的权限配置，然后用 `codex sandbox --permission-profile memory-mcp` 把原来的 `npx` 命令包起来，以限制该 server 能往哪里写，并阻止它访问网络：

#### TOML

```
1[permissions.memory-mcp.filesystem]2# Allow broad reads for Node.js/npm dependencies and configuration.3":root" = "read"4"~/.npm" = "write"5"~/mcp-data" = "write"67[permissions.memory-mcp.network]8enabled = false910[mcp_servers.memory]11command = "codex"12args = [13  "sandbox",14  "--permission-profile",15  "memory-mcp",16  "--",17  "npx",18  "--offline",19  "@modelcontextprotocol/server-memory@1.0.0"20]2122[mcp_servers.memory.env]23MEMORY_FILE_PATH = "~/mcp-data/memory.jsonl"
```

在启动 server 之前，先创建它的数据目录，并用固定版本的包填充 npm 缓存。这样 `npx --offline` 就能在一个禁用网络访问的配置下启动该 server：

#### Bash

```
1# The sandbox can write to this folder, but it cannot create it.2mkdir -p ~/mcp-data34# Installing the MCP server requires network access.5npx -y --package=@modelcontextprotocol/server-memory@1.0.0 -c true
```

包一旦进入缓存，Codex 就能在没有网络访问的情况下启动 memory server，写入范围仅限于 npm 缓存和该 server 的数据目录。

## Codex 沙箱的实现

沙箱实现把权限配置转换成由操作系统强制执行的限制。网络代理的核心请求处理与策略逻辑在三大操作系统之间是共用的，而代理的搭建以及与沙箱的集成则因操作系统而异。我们先看共用的代理，然后依次看 macOS、Linux 和 Windows 上的实现。

### 网络代理

为了强制执行权限配置中的网络限制，harness 会启动一个网络代理，并把沙箱配置成允许连接到它，同时阻断到外部主机的直接连接。代理会依据配置中的域名规则检查每个请求，决定是否转发。

在 Codex 仓库中，网络代理实现在 [codex-network-proxy](https://github.com/openai/codex/blob/main/codex-rs/network-proxy/README.md) crate 里，harness 把它当作库来使用，它也可以被构建成[独立的命令行程序](https://github.com/openai/codex/blob/b6130e72f3e4b360f7a3bf97ea62d0eeeb39ffca/codex-rs/network-proxy/Cargo.toml#L12-L14)。启用时，`codex-network-proxy` 默认会同时启动一个 HTTP 代理和一个 SOCKS5 代理。这些代理地址通过环境变量传递给沙箱启动的进程。除了注入 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 这类标准环境变量之外，还会注入一批广为人知的[应用专属环境变量](https://github.com/openai/codex/blob/bd274564e1b1b3febb3886d274e6d97c2a3d275e/codex-rs/network-proxy/src/proxy.rs#L790-L813)（例如 `PIP_PROXY`）。必须承认，并非所有程序都遵循这些环境变量。如果某个程序尝试直接连接外部主机，操作系统的沙箱限制会拦住它，具体见下文各平台相关小节。

网络代理负责实现权限配置中定义的网络限制。例如，前面展示的 `dev` 配置允许请求 `*.openai.com`，并显式拒绝请求 `evil.example`。当请求的目标域名既不匹配 allow 规则也不匹配 deny 规则时，代理可以挂起该请求，转交给 harness 请求批准。与 shell 命令的例子一样，Codex 可能直接询问用户，也可能把请求转给 [auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review)。收到决定后，代理要么放行请求，要么以错误响应拒绝它。

这里的顺序很重要，因为即便是一次 DNS 查询，也可能泄露编码在主机名里的信息。因此代理只有在判定请求被允许或已获批准之后，才会去解析所请求的主机名。需要注意的是，宽泛的通配符规则或对 DNS 服务的访问，仍然可能让基于 DNS 的数据外泄成为可能。

### macOS

在 macOS 上，Codex 使用 [Seatbelt](https://theapplewiki.com/wiki/Dev:Seatbelt)，这是 Apple 由内核强制执行的沙箱机制。Seatbelt 策略用 Sandbox Profile Language（SBPL）编写，这是一种基于 Scheme、用来表达沙箱限制的语言。Codex 通过 macOS 的 `/usr/bin/sandbox-exec` 命令调用 Seatbelt。和 `codex sandbox` 一样，它接收描述沙箱的选项，后面跟着要运行的命令：

#### Bash

```
1sandbox-exec -p PROFILE [-Dkey=value]* -- PROG ARGS...
```

`PROFILE` 是一段 SBPL 字符串，其中包含配置沙箱的条目。例如，下面这段 SBPL 让 `/dev/null` 和 `/dev/zero` 在该沙箱策略下可读可写：

#### Scheme

```
1(allow file-read* file-test-existence file-write-data2  (literal "/dev/null")3  (literal "/dev/zero"))
```

当一次沙箱调用启用了网络代理时，会向该策略注入类似下面的规则，把连接限制到相应的本地端口：

#### Scheme

```
1; local HTTP proxy launched by Codex2(allow network-outbound (remote ip "localhost:3128"))34; local SOCKS proxy launched by Codex5(allow network-outbound (remote ip "localhost:8081"))
```

Codex 的基础策略以 `(deny default)` 开头，因此除非显式允许，对外连接始终保持阻断。

最后，SBPL 里可以使用 `(param)` 形式的占位符：

#### Scheme

```
1; Pass -DWRITABLE_ROOT_0=/path/to/dir to specify a folder that cannot be removed.2(deny file-write-unlink3  (require-all4    (literal (param "WRITABLE_ROOT_0"))5    (vnode-type DIRECTORY)))
```

这些占位符由传给 `sandbox-exec` 的 `-Dkey=value` 选项填充。

为了实现自己的沙箱 API，Codex 会从一个[基础策略](https://github.com/openai/codex/blob/bee28e8a061c38c781c74299f2c1d90e3732da18/codex-rs/sandboxing/src/seatbelt_base_policy.sbpl)出发[构建参数列表](https://github.com/openai/codex/blob/bee28e8a061c38c781c74299f2c1d90e3732da18/codex-rs/sandboxing/src/seatbelt.rs#L871)传给 `sandbox-exec`，再用 `permission_profile` 和其他上下文对它进行增补，生成完整的 Seatbelt 策略。生成的策略连同附带的 `-D` 参数一起，配置了由 Seatbelt 强制执行的那些限制，而网络代理则强制执行额外的网络规则。参数列表拼好之后，调用 `sandbox-exec` 就很简单了。

生成正确的 SBPL 很有挑战性，因为 Apple 并没有为第三方使用而记录这门语言。事实上，`man sandbox-exec` 里写着 `The sandbox-exec command is DEPRECATED`（通过 `man 3 sandbox_init` 记录的 `sandbox_init()` 库函数也一样）。尽管有废弃警告，macOS 仍然在 `/usr/share/sandbox` 中随系统提供 Seatbelt 策略，第三方软件——[包括 Google Chrome 和 Chromium](https://www.chromium.org/developers/design-documents/sandbox/osx-sandboxing-design/)——也仍在依赖 Seatbelt。因此，在可预见的未来，我们打算继续使用 Seatbelt。

### Linux

为了在 Linux 上创建沙箱，Codex 结合使用了 [bubblewrap](https://github.com/containers/bubblewrap)（`bwrap`）和 [seccomp-bpf](https://en.wikipedia.org/wiki/Seccomp)——前者是用于构建隔离环境的命令行工具，后者是 Linux 内核中用于过滤系统调用的机制。一个名为 `codex-linux-sandbox` 的内部辅助程序负责协调整个搭建过程。与 macOS 上的 `sandbox-exec` 类似，它接收沙箱配置，后面跟着要运行的命令：

#### Bash

```
1codex-linux-sandbox SANDBOX_ARGS... -- PROG ARGS...
```

当需要文件系统隔离或代理路由时，`codex-linux-sandbox` 会调用 `bwrap` 创建初始的沙箱环境。随后 `bwrap` 在其中启动 `codex-linux-sandbox --apply-seccomp-then-exec`。这第二次调用会使用 seccomp-bpf 施加额外限制，然后运行用户的命令。

为了构建这个初始沙箱环境，Codex 用 bubblewrap 在独立的 mount namespace 中创建一个文件系统视图，使其反映权限配置里的文件系统规则。由于这对沙箱实现至关重要，Codex 自带了一份 `bwrap` 副本，以防用户没有自行安装；但如果 `PATH` 上存在[兼容的](https://github.com/openai/codex/pull/15791)[`bwrap`](https://github.com/openai/codex/pull/15791) 安装，它会优先使用。根据实际经验，[有些 Linux 发行版默认禁止访问用户命名空间](https://github.com/openai/codex/pull/14963)，但会对系统自带的 `bwrap` 网开一面。

同样与 `sandbox-exec` 类似，`bwrap` 接收沙箱配置，后面跟着要在沙箱内运行的命令。`bwrap` 不使用 SBPL 那样的自定义配置语言，而是用一个个独立参数来配置。Codex 使用以下选项来创建文件系统视图：

- `--bind` 指定可写的文件或目录
- `--ro-bind` 指定只读的文件或目录
- `--perms 000 --tmpfs DIR --remount-ro DIR` 禁止访问 `DIR`
- `--perms 000 --ro-bind-data FD FILE` 禁止访问 `FILE`（其中 `FD` 是指向 `/dev/null` 的已打开文件描述符）

要用这些选项实现 deny glob，Codex 会在启动每条命令之前把它们展开成具体路径。此后新匹配上的路径不会被自动加入该命令的沙箱限制。

Codex 还会指定 `--unshare-ipc`、`--unshare-pid` 之类的选项，防止沙箱访问宿主机上的其他类型资源，因此 bubblewrap 影响的不只是文件可见性。

使用 bubblewrap 时，只要网络被禁用或连接必须经过网络代理，Codex 就会传入 `--unshare-net`，这会为沙箱创建一个新的网络命名空间。之后我们用 seccomp-bpf 对该命令可用的网络系统调用和 socket 类型施加额外限制。

具体来说，我们用 [seccompiler crate](https://crates.io/crates/seccompiler) [根据所需的过滤器动态编译一个 BPF 程序](https://github.com/openai/codex/blob/ff2346f33f851bd4e90c8e42ae60abcc7e7f293b/codex-rs/linux-sandbox/src/seccomp.rs#L177-L302)，并把它应用在沙箱内的一个 launcher 进程上，使这些约束被整个进程树继承。因此，`bwrap` 运行的不是用户的命令，而是 `codex-linux-sandbox` launcher，先带上它自己的配置参数，后面跟着用户的命令：

#### Bash

```
1bwrap BWRAP_ARGS... -- \2  codex-linux-sandbox --apply-seccomp-then-exec CODEX_LINUX_SANDBOX_ARGS... -- \3  PROG ARGS...
```

为了在没有提权的情况下应用 seccomp 过滤器，[launcher 会设置 Linux 的 `no_new_privs` 标志](https://github.com/openai/codex/blob/ba0dfd38979033f514a28d9514215bad46957a18/codex-rs/linux-sandbox/src/seccomp.rs#L68-L76)。这个标志会被子进程继承，阻止它们在执行另一个程序（例如 setuid 可执行文件）时获得额外的权限。

seccomp 过滤器取决于网络配置。当网络访问被禁用时，我们会拦住一批与网络相关的系统调用，例如 `connect(2)` 和 `bind(2)`。而当沙箱中启用了网络代理时，我们允许 IP socket，好让 `codex-linux-sandbox` 创建的 TCP listener 可以被访问，但默认阻止创建独立的 Unix domain socket，因为那可能导致对宿主机资源的意外访问。

#### 连接网络代理

当沙箱配置需要使用网络代理时，Codex harness 会创建一个代理实例，让它在同一个 Codex 线程内的多次 `codex-linux-sandbox` 调用之间复用。每个沙箱都需要一条从自己隔离的网络命名空间通向这个共享代理的路径。Codex 在该命名空间内提供一个回环 TCP listener，并安排沙箱外的一个进程接受它的连接、转发给代理。

下面的几张图展示了一个代理端点的搭建过程，最后一张图展示了通过它建立的一条连接。在启动 bubblewrap 之前，`codex-linux-sandbox` 会创建一对 Unix socket 作为控制通道，并 fork 自己。子进程运行 `run_host_bridge()`，等待通过该通道接收 listener 的文件描述符：

![示意图：Codex harness 启动 codex-linux-sandbox，后者 fork 出一个中继进程，通过 Unix socket 控制通道与它相连。](https://images.ctfassets.net/kftzwdyauwt9/fF0Stm84x5aGz27y1DXKL/8718b7869db26ba62b9c2d55f1ec2849/preparing-relay-process-diagram-desktop-light.svg?w=3840&q=90)

在这个例子中，父进程用 `exec` 把自己的程序映像替换成 `bwrap`。这搭建起沙箱，并在其中启动 `codex-linux-sandbox --apply-seccomp-then-exec`，同时把控制通道的 FD 一路传进去：

![示意图：bwrap 创建沙箱网络命名空间，并在其中启动 codex-linux-sandbox，同时有一条 Unix socket 控制通道通向沙箱外的中继进程。](https://images.ctfassets.net/kftzwdyauwt9/1fI91cZrglfbUhn7ZFs0bS/6ccf3d41b7c58fffbc20ca2baaf424a5/creating-sandbox-diagram-desktop-light.svg?w=3840&q=90)

在沙箱的网络命名空间内部，`codex-linux-sandbox` 的第二次调用会创建一个回环 TCP listener，并通过 socket 把它的文件描述符传出去。这个 listener 仍然与沙箱的网络命名空间相关联，使得留在沙箱外的那个子进程能够接受来自沙箱内程序的连接，同时在宿主机的网络命名空间里发起自己的上游连接。交接完成后，两个进程都关闭各自的控制通道描述符，沙箱内的进程也关闭自己那份 listener。

TCP listener 就绪后，沙箱内的进程会[给 `HTTP_PROXY` 等相关环境变量设置合适的值](https://github.com/openai/codex/blob/d93071fae87f73ba1d251ebb3808773f18f0b77a/codex-rs/linux-sandbox/src/proxy_routing.rs#L200-L202)，让它们指向该 listener。接着它在 fork 并执行用户的命令之前应用 seccomp：

![示意图：沙箱内的程序连接到回环 TCP listener，由沙箱外的 codex-linux-sandbox 中继把流量转发给 Codex 网络代理。](https://images.ctfassets.net/kftzwdyauwt9/5Q2GgA0Fl9vAI9IVu0HtHu/0c105caec1e72c5ac279f2ccc667963a/relaying-proxy-connections-diagram-desktop-light.svg?w=3840&q=90)

沙箱外的进程会一直保持 listener 打开。对于每一条被接受的连接，它会向配置好的代理发起一条连接，并在两个方向上转发数据。

这套额外的机制让命令拥有了自己的网络命名空间，包括一个独立的回环接口。在 macOS 上，Seatbelt 允许命令直接连接宿主机回环接口上指定的端口。在 Linux 上，命令改为连接到它自己隔离命名空间内的一个 listener，由沙箱外的进程把这些连接中继给配置好的代理。正是文件描述符的交接，让这种连接方式成为可能，同时又不把宿主机的网络命名空间暴露给命令。

### Windows

今年早些时候，我们实现并[撰文介绍过我们在 Windows 上的沙箱工作](https://openai.com/index/building-codex-windows-sandbox/)。此后，Microsoft 发布了名为 MXC 的库，以及 Windows 操作系统内一批用于进程隔离的新特性。我们目前正在用基于 MXC 库的沙箱替换现有的沙箱。

#### 什么是 MXC？

MXC（Microsoft eXecution Container）是 Microsoft 的一套[沙箱化代码执行系统](https://github.com/microsoft/mxc)，支持在 Windows、Linux 和 macOS 上使用多种隔离后端。Codex 在兼容的 Windows 设备上支持基于 MXC 的沙箱，用原生进程隔离把命令限制在用户现有的环境之内。

我们正在转向 MXC，以提升安全性与易用性，同时解决现有 Windows 沙箱的几项局限：

- 搭建沙箱需要提权/管理员权限
- ACL 检查与设置操作开销大、速度慢
- 在主机上留下持久化的沙箱搭建状态，包括 ACL、防火墙规则、沙箱用户、控制平面文件

MXC 提供了一套 [JSON 配置 schema](https://github.com/microsoft/mxc/blob/main/docs/schema.md)。Codex 使用 [MXC SDK](https://crates.io/crates/mxc-sdk) 按该 schema 构造执行请求，其中包含命令、工作目录、环境和权限。这些权限涵盖文件系统与网络访问，以及桌面、剪贴板等 Windows 资源。

#### 把策略转换成 MXC 调用

为了在兼容性与安全性之间取得平衡，Codex 对若干控制项采用固定设置。它允许读取注册表，并保留 PowerShell 启动过程中所需的 Win32k 和桌面访问权限。剪贴板访问、输入注入以及桌面和系统设置类的控制项则被禁用。最后，还会阻止 MXC 退回到修改宿主机文件系统权限的做法。

Codex 会把权限配置中的文件系统与网络规则转换成 MXC 的配置。沿用前面的 `dev` 配置，并假设：

- `C:\`、`D:\` 和 `Z:\ ` 是这台机器仅有的本地驱动器。
- 工作区根目录和工作目录是 `C:\work\demo`。
- 用户的主目录是 `D:\Users\dev`，因此 `~/build-cache` 解析为 `D:\Users\dev\build-cache`。
- deny glob 只匹配 `C:\work\demo\config\dev.env` 和 `C:\work\demo\config\prod.env`。

对应的 MXC 设置大致会包含：

#### JSON

```
1{2  ...3  "filesystem": {4    "readwritePaths": [5      "C:\\work\\demo",6      "D:\\Users\\dev\\build-cache",7      ...8    ],9    "readonlyPaths": [10      "C:\\",11      "D:\\",12      "Z:\\",13      "C:\\work\\demo\\.agents",14      "C:\\work\\demo\\.aws",15      "C:\\work\\demo\\.codex",16      "C:\\work\\demo\\.devcontainer",17      "C:\\work\\demo\\.git",18      "C:\\work\\demo\\.vscode",19      ...20    ],21    "deniedPaths": [22      "C:\\work\\demo\\config\\dev.env",23      "C:\\work\\demo\\config\\prod.env",24      "C:\\work\\demo\\secrets"25    ]26  },27  "network": {28    "egress": {29      "default": "deny",30      "allow": [{31        "to": [32          {"cidr": "127.0.0.0/8"},33          {"cidr": "::1/128"}34        ]35      }]36    },37    "ingress": {38      "default": "deny",39      "hostLoopback": "allow"40    }41  },42  ...43}
```

#### 驱动器根目录访问

MXC 的文件系统策略默认拒绝访问。因此 Codex 为本地驱动器根目录添加只读授权，以提供这份配置所允许的广泛读取。这些授权递归生效，同时受用户现有操作系统权限的约束。

有一个细节：*可写*的驱动器根目录授权不会递归生效，所以 Codex 会把它们展开，把驱动器下已有的直接子项一并包含进来。

#### 冲突的授权

更具体的路径会覆盖祖先路径的授权，因此 `C:\work\demo` 可以在只读的 `C:\` 之下保持可写，而 `C:\work\demo\.git` 仍然只读。

当不同的路径写法或符号链接/联接点别名指向同一个路径时，MXC 会采用更严格的权限：deny 优先于只读，只读优先于读写。

#### deny glob

MXC 只接受具体的 deny 路径，因此 Codex 会在启动前把 deny glob 展开成匹配的文件和目录。命令运行期间新出现的、匹配该 glob 的路径不会被自动加入。

#### 网络访问

`*.openai.com` 这类域名规则由前面介绍过的共享 Codex 网络代理强制执行。Codex 在沙箱之外运行该代理，并通过前面提到的那些标准 `*_PROXY` 环境变量把它的地址传给命令。MXC 阻断直接的外部连接，同时允许宿主机回环连接，其中包括对代理的访问。其他本地服务仍然可以访问。

在 macOS、Linux 和 Windows 上，harness 都用同一套沙箱 API 在某个权限配置下启动命令。各平台特有的实现则负责完成施加这些限制所需的搭建工作。

## 在 Codex 沙箱之上构建

编写并执行代码，为 agent 提供了一种灵活解决问题的方式，其用途远不止软件开发。Codex 沙箱让它们能在用户现有的环境中使用这种能力，同时对文件系统和网络访问施加明确的限制。它是 harness 内部一个可复用的基础构件，而 `codex sandbox` 命令让你自己构建的工具也能用上它。

随着 agent 承担的任务越来越多，我们希望让沙箱化对更多工具和环境都切实可用。这意味着让权限更易于配置，并在操作系统提供更好的防护能力时加以利用。我们的目标是扩大 agent 能做的事情，同时让人始终掌控它们能访问什么。
