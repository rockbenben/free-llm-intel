# 推进低资源编程语言的编码能力

![](https://openai.com/_next/static/immutable/media/lab.44a_dymau51y3.webp)[ COBOL ][ OCaml]![](https://openai.com/_next/static/immutable/media/laptop.2t2hneg7lf1gz.webp)[ Fortran][ Visual Basic ]![](https://openai.com/_next/static/immutable/media/chip.1t86cqmsrm7g2.webp)Advancing coding in low‑resource programming languages

我们最新的模型进展，让在 COBOL、Fortran、Visual Basic 这类低资源编程语言中构建与迁移软件的能力更强。相比 Python、JavaScript 这样的语言，这些语言里可供模型学习的代码和文档要少得多，但它们支撑着世界各地关键的基础设施和基本服务。COBOL [支撑](https://www.ibm.com/think/topics/cobol)着 40% 以上的在线银行系统、80% 的线下信用卡交易和 95% 的 ATM 交易，而 Fortran 被用于[天气预报](https://repository.library.noaa.gov/view/noaa/71120)和[核反应堆安全分析](https://www.nrc.gov/education-regulatory-research/research/computer-codes)。提升 AI 在这些语言中工作的能力，可以帮助团队维护并现代化那些基本服务所依赖的软件。

这项工作由开发者和企业客户的反馈指引，他们告诉我们，编码模型在这些语言上常常力不从心。维护和现代化这类软件可能很困难：文档可能不完整，最初的开发者可能已经离开公司，而重要的业务规则可能只存在于代码之中。无论团队是在修复 bug 还是迁移到另一种语言，他们都需要保住系统赖以运行的行为。

为了衡量进展，我们开发了两项评测。MultiLangBench 考察模型能否在 20 种不同的编程语言中从零构建一个与 SQLite 兼容的数据库引擎。我们的 COBOL 迁移评测考察模型能否把已有程序迁移到另一种语言，同时保留它们原有的行为。两者合起来检验两项互补的能力：构建新软件，以及保留现有软件所做的事。

我们最新的模型在两项评测中都表现出显著提升，以更低的成本给出高得多的准确率。

在 MultiLangBench 上，GPT‑6 Astra 在 20 种编程语言上的平均测试通过率达到 87.4%，高于 GPT‑5.6 Sol 的 26.8%，并且每一种被测语言都有改进。GPT‑6 Luna 同样优于 GPT‑5.6 Sol，达到 40.3%，而估计的 API 成本约低 78%。

在我们的 COBOL 迁移评测上，GPT‑6.1 Sol 在低推理强度下取得 86.6% 的准确率，而 GPT‑5.6 Sol 只有 5.4%，成本还低 39%。在更高的推理强度下，准确率达到 97.9%，几乎触及这项评测的饱和点。

这些结果共同说明，我们的模型在处理各种编程语言时正在明显变得更强，同时也更有成本效益。

## 1. 从零构建 SQLite（MultiLangBench）

MultiLangBench 要求模型用指定的编程语言构建一个与 SQLite 兼容的数据库引擎。模型必须组织代码库、管理状态、处理错误，并在保留已有功能的前提下加入新特性。

为了在不同语言之间比较实现，我们把数据库文件用作共享接口。候选程序收到一个初始数据库和一条 SQL 查询，然后产出一个被修改过的数据库。我们用 SQLite 的参考实现来检查结果数据库是否含有预期的内容。这样，无论用哪种语言构建引擎，我们都能套用同一套测试。

我们把 SQLite 现有测试套件中的测试改编成这种格式。这项评测衡量模型在一次长时间的编码会话中能构建出多少可用的功能，同时报告测试通过率和 API 成本。

在最高推理强度下，GPT‑6 Astra 在这 20 种语言上的平均测试通过率达到 87.4%，高于 GPT‑5.6 Sol 的 26.8%。每一种被测语言都有提升，包括 COBOL（10.9% 到 72.1%）、OCaml（25.6% 到 85.8%）、Fortran（21.4% 到 83.5%）和 Visual Basic（27.5% 到 89.4%）。Astra 在 20 种语言中有 19 种得分超过 83%，最难的仍是 COBOL，为 72%。

GPT‑6 Luna 提供了一个成本更低的选择，同样在每一种被测语言上都优于 GPT‑5.6 Sol。在最高推理强度下，它的平均测试通过率达到 40.3%。提升幅度包括 COBOL（10.9% 到 17.1%）、OCaml（25.6% 到 34.1%）、Fortran（21.4% 到 31.4%）和 Visual Basic（27.5% 到 41.6%）。这些改进对应的平均 API 成本估计为每个样本 $0.77，而 GPT‑5.6 Sol 为 $3.48，约低 78%。

我们正在 [GitHub](https://github.com/openai/MultiLangBench) 上发布 MultiLangBench 的评测配置与测试套件，并公开每种语言的结果。开发者可以查看这项评测究竟在测什么，检视自己使用的语言上的表现，并找出对自身工作影响最大的差距。

## 2. 迁移一个 COBOL 代码库

我们的第二项评测要求模型把 COBOL 程序迁移到 C++、Java、Kotlin、Python 或 Rust，同时保留每个程序原有的行为。

要成功迁移，就得同时理解程序的业务逻辑和 COBOL 特有的语言行为。COBOL 程序常常处理金融交易和业务记录，其中取整规则、缺失记录的处理这类细节反映的是业务要求。举例来说，COBOL 的定点运算会直接丢弃多余的小数位，除非显式要求做舍入。如果重写版本改为对这些值做舍入，程序可以毫无报错地运行，却产出不同的财务结果。

为了检验这些行为是否被保留，我们在隐藏测试上评测模型，这些测试要求可观察输出逐字节一致。只有全部测试通过，一次迁移才算成功。这类保留行为的能力对维护并现代化老旧系统的团队很有用，不过要把它用到生产软件上，仍然需要专家审查，并针对系统的业务规则和依赖进行测试。

在这项评测上，GPT‑6.1 Sol 在低推理强度下取得 86.6% 的准确率，API 成本只有 GPT‑5.6 Sol 的 61%，而后者在同样的设置下只有 5.4%。在更高的推理强度下，准确率达到 97.9%，让这项评测接近饱和。这些评测结果说明，对于正在现代化自身业务所依赖软件的团队，更准确、更可负担的代码迁移正在取得进展。

## 推进面向企业软件的能力

这些评测，加上开发者和企业客户的直接反馈，帮助我们看清我们的模型在哪些方面有了进步、在哪些方面仍然不足。

我们的目标是帮助模型在更多语言中运用软件工程技能：读懂陌生的代码仓库、规划改动、使用构建工具、运行测试、排查失败。

你可以通过 API，在你团队使用的语言上就编码任务试用我们最新的模型。你的反馈——哪些做法有效、模型在哪些地方还吃力、我们接下来应当优先关注哪些语言或工作流——会影响我们训练和评测模型的方式，从而更好地支撑你所依赖的软件。
