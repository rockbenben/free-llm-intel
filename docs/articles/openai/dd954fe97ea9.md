# 根据人类偏好微调 GPT‑2

阅读论文


查看代码



我们在多种任务上用人类反馈对 774M 参数的 GPT‑2 语言模型做了微调，成功匹配上了外部人类标注员的偏好——尽管这些偏好并不总是和我们的一致。具体来说，在摘要任务中，标注员更偏爱直接从输入里整句照抄的句子（我们只要求他们保证准确性），于是我们的模型就学会了抄写。摘要任务用了 6 万个人类标注；而按各种风格续写文本这类更简单的任务，只需要 5 千个。我们的动机是把安全技术往"机器与人对话"这个更一般的任务上推进，我们相信这是提取人类价值观信息的关键。

我们认为语言是让强化学习在真实世界任务中既可用又安全的关键要素。此前关于学习人类偏好模型的工作（[Previous⁠](https://openai.com/index/learning-from-human-preferences/) [work](https://arxiv.org/abs/1811.06521)）主要集中在简单的模拟环境（Atari 游戏或机器人任务），这些环境体现不出语言的复杂性。语言同时也是 [amplification⁠(放大)](https://openai.com/index/learning-complex-goals-with-iterated-amplification/) 和 [debate⁠(辩论)](https://openai.com/index/debate/) 这类算法的必要组成，这些算法针对的是偏好背后的推理过程。

这项工作把人类偏好学习应用到若干自然语言任务上：用 [BookCorpus](https://github.com/soskek/bookcorpus) 续写带有积极情绪或身体描写语言风格的文本，以及对来自 [TL;DR](https://www.aclweb.org/anthology/W17-4508) 和 [CNN/Daily Mail](https://github.com/abisee/cnn-dailymail) 数据集的内容做摘要。每个任务都可以看作一个文本补全问题：给定一段文本 *X*，我们问的是一段什么样的文本 *Y* 应该接在后面。[A](https://openai.com/index/fine-tuning-gpt-2/#citation-bottom-A)

我们从预训练好的语言模型（[GPT‑2 的 774M 参数版本⁠](https://openai.com/index/gpt-2-6-month-follow-up/)）出发，然后请 [人类标注员](https://scale.ai/) 在四个样本中挑出最好的一个，以此微调模型。在风格续写任务上，微调很省样本：5000 个人类样本就能达到人类评判意义上的强表现。在摘要任务上，用 60000 次比较训练出来的模型学会了从输入中整句照抄、同时跳过无关的开场废话；抄写是保证摘要准确的一种省力办法，但可能利用了标注员依赖简单启发式判断这一点。

## 摘要

我们也把人类微调用在两个摘要任务上：对 CNN/Daily Mail 数据集的文章做摘要，以及对 TL;DR 数据集中的 Reddit 片段做摘要。

这两个任务更难：我们的主力模型用了 60000 次四选一比较。我们还需要*在线*（online）数据收集，即在训练过程中随策略变化持续生成展示给人看的样本；只给人展示基座 GPT‑2 语言模型样本的*离线*（offline）数据收集策略表现很差。

按人类标注员的标准，我们的模型取得了很好的表现，但很可能是在利用标注员依赖简单启发式这一点：他们比起我们的模型，更偏好 lead-3 这个基线（照抄前三句）。不过，把有监督微调和人类微调结合后，我们的模型在 ROUGE 分数上超过了 lead-3。

读者可能已经注意到这些样本的几点情况。第一，我们 RL 微调后的模型主要是一台聪明的抄写机器：它通常靠从文章或 Reddit 片段里整句照抄来"摘要"。相比之下，zero-shot 和有监督微调的样本更新颖：

| **模型** | **CNN/Daily Mail** | **tl;dr** |
| --- | --- | --- |
| 参考摘要 | 96.7 | 98.9 |
| Zero-shot | 91.7 | 96.3 |
| 微调后 | 2.5 | 29.0 |
| 有监督 | 83.6 | 96.9 |
| 有监督 + 微调后 | 69.6 | 94.0 |

**句子新颖度**：摘要中未出现在原文里的句子所占百分比。

RL 微调模型确实会变换抄写的位置：在 TL;DR 和 CNN/Daily Mail 上，它抄输入开头的比例分别是 28.3% 和 77.6%；而如果输入以无信息量的开场废话开头（TL;DR 定义为 "hi"、"hello"、"hey"、"ok"、"okay"、"so"，CNN/Daily Mail 定义为前三个词中出现冒号，例如 "Winner: Simon Wood took home the TV crown [...]"），这两个数字降到 0.2% 和 1.4%。

第二，虽然按 n-gram 或句子来衡量，GPT‑2 zero-shot 和 GPT‑2 有监督微调版本的摘要更新颖，但它们在内容上也更"新颖"，也就是说它们不真实：

| **模型** | **CNN/Daily Mail** | **tl;dr** |
| --- | --- | --- |
| Zero-shot | 6/30 | 6/30 |
| 微调后 | 29/30 | 26/30 |
| 有监督 | 19/30 | 8/30 |
| 有监督 + 微调后 | 20/30 | 11/30 |

**摘要准确率**：由作者对每个数据集的 30 篇文章判定，生成摘要的准确频率。

这些结果至少有两种解读。第一种是：抄写是做到准确最容易的办法。标注员被告知要惩罚不准确，但没有被告知要惩罚抄写。zero-shot 模型有时也会抄，而它抄的时候是准确的，于是抄写被强化了。结果就是一个基本只会抄写、但至少不撒谎的模型。

不过这并不能完全解释人类评估的结果：在两个数据集上，我们的模型和照抄前三句的简单 lead-3 基线，都被标注员强烈偏好于人类写的参考摘要。而作者们并不认同：我们认为参考摘要更准确，也更好地抓住了整体信息。这暴露出一个错位——我们希望模型学到的"质量"概念，与人类标注员实际评估的东西并不一致。标注员想尽可能快地干活，而"只要摘要在抄，就选它"这条启发式能让他们非常快。

## 挑战与经验教训

### 在线数据收集很难

要在摘要任务上拿到最好的结果，在线数据收集是必需的，但它带来了好几个麻烦：

- **软件复杂度**。把数据收集、奖励模型训练和 RL 微调交错在一起，系统比各组件彼此独立时复杂得多。
- **机器学习复杂度**。任何一个组件里的 ML bug 都会拖垮整个系统，而要单独调试某个组件也很别扭。
- **质量控制问题**。在线标注采集要求从生成样本到从 [Scale](https://scale.ai/) 拿回数据之间的延迟很低（通常约 30 分钟）。低延迟下的质量控制很难，数据质量的退化常常要等训练跑完才被发现。

我们认为离线与在线数据收集之间合适的中间点是*分批*（batched）数据收集：在大批量收集数据（可以容忍更高延迟）与用已收集数据训练之间交替。人类数据的成本决定了数据量始终偏低，所以每次从头重训（准确说，从 GPT‑2 这个起点重训）都很容易。

### 任务含糊会让标注变难

单个标注员也许能清楚判断某个样本是否单独地准确、合语法、不冗余、是否抓到要点，但比较两份摘要往往需要对不同类型的缺陷做主观权衡。可行的话，设计不那么含糊的标注任务、又能拿到同样信息，看起来更好。例如，与其让人比较摘要，不如请他们用文字描述摘要的问题，或给出修改建议。即使两个人对"最主要的问题是什么"意见不同，他们也可能同意对方至少指出了*某个*问题；一致性更高，质量控制和整个实验流程都会更轻松。

### Bug 会优化出糟糕行为

我们的一次代码重构引入了一个 bug，把奖励的符号取反了。取反奖励通常只会产出语无伦次的文本，但这个 bug 同时也把 KL 惩罚的符号取反了。结果是一个一边优化负面情绪、一边保持自然语言的模型。由于我们的说明要求人类对包含露骨性内容的续写打很低的分，模型很快就学会了只输出这类内容。这个 bug 很特别，因为产出不是乱码，而是最大程度地糟糕。训练进行时作者们都在睡觉，所以问题直到训练结束才被发现。如果有类似丰田 [Andon cord](https://en.wikipedia.org/wiki/Andon_(manufacturing))（安灯绳）这样的机制就能避免——它允许任何标注员叫停有问题的训练过程。

## 展望

我们在两类自然语言任务——风格化续写和摘要——上演示了从人类偏好中学习奖励。结果喜忧参半：续写任务用极少的样本就取得了不错的效果，但我们的摘要模型只是"聪明的抄写员"：它们从输入文本里抄，但会跳过无关的开场废话。聪明抄写的优势在于真实：zero-shot 模型和有监督模型会生成自然、看着可信、却常常是谎言的摘要。我们认为我们实验的瓶颈是数据质量，而在线数据收集的环境又放大了这个问题，未来计划改用分批数据收集。

我们认为把奖励学习应用到语言上，在能力和安全两个视角上都很重要。能力方面，强化学习能纠正有监督学习察觉不到的错误，而用程序化奖励函数的 RL 则"[可能损害模型质量](https://arxiv.org/abs/1705.04304)"。安全方面，面向语言的奖励学习让"不要撒谎"这类重要准则能在训练期间被表达出来，也是迈向可扩展安全方法（如 [debate⁠(辩论)](https://openai.com/index/debate/) 和 [amplification⁠(放大)](https://openai.com/index/amplifying-ai-training/)）的一步。
