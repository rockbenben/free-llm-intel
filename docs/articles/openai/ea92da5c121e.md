# 我们如何为 ChatGPT 搭一套全新的广告技术栈，兼顾用户信任与相关性

作者：Ritendra Datta 与 Karthik Gopalratnam，Members of Technical Staff

传统广告系统是为响应用户意图的离散单元而打造的。用户在网上搜索或浏览某样东西，广告系统就把这些查询和页面浏览当作事件接收下来，再基于这些事件去寻找匹配的广告。为 ChatGPT 构建广告技术栈则不同：用户意图是在一次次对话中逐渐成形的，会随着同一场对话的多个轮次不断变化，有时根本不存在合适的广告时机。为了支撑这一新范式，我们打造了一套定制的广告投放系统。这种新型广告技术栈建立一个自研的、post-trained 的 frontier LLM 之上，它通过发起 tool call 来完成 retrieval（找出靠前的候选）、ranking（预测用户互动）、relevance（评估广告有多大用处），并运行 auction 来做最终的广告选择与定价。

我们的广告系统靠三个关键设计决策来承接用户需求不断演进这件事的细微之处：1）实现有状态的广告会话，也就是信息会跨对话轮次、跨多场对话被记住；2）依赖一个自研的、post-trained 的 LLM，它采用 tool call 架构来理解对话的上下文与背后的意图，进而有效地挑选、排序并投放广告；3）把广告选择过程与 ChatGPT 的答案生成拆分开，放在它自己的服务里运行，以免广告影响答案、并保持 ChatGPT 中立的语气。我们用 post-trained 的 LLM 来编排整条广告流程，依据用户当前这一轮以及历史对话，决定在合适的时机呈现合适的广告。过去，冷启动这样一个能自我改进的广告系统要花上数年，而 ChatGPT Ads 的年化营收 run rate 已达到 10 亿美元，[距离上线不到 200 天](https://openai.com/index/expanding-access-to-ai-with-chatgpt-ads/)；如今，自上线以来已有超过 10 万家广告主在 ChatGPT 上投放过广告。

## 在 agentic 对话里，广告应该怎么做？

传统的广告请求通常始于一个定义明确的事件。用户提交一条搜索查询或打开一个网页，广告系统就收到一个请求。这类系统相当简单：它检索出潜在的广告候选，对它们排序，运行一次 auction 来给这个机会合理定价，然后把得到的广告展示给用户。ChatGPT 并不会天然产生这样具体的时刻。

在 ChatGPT 的对话里，人们带着目标而来，而不是一句一问一答式的搜索查询。他们可能在规划一趟旅行、为自己的生意挑选软件、布置一个家，或学习一项新爱好。这些事不会在一轮对话里全部发生。ChatGPT 常常会在过程中帮助用户厘清真正重要的是什么。

举个例子，我们的工程团队问过 ChatGPT 如何为参加一场比赛做训练：对话以一个关于跑步的泛泛问题开始。几轮之后，他们开始询问有助于训练的运动鞋。随着每一个约束条件出现，这场对话的商业含义随之改变——而且这种个性化上下文会跨多个会话不断演进。一个只根据第一条消息就行动的系统，可能检索到完全错误的意图，从而损害用户体验、给用户添堵。

构建我们的广告系统，要求我们跳出请求-响应式的广告架构，从零开始搭建一套广告技术栈，在把用户信任与价值放在首位的同时，去寻找潜在的经济机会。

## 记住对话，却不影响 ChatGPT 的答案

像传统广告系统那样把每条消息都当成一个独立请求，在我们的聊天场景里会带来几重风险：1）把用户目标过度简化，从而误读它；2）在用户的真实需求尚未清晰之前就过早启动广告流程；3）展示出来的广告不是在支持用户的旅程，而是在打断它；4）每次请求发生变化就低效地把广告流程重跑一遍，制造噪声并浪费成本。我们没有围绕单个事件来构建，而是让广告系统（由 retrieval、ranking 和 delivery 组成）维护一个有状态的会话，也就是广告会话会在一个符合投放资格的轮次期间持续运行，随着信息演进不断记住并更新它。ChatGPT 把初始的请求上下文发送给广告服务器。广告系统跟随并适应正在展开的这场交流，而不是依赖一条被压平的查询。

广告选择过程与 ChatGPT 的常规回复生成并行运行，以确保广告流程不会影响 ChatGPT 的回复。广告是在一个独立系统里完成筛选和选择的，这个系统消费对话内容，并受自己的 eligibility、质量与 delivery 约束。这条关键的架构边界——用不同的服务，各自使用不同的模型和不同的代码——让 ChatGPT 核心服务器负责生成自然回复；与此同时，广告系统独立判断是否存在合适的广告机会，如果有，就通过一条独立的 serving 流程准备一个标注为 sponsored 的广告位。

*广告投放与 ChatGPT 的回答路径并行运行。*

除了保护用户体验，这种隔离还有一些实际后果。ChatGPT 对广告系统没有任何依赖——这些服务以任何方式都没有交织在一起，也不共用一个内容生成模型。所以即使广告投放系统不可用或变慢，ChatGPT 的自然回复照常进行、不受影响。这意味着广告系统不可能拖垮或延迟 ChatGPT 这个产品。这种隔离的另一个好处是，它把有价值广告的门槛保持得非常高。不返回任何广告，是一种平常而成功的结果。只有当某条广告显然对用户和广告主都有益时，系统才会投放它。

## 由 LLM 理解对话并调用工具

我们广告技术栈里的另一个关键架构组件，是一个 post-trained 的 LLM，它负责理解对话，并在一个 agentic 循环里跑完整条广告流程——向广告系统的核心功能发起 tool call，从 retrieval 阶段到 ranking、再到 auction，最终到 delivery。我们把这一个 LLM 称为 *orchestrator*。

广告流程的第一部分，是理解用户意图并启动 retrieval 过程——retrieval 是一次刻意求宽、追求速度的潜在广告搜集，供后续层层过滤。逐段增量地接收对话，会让 retrieval 问题变得更丰富也更含糊，因为广告系统需要把当前意图与过时的上下文区分开。orchestrator 必须能理解对早前消息的指代，识别用户何时只是在假设性地谈论，并避免把每一次提到某个产品或服务都当成一次购买请求。

广告 orchestrator 使用可用的对话与用户上下文，反复迭代以找到好的广告，并一次次决定什么时候调用哪个工具，其底层目标是在那场对话与那个上下文里找到最合适的广告（也就是在高用户价值与高广告主价值之间取得平衡的广告）。如果用户选择开启广告个性化，orchestrator 还会利用可获得的、关于用户过往对话的非敏感信息，来寻找最匹配的广告。

## orchestrator 如何在 agentic 循环里调用广告工具

广告系统由一个个独立的工具组成，orchestrator 反复调用这些工具，为一场对话找出最好的广告。从高层看，orchestrator 先把对话转成简短的文本摘要，再把摘要转成语义 embedding（被存储下来的语义，便于广告系统快速筛查），然后用这些语义 embedding 检索广告候选，按 eligibility 过滤这些候选（依据预算、用户设置以及其他前置检查），评估它们的质量与相关性，最后再做一次 ranking，找出可以在聊天回复末尾展示的高价值机会。因此，每条广告都必须在资格和相关性两方面跨过很高的门槛，才有资格被投放。

### 准备能捕捉意图的 retrieval 查询

orchestrator LLM 首先准备一条或多条能代表相关商业意图的查询。这一步可能包括改写对话上下文，把商业可能性扩展到 1:1 搜索查询之外，然后创建语义表示——由 orchestrator 把一场多轮对话蒸馏成一个摘要版本交给 retrieval 系统，从而以聚焦的方式从我们的数据库里检索广告。

如果广告位只在系统深入理解了用户意图时才出现，那么对用户和广告主都会更好。多条查询能够保留意图的不同侧面。例如，一场关于规划旅行的对话，可能同时包含交通、住宿、活动这几类彼此不同的需求。retrieval 系统可以保留这些区分，而不是把整场对话压缩成一条字面字符串。

举个例子，来看一段可能发生的、关于徒步鞋的对话序列：

- 去 Yosemite 玩两天，我需要准备哪些东西？
- 下周会冷吗？
- 新 [insert brand] 产品线？

尽管用户并没有把关于鞋品牌的问题和 Yosemite 之行联系起来，这场对话在我们的广告系统里可能被表示成两条查询，例如 `[shoes appropriate for hiking trip]` 和 `[new [brand] product lines good for travel]`。这可能只是第一次尝试；orchestrator 的设计就是不断迭代这些表示，直到在我们的库存里找到对用户很有价值的广告。

### 检索可能的广告

retrieval 是刻意构建一个宽泛广告候选池的过程。候选可以来自不同的 retrieval 策略，之后在同一条 serving 约束下相互竞争。我们建了多个索引，分别针对不同的系统与产品约束做优化（例如，商品 feed 广告的索引在设计上会感知商品的正面或负面评价，以便抓取出尽可能好的广告；而这对那些没有关联评价的其他广告并不适用）。每个索引都针对某种形式的 approximate-nearest-neighbor（ANN）检索做了优化，使用代表用户意图的 embedding。这种 ANN 检索是在大型语义索引上做 retrieval 的一种近似算法，也就是说广告能被非常快地取出：它追求一个足够好的解，而不是去找“正确”的那个解，同时保留住绝大多数相关候选。

![流程图：改写后的查询被编码为高维语义 embedding，在常规广告、商品广告以及可选策略中检索，随后合并成一个宽泛的候选池。](https://images.ctfassets.net/kftzwdyauwt9/6F3yNWmGw0m9mY9u3BtKT8/c811e3d73a0d72b9deb12fe92ac59f2c/candidate-desktop-light.svg?w=3840&q=90)

广告系统在检索阶段用改写后的查询生成语义 embedding，产出一个宽泛的广告候选池。

### 过滤掉不符合资格的候选

过滤的目标，是把所有在相关性、出价与预算上达不到投放门槛的广告候选从考虑范围中剔除。具体取决于候选与配置，过滤检查可能包括 creative 与 campaign 可用性（campaign 或广告 creative 是否处于激活状态）、campaign 定向（例如该 campaign 被允许在哪些地区投放）、政策限制（关于什么内容可以投广告的合规要求）、预算可用性（campaign 是否还有可花的预算）、pacing（该 campaign 现在该不该花预算，还是应该在一天中的其他时段花）、广告位兼容性（这条广告有资格出现在哪几类对话里），以及广告主级与 campaign 级去重（为每个广告主挑选合适数量的广告，以确保各家企业之间的公平参与）。

### 评估相关性与质量

通过 eligibility 检查的候选进入打分阶段，此时 orchestrator 会向各个打分系统发起 tool call——出于 serving 方面的考虑，例如语义相关性（这条广告与用户的目标相关吗？）、预测互动（这条广告有可能被看到、被点击，并转化成广告主期望的结果吗？）、历史表现（这条广告此前展示给用户时表现好吗？）。orchestrator 还会在 auction 之前过滤广告，以确保相关性与安全性。这些系统把范围收窄成一个准备好进入 auction 的更小候选池，但它们仍然不决定最终投放的那条广告。

### 运行广告 auction

orchestrator 在这场对话的上下文中评估准备好的候选，挑出哪些广告候选足够合理、可以进入最终的 auction。orchestrator 并不直接决定哪条广告会被投放，也不负责定价。它只是把在上下文上合适的候选提名出来，交给 auction 工具去评估。

auction 会执行最后的 serving 机制，包括 auction 准入（跨过相关性与价值的最低门槛）、pacing（让广告预算花得更均匀）、出价与 auction 特征计算、质量调整后的 ranking、定价，以及最终选择。

### 最后的资格检查

auction 之后，有两种情况会导致广告无法投放，这两点都是 ChatGPT 这种对话式媒介特有的。

- **广告在这段对话里可能显得不合适**：尽管对话本身已被 integrity models（决定何时适合投放广告的那些模型）判定为可以投广告，广告本身也被判定为符合政策，但有时广告在某些对话的语境里就是会显得不合适。orchestrator 会阻止这类广告被展示。
- **广告请求可能来不及到达**：如果 ChatGPT 模型已经准备好回复，而广告还没准备好可展示，那条广告请求就会超时，广告也就不会被投放。因此广告系统的目标之一就是尽可能快地运行。ChatGPT 模型的响应时间是动态的，我们不会为了等广告加载而推迟聊天回复。

如果以上检查全部通过，我们就把广告发给前端去渲染。我们把这算作一次服务端广告 *delivery*，但我们仍然可能不会把广告展示给用户——而这是有意为之。

## 最后一步：把广告展示给用户

在 ChatGPT 这样的对话式产品里，把一个广告 creative 在服务端完成 delivery 并不能保证广告一定会被展示；广告还必须及时到达，才能被纳入当前这一轮。广告 creative 包含标题、描述、落地链接，以及可能有的 call to action。此外，广告系统还会返回一段由模型生成的 preamble，也就是一小段中性的引导语，用来说明这条广告与当前对话的关系。把 preamble 与 creative 分开，既保住了广告主想表达的内容，又让 ChatGPT 的语气保持中立。

ChatGPT 前端把 preamble 与广告 creative 作为一个整体接收。如果它在 ChatGPT 的回复完全生成之前到达，前端就把广告展示在 ChatGPT 回复的下方，并清楚标注为 sponsored。如果到达得太晚，这一轮就不展示该广告。这就是服务端广告 delivery 与面向用户的广告曝光之间的区别。

![时序图：serving 系统准备好广告赢家，ChatGPT 做最后检查，在用户体验中展示，并以各种确认回执把选定与成功投放区分开。](https://images.ctfassets.net/kftzwdyauwt9/6vmYf9DmmKLaEK7tpg4fcl/81d90e06c50c558a5196fb4b91fb3cc9/selecting-ads-desktop-light.svg?w=3840&q=90)

*赢家的选定与投放是两个分离的事件。只有当 ChatGPT 批准并展示了这个广告位、并且投放得到确认后，一条被选中的广告才算完成 delivery。*

## 广告展示之后会发生什么

我们的广告技术栈使用传统的日志与数据 pipeline，这带来三个主要好处：广告主能更容易地把他们现有的系统与我们的技术栈对接，广告主能借助报表数据改进自己的策略，我们的团队也能找到系统里可以改进的地方。在这些报表与优化工具之外，我们还部署了一个高质量的模型来评估我们的投放并训练其他广告模型，从而形成一个强有力的自我改进循环。

对发生了什么做细致拆解，能帮我们独立地理解并改进广告系统的每一部分。日志处理系统还会记录这些细粒度的结果：

- 这一轮不具备投放广告的资格。
- 一次广告会话开始了，但没有发起 retrieval。
- retrieval 没有返回任何候选。
- 检索到了候选，但在 hydration 或 eligibility 上失败。
- 一条广告被投放出去，并在之后收到了互动。

这些细致拆解帮助我们独立地改进广告 serving 系统的每一部分。要改进机会识别，需要的证据不同于改进 retrieval、候选质量、auction 参与度或 delivery 可靠性所需的证据。

![流程图：一个具备资格的 ChatGPT 轮次产出商品、serving 与质量三方面结果，这些结果经过受隐私控制的分析，进入聚合度量与允许用于模型改进的数据。](https://images.ctfassets.net/kftzwdyauwt9/1pmJyqwks8d8KQ97APZQ5o/5b7b9af4998894ef42b394adaf19bb90/privacy-desktop-light.svg?w=3840&q=90)

*delivery、serving 与质量系统各自观察生命周期的不同环节。受隐私控制的加工决定了哪些数据可以用于度量和模型改进。*

### 高能力模型评估并改进整套技术栈

基于模型的评估这一思路在于：由我们最强、推理层级最高的模型来观察并评判我们系统的结果，再通过训练让那个 post-trained 的 LLM 表现更好，从而完成改进。举个例子，如果最强的模型负责收集反馈、并把这些小 worker 训练到尽力做好，那么我们在编排或 retrieval 环节就可以用更小、更高效的模型，或推理层级更低的模型。

### 人的反馈把有品位的走向定下来

我们会收集并响应用户的反馈（用户的点击与隐藏操作），也会通过我们的 Ads Manager 收集面向用户的调研和来自广告主的直接反馈。在建设过程中，我们还让团队随时接收反馈，直接倾听 ChatGPT 用户与广告主各自想要什么。这一反馈来源比我们模型的观察性反馈更能影响我们的方向，也是我们能够快速迭代、做出正确产品决策的一部分原因。模型也许能理解用户意图、批判性地思考并交付有价值的东西，但品位是由人塑造的。

## 接下来

一年前，我们还没有广告系统，只有少数几个人在思考这个问题域。如今我们有了一套稳固的广告系统，支撑起超过 10 亿美元的年化 run rate，并由一个基于 LLM 的 orchestrator 跑完整条广告流程。Codex 是一个根本性的力量放大器，让我们能以空前的速度把自己的系统从零起步推到这一重大的使用量里程碑。从第一天起，我们就把团队和开发工作流设置为用 Codex 快速构建并扩展这套系统。我们为 Codex 建了护栏，让它能可靠且安全地交付代码。与此同时，我们为 Codex 配置了数据基础设施插件，大幅收紧“收集洞察—把改进落到系统上”这个循环，包括新产品功能、质量改进以及更好的系统性能。

我们系统的边界（以我们的[广告原则](https://openai.com/index/our-approach-to-advertising-and-expanding-access/)为根基）与基于 LLM 的 orchestrator 结合在一起，让我们能把广告做得有用，而又不必把每场对话都当成一次广告请求。展望未来，我们会继续尝试更动态的广告形式，以提升用户价值（例如让用户能够通过广告直接与企业对话）和广告主价值。这套技术栈自我改进的架构建立在 OpenAI 模型之上，配合持续的反馈循环，会加速我们随时间不断改善相关性与个性化的能力。
