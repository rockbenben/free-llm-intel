# 在 OpenAI 上扩展 Git

在投资 Git 生态系统的同时构建代理规模的源代码控制。

作者：技术人员 Aaron Friel、Taylor Blau 和 Ted Nyman

在过去的一年里，我们单一仓库的规模和需求以惊人的速度增长。很明显，我们需要改进我们的源代码控制系统，以扩展到 Codex 所实现的并发工作水平。

我们构建了 Pando，一个新的 Git 存储库后端，没有中断任何工程工作或改变我们团队使用 Git 的方式。 Pando 现在为 OpenAI monorepo 的所有开发提供支持。 Pando 旨在满足两个雄心勃勃的目标：首先，水平可扩展写入，针对并发推送到多个分支进行优化。其次，最大化读取吞吐量，以便客户端可以足够快地下载数据，以完全饱和其可用网络带宽。

我们实现了这些目标，同时保留了与 Git 协议和客户端的兼容性，使我们的工程师和代理能够将 Pando 无缝地采用到他们现有的工作流程中。在生产中，Pando 将中位推送延迟缩短了近 5 倍。现在，它每天提供近 PB 的 Git 数据。

在这里，我们将介绍构建新的源代码控制系统的动机，以及为什么我们选择保留与 Git 的兼容性。我们将把我们的系统与常见的 Git 扩展方法进行比较，描述为什么 Pando 能够独特地满足 OpenAI 的可扩展性需求。我们还讨论了下一步的发展，以及我们将如何继续为 Git 做出贡献以支持代理规模的工作。

## 为什么我们需要一个新的源代码控制系统

Codex 改变了 OpenAI 的开发规模和速度，使工程师能够并行完成更多工作。这意味着更多的分支和推送、更多的合并以及更多来自开发环境、研究工作和 CI 的获取和克隆。

这些要求复合在一起。一名工程师现在可以立即为 CI 准备好多项更改，并且每次推送都可以设置多个作业来获取相同的提交。

从去年年底开始，支持我们单一存储库的系统就开始难以跟上。我们遭遇了读取和推送缓慢以及合并失败的问题，可靠性有时会低于 90%。我们是否已经达到了 Git 本身的极限，或者我们服务单一存储库的方式的极限？ Git 诞生于一个通过电子邮件交换内核补丁的社区。二十多年来，随着开发人员构建软件的方式发生变化，开发人员围绕 Git 调整了他们的工具。当我们开始在自己的单一存储库中感受到摩擦时，我们可以继续在这项工作的基础上继续发展，这对我们来说很重要。

我们找到了一种方法来保持熟悉的工作流程，同时重建后端以并行处理对不同分支的推送，并同时向许多读者提供相同的历史记录。以 Git 作为我们源代码控制工作流程的基础，这意味着对客户端的改进可能比 OpenAI 更有用。我们希望将这些改进从我们的 [Git 副本](https://github.com/openai/git) 贡献给上游，与更广泛的社区分享。

### 大规模 Git 工程

扩展源代码控制系统有两个基本维度：许多作者推送到不同的分支，以及许多读者获取相同的历史记录。 Pando 对两者进行了优化。

首先，Pando 独立协调每个分支的更新。对不相关分支的更新可以并行进行，读取分支的读者可以获得该修订所需的历史记录。权衡是，查看多个分支的读者可以在不同的时间点看到它们。

其次，Pando 在提取过程中重用包文件（Git 用于将多个对象压缩在一起的格式），而不是为每个客户端生成单独的包文件。客户端可以下载一些它已经拥有的对象，但是服务器可以通过很少的计算向许多客户端提供相同的字节。

这些选择让我们可以跨分支扩展写入并提供从缓存的读取服务。为了了解它们如何组合在一起，让我们从 Git 如何存储和传输历史记录开始。

### Git 对象存储入门

Git 必须能够保持存储库的两个部分同步：*对象*和*引用*。

Git 存储库记录文件快照以及将它们连接为对象图的历史记录。对象可以是 blob、树、提交或标签。 Blob 保存单个文件的内容，树将名称与 Blob 或其他树相关联以形成目录结构。提交指向根树和零个或多个父提交，形成存储库的历史记录。

对象由其类型和内容的哈希值来标识。对象也是不可变的：记录更改的文件会创建一个新的 blob，而未更改的文件和目录可以重用现有对象。

分支和标签是指向提交的引用或“refs”。在分支上提交会创建一个新的提交并更新分支的引用以指向它。

![分支 refs/heads/main 指向提交 C2，其父级是 C1。 C1 指向根树 T1，其中 parser.py 引用 blob B1。 C2 指向根树 T2，其中 parser.py 引用 blob B2。在两个根树中，docs/ 指的是同一棵树 T3。它的 README.md 入口指向 blob B3，usage.md 指向 blob B4.](https://images.ctfassets.net/kftzwdyauwt9/2HM5lol94vaZXcGl7zXuf1/96c979a79f2b5971397cf3068a4767da/how-git-objects-reference-each-other-diagram-desktop-light.svg?w=3840&q=90)

Git 对象通过 ID 相互引用、提交到树、树到树和 blob。分支 refs/heads/main 指向提交 C2，其父级是 C1。 C1 指向根树 T1，其中 parser.py 引用 blob B1。 C2 指向根树 T2，其中 parser.py 引用 blob B2。在两个根树中，docs/ 指的是同一棵树 T3。其 README.md 条目指向 blob B3，usage.md 指向 blob B4。

Git 以“松散”或“打包”状态存储对象。松散对象存储在由其对象 ID 标识的单独文件中。打包的对象一起存储在一个包文件中，从而使相似的对象能够存储为彼此的增量。

![ $GIT_DIR/objects 下出现了两个版本的 parser.py 。作为松散对象，blob A 包含 parse()，blob B 包含 parse() 和 parse_file()。 packfile 完整存储 A 并将 B 表示为复制所有 A 并附加 parse_file() 的指令。随附的 *.idx 文件按对象定位 packfile 中的两个 blob ID.](https://images.ctfassets.net/kftzwdyauwt9/4xklltw3tJY3qRk8mzW0l3/f7f44a2cb856b0067 7a31506465e6d1a/存储-git-objects-in-packfiles-diagram-desktop-light.svg?w=3840&q=90)

Git 可以将 Blob 存储为单独的文件或将它们打包在一起，将一个 Blob 编码为另一个 Blob 的增量。

在 Git 中，如果 Git 可以通过跟踪来自该提交的链接通过其父对象、树和 blob 找到该对象，则该对象可以从该提交“访问”。在获取期间，客户端告诉服务器它想要哪些提交以及它已经拥有哪些提交。服务器找到可从所需提交访问的对象，排除它知道客户端已经拥有的对象，并将剩余部分作为包文件以 Git 在磁盘上使用的相同格式发送。完整克隆开始时没有任何对象，因此它需要从正在克隆的历史记录中可访问的所有对象。

推送通过要求服务器更新一个或多个引用来向另一个方向传输对象。客户端使用服务器的一组广告引用来避免发送服务器已有的对象。因此，发送的包可以依赖于现有的对象：单独接收包不足以重建新的历史记录。

复制 Git 存储库意味着保持对象和引用在多个服务器上可用。在副本可以提供引用的新值之前，它必须能够提供可从该值访问的对象。该服务还需要协调竞争的“参考更新”，即尝试将同一分支从同一旧提示移动到不同的新提交的推送。对存储库的所有写入施加单一顺序的系统可能会使对不相关分支的推送相互等待。

## 现有的分布式Git服务模式

在设计 Pando 时，我们评估了使用 Git 扩展源代码控制的传统方法：一种使用三阶段提交（3PC，一种用于协调跨多个节点提交的协议）协调存储库副本之间的引用更新，另一种通过 Blob 存储中的共享预写日志（WAL，应用之前写入的更改记录）来排序更新。

### 三阶段提交（3PC）

在我们建模的三阶段提交设计中，Git 服务在多个副本上保留存储库的完整副本。当任何服务器收到推送时，传入的包文件将被复制并并行发送到所有副本。要发布推送，大多数副本必须接受引用更新。管理此操作的服务器是协调器，它需要协调器和每个其他副本之间进行多轮通信。

为了接受引用更新，每个副本都会锁定其引用的副本，并检查它是否仍然指向客户端期望的提交。然后，协调器向接受的副本发送一条预提交消息。一旦大多数人确认预提交消息，协调员就会告诉他们执行更新。然后，任何最新的副本都可以从其存储库的本地副本通告新的分支提示。

保留完整的副本可以在本地提供读取服务，并保证客户端无论选择哪个副本都可以获得所有引用的一致视图。因此，引用一次更新一个，并且每次推送都需要多次往返来协调副本之间的引用更新。

等待仲裁会将副本磁盘性能和通信延迟置于推送路径上。随着写入量的增长，副本必须跟上传入包和读取流量。

### 预写日志 (WAL)

在我们建模的基于 WAL 的设计中，Git 服务使用 Blob 存储中的共享清单来排序存储库中的更新。当服务器收到推送时，它将传入的包文件上传到 blob 存储，并在存储库的本地副本中准备引用更新。为了发布推送，它会向存储在 blob 存储中的共享清单添加一个条目，该条目记录引用更新并指向 packfile。然后，Git 服务器使用比较和交换操作更新清单。这会自动替换清单，否则会拒绝更改。如果另一个编写者同时更新了它，服务器会读取中间条目，检查其引用更新是否仍然有效，并使用已上传的包重试。

编写者可以并行上传他们的包文件，但即使推送到不相关的分支也需要更新相同的清单。成功比较和交换的往返时间限制了存储库发布新清单的频率。低延迟的 blob 存储使这一步变得更快。批处理允许一个清单同时更新多个引用，但代价是排队更新和增加延迟。

Blob 存储可以并行接收包文件，但对共享清单的更新仍然相互竞争。仅增加 Blob 存储的容量并不能解决该瓶颈。每个副本仍需要从 Blob 存储中读取包并为其建立索引，然后才能在本地提供这些包。如果传入的写入速度超过了工作速度，副本就会落后，客户端会等待更长时间才能获取新推送的提交。

这让我们想到了潘多。 Pando 是一种为 Git 存储库提供服务的新架构，其目标是扩展到许多客户端同时推送。它的工作原理如下：

### 重新思考约束

在开发 Pando 之前，我们有一种预感，我们可以在不影响 Git 的情况下满足我们的要求，但我们确实需要在大多数 Git 系统认为是要求的一些事情上做出妥协：

- **存储库范围内的一致性**：提供所有引用的一致的时间点快照需要跨存储库进行协调。在将所有引用更新一起排序的系统中，推送到不相关的分支在单个协调点上竞争。
- **每个客户端都有唯一的包文件**：如果具有不同本地历史记录的两个客户端获取相同的分支，服务器可能需要为每个客户端生成不同的包，以避免发送它们已经拥有的对象。创建这些响应会消耗 CPU 和磁盘 I/O，因此难以扩展到大量读取器。

相反，Pando 提供了宽松的一致性模型（因果一致性）来扩展写入，并重用包文件来扩展读取。

### 因果一致性 (CC)

当客户端推送到分支时，Pando 将传入的包文件作为不可变的 blob 存储在 blob 存储中。每次分支移动时，Pando 都会在元数据存储中记录一个“参考版本”，其中包含新提示、提供该提示的包以及该包所依赖的任何早期参考版本。 Blob 存储和元数据存储都是水平可扩展的。

从 Pando 获取提交或引用需要向客户端重放一组引用版本（包文件），从而重建创建所获取的引用版本的客户端的状态。这在整个存储库中提供了较弱的一致性形式，同时为单个引用的更新提供了可序列化性。客户端仅在同时推送到同一引用时才会发生冲突。读取多个分支的客户端不能假设这些读取描述了存储库中的单个时间点。

![在左侧，三个连续的主干包包含提交 A、B 和 C； D 和 E；在右侧，主干和主题在 C 处分叉。主干前进到 G，而主题前进到 D、E 和 F。最新的主题包包含 D、E 和 F。虚线轮廓标记 D 和 E 也出现在早期的主题包中。蓝色箭头标记了新包对 G 的主干的依赖。F 的 Git 父级是E.](https://images.ctfassets.net/kftzwdyauwt9/5wDkqDPp9fjzOjtAQRDRzw/117b2f107fd11818f7e9154c958b0878/representing-branches-in-pando-diagram-desktop-light.svg?w=3840&q=90)

推送到主干会添加一个增量包，其中包含一个或多个提交。每次推送到侧分支都会再次包含该主题的早期提交，因此具有广告主干版本的客户端可以在一个包中获取该主题。

这是*因果一致性*的一种形式。为了获取参考资料，读者需要观察其作者的历史。在推送过程中，Pando 控制客户端和服务器同意的共享历史记录，确保客户端生成更容易共享的包文件。

因此，Pando 不提供 Git 操作期间所有引用的时间点状态，也不提供克隆或获取中引用更新的顺序。具体来说，假设分支“foo”和“bar”在完整克隆的协商期间都被更新。在协商过程中，一个客户端可能会观察版本 1 的“foo”和版本 2 的“bar”，而另一个客户端可能会观察版本 2 的“foo”和版本 1 的“bar”。实际上，用户和代理对引用更新的全局顺序是不可知的，而是依赖于单个引用的更新顺序。

### 比较方法

在这三个一致性模型的模拟中，我们配置 1,000 个客户端，每个客户端选择一个不同的分支，然后重复推送唯一的提交，测量总挂钟持续时间和推送获取延迟。后者是工作负载的重要指标，因为它测量用户和代理协作或使用依赖版本控制的其他系统的往返时间。该仿真对从商品到高级虚拟机和 blob 存储系统的硬件进行建模。在这个模拟中，我们放宽了三阶段提交的存储库范围的一致性。

综合教学模型，而不是生产基准。平均推送获取涵盖主题推送，从第一次尝试到重试，直到独立读者验证该提交。它包括等待读取器插槽并排除构建和测试。启用合并后，编写器完成包括所需的提取和主干合并。

运行此模拟，将 Pando 与其他两种方法进行比较。选择基础设施（从普通硬件到高级硬件）、客户端数量以及更多设置，以了解它们的比较结果。

当磁盘饱和时，建模的三阶段提交系统在负载下显示出明显更长的写入延迟；同时，出于同样的原因，预写日志系统显示出明显更长的读取延迟，因为服务器很难跟上从日志中读取的速度。在我们的 monorepo 的现实测试和模拟中，Pando 支持数千个客户端，能够同时推送而不影响负载下的性能。

在处理推送时，Pando 会验证传入的包文件，同时将其流式传输到 blob 存储，而不将其解包到本地存储库中。当客户端开始获取时，Pando 选择读者需要的存储包，然后读者下载它们。没有服务器需要将包文件应用到本地存储库或执行昂贵的解包和打包操作。由于这些服务器主要执行协商和包文件选择，因此 Pando 服务器可以在商用硬件上运行。

这使得 Pando 能够扩展到客户端、客户端和 Pando 之间的网络以及 blob 存储服务的限制。有了足够的容量，在独立分支上工作的客户端就可以按照自己的连接允许的速度传输包。为了以这种速度为更多客户提供服务，我们可以添加 Pando 服务器并扩展元数据存储和 blob 存储。

## 在 Pando 中推送和获取分支

Pando 将 writer 的 packfile 存储在 blob 存储中，并将 ref 版本记录在元数据服务中。在获取时，Pando 选择读者需要的包，然后 Express 为他们提供服务。

流式推送获取分支

- 包文件字节
- 元数据
- 请求/确认
- 包文件 URI

代理编辑文件并在本地创建提交，然后运行“git push”，这会创建这些更改的包文件以更新分支。 Pando 接收包并将其流式传输到 blob 存储。在使用单通道解码验证传入推送后，Pando 使用多密钥事务在我们的元数据存储中记录引用版本并自动更新引用指针。这使得 Pando 能够提供“读你自己写”的一致性。整个写入操作需要 *$O(1)$* 元数据读取和写入。

当另一个客户端获取分支时，Pando 使用客户端已有的历史记录选择一组存储的包。此操作需要 *$O(\log \Delta)$* 元数据读取，*$\Delta$* 是客户端拥有的内容与客户端想要的内容之间的参考版本中的最短距离。服务器返回包文件 URI，客户端通过 Express 服务下载它们，该服务将包文件存储在区域缓存中。

此设计依赖于 Pando 架构的三个核心服务：推送、获取和压缩。

### 缩放推送

当客户端推送时，传统的 Git 服务器就像一个扑克玩家展示其所有牌，向客户端显示其拥有的每个分支。然后，客户端收集提交、树和 blob 以创建一个包文件，该包文件*排除*它知道服务器已经拥有的对象。

广告更多的裁判可以使推动力更小。它还可能使包更难重用，因为另一个客户端可能会丢失作者遗漏的对象。

Pando采取了不同的方法。它没有展示其全部信息，而是仅向客户宣传一组选定的分支。这样做有两个原因：

- 为每个裁判提供一致的视图是昂贵的。拥有数百万个分支，仅 ref 广告就可以超过 100 MiB。提供这一点需要每个服务器要么维护当前映射（需要大量的协调开销），要么维护随引用数量扩展的数据库查询。
- 通过仅向客户端提供引用的子集，客户端将生成一个仅取决于服务器明确允许客户端排除的内容的包。跟踪依赖关系允许 Pando 重用客户端在一次推送中生成的包文件，将其作为对后续获取的响应。

随着 Git 服务器公布更多的引用，推送的客户端就有更多的源来排除对象，从而使它们能够生成更小的包。然而，重用这些包文件需要服务器能够证明获取的客户端具有每个依赖项。否则，packfile 可能会省略客户端需要的对象。

另一方面，如果 Git 服务器根本不发布任何广告，客户端将生成一个包含存储库完整历史记录的包文件。该包文件可以被任何其他客户端使用，但要以有效获取完整克隆的任何分支为代价，付出巨大的代价。

广告更多的引用会产生更小的包文件。大部分尺寸的减小可以来自于仅对其中一项进行广告。

默认情况下，当客户端推送新功能分支时，Pando 仅通告指定的主干分支作为基础。这使得广告的大小与存储库获得分支的大小相同，但需要权衡。当工程师多次推送到单个分支或将一个功能分支堆叠在另一个功能分支之上时，客户端必须重新发送主干之外的所有内容。

这会导致连续的分支推送变得更大，包含潜在冗余的对象，并使用额外的客户端带宽。在我们的 monorepo 中，以这种方式生成的包文件中位数低于 20 KiB，第 99 个百分位低于 3 MiB。对于我们来说，这是一个明智的权衡，因为已经拥有广告主干历史记录的读者可以使用该包文件获取分支。

选择要向客户端通告的引用集后，Pando 接受推送并更新其元数据存储。 Pando 将元数据更新分为同步部分和异步部分。同步元数据更新确保客户端可以立即获取新更新的提交。这会写入一个新的 ref 版本，并更新映射到该新版本的 ref 指针，该新版本存储该新提示、用于协商包文件的依赖项以及指向已推送的包文件的链接。

同时，异步工作被记录在同一个事务中，例如调度compaction。对于非常大的推送，仅同步写入提交的子集。这使得我们只需要对元数据存储进行恒定数量的读取和写入，而不管推送的大小。

重要的是，Pando 服务器可以独立接受对不相关引用的推送。唯一有争议的键是 ref 指针，我们使用类似原子比较和交换的操作来保护它。我们可以通过添加 Pando 服务器、元数据存储扩展单元或 Blob 存储来扩展写入吞吐量。

### 线速获取和克隆性能

当客户端执行获取时，它会向服务器提供两组提交 ID，在协议中称为“have”和“want”。在传统的 Git 服务器中，服务器计算有者可到达的对象和有者可到达的对象之间的集合差，压缩它们，并将结果发送到客户端。虽然开源 Git 服务器在本地有各种索引来加速此操作，但这些包文件的计算成本可能很高，并且通常难以缓存。

相反，Pando 使用推送中记录的提交映射来查找客户端的“have”和“want”，将它们解析为一组包含这些提交的引用版本。每个参考版本都链接到 Pando 之前收到的包文件。服务器使用它来解决客户端的需求，选择涵盖客户端所需的对象集的包文件。

#### 计划在 Pando 获取

Pando 将客户端拥有的内容与其想要的内容进行比较，然后选择所需的存储包文件 - 包括任何缺少的分支依赖项。

Pando 将 Git 协议的“haves”和“wants”映射到一系列参考版本。想要一个侧分支意味着想要达到它对主干的依赖关系。

Git 协议仅允许在克隆或获取时在 HTTP 响应中发送单个包文件。然而，Git 协议的一个未被充分重视的功能“packfile-uri”允许服务器返回单独下载其他包的链接。 Pando 专门使用它，并内联传输一个空的包文件。为了支持此功能，OpenAI 对上游“packfile-uri”做出了许多改进。

OpenAI 系统在许多地理区域运行，因此我们维护 Pando 集群，每个集群都有本地缓存​​。包交付服务 Express 会缓存我们的 Blob 存储，而一个单独的服务会缓存元数据存储。这些缓存使 Pando 能够完全从该集群中的缓存状态中处理对提交 ID 的请求或对引用的特殊读取。我们使用一致的散列将对包文件的请求路由到 Express 服务器，缓存命中率超过 99%。

该缓存系统提供极高的吞吐量，能够满足客户端和 Pando 之间的网络限制。使用这些包文件 URI 和本地缓存，我们验证了仅使用标准云提供商虚拟机，我们看到克隆和获取操作使 10 Gbps 网络链接饱和。

### 压缩和第一个字节的时间

对于大多数 Git 服务器来说，重新打包和垃圾收集对于维持不断增长的存储库的性能是必要的。这两个步骤都会回收空间，但都是计算和 I/O 密集型的。

在像 OpenAI 的 monorepo 这样快速移动的存储库中，为自上次获取以来发生的每次推送发送单独的包文件 URI 是不可行的。每天，客户需要下载数万个包文件才能赶上他们的主干。

相反，Pando 在后台组合包来减少这种开销，采用类似于日志结构合并树中的压缩的设计。每次推送都会生成 Pando 所说的“L0”包文件，代表 Pando 可以传输的最小数据单元。随着时间的推移，后台工作人员将这些包文件收集到涵盖一系列参考版本的封面中，从 L0 开始按几何比例缩放。如今，我们的 monorepo 使用了高达 L4 的包文件封面。

这些盖子有双重用途。当一个盖子足够满后，压缩工作人员将认领它并生成一个包文件。这通过重新组织 packfile 内的对象来提高压缩率。但它还通过充当引用版本的跳过列表来提高获取协商性能。通过同时扫描每个级别的索引，Pando 可以选择一组包在对数时间内发送给客户端。这些包文件覆盖，无论是否重新打包，都可以提供更有效的解决方案来获取规划，从而降低 Pando 的吞吐量和延迟要求。

与许多 Git 服务器不同，包文件保存在各个级别，不会被丢弃或垃圾收集。每个级别的包都用于根据客户在获取中请求的“拥有”和“想要”来持续为客户提供服务。对于使用 Pando 作为 API 的客户端来说，从包文件中读取任意对象往往需要从 L0 读取比从 L4 读取更少的数据，因为它不太可能被压缩。

Pando 中的压缩显着减少了发送给客户端的总传输大小，并使包规划能够根据客户端落后的程度进行亚线性扩展。这对于大型且快速变化的存储库尤其重要，我们预计这将成为软件开发的新常态。

在验证 Pando 的设计时，我们采用了多种方法。我们应用我们的原则来[构建更安全的软件基础⁠](https://openai.com/index/cooperative-disclosure-of-ritic-vulnerability/#building-more-secure-software-foundations)。作为一个全新项目，我们选择在 Rust 中实现 Pando，并且没有遗留依赖。我们编写了一个一致性测试套件，以便代理可以根据标准 Git 行为测试他们的更改。我们还开发了确定性模拟测试工具，使我们能够检查系统的不变量和属性，使我们能够发现并减轻谈判和包装规划中微妙的竞争条件和回归。

我们最初部署 Pando 是作为我们现有源代码控制系统的读写代理。这使我们能够保持 Pando 和之前的系统同步，这样我们就可以安全地将流量转移到 Pando 上，而无需停机。

作为缓存设计的一部分，Pando 还可以在代理之前删除重复数据并合并请求。这使我们能够在将系统一次迁移到 Pando 时保持现有工具的正常运行。随着我们将更多工作负载迁移到 Pando，它们的推送填充了 Pando 的缓存并提高了我们之前后端的可靠性。

为了优化使用 Pando 时的性能，我们开始将 Git 的公共发行版运送到开发人员计算机和 ChatGPT 桌面应用程序中。为了将客户端迁移到 Pando，我们使用了 Git CLI 的内部包装器来分阶段迁移客户端。我们创建了许多其他工具来处理变更请求、代码审查和自动化 API。我们迁移了数百个依赖于旧版 API、Webhook 和存储库下载以及 Git 流量的集成。

Codex 本身帮助开发人员和团队采取了行动。我们创建了准备现有结帐并指导代理商使用新系统的技能。因此，开发人员只需要求 Codex 迁移他们的开发环境和服务即可。
