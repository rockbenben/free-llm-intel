# 深度学习的基础设施

配图：Ludwig Pettersson

深度学习是一门经验科学，一个团队的基础设施质量是进度的乘数。幸运的是，今天的开源生态让任何人都能打造优秀的深度学习基础设施。

## 概述

在这篇文章中，我们将分享深度学习研究通常如何推进、描述我们为支撑研究做出的基础设施选择，并开源 [kubernetes-ec2-autoscaler⁠（在新窗口中打开）](https://github.com/openai/kubernetes-ec2-autoscaler)——一个面向批处理优化的 Kubernetes 弹性伸缩管理器。希望这篇文章能对你构建自己的深度学习基础设施有所帮助。

## 使用场景

典型的深度学习进展始于一个想法，你会先在一个小问题上测试它。在这个阶段，你需要快速跑许多临时实验。理想情况下，你可以直接 SSH 登录一台机器，在 screen 里跑一个脚本，不到一小时就拿到结果。

要让模型真正可用，通常需要你见到它以任何可以想到的方式失败，并想办法修复这些局限。（这与构建任何新软件系统类似——你会把代码运行很多遍，建立对其行为的直觉。）

因此，深度学习基础设施必须允许用户灵活地内省模型，仅仅暴露汇总统计量是不够的。

当模型显示出足够前景后，你会把它扩展到更大的数据集和更多 GPU 上。这需要消耗大量机时、持续数天的长任务。你需要细致的实验管理，并对所选超参数范围做极其用心的思考。

早期研究过程是无结构、快节奏的；后者则是有条理、有些痛苦的，但两者对于取得出色结果都绝对必要。

## 一个例子

论文 [Improved Techniques for Training GANs⁠（在新窗口中打开）](https://arxiv.org/abs/1606.03498) 始于 [Tim Salimans⁠（在新窗口中打开）](http://timsalimans.com/) 为改进[生成对抗网络⁠](https://openai.com/index/generative-models/#gan)训练而构思的若干想法。我们描述其中最简单的那个（它恰好产出了最好看的样本，尽管并非最好的半监督学习）。

GAN 由生成器和判别器两个网络组成。生成器试图欺骗判别器，判别器则试图区分生成数据与真实数据。直觉上，能骗过所有判别器的生成器就很不错。但存在一种难以修复的失败模式：生成器可能“崩溃”（collapse），永远输出完全相同的（很可能看起来还很真实的！）样本。

Tim 的想法是给判别器输入整个 [minibatch⁠（在新窗口中打开）](https://www.coursera.org/learn/machine-learning/lecture/9zJUs/mini-batch-gradient-descent) 的样本，而不只是单个样本。这样判别器就能分辨生成器是否只产出一张图片。一旦发现崩溃，梯度就会传回生成器以纠正问题。

下一步是在 [MNIST⁠（在新窗口中打开）](http://yann.lecun.com/exdb/mnist/) 和 [CIFAR-10⁠（在新窗口中打开）](https://www.cs.toronto.edu/~kriz/cifar.html) 上快速验证想法。这要求以最快速度搭建小型原型、在真实数据上运行并检查结果。经过几轮快速迭代，Tim 得到了非常鼓舞人心的 [CIFAR-10 样本⁠（在新窗口中打开）](https://cdn.openai.com/infrastructure-for-deep-learning/cifar10samples-2.jpg)——差不多是我们在这个数据集上见过的最好的样本。

然而，深度学习（以及一般意义上的 AI 算法）必须扩展规模才能真正惊艳——小神经网络只是概念验证，大神经网络才真正解决问题并有用。于是 [Ian Goodfellow⁠（在新窗口中打开）](https://www.linkedin.com/in/ian-goodfellow-b7187213) 着手把模型扩展到 [ImageNet⁠（在新窗口中打开）](http://image-net.org/) 上。

我们的模型学习生成 ImageNet 图像

面对更大的模型和数据集，Ian 需要把模型并行到多个 GPU 上。每个任务都会把多台机器的 CPU 和 GPU 利用率推到 90%，即便如此，模型也需要训练数天。在这种状态下，每个实验都弥足珍贵，他会一丝不苟地记录每个实验的结果。

最终，虽然结果不错，但没有达到我们的期望。我们测试了许多关于原因的解释，仍未破解。科学的本质就是如此。

## 基础设施

### 软件

我们 TensorFlow 代码的一个片段

我们绝大多数研究代码用 Python 编写，正如我们的开源项目所反映的：[improved-gan⁠（在新窗口中打开）](https://github.com/openai/improved-gan)、[vime⁠（在新窗口中打开）](https://github.com/openai/vime)、[iaf⁠（在新窗口中打开）](https://github.com/openai/iaf)、[imitation⁠（在新窗口中打开）](https://github.com/openai/imitation)。GPU 计算上我们主要使用 [TensorFlow⁠（在新窗口中打开）](https://www.tensorflow.org/)（特殊情况下用 [Theano⁠（在新窗口中打开）](http://deeplearning.net/software/theano/)）；CPU 上我们使用它们或 [Numpy⁠（在新窗口中打开）](http://www.numpy.org/)。研究人员有时也会在 TensorFlow 之上使用 [Keras⁠（在新窗口中打开）](https://keras.io/) 这类更高层的框架。

与深度学习社区的普遍做法一样，我们使用 Python 2.7。我们通常使用 [Anaconda⁠（在新窗口中打开）](https://www.continuum.io/anaconda-overview)，它对 [OpenCV⁠（在新窗口中打开）](http://opencv.org/) 等本来难以安装的科学库提供了方便的打包和[性能优化⁠（在新窗口中打开）](https://docs.continuum.io/anaconda/#high-performance)。

### 硬件

对于理想的批处理任务，集群节点数量翻倍应使任务运行时间减半。遗憾的是，在深度学习中，人们通常看到多 GPU 带来的加速是非常[次线性⁠（在新窗口中打开）](https://research.googleblog.com/2016/04/announcing-tensorflow-08-now-with.html)的。因此顶级性能需要顶级 GPU。我们也大量使用 CPU 跑[模拟器⁠（在新窗口中打开）](https://gym.openai.com/envs#box2d)、[强化学习环境⁠（在新窗口中打开）](https://gym.openai.com/envs#atari)或小型模型（这类模型在 GPU 上并不会更快）。

nvidia-smi 显示满载的 Titan X

[AWS⁠（在新窗口中打开）](https://aws.amazon.com/) 慷慨地同意向我们捐赠大量算力。我们把 AWS 用于 CPU 实例以及 GPU 任务的横向扩容。我们也自建物理服务器，主要运行 [Titan X⁠（在新窗口中打开）](http://www.geforce.com/hardware/10series/titan-x-pascal) GPU。我们预期长期会采用混合云：尝试不同的 GPU、互联方式以及其他可能对未来深度学习至关重要的技术，非常有价值。

同一台物理机上的 htop，显示 CPU 仍有大量空闲。我们通常把 CPU 密集型负载与 GPU 密集型负载分开运行。

### 资源供给

我们像很多公司对待产品一样对待基础设施：必须呈现简单的接口，可用性与功能同样重要。我们使用一套统一的工具来管理所有服务器，并把它们配置得尽可能一致。

我们用于管理 Auto Scaling 组的 Terraform 配置片段。Terraform 会创建、修改或销毁你正在运行的云资源，使其与配置文件一致。

我们用 [Terraform⁠（在新窗口中打开）](https://www.terraform.io/) 搭建 AWS 云资源（实例、网络路由、DNS 记录等）。我们的云端和物理节点都运行 [Ubuntu⁠（在新窗口中打开）](http://www.ubuntu.com/)，并用 [Chef⁠（在新窗口中打开）](https://www.chef.io/chef/) 配置。为了更快的启动时间，我们用 [Packer⁠（在新窗口中打开）](https://www.packer.io/) 预烘焙集群 AMI。我们所有集群都使用互不重叠的 IP 段，并通过公网互联：用户笔记本用 [OpenVPN⁠（在新窗口中打开）](https://openvpn.net/)，物理节点用 [strongSwan⁠（在新窗口中打开）](https://www.strongswan.org/)（充当 AWS 的 [Customer Gateway⁠（在新窗口中打开）](http://docs.aws.amazon.com/AmazonVPC/latest/NetworkAdminGuide/Introduction.html)）。

我们把用户的家目录、数据集和结果存放在 [NFS⁠（在新窗口中打开）](https://en.wikipedia.org/wiki/Network_File_System)（物理硬件上）以及 [EFS⁠（在新窗口中打开）](https://aws.amazon.com/efs/)/[S3⁠（在新窗口中打开）](https://aws.amazon.com/s3/)（AWS 上）。

### 编排

可扩展的基础设施往往会让简单的事情变复杂。我们在小规模与大规模任务的基建上投入同等精力，并持续打磨工具箱，让分布式使用场景像本地一样触手可及。

我们提供一组可 SSH 登录的节点（含带 GPU 与不带 GPU 的）用于临时实验，并把 [Kubernetes⁠（在新窗口中打开）](http://kubernetes.io/) 作为物理节点和 AWS 节点的集群调度器。我们的集群横跨 3 个 AWS 区域——我们的任务突发性强，有时会在单个区域撞上容量上限。

Kubernetes 要求每个任务都是 Docker 容器，这给了我们依赖隔离和代码快照。但构建新的 Docker 容器可能给研究者的迭代周期增加宝贵的额外秒数，所以我们也提供工具，把研究者笔记本上的代码透明地推送进标准镜像。

TensorBoard 中的模型学习曲线

我们把 Kubernetes 的 [flannel⁠（在新窗口中打开）](https://coreos.com/flannel/docs/latest/) 网络直接开放给研究者的笔记本，让用户无缝访问自己正在运行的任务。这对于访问 [TensorBoard⁠（在新窗口中打开）](https://www.tensorflow.org/versions/r0.10/how_tos/summaries_and_tensorboard/index.html) 等监控服务尤其有用。（我们最初的方案——从严格隔离的角度看更干净——要求为每个想暴露的端口创建一个 Kubernetes [Service⁠（在新窗口中打开）](http://kubernetes.io/docs/user-guide/services/)，但我们发现摩擦太大。）

## kubernetes-ec2-autoscaler

我们的工作负载突发且不可预测：一条研究线可能很快从单机实验变成需要 1,000 核。例如，几周内，一个实验从单块 Titan X 的交互阶段，到 60 块 Titan X 的实验阶段，再到需要近 1,600 块 AWS GPU。因此我们的云基础设施需要动态供给 Kubernetes 节点。

在 [Auto Scaling⁠（在新窗口中打开）](https://aws.amazon.com/autoscaling/) 组里运行 Kubernetes 节点很容易，但要正确管理这些组的规模就难了。批处理任务提交后，集群确切知道自己需要什么资源，应当直接分配。（相比之下，AWS 的 [Scaling Policies⁠（在新窗口中打开）](http://docs.aws.amazon.com/autoscaling/latest/userguide/policy_creating.html) 会零敲碎打地新建节点直到资源不再耗尽，可能需要多轮迭代。）此外，集群需要在终止节点前先[排空⁠（在新窗口中打开）](http://kubernetes.io/docs/user-guide/kubectl/kubectl_drain/)（drain）它们，以避免丢失进行中的任务。

直接用裸 EC2 跑大型批处理任务很诱人，事实上我们最初就是这么做的。但 Kubernetes 生态带来了很多价值：低摩擦的工具、日志、监控、把物理节点与运行中实例分开管理的能力，等等。让 Kubernetes 正确自动扩容，比在裸 EC2 上重建这一生态要容易。

我们正在发布 [kubernetes-ec2-autoscaler⁠（在新窗口中打开）](https://github.com/openai/kubernetes-ec2-autoscaler)，一个面向批处理优化的 Kubernetes 弹性伸缩管理器。它以普通 [Pod⁠（在新窗口中打开）](http://kubernetes.io/docs/user-guide/pods/) 的形式运行在 Kubernetes 上，唯一要求是你的工作节点位于 Auto Scaling 组中。

我们 Kubernetes 集群的 Launch Configurations

该 autoscaler 的工作原理是轮询 Kubernetes master 的状态——其中包含计算集群资源需求与容量所需的一切。若容量过剩，它排空相关节点并最终终止。若需要更多资源，它计算应创建哪些服务器并相应增大 Auto Scaling 组规模（或直接[解除封锁⁠（在新窗口中打开）](http://kubernetes.io/docs/user-guide/kubectl/kubectl_uncordon/)已排空的节点，避免新节点的启动时间）。

kubernetes-ec2-autoscaler 支持多个 Auto Scaling 组、CPU 之外的资源（内存和 GPU），以及对任务的细粒度约束，如 AWS 区域和实例规格。此外，突发负载可能导致 Auto Scaling 组超时和报错——出人意料的是，连 AWS 也没有无限容量。此时 kubernetes-ec2-autoscaler 会检测到错误并溢出（overflow）到第二个 AWS 区域。

我们的基础设施旨在最大化深度学习研究者的生产力，让他们专注于科学本身。我们正在构建工具以进一步改善基础设施与工作流，并将在未来的数周和数月内分享这些成果。欢迎[加入我们⁠（在新窗口中打开）](https://jobs.lever.co/openai/f7801a92-1e2f-4656-a572-962b53ec34f6)，让这一切更快！
