# 借助 MRC 多路径可靠连接，释放大规模 AI 训练网络


前沿模型训练依赖可靠的超算网络，能在 GPU 之间快速搬运数据。为把这件事做得更快、更高效，OpenAI 与 AMD、Broadcom、Intel、Microsoft 和 NVIDIA 合作开发了 MRC（Multipath Reliable Connection，多路径可靠连接）：一种新型协议，可提升大规模训练集群中 GPU 网络的性能与韧性。我们于今日通过开放计算项目（OCP）[发布了 MRC⁠(opens in a new window)](https://www.opencompute.org/documents/ocp-mrc-1-0-pdf)，以便更广泛的业界使用它。

每周使用 ChatGPT 的人数已超过 9 亿，我们的系统正在成为 AI 的核心基础设施，帮助全球个人和企业基于能力越来越强的模型进行创造。在 [Stargate⁠](https://openai.com/index/building-the-compute-infrastructure-for-the-intelligence-age/) 启动之前，我们用几年时间与合作伙伴密切协作，谨慎地共同开发、上线并运维了前三代超算。这些宝贵经验让我们坚信：要在 Stargate 这一量级上高效利用算力并完成我们的使命，就必须重新审视并大幅削减整个栈每一层的复杂度——包括网络设计。

发布 MRC 规范是 OpenAI 整体算力战略的一部分：在关键基础设施层采用共享标准，能让 AI 系统更高效、更可靠地扩展，并覆盖更广泛的合作伙伴生态。在本文中，我们将介绍 MRC 的设计，包括：i）它如何让我们构建多平面高速网络，以更少的组件和更低的功耗形成冗余，从而抵御网络故障；ii）MRC 的自适应分组喷洒如何几乎消除核心拥塞；iii）我们的部署如何使用静态源路由绕过故障，消除一整类路由失效。这些优势合力让我们能更快地为每个人交付更好的模型。

## 为什么网络需要新设计

训练大型 AI 模型时，单个训练步可能涉及数百万次数据传输。一次传输迟到，就会波及整个作业，可能让 GPU 空转。网络拥塞、链路故障和设备故障是传输延迟和抖动最常见的来源。

随着集群规模扩大，这些问题变得更频繁、也更难解决。这使网络技术成为 Stargate 设计中的关键一环。

为了支撑 Stargate 超算当前的规模，我们面临两大网络挑战。首先，只要可能，就应尽量降低网络拥塞发生的可能性。有些瓶颈不可避免，比如两块 GPU 同时向同一目的地发送。但在这些情况之外，我们应当通过设计来避免拥塞。

其次，我们必须把网络故障对训练作业本身的影响降到最低。在足够大的规模下，即使最好的网络也会有持续一定水平的链路和交换机故障。以往，一次故障往往导致训练作业崩溃，迫使从保存的检查点重启，或者让进度停滞数十秒，等待网络重新计算路由。这类中断在 GPU 周期和时间上都很昂贵。对于同步预训练——许多机器上的许多 GPU 步调一致地协同训练同一个 AI 模型——尤其如此。作业越大，任何一次链路抖动或故障的影响就越大。这些负载实际上充当着"故障放大器"，因此防止放大已成为关键。

## 我们的答案：MRC

我们的目标不只是搭一张快网，而是要搭一张即便在故障下也能提供高度可预测性能、让训练作业持续推进的网络。

为了实现这种可靠性，我们的 Scaling 团队在过去两年与 [AMD⁠(opens in a new window)](https://www.amd.com/en/blogs/2026/amd-advances-ai-networking-at-scale-with-mrc.html)、[Broadcom⁠(opens in a new window)](https://www.broadcom.com/blog/enabling-ai-networking-scale-with-multi-path-reliable-connections-mrc-)、Intel、[Microsoft⁠(opens in a new window)](https://aka.ms/BuildingResilientNetworksForAISupercomputers) 和 [NVIDIA⁠(opens in a new window)](https://blogs.nvidia.com/blog/spectrum-x-ethernet-mrc/) 合作，开发出一种构建和运维网络的新方式。这一合作的成果就是我们所称的 [多路径可靠连接（MRC）⁠(opens in a new window)](https://cdn.openai.com/pdf/resilient-ai-supercomputer-networking-using-mrc-and-srv6.pdf)。这是一种内置于最新 800Gb/s 网络接口中的新网络协议，能让我们把一次传输分散到数百条路径上，在微秒级绕过故障路由，并运行更简单的网络控制平面。

MRC 扩展了 RoCE（RDMA over Converged Ethernet，融合以太网上的 RDMA）——这是 InfiniBand 贸易协会（IBTA）标准，让 GPU 与 CPU 之间能够实现硬件加速的远程直接内存访问。MRC 借鉴了超以太网联盟（UEC）开发的技术，并以基于 SRv6 的源路由加以扩展，以支撑大规模 AI 网络架构。

MRC 已经在 OpenAI 所有用于训练前沿模型的最大规模 NVIDIA GB200 超算上部署，包括我们与 Oracle Cloud Infrastructure（OCI）在德州 Abilene 合作的站点，以及 Microsoft 的 Fairwater 超算。MRC 已被用于训练多个 OpenAI 模型，所用硬件来自 NVIDIA 和 Broadcom。今天，MRC 规范作为 OCP 的贡献对社区开放，供使用与扩展。我们共同撰写并发表了一篇详述我们经验的论文：[*Resilient AI Supercomputer Networking using MRC and SRv6*⁠(opens in a new window)](https://cdn.openai.com/pdf/resilient-ai-supercomputer-networking-using-mrc-and-srv6.pdf)。

## 根基：多平面网络

构建高韧性网络，要求我们从这样一种网络拓扑起步：它具备足够的天然冗余，即便网络中的链路或交换机出现故障，所有流依然能够获得良好性能。

我们不是把每个网络接口视为一条 800Gb/s 链路，而是把它拆分成多条较小的链路。例如，一个接口可以连接到八台不同的交换机。这样你可以构建八个彼此并行的独立网络（称为平面，plane），每个平面运行在 100Gb/s，而不是一张 800Gb/s 的单一网络。

这一改变对集群形态影响巨大。一台可以以 800Gb/s 连接 64 端口的交换机，改为可以以 100Gb/s 连接 512 个端口。这让你只需两层交换机，就能搭建一张完全连接约 131,000 块 GPU 的网络。传统的 800Gb/s 网络则需要三到四层。

*MRC 对多平面网络的支持意味着，我们只需两层交换机就能连接超过十万块 GPU。相比传统方案，这降低了所需电力、可能失效的组件数量以及网络总成本。*

结果是一张成本更低、功耗更低，并且比传统网络设计提供更多路径多样性的网络。它还能让更多流量停留在 Tier 0 交换机本地，从而提升性能。

然而，这些路径多样性可能难以被充分利用。AI 训练常用的传统网络协议通常要求每一次传输只沿一条路径走，以便按序到达。在一张大型多平面网络中，这带来两个问题：不同的流会在同一条链路上碰撞造成拥塞，每个流也只能用到诸多平面中的一个。如果我们不做任何其他改变，多平面网络将导致严重拥塞和糟糕的整体性能。

*单路径流，例如经典 RoCE 部署，会频繁让个别链路变得拥塞。因为集合通信对最坏时延敏感，这对 AI 训练负载尤其具有破坏性。*

## MRC 的转变：把分组喷洒到数百条路径上

MRC 从根本上改变了这一模型。MRC 不再把一次传输绑定到一条路径，而是把一次传输的分组喷洒到我们网络中的数百条路径上，横跨所有不同的平面。分组可能乱序到达，但所有 MRC 分组都携带其最终内存地址，因此目标端可以在分组到达时就把它们交付到内存。

*MRC 一次把分组分散到多条路径上，减少拖慢同步 AI 训练的拥塞。*

*通过将流量分散到多条路径，MRC 避免了网络热点，防止部分事务远比其他事务耗时。这防止了会影响同步 AI 训练的减速。*

*跨多条路径的分组喷洒。动画由 Mark Handley 制作。*

每个 MRC 连接会为其使用的多条路径保留少量状态。如果检测到某条路径开始拥塞，它就会把这条路径换成另一条，从而均衡整个网络的负载。如果丢了一个分组，它会采取保守选择：假设该路径上出了某种故障，立即停止使用它，并重传所有可能丢失的分组。MRC 弃用一条路径后，会发送探测分组以检查是否真的发生了故障，以及如果发生了，是否已经恢复。

故障并不是丢包的唯一原因；另一种常见的丢包原因是目的地侧的拥塞。MRC 通过分组裁剪（packet trimming）来处理这一情况。如果交换机本会因拥塞丢弃某个分组，它会把有效载荷裁掉，只把头部转发给目的地，从而触发显式的重传请求。分组裁剪减少了误判——即错误地假设丢包就意味着路径故障。

多平面拓扑、喷洒、负载均衡与裁剪的组合，使得一条 MRC 连接能在微秒级检测到网络故障并绕开它们，将对同步训练作业的影响降到最低。相比之下，传统网络架构可能需要数秒乃至数十秒才能稳定并绕过故障。

## 用源路由取代动态路由

MRC 让我们在网络简化上更进一步。

传统上，交换机会运行 BGP（边界网关协议）等动态路由协议来计算可用路径并绕过故障。但交换机是运行复杂软件的复杂设备。当它们以微妙的方式失效时，这类问题很难诊断，并可能在被修复之前导致连接失败。

有了 MRC，动态路由不再那么必要。如果某条路径丢包，MRC 就停止使用它。我们采取了更激进的做法：禁用动态路由，改用 IPv6 段路由（SRv6）。SRv6 让发送方直接指定每个分组在网络中应当走的路径。做法是把交换机标识序列嵌入每个分组的目的地址中。

*SRv6 允许发送方对分组经过网络的完整路径进行编码。因为路径是确定的，发送方可以独立地针对某条路径上的拥塞或丢包作出反应。*

拆解一下：转发时，交换机会检查自己的标识是否在字段中。如果在，它通过把目的地址右移来移除这一标识，从而露出下一台交换机的标识。然后交换机在一张静态路由表中查找这一标识，由它决定分组下一跳的位置。与动态路由不同，这张静态路由表在交换机首次配置时就设好，之后不再更改。

MRC 使用 SRv6 把分组喷洒到所有网络平面，同时也并行喷洒到每个平面上的多条路径。若一条路径故障，MRC 就停止使用它。交换机不需要重新计算路由，也不需要做任何事——只需按静态路由盲从转发即可。

## 生产环境下的实际表现

我们的训练网络有数百万条链路。虽然这些网络质量很高，但在足够大的规模下，某些链路抖动不可避免。训练过程中，我们观察到 tier-0 与 tier-1 交换机之间每分钟出现多次链路抖动的情况，但 MRC 确保它们对我们的同步预训练作业没有可测量的影响。实际上，影响小到我们甚至不需要优先立刻修复这些链路。

不只是链路会故障。在为 ChatGPT 和 Codex 训练一款近期前沿模型时，我们不得不重启四台 tier-1 交换机。以往，重启一台交换机会要求运维团队极为小心，避免打扰训练。有了 MRC，我们甚至不需要与集群中运行训练作业的团队协调。许多链路修复也是如此。过去，当需要维护时必须与运维团队协调禁用一条链路。如今，我们可以在链路仍在使用时就进行修复。如果一条链路仍然工作得足够好，MRC 就会使用它；否则 MRC 会避开它，直到修好为止。

*训练运行期间采集的真实数据，展示 MRC 对一台 T1 交换机完全失效的应对。训练作业出现短暂减速，但很快恢复。*

在 MRC 之前，如果 GPU 网络接口与 tier-0 交换机之间的一条链路故障，训练作业就会失败。有了 MRC，作业能以合理的性能继续运行。若一个 8 端口网络接口失去一个端口，最大速率下降 1/8。MRC 会检测到这一点，重新计算路径以避开失效的平面，并立即通知对端不要使用该平面接收流量。大多数故障链路会在 1 分钟内恢复，此时 MRC 会重新启用该平面。

失去一条 GPU 接口链路造成的减速因训练作业而异，但实践中，往往明显低于所失去的物理容量。

## 关键改进

MRC 最终为我们在扩展超算时带来三项关键优势。

第一，它让我们只需两层以太网交换机，就能为超过 100,000 块 GPU 的超算搭建多平面高速网络。这给我们提供了足够的冗余抵御网络故障，同时功耗低于同等的三/四层单平面网络。

第二，MRC 的自适应分组喷洒能如此良好地做负载均衡，使我们几乎看不到网络核心的拥塞。这极大地减少了同步训练中不同流之间吞吐的差异——在同步训练中，消除离群值是性能的核心。这也意味着，多个作业共享集群时，彼此不会相互影响性能。

最后，MRC 使用 SRv6 源路由快速绕过故障、只把分组发送到正常工作的路径上。这让我们能运行简单的静态网络控制平面，消除一整类动态路由失效行为。

## 开放协议

MRC 显著提升我们训练新型前沿模型的能力，确保网络能跟上研究人员雄心勃勃的 AI 路线图。相比以往方法，MRC 带来重大改进，助力我们可靠地把 AGI 的益处带给每一个人这一目标加速实现。我们为这一跨行业合作感到自豪。

随着训练集群持续增长，网络设计日益决定可用算力中实际能被使用的比例。MRC 帮助 GPU 在拥塞、链路故障和维护事件面前保持协同推进——这些事件在以往会打断训练。在真正的规模下，这种可靠性和效率并非锦上添花，而是让同步前沿模型训练成为可能的必要条件之一。
