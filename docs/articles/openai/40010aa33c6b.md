# 关于语言模型安全与滥用的经验教训

我们阐述最新的思考，希望帮助其他 AI 开发者应对已部署模型的安全与滥用问题。

阅读研究议程

配图：Justin Jay Wang

## 概述

部署强大 AI 系统带给我们对安全与滥用的理解，远比仅靠研究所能获得的更丰富。值得注意的是：基于 API 的语言模型滥用形式常常与我们最担心的不同；我们发现了现有语言模型评估的局限，正以新的基准和分类器来弥补；基础研究性的安全工作对 AI 系统的商业实用性也有显著助益。

过去两年里，我们对语言模型如何被使用与滥用了解了许多——这些洞识若没有真实部署的经历就无法获得。2020 年 6 月，我们开始向开发者和研究者开放 [OpenAI API⁠](https://openai.com/api/)——一个访问并基于 OpenAI 新研发的 AI 模型构建应用的接口。以降低伤害风险的方式部署 GPT-3、Codex 及其他模型，带来了各种技术与政策挑战。

## 我们的模型部署方法概述

大型语言模型现在能够执行[极其广泛的任务](https://arxiv.org/abs/2005.14165)，且常常开箱即用。它们的风险概况、潜在应用以及对社会的更广泛影响，仍[未被充分](https://arxiv.org/abs/2108.07258)[理解](https://arxiv.org/abs/2102.02503)https://deepmind.com/research/publications/2021/ethical-and-social-risks-of-harm-from-language-models。因此，我们的部署方法强调持续迭代，并运用以下策略，力求在降低相关风险的同时最大化部署的收益：

- 部署前风险分析，借助不断丰富的安全评估和红队测试工具（例如，我们用下文[讨论过的⁠](https://openai.com/index/language-model-safety-and-misuse/#risk-impact-measurement)评估来检查 InstructGPT 是否存在安全退化）
- 从小规模用户群起步（例如，GPT-3 和我们的 [InstructGPT⁠](https://openai.com/index/instruction-following/) 系列最初都是私有 beta）
- 研究新型用例试点的结果（例如，与少数客户合作，探索我们可以在什么条件下安全地开启长篇内容生成）
- 实施有助于掌握使用态势的流程（例如，用例审查、token 配额和速率限制）
- 开展详细的复盘审查（例如，对安全事件和重大部署进行回顾）

负责任部署没有灵丹妙药，因此我们努力在开发和部署的每个阶段了解并应对模型的局限与潜在的滥用途径。这一做法让我们能在小规模下尽可能多地了解安全与政策问题，并在启动更大规模部署之前吸收这些经验。

> “负责任部署没有灵丹妙药。”

我们迄今投入的领域（不穷尽）包括[A](https://openai.com/index/language-model-safety-and-misuse/#citation-bottom-A)：

- 预训练[数据](https://arxiv.org/abs/2005.14165)的策划与过滤
- [微调⁠](https://openai.com/index/improving-language-model-behavior/)模型以更好地[遵循指令⁠](https://openai.com/index/instruction-following/)
- 对潜在部署进行风险分析
- 提供详尽的用户[文档](https://beta.openai.com/docs/introduction/overview)
- 构建[工具](https://beta.openai.com/docs/engines/content-filter)筛查有害的模型输出
- 依据我们的[政策](https://beta.openai.com/docs/usage-guidelines)审查用例
- 监控[滥用⁠](https://openai.com/index/language-model-safety-and-misuse/#misuse)迹象
- 研究我们[模型的影响⁠](https://openai.com/index/language-model-safety-and-misuse/#risk-impact-measurement)

每个干预环节都有局限，因此必须采取整体性的方法。

有些方面我们本可以做得更好，至今仍改进空间。例如，我们最初做 GPT-3 时，把它看作内部研究成果而非生产系统，对有毒训练数据的过滤不如后来严格。对后续模型，我们投入了更多研究与清除此类材料的工作。在一些我们尚无明确政策的滥用情形上，我们处理得更慢，也在这些政策的迭代上变得更好。我们持续迭代一整套安全要求，力求在有效应对风险的同时，向开发者清晰传达、并将不必要的摩擦降到最低。

尽管如此，我们相信与放任不管的做法相比，我们的方法使我们能够度量并减少语言模型使用带来的各类伤害，同时让模型能够支撑广泛的学术、艺术和商业应用。[B](https://openai.com/index/language-model-safety-and-misuse/#citation-bottom-B)

## 语言模型滥用的多种形态与规模

自 2018 年早期关于 [AI 恶意使用](https://arxiv.org/abs/1802.07228)的研究以及 2019 年[GPT-2](https://arxiv.org/abs/1908.09203)的工作以来，OpenAI 一直在研究 AI 滥用风险，并特别关注 AI 系统为影响力行动赋能的问题。我们与[外部专家](https://www.cambridge.org/core/journals/journal-of-experimental-political-science/article/all-the-news-thats-fit-to-fabricate-aigenerated-text-as-a-tool-of-media-misinformation/40F27F0661B839FA47375F538C19FA59)合作开发[概念验证](https://arxiv.org/abs/1908.09203)，并推动第三方对此类风险进行[审慎](https://arxiv.org/abs/2009.06807)[分析](https://cset.georgetown.edu/publication/truth-lies-and-automation/)。我们持续致力于应对语言模型加持的影响力行动相关风险，近期还共同组织了一场相关主题的研讨会。[C](https://openai.com/index/language-model-safety-and-misuse/#citation-bottom-C)

然而，我们已检测并阻止了数百个试图将 GPT-3 滥用于远比“为影响力行动制造虚假信息”更广泛用途的行为主体，其中的方式我们或未曾预料，或虽曾预料但没想到会如此普遍。[D](https://openai.com/index/language-model-safety-and-misuse/#citation-bottom-D)我们的[用例指南](https://beta.openai.com/docs/usage-guidelines/use-case-guidelines)、[内容指南](https://beta.openai.com/docs/usage-guidelines/content-guidelines)以及内部的检测响应基础设施，最初是根据内外部研究所预见的风险来设计的，比如用 GPT-3 生成误导性政治内容、或用 Codex 生成恶意软件。随着在真实世界遭遇的滥用案例不断出现——这些案例在我们最初的风险评估中并不像影响力行动那样显眼——我们的检测与应对也在不断演进。例子包括可疑药品的垃圾广告推广，以及扮演种族主义幻想的角色扮演。

为支持语言模型滥用及其缓解手段的研究，我们正在积极探索今年分享安全事件统计数据的机会，让关于语言模型滥用的讨论更加具体。

## 风险与影响度量的困难

语言模型风险与影响的许多方面仍难以度量，因此难以以可问责的方式监控、最小化和披露。我们积极使用既有的学术基准来评估语言模型，也乐于继续借鉴外部成果，但我们同时发现，现有基准数据集往往不能反映我们在实践中所见的安全与滥用风险。[E](https://openai.com/index/language-model-safety-and-misuse/#citation-bottom-E)

这些局限的根源在于：学术数据集很少是为指导语言模型生产使用而创建的，也享受不到大规模部署模型所积累的经验。因此，我们一直在开发新的评估数据集和框架来度量模型安全，并计划近期发布。具体而言，我们制定了衡量模型输出毒性的新评估指标，还开发了内部分类器，用于检测违反我们[内容政策](https://beta.openai.com/docs/usage-guidelines/content-guidelines)的内容，如色情内容、仇恨言论、暴力、骚扰和自残。这两者反过来也被用于改进预训练数据[F](https://openai.com/index/language-model-safety-and-misuse/#citation-bottom-F)——即用分类器过滤内容、用评估指标衡量数据集干预的效果。

按多个维度可靠地对单个模型输出进行分类已经很困难，而在 OpenAI API 的规模上衡量其社会影响更是难上加难。为建立这种度量的机构能力，我们开展了若干内部研究，但它们常常带来多于答案的问题。

我们尤其希望更好理解模型的经济影响及其分布。我们有充分理由相信，当前模型部署对劳动力市场的影响在绝对量级上可能已经相当显著，并会随着模型能力和覆盖范围的增长而扩大。迄今为止，我们了解到多种局部效应，包括个人从事的既有任务（如文案写作与摘要）出现的巨大生产率提升（有时导致岗位替代与新增岗位产生），以及 API 解锁了以前不可行的新应用的案例，例如[大规模定性反馈的合成⁠](https://openai.com/index/gpt-3-apps/)。但我们对净效应仍缺乏好的理解。

我们认为，开发和部署强大 AI 技术的各方有责任直面其工作的正面与负面影响。我们在本文结尾部分讨论了朝此方向迈出的一些步骤。

## AI 系统安全与实用之间的关系

我们在 2018 年发布的[章程⁠](https://openai.com/charter/)中表示，我们“担心后期 AGI 开发演变成一场没有时间为充分安全预防留余地的竞赛”。随后我们发表了对竞争性 AI 开发的详细[分析⁠](https://openai.com/index/cooperation-on-safety/)，并密切关注[后续](https://cltc.berkeley.edu/wp-content/uploads/2020/08/Flight-to-Safety-Critical-AI.pdf)研究。与此同时，通过 OpenAI API 部署 AI 系统也加深了我们对安全与实用性之间协同的理解。

例如，开发者压倒性地更喜欢我们的 InstructGPT 模型——它经过微调以更好遵循用户意图[G](https://openai.com/index/language-model-safety-and-misuse/#citation-bottom-G)——而非基础 GPT-3 模型。值得注意的是，InstructGPT 最初并非出于商业考量，而是旨在推进长期[对齐问题⁠](https://openai.com/alignment/)的研究。就实际而言，这意味着客户（也许不出意料）远更喜欢能保持任务专注、理解用户意图、并且更少产生有害或错误输出的模型。[H](https://openai.com/index/language-model-safety-and-misuse/#citation-bottom-H)其他基础研究也是如此，比如我们关于[利用⁠](https://openai.com/index/webgpt/)从互联网检索的信息来更真实回答问题的工作，同样有潜力提升 AI 系统的商业实用性。[I](https://openai.com/index/language-model-safety-and-misuse/#citation-bottom-I)这些协同并非总会发生。例如，越强大的系统往往需要越多的时间评估和有效对齐，从而错失即时的盈利机会。而且由于负外部性，用户效用与社会效用也可能不一致——想想全自动文案生成：它对内容创作者有利，但对整个信息生态不利。

看到安全与实用性高度协同的案例令人振奋，但即便安全与政策研究和商业实用性发生权衡，我们也承诺持续投入。

> “即便安全与政策研究和商业实用性发生权衡，我们也承诺持续投入。”

## 参与的方式

以上每一条经验教训都会引出新的问题。我们还可能漏检和漏判哪些安全事件？如何更好地度量风险与影响？如何持续同时提升模型的安全与实用，并在二者出现权衡时妥善取舍？

我们正在与其他部署语言模型的公司积极讨论许多这类问题。但我们也知道，没有任何一个组织或一组组织掌握全部答案。我们想强调几种让读者更多参与理解和塑造我们最前沿 AI 系统部署的方式。

第一，亲身接触最前沿的 AI 系统，对其理解其能力与影响极其宝贵。在建立起有效检测和响应滥用的信心后，我们最近取消了 API 排队名单。位于[支持国家和地区](https://beta.openai.com/docs/supported-countries)的个人可以在[这里⁠](https://openai.com/api/)注册，快速获得 OpenAI API 访问。

第二，研究我们特别关注的主题（如偏见与滥用）、且能受益于经费支持的研究人员，可以用[这个表单](https://share.hsforms.com/1b-BEAq_qQpKcfFGKwwuhxA4sk30)申请补贴的 API 额度。外部研究对于我们理解这些多面系统、以及更广泛的公众理解都至关重要。

最后，今天我们发布了一份[研究议程⁠](https://openai.com/index/economic-impacts/)，探讨与 Codex 模型家族相关的劳动力市场影响，并公开征集外部合作者来开展这项研究。我们期待与独立研究者合作，研究我们的技术带来的效应，为恰当的政策干预提供依据，并最终把思考从代码生成扩展到其他模态。

## 脚注

- A：本文基于我们通过 API 部署语言模型的做法，因此所述经验与缓解措施对同样采用 API 部署的各方最有参考价值。不过，我们也预期部分讨论内容对使用语言模型构建第一方应用的开发者、以及考虑开源发布语言模型的人有所裨益。
- B：本文旨在解释并分享我们做法中的心得，而非建议所有主体都应当照搬同一方法，也不是说同一方法适用于所有可能的 AI 系统。不同的部署路径各有利弊；不同模型从部署前研究中获益程度不一；某些情况下，不同主体走不同的部署路径反而有价值。
- C：本次研讨会的更多细节将见基于其撰写的即将发布的成果。
- D：我们针对滥用所强调的缓解措施也在演进。例如，鉴于以往影响力行动中有人手工撰写长篇误导内容，我们最初将长篇文本生成视为威胁载体，并因此设置了生成文本的最大输出长度。但基于长篇生成的试点研究，我们发现输出限制对违反政策的行为影响很小——我们转而认为，放大误导性内容或提高其互动的短内容可能是更大的风险。
- E：从追求对真实语言模型输出安全性的整体评估的从业者视角看，现有数据集的局限示例包括：焦点过窄（如只衡量职业性别偏见）；焦点过宽（如把一切都归入“毒性”之下）；倾向于抽离具体使用与语境；未能衡量语言模型使用的*生成*维度（如采用选择题形式）；提示与真实语言模型用例中常用的提示风格不同；未能捕捉实践中重要的安全维度（如输出是否遵循指令中出于安全考虑的约束）；或未能捕捉我们发现与滥用相关联的输出类型（如色情内容）。
- F：尽管我们的努力特别针对现有基准和我们自身模型的局限，我们也承认所使用的方法（如基于分类器的数据过滤）同样有局限。例如，用可操作的方式定义我们想通过过滤检测的内容领域很有挑战，过滤本身也可能引入有害偏见。此外，有毒数据的标注是这项工作的关键环节，保障标注人员的心理健康是整个行业的难题。
- G：我们的 API 的相关“用户”视语境而定，可能是构建应用的开发者，也可能是与该应用交互的终端用户。我们的对齐模型应反映何种价值观，有深刻的问题悬而未决；我们希望在把语言模型对齐为更有帮助、更真实、更少伤害的过程中，更好地平衡各类潜在用户的价值观和相互冲突的目标。
- H：对齐更好的模型还有更多实际优势，例如减少对“提示工程”（通过提供期望行为的示例来引导模型）的需求，节省模型上下文窗口的空间，用于其他目的。
- I：研究之外，我们发现一些出于安全考虑的干预措施有时会给客户带来意外好处。例如，旨在遏制垃圾信息或误导内容的速率限制，也帮助客户控制了成本。
