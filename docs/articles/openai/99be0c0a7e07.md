# 管理前沿 AI 风险：从训练到部署

2026 年 11 月 18 日 · 安全

前沿模型的能力正在快速提升，而我们理解、对齐并保障它们安全的能力必须始终领先一步。我们在把控模型开发与发布的节奏，包括在需要更多时间才能达到安全标准时[暂停](https://openai.com/index/pacing-model-development-cyber-capabilities/) [内部训练](https://alignment.openai.com/misalignment-reports/an-agent-used-dns-to-reach-an-external-chatbot/)，或暂缓发布 GPT‑6.1 Astra 这类模型。我们引入了[安全案例](https://openai.com/index/towards-safety-cases-for-frontier-ai-training/)等新流程，并要求在整个训练过程中提供更强的对齐行为证据。这些要求拖慢了模型发布的节奏，但也让我们更有信心安全地向前推进。

自 7 月的 [Hugging Face 事件](https://openai.com/index/hugging-face-incident-and-the-road-ahead/)以来，我们加强了针对模型训练、测试和部署方式的防护措施与对齐要求。本文说明我们在每个阶段如何评估和管理风险——从高度隔离的沙箱训练环境，一直到你在自己电脑上使用的 Codex 部署。我们在每个阶段都对模型和防护措施进行评估，并要求通过安全审查才能进入下一阶段。

## 模型全生命周期的纵深防御

我们采用*纵深防御*，通过多层保护来降低对任何单一防护措施的依赖。如果某一层失效，其他层会帮助防止伤害、限制后果，或提醒我们以便介入。

我们围绕四个层次来组织这些保护措施：

有效的监控取决于**模型可监控性**——即监控系统能否可靠地从模型的推理和行动中发现错误或不安全行为。例如，一个在思维链（CoT）中说出自己想要作弊的模型，比一个隐藏这一信息的模型更容易被监控。我们在训练期间和部署之前评估可监控性，开发更好的[衡量方法](https://alignment.openai.com/beyond-gmean-squared/)，并[研究哪些因素会影响它](https://alignment.openai.com/cot-monitorability-model-lifecycle/)。

Hugging Face 事件说明了为什么我们不应只靠沙箱来约束能力极强的模型。现在我们会在大多数内部和外部部署环境中监控前沿模型，包括所有[使用工具的内部部署](https://openai.com/index/how-we-detect-frontier-model-misalignment/)。

每一层的作用在模型开发与部署的三个阶段中会发生变化：

- **研究：**我们在沙箱环境中训练、测试和使用模型。
- **内部部署：**OpenAI 员工将模型用于实际工作。
- **外部部署：**模型向更广泛的人群和组织开放。

不同阶段我们依赖不同的层次。在训练期间，对齐尚不确定，我们更倚重沙箱和监控。随着模型在部署中获得更广泛的访问权限，对齐和系统级控制变得越来越重要。在每个阶段，我们都会评估这些保护措施组合起来是否足以匹配模型的能力和访问权限。我们的判定可能会由安全咨询小组（SAG）复核，并接受 OpenAI Foundation 董事会安全与安保委员会（SSC）的监督。

### 研究阶段：把模型约束在沙箱环境中

在研究阶段，我们评估模型，以建立对其对齐特性的信心。由于我们还不能完全依靠对齐来防止伤害，我们大量依赖安全和沙箱来限制模型可以访问什么、可以做什么。

基于对齐研究、监控系统以及互联网基础设施安全的现状，我们认为负责任的做法是在[完全没有实时互联网访问](https://openai.com/index/securing-our-frontier-model-training-environment/)的条件下开展前沿模型训练。Hugging Face 事件之后，我们[大幅重构](https://openai.com/index/securing-our-frontier-model-training-environment/)了内部研究系统，用以下方式约束模型：

- 限制模型权限的沙箱
- 进一步把工作负载与底层计算机隔离开的虚拟机
- 将整个集群与互联网切断的网络和云边界

我们持续对这个系统进行红队测试，让我们最强的模型组成团队，尝试接入实时互联网、突破安全边界，或与它们本应隔离的 agent 通信。这有助于检验这套约束机制能否扛住它所要约束的模型的能力。

作为额外的一层防御，我们监控所有前沿推理，以检测模型是否绕过了我们的安全不变量。如果监控发现模型已经接入互联网，我们会[呼叫安全团队](https://openai.com/index/how-we-detect-frontier-model-misalignment/)并自动暂停该工作负载。

当约束失效时，监控是一道关键的兜底。在最近的一份失准报告中，我们分享了监控[发现一个内部研究模型利用 DNS 配置错误](https://alignment.openai.com/misalignment-reports/an-agent-used-dns-to-reach-an-external-chatbot/)获得有限互联网访问的情况。9 月 20 日至 10 月 1 日，我们暂停了最强模型的训练和评估，同时调查并[修复了这一安全缺口](https://openai.com/index/securing-our-frontier-model-training-environment/)。

为了让干预既快又可靠，我们构建了 [Control Room](https://openai.com/index/control-room/)：这是一个中心系统，负责跟踪研究工作负载，并在收到停止某个任务的指令后 35 秒内阻止模型继续输出。这些控制直接在推理基础设施中强制执行，因此不依赖每个研究工作负载自行实现关停机制。对于前沿模型的研究工作负载，如果 Control Room 变得不可用，它们也会停止模型输出。

红队测试和监控是协同工作的。我们无法保证沙箱牢不可破，但红队测试能帮我们评估模型逃逸它需要付出多大努力。模型需要的努力越多，监控发现并阻止它的机会就越多。

我们在研究阶段强制要求严格的安全与监控控制，原因有几点：

- **模型仍在评估之中。**有些模型尚未完成公开发布所需的安全训练、对齐审计和审查。
- **前沿研究环境可能放大风险。**某些研究任务需要更激进的设置，使模型比外部部署时通常看到的更执着或能力更强（例如，解决 [Navier Stokes 问题](https://openai.com/index/navier-stokes-solution/)需要一支由 10,000 个 agent 组成的团队）。
- **大规模训练运行中，直接的人工监督更少。**与典型的 Codex 会话不同，我们的训练工作负载涉及大量模型操作，而没有一个人跟进每一次交互。

### 内部部署：测试对齐，密切监控行为

在广泛发布之前，员工会把[前沿模型从沙箱研究用途切换到无沙箱的内部使用](https://openai.com/index/research-acceleration-view-inside-openai/)，例如让员工可以在 ChatGPT 中访问该模型。这让我们更好地理解模型[在实际场景中的行为](https://alignment.openai.com/eval-production-behavior-gap/)，并为部署决策提供依据。

在这一阶段，我们让模型访问更广泛的互联网、我们的 Slack、代码库和内部基础设施。风险随之发生显著变化，因为模型的行为现在会直接影响我们用来构建和运营 OpenAI 的系统。在内部部署期间，我们需要更多地依赖模型对齐、系统防护措施和监控，而不是安全控制。

前沿模型要在沙箱之外部署，必须先经过对齐和[可监控性测试](https://alignment.openai.com/beyond-gmean-squared/)。我们有一套对齐评估，既检验特定的对齐失效模式（例如规避安全与安保限制），也做倾向性的宽泛测量（例如重采样内部 Codex 轨迹并检查是否存在失准）。关于我们的对齐与可监控性评估，可以在最新的 [GPT‑6 Astra 系统卡](https://deploymentsafety.openai.com/gpt-6-astra)中看到更多内容。

参照我们生产环境的设置，我们额外加了一层由系统级分类器构成的防御，这些分类器旨在防范网络滥用和生物武器化等前沿危害。我们通常还要求使用 Codex 的员工启用 [Auto-Review](https://alignment.openai.com/auto-review/)，它会评估潜在有风险的操作并将其上报回用户。

最后，在内部部署期间，我们对每一次前沿推理都监控是否存在失准行为。由于模型现在的权限扩大，并且可以访问内部信息和系统，数据外泄或把敏感数据发送到未授权目的地这类风险就变得尤其需要检测。监控还帮助我们调查[新形式的失准](https://alignment.openai.com/misalignment-reports/)。

### 外部部署：大规模防范滥用与失准

公开部署会让模型接触到多得多的用户、任务和环境，风险的范围和种类都随之增加。在这一阶段，我们还需要防范那些蓄意引导模型实施伤害的潜在恶意行为者。

在公开发布之前，模型和系统防护措施必须满足我们的外部部署安全要求。我们通过以下方式评估：

- **执行更大规模的对齐与安全评估。**对前沿模型而言，这包括用我们内部的自动化红队进行新一轮[自适应测试](https://openai.com/index/unlocking-self-improvement-gpt-red/)，对模型的鲁棒性做压力测试。我们在[系统卡](https://deploymentsafety.openai.com/gpt-6-astra)中公布能力与安全评估的结果。
- **对我们能力最强的模型，我们还会与第三方一起做测试**，既对我们的防滥用措施施压，也对模型底层的对齐状况施压。
- **检查内部部署阶段产生的监控标记**，以追踪基础模型底层对齐状况的任何变化。

除了我们的“同步”防护措施（如模型安全训练和系统分类器）之外，对外部部署我们还借助离线执行与调查。这些团队把规模化部署的 agent 调查员与人工复核结合起来，以发现和识别潜在威胁行为者，覆盖网络滥用、生物武器化、[蒸馏](https://openai.com/index/disrupting-a-coordinated-model-distillation-campaign/)以及源自模型自身的失准。离线执行尤其有助于在账户*之间*收集信息，从而对潜在威胁形成更完整的图景。

[Daybreak](https://openai.com/daybreak/) 和 [Rosalind](https://openai.com/index/introducing-gpt-rosalind/) 等可信访问计划提供了另一层安全保障，在加快防御方和正当研究者的同时，限制潜在攻击者的访问。

## 事件响应与披露

当我们发现安全防护的某一层出现失效时，无论是否真的造成了伤害，我们都希望迅速调查、分级，并在可能且适当的情况下对外披露该失效。根据我们的[失准报告](https://openai.com/index/model-misalignment-reporting-framework/)政策，任何员工都可以标记某个事件，要求公开披露。这些报告会被调查；如果在是否应对外披露上存在分歧，决定将上报至我们的安全咨询小组（SAG）。除了依靠员工报告，我们也会主动寻找失准事件，以便处理并分享发现。

你可以在[这里](https://alignment.openai.com/misalignment-reports/)查看我们的失准报告。

这项工作既依赖研究进展，也依赖运营纪律：正确配置控制项、测试它们之间如何相互作用，并在它们失效时果断响应。一个配置错误的网络服务或一次失败的自动停止，就可能瓦解原本很强的防护。

随着模型获得新能力，我们需要不断质疑防护措施背后的假设，并在必要时加以改进。来自研究、内部使用和公开部署的经验教训，必须用以指导我们如何训练、评估和部署下一代模型。

我们会继续通过系统卡、事件报告、内部部署[风险报告](https://cdn.openai.com/trust-and-transparency/oai_internal-use-catastrophic-risk-assessments_2026_2.pdf)和[外部评估](https://openai.com/index/priorities-principles-third-party-assessments/)分享发现，让其他人能够审视我们的做法，包括其局限。当这些证据达不到我们为安全设定的标准时，我们会再次暂停训练或暂缓发布，直到满足这些要求。
