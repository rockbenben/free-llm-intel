# 将 Kubernetes 扩展到 7,500 个节点

我们已把 Kubernetes 集群扩展到 7,500 个节点，为 [GPT‑3⁠（在新窗口中打开）](https://arxiv.org/abs/2005.14165)、[CLIP⁠](https://openai.com/index/clip/)、[DALL·E⁠](https://openai.com/index/dall-e/) 这样的大模型构建了可扩展的基础设施，同时也支撑了像 [Scaling Laws for Neural Language Models⁠（在新窗口中打开）](https://arxiv.org/abs/2001.08361) 这类快速小规模迭代研究。

把单个 Kubernetes 集群扩展到这种规模很少见，需要格外用心，但收益是一套简洁的基础设施，让机器学习研究团队跑得更快、无需改动代码即可扩容。

自我们上一篇关于[扩展到 2,500 个节点⁠](https://openai.com/index/scaling-kubernetes-to-2500-nodes/)的文章以来，我们持续扩充基础设施以满足研究者的需求，途中收获了许多新经验。本文总结这些经验，供 Kubernetes 社区的其他人参考，文末列出我们下一步要解决的未解难题。


## 我们的工作负载

在深入之前，先描述我们的工作负载很重要。我们在 Kubernetes 上运行的应用与硬件，与典型公司遇到的情况很不一样。我们的问题和相应对策，未必适合你的环境！

一个大型机器学习任务横跨许多节点，当它能独占每个节点的全部硬件资源时运行效率最高。这让 GPU 可以通过 [NVLink⁠（在新窗口中打开）](https://www.nvidia.com/en-us/data-center/nvlink/) 直接互通，或让 GPU 通过 [GPUDirect⁠（在新窗口中打开）](https://developer.nvidia.com/gpudirect) 与网卡直接通信。因此对我们许多工作负载来说，一个 pod 占用整个节点。NUMA、CPU 或 PCIE 资源争用不是调度考虑因素。装箱碎片化（bin-packing/fragmentation）不是常见问题。我们当前的集群具备全对分带宽，因此也不需要考虑机架或网络拓扑。所有这些因素意味着：虽然节点很多，调度器的压力却相对较低。

话虽如此，kube-scheduler 的压力是尖峰式的。一个新任务可能同时创建数百个 pod，然后回落到相对较低的变更速率。


我们最大的任务运行 MPI，任务内的所有 pod 都参与同一个 MPI communicator。任何一个参与的 pod 死亡，整个任务就会停摆、需要重启。任务会定期做 checkpoint，重启后从最近的 checkpoint 继续。因此我们把这类 pod 视为*半有状态*（semi-stateful）——被杀掉的 pod 可以被替换、工作可以继续，但这样做有破坏性，应尽量少发生。

我们并不怎么依赖 Kubernetes 的负载均衡。我们的 HTTPS 流量非常少，不需要 A/B 测试、蓝绿部署或金丝雀发布。pod 之间直接用各自的 pod IP 通信，通过 SSH 承载 MPI，而不是通过 service endpoint。服务“发现”也很有限：我们只在任务启动时一次性查询哪些 pod 参与 MPI。

大多数任务会与某种 blob 存储交互。它们要么直接从 blob 存储流式读取数据集分片或 checkpoint，要么先缓存到快速的本地临时磁盘。在需要 POSIX 语义的场景我们有少量 PersistentVolume，但 blob 存储可扩展性强得多，也不需要缓慢的卸载/挂载操作。

最后，我们工作的本质是研究，这意味着工作负载本身时刻在变。虽然超级计算团队力求提供我们视为“生产级”品质的计算基础设施，但跑在集群上的应用是短命的，其开发者迭代飞快。任何时刻都可能出现新的使用模式，挑战我们关于趋势与合理取舍的假设。我们需要一个可持续的系统，同时允许我们在变化发生时快速响应。

## 网络

随着集群内节点和 pod 数量增长，我们发现 Flannel 难以扩展所需的吞吐量。我们改用 Azure VMSS 原生 pod 网络技术作为我们的 IP 配置及相应的 CNI 插件。这让我们的 pod 获得了主机级的网络吞吐。

我们切换到基于 alias 的 IP 寻址的另一个原因是：在最大的集群上，任何时刻可能约有 20 万个 IP 地址在用。当我们测试基于路由（route-based）的 pod 网络时，发现可有效使用的路由数量存在重大限制。

避免封装加大了对底层 SDN 或路由引擎的要求，但让我们的网络配置保持简单。添加 VPN 或隧道不需要任何额外适配器。我们不必担心因网络某些部分 MTU 更低而导致的分片。网络策略与流量监控也很直接——数据包的源和目的不存在歧义。

我们在主机上使用 iptables 标记，按 Namespace 和 pod 追踪网络资源用量。这让研究者能可视化自己的网络使用模式。特别是，由于我们许多实验有不同的“对外互联网”与“pod 间”通信模式，能够排查瓶颈可能发生在哪里往往很有用。

iptables 的 `mangle` 规则可以按任意条件给数据包打标记。下面是我们用于区分内部流量与互联网流量的规则。`FORWARD` 规则覆盖来自 pod 的流量，而 `INPUT` 和 `OUTPUT` 覆盖来自主机的流量：

#### Plain Text

```
1iptables -t mangle -A INPUT ! -s 10.0.0.0/8 -m comment --comment "iptables-exporter openai traffic=internet-in"2iptables -t mangle -A FORWARD ! -s 10.0.0.0/8 -m comment --comment "iptables-exporter openai traffic=internet-in"3iptables -t mangle -A OUTPUT ! -d 10.0.0.0/8 -m comment --comment "iptables-exporter openai traffic=internet-out"4iptables -t mangle -A FORWARD ! -d 10.0.0.0/8 -m comment --comment "iptables-exporter openai traffic=internet-out"
```

一旦打标，iptables 就会启动计数器，追踪匹配该规则的字节数与包数。你可以直接用 `iptables` 查看这些计数器：

#### Plain Text

```
1% iptables -t mangle -L -v2Chain FORWARD (policy ACCEPT 50M packets, 334G bytes)3 pkts bytes target     prot opt in     out     source               destination4....51253K  555M            all  --  any    any     anywhere            !10.0.0.0/8           /* iptables-exporter openai traffic=internet-out */61161K 7937M            all  --  any    any    !10.0.0.0/8           anywhere             /* iptables-exporter openai traffic=internet-in */
```

随后我们用一个名为 [iptables-exporter⁠（在新窗口中打开）](https://github.com/madron/iptables-exporter/) 的开源 Prometheus exporter 把这些计数接入监控系统。这是追踪满足各种不同条件数据包的简单方式。


我们网络模型一个颇为独特的方面是：我们向研究者完整暴露节点、pod 和 service 的网络 CIDR 范围。我们采用星型（hub and spoke）网络模型，用原生节点与 pod CIDR 范围路由流量。研究者连接到 hub，从那里可以访问各个独立集群（spoke）。但集群之间不能互相通信。这确保集群保持隔离，不存在可能破坏故障隔离的跨集群依赖。

我们用一台“NAT”主机对来自集群外部的流量做 service 网络 CIDR 范围的转换。这套设置让研究者在为其实验选择网络配置的方式与类型上拥有很大的灵活性。

## API 服务器

Kubernetes API Server 与 etcd 是集群健康运行的关键组件，因此我们特别关注这些系统的压力。我们使用 [kube-prometheus⁠（在新窗口中打开）](https://github.com/coreos/kube-prometheus) 提供的 Grafana 仪表盘，以及额外的内部仪表盘。我们发现，对 API Server 上 HTTP 429（请求过多）与 5xx（服务器错误）状态码的速率做告警，是问题的高层信号，很有用。


虽然有人把 API Server 跑在 kube 里，我们始终把它们运行在集群之外。etcd 与 API 服务器都跑在各自专用的节点上。我们最大的集群运行 5 个 API 服务器和 5 个 etcd 节点，以分摊负载并在单点故障时减小影响。自[上一篇博客⁠](https://openai.com/index/scaling-kubernetes-to-2500-nodes/)中把 Kubernetes Events 拆分到独立 etcd 集群以来，etcd 没有出过值得注意的问题。API 服务器是无状态的，通常很容易在自愈实例组或规模集里运行。我们尚未尝试构建 etcd 集群的自愈自动化，因为事故极其罕见。

API 服务器可能占用相当多的内存，且往往随集群节点数线性增长。在 7,500 节点的集群上，我们观察到每个 API 服务器最多使用 70GB 堆内存，所以幸运的是，在未来这应当仍远在硬件能力之内。


API 服务器的一大压力来自对 Endpoints 的 WATCH。有些服务（如 ‘kubelet’ 和 ‘node-exporter’）的成员是整个集群的每个节点。每当节点加入或移出集群，这个 WATCH 就会触发。而由于通常每个节点自身都通过 kube-proxy 在 watch `kubelet` 服务，这些响应的数量与带宽需求是 N2 N^2 N2 级别的、极其巨大，偶尔达到 1GB/s 以上。Kubernetes 1.17 推出的 [EndpointSlices⁠（在新窗口中打开）](https://kubernetes.io/docs/concepts/services-networking/endpoint-slices/) 是一大利好，把这一负载降低了 1000 倍。


总体而言，我们会格外留意任何随集群规模增长的 API 服务器请求。我们尽量避免让任何 DaemonSet 与 API 服务器交互。在确实需要每个节点 watch 变更的场合，引入中间缓存服务——比如 [Datadog Cluster Agent⁠（在新窗口中打开）](https://docs.datadoghq.com/agent/cluster_agent/)——似乎是避免全集群瓶颈的好模式。

随着集群增长，我们实际上越来越不做自动扩缩容。但一次性扩太多时我们偶尔遇到麻烦。新节点加入集群会产生大量请求，一次添加数百个节点可能压垮 API 服务器容量。把峰值抹平——哪怕只几秒钟——就帮助避免过宕机。

## 用 Prometheus 与 Grafana 做时序指标

我们用 Prometheus 收集时序指标，用 Grafana 做图表、仪表盘和告警。我们起步于部署 [kube-prometheus⁠（在新窗口中打开）](https://github.com/coreos/kube-prometheus)，它收集大量指标并配有可视化仪表盘。随着时间推移，我们添加了自己的许多仪表盘、指标和告警。

随着节点越来越多，我们为 Prometheus 收集指标的庞大数量而挣扎。kube-prometheus 暴露的数据很多都有用，但有些我们其实从来不看，有些则粒度太细，无法有效收集、存储和查询。我们用 [Prometheus 规则⁠（在新窗口中打开）](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#relabel_config)把其中一些指标“drop”掉、不再摄入。

有一段时间，我们被一个问题困扰：Prometheus 内存占用不断攀升，最终在 OOM 错误中把容器打挂（OOM）。即使给应用配了海量内存也是如此。更糟的是，一旦崩溃，它需要数小时重放预写日志（WAL）文件才能恢复可用。

最终我们把 [OOM 的根源⁠（在新窗口中打开）](https://github.com/prometheus/prometheus/issues/5547#issuecomment-592797528)定位到 Grafana 与 Prometheus 的一处交互：Grafana 会用 `{le!=""}`（基本上是“给我所有直方图指标”）的查询调用 Prometheus 的 `/api/v1/series` API。`/api/v1/series` 的实现在时间和空间上都不设上限——对于结果很多的查询，它会无止境地消耗内存与时间；即使请求方已经放弃并关闭连接，它仍在继续增长。对我们而言，内存永远不够，Prometheus 最终崩溃。我们给 Prometheus 打了一个[补丁⁠（在新窗口中打开）](https://github.com/openai/prometheus/pull/1)，把该 API 包在带超时强制的 Context 里，彻底修复了问题。

虽然 Prometheus 崩溃频率大大降低，但在需要重启的时刻，WAL 重放仍是问题。重放完所有 WAL 日志往往需要数小时，之后 Prometheus 才能开始收集新指标、提供查询服务。在 [Robust Perception⁠（在新窗口中打开）](https://www.robustperception.io/) 的帮助下，我们发现设置 `GOMAXPROCS=24` 带来大幅改善。Prometheus 在 WAL 重放时试图使用所有核心，而在核心数很多的服务器上，争用会摧毁一切性能。

我们正在探索提升监控容量的新选项，见下文“未解决的问题”一节。

## 健康检查

在如此大的集群上，我们当然依赖自动化来发现并移除集群中行为异常的节点。随着时间推移，我们构建了一批健康检查系统。

### 被动健康检查

一些健康检查是被动的，在所有节点上持续运行。它们监控基础系统资源，例如网络可达性、故障或写满的磁盘、GPU 错误。GPU 的问题是多种多样的，但常见的一种是“不可纠正的 ECC 错误”。Nvidia 的数据中心 GPU 管理器（DCGM）工具可以方便地查询此类错误和许多其他 “Xid” 错误。我们追踪这些错误的方式之一，是通过 [dcgm-exporter⁠（在新窗口中打开）](https://github.com/NVIDIA/gpu-monitoring-tools#dcgm-exporter) 把这些指标摄入监控系统 Prometheus。它会表现为 `DCGM_FI_DEV_XID_ERRORS` 指标，并被设为最近发生的错误代码。此外，[NVML Device Query API⁠（在新窗口中打开）](https://docs.nvidia.com/deploy/nvml-api/group__nvmlDeviceQueries.html#group__nvmlDeviceQueries) 暴露关于 GPU 健康与运行的更详细信息。

一旦检测到错误，通常可以通过重置 GPU 或系统修复，尽管某些情况下底层 GPU 确实需要物理更换。

另一种健康检查追踪来自上游云厂商的维护事件。各大云厂商都提供某种途径，得知当前 VM 是否即将进行最终会导致中断的维护事件——VM 可能需要重启以应用底层 hypervisor 补丁，或把物理节点更换到其他硬件。

这些被动健康检查在所有节点后台持续运行。如果某项检查开始失败，节点会被自动 cordon（封锁），不再调度新 pod。对更严重的健康检查失败，我们还会尝试 pod 驱逐，要求当前运行的所有 pod 立即退出。是否允许驱逐，最终仍取决于 pod 本身，可通过 Pod Disruption Budget 配置。最终——要么所有 pod 已终止，要么 7 天已过（这是我们 SLA 的一部分）——我们会强制终止该 VM。

### 主动 GPU 测试

遗憾的是，并非所有 GPU 问题都会表现为 DCGM 可见的错误码。我们自建了一个测试库来压测 GPU，捕捉额外问题、确保硬件与驱动行为符合预期。这些测试无法在后台运行——它们需要独占使用 GPU 几秒到几分钟。

我们首先在节点启动时运行这些测试，这套系统叫“preflight”。所有节点加入集群时都带有 “preflight” taint 和 label。该 taint 阻止普通 pod 调度到该节点。我们配置了一个 DaemonSet，在所有带此 label 的节点上运行 preflight 测试 pod。测试成功完成后，测试自身会移除 taint 和 label，节点随即进入可用状态。

之后，我们在节点生命周期内也会周期运行这些测试。我们把它做成 CronJob，允许它落在集群中任意可用节点上。哪些节点会被测到确实有些随机、不可控，但我们发现长期下来它提供了足够的覆盖，且协调与干扰都最小。

## 配额与资源用量

随着集群扩大，研究者开始发现自己难以拿到分配给他们的全部容量。传统作业调度系统有很多在竞争团队之间公平运行任务的特性，而 Kubernetes 没有。随着时间推移，我们从这些作业调度系统中获取灵感，以 Kubernetes 原生的方式构建了若干能力。

### 团队 taint

我们在每个集群里运行一个叫 “team-resource-manager” 的服务，它有多重职能。其数据源是一个 ConfigMap，为在该集群拥有容量的所有研究团队指定（节点选择器、要应用的团队 label、分配量）三元组。它将其与集群当前节点做调和，用 `openai.com/team=teamname:NoSchedule` 给适当数量的节点打 taint。

team-resource-manager 还带有 admission webhook 服务，在每个作业提交时，根据提交者的团队归属自动应用相应的 toleration。使用 taint 让我们可以灵活约束 Kubernetes 的 pod 调度器，例如允许低优先级 pod 带“任意”toleration，这使团队之间无需重型协调即可借用彼此的容量。

### CPU 与 GPU 气球

除了用 cluster-autoscaler 动态伸缩基于 VM 的集群，我们还用它来修复（移除并重新添加）集群内不健康的成员。做法是把集群的 “min size” 设为零、“max size” 设为可用容量。但 cluster-autoscaler 看到空闲节点时，会尝试缩容到仅满足需求的容量。出于多种原因（VM 启动延迟、预付成本、前述 API 服务器影响），这种空闲缩容并不理想。

因此，我们为纯 CPU 与 GPU 主机引入了气球（balloon）Deployment。该 Deployment 包含一个 ReplicaSet，按“max size”数量运行低优先级 pod。这些 pod 占用节点内资源，autoscaler 因此不把它们视作空闲。但由于它们是低优先级，调度器可以随时驱逐它们，为实际工作腾位置。（我们选择 Deployment 而非 DaemonSet，是为了避免 DaemonSet 被视为节点上的空闲负载。）

值得一提的是，我们用 pod 反亲和确保 pod 均匀分布在节点上。早期版本的 Kubernetes 调度器在 pod 反亲和上存在 O(N2) O(N^2)  O(N2) 的性能问题。Kubernetes 1.18 起已修正。

## 成组调度（Gang scheduling）

我们的实验通常涉及一个或多个 StatefulSet，各自承担训练工作的不同部分。对优化器类任务，研究者需要 StatefulSet 的全部成员都被调度后（才能开始训练，因为我们常用 MPI 在优化器成员间协调，而 MPI 对组成员变化敏感）。

但默认情况下，Kubernetes 不一定会优先满足某个 StatefulSet 的全部请求而不是另一个。例如，两个实验各自请求集群 100% 的容量时，Kubernetes 可能各调度一半 pod，而不是让其中一个实验全部运行，导致两个实验都无法推进的死锁。

我们尝试过几种需要自定义调度器的方案，但遇到与普通 pod 调度冲突的边界情况。Kubernetes 1.18 为核心调度器引入了插件架构，让原生添加这类功能变得容易得多。我们最近选定了 [Coscheduling 插件⁠（在新窗口中打开）](https://github.com/kubernetes/enhancements/pull/1463) 作为解决该问题的好办法。

## 未解决的问题

随着集群继续扩大，仍有不少问题待处理。其中几个是：

### 指标

在我们的规模上，Prometheus 内置 TSDB 存储引擎暴露出许多困难：压缩缓慢、每次重启重放 WAL（预写日志）耗时很长。查询也往往触发 “query processing would load too many samples” 错误。我们正在迁移到另一个 Prometheus 兼容的存储与查询引擎。敬请期待后续博客分享进展！

### Pod 网络流量整形

随着集群扩大，每个 pod 被计算有一定的互联网带宽可用。人均互联网带宽总需求已变得可观，而我们的研究者现在有可能无意中给互联网其他位置造成重大资源压力，比如待下载的数据集和待安装的软件包源。

## 结论

我们发现 Kubernetes 对研究需求而言是异常灵活的平台。它能扩展到我们给它的最苛刻的工作负载。不过仍有许多需要改进之处，OpenAI 的超级计算团队将持续探索 Kubernetes 的扩展之道。如果你觉得这类工作有趣，不妨考虑[加入⁠](https://openai.com/careers/) OpenAI！
