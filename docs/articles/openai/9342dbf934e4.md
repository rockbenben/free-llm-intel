# OpenAI 的 Performance Factory 如何让 ChatGPT 保持快速

我们由 Codex 驱动的系统把性能问题的发现与修复都自动化了。

作者：Okay Zed、Cyrus Forbes，Members of Technical Staff

agentic 开发令人瞠目的节奏，让性能工程的传统做法难以为继。为了跟上，我们构建了 Performance Factory：一个自主系统，它动用 Codex 与我们模型的全部能力，以前所未有的速度发现并修复性能回退。Performance Factory 运行在云端，把性能问题的调查与解决自动化，让我们能跟上路线图里的野心。

在 Performance Factory 中，我们的工程师为周期性任务定义工作流，并为执行这些工作流的 Codex agent 编写指令。其中，Regression Workflow 在性能告警触发时开出一个任务。agent 调查变慢的原因，把发现记录在任务里，并提出修复方案供工程师评审。部署之后，另一个 agent 接手同一个任务，检查性能是否回到基线。从调查、撰写修复到验证缓解，Performance Factory 里的这第一个工作流已经把修复性能回退的整个过程自动化了。在短短三个多月里，Regression Workflow 追踪了 1,700 多次调查，并对 600 多个案例完成了根因定位。算下来每天 17 次自动调查。

本文中，我们会分享我们对 Codex 的使用如何演变成今天的 Performance Factory，带大家走一遍第一个投入运行的工作流，并分享在生产环境中构建与运行 agent 工作流的早期经验。

## 从人工调查到自动化工作流

随着我们把 Codex 用在越来越多的性能工作上，我们注意到团队的工作方式呈现出阶段性的演进。希望其他服务团队在各自领域引入 agentic 工作流时，能从我们的过程中得到参考。

*软件工作从人力劳作，演进到与机器协作，再到 agent 工厂。*

**1. Codex 之前**。在 Codex 之前，工程师要手工查看指标和日志、比对 trace、调试线上机器、读代码，来调查变慢的原因。这种活很费时间，而且要往哪儿看往往需要对服务有深入了解。相关信号很容易被漏掉。当我们反复遇到同类问题时——比如 ChatGPT 首 token 延迟的回退——我们构建了更高级的工具，例如 CPU profiler 与内存分配 profiler，让这些调查更容易些。久而久之，我们积累的工具超过 30 个。

**2. Codex 作为伙伴**。有了 Codex 这个伙伴之后，工程师可以问一句“这里为什么变慢了？”，然后和 Codex 一起调查，哪怕面对的是一个不熟悉的系统。Codex 能搜索庞大的代码库、找出相关指标与 trace、追踪服务之间的交互，并做恰当的 profiling，把发生过的事情拼合起来。但工程师仍然要掌舵：得知道用哪个性能工具，以及如何引导调查。困难的调查变得对更多人可调，所需的专业经验和时间都更少。

**3. 可复用的 skill**。为了进一步自动化，我们把性能团队的调查流程固化进一个共享 skill，名为 `perf-forensics`。它告诉 Codex 有哪些工具可用、何时使用，以及如何一步步排查变慢，这样 Codex 就能从几个角度尝试解决问题：

- 找出变慢是从什么时候开始的
- 识别受影响的请求
- 调查部署或配置变更能否解释这一现象

我们用基于过往性能回退的 eval 测试并打磨 `perf-forensics` skill。对于我们关注的那几类回退（例如 ChatGPT 延迟上升与可用性下降），现在只要把告警交给 Codex，一次运行就能拿回一份诊断，而不必一步步引导它。

**4. 人的代理**。随着我们不断添加和改进 `perf-forensics` 这类与性能相关的 Codex skill，我们开始觉得自己成了告警与 Codex 之间的代理。告警一响，工程师就把它复制粘贴进 Codex、配上正确的 skill，再把发现粘回 Slack。

**5. 自动调查**。接下来，我们把调查搬到云端，让告警能自动启动一个 Codex 会话。Codex 调查变慢的原因，把发现发在 Slack 线程里，但自动化到这条回复就结束了。工程师仍然要接住诊断、开发修复方案，并在部署后检查是否奏效。告警一多，连判断哪些回退需要处理，都得在 Slack 线程里翻找。

**6. 工厂**。我们构建 Performance Factory 来运行端到端的 agentic 性能工程工作流。它追踪每个活跃任务下一步需要什么，并在该步骤就绪时分配 agent。每个任务保留自己的状态与发现，因此工作可以在 agent 与工程师之间流转，也能在代码评审或部署之后接着做。对一次回退来说，工作从调查一条告警开始，到在生产环境验证恢复结束。我们可以把常见优化做成工作流，在我们的各项服务上定期运行。一个发现潜在优化点的工作流，可以在另一个工作流里开出任务去测试并实现它。

## Performance Factory 系统的四个部分

Performance Factory 由四个组件构成：带可配置工作流的任务追踪器、把就绪工作分配给 agent 的 dispatch loop、在云端运行 Codex 的 API，以及在某些变化发生时唤醒 agent 的 subscription（例如 GitHub 评审意见发布，或某次部署完成）。

![Performance Factory 的编排流程：告警、工程师与其他 agent 创建任务；任务服务把就绪的任务交给 dispatch loop，后者在云端启动 Codex turn。agent 记录进展，而 subscription 在 PR 评论或部署之后唤醒等待中的任务。](https://images.ctfassets.net/kftzwdyauwt9/4GVsirng1kgJ1GzSsQ9Iof/f21a0b8682d456132be1ef8e1b9ce0ed/performance-factory-orchestrator-architecture-light.png?w=3840&q=90&fm=webp)

*Performance Factory 由任务服务、dispatch loop、云端执行与 subscription 组成。*

### 带可配置工作流的任务服务

任务服务是工程师定义工作流的地方：添加配置文件，以及用 Markdown 写给 agent 遵循的 prompt。配置文件列出任务可以经历的状态、允许的状态转移，以及哪些步骤需要工程师。单独的 prompt 告诉 agent 在每一步该做什么。

#### 纯文本

```
1code-change/2├── config.toml3└── work/4    ├── implementing.md5    └── reviewing.md
```

一个 code change 任务包含一个配置文件，以及用于实现与评审的 Markdown prompt。

每一项工作都会成为某个工作流里的一个任务，所有工作流都能在一个 UI 里看到。工程师可以看到哪些任务是开放的、跟进进展，也可以把任务分享给更了解上下文、或能帮忙推进下一步的同事。

### 分配工作的 dispatch loop

dispatch loop 定期检查哪些任务已经可以进入下一步。它为每个任务分配 agent，方式是带着该任务当前状态对应的指令启动一次 Codex turn。agent 在任务上记录进展，若完成该步骤就把任务推进到下一个状态。

### 云端运行的 Codex

任务分配出去后，agent 需要一个干活的地方，并且能用上工程师平时用的那些工具。我们构建了一个内部 API，可以用程序方式在云端触发一次 Codex turn。这次 Codex turn 运行在我们网络内部的一个环境里，能访问我们的代码仓库，以及我们工程师使用的可观测性工具，例如指标、日志、trace、CPU profile 与内存快照。

agent 以一个服务身份运行，这样我们可以限定它的权限范围，也能看出哪些操作来自我们的性能 agent。把 agentic 工作搬到云端，让我们可以并行跑任务，而不必依赖工程师的笔记本开着，也不必手工管理一台台云端开发机。

### 在变化发生时唤醒 agent 的 subscription

有些工作需要等人或等一次部署，agent 不该在这期间一直空转。当任务需要等待时，它可以订阅事件，例如 GitHub pull request 上的评审意见或失败的 CI 检查，以便在可以继续推进时收到通知。当进来的事件与订阅匹配，任务重新变为就绪，dispatch loop 便可以分配 agent 继续这项工作。

## 第一个工作流：从告警到恢复

发现、定位根因并解决性能回退，是我们在 Performance Factory 里构建的第一个工作流，我们称之为 Regression Workflow。一次性能回退会经过若干阶段：**待调查**、**已定位根因**、**已提出修复**、**已解决**，因此我们让这个自动化工作流对应这些阶段，并推动任务走完它们。

当它配置的某条性能告警触发时，Regression Workflow 会开出一个任务，由 agent 接手并推动它跨越这些阶段。任务把自身状态与关键发现记录在任何单个 agent 的上下文之外，好让其他 agent 或工程师能接手。工程师可以在 Slack 或 Regression Workflow 的 UI 里跟进、补充上下文、评审提出的改动。修复部署之后，agent 会先检查性能是否已恢复原状，再结掉该任务。

*Regression Workflow 的步骤包括定位根因、提出修复、评审与部署、验证恢复。*

### Agent 定位根因

定位根因（可能不止一个）是工作流里的第一个大步骤。agent 先弄清哪些指标变差了、从什么时候开始变化、以及哪些服务请求受到影响。`perf-forensics` skill 让 Codex 能用上我们性能工程师使用的工具，并给出一套梳理这些问题的打法。

告警是在某个指标越过阈值时触发的，但性能回退可能在几小时前就开始了。agent 回看数据，找出指标最早变差的时间点。接着它比较各组请求：是同类请求确实变慢了，还是我们服务的本来就很慢的请求变多了？这两种发现指向不同的原因。

一旦知道该在何时、何处查看，agent 就会检查部署与 feature flag 变更，然后阅读相关代码。它会确认某项改动究竟何时到达受影响的请求，并用日志或 trace 检验这段代码能否解释所发生的情况。

### 对抗式评审让诊断更可靠

早期，agent 有时找到第一个说得通的解释就停下了，而其中一些诊断后来被证明是错的。为了抓住这类错误，我们加了一道对抗式评审：由一个单独的 Codex 会话尝试推翻所提出的诊断。评审者会复核假设、检验反事实。如果某次 rollout 导致了变慢，那么没有暴露在其中的同类请求是否保持正常？如果疑似肇事的改动被回滚，受影响的指标是否恢复了？

在一次调查中，agent 把 ChatGPT 会话失败追溯到图片下载报错，并标记为已找到原因。Codex 评审者注意到，负责定位文件的内部服务早已恢复，而图片请求仍在失败。该诊断解释不了持续发生的失败，于是这位 AI 评审者重新打开调查，并记录下还有哪些问题需要确认。

把较大的工作拆成若干聚焦的 Codex turn，对我们很有效。在对 100 条根因建议的人工评审中，我们判定 70% 是准确的，另外 30% 需要进一步细化，或未能完全确立因果。在 Regression Workflow 中，不同的 turn 分别负责调查回退、质疑诊断、提出修复，通过相互制衡来提高准确率。

### 修复回退才是难的部分

诊断通过对抗式评审后，工作流会让 Codex 实现修复并开一个 pull request。工程师评审该 PR，决定是否合并。我们在这道交接上投入了大量工作，力求尽可能顺手。每个任务都有一份报告，其中自动生成对回退、影响、根因与拟定修复的摘要。我们把这类摘要调得易于快速浏览，包含指标时间序列、CPU 火焰图与 trace，帮助工程师迅速理解结论并核验证据。工程师可以直接修改 PR，也可以依据诊断自己写修复。如果他们在 PR 上留言，工作流会唤醒 agent 来处理这些意见。

![Performance Factory 的报告显示 worker 启动时间翻了一倍多，并给出影响与恢复情况、根因与拟定修复。](https://images.ctfassets.net/kftzwdyauwt9/5w8KpwlFR3tNfJbAStImkG/ee5f1df65a302cb09dde0a7d52d09138/performance-factory-worker-startup-report.png?w=3840&q=90&fm=webp)

*一次性能回退的任务报告示例，展示了关键细节、根因与拟定修复。*

工程师部署修复之后，工作流会唤醒 agent 检查性能是否回到了先前的基线。如果回去了，agent 就把任务标记为已解决。如果性能只部分恢复，agent 会结掉原来的回退，并为剩下的变慢新开一个任务——那可能是另一个原因造成的。如果毫无改善，agent 会记录发生的情况，并把这次回退打回去重新调查。

把修复做对，比找到原因更难。例如我们见过 agent 提出的改动比必要的更复杂，或引入了新问题。与根因这一步类似，我们给每个拟定的修复都加了一道对抗式评审，检查它是否针对根因，并帮助抓住 bug 或意外后果。有些修复还需要更高层次的架构决策。例如加一层缓存可能提升性能，却带来数据陈旧的问题。这类改动需要熟悉该服务、能权衡取舍的工程师来把关。

我们正用这些案例构建一个评估与改进闭环。把 agent 提出的修复与工程师最终合并的改动相比较，我们能更好地理解提案差在哪里、据此构建 eval、改进工作流。我们也在尝试使用合成的性能测试，让 agent 在请工程师评审之前先自行度量拟定的修复并加以修订。我们还在探索如何让 agent 使用我们其他的 agentic 评审工具来识别低风险改动，最终在没有人留在闭环里的情况下把这些修复发布出去。

## 我们学到了什么

构建并运行 Performance Factory，让我们在开发和运营生产环境中的 agent 工作流上学到很多。以下是一些经验，供正在搭建自有 agentic 工作流的团队参考。

### 保护工程师的注意力

Codex 调查的原始输出可能是一堵难以解析的文字墙。要弄清 agent 在主张什么，还得去翻出对应的图表看数据是否支撑它，都很费劲。我们希望工程师把注意力花在决策上，而不是用来复原 agent 做过的事。

agent 能调查的回退数量，远超一个团队有空去读的数量。我们的第一个版本给了工程师一个塞满发现的 UI，但还是得有人来判断哪些信息要紧。同一次回退还可能在告警、监控与各个渠道里表现为若干起不同的事件。现在这个工作流会把相关事件关联起来，按团队关心的指标分组，并对估计影响排序。工程师就能专注于补充上下文、权衡取舍、决定发布什么。

### 评估你对 agent 做的改动

更新一个调查 skill，或升级模型，可能让 agent 在某些案例上诊断得更好、在另一些上更差，所以我们需要在更新前测试其影响。我们分开测两件事：1) agent 调查得有多好；2) 它给出的摘要对工程师有多大用处。

#### 评估调查质量

对调查而言，我们用历史上真实的生产事故做回测。我们把那些事故变成一套测试用例，在改动 skill 时可以重跑。由 Codex agent 尝试调查并解决该事故，我们再拿 agent 的表现与过去的真实处置记录对比。每个用例都从一个全新的 Codex 调查者和原始信号开始，信号中凡是可能泄露答案的细节都会被剥掉。

用历史数据做测试要小心。指标与 trace 会过期，而恢复之后才收集的证据又可能泄露原因。只有当我们清楚调查者能看到哪些证据时，测试才有意义。agent 可以在既定范围内查看代码、查询生产遥测数据，但不能使用保存的记忆（以往调查的笔记）、不能读取事故复盘文档、也看不到先前运行的结果。事后我们还会检查它的对话记录，看是否混入了可能让测试失效的信息。

我们给三项打分：问题何时开始、规模多大、哪些请求受影响。我们还会评估 agent 如何用证据对可能原因排序，以及如何说明哪些地方仍不确定。agent 可能把时间点搞对了，却怪错了部署，所以我们把这两项分开打分。

#### 评估 agent 到工程师的交接

我们用已保存任务的快照来评估任务摘要。这类回测特别合适，因为摘要不依赖会过期的外部指标或 trace。另有一个独立的评分者，检查不熟悉该系统的工程师能否看懂发生了什么、为什么重要，有用的图表是否保留下来，以及拟定的下一步是否有证据支撑。

### 把反复出现的故障变成自修复

最后，我们的 agent 和它们所调查的服务一样需要被监控。一个坏掉的 profiler 或一项缺失的权限，都可能让 agent 无法验证变慢的原因。这类故障在最终报告里很难被看出来，所以我们每天跑一个 agent，翻查近期运行的消息与日志，找工具故障与访问错误。

我们用 Performance Factory 做自修复，解决这项检查发现的那些问题。当同一个工具错误阻塞了多次调查，agent 就创建一个任务去修它。如果原因清楚，agent 提出修复，工程师评审该改动并决定是否合并。合并这类改动后，我们还会用 eval 检查 agent 能否越过此前卡住它的那一步。

## 接下来：更广的应用、主动监控

Regression Workflow 只是 agent 工厂这一模式的一个实例：任务在显式状态之间流转。后续工作就绪时由 agent 推进任务；独立的评审者质疑结论；当下一个决策需要判断时，工程师介入。其他工作流可以复用同一套机制，只需换掉状态、指令与事件。

*从一个工作流到多个工作流。Performance Factory 可以跨工作流协调 agent，某个工作流里的 agent 能为另一个工作流创建任务。*

目前，我们的 Regression Workflow 只在告警触发时启动。不过我们正在研究更主动的方式，让 Performance Factory 即使没有告警，也能发现变慢的地方和可优化的点。我们希望 agent 利用我们已经采集的大量细粒度性能数据，找出告警漏掉的回退，或发现可优化之处。通过比对不同类型的数据（成批的 CPU 与内存 profile、堆转储、跨版本的请求 trace），agent 也许能注意到某个请求的 CPU 用量小幅上升。随后它可以在 Regression Workflow 里开一个任务，把这个上升追溯到原因、实现修复、开一个 PR 供工程师评审。

在已经知道该找什么的情况下，我们正把已知信号固化进更多 Performance Factory 工作流。比如我们的 service rightsizing skill 能帮 agent 发现这样的 autoscaling 设置：它让服务跑着比实际需要更多的 replica。一旦我们学会了识别这类模式，就想为它构建一个工作流，并在所有服务上定期运行，在快速变化的环境里持续优化。有了 Performance Factory，工程师从一次变慢中学到的东西，可以影响我们如何调查与修复下一次问题，哪怕那是几个月后、发生在另一个服务里。

下次你用 ChatGPT 觉得变慢时，很可能 Performance Factory 已经在查明原因了。今天，瓶颈也许在于等工程师评审并合并修复。我们已经在探索 agent 能否自己完成这一步。随着产品开发借助 Codex 不断加速，性能系统也需要变得越来越自主、越来越能自我改进才能跟上。Codex 已经帮我们把 ChatGPT 造得更快，现在它又帮我们让 ChatGPT 保持快速。
