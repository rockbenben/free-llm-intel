# 应对对抗性蒸馏

我们如何应对蒸馏带来的安全风险，以及我们在强化全行业防护方面获得的经验。

随着前沿模型的能力不断提升，防护措施在决定这些模型能否被负责任地使用上起着越来越重要的作用。对抗性蒸馏为恶意行为者提供了一条绕过适当防护、复制这些能力的路径。行为者可能未经授权就使用某个前沿模型的输出，去训练另一个具备相似能力的模型，然后在不具备同等保护的情况下将其部署。例如，对手可能蒸馏某个模型的网络能力，再用由此得到的模型协助发动网络攻击——这些攻击原本的模型会拒绝协助，或者会被其防护措施拦下。

本文介绍 OpenAI 如何检测并阻断对抗性蒸馏、如何加强对模型受保护推理的保护，以及我们总结出的、有助于全行业强化防御的经验。

我们应对对抗性蒸馏的方法，把对抗性测试、模型训练、分类器和 API 层保护，与对协同提取模型能力行为的调查结合起来。这些更新后的防护措施，与我们用于生物学和网络安全领域的防护更为接近。

我们尤其重视阻止攻击者提取模型受保护的推理：即模型在求解过程中于内部生成的中间步骤，也就是所谓的思维链。这些轨迹可能包含最终答案中略去的信息，因而对另一个模型来说格外有价值，是极佳的训练数据。

我们已在 GPT‑6.2 Astra 和 GPT‑6.2 Sol 中强化了针对受保护推理提取的防御。在一次使用[强自动化红队测试](https://openai.com/index/unlocking-self-improvement-gpt-red/)的内部自适应评测中，我们检验了攻击者能否还原模型在回答先前 prompt 时生成的受保护推理。平均攻击成功率从使用原始防护的 GPT‑6 Astra 的 54.0%，降至使用更新防护的 GPT‑6.2 Astra 的 0.2%。

## 为什么蒸馏是安全问题

蒸馏是一种常见的机器学习技术，即一个模型从另一个模型产生的数据中学习。例如，模型可以学习另一个模型的答案、它的推理过程，或者它对哪些答案更好、为什么更好的判断。除知识产权方面的顾虑之外，未经授权的蒸馏还带来严重的安全风险。通过对抗性蒸馏，第二个模型可以学到先进的前沿能力，却不必继承约束原模型如何使用这些能力的防护措施。

在网络安全和生物学这类两用领域，这一顾虑尤为明显。帮助防御方发现软件漏洞的模型，同样能帮助攻击者利用这些漏洞；协助生物学研究的模型，同样能帮助他人培养有害病原体。若这些能力被转移到防护更弱的模型上，该模型就可能提供原模型会拒绝、或原防护会拦下的协助。

## 保护精确推理轨迹对网络安全的重要性

我们的模型帮助用户完成编程和防御性网络安全任务。用大量此类良性输出训练出的第二个模型，可能学到同样适用于攻击性网络安全任务的技能。为更好地理解这一点，我们研究蒸馏——尤其是涉及推理轨迹的蒸馏——会如何转移有风险的网络能力。

在这一设定中，产生训练数据的模型称为教师模型，向它学习的模型称为学生模型。在一项关于网络能力如何转移的内部研究中，我们把用户通常可见的内容——最终回答、推理摘要和工具交互——作为蒸馏的基线，并测试当学生模型能接触教师模型的精确推理轨迹时会额外转移多少网络能力。

每次训练都从同一个预训练学生模型出发。我们构建了一个监督微调数据集，主要由 Astra 级教师模型完成编程和防御性网络安全任务时的轨迹组成。每条轨迹都包含模型处理任务时采取的每一步，包括所有工具交互和最终回答。我们在微调后对每个学生模型做一次评测，在网络安全与编程环境中进行一轮轻量强化学习后再评测一次。

经过监督微调，用精确推理轨迹训练的学生模型总体优于用推理摘要训练的学生模型。经过强化学习后，在图中所示两个基准的、所测试的最大推理预算下，精确轨迹学生模型的得分仍然更高；而在较低预算下，由摘要训练的学生模型得分更高。[1](https://openai.com/index/combatting-adversarial-distillation/#citation-bottom-1)

我们的网络蒸馏结果表明，保护推理轨迹能够限制网络能力的转移，即便底层任务属于我们的使用政策所允许的范围。在许多此类交互中，精确推理轨迹能教会学生模型一些可泛化到教师模型原本任务之外的技能。我们将继续研究在不同学生模型和不同蒸馏训练配方下，能力额外转移的程度。

## 相互强化的多层防御

我们在防护体系的两个互补层面上防御对抗性蒸馏。在请求层面，模型行为、分类器检查和 API 控制共同限制推理轨迹被提取。在行动层面，我们从请求级和账户级信号中寻找能够揭示协同提取企图的模式。反过来，调查中发现的攻击又成为训练和检验防护措施的样本。

### 保护单个请求与响应

#### 针对模型行为的防御性训练

对抗性训练教会模型识别推理提取企图，并拒绝披露受保护的推理，同时保留对合理的解释与协助请求的正常回应。对抗性训练样本来自内部自动化红队测试、调查以及外部研究者或行业伙伴对潜在安全弱点负责任披露所发现的成功攻击。

#### 分类器防护

我们用输入分类器检测提取受保护推理的企图，用输出分类器检测助手消息和工具调用参数中受保护推理的泄漏。这些防护对流式与非流式响应同样生效。

工具调用的覆盖很重要，因为模型可以在工具参数中暴露受保护的推理，却不把它写进最终回答。输出分类器能在这些内容到达调用方之前拦截可疑泄漏。

#### API 层保护

API 层保护限制受保护推理在不同交互和不同模型之间被复用。[我们 9 月的披露](https://openai.com/index/disrupting-a-coordinated-model-distillation-campaign/)描述了这样的攻击：把加密的推理从一段对话转移到另一段对话，再要求模型以用户可读的形式揭示该推理。我们加强了跨用户、工作区、组织和模型系列边界的保护，包括封堵了一条可能暴露其他用户加密推理的路径。

在 GPT‑6.2 Astra 和 GPT‑6.2 Sol 上，我们把模型的受保护推理与产生它的对话历史绑定。随着新消息加入，模型可以在先前的推理基础上继续。如果较早的消息被改写，我们的 API 会[丢弃其后的推理](https://developers.openai.com/api/docs/guides/keep-prefix-unchanged)。我们同时阻止防护更弱的旧模型系列读取 GPT‑6.2 Astra 和 Sol 的受保护推理。

### 调查并阻断协同行动

当我们的系统检测到未经授权的对抗性蒸馏行动——这类行动往往包含协同提取模型推理的企图——我们会调查相关账户。一旦确认违规，我们会依据政策和服务条款，对这一账户网络采取处置措施。通过对每个行动的调查，我们获得可用于升级防御的洞见，从而更好地识别类似活动。我们还会与其他模型提供方共享妥协指标，便于他们调查自家服务上的相关滥用行为。

这项工作不止于我们自己的平台。[我们的一致性标准政策](https://openai.com/index/broad-access-through-consistent-standards/)为提供我们模型的各家提供方确立了共同的防护标准与协同处置机制。我们在适当情况下与伙伴紧密合作，维护这些标准，并强化各部署环境中的保护。

在适当情况下与行业和政府共享相关发现，有助于阻断这类行动，也能让模型开发者和提供方更好地识别和防御针对前沿模型的蒸馏企图。

## 衡量进展

### 对推理提取的抵抗力

为衡量请求层面的各项防护协同工作的效果，我们在一个尽量贴近模型与防护真实生产部署的设定中，测试攻击者是否仍能提取受保护的推理。在静态评测中，我们重放一组固定的、此前成功过的攻击，看哪些仍能暴露受保护推理。在自适应评测中，自动化 AI 红队会根据系统响应调整策略，从而发现静态测试遗漏的弱点。

我们还会改变测试方能看到什么。黑盒测试给他们的视野与外部用户相同，白盒测试则提供关于系统的额外信息，帮助他们构造更强的攻击。在自适应黑盒评测中，我们测试攻击者能否还原模型在回答先前请求或当前请求时生成的受保护推理。在使用更新防护的 GPT‑6.2 Astra 上，各类攻击的平均成功率均低于 1%。这两项成功率都显著低于使用原始防护的 GPT‑6 Astra。我们目前也在把选定的防护改进应用到 GPT‑6 Astra 上。

### 行动检测与处置

今年以来，我们在平台上发现了多起未经授权的对抗性蒸馏行动，并在 9 月的[报告](https://openai.com/index/disrupting-a-coordinated-model-distillation-campaign/)中分享了初步发现。我们每周针对这些行动采取处置，规模从数千个账户到数万个账户不等，且今年夏天以来频率显著上升。

为衡量工作的成效，我们还跟踪蒸馏滥用的普遍程度，以及从检测到处置之间的时间。我们的目标是压缩蒸馏者所能获取的数据量与数据价值，提高蒸馏行动的成本，并缩短响应新攻击所需的时间。我们通过对抗性测试和调查持续改进这些防御。

## 对抗性蒸馏的国家安全影响

对抗性蒸馏还构成国家安全风险。境外行为者若从美国模型复制出先进能力，就可以在开发者所设保护之外部署它们。今年 2 月，我们向国会[做了简报](https://assets.bwbx.io/documents/users/iqjWHBFdfxIU/rRmql_jJcxb4/v0)，说明有迹象显示 DeepSeek 正试图蒸馏美国的前沿模型。9 月，我们[报告](https://openai.com/index/disrupting-a-coordinated-model-distillation-campaign/)阻断了一起提取模型受保护推理的行动，并把其中核心部分归因于与 Kimi 的开发者 Moonshot AI 有关联的个人。我们计划很快分享更多关于近期所阻断行动的细节。

我们支持通过立法，让美国政府有更多手段识别和制裁非法从美国 AI 模型中提取能力的境外行为者。我们也已告知国会，我们支持《芯片安全法案》（Chip Security Act）、《AI OVERWATCH 法案》和《MATCH 法案》。更严格的出口管制可以限制对手获得训练前沿模型所需的硬件；而蒸馏防御则让对手更难从已经训练好的模型中获取部分同样的能力。两项努力共同帮助美国保持在前沿 AI 领域的领先，也让开发者在需要时间测试防护时拥有更大的推迟发布空间。

## 其他人如何在此基础上推进

支持前沿能力的安全扩散，是我们反蒸馏工作的重要目标。迄今的经验表明，其他模型开发者和平台可以采取几项有用的措施：

- 在整个交互过程中保护私有推理。检查助手消息和工具调用参数是否有泄漏，并限制加密推理在对话之间、模型之间被复用的方式。
- 把通过红队测试、生产监控或负责任披露发现的成功提取攻击日志保留下来，用作回归测试。在适当情况下并符合适用隐私政策的前提下，用这些样本改进模型训练和分类器。评测更新后的防御时，重放原始攻击，检验自适应红队是否仍能找到穿透这些防御的方法。
- 把请求层面的缓解措施与行动层面的调查和处置结合起来。
- 与部署伙伴协调防护要求和处置机制，并与其他 AI 模型开发者交流经验，确保全行业蒸馏防护具备较高的下限。

我们此前还通过[前沿模型论坛](https://www.frontiermodelforum.org/)（Frontier Model Forum）和适当的政府信息共享渠道分享发现，帮助其他开发者强化防御，同时把攻击者可能利用的细节保持在私密范围内。我们将继续与研究者、开发者和伙伴合作，分享我们关于新型攻击和有效防御的所知。

在让前沿 AI 广泛可用的同时，我们的对抗性蒸馏防御旨在降低其能力在没有充分防护的情况下被复制的风险，以支持我们的使命：确保通用人工智能被安全部署，并惠及全人类。
