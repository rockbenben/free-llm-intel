# 快速扩展在线存储以服务超过 10 亿 ChatGPT 用户（第二部分）

我们如何在应用程序存储平台 Habitat 中优化 Azure Cosmos DB 以管理前所未有的增长。

作者：Jon Lee、Hrachya Hakobyan 和 Chaomin Yu，技术人员

所有 OpenAI 产品都需要快速、可靠地访问由我们的存储平台 Habitat 提供的数据。它必须在几毫秒内响应 40 个地理区域的超过 10 亿用户。我们的基础设施面临着巨大的挑战：支持爆炸性增长和新用例，同时继续提高可靠性、性能和产品开发速度。解决这一挑战需要重新思考我们的在线存储平台的设计和运营方式。我们不断评估权衡，遵循以下模式：首先对于关键任务产品流量来说足够可靠，然后对于全球用户来说足够快，最后，能够灵活地大规模运营。

这个由两部分组成的系列介绍了我们如何将 Habitat 从一个简单的客户端库和数据库开发为一个可服务超过 500 PB 数据的全球分布式存储平台。 [第一部分](https://openai.com/index/scaling-storage-one-billion-users-part-one/) 重点介绍了 Habitat 从 Python 客户端到服务的演变。它还涵盖了使我们能够推动基于 Python 的服务远远超出许多人认为实用的技术。

在这篇文章的第二部分中，我们将介绍如何扩展底层存储组件：Azure Cosmos DB。通过与 Azure 团队的密切合作，我们找到了一种可行的共同管理容器的多租户方法，在全球范围内具有出色的读取性能。

## 使多租户大规模可靠

随着公司规模的扩大，基础设施团队通常从运行单租户系统发展为多租户系统。在单租户模式下，每个产品表面团队都维护自己的系统，可减少爆炸半径并提供简单的所有权边界和工作负载隔离。随着团队和产品面的增长，运行成本变得昂贵。单租户使每个产品团队都负责容量规划，并且通常会导致严重的过度配置。

相反，多租户将控制权分配给集中式数据库团队，他们在配置资源方面拥有更好的知识和经验。但多租户也带来了自己的问题，例如吵闹的邻居问题，其中一个租户消耗了异常大的资源份额，从而损害了其他租户的利益。

在 Habitat 中，我们必须权衡所有这些权衡，才能大规模设计可靠、高效的存储系统。如今，Habitat 是许多 OpenAI 产品的多租户数据库层，但我们经历了从使用一个多租户 Azure Cosmos DB 容器到预配单租户支持容器，再到默认恢复为多租户容器的循环过程。我们在 Habitat 上的多租户故事还处于早期阶段：我们支持大量用例，但我们已经能够通过尽可能利用 Azure Cosmos DB 的内置原语来推迟在该领域的投资。

## Azure Cosmos DB 容器的简化入门

在开始我们的 Azure Cosmos DB 之旅之前，先了解一些基本背景：

- Azure Cosmos DB 帐户定义一组容器和复制策略
- 每个容器都配置有一定的吞吐量（以每秒请求单位 (RU/s) 为单位）
- 每个容器内的数据以典型的按指定逻辑分区键分片的方式存储，并记录每个逻辑分区键的存储和吞吐量限制
- Azure Cosmos DB 在较少的支持物理分区上处理逻辑分区键的分片，当存储超过阈值或容器需要更多物理分区来维持预配吞吐量时，将它们拆分为多个物理分区

## 第一阶段：依赖 Azure Cosmos DB 原语

我们最初允许任何客户端加载，依靠每个逻辑分区键规定的 10K RU/s 限制来提供背压。当我们第一次开始时，我们还在每个帐户中仅使用一个默认的 Azure Cosmos DB 容器。这种方法效果很好，但由于以下几个原因而被证明是有问题的：

### 逻辑分区键限制

由于早期的 API 选择，我们直接向客户端公开了逻辑分区键选择。因此，在不同的产品用例中，常用分区键（例如“user_id”或“workspace_id”）经常发生冲突。由于这些用例共享 Azure Cosmos DB 对相同逻辑分区键的限制，因此设计限制了给定用户的总体吞吐量。

在迁移到 Habitat 和 Azure Cosmos DB 之前，我们在扩展 Postgres 时遇到的一个常见问题是来自非常热门的组织或热键（一个租户生成不成比例的高负载）的许多请求能够删除整个数据库。我们花费了大量的集体努力来缓存这些密钥并将租约构建到缓存未命中中，以便由此产生的缓存未命中负载不会影响底层数据库。

## 不同的客户端，相同的分区键

### 吵闹的邻居

虽然记录的数据大小和吞吐量限制适用于逻辑分区键，但物理分区实际上是强制实施限制的地方。实际上，这意味着逻辑分区无法达到 10,000 RU/s。相反，它们与该物理分区上并置的所有其他逻辑分区键共享物理分区的限制。

这使得嘈杂的邻居影响许多不相关的逻辑分区键，工作负载对利基产品功能的数据进行操作，从而扰乱了核心登录和注册流程。

图02b·吵闹的邻居

## 不同用户，同一个物理分区

### 弱分区

给定物理分区的吞吐量限制也是可变的，具体取决于分配给 Azure Cosmos DB 容器的总吞吐量。容器的预配置吞吐量大致均匀地分布在该容器的物理分区上。

随着数据量的增长，物理分区会分裂，从而增加分区总数，而总预配置吞吐量保持不变。结果是每个分区的有效吞吐量限制随着数据大小的增长而缩小。

对于我们大多数存储量大、类似 blob 的用例，这会创建一种故障模式，其中存储增长本身就会降低活动工作负载的吞吐量，即使请求率和使用率保持稳定也是如此。

## 第二阶段：尝试工作负载隔离和单租户

单独的容器有助于部分解决这些分区键限制和嘈杂的邻居。通过使用单独的容器，每个容器都可以分配自己独立的物理分区，并且只有该容器本身的不同工作负载可能是嘈杂的邻居或在分区键空间中重叠。不利的一面是，配置新容器的开销不为零——每个容器都需要个性化的容量规划——因此我们希望仅在有意义的服务或用例边界上创建容器。

我们开始对需要强隔离的最关键的新用例使用单独的 Azure Cosmos DB 容器。结合通过同步为每个容器配置的总吞吐量与其物理分区数量来管理弱分区的脚本，我们基本上避免了所面临的所有问题。

然而，由于我们从默认容器开始，不幸的是，许多遗留的关键用例在没有数据迁移的情况下被困在那里。为了保护仍然依赖于共享默认容器中数据的关键服务，我们经常建议团队为新服务或主要产品功能创建单独的容器。随着我们的扩展，默认容器的压力越来越大，生产事件也越来越多。我们开始为任何新服务或大型产品功能提供容器，只是为了保护默认容器免受更多负载。

这使我们避免了许多站点范围的中断，限制了功能或服务降级中断的影响范围。然而，配置新容器的开销最终还是困扰着我们：

### 总量增长缺乏稳定

在旧的共享默认容器中，任何特定的新用例从 0 QPS 到 100 万 QPS 都不太可能显着改变总聚合使用量。然而，在孤立的容器上，QPS 从 0 到 100 万的新用例可能比仅归因于内部测试的基线负载高出 1,000 倍。

有了专用容器，团队现在需要记住预先配置容器以达到其启动时的预期吞吐量水平。产品团队经常将他们的功能交付到生产中，而忘记预先扩展，而我们会在发布当天坐在 SEV 房间里，试图在最后一刻扩展容器。

这是多租户系统的核心工作负载混合优势，我们为了通过此容器策略实现更好的隔离而失去了这一优势。

### 容量规划

随着时间的推移，监控专用容器的使用情况还需要对流量何时发生变化或增长有深入的产品了解。

我们可以提供一个基本的控制平面脚本，根据增长趋势来扩展每个容器的预配置吞吐量，但如果没有稳定的总体增长，正确扩展这些脚本基本上使 OpenAI 的每个产品团队都能够参与容量规划。

这未能在组织上进行扩展，因为每个服务所属团队为其 Azure Cosmos DB 配置付出的努力程度存在很大差异。

## 第三阶段：默认使用多租户，具有数据移动能力

随着组织的发展，这些运营问题变得难以规模化。没有单独的中央团队进行规划会导致许多团队规划不佳。因此，我们最终转向多租户解决方案，并与 Azure 团队密切合作，通过共享租户设计修复了我们最初的多租户问题：

### 热键节流

首先限制最热的键可以防止嘈杂的邻居消耗给定物理分区的所有可用吞吐量这可以减少嘈杂的邻居效应，其中一个热键可以具有站点范围的爆炸半径。

### 服务质量 (QoS)

请求分层 QoS 同样可以防止脱机工作负载（例如批量插入或数据提取）利用给定物理分区的所有吞吐量。通过为这些工作负载的请求分配较低的优先级，它们首先会受到限制，从而防止对服务最终用户的较高优先级的交互式请求进行限制。

### 无服务器模式

Azure Cosmos DB 已经有了无服务器模式，可以通过预配模式解决弱分区问题。然而，它有一个主要缺点：它仅根据存储使用情况进行扩展，并将每个物理分区的 RU 使用量限制为 5K RU/s。这将解决我们的弱分区问题，但会阻止我们扩展 RU 密集型用例。

Azure Cosmos DB 团队为我们构建了新的改进的无服务器模式，允许每个物理分区扩展到 10K RU/s，除了基于存储使用的拆分之外，还引入了基于 RU 使用的拆分，使我们能够停止手动监控和扩展容器。

通过这些更改，我们已经能够重新使用一个共享容器，这大大简化了为产品团队进行任何前期或持续容量规划的需要，同时保持工作负载之间的隔离。从那以后的几个月里，尽管我们加快了产品开发，但我们没有发生任何供应或吵闹的邻居事件。

## 共同管理服务的可靠性更高

当公司发展到 OpenAI 的规模时，托管服务的“托管”程度就会降低。许多工作负载成为云提供商基础设施中的异常值。随着 OpenAI 成为 Azure Cosmos DB 的最大用户之一，成功运营它需要不同的模型：共享测试、共享仪表板、直接工程渠道以及仅在我们的规模中出现的故障模式的共同所有权。如今，我们最大的 Azure Cosmos DB 帐户存储了 10 PB 的数据，并提供超过 20M QPS。据我们所知，我们是唯一一家如此规模部署 Azure Cosmos DB 的公司。

2024 年底，一次区域性停电清楚地表明了这种合作的必要性。当时，我们最大的 Azure Cosmos DB 帐户之一的主要 Azure 区域发生了停电。在最终的故障转移练习中，我们意识到我们最大的帐户需要几个小时才能故障转移到次要区域，我们的团队和 Azure Cosmos DB 团队都没有在我们的规模上进行过测试。

大约一个月后，当这些帐户无法返回原始区域时，我们引发了另一次严重的中断。与原始区域的连接混乱导致原始区域的 Azure Cosmos DB 网关不堪重负。网关模式 Azure Cosmos DB 客户端处理故障转移的方式存在一个怪癖，导致所有客户端立即建立连接并向原始区域发送请求，即使只有一部分物理分区已移回该区域。

在每次中断中，OpenAI 和 Azure 都运行了其事件管理流程，确定了许多根本原因并部署了修复程序。但这些中断是我们团队和 Azure Cosmos DB 团队操作和测试方式之间更大系统性问题的症状。起初，利用托管服务使我们能够快速行动并专注于业务目标。随着规模的扩大，托管服务的管理程度越来越低，需要与服务提供商在从设计到运营的各个层面进行深度集成。

如今，Habitat 和 Azure 工程团队共同监控 Habitat 的每一层，从我们的服务层到 Azure Cosmos DB 的物理存储层。我们针对生产规模但非生产的 Azure Cosmos DB 帐户操作和测试更改。我们一起测试和迭代 SDK，并确定如何扩展和调整 Azure Cosmos DB 帐户的最佳实践。我们可以通过 Teams 直接进行工程访问，甚至公开了无需通过支持层即可直接相互寻呼的方法。

去年，我们进行了大量的联合工作，以提高 Azure Cosmos DB 控制平面和网关的可扩展性，在网关中添加负载保护和缓存各种 Azure Cosmos DB 元数据，以保护 Azure Cosmos DB 元数据分区，通过连接池和更高的连接重用来减轻 Python 栖息地服务进程群的压力，尽可能共置工作负载，以及通过不同的 VPC 将关键工作负载与离线工作负载隔离。

去年，这种程度的联合工程对于我们的 Azure Cosmos DB 稳定性至关重要。任何足够大或足够关键的系统都需要这种团队合作：打破所有权壁垒并跨组织边界运行。

## 在全球范围内提高绩效

正如第一部分中提到的，我们的核心理念是：让它工作、让它快速、让它便宜。首先是可靠性，然后是性能，最后是效率。 Habitat 已成为 OpenAI 的关键基础设施，因此首要任务是使其可靠。随着系统在 2025 年趋于稳定以及 OpenAI 在全球范围内的扩张，延迟成为用户和产品团队的下一个限制。

计算和存储容量通常位于不同区域，跨区域请求不可避免。

延迟差异很大，具体取决于数据存储位置和请求服务位置。为了使 Habitat 请求具有高性能，产品开发人员依赖于额外的客户端缓存、请求批处理、最大限度地减少数据库读取和写入，并尽可能将工作移出关键路径。虽然这导致了一些有趣的产品设计，对数据库问题更具弹性，但它也使产品变得更加复杂并减慢了产品迭代：未能实现 Habitat 鼓励快速产品开发且不需要了解数据库的目标。

这是我们 2026 年的重点，我们制定了优化读取性能的分层策略，这代表了 Habitat 90% 以上的请求：

### 在容量允许的情况下将数据存储在用户附近

我们在全球不同的 Azure 区域拥有多个 Azure Cosmos DB 帐户，供有数据驻留要求的用户使用。即使对于没有硬数据驻留要求的用户，在用户附近托管数据也可以通过降低延迟来改善他们的体验。

在实践中，我们无法在数据驻留用例之外广泛实现这一点，因为放置受到物理云容量的限制。由于我们数据集的大小，许多区域无法容纳其用户流量比例所需的大量存储空间。

在数据中心容量、电力或冷却有限的地区，我们有时面临直接的权衡：为托管存储保留容量并降低 Habitat 延迟，或者使用该容量来提供额外的计算服务并将存储请求路由到更远的地方。

因此，放置决策通常是以下产品之间的权衡：A) 优化不同产品和用户子集的延迟，B) 原始存储和计算容量。

### 仅广泛复制最小和对延迟最敏感的数据集

对于延迟最关键的工作负载（例如每个请求所需的身份验证元数据），我们通过在许多次要区域中使用高度复制的 Azure Cosmos DB 帐户来减少计算和 Habitat 之间的 RTT。一些帐户会复制到我们提供流量的所有 40 个 Azure 区域；其他的复制到每个大陆至少一个区域。

我们必须比预期更早地在 Habitat 中构建透明的数据移动和路由层，以便我们可以在具有不同复制拓扑的帐户之间移动数据集。

然而，这种方法最终也受到容量限制，因此仅限于一些手工选择的数据集。

### 依靠集成缓存来处理其他一切

Habitat 工作负载的读取量非常大，应用程序不断获取设置、状态和其他属性；不成比例的流量归因于相对较小的频繁访问类型的工作集。这使得该系统特别适合分布式缓存。虽然缓存提高了单区域基础设施的性能，但在跨区域工作时，这种改进会更加复杂，它可以用来“隐藏”跨区域延迟。

我们已将分布式后备缓存层集成到 Habitat 中。它将最近访问的对象和边缘的副本存储在 Valkey 服务器中，这些服务器放置在我们的基础设施中靠近处理用户请求的位置。通常，此类缓存使用 TTL，在命中率和陈旧性之间进行权衡。短 TTL 可以减少过时性，但会削弱缓存的积极影响，因为项目很快就会从缓存中过期，并且必须更频繁地检索。较长的 TTL 可以提高命中率，但会长时间提供陈旧数据，从而导致较差的用户体验和不可预测的产品行为。

另一种方法是当应用程序对相同的底层数据执行写入操作时执行显式失效操作。这极大地提高了缓存数据的新鲜度，但可能很难做到正确。它还仍然受到许多边缘情况的影响，例如部分故障，这会使缓存失效。多区域部署使这些问题变得更加复杂，跨区域网络的可靠性较低，并且缓存与底层存储的复制竞争。用 TTL 来补充这一点限制了最大的陈旧性，但仍然受到上面讨论的相同的底层 TTL 权衡的影响。

我们追随 Meta 的 TAO 等系统的脚步，采用了更先进的失效方法。 Habitat 的集成缓存依靠通过 Azure Cosmos DB 的更改源进行的更改数据捕获 (CDC)，在几秒钟内将失效传播到全球范围内，从而实现高命中率，同时保持较低的过时性。我们基础设施中的服务会使用此更改源，并在更新底层数据时对本地缓存执行失效操作。这会导致下次读取数据时未命中，并且缓存会被最新版本的数据填充。

### 使用 Rust 减少代理开销

我们还通过用 Rust 重写代码来消除 Habitat 服务本身的开销，从而显着减少了延迟，这比原始 Python 的性能更高。

总之，这些变化将我们的整体全局读取 p50 从大约 120 毫秒减少到大约 10 毫秒，自今年早些时候开始关注性能以来，提高了 12 倍。

## 扩展变更数据捕获

可靠且可扩展的 CDC（将数据库更改传播到下游系统）不仅仅是 Habitat 缓存策略的关键组成部分。每秒捕获数百万个更改，跨越数千个容器和数百万个容器分区，通过一百多个 Kafka 主题提供数据，还支持最终一致的二级索引、数据移动管道、离线分析和其他实时产品功能。随着我们的支持基础设施在全球范围内发展，监听行变化变得越来越复杂。如果客户端想要注册回调以在其类型的行发生更改时运行，除其他外，他们必须首先确定哪些 Cosmos 帐户和容器包含其数据、哪个 CDC 服务部署正在侦听这些容器的相应区域中运行，并正确扩展 CDC 服务工作人员队列、Kafka 及其使用者。我们的 CDC 平台旨在将所有这些从产品开发人员手中抽象出来，并提供一个简单的界面，客户可以在其中注册他们想要在更改的行上调用的函数，而我们则处理所有的管道和扩展。

内部控制平面持续确保捕获所有必需的容器，选择要读取的 Cosmos 区域，并在多个地理区域的数千名工作人员之间高效地分配工作。使用副本区域和较低优先级的提要读取可以保护对延迟敏感的 Habitat 流量免受后台捕获工作负载的影响。在这么大的队列中，工作线程崩溃、容器问题、租赁存储错误、无效配置和目标故障不断发生。我们强化了 CDC 工作线程生命周期和租赁处理，隔离了流之间的故障，并为配置更改和部署建立了保护措施。我们利用死信队列来防止由于永久交付失败而造成的队头阻塞。我们通过将读取器切换到备用 Cosmos 区域来容忍区域中断。在我们的规模下，我们甚至不得不对 Azure 的 CDC SDK 进行更改，通过在内存中批处理检查点并仅定期刷新它们来提高其检查点实现的效率。

虽然 Habitat 对 Azure Cosmos DB 的内部使用很复杂，但其价值主张始终是从产品开发人员那里抽象出基础架构细节，以提高产品开发速度，我们的 CDC 平台也不例外。

## 展望未来

一个小团队能够通过故意缩小存储 API、继续扩展 Python 服务并优先处理最紧迫的工程挑战来支持快速增长的存储平台。我们首先关注关键任务产品流量的可靠性，然后关注全球用户的读取性能，最后关注大规模运营效率。这种方法实现了快速增长和新用例，同时提高了可靠性、性能和产品开发速度。

为了为下一个十亿用户扩展 Habitat 和对话存储，我们需要解决在更大范围内跨基础设施复制数据的困难。为了预防这种情况，我们一直在构建一个自定义的内部 EB 级在线存储系统，针对庞大的 Habitat 数据类型进行了优化。这个正在开发的系统将 Rockset 的 RocksDB Cloud 核心与基于 Raft 的复制相结合。它实现与 Azure Cosmos DB 相同的文档模型，但使用分解存储和物理复制来减少所需的闪存容量，以换取较低的峰值 qps。
