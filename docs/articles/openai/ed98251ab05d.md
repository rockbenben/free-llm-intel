# 在 API 中推出结构化输出

我们在 API 中推出结构化输出（Structured Outputs）——模型输出现在能够可靠地遵循开发者提供的 JSON Schema。

去年在 DevDay 上，我们推出了 JSON mode——对于想用我们的模型构建可靠应用的开发者来说，这是一个有用的基础构件。虽然 JSON mode 提升了模型生成有效 JSON 输出的可靠性，但它并不保证模型的响应会符合某个特定 schema。今天我们推出 API 中的结构化输出，这是一项新功能，旨在确保模型生成的输出与开发者提供的 JSON Schema 完全一致。

从非结构化输入生成结构化数据，是当今应用中 AI 的核心用例之一。开发者用 OpenAI API 构建强大的助手，使其能够通过[函数调用](https://platform.openai.com/docs/guides/function-calling)获取数据并回答问题、为数据录入提取结构化数据，并构建让 LLM 可以采取行动的多步智能体工作流。长期以来，开发者一直通过开源工具、提示词工程以及反复重试请求等方式来绕过 LLM 在这方面的局限，以确保模型输出符合与其系统互操作所需的格式。结构化输出解决了这个问题：它把 OpenAI 模型约束为匹配开发者提供的 schema，并训练我们的模型以更好地理解复杂的 schema。

在我们针对复杂 JSON schema 遵循能力的评测中，新模型 `gpt-4o-2024-08-06` 配合结构化输出取得了 100% 的满分。相比之下，`gpt-4-0613` 得分不到 40%。

## 如何使用结构化输出

我们在 API 中以两种形式引入结构化输出：

1. **函数调用：** 通过 `tools` 使用结构化输出，方法是在你的函数定义中把 `strict: true` 设为真。该功能适用于所有支持 tools 的模型，包括 `gpt-4-0613` 和 `gpt-3.5-turbo-0613` 及之后的所有模型。启用结构化输出后，模型输出将匹配所提供的 tool 定义。

2. **`response_format` 参数的一个新选项：** 开发者现在可以通过 `json_schema` 提供 JSON Schema，这是 `response_format` 参数的一个新选项。当模型不调用工具、而是以结构化方式回应用户时，这非常有用。该功能适用于我们最新的 GPT‑4o 模型：今天发布的 `gpt-4o-2024-08-06` 以及 `gpt-4o-mini-2024-07-18`。当提供的 `response_format` 把 `strict: true` 设为真时，模型输出将匹配所提供的 schema。

## 安全的结构化输出

安全是 OpenAI 的首要任务——新的结构化输出功能会遵守我们现有的安全政策，并且仍允许模型拒绝不安全的请求。为简化开发，API 响应中新增了一个 `refusal` 字符串值，让开发者能够以编程方式检测模型是生成了拒绝还是匹配 schema 的输出。当响应不包含拒绝、且模型的响应没有被提前中断（由 `finish_reason` 指示）时，模型的响应将可靠地产出匹配所供 schema 的有效 JSON。

#### JSON

```
1{2  "id": "chatcmpl-9nYAG9LPNonX8DAyrkwYfemr3C8HC",3  "object": "chat.completion",4  "created": 1721596428,5  "model": "gpt-4o-2024-08-06",6  "choices": [7    {8      "index": 0,9      "message": {10        "role": "assistant",11        "refusal": "I'm sorry, I cannot assist with that request."12      },13      "logprobs": null,14      "finish_reason": "stop"15    }16  ],17  "usage": {18    "prompt_tokens": 81,19    "completion_tokens": 11,20    "total_tokens": 9221  },22  "system_fingerprint": "fp_3407719c7f"23}
```

## 底层原理

我们采用两步方法来提升匹配 JSON Schema 的模型输出可靠性。首先，我们把最新模型 `gpt-4o-2024-08-06` 训练为理解复杂 schema，以及如何最好地产出匹配它们的输出。然而，模型行为本质上是不确定的——尽管该模型性能有提升（在我们的基准上达 93%），它仍未达到开发者构建健壮应用所需的可靠性。因此我们还采用了一种确定性的、基于工程的方法来约束模型的输出，以达到 100% 的可靠性。

## 受约束解码

我们的方法基于一种称为受约束采样或受约束解码（constrained decoding）的技术。默认情况下，当模型被采样以产出输出时，它们完全不受约束，可以从词表中选择任意 token 作为下一个输出。正是这种灵活性让模型可能犯错；例如，它们通常可以在任意时刻采样一个花括号 token，即便那样并不会产生有效的 JSON。为了强制产出有效输出，我们把模型约束为只能选择根据所供 schema 有效的 token，而不是所有可用的 token。

在实践中实现这种约束颇具挑战，因为在模型输出的不同阶段有效 token 也不同。假设我们有如下 schema：

#### JSON

```
1{2  "type": "object",3  "properties": {4    "value": { "type": "number" }5  },6  "required": ["value"],7  "additionalProperties": false8}
```

在输出开头有效的 token 包括 `{`、`{“`、`{
` 之类。然而，一旦模型已经采样出 `{“val`，`{` 就不再是有效 token。因此我们需要实现动态受约束解码，在每生成一个 token 后判定哪些 token 有效，而不是在响应一开始就预先确定。

为此，我们把所供的 JSON Schema 转换为上下文无关文法（CFG）。文法是一套定义语言的规则，而上下文无关文法是符合特定规则的文法。你可以把 JSON 和 JSON Schema 看作有规则来定义语言内何者有效的特定语言。正如英语中一个没有动词的句子不合语法，JSON 中一个尾随逗号也不合语法。

因此，对每个 JSON Schema，我们计算一个表示该 schema 的文法，并对其组件进行预处理，以便在模型采样期间易于访问。这就是为什么用新 schema 的首个请求会带来延迟开销——我们必须预处理 schema 以生成这个产物，好让我们在采样期间高效使用它。

在采样期间，每生成一个 token 后，我们的推理引擎会根据此前已生成的 token 以及文法中指示哪些 token 接下来有效的规则，判定哪些 token 可以产出。然后我们用这份 token 列表对下一步采样做掩码，从而有效地把无效 token 的概率降为 0。由于我们已经预处理了 schema，可以使用缓存的数据结构高效完成这一点，延迟开销极小。

## 其他方法

针对该问题的其他方法通常使用有限状态机（FSM）或正则表达式（一般用 FSM 实现）来做受约束解码。它们的运作方式类似——都是在每产出一个 token 后动态更新哪些 token 有效——但与 CFG 方法有一些关键差异。值得注意的是，CFG 能表达的语言类比 FSM 更广。对于像上面 `value` schema 这样非常简单的 schema，这在实践中并无影响。然而我们发现，对于涉及嵌套或递归数据结构的更复杂 schema，这一差异是有意义的。举个例子，FSM 通常无法表达递归类型，这意味着基于 FSM 的方法在深度嵌套 JSON 中匹配括号时会力不从心。下面是一个递归 schema 示例，它在 OpenAI API 上受结构化输出支持，但用 FSM 则无法表达。

#### JSON

```
1{2  "name": "ui",3  "description": "Dynamically generated UI",4  "strict": true,5  "schema": {6    "type": "object",7    "properties": {8      "type": {9        "type": "string",10        "description": "The type of the UI component",11        "enum": ["div", "button", "header", "section", "field", "form"]12      },13      "label": {14        "type": "string",15        "description": "The label of the UI component, used for buttons or form fields"16      },17      "children": {18        "type": "array",19        "description": "Nested UI components",20        "items": {21          "$ref": "#"22        }23      },24      "attributes": {25        "type": "array",26        "description": "Arbitrary attributes for the UI component, suitable for any element",27        "items": {28          "type": "object",29          "properties": {30            "name": {31              "type": "string",32              "description": "The name of the attribute, for example onClick or className"33            },34            "value": {35              "type": "string",36              "description": "The value of the attribute"37            }38          }39        }40      }41    },42    "required": ["type", "label", "children", "attributes"],43    "additionalProperties": false44  }45}
```

注意，每个 UI 元素都可以带有任意子元素，而这些子元素递归地引用根 schema。这种灵活性正是 CFG 方法所能提供的。

## 限制与约束

使用结构化输出时有几项限制需要注意：

- 结构化输出仅支持 JSON Schema 的一个子集，详见[我们的文档](https://platform.openai.com/docs/guides/structured-outputs)。这帮助我们确保最佳性能。
- 使用新 schema 的首个 API 响应会带来额外延迟，但后续响应会很快、没有延迟惩罚。这是因为在首个请求期间，我们如上所述处理 schema，然后缓存这些产物以供后续快速复用。典型 schema 在首个请求时处理时间不到 10 秒，但更复杂的 schema 可能需要最多一分钟。
- 如果模型选择拒绝一个不安全请求，它可能未能遵循 schema。如果它选择拒绝，返回消息中的 `refusal` 布尔值会被设为 true 以指示这一点。
- 如果生成在到达 `max_tokens` 或其他停止条件之前未完成，模型可能未能遵循 schema。
- 结构化输出并不能防止所有类型的模型错误。例如，模型仍可能在 JSON 对象的值内部犯错（比如把数学方程中的某一步算错）。如果开发者发现了错误，我们建议在系统指令中提供示例，或将任务拆分为更简单的子任务。
- 结构化输出与并行函数调用不兼容。当生成并行函数调用时，它可能不匹配所供 schema。请将 `parallel_tool_calls: false` 设为禁用并行函数调用。
- 通过结构化输出提供的 JSON Schema 不符合[零数据保留](https://platform.openai.com/docs/models/how-we-use-your-data)（ZDR）条件。

## 可用性

结构化输出今天已在 API 中全面可用。

带函数调用的结构化输出在所有支持 API 函数调用的模型上均可用。这包括我们最新的模型（`gpt-4o`、`gpt-4o-mini`）、`gpt-4-0613` 和 `gpt-3.5-turbo-0613` 及之后的所有模型，以及任何支持函数调用的微调模型。该功能可在 Chat Completions API、Assistants API 和 Batch API 上使用。带函数调用的结构化输出也兼容视觉输入。

带响应格式的结构化输出可在 `gpt-4o-mini` 和 `gpt-4o-2024-08-06` 以及基于这些模型的任何微调模型上使用。该功能可在 Chat Completions API、Assistants API 和 Batch API 上使用。带响应格式的结构化输出也兼容视觉输入。

通过切换到新模型 `gpt-4o-2024-08-06`，相比 `gpt-4o-2024-05-13`，开发者在输入上可节省 50%（每百万输入 token 2.50 美元），在输出上可节省 33%（每百万输出 token 10.00 美元）。

要开始使用结构化输出，请查看我们的[文档](https://platform.openai.com/docs/guides/structured-outputs)。
