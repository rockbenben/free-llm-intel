# Netomi 关于将 agentic 系统规模化进入企业的经验

基于 OpenAI GPT‑4.1 与 GPT‑5.2 打造的 Netomi，提供了在企业范围内规模化部署安全、可预测的 agentic 系统的蓝图。

企业期望 AI agent 能可靠地处理混乱的工作流、默认遵守政策、在高负载下运转，并且把工作过程亮出来给人看。

[Netomi⁠⁠（在新窗口中打开）](https://www.netomi.com/) 构建的系统正达到这一高标准，服务着美国联合航空、DraftKings 等财富 500 强客户。其平台将用于低延迟、可靠工具调用的 GPT‑4.1，与用于更深入多步规划的 GPT‑5.2 配对使用，并运行在一个受治理的执行层内，确保模型驱动的动作在真实生产条件下保持可预测。

在这一规模上运行 agentic 系统，让 Netomi 总结出一套让这类部署在企业内部真正运转起来的蓝图。

> "我们的目标是编排人类客服通常要同时应付的众多系统，并以机器速度安全地完成。"

Puneet Mehta，CEO

## 经验一：为真实世界的复杂性而设计，而非理想化流程

企业里的一次请求很少只对应一个 API。真实工作流横跨订票引擎、常旅客数据库、CRM 系统、政策逻辑、支付和知识源，数据往往不完整、相互冲突或有时效性。依赖脆弱流程的系统在这种变化多端之下会崩溃。

Netomi 将其 Agentic OS 设计为：OpenAI 模型居于一条为这种程度的模糊性而建的受治理编排管线中心。平台用 GPT‑4.1 做快速可靠的推理与工具调用——这对实时工作流至关重要——在需要多步规划或更深推理时启用 GPT‑5.2。

为确保 agent 在冗长复杂任务中行为一致，Netomi 遵循 OpenAI 推荐的 agentic 提示词模式：

- **坚持提醒**（Persistence reminders），帮助 GPT‑5.2 在长链路多步工作流中延续推理
- **明确的工具使用预期**，在交易类操作中引导 GPT‑4.1 调用工具获取权威信息，抑制幻觉式回答
- **结构化规划**，借助 GPT‑5.2 更深的推理来勾勒并执行多步任务
- **由 agent 决定的富媒体输出**，依靠 GPT‑5.2 检测并判断何时应让工具调用返回图像、视频、表单等富多模态元素

这些模式共同帮助模型可靠地把非结构化请求映射为多步工作流，并在不连续的交互中维持状态。

很少有行业像航空业这样清晰地暴露出对多步推理的需求：一次客服交互通常横跨多个系统和政策层级。一个简单问题可能要求核查票价规则、重新计算常旅客权益、发起改签，并与航班运行协调。

"在航空业，情境每分钟都在变。AI 必须对顾客所处的场景进行推理——而不只是执行一个孤岛任务，"Mehta 说。"这就是为什么态势感知比单纯的工作流重要得多，也是为什么以上下文为中心的集成架构不可或缺。"

借助 GPT‑4.1 和 GPT‑5.2，Netomi 得以持续把这些模式扩展为更丰富的多步自动化——让模型不只是回答问题，还用于规划任务、编排动作、协调一家大型航空公司所依赖的后端系统。

## 经验二：一切并行化，满足企业级延迟预期

在高压时刻——暴风雨中改签、解决计费纠纷、应对突发流量高峰——用户会抛弃任何迟疑的系统。延迟决定信任。

多数 AI 系统失败在于串行执行任务：分类 → 检索 → 校验 → 调用工具 → 生成输出。Netomi 反其道而行，为并发而设计，充分利用 GPT‑4.1 的低延迟流式输出与稳定的工具调用。

GPT‑4.1 提供快速的首 token 时间和可预测的工具调用行为，使这种架构在规模化下切实可行；GPT‑5.2 则在需要时提供更深的多步推理路径。Netomi 的并发框架确保整个系统——而不仅是模型——保持在关键延迟阈值之内。

这种并发要求并非航空业独有。任何会遭遇突发极端流量洪峰的系统都需要同样的架构纪律。例如 DraftKings 定期对这一模式做压力测试——重大体育赛事期间流量会飙升至每秒超过 40,000 个并发客户请求。

在这类活动期间，即便工作流触及账户、支付、知识查询和监管核查，Netomi 依然保持了 3 秒以内的响应和 98% 的意图分类准确率。

"AI 是我们于最关键时刻服务客户的中心与命脉，"DraftKings 联合创始人兼运营总裁 Paul Liberman 说。"Netomi 的平台帮助我们以敏捷和精准应对海量活动洪峰。"

在规模化场景中，Netomi 的并发模型依赖 GPT‑4.1 快速、可预测的工具调用，使多步工作流在极端负载下保持响应。

## 经验三：让治理成为运行时的内生部分

企业 AI 必须生而可信，治理要直接织入运行时——而不是外加一层。

当意图置信度低于阈值、或请求无法被高置信度分类时，Netomi 的治理机制随即介入，决定如何处理该请求，确保系统从自由生成退让到受控执行路径。

在技术层面，治理层负责：

- **Schema 校验**：在执行前依据预期参数与 OpenAPI 契约校验每一次工具调用
- **政策执行**：在推理与工具调用过程中内联应用主题过滤、品牌限制与合规检查
- **PII 保护**：在预处理和响应处理中检测并遮蔽敏感数据
- **确定性回退**：当意图、数据或工具调用存在歧义时，路由回已知的安全行为
- **运行时可观测性**：暴露 token 轨迹、推理步骤和工具链日志，供实时检查与调试

在牙科保险这类强监管领域，这种治理不容妥协。Netomi 的一家保险业客户每年在全部 50 个州处理近 200 万次医疗服务提供方请求，包括资格核验、福利查询和理赔状态查询——一次错误回答就可能造成下游监管或服务风险。

在公开投保期，审查强度与业务量同时见顶，这家公司需要把政策执行作为运行时本身一部分的 AI。Netomi 的架构经受住了这一复杂要求。

"我们构建系统时，确保 agent 一旦触及不确定，就确切知道如何安全退让，"Mehta 说。"治理不是外挂的——它是运行时的一部分。"

## 一套让 agentic 系统真正服务企业的设计蓝图

Netomi 的路径揭示了赢得企业信任所需的要素：为复杂性而设计、以并行化满足延迟要求、把治理烘焙进每一个工作流。OpenAI 模型构成推理中枢，而 Netomi 的系统工程确保这种智能在运营上安全、可审计，并达到财富 500 强环境的就绪标准。

这些原则帮助 Netomi 在世界上要求最苛刻的一些行业中规模化落地——也为任何想把 agentic AI 变成生产级基础设施的初创公司提供了蓝图。
