## 挑战不在于任务本身，而在于规模

iFood 维护着超过 15,000 个代码仓库。每个仓库都需要定期执行特定任务：验证代码以确保其符合内部标准、修复存在漏洞的依赖项，或运行分析。

这些任务单独来看都不困难。挑战出现在任务数量成倍增加时。

“为一个仓库解决这个问题很容易。挑战在于大规模地解决它，”iFood 高级软件工程师 Victor Coelho 说。“Remote Agents Platform 的设计目标，就是让在全部 15,000 个仓库中大规模解决这一问题成为可能。”

在该平台出现之前，每个团队都以自己的方式应对这个问题——而他们都遇到了同一个障碍。

“以前，我们的解决方案是碎片化的。想象一下，iFood 的多个团队试图解决不同的问题，却没有这一层——这个智能体运行时——可供他们使用。最终，那些解决方案总是遇到同一个问题。”

缺失的并不是智能或用例，而是执行基础设施。一个专用的 *runtime*。

> “团队可以专注于解决业务问题，并把执行委托给我们的平台。”

—Victor Coelho，iFood 高级软件工程师

## 云端编码智能体，可通过 API 访问

团队将 Remote Agents Platform 描述为一个 API，用于启动远程智能体编码任务。该循环包含三个步骤：用户通过 REST 调用提交提示词和环境要求；平台在隔离沙箱内的专用远程运行器上处理任务；之后获取结果。

“平台的入口，也就是它的接口，是一个简单的 REST API。用户可以使用这个 API 创建他们所需的运行。在内部，我们处理并管理整个生命周期，并将执行委托给隔离沙箱，”他解释道。任务进度可以实时监控。

运行器的内部设计在两类不同的步骤之间交替——这种组合使整个工作流具有可预测性。

确定性步骤构成工作流的首尾：开始时克隆仓库、导入智能体可用的 *skills*，并设置工作分支；结束时发布合并请求，并提供生成的产物。中间是智能体执行本身，在沙箱内运行 GPT‑5.6 Luna。

“这是两者的结合：工作流中的确定性步骤与智能体执行。”

沙箱运行 Ubuntu，包含 iFood 生态系统所需的工具链——Python、Java、Kotlin、C#、TypeScript、Rust、JavaScript 和 Go——以及通用工具。在沙箱之外，智能体可以访问 Nexus、GitLab、Docker、Snyk、Kubernetes 和 AWS。

## 为什么选择 GPT‑5.6 Luna

模型选择归结为三个需要综合考虑的因素，而不是只看其中一个。

“我们选择 GPT‑5.6 Luna，是因为在同一 checkpoint 的模型中，基准测试显示它在智能、效率和执行速度——也就是完成任务的速度——之间提供了很好的平衡。这三项特质共同促使我们选择了 GPT‑5.6 Luna。”

对于为规模化而构建的平台，这种平衡比一次性用例更重要。随着数万个 token 被消耗，每次运行平均四美分的成本不再是一个小细节，而成为架构层面的考虑因素。

> “考虑到我们计划在 iFood 的许多用例中扩展该平台，OpenAI 模型所提供的效率与智能平衡，确保我们能够可持续地扩展。”

—Victor Coelho，iFood 高级软件工程师

## 如何判断智能体是否完成了任务

大规模委托执行带来了一个新挑战：自动判断智能体是否完成了它应该完成的工作。

iFood 的答案在会话之后的步骤中。执行完成后，结果会使用 OpenAI 的 Structured Outputs 处理，这要求输出符合预定义契约。

> “我们使用 Structured Outputs 处理结果，这确保响应遵循预定义契约。从智能体会话中，我们可以识别出预期响应结构内的输出。这有助于减少不确定性，并确保我们始终能从智能体会话中获得响应，无论结果是肯定还是否定。”

—Victor Coelho，iFood 高级软件工程师

## 首个主要用户：安全

该平台已经为 iFood 内部安全产品提供支持，该产品会扫描 15,000 个仓库中存在漏洞的依赖项，并尝试修复它们。

迁移产生了直接影响：“借助我们的平台，这些变更、这些修复的准确率提高了一倍以上，”Coelho 说。

这个用例说明了平台背后的理念：安全团队不需要构建自己的智能体运行时，也不需要成为智能体编排专家。它只需要调用一个 API。

## 异步执行把时间还给开发者

团队强调的是异步执行让开发者腾出时间做什么，而不是替代开发者。

由于任务被委托出去并在无人监督下运行，开发者不必持续专注于监控它。

“当他们开会时，可以启动代码修复、性能分析或其他更常规的任务——这些任务可以委托出去，而无需在当时监控它。”

常规工作不再争夺团队的注意力。这就为需要判断力的问题留出了时间。

> “你可以释放这些生产力收益，而不必在工作进行时持续监控。”

—Victor Coelho，iFood 高级软件工程师

## 以启发它的 API 为蓝本

Remote Agents Platform 被设计为一个内部层，其方式类似于 OpenAI 向外部客户提供此类任务。

“Remote Agents Platform 从 OpenAI 的 API 中汲取了很多灵感，包括 Batch API 和 Agents API，后者是更新的 OpenAI 产品。我们构建了一个类似这些产品的平台，但它是 iFood 内部的。”

这种启发不仅停留在概念层面，还延伸到接口设计、资源组织方式，以及异步执行并稍后获取结果的方法。

> “这些产品直接启发了我们构建解决方案的方式。”

—Victor Coelho，iFood 高级软件工程师

## 结果一览

- 平台已完成超过 25,000 项任务，消耗超过 270 亿个 token，平均每次运行成本为 US$0.04。
- 迁移到 Remote Agents Platform 后，内部安全平台修复的准确率和已解决漏洞数量均提高了一倍以上。
- 覆盖范围扩展到 iFood 的超过 15,000 个代码仓库。
- 所有运行均使用 GPT‑5.6 Luna，因其在智能、效率和速度之间的平衡而被选中。
- Structured Outputs 确保每个会话返回的结果都遵循预定义契约，无论结果是肯定还是否定。
- 产品团队已从构建碎片化解决方案转向通过 REST API 委托智能体执行。

## 给领导者的经验

- **瓶颈往往是运行时，而不是用例。** 多个团队已经知道他们想要自动化什么；他们缺少的是一个运行它的环境。
- **将确定性步骤与智能体执行结合。** 克隆、发布和提供产物不需要模型；中间复杂任务才需要。
- **把每次运行成本视为架构决策。** 在规模化场景下，每任务成本决定了哪些工作可行、可以自动化。
- **要求输出遵循契约。** 没有结构化响应，就无法在大规模场景下判断智能体是否达成目标。
- **异步执行才是真正的生产力提升。** 价值在于无需监控工作，而不是一边盯着一边更快完成。

## 建议

- 通过内部 API 暴露智能体能力，让其他团队无需重建基础设施即可使用。
- 将每次运行隔离在各自沙箱中，并预装你的生态系统所需的工具链。
- 选择模型时综合考虑智能、成本和速度，而不是只看单一基准测试。
- 使用结构化输出自动分类成功与失败。
- 从拥有明确痛点和大量需求的内部用户开始——在 iFood，这就是安全平台。

## 下一步

团队计划将该平台推广到 iFood 内更多用例，扩大将智能体执行委托给它的内部产品范围——而每任务成本将决定这种扩展能否持续。
