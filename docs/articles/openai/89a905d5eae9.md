# iFood 如何将编码 agent 推广到 15,000 个代码仓库

Remote Agents Platform 把工程任务变成了 API 调用。团队委派任务，由远程沙箱执行，再以合并请求的形式返回结果。内部安全平台修复的漏洞数量增至原来的两倍以上。

## 挑战在于规模

iFood 维护着超过 15,000 个代码仓库。每个仓库都需要定期完成一些指定工作，例如验证代码是否符合内部标准、修复有漏洞的依赖项，或执行分析任务。

这些工作单独做起来都不难。难点在于任务一多，如何把它们做完。

“处理一个仓库很容易，难的是大规模处理，”iFood 高级软件工程师 Victor Coelho 说，“Remote Agents Platform 的设计目标，就是让我们能在全部 15,000 个仓库中大规模解决这些问题。”

建平台之前，各团队都有自己的办法，最终却都遇到了同一个障碍。

“过去，我们的方案彼此割裂。想象一下，iFood 有多个团队在解决不同的问题，但都缺少这样一层供 agent 使用的运行时。最后，这些方案总会卡在同一个问题上。”

各团队已有模型能力，也有明确的使用场景。它们缺的是执行基础设施，即专用的*运行时*。

> “团队可以专心解决业务问题，把执行交给我们的平台。”

——iFood 高级软件工程师 Victor Coelho

## 通过 API 使用云端编码 agent

团队把 Remote Agents Platform 描述为用于启动远程编码 agent 任务的 API。一次任务分三步。用户通过 REST 调用提交提示词和环境要求，平台在隔离沙箱内的专用远程 runner 上处理任务，之后再获取结果。

他解释道：“平台的入口，也就是它的接口，是一个简单的 REST API。用户可以用它按需创建运行任务。平台在内部管理运行的整个生命周期，并把执行委派给隔离的沙箱。”用户可以实时查看任务进度。

runner 内部把两类步骤穿插在一起，让整个工作流程可预测。

开头和结尾都是确定性步骤。开头克隆仓库、导入 agent 可用的 *skills*、准备工作分支，结尾发布合并请求并提供生成的产物。中间由 agent 执行任务，在沙箱中运行 GPT‑5.6 Luna。

“工作流结合了这两类步骤，既有确定性步骤，也有 agent 执行。”

沙箱使用 Ubuntu，配备 iFood 生态所需的 Python、Java、Kotlin、C#、TypeScript、Rust、JavaScript 和 Go 工具链，以及通用工具。沙箱之外，agent 可以访问 Nexus、GitLab、Docker、Snyk、Kubernetes 和 AWS。

## 为什么选用 GPT‑5.6 Luna

选型时，团队一并权衡了三个因素。

“我们选择 GPT‑5.6 Luna，是因为基准测试显示，在同一 checkpoint 的模型中，它很好地平衡了智能、效率和执行速度，也就是它完成任务的快慢。综合这三点，我们选择了 GPT‑5.6 Luna。”

对于要规模化运行的平台，这种平衡比一次性的应用场景更重要。当运行消耗的 token 数达到数万时，每次平均 4 美分的成本就成了架构设计中的考虑因素。

> “我们计划让平台覆盖 iFood 的多种使用场景。OpenAI 模型在效率和智能之间取得的平衡，让我们能够持续扩大使用规模。”

——iFood 高级软件工程师 Victor Coelho

## 如何判断 agent 是否完成了任务

大规模委派执行也带来了一个新问题，平台需要自动判断 agent 是否完成了交办的工作。

iFood 在会话结束后的步骤中解决这个问题。执行完毕后，平台用 OpenAI 的 Structured Outputs 处理结果，要求输出符合预先定义的契约。

> “我们用 Structured Outputs 处理结果，确保响应遵循预定义的契约。我们可以在预期的响应结构里识别出这次 agent 会话的输出。这样可以减少不确定性，确保无论成功还是失败，agent 的会话总会给出响应。”

——iFood 高级软件工程师 Victor Coelho

## 首个大规模应用来自安全团队

平台已经为 iFood 的一款内部安全产品提供支持。该产品扫描 15,000 个代码仓库里有漏洞的依赖项，并尝试修复。

迁移带来了直接成效。Coelho 说：“用了我们的平台后，这些变更，也就是这些修复，准确率提高到了原来的两倍以上。”

这个用例说明了平台的设计初衷。安全团队只需调用 API，就能使用相应能力，无需自行开发 agent 运行时或掌握 agent 编排。

## 异步执行让开发者腾出时间

团队强调，异步执行的价值在于解放开发者的时间，开发者可以腾出手来处理其他工作。

任务委派后可以自行运行，开发者不用一直盯着进度。

“比如开会时，他们可以发起代码修复、性能分析，或其他相对常规的任务。这些任务可以委派出去，当时用不着盯着。”

例行工作不再占用团队的注意力，团队也就有时间处理需要判断力的问题。

> “这些效率收益可以拿到，用不着在工作进行的同时盯全过程。”

——iFood 高级软件工程师 Victor Coelho

## 借鉴 OpenAI API 的设计

Remote Agents Platform 是 iFood 为内部使用设计的一层基础设施。OpenAI 向外部客户提供这类任务能力的方式，是它的参考。

“Remote Agents Platform 从 OpenAI 的 API 得到了很多启发，包括 Batch API 和 OpenAI 较新推出的 Agents API。我们做了一个类似的平台，供 iFood 内部使用。”

团队借鉴了这些 API 的理念，也借鉴了接口设计、资源组织方式和异步执行后再取回结果的做法。

> “我们构建这套方案时，直接借鉴了这些产品。”

——iFood 高级软件工程师 Victor Coelho

## 成效一览

- 平台已完成超过 25,000 项任务，消耗超过 270 亿 token，每次运行的平均成本为 0.04 美元。
- 迁移到 Remote Agents Platform 后，内部安全平台的修复准确率和修复的漏洞数量均增至原来的两倍以上。
- 覆盖 iFood 超过 15,000 个代码仓库。
- 所有任务均使用 GPT‑5.6 Luna。选用该模型是为了兼顾智能、效率和速度。
- Structured Outputs 确保每次会话都返回符合预定义契约的结果，无论成功还是失败。
- 各产品团队过去各自搭建方案，现在通过 REST API 委派 agent 执行任务。

## 给团队负责人的经验

- **常见瓶颈在运行时。** 好几个团队已经知道要自动化哪些工作，缺的是运行这些工作的环境。
- **把确定性步骤与 agent 执行结合起来。** 克隆仓库、发布结果和提供产物可以交给固定流程，中间的复杂任务则需要模型。
- **把单次运行成本纳入架构决策。** 大规模运行时，单次任务的成本会决定哪些工作能够自动化。
- **要求输出遵守契约。** 只有具备结构化响应，才能大规模判断 agent 是否达成了目标。
- **异步执行让人腾出时间，生产力提升体现在这里。** 它的价值在于人可以去做别的事，无需全程盯着任务。

## 建议

- 通过内部 API 提供 agent 能力，让其他团队可以直接使用，无需重建基础设施。
- 在各自独立的沙箱中运行任务，并预装组织所用的工具链。
- 选择模型时综合考虑智能、成本和速度，避免由某项基准测试单独决定。
- 使用结构化输出自动判断成功或失败。
- 先从有明确痛点、任务量大的内部用户做起。iFood 选择的是安全平台。

## 后续计划

团队计划把平台推广到 iFood 内更多场景，让更多内部产品可以委派 agent 执行任务。能否持续扩大使用范围，取决于单次任务的成本。
